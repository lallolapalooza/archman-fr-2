NOM

podman-run - Exécute une commande dans un nouveau conteneur

SYNOPIS

podman run [options] image [commande [arg ...]]

podman container run [options] image [commande [arg ...]]

DESCRIPTION

Exécute un processus dans un nouveau conteneur. podman run démarre un processus avec son propre système de fichiers, son propre réseau et son propre arbre de processus isolé. L'image qui démarre le processus peut définir des valeurs par défaut relatives au processus qui sera exécuté dans le conteneur, au réseau à exposer, et plus encore, mais podman run donne le contrôle final à l'opérateur ou à l'administrateur qui démarre le conteneur à partir de l'image. Pour cette raison, podman run a plus d'options que toute autre commande Podman.

Si l'image n'est pas déjà chargée, alors podman run téléchargera l'image, ainsi que toutes ses dépendances, depuis le dépôt, de la même manière que l'exécution de podman pull image, avant de démarrer le conteneur à partir de cette image.

Plusieurs fichiers seront automatiquement créés dans le conteneur. Ceux-ci incluent /etc/hosts, /etc/hostname, et /etc/resolv.conf pour gérer le réseau. Ceux-ci seront basés sur la version hôte de ces fichiers, bien qu'ils puissent être personnalisés avec des options (par exemple, --dns peut remplacer les serveurs DNS de l'hôte dans le fichier resolv.conf créé). De plus, un fichier d'environnement du conteneur est créé dans chaque conteneur pour indiquer aux programmes qu'ils s'exécutent dans un conteneur. Ce fichier est situé à l'adresse /run/.containerenv (ou /var/run/.containerenv pour les conteneurs FreeBSD). Lors de l'utilisation du drapeau --privileged, le fichier .containerenv contient des paires nom/valeur indiquant la version du moteur de conteneur, si le moteur est en cours d'exécution en mode sans privilèges (rootless), le nom et l'ID du conteneur, ainsi que le nom et l'ID de l'image sur laquelle le conteneur est basé. Remarque : /run/.containerenv ne sera pas créé lorsqu'un volume est monté sur /run.

Lors de l'exécution à partir d'un espace de noms réseau défini par l'utilisateur, le fichier /etc/netns/NSNAME/resolv.conf sera utilisé s'il existe, sinon /etc/resolv.conf sera utilisé.

Les paramètres par défaut sont définis dans containers.conf. La plupart des paramètres pour les connexions distantes utilisent le fichier containers.conf des serveurs, sauf lorsqu'il est documenté dans les pages de manuel.

IMAGE

L'image est spécifiée en utilisant le format transport:chemin. Si aucun transport n'est spécifié, le transport docker (registre de conteneur) est utilisé par défaut. Pour les Podman distants, y compris les machines Mac et Windows (à l'exclusion de WSL2), docker est le seul transport autorisé.

dir:chemin
Un répertoire local existant chemin stockant le manifeste, les archives de couches et les signatures sous forme de fichiers individuels. Il s'agit d'un format non standardisé, principalement utile pour le débogage ou l'inspection non invasive de conteneurs.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman run dir:/tmp/fedora echo hello

docker://référence-docker (Défaut)
Une référence d'image stockée dans un registre d'images de conteneurs distant. Exemple : "quay.io/podman/stable:latest". La référence peut inclure un chemin vers un registre spécifique ; si ce n'est pas le cas, les registres listés dans registries.conf sont interrogés pour trouver une image correspondante. Par défaut, les identifiants de podman login (stockés par défaut à ${XDG_RUNTIME_DIR}/containers/auth.json) sont utilisés pour l'authentification ; sinon, il se rabat sur les identifiants dans $HOME/.docker/config.json.

$ podman run registry.fedoraproject.org/fedora:latest echo hello

docker-archive:chemin[:référence-docker] Une image stockée dans le fichier formaté docker save. référence-docker est uniquement utilisé lors de la création d'un tel fichier, et il ne doit pas contenir de digest.

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman run docker-archive:/tmp/fedora echo hello

Remarque : Sur les clients distants, y compris les machines Mac et Windows (à l'exclusion de WSL2), ce transport n'est pas pris en charge.

docker-daemon:référence-docker
Une image au format référence-docker stockée dans le stockage interne du démon docker. La référence-docker peut également être un ID d'image (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman run docker-daemon:docker.io/library/fedora echo hello

Remarque : Sur les clients distants, y compris les machines Mac et Windows (à l'exclusion de WSL2), ce transport n'est pas pris en charge.

oci-archive:chemin:tag
Une image dans un répertoire conforme à la "spécification de mise en page des images de conteneurs ouverts" au chemin spécifié et identifiée par un tag.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman run oci-archive:/tmp/fedora echo hello

Remarque : Sur les clients distants, y compris les machines Mac et Windows (à l'exclusion de WSL2), ce transport n'est pas pris en charge.

OPTIONS

--add-host=nomhôte[;nomhôte[;...]]:ip

Ajoute un mappage hôte-IP personnalisé au fichier /etc/hosts du conteneur.

L'option prend un ou plusieurs noms d'hôtes séparés par des points-virgules à mapper à une seule adresse IPv4 ou IPv6, séparée par un deux-points. Elle peut également être utilisée pour remplacer les adresses IP des noms d'hôtes que Podman ajoute par défaut à /etc/hosts (voir également les options --name et --hostname). Cette option peut être spécifiée plusieurs fois pour ajouter des mappages supplémentaires à /etc/hosts. Elle entre en conflit avec l'option --no-hosts et avec no_hosts=true dans containers.conf.

Au lieu d'une adresse IP, le drapeau spécial host-gateway peut être donné. Cela se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Podman puisse déterminer automatiquement l'adresse host-gateway, ce qui provoquera alors une erreur de Podman. Vous pouvez remplacer cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Podman pour ajouter automatiquement les noms d'hôtes host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez empêcher cela en donnant l'option --no-hosts, ou en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Podman ne parvient pas à déterminer automatiquement l'adresse IP, Podman omettra silencieusement d'ajouter ces noms d'hôtes internes à /etc/hosts. Si Podman s'exécute dans une machine virtuelle utilisant podman machine (cela inclut les hôtes Mac et Windows), Podman omettra silencieusement d'ajouter les noms d'hôtes internes à /etc/hosts, sauf si une adresse IP a été configurée manuellement ; les noms d'hôtes internes sont résolus par le résolveur DNS gvproxy à la place.

Podman utilisera par défaut le fichier /etc/hosts de l'hôte comme base, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré en utilisant la configuration base_hosts_file dans containers.conf.

--annotation=clé=valeur

Ajoute une annotation au conteneur. Cette option peut être définie plusieurs fois.

--arch=ARCH

Remplace l'architecture, par défaut celle de l'hôte, de l'image à télécharger. Par exemple, arm. Sauf remplacement, les recherches ultérieures de la même image dans le stockage local correspondent à cette architecture, indépendamment de l'hôte.

--attach, -a=stdin | stdout | stderr

Se connecte à STDIN, STDOUT ou STDERR.

En mode avant (par défaut lorsque -d n'est pas spécifié), podman run peut démarrer le processus dans le conteneur et attacher la console à l'entrée, la sortie et l'erreur standard du processus. Il peut même faire semblant d'être un TTY (ce que la plupart des exécutables en ligne de commande attendent) et transmettre les signaux. L'option -a peut être définie pour chacun des stdin, stdout et stderr.

--blkio-weight=poids

Poids relatif de l'IO de bloc. Le poids est une valeur comprise entre 10 et 1000.

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif de l'IO de bloc par périphérique.

--cap-add=capacité

Ajouter des capacités Linux.

L'octroi de capacités supplémentaires augmente les privilèges des processus s'exécutant dans le conteneur et peut potentiellement lui permettre de s'échapper de son confinement. Les capacités telles que CAP_SYS_ADMIN, CAP_SYS_PTRACE, CAP_MKNOD et CAP_SYS_MODULE sont particulièrement dangereuses lorsqu'elles ne sont pas utilisées dans un espace de noms utilisateur. Veuillez vous référer à user_namespaces(7) pour une explication plus détaillée de l'interaction entre les espaces de noms utilisateur et les capacités.

Avant d'ajouter une capacité, examinez ses implications en matière de sécurité et assurez-vous qu'elle est réellement nécessaire pour la fonctionnalité du conteneur. Voir capabilities(7) pour plus d'informations.

--cap-drop=capacité

Supprimer les capacités Linux.

--cert-dir=chemin

Utiliser les certificats dans chemin (*.crt, *.cert, *.key) pour se connecter au registre. (Par défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exclusion de WSL2))

--cgroup-conf=CLÉ=VALEUR

Lors de l'exécution sur cgroup v2, spécifiez le fichier cgroup dans lequel écrire et sa valeur. Par exemple, --cgroup-conf=memory.high=1073741824 définit la limite memory.high à 1 Go.

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup pour le conteneur est créé. Si le chemin n'est pas absolu, le chemin est considéré comme relatif au chemin des cgroups du processus init. Les cgroups sont créés s'ils n'existent pas déjà.

--cgroupns=mode

Définir le mode de l'espace de noms cgroup pour le conteneur.

  • host : utiliser l'espace de noms cgroup de l'hôte dans le conteneur.
  • container:id : rejoindre l'espace de noms du conteneur spécifié.
  • private : créer un nouvel espace de noms cgroup.
  • ns:chemin : rejoindre l'espace de noms au chemin spécifié.

Si l'hôte utilise cgroups v1, la valeur par défaut est définie sur host. Sur cgroups v2, la valeur par défaut est private.

--cgroups=comment

Détermine si le conteneur crée des cgroups.

La valeur par défaut est enabled.

L'option enabled crée un nouveau cgroup sous le cgroup-parent. L'option disabled force le conteneur à ne pas créer de cgroups, et entre donc en conflit avec les options de cgroup (--cgroupns et --cgroup-parent). L'option no-conmon désactive un nouveau cgroup uniquement pour le processus conmon. L'option split divise le cgroup actuel en deux sous-cgroups : un pour conmon et un pour la charge utile du conteneur. Il n'est pas possible de définir --cgroup-parent avec split.

--chrootdirs=chemin

Chemin vers un répertoire à l'intérieur du conteneur qui est traité comme un répertoire chroot. Tout fichier géré par Podman (par exemple, /etc/resolv.conf, /etc/hosts, /etc/hostname) qui est monté dans le répertoire racine est également monté à cet emplacement. Plusieurs répertoires sont séparés par une virgule.

--cidfile=fichier

Écrire l'ID du conteneur dans fichier. Le fichier est supprimé avec le conteneur, sauf lorsqu'il est utilisé avec podman --remote run sur des conteneurs détachés.

--conmon-pidfile=fichier

Écrire le PID du processus conmon dans un fichier. Comme conmon s'exécute dans un processus séparé de Podman, ceci est nécessaire lors de l'utilisation de systemd pour redémarrer les conteneurs Podman. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exclusion de WSL2))

--cpu-period=limite

Définir la période CPU pour le Completely Fair Scheduler (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié pour s'exécuter avant la fin de la période actuelle. La valeur par défaut est de 100000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpu-quota=limite

Limiter le quota du Completely Fair Scheduler (CFS) CPU.

Limiter l'utilisation du CPU par le conteneur. Par défaut, les conteneurs s'exécutent avec la totalité des ressources CPU. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser cette quantité de temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpu-rt-period=microsecondes

Limiter la période temps réel du CPU en microsecondes.

Limiter l'utilisation du CPU temps réel du conteneur. Cette option indique au noyau de restreindre l'utilisation du CPU temps réel du conteneur à la période spécifiée.

Cette option n'est prise en charge que sur les systèmes rootful cgroups V1.

--cpu-rt-runtime=microsecondes

Limiter le temps d'exécution temps réel du CPU en microsecondes.

Limiter l'utilisation du CPU temps réel des conteneurs. Cette option indique au noyau de limiter la quantité de temps qu'une tâche temps réel peut consommer au cours d'une période CPU donnée. Ex : Une période de 1 000 000 us et un temps d'exécution de 950 000 us signifie que ce conteneur peut consommer 95% du CPU disponible et laisser les 5% restants aux tâches de priorité normale.

La somme de tous les temps d'exécution entre les conteneurs ne peut pas dépasser la quantité allouée au cgroup parent.

Cette option n'est prise en charge que sur les systèmes rootful cgroups V1.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est de 1024.

La proportion ne s'applique que lorsque des processus gourmands en CPU s'exécutent. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, l'un ayant une part CPU de 1024 et les deux autres un réglage de part CPU de 512. Lorsque les processus dans les trois conteneurs tentent d'utiliser 100% du CPU, le premier conteneur reçoit 50% du temps CPU total. Si un quatrième conteneur est ajouté avec une part CPU de 1024, le premier conteneur n'obtient que 33% du CPU. Les conteneurs restants reçoivent respectivement 16,5%, 16,5% et 33% du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont réparties sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut utiliser 100% de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est lancé avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la division suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100% de CPU0
101 C1 1 100% de CPU1
102 C1 2 100% de CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpus=nombre

Nombre de CPUs. La valeur par défaut est 0.0, ce qui signifie aucune limite. C'est un raccourci pour --cpu-period et --cpu-quota, par conséquent, l'option ne peut pas être spécifiée avec --cpu-period ou --cpu-quota.

Sur certains systèmes, la modification des limites CPU peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par exemple, 0,1), sous forme de plage (par exemple, 0-3), ou toute combinaison de ceux-ci (par exemple, 0-3,7,11-15

).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--cpuset-mems=nœuds

Nœuds de mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Efficace uniquement sur les systèmes NUMA.

S'il y a quatre nœuds de mémoire sur le système (0-3), utilisez --cpuset-mems=0,1 puis les processus du conteneur n'utiliseront que la mémoire des deux premiers nœuds de mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--creds=[nom_utilisateur[:mot_de_passe]]

Le [nom_utilisateur[:mot_de_passe]] à utiliser pour s'authentifier auprès du registre, si nécessaire. Si une ou les deux valeurs ne sont pas fournies, une invite de commande apparaît et la valeur peut être saisie. Le mot de passe est saisi sans écho.

Notez que les identifiants spécifiés sont uniquement utilisés pour s'authentifier auprès des registres cibles. Ils ne sont pas utilisés pour les miroirs ou lorsque le registre est réécrit (voir containers-registries.conf(5)); pour s'authentifier auprès de ceux-ci, envisagez d'utiliser un fichier containers-auth.json(5).

--decryption-key=clé[:phrase_secrète]

La [clé[:phrase_secrète]] à utiliser pour le déchiffrement des images. La clé peut pointer vers des clés et/ou des certificats. Le déchiffrement est tenté avec toutes les clés. Si la clé est protégée par une phrase secrète, il est obligatoire de la passer dans l'argument et de l'omettre sinon.

--detach, -d

Mode détaché : exécute le conteneur en arrière-plan et affiche le nouvel ID de conteneur. La valeur par défaut est false.

À tout moment, exécutez podman ps dans l'autre terminal pour afficher la liste des conteneurs en cours d'exécution. Rattachez-vous à un conteneur détaché avec la commande podman attach.

Lorsque vous êtes attaché via le mode tty, détachez-vous du conteneur (et laissez-le en cours d'exécution) en utilisant une séquence de touches configurable. La séquence par défaut est ctrl-p,ctrl-q. Spécifiez la séquence de touches en utilisant l'option --detach-keys, ou configurez-la dans le fichier containers.conf : voir containers.conf(5) pour plus d'informations.

--detach-keys=séquence

Spécifie la séquence de touches pour détacher un conteneur. Le format est un seul caractère [a-Z] ou un ou plusieurs caractères ctrl-<valeur> où <valeur> est l'un des suivants : a-z, @, ^, [, , ou _. Spécifier "" désactive cette fonctionnalité. La valeur par défaut est ctrl-p,ctrl-q.

Cette option peut également être définie dans le fichier containers.conf(5).

--device=périphérique_hote[:périphérique_conteneur][:permissions]

Ajoute un périphérique hôte au conteneur. Le paramètre facultatif permissions peut être utilisé pour spécifier les permissions du périphérique en combinant r pour lecture, w pour écriture, et m pour mknod(2).

Exemple : --device=/dev/sdc:/dev/xvdc:rwm.

Note : si périphérique_hote est un lien symbolique, il est d'abord résolu. Le conteneur ne stocke que les numéros majeurs et mineurs du périphérique hôte.

Podman peut charger les modules de noyau requis pour utiliser le périphérique spécifié. Les périphériques pour lesquels Podman charge des modules lorsque nécessaire sont : /dev/fuse.

En mode sans root, le nouveau périphérique est monté en bind dans le conteneur depuis l'hôte plutôt que Podman ne le crée dans l'espace du conteneur. Comme le montage bind conserve son étiquette SELinux sur les systèmes SELinux, le conteneur peut obtenir une erreur d'autorisation lors de l'accès au périphérique monté. Modifiez les paramètres SELinux pour autoriser les conteneurs à utiliser toutes les étiquettes de périphérique via la commande suivante :

$ sudo setsebool -P container_use_devices=true

Note : si l'utilisateur n'a accès que via un groupe, l'accès au périphérique depuis l'intérieur d'un conteneur sans root échoue. Utilisez l'option --group-add keep-groups pour transmettre les accès aux groupes supplémentaires de l'utilisateur au conteneur.

--device-cgroup-rule="type major:minor mode"

Ajoute une règle à la liste des périphériques autorisés de cgroup. La règle est attendue dans le format spécifié dans la documentation du noyau Linux admin-guide/cgroup-v1/devices : - type : a (tout), c (caractère) ou b (bloc) ; - major et minor : soit un nombre, soit * pour tout ; - mode : une composition de r (lecture), w (écriture) et m (mknod(2)).

--device-read-bps=chemin:débit

Limite le débit de lecture (en octets par seconde) d'un périphérique (par exemple, --device-read-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--device-read-iops=chemin:débit

Limite le débit de lecture (en opérations d'E/S par seconde) d'un périphérique (par exemple, --device-read-iops=/dev/sda:1000).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--device-write-bps=chemin:débit

Limite le débit d'écriture (en octets par seconde) vers un périphérique (par exemple, --device-write-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Action to take once the container transitions to an unhealthy state. The default is none.

  • none: Take no action.
  • kill: Kill the container.
  • restart: Restart the container. Do not combine the restart action with the --restart flag. When running inside of a systemd unit, consider using the kill or stop action instead to make use of systemd's restart policy.
  • stop: Stop the container.

The number of retries allowed before a healthcheck is considered to be unhealthy. The default value is 3.

The initialization time needed for a container to bootstrap. The value can be expressed in time format like 2m3s. The default value is 0s.

Note: The health check command is executed as soon as a container is started, if the health check is successful the container's health state will be updated to healthy. However, if the health check fails, the health state will stay as starting until either the health check is successful or until the --health-start-period time is over. If the health check command fails after the --health-start-period time is over, the health state will be updated to unhealthy. Note: This parameter will overwrite related healthcheck configuration from the image.

--health-startup-cmd="command" | '["command", arg1 , ...]'

Set a startup healthcheck command for a container. This command is executed inside the container and is used to gate the regular healthcheck. When the startup command succeeds, the regular healthcheck begins and the startup healthcheck ceases. Optionally, if the command fails for a set number of attempts, the container is restarted. A startup healthcheck can be used to ensure that containers with an extended startup period are not marked as unhealthy until they are fully started. Startup healthchecks can only be used when a regular healthcheck (from the container's image or the --health-cmd option) is also set.

--health-startup-interval=interval

Set an interval for the startup healthcheck. An interval of disable results in no automatic timer setup. The default is 30s.

--health-startup-retries=retries

The number of attempts allowed before the startup healthcheck restarts the container. If set to 0, the container is never restarted. The default is 0.

--health-startup-success=retries

The number of successful runs required before the startup healthcheck succeeds and the regular healthcheck begins. A value of 0 means that any success begins the regular healthcheck. The default is 0.

--health-startup-timeout=timeout

The maximum time a startup healthcheck command has to complete before it is marked as failed. The value can be expressed in a time format like 2m3s. The default value is 30s.

--health-timeout=timeout

The maximum time allowed to complete the healthcheck before an interval is considered failed. Like start-period, the value can be expressed in a time format such as 1m22s. The default value is 30s.

Note: A timeout marks the healthcheck as failed. If the healthcheck command itself runs longer than the specified timeout, it will be sent a SIGKILL signal.

--mount=type=TYPE,OPTION-SPÉCIFIQUE-TYPE[,...]

Attacher un montage de système de fichiers au conteneur.

Les TYPEs de montage actuellement pris en charge sont artifact, bind, devpts, glob, image, ramfs, tmpfs et volume.

Opti

communs à tous les types de montage :

  • src, source : spécification de la source de montage pour bind, glob et volume. Obligatoire pour artifact, bind, glob, image et volume.
  • dst, dest, destination, target : spécification de la destination de montage.

Lorsque des globes sources sont spécifiés sans le répertoire de destination, les fichiers et répertoires sont montés avec leur chemin complet dans le conteneur. Lorsque la destination est spécifiée, les fichiers et répertoires correspondant au globe sur le nom de fichier de base dans le répertoire de destination sont montés. L'option type=glob,src=/foo*,destination=/tmp/bar indique aux moteurs de conteneur de monter les fichiers hôtes correspondant à /foo* dans le répertoire /tmp/bar/ du conteneur.

Options spécifiques au type=artifact :

  • digest : Si la source de l'artefact contient plusieurs blobs, un digest peut être spécifié pour ne monter que le blob spécifique avec ce digest.
  • title : Si la source de l'artefact contient plusieurs blobs, un titre peut être défini et comparé à l'annotation org.opencontainers.image.title.
  • name : Ceci peut être utilisé pour remplacer le nom de fichier que nous utilisons à l'intérieur du conteneur pour le montage. Sur un artefact à blob unique, le nom est utilisé tel quel si dst est un répertoire et ignoré sinon. Avec un artefact à plusieurs blobs, le nom sera utilisé avec un suffixe d'index <nom>-x où x est l'index de couche dans l'artefact en commençant par 0.

L'argument src contient le nom de l'artefact, qui doit déjà exister localement. L'argument dst contient le chemin cible ; si le chemin dans le conteneur est un répertoire, le titre du blob (annotation org.opencontainers.image.title) sera utilisé comme nom de fichier et joint au chemin. Si l'annotation n'existe pas, le digest sera utilisé comme nom de fichier à la place. Il en résulte que tous les blobs de l'artefact sont montés dans le conteneur au chemin donné.

Cependant, si le chemin dst est un fichier existant dans le conteneur, le blob sera monté directement dessus. Cela ne fonctionne que lorsque l'artefact contient un seul blob ou lorsque digest ou title sont spécifiés.

Si le chemin dst n'existe pas encore dans le conteneur, alors si l'artefact contient un seul blob, il se comporte comme dans le cas du fichier existant et monte directement sur ce chemin. Si l'artefact a plus d'un blob, il se comporte comme dans le cas du répertoire existant et monte chaque blob comme un fichier dans le chemin dst.

Options spécifiques au type=volume :

  • ro, readonly : true ou false (défaut si non spécifié : false).
  • U, chown : true ou false (défaut si non spécifié : false). Modifie récursivement le propriétaire et le groupe du volume source en fonction de l'UID et du GID du conteneur.
  • subpath : Monte seulement un sous-chemin spécifique à l'intérieur du volume, au lieu du volume entier.
  • idmap : Si spécifié, crée un montage mappé sur l'espace de noms d'utilisateur cible dans le conteneur. L'option idmap n'est prise en charge que par Podman en mode rootful. Le noyau Linux n'autorise pas l'utilisation de systèmes de fichiers mappés pour les utilisateurs non privilégiés. L'option idmap prend en charge un mappage personnalisé qui peut être différent de l'espace de noms utilisateur utilisé par le conteneur. Le mappage peut être spécifié après l'option idmap, par exemple : idmap=uids=0-1-10#10-11-10;gids=0-100-10. Pour chaque triplet, la première valeur est le début des identifiants du système de fichiers sous-jacent qui sont mappés sur la deuxième valeur sur l'hôte. La longueur de ce mappage est donnée dans la troisième valeur. Plusieurs plages sont séparées par #. Si le mappage spécifié est précédé d'un '@', alors le mappage est considéré comme relatif à l'espace de noms utilisateur du conteneur. L'ID hôte du mappage est modifié pour tenir compte de la position relative de l'utilisateur du conteneur dans l'espace de noms utilisateur du conteneur.

Options spécifiques au type=image :

  • rw, readwrite : true ou false (défaut si non spécifié : false).
  • subpath : Monte seulement un chemin spécifique à l'intérieur de l'image, au lieu de l'image entière.

Options spécifiques à bind et glob :

  • ro, readonly : true ou false (défaut si non spécifié : false).
  • bind-propagation : shared, slave, private, unbindable, rshared, rslave, runbindable, ou rprivate (défaut).[1] ⟨#Footnote1⟩ Voir aussi mount(2).
  • bind-nonrecursive : ne pas configurer de montage bind récursif. Par défaut, il est récursif.
  • relabel : shared, private.
  • idmap : true ou false (défaut si non spécifié : false). Si vrai, crée un montage mappé sur l'espace de noms d'utilisateur cible dans le conteneur. L'option idmap n'est prise en charge que par Podman en mode rootful.
  • U, chown : true ou false (défaut si non spécifié : false). Modifie récursivement le propriétaire et le groupe du volume source en fonction de l'UID et du GID du conteneur.
  • no-dereference : ne pas déréférencer les liens symboliques mais copier la source du lien dans la destination du montage.

Options spécifiques à type=tmpfs et ramfs :

  • ro, readonly : true ou false (défaut si non spécifié : false).
  • tmpfs-size : Taille du montage tmpfs/ramfs, en octets. Illimitée par défaut sous Linux.
  • tmpfs-mode : Mode de fichier octal du tmpfs/ramfs (par exemple, 700 ou 0700).
  • tmpcopyup : Active la copie depuis le répertoire de l'image à l'emplacement correspondant vers le tmpfs/ramfs. Utilisé par défaut.
  • noatime : Désactive la mise à jour des heures d'accès aux fichiers lors de la lecture du fichier.
  • notmpcopyup : Désactive la copie des fichiers depuis l'image vers le tmpfs/ramfs.
  • U, chown : true ou false (défaut si non spécifié : false). Modifie récursivement le propriétaire et le groupe du volume source en fonction de l'UID et du GID du conteneur.

Options spécifiques au type=devpts :

  • uid : UID numérique du propriétaire du fichier (défaut : 0).
  • gid : GID numérique du propriétaire du fichier (défaut : 0).
  • mode : masque de permission octal pour le fichier (défaut : 600).
  • max : nombre maximum de PTY (défaut : 1048576).

Exemples :

  • type=bind,source=/path/on/host,destination=/path/in/container
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared,U=true
  • type=devpts,destination=/dev/pts
  • type=glob,src=/usr/lib/libfoo*,destination=/usr/lib,ro=true
  • type=image,source=fedora,destination=/fedora-image,rw=true
  • type=ramfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,destination=/path/in/container,noswap
  • type=artifact,src=quay.io/libpod/testartifact:20250206-single,dst=/data
  • type=artifact,src=quay.io/libpod/testartifact:20250206-multi,dst=/data,title=test1
  • type=volume,src=test_vol,dst=/data,subpath=/code/docs

--name=name

Attribue un nom au conteneur.

L'opérateur peut identifier un conteneur de trois manières :

  • Identifiant long UUID (“f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778”) ;
  • Identifiant court UUID (“f78375b1c487”) ;
  • Nom (“jonah”).

Podman génère un UUID pour chaque conteneur et, si aucun nom n'est attribué au conteneur à l'aide de --name, Podman génère un nom de chaîne aléatoire. Le nom peut être utile comme moyen plus convivial d'identifier les conteneurs. Cela fonctionne pour les conteneurs en arrière-plan et en premier plan. Le nom du conteneur est également ajouté au fichier /etc/hosts à l'aide de l'adresse IP principale du conteneur (voir également l'option --add-host).

--network=mode, --net

Définit le mode réseau pour le conteneur.

Les valeurs valides pour mode sont :

•
bridge[:OPTIONS,...] : Crée une pile réseau sur le pont par défaut. C'est le défaut pour les conteneurs rootful. Il est possible de spécifier ces options supplémentaires :
  • alias=name : Ajoute un alias à portée réseau pour le conteneur.
  • ip=IPv4 : Spécifie une adresse IPv4 statique pour ce conteneur.
  • ip6=IPv6 : Spécifie une adresse IPv6 statique pour ce conteneur.
  • mac=MAC : Spécifie une adresse MAC statique pour ce conteneur.
  • interface_name=name : Spécifie un nom pour l'interface réseau créée à l'intérieur du conteneur.
  • host_interface_name=name : Spécifie un nom pour l'interface réseau créée à l'extérieur du conteneur.
Toute autre option sera transmise à netavark sans validation. Cela peut être utile pour passer des arguments aux plugins netavark.

Par exemple, pour définir une adresse IPv4 statique et une adresse MAC statique, utilisez --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <network name or ID>[:OPTIONS,...] : Connexion à un réseau défini par l'utilisateur ; c'est le nom ou l'ID du réseau créé par podman network create. Il est possible de spécifier les mêmes options décrites sous le mode bridge ci-dessus. Utilisez l'option --network plusieurs fois pour spécifier des réseaux supplémentaires.
    Pour des raisons de compatibilité ascendante, il est également possible de spécifier des réseaux séparés par des virgules dans le premier argument --network, mais cela vous empêche d'utiliser les options décrites dans la section bridge ci-dessus.
  • none : Crée un espace de noms réseau pour le conteneur mais ne configure pas d'interfaces réseau pour celui-ci, le conteneur n'a donc pas de connectivité réseau.
  • container:id : Réutilise la pile réseau d'un autre conteneur.
  • host : Utilise l'espace de noms réseau de l'hôte pour le conteneur au lieu d'en créer un isolé. Avertissement : Cela donne au conteneur un accès complet aux sockets Unix abstraits et aux sockets TCP/UDP liés à localhost. Étant donné que ces mécanismes sont souvent utilisés pour empêcher l'accès à des services système sensibles, en les isolant de l'accès par des entités externes, l'utilisation de cette option peut être considérée comme une vulnérabilité de sécurité.
  • ns:path : Chemin vers un espace de noms réseau à j
oin.
  • private : Crée un nouvel espace de noms pour le conteneur. Cela utilise le mode bridge pour les conteneurs rootful et slirp4netns pour les conteneurs rootless.
  • slirp4netns[:OPTIONS,...] : Utilise slirp4netns(1) pour créer une pile réseau utilisateur. Il est possible de spécifier ces options supplémentaires, elles peuvent également être définies avec network_cmd_options dans containers.conf :
    • allow_host_loopback=true|false : Autorise slirp4netns à atteindre la IP de bouclage de l'hôte (par défaut 10.0.2.2 ou la deuxième IP du sous-réseau CIDR de slirp4netns lorsqu'il est modifié, voir l'option cidr ci-dessous). La valeur par défaut est false.
    • mtu=MTU : Spécifie la MTU à utiliser pour ce réseau. (Par défaut est 65520).
    • cidr=CIDR : Spécifie la plage IP à utiliser pour ce réseau. (Par défaut est 10.0.2.0/24).
    • enable_ipv6=true|false : Active IPv6. Par défaut, c'est true. (Requis pour outbound_addr6).
    • outbound_addr=INTERFACE : Spécifie l'interface sortante à laquelle slirp se lie (trafic ipv4 uniquement).
    • outbound_addr=IPv4 : Spécifie l'adresse ipv4 sortante à laquelle slirp se lie.
    • outbound_addr6=INTERFACE : Spécifie l'interface sortante à laquelle slirp se lie (trafic ipv6 uniquement).
    • outbound_addr6=IPv6 : Spécifie l'adresse ipv6 sortante à laquelle slirp se lie.
    • port_handler=rootlesskit : Utilise rootlesskit pour la redirection de port. Par défaut.
      Note : Rootlesskit modifie l'adresse IP source des paquets entrants vers une adresse IP dans l'espace de noms réseau du conteneur, généralement 10.0.2.100. Si l'application nécessite l'adresse IP source réelle, par exemple pour les journaux du serveur Web, utilisez le gestionnaire de ports slirp4netns. Le gestionnaire de ports rootlesskit est également utilisé pour les conteneurs rootless lorsqu'ils sont connectés à des réseaux définis par l'utilisateur.
    • port_handler=slirp4netns : Utilise la redirection de port slirp4netns, elle est plus lente que rootlesskit mais préserve la bonne adresse IP source. Ce gestionnaire de ports ne peut pas être utilisé pour les réseaux définis par l'utilisateur.
    •
    pasta[:OPTIONS,...] : Utilise pasta(1) pour créer une pile de réseau en mode utilisateur.
    C'est la valeur par défaut pour les conteneurs rootless et ne prend en charge que le mode rootless.
    Par défaut, les adresses et routes IPv4 et IPv6, ainsi que le nom d'interface du pod, sont copiés depuis l'hôte. La redirection de port préserve l'adresse IP source d'origine. Les options décrites dans pasta(1) peuvent être spécifiées comme arguments séparés par des virgules.
    En termes d'options de pasta(1), --config-net est donné par défaut, afin de configurer le réseau lors du démarrage du conteneur, et --no-map-gw est également supposé par défaut, pour éviter l'accès direct du conteneur à l'hôte en utilisant l'adresse de passerelle. Ce dernier peut être remplacé en passant --map-gw dans les options spécifiques à pasta (bien qu'il ne s'agisse pas d'une option pasta(1) réelle).
    Pour une meilleure intégration avec la gestion DNS, --dns-forward 169.254.1.1 est passé, et cette adresse est ajoutée à resolv.conf(5) comme premier résolveur. Il est possible de passer --dns-forward explicitement si une adresse IP différente doit être utilisée. Pour que l'entrée host.containers.internal dans /etc/hosts fonctionne et permette les connexions à l'hôte, --map-guest-addr 169.254.1.2 est passé. Encore une fois, cela peut être réglé explicitement pour choisir une adresse IP différente.
    De plus, -t none et -u none sont passés si, respectivement, aucun transfert de port TCP ou UDP de l'hôte vers le conteneur n'est configuré (via l'option --publish de Podman ou en passant directement les options pasta -t/-u), pour désactiver le transfert de port automatique basé sur les ports liés. De même, -T none et -U none sont donnés pour désactiver la même fonctionnalité du conteneur vers l'hôte.
    Toutes les options peuvent également être définies dans containers.conf(5) ; voir la clé pasta_options sous la section réseau de ce fichier.
    Quelques exemples :
    • pasta:--map-gw : Permet au conteneur d'atteindre directement l'hôte en utilisant l'adresse de passerelle.
    • pasta:--mtu,1500 : Spécifie une MTU de 1500 octets pour l'interface tap dans le conteneur.
    • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) : désactive IPv6, attribue 10.0.2.0/24 à l'interface tap0 dans le conteneur, avec une passerelle 10.0.2.3, active le transmetteur DNS accessible à 10.0.2.3, définit la MTU à 1500 octets, désactive NDP, DHCPv6 et DHCP support.
    • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) avec les remplacements Podman : idem que ci-dessus, mais laisse la MTU à 65520 octets
    • pasta:-t,auto,-u,auto,-T,auto,-U,auto : active le transfert de port automatique basé sur les ports liés observés des côtés hôte et conteneur
    • pasta:-T,5201 : active le transfert du port TCP 5201 du conteneur vers l'hôte, en utilisant l'interface de bouclage au lieu de l'interface tap pour une performance améliorée

    Invalide si utilisé avec --dns, --dns-option ou --dns-search et que --network est défini sur none ou container:id.

    Si utilisé conjointement avec --pod, le conteneur rejoint l'espace de noms réseau du pod.

    --network-alias=alias

    Ajoute un alias à portée réseau pour le conteneur, définissant l'alias pour tous les réseaux auxquels le conteneur se joint. Pour définir un nom uniquement pour un réseau spécifique, utilisez l'option alias comme décrit sous l'option --network. Si le réseau a le DNS activé (podman network inspect -f {{.DNSEnabled}} <name>), ces alias peuvent être utilisés pour la résolution de noms sur le réseau donné. Cette option peut être spécifiée plusieurs fois. NOTE : Lors de l'utilisation de CNI, un conteneur n'a accès qu'aux alias sur le premier réseau auquel il se joint. Cette limitation n'existe pas avec netavark/aardvark-dns.

    --no-healthcheck

    Désactive tous les contrôles de santé définis pour le conteneur.

    --no-hostname

    Ne crée pas le fichier /etc/hostname dans les conteneurs.

    Par défaut, Podman gère le fichier /etc/hostname, ajoutant le propre nom d'hôte du conteneur. Lorsque l'option --no-hostname est définie, le fichier /etc/hostname de l'image sera préservé sans modification s'il existe.

    --no-hosts

    Ne modifie pas le fichier /etc/hosts dans le conteneur.

    Podman prend le contrôle du fichier /etc/hosts du conteneur par défaut et ajoute des entrées pour le nom du conteneur (voir l'option --name) et le nom d'hôte (voir l'option --hostname), les hôtes internes host.containers.internal et host.docker.internal, ainsi que tout nom d'hôte ajouté à l'aide de l'option --add-host. Référez-vous à l'option --add-host pour plus de détails. Passer --no-hosts désactive cela, de sorte que le fichier /etc/hosts de l'image reste inchangé. La même chose peut être réalisée globalement en définissant no_hosts=true dans containers.conf.

    Cette option est en conflit avec --add-host.

    --oom-kill-disable

    Désactive ou non le tueur OOM pour le conteneur.

    Ce drapeau n'est pas pris en charge sur les systèmes cgroups V2.

    --oom-score-adj=num

    Ajuste les préférences OOM de l'hôte pour les conteneurs (accepte des valeurs de -1000 à 1000).

    Lors de l'exécution en mode rootless, la valeur spécifiée ne peut pas être inférieure à oom_score_adj pour le processus actuel. Dans ce cas, l'oom-score-adj est limité à la valeur du processus actuel.

    --os=OS

    Remplace le système d'exploitation, par défaut celui de l'hôte, de l'image à télécharger. Par exemple, windows. Sauf si remplacé, les recherches ultérieures de la même image dans le stockage local correspondent à cet OS, quel que soit l'hôte.

    --passwd

    Permet à Podman d'ajouter des entrées à /etc/passwd et /etc/group lorsqu'il est utilisé conjointement avec l'option --user. Ceci est utilisé pour remplacer la configuration utilisateur fournie par Podman en faveur de configurations d'entrypoint telles que libnss-extrausers.

    --passwd-entry=ENTRY

    Personnalise l'entrée qui est écrite dans le fichier /etc/passwd dans le conteneur lorsque --passwd est utilisé.

    Les variables $USERNAME, $UID, $GID, $NAME, $HOME sont automatiquement remplacées par leur valeur au moment de l'exécution.

    --personality=persona

    La personnalité définit le domaine d'exécution via la personnalité Linux (2).

    --pid=mode

    Définit le mode de l'espace de noms PID pour le conteneur. Par défaut, il crée un espace de noms PID privé pour le conteneur.

    • container:id : rejoint l'espace de noms PID d'un autre conteneur ;
    • host : utilise l'espace de noms PID de l'hôte pour le conteneur. Notez que le mode hôte donne au conteneur un accès complet aux PID locaux et est donc considéré comme non sécurisé ;
    • ns:path : rejoint l'espace de noms PID spécifié ;
    • private : crée un nouvel espace de noms pour le conteneur (par défaut).

    --pidfile=path

    Lorsque l'emplacement du fichier PID est spécifié, le PID du processus du conteneur est écrit dans le fichier PID. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (hors WSL2)). Si l'option fichier PID n'est pas spécifiée, le PID du processus du conteneur est écrit dans /run/containers/storage/${storage-driver}-containers/$CID/userdata/pidfile.

    Après le démarrage du conteneur, l'emplacement du fichier PID peut être découvert avec la commande podman inspect suivante :

    $ podman inspect --format '{{ .PidFile }}' $CID
/run/containers/storage/${storage-driver}-containers/$CID/userdata/pidfile

    --pids-limit=limit

    Ajuste la limite de PIDs du conteneur. Définir à -1 pour avoir des PIDs illimités pour le conteneur. La valeur par défaut est 2048 sur les systèmes qui prennent en charge le contrôleur cgroup "pids".

    --platform=OS/ARCH

    Spécifie la plateforme pour sélectionner l'image. (Conflit avec --arch et --os) L'option --platform peut être utilisée pour remplacer l'architecture et le système d'exploitation actuels. Sauf remplacement, les recherches ultérieures de la même image dans le stockage local

    cette plateforme, quelle que soit l'hôte.

    --pod=nom

    Exécute un conteneur dans un pod existant. Podman crée le pod automatiquement si le nom du pod est précédé de new:. Pour créer un pod avec des options plus granulaires, utilisez la commande podman pod create avant de créer un conteneur. Lorsqu'un conteneur est exécuté avec un pod doté d'un conteneur d'infrastructure, le conteneur d'infrastructure démarre en premier.

    --pod-id-file=fichier

    Exécute un conteneur dans un pod existant et lit l'ID du pod à partir du fichier spécifié. Lorsqu'un conteneur est exécuté dans un pod qui possède un conteneur d'infrastructure, le conteneur d'infrastructure démarre en premier.

    --preserve-fd=FD1[,FD2,...]

    Transmet au processus les descripteurs de fichiers supplémentaires spécifiés dans la liste séparée par des virgules. Peut être spécifié plusieurs fois. Cette option n'est prise en charge qu'avec le runtime OCI crun. L'utilisation de cette option avec d'autres runtimes OCI peut présenter un risque de sécurité.

    (Cette option n'est pas disponible avec le client Podman distant, y compris sur les machines Mac et Windows (à l'exception de WSL2))

    --preserve-fds=N

    Transmet au processus N descripteurs de fichiers supplémentaires (en plus de 0, 1, 2). Le total des descripteurs de fichiers est de 3+N. (Cette option n'est pas disponible avec le client Podman distant, y compris sur les machines Mac et Windows (à l'exception de WSL2))

    --privileged

    Accorde des privilèges étendus à ce conteneur. La valeur par défaut est false.

    Par défaut, les conteneurs Podman ne sont pas privilégiés (=false) et ne peuvent pas, par exemple, modifier des parties du système d'exploitation. En effet, par défaut, un conteneur n'a qu'un accès limité aux périphériques. Un conteneur « privilégié » a le même accès aux périphériques que l'utilisateur qui lance le conteneur, à l'exception des consoles virtuelles (/dev/tty\d+) lorsqu'il s'exécute en mode systemd (--systemd=always).

    Un conteneur privilégié désactive les fonctionnalités de sécurité qui isolent le conteneur de l'hôte. Les capacités supprimées, les périphériques limités, les points de montage en lecture seule, la séparation Apparmor/SELinux et les filtres Seccomp sont tous désactivés. En raison des fonctionnalités de sécurité désactivées, le champ privilégié ne doit presque jamais être défini car les conteneurs peuvent facilement s'échapper de leur confinement.

    Les conteneurs s'exécutant dans un espace de noms utilisateur (par exemple, les conteneurs rootless) ne peuvent pas avoir plus de privilèges que l'utilisateur qui les a lancés.

    --publish, -p=[[ip:][portHote:]]portConteneur[/protocole]

    Publie le port, ou une plage de ports, d'un conteneur sur l'hôte.

    Le portHote et le portConteneur peuvent tous deux être spécifiés comme une plage de ports. Lors de la spécification de plages pour les deux, le nombre de ports de conteneur dans la plage doit correspondre au nombre de ports hôtes dans la plage.

    Si l'adresse IP de l'hôte est définie sur 0.0.0.0 ou n'est pas définie du tout, le port est lié à toutes les adresses IP de l'hôte.

    Par défaut, Podman publie les ports TCP. Pour publier un port UDP à la place, indiquez udp comme protocole. Pour publier à la fois les ports TCP et UDP, définissez --publish deux fois, avec respectivement tcp et udp comme protocoles. Les conteneurs rootful peuvent également publier des ports en utilisant le protocole sctp.

    Le port hôte n'a pas besoin d'être spécifié (par exemple, podman run -p 127.0.0.1::80). S'il ne l'est pas, le port du conteneur se voit attribuer aléatoirement un port sur l'hôte.

    Utilisez podman port pour voir le mappage réel : podman port $CONTENEUR $PORTCONTENEUR.

    La publication de ports n'est prise en charge que pour les conteneurs utilisant leur propre espace de noms réseau via les réseaux bridge, ou les modes réseau pasta et slirp4netns.

    Remarque : Si un conteneur s'exécute dans un pod, il n'est pas nécessaire de publier le port pour les conteneurs du pod. Le port ne doit être publié que par le pod lui-même. Les piles réseau des pods agissent comme la pile réseau de l'hôte, ce qui signifie qu'une variété de conteneurs dans le pod et de programmes dans le conteneur partagent tous une seule interface, une adresse IP et des ports associés. Si un conteneur se lie à un port, aucun autre conteneur ne peut utiliser ce port dans le pod tant qu'il est utilisé. Les conteneurs du pod peuvent également communiquer via localhost en faisant en sorte qu'un conteneur se lie à localhost dans le pod, et qu'un autre se connecte à ce port.

    --publish-all, -P

    Publie tous les ports exposés sur des ports aléatoires sur les interfaces hôtes. La valeur par défaut est false.

    Lorsqu'il est défini sur true, publie tous les ports exposés sur les interfaces hôtes. Si l'opérateur utilise -P (ou -p), Podman rend le port exposé accessible sur l'hôte et les ports sont disponibles pour tout client pouvant atteindre l'hôte.

    Lors de l'utilisation de cette option, Podman lie tout port exposé à un port aléatoire sur l'hôte dans une plage de ports éphémères définie par /proc/sys/net/ipv4/ip_local_port_range. Pour trouver le mappage entre les ports hôtes et les ports exposés, utilisez podman port.

    --pull=politique

    Politique de téléchargement d'image. La valeur par défaut est missing.

    • always : Télécharge toujours l'image et génère une erreur si le téléchargement échoue.
    • missing : Télécharge l'image uniquement lorsque l'image n'est pas présente dans le stockage local des conteneurs. Génère une erreur si aucune image n'est trouvée et que le téléchargement échoue.
    • never : Ne télécharge jamais l'image, mais utilise celle du stockage local des conteneurs. Génère une erreur si aucune image n'est trouvée.
    • newer : Télécharge si l'image du registre est plus récente que celle du stockage local des conteneurs. Une image est considérée comme plus récente lorsque les empreintes sont différentes. La comparaison des horodatages est sujette à des erreurs. Les erreurs de téléchargement sont supprimées si une image locale a été trouvée.

    --quiet, -q

    Supprime les informations de sortie lors du téléchargement d'images

    --rdt-class=classe-de-service-intel-rdt

    Rdt-class définit la classe de service (CLOS ou COS) dans laquelle le conteneur doit s'exécuter. Basé sur la fonctionnalité Cache Allocation Technology (CAT) qui fait partie de l'ensemble de fonctionnalités Intel Resource Director Technology (RDT), tous les processus du conteneur s'exécuteront dans la COS préconfigurée, représentant une partie du cache. La COS doit être créée et configurée à l'aide d'un système de fichiers pseudo (généralement monté sur /sys/fs/resctrl) que le pilote de noyau resctrl fournit. L'attribution du conteneur à une COS nécessite des privilèges root et ne fonctionne donc pas dans un environnement rootless. Actuellement, la fonctionnalité n'est prise en charge qu'en utilisant runc comme runtime. Voir ⟨https://docs.kernel.org/arch/x86/resctrl.html⟩ pour plus de détails sur la création d'une COS avant qu'un conteneur puisse lui être attribué.

    --read-only

    Monte le système de fichiers racine du conteneur en lecture seule.

    Par défaut, les systèmes de fichiers racine des conteneurs sont inscriptibles, permettant aux processus d'écrire des fichiers n'importe où. En spécifiant le drapeau --read-only, le système de fichiers racine des conteneurs est monté en lecture seule, interdisant toute écriture.

    --read-only-tmpfs

    Lors de l'exécution de conteneurs --read-only, monte un tmpfs en lecture-écriture sur /dev, /dev/shm, /run, /tmp et /var/tmp. La valeur par défaut est true.

    --read-only --read-only-tmpfs / /run, /tmp, /var/tmp
    true true r/o r/w
    true false r/o r/o
    false false r/w r/w
    false true r/w r/w

    Lorsque --read-only=true et --read-only-tmpfs=true, des tmpfs supplémentaires sont montés sur les répertoires /tmp, /run et /var/tmp.

Les répertoires sont exposés depuis l'image sous-jacente, ce qui signifie qu'ils sont en lecture seule par défaut. Cela rend le conteneur totalement en lecture seule.     --secret=secret[,opt=opt ...]

    Donne accès à un secret au conteneur. Peut être spécifié plusieurs fois.

    Un secret est un bloc de données sensibles dont un conteneur a besoin à l'exécution mais qui n'est pas stocké dans l'image ou dans le contrôle de version, tel que les noms d'utilisateur et mots de passe, les certificats et clés TLS, les clés SSH ou d'autres chaînes génériques ou contenus binaires importants (jusqu'à 512 Ko).

    Lorsque les secrets sont spécifiés comme type mount, les secrets sont copiés et montés dans le conteneur lors de la création d'un conteneur. Lorsque les secrets sont spécifiés comme type env, le secret est défini comme une variable d'environnement dans le conteneur. Les secrets sont écrits dans le conteneur au moment de la création du conteneur, et la modification du secret à l'aide des commandes podman secret après la création du conteneur affecte le secret à l'intérieur du conteneur.

    Les secrets et leur stockage sont gérés à l'aide de la commande podman secret.

    Options de Secret

    • type=mount|env : Comment le secret est exposé au conteneur.
      mount monte le secret dans le conteneur sous forme de fichier.
      env expose le secret en tant que variable d'environnement.
      Par défaut : mount.
    • target=target : Cible du secret.
      Pour les secrets montés, il s'agit du chemin d'accès au secret à l'intérieur du conteneur.
      Si un chemin d'accès complet est fourni, le secret est monté à cet emplacement.
      Sinon, le secret est monté sur
      /run/secrets/target pour les conteneurs Linux ou
      /var/run/secrets/target pour les conteneurs FreeBSD.
      Si la cible n'est pas définie, le secret est monté sur /run/secrets/nomsecret par défaut.
      Pour les secrets env, il s'agit de la clé de la variable d'environnement. La valeur par défaut est nomsecret.
    • uid=0 : UID du secret. Par défaut : 0. Type de montage de secret uniquement.
    • gid=0 : GID du secret. Par défaut : 0. Type de montage de secret uniquement.
    • mode=0 : Mode du secret. Par défaut : 0444. Type de montage de secret uniquement.

    Exemples

    Montage sur /my/location/mysecret avec UID 1 :

    --secret mysecret,target=/my/location/mysecret,uid=1

    Montage sur /run/secrets/customtarget avec le mode 0777 :

    --secret mysecret,target=customtarget,mode=0777

    Créer une variable d'environnement secrète appelée ENVSEC :

    --secret mysecret,type=env,target=ENVSEC

    --uidmap=[indicateurs]uid_conteneur:uid_hôte[:quantité]

    Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant le mappage UID fourni. Cette option entre en conflit avec les options --userns et --subuidname. Cette option fournit un moyen de mapper les UID hôtes aux UID conteneurs. Elle peut être passée plusieurs fois pour mapper différentes plages.

    Les valeurs possibles des indicateurs optionnels sont discutées plus loin sur cette page. La valeur quantité est optionnelle et supposée être 1 si elle n'est pas fournie.

    La valeur uid_hôte est basée sur l'utilisateur exécutant la commande, qu'il soit rootful ou rootless.

    • utilisateur rootful : [indicateurs]uid_conteneur:uid_hôte[:quantité]
    • utilisateur rootless : [indicateurs]uid_conteneur:uid_intermédiaire[:quantité]

    Mappages rootful

    Lorsque podman run est appelé par un utilisateur privilégié, l'option --uidmap fonctionne comme un mappage direct entre les UID hôtes et les UID conteneurs.

    UID hôte -> UID conteneur

    La quantité spécifie le nombre d'UID consécutifs qui sont mappés. Si, par exemple, la quantité est 4, le mappage ressemble à ceci :

    UID hôte UID conteneur
    uid_hôte uid_conteneur
    uid_hôte + 1 uid_conteneur + 1
    uid_hôte + 2 uid_conteneur + 2
    uid_hôte + 3 uid_conteneur + 3

    Mappages rootless

    Lorsque podman run est appelé par un utilisateur non privilégié (c'est-à-dire en mode rootless), la valeur uid_hôte est interprétée comme un "UID intermédiaire". Dans le cas rootless, les UID hôtes ne sont pas directement mappés aux UID conteneurs. Au lieu de cela, le mappage se fait en deux étapes :

    UID hôte -> UID intermédiaire -> UID conteneur

    L'option --uidmap n'influence que la deuxième étape du mappage.

    La première étape de mappage est dérivée par Podman à partir du contenu du fichier /etc/subuid et de l'UID de l'utilisateur appelant Podman.

    Première étape de mappage :

    UID hôte UID intermédiaire
    UID de l'utilisateur Podman 0
    1er UID subordonné 1
    2ème UID subordonné 2
    3ème UID subordonné 3
    nième UID subordonné n

    Pour pouvoir utiliser des UID intermédiaires supérieurs à zéro, l'utilisateur doit avoir des UID subordonnés configurés dans /etc/subuid. Voir subuid(5).

    La deuxième étape de mappage est configurée avec --uidmap.

    Si, par exemple, la quantité est 5, la deuxième étape de mappage ressemble à ceci :

    UID intermédiaire UID conteneur
    uid_intermédiaire uid_conteneur
    uid_intermédiaire + 1 uid_conteneur + 1
    uid_intermédiaire + 2 uid_conteneur + 2
    uid_intermédiaire + 3 uid_conteneur + 3
    uid_intermédiaire + 4 uid_conteneur + 4

    Lors de l'exécution en mode rootless, Podman utilise toutes les plages configurées dans le fichier /etc/subuid.

    L'ID utilisateur actuel est mappé à l'UID=0 dans l'espace de noms utilisateur rootless. Chaque plage supplémentaire est ajoutée séquentiellement ensuite :

    Hôte Espace de noms utilisateur rootless Longueur
    $UID 0 1
    1 $PREMIERE_PLAGE_ID $LONGUEUR_PREMIERE_PLAGE
    1+$LONGUEUR_PREMIERE_PLAGE $DEUXIEME_PLAGE_ID $LONGUEUR_DEUXIEME_PLAGE

    Référencement d'un ID hôte de l'espace parent

    En tant qu'utilisateur rootless, l'ID hôte donné dans --uidmap ou --gidmap est mappé à partir de l'espace intermédiaire généré par Podman. Il est parfois souhaitable de faire référence directement à l'espace hôte. Il est possible de le faire manuellement, en exécutant podman unshare cat /proc/self/gid_map, en trouvant l'ID hôte désiré dans la deuxième colonne de la sortie, et en obtenant l'ID intermédiaire correspondant de la première colonne.

    Podman peut effectuer tout cela en faisant précéder l'ID hôte du mappage du symbole @. Par exemple, en spécifiant --gidmap 100000:@2000:1, podman recherchera l'ID intermédiaire correspondant à l'ID hôte 2000 et mappera l'ID intermédiaire trouvé à l'ID conteneur 100000. L'ID hôte donné doit avoir été subordonné (sinon il ne serait pas mappé dans l'espace intermédiaire en premier lieu).

    Si la longueur est supérieure à un, par exemple avec --gidmap 100000:@2000:

    2, Podman mappera les identifiants hôte 2000 et 2001 respectivement à 100000 et 100001, quelle que soit la manière dont le mappage intermédiaire est défini.

    Extension des mappages précédents

    Certaines modifications de mappage peuvent être fastidieuses. Par exemple, un utilisateur commence avec un mappage tel que --gidmap="0:0:65000", qui doit être modifié pour que l'identifiant parent 1 soit mappé à l'identifiant conteneur 100000 au lieu de cela, laissant l'identifiant conteneur 1 non attribué. Le --gidmap correspondant devient --gidmap="0:0:1" --gidmap="2:2:65534" --gidmap="100000:1:1".

    Cette notation peut être simplifiée en utilisant le drapeau +, qui prend en charge la rupture des mappages précédents en supprimant toute affectation conflictuelle avec le mappage donné. Le drapeau est donné avant l'identifiant du conteneur comme suit : --gidmap="0:0:65000" --gidmap="+100000:1:1"

    Drapeau Exemple Description
    + +100000:1:1 Étendre le mappage précédent

    Cette notation entraîne des lacunes dans l'affectation, il peut donc être utile de combler ces lacunes par la suite : --gidmap="0:0:65000" --gidmap="+100000:1:1" --gidmap="1:65001:1"

    Un cas d'utilisation spécifique pour ce drapeau est dans le contexte des utilisateurs sans privilèges (rootless). Un utilisateur sans privilèges peut spécifier des mappages avec le drapeau + comme dans --gidmap="+100000:1:1". Podman "remplira les lacunes" à partir de zéro avec tous les identifiants intermédiaires restants. Ceci est pratique lorsqu'un utilisateur souhaite mapper un identifiant intermédiaire spécifique à un identifiant de conteneur, laissant le reste des identifiants subordonnés être mappés par Podman à volonté.

    Passer seulement un des arguments --uidmap ou --gidmap

    Habituellement, les identifiants utilisateur et groupe subordonnés sont attribués simultanément, et pour tout utilisateur, les identifiants utilisateur subordonnés correspondent aux identifiants groupe subordonnés. Par souci de commodité, si seulement un des arguments --uidmap ou --gidmap est donné, podman suppose que le mappage se réfère aux UID et GID et applique le mappage donné aux deux. Si seule l'une des deux valeurs doit être modifiée, les mappages doivent inclure les drapeaux u ou g pour spécifier qu'ils ne s'appliquent qu'aux UID ou GID et ne doivent pas être copiés.

    Drapeau Exemple Description
    u u20000:2000:1 Le mappage ne s'applique qu'aux UID
    g g10000:1000:1 Le mappage ne s'applique qu'aux GID

    Par exemple, étant donné la commande

    podman run --gidmap "0:0:1000" --gidmap "g2000:2000:1"

    Comme aucun argument --uidmap n'est donné, le --gidmap est copié dans --uidmap, donnant une commande équivalente à

    podman run --gidmap "0:0:1000" --gidmap "2000:2000:1" --uidmap "0:0:1000"

    Le --gidmap "g2000:2000:1" a utilisé le drapeau g et, par conséquent, n'a pas été copié dans --uidmap.

    Mappage sans privilèges de GID hôtes supplémentaires

    Un utilisateur sans privilèges peut souhaiter mapper un groupe hôte spécifique qui a déjà été subordonné dans /etc/subgid sans spécifier le reste du mappage.

    Cela peut être fait avec --gidmap "+ggid_conteneur:@gid_hôte"

    Où :

    • Le GID hôte est donné par le symbole @
    • Le mappage de ce GID n'est pas copié dans --usermap grâce au drapeau g.
    • Le reste des identifiants de conteneur sera mappé à partir de 0 à n, avec tous les GID subordonnés restants, grâce au drapeau +.

    Par exemple, si un utilisateur appartient au groupe 2000 et que ce groupe lui est subordonné (avec usermod --add-subgids 2000-2000 $USER), l'utilisateur peut mapper le groupe dans le conteneur avec : --gidmap=+g100000:@2000.

    Si ce mappage est combiné avec l'option --group-add=keep-groups, le processus dans le conteneur appartiendra au groupe 100000, et les fichiers appartenant au groupe 2000 sur l'hôte apparaîtront comme appartenant au groupe 100000 à l'intérieur du conteneur.

    podman run --group-add=keep-groups --gidmap="+g100000:@2000" ...

    Pas d'UID subordonnés

    Même si un utilisateur n'a pas d'UID subordonnés dans /etc/subuid, --uidmap peut être utilisé pour mapper l'UID normal de l'utilisateur à un UID de conteneur en exécutant podman run --uidmap $uid_conteneur:0:1 --user $uid_conteneur ....

    --ulimit=option

    Options Ulimit. Définit les valeurs ulimits à l'intérieur du conteneur.

    --ulimit avec une limite souple et une limite dure au format =[:]. Par exemple :

    $ podman run --ulimit nofile=1024:1024 --rm ubi9 ulimit -n 1024

    Définissez -1 pour la limite souple ou dure afin de définir la limite à la limite maximale du processus actuel. En mode rootful, c'est souvent illimité.

    Si nofile et nproc ne sont pas définis, une valeur par défaut de 1048576 sera utilisée, sauf indication contraire dans containers.conf(5). Cependant, si la valeur par défaut dépasse la limite dure pour l'utilisateur sans privilèges actuel, la limite dure actuelle sera appliquée à la place.

    Utilisez host pour copier la configuration actuelle de l'hôte.

    N'utilisez pas nproc avec le drapeau ulimit car Linux utilise nproc pour définir le nombre maximum de processus disponibles pour un utilisateur, et non pour un conteneur.

    Utilisez l'option --pids-limit pour modifier le contrôle cgroup afin de limiter le nombre de processus dans un conteneur.

    --umask=umask

    Définit le umask à l'intérieur du conteneur. Par défaut, 0022. Les connexions à distance utilisent le fichier local containers.conf pour les valeurs par défaut.

    --unsetenv=env

    Annule les variables d'environnement par défaut pour le conteneur. Les variables d'environnement par défaut incluent les variables fournies nativement par Podman, les variables d'environnement configurées par l'image et les variables d'environnement de containers.conf.

    --unsetenv-all

    Annule toutes les variables d'environnement par défaut pour le conteneur. Les variables d'environnement par défaut incluent les variables fournies nativement par Podman, les variables d'environnement configurées par l'image et les variables d'environnement de containers.conf.

    --user, -u=utilisateur[:groupe]

    Définit le nom d'utilisateur ou l'UID utilisé et, éventuellement, le nom de groupe ou le GID pour la commande spécifiée. Utilisateur et groupe peuvent être des symboles ou des nombres.

    Sans cet argument, la commande s'exécute en tant qu'utilisateur spécifié dans l'image du conteneur. Sauf indication contraire par une commande USER dans le Containerfile ou par une valeur passée à cette option, cet utilisateur est généralement défini par défaut sur root.

    Lorsqu'un espace de noms d'utilisateur n'est pas utilisé, l'UID et le GID utilisés dans le conteneur et sur l'hôte correspondent. Lorsque des espaces de noms d'utilisateur sont utilisés, cependant, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte. Dans les conteneurs sans privilèges, par exemple, un espace de noms d'utilisateur est toujours utilisé, et root dans le conteneur correspond par défaut à l'UID et au GID de l'utilisateur qui invoque Podman.

    --userns=mode

    Définit le mode d'espace de noms d'utilisateur pour le conteneur.

    Si --userns n'est pas défini, la valeur par défaut est déterminée comme suit : - Si --pod est défini, --userns est ignoré et l'espace de noms d'utilisateur du pod est utilisé. - Si la variable d'environnement PODMAN_USERNS est définie, sa valeur est utilisée. - Si userns est spécifié dans containers.conf, cette valeur est utilisée. - Sinon, --userns=host est supposé.

    --userns="" (c'est-à-dire une chaîne vide) est un alias pour --userns=host.

    Cette option est incompatible avec --gidmap, --uidmap, --subuidname et --subgidname.

    Mappages de clés --userns pour les utilisateurs sans privilèges :

    Clé Utilisateur hôte Utilisateur conteneur
    auto $UID nil (l'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)
    host $UID 0 (Compte utilisateur par défaut mappé à l'utilisateur root dans le conteneur.)
    keep-id $UID $UID (Mappe le compte utilisateur au même UID à l'intérieur du conteneur.)
    keep-id:uid=200,gid=210 $UID 200:210 (Mappe le compte utilisateur à l'UID, GID spécifié à l'intérieur du conteneur.)
    nomap $UID nil (l'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)

    Les valeurs de mode valides sont :

    auto[:OPTIONS,...] : crée automatiquement un espace de noms d'utilisateur unique.

    • mode rootful : le drapeau --userns=auto nécessite que le nom d'utilisateur containers soit spécifié dans les fichiers /etc/subuid et /etc/subgid, avec une plage inutilisée d'identifiants d'utilisateurs subordonnés que les conteneurs Podman sont autorisés à allouer. Exemple : containers:2147483647:2147483648.
    • mode sans privilèges : la plage d'utilisateurs des fichiers /etc/subuid et /etc/subgid sera utilisée. Notez que l'exécution d'un seul conteneur sans utiliser --userns=auto utilisera toute la plage d'UID et ne permettra pas de subdivision supplémentaire. Voir subuid(5).

    Podman alloue des plages uniques d'UID et de GID à partir des identifiants d'utilisateurs subordonnés containers. La taille des plages est basée sur le nombre d'UID requis dans l'image. Le nombre d'UID et de GID peut être remplacé par l'option size.

    L'option --userns=keep-id utilise tous les subuids et subgids de l'utilisateur. L'option --userns=nomap utilise tous les subuids et subgids de l'utilisateur, à l'exception de l'ID propre de l'utilisateur. L'utilisation de --userns=auto lors du démarrage de nouveaux conteneurs ne fonctionne pas tant qu'il existe des conteneurs qui ont été démarrés avec --userns=nomap ou --userns=keep-id sans limiter la taille de l'espace de noms utilisateur.

    Options valides pour auto :

    • gidmapping=GID_CONTENEUR:GID_HOTE:TAILLE : pour forcer un mappage GID à être présent dans l'espace de noms utilisateur.
    • size=TAILLE : pour spécifier une taille explicite pour l'espace de noms utilisateur automatique. par exemple --userns=auto:size=8192. Si size n'est pas
    t spécifié, auto estime une taille pour l'espace de noms utilisateur.
  • uidmapping=UID_CONTENEUR:UID_HOTE:TAILLE: pour forcer un mappage UID à être présent dans l'espace de noms utilisateur.

    • L'UID et le GID hôte dans gidmapping et uidmapping peuvent éventuellement être préfixés par le symbole @. Dans ce cas, podman recherchera l'ID intermédiaire correspondant à l'ID hôte et mappera l'ID intermédiaire trouvé à l'ID du conteneur. Pour plus de détails, voir --uidmap.

    container:id: rejoindre l'espace de noms utilisateur du conteneur spécifié.

    host ou "" (chaîne vide) : s'exécuter dans l'espace de noms utilisateur de l'appelant. Les processus s'exécutant dans le conteneur ont les mêmes privilèges sur l'hôte que tout autre processus lancé par l'utilisateur appelant.

    keep-id : crée un espace de noms utilisateur où l'UID:GID de l'utilisateur actuel sont mappés aux mêmes valeurs dans le conteneur. Pour les conteneurs créés par root, le mappage actuel est créé dans un nouvel espace de noms utilisateur.

    De plus, le processus init dans le conteneur s'exécutera sous l'UID de l'utilisateur actuel. Ce comportement remplace l'instruction USER de l'image, sauf si vous définissez explicitement --user.

    Options valides pour keep-id :

    • uid=UID : remplace l'UID à l'intérieur du conteneur utilisé pour mapper l'utilisateur actuel.
    • gid=GID : remplace le GID à l'intérieur du conteneur utilisé pour mapper l'utilisateur actuel.
    • size=TAILLE : remplace la taille de l'espace de noms utilisateur configuré. Il est utile de ne pas saturer tous les ID disponibles. Non pris en charge lors de l'exécution en tant que root.

    nomap : crée un espace de noms utilisateur où l'UID:GID de l'utilisateur rootless actuel ne sont pas mappés dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.

    ns:namespace : exécute le conteneur dans l'espace de noms utilisateur existant donné.

    --uts=mode

    Définit le mode de l'espace de noms UTS pour le conteneur. Les valeurs suivantes sont prises en charge :

    • host : utilise l'espace de noms UTS de l'hôte à l'intérieur du conteneur.
    • private : crée un nouvel espace de noms pour le conteneur (par défaut).
    • ns:[chemin] : exécute le conteneur dans l'espace de noms UTS existant donné.
    • container:[conteneur] : rejoint l'espace de noms UTS du conteneur spécifié.

    --variant=VARIANT

    Utilise VARIANT au lieu de la variante d'architecture par défaut de l'image du conteneur. Certaines images peuvent utiliser plusieurs variantes des architectures arm, telles que arm/v5 et arm/v7.

    --volume, -v=[[VOLUME-SOURCE|RÉPERTOIRE-HÔTE:]RÉPERTOIRE-CONTENEUR[:OPTIONS]]

    Crée un montage de liaison (bind mount). Si -v /RÉPERTOIRE-HÔTE:/RÉPERTOIRE-CONTENEUR est spécifié, Podman monte /RÉPERTOIRE-HÔTE de l'hôte dans /RÉPERTOIRE-CONTENEUR dans le conteneur Podman. De même, -v VOLUME-NOMMÉE:/RÉPERTOIRE-CONTENEUR monte le volume nommé depuis l'hôte dans le conteneur. Si ce volume nommé n'existe pas, Podman en crée un. Si aucune source n'est donnée, le volume est créé en tant que volume nommé anonymement avec un nom généré aléatoirement, et il est supprimé lorsque le conteneur est supprimé via l'option --rm ou la commande podman rm --volumes.

    (Notez lors de l'utilisation du client distant, y compris les machines Mac et Windows (à l'exclusion de WSL2), les volumes sont montés depuis le serveur distant, pas nécessairement la machine cliente.)

    Les OPTIONS sont une liste séparée par des virgules et peuvent être une ou plusieurs des suivantes :

    • rw|ro
    • z|Z
    • [O]
    • [U]
    • [no]copy
    • [no]dev
    • [no]exec
    • [no]suid
    • [r]bind
    • [r]shared|[r]slave|[r]private[r]unbindable [1] ⟨#Footnote1⟩
    • idmap[=options]

    Le RÉPERTOIRE-CONTENEUR doit être un chemin absolu tel que /src/docs. Le volume est monté dans le conteneur à ce répertoire.

    Si une source de volume est spécifiée, elle doit être un chemin sur l'hôte ou le nom d'un volume nommé. Les chemins d'hôte peuvent être absolus ou relatifs ; les chemins relatifs sont résolus par rapport au répertoire dans lequel Podman est exécuté. Si la source n'existe pas, Podman renvoie une erreur. Les utilisateurs doivent pré-créer les fichiers ou répertoires source.

    Toute source qui ne commence pas par un . ou un / est traitée comme le nom d'un volume nommé. Si un volume de ce nom n'existe pas, il est créé. Les volumes créés avec des noms ne sont pas anonymes et ne sont pas supprimés par l'option --rm et la commande podman rm --volumes.

    Spécifiez plusieurs options -v pour monter un ou plusieurs volumes dans un conteneur.

    Montages de volumes protégés en écriture

    Ajoutez l'option :ro ou :rw pour monter un volume en mode lecture seule ou lecture-écriture, respectivement. Par défaut, les volumes sont montés en lecture-écriture. Voir les exemples.

    Changement de propriétaire des montages de volumes

    Lorsqu'un volume nommé est monté pour la première fois sur un conteneur, Podman ajuste automatiquement la propriété du point de montage du volume lors de l'initialisation du conteneur. Cette opération de changement de propriétaire (chown) se produit dans les conditions suivantes :

    • Le volume n'a pas encore été utilisé (NeedsChown est défini sur true)
    • Le volume est vide ou n'a pas encore été copié
    • Le volume n'est pas géré par un pilote de volume externe
    • Le pilote de volume n'est pas "image"

    Pour les volumes avec des montages idmapped (utilisant l'option idmap), le changement de propriétaire prend en compte les mappages d'espace de noms utilisateur du conteneur, mais le volume idmapped conserve un mappage UID/GID correct. Pour les volumes sans idmapping, le point de montage est chowné pour correspondre à l'utilisateur et au groupe du processus du conteneur, mappé à l'espace de noms utilisateur de l'hôte si le remappage de l'espace de noms utilisateur est activé.

    Si un conteneur est créé dans un nouvel espace de noms utilisateur, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte.

    Le suffixe :U indique à Podman d'utiliser l'UID et le GID hôte corrects basés sur l'UID et le GID à l'intérieur du conteneur, pour changer récursivement le propriétaire et le groupe du volume source. Chowning parcourt le système de fichiers sous le volume et change l'UID/GID sur chaque fichier. Si le volume a des milliers d'inodes, ce processus prend beaucoup de temps, retardant le démarrage du conteneur.

    Avertissement : utiliser avec précaution car cela modifie le système de fichiers de l'hôte.

    Labellisation des montages de volumes

    Les systèmes de labellisation comme SELinux exigent que des labels appropriés soient placés sur le contenu des volumes montés dans un conteneur. Sans label, le système de sécurité pourrait empêcher les processus s'exécutant dans le conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les labels définis par l'OS.

    Pour modifier un label dans le contexte du conteneur, ajoutez l'un des deux suffixes :z ou :Z au montage du volume. Ces suffixes indiquent à Podman de relabéliser les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux conteneurs ou plus partagent le contenu du volume. Par conséquent, Podman labellise le contenu avec un label de contenu partagé. Les labels de volume partagé permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman de labelliser le contenu avec un label privé non partagé. Seul le conteneur actuel peut utiliser un volume privé.

    Remarque : tous les conteneurs au sein d'un pod partagent le même label SELinux. Cela signifie que tous les conteneurs au sein de ce pod peuvent lire/écrire des volumes partagés dans le conteneur créé avec le label :Z sur l'un des conteneurs. Le relabélisage parcourt le système de fichiers sous le volume et modifie le label sur chaque fichier ; si le volume a des milliers d'inodes, ce processus prend beaucoup de temps, retardant le démarrage du conteneur. Si le volume a été précédemment relabélisé avec l'option z, Podman est optimisé pour ne pas relabéliser une seconde fois. Si des fichiers sont déplacés dans le volume, les labels peuvent être modifiés manuellement avec la commande chcon -Rt container_file_t PATH.

    Remarque : ne relabélisez pas les fichiers et répertoires système. Relabéliser le contenu système peut provoquer la défaillance d'autres services confinés sur la machine. Pour ces types de conteneurs, nous recommandons de désactiver la séparation SELinux. L'option --security-opt label=disable désactive la séparation SELinux pour le conteneur. Par exemple, si un utilisateur souhaite monter tout son répertoire personnel dans un conteneur, il doit désactiver la séparation SELinux.

    $ podman run --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

    Montages de volumes en superposition (overlay)

    L'indicateur :O indique à Podman de monter le répertoire de l'hôte comme stockage temporaire en utilisant le système de fichiers overlay. Les processus du conteneur peuvent modifier le contenu du point de montage, qui est stocké dans le stockage du conteneur dans un répertoire séparé. En termes d'overlay, le répertoire source est le inférieur (lower), et le répertoire de stockage du conteneur est le supérieur (upper). Les modifications apportées au point de montage sont détruites lorsque le conteneur a fini de s'exécuter, similaire à un point de montage tmpfs qui est démonté.

    Pour les utilisateurs avancés, l'option overlay prend également en charge des upperdir et workdir personnalisés et non volatils pour le montage overlay. Les upperdir et workdir personnalisés peuvent être entièrement gérés par les utilisateurs eux-mêmes, et Podman ne les supprime pas à la fin du cycle de vie. Exemple : :O,upperdir=/some/upper,workdir=/some/work

    Les exécutions ultérieures du conteneur voient le contenu du répertoire source d'origine, toutes les modifications des exécutions précédentes du conteneur n'existent plus.

    Un cas d'utilisation du montage overlay est le partage du cache de paquets de l'hôte dans le conteneur pour accélérer les compilations.

    Remarque : l'indicateur O est en conflit avec d'autres options listées ci-dessus.

    Le contenu monté dans le conteneur est labellisé avec le label privé. Sur les systèmes SELinux, les labels dans le répertoire source doivent être lisibles par le label du conteneur. Généralement, les conteneurs peuvent lire/exécuter container_share_t et lire/écrire container_file_t. Si les labels ne peuvent pas être modifiés sur un volume source, la séparation SELinux du conteneur doit être désactivée pour que le conteneur fonctionne.

    Ne modifiez pas le répertoire source monté dans le conteneur avec un montage overlay, cela pourrait entraîner des échecs inattendus. Modifiez uniquement le répertoire après la fin de l'exécution du conteneur.

    Propagation des montages

    Par défaut, les volumes montés par liaison (bind-mounted) sont privés. Cela signifie que tous les montages effectués à l'intérieur du conteneur ne sont pas visibles sur l'hôte et vice versa. On peut changer ce comportement en spécifiant une propriété de propagation de montage de volume. Lorsqu'un volume est partagé, les montages effectués sous ce volume à l'intérieur du conteneur sont visibles sur l'hôte et

    Fait vice versa. La création d'un volume esclave[1] ⟨#Footnote1⟩ n'autorise qu'une propagation de montage unidirectionnelle : les montages effectués sur l'hôte sous ce volume sont visibles à l'intérieur du conteneur mais pas l'inverse.

    Pour contrôler la propriété de propagation de montage d'un volume, on peut utiliser les drapeaux de propagation [r]shared, [r]slave, [r]private ou [r]unbindable. La propriété de propagation peut être spécifiée uniquement pour les volumes montés par liaison et non pour les volumes internes ou nommés. Pour que la propagation de montage fonctionne, le point de montage source (le point de montage où le répertoire source est monté) doit avoir les bonnes propriétés de propagation. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le point de montage source doit être soit partagé, soit esclave. [1] ⟨#Footnote1⟩

    Pour monter récursivement un volume et tous ses sous-montages dans un conteneur, utilisez l'option rbind. Par défaut, l'option de liaison est utilisée et les sous-montages du répertoire source ne sont pas montés dans le conteneur.

    Le montage du volume avec une option copy indique à Podman de copier le contenu du répertoire de destination sous-jacent sur les volumes internes nouvellement créés. La copie ne se fait que lors de la création initiale du volume. Le contenu n'est pas copié lorsque le volume est utilisé ultérieurement sur différents conteneurs. L'option copy est ignorée sur les montages par liaison et n'a aucun effet.

    Le montage des volumes avec l'option nosuid signifie que les exécutables SUID sur le volume ne peuvent pas être utilisés par les applications pour changer leur privilège. Par défaut, les volumes sont montés avec nosuid.

    Le montage du volume avec l'option noexec signifie qu'aucun exécutable sur le volume ne peut être exécuté dans le conteneur.

    Le montage du volume avec l'option nodev signifie qu'aucun périphérique sur le volume ne peut être utilisé par les processus dans le conteneur. Par défaut, les volumes sont montés avec nodev.

    Si HOST-DIR est un point de montage, alors les options dev, suid et exec sont ignorées par le noyau.

    Utilisez df HOST-DIR pour trouver le montage source, puis utilisez findmnt -o TARGET,PROPAGATION source-mount-dir pour trouver les propriétés de propagation du montage source. Si l'utilitaire findmnt(1) n'est pas disponible, on peut regarder l'entrée de montage pour le point de montage source dans /proc/self/mountinfo. Regardez dans les "champs optionnels" et voyez si des propriétés de propagation sont spécifiées. Là, shared:N signifie que le montage est partagé, master:N signifie que le montage est esclave, et s'il n'y a rien, le montage est privé. [1] ⟨#Footnote1⟩

    Pour changer les propriétés de propagation d'un point de montage, utilisez la commande mount(8). Par exemple, si l'on veut monter par liaison le répertoire source /foo, on peut faire mount --bind /foo /foo et mount --make-private --make-shared /foo. Cela convertit /foo en un point de montage partagé. Alternativement, on peut changer directement les propriétés de propagation du montage source. Disons que / est le montage source pour /foo, alors utilisez mount --make-shared / pour convertir / en un montage partagé.

    Note : si l'utilisateur n'a des droits d'accès qu'via un groupe, l'accès au volume depuis un conteneur sans privilèges échoue.

    Montage idmapped

    Si idmap est spécifié, créez un montage idmapped vers l'espace de noms utilisateur cible dans le conteneur. L'option idmap prend en charge un mappage personnalisé qui peut être différent de l'espace de noms utilisateur utilisé par le conteneur. Le mappage peut être spécifié après l'option idmap comme suit : idmap=uids=0-1-10#10-11-10;gids=0-100-10. Pour chaque triplet, la première valeur est le début des identifiants du système de fichiers sous-jacent qui sont mappés à la deuxième valeur sur l'hôte. La longueur de ce mappage est donnée par la troisième valeur. Plusieurs plages sont séparées par #.

    Utilisez l'option --group-add keep-groups pour transmettre l'accès aux groupes supplémentaires de l'utilisateur dans le conteneur.

    --volumes-from=CONTENEUR[:OPTIONS]

    Monte les volumes du ou des conteneurs spécifiés. Utilisé pour partager des volumes entre conteneurs. Les options sont une liste séparée par des virgules avec les éléments suivants disponibles :

    • rw|ro
    • z

    Monte les volumes déjà montés d'un conteneur source vers un autre conteneur. CONTENEUR peut être un nom ou un ID. Pour partager un volume, utilisez l'option --volumes-from lors de l'exécution du conteneur cible. Les volumes peuvent être partagés même si le conteneur source n'est pas en cours d'exécution.

    Par défaut, Podman monte les volumes dans le même mode (lecture-écriture ou lecture seule) qu'ils sont montés dans le conteneur source. Ceci peut être modifié en ajoutant une option ro ou rw.

    Les systèmes d'étiquetage comme SELinux nécessitent que des étiquettes appropriées soient placées sur le contenu du volume monté dans un conteneur. Sans étiquette, le système de sécurité pourrait empêcher les processus s'exécutant à l'intérieur du conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par le système d'exploitation.

    Pour changer une étiquette dans le contexte du conteneur, ajoutez z au montage du volume. Ce suffixe indique à Podman de ré-étiqueter les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux entités partagent le contenu du volume. En conséquence, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagé permettent à tous les conteneurs de lire/écrire le contenu.

    Si l'emplacement du volume du conteneur source chevauche des données résidant dans un conteneur cible, alors le volume masque ces données sur la cible.

    --workdir, -w=dir

    Répertoire de travail à l'intérieur du conteneur.

    Le répertoire de travail par défaut pour l'exécution des binaires à l'intérieur d'un conteneur est le répertoire racine (/). Le développeur de l'image peut définir une valeur par défaut différente avec l'instruction WORKDIR. L'opérateur peut remplacer le répertoire de travail en utilisant l'option -w.

    Statut de sortie

    Le code de sortie de podman run donne des informations sur la raison pour laquelle le conteneur n'a pas pu s'exécuter ou pourquoi il s'est terminé. Lorsque podman run se termine avec un code non nul, les codes de sortie suivent le standard de chroot(1), voir ci-dessous :

    125 L'erreur concerne Podman lui-même

    $ podman run --foo busybox; echo $?
Error: unknown flag: --foo
125

    126 La commande contenue ne peut pas être invoquée

    $ podman run busybox /etc; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"/etc\": permission denied": OCI runtime error
126

    127 La commande contenue est introuvable

    $ podman run busybox foo; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"foo\": executable file not found in $PATH": OCI runtime error
127

    Code de sortie code de sortie de la commande contenue

    $ podman run busybox /bin/sh -c 'exit 3'; echo $?
3

    EXEMPLES

    Exécution du conteneur en mode lecture seule

    Pendant le développement d'images de conteneurs, les conteneurs ont souvent besoin d'écrire dans le contenu de l'image. Installer des paquets dans /usr, par exemple. En production, les applications ont rarement besoin d'écrire dans l'image. Les applications de conteneurs écrivent dans des volumes s'ils ont besoin d'écrire dans des systèmes de fichiers. Les applications peuvent être rendues plus sécurisées en les exécutant en mode lecture seule à l'aide de l'interrupteur --read-only. Cela protège l'image du conteneur contre les modifications. Par défaut, les conteneurs en lecture seule peuvent écrire dans des données temporaires. Podman monte un tmpfs sur /run et /tmp à l'intérieur du conteneur.

    $ podman run --read-only -i -t fedora /bin/bash

    Si le conteneur n'écrit dans aucun système de fichiers à l'intérieur du conteneur, y compris tmpfs, définissez --read-only-tmpfs=false.

    $ podman run --read-only --read-only-tmpfs=false --tmpfs /run -i -t fedora /bin/bash

    Exposition des bibliothèques partagées à l'intérieur du conteneur en lecture seule à l'aide d'un glob

    $ podman run --mount type=glob,src=/usr/lib64/libnvidia\*,ro=true -i -t fedora /bin/bash

    Exposition des messages de log du conteneur au log de l'hôte

    Monte par liaison le répertoire /dev/log pour que les messages qui sont enregistrés dans le conteneur apparaissent dans le syslog/journal de l'hôte.

    $ podman run -v /dev/log:/dev/log -i -t fedora /bin/bash

    Depuis l'intérieur du conteneur, testez cela en envoyant un message au log.

    (bash)# logger "Hello from my container"

    Puis quittez et vérifiez le journal.

    (bash)# exit
$ journalctl -b | grep Hello

    Cela liste le message envoyé au logger.

    Attachement à un ou plusieurs à partir de STDIN, STDOUT, STDERR

    Sans spécifier l'option -a, Podman attache tout (stdin, stdout, stderr). Remplacez la valeur par défaut en spécifiant -a (stdin, stdout, stderr), comme dans :

    $ podman run -a stdin -a stdout -i -t fedora /bin/bash

    Partage de l'IPC entre conteneurs

    Utilisation de shm_server.c disponible ici : https://www.cs.cf.ac.uk/Dave/C/node27.html

    Test du mode --ipc=host :

    L'hôte affiche un segment de mémoire partagée avec 7 processus y étant attachés, il s'agit d'httpd :

    $ sudo ipcs -m
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status
0x01128e25 0          root       600        1000       7

    Maintenant, exécutez un conteneur régulier, et il ne voit correctement PAS le segment de mémoire partagée de l'hôte :

    $ podman run -it shm ipcs -m
------ Shared Memory Segments --------
key        shmid      owner      perms      bytes      nattch     status

    Exécutez un conteneur avec la nouvelle option --ipc=host, et il voit maintenant le segment de mémoire partagée de l'httpd de l'hôte :

    $ podman run -it --ipc=host shm ipcs -m
------ Shared Memory Segments
    -------- clé shmid propriétaire perms octets nattch statut 0x01128e25 0 root 600 1000 7

    Test du mode --ipc=container:id :

    Démarrez un conteneur avec un programme pour créer un segment de mémoire partagée :

    $ podman run -it shm bash
$ sudo shm/shm_server &
$ sudo ipcs -m
------ Segments de mémoire partagée --------
clé        shmid      propriétaire      perms      octets      nattch     statut
0x0000162e 0          root       666        27         1

    La création d'un 2ème conteneur montre correctement qu'il n'y a pas de segment de mémoire partagée du 1er conteneur :

    $ podman run shm ipcs -m
------ Segments de mémoire partagée --------
clé        shmid      propriétaire      perms      octets      nattch     statut

    La création d'un 3ème conteneur utilisant l'option --ipc=container:id montre maintenant le segment de mémoire partagée du premier :

    $ podman run -it --ipc=container:ed735b2264ac shm ipcs -m
$ sudo ipcs -m
------ Segments de mémoire partagée --------
clé        shmid      propriétaire      perms      octets      nattch     statut
0x0000162e 0          root       666        27         1

    Mappage des ports pour une utilisation externe

    Le port exposé d'une application peut être mappé à un port de l'hôte en utilisant le drapeau -p. Par exemple, le port 80 d'httpd peut être mappé au port 8080 de l'hôte en utilisant la commande suivante :

    $ podman run -p 8080:80 -d -i -t fedora/httpd

    Montage des volumes externes

    Pour monter un répertoire de l'hôte en tant que volume de conteneur, spécifiez le chemin absolu du répertoire et le chemin absolu du répertoire du conteneur séparés par un deux-points. Si la source est un volume nommé géré par Podman, il est recommandé d'utiliser son nom plutôt que le chemin vers le volume. Sinon, le volume est considéré comme orphelin et sera supprimé par la commande podman volume prune :

    $ podman run -v /var/db:/data1 -i -t fedora bash
$ podman run -v data:/data2 -i -t fedora bash
$ podman run -v /var/cache/dnf:/var/cache/dnf:O -ti fedora dnf -y update

    Si le conteneur a besoin d'un volume monté en écriture par un utilisateur non root à l'intérieur du conteneur, utilisez l'option U. Cette option indique à Podman de changer le propriétaire du volume source pour qu'il corresponde à l'UID et au GID par défaut utilisés dans le conteneur.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id -v ~/data:/var/lib/mysql:Z,U mariadb

    Alternativement, si le conteneur a besoin d'un volume en écriture par un utilisateur non root à l'intérieur du conteneur, l'option --userns=keep-id permet aux utilisateurs de spécifier l'UID et le GID de l'utilisateur exécutant Podman à des UIDs et GIDs spécifiques dans le conteneur. Étant donné que les processus s'exécutant dans le conteneur s'exécutent avec l'UID de l'utilisateur, ils peuvent lire/écrire des fichiers appartenant à l'utilisateur.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id:uid=999,gid=999 -v ~/data:/var/lib/mysql:Z mariadb

    En utilisant les drapeaux --mount pour monter un répertoire de l'hôte en tant que dossier de conteneur, spécifiez le chemin absolu du répertoire ou le nom du volume, et le chemin absolu à l'intérieur du répertoire du conteneur :

    $ podman run --mount type=bind,src=/var/db,target=/data1 busybox sh
$ podman run --mount type=bind,src=volume-name,target=/data1 busybox sh

    Lors de l'utilisation de SELinux, gardez à l'esprit que l'hôte n'a aucune connaissance de la politique SELinux du conteneur. Par conséquent, dans l'exemple ci-dessus, si la politique SELinux est appliquée, le répertoire /var/db n'est pas accessible en écriture par le conteneur. Un message "Permission Denied" apparaît, et un message avc: est ajouté au syslog de l'hôte.

    Pour contourner cela, au moment de la rédaction de cette page de manuel, la commande suivante doit être exécutée afin que le type d'étiquette de politique SELinux approprié soit attaché au répertoire de l'hôte :

    $ chcon -Rt svirt_sandbox_file_t /var/db

    Maintenant, l'écriture dans le volume /data1 dans le conteneur est autorisée et les modifications sont reflétées sur l'hôte dans /var/db.

    Utilisation d'un étiquetage de sécurité alternatif

    Remplacez le schéma d'étiquetage par défaut pour chaque conteneur en spécifiant le drapeau --security-opt. Par exemple, spécifiez le niveau MCS/MLS, une exigence pour les systèmes MLS. La spécification du niveau dans la commande suivante permet de partager le même contenu entre les conteneurs.

    podman run --security-opt label=level:s0:c100,c200 -i -t fedora bash

    Un exemple MLS pourrait être :

    $ podman run --security-opt label=level:TopSecret -i -t rhel7 bash

    Pour désactiver l'étiquetage de sécurité pour ce conteneur par rapport à l'exécution avec le

    drapeau --permissive, utilisez la commande suivante :

    $ podman run --security-opt label=disable -i -t fedora bash

    Renforcez la politique de sécurité sur les processus à l'intérieur d'un conteneur en spécifiant un type alternatif pour le conteneur. Par exemple, exécutez un conteneur qui n'est autorisé qu'à écouter sur les ports Apache en exécutant la commande suivante :

    $ podman run --security-opt label=type:svirt_apache_t -i -t centos bash

    Notez qu'une politique SELinux définissant un type svirt_apache_t doit être écrite.

    Pour masquer des chemins spécifiques supplémentaires dans le conteneur, spécifiez les chemins séparés par un deux-points en utilisant l'option mask avec le drapeau --security-opt.

    $ podman run --security-opt mask=/foo/bar:/second/path fedora bash

    Pour démasquer tous les chemins qui sont masqués par défaut, définissez l'option unmask sur ALL. Ou pour ne démasquer que des chemins spécifiques, spécifiez les chemins comme indiqué ci-dessus avec l'option mask.

    $ podman run --security-opt unmask=ALL fedora bash

    Pour démasquer tous les chemins qui commencent par /proc, définissez l'option unmask sur /proc/*.

    $ podman run --security-opt unmask=/proc/* fedora bash
    $ podman run --security-opt unmask=/foo/bar:/sys/firmware fedora bash

    Définition du poids de l'appareil via le drapeau --blkio-weight-device.

    $ podman run -it --blkio-weight-device "/dev/sda:200" ubuntu

    Utilisation d'un conteneur podman avec une entrée provenant d'un tuyau

    $ echo "asdf" | podman run --rm -i --entrypoint /bin/cat someimage
asdf

    Définition des conteneurs séparés par des espaces de noms utilisateur automatiques

    # podman run --userns=auto:size=65536 ubi8-micro cat /proc/self/uid_map
0 2147483647      65536
# podman run --userns=auto:size=65536 ubi8-micro cat /proc/self/uid_map
0 2147549183      65536

    Définition des paramètres du noyau dans un espace de noms (Sysctls)

    L'option --sysctl définit les paramètres du noyau dans un espace de noms (sysctls) dans le conteneur. Par exemple, pour activer le transfert IP dans l'espace de noms réseau du conteneur, exécutez cette commande :

    $ podman run --sysctl net.ipv4.ip_forward=1 someimage

    Notez que tous les sysctls ne sont pas isolés dans un espace de noms. Podman ne prend pas en charge la modification des sysctls à l'intérieur d'un conteneur qui modifie également le système hôte. À mesure que le noyau évolue, nous nous attendons à ce que davantage de sysctls soient isolés dans des espaces de noms.

    Consultez la définition de l'option --sysctl ci-dessus pour la liste actuelle des sysctls pris en charge.

    Définition du mappage UID/GID dans un nouvel espace de noms utilisateur

    L'exécution d'un conteneur dans un nouvel espace de noms utilisateur nécessite un mappage des UIDs et GIDs de l'hôte.

    $ podman run --uidmap 0:30000:7000 --gidmap 0:30000:7000 fedora echo hello

    Configuration des options de stockage depuis la ligne de commande

    Podman permet la configuration du stockage en modifiant les valeurs dans /etc/container/storage.conf ou en utilisant des options globales. Ceci montre comment utiliser un magasin d'images supplémentaire pour une exécution unique de busybox en utilisant des options globales.

    podman --log-level=debug --storage-opt "additionalimagestore=/tmp/readonly-images" run busybox /bin/sh

    Configuration du fuseau horaire dans un conteneur

    $ podman run --tz=local alpine date
$ podman run --tz=Asia/Shanghai alpine date
$ podman run --tz=US/Eastern alpine date

    Ajout de conteneurs de dépendance

    Le premier conteneur, container1, n'est pas démarré initialement, mais doit être en cours d'exécution avant que container2 ne démarre. La commande podman run démarre le conteneur automatiquement avant de démarrer container2.

    $ podman create --name container1 -t -i fedora bash
$ podman run --name container2 --requires container1 -t -i fedora bash

    Plusieurs conteneurs peuvent être requis.

    $ podman create --name container1 -t -i fedora bash
$ podman create --name container2 -t -i fedora bash
$ podman run --name container3 --requires container1,container2 -t -i fedora bash

    Configuration pour conserver les groupes supplémentaires pour l'accès au volume

    $ podman run -v /var/lib/design:/var/lib/design --group-add keep-groups ubi8

    Configuration du domaine d'exécution pour les conteneurs à l'aide du drapeau personality

    $ podman run --name container1 --personality=LINUX32 fedora bash

    Exécution d'un conteneur avec un rootfs externe monté en overlay

    $ podman run --name container1 --rootfs /path/to/rootfs:O bash

    Rootless Containers

    Podman runs as a non-root user on most systems. This feature requires that a new enough version of shadow-utils be installed. The shadow-utils package must include the newuidmap(1) and newgidmap(1) executables.

    In order for users to run rootless, there must be an entry for their username in /etc/subuid and /etc/subgid which lists the UIDs for their user namespace.

    Rootless Podman works better if the fuse-overlayfs and slirp4netns packages are installed. The fuse-overlayfs package provides a userspace overlay storage driver, otherwise users need to use the vfs storage driver, which can be disk space expensive and less performant than other drivers.

    To enable VPN on the container, slirp4netns or pasta needs to be specified; without either, containers need to be run with the --network=host flag.

    ENVIRONMENT

    Environment variables within containers can be set using multiple different options, in the following order of precedence (later entries override earlier entries):

    • Container image: Any environment variables specified in the container image.
    • --http-proxy: By default, several environment variables are passed in from the host, such as http_proxy and no_proxy. See --http-proxy for details.
    • --env-host: Host environment of the process executing Podman is added.
    • --env-file: Any environment variables specified via env-files. If multiple files are specified, then they override each other in order of entry.
    • --env: Any environment variables specified overrides previous settings.

    Run containers and set the environment ending with a *. The trailing * glob functionality is only active when no value is specified:

    $ export ENV1=a
$ podman run --env 'ENV*' alpine env | grep ENV
ENV1=a
$ podman run --env 'ENV*=b' alpine env | grep ENV
ENV*=b

    CONMON

    When Podman starts a container it actually executes the conmon program, which then executes the OCI Runtime. Conmon is the container monitor. It is a small program whose job is to watch the primary process of the container, and if the container dies, save the exit code. It also holds open the tty of the container, so that it can be attached to later. This is what allows Podman to run in detached mode (backgrounded), so Podman can exit but conmon continues to run. Each container has their own instance of conmon. Conmon waits for the container to exit, gathers and saves the exit code, and then launches a Podman process to complete the container cleanup, by shutting down the network and storage. For more information about conmon, see the conmon(8) man page.
