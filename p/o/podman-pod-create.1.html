podman-pod-create(1) Manuel des commandes générales podman-pod-create(1)

NOM

podman-pod-create - Créer un nouveau pod

SYNTAXE

podman pod create [options] [nom]

DESCRIPTION

Crée un pod vide, ou une unité de conteneurs multiples, et le prépare à l'ajout de conteneurs. Le pod peut être créé avec un nom spécifique. Si aucun nom n'est donné, un nom aléatoire est généré. L'ID du pod est imprimé sur STDOUT. Vous pouvez ensuite utiliser podman create --pod <id_pod|nom_pod> ... pour ajouter des conteneurs au pod, et podman pod start <id_pod|nom_pod> pour démarrer le pod.

L'opérateur peut identifier un pod de trois manières : identifiant long UUID (“f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778”) identifiant court UUID (“f78375b1c487”) Nom (“jonah”)

podman génère un UUID pour chaque pod, et si aucun nom n'est assigné au conteneur avec --name, alors un nom de chaîne aléatoire lui est généré. Ce nom est utile pour identifier un pod.

Note : les indicateurs liés aux limites de ressources fonctionnent en définissant les limites explicitement dans le parent cgroup du pod pour tous les conteneurs rejoignant le pod. Un conteneur peut outrepasser les limites de ressources lors de son ajout à un pod. Par exemple, si un pod a été créé via podman pod create --cpus=5, spécifier podman container create --pod=<id_pod|nom_pod> --cpus=4 fait que le conteneur utilise la limite la plus basse. De plus, les conteneurs qui spécifient leur propre cgroup, comme --cgroupns=host, ne reçoivent PAS les ressources cgroup assignées au niveau du pod.

OPTIONS

--add-host=nom_hote[;nom_hote[;...]]:ip

Ajoute un mappage hôte-vers-IP personnalisé au fichier /etc/hosts du pod.

L'option prend en charge un ou plusieurs noms d'hôtes séparés par des points-virgules, à mapper à une seule adresse IPv4 ou IPv6, séparés par deux-points. Elle peut également être utilisée pour écraser les adresses IP des noms d'hôtes que Podman ajoute à /etc/hosts par défaut (voir également les options --name et --hostname). Cette option peut être spécifiée plusieurs fois pour ajouter des mappages supplémentaires à /etc/hosts. Elle est en conflit avec l'option --no-hosts et avec no_hosts=true dans containers.conf.

Au lieu d'une adresse IP, le drapeau spécial host-gateway peut être donné. Celui-ci se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Podman puisse déterminer automatiquement l'adresse host-gateway, ce qui provoquera alors une erreur Podman. Vous pouvez écraser cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Podman pour ajouter automatiquement les noms d'hôtes host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez l'empêcher en donnant l'option --no-hosts, ou en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Podman ne parvient pas à déterminer l'adresse IP automatiquement, Podman omettra silencieusement d'ajouter ces noms d'hôtes internes à /etc/hosts. Si Podman s'exécute dans une machine virtuelle en utilisant podman machine (cela inclut les hôtes Mac et Windows), Podman omettra silencieusement d'ajouter les noms d'hôtes internes à /etc/hosts, sauf si une adresse IP a été configurée manuellement ; les noms d'hôtes internes sont résolus par le résolveur DNS gvproxy à la place.

Podman utilisera par défaut le fichier /etc/hosts de l'hôte comme base, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré en utilisant la configuration base_hosts_file dans containers.conf.

Le fichier /etc/hosts est partagé entre tous les conteneurs du pod.

--blkio-weight=poids

Poids relatif de l'entrée/sortie du blocage. Le poids est une valeur comprise entre 10 et 1000.

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif du périphérique pour l'entrée/sortie du blocage.

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup pour le pod est créé. Si le chemin n'est pas absolu, le chemin est considéré comme relatif au chemin cgroups du processus d'initialisation. Les cgroups sont créés s'ils n'existent pas déjà.

--cpu-shares, -c=parts

Parts du CPU (poids relatif).

Par défaut, tous les conteneurs obtiennent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est 1024.

La proportion ne s'applique que lorsque des processus intensifs en CPU sont en cours d'exécution. Lorsque les tâches d'un conteneur sont inactives, les autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, l'un ayant une part CPU de 1024 et les deux autres un réglage de part CPU de 512. Lorsque les processus de ces trois conteneurs tentent d'utiliser 100 % du CPU, le premier conteneur reçoit 50 % du temps CPU total. Si un quatrième conteneur est ajouté avec une part CPU de 1024, le premier conteneur n'obtient que 33 % du CPU. Les conteneurs restants reçoivent respectivement 16,5 %, 16,5 % et 33 % du CPU.

Sur un système multi-cœur, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100 % du temps CPU, il peut utiliser 100 % de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est lancé avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la division suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100% du CPU0
101 C1 1 100% du CPU1
102 C1 2 100% du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--cpus=quantité

Définit le nombre total de CPUs délégués au pod. La valeur par défaut est 0.000, ce qui indique qu'il n'y a pas de limite à la puissance de calcul.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par ex. 0,1), sous forme de plage (par ex. 0-3), ou toute combinaison de celles-ci (par ex. 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). N'est efficace que sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1, alors les processus du conteneur n'utilisent la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

--memory, -m=taille

Mémoire maximale à utiliser par le pod. La valeur peut être un entier suivi d'une unité de mesure comme b (octets), k (kibioctets), m (mebioctets), ou g (gibioctets). Si aucune unité n'est spécifiée, il est considéré comme des octets. Les valeurs par défaut sont illimitées.

La valeur 0 signifie illimité. Par exemple, -m 1GB

On some systems, changing the resource limits may not be allowed for non-root users. For more details, see https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

This option is not supported on cgroups V1 rootless systems.

--memory-reservation=taille

Quantité de mémoire garantie pour le pod.

This option is not supported on cgroups V1 rootless systems.

--memory-swap=taille

Mémoire totale et swap à utiliser par le pod. Cette option n'a de sens que si la mémoire est également limitée.

Cette option n'est pas prise en charge sur les systèmes sans privilèges cgroups V1.

--pod-id-file=chemin_fichier

Enregistrer l'ID du pod dans le fichier.

--quiet, -q

Ne pas imprimer l'ID du pod sur STDOUT.

--replace

Remplacer un pod existant.

--share-process-namespace, --sp

Partager les espaces de noms de processus avec le pod.

Les conteneurs du pod partageront le même espace de noms de processus. Cela signifie qu'ils verront les mêmes processus et pourront s'envoyer des signaux (par exemple, à l'aide de kill). Notez que cela ne peut être activé que lors de la création du pod.

--userns-remap=utilisateur[:groupe]

Utiliser le mappage d'espace de noms utilisateur pour le pod.

EXEMPLES

Créez un pod nommé 'webserver' avec des limites de CPU de 2 et 1 Go de mémoire :

$ podman pod create --name webserver --cpus=2 -m 1GB

Créez un pod sans nom avec des limites de ressources spécifiques :

$ podman pod create --cpu-shares=512 --memory=512m

Créez un pod et enregistrez son ID dans un fichier :

$ podman pod create --pod-id-file /tmp/my-pod-id

MANUAL OPTIONS

Les options suivantes sont spécifiques aux pods et ne s'appliquent pas aux conteneurs individuels créés avec podman create ou podman run.

--infra, --no-infra
La création d'un pod implique l'exécution d'un conteneur d'infrastructure qui maintient l'espace de noms réseau, IPC et PID du pod. Par défaut, Podman crée ce conteneur d'infrastructure (--infra). Avec --no-infra, ce conteneur d'infrastructure n'est pas créé. Cela est utile lors de la création de pods où les conteneurs sont censés fournir leur propre infrastructure, ou lorsque vous n'avez pas besoin d'un conteneur d'infrastructure. Il n'est pas possible de démarrer un pod si --no-infra a été utilisé pour le créer.

--device=périphérique-hôte[:périphérique-conteneur][:permissions]

Ajoute un périphérique hôte au pod. Le paramètre facultatif permissions peut être utilisé pour spécifier les permissions du périphérique en combinant r pour lecture, w pour écriture et m pour mknod(2).

Exemple : --device=/dev/sdc:/dev/xvdc:rwm.

Remarque : si périphérique-hôte est un lien symbolique, il est résolu en premier. Le pod ne stocke que les numéros majeurs et mineurs du périphérique hôte.

Podman peut charger les modules du noyau requis pour l'utilisation du périphérique spécifié. Les périphériques pour lesquels Podman charge des modules si nécessaire sont : /dev/fuse.

En mode rootless, le nouveau périphérique est monté par liaison dans le conteneur depuis l'hôte plutôt que Podman ne le crée dans l'espace du conteneur. Étant donné que le montage par liaison conserve son étiquette SELinux sur les systèmes SELinux, le conteneur peut recevoir une erreur de permission lors de l'accès au périphérique monté. Modifiez les paramètres SELinux pour autoriser les conteneurs à utiliser toutes les étiquettes de périphérique via la commande suivante :

$ sudo setsebool -P container_use_devices=true

Remarque : le pod implémente les périphériques en stockant la configuration initiale fournie par l'utilisateur et en recréant le périphérique pour chaque conteneur ajouté au pod.

--device-read-bps=chemin:débit

Limite le débit de lecture (en octets par seconde) à partir d'un périphérique (par exemple --device-read-bps=/dev/sda:1mo).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless avec cgroups V1.

--device-write-bps=chemin:débit

Limite le débit d'écriture (en octets par seconde) vers un périphérique (par exemple --device-write-bps=/dev/sda:1mo).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless avec cgroups V1.

--dns=adresse-ip

Définit des serveurs DNS personnalisés dans le fichier /etc/resolv.conf partagé entre tous les conteneurs du pod. Une option spéciale, "none", est autorisée, qui désactive la création de /etc/resolv.conf pour le pod.

--dns-option=option

Définit des options DNS personnalisées dans le fichier /etc/resolv.conf partagé entre tous les conteneurs du pod.

--dns-search=domaine

Définit des domaines de recherche DNS personnalisés dans le fichier /etc/resolv.conf partagé entre tous les conteneurs du pod.

--exit-policy=continue | stop

Définit la politique de sortie du pod lorsque le dernier conteneur se termine. Les politiques prises en charge sont :

Politique de sortie Description
continue Le pod continue de s'exécuter, en gardant son conteneur infra actif, lorsque le dernier conteneur se termine. Utilisé par défaut.
stop Le pod (y compris son conteneur infra) est arrêté lorsque le dernier conteneur se termine. Utilisé dans kube play et les quadlets.

--gidmap=gid-pod:gid-hôte:quantité

Mappage GID pour l'espace utilisateur. L'utilisation de ce drapeau exécute tous les conteneurs du pod avec l'espace utilisateur activé. Il entre en conflit avec les drapeaux --userns et --subgidname.

--gpus=ENTRÉE

Périphériques GPU à ajouter au conteneur ('all' pour passer tous les GPU) Actuellement, seuls les périphériques Nvidia sont pris en charge.

--help, -h

Affiche le message d'utilisation.

--hostname=nom

Définit le nom d'hôte du pod à l'intérieur de tous les conteneurs.

Le nom d'hôte donné est également ajouté au fichier /etc/hosts en utilisant l'adresse IP principale du conteneur (voir également l'option --add-host).

--hosts-file=chemin | none | image

Fichier de base pour créer le fichier /etc/hosts à l'intérieur du conteneur. Il doit s'agir d'un chemin absolu vers un fichier sur le système hôte, ou de l'un des indicateurs spéciaux suivants :
"" Utilise le base_hosts_file configuré dans containers.conf (par défaut)
none N'utilise aucun fichier de base (c'est-à-dire commence avec un fichier vide)
image Utilise le fichier /etc/hosts de l'image du conteneur comme fichier de base

--infra

Crée un conteneur infra et l'associe au pod. Un conteneur infra est un conteneur léger utilisé pour coordonner l'espace de noms du noyau partagé d'un pod. Par défaut : true.

--infra-command=commande

La commande exécutée pour démarrer le conteneur infra. Par défaut : "/pause".

--infra-conmon-pidfile=fichier

Écrit le PID du processus conmon du conteneur infra dans un fichier. Comme conmon s'exécute dans un processus séparé de Podman, cela est nécessaire lors de l'utilisation de systemd pour gérer les conteneurs et les pods Podman.

--infra-image=image

L'image personnalisée utilisée pour le conteneur infra. Sauf indication contraire, Podman crée une image locale personnalisée qui ne nécessite pas de téléchargement d'image.

--infra-name=nom

Le nom utilisé pour le conteneur infra du pod.

--ip=ipv4

Spécifie une adresse IPv4 statique pour le pod, par exemple 10.88.64.128. Cette option ne peut être utilisée que si le pod est connecté à un seul réseau – c'est-à-dire si --network=nom-réseau est utilisé au plus une fois – et si le pod ne rejoint pas l'espace de noms réseau d'un autre conteneur via --network=container:id. L'adresse doit être dans le pool d'adresses IP du réseau (par défaut 10.88.0.0/16).

Pour spécifier plusieurs adresses IP statiques par pod, définissez plusieurs réseaux en utilisant l'option --network avec une adresse IP statique spécifiée pour chacun en utilisant le mode ip pour cette option.

--ip6=ipv6

Spécifie une adresse IPv6 statique pour le pod, par exemple fd46:db93:aa76:ac37::10. Cette option ne peut être utilisée que si le pod est connecté à un seul réseau – c'est-à-dire si --network=nom-réseau est utilisé au plus une fois – et si le pod ne rejoint pas l'espace de noms réseau d'un autre conteneur via --network=container:id. L'adresse doit être dans le pool d'adresses IPv6 du réseau.

Pour spécifier plusieurs adresses IPv6 statiques par pod, définissez plusieurs réseaux en utilisant l'option --network avec une adresse IPv6 statique spécifiée pour chacun en utilisant le mode ip6 pour cette option.

--label, -l=clé=valeur

Ajoute des métadonnées à un pod.

--label-file=fichier

Lit un fichier délimité par des lignes d'étiquettes.

--mac-address=adresse

Adresse MAC de l'interface réseau du pod (par exemple 92:d0:c6:0a:29:33). Cette option ne peut être utilisée que si le pod est connecté à un seul réseau – c'est-à-dire si --network=nom-réseau est utilisé au plus une fois – et si le pod ne rejoint pas l'espace de noms réseau d'un autre conteneur via --network=container:id.

N'oubliez pas que l'adresse MAC dans un réseau Ethernet doit être unique. L'adresse link-local IPv6 est basée sur l'adresse MAC du périphérique conformément à la RFC4862.

Pour spécifier plusieurs adresses MAC statiques par pod, définissez plusieurs réseaux en utilisant l'option --network avec une adresse MAC statique spécifiée pour chacun en utilisant le mode mac pour cette option.

--memory, -m=nombre[unité]

Limite de mémoire. Une unité peut être o (octets), k (kio), m (mio) ou g (gio).

Permet de contraindre la mémoire disponible pour un conteneur. Si l'hôte prend en charge la mémoire swap, le réglage de mémoire -m peut être supérieur à la RAM physique. Si une limite de 0 est spécifiée (sans utiliser -m), la mémoire du conteneur n'est pas limitée. La limite réelle peut être arrondie à un multiple de la taille de page du système d'exploitation (la valeur est très grande, c'est des millions de trillions).

Cette option n'est pas prise en charge sur les systèmes rootless avec cgroups V1.

--memory-swap=nombre[unité]

Une valeur limite égale à la mémoire plus le swap. Une unité peut être o (octets), k (kio), m (mio) ou g (gio).

Doit être utilisé avec le drapeau -m (--memory). La valeur de l'argument doit être supérieure à celle de
-m (--memory). Par défaut, elle est définie sur le double de la valeur de --memory.

Définissez nombre sur -1 pour activer le swap illimité.

Cette option n'est pas prise en charge sur les systèmes rootless avec cgroups V1.

--name, -n=nom

Attribue un nom au pod.

--network=mode, --net

Définit le mode réseau du pod.

Les valeurs valides pour mode sont :

•
bridge[:OPTIONS,...] : Crée une pile réseau sur le pont par défaut. C'est le comportement par défaut pour les conteneurs rootful. Il est possible de spécifier les options supplémentaires suivantes :
  • alias=nom : Ajoute un alias spécifique au réseau pour le conteneur.
  • ip=IPv4 : Spécifie une adresse IPv4 statique pour ce conteneur.
  • ip6=IPv6 : Spécifie une adresse IPv6 statique pour ce conteneur.
  • mac=MAC : Spécifie une adresse MAC statique pour ce conteneur.
  • interface_name=name : Spécifie un nom pour l'interface réseau créée à l'intérieur du conteneur.
  • host_interface_name=name : Spécifie un nom pour l'interface réseau créée à l'extérieur du conteneur.
Toute autre option sera transmise à netavark sans validation. Cela peut être utile pour transmettre des arguments aux plugins netavark.

Par exemple, pour définir une adresse IPv4 statique et une adresse MAC statique, utilisez --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nom ou ID du réseau>[:OPTIONS,...] : Se connecter à un réseau défini par l'utilisateur ; il s'agit du nom ou de l'ID d'un réseau créé par podman network create. Il est possible de spécifier les mêmes options que celles décrites ci-dessus pour le mode bridge. Utilisez l'option --network plusieurs fois pour spécifier des réseaux supplémentaires.
    Pour des raisons de compatibilité ascendante, il est également possible de spécifier des réseaux séparés par des virgules dans le premier argument --network, cependant cela vous empêche d'utiliser les options décrites dans la section bridge ci-dessus.
  • none : Crée un espace de noms réseau pour le conteneur mais ne configure pas d'interfaces réseau pour celui-ci, le conteneur n'a donc aucune connectivité réseau.
  • container:id : Réutilise la pile réseau d'un autre conteneur.
  • host : Utilise l'espace de noms réseau de l'hôte pour le conteneur au lieu d'en créer un isolé. Attention : Cela donne au conteneur un accès complet aux sockets Unix abstraits et aux sockets TCP/UDP liés à localhost. Comme ces mécanismes sont souvent utilisés pour empêcher l'accès à des services système sensibles, en les isolant des entités externes, l'utilisation de cette option peut être considérée comme une vulnérabilité de sécurité.
  • ns:path : Chemin vers un espace de noms réseau à rejoindre.
  • private : Crée un nouvel espace de noms pour le conteneur. Ceci utilise le mode bridge pour les conteneurs rootful et slirp4netns pour les conteneurs rootless.
  • slirp4netns[:OPTIONS,...] : utilise slirp4netns(1) pour créer une pile réseau utilisateur. Il est possible de spécifier ces options supplémentaires, qui peuvent également être définies avec network_cmd_options dans containers.conf :
  • allow_host_loopback=true|false : Permet à slirp4netns d'atteindre l'IP de bouclage de l'hôte (par défaut, 10.0.2.2 ou la deuxième IP du sous-réseau CIDR de slirp4netns lorsqu'il est modifié, voir l'option cidr ci-dessous). La valeur par défaut est false.
  • mtu=MTU : Spécifie l'MTU à utiliser pour ce réseau. (Par défaut : 65520).
  • cidr=CIDR : Spécifie la plage d'IP à utiliser pour ce réseau. (Par défaut : 10.0.2.0/24).
  • enable_ipv6=true|false : Active l'IPv6. Par défaut : true. (Requis pour outbound_addr6).
  • outbound_addr=INTERFACE : Spécifie l'interface sortante sur laquelle slirp se lie (trafic IPv4 uniquement).
  • outbound_addr=IPv4 : Spécifie l'adresse IPv4 sortante sur laquelle slirp se lie.
  • outbound_addr6=INTERFACE : Spécifie l'interface sortante sur laquelle slirp se lie (trafic IPv6 uniquement).
  • outbound_addr6=IPv6 : Spécifie l'adresse IPv6 sortante sur laquelle slirp se lie.
  • port_handler=rootlesskit : Utilise rootlesskit pour la redirection de port. Par défaut.
    Note : Rootlesskit modifie l'adresse IP source des paquets entrants vers une adresse IP dans l'espace de noms réseau du conteneur, généralement 10.0.2.100. Si l'application nécessite la véritable adresse IP source, par exemple pour les journaux des serveurs web, utilisez le gestionnaire de ports slirp4netns. Le gestionnaire de ports rootlesskit est également utilisé pour les conteneurs rootless connectés à des réseaux définis par l'utilisateur.
  • port_handler=slirp4netns : Utilise la redirection de port slirp4netns, elle est plus lente que rootlesskit mais préserve la bonne adresse IP source. Ce gestionnaire de ports ne peut pas être utilisé pour les réseaux définis par l'utilisateur.
•
pasta[:OPTIONS,...] : utilise pasta(1) pour créer une pile de réseau en mode utilisateur.
C'est le mode par défaut pour les conteneurs rootless et il n'est pris en charge qu'en mode rootless.
Par défaut, les adresses et les routes IPv4 et IPv6, ainsi que le nom de l'interface pod, sont copiés de l'hôte. La redirection de port préserve l'adresse IP source d'origine. Les options décrites dans pasta(1) peuvent être spécifiées comme arguments séparés par des virgules.
En termes d'options de pasta(1), --config-net est donné par défaut, afin de configurer le réseau lors du démarrage du conteneur, et --no-map-gw est également supposé par défaut, pour éviter l'accès direct du conteneur à l'hôte en utilisant l'adresse de passerelle. Ce dernier peut être remplacé en passant --map-gw dans les options spécifiques à pasta (bien que ce ne soit pas une option réelle de pasta(1)).
Pour une meilleure intégration avec la gestion des DNS, --dns-forward 169.254.1.1 est passé, et cette adresse est ajoutée à resolv.conf(5) comme premier résolveur. Il est possible de passer --dns-forward explicitement au cas où une adresse IP différente devrait être utilisée. Pour que l'entrée host.containers.internal dans /etc/hosts fonctionne et permette les connexions à l'hôte, --map-guest-addr 169.254.1.2 est passé. Encore une fois, cela peut être défini explicitement pour choisir une adresse IP différente.
De plus, -t none et -u none sont passés si, respectivement, aucune redirection de port TCP ou UDP de l'hôte vers le conteneur n'est configurée (via --publish de Podman ou en passant directement les options -t/-u de pasta), afin de désactiver la redirection automatique de port basée sur les ports liés. De même, -T none et -U none sont donnés pour désactiver la même fonctionnalité du conteneur vers l'hôte.
Toutes les options peuvent également être définies dans containers.conf(5) ; voir la clé pasta_options dans la section network de ce fichier.
Quelques exemples :
  • pasta:--map-gw : Permet au conteneur d'atteindre directement l'hôte en utilisant l'adresse de passerelle.
  • pasta:--mtu,1500 : Spécifie une MTU de 1500 octets pour l'interface tap dans le conteneur.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) : désactive l'IPv6, attribue 10.0.2.0/24 à l'interface tap0 dans le conteneur, avec une passerelle 10.0.2.3, active le transmetteur DNS joignable à 10.0.2.3, définit la MTU à 1500 octets, désactive le support NDP, DHCPv6 et DHCP.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) avec les remplacements de Podman : identique à ci-dessus, mais laisse la MTU à 65520 octets
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto : active la redirection automatique de port basée sur les ports liés observés des côtés hôte et conteneur
  • pasta:-T,5201 : active la redirection du port TCP 5201 du conteneur vers l'hôte, en utilisant l'interface de bouclage au lieu de l'interface tap pour améliorer les performances

Invalide si vous utilisez --dns, --dns-option ou --dns-search avec --network défini sur none ou container:id.

--network-alias=alias

Ajoute un alias à l'échelle du réseau pour le pod, définissant l'alias pour tous les réseaux que le conteneur rejoint. Pour définir un nom uniquement pour un réseau spécifique, utilisez l'option alias comme décrit sous l'option --network. Si le réseau a le DNS activé (podman network inspect -f {{.DNSEnabled}} <nom>), ces alias peuvent être utilisés pour la résolution de noms sur le réseau donné. Cette option peut être spécifiée plusieurs fois. REMARQUE : Lors de l'utilisation de CNI, un pod n'a accès qu'aux alias du premier réseau qu'il rejoint. Cette limitation n'existe pas avec netavark/aardvark-dns.

--no-hostname

Ne crée pas le fichier /etc/hostname dans les conteneurs.

Par défaut, Podman gère le fichier /etc/hostname, en ajoutant le propre nom d'hôte du conteneur. Lorsque l'option --no-hostname est définie, le fichier /etc/hostname de l'image sera préservé sans modification s'il existe.

--no-hosts

Ne modifie pas le fichier /etc/hosts dans le pod.

Podman prend le contrôle du fichier /etc/hosts du pod par défaut et ajoute des entrées pour le nom du conteneur (voir l'option --name) et le nom d'hôte (voir l'option --hostname), les hôtes internes host.containers.internal et host.docker.internal, ainsi que tout nom d'hôte ajouté à l'aide de l'option --add-host. Référez-vous à l'option --add-host pour plus de détails. Passer --no-hosts désactive cela, de sorte que le fichier /etc/hosts de l'image reste inchangé. La même chose peut être obtenue globalement en définissant no_hosts=true dans containers.conf.

Cette option est en conflit avec --add-host.

--pid=pid

Définit le mode PID pour le pod. La valeur par défaut est de créer un espace de noms PID privé pour le pod. Nécessite que l'espace de noms PID soit partagé via --share.

host: utilise l'espace de noms PID de l'hôte pour le pod
ns: rejoint l'espace de noms PID spécifié
private: crée un nouvel espace de noms pour le pod (par défaut)

--pod-id-file=path

Écrit l'ID du pod dans le fichier.

--publish, -p=[[ip:][portHote]:portConteneur[/protocole]]

Publie un port de conteneur, ou une plage de ports, au sein de ce pod vers l'hôte.

Les deux portHote et portConteneur peuvent être spécifiés sous forme de plages de ports. Lors de la spécification de plages pour les deux, le nombre de ports de conteneur dans la plage doit correspondre au nombre de ports hôtes dans la plage.

Si l'IP de l'hôte est définie sur 0.0.0.0 ou n'est pas définie du tout, le port est lié à toutes les IPs sur l'hôte.

Par défaut, Podman publie les ports TCP. Pour publier un port UDP à la place, donnez udp comme protocole. Pour publier des ports TCP et UDP, définissez --publish deux fois, avec tcp et udp comme protocoles respectivement. Les conteneurs rootful peuvent également publier des ports en utilisant le protocole sctp.

Le port hôte n'a pas besoin d'être spécifié (par exemple, podman run -p 127.0.0.1::80). S'il ne l'est pas, un port est attribué aléatoirement au port du conteneur sur l'hôte.

Utilisez podman port pour voir la cartographie réelle : podman port $CONTENEUR $PORT_CONTENEUR.

La publication de port n'est prise en charge que pour les conteneurs qui utilisent leur propre espace de noms réseau

acez les réseaux bridge, ou les modes réseau pasta et slirp4netns.

Note : Vous ne devez pas publier les ports des conteneurs individuellement dans le pod, mais uniquement par le pod lui-même.

Note : Ceci ne peut pas être modifié une fois le pod créé.

--replace

Si un autre pod portant le même nom existe déjà, il est remplacé et supprimé. La valeur par défaut est false.

--restart=politique

Politique de redémarrage à suivre lorsque les conteneurs se terminent. La politique de redémarrage ne prend pas effet si un conteneur est arrêté via les commandes podman kill ou podman stop.

Les valeurs valides pour politique sont :

  • no : Ne pas redémarrer les conteneurs à la sortie
  • never : Synonyme de no ; ne pas redémarrer les conteneurs à la sortie
  • on-failure[:max_retries] : Redémarrer les conteneurs lorsqu'ils se terminent avec un code de sortie non nul, en réessayant indéfiniment ou jusqu'à ce que le nombre optionnel max_retries soit atteint
  • always : Redémarrer les conteneurs lorsqu'ils se terminent, quel que soit leur état, en réessayant indéfiniment
  • unless-stopped : Identique à always

Podman fournit un fichier d'unité systemd, podman-restart.service, qui redémarre les conteneurs après un redémarrage du système.

Lors de l'exécution de conteneurs dans des services systemd, utilisez la fonctionnalité de redémarrage fournie par systemd. En d'autres termes, n'utilisez pas cette option dans une unité de conteneur, mais définissez la directive systemd Restart= dans la section [Service]. Voir podman-systemd.unit(5) et systemd.service(5).

Politique de redémarrage par défaut pour tous les conteneurs d'un pod.

--security-opt=option

Options de sécurité

  • apparmor=unconfined : Désactiver le confinement apparmor pour le pod
  • apparmor=profil-alternatif : Définir le profil de confinement apparmor pour le pod
  • label=user:UTILISATEUR : Définir l'utilisateur de label pour les processus du pod
  • label=role:RÔLE : Définir le rôle de label pour les processus du pod
  • label=type:TYPE : Définir le type de processus de label pour les processus du pod
  • label=level:NIVEAU : Définir le niveau de label pour les processus du pod
  • label=filetype:TYPE : Définir le type de fichier de label pour les fichiers du pod
  • label=disable : Désactiver la séparation des labels pour le pod

Note : Le marquage peut être désactivé pour tous les pods/conteneurs en définissant label=false dans le fichier containers.conf (/etc/containers/containers.conf ou $HOME/.config/containers/containers.conf).

  • label=nested : Permet les modifications SELinux à l'intérieur du conteneur. Les conteneurs sont autorisés à modifier les labels SELinux sur les fichiers et les processus, tant que la politique SELinux le permet. Sans nested, les conteneurs voient SELinux comme désactivé, même lorsqu'il est activé sur l'hôte. Les conteneurs ne peuvent pas définir de labels.
  • mask=/chemin/1:/chemin/2 : Les chemins à masquer séparés par un deux-points. Un chemin masqué ne peut pas être accédé à l'intérieur des conteneurs du pod.
  • no-new-privileges : Désactive l'acquisition de privilèges supplémentaires par les processus du conteneur via l'appel système execve(2) (par exemple, via les bits setuid ou setgid, ou via les capacités de fichier). Les programmes qui dépendent des bits setuid/setgid définis sur leur exécutable pour changer l'ID utilisateur ou l'ID groupe ne peuvent plus le faire, et toutes les capacités de fichier ajoutées à l'exécutable (par exemple, via setcap) ne sont pas ajoutées à l'ensemble des capacités autorisées. Pour plus de détails, voir : https://docs.kernel.org/userspace-api/no_new_privs.html.
  • seccomp=unconfined : Désactiver le confinement seccomp pour le pod.
  • seccomp=profile.json : Fichier JSON à utiliser comme filtre seccomp. Notez que l'annotation io.podman.annotations.seccomp est définie avec la valeur spécifiée, comme indiqué dans podman inspect.
  • proc-opts=OPTIONS : Liste d'options séparées par des virgules à utiliser pour le montage /proc. Plus de détails sur les options de montage possibles sont spécifiés dans la page de manuel proc(5).
  • unmask=ALL ou /chemin/1:/chemin/2, ou chemins expansés par shell (/proc/*) : Chemins à démasquer séparés par un deux-points. Si défini sur ALL, il démasque tous les chemins qui sont masqués ou rendus en lecture seule par défaut. Les chemins masqués par défaut sont /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, et /sys/fs/selinux, /sys/devices/virtual/powercap. Les chemins par défaut qui sont en lecture seule sont /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

Note : Le marquage peut être désactivé pour tous les conteneurs en définissant label=false dans le fichier containers.conf(5).

--share=namespace

Une liste d'espaces de noms de noyau séparés par des virgules à partager. Si aucun ou "" n'est spécifié, aucun espace de noms n'est partagé, et le conteneur infra n'est pas créé à moins d'être explicitement spécifié via --infra=true. Les espaces de noms parmi lesquels choisir sont cgroup, ipc, net, pid, uts. Si l'option est précédée d'un "+", l'espace de noms est ajouté à la liste par défaut. Sinon, il remplace la liste par défaut. Les valeurs par défaut correspondent aux valeurs par défaut de Kubernetes (ipc, net, uts).

--share-parent

Ce booléen détermine si tous les conteneurs entrant dans le pod utilisent le pod comme parent cgroup. La valeur par défaut de cette option est true. Utilisez l'option --share pour partager l'espace de noms cgroup plutôt qu'un parent cgroup dans un pod.

Note : Cette option est en conflit avec l'option --share=cgroup car cette option définit le pod comme parent cgroup mais place le conteneur dans le même cgroupNS que le conteneur infra.

--shm-size=nombre[unité]

Taille de /dev/shm. Une unité peut être b (octets), k (kibioctets), m (mebioctets), ou g (gibioctets). Si l'unité est omise, le système utilise les octets. Si la taille est omise, la valeur par défaut est 64m. Lorsque taille est 0, il n'y a aucune limite à la quantité de mémoire utilisée pour l'IPC par le pod. Cette option est en conflit avec --ipc=host.

--shm-size-systemd=nombre[unité]

Taille des montages tmpfs spécifiques à systemd tels que /run, /run/lock, /var/log/journal et /tmp. Une unité peut être b (octets), k (kibioctets), m (mebioctets), ou g (gibioctets). Si l'unité est omise, le système utilise les octets. Si la taille est omise, la valeur par défaut est 64m. Lorsque taille est 0, l'utilisation est limitée à 50% de la mémoire disponible de l'hôte.

--subgidname=nom

Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant le mapping avec nom dans le fichier /etc/subgid. Si vous exécutez en tant que non-root, l'utilisateur doit avoir le droit d'utiliser le mapping. Voir subgid(5). Ce drapeau est en conflit avec --userns et --gidmap.

--subuidname=nom

Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant le mapping avec nom dans le fichier /etc/subuid. Si vous exécutez en tant que non-root, l'utilisateur doit avoir le droit d'utiliser le mapping. Voir subuid(5). Ce drapeau est en conflit avec --userns et --uidmap.

Définit le mode d'espace de noms utilisateur pour tous les conteneurs d'un pod. Il est défini par défaut par la variable d'environnement PODMAN_USERNS. Une valeur vide ("") signifie que les espaces de noms utilisateur sont désactivés.

--user=username[:groupname]

Run the specified user and group inside the container. The user and group must exist within the container's filesystem. The user and group can be specified by name or by UID/GID. If only a username/UID is specified, the primary group of that user is used. If the user/UID is specified with its primary group, the container will run with that UID/GID pair. If only the group/GID is specified, the user is set to root (0).

If the user is specified with a UID and GID that are not mapped in the user namespace, the user can potentially perform actions outside the container that the user running Podman can perform on the host.

The default behavior is to run as the user and group defined in the container image. If the user and group are not defined in the image, Podman defaults to the UID and GID of the user running Podman on the host.

When using user namespaces, the --user option can be used in conjunction with --uidmap and --gidmap options. See user(5) for more details about user namespaces.

When the container is run as a non-root user, the user has the same privileges on the host as any other process launched by the calling user (default).

  • keep-id: crée un espace de noms utilisateur où l'UID:GID de l'utilisateur sans privilèges actuel est mappé aux mêmes valeurs dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.
  • nomap: crée un espace de noms utilisateur où l'UID:GID de l'utilisateur sans privilèges actuel n'est pas mappé dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.

--uts=mode

Définit le mode de l'espace de noms UTS pour le pod. Les valeurs suivantes sont prises en charge:

  • host: utilise l'espace de noms UTS de l'hôte dans le pod.
  • private: crée un nouvel espace de noms pour le pod (par défaut).
  • ns:[chemin]: exécute le pod dans l'espace de noms UTS existant donné.

--volume, -v=[[SOURCE-VOLUME|RÉPERTOIRE-HÔTE:]RÉPERTOIRE-CONTENEUR[:OPTIONS]]

Crée un montage par liaison (bind mount). Si -v /RÉPERTOIRE-HÔTE:/RÉPERTOIRE-CONTENEUR est spécifié, Podman monte par liaison /RÉPERTOIRE-HÔTE de l'hôte dans /RÉPERTOIRE-CONTENEUR dans le conteneur Podman. De même, -v SOURCE-VOLUME:/RÉPERTOIRE-CONTENEUR monte le volume nommé depuis l'hôte dans le conteneur. Si aucun volume nommé de ce type n'existe, Podman en crée un. Si aucune source n'est donnée, le volume est créé en tant que volume anonyme avec un nom généré aléatoirement, et est supprimé lorsque le pod est supprimé via le drapeau --rm ou la commande podman rm --volumes.

(Remarque lors de l'utilisation du client distant, y compris les machines Mac et Windows (à l'exclusion de WSL2), les volumes sont montés depuis le serveur distant, pas nécessairement la machine cliente.)

Les OPTIONS sont une liste séparée par des virgules et peuvent être une ou plusieurs des options suivantes:

  • rw|ro
  • z|Z
  • [O]
  • [U]
  • [no]copy
  • [no]dev
  • [no]exec
  • [no]suid
  • [r]bind
  • [r]shared|[r]slave|[r]private[r]unbindable [1] ⟨#Footnote1⟩
  • idmap[=options]

Le RÉPERTOIRE-CONTENEUR doit être un chemin absolu tel que /src/docs. Le volume est monté dans le conteneur à ce répertoire.

Si une source de volume est spécifiée, elle doit être un chemin sur l'hôte ou le nom d'un volume nommé. Les chemins d'hôte peuvent être absolus ou relatifs; les chemins relatifs sont résolus par rapport au répertoire dans lequel Podman est exécuté. Si la source n'existe pas, Podman renvoie une erreur. Les utilisateurs doivent pré-créer les fichiers ou répertoires source.

Toute source qui ne commence pas par un . ou un / est traitée comme le nom d'un volume nommé. Si un volume portant ce nom n'existe pas, il est créé. Les volumes créés avec des noms ne sont pas anonymes et ils ne sont pas supprimés par l'option --rm et la commande podman rm --volumes.

Spécifiez plusieurs options -v pour monter un ou plusieurs volumes dans un pod.

Montages de volumes protégés en écriture

Ajoutez l'option :ro ou :rw pour monter un volume en mode lecture seule ou lecture-écriture, respectivement. Par défaut, les volumes sont montés en lecture-écriture. Voir les exemples.

Changement de propriétaire des montages de volumes

Lorsqu'un volume nommé est monté pour la première fois sur un conteneur, Podman ajuste automatiquement la propriété du point de montage du volume lors de l'initialisation du conteneur. Cette opération de changement de propriétaire (chown) se produit dans les conditions suivantes:

  • Le volume n'a pas encore été utilisé (a NeedsChown défini sur true)
  • Le volume est vide ou n'a pas encore été copié
  • Le volume n'est pas géré par un pilote de volume externe
  • Le pilote de volume n'est pas "image"

Pour les volumes avec des montages idmappés (utilisant l'option idmap), le changement de propriété prend en compte les mappages d'espaces de noms utilisateur du conteneur, mais le volume idmappé conserve un mappage UID/GID correct. Pour les volumes sans idmapping, le point de montage est chowné pour correspondre à l'utilisateur et au groupe du processus du conteneur, mappé à l'espace de noms utilisateur de l'hôte si le remappage d'espace de noms utilisateur est activé.

Si un pod est créé dans un nouvel espace de noms utilisateur, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte.

Le suffixe :U indique à Podman d'utiliser l'UID et le GID de l'hôte corrects basés sur l'UID et le GID à l'intérieur du pod, pour changer récursivement le propriétaire et le groupe du volume source. Le changement de propriétaire parcourt le système de fichiers sous le volume et modifie l'UID/GID de chaque fichier. Si le volume a des milliers d'inodes, ce processus prend du temps, retardant le démarrage du pod.

Attention utilisez avec prudence car cela modifie le système de fichiers de l'hôte.

Étiquetage des montages de volumes

Les systèmes d'étiquetage comme SELinux nécessitent que des étiquettes correctes soient placées sur le contenu du volume monté dans un pod. Sans étiquette, le système de sécurité peut empêcher les processus s'exécutant à l'intérieur du pod d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par l'OS.

Pour modifier une étiquette dans le contexte du pod, ajoutez l'un des deux suffixes :z ou :Z au montage du volume. Ces suffixes indiquent à Podman de relabéliser les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux pods ou plus partagent le contenu du volume. En conséquence, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagé permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman d'étiqueter le contenu avec une étiquette privée non partagée. Seul le pod actuel peut utiliser un volume privé.

Remarque: tous les conteneurs d'un pod partagent la même étiquette SELinux. Cela signifie que tous les conteneurs de ce pod peuvent lire/écrire les volumes partagés dans le conteneur créé avec le :Z sur l'un quelconque des conteneurs. Le relabélage parcourt le système de fichiers sous le volume et modifie l'étiquette de chaque fichier; si le volume a des milliers d'inodes, ce processus prend du temps, retardant le démarrage du pod. Si le volume a été précédemment relabélisé avec l'option z, Podman est optimisé pour ne pas relabéliser une deuxième fois. Si des fichiers sont déplacés dans le volume, les étiquettes peuvent être modifiées manuellement avec la commande chcon -Rt container_file_t CHEMIN.

Remarque: ne relabélisez pas les fichiers et répertoires système. Le relabélage de contenu système peut entraîner l'échec d'autres services confinés sur la machine. Pour ces types de conteneurs, nous recommandons de désactiver la séparation SELinux. L'option --security-opt label=disable désactive la séparation SELinux pour le pod. Par exemple, si un utilisateur voulait monter son répertoire personnel entier dans un pod, il doit désactiver la séparation SELinux.

$ podman pod create --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

Montages de volumes superposés (Overlay)

Le drapeau :O indique à Podman de monter le répertoire de l'hôte en tant que stockage temporaire à l'aide du système de fichiers overlay. Les processus du pod peuvent modifier le contenu à l'intérieur du point de montage, qui est stocké dans le stockage du conteneur dans un répertoire séparé. En termes d'overlay, le répertoire source est le niveau inférieur (lower) et le répertoire de stockage du conteneur est le niveau supérieur (upper). Les modifications apportées au point de montage sont détruites lorsque le pod a fini son exécution, de manière similaire à un point de montage tmpfs qui est démonté.

Pour les utilisateurs avancés, l'option overlay prend également en charge des upperdir et workdir personnalisés et non volatils pour le montage overlay. Les upperdir et workdir personnalisés peuvent être entièrement gérés par les utilisateurs eux-mêmes, et Podman ne les supprime pas à la fin du cycle de vie. Exemple: :O,upperdir=/some/upper,workdir=/some/work

Les exécutions ultérieures du conteneur voient le contenu du répertoire source d'origine, toutes les modifications des exécutions de pod précédentes n'existent plus.

Un cas d'utilisation du montage overlay est le partage du cache de paquets de l'hôte dans le conteneur pour accélérer les builds.

Remarque: le drapeau O entre en conflit avec les autres options listées ci-dessus.

Le contenu monté dans le conteneur est étiqueté avec l'étiquette privée. Sur les systèmes SELinux, les étiquettes dans le répertoire source doivent être lisibles par l'étiquette de conteneur d'infrastructure du pod. Habituellement, les conteneurs peuvent lire/exécuter container_share_t et peuvent lire/écrire container_file_t. Si les étiquettes sur un volume source ne peuvent pas être modifiées, la séparation SELinux des conteneurs doit être désactivée pour que le pod ou le conteneur d'infrastructure fonctionne.

Ne modifiez pas le répertoire source monté dans le pod avec un montage overlay, cela peut entraîner des échecs inattendus. Modifiez le répertoire uniquement après la fin de l'exécution du conteneur.

Propagation des montages

Par défaut, les volumes montés par liaison sont privés. Cela signifie que tous les montages effectués à l'intérieur du pod ne sont pas visibles sur l'hôte et vice versa. On peut changer ce comportement en spécifiant une propriété de propagation de montage de volume. Lorsqu'un volume est partagé (shared), les montages effectués sous ce volume à l'intérieur du pod sont visibles sur l'hôte et vice versa. Rendre un volume esclave (slave) [1] ⟨#Footnote1⟩ active la propagation de montage unidirectionnelle: les montages effectués sur l'hôte sous ce volume sont visibles dans le conteneur, mais pas l'inverse.

Pour contrôler la propriété de propagation de montage d'un volume, vous pouvez utiliser le drapeau de propagation [r]shared, [r]slave, [r]private ou [r]unbindable. La propriété de propagation ne peut être spécifiée que pour les volumes montés par liaison et non pour les volumes internes ou les volumes nommés. Pour que la propagation de montage fonctionne, le point de montage source (le point de montage où le répertoire source est monté) doit avoir les bonnes propriétés de propagation. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le point de montage source doit être partagé ou esclave. [1] ⟨#Footnote1⟩

Pour monter récursivement un volume et tous ses sous-montages dans un pod, utilisez l'option rbind. Par défaut, l'option bind est utilisée, et les sous-montages du répertoire source ne sont pas montés dans le pod.

Monter le volume avec une option copy indique à podman de copier le contenu du répertoire de destination sous-jacent sur les volumes internes nouvellement créés. La copie ne se produit que lors de la création initiale du volume. Le contenu n'est pas copié lorsque le volume est utilisé ultérieurement sur différents conteneurs. L'option copy est ignorée sur les montages par liaison et n'a aucun effet.

Monter des volumes avec l'option nosuid signifie que les exécutables SUID sur le volume ne peuvent pas être utilisés par les applications pour changer leurs privilèges. Par défaut, les volumes sont montés avec nosuid.

Monter le volume avec l'option noexec signifie qu'aucun exécutable sur le volume ne peut être exécuté dans le pod.

Monter le volume avec l'option nodev signifie qu'aucun périphérique sur le volume ne peut être utilisé par les processus à l'intérieur du pod. Par défaut, les volumes sont montés avec nodev

b>.

Si le HOST-DIR est un point de montage, alors les options dev, suid et exec sont ignorées par le noyau.

Utilisez df HOST-DIR pour identifier le montage source, puis utilisez findmnt -o TARGET,PROPAGATION source-mount-dir pour identifier la propagation propriétés du montage source. Si l'utilitaire findmnt(1) n'est pas disponible, alors on peut regarder l'entrée de montage du point de montage source dans /proc/self/mountinfo. Regardez les "champs optionnels" et voyez si des propriétés de propagation sont spécifiées. Là, shared:N signifie que le montage est partagé, master:N signifie que le montage est esclave, et si rien n'est là, le montage est privé. [1] ⟨#Footnote1⟩

Pour modifier les propriétés de propagation d'un point de montage, utilisez la commande mount(8). Par exemple, si l'on souhaite faire un montage de liaison du répertoire source /foo, on peut faire mount --bind /foo /foo et mount --make-private --make-shared /foo. Ceci convertit /foo en un point de montage partagé. Alternativement, on peut modifier directement les propriétés de propagation du montage source. Disons que / est le montage source pour /foo, alors utilisez mount --make-shared / pour convertir / en un montage partagé.

Note : si l'utilisateur n'a accès que via un groupe, l'accès au volume depuis un pod sans root échoue.

Montage idmapped

Si idmap est spécifié, créez un montage idmapped vers l'espace de noms utilisateur cible dans le conteneur. L'option idmap prend en charge un mappage personnalisé qui peut être différent de l'espace de noms utilisateur utilisé par le conteneur. Le mappage peut être spécifié après l'option idmap comme ceci : idmap=uids=0-1-10#10-11-10;gids=0-100-10. Pour chaque triplet, la première valeur est le début des identifiants du système de fichiers sous-jacent qui sont mappés à la deuxième valeur sur l'hôte. La longueur de ce mappage est donnée dans la troisième valeur. Plusieurs plages sont séparées par #.

--volumes-from=CONTENEUR[:OPTIONS]

Monte les volumes du (des) conteneur(s) spécifié(s). Utilisé pour partager des volumes entre conteneurs et pods. Les options est une liste séparée par des virgules avec les éléments suivants disponibles :

  • rw|ro
  • z

Monte les volumes déjà montés d'un conteneur source sur un autre pod. CONTENEUR peut être un nom ou un ID. Pour partager un volume, utilisez l'option --volumes-from lors de l'exécution du conteneur cible. Les volumes peuvent être partagés même si le conteneur source n'est pas en exécution.

Par défaut, Podman monte les volumes dans le même mode (lecture-écriture ou lecture seule) qu'il est monté dans le conteneur source. Ceci peut être modifié en ajoutant une option ro ou rw.

Les systèmes d'étiquetage comme SELinux exigent que les étiquettes correctes soient placées sur le contenu du volume monté dans un pod. Sans étiquette, le système de sécurité pourrait empêcher les processus en cours d'exécution à l'intérieur du conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par l'OS.

Pour modifier une étiquette dans le contexte du pod, ajoutez z au montage du volume. Ce suffixe indique à Podman de ré-étiqueter les objets fichiers sur les volumes partagés. L'option z indique à Podman que deux entités partagent le contenu du volume. Par conséquent, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagées permettent à tous les conteneurs de lire/écrire le contenu.

Si l'emplacement du volume du conteneur source chevauche des données résidant sur un pod cible, alors le volume masque ces données sur la cible.

EXEMPLES

Créer un pod nommé.

$ podman pod create --name test

Créer un pod nommé.

$ podman pod create mypod

Créer un pod sans conteneur infra.

$ podman pod create --infra=false

Créer un pod nommé avec une commande pour le conteneur infra à exécuter.

$ podman pod create --infra-command /top toppod

Créer un pod avec des ports publiés sur l'hôte.

$ podman pod create --publish 8443:443

Créer un pod avec la configuration réseau spécifiée.

$ podman pod create --network slirp4netns:outbound_addr=127.0.0.1,allow_host_loopback=true

Créer un pod avec le réseau spécifié.

$ podman pod create --network pasta

Créer un pod sur deux réseaux.

$ podman pod create --network net1:ip=10.89.1.5 --network net2:ip=10.89.10.10

Créer un pod avec des limites CPU et mémoire partagées pour tous les conteneurs.

$ podman pod create --cpus=2 --memory=512m mypod

Créer un pod avec des montages de volumes partagés accessibles à tous les conteneurs.

$ podman pod create --volume /host/path:/container/path:Z mypod

Créer un pod avec des limites de ressources partagées et des montages de volumes pour tous les conteneurs.

$ podman pod create --volume /data:/data:Z --volume /config:/etc/config:ro --cpus=1.5 --memory=1g --cpu-shares=512 mypod

Créer un pod avec accès aux périphériques partagés et limites de ressources.

$ podman pod create --device /dev/sda:/dev/sda:rw --cpus=4 --memory=2g --blkio-weight=500 mypod

Créer un pod avec des limites d'ensembles CPU partagés et des volumes provenant d'un autre conteneur qui seront partagés avec tous les conteneurs du pod.

$ podman pod create --cpuset-cpus=0,2 --volumes-from=source-container --memory=1g mypod

Créer un pod avec des ressources partagées et ajouter des conteneurs à celui-ci.

$ podman pod create --cpus=2 --memory=1g --volume /data:/data:Z mypod
$ podman create --pod mypod nginx
$ podman create --pod mypod redis
