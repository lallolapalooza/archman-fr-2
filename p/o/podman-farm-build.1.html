NAME

podman-farm-build - Construit des images sur les nœuds de la ferme, puis les regroupe dans une liste de manifestes

SYNOPSIS

podman farm build [options] [contexte]

DESCRIPTION

podman farm build Construit une image sur tous les nœuds d'une ferme et les regroupe dans une liste de manifestes. Il exécute la commande podman build sur les nœuds de la ferme avec le Containerfile donné. Une fois les images construites sur tous les nœuds de la ferme, les images seront poussées vers le registre spécifié via le drapeau --tag. Une fois que toutes les images ont été poussées, une liste de manifestes sera créée localement et poussée également vers le registre.

La liste de manifestes contiendra une image par type d'architecture native présent dans la ferme.

La fonction principale de cette commande est de créer des constructions multi-architectures qui seront plus rapides que de le faire par émulation en utilisant podman build --arch --platform.

Si aucune ferme n'est spécifiée, la construction sera envoyée à tous les nœuds que podman system connection connaît.

Remarque : Étant donné que les images construites sont directement poussées vers un registre, l'utilisateur doit passer un nom d'image complet en utilisant l'option --tag sous la forme registre/répertoire/nomImage[:étiquette]`.

OPTIONS

--add-host=hostname[;hostname[;...]]:ip

Ajoute un mappage personnalisé hôte-IP au fichier /etc/hosts du conteneur.

L'option prend un ou plusieurs noms d'hôtes séparés par des points-virgules à mapper à une seule adresse IPv4 ou IPv6, séparés par un deux-points. Elle peut également être utilisée pour remplacer les adresses IP des noms d'hôtes que Podman ajoute à /etc/hosts par défaut (voir aussi les options --name et --hostname). Cette option peut être spécifiée plusieurs fois pour ajouter des mappages supplémentaires à /etc/hosts. Elle entre en conflit avec l'option --no-hosts et avec no_hosts=true dans containers.conf.

Au lieu d'une adresse IP, le drapeau spécial host-gateway peut être donné. Cela se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Podman puisse déterminer l'adresse host-gateway automatiquement, ce qui entraînera un échec de Podman avec un message d'erreur. Vous pouvez remplacer cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Podman pour ajouter automatiquement les noms d'hôtes host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez empêcher cela en donnant l'option --no-hosts, ou en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Podman ne parvient pas à déterminer l'adresse IP automatiquement, Podman omettra silencieusement d'ajouter ces noms d'hôtes internes à /etc/hosts. Si Podman s'exécute dans une machine virtuelle en utilisant podman machine (y compris les hôtes Mac et Windows), Podman omettra silencieusement d'ajouter les noms d'hôtes internes à /etc/hosts, sauf si une adresse IP a été configurée manuellement ; les noms d'hôtes internes sont résolus par le résolveur DNS de gvproxy à la place.

Par défaut, Podman utilise le fichier /etc/hosts de l'hôte comme base, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré en utilisant la configuration base_hosts_file dans containers.conf.

--annotation=annotation=valeur

Ajoute une annotation d'image (par exemple, annotation=valeur) aux métadonnées de l'image. Peut être utilisé plusieurs fois.

Remarque : ces informations ne sont pas présentes dans les formats d'image Docker, elles sont donc ignorées lors de l'écriture d'images dans les formats Docker.

--authfile=chemin

Chemin du fichier d'authentification. Par défaut, il s'agit de ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, qui est défini à l'aide de docker login.

Remarque : Il existe également une option pour remplacer le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. Cela peut être fait avec export REGISTRY_AUTH_FILE=chemin.

--build-arg=arg=valeur

Spécifie un argument de construction et sa valeur, qui est interpolé dans les instructions lues à partir des Containerfiles de la même manière que les variables d'environnement, mais qui ne sont pas ajoutés à la liste des variables d'environnement dans la configuration de l'image résultante.

--build-arg-file=chemin

Spécifie un fichier contenant des lignes d'arguments de construction de la forme arg=valeur. Le nom de fichier suggéré est argfile.conf.

Les lignes de commentaires commençant par # sont ignorées, ainsi que les lignes vides. Toutes les autres doivent être au format arg=valeur passé à --build-arg.

Si plusieurs arguments sont fournis via les options --build-arg-file et --build-arg, les arguments de construction sont fusionnés à travers tous les fichiers fournis et les arguments de ligne de commande.

Tous les fichiers fournis dans une option --build-arg-file sont lus avant les arguments fournis via l'option --build-arg.

Lorsqu'un nom d'argument donné est spécifié plusieurs fois, la dernière instance est celle qui est passée aux constructions résultantes. Cela signifie que les valeurs de --build-arg remplacent toujours celles d'un --build-arg-file.

--build-context=nom=valeur

Spécifie un contexte de construction supplémentaire en utilisant son nom court et son emplacement. Des contextes de construction supplémentaires peuvent être référencés de la même manière que nous accédons à différentes étapes dans l'instruction COPY.

Les valeurs valides sont :

  • Répertoire local – par exemple, --build-context project2=../path/to/project2/src
  • URL HTTP vers une archive tar – par exemple, --build-context src=https://example.org/releases/src.tar
  • Image de conteneur – spécifiée avec un préfixe container-image://, par exemple, --build-context alpine=container-image://alpine:3.15, (accepte également docker://, docker-image://)

Côté Containerfile, référez-vous au contexte de construction sur toutes les commandes qui acceptent le paramètre “from”. Voici à quoi cela pourrait ressembler :

FROM [nom]
COPY --from=[nom] ...
RUN --mount=from=[nom] …

La valeur de [nom] est mise en correspondance avec l'ordre de priorité suivant :

  • Contexte de construction nommé défini avec --build-context [nom]=..
  • Étape définie avec AS [nom] dans Containerfile
  • Image [nom], locale ou dans un registre distant

--cache-from=image

Répertoire à utiliser comme source potentielle de cache. Lorsqu'il est spécifié, Buildah essaie de rechercher des images de cache dans le répertoire spécifié et tente de tirer des images de cache au lieu d'exécuter réellement les étapes de construction localement. Buildah tente uniquement de tirer des images précédemment mises en cache si elles sont considérées comme des succès de cache valides.

Utilisez l'option --cache-to pour peupler un répertoire distant avec du contenu de cache.

Exemple

# peupler un cache et le consulter également
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Remarque : l'option --cache-from est ignorée à moins que --layers ne soit spécifié.

--cache-to=image

Définissez ce drapeau pour spécifier un répertoire distant utilisé pour stocker les images de cache. Buildah tente de pousser l'image de cache nouvellement construite vers le répertoire distant.

Remarque : Utilisez l'option --cache-from afin d'utiliser le contenu du cache dans un répertoire distant.

Exemple

# peupler un cache et le consulter également
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Remarque : l'option --cache-to est ignorée à moins que --layers ne soit spécifié.

--cache-ttl

Limiter l'utilisation des images mises en cache pour ne considérer

images avec des horodatages de création antérieurs à durée. Par exemple, si --cache-ttl=1h est spécifié, Buildah prend en compte les images de cache intermédiaires créées dans l'heure qui précède, et ignore les images de cache intermédiaires antérieures à cette durée.

Note : La définition manuelle de --cache-ttl=0 équivaut à utiliser --no-cache dans l'implémentation, car cela signifie que l'utilisateur ne souhaite pas utiliser le cache du tout.

--cap-add=CAP_xxx

Lors de l'exécution d'instructions RUN, exécute la commande spécifiée dans l'instruction avec la capacité spécifiée ajoutée à son ensemble de capacités. Certaines capacités sont accordées par défaut ; cette option peut être utilisée pour en ajouter.

--cap-drop=CAP_xxx

Lors de l'exécution d'instructions RUN, exécute la commande spécifiée dans l'instruction avec la capacité spécifiée retirée de son ensemble de capacités. Les capacités CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_NET_BIND_SERVICE, CAP_SETFCAP, CAP_SETGID, CAP_SETPCAP et CAP_SETUID sont accordées par défaut ; cette option peut être utilisée pour les supprimer.

Si une capacité est spécifiée aux deux options --cap-add et --cap-drop, elle est supprimée, quel que soit l'ordre dans lequel les options ont été données.

--cert-dir=chemin

Utilise les certificats situés dans chemin (*.crt, *.cert, *.key) pour se connecter au registre. (Par défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2))

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup pour le conteneur est créé. Si le chemin n'est pas absolu, il est considéré comme relatif au chemin des cgroups du processus d'initialisation. Les cgroups sont créés s'ils n'existent pas déjà.

--cgroupns=comment

Définit la configuration des espaces de noms cgroup lors du traitement des instructions RUN. La valeur configurée peut être "" (chaîne vide) ou "private" pour indiquer qu'un nouvel espace de noms cgroup est créé, ou elle peut être "host" pour indiquer que l'espace de noms cgroup dans lequel buildah est lui-même exécuté est réutilisé.

--cleanup

Supprime les images construites des nœuds de la ferme en cas de succès (Par défaut : false).

--compat-volumes

Gère les répertoires marqués à l'aide de l'instruction VOLUME (à la fois dans cette construction et ceux hérités des images de base) de telle sorte que leur contenu ne puisse être modifié que par les instructions ADD et COPY. Toute modification effectuée dans ces emplacements par des instructions RUN sera annulée. Avant l'introduction de cette option, ce comportement était le défaut, mais il est maintenant désactivé par défaut.

--cpp-flag=flags

Définit les indicateurs supplémentaires à passer au préprocesseur C cpp(1). Les Containerfiles se terminant par le suffixe ".in" sont prétraités via cpp(1). Cette option peut être utilisée pour passer des indicateurs supplémentaires à cpp.Note : Vous pouvez également définir des CPPFLAGS par défaut en définissant la variable d'environnement BUILDAH_CPPFLAGS (par exemple, export BUILDAH_CPPFLAGS="-DDEBUG").

--cpu-period=limite

Définit la période CPU pour le planificateur Completely Fair Scheduler (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié pour s'exécuter avant la fin de la période en cours. Par défaut, 100000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpu-quota=limite

Limite le quota CPU du Completely Fair Scheduler (CFS).

Limite l'utilisation du CPU du conteneur. Par défaut, les conteneurs s'exécutent avec la pleine ressource CPU. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser ce temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en ajustant le poids de la part CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est 1024.

La proportion ne s'applique que lorsque des processus intensifs en CPU s'exécutent. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérons trois conteneurs, l'un avec une cpu-share de 1024 et deux autres avec un réglage de cpu-share de 512. Lorsque les processus dans les trois conteneurs tentent d'utiliser 100 % du CPU, le premier conteneur reçoit 50 % du temps CPU total. Si un quatrième conteneur est ajouté avec une cpu-share de 1024, le premier conteneur ne reçoit que 33 % du CPU. Les conteneurs restants reçoivent respectivement 16,5 %, 16,5 % et 33 % du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100 % du temps CPU, il peut utiliser 100 % de chaque cœur CPU individuel.

Par exemple, considérons un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la division suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100 % du CPU0
101 C1 1 100 % du CPU1
102 C1 2 100 % du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par exemple, 0,1), de plage (par exemple, 0-3), ou toute combinaison de ceux-ci (par exemple, 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpuset-mems=noeuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Uniquement efficace sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1 alors les processus du conteneur n'utiliseront la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--created-annotation

Ajoute une annotation d'image (voir aussi --annotation) aux métadonnées de l'image, définissant "org.opencontainers.image.created" à l'heure actuelle, ou à la date spécifiée pour le drapeau --source-date-epoch ou --timestamp, si l'un d'eux a été utilisé. Si false, aucune annotation de ce type ne sera présente dans l'image écrite.

Note : Ces informations ne sont pas présentes dans les formats d'image Docker, elles sont doncDiscarded lors de l'écriture d'images dans des formats Docker.

--creds=[nom_utilisateur[:mot_de_passe]]

Le [nom_utilisateur[:mot_de_passe]] à utiliser pour s'authentifier auprès du registre, si nécessaire. Si une ou deux valeurs ne sont pas fournies, une invite de commande apparaît et la valeur peut être saisie. Le mot de passe est saisi sans écho.

Notez que les identifiants spécifiés ne sont utilisés que pour s'authentifier auprès des registres cibles. Ils ne sont pas utilisés pour les miroirs ou lorsque le registre est réécrit (voir containers-registries.conf(5)) ; pour s'authentifier auprès de ceux-ci, envisagez d'utiliser un fichier containers-auth.json(5).

--decryption-key=clé[:phrase_de_passe]

La [clé[:phrase_de_passe]] à utiliser pour le déchiffrement des images. La clé peut pointer vers des clés et/ou des certificats. Le déchiffrement est tenté avec toutes les clés. Si la clé est protégée par une phrase de passe, elle doit être passée dans l'argument et omise sinon.

--device=périphérique_hôte[:périphérique_conteneur][:permissions]

Ajoute un périphérique hôte au conteneur. Le paramètre permissions facultatif peut être utilisé pour spécifier les permissions du périphérique en combinant r pour lire, w pour écrire et m pour mknod(2).

Exemple : --device=/dev/sdc:/dev/xvdc:rwm.

Note : si host-device est un lien symbolique, il est résolu en premier. Le conteneur ne stocke que les numéros majeur et mineur du périphérique hôte.

Podman peut charger les modules du noyau requis pour utiliser le périphérique spécifié. Les périphériques pour lesquels Podman charge les modules si nécessaire sont : /dev/fuse.

En mode sans privilèges (rootless), le nouveau périphérique est monté en bind dans le conteneur depuis l'hôte plutôt que Podman ne le crée dans l'espace du conteneur. Étant donné que le montage en bind conserve son étiquette SELinux sur les systèmes SELinux, le conteneur peut recevoir une erreur d'autorisation lors de l'accès au périphérique monté. Modifiez les paramètres SELinux pour autoriser les conteneurs à utiliser toutes les étiquettes de périphérique via la commande suivante :

$ sudo setsebool -P container_use_devices=true

Note : si l'utilisateur n'a des droits d'accès que via un groupe, l'accès au périphérique depuis un conteneur sans privilèges échoue. Le runtime crun(1) offre une solution de contournement en ajoutant l'option --annotation run.oci.keep_original_groups=1.

--disable-compression, -D

Ne pas compresser les couches de système de fichiers lors de la construction de l'image, sauf si cela est requis par l'emplacement où l'image est écrite. Ceci est le paramètre par défaut, car les couches d'image sont compressées automatiquement lorsqu'elles sont envoyées vers des registres, et les images écrites dans le stockage local n'ont besoin d'être décompressées qu'à nouveau pour être stockées. La compression peut être forcée dans tous les cas en spécifiant --disable-compression=false.

--dns=ipaddr

Définir des serveurs DNS personnalisés.

Cette option peut être utilisée pour remplacer la configuration DNS transmise au conteneur. Généralement, ceci est nécessaire lorsque la configuration DNS de l'hôte est invalide pour le conteneur (par exemple, 127.0.0.1). Dans ce cas, le drapeau --dns est nécessaire à chaque exécution.

La valeur spéciale none peut être spécifiée pour désactiver la création de /etc/resolv.conf dans le conteneur par Podman. Le fichier /etc/resolv.conf dans l'image est alors utilisé sans modifications.

Notez que ipaddr peut être ajouté directement au /etc/resolv.conf du conteneur. Cependant, cela n'est pas garanti. Par exemple, passer un réseau personnalisé dont dns_enabled est défini sur true à --network entraînera /etc/resolv.conf à ne faire référence qu'au serveur aardvark-dns. aardvark-dns transmettra ensuite à ipaddr fourni pour toutes les requêtes de nom non-conteneur.

Cette option ne peut pas être combinée avec --network défini sur none.

Note : cette option ne prend effet que pendant les instructions RUN dans la construction. Elle n'affecte pas /etc/resolv.conf dans l'image finale.

--dns-option=option

Définir des options DNS personnalisées à utiliser pendant la construction.

--dns-search=domain

Définir des domaines de recherche DNS personnalisés à utiliser pendant la construction.

--env=env[=value]

Ajoute une valeur (par exemple, env=value) à l'image construite. Peut être utilisé plusieurs fois. Si ni = ni une valeur ne sont spécifiés, mais que env est défini dans l'environnement actuel, la valeur de l'environnement actuel est ajoutée à l'image. Pour supprimer une variable d'environnement de l'image construite, utilisez l'option --unsetenv.

--file, -f=Containerfile

Spécifie un fichier Containerfile qui contient des instructions pour construire l'image, soit un fichier local, soit une URL http ou https. Si plus d'un fichier Containerfile est spécifié, les instructions FROM ne sont acceptées que du dernier fichier spécifié.

Si un contexte de construction n'est pas spécifié et qu'au moins un fichier Containerfile est un fichier local, le répertoire dans lequel il réside est utilisé comme contexte de construction.

Spécifier l'option -f - entraîne la lecture du contenu du Containerfile depuis stdin.

--force-rm

Supprimer toujours les conteneurs intermédiaires après une construction, même si la construction échoue (par défaut true).

--format

Contrôle le format du manifeste et des données de configuration de l'image construite. Les formats reconnus incluent oci (OCI image-spec v1.0, par défaut) et docker (version 2, utilisant le format de schéma 2 pour le manifeste).

Note : vous pouvez également remplacer le format par défaut en définissant la variable d'environnement BUILDAH_FORMAT. export BUILDAH_FORMAT=docker

--from

Remplace la première instruction FROM dans le Containerfile. S'il y a plusieurs instructions FROM dans un Containerfile, seule la première est modifiée.

Avec le client podman distant, tous les transports de conteneurs ne fonctionnent pas comme prévu. Par exemple, oci-archive:/x.tar fait référence à /x.tar sur la machine distante et non sur le client. Lors de l'utilisation de clients distants podman, il est préférable de se limiter aux transports containers-storage et docker://.

--group-add=group | keep-groups

Attribue des groupes supplémentaires à l'utilisateur principal s'exécutant dans le processus du conteneur.

•
keep-groups est un indicateur spécial qui indique à Podman de conserver l'accès aux groupes supplémentaires.

Permet au conteneur d'utiliser l'accès aux groupes supplémentaires de l'utilisateur. Si les systèmes de fichiers ou les périphériques ne sont accessibles que par le groupe de l'utilisateur sans privilèges, cet indicateur indique au runtime OCI de transmettre l'accès au groupe dans le conteneur. Actuellement disponible uniquement avec le runtime OCI crun. Note : keep-groups est exclusif, d'autres groupes ne peuvent pas être spécifiés avec cet indicateur. (Non disponible pour les commandes distantes, y compris les machines Mac et Windows (à l'exception de WSL2)).

--help, -h

Affiche le message d'utilisation

--hooks-dir=path

Chaque fichier *.json dans le chemin configure un hook pour les conteneurs de construction buildah. Pour plus de détails sur la syntaxe des fichiers JSON et la sémantique de l'injection de hooks. Buildah prend actuellement en charge les schémas de hook 1.0.0 et 0.1.0, bien que le schéma 0.1.0 soit déprécié.

Cette option peut être définie plusieurs fois ; les chemins des options ultérieures ont une priorité plus élevée.

Pour les conditions d'annotation, buildah utilise toutes les annotations définies dans la configuration OCI générée.

Pour les conditions de montage en bind, seuls les montages explicitement demandés par l'appelant via --volume sont pris en compte. Les montages en bind que buildah insère par défaut (par exemple, /dev/shm) ne sont pas pris en compte.

Si --hooks-dir n'est pas défini pour les appelants privilégiés (root), Buildah utilise actuellement /usr/share/containers/oci/hooks.d et /etc/containers/oci/hooks.d par ordre de priorité croissante. L'utilisation de ces valeurs par défaut est dépréciée. Migrez vers la définition explicite de --hooks-dir.

--http-proxy

Par défaut, les variables d'environnement proxy sont transmises au conteneur si elles sont définies pour le processus Podman. Ceci peut être désactivé en définissant la valeur sur false. Les variables d'environnement transmises incluent http_proxy, https_proxy, ftp_proxy, no_proxy, et également les versions en majuscules de celles-ci. Cette option n'est nécessaire que lorsque le système hôte doit utiliser un proxy mais que le conteneur n'utilise aucun proxy. --network=mode, --net

Définit la configuration des espaces de noms réseau lors du traitement des instructions RUN.

Les valeurs valides pour mode sont :

  • none : pas de réseau.
  • host : utilise la pile réseau de l'hôte Podman. Note : le mode host donne au conteneur un accès complet aux services système locaux tels que D-bus et est donc considéré comme non sécurisé.
  • ns:chemin : chemin d'un espace de noms réseau à rejoindre.
  • private : crée un nouvel espace de noms pour le conteneur (par défaut)
  • <nom_réseau|ID> : rejoint le réseau avec le nom ou l'ID donné, par exemple, utilisez --network monnet pour rejoindre le réseau nommé monnet. Uniquement pris en charge pour les utilisateurs rootful.
  • slirp4netns[:OPTIONS,...] : utilise slirp4netns(1) pour créer une pile réseau utilisateur. Il est possible de spécifier ces options supplémentaires, elles peuvent également être définies avec network_cmd_options dans containers.conf :
  • allow_host_loopback=true|false : permet à slirp4netns d'atteindre l'IP de bouclage de l'hôte (la valeur par défaut est 10.0.2.2 ou la deuxième IP du sous-réseau CIDR de slirp4netns lorsqu'il est modifié, voir l'option cidr ci-dessous). La valeur par défaut est false.
  • mtu=MTU : spécifie le MTU à utiliser pour ce réseau. (La valeur par défaut est 65520).
  • cidr=CIDR : spécifie la plage d'adresses IP à utiliser pour ce réseau. (La valeur par défaut est 10.0.2.0/24).
  • enable_ipv6=true|false : active l'IPv6. La valeur par défaut est true. (Requis pour outbound_addr6).
  • outbound_addr=INTERFACE : spécifie l'interface de sortie sur laquelle slirp se lie (trafic IPv4 uniquement).
  • outbound_addr=IPv4 : spécifie l'adresse IPv4 de sortie sur laquelle slirp se lie.
  • outbound_addr6=INTERFACE : spécifie l'interface de sortie sur laquelle slirp se lie (trafic IPv6 uniquement).
  • outbound_addr6=IPv6 : spécifie l'adresse IPv6 de sortie sur laquelle slirp se lie.
•
pasta[:OPTIONS,...] : utilise pasta(1) pour créer une pile réseau en mode utilisateur.
C'est la valeur par défaut pour les conteneurs sans root et elle n'est prise en charge qu'en mode sans root.
Par défaut, les adresses et les routes IPv4 et IPv6, ainsi que le nom de l'interface du pod, sont copiés de l'hôte. Si le transfert de port n'est pas configuré, les ports sont transférés dynamiquement à mesure que les services sont liés de chaque côté (espace de noms init ou espace de noms du conteneur). Le transfert de port préserve l'adresse IP source d'origine. Les options décrites dans pasta(1) peuvent être spécifiées comme arguments séparés par des virgules.
En termes d'options de pasta(1), --config-net est donné par défaut, afin de configurer le réseau au démarrage du conteneur, et --no-map-gw est également supposé par défaut, pour éviter l'accès direct du conteneur à l'hôte en utilisant l'adresse de la passerelle. Ce dernier peut être remplacé en passant --map-gw dans les options spécifiques à pasta (malgré le fait que ce ne soit pas une option réelle de pasta(1)).
De plus, -t none et -u none sont passés pour désactiver le transfert automatique de ports basé sur les ports liés. De même, -T none et -U none sont donnés pour désactiver la même fonctionnalité du conteneur vers l'hôte.
Quelques exemples :
  • pasta:--map-gw : permet au conteneur d'atteindre directement l'hôte en utilisant l'adresse de la passerelle.
  • pasta:--mtu,1500 : spécifie un MTU de 1500 octets pour l'interface tap dans le conteneur.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options slirp4netns(1) par défaut : désactive l'IPv6, attribue 10.0.2.0/24 à l'interface tap0 dans le conteneur, avec une passerelle 10.0.2.3, active le relais DNS joignable à 10.0.2.3, définit le MTU à 1500 octets, désactive NDP, DHCPv6 et le support DHCP.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options slirp4netns(1) par défaut avec les remplacements Podman : identique à ce qui précède, mais laisse le MTU à 65520 octets
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto : active le transfert automatique de ports basé sur les ports liés observés des deux côtés (hôte et conteneur)
  • pasta:-T,5201 : active le transfert du port TCP 5201 du conteneur vers l'hôte, en utilisant l'interface de bouclage au lieu de l'interface tap pour améliorer les performances

--pull=politique

Politique de récupération d'image. La valeur par défaut est missing.

  • always : Récupère toujours l'image et génère une erreur si la récupération échoue.
  • missing : Ne récupère l'image que lorsqu'elle n'existe pas dans le stockage local des conteneurs. Génère une erreur si aucune image n'est trouvée et que la récupération échoue.
  • never : Ne récupère jamais l'image, mais utilise celle du stockage local des conteneurs. Génère une erreur lorsqu'aucune image n'est trouvée.
  • newer : Récupère si l'image sur le registre est plus récente que celle du stockage local des conteneurs. Une image est considérée comme plus récente lorsque les digests sont différents. La comparaison des horodatages est sujette à des erreurs. Les erreurs de récupération sont supprimées si une image locale a été trouvée.

--source-date-epoch=secondes

Définit le timestamp de "création" de l'image construite sur ce nombre de secondes depuis l'époque (heure Unix 0, c'est-à-dire 00:00:00 UTC le 1er janvier 1970) (par défaut, utilise la valeur définie dans la variable d'environnement SOURCE_DATE_EPOCH, ou l'heure actuelle si elle n'est pas définie).

Le timestamp de "création" est écrit dans la configuration et le manifeste de l'image lors de son enregistrement, de sorte que l'exécution de la même construction deux fois différentes produira normalement des images avec des hachages sha256 différents, même si aucune autre modification n'a été apportée au Containerfile et au contexte de construction.

Lorsque ce drapeau est défini, un argument de construction SOURCE_DATE_EPOCH fournira sa valeur pour une étape dans laquelle il est déclaré.

Lorsque ce drapeau est défini, le timestamp de "création" de la configuration de l'image est toujours défini sur l'heure spécifiée, ce qui devrait permettre de construire des images identiques à des moments différents en utilisant le même ensemble d'entrées.

Lorsque ce drapeau est défini, la sortie écrite comme spécifié dans le drapeau --output portera exactement le timestamp spécifié.

Entre en conflit avec le drapeau similaire --timestamp, qui définit également son heure spécifiée sur le contenu des nouvelles couches.

--squash

Remettre à plat toutes les nouvelles couches de l'image en une seule nouvelle couche ; les couches préexistantes ne sont pas remises à plat.

--squash-all

Remettre à plat toutes les couches de la nouvelle image (y compris celles héritées d'une image de base) en une seule nouvelle couche.

--ssh=défaut | id=socket>

Socket ou clés de l'agent SSH à exposer à la construction. Le chemin du socket peut être laissé vide pour utiliser la valeur de default=$SSH_AUTH_SOCK

Pour utiliser ultérieurement l'agent ssh, utilisez l'option --mount dans une instruction RUN au sein d'un Containerfile :

RUN --mount=type=ssh,id=id mycmd

--tag, -t=nomImage

Spécifie le nom qui est attribué à l'image résultante si le processus de construction se termine avec succès. Si nomImage n'inclut pas de nom de registre, le nom de registre localhost est préfixé au nom de l'image.

--target=nomEtape

Définit l'étape de construction cible à construire. Lors de la construction d'un Containerfile avec plusieurs étapes de construction, --target peut être utilisé pour spécifier une étape de construction intermédiaire par son nom comme étape finale pour l'image résultante. Les commandes après l'étape cible sont ignorées.

--timestamp=secondes

Définit le timestamp de création sur les secondes depuis l'époque pour permettre des constructions déterministes (par défaut, l'heure actuelle). Par défaut, le timestamp de création est modifié et écrit dans le manifeste de l'image à chaque enregistrement, provoquant une différence dans le hachage sha256 de l'image même si les sources sont exactement les mêmes par ailleurs. Lorsque --timestamp est défini, le timestamp de création est toujours défini sur l'heure spécifiée et donc non modifié, permettant au hachage sha256 de l'image de rester le même. Tous les fichiers enregistrés dans les couches de l'image sont créés avec le timestamp.

Si la seule instruction dans un Containerfile est FROM, ce drapeau n'a aucun effet.

--tls-verify

Exige HTTPS et vérifie les certificats lors du contact avec les registres (par défaut : true). S'il est explicitement défini sur true, la vérification TLS est utilisée. S'il est défini sur false, la vérification TLS n'est pas utilisée. Si non spécifié, la vérification TLS est utilisée à moins que le registre cible ne soit répertorié comme registre non sécurisé dans containers-registries.conf(5)

--ulimit=type=limite-douce[:limite-stricte]

Spécifie les limites de ressources à appliquer aux processus lancés lors du traitement des instructions RUN. Cette option peut être spécifiée plusieurs fois. Les types de ressources reconnus incluent :
"core" : taille maximale du dump de noyau (ulimit -c)
"cpu" : temps CPU maximal (ulimit -t)
"data" : taille maximale du segment de données d'un processus (ulimit -d)
"fsize" : taille maximale des nouveaux fichiers (ulimit -f)
"locks" : nombre maximal de verrous de fichiers (ulimit -x)
"memlock" : quantité maximale de mémoire verrouillée (ulimit -l)
"msgqueue" : quantité maximale de données dans les files d'attente de messages (ulimit -q)
"nice" : ajustement de la courtoisie (nice -n, ulimit -e)
"nofile" : nombre maximal de fichiers ouverts (ulimit -n)
"nproc" : nombre maximal de processus (ulimit -u)
"rss" : taille maximale du RSS d'un processus (ulimit -m)
"rtprio" : priorité d'ordonnancement temps réel maximale (ulimit -r)
"rttime" : temps d'exécution temps réel maximal entre les appels système bloquants
"sigpending" : nombre maximal de signaux en attente (ulimit -i)
"stack" : taille maximale de la pile (ulimit -s)

--unsetannotation=annotation

Supprimer l'annotation de l'image, faisant en sorte que l'annotation ne soit pas héritée de l'image de base.

--unsetenv=env

Supprimer les variables d'environnement de l'image finale.

--unsetlabel=label

Supprimer le label de l'image, faisant en sorte que le label ne soit pas hérité de l'image de base.

--userns=how

Définit la configuration pour les espaces de noms utilisateur lors du traitement des instructions RUN. La valeur configurée peut être "" (la chaîne vide) ou "container" pour indiquer qu'un nouvel espace de noms utilisateur est créé, elle peut être "host" pour indiquer que l'espace de noms utilisateur dans lequel podman lui-même est exécuté est réutilisé, ou elle peut être le chemin vers un espace de noms utilisateur déjà utilisé par un autre processus.

--userns-gid-map=mapping

Spécifie directement un mappage GID à utiliser pour définir la propriété, au niveau du système de fichiers, du contenu du conteneur de travail. Les commandes exécutées lors du traitement des instructions RUN sont exécutées par défaut dans leurs propres espaces de noms utilisateur, configurés à l'aide des mappages UID et GID.

Les entrées de ce mappage prennent la forme d'un ou plusieurs triplets d'un GID de départ dans le conteneur, d'un GID de départ correspondant au niveau de l'hôte, et du nombre d'ID consécutifs que l'entrée de mappage représente.

Si cette option n'est pas spécifiée, mais qu'un paramètre global --userns-gid-map est fourni, les paramètres de l'option globale sont utilisés.

Si ni --userns-uid-map-user, ni --userns-gid-map-group, ni --userns-gid-map ne sont spécifiés, mais que --userns-uid-map est spécifié, le mappage GID est défini pour utiliser les mêmes valeurs numériques que le mappage UID.

--userns-gid-map-group=groupe

Spécifie qu'un mappage GID à utiliser pour définir la propriété, au niveau du système de fichiers, du contenu du conteneur de travail, peut être trouvé dans les entrées du fichier /etc/subgid correspondant au groupe spécifié. Les commandes exécutées lors du traitement des instructions RUN sont exécutées par défaut dans leurs propres espaces de noms utilisateur, configurés à l'aide des mappages UID et GID. Si --userns-uid-map-user est spécifié, mais que --userns-gid-map-group n'est pas spécifié, podman suppose que le nom d'utilisateur spécifié est également un nom de groupe approprié à utiliser comme paramètre par défaut pour cette option.

NAME

podman-farm-build - build image and manifest list

SYNOPSIS

podman farm build [options] path

DESCRIPTION

The podman farm build command allows you to build named images and manifest lists using the specified Containerfile and the default farm.

This command is equivalent to running Buildah with the --manifest option.

When running a build on the default farm, the podman-farm-build(1) command will build the image and manifest list locally. The command produces images and manifest lists on the local host.

OPTIONS

-f, --file path

Use a Containerfile to perform the build. The default is the Containerfile in the current directory.

--cleanup

Remove all images from farm nodes, after they are pushed to registry.

--farm farm-name

Use the specified farm. Podman can be configured to use multiple farms in the registries.conf(5) file.

--local

Build the image and manifest list locally.

--platforms platform-list

Build the image and manifest list for the specified platforms. The list is a comma-separated list of platforms. For example, --platforms arm64,amd64.

-t, --tag name

Tag the built image and manifest list with the specified name.

The following options are available for volume mounts:

A volume is a directory, or a file, on the host machine that is mounted into a container. The -v option can be used multiple times to specify multiple volumes. The format is:

-v HOST-DIR:CONTAINER-DIR[:OPTIONS]

HOST-DIR

The path to the directory or file on the host machine.

CONTAINER-DIR

The path to the directory or file in the container. Must be an absolute path.

OPTIONS

An optional comma-separated list and can be one or more of:

  • [rw|ro]
  • [z|Z|O]
  • [[r]shared|[r]slave|[r]private][1] ⟨#Footnote1⟩

The CONTAINER-DIR must be an absolute path such as /src/docs. The HOST-DIR must be an absolute path as well. Podman bind-mounts the HOST-DIR to the specified path when processing RUN instructions.

You can specify multiple -v options to mount one or more mounts.

You can add the :ro or :rw suffix to a volume to mount it read-only or read-write mode, respectively. By default, the volumes are mounted read-write. See examples.

Chowning Volume Mounts

By default, Podman does not change the owner and group of source volume directories mounted. When running using user namespaces, the UID and GID inside the namespace may correspond to another UID and GID on the host.

The :U suffix tells Podman to use the correct host UID and GID based on the UID and GID within the namespace, to change recursively the owner and group of the source volume.

Warning use with caution since this modifies the host filesystem.

Labeling Volume Mounts

Labeling systems like SELinux require that proper labels are placed on volume content mounted into a container. Without a label, the security system might prevent the processes running inside the container from using the content. By default, Podman does not change the labels set by the OS.

To change a label in the container context, add one of these two suffixes :z or :Z to the volume mount. These suffixes tell Podman to relabel file objects on the shared volumes. The z option tells Podman that two containers share the volume content. As a result, Podman labels the content with a shared content label. Shared volume labels allow all containers to read/write content. The Z option tells Podman to label the content with a private unshared label. Only the current container can use a private volume.

Note: Do not relabel system files and directories. Relabeling system content might cause other confined services on the host machine to fail. For these types of containers, disabling SELinux separation is recommended. The option --security-opt label=disable disables SELinux separation for the container. For example, if a user wanted to volume mount their entire home directory into the build containers, they need to disable SELinux separation.

$ podman build --security-opt label=disable -v $HOME:/home/user .

Overlay Volume Mounts

The :O flag tells Podman to mount the directory from the host as a temporary storage using the Overlay file system. The RUN command containers are allowed to modify contents within the mountpoint and are stored in the container storage in a separate directory. In Overlay FS terms the source directory is the lower, and the container storage directory is the upper. Modifications to the mount point are destroyed when the RUN command finishes executing, similar to a tmpfs mount point.

Any subsequent execution of RUN commands sees the original source directory content, any changes from previous RUN commands no longer exists.

One use case of the overlay mount is sharing the package cache from the host into the container to allow speeding up builds.

Note:

  • Overlay mounts are not currently supported in rootless mode.
  • The O flag is not allowed to be specified with the Z or z flags. Content mounted into the container is labeled with the private label. On SELinux systems, labels in the source directory needs to be readable by the container label. If not, SELinux container separation must be disabled for the container to work.
  • Modification of the directory volume mounted into the container with an overlay mount can cause unexpected failures. Do not modify the directory until the container finishes running.

By default bind mounted volumes are private. That means any mounts done inside containers are not be visible on the host and vice versa. This behavior can be changed by specifying a volume mount propagation property.

When the mount propagation policy is set to shared, any mounts completed inside the container on that volume is visible to both the host and container. When the mount propagation policy is set to slave, one way mount propagation is enabled and any mounts completed on the host for that volume is visible only inside of the container. To control the mount propagation property of volume use the :[r]shared, :[r]slave or :[r]private propagation flag. For mount propagation to work on the source mount point (mount point where source dir is mounted on) has to have the right propagation properties. For shared volumes, the source mount point has to be shared. And for slave volumes, the source mount has to be either shared or slave. [1] ⟨#Footnote1⟩

Use df <source-dir> to determine the source mount and then use findmnt -o TARGET,PROPAGATION <source-mount-dir> to determine propagation properties of source mount, if findmnt utility is not available, the source mount point can be determined by looking at the mount entry in /proc/self/mountinfo. Look at optional fields and see if any propagation properties are specified. shared:X means the mount is shared, master:X means the mount is slave and if nothing is there that means the mount is private. [1] ⟨#Footnote1⟩

To change propagation properties of a mount point use the mount command. For example, to bind mount the source directory /foo do mount --bind /foo /foo and mount --make-private --make-shared /foo. This converts /foo into a shared mount point. The propagation properties of the source mount can be changed directly. For instance if / is the source mount for /foo, then use mount --make-shared / to convert / into a shared mount.

EXAMPLES

Build named image and manifest list using specified Containerfile with default farm:

$ podman farm build --local -t name -f /path/to/containerfile .

Build named image and manifest list using the specified farm:

$ podman farm build --farm myfarm -t name .

Build named image and manifest list using the specified farm, removing all images from farm nodes, after they are pushed to registry:

$ podman farm build --farm myfarm --cleanup -t name .

Build named images and manifest list for specified platforms using default farm:

$ podman farm build --platforms arm64,amd64 -t name .
