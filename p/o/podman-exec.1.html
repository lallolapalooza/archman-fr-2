podman-exec(1) Manuel des commandes générales podman-exec(1)

NOM

podman-exec - Exécute une commande dans un conteneur en cours d'exécution

SYNOPIS

podman exec [options] conteneur commande [arg ...]

podman container exec [options] conteneur commande [arg ...]

DESCRIPTION

podman exec exécute une commande dans un conteneur en cours d'exécution.

OPTIONS

--cidfile=fichier

Lit l'ID du conteneur cible à partir du fichier spécifié.

--detach, -d

Démarre la session d'exécution, mais ne s'y attache pas. La commande s'exécute en arrière-plan et la session d'exécution est automatiquement supprimée une fois terminée. La commande podman exec affiche l'ID de la session d'exécution et se termine immédiatement après son démarrage.

--detach-keys=séquence

Spécifie la séquence de touches pour détacher un conteneur. Le format est un seul caractère [a-Z] ou un ou plusieurs caractères ctrl-<valeur> où <valeur> est l'un des éléments suivants : a-z, @, ^, [, , ou _. La spécification de « » » désactive cette fonctionnalité. La valeur par défaut est ctrl-p,ctrl-q.

Cette option peut également être définie dans le fichier containers.conf(5).

--env, -e=env

Définit des variables d'environnement.

Cette option permet des variables d'environnement arbitraires qui sont disponibles pour le processus à lancer dans le conteneur. Si une variable d'environnement est spécifiée sans valeur, Podman vérifie l'environnement de l'hôte pour une valeur et ne définit la variable que si elle est définie sur l'hôte. À titre de cas particulier, si une variable d'environnement se terminant par * est spécifiée sans valeur, Podman recherche dans l'environnement de l'hôte les variables commençant par le préfixe et ajoute ces variables au conteneur.

--env-file=fichier

Lit un fichier délimité par des lignes de variables d'environnement.

--interactive, -i

Lorsque défini sur true, rend stdin disponible pour le processus contenu. Si false, le stdin du processus contenu est vide et immédiatement fermé.

Si attaché, stdin est transmis au processus contenu. Si détaché, la lecture de stdin sera bloquée jusqu'à ce qu'elle soit attachée ultérieurement.

Attention : Podman consommera l'entrée de stdin dès qu'elle sera disponible, même si le processus contenu ne la demande pas.

--latest, -l

Au lieu de fournir le nom ou l'ID du conteneur, utilise le dernier conteneur créé. Note : le dernier conteneur démarré peut provenir d'autres utilisateurs de Podman sur la machine hôte. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2))

--preserve-fd=FD1[,FD2,...]

Transmet au processus les descripteurs de fichiers supplémentaires spécifiés dans la liste séparée par des virgules. Peut être spécifié plusieurs fois. Cette option n'est prise en charge qu'avec le runtime OCI crun. Cela peut représenter un risque de sécurité d'utiliser cette option avec d'autres runtimes OCI.

(Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2))

--preserve-fds=N

Transmet au processus N descripteurs de fichiers supplémentaires (en plus de 0, 1, 2). Le total des FD est de 3+N. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2))

--privileged

Accorde des privilèges étendus à ce conteneur. La valeur par défaut est false.

Par défaut, les conteneurs Podman ne sont pas privilégiés (=false) et ne peuvent pas, par exemple, modifier des parties du système d'exploitation. En effet, par défaut, un conteneur n'est autorisé qu'un accès limité aux périphériques. Un conteneur "privilégié" a le même accès aux périphériques que l'utilisateur qui lance le conteneur, à l'exception des consoles virtuelles (/dev/tty\d+) lorsqu'il est exécuté en mode systemd (--systemd=always).

Un conteneur privilégié désactive les fonctionnalités de sécurité qui isolent le conteneur de l'hôte. Les capacités supprimées, les périphériques limités, les points de montage en lecture seule, la séparation Apparmor/SELinux et les filtres Seccomp sont tous désactivés. En raison des fonctionnalités de sécurité désactivées, le champ privilégié ne devrait presque jamais être défini, car les conteneurs peuvent facilement s'échapper de leur confinement.

Les conteneurs exécutés dans un espace de noms utilisateur (par exemple, les conteneurs sans privilèges) ne peuvent pas avoir plus de privilèges que l'utilisateur qui les a lancés.

--tty, -t

Alloue un pseudo-TTY. La valeur par défaut est false.

Lorsque défini sur true, Podman alloue un pseudo-TTY et s'attache à l'entrée standard du conteneur. Cela peut être utilisé, par exemple, pour exécuter un shell interactif jetable.

REMARQUE: L'indicateur --tty empêche la redirection de la sortie standard. Il combine STDOUT et STDERR, il peut insérer des caractères de contrôle et il peut bloquer les pipes. Cette option n'est utilisée que lorsqu'elle est exécutée interactivement dans un terminal. Lors de l'alimentation d'une entrée dans Podman, utilisez uniquement -i, pas -it.

--user, -u=utilisateur[:groupe]

Définit le nom d'utilisateur ou l'UID utilisé et, éventuellement, le nom de groupe ou le GID pour la commande spécifiée. Utilisateur et groupe peuvent être symboliques ou numériques.

Sans cet argument, la commande s'exécute en tant qu'utilisateur spécifié dans l'image du conteneur. Sauf si remplacé par une commande USER dans le Containerfile ou par une valeur passée à cette option, cet utilisateur est généralement par défaut root.

Lorsqu'un espace de noms utilisateur n'est pas utilisé, l'UID et le GID utilisés dans le conteneur et sur l'hôte correspondent. Cependant, lorsque des espaces de noms utilisateur sont utilisés, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte. Dans les conteneurs sans privilèges, par exemple, un espace de noms utilisateur est toujours utilisé, et root dans le conteneur correspond par défaut à l'UID et au GID de l'utilisateur invoquant Podman.

--workdir, -w=rép

Répertoire de travail à l'intérieur du conteneur.

Le répertoire de travail par défaut pour l'exécution de binaires dans un conteneur est le répertoire racine (/). Le développeur de l'image peut définir un autre défaut avec l'instruction WORKDIR. L'opérateur peut remplacer le répertoire de travail en utilisant l'option -w.

Statut de sortie

Le code de sortie de podman exec donne des informations sur la raison pour laquelle la commande dans le conteneur n'a pas pu s'exécuter ou pourquoi elle s'est terminée. Lorsque podman exec se termine avec un code non nul, les codes de sortie suivent le standard chroot, voir ci-dessous :

125 L'erreur concerne Podman lui-même

$ podman exec --foo ctrID /bin/sh; echo $?
Error: unknown flag: --foo
125

126 La commande contenue ne peut pas être invoquée

$ podman exec ctrID /etc; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"/etc\": permission denied": OCI runtime error
126

127 La commande contenue est introuvable

$ podman exec ctrID foo; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"foo\": executable file not found in $PATH": OCI runtime error
127

Code de sortie Le code de sortie de la commande contenue

$ podman exec ctrID /bin/sh -c 'exit 3'; echo $?
3

EXEMPLES

Exécute une commande dans le conteneur sélectionné avec une stdin et un tty alloués :

$ podman exec -it ctrID ls

Exécute une commande avec le répertoire de travail remplacé dans le conteneur sélectionné avec une stdin et un tty alloués :

$ podman exec -it -w /tmp myCtr pwd

Exécute une commande en tant qu'utilisateur spécifié dans le conteneur sélectionné :

$ podman exec --user root ctrID ls

Exécute une commande mais ne s'attache pas à la session d'exécution, laissant la commande s'exécuter en arrière-plan :

$ podman exec -d ctrID find /path/to/search -name yourfile
