podman-kube-play(1) Manuel des commandes générales podman-kube-play(1)

NOM

podman-kube-play - Créer des conteneurs, des pods et des volumes basés sur des fichiers YAML Kubernetes

SYNTAXE

podman kube play [options] fichier.yml|-|https://website.io/file.yml

DESCRIPTION

podman kube play lit un fichier structuré de YAML Kubernetes. Il recrée les conteneurs, pods ou volumes décrits dans le YAML. Les conteneurs au sein d'un pod sont ensuite démarrés, et l'ID du nouveau Pod ou le nom du nouveau Volume est affiché. Si le fichier YAML est spécifié comme "-", alors podman kube play lit le fichier YAML depuis l'entrée standard. L'entrée peut également être une URL pointant vers un fichier YAML tel que https://podman.io/demo.yml. podman kube play lit le YAML de l'URL et crée des pods et des conteneurs à partir de celui-ci.

En utilisant l'option de ligne de commande --down, il est également capable de démonter les pods créés par une exécution précédente de podman kube play.

En utilisant l'option de ligne de commande --replace, il démonte les pods (s'il y en a) créés par une exécution précédente de podman kube play et recrée les pods avec le fichier YAML Kubernetes.

Idéalement, le fichier d'entrée est créé par la commande Podman (voir podman-kube-generate(1)). Cela garantit une importation fluide et des résultats attendus.

Actuellement, les types Kubernetes pris en charge sont :

  • Pod
  • Deployment
  • PersistentVolumeClaim
  • ConfigMap
  • Secret
  • DaemonSet
  • Job

Pods ou Déploiements Kubernetes

Seuls cinq types de volumes sont pris en charge par kube play : les types de volumes hostPath, emptyDir, configMap, persistentVolumeClaim et image.

  • Lors de l'utilisation du type de volume hostPath, seuls les sous-types défaut (vide), DirectoryOrCreate, Directory, FileOrCreate, File, Socket, CharDevice et BlockDevice sont pris en charge. Podman interprète la valeur du hostPath path comme un chemin de fichier lorsqu'il contient au moins une barre oblique, sinon Podman traite la valeur comme le nom d'un volume nommé.
  • Lors de l'utilisation d'un persistentVolumeClaim, la valeur de claimName est le nom du volume nommé Podman.
  • Lors de l'utilisation d'un volume emptyDir, Podman crée un volume anonyme qui est attaché aux conteneurs exécutés à l'intérieur du pod et est supprimé une fois le pod supprimé.
  • Lors de l'utilisation d'un volume configMap, Podman crée un volume anonyme qui est attaché aux conteneurs exécutés à l'intérieur du pod et est supprimé une fois le pod supprimé.
  • Lors de l'utilisation d'un volume image, Podman crée un volume d'image en lecture seule avec un sous-chemin vide (toute l'image est montée). L'image doit déjà exister localement. Elle est prise en charge uniquement en mode rootful.

Note : La politique de redémarrage par défaut pour les conteneurs est always. Vous pouvez modifier la valeur par défaut en définissant le champ restartPolicy dans le spec.

Note : Lors de la lecture d'un fichier YAML kube avec des conteneurs init, le conteneur init est créé avec la valeur de type init once. Pour modifier le type par défaut, utilisez l'annotation io.podman.annotations.init.container.type pour définir le type sur always.

Note : Les types de volume hostPath créés par kube play reçoivent un label SELinux partagé (z), les montages bind ne sont pas relabellisés (utilisez chcon -t container_file_t -R <répertoire>).

Note : Pour définir les userns d'un pod, utilisez l'annotation io.podman.annotations.userns dans la définition du pod/déploiement. Par exemple, l'annotation io.podman.annotations.userns=keep-id indique à Podman de créer un espace de noms utilisateur où l'UID:GID de l'utilisateur rootless actuel est mappé aux mêmes valeurs dans le conteneur. Ceci peut être écrasé par l'indicateur --userns.

Note : Utilisez l'annotation io.podman.annotations.volumes-from pour monter les volumes d'un conteneur à un autre. Vous pouvez monter des volumes depuis plusieurs conteneurs sources vers un conteneur cible. Les conteneurs sources appartenant au même pod doivent être définis avant le conteneur source dans le fichier YAML kube. Le format de l'annotation est io.podman.annotations.volumes-from/conteneurCible: "conteneurSource1:optionsMontage1;conteneurSource2:optionsMontage2".

Note : Si le tag :latest est utilisé, Podman tente de tirer l'image d'un registre. Si l'image a été construite localement avec Podman ou Buildah, elle a localhost comme domaine, dans ce cas, Podman utilise l'image du stockage local même si elle a le tag :latest.

Note : La commande podman play kube est un alias de podman kube play, et effectue la même fonction.

Note : La commande podman kube down peut être utilisée pour arrêter et supprimer les pods ou conteneurs basés sur le même fichier YAML Kubernetes que celui utilisé par podman kube play pour les créer.

Note : Pour personnaliser le nom du conteneur infra créé lors de podman kube play, utilisez l'annotation io.podman.annotations.infra.name dans la définition du pod. Cette annotation est automatiquement définie lors de la génération d'un fichier YAML kube à partir d'un pod créé avec l'indicateur --infra-name défini.

Note : Utilisez l'annotation io.podman.annotations.pids-limit/$ctrname pour configurer la limite de pids du pod.

Note : Utilisez l'annotation io.podman.annotations.cpuset/$ctrname pour restreindre l'exécution d'un conteneur à un ensemble spécifique de cœurs CPU. Ceci est équivalent à l'option --cpuset-cpus=nombre dans podman-run(1).

Note : Utilisez l'annotation io.podman.annotations.memory-nodes/$ctrname pour restreindre les allocations mémoire d'un conteneur à un ensemble spécifique de nœuds mémoire sur les systèmes NUMA. Ceci est équivalent à l'option --cpuset-mems=nœuds dans podman-run(1).

PersistentVolumeClaims Kubernetes

Un PersistentVolumeClaim Kubernetes représente un volume nommé Podman. Seul le nom PersistentVolumeClaim est requis par Podman pour créer un volume. Les annotations Kubernetes peuvent être utilisées pour exploiter les options disponibles pour les volumes Podman.

  • volume.podman.io/driver
  • volume.podman.io/device
  • volume.podman.io/type
  • volume.podman.io/uid
  • volume.podman.io/gid
  • volume.podman.io/mount-options
  • volume.podman.io/import-source
  • volume.podman.io/image

Utilisez volume.podman.io/import-source pour importer le contenu de l'archive (tarball) (.tar, .tar.gz, .tgz, .bzip, .tar.xz, .txz, .tar.zst) spécifié dans la valeur de l'annotation dans le volume Podman créé.

Kube play est capable de construire des images à la volée étant donné la structure de répertoires correcte et les Containerfiles. Cette option n'est pas encore disponible pour les clients distants, y compris les machines Mac et Windows (hors WSL2). Considérez l'extrait suivant d'un fichier YAML :

apiVersion: v1
kind: Pod
metadata:
...
spec:
  containers:
  - name: container
    image: foobar
...

S'il existe un répertoire nommé foobar dans le répertoire de travail actuel avec un fichier nommé Containerfile ou Dockerfile, Podman kube play construit cette image et la nomme foobar. Un exemple de structure de répertoire pour cet exemple ressemble à ceci :

|- mesfichierskube
    |- monfichierplay.yaml
    |- foobar
         |- Containerfile

La construction considère foobar comme le répertoire de contexte pour la construction. S'il existe une image dans le stockage local appelée foobar, l'image n'est pas construite à moins que l'indicateur --build ne soit utilisé. Utilisez --build=false pour désactiver complètement les constructions.

Kube play prend en charge les sélecteurs de périphériques CDI (Container Device Interface) pour partager des périphériques hôtes (par exemple, des GPU) avec des conteneurs. Le format de configuration suit la gestion des ressources étendues de Kubernetes :

apiVersion: v1
kind: Pod
spec:
  containers:
  - name: container
    resources:
      limits:
        nvidia.com/gpu=all: 1

Pour activer le partage de périphériques hôtes, de manière analogue à l'utilisation de l'indicateur --device, Podman kube prend en charge un sélecteur CDI personnalisé : podman.io/device=<chemin_périphérique_hôte>.

ConfigMap Kubernetes

Les ConfigMaps Kubernetes peuvent être référencés comme source de variables d'environnement ou de volumes dans les Pods ou les Déploiements. Les ConfigMaps ne sont pas des objets autonomes dans Podman ; au lieu de cela, lorsqu'un conteneur utilise un ConfigMap, Podman crée les variables d'environnement ou les volumes selon les besoins.

Par exemple, le document YAML suivant définit un ConfigMap puis l'utilise dans un Pod :

apiVersion: v1
kind: ConfigMap
metadata:
  name: foo
data:
    FOO: bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: fooba
r envFrom: - configMapRef: name: foo optional: false

et, par conséquent, la variable d'environnement FOO est définie sur bar pour le conteneur container-1.

Secret Kubernetes

Un secret Kubernetes représente un secret nommé Podman. Le secret Kubernetes est enregistré dans son intégralité et peut être référencé comme source de variables d'environnement ou de volumes dans les Pods ou les Déploiements.

Par exemple, le document YAML suivant définit un secret, puis l'utilise dans un Pod :

kind: Secret
apiVersion: v1
metadata:
  name: foo
data:
  foo: YmFy # base64 pour bar
---
apiVersion: v1
kind: Pod
metadata:
  name: foobar
spec:
  containers:
  - name: container-1
    image: foobar
    env:
    - name: FOO
      valueFrom:
        secretKeyRef:
          name: foo
          key: foo

Et, par conséquent, la variable d'environnement FOO est définie sur bar pour le conteneur container-1.

Montage automatique de volumes (obsolète)

Note : L'annotation de montage automatique est obsolète. Kubernetes prend en charge nativement les volumes d'images, et ceux-ci doivent être utilisés plutôt que cette annotation spécifique à Podman.

Une image peut être montée automatiquement dans un conteneur si l'annotation io.podman.annotations.kube.image.automount/$ctrname est fournie. Les règles suivantes s'appliquent :

  • L'image doit déjà exister localement.
  • L'image doit avoir au moins une directive de volume.
  • Le chemin indiqué par la directive de volume sera monté depuis l'image dans le conteneur. Par exemple, une image avec un volume à /test/test_dir aura /test/test_dir dans l'image montée sur /test/test_dir dans le conteneur.
  • Plusieurs images peuvent être spécifiées. Si plusieurs images ont un volume au même chemin, la dernière image spécifiée l'emporte.
  • Les images sont toujours montées en lecture seule.
  • Les images à monter sont définies dans l'annotation "io.podman.annotations.kube.image.automount/$ctrname" sous forme de liste séparée par des points-virgules. Elles sont montées dans un seul conteneur du pod, pas dans l'ensemble du pod. L'annotation peut être spécifiée pour des conteneurs supplémentaires si des montages supplémentaires sont requis.

OPTIONS

--annotation=clé=valeur

Ajoute une annotation au conteneur ou au pod. Cette option peut être définie plusieurs fois.

Note : Pour podman kube play, le drapeau --annotation ajoute des annotations spécifiques à Podman aux conteneurs et aux pods créés par Podman, et non au fichier YAML Kubernetes lui-même. Ces annotations peuvent être utilisées pour configurer des fonctionnalités spécifiques à Podman telles que les espaces de noms utilisateur (io.podman.annotations.userns), les volumes-from (io.podman.annotations.volumes-from) et d'autres comportements de conteneurs.

--authfile=chemin

Chemin du fichier d'authentification. Par défaut, il s'agit de ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et de $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, lequel est défini à l'aide de docker login.

Note : Il existe également la possibilité de remplacer le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. Cela peut être fait avec export REGISTRY_AUTH_FILE=chemin.

--build

Construit les images même si elles sont trouvées dans le stockage local. Utilisez --build=false pour désactiver complètement les constructions. (Cette option n'est pas disponible avec le client Podman distant)

Note : Vous pouvez également remplacer le type d'isolation par défaut en définissant la variable d'environnement BUILDAH_ISOLATION. export BUILDAH_ISOLATION=oci. Voir podman-build.1.md pour plus d'informations.

--cert-dir=chemin

Utilise les certificats situés dans chemin (*.crt, *.cert, *.key) pour se connecter au registre. (Par défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (hors WSL2))

--configmap=chemin

Utilise un fichier YAML de configmap Kubernetes situé dans chemin pour fournir une source pour les valeurs des variables d'environnement dans les conteneurs du pod. (Cette option n'est pas disponible avec le client Podman distant)

Note : L'option --configmap peut être utilisée plusieurs fois ou une liste de chemins séparés par des virgules peut être utilisée pour transmettre plusieurs fichiers YAML de configmap Kubernetes. Le fichier YAML peut être au format YAML multi-documents. Cependant, il ne doit contenir que des configmaps.

--context-dir=chemin

Utilise chemin comme répertoire de contexte de construction pour chaque image. Nécessite que l'option --build soit vraie. (Cette option n'est pas disponible avec le client Podman distant)

--creds=[nom_utilisateur[:mot_de_passe]]

Le [nom_utilisateur[:mot_de_passe]] à utiliser pour s'authentifier auprès du registre, si nécessaire. Si une ou les deux valeurs ne sont pas fournies, une invite de commande apparaît et la valeur peut être saisie. Le mot de passe est saisi sans écho.

Notez que les informations d'identification spécifiées sont uniquement utilisées pour s'authentifier auprès des registres cibles. Elles ne sont pas utilisées pour les miroirs ou lorsque le registre est réécrit (voir containers-registries.conf(5)) ; pour s'authentifier auprès de ceux-ci, envisagez d'utiliser un fichier containers-auth.json(5).

--force

Supprime les volumes liés aux PersistentVolumeClaims dans le cadre de --down

--help, -h

Affiche le message d'utilisation

--ip=adresse IP

Attribue une adresse IP statique au pod. Cette option peut être spécifiée plusieurs fois lorsque kube play crée plus d'un pod. Note : Lors de la connexion à plusieurs réseaux, utilisez la syntaxe --network nom:ip=<ip>.

--log-driver=driver

Définit le pilote d'enregistrement pour tous les conteneurs créés.

--log-opt=nom=valeur

Options spécifiques au pilote d'enregistrement.

Définit une configuration d'enregistrement personnalisée. Les *noms* suivants sont pris en charge :

path : spécifie un chemin vers le fichier de log
(par exemple, --log-opt path=/var/log/container/mycontainer.json) ;

max-size : spécifie une taille maximale pour le fichier de log
(par exemple, --log-opt max-size=10mb) ;

tag : spécifie une étiquette de log personnalisée pour le conteneur
(par exemple, --log-opt tag="{{.ImageName}}". Il prend en charge les mêmes clés que podman inspect --format. Cette option n'est actuellement prise en charge que par le pilote de log journald.

--mac-address=adresse MAC

Attribue une adresse MAC statique au pod. Cette option peut être spécifiée plusieurs fois lorsque kube play crée plus d'un pod. Note : Lors de la connexion à plusieurs réseaux, utilisez la syntaxe --network nom:mac=<mac>.

--network=mode, --net

Définit le mode réseau pour le pod.

Les valeurs valides pour mode sont :

•
bridge[:OPTIONS,...] : Crée une pile réseau sur le pont par défaut. C'est le comportement par défaut pour les conteneurs rootful. Il est possible de spécifier les options supplémentaires suivantes :
  • alias=nom : Ajoute un alias spécifique au réseau pour le conteneur.
  • ip=IPv4 : Spécifie une adresse IPv4 statique pour ce conteneur.
  • ip6=IPv6 : Spécifie une adresse IPv6 statique pour ce conteneur.
  • mac=MAC : Spécifie une adresse MAC statique pour ce conteneur.
  • interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'intérieur du conteneur.
  • host_interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'extérieur du conteneur.
Toute autre option sera transmise à netavark sans validation. Cela peut être utile pour passer des arguments aux plugins netavark.

Par exemple, pour définir une adresse ipv4 statique et une adresse mac statique, utilisez --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nom ou ID de réseau>[:OPTIONS,...] : Se connecte à un réseau défini par l'utilisateur ; il s'agit du nom ou de l'ID d'un réseau créé par podman network create. Il est possible de spécifier les mêmes options décrites sous le mode bridge ci-dessus. Utilisez l'option --network plusieurs fois pour spécifier des réseaux supplémentaires.
    Pour des raisons de compatibilité ascendante, il est également possible de spécifier des réseaux séparés par des virgules dans le premier argument --network, mais cela vous empêche d'utiliser les options décrites dans la section bridge ci-dessus.
  • none : Crée un espace de noms réseau pour le conteneur mais ne configure aucune interface réseau pour celui-ci, de sorte que le conteneur n'a aucune connectivité réseau.
  • container:id : Réutilise la pile réseau d'un autre conteneur.
  • host : Utilise l'espace de noms réseau de l'hôte pour le conteneur au lieu d'en créer un isolé. Avertissement : Cela donne au conteneur un accès complet aux sockets Unix abstraits et aux sockets TCP/UDP liés à localhost. Étant donné que ces mécanismes sont souvent utilisés pour empêcher l'accès à des services système sensibles, en les isolant de l'accès par des entités externes, l'utilisation de cette option peut être considérée comme une vulnérabilité de sécurité.
  • ns:chemin : Chemin vers un espace de noms réseau à rejoindre.
  • private : Crée un nouvel espace de noms pour le conteneur. Ceci utilise le mode bridge pour les conteneurs rootful et slirp4netns pour les conteneurs rootless.
  • slirp4netns[:OPTIONS,...] : utilise slirp4netns(1) pour créer une pile réseau utilisateur. Il est possible de spécifier les options supplémentaires suivantes, qui peuvent également être définies avec network_cmd_options dans containers.conf :
  • allow_host_loopback=true|false : Autorise slirp4netns à accéder à l'IP de bouclage de l'hôte (par défaut, 10.0.2.2 ou la deuxième IP du sous-réseau CIDR de slirp4netns lorsqu'il est modifié, voir l'option cidr ci-dessous). La valeur par défaut est false.
  • mtu=MTU : Spécifie l'MTU à utiliser pour ce réseau. (Par défaut : 65520).
  • cidr=CIDR : Spécifie la plage IP à utiliser pour t son réseau. (Défaut : 10.0.2.0/24).
  • enable_ipv6=true|false : Activer IPv6. La valeur par défaut est true. (Requis pour outbound_addr6).
  • outbound_addr=INTERFACE : Spécifier l'interface de sortie sur laquelle slirp se lie (trafic ipv4 uniquement).
  • outbound_addr=IPv4 : Spécifier l'adresse ipv4 de sortie sur laquelle slirp se lie.
  • outbound_addr6=INTERFACE : Spécifier l'interface de sortie sur laquelle slirp se lie (trafic ipv6 uniquement).
  • outbound_addr6=IPv6 : Spécifier l'adresse ipv6 de sortie sur laquelle slirp se lie.
  • port_handler=rootlesskit : Utiliser rootlesskit pour le transfert de ports. Par défaut.
    Note : Rootlesskit change l'adresse IP source des paquets entrants vers une adresse IP dans l'espace de noms réseau du conteneur, généralement 10.0.2.100. Si l'application nécessite l'adresse IP source réelle, par exemple pour les journaux du serveur web, utilisez le gestionnaire de ports slirp4netns. Le gestionnaire de ports rootlesskit est également utilisé pour les conteneurs sans privilèges connectés à des réseaux définis par l'utilisateur.
  • port_handler=slirp4netns : Utiliser le transfert de ports slirp4netns, il est plus lent que rootlesskit mais préserve l'adresse IP source correcte. Ce gestionnaire de ports ne peut pas être utilisé pour les réseaux définis par l'utilisateur.
•
pasta[:OPTIONS,...] : utiliser pasta(1) pour créer une pile réseau en mode utilisateur.
C'est la valeur par défaut pour les conteneurs sans privilèges et pris en charge uniquement en mode sans privilèges.
Par défaut, les adresses et routes IPv4 et IPv6, ainsi que le nom de l'interface du pod, sont copiés depuis l'hôte. Le transfert de ports préserve l'adresse IP source d'origine. Les options décrites dans pasta(1) peuvent être spécifiées sous forme d'arguments séparés par des virgules.
En termes d'options de pasta(1), --config-net est donné par défaut, afin de configurer le réseau au démarrage du conteneur, et --no-map-gw est également supposé par défaut, pour éviter l'accès direct du conteneur à l'hôte en utilisant l'adresse de la passerelle. Ce dernier peut être remplacé en passant --map-gw dans les options spécifiques à pasta (malgré le fait que ce ne soit pas une option réelle de pasta(1)).
Pour une meilleure intégration avec la gestion DNS, --dns-forward 169.254.1.1 est passé, et cette adresse est ajoutée à resolv.conf(5) en tant que premier résolveur. Il est possible de passer --dns-forward explicitement au cas où une adresse IP différente devrait être utilisée. Pour que l'entrée host.containers.internal dans /etc/hosts fonctionne et permette les connexions à l'hôte, --map-guest-addr 169.254.1.2 est passé. Encore une fois, cela peut être défini explicitement pour choisir une adresse IP différente.
De plus, -t none et -u none sont passés si, respectivement, aucun transfert de port TCP ou UDP de l'hôte vers le conteneur n'est configuré (via --publish de Podman ou en passant directement les options -t/-u de pasta), pour désactiver le transfert de ports automatique basé sur les ports liés. De même, -T none et -U none sont donnés pour désactiver la même fonctionnalité du conteneur vers l'hôte.
Toutes les options peuvent également être définies dans containers.conf(5) ; voir la clé pasta_options dans la section réseau de ce fichier.
Quelques exemples :
  • pasta:--map-gw : Permettre au conteneur d'atteindre directement l'hôte en utilisant l'adresse de la passerelle.
  • pasta:--mtu,1500 : Spécifier une MTU de 1500 octets pour l'interface tap dans le conteneur.
  • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) : désactiver IPv6, assigner 10.0.2.0/24 à l'interface tap0 dans le conteneur, avec une passerelle 10.0.2.3, activer le forwarder DNS joignable à 10.0.2.3, définir la MTU à 1500 octets, désactiver NDP, DHCPv6 et DHCP.
  • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) avec les remplacements de Podman : identique à ci-dessus, mais laisser la MTU à 65520 octets
  • pasta:-t,auto,-u,auto,-T,auto,-U,auto : activer le transfert de ports automatique basé sur les ports liés observés des deux côtés, hôte et conteneur
  • pasta:-T,5201 : activer le transfert du port TCP 5201 du conteneur vers l'hôte, en utilisant l'interface de boucle locale au lieu de l'interface tap pour de meilleures performances

Lorsqu'aucune option réseau n'est spécifiée et que le mode réseau host n'est pas configuré dans le fichier YAML, une nouvelle pile réseau est créée et les pods y sont attachés, rendant possible la communication inter-pods.

--no-hostname

Ne pas créer le fichier /etc/hostname dans les conteneurs.

Par défaut, Podman gère le fichier /etc/hostname, en ajoutant le propre nom d'hôte du conteneur. Lorsque l'option --no-hostname est définie, le fichier /etc/hostname de l'image sera préservé sans modification s'il existe.

--no-hosts

Ne pas modifier le fichier /etc/hosts dans le pod.

Podman prend le contrôle du fichier /etc/hosts du pod par défaut et ajoute des entrées pour le nom du conteneur (voir l'option --name) et le nom d'hôte (voir l'option --hostname), les hôtes internes host.containers.internal et host.docker.internal, ainsi que tout nom d'hôte ajouté à l'aide de l'option --add-host. Reportez-vous à l'option --add-host pour plus de détails. Passer --no-hosts désactive cela, de sorte que le fichier /etc/hosts de l'image est conservé sans modification. La même chose peut être obtenue globalement en définissant no_hosts=true dans containers.conf.

Cette option est en conflit avec les hôtes ajoutés dans le YAML Kubernetes.

--no-pod-prefix

Ne pas préfixer le nom du conteneur avec le nom du pod.

--publish=[[ip:][hostPort]:]containerPort[/protocol]

Définir ou remplacer une définition de port dans le fichier YAML.

Les listes de ports dans le fichier YAML et la ligne de commande sont fusionnées. La correspondance se fait en utilisant le champ containerPort. Si containerPort existe à la fois dans le fichier YAML et dans l'option, cette dernière a la priorité.

--publish-all

Définir cette option à true exposera tous les ports à l'hôte, même s'ils ne sont spécifiés que via containerPort dans le YAML K8. En termes de quel port sera exposé, --publish a une priorité plus élevée que hostPort, qui a une priorité plus élevée que containerPort.

Si défini à false (ce qui est la valeur par défaut), seuls les ports définis via hostPort ou --publish sont publiés sur l'hôte.

--quiet, -q

Supprimer les informations de sortie lors du téléchargement des images

--replace

Détruit les pods créés par une exécution précédente de kube play et recrée les pods. Cette option est utilisée pour maintenir les pods existants à jour en fonction du YAML Kubernetes.

--seccomp-profile-root=chemin

Chemin du répertoire pour les profils seccomp (défaut : "/var/lib/kubelet/seccomp"). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exception de WSL2)).

--start

Démarrer le pod après sa création, définir à false pour seulement le créer.

--tls-verify

Exiger HTTPS et vérifier les certificats lors du contact avec les registres (défaut : true). S'il est explicitement défini à true, la vérification TLS est utilisée. S'il est défini à false, la vérification TLS n'est pas utilisée. Si non spécifié, la vérification TLS est utilisée à moins que le registre cible ne soit listé comme un registre non sécurisé dans containers-registries.conf(5)

--userns=mode

Définir le mode de l'espace de noms utilisateur pour le conteneur.

Si --userns n'est pas défini, la valeur par défaut est déterminée comme suit. - Si --pod est défini, --userns est ignoré et l'espace de noms utilisateur du pod est utilisé. - Si la variable d'environnement PODMAN_USERNS est définie, sa valeur est utilisée. - Si userns est spécifié dans containers.conf, cette valeur est utilisée. - Sinon, --userns=host est supposé.

--userns="" (c'est-à-dire une chaîne vide) est un alias pour --userns=host.

Cette option est incompatible avec --gidmap, --uidmap, --subuidname et --subgidname.

Mappages des clés --userns pour les utilisateurs sans privilèges :

Clé Utilisateur hôte Utilisateur conteneur
auto $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)
host $UID 0 (Le compte utilisateur par défaut est mappé à l'utilisateur root dans le conteneur.)
keep-id $UID $UID (Mappe le compte utilisateur au même UID dans le conteneur.)
keep-id:uid=200,gid=210 $UID 200:210 (Mappe le compte utilisateur à l'UID, valeur GID spécifiée dans le conteneur.)
nomap $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)

Les valeurs valides pour mode sont :

auto[:OPTIONS,...] : crée automatiquement un espace de noms utilisateur unique.

  • Mode rootful : Le drapeau --userns=auto nécessite que le nom d'utilisateur containers soit spécifié dans les fichiers /etc/subuid et /etc/subgid, avec une plage inutilisée d'identifiants d'utilisateurs subordonnés que Podman peut allouer aux conteneurs. Exemple : containers:2147483647:2147483648.
  • Mode sans privilèges : La plage d'utilisateurs des fichiers /etc/subuid et /etc/subgid sera utilisée. Notez que l'exécution d'un seul conteneur sans utiliser --userns=auto utilisera la plage entière d'UID et n'autorisera pas de subdivision supplémentaire. Voir subuid(5).

Podman alloue des plages uniques d'UID et de GID à partir des identifiants d'utilisateurs subordonnés containers. La taille des plages est basée sur le nombre d'UID requis dans l'image. Le nombre d'UID et de GID peut être remplacé par l'option size.

L'option --userns=keep-id utilise tous les subuids et subgids de l'utilisateur. L'option --userns=nomap utilise tous les subuids et subgids de l'utilisateur, sauf l'ID de l'utilisateur lui-même. L'utilisation de --userns=auto lors du démarrage de nouveaux conteneurs ne fonctionne pas tant qu'il existe des conteneurs démarrés avec --userns=nomap ou --userns=keep-id sans limiter la taille de l'espace de noms utilisateur.

Options valides pour auto op

tions :

  • gidmapping=CONTAINER_GID:HOST_GID:SIZE : pour forcer un mappage GID à être présent dans l'espace de noms utilisateur.
  • size=SIZE : pour spécifier une taille explicite pour l'espace de noms utilisateur automatique. Par exemple, --userns=auto:size=8192. Si size n'est pas spécifié, auto estime une taille pour l'espace de noms utilisateur.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE : pour forcer un mappage UID à être présent dans l'espace de noms utilisateur.

L'UID et le GID de l'hôte dans gidmapping et uidmapping peuvent être préfixés optionnellement avec le symbole @. Dans ce cas, podman recherchera l'ID intermédiaire correspondant à l'ID de l'hôte et mappera l'ID intermédiaire trouvé à l'ID du conteneur. Pour plus de détails, voir --uidmap.

container:id : rejoint l'espace de noms utilisateur du conteneur spécifié.

host ou "" (chaîne vide) : s'exécute dans l'espace de noms utilisateur de l'appelant. Les processus s'exécutant dans le conteneur ont les mêmes privilèges sur l'hôte que tout autre processus lancé par l'utilisateur appelant.

keep-id : crée un espace de noms utilisateur où l'UID :GID de l'utilisateur actuel sont mappés aux mêmes valeurs dans le conteneur. Pour les conteneurs créés par root, le mappage actuel est créé dans un nouvel espace de noms utilisateur.

De plus, le processus d'initialisation à l'intérieur du conteneur s'exécutera sous l'UID de l'utilisateur actuel. Ce comportement remplace l'instruction USER de l'image, sauf si vous spécifiez explicitement --user.

Options valides pour keep-id :

  • uid=UID : remplace l'UID à l'intérieur du conteneur utilisé pour mapper l'utilisateur actuel.
  • gid=GID : remplace le GID à l'intérieur du conteneur utilisé pour mapper l'utilisateur actuel.
  • size=SIZE : remplace la taille de l'espace de noms utilisateur configuré. Il est utile de ne pas saturer tous les IDs disponibles. Non supporté lors de l'exécution en tant que root.

nomap : crée un espace de noms utilisateur où l'UID :GID de l'utilisateur rootless actuel ne sont pas mappés dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.

ns:namespace : exécute le pod dans l'espace de noms utilisateur existant donné.

--wait, -w

Exécute les pods et les conteneurs au premier plan. La valeur par défaut est false.

À tout moment, vous pouvez exécuter podman pod ps dans un autre shell pour afficher une liste des pods et conteneurs en cours d'exécution.

Lorsqu'il est attaché en mode tty, vous pouvez arrêter les pods et les conteneurs en appuyant sur Ctrl-C ou en recevant d'autres signaux d'interruption.

Tous les pods, conteneurs et volumes créés avec podman kube play sont supprimés à la sortie.

podman-play-kube.1.en

NAME

podman-play-kube - Run containerized applications defined by Kubernetes Pod, Deployment, or DaemonSet YAML files

SYNOPSIS

podman play kube [options] [kube_file...]

DESCRIPTION

The podman play kube command takes one or more Kubernetes YAML files as input and creates containers, networks, and volumes based on the definitions in the files. This allows users to run applications defined for Kubernetes locally using Podman. The command supports Pod, Deployment, DaemonSet, and StatefulSet resource types.

Supported resource types include:

  • Pods
  • Deployments
  • DaemonSets
  • StatefulSets
  • Services (only Service type LoadBalancer and NodePort are supported, and they are translated to port mappings on the host)
  • ConfigMaps
  • PersistentVolumeClaims

The command translates Kubernetes resources into Podman equivalents. For example, a Kubernetes Pod is created as a Podman pod, Kubernetes Services are translated into port mappings, and Kubernetes Deployments and DaemonSets are translated into multiple Podman containers within a Podman pod.

OPTIONS

Option Description
--down, -d Tear down the containers and networks defined by the Kubernetes YAML files. This option is equivalent to running `podman play kube --rm` and then deleting the containers and networks.
--dry-run Print the Podman commands that would be executed without actually running them.
--force, -f Force the recreation of containers, even if they already exist.
--network Specify a network to use for the containers. If not specified, a new network will be created.
--rm Remove containers and networks when they are stopped.
--save Save the generated Podman commands to a file.
--tls-verify Verify the identity of the remote insecure registry (default: true).
-v, --volume-driver Volume driver name. Not currently used by podman play kube.
--volume-dir Directory to use for volumes. If not specified, a default directory will be used.

EXAMPLES

Run a Kubernetes Pod defined in pod.yaml:

podman play kube pod.yaml

Run a Kubernetes Deployment defined in deployment.yaml and remove the containers when stopped:

podman play kube --rm deployment.yaml

Tear down the containers and networks defined in deployment.yaml:

podman play kube --down deployment.yaml
