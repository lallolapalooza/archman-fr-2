podman(1) Manuel des commandes générales podman(1)

NOM

podman - Outil simple de gestion de pods, conteneurs et images

SYNTAXE

podman [options] commande

DESCRIPTION

Podman (Pod Manager) est un moteur de conteneurs complet, un outil simple sans démon. Podman fournit une ligne de commande comparable à Docker-CLI, facilitant la transition depuis d'autres moteurs de conteneurs et permettant la gestion des pods, des conteneurs et des images. En bref : alias docker=podman. La plupart des commandes Podman peuvent être exécutées par un utilisateur ordinaire, sans nécessiter de privilèges supplémentaires.

Podman utilise Buildah(1) en interne pour créer des images de conteneurs. Les deux outils partagent le stockage des images (pas des conteneurs), donc chacun peut utiliser ou manipuler des images (mais pas des conteneurs) créées par l'autre.

Les paramètres par défaut des options sont définis dans containers.conf. La plupart des paramètres pour les connexions à distance utilisent le containers.conf du serveur, sauf indication contraire dans les pages de manuel.

podman [OPTIONS GLOBALES]

OPTIONS GLOBALES

--cdi-spec-dir=chemin

Le chemin du répertoire des spécifications CDI (peut être défini plusieurs fois). Le chemin par défaut est /etc/cdi.

--cgroup-manager=gestionnaire

Le gestionnaire de CGroup à utiliser pour les cgroups des conteneurs. Les valeurs supportées sont cgroupfs ou systemd. Le défaut est systemd sauf si remplacé dans le fichier containers.conf.

Note : L'utilisation de cette option peut causer des problèmes avec certaines commandes appelées sur des conteneurs précédemment créés par l'autre type de gestionnaire de CGroup. Note : Le gestionnaire de CGroup n'est pas supporté en mode sans privilèges lors de l'utilisation de la version V1 des CGroups.

--config

Emplacement du fichier de configuration. Principalement pour la compatibilité avec Docker, seules les parties relatives à l'authentification de la configuration sont supportées.

--conmon

Chemin du binaire conmon (Le chemin par défaut est configuré dans containers.conf)

--connection, -c

Connexion à utiliser pour podman distant, y compris les machines Mac et Windows (hors WSL2), (La connexion par défaut est configurée dans containers.conf) Définir cette option bascule l'option --remote sur true. Les connexions distantes utilisent le containers.conf local pour les paramètres par défaut.

--events-backend=type

Backend à utiliser pour stocker les événements. Les valeurs autorisées sont file, journald, et none. Lorsque file est spécifié, les événements sont stockés sous <tmpdir>/events/events.log (voir --tmpdir ci-dessous).

--help, -h

Affiche le message d'utilisation

--hooks-dir=chemin

Chaque fichier *.json dans le chemin configure un hook pour les conteneurs Podman. Pour plus de détails sur la syntaxe des fichiers JSON et la sémantique de l'injection de hooks, voir oci-hooks(5). Podman et libpod supportent actuellement les schémas de hooks 1.0.0 et 0.1.0, bien que le schéma 0.1.0 soit déprécié.

Cette option peut être définie plusieurs fois ; les chemins des options ultérieures ont une priorité plus élevée (voir oci-hooks(5) pour la priorité des répertoires).

Pour les conditions d'annotation, libpod utilise toutes les annotations définies dans la configuration OCI générée.

Pour les conditions de montage de liaison, seuls les montages explicitement demandés par l'appelant via --volume sont pris en compte. Les montages de liaison que libpod insère par défaut (par exemple /dev/shm) ne sont pas pris en compte.

Si --hooks-dir n'est pas défini pour les appelants privilégiés, Podman et libpod utilisent par défaut /usr/share/containers/oci/hooks.d et /etc/containers/oci/hooks.d par ordre de priorité croissante. L'utilisation de ces valeurs par défaut est dépréciée. Migrez vers la définition explicite de --hooks-dir.

Podman et libpod supportent actuellement un état supplémentaire precreate qui est appelé avant l'opération create du runtime. Contrairement aux autres étapes, qui reçoivent l'état du conteneur sur leur entrée standard, les hooks precreate reçoivent la configuration de runtime proposée sur leur entrée standard. Ils peuvent modifier cette configuration comme bon leur semble, et écrire la forme modifiée sur leur sortie standard.

ATTENTION : le hook precreate permet des changements puissants, tels que l'ajout de montages supplémentaires à la configuration du runtime. Ce pouvoir le rend également facile à mal utiliser. Avant de signaler des erreurs libpod, essayez d'exécuter un conteneur avec les hooks precreate désactivés pour voir si le problème vient de l'un des hooks.

--identity=chemin

Chemin du fichier d'identité ssh. Si le fichier d'identité a été chiffré, podman demande à l'utilisateur la phrase de passe. Si aucun fichier d'identité n'est fourni et qu'aucun utilisateur n'est spécifié, podman utilise par défaut l'utilisateur exécutant la commande podman. Podman demande le mot de passe de connexion sur le serveur distant.

Priorité de résolution de la valeur d'identité :
- valeur de la ligne de commande
- variable d'environnement CONTAINER_SSHKEY, si CONTAINER_HOST est trouvée
- containers.conf Les connexions distantes utilisent le containers.conf local pour la valeur par défaut.

--imagestore=chemin

Chemin de l'imagestore où sont stockées les images. Par défaut, la bibliothèque de stockage stocke toutes les images dans le graphroot, mais si un imagestore est fourni, la bibliothèque de stockage stockera les images nouvellement téléchargées dans l'imagestore fourni et continuera à utiliser le graphroot pour tout le reste. Si l'utilisateur utilise le pilote overlay, les images qui faisaient déjà partie du graphroot resteront accessibles.

Ceci remplacera l'option imagestore dans containers-storage.conf(5), reportez-vous à containers-storage.conf(5) pour plus de détails.

--log-level=niveau

Messages de log d'un niveau égal ou supérieur au niveau spécifié : debug, info, warn, error, fatal ou panic (défaut : warn)

--module=chemin

Charge le module containers.conf(5) spécifié. Peut être un chemin absolu ou relatif. Veuillez vous référer à containers.conf(5) pour plus de détails.

Cette option n'est pas supportée sur le client distant, y compris les machines Mac et Windows (hors WSL2). De plus, cette option est une option de niveau racine et doit être spécifiée avant toute sous-commande Podman.

--network-cmd-path=chemin

Chemin vers le binaire de commande slirp4netns(1) à utiliser pour la configuration d'un réseau slirp4netns. Si "" est utilisé, le binaire sera d'abord recherché en utilisant l'option helper_binaries_dir dans containers.conf, puis dans la variable d'environnement $PATH. Note : Cette option est dépréciée et sera supprimée avec Podman 6.0. Utilisez l'option helper_binaries_dir dans containers.conf à la place.

--network-config-dir=répertoire

Chemin vers le répertoire où se trouvent les fichiers de configuration réseau. Pour le backend netavark, "/etc/containers/networks" est utilisé comme racine et "$graphroot/networks" comme sans privilèges. Pour le backend CNI, le défaut est "/etc/cni/net.d" comme racine et "$HOME/.config/cni/net.d" comme sans privilèges. CNI est déprécié et sera supprimé dans la prochaine version majeure de Podman 5.0 au profit de Netavark.

--out=chemin

Redirige la sortie de podman vers le chemin spécifié sans affecter la sortie du conteneur ou ses logs. Ce paramètre peut être utilisé pour capturer la sortie de n'importe quelle commande de podman directement dans un fichier et permettre la suppression de la sortie de podman en spécifiant /dev/null comme chemin. Pour désactiver explicitement la journalisation du conteneur, l'option --log-driver doit être utilisée.

--remote, -r

Lorsqu'il est vrai, l'accès au service Podman est distant. Le défaut est false. Les paramètres peuvent être modifiés dans le fichier containers.conf. Si la variable d'environnement CONTAINER_HOST est définie, l'option --remote devient vraie par défaut.

OPTIONS

Les options suivantes sont disponibles :

--root=valeur

Répertoire racine de stockage dans lequel les données, y compris les images, sont stockées (par défaut : « /var/lib/containers/storage » pour l’UID 0, « $HOME/.local/share/containers/storage » pour les autres utilisateurs). Répertoire racine par défaut configuré dans containers-storage.conf(5).

Le remplacement de cette option entraîne l’ignorance des paramètres storage-opt dans containers-storage.conf(5). L’utilisateur doit spécifier des options supplémentaires via l’indicateur --storage-opt.

--runroot=valeur

Répertoire d’état de stockage où toutes les informations d’état sont stockées (par défaut : « /run/containers/storage » pour l’UID 0, « /run/user/$UID/run » pour les autres utilisateurs). Répertoire d’état par défaut configuré dans containers-storage.conf(5).

--runtime=valeur

Nom du runtime OCI tel que spécifié dans containers.conf ou chemin absolu vers le binaire compatible OCI utilisé pour exécuter les conteneurs.

--runtime-flag=indicateur

Ajoute des indicateurs globaux pour le runtime du conteneur. Pour lister les indicateurs pris en charge, veuillez consulter les pages de manuel du runtime de conteneur sélectionné (runc est le runtime par défaut, la page de manuel à consulter est runc(8). Lorsque la machine est configurée pour cgroup V2, le runtime par défaut est crun, la page de manuel à consulter est crun(8).).

Les indicateurs de runtime par défaut peuvent être ajoutés dans containers.conf.

Remarque : Ne pas faire précéder l’indicateur par --. Pour transmettre l’indicateur runc --log-format json à podman build, l’option donnée peut être --runtime-flag log-format=json.

--ssh=valeur

Cette option permet à l’utilisateur de modifier le mode ssh, ce qui signifie qu’au lieu d’utiliser le mode golang par défaut, on peut utiliser --ssh=native pour utiliser le binaire ssh installé et le fichier de configuration déclaré dans containers.conf.

--storage-driver=valeur

Pilote de stockage. Le pilote de stockage par défaut pour l’UID 0 est configuré dans containers-storage.conf(5) en mode sans root), et est vfs pour les utilisateurs non-root lorsque fuse-overlayfs n’est pas disponible. La variable d’environnement STORAGE_DRIVER remplace la valeur par défaut. Le pilote spécifié par --storage-driver remplace tout.

Le remplacement de cette option entraîne l’ignorance des paramètres storage-opt dans containers-storage.conf(5). L’utilisateur doit spécifier des options supplémentaires via l’indicateur --storage-opt.

--storage-opt=valeur

Spécifie une option de pilote de stockage. Les options de pilote de stockage par défaut sont configurées dans containers-storage.conf(5). La variable d’environnement STORAGE_OPTS remplace la valeur par défaut. Les options spécifiées par --storage-opt remplacent tout. Spécifiez --storage-opt=« » pour qu’aucune option de stockage ne soit utilisée.

--syslog

Envoyer les informations de journalisation à syslog ainsi qu’à la console (par défaut false).

Sur les clients distants, y compris les machines Mac et Windows (à l’exception de WSL2), la journalisation est dirigée vers le fichier $HOME/.config/containers/podman.log.

--tls-ca=chemin

Chemin vers un fichier PEM contenant le paquet d’autorité de certification pour vérifier le certificat du serveur.

--tls-cert=chemin

Chemin vers un fichier PEM contenant le certificat client TLS à présenter au serveur. --tls-key doit également être fourni.

--tls-key=chemin

Chemin vers un fichier PEM contenant la clé privée correspondant à --tls-cert. --tls-cert doit également être fourni.

--tmpdir=chemin

Chemin vers le répertoire tmp, pour le contenu du runtime libpod. Par défaut, il s’agit de $XDG_RUNTIME_DIR/libpod/tmp en mode sans root et /run/libpod/tmp en mode root.

NOTE --tmpdir n’est pas utilisé pour le stockage temporaire des images téléchargées. Utilisez la variable d’environnement TMPDIR pour modifier l’emplacement du stockage temporaire des images de conteneurs téléchargées. Podman utilise par défaut /var/tmp.

--transient-store

Active un mode de stockage transitoire global où tous les métadonnées du conteneur sont stockées sur un support non persistant (c’est-à-dire à l’emplacement spécifié par --runroot). Ce mode permet de démarrer les conteneurs plus rapidement, ainsi que de garantir un état frais au démarrage en cas d’arrêts brutaux ou d’autres problèmes. Cependant, il n’est pas compatible avec un modèle traditionnel où les conteneurs persistent après les redémarrages.

La valeur par défaut pour ceci est configurée dans containers-storage.conf(5).

--url=valeur

URL pour accéder au service Podman (par défaut dans containers.conf, unix:///run/user/$UID/podman/podman.sock sans root ou en tant que root unix:///run/podman/podman.sock). La définition de cette option bascule l’option --remote à true.

•
CONTAINER_HOST est du format <schéma>://[<utilisateur[:<mot de passe>]@]<hôte>[:<port>][<chemin>]

Détails :

- schéma est l’un des suivants :

* ssh (par défaut) : un socket de domaine Unix local (unix(7)) sur l’hôte et le port nommés, accessible via SSH

* tcp : une connexion TCP non chiffrée et non authentifiée vers l’hôte et le port nommés

* unix : un socket de domaine Unix local (unix(7)) à l’emplacement spécifié, ou la valeur par défaut pour l’utilisateur

- utilisateur est par défaut soit root, soit l’utilisateur actuellement en cours d’exécution (uniquement ssh)

- mot de passe n’a pas de valeur par défaut (uniquement ssh)

- hôte doit être fourni et est soit l’adresse IP, soit le nom de la machine hébergeant le service Podman (ssh et tcp)

- port est par défaut 22 (ssh et tcp)

- chemin est par défaut soit /run/podman/podman.sock, soit /run/user/$UID/podman/podman.sock si exécuté sans root (unix), ou doit être explicitement spécifié (ssh)

Priorité de résolution de la valeur URL :

- valeur de la ligne de commande

- variable d’environnement CONTAINER_HOST

- table engine.service_destinations dans containers.conf, à l’exclusion du répertoire /usr/share/containers

- unix:///run/podman/podman.sock

Les connexions distantes utilisent containers.conf locale pour la valeur par défaut.

Quelques exemples de valeurs d’URL dans des formats valides :

- unix:///run/podman/podman.sock

- unix:///run/user/$UID/podman/podman.sock

- ssh://notroot@localhost:22/run/user/$UID/podman/podman.sock

- ssh://root@localhost:22/run/podman/podman.sock

- tcp://localhost:34451

- tcp://127.0.0.1:34451

--version, -v

Affiche la version

--volumepath=valeur

Répertoire de volumes où sont stockées les informations de volumes intégrés (par défaut : « /var/lib/containers/storage/volumes » pour l’UID 0, « $HOME/.local/share/containers/storage/volumes » pour les autres utilisateurs). Le chemin de volume par défaut peut être remplacé dans containers.conf.

Variables d'Environnement

Podman peut configurer des variables d’environnement à partir de la table env de [engine] dans containers.conf. Ces variables peuvent être remplacées en passant des variables d’environnement avant les commandes podman.

CONTAINERS_CONF

Définit les emplacements par défaut du fichier containers.conf

CONTAINERS_REGISTRIES_CONF

Définit l’emplacement par défaut du fichier registries.conf.

CONTAINERS_STORAGE_CONF

Définit l’emplacement par défaut du fichier storage.conf.

CONTAINER_CONNECTION

Remplace la valeur par défaut de --connection pour accéder au service Podman. Active automatiquement l’option --remote.

CONTAINER_HOST

Définit la valeur par défaut de --url pour accéder au service Podman. Active automatiquement l’option --remote.

CONTAINER_SSHKEY

Définit le chemin par défaut de --identity vers la valeur du fichier de clé ssh utilisé pour accéder au service Podman.

PODMAN_CONNECTIONS_CONF

Le chemin vers le fichier où sont stockées les connexions système et les fermes créées avec podman system connection add et podman farm add, par défaut il utilise ~/.config/containers/podman-connections.json.

STORAGE_DRIVER

Définit la valeur par défaut de --storage-driver.

STORAGE_OPTS

Définit la valeur par défaut de --storage-opt.

TMPDIR

Définit l’emplacement de stockage temporaire des images de conteneurs téléchargées. Podman utilise par défaut /var/tmp.

XDG_CONFIG_HOME

En mode sans root, les fichiers de configuration sont lus à partir de XDG_CONFIG_HOME lorsqu’il est spécifié, sinon dans le répertoire personnel de l’utilisateur sous $HOME/.config/containers.

XDG_DATA_HOME

En mode sans root, les images sont téléchargées sous XDG_DATA_HOME lorsqu’il est spécifié, sinon dans le répertoire personnel de l’utilisateur sous $HOME/.local/share/containers/storage.

XDG_RUNTIME_DIR

En mode sans root, les données de configuration temporaires sont stockées dans ${XDG_RUNTIME_DIR}/containers.

Accès Distant

La commande Podman peut être utilisée avec des services distants en utilisant l’indicateur --remote. Les connexions peuvent être établies à l’aide de sockets de domaine Unix locaux, de ssh ou directement à des sockets tcp. Lors de la spécification de l’indicateur podman --remote, seules les options globales --url, --identity, --log-level, --connection sont utilisées.

Remarque :

Lorsqu’une connexion à un service distant est établie, certaines options et commandes peuvent se comporter différemment ou ne pas être disponibles. Par exemple, les commandes qui modifient le stockage de l’hôte distant (comme podman pull, podman build, podman run, etc.) continueront de fonctionner comme prévu, mais les commandes liées à la configuration du système hôte Podman lui-même (comme podman system reset) ne fonctionneront pas.

Lorsque vous utilisez l’indicateur --remote avec une connexion ssh, Podman utilisera la configuration SSH configurée dans votre fichier ~/.ssh/config (par exemple, pour spécifier une clé SSH différente, un port différent, etc.). Vous pouvez également utiliser l’indicateur --identity pour spécifier explicitement le chemin vers une clé SSH.

Pour plus de détails sur la configuration et l’utilisation de l’accès distant, veuillez consulter la documentation de Podman ou les pages de manuel relatives à la configuration du service Podman.

INFORMATIONS DE CONNEXION

Les informations de connexion peuvent également être gérées à l'aide du fichier containers.conf.

CODES DE SORTIE

Le code de sortie de podman donne des informations sur la raison pour laquelle le conteneur n'a pas pu démarrer ou pourquoi il s'est arrêté. Lorsque les commandes podman se terminent avec un code non nul, les codes de sortie suivent la norme chroot, voir ci-dessous :

125 L'erreur concerne podman **lui-même**.

$ podman run --foo busybox; echo $?
Error: unknown flag: --foo
125

126 L'exécution d'une commande de conteneur et la commande ne peut pas être invoquée.

$ podman run busybox /etc; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"/etc\": permission denied": OCI runtime error
126

127 L'exécution d'une commande de conteneur et la commande ne peut pas être trouvée.

$ podman run busybox foo; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"foo\": executable file not found in $PATH": OCI runtime error
127

Code de sortie Sinon, podman renvoie le code de sortie de la commande du conteneur.

$ podman run busybox /bin/sh -c 'exit 3'; echo $?
3

FICHIERS DE CONFIGURATION

containers.conf (/usr/share/containers/containers.conf, /etc/containers/containers.conf, $HOME/.config/containers/containers.conf)

Podman dispose de valeurs par défaut intégrées pour les options de ligne de commande. Ces valeurs par défaut peuvent être remplacées en utilisant les fichiers de configuration containers.conf.

Les distributions fournissent le fichier /usr/share/containers/containers.conf avec leurs paramètres par défaut. Les administrateurs peuvent remplacer les champs de ce fichier en créant le fichier /etc/containers/containers.conf. Les utilisateurs peuvent modifier davantage les valeurs par défaut en créant le fichier $HOME/.config/containers/containers.conf. Podman fusionne ses valeurs par défaut intégrées avec les champs spécifiés de ces fichiers, s'ils existent. Les champs spécifiés dans le fichier utilisateur remplacent le fichier de l'administrateur, qui remplace le fichier de la distribution, qui remplace les valeurs par défaut intégrées.

Podman utilise les valeurs par défaut intégrées si aucun fichier containers.conf n'est trouvé.

Si la variable d'environnement CONTAINERS_CONF est définie, alors sa valeur est utilisée pour le fichier containers.conf plutôt que la valeur par défaut.

mounts.conf (/usr/share/containers/mounts.conf)

Le fichier mounts.conf spécifie les répertoires de montage de volume qui sont automatiquement montés à l'intérieur des conteneurs lors de l'exécution des commandes podman run ou podman start. Les administrateurs peuvent remplacer le fichier par défaut en créant /etc/containers/mounts.conf.

Lorsque Podman s'exécute en mode rootless, le fichier $HOME/.config/containers/mounts.conf remplace la valeur par défaut s'il existe. Pour plus de détails, voir containers-mounts.conf(5).

policy.json (/etc/containers/policy.json, $HOME/.config/containers/policy.json)

Les fichiers de politique de vérification de signature sont utilisés pour spécifier la politique, par exemple, les clés de confiance, applicable lors de la décision d'accepter une image, ou des signatures individuelles de cette image, comme valide. Pour plus de détails, voir containers-policy.json(5).

registries.conf (/etc/containers/registries.conf, $HOME/.config/containers/registries.conf)

registries.conf est le fichier de configuration qui spécifie quels registres de conteneurs sont consultés lors de la complétion des noms d'images qui n'incluent pas de registre ou de partie de domaine.

Les utilisateurs non root de Podman peuvent créer le fichier $HOME/.config/containers/registries.conf pour qu'il soit utilisé à la place des valeurs par défaut du système.

Si la variable d'environnement CONTAINERS_REGISTRIES_CONF est définie, alors sa valeur est utilisée pour le fichier registries.conf plutôt que la valeur par défaut.

storage.conf (/etc/containers/storage.conf, $HOME/.config/containers/storage.conf)

storage.conf est le fichier de configuration de stockage pour tous les outils utilisant containers/storage

Le fichier de configuration de stockage spécifie toutes les options de stockage de conteneur disponibles pour les outils utilisant le stockage de conteneur partagé.

Lorsque Podman s'exécute en mode rootless, le fichier $HOME/.config/containers/storage.conf est utilisé à la place des valeurs par défaut du système.

Si la variable d'environnement CONTAINERS_STORAGE_CONF est définie, alors sa valeur est utilisée pour le fichier storage.conf plutôt que la valeur par défaut.

Mode Rootless

Podman peut également être utilisé en tant qu'utilisateur non root. Lorsque podman s'exécute en mode rootless, un espace de noms utilisateur est

automatiquement créé pour l'utilisateur, défini dans /etc/subuid et /etc/subgid.

Les conteneurs créés par un utilisateur non root ne sont pas visibles par les autres utilisateurs et ne sont pas vus ou gérés par Podman s'exécutant en tant que root.

Il est nécessaire d'avoir plusieurs UID/GID attribués à un utilisateur. Assurez-vous que l'utilisateur est présent dans les fichiers /etc/subuid et /etc/subgid.

Exécutez les commandes suivantes pour ajouter les plages aux fichiers

$ sudo usermod --add-subuids 10000-75535 USERNAME
$ sudo usermod --add-subgids 10000-75535 USERNAME

Ou ajoutez simplement le contenu manuellement.

$ echo USERNAME:10000:65536 >> /etc/subuid
$ echo USERNAME:10000:65536 >> /etc/subgid

Consultez les pages de manuel subuid(5) et subgid(5) pour plus d'informations.

Note: les espaces blancs dans une ligne de /etc/subuid ou /etc/subgid, y compris les espaces de fin de ligne, peuvent entraîner des échecs de non-prise en compte des entrées.

Les images sont téléchargées sous XDG_DATA_HOME si spécifié, sinon dans le répertoire personnel de l'utilisateur sous .local/share/containers/storage.

Actuellement, slirp4netns ou pasta est requis pour créer un périphérique réseau, sinon les conteneurs sans root doivent s'exécuter dans l'espace de noms réseau de l'hôte.

Dans certains environnements comme le HPC (High Performance Computing), les utilisateurs ne peuvent pas bénéficier des UID et GID supplémentaires des systèmes /etc/subuid et /etc/subgid. Cependant, dans cet environnement, Podman sans root peut fonctionner avec un seul UID. Pour que cela fonctionne, définissez l'option ignore_chown_errors dans le fichier containers-storage.conf(5). Cette option indique à Podman, lors du téléchargement d'une image, d'ignorer les erreurs de chown lors de la tentative de modification d'un fichier d'une image de conteneur pour qu'il corresponde à l'UID non root de l'image. Cela signifie que tous les fichiers sont sauvegardés avec l'UID de l'utilisateur. Notez que cela peut causer des problèmes lors de l'exécution du conteneur.

NOTE: Systèmes de fichiers non pris en charge en mode sans root

Le système de fichiers Overlay (OverlayFS) n'est pas pris en charge avec les noyaux antérieurs à 5.12.9 en mode sans root. Le paquet fuse-overlayfs est un outil qui fournit la fonctionnalité d'OverlayFS dans l'espace de noms utilisateur, permettant le montage de systèmes de fichiers dans des environnements sans root. Il est recommandé d'installer le paquet fuse-overlayfs. En mode sans root, Podman utilise automatiquement le programme fuse-overlayfs comme programme de montage (mount_program) s'il est installé, tant que le fichier $HOME/.config/containers/storage.conf n'a pas été créé précédemment. Si storage.conf existe dans le répertoire personnel, ajoutez mount_program = "/usr/bin/fuse-overlayfs" sous [storage.options.overlay] pour activer cette fonctionnalité.

Le système de fichiers réseau (NFS) et d'autres systèmes de fichiers distribués (par exemple: Lustre, Spectrum Scale, General Parallel File System (GPFS)) ne sont pas pris en charge lors de l'exécution en mode sans root, car ces systèmes de fichiers ne comprennent pas l'espace de noms utilisateur. Cependant, Podman sans root peut utiliser un répertoire personnel NFS en modifiant le fichier $HOME/.config/containers/storage.conf pour que l'option graphroot pointe vers un répertoire stocké sur un stockage local (non NFS).
