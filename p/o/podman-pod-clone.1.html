podman-pod-clone(1) Manuel des commandes générales podman-pod-clone(1)

NOM

podman-pod-clone - Crée une copie d'un pod existant

SYNTAXE

podman pod clone [options] pod nom

DESCRIPTION

podman pod clone crée une copie d'un pod, recréant la configuration identique pour le pod et pour tous ses conteneurs. Les utilisateurs peuvent modifier le nouveau nom du pod et sélectionner les détails du pod dans le conteneur d'infrastructure

OPTIONS

--blkio-weight=poids

Poids relatif de l'IO bloc. Le poids est une valeur comprise entre 10 et 1000.

Cette option n'est pas supportée sur les systèmes sans privilèges utilisant cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif par périphérique pour l'IO bloc.

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup du pod est créé. Si le chemin n'est pas absolu, il est considéré comme relatif au chemin cgroups du processus d'initialisation. Les cgroups sont créés s'ils n'existent pas déjà.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est 1024.

La proportion ne s'applique que lorsque des processus gourmands en CPU s'exécutent. Lorsque les tâches dans un conteneur sont inactives, les autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, l'un avec une part CPU de 1024 et les deux autres avec un réglage de part CPU de 512. Lorsque les processus dans les trois conteneurs tentent d'utiliser 100% du CPU, le premier conteneur reçoit 50% du temps CPU total. Si un quatrième conteneur est ajouté avec une part CPU de 1024, le premier conteneur ne reçoit que 33% du CPU. Les conteneurs restants reçoivent respectivement 16,5%, 16,5% et 33% du CPU.

Sur un système multi-cœur, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut utiliser 100% de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la répartition suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100% du CPU0
101 C1 1 100% du CPU1
102 C1 2 100% du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non privilégiés. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes sans privilèges utilisant cgroups V1.

--cpus

Définit un nombre de CPUs pour le pod qui remplace les limites CPU du pod original. S'il n'y en a pas de spécifié, les Nano CPUs du pod original sont utilisés.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par exemple, 0,1), d'une plage (par exemple, 0-3), ou de toute combinaison de ceux-ci (par exemple, 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non privilégiés. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes sans privilèges utilisant cgroups V1.

S'il n'y en a pas de spécifié, le cpuset du pod original est utilisé.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Seulement efficace sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1 alors les processus du conteneur n'utilisent la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non privilégiés. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes sans privilèges utilisant cgroups V1.

--destroy

Supprime le pod original que nous clonons une fois utilisé pour imiter la configuration.

--device=périphérique-hote[:périphérique-conteneur][:permissions]

Ajoute un périphérique hôte au pod. Le paramètre optionnel permissions peut être utilisé pour spécifier les permissions du périphérique en combinant r pour lire, w pour écrire, et m pour mknod(2).

Exemple : --device=/dev/sdc:/dev/xvdc:rwm.

Note : si périphérique-hote est un lien symbolique, il est résolu en premier. Le pod ne stocke que les numéros majeur et mineur du périphérique hôte.

Podman peut charger les modules noyau nécessaires à l'utilisation du périphérique spécifié. Les périphériques pour lesquels Podman charge des modules si nécessaire sont : /dev/fuse.

En mode sans privilèges, le nouveau périphérique est monté en bind depuis l'hôte dans le conteneur plutôt que Podman ne le crée dans l'espace du conteneur. Comme le montage en bind conserve son étiquette SELinux sur les systèmes SELinux, le conteneur peut rencontrer une erreur de permission lors de l'accès au périphérique monté. Modifiez les paramètres SELinux pour permettre aux conteneurs d'utiliser toutes les étiquettes de périphérique via la commande suivante :

$ sudo setsebool -P container_use_devices=true

Note : le pod implémente les périphériques en stockant la configuration initiale passée par l'utilisateur et en recréant le périphérique pour chaque conteneur ajouté au pod.

--device-read-bps=chemin:taux

Limite le taux de lecture (en octets par seconde) depuis un périphérique (par exemple, --device-read-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non privilégiés. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes sans privilèges utilisant cgroups V1.

--device-write-bps=chemin:taux

Limite le taux d'écriture (en octets par seconde) vers un périphérique (par exemple, --device-write-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non privilégiés. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas supportée sur les systèmes sans privilèges utilisant cgroups V1.

--gidmap=pod_gid:hôte_gid:montant

Carte GID pour l'espace utilisateur. L'utilisation de ce drapeau exécute tous les conteneurs du pod avec l'espace utilisateur activé. Il est en conflit avec les drapeaux --userns et --subgidname.

--gpus=ENTRÉE

Périphériques GPU à ajouter au conteneur ('all' pour passer tous les GPU) Actuellement, seuls les périphériques Nvidia sont supportés.

--help,

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

-h

Imprimer l'énoncé d'utilisation.

--hostname=nom

Définir le nom d'hôte du pod à l'intérieur de tous les conteneurs.

Le nom d'hôte donné est également ajouté au fichier /etc/hosts en utilisant l'adresse IP principale du conteneur (voir également l'option --add-host).

--infra-command=commande

La commande exécutée pour démarrer le conteneur infra. Par défaut : "/pause".

--infra-conmon-pidfile=fichier

Écrire le PID du processus conmon du conteneur infra dans un fichier. Comme conmon s'exécute dans un processus distinct de Podman, cela est nécessaire lors de l'utilisation de systemd pour gérer les conteneurs et les pods Podman.

--infra-name=nom

Le nom utilisé pour le conteneur infra du pod.

--label, -l=clé=valeur

Ajouter des métadonnées à un pod.

--label-file=fichier

Lire un fichier de libellés délimités par des sauts de ligne.

--memory, -m=nombre[unité]

Limite de mémoire. Une unité peut être b (octets), k (kibioctets), m (mebioctets) ou g (gibioctets).

Permet de contraindre la mémoire disponible pour un conteneur. Si l'hôte prend en charge la mémoire swap, le réglage mémoire -m peut être supérieur à la RAM physique. Si une limite de 0 est spécifiée (sans utiliser -m), la mémoire du conteneur n'est pas limitée. La limite réelle peut être arrondie à un multiple de la taille de page du système d'exploitation (la valeur est très grande, c'est des millions de trillions).

Cette option n'est pas prise en charge sur les systèmes sans privilèges V1 de cgroups.

--memory-swap=nombre[unité]

Une valeur de limite égale à la mémoire plus le swap. Une unité peut être b (octets), k (kibioctets), m (mebioctets) ou g (gibioctets).

Doit être utilisé avec le drapeau -m (--memory). La valeur de l'argument doit être supérieure à celle de
-m (--memory) Par défaut, elle est définie sur le double de la valeur de --memory.

Définissez nombre sur -1 pour activer le swap illimité.

Cette option n'est pas prise en charge sur les systèmes sans privilèges V1 de cgroups.

--name, -n

Définir un nom personnalisé pour le pod cloné. Le défaut s'il n'est pas spécifié est de la syntaxe : <NOM_ORIGINAL>-clone

--pid=pid

Définir le mode PID pour le pod. Par défaut, un espace de noms PID privé est créé pour le pod. Nécessite que l'espace de noms PID soit partagé via --share.

host: utiliser l'espace de noms PID de l'hôte pour le pod
ns: rejoindre l'espace de noms PID spécifié
private: créer un nouvel espace de noms pour le pod (par défaut)

--restart=politique

Politique de redémarrage à suivre lorsque les conteneurs se terminent. La politique de redémarrage ne prend pas effet si un conteneur est arrêté via les commandes podman kill ou podman stop.

Les valeurs valides pour politique sont :

  • no : Ne pas redémarrer les conteneurs à la sortie
  • never : Synonyme de no ; ne pas redémarrer les conteneurs à la sortie
  • on-failure[:max_retries] : Redémarrer les conteneurs lorsqu'ils se terminent avec un code de sortie non nul, en essayant indéfiniment ou jusqu'à ce que le nombre max_retries optionnel soit atteint
  • always : Redémarrer les conteneurs lorsqu'ils se terminent, quel que soit leur état, en essayant indéfiniment
  • unless-stopped : Identique à always

Podman fournit un fichier d'unité systemd, podman-restart.service, qui redémarre les conteneurs après un redémarrage du système.

Lors de l'exécution de conteneurs dans des services systemd, utilisez la fonctionnalité de redémarrage fournie par systemd. Autrement dit, n'utilisez pas cette option dans une unité de conteneur, mais définissez la directive systemd Restart= dans la section [Service]. Voir podman-systemd.unit(5) et systemd.service(5).

Politique de redémarrage par défaut pour tous les conteneurs d'un pod.

--security-opt=option

Options de sécurité

  • apparmor=unconfined : Désactiver le confinement apparmor pour le pod
  • apparmor=profil-alternatif : Définir le profil de confinement apparmor pour le pod
  • label=user:UTILISATEUR: Définir l'utilisateur de libellé pour les processus du pod
  • label=role:RÔLE: Définir le rôle de libellé pour les processus du pod
  • label=type:TYPE: Définir le type de processus de libellé pour les processus du pod
  • label=level:NIVEAU: Définir le niveau de libellé pour les processus du pod
  • label=filetype:TYPE: Définir le type de fichier de libellé pour les fichiers du pod
  • label=disable: Désactiver la séparation des libellés pour le pod

Note : L'étiquetage peut être désactivé pour tous les pods/conteneurs en réglant label=false dans le fichier containers.conf (/etc/containers/containers.conf ou $HOME/.config/containers/containers.conf).

  • label=nested: Permet les modifications SELinux à l'intérieur du conteneur. Les conteneurs sont autorisés à modifier les libellés SELinux sur les fichiers et les processus, tant que la politique SELinux le permet. Sans nested, les conteneurs voient SELinux comme désactivé, même s'il est activé sur l'hôte. Les conteneurs sont empêchés de définir des libellés.
  • mask=/chemin/1:/chemin/2: Les chemins à masquer séparés par un deux-points. Un chemin masqué ne peut pas être accédé à l'intérieur des conteneurs du pod.
  • no-new-privileges: Désactive l'acquisition de privilèges supplémentaires par les processus du conteneur via l'appel système execve(2) (par exemple, via les bits setuid ou setgid, ou via les capacités de fichier). Les programmes qui dépendent des bits setuid/setgid définis sur leur exécutable pour changer l'ID utilisateur ou l'ID de groupe ne peuvent plus le faire, et toutes les capacités de fichier ajoutées à l'exécutable (par exemple, via setcap) ne sont pas ajoutées à l'ensemble des capacités autorisées. Pour plus de détails, voir : https://docs.kernel.org/userspace-api/no_new_privs.html.
  • seccomp=unconfined: Désactive le confinement seccomp pour le pod.
  • seccomp=profile.json: Fichier JSON à utiliser comme filtre seccomp. Notez que l'annotation io.podman.annotations.seccomp est définie avec la valeur spécifiée comme indiqué dans podman inspect.
  • proc-opts=OPTIONS : Liste d'options séparées par des virgules à utiliser pour le montage /proc. Plus de détails sur les options de montage possibles sont spécifiés dans la page de manuel proc(5).
  • unmask=ALL ou /chemin/1:/chemin/2, ou chemins développés par le shell (/proc/*): Chemins à démasquer séparés par un deux-points. S'il est défini sur ALL, il démasque tous les chemins qui sont masqués ou rendus en lecture seule par défaut. Les chemins par défaut masqués sont /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, et /sys/fs/selinux, /sys/devices/virtual/powercap. Les chemins par défaut qui sont en lecture seule sont /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

Note : L'étiquetage peut être désactivé pour tous les conteneurs en définissant label=false dans le fichier containers.conf(5).

--shm-size=nombre[unité]

Taille de /dev/shm. Une unité peut être b (octets), k (kibioctets), m (mebioctets) ou g (gibioctets). Si l'unité est omise, le système utilise des octets. Si la taille est omise, la valeur par défaut est 64m. Lorsque la taille est 0, il n'y a aucune limite à la quantité de mémoire utilisée pour l'IPC par le pod. Cette option est incompatible avec --ipc=host.

--shm-size-systemd=nombre[unité]

Taille des montages tmpfs spécifiques à systemd tels que /run, /run/lock, /var/log/journal et /tmp. Une unité peut être b (octets), k (kibioctets), m (mebioctets) ou g (gibioctets). Si l'unité est omise, le système utilise des octets. Si la taille est omise, la valeur par défaut est 64m. Lorsque la taille est 0, l'utilisation est limitée à 50 % de la mémoire disponible de l'hôte.

--start

Lorsqu'il est défini sur vrai, ce drapeau démarre le pod nouvellement créé une fois le processus de clonage terminé. Tous les conteneurs du pod sont démarrés.

--subgidname=nom

Exécuter le conteneur dans un nouvel espace de noms utilisateur en utilisant la correspondance avec le nom dans le fichier /etc/subgid. Si vous exécutez sans privilèges, l'utilisateur doit avoir le droit d'utiliser la correspondance. Voir subgid(5). Ce drapeau est incompatible avec les options --userns et --gidmap.

--subuidname=nom

Exécuter le conteneur dans un nouvel espace de noms utilisateur en utilisant la correspondance avec le nom dans le fichier /etc/subuid. Si vous exécutez sans privilèges, l'utilisateur doit avoir le droit d'utiliser la correspondance. Voir subuid(5). Ce drapeau est incompatible avec les options --userns et --uidmap.

--sysctl=nom=valeur

Configurer les paramètres du noyau en espace de noms pour tous les conteneurs du pod.

Pour l'espace de noms IPC, les sysctls suivants sont autorisés :

  • kernel.msgmax
  • kernel.msgmnb
  • kernel.msgmni
  • kernel.sem
  • kernel.shmall
  • kernel.shmmax
  • kernel.shmmni
  • kernel.shm_rmid_forced
  • Sysctls commençant par fs.mqueue.*

Note : si l'espace de noms ipc n'est pas partagé au sein du pod, les sysctls ci-dessus ne sont pas autorisés.

Pour l'espace de noms réseau, seuls les sysctls commençant par net.* sont autorisés.

Note : si l'espace de noms réseau n'est pas partagé au sein du pod, les sysctls ci-dessus ne sont pas autorisés.

--uidmap=uid_conteneur:uid_hôte:quantité

Exécuter tous les conteneurs du pod dans un nouvel espace de noms utilisateur en utilisant la correspondance fournie. Cette option est incompatible avec les options --userns et --subuidname. Cette option fournit un moyen de mapper les UID hôtes aux UID des conteneurs. Elle peut être passée plusieurs fois pour mapper différentes plages.

--userns=mode

Définir le mode de l'espace de noms utilisateur

de pour tous les conteneurs d'un pod. Il s'agit par défaut de la variable d'environnement PODMAN_USERNS. Une valeur vide ("") signifie que les espaces de noms utilisateur sont désactivés.

Mappages des clés --userns= pour les utilisateurs sans root :

Clé Utilisateur Hôte Utilisateur Conteneur
"" $UID 0 (Compte utilisateur par défaut mappé sur l'utilisateur root dans le conteneur.)
host $UID 0 (Compte utilisateur par défaut mappé sur l'utilisateur root dans le conteneur.)
keep-id $UID $UID (Mappe le compte utilisateur sur le même UID dans le conteneur.)
auto $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)
nomap $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)

Les valeurs valides pour mode sont :

•
auto[:OPTIONS,...] : crée automatiquement un espace de noms. Il est possible de spécifier ces options pour auto :
  • gidmapping=CONTAINER_GID:HOST_GID:SIZE pour forcer la présence d'un mappage GID dans l'espace de noms utilisateur.
  • size=SIZE : pour spécifier une taille explicite pour l'espace de noms utilisateur automatique. Par exemple, --userns=auto:size=8192. Si size n'est pas spécifié, auto estime la taille de l'espace de noms utilisateur.
  • uidmapping=CONTAINER_UID:HOST_UID:SIZE pour forcer la présence d'un mappage UID dans l'espace de noms utilisateur.
  • host : s'exécute dans l'espace de noms utilisateur de l'appelant. Les processus s'exécutant dans le conteneur ont les mêmes privilèges sur l'hôte que tout autre processus lancé par l'utilisateur appelant (par défaut).
  • keep-id : crée un espace de noms utilisateur où l'UID:GID de l'utilisateur sans root actuel est mappé aux mêmes valeurs dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.
  • nomap : crée un espace de noms utilisateur où l'UID:GID de l'utilisateur sans root actuel ne sont pas mappés dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.

--uts=mode

Définit le mode de l'espace de noms UTS pour le pod. Les valeurs suivantes sont prises en charge :

  • host : utilise l'espace de noms UTS de l'hôte à l'intérieur du pod.
  • private : crée un nouvel espace de noms pour le pod (par défaut).
  • ns:[path] : exécute le pod dans l'espace de noms UTS existant donné.

--volume, -v=[[SOURCE-VOLUME|CHEMIN-HÔTE:]RÉPERTOIRE-CONTENEUR[:OPTIONS]]

Crée un montage bind. Si -v /CHEMIN-HÔTE:/RÉPERTOIRE-CONTENEUR est spécifié, Podman monte par bind /CHEMIN-HÔTE depuis l'hôte dans /RÉPERTOIRE-CONTENEUR dans le conteneur Podman. De même, -v SOURCE-VOLUME:/RÉPERTOIRE-CONTENEUR monte le volume nommé depuis l'hôte dans le conteneur. Si aucun volume nommé de ce type n'existe, Podman en crée un. Si aucune source n'est donnée, le volume est créé comme un volume anonyme avec un nom généré aléatoirement, et est supprimé lorsque le pod est supprimé via le flag --rm ou la commande podman rm --volumes.

(Notez que lors de l'utilisation du client distant, y compris sur les machines Mac et Windows (à l'exception de WSL2), les volumes sont montés depuis le serveur distant, pas nécessairement la machine cliente.)

Les OPTIONS sont une liste séparée par des virgules et peuvent être une ou plusieurs parmi :

  • rw|ro
  • z|Z
  • [O]
  • [U]
  • [no]copy
  • [no]dev
  • [no]exec
  • [no]suid
  • [r]bind
  • [r]shared|[r]slave|[r]private[r]unbindable [1] ⟨#Footnote1⟩
  • idmap[=options]

Le RÉPERTOIRE-CONTENEUR doit être un chemin absolu tel que /src/docs. Le volume est monté dans le conteneur à ce répertoire.

Si une source de volume est spécifiée, elle doit être un chemin sur l'hôte ou le nom d'un volume nommé. Les chemins hôtes peuvent être absolus ou relatifs ; les chemins relatifs sont résolus par rapport au répertoire dans lequel Podman est exécuté. Si la source n'existe pas, Podman renvoie une erreur. Les utilisateurs doivent pré-créer les fichiers ou répertoires sources.

Toute source qui ne commence pas par un . ou un / est traitée comme le nom d'un volume nommé. Si un volume portant ce nom n'existe pas, il est créé. Les volumes créés avec des noms ne sont pas anonymes et ne sont pas supprimés par l'option --rm et la commande podman rm --volumes.

Spécifiez plusieurs options -v pour monter un ou plusieurs volumes dans un pod.

Montages de volumes protégés en écriture

Ajoutez l'option :ro ou :rw pour monter un volume en lecture seule ou en lecture-écriture, respectivement. Par défaut, les volumes sont montés en lecture-écriture. Voir les exemples.

Changement de propriétaire des montages de volumes

Lorsqu'un volume nommé est monté pour la première fois sur un conteneur, Podman ajuste automatiquement la propriété du point de montage du volume lors de l'initialisation du conteneur. Cette opération de changement de propriétaire se produit dans les conditions suivantes :

  • Le volume n'a pas encore été utilisé (a NeedsChown défini sur true)
  • Le volume est vide ou n'a pas encore été copié
  • Le volume n'est pas géré par un pilote de volume externe
  • Le pilote de volume n'est pas "image"

Pour les volumes avec des montages idmappés (utilisant l'option idmap), le changement de propriété prend en compte les mappages d'espaces de noms utilisateur du conteneur, mais le volume idmappé conserve un mappage UID/GID correct. Pour les volumes sans idmapping, le point de montage est re-propriété pour correspondre à l'utilisateur et au groupe du processus du conteneur, mappé à l'espace de noms utilisateur de l'hôte si le remappage de l'espace de noms utilisateur est activé.

Si un pod est créé dans un nouvel espace de noms utilisateur, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte.

Le suffixe :U indique à Podman d'utiliser l'UID et le GID hôtes corrects basés sur l'UID et le GID dans le pod, pour changer récursivement le propriétaire et le groupe du volume source. Le re-propriété parcourt le système de fichiers sous le volume et modifie l'UID/GID sur chaque fichier. Si le volume a des milliers d'inodes, ce processus prend beaucoup de temps, retardant le démarrage du pod.

Attention, utilisez avec prudence car cela modifie le système de fichiers hôte.

Labellisation des montages de volumes

Les systèmes de labellisation comme SELinux nécessitent que des étiquettes appropriées soient placées sur le contenu du volume monté dans un pod. Sans étiquette, le système de sécurité pourrait empêcher les processus s'exécutant dans le pod d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par le système d'exploitation.

Pour modifier une étiquette dans le contexte du pod, ajoutez l'un des deux suffixes :z ou :Z au montage du volume. Ces suffixes indiquent à Podman de re-labelliser les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux pods ou plus partagent le contenu du volume. En conséquence, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagé permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman d'étiqueter le contenu avec une étiquette privée non partagée. Seul le pod actuel peut utiliser un volume privé.

Remarque : tous les conteneurs d'un pod partagent la même étiquette SELinux. Cela signifie que tous les conteneurs de ce pod peuvent lire/écrire les volumes partagés dans le conteneur créé avec :Z sur l'un des conteneurs. La re-labellisation parcourt le système de fichiers sous le volume et modifie l'étiquette sur chaque fichier ; si le volume a des milliers d'inodes, ce processus prend beaucoup de temps, retardant le démarrage du pod. Si le volume a été précédemment re-labellisé avec l'option z, Podman est optimisé pour ne pas re-labelliser une deuxième fois. Si des fichiers sont déplacés dans le volume, les étiquettes peuvent être modifiées manuellement avec la commande chcon -Rt container_file_t PATH.

Remarque : ne re-labellisez pas les fichiers et répertoires système. La re-labellisation du contenu système peut entraîner l'échec d'autres services confinés sur la machine. Pour ce type de conteneurs, nous recommandons de désactiver la séparation SELinux. L'option --security-opt label=disable désactive la séparation SELinux pour le pod. Par exemple, si un utilisateur souhaitait monter par volume tout son répertoire personnel dans un pod, il doit désactiver la séparation SELinux.

$ podman pod clone --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

Montages de volumes superposés

Le flag :O indique à Podman de monter le répertoire de l'hôte comme stockage temporaire en utilisant le système de fichiers overlay. Les processus du pod peuvent modifier le contenu du point de montage, qui est stocké dans le stockage du conteneur dans un répertoire séparé. En termes d'overlay, le répertoire source est le inférieur, et le répertoire de stockage du conteneur est le supérieur. Les modifications apportées au point de montage sont détruites lorsque le pod a terminé son exécution, de manière similaire au démontage d'un point de montage tmpfs.

Pour les utilisateurs avancés, l'option overlay prend également en charge des upperdir et workdir personnalisés non volatils pour le montage overlay. Les upperdir et workdir personnalisés peuvent être entièrement gérés par les utilisateurs eux-mêmes, et Podman ne les supprime pas à la fin du cycle de vie. Exemple : :O,upperdir=/some/upper,workdir=/some/work

Les exécutions ultérieures du conteneur voient le contenu du répertoire source d'origine, toutes les modifications des exécutions précédentes de pod n'existent plus.

Un cas d'utilisation du montage overlay est le partage du cache de paquets de l'hôte dans le conteneur pour accélérer les constructions.

Remarque : le flag O est en conflit avec les autres options listées ci-dessus.

Le contenu monté dans le conteneur est étiqueté avec l'étiquette privée. Sur les systèmes SELinux, les étiquettes du répertoire source doivent être lisibles par l'étiquette du conteneur infra du pod. Habituellement, les conteneurs peuvent lire/exécuter container_share_t et peuvent lire/écrire container_file_t. Si les étiquettes sur un volume source ne peuvent pas être modifiées, la séparation des conteneurs SELinux doit être désactivée pour que le pod ou le conteneur infra fonctionne.

Ne modifiez pas le répertoire source monté dans le pod avec un montage overlay, cela pourrait entraîner des échecs inattendus. Modifiez le répertoire uniquement après la fin de l'exécution du conteneur.

Propagation des montages

Par défaut, les volumes montés par bind sont privés. Cela signifie que tous les montages effectués dans le pod ne sont pas visibles sur l'hôte et vice versa. On peut changer ce comportement en spécifiant une propriété de propagation de montage de volume. Lorsqu'un volume est partagé, les montages effectués sous ce volume dans le pod sont visibles sur l'hôte et vice versa. NAME

podman-pod-clone - Clone a pod to a new pod

SYNOPSIS

podman pod clone [-d,--destroy] [--name=-NAME] [--network=-NETWORK] [--infra] [--quiet | -q] [--cpus=-CPUS] [--cpu-shares=-CPU_SHARES] [--memory=-MEMORY] [--memory-swap=-MEMORY_SWAP] POD [POD...]

DESCRIPTION

The podman pod clone command creates a clone of an existing pod. The clone is an exact copy of the original pod's configuration, including all containers and their configurations, volumes, and other pod settings. The cloned pod will be a new, independent entity. Changes made to the original pod after cloning will not affect the cloned pod, and vice versa.

The podman pod clone command supports cloning multiple pods at once.

When cloning pods, the original pod's --volumes-from and --mount options are inherited by the cloned pod. This ensures that volumes are correctly shared or mounted in the new pod.

By default, the cloned pod will have the same name as the original pod, with the suffix -clone appended. You can specify a new name for the cloned pod using the --name option.

The --destroy option can be used to remove the original pod after it has been successfully cloned. This is useful for creating a snapshot or backup of a pod.

The --network option allows you to specify the network for the cloned pod. You can use a bridge, host, or any valid network name or ID.

The --infra option, when used, will clone the infra container for the pod. The infra container is the first container started in the pod and is responsible for setting up the pod's network namespace.

The --quiet or -q option suppresses the output of the cloned pod's ID.

The --cpus, --cpu-shares, --memory, and --memory-swap options allow you to modify the resource limits for the cloned pod. These options override the original pod's resource limits.

If the original pod contains volumes that are bind mounts, the podman pod clone command will create new bind mounts for the cloned pod. The cloned pod's bind mounts will point to the same host directories as the original pod's bind mounts. This means that changes made to the data in these directories will be reflected in both the original and cloned pods.

If the original pod contains named volumes, the podman pod clone command will create new named volumes for the cloned pod. These new named volumes will be empty, and will not contain any data from the original pod's named volumes. To copy data from the original pod's named volumes to the cloned pod's named volumes, you must manually copy the data after cloning.

Mount propagation options control how mounts are shared between the host and containers, or between containers. Podman supports the following propagation options:

bind
Mounts the source directory into the container. The container can access the source directory, but the host cannot access the container's mount. This is the default option.
rbind
Recursively mounts the source directory and all of its submounts into the container. This option is useful when the source directory contains nested mount points that need to be accessed from within the container.
copy-up
Copies the contents of the source directory into a new volume. The volume is then mounted into the container. This option is useful when you want to ensure that the container has its own copy of the data, and that changes made within the container do not affect the host system. This option is ignored on bind mounts.
volume
Mounts a named volume into the container. Named volumes are managed by Podman and are stored in a central location on the host system. This option is useful for persistent storage of data.

Propagation flags can be specified only for bind mounted volumes and not for internal volumes or named volumes. For mount propagation to work, the source mount point must have the correct propagation properties. For shared volumes, the source mount point must be shared. And for slave volumes, the source mount point must be either shared or slave. [1]

The copy-up option tells Podman to copy content from the underlying destination directory onto newly created internal volumes. The copy only happens on the initial creation of the volume. Content is not copied up when the volume is subsequently used on different containers. The copy-up option is ignored on bind mounts and has no effect.

Mounting the volume with a nosuid option means that SUID executables on the volume cannot be used by applications to change their privilege. By default, volumes are mounted with nosuid.

Mounting the volume with the noexec option means that no executables on the volume can be executed within the pod.

Mounting the volume with the nodev option means that no devices on the volume can be used by processes within the pod. By default, volumes are mounted with nodev.

If the HOST-DIR is a mount point, then dev, suid, and exec options are ignored by the kernel.

Use df HOST-DIR to figure out the source mount, then use findmnt -o TARGET,PROPAGATION source-mount-dir to figure out propagation properties of source mount. If findmnt(1) utility is not available, then one can look at the mount entry for the source mount point in /proc/self/mountinfo. Look at the "optional fields" and see if any propagation properties are specified. In there, shared:N means the mount is shared, master:N means mount is slave, and if nothing is there, the mount is private. [1]

To change propagation properties of a mount point, use mount(8) command. For example, if one wants to bind mount source directory /foo, one can do mount --bind /foo /foo and mount --make-private --make-shared /foo. This converts /foo into a shared mount point. Alternatively, one can directly change propagation properties of source mount. Say / is source mount for /foo, then use mount --make-shared / to convert / into a shared mount.

Note: if the user only has access rights via a group, accessing the volume from inside a rootless pod fails.

Idmapped mount

If idmap is specified, create an idmapped mount to the target user namespace in the container. The idmap option supports a custom mapping that can be different than the user namespace used by the container. The mapping can be specified after the idmap option like: idmap=uids=0-1-10#10-11-10;gids=0-100-10. For each triplet, the first value is the start of the backing file system IDs that are mapped to the second value on the host. The length of this mapping is given in the third value. Multiple ranges are separated with #.

--volumes-from=CONTAINER[:OPTIONS]

Mount volumes from the specified container(s). Used to share volumes between containers and pods. The options is a comma-separated list with the following available elements:

  • rw|ro
  • z

Mounts already mounted volumes from a source container onto another pod. CONTAINER may be a name or ID. To share a volume, use the --volumes-from option when running the target container. Volumes can be shared even if the source container is not running.

By default, Podman mounts the volumes in the same mode (read-write or read-only) as it is mounted in the source container. This can be changed by adding a ro or rw option.

Labeling systems like SELinux require that proper labels are placed on volume content mounted into a pod. Without a label, the security system might prevent the processes running inside the container from using the content. By default, Podman does not change the labels set by the OS.

To change a label in the pod context, add z to the volume mount. This suffix tells Podman to relabel file objects on the shared volumes. The z option tells Podman that two entities share the volume content. As a result, Podman labels the content with a shared content label. Shared volume labels allow all containers to read/write content.

If the location of the volume from the source container overlaps with data residing on a target pod, then the volume hides that data on the target.
