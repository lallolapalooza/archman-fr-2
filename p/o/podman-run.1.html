NOM

podman-run - Exécuter une commande dans un nouveau conteneur

SYNOPIS

podman run [options] image [commande [arg ...]]

podman container run [options] image [commande [arg ...]]

DESCRIPTION

Exécute un processus dans un nouveau conteneur. podman run démarre un processus avec son propre système de fichiers, son propre réseau et sa propre arborescence de processus isolée. L'image qui démarre le processus peut définir des valeurs par défaut relatives au processus qui sera exécuté dans le conteneur, au réseau à exposer, et plus encore, mais podman run donne le contrôle final à l'opérateur ou à l'administrateur qui démarre le conteneur à partir de l'image. Pour cette raison, podman run possède plus d'options que toute autre commande Podman.

Si l'image n'est pas déjà chargée, podman run téléchargera l'image, ainsi que toutes ses dépendances, depuis le dépôt de la même manière que l'exécution de podman pull image, avant de démarrer le conteneur à partir de cette image.

Plusieurs fichiers seront automatiquement créés dans le conteneur. Cela inclut /etc/hosts, /etc/hostname et /etc/resolv.conf pour gérer le réseau. Ceux-ci seront basés sur la version de ces fichiers de l'hôte, bien qu'ils puissent être personnalisés avec des options (par exemple, --dns peut remplacer les serveurs DNS de l'hôte dans le fichier resolv.conf créé). De plus, un fichier d'environnement de conteneur est créé dans chaque conteneur pour indiquer aux programmes qu'ils s'exécutent dans un conteneur. Ce fichier est situé à /run/.containerenv (ou /var/run/.containerenv pour les conteneurs FreeBSD). Lorsque l'option --privileged est utilisée, le fichier .containerenv contient des paires nom/valeur indiquant la version du moteur de conteneurisation, si le moteur fonctionne en mode sans privilèges (rootless), le nom et l'ID du conteneur, ainsi que le nom et l'ID de l'image sur lesquels le conteneur est basé. Note : /run/.containerenv ne sera pas créé lorsqu'un volume est monté sur /run.

Lors de l'exécution à partir d'un espace de noms réseau défini par l'utilisateur, le fichier /etc/netns/NSNAME/resolv.conf sera utilisé s'il existe, sinon /etc/resolv.conf sera utilisé.

Les paramètres par défaut sont définis dans containers.conf. La plupart des paramètres pour les connexions distantes utilisent le fichier containers.conf du serveur, sauf indication contraire dans les pages de manuel.

IMAGE

L'image est spécifiée à l'aide du format transport:chemin. Si aucun transport n'est spécifié, le transport docker (registre de conteneurs) est utilisé par défaut. Pour les clients Podman distants, y compris les machines Mac et Windows (hors WSL2), docker est le seul transport autorisé.

dir:chemin
Un répertoire local existant chemin stockant le manifeste, les archives de couches et les signatures sous forme de fichiers individuels. Il s'agit d'un format non standardisé, principalement utile pour le débogage ou l'inspection non invasive de conteneurs.

$ podman save --format docker-dir fedora -o /tmp/fedora
$ podman run dir:/tmp/fedora echo hello

docker://référence-docker (Par défaut)
Une référence d'image stockée dans un registre d'images de conteneurs distant. Exemple : "quay.io/podman/stable:latest". La référence peut inclure un chemin vers un registre spécifique ; sinon, les registres listés dans registries.conf sont interrogés pour trouver une image correspondante. Par défaut, les identifiants de connexion de podman login (stockés dans $XDG_RUNTIME_DIR/containers/auth.json par défaut) sont utilisés pour l'authentification ; sinon, le système se rabat sur les identifiants dans $HOME/.docker/config.json.

$ podman run registry.fedoraproject.org/fedora:latest echo hello

docker-archive:chemin[:référence-docker] Une image stockée dans un fichier au format docker save. référence-docker est uniquement utilisée lors de la création d'un tel fichier, et elle ne doit pas contenir de digest.

$ podman save --format docker-archive fedora -o /tmp/fedora
$ podman run docker-archive:/tmp/fedora echo hello

Note : Sur les clients distants, y compris les machines Mac et Windows (hors WSL2), ce transport n'est pas supporté.

docker-daemon:référence-docker
Une image au format référence-docker stockée dans le stockage interne du démon Docker. La référence-docker peut également être un ID d'image (docker-daemon:algo:digest).

$ sudo docker pull fedora
$ sudo podman run docker-daemon:docker.io/library/fedora echo hello

Note : Sur les clients distants, y compris les machines Mac et Windows (hors WSL2), ce transport n'est pas supporté.

oci-archive:chemin:étiquette
Une image dans un répertoire conforme à la spécification "Open Container Image Layout Specification" situé au chemin spécifié et identifié par une étiquette.

$ podman save --format oci-archive fedora -o /tmp/fedora
$ podman run oci-archive:/tmp/fedora echo hello

Note : Sur les clients distants, y compris les machines Mac et Windows (hors WSL2), ce transport n'est pas supporté.

OPTIONS

--add-host=nomhôte[;nomhôte[;...]]:ip

Ajoute une correspondance personnalisée nom d'hôte vers IP au fichier /etc/hosts du conteneur.

L'option prend un ou plusieurs noms d'hôtes séparés par des points-virgules à mapper vers une seule adresse IPv4 ou IPv6, séparés par un deux-points. Elle peut également être utilisée pour remplacer les adresses IP des noms d'hôtes que Podman ajoute par défaut à /etc/hosts (voir également les options --name et --hostname). Cette option peut être spécifiée plusieurs fois pour ajouter des correspondances supplémentaires à /etc/hosts. Elle est en conflit avec l'option --no-hosts et avec no_hosts=true dans containers.conf.

Au lieu d'une adresse IP, le drapeau spécial host-gateway peut être donné. Celui-ci se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Podman puisse déterminer automatiquement l'adresse host-gateway, ce qui provoquerait une erreur de Podman. Vous pouvez remplacer cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Podman pour ajouter automatiquement les noms d'hôtes host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez l'éviter en donnant l'option --no-hosts ou en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Podman ne parvient pas à déterminer l'adresse IP automatiquement, Podman omettra silencieusement l'ajout de ces noms d'hôtes internes à /etc/hosts. Si Podman s'exécute dans une machine virtuelle à l'aide de podman machine (cela inclut les hôtes Mac et Windows), Podman omettra silencieusement l'ajout des noms d'hôtes internes à /etc/hosts, sauf si une adresse IP a été configurée manuellement ; les noms d'hôtes internes sont résolus par le résolveur DNS de gvproxy à la place.

Podman utilisera le fichier /etc/hosts de l'hôte comme base par défaut, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré à l'aide de la configuration base_hosts_file dans containers.conf.

--annotation=clé=valeur

Ajoute une annotation au conteneur. Cette option peut être définie plusieurs fois.

--arch=ARCH

Remplace l'architecture de l'image à télécharger, par défaut celle de l'hôte. Par exemple, arm. Sauf si elle est remplacée, les recherches ultérieures de la même image dans le stockage local correspondent à cette architecture, quelle que soit l'hôte.

--attach, -a=stdin | stdout | stderr

Se connecte à STDIN, STDOUT ou STDERR.

En mode interactif (par défaut lorsque -d n'est pas spécifié), podman run peut démarrer le processus dans le conteneur et attacher la console à l'entrée, à la sortie et à l'erreur standard du processus. Il peut même prétendre être un TTY (ce que la plupart des exécutables en ligne de commande attendent) et transmettre les signaux. L'option -a peut être définie pour chacun des flux stdin, stdout et stderr.

Chemin du fichier d'authentification. Par défaut, il s'agit de ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation n'est pas

--blkio-weight=poids

Poids relatif du système d'entrée/sortie de blocs. Le poids est une valeur comprise entre 10 et 1000.

Cette option n'est pas prise en charge sur les systèmes sans racine cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif du système d'entrée/sortie de blocs par périphérique.

--cap-add=capability

Ajouter des capacités Linux.

L'octroi de capacités supplémentaires augmente les privilèges des processus s'exécutant à l'intérieur du conteneur et potentiellement lui permet de s'échapper de son confinement. Des capacités telles que CAP_SYS_ADMIN, CAP_SYS_PTRACE, CAP_MKNOD et CAP_SYS_MODULE sont particulièrement dangereuses lorsqu'elles ne sont pas utilisées dans un espace de noms d'utilisateur. Veuillez vous référer à user_namespaces(7) pour une explication plus détaillée de l'interaction entre les espaces de noms d'utilisateurs et les capacités.

Avant d'ajouter une capacité, examinez ses implications en matière de sécurité et assurez-vous qu'elle est réellement nécessaire pour la fonctionnalité du conteneur. Voir capabilities(7) pour plus d'informations.

--cap-drop=capability

Supprimer des capacités Linux.

--cert-dir=chemin

Utiliser les certificats dans chemin (*.crt, *.cert, *.key) pour se connecter au registre. (Par défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (hors WSL2))

--cgroup-conf=CLÉ=VALEUR

Lorsqu'il s'exécute sur cgroup v2, spécifier le fichier cgroup dans lequel écrire et sa valeur. Par exemple, --cgroup-conf=memory.high=1073741824 définit la limite memory.high à 1 Go.

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup pour le conteneur est créé. Si le chemin n'est pas absolu, le chemin est considéré comme relatif au chemin des cgroups du processus d'initialisation. Les cgroups sont créés s'ils n'existent pas déjà.

--cgroupns=mode

Définir le mode de l'espace de noms cgroup pour le conteneur.

  • host : utiliser l'espace de noms cgroup de l'hôte à l'intérieur du conteneur.
  • container:id : rejoindre l'espace de noms du conteneur spécifié.
  • private : créer un nouvel espace de noms cgroup.
  • ns:chemin : rejoindre l'espace de noms au chemin spécifié.

Si l'hôte utilise cgroups v1, la valeur par défaut est définie sur host. Sur cgroups v2, la valeur par défaut est private.

--cgroups=comment

Détermine si le conteneur crée des cgroups.

La valeur par défaut est enabled.

L'option enabled crée un nouveau cgroup sous le cgroup-parent. L'option disabled force le conteneur à ne pas créer de cgroups, et entre donc en conflit avec les options cgroup (--cgroupns et --cgroup-parent). L'option no-conmon désactive un nouveau cgroup uniquement pour le processus conmon. L'option split divise le cgroup actuel en deux sous-cgroups : un pour conmon et un pour la charge utile du conteneur. Il n'est pas possible de définir --cgroup-parent avec split.

--chrootdirs=chemin

Chemin vers un répertoire à l'intérieur du conteneur qui est traité comme un répertoire chroot. Tout fichier géré par Podman (par exemple, /etc/resolv.conf, /etc/hosts, /etc/hostname) qui est monté dans le répertoire racine est également monté à cet emplacement. Les répertoires multiples sont séparés par une virgule.

--cidfile=fichier

Écrit l'ID du conteneur dans fichier. Le fichier est supprimé en même temps que le conteneur, sauf lors de l'utilisation de podman --remote run sur des conteneurs détachés.

--conmon-pidfile=fichier

Écrit le pid du processus conmon dans un fichier. Comme conmon s'exécute dans un processus séparé de Podman, cela est nécessaire lors de l'utilisation de systemd pour redémarrer les conteneurs Podman. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (hors WSL2))

--cpu-period=limite

Définit la période CPU pour le planificateur Completely Fair Scheduler (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié pour s'exécuter avant la fin de la période actuelle. La valeur par défaut est de 100000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans racine cgroups V1.

--cpu-quota=limite

Limite le quota CPU du planificateur Completely Fair Scheduler (CFS).

Limite l'utilisation du CPU par le conteneur. Par défaut, les conteneurs s'exécutent avec la pleine ressource CPU. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser cette quantité de temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans racine cgroups V1.

--cpu-rt-period=microsecondes

Limite la période temps réel CPU en microsecondes.

Limite l'utilisation du CPU en temps réel par le conteneur. Cette option indique au noyau de restreindre l'utilisation du CPU en temps réel du conteneur à la période spécifiée.

Cette option n'est prise en charge que sur les systèmes avec privilèges cgroups V1.

--cpu-rt-runtime=microsecondes

Limite le temps d'exécution temps réel CPU en microsecondes.

Limite l'utilisation du CPU en temps réel des conteneurs. Cette option indique au noyau de limiter la quantité de temps qu'une tâche en temps réel peut consommer pendant une période CPU donnée. Ex : Une période de 1 000 000 µs et un temps d'exécution de 950 000 µs signifie que ce conteneur peut consommer 95 % du CPU disponible et laisser les 5 % restants aux tâches de priorité normale.

La somme de tous les temps d'exécution entre les conteneurs ne peut pas dépasser la quantité allouée au cgroup parent.

Cette option n'est prise en charge que sur les systèmes avec privilèges cgroups V1.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs obtiennent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est de 1024.

La proportion ne s'applique que lorsque des processus intensifs en CPU s'exécutent. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, l'un a une valeur cpu-share de 1024 et les deux autres ont un réglage cpu-share de 512. Lorsque les processus dans les trois conteneurs tentent d'utiliser 100 % du CPU, le premier conteneur reçoit 50 % du temps CPU total. Si un quatrième conteneur est ajouté avec un cpu-share de 1024, le premier conteneur ne reçoit que 33 % du CPU. Les conteneurs restants reçoivent respectivement 16,5 %, 16,5 % et 33 % du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100 % du temps CPU, il peut utiliser 100 % de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la division suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100 % du CPU0
101 C1 1 100 % du CPU1
102 C1 2 100 % du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans racine cgroups V1.

--cpus=nombre

Nombre de CPUs. La valeur par défaut est 0.0, ce qui signifie aucune limite. C'est un raccourci pour --cpu-period et --cpu-quota, par conséquent l'option ne peut pas être spécifiée avec --cpu-period ou --cpu-quota.

Sur certains systèmes, la modification des limites CPU peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans racine cgroups V1.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par exemple, 0,1), de plage (par exemple, 0-3), ou de toute combinaison de ceux-ci (par exemple, 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Uniquement efficace sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1, puis les processus du conteneur n'utiliseront la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--creds=[nomutilisateur[:motdepasse]]

Le [nomutilisateur[:motdepasse]] à utiliser pour s'authentifier auprès du registre, si nécessaire. Si une ou deux valeurs ne sont pas fournies, une invite de commande apparaît et la valeur peut être saisie. Le mot de passe est saisi sans écho.

Notez que les identifiants spécifiés sont uniquement utilisés pour s'authentifier auprès des registres cibles. Ils ne sont pas utilisés pour les miroirs ou lorsque le registre est réécrit (voir containers-registries.conf(5)); pour s'authentifier auprès de ceux-ci, envisagez d'utiliser un fichier containers-auth.json(5).

--decryption-key=clé[:phraseclée]

La [clé[:phraseclée]] à utiliser pour le déchiffrement des images. La clé peut pointer vers des clés et/ou des certificats. Le déchiffrement est tenté avec toutes les clés. Si la clé est protégée par une phrase secrète, celle-ci doit être fournie dans l'argument et omise sinon.

--detach, -d

Mode détaché : exécute le conteneur en arrière-plan et affiche le nouveau conteneur ID. La valeur par défaut est false.

À tout moment, exécutez podman ps dans l'autre terminal pour afficher une liste des conteneurs en cours d'exécution. Rattachez-vous à un conteneur détaché avec la commande podman attach.

Lorsqu'il est attaché via le mode tty, détachez-vous du conteneur (et laissez-le en cours d'exécution) en utilisant une séquence de touches configurable. La séquence par défaut est ctrl-p,ctrl-q. Spécifiez la séquence de touches à l'aide de l'option --detach-keys, ou configurez-la dans le fichier containers.conf: voir containers.conf(5) pour plus d'informations.

--detach-keys=séquence

Spécifiez la séquence de touches pour détacher un conteneur. Le format est un seul caractère [a-Z] ou un ou plusieurs caractères ctrl-<valeur> où <valeur> est l'un des éléments suivants : a-z, @, ^, [, , ou _. Spécifier "" désactive cette fonctionnalité. La valeur par défaut est ctrl-p,ctrl-q.

Cette option peut également être définie dans le fichier containers.conf(5).

--device=périphérique-hôte[:périphérique-conteneur][:permissions]

Ajoute un périphérique hôte au conteneur. Le paramètre facultatif permissions peut être utilisé pour spécifier les autorisations du périphérique en combinant r pour lecture, w pour écriture et m pour mknod(2).

Exemple : --device=/dev/sdc:/dev/xvdc:rwm.

Remarque : si périphérique-hôte est un lien symbolique, il est d'abord résolu. Le conteneur ne stocke que les numéros majeur et mineur du périphérique hôte.

Podman peut charger les modules de noyau requis pour utiliser le périphérique spécifié. Les périphériques pour lesquels Podman charge les modules si nécessaire sont : /dev/fuse.

En mode sans root, le nouveau périphérique est monté par liaison dans le conteneur depuis l'hôte au lieu que Podman ne le crée dans l'espace du conteneur. Comme le montage par liaison conserve son libellé SELinux sur les systèmes SELinux, le conteneur peut obtenir une erreur de permission lors de l'accès au périphérique monté. Modifiez les paramètres SELinux pour autoriser les conteneurs à utiliser tous les libellés de périphérique via la commande suivante :

$ sudo setsebool -P container_use_devices=true

Remarque : si l'utilisateur n'a accès que via un groupe, l'accès au périphérique depuis l'intérieur d'un conteneur sans root échoue. Utilisez l'option --group-add keep-groups pour transmettre l'accès aux groupes supplémentaires de l'utilisateur au conteneur.

--device-cgroup-rule="type majeur:mineur mode"

Ajoute une règle à la liste des périphériques autorisés du cgroup. La règle doit être au format spécifié dans la documentation du noyau Linux admin-guide/cgroup-v1/devices : - type : a (tous), c (caractère) ou b (bloc) ; - majeur et mineur : soit un nombre, soit * pour tous ; - mode : une composition de r (lecture), w (écriture) et m (mknod(2)).

--device-read-bps=chemin:débit

Limite le débit de lecture (en octets par seconde) à partir d'un périphérique (par exemple, --device-read-bps=/dev/sda:1mo).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--device-read-iops=chemin:débit

Limite le débit de lecture (en opérations d'E/S par seconde) à partir d'un périphérique (par exemple, --device-read-iops=/dev/sda:1000).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root utilisant cgroups V1.

--device-write-bps=chemin:débit

Limite le débit d'écriture (en octets par seconde) vers un périphérique (par exemple, --device-write-bps=/dev/sda:1mo).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

--mount=type=TYPE,TYPE-SPECIFIC-OPTION[,...]

Attacher un montage de système de fichiers au conteneur.

Les TYPEs de montage actuellement pris en charge sont artifact, bind, devpts, glob, image, ramfs, tmpfs et volume.

Options communes

to all mount types:

  • src, source: mount source spec for bind, glob, and volume. Mandatory for artifact, bind, glob, image and volume.
  • dst, dest, destination, target: mount destination spec.

When source globs are specified without the destination directory, the files and directories are mounted with their complete path within the container. When the destination is specified, the files and directories matching the glob on the base file name on the destination directory are mounted. The option type=glob,src=/foo*,destination=/tmp/bar tells container engines to mount host files matching /foo* to the /tmp/bar/ directory in the container.

Options specific to type=artifact:

  • digest: If the artifact source contains multiple blobs a digest can be specified to only mount the one specific blob with the digest.
  • title: If the artifact source contains multiple blobs a title can be set which is compared against org.opencontainers.image.title annotation.
  • name: This can be used to overwrite the filename we use inside the container for mounting. On a single blob artifact the name is used as is if dst is a directory and otherwise ignored. With a multi blob artifact the name will be used with an index suffix <name>-x where x is the layer index in the artifact starting with 0.

The src argument contains the name of the artifact, which must already exist locally. The dst argument contains the target path, if the path in the container is a directory the blob title (org.opencontainers.image.title annotation) will be used as filename and joined to the path. If the annotation does not exist the digest will be used as filename instead. This results in all blobs of the artifact mounted into the container at the given path.

However, if the dst path is an existing file in the container, then the blob will be mounted directly on it. This only works when the artifact contains a single blob or when either digest or title are specified.

If the dst path does not already exist in the container then if the artifact contains a single blob it behaves like existing file case and mounts directly to that path. If the artifact has more than one blob it works like the existing directory case and mounts each blob as file within the dst path.

Options specific to type=volume:

  • ro, readonly: true or false (default if unspecified: false).
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.
  • subpath: Mount only a specific subpath within the volume, instead of the whole volume.
  • idmap: If specified, create an idmapped mount to the target user namespace in the container. The idmap option is only supported by Podman in rootful mode. The Linux kernel does not allow the use of idmapped file systems for unprivileged users. The idmap option supports a custom mapping that can be different than the user namespace used by the container. The mapping can be specified after the idmap option like: idmap=uids=0-1-10#10-11-10;gids=0-100-10. For each triplet, the first value is the start of the backing file system IDs that are mapped to the second value on the host. The length of this mapping is given in the third value. Multiple ranges are separated with #. If the specified mapping is prepended with a '@', then the mapping is considered relative to the container user namespace. The host ID for the mapping is changed to account for the relative position of the container user in the container user namespace.

Options specific to type=image:

  • rw, readwrite: true or false (default if unspecified: false).
  • subpath: Mount only a specific path within the image, instead of the whole image.

Options specific to bind and glob:

  • ro, readonly: true or false (default if unspecified: false).
  • bind-propagation: shared, slave, private, unbindable, rshared, rslave, runbindable, or rprivate (default).[1] ⟨#Footnote1⟩ See also mount(2).
  • bind-nonrecursive: do not set up a recursive bind mount. By default it is recursive.
  • relabel: shared, private.
  • idmap: true or false (default if unspecified: false). If true, create an idmapped mount to the target user namespace in the container. The idmap option is only supported by Podman in rootful mode.
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.
  • no-dereference: do not dereference symlinks but copy the link source into the mount destination.

Options specific to type=tmpfs and ramfs:

  • ro, readonly: true or false (default if unspecified: false).
  • tmpfs-size: Size of the tmpfs/ramfs mount, in bytes. Unlimited by default in Linux.
  • tmpfs-mode: Octal file mode of the tmpfs/ramfs (e.g. 700 or 0700.).
  • tmpcopyup: Enable copyup from the image directory at the same location to the tmpfs/ramfs. Used by default.
  • noatime: Disable updating file access times when the file is read.
  • notmpcopyup: Disable copying files from the image to the tmpfs/ramfs.
  • U, chown: true or false (default if unspecified: false). Recursively change the owner and group of the source volume based on the UID and GID of the container.

Options specific to type=devpts:

  • uid: numeric UID of the file owner (default: 0).
  • gid: numeric GID of the file owner (default: 0).
  • mode: octal permission mask for the file (default: 600).
  • max: maximum number of PTYs (default: 1048576).

Examples:

  • type=bind,source=/path/on/host,destination=/path/in/container
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared
  • type=bind,src=/path/on/host,dst=/path/in/container,relabel=shared,U=true
  • type=devpts,destination=/dev/pts
  • type=glob,src=/usr/lib/libfoo*,destination=/usr/lib,ro=true
  • type=image,source=fedora,destination=/fedora-image,rw=true
  • type=ramfs,tmpfs-size=512M,destination=/path/in/container
  • type=tmpfs,tmpfs-size=512M,destination=/path/in/container

--name=name

Assign a name to the container.

The operator can identify a container in three ways:

  • UUID long identifier (“f78375b1c487e03c9438c729345e54db9d20cfa2ac1fc3494b6eb60872e74778”);
  • UUID short identifier (“f78375b1c487”);
  • Name (“jonah”).

Podman generates a UUID for each container, and if no name is assigned to the container using --name, Podman generates a random string name. The name can be useful as a more human-friendly way to identify containers. This works for both background and foreground containers. The container's name is also added to the /etc/hosts file using the container's primary IP address (also see the --add-host option).

--network=mode, --net

Set the network mode for the container.

Valid mode values are:

•
bridge[:OPTIONS,...]: Create a network stack on the default bridge. This is the default for rootful containers. It is possible to specify these additional options:
  • alias=name: Add network-scoped alias for the container.
  • ip=IPv4: Specify a static IPv4 address for this container.
  • ip6=IPv6: Specify a static IPv6 address for this container.
  • mac=MAC: Specify a static MAC address for this container.
  • interface_name=name: Specify a name for the created network interface inside the container.
  • host_interface_name=name: Specify a name for the created network interface outside the container.
Any other options will be passed through to netavark without validation. This can be useful to pass arguments to netavark plugins.

For example, to set a static ipv4 address and a static mac address, use --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <network name or ID>[:OPTIONS,...]: Connect to a user-defined network; this is the network name or ID from a network created by podman network create. It is possible to specify the same options described under the bridge mode above. Use the --network option multiple times to specify additional networks.
    For backwards compatibility it is also possible to specify comma-separated networks on the first --network argument, however this prevents you from using the options described under the bridge section above.
  • none: Create a network namespace for the container but do not configure network interfaces for it, thus the container has no network connectivity.
  • container:id: Reuse another container's network stack.
  • host: Use the host's network namespace for the container instead of creating an isolated namespace. Warning: This gives the container full access to abstract Unix domain sockets and to TCP/UDP sockets bound to localhost. Since these mechanisms are often used to prevent access to sensitive system services, isolating them from access by external entities, use of this option may be considered a security vulnerability.
  • ns:path: Path to a network namespace to join.
aux types de montage :

  • src, source : spécification de la source du montage pour bind, glob et volume. Obligatoire pour artifact, bind, glob, image et volume.
  • dst, dest, destination, target : spécification de la destination du montage.

Lorsque des jokers de source sont spécifiés sans le répertoire de destination, les fichiers et répertoires sont montés avec leur chemin complet dans le conteneur. Lorsque la destination est spécifiée, les fichiers et répertoires correspondant au joker sur le nom de fichier de base dans le répertoire de destination sont montés. L'option type=glob,src=/foo*,destination=/tmp/bar indique aux moteurs de conteneur de monter les fichiers de l'hôte correspondant à /foo* dans le répertoire /tmp/bar/ du conteneur.

Options spécifiques au type=artifact :

  • digest : Si la source de l'artefact contient plusieurs blobs, un digest peut être spécifié pour monter uniquement le blob spécifique avec ce digest.
  • title : Si la source de l'artefact contient plusieurs blobs, un titre peut être défini et comparé à l'annotation org.opencontainers.image.title.
  • name : Peut être utilisé pour remplacer le nom de fichier utilisé dans le conteneur pour le montage. Sur un artefact à blob unique, le nom est utilisé tel quel si dst est un répertoire et ignoré sinon. Avec un artefact à plusieurs blobs, le nom sera utilisé avec un suffixe d'index <name>-x où x est l'index de la couche dans l'artefact, commençant à 0.

L'argument src contient le nom de l'artefact, qui doit déjà exister localement. L'argument dst contient le chemin cible ; si le chemin dans le conteneur est un répertoire, le titre du blob (annotation org.opencontainers.image.title) sera utilisé comme nom de fichier et joint au chemin. Si l'annotation n'existe pas, le digest sera utilisé à la place comme nom de fichier. Il en résulte que tous les blobs de l'artefact sont montés dans le conteneur au chemin donné.

Cependant, si le chemin dst est un fichier existant dans le conteneur, le blob sera monté directement dessus. Cela ne fonctionne que si l'artefact contient un seul blob ou si digest ou title est spécifié.

Si le chemin dst n'existe pas encore dans le conteneur, alors si l'artefact contient un seul blob, il se comporte comme le cas d'un fichier existant et se monte directement à ce chemin. Si l'artefact a plus d'un blob, il fonctionne comme le cas du répertoire existant et monte chaque blob en tant que fichier dans le chemin dst.

Options spécifiques au type=volume :

  • ro, readonly : true ou false (par défaut si non spécifié : false).
  • U, chown : true ou false (par défaut si non spécifié : false). Change récursivement le propriétaire et le groupe du volume source en fonction de l'UID et du GID du conteneur.
  • subpath : Monte uniquement un sous-chemin spécifique dans le volume, au lieu du volume entier.
  • idmap : Si spécifié, crée un montage mappé par ID vers l'espace de noms d'utilisateur cible dans le conteneur. L'option idmap n'est prise en charge que par Podman en mode rootful. Le noyau Linux n'autorise pas l'utilisation de systèmes de fichiers mappés par ID pour les utilisateurs non privilégiés. L'option idmap prend en charge un mappage personnalisé qui peut différer de l'espace de noms d'utilisateur utilisé par le conteneur. Le mappage peut être spécifié après l'option idmap comme suit : idmap=uids=0-1-10#10-11-10;gids=0-100-10. Pour chaque triplet, la première valeur est le début des ID du système de fichiers sous-jacent qui sont mappés à la deuxième valeur sur l'hôte. La longueur de ce mappage est donnée dans la troisième valeur. Plusieurs plages sont séparées par #. Si le mappage spécifié est précédé de '@', alors le mappage est considéré comme relatif à l'espace de noms d'utilisateur du conteneur. L'ID de l'hôte pour le mappage est modifié pour tenir compte de la position relative de l'utilisateur du conteneur dans l'espace de noms d'utilisateur du conteneur.

Options spécifiques au type=image :

Options spécifiques à bind et glob :

  • U, chown : true ou false (par défaut si non spécifié : false). Change récursivement le propriétaire et le groupe du volume source en fonction de l'UID et du GID du conteneur.
  • no-dereference : ne pas déréférencer les liens symboliques mais copier la source du lien dans la destination du montage.

Options spécifiques aux types=tmpfs et ramfs :

Le nom peut être utile comme moyen plus convivial d'identifier les conteneurs. Cela fonctionne pour les conteneurs en arrière-plan et au premier plan. Le nom du conteneur est également ajouté au fichier /etc/hosts en utilisant l'adresse IP principale du conteneur (voir également l'option --add-host).

--network=mode, --net

Définit le mode réseau pour le conteneur.

Les valeurs valides pour mode sont :

•
bridge[:OPTIONS,...] : Crée une pile réseau sur le pont (bridge) par défaut. C'est le mode par défaut pour les conteneurs rootful. Il est possible de spécifier les options supplémentaires suivantes :
  • alias=nom : Ajoute un alias à portée réseau pour le conteneur.
  • ip=IPv4 : Spécifie une adresse IPv4 statique pour ce conteneur.
  • ip6=IPv6 : Spécifie une adresse IPv6 statique pour ce conteneur.
  • mac=MAC : Spécifie une adresse MAC statique pour ce conteneur.
  • interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'intérieur du conteneur.
  • host_interface_name=nom : Spécifie un nom pour l'interface réseau créée à l'extérieur du conteneur.
Toute autre option sera transmise à netavark sans validation. Cela peut être utile pour passer des arguments aux plugins netavark.

Par exemple, pour définir une adresse IPv4 statique et une adresse MAC statique, utilisez --network bridge:ip=10.88.0.10,mac=44:33:22:11:00:99.

  • <nom ou ID du réseau>[:OPTIONS,...] : Se connecte à un réseau défini par l'utilisateur ; il s'agit du nom ou de l'ID d'un réseau créé par podman network create. Il est possible de spécifier les mêmes options décrites sous le mode bridge ci-dessus. Utilisez l'option --network plusieurs fois pour spécifier des réseaux supplémentaires.
    Pour la compatibilité ascendante, il est également possible de spécifier des réseaux séparés par des virgules dans le premier argument --network, mais cela vous empêche d'utiliser les options décrites dans la section bridge ci-dessus.
  • none : Crée un espace de noms réseau pour le conteneur mais ne configure aucune interface réseau pour celui-ci, de sorte que le conteneur n'a aucune connectivité réseau.
  • container:id : Réutilise la pile réseau d'un autre conteneur.
  • host : Utilise l'espace de noms réseau de l'hôte pour le conteneur au lieu d'en créer un isolé. Attention : Cela donne au conteneur un accès complet aux sockets Unix abstraits et aux sockets TCP/UDP liés à localhost. Étant donné que ces mécanismes sont souvent utilisés pour empêcher l'accès aux services système sensibles, en les isolant de l'accès par des entités externes, l'utilisation de cette option peut être considérée comme une vulnérabilité de sécurité.
  • ns:chemin : Chemin vers un espace de noms réseau à joindre.
  • private: Crée un nouvel espace de noms pour le conteneur. Utilise le mode bridge pour les conteneurs rootful et slirp4netns pour ceux rootless.
  • slirp4netns[:OPTIONS,...]: utilise slirp4netns(1) pour créer une pile réseau utilisateur. Il est possible de spécifier ces options supplémentaires, elles peuvent également être définies avec network_cmd_options dans containers.conf :
    • allow_host_loopback=true|false: Permet à slirp4netns d'atteindre l'IP de bouclage de l'hôte (la valeur par défaut est 10.0.2.2 ou la deuxième IP du sous-réseau CIDR de slirp4netns lorsqu'il est modifié, voir l'option cidr ci-dessous). La valeur par défaut est false.
    • mtu=MTU: Spécifie la MTU à utiliser pour ce réseau. (La valeur par défaut est 65520).
    • cidr=CIDR: Spécifie la plage d'adresses IP à utiliser pour ce réseau. (La valeur par défaut est 10.0.2.0/24).
    • enable_ipv6=true|false: Active l'IPv6. La valeur par défaut est true. (Requis pour outbound_addr6).
    • outbound_addr=INTERFACE: Spécifie l'interface sortante à laquelle slirp se lie (trafic ipv4 uniquement).
    • outbound_addr=IPv4: Spécifie l'adresse ipv4 sortante à laquelle slirp se lie.
    • outbound_addr6=INTERFACE: Spécifie l'interface sortante à laquelle slirp se lie (trafic ipv6 uniquement).
    • outbound_addr6=IPv6: Spécifie l'adresse ipv6 sortante à laquelle slirp se lie.
    • port_handler=rootlesskit: Utilise rootlesskit pour la redirection de port. Par défaut.
      Note : Rootlesskit modifie l'adresse IP source des paquets entrants en une adresse IP de l'espace de noms réseau du conteneur, généralement 10.0.2.100. Si l'application nécessite la véritable adresse IP source, par exemple pour les journaux du serveur web, utilisez le gestionnaire de ports slirp4netns. Le gestionnaire de ports rootlesskit est également utilisé pour les conteneurs rootless lorsqu'ils sont connectés à des réseaux définis par l'utilisateur.
    • port_handler=slirp4netns: Utilise la redirection de port slirp4netns, qui est plus lente que rootlesskit mais préserve la bonne adresse IP source. Ce gestionnaire de ports ne peut pas être utilisé pour les réseaux définis par l'utilisateur.
    •
    pasta[:OPTIONS,...]: utilise pasta(1) pour créer une pile réseau en mode utilisateur.
    C'est la valeur par défaut pour les conteneurs rootless et uniquement supporté en mode rootless.
    Par défaut, les adresses et les routes IPv4 et IPv6, ainsi que le nom de l'interface du pod, sont copiés depuis l'hôte. La redirection de port préserve l'adresse IP source d'origine. Les options décrites dans pasta(1) peuvent être spécifiées comme arguments séparés par des virgules.
    En termes d'options de pasta(1), --config-net est donné par défaut, afin de configurer le réseau lorsque le conteneur est démarré, et --no-map-gw est également supposé par défaut, pour éviter l'accès direct du conteneur à l'hôte en utilisant l'adresse de passerelle. Ce dernier peut être outrepassé en passant --map-gw dans les options spécifiques à pasta (bien que ce ne soit pas une option réelle de pasta(1)).
    Pour une meilleure intégration avec la gestion du DNS, --dns-forward 169.254.1.1 est passé, et cette adresse est ajoutée à resolv.conf(5) en tant que premier résolveur. Il est possible de passer --dns-forward explicitement dans le cas où une adresse IP différente devrait être utilisée. Pour que l'entrée d'hôte host.containers.internal dans /etc/hosts fonctionne et permette les connexions à l'hôte, --map-guest-addr 169.254.1.2 est passé. Encore une fois, cela peut être défini explicitement pour choisir une adresse IP différente.
    De plus, -t none et -u none sont passés si, respectivement, aucune redirection de port TCP ou UDP de l'hôte vers le conteneur n'est configurée (via --publish de Podman ou en passant directement les options -t/-u de pasta), afin de désactiver la redirection automatique de port basée sur les ports liés. De même, -T none et -U none sont donnés pour désactiver la même fonctionnalité du conteneur vers l'hôte.
    Toutes les options peuvent également être définies dans containers.conf(5) ; voir la clé pasta_options dans la section réseau de ce fichier.
    Quelques exemples :
    • pasta:--map-gw: Permet au conteneur d'atteindre directement l'hôte en utilisant l'adresse de passerelle.
    • pasta:--mtu,1500: Spécifie une MTU de 1500 octets pour l'interface tap dans le conteneur.
    • pasta:--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,-m,1500,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) : désactive l'IPv6, attribue 10.0.2.0/24 à l'interface tap0 dans le conteneur, avec la passerelle 10.0.2.3, active le transmetteur DNS accessible à 10.0.2.3, définit la MTU à 1500 octets, désactive NDP, DHCPv6 et DHCP support.
    • pasta:-I,tap0,--ipv4-only,-a,10.0.2.0,-n,24,-g,10.0.2.2,--dns-forward,10.0.2.3,--no-ndp,--no-dhcpv6,--no-dhcp, équivalent aux options par défaut de slirp4netns(1) avec les remplacements Podman : identique à ci-dessus, mais laisse la MTU à 65520 octets
    • pasta:-t,auto,-u,auto,-T,auto,-U,auto: active la redirection automatique de port basée sur les ports liés observés des deux côtés, hôte et conteneur
    • pasta:-T,5201: active la redirection du port TCP 5201 du conteneur vers l'hôte, en utilisant l'interface de bouclage au lieu de l'interface tap pour de meilleures performances

    Invalide si utilisé avec --dns, --dns-option, ou --dns-search avec --network défini sur none ou container:id.

    Si utilisé conjointement avec --pod, le conteneur rejoint l'espace de noms réseau du pod.

    --pod-id-file=fichier

    Exécute un conteneur dans un pod existant et lit l'ID du pod à partir du fichier spécifié. Lorsqu'un conteneur est exécuté dans un pod qui possède un conteneur d'infrastructure, le conteneur d'infrastructure démarre en premier.

    --preserve-fd=FD1[,FD2,...]

    Transmet au processus les descripteurs de fichiers supplémentaires spécifiés dans la liste séparée par des virgules. Peut être spécifié plusieurs fois. Cette option n'est prise en charge qu'avec le runtime OCI crun. L'utilisation de cette option avec d'autres runtimes OCI peut présenter un risque de sécurité.

    (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (hors WSL2))

    --preserve-fds=N

    Transmet au processus N descripteurs de fichiers supplémentaires (en plus de 0, 1, 2). Le total des FD est de 3+N. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (hors WSL2))

    --privileged

    Accorde des privilèges étendus à ce conteneur. La valeur par défaut est false.

    Par défaut, les conteneurs Podman ne sont pas privilégiés (=false) et ne peuvent pas, par exemple, modifier des parties du système d'exploitation. En effet, par défaut, un conteneur n'a accès qu'à un nombre limité de périphériques. Un conteneur "privilégié" a le même accès aux périphériques que l'utilisateur qui lance le conteneur, à l'exception des consoles virtuelles (/dev/tty\d+) lorsqu'il s'exécute en mode systemd (--systemd=always).

    Un conteneur privilégié désactive les fonctionnalités de sécurité qui isolent le conteneur de l'hôte. Les capacités supprimées, les périphériques limités, les points de montage en lecture seule, la séparation Apparmor/SELinux et les filtres Seccomp sont tous désactivés. En raison des fonctionnalités de sécurité désactivées, le champ privilégié ne doit presque jamais être défini, car les conteneurs peuvent facilement s'échapper de leur confinement.

    Les conteneurs s'exécutant dans un espace de noms utilisateur (par exemple, les conteneurs sans root) ne peuvent pas avoir plus de privilèges que l'utilisateur qui les a lancés.

    --publish, -p=[[ip:][portHote]:]portConteneur[/protocole]

    Publie un port, ou une plage de ports, d'un conteneur sur l'hôte.

    Le portHote et le portConteneur peuvent tous deux être spécifiés comme une plage de ports. Lors de la spécification de plages pour les deux, le nombre de ports conteneurs dans la plage doit correspondre au nombre de ports hôtes dans la plage.

    Si l'adresse IP de l'hôte est définie sur 0.0.0.0 ou n'est pas définie du tout, le port est lié à toutes les adresses IP de l'hôte.

    Par défaut, Podman publie les ports TCP. Pour publier un port UDP à la place, donnez udp comme protocole. Pour publier des ports TCP et UDP, définissez --publish deux fois, avec tcp et udp comme protocoles respectivement. Les conteneurs rootful peuvent également publier des ports en utilisant le protocole sctp.

    Le port hôte ne doit pas nécessairement être spécifié (par exemple, podman run -p 127.0.0.1::80). S'il ne l'est pas, un port aléatoire sera attribué au port conteneur sur l'hôte.

    Utilisez podman port pour voir le mappage réel : podman port $CONTENEUR $PORTCONTENEUR.

    La publication de ports n'est prise en charge que pour les conteneurs utilisant leur propre espace de noms réseau via des réseaux bridge, ou les modes réseau pasta et slirp4netns.

    Remarque : Si un conteneur s'exécute dans un pod, il n'est pas nécessaire de publier le port pour les conteneurs du pod. Le port doit uniquement être publié par le pod lui-même. Les piles réseau des pods agissent comme la pile réseau de l'hôte - ce qui signifie qu'une variété de conteneurs dans le pod et de programmes dans le conteneur partagent tous une seule interface, une adresse IP et les ports associés. Si un conteneur se lie à un port, aucun autre conteneur ne peut utiliser ce port dans le pod tant qu'il est utilisé. Les conteneurs du pod peuvent également communiquer via localhost en faisant en sorte qu'un conteneur se lie à localhost dans le pod, et qu'un autre se connecte à ce port.

    --publish-all, -P

    Publie tous les ports exposés sur des ports aléatoires sur les interfaces de l'hôte. La valeur par défaut est false.

    Lorsqu'il est défini sur true, publie tous les ports exposés sur les interfaces de l'hôte. Si l'opérateur utilise -P (ou -p), Podman rend le port exposé accessible sur l'hôte et les ports sont disponibles pour tout client pouvant atteindre l'hôte.

    Lors de l'utilisation de cette option, Podman lie tout port exposé à un port aléatoire sur l'hôte dans une plage de ports éphémères définie par /proc/sys/net/ipv4/ip_local_port_range. Pour trouver le mappage entre les ports hôtes et les ports exposés, utilisez podman port.

    --pull=politique

    Politique de téléchargement d'image. La valeur par défaut est missing.

    • always : Télécharge toujours l'image et génère une erreur si le téléchargement échoue.
    • missing : Télécharge l'image uniquement lorsque l'image n'est pas présente dans le stockage local des conteneurs. Génère une erreur si aucune image n'est trouvée et que le téléchargement échoue.
    • never : Ne télécharge jamais l'image mais utilise celle du stockage local des conteneurs. Génère une erreur si aucune image n'est trouvée.
    • newer : Télécharge si l'image dans le registre est plus récente que celle du stockage local des conteneurs. Une image est considérée comme plus récente lorsque les digests sont différents. La comparaison des horodatages est sujette à erreur. Les erreurs de téléchargement sont supprimées si une image locale a été trouvée.

    --quiet, -q

    Supprime les informations de sortie lors du téléchargement des images.

    --rdt-class=intel-rdt-class-of-service

    Rdt-class définit la classe de service (CLOS ou COS) dans laquelle le conteneur doit s'exécuter. Basé sur la fonctionnalité Cache Allocation Technology (CAT) qui fait partie de l'ensemble de fonctionnalités Intel Resource Director Technology (RDT), tous les processus du conteneur s'exécuteront dans la COS préconfigurée, représentant une partie du cache. La COS doit être créée et configurée à l'aide d'un système de fichiers pseudo (généralement monté sur /sys/fs/resctrl) que le pilote de noyau resctrl fournit. L'attribution du conteneur à une COS nécessite des privilèges root et donc ne fonctionne pas dans un environnement sans root. Actuellement, la fonctionnalité n'est prise en charge qu'avec runc comme runtime. Voir ⟨https://docs.kernel.org/arch/x86/resctrl.html⟩ pour plus de détails sur la création d'une COS avant qu'un conteneur puisse lui être attribué.

    --read-only

    Monte le système de fichiers racine du conteneur en lecture seule.

    Par défaut, les systèmes de fichiers racines des conteneurs sont inscriptibles, permettant aux processus d'écrire des fichiers n'importe où. En spécifiant le drapeau --read-only, le système de fichiers racine des conteneurs est monté en lecture seule, interdisant toute écriture.

    --read-only-tmpfs

    Lors de l'exécution de conteneurs --read-only, monte un tmpfs en lecture-écriture sur /dev, /dev/shm, /run, /tmp et /var/tmp. La valeur par défaut est true.

    --read-only --read-only-tmpfs / /run, /tmp, /var/tmp
    true true r/o r/w
    true false r/o r/o
    false false r/w r/w
    false true r/w r/w

    Lorsque --read-only=true et --read-only-tmpfs=true, des tmpfs supplémentaires sont montés sur les répertoires /tmp, /run et /var/tmp.

    Lorsque --read-only=true et --read-only-tmpfs=false, /dev et /dev/shm sont marqués en lecture seule (Read/Only) et aucun tmpfs n'est monté sur /tmp, /run et /var/tmp. Les répertoires sont exposés depuis l'image sous-jacente, ce qui signifie qu'ils sont en lecture seule par défaut. Cela rend le conteneur totalement en lecture seule. Aucun répertoire inscriptible n'existe dans le conteneur. Dans ce mode, les répertoires inscriptibles doivent être ajoutés via des volumes ou des montages externes.

    Par défaut, lorsque --read-only=false, /dev et /dev/shm sont en lecture-écriture, et /tmp, /run, et /var/tmp sont des répertoires en lecture-écriture de l'image conteneur.

    --replace

    Si un autre conteneur portant le même nom existe déjà, remplacez-le et supprimez-le. La valeur par défaut est false.

    --requires=conteneur

    Spécifie une ou plusieurs dépendances. Une dépendance est un conteneur dont le démarrage est requis avant ce conteneur. Les conteneurs peuvent être spécifiés par nom ou ID, avec plusieurs conteneurs séparés par des virgules.

    --restart=politique

    Politique de redémarrage à suivre lors de la sortie des conteneurs. La politique de redémarrage n'a pas d'effet si un conteneur est arrêté via les commandes podman kill ou podman stop.

    Les valeurs de politique valides sont :

    • no : Ne pas redémarrer les conteneurs à la sortie
    • never : Synonyme de no ; ne pas redémarrer les conteneurs à la sortie
    • on-failure[:max_retries] : Redémarrer les conteneurs lorsqu'ils se terminent avec un code de sortie non nul, en essayant indéfiniment ou jusqu'à ce que le nombre facultatif de max_retries soit atteint
    • always : Redémarrer les conteneurs lorsqu'ils se terminent, quel que soit leur statut, en essayant indéfiniment
    • unless-stopped : Identique à always

    Podman fournit un fichier d'unité systemd, podman-restart.service, qui redémarre les conteneurs après un redémarrage du système.

    Lors de l'exécution de conteneurs dans des services systemd, utilisez la fonctionnalité de redémarrage fournie par systemd. Autrement dit, n'utilisez pas cette option dans une unité de conteneur, mais définissez la directive Restart= dans la section [Service]. Voir podman-systemd.unit(5) et systemd.service(5).

    --retry=tentatives

    Nombre de tentatives de téléchargement ou d'envoi d'images entre le registre et le stockage local en cas d'échec. Par défaut, 3.

    --retry-delay=durée

    Durée du délai entre les tentatives de nouvelle tentative lors du téléchargement

    ou_a_pousser des images entre le registre et le stockage local en cas d'échec. La valeur par défaut est de deux secondes, puis le délai augmente exponentiellement. Le délai est utilisé lorsque cette valeur est définie et qu'aucun retraitement exponentiel ne se produit.

    --rm

    Supprime automatiquement le conteneur et tous les volumes anonymes sans nom associés au conteneur lorsqu'il se termine. La valeur par défaut est false.

    --rmi

    Après la sortie du conteneur, supprime l'image à moins qu'un autre conteneur ne l'utilise. Implique --rm sur le nouveau conteneur. La valeur par défaut est false.

    --rootfs

    Si spécifié, le premier argument fait référence à un conteneur décompressé sur le système de fichiers.

    Ceci est utile pour exécuter un conteneur sans nécessiter de gestion d'image, le rootfs du conteneur étant censé être géré en externe.

    Montages Overlay Rootfs

    Le drapeau :O indique à Podman de monter le répertoire du chemin rootfs comme stockage en utilisant le système de fichiers overlay. Les processus du conteneur peuvent modifier le contenu à l'intérieur du point de montage, qui est stocké dans le stockage du conteneur dans un répertoire séparé. En termes d'overlay, le répertoire source est le inférieur (lower) et le répertoire de stockage du conteneur est le supérieur (upper). Les modifications apportées au point de montage sont détruites lorsque le conteneur a fini de s'exécuter, de manière similaire au démontage d'un point de montage tmpfs.

    Remarque : Sur les systèmes SELinux, le rootfs doit avoir le bon label, qui est par défaut unconfined_u:object_r:container_file_t:s0.

    idmap

    Si idmap est spécifié, crée un montage idmapped vers l'espace de noms utilisateur cible dans le conteneur. L'option idmap prend en charge un mappage personnalisé qui peut être différent de l'espace de noms utilisateur utilisé par le conteneur. Le mappage peut être spécifié après l'option idmap, comme ceci : idmap=uids=0-1-10#10-11-10;gids=0-100-10. Pour chaque triplet, la première valeur est le début des IDs du système de fichiers de base qui sont mappés à la deuxième valeur sur l'hôte. La longueur de ce mappage est donnée par la troisième valeur. Plusieurs plages sont séparées par #.

    --sdnotify=container | conmon | healthy | ignore

    Détermine comment utiliser le NOTIFY_SOCKET, tel que passé avec systemd et Type=notify.

    La valeur par défaut est container, ce qui signifie permettre au runtime OCI de proxifier le socket dans le conteneur pour recevoir la notification de préparation. Podman définit MAINPID à l'ID du processus de conmon. L'option conmon définit MAINPID à l'ID du processus de conmon et envoie READY lorsque le conteneur a démarré. Le socket n'est jamais passé au runtime ou au conteneur. L'option healthy définit MAINPID à l'ID du processus de conmon et envoie READY lorsque le conteneur est devenu sain ; nécessite qu'un healthcheck soit défini. Le socket n'est jamais passé au runtime ou au conteneur. L'option ignore supprime NOTIFY_SOCKET de l'environnement pour lui-même et pour les processus enfants, dans le cas où un autre processus au-dessus de Podman utilise NOTIFY_SOCKET et que Podman ne l'utilise pas.

    --seccomp-policy=politique

    Spécifie la politique pour sélectionner le profil seccomp. S'il est défini sur image, Podman recherche un label "io.containers.seccomp.profile" dans la configuration de l'image du conteneur et utilise sa valeur comme profil seccomp. Sinon, Podman suit la politique default en appliquant le profil par défaut sauf indication contraire via --security-opt seccomp comme décrit ci-dessous.

    Notez que cette fonctionnalité est expérimentale et peut changer à l'avenir.

    --secret=secret[,opt=opt ...]

    Donne au conteneur l'accès à un secret. Peut être spécifié plusieurs fois.

    Un secret est un bloc de données sensibles dont un conteneur a besoin au moment de l'exécution mais qui n'est pas stocké dans l'image ou dans le contrôle de source, comme les noms d'utilisateur et les mots de passe, les certificats et clés TLS, les clés SSH ou d'autres chaînes génériques importantes ou contenu binaire (jusqu'à 512 Ko).

    Lorsque les secrets sont spécifiés comme type mount, les secrets sont copiés et montés dans le conteneur lors de la création d'un conteneur. Lorsque les secrets sont spécifiés comme type env, le secret est défini comme variable d'environnement dans le conteneur. Les secrets sont écrits dans le conteneur au moment de la création du conteneur, et la modification du secret à l'aide des commandes podman secret après la création du conteneur affecte le secret à l'intérieur du conteneur.

    Les secrets et leur stockage sont gérés à l'aide de la commande podman secret.

    Options de secret

    • type=mount|env : Comment le secret est exposé au conteneur.
      mount monte le secret dans le conteneur sous forme de fichier.
      env expose le secret comme variable d'environnement.
      La valeur par défaut est mount.
    • target=target : Cible du secret.
      Pour les secrets montés, il s'agit du chemin d'accès au secret à l'intérieur du conteneur.
      Si un chemin d'accès complet est fourni, le secret est monté à cet emplacement.
      Sinon, le secret est monté sur
      /run/secrets/target pour les conteneurs Linux ou
      /var/run/secrets/target pour les conteneurs FreeBSD.
      Si la cible n'est pas définie, le secret est monté sur /run/secrets/nomsecret par défaut.
      Pour les secrets env, il s'agit de la clé de la variable d'environnement. La valeur par défaut est nomsecret.
    • uid=0 : UID du secret. La valeur par défaut est 0. Type de montage secret uniquement.
    • gid=0 : GID du secret. La valeur par défaut est 0. Type de montage secret uniquement.
    • mode=0 : Mode du secret. La valeur par défaut est 0444. Type de montage secret uniquement.

    Exemples

    Monter sur /mon/emplacement/monsecret avec UID 1 :

    --secret monsecret,target=/mon/emplacement/monsecret,uid=1

    Monter sur /run/secrets/cibletotale avec le mode 0777 :

    --secret monsecret,target=cibletotale,mode=0777

    Créer une variable d'environnement secrète nommée ENVSEC :

    --secret monsecret,type=env,target=ENVSEC

    --security-opt=option

    Options de sécurité

    • apparmor=unconfined : Désactive la limitation apparmor pour le conteneur
    • apparmor=profil-alternatif : Définit le profil de limitation apparmor pour le conteneur
    • label=user:UTILISATEUR: Définit l'utilisateur du label pour les processus du conteneur
    • label=role:ROLE: Définit le rôle du label pour les processus du conteneur
    • label=type:TYPE: Définit le type de processus du label pour les processus du conteneur
    • label=level:NIVEAU: Définit le niveau du label pour les processus du conteneur
    • label=filetype:TYPE: Définit le type de fichier du label pour les fichiers du conteneur
    • label=disable: Désactive la séparation des labels pour le conteneur

    Remarque : La labellisation peut être désactivée pour tous les conteneurs en définissant label=false dans le fichier containers.conf (/etc/containers/containers.conf ou $HOME/.config/containers/containers.conf).

    • label=nested: Permet les modifications SELinux à l'intérieur du conteneur. Les conteneurs sont autorisés à modifier les labels SELinux sur les fichiers et les processus, tant que la politique SELinux le permet. Sans nested, les conteneurs voient SELinux comme désactivé, même lorsqu'il est activé sur l'hôte. Les conteneurs sont empêchés de définir des labels.
    • mask=/chemin/1:/chemin/2: Les chemins à masquer séparés par deux-points. Un chemin masqué ne peut pas être accédé à l'intérieur du conteneur.
    • no-new-privileges: Désactive la capacité pour les processus du conteneur de gagner des privilèges supplémentaires via l'appel système execve(2) (par exemple, via les bits setuid ou setgid, ou via les capacités de fichiers). Les programmes qui dépendent des bits setuid/setgid définis sur leur exécutable pour changer d'ID utilisateur ou d'ID de groupe ne peuvent plus le faire, et toutes les capacités de fichiers ajoutées à l'exécutable (par exemple, via setcap) ne sont pas ajoutées à l'ensemble des capacités autorisées. Pour plus de détails, voir : https://docs.kernel.org/userspace-api/no_new_privs.html.
    • seccomp=unconfined: Désactive la limitation seccomp pour le conteneur.
    • seccomp=profile.json: Fichier JSON à utiliser comme filtre seccomp. Notez que l'annotation io.podman.annotations.seccomp est définie avec la valeur spécifiée, comme montré dans podman inspect.
    • proc-opts=OPTIONS : Liste d'options séparées par des virgules à utiliser pour le montage /proc. Plus de détails sur les options de montage possibles sont spécifiés dans la page de manuel proc(5).
    • unmask=ALL ou /chemin/1:/chemin/2, ou chemins développés par shell (/proc/*): Chemins à démasquer séparés par deux-points. S'il est défini sur ALL, il démasque tous les chemins qui sont masqués ou rendus en lecture seule par défaut. Les chemins masqués par défaut sont /proc/acpi, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/sched_debug, /proc/scsi, /proc/timer_list, /proc/timer_stats, /sys/firmware, et /sys/fs/selinux, /sys/devices/virtual/powercap. Les chemins par défaut qui sont en lecture seule sont /proc/asound, /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger, /sys/fs/cgroup.

    Remarque : La labellisation peut être désactivée pour tous les conteneurs en définissant label=false dans le fichier containers.conf(5).

    --shm-size=nombre[unité]

    Taille de /dev/shm. Une unité peut être b (octets), k (kibioctets), m (mebioctets) ou g (gibioctets). Si l'unité est omise, le système utilise des octets. Si la taille est omise, la valeur par défaut est 64m. Lorsque la taille est 0, il n'y a aucune limite à la quantité de mémoire utilisée pour l'IPC par le conteneur. Cette option est en conflit avec --ipc=host.

    --shm-size-systemd=nombre[unité]

    Taille des montages tmpfs spécifiques à systemd tels que /run, /run/lock, /var/log/journal et /tmp. Une unité peut être b (octets), k (kibioctets), m (mebioctets) ou g (gibioctets). Si l'unité est omise, le système utilise des octets. Si la taille est omise, la valeur par défaut est 64m. Lorsque la taille est 0, l'utilisation est limitée à 50% de la mémoire disponible de l'hôte.

    --sig-proxy

    Proxifie les signaux reçus vers le processus du conteneur. SIGCHLD, SIGURG, SIGSTOP et SIGKILL ne sont pas proxifiés.

    La valeur par défaut est true.

    --stop-signal=signal

    Signal pour arrêter un conteneur. La valeur par défaut est SIGTERM.

    --stop-timeout=secondes

    Délai d'attente pour arrêter un conteneur. La valeur par défaut est 10. Les connexions distantes utilisent le fichier containers.conf local pour les valeurs par défaut.

    --subgidname=nom

    Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant la correspondance avec le nom nom dans le fichier /etc/subgid. Si l'exécution est sans privilèges (rootless), l'utilisateur doit avoir le droit d'utiliser la correspondance. Voir subgid(5). Cet indicateur entre en conflit avec --userns et --gidmap.

    --subuidname=nom

    Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant la correspondance avec le nom nom dans le fichier /etc/subuid. Si l'exécution est sans privilèges (rootless), l'utilisateur doit avoir le droit d'utiliser la correspondance. Voir subuid(5). Cet indicateur entre en conflit avec --userns et --uidmap.

    --sysctl=nom=valeur

    Configure les paramètres du noyau nommés (namespaced) à l'exécution.

    Pour l'espace de noms IPC, les sysctls suivants sont autorisés :

    • kernel.msgmax
    • kernel.msgmnb
    • kernel.msgmni
    • kernel.sem
    • kernel.shmall
    • kernel.shmmax
    • kernel.shmmni
    • kernel.shm_rmid_forced
    • Sysctls commençant par fs.mqueue.*

    Note : si l'option --ipc=host est utilisée, les sysctls ci-dessus ne sont pas autorisés.

    Pour l'espace de noms réseau, seuls les sysctls commençant par net.* sont autorisés.

    Note : si l'option --network=host est utilisée, les sysctls ci-dessus ne sont pas autorisés.

    --systemd=true | false | always

    Exécute le conteneur en mode systemd. La valeur par défaut est true.

    • true active le mode systemd uniquement lorsque la commande exécutée dans le conteneur est systemd, /usr/sbin/init, /sbin/init ou /usr/local/sbin/init.
    • false désactive le mode systemd.
    • always force l'activation du mode systemd.

    L'exécution du conteneur en mode systemd entraîne les modifications suivantes :

    •
    Podman monte des systèmes de fichiers tmpfs sur les répertoires suivants :
    • /run
    • /run/lock
    • /tmp
    • /sys/fs/cgroup/systemd (sur un système cgroup v1)
    • /var/lib/journal
    • Podman définit le signal d'arrêt par défaut sur SIGRTMIN+3.
    • Podman définit la variable d'environnement container_uuid dans le conteneur avec les 32 premiers caractères de l'ID du conteneur.
    • Podman ne monte pas les consoles virtuelles (/dev/tty\d+) lorsqu'il est exécuté avec --privileged.
    • Sur cgroup v2, /sys/fs/cgroup est monté en écriture.

    Cela permet à systemd de s'exécuter dans un conteneur confiné sans aucune modification.

    Notez que sur les systèmes SELinux, systemd tente d'écrire dans le système de fichiers cgroup. Les conteneurs qui écrivent dans le système de fichiers cgroup sont refusés par défaut. Le booléen container_manage_cgroup doit être activé pour que cela soit autorisé sur un système séparé par SELinux.

    setsebool -P container_manage_cgroup true

    --timeout=secondes

    Temps maximum autorisé pour qu'un conteneur s'exécute avant que conmon ne lui envoie le signal de terminaison. Par défaut, les conteneurs s'exécutent jusqu'à ce qu'ils se terminent ou soient arrêtés par podman stop.

    --tls-verify

    Exige HTTPS et vérifie les certificats lors du contact avec les registres (par défaut : true). S'il est explicitement défini sur true, la vérification TLS est utilisée. S'il est défini sur false, la vérification TLS n'est pas utilisée. Si non spécifié, la vérification TLS est utilisée à moins que le registre cible ne soit listé comme registre non sécurisé dans containers-registries.conf(5)

    --tmpfs=fs

    Crée un montage tmpfs.

    Monte un système de fichiers temporaire (tmpfs) dans un conteneur, par exemple :

    $ podman run -d --tmpfs /tmp:rw,size=787448k,mode=1777 my_image

    Cette commande monte un tmpfs sur /tmp à l'intérieur du conteneur. Les options de montage prises en charge sont les mêmes que les options de montage par défaut de Linux. Si aucune option n'est spécifiée, le système utilise les options suivantes : rw,noexec,nosuid,nodev.

    --tty, -t

    Alloue un pseudo-TTY. La valeur par défaut est false.

    Lorsqu'il est défini sur true, Podman alloue un pseudo-TTY et se connecte à l'entrée standard du conteneur. Cela peut être utilisé, par exemple, pour exécuter un shell interactif à usage unique.

    NOTE : l'indicateur --tty empêche la redirection de la sortie standard. Il combine STDOUT et STDERR, peut insérer des caractères de contrôle et peut bloquer les pipes. Cette option n'est utilisée que lors de l'exécution interactive dans un terminal. Lors de l'alimentation en entrée de Podman, utilisez uniquement -i, pas -it.

    echo "asdf" | podman run --rm -i someimage /bin/cat

    --tz=fuseau_horaire

    Définit le fuseau horaire dans le conteneur. Cet indicateur accepte les fuseaux horaires basés sur la région, l'heure GMT, ainsi que local, qui définit le fuseau horaire du conteneur pour qu'il corresponde à la machine hôte. Voir /usr/share/zoneinfo/ pour les fuseaux horaires valides. Les connexions distantes utilisent le fichier containers.conf local pour les valeurs par défaut.

    --uidmap=[indicateurs]uid_conteneur:uid_origine[:montant]

    Exécute le conteneur dans un nouvel espace de noms utilisateur en utilisant la correspondance UID fournie. Cette option entre en conflit avec les options --userns et --subuidname. Cette option fournit un moyen de mapper les UID hôtes aux UID des conteneurs. Elle peut être passée plusieurs fois pour mapper différentes plages.

    Les valeurs possibles des indicateurs optionnels sont discutées plus loin sur cette page. La valeur montant est facultative et est supposée être 1 si elle n'est pas donnée.

    La valeur uid_origine est basée sur l'utilisateur qui exécute la commande, qu'il s'agisse d'un utilisateur rootful ou rootless.

    • utilisateur rootful : [indicateurs]uid_conteneur:uid_hôte[:montant]
    • utilisateur rootless : [indicateurs]uid_conteneur:uid_intermédiaire[:montant]

    Correspondances rootful

    Lorsque podman run est appelé par un utilisateur privilégié, l'option --uidmap fonctionne comme une correspondance directe entre les UID hôtes et les UID des conteneurs.

    UID hôte -> UID conteneur

    Le montant spécifie le nombre d'UID consécutifs qui sont mappés. Si, par exemple, montant est 4, la correspondance ressemble à ceci :

    UID hôte UID conteneur
    uid_origine uid_conteneur
    uid_origine + 1 uid_conteneur + 1
    uid_origine + 2 uid_conteneur + 2
    uid_origine + 3 uid_conteneur + 3

    Correspondances rootless

    Lorsque podman run est appelé par un utilisateur non privilégié (c'est-à-dire en mode rootless), la valeur uid_origine est interprétée comme un "UID intermédiaire". Dans le cas rootless, les UID hôtes ne sont pas directement mappés aux UID des conteneurs. La correspondance se fait plutôt en deux étapes :

    UID hôte -> UID intermédiaire -> UID conteneur

    L'option --uidmap influence uniquement la deuxième étape de correspondance.

    La première étape de correspondance est dérivée par Podman du contenu du fichier /etc/subuid et de l'UID de l'utilisateur appelant Podman.

    Première étape de correspondance :

    UID hôte UID intermédiaire
    UID pour l'utilisateur Podman 0
    1er UID subordonné 1
    2ème UID subordonné 2
    3ème UID subordonné 3
    nième UID subordonné n

    Pour pouvoir utiliser des UID intermédiaires supérieurs à zéro, l'utilisateur doit avoir des UID subordonnés configurés dans /etc/subuid. Voir subuid(5).

    La deuxième étape de correspondance est configurée avec --uidmap.

    Si, par exemple, montant est 5, la deuxième étape de correspondance ressemble à ceci :

    UID intermédiaire UID conteneur
    uid_origine uid_conteneur
    uid_origine + 1 uid_conteneur + 1
    uid_origine + 2 uid_conteneur + 2
    uid_origine + 3 uid_conteneur + 3
    uid_origine + 4 uid_conteneur + 4

    Lors de l'exécution en mode rootless, Podman utilise toutes les plages configurées dans le fichier /etc/subuid.

    L'ID utilisateur actuel est mappé à l'UID=0 dans l'espace de noms utilisateur rootless. Chaque plage supplémentaire est ajoutée séquentiellement ensuite :

    Hôte Espace de noms utilisateur rootless Longueur
    $UID 0 1
    1 $FIRST_RANGE_ID $FIRST_RANGE_LENGTH
    1+$FIRST_RANGE_LENGTH $SECOND_RANGE_ID $SECOND_RANGE_LENGTH

    Référencement d'un ID hôte de l'espace de noms parent

    En tant qu'utilisateur rootless, l'ID hôte donné dans --uidmap ou --gidmap est mappé depuis l'espace de noms intermédiaire généré par Podman. Parfois, il est souhaitable de faire référence directement à l'espace de noms hôte. Il est possible de le faire manuellement, en exécutant podman unshare cat /proc/self/gid_map, en trouvant l'ID hôte désiré dans la deuxième colonne de la sortie, et en obtenant l'ID intermédiaire correspondant dans la première colonne.

    Podman peut effectuer tout cela en faisant précéder l'ID hôte dans la correspondance par le symbole @. Par exemple, en spécifiant --gidmap 100000:@2000:1, Podman recherchera l'ID intermédiaire correspondant à l'ID hôte 2000 et mappera l'ID intermédiaire trouvé à l'ID conteneur 100000. L'ID hôte donné doit avoir été subordonné (sinon il ne serait pas mappé dans l'espace intermédiaire en premier lieu).

    Si la longueur est supérieure à un, par exemple avec --gidmap 100000:@2000:2, Pod

    man will map host ids 2000 et 2001 à 100000 et 100001, respectivement, quelle que soit la manière dont le mappage intermédiaire est défini.

    Extension des mappages précédents

    Certaines modifications de mappage peuvent être fastidieuses. Par exemple, un utilisateur commence avec un mappage tel que --gidmap="0:0:65000", qui doit être modifié de telle sorte que l'ID parent 1 soit mappé à l'ID conteneur 100000 à la place, laissant l'ID conteneur 1 non attribué. Le --gidmap correspondant devient --gidmap="0:0:1" --gidmap="2:2:65534" --gidmap="100000:1:1".

    Cette notation peut être simplifiée à l'aide du drapeau +, qui s'occupe de diviser les mappages précédents en supprimant toute attribution conflictuelle avec le mappage donné. Le drapeau est donné avant l'ID du conteneur comme suit : --gidmap="0:0:65000" --gidmap="+100000:1:1"

    Drapeau Exemple Description
    + +100000:1:1 Étendre le mappage précédent

    Cette notation entraîne des lacunes dans l'attribution, il peut donc être pratique de combler ces lacunes par la suite : --gidmap="0:0:65000" --gidmap="+100000:1:1" --gidmap="1:65001:1"

    Un cas d'utilisation spécifique pour ce drapeau est dans le contexte des utilisateurs sans privilèges. Un utilisateur sans privilèges peut spécifier des mappages avec le drapeau + comme dans --gidmap="+100000:1:1". Podman "remplira alors les lacunes" à partir de zéro avec tous les ID intermédiaires restants. Ceci est pratique lorsqu'un utilisateur souhaite mapper un ID intermédiaire spécifique à un ID de conteneur, laissant les autres ID subordonnés être mappés par Podman à volonté.

    Passer un seul parmi --uidmap ou --gidmap

    Habituellement, les ID utilisateur et groupe subordonnés sont attribués simultanément, et pour tout utilisateur, les ID utilisateur subordonnés correspondent aux ID groupe subordonnés. Par commodité, si un seul parmi --uidmap ou --gidmap est donné, podman suppose que le mappage fait référence aux deux UID et GID et applique le mappage donné aux deux. Si une seule des deux valeurs doit être modifiée, les mappages doivent inclure les drapeaux u ou g pour spécifier qu'ils s'appliquent uniquement aux UID ou aux GID et ne doivent pas être copiés.

    Drapeau Exemple Description
    u u20000:2000:1 Le mappage s'applique uniquement aux UID
    g g10000:1000:1 Le mappage s'applique uniquement aux GID

    Par exemple, étant donné la commande

    podman run --gidmap "0:0:1000" --gidmap "g2000:2000:1"

    Comme aucun --uidmap n'est donné, le --gidmap est copié vers --uidmap, ce qui donne une commande équivalente à

    podman run --gidmap "0:0:1000" --gidmap "2000:2000:1" --uidmap "0:0:1000"

    Le --gidmap "g2000:2000:1" a utilisé le drapeau g et par conséquent, il n'a pas été copié vers --uidmap.

    Mappage sans privilèges d'ID de groupe hôtes supplémentaires

    Un utilisateur sans privilèges peut souhaiter mapper un groupe hôte spécifique qui a déjà été subordonné dans /etc/subgid sans spécifier le reste du mappage.

    Cela peut être fait avec --gidmap "+gID_groupe_conteneur:@ID_groupe_hôte"

    Où :

    • L'ID de groupe hôte est donné via le symbole @
    • Le mappage de cet ID de groupe n'est pas copié vers --usermap grâce au drapeau g.
    • Le reste des ID de conteneur sera mappé à partir de 0 à n, avec tous les ID de groupe subordonnés restants, grâce au drapeau +.

    Par exemple, si un utilisateur appartient au groupe 2000 et que ce groupe est subordonné à cet utilisateur (avec usermod --add-subgids 2000-2000 $USER), l'utilisateur peut mapper le groupe dans le conteneur avec : --gidmap=+g100000:@2000.

    Si ce mappage est combiné avec l'option --group-add=keep-groups, le processus dans le conteneur appartiendra au groupe 100000, et les fichiers appartenant au groupe 2000 sur l'hôte apparaîtront comme étant détenus par le groupe 100000 à l'intérieur du conteneur.

    podman run --group-add=keep-groups --gidmap="+g100000:@2000" ...

    Pas d'UID subordonnés

    Même si un utilisateur n'a pas d'UID subordonnés dans /etc/subuid, --uidmap peut être utilisé pour mapper l'UID normal de l'utilisateur à un UID de conteneur en exécutant podman run --uidmap $uid_conteneur:0:1 --user $uid_conteneur ....

    Pods

    L'option --uidmap ne peut pas être appelée en conjonction avec l'option --pod car un uidmap ne peut pas être défini au niveau du conteneur lorsqu'il est dans un pod.

    --ulimit=option

    Options Ulimit. Définit les valeurs de ulimits à l'intérieur du conteneur.

    --ulimit avec une limite souple et une limite stricte au format =[:]. Par exemple :

    $ podman run --ulimit nofile=1024:1024 --rm ubi9 ulimit -n 1024

    Définir -1 pour la limite souple ou stricte afin de définir la limite à la limite maximale du processus actuel. En mode rootful, c'est souvent illimité.

    Si nofile et nproc ne sont pas définis, une valeur par défaut de 1048576 sera utilisée, sauf indication contraire dans containers.conf(5). Cependant, si la valeur par défaut dépasse la limite stricte pour l'utilisateur sans privilèges actuel, la limite stricte actuelle sera appliquée à la place.

    Utilisez host pour copier la configuration actuelle de l'hôte.

    N'utilisez pas nproc avec le drapeau ulimit car Linux utilise nproc pour définir le nombre maximum de processus disponibles pour un utilisateur, pas pour un conteneur.

    Utilisez l'option --pids-limit pour modifier le contrôle cgroup afin de limiter le nombre de processus dans un conteneur.

    --umask=umask

    Définit l'umask à l'intérieur du conteneur. Par défaut, 0022. Les connexions à distance utilisent le fichier containers.conf local pour les valeurs par défaut.

    --unsetenv=env

    Supprime les variables d'environnement par défaut pour le conteneur. Les variables d'environnement par défaut incluent les variables fournies nativement par Podman, les variables d'environnement configurées par l'image, et les variables d'environnement de containers.conf.

    --unsetenv-all

    Supprime toutes les variables d'environnement par défaut pour le conteneur. Les variables d'environnement par défaut incluent les variables fournies nativement par Podman, les variables d'environnement configurées par l'image, et les variables d'environnement de containers.conf.

    --user, -u=utilisateur[:groupe]

    Définit le nom d'utilisateur ou l'UID utilisé et, facultativement, le nom de groupe ou le GID pour la commande spécifiée. L'utilisateur et le groupe peuvent être symboliques ou numériques.

    Sans cet argument, la commande s'exécute en tant qu'utilisateur spécifié dans l'image du conteneur. Sauf indication contraire par une commande USER dans le Containerfile ou par une valeur passée à cette option, cet utilisateur est généralement root par défaut.

    Lorsqu'un espace de noms utilisateur n'est pas utilisé, l'UID et le GID utilisés dans le conteneur et sur l'hôte correspondent. Lorsque des espaces de noms utilisateur sont utilisés, cependant, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte. Dans les conteneurs sans privilèges, par exemple, un espace de noms utilisateur est toujours utilisé, et root dans le conteneur correspond par défaut à l'UID et au GID de l'utilisateur qui invoque Podman.

    --userns=mode

    Définit le mode d'espace de noms utilisateur pour le conteneur.

    Si --userns n'est pas défini, la valeur par défaut est déterminée comme suit : - Si --pod est défini, --userns est ignoré et l'espace de noms utilisateur du pod est utilisé. - Si la variable d'environnement PODMAN_USERNS est définie, sa valeur est utilisée. - Si userns est spécifié dans containers.conf, cette valeur est utilisée. - Sinon, --userns=host est supposé.

    --userns="" (c'est-à-dire une chaîne vide) est un alias pour --userns=host.

    Cette option est incompatible avec --gidmap, --uidmap, --subuidname et --subgidname.

    Mappages de clés --userns pour utilisateurs sans privilèges :

    Clé Utilisateur hôte Utilisateur conteneur
    auto $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)
    host $UID 0 (Le compte utilisateur par défaut est mappé à l'utilisateur root dans le conteneur.)
    keep-id $UID $UID (Mappe le compte utilisateur au même UID dans le conteneur.)
    keep-id:uid=200,gid=210 $UID 200:210 (Mappe le compte utilisateur à l'UID et au GID spécifiés dans le conteneur.)
    nomap $UID nil (L'UID de l'utilisateur hôte n'est pas mappé dans le conteneur.)

    Les valeurs valides pour mode sont :

    auto[:OPTIONS,...]: crée automatiquement un espace de noms utilisateur unique.

    • mode rootful : Le drapeau --userns=auto exige que le nom d'utilisateur containers soit spécifié dans les fichiers /etc/subuid et /etc/subgid, avec une plage inutilisée d'ID utilisateur subordonnés que les conteneurs Podman sont autorisés à allouer. Exemple : containers:2147483647:2147483648.
    • mode sans privilèges : Les plages d'utilisateurs des fichiers /etc/subuid et /etc/subgid seront utilisées. Notez que l'exécution d'un seul conteneur sans utiliser --userns=auto utilisera toute la plage d'UID et ne permettra pas de subdiviser davantage. Voir subuid(5).

    Podman alloue des plages uniques d'UID et de GID à partir des ID utilisateur subordonnés containers. La taille des plages est basée sur le nombre d'UID requis dans l'image. Le nombre d'UID et de GID peut être remplacé par l'option size.

    L'option --userns=keep-id utilise tous les subuid et subgid de l'utilisateur. L'option --userns=nomap utilise tous les subuid et subgid de l'utilisateur, à l'exception de l'ID propre de l'utilisateur. Utiliser --userns=auto lors du démarrage de nouveaux conteneurs ne fonctionne pas tant qu'il existe des conteneurs qui ont été démarrés avec --userns=nomap ou --userns=keep-id sans limiter la taille de l'espace de noms utilisateur.

    Options valides pour auto :

    • gidmapping=GID_CONTENEUR:GID_HOTE:TAILLE : pour forcer un mappage de GID à être présent dans l'espace de noms utilisateur.
    • size=TAILLE : pour spécifier une taille explicite pour l'espace de noms utilisateur automatique. par exemple, --userns=auto:size=8192. Si size n'est pas spécifié, Spécifié, auto estime une taille pour l'espace de noms utilisateur.
    • uidmapping=CONTAINER_UID:HOST_UID:SIZE : pour forcer un mappage UID à être présent dans l'espace de noms utilisateur.

    L'UID et le GID hôtes dans gidmapping et uidmapping peuvent être précédés du symbole @. Dans ce cas, Podman recherchera l'ID intermédiaire correspondant à l'ID hôte et mappera l'ID intermédiaire trouvé à l'ID du conteneur. Pour plus de détails, voir --uidmap.

    container:id : rejoindre l'espace de noms utilisateur du conteneur spécifié.

    host ou "" (chaîne vide) : exécuter dans l'espace de noms utilisateur de l'appelant. Les processus exécutés dans le conteneur ont les mêmes privilèges sur l'hôte que tout autre processus lancé par l'utilisateur appelant.

    keep-id : crée un espace de noms utilisateur où l'UID:GID de l'utilisateur courant est mappé aux mêmes valeurs dans le conteneur. Pour les conteneurs créés par root, le mappage actuel est créé dans un nouvel espace de noms utilisateur.

    De plus, le processus d'initialisation dans le conteneur s'exécutera sous l'UID de l'utilisateur courant. Ce comportement remplace l'instruction USER de l'image, sauf si vous définissez explicitement --user.

    Options valides pour keep-id :

    • uid=UID : remplace l'UID à l'intérieur du conteneur qui est utilisé pour mapper l'utilisateur courant.
    • gid=GID : remplace le GID à l'intérieur du conteneur qui est utilisé pour mapper l'utilisateur courant.
    • size=SIZE : remplace la taille de l'espace de noms utilisateur configuré. Il est utile de ne pas saturer tous les ID disponibles. Non pris en charge lors de l'exécution en tant que root.

    nomap : crée un espace de noms utilisateur où l'UID:GID de l'utilisateur rootless courant n'est pas mappé dans le conteneur. Cette option n'est pas autorisée pour les conteneurs créés par l'utilisateur root.

    ns:namespace : exécuter le conteneur dans l'espace de noms utilisateur existant donné.

    --uts=mode

    Définit le mode de l'espace de noms UTS pour le conteneur. Les valeurs suivantes sont prises en charge :

    • host : utilise l'espace de noms UTS de l'hôte à l'intérieur du conteneur.
    • private : crée un nouvel espace de noms pour le conteneur (par défaut).
    • ns:[chemin] : exécute le conteneur dans l'espace de noms UTS existant donné.
    • container:[conteneur] : rejoint l'espace de noms UTS du conteneur spécifié.

    --variant=VARIANT

    Utilise VARIANT au lieu de la variante d'architecture par défaut de l'image du conteneur. Certaines images peuvent utiliser plusieurs variantes des architectures ARM, telles que arm/v5 et arm/v7.

    --volume, -v=[[SOURCE-VOLUME|RÉPERTOIRE-HÔTE:]RÉPERTOIRE-CONTENEUR[:OPTIONS]]

    Crée un montage bind. Si -v /RÉPERTOIRE-HÔTE:/RÉPERTOIRE-CONTENEUR est spécifié, Podman monte /RÉPERTOIRE-HÔTE de l'hôte dans /RÉPERTOIRE-CONTENEUR dans le conteneur Podman. De même, -v SOURCE-VOLUME:/RÉPERTOIRE-CONTENEUR monte le volume nommé depuis l'hôte dans le conteneur. Si aucun volume nommé n'existe, Podman en crée un. Si aucune source n'est donnée, le volume est créé en tant que volume anonyme avec un nom généré aléatoirement, et il est supprimé lorsque le conteneur est supprimé via l'option --rm ou la commande podman rm --volumes.

    (Note : lors de l'utilisation du client distant, y compris les machines Mac et Windows (à l'exclusion de WSL2), les volumes sont montés depuis le serveur distant, pas nécessairement depuis la machine cliente.)

    Les OPTIONS sont une liste séparée par des virgules et peut être une ou plusieurs des options suivantes :

    • rw|ro
    • z|Z
    • [O]
    • [U]
    • [no]copy
    • [no]dev
    • [no]exec
    • [no]suid
    • [r]bind
    • [r]shared|[r]slave|[r]private[r]unbindable [1] ⟨#Note1⟩
    • idmap[=options]

    Le RÉPERTOIRE-CONTENEUR doit être un chemin absolu tel que /src/docs. Le volume est monté dans le conteneur à ce répertoire.

    Si une source de volume est spécifiée, il doit s'agir d'un chemin sur l'hôte ou du nom d'un volume nommé. Les chemins d'hôte peuvent être absolus ou relatifs ; les chemins relatifs sont résolus par rapport au répertoire dans lequel Podman est exécuté. Si la source n'existe pas, Podman renvoie une erreur. Les utilisateurs doivent pré-créer les fichiers ou répertoires sources.

    Toute source qui ne commence pas par . ou / est traitée comme le nom d'un volume nommé. Si un volume portant ce nom n'existe pas, il est créé. Les volumes créés avec des noms ne sont pas anonymes, et ils ne sont pas supprimés par l'option --rm et la commande podman rm --volumes.

    Spécifiez plusieurs options -v pour monter un ou plusieurs volumes dans un conteneur.

    Montages de volumes protégés en écriture

    Ajoutez l'option :ro ou :rw pour monter un volume en mode lecture seule ou lecture-écriture, respectivement. Par défaut, les volumes sont montés en lecture-écriture. Voir les exemples.

    Changement de propriétaire des montages de volumes

    Lorsqu'un volume nommé est monté pour la première fois sur un conteneur, Podman ajuste automatiquement la propriété du point de montage du volume lors de l'initialisation du conteneur. Cette opération de chown se produit dans les conditions suivantes :

    • Le volume n'a pas encore été utilisé (a NeedsChown défini sur true)
    • Le volume est vide ou n'a pas encore été copié
    • Le volume n'est pas géré par un pilote de volume externe
    • Le pilote de volume n'est pas "image"

    Pour les volumes avec des montages idmapped (utilisant l'option idmap), le changement de propriété prend en compte les mappages d'espace de noms utilisateur du conteneur, mais le volume idmapped conserve un mappage UID/GID correct. Pour les volumes sans idmapping, le point de montage est chowné pour correspondre à l'utilisateur et au groupe du processus du conteneur, mappé à l'espace de noms utilisateur hôte si le remappage de l'espace de noms utilisateur est activé.

    Si un conteneur est créé dans un nouvel espace de noms utilisateur, l'UID et le GID dans le conteneur peuvent correspondre à un autre UID et GID sur l'hôte.

    Le suffixe :U indique à Podman d'utiliser l'UID et le GID hôtes corrects basés sur l'UID et le GID à l'intérieur du conteneur, pour changer récursivement le propriétaire et le groupe du volume source. Chowning parcourt le système de fichiers sous le volume et change l'UID/GID sur chaque fichier. Si le volume contient des milliers d'inodes, ce processus prend beaucoup de temps, retardant le démarrage du conteneur.

    Attention : utiliser avec prudence car cela modifie le système de fichiers hôte.

    Labellisation des montages de volumes

    Les systèmes de labellisation comme SELinux nécessitent que des labels appropriés soient placés sur le contenu du volume monté dans un conteneur. Sans label, le système de sécurité pourrait empêcher les processus exécutés dans le conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les labels définis par le système d'exploitation.

    Pour changer un label dans le contexte du conteneur, ajoutez l'un des deux suffixes :z ou :Z au montage du volume. Ces suffixes indiquent à Podman de relabelliser les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux conteneurs ou plus partagent le contenu du volume. En conséquence, Podman labellise le contenu avec un label de contenu partagé. Les labels de volume partagés permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman de labelliser le contenu avec un label privé non partagé. Seul le conteneur actuel peut utiliser un volume privé.

    Note : tous les conteneurs d'un pod partagent le même label SELinux. Cela signifie que tous les conteneurs de ce pod peuvent lire/écrire les volumes partagés dans le conteneur créé avec :Z sur l'un des conteneurs. Le relabelling parcourt le système de fichiers sous le volume et change le label sur chaque fichier ; si le volume contient des milliers d'inodes, ce processus prend beaucoup de temps, retardant le démarrage du conteneur. Si le volume a été précédemment relabellisé avec l'option z, Podman est optimisé pour ne pas relabelliser une seconde fois. Si des fichiers sont déplacés dans le volume, les labels peuvent être modifiés manuellement avec la commande chcon -Rt container_file_t CHEMIN.

    Note : ne relabellisez pas les fichiers et répertoires système. Le relabelling de contenu système peut entraîner l'échec d'autres services contraints sur la machine. Pour ces types de conteneurs, nous recommandons de désactiver la séparation SELinux. L'option --security-opt label=disable désactive la séparation SELinux pour le conteneur. Par exemple, si un utilisateur voulait monter l'intégralité de son répertoire personnel dans un conteneur, il doit désactiver la séparation SELinux.

    $ podman run --security-opt label=disable -v $HOME:/home/user fedora touch /home/user/file

    Montages de volumes en superposition

    Le drapeau :O indique à Podman de monter le répertoire de l'hôte comme stockage temporaire en utilisant le système de fichiers overlay. Les processus du conteneur peuvent modifier le contenu du point de montage, qui est stocké dans le stockage du conteneur dans un répertoire séparé. En termes d'overlay, le répertoire source est le inférieur, et le répertoire de stockage du conteneur est le supérieur. Les modifications apportées au point de montage sont détruites lorsque le conteneur a terminé son exécution, similaire au démontage d'un point de montage tmpfs.

    Pour les utilisateurs avancés, l'option overlay prend également en charge des upperdir et workdir personnalisés non volatils pour le montage en superposition. Les upperdir et workdir personnalisés peuvent être entièrement gérés par les utilisateurs eux-mêmes, et Podman ne les supprime pas à la fin du cycle de vie. Exemple : :O,upperdir=/some/upper,workdir=/some/work

    Les exécutions ultérieures du conteneur verront le contenu du répertoire source d'origine, toute modification des exécutions précédentes du conteneur n'existera plus.

    Un cas d'utilisation du montage en superposition est le partage du cache de paquets de l'hôte dans le conteneur pour accélérer les builds.

    Note : le drapeau O entre en conflit avec les autres options listées ci-dessus.

    Le contenu monté dans le conteneur est labellisé avec le label privé. Sur les systèmes SELinux, les labels dans le répertoire source doivent être lisibles par le label du conteneur. Généralement, les conteneurs peuvent lire/exécuter container_share_t et peuvent lire/écrire container_file_t. Si les labels ne peuvent pas être changés sur un volume source, la séparation SELinux du conteneur doit être désactivée pour que le conteneur fonctionne.

    Ne modifiez pas le répertoire source monté dans le conteneur avec un montage en superposition, cela peut entraîner des échecs inattendus. Ne modifiez le répertoire qu'après la fin de l'exécution du conteneur.

    Propagation des montages

    Par défaut, les volumes montés en bind sont privés. Cela signifie que tous les montages effectués dans le conteneur ne sont pas visibles sur l'hôte et vice versa. On peut changer ce comportement en spécifiant une propriété de propagation de montage de volume. Lorsqu'un volume est partagé, les montages effectués sous ce volume dans le conteneur sont visibles sur l'hôte et vice versa. Création d'un volume esclave[1] ⟨#Footnote1⟩ n'active la propagation des montages que dans un seul sens : les montages effectués sur l'hôte sous ce volume sont visibles à l'intérieur du conteneur, mais pas l'inverse.

    Pour contrôler la propriété de propagation des montages d'un volume, on peut utiliser les indicateurs de propagation [r]partagé, [r]esclave, [r]privé ou [r]non-liable. La propriété de propagation ne peut être spécifiée que pour les volumes montés par liaison (bind mounts) et non pour les volumes internes ou nommés. Pour que la propagation des montages fonctionne, le point de montage source (le point de montage où le répertoire source est monté) doit avoir les bonnes propriétés de propagation. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le point de montage source doit être soit partagé, soit esclave. [1] ⟨#Footnote1⟩

    Pour monter un volume et tous ses sous-montages de manière récursive dans un conteneur, utilisez l'option rbind. Par défaut, l'option bind est utilisée, et les sous-montages du répertoire source ne sont pas montés dans le conteneur.

    Monter le volume avec une option copie indique à podman de copier le contenu du répertoire de destination sous-jacent sur les volumes internes nouvellement créés. La copie n'a lieu que lors de la création initiale du volume. Le contenu n'est pas copié lorsque le volume est utilisé ultérieurement sur différents conteneurs. L'option copie est ignorée sur les montages par liaison (bind mounts) et n'a aucun effet.

    Monter les volumes avec l'option nosuid signifie que les exécutables SUID sur le volume ne peuvent pas être utilisés par les applications pour changer leurs privilèges. Par défaut, les volumes sont montés avec nosuid.

    Monter le volume avec l'option noexec signifie qu'aucun exécutable sur le volume ne peut être exécuté dans le conteneur.

    Monter le volume avec l'option nodev signifie qu'aucun périphérique sur le volume ne peut être utilisé par les processus à l'intérieur du conteneur. Par défaut, les volumes sont montés avec nodev.

    Si HOST-DIR est un point de montage, alors les options dev, suid et exec sont ignorées par le noyau.

    Utilisez df HOST-DIR pour trouver le montage source, puis utilisez findmnt -o TARGET,PROPAGATION source-mount-dir pour trouver les propriétés de propagation du montage source. Si l'utilitaire findmnt(1) n'est pas disponible, alors on peut regarder l'entrée de montage pour le point de montage source dans /proc/self/mountinfo. Regardez les « champs optionnels » et voyez si des propriétés de propagation sont spécifiées. Là, shared:N signifie que le montage est partagé, master:N signifie que le montage est esclave, et si rien n'est présent, le montage est privé. [1] ⟨#Footnote1⟩

    Pour modifier les propriétés de propagation d'un point de montage, utilisez la commande mount(8). Par exemple, si l'on veut monter par liaison le répertoire source /foo, on peut faire mount --bind /foo /foo et mount --make-private --make-shared /foo. Cela convertit /foo en un point de montage partagé. Alternativement, on peut modifier directement les propriétés de propagation du montage source. Disons que / est le montage source pour /foo, alors utilisez mount --make-shared / pour convertir / en un montage partagé.

    Remarque : si l'utilisateur n'a des droits d'accès que via un groupe, l'accès au volume depuis un conteneur sans privilèges (rootless) échoue.

    Montage idmapped

    Si idmap est spécifié, créez un montage idmapped vers l'espace de noms d'utilisateur cible dans le conteneur. L'option idmap prend en charge un mappage personnalisé qui peut être différent de l'espace de noms d'utilisateur utilisé par le conteneur. Le mappage peut être spécifié après l'option idmap comme suit : idmap=uids=0-1-10#10-11-10;gids=0-100-10. Pour chaque triplet, la première valeur est le début des ID du système de fichiers sous-jacent qui sont mappés à la deuxième valeur sur l'hôte. La longueur de ce mappage est donnée par la troisième valeur. Plusieurs plages sont séparées par #.

    Utilisez l'option --group-add keep-groups pour passer l'accès aux groupes supplémentaires de l'utilisateur dans le conteneur.

    --volumes-from=CONTENEUR[:OPTIONS]

    Monte les volumes du ou des conteneurs spécifiés. Utilisé pour partager des volumes entre conteneurs. Les options est une liste séparée par des virgules avec les éléments suivants disponibles :

    • rw|ro
    • z

    Monte les volumes déjà montés d'un conteneur source vers un autre conteneur. CONTENEUR peut être un nom ou un ID. Pour partager un volume, utilisez l'option --volumes-from lors de l'exécution du conteneur cible. Les volumes peuvent être partagés même si le conteneur source n'est pas en cours d'exécution.

    Par défaut, Podman monte les volumes dans le même mode (lecture-écriture ou lecture seule) qu'ils sont montés dans le conteneur source. Cela peut être modifié en ajoutant une option ro ou rw.

    Les systèmes d'étiquetage comme SELinux exigent que des étiquettes appropriées soient placées sur le contenu du volume monté dans un conteneur. Sans étiquette, le système de sécurité peut empêcher les processus s'exécutant à l'intérieur du conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par l'OS.

    Pour modifier une étiquette dans le contexte du conteneur, ajoutez z au montage du volume. Ce suffixe indique à Podman de réétiqueter les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux entités partagent le contenu du volume. Par conséquent, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagé permettent à tous les conteneurs de lire/écrire le contenu.

    Si l'emplacement du volume du conteneur source chevauche les données résidant sur un conteneur cible, le volume masque ces données sur la cible.

    --workdir, -w=dir

    Répertoire de travail à l'intérieur du conteneur.

    Le répertoire de travail par défaut pour l'exécution des binaires dans un conteneur est le répertoire racine (/). Le développeur de l'image peut définir une valeur par défaut différente avec l'instruction WORKDIR. L'opérateur peut remplacer le répertoire de travail en utilisant l'option -w.

    Statut de sortie

    Le code de sortie de podman run fournit des informations sur la raison pour laquelle le conteneur n'a pas pu s'exécuter ou pourquoi il s'est terminé. Lorsque podman run se termine avec un code non nul, les codes de sortie suivent le standard chroot(1), voir ci-dessous :

    125 L'erreur concerne Podman lui-même

    $ podman run --foo busybox; echo $?
Error: unknown flag: --foo
125

    126 La commande contenue ne peut pas être invoquée

    $ podman run busybox /etc; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"/etc\": permission denied": OCI runtime error
126

    127 La commande contenue est introuvable

    $ podman run busybox foo; echo $?
Error: container_linux.go:346: starting container process caused "exec: \"foo\": executable file not found in $PATH": OCI runtime error
127

    Code de sortie Code de sortie de la commande contenue

    $ podman run busybox /bin/sh -c 'exit 3'; echo $?
3

    EXEMPLES

    Exécution d'un conteneur en mode lecture seule

    Pendant le développement d'images de conteneurs, les conteneurs ont souvent besoin d'écrire dans le contenu de l'image. Par exemple, en installant des paquets dans /usr. En production, les applications ont rarement besoin d'écrire dans l'image. Les applications de conteneur écrivent dans des volumes si elles ont besoin d'écrire sur des systèmes de fichiers. Les applications peuvent être rendues plus sécurisées en les exécutant en mode lecture seule à l'aide du commutateur --read-only. Cela protège l'image du conteneur contre les modifications. Par défaut, les conteneurs en lecture seule peuvent écrire dans des données temporaires. Podman monte un tmpfs sur /run et /tmp à l'intérieur du conteneur.

    $ podman run --read-only -i -t fedora /bin/bash

    Si le conteneur n'écrit sur aucun système de fichiers à l'intérieur du conteneur, y compris tmpfs, définissez --read-only-tmpfs=false.

    $ podman run --read-only --read-only-tmpfs=false --tmpfs /run -i -t fedora /bin/bash

    Exposition des bibliothèques partagées à l'intérieur du conteneur en lecture seule à l'aide d'un glob

    $ podman run --mount type=glob,src=/usr/lib64/libnvidia\*,ro=true -i -t fedora /bin/bash

    Exposition des messages de log du conteneur au log de l'hôte

    Monter par liaison le répertoire /dev/log pour que les messages enregistrés dans le conteneur apparaissent dans syslog/journal de l'hôte.

    $ podman run -v /dev/log:/dev/log -i -t fedora /bin/bash

    Depuis l'intérieur du conteneur, testez ceci en envoyant un message au log.

    (bash)# logger "Hello from my container"

    Ensuite, quittez et vérifiez le journal.

    (bash)# exit
$ journalctl -b | grep Hello

    Cela liste le message envoyé au logger.

    Attachement à un ou plusieurs à partir de STDIN, STDOUT, STDERR

    Sans spécifier l'option -a, Podman attache tout (stdin, stdout, stderr). Remplacez le comportement par défaut en spécifiant -a (stdin, stdout, stderr), comme suit :

    $ podman run -a stdin -a stdout -i -t fedora /bin/bash

    Mappage des ports pour une utilisation externe

    Le port exposé d'une application peut être mappé sur un port hôte à l'aide du drapeau -p. Par exemple, le port 80 d'httpd peut être mappé sur le port hôte 8080 en utilisant la commande suivante :

    $ podman run -p 8080:80 -d -i -t fedora/httpd

    Montage de volumes externes

    Pour monter un répertoire hôte en tant que volume de conteneur, spécifiez le chemin absolu du répertoire et le chemin absolu du répertoire de conteneur séparés par un deux-points. Si la source est un volume nommé géré par Podman, il est recommandé d'utiliser son nom plutôt que le chemin vers le volume. Sinon, le volume est considéré comme orphelin et effacé par la commande podman volume prune :

    $ podman run -v /var/db:/data1 -i -t fedora bash
$ podman run -v data:/data2 -i -t fedora bash
$ podman run -v /var/cache/dnf:/var/cache/dnf:O -ti fedora dnf -y update

    Si le conteneur a besoin d'un volume monté inscriptible par un utilisateur non root à l'intérieur du conteneur, utilisez l'option U. Cette option indique à Podman de changer le propriétaire du volume source pour qu'il corresponde à l'UID et au GID par défaut utilisés dans le conteneur.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id -v ~/data:/var/lib/mysql:Z,U mariadb

    Alternativement, si le conteneur a besoin d'un volume inscriptible par un utilisateur non root à l'intérieur du conteneur, l'option --userns=keep-id permet aux utilisateurs de spécifier l'UID et le GID de l'utilisateur exécutant Podman sur des UIDs et GIDs spécifiques dans le conteneur. Étant donné que les processus s'exécutant dans le conteneur tournent en tant qu'UID de l'utilisateur, ils peuvent lire/écrire des fichiers appartenant à l'utilisateur.

    $ podman run -d -e MARIADB_ROOT_PASSWORD=root --user mysql --userns=keep-id:uid=999,gid=999 -v ~/data:/var/lib/mysql:Z mariadb

    En utilisant les drapeaux --mount pour monter un répertoire hôte comme dossier de conteneur, spécifiez le chemin absolu du répertoire ou le nom du volume, et le chemin absolu dans le répertoire du conteneur :

    $ podman run --mount type=bind,src=/var/db,target=/data1 busybox sh
$ podman run --mount type=bind,src=volume-name,target=/data1 busybox sh

    Lorsque vous utilisez SELinux, sachez que l'hôte n'a aucune connaissance de la politique SELinux du conteneur. Par conséquent, dans l'exemple ci-dessus, si la politique SELinux est appliquée, le répertoire /var/db n'est pas inscriptible par le conteneur. Un message "Permission Denied" apparaît, et un message avc: est ajouté au syslog de l'hôte.

    Pour contourner ce problème, au moment de la rédaction de cette page de manuel, la commande suivante doit être exécutée afin que le type d'étiquette de politique SELinux approprié soit attaché au répertoire hôte :

    $ chcon -Rt svirt_sandbox_file_t /var/db

    Maintenant, l'écriture dans le volume /data1 dans le conteneur est autorisée et les changements se reflètent sur l'hôte dans /var/db.

    Utilisation d'un étiquetage de sécurité alternatif

    Remplacez le schéma d'étiquetage par défaut pour chaque conteneur en spécifiant le drapeau --security-opt. Par exemple, spécifiez le niveau MCS/MLS, une exigence pour les systèmes MLS. La spécification du niveau dans la commande suivante permet de partager le même contenu entre les conteneurs.

    podman run --security-opt label=level:s0:c100,c200 -i -t fedora bash

    Un exemple MLS pourrait être :

    $ podman run --security-opt label=level:TopSecret -i -t rhel7 bash

    Pour désactiver l'étiquetage de sécurité pour ce conteneur par opposition à l'exécution avec le

    drapeau --permissive, utilisez la commande suivante :

    $ podman run --security-opt label=disable -i -t fedora bash

    Renforcez la politique de sécurité sur les processus à l'intérieur d'un conteneur en spécifiant un type alternatif pour le conteneur. Par exemple, exécutez un conteneur autorisé uniquement à écouter sur les ports Apache en exécutant la commande suivante :

    $ podman run --security-opt label=type:svirt_apache_t -i -t centos bash

    Notez qu'une politique SELinux définissant un type svirt_apache_t doit être rédigée.

    Pour masquer des chemins spécifiques supplémentaires dans le conteneur, spécifiez les chemins séparés par deux-points en utilisant l'option mask avec le drapeau --security-opt.

    $ podman run --security-opt mask=/foo/bar:/second/path fedora bash

    Pour démasquer tous les chemins masqués par défaut, définissez l'option unmask sur ALL. Ou pour ne démasquer que des chemins spécifiques, spécifiez les chemins comme indiqué ci-dessus avec l'option mask.

    $ podman run --security-opt unmask=ALL fedora bash

    Pour démasquer tous les chemins commençant par /proc, définissez l'option unmask sur /proc/*.

    $ podman run --security-opt unmask=/proc/* fedora bash
    $ podman run --security-opt unmask=/foo/bar:/sys/firmware fedora bash

    $ podman run -it --blkio-weight-device "/dev/sda:200" ubuntu

    Définition de paramètres du noyau en espace de noms (Sysctls)

    Le drapeau --sysctl définit des paramètres du noyau en espace de noms (sysctls) dans le conteneur. Par exemple, pour activer le transfert IP dans l'espace de noms réseau du conteneur, exécutez cette commande :

    $ podman run --sysctl net.ipv4.ip_forward=1 someimage

    Notez que tous les sysctls ne sont pas en espace de noms. Podman ne prend pas en charge la modification des sysctls à l'intérieur d'un conteneur qui modifie également le système hôte. À mesure que le noyau évolue, nous nous attendons à ce que davantage de sysctls deviennent des espaces de noms.

    Consultez la définition de l'option --sysctl ci-dessus pour la liste actuelle des sysctls pris en charge.

    $ podman run --uidmap 0:30000:7000 --gidmap 0:30000:7000 fedora echo hello

    Conteneurs sans root

    Podman s'exécute en tant qu'utilisateur non root sur la plupart des systèmes. Cette fonctionnalité nécessite qu'une version suffisamment récente de shadow-utils soit installée. Le paquet shadow-utils doit inclure les exécutables newuidmap(1) et newgidmap(1).

    Pour que les utilisateurs puissent exécuter sans root, il doit y avoir une entrée pour leur nom d'utilisateur dans /etc/subuid et /etc/subgid qui liste les UID pour leur espace de noms utilisateur.

    Podman sans root fonctionne mieux si les paquets fuse-overlayfs et slirp4netns sont installés. Le paquet fuse-overlayfs fournit un pilote de stockage overlay en espace utilisateur, sinon les utilisateurs devront utiliser le pilote de stockage vfs, qui peut être coûteux en espace disque et moins performant que d'autres pilotes.

    Pour activer le VPN sur le conteneur, slirp4netns ou pasta doit être spécifié ; sans l'un ou l'autre, les conteneurs doivent être exécutés avec le drapeau --network=host.

    ENVIRONNEMENT

    Les variables d'environnement dans les conteneurs peuvent être définies en utilisant plusieurs options différentes, dans l'ordre de priorité suivant (les entrées ultérieures remplacent les entrées précédentes) :

    • Image du conteneur : toutes les variables d'environnement spécifiées dans l'image du conteneur.
    • --http-proxy : par défaut, plusieurs variables d'environnement sont transmises depuis l'hôte, telles que http_proxy et no_proxy. Voir --http-proxy pour les détails.
    • --env-host : l'environnement hôte du processus exécutant Podman est ajouté.
    • --env-file : toutes les variables d'environnement spécifiées via les fichiers env. Si plusieurs fichiers sont spécifiés, ils se remplacent mutuellement dans l'ordre d'entrée.
    • --env : toutes les variables d'environnement spécifiées remplacent les paramètres précédents.

    Exécutez des conteneurs et définissez l'environnement se terminant par un *. La fonctionnalité globale * n'est active que lorsqu'aucune valeur n'est spécifiée :

    $ export ENV1=a
$ podman run --env 'ENV*' alpine env | grep ENV
ENV1=a
$ podman run --env 'ENV*=b' alpine env | grep ENV
ENV*=b

    CONMON

    Lorsque Podman démarre un conteneur, il exécute en fait le programme conmon, qui à son tour exécute le Runtime OCI. Conmon est le moniteur de conteneur. C'est un petit programme dont le rôle est de surveiller le processus principal du conteneur, et si le conteneur meurt, de sauvegarder le code de sortie. Il maintient également le tty du conteneur ouvert, afin qu'il puisse y être attaché plus tard. C'est ce qui permet à Podman de s'exécuter en mode détaché (en arrière-plan), Podman peut donc se terminer mais conmon continue de s'exécuter. Chaque conteneur a sa propre instance de conmon. Conmon attend que le conteneur se termine, récupère et sauvegarde le code de sortie, puis lance un processus Podman pour terminer le nettoyage du conteneur, en arrêtant le réseau et le stockage. Pour plus d'informations sur conmon, consultez la page de manuel conmon(8).
