NOM

podman-generate-systemd - [DÉPRÉCIÉ] Générer le(s) fichier(s) d'unité systemd pour un conteneur ou un pod

SYNTAXE

podman generate systemd [options] conteneur|pod

DESCRIPTION

DÉPRÉCIÉ : Note : podman generate systemd est déprécié. Nous recommandons d'utiliser les fichiers [Quadlet] lors de l'exécution de conteneurs ou de pods Podman sous systemd. Il n'est pas prévu de supprimer cette commande. Elle recevra des corrections urgentes de bugs mais aucune nouvelle fonctionnalité.

podman generate systemd crée un fichier d'unité systemd qui peut être utilisé pour contrôler un conteneur ou un pod. Par défaut, la commande affiche le contenu des fichiers d'unité sur la sortie standard.

La génération de fichiers d'unité pour un pod nécessite que le pod soit créé avec un conteneur d'infrastructure (voir --infra=true). Un conteneur d'infrastructure s'exécute pendant toute la durée de vie d'un pod et est donc requis pour que systemd gère le cycle de vie de l'unité principale du pod.

  • Note : Lors de l'utilisation de cette commande avec le client distant, y compris les machines Mac et Windows (à l'exception de WSL2), placez les unités générées sur le système distant. De plus, assurez-vous que la variable d'environnement XDG_RUNTIME_DIR est définie. Si elle n'est pas définie, définissez-la via export XDG_RUNTIME_DIR=/run/user/$(id -u).
  • Note : La commande podman run générée contient une option --sdnotify dont la valeur est prise du conteneur. Si le conteneur n'a aucune valeur explicitement définie ou si la valeur est définie sur ignore, la valeur conmon est utilisée. La raison de remplacer la valeur par défaut container est que presque aucune charge de travail de conteneur n'envoie de messages de notification. Systemd attend un message de prêt qui n'arrive jamais, si la valeur container est utilisée pour un conteneur qui n'envoie pas de messages de notification. L'utilisation de la valeur par défaut a pu être involontaire de la part de l'utilisateur, d'où la valeur par défaut remplacée.

Intégration Kubernetes

Un fichier YAML Kubernetes peut être exécuté dans systemd via le modèle systemd podman-kube@.service. L'argument du modèle est le chemin vers le fichier YAML. Étant donné un fichier workload.yaml dans le répertoire personnel, il peut être exécuté comme suit :

$ échappé=$(systemd-escape ~/workload.yaml)
$ systemctl --user start podman-kube@$échappé.service
$ systemctl --user is-active podman-kube@$échappé.service
active

OPTIONS

--after=nom_dépendance

Ajoute l'option d'unité systemd après (After=), qui définit les dépendances d'ordre entre la liste des dépendances et ce service. Cette option peut être spécifiée plusieurs fois.

Les dépendances définies par l'utilisateur sont ajoutées au fichier d'unité généré, mais toute option existante nécessaire ou définie par défaut (par exemple, online.target) n'est pas supprimée ou remplacée.

--container-prefix=préfixe

Définit le préfixe du nom de l'unité systemd pour les conteneurs. Le préfixe par défaut est container.

--env, -e=env

Définit des variables d'environnement dans les fichiers d'unité systemd.

Si une variable d'environnement est spécifiée sans valeur, Podman recherche la valeur dans l'environnement hôte et ne définit la variable que si elle est définie sur l'hôte. Cas spécial : si une variable d'environnement se terminant par * est spécifiée sans valeur, Podman recherche dans l'environnement hôte les variables commençant par ce préfixe et ajoute ces variables aux fichiers d'unité systemd.

--files, -f

Génère des fichiers au lieu d'afficher sur la sortie standard. Les fichiers générés sont nommés {container,pod}-{ID,name}.service et sont placés dans le répertoire de travail actuel.

Note : Sur un système avec SELinux activé, les fichiers générés héritent des contextes du répertoire de travail actuel. Selon la configuration SELinux, des modifications des fichiers générés à l'aide de restorecon, chcon ou semanage peuvent être nécessaires pour permettre à systemd d'accéder à ces fichiers. Alternativement, utilisez l'option -Z lors de l'exécution de mv ou cp.

--format=format

Affiche les unités créées dans le format spécifié (json). Si --files est spécifié, les chemins vers les fichiers créés sont affichés au lieu du contenu de l'unité.

--name, -n

Utilise le nom du conteneur pour le début, l'arrêt et la description dans le fichier d'unité.

--new

Cette option génère des fichiers d'unité qui ne s'attendent pas à ce que les conteneurs et les pods existent. Au lieu de cela, de nouveaux conteneurs et pods sont créés en fonction de leurs fichiers de configuration. Les fichiers d'unité sont créés au mieux et peuvent nécessiter une édition supplémentaire ; veuillez examiner attentivement les fichiers générés avant de les utiliser en production.

Notez que --new ne fonctionne que sur les conteneurs et les pods créés directement via Podman (c'est-à-dire podman [container] {create,run} ou podman pod create). Il ne fonctionne pas sur les conteneurs ou les pods créés via l'API REST ou via podman kube play. Pour podman kube play, utilisez plutôt le modèle systemd podman-kube@.service.

--no-header

Ne génère pas l'en-tête incluant les métadonnées telles que la version de Podman et l'horodatage.

--pod-prefix=préfixe

Définit le préfixe du nom de l'unité systemd pour les pods. Le préfixe par défaut est pod.

--requires=nom_dépendance

Définit l'option systemd requires (Requires=). Semblable à wants, mais déclare une dépendance plus forte.

--restart-policy=politique

Définit la politique de redémarrage systemd. La politique de redémarrage doit être l'une des suivantes : "no", "on-success", "on-failure", "on-abnormal", "on-watchdog", "on-abort", ou "always". La politique par défaut est on-failure sauf si le conteneur a été créé avec une politique de redémarrage personnalisée.

Notez que la génération d'une unité sans --new sur un conteneur avec une politique de redémarrage personnalisée peut entraîner des problèmes à l'arrêt ; systemd tente d'arrêter l'unité pendant que Podman tente de la redémarrer. Il est recommandé de créer le conteneur sans --restart et d'utiliser l'option --restart-policy lors de la génération du fichier d'unité.

--restart-sec=temps

Définit la valeur restartsec du service systemd. Configure le temps d'attente avant de redémarrer un service (tel que configuré avec restart-policy). Prend une valeur en secondes.

--separator=séparateur

Définit le séparateur du nom de l'unité systemd entre le nom/ID d'un conteneur/pod et le préfixe. Le séparateur par défaut est -.

--start-timeout=valeur

Remplace le délai d'attente de démarrage par défaut pour le conteneur avec la valeur donnée en secondes.

--stop-timeout=valeur

Remplace le délai d'attente d'arrêt par défaut pour le conteneur avec la valeur donnée en secondes.

--template

Ajoute des spécificateurs de modèle pour exécuter plusieurs services à partir du fichier d'unité systemd.

Notez que si --new n'a pas été défini sur true, il est défini sur true par défaut. Cependant, la commande échoue si --new est explicitement défini sur false.

--wants=nom_dépendance

Ajoute l'option systemd wants (Wants=), dont ce service dépend (faiblement). Cette option peut être spécifiée plusieurs fois. Cette option n'influence pas l'ordre dans lequel les services sont démarrés ou arrêtés.

Les dépendances définies par l'utilisateur sont ajoutées au fichier d'unité généré, mais toute option existante nécessaire ou définie par défaut (par exemple, online.target) n'est pas supprimée ou remplacée.

EXEMPLES

Générer et afficher un fichier d'unité systemd pour un conteneur

Pour générer un fichier d'unité systemd pour le conteneur nommé `mycontainer` et afficher le résultat sur la sortie standard :

$ podman generate systemd mycontainer

Générer un fichier d'unité systemd pour un pod

Pour générer un fichier d'unité systemd pour le pod nommé `mypod` et afficher le résultat sur la sortie standard :

$ podman generate systemd mypod

Générer des fichiers d'unité systemd pour tous les conteneurs et pods

Pour générer des fichiers d'unité systemd pour tous les conteneurs et pods en cours d'exécution et enregistrer les fichiers dans le répertoire actuel :

$ podman generate systemd --files --name

Générer un fichier d'unité systemd pour un conteneur avec les détails de redémarrage

Pour générer un fichier d'unité systemd pour un conteneur nommé `mycontainer` et définir la politique de redémarrage sur `always` et le temps de redémarrage sur 5 secondes :

$ podman generate systemd --restart-policy=always --restart-sec=5s mycontainer

Générer un fichier d'unité systemd pour un conteneur sans en-tête

Pour générer un fichier d'unité systemd pour le conteneur nommé `mycontainer` sans la section d'en-tête :

$ podman generate systemd --no-header mycontainer

Générer des fichiers d'unité systemd pour des conteneurs en utilisant le nouveau mode

Pour générer des fichiers d'unité systemd pour des conteneurs en utilisant le mode --new :

$ podman generate systemd --new --name --files mycontainer

Générer un fichier d'unité systemd en utilisant le mode template

Pour générer un fichier d'unité systemd pour un conteneur en utilisant le mode --template :

$ podman generate systemd --template mycontainer

Générer des unités systemd en utilisant des dépendances spécifiques

Pour générer un fichier d'unité systemd pour un conteneur nommé `mycontainer` avec des dépendances Wants= et After= spécifiées :

$ podman generate systemd --wants=network-online.target --after=docker.service mycontainer

podman(1), podman-kube(1), systemd.unit(5), systemd.service(5)

NOM

podman-generate-systemd - Générer des fichiers unitaires systemd pour des conteneurs et des pods

SYNTAXE

podman generate systemd [-a | --all] [-f | --files] [-n | --new] [-o | --output file] [-p | --prefix string] [-t | --time seconds] [-h | --help] container ...

DESCRIPTION

La commande podman generate systemd génère des fichiers unitaires systemd pour les conteneurs ou les pods spécifiés. Ces fichiers unitaires peuvent être utilisés pour gérer le cycle de vie des conteneurs et des pods en tant que services systemd.

Par défaut, podman generate systemd imprime le contenu du fichier unitaire systemd sur la sortie standard. Si l'option --files est spécifiée, elle enregistre les fichiers unitaires dans des fichiers distincts et les place dans le répertoire courant.

OPTIONS

podman generate systemd est capable de générer des fichiers unitaires systemd pour un ou plusieurs conteneurs et pods.

Générer un fichier unitaire systemd pour un conteneur

Générer un fichier unitaire systemd pour un conteneur s'exécutant avec nginx, avec une politique de redémarrage toujours et un délai d'expiration de 1 seconde vers stdout. Notez que l'option RequiresMountsFor dans la section Unit garantit que le stockage du conteneur pour le GraphRoot et le RunRoot sont montés avant le démarrage du service. Pour les systèmes avec un stockage de conteneur sur des disques comme iSCSI ou d'autres protocoles de bloc distants, cela garantit que Podman n'est pas exécuté avant que toute opération de stockage nécessaire ne soit opérationnelle.

$ podman create --name nginx nginx:latest
$ podman generate systemd --restart-policy=always -t 1 nginx
# container-de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6.service
# autogenerated by Podman 1.8.0
# Wed Mar 09 09:46:45 CEST 2020
[Unit]
Description=Podman container-de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6.service
Documentation=man:podman-generate-systemd(1)
Wants=network-online.target
After=network-online.target
RequiresMountsFor=/var/run/container/storage
[Service]
Restart=always
ExecStart=/usr/bin/podman start de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6
ExecStop=/usr/bin/podman stop   
        -t 1 de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6
KillMode=none
Type=forking
PIDFile=/run/user/1000/overlay-containers/de1e3223b1b888bc02d0962dd6cb5855eb00734061013ffdd3479d225abacdc6/userdata/conmon.pid
[Install]
WantedBy=default.target

Générer un fichier unitaire systemd pour un conteneur avec le drapeau --new

Le drapeau --new génère des fichiers unitaires systemd qui créent et suppriment des conteneurs lors des commandes de démarrage et d'arrêt du service (voir les actions de service ExecStartPre et ExecStopPost). Ces fichiers unitaires ne sont pas liés à une seule machine et peuvent être facilement partagés et utilisés sur d'autres machines.

$ sudo podman generate systemd --new --files --name bb310a0780ae
# container-busy_moser.service
# autogenerated by Podman 1.8.3
# Fri Apr  3 09:40:47 EDT 2020
[Unit]
Description=Podman container-busy_moser.service
Documentation=man:podman-generate-systemd(1)
Wants=network-online.target
After=network-online.target
RequiresMountsFor=/var/run/container/storage
[Service]
Environment=PODMAN_SYSTEMD_UNIT=%n
Restart=on-failure
ExecStartPre=/bin/rm -f %t/%n-pid %t/%n-cid
ExecStart=/usr/local/bin/podman run   
        --conmon-pidfile %t/%n-pid   
	--cidfile %t/%n-cid   
	--cgroups=no-conmon   
	-d   
	-dit alpine
ExecStop=/usr/local/bin/podman stop   
        --ignore   
        --cidfile %t/%n-cid -t 10
ExecStopPost=/usr/local/bin/podman rm   
        --ignore   
        -f   
	--cidfile %t/%n-cid
PIDFile=%t/%n-pid
KillMode=none
Type=forking
[Install]
WantedBy=default.target

Générer des fichiers unitaires systemd pour un pod avec deux conteneurs alpine simples

Notez que systemctl ne doit être utilisé que sur l'unité de pod et non pour démarrer ou arrêter des conteneurs individuellement. Les conteneurs sont gérés par le service de pod ainsi que par le conteneur d'infrastructure interne.

Utilisez systemctl status ou journalctl pour examiner les fichiers unitaires de conteneur ou de pod.

$ podman pod create --name systemd-pod
$ podman create --pod systemd-pod alpine top
$ podman create --pod systemd-pod alpine top
$ podman generate systemd --files --name systemd-pod
/home/user/pod-systemd-pod.service
/home/user/container-amazing_chandrasekhar.service
/home/user/container-jolly_shtern.service
$ cat pod-systemd-pod.service

Installation des fichiers unitaires systemd générés.

Les fichiers unitaires générés par Podman incluent une section [Install], qui contient des informations d'installation pour l'unité. Elle est utilisée par les commandes enable et disable de systemctl(1) lors de l'installation.

Une fois le fichier unitaire systemd généré, installez-le dans /etc/systemd/system pour qu'il soit exécuté par l'utilisateur root ou dans $HOME/.config/systemd/user pour l'installer en tant qu'utilisateur non root. Activez le ou les fichiers unitaires copiés en utilisant systemctl enable.

Remarque : Copier les fichiers unitaires dans /etc/systemd/system et les activer marque le fichier unitaire pour démarrage automatique au boot. De même, copier un fichier unitaire dans $HOME/.config/systemd/user et l'activer marque le fichier unitaire pour démarrage automatique à la connexion de l'utilisateur.

# Fichiers systemd générés.
$ podman pod create --name systemd-pod
$ podman create --pod systemd-pod alpine top
$ podman generate systemd --files --name systemd-pod
# Copier tous les fichiers générés.
$ sudo cp pod-systemd-pod.service container-great_payne.service /etc/systemd/system
$ systemctl enable pod-systemd-pod.service
Created symlink /etc/systemd/system/multi-user.target.wants/pod-systemd-pod.service → /etc/systemd/system/pod-systemd-pod.service.
Created symlink /etc/systemd/system/default.target.wants/pod-systemd-pod.service → /etc/systemd/system/pod-systemd-pod.service.
$ systemctl is-enabled pod-systemd-pod.service
enabled

Pour exécuter les services utilisateur placés dans $HOME/.config/systemd/user à la première connexion de cet utilisateur, activez le service avec le drapeau --user.

$ systemctl --user enable <.service>

L'instance utilisateur systemd est tuée après la fermeture de la dernière session de l'utilisateur. L'instance utilisateur systemd peut être démarrée au boot et maintenue en cours d'exécution même après la déconnexion de l'utilisateur en activant le lingering en utilisant

$ loginctl enable-linger <username>

Utiliser systemctl pour effectuer des opérations sur les fichiers unitaires installés générés.

Créez et activez des fichiers unitaires systemd pour un pod en utilisant les exemples ci-dessus comme référence et utilisez systemctl pour effectuer des opérations.

Étant donné que systemctl utilise par défaut l'utilisateur root, toutes les modifications effectuées avec systemctl peuvent être vues en ajoutant sudo aux commandes cli de podman. Pour effectuer des actions systemctl en tant qu'utilisateur non root, utilisez le drapeau --user lors de l'interaction avec systemctl.

Remarque : Si les conteneurs ou pods précédemment créés utilisent des ressources partagées, telles que des ports, assurez-vous de les supprimer avant de démarrer les unités systemd générées.

$ systemctl --user start pod-systemd-pod.service
$ podman pod ps
POD ID         NAME          STATUS    CREATED          # OF CONTAINERS   INFRA ID
0815c7b8e7f5   systemd-pod   Running   29 minutes ago   2                 6c5d116f4bbe
$ sudo podman ps # 0 Number of pods on root.
CONTAINER ID  IMAGE  COMMAND  CREATED  STATUS  PORTS  NAMES
$ systemctl stop pod-systemd-pod.service
$ podman pod ps
POD ID         NAME          STATUS   CREATED          # OF CONTAINERS   INFRA ID
272d2813c798   systemd-pod   Exited   29 minutes ago   2                 6c5d116f4bbe

Créez un conteneur alpine simple et générez le fichier unitaire systemd avec le drapeau --new. Activez le service et contrôlez les opérations à l'aide des commandes systemctl.

Remarque : Lors du démarrage du conteneur à l'aide de systemctl start plutôt que de modifier le conteneur déjà en cours d'exécution, il lance un nouveau conteneur avec une configuration similaire.

# Activer le service.
$ sudo podman ps -a

podman-generate-systemd(1)

NOM

podman-generate-systemd - Générer des fichiers d'unité systemd pour les conteneurs ou les pods

SYNOPSIS

podman generate systemd [OPTSION ...]
[--container-name | --pod-name] CONTAINER | POD ...

DESCRIPTION

Génère des fichiers d'unité systemd pour un ou plusieurs conteneurs ou pods Podman. Ces fichiers peuvent être utilisés pour gérer des conteneurs ou des pods avec systemd.

Les options suivantes peuvent être utilisées pour personnaliser la sortie.

OPTIONS

--container-name
Génère un fichier d'unité systemd pour le ou les conteneurs spécifiés par leur nom.
--file <fichier>, -f <fichier>
Écrit la sortie dans le fichier spécifié au lieu de la sortie standard.
--new
Crée un nouveau fichier d'unité systemd. S'il existe déjà, il sera écrasé.
--no-dependencies
N'inclut pas les dépendances système pour le conteneur ou le pod.
--online-heap
Soutient les heap online. Ne pas utiliser sauf si vous savez ce que vous faites.
--pod-name
Génère un fichier d'unité systemd pour le ou les pods spécifiés par leur nom.
--separator <séparateur>
Utilise le séparateur spécifié pour générer plusieurs fichiers d'unité systemd. Le séparateur par défaut est un nouveau saut de ligne.
--start-after <unité>
Ajoute une directive After= à la sortie pour s'assurer que le conteneur ou le pod démarre après l'unité spécifiée.
--template
Génère un fichier d'unité systemd au format modèle. Le nom du fichier sera basé sur le nom du conteneur ou du pod.
--time
Définit la valeur de Time= dans la section [Install] du fichier d'unité systemd.
--user-unit
Génère un fichier d'unité systemd pour une utilisation avec les unités utilisateur de systemd.

EXEMPLES

Générer un fichier d'unité systemd pour un conteneur nommé mon_conteneur et l'écrire dans la sortie standard :

podman generate systemd --container-name mon_conteneur

Générer un fichier d'unité systemd pour un pod nommé mon_pod et l'enregistrer dans mon_pod.service :

podman generate systemd --pod-name mon_pod --file mon_pod.service

Générer un fichier d'unité systemd au format modèle pour un conteneur nommé mon_conteneur :

podman generate systemd --container-name mon_conteneur --template

VOIR AUSSI

podman(1), podman-run(1), systemd.unit(5)
