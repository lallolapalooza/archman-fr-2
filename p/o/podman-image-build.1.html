NOM

podman-build - Construire une image conteneurisée à l'aide d'un Containerfile

SYNOPIS

podman build [options] [contexte]

podman image build [options] [contexte]

DESCRIPTION

podman build Construit une image en utilisant les instructions d'un ou plusieurs Containerfiles ou Dockerfiles et d'un répertoire de contexte de construction spécifié. Un Containerfile utilise en interne la même syntaxe qu'un Dockerfile. Pour ce document, un fichier désigné comme Containerfile peut être nommé 'Containerfile' ou 'Dockerfile' exclusivement. Tout fichier ayant une extension supplémentaire ne sera pas reconnu par podman build . sauf si l'option -f est utilisée pour spécifier le fichier.

Le répertoire de contexte de construction peut être spécifié sous forme d'URL http(s) d'une archive, d'un dépôt git ou d'un Containerfile.

Lorsqu'il est appelé avec -f et un chemin vers un Containerfile, sans répertoire CONTEXT explicite, Podman utilise le répertoire parent du Containerfile comme son contexte de construction.

Les Containerfiles se terminant par le suffixe ".in" sont prétraités via CPP(1). Cela peut être utile pour décomposer les Containerfiles en plusieurs parties réutilisables qui peuvent être utilisées via la directive #include de CPP. Les Containerfiles se terminant par .in sont limités aux lignes sans commentaire, sauf s'il s'agit de commandes CPP. Notez qu'un fichier Containerfile.in peut toujours être utilisé par d'autres outils lors de son prétraitement manuel via cpp -E.

Lorsque l'URL est une archive, le contenu de l'URL est téléchargé dans un emplacement temporaire et extrait avant l'exécution.

Lorsque l'URL est un Containerfile, le Containerfile est téléchargé dans un emplacement temporaire.

Lorsqu'un dépôt Git est défini comme URL, le dépôt est cloné localement puis défini comme contexte. Une URL est traitée comme un dépôt Git si elle a un préfixe git:// ou une suffixe .git.

NOTE : podman build utilise du code provenant du projet Buildah pour construire des images conteneurisées. Ce code Buildah crée des conteneurs Buildah pour les options RUN dans le stockage des conteneurs. Dans certaines situations, lorsque podman build plante ou que les utilisateurs tuent le processus podman build, ces conteneurs externes peuvent rester dans le stockage des conteneurs. Utilisez la commande podman ps --all --external pour voir ces conteneurs.

La commande podman buildx build est un alias de podman build. Toutes les fonctionnalités de buildx build ne sont pas disponibles dans Podman. L'option buildx build est fournie pour la compatibilité de script.

OPTIONS

--add-host=nom_hôte[;nom_hôte[;...]]:ip

Ajoute un mappage personnalisé nom d'hôte vers IP au fichier /etc/hosts du conteneur.

L'option prend un ou plusieurs noms d'hôtes séparés par des points-virgules à mapper à une seule adresse IPv4 ou IPv6, séparés par deux points. Elle peut également être utilisée pour écraser les adresses IP des noms d'hôtes que Podman ajoute à /etc/hosts par défaut (voir également les options --name et --hostname). Cette option peut être spécifiée plusieurs fois pour ajouter des mappages supplémentaires à /etc/hosts. Elle entre en conflit avec l'option --no-hosts et avec no_hosts=true dans containers.conf.

Au lieu d'une adresse IP, le drapeau spécial host-gateway peut être donné. Cela se résout en une adresse IP que le conteneur peut utiliser pour se connecter à l'hôte. L'adresse IP choisie dépend de votre configuration réseau, il n'y a donc aucune garantie que Podman puisse déterminer automatiquement l'adresse host-gateway, ce qui provoquera alors un échec de Podman avec un message d'erreur. Vous pouvez écraser cette adresse IP en utilisant l'option host_containers_internal_ip dans containers.conf.

L'adresse host-gateway est également utilisée par Podman pour ajouter automatiquement les noms d'hôtes host.containers.internal et host.docker.internal à /etc/hosts. Vous pouvez empêcher cela en donnant l'option --no-hosts, ou en définissant host_containers_internal_ip="none" dans containers.conf. Si aucune adresse host-gateway n'a été configurée manuellement et que Podman ne parvient pas à déterminer l'adresse IP automatiquement, Podman omettra silencieusement l'ajout de ces noms d'hôtes internes à /etc/hosts. Si Podman s'exécute dans une machine virtuelle en utilisant podman machine (cela inclut les hôtes Mac et Windows), Podman omettra silencieusement l'ajout des noms d'hôtes internes à /etc/hosts, sauf si une adresse IP a été configurée manuellement ; les noms d'hôtes internes sont résolus par le résolveur DNS gvproxy à la place.

Podman utilisera par défaut le fichier /etc/hosts de l'hôte comme base, c'est-à-dire que tout nom d'hôte présent dans ce fichier sera également présent dans le fichier /etc/hosts du conteneur. Un fichier de base différent peut être configuré en utilisant la configuration base_hosts_file dans containers.conf.

--all-platforms

Au lieu de construire pour un ensemble de plateformes spécifiées à l'aide de l'option --platform, inspecter les images de base de la construction, et construire pour toutes les plateformes pour lesquelles elles sont toutes disponibles. Les étapes qui utilisent scratch comme point de départ ne peuvent pas être inspectées, donc au moins une étape non-scratch doit être présente pour que la détection fonctionne utilement.

--annotation=annotation=valeur

Ajoute une annotation à l'image (par exemple, annotation=valeur) aux métadonnées de l'image. Peut être utilisé plusieurs fois.

Note : ces informations ne sont pas présentes dans les formats d'image Docker, elles sont donc supprimées lors de l'écriture d'images au format Docker.

--arch=arch

Définit l'architecture de l'image à construire, et celle de l'image de base à extraire, si la construction en utilise une, à la valeur fournie au lieu d'utiliser l'architecture de l'hôte de construction. Sauf indication contraire, les recherches ultérieures de la même image dans le stockage local correspondent à cette architecture, indépendamment de l'hôte. (Exemples : arm, arm64, 386, amd64, ppc64le, s390x)

--authfile=chemin

Chemin du fichier d'authentification. Par défaut, il s'agit de ${XDG_RUNTIME_DIR}/containers/auth.json sous Linux, et de $HOME/.config/containers/auth.json sous Windows/macOS. Le fichier est créé par podman login. Si l'état d'autorisation n'y est pas trouvé, $HOME/.docker/config.json est vérifié, qui est défini à l'aide de docker login.

Note : Il existe également l'option pour écraser le chemin par défaut du fichier d'authentification en définissant la variable d'environnement REGISTRY_AUTH_FILE. Cela peut être fait avec export REGISTRY_AUTH_FILE=chemin.

--build-arg=arg=valeur

Spécifie un argument de construction et sa valeur, qui est interpolé dans les instructions lues depuis les Containerfiles de la même manière que les variables d'environnement, mais qui ne sont pas ajoutées à la liste des variables d'environnement dans la configuration de l'image résultante.

--build-arg-file=chemin

Spécifie un fichier contenant des lignes d'arguments de construction de la forme arg=valeur. Le nom de fichier suggéré est argfile.conf.

Les lignes de commentaire commençant par # sont ignorées, ainsi que les lignes vides. Toutes les autres doivent être du format arg=valeur passé à --build-arg.

Si plusieurs arguments sont fournis via les options --build-arg-file et --build-arg, les arguments de construction sont fusionnés à travers tous les fichiers et arguments de ligne de commande fournis.

Tout fichier fourni dans une option --build-arg-file est lu avant les arguments fournis via l'option --build-arg.

Lorsqu'un nom d'argument donné est spécifié plusieurs fois, la dernière instance est celle qui est passée aux constructions résultantes. Cela signifie que les valeurs --build-arg remplacent toujours celles d'un --build-arg-file.

--build-context=nom=valeur

Spécifie un contexte de construction supplémentaire en utilisant son nom court et son emplacement. Les contextes de construction supplémentaires peuvent être référencés de la même manière que nous accédons à différentes étapes dans l'instruction COPY.

Les valeurs valides sont :

  • Répertoire local – par exemple, --build-context project2=../chemin/vers/project2/src
  • URL HTTP vers une archive tar – par exemple, --build-context src=https://example.org/releases/src.tar
  • Image conteneur – spécifiée avec un préfixe container-image://, par exemple --build-context alpine=container-imag

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

e://alpine:3.15, (accepte aussi docker://, docker-image://)

Côté Containerfile, référencez le contexte de build sur toutes les commandes qui acceptent le paramètre “from”. Voici à quoi cela pourrait ressembler :

FROM [nom]
COPY --from=[nom] ...
RUN --mount=from=[nom] …

La valeur de [nom] est recherchée selon l'ordre de priorité suivant :

  • Contexte de build nommé défini avec --build-context [nom]=..
  • Étape définie avec AS [nom] dans Containerfile
  • Image [nom], locale ou dans un registre distant

--cache-from=image

Dépôt à utiliser comme source de cache potentielle. Lorsqu'il est spécifié, Buildah essaie de rechercher des images de cache dans le dépôt spécifié et tente de tirer des images de cache au lieu d'exécuter réellement les étapes de build localement. Buildah tente seulement de tirer des images précédemment mises en cache si elles sont considérées comme des succès de cache valides.

Utilisez l'option --cache-to pour peupler un dépôt distant avec du contenu de cache.

Exemple

# peupler un cache et le consulter également
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Note : L'option --cache-from est ignorée à moins que --layers ne soit spécifié.

--cache-to=image

Définissez ce drapeau pour spécifier un dépôt distant utilisé pour stocker les images de cache. Buildah tente de pousser l'image de cache nouvellement construite vers le dépôt distant.

Note : Utilisez l'option --cache-from pour utiliser le contenu du cache dans un dépôt distant.

Exemple

# peupler un cache et le consulter également
buildah build -t test --layers --cache-to registry/myrepo/cache --cache-from registry/myrepo/cache .

Note : L'option --cache-to est ignorée à moins que --layers ne soit spécifié.

--cache-ttl

Limitez l'utilisation des images mises en cache pour ne considérer que les images dont les horodatages de création sont inférieurs à durée. Par exemple, si --cache-ttl=1h est spécifié, Buildah considère les images de cache intermédiaires créées dans la durée d'une heure, et les images de cache intermédiaires en dehors de cette durée sont ignorées.

Note : Définir manuellement --cache-ttl=0 équivaut à utiliser --no-cache dans l'implémentation, car cela signifie que l'utilisateur ne souhaite pas utiliser le cache du tout.

--cap-add=CAP_xxx

Lors de l'exécution des instructions RUN, exécutez la commande spécifiée dans l'instruction avec la capacité spécifiée ajoutée à son ensemble de capacités. Certaines capacités sont accordées par défaut ; cette option peut être utilisée pour en ajouter d'autres.

--cap-drop=CAP_xxx

Lors de l'exécution des instructions RUN, exécutez la commande spécifiée dans l'instruction avec la capacité spécifiée retirée de son ensemble de capacités. Les capacités CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_FOWNER, CAP_FSETID, CAP_KILL, CAP_NET_BIND_SERVICE, CAP_SETFCAP, CAP_SETGID, CAP_SETPCAP et CAP_SETUID sont accordées par défaut ; cette option peut être utilisée pour les retirer.

Si une capacité est spécifiée pour les options --cap-add et --cap-drop, elle est supprimée, quel que soit l'ordre dans lequel les options ont été données.

--cert-dir=chemin

Utilisez les certificats situés dans chemin (*.crt, *.cert, *.key) pour vous connecter au registre. (Par défaut : /etc/containers/certs.d) Pour plus de détails, voir containers-certs.d(5). (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (hors WSL2))

--cgroup-parent=chemin

Chemin vers les cgroups sous lequel le cgroup pour le conteneur est créé. Si le chemin n'est pas absolu, il est considéré comme relatif au chemin cgroups du processus init. Les cgroups sont créés s'ils n'existent pas déjà.

--cgroupns=comment

Définit la configuration des espaces de noms cgroup lors du traitement des instructions RUN. La valeur configurée peut être une chaîne vide ("") ou "private" pour indiquer qu'un nouvel espace de noms cgroup est créé, ou elle peut être "host" pour indiquer que l'espace de noms cgroup dans lequel buildah lui-même est exécuté est réutilisé.

--compat-volumes

Gère les répertoires marqués à l'aide de l'instruction VOLUME (à la fois dans ce build et ceux hérités des images de base) de telle sorte que leur contenu ne puisse être modifié que par les instructions ADD et COPY. Toute modification apportée à ces emplacements par des instructions RUN sera annulée. Avant l'introduction de cette option, ce comportement était le défaut, mais il est maintenant désactivé par défaut.

--compress

Cette option est ajoutée pour s'aligner sur les autres CLIs de conteneurs. Podman ne communique pas avec un démon ou un serveur distant. Par conséquent, la compression des données avant leur envoi est sans intérêt pour Podman. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (hors WSL2))

--cpp-flag=indicateurs

Définissez des indicateurs supplémentaires à passer au préprocesseur C cpp(1). Les Containerfiles se terminant par le suffixe ".in" sont prétraités via cpp(1). Cette option peut être utilisée pour passer des indicateurs supplémentaires à cpp. Note : Vous pouvez également définir des CPPFLAGS par défaut en définissant la variable d'environnement BUILDAH_CPPFLAGS (par exemple, export BUILDAH_CPPFLAGS="-DDEBUG").

--cpu-period=limite

Définit la période CPU pour le Completely Fair Scheduler (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié pour s'exécuter avant la fin de la période en cours. La valeur par défaut est de 100000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--cpu-quota=limite

Limite le quota CPU du Completely Fair Scheduler (CFS).

Limite l'utilisation du CPU du conteneur. Par défaut, les conteneurs s'exécutent avec la pleine ressource CPU. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser ce temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--cpu-shares, -c=parts

Parts de CPU (poids relatif).

Par défaut, tous les conteneurs obtiennent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est 1024.

La proportion ne s'applique que lorsque des processus gourmands en CPU s'exécutent. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, l'un avec une part de CPU de 1024 et les deux autres avec un réglage de part de CPU de 512. Lorsque les processus des trois conteneurs tentent d'utiliser 100 % du CPU, le premier conteneur reçoit 50 % du temps CPU total. Si un quatrième conteneur est ajouté avec une part de CPU de 1024, le premier conteneur ne reçoit que 33 % du CPU. Les conteneurs restants reçoivent 16,5 %, 16,5 % et 33 % du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont réparties sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100 % du temps CPU, il peut utiliser 100 % de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la répartition suivante des parts CPU :

PID conteneur CPU Part CPU
100 C0 0 100% du CPU0
101 C1 1 100% du CPU1
102 C1 2 100% du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par exemple, 0,1), de plage (par exemple, 0-3), ou toute combinaison des deux (par exemple, 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Uniquement efficace sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1, alors les processus du conteneur n'utiliseront la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut

y pas autorisé pour les utilisateurs non root. Pour plus de détails, voir https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes sans root cgroups V1.

--created-annotation

Ajoute une annotation d'image (voir également --annotation) aux métadonnées de l'image, définissant « org.opencontainers.image.created » à l'heure actuelle, ou à la date spécifiée avec le drapeau --source-date-epoch ou --timestamp, si l'un d'eux a été utilisé. Si false, aucune annotation de ce type ne sera présente dans l'image écrite.

Remarque : ces informations ne sont pas présentes dans les formats d'image Docker, elles sont donc ignorées lors de l'écriture d'images au format Docker.

--creds=[nom d'utilisateur[:mot de passe]]

Le [nom d'utilisateur[:mot de passe]] à utiliser pour s'authentifier auprès du registre, si nécessaire. Si une ou deux valeurs ne sont pas fournies, une invite de commande apparaît et la valeur peut être saisie. Le mot de passe est saisi sans écho.

Notez que les informations d'identification spécifiées sont uniquement utilisées pour s'authentifier auprès des registres cibles. Elles ne sont pas utilisées pour les miroirs ou lorsque le registre est réécrit (voir containers-registries.conf(5)) ; pour vous authentifier auprès de ceux-ci, envisagez d'utiliser un fichier containers-auth.json(5).

--cw=options

Produit une image adaptée à une utilisation en tant que charge de travail confidentielle s'exécutant dans un environnement d'exécution de confiance (TEE) à l'aide de krun (c'est-à-dire crun compilé avec la fonctionnalité libkrun activée et appelé en tant que krun). Au lieu du contenu conventionnel, le système de fichiers racine de l'image contiendra une image disque chiffrée et des informations de configuration pour krun.

La valeur de options est une liste de paires clé=valeur séparées par des virgules, fournissant les informations de configuration nécessaires à la production des données supplémentaires qui seront incluses dans l'image du conteneur.

Les clés reconnues sont :

attestation_url : L'emplacement d'un serveur d'attestation / courtier de clés. Si une valeur est spécifiée, l'identifiant de charge de travail de la nouvelle image, ainsi que la phrase secrète utilisée pour chiffrer l'image disque, seront enregistrés auprès du serveur, et l'emplacement du serveur sera stocké dans l'image du conteneur. Au moment de l'exécution, krun est censé contacter le serveur pour récupérer la phrase secrète en utilisant l'identifiant de charge de travail, qui est également stocké dans l'image du conteneur. Si aucune valeur n'est spécifiée, une valeur passphrase doit être spécifiée.

cpus : Le nombre de CPU virtuels avec lesquels l'image est censée s'exécuter au moment de l'exécution. S'il n'est pas spécifié, une valeur par défaut sera fournie.

firmware_library : L'emplacement de la bibliothèque partagée libkrunfw-sev. S'il n'est pas spécifié, buildah vérifie sa présence dans un certain nombre d'emplacements codés en dur.

memory : La quantité de mémoire avec laquelle l'image est censée s'exécuter au moment de l'exécution, en nombre de mégaoctets. S'il n'est pas spécifié, une valeur par défaut sera fournie.

passphrase : La phrase secrète à utiliser pour chiffrer l'image disque qui sera incluse dans l'image du conteneur. Si aucune valeur n'est spécifiée, mais qu'une valeur attestation_url est spécifiée, une phrase secrète générée aléatoirement sera utilisée. Les auteurs recommandent de définir une attestation_url mais pas une passphrase.

slop : Espace supplémentaire à allouer pour l'image disque par rapport à la taille du contenu de l'image du conteneur, exprimé soit en pourcentage (..%), soit en valeur de taille (octets, ou unités plus grandes si des suffixes comme KB ou MB sont présents), soit en somme de deux spécifications ou plus. S'il n'est pas spécifié, buildah suppose que 25 % d'espace supplémentaire par rapport au contenu seront suffisants, mais cette option est fournie au cas où son estimation serait incorrecte.

type : Le type d'environnement d'exécution de confiance (TEE) pour lequel l'image doit être marquée. Les valeurs acceptées sont « SEV » (AMD Secure Encrypted Virtualization - Encrypted State) et « SNP » (AMD Secure Encrypted Virtualization - Secure Nested Paging). S'il n'est pas spécifié, la valeur par défaut est « SNP ».

workload_id : Un identifiant de charge de travail qui sera enregistré dans l'image du conteneur, à utiliser au moment de l'exécution pour récupérer la phrase secrète utilisée pour chiffrer l'image disque. S'il n'est pas spécifié, une valeur semi-aléatoire sera dérivée de l'ID de l'image de base.

Cette option n'est pas prise en charge sur le client distant, y compris les machines Mac et Windows (à l'exception de WSL2).

--decryption-key=clé[:phrase secrète]

La [clé[:phrase secrète]] à utiliser pour le déchiffrement des images. La clé peut pointer vers des clés et/ou des certificats. Le déchiffrement est essayé avec toutes les clés. Si la clé est protégée par une phrase secrète, elle doit être passée dans l'argument et omise sinon.

--device=périphérique hôte[:périphérique conteneur][:permissions]

Ajoute un périphérique hôte au conteneur. Le paramètre facultatif permissions peut être utilisé pour spécifier les permissions du périphérique en combinant r pour lecture, w pour écriture et m pour mknod(2).

Exemple : --device=/dev/sdc:/dev/xvdc:rwm.

Remarque : si périphérique hôte est un lien symbolique, il est d'abord résolu. Le conteneur ne stocke que les numéros majeurs et mineurs du périphérique hôte.

Podman peut charger les modules du noyau requis pour utiliser le périphérique spécifié. Les périphériques pour lesquels Podman charge des modules si nécessaire sont : /dev/fuse.

En mode sans root, le nouveau périphérique est monté par liaison dans le conteneur depuis l'hôte plutôt que Podman ne le crée dans l'espace du conteneur. Comme le montage par liaison conserve son étiquette SELinux sur les systèmes SELinux, le conteneur peut recevoir une erreur de permission lors de l'accès au périphérique monté. Modifiez les paramètres SELinux pour autoriser les conteneurs à utiliser toutes les étiquettes de périphérique via la commande suivante :

$ sudo setsebool -P container_use_devices=true

Remarque : si l'utilisateur n'a des droits d'accès que via un groupe, l'accès au périphérique depuis un conteneur sans root échoue. Le runtime crun(1) offre une solution de contournement en ajoutant l'option --annotation run.oci.keep_original_groups=1.

--disable-compression, -D

Ne pas compresser les couches de système de fichiers lors de la construction de l'image, sauf si cela est requis par l'emplacement où l'image est écrite. C'est le réglage par défaut, car les couches d'image sont compressées automatiquement lorsqu'elles sont envoyées aux registres, et les images écrites dans le stockage local n'ont besoin d'être décompressées qu'à nouveau pour être stockées. La compression peut être forcée dans tous les cas en spécifiant --disable-compression=false.

--disable-content-trust

    Lors de la génération de SBOMs, les analyse à la recherche d'informations PURL (package URL ⟨https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst⟩), et enregistre une liste des PURL trouvées dans le chemin spécifié dans l'image de sortie. Il n'y a pas de valeur par défaut.

    --sbom-merge-strategy=méthode

    Si plusieurs valeurs --sbom-scanner-command sont utilisées, utilise la méthode spécifiée pour fusionner la sortie des commandes ultérieures avec la sortie des commandes précédentes. Les valeurs reconnues incluent :

    • cat
      Concatène les fichiers.
    • merge-cyclonedx-by-component-name-and-version
      Fusionne les champs "component" des documents JSON, en ignorant les valeurs des
      documents lorsque la combinaison de leurs valeurs "name" et "version" est
      déjà présente. Les documents sont traités dans l'ordre où ils sont
      générés, ce qui correspond à l'ordre dans lequel les commandes qui les génèrent
      ont été spécifiées.
    • merge-spdx-by-package-name-and-versioninfo
      Fusionne les champs "package" des documents JSON, en ignorant les valeurs des
      documents lorsque la combinaison de leurs valeurs "name" et "versionInfo" est
      déjà présente. Les documents sont traités dans l'ordre où ils sont
      générés, ce qui correspond à l'ordre dans lequel les commandes qui les génèrent
      ont été spécifiées.

    Lors de la génération de SBOMs, les analyse à la recherche d'informations PURL (package URL ⟨https://github.com/package-url/purl-spec/blob/master/PURL-SPECIFICATION.rst⟩), et enregistre une liste des PURL trouvées dans le fichier nommé dans le système de fichiers local. Il n'y a pas de valeur par défaut.

    --sbom-scanner-command=image

    Génère des SBOMs en exécutant la commande spécifiée depuis l'image du scanner. Si plusieurs commandes sont spécifiées, elles sont exécutées dans l'ordre où elles sont spécifiées. Ces substitutions de texte sont effectuées :

    - {CONTEXT}

    - {OUTPUT}

    --secret=id=id[,src=envOuFichier][,env=ENV][,type=fichier | env]

    Transmet des informations secrètes à utiliser dans le Containerfile pour construire des images de manière sécurisée, qui ne seront pas stockées dans l'image finale, ni vues dans d'autres étapes. La valeur du secret sera lue à partir d'une variable d'environnement ou d'un fichier nommé par l'option "id", ou nommé par l'option "src" si elle est spécifiée, ou à partir d'une variable d'environnement spécifiée par l'option "env". Voir EXEMPLES ⟨#examples⟩. Le secret sera monté dans le conteneur à /run/secrets/id par défaut.

    Pour utiliser ultérieurement le secret, utilisez l'option --mount dans une instruction RUN au sein d'un Containerfile :

    RUN --mount=type=secret,id=monsecret cat /run/secrets/monsecret

    L'emplacement du secret dans le conteneur peut être remplacé en utilisant l'option "target", "dst", ou "destination" de l'option RUN --mount.

    RUN --mount=type=secret,id=monsecret,target=/run/secrets/monautresecret cat /run/secrets/monautresecret

    Note : la modification du contenu des fichiers secrets ne déclenchera pas une reconstruction des couches qui utilisent ces secrets.

    --source-date-epoch=secondes

    Définit l'horodatage "created" pour l'image construite au nombre de secondes depuis l'époque (heure Unix 0, c'est-à-dire 00:00:00 UTC le 1er janvier 1970) (par défaut, utilise la valeur définie dans la variable d'environnement SOURCE_DATE_EPOCH, ou l'heure actuelle si elle n'est pas définie).

    L'horodatage "created" est écrit dans la configuration et le manifeste de l'image lors de la validation de l'image, donc exécuter la même construction deux fois de suite produira normalement des images avec des hachages sha256 différents, même si aucun autre changement n'a été apporté au Containerfile et au contexte de construction.

    Lorsque cette option est définie, un argument de construction SOURCE_DATE_EPOCH fournira sa valeur pour une étape dans laquelle il est déclaré.

    Lorsque cette option est définie, l'horodatage "created" de la configuration de l'image est toujours défini sur l'heure spécifiée, ce qui devrait permettre de construire des images identiques à différents moments en utilisant le même ensemble d'entrées.

    Lorsque cette option est définie, la sortie écrite comme spécifié dans l'option --output portera exactement l'horodatage spécifié.

    , qui définit également son heure spécifiée sur le contenu des nouvelles couches.

    --timestamp=secondes

    Définit l'horodatage de création en secondes depuis l'époque pour permettre des constructions déterministes (par défaut, heure actuelle). Par défaut, l'horodatage de création est modifié et écrit dans le manifeste de l'image à chaque commit, ce qui entraîne une modification du hachage sha256 de l'image même si les sources sont par ailleurs exactement les mêmes.     Changer la propriété des montages de volume

    Par défaut, Podman ne modifie pas le propriétaire et le groupe des répertoires sources montés. Lors de l'exécution à l'aide d'espaces de noms utilisateur, l'UID et le GID à l'intérieur de l'espace de noms peuvent

    correspond à un autre UID et GID sur l'hôte.

    Le suffixe :U indique à Podman d'utiliser l'UID et le GID corrects de l'hôte en fonction de l'UID et du GID à l'intérieur de l'espace de noms, pour modifier récursivement le propriétaire et le groupe du volume source.

    Attention à utiliser avec prudence car cela modifie le système de fichiers de l'hôte.

    Labellisation des montages de volumes

    Les systèmes de labellisation comme SELinux nécessitent que des labels appropriés soient placés sur le contenu du volume monté dans un conteneur. Sans label, le système de sécurité pourrait empêcher les processus exécutés dans le conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les labels définis par l'OS.

    Pour modifier un label dans le contexte du conteneur, ajoutez l'un de ces deux suffixes :z ou :Z au montage du volume. Ces suffixes indiquent à Podman de relabéliser les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux conteneurs partagent le contenu du volume. En conséquence, Podman étiquette le contenu avec un label de contenu partagé. Les labels de volume partagé permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman d'étiqueter le contenu avec un label privé non partagé. Seul le conteneur actuel peut utiliser un volume privé.

    Note : Ne relabélisez pas les fichiers et répertoires système. La relabélisation du contenu système pourrait entraîner l'échec d'autres services confinés sur la machine hôte. Pour ces types de conteneurs, il est recommandé de désactiver la séparation SELinux. L'option --security-opt label=disable désactive la séparation SELinux pour le conteneur. Par exemple, si un utilisateur voulait monter son répertoire personnel entier dans les conteneurs de build, il doit désactiver la séparation SELinux.

    $ podman build --security-opt label=disable -v $HOME:/home/user .

    Montages de volumes superposés

    Le drapeau :O indique à Podman de monter le répertoire de l'hôte comme stockage temporaire en utilisant le système de fichiers Overlay. Les conteneurs de la commande RUN sont autorisés à modifier le contenu à l'intérieur du point de montage et celui-ci est stocké dans le stockage du conteneur dans un répertoire séparé. En termes d'Overlay FS, le répertoire source est le niveau inférieur (lower) et le répertoire de stockage du conteneur est le niveau supérieur (upper). Les modifications du point de montage sont détruites lorsque la commande RUN a fini de s'exécuter, de manière similaire à un point de montage tmpfs.

    Toute exécution ultérieure des commandes RUN verra le contenu du répertoire source original, les modifications des commandes RUN précédentes n'existeront plus.

    Un cas d'utilisation du montage overlay est le partage du cache de paquets de l'hôte dans le conteneur pour accélérer les builds.

    Note :

    • Les montages Overlay ne sont actuellement pas pris en charge en mode rootless.
    • Le drapeau O ne peut pas être spécifié avec les drapeaux Z ou z. Le contenu monté dans le conteneur est labellisé avec le label privé. Sur les systèmes SELinux, les labels dans le répertoire source doivent être lisibles par le label du conteneur. Sinon, la séparation des conteneurs SELinux doit être désactivée pour que le conteneur fonctionne.
    • La modification du répertoire du volume monté dans le conteneur avec un montage overlay peut entraîner des échecs inattendus. Ne modifiez pas le répertoire avant que le conteneur ait fini de s'exécuter.

    Par défaut, les volumes bind-montés sont privés. Cela signifie que tout montage effectué à l'intérieur des conteneurs n'est pas visible sur l'hôte et vice versa. Ce comportement peut être modifié en spécifiant une propriété de propagation de montage de volume.

    Lorsque la politique de propagation de montage est définie sur shared, tout montage effectué à l'intérieur du conteneur sur ce volume est visible par l'hôte et le conteneur. Lorsque la politique de propagation de montage est définie sur slave, la propagation de montage unidirectionnelle est activée et tout montage effectué sur l'hôte pour ce volume n'est visible qu'à l'intérieur du conteneur. Pour contrôler la propriété de propagation de montage du volume, utilisez le drapeau de propagation :[r]shared, :[r]slave ou :[r]private. Pour que la propagation de montage fonctionne, le point de montage source (point de montage où le répertoire source est monté) doit avoir les bonnes propriétés de propagation. Pour les volumes partagés, le point de montage source doit être partagé. Et pour les volumes esclaves, le montage source doit être soit partagé, soit esclave. [1] ⟨#Footnote1⟩

    Utilisez df <source-dir> pour déterminer le montage source, puis utilisez findmnt -o TARGET,PROPAGATION <source-mount-dir> pour déterminer les propriétés de propagation du montage source. Si l'utilitaire findmnt n'est pas disponible, le point de montage source peut être déterminé en examinant l'entrée de montage dans /proc/self/mountinfo. Regardez les champs optionnels et voyez si des propriétés de propagation sont spécifiées. shared:X signifie que le montage est partagé, master:X signifie que le montage est esclave et s'il n'y a rien, cela signifie que le montage est privé. [1] ⟨#Footnote1⟩

    Pour modifier les propriétés de propagation d'un point de montage, utilisez la commande mount. Par exemple, pour bind-monter le répertoire source /foo, exécutez mount --bind /foo /foo puis mount --make-private --make-shared /foo. Ceci convertit /foo en un point de montage partagé. Les propriétés de propagation du montage source peuvent être modifiées directement. Par exemple, si / est le montage source pour /foo, alors utilisez mount --make-shared / pour convertir / en un montage partagé.

    EXEMPLES

    Construire une image en utilisant des Containerfiles locaux

    Construire une image en utilisant un Containerfile avec le contenu du répertoire courant :

    $ podman build .

    Construire une image en utilisant un Containerfile spécifié avec le contenu du répertoire courant :

    $ podman build -f Containerfile.simple .

    Construire une image en utilisant un Containerfile depuis stdin avec le contenu du répertoire courant :

    $ cat $HOME/Containerfile | podman build -f - .

    Construire une image en utilisant plusieurs Containerfiles avec le contenu du répertoire courant :

    $ podman build -f Containerfile.simple -f Containerfile.notsosimple .

    Construire une image en utilisant un Containerfile spécifié avec le contenu du répertoire $HOME. Notez que cpp est appliqué au Containerfile.in avant d'être traité comme un Containerfile :

    $ podman build -f Containerfile.in $HOME

    Construire une image avec le tag spécifié en utilisant un Containerfile et le contenu du répertoire courant :

    $ podman build -t imageName .

    Construire une image en ignorant la vérification des registres pour toutes les images tirées via le Containerfile :

    $ podman build --tls-verify=false -t imageName .

    Construire une image avec le format de journalisation spécifié :

    $ podman build --runtime-flag log-format=json .

    Construire une image en utilisant le mode de débogage pour la journalisation :

    $ podman build --runtime-flag debug .

    Construire une image en utilisant les attributs de registre spécifiés lors du tirage des images du Containerfile sélectionné :

    $ podman build --authfile /tmp/auths/myauths.json --cert-dir $HOME/auth --tls-verify=true --creds=username:password -t imageName -f Containerfile.simple .

    Construire une image en utilisant les contrôles de ressources spécifiés lors de l'exécution des conteneurs pendant la construction :

    $ podman build --memory 40m --cpu-period 10000 --cpu-quota 50000 --ulimit nofile=1024:1028 -t imageName .

    Construire une image en utilisant les labels SELinux et la configuration cgroup spécifiés pour les conteneurs en cours d'exécution pendant la construction :

    $ podman build --security-opt label=level:s0:c100,c200 --cgroup-parent /path/to/cgroup/parent -t imageName .

    Construire une image avec un volume monté en lecture seule et relabélisé SELinux depuis l'hôte vers les conteneurs en cours d'exécution pendant la construction :

    $ podman build --volume /home/test:/myvol:ro,Z -t imageName .

    Construire une image avec un volume overlay monté depuis l'hôte vers les conteneurs en cours d'exécution pendant la construction :

    $ podman build -v /var/lib/yum:/var/lib/yum:O -t imageName .

    Construire une image en utilisant des couches, puis en supprimant les conteneurs intermédiaires même si la construction échoue.

    $ podman build --layers --force-rm -t imageName .

    Construire une image en ignorant le cache et sans supprimer les conteneurs intermédiaires même si la construction réussit :

    $ podman build --no-cache --rm=false -t imageName .

    Construire une image en utilisant le réseau spécifié lors de l'exécution des conteneurs pendant la construction :

    $ podman build --network mynet .

    Construire une image en utilisant un secret stocké dans une variable d'environnement ou un fichier nommé mysecret pour être utilisé avec l'instruction RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret :

    $ podman build --secret=id=mysecret .

    Construire une image en utilisant un secret stocké dans une variable d'environnement nommée MYSECRET pour être utilisé avec l'instruction RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret :

    $ podman build --secret=id=mysecret,env=MYSECRET .
$ podman build --secret=id=mysecret,src=MYSECRET,type=env .

    Construire une image en utilisant un secret stocké dans un fichier nommé .mysecret pour être utilisé avec l'instruction RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret :

    $ podman build --secret=id=mysecret,src=.mysecret .
$ podman build --secret=id=mysecret,src=.mysecret,type=file .

    Construction d'une image multi-architecture en utilisant l'option --manifest (nécessite un logiciel d'émulation)

    Construire une image en utilisant les architectures spécifiées et la lier à un seul manifest en cas de succès :

    $ podman build --arch arm --manifest myimage /tmp/mysrc
$ podman build --arch amd64 --manifest myimage /tmp/mysrc
$ podman build --arch s390x --manifest myimage /tmp/mysrc

    De même, construire en utilisant une seule commande

    $ podman build --platform linux/s390x,linux/ppc64le,linux/amd64 --manifest myimage /tmp/mysrc

    Construire une image en utilisant plusieurs architectures spécifiées et la lier à un seul manifest en cas de succès :

    $ podman build --platform linux/arm64 --platform linux/amd64 --manifest myimage /tmp/mysrc

    Construction d'une image en utilisant une URL, un dépôt Git, ou une archive

    Le répertoire de contexte de build peut être spécifié comme une URL vers un Containerfile, un dépôt Git, ou une URL vers une archive. Si l'URL est un Containerfile, il est téléchargé vers un emplacement temporaire et utilisé comme contexte. Lorsqu'un dépôt Git est défini comme URL, le dépôt est cloné localement vers un emplacement temporaire, puis utilisé comme contexte. Enfin, si l'URL est une archive, elle est téléchargée vers un emplacement temporaire et extraite avant d'être utilisée comme contexte.

    Construction d'une image en utilisant une URL vers un Containerfile

    Le contexte de build est la dernière partie de la commande :

    $ podman build Containerfile.tar.gz
$ podman build git://example.com/somerepo.git
$ podman build https://example.com/containerfile.tar.gz

    NAME

    podman-image-build.1.en - Build images using Containerfiles or Dockerfiles

    SYNOPSIS

    podman image build [options] PATH | URL

    DESCRIPTION

    Builds a container image from a Containerfile or Dockerfile. The build process uses the Podman build command. By default, the build context is the directory containing the Containerfile or Dockerfile. Podman supports building images from a URL to a Containerfile, a Git repository, or an archive file.

    EXAMPLES

    Building an image using a URL to a Containerfile

    Build image from Containerfile downloaded into temporary location used as the build context:

    $ podman build https://10.10.10.1/podman/Containerfile

    Building an image using a Git repository

    Podman clones the specified GitHub repository to a temporary location and uses it as the context. The Containerfile at the root of the repository is used and it only works if the GitHub repository is a dedicated repository.

    Build image from specified git repository downloaded into temporary location used as the build context:

    $ podman build -t hello  https://github.com/containers/PodmanHello.git
$ podman run hello

    Note: GitHub does not support using git:// for performing clone operation due to recent changes in their security guidance (https://github.blog/2021-09-01-improving-git-protocol-security-github/). Use an https:// URL if the source repository is hosted on GitHub.

    Building an image using a URL to an archive

    Podman fetches the archive file, decompresses it, and uses its contents as the build context. The Containerfile at the root of the archive and the rest of the archive are used as the context of the build. Passing the -f PATH/Containerfile option as well tells the system to look for that file inside the contents of the archive.

    $ podman build -f dev/Containerfile https://10.10.10.1/podman/context.tar.gz

    Note: supported compression formats are 'xz', 'bzip2', 'gzip' and 'identity' (no compression).

    Files

    .containerignore/.dockerignore

    If the file .containerignore or .dockerignore exists in the context directory, podman build reads its contents. Use the --ignorefile option to override the .containerignore path location. Podman uses the content to exclude files and directories from the context directory, when executing COPY and ADD directives in the Containerfile/Dockerfile

    The .containerignore and .dockerignore files use the same syntax; if both are in the context directory, podman build only uses .containerignore.

    Users can specify a series of Unix shell globs in a .containerignore file to identify files/directories to exclude.

    Podman supports a special wildcard string ** which matches any number of directories (including zero). For example, */.go excludes all files that end with .go that are found in all directories.

    Example .containerignore file:

    # exclude this content for image
*/*.c
**/output*
src

    */*.c Excludes files and directories whose names ends with .c in any top level subdirectory. For example, the source file include/rootless.c.

    **/output* Excludes files and directories starting with output from any directory.

    src Excludes files named src and the directory src as well as any content in it.

    Lines starting with ! (exclamation mark) can be used to make exceptions to exclusions. The following is an example .containerignore file that uses this mechanism:

    *.doc
!Help.doc

    Exclude all doc files except Help.doc from the image.

    This functionality is compatible with the handling of .containerignore files described here: containerignore(5)

    registries.conf (/etc/containers/registries.conf)

    registries.conf is the configuration file which specifies which container registries is consulted when completing image names which do not include a registry or domain portion. See containers-registries.conf(5)

    Troubleshooting

    lastlog sparse file

    Using a useradd command within a Containerfile with a large UID/GID creates a large sparse file /var/log/lastlog. This can cause the build to hang forever. Go language does not support sparse files correctly, which can lead to some huge files being created in the container image.

    When using the useradd command within the build script, pass the --no-log-init or -l option to the useradd command. This option tells useradd to stop creating the lastlog file.
