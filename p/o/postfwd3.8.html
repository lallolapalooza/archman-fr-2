DESCRIPTION

INTRODUCTION

postfwd3 est écrit pour combiner des restrictions postfix complexes dans un ensemble de règles similaire à celles de la plupart des pare-feu. Le programme utilise le protocole de délégation de politique de postfix pour contrôler l'accès au système de messagerie avant qu'un message ne soit accepté (veuillez visiter http://www.postfix.org/SMTPD_POLICY_README.html pour plus d'informations).

postfwd3 vous permet de choisir une action (par exemple, rejeter, dunno) pour une combinaison de plusieurs paramètres smtp (comme l'adresse de l'expéditeur et du destinataire, la taille ou l'empreinte numérique TLS du client). Il offre également des macros/acl simples qui devraient permettre des configurations simples et faciles à lire.

Fonctionnalités :

* Combinaisons complexes de paramètres smtp

* Recherches combinées RBL/RHSBL avec des actions arbitraires en fonction des résultats

* Système de notation

* Règles basées sur la date/heure

* Macros/ACL, groupes dynamiques, négation

* Comparaison des attributs de requête (par exemple, client_name et helo_name)

* Mise en cache interne pour les requêtes et les recherches DNS

* Statistiques intégrées pour l'analyse de l'efficacité des règles

CONFIGURATION

Le programme est initialisé en utilisant les paramètres par défaut, qui peuvent être surchargés en utilisant des options de ligne de commande.

Les règles sont définies en utilisant des paramètres spéciaux (voir l'option -f ou -r).

Les règles sont évaluées dans l'ordre où elles sont spécifiées dans l'ensemble de règles.

EXEMPLE

Voici un petit exemple pour illustrer certaines fonctionnalités :

postfwd3 -f /etc/postfwd.cf -o /var/run/postfwd.pid -d \
  --cache 300 --cleanup-requests 60 \
  --cache_socket tcp:127.0.0.1:10043 --cache_port 10043 \
  --cacheid sender,recipient \
  --plugins /usr/lib/postfwd/plugins.so \
  --default_group_ttl 600 \
  --group_maxitems 1000 \
  --cleanup-groups 60

Ce qui précède démarre postfwd3 en tant que démon, en utilisant /etc/postfwd.cf comme fichier de configuration des règles, en stockant le pid dans /var/run/postfwd.pid. Il active la mise en cache des requêtes pendant 300 secondes et le nettoyage des requêtes toutes les 60 secondes via la socket tcp:127.0.0.1:10043 sur le port 10043. Les requêtes sont mises en cache en utilisant une combinaison de l'expéditeur et du destinataire. Les plugins sont chargés depuis /usr/lib/postfwd/plugins.so. Le TTL par défaut pour les groupes est de 600 secondes, avec un maximum de 1000 éléments par groupe, et le cache des groupes est nettoyé toutes les 60 secondes.

Le fichier de configuration postfwd.cf contiendrait des lignes similaires à celles-ci :

# Règle 1: Rejeter les expéditeurs connus pour du spam
#score = 10
#client_addr = 1.2.3.4
#client_addr = 1.2.3.0/24

# Règle 2: Refuser les destinataires internes si le serveur HELO n'est pas valide
#score = 5
#recipient = *@example.com
#helo_name != example.com

# Règle 3: Vérifier les listes noires DNSBL
#score = 100
#client_ptr = bogus.example.net
#client_ptr = *.bl.example.com

# Règle 4: Définir un score pour les expéditeurs non mis en cache
#score = 2
#sender_net = *
# Action par défaut : autoriser
#score = -1
#sender_net = *

Vous pouvez utiliser l'option --test pour vérifier la configuration de vos règles.

Une fois que postfwd3 est en cours d'exécution, vous devez configurer votre main.cf de postfix pour utiliser le protocole de politique :

# main.cf
smtpd_policy_service_timeout = 10s
smtpd_policy_service_retry_delay = 5s
smtpd_policy_service_max_try = 2
smtpd_policy_service_protocol_timeout = 10s
smtpd_policy_service_reverse_client_lookup = yes

# Utiliser par défaut le service de politique postfwd3
smtpd_policy_service_bind_address = 127.0.0.1:10045
# Ou si vous utilisez un socket Unix :
# smtpd_policy_service_bind_address = unix:/var/run/postfwd.sock

# Vous pouvez également spécifier des actions par défaut pour l'expéditeur et le destinataire.
# Cela est utile si le service de politique ne répond pas.
# smtpd_policy_service_default_action = DUNNO

Veuillez noter que l'option --server_socket peut être utilisée pour spécifier un socket différent du port par défaut 10045.

Vous pouvez également ajouter postfwd3 à la liste des services de politique exécutés en série.

CONFIGURATION

Une ligne de configuration se compose de paires optionnelles élément=valeur, séparées par des points-virgules (`;`) et de l'action souhaitée appropriée :

[ <item1>=<valeur>; <item2>=<valeur>; ... ] action=<résultat>

Exemple :

client_address=192.168.1.1 ; sender==no@bad.local ; action=REJECT

Ceci refusera tout courrier provenant de 192.168.1.1 avec l'expéditeur d'enveloppe no@bad.local. L'ordre des éléments n'a pas d'importance. Ainsi, ce qui suit conduirait au même résultat que l'exemple précédent :

action=REJECT ; client_address=192.168.1.1 ; sender==no@bad.local

La manière dont les éléments de requête sont comparés à l'ensemble de règles peut être influencée de la manière suivante :

====================================================================
 ELEMENT == VALEUR                vrai si ELEMENT est égal à VALEUR
 ELEMENT => VALEUR                vrai si ELEMENT >= VALEUR
 ELEMENT =< VALEUR                vrai si ELEMENT <= VALEUR
 ELEMENT >  VALEUR                vrai si ELEMENT >  VALEUR
 ELEMENT <  VALEUR                vrai si ELEMENT <  VALEUR
 ELEMENT =~ VALEUR                vrai si ELEMENT ~= /^VALEUR$/i
 ELEMENT != VALEUR                faux si ELEMENT est égal à VALEUR
 ELEMENT !> VALEUR                faux si ELEMENT >= VALEUR
 ELEMENT !< VALEUR                faux si ELEMENT <= VALEUR
 ELEMENT !~ VALEUR                faux si ELEMENT ~= /^VALEUR$/i
 ELEMENT =  VALEUR                comportement par défaut (voir la section ÉLÉMENTS)
====================================================================

Pour identifier des règles uniques dans vos fichiers journaux, vous pouvez leur ajouter un identifiant unique :

id=R_001 ; action=REJECT ; client_address=192.168.1.1 ; sender==no@bad.local

Vous pouvez utiliser ces identifiants comme cible pour la commande `jump()` (voir la section ACTIONS ci-dessous). Les espaces de début ou de fin seront ignorés. Utilisez '#' pour commenter votre configuration. Les autres l'apprécieront.

Un ensemble de règles se compose d'une ou plusieurs règles, qui peuvent être chargées à partir de fichiers ou passées en arguments de ligne de commande. Veuillez consulter la section LIGNE DE COMMANDE ci-dessous pour plus d'informations à ce sujet.

Depuis la version 1.30 de postfwd, les règles s'étendant sur plusieurs lignes peuvent être définies en préfixant les lignes suivantes avec un ou plusieurs espaces blancs (ou '}' pour les macros) :

id=RULE001
        client_address=192.168.1.0/24
        sender==no@bad.local
        action=REJECT no access

Les versions de postfwd antérieures à 1.30 nécessitent des ';' et des '\' en fin de ligne :

id=RULE001; \
        client_address=192.168.1.0/24; \
        sender==no@bad.local; \
        action=REJECT no access

ÉLÉMENTS

id                      - un id de règle unique, utilisable pour l'analyse des journaux
                          les id servent également de cibles pour la commande "jump".
date, time              - une plage de date ou d'heure pendant laquelle la règle spécifiée doit être déclenchée
                          # FORMAT :
                          # 29 fév.
                          date=29.02.2008
                          # 24 déc. - 26 déc.
                          date=24.12.2008-26.12.2008
                          # à partir d'aujourd'hui jusqu'au 23 nov.
                          date=-23.09.2008
                          # à partir du 1er avril jusqu'à aujourd'hui
                          date=01.04.2008-
days, months            - une plage de jours de la semaine (Lun-Dim) ou de mois (Jan-Déc)
                          pendant laquelle la règle spécifiée doit être déclenchée
score                   - lorsque le score spécifié est atteint (voir section ACTIONS)
                          l'action spécifiée sera retournée à postfix
                          les scores sont définis globalement jusqu'à redéfinition !
request_score           - cette valeur permet d'accéder au score d'une requête. elle
                          peut être utilisée comme variable ($$request_score).
rbl, rhsbl,             - interroge les RBL/RHSBL spécifiés, les valeurs possibles sont :
rhsbl_client,             <nom>[/<réponse>/<maxcache>, <nom>/<réponse>/<maxcache>]
rhsbl_sender,             (par défaut : réponse=^127\.0\.0\.\d+$ maxcache=3600)
rhsbl_reverse_client      les résultats de toutes les requêtes rhsbl_* seront combinés
                          dans rhsbl_count (voir ci-dessous).
rblcount, rhsblcount    - nombre minimum de succès RBL/RHSBL pour correspondre. si non spécifié
                          un seul succès RBL/RHSBL correspondra aux éléments rbl/rhsbl.
                          vous pouvez spécifier 'all' pour évaluer tous les éléments, et l'utiliser
                          comme variable dans une action (voir section ACTIONS)
                          (par défaut : 1)
sender_localpart,       - la partie locale/domaine de l'adresse de l'expéditeur
sender_domain
recipient_localpart,    - la partie locale/domaine de l'adresse du destinataire
recipient_domain
helo_address            - postfwd3 essaie de rechercher le helo_name. utilisez
                          helo_address=!!(0.0.0.0/0) pour vérifier s'il est inconnu.
                          Veuillez ne pas utiliser ceci pour le contrôle d'accès positif
                          (listes blanches), car il pourrait être falsifié.
sender_ns_names,        - postfwd3 essaie de rechercher les noms/adresses IP
sender_ns_addrs           des serveurs de noms pour la partie domaine de l'expéditeur.
                          Veuillez ne pas utiliser ceci pour le contrôle d'accès positif
                          (listes blanches), car il pourrait être falsifié.
sender_mx_names,        - postfwd3 essaie de rechercher les noms/adresses IP
sender_mx_addrs           des enregistrements mx pour la partie domaine de l'expéditeur.
                          Veuillez ne pas utiliser ceci pour le contrôle d'accès positif
                          (listes blanches), car il pourrait être falsifié.
version                 - version de postfwd3, contient "postfwd3 n.nn"
                          cela permet des vérifications basées sur la version dans vos ensembles de règles
                          (par ex. pour la migration). fonctionne aussi avec les anciennes versions,
                          car un élément inexistant retourne toujours faux :
                          # version >= 1.10
                          id=R01; version~=1\.[1-9][0-9]; sender_domain==some.org \
                                ; action=REJECT désolé pas d'accès
postfwd_port            - port du serveur postfwd, permet d'utiliser le même ensemble de règles pour différentes
                          instances :
                          # la règle ne se déclenche que pour l'instance sur le port 10045
                          id=PORT10045; postfwd_port==10045; action=DUNNO
postfwd_interface       - interface d'initialisation du serveur postfwd, voir postfwd_port
ratecount               - disponible uniquement pour les actions rate(), size() et rcpt().
                          contient le compteur de limite réel :
                                id=R01; action=rate(sender/200/600/REJECT limite de 200 dépassée [$$ratecount hits])
                                id=R02; action=rate(sender/100/600/WARN limite de 100 dépassée [$$ratecount hits])

L'utilisation multiple du même élément est autorisée et sera comparée comme un OU logique, ce qui signifie que ceci fonctionnera comme prévu :

        ccert_fingerprint=11:22:33:44:55:66:77:88:99
        ccert_fingerprint=22:33:44:55:66:77:88:99:00
        ccert_fingerprint=33:44:55:66:77:88:99:00:11
        sender=@domain\.local$

Les éléments client_address, rbl et rhsbl peuvent également être spécifiés comme valeurs séparées par des espaces ou des virgules :

id=SKIP01; action=dunno
        client_address=192.168.1.0/24, 172.16.254.23
id=SKIP02; action=dunno
        client_address= 10.10.3.32 10.216.222.0/27

Les éléments suivants doivent être uniques :

id, valeurs minimum et maximum, rblcount et rhsblcount

Tout élément peut être nié en le préfixant de '!!', par exemple :

id=HOST001 ;  hostname == !!secure.trust.local ;  action=REJECT seulement secure.trust.local s'il vous plaît

ou en utilisant l'opérateur de comparaison approprié :

id=HOST001 ;  hostname != secure.trust.local ;  action=REJECT seulement secure.trust.local s'il vous plaît

Pour éviter toute confusion avec les expressions régulières ou simplement pour une meilleure lisibilité, vous pouvez utiliser '!!(...)' :

id=USER01 ;  sasl_username =~ !!( /^(bob|alice)$/ )  ;  action=REJECT qui est-ce ?

Les attributs de requête peuvent être comparés en les préfixant de '$$', par exemple :

id=R-003 ;  client_name = !! $$helo_name      ;  action=WARN helo ne correspond pas au DNS
# ou
id=R-003 ;  client_name = !!($$(helo_name))   ;  action=WARN helo ne correspond pas au DNS

Ceci n'est valide que pour les valeurs PCRE (voir la liste ci-dessus). La comparaison sera effectuée comme une correspondance exacte insensible à la casse. Utilisez l'option '-vv' pour le débogage.

Ces éléments spéciaux seront réinitialisés pour chaque nouvelle règle :

pre>rblcount - contient le nombre de réponses RBL rhsblcount - contient le nombre de réponses RHSBL matches - contient le nombre d'éléments correspondants dnsbltext - contient la partie TXT DNS de toutes les réponses RBL et RHSBL sous la forme rbltype:rblname:<txt>; rbltype:rblname:<txt>; ...

Ces éléments spéciaux seront modifiés pour toute règle correspondante :

request_hits    - contient les identifiants de toutes les règles correspondantes

Cela signifie qu'il peut être nécessaire de les sauvegarder si vous envisagez d'utiliser ces valeurs dans des règles ultérieures :

# définir les valeurs
id=RBL01 ; rhsblcount=all; rblcount=all
        action=set(HIT_rhls=$$rhsblcount,HIT_rbls=$$rblcount,HIT_txt=$$dnsbltext)
        rbl=list.dsbl.org, bl.spamcop.net, dnsbl.sorbs.net, zen.spamhaus.org
        rhsbl_client=rddn.dnsbl.net.au, rhsbl.ahbl.org, rhsbl.sorbs.net
        rhsbl_sender=rddn.dnsbl.net.au, rhsbl.ahbl.org, rhsbl.sorbs.net
# comparer
id=RBL02 ; HIT_rhls>=1 ; HIT_rbls>=1 ; action=554 5.7.1 bloqué en utilisant $$HIT_rhls RHSBLs et $$HIT_rbls RBLs [INFO: $$HIT_txt]
id=RBL03 ; HIT_rhls>=2               ; action=554 5.7.1 bloqué en utilisant $$HIT_rhls RHSBLs [INFO: $$HIT_txt]
id=RBL04 ; HIT_rbls>=2               ; action=554 5.7.1 bloqué en utilisant $$HIT_rbls RBLs [INFO: $$HIT_txt]

FICHIERS

Depuis postfwd1 v1.15 et postfwd3 v0.18, de longues listes d'éléments peuvent être stockées dans des fichiers séparés :

id=R001 ;  ccert_fingerprint==file:/etc/postfwd/wl_ccerts ;  action=DUNNO

postfwd3 lira une liste d'éléments (un élément par ligne) depuis /etc/postfwd/wl_ccerts. Les commentaires sont autorisés :

# client1
11:22:33:44:55:66:77:88:99
# client2
22:33:44:55:66:77:88:99:00
# client3
33:44:55:66:77:88:99:00:11

Pour utiliser des tables existantes au format clé=valeur, vous pouvez utiliser :

id=R001 ;  ccert_fingerprint==table:/etc/postfwd/wl_ccerts ;  action=DUNNO

Ceci ignorera la valeur de droite. Les éléments peuvent être mélangés :

id=R002 ;  action=REJECT
        client_name==unknown
        client_name==file:/etc/postfwd/blacklisted

et pour les éléments non-pcre (séparés par des virgules) :

id=R003 ;  action=REJECT
        client_address==10.1.1.1, file:/etc/postfwd/blacklisted
id=R004 ;  action=REJECT
        rbl=myrbl.home.local, zen.spamhaus.org, file:/etc/postfwd/rbls_changing

Vous pouvez vérifier votre configuration avec l'option --show_config dans la ligne de commande :

# postfwd3 --showconfig --rule='action=DUNNO; client_address=10.1.0.0/16, file:/etc/postfwd/wl_clients, 192.168.2.1'

devrait donner quelque chose comme :

Rule   0: id->"R-0"; action->"DUNNO"; client_address->"=;10.1.0.0/16, =;194.123.86.10, =;186.4.6.12, =;192.168.2.1"

Si un fichier ne peut pas être lu, il sera ignoré :

# postfwd3 --showconfig --rule='action=DUNNO; client_address=10.1.0.0/16, file:/etc/postfwd/wl_clients, 192.168.2.1'
[LOG warning]: error: file /etc/postfwd/wl_clients not found - file will be ignored ?
Rule   0: id->"R-0"; action->"DUNNO"; client_address->"=;10.1.0.0/16, =;192.168.2.1"

Les éléments de fichier sont évalués au moment de la configuration. Par conséquent, postfwd3 doit être rechargé si un fichier a été modifié.

Si vous souhaitez spécifier un fichier qui sera rechargé à chaque requête, vous pouvez utiliser lfile: et ltable :

id=R001; client_address=lfile:/etc/postfwd/client_whitelist; action=dunno

Ceci vérifiera l'heure de modification de /etc/postfwd/client_whitelist à chaque évaluation de la règle et la rechargera si nécessaire. Bien sûr, cela pourrait augmenter la charge du système, alors utilisez-le avec précaution.

L'option --showconfig illustre la différence :

## évalué au moment de la configuration
# postfwd3 --nodaemon -L --rule='client_address=table:/etc/postfwd/clients; action=dunno' -C
Rule   0: id->"R-0"; action->"dunno"; client_address->"=;1.1.1.1, =;1.1.1.2, =;1.1.1.3"
## évalué pour chaque correspondance de règle
# postfwd3 --nodaemon -L --rule='client_address=ltable:/etc/postfwd/clients; action=dunno' -C
Rule   0: id->"R-0"; action->"dunno"; client_address->"=;ltable:/etc/postfwd/clients"

Les fichiers peuvent faire référence à d'autres fichiers. Ce qui suit est valide.

-- FICHIER /etc/postfwd/rules.cf --
id=R01; client_address=file:/etc/postfwd/clients_master.cf; action=DUNNO
-- FICHIER /etc/postfwd/clients_master.cf --
192.168.1.0/24
file:/etc/postfwd/clients_east.cf
file:/etc/postfwd/clients_west.cf
-- FICHIER /etc/postfwd/clients_east.cf --
192.168.2.0/24
-- FICHIER /etc/postfwd/clients_west.cf --
192.168.3.0/24

Notez qu'il n'y a actuellement pas de détection de boucle (/a/file appelle /a/file) et que cette fonctionnalité n'est disponible qu'avec postfwd1 v1.15 et postfwd3 v0.18 et supérieurs.

ACTIONS

Général

Les actions seront exécutées lorsque tous les éléments de la règle auront correspondé à une requête (ou au moins un élément de n'importe quelle liste d'éléments). Vous pouvez faire référence aux attributs de la requête en les précédant du caractère $$, comme ceci :

id=R-003; client_name = !!$$helo_name; action=WARN helo '$$helo_name' does not match DNS '$$client_name'
# ou
id=R-003; client_name = !!$$helo_name; action=WARN helo '$$(helo_name)' does not match DNS '$$(client_name)'

actions postfix

Les actions seront renvoyées à postfix en réponse aux requêtes de délégation de politique. Toute action comprise par postfix est autorisée - voir "man 5 access" ou http://www.postfix.org/access.5.html pour une description. Si aucune action n'est spécifiée, l'action postfix WARN, qui enregistre simplement l'événement, sera utilisée pour la règle correspondante.

postfwd3 renverra dunno s'il a atteint la fin de l'ensemble de règles et qu'aucune règle n'a correspondu. Ceci peut être modifié en plaçant une dernière règle ne contenant qu'une déclaration d'action :

...
action=dunno ; sender=@domain.local     # l'expéditeur est ok
action=reject                           # refuser par défaut

actions postfwd3

Les actions postfwd3 contrôlent le comportement du programme. Actuellement, vous pouvez spécifier les actions suivantes :

jump (<id>)
saute à la règle avec l'id <id>, utilisez ceci pour sauter certaines règles.
vous pouvez sauter en arrière - mais rappelez-vous qu'il n'y a pas de
détection de boucle pour le moment ! les sauts vers des ids inexistants seront ignorés.
score (<score>)
le score de la requête sera modifié par le <score> spécifié,
qui doit être une valeur flottante. le modificateur peut être soit
        +n.nn   ajoute n.nn au score actuel
        -n.nn   soustrait n.nn au score actuel
        *n.nn   multiplie le score actuel par n.nn
        /n.nn   divise le score actuel par n.nn
        =n.nn   définit le score actuel à n.nn
si le score dépasse le maximum défini par l'option --scores (voir LIGNE DE COMMANDE) ou l'élément score (voir la section ÉLÉMENTS), l'action
définie pour ce cas sera retournée (par défaut : 5.0=>"REJECT postfwd3 score exceeded").
set (<item>=<value>,<item>=<value>,...)
cette commande permet d'insérer ou de remplacer des attributs de requête, qui pourront ensuite être comparés à votre ensemble de règles ultérieur. utilisez ceci pour accélérer les comparaisons répétées avec de grandes listes d'éléments.
veuillez consulter la section EXEMPLES pour plus d'informations. vous pouvez séparer plusieurs paires clé=valeur
par des caractères ",".
rate (<item>/<max>/<time>/<action>)
cette commande crée un compteur pour l'<item> donné, qui sera incrémenté chaque fois qu'une requête
le contenant arrive. s'il dépasse <max> dans les <time> secondes, il renverra <action> à postfix.
les compteurs de taux sont très rapides car ils sont exécutés avant l'analyse de l'ensemble de règles.
veuillez noter que <action> était limité aux actions postfix (pas d'actions postfwd) pour les versions de postfwd <1.33 !
    # pas plus de 3 requêtes par 5 minutes
    # du même client "unknown"
    id=RATE01 ;  client_name==unknown
       action=rate(client_address/3/300/450 4.7.1 sorry, max 3 requests per 5 minutes)
size (<item>/<max>/<time>/<action>)
cette commande fonctionne de manière similaire à la commande rate() à la différence près que le compteur de taux
est incrémenté par l'attribut de taille de la requête. pour ce faire de manière fiable, vous devriez appeler postfwd3 depuis
smtpd_end_of_data_restrictions. si vous voulez être sûr, vous pouvez le vérifier dans l'ensemble de règles :
   # limite de taille 1.5 Mo par heure par client
   id=SIZE01 ;  protocol_state==END-OF-MESSAGE ;  client_address==!!(10.1.1.1)
      action=size(client_address/1572864/3600/450 4.7.1 sorry, max 1.5mb per hour)
rcpt (<item>/<max>/<time>/<action>)
cette commande fonctionne de manière similaire à la commande rate() à la différence près que le compteur de taux
est incrémenté par l'attribut recipient_count de la requête. pour ce faire de manière fiable, vous devriez appeler postfwd
depuis smtpd_data_restrictions ou smtpd_end_of_data_restrictions. si vous voulez être sûr, vous pouvez
le vérifier dans l'ensemble de règles :
   # limite de 3 destinataires par heure par client
   id=RCPT01 ;  protocol_state==END-OF-MESSAGE ;  client_address==!!(10.1.1.1)
      action=rcpt(client_address/3/3600/450 4.7.1 sorry, max 3 recipients per hour)
rate5321,size5321,rcpt5321 (<item>/<max>/<time>/<action>)
identique aux fonctions non-5321 correspondantes, à la différence près que la partie locale
des adresses de l'expéditeur ou du destinataire est évaluée en tenant compte de la casse conformément à la rfc5321. Cela
signifie que les requêtes provenant de bob@example.local et BoB@example.local seront traitées différemment.
groupadd(<groupname>/<item>[/<ttl>])
sauvegarde <item> dans le groupe dynamique <group> pour une utilisation ultérieure. l'objet sera supprimé de ce
groupe après ttl secondes. s'il n'est pas défini, postfwd3 utilisera la valeur par défaut --default_group_ttl [3600s].
Veuillez lire le chapitre sur les groupes dynamiques avant utilisation !
   # ajouter client_address au groupe %%blacklisted_hosts
   id=ADDGROUP
        rbl=zen.spamhaus.org,bl.spamcop.net,ix.dnsbl.manitu.net
        action=groupadd(%%blacklisted_hosts/client_address/86400)
groupdel(<groupname>/<item>)
supprime <item> du groupe dynamique <group>. Veuillez lire le chapitre sur les groupes dynamiques avant utilisation !
   # supprimer un client_address du groupe %%blacklisted_hosts
   id=DELGROUP
        rbl=lists.dnswl.org
        action=groupdel(%%blacklisted_hosts/client_address)
ask (<addr>:<port>[:<ignore>])
permet de déléguer la décision de politique à un autre service de politique (par exemple, postgrey). le premier
et le deuxième argument (adresse et port) sont obligatoires. un troisième argument optionnel peut être
spécifié pour indiquer à postfwd3 d'ignorer certaines réponses et de continuer l'analyse de l'ensemble de règles :
   # exemple1 : interroger postgrey et renvoyer sa réponse à postfix
   id=GREY; client_address==10.1.1.1; action=ask(127.0.0.1:10031)
   # exemple2 : interroger postgrey mais ignorer sa réponse si elle correspond à 'DUNNO'
   # et continuer l'analyse des règles de postfwd
   id=GREY; client_address==10.1.1.1; action=ask(127.0.0.1:10031:^dunno$)
mail(server/helo/from/to/subject/body)
Cette commande est obsolète. Vous devriez essayer d'utiliser l'action sendmail() à la place.
Commande mail très basique, qui envoie un message avec les arguments donnés. LIMITATIONS :
Ceci effectue essentiellement un telnet. Aucune authentification ou TLS ne sont disponibles. De plus, elle ne suit pas l'état de notification et vous notifiera à chaque fois que la règle correspondante sera déclenchée.
sendmail(sendmail-path::from::to::subject::body)
Commande mail, qui utilise un binaire sendmail existant et envoie un message avec les arguments donnés.
LIMITATIONS : La commande ne suit pas l'état de notification et vous notifiera à chaque fois que la
règle correspondante sera déclenchée (ce qui pourrait signifier 100 e-mails pour un m
ail à 100 destinataires au stade RCPT).
wait (<délai>)
met en pause l'exécution du programme pendant <délai> secondes. utilisez ceci pour
retarder ou limiter les connexions.
note (<chaîne>)
enregistre simplement la chaîne donnée et continue l'analyse du jeu de règles.
si la chaîne est vide, rien ne sera enregistré (noop).
quit (<code>)
termine le programme avec le code de sortie donné. postfix n'aime pas trop
cela, alors utilisez-le avec précaution.

Vous pouvez faire référence aux attributs de la requête, comme

id=R-HELO ;  helo_name=^[^\.]+$ ;  action=REJECT helo invalide '$$helo_name'

Depuis la version 2.00 de postfwd3, une règle peut avoir plusieurs actions postfwd, comme

# si le client est trouvé sur list.dnswl.org,
#   1. envoyer une note
#   2. ajouter son ip au groupe %%WHITELISTED
#   3. autoriser la requête
id=ADDR01
        rbl=list.dnswl.org
        action=note(ajout de $$client_address à WHITELIST)
        action=groupadd(%%WHITELISTED/client_address)
        action=PERMIT_AUTH_DESTINATION

MACROS/ACLs

L'utilisation multiple d'éléments longs ou de leurs combinaisons peut être abrégée par des macros. Celles-ci doivent être préfixées par '&&' (deux caractères '&'). Les macros doivent d'abord être définies comme suit :

&&RBLS { rbl=zen.spamhaus.org,list.dsbl.org,bl.spamcop.net,dnsbl.sorbs.net,ix.dnsbl.manitu.net; };

Ensuite, elles peuvent être utilisées dans vos règles, comme suit :

&&RBLS ;  client_name=^unknown$                         ; action=REJECT
&&RBLS ;  client_name=(\d+[\.-_]){4}                    ; action=REJECT
&&RBLS ;  client_name=[\.-_](adsl|dynamic|ppp|)[\.-_]   ; action=REJECT

Les macros peuvent également contenir des actions :

# définition
&&GONOW { action=REJECT votre requête a déclenché notre politique de détection de spam qui rejette ce message. Plus d'informations sur http://www.domain.local; };
# règles
&&GONOW ;  &&RBLS ;  client_name=^unknown$
&&GONOW ;  &&RBLS ;  client_name=(\d+[\.-_]){4}
&&GONOW ;  &&RBLS ;  client_name=[\.-_](adsl|dynamic|ppp|)[\.-_]

Les macros peuvent également contenir d'autres macros :

# définition
&&RBLS{
        rbl=zen.spamhaus.org
        rbl=list.dsbl.org
        rbl=bl.spamcop.net
        rbl=dnsbl.sorbs.net
        rbl=ix.dnsbl.manitu.net
};
&&DYNAMIC{
        client_name=^unknown$
        client_name=(\d+[\.-_]){4}
        client_name=[\.-_](adsl|dynamic|ppp|)[\.-_]
};
&&GOAWAY { &&RBLS; &&DYNAMIC; };
# règles
&&GOAWAY ; action=REJECT client dynamique et listé sur RBL

Fondamentalement, les macros sont de simples substitutions de texte - voir la section "PARSER" pour plus d'informations.

GROUPES DYNAMIQUES

Les groupes dynamiques sont des objets de liste. Vous pouvez ajouter ou supprimer des éléments et comparer des éléments de requête à leur contenu dans votre jeu de règles. Les groupes sont sauvegardés de manière persistante pour les requêtes ultérieures. De cette façon, vous pouvez sauvegarder des informations pour une utilisation ultérieure. Chaque élément d'un groupe a une valeur de durée de vie.

Les noms de groupe doivent être précédés de doubles caractères '%' , comme %%GROUPNAME :

# ajouter client_address au groupe %%BLACKLISTED, si envoyé à spamtrap
id=SPAMTRAP; recipient==spamtrap@domain.local; action=groupadd(%%BLACKLISTED/client_address)
# rejeter toute requête provenant de client_address dans le groupe %%BLACKLISTED
id=BLACKLISTED; client_address=%%BLACKLISTED; action=REJECT

La fonction groupadd() reçoit les arguments suivants. La valeur <ttl> est optionnelle. Si elle n'est pas spécifiée, postfwd3 utilisera la valeur par défaut --default_group_ttl [300s] :

groupadd ( <NomDuGroupe> / <élément> [ / <ttl> ] )

postfwd sauvegardera ces données dans la structure suivante :

%Group_Cache -> %<NomDuGroupe> -> $<élément> = <ttl>

La fonction groupdel() supprime un élément d'un groupe :

groupdel ( <NomDuGroupe> / <élément> )

Les membres expirés seront supprimés à l'étape de nettoyage après --cleanup_groups <i> secondes.

Pour comparer des requêtes avec des groupes dynamiques, ceux-ci doivent être référencés en les précédant de '%%' :

<élément> = %%<NomDuGroupe>

Les groupes vides comparent toujours à faux. Le jeu de règles suivant est possible :

# autoriser toute requête provenant de client_address dans le groupe %%WHITELISTED
id=WHITEGROUP; client_address=%%WHITELISTED; action=DUNNO
# rejeter toute requête provenant de client_address dans le groupe %%BLACKLISTED
id=BLACKGROUP; client_address=%%BLACKLISTED; action=REJECT
# ... autres règles ...
# ... liste blanche ...
id=W_TRUST; action=set(WHITE=1)
    client_address=file:/etc/postfwd/whitelist_networks
# ... liste blanche DNS ...
id=W_DNSWL; action=set(WHITE=1)
    rbl=list.dnswl.org
# ... -> l'ajouter à la liste blanche pour un jour et autoriser la requête
id=W_GROUP; WHITE==1
    action=groupadd(%%WHITELISTED/client_address/86400)
    action=DUNNO
# ... ou bloquer en envoyant à spamtrap ...
id=B_SPAMTRAP; action=set(BLACK=1)
    recipient==spamtrap@domain.local
# ... ou bloqué par DNS ...
id=B_DNSBL; action=set(BLACK=1)
    rbl=zen.spamhaus.org
# ... -> l'ajouter au groupe BLACKLISTED pendant 1 heure et rejeter
id=B_GROUP; BLACK==1
    action=groupadd(%%BLACKLISTED/client_address/3600)
    action=REJECT

Limitations

Actuellement, les groupes dynamiques sont conservés en mémoire. Par défaut, postfwd3 n'accepte qu'un maximum de 999999 membres dans un groupe. Pour désactiver cette limite, définissez --group_maxitems à '-1'.

Avec la personnalité PreFork, vous devez être conscient que ces informations doivent être partagées via le démon de cache.

En bref : Ne laissez pas ces listes devenir excessivement grandes à moins d'avoir suffisamment de capacité système pour le faire. Si nécessaire, ajustez votre configuration en définissant la valeur <ttl> et --group_maxitems.

PLUGINS

Description

L'interface des plugins vous permet de définir vos propres contrôles et d'améliorer les fonctionnalités de postfwd. N'hésitez pas à partager des choses utiles !

Attention

Notez que l'interface des plugins est encore en phase de développement. Veuillez tester vos plugins avec soin, car des erreurs pourraient faire planter postfwd ! Il est également autorisé de surcharger des attributs ou des fonctions intégrées, mais assurez-vous de savoir ce que vous faites car certains d'entre eux sont utilisés en interne.

Veuillez tenir compte de la sécurité lorsque vous accédez à des ressources sensibles et ne jamais, jamais exécuter postfwd en tant qu'utilisateur privilégié ! Ne faites jamais confiance à vos entrées (en particulier les noms d'hôte et les adresses e-mail).

ITEMS

Les plugins d'éléments sont des sous-routines Perl qui intègrent des attributs supplémentaires aux requêtes avant qu'elles ne soient évaluées par rapport au jeu de règles de postfwd, comme tout autre élément du protocole de délégation de politique. Cela vous permet de créer vos propres contrôles.

Les éléments de plugin ne peuvent pas être utilisés de manière sélective. Ces fonctions seront exécutées pour chaque requête que postfwd reçoit, alors gardez les performances à l'esprit.

SYNOPSIS : postfwd_items_plugin{<nom>}($requête)

signifie que votre sous-routine, appelée <nom>, a accès à une référence de hachage appelée $requête, qui contient tous les attributs de la requête, comme $requête->{client_name} et enregistre des valeurs sous la forme suivante :

sauvegarde : $result->{<élément>} = <valeur>

cela crée le nouvel élément <élément> contenant <valeur>, qui sera intégré à la requête de délégation de politique et pourra donc être utilisé dans le jeu de règles de postfwd.

# ne PAS supprimer la ligne suivante
%postfwd_items_plugin = (
        # EXEMPLES - intégrés dans postfwd. pas besoin de les activer ici.

                # permet de vérifier la version de postfwd dans le jeu de règles
                "version" => sub {
                        my($requête) = shift;
                        $requête->{version} => $NAME." ".$VERSION,
                },

                # sender_domain et recipient_domain
                "address_parts" => sub {
                        my($requête) = shift;
                        $requête->{sender} =~ /@([^@]*)$/;
                        $requête->{sender_domain} = ($1 || '');
                        $requête->{recipient} =~ /@([^@]*)$/;
                        $requête->{recipient_domain} = ($1 || '');
                },
# ne PAS supprimer la ligne suivante
);

COMPARE

Les plugins de comparaison vous permettent de définir comment vos nouveaux éléments doivent être comparés au jeu de règles. Ceux-ci sont optionnels. Si vous n'en spécifiez pas, la comparaison par défaut (== pour une correspondance exacte, =~ pour PCRE, ...) sera utilisée.

SYNOPSIS :  <élément> => sub { return &{$postfwd_compare{<type>}}(@_); },
# ne PAS supprimer la ligne suivante
%postfwd_compare_plugin = (

                # Exemple simple
                # SYNOPSIS :  <résultat> = <élément> (return &{$postfwd_compare{<type>}}(@_))
                "client_address"  => sub { return &{$postfwd_compare{cidr}}(@_); },
                "size"            => sub { return &{$postfwd_compare{numeric}}(@_); },
                "recipient_count" => sub { return &{$postfwd_compare{numeric}}(@_); },

                # SYNOPSIS :  <résultat> = <élément>(<opérateur>, <valeur de règle>, <valeur de requête>, <requête>)
                "numeric" => sub {
                        my($cmp,$val,$myitem,$request) = @_;
                        my($myresult) = undef;  $myitem ||= "0"; $val ||= "0";
                        if ($cmp eq '==') {
                                $myresult = ($myitem == $val);
                        } elsif ($cmp eq '=<') {
                                $myresult = ($myitem <= $val);
                        } elsif ($cmp eq '=>') {
                                $myresult = ($myitem >= $val);
                        } elsif ($cmp eq '<') {
                                $myresult = ($myitem < $val);
                        } elsif ($cmp eq '>') {
                                $myresult = ($myitem > $val);
                        } elsif ($cmp eq '!=') {
                                $myresult = not($myitem == $val);
                        } elsif ($cmp eq '!<') {
                                $myresult = not($myitem <= $val);
                        } elsif ($cmp eq '!>') {
                                $myresult = not($myitem >= $val);
                        } else {
                                $myresult = ($myitem >= $val);
                        };
                        return $myresult;
                },

);

LIGNE DE COMMANDE

Ensemble de règles

Les arguments suivants sont utilisés pour spécifier la source de l'ensemble de règles postfwd3. Cela signifie qu'au moins un des éléments suivants est requis pour que postfwd3 fonctionne.

-f, --file <fichier>
Lit les règles depuis <fichier>. Veuillez consulter la section CONFIGURATION
pour plus d'informations.
-r, --rule <règle>
Ajoute <règle> à l'ensemble de règles. N'oubliez pas que vous pourriez avoir à
mettre entre guillemets les chaînes qui contiennent des espaces ou des
caractères spéciaux du shell.

Paramètres

-F, --loadsettings <fichier>
Charge les paramètres du programme depuis <fichier>. Les données doivent être
au format Data::Dumper. Veuillez lire la section PARAMÈTRES pour plus
d'informations.
--savesettings <fichier>
Enregistre les paramètres du programme dans <fichier> au format
Data::Dumper. Veuillez lire la section PARAMÈTRES pour plus d'informations.
--showsettings
Exporte les paramètres du programme au format Data::Dumper vers la sortie
standard. Cette sortie peut être enregistrée dans un fichier et utilisée
ultérieurement avec l'option --loadsettings.

Score

-s, --scores <val>=<action>
Retourne <action> à postfix lorsque le score de la requête dépasse <val>

Une utilisation multiple est autorisée. Enchaînez simplement vos arguments, par exemple :

postfwd3 -r "<élément>=<valeur>;action=<résultat>" -f <fichier> -f <fichier> ...
  ou
postfwd3 --scores 4.5="AVERTIR score élevé" --scores 5.0="REJETER score postfwd3 trop élevé" ...

En cas de scores multiples, la correspondance la plus élevée comptera. L'ordre des arguments sera reflété dans l'ensemble de règles postfwd3.

Réseau

postfwd3 peut être exécuté en tant que démon afin d'écouter sur le réseau les requêtes entrantes. Les arguments suivants contrôleront son comportement dans ce cas.

-d, --daemon, --nodaemon
postfwd3 s'exécutera en tant que démon et écoutera sur le réseau les
requêtes entrantes (par défaut 127.0.0.1:10045). Utilisez --nodaemon pour
maintenir postfwd3 en cours d'exécution en premier plan.
-i, --interface <dev>
Lie postfwd3 à l'interface spécifiée (par défaut 127.0.0.1).
-p, --port <port>
postfwd3 écoute sur le port spécifié (par défaut tcp/10045).
--proto <type>
Le type de protocole pour le socket de postfwd. Actuellement, vous pouvez
utiliser 'tcp' ou 'unix' ici. Pour utiliser postfwd3 avec un socket de
domaine Unix, exécutez-le comme suit :
    postfwd3 --proto=unix --port=/quelque part/postfwd.socket
-u, --user <nom>
Change l'utilisateur réel et effectif en <nom>.
-g, --group <nom>
Change le groupe réel et effectif en <nom>.
--personality <type>
Type de serveur de politique, autorise 'PreFork' ou 'Multiplex'.
Cette option remplace --autopersonality.
--v1
définit la personnalité sur 'Multiplex'
Cette option remplace --autopersonality.
--v2
définit la personnalité sur 'PreFork'
Cette option remplace --autopersonality.
--autopersonality
postfwd3 détermine la personnalité par le nom du programme :
   * 'Multiplex' pour 'postfwd' ou 'postfwd1'
   * 'PreFork' pour 'postfwd2'
vous pouvez désactiver cela en utilisant --noautopersonality ou
en utilisant explicitement --personality, --v1 ou --v2
--umask <masque>
Modifie l'umask pour les permissions de fichier du processus maître (pidfile).
Attention : il s'agit de l'umask, pas de chmod - vous devez spécifier les bits
qui ne doivent PAS s'appliquer. Par exemple : umask 077 équivaut à chmod 700.
--cache_umask <masque>
Modifie l'umask pour les permissions de fichier du processus de cache
(socket de domaine Unix).
--server_umask <masque>
Modifie l'umask pour les permissions de fichier du processus serveur
(socket de domaine Unix).
-R, --chroot <chemin>
Chroute le processus vers le chemin spécifié.
Veuillez consulter http://postfwd.org/postfwd3-chroot.html avant utilisation !
--pidfile <chemin>
L'identifiant du processus sera enregistré dans le fichier spécifié.
--facility <f>
définit la facilité syslog, par défaut 'mail'
--socktype <s>
définit le type de socket Sys::Syslog à 'native', 'inet' ou 'unix'.
Par défaut, il s'agit d'une auto-détection en fonction de la version du module
et du système d'exploitation.
-l, --logname <étiquette>
Étiquette les messages syslog. Utile lors de l'exécution de plusieurs
instances de postfwd.
--loglen <entier>
Tronque tout message syslog après <entier> caractères.

Charge les plugins postfwd depuis le fichier. Veuillez consulter
http://postfwd.org/postfwd.plugins ou le fichier

En mode démon, postfwd3 recharge son ensemble de règles après avoir reçu un signal HUP. Veuillez consulter la description du commutateur '-I' pour que votre configuration soit rafraîchie pour chaque requête reçue par postfwd3.

ANALYSEUR

Configuration

L'ensemble de règles postfwd3 peut être spécifié en ligne de commande (option -r) ou lu à partir de fichiers (-f). L'ordre de vos arguments sera conservé. Vous devriez vérifier l'analyseur avec l'option -C | --showconfig en ligne de commande avant d'appliquer une nouvelle configuration. L'appel suivant :

postfwd3 --showconfig \
        -r "id=TEST; recipient_count=100; action=WARN mail with 100+ recipients" \
        -f /etc/postfwd.cf \
        -r "id=DEFAULT; action=dunno";

produira la sortie suivante :

Rule   0: id->"TEST" action->"WARN mail with 100+ recipients"; recipient_count->"100"
...
... <contenu de /etc/postfwd.cf> ...
...
Rule <n>: id->"DEFAULT" action->"dunno"

Plusieurs éléments du même type seront ajoutés à des listes (voir la section "ÉLÉMENTS" pour plus d'informations) :

postfwd3 --showconfig \
        -r "client_address=192.168.1.0/24; client_address=172.16.26.32; action=dunno"

résultera en :

Rule   0: id-&quo

NOM

postfwd3 - serveur de politique pour Postfix

SYNOPSIS

postfwd3 [options] [request file]

DESCRIPTION

postfwd3 implémente le protocole de politique de Postfix, tel que décrit dans http://www.postfix.org/SMTPD_POLICY_README.html. Il est écrit en Perl et conçu pour être utilisé comme serveur de politique par Postfix. Il peut également être utilisé en ligne de commande pour tester des requêtes de politique.

Règles

Le fichier de configuration contient des règles qui sont lues à l'étape de configuration. Les règles sont des paires clé-valeur qui décrivent les conditions et les actions à effectuer. Par exemple:

id=R001; client_address=192.168.1.0/24, 172.16.26.32; action="dunno"

Les macros sont évaluées à l'étape de configuration, ce qui signifie que

postfwd3 --showconfig \
        -r "&&RBLS { rbl=bl.spamcop.net; client_name=^unknown$; };" \
        -r "id=RBL001; &&RBLS; action=REJECT listed on spamcop and bad rdns";

résultera par:

Rule   0: id->"RBL001"; action->"REJECT listed on spamcop and bad rdns"; rbl->"bl.spamcop.net"; client_name->"^unknown$"

Traitement des requêtes

Lorsqu'une requête de délégation de politique arrive, elle est comparée à l'ensemble de règles de postfwd. Pour inspecter le traitement en détail, augmentez la verbosité à l'aide de l'option « -v » ou « -vv ». « -L » redirige les messages de journalisation vers stdout.

En gardant l'ordre général de l'ensemble de règles, les éléments sont comparés dans un ordre aléatoire, ce qui signifie fondamentalement que

id=R001; action=dunno; client_address=192.168.1.1; sender=bob@alice.local

est équivalent à

id=R001; sender=bob@alice.local; client_address=192.168.1.1; action=dunno

Les listes sont évaluées dans l'ordre spécifié. Cela permet de placer les expressions les plus rapides en premier :

postfwd3 -vv --cmd -r "id=RBL001; rbl=localrbl.local zen.spamhaus.org; action=REJECT" /some/where/request.sample

produit le résultat suivant :

[LOGS info]: compare rbl: "remotehost.remote.net[68.10.1.7]"  ->  "localrbl.local"
[LOGS info]: count1 rbl:  "2"  ->  "0"
[LOGS info]: query rbl:   localrbl.local 7.1.10.68 (7.1.10.68.localrbl.local)
[LOGS info]: count2 rbl:  "2"  ->  "0"
[LOGS info]: match rbl:   FALSE
[LOGS info]: compare rbl: "remotehost.remote.net[68.10.1.7]"  ->  "zen.spamhaus.org"
[LOGS info]: count1 rbl:  "2"  ->  "0"
[LOGS info]: query rbl:   zen.spamhaus.org 7.1.10.68 (7.1.10.68.zen.spamhaus.org)
[LOGS info]: count2 rbl:  "2"  ->  "0"
[LOGS info]: match rbl:   FALSE
[LOGS info]: Action: dunno

L'opérateur de négation !!(<valeur>) a la priorité la plus élevée et est donc évalué en premier. Ensuite, les substitutions de variables sont effectuées :

postfwd3 -vv --cmd -r "id=TEST; action=REJECT; client_name=!!($$heloname)" /some/where/request.sample

donnera :

[LOGS info]: compare client_name:     "unknown"  ->  "!!($$helo_name)"
[LOGS info]: negate client_name:      "unknown"  ->  "$$helo_name"
[LOGS info]: substitute client_name:  "unknown"  ->  "english-breakfast.cloud8.net"
[LOGS info]: match client_name:  TRUE
[LOGS info]: Action: REJECT

Évaluation de l'ensemble de règles

Une règle correspond lorsque tous les éléments (ou au moins un élément d'une liste pour chaque élément) correspondent. Dès qu'un élément (ou tous les éléments d'une liste) ne parvient pas à être comparé à l'attribut de la requête, l'analyseur passe à la règle suivante dans l'ensemble de règles de postfwd3.

Si une règle correspond, il y a deux options :

* La règle renvoie une action postfix (dunno, reject, ...) L'analyseur arrête le traitement des règles et renvoie l'action à postfix. D'autres règles ne seront pas évaluées.

* La règle renvoie une action postfwd3 (jump(), note(), ...) L'analyseur évalue l'action donnée et continue avec la règle suivante (sauf pour les actions jump() ou quit() - veuillez consulter la section « ACTIONS » pour plus d'informations). Rien ne sera envoyé à postfix.

Si aucune règle n'a correspondu et que la fin de l'ensemble de règles est atteinte, postfwd3 renverra « dunno » sans rien enregistrer, sauf en mode verbeux. Vous pouvez placer une dernière règle « catch-all » pour modifier ce comportement :

... <vos règles> ...
id=DEFAULT ;  action=dunno

enregistrera toute requête qui passe l'ensemble de règles sans avoir atteint une règle précédente.

PARAMÈTRES

Depuis la version postfwd3 2.00-pre6, les paramètres du programme peuvent être récupérés à partir d'un fichier. Les informations doivent être analysables par la fonction perl eval(). Les commentaires sont autorisés :

# exemple de paramètres pour postfwd3
{
   # activer la journalisation détaillée
   verbose => 1,
   # utilisateur et groupe pour postfwd
   base => {
       group => 'postfw',
       user => 'postfw'
   },
   # paramètres du serveur
   server => {
       proto => 'tcp',
       host => '127.0.0.1',
       port => '10099'
   }
}

postfwd3 peut également exporter les paramètres du programme dans ce format en utilisant Data::Dumper.

# afficher la configuration
postfwd3 --showsettings
# enregistrer la configuration dans un fichier
postfwd3 --savesettings=/path/to/file
# lire la configuration à partir d'un fichier
postfwd3 --loadsettings=/path/to/file

Une utilisation multiple de --loadsettings ou de la forme courte -F est autorisée. L'ordre sera conservé. Les arguments en ligne de commande remplacent les paramètres récupérés à partir d'un fichier.

# charger les paramètres de base, remplacer par les paramètres du nœud et définir le port et la journalisation détaillée
postfwd3 -v -p 10050 -F /path/to/basefile -F /path/to/nodefile

Des exemples de fichiers de configuration sont distribués dans le dossier etc/ de l'archive postfwd3.

DÉBOGAGE

Pour déboguer des étapes spécifiques de l'analyseur, le commutateur '--debug' prend une liste de classes de débogage. Depuis postfwd3 2.00, la liste des classes de débogage disponibles peut être obtenue en exécutant :

postfwd3 --debugclasses

INTÉGRATION

Intégration via le mode démon

La façon courante d'utiliser postfwd3 est de le démarrer en tant que démon, en écoutant sur un port tcp spécifié. postfwd3 générera plusieurs processus enfants qui communiqueront avec un cache parent. C'est la manière préférée d'utiliser postfwd3 dans les environnements à fort volume. Démarrez postfwd3 avec les paramètres suivants :

postfwd3 -d -f /etc/postfwd.cf -i 127.0.0.1 -p 10045 -u nobody -g nobody -S

Pour une mise en cache efficace, vérifiez si vous pouvez utiliser les options --cacheid, --cache-rdomain-only, --cache-no-sender et --cache-no-size.

Vérifiez maintenant vos journaux système (installation par défaut « mail ») pour une ligne comme :

Aug  9 23:00:24 mail postfwd[5158]: postfwd3 n.nn ready for input

et utilisez `netstat -an|grep 10045` pour vérifier quelque chose comme

tcp  0  0  127.0.0.1:10045  0.0.0.0:*  LISTEN

Si tout fonctionne, ouvrez votre fichier main.cf de postfix et insérez ce qui suit :

127.0.0.1:10045_time_limit      = 3600                                          <--- intégration
smtpd_recipient_restrictions    = permit_mynetworks                             <--- recommandé
                                  reject_unauth_destination                     <--- recommandé
                                  check_policy_service inet:127.0.0.1:10045     <--- intégration

Rechargez votre configuration avec `postfix reload` et surveillez vos journaux. Si cela fonctionne, vous devriez voir des lignes comme les suivantes dans votre journal de messagerie :

Aug  9 23:01:24 mail postfwd[5158]: rule=22, id=ML_POSTFIX, client=english-breakfast.cloud9.net[168.100.1.7], sender=owner-postfix-users@postfix.tld, recipient=someone@domain.local, helo=english-breakfast.cloud9.net, proto=ESMTP, state=RCPT, action=dunno

Si vous souhaitez vérifier les éléments de taille ou rcpt_count, vous devez intégrer postfwd3 dans smtp_data_restrictions ou smtpd_end_of_data_restrictions. Bien sûr, vous pouvez également spécifier une classe de restriction et l'utiliser dans vos tables d'accès. Créez d'abord un fichier /etc/postfix/policy contenant :

domain1.local           postfwdcheck
domain2.local           postfwdcheck
...

Ensuite, postmap ce fichier (`postmap hash:/etc/postfix/policy`), ouvrez votre main.cf et entrez :

# Classes de restriction
smtpd_restriction_classes       = postfwdcheck, <quelques autres>...                          <--- intégration
postfwdcheck                    = check_policy_service inet:127.0.0.1:10045             <--- intégration
127.0.0.1:10045_time_limit      = 3600                                                  <--- intégration
smtpd_recipient_restrictions    = permit_mynetworks,                                    <--- recommandé
                                  reject_unauth_destination,                            <--- recommandé
                                  ...                                                   <--- optionnel
                                  check_recipient_access hash:/etc/postfix/policy,      <--- intégration
                                  ...                                                   <--- optionnel

Rechargez postfix et surveillez vos journaux.

PERFORMANCE

Certaines de ces propositions pourraient ne pas correspondre à votre environnement. Veuillez vérifier vos exigences et tester soigneusement les nouvelles options !

- utiliser les options de mise en cache
- utiliser l'opérateur de correspondance correct ==, <=, >=
- utiliser ^ et/ou $ dans les expressions régulières
- utiliser des listes d'éléments (plus rapides que des règles uniques)
- utiliser l'action set() sur des listes d'éléments répétées
- utiliser des sauts et des limitations de débit
- utiliser une règle de pré-recherche pour les rbl/rhsbl avec une action note() vide
