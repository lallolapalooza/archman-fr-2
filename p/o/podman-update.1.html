NOM

podman-update - Met à jour la configuration d'un conteneur donné

SYNTAXE

podman update [options] conteneur

podman container update [options] conteneur

DESCRIPTION

Met à jour la configuration d'un conteneur existant, permettant des modifications aux limites de ressources et aux contrôles de santé.

OPTIONS

--blkio-weight=poids

Poids relatif de l'E/S bloc. Le poids est une valeur comprise entre 10 et 1000.

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--blkio-weight-device=périphérique:poids

Poids relatif du périphérique pour l'E/S bloc.

--cpu-period=limite

Définit la période CPU pour le planificateur équitable (CFS), qui est une durée en microsecondes. Une fois le quota CPU du conteneur épuisé, il ne sera pas planifié pour s'exécuter avant la fin de la période en cours. Par défaut, la valeur est de 100000 microsecondes.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpu-quota=limite

Limite le quota CPU du planificateur équitable (CFS).

Limite l'utilisation du CPU du conteneur. Par défaut, les conteneurs s'exécutent avec toutes les ressources CPU disponibles. La limite est un nombre en microsecondes. Si un nombre est fourni, le conteneur est autorisé à utiliser cette quantité de temps CPU jusqu'à la fin de la période CPU (contrôlable via --cpu-period).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpu-rt-period=microsecondes

Limite la période temps réel du CPU en microsecondes.

Limite l'utilisation du CPU temps réel du conteneur. Cette option indique au noyau de restreindre l'utilisation du CPU temps réel du conteneur à la période spécifiée.

Cette option n'est prise en charge que sur les systèmes rootful cgroups V1.

--cpu-rt-runtime=microsecondes

Limite le temps d'exécution temps réel du CPU en microsecondes.

Limite l'utilisation du CPU temps réel des conteneurs. Cette option indique au noyau de limiter la quantité de temps que les tâches temps réel peuvent consommer pendant une période CPU donnée. Par exemple : une période de 1 000 000µs et un temps d'exécution de 950 000µs signifient que ce conteneur peut consommer 95% du CPU disponible et laisser les 5% restants aux tâches de priorité normale.

La somme de tous les temps d'exécution entre les conteneurs ne peut pas dépasser la quantité allouée au cgroup parent.

Cette option n'est prise en charge que sur les systèmes rootful cgroups V1.

--cpu-shares, -c=parts

Parts CPU (poids relatif).

Par défaut, tous les conteneurs reçoivent la même proportion de cycles CPU. Cette proportion peut être modifiée en changeant le poids des parts CPU du conteneur par rapport au poids combiné de tous les conteneurs en cours d'exécution. Le poids par défaut est de 1024.

La proportion ne s'applique que lorsque des processus intensifs en CPU sont en cours d'exécution. Lorsque les tâches d'un conteneur sont inactives, d'autres conteneurs peuvent utiliser le temps CPU restant. La quantité réelle de temps CPU varie en fonction du nombre de conteneurs en cours d'exécution sur le système.

Par exemple, considérez trois conteneurs, l'un avec des parts CPU de 1024 et les deux autres avec un réglage de parts CPU de 512. Lorsque les processus dans les trois conteneurs tentent d'utiliser 100% du CPU, le premier conteneur reçoit 50% du temps CPU total. Si un quatrième conteneur est ajouté avec des parts CPU de 1024, le premier conteneur ne reçoit que 33% du CPU. Les conteneurs restants reçoivent 16,5%, 16,5% et 33% du CPU.

Sur un système multi-cœurs, les parts de temps CPU sont distribuées sur tous les cœurs CPU. Même si un conteneur est limité à moins de 100% du temps CPU, il peut utiliser 100% de chaque cœur CPU individuel.

Par exemple, considérez un système avec plus de trois cœurs. Si le conteneur C0 est démarré avec --cpu-shares=512 exécutant un processus, et un autre conteneur C1 avec --cpu-shares=1024 exécutant deux processus, cela peut entraîner la division des parts CPU suivante :

PID Conteneur CPU Parts CPU
100 C0 0 100% du CPU0
101 C1 1 100% du CPU1
102 C1 2 100% du CPU2

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpus=nombre

Nombre de CPUs. La valeur par défaut est 0.0, ce qui signifie aucune limite. Ceci est un raccourci pour --cpu-period et --cpu-quota, par conséquent l'option ne peut pas être spécifiée avec --cpu-period ou --cpu-quota.

Sur certains systèmes, la modification des limites CPU peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpuset-cpus=nombre

CPUs dans lesquels autoriser l'exécution. Peut être spécifié sous forme de liste séparée par des virgules (par ex. 0,1), d'une plage (par ex. 0-3), ou d'une combinaison de ceux-ci (par ex. 0-3,7,11-15).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--cpuset-mems=nœuds

Nœuds mémoire (MEMs) dans lesquels autoriser l'exécution (0-3, 0,1). Uniquement efficace sur les systèmes NUMA.

S'il y a quatre nœuds mémoire sur le système (0-3), utilisez --cpuset-mems=0,1 alors les processus dans le conteneur n'utiliseront la mémoire que des deux premiers nœuds mémoire.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--device-read-bps=chemin:taux

Limite le taux de lecture (en octets par seconde) d'un périphérique (par ex. --device-read-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/ma

--device-read-iops=chemin:taux

Limite le taux d'E/S (en opérations par seconde) d'un périphérique (par ex. --device-read-iops=/dev/sda:1000).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--device-write-bps=chemin:taux

Limite le taux d'écriture (en octets par seconde) d'un périphérique (par ex. --device-write-bps=/dev/sda:1mb).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--device-write-iops=chemin:taux

Limite le taux d'E/S d'écriture (en opérations par seconde) d'un périphérique (par ex. --device-write-iops=/dev/sda:1000).

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--disable-healthcheck

Désactive le contrôle de santé du conteneur.

--health-cmd=commande

Commande à exécuter dans le conteneur pour effectuer un contrôle de santé.

--health-interval=durée

Intervalles entre les contrôles de santé. La durée doit être une chaîne de caractères qui peut être interprétée comme une durée, par exemple 30s, 1m30s, ou 2h45m.

--health-retries=nombre

Nombre de tentatives de contrôle de santé échouées avant que le conteneur ne soit considéré comme mort.

--health-start-period=durée

Période de démarrage pour le contrôle de santé. La durée doit être une chaîne de caractères qui peut être interprétée comme une durée, par exemple 30s, 1m30s, ou 2h45m.

--health-timeout=durée

Délai d'attente pour chaque contrôle de santé. La durée doit être une chaîne de caractères qui peut être interprétée comme une durée, par exemple 30s, 1m30s, ou 2h45m.

--kernel-memory=limite

Limite mémoire du noyau. Spécifiez la limite mémoire en octets. Par exemple, --kernel-memory=1gb.

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--memory, -m=limite

Limite mémoire. Spécifiez la limite mémoire en octets. Par exemple, --memory=1gb.

Sur certains systèmes, la modification des limites de ressources peut ne pas être autorisée pour les utilisateurs non root. Pour plus de détails, consultez https://github.com/containers/podman/blob/main/troubleshooting.md#26-running-containers-with-resource-limits-fails-with-a-permissions-error

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--memory-reservation=limite

Mémoire réservée. Spécifiez la limite mémoire en octets. Par exemple, --memory-reservation=1gb.

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--memory-swap=limite

Limite mémoire swap. Spécifiez la limite mémoire en octets. Par exemple, --memory-swap=1gb.

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--memory-swappiness=valeur

Mémoire swappiness. La valeur doit être un entier compris entre 0 et 100.

Cette option n'est pas prise en charge sur les systèmes rootless cgroups V1.

--pids-limit=limite

Limite du nombre de processus. Spécifiez le nombre maximum de processus que le conteneur peut créer. La valeur par défaut est -1, ce qui signifie pas de limite.

--restart=policière

Politique de redémarrage du conteneur. Les valeurs possibles sont : no, on-failure, always, et unless-stopped.

Notez que cette option change la politique de redémarrage du conteneur, et ne le redémarre pas.

--stop-signal=signal

Signal à envoyer au processus principal du conteneur lorsque le conteneur est arrêté.

--stop-timeout=secondes

Durée maximale en secondes à attendre pour que le conteneur s'arrête proprement avant d'envoyer un signal SIGKILL.

EXEMPLES

Mettre à jour les parts CPU d'un conteneur:

$ podman update --cpu-shares=512 mycontainer

Augmenter la limite mémoire d'un conteneur:

$ podman update -m=2g mycontainer

Mettre à jour la politique de redémarrage d'un conteneur:

$ podman update --restart=always mycontainer

Désactiver le contrôle de santé d'un conteneur:

$ podman update --disable-healthcheck mycontainer

Mettre à jour les paramètres du contrôle de santé d'un conteneur:

$ podman update --health-cmd="wget -q --spider http://localhost" --health-interval=30s --health-retries=3 --health-timeout=5s mycontainer

Cette option n'est pas prise en charge sur les systèmes rootless de cgroups V1.

--env, -e=env

Ajoute une valeur (par exemple, env=valeur) au conteneur. Peut être utilisé plusieurs fois. Si la valeur existe déjà dans le conteneur, elle est remplacée. Pour supprimer une variable d'environnement du conteneur, utilisez l'option --unsetenv.

Notez que les mises à jour des variables d'environnement n'affectent le processus principal du conteneur qu'après le prochain démarrage.

--health-cmd="commande" | '["commande", arg1 , ...]'

Définit ou modifie une commande de vérification de l'état de santé d'un conteneur. La commande est une commande à exécuter à l'intérieur du conteneur qui détermine l'état de santé du conteneur. La commande est requise pour que les autres options de vérification de l'état de santé soient appliquées. Une valeur de none désactive les vérifications de l'état de santé existantes.

Plusieurs options peuvent être passées sous forme de tableau JSON ; sinon, la commande est interprétée comme un argument de /bin/sh -c.

Remarque : les valeurs par défaut sont utilisées même si la vérification de l'état de santé est configurée dans l'image.

--health-interval=intervalle

Définit un intervalle pour les vérifications de l'état de santé. Un intervalle de disable n'entraîne aucune configuration de minuterie automatique. La valeur par défaut est 30s.

Remarque : ce paramètre remplacera la configuration de vérification de l'état de santé liée à partir de l'image.

La modification de ce paramètre réinitialise la minuterie.

--health-log-destination=chemin_du_répertoire

Définit la destination du journal des vérifications de l'état de santé. Chemin du répertoire, local ou events_logger (utilisation locale du fichier d'état du conteneur) (Défaut : local)

  • local : (par défaut) Les journaux des vérifications de l'état de santé sont stockés dans les conteneurs de surcouche. (Par exemple : $runroot/healthcheck.log)
  • directory : crée un fichier journal nommé <ID_conteneur>-healthcheck.log avec les journaux des vérifications de l'état de santé dans le répertoire spécifié.
  • events_logger : le journal sera écrit avec le mécanisme de journalisation défini par events_logger. Il enregistre également le journal dans un répertoire par défaut, pour des performances sur un système avec un grand nombre de journaux.

Attention : modifier ce paramètre peut entraîner la perte des journaux précédents.

--health-max-log-count=nombre de journaux stockés

Définit le nombre maximum de tentatives dans le fichier journal des vérifications de l'état de santé ('0' signifie un nombre infini de tentatives dans le fichier journal) (Défaut : 5 tentatives)

--health-max-log-size=taille du journal stocké

Définit la longueur maximale en caractères du journal des vérifications de l'état de santé stocké. ("0" signifie une longueur de journal infinie) (Défaut : 500 caractères)

--health-on-failure=action

Action à entreprendre une fois que le conteneur passe à un état non sain. La valeur par défaut est none.

  • none : Aucune action.
  • kill : Arrêter le conteneur.
  • restart : Redémarrer le conteneur. Ne pas combiner l'action restart avec le drapeau --restart. Lors de l'exécution à l'intérieur d'une unité systemd, envisagez d'utiliser l'action kill ou stop à la place pour utiliser la politique de redémarrage de systemd.
  • stop : Arrêter le conteneur.

--health-retries=tentatives

Le nombre de tentatives autorisées avant qu'une vérification de l'état de santé ne soit considérée comme non saine. La valeur par défaut est 3.

Remarque : ce paramètre peut remplacer la configuration de vérification de l'état de santé de l'image.

--health-start-period=période

Le temps d'initialisation nécessaire au démarrage d'un conteneur. La valeur peut être exprimée dans un format de temps comme 2m3s. La valeur par défaut est 0s.

Remarque : la commande de vérification de l'état de santé est exécutée dès qu'un conteneur est démarré. Si la vérification de l'état de santé réussit, l'état de santé du conteneur sera mis à jour à healthy. Cependant, si la vérification de l'état de santé échoue, l'état de santé restera starting jusqu'à ce que la vérification de l'état de santé réussisse ou que le temps --health-start-period soit écoulé. Si la commande de vérification de l'état de santé échoue après l'expiration du temps --health-start-period, l'état de santé sera mis à jour à unhealthy. La commande de vérification de l'état de santé est exécutée périodiquement en fonction de la valeur de --health-interval.

Remarque : ce paramètre remplacera la configuration de vérification de l'état de santé liée à partir de l'image.

--health-startup-cmd="commande" | '["commande", arg1 , ...]'

Définit une commande de vérification de l'état de santé au démarrage pour un conteneur. Cette commande est exécutée à l'intérieur du conteneur et est utilisée pour contrôler la vérification de l'état de santé régulière. Lorsque la commande de démarrage réussit, la vérification de l'état de santé régulière commence et la vérification de l'état de santé au démarrage cesse. Optionnellement, si la commande échoue pendant un nombre défini de tentatives, le conteneur est redémarré. Une vérification de l'état de santé au démarrage peut être utilisée pour s'assurer que les conteneurs avec une période de démarrage prolongée ne sont pas marqués comme non sains tant qu'ils ne sont pas entièrement démarrés. Les vérifications de l'état de santé au démarrage ne peuvent être utilisées que lorsqu'une vérification de l'état de santé régulière (provenant de l'image du conteneur ou de l'option --health-cmd) est également définie.

--health-startup-interval=intervalle

Définit un intervalle pour la vérification de l'état de santé au démarrage. Un intervalle de disable n'entraîne aucune configuration de minuterie automatique. La valeur par défaut est 30s.

La modification de ce paramètre réinitialise la minuterie, en fonction de l'état du conteneur.

--health-startup-retries=tentatives

Le nombre de tentatives autorisées avant que la vérification de l'état de santé au démarrage ne redémarre le conteneur. S'il est défini sur 0, le conteneur n'est jamais redémarré. La valeur par défaut est 0.

--health-startup-success=tentatives

Le nombre de succès requis avant que la vérification de l'état de santé au démarrage ne réussisse et que la vérification de l'état de santé régulière ne commence. Une valeur de 0 signifie que tout succès lance la vérification de l'état de santé régulière.

--health-startup-timeout=délai_d'attente

Le temps maximum dont dispose une commande de vérification de l'état de santé au démarrage pour se terminer avant d'être marquée comme échouée. La valeur peut être exprimée dans un format de temps comme 2m3s. La valeur par défaut est 30s.

--health-timeout=délai_d'attente

Le temps maximum autorisé pour terminer la vérification de l'état de santé avant qu'un intervalle ne soit considéré comme échoué. Comme pour start-period, la valeur peut être exprimée dans un format de temps tel que 1m22s. La valeur par défaut est 30s.

Remarque : un délai d'attente marque la vérification de l'état de santé comme échouée. Si la commande de vérification de l'état de santé elle-même s'exécute plus longtemps que le délai_d'attente spécifié, elle recevra un signal SIGKILL.

Remarque : ce paramètre remplacera la configuration de vérification de l'état de santé liée à partir de l'image.

--latest, -l

Au lieu de fournir le nom ou l'ID du conteneur, utilisez le dernier conteneur créé. Remarque : le dernier conteneur démarré peut appartenir à d'autres utilisateurs de Podman sur la machine hôte. (Cette option n'est pas disponible avec le client Podman distant, y compris les machines Mac et Windows (à l'exclusion de WSL2)).

--memory, -m=nombre[unité]

Limite de mémoire. Une unité peut être b (octets), k (kibioctets), m (mébioctets) ou g (gibioctets).

Permet de contraindre la mémoire disponible pour un conteneur. Si l'hôte prend en charge la mémoire swap, le réglage de mémoire -m peut être supérieur à la RAM physique. Si une limite de 0 est spécifiée (sans utiliser -m), la mémoire du conteneur n'est pas limitée. La limite réelle peut être arrondie au multiple de la taille de page du système d'exploitation (la valeur est très grande, des millions de trillions).

Cette option n'est pas prise en charge sur les systèmes rootless de cgroups V1.

--memory-reservation=nombre[unité]

Limite souple de mémoire. Une unité peut être b (octets), k (kibioctets), m (mébioctets) ou g (gibioctets).

Après avoir défini la réservation de mémoire, lorsque le système détecte une contention de mémoire ou un manque de mémoire, les conteneurs sont forcés de limiter leur consommation à leur réservation. Définissez donc toujours la valeur en dessous de --memory, sinon la limite stricte a la priorité. Par défaut, la réservation de mémoire est identique à la limite de mémoire.

podman-update 1

NAME

podman-update - Update a container's resources

SYNOPSIS

podman update [options] container

DESCRIPTION

The podman update command allows you to update existing containers. You can update resources such as cpu, memory, and io settings for running or stopped containers.

To update a container, you can use the container name or ID.

To update the latest created container, you can use the --latest option.

OPTIONS

--blkio-weight=number

Block I/O (libaio) weight (10-1000). Default weight is 0, which means inherit parent's weight. This is a relative weight.

--blkio-weight-device=weight:device

Block I/O weight (relative weight) vs. other processes. The format is weight:major:minor. Can specify multiple devices.

--cpu-period=number

Limit the CPU usage of the specified container to a given percentage. Value is a percentage of the available CPU bandwidth (i.e. 50 is 50%).

This option is only supported on cgroups V1 rootful systems.

--cpu-shares=number

CPU shares (relative weight). Default is 1024.

--cpus=number

Keep container running and use this many CPUs. The value is a fractional number of CPUs. For example, 0.5 means one job runs on one CPU, and it can use at most 50% of the CPU time.

--cpuset-cpus=list

Limit the CPU cores that a container can use. List is a comma-separated value of integers. For example, 0,1. Default is to use all available CPU cores.

--cpuset-mems=list

Limit the memory nodes that a container can use. List is a comma-separated value of integers. For example, 0,1. Default is to use all available memory nodes.

--device-read-bps=rate

Limit read rate (bytes per second) from a device. Format is rate:major:minor.

--device-read-iops=rate

Limit read rate (IO per second) from a device. Format is rate:major:minor.

--device-write-bps=rate

Limit write rate (bytes per second) to a device. Format is rate:major:minor.

--device-write-iops=rate

Limit write rate (IO per second) to a device. Format is rate:major:minor.

--memory=number[unit]

Memory limit. unit can be b (bytes), k (kibibytes), m (mebibytes), or g (gibibytes).

--memory-reservation=number[unit]

Memory reservation. A soft limit to prefer memory allocation under high load. unit can be b (bytes), k (kibibytes), m (mebibytes), or g (gibibytes).

--memory-swap=number[unit]

A limit value equal to memory plus swap. A unit can be b (bytes), k (kibibytes), m (mebibytes), or g (gibibytes).

Must be used with the -m (--memory) flag. The argument value must be larger than that of
-m (--memory) By default, it is set to double the value of --memory.

Set number to -1 to enable unlimited swap.

This option is not supported on cgroups V1 rootless systems.

--memory-swappiness=number

Tune a container's memory swappiness behavior. Accepts an integer between 0 and 100.

This flag is only supported on cgroups V1 rootful systems.

--no-healthcheck

Disable any defined healthchecks for container.

--pids-limit=limit

Tune the container's pids limit. Set to -1 to have unlimited pids for the container. The default is 2048 on systems that support "pids" cgroup controller.

--restart=policy

Restart policy to follow when containers exit. Restart policy does not take effect if a container is stopped via the podman kill or podman stop commands.

Valid policy values are:

  • no : Do not restart containers on exit
  • never : Synonym for no; do not restart containers on exit
  • on-failure[:max_retries] : Restart containers when they exit with a non-zero exit code, retrying indefinitely or until the optional max_retries count is hit
  • always : Restart containers when they exit, regardless of status, retrying indefinitely
  • unless-stopped : Identical to always

Podman provides a systemd unit file, podman-restart.service, which restarts containers after a system reboot.

When running containers in systemd services, use the restart functionality provided by systemd. In other words, do not use this option in a container unit, instead set the Restart= systemd directive in the [Service] section. See podman-systemd.unit(5) and systemd.service(5).

--unsetenv=env

Unset environment variables from the container.

Note that the env updates only affect the main container process after the next start.

EXAMPLES

Update a container with a new cpu quota and period:

podman update --cpus=0.5 ctrID

Update the latest container with a new cpu value:

podman update --latest --cpus=1

Update a container with multiple options at ones:

podman update --cpus 5 --cpuset-cpus 0 --cpu-shares 123 --cpuset-mems 0 \  
  --memory 1G --memory-swap 2G --memory-reservation 2G \  
  --blkio-weight-device /dev/sda:123 --blkio-weight 123 \  
  --device-read-bps /dev/sda:10mb --device-write-bps /dev/sda:10mb \  
  --device-read-iops /dev/sda:1000 --device-write-iops /dev/sda:1000 \  
  --pids-limit 123 ctrID
