Une liste des problèmes courants et des solutions pour Podman

1) Variété de problèmes - Valider la version

Un grand nombre de problèmes signalés contre Podman se trouvent souvent déjà résolus dans les versions plus récentes du projet. Avant de signaler un problème, veuillez vérifier la version que vous utilisez avec podman version et la comparer à la dernière version documentée en haut du fichier ⟨README.md⟩ de Podman.

Si elles diffèrent, veuillez mettre à jour votre version de PODMAN à la dernière version possible et réessayer votre commande avant de signaler le problème.

2) Impossible d'utiliser le montage de volume, obtenir un refus d'autorisation

$ podman run -v ~/mycontent:/content fedora touch /content/file
touch: impossible de toucher '/content/file': Permission refusée

Solution

Ceci est parfois causé par SELinux, et parfois par des espaces de noms d'utilisateur.

Les systèmes d'étiquetage comme SELinux exigent que les bonnes étiquettes soient placées sur le contenu du volume monté dans un conteneur. Sans étiquette, le système de sécurité pourrait empêcher les processus s'exécutant à l'intérieur du conteneur d'utiliser le contenu. Par défaut, Podman ne modifie pas les étiquettes définies par le système d'exploitation.

Pour changer une étiquette dans le contexte du conteneur, vous pouvez ajouter l'un des deux suffixes :z ou :Z au montage de volume. Ces suffixes indiquent à Podman de réétiqueter les objets de fichier sur les volumes partagés. L'option z indique à Podman que deux conteneurs partagent le contenu du volume. En conséquence, Podman étiquette le contenu avec une étiquette de contenu partagé. Les étiquettes de volume partagé permettent à tous les conteneurs de lire/écrire le contenu. L'option Z indique à Podman d'étiqueter le contenu avec une étiquette privée non partagée. Seul le conteneur actuel peut utiliser un volume privé.

$ podman run -v ~/mycontent:/content:Z fedora touch /content/file

Assurez-vous que le contenu est privé pour le conteneur. Ne réétiquetez pas les répertoires système et le contenu. La réétiquetage du contenu système pourrait causer l'échec d'autres services confinés sur votre machine. Pour ces types de conteneurs, nous recommandons de désactiver la séparation SELinux. L'option --security-opt label=disable désactivera la séparation SELinux pour le conteneur.

$ podman run --security-opt label=disable -v ~:/home/user fedora touch /home/user/file

Dans les cas où l'image du conteneur s'exécute en tant qu'utilisateur spécifique, non-root, la solution consiste à corriger l'espace de noms d'utilisateur. Cela inclurait les images de conteneurs telles que l'image Jupyter Notebook (qui s'exécute en tant que « jovyan ») et l'image Postgres (qui s'exécute en tant que « postgres »). Dans les deux cas, utilisez le commutateur --userns pour mapper les espaces de noms d'utilisateur, le plus souvent en utilisant l'option keep-id.

$ podman run -v "$PWD":/home/jovyan/work --userns=keep-id jupyter/scipy-notebook

3) Aucune telle image ou les clés brutes ne peuvent contenir ':'

Lorsque vous effectuez une commande podman pull ou podman build et qu'une image « courante » ne peut pas être tirée, il est probable que le fichier /etc/containers/registries.conf ne soit pas installé ou soit potentiellement mal configuré.

Symptôme

$ sudo podman build -f Dockerfile
STEP 1: FROM alpine
error building: error creating build container: no such image "alpine" in registry: image not known

ou

$ sudo podman pull fedora
error pulling image "fedora": unable to pull fedora: error getting default registries to try: Near line 9 (last key parsed ''): Bare keys cannot contain ':'.

Solution

  • Vérifiez que le fichier /etc/containers/registries.conf existe. Si non, vérifiez que le paquet containers-common est installé.
  • Vérifiez que les entrées dans la liste unqualified-search-registries du fichier /etc/containers/registries.conf sont valides et accessibles.
•
c'est-à-dire unqualified-search-registries = ["registry.fedoraproject.org", "quay.io", "registry.access.redhat.com"]

4) http: le serveur a donné une réponse HTTP à un client HTTPS

Lorsque vous utilisez une commande Podman telle que build, commit, pull ou push vers un registre, la vérification TLS est activée par défaut. Si le chiffrement n'est pas utilisé avec ces commandes, cette erreur peut se produire.

Symptôme

$ sudo podman push alpine docker://localhost:5000/myalpine:latest
Getting image source signatures
Get https://localhost:5000/v2/: http: server gave HTTP response to HTTPS client

Solution

Par défaut, la vérification TLS est activée lors de la communication avec les registres depuis Podman. Si le registre n'exige pas de chiffrement, les commandes Podman telles que build, commit, pull et push échoueront à moins que la vérification TLS ne soit désactivée en utilisant l'option --tls-verify. REMARQUE : Il n'est absolument pas recommandé de communiquer avec un registre sans utiliser la vérification TLS.

  • Désactivez la vérification TLS en passant false à l'option tls-verify.
  • Par exemple : podman push --tls-verify=false alpine docker://localhost:5000/myalpine:latest

Pour une solution globale, les utilisateurs[1] peuvent créer le fichier /etc/containers/registries.conf.d/registry-NAME.conf (en remplaçant NAME par le nom de ce registre) avec le contenu suivant (en remplaçant FULLY.QUALIFIED.NAME.OF.REGISTRY par l'adresse de ce registre) :

[[registry]]
location = "FULLY.QUALIFIED.NAME.OF.REGISTRY"
insecure = true

[1] Si vous utilisez un Mac / Windows, vous devez exécuter podman machine ssh pour vous connecter à la machine podman avant d'ajouter l'entrée insecure au fichier registry—conf.

Ceci est une méthode non sécurisée et doit être utilisée avec prudence.

5) Les conteneurs sans root ne peuvent pas pinger les hôtes

Lorsque vous utilisez la commande ping depuis un conteneur non-root, la commande peut échouer en raison d'un manque de privilèges.

Symptôme

$ podman run --rm fedora ping -W10 -c1 redhat.com
PING redhat.com (209.132.183.105): 56 data bytes
--- redhat.com ping statistics ---
1 packets transmitted, 0 packets received, 100% packet loss

Solution

Il est fort probable qu'il soit nécessaire d'activer les pings non privilégiés sur l'hôte. Assurez-vous que l'UID de l'utilisateur fait partie de la plage dans le fichier /proc/sys/net/ipv4/ping_group_range.

Pour modifier sa valeur, vous pouvez utiliser quelque chose comme :

# sysctl -w "net.ipv4.ping_group_range=0 2000000"

Pour rendre le changement permanent, vous devrez ajouter un fichier dans /etc/sysctl.d contenant net.ipv4.ping_group_range=0 $MAX_UID.

6) La construction se bloque lorsque le Dockerfile contient la commande useradd

Lorsque le Dockerfile contient une commande comme RUN useradd -u 99999000 -g users newuser, la construction peut se bloquer.

Symptôme

Si vous utilisez une commande useradd dans un Dockerfile avec un UID/GID important, cela créera un fichier sparse volumineux /var/log/lastlog. Cela peut faire que la construction se bloque indéfiniment. Le langage Go ne prend pas correctement en charge les fichiers sparse, ce qui peut entraîner la création de fichiers énormes.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Solution

Si l'entrée dans le Dockerfile ressemblait à : RUN useradd -u 99999000 -g users newuser, ajoutez le paramètre --no-log-init pour le modifier en : RUN useradd --no-log-init -u 99999000 -g users newuser. Cette option indique à useradd de ne pas créer le fichier lastlog.

7) Permission refusée lors de l'exécution de commandes Podman

Lorsque Podman sans privilèges tente d'exécuter un conteneur sur un répertoire personnel non exécutable (noexec), une erreur de permission sera générée.

Symptôme

Si vous exécutez Podman ou Buildah sur un répertoire personnel monté en mode noexec, ils échoueront avec un message tel que :

$ podman run centos:7
standard_init_linux.go:203: exec user process caused "permission denied"

Solution

Étant donné que l'administrateur du système a configuré votre répertoire personnel en mode noexec, vous ne serez pas autorisé à exécuter des conteneurs à partir du stockage de votre répertoire personnel. Il est possible de contourner ce problème en spécifiant manuellement un chemin de stockage de conteneur qui ne se trouve pas sur un montage noexec. Copiez simplement le fichier /etc/containers/storage.conf vers ~/.config/containers/ (en créant le répertoire si nécessaire). Spécifiez un répertoire graphroot qui n'est pas sur un point de montage noexec et auquel vous avez des privilèges de lecture/écriture. Vous devrez également modifier d'autres champs pour qu'ils pointent vers des répertoires inscriptibles.

Par exemple :

$ cat ~/.config/containers/storage.conf
[storage]
  driver = "overlay"
  runroot = "/run/user/1000"
  graphroot = "/execdir/myuser/storage"
  [storage.options]
    mount_program = "/bin/fuse-overlayfs"

8) Permission refusée lors de l'exécution de systemd dans un conteneur Podman

Lors de l'exécution de systemd en tant que PID 1 à l'intérieur d'un conteneur sur une machine isolée par SELinux, il doit écrire dans le système de fichiers cgroup.

Symptôme

Systemd reçoit un message de permission refusée en tentant d'écrire dans le système de fichiers cgroup, et des messages AVC commencent à apparaître dans le fichier audit.log ou dans le journal du système.

Solution

Les versions plus récentes de Podman (2.0 ou ultérieure) prennent en charge l'exécution de conteneurs basés sur init avec des étiquettes SELinux différentes, ce qui permet au processus du conteneur d'accéder au système de fichiers cgroup. Cette fonctionnalité nécessite container-selinux-2.132 ou des versions plus récentes.

Avant Podman 2.0, le booléen SELinux container_manage_cgroup permettait aux processus des conteneurs d'écrire dans le système de fichiers cgroup. Activez ce booléen, sur les systèmes isolés par SELinux, pour permettre à systemd de fonctionner correctement dans le conteneur. Ne le faites que sur les systèmes exécutant d'anciennes versions de Podman.

# setsebool -P container_manage_cgroup true

9) Newuidmap manquant lors de l'exécution de commandes Podman sans privilèges

Podman sans privilèges nécessite que les programmes newuidmap et newgidmap soient installés.

Symptôme

Si vous exécutez Podman ou Buildah en tant qu'utilisateur sans privilèges, vous recevez une erreur signalant l'absence de l'exécutable newuidmap.

$ podman run -ti fedora sh
command required for rootless mode with multiple IDs: exec: "newuidmap": executable file not found in $PATH

Solution

Installez une version de shadow-utils qui inclut ces exécutables. Notez que pour RHEL et CentOS 7, au moins la version 7.7 doit être installée pour que la prise en charge soit disponible.

10) rootless setup user: argument invalide

Podman sans privilèges nécessite que l'utilisateur qui l'exécute ait une plage d'UIDs listée dans /etc/subuid et /etc/subgid.

Symptôme

Un utilisateur, soit via --user, soit via la configuration par défaut pour l'image, n'est pas mappé à l'intérieur de l'espace de noms.

$ podman run --rm -ti --user 1000000 alpine echo hi
Error: container create failed: container_linux.go:344: starting container process caused "setup user: invalid argument"

Solution

Mettez à jour /etc/subuid et /etc/subgid avec des champs pour les utilisateurs qui ressemblent à ceci :

$ cat /etc/subuid
johndoe:100000:65536
test:165536:65536

Le format de ce fichier est NOMUTILISATEUR:UID:PLAGE

  • nom d'utilisateur tel qu'il apparaît dans /etc/passwd ou getpwent.
  • L'UID initial alloué à l'utilisateur.
  • La taille de la plage d'UIDs allouée à l'utilisateur.

Cela signifie que johndoe se voit attribuer les UIDs 100000-165535 ainsi que son UID standard dans le fichier /etc/passwd.

Vous devez vous assurer que chaque utilisateur dispose d'une plage d'UIDs unique, car des UIDs qui se chevauchent pourraient potentiellement permettre à un utilisateur d'attaquer un autre utilisateur. De plus, assurez-vous que la plage d'UIDs que vous allouez peut couvrir tous les UIDs requis par le conteneur. Par exemple, si le conteneur a un utilisateur avec l'UID 10000, assurez-vous d'avoir au moins 10000 subuids, et si le conteneur doit être exécuté en tant qu'utilisateur avec l'UID 1000000, assurez-vous d'avoir au moins 1000000 subuids.

Vous pouvez également utiliser le programme usermod pour attribuer des UIDs à un utilisateur.

Si vous mettez à jour le fichier /etc/subuid ou /etc/subgid, vous devez arrêter tous les conteneurs en cours d'exécution et tuer le processus de pause. Ceci est fait automatiquement par la commande system migrate, qui peut également être utilisée pour arrêter tous les conteneurs et tuer le processus de pause.

# usermod --add-subuids 200000-201000 --add-subgids 200000-201000 johndoe
# grep johndoe /etc/subuid /etc/subgid
/etc/subuid:johndoe:200000:1001
/etc/subgid:johndoe:200000:1001

11) Changer l'emplacement du Graphroot entraîne une permission refusée

Lorsque je modifie l'emplacement de stockage du graphroot dans storage.conf, la prochaine fois que j'exécute Podman, je reçois une erreur telle que :

# podman run -p 5000:5000 -it centos bash
bash: error while loading shared libraries: /lib64/libc.so.6: cannot apply additional memory protection after relocation: Permission denied

Par exemple, l'administrateur configure un disque de spare pour être monté sur /src/containers, et pointe storage.conf vers ce répertoire.

Symptôme

SELinux empêche les conteneurs d'utiliser des emplacements arbitraires pour le stockage overlay. Ces répertoires doivent être étiquetés avec les mêmes étiquettes que si le contenu était sous /var/lib/containers/storage.

Solution

Informez SELinux du nouveau stockage de conteneurs en créant un enregistrement d'équivalence. Cela indique à SELinux d'étiqueter le contenu sous le nouveau chemin, comme s'il était stocké sous /var/lib/containers/storage.

# semanage fcontext -a -e /var/lib/containers /srv/containers
# restorecon -R -v /srv/containers

La commande semanage ci-dessus indique à SELinux de définir l'étiquetage par défaut de /srv/containers pour qu'il corresponde à /var/lib/containers. La commande restorecon indique à SELinux d'appliquer les étiquettes au contenu réel.

Désormais, tout nouveau contenu créé dans ces répertoires sera automatiquement créé avec la bonne étiquette.

12) Le pull d'image anonyme échoue avec 'nom d'utilisateur/mot de passe invalide'

Le tirage d'une image anonyme qui ne nécessite pas d'authentification peut entraîner une erreur nom d'utilisateur/mot de passe invalide.

Symptôme

Si vous tirez une image anonyme, une qui ne devrait pas nécessiter d'identifiants, vous pouvez recevoir une erreur nom d'utilisateur/mot de passe invalide si vous avez des identifiants établis dans le fichier d'authentification pour le registre de conteneurs cible qui ne sont plus valides.

$ podman run -it --rm docker://docker.io/library/alpine:latest ls
Trying to pull docker://docker.io/library/alpine:latest...ERRO[0000] Error pulling image ref //alpine:latest: Error determining manifest MIME type for docker://alpine:latest: unable to retrieve auth token: invalid username/password
Failed
Error: unable to pull docker://docker.io/library/alpine:latest: unable to pull image: Error determining manifest MIME type for docker://alpine:latest: unable to retrieve auth token: invalid username/password

Cela peut se produire si le fichier d'authentification est modifié 'à la main' ou si les identifiants sont établis localement puis que le mot de passe est mis à jour ultérieurement dans le registre de conteneurs.

Solution

Selon l'outil de conteneur utilisé pour établir les identifiants, utilisez podman logout ou docker logout pour supprimer les identifiants du fichier d'authentification.

13) L'exécution de Podman à l'intérieur d'un conteneur provoque des plantages de conteneur et des états incohérents

L'exécution de Podman dans un conteneur et le transfert de certains, mais pas tous, des répertoires hôtes requis peuvent entraîner un comportement incohérent du conteneur.

Symptôme

Après avoir créé un conteneur avec les répertoires de stockage de Podman montés depuis l'hôte et r

Running Podman inside a container

When running Podman inside a container, all containers show their state as "configured" or "created", even if they were running or stopped.

Solution

When running Podman inside a container, it is recommended to mount at a minimum /var/lib/containers/storage/ as a volume. Typically, you will not mount in the host version of the directory, but if you wish to share containers with the host, you can do so. If you do mount in the host's /var/lib/containers/storage, however, you must also mount in the host's /run/libpod and /run/containers/storage directories. Not doing this will cause Podman in the container to detect that temporary files have been cleared, leading it to assume a system restart has taken place. This can cause Podman to reset container states and lose track of running containers.

For running containers on the host from inside a container, we also recommend the Podman remote client ⟨docs/tutorials/remote_client.md⟩, which only requires a single socket to be mounted into the container.

14) Rootless 'podman build' fails EPERM on NFS:

NFS enforces file creation on different UIDs on the server side and does not understand user namespace, which rootless Podman requires. When a container root process like YUM attempts to create a file owned by a different UID, NFS Server denies the creation. NFS is also a problem for the file locks when the storage is on it. Other distributed file systems (for example: Lustre, Spectrum Scale, the General Parallel File System (GPFS)) are also not supported when running in rootless mode as these file systems do not understand user namespace.

Symptom

$ podman build .
ERRO[0014] Error while applying layer: ApplyLayer exit status 1 stdout:  stderr: open /root/.bash_logout: permission denied
error creating build container: Error committing the finished image: error adding layer with blob "sha256:a02a4930cb5d36f3290eb84f4bfa30668ef2e9fe3a1fb73ec015fc58b9958b17": ApplyLayer exit status 1 stdout:  stderr: open /root/.bash_logout: permission denied

Solution

Choose one of the following:
* Set up containers/storage in a different directory, not on an NFS share.
* Create a directory on a local file system.
* Edit ~/.config/containers/containers.conf and point the volume_path option to that local directory. (Copy /usr/share/containers/containers.conf if ~/.config/containers/containers.conf does not exist)
* Otherwise just run Podman as root, via sudo podman

20) Passed-in devices or files can't be accessed in rootless container

As a non-root user you have group access rights to a device or files that you want to pass into a rootless container with --device=... or --volume=...

Symptom

Any access inside the container is rejected with "Permission denied".

Solution

The runtime uses setgroups(2) hence the process loses all additional groups the non-root user has. Use the --group-add keep-groups flag to pass the user's supplementary group access into the container. Currently only available with the crun OCI runtime.

21) A rootless container running in detached mode is closed at logout

When running a container with a command like podman run --detach httpd as a rootless user, the container is closed upon logout and is not kept running.

Symptom

When logging out of a rootless user session, all containers that were started in detached mode are stopped and are not kept running. As the root user, these same containers would survive the logout and continue running.

Solution

When systemd notes that a session that started a Podman container has exited, it will also stop any containers that have been associated with it. To avoid this, use the following command before logging out: loginctl enable-linger. To later revert the linger functionality, use loginctl disable-linger.

22) Containers default detach keys conflict with shell history navigation

When running containers in the foreground, hitting Ctrl+p followed by Ctrl+q detaches the container. However, in many shells, this sequence of key presses also manipulates the shell history. This is confusing for users.

Symptom

Attempting to detach a container running in the foreground may accidentally move you to a different line in the shell history.

Solution

You can change the detach keys sequence by setting the detach-keys option in the containers.conf file. For example, to change the sequence to Ctrl+s followed by Ctrl+w, you would add the following lines to your ~/.config/containers/containers.conf file:

[containers]
detach-keys = "ctrl-s,ctrl-w"

Note that if the containers.conf file does not exist, you will need to copy the default file from /usr/share/containers/containers.conf to ~/.config/containers/containers.conf and then edit it.

23) Rootless container exit when using systemd v248+

As of systemd v248, systemd terminates lingering user sessions if they are not actively connected to a graphical session or a TTY. This behavior impacts rootless containers started from such sessions, causing them to exit unexpectedly.

Symptom

Rootless containers started in detached mode exit when the user logs out or disconnects from their graphical session or TTY, even if `loginctl enable-linger` was previously set.

Solution

To keep rootless containers running, you need to manually start them as a service via systemd. Create a user systemd service file (e.g., ~/.config/systemd/user/mycontainer.service) with the following content:

[Unit]
Description=My Detached Container
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
ExecStart=/usr/bin/podman run --rm --name mycontainer IMAGE
ExecStop=/usr/bin/podman stop mycontainer
Restart=on-failure

[Install]
WantedBy=default.target

Replace IMAGE with the actual image name and adjust the container name and other podman run options as needed. Then, enable and start the service:

$ systemctl --user enable mycontainer.service
$ systemctl --user start mycontainer.service

This approach ensures the container runs as a managed service, persisting across user logouts and system reboots.

22) Les touches de détachement par défaut entrent en conflit avec la navigation dans l'historique du shell

Podman utilise par défaut ctrl-p,ctrl-q pour détacher un conteneur en cours d'exécution. Les shells bash et zsh utilisent par défaut ctrl-p pour afficher la commande précédente. Cela pose des problèmes lors de l'exécution d'un shell à l'intérieur d'un conteneur.

Symptôme

Avec la combinaison de touches de détachement par défaut ctrl-p,ctrl-q, la navigation dans l'historique du shell (testée dans bash et zsh) utilisant ctrl-p pour accéder à la commande précédente n'affichera pas cette commande précédente, ni quoi que ce soit d'autre. Conmon attend un caractère supplémentaire pour voir si l'utilisateur souhaite se détacher du conteneur. L'ajout de caractères supplémentaires à la commande provoquera son affichage ainsi que le caractère supplémentaire. Si l'utilisateur tape ctrl-p une deuxième fois, le shell affichera l'avant-dernière commande.

Solution

La solution consiste à modifier les detach_keys par défaut. Par exemple, pour modifier les valeurs par défaut en ctrl-q,ctrl-q, utilisez l'option --detach-keys.

$ podman run -ti --detach-keys ctrl-q,ctrl-q fedora sh

Pour que ce changement soit le défaut pour tous les conteneurs, les utilisateurs peuvent modifier le fichier containers.conf. Cela peut être fait simplement dans votre répertoire personnel, en ajoutant les lignes suivantes à containers.conf de l'utilisateur :

$ cat >> ~/.config/containers/containers.conf << _eof
[engine]
detach_keys="ctrl-q,ctrl-q"
_eof

Afin d'affecter les conteneurs exécutés en tant que root et tous les utilisateurs, modifiez les valeurs par défaut du système dans /etc/containers/containers.conf.

23) Un conteneur avec des ports exposés ne s'exécute pas dans un pod

Un conteneur avec des ports publiés avec l'option --publish ou -p ne peut pas être exécuté dans un pod.

Symptôme

$ podman pod create --name srcview -p 127.0.0.1:3434:3434 -p 127.0.0.1:7080:7080 -p 127.0.0.1:3370:3370                        4b2f4611fa2cbd60b3899b936368c2b3f4f0f68bc8e6593416e0ab8ecb0a3f1d
$ podman run --pod srcview --name src-expose -p 3434:3434 -v "${PWD}:/var/opt/localrepo":Z,ro sourcegraph/src-expose:latest serve /var/opt/localrepo
Error: cannot set port bindings on an existing container network namespace

Solution

C'est une limitation connue. Si un conteneur doit être exécuté dans un pod, il n'est pas nécessaire de publier le port pour les conteneurs du pod. Le port doit uniquement être publié par le pod lui-même. Les piles réseau des pods agissent comme la pile réseau de l'hôte - vous avez une variété de conteneurs dans le pod, et des programmes dans le conteneur, partageant tous une seule interface et une seule adresse IP, ainsi que les ports associés. Si un conteneur se lie à un port, aucun autre conteneur ne peut utiliser ce port dans le pod tant qu'il est utilisé. Les conteneurs du pod peuvent également communiquer via localhost en faisant en sorte qu'un conteneur se lie à localhost dans le pod, et qu'un autre se connecte à ce port.

Dans l'exemple de la section symptôme, supprimer le -p 3434:3434 permettrait à la commande podman run de se terminer, et le conteneur faisant partie du pod aurait toujours accès à ce port. Par exemple :

$ podman run --pod srcview --name src-expose -v "${PWD}:/var/opt/localrepo":Z,ro sourcegraph/src-expose:latest serve /var/opt/localrepo

25) podman run --rootfs link/to//read/only/dir ne fonctionne pas

Une erreur telle que "OCI runtime error" sur un système de fichiers en lecture seule ou l'erreur "{image} n'est pas un chemin absolu ou est un lien symbolique" sont souvent des indicateurs de ce problème. Symptôme

Solution

Exécutez le conteneur une fois en mode lecture/écriture. Podman créera tous les FDs sur le rootfs, et à partir de ce moment, vous pourrez exécuter avec un rootfs en lecture seule.

26) L'exécution de conteneurs avec des limites de ressources échoue avec une erreur de permission

Symptôme

L'exécution d'un conteneur avec des options de limite de ressources échouera avec une erreur similaire à la suivante :

--cpus, --cpu-period, --cpu-quota, --cpu-shares :

--cpuset-cpus, --cpuset-mems :

Error: OCI runtime error: crun: the requested cgroup controller `cpuset` is not available

Cela signifie que la délégation des limites de ressources n'est pas activée pour l'utilisateur actuel.

Solution

Vous pouvez vérifier si la délégation des limites de ressources est activée en exécutant la commande suivante :

$ cat "/sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service/cgroup.controllers"

Exemple de sortie possible :

memory pids

Dans l'exemple ci-dessus, cpu et cpuset ne sont pas listés, ce qui signifie que l'utilisateur actuel n'a pas la permission de définir des limites de CPU ou de CPUSET.

Si vous souhaitez activer la délégation des limites de CPU ou de CPUSET pour tous les utilisateurs, vous pouvez créer le fichier /etc/systemd/system/user@.service.d/delegate.conf avec le contenu suivant :

[Service]
Delegate=memory pids cpu cpuset

Après vous être déconnecté et reconnecté, vous devriez avoir la permission de définir les limites de CPU et de CPUSET.

Symptôme

Les règles de pare-feu créées par podman sont perdues lorsque le pare-feu est rechargé.

Solution

@ranjithrajaram a créé un hook systemd pour résoudre ce problème.

1) Pour "firewall-cmd --reload", créez un fichier d'unité systemd avec le contenu suivant :

[Unit]

Wants=dbus.service
After=dbus.service
[Service]
Type=simple
ExecStart=/bin/bash -c '/bin/busctl monitor --system --match "interface=org.fedoraproject.FirewallD1,member=Reloaded" --match "interface=org.fedoraproject.FirewallD1,member=PropertiesChanged" | while read -r line ; do podman network reload --all ; done'
[Install]
WantedBy=default.target

[Unit]
Description=podman network reload
Wants=firewalld.service
After=firewalld.service
PartOf=firewalld.service
[Service]
Type=simple
RemainAfterExit=yes
ExecStart=/usr/bin/podman network reload --all
[Install]
WantedBy=default.target

Pour RHEL 8, vous pouvez utiliser le script bash suivant en une seule ligne.

Wants=dbus.service

34) Le conteneur crée un fichier qui n'appartient pas à l'UID régulier de l'utilisateur

Après avoir exécuté un conteneur avec Podman sans privilèges root, l'utilisateur non root voit un UID et un GID numériques au lieu d'un nom d'utilisateur et d'un nom de groupe.

Symptôme

Lors de la liste des permissions de fichiers avec ls -l sur l'hôte, dans un répertoire qui a été passé comme --volume /some/dir à podman run, l'UID et le GID sont affichés au lieu du nom d'utilisateur et du nom de groupe correspondants. Les numéros d'UID et de GID affichés proviennent des plages d'UID et de GID subordonnés de l'utilisateur sur le système hôte.

Un exemple

$ mkdir dir1
$ chmod 777 dir1
$ podman run --rm -v ./dir1:/dir1:Z   
             --user 2003:2003   
             docker.io/library/ubuntu bash -c "touch /dir1/a; chmod 600 /dir1/a"
$ ls -l dir1/a
-rw-------. 1 102002 102002 0 Jan 19 19:35 dir1/a
$ less dir1/a
less: dir1/a: Permission denied

Solution

Si vous souhaitez lire, chown, ou supprimer un tel fichier, entrez dans un espace de noms utilisateur. Au lieu d'exécuter des commandes telles que less dir1/a ou rm dir1/a, vous devez préfixer la ligne de commande avec podman unshare, c'est-à-dire podman unshare less dir1/a ou podman unshare rm dir1/a. Pour changer la propriété du fichier dir1/a à l'UID et au GID de votre utilisateur régulier, exécutez podman unshare chown 0:0 dir1/a. Un fichier ayant la propriété 0:0 dans l'espace de noms utilisateur appartient à l'utilisateur régulier sur l'hôte. Pour utiliser les fonctionnalités de Bash, telles que l'expansion de variables et le globbing, vous devez encapsuler la commande avec bash -c, par exemple podman unshare bash -c 'ls $HOME/dir1/a*'.

Aurait-il été possible d'exécuter Podman d'une autre manière pour que votre utilisateur régulier devienne le propriétaire du fichier ? Oui, vous pouvez utiliser l'option --userns keep-id:uid=$uid,gid=$gid pour modifier la façon dont les UID et GID sont mappés entre le conteneur et l'hôte. Essayons.

Dans l'exemple ci-dessus, ls -l affiche l'UID 102002 et le GID 102002. Définissez les variables shell

$ uid_from_ls=102002
$ gid_from_ls=102002

Définissez les variables shell sur l'UID et le GID subordonnés les plus bas

$ lowest_subuid=$(podman info --format "{{ (index .Host.IDMappings.UIDMap 1).HostID }}")
$ lowest_subgid=$(podman info --format "{{ (index .Host.IDMappings.GIDMap 1).HostID }}")

Calculez l'UID et le GID à l'intérieur du conteneur qui correspondent au propriétaire du fichier créé sur l'hôte.

$ uid=$(( $uid_from_ls - $lowest_subuid + 1))
$ gid=$(( $gid_from_ls - $lowest_subgid + 1))

(Dans le calcul, on a supposé qu'il n'y avait qu'une seule plage de subuid et une seule plage de subgid)

$ echo $uid 2003 $ echo $gid 2003

Le calcul montre que l'UID est 2003 et le GID est 2003 à l'intérieur du conteneur. Ce n'est pas surprenant car c'est ce qui a été spécifié précédemment avec --user=2003:2003, mais le même calcul pourrait être utilisé chaque fois qu'un nom d'utilisateur est spécifié ou que l'option --user n'est pas utilisée.

Exécutez à nouveau le conteneur, mais cette fois avec les UID et GID mappés

$ mkdir dir1
$ chmod 777 dir1
$ podman run --rm
  -v ./dir1:/dir1:Z   
  --user $uid:$gid   
  --userns keep-id:uid=$uid,gid=$gid   
     docker.io/library/ubuntu bash -c "touch /dir1/a; chmod 600 /dir1/a"
$ id -u
tester
$ id -g
tester
$ ls -l dir1/a
-rw-------. 1 tester tester 0 Jan 19 20:31 dir1/a
$

Dans cet exemple, l'option --user a spécifié un utilisateur sans privilèges root dans le conteneur. Étant donné que l'utilisateur sans privilèges root pourrait également être spécifié dans l'image du conteneur, par exemple :

$ podman image inspect --format "user: {{.User}}" IMAGE
user: hpc

le même problème pourrait également survenir même sans spécifier --user.

Une autre variante du même problème peut survenir lors de l'utilisation de --user=root:root (par défaut), mais où l'utilisateur root crée des fichiers n'appartenant pas à root d'une manière ou d'une autre (par exemple, en les créant lui-même, ou en changeant l'UID effectif à un utilisateur sans privilèges root puis en créant des fichiers).

Voir également l'astuce de dépannage :

⟨#39-podman-run-échoue-avec-l'erreur-espace-de-noms-non-reconnu-keep-iduid1000gid1000-passé⟩

35) Les périphériques ou fichiers transmis ne sont pas accessibles dans le conteneur sans privilèges root (problème de mappage UID/GID)

En tant qu'utilisateur non root, vous avez des droits d'accès aux périphériques, fichiers et répertoires que vous souhaitez passer dans un conteneur sans privilèges root avec --device=..., --volume=... ou --mount=...

Podman mappe par défaut un utilisateur non root à l'intérieur d'un conteneur vers l'un des UID subordonnés et GID subordonnés de l'utilisateur sur l'hôte. Lorsque l'utilisateur du conteneur tente d'accéder à un fichier, une erreur "Permission denied" peut survenir car l'utilisateur du conteneur n'a pas les permissions de l'utilisateur régulier de l'hôte.

Symptôme

•
Tout accès à l'intérieur du conteneur est rejeté avec "Permission denied" pour les fichiers, répertoires ou périphériques transmis au conteneur avec --device=..,--volume=.. ou --mount=.., par exemple 
$ mkdir dir1
$ chmod 700 dir1
$ podman run --rm -v ./dir1:/dir1:Z   
             --user 2003:2003   
             docker.io/library/ubuntu ls /dir1
ls: impossible d'ouvrir le répertoire '/dir1': Permission denied

Solution

Nous suivons essentiellement la même solution que dans le conseil de dépannage précédent :

⟨#34-le-conteneur-crée-un-fichier-qui-n'appartient-pas-à-l'UID-régulier-de-l'utilisateur⟩

mais pour ce problème, l'UID et le GID du conteneur ne peuvent pas être calculés aussi facilement par simple addition et soustraction.

En d'autres termes, il peut être plus difficile de trouver l'UID et le GID à l'intérieur du conteneur que nous voulons mapper à l'utilisateur régulier sur l'hôte.

Si l'option --user est utilisée avec un UID et un GID numériques pour spécifier un utilisateur sans privilèges root, nous connaissons déjà la réponse.

Si l'option --user est utilisée avec un nom d'utilisateur et un nom de groupe, nous pourrions rechercher l'UID et le GID dans le fichier /etc/passwd du conteneur.

35) Dépannage de l'utilisateur de conteneur sans privilèges

Si l'utilisateur du conteneur n'est pas défini via --user mais plutôt à partir de l'image du conteneur, nous pouvons inspecter l'image du conteneur

$ podman image inspect --format "user: {{.User}}" IMAGE
user: hpc

et ensuite le rechercher dans /etc/passwd du conteneur.

Si le problème survient dans un conteneur qui est démarré pour s'exécuter en tant que root mais qui passe ensuite à un UID effectif d'un utilisateur sans privilèges, il peut être moins simple de trouver l'UID et le GID. La lecture du Containerfile, du Dockerfile ou de /etc/passwd pourrait donner un indice.

Pour exécuter le conteneur avec l'UID et le GID du conteneur sans privilèges mappés à l'UID et au GID réguliers de l'utilisateur sur l'hôte, suivez ces étapes :

Définissez les variables shell uid et gid dans un shell Bash avec l'UID et le GID de l'utilisateur qui s'exécutera dans le conteneur, par exemple :

$ uid=2003
$ gid=2003

et exécutez

$ mkdir dir1
$ echo hello > dir1/file.txt
$ chmod 700 dir1/file.txt
$ podman run --rm   
  -v ./dir1:/dir1:Z   
  --user $uid:$gid   
  --userns keep-id:uid=$uid,gid=$gid   
  docker.io/library/alpine cat /dir1/file.txt
hello

Voir aussi l'astuce de dépannage :

⟨#39-podman-run-fails-with-error-unrecognized-namespace-mode-keep-iduid1000gid1000-passed⟩

36) Les images dans les magasins supplémentaires peuvent être supprimées même si des conteneurs les utilisent

Lorsqu'une image dans un magasin supplémentaire est utilisée, elle n'est pas verrouillée et peut donc être supprimée même si des conteneurs l'utilisent.

Symptôme

WARN[0000] Impossible d'accéder à la couche inférieure "/var/lib/containers/storage/overlay/l/7HS76F2P5N73FDUKUQAOJA3WI5" car elle n'existe pas. Parcours du stockage pour recréer les symlinks manquants.

Solution

Il incombe à l'utilisateur de s'assurer que les images dans un magasin supplémentaire ne sont pas supprimées pendant qu'elles sont utilisées par des conteneurs dans un autre magasin.

37) Synchronisation des corrections de bogues pour podman-remote ou les configurations utilisant l'API Podman

Après avoir mis à niveau Podman vers une nouvelle version, un problème avec la version précédente de Podman persiste lors de l'utilisation de podman-remote.

Symptôme

Lors de l'exécution de commandes podman remote avec le Podman le plus récent, des problèmes qui ont été corrigés dans une version antérieure de Podman peuvent survenir soit du côté du client Podman, soit du côté du serveur Podman.

Solution

Lors de la mise à niveau de Podman vers une version particulière pour les corrections nécessaires, les utilisateurs font souvent l'erreur de ne mettre à niveau que le client Podman. Cependant, supposez qu'une configuration utilise podman-remote ou utilise un client qui communique avec le serveur Podman sur une machine distante via l'API REST. Dans ce cas, il est nécessaire de mettre à niveau à la fois le client Podman et le serveur Podman fonctionnant sur la machine distante. Le client et le serveur Podman doivent être mis à niveau vers la même version.

Exemple : Si un bogue particulier a été corrigé dans la version v4.1.0, le client Podman doit avoir la version v4.1.0 et le serveur Podman doit avoir la version v4.1.0.

38) Des retours chariot inattendus sont affichés sur le terminal

Lors de l'utilisation de l'indicateur --tty (-t), des retours chariot inattendus sont affichés sur le terminal.

Symptôme

Le programme du conteneur imprime une nouvelle ligne (\n) mais le terminal affiche un retour chariot et une nouvelle ligne (\r\n).

$ podman run --rm -t fedora echo abc | od -c
0000000   a   b   c  \r  \n
0000005

Lorsqu'il est exécuté directement sur l'hôte, le résultat est conforme aux attentes.

$ echo abc | od -c
0000000   a   b   c  \n
0000004

Des retours chariot supplémentaires peuvent également décaler l'invite vers la droite.

$ podman run --rm -t fedora sh -c "echo 1; echo 2; echo 3" | cat -A
1^M$
    2^M$
        3^M$
            $

Solution

Exécutez Podman sans l'indicateur --tty (-t).

$ podman run --rm fedora echo abc | od -c
0000000   a   b   c  \n
0000004

L'indicateur --tty (-t) ne doit être utilisé que lorsque le programme nécessite une interaction utilisateur dans le terminal, par exemple en attendant que l'utilisateur tape une réponse à une question.

D'où vient le retour chariot \r supplémentaire ?

Le \r supplémentaire n'est pas émis par Podman mais par le terminal. En fait, une reconfiguration du terminal peut faire disparaître le \r supplémentaire.

$ podman run --rm -t fedora /bin/sh -c "stty -onlcr && echo abc" | od -c
0000000   a   b   c  \n
0000004

39) Podman run échoue avec l'erreur : mode de namespace non reconnu keep-id:uid=1000,gid=1000 passé

Podman 4.3.0 a introduit les options uid et gid qui peuvent être fournies à --userns keep-id et qui ne sont pas reconnues par les anciennes versions de Podman.

Symptôme

Lors de l'utilisation d'une version de Podman antérieure à 4.3.0, les options uid et gid ne sont pas reconnues et une erreur "mode de namespace non reconnu" est levée.

$ uid=1000
$ gid=1000
$ podman run --rm
  --user $uid:$gid   
  --userns keep-id:uid=$uid,gid=$gid   
     docker.io/library/ubuntu /bin/cat /proc/self/uid_map
Error: unrecognized namespace mode keep-id:uid=1000,gid=1000 passed
$

Solution

Utilisez les options --uidmap et --gidmap pour décrire le même mappage UID et GID.

Exécutez

$ uid=1000
$ gid=1000
$ subuidSize=$(( $(podman info --format "{{ range   
   .Host.IDMappings.UIDMap }}+{{.Size }}{{end }}" ) - 1 ))
$ subgidSize=$(( $(podman info --format "{{ range   
   .Host.IDMappings.GIDMap }}+{{.Size }}{{end }}" ) - 1 ))
$ podman run --rm   
  --user $uid:$gid   
  --uidmap 0:1:$uid   
  --uidmap $uid:0:1   
  --uidmap $(($uid+1)):$(($uid+1)):$(($subuidSize-$uid))   
  --gidmap 0:1:$gid   
  --gidmap $gid:0:1   
  --gidmap $(($gid+1)):$(($gid+1)):$(($subgidSize-$gid))   
     docker.io/library/ubuntu /bin/cat /proc/self/uid_map
         0          1       1000
      1000          0          1
      1001       1001      64536

qui utilise le même mappage UID et GID qu'en spécifiant --userns keep-id:uid=$uid,gid=$gid avec Podman 4.3.0 (ou version ultérieure)

$ uid=1000
$ gid=1000
$ podman run --rm   
  --user $uid:$gid   
  --userns keep-id:uid=$uid,gid=$gid   
     docker.io/library/ubuntu /bin/cat /proc/self/uid_map
         0          1       1000
      1000          0          1
      1001       1001      64536

Remplacez /bin/cat /proc/self/uid_map par /bin/cat /proc/self/gid_map pour afficher le mappage GID.

40) Podman ne trouve pas l'image attendue avec l'erreur localisant l'image tirée , image inconnue

Lorsque vous essayez d'exécuter une commande Podman qui tire une image du stockage local ou d'un dépôt distant, une erreur indiquant "image inconnue" ou "erreur lors de la localisation de l'image tirée" est levée. Même si l'image avait été vérifiée avant l'invocation de la commande Podman.

Symptôme

Après avoir vérifié qu'une image est en place soit localement, soit dans un dépôt distant, une commande Podman faisant référence à cette image échoue de manière similaire à :

# ls Containerfile
FROM registry.access.redhat.com/ubi8-minimal:latest
MAINTAINER Podman Community
USER root
# podman build .
STEP 1/2: FROM registry.access.redhat.com/ubi8-minimal
Trying to pull registry.access.redhat.com/ubi8-minimal:latest...
Getting image source signatures
Checking if image destination supports signatures
Copying blob a6577091999b done
Copying config abb1ba1bce done
Writing manifest to image destination
Storing signatures
Error: error creating build container: error locating pulled image "registry.access.redhat.com/ubi8-minimal:latest" name in containers storage: registry.access.redhat.com/ubi8-minimal:latest: image not known

Solution

La cause générale est un problème de temporisation. Pour rendre les commandes Podman aussi efficaces que possible, des verrous de lecture et d'écriture ne sont établis que pour les sections critiques du code. Lors du tirage d'une image d'un dépôt, une copie de cette image est d'abord écrite dans le stockage local à l'aide d'un verrou d'écriture. Ce verrou est relâché avant que l'image ne soit acquise/lue. Si un autre processus exécute une commande nuisible telle que podman system prune --all ou podman system reset ou podman rmi --all, entre le moment où l'image est écrite et avant que le premier processus ne puisse l'acquérir, ce type d'erreur image inconnue peut survenir.

Les mainteneurs de Podman ont envisagé des verrous plus robustes pour fermer cette fenêtre de temporisation. Cependant, le ralentissement que toutes les commandes Podman rencontreraient n'a pas été considéré comme valant le coût de fermeture complète de cette petite fenêtre de temporisation.

41) Une étape de build podman avec --mount=type=secret échoue avec opération non autorisée

L'exécution d'une étape dans un Dockerfile/Containerfile qui monte des secrets en utilisant --mount=type=secret échoue avec "opération non autori

mitted" lorsqu'il est exécuté sur un système de fichiers hôte monté avec nosuid et lors de l'utilisation du runtime runc.

Symptôme

Une ligne RUN dans le Dockerfile/Containerfile contient un montage secret tel que --mount=type=secret,id=MY_USER,target=/etc/dnf/vars/MY_USER. Lors de l'exécution de podman build, le processus échoue avec un message d'erreur tel que :

STEP 3/13: RUN --mount=type=secret,id=MY_USER,target=/etc/dnf/vars/MY_USER     --mount=type=secret,id=MY_USER,target=/etc/dnf/vars/MY_USER     ...: time="2023-06-13T18:04:59+02:00" level=error msg="runc create failed: unable to start container process: error during container init: error mounting \"/var/tmp/buildah2251989386/mnt/buildah-bind-target-11\" to rootfs at \"/etc/dnf/vars/MY_USER\": mount /var/tmp/buildah2251989386/mnt/buildah-bind-target-11:/etc/dnf/vars/MY_USER (via /proc/self/fd/7), flags: 0x1021: operation not permitted"
: exit status 1
ERRO[0002] did not get container create message from subprocess: EOF

Solution

  • Installez crun, par exemple avec dnf install crun.
  • Utilisez le runtime crun en passant --runtime /usr/bin/crun à podman build.

Voir également le problème Buildah 4228 pour une discussion complète du problème.

42) Les builds podman-dans-podman intensifs en E/S de fichiers sont très lents

Lorsque vous utilisez le pilote de stockage overlay pour effectuer un podman build imbriqué dans un conteneur en cours d'exécution, les opérations d'E/S de fichiers telles que COPY d'une grande quantité de données sont très lentes ou peuvent se bloquer complètement.

Symptôme

En utilisant le pilote de stockage overlay par défaut, une ligne COPY, ADD ou une ligne RUN intensive en E/S dans un Containerfile exécutée à l'intérieur d'un autre conteneur est très lente ou se bloque complètement lors de l'exécution d'un podman build à l'intérieur du conteneur parent en cours d'exécution.

Solution

Cela pourrait être causé par le conteneur enfant utilisant fuse-overlayfs pour écrire dans /var/lib/containers/storage. Les écritures peuvent être lentes avec fuse-overlayfs. La solution est d'utiliser le système de fichiers overlay natif en utilisant un répertoire local sur le système hôte comme volume vers /var/lib/containers/storage comme ceci : podman run --privileged --rm -it -v ./nested_storage:/var/lib/containers/storage parent:latest. Assurez-vous que l'image de base de parent:latest dans cet exemple ne contient rien dans /var/lib/containers/storage dans l'image elle-même pour que cela fonctionne. Une fois que vous utilisez le volume natif, le conteneur imbriqué ne devrait pas se rabattre sur fuse-overlayfs pour écrire des fichiers et le build imbriqué se terminera beaucoup plus rapidement.

Si vous n'avez pas accès au processus d'exécution parent, comme dans un environnement CI, alors la deuxième option consiste à changer le pilote de stockage en vfs dans l'image parente en changeant cette ligne dans votre fichier storage.conf : driver = "vfs". Vous devrez peut-être exécuter podman system reset pour que cela prenne effet. Vous saurez que c'est changé lorsque podman info |grep graphDriverName affichera graphDriverName: vfs. Cette méthode est plus lente que la méthode du volume ci-dessus, mais elle est significativement plus rapide que fuse-overlayfs.

43) podman run --userns=auto échoue avec Error: creating container storage: not enough unused IDs in user namespace

L'utilisation de --userns=auto lors de la création de nouveaux conteneurs ne fonctionne pas tant qu'il existe des conteneurs créés avec --userns=keep-id ou --userns=nomap.

Symptôme

1.
Exécuter avec --userns=auto $ podman run --rm -d --userns=auto alpine sleep 3600 La commande réussit.
2.
Exécuter avec --userns=auto $ podman run --rm -d --userns=auto alpine sleep 3600 La commande réussit.
3.
Exécuter avec --userns=keep-id $ podman run --rm -d --userns=keep-id alpine sleep 3600 La commande réussit.
4.
Exécuter avec --userns=auto $ podman run --rm -d --userns=auto alpine sleep 3600 La commande échoue avec le message d'erreur Error: creating container storage: not enough unused IDs in user namespace

Solution

Tous les conteneurs existants créés avec --userns=keep-id ou --userns=nomap doivent d'abord être supprimés avant qu'un nouveau conteneur puisse être créé avec --userns=auto.

44) sudo podman run --userns=auto échoue avec Cannot find mappings for user containers

Lorsque Podman rootful est appelé avec --userns=auto, Podman doit sélectionner des sous-plages de subuids et subgids pour l'espace de noms utilisateur du conteneur. Podman rootful garantit que les plages de subuid et de subgid pour de tels conteneurs ne se chevauchent pas, mais comment Podman rootful peut-il empêcher d'autres outils d'utiliser accidentellement ces ID ?

Il n'est pas possible d'empêcher d'autres outils exécutés en tant que root d'utiliser ces ID, mais de tels outils n'utiliseraient normalement pas des subuids et des subgids déjà attribués à un utilisateur dans /etc/subuid et /etc/subgid.

Le nom d'utilisateur containers sur l'hôte a une fonction spéciale pour Podman rootful. Podman rootful utilise les subuids et subgids de l'utilisateur containers lors de l'exécution de conteneurs --userns=auto. L'utilisateur containers n'a pas besoin de ces subuids et subgids car aucun processus ne devrait être démarré en tant qu'utilisateur containers. En d'autres termes, l'utilisateur containers est un utilisateur spécial qui n'existe sur le système que pour réserver des subuids et subgids pour Podman rootful.

containers est le nom d'utilisateur par défaut, mais il peut être modifié en définissant l'option root-auto-userns-user dans le fichier /etc/containers/storage.conf.

Symptôme

Exécutez Podman rootful avec --userns=auto

sudo podman run --rm --userns=auto alpine echo hello

La commande échoue avec le message d'erreur :

ERRO[0000] Cannot find mappings for user "containers": no subuid ranges found for user "containers" in /etc/subuid
Error: creating container storage: not enough unused IDs in user namespace

Les fichiers /etc/subuid et /etc/subgid ne contiennent aucune ligne commençant par containers:.

Solution

Ajoutez des plages subuid et subgid pour l'utilisateur containers dans /etc/subuid et /etc/subgid ou fournissez de telles plages avec /etc/nsswitch.conf. Pour plus de détails, voir subid(5).

Les étapes suivantes créent l'utilisateur containers et lui attribuent de grandes plages subuid et subgid :

1.
Créez l'utilisateur containers sudo useradd --comment "Helper user to reserve subuids and subgids for Podman"
--no-create-home
--shell /usr/sbin/nologin
containers
2.
Vérifiez les plages subuid et subgid de l'utilisateur containers $ grep ^containers: /etc/subuid containers:720896:65536 $ grep ^containers: /etc/subgid containers:720896:65536 Par défaut, useradd attribue 65536 subuids et 65536 subgids à un nouvel utilisateur. Généralement, vous voudrez que le pool réservé soit plus grand que cela. Plus la taille est grande, plus le nombre de conteneurs pouvant être démarrés avec sudo podman run --userns=auto ... est élevé.
3.
Modifiez la ligne de l'utilisateur containers dans les fichiers /etc/subuid et /etc/subgid pour agrandir les plages. Assurez-vous que la plage subuid de l'utilisateur containers ne se chevauche pas avec d'autres plages subuid dans les fichiers /etc/subuid. Assurez-vous que la plage subgid de l'utilisateur containers ne se chevauche pas avec d'autres plages subgid dans les fichiers /etc/subgid.

Testez à nouveau la commande echo

sudo podman run --rm --userns=auto alpine echo hello

La commande réussit et affiche hello.

45) Podman échoue avec lsetxattr(label=system_u:object_r:container_file_t:s0) /dir: operation not permitted

Des permissions de fichiers strictes empêchent Podman de modifier les étiquettes de contexte SELinux des fichiers dans un répertoire monté par liaison. L'erreur peut également se produire lors de l'utilisation de répertoires montés par liaison qui résident sur des systèmes de fichiers ne prenant pas en charge les XATTR (comme les anciennes versions de NFS).

Symptôme

1.
Créez un répertoire
podman-troubleshooting(7)

Troubleshooting

A list of common issues and solutions for Podman

A list of common issues and solutions for Podman

1.
Create a directory owned by root sudo mkdir /var/test
2.
Give everyone read access to the directory sudo chmod 755 /var/test
3.
Run ls directly on the host ls /var/test The command succeeds.
4.
Run rootless podman with the directory bind-mounted. Set z as volume option. podman run --rm -v /var/test:/dir:z fedora ls /dir The command fails with the following error message: Error: lsetxattr(label=system_u:object_r:container_file_t:s0) /var/test: operation not permitted The error is expected because the unprivileged user does not have the privileges to modify the SELinux context of the directory /var/test
5.
Repeat the previous command but remove the volume option podman run --rm -v /var/test:/dir fedora ls /dir The command is blocked by SELinux and fails with the following error message: ls: cannot open directory '/dir': Permission denied

Note, access to the bind-mounted directory depends on SELinux rules. For example, bind-mounting the directory /usr/share succeeds even though the user does not have write permissions to the directory. The following command succeeds:

podman run --rm -v /usr/share:/dir fedora ls /dir

Solution

Alternative 1

Use the O flag to mount the directory from the host as a temporary storage using the overlay file system.

podman run --rm -v /var/test:/dir:O fedora ls /dir

Modifications to the mount point are destroyed when the container finishes executing, similar to a tmpfs mount point being unmounted.

The following command succeeds:

podman run --rm -v /var/test:/dir:O fedora touch /dir/file

The command touch creates the file but the file is discarded when the container finishes.

Alternative 2

If the directory /var/test resides on a file system that supports XATTR, set a directory SELinux context that corresponds to the podman volume flag :z

sudo chcon -R system_u:object_r:container_file_t:s0 /var/test

The following command now succeeds

podman run --rm -v /var/test:/dir ls /dir

Alternative 3

Modify the default SELinux context configuration for the directory /var/test with the command

sudo semanage fcontext -a -s system_u -t container_file_t "/var/test(/.*)?"

Change the SElinux contexts recursively for files and directories under /var/test to match the new configuration

sudo restorecon -R -F -v /var/test

Alternative 4

Add the option --security-opt label=disable to disable SELinux for the Podman command.

podman run --rm --security-opt label=disable -v /var/test:/dir fedora ls /dir
