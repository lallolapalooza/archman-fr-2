POLKIT(8) polkit POLKIT(8)

NOM

polkit — Gestionnaire d'autorisation

APERÇU

polkit fournit une API d'autorisation destinée à être utilisée par des programmes privilégiés (« MÉCANISMES ») offrant des services à des programmes non privilégiés (« SUJETS ») souvent via un mécanisme de communication inter-processus. Dans ce scénario, le mécanisme traite généralement le sujet comme non fiable. Pour chaque requête d'un sujet, le mécanisme doit déterminer si la requête est autorisée ou s'il doit refuser de servir le sujet. En utilisant les API de polkit, un mécanisme peut déléguer cette décision à une partie fiable : l'autorité polkit.

L'autorité polkit est implémentée sous forme de démon système, polkitd(8), qui lui-même a peu de privilèges car il s'exécute en tant qu'utilisateur système polkitd. Les mécanismes, les sujets et les agents d'authentification communiquent avec l'autorité via le bus de messages système.

En plus de servir d'autorité, polkit permet aux utilisateurs d'obtenir une autorisation temporaire en authentifiant soit un utilisateur administrateur, soit le propriétaire de la session à laquelle le client appartient. Ceci est utile pour les scénarios où un mécanisme a besoin de vérifier que l'opérateur du système est bien l'utilisateur ou un utilisateur administrateur.

ARCHITECTURE SYSTÈME

L'architecture système de polkit comprend l'Autorité (implémentée comme un service sur le bus de messages système) et un Agent d'Authentification par session utilisateur (fourni et démarré par l'environnement graphique de l'utilisateur). Les Actions sont définies par les applications. Les fournisseurs, les sites et les administrateurs système peuvent contrôler la politique d'autorisation via des Règles d'Autorisation.

La bibliothèque libpolkit-agent-1 fournit une abstraction du système d'authentification natif, par exemple pam(8), ainsi que des facilités d'enregistrement et de communication avec le service D-Bus de polkit.

Consultez la documentation pour les développeurs[3] pour plus d'informations sur l'écriture d'applications polkit.

AGENTS D'AUTHENTIFICATION

Un agent d'authentification est utilisé pour faire prouver à l'utilisateur d'une session qu'il est bien cet utilisateur (en s'authentifiant comme l'utilisateur) ou un utilisateur administrateur (en s'authentifiant comme un administrateur). Afin de bien s'intégrer au reste de la session utilisateur (par exemple, pour correspondre au style visuel), les agents d'authentification sont censés être fournis par la session utilisateur utilisée. Par exemple, un agent d'authentification peut ressembler à ceci :

[IMAGE][4] 
+----------------------------------------------------------+
|                                                          |
|  [Icône]  Authentification requise                     |
|                                                          |
|          Une authentification est requise pour formater  |
|          le SSD INTEL DSA2MH080G1GC (/dev/sda)           |
|                                                          |
|          Administrateur                                  |
|                                                          |
|          Mot de passe : [________________________________]  |
|                                                          |
| [Annuler]                                 [Authentifier] |
+----------------------------------------------------------+

Si le système est configuré sans compte root, il peut demander un utilisateur spécifique désigné comme utilisateur administrateur :

[IMAGE][5] 
+----------------------------------------------------------+
|                                                          |
|  [Icône]  Authentification requise                     |
|                                                          |
|          Une authentification est requise pour formater  |
|          le SSD INTEL DSA2MH080G1GC (/dev/sda)           |
|                                                          |
|          [Icône] David Zeuthen                           |
|                                                          |
|          Mot de passe : [________________________________]  |
|                                                          |
| [Annuler]                                 [Authentifier] |
+----------------------------------------------------------+

Les applications qui ne s'exécutent pas sous un environnement de bureau (par exemple, si elles sont lancées depuis une connexion ssh(1)) peuvent ne pas avoir d'agent d'authentification associé. Ces applications peuvent utiliser le type PolkitAgentTextListener ou l'aide pkttyagent(1) pour que l'utilisateur puisse s'authentifier via une interface textuelle.

DÉCLARATION DES ACTIONS

Un mécanisme doit déclarer un ensemble d'actions pour pouvoir utiliser polkit. Les actions correspondent aux opérations que les clients peuvent demander au mécanisme d'exécuter et sont définies dans des fichiers XML que le mécanisme installe dans le répertoire /usr/share/polkit-1/actions.

Les actions polkit sont dans des espaces de noms et ne peuvent contenir que les caractères « [A-Z][a-z][0-9].- », c'est-à-dire des caractères ASCII, des chiffres, des points et des traits d'union. Chaque fichier XML peut contenir plus d'une action, mais toutes les actions doivent être dans le même espace de noms et le fichier doit être nommé d'après l'espace de noms et avoir l'extension .policy.

Le fichier XML doit avoir la déclaration doctype suivante

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE policyconfig PUBLIC "-//freedesktop//DTD polkit Policy Configuration 1.0//EN"
"http://www.freedesktop.org/software/polkit/policyconfig-1.dtd">

L'élément policyconfig doit être présent exactement une fois. Les éléments qui peuvent être utilisés à l'intérieur de policyconfig incluent :

vendor

Le nom du projet ou du fournisseur qui fournit les actions dans le document XML. Facultatif.

vendor_url

Une URL vers le projet ou le fournisseur qui fournit les actions dans le document XML. Facultatif.

icon_name

Une icône représentant le projet ou le fournisseur qui fournit les actions dans le document XML. Le nom de l'icône doit respecter la Spécification de nommage des icônes Freedesktop.org[6]. Facultatif.

action

Il s'agit de l'élément principal pour déclarer une action. Il doit avoir un attribut id qui est le nom unique de l'action dans l'espace de noms (par exemple, org.freedesktop.udisks2.filesystem-mount). Les actions peuvent avoir les enfants suivants :

alias

Permet de spécifier des noms alternatifs pour une action. Peut avoir un attribut name. Peut être présent plusieurs fois.

group

Un groupe d'actions apparentées. Peut avoir les enfants suivants :

action_id

Fait référence à un action déclaré dans ce fichier ou un autre fichier de politique. Doit avoir un attribut member.

description

Description de l'action. Peut avoir un attribut xml:lang pour spécifier la langue.

message

Message affiché à l'utilisateur. Peut avoir un attribut xml:lang pour spécifier la langue.

defaults

Définit les autorisations par défaut pour l'action. Doit avoir un attribut online (déterminé si l'action doit être effectuée en ligne ou hors ligne). Doit avoir un attribut type qui peut être "allow" (autoriser), "deny" (refuser) ou "auth_admin" (authentification administrateur requise). Doit avoir un attribut service (nom du service). Les autorisations par défaut peuvent être surchargées par les règles.

allow_active

Spécifie si l'action est autorisée lorsqu'elle est effectuée dans le contexte d'un utilisateur qui est actuellement actif dans une session graphique. Peut avoir un attribut reason (raison).

annotate

Permet de joindre des informations supplémentaires à l'action. Peut avoir un attribut key.

result_any

Définit le résultat attendu pour n'importe quel utilisateur. Peut avoir un attribut reason.

result_user

Définit le résultat attendu pour l'utilisateur exécutant l'action. Peut avoir un attribut reason.

result_admin

Définit le résultat attendu pour un utilisateur administrateur. Peut avoir un attribut reason.

Voici un exemple de fichier de politique :

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE policyconfig PUBLIC "-//freedesktop//DTD polkit Policy Configuration 1.0//EN"
"http://www.freedesktop.org/software/polkit/policyconfig-1.dtd">
<policyconfig>
  <vendor>Example Project</vendor>
  <vendor_url>http://www.example.com</vendor_url>
  <icon_name>preferences-system</icon_name>

  <action id="org.freedesktop.policykit.example.run-command">
    <description>Run a command as root</description>
    <message>Authentication is required to run a command as administrator.</message>
    <defaults>
      <allow_any>auth_admin</allow_any>
      <allow_inactive>auth_admin</allow_inactive>
    </defaults>
    <annotate key="org.freedesktop.policykit.execpath">/usr/bin/widely-used-command</annotate>
  </action>
</policyconfig>

RÈGLES D'AUTORISATION

Les règles d'autorisation permettent aux administrateurs système de modifier le comportement de polkit sans avoir à modifier les fichiers d'actions. Les règles d'autorisation sont écrites en JavaScript et sont placées dans le répertoire /etc/polkit-1/rules.d/ ou /usr/share/polkit-1/rules.d/. Les règles dans /etc/polkit-1/rules.d/ s'exécutent avant celles dans /usr/share/polkit-1/rules.d/. Les règles sont traitées par ordre alphabétique de leur nom de fichier.

Une règle est un objet JavaScript qui a une méthode handle_action. Cette méthode est appelée lorsque polkit traite une action. Elle prend deux arguments :

  • action : un objet représentant l'action demandée.
  • details : un objet contenant des informations supplémentaires sur la demande, comme le sujet, l'objet et les paramètres.

La méthode handle_action doit retourner l'une des valeurs suivantes :

  • polkit.Result.YES : Autoriser l'action.
  • polkit.Result.NO : Refuser l'action.
  • polkit.Result.AUTH_ADMIN : Demander l'authentification d'un administrateur.
  • polkit.Result.AUTH_SELF : Demander l'authentification de l'utilisateur lui-même.

Voici un exemple de règle d'autorisation qui autorise toujours l'action 'org.freedesktop.policykit.example.run-command' :

polkit.addRule(function(action, details) {
    if (action.id == "org.freedesktop.policykit.example.run-command") {
        return polkit.Result.YES;
    }
});

Voici un exemple de règle qui demande l'authentification administrateur pour l'action 'org.freedesktop.policykit.example.run-command' uniquement si le sujet est l'utilisateur 'alice' :

polkit.addRule(function(action, details) {
    if (action.id == "org.freedesktop.policykit.example.run-command" &&
        details.user == "alice") {
        return polkit.Result.AUTH_ADMIN;
    }
});

Les règles peuvent inspecter divers aspects de la demande, tels que le sujet (utilisateur, groupe, session), l'objet (le périphérique ou le service visé) et les paramètres passés à l'action.

Pour plus de détails sur l'écriture des règles d'autorisation, consultez la documentation de polkit.

UTILISATION

polkit est généralement utilisé par des applications et des services système pour contrôler l'accès aux ressources privilégiées. Les utilisateurs interagissent rarement directement avec polkit, sauf pour répondre aux demandes d'authentification faites par les agents d'authentification.

Les commandes utiles liées à polkit incluent :

  • pkcheck(1) : Vérifie si un utilisateur a l'autorisation d'effectuer une action.
  • pkttyagent(1) : Un agent d'authentification en ligne de commande.
  • polkitd(8) : Le démon de polkit.

Les éléments qui peuvent être utilisés à l'intérieur de action incluent :

description

message

Un message lisible par l'homme affiché à l'utilisateur lors de la demande d'informations d'identification lorsqu'une authentification est nécessaire, par exemple « L'installation d'un logiciel non signé nécessite une authentification ».

defaults

Cet élément est utilisé pour spécifier des autorisations implicites pour les clients. Les éléments qui peuvent être utilisés à l'intérieur de defaults incluent :

allow_any

Autorisations implicites qui s'appliquent à n'importe quel client. Facultatif.

allow_inactive

Autorisations implicites qui s'appliquent aux clients dans des sessions inactives sur les consoles locales. Facultatif.

allow_active

Autorisations implicites qui s'appliquent aux clients dans des sessions actives sur les consoles locales. Facultatif.

Chacun des éléments allow_any, allow_inactive et allow_active peut contenir les valeurs suivantes :

no

Non autorisé.

yes

Autorisé.

auth_self

L'authentification par le propriétaire de la session dont provient le client est requise. Notez que ce n'est pas assez restrictif pour la plupart des utilisations sur des systèmes multi-utilisateurs ; auth_admin* est généralement recommandé.

auth_admin

L'authentification par un utilisateur administrateur est requise.

auth_self_keep

Comme auth_self, mais l'autorisation est conservée pendant une courte période (par exemple, cinq minutes). L'avertissement concernant auth_self ci-dessus s'applique de la même manière.

auth_admin_keep

Comme auth_admin, mais l'autorisation est conservée pendant une courte période (par exemple, cinq minutes).

annotate

Utilisé pour annoter une action avec une paire clé/valeur. La clé est spécifiée à l'aide de l'attribut key et la valeur est spécifiée à l'aide de l'attribut value. Cet élément peut apparaître zéro ou plusieurs fois. Voir ci-dessous pour les annotations connues.

vendor

Utilisé pour remplacer le fournisseur sur une base par action. Facultatif.

vendor_url

Utilisé pour remplacer l'URL du fournisseur sur une base par action. Facultatif.

icon_name

Utilisé pour remplacer le nom de l'icône sur une base par action. Facultatif.

Pour la localisation, les éléments description et message peuvent apparaître plusieurs fois avec différents attributs xml:lang.

Pour lister les actions polkit installées, utilisez la commande pkaction(1).

Annotations connues

L'annotation org.freedesktop.policykit.exec.path est utilisée par le programme pkexec fourni avec polkit - voir la page de manuel pkexec(1) pour plus de détails.

L'annotation org.freedesktop.policykit.imply (sa valeur est une chaîne contenant une liste d'identifiants d'action séparés par des espaces) peut être utilisée pour définir des méta-actions. La façon dont cela fonctionne est que si un sujet est autorisé pour une action avec cette annotation, alors il est également autorisé pour toute action spécifiée par l'annotation. Une utilisation typique de cette annotation est lors de la définition d'un shell d'interface utilisateur avec un seul bouton de verrouillage qui devrait déverrouiller plusieurs actions de mécanismes distincts.

L'annotation org.freedesktop.policykit.owner peut être utilisée pour définir un ensemble d'utilisateurs qui peuvent interroger si un client est autorisé à effectuer cette action. Si cette annotation n'est pas spécifiée, alors seul root peut interroger si un client exécuté par un autre utilisateur est autorisé pour une action. La valeur de cette annotation est une chaîne contenant une liste d'entrées PolkitIdentity séparées par des espaces, par exemple « unix-user:42 unix-user:colord ». Une utilisation typique de cette annotation est pour un processus démon qui s'exécute en tant qu'utilisateur système plutôt qu'en tant que root.

RÈGLES D'AUTORISATION

polkitd lit les fichiers .rules des répertoires suivants dans cet ordre :

•/etc/polkit-1/rules.d
•/run/polkit-1/rules.d
•/usr/local/share/polkit-1/rules.d
•/usr/share/polkit-1/rules.d

Ces répertoires sont traités dans l'ordre lexical basé sur le nom de base de chaque fichier. En cas d'égalité, les fichiers des répertoires situés plus tôt dans la liste sont traités en premier. Par exemple, pour les quatre fichiers suivants, l'ordre est le suivant :

•/etc/polkit-1/rules.d/10-auth.rules
•/run/polkit-1/rules.d/10-auth.rules
•/usr/local/share/polkit-1/rules.d/10-auth.rules
•/usr/share/polkit-1/rules.d/10-auth.rules

Tous ces répertoires sont surveillés, donc si un fichier de règles est modifié, ajouté ou supprimé, les règles existantes sont purgées et tous les fichiers sont lus et traités à nouveau. Les fichiers de règles sont écrits dans le langage de programmation JavaScript[7] et interagissent avec polkitd via l'objet global polkit (de type Polkit).

Bien que l'interpréteur JavaScript utilisé dans certaines versions de polkit puisse prendre en charge des fonctionnalités non standard (telles que le mot-clé let), les règles d'autorisation doivent être conformes à ECMA-262 édition 5[8] (en d'autres termes, l'interpréteur JavaScript utilisé peut changer dans les futures versions de polkit).

Les règles d'autorisation sont destinées à deux publics spécifiques :

•Administrateurs système
•Systèmes d'exploitation / Environnements à usage spécial

et à ces publics uniquement. En particulier, les applications, les mécanismes et les systèmes d'exploitation à usage général ne doivent jamais inclure de règles d'autorisation.

Le type Polkit

Les méthodes suivantes sont disponibles sur l'objet polkit :

void addRule(polkit.Result function(action, subject) {...});

void addAdminRule(string[] function(action, subject) {...});

void log(string message);

string spawn(string[] argv);

La méthode addRule() est utilisée pour ajouter une fonction qui peut être appelée chaque fois qu'une vérification d'autorisation pour action et subject est effectuée. Les fonctions sont appelées dans l'ordre où elles ont été ajoutées jusqu'à ce que l'une des fonctions renvoie une valeur. Par conséquent, pour ajouter une règle d'autorisation qui est traitée avant les autres règles, placez-la dans un fichier dans /etc/polkit-1/rules.d avec un nom qui se classe avant les autres fichiers de règles, par exemple 00-early-checks.rules. Chaque fonction doit renvoyer une valeur de polkit.Result

polkit.Result = {
    NO              : "no",
    YES             : "yes",
    AUTH_SELF       : "auth_self",
    AUTH_SELF_KEEP  : "auth_self_keep",
    AUTH_ADMIN      : "auth_admin",
    AUTH_ADMIN_KEEP : "auth_admin_keep",
    NOT_HANDLED     : null
};

correspondant aux valeurs qui peuvent être utilisées par défaut. Si la fonction renvoie polkit.Result.NOT_HANDLED, null, undefined ou ne renvoie aucune valeur, la fonction utilisateur suivante est essayée.

Gardez à l'esprit que si polkit.Result.AUTH_SELF_KEEP ou polkit.Result.AUTH_ADMIN_KEEP est renvoyé, les vérifications d'autorisation pour le même identifiant d'action et le même sujet réussiront (c'est-à-dire renverront polkit.Result.YES) pendant une courte période (par exemple, cinq minutes) *même* si les variables transmises avec la vérification sont différentes. Par conséquent, si le résultat d'une règle d'autorisation dépend de telles variables, il ne doit pas utiliser les constantes « *_KEEP » (si une fonctionnalité similaire est requise, la règle d'autorisation peut facilement implémenter des autorisations temporaires en utilisant le type Date[9] pour les horodatages).

La méthode addAdminRule() est utilisée pour ajouter une fonction qui peut être appelée chaque fois que l'authentification administrateur est requise. La fonction est utilisée pour spécifier quelles identités peuvent être utilisées pour l'authentification administrateur pour la vérification d'autorisation identifiée par action et subject. Les fonctions ajoutées sont appelées dans l'ordre où elles ont été ajoutées jusqu'à ce qu'une des fonctions renvoie une valeur. Chaque fonction doit renvoyer un tableau de chaînes où chaque chaîne est de la forme « unix-group:<group> », « unix-netgroup:<netgroup> » ou « unix-user:<user> ». Si la fonction renvoie null, undefined ou ne renvoie aucune valeur, la fonction suivante est essayée.

Il n'y a aucune garantie qu'une fonction enregistrée avec addRule() ou addAdminRule() soit jamais appelée - par exemple, un fichier de règles précoce pourrait enregistrer une fonction qui renvoie toujours une valeur, garantissant ainsi que les fonctions ajoutées plus tard ne sont jamais appelées.

Si le code fourni par l'utilisateur prend trop de temps à s'exécuter, aucune exception ne sera levée et le script sera tué immédiatement (la limite actuelle est de 15 secondes). Ceci est utilisé pour attraper les scripts qui s'emballent.

La méthode spawn() lance un programme d'aide externe identifié par le vecteur d'arguments argv et attend qu'il se termine. Si une erreur se produit ou si le programme d'aide ne se termine pas normalement avec le code de sortie 0, une exception est levée. Si le programme d'aide ne se termine pas dans les 10 secondes, il est tué. Sinon, la sortie standard du programme est renvoyée sous forme de chaîne. La méthode spawn() doit être utilisée avec parcimonie car les programmes d'aide peuvent prendre un temps très long ou indéterminé pour se terminer et aucune autre vérification d'autorisation ne peut être traitée pendant que le programme d'aide s'exécute. Notez que les programmes lancés s'exécuteront en tant qu'utilisateur système polkitd sans privilèges.

La méthode log() écrit le message donné dans le journal système, précédé du nom de fichier et du numéro de ligne du fichier JavaScript. Les entrées de journal sont émises à l'aide du drapeau LOG_AUTHPRIV, ce qui signifie que les entrées de journal finissent généralement dans le fichier /var/log/secure. La méthode log() est généralement utilisée uniquement lors du débogage des règles. Les types Action et Subject ont des méthodes toString() appropriées définies pour faciliter la journalisation, par exemple,
