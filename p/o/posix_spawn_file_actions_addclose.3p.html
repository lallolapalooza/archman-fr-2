POSIX_SPAWN_FILE_ACTIONS_ADDCLOSE(3P) Manuel du programmeur POSIX POSIX_SPAWN_FILE_ACTIONS_ADDCLOSE(3P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

posix_spawn_file_actions_addclose, posix_spawn_file_actions_addopen — ajouter une action de fermeture ou d'ouverture à un objet d'actions de fichiers de spawn (TEMPS RÉEL AVANCÉ)

SYNTAXE

#include <spawn.h>
int posix_spawn_file_actions_addclose(posix_spawn_file_actions_t
    *file_actions, int fildes);
int posix_spawn_file_actions_addopen(posix_spawn_file_actions_t
    *restrict file_actions, int fildes,
    const char *restrict path, int oflag, mode_t mode);

DESCRIPTION

Ces fonctions ajoutent ou suppriment une action de fermeture ou d'ouverture à un objet d'actions de fichiers.

Un objet d'actions de fichiers de spawn est de type posix_spawn_file_actions_t (défini dans <spawn.h>) et est utilisé pour spécifier une série d'actions à effectuer par une opération posix_spawn() ou posix_spawnp() afin d'obtenir l'ensemble des descripteurs de fichiers ouverts pour le processus enfant à partir de l'ensemble des descripteurs de fichiers ouverts du processus parent. POSIX.1-2008 ne définit pas d'opérateurs de comparaison ou d'affectation pour le type posix_spawn_file_actions_t.

Un objet d'actions de fichiers de spawn, lorsqu'il est passé à posix_spawn() ou posix_spawnp(), spécifie comment l'ensemble des descripteurs de fichiers ouverts dans le processus appelant est transformé en un ensemble de descripteurs de fichiers potentiellement ouverts pour le processus lancé. Cette transformation s'effectue comme si la séquence d'actions spécifiée était exécutée exactement une fois, dans le contexte du processus lancé (avant l'exécution de la nouvelle image de processus), dans l'ordre où les actions ont été ajoutées à l'objet ; de plus, lors de l'exécution de la nouvelle image de processus, tout descripteur de fichier (de ce nouvel ensemble) dont le drapeau FD_CLOEXEC est défini sera fermé (voir posix_spawn()).

La fonction posix_spawn_file_actions_addclose() ajoute une action close à l'objet référencé par file_actions qui provoquera la fermeture du descripteur de fichier fildes (comme si close(fildes) avait été appelé) lorsqu'un nouveau processus est lancé en utilisant cet objet d'actions de fichiers.

La fonction posix_spawn_file_actions_addopen() ajoute une action open à l'objet référencé par file_actions qui provoquera l'ouverture du fichier nommé par path (comme si open(path, oflag, mode) avait été appelé, et le descripteur de fichier retourné, s'il n'était pas fildes, avait été modifié en fildes) lorsqu'un nouveau processus est lancé en utilisant cet objet d'actions de fichiers. Si fildes était déjà un descripteur de fichier ouvert, il sera fermé avant que le nouveau fichier ne soit ouvert.

La chaîne de caractères décrite par path sera copiée par la fonction posix_spawn_file_actions_addopen().

VALEUR DE RETOUR

En cas de succès, ces fonctions renvoient zéro ; sinon, un numéro d'erreur est retourné pour indiquer l'erreur.

ERREURS

La fonction posix_spawn_file_actions_addopen() échouera si :

EBADF
La valeur spécifiée par fildes est négative ou supérieure ou égale à {OPEN_MAX}.

La fonction posix_spawn_file_actions_addclose() échouera si :

EBADF
La valeur spécifiée par fildes est négative.

Ces fonctions peuvent échouer si :

EINVAL
La valeur spécifiée par file_actions est invalide.
ENOMEM
La mémoire disponible est insuffisante pour ajouter à l'objet d'actions de fichiers de spawn.

Il ne sera pas considéré comme une erreur si l'argument fildes passé à ces fonctions spécifie un descripteur de fichier pour lequel l'opération spécifiée n'a pas pu être effectuée au moment de l'appel. Toute erreur de ce type sera détectée lorsque l'objet d'actions de fichiers associé sera utilisé ultérieurement lors d'une opération posix_spawn() ou posix_spawnp().

EXEMPLES

UTILISATION APPLICATIVE

Ces fonctions font partie de l'option Spawn et peuvent ne pas être fournies sur toutes les implémentations.

Les implémentations peuvent utiliser des descripteurs de fichiers qui doivent être hérités par les processus enfants pour que le processus enfant reste conforme, par exemple à des fins de catalogue de messages ou de traçage. Par conséquent, une application qui appelle posix_spawn_file_actions_addclose() avec un entier arbitraire risque un comportement non conforme, et cette fonction ne peut être utilisée de manière portable que pour fermer des valeurs de descripteurs de fichiers que l'application a obtenues par des actions explicites, ou pour les trois descripteurs de fichiers correspondant aux flux de fichiers standards. Afin d'éviter une condition de concurrence qui laisserait fuiter un descripteur de fichier non intentionnel vers un processus enfant, une application devrait envisager d'ouvrir tous les descripteurs de fichiers avec le bit FD_CLOEXEC défini, sauf si le descripteur de fichier est destiné à être hérité lors d'un exec.

RATIONALE

Un objet d'actions de fichiers de spawn peut être initialisé pour contenir une séquence ordonnée d'opérations close(), dup2() et open() qui seront utilisées par posix_spawn() ou posix_spawnp() pour obtenir l'ensemble des descripteurs de fichiers ouverts hérités par le processus lancé à partir de l'ensemble des descripteurs de fichiers ouverts dans le parent au moment de l'appel posix_spawn() ou posix_spawnp(). Il avait été suggéré que les opérations close() et dup2() suffisent à réorganiser les descripteurs de fichiers, et que les fichiers qui doivent être ouverts pour être utilisés par le processus lancé peuvent être gérés soit en les faisant ouvrir par le processus appelant avant l'appel posix_spawn() ou posix_spawnp() (et en les fermant après), soit en passant des noms de chemins au processus lancé (dans argv) afin qu'il puisse les ouvrir lui-même. Les développeurs du standard recommandent que les applications utilisent l'une ou l'autre de ces deux méthodes quand cela est pratique, car le statut d'erreur détaillé d'une opération d'ouverture échouée est toujours disponible pour l'application de cette manière. Cependant, les développeurs du standard estiment que permettre à un objet d'actions de fichiers de spawn de spécifier des opérations d'ouverture reste approprié car :

1.
C'est cohérent avec la fonctionnalité équivalente de POSIX.5 (Ada).
2.
Il prend en charge le paradigme de redirection d'E/S couramment employé par les programmes POSIX conçus pour être invoqués depuis un shell. Lorsque un tel programme est le processus enfant, il peut ne pas être conçu pour ouvrir des fichiers par lui-même.
3.
Il permet des ouvertures de fichiers qui pourraient sinon échouer ou violer les droits de propriété/accès du fichier si elles étaient exécutées par le processus parent.

Concernant le point 2. ci-dessus, notez que l'action d'ouverture de spawn offre à posix_spawn() et posix_spawnp() la même capacité que les opérateurs de redirection du shell offrent à system(), mais sans l'exécution intermédiaire d'un shell ; par exemple :

system ("myprog <file1 3<file2");

Concernant le point 3. ci-dessus, notez que si le processus appelant a besoin d'ouvrir un ou plusieurs fichiers pour y accéder par le processus lancé, mais dispose de descripteurs de fichiers disponibles insuffisants, l'action d'ouverture est nécessaire pour permettre à l'opération open() de se produire dans le contexte du processus enfant après que d'autres descripteurs de fichiers aient été fermés (qui doivent rester ouverts dans le parent).

Mappage des descripteurs de fichier

Les développeurs standards avaient initialement proposé d'utiliser un tableau qui spécifiait le mappage des descripteurs de fichiers enfants vers ceux du parent. Il a été souligné par le groupe de vote qu'il n'est pas possible de réorganiser arbitrairement les descripteurs de fichiers dans une implémentation de bibliothèque de posix_spawn() ou posix_spawnp() sans provision pour une ou plusieurs entrées de descripteurs de fichiers de secours (qui peuvent simplement ne pas être disponibles). Un tel tableau nécessite qu'une implémentation développe une stratégie complexe pour atteindre le mappage souhaité sans fermer inadvertamment le mauvais descripteur de fichier au mauvais moment.

Il a été noté par un membre du groupe de travail des liaisons de langage Ada que la famille Start_Process approuvée du langage Ada pour les primitives de processus POSIX utilise un ensemble spécifié par l'appelant d'actions sur les fichiers pour modifier les sémantiques normales de fork()/exec pour l'héritage des descripteurs de fichiers d'une manière très flexible, mais aucun problème de ce type n'existe car le fardeau de déterminer comment réaliser le mappage final des descripteurs de fichiers incombe entièrement à l'application. De plus, bien que l'interface d'actions sur les fichiers puisse sembler effrayante à première vue, elle est en fait assez simple à implémenter dans une bibliothèque ou dans le noyau.

La fonction posix_spawn_file_actions_addclose() n'est pas tenue de vérifier si le descripteur de fichier est inférieur à {OPEN_MAX} car dans certaines implémentations, {OPEN_MAX} reflète la limite souple RLIMIT_NOFILE et par conséquent, l'appel à setrlimit() pour réduire cette limite peut entraîner une valeur de {OPEN_MAX} inférieure ou égale à un descripteur de fichier déjà ouvert. Les applications doivent pouvoir fermer de tels descripteurs de fichiers lors du spawn. Dans les implémentations où {OPEN_MAX} ne change pas, il est recommandé que posix_spawn_file_actions_addclose() retourne [EBADF] si fildes est supérieur ou égal à {OPEN_MAX}.
