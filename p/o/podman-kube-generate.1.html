NOM

podman-kube-generate - Génère du YAML Kubernetes à partir de conteneurs, pods ou volumes Podman

SYNTAXE

podman kube generate [options] conteneur... | pod... | volume...

DESCRIPTION

podman kube generate génère du YAML Kubernetes (spécification v1) à partir de conteneurs, pods ou volumes Podman. Indépendamment du fait que l'entrée concerne des conteneurs ou des pods, Podman génère par défaut la spécification sous forme de Pod. L'entrée peut être un ou plusieurs noms ou identifiants de conteneurs, pods ou volumes.

Conteneurs ou Pods Podman

Les volumes apparaissent dans le YAML généré selon deux types de volumes différents. Les volumes montés en bind deviennent des types de volumes hostPath et les volumes nommés deviennent des types de volumes persistentVolumeClaim. Les types de volumes hostPath générés sont l'un des trois sous-types en fonction de l'état du chemin d'accès hôte : DirectoryOrCreate lorsqu'aucun fichier ou répertoire n'existe sur l'hôte, Directory lorsque le chemin d'accès hôte est un répertoire, ou File lorsque le chemin d'accès hôte est un fichier. La valeur de claimName pour un persistentVolumeClaim est le nom du volume nommé enregistré dans Podman.

Les conflits de noms potentiels entre volumes sont évités en utilisant un schéma de nommage standard pour chaque type de volume. Les types de volumes hostPath sont nommés selon le chemin d'accès sur la machine hôte, en remplaçant les barres obliques par des tirets, moins toute barre oblique initiale et finale. Le cas spécial de la racine du système de fichiers, /, se traduit par le nom root. De plus, le nom est suffixé avec -host pour éviter les conflits de nommage avec les volumes persistentVolumeClaim. Chaque type de volume persistentVolumeClaim utilise le nom de son volume nommé associé suffixé par -pvc.

Notez que si un conteneur d'initialisation est créé avec le type once et que le pod a été démarré, il n'apparaît pas dans le YAML kube généré car les conteneurs d'initialisation de type once sont supprimés après leur exécution. Si le pod a seulement été créé et non démarré, il est présent dans le YAML kube généré. Les conteneurs d'initialisation créés avec le type always sont toujours générés dans le YAML kube car ils ne sont jamais supprimés, même après avoir terminé leur exécution.

Note : Lors de l'utilisation de volumes et de la génération d'un fichier YAML Kubernetes pour un conteneur podman non privilégié et sans privilèges sur un système avec SELinux activé, l'une des options suivantes doit être remplie :
* Ajoutez l'option "privileged: true" à la spécification du pod
* Ajoutez type: spc_t sous le securityContext seLinuxOptions dans la spécification du pod
* Re-étiquetez le volume via la commande CLI chcon -t container_file_t -R <répertoire>

Une fois cela effectué, les permissions correctes sont en place pour accéder au volume lorsque le pod/conteneur est créé dans un cluster Kubernetes.

Notez que le fichier YAML Kubernetes généré peut être utilisé pour relancer le déploiement via podman-play-kube(1).

Notez que si le pod généré a été créé avec l'option --infra-name définie, alors le fichier kube YAML généré aura io.podman.annotations.infra.name défini, où la valeur est le nom du conteneur d'infrastructure défini par l'utilisateur.

Notez que Deployment et DaemonSet ne peuvent avoir que restartPolicy défini sur Always.

Notez que Job ne peut avoir que restartPolicy défini sur OnFailure ou Never. Par défaut, podman le définit sur Never lors de la génération d'un fichier kube YAML en utilisant kube generate.

OPTIONS

--filename, -f=nomfichier

Écrire dans le fichier spécifié au lieu de STDOUT. Si le fichier existe déjà, kube generate refuse de le remplacer et renvoie une erreur.

--podman-only

Ajouter les annotations réservées à podman dans le fichier YAML généré (Ne peut pas être utilisé par Kubernetes)

--replicas, -r=nombre de répliques

La valeur à définir pour replicas lors de la génération d'un type Deployment. Note : ceci ne peut être défini qu'avec l'option --type=deployment.

--service, -s

Générer un objet de service Kubernetes en plus des Pods. Utilisé pour générer une spécification de service pour la sortie des Pods correspondants. En particulier, si l'objet a des liaisons de port, la spécification de service inclut une déclaration NodePort pour exposer le service. Un port aléatoire est attribué par Podman dans la spécification.

--type, -t=pod | deployment | daemonset | job

Le type Kubernetes à générer dans le fichier YAML. Actuellement, les seules spécifications Kubernetes prises en charge sont Pod, Deployment, Job et DaemonSet. Par défaut, la spécification Pod est générée.

EXEMPLES

Créer un fichier YAML de Pod Kubernetes pour le conteneur spécifié.

$ podman kube generate some-mariadb
# Enregistrez la sortie de ce fichier et utilisez kubectl create -f pour l'importer
# dans Kubernetes.
#
# Créé avec podman-4.8.2
# NOTE : Si vous avez généré ce yaml à partir d'un conteneur podman non privilégié et sans privilèges sur un système avec SELinux activé, consultez la page man de podman generate kube pour connaître les étapes à suivre afin de garantir que votre pod/conteneur dispose des bonnes permissions pour accéder aux volumes ajoutés.
---
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: "2024-01-09T02:24:55Z"
  labels:
    app: some-mariadb-pod
  name: some-mariadb-pod
spec:
  containers:
  - args:
    - mariadbd
    env:
    - name: MARIADB_ROOT_PASSWORD
      value: x
    image: docker.io/library/mariadb:10.11
    name: some-mariadb
    ports:
    - containerPort: 3306
      hostPort: 34891
    volumeMounts:
    - mountPath: /var/lib/mysql
      name: mariadb_data-pvc
  volumes:
  - name: mariadb_data-pvc
    persistentVolumeClaim:
      claimName: mariadb_data

Créer un fichier YAML de déploiement Kubernetes avec 3 répliques pour le conteneur spécifié.

$ podman kube generate --type deployment --replicas 3 dep-ct
r
# Enregistrez la sortie de ce fichier et utilisez kubectl create -f pour l'importer
# dans Kubernetes.
#
# Créé avec podman-4.5.0-dev
apiVersion: apps/v1
kind: Deployment
metadata:
  creationTimestamp: "2023-03-27T20:45:08Z"
  labels:
    app: dep-ctr-pod
  name: dep-ctr-pod-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: dep-ctr-pod
  template:
    metadata:
      annotations:
        io.podman.annotations.ulimit: nofile=524288:524288,nproc=127332:127332
      creationTimestamp: "2023-03-27T20:45:08Z"
      labels:
        app: dep-ctr-pod
      name: dep-ctr-pod
    spec:
      containers:
      - command:
        - top
        image: docker.io/library/alpine:latest
        name: dep-ctr

Créer un fichier YAML de Pod Kubernetes pour le conteneur spécifié avec le répertoire hôte /home/user/my-data monté en bind sur le chemin du conteneur /volume.

$ podman kube generate my-container-with-bind-mounted-data
# Enregistrez la sortie de ce fichier et utilisez kubectl create -f pour l'importer
# dans Kubernetes.
#
# Créé avec podman-3.1.0-dev
apiVersion: v1
kind: Pod
metadata:
  creationTimestamp: "2021-03-18T16:26:08Z"
  labels:
    app: my-container-with-bind-mounted-data
  name: my-container-with-bind-mounted-data
spec:
  containers:
  - command:
    - /bin/sh
    image: docker.io/library/alpine:latest
    name: test-bind-mount
    volumeMounts:
    - mountPath: /volume
      name: home-user-my-data-host
  restartPolicy: Never
  volumes:
  - hostPath:
      path: /home/user/my-data
      type: Directory
    name: home-user-my-data-host
