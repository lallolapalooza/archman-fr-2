NOM

pkeys - présentation des clés de protection de la mémoire

DESCRIPTION

Les clés de protection de la mémoire (pkeys) sont une extension des permissions de mémoire existantes basées sur les pages. Les permissions de page normales utilisant les tables de pages nécessitent des appels système coûteux et des invalidations de TLB lors du changement des permissions. Les clés de protection de la mémoire fournissent un mécanisme pour changer les protections sans nécessiter de modifier les tables de pages à chaque changement de permission.

Pour utiliser les pkeys, le logiciel doit d'abord "taguer" une page dans les tables de pages avec une pkey. Une fois ce tag en place, une application n'a qu'à modifier le contenu d'un registre pour supprimer le droit d'écriture, ou tout accès à une page taguée.

Les clés de protection fonctionnent en conjonction avec les permissions existantes PROT_READ, PROT_WRITE et PROT_EXEC passées aux appels système tels que mprotect(2) et mmap(2), mais agissent toujours pour restreindre davantage ces mécanismes de permission traditionnels.

Si un processus effectue un accès qui viole les restrictions de pkey, il reçoit un signal SIGSEGV. Voir sigaction(2) pour les détails des informations disponibles avec ce signal.

Pour utiliser la fonctionnalité des pkeys, le processeur doit la prendre en charge, et le noyau doit contenir le support de cette fonctionnalité sur un processeur donné. Depuis début 2016, seuls les futurs processeurs Intel x86 sont pris en charge, et ce matériel prend en charge 16 clés de protection dans chaque processus. Cependant, la pkey 0 est utilisée comme clé par défaut, donc un maximum de 15 sont disponibles pour une utilisation réelle par les applications. La clé par défaut est assignée à toute région mémoire pour laquelle aucune pkey n'a été explicitement assignée via pkey_mprotect(2).

Les clés de protection ont le potentiel d'ajouter une couche de sécurité et de fiabilité aux applications. Mais elles n'ont pas été principalement conçues comme une fonctionnalité de sécurité. Par exemple, WRPKRU est une instruction complètement non privilégiée, donc les pkeys sont inutiles dans tous les cas où un attaquant contrôle le registre PKRU ou peut exécuter des instructions arbitraires.

Les applications doivent être très prudentes pour s'assurer qu'elles ne "fuient" pas les clés de protection. Par exemple, avant d'appeler pkey_free(2), l'application doit être sûre qu'aucune mémoire n'a cette pkey assignée. Si l'application a laissé la pkey libérée assignée, un futur utilisateur de cette pkey pourrait involontairement modifier les permissions d'une structure de données non liée, ce qui pourrait avoir un impact sur la sécurité ou la stabilité. Le noyau permet actuellement aux pkeys utilisées d'avoir pkey_free(2) appelé sur elles car cela aurait des implications de performance processeur ou mémoire pour effectuer les vérifications supplémentaires nécessaires pour le refuser. L'implémentation des vérifications nécessaires est laissée aux applications. Les applications peuvent implémenter ces vérifications en recherchant dans le fichier /proc/pid/smaps les régions mémoire avec la pkey assignée. Plus de détails peuvent être trouvés dans proc(5).

Toute application souhaitant utiliser les clés de protection doit être capable de fonctionner sans elles. Elles pourraient être indisponibles parce que le matériel sur lequel l'application s'exécute ne les prend pas en charge, le code du noyau ne contient pas le support, le support du noyau a été désactivé, ou parce que toutes les clés ont été allouées, peut-être par une bibliothèque que l'application utilise. Il est recommandé que les applications souhaitant utiliser les clés de protection appellent simplement pkey_alloc(2) et testent si l'appel réussit, au lieu de tenter de détecter le support de la fonctionnalité d'une autre manière.

Bien que non nécessaire, le support matériel pour les clés de protection peut être énuméré avec l'instruction cpuid. Les détails sur la manière de le faire peuvent être trouvés dans le Manuel des développeurs Intel. Le noyau effectue cette énumération et expose les informations dans /proc/cpuinfo sous le champ "flags". La chaîne "pku" dans ce champ indique le support matériel pour les clés de protection et la chaîne "ospke" indique que le noyau contient et a activé le support des clés de protection.

Les applications utilisant des threads et des clés de protection doivent être particulièrement prudentes. Les threads héritent des droits de clé de protection du parent au moment de l'appel système clone(2). Les applications devraient soit s'assurer que leurs propres permissions sont appropriées pour les threads enfants au moment où clone(2) est appelé, soit s'assurer que chaque thread enfant peut effectuer sa propre initialisation des droits de clé de protection.

Comportement du gestionnaire de signaux

Chaque fois qu'un gestionnaire de signaux est invoqué (y compris les signaux imbriqués), le thread reçoit temporairement un nouvel ensemble par défaut de droits de clé de protection qui remplacent les droits du contexte interrompu. Cela signifie que les applications doivent rétablir leurs droits de clé de protection souhaités lors de l'entrée dans un gestionnaire de signaux si les droits souhaités diffèrent des valeurs par défaut. Les droits de tout contexte interrompu sont restaurés lorsque le gestionnaire de signaux revient.

Ce comportement de signal est inhabituel et est dû au fait que le registre PKRU x86 (qui stocke les droits d'accès des clés de protection) est géré avec le même mécanisme matériel (XSAVE) qui gère les registres à virgule flottante. Le comportement de signal est le même que celui des registres à virgule flottante.

Appels système de protection par clés

Le noyau Linux implémente les appels système suivants liés aux pkeys : pkey_mprotect(2), pkey_alloc(2) et pkey_free(2).

Les appels système pkey de Linux ne sont disponibles que si le noyau a été configuré et compilé avec l'option CONFIG_X86_INTEL_MEMORY_PROTECTION_KEYS.

EXEMPLES

Le programme ci-dessous alloue une page de mémoire avec des permissions de lecture et d'écriture. Il écrit ensuite des données dans la mémoire et les lit avec succès. Après cela, il tente d'allouer une clé de protection et désactive l'accès à la page en utilisant l'instruction WRPKRU. Il essaie ensuite d'accéder à la page, ce qui devrait provoquer un signal fatal pour l'application.


$ ./a.out
buffer contains: 73
about to read buffer again...
Segmentation fault (core dumped)

Source du programme

#define _GNU_SOURCE
#include <err.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
int
main(void)
{
    int status;
    int pkey;
    int *buffer;
    /*
     * Alloue une page de mémoire.
     */
    buffer = mmap(NULL, getpagesize(), PROT_READ | PROT_WRITE,
                  MAP_ANONYMOUS | MAP_PRIVATE, -1, 0);
    if (buffer == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    /*
     * Insère des données aléatoires dans la page (toujours OK à manipuler).
     */
    *buffer = __LINE__;
    printf("buffer contains: %d\n", *buffer);
    /*
     * Alloue une clé de protection :
     */
    pkey = pkey_alloc(0, 0);
    if (pkey == -1)
        err(EXIT_FAILURE, "pkey_alloc");
    /*
     * Désactive l'accès à toute mémoire avec "pkey" réglée,
     * même s'il n'y en a aucune pour le moment.
     */
    status = pkey_set(pkey, PKEY_DISABLE_ACCESS);
    if (status)
        err(EXIT_FAILURE, "pkey_set");
    /*
     * Définit la clé de protection sur "buffer".
     * Notez qu'il est toujours en lecture/écriture en ce qui concerne mprotect()
     * et que le pkey_set() précédent le remplace.
     */
    status = pkey_mprotect(buffer, getpagesize(),
                           PROT_READ | PROT_WRITE, pkey);
    if (status == -1)
        err(EXIT_FAILURE, "pkey_mprotect");
    printf("about to read buffer again...\n");
    /*
     * Cela va planter, car nous avons interdit l'accès.
     */
    printf("buffer contains: %d\n", *buffer);
    status = pkey_free(pkey);
    if (status == -1)
        err(EXIT_FAILURE, "pkey_free");
    exit(EXIT_SUCCESS);
}
