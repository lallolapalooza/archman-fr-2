pkg_mkIndex(n) Commandes intégrées Tcl pkg_mkIndex(n)

NOM

pkg_mkIndex - Créer un index pour le chargement automatique des paquets

SYNTAXE

pkg_mkIndex ?options...? rép ?motif motif ...?

DESCRIPTION

Pkg_mkIndex est une procédure utilitaire qui fait partie de la bibliothèque Tcl standard. Elle est utilisée pour créer des fichiers d'index qui permettent de charger automatiquement les paquets lorsque les commandes package require sont exécutées. Pour utiliser pkg_mkIndex, suivez ces étapes :

[1]
Créez le(s) paquet(s). Chaque paquet peut être constitué d'un ou plusieurs fichiers script Tcl ou de fichiers binaires. Les fichiers binaires doivent pouvoir être chargés avec la commande load avec un seul argument ; par exemple, si le fichier est test.so, il doit être possible de charger ce fichier avec la commande load test.so. Chaque fichier script doit contenir une commande package provide pour déclarer le paquet et son numéro de version, et chaque fichier binaire doit contenir un appel à Tcl_PkgProvide.
[2]
Créez l'index en invoquant pkg_mkIndex. L'argument rép donne le nom d'un répertoire et chaque argument motif est un motif de style glob qui sélectionne les fichiers script ou binaires dans rép. Le motif par défaut est *.tcl et *.[info sharedlibextension].

Pkg_mkIndex créera un fichier pkgIndex.tcl dans rép avec les informations du paquet pour tous les fichiers donnés par les arguments motif. Il le fait en chargeant chaque fichier dans un interpréteur enfant et en vérifiant quels paquets et quelles nouvelles commandes apparaissent (c'est pourquoi il est essentiel d'avoir des commandes package provide ou des appels à Tcl_PkgProvide dans les fichiers, comme décrit ci-dessus). Si vous avez un paquet réparti entre scripts et fichiers binaires, ou si vous avez des dépendances entre fichiers, vous devrez peut-être utiliser l'option -load ou ajuster l'ordre dans lequel pkg_mkIndex traite les fichiers. Voir CAS COMPLEXES ci-dessous.

[3]
Installez le paquet en tant que sous-répertoire de l'un des répertoires donnés par la variable tcl_pkgPath. Si $tcl_pkgPath contient plus d'un répertoire, les paquets dépendants de la machine (par exemple, ceux qui contiennent des bibliothèques partagées binaires) doivent normalement être installés dans le premier répertoire et les paquets indépendants de la machine (par exemple, ceux qui contiennent uniquement des scripts Tcl) doivent être installés dans le second répertoire. Le sous-répertoire doit inclure les scripts et/ou fichiers binaires du paquet ainsi que le fichier pkgIndex.tcl. Tant que le paquet est installé en tant que sous-répertoire d'un répertoire dans $tcl_pkgPath, il sera automatiquement trouvé lors des commandes package require.

Si vous installez le paquet ailleurs, vous devez vous assurer que le répertoire contenant le paquet est inclus dans la variable globale auto_path ou est un sous-répertoire immédiat de l'un des répertoires de auto_path. Auto_path contient une liste de répertoires qui sont recherchés par le chargeur automatique et le chargeur de paquets ; par défaut, il inclut $tcl_pkgPath. Le chargeur de paquets vérifie également tous les sous-répertoires des répertoires de auto_path. Vous pouvez ajouter un répertoire à auto_path explicitement dans votre application, ou vous pouvez ajouter le répertoire à votre variable d'environnement TCLLIBPATH : si cette variable d'environnement est présente, Tcl initialise auto_path à partir de celle-ci lors du démarrage de l'application.

[4]
Une fois les étapes ci-dessus effectuées, tout ce que vous avez à faire pour utiliser un paquet est d'invoquer package require. Par exemple, si les versions 2.1, 2.3 et 3.1 du paquet Test ont été indexées par pkg_mkIndex, la commande package require Test rendra la version 3.1 disponible et la commande package require -exact Test 2.1 rendra la version 2.1 disponible. Il peut y avoir de nombreuses versions d'un paquet dans les différents fichiers d'index de auto_path, mais une seule sera effectivement chargée dans un interpréteur donné, en fonction du premier appel à package require. Différentes versions d'un paquet peuvent être chargées dans différents interpréteurs.

OPTIONS

Les commutateurs optionnels sont :

-direct
L'index généré implémentera le chargement direct du paquet lors de package require. C'est le comportement par défaut.
-lazy
L'index généré gérera le chargement différé du paquet jusqu'à l'utilisation de l'une des commandes fournies par le paquet, au lieu de le charger immédiatement lors de package require. Ceci n'est pas compatible avec l'utilisation de auto_reset, et par conséquent son utilisation est déconseillée.
-load pkgPat
Le processus d'indexation préchargera tous les paquets existant dans l'interpréteur actuel et correspondant à pkgPat dans l'interpréteur enfant utilisé pour générer l'index. La correspondance de motif utilise les règles de comparaison de chaînes, mais sans tenir compte de la casse. Voir CAS COMPLEXES ci-dessous.
-verbose
Générer des sorties pendant le processus d'indexation. Les sorties sont effectuées via la procédure tclLog, qui imprime par défaut sur stderr.
--
Fin des drapeaux, au cas où rép commencerait par un tiret.

PAQUETS ET LE CHARGEUR AUTOMATIQUE

Les fonctionnalités de gestion des paquets chevauchent quelque peu avec le chargeur automatique, car les deux permettent de charger des fichiers à la demande. Cependant, la gestion des paquets est un mécanisme de plus haut niveau qui utilise le chargeur automatique pour la dernière étape du processus de chargement. Il est généralement préférable d'indexer un paquet avec pkg_mkIndex plutôt qu'avec auto_mkindex car le mécanisme de paquet fournit le contrôle de version : plusieurs versions d'un paquet peuvent être rendues disponibles dans les fichiers d'index, différentes applications utilisant différentes versions en fonction des commandes package require. En revanche, auto_mkindex ne comprend pas les versions, il ne peut donc gérer qu'une seule version de chaque paquet. Il n'est probablement pas judicieux d'indexer un paquet donné à la fois avec pkg_mkIndex et auto_mkindex. Si vous utilisez pkg_mkIndex pour indexer un paquet, ses commandes ne pourront pas être appelées tant que package require n'aura pas été utilisé pour sélectionner une version ; en revanche, les paquets indexés avec auto_mkindex peuvent être utilisés immédiatement car il n'y a pas de contrôle de version.

COMMENT ÇA MARCHE

Pkg_mkIndex dépend de la commande package unknown, de la commande package ifneeded et du chargeur automatique. La première fois qu'une commande package require est invoquée, le script package unknown est invoqué. Celui-ci est configuré par l'initialisation Tcl pour évaluer tous les fichiers pkgIndex.tcl présents dans auto_path. Les fichiers pkgIndex.tcl contiennent des commandes package ifneeded pour chaque version de chaque paquet disponible ; ces commandes invoquent des commandes package provide pour annoncer la disponibilité du paquet, et elles configurent les informations du chargeur automatique pour charger les fichiers du paquet. Si l'indicateur -lazy a été fourni lors de la génération de pkgIndex.tcl, un fichier donné d'une version donnée d'un paquet n'est réellement chargé que lors de la première utilisation d'une de ses commandes. Ainsi, après avoir invoqué package require, vous ne verrez peut-être pas les commandes du paquet dans l'interpréteur, mais vous pourrez les appeler et elles seront chargées automatiquement.

CHARGEMENT DIRECT

Certains paquets, par exemple ceux qui utilisent des espaces de noms et exportent des commandes, ou ceux qui nécessitent une initialisation spéciale, peuvent choisir que leurs fichiers de paquet soient chargés immédiatement lors de package require au lieu de retarder le chargement réel à la première utilisation d'une des commandes du paquet. C'est le mode par défaut lors de la génération de l'index du paquet. Il peut être remplacé en spécifiant l'argument -lazy.

CAS COMPLEXES

La plupart des cas complexes de dépendances entre scripts et fichiers binaires, et de paquets répartis entre scripts et fichiers binaires sont gérés correctement. Cependant, vous devrez peut-être ajuster l'ordre dans lequel les fichiers sont traités par pkg_mkIndex. Ces problèmes sont décrits en détail ci-dessous.

COMMENT GÉNÉRAL

Si chaque script ou fichier contient un seul package, et que les packages ne sont contenus que dans un seul fichier, alors les choses sont simples. Vous spécifiez simplement tous les fichiers à indexer dans n'importe quel ordre avec quelques motifs glob.

En général, il est acceptable que les scripts aient des dépendances sur d'autres packages. Si les scripts contiennent des commandes package require, celles-ci sont "stubbed" (simulées) dans l'interpréteur utilisé pour traiter les scripts, donc elles ne causent pas de problèmes. Si les scripts appellent d'autres packages dans du code global, ces appels sont gérés par une commande unknown "stubbed". Cependant, si les scripts font des références de variables à des variables d'autres packages dans du code global, cela causera des erreurs. C'est aussi un mauvais style de codage.

Si les fichiers binaires ont des dépendances sur d'autres packages, les choses peuvent devenir délicates car il n'est pas possible de "stubber" les API de niveau C telles que l'API Tcl_PkgRequire lors du chargement d'un fichier binaire. Par exemple, supposons que le package BLT requière Tk et l'exprime avec un appel à Tcl_PkgRequire dans sa routine Blt_Init. Pour supporter cela, vous devez exécuter pkg_mkIndex dans un interpréteur où Tk est chargé. Vous pouvez y parvenir avec l'option -load pkgPat. Si vous spécifiez cette option, pkg_mkIndex chargera tous les packages listés par info loaded et qui correspondent à pkgPat dans l'interpréteur utilisé pour traiter les fichiers. Dans la plupart des cas, cela satisfera les appels Tcl_PkgRequire effectués par les fichiers binaires.

Si vous indexez deux fichiers binaires et que l'un dépend de l'autre, vous devriez spécifier celui qui a les dépendances en dernier. De cette façon, celui sans dépendances sera chargé et indexé, puis le package qu'il fournit sera disponible lorsque le second fichier sera traité. Vous devrez peut-être également charger le premier package dans l'interpréteur temporaire utilisé pour créer l'index en utilisant le drapeau -load; cela ne nuira pas de spécifier des motifs de package qui ne sont pas encore chargés.

Si vous avez un package qui est réparti entre des scripts et un fichier binaire, alors vous devriez éviter le drapeau -load. Le problème est que si vous chargez un package avant de calculer l'index, cela masque tout autre fichier qui fournit une partie du même package. Si vous devez utiliser -load, alors vous devez spécifier les scripts en premier; sinon, le package chargé à partir du fichier binaire peut masquer le package défini par les scripts.
