pthread_mutex_init(3) Manuel des fonctions de bibliothèque pthread_mutex_init(3)

NOM

pthread_mutex_init, pthread_mutex_lock, pthread_mutex_trylock, pthread_mutex_unlock, pthread_mutex_destroy - opérations sur les mutex

SYNTAXE

#include <pthread.h>
pthread_mutex_t fastmutex = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_t recmutex = PTHREAD_RECURSIVE_MUTEX_INITIALIZER_NP;
pthread_mutex_t errchkmutex = PTHREAD_ERRORCHECK_MUTEX_INITIALIZER_NP;
int pthread_mutex_init(pthread_mutex_t *mutex,
                       const pthread_mutexattr_t *mutexattr);
int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);
int pthread_mutex_destroy(pthread_mutex_t *mutex);

DESCRIPTION

Un mutex est un dispositif d'EXclusion MUTuelle, utile pour protéger les structures de données partagées contre les modifications concurrentes et pour implémenter des sections critiques et des moniteurs.

Un mutex a deux états possibles : déverrouillé (non possédé par un thread) et verrouillé (possédé par un thread). Un mutex ne peut jamais être possédé par deux threads différents simultanément. Un thread tentant de verrouiller un mutex déjà verrouillé par un autre thread est suspendu jusqu'à ce que le thread propriétaire déverrouille d'abord le mutex.

pthread_mutex_init() initialise l'objet mutex pointé par mutex conformément aux attributs de mutex spécifiés dans mutexattr. Si mutexattr est NULL, les attributs par défaut sont utilisés.

L'implémentation LinuxThreads ne prend en charge qu'un seul type d'attribut de mutex, la sorte de mutex, qui est soit "rapide" ("fast"), "récursif" ("recursive"), soit "de vérification d'erreur" ("error checking"). Le type d'un mutex détermine s'il peut être verrouillé à nouveau par un thread qui le possède déjà. Le type par défaut est "rapide". Voir pthread_mutexattr_init(3) pour plus d'informations sur les attributs de mutex.

Les variables de type pthread_mutex_t peuvent également être initialisées statiquement, en utilisant les constantes PTHREAD_MUTEX_INITIALIZER (pour les mutex rapides), PTHREAD_RECURSIVE_MUTEX_INITIALIZER_NP (pour les mutex récursifs) et PTHREAD_ERRORCHECK_MUTEX_INITIALIZER_NP (pour les mutex de vérification d'erreur).

pthread_mutex_lock() verrouille le mutex donné. Si le mutex est actuellement déverrouillé, il devient verrouillé et possédé par le thread appelant, et pthread_mutex_lock() retourne immédiatement. Si le mutex est déjà verrouillé par un autre thread, pthread_mutex_lock() suspend le thread appelant jusqu'à ce que le mutex soit déverrouillé.

Si le mutex est déjà verrouillé par le thread appelant, le comportement de pthread_mutex_lock() dépend du type du mutex. Si le mutex est de type "rapide", le thread appelant est suspendu jusqu'à ce que le mutex soit déverrouillé, provoquant ainsi effectivement un blocage du thread appelant (deadlock). Si le mutex est de type "vérification d'erreur", pthread_mutex_lock() retourne immédiatement avec le code d'erreur EDEADLK. Si le mutex est de type "récursif", pthread_mutex_lock() réussit et retourne immédiatement, enregistrant le nombre de fois où le thread appelant a verrouillé le mutex. Un nombre égal d'opérations pthread_mutex_unlock() doit être effectué avant que le mutex ne revienne à l'état déverrouillé.

pthread_mutex_trylock() se comporte de manière identique à pthread_mutex_lock(), sauf qu'il ne bloque pas le thread appelant si le mutex est déjà verrouillé par un autre thread (ou par le thread appelant dans le cas d'un mutex "rapide"). Au lieu de cela, pthread_mutex_trylock() retourne immédiatement avec le code d'erreur EBUSY.

pthread_mutex_unlock() déverrouille le mutex donné. Le mutex est supposé être verrouillé et possédé par le thread appelant à l'entrée de pthread_mutex_unlock(). Si le mutex est de type "rapide", pthread_mutex_unlock() le retourne toujours à l'état déverrouillé. S'il est de type "récursif", il décrémente le compteur de verrouillage du mutex (nombre d'opérations pthread_mutex_lock() effectuées dessus par le thread appelant), et ce n'est que lorsque ce compteur atteint zéro que le mutex est effectivement déverrouillé.

Sur les mutex de type "vérification d'erreur" et "récursif", pthread_mutex_unlock() vérifie réellement à l'exécution que le mutex est verrouillé à l'entrée, et qu'il a été verrouillé par le même thread qui appelle maintenant pthread_mutex_unlock(). Si ces conditions ne sont pas remplies, un code d'erreur est retourné et le mutex reste inchangé. Les mutex "rapides" n'effectuent aucune de ces vérifications, permettant ainsi à un mutex verrouillé d'être déverrouillé par un thread autre que son propriétaire. Ceci est un comportement non portable et ne doit pas être utilisé.

pthread_mutex_destroy() détruit un objet mutex, libérant les ressources qu'il pourrait détenir. Le mutex doit être déverrouillé à l'entrée. Dans l'implémentation LinuxThreads, aucune ressource n'est associée aux objets mutex, donc pthread_mutex_destroy() ne fait effectivement rien d'autre que vérifier que le mutex est déverrouillé.

ANNULATION

Aucune des fonctions de mutex n'est un point d'annulation, pas même pthread_mutex_lock(), malgré le fait qu'elle puisse suspendre un thread pendant des durées arbitraires. De cette manière, le statut des mutex aux points d'annulation est prévisible, permettant aux gestionnaires d'annulation de déverrouiller précisément les mutex qui doivent être déverrouillés avant que le thread ne cesse de s'exécuter. Par conséquent, les threads utilisant l'annulation différée ne doivent jamais détenir un mutex pendant de longues périodes.

SURETÉ DES SIGNAUX ASYNCHRONES

Les fonctions de mutex ne sont pas sûres pour les signaux asynchrones. Cela signifie qu'elles ne doivent pas être appelées depuis un gestionnaire de signaux. En particulier, appeler pthread_mutex_lock() ou pthread_mutex_unlock() depuis un gestionnaire de signaux peut entraîner un blocage (deadlock) du thread appelant.

VALEUR DE RETOUR

pthread_mutex_init() retourne toujours 0. Les autres fonctions de mutex retournent 0 en cas de succès et un code d'erreur non nul en cas d'erreur.

ERREURS

La fonction pthread_mutex_lock() retourne le code d'erreur suivant en cas d'erreur :

EINVAL
Le mutex n'a pas été initialisé correctement.
EDEADLK
Le mutex est déjà verrouillé par le thread appelant (mutex de type "vérification d'erreur" seulement).

La fonction pthread_mutex_trylock() retourne les codes d'erreur suivants en cas d'erreur :

EBUSY
Le mutex n'a pas pu être acquis car il était actuellement verrouillé.
EINVAL
Le mutex n'a pas été initialisé correctement.

La fonction pthread_mutex_unlock() retourne le code d'erreur suivant en cas d'erreur :

EINVAL
Le mutex n'a pas été initialisé correctement.
EPERM
Le thread appelant ne possède pas le mutex (mutex de type "vérification d'erreur" seulement).

La fonction pthread_mutex_destroy() retourne le code d'erreur suivant en cas d'erreur :

EBUSY
Le mutex est actuellement verrouillé.

VOIR AUSSI

pthread_mutexattr_init(3), pthread_mutexattr_setkind_np(3), pthread_cancel(3).
