PTHREAD_COND_BROADCAST(3P) Manuel du programmeur POSIX PTHREAD_COND_BROADCAST(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consulter la page de manuel Linux correspondante pour les détails du comportement Linux), ou l'interface peut ne pas être implémentée sur Linux.

NOM

pthread_cond_broadcast, pthread_cond_signal — diffusion ou signalement d'une condition

SYNTAXE

#include <pthread.h>
int pthread_cond_broadcast(pthread_cond_t *cond);
int pthread_cond_signal(pthread_cond_t *cond);

DESCRIPTION

Ces fonctions débloqueront les threads bloqués sur une variable de condition.

La fonction pthread_cond_broadcast() débloquera tous les threads actuellement bloqués sur la variable de condition spécifiée cond.

La fonction pthread_cond_signal() débloquera au moins un des threads bloqués sur la variable de condition spécifiée cond (s'il y a des threads bloqués sur cond).

Si plus d'un thread est bloqué sur une variable de condition, la politique de planification déterminera l'ordre dans lequel les threads seront débloqués. Lorsque chaque thread débloqué à la suite d'un pthread_cond_broadcast() ou d'un pthread_cond_signal() revient de son appel à pthread_cond_wait() ou pthread_cond_timedwait(), le thread possédera le mutex avec lequel il a appelé pthread_cond_wait() ou pthread_cond_timedwait(). Le(s) thread(s) débloqué(s) concourra/concurreront pour le mutex conformément à la politique de planification (si applicable), et comme s'il(s) avait/avaient appelé pthread_mutex_lock().

Les fonctions pthread_cond_broadcast() ou pthread_cond_signal() peuvent être appelées par un thread, qu'il possède ou non actuellement le mutex que les threads appelant pthread_cond_wait() ou pthread_cond_timedwait() ont associé à la variable de condition pendant leurs attentes ; cependant, si un comportement de planification prévisible est requis, ce mutex doit être verrouillé par le thread appelant pthread_cond_broadcast() ou pthread_cond_signal().

Les fonctions pthread_cond_broadcast() et pthread_cond_signal() n'auront aucun effet s'il n'y a actuellement aucun thread bloqué sur cond.

Le comportement est indéfini si la valeur spécifiée par l'argument cond de pthread_cond_broadcast() ou pthread_cond_signal() ne fait pas référence à une variable de condition initialisée.

VALEUR DE RETOUR

En cas de succès, les fonctions pthread_cond_broadcast() et pthread_cond_signal() retourneront zéro ; sinon, un numéro d'erreur sera retourné pour indiquer l'erreur.

ERREURS

Ces fonctions ne retourneront pas de code d'erreur de [EINTR].

Les sections suivantes sont informatives.

EXEMPLES

Aucun.

UTILISATION APPLICATIVE

La fonction pthread_cond_broadcast() est utilisée chaque fois que l'état de la variable partagée a été modifié d'une manière telle que plus d'un thread peut poursuivre sa tâche. Considérer un problème de producteur unique/consommateurs multiples, où le producteur peut insérer plusieurs éléments dans une liste qui est accédée un élément à la fois par les consommateurs. En appelant la fonction pthread_cond_broadcast(), le producteur notifierait tous les consommateurs qui pourraient attendre, et ainsi l'application recevrait plus de débit sur un système multiprocesseur. De plus, pthread_cond_broadcast() facilite l'implémentation d'un verrou lecture-écriture. La fonction pthread_cond_broadcast() est nécessaire pour réveiller tous les lecteurs en attente lorsqu'un écrivain relâche son verrou. Enfin, l'algorithme de validation en deux phases peut utiliser cette fonction de diffusion pour notifier tous les clients d'un engagement de transaction imminent.

Il n'est pas sûr d'utiliser la fonction pthread_cond_signal() dans un gestionnaire de signaux qui est invoqué de manière asynchrone. Même si c'était sûr, il y aurait toujours une condition de concurrence entre le test de la valeur booléenne pthread_cond_wait() qui ne pourrait pas être éliminée efficacement.

Les mutex et les variables de condition ne sont donc pas adaptés pour libérer un thread en attente en signalant depuis un code exécuté dans un gestionnaire de signaux.

RATIONALE

Si une implémentation détecte que la valeur spécifiée par l'argument cond de pthread_cond_broadcast() ou pthread_cond_signal() ne fait pas référence à une variable de condition initialisée, il est recommandé que la fonction échoue et signale une erreur [EINVAL].

Réveils multiples par signal de condition

Sur un système multiprocesseur, il peut être impossible pour une implémentation de pthread_cond_signal() d'éviter le déblocage de plus d'un thread bloqué sur une variable de condition. Par exemple, considérez l'implémentation partielle suivante de pthread_cond_wait() et pthread_cond_signal(), exécutée par deux threads dans l'ordre donné. Un thread essaie d'attendre sur la variable de condition, un autre exécute simultanément pthread_cond_signal(), tandis qu'un troisième thread est déjà en attente.

pthread_cond_wait(mutex, cond):
    value = cond->value; /* 1 */
    pthread_mutex_unlock(mutex); /* 2 */
    pthread_mutex_lock(cond->mutex); /* 10 */
    if (value == cond->value) { /* 11 */
        me->next_cond = cond->waiter;
        cond->waiter = me;
        pthread_mutex_unlock(cond->mutex);
        unable_to_run(me);
    } else
        pthread_mutex_unlock(cond->mutex); /* 12 */
    pthread_mutex_lock(mutex); /* 13 */
pthread_cond_signal(cond):
    pthread_mutex_lock(cond->mutex); /* 3 */
    cond->value++; /* 4 */
    if (cond->waiter) { /* 5 */
        sleeper = cond->waiter; /* 6 */
        cond->waiter = sleeper->next_cond; /* 7 */
        able_to_run(sleeper); /* 8 */
    }
    pthread_mutex_unlock(cond->mutex); /* 9 */

L'effet est que plus d'un thread peut revenir de son appel à pthread_cond_wait() ou pthread_cond_timedwait() suite à un appel à pthread_cond_signal(). Cet effet est appelé « réveil intempestif ». Notez que la situation est auto-correctrice dans le sens où le nombre de threads ainsi réveillés est fini ; par exemple, le thread suivant à appeler pthread_cond_wait() après la séquence d'événements ci-dessus sera bloqué.

Bien que ce problème puisse être résolu, la perte d'efficacité pour une condition marginale qui ne se produit que rarement est inacceptable, surtout étant donné qu'il faut tester le prédicat associé à une variable de condition de toute façon. La correction de ce problème réduirait inutilement le degré de concurrence dans ce bloc de construction de base pour toutes les opérations de synchronisation de niveau supérieur.

Un avantage supplémentaire de permettre les réveils intempestifs est que les applications sont obligées de coder une boucle de test de prédicat autour de l'attente de condition. Cela rend également l'application tolérante aux diffusions ou signaux de condition superflus sur la même variable de condition qui pourraient être codés dans une autre partie de l'application. Les applications résultantes sont donc plus robustes. Par conséquent, POSIX.1-2008 documente explicitement que des réveils intempestifs peuvent survenir.

pthread_cond_broadcast(3p)

2017-09-15

NAME

pthread_cond_broadcast, pthread_cond_signal - broadcast or signal a condition

SYNOPSIS

#include <pthread.h>

int pthread_cond_broadcast(pthread_cond_t *cond);
int pthread_cond_signal(pthread_cond_t *cond);

DESCRIPTION

The pthread_cond_broadcast() function shall unblock all threads currently blocked waiting on the condition variable specified by cond. The calling thread must have ownership of the mutex with which the condition variable was associated at the time of the call.

The pthread_cond_signal() function shall unblock at least one of the threads currently blocked waiting on the condition variable specified by cond. If there are no such threads, pthread_cond_signal() shall have no effect. The calling thread must have ownership of the mutex with which the condition variable was associated at the time of the call.

In both cases, the thread(s) that are unblocked remain blocked until they can successfully regain ownership of the mutex that was associated with the condition variable, and then they return from their call to pthread_cond_wait() or pthread_cond_timedwait().

When multiple threads are unblocked, they are not necessarily unblocked in any particular order. The scheduling and execution of threads are determined by the thread scheduling policy.

If the mutex is not locked by the calling thread when either function is called, the behavior is undefined.

These functions are thread-safe.

If cond is an invalid condition variable, the behavior is undefined.

RETURN VALUE

On success, these functions shall return 0; otherwise, they shall return an error number to indicate the error.

ERRORS

ENOTSUP The implementation does not support this condition variable operation.

EINVAL The value specified by cond is not a valid condition variable.

EBUSY The mutex associated with cond is locked by another thread.

EXAMPLES

See pthread_cond_wait(3p).

APPLICATION USAGE

The pthread_cond_signal() function is a basic building block for thread synchronization. It is typically used to wake up a single thread that is waiting for a condition to be met. The pthread_cond_broadcast() function is used to wake up all threads that are waiting for a condition to be met. This is useful when multiple threads can potentially satisfy the condition, but only one of them needs to proceed.

A common pattern is to use these functions in conjunction with a mutex to protect shared data. A thread that modifies the shared data may call pthread_cond_signal() or pthread_cond_broadcast() to notify other threads that the data has changed. The waiting threads will then wake up, re-acquire the mutex, and check the condition again.

RATIONALE

The condition variable functions provide a way for threads to wait for certain conditions to be met without busy-waiting. They are essential for building complex synchronization primitives and for managing shared resources in multithreaded applications.
