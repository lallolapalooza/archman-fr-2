PTHREAD_KEY_CREATE(3P) Manuel du programmeur POSIX PTHREAD_KEY_CREATE(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pthread_key_create — création de clé de données spécifiques au thread

SYNTAXE

#include <pthread.h>
int pthread_key_create(pthread_key_t *key, void (*destructor)(void*));

DESCRIPTION

La fonction pthread_key_create() crée une clé de données spécifiques au thread, visible par tous les threads du processus. Les valeurs de clé fournies par pthread_key_create() sont des objets opaques utilisés pour localiser les données spécifiques au thread. Bien que la même valeur de clé puisse être utilisée par différents threads, les valeurs liées à la clé par pthread_setspecific() sont maintenues par thread et persistent pendant la durée de vie du thread appelant.

Lors de la création de la clé, la valeur NULL est associée à la nouvelle clé dans tous les threads actifs. Lors de la création d'un thread, la valeur NULL est associée à toutes les clés définies dans le nouveau thread.

Une fonction destructrice optionnelle peut être associée à chaque valeur de clé. Lors de la sortie d'un thread, si une valeur de clé a un pointeur destructeur non NULL, et si le thread a une valeur non NULL associée à cette clé, la valeur de la clé est définie à NULL, puis la fonction pointée est appelée avec la valeur précédemment associée comme seul argument. L'ordre des appels aux destructeurs n'est pas spécifié s'il existe plus d'un destructeur pour un thread lors de sa sortie.

Si, après que tous les destructeurs ont été appelés pour toutes les valeurs non NULL avec des destructeurs associés, il reste des valeurs non NULL avec des destructeurs associés, le processus est répété. Si, après au moins {PTHREAD_DESTRUCTOR_ITERATIONS} itérations d'appels aux destructeurs pour les valeurs non NULL en attente, il reste des valeurs non NULL avec des destructeurs associés, les implémentations peuvent arrêter d'appeler les destructeurs, ou elles peuvent continuer à appeler les destructeurs jusqu'à ce qu'il n'y ait plus de valeurs non NULL avec des destructeurs associés, même si cela peut entraîner une boucle infinie.

VALEUR DE RETOUR

En cas de succès, la fonction pthread_key_create() stocke la nouvelle valeur de clé créée à *key et retourne zéro. Sinon, un numéro d'erreur est retourné pour indiquer l'erreur.

ERREURS

La fonction pthread_key_create() échoue si :

EAGAIN
Le système manquait des ressources nécessaires pour créer une autre clé de données spécifique au thread, ou la limite imposée par le système sur le nombre total de clés par processus {PTHREAD_KEYS_MAX} a été dépassée.
ENOMEM
La mémoire disponible est insuffisante pour créer la clé.

La fonction pthread_key_create() ne retournera pas le code d'erreur [EINTR].

Les sections suivantes sont informatives.

EXEMPLES

L'exemple suivant montre une fonction qui initialise une clé de données spécifique au thread lors de son premier appel, et associe un objet spécifique au thread à chaque thread appelant, en initialisant cet objet si nécessaire.

static pthread_key_t key;
static pthread_once_t key_once = PTHREAD_ONCE_INIT;
static void
make_key()
{
    (void) pthread_key_create(&key, NULL);
}
func()
{
    void *ptr;
    (void) pthread_once(&key_once, make_key);
    if ((ptr = pthread_getspecific(key)) == NULL) {
        ptr = malloc(OBJECT_SIZE);
        ...
        (void) pthread_setspecific(key, ptr);
    }
    ...
}

Notez que la clé doit être initialisée avant que pthread_getspecific() ou pthread_setspecific() puissent être utilisés. L'appel pthread_key_create() peut soit être explicitement fait dans une routine d'initialisation de module, soit être fait implicitement par le premier appel à un module comme dans cet exemple. Toute tentative d'utiliser la clé avant son initialisation est une erreur de programmation, rendant le code ci-dessous incorrect.

static pthread_key_t key;
func()
{
    void *ptr;
   /* CLÉ NON INITIALISÉE !!! CELA NE FONCTIONNERA PAS !!! */
    if ((ptr = pthread_getspecific(key)) == NULL &&
        pthread_setspecific(key, NULL) != 0) {
        pthread_key_create(&key, NULL);
        ...
    }
}

UTILISATION APPLICATION

Aucune.

RATIONALE

Fonctions destructrices

Normalement, la valeur liée à une clé au nom d'un thread particulier est un pointeur vers un espace alloué dynamiquement au nom du thread appelant. Les fonctions destructrices spécifiées avec pthread_key_create() sont destinées à être utilisées pour libérer cet espace lors de la sortie du thread. Les gestionnaires de nettoyage d'annulation de thread ne peuvent pas être utilisés à cette fin car les données spécifiques au thread peuvent persister en dehors de la portée lexicale dans laquelle les gestionnaires de nettoyage d'annulation opèrent.

Si la valeur associée à une clé doit être mise à jour pendant la durée de vie du thread, il peut être nécessaire de libérer l'espace associé à l'ancienne valeur avant que la nouvelle valeur ne soit liée. Bien que la fonction pthread_setspecific() puisse le faire automatiquement, cette fonctionnalité n'est pas nécessaire assez souvent pour justifier la complexité ajoutée. Au lieu de cela, le programmeur est responsable de la libération de l'espace obsolète :

pthread_getspecific(key, &old);
new = allocate();
destructor(old);
pthread_setspecific(key, new);
Note :
L'exemple ci-dessus pourrait fuir de l'espace s'il est exécuté avec l'annulation asynchrone activée. Aucun problème de ce type ne se produit dans l'état d'annulation par défaut si aucun point d'annulation ne se produit entre le get et le set.

Il n'y a pas de notion de fonction sûre pour les destructeurs. Si une application n'appelle pas pthread_exit() depuis un gestionnaire de signaux, ou si elle bloque tout signal dont le gestionnaire peut appeler pthread_exit() tout en appelant des fonctions non sûres pour l'annulation, toutes les fonctions peuvent être appelées en toute sécurité depuis les destructeurs.

Création de clés de données non idempotente

Il y a eu des demandes pour rendre pthread_key_create() idempotent par rapport à un paramètre d'adresse key donné. Cela permettrait aux applications d'appeler pthread_key_create() plusieurs fois pour une adresse key donnée et garantirait qu'une seule clé serait créée. Cela nécessiterait que la valeur de clé soit préalablement initialisée (éventuellement à la compilation) à une valeur nulle connue et exigerait qu'une exclusion mutuelle implicite soit effectuée en fonction de l'adresse et du contenu du paramètre key afin de garantir qu'exactement une clé serait créée.

Malheureusement, l'exclusion mutuelle implicite ne serait pas limitée à pthread_key_create() uniquement. Sur de nombreuses implémentations, une exclusion mutuelle implicite devrait également être effectuée par pthread_getspecific() et pthread_setspecific() afin de se protéger contre l'utilisation de valeurs de clé stockées incomplètement ou pas encore visibles. Cela pourrait augmenter considérablement le coût des opérations importantes, en particulier pthread_getspecific().

Par conséquent, cette proposition a été rejetée. La fonction pthread_key_create() n'effectue aucune synchronisation implicite. Il appartient au programmeur de s'assurer qu'elle est appelée exactement une fois par clé avant utilisation de la clé. Plusieurs mécanismes simples peuvent déjà être utilisés pour y parvenir, notamment l'appel de fonctions d'initialisation de module explicites, l'utilisation de mutex et l'utilisation de pthread_once(). Cela ne représente aucun fardeau significatif pour le programmeur, n'introduit aucun mécanisme de synchronisation implicite ad hoc potentiellement déroutant, et permet potentiellement aux opérations de données spécifiques aux threads couramment utilisées d'être plus efficaces.
