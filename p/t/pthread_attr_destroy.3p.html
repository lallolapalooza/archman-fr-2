PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pthread_attr_destroy, pthread_attr_init — détruire et initialiser l'objet d'attributs de thread

SYNOPSIS

#include <pthread.h>
int pthread_attr_destroy(pthread_attr_t *attr);
int pthread_attr_init(pthread_attr_t *attr);

DESCRIPTION

La fonction pthread_attr_destroy() détruit un objet d'attributs de thread. Une implémentation peut amener pthread_attr_destroy() à définir attr à une valeur invalide indéfinie par l'implémentation. Un objet d'attributs attr détruit peut être réinitialisé en utilisant pthread_attr_init() ; les résultats de toute autre référence à l'objet après sa destruction sont indéfinis.

La fonction pthread_attr_init() initialise un objet d'attributs de thread attr avec la valeur par défaut pour tous les attributs individuels utilisés par une implémentation donnée.

L'objet d'attributs résultant (éventuellement modifié en définissant les valeurs des attributs individuels) lorsqu'il est utilisé par pthread_create() définit les attributs du thread créé. Un seul objet d'attributs peut être utilisé dans plusieurs appels simultanés à pthread_create(). Les résultats sont indéfinis si pthread_attr_init() est appelé en spécifiant un objet d'attributs attr déjà initialisé.

Le comportement est indéfini si la valeur spécifiée par l'argument attr à pthread_attr_destroy() ne fait pas référence à un objet d'attributs de thread initialisé.

VALEUR DE RETOUR

En cas de succès, pthread_attr_destroy() et pthread_attr_init() retournent la valeur 0 ; sinon, un numéro d'erreur est retourné pour indiquer l'erreur.

ERREURS

La fonction pthread_attr_init() échoue si :

ENOMEM
Une mémoire insuffisante existe pour initialiser l'objet d'attributs de thread.

Ces fonctions ne retourneront pas de code d'erreur [EINTR].

RATIONALE

Les objets d'attributs sont fournis pour les threads, les mutex et les variables de condition comme mécanisme pour supporter une standardisation future probable dans ces domaines sans nécessiter que la fonction elle-même soit modifiée.

Les objets d'attributs fournissent une isolation propre des aspects configurables des threads. Par exemple, la « taille de la pile » est un attribut important d'un thread, mais elle ne peut pas être exprimée de manière portable. Lors du portage d'un programme multithreadé, les tailles de pile doivent souvent être ajustées. L'utilisation d'objets d'attributs peut aider en permettant que les changements soient isolés en un seul endroit, plutôt que d'être répartis sur chaque instance de création de thread.

Les objets d'attributs peuvent être utilisés pour configurer des « classes » de threads avec des attributs similaires ; par exemple, « threads avec de grandes piles et une priorité élevée » ou « threads avec des piles minimales ». Ces classes peuvent être définies en un seul endroit et ensuite référencées partout où des threads doivent être créés. Les changements dans les décisions de « classe » deviennent simples, et une analyse détaillée de chaque appel pthread_create() n'est pas requise.

Les objets d'attributs sont définis comme des types opaques comme une aide à l'extensibilité. Si ces objets étaient spécifiés comme des structures, l'ajout de nouveaux attributs forcerait la recompilation de tous les programmes multithreadés lorsque les objets d'attributs sont étendus ; cela pourrait ne pas être possible si différents composants du programme étaient fournis par différents fournisseurs.

De plus, les objets d'attributs opaques offrent des opportunités d'amélioration des performances. La validité des arguments peut être vérifiée une fois lors de la définition des attributs, plutôt qu'à chaque création de thread. Les implémentations ont souvent besoin de mettre en cache des objets noyau coûteux à créer. Les objets d'attributs opaques fournissent un mécanisme efficace pour détecter lorsque les objets mis en cache deviennent invalides en raison de changements d'attributs.

Étant donné que l'affectation n'est pas nécessairement définie sur un type opaque donné, les valeurs par défaut indéfinies par l'implémentation ne peuvent pas être définies de manière portable. La solution à ce problème est de permettre aux objets d'attributs d'être initialisés dynamiquement par des fonctions d'initialisation d'objets d'attributs, de sorte que les valeurs par défaut puissent être fournies automatiquement par l'implémentation.

La proposition suivante a été fournie comme alternative suggérée aux attributs fournis :

1.
Maintenir le style de passage d'un paramètre formé par l'opération OU logique (OU exclusif) des drapeaux aux routines d'initialisation (pthread_create(), pthread_mutex_init(), pthread_cond_init()). Le paramètre contenant les drapeaux devrait être un type opaque pour l'extensibilité. Si aucun drapeau n'est défini dans le paramètre, alors les objets sont créés avec des caractéristiques par défaut. Une implémentation peut spécifier des valeurs de drapeaux indéfinies par l'implémentation et le comportement associé.
2.
Si une spécialisation supplémentaire des mutex et des variables de condition est nécessaire, les implémentations peuvent spécifier des procédures supplémentaires qui opèrent sur les objets pthread_mutex_t et pthread_cond_t (au lieu des objets d'attributs).

Les difficultés avec cette solution sont :

1.
Un masque de bits n'est pas opaque si les bits doivent être définis dans des objets d'attributs de masque de bits à l'aide d'opérations OU logiques explicitées. Si l'ensemble des options dépasse un int, les programmeurs d'applications doivent connaître l'emplacement de chaque bit. Si les bits sont définis ou lus par encapsulation (c'est-à-dire, fonctions de lecture et d'écriture), alors le masque de bits n'est qu'une implémentation des objets d'attributs tels que définis actuellement et ne devrait pas être exposé au programmeur.
2.
De nombreux attributs ne sont pas booléens ou de très petites valeurs entières. Par exemple, la politique de planification peut être placée dans un champ de 3 ou 4 bits, mais la priorité nécessite 5 bits ou plus, occupant ainsi au moins 8 bits sur les 16 bits possibles sur les machines avec des entiers de 16 bits. Pour cette raison, le masque de bits ne peut raisonnablement contrôler que si des attributs particuliers sont définis ou non, et il ne peut pas servir de référentiel pour la valeur elle-même. La valeur doit être spécifiée comme paramètre de fonction (ce qui n'est pas extensible), ou en définissant un champ de structure (ce qui n'est pas opaque), ou par des fonctions de lecture et d'écriture (faisant du masque de bits un ajout redondant aux objets d'attributs).

La taille de la pile est définie comme un attribut optionnel car la notion même de pile est intrinsèquement dépendante de la machine. Certaines implémentations peuvent ne pas être en mesure de modifier la taille de la pile, par exemple, et d'autres peuvent ne pas en avoir besoin car les pages de pile peuvent être discontinues et peuvent être allouées et libérées à la demande.

Le mécanisme d'attributs a été conçu en grande partie pour l'extensibilité. Les futures extensions au mécanisme d'attributs ou à tout objet d'attributs défini dans ce volume de POSIX.1‐2017 devront être faites avec soin afin de ne pas affecter la compatibilité binaire.

Les objets d'attributs, même s'ils sont alloués au moyen de fonctions d'allocation dynamique telles que malloc(), peuvent avoir leur taille fixée à la compilation. Cela signifie, par exemple, qu'un pthread_create() dans une implémentation avec des extensions à pthread_attr_t ne peut pas regarder au-delà de la zone que l'application binaire suppose être valide. Cela suggère que les implémentations devraient conserver un champ de taille dans l'objet d'attributs, ainsi que potentiellement des informations de version, si des extensions dans des directions différentes (potentiellement par différents fournisseurs) doivent être prises en charge.

Si une implémentation détecte que la valeur spécifiée par l'argument attr à pthread_attr_destroy() ne fait pas référence à un objet d'attributs de thread initialisé, il est recommandé que la fonction échoue et signale une erreur [EINVAL].

NAME

pthread_attr_destroy - détruire les attributs d'un thread

SYNOPSIS

#include <pthread.h>

int pthread_attr_destroy(pthread_attr_t *attr);

DESCRIPTION

La fonction pthread_attr_destroy détruit un objet d'attributs de thread ; le stockage utilisé par cet objet est rendu disponible pour une réutilisation ultérieure. L'objet d'attributs spécifié par attr est rendu invalide. Il est sûr d'appeler pthread_attr_destroy sur un objet d'attributs qui a été détruit, mais il est déconseillé.

Après qu'un appel réussi à pthread_attr_destroy a retourné, l'objet attr ne peut plus être utilisé. Si un thread est créé avec pthread_create() en utilisant un objet d'attributs qui a été détruit, le comportement n'est pas défini.

RETURN VALUE

En cas de succès, pthread_attr_destroy renvoie 0. Sinon, un numéro d'erreur est renvoyé pour indiquer l'erreur.

ERRORS

La fonction pthread_attr_destroy peut échouer avec l'erreur suivante :

EINVAL
La valeur spécifiée par attr n'est pas valide.

EXAMPLES

Aucune.

APPLICATION USAGE

Aucune.

RATIONALE

La fonction pthread_attr_init() initialise un objet d'attributs de thread pour une utilisation ultérieure avec pthread_attr_set*() et pthread_create(). La fonction pthread_attr_destroy() libère les ressources associées à l'objet d'attributs.

Il est possible que pthread_attr_destroy() soit appelée sur un objet d'attributs qui est déjà en cours d'utilisation par un thread en attente de création. Dans ce cas, pthread_attr_destroy() devrait échouer.

Il est également possible que pthread_attr_destroy() soit appelée sur un objet d'attributs qui a été détruit par un appel antérieur. Dans ce cas, il est recommandé que la fonction échoue et signale une erreur [EBUSY].
