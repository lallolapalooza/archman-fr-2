NOM

pt-table-checksum - Vérifie l'intégrité de la réplication MySQL.

SYNOPSIS

Utilisation : pt-table-checksum [OPTIONS] [DSN]

pt-table-checksum effectue une vérification de cohérence de réplication en ligne en exécutant des requêtes de checksum sur la source de réplication, qui produisent des résultats différents sur les répliques qui sont incohérentes avec la source. Le "STATUT DE SORTIE" de l'outil est non nul si des différences sont trouvées, ou si des avertissements ou des erreurs se produisent.

La commande suivante se connectera à la source de réplication sur localhost, vérifiera chaque table et rapportera les résultats sur chaque réplique détectée :

pt-table-checksum

Cet outil est axé sur la recherche efficace de différences de données. Si des données sont différentes, vous pouvez résoudre le problème avec pt-table-sync.

RISQUES

Percona Toolkit est mature, éprouvé sur le terrain et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Examiner les "BOGUES" connus de l'outil
  • Tester l'outil sur un serveur non-production
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

Voir aussi "LIMITATIONS".

DESCRIPTION

pt-table-checksum est conçu pour faire la bonne chose par défaut dans presque tous les cas. En cas de doute, utilisez "--explain" pour voir comment l'outil va checksummer une table. Voici un aperçu général de son fonctionnement.

Contrairement aux anciennes versions de pt-table-checksum, cet outil est axé sur un seul objectif et ne présente pas beaucoup de complexité ni ne prend en charge de nombreuses techniques de checksumming différentes. Il exécute des requêtes de checksum sur un seul serveur, et celles-ci transitent par la réplication pour être ré-exécutées sur les répliques. Si vous avez besoin de l'ancien comportement, vous pouvez utiliser la version 1.0 de Percona Toolkit.

pt-table-checksum se connecte au serveur que vous spécifiez, et trouve les bases de données et les tables qui correspondent aux filtres que vous spécifiez (le cas échéant). Il travaille table par table, il n'accumule donc pas de grandes quantités de mémoire et n'effectue pas beaucoup de travail avant de commencer le checksumming. Cela le rend utilisable sur de très grands serveurs. Nous l'avons utilisé sur des serveurs avec des centaines de milliers de bases de données et de tables, et des trillions de lignes. Quelle que soit la taille du serveur, pt-table-checksum fonctionne de manière égale.

Une raison pour laquelle il peut fonctionner sur de très grandes tables est qu'il divise chaque table en blocs de lignes, et effectue le checksum de chaque bloc avec une seule requête REPLACE..SELECT. Il varie la taille des blocs pour que les requêtes de checksum s'exécutent dans le temps souhaité. L'objectif de diviser les tables en blocs, au lieu de traiter chaque table avec une seule grosse requête, est de garantir que les checksums ne sont pas intrusifs et ne causent pas trop de retard de réplication ou de charge sur le serveur. C'est pourquoi le temps cible pour chaque bloc est de 0,5 seconde par défaut.

L'outil suit la rapidité avec laquelle le serveur est capable d'exécuter les requêtes et ajuste les blocs au fur et à mesure qu'il en apprend davantage sur les performances du serveur. Il utilise une moyenne pondérée exponentiellement décroissante pour maintenir la taille des blocs stable, tout en restant réactif si les performances du serveur changent pendant le checksumming pour quelque raison que ce soit. Cela signifie que l'outil se limitera rapidement si votre serveur devient très chargé pendant un pic de trafic ou une tâche d'arrière-plan, par exemple.

Le découpage en blocs est réalisé par une technique que nous appelions "nibbling" dans d'autres outils de Percona Toolkit. C'est la même technique utilisée pour pt-archiver, par exemple. Les algorithmes de découpage hérités utilisés dans les anciennes versions de pt-table-checksum sont supprimés, car ils ne produisaient pas de blocs de taille prévisible et ne fonctionnaient pas bien sur de nombreuses tables. Tout ce qui est nécessaire pour diviser une table en blocs est un index quelconque (de préférence une clé primaire ou un index unique). S'il n'y a pas d'index, et que la table contient un nombre de lignes suffisamment petit, l'outil effectuera le checksum de la table en un seul bloc.

pt-table-checksum possède de nombreuses autres protections pour garantir qu'il n'interfère pas avec le fonctionnement d'un serveur, y compris les répliques. Pour ce faire, pt-table-checksum détecte les répliques et s'y connecte automatiquement. (Si cela échoue, vous pouvez lui donner un indice avec l'option "--recursion-method".)

L'outil surveille continuellement les répliques. Si une réplique est trop en retard dans la réplication, pt-table-checksum fait une pause pour lui permettre de rattraper son retard. Si une réplique a une erreur, ou si la réplication s'arrête, pt-table-checksum fait une pause et attend. De plus, pt-table-checksum recherche les causes courantes de problèmes, telles que les filtres de réplication, et refuse de fonctionner à moins que vous ne le forciez. Les filtres de réplication sont dangereux, car les requêtes exécutées par pt-table-checksum pourraient potentiellement entrer en conflit avec eux et provoquer l'échec de la réplication.

pt-table-checksum vérifie que les blocs ne sont pas trop grands pour être checksummés en toute sécurité. Il effectue une requête EXPLAIN sur chaque bloc, et ignore les blocs qui pourraient être plus grands que le nombre souhaité de lignes. Vous pouvez configurer la sensibilité de cette protection avec l'option "--chunk-size-limit". Si une table doit être checksummée en un seul bloc parce qu'elle a peu de lignes, alors pt-table-checksum vérifie en outre que la table n'est pas surdimensionnée sur les répliques. Cela évite le scénario suivant : une table est vide sur la source de réplication mais est très grande sur une réplique, et est checksummée en une seule grosse requête, ce qui provoque un très long délai dans la réplication.

Il existe plusieurs autres protections. Par exemple, pt-table-checksum règle son timeout de verrouillage InnoDB au niveau de la session à 1 seconde, de sorte que s'il y a une attente de verrouillage, il en sera la victime au lieu de provoquer le timeout d'autres requêtes. Une autre protection vérifie la charge du serveur de base de données et fait une pause si la charge est trop élevée. Il n'y a pas de réponse unique pour savoir comment faire cela, mais par défaut pt-table-checksum fera une pause s'il y a plus de 25 requêtes exécutées simultanément. Vous devriez probablement définir une valeur raisonnable pour votre serveur avec l'option "--max-load".

Le checksumming est généralement une tâche de faible priorité qui devrait céder le passage aux autres travaux sur le serveur. Cependant, un outil qui doit être redémarré constamment est difficile à utiliser. Ainsi, pt-table-checksum est très résilient aux erreurs. Par exemple, si l'administrateur de la base de données a besoin de tuer les requêtes de pt-table-checksum pour une raison quelconque, ce n'est pas une erreur fatale. Les utilisateurs exécutent souvent pt-kill pour tuer toutes les requêtes de checksum de longue durée. L'outil réessaiera une requête tuée une fois, et si elle échoue à nouveau, il passera au bloc suivant de cette table. Le même comportement s'applique s'il y a un timeout d'attente de verrouillage. L'outil affichera un avertissement si une telle erreur se produit, mais une seule fois par table. Si la connexion à un serveur échoue, pt-table-checksum tentera de se reconnecter et continuera à fonctionner.

Si pt-table-checksum rencontre une condition qui le fait s'arrêter complètement, il est facile de le reprendre avec l'option "--resume". Il commencera par le dernier bloc de la dernière table qu'il a traitée. Vous pouvez également arrêter l'outil en toute sécurité avec CTRL-C. Il terminera le bloc qu'il traite actuellement, puis quittera. Vous pourrez le reprendre comme d'habitude par la suite.

Une fois que pt-table-checksum a terminé le checksumming de tous les blocs d'une table, il fait une pause et attend que toutes les répliques détectées aient fini d'exécuter les requêtes de checksum. Une fois cela terminé, il vérifie toutes les répliques pour voir si elles ont les mêmes données que la source, puis affiche une ligne de sortie avec les résultats. Vous pouvez voir un exemple de sa sortie plus loin dans cette documentation.

L'outil affiche des indicateurs de progression pendant les opérations longues. Il affiche un indicateur de progression à mesure que chaque table est checksummée. La progression est calculée par le nombre estimé de lignes dans la table. Il affichera également un rapport de progression lorsqu'il fera une pause pour attendre que la réplication rattrape son retard, et lorsqu'il attendra pour vérifier les différences entre les répliques et la source. Vous pouvez rendre la sortie moins verbeuse avec l'option "--quiet".

Si vous le souhaitez, vous pouvez interroger manuellement les tables de checksum pour obtenir un rapport sur les bases de données et les tables présentant des différences par rapport à la source. La requête suivante signalera chaque base de données et table avec des différences, ainsi qu'un résumé du nombre de blocs et de lignes potentiellement affectés :

SELECT db, tbl, SUM(this_cnt) AS total_rows, COUNT(*) AS chunks
FROM percona.checksums
WHERE (
 source_cnt <> this_cnt
 OR source_crc <> this_crc
 OR ISNULL(source_crc) <> ISNULL(this_crc))
GROUP BY db, tbl;

La table référencée dans cette requête est la table de checksum, où les checksums sont stockés. Chaque ligne de la table contient le checksum d'un bloc de données f

CONFIGURATION

pt-table-checksum est une application Perl qui vérifie la cohérence des données entre les serveurs MySQL. Il fonctionne en calculant des sommes de contrôle (checksums) pour des tables spécifiées sur un serveur maître, puis en calculant des sommes de contrôle similaires pour ces tables sur les serveurs esclaves. Il enregistre ensuite les différences dans une table appelée checksums. Ce tableau est utilisé par pt-table-sync pour synchroniser les données.

pt-table-checksum est très efficace pour trouver les différences, mais il ne peut pas les corriger. C'est le rôle de pt-table-sync.

pt-table-checksum et pt-table-sync sont deux outils liés qui fonctionnent de manière indépendante. pt-table-checksum peut trouver des différences, mais il ne peut pas les corriger. pt-table-sync peut corriger des différences, mais il ne peut pas les trouver. En les utilisant ensemble, vous pouvez maintenir des données cohérentes sur plusieurs serveurs MySQL. C'est pourquoi on les appelle souvent "la paire".

Notez que pt-table-checksum n'est pas compatible avec pt-table-sync version 1.0. Dans certains cas, ce n'est pas un problème majeur. L'ajout d'une colonne boundaries à la table, puis sa mise à jour avec une clause WHERE générée manuellement, peut suffire à permettre à pt-table-sync version 1.0 d'interagir avec pt-table-checksum version 2.0. En supposant une clé primaire entière nommée 'id', vous pouvez essayer quelque chose comme ceci :

ALTER TABLE checksums ADD boundaries VARCHAR(500);
UPDATE checksums
 SET boundaries = COALESCE(CONCAT('id BETWEEN ', lower_boundary,
    ' AND ', upper_boundary), '1=1');

Prenez en considération que, par défaut, pt-table-checksum utilise des sommes de contrôle "CRC32". "CRC32" n'est pas un algorithme cryptographique et, pour cette raison, il est susceptible d'avoir des collisions. D'autre part, l'algorithme "CRC32" est plus rapide et moins gourmand en CPU que "MD5" et "SHA1".

Matériel de lecture connexe : UDF Percona Toolkit : https://docs.percona.com/percona-server/8.0/udf-percona-toolkit.html Comment éviter les collisions de hachage lors de l'utilisation de la fonction CRC32 de MySQL : https://www.percona.com/blog/2014/10/13/how-to-avoid-hash-collisions-when-using-mysqls-crc32-function/

LIMITATIONS

Répliques utilisant la réplication basée sur les lignes
pt-table-checksum nécessite une réplication basée sur les instructions et définit "binlog_format=STATEMENT" sur la source, mais en raison d'une limitation de MySQL, les répliques n'honorent pas ce changement. Par conséquent, les sommes de contrôle ne seront pas répliquées au-delà des répliques utilisant la réplication basée sur les lignes qui sont des sources pour d'autres répliques.

L'outil vérifie automatiquement le "binlog_format" sur tous les serveurs. Voir "--[no]check-binlog-format".

(Bug 899415 https://bugs.launchpad.net/percona-toolkit/+bug/899415)

Différences de schéma et de table
L'outil présume que les schémas et les tables sont identiques sur la source et toutes les répliques. La réplication échouera si, par exemple, une réplique ne possède pas de schéma qui existe sur la source (et que ce schéma est vérifié), ou si la structure d'une table sur une réplique est différente de celle sur la source.

Percona XtraDB Cluster

pt-table-checksum fonctionne avec Percona XtraDB Cluster (PXC) 5.5.28-23.7 et versions ultérieures. Le nombre de configurations possibles de Percona XtraDB Cluster est important, étant donné qu'il peut également être utilisé avec la réplication régulière. Par conséquent, seules les configurations listées ci-dessous sont prises en charge et connues pour fonctionner. Les autres configurations, comme cluster à cluster, ne sont pas prises en charge et ne fonctionnent probablement pas.

Sauf indication contraire, toutes les configurations prises en charge suivantes nécessitent que vous utilisiez la méthode "dsn" pour "--recursion-method" afin de spécifier les nœuds du cluster. De plus, la vérification du délai (voir "VÉRIFICATIONS DES RÉPLIQUES") n'est pas effectuée pour les nœuds du cluster.

Cluster unique
La configuration PXC la plus simple est un cluster unique : tous les serveurs sont des nœuds de cluster et il n'y a pas de répliques régulières. Si tous les nœuds sont spécifiés dans la table DSN (voir "--recursion-method"), vous pouvez exécuter l'outil sur n'importe quel nœud et toutes les différences sur les autres nœuds seront détectées.

Tous les nœuds doivent appartenir au même cluster (avoir la même valeur "wsrep_cluster_name"), sinon l'outil se terminera avec une erreur. Bien qu'il soit possible d'avoir des clusters différents portant le même nom, cela ne doit pas être fait et n'est pas pris en charge. Cela s'applique à toutes les configurations prises en charge.

Cluster unique avec répliques
Les nœuds du cluster peuvent également être des sources de réplication régulières et répliquer vers des répliques régulières. Cependant, l'outil ne peut détecter des différences sur une réplique que s'il est exécuté sur le "nœud source" de la réplique. Par exemple, si la configuration du cluster est, 
node1 <-> node2 <-> node3
            |         |
            |         +-> replica3
            +-> replica2

vous pouvez détecter des différences sur replica3 en exécutant l'outil sur node3, mais pour détecter des différences sur replica2, vous devez exécuter l'outil à nouveau sur node2. Si vous exécutez l'outil sur node1, il ne détectera aucune différence sur aucune des répliques.

Actuellement, l'outil ne détecte pas cette configuration ni ne signale les répliques qui ne peuvent pas être vérifiées (par exemple, replica2 lors de l'exécution sur node3).

Les répliques dans cette configuration sont toujours soumises à "--[no]check-binlog-format".

Source de réplication vers un cluster unique
Il est possible qu'une source régulière réplique vers un cluster, comme si le cluster était une seule réplique logique, comme ceci : 
source -> node1 <-> node2 <-> node3

L'outil prend en charge cette configuration, mais uniquement s'il est exécuté sur la source et si tous les nœuds du cluster sont cohérents avec la "réplique directe" (node1 dans cet exemple) de la source. Par exemple, si tous les nœuds ont la valeur "foo" pour la ligne 1, mais que la source a la valeur "bar" pour la même ligne, cette différence sera détectée. Ou si seule node1 présente cette différence, elle sera également détectée. Mais si seules node2 ou node3 présentent cette différence, elle ne sera pas détectée. Par conséquent, cette configuration est utilisée pour vérifier que la source et le cluster dans leur ensemble sont cohérents.

Dans cette configuration, l'outil peut détecter automatiquement la "réplique directe" (node1) lorsqu'il est exécuté sur la source, vous n'avez donc pas à utiliser la méthode "dsn" pour "--recursion-method", car node1 représentera le cluster entier, c'est pourquoi tous les autres nœuds doivent y être cohérents.

L'outil émet un avertissement lorsqu'il détecte cette configuration pour vous rappeler qu'elle ne fonctionne que lorsqu'elle est utilisée comme décrit ci-dessus. Ces avertissements n'affectent pas le code de sortie de l'outil ; ce ne sont que des rappels pour aider à éviter les faux résultats positifs.

Prise en charge de RocksDB
En raison des limitations du moteur RocksDB, comme la non-prise en charge de binlog_format=STATEMENT ou la manière dont RocksDB gère les verrous d'intervalle (Gap locks), pt-table-checksum ignorera les tables utilisant le moteur RocksDB. Plus d'informations : (https://www.percona.com/doc/percona-server/LATEST/myrocks/limitations.html)

Les résultats de chaque table sont imprimés lorsque l'outil a fini de calculer la somme de contrôle de la table. Les colonnes sont les suivantes :

TS
L'horodatage (sans l'année) lorsque l'outil a fini de calculer la somme de contrôle de la table.
ERRORS
Le nombre d'erreurs et d'avertissements qui se sont produits lors du calcul de la somme de contrôle de la table. Les erreurs et les avertissements sont imprimés sur la sortie standard d'erreur pendant que la table est en cours de traitement.
DIFFS
Le nombre de morceaux qui diffèrent de la source sur une ou plusieurs répliques. Si "--no-replicate-check" est spécifié, cette colonne contiendra toujours des zéros. Si "--replicate-check-only" est spécifié, seules les tables présentant des différences seront imprimées.
ROWS
Le nombre de lignes sélectionnées et dont la somme de contrôle a été calculée dans la table. Il peut être différent du nombre de lignes de la table si vous utilisez l'option --where.
DIFF_ROWS
Le nombre maximum de différences par morceau. Si un morceau a 2 lignes différentes et qu'un autre morceau en a 3, cette valeur sera 3.
CHUNKS
Le nombre de morceaux dans lesquels la table a été divisée.
SKIPPED
Le nombre de morceaux qui ont été ignorés en raison d'un ou plusieurs des problèmes suivants : 
* MySQL n'utilise pas --chunk-index
* MySQL n'utilise pas l'index complet du morceau (--[no]check-plan)
* La taille du morceau est supérieure à --chunk-size * --chunk-size-limit
* Délai d'attente de verrouillage dépassé (--retries)
* Requête de somme de contrôle annulée (--retries)

À partir de pt-table-checksum 2.2.5, les morceaux ignorés entraînent un "CODE DE SORTIE" non nul.

TIME
Le temps écoulé pendant le calcul de la somme de contrôle de la table.
TABLE
La base de données et la table dont la somme de contrôle a été calculée.

STATUT DE SORTIE

pt-table-checksum a trois statuts de sortie possibles : zéro, 255 et toute autre valeur est un masque de bits avec des drapeaux pour différents problèmes.

Un statut de sortie zéro indique aucune erreur, aucun avertissement, aucune différence de somme de contrôle, ou aucun bloc ou table ignoré.

Un statut de sortie 255 indique une erreur fatale. En d'autres termes : l'outil est mort ou a planté. L'erreur est imprimée sur "STDERR".

Si le statut de sortie n'est ni zéro ni 255, alors sa valeur fonctionne comme un masque de bits avec ces drapeaux :

FLAG              BIT VALUE  SIGNIFICATION
================  =========  ==========================================
ERROR                     1  Une erreur non fatale s'est produite
ALREADY_RUNNING           2  Le fichier --pid existe et le PID est en cours d'exécution
CAUGHT_SIGNAL             4  Signal SIGHUP, SIGINT, SIGPIPE ou SIGTERM intercepté
NO_REPLICAS_FOUND         8  Aucune réplique ou nœud de cluster trouvé
TABLE_DIFF               16  Au moins une différence a été trouvée
SKIP_CHUNK               32  Au moins un bloc a été ignoré
SKIP_TABLE               64  Au moins une table a été ignorée
REPLICATION_STOPPED     128  La réplique est en panne ou arrêtée

Si un drapeau est défini, le statut de sortie sera non nul. Utilisez l'opération booléenne "ET" pour vérifier un drapeau particulier. Par exemple, si "$exit_status & 16" est vrai, alors au moins une différence a été trouvée.

Depuis pt-table-checksum 2.2.5, les blocs ignorés entraînent un statut de sortie non nul. Un statut de sortie de zéro ou 32 équivaut à un statut de sortie zéro avec des blocs ignorés dans les versions précédentes de l'outil.

OPTIONS

Cet outil accepte des arguments de ligne de commande supplémentaires. Référez-vous à la section "SYNOPSIS" et aux informations d'utilisation pour plus de détails.

--ask-pass
groupe : Connexion

Demande un mot de passe lors de la connexion à MySQL.

--channel
type : chaîne

Nom du canal utilisé lors de la connexion à un serveur à l'aide de canaux de réplication. Supposons que vous ayez deux sources de réplication, source_a sur le port 12345, source_b sur le port 1236 et une réplique connectée aux deux sources en utilisant les canaux chan_source_a et chan_source_b. Si vous voulez exécuter pt-table-sync pour synchroniser la réplique par rapport à source_a, pt-table-checksum ne sera pas en mesure de déterminer quelle est la source correcte car SHOW REPLICA STATUS renverra 2 lignes. Dans ce cas, vous pouvez utiliser --channel=chan_source_a pour spécifier le nom du canal à utiliser dans la commande SHOW REPLICA STATUS.

--[no]check-binlog-format
par défaut : oui

Vérifie que le "binlog_format" est le même sur tous les serveurs.

Voir "Répliques utilisant la réplication basée sur les lignes" sous "LIMITATIONS".

--binary-index
Cette option modifie le comportement de "--create-replicate-table" de telle sorte que les colonnes de limite supérieure et inférieure de la table répliquée soient créées avec le type de données BLOB. Ceci est utile dans les cas où vous avez des problèmes pour vérifier les sommes de contrôle de tables avec des clés qui incluent un type de données binaire ou qui ont des jeux de caractères non standard. Voir "--replicate".
--check-interval
type : temps ; par défaut : 1 ; groupe : Limitation de débit

Temps de pause entre les vérifications pour "--max-lag".

--[no]check-plan
par défaut : oui

Vérifie les plans d'exécution des requêtes pour la sécurité. Par défaut, cette option amène pt-table-checksum à exécuter EXPLAIN avant d'exécuter des requêtes destinées à accéder à une petite quantité de données, mais qui pourraient accéder à de nombreuses lignes si MySQL choisit un mauvais plan d'exécution. Celles-ci incluent les requêtes pour déterminer les limites des blocs et les requêtes de blocs elles-mêmes. Si MySQL semble utiliser un mauvais plan d'exécution de requête, l'outil ignorera le bloc de la table.

L'outil utilise plusieurs heuristiques pour déterminer si un plan d'exécution est mauvais. La première est de savoir si EXPLAIN signale que MySQL a l'intention d'utiliser l'index souhaité pour accéder aux lignes. Si MySQL choisit un index différent, l'outil considère la requête comme non sécurisée.

L'outil vérifie également la proportion de l'index que MySQL signale qu'il utilisera pour la requête. La sortie EXPLAIN l'indique dans la colonne key_len. L'outil mémorise le plus grand key_len vu, et ignore les blocs où MySQL signale qu'il utilisera un préfixe plus petit de l'index. Cette heuristique peut être comprise comme l'ignorance des blocs qui ont un plan d'exécution moins bon que d'autres blocs.

L'outil imprime un avertissement la première fois qu'un bloc est ignoré en raison d'un mauvais plan d'exécution dans chaque table. Les blocs suivants sont ignorés silencieusement, bien que vous puissiez voir le nombre de blocs ignorés dans la colonne SKIPPED dans la sortie de l'outil.

Cette option ajoute un travail de configuration à chaque table et à chaque bloc. Bien que le travail ne soit pas intrusif pour MySQL, il entraîne davantage d'allers-retours vers le serveur, ce qui consomme du temps. Rendre les blocs trop petits entraînera une augmentation relative de la surcharge. Il est donc recommandé de ne pas rendre les blocs trop petits, car l'outil pourrait prendre très longtemps à se terminer si vous le faites.

--chunk-time
type : float ; défaut : 0.5

Ajuster la taille du bloc dynamiquement pour que chaque requête de somme de contrôle prenne ce temps pour s'exécuter.

L'outil suit le taux de sommes de contrôle (lignes par seconde) pour toutes les tables et pour chaque table individuellement. Il utilise ces taux pour ajuster la taille du bloc après chaque requête de somme de contrôle, de sorte que la prochaine requête de somme de contrôle prenne ce montant de temps (en secondes) pour s'exécuter.

L'algorithme est le suivant : au début de chaque table, la taille du bloc est initialisée à partir de la moyenne globale des lignes par seconde depuis le début du travail de l'outil, ou de la valeur de "--chunk-size" si l'outil n'a pas encore commencé à travailler. Pour chaque bloc subséquent d'une table, l'outil ajuste la taille du bloc pour essayer de faire en sorte que les requêtes s'exécutent dans le temps désiré. Il maintient une moyenne mobile exponentiellement décroissante des requêtes par seconde, de sorte que si les performances du serveur changent en raison de modifications de la charge du serveur, l'outil s'adapte rapidement. Cela permet à l'outil d'obtenir des requêtes dont le temps d'exécution est prévisible pour chaque table, et pour le serveur dans son ensemble.

Si cette option est réglée à zéro, la taille du bloc ne s'ajuste pas automatiquement, donc les temps d'exécution des requêtes de sommes de contrôle varieront, mais les tailles des requêtes de sommes de contrôle ne varieront pas. Une autre façon de faire la même chose est de spécifier une valeur pour "--chunk-size" explicitement, au lieu de laisser la valeur par défaut.

--recursion-method
type: tableau; défaut: processlist,hosts

Méthode de récursion préférée pour découvrir les répliques. pt-table-checksum effectue plusieurs `"VÉRIFICATIONS DES RÉPLIQUES"` avant et pendant l'exécution.

Bien que les répliques ne soient pas obligatoires pour exécuter pt-table-checksum, l'outil ne peut pas détecter les différences sur les répliques qu'il ne peut pas découvrir. Par conséquent, un avertissement est affiché et le `"STATUT DE SORTIE"` est non nul si aucune réplique n'est trouvée et que la méthode n'est pas `"none"`. Si cela se produit, essayez une méthode de récursion différente, ou utilisez la méthode `"dsn"` pour spécifier les répliques à vérifier.

Les méthodes possibles sont :

MÉTHODE      UTILISE
===========  =================================================
processlist  SHOW PROCESSLIST
hosts        SHOW REPLICAS (SHOW SLAVE HOSTS avant MySQL 8.1)
cluster      SHOW STATUS LIKE 'wsrep\_incoming\_addresses'
dsn=DSN      DSNs à partir d'une table
none         Ne pas trouver de répliques

La méthode `"processlist"` est celle par défaut, car `"SHOW REPLICAS"` n'est pas fiable. Cependant, si le serveur utilise un port non standard (pas 3306), alors la méthode `"hosts"` devient la méthode par défaut car elle fonctionne mieux dans ce cas.

La méthode `"hosts"` nécessite que les répliques soient configurées avec `"report_host"`, `"report_port"`, etc.

La méthode `"cluster"` nécessite un cluster basé sur Galera 23.7.3 ou plus récent, comme les versions 5.5.29 et supérieures de Percona XtraDB Cluster. Cela découvrira automatiquement les nœuds d'un cluster en utilisant `"SHOW STATUS LIKE 'wsrep\_incoming\_addresses'"`. Vous pouvez combiner `"cluster"` avec `"processlist"` et `"hosts"` pour découvrir automatiquement les nœuds du cluster et les répliques, mais cette fonctionnalité est expérimentale.

La méthode `"dsn"` est spéciale : plutôt que de découvrir automatiquement les répliques, cette méthode spécifie une table avec les DSN des répliques. L'outil ne se connectera qu'à ces répliques. Cette méthode fonctionne mieux lorsque les répliques n'utilisent pas le même nom d'utilisateur ou mot de passe MySQL que la source, ou lorsque vous souhaitez empêcher l'outil de se connecter à certaines répliques. La méthode `"dsn"` est spécifiée comme suit : `"--recursion-method dsn=h=host,D=percona,t=dsns"`. Le DSN spécifié doit avoir des parties D et t, ou juste une partie t qualifiée par la base de données, qui spécifie la table DSN. La table DSN doit avoir la structure suivante :

CREATE TABLE `dsns` (
  `id` int(11) NOT NULL AUTO_INCREMENT,
  `parent_id` int(11) DEFAULT NULL,
  `dsn` varchar(255) NOT NULL,
  PRIMARY KEY (`id`)
);

Les DSN sont triés par `"id"`, mais `"id"` et `"parent_id"` sont autrement ignorés. La colonne `"dsn"` contient un DSN de réplique tel qu'il serait donné sur la ligne de commande, par exemple : `"h=replica_host,u=repl_user,p=repl_pass"`.

La méthode `"none"` fait en sorte que l'outil ignore toutes les répliques et les nœuds du cluster. Cette méthode n'est pas recommandée car elle désactive effectivement les `"VÉRIFICATIONS DES RÉPLIQUES"` et aucune différence ne peut être trouvée. Elle est cependant utile si vous avez seulement besoin d'écrire des sommes de contrôle sur la source ou sur un seul nœud du cluster. L'alternative plus sûre est `"--no-replicate-check"` : l'outil trouve les répliques et les nœuds du cluster, effectue les `"VÉRIFICATIONS DES RÉPLIQUES"`, mais ne vérifie pas les différences. Voir `"--[no]replicate-check"`.

--replicate
type: chaîne; défaut: percona.checksums

Écrit les résultats des sommes de contrôle dans cette table. La table de réplication doit avoir cette structure (MAGIC_create_replicate) :

CREATE TABLE checksums (
   db             CHAR(64)     NOT NULL,
   tbl            CHAR(64)     NOT NULL,
   chunk          INT          NOT NULL,
   chunk_time     FLOAT            NULL,
   chunk_index    VARCHAR(200)     NULL,
   lower_boundary TEXT             NULL,
   upper_boundary TEXT             NULL,
   this_crc       CHAR(40)     NOT NULL,
   this_cnt       INT          NOT NULL,
   source_crc     CHAR(40)         NULL,
   source_cnt     INT              NULL,
   ts             TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
   PRIMARY KEY (db, tbl, chunk),
   INDEX ts_db_tbl (ts, db, tbl)
) ENGINE=InnoDB DEFAULT CHARSET=utf8;

Note : le type de données de `lower_boundary` et `upper_boundary` peut être BLOB. Voir `"--binary-index"`.

Par défaut, `"--create-replicate-table"` est vrai, donc la base de données et la table spécifiées par cette option sont créées automatiquement si elles n'existent pas.

Assurez-vous de choisir un moteur de stockage approprié pour la table de réplication. Si vous vérifiez des tables InnoDB, et que vous utilisez MyISAM pour cette table, un interblocage brisera la réplication, b

parce que le mélange de tables transactionnelles et non transactionnelles dans les instructions de sommes de contrôle entraînera son écriture dans le binlog même s'il y a eu une erreur. Il sera ensuite rejoué sans interblocage sur les réplicas, et interrompra la réplication avec "erreur différente sur la source et le réplica." Ce n'est pas un problème avec pt-table-checksum; c'est un problème avec la réplication MySQL, et vous pouvez en savoir plus à ce sujet dans le manuel MySQL.

La table répliquée n'est jamais soumise à une somme de contrôle (l'outil l'ajoute automatiquement à "--ignore-tables").

--[no]replicate-check
par défaut : yes

Vérifie les différences de données sur les réplicas après avoir terminé chaque table. L'outil trouve les différences en exécutant une simple instruction SELECT sur tous les réplicas détectés. La requête compare les résultats de la somme de contrôle du réplica aux résultats de la somme de contrôle de la source. Elle signale les différences dans la colonne DIFFS de la sortie.

--replicate-check-only
Vérifie la cohérence des réplicas sans exécuter de requêtes de sommes de contrôle. Cette option est utilisée uniquement avec "--[no]replicate-check". Si elle est spécifiée, pt-table-checksum ne soumet aucune table à une somme de contrôle. Il vérifie les différences sur les réplicas trouvées par des sommes de contrôle précédentes, puis se termine. Cela peut être utile si vous exécutez pt-table-checksum en mode silencieux dans un cron job, par exemple, et que vous souhaitez plus tard un rapport sur les résultats du cron job, par exemple pour implémenter une vérification Nagios.
--replicate-check-retries
type : int ; par défaut : 1

Réessaie la comparaison de sommes de contrôle ce nombre de fois lorsqu'une différence est rencontrée. Ce n'est que lorsqu'une différence persiste après ce nombre de vérifications qu'elle est considérée comme valide. L'utilisation de cette option avec une valeur de 2 ou plus atténue les différences fallacieuses qui surviennent lors de l'utilisation de l'option "--resume".

--replicate-database
type : string

UTILISE uniquement cette base de données. Par défaut, pt-table-checksum exécute USE pour sélectionner la base de données qui contient la table sur laquelle il travaille actuellement. C'est un effort maximal pour éviter les problèmes avec les filtres de réplication tels que binlog_ignore_db et replicate_ignore_db. Cependant, les filtres de réplication peuvent créer une situation où il n'y a tout simplement pas de bonne façon de faire les choses. Certaines instructions pourraient ne pas être répliquées, et d'autres pourraient entraîner l'échec de la réplication. Dans de tels cas, vous pouvez utiliser cette option pour spécifier une base de données par défaut que pt-table-checksum sélectionne avec USE, et ne change jamais. Voir aussi "--[no]check-replication-filters".

--resume
Reprend le calcul des sommes de contrôle à partir du dernier bloc terminé (désactive "--[no]empty-replicate-table"). Si l'outil s'arrête avant d'avoir calculé la somme de contrôle de toutes les tables, cette option permet de reprendre le calcul à partir du dernier bloc de la dernière table terminée.
--retries
type : int ; par défaut : 2

Réessaie un bloc ce nombre de fois lorsqu'il y a une erreur non fatale. Les erreurs non fatales sont des problèmes tels qu'un délai d'attente de verrouillage ou l'interruption de la requête.

Combinez cette option avec "--resume" pour calculer la somme de contrôle d'autant de tables que possible dans un délai imparti, en reprenant là où l'outil s'est arrêté la prochaine fois qu'il sera exécuté.

VÉRIFICATIONS DES RÉPLICAS

Par défaut, pt-table-checksum tente de trouver et de se connecter à tous les réplicas connectés à l'hôte source. Ce processus automatisé est appelé "récursion de réplica" et est contrôlé par les options "--recursion-method" et "--recurse".

TABLE CHECKSUM

Le tableau de hachage de table pt-table-checksum exécute les contrôles suivants sur toutes les répliques :

1. "--[no]check-replication-filters"
pt-table-checksum vérifie les filtres de réplication sur toutes les répliques car ils peuvent compliquer ou casser le processus de hachage. Par défaut, l'outil se terminera si des filtres de réplication sont trouvés, mais ce contrôle peut être désactivé en spécifiant "--no-check-replication-filters".
2. Tableau "--replicate"
pt-table-checksum vérifie que le tableau "--replicate" existe sur toutes les répliques, sinon la somme de contrôle peut casser la réplication lorsque les mises à jour du tableau source sont répliquées vers une réplique qui n'a pas le tableau. Ce contrôle ne peut pas être désactivé, et l'outil attend indéfiniment jusqu'à ce que le tableau existe sur toutes les répliques, affichant des messages de "--progress" pendant l'attente.
3. Taille de bloc unique
Si un tableau peut être haché en un seul bloc sur la source, pt-table-checksum vérifiera que la taille du tableau sur toutes les répliques est inférieure à "--chunk-size" * "--chunk-size-limit". Ceci empêche un problème rare où le tableau sur la source est vide ou petit, mais sur une réplique, il est beaucoup plus grand. Dans ce cas, le hachage en bloc unique sur la source surchargerait la réplique.

Un autre problème rare survient lorsque la taille du tableau sur une réplique est proche de "--chunk-size" * "--chunk-size-limit". Dans de tels cas, le tableau est plus susceptible d'être ignoré même s'il est sûr de le hacher en un seul bloc. Cela se produit car les tailles de tableau sont des estimations. Lorsque ces estimations et "--chunk-size" * "--chunk-size-limit" sont presque égales, ce contrôle devient plus sensible à la marge d'erreur des estimations plutôt qu'à des différences significatives réelles dans les tailles de tableau. La spécification d'une valeur plus grande pour "--chunk-size-limit" aide à éviter ce problème.

Ce contrôle ne peut pas être désactivé.

4. Retard
Après chaque bloc, pt-table-checksum vérifie le retard sur toutes les répliques, ou uniquement sur la réplique spécifiée par "--check-replica-lag". Cela aide l'outil à ne pas surcharger les répliques avec des données de hachage. Il n'y a aucun moyen de désactiver ce contrôle, mais vous pouvez spécifier une seule réplique à vérifier avec "--check-replica-lag", et si cette réplique est la plus rapide, cela aidera à empêcher l'outil d'attendre trop longtemps que le retard de la réplique diminue.
5. Blocs de hachage
Lorsque pt-table-checksum a fini de hacher un tableau, il attend que le dernier bloc de hachage soit répliqué sur toutes les répliques afin de pouvoir effectuer "--[no]replicate-check". La désactivation de cette option en spécifiant --no-replicate-check désactive ce contrôle, mais désactive également le rapport immédiat des différences de hachage, nécessitant ainsi une deuxième exécution de l'outil avec "--replicate-check-only" pour trouver et afficher les différences de hachage.

PLUGIN

Le fichier spécifié par "--plugin" doit définir une classe (c'est-à-dire un paquet) appelée "pt_table_checksum_plugin" avec une sous-routine new(). L'outil créera une instance de cette classe et appellera toutes les fonctions d'accroche qu'elle définit. Aucune fonction d'accroche n'est requise, mais un plugin n'est pas très utile sans elles.

Ces fonctions d'accroche, dans cet ordre, sont appelées si elles sont définies :

init
before_replicate_check
after_replicate_check
get_replica_lag
before_checksum_table
after_checksum_table

Chaque fonction d'accroche reçoit des arguments différents. Pour savoir quels arguments sont passés à une fonction d'accroche, recherchez le nom de la fonction d'accroche dans le code source de l'outil, par exemple :

# --plugin hook
if ( $plugin && $plugin->can('init') ) {
   $plugin->init(
      replicas         => $replicas,
      replica_lag_cxns => $replica_lag_cxns,
      repl_table       => $repl_table,
   );
}

Le commentaire "# --plugin hook" précède chaque appel de fonction d'accroche.

Veuillez contacter Percona si vous avez des questions ou si vous avez besoin d'aide.
