NOM

pt-stalk - Collecte des données médico-légales sur MySQL lorsque des problèmes surviennent.

SYNTAXE

Utilisation : pt-stalk [OPTIONS]

pt-stalk attend qu'une condition de déclenchement se produise, puis collecte des données pour aider à diagnostiquer les problèmes. L'outil est conçu pour s'exécuter en tant que démon avec des privilèges root, afin que vous puissiez diagnostiquer des problèmes intermittents que vous ne pouvez pas observer directement. Vous pouvez également l'utiliser pour exécuter une commande personnalisée, ou pour collecter des données à la demande sans attendre que le déclencheur se produise.

RISQUES

Percona Toolkit est mature, éprouvé dans le monde réel et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Vérifier les « BOGUES » connus de l'outil
  • Tester l'outil sur un serveur non-production
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

DESCRIPTION

Parfois, un problème survient peu fréquemment et pendant une courte durée, ne vous laissant aucune chance de voir le système lorsqu'il se produit. Comment résoudre des problèmes MySQL intermittents lorsque vous ne pouvez pas les observer ? C'est pourquoi pt-stalk existe. En plus de l'utiliser lorsqu'il y a un problème connu sur vos serveurs, il est conseillé d'exécuter pt-stalk en permanence, même lorsque vous pensez que rien ne va mal. Vous apprécierez les données qu'il collecte lorsqu'un problème survient, car des problèmes tels que le blocage de MySQL ou les pics d'activité ne laissent généralement aucune preuve à utiliser pour l'analyse des causes profondes.

pt-stalk fait deux choses : il surveille un serveur MySQL et attend qu'une condition de déclenchement se produise, et il collecte des données de diagnostic lorsque ce déclenchement se produit. Pour éviter les faux positifs causés par des problèmes de courte durée, la condition de déclenchement doit être vraie au moins « --cycles » fois avant qu'un « --collect » ne soit déclenché.

Pour utiliser pt-stalk efficacement, vous devez définir un bon déclencheur. Un bon déclencheur est suffisamment sensible pour se déclencher de manière fiable lorsqu'un problème survient, afin de ne pas manquer une occasion de résoudre des problèmes. D'un autre côté, un bon déclencheur n'est pas sujet aux faux positifs, vous ne collectez donc pas d'informations lorsque le serveur fonctionne normalement.

Les déclencheurs les plus fiables pour MySQL ont tendance à être le nombre de connexions au serveur et le nombre de requêtes s'exécutant simultanément. Ceux-ci sont disponibles dans la commande SHOW GLOBAL STATUS sous les noms Threads_connected et Threads_running. Parfois, Threads_connected n'est pas un indicateur fiable de problème, mais Threads_running l'est généralement. Votre rôle, en tant qu'utilisateur de l'outil, est de définir une condition de déclenchement appropriée pour l'outil. Choisissez judicieusement, car la qualité de vos résultats dépendra du déclencheur que vous choisissez.

Vous définissez le déclencheur avec les options « --function », « --variable », « --threshold » et « --cycles ». Les valeurs par défaut pour ces options définissent un déclencheur raisonnable, mais vous devriez les ajuster ou les modifier pour répondre à votre système et à vos besoins particuliers.

Par défaut, l'outil pt-stalk surveille MySQL indéfiniment jusqu'à ce que le déclencheur se produise, puis il collecte des données de diagnostic pendant un certain temps, et se met en veille ensuite pour éviter de collecter des données de manière répétée si le déclencheur reste vrai. L'ordre général des opérations est :

while true; do
   if --variable from --function > --threshold; then
      cycles_true++
      if cycles_true >= --cycles; then
         --notify-by-email
         if --collect; then
            if --disk-bytes-free and --disk-pct-free ok; then
               (--collect for --run-time seconds) &
            fi
            rm files in --dest older than --retention-time
         fi
         iter++
         cycles_true=0
      fi
      if iter < --iterations; then
         sleep --sleep seconds
      else
         break
      fi
   else
      if iter < --iterations; then
         sleep --interval seconds
      else
         break
      fi
   fi
done
rm old --dest files older than --retention-time
if --collect process are still running; then
   wait up to --run-time * 3 seconds
   kill any remaining --collect processes
fi

Les données de diagnostic sont écrites dans des fichiers dont les noms commencent par un horodatage, de sorte que vous pouvez distinguer les échantillons les uns des autres au cas où l'outil collecterait des données plusieurs fois. L'outil pt-sift est conçu pour vous aider à parcourir et analyser les échantillons de données résultants.

Bien que cela semble simple, il existe en pratique un certain nombre de subtilités, comme la détection du moment où le disque commence à se remplir afin que l'outil ne provoque pas une pénurie d'espace disque sur le serveur. Cet outil gère ces types de problèmes potentiels, il est donc conseillé d'utiliser cet outil plutôt que d'écrire quelque chose à partir de zéro et de faire face à certains des dangers que cet outil est conçu pour éviter.

CONFIGURATION

Vous pouvez utiliser les fichiers de configuration standard de Percona Toolkit pour définir les options de ligne de commande.

Vous voudrez probablement exécuter l'outil en tant que démon et personnaliser au moins le « --threshold ». Voici un exemple de fichier de configuration pour le déclenchement lorsqu'il y a plus de 20 requêtes en cours d'exécution :

daemonize
threshold=20

Si vous n'exécutez pas l'outil en tant que root, vous devrez spécifier plusieurs options, telles que « --pid », « --log » et « --dest », sinon l'outil risque d'échouer au démarrage.

OPTIONS

--ask-pass
Demande un mot de passe lors de la connexion à MySQL.
--collect
par défaut : oui ; peut être nié : oui

Collecte des données de diagnostic lorsque le déclencheur se produit. Spécifiez « --no-collect » pour que l'outil surveille le système mais ne collecte pas de données.

Voir aussi « --stalk ».

--collect-gdb
Collecte des traces de pile GDB. Ceci est réalisé en s'attachant à MySQL et en imprimant les traces de pile de tous les threads. Cela bloquera le serveur pendant une certaine période, allant d'une seconde environ à beaucoup plus longtemps sur des systèmes très occupés avec beaucoup de mémoire et de nombreux threads dans le serveur. Pour cette raison, il est désactivé par défaut. Cependant, si vous essayez de diagnostiquer un blocage ou un gel du serveur, le blocage du serveur ne cause aucun dommage supplémentaire, et les traces de pile peuvent être vitales pour le diagnostic.

En plus de bloquer le serveur, il existe également un risque que le serveur plante ou fonctionne mal après que GDB s'en soit détaché.

--collect-oprofile
Collecte des données oprofile. Ceci est réalisé en démarrant une session oprofile, en la laissant s'exécuter pendant le temps de collecte, puis en arrêtant et en enregistrant les données de profil résultantes dans l'emplacement par défaut du système. Veuillez lire la documentation oprofile de votre système pour en savoir plus à ce sujet.
--collect-strace
Collecte des données strace. Ceci est réalisé en attachant strace au serveur, ce qui le rendra très lent jusqu'à ce que strace se détache. Les mêmes précautions s'appliquent que celles énumérées dans --collect-gdb. Vous ne devriez pas activer cette option avec --collect-gdb, car GDB et strace ne peuvent pas s'attacher simultanément au processus serveur.
--collect-tcpdump
Collecte des données tcpdump. Cette option amène tcpdump à capturer tout le trafic sur toutes les interfaces pour le port sur lequel MySQL écoute. Vous pouvez ensuite utiliser pt-query-digest pour décoder le protocole MySQL et en extraire un journal du trafic de requêtes.
--config
type : string

Lit cette liste de fichiers de configuration séparés par des virgules. S'il est spécifié, cela doit être la première option sur la ligne de commande.

--cycles
type : int ; par défaut : 5

Combien de fois « --variable » doit être supérieur à « --threshold » avant de déclencher « --collect ». Cela permet d'éviter les faux positifs et rend moins probable le déclenchement de la condition de déclenchement lorsque le problème se résout rapidement.

--daemonize
Démonise l'outil. Cela amène l'outil à se forker en arrière-plan et à enregistrer sa sortie comme spécifié dans --log.
--defaults-file
forme courte : -F ; type : string

Ne lire que les options mysql du fichier donné. Vous devez fournir un chemin d'accès absolu.

type : string ; par défaut : /var/lib/pt-stalk

Où enregistrer les données de diagnostic de « --collect ». Chaque

--disk-bytes-free
type : taille ; défaut : 100M

Ne pas "--collect" si le disque a moins d'espace libre que cette quantité. Cela empêche l'outil de remplir le disque avec des données de diagnostic.

Si le répertoire "--dest" contient un exemple de données précédemment capturé, l'outil mesurera sa taille et l'utilisera comme une estimation de la quantité de données susceptibles d'être collectées cette fois-ci également. Il sera alors encore plus pessimiste et refusera de collecter des données à moins que le disque n'ait suffisamment d'espace libre pour contenir l'exemple tout en conservant la quantité d'espace libre souhaitée. Par exemple, si vous souhaitez 100 Mo d'espace libre et que l'exemple de diagnostic précédent a consommé 100 Mo, l'outil ne collectera aucune donnée à moins que le disque n'ait 200 Mo d'espace libre.

Les suffixes valides pour la valeur de taille sont k, M, G et T.

--disk-pct-free
type : entier ; défaut : 5

Ne pas "--collect" si le disque a moins que ce pourcentage d'espace libre. Cela empêche l'outil de remplir le disque avec des données de diagnostic.

Cette option fonctionne de manière similaire à "--disk-bytes-free" mais spécifie une marge de sécurité en pourcentage au lieu d'une marge de sécurité en octets. L'outil respecte les deux options et ne collectera aucune donnée à moins que les deux marges ne soient satisfaites.

--function
type : chaîne ; défaut : status

Ce qu'il faut surveiller pour le déclencheur. La valeur par défaut surveille "SHOW GLOBAL STATUS", mais vous pouvez également surveiller "SHOW PROCESSLIST" et spécifier un fichier avec votre propre code personnalisé. Cette fonction fournit la valeur de "--variable", qui est ensuite comparée à "--threshold" pour voir si la condition du déclencheur est remplie. D'autres options peuvent être nécessaires également ; voir ci-dessous. Les valeurs possibles sont :

  • status

    Surveille "SHOW GLOBAL STATUS" pour le déclencheur. La valeur de "--variable" définit ensuite quel compteur de statut est le déclencheur.

  • processlist

    Surveille "SHOW FULL PROCESSLIST" pour le déclencheur. La valeur du déclencheur est le nombre de processus dont la colonne "--variable" correspond à l'option "--match". Par exemple, pour déclencher "--collect" lorsque plus de 10 processus sont dans l'état "statistics", spécifiez :

    --function processlist \
--variable State       \
--match statistics     \
--threshold 10

En outre, vous pouvez spécifier un fichier contenant votre fonction de déclenchement personnalisée, écrite en script shell Unix. Il peut s'agir d'un wrapper qui exécute ce que vous voulez. Si l'argument de "--function" est un fichier, il a la priorité sur les fonctions intégrées, donc s'il existe un fichier dans le répertoire de travail nommé "status" ou "processlist", l'outil utilisera ce fichier même si ce sont des valeurs intégrées valides.

Le fichier fonctionne en fournissant une fonction appelée "trg_plugin", et l'outil source simplement le fichier et exécute la fonction. Par exemple, le fichier pourrait contenir :

trg_plugin() {
   mysql $EXT_ARGV -e "SHOW ENGINE INNODB STATUS" \
     | grep -c "has waited at"
}

Ce fragment comptera le nombre d'attentes de mutex à l'intérieur d'InnoDB. Il illustre le principe général : la fonction doit générer un nombre, qui est ensuite comparé à "--threshold" comme d'habitude. La variable $EXT_ARGV contient les options MySQL mentionnées dans le "SYNOPSIS" ci-dessus.

Le fichier ne doit pas modifier les variables globales existantes de l'outil. Préfixez toutes les variables globales spécifiques au fichier avec "PLUGIN_" ou rendez-les locales.

--help
Afficher l'aide et quitter.
--host
forme courte : -h ; type : chaîne

Hôte auquel se connecter.

--interval
type : entier ; défaut : 1

À quelle fréquence vérifier si le déclencheur est vrai, en secondes.

--iterations
type : entier

Combien de fois "--collect" les données de diagnostic. Par défaut, l'outil s'exécute indéfiniment et collecte des données à chaque fois que le déclencheur se produit. Spécifiez "--iterations" pour collecter des données un nombre limité de fois. Cette option est également utile avec "--no-stalk" pour collecter des données une seule fois et quitter, par exemple.

--log
type : chaîne ; défaut : /var/log/pt-stalk.log

Afficher toute la sortie dans ce fichier lorsqu'il est démonisé.

--match
type : chaîne

Le modèle à utiliser lors de la surveillance de SHOW PROCESSLIST. Voir "--function" pour plus de détails.

--notify-by-email
type : chaîne

Envoyer un e-mail à ces adresses pour chaque "--collect".

--password
forme courte : -p ; type : chaîne

Mot de passe à utiliser lors de la connexion. Si le mot de passe contient des virgules, elles doivent être échappées avec une barre oblique inverse : "exam\,ple"

--pid
type : chaîne ; défaut : /var/run/pt-stalk.pid

Créer le fichier PID spécifié. L'outil ne démarrera pas si le fichier PID existe déjà et si le PID qu'il contient est différent du PID actuel. Cependant, si le fichier PID existe et que le PID qu'il contient n'est plus en cours d'exécution, l'outil écrasera le fichier PID avec le PID actuel. Le fichier PID est supprimé automatiquement lorsque l'outil se termine.

--plugin
type : chaîne

Charger un plugin pour s'intégrer à l'outil et étendre ses fonctionnalités. Le fichier spécifié n'a pas besoin d'être exécutable, ni sa première ligne d'être une ligne shebang. Il doit seulement définir une ou plusieurs des fonctions Bash suivantes :

before_stalk
Appelée avant le stalking.
before_collect
Appelée lorsque le déclencheur se produit, avant d'exécuter des sous-processus "--collect" en arrière-plan.
after_collect
Appelée après l'exécution d'un processus de collecte. Le PID du processus de collecte est passé comme premier argument. Ce hook est appelé avant "after_collect_sleep".
after_collect_sleep
Appelée après une pause de "--sleep" secondes pour que le processus de collecte se termine. Ce hook est appelé après "after_collect".
after_interval_sleep
Appelée après une pause de "--interval" secondes après chaque vérification du déclencheur.
after_stalk
Appelée après le stalking. Comme pt-stalk effectue un stalking indéfiniment par défaut, ce hook n'est appelé que si "--iterations" est spécifié.

Par exemple, un plugin très simple qui touche un fichier lorsque "--collect" est déclenché :

before_collect() {
   touch /tmp/foo
}

Comme le plugin est entièrement sourcé (importé) dans l'espace de noms de l'outil, faites attention à ne pas définir d'autres fonctions ou variables globales qui existent déjà dans l'outil. Vous devriez préfixer toutes les fonctions et variables globales spécifiques au plugin avec "plugin_" ou "PLUGIN_".

Les plugins ont accès à toutes les options de ligne de commande, mais ils ne doivent pas les modifier. Chaque option est une variable globale comme $OPT_DEST qui correspond à "--dest". Par conséquent, la variable globale pour chaque option de ligne de commande est "OPT_" plus le nom de l'option en majuscules avec les tirets remplacés par des underscores.

Les plugins peuvent arrêter l'outil en définissant la variable globale "OKTORUN" à 1. Dans ce cas, la variable globale "EXIT_REASON" doit également être définie pour indiquer pourquoi l'outil a été arrêté.

Les auteurs de plugins doivent garder à l'esprit que le préfixe de destination de fichier actuellement utilisé doit être accessible via la variable $prefix, plutôt que $OPT_PREFIX.

--mysql-only
Déclencher uniquement les captures liées à MySQL, en ignorant toutes les autres. La seule valeur non liée à MySQL collectée est l'espace disque, car elle est nécessaire pour calculer l'espace disque libre disponible pour écrire les fichiers de résultats. Cette option est utile pour les instances RDS.
--port
forme courte : -P ; type : entier

Numéro de port à utiliser pour la connexion.

--prefix
type : chaîne

Le préfixe du nom de fichier pour les échantillons de diagnostic. Par défaut, tous les fichiers créés par la même instance "--collect" ont un préfixe d'horodatage basé sur l'heure locale actuelle, comme "2011_12_06_14_02_02", ce qui correspond au 6 décembre 2011 à 14h02m02s.

--retention-count
type : entier ; défaut : 0

Conserver les données des N dernières exécutions. Si N > 0, le programme conservera les données des N dernières exécutions et supprimera les anciennes données.

--retention-size
type : entier ; défaut : 0

Conserver jusqu'à --retention-size Mo de données. Il conservera au moins 1 exécution même si la taille est supérieure à celle spécifiée dans ce paramètre.

--retention-time
type : entier ; défaut : 30

Nombre de jours pendant lesquels conserver les échantillons collectés. Tout échantillon qui

plus âgées seront purgées.

--run-time
type : int ; défaut : 30

Durée pendant laquelle collecter des données de diagnostic lorsque le déclencheur se produit. La valeur est en secondes et ne doit pas être supérieure à « --sleep ». Il n'est généralement pas nécessaire de modifier cette valeur ; si les 30 secondes par défaut ne permettent pas de collecter suffisamment de données, une durée plus longue est peu susceptible d'aider car le système ou le serveur MySQL est probablement trop occupé pour répondre. En fait, dans de nombreux cas, une période de collecte plus courte est appropriée.

Cette valeur est utilisée deux autres fois. Après la collecte, le sous-processus de collecte attendra encore « --run-time » secondes pour que ses commandes se terminent. Certaines commandes peuvent prendre du temps si le système fonctionne très lentement (ce qui est probablement le cas étant donné qu'une collecte a été déclenchée). Comme les fichiers vides sont supprimés, le temps d'attente supplémentaire donne aux commandes le temps de se terminer et d'écrire leurs données. La valeur est potentiellement réutilisée juste avant que l'outil ne se termine pour attendre à nouveau que les sous-processus de collecte se terminent. Dans la plupart des cas, cela ne se produira pas en raison du temps d'attente supplémentaire mentionné ci-dessus. Si cela se produit, l'outil enregistrera « En attente de N secondes maximum pour que les sous-processus se terminent... » où N est trois fois « --run-time ». Dans les deux cas, après l'attente, l'outil tue tous ses sous-processus.

--sleep
type : int ; défaut : 300

Durée de la mise en veille après « --collect ». Cela empêche l'outil de se déclencher en continu, ce qui pourrait poser un problème si le processus de collecte est intrusif. Cela évite également de remplir le disque ou de collecter trop de données pour une analyse raisonnable.

--sleep-collect
type : int ; défaut : 1

Durée de la mise en veille entre les cycles de collecte. Ceci est utile avec « --no-stalk » pour des collectes longues. Par exemple, pour collecter des données toutes les minutes pendant une heure, spécifiez : « --no-stalk --run-time 3600 --sleep-collect 60 ».

--socket
forme courte : -S ; type : string

Fichier socket à utiliser pour la connexion.

--stalk
défaut : oui ; négable : oui

Surveille le serveur et attend que le déclencheur se produise. Spécifiez « --no-stalk » pour collecter immédiatement des données de diagnostic, c'est-à-dire sans attendre que le déclencheur se produise. Vous voudrez probablement également spécifier des valeurs pour « --interval », « --iterations » et « --sleep ». Par exemple, pour collecter immédiatement des données pendant 1 minute puis quitter, spécifiez :

--no-stalk --run-time 60 --iterations 1

« --cycles », « --daemonize », « --log » et « --pid » n'ont aucun effet avec « --no-stalk ». Les options de sauvegarde, telles que « --disk-bytes-free » et « --disk-pct-free », sont toujours respectées.

Voir aussi « --collect ».

--system-only
Déclenche uniquement les captures liées au système d'exploitation, en ignorant toutes les autres.
--threshold
type : int ; défaut : 25

La valeur maximale acceptable pour « --variable ». « --collect » est déclenché lorsque la valeur de « --variable » est supérieure à « --threshold » pendant « --cycles » fois. Actuellement, il n'y a aucun moyen de définir un seuil inférieur pour vérifier une valeur de « --variable » trop basse.

Voir aussi « --function ».

--user
forme courte : -u ; type : string

Utilisateur pour la connexion si ce n'est pas l'utilisateur actuel.

--variable
type : string ; défaut : Threads_running

La variable à comparer à « --threshold ». Voir aussi « --function ».

--verbose
type : int ; défaut : 2

Affiche plus ou moins d'informations pendant l'exécution. Comme l'outil est conçu pour être un démon de longue durée, le niveau de verbosité par défaut n'affiche que les informations les plus importantes. Si vous exécutez l'outil de manière interactive, vous pourriez vouloir utiliser un niveau de verbosité plus élevé.

ENVIRONNEMENT

Cet outil ne nécessite aucune variable d'environnement pour la configuration, bien qu'il puisse être influencé pour fonctionner différemment par plusieurs variables. Gardez à l'esprit qu'il s'agit de paramètres experts, et qu'ils ne doivent pas être utilisés dans la plupart des cas.

Plus précisément, les variables qui peuvent être définies sont :

CMD_GDB
CMD_IOSTAT
CMD_MPSTAT
CMD_MYSQL
CMD_MYSQLADMIN
CMD_OPCONTROL
CMD_OPREPORT
CMD_PMAP
CMD_STRACE
CMD_SYSCTL
CMD_TCPDUMP
CMD_VMSTAT

Par exemple, pendant la collecte, iostat est appelé avec un argument -dx, mais comme vous avez une partition NFS, vous avez également besoin du drapeau -n. Au lieu de modifier la source, vous pouvez appeler pt-stalk comme suit :

CMD_IOSTAT="iostat -n" pt-stalk ...

ce qui fera exactement ce dont vous avez besoin. Combiné avec les hooks de plugin, cela vous donne un contrôle précis sur ce que fait l'outil.

Il est possible d'activer le mode « debug » dans mysqladmin en spécifiant :

"CMD_MYSQLADMIN='mysqladmin debug' pt-stalk params ..."

EXIGENCES DU SYSTÈME

Cet outil nécessite Bash v3 ou plus récent. Certaines options nécessitent d'autres programmes :

« --collect-gdb » nécessite « gdb »
« --collect-oprofile » nécessite « opcontrol » et « opreport »
« --collect-strace » nécessite « strace »
« --collect-tcpdump » nécessite « tcpdump »

BOGUES

Pour une liste des bogues connus, voir https://jira.percona.com/projects/PT/issues.

Veuillez signaler les bogues à https://jira.percona.com/projects/PT. Incluez les informations suivantes dans votre rapport de bogue :

  • Commande complète utilisée pour exécuter l'outil
  • Version de l'outil « --version »
  • Version MySQL de tous les serveurs concernés
  • Sortie de l'outil, y compris STDERR
  • Fichiers d'entrée (journaux/sauvegardes/fichiers de configuration, etc.)

pt-stalk(1p) — Documentation Linux et UNIX

NAME

pt-stalk - Collecte des informations sur les serveurs MySQL ou MariaDB lorsque certains événements se produisent.

SYNOPSIS

pt-stalk [options] [--execute <commande>]

RISKS

Cet outil est destiné aux utilisateurs avancés. Une mauvaise utilisation peut entraîner la perte de données ou rendre les serveurs indisponibles.

DESCRIPTION

pt-stalk est un outil de diagnostic qui collecte des informations sur les serveurs MySQL ou MariaDB lorsqu'un événement spécifié se produit. Il est particulièrement utile pour capturer l'état d'un serveur lors de problèmes intermittents ou difficiles à reproduire.

Il peut surveiller divers événements, tels que :

  • Erreurs dans les logs MySQL/MariaDB.
  • Requêtes lentes (définies par un seuil).
  • Utilisation élevée du CPU ou de la mémoire sur le serveur.
  • Événements déclenchés manuellement.

Lorsqu'un événement est détecté, pt-stalk peut exécuter une série de commandes pour collecter des informations détaillées, notamment :

  • SHOW PROCESSLIST
  • SHOW GLOBAL STATUS
  • SHOW GLOBAL VARIABLES
  • SHOW ENGINE INNODB STATUS
  • mysqldumpslow
  • Informations sur le système d'exploitation et les processus.
  • Etc.

Les données collectées sont enregistrées dans des fichiers, généralement dans un répertoire spécifié par l'utilisateur, pour une analyse ultérieure.

CONFIGURING

pt-stalk peut être configuré via des options de ligne de commande ou un fichier de configuration.

Les principales options de configuration incluent :

--config
Spécifie le chemin vers un fichier de configuration.
--defaults-file
Spécifie le chemin vers un fichier de configuration MySQL/MariaDB.
--host, --port, --user, --password
Informations de connexion au serveur MySQL/MariaDB.
--interval
L'intervalle (en secondes) entre les vérifications.
--run-on-master
Exécute les commandes sur le maître (lorsque le serveur est configuré en réplication).
--check-server-id
Vérifie l'ID du serveur avant de collecter des données.

OPTIONS

pt-stalk offre une large gamme d'options pour personnaliser son comportement. Les options les plus courantes incluent :

--query-criteria
Définit les critères pour déclencher la collecte de données basée sur les requêtes lentes. Par exemple : --query-criteria 'time=5' pour capturer les requêtes prenant plus de 5 secondes.
--error-log
Spécifie le chemin vers le fichier log d'erreurs MySQL/MariaDB à surveiller.
--collect
Définit les commandes à exécuter lorsque l'événement se produit. Les commandes prédéfinies sont disponibles (par exemple, processlist, globalstatus).
--collect-execute
Permet d'exécuter une commande personnalisée.
--outdir
Spécifie le répertoire où les fichiers de sortie seront enregistrés.
--filesize
Définit la taille maximale des fichiers de sortie.
--watches
Spécifie un fichier contenant des événements personnalisés à surveiller.
--daemonize
Exécute pt-stalk en arrière-plan comme un démon.
--pidfile
Spécifie le fichier PID pour le processus démonisé.
--log
Spécifie un fichier log pour l'activité de pt-stalk.

Voir la documentation complète de pt-stalk pour la liste exhaustive des options.

ENVIRONMENT

L'outil peut utiliser des variables d'environnement pour certaines configurations, telles que les informations de connexion au serveur.

SYSTEM REQUIREMENTS

Perl, et les modules Perl nécessaires (listés dans la documentation de pt-stalk).
