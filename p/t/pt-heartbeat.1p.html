NOM

pt-heartbeat - Surveille le retard de réplication MySQL.

SYNOPIS

Usage : pt-heartbeat [OPTIONS] [DSN] --update|--monitor|--check|--stop

pt-heartbeat mesure le retard de réplication sur un serveur MySQL ou PostgreSQL. Vous pouvez l'utiliser pour mettre à jour une source de réplication ou surveiller une réplique. Si possible, les options de connexion MySQL sont lues depuis votre fichier .my.cnf.

Démarre un processus daemonisé pour mettre à jour la table test.heartbeat sur la source de réplication :

pt-heartbeat -D test --update -h source-server --daemonize

Surveille le retard de réplication sur la réplique :

pt-heartbeat -D test --monitor -h replica-server
pt-heartbeat -D test --monitor -h replica-server --dbi-driver Pg

Vérifie une fois le retard de la réplique et quitte (en utilisant le DSN optionnel pour spécifier l'hôte de la réplique) :

pt-heartbeat -D test --check h=replica-server

RISQUES

Percona Toolkit est mature, éprouvé sur le terrain et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Examiner les "BUGS" connus de l'outil
  • Tester l'outil sur un serveur non productif
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

DESCRIPTION

pt-heartbeat est un système de surveillance du retard de réplication MySQL et PostgreSQL en deux parties qui mesure le retard en examinant les données répliquées réelles. Cela évite de dépendre du mécanisme de réplication lui-même, qui est peu fiable. (Par exemple, "SHOW REPLICA STATUS" sur MySQL).

La première partie est une instance "--update" de pt-heartbeat qui se connecte à une source de réplication et met à jour un horodatage ("enregistrement de pulsation") toutes les "--interval" secondes. Comme la table heartbeat peut contenir des enregistrements de plusieurs sources de réplication (voir "HIÉRARCHIE MULTI-RÉPLICA"), l'ID du serveur (@@server_id) est utilisé pour identifier les enregistrements.

La seconde partie est une instance "--monitor" ou "--check" de pt-heartbeat qui se connecte à une réplique, examine l'enregistrement de pulsation répliqué de sa source immédiate ou du "--source-server-id" spécifié, et calcule la différence par rapport à l'heure système actuelle. Si la réplication entre la réplique et la source est retardée ou interrompue, la différence calculée sera supérieure à zéro et potentiellement croissante si "--monitor" est spécifié.

Vous devez soit créer manuellement la table heartbeat sur la source de réplication, soit utiliser "--create-table". Voir "--create-table" pour la structure correcte de la table heartbeat. Le moteur de stockage "MEMORY" est suggéré, mais pas obligatoire bien sûr, pour MySQL.

La table heartbeat doit contenir une ligne de pulsation. Par défaut, une ligne de pulsation est insérée si elle n'existe pas. Cette fonctionnalité peut être désactivée avec l'option "--[no]insert-heartbeat-row" au cas où l'utilisateur de la base de données n'a pas les privilèges INSERT.

pt-heartbeat ne dépend que de l'enregistrement de pulsation étant répliqué sur la réplique, il fonctionne donc indépendamment du mécanisme de réplication (réplication intégrée, un système tel que Continuent Tungsten, etc.). Il fonctionne à n'importe quelle profondeur dans la hiérarchie de réplication ; par exemple, il rapportera de manière fiable à quel point une réplique est en retard par rapport à la source de sa source de sa source. Et si la réplication est arrêtée, il continuera à fonctionner et à rapporter (avec précision !) que la réplique prend de plus en plus de retard par rapport à la source.

pt-heartbeat a une résolution maximale de 0,01 seconde. Les horloges des serveurs source et réplique doivent être étroitement synchronisées via NTP. Par défaut, les vérifications "--update" se produisent au début de la seconde (par exemple, 00:01) et les vérifications "--monitor" se produisent à mi-chemin entre les secondes (par exemple, 00:01.5). Tant que les horloges des serveurs sont étroitement synchronisées et que les événements de réplication se propagent en moins d'une demi-seconde, pt-heartbeat rapportera zéro seconde de retard.

pt-heartbeat tentera de se reconnecter en cas d'erreur de connexion, mais ne réessayera pas s'il ne parvient pas à obtenir une connexion lors du démarrage.

L'option "--dbi-driver" vous permet également de surveiller PostgreSQL avec pt-heartbeat. Il est rapporté qu'il fonctionne bien avec la réplication Slony-1.

HIÉRARCHIE MULTI-RÉPLICA

Si la hiérarchie de réplication comporte plusieurs répliques qui sont sources d'autres répliques, comme "source -> replica1 -> replica2", des instances "--update" peuvent être exécutées sur les répliques ainsi que sur la source. La table heartbeat par défaut (voir "--create-table") est indexée sur la colonne "server_id", de sorte que chaque serveur mettra à jour la ligne où "server_id=@@server_id".

Pour "--monitor" et "--check", si "--source-server-id" n'est pas spécifié, l'outil essaie de découvrir et d'utiliser la source immédiate de la réplique. Si cela échoue, ou si vous souhaitez surveiller le retard d'une autre source, vous pouvez spécifier le "--source-server-id" à utiliser.

Par exemple, si la hiérarchie de réplication est "source -> replica1 -> replica2" avec les IDs de serveur correspondants 1, 2 et 3, vous pouvez :

pt-heartbeat --daemonize -D test --update -h source
pt-heartbeat --daemonize -D test --update -h replica1

Puis vérifier (ou surveiller) le retard de réplication de la source à replica2 :

pt-heartbeat -D test --source-server-id 1 --check replica2

Ou vérifier le retard de réplication de replica1 à replica2 :

pt-heartbeat -D test --source-server-id 2 --check replica2

L'arrêt de l'instance "--update" sur replica1 n'affectera pas l'instance sur la source.

STATUT DU LOG BINAIRE (MAÎTRE) ET DE LA RÉPLICA

La table heartbeat par défaut (voir "--create-table") contient des colonnes pour enregistrer les informations de "SHOW BINARY LOG STATUS" ("SHOW MASTER STATUS" avant MySQL 8.4) et "SHOW REPLICA STATUS". Ces colonnes sont optionnelles. Si l'une d'elles est présente, les informations correspondantes seront enregistrées.

Percona XtraDB Cluster

Bien que pt-heartbeat doive fonctionner avec toutes les versions prises en charge de Percona XtraDB Cluster (PXC), nous recommandons d'utiliser les versions 5.5.28-23.7 et ultérieures.

Si vous configurez des instances de pulsation entre les nœuds du cluster, gardez à l'esprit que, puisque la vitesse du cluster est déterminée par son nœud le plus lent, pt-heartbeat ne rapportera pas la vitesse du cluster lui-même, mais seulement la vitesse à laquelle les événements sont répliqués d'un nœud à un autre.

Vous devez spécifier "--source-server-id" pour les instances "--monitor" et "--check".

OPTIONS

Les options suivantes sont disponibles pour l'outil "pt-heartbeat".

--ask-pass
Demander le mot de passe.
--[no]check-replication-filters
type: bool; default: yes

Vérifier si les filtres de réplication sont configurés de manière incorrecte.

Si vous spécifiez cette option, "pt-heartbeat" vérifie que les filtres de réplication (par exemple, "replicate-do-db") ne sont pas configurés de manière incorrecte pour le serveur de la source (celui qui écrit dans la table heartbeat). Par défaut, "pt-heartbeat" suppose que la source ne fait rien d'autre que d'écrire des données dans la table heartbeat. Si la source est configurée pour répliquer seulement certaines bases de données, cela pourrait avoir pour effet de ne pas répliquer la table heartbeat, auquel cas "pt-heartbeat" ne peut pas déterminer quand elle est mise à jour.

Si vous ne voulez pas que cette vérification soit effectuée, vous pouvez la désactiver en utilisant "--no-check-replication-filters".

--charset
short form: -A; type: string

Utiliser la valeur spécifiée comme jeu de caractères par défaut.

--config
type: string

Lire les options de configuration à partir de ce fichier. Notez que les options de ligne de commande écrasent les options du fichier de configuration.

--create-table
Crée la table heartbeat si elle n'existe pas.

Par défaut, la table heartbeat est créée avec les colonnes suivantes :

  `ts`      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `server_id` INT UNSIGNED NOT NULL PRIMARY KEY

Si la table est créée avec succès, cela est rapporté et l'outil quitte. La table est alors créée avec les permissions appropriées pour le script, mais si le script est exécuté avec des privilèges trop faibles pour créer une table, il peut échouer. Vous pouvez spécifier les colonnes dans un fichier de configuration ou via la ligne de commande, mais les colonnes spécifiées sont fixes. Si vous souhaitez spécifier vos propres colonnes, vous devrez créer la table manuellement.

Cette option est utile si vous n'êtes pas sûr que la table existe et que vous n'avez pas les privilèges nécessaires pour la créer vous-même. Elle doit être utilisée avec le paramètre "--update".

--database
short form: -D; type: string

Base de données à utiliser.

--debug
type: boolean

Activer la sortie de débogage détaillée.

--defaults-file
short form: -F; type: string

Ne lire les options par défaut que dans le fichier spécifié.

--interval
short form: -i; type: time; default: 1

Durée, en secondes, entre chaque mise à jour de la table heartbeat.

--master-info-repository
type: string; default: TABLE

Où trouver les informations du master. Les valeurs possibles sont TABLE et FILE.

--master-info-file
type: string; default: master.info

Le fichier où le nom du master et sa position sont stockés. Utilisé uniquement si "--master-info-repository" est défini sur FILE.

--master-info-table
type: string; default: MASTER_INFO

La table où le nom du master et sa position sont stockés. Utilisé uniquement si "--master-info-repository" est défini sur TABLE.

--master-user
type: string

Utilisateur pour se connecter au master.

--master-password
type: string

Mot de passe pour se connecter au master.

--monitor
Surveiller la réplication.

Quand cette option est spécifiée, "pt-heartbeat" vérifie la réplication en comparant l'heure de la table heartbeat sur la source avec l'heure actuelle. Le délai de réplication est calculé et affiché. Les valeurs spécifiées avec l'option "--interval" sont utilisées pour déterminer la fréquence des vérifications.

L'outil est conçu pour être utilisé avec une seule instance qui gère la table heartbeat sur le master, et une ou plusieurs autres instances qui surveillent la réplication sur les esclaves. Par défaut, les esclaves sont recherchés en utilisant les méthodes de découverte standard de "MySQL::Replication", qui incluent la vérification de "SHOW SLAVE STATUS" sur la connexion fournie, puis la recherche de réplicas à l'aide de la méthode préférée.

Une méthode préférée peut être spécifiée et elle sera essayée en premier. Si aucune réplique n'est trouvée, les autres méthodes seront essayées.

--replace
Utiliser "REPLACE" au lieu de "UPDATE" pour --update.

Lorsque vous exécutez en mode "--update", utilisez "REPLACE" au lieu de "UPDATE" pour définir l'horodatage de la table heartbeat. L'instruction "REPLACE" est une extension MySQL au SQL. Cette option est utile lorsque vous ne savez pas si la table contient des lignes ou non. Elle doit être utilisée en conjonction avec --update.

type: time

Temps d'exécution avant de quitter.

--sentinel
type: string; default: /tmp/pt-heartbeat-sentinel

Quitter si ce fichier existe.

--slave-user
type: string

Cette option est obsolète et sera supprimée dans les futures versions. Utilisez "--replica-user" à la place.

--slave-password
type: string

Cette option est obsolète et sera supprimée dans les futures versions. Utilisez "--replica-password" à la place.

--replica-user
type: string

Définit l'utilisateur à utiliser pour se connecter aux réplicas. Ce paramètre vous permet d'avoir un utilisateur différent avec moins de privilèges sur les réplicas, mais cet utilisateur doit exister sur tous les réplicas.

--replica-password
type: string

Définit le mot de passe à utiliser pour se connecter aux réplicas. Il peut être utilisé avec --replica-user et le mot de passe de l'utilisateur doit être le même sur tous les réplicas.

--set-vars
type: Array

Définit les variables MySQL dans cette liste de paires "variable=valeur" séparées par des virgules.

Par défaut, l'outil définit :

wait_timeout=10000

Les variables spécifiées sur la ligne de commande remplacent ces valeurs par défaut. Par exemple, spécifier "--set-vars wait_timeout=500" remplace la valeur par défaut de 10000.

L'outil affiche un avertissement et continue si une variable ne peut pas être définie.

--skew
type: float; default: 0.5

Temps de délai des vérifications.

Par défaut, les vérifications sont retardées d'une demi-seconde. Comme la mise à jour se produit dès que possible après le début de la seconde sur la source de réplication, cela permet une demi-seconde de délai de réplication avant de signaler que le réplica a un retard d'une seconde par rapport à la source. Si vos horloges ne sont pas parfaitement précises ou s'il y a une autre raison pour laquelle vous souhaitez retarder le réplica plus ou moins, vous pouvez ajuster cette valeur. Essayez de définir la variable d'environnement "PTDEBUG" pour voir l'effet que cela produit.

--socket
short form: -S; type: string

Fichier socket à utiliser pour la connexion.

--stop
Arrêter les instances en cours d'exécution en créant le fichier sentinel.

Cela devrait avoir pour effet d'arrêter toutes les instances en cours d'exécution qui surveillent le même fichier sentinel. Si aucune des options "--update", "--monitor" ou "--check" n'est spécifiée, "pt-heartbeat" quittera après avoir créé le fichier. Si l'une de ces options est spécifiée, "pt-heartbeat" attendra l'intervalle donné par "--interval", puis supprimera le fichier et continuera à fonctionner.

Vous trouverez cela utile pour arrêter gracieusement les tâches cron si nécessaire, ou pour remplacer une instance en cours d'exécution par une autre. Par exemple, si vous souhaitez arrêter et redémarrer "pt-heartbeat" toutes les heures (juste pour vous assurer qu'il est redémarré chaque heure, en cas de panne de serveur ou d'un autre problème), vous pouvez utiliser une ligne "crontab" comme ceci :

0 * * * * pt-heartbeat --update -D test --stop \
  --sentinel /tmp/pt-heartbeat-hourly

Le "--sentinel" non par défaut s'assurera que le job "cron" horaire arrête uniquement les instances précédemment démarrées avec les mêmes options (c'est-à-dire, provenant du même job "cron").

Voir aussi "--sentinel".

--table
type: string; default: heartbeat

La table à utiliser pour le heartbeat.

Ne spécifiez pas database.table ; utilisez "--database" pour spécifier la base de données.

Voir "--create-table".

--update
Mettre à jour le heartbeat d'une source de réplication.
--user
short form: -u; type: string

Utilisateur pour la connexion si ce n'est pas l'utilisateur actuel.

--utc
Ignorer les fuseaux horaires système et utiliser uniquement l'UTC. Par défaut, pt-heartbeat ne vérifie ni n'ajuste les différents fuseaux horaires système ou MySQL, ce qui peut amener l'outil à calculer le décalage de manière incorrecte. Spécifier cette option est une bonne idée car elle garantit que l'outil fonctionne correctement indépendamment des fuseaux horaires.

Si elle est utilisée, cette option doit être utilisée pour toutes les instances de pt-heartbeat : "--update", "--monitor", "--check", etc. Vous devriez probablement définir l'option dans un fichier "--config". Mélanger cette option avec des instances de pt-heartbeat qui n'utilisent pas cette option entraînera des lectures de décalage faussement positives dues à des fuseaux horaires différents (sauf si tous vos systèmes sont configurés pour utiliser l'UTC, auquel cas cette option n'est pas nécessaire).

--version
Afficher la version et quitter.
--[no]version-check
default: yes

Vérifier la dernière version de Percona Toolkit, MySQL et d'autres programmes.

Il s'agit d'une fonctionnalité standard de "vérifier les mises à jour automatiquement", avec deux fonctionnalités supplémentaires. Premièrement, l'outil vérifie sa propre version ainsi que les versions des logiciels suivants : système d'exploitation, Percona Monitoring and Management (PMM), MySQL, Perl, pilote MySQL pour Perl (DBD::mysql) et Percona Toolkit. Deuxièmement, il vérifie et avertit des versions présentant des problèmes connus. Par exemple, MySQL 5.5.25 avait un bug critique et a été re-publié sous le nom 5.5.25a.

Une connexion sécurisée au serveur de base de données de vérification de version de Percona est établie pour effectuer ces vérifications. Chaque requête est enregistrée par le serveur, y compris les numéros de version des logiciels et l'identifiant unique du système vérifié. L'identifiant est généré par le script d'installation de Percona Toolkit ou lorsque l'appel à la base de données de vérification de version est effectué pour la première fois.

Toutes les mises à jour ou tous les problèmes connus sont imprimés sur STDOUT avant la sortie normale de l'outil. Cette fonctionnalité ne devrait jamais interférer avec le fonctionnement normal de l'outil.

Pour plus d'informations, visitez https://www.percona.com/doc/percona-toolkit/LATEST/version-check.html.

OPTIONS DSN

Ces options DSN sont utilisées pour créer un DSN. Chaque option est donnée sous la forme "option=valeur". Les options sont sensibles à la casse, donc P et p ne sont pas la même option. Il ne peut y avoir d'espace avant ou après le "=" et si la valeur contient un espace, elle doit être mise entre guillemets. Les options DSN sont séparées par des virgules. Voir le manuel de percona-toolkit pour tous les détails.

  • A

    dsn: charset; copy: yes

    Jeu de caractères par défaut.

  • D

    dsn: database; copy: yes

    Base de données par défaut.

  • F

    dsn: mysql_read_default_file; copy: yes

    Lire uniquement les options par défaut dans le fichier spécifié.

  • h

    dsn: host; copy: yes

    Se connecter à l'hôte.

  • p

    dsn: password; copy: yes

    Mot de passe à utiliser lors de la connexion. Si le mot de passe contient des virgules, elles doivent être échappées avec une barre oblique inverse : "exam\,ple"

  • P

    dsn: port; copy: yes

    Numéro de port à utiliser pour la connexion.

  • S

    dsn: mysql_socket; copy: yes

    Fichier socket à utiliser pour la connexion.

  • u

    dsn: user; copy: yes

    Utilisateur pour la connexion si ce n'est pas l'utilisateur actuel.

  • s

    dsn: mysql_ssl; copy: yes

    Créer une connexion SSL.

ENVIRONNEMENT

La variable d'environnement "PTDEBUG" active la sortie de débogage détaillée sur STDERR. Pour activer le débogage et capturer toute la sortie dans un fichier, exécutez l'outil comme suit :

PTDEBUG=1 pt-heartbeat ... > FICHIER 2>&1

Soyez prudent : la sortie de débogage est volumineuse et peut générer plusieurs mégaoctets de sortie.

ATTENTION

L'utilisation de <PTDEBUG> peut exposer des mots de passe. Lorsque le débogage est activé, tous les paramètres de la ligne de commande sont affichés dans la sortie.
