NOM

pthread_mutex_lock, pthread_mutex_trylock, pthread_mutex_unlock — verrouiller et déverrouiller un mutex

SYNOPSIS

#include <pthread.h>
int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);

DESCRIPTION

L'objet mutex référencé par mutex doit être verrouillé par un appel à pthread_mutex_lock() qui retourne zéro ou [EOWNERDEAD]. Si le mutex est déjà verrouillé par un autre thread, le thread appelant doit bloquer jusqu'à ce que le mutex devienne disponible. Cette opération doit retourner avec l'objet mutex référencé par mutex dans l'état verrouillé avec le thread appelant comme propriétaire. Si un thread tente de relocker un mutex qu'il a déjà verrouillé, pthread_mutex_lock() doit se comporter comme décrit dans la colonne Relock du tableau suivant. Si un thread tente de déverrouiller un mutex qu'il n'a pas verrouillé ou un mutex qui est déverrouillé, pthread_mutex_unlock() doit se comporter comme décrit dans la colonne Unlock When Not Owner du tableau suivant.

Si le type de mutex est PTHREAD_MUTEX_DEFAULT, le comportement de pthread_mutex_lock() peut correspondre à l'un des trois autres types de mutex standard décrits dans le tableau ci-dessus. S'il ne correspond pas à l'un de ces trois, le comportement est indéfini pour les cas marqués †.

Lorsque le tableau indique un comportement récursif, le mutex doit maintenir le concept d'un compteur de verrouillage. Lorsqu'un thread acquiert avec succès un mutex pour la première fois, le compteur de verrouillage doit être défini à un. Chaque fois qu'un thread relock ce mutex, le compteur de verrouillage doit être incrémenté de un. Chaque fois que le thread déverrouille le mutex, le compteur de verrouillage doit être décrémenté de un. Lorsque le compteur de verrouillage atteint zéro, le mutex doit devenir disponible pour que d'autres threads puissent l'acquérir.

La fonction pthread_mutex_trylock() doit être équivalente à pthread_mutex_lock(), sauf que si l'objet mutex référencé par mutex est actuellement verrouillé (par n'importe quel thread, y compris le thread courant), l'appel doit retourner immédiatement. Si le type de mutex est PTHREAD_MUTEX_RECURSIVE et que le mutex est actuellement possédé par le thread appelant, le compteur de verrouillage du mutex doit être incrémenté de un et la fonction pthread_mutex_trylock() doit retourner succès immédiatement.

La fonction pthread_mutex_unlock() doit libérer l'objet mutex référencé par mutex. La manière dont un mutex est libéré dépend de l'attribut de type du mutex. S'il y a des threads bloqués sur l'objet mutex référencé par mutex lors de l'appel à pthread_mutex_unlock(), entraînant la disponibilité du mutex, la politique de planification doit déterminer quel thread acquerra le mutex.

(Dans le cas des mutex PTHREAD_MUTEX_RECURSIVE, le mutex doit devenir disponible lorsque le compteur atteint zéro et que le thread appelant n'a plus aucun verrouillage sur ce mutex.)

Si un signal est délivré à un thread attendant un mutex, au retour du gestionnaire de signal, le thread doit reprendre l'attente du mutex comme s'il n'avait pas été interrompu.

Si mutex est un mutex robuste et que le processus contenant le thread propriétaire a terminé tout en détenant le verrou du mutex, un appel à pthread_mutex_lock() doit retourner la valeur d'erreur [EOWNERDEAD]. Si mutex est un mutex robuste et que le thread propriétaire a terminé tout en détenant le verrou du mutex, un appel à pthread_mutex_lock() peut retourner la valeur d'erreur [EOWNERDEAD] même si le processus dans lequel réside le thread propriétaire n'a pas terminé. Dans ces cas, le mutex est verrouillé par le thread mais l'état qu'il protège est marqué comme incohérent. L'application doit s'assurer que l'état est rendu cohérent pour la réutilisation et, une fois cela terminé, appeler pthread_mutex_consistent(). Si l'application ne parvient pas à récupérer l'état, elle doit déverrouiller le mutex sans appel préalable à pthread_mutex_consistent(), après quoi le mutex est marqué comme définitivement inutilisable.

Si mutex ne fait pas référence à un objet mutex initialisé, le comportement de pthread_mutex_lock(), pthread_mutex_trylock(), et pthread_mutex_unlock() est indéfini.

VALEUR DE RETOUR

En cas de succès, les fonctions pthread_mutex_lock(), pthread_mutex_trylock(), et pthread_mutex_unlock() doivent retourner zéro ; sinon, un numéro d'erreur doit être retourné pour indiquer l'erreur.

ERREURS

Les fonctions pthread_mutex_lock() et pthread_mutex_trylock() échoueront si :

EAGAIN
Le mutex n'a pas pu être acquis car le nombre maximum de verrous récursifs pour mutex a été dépassé.
EINVAL
Le mutex a été créé avec l'attribut protocol ayant la valeur PTHREAD_PRIO_PROTECT et la priorité du thread appelant est supérieure au plafond de priorité actuel du mutex.
ENOTRECOVERABLE

L'état protégé par le mutex n'est pas récupérable.
EOWNERDEAD

Le mutex est un mutex robuste et le processus contenant le thread précédent a terminé tout en détenant le verrou du mutex. Le verrou du mutex sera acquis par le thread appelant et il appartient au nouveau propriétaire de rendre l'état cohérent.

La fonction pthread_mutex_lock() échouera si :

EDEADLK
Le type de mutex est PTHREAD_MUTEX_ERRORCHECK et le thread courant possède déjà le mutex.

NAME

pthread_mutex_lock, pthread_mutex_trylock, pthread_mutex_unlock — thread functions to lock and unlock a mutex

SYNOPSIS

#include <pthread.h>

int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);

DESCRIPTION

The pthread_mutex_lock() function shall lock the mutex object referenced by mutex. If the mutex is already locked by another thread, the calling thread shall block until the mutex becomes available. The calling thread shall acquire the mutex whether it was previously locked or not. When a mutex is locked, it is owned by the calling thread. The effect of a thread calling pthread_mutex_lock() when it already owns the mutex is undefined if the mutex is of type PTHREAD_MUTEX_NORMAL. In this case, the calling thread will deadlock. Otherwise, the thread shall return to the calling thread without blocking. If a thread attempts to lock a mutex that it already owns, and the mutex is of type PTHREAD_MUTEX_RECURSIVE or PTHREAD_MUTEX_ERRORCHECK, the function shall return successfully. The recursive mutex allows a thread to lock it multiple times.

The pthread_mutex_trylock() function shall lock the mutex object referenced by mutex only if the mutex is unlocked at the time of the call. If the mutex is already locked by another thread, the function shall return immediately with the return value [EBUSY]. Otherwise, the mutex shall be locked and the function shall return [0].

The pthread_mutex_unlock() function shall unlock the mutex object referenced by mutex. If the calling thread is not the owner of the mutex, an error may be returned. If the mutex is unlocked, the function shall return an error. The calling thread must own the mutex when calling pthread_mutex_unlock(). Otherwise, the behavior is undefined.

If any threads are blocked waiting for a mutex to become unlocked, the scheduling policy for the mutex owner is used to determine which of the waiting threads shall be awakened. The awakened thread shall acquire the mutex and return [0] from its call to pthread_mutex_lock().

If the implementation detects that the value specified by the mutex argument does not refer to an initialized mutex object, the behavior is undefined.

Robust mutexes are a variation of standard mutexes that provide mechanisms for handling the termination of a thread while it owns a mutex. This is controlled by the PTHREAD_ROBUST_MUTEX_OPTION_NP attribute, which can be set using pthread_mutexattr_setrobust_np(). If this option is enabled, the mutex is considered a robust mutex. If a thread terminates while holding a lock on a robust mutex, the mutex becomes available to other threads. The next thread to successfully lock the mutex will receive the [EOWNERDEAD] error, indicating that the previous owner died while holding the lock.

RETURN VALUE

On success, these functions shall return [0]. Otherwise, on failure, they shall return an error number indicated below.

ERRORS

The pthread_mutex_lock() and pthread_mutex_trylock() functions shall fail if:

EBUSY
The mutex could not be acquired because it was already locked.

The pthread_mutex_unlock() function shall fail if:

EPERM
The mutex type is PTHREAD_MUTEX_ERRORCHECK or PTHREAD_MUTEX_RECURSIVE, or the mutex is a robust mutex, and the current thread does not own the mutex.

The pthread_mutex_lock() and pthread_mutex_trylock() functions may fail if:

EOWNERDEAD

The mutex is a robust mutex and the previous owning thread terminated while holding the mutex lock. The mutex lock shall be acquired by the calling thread and it is up to the new owner to make the state consistent.

The pthread_mutex_lock() function may fail if:

EDEADLK
A deadlock condition was detected.

These functions shall not return an error code of [EINTR].

The following sections are informative.

EXAMPLES

None.

APPLICATION USAGE

Applications that have assumed that non-zero return values are errors will need updating for use with robust mutexes, since a valid return for a thread acquiring a mutex which is protecting a currently inconsistent state is [EOWNERDEAD]. Applications that do not check the error returns, due to ruling out the possibility of such errors arising, should not use robust mutexes. If an application is supposed to work with normal and robust mutexes it should check all return values for error conditions and if necessary take appropriate action.

RATIONALE

Mutex objects are intended to serve as a low-level primitive from which other thread synchronization functions can be built. As such, the implementation of mutexes should be as efficient as possible, and this has ramifications on the features available at the interface.

The mutex functions and the particular default settings of the mutex attributes have been motivated by the desire to not preclude fast, inlined implementations of mutex locking and unlocking.

Since most attributes only need to be checked when a thread is going to be blocked, the use of attributes does not slow the (common) mutex-locking case.

Likewise, while being able to extract the thread ID of the owner of a mutex might be desirable, it would require storing the current thread ID when each mutex is locked, and this could incur unacceptable levels of overhead. Similar arguments apply to a mutex_tryunlock operation.

For further rationale on the extended mutex types, see the Rationale (Informative) volume of POSIX.1‐2017, Threads Extensions.

If an implementation detects that the value specified by the mutex argument does not refer to an initialized mutex object, it is recommended that the function should fail and report an [EINVAL] error.
