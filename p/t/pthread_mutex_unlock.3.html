pthread_mutex_init(3) Manuel des fonctions de bibliothèque pthread_mutex_init(3)

NOM

pthread_mutex_init, pthread_mutex_lock, pthread_mutex_trylock, pthread_mutex_unlock, pthread_mutex_destroy - opérations sur les mutex

SYNTAXE

#include <pthread.h>
pthread_mutex_t mutexrapide = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_t mutexrecursif = PTHREAD_RECURSIVE_MUTEX_INITIALIZER_NP;
pthread_mutex_t mutexveriferr = PTHREAD_ERRORCHECK_MUTEX_INITIALIZER_NP;
int pthread_mutex_init(pthread_mutex_t *mutex,
                       const pthread_mutexattr_t *mutexattr);
int pthread_mutex_lock(pthread_mutex_t *mutex);
int pthread_mutex_trylock(pthread_mutex_t *mutex);
int pthread_mutex_unlock(pthread_mutex_t *mutex);
int pthread_mutex_destroy(pthread_mutex_t *mutex);

DESCRIPTION

Un mutex est un dispositif d'EXclusion MUTuelle, et est utile pour protéger les structures de données partagées contre les modifications concurrentes, et implémenter des sections critiques et des moniteurs.

Un mutex a deux états possibles : déverrouillé (non possédé par un fil d'exécution), et verrouillé (possédé par un fil d'exécution). Un mutex ne peut jamais être possédé par deux fils d'exécution différents simultanément. Un fil d'exécution tentant de verrouiller un mutex qui est déjà verrouillé par un autre fil d'exécution est suspendu jusqu'à ce que le fil d'exécution propriétaire déverrouille d'abord le mutex.

pthread_mutex_init() initialise l'objet mutex pointé par mutex conformément aux attributs de mutex spécifiés dans mutexattr. Si mutexattr est NULL, les attributs par défaut sont utilisés à la place.

L'implémentation LinuxThreads ne prend en charge qu'un seul type d'attributs de mutex, le genre de mutex, qui peut être "rapide", "récursif", ou "vérification d'erreur". Le genre d'un mutex détermine s'il peut être verrouillé à nouveau par un fil d'exécution qui le possède déjà. Le genre par défaut est "rapide". Voir pthread_mutexattr_init(3) pour plus d'informations sur les attributs de mutex.

Les variables de type pthread_mutex_t peuvent également être initialisées statiquement, en utilisant les constantes PTHREAD_MUTEX_INITIALIZER (pour les mutex rapides), PTHREAD_RECURSIVE_MUTEX_INITIALIZER_NP (pour les mutex récursifs), et PTHREAD_ERRORCHECK_MUTEX_INITIALIZER_NP (pour les mutex de vérification d'erreur).

pthread_mutex_lock() verrouille le mutex donné. Si le mutex est actuellement déverrouillé, il devient verrouillé et possédé par le fil d'exécution appelant, et pthread_mutex_lock() retourne immédiatement. Si le mutex est déjà verrouillé par un autre fil d'exécution, pthread_mutex_lock() suspend le fil d'exécution appelant jusqu'à ce que le mutex soit déverrouillé.

Si le mutex est déjà verrouillé par le fil d'exécution appelant, le comportement de pthread_mutex_lock() dépend du genre du mutex. Si le mutex est de genre "rapide", le fil d'exécution appelant est suspendu jusqu'à ce que le mutex soit déverrouillé, causant ainsi effectivement un blocage du fil d'exécution appelant. Si le mutex est de genre "vérification d'erreur", pthread_mutex_lock() retourne immédiatement avec le code d'erreur EDEADLK. Si le mutex est de genre "récursif", pthread_mutex_lock() réussit et retourne immédiatement, enregistrant le nombre de fois où le fil d'exécution appelant a verrouillé le mutex. Un nombre égal d'opérations pthread_mutex_unlock() doit être effectué avant que le mutex ne retourne à l'état déverrouillé.

pthread_mutex_trylock() se comporte de manière identique à pthread_mutex_lock(), sauf qu'il ne bloque pas le fil d'exécution appelant si le mutex est déjà verrouillé par un autre fil d'exécution (ou par le fil d'exécution appelant dans le cas d'un mutex "rapide"). Au lieu de cela, pthread_mutex_trylock() retourne immédiatement avec le code d'erreur EBUSY.

pthread_mutex_unlock() déverrouille le mutex donné. Le mutex est supposé être verrouillé et possédé par le fil d'exécution appelant à l'entrée de pthread_mutex_unlock(). Si le mutex est de genre "rapide", pthread_mutex_unlock() le retourne toujours à l'état déverrouillé. S'il est de genre "récursif", il décrémente le compteur de verrouillage du mutex (nombre d'opérations pthread_mutex_lock() effectuées sur lui par le fil d'exécution appelant), et ce n'est que lorsque ce compteur atteint zéro que le mutex est réellement déverrouillé.

Sur les mutex "vérification d'erreur" et "récursifs", pthread_mutex_unlock() vérifie effectivement à l'exécution que le mutex est verrouillé à l'entrée, et qu'il a été verrouillé par le même fil d'exécution qui appelle maintenant pthread_mutex_unlock(). Si ces conditions ne sont pas remplies, un code d'erreur est retourné et le mutex reste inchangé. Les mutex "rapides" n'effectuent aucune de ces vérifications, permettant ainsi à un mutex verrouillé d'être déverrouillé par un fil d'exécution autre que son propriétaire. C'est un comportement non portable et sur lequel il ne faut pas compter.

pthread_mutex_destroy() détruit un objet mutex, libérant les ressources qu'il pourrait détenir. Le mutex doit être déverrouillé à l'entrée. Dans l'implémentation LinuxThreads, aucune ressource n'est associée aux objets mutex, donc pthread_mutex_destroy() ne fait rien d'autre que de vérifier que le mutex est déverrouillé.

ANNULATION

Aucune des fonctions de mutex n'est un point d'annulation, pas même pthread_mutex_lock(), malgré le fait qu'elle puisse suspendre un fil d'exécution pendant des durées arbitraires. De cette façon, le statut des mutex aux points d'annulation est prévisible, permettant aux gestionnaires d'annulation de déverrouiller précisément les mutex qui doivent être déverrouillés avant que le fil d'exécution ne cesse de s'exécuter. Par conséquent, les fils d'exécution utilisant l'annulation différée ne doivent jamais détenir un mutex pendant des périodes prolongées.

SÉCURITÉ DES SIGNAUX ASYNC

Les fonctions de mutex ne sont pas sûres pour les signaux asynchrones. Ce que cela signifie, c'est qu'elles ne doivent pas être appelées à partir d'un gestionnaire de signaux. En particulier, appeler pthread_mutex_lock() ou pthread_mutex_unlock() à partir d'un gestionnaire de signaux peut provoquer un blocage du fil d'exécution appelant.

VALEUR DE RETOUR

pthread_mutex_init() retourne toujours 0. Les autres fonctions de mutex retournent 0 en cas de succès et un code d'erreur non nul en cas d'erreur.

ERREURS

La fonction pthread_mutex_lock() retourne le code d'erreur suivant en cas d'erreur :

EINVAL
Le mutex n'a pas été correctement initialisé.
EDEADLK
Le mutex est déjà verrouillé par le fil d'exécution appelant (mutex de type "vérification d'erreur" uniquement).

La fonction pthread_mutex_trylock() retourne les codes d'erreur suivants en cas d'erreur :

EBUSY
Le mutex n'a pas pu être acquis car il était actuellement verrouillé.
EINVAL
Le mutex n'a pas été correctement initialisé.

La fonction pthread_mutex_unlock() retourne le code d'erreur suivant en cas d'erreur :

EINVAL
Le mutex n'a pas été correctement initialisé.
EPERM
Le fil d'exécution appelant ne possède pas le mutex (mutex de type "vérification d'erreur" uniquement).

La fonction pthread_mutex_destroy() retourne le code d'erreur suivant en cas d'erreur :

EBUSY
Le mutex est actuellement verrouillé.

VOIR AUSSI

pthread_mutexattr_init(3), pthread_mutexattr_setkind_np(3), pthread_cancel(3).

NAME

pthread_mutex_unlock - déverrouille un mutex

SYNOPSIS

#include <pthread.h>

int pthread_mutex_unlock(pthread_mutex_t *mutex);

DESCRIPTION

La fonction pthread_mutex_unlock déverrouille le mutex référencé par mutex.

Si le thread appelant n'a pas verrouillé le mutex, le comportement est indéfini.

Si un autre thread attend pour acquérir le verrou sur le mutex, ce thread sera réveillé et acquerra le verrou. Il n'y a aucune garantie quant à l'ordre dans lequel les threads en attente seront réveillés.

Si le mutex est de type PTHREAD_MUTEX_ERRORCHECK et que le thread appelant n'a pas verrouillé le mutex, une erreur sera retournée.

Si le mutex est de type PTHREAD_MUTEX_RECURSIVE et que le thread appelant est le propriétaire du mutex, le compteur d'acquisition du mutex est décrémenté. Le mutex est effectivement déverrouillé lorsque le compteur atteint zéro.

CANCELLATION

Une annulation de thread peut se produire à tout moment. Si un thread est annulé alors qu'il est en train d'acquérir un mutex (par exemple, en appelant pthread_mutex_lock), le verrou du mutex peut rester acquis.

Si un thread est annulé alors qu'il est sur le point de libérer un mutex (après avoir réussi à l'acquérir), le mutex sera libéré.

Pour une gestion plus robuste de l'annulation lors de l'acquisition d'un mutex, il est recommandé d'utiliser pthread_mutex_lock en conjonction avec des points d'annulation désactivés, ou d'utiliser des mécanismes de gestion des exceptions pour garantir que les mutex sont déverrouillés.

ASYNC-SIGNAL SAFETY

La fonction pthread_mutex_unlock est asynchrone-signalement sûre.

RETURN VALUE

En cas de succès, pthread_mutex_unlock retourne 0. En cas d'erreur, un numéro d'erreur est retourné.

ERRORS

EINVAL
La valeur spécifiée par mutex est invalide.
EPERM
Le thread appelant ne possède pas le mutex.

SEE ALSO

pthread_mutex_destroy(3), pthread_mutex_init(3), pthread_mutex_lock(3), pthread_mutex_trylock(3), pthread_mutexattr_destroy(3), pthread_mutexattr_init(3), pthread_mutexattr_settype(3), pthread_mutexattr_gettype(3), pthread_cond_wait(3), pthreads(7)

EXAMPLE

Voici un exemple d'utilisation de pthread_mutex_unlock :

pthread_mutex_t mut;
int x;

pthread_mutex_lock(&mut);
/* opération sur x */
pthread_mutex_unlock(&mut);
