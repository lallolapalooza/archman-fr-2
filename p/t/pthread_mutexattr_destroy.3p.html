PTHREAD_MUTEXATTR_DESTROY(3P) Manuel du programmeur POSIX PTHREAD_MUTEXATTR_DESTROY(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pthread_mutexattr_destroy, pthread_mutexattr_init — détruire et initialiser l'objet d'attributs de mutex

SYNOPSIS

#include <pthread.h>
int pthread_mutexattr_destroy(pthread_mutexattr_t *attr);
int pthread_mutexattr_init(pthread_mutexattr_t *attr);

DESCRIPTION

La fonction pthread_mutexattr_destroy() détruit un objet d'attributs de mutex ; l'objet devient, en effet, non initialisé. Une implémentation peut provoquer le fait que pthread_mutexattr_destroy() place l'objet référencé par attr dans une valeur invalide.

Un objet d'attributs attr détruit peut être réinitialisé à l'aide de pthread_mutexattr_init() ; les résultats de toute autre référence à l'objet après sa destruction sont indéfinis.

La fonction pthread_mutexattr_init() initialise un objet d'attributs de mutex attr avec la valeur par défaut pour tous les attributs définis par l'implémentation.

Les résultats sont indéfinis si pthread_mutexattr_init() est appelée en spécifiant un objet d'attributs attr déjà initialisé.

Après qu'un objet d'attributs de mutex a été utilisé pour initialiser un ou plusieurs mutex, toute fonction affectant l'objet d'attributs (y compris sa destruction) ne doit pas affecter les mutex précédemment initialisés.

Le comportement est indéfini si la valeur spécifiée par l'argument attr à pthread_mutexattr_destroy() ne fait pas référence à un objet d'attributs de mutex initialisé.

VALEUR DE RETOUR

En cas de succès, pthread_mutexattr_destroy() et pthread_mutexattr_init() retournent zéro ; sinon, un numéro d'erreur est retourné pour indiquer l'erreur.

ERREURS

La fonction pthread_mutexattr_init() échoue si :

ENOMEM
Une mémoire insuffisante existe pour initialiser l'objet d'attributs de mutex.

Ces fonctions ne retourneront pas de code d'erreur [EINTR].

RATIONALE

Si une implémentation détecte que la valeur spécifiée par l'argument attr à pthread_mutexattr_destroy() ne fait pas référence à un objet d'attributs de mutex initialisé, il est recommandé que la fonction échoue et signale une erreur [EINVAL].

Voir pthread_attr_destroy() pour une explication générale des attributs. Les objets d'attributs permettent aux implémentations d'expérimenter des extensions utiles et autorisent l'extension de ce volume de POSIX.1-2017 sans modifier les fonctions existantes. Ainsi, ils permettent une extensibilité future de ce volume de POSIX.1-2017 et réduisent la tentation de standardiser prématurément sur des sémantiques qui ne sont pas encore largement implémentées ou comprises.

Des exemples d'attributs de mutex supplémentaires possibles qui ont été discutés sont spin_only, limited_spin, no_spin, recursive, et metered. (Pour expliquer ce que ces derniers attributs pourraient signifier : les mutex récursifs permettraient un ré-verrouillage multiple par le propriétaire actuel ; les mutex mesurés conserveraient de manière transparente des enregistrements de la longueur de la file d'attente, du temps d'attente, etc.) Étant donné qu'il n'y a pas encore d'accord général sur l'utilité de ceux-ci, résultant d'implémentations et d'expériences d'utilisation partagées, ils ne sont pas encore spécifiés dans ce volume de POSIX.1-2017. Les objets d'attributs de mutex, cependant, rendent possible le test de ces concepts pour une standardisation ultérieure.

Attributs de mutex et performance

Des précautions ont été prises pour garantir que les valeurs par défaut des attributs de mutex soient définies de telle sorte que les mutex initialisés avec les valeurs par défaut aient des sémantiques suffisamment simples pour que le verrouillage et le déverrouillage puissent être effectués avec l'équivalent d'une instruction de test-et-définition (plus éventuellement quelques autres instructions de base).

Il existe au moins une méthode d'implémentation qui peut être utilisée pour réduire le coût des tests lors du verrouillage si un mutex a des attributs non par défaut. Une méthode que peut employer une implémentation (et cela peut être rendu entièrement transparent aux applications entièrement conformes à POSIX) consiste à pré-verrouiller secrètement tous les mutex initialisés avec des attributs non par défaut. Toute tentative ultérieure de verrouiller un tel mutex provoque le branchement de l'implémentation vers le « chemin lent » comme si le mutex était indisponible ; ensuite, sur le chemin lent, l'implémentation peut effectuer le « vrai travail » pour verrouiller un mutex non par défaut. L'opération de déverrouillage sous-jacente est plus compliquée car l'implémentation ne souhaite jamais vraiment relâcher le pré-verrouillage sur ce type de mutex. Cela illustre que, selon le matériel, il peut y avoir certaines optimisations qui peuvent être utilisées afin que quels que soient les attributs de mutex considérés comme « les plus fréquemment utilisés » puissent être traités le plus efficacement.

Mémoire partagée entre processus et synchronisation

L'existence de fonctions de mappage mémoire dans ce volume de POSIX.1-2017 conduit à la possibilité qu'une application alloue les objets de synchronisation de cette section dans une mémoire accessible par plusieurs processus (et donc par des threads de plusieurs processus).

Afin de permettre une telle utilisation, tout en maintenant le cas habituel (c'est-à-dire l'utilisation au sein d'un seul processus) efficace, une option process-shared a été définie.

Si une implémentation prend en charge l'option _POSIX_THREAD_PROCESS_SHARED, alors l'attribut process-shared peut être utilisé pour indiquer que les mutex ou les variables de condition peuvent être accédés par des threads de plusieurs processus.

Le réglage par défaut de PTHREAD_PROCESS_PRIVATE a été choisi pour l'attribut process-shared afin que les formes les plus efficaces de ces objets de synchronisation soient créées par défaut.

Les variables de synchronisation initialisées avec l'attribut process-shared PTHREAD_PROCESS_PRIVATE ne peuvent être opérées que par les threads du processus qui les a initialisées. Les variables de synchronisation initialisées avec l'attribut process-shared PTHREAD_PROCESS_SHARED peuvent être opérées par n'importe quel thread dans n'importe quel processus qui y a accès. En particulier, ces processus peuvent exister au-delà de la durée de vie du processus initialisateur. Le code suivant concerne trois processus distincts qui créent, postent et attendent sur un sémaphore dans le fichier /tmp/semaphore. Une fois le fichier créé, les programmes post et wait incrémentent et décrémentent le sémaphore de comptage (attendant et se réveillant si nécessaire) même s'ils n'ont pas initialisé le sémaphore.

/* create.c */
#include "pthread.h"
#include "sem.h"
int
main()
{
    semaphore_t *semap;
    semap = semaphore_create("/tmp/semaphore");
    if (semap == NULL)
        exit(1);
    semaphore_close(semap);
    return (0);
}
/* post */
#include "pthread.h"
#include "sem.h"
int
main()
{
    semaphore_t *semap;
    semap = semaphore_open("/tmp/semaphore");

        exit(1);
    semaphore_post(semap);
    semaphore_close(semap);
    return (0);
}
