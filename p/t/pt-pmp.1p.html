NOM

pt-pmp - Agrège les traces de pile GDB pour un programme sélectionné.

SYNOPIS

Utilisation : pt-pmp [OPTIONS] [FICHIERS]

pt-pmp est un profileur à la façon de pauvre homme (poor man's profiler), inspiré par http://poormansprofiler.org. Il peut créer et résumer des traces de pile complètes des processus sous Linux. Les résumés des traces de pile peuvent être un outil inestimable pour diagnostiquer ce sur quoi un processus est en attente.

RISQUES

Percona Toolkit est mature, éprouvé sur le terrain et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Vérifier les "BUGS" connus de l'outil
  • Tester l'outil sur un serveur non-production
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

DESCRIPTION

pt-pmp effectue deux tâches : il obtient une trace de pile et il résume la trace de pile. Si un fichier est donné en ligne de commande, l'outil saute la première étape et agrège simplement le fichier.

Pour résumer la trace de pile, l'outil extrait le nom de la fonction (symbole) de chaque niveau de la pile, et les combine avec des virgules. Il fait cela pour chaque thread dans la sortie. Ensuite, il trie les threads similaires ensemble et compte combien il y en a de chaque, puis les trie du plus fréquent au moins fréquent.

pt-pmp est un outil en lecture seule. Cependant, la collecte des traces de pile GDB est réalisée en attachant GDB au programme et en affichant les traces de pile de tous les threads. Cela bloquera le programme pendant une certaine période de temps, allant d'une seconde environ à beaucoup plus sur des systèmes très chargés avec beaucoup de mémoire et de nombreux threads dans le programme. Dans l'utilisation par défaut de l'outil comme outil de profilage MySQL, cela signifie que MySQL ne répondra pas pendant que l'outil s'exécute, bien que si vous utilisez l'outil pour diagnostiquer un serveur ne répondant pas, il n'y a vraiment aucune raison de ne pas le faire. En plus de bloquer le serveur, il y a également un certain risque que le serveur plante ou fonctionne mal après que GDB s'en soit détaché.

Les dumpers "eu" et "pteu" utilisent eu-stack (https://sourceware.org/elfutils/) au lieu de GDB. eu-stack collecte les piles avec un impact minimal et ne cause pas les mêmes problèmes que GDB. Les dumpers "eu" et "pteu" sont recommandés au lieu de GDB et l'un d'eux sera le dumper par défaut dans les futures versions.

OPTIONS

--binaire
forme courte : -b ; type : chaîne ; par défaut : mysqld

Le binaire à tracer.

--dumper
forme courte : -d ; type : chaîne ; par défaut : gdb

Quel dumper utiliser pour obtenir les traces de pile (gdb : gdb, eu : eu-stack, pteu : pt-eustack-resolver).

--aide
Afficher l'aide et quitter.
--intervalle
forme courte : -s ; type : entier ; par défaut : 0

Nombre de secondes à attendre entre les "--iterations".

--iterations
forme courte : -i ; type : entier ; par défaut : 1

Combien de traces collecter et agréger.

--lignes
forme courte : -l ; type : entier ; par défaut : 0

Agrège seulement le premier nombre spécifié de fonctions ; 0=infini.

--pid
forme courte : -p ; type : entier

ID du processus à tracer ; remplace "--binaire".

--readnever
Passe l'option "--readnever" à "gdb". Avec cette option, "gdb" ne lira pas les fichiers de symboles, produisant ainsi des traces de pile beaucoup plus rapidement. Cependant, de telles traces peuvent ne pas être suffisantes pour le diagnostic.
--sauver-echantillons
forme courte : -k ; type : chaîne

Conserver les traces brutes dans ce fichier après l'agrégation.

--tids
forme courte : -t ; type : chaîne ; par défaut : *

Extraire les traces uniquement pour des tids spécifiques.

Cette option utilise des expressions régulières pour sélectionner les threads. Par exemple, si la trace de pile collectée contient des données pour les threads :

[Nouveau Thread 0x52173940 (LWP 23846)]
[Nouveau Thread 0x52132940 (LWP 23845)]
[Nouveau Thread 0x520f1940 (LWP 23844)]
[Nouveau Thread 0x520b0940 (LWP 23798)]
[Nouveau Thread 0x5206f940 (LWP 23776)]
[Nouveau Thread 0x5202e940 (LWP 23775)]
[Nouveau Thread 0x51fed940 (LWP 23774)]
[Nouveau Thread 0x51fac940 (LWP 23728)]
[Nouveau Thread 0x51f6b940 (LWP 23727)]
[Nouveau Thread 0x51f2a940 (LWP 21264)]
[Nouveau Thread 0x51ee9940 (LWP 21263)]
[Nouveau Thread 0x51ea8940 (LWP 21201)]

"-t 21" affichera les traces de pile pour les threads 21264, 21263, 21201

"-t 21201,23846" affichera les traces de pile pour les threads 21201, 23846

"-t 21201,237.8" affichera les traces de pile pour les threads 21201, 23798, 23728

--version
Afficher la version et quitter.

ENVIRONNEMENT

Cet outil n'utilise aucune variable d'environnement.

EXIGENCES SYSTÈME

Cet outil nécessite Bash v3 ou plus récent. Si aucun fichier de trace n'est fourni, alors gdb est également requis pour créer des traces de pile pour le processus spécifié en ligne de commande.

BOGUES

Pour une liste des bogues connus, voir https://jira.percona.com/projects/PT/issues.

Veuillez signaler les bogues à https://jira.percona.com/projects/PT. Incluez les informations suivantes dans votre rapport de bogue :

  • Ligne de commande complète utilisée pour exécuter l'outil
  • "--version" de l'outil
  • Version MySQL de tous les serveurs impliqués
  • Sortie de l'outil, y compris STDERR
  • Fichiers d'entrée (journaux/dumps/fichiers de configuration, etc.)

Si possible, incluez la sortie de débogage en exécutant l'outil avec "PTDEBUG" ; voir "ENVIRONNEMENT".

ATTENTION

L'utilisation de <PTDEBUG> peut exposer des mots de passe. Lorsque le débogage est activé, tous les paramètres de la ligne de commande sont affichés dans la sortie.
