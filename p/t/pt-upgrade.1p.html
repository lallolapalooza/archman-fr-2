NOM

pt-upgrade - Vérifie que les résultats des requêtes sont identiques sur différents serveurs.

SYNTAXE

Utilisation : pt-upgrade [OPTIONS] JOURNAUX|RÉSULTATS DSN [DSN]

pt-upgrade exécute des requêtes dans les "JOURNAUX" MySQL donnés sur chaque "DSN", compare les résultats et signale toute différence significative. L'outil peut également enregistrer les résultats pour des analyses ultérieures. "JOURNAUX" peut être lent, général, binaire, tcpdump et « brut ».

Compare host2 à host1 en utilisant les requêtes dans "slow.log" :

pt-upgrade h=host1 h=host2 slow.log

Compare host2 aux résultats enregistrés de host1 :

pt-upgrade h=host1 --save-results host1_results/ slow.log
pt-upgrade host1_results1/ h=host2

RISQUES

Percona Toolkit est mature, éprouvé sur le terrain et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Consulter les "BOGUES" connus de l'outil
  • Tester l'outil sur un serveur non-production
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

DESCRIPTION

pt-upgrade aide à déterminer s'il est sûr de mettre à niveau (ou rétrograder) vers une nouvelle version de MySQL. Un plan de mise à niveau sûr et conservateur comporte plusieurs étapes, dont l'une consiste à s'assurer que les requêtes produiront des résultats identiques sur la nouvelle version de MySQL.

pt-upgrade exécute des requêtes à partir des journaux lents, généraux, binaires, tcpdump et « bruts » sur deux serveurs, compare plusieurs aspects de l'exécution et des résultats de chaque requête, et signale toute différence significative. Les deux serveurs sont généralement des serveurs de développement, l'un exécutant la version actuelle de production de MySQL et l'autre exécutant la nouvelle version de MySQL.

CAS D'UTILISATION

pt-upgrade a deux cas d'utilisation. Le premier, cas canonique, est l'exécution « hôte à hôte ». Un fichier journal et deux DSN sont fournis sur la ligne de commande, un pour chaque serveur MySQL. Voir le premier exemple dans la « SYNTAXE ». Les requêtes sont exécutées et comparées sur chaque serveur pendant que l'outil s'exécute. Les requêtes avec des différences sont imprimées pendant que l'outil s'exécute, ou lorsqu'il se termine (voir « QUAND LES REQUÊTES SONT SIGNALÉES »). Rien n'est enregistré sur le disque, donc ce cas d'utilisation nécessite moins d'espace disque dur, mais les requêtes doivent être exécutées sur les deux serveurs si l'outil est réexécuté, même si l'un des serveurs n'a pas changé. S'il y a beaucoup de requêtes ou si leur exécution prend beaucoup de temps, et qu'un serveur ne change pas, vous pourriez vouloir utiliser le deuxième cas d'utilisation.

Le deuxième cas d'utilisation est l'exécution de « résultats de référence vers hôte ». Les résultats de référence sont les résultats complets d'un seul serveur MySQL, enregistrés sur disque. Dans ce cas, vous devez d'abord générer les résultats de référence avec « --save-results », puis exécuter l'outil une seconde fois pour comparer un autre serveur MySQL aux résultats. Voir le second exemple dans la « SYNTAXE ». Les résultats sont généralement générés pour la version actuelle de MySQL qui ne change pas. Ce cas d'utilisation peut nécessiter *beaucoup* d'espace disque car les résultats (c'est-à-dire les lignes) pour toutes les requêtes doivent être enregistrés, plus d'autres données sur les requêtes. Si vous prévoyez de faire de nombreuses comparaisons par rapport à une version fixe de MySQL, ce cas d'utilisation est plus efficace. Ou si vous n'avez pas accès aux deux serveurs en même temps, ce cas d'utilisation vous permet « d'exécuter maintenant, comparer plus tard ».

CONSIDÉRATIONS IMPORTANTES

CONSISTANCE

Des environnements cohérents et des données cohérentes sont cruciaux pour obtenir un rapport précis. pt-upgrade ne doit jamais être exécuté sur un serveur de production ou un serveur actif car il n'y a aucun moyen simple d'assurer une lecture synchrone pour chaque requête. Si des données changent sur l'un ou l'autre serveur pendant que pt-upgrade s'exécute, le rapport pourrait contenir plus de faux positifs que de différences légitimes. pt-upgrade suppose que les deux serveurs MySQL sont statiques, inchangés (sauf toute modification apportée par l'outil s'il est exécuté avec « --no-read-only »). Une charge de travail en lecture seule ne devrait pas affecter l'outil, sauf peut-être les temps d'exécution des requêtes, donc des réplicas en lecture seule pourraient être utilisés.

COMPARÉ À

Dans une comparaison hôte à hôte, les résultats du premier hôte établissent la norme par rapport à laquelle les résultats du second hôte sont comparés. Dans une comparaison de résultats de référence à hôte, les résultats de référence sont la norme par rapport à laquelle l'hôte est comparé. Les phrases comparatives comme « plus petit que », « meilleur que », etc. signifient par rapport à la norme.

Par exemple, si le temps d'exécution d'un événement est de 0.01 sur le premier hôte et de 0.5 sur le second hôte, il s'agit d'une différence significative car 0.5 est pire que 0.1, et la requête sera donc signalée.

LECTURE SEULE

Par défaut, pt-upgrade n'exécute que les instructions "SELECT" et "SET". (Cela n'inclut pas les instructions 'SELECT...INTO', qui ne renvoient pas de lignes mais déversent la sortie dans un fichier ou une variable.) Si vous utilisez des serveurs de test ou de développement recréables et souhaitez comparer également les instructions d'écriture (par exemple, "INSERT", "UPDATE", "DELETE"), spécifiez "--no-read-only". Si vous utilisez un journal binaire, vous devez spécifier "--no-read-only" car les journaux binaires ne contiennent pas d'instructions "SELECT". Voir « --[no]read-only ».

TRANSACTIONS

L'outil ne crée pas ses propres transactions, mais toutes les transactions du "JOURNAL" sont exécutées telles quelles. Étant donné que les journaux sont sériels, les transactions ne devraient normalement pas poser de problème. Si, cependant, vous avez besoin de comparer des requêtes qui sont d'une manière ou d'une autre liées transactionnellement (auquel cas vous devrez probablement également désactiver « --[no]read-only »), alors pt-upgrade ne fera probablement pas ce dont vous avez besoin car il n'est pas conçu à cet effet.

pt-upgrade s'exécute avec "autocommit=1" par défaut.

LIMITATION DE DÉBIT

pt-upgrade n'a pas d'options de limitation de débit car l'outil ne doit être exécuté que sur des serveurs de test ou de développement dédiés. Ne pas exécuter pt-upgrade sur des serveurs de production ! Par conséquent, l'outil est gourmand en CPU, mémoire, disque et réseau. Il exécute les requêtes aussi vite que possible.

DIFFÉRENCES DE REQUÊTES

Des différences significatives de requêtes sont déterminées en comparant ces aspects de chaque requête des deux hôtes :

Nombre de lignes
Le nombre de lignes renvoyées par la requête doit être le même. Ceci est signalé comme « lignes manquantes » sous « Différences de lignes ».
Données de ligne
Les données de ligne renvoyées par la requête doivent être les mêmes. Toutes les différences sont significatives : espaces blancs, précision des décimaux, etc.
Avertissements
La requête ne doit produire aucune erreur ou avertissement, ou produire les mêmes erreurs ou avertissements.
Temps d'exécution
Une requête s'exécute rarement avec un temps constant, mais son temps d'exécution doit être du même ordre de grandeur ou inférieur.
Erreurs de requête
Si une requête provoque une erreur SQL sur un seul hôte, cela est signalé comme « Erreurs de requête ». Puisque la requête fonctionne sur un hôte, sa syntaxe est probablement valide, et l'erreur est due à une condition spécifique à l'autre hôte.
Erreurs SQL
Si une requête provoque une erreur SQL sur les deux hôtes, cela est signalé
ed comme "Erreurs SQL". La syntaxe SQL de la requête pourrait être invalide.

RAPPORT

Au fur et à mesure de son exécution, pt-upgrade affiche les requêtes présentant des différences dès que possible (voir "QUAND LES REQUÊTES SONT RAPPORTÉES"). Pour éviter que le rapport ne devienne trop long, les requêtes ne sont pas rapportées individuellement mais regroupées par empreinte dans des classes. Une empreinte de requête est la forme abstraite d'une requête, créée en supprimant les valeurs littérales, en normalisant les espaces blancs, etc. Ainsi, ces requêtes appartiennent à la même classe :

SELECT c FROM t WHERE id = 1
SELECT c FROM t WHERE id=5
select  c  from  t  where  id  =  9

L'empreinte pour ces requêtes est :

select c from t where id=?

Chaque classe de requête peut contenir jusqu'à "--max-class-size" requêtes uniques (1 000 par défaut). Jusqu'à "--max-examples" sont rapportés pour chaque type de différence, par classe de requête. Du fait d'appartenir à la même classe, un exemple de différence d'une requête est généralement représentatif de toutes les requêtes présentant la même différence, il n'est donc pas nécessaire de rapporter chaque exemple. Le nombre total de requêtes dans une classe présentant une différence particulière est indiqué dans le rapport.

EXEMPLE

#-----------------------------------------------------------------------
# Journaux
#-----------------------------------------------------------------------
Fichier : /opt/mysql/slow.log
Taille : 59700
#-----------------------------------------------------------------------
# Hôtes
#-----------------------------------------------------------------------
host1:
  DSN :       h=127.1,P=12345
  hostname :  dev1
  MySQL :     MySQL 5.1.68
host2:
  DSN :       h=127.1,P=12348
  hostname :  dev2
  MySQL :     MySQL 5.5.10
########################################################################
# Classe de requête AAD020567F8398EE
########################################################################
Rapport de la classe car elle contient des différences, mais n'a pas encore été rapportée.
Requêtes totales      1
Requêtes uniques     1
Requêtes écartées  0
insert into t (id, username) values(?+)
##
## Avertissements diff: 1
##
-- 1.
   Code : 1265
  Niveau : Avertissement
Message : Données tronquées pour la colonne 'username' à la ligne 1
vs.
Pas d'avertissement 1265
INSERT INTO t (id, username) VALUES (NULL, 'long_username')
#-----------------------------------------------------------------------
# Statistiques
#-----------------------------------------------------------------------
requetes_echouees        0
pas_select            0
requetes_filtrees      0
requetes_sans_diffs      0
requetes_lues          1
requetes_avec_diffs    1
requetes_avec_erreurs   0

Les sections "Classe de requête <ID>" sont les plus importantes car elles listent les "DIFFÉRENCES DE REQUÊTES". La première partie de la section liste la raison pour laquelle la classe de requête a été rapportée, suivie du nombre de requêtes dans la classe, puis de l'empreinte qui définit la classe.

Le reste de la section de la classe de requête liste les "DIFFÉRENCES DE REQUÊTES" qui ont provoqué le rapport de la classe. Chaque type de différence commence par un en-tête double dièse qui liste le type et le nombre total de requêtes dans la classe présentant cette différence. Ensuite, jusqu'à "--max-examples" sont listés, numérotés "-- 1.", "--- 2.", etc. Chaque exemple liste la différence pour les premier et second hôtes (respectifs de la section "Hôtes"), suivi de la première instruction SQL qui a révélé la différence.

QUAND LES REQUÊTES SONT RAPPORTÉES

Une classe de requête est rapportée dès qu'une des "DIFFÉRENCES DE REQUÊTES" ou des erreurs de requête a atteint "--max-examples". Sinon, toutes les requêtes présentant des différences sont rapportées à la fin de l'exécution de l'outil.

Par exemple, si deux différences de temps d'exécution de requête sont trouvées pour une classe de requête, elle n'est pas encore rapportée. Une fois qu'une troisième différence de temps d'exécution de requête est trouvée, la classe de requête est rapportée, y compris toutes les autres différences qui auraient pu être trouvées également. Les requêtes de la classe continueront d'être exécutées, mais la classe ne sera plus rapportée.

SORTIE

Le "RAPPORT" est imprimé sur STDOUT pendant l'exécution de l'outil. Les avertissements internes, les erreurs et "--progress" sont imprimés sur STDERR. Pour les séparer, exécutez l'outil comme suit :

pt-upgrade ... 1>rapport 2>err &

Ensuite, utilisez "tail -f err" pendant l'exécution de l'outil pour suivre sa "--progress".

STATUT DE SORTIE

En général, l'outil se termine avec un code de sortie zéro s'il s'est terminé normalement, sans avertissement ni erreur interne, et sans "DIFFÉRENCES DE REQUÊTES" trouvées. Sinon, l'outil se termine avec un code non nul parmi les suivants :

  • 1

    Il y a eu trop d'erreurs ou d'avertissements internes ; voir STDERR. Voir également "--[no]continue-on-error".

  • 4

    Il y a eu des "DIFFÉRENCES DE REQUÊTES" ; voir le "RAPPORT".

  • 8

    "--run-time" a expiré ; l'outil n'a pas fini de lire les journaux ou les résultats de référence.

D'autres codes de sortie indiquent que l'outil a planté ou s'est arrêté de manière inattendue. L'erreur qui a causé cela aurait dû être imprimée sur STDERR.

Pour vérifier un code de sortie particulier, effectuez un "ET" logique ("&") du statut de sortie final avec le code de sortie. Par exemple, un statut de sortie de 5 implique les codes 1 et 4 car "5 & 1" est vrai, et "5 & 4" est vrai.

OPTIONS

Cet outil accepte des arguments de ligne de commande supplémentaires. Référez-vous à la "SYNOPSE" et aux informations d'utilisation pour plus de détails.

--ask-pass
Demande un mot de passe lors de la connexion à MySQL.
--charset
forme courte : -A; type : chaîne

Jeu de caractères par défaut. Si la valeur est utf8, définit le mode binaire de Perl sur STDOUT en utf8, transmet l'option mysql_enable_utf8 à DBD::mysql, et exécute SET NAMES UTF8 après la connexion à MySQL. Toute autre valeur définit le mode binaire sur STDOUT sans la couche utf8, et exécute SET NAMES après la connexion à MySQL.

--config
type : Tableau

Lit cette liste de fichiers de configuration séparés par des virgules ; si spécifié, cela doit être la première option sur la ligne de commande.

--[no]continue-on-error
par défaut : oui

Continue l'analyse même en cas d'erreur. L'outil ne continuera pas indéfiniment : il s'arrête après 100 erreurs, auquel cas il y a probablement un bug dans l'outil ou l'entrée est invalide.

--[no]create-upgrade-table
par défaut : oui

Crée la base de données et la table "--upgrade-table".

--daemonize
Forks en arrière-plan et se détache du terminal. Uniquement sur les systèmes d'exploitation POSIX.
--database
forme courte : -D; type : chaîne

Base de données par défaut lors de la connexion à MySQL.

--defaults-file
forme courte : -F; type : chaîne

Ne lit les options MySQL que dans le fichier donné. Vous devez fournir un chemin absolu.

--[no]disable-query-cache
par défaut : oui

Exécute "SET SESSION query_cache_type = OFF" pour désactiver le cache de requêtes.

--dry-run
Exécute mais n'exécute ni ne compare les requêtes. Ceci est utile pour vérifier les options de ligne de commande, les connexions à MySQL, et l'analyse des journaux ou des résultats de référence.
--filter
type : chaîne

Autorise les événements pour lesquels ce code Perl retourne vrai.

Voir la même option dans la documentation de pt-query-digest.

--help
Affiche l'aide et quitte.
--host
forme courte : -h; type : chaîne

Nom d'hôte ou IP de MySQL.

--ignore-warnings
type : Hash

Ignore ces codes d'avertissement MySQL lors de la comparaison des avertissements.

--log
type : chaîne

Imprime STDOUT et STDERR dans ce fichier lorsqu'il est démoniaqué. Cette option ne prend effet que lorsque "--daemonize" est spécifié. Le fichier est créé s'il n'existe pas, sinon la sortie y est ajoutée.

--max-class-size
type : entier; par défaut : 1000

Nombre maximum de requêtes uniques par classe de requête. Voir "RAPPORT".

--max-examples
type : entier; par défaut : 3

Nombre maximum d'exemples à lister pour chaque "DIFFÉRENCE DE REQUÊTE". Une classe de requête est rapportée dès que ce nombre d'exemples pour un type quelconque de différence de requête est trouvé.

--password
forme courte : -p; type : chaîne

Mot de passe MySQL pour l'"--user".

--pid
type : chaîne

Crée le fichier PID donné. L'outil ne démarrera pas si le fichier PID existe déjà et que le PID qu'il contient est différent du PID actuel. Cependant, si le fichier PID existe et que le PID qu'il contient n'est plus en cours d'exécution, l'outil écrasera le fichier PID avec le PID actuel. Le fichier PID est supprimé automatiquement à la sortie de l'outil.

--port
forme courte : -P; type : entier

Numéro de port MySQL.

--progress
type : tableau; par défaut : time,30

Imprime des rapports de progression sur STDERR. L'outil imprime des rapports de progression lors de la lecture des journaux ou des résultats de référence, estimant approximativement le temps restant avant la fin.

La valeur est une liste séparée par des virgules avec deux parties. La première partie peut être un pourcentage, un temps ou des itérations ; la seconde partie spécifie la fréquence à laquelle une mise à jour doit être imprimée, en pourcentage, secondes ou nombre d'itérations.

--[no]read-only
par défaut : oui

Exécute uniquement les requêtes "SELECT"

Create the table used to clear warnings. This is a "meta-table" used to track warnings from previous executions of <command>. See --upgrade-table for details.

--[no]dry-run
default: no

Print the queries that would be executed, but do not execute them. This option is useful for debugging or testing.

--help

--host

Host name of the database server.

--password
short form: -p; type: string

Password for connecting to the database.

--port
short form: -P; type: integer

Port number to use for connection.

--print-only-processed

Print only queries that have been processed. This is useful when comparing query results, as it allows you to see exactly which queries were run.

This option is not available when running in read-only mode, because the tool needs to execute queries to determine if they have been processed. See --read-only.

--read-only
default: yes

In default read-only mode, the tool executes only "SELECT" queries. It does not execute "DROP", "DELETE", "UPDATE", "SET" statements. If "--no-read-only" is specified, all queries are executed: "DROP", "DELETE", "UPDATE", etc. Even when running in default read-only mode, you should use a MySQL user with only "SELECT" privileges to insure against bugs in the tool.

--report
type: Hash; default: hosts, logs, queries, stats

Print these sections of the "REPORT".

--run-time
type: time

How long to run before exiting. By default, the tool runs until it finishes reading the logs or reference results.

--save-results
type: string

Save reference results to this directory. This option works only when one DSN is specified, to generate reference results. When comparing a host to reference results, specify its results directory instead of its DSN. See the second example in the "SYNOPSIS".

Reference results can use a lot of disk space.

--set-vars
type: Array

Set the MySQL variables in this comma-separated list of "variable=value" pairs.

By default, the tool sets:

wait_timeout=10000

Variables specified on the command line override these defaults. For example, specifying "--set-vars wait_timeout=500" overrides the defaultvalue of 10000.

The tool prints a warning and continues if a variable cannot be set.

--socket
short form: -S; type: string

Socket file to use for connection.

--type
type: string; default: slowlog

Type of log files. Valid types are:

VALUE    LOG TYPE
=======  ===========================================
slowlog  MySQL slow log
genlog   MySQL general log
binlog   MySQL binary log (converted by mysqlbinlog)
tcpdump  TCP dump file generated by tcpdump command
rawlog   Custom log with one SQL statement per line
--upgrade-table
type: string; default: percona_schema.pt_upgrade

Use this table to clear warnings. To clear all warnings from previous queries, pt-upgrade executes "SELECT * FROM --upgrade-table LIMIT 1" on each host before executing each query.

The table must be database-qualified. The database and table are automatically created unless "--no-create-upgrade-table" is specified (see "--[no]create-upgrade-table"). If the table does not already exist, it is created with this definition:

CREATE TABLE pt_upgrade (
  id INT NOT NULL PRIMARY KEY
)
--user
short form: -u; type: string

MySQL user if not the current system user.

--version
Show version and exit.
--[no]version-check
default: yes

Check for the latest version of Percona Toolkit, MySQL, and other programs.

This is a standard "check for updates automatically" feature, with two additional features. First, the tool checks its own version and also the versions of the following software: operating system, Percona Monitoring and Management (PMM), MySQL, Perl, MySQL driver for Perl (DBD::mysql), and Percona Toolkit. Second, it checks for and warns about versions with known problems. For example, MySQL 5.5.25 had a critical bug and was re-released as 5.5.25a.

A secure connection to Percona’s Version Check database server is done to perform these checks. Each request is logged by the server, including software version numbers and unique ID of the checked system. The ID is generated by the Percona Toolkit installation script or when the Version Check database call is done for the first time.

Any updates or known problems are printed to STDOUT before the tool's normal output. This feature should never interfere with the normal operation of the tool.

For more information, visit https://www.percona.com/version-check.

--watch-server
type: string

Parse only events for this IP:port for "--type" tcpdump. All other IP addresses are ignored. If not specified, pt-upgrade watches all servers by looking for any IP address using port 3306 or "mysql". If you're watching a server with a non-standard port, this won't work, so you must specify the IP address and port to watch.

If you want to watch a mix of servers, some running on standard port 3306 and some running on non-standard ports, you need to create separate tcpdump outputs for the non-standard port servers and then specify this option for each. At present pt-upgrade cannot auto-detect servers on port 3306 and also be told to watch a server on a non-standard port.

DSN OPTIONS

These DSN options are used to create a DSN. Each option is given like "option=value". The options are case-sensitive, so P and p are not the same option. There cannot be whitespace before or after the "=", and if the value contains whitespace it must be quoted. DSN options are comma-separated. See the percona-toolkit manpage for full details.

  • A

    dsn: charset; copy: yes

    Default character set.

  • D

    dsn: database; copy: yes

    Default database.

  • F

    dsn: mysql_read_default_file; copy: yes

    Only read default options from the given file

  • h

    dsn: host; copy: yes

    Connect to host.

  • L

    copy: yes

    Explicitly enable LOAD DATA LOCAL INFILE.

    For some reason, some vendors compile libmysql without the --enable-local-infile option, which disables the statement. This can lead to weird situations, like the server allowing LOCAL INFILE, but the client throwing exceptions if it's used.

    However, as long as the server allows LOAD DATA, clients can easily re-enable it; See https://dev.mysql.com/doc/refman/en/load-data-local-security.html and http://search.cpan.org/~capttofu/DBD-mysql/lib/DBD/mysql.pm. This option does exactly that.

    Although we've not found a case where turning this option leads to errors or differing behavior, to be on the safe side, this option is not on by default.

  • p

    dsn: password; copy: yes

    Password to use when connecting. If password contains commas they must be escaped with a backslash: "exam\,ple"

  • P

    dsn: port; copy: yes

    Port number to use for connection.

  • S

    dsn: mysql_socket; copy: yes

    Socket file to use for connection.

  • u

    dsn: user; copy: yes

    User for login if not current user.

  • s

    dsn: mysql_ssl; copy: yes

    Create SSL connection

ENVIRONMENT

The environment variable "PTDEBUG" enables verbose debugging output to STDERR. To enable debugging and capture all output to a file, run the tool like:

PTDEBUG=1 pt-upgrade ... > FILE 2>&1

Be careful: debugging output is voluminous and can generate several megabytes of output.

ATTENTION

Using <PTDEBUG> might expose passwords. When debug is enabled, all command line parameters are shown in the output.

SYSTEM REQUIREMENTS

You need Perl, DBI, DBD::mysql, and some core packages that ought to be installed in any reasonably new version of Perl.

NOM

pt-upgrade - met à jour les serveurs MySQL de manière plus sûre

SYNTAXE

pt-upgrade [options] --source DSN --dest DSN

DESCRIPTION

pt-upgrade est un outil qui vous permet de mettre à jour vos serveurs MySQL de manière plus sûre. Il est conçu pour minimiser les risques associés aux mises à jour de bases de données, en fournissant des mécanismes de comparaison et de vérification avant, pendant et après la mise à jour.

CAS D'EMPLOI

Cet outil est particulièrement utile pour les mises à jour majeures de version de MySQL, où les changements entre versions peuvent introduire des incompatibilités ou des comportements inattendus. Il permet de comparer une base de données sur un serveur source avec une base de données sur un serveur de destination, idéalement après avoir effectué une mise à jour sur le serveur de destination.

CONSIDÉRATIONS IMPORTANTES

Assurez-vous que les deux serveurs (source et destination) sont accessibles et que la connectivité réseau est stable. La comparaison peut prendre du temps en fonction de la taille de la base de données.

DIFFÉRENCES DE REQUÊTES

L'outil peut comparer les résultats de requêtes exécutées sur les deux serveurs pour détecter des différences de comportement.

RAPPORT

pt-upgrade génère un rapport détaillé des différences trouvées, qu'il s'agisse de différences de schéma, de données ou de résultats de requêtes.

QUAND LES REQUÊTES SONT SIGNALÉES

Les requêtes sont signalées lorsqu'elles produisent des résultats différents sur le serveur source et le serveur de destination.

SORTIE

La sortie est généralement un rapport textuel des différences identifiées. Des options peuvent permettre de générer la sortie dans différents formats.

STATUT DE SORTIE

Le code de sortie indique le succès ou l'échec de l'opération, et souvent le nombre de différences trouvées.

OPTIONS

De nombreuses options sont disponibles pour personnaliser le comportement de l'outil, telles que la spécification des bases de données à comparer, les requêtes à exécuter, et le format de sortie.

OPTIONS DSN

Les options DSN (Data Source Name) permettent de spécifier les informations de connexion aux serveurs MySQL source et destination (hôte, port, utilisateur, mot de passe, etc.).

ENVIRONNEMENT

Les variables d'environnement peuvent affecter le comportement de l'outil, notamment pour les informations de connexion.

ATTENTION

Utilisez cet outil avec prudence, surtout sur des environnements de production. Il est recommandé de tester l'outil sur un environnement de développement ou de staging avant de l'utiliser en production.

EXIGENCES SYSTÈME

Nécessite Perl et les modules appropriés, ainsi qu'un accès aux serveurs MySQL.
