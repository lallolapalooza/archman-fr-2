NOM

pthreads — POSIX threads

DESCRIPTION

POSIX.1 spécifie un ensemble d'interfaces (fonctions, fichiers d'en-tête) pour la programmation multi-thread couramment appelées threads POSIX, ou Pthreads. Un seul processus peut contenir plusieurs threads, qui exécutent tous le même programme. Ces threads partagent la même mémoire globale (données et tas), mais chaque thread possède sa propre pile (variables automatiques).

POSIX.1 exige également que les threads partagent un ensemble d'autres attributs (c'est-à-dire que ces attributs sont au niveau du processus plutôt que par thread) :

•
identifiant de processus
•
identifiant du processus parent
•
identifiant de groupe de processus et identifiant de session
•
terminal de contrôle
•
identifiants utilisateur et groupe
•
descripteurs de fichiers ouverts
•
verrous d'enregistrement (voir fcntl(2))
•
dispositions de signaux
•
masque de création de mode de fichier (umask(2))
•
répertoire courant (chdir(2)) et répertoire racine (chroot(2))
•
minuteurs d'intervalle (setitimer(2)) et minuteurs POSIX (timer_create(2))
•
valeur nice (setpriority(2))
•
limites de ressources (setrlimit(2))
•
mesures de la consommation de temps CPU (times(2)) et de ressources (getrusage(2))

Outre la pile, POSIX.1 spécifie que divers autres attributs sont distincts pour chaque thread, notamment :

•
identifiant de thread (type de données pthread_t)
•
masque de signaux (pthread_sigmask(3))
•
la variable errno
•
pile de signaux alternative (sigaltstack(2))
•
politique et priorité d'ordonnancement temps réel (sched(7))

Les fonctionnalités Linux suivantes sont également spécifiques à chaque thread :

•
capacités (voir capabilities(7))
•
affinité CPU (sched_setaffinity(2))

Valeurs de retour des fonctions Pthreads

La plupart des fonctions pthreads retournent 0 en cas de succès et un numéro d'erreur en cas d'échec. Les numéros d'erreur qui peuvent être retournés ont la même signification que les numéros d'erreur retournés dans errno par les appels système conventionnels et les fonctions de la bibliothèque C. Notez que les fonctions pthreads ne définissent pas errno. Pour chacune des fonctions pthreads qui peuvent retourner une erreur, POSIX.1-2001 spécifie que la fonction ne peut jamais échouer avec l'erreur EINTR.

Identifiants de thread

Chacun des threads d'un processus possède un identifiant de thread unique (stocké dans le type pthread_t). Cet identifiant est retourné à l'appelant de pthread_create(3), et un thread peut obtenir son propre identifiant de thread en utilisant pthread_self(3).

Les identifiants de thread ne sont garantis d'être uniques qu'à l'intérieur d'un processus. (Dans toutes les fonctions pthreads qui acceptent un identifiant de thread comme argument, cet identifiant fait par définition référence à un thread du même processus que l'appelant.)

Le système peut réutiliser un identifiant de thread après qu'un thread terminé a été joint, ou qu'un thread détaché a terminé. POSIX indique : « Si une application tente d'utiliser un identifiant de thread dont la durée de vie est terminée, le comportement est indéfini. »

Fonctions async-cancel-safe

Une fonction async-cancel-safe est une fonction qui peut être appelée en toute sécurité dans une application où l'annulabilité asynchrone est activée (voir pthread_setcancelstate(3)).

Seules les fonctions suivantes sont requises pour être async-cancel-safe par POSIX.1-2001 et POSIX.1-2008 :

Une implémentation peut également marquer d'autres fonctions non spécifiées dans la norme comme points d'annulation. En particulier, une implémentation marquera probablement toute fonction non standard qui peut bloquer comme point d'annulation. (Cela inclut la plupart des fonctions qui peuvent toucher des fichiers.)

Il est à noter que même si une application n'utilise pas l'annulation asynchrone, l'appel d'une fonction de la liste ci-dessus depuis un gestionnaire de signal asynchrone peut provoquer l'équivalent d'une annulation asynchrone. Le code utilisateur sous-jacent peut ne pas s'attendre à une annulation asynchrone et l'état des données utilisateur peut devenir incohérent. Par conséquent, les signaux doivent être utilisés avec prudence lors de l'entrée dans une région d'annulation différée.

Compilation sous Linux

Sous Linux, les programmes qui utilisent l'API Pthreads doivent être compilés en utilisant cc -pthread.

Implémentations Linux des threads POSIX

Au fil du temps, deux implémentations de threading ont été fournies par la bibliothèque C GNU sous Linux :

LinuxThreads
C'est l'implémentation Pthreads d'origine. Depuis glibc 2.4, cette implémentation n'est plus prise en charge.
NPTL (Native POSIX Threads Library)
C'est l'implémentation Pthreads moderne. Par rapport à LinuxThreads, NPTL offre une conformité plus étroite avec les exigences de la spécification POSIX.1 et de meilleures performances lors de la création d'un grand nombre de threads. NPTL est disponible depuis glibc 2.3.2 et nécessite des fonctionnalités présentes dans le noyau Linux 2.6.

Ces deux implémentations sont dites 1:1, ce qui signifie que chaque thread correspond à une entité de planification du noyau. Les deux implémentations de threading utilisent l'appel système Linux clone(2). Dans NPTL, les primitives de synchronisation de thread (mutex, jointure de thread, etc.) sont implémentées à l'aide de l'appel système Linux futex(2).

LinuxThreads

Les caractéristiques notables de cette implémentation sont les suivantes :

•
En plus du thread principal (initial) et des threads que le programme crée à l'aide de pthread_create(3), l'implémentation crée un thread "gestionnaire". Ce thread gère la création et la terminaison des threads. (Des problèmes peuvent survenir si ce thread est involontairement tué.)
•
Les signaux sont utilisés en interne par l'implémentation. Sur Linux 2.2 et versions ultérieures, les trois premiers signaux temps réel sont utilisés (voir également signal(7)). Sur les anciens noyaux Linux, SIGUSR1 et SIGUSR2 sont utilisés. Les applications doivent éviter l'utilisation de l'ensemble de signaux utilisé par l'implémentation.
•
Les threads ne partagent pas les identifiants de processus. (En fait, les threads LinuxThreads sont implémentés comme des processus qui partagent plus d'informations que d'habitude, mais qui ne partagent pas d'identifiant de processus commun.) Les threads LinuxThreads (y compris le thread gestionnaire) sont visibles comme des processus distincts à l'aide de ps(1).

L'implémentation LinuxThreads dévie de la spécification POSIX.1 de plusieurs manières, y compris les suivantes :

•
Les appels à getpid(2) renvoient une valeur différente dans chaque thread.
•
Les appels à getppid(2) dans des threads autres que le thread principal renvoient l'identifiant du processus du thread gestionnaire ; au lieu de cela, getppid(2) dans ces threads devrait renvoyer la même valeur que getppid(2) dans le thread principal.
•
Lorsqu'un thread crée un nouveau processus enfant à l'aide de fork(2), tout thread devrait pouvoir attendre(2) l'enfant. Cependant, l'implémentation ne permet qu'au thread qui a créé l'enfant de l'attendre(2).
•
Lorsqu'un thread appelle execve(2), tous les autres threads sont terminés (comme requis par POSIX.1). Cependant, le processus résultant a le même PID que le thread qui a appelé execve(2) : il devrait avoir le même PID que le thread principal.
•
Les threads ne partagent pas les identifiants utilisateur et groupe. Cela peut entraîner des complications avec les programmes set-user-ID et peut entraîner des échecs dans les fonctions Pthreads si une application modifie ses identifiants à l'aide de seteuid(2) ou similaire.
•
Les threads ne partagent pas d'identifiant de session et d'identifiant de groupe de processus communs.
•
Les threads ne partagent pas les verrous d'enregistrement créés à l'aide de fcntl(2).
•
Les informations renvoyées par times(2) et getrusage(2) sont par thread plutôt que globales au processus.
•
Les threads ne partagent pas les valeurs d'annulation de sémaphores (voir semop(2)).
•
Les threads ne partagent pas de minuteurs d'intervalle.
•
Les threads ne partagent pas de valeur de priorité commune.
•
POSIX.1 distingue les notions de signaux adressés au processus dans son ensemble et de signaux adressés à des threads individuels. Selon POSIX.1, un signal dirigé au processus (envoyé à l'aide de kill(2), par exemple) doit être géré par un seul thread, arbitrairement sélectionné, au sein du processus. LinuxThreads ne prend pas en charge la notion de signaux dirigés au processus : les signaux ne peuvent être envoyés qu'à des threads spécifiques.
•
Les threads ont des paramètres de pile de signaux alternatifs distincts. Cependant, les paramètres de pile de signaux alternatifs d'un nouveau thread sont copiés à partir du thread qui l'a créé, de sorte que les threads partagent initialement une pile de signaux alternatifs. (Un nouveau thread devrait commencer sans pile de signaux alternatifs définie. Si deux threads traitent des signaux sur leur pile de signaux alternatifs partagée en même temps, des pannes de programme imprévisibles sont susceptibles de se produire.)

NPTL

Avec NPTL, tous les threads d'un processus sont placés dans le même groupe de threads ; tous les membres d'un groupe de threads partagent le même PID. NPTL n'emploie pas de thread gestionnaire.

NPTL utilise en interne les deux premiers signaux temps réel ; ces signaux ne peuvent pas être utilisés dans les applications. Voir nptl(7) pour plus d'informations.

NPTL présente encore au moins une non-conformité avec POSIX.1 :

•
Les threads ne partagent pas de valeur de priorité commune.

Certaines non-conformités NPTL se produisent uniquement avec les anciens noyaux :

•
Les informations renvoyées par times(2) et getrusage(2) sont par thread plutôt que globales au processus (corrigé dans Linux 2.6.9).
•
Les threads ne partagent pas les limites de ressources (corrigé dans Linux 2.6.10).
•
Les threads ne partagent pas de minuteurs d'intervalle (corrigé dans Linux 2.6.12).
•
Seul le thread principal est autorisé à démarrer une nouvelle session à l'aide de setsid(2) (corrigé dans Linux 2.6.16).
•
Seul le thread principal est autorisé à faire du processus un leader de groupe de processus à l'aide de setpgid(2) (corrigé dans Linux 2.6.16).
•
Les threads ont des paramètres de pile de signaux alternatifs distincts. Cependant, les paramètres de pile de signaux alternatifs d'un nouveau thread pthreads(7) — man pages

NOM

pthreads – bibliothèque de threads POSIX (Threads POSIX)

DESCRIPTION

Les threads POSIX (pthreads) sont un ensemble d'API C pour la création et la gestion de threads dans un processus. Un thread est une unité d'exécution qui peut partager le même espace d'adressage qu'un autre thread du même processus. L'utilisation de threads peut améliorer les performances des applications en permettant des calculs parallèles et en gérant plus efficacement les opérations d'E/S.

Le modèle de threading POSIX est défini par la norme IEEE Std 1003.1-2001. La bibliothèque glibc implémente cette norme via une variété d'implémentations de bas niveau. Les deux implémentations historiques importantes sont LinuxThreads et NPTL.

•
LinuxThreads : C'était l'implémentation originale de threads dans Linux. Elle utilisait une sémantique de « processus » pour les threads, ce qui signifie que chaque thread était un processus distinct géré par le noyau. Cela entraînait une surcharge significative et des problèmes de compatibilité avec certaines fonctionnalités POSIX, comme le blocage des signaux.
•
NPTL (Native POSIX Threads Library) : Il s'agit de l'implémentation actuelle par défaut dans Linux. NPTL est une implémentation plus efficace qui utilise des primitives du noyau telles que futex(2) pour une gestion des threads beaucoup plus rapide et plus conforme à la norme POSIX. La conception de NPTL a été influencée par des implémentations de threads similaires dans d'autres systèmes d'exploitation.

Il est important de noter que les piles des threads sont copiées à partir de la pile du thread qui les a créés, de sorte que les threads partagent initialement une pile de signaux alternative (corrigé dans Linux 2.6.16).

Notez les points supplémentaires suivants concernant l'implémentation NPTL :

•
Si la limite de ressources logicielles de taille de pile (voir la description de RLIMIT_STACK dans setrlimit(2)) est définie sur une valeur autre que unlimited, alors cette valeur définit la taille de pile par défaut pour les nouveaux threads. Pour être efficace, cette limite doit être définie avant l'exécution du programme, peut-être en utilisant la commande intégrée du shell ulimit -s (limit stacksize dans le C shell).

Détermination de l'implémentation des threads

Depuis glibc 2.3.2, la commande getconf(1) peut être utilisée pour déterminer l'implémentation des threads du système, par exemple :


bash$ getconf GNU_LIBPTHREAD_VERSION
NPTL 2.3.4

Avec les anciennes versions de glibc, une commande telle que la suivante devrait suffire pour déterminer l'implémentation par défaut des threads :


bash$ $( ldd /bin/ls | grep libc.so | awk '{print $3}' ) | \
                egrep -i 'threads|nptl'
        Native POSIX Threads Library by Ulrich Drepper et al

Sélection de l'implémentation des threads : LD_ASSUME_KERNEL

Sur les systèmes dotés d'une glibc qui prend en charge à la fois LinuxThreads et NPTL (c'est-à-dire glibc 2.3.*), la variable d'environnement LD_ASSUME_KERNEL peut être utilisée pour remplacer le choix par défaut de l'implémentation des threads par le lieur dynamique. Cette variable indique au lieur dynamique de supposer qu'il s'exécute sur une version particulière du noyau. En spécifiant une version du noyau qui ne fournit pas le support requis par NPTL, nous pouvons forcer l'utilisation de LinuxThreads. (La raison la plus probable pour le faire est d'exécuter une application (cassée) qui dépend d'un comportement non conforme dans LinuxThreads.) Par exemple :


bash$ $( LD_ASSUME_KERNEL=2.2.5 ldd /bin/ls | grep libc.so | \
                awk '{print $3}' ) | egrep -i 'threads|nptl'
        linuxthreads-0.10 by Xavier Leroy
