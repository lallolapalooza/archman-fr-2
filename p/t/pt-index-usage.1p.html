NOM

pt-index-usage - Lit les requêtes à partir d'un journal et analyse comment elles utilisent les index.

SYNTAXE

Utilisation : pt-index-usage [OPTIONS] [FICHIERS]

pt-index-usage lit les requêtes à partir de journaux et analyse comment elles utilisent les index.

Analyser les requêtes dans slow.log et afficher les rapports :

pt-index-usage /chemin/vers/slow.log --host localhost

Désactiver les rapports et enregistrer les résultats dans la base de données percona pour une analyse ultérieure :

pt-index-usage slow.log --no-report --save-results-database percona

RISQUES

Percona Toolkit est mature, éprouvé sur le terrain et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Examiner les "BUGS" connus de l'outil
  • Tester l'outil sur un serveur non opérationnel
  • Sauvegarder votre serveur opérationnel et vérifier les sauvegardes

DESCRIPTION

Cet outil se connecte à un serveur de base de données MySQL, parcourt un journal de requêtes et utilise EXPLAIN pour demander à MySQL comment il utilisera chaque requête. Une fois terminé, il imprime un rapport sur les index que les requêtes n'ont pas utilisés.

Le journal de requêtes doit être au format du journal de requêtes lentes de MySQL. Si vous avez besoin d'entrer un format différent, vous pouvez utiliser pt-query-digest pour traduire les formats. Si vous ne spécifiez pas de nom de fichier, l'outil lit depuis STDIN.

L'outil exécute deux étapes. Dans la première étape, l'outil fait l'inventaire de toutes les tables et index de votre base de données, afin de pouvoir comparer les index existants à ceux qui ont été réellement utilisés par les requêtes du journal. Dans la deuxième étape, il exécute EXPLAIN sur chaque requête du journal de requêtes. Il utilise des connexions de base de données séparées pour inventorier les tables et exécuter EXPLAIN, il ouvre donc deux connexions à la base de données.

Si une requête n'est pas un SELECT, il essaie de la transformer en une requête SELECT approximativement équivalente afin de pouvoir être expliquée (EXPLAINed). Ce n'est pas un processus parfait, mais il est suffisamment bon pour être utile.

L'outil saute l'étape EXPLAIN pour les requêtes qui sont des doublons exacts de celles vues précédemment. Il suppose que la même requête générera le même plan EXPLAIN qu'auparavant (ce qui est généralement une hypothèse sûre et généralement bon pour les performances), et incrémente simplement le nombre de fois où les index ont été utilisés. Cependant, les requêtes qui ont la même empreinte mais des sommes de contrôle différentes seront ré-expliquées. Les requêtes qui ont des constantes littérales différentes peuvent avoir des plans d'exécution différents, et il est important de le mesurer.

Après avoir expliqué la requête, il est nécessaire d'essayer de mapper les alias de la requête aux noms de table d'origine. Par exemple, considérez le plan EXPLAIN pour la requête suivante :

SELECT * FROM tbl1 AS foo;

La sortie EXPLAIN montrera l'accès à la table "foo", et cela doit être traduit en "tbl1". Ce processus implique une analyse complexe. Il est généralement très précis, mais il y a une certaine chance qu'il ne fonctionne pas correctement. Si vous trouvez des cas où il échoue, soumettez un rapport de bug et un cas de test reproductible.

Les requêtes qui ne peuvent pas être expliquées entraîneront le blacklistage de toutes les requêtes ultérieures ayant la même empreinte. Ceci afin de réduire le travail qu'elles causent et de les empêcher de continuer à afficher des messages d'erreur.

SORTIE

Après avoir lu tous les événements du journal, l'outil imprime des instructions DROP pour chaque index qui n'a pas été utilisé. Il saute les index pour les tables qui n'ont jamais été consultées par aucune requête du journal, afin d'éviter les faux positifs.

Si vous ne spécifiez pas "--quiet", l'outil affiche également des avertissements concernant les instructions qui ne peuvent pas être expliquées et similaires. Ceux-ci vont vers la sortie d'erreur standard.

Les rapports de progression sont activés par défaut (voir "--progress"). Ceux-ci vont également vers la sortie d'erreur standard.

OPTIONS

Cet outil accepte des arguments de ligne de commande supplémentaires. Reportez-vous à la "SYNTAXE" et aux informations d'utilisation pour plus de détails.

--ask-pass
Demande un mot de passe lors de la connexion à MySQL.
--charset
forme courte : -A ; type : chaîne

Jeu de caractères par défaut. Si la valeur est utf8, définit le mode binaire de Perl sur STDOUT en utf8, passe l'option mysql_enable_utf8 à DBD::mysql et exécute SET NAMES UTF8 après la connexion à MySQL. Toute autre valeur définit le mode binaire sur STDOUT sans la couche utf8 et exécute SET NAMES après la connexion à MySQL.

--config
type : Tableau

Lit cette liste de fichiers de configuration séparés par des virgules ; si spécifié, cela doit être la première option sur la ligne de commande.

--create-save-results-database
Crée la base de données "--save-results-database" si elle n'existe pas.

Si la base de données "--save-results-database" existe déjà et que cette option est spécifiée, la base de données est utilisée et les tables nécessaires sont créées si elles n'existent pas déjà.

--[no]create-views
Crée des vues pour les requêtes d'exemple "--save-results-database".

Plusieurs requêtes d'exemple sont fournies pour interroger les tables de "--save-results-database". Ces requêtes d'exemple sont, par défaut, créées sous forme de vues. Spécifier "--no-create-views" empêche la création de ces vues.

--database
forme courte : -D ; type : chaîne

La base de données à utiliser pour la connexion.

--databases
forme courte : -d ; type : hachage

N'obtient les tables et les index que de cette liste de bases de données séparées par des virgules.

--databases-regex
type : chaîne

N'obtient les tables et les index que des bases de données dont les noms correspondent à cette expression régulière Perl.

--defaults-file
forme courte : -F ; type : chaîne

Ne lit les options mysql que dans le fichier donné. Vous devez donner un chemin absolu.

--drop
type : Hachage ; par défaut : non-unique

Suggère de supprimer uniquement ces types d'index inutilisés.

Par défaut, pt-index-usage ne suggère de supprimer que les index secondaires inutilisés, pas les index primaires ou uniques. Vous pouvez spécifier les types d'index inutilisés que l'outil suggère de supprimer : primary, unique, non-unique, all.

Une instruction "ALTER TABLE" distincte pour chaque type est imprimée. Ainsi, si vous spécifiez "--drop all" et qu'il y a une clé primaire et un index non unique, l'"ALTER TABLE ... DROP" pour chacun sera imprimé sur des lignes séparées.

--empty-save-results-tables
Supprime et recrée toutes les tables préexistantes dans la base de données "--save-results-database". Cela permet de supprimer les informations des exécutions précédentes avant l'exécution actuelle.
--help
Affiche l'aide et quitte.
--host
forme courte : -h ; type : chaîne

Se connecter à l'hôte.

--ignore-databases
type : Hachage

Ignore cette liste de bases de données séparées par des virgules.

--ignore-databases-regex
type : chaîne

Ignore les bases de données dont les noms correspondent à cette expression régulière Perl.

--ignore-tables
type : Hachage

Ignore cette liste de noms de tables séparés par des virgules.

Les noms de tables peuvent être qualifiés avec le nom de la base de données.

--ignore-tables-regex
type : chaîne

Ignore les tables dont les noms correspondent à l'expression régulière Perl.

--mysql_ssl
forme courte : -s ; type : entier

Crée une connexion MySQL SSL.

--password
forme courte : -p ; type : chaîne de caractères

Mot de passe à utiliser lors de la connexion. Si le mot de passe contient des virgules, elles doivent être échappées avec une barre oblique inverse : « exam\,ple »

--port
forme courte : -P ; type : entier

Numéro de port à utiliser pour la connexion.

--progress
type : tableau ; par défaut : time,30

Afficher les rapports de progression sur STDERR. La valeur est une liste séparée par des virgules avec deux parties. La première partie peut être un pourcentage, un temps ou des itérations ; la seconde partie spécifie la fréquence de mise à jour, en pourcentage, secondes ou nombre d'itérations.

--quiet
forme courte : -q

Ne pas afficher d'avertissements. Désactive également « --progress ».

--[no]report
par défaut : oui

Afficher les rapports pour « --report-format ».

Vous pourriez vouloir désactiver les rapports en spécifiant « --no-report » si, par exemple, vous spécifiez également « --save-results-database » et que vous ne souhaitez interroger les tables de résultats que plus tard.

--report-format
type : Tableau ; par défaut : drop_unused_indexes

Actuellement, il n'y a qu'un seul rapport : drop_unused_indexes. Ce rapport affiche les instructions SQL pour supprimer les index inutilisés. Voir également « --drop ».

Voir également « --[no]report ».

--save-results-database
type : DSN

Enregistrer les résultats dans des tables de cette base de données. Les informations sur les index, les requêtes, les tables et leur utilisation sont stockées dans plusieurs tables de la base de données spécifiée. Les tables sont automatiquement créées si elles n'existent pas. Si la base de données n'existe pas, elle peut être créée automatiquement avec « --create-save-results-database ». Dans ce cas, la connexion est initialement créée sans base de données par défaut, puis après la création de la base de données, elle est utilisée.

pt-index-usage exécute des instructions INSERT pour enregistrer les résultats. Par conséquent, vous devez être prudent si vous utilisez cette fonctionnalité sur un serveur de production. Cela pourrait augmenter la charge, causer des problèmes si vous ne souhaitez pas que le serveur soit écrit, ou ainsi de suite.

Après une exécution, vous pouvez interroger les tables d'utilisation pour répondre à diverses questions sur l'utilisation des index. Les tables ont les définitions CREATE TABLE suivantes :

MAGIC_create_indexes :

CREATE TABLE IF NOT EXISTS indexes (
  db           VARCHAR(64) NOT NULL,
  tbl          VARCHAR(64) NOT NULL,
  idx          VARCHAR(64) NOT NULL,
  cnt          BIGINT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY  (db, tbl, idx)
)

MAGIC_create_queries :

CREATE TABLE IF NOT EXISTS queries (
  query_id     CHAR(32) NOT NULL,
  fingerprint  TEXT NOT NULL,
  sample       TEXT NOT NULL,
  PRIMARY KEY  (query_id)
)

MAGIC_create_tables :

CREATE TABLE IF NOT EXISTS tables (
  db           VARCHAR(64) NOT NULL,
  tbl          VARCHAR(64) NOT NULL,
  cnt          BIGINT UNSIGNED NOT NULL DEFAULT 0,
  PRIMARY KEY  (db, tbl)
)

MAGIC_create_index_usage :

CREATE TABLE IF NOT EXISTS index_usage (
  query_id      CHAR(32) NOT NULL,
  db            VARCHAR(64) NOT NULL,
  tbl           VARCHAR(64) NOT NULL,
  idx           VARCHAR(64) NOT NULL,
  cnt           BIGINT UNSIGNED NOT NULL DEFAULT 1,
  UNIQUE INDEX  (query_id, db, tbl, idx)
)

MAGIC_create_index_alternatives :

CREATE TABLE IF NOT EXISTS index_alternatives (
  query_id      CHAR(32) NOT NULL,        -- Cette requête a utilisé
  db            VARCHAR(64) NOT NULL,     -- cet index, mais...
  tbl           VARCHAR(64) NOT NULL,     --
  idx           VARCHAR(64) NOT NULL,     --
  alt_idx       VARCHAR(64) NOT NULL,     -- était une alternative
  cnt           BIGINT UNSIGNED NOT NULL DEFAULT 1,
  UNIQUE INDEX  (query_id, db, tbl, idx, alt_idx),
  INDEX         (db, tbl, idx),
  INDEX         (db, tbl, alt_idx)
)

Les éléments suivants sont des requêtes que vous pouvez exécuter sur ces tables pour répondre à des questions courantes que vous pourriez avoir. Chaque requête est également créée en tant que vue (avec MySQL v5.0 et plus récent) si « --[no]create-views » est vrai (ce qui est le cas par défaut). Les noms des vues sont les chaînes après le préfixe « MAGIC_view_ ».

Question : quelles requêtes utilisent parfois des index différents et quelle est la fraction du temps où chaque index est choisi ? MAGIC_view_query_uses_several_indexes :

SELECT iu.query_id, CONCAT_WS('.', iu.db, iu.tbl, iu.idx) AS idx,
   variations, iu.cnt, iu.cnt / total_cnt * 100 AS pct
FROM index_usage AS iu
   INNER JOIN (
      SELECT query_id, db, tbl, SUM(cnt) AS total_cnt,
        COUNT(*) AS variations
      FROM index_usage
      GROUP BY query_id, db, tbl
      HAVING COUNT(*) > 1
   ) AS qv USING(query_id, db, tbl);

Question : quels index ont beaucoup d'alternatives, c'est-à-dire sont choisis à la place d'autres index, et pour quelles requêtes ? MAGIC_view_index_has_alternates :

SELECT CONCAT_WS('.', db, tbl, idx) AS idx_chosen,
   GROUP_CONCAT(DISTINCT alt_idx) AS alternatives,
   GROUP_CONCAT(DISTINCT query_id) AS queries, SUM(cnt) AS cnt
FROM index_alternatives
GROUP BY db, tbl, idx
HAVING COUNT(*) > 1;

Question : quels index sont considérés comme des alternatives pour d'autres index, et pour quelles requêtes ? MAGIC_view_index_alternates :

SELECT CONCAT_WS('.', db, tbl, alt_idx) AS idx_considered,
   GROUP_CONCAT(DISTINCT idx) AS alternative_to,
   GROUP_CONCAT(DISTINCT query_id) AS queries, SUM(cnt) AS cnt
FROM index_alternatives
GROUP BY db, tbl, alt_idx
HAVING COUNT(*) > 1;

Question : lesquels parmi ceux-ci ne sont jamais choisis par aucune requête, et sont donc superflus ? MAGIC_view_unused_index_alternates :

SELECT CONCAT_WS('.', i.db, i.tbl, i.idx) AS idx,
   alt.alternative_to, alt.queries, alt.cnt
FROM indexes AS i
   INNER JOIN (
      SELECT db, tbl, alt_idx, GROUP_CONCAT(DISTINCT idx) AS alternative_to,
         GROUP_CONCAT(DISTINCT query_id) AS queries, SUM(cnt) AS cnt
      FROM index_alternatives
      GROUP BY db, tbl, alt_idx
      HAVING COUNT(*) > 1
   ) AS alt ON i.db = alt.db AND i.tbl = alt.tbl
     AND i.idx = alt.alt_idx
WHERE i.cnt = 0;

Question : étant donné une table, quels index ont été utilisés, par combien de requêtes, avec combien d'empreintes digitales distinctes ? Y avait-il des alternatives ? Quels index n'ont pas été utilisés ? Vous pouvez modifier la liste SELECT de la requête suivante pour également voir les identifiants de requête concernés. MAGIC_view_index_usage :

SELECT i.idx, iu.usage_cnt, iu.usage_total,
   ia.alt_cnt, ia.alt_total
FROM indexes AS i
   LEFT OUTER JOIN (
      SELECT db, tbl, idx, COUNT(*) AS usage_cnt,
         SUM(cnt) AS usage_total, GROUP_CONCAT(query_id) AS used_by
      FROM index_usage
      GROUP BY db, tbl, idx
   ) AS iu ON i.db=iu.db AND i.tbl=iu.tbl AND i.idx = iu.idx
   LEFT OUTER JOIN (
      SELECT db, tbl, idx, COUNT(*) AS alt_cnt,
         SUM(cnt) AS alt_total,
         GROUP_CONCAT(query_id) AS alt_queries
      FROM index_alternatives
      GROUP BY db, tbl, idx
   ) AS ia ON i.db=ia.db AND i.tbl=ia.tbl AND i.idx = ia.idx;

Question : quels index sur une table donnée sont vitaux pour au moins une requête (il n'y a pas d'alternative) ? MAGIC_view_required_indexes :

SELECT i.db, i.tbl, i.idx, no_alt.queries
FROM indexes AS i
   INNER JOIN (
      SELECT iu.db, iu.tbl, iu.idx,
         GROUP_CONCAT(iu.query_id) AS queries
      FROM index_usage AS iu
         LEFT OUTER JOIN index_alternatives AS ia
            USING(db, tbl, idx)
      WHERE ia.db IS NULL
      GROUP BY iu.db, iu.tbl, iu.idx
   ) AS no_alt ON no_alt.db = i.db AND no_alt.tbl = i.tbl
      AND no_alt.idx = i.idx
ORDER BY i.db, i.tbl, i.idx, no_alt.queries;
--set-vars
type : Tableau

Définir les variables MySQL dans cette liste séparée par des virgules de paires « variable=valeur ».

Par défaut, l'outil définit :

wait_timeout=10000

Les variables spécifiées sur la ligne de commande remplacent ces valeurs par défaut. Par exemple, spécifier « --set-vars wait_timeout=500 » remplace la valeur par défaut de 10000.

L'outil affiche un avertissement et continue si une variable ne peut pas être définie.

forme courte : -t ; type : hachage

Obtenir les index uniquement de cette liste de tables séparées par des virgules.

type : chaîne de caractères

Utilisateur pour la connexion si ce n'est pas l'utilisateur actuel.

--version
Afficher la version et quitter.
--[no]version-check
par défaut : oui

Vérifier la dernière version de Percona Toolkit, MySQL et d'autres programmes.

Il s'agit d'une fonctionnalité standard de « vérifier automatiquement les mises à jour », avec deux fonctionnalités supplémentaires. Premièrement, l'outil vérifie sa propre version ainsi que les versions des logiciels suivants : système d'exploitation, Percona Monitoring and Management (PMM), MySQL, pilote MySQL pour Perl (DBD::mysql) et Percona Toolkit. Deuxièmement, il vérifie et avertit des versions présentant des problèmes connus. Par exemple, MySQL 5.5.25 avait un bug critique et a été réédité sous la version 5.5.25a.

Une connexion sécurisée au serveur de base de données Version Check de Percona est établie pour effectuer ces vérifications. Chaque requête est enregistrée par le serveur, y compris les numéros de version des logiciels et l'identifiant unique du système vérifié. L'identifiant est généré par le script d'installation de Percona Toolkit ou lors du premier appel à la base de données Version Check.

Toutes les mises à jour ou problèmes connus sont affichés sur STDOUT avant la sortie normale de l'outil. Cette fonctionnalité ne devrait jamais interférer avec le fonctionnement normal de l'outil.

Pour plus d'informations, visitez https://www.percona.com/doc/percona-toolkit/LATEST/version-check.html.

OPTIONS DSN

Ces options DSN sont utilisées pour créer un DSN. Chaque option est donnée sous la forme « option=valeur ». Les options sont sensibles à la casse, donc P et p ne sont pas la même option. Il ne peut y avoir d'espace avant ou après le signe « = ».

et si la valeur contient des espaces, elle doit être mise entre guillemets. Les options DSN sont séparées par des virgules. Voir la page de manuel de percona-toolkit pour plus de détails.

  • A

    dsn : charset ; copy : yes

    Jeu de caractères par défaut.

  • D

    dsn : database ; copy : yes

    Base de données à laquelle se connecter.

  • F

    dsn : mysql_read_default_file ; copy : yes

    Lire uniquement les options par défaut du fichier donné

  • h

    dsn : host ; copy : yes

    Se connecter à l'hôte.

  • p

    dsn : password ; copy : yes

    Mot de passe à utiliser lors de la connexion. Si le mot de passe contient des virgules, elles doivent être échappées avec une barre oblique inverse : "exam\,ple"

  • P

    dsn : port ; copy : yes

    Numéro de port à utiliser pour la connexion.

  • S

    dsn : mysql_socket ; copy : yes

    Fichier socket à utiliser pour la connexion.

  • u

    dsn : user ; copy : yes

    Utilisateur pour la connexion si ce n'est pas l'utilisateur actuel.

  • s

    dsn : mysql_ssl ; copy : yes

    Créer une connexion SSL

ENVIRONNEMENT

La variable d'environnement "PTDEBUG" active la sortie de débogage détaillée sur STDERR. Pour activer le débogage et capturer toute la sortie dans un fichier, exécutez l'outil comme ceci :

PTDEBUG=1 pt-index-usage ... > FICHIER 2>&1

Attention : la sortie de débogage est volumineuse et peut générer plusieurs mégaoctets de sortie.

ATTENTION

L'utilisation de <PTDEBUG> peut exposer des mots de passe. Lorsque le débogage est activé, tous les paramètres de la ligne de commande sont affichés dans la sortie.

CONFIGURATION REQUISE

Vous avez besoin de Perl, DBI, DBD::mysql et de certains packages de base qui devraient être installés dans toute version raisonnablement récente de Perl.
