PTHREAD_MUTEX_TIMEDLOCK(3P) Manuel du programmeur POSIX PTHREAD_MUTEX_TIMEDLOCK(3P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pthread_mutex_timedlock — verrouiller un mutex

SYNTAXE

#include <pthread.h>
#include <time.h>
int pthread_mutex_timedlock(pthread_mutex_t *restrict mutex,
    const struct timespec *restrict abstime);

DESCRIPTION

La fonction pthread_mutex_timedlock() verrouille l'objet mutex référencé par mutex. Si le mutex est déjà verrouillé, le thread appelant sera bloqué jusqu'à ce que le mutex devienne disponible, comme avec la fonction pthread_mutex_lock(). Si le mutex ne peut pas être verrouillé sans attendre qu'un autre thread déverrouille le mutex, cette attente sera terminée lorsque le délai d'attente spécifié expirera.

Le délai d'attente expirera lorsque l'heure absolue spécifiée par abstime sera atteinte (c'est-à-dire lorsque la valeur de cette horloge sera égale ou supérieure à abstime), ou si l'heure absolue spécifiée par abstime a déjà été dépassée au moment de l'appel.

Le délai d'attente sera basé sur l'horloge CLOCK_REALTIME. La résolution du délai d'attente sera la résolution de l'horloge sur laquelle il est basé. Le type de données timespec est défini dans l'en-tête <time.h>.

En aucun cas la fonction ne doit échouer avec un délai d'attente si le mutex peut être verrouillé immédiatement. La validité du paramètre abstime ne doit pas être vérifiée si le mutex peut être verrouillé immédiatement.

Par conséquent, en raison des règles d'héritage de priorité (pour les mutex initialisés avec le protocole PRIO_INHERIT), si une attente de mutex chronométrée est terminée parce que son délai d'attente expire, la priorité du propriétaire du mutex sera ajustée si nécessaire pour refléter le fait que ce thread n'est plus parmi les threads en attente du mutex.

Si mutex est un mutex robuste et que le processus contenant le thread propriétaire a terminé tout en détenant le verrou du mutex, un appel à pthread_mutex_timedlock() retournera la valeur d'erreur [EOWNERDEAD]. Si mutex est un mutex robuste et que le thread propriétaire a terminé tout en détenant le verrou du mutex, un appel à pthread_mutex_timedlock() peut retourner la valeur d'erreur [EOWNERDEAD] même si le processus dans lequel réside le thread propriétaire n'a pas terminé. Dans ces cas, le mutex est verrouillé par le thread mais l'état qu'il protège est marqué comme incohérent. L'application doit s'assurer que l'état est rendu cohérent pour la réutilisation et, une fois cela terminé, appeler pthread_mutex_consistent(). Si l'application ne parvient pas à récupérer l'état, elle doit déverrouiller le mutex sans avoir préalablement appelé pthread_mutex_consistent(), après quoi le mutex est marqué comme définitivement inutilisable.

Si mutex ne fait pas référence à un objet mutex initialisé, le comportement est indéfini.

VALEUR DE RETOUR

En cas de succès, la fonction pthread_mutex_timedlock() renvoie zéro ; sinon, un numéro d'erreur est retourné pour indiquer l'erreur.

ERREURS

La fonction pthread_mutex_timedlock() échouera si :

EAGAIN
Le mutex n'a pas pu être acquis car le nombre maximum de verrous récursifs pour mutex a été dépassé.
EDEADLK
Le type de mutex est PTHREAD_MUTEX_ERRORCHECK et le thread actuel possède déjà le mutex.
EINVAL
Le mutex a été créé avec l'attribut de protocole ayant la valeur PTHREAD_PRIO_PROTECT et la priorité du thread appelant est supérieure au plafond de priorité actuel du mutex.
EINVAL
Le processus ou le thread aurait été bloqué, et le paramètre abstime spécifiait une valeur de champ nanosecondes inférieure à zéro ou supérieure ou égale à 1000 millions.
ENOTRECOVERABLE

L'état protégé par le mutex n'est pas récupérable.
EOWNERDEAD

Le mutex est un mutex robuste et le processus contenant le thread propriétaire précédent a terminé tout en détenant le verrou du mutex. Le verrou du mutex sera acquis par le thread appelant et il appartient au nouveau propriétaire de rendre l'état cohérent.
ETIMEDOUT
Le mutex n'a pas pu être verrouillé avant l'expiration du délai spécifié.

La fonction pthread_mutex_timedlock() peut échouer si :

EDEADLK
Une condition de blocage mutuel a été détectée.
EOWNERDEAD

Le mutex est un mutex robuste et le thread propriétaire précédent a terminé tout en détenant le verrou du mutex. Le verrou du mutex sera acquis par le thread appelant et il appartient au nouveau propriétaire de rendre l'état cohérent.

Cette fonction ne retournera pas un code d'erreur de [EINTR].

Les sections suivantes sont informatives.

EXEMPLES

Aucun.

USAGE APPLICATIF

Les applications qui ont supposé que les valeurs de retour non nulles étaient des erreurs devront être mises à jour pour être utilisées avec des mutex robustes, car un retour valide pour un thread acquérant un mutex qui protège un état actuellement incohérent est [EOWNERDEAD]. Les applications qui ne vérifient pas les retours d'erreur, parce qu'elles excluent la possibilité que de telles erreurs surviennent, ne devraient pas utiliser de mutex robustes. Si une application est censée fonctionner avec des mutex normaux et robustes, elle doit vérifier toutes les valeurs de retour pour les conditions d'erreur et, si nécessaire, prendre les mesures appropriées.

RATIONALE

Voir pthread_mutex_lock().
