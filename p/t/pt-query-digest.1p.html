NOM

pt-query-digest - Analyse les requêtes MySQL à partir des logs, de la processlist et de tcpdump.

SYNOPIS

Utilisation : pt-query-digest [OPTIONS] [FICHIERS] [DSN]

pt-query-digest analyse les requêtes MySQL des logs slow, general et binary. Il peut aussi analyser les requêtes issues de "SHOW PROCESSLIST" et les données du protocole MySQL provenant de tcpdump. Par défaut, les requêtes sont groupées par empreinte (fingerprint) et rapportées par ordre décroissant du temps de requête (c'est-à-dire les requêtes les plus lentes en premier). Si aucun "FICHIER" n'est fourni, l'outil lit depuis "STDIN". Le "DSN" optionnel est utilisé pour certaines options comme "--since" et "--until".

Rapporter les requêtes les plus lentes depuis "slow.log" :

pt-query-digest slow.log

Rapporter les requêtes les plus lentes de la processlist sur host1 :

pt-query-digest --processlist h=host1

Capturer les données du protocole MySQL avec tcpdump, puis rapporter les requêtes les plus lentes :

tcpdump -s 65535 -x -nn -q -tttt -i any -c 1000 port 3306 > mysql.tcp.txt
pt-query-digest --type tcpdump mysql.tcp.txt

Sauvegarder les données de requêtes de "slow.log" vers host2 pour une revue ultérieure et une analyse de tendances :

pt-query-digest --review h=host2 --no-report slow.log

DESCRIPTION

pt-query-digest est un outil sophistiqué mais facile à utiliser pour analyser les requêtes MySQL. Il peut analyser les requêtes provenant des logs MySQL slow, general et binary. (Les logs binaires doivent d'abord être convertis en texte, voir "--type"). Il peut également utiliser "SHOW PROCESSLIST" et les données du protocole MySQL provenant de tcpdump. Par défaut, l'outil rapporte quelles requêtes sont les plus lentes, et donc les plus importantes à optimiser. Des rapports plus complexes et personnalisés peuvent être créés en utilisant des options comme "--group-by", "--filter", et "--embedded-attributes".

L'analyse des requêtes est une meilleure pratique qui devrait être effectuée fréquemment. Pour faciliter cela, pt-query-digest dispose de deux fonctionnalités : la revue des requêtes ("--review") et l'historique des requêtes ("--history"). Lorsque l'option "--review" est utilisée, toutes les requêtes uniques sont sauvegardées dans une base de données. Lorsque l'outil est exécuté à nouveau avec "--review", les requêtes marquées comme revues dans la base de données ne sont pas imprimées dans le rapport. Cela met en évidence les nouvelles requêtes qui nécessitent une revue. Lorsque l'option "--history" est utilisée, les métriques des requêtes (temps de requête, temps de verrouillage, etc.) pour chaque requête unique sont sauvegardées dans une base de données. Chaque fois que l'outil est exécuté avec "--history", plus de données historiques sont sauvegardées, ce qui peut être utilisé pour suivre et analyser les performances des requêtes au fil du temps.

ATTRIBUTS

pt-query-digest fonctionne sur des événements, qui sont une collection d'attributs clé-valeur appelés attributs. Vous reconnaîtrez la plupart des attributs immédiatement : "Query_time", "Lock_time", et ainsi de suite. Vous pouvez juste regarder un log lent et les voir. Cependant, il y en a certains qui n'existent pas dans le log lent, et les logs lents peuvent en fait inclure différents types d'attributs (par exemple, vous pourriez avoir un serveur avec les patchs Percona).

Voir "RÉFÉRENCE DES ATTRIBUTS" vers la fin de cette documentation pour une liste des attributs courants et spécifiques à "--type". Une familiarité avec ces attributs est nécessaire pour travailler avec "--filter", "--ignore-attributes", et d'autres options liées aux attributs.

Avec une utilisation créative de "--filter", vous pouvez créer de nouveaux attributs dérivés des attributs existants. Par exemple, pour créer un attribut appelé "Row_ratio" pour examiner le ratio de "Rows_sent" à "Rows_examined", spécifiez un filtre comme :

--filter '($event->{Row_ratio} = $event->{Rows_sent} / ($event->{Rows_examined})) && 1'

L'astuce "&& 1" est nécessaire pour créer une syntaxe valide sur une seule ligne qui est toujours vraie, même si l'assignation s'évalue de manière fausse. Le nouvel attribut apparaîtra automatiquement dans la sortie :

# Row ratio        1.00    0.00      1    0.50      1    0.71    0.50

Les attributs créés de cette manière peuvent être spécifiés pour "--order-by" ou toute option nécessitant un attribut.

SORTIE

La sortie par défaut "--output" est un rapport d'analyse de requêtes. L'option "--[no]report" contrôle si ce rapport est imprimé ou non. Parfois, vous voudrez peut-être analyser toutes les requêtes mais supprimer le rapport, par exemple lors de l'utilisation de "--review" ou "--history".

Il y a un paragraphe pour chaque classe de requêtes analysées. Une "classe" de requêtes a toutes la même valeur pour l'attribut "--group-by" qui est "fingerprint" par défaut. (Voir "ATTRIBUTS".) Une empreinte est une version abstraite du texte de la requête avec les littéraux supprimés, les espaces blancs réduits, etc. Le rapport est formaté de manière à pouvoir être facilement copié dans des e-mails sans retour à la ligne, et toutes les lignes non-requêtes commencent par un commentaire, de sorte que vous pouvez l'enregistrer dans un fichier .sql et l'ouvrir dans votre éditeur de texte préféré avec coloration syntaxique. Il y a un profil de temps de réponse au début.

La sortie décrite ici est contrôlée par "--report-format". Cette option vous permet de spécifier quoi imprimer et dans quel ordre. La sortie par défaut dans l'ordre par défaut est décrite ici.

Le rapport, par défaut, commence par un paragraphe sur l'ensemble de l'exécution de l'analyse. Les informations sont très similaires à ce que vous verrez pour chaque classe de requêtes dans le log, mais il manque certaines informations qui seraient trop coûteuses à conserver globalement pour l'analyse. Il contient également des statistiques sur l'exécution du code lui-même, telles que l'utilisation du CPU et de la mémoire, la date et l'heure locales de l'exécution, et une liste des fichiers d'entrée lus/analysés.

Suit le profil du temps de réponse sur les événements. C'est une vue très résumée des événements uniques dans le rapport de requêtes détaillé qui suit. Il contient les colonnes suivantes :

Colonne       Signification
============  ==========================================================
Rang          Le rang de la requête dans l'ensemble des requêtes analysées
ID de requête Le fingerprint de la requête
Temps de réponse Le temps de réponse total, et le pourcentage du total
Appels        Le nombre de fois où cette requête a été exécutée
R/Appel       Le temps de réponse moyen par exécution
V/M           Le ratio Variance-à-moyenne du temps de réponse
Élément       La requête distillée

Une ligne finale dont le rang est indiqué comme MISC contient des statistiques agrégées sur les requêtes qui n'ont pas été incluses dans le rapport, en raison d'options telles que "--limit" et "--outliers". Pour plus de détails sur le ratio variance-à-moyenne, veuillez consulter http://en.wikipedia.org/wiki/Index_of_dispersion.

Ensuite, le rapport détaillé des requêtes est imprimé. Chaque requête apparaît dans un paragraphe. Voici un exemple, légèrement reformaté pour que 'perldoc' ne retourne pas à la ligne dans un terminal. Ce qui suit sera tout un paragraphe, mais nous allons le diviser pour le commenter.

# Requête 2 : 0.01 QPS, 0.02x conc, ID 0xFDEA8D2993C9CAF3 à l'octet 160665

Cette ligne identifie le numéro séquentiel de la requête dans l'ordre de tri spécifié par "--order-by". Ensuite, il y a les requêtes par seconde, et la concurrence approximative pour cette requête (calculée comme une fonction de la durée et du temps total de Query_time). Ensuite, il y a un ID de requête. Cet ID est une version hexadécimale de la somme de contrôle de la requête dans la base de données, si vous utilisez "--review". Vous pouvez sélectionner les détails de la requête revue à partir de la base de données avec une requête comme "SELECT .... WHERE checksum=0xFDEA8D2993C9CAF3".

Si vous enquêtez sur le rapport et souhaitez imprimer chaque échantillon d'une requête particulière, alors le filtre suivant peut

be helpful:

pt-query-digest slow.log           \
   --no-report                     \
   --output slowlog                \
   --filter '$event->{fingerprint} \
        && make_checksum($event->{fingerprint}) eq "FDEA8D2993C9CAF3"'

Notez que vous devez supprimer le préfixe "0x" de la somme de contrôle.

Enfin, si vous souhaitez trouver un exemple de la requête dans le fichier journal, il y a le décalage d'octet où vous pouvez chercher. (Ce n'est pas toujours précis, en raison de certaines anomalies dans le format du journal lent, mais c'est généralement correct.) La position fait référence à l'échantillon le plus mauvais, ce que nous verrons plus en détail ci-dessous.

Vient ensuite le tableau des métriques concernant cette classe de requêtes.

#           pct   total    min    max     avg     95%  stddev  median
# Count       0       2
# Exec time  13   1105s   552s   554s    553s    554s      2s    553s
# Lock time   0   216us   99us  117us   108us   117us    12us   108us
# Rows sent  20   6.26M  3.13M  3.13M   3.13M   3.13M   12.73   3.13M
# Rows exam   0   6.26M  3.13M  3.13M   3.13M   3.13M   12.73   3.13M

La première ligne contient les en-têtes de colonne du tableau. Le pourcentage est le pourcentage du total pour l'ensemble de l'exécution de l'analyse, et le total est la valeur réelle de la métrique spécifiée. Par exemple, dans ce cas, nous pouvons voir que la requête a été exécutée 2 fois, ce qui représente 13 % du nombre total de requêtes dans le fichier. Les colonnes min, max et avg s'expliquent d'elles-mêmes. La colonne 95 % montre le 95e centile ; 95 % des valeurs sont inférieures ou égales à cette valeur. L'écart type indique à quel point les valeurs sont regroupées. L'écart type et la médiane sont tous deux calculés à partir du 95e centile, en écartant les valeurs extrêmement grandes.

Les statistiques stddev, median et 95e percentile sont approximatives. Des statistiques exactes nécessitent de conserver chaque valeur vue, de les trier et d'effectuer des calculs dessus. Cela consomme beaucoup de mémoire. Pour éviter cela, nous conservons 1000 classes, chacune étant 5 % plus grande que la précédente, allant de 0,000001 à un très grand nombre. Lorsque nous voyons une valeur, nous incrémentons la classe dans laquelle elle tombe. Ainsi, nous avons une mémoire fixe par classe de requêtes. L'inconvénient est l'imprécision, qui tombe généralement dans la plage de 5 %.

Ensuite, nous avons les statistiques sur les utilisateurs, les bases de données et la période pour la requête.

# Users       1   user1
# Databases   2     db1(1), db2(1)
# Time range 2008-11-26 04:55:18 to 2008-11-27 00:15:15

Les utilisateurs et les bases de données sont présentés sous forme de nombre de valeurs distinctes, suivies des valeurs. S'il n'y en a qu'une, elle est affichée seule ; s'il y en a plusieurs, nous affichons chacune des plus fréquentes, suivie du nombre de fois où elle apparaît.

# Query_time distribution
#   1us
#  10us
# 100us
#   1ms
#  10ms  #####
# 100ms  ####################
#    1s  ##########
#  10s+

Les temps d'exécution montrent un graphique logarithmique du regroupement des temps. Chaque requête va dans l'une des "classes" et est comptée. Les classes sont des puissances de dix. La première classe regroupe toutes les valeurs dans la "plage de la microseconde unique" -- c'est-à-dire moins de 10 µs. La deuxième est les "dizaines de microsecondes", qui va de 10 µs jusqu'à (mais sans inclure) 100 µs ; et ainsi de suite. L'attribut représenté peut être modifié en spécifiant "--report-histogram", mais il est limité aux attributs basés sur le temps.

# Tables
#    SHOW TABLE STATUS LIKE 'table1'\G
#    SHOW CREATE TABLE `table1`\G
# EXPLAIN
SELECT * FROM table1\G

Cette section est une commodité : si vous essayez d'optimiser les requêtes que vous voyez dans le journal lent, vous voudrez probablement examiner la structure et la taille de la table. Ce sont des commandes prêtes à copier-coller pour le faire.

Enfin, nous voyons un échantillon des requêtes de cette classe de requêtes. Ce n'est pas un échantillon aléatoire. C'est la requête qui a eu les performances les plus mauvaises, selon l'ordre de tri donné par "--order-by". Vous verrez normalement une ligne commentée "# EXPLAIN" juste avant, afin que vous puissiez copier-coller la requête pour examiner son plan EXPLAIN. Mais pour les requêtes autres que SELECT, ce n'est pas possible, donc l'outil essaie de transformer la requête en une requête SELECT à peu près équivalente, et l'ajoute ci-dessous.

Si vous souhaitez trouver cet exemple d'événement dans le journal, utilisez le décalage mentionné ci-dessus, et quelque chose comme ce qui suit :

tail -c +<offset> /path/to/file | head

Voir également "--report-format".

REVISION DE REQUETE

Une "révision" de requête est le processus de stockage de toutes les empreintes de requêtes analysées. Cela présente plusieurs avantages :

  • Vous pouvez ajouter des métadonnées aux classes de requêtes, comme les marquer pour un suivi, ajouter des notes aux requêtes ou les marquer avec un ID de ticket pour votre système de suivi des problèmes.
  • Vous pouvez vous référer aux valeurs stockées lors des exécutions ultérieures afin de savoir si vous avez déjà vu une requête auparavant. Cela peut vous aider à réduire le travail en double.
  • Vous pouvez stocker des données historiques telles que le nombre de lignes, les temps de requête et généralement tout ce que vous pouvez voir dans le rapport.

Pour utiliser cette fonctionnalité, exécutez pt-query-digest avec l'option "--review". Il stockera les empreintes et d'autres informations dans la table que vous spécifiez. La prochaine fois que vous l'exécuterez avec la même option, il fera ce qui suit :

  • Il ne vous montrera pas les requêtes que vous avez déjà révisées. Une requête est considérée comme déjà révisée si vous avez défini une valeur pour la colonne "reviewed_by". (Si vous souhaitez voir les requêtes que vous avez déjà révisées, utilisez l'option "--report-all".)
  • Les requêtes que vous avez révisées et qui n'apparaissent pas dans la sortie entraîneront des lacunes dans la séquence des numéros de requête sur la première ligne de chaque paragraphe. Et la valeur que vous avez spécifiée pour "--limit" sera toujours respectée. Ainsi, si vous avez révisé toutes les requêtes du top 10 et que vous demandez le top 10, vous ne verrez rien dans la sortie.
  • Si vous souhaitez voir les requêtes que vous avez déjà révisées, vous pouvez spécifier "--report-all". Vous verrez alors la sortie d'analyse normale, mais vous verrez également les informations de la table de révision, juste en dessous du graphique des temps d'exécution. Par exemple, 
    # Review information
#      comments: really bad IN() subquery, fix soon!
#    first_seen: 2008-12-01 11:48:57
#   jira_ticket: 1933
#     last_seen: 2008-12-18 11:49:07
#      priority: high
#   reviewed_by: xaprb
#   reviewed_on: 2008-12-18 15:03:11

    Ces métadonnées sont utiles car, à mesure que vous analysez vos requêtes, vos commentaires sont intégrés directement dans le rapport.

EMPREINTES

Une empreinte de requête est la forme abstraite d'une requête, ce qui permet de regrouper des requêtes similaires. L'abstraction d'une requête supprime les valeurs littérales, normalise les espaces blancs, etc. Par exemple, considérons ces deux requêtes :

SELECT name, password FROM user WHERE id='12823';
select name,   password from user
   where id=5;

Ces deux requêtes deviendront :

select name, password from user where id=?

Une fois l'empreinte de la requête connue, nous pouvons parler d'une requête comme si elle représentait toutes les requêtes similaires.

Ce que "pt-query-digest" fait est analogue à une instruction GROUP BY en SQL. (Mais notez que "colonnes multiples" ne définit pas un regroupement multi-colonnes ; cela définit plusieurs rapports !) Si votre ligne de commande ressemble à ceci :

pt-query-digest               \
    --group-by fingerprint    \
    --order-by Query_time:sum \
    --limit 10                \
    slow.log

Le pseudo-SQL correspondant ressemble à ceci :

SELECT WORST(query BY Query_time), SUM(Query_time), ...
FROM /path/to/slow.log
GROUP BY FINGERPRINT(query)
ORDER BY SUM(Query_time) DESC
LIMIT 10

Vous pouvez également utiliser la valeur "distill", qui est une sorte de super-empreinte. Voir "--group-by" pour plus de détails.

L'empreinte des requêtes prend en charge de nombreux cas spéciaux, qui se sont avérés nécessaires dans le monde réel. Par exemple, une liste "IN" avec 5 littéraux est en réalité équivalente à une avec 4 littéraux, de sorte que les listes de littéraux sont réduites à un seul. Si vous trouvez quelque chose qui n'est pas correctement empreint, veuillez soumettre un rapport de bug avec un cas de test reproductible.

Voici une liste des transformations lors de l'empreinte, qui peut ne pas être exhaustive :

  • Regrouper toutes les requêtes SELECT de mysqldump ensemble, même si elles portent sur des tables différentes. Il en va de même pour toutes les requêtes de pt-table-checksum.
  • Raccourcir les instructions INSERT multi-valeurs en une seule liste VALUES().
  • Supprimer les commentaires.
  • Abstraire les bases de données dans les instructions USE, de sorte que toutes les instructions USE soient regroupées ensemble.
  • Remplacer tous les littéraux, tels que les chaînes entre guillemets. Pour des raisons d'efficacité, le code qui remplace les nombres littéraux est quelque peu non sélectif et peut remplacer certaines choses comme des nombres alors qu'elles ne le sont pas vraiment. Les littéraux hexadécimaux sont également remplacés. NULL est traité comme un littéral. Les nombres incorporés dans les identifiants sont également remplacés, de sorte que les tables nommées de manière similaire seront empreintes avec les mêmes valeurs (par exemple, users_2009 et users_2010 seront empreintes identiquement).
  • Réduire tout espace blanc à un seul espace.
  • Mettre tout le texte de la requête en minuscules.
  • Remplacer tous les littéraux à l'intérieur des listes IN() et VALUES() par un seul espace réservé, quelle que soit la cardinalité.
  • Réduire plusieurs requêtes UNION identiques en une seule.

OPTIONS

Cet outil accepte des arguments de ligne de commande supplémentaires. Référez-vous à la "SYNTAXE" et aux informations d'utilisation pour les détails.

--ask-pass
Demande un mot de passe lors de la connexion à MySQL.
--attribute-aliases
type: tableau; par défaut: db|Schema

Liste d'attribut|alias, etc.

Certains attributs ont plusieurs noms, comme db et Schema. Si un événement n'a pas l'attribut principal, pt-query-digest recherche un attribut alias. S'il trouve un alias, il crée l'attribut principal avec la valeur de l'attribut alias et supprime l'attribut alias.

Si l'événement a l'attribut principal, tous les attributs alias sont supprimés.

Cela permet de simplifier les attributs d'événements afin qu'il n'y ait pas, par exemple, de lignes de rapport pour db et Schema.

--attribute-value-limit
type: entier; par défaut: 0

Une limite de sécurité pour les valeurs d'attribut.

Cette option traite les bogues dans la fonctionnalité de journalisation lente qui provoquent de grandes valeurs pour l'attribut

es. Si la valeur de l'attribut est supérieure à celle-ci, la dernière valeur vue pour cette classe de requête est utilisée à la place. Désactivé par défaut.

--charset
forme courte : -A ; type : chaîne de caractères

Jeu de caractères par défaut. Si la valeur est utf8, définit le mode binaire de Perl sur STDOUT à utf8, transmet l'option mysql_enable_utf8 à DBD::mysql et exécute SET NAMES UTF8 après la connexion à MySQL. Toute autre valeur définit le mode binaire sur STDOUT sans la couche utf8 et exécute SET NAMES après la connexion à MySQL.

--config
type : Tableau

Lire cette liste de fichiers de configuration séparés par des virgules ; si spécifié, cela doit être la première option sur la ligne de commande.

--[no]continue-on-error
par défaut : oui

Continuer l'analyse même en cas d'erreur. L'outil ne continuera pas indéfiniment : il s'arrête une fois qu'un processus provoque 100 erreurs, auquel cas il y a probablement un bug dans l'outil ou l'entrée est invalide.

--[no]create-history-table
par défaut : oui

Créer la table "--history" si elle n'existe pas.

Cette option provoque la création de la table spécifiée par "--history" avec la structure par défaut montrée dans la documentation pour "--history".

--[no]create-review-table
par défaut : oui

Créer la table "--review" si elle n'existe pas.

Cette option provoque la création de la table spécifiée par "--review" avec la structure par défaut montrée dans la documentation pour "--review".

--daemonize
Se séparer et passer en arrière-plan, détaché du shell. Systèmes d'exploitation POSIX uniquement.
--database
forme courte : -D ; type : chaîne de caractères

Se connecter à cette base de données.

--defaults-file
forme courte : -F ; type : chaîne de caractères

Lire uniquement les options mysql à partir du fichier donné. Vous devez fournir un chemin d'accès absolu.

--embedded-attributes
type : tableau

Deux motifs regex Perl pour capturer des pseudo-attributs intégrés dans les requêtes.

Les attributs intégrés peuvent être des paires attribut-valeur spéciales que vous avez cachées dans des commentaires. Le premier motif doit correspondre à l'ensemble des attributs (s'il y en a plusieurs). Le second motif doit correspondre et capturer les paires attribut-valeur du premier motif.

Par exemple, supposons que votre requête ressemble à ceci :

SELECT * from users -- file: /login.php, line: 493;

Vous pourriez exécuter pt-query-digest avec l'option suivante :

pt-query-digest --embedded-attributes ' -- .*','(\w+): ([^\,]+)'

La première expression régulière capture l'intégralité du commentaire :

" -- file: /login.php, line: 493;"

La seconde la divise en paires attribut-valeur et les ajoute à l'événement :

ATTRIBUTE  VALEUR
=========  ==========
file       /login.php
line       493

NOTE : Toutes les virgules dans les motifs regex doivent être échappées avec \ sinon le motif sera cassé.

--expected-range
type : tableau ; par défaut : 5,10

Expliquer les éléments lorsqu'il y en a plus ou moins que prévu.

Définit le nombre d'éléments attendus dans le rapport donné par "--[no]report", tel que contrôlé par "--limit" et "--outliers". S'il y a plus ou moins d'éléments dans le rapport, chacun expliquera pourquoi il a été inclus.

--explain
type : DSN

Exécuter EXPLAIN pour la requête d'échantillon avec ce DSN et imprimer les résultats.

Cela ne fonctionne que lorsque "--group-by" inclut fingerprint. Il fait exécuter EXPLAIN à pt-query-digest et inclure la sortie dans le rapport. Par mesure de sécurité, les requêtes qui semblent avoir une sous-requête que EXPLAIN exécutera ne seront pas expliquées. Ce sont généralement des requêtes de type "table dérivée" de la forme

select ... from ( select .... ) der;

Les résultats de EXPLAIN sont imprimés sous forme de format vertical complet dans le rapport d'événement, qui apparaît à la fin de chaque rapport d'événement dans un style vertical ("\G") comme MySQL l'imprime.

--filter
type : chaîne de caractères

Supprimer les événements pour lesquels ce code Perl ne renvoie pas vrai.

Cette option est une chaîne de code Perl ou un fichier contenant du code Perl qui est compilé en une sous-routine avec un argument : $event. C'est un hashref. Si la valeur donnée est un fichier lisible, alors pt-query-digest lit l'intégralité du fichier et utilise son contenu comme code. Le fichier ne doit pas contenir de ligne shebang (#!/usr/bin/perl).

Si le code renvoie vrai, la chaîne de callbacks continue ; sinon, elle se termine. Le code est la dernière instruction de la sous-routine autre que "return $event". Le modèle de sous-routine est :

sub { $event = shift; filter && return $event; }

Les filtres donnés sur la ligne de commande sont enveloppés entre parenthèses comme "( filter )". Pour des filtres complexes et multi-lignes, vous devez placer le code dans un fichier afin qu'il ne soit pas enveloppé entre parenthèses. Dans les deux cas, le filtre doit produire un code syntaxiquement valide compte tenu du modèle. Par exemple, une branche if-else donnée sur la ligne de commande ne serait pas valide :

--filter 'if () { } else { }'  # FAUX

Comme il est donné sur la ligne de commande, la branche if-else serait enveloppée entre parenthèses, ce qui n'est pas syntaxiquement valide. Pour accomplir quelque chose de plus complexe comme ceci, il faudrait placer le code dans un fichier, par exemple filter.txt :

my $event_ok; if (...) { $event_ok=1; } else { $event_ok=0; } $event_ok

Spécifiez ensuite "--filter filter.txt" pour lire le code à partir de filter.txt.

Si le code du filtre ne compile pas, pt-query-digest mourra avec une erreur. Si le code du filtre compile, une erreur peut toujours se produire à l'exécution si le code tente de faire quelque chose de mal (comme faire correspondre un motif à une valeur indéfinie). pt-query-digest ne fournit aucune protection, donc codez avec précaution !

Un exemple de filtre qui supprime tout sauf les instructions SELECT :

--filter '$event->{arg} =~ m/^select/i'

Ceci est compilé en une sous-routine comme suit :

sub { $event = shift; ( $event->{arg} =~ m/^select/i ) && return $event; }

Il est permis que le code ait des effets secondaires (pour modifier $event).

Voir "ATTRIBUTES REFERENCE" pour une liste d'attributs courants et spécifiques à "--type".

Voici d'autres exemples de code de filtre :

Hôte/IP correspond à domain.com
--filter '($event->{host} || $event->{ip} || "") =~ m/domain.com/'

Parfois, MySQL enregistre l'hôte où l'IP est attendue. Par conséquent, nous vérifions les deux.

Utilisateur correspond à john
--filter '($event->{user} || "") =~ m/john/'
Plus d'une alerte
--filter '($event->{Warning_count} || 0) > 1'
Requête effectue un scan complet de table ou un join complet
--filter '(($event->{Full_scan} || "") eq "Yes") || (($event->{Full_join} || "") eq "Yes")'
La requête n'a pas été servie depuis le cache de requêtes
--filter '($event->{QC_Hit} || "") eq "No"'
La requête est de 1 Mo ou plus grande
--filter '$event->{bytes} >= 1_048_576'

Comme "--filter" vous permet de modifier $event, vous pouvez l'utiliser pour faire d'autres choses, comme créer de nouveaux attributs. Voir "ATTRIBUTS" pour un exemple.

--group-by
type : Tableau ; par défaut : fingerprint

Quel attribut des événements regrouper.

En général, vous pouvez regrouper les requêtes en classes basées sur n'importe quel attribut de la requête, comme "user" ou "db", ce qui vous montrera par défaut quels utilisateurs et quelles bases de données reçoivent le plus de "Query_time". L'attribut par défaut, "fingerprint", regroupe les requêtes similaires et abstraites en classes ; voir ci-dessous et aussi "FINGERPRINTS".

Un rapport est imprimé pour chaque valeur "--group-by" (sauf si "--no-report" est donné). Par conséquent, "--group-by user,db" signifie "rapport sur les requêtes avec le même utilisateur et rapport sur les requêtes avec la même base de données" ; cela ne signifie pas "rapport sur les requêtes avec le même utilisateur et la même base de données". Voir aussi "OUTPUT".

Chaque valeur doit avoir une valeur correspondante dans la même position dans "--order-by". Cependant, ajouter des valeurs à "--group-by" ajoutera automatiquement des valeurs à "--order-by", pour votre commodité.

Il existe plusieurs valeurs magiques qui provoquent une analyse de données supplémentaire avant le regroupement :

fingerprint
Cela provoque l'identification des événements pour abstraire les requêtes dans une forme canonique, qui est ensuite utilisée pour regrouper les événements ensemble dans une classe. Voir "FINGERPRINTS" pour en savoir plus sur l'identification.
tables
Cela provoque l'inspection des événements pour ce qui semble être des tables, puis leur agrégation par cela. Notez qu'une requête contenant deux tables ou plus sera comptée autant de fois qu'il y a de tables ; ainsi, un join contre deux tables comptera le Query_time contre les deux tables.
distill
Ceci est une sorte d'empreinte digitale super qui réduit les requêtes en une suggestion de ce qu'elles font, comme "INSERT SELECT table1 table2".

type : Tableau ; défaut : Query_time:sum

Ceci est une liste d'expressions de tri séparées par des virgules, une pour chaque attribut de "--group-by". Aggregate Meaning
========= ============================
sum       Somme/valeur totale de l'attribut
min       Valeur minimale de l'attribut
max       Valeur maximale de l'attribut
cnt       Fréquence/nombre de la requête

Par exemple, la valeur par défaut "Query_time:sum" signifie que les requêtes dans le rapport d'analyse des requêtes seront ordonnées (triées) par leur temps d'exécution total ("Exec time"). "Query_time:max" ordonne les requêtes par leur temps d'exécution maximal, de sorte que la requête avec le plus grand "Query_time" unique sera listée en premier. "cnt" se réfère davantage à la fréquence de la requête dans son ensemble, à sa fréquence d'apparition ; "Count" est sa ligne correspondante dans le rapport d'analyse des requêtes. Donc, tout attribut et "cnt" devrait produire le même rapport dans lequel les requêtes sont triées par le nombre de fois où elles sont

Lorsque vous analysez des logs généraux ("--type" "genlog"), la valeur par défaut de "--order-by" devient "Query_time:cnt". Les logs généraux ne rapportent pas les temps de requête, donc seul l'agrégat "cnt" a du sens car tous les temps de requête sont nuls.

Si vous spécifiez un attribut qui n'existe pas dans les événements, pt-query-digest revient à la valeur par défaut "Query_time:sum" et affiche un avis au début du rapport pour chaque classe de requête. -temps « s'exécute. Les valeurs possibles pour cette option sont les suivantes :

Le premier horodatage vu est mémorisé, et chaque horodatage après cela est comparé au premier pour déterminer combien de temps de journal s'est écoulé. Par exemple, si le premier horodatage vu est « 12:00:00 » et le suivant est « 12:01:30 », cela fait 1 minute et 30 secondes de temps de journal. L'outil lira les événements jusqu'à ce que le temps de journal soit supérieur ou égal à la valeur spécifiée de « --run-time ».

Comme les horodatages dans les journaux ne sont pas toujours affichés, ou pas toujours fréquemment, ce mode varie en précision.

intervalle
« --run-time » spécifie des intervalles de temps de journal dans lesquels les événements sont divisés et les rapports sont générés. Ce mode est différent des autres car il ne spécifie pas combien de temps exécuter. La valeur de « --run-time » doit être un intervalle qui divise uniformément en minutes, heures ou jours. Par exemple, « 5m » divise uniformément en heures (60/5=12, donc 12 intervalles de 5 minutes par heure) mais « 7m » ne le fait pas (60/7=8.6).

Spécifier « --run-time-mode interval --run-time 30m --iterations 0 » est similaire à spécifier « --run-time-mode clock --run-time 30m --iterations 0 ». Dans ce dernier cas, pt-query-digest s'exécutera indéfiniment, produisant des rapports toutes les 30 minutes, mais cela ne fonctionne efficacement qu'avec des entrées continues comme STDIN et la liste de processus. Pour des entrées fixes, comme les fichiers journaux, le premier exemple produit plusieurs rapports en divisant le journal en intervalles de 30 minutes basés sur les horodatages.

Les intervalles sont calculés à partir de la seconde/minute/heure zéro dans laquelle se produit un horodatage, et non à partir de l'heure qu'il spécifie. Par exemple, avec des intervalles de 30 minutes et un horodatage de « 12:10:30 », l'intervalle n'est pas « 12:10:30 » à « 12:40:30 », mais « 12:00:00 » à « 12:29:59 ». Ou, avec des intervalles d'une heure, c'est « 12:00:00 » à « 12:59:59 ». Lorsqu'un nouvel horodatage dépasse l'intervalle, un rapport est imprimé, et le prochain intervalle est recalculé en fonction du nouvel horodatage.

Comme « --iterations » vaut 1 par défaut, vous voudrez probablement spécifier une nouvelle valeur, sinon pt-query-digest n'obtiendra et ne rapportera que le premier intervalle du journal, car 1 intervalle = 1 itération. Si vous voulez obtenir et rapporter chaque intervalle dans un journal, spécifiez « --iterations » 0.

Par exemple, « --sample 2 » autorisera deux requêtes d'échantillon pour chaque empreinte. Utile en conjonction avec « --output slowlog » pour imprimer les requêtes. pt-query-digest --sample 2 --no-report --output slowlog slow.log

Cette option vous permet d'ignorer les requêtes plus anciennes qu'une certaine valeur et de n'analyser que les requêtes plus récentes que la valeur. La valeur peut être de plusieurs types :

* Valeur de temps simple N avec suffixe optionnel : N[shmd], où
  s=secondes, h=heures, m=minutes, d=jours (s par défaut si aucun suffixe
  n'est donné) ; c'est comme dire « depuis N[shmd] »
* Date complète avec heures optionnelles : minutes : secondes :
  AAAA-MM-JJ [HH:MM:SS]
* Date courte, style MySQL :
  AA MM JJ [HH:MM:SS]
* Toute expression de temps évaluée par MySQL :
  CURRENT_DATE - INTERVAL 7 DAY

Si vous donnez une expression de temps MySQL, et que vous n'avez pas non plus spécifié de DSN pour « --explain », « --processlist », ou « --review », alors vous devez spécifier un DSN sur la ligne de commande afin que pt-query-digest puisse se connecter à MySQL pour évaluer l'expression.

L'expression de temps MySQL est encapsulée dans une requête comme « SELECT UNIX_TIMESTAMP(<expression>) », alors assurez-vous que l'expression est valide dans cette requête. Par exemple, n'utilisez pas UNIX_TIMESTAMP() car UNIX_TIMESTAMP(UNIX_TIMESTAMP()) renvoie 0.

Les événements sont supposés être dans l'ordre chronologique : événements plus anciens au début du journal et événements plus récents à la fin du journal. « --since » est strict : il ignore toutes les requêtes jusqu'à ce qu'une soit trouvée qui soit suffisamment récente. Par conséquent, si les événements de requête ne sont pas horodatés de manière cohérente, certains peuvent être ignorés alors qu'ils sont en fait suffisamment récents.

Voir aussi « --until ».

--timeline
Afficher une chronologie des événements.

Cette option fait que pt-query-digest imprime un autre type de rapport : une chronologie des événements. Chaque requête est toujours regroupée et agrégée en classes selon « --group-by », mais elles sont ensuite imprimées dans l'ordre chronologique. Le rapport de chronologie imprime l'horodatage, l'intervalle, le compte et la valeur de chaque classe.

Si tout ce que vous voulez est le rapport de chronologie, alors spécifiez « --no-report » pour supprimer le rapport d'analyse de requête par défaut. Sinon, le rapport de chronologie sera imprimé à la fin avant le profil de temps de réponse (voir « --report-format » et « OUTPUT »).

Par exemple, ceci :

pt-query-digest /path/to/log --group-by distill --timeline

imprimera quelque chose comme :

# ########################################################
# rapport distill
# ########################################################
# 2009-07-25 11:19:27 1+00:00:01   2 SELECT foo
# 2009-07-27 11:19:30      00:01   2 SELECT bar
# 2009-07-27 11:30:00 1+06:30:00   2 SELECT foo
--type
type : Tableau ; par défaut : slowlog

Le type d'entrée à analyser. Les types autorisés sont

binlog
Analyser un fichier de journal binaire qui a d'abord été converti en texte en utilisant mysqlbinlog.

Par exemple :

mysqlbinlog mysql-bin.000441 > mysql-bin.000441.txt
pt-query-digest --type binlog mysql-bin.000441.txt
genlog
Analyser un fichier de journal général MySQL. Les journaux généraux manquent de beaucoup d'« ATTRIBUTS », notamment « Query_time ». Le « --order-by » par défaut pour les journaux généraux est modifié en « Query_time:cnt ».
slowlog
Analyser un fichier journal dans n'importe quelle variation du format de journal lent MySQL.
tcpdump
Inspecter les paquets réseau et décoder le protocole client MySQL, en extrayant les requêtes et les réponses de celui-ci.

pt-query-digest ne surveille pas réellement le réseau (c'est-à-dire qu'il ne « capture pas les paquets »). Au lieu de cela, il analyse simplement la sortie de tcpdump. Vous êtes responsable de la génération de cette sortie ; pt-query-digest ne le fait pas pour vous. Ensuite, vous envoyez cela à pt-query-digest comme vous le feriez pour n'importe quel fichier journal : comme des fichiers sur la ligne de commande ou à STDIN.

L'analyseur s'attend à ce que l'entrée soit formatée avec les options suivantes : « -x -n -q -tttt ». Par exemple, si vous voulez capturer la sortie de votre machine locale, vous pouvez faire quelque chose comme ce qui suit (le port doit être le dernier sur FreeBSD) :

tcpdump -s 65535 -x -nn -q -tttt -i any -c 1000 port 3306 \
  > mysql.tcp.txt
pt-query-digest --type tcpdump mysql.tcp.txt

Les autres paramètres de tcpdump, tels que -s, -c et -i, dépendent de vous. Assurez-vous simplement que la sortie ressemble à ceci (il y a un saut de ligne dans la première ligne pour éviter les problèmes de page man) :

2009-04-12 09:50:16.804849 IP 127.0.0.1.42167
       > 127.0.0.1.3306: tcp 37
    0x0000:  4508 0059 6eb2 4000 4006 cde2 7f00 0001
    0x0010:  ....

N'oubliez pas que tcpdump a une option -c pratique pour s'arrêter après avoir capturé un certain nombre de paquets ! C'est très utile pour tester votre commande tcpdump. Notez que tcpdump ne peut pas capturer le trafic sur un socket Unix. Lisez http://bugs.mysql.com/bug.php?id=31577 si vous êtes confus à ce sujet

--tcpdump

Analyze tcpdump output. This option is useful for analyzing network traffic that is captured by tcpdump.

Devananda Van Der Veen explained on the MySQL Performance Blog how to capture traffic without dropping packets on busy servers. Dropped packets cause pt-query-digest to miss the response to a request, then see the response to a later request and assign the wrong execution time to the query. You can change the filter to something like the following to help capture a subset of the queries. (See https://www.percona.com/blog/how-to-use-tcpdump-on-very-busy-hosts/ for details.)

tcpdump -i any -s 65535 -x -n -q -tttt \
   'port 3306 and tcp[1] & 7 == 2 and tcp[3] & 7 == 2'

All MySQL servers running on port 3306 are automatically detected in the tcpdump output. Therefore, if the tcpdump output contains packets from multiple servers on port 3306 (for example, 10.0.0.1:3306, 10.0.0.2:3306, etc.), all packets/queries from all these servers will be analyzed together as if they were one server.

If you're analyzing traffic for a MySQL server that is not running on port 3306, see "--watch-server".

Also note that pt-query-digest may fail to report the database for queries when parsing tcpdump output. The database is discovered only in the initial connect events for a new client or when <USE db> is executed. If the tcpdump output contains neither of these, then pt-query-digest cannot discover the database.

Server-side prepared statements are supported. SSL-encrypted traffic cannot be inspected and decoded.

--variations
type: Array

Report the number of variations in these attributes' values.

Variations show how many distinct values an attribute had within a class. The usual value for this option is "arg" which shows how many distinct queries were in the class. This can be useful to determine a query's cacheability.

Distinct values are determined by CRC32 checksums of the attributes' values. These checksums are reported in the query report for attributes specified by this option, like:

# arg crc      109 (1/25%), 144 (1/25%)... 2 more

In that class there were 4 distinct queries. The checksums of the first two variations are shown, and each one occurred once (or, 25% of the time).

The counts of distinct variations is approximate because only 1,000 variations are saved. The mod (%) 1000 of the full CRC32 checksum is saved, so some distinct checksums are treated as equal.

Output a trailing "\G" in the reported SQL queries.

--watch-server
type: string

This option tells pt-query-digest which server IP address and port (like "10.0.0.1:3306") to watch when parsing tcpdump (for "--type" tcpdump); all other servers are ignored. If you don't specify it, pt-query-digest watches all servers by looking for any IP address using port 3306 or "mysql". If you're watching a server with a non-standard port, this won't work, so you must specify the IP address and port to watch.

If you want to watch a mix of servers, some running on standard port 3306 and some running on non-standard ports, you need to create separate tcpdump outputs for the non-standard port servers and then specify this option for each. At present pt-query-digest cannot auto-detect servers on port 3306 and also be told to watch a server on a non-standard port.

REFERENCE DES ATTRIBUTS

Les événements peuvent avoir les attributs suivants. Si vous écrivez un filtre "--filter", assurez-vous de vérifier qu'un attribut est défini dans chaque événement avant de l'utiliser, sinon le code du filtre pourrait faire planter l'outil avec une erreur "utilisation de valeur non initialisée".

Vous pouvez exporter les attributs d'événements pour n'importe quelle entrée comme suit :

$ pt-query-digest                  \
    slow.log                       \
    --filter 'print Dumper $event' \
    --no-report                    \
    --sample 1

Cela produira beaucoup de sortie avec des paires "attribut => valeur" comme :

$VAR1 = {
  Query_time => '0.033384',
  Rows_examined => '0',
  Rows_sent => '0',
  Thread_id => '10',
  Tmp_table => 'No',
  Tmp_table_on_disk => 'No',
  arg => 'SELECT col FROM tbl WHERE id=5',
  bytes => 103,
  cmd => 'Query',
  db => 'db1',
  fingerprint => 'select col from tbl where id=?',
  host => '',
  pos_in_log => 1334,
  ts => '071218 11:48:27',
  user => '[SQL_SLAVE]'
};

COMMUNS

Ces attributs sont communs à toutes les entrées "--type" et "--processlist", sauf indication contraire.

arg
Le texte de la requête, ou la commande pour les commandes d'administration comme "Ping".
bytes
La longueur en octets de l'"arg".
cmd
"Query" ou "Admin".
db
La base de données actuelle. La valeur provient des instructions USE database. Par défaut, "Schema" est un alias qui est automatiquement changé en "db" ; voir "--attribute-aliases".
fingerprint
Une forme abstraite de la requête. Voir "EMPREINTES".
host
L'hôte client qui a exécuté la requête.
pos_in_log
Le décalage en octets de l'événement dans le journal ou tcpdump, sauf pour "--processlist".
Query_time
Le temps total qu'a pris la requête, y compris le temps de verrouillage.
ts
L'horodatage du moment où la requête s'est terminée.

LOGS LENTS, GENERAUX ET BINAIRES

Les événements ont tous les attributs disponibles du fichier journal. Par conséquent, il vous suffit de regarder le fichier journal pour voir quels événements sont disponibles, mais rappelez-vous : tous les événements n'ont pas les mêmes attributs.

Percona Server ajoute de nombreux attributs au journal lent ; voir http://www.percona.com/docs/wiki/patches:slow_extended pour plus d'informations.

TCPDUMP

Ces attributs sont disponibles lors de l'analyse de "--type" tcpdump.

Error_no
Le numéro d'erreur MySQL si la requête a provoqué une erreur.
ip
L'adresse IP du client. Certains fichiers journaux peuvent également contenir cet attribut.
No_good_index_used
Oui ou Non si aucun bon index n'a été trouvé pour la requête (indicateur défini par le serveur).
No_index_used
Oui ou Non si la requête n'a utilisé aucun index (indicateur défini par le serveur).
port
Le numéro de port du client.
Warning_count
Le nombre d'avertissements, tels qu'affichés par ailleurs par "SHOW WARNINGS".
