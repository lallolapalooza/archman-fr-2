PTHREAD_MUTEX_DESTROY(3P) Manuel du programmeur POSIX PTHREAD_MUTEX_DESTROY(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pthread_mutex_destroy, pthread_mutex_init — détruit et initialise un mutex

SYNOPIS

#include <pthread.h>
int pthread_mutex_destroy(pthread_mutex_t *mutex);
int pthread_mutex_init(pthread_mutex_t *restrict mutex,
    const pthread_mutexattr_t *restrict attr);
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

DESCRIPTION

La fonction pthread_mutex_destroy() détruit l'objet mutex référencé par mutex ; l'objet mutex devient, en effet, non initialisé. Une implémentation peut amener pthread_mutex_destroy() à définir l'objet référencé par mutex à une valeur invalide.

Un mutex détruit peut être réinitialisé en utilisant pthread_mutex_init() ; les résultats d'une référence ultérieure à l'objet après sa destruction sont indéfinis.

Il est sûr de détruire un mutex initialisé qui est déverrouillé. Tenter de détruire un mutex verrouillé, ou un mutex qu'un autre thread essaie de verrouiller, ou un mutex qui est utilisé dans un appel pthread_cond_timedwait() ou pthread_cond_wait() par un autre thread, entraîne un comportement indéfini.

La fonction pthread_mutex_init() initialise le mutex référencé par mutex avec les attributs spécifiés par attr. Si attr est NULL, les attributs de mutex par défaut sont utilisés ; l'effet doit être le même que de passer l'adresse d'un objet d'attributs de mutex par défaut. Après une initialisation réussie, l'état du mutex devient initialisé et déverrouillé.

Voir la Section 2.9.9, Copies d'objets de synchronisation et mappages alternatifs pour des exigences supplémentaires.

Tenter d'initialiser un mutex déjà initialisé entraîne un comportement indéfini.

Dans les cas où des attributs de mutex par défaut sont appropriés, la macro PTHREAD_MUTEX_INITIALIZER peut être utilisée pour initialiser les mutex. L'effet sera équivalent à une initialisation dynamique par un appel à pthread_mutex_init() avec le paramètre attr spécifié comme NULL, à l'exception du fait qu'aucun contrôle d'erreur n'est effectué.

Le comportement est indéfini si la valeur spécifiée par l'argument mutex à pthread_mutex_destroy() ne fait pas référence à un mutex initialisé.

Le comportement est indéfini si la valeur spécifiée par l'argument attr à pthread_mutex_init() ne fait pas référence à un objet d'attributs de mutex initialisé.

VALEUR DE RETOUR

En cas de succès, les fonctions pthread_mutex_destroy() et pthread_mutex_init() retournent zéro ; sinon, un numéro d'erreur est retourné pour indiquer l'erreur.

ERREURS

La fonction pthread_mutex_init() échoue si :

EAGAIN
Le système n'avait pas les ressources nécessaires (autres que la mémoire) pour initialiser un autre mutex.
ENOMEM
Une mémoire insuffisante existe pour initialiser le mutex.
EPERM
L'appelant n'a pas le privilège d'effectuer l'opération.

La fonction pthread_mutex_init() peut échouer si :

EINVAL
L'objet d'attributs référencé par attr a l'attribut mutex robuste défini sans que l'attribut de partage de processus soit défini.

Ces fonctions ne retournent pas de code d'erreur [EINTR].

JUSTIFICATION

Si une implémentation détecte que la valeur spécifiée par l'argument mutex à pthread_mutex_destroy() ne fait pas référence à un mutex initialisé, il est recommandé que la fonction échoue et signale une erreur [EINVAL].

Si une implémentation détecte que la valeur spécifiée par l'argument mutex à pthread_mutex_destroy() ou pthread_mutex_init() fait référence à un mutex verrouillé ou à un mutex qui est référencé (par exemple, lors de son utilisation dans un appel pthread_cond_timedwait() ou pthread_cond_wait()) par un autre thread, ou détecte que la valeur spécifiée par l'argument mutex à pthread_mutex_init() fait référence à un mutex déjà initialisé, il est recommandé que la fonction échoue et signale une erreur [EBUSY].

Si une implémentation détecte que la valeur spécifiée par l'argument attr à pthread_mutex_init() ne fait pas référence à un objet d'attributs de mutex initialisé, il est recommandé que la fonction échoue et signale une erreur [EINVAL].

Implémentations Alternatives Possibles

Ce volume de POSIX.1-2017 prend en charge plusieurs implémentations alternatives de mutex. Une implémentation peut stocker le verrou directement dans l'objet de type pthread_mutex_t. Alternativement, une implémentation peut stocker le verrou dans le tas et simplement stocker un pointeur, un handle ou un identifiant unique dans l'objet mutex. L'une ou l'autre implémentation a des avantages ou peut être requise sur certaines configurations matérielles. Afin que du code portable puisse être écrit et qui soit invariant à ce choix, ce volume de POSIX.1-2017 ne définit pas l'affectation ou l'égalité pour ce type, et utilise le terme « initialiser » pour renforcer la notion (plus restrictive) que le verrou peut réellement résider dans l'objet mutex lui-même.

Notez que cela exclut une sur-spécification du type de mutex ou de variable de condition et motive l'opacité du type.

Une implémentation est autorisée, mais pas obligée, à faire stocker une valeur illégale dans le mutex par pthread_mutex_destroy(). Cela peut aider à détecter les programmes erronés qui essaient de verrouiller (ou de référencer autrement) un mutex qui a déjà été détruit.

Compromis entre Vérifications d'Erreurs et Performances Supporté

De nombreuses conditions d'erreur qui peuvent survenir ne sont pas obligatoires à détecter par l'implémentation afin de permettre aux implémentations de faire des compromis entre les performances versus le degré de vérification des erreurs selon les besoins de leurs applications spécifiques et de leur environnement d'exécution. En règle générale, les conditions causées par le système (comme un manque de mémoire) sont obligatoires à détecter, mais les conditions causées par une application mal codée (comme ne pas fournir une synchronisation adéquate pour empêcher la suppression d'un mutex pendant son utilisation) sont spécifiées pour entraîner un comportement indéfini.

Une large gamme d'implémentations est ainsi rendue possible. Par exemple, une implémentation destinée au débogage d'applications peut implémenter toutes les vérifications d'erreurs, mais une implémentation exécutant une application unique, prouvablement correcte, sous des contraintes de performance très strictes dans un ordinateur embarqué pourrait implémenter des vérifications minimales. Une implémentation pourrait même être fournie en deux versions, similaires aux options que les compilateurs offrent : une version complète, mais plus lente, et une version à vérification limitée, mais plus rapide. Interdire cette optionalité serait un mauvais service aux utilisateurs.

En limitant soigneusement l'utilisation du « comportement indéfini » uniquement aux choses qu'une application erronée (mal codée) pourrait faire, et en définissant que les erreurs de non-disponibilité des ressources sont obligatoires, ce volume de POSIX.1-2017 garantit qu'une application entièrement conforme est portable sur toute la gamme d'implémentations, sans obliger toutes les implémentations à ajouter de la surcharge pour vérifier de nombreuses choses qu'un programme correct ne fait jamais. DESCRIPTION

These functions are related to mutexes, which are synchronization primitives used to protect shared data from being accessed by multiple threads simultaneously.

Return Values for Mutex Initialization and Destruction

On success, these functions return 0. On failure, they return an error number. If the mutex is locked or is currently being used in a condition wait by another thread, attempting to destroy it results in undefined behavior.

The mutex attribute functions behave as follows:

EBUSY
The attribute object is currently in use by another thread.
EINVAL
The value specified by attr is invalid.

Error Handling and Undefined Behavior

The POSIX standard specifies that certain operations on mutexes result in undefined behavior. This means that anything can happen, including program termination or returning an incorrect error code. Implementations are not required to detect these conditions, but they are recommended to return a specific error number if they do detect them, to aid developers in diagnosing problems.

Why No Limits are Defined

The number of mutexes and condition variables is not explicitly limited by the standard. This is because these objects can often be created dynamically and allocated in application memory, meaning there is no fixed maximum.

Static Initializers for Mutexes and Condition Variables

The standard provides static initializers for mutexes and condition variables (e.g., PTHREAD_MUTEX_INITIALIZER). This allows for statically allocated synchronization objects to be used without runtime initialization, simplifying code and reducing overhead, especially for self-initializing modules.

The example shows how static initialization eliminates the need for explicit initialization functions and checks, making the code cleaner and potentially faster on systems where synchronization objects reside in application memory.

For systems that require mutexes to be allocated from special memory, implementations may need to perform runtime initialization checks even for statically initialized mutexes. This is typically handled by storing a special value in the mutex that triggers initialization on the first access, minimizing performance impact on subsequent operations.

The overhead for out-of-line mutex allocation is generally comparable to implicitly initialized modules. Static initialization offers significant performance benefits for inline allocations.

Concerns about threads serializing during the initialization of statically allocated mutexes are addressed by implementation techniques like hashing and the fact that such serialization occurs only a limited number of times. Dynamically allocated objects are still initialized using the standard pthread_*_init functions.

If performance is critical on a specific implementation, applications can avoid static initialization by explicitly using the pthread_*_init functions for all synchronization objects.

Destroying Mutexes

A mutex can be destroyed after it has been unlocked. Attempting to destroy a locked mutex, or one involved in a condition wait, results in undefined behavior. Developers must ensure no other threads are referencing the mutex before destroying it.

Robust Mutexes

Implementations are required to provide robust mutexes when the process-shared attribute is set to PTHREAD_PROCESS_SHARED. They may optionally provide robust mutexes for PTHREAD_PROCESS_PRIVATE.
