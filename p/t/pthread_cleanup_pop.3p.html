PTHREAD_CLEANUP_POP(3P) Manuel du programmeur POSIX PTHREAD_CLEANUP_POP(3P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pthread_cleanup_pop, pthread_cleanup_push — établir des gestionnaires d'annulation

SYNTAXE

#include <pthread.h>
void pthread_cleanup_pop(int execute);
void pthread_cleanup_push(void (*routine)(void*), void *arg);

DESCRIPTION

La fonction pthread_cleanup_pop() supprime la routine au sommet de la pile de nettoyage d'annulation du thread appelant et l'invoque éventuellement (si execute est non nul).

La fonction pthread_cleanup_push() empile le gestionnaire de nettoyage d'annulation spécifié routine sur la pile de nettoyage d'annulation du thread appelant. Le gestionnaire de nettoyage d'annulation sera dépilé de la pile de nettoyage d'annulation et invoqué avec l'argument arg lorsque :

*
Le thread se termine (c'est-à-dire, appelle pthread_exit()).
*
Le thread agit sur une demande d'annulation.
*
Le thread appelle pthread_cleanup_pop() avec un argument execute non nul.

Il n'est pas spécifié si pthread_cleanup_push() et pthread_cleanup_pop() sont des macros ou des fonctions. Si une définition de macro est supprimée afin d'accéder à une fonction réelle, ou si un programme définit un identifiant externe avec l'un de ces noms, le comportement est indéfini. L'application doit s'assurer qu'elles apparaissent comme des instructions, et par paires dans la même portée lexicale (c'est-à-dire, la macro pthread_cleanup_push() peut être considérée comme se développant en une liste de tokens dont le premier token est '{' et pthread_cleanup_pop() se développant en une liste de tokens dont le dernier token est le '}' correspondant).

L'effet de l'appel de longjmp() ou siglongjmp() est indéfini s'il y a eu des appels à pthread_cleanup_push() ou pthread_cleanup_pop() sans l'appel correspondant depuis que le tampon de saut a été rempli. L'effet de l'appel de longjmp() ou siglongjmp() depuis un gestionnaire de nettoyage d'annulation est également indéfini à moins que le tampon de saut n'ait également été rempli dans le gestionnaire de nettoyage d'annulation.

L'effet de l'utilisation de return, break, continue, et goto pour quitter prématurément un bloc de code décrit par une paire de fonctions pthread_cleanup_push() et pthread_cleanup_pop() est indéfini.

VALEUR DE RETOUR

Les fonctions pthread_cleanup_push() et pthread_cleanup_pop() ne doivent pas retourner de valeur.

ERREURS

Aucune erreur n'est définie.

Ces fonctions ne doivent pas retourner un code d'erreur de [EINTR].

Les sections suivantes sont informatives.

EXEMPLES

L'exemple suivant utilise des primitives de thread pour implémenter un verrou de lecture/écriture prioritaire pour les écrivains et annulable :

typedef struct {
    pthread_mutex_t lock;
    pthread_cond_t rcond,
        wcond;
    int lock_count; /* < 0 .. Détenu par un écrivain. */
                    /* > 0 .. Détenu par lock_count lecteurs. */
                    /* = 0 .. Détenu par personne. */
    int waiting_writers; /* Nombre d'écrivains en attente. */
} rwlock;
void
waiting_reader_cleanup(void *arg)
{
    rwlock *l;
    l = (rwlock *) arg;
    pthread_mutex_unlock(&l->lock);
}
void
lock_for_read(rwlock *l)
{
    pthread_mutex_lock(&l->lock);
    pthread_cleanup_push(waiting_reader_cleanup, l);
    while ((l->lock_count < 0) || (l->waiting_writers != 0))
        pthread_cond_wait(&l->rcond, &l->lock);
    l->lock_count++;
   /*
    * Notez que pthread_cleanup_pop exécute
    * waiting_reader_cleanup.
    */
    pthread_cleanup_pop(1);
}
void
release_read_lock(rwlock *l)
{
    pthread_mutex_lock(&l->lock);
    if (--l->lock_count == 0)
        pthread_cond_signal(&l->wcond);
    pthread_mutex_unlock(&l->lock);
}
void
waiting_writer_cleanup(void *arg)
{
    rwlock *l;
    l = (rwlock *) arg;
    if ((--l->waiting_writers == 0) && (l->lock_count >= 0)) {
       /*
        * Cela ne se produit que si nous avons été annulés. Si le
        * verrou n'est pas détenu par un écrivain, il peut y avoir des lecteurs qui
        * ont été bloqués car waiting_writers était positif; ils
        * peuvent maintenant être débloqués.
        */
        pthread_cond_broadcast(&l->rcond);
    }
    pthread_mutex_unlock(&l->lock);
}
void
lock_for_write(rwlock *l)
{
    pthread_mutex_lock(&l->lock);
    l->waiting_writers++;
    pthread_cleanup_push(waiting_writer_cleanup, l);
    while (l->lock_count != 0)
        pthread_cond_wait(&l->wcond, &l->lock);
    l->lock_count = -1;
   /*
    * Notez que pthread_cleanup_pop exécute
    * waiting_writer_cleanup.
    */
    pthread_cleanup_pop(1);
}
void
release_write_lock(rwlock *l)
{
    pthread_mutex_lock(&l->lock);
    l->lock_count = 0;
    if (l->waiting_writers == 0)
        pthread_cond_broadcast(&l->rcond);
    else
        pthread_cond_signal(&l->wcond);
    pthread_mutex_unlock(&l->lock);
}
/*
 * Cette fonction est appelée pour initialiser le verrou lecture/écriture.
 */
void
initialize_rwlock(rwlock *l)
{
    pthread_mutex_init(&l->lock, pthread_mutexattr_default);
    pthread_cond_init(&l->wcond, pthread_condattr_default);
    pthread_cond_init(&l->rcond, pthread_condattr_default);
    l->lock_count = 0;
    l->waiting_writers = 0;
}
reader_thread()
{
    lock_for_read(&lock);
    pthread_cleanup_push(release_read_lock, &lock);
   /*
    * Le thread détient le verrou de lecture.
    */
    pthread_cleanup_pop(1);
}
writer_thread()
{
    lock_for_write(&lock);
    pthread_cleanup_push(release_write_lock, &lock);
   /*
    * Le thread détient le verrou d'écriture.
    */
pthread_cleanup_pop(1);
}

UTILISATION APPLICATIVE

Les deux routines qui empilent et dépilent les gestionnaires de nettoyage d'annulation, pthread_cleanup_push() et pthread_cleanup_pop(), peuvent être considérées comme des parenthèses gauche et droite. Elles doivent toujours être appariées.

RATIONALE

La restriction selon laquelle les deux routines qui empilent et dépilent les gestionnaires de nettoyage d'annulation, pthread_cleanup_push() et pthread_cleanup_pop(), doivent apparaître dans la même portée lexicale permet des implémentations macro ou compilateur efficaces et une gestion de stockage efficace. Une implémentation type de ces routines sous forme de macros pourrait ressembler à ceci :

#define pthread_cleanup_push(rtn,arg) { \
    struct _pthread_handler_rec __cleanup_handler, **__head; \
    __cleanup_handler.rtn = rtn; \
    __cleanup_handler.arg = arg; \
    (void) pthread_getspecific(_pthread_handler_key, &__head); \
    __cleanup_handler.next = *__head; \
    *__head = &__cleanup_handler;
#define pthread_cleanup_pop(ex) \
    *__head = __cleanup_handler.next; \
    if (ex) (*__cleanup_handler.rtn)(__cleanup_handler.arg); \
}

Une implémentation plus ambitieuse de ces routines pourrait faire encore mieux en permettant au compilateur de noter que le gestionnaire de nettoyage d'annulation est une constante et peut être développé en ligne.

Ce volume de POSIX.1‐2017 laisse actuellement indéfini l'effet de l'appel de longjmp() depuis un gestionnaire de signaux exécutant une fonction d'interface système POSIX. Si une implémentation souhaite autoriser cela et offrir un comportement raisonnable au programmeur, la fonction longjmp() doit appeler tous les gestionnaires de nettoyage d'annulation qui ont été empilés mais non dépilés depuis que setjmp() a été appelé.

Considérez une fonction multithread appelée par un thread qui utilise des signaux. Si un signal était délivré à un gestionnaire de signaux pendant l'opération de qsort() et que ce gestionnaire appelait longjmp() (qui, à son tour, n'appelait pas les gestionnaires de nettoyage d'annulation), les threads auxiliaires créés par la fonction qsort() ne seraient pas annulés. Au lieu de cela, ils continueraient à s'exécuter et à écrire dans le tableau d'arguments même si le tableau avait été dépilé de la pile.

">Notez que le mécanisme de traitement de nettoyage spécifié est particulièrement lié au langage C et, bien que la nécessité d'un mécanisme uniforme pour exprimer le nettoyage soit indépendante du langage, le mécanisme utilisé dans d'autres langages peut être très différent. De plus, ce mécanisme n'est vraiment nécessaire qu'en raison de l'absence d'un véritable mécanisme d'exception dans le langage C, qui serait la solution idéale.

Il n'y a pas de notion de fonction sûre pour le nettoyage de l'annulation. Si une application n'a pas de points d'annulation dans ses gestionnaires de signaux, bloque tout signal dont le gestionnaire pourrait avoir des points d'annulation lors de l'appel de fonctions asynchrones-non sûres, ou désactive l'annulation lors de l'appel de fonctions asynchrones-non sûres, toutes les fonctions peuvent être appelées en toute sécurité depuis les routines de nettoyage d'annulation.
