NOM

pt-kill - Tuer des requêtes MySQL qui correspondent à certains critères.

SYNOPSIS

Utilisation : pt-kill [OPTIONS] [DSN]

pt-kill tue les connexions MySQL. pt-kill se connecte à MySQL et obtient les requêtes à partir de SHOW PROCESSLIST, sauf si l'option "--test-matching" est donnée. Sinon, il lit les requêtes à partir d'un ou plusieurs fichiers qui contiennent la sortie de SHOW PROCESSLIST. Si le fichier est -, pt-kill lit depuis STDIN.

Tuer les requêtes exécutées depuis plus de 60s :

pt-kill --busy-time 60 --kill

Afficher, sans tuer, les requêtes exécutées depuis plus de 60s :

pt-kill --busy-time 60 --print

Vérifier les processus en veille et les tuer tous toutes les 10s :

pt-kill --match-command Sleep --kill --victims all --interval 10

Afficher tous les processus de connexion :

pt-kill --match-state login --print --victims all

Voir quelles requêtes dans la liste des processus actuellement correspondraient :

mysql -e "SHOW PROCESSLIST" > proclist.txt
pt-kill --test-matching proclist.txt --busy-time 60 --print

RISQUES

Percona Toolkit est mature, éprouvé dans le monde réel et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Examiner les "BUGS" connus de l'outil
  • Tester l'outil sur un serveur non-production
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

DESCRIPTION

pt-kill capture les requêtes de SHOW PROCESSLIST, les filtre, puis les tue ou les affiche. Ceci est également connu sous le nom de "chasseur de requêtes lentes" dans certains cercles. L'idée est de surveiller les requêtes qui pourraient consommer trop de ressources et de les tuer.

Pour plus de brièveté, nous parlons de tuer des requêtes, mais elles peuvent simplement être imprimées (ou une autre action future) selon les options données.

Normalement, pt-kill se connecte à MySQL pour obtenir les requêtes de SHOW PROCESSLIST. Alternativement, il peut lire la sortie de SHOW PROCESSLIST à partir de fichiers. Dans ce cas, pt-kill ne se connecte pas à MySQL et "--kill" n'a aucun effet. Vous devriez plutôt utiliser "--print" lors de la lecture de fichiers. La capacité de lire un fichier avec "--test-matching" vous permet de capturer SHOW PROCESSLIST et de le tester plus tard avec pt-kill pour vous assurer que vos correspondances tuent les bonnes requêtes. Il y a beaucoup de règles spéciales à suivre, comme "ne pas tuer les threads de réplication", alors faites attention à ne pas tuer quelque chose d'important !

Deux options importantes à connaître sont "--busy-time" et "--victims". Premièrement, alors que la plupart des options de correspondance/filtre correspondent à leur valeur correspondante de SHOW PROCESSLIST (par exemple, "--match-command" correspond à la valeur Command d'une requête), la valeur Time est mise en correspondance par "--busy-time". Voir aussi "--interval".

Deuxièmement, "--victims" contrôle quelles requêtes correspondantes de chaque classe sont tuées. Par défaut, la requête correspondante avec la valeur Time la plus élevée est tuée (la requête la plus ancienne). Voir la section suivante, "GROUPEMENT, CORRESPONDANCE ET TUERIE", pour plus de détails.

Habituellement, vous devez spécifier au moins une option "--match", sinon aucune requête ne correspondra. Ou, vous pouvez spécifier "--match-all" pour faire correspondre toutes les requêtes qui ne sont pas ignorées par une option "--ignore".

GROUPEMENT, CORRESPONDANCE ET TUERIE

Les requêtes passent par plusieurs étapes pour déterminer lesquelles exactement seront tuées (ou affichées - quelle que soit l'action spécifiée). Comprendre ces étapes vous aidera à faire correspondre précisément les requêtes que vous souhaitez.

La première étape consiste à regrouper les requêtes en classes. L'option "--group-by" contrôle le groupement. Par défaut, cette option n'a pas de valeur, donc toutes les requêtes sont regroupées en une seule classe par défaut. Tous les types de correspondance et de filtrage (l'étape suivante) sont appliqués par classe. Par conséquent, vous pourriez avoir besoin de regrouper les requêtes afin de faire correspondre/filtrer certaines classes mais pas d'autres.

La deuxième étape est la correspondance. La correspondance implique le filtrage car si une requête ne correspond pas à certains critères, elle est supprimée de sa classe. La correspondance se produit pour chaque classe. Premièrement, les requêtes sont filtrées de leur classe par les différentes options de "Correspondance des requêtes" comme "--match-user". Ensuite, des classes entières sont filtrées par les différentes options de "Correspondance des classes" comme "--query-count".

La troisième étape est la sélection des victimes, c'est-à-dire, quelles requêtes correspondantes dans chaque classe tuer. Ceci est contrôlé par l'option "--victims". Bien que de nombreuses requêtes dans une classe puissent correspondre, vous pourriez seulement vouloir tuer la requête la plus ancienne, ou toutes les requêtes, etc.

La quatrième et dernière étape consiste à effectuer une action sur toutes les requêtes correspondantes de toutes les classes. Les options "Actions" spécifient quelles actions seront effectuées. À ce stade, il n'y a plus de classes, juste une seule liste de requêtes à tuer, afficher, etc.

pt-kill tuera toutes les requêtes correspondant à N'IMPORTE LEQUEL des critères spécifiés (OU logique). Par exemple, en utilisant :

--busy-time 114 --match-command 'Query|Execute'

tuera toutes les requêtes ayant busy-time > 114 "OU" où la commande est "Query" ou "Execute"

Si vous souhaitez tuer uniquement les requêtes où "busy-time" est supérieur à 114 et où la commande est Query ou Execute, vous devez utiliser "--kill-busy-commands" :

--busy-time 114 --kill-busy-commands 'Query|Execute'

SORTIE

Si seulement "--kill" est donné, alors il n'y a pas de sortie. Si seulement "--print" est donné, alors une instruction KILL horodatée est imprimée pour chaque requête qui aurait été tuée, comme :

# 2009-07-15T15:04:01 KILL 8 (Query 42 sec) SELECT * FROM huge_table

La ligne montre un horodatage, l'Id de la requête (8), son Temps (42 sec) et ses Informations (généralement le SQL de la requête).

Si "--kill" et "--print" sont tous deux donnés, alors les requêtes correspondantes sont tuées et une ligne comme celle ci-dessus est imprimée pour chacune.

Chaque commande exécutée par "--execute-command" est responsable de sa propre sortie et de sa journalisation. Après avoir été exécutée, pt-kill n'a aucun contrôle ou interaction avec la commande.

OPTIONS

Spécifiez au moins l'une des options "--kill", "--kill-query", "--print", "--execute-command" ou "--stop".

"--any-busy-time" et "--each-busy-time" s'excluent mutuellement.

"--kill" et "--kill-query" s'excluent mutuellement.

"--daemonize" et "--test-matching" s'excluent mutuellement.

Cet outil accepte des arguments de ligne de commande supplémentaires. Reportez-vous à la "SYNOPSIS" et aux informations d'utilisation pour plus de détails.

--filter
type : chaîne

Écarte les événements pour lesquels ce code Perl ne renvoie pas vrai.

Cette option est une chaîne de code Perl ou un fichier contenant du code Perl qui est compilé en une sous-routine avec un argument : $event. Il s'agit d'un hashref. Si la valeur fournie est un fichier lisible, pt-kill lit l'intégralité du fichier et utilise son contenu comme code. Le fichier ne doit pas contenir de ligne shebang (#!/usr/bin/perl).

Si le code renvoie vrai, la chaîne de rappels continue ; sinon, elle se termine. Le code est la dernière instruction de la sous-routine autre que "return $event". Le modèle de sous-routine est :

sub { $event = shift; filter && return $event; }

Les filtres donnés sur la ligne de commande sont encapsulés entre parenthèses comme "( filtre )". Pour des filtres complexes et multi-lignes, vous devez placer le code dans un fichier afin qu'il ne soit pas encapsulé entre parenthèses. Dans les deux cas, le filtre doit produire un code syntaxiquement valide étant donné le modèle. Par exemple, une branche if-else donnée sur la ligne de commande ne serait pas valide :

--filter 'if () { } else { }'  # FAUX

Comme il est donné sur la ligne de commande, la branche if-else serait encapsulée entre parenthèses, ce qui n'est pas syntaxiquement valide. Ainsi, pour accomplir quelque chose de plus complexe comme cela, il faudrait placer le code dans un fichier, par exemple filter.txt :

my $event_ok; if (...) { $event_ok=1; } else { $event_ok=0; } $event_ok

Ensuite, spécifiez "--filter filter.txt" pour lire le code depuis filter.txt.

Si le code du filtre ne compile pas, pt-kill échouera avec une erreur. Si le code du filtre compile, une erreur peut toujours survenir à l'exécution si le code tente de faire quelque chose de mal (comme faire correspondre un modèle à une valeur indéfinie). pt-kill ne fournit aucune protection, alors codez prudemment !

Il est permis que le code ait des effets de bord (pour modifier $event).

--group-by
type : chaîne

Applique les correspondances à chaque classe de requêtes regroupées par cette colonne de SHOW PROCESSLIST. En plus des colonnes de base de SHOW PROCESSLIST (user, host, command, state, etc.), les requêtes peuvent être mises en correspondance par "fingerprint", qui abstrait la requête SQL dans la colonne "Info".

Par défaut, les requêtes ne sont pas regroupées, donc les correspondances et les actions s'appliquent à toutes les requêtes. Le regroupement permet aux correspondances et aux actions de s'appliquer à des classes de requêtes similaires, si des requêtes de la classe correspondent.

Par exemple, la détection de stampedes de cache (voir "all-but-oldest" sous "--victims" pour une explication de ce terme) nécessite que les requêtes soient regroupées par l'attribut "arg". Cela crée des classes de requêtes identiques (sans les commentaires). Ainsi, les requêtes "SELECT c FROM t WHERE id=1" et "SELECT c FROM t WHERE id=1" sont regroupées dans la même classe, mais la requête "SELECT c FROM t WHERE id=3" n'est pas identique aux deux premières requêtes, elle est donc regroupée dans une autre classe. Ensuite, lorsque "--victims" "all-but-oldest" est spécifié, toutes sauf la requête la plus ancienne de chaque classe sont tuées pour chaque classe de requêtes qui correspond aux critères de correspondance.

Indique que l'instance en question se trouve sur Amazon RDS. Par défaut, pt-kill exécute la commande MySQL "kill" pour "--kill" et "kill query" "--kill-query". La présence du fichier spécifié par "--sentinel" entraînera la sortie de toutes les instances en cours d'exécution de pt-kill. Vous pourriez trouver cela utile pour arrêter les tâches cron gracieusement si nécessaire. Voir aussi "--stop".

--[no]version-check
défaut : yes

Vérifie la dernière version de Percona Toolkit, MySQL et d'autres programmes.

Il s'agit d'une fonctionnalité standard de "vérification des mises à jour automatique", avec deux fonctionnalités supplémentaires. Premièrement, l'outil vérifie sa propre version ainsi que les versions des logiciels suivants : système d'exploitation, Percona Monitoring and Management (PMM), MySQL, Perl, pilote MySQL pour Perl (DBD::mysql) et Percona Toolkit. Deuxièmement, il recherche et avertit des versions présentant des problèmes connus. Par exemple, MySQL 5.5.25 avait un bug critique et a été re-publié sous la version 5.5.25a.

Une connexion sécurisée au serveur de base de données Percona’s Version Check est établie pour effectuer ces vérifications. Chaque requête est enregistrée par le serveur, y compris les numéros de version des logiciels et l'identifiant unique du système vérifié. L'identifiant est généré par le script d'installation de Percona Toolkit ou lorsque l'appel à la base de données de vérification de version est effectué pour la première fois.

Toutes les mises à jour ou problèmes connus sont affichés sur STDOUT avant la sortie normale de l'outil. Cette fonctionnalité ne devrait jamais interférer avec le fonctionnement normal de l'outil.

Pour plus d'informations, visitez https://www.percona.com/doc/percona-toolkit/LATEST/version-check.html.

--victims
type : string ; défaut : oldest

Laquelle des requêtes correspondantes dans chaque classe sera arrêtée. Après que les classes ont été mises en correspondance/filtrées, cette option spécifie quelle(s) requête(s) correspondante(s) dans chaque classe sera(ont) arrêtée(s) (ou affichée(s), etc.). Les valeurs suivantes sont possibles :

oldest
Arrête uniquement la seule requête la plus ancienne. Ceci afin d'éviter d'arrêter des requêtes qui ne sont pas réellement longues à exécuter, mais simplement longues à attendre. Cela trie les requêtes correspondantes par Time et arrête celle qui a la valeur Time la plus élevée.
all
Arrête toutes les requêtes de la classe.
all-but-oldest
Arrête toutes les requêtes sauf la plus ancienne. C'est l'inverse de la valeur "oldest".

Cette valeur peut être utilisée pour éviter les "cache stampedes", la condition où plusieurs requêtes identiques sont exécutées et créent une file d'attente pendant que la première requête tente de se terminer. Étant donné que toutes les requêtes sont identiques, toutes sauf la première sont arrêtées afin qu'elle puisse se terminer et remplir le cache.

--wait-after-kill
type : time

Attend après avoir arrêté une requête, avant d'en rechercher d'autres à arrêter. Le but est de donner aux requêtes bloquées une chance de s'exécuter, afin de ne pas arrêter une requête qui bloque un grand nombre d'autres requêtes, puis d'arrêter les autres immédiatement après.

--wait-before-kill
type : time

Attend avant d'arrêter une requête. Le but est de donner à "--execute-command" une chance de voir la requête correspondante et de collecter d'autres informations MySQL ou système avant qu'elle ne soit arrêtée.

CORRESPONDANCES DE REQUÊTES

Ces options filtrent les requêtes de leurs classes. Si une requête ne correspond pas, elle est supprimée de sa classe. Les options "--ignore" ont la priorité. Les correspondances pour command, db, host, etc. correspondent aux colonnes retournées par SHOW PROCESSLIST : Command, db, Host, etc. Toutes les correspondances de motifs sont sensibles à la casse par défaut, mais elles peuvent être rendues insensibles à la casse en spécifiant un motif regex tel que "(?i-xsm:select)".

Voir aussi "GROUP, MATCH AND KILL".

--busy-time
type : time ; groupe : Query Matches

Correspond aux requêtes qui s'exécutent depuis plus longtemps que cette durée. Les requêtes doivent être dans l'état Command=Query. Cela correspond à la valeur Time d'une requête telle que rapportée par SHOW PROCESSLIST.

--idle-time
type : time ; groupe : Query Matches

Correspond aux requêtes qui sont restées inactives/en veille pendant plus longtemps que cette durée. Les requêtes doivent être dans l'état Command=Sleep. Cela correspond à la valeur Time d'une requête telle que rapportée par SHOW PROCESSLIST.

--ignore-command
type : string ; groupe : Query Matches

Ignore les requêtes dont la commande correspond à cette regex Perl.

Voir "--match-command".

--ignore-db
type : string ; groupe : Query Matches

Ignore les requêtes dont la base de données (db) correspond à cette regex Perl.

Voir "--match-db".

--ignore-host
type : string ; groupe : Query Matches

Ignore les requêtes dont l'hôte (Host) correspond à cette regex Perl.

La valeur Host inclut souvent le port, par exemple "host:port".

--ignore-info
type : string ; groupe : Query Matches

Ignore les requêtes dont les informations (Info) correspondent à cette regex Perl.

Voir "--match-info".

--[no]ignore-self
défaut : yes ; groupe : Query Matches

Ne pas arrêter la propre connexion de pt-kill.

--ignore-state
type : string ; groupe : Query Matches ; défaut : Locked

Ignore les requêtes dont l'état (State) correspond à cette regex Perl. Par défaut, cela empêche les threads d'être arrêtés s'ils sont verrouillés en attendant un autre thread.

Voir "--match-state".

--ignore-user
type : string ; groupe : Query Matches

Ignore les requêtes dont l'utilisateur correspond à cette regex Perl.

Voir "--match-user".

--match-all
groupe : Query Matches

Correspond à toutes les requêtes qui ne sont pas ignorées. Si aucune option d'ignorance n'est spécifiée, alors toutes les requêtes correspondent (sauf les threads de réplication, à moins que "--replication-threads" ne soit également spécifié). Cette option vous permet de spécifier des correspondances négatives, c'est-à-dire "correspond à toutes les requêtes *sauf*..." où les exceptions sont définies en spécifiant diverses options "--ignore".

Cette option n'est *pas* la même que "--victims" "all". Cette option correspond à toutes les requêtes au sein d'une classe, tandis que "--victims" "all" spécifie que toutes les requêtes correspondantes d'une classe (quelle que soit la façon dont elles ont correspondu) seront arrêtées. Normalement, cependant, les deux sont utilisées ensemble car si, par exemple, vous spécifiez "--victims" "oldest", alors même si toutes les requêtes correspondent, seule la plus ancienne sera arrêtée.

--match-command
type : string ; groupe : Query Matches

Correspond uniquement aux requêtes dont la commande correspond à cette regex Perl.

Les valeurs courantes de Command sont :

Query
Sleep
Binlog Dump
Connect
Delayed insert
Execute

SYNOPSIS

pt-kill [OPTIONS] [DSN]

DESCRIPTION

pt-kill is a tool to find and kill MySQL queries. It can find queries based on many different criteria, and can kill them on behalf of the user or kill the entire connection.

The tool can match queries based on how long they have been running, how many queries there are, or which host they came from. It can then take action by printing a KILL statement, or actually killing the query or connection.

The tool can group queries by various criteria and then match against classes of queries. For example, it can match against a class of queries from a specific host, and then kill all queries in that class that have been running for longer than a specified time.

The tool can be run in two modes:

  • Kill Mode: The tool connects to the MySQL server, finds queries based on the specified criteria, and kills them. This is the default mode.

  • Test Mode: The tool reads processlist snapshots from files and tests the matching criteria against them. This is enabled with the --test-matching option. This mode does not connect to MySQL server and does not kill any queries.

It is essential to understand that pt-kill can kill queries or connections. Killing a connection affects all queries running in that connection. If you want to kill only specific queries and not their connections, use --kill-query. Otherwise, --kill will kill the connection for matching queries.

The tool supports the following options for matching queries and taking actions:

MATCHES

These options specify criteria for matching queries. You can specify multiple matches, and all matches must be true for a query to be considered a match.

--busy-time
type: time; group: Query Matches

Match queries that have been running for longer than this time. "Longer than" means that if you specify 10, for example, queries running for greater than 10 seconds will match.

See also "--any-busy-time" and "--each-busy-time".

--connection-id
type: int; group: Query Matches

Match queries whose connection ID matches this value.

--daemon-debug
group: Query Matches

Enable debugging for the daemonized tool.

--execute-command
type: string; group: Actions

Execute this command when a query matches.

After the command is executed, pt-kill has no control over it, so the command is responsible for its own info gathering, logging, interval, etc. The command is executed each time a query matches, so be careful that the command behaves well when multiple instances are ran. No information from pt-kill is passed to the command.

See also "--wait-before-kill".

--fingerprint
group: Actions

Modifies the "--print" behaviour and forces the query fingerprint to be displayed instead of an original query.

--group-by
type: string; default: User@Host

Group queries by this attribute. See "GROUP, MATCH AND KILL".

--ignore-self
group: Query Matches

Ignore queries run by pt-kill itself.

This is useful to prevent pt-kill from killing its own queries. By default, pt-kill does not kill its own queries.

--kill
group: Actions

Kill the connection for matching queries.

This option makes pt-kill kill the connections (a.k.a. processes, threads) that have matching queries. Use "--kill-query" if you only want to kill individual queries and not their connections.

Unless "--print" is also given, no other information is printed that shows that pt-kill matched and killed a query.

See also "--wait-before-kill" and "--wait-after-kill".

--kill-busy-commands
type: string; default: Query

group: Actions

Comma sepatated list of commands that will be watched/killed if they ran for more than "--busy-time" seconds. Default: "Query"

By default, "--busy-time" kills only "Query" commands but in some cases, it is needed to make "--busy-time" to watch and kill other commands. For example, a prepared statement execution command is "Execute" instead of "Query". In this case, specifying "--kill-busy-commands=Query,Execute" will also kill the prepared stamente execution.

--kill-query
group: Actions

Kill matching queries.

This option makes pt-kill kill matching queries. This requires MySQL 5.0 or newer. Unlike "--kill" which kills the connection for matching queries, this option only kills the query, not its connection.

--login-group
type: string; group: Query Matches

Match queries run by users in this login group.

--long-running-any
type: time; group: Query Matches

Match query class if any query has been running for longer than this time. This option is deprecated and replaced by --any-busy-time.

--long-running-each
type: time; group: Query Matches

Match query class if each query has been running for longer than this time. This option is deprecated and replaced by --each-busy-time.

--match-all-databases
group: Query Matches

Match queries against all databases.

By default, pt-kill only matches queries against the default database. This option enables matching against all databases.

--match-user-regex
type: string; group: Query Matches

Match queries from users matching this regex.

--print
group: Actions

Print a KILL statement for matching queries; does not actually kill queries.

If you just want to see which queries match and would be killed without actually killing them, specify "--print". To both kill and print matching queries, specify both "--kill" and "--print".

--query-all
type: string; group: Query Matches

Match queries that match this regex.

--query-by-command
type: string; group: Query Matches

Match queries whose command matches this value.

Examples: Query, Sleep, Connect.

--query-by-db
type: string; group: Query Matches

Match queries running against this database.

--query-by-host
type: string; group: Query Matches

Match queries coming from this host.

--query-by-user
type: string; group: Query Matches

Match queries run by this user.

--replication-threads
group: Query Matches

By default, matches do not apply to replication threads; i.e. replication threads are completely ignored. Specifying this option allows matches to match (and potentially kill) replication threads on replication sources and replicas.

--test-matching
type: array; group: Query Matches

Files with processlist snapshots to test matching options against. Since the matching options can be complex, you can save snapshots of processlist in files, then test matching options against queries in those files.

This option disables "--run-time", "--interval", and "--[no]ignore-self".

CLASS MATCHES

These matches apply to entire query classes. Classes are created by specifying the "--group-by" option, else all queries are members of a single, default class.

See also "GROUP, MATCH AND KILL".

--any-busy-time
type: time; group: Class Matches

Match query class if any query has been running for longer than this time. "Longer than" means that if you specify 10, for example, the class will only match if there's at least one query that has been running for greater than 10 seconds.

See "--each-busy-time" for more details.

--each-busy-time
type: time; group: Class Matches

Match query class if each query has been running for longer than this time. "Longer than" means that if you specify 10, for example, the class will only match if each and every query has been running for greater than 10 seconds.

See also "--any-busy-time" (to match a class if ANY query has been running longer than the specified time) and "--busy-time".

--query-count
type: int; group: Class Matches

Match query class if it has at least this many queries. When queries are grouped into classes by specifying "--group-by", this option causes matches to apply only to classes with at least this many queries. If "--group-by" is not specified then this option causes matches to apply only if there are at least this many queries in the entire SHOW PROCESSLIST.

--verbose
short form: -v

Print information to STDOUT about what is being done.

ACTIONS

These actions are taken for every matching query from all classes. The actions are taken in this order: "--print", "--execute-command", "--kill" / "--kill-query". This order allows "--execute-command" to see the output of "--print" and the query before "--kill" / "--kill-query". This may be helpful because pt-kill does not pass any information to "--execute-command".

See also "GROUP, MATCH AND KILL".

--execute-command
type: string; group: Actions

Execute this command when a query matches.

After the command is executed, pt-kill has no control over it, so the command is responsible for its own info gathering, logging, interval, etc. The command is executed each time a query matches, so be careful that the command behaves well when multiple instances are ran. No information from pt-kill is passed to the command.

See also "--wait-before-kill".

See also "--wait-before-kill" and "--wait-after-kill".

DSN OPTIONS

These DSN options are used to create a DSN. Each option is given like "option=value". The options are case-sensitive, so P and p are not the same option. There cannot be whitespace before or after the "=" and if the value contains whitespace it must be quoted. DSN options are comma-separated. See the percona-toolkit manpage for full details.

  • A

    dsn: charset; copy: yes

    Default character set.

  • D

    dsn: database; copy: yes

    Default database.

  • F

    dsn: mysql_read_default_file; copy: yes

    Only read default options from the given file

  • h

    dsn: host; copy: yes

    Connect to host.

  • p

    dsn: password; copy: yes

    Password to use when connecting. If password contains commas they must be escaped with a backslash: "exam\,ple"

  • P

    dsn: port; copy: yes

    Port number to use for connection.

  • S

    dsn: mysql_socket; copy: yes

    Socket file to use for connection.

  • u

    dsn: user; copy: yes

    User for login if not current user.

  • t

    Table to log actions in, if passed through --log-dsn.

  • s

    dsn: mysql_ssl; copy: yes

    Create SSL connection

ENVIRONMENT

The environment variable "PTDEBUG" enables verbose debugging output to STDERR. To enable debugging and capture all output to a file, run the tool like:

PTDEBUG=1 pt-kill ... > FILE 2>&1

Be careful: debugging output is voluminous and can generate several megabytes of output.

ATTENTION

Using <PTDEBUG> might expose passwords. When debug is enabled, all command line parameters are shown in the output.
