pthread_atfork(3) Manuel des fonctions de bibliothèque pthread_atfork(3)

NOM

pthread_atfork - enregistrer des gestionnaires de fork

BIBLIOTHÈQUE

Bibliothèque POSIX threads (libpthread, -lpthread)

SYNTAXE

#include <pthread.h>
int pthread_atfork(typeof(void (void)) *prepare,
                   typeof(void (void)) *parent,
                   typeof(void (void)) *child);

DESCRIPTION

La fonction pthread_atfork() enregistre des gestionnaires de fork qui doivent être exécutés lorsque fork(2) est appelé par un thread quelconque dans un processus. Les gestionnaires sont exécutés dans le contexte du thread qui appelle fork(2).

Trois types de gestionnaires peuvent être enregistrés :

•
prepare spécifie un gestionnaire qui est exécuté dans le processus parent avant que le traitement de fork(2) ne commence.
•
parent spécifie un gestionnaire qui est exécuté dans le processus parent après que le traitement de fork(2) soit terminé.
•
child spécifie un gestionnaire qui est exécuté dans le processus enfant après que le traitement de fork(2) soit terminé.

L'un des trois arguments peut être NULL si aucun gestionnaire n'est nécessaire dans la phase correspondante du traitement de fork(2).

VALEUR DE RETOUR

En cas de succès, pthread_atfork() retourne zéro. En cas d'erreur, il retourne un numéro d'erreur. pthread_atfork() peut être appelé plusieurs fois par un processus pour enregistrer des gestionnaires supplémentaires. Les gestionnaires pour chaque phase sont appelés dans un ordre spécifié : les gestionnaires prepare sont appelés dans l'ordre inverse de leur enregistrement ; les gestionnaires parent et child sont appelés dans l'ordre de leur enregistrement.

ERREURS

ENOMEM
Impossible d'allouer de la mémoire pour enregistrer l'entrée de la liste des gestionnaires de fork.

NORMES

POSIX.1-2008.

HISTORIQUE

POSIX.1-2001.

NOTES

Lorsque fork(2) est appelé dans un processus multithreadé, seul le thread appelant est dupliqué dans le processus enfant. L'intention initiale de pthread_atfork() était de permettre au processus enfant d'être ramené à un état cohérent. Par exemple, au moment de l'appel à fork(2), d'autres threads peuvent avoir verrouillé des mutex qui sont visibles dans la mémoire de l'espace utilisateur dupliquée dans l'enfant. Ces mutex ne seraient jamais déverrouillés, car les threads qui ont placé les verrous ne sont pas dupliqués dans l'enfant. L'intention de pthread_atfork() était de fournir un mécanisme par lequel l'application (ou une bibliothèque) pourrait garantir que les mutex et autres états du processus et du thread seraient restaurés à un état cohérent. En pratique, cette tâche est généralement trop difficile pour être réalisable.

Après un fork(2) dans un processus multithreadé, l'enfant ne devrait appeler que des fonctions sûres pour les signaux (voir signal-safety(7)) jusqu'à ce qu'il appelle execve(2) pour exécuter un nouveau programme.

POSIX.1 spécifie que pthread_atfork() ne doit pas échouer avec l'erreur EINTR.

VOIR AUSSI

fork(2), atexit(3), pthreads(7)
