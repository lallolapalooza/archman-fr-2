PTHREAD_CREATE(3P) Manuel du programmeur POSIX PTHREAD_CREATE(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pthread_create — création de thread

SYNOPSIS

#include <pthread.h>
int pthread_create(pthread_t *restrict thread,
    const pthread_attr_t *restrict attr,
    void *(*start_routine)(void*), void *restrict arg);

DESCRIPTION

La fonction pthread_create() crée un nouveau thread, avec les attributs spécifiés par attr, au sein d'un processus. Si attr est NULL, les attributs par défaut sont utilisés. Si les attributs spécifiés par attr sont modifiés ultérieurement, les attributs du thread ne seront pas affectés. En cas de succès, pthread_create() stocke l'ID du thread créé à l'emplacement référencé par thread.

Le thread est créé en exécutant start_routine avec arg comme seul argument. Si start_routine retourne, l'effet est identique à un appel implicite à pthread_exit() utilisant la valeur de retour de start_routine comme statut de sortie. Notez que le thread dans lequel main() a été initialement invoqué est différent de celui-ci. Lorsqu'il retourne de main(), l'effet est identique à un appel implicite à exit() utilisant la valeur de retour de main() comme statut de sortie.

L'état des signaux du nouveau thread est initialisé comme suit :

*
Le masque des signaux est hérité du thread créateur.
*
L'ensemble des signaux en attente pour le nouveau thread est vide.

La locale actuelle du thread et la pile alternative ne sont pas héritées.

L'environnement flottant est hérité du thread créateur.

Si pthread_create() échoue, aucun nouveau thread n'est créé et le contenu de l'emplacement référencé par thread est indéfini.

Si _POSIX_THREAD_CPUTIME est défini, le nouveau thread aura une horloge de temps CPU accessible, et la valeur initiale de cette horloge sera définie à zéro.

Le comportement est indéfini si la valeur spécifiée par l'argument attr de pthread_create() ne fait pas référence à un objet d'attributs de thread initialisé.

VALEUR DE RETOUR

En cas de succès, la fonction pthread_create() retourne zéro ; sinon, un numéro d'erreur est retourné pour indiquer l'erreur.

ERREURS

La fonction pthread_create() échoue si :

EAGAIN
Le système n'avait pas les ressources nécessaires pour créer un autre thread, ou la limite imposée par le système sur le nombre total de threads dans un processus {PTHREAD_THREADS_MAX} serait dépassée.
EPERM
L'appelant n'a pas les privilèges appropriés pour définir les paramètres de planification ou la politique de planification requis.

La fonction pthread_create() ne retourne pas un code d'erreur [EINTR].

EXEMPLES

UTILISATION PAR L'APPLICATION

Il n'y a aucune obligation pour l'implémentation que l'ID du thread créé soit disponible avant que le nouveau thread ne commence son exécution. Le thread appelant peut obtenir l'ID du thread créé via l'argument thread de la fonction pthread_create(), et le nouveau thread peut obtenir son ID en appelant pthread_self().

RATIONNEL

Une alternative suggérée à pthread_create() serait de définir deux opérations distinctes : créer et démarrer. Certaines applications trouveraient un tel comportement plus naturel. Ada, en particulier, sépare la « création » d'une tâche de son « activation ».

La division de l'opération a été rejetée par les développeurs du standard pour de nombreuses raisons :

*
Le nombre d'appels requis pour démarrer un thread passerait d'un à deux et imposerait ainsi une charge supplémentaire aux applications qui ne nécessitent pas de synchronisation supplémentaire. Le second appel, cependant, pourrait être évité par la complication supplémentaire d'un attribut d'état de démarrage.
*
Un état supplémentaire serait introduit : « créé mais pas démarré ». Cela obligerait le standard à spécifier le comportement des opérations sur les threads lorsque la cible n'a pas encore commencé son exécution.
*
Pour les applications qui nécessitent un tel comportement, il est possible de simuler les deux étapes séparées avec les facilités actuellement fournies. La start_routine() peut se synchroniser en attendant sur une variable de condition signalée par l'opération de démarrage.

Un implémenteur Ada peut choisir de créer le thread à l'un des deux points du programme Ada : lorsque l'objet tâche est créé, ou lorsque la tâche est activée (généralement à un « begin »). Si la première approche est adoptée, la start_routine() doit attendre sur une variable de condition pour recevoir l'ordre de commencer « l'activation ». La seconde approche ne nécessite pas de telle variable de condition ni de synchronisation supplémentaire. Dans l'une ou l'autre approche, un bloc de contrôle de tâche Ada distinct devrait être créé lors de la création de l'objet tâche pour contenir les files d'attente de rendez-vous, etc.

Une extension du modèle précédent serait de permettre la modification de l'état du thread entre la création et le démarrage. Cela permettrait d'éliminer l'objet d'attributs de thread. Ceci a été rejeté car :

*
Tout état dans l'objet d'attributs de thread doit pouvoir être défini pour le thread. Cela nécessiterait la définition de fonctions pour modifier les attributs du thread. Il n'y aurait aucune réduction du nombre d'appels de fonction requis pour configurer le thread. En fait, pour une application qui crée tous les threads en utilisant des attributs identiques, le nombre d'appels de fonction requis pour configurer les threads serait considérablement augmenté. L'utilisation d'un objet d'attributs de thread permet à l'application d'effectuer un ensemble d'appels de fonction de réglage d'attributs. Sinon, l'ensemble des appels de fonction de réglage d'attributs doit être effectué pour chaque création de thread.
*
Selon l'architecture d'implémentation, les fonctions de réglage de l'état du thread nécessiteraient des appels système, ou pour d'autres raisons d'implémentation, ne pourraient pas être implémentées sous forme de macros, augmentant ainsi le coût de création du thread.
*
La capacité pour les applications de segmenter les threads par classe serait perdue.

Une autre alternative suggérée utilise un modèle similaire à celui de la création de processus, tel que « thread fork ». Les sémantiques de fork fourniraient plus de flexibilité et la fonction « create » peut être implémentée simplement en effectuant un thread fork suivi immédiatement d'un appel à la « start routine » souhaitée pour le thread. Cette alternative présente ces problèmes :

*
Pour de nombreuses implémentations, la pile entière du thread appelant devrait être dupliquée, car dans de nombreuses architectures, il n'y a aucun moyen de déterminer la taille de la trame d'appel.
*
L'efficacité est réduite car au moins une partie de la pile doit être copiée, même si dans la plupart des cas le thread n'a jamais besoin du contexte copié, puisqu'il appelle simplement la routine de démarrage souhaitée.

Si une implémentation détecte que la valeur spécifiée par l'argument attr à pthread_create() ne fait pas référence à un objet d'attributs de thread initialisé, il est recommandé que la fonction échoue et signale une erreur [EINVAL].
