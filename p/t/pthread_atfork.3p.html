PTHREAD_ATFORK(3P) Manuel du programmeur POSIX PTHREAD_ATFORK(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

pthread_atfork — enregistrer les gestionnaires de fork

SYNOPIS

#include <pthread.h>
int pthread_atfork(void (*prepare)(void), void (*parent)(void),
    void (*child)(void));

DESCRIPTION

La fonction pthread_atfork() déclare des gestionnaires de fork à appeler avant et après fork(), dans le contexte du thread qui a appelé fork(). Le gestionnaire de fork prepare est appelé avant le début du traitement de fork(). Le gestionnaire de fork parent est appelé après la fin du traitement de fork() dans le processus parent. Le gestionnaire de fork child est appelé après la fin du traitement de fork() dans le processus enfant. Si aucun traitement n'est souhaité à un ou plusieurs de ces trois points, les adresses de gestionnaire de fork correspondantes peuvent être définies sur NULL.

Si un appel fork() dans un processus multi-threadé conduit un gestionnaire de fork child à appeler une fonction qui n'est pas async-signal-safe, le comportement est indéfini.

L'ordre des appels à pthread_atfork() est significatif. Les gestionnaires de fork parent et child sont appelés dans l'ordre où ils ont été établis par les appels à pthread_atfork(). Les gestionnaires de fork prepare sont appelés dans l'ordre inverse.

VALEUR RENVOYÉE

En cas de succès, pthread_atfork() renvoie la valeur zéro ; sinon, un numéro d'erreur est renvoyé pour indiquer l'erreur.

ERREURS

La fonction pthread_atfork() échoue si :

ENOMEM
Il n'y a pas assez d'espace dans la table pour enregistrer les adresses des gestionnaires de fork.

La fonction pthread_atfork() ne renvoie pas le code d'erreur [EINTR].

EXEMPLES

Aucun.

UTILISATION PAR L'APPLICATION

Le schéma d'utilisation initial envisagé pour pthread_atfork() était que le gestionnaire de fork prepare verrouille les mutex et autres verrous, et que les gestionnaires parent et child les déverrouillent. Cependant, puisque toutes les fonctions de déverrouillage pertinentes, à l'exception de sem_post(), ne sont pas async-signal-safe, cette utilisation entraîne un comportement indéfini dans le processus enfant, à moins que la seule fonction de déverrouillage appelée soit sem_post().

RATIONALE

Il existe au moins deux problèmes sérieux avec la sémantique de fork() dans un programme multi-threadé. Un problème concerne l'état (par exemple, la mémoire) couvert par des mutex. Considérons le cas où un thread a un mutex verrouillé et que l'état couvert par ce mutex est incohérent tandis qu'un autre thread appelle fork(). Dans l'enfant, le mutex est dans l'état verrouillé (verrouillé par un thread inexistant et ne peut donc jamais être déverrouillé). Le fait que l'enfant réinitialise simplement le mutex est insatisfaisant car cette approche ne résout pas la question de la correction ou du traitement de l'état incohérent dans l'enfant.

Il est suggéré que les programmes qui utilisent fork() appellent une fonction exec très rapidement après dans le processus enfant, réinitialisant ainsi tous les états. En attendant, seules une courte liste de routines de bibliothèque async-signal-safe sont garanties d'être disponibles.

Malheureusement, cette solution ne répond pas aux besoins des bibliothèques multi-threadées. Les programmes d'application peuvent ne pas être conscients qu'une bibliothèque multi-threadée est utilisée, et ils se sentent libres d'appeler un certain nombre de routines de bibliothèque entre les appels fork() et exec, comme ils l'ont toujours fait. En effet, ils peuvent être des programmes monofilés existants et ne peuvent donc pas être censés respecter de nouvelles restrictions imposées par la bibliothèque de threads.

D'autre part, la bibliothèque multi-threadée a besoin d'un moyen de protéger son état interne pendant fork() au cas où elle serait réutilisée plus tard dans le processus enfant. Le problème survient particulièrement dans les bibliothèques d'E/S multi-threadées, qui sont presque sûres d'être appelées entre les appels fork() et exec pour effectuer la redirection des E/S. La solution peut nécessiter le verrouillage des variables mutex pendant fork(), ou elle peut impliquer simplement la réinitialisation de l'état dans l'enfant après la fin du traitement fork().

La fonction pthread_atfork() visait à fournir aux bibliothèques multi-threadées un moyen de se protéger des programmes d'application innocents qui appellent fork(), et à fournir aux programmes d'application multi-threadés un mécanisme standard pour se protéger des appels fork() dans une routine de bibliothèque ou dans l'application elle-même.

L'utilisation attendue était que le gestionnaire de préparation acquiert tous les verrous mutex et que les deux autres gestionnaires de fork les libèrent.

Par exemple, une application pourrait avoir fourni une routine de préparation qui acquiert les mutex nécessaires maintenus par la bibliothèque et fourni des routines enfant et parent qui libèrent ces mutex, garantissant ainsi que l'enfant aurait obtenu un instantané cohérent de l'état de la bibliothèque (et qu'aucun mutex n'aurait été abandonné). C'est bon en théorie, mais en réalité peu pratique. Chaque mutex et verrou du processus doit être localisé et verrouillé. Chaque composant d'un programme, y compris les composants tiers, doit participer et ils doivent s'accorder sur qui est responsable de quel mutex ou verrou. Ceci est particulièrement problématique pour les mutex et verrous dans la mémoire allouée dynamiquement. Tous les mutex et verrous internes à l'implémentation doivent également être verrouillés. Cela retarde potentiellement le thread appelant fork() pendant longtemps, voire indéfiniment, car les utilisations de ces objets de synchronisation peuvent ne pas être sous le contrôle de l'application. Un dernier problème à mentionner ici est le problème du verrouillage des flux. Au moins les flux sous le contrôle du système (comme stdin, stdout, stderr) doivent être protégés en verrouillant le flux avec flockfile(). Mais l'application elle-même aurait pu le faire, potentiellement dans le même thread appelant fork(). Dans ce cas, le processus sera bloqué.

Alternativement, certaines bibliothèques auraient pu fournir uniquement une routine child qui réinitialise les mutex de la bibliothèque et tous les états associés à une valeur connue (par exemple, ce qu'elle était lorsque l'image a été exécutée initialement). Cette approche n'est cependant pas possible, car les implémentations sont autorisées à échouer aux appels *_init() et *_destroy() pour les mutex et verrous si le mutex ou le verrou est toujours verrouillé. Dans ce cas, la routine child ne peut pas réinitialiser les mutex et les verrous.

Lorsque fork() est appelé, seul le thread appelant est dupliqué dans le processus enfant. Les variables de synchronisation restent dans le même état dans l'enfant qu'elles l'étaient dans le parent au moment où fork() a été appelé. Ainsi, par exemple, les verrous mutex peuvent être détenus par des threads qui n'existent plus dans le processus enfant, et les états associés peuvent être incohérents. L'intention était que le processus parent ait pu éviter cela par un code explicite qui acquiert et libère les verrous critiques pour l'enfant via pthread_atfork(). De plus, tous les threads critiques auraient dû être recréés et réinitialisés à l'état correct dans l'enfant (également via pthread_atfork()).

Un paquet de plus haut niveau peut acquérir des verrous sur ses propres structures de données avant d'invoquer des paquets de plus bas niveau. Dans ce scénario, l'ordre spécifié pour les appels de gestionnaires de fork permet une règle simple d'initialisation pour éviter les interblocages de paquets : un paquet initialise tous les paquets dont il dépend avant d'appeler la fonction pthread_atfork() pour lui-même.

Comme expliqué, il n'y a pas de solution appropriée pour les fonctionnalités qui nécessitent des opérations non atomiques à protéger via des mutex et des verrous. C'est pourquoi la norme POSIX.1 depuis la version de 1996 exige que le processus enfant après fork() dans un processus multi-threadé n'appelle que des interfaces async-signal-safe.
