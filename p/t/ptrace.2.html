ptrace(2) Manuel des appels système ptrace(2)

NOM

ptrace - traçage de processus

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/ptrace.h>
long ptrace(enum __ptrace_request op, pid_t pid,
            void *addr, void *data);

DESCRIPTION

L'appel système ptrace() fournit un moyen par lequel un processus (le « traceur ») peut observer et contrôler l'exécution d'un autre processus (le « tracé »), et examiner et modifier la mémoire et les registres du tracé. Il est principalement utilisé pour implémenter le débogage par points d'arrêt et le traçage des appels système.

Un tracé doit d'abord être attaché au traceur. L'attachement et les commandes ultérieures sont par thread : dans un processus multithreadé, chaque thread peut être attaché individuellement à un traceur (potentiellement différent), ou ne pas être attaché et donc non débogué. Par conséquent, « tracé » signifie toujours « (un) thread », jamais « un processus (potentiellement multithreadé) ». Les commandes ptrace sont toujours envoyées à un tracé spécifique en utilisant un appel de la forme


ptrace(PTRACE_foo, pid, ...)

où pid est l'ID de thread du thread Linux correspondant.

(Notez que dans cette page, un « processus multithreadé » signifie un groupe de threads créés à l'aide de l'indicateur CLONE_THREAD de clone(2).)

Un processus peut initier un traçage en appelant fork(2) et en faisant effectuer un PTRACE_TRACEME par le processus enfant résultant, suivi (typiquement) d'un execve(2). Alternativement, un processus peut commencer à tracer un autre processus en utilisant PTRACE_ATTACH ou PTRACE_SEIZE.

Pendant qu'il est tracé, le tracé s'arrêtera chaque fois qu'un signal sera délivré, même si le signal est ignoré. (Une exception est SIGKILL, qui a son effet habituel.) Le traceur sera notifié lors de son prochain appel à waitpid(2) (ou l'un des appels système « wait » associés) ; cet appel renverra une valeur status contenant des informations indiquant la cause de l'arrêt dans le tracé. Pendant que le tracé est arrêté, le traceur peut utiliser diverses opérations ptrace pour inspecter et modifier le tracé. Le traceur provoque ensuite la reprise normale de l'exécution du tracé, en ignorant éventuellement le signal délivré (ou même en délivrant un signal différent à la place).

Si l'option PTRACE_O_TRACEEXEC n'est pas activée, tous les appels réussis à execve(2) par le processus tracé provoqueront l'envoi d'un signal SIGTRAP, donnant au parent une chance de prendre le contrôle avant que le nouveau programme ne commence son exécution.

Lorsque le traceur a terminé le traçage, il peut provoquer la reprise de l'exécution du tracé en mode normal et non tracé via PTRACE_DETACH.

La valeur de op détermine l'opération à effectuer :

PTRACE_TRACEME
Indique que ce processus doit être tracé par son parent. Un processus ne devrait probablement pas effectuer cette opération si son parent ne s'attend pas à le tracer. (pid, addr et data sont ignorés.)
L'opération PTRACE_TRACEME est utilisée uniquement par le tracé ; les opérations restantes sont utilisées uniquement par le traceur. Dans les opérations suivantes, pid spécifie l'ID de thread du tracé sur lequel agir. Pour les opérations autres que PTRACE_ATTACH, PTRACE_SEIZE, PTRACE_INTERRUPT et PTRACE_KILL, le tracé doit être arrêté.
PTRACE_PEEKTEXT
PTRACE_PEEKDATA
Lit un mot à l'adresse addr dans la mémoire du tracé, renvoyant le mot comme résultat de l'appel ptrace(). Linux n'a pas d'espaces d'adressage texte et données distincts, donc ces deux opérations sont actuellement équivalentes. (data est ignoré ; mais voir NOTES.)
PTRACE_PEEKUSER
Lit un mot à l'offset addr dans la zone USER du tracé, qui contient les registres et d'autres informations sur le processus (voir <sys/user.h>). Le mot est renvoyé comme résultat de l'appel ptrace(). Généralement, l'offset doit être aligné sur un mot, bien que cela puisse varier selon l'architecture. Voir NOTES. (data est ignoré ; mais voir NOTES.)
PTRACE_POKETEXT
PTRACE_POKEDATA
Copie le mot data à l'adresse addr dans la mémoire du tracé. Comme pour PTRACE_PEEKTEXT et PTRACE_PEEKDATA, ces deux opérations sont actuellement équivalentes.
PTRACE_POKEUSER
Copie le mot data à l'offset addr dans la zone USER du tracé. Comme pour PTRACE_PEEKUSER, l'offset doit généralement être aligné sur un mot. Afin de maintenir l'intégrité du noyau, certaines modifications de la zone USER sont interdites.
PTRACE_GETREGS
PTRACE_GETFPREGS
Copie les registres à usage général ou les registres à virgule flottante du tracé, respectivement, à l'adresse data dans le traceur. Voir <sys/user.h> pour des informations sur le format de ces données. (addr est ignoré.) Notez que les systèmes SPARC ont le sens de data et addr inversé ; c'est-à-dire que data est ignoré et les registres sont copiés à l'adresse addr. PTRACE_GETREGS et PTRACE_GETFPREGS ne sont pas présents sur toutes les architectures.
PTRACE_GETREGSET (depuis Linux 2.6.34)
Lit les registres du tracé. addr spécifie, d'une manière dépendante de l'architecture, le type de registres à lire. NT_PRSTATUS (avec la valeur numérique 1) entraîne généralement la lecture des registres à usage général. Si le CPU possède, par exemple, des registres à virgule flottante et/ou vectoriels, ils peuvent être récupérés en définissant addr sur la constante NT_foo correspondante. data pointe vers une struct iovec, qui décrit l'emplacement et la taille du tampon de destination. Au retour, le noyau modifie iov.len pour indiquer le nombre réel d'octets renvoyés.
PTRACE_SETREGS
PTRACE_SETFPREGS
Modifie les registres à usage général ou à virgule flottante du tracé, respectivement, à partir de l'adresse data dans le traceur. Comme pour PTRACE_POKEUSER, certaines modifications des registres à usage général peuvent être interdites. (addr est ignoré.) Notez que les systèmes SPARC ont le sens de data et addr inversé ; c'est-à-dire que data est ignoré et les registres sont copiés depuis l'adresse addr. PTRACE_SETREGS et PTRACE_SETFPREGS ne sont pas présents sur toutes les architectures.
PTRACE_SETREGSET (depuis Linux 2.6.34)
Modifie les registres du tracé. La signification de addr et data est analogue à PTRACE_GETREGSET.
PTRACE_GETSIGINFO (depuis Linux 2.3.99-pre6)
Récupère des informations sur le signal qui a provoqué l'arrêt. Copie une structure siginfo_t (voir sigaction(2)) du tracé vers l'adresse data dans le traceur. (addr est ignoré.)
PTRACE_SETSIGINFO (depuis Linux 2.3.99-pre6)
Définit les informations du signal : copie une structure siginfo_t depuis l'adresse data dans le traceur vers le tracé. Cela n'affectera que les signaux qui seraient normalement délivrés au tracé et qui ont été interceptés par le traceur. Il peut être difficile de distinguer ces signaux normaux des signaux synthétiques

générés par ptrace() lui-même. (addr est ignoré.)
PTRACE_PEEKSIGINFO (depuis Linux 3.10)
Récupère les structures siginfo_t sans retirer les signaux d'une file d'attente. addr pointe vers une structure ptrace_peeksiginfo_args qui spécifie la position ordinale à partir de laquelle la copie des signaux doit commencer, et le nombre de signaux à copier. Les structures siginfo_t sont copiées dans le tampon pointé par data. La valeur de retour contient le nombre de signaux copiés (zéro indique qu'aucun signal ne correspond à la position ordinale spécifiée). Dans les structures siginfo retournées, le champ si_code inclut des informations (__SI_CHLD, __SI_FAULT, etc.) qui ne sont pas autrement exposées à l'espace utilisateur.


struct ptrace_peeksiginfo_args {
    u64 off;    /* Position ordinale dans la file d'attente à laquelle
                   commencer la copie des signaux */
    u32 flags;  /* PTRACE_PEEKSIGINFO_SHARED ou 0 */
    s32 nr;     /* Nombre de signaux à copier */
};
Actuellement, il n'y a qu'un seul drapeau, PTRACE_PEEKSIGINFO_SHARED, pour vider les signaux de la file d'attente de signaux du processus entier. Si ce drapeau n'est pas défini, les signaux sont lus à partir de la file d'attente par thread du thread spécifié.
PTRACE_GETSIGMASK (depuis Linux 3.11)
Place une copie du masque des signaux bloqués (voir sigprocmask(2)) dans le tampon pointé par data, qui doit être un pointeur vers un tampon de type sigset_t. L'argument addr contient la taille du tampon pointé par data (c'est-à-dire sizeof(sigset_t)).
PTRACE_SETSIGMASK (depuis Linux 3.11)
Modifie le masque des signaux bloqués (voir sigprocmask(2)) pour la valeur spécifiée dans le tampon pointé par data, qui doit être un pointeur vers un tampon de type sigset_t. L'argument addr contient la taille du tampon pointé par data (c'est-à-dire sizeof(sigset_t)).
PTRACE_SETOPTIONS (depuis Linux 2.4.6; voir BUGS pour les mises en garde)
Définit les options ptrace à partir de data. (addr est ignoré.) data est interprété comme un masque de bits d'options, qui sont spécifiées par les drapeaux suivants :
PTRACE_O_EXITKILL (depuis Linux 3.8)
Envoie un signal SIGKILL au tracee si le traceur se termine. Cette option est utile pour les geôliers ptrace qui veulent s'assurer que les tracees ne peuvent jamais échapper au contrôle du traceur.
PTRACE_O_TRACECLONE (depuis Linux 2.5.46)
Arrête le tracee lors du prochain appel clone(2) et démarre automatiquement le traçage du processus nouvellement cloné, qui commencera par un SIGSTOP, ou PTRACE_EVENT_STOP si PTRACE_SEIZE a été utilisé. Un appel waitpid(2) par le traceur renverra une valeur status telle que
  status>>8 == (SIGTRAP | (PTRACE_EVENT_CLONE<<8))
Le PID du nouveau processus peut être récupéré avec PTRACE_GETEVENTMSG.
Cette option peut ne pas intercepter les appels clone(2) dans tous les cas. Si le tracee appelle clone(2) avec le drapeau CLONE_VFORK, PTRACE_EVENT_VFORK sera délivré à la place si PTRACE_O_TRACEVFORK est défini ; sinon, si le tracee appelle clone(2) avec le signal de sortie défini à SIGCHLD, PTRACE_EVENT_FORK sera délivré si PTRACE_O_TRACEFORK est défini.
PTRACE_O_TRACEEXEC (depuis Linux 2.5.46)
Arrête le tracee lors du prochain appel execve(2). Un appel waitpid(2) par le traceur renverra une valeur status telle que
  status>>8 == (SIGTRAP | (PTRACE_EVENT_EXEC<<8))
Si le thread qui exécute n'est pas un chef de groupe de threads, l'ID du thread est réinitialisé à l'ID du chef de groupe de threads avant cet arrêt. Depuis Linux 3.0, l'ancien ID de thread peut être récupéré avec PTRACE_GETEVENTMSG.
PTRACE_O_TRACEEXIT (depuis Linux 2.5.60)
Arrête le tracee à la sortie. Un appel waitpid(2) par le traceur renverra une valeur status telle que
  status>>8 == (SIGTRAP | (PTRACE_EVENT_EXIT<<8))
Le statut de sortie du tracee peut être récupéré avec PTRACE_GETEVENTMSG.
Le tracee est arrêté tôt pendant la sortie du processus, lorsque les registres sont toujours disponibles, permettant au traceur de voir où la sortie s'est produite, tandis que la notification de sortie normale est effectuée après que le processus a fini de sortir. Même si le contexte est disponible, le traceur ne peut pas empêcher la sortie à ce stade.
PTRACE_O_TRACEFORK (depuis Linux 2.5.46)
Arrête le tracee lors du prochain appel fork(2) et démarre automatiquement le traçage du processus nouvellement créé, qui commencera par un SIGSTOP, ou PTRACE_EVENT_STOP si PTRACE_SEIZE a été utilisé. Un appel waitpid(2) par le traceur renverra une valeur status telle que
  status>>8 == (SIGTRAP | (PTRACE_EVENT_FORK<<8))
Le PID du nouveau processus peut être récupéré avec PTRACE_GETEVENTMSG.
PTRACE_O_TRACESYSGOOD (depuis Linux 2.4.6)
Lors de la délivrance des interruptions d'appel système, définit le bit 7 dans le numéro de signal (c'est-à-dire, délivre SIGTRAP|0x80). Cela permet au traceur de distinguer facilement les interruptions normales de celles causées par un appel système.
PTRACE_O_TRACEVFORK (depuis Linux 2.5.46)
Arrête le tracee lors du prochain appel vfork(2) et démarre automatiquement le traçage du processus nouvellement créé, qui commencera par un SIGSTOP, ou PTRACE_EVENT_STOP si PTRACE_SEIZE a été utilisé. Un appel waitpid(2) par le traceur renverra une valeur status telle que
  status>>8 == (SIGTRAP | (PTRACE_EVENT_VFORK<<8))
Le PID du nouveau processus peut être récupéré avec PTRACE_GETEVENTMSG.
PTRACE_O_TRACEVFORKDONE (depuis Linux 2.5.60)
Arrête le tracee à la fin du prochain appel vfork(2). Un appel waitpid(2) par le traceur renverra une valeur status telle que
  status>>8 == (SIGTRAP | (PTRACE_EVENT_VFORK_DONE<<8))
Le PID du nouveau processus peut (depuis Linux 2.6.18) être récupéré avec PTRACE_GETEVENTMSG.
PTRACE_O_TRACESECCOMP (depuis Linux 3.5)
Arrête le tracee lorsqu'une règle seccomp(2) SECCOMP_RET_TRACE est déclenchée. Un appel waitpid(2) par le traceur renverra une valeur status telle que
  status>>8 == (SIGTRAP | (PTRACE_EVENT_SECCOMP<<8))
Bien que cela déclenche un arrêt PTRACE_EVENT, c'est similaire à un arrêt à l'entrée d'un appel système. Pour plus de détails, voir la note sur PTRACE_EVENT_SECCOMP ci-dessous. Les données de l'événement seccomp (provenant de la partie SECCOMP_RET_DATA de la règle du filtre seccomp) peuvent être récupérées avec PTRACE_GETEVENTMSG.
PTRACE_O_SUSPEND_SECCOMP (depuis Linux 4.3)
Suspend les protections seccomp du tracee. Ceci s'applique quel que soit le mode, et peut être utilisé lorsque le tracee n'a pas encore installé de filtres seccomp. C'est-à-dire qu'un cas d'utilisation valide est de suspendre les protections seccomp d'un tracee avant qu'elles ne soient installées par le tracee, de laisser le tracee installer les filtres, puis de désactiver ce drapeau lorsque les filtres doivent être repris. La définition de cette option nécessite que le traceur ait la capacité CAP_SYS_ADMIN, qu'il n'ait aucune protection seccomp installée, et que PTRACE_O_SUSPEND_SECCOMP ne soit pas défini sur lui-même.
PTRACE_GETEVENTMSG (depuis Linux 2.5.46)
Récupère un message (sous forme de unsigned long) concernant l'événement ptrace qui vient de se produire, le plaçant à l'adresse data dans le traceur. Pour PTRACE_EVENT_EXIT, il s'agit du statut de sortie du tracee. Pour PTRACE_EVENT_FORK, PTRACE_EVENT_VFORK, PTRACE_EVENT_VFORK_DONE et PTRACE_EVENT_CLONE, il s'agit du PID du nouveau processus. Pour PTRACE_EVENT_SECCOMP, il s'agit du SECCOMP_RET_DATA du filtre seccomp associé à la règle déclenchée. (addr est ignoré.)
PTRACE_CONT
Redémarre le processus tracee arrêté. Si data est différent de zéro, il est interprété comme le numéro d'un signal à délivrer au tracee ; sinon, aucun signal n'est délivré. Ainsi, par exemple, le traceur peut contrôler si un signal envoyé au tracee est délivré ou non. (addr est ignoré.)
PTRACE_SYSCALL
PTRACE_SINGLESTEP
Redémarre le tracee arrêté comme pour PTRACE_CONT, mais organise pour que le tracee soit arrêté à la prochaine entrée ou sortie d'un appel système, ou après l'exécution d'une seule instruction, respectivement. (Le tracee sera également, comme d'habitude, arrêté lors
(réception d'un signal.) Du point de vue du traceur, le tracé apparaîtra comme arrêté à la réception d'un SIGTRAP. Ainsi, pour PTRACE_SYSCALL, par exemple, l'idée est d'inspecter les arguments de l'appel système au premier arrêt, puis d'effectuer un autre PTRACE_SYSCALL et d'inspecter la valeur de retour de l'appel système au second arrêt. L'argument data est traité comme pour PTRACE_CONT. (addr est ignoré.)
PTRACE_SET_SYSCALL (depuis Linux 2.6.16)
Lors d'un arrêt à l'entrée d'un appel système, modifie le numéro de l'appel système sur le point d'être exécuté pour le numéro spécifié dans l'argument data. L'argument addr est ignoré. Cette opération n'est actuellement prise en charge que sur arm (et arm64, mais uniquement pour des raisons de compatibilité ascendante), mais la plupart des autres architectures ont d'autres moyens d'y parvenir (généralement en modifiant le registre dans lequel le code utilisateur a passé le numéro de l'appel système).
PTRACE_SYSEMU
PTRACE_SYSEMU_SINGLESTEP (depuis Linux 2.6.14)
Pour PTRACE_SYSEMU, continue et s'arrête à l'entrée de l'appel système suivant, qui ne sera pas exécuté. Voir la documentation sur les arrêts d'appels système ci-dessous. Pour PTRACE_SYSEMU_SINGLESTEP, fait de même mais effectue également un pas à pas si ce n'est pas un appel système. Cet appel est utilisé par des programmes comme User Mode Linux qui souhaitent émuler tous les appels système du processus tracé. L'argument data est traité comme pour PTRACE_CONT. L'argument addr est ignoré. Ces opérations ne sont actuellement prises en charge que sur x86.
PTRACE_LISTEN (depuis Linux 3.4)
Redémarre le processus tracé arrêté, mais l'empêche de s'exécuter. L'état résultant du processus tracé est similaire à celui d'un processus arrêté par un SIGSTOP (ou un autre signal d'arrêt). Voir la sous-section "arrêt de groupe" pour plus d'informations. PTRACE_LISTEN ne fonctionne que sur les processus tracés attachés par PTRACE_SEIZE.
PTRACE_KILL
Envoie un SIGKILL au processus tracé pour le terminer. (addr et data sont ignorés.)
Cette opération est dépréciée ; ne l'utilisez pas ! Envoyez plutôt un SIGKILL directement en utilisant kill(2) ou tgkill(2). Le problème avec PTRACE_KILL est qu'il nécessite que le processus tracé soit dans un état d'arrêt de livraison de signal, sinon il peut ne pas fonctionner (c'est-à-dire qu'il peut se terminer avec succès mais ne pas tuer le processus tracé). En revanche, l'envoi direct d'un SIGKILL n'a pas une telle limitation.
PTRACE_INTERRUPT (depuis Linux 3.4)
Arrête un processus tracé. Si le processus tracé est en cours d'exécution ou en sommeil dans l'espace noyau et que PTRACE_SYSCALL est actif, l'appel système est interrompu et un arrêt de sortie d'appel système est signalé. (L'appel système interrompu est redémarré lorsque le processus tracé est redémarré.) Si le processus tracé était déjà arrêté par un signal et que PTRACE_LISTEN lui a été envoyé, le processus tracé s'arrête avec PTRACE_EVENT_STOP et WSTOPSIG(status) renvoie le signal d'arrêt. Si un autre arrêt ptrace se produit en même temps (par exemple, si un signal est envoyé au processus tracé), cet arrêt ptrace se produit. Si rien de ce qui précède ne s'applique (par exemple, si le processus tracé est en cours d'exécution dans l'espace utilisateur), il s'arrête avec PTRACE_EVENT_STOP et WSTOPSIG(status) est égal à SIGTRAP. PTRACE_INTERRUPT ne fonctionne que sur les processus tracés attachés par PTRACE_SEIZE.
PTRACE_ATTACH
Attache au processus spécifié par pid, en faisant de celui-ci un processus tracé du processus appelant. Le processus tracé reçoit un SIGSTOP, mais ne s'est pas nécessairement arrêté à la fin de cet appel ; utilisez waitpid(2) pour attendre que le processus tracé s'arrête. Voir la sous-section "Attacher et détacher" pour plus d'informations. (addr et data sont ignorés.)
La permission d'effectuer un PTRACE_ATTACH est régie par une vérification du mode d'accès ptrace PTRACE_MODE_ATTACH_REALCREDS ; voir ci-dessous.
PTRACE_SEIZE (depuis Linux 3.4)
Attache au processus spécifié par pid, en faisant de celui-ci un processus tracé du processus appelant. Contrairement à PTRACE_ATTACH, PTRACE_SEIZE n'arrête pas le processus. Les arrêts de groupe sont rapportés comme PTRACE_EVENT_STOP et WSTOPSIG(status) renvoie le signal d'arrêt. Les enfants automatiquement attachés s'arrêtent avec PTRACE_EVENT_STOP et WSTOPSIG(status) renvoie SIGTRAP au lieu de leur recevoir le signal SIGSTOP. execve(2) ne délivre pas de SIGTRAP supplémentaire. Seul un processus "seized" (capturé) peut accepter les commandes PTRACE_INTERRUPT et PTRACE_LISTEN. Le comportement "seized" décrit ci-dessus est hérité par les enfants qui sont automatiquement attachés en utilisant PTRACE_O_TRACEFORK, PTRACE_O_TRACEVFORK, et PTRACE_O_TRACECLONE. addr doit être zéro. data contient un masque de bits d'options ptrace à activer immédiatement.
La permission d'effectuer un PTRACE_SEIZE est régie par une vérification du mode d'accès ptrace PTRACE_MODE_ATTACH_REALCREDS ; voir ci-dessous.
PTRACE_SECCOMP_GET_FILTER (depuis Linux 4.4)
Cette opération permet au traceur de récupérer les filtres BPF classiques du processus tracé.
addr est un entier spécifiant l'index du filtre à récupérer. Le filtre le plus récemment installé a l'index 0. Si addr est supérieur au nombre de filtres installés, l'opération échoue avec l'erreur ENOENT.
data est soit un pointeur vers un tableau de struct sock_filter suffisamment grand pour stocker le programme BPF, soit NULL si le programme ne doit pas être stocké.
En cas de succès, la valeur de retour est le nombre d'instructions dans le programme BPF. Si data était NULL, cette valeur de retour peut être utilisée pour dimensionner correctement le tableau struct sock_filter passé lors d'un appel ultérieur.
Cette opération échoue avec l'erreur EACCES si l'appelant ne possède pas la capacité CAP_SYS_ADMIN ou si l'appelant est en mode seccomp strict ou filtré. Si le filtre référencé par addr n'est pas un filtre BPF classique, l'opération échoue avec l'erreur EMEDIUMTYPE.
Cette opération est disponible si le noyau a été configuré avec les options CONFIG_SECCOMP_FILTER et CONFIG_CHECKPOINT_RESTORE.
PTRACE_DETACH
Redémarre le processus tracé arrêté comme pour PTRACE_CONT, mais le détache d'abord. Sous Linux, un processus tracé peut être détaché de cette manière, quelle que soit la méthode utilisée pour initier le traçage. (addr est ignoré.)
PTRACE_GET_THREAD_AREA (depuis Linux 2.6.0)
Cette opération effectue une tâche similaire à get_thread_area(2). Elle lit l'entrée TLS dans le GDT dont l'index est donné dans addr, plaçant une copie de l'entrée dans le struct user_desc pointé par data. (Par contraste avec get_thread_area(2), le entry_number du struct user_desc est ignoré.)
PTRACE_SET_THREAD_AREA (depuis Linux 2.6.0)
Cette opération effectue une tâche similaire à set_thread_area(2). Elle définit l'entrée TLS dans le GDT dont l'index est donné dans addr, lui attribuant les données fournies dans le struct user_desc pointé par data. (Par contraste avec set_thread_area(2), le entry_number du struct user_desc est ignoré ; en d'autres termes, cette opération ptrace ne peut pas être utilisée pour allouer une entrée TLS libre.)
PTRACE_GET_SYSCALL_INFO (depuis Linux 5.3)
Récupère des informations sur l'appel système qui a provoqué l'arrêt. Les informations sont placées dans le tampon pointé par l'argument data, qui doit être un pointeur vers un tampon de type struct ptrace_syscall_info. L'argument addr contient la taille du tampon pointé par l'argument data (c'est-à-dire sizeof(struct ptrace_syscall_info)). La valeur de retour contient le nombre d'octets disponibles à écrire par le noyau. Si la taille des données à écrire par le noyau dépasse la taille spécifiée par l'argument addr, les données de sortie sont tronquées.
La structure ptrace_syscall_info contient les champs suivants :

struct ptrace_syscall_info {
    __u8 op;        /* Type d'arrêt d'appel système */
    __u32 arch;     /* Valeur AUDIT_ARCH_* ; voir seccomp(2) */
    __u64 instruction_pointer; /* Pointeur d'instruction CPU */
    __u64 stack_pointer;    /* Pointeur de pile CPU */
    union {
        struct {    /* op == PTRACE_SYSCALL_INFO_ENTRY */
            __u64 nr;       /* Numéro d'appel système */
            __u64 args[6];  /* Arguments d'appel système */
        } entry;
        struct {    /* op == PTRACE_SYSCALL_INFO_EXIT */
            __s64 rval;     /* Valeur de retour d'appel système */
            __u8 is_error;  /* Indicateur d'erreur d'appel système ;

NAME

ptrace - process tracing and control

SYNOPSIS

#include <sys/ptrace.h>

<unistd.h>

<sys/wait.h>

long ptrace(enum __ptrace_request request, pid_t pid, void *addr, void *data);

DESCRIPTION

The ptrace system call provides a mechanism by which one process (the parent) can observe and control the execution of another process (the child).

It can be used to implement a process debugger, for example. The child process is required to first ptrace(PTRACE_TRACEME, 0, NULL, NULL). Then, it is normally executed using execve(2) (or other execution-starting system calls). When the child process incurs a condition that requires the tracer's attention (a "stop"), the child is stopped, and the tracer is notified.

The tracer can then examine and modify the child's memory and registers, and control the child's execution, typically using further ptrace calls. When finished, the tracer can restart the child, continue execution, or kill it.

The set of request arguments is extensive. The full list is in <sys/ptrace.h>, but the most common ones are:

PTRACE_TRACEME
Used by a child process prior to calling execve(2). It indicates that this process should be traced by its parent. All signals received by the child will be delivered to the parent. The child process is stopped when it receives a signal (as if it were traced by the parent using ptrace) and when it calls execve(2). pid, addr, and data are ignored.
PTRACE_PEEKTEXT, PTRACE_PEEKDATA
Read a word from the child process's memory at the address addr. The word is returned as the result of the ptrace call. addr must be aligned to a word boundary. data is ignored. PTRACE_PEEKTEXT and PTRACE_PEEKDATA are synonyms; the choice depends on the architecture.
PTRACE_PEEKUSER
Read a word from the child process's user area at offset addr. The user area is a memory region that holds the kernel's view of the process state, including its registers. The word is returned as the result of the ptrace call. addr must be aligned to a word boundary. data is ignored. The offsets are defined in <sys/user.h>.
PTRACE_POKETEXT, PTRACE_POKEDATA
Write the word data to the child process's memory at the address addr. addr must be aligned to a word boundary. The effect is to overwrite the child's memory. PTRACE_POKETEXT and PTRACE_POKEDATA are synonyms; the choice depends on the architecture.
PTRACE_POKEUSER
Write the word data to the child process's user area at offset addr. addr must be aligned to a word boundary. The effect is to overwrite the child's saved registers or other user area information.
PTRACE_SYSCALL
Continue the child process, but stop when the child enters the next system call, or when the child receives a signal. The child is then stopped, and waitpid(2) in the parent will return with status >> 8 == (SIGTRAP | (trapno << 8)). See PTRACE_SYSCALL_INFO_ENTRY below. addr is ignored. data is treated as the signal number to be delivered to the child. If data is 0, then no signal is sent.
PTRACE_CONT
Continue the child process. addr is the address where the child should resume execution (a NULL value means resume at the current location). data is the signal number to be delivered to the child. If data is 0, then no signal is sent. If the child was stopped at a system call using PTRACE_SYSCALL, that system call will be restarted (unless the signal is SIGKILL`).
PTRACE_SINGLESTEP
Like PTRACE_CONT, but the child process is restarted with single-step tracing enabled. This causes the child to be stopped when it executes the next instruction. addr and data are ignored (as is the signal number, even if nonzero).
PTRACE_DETACH
Like PTRACE_CONT, but detach the child from the tracer. The child continues its execution, and tracing is disabled for it. addr must be 0. data is the signal number to be delivered to the child. If data is 0, then no signal is sent.
PTRACE_ATTACH
Attach to an existing process specified by pid. The process must be a descendant of the calling process (unless the caller has CAP_SYS_PTRACE capability). The process is sent SIGSTOP, and it stops. The tracer can then use other ptrace requests to observe and control the traced process. addr and data are ignored.
PTRACE_SEIZE
Similar to PTRACE_ATTACH, but it suppresses the SIGSTOP signal. The process is stopped by the ptrace call itself, and the tracer is notified via waitpid(2) with status >> 8 == (PTRACE_EVENT_STOP | (SIGTRAP << 8)). addr and data are ignored.
PTRACE_INTERRUPT
Interrupt the specified process. This is similar to PTRACE_SEIZE, but it stops the process as soon as possible, even if it is currently in a system call. The tracer is notified via waitpid(2) with status >> 8 == (PTRACE_EVENT_STOP | (SIGTRAP << 8)). addr and data are ignored.
PTRACE_KILL
Terminates the child process specified by pid. It is equivalent to sending SIGKILL to the child. addr and data are ignored.
PTRACE_LISTEN
Wait for the specified process pid to stop. This is used when tracing a process group. The tracer calls ptrace for each process in the group with PTRACE_ATTACH. Then, the tracer calls ptrace for each process with PTRACE_LISTEN. This call will return when any of the processes in the group stops. The return value is the pid of the stopped process. addr and data are ignored.
PTRACE_SIGIMGPOLICY
Get the security policy identifier that caused the process to stop.
PTRACE_SECCOMP_ERRNO
Get the errno value that caused the seccomp filter to kill the process.
PTRACE_GET_SYSCALL_INFO
Returns detailed information about the cause of a system call stop. The information is written to the memory region pointed to by data. The layout of this structure depends on the type of stop. The addr argument specifies the type of information requested. The structure that is filled is a union, struct ptrace_syscall_info, with the following members:
PTRACE_SYSCALL_INFO_ENTRY
The entry component of the union contains information relating to a system call entry stop.
PTRACE_SYSCALL_INFO_EXIT
The exit component of the union contains information relating to a system call exit stop.
PTRACE_SYSCALL_INFO_SECCOMP
The seccomp component of the union contains information relating to a PTRACE_EVENT_SECCOMP stop.
PTRACE_SYSCALL_INFO_NONE
No component of the union contains relevant information.
In case of system call entry or exit stops, the data returned by PTRACE_GET_SYSCALL_INFO is limited to type PTRACE_SYSCALL_INFO_NONE unless PTRACE_O_TRACESYSGOOD option is set before the corresponding system call stop has occurred.

Death under ptrace

When a (possibly multithreaded) process receives a killing signal (one whose disposition is set to SIG_DFL and whose default action is to kill the process), all threads exit. Tracees report their death to their tracer(s). Notification of this event is delivered via waitpid(2).

Note that the killing signal will first cause signal-delivery-stop (on one tracee only), and only after it is injected by the tracer (or after it was dispatched to a thread which isn't traced), will death from the signal happen on all tracees within a multithreaded process. (The term "signal-delivery-stop" is explained below.)

SIGKILL does not generate signal-delivery-stop and therefore the tracer can't suppress it. SIGKILL kills even within system calls (syscall-exit-stop is not generated prior to death by SIGKILL). The net effect is that SIGKILL always kills the process (all its threads), even if some threads of the process are ptraced.

When the tracee calls _exit(2), it reports its death to its tracer. Other threads are not affected.

When any thread executes exit_group(2), every tracee in its thread group reports its death to its tracer.

If the PTRACE_O_TRACEEXIT option is on, PTRACE_EVENT_EXIT will happen before actual death. This applies to exits via exit(2), exit_group(2), and signal deaths (except SIGKILL, depending on the kernel version; see BUGS below), and when threads are torn down on execve(2) in a multithreaded process.

The tracer cannot assume that the ptrace-stopped tracee exists. There are many scenarios when the tracee may die while stopped (such as SIGKILL). Therefore, the tracer must be prepared to handle an ESRCH error on any ptrace operation. Unfortunately, the same error is returned if the tracee exists but is not ptrace-stopped (for commands which require a stopped tracee), or if it is not traced by the process which issued the ptrace call. The tracer needs to keep track of the stopped/running state of the tracee, and interpret ESRCH as "tracee died unexpectedly" only if it knows that the tracee has been observed to enter ptrace-stop. Note that there is no guarantee that waitpid(WNOHANG) will reliably report the tracee's death status if a ptrace operation returned ESRCH. waitpid(WNOHANG) may return 0 instead. In other words, the tracee may be "not yet fully dead", but already refusing ptrace operations.

The tracer can't assume that the tracee always ends its life by reporting WIFEXITED(status) or WIFSIGNALED(status); there are cases where this does not occur. For example, if a thread other than thread group leader does an execve(2), it disappears; its PID will never be seen again, and any subsequent ptrace stops will be reported under the thread group leader's PID.

Stopped states

A tracee can be in two states: running or stopped. For the purposes of ptrace, a tracee which is blocked in a system call (such as read(2), pause(2), etc.) is nevertheless considered to be running, even if the tracee is blocked for a long time. The state of the tracee after PTRACE_LISTEN is somewhat of a gray area: it is not in any ptrace-stop (ptrace commands won't work on it, and it will deliver waitpid(2) notifications), but it also may be considered "stopped" because it is not executing instructions (is not scheduled), and if it was in group-stop before PTRACE_LISTEN, it will not respond to signals until SIGCONT is received.

There are many kinds of states when the tracee is stopped, and in ptrace discussions they are often conflated. Therefore, it is important to use precise terms.

In this manual page, any stopped state in which the tracee is ready to accept ptrace commands from the tracer is called ptrace-stop. Ptrace-stops can be further subdivided into signal-delivery-stop, group-stop, syscall-stop, PTRACE_EVENT stops, and so on. These stopped states are described in detail below.

When the running tracee enters ptrace-stop, it notifies its tracer using waitpid(2) (or one of the other "wait" system calls). Most of this manual page assumes that the tracer waits with:


pid = waitpid(pid_or_minus_1, &status, __WALL);

Ptrace-stopped tracees are reported as returns with pid greater than 0 and WIFSTOPPED(status) true.

The __WALL flag does not include the WSTOPPED and WEXITED flags, but implies their functionality.

Setting the WCONTINUED flag when calling waitpid(2) is not recommended: the "continued" state is per-process and consuming it can confuse the real parent of the tracee.

Use of the WNOHANG flag may cause waitpid(2) to return 0 ("no wait results available yet") even if the tracer knows there should be a notification. Example:


errno = 0;
ptrace(PTRACE_CONT, pid, 0L, 0L);
if (errno == ESRCH) {
    /* tracee is dead */
    r = waitpid(tracee, &status, __WALL | WNOHANG);
    /* r can still be 0 here! */
}

The following kinds of ptrace-stops exist: signal-delivery-stops, group-stops, PTRACE_EVENT stops, syscall-stops. They all are reported by waitpid(2) with WIFSTOPPED(status) true. They may be differentiated by examining the value status>>8, and if there is ambiguity in that value, by querying PTRACE_GETSIGINFO. (Note: the WSTOPSIG(status) macro can't be used to perform this examination, because it returns the value (status>>8) & 0xff.)

Signal-delivery-stop

When a (possibly multithreaded) process receives any signal except SIGKILL, the kernel selects an arbitrary thread which handles the signal. (If the signal is generated with tgkill(2), the target thread can be explicitly selected by the caller.) If the selected thread is traced, it enters signal-delivery-stop. At this point, the signal is not yet delivered to the process, and can be suppressed by the tracer. If the tracer doesn't suppress the signal, it passes the signal to the tracee in the next ptrace restart operation. This second step of signal delivery is called signal injection in this manual page. Note that if the signal is blocked, signal-delivery-stop doesn't happen until the signal is unblocked, with the usual exception that SIGSTOP can't be blocked.

Signal-delivery-stop is observed by the tracer as waitpid(2) returning with WIFSTOPPED(status) true, with the signal returned by WSTOPSIG(status). If the signal is SIGTRAP, this may be a different kind of ptrace-stop; see the "Syscall-stops" and "execve" sections below for details. If WSTOPSIG(status) returns a stopping signal, this may be a group-stop; see below.

Signal injection and suppression

After signal-delivery-stop is observed by the tracer, the tracer should restart the tracee with the call


ptrace(PTRACE_restart, pid, 0, sig)

where PTRACE_restart is one of the restarting ptrace operations. If sig is 0, then a signal is not delivered. Otherwise, the signal sig is delivered. This operation is called signal injection in this manual page, to distinguish it from signal-delivery-stop.

The sig value may be different from the WSTOPSIG(status) value: the tracer can cause a different signal to be injected.

Note that a suppressed signal still causes system calls to return prematurely. In this case, system calls will be restarted: the tracer will observe the tracee to reexecute the interrupted system call (or restart_syscall(2) system call for a few system calls which use a different mechanism for restarting) if the tracer uses PTRACE_SYSCALL. Even system calls (such as poll(2)) which are not restartable after signal are restarted after signal is suppressed; however, kernel bugs exist which cause some system calls to fail with EINTR even though no observable signal is injected to the tracee.

Restarting ptrace commands issued in ptrace-stops other than signal-delivery-stop are not guaranteed to inject a signal, even if sig is nonzero. No error is reported; a nonzero sig may simply be ignored. Ptrace users should not try to "create a new signal" this way: use tgkill(2) instead.

Arrêt en groupe

Lorsqu'un processus (éventuellement multithreadé) reçoit un signal d'arrêt, tous ses threads s'arrêtent. Si certains threads sont tracés, ils entrent dans un arrêt en groupe. Notez que le signal d'arrêt provoquera d'abord un arrêt de livraison de signal (sur un seul tracee), et ce n'est qu'après son injection par le traceur (ou après qu'il a été distribué à un thread qui n'est pas tracé), que l'arrêt en groupe sera initié sur *tous* les tracees au sein du processus multithreadé. Comme d'habitude, chaque tracee signale son arrêt en groupe séparément au traceur correspondant.

L'arrêt en groupe est observé par le traceur comme waitpid(2) retournant avec WIFSTOPPED(status) vrai, le signal d'arrêt étant disponible via WSTOPSIG(status). Le même résultat est retourné par d'autres classes d'arrêts ptrace, c'est pourquoi la pratique recommandée est d'effectuer l'appel


ptrace(PTRACE_GETSIGINFO, pid, 0, &siginfo)

L'appel peut être évité si le signal n'est pas SIGSTOP, SIGTSTP, SIGTTIN ou SIGTTOU ; seuls ces quatre signaux sont des signaux d'arrêt. Si le traceur observe autre chose, il ne peut pas s'agir d'un arrêt en groupe. Sinon, le traceur doit appeler PTRACE_GETSIGINFO. Si PTRACE_GETSIGINFO échoue avec EINVAL, alors il s'agit définitivement d'un arrêt en groupe. (D'autres codes d'échec sont possibles, tels que ESRCH ("aucun processus de ce type") si un SIGKILL a tué le tracee.)

Si le tracee a été attaché en utilisant PTRACE_SEIZE, l'arrêt en groupe est indiqué par PTRACE_EVENT_STOP: status>>16 == PTRACE_EVENT_STOP. Cela permet de détecter les arrêts en groupe sans nécessiter un appel supplémentaire à PTRACE_GETSIGINFO.

Depuis Linux 2.6.38, après que le traceur a vu l'arrêt ptrace du tracee et jusqu'à ce qu'il le redémarre ou le tue, le tracee ne s'exécute pas et n'envoie pas de notifications (sauf la mort par SIGKILL) au traceur, même si le traceur entre dans un autre appel à waitpid(2).

Le comportement du noyau décrit dans le paragraphe précédent provoque un problème dans la gestion transparente des signaux d'arrêt. Si le traceur redémarre le tracee après un arrêt en groupe, le signal d'arrêt est effectivement ignoré — le tracee ne reste pas arrêté, il s'exécute. Si le traceur ne redémarre pas le tracee avant d'entrer dans le prochain appel à waitpid(2), les futurs signaux SIGCONT ne seront pas rapportés au traceur ; cela aurait pour effet que les signaux SIGCONT n'auraient aucun effet sur le tracee.

Depuis Linux 3.4, il existe une méthode pour surmonter ce problème : au lieu de PTRACE_CONT, une commande PTRACE_LISTEN peut être utilisée pour redémarrer un tracee d'une manière où il ne s'exécute pas, mais attend un nouvel événement qu'il peut rapporter via waitpid(2) (par exemple, lorsqu'il est redémarré par un SIGCONT).

Arrêts d'appel système

Si le tracee a été redémarré par PTRACE_SYSCALL ou PTRACE_SYSEMU, le tracee entre dans un arrêt avant l'appel système juste avant d'entrer dans n'importe quel appel système (qui ne sera pas exécuté si le redémarrage a été effectué avec PTRACE_SYSEMU, indépendamment de toute modification apportée aux registres à ce stade ou de la manière dont le tracee est redémarré après cet arrêt). Quelle que soit la méthode ayant provoqué l'arrêt avant l'appel système, si le traceur redémarre le tracee avec PTRACE_SYSCALL, le tracee entre dans un arrêt après l'appel système lorsque l'appel système est terminé, ou s'il est interrompu par un signal. (C'est-à-dire qu'un arrêt de livraison de signal ne se produit jamais entre un arrêt avant l'appel système et un arrêt après l'appel système ; il se produit *après* l'arrêt après l'appel système.). Si le tracee est continué en utilisant une autre méthode (y compris PTRACE_SYSEMU), aucun arrêt après l'appel système ne se produit. Notez que toutes les mentions de PTRACE_SYSEMU s'appliquent également à PTRACE_SYSEMU_SINGLESTEP.

Cependant, même si le tracee a été continué en utilisant PTRACE_SYSCALL, il n'est pas garanti que le prochain arrêt sera un arrêt après appel système. D'autres possibilités sont que le tracee peut s'arrêter dans un arrêt PTRACE_EVENT (y compris les arrêts seccomp), sortir (s'il est entré dans _exit(2) ou exit_group(2)), être tué par SIGKILL, ou mourir silencieusement (s'il s'agit du leader du groupe de threads, que execve(2) a eu lieu dans un autre thread, et que ce thread n'est pas tracé par le même traceur ; cette situation est discutée plus loin).

Les arrêts d'appel système (avant et après) sont observés par le traceur comme waitpid(2) retournant avec WIFSTOPPED(status) vrai, et WSTOPSIG(status) donnant SIGTRAP. Si l'option PTRACE_O_TRACESYSGOOD a été définie par le traceur, alors WSTOPSIG(status) donnera la valeur (SIGTRAP | 0x80).

Les arrêts d'appel système peuvent être distingués des arrêts de livraison de signal avec SIGTRAP en interrogeant PTRACE_GETSIGINFO pour les cas suivants :

si_code <= 0

si_code == SI_KERNEL (0x80)
SIGTRAP
/b> a été envoyé par le noyau.
si_code == SIGTRAP ou si_code == (SIGTRAP|0x80)
Il s'agit d'un arrêt d'appel système.

Cependant, les arrêts d'appels système se produisent très souvent (deux fois par appel système), et l'exécution de PTRACE_GETSIGINFO pour chaque arrêt d'appel système peut être assez coûteuse.

Certaines architectures permettent de distinguer les cas en examinant les registres. Par exemple, sur x86, rax == -ENOSYS dans un arrêt d'entrée d'appel système. Étant donné que SIGTRAP (comme tout autre signal) se produit toujours *après* l'arrêt de sortie d'appel système, et qu'à ce stade rax ne contient presque jamais -ENOSYS, le SIGTRAP ressemble à un "arrêt d'appel système qui n'est pas un arrêt d'entrée d'appel système"; en d'autres termes, il ressemble à un "arrêt de sortie d'appel système errant" et peut être détecté de cette manière. Mais une telle détection est fragile et doit être évitée.

L'utilisation de l'option PTRACE_O_TRACESYSGOOD est la méthode recommandée pour distinguer les arrêts d'appels système des autres types d'arrêts ptrace, car elle est fiable et n'entraîne pas de pénalité de performance.

Les arrêts d'entrée d'appel système et les arrêts de sortie d'appel système sont indiscernables pour le traceur. Le traceur doit suivre la séquence des arrêts ptrace afin de ne pas interpréter à tort un arrêt d'entrée d'appel système comme un arrêt de sortie d'appel système ou vice versa. En général, un arrêt d'entrée d'appel système est toujours suivi d'un arrêt de sortie d'appel système, d'un arrêt PTRACE_EVENT, ou de la mort du tracé ; aucun autre type d'arrêt ptrace ne peut survenir entre-temps. Cependant, notez que les arrêts seccomp (voir ci-dessous) peuvent provoquer des arrêts de sortie d'appel système, sans arrêts d'entrée d'appel système précédents. Si seccomp est utilisé, il faut veiller à ne pas interpréter à tort de tels arrêts comme des arrêts d'entrée d'appel système.

Si, après un arrêt d'entrée d'appel système, le traceur utilise une commande de redémarrage autre que PTRACE_SYSCALL, un arrêt de sortie d'appel système n'est pas généré.

PTRACE_GETSIGINFO sur les arrêts d'appels système renvoie SIGTRAP dans si_signo, avec si_code défini sur SIGTRAP ou (SIGTRAP|0x80).

Arrêts PTRACE_EVENT_SECCOMP (Linux 3.5 à Linux 4.7)

Le comportement des arrêts PTRACE_EVENT_SECCOMP et leur interaction avec d'autres types d'arrêts ptrace a changé entre les versions du noyau. Ce document décrit le comportement depuis leur introduction jusqu'à Linux 4.7 (inclus). Le comportement dans les versions ultérieures du noyau est décrit dans la section suivante.

Un arrêt PTRACE_EVENT_SECCOMP se produit chaque fois qu'une règle SECCOMP_RET_TRACE est déclenchée. Ceci est indépendant de la méthode utilisée pour redémarrer l'appel système. Notamment, seccomp s'exécute toujours même si le tracé a été redémarré à l'aide de PTRACE_SYSEMU et que cet appel système est inconditionnellement ignoré.

Les redémarrages à partir de cet arrêt se comporteront comme si l'arrêt s'était produit juste avant l'appel système en question. En particulier, PTRACE_SYSCALL et PTRACE_SYSEMU provoqueront normalement un arrêt d'entrée d'appel système ultérieur. Cependant, si après le PTRACE_EVENT_SECCOMP le numéro d'appel système est négatif, l'arrêt d'entrée d'appel système et l'appel système lui-même seront ignorés. Cela signifie que si le numéro d'appel système est négatif après un PTRACE_EVENT_SECCOMP et que le tracé est redémarré à l'aide de PTRACE_SYSCALL, le prochain arrêt observé sera un arrêt de sortie d'appel système, plutôt que l'arrêt d'entrée d'appel système qui aurait pu être attendu.

Arrêts PTRACE_EVENT_SECCOMP (depuis Linux 4.8)

À partir de Linux 4.8, l'arrêt PTRACE_EVENT_SECCOMP a été réorganisé pour se produire entre l'arrêt d'entrée d'appel système et l'arrêt de sortie d'appel système. Notez que seccomp ne s'exécute plus (et aucun PTRACE_EVENT_SECCOMP ne sera signalé) si l'appel système est ignoré en raison de PTRACE_SYSEMU.

Fonctionnellement, un arrêt PTRACE_EVENT_SECCOMP se comporte de manière comparable à un arrêt d'entrée d'appel système (c'est-à-dire que les continuations utilisant PTRACE_SYSCALL provoqueront des arrêts de sortie d'appel système, le numéro d'appel système peut être modifié et tout autre registre modifié est visible pour l'appel système à exécuter).

Après un arrêt PTRACE_EVENT_SECCOMP, seccomp sera réexécuté, une règle SECCOMP_RET_TRACE fonctionnant désormais de la même manière qu'une SECCOMP_RET_ALLOW. Plus précisément, cela signifie que si les registres ne sont pas modifiés pendant l'arrêt PTRACE_EVENT_SECCOMP, l'appel système sera alors autorisé.

Commandes ptrace informationnelles et de redémarrage

La plupart des commandes ptrace (toutes sauf PTRACE_ATTACH, PTRACE_SEIZE, PTRACE_TRACEME, PTRACE_INTERRUPT et PTRACE_KILL) nécessitent que le tracé soit dans un état d'arrêt ptrace, sinon elles échouent avec ESRCH.

Lorsque le tracé est dans un état d'arrêt ptrace, le traceur peut lire et écrire des données dans le tracé à l'aide de commandes informationnelles. Ces commandes laissent le tracé dans un état d'arrêt ptrace :


ptrace(PTRACE_PEEKTEXT/PEEKDATA/PEEKUSER, pid, addr, 0);
ptrace(PTRACE_POKETEXT/POKEDATA/POKEUSER, pid, addr, long_val);
ptrace(PTRACE_GETREGS/GETFPREGS, pid, 0, &struct);
ptrace(PTRACE_SETREGS/SETFPREGS, pid, 0, &struct);
ptrace(PTRACE_GETREGSET, pid, NT_foo, &iov);
ptrace(PTRACE_SETREGSET, pid, NT_foo, &iov);
ptrace(PTRACE_GETSIGINFO, pid, 0, &siginfo);
ptrace(PTRACE_SETSIGINFO, pid, 0, &siginfo);
ptrace(PTRACE_GETEVENTMSG, pid, 0, &long_var);
ptrace(PTRACE_SETOPTIONS, pid, 0, PTRACE_O_flags);

Notez que certaines erreurs ne sont pas signalées. Par exemple, la définition des informations de signal (siginfo) peut ne pas avoir d'effet dans certains arrêts ptrace, pourtant l'appel peut réussir (renvoyer 0 et ne pas définir errno) ; interroger PTRACE_GETEVENTMSG peut réussir et renvoyer une valeur aléatoire si l'arrêt ptrace actuel n'est pas documenté comme renvoyant un message d'événement significatif.

L'appel


ptrace(PTRACE_SETOPTIONS, pid, 0, PTRACE_O_flags);

affecte un tracé. Les drapeaux actuels du tracé sont remplacés. Les drapeaux sont hérités par les nouveaux tracés créés et "automatiquement attachés" via les options PTRACE_O_TRACEFORK, PTRACE_O_TRACEVFORK ou PTRACE_O_TRACECLONE actives.

Un autre groupe de commandes fait exécuter le tracé arrêté par ptrace. Elles ont la forme :


ptrace(cmd, pid, 0, sig);

où cmd est PTRACE_CONT, PTRACE_LISTEN, PTRACE_DETACH, PTRACE_SYSCALL, PTRACE_SINGLESTEP, PTRACE_SYSEMU ou PTRACE_SYSEMU_SINGLESTEP. Si le tracé est dans un état d'arrêt de livraison de signal, sig est le signal à injecter (s'il n'est pas nul). Sinon, sig peut être ignoré. (Lors du redémarrage d'un tracé à partir d'un arrêt ptrace autre qu'un arrêt de livraison de signal, la pratique recommandée est de toujours passer 0 dans sig.)

Attachement et détachement

Un thread peut être attaché au traceur à l'aide de l'appel


ptrace(PTRACE_ATTACH, pid, 0, 0);

ou


ptrace(PTRACE_SEIZE, pid, 0, PTRACE_O_flags);

PTRACE_ATTACH envoie SIGSTOP à ce thread. Si le traceur souhaite que ce SIGSTOP n'ait aucun effet, il doit le supprimer. Notez que si d'autres signaux sont envoyés simultanément à ce thread lors de l'attachement, le traceur peut voir le tracé entrer d'abord dans un état d'arrêt de livraison de signal avec d'autres signal(s) ! La pratique courante consiste à réinjecter ces signaux jusqu'à ce que SIGSTOP soit vu, puis à supprimer l'injection de SIGSTOP. Le défaut de conception ici est qu'un attachement ptrace et un SIGSTOP livré simultanément peuvent entrer en concurrence et que le SIGSTOP concurrent peut être perdu.

Comme l'attachement envoie SIGSTOP et que le traceur le supprime généralement, cela peut entraîner un retour EINTR errant de l'appel système en cours d'exécution dans le tracé, comme décrit dans la section "Injection et suppression de signaux".

Depuis Linux 3.4, PTRACE_SEIZE peut être utilisé à la place de PTRACE_ATTACH. PTRACE_SEIZE n'arrête pas le processus attaché. Si vous avez besoin de l'arrêter après l'attachement (ou à tout autre moment) sans lui envoyer de signaux, utilisez la commande PTRACE_INTERRUPT.

L'opération


ptrace(PTRACE_TRACEME, 0, 0, 0);

transforme le thread appelant en un tracé. Le thread continue de s'exécuter (n'entre pas dans un état d'arrêt ptrace). Une pratique courante est de suivre PTRACE_TRACEME avec


raise(SIGSTOP);

et de permettre au parent (qui est maintenant notre traceur) d'observer notre arrêt de livraison de signal.

Si les options PTRACE_O_TRACEFORK, PTRACE_O_TRACEVFORK ou PTRACE_O_TRACECLONE sont actives, alors les enfants créés respectivement par vfork(2) ou clone(2) avec l'indicateur CLONE_VFORK, fork(2) ou clone(2) avec le signal de sortie défini sur SIGCHLD, et d'autres types de clone(2), sont automatiquement attachés au même traceur qui traçait leur parent. SIGSTOP est livré aux enfants, leur faisant entrer dans un état d'arrêt de livraison de signal après qu'ils aient quitté l'appel système qui les a créés.

Le détachement du tracé est effectué par :


ptrace(PTRACE_DETACH, pid, 0, sig);

PTRACE_DETACH est une opération de redémarrage ; par conséquent, elle nécessite que le tracé soit dans un état d'arrêt ptrace. Si le tracé est dans un état d'arrêt de livraison de signal, un signal peut être injecté. Sinon, le paramètre sig peut être silencieusement ignoré.

Si le tracé est en cours d'exécution lorsque le traceur souhaite le détacher, la solution habituelle consiste à envoyer SIGSTOP (à l'aide de tgkill(2), pour s'assurer qu'il va au thread correct), attendre que le tracé s'arrête dans un état d'arrêt de livraison de signal pour SIGSTOP, puis le détacher (en supprimant l'injection de SIGSTOP). Un défaut de conception est que cela peut entrer en concurrence avec des SIGSTOP simultanés. Une autre complication est que le tracé peut entrer dans d'autres arrêts ptrace et doit être redémarré et attendu à nouveau, jusqu'à ce que SIGSTOP soit vu. Une autre complication encore est de s'assurer que le tracé n'est pas déjà arrêté par ptrace, car aucun signal n'est livré pendant ce temps - même pas SIGSTOP.

Si le traceur meurt, tous les tracés sont automatiquement détachés.

d et redémarrés, sauf s'ils étaient en arrêt de groupe. La gestion du redémarrage à partir d'un arrêt de groupe est actuellement boguée, mais le comportement "prévu" est de laisser le traceur arrêté et en attente de SIGCONT. Si le traceur est redémarré à partir d'un arrêt de livraison de signal, le signal en attente est injecté.

execve(2) sous ptrace

Lorsqu'un thread dans un processus multithread appelle execve(2), le noyau détruit tous les autres threads du processus et réinitialise l'ID du thread qui a effectué l'appel à l'ID du groupe de threads (ID du processus). (Ou, pour le dire autrement, lorsqu'un processus multithread effectue un execve(2), à la fin de l'appel, il semble que l'execve(2) ait eu lieu dans le chef du groupe de threads, quel que soit le thread qui ait effectué l'execve(2).) Cette réinitialisation de l'ID du thread semble très déroutante pour les traceurs :

•
Tous les autres threads s'arrêtent en arrêt PTRACE_EVENT_EXIT, si l'option PTRACE_O_TRACEEXIT a été activée. Ensuite, tous les autres threads, à l'exception du chef de groupe de threads, signalent leur mort comme s'ils étaient sortis via _exit(2) avec le code de sortie 0.
•
Le traceur qui effectue l'appel à exec modifie son ID de thread pendant l'appel à execve(2). (Rappelez-vous, sous ptrace, le "pid" retourné par waitpid(2), ou passé aux appels ptrace, est l'ID du thread du traceur.) C'est-à-dire que l'ID du thread du traceur est réinitialisé pour être identique à son ID de processus, qui est identique à l'ID du thread du chef de groupe de threads.
•
Ensuite, un arrêt PTRACE_EVENT_EXEC se produit, si l'option PTRACE_O_TRACEEXEC a été activée.
•
Si le chef de groupe de threads a déjà signalé son arrêt PTRACE_EVENT_EXIT à ce moment-là, il semble au traceur que le chef de groupe de threads mort "réapparaît de nulle part". (Note : le chef de groupe de threads ne signale pas sa mort via WIFEXITED(status) tant qu'il n'y a pas au moins un autre thread vivant. Cela élimine la possibilité que le traceur le voie mourir puis réapparaître.) Si le chef de groupe de threads était toujours en vie, pour le traceur cela peut ressembler à un retour d'appel système différent de celui entré, ou même à un "retour d'appel système alors qu'il n'était dans aucun appel système". Si le chef de groupe de threads n'était pas tracé (ou était tracé par un traceur différent), alors pendant execve(2), il semblera qu'il soit devenu un traceur du traceur du traceur exécutant l'appel.

Tous les effets ci-dessus sont des artefacts du changement d'ID de thread dans le traceur.

L'option PTRACE_O_TRACEEXEC est l'outil recommandé pour gérer cette situation. Premièrement, elle active l'arrêt PTRACE_EVENT_EXEC, qui se produit avant le retour de execve(2). Dans cet arrêt, le traceur peut utiliser PTRACE_GETEVENTMSG pour récupérer l'ancien ID de thread du traceur. (Cette fonctionnalité a été introduite dans Linux 3.0.) Deuxièmement, l'option PTRACE_O_TRACEEXEC désactive la génération héritée de SIGTRAP lors de execve(2).

Lorsque le traceur reçoit la notification d'arrêt PTRACE_EVENT_EXEC, il est garanti que, à l'exception de ce traceur et du chef de groupe de threads, aucun autre thread du processus n'est en vie.

En recevant la notification d'arrêt PTRACE_EVENT_EXEC, le traceur doit nettoyer toutes ses structures de données internes décrivant les threads de ce processus, et ne conserver qu'une seule structure de données - celle qui décrit le seul traceur toujours en cours d'exécution, avec


ID du thread == ID du groupe de threads == ID du processus.

Exemple : deux threads appellent execve(2) en même temps :

*** nous recevons un arrêt d'entrée d'appel système dans le thread 1 : **
PID1 execve("/bin/foo", "foo" <non terminé ...>
*** nous émettons PTRACE_SYSCALL pour le thread 1 **
*** nous recevons un arrêt d'entrée d'appel système dans le thread 2 : **
PID2 execve("/bin/bar", "bar" <non terminé ...>
*** nous émettons PTRACE_SYSCALL pour le thread 2 **
*** nous recevons PTRACE_EVENT_EXEC pour PID0, nous émettons PTRACE_SYSCALL **
*** nous recevons un arrêt de sortie d'appel système pour PID0 : **
PID0 <... execve repris> )             = 0

Si l'option PTRACE_O_TRACEEXEC n'est pas activée pour le traceur exécutant l'appel, et si le traceur a été PTRACE_ATTACHé plutôt que PTRACE_SEIZEd, le noyau délivre un SIGTRAP supplémentaire au traceur après le retour de execve(2). Ceci est un signal ordinaire (similaire à celui qui peut être généré par kill -TRAP), pas un type spécial d'arrêt ptrace. L'utilisation de PTRACE_GETSIGINFO pour ce signal renvoie si_code défini à 0 (SI_USER). Ce signal peut être bloqué par le masque de signaux, et peut donc être délivré (bien) plus tard.

Généralement, le traceur (par exemple, strace(1)) ne voudrait pas montrer ce signal SIGTRAP post-execve supplémentaire à l'utilisateur, et supprimerait sa livraison au traceur (si SIGTRAP est défini sur SIG_DFL, c'est un signal mortel). Cependant, déterminer quel SIGTRAP supprimer n'est pas facile. Définir l'option PTRACE_O_TRACEEXEC ou utiliser PTRACE_SEIZE et ainsi supprimer ce SIGTRAP supplémentaire est l'approche recommandée.

Parent réel

L'API ptrace (abusé) utilise la signalisation standard parent/enfant UNIX via waitpid(2). Cela avait l'habitude d'entraîner le parent réel du processus à ne plus recevoir plusieurs types de notifications waitpid(2) lorsque le processus enfant était tracé par un autre processus.

Beaucoup de ces bogues ont été corrigés, mais à partir de Linux 2.6.38, plusieurs existent encore ; voir BUGS ci-dessous.

À partir de Linux 2.6.38, ce qui suit est considéré comme fonctionnant correctement :

•
La sortie/mort par signal est d'abord signalée au traceur, puis, lorsque le traceur consomme le résultat de waitpid(2), au parent réel (au parent réel uniquement lorsque l'ensemble du processus multithread se termine). VALEUR DE RETOUR

En cas de succès, les opérations PTRACE_PEEK* retournent les données demandées (mais voir NOTES), l'opération PTRACE_SECCOMP_GET_FILTER retourne le nombre d'instructions dans le programme BPF, l'opération PTRACE_GET_SYSCALL_INFO retourne le nombre d'octets disponibles à être écrits par le noyau, et les autres opérations retournent zéro.

Vérification du mode d'accès ptrace

Diverses parties de l'API noyau/espace utilisateur (pas seulement les opérations ptrace()), nécessitent des vérifications dites de "mode d'accès ptrace", dont le résultat détermine si une opération est permise (ou, dans quelques cas, renvoie des données nettoyées pour une opération de "lecture"). Ces vérifications sont effectuées dans

cases où un processus peut inspecter des informations sensibles concernant, ou dans certains cas modifier l'état d'un, autre processus. Les vérifications sont basées sur des facteurs tels que les informations d'identification et les capacités des deux processus, que le processus "cible" soit vidable ou non, et les résultats des vérifications effectuées par tout module de sécurité Linux (LSM) activé — par exemple, SELinux, Yama ou Smack — et par le LSM commoncap (qui est toujours appelé).

Avant Linux 2.6.27, toutes les vérifications d'accès étaient d'un seul type. Depuis Linux 2.6.27, deux niveaux de mode d'accès sont distingués :

PTRACE_MODE_READ
Pour les opérations de "lecture" ou d'autres opérations moins dangereuses, telles que : get_robust_list(2) ; kcmp(2) ; lecture de /proc/pid/auxv, /proc/pid/environ ou /proc/pid/stat ; ou readlink(2) d'un fichier /proc/pid/ns/*.
PTRACE_MODE_ATTACH
Pour les opérations d'"écriture", ou d'autres opérations plus dangereuses, telles que : l'attachement ptrace (PTRACE_ATTACH) à un autre processus ou l'appel à process_vm_writev(2). (PTRACE_MODE_ATTACH était effectivement le défaut avant Linux 2.6.27.)

Depuis Linux 4.5, les vérifications de mode d'accès ci-dessus sont combinées (OU logique) avec l'un des modificateurs suivants :

PTRACE_MODE_FSCREDS
Utilise l'UID et le GID du système de fichiers de l'appelant (voir credentials(7)) ou les capacités effectives pour les vérifications LSM.
PTRACE_MODE_REALCREDS
Utilise l'UID et le GID réels de l'appelant ou les capacités autorisées pour les vérifications LSM. C'était effectivement le défaut avant Linux 4.5.

Étant donné que combiner l'un des modificateurs d'informations d'identification avec l'un des modes d'accès susmentionnés est typique, certaines macros sont définies dans les sources du noyau pour les combinaisons :

PTRACE_MODE_READ_FSCREDS
Défini comme PTRACE_MODE_READ | PTRACE_MODE_FSCREDS.
PTRACE_MODE_READ_REALCREDS
Défini comme PTRACE_MODE_READ | PTRACE_MODE_REALCREDS.
PTRACE_MODE_ATTACH_FSCREDS
Défini comme PTRACE_MODE_ATTACH | PTRACE_MODE_FSCREDS.
PTRACE_MODE_ATTACH_REALCREDS
Défini comme PTRACE_MODE_ATTACH | PTRACE_MODE_REALCREDS.

Un modificateur supplémentaire peut être combiné (OU logique) avec le mode d'accès :

PTRACE_MODE_NOAUDIT (depuis Linux 3.3)
Ne pas auditer cette vérification de mode d'accès. Ce modificateur est utilisé pour les vérifications de mode d'accès ptrace (telles que les vérifications lors de la lecture de /proc/pid/stat) qui entraînent simplement le filtrage ou la sanitisation de la sortie, plutôt que le retour d'une erreur à l'appelant. Dans ces cas, l'accès au fichier n'est pas une violation de sécurité et il n'y a aucune raison de générer un enregistrement d'audit de sécurité. Ce modificateur supprime la génération d'un tel enregistrement d'audit pour la vérification d'accès particulière.

Notez que toutes les constantes PTRACE_MODE_* décrites dans cette sous-section sont internes au noyau et ne sont pas visibles dans l'espace utilisateur. Les noms des constantes sont mentionnés ici afin de labelliser les différents types de vérifications de mode d'accès ptrace qui sont effectuées pour divers appels système et accès à divers pseudo-fichiers (par exemple, sous /proc). Ces noms sont utilisés dans d'autres pages de manuel pour fournir un raccourci simple pour étiqueter les différentes vérifications du noyau.

L'algorithme employé pour la vérification du mode d'accès ptrace détermine si le processus appelant est autorisé à effectuer l'action correspondante sur le processus cible. (Dans le cas de l'ouverture des fichiers /proc/pid, le "processus appelant" est celui qui ouvre le fichier, et le processus avec le PID correspondant est le "processus cible".) L'algorithme est le suivant :

(1)
Si le thread appelant et le thread cible sont dans le même groupe de threads, l'accès est toujours autorisé.
(2)
Si le mode d'accès spécifie PTRACE_MODE_FSCREDS, alors, pour la vérification de l'étape suivante, utiliser l'UID et le GID du système de fichiers de l'appelant. (Comme noté dans credentials(7), l'UID et le GID du système de fichiers ont presque toujours les mêmes valeurs que les identifiants effectifs correspondants.)
Sinon, le mode d'accès spécifie PTRACE_MODE_REALCREDS, donc utiliser l'UID et le GID réels de l'appelant pour les vérifications de l'étape suivante. (La plupart des API qui vérifient l'UID et le GID de l'appelant utilisent les identifiants effectifs. Pour des raisons historiques, la vérification PTRACE_MODE_REALCREDS utilise les identifiants réels à la place.)
(3)
Refuser l'accès si aucune des conditions suivantes n'est remplie :
•
Les UID réels, effectifs et saved-set de l'utilisateur cible correspondent à l'UID de l'appelant, et les GID réels, effectifs et saved-set de l'utilisateur cible correspondent au GID de l'appelant.
•
L'appelant possède la capacité CAP_SYS_PTRACE dans l'espace utilisateur du processus cible.
(4)
Refuser l'accès si l'attribut "dumpable" du processus cible a une valeur autre que 1 (SUID_DUMP_USER ; voir la discussion sur PR_SET_DUMPABLE dans prctl(2)), et que l'appelant ne possède pas la capacité CAP_SYS_PTRACE dans l'espace utilisateur du processus cible processus.
(5)
L'interface security_ptrace_access_check() du LSM du noyau est appelée pour voir si l'accès ptrace est autorisé. Les résultats dépendent du/des LSM(s). L'implémentation de cette interface dans le LSM commoncap effectue les étapes suivantes :
(5.1)
Si le mode d'accès inclut PTRACE_MODE_FSCREDS, alors utiliser l'ensemble de capacités effectives de l'appelant dans la vérification suivante ; sinon (le mode d'accès spécifie PTRACE_MODE_REALCREDS, donc) utiliser l'ensemble de capacités autorisées de l'appelant.
(5.2)
Refuser l'accès si aucune des conditions suivantes n'est remplie :
•
L'appelant et le processus cible sont dans le même espace utilisateur, et les capacités de l'appelant sont un sur-ensemble des capacités autorisées du processus cible.
•
L'appelant possède la capacité CAP_SYS_PTRACE dans l'espace utilisateur du processus cible.
Notez que le LSM commoncap ne fait pas de distinction entre PTRACE_MODE_READ et PTRACE_MODE_ATTACH.
(6)

ptrace(2) — Arch Linux

NAME

ptrace - process trace

LIBRARY

libc, with support for the GNU C Library (glibc)

SYNOPSIS

#include <sys/user.h>
#include <sys/ptrace.h>

long ptrace(enum __ptrace_request request, pid_t pid, void *addr, void *data);

DESCRIPTION

The ptrace() system call provides a way for a parent process to observe and control the execution of another process (its child, or a grandchild, etc.). It may also be used to implement system call tracers and debuggers.

The ptrace() system call is used to interact with a tracee process. The precise behavior depends on the value of the request argument. The pid, addr, and data arguments are interpreted differently depending on the request.

In the following descriptions, the process performing the ptrace() call is called the tracer, and the process being observed or controlled is called the tracee.

The tracee must be a child of the tracer, or a child of a child, etc. (a descendant). The tracer must have the CAP_SYS_PTRACE capability, or the tracee must have the same real UID and effective UID as the tracer. See capabilities(7).

PTRACE_TRACEME

Used by a tracee to indicate that its parent wants to trace it. The tracee stops, and its parent can now use the other ptrace() requests to observe and control it. This is typically used shortly after a fork(2); the child calls PTRACE_TRACEME and then the parent continues execution. If PTRACE_TRACEME is successful, the tracee is stopped and its parent is notified via waitpid(2) with status indicating that the child stopped.

The pid, addr, and data arguments are ignored.

PTRACE_ATTACH

The tracer attempts to attach to the process specified by pid. The tracee process is stopped, and its parent (the tracer) is notified via waitpid(2). The tracee must be a descendant of the tracer. See also NOTES.

The addr and data arguments are ignored.

PTRACE_DETACH

Like PTRACE_ATTACH, but the tracer detaches from the tracee process specified by pid. The tracee is allowed to continue execution. If the tracee was stopped, it is restarted. The addr argument is interpreted as the address of a signal to be sent to the tracee if it was stopped due to a signal.

If addr is non-zero, a signal specified by data is sent to the tracee. If addr is zero, the tracee is restarted without a signal.

The data argument is ignored if addr is non-zero.

PTRACE_PEEKTEXT

Read a word (4 or 8 bytes) from the tracee's memory space at the location specified by addr, and return the value as the return value of ptrace(). The tracee is not stopped.

The data argument is ignored.

PTRACE_PEEKDATA

Synonym for PTRACE_PEEKTEXT.

PTRACE_PEEKUSER

Read a word from the tracee's user area at the offset specified by addr, and return the value as the return value of ptrace(). The user area is a memory region containing the tracee's registers and other per-process information. The offset addr must be a multiple of the size of a word.

The data argument is ignored.

PTRACE_POKETEXT

Write a word (specified by data) from the tracer's memory space to the tracee's memory space at the location specified by addr. The tracee is stopped.

The pid argument is ignored.

PTRACE_POKEDATA

Synonym for PTRACE_POKETEXT.

PTRACE_POKEUSER

Write a word (specified by data) from the tracer's memory space to the tracee's user area at the offset specified by addr. The offset addr must be a multiple of the size of a word. The tracee is stopped.

The pid argument is ignored.

PTRACE_CONT

Continue the tracee process specified by pid from the location where it stopped. If data is non-zero, it is interpreted as a signal number to be sent to the tracee. Otherwise, the tracee is continued without a signal.

The addr argument is the address from which to restart execution. If addr is 0, execution is restarted from the current instruction pointer.

PTRACE_SYSCALL

Like PTRACE_CONT, but the tracee is stopped again when it enters the next system call (either upon entry or returning from it).

PTRACE_SINGLESTEP

Like PTRACE_CONT, but the tracee is stopped again after executing a single machine instruction.

PTRACE_GETREGS

Like PTRACE_PEEKUSER, but reads all the tracee's CPU registers into the buffer pointed to by data. The addr argument is ignored.

The buffer must be large enough to hold a struct user_regs_struct. See user_regs(7).

PTRACE_SETREGS

Like PTRACE_POKEUSER, but writes all the tracee's CPU registers from the buffer pointed to by data. The addr argument is ignored.

PTRACE_GETFPREGS

Like PTRACE_GETREGS, but reads the tracee's floating-point registers.

The buffer must be large enough to hold a struct user_fpregs_struct.

PTRACE_SETFPREGS

Like PTRACE_SETREGS, but writes the tracee's floating-point registers.

PTRACE_GETFPXREGS

Like PTRACE_GETREGS, but reads the tracee's extended floating-point registers (if supported).

The buffer must be large enough to hold a struct user_fpxregs_struct.

PTRACE_SETFPXREGS

Like PTRACE_SETREGS, but writes the tracee's extended floating-point registers.

PTRACE_GETSIGINFO

Like PTRACE_PEEKUSER, but reads the signal information (struct siginfo) associated with the stop of the tracee into the buffer pointed to by data. The addr argument is ignored.

PTRACE_SETSIGINFO

Like PTRACE_POKEUSER, but writes the signal information from the buffer pointed to by data to the tracee. The addr argument is ignored.

PTRACE_GETEVENTMSG

Like PTRACE_PEEKUSER, but reads a message associated with a trace event into the value pointed to by data. The addr argument is ignored.

This request is used in conjunction with PTRACE_SETOPTIONS and trace events.

PTRACE_SETOPTIONS

Set options for the tracee. The data argument is a bitmask of options. The addr argument is ignored.

The available options are:

PTRACE_O_TRACESYSGOOD

If this option is set, then system call traps (from PTRACE_SYSCALL) do not generate SIGTRAP. Instead, signals that would normally be delivered are delivered, and the system call trap is ignored. This makes it easier to trace system calls for non-ptrace'd children that are ptrace'd. This is useful for syscall auditing. For systems where the syscall trap is delivered via SIGTRAP, this option causes the tracee to stop with SIGTRAP *after* the syscall has completed, but only if the syscall trap was not otherwise enabled.

PTRACE_O_TRACEFORK

If this option is set, then the tracee will generate a SIGTRAP signal when it calls fork(2), vfork(2), or clone(2). The tracer will receive a PTRACE_EVENT_FORK stop. When the tracee stops, the new child process is also stopped.

The tracer can then use PTRACE_ATTACH to trace the new child. The pid argument to ptrace() will be the PID of the new child.

PTRACE_O_TRACEVFORK

If this option is set, then the tracee will generate a SIGTRAP signal when it calls vfork(2) or clone(2) with the CLONE_VFORK flag. The tracer will receive a PTRACE_EVENT_VFORK stop.

The tracer can then use PTRACE_ATTACH to trace the new child. The pid argument to ptrace() will be the PID of the new child.

Unlike PTRACE_O_TRACEFORK, the tracee will not stop until the child process has called execve(2) or exit(2).

PTRACE_O_TRACECLONE

If this option is set, then the tracee will generate a SIGTRAP signal when it calls clone(2). The tracer will receive a PTRACE_EVENT_CLONE stop.

The tracer can then use PTRACE_ATTACH to trace the new child. The pid argument to ptrace() will be the PID of the new child.

PTRACE_O_TRACEEXEC

If this option is set, then the tracee will generate a SIGTRAP signal when it calls execve(2). The tracer will receive a PTRACE_EVENT_EXEC stop.

This allows the tracer to observe the execve(2) call.

PTRACE_O_TRACEVFORKDONE

If this option is set, then the tracee will generate a SIGTRAP signal when a child process created by vfork(2) or clone(2) with the CLONE_VFORK flag calls execve(2) or exit(2). The tracer will receive a PTRACE_EVENT_VFORKDONE stop.

PTRACE_O_TRACEEXIT

If this option is set, then the tracee will generate a SIGTRAP signal when it calls exit(2) or exits for any reason. The tracer will receive a PTRACE_EVENT_EXIT stop.

This stop occurs before the exit handler is run.

PTRACE_SETUSERCREDS

Set the user credentials of the tracee to the same as the tracer. This is used to allow a debugger to trace processes that have changed their user ID (e.g., setuid executables). This request can only be used by the root user.

The pid, addr, and data arguments are ignored.

PTRACE_SECCOMP_FILTER

Attach a seccomp filter to the tracee. The filter is specified by the data argument, which is a pointer to a null-terminated list of seccomp(2) filter instructions. The addr argument is the length of the filter.

This request is intended to be used by debuggers to implement system call filtering.

Trace events

When a tracee stops due to a PTRACE_O_TRACE* option, the tracer can obtain the event code by calling ptrace(PTRACE_PEEKUSER, ...), reading from the orig_eax field in the struct user_regs_struct. The tracer can then restart the tracee using PTRACE_SYSCALL, and the tracee will stop again when the event is completed.

The event codes are:

PTRACE_EVENT_FORK
PTRACE_EVENT_VFORK
PTRACE_EVENT_CLONE
PTRACE_EVENT_EXEC
PTRACE_EVENT_VFORKDONE
PTRACE_EVENT_EXIT

When a trace event occurs, the tracee is stopped. The tracer can then issue a PTRACE_GETEVENTMSG request to get a message associated with the event. For PTRACE_EVENT_FORK, PTRACE_EVENT_VFORK, PTRACE_EVENT_CLONE, the message is the PID of the newly created process.

Interaction with user namespaces

When a process is running within a user namespace, the tracer must have the CAP_SYS_PTRACE capability within that namespace to trace processes within that namespace. If the tracer is in a parent user namespace, it will not be able to trace processes in a child user namespace, even if it has the CAP_SYS_PTRACE capability in the parent namespace.

This restriction applies to operations within the child user namespace (and further-removed descendants of that namespace). Consequently, when a process tries to use user namespaces to sandbox itself, it inadvertently weakens the protections offered by the Yama LSM.

C library/kernel differences

At the system call level, the PTRACE_PEEKTEXT, PTRACE_PEEKDATA, and PTRACE_PEEKUSER operations have a different API: they store the result at the address specified by the data parameter, and the return value is the error flag. The glibc wrapper function provides the API given in DESCRIPTION above, with the result being returned via the function return value.

BUGS

On hosts with Linux 2.6 kernel headers, PTRACE_SETOPTIONS is declared with a different value than the one for Linux 2.4. This leads to applications compiled with Linux 2.6 kernel headers failing when run on Linux 2.4. This can be worked around by redefining PTRACE_SETOPTIONS to PTRACE_OLDSETOPTIONS, if that is defined.

Group-stop notifications are sent to the tracer, but not to real parent. Last confirmed on 2.6.38.6.

If a thread group leader is traced and exits by calling _exit(2), a PTRACE_EVENT_EXIT stop will happen for it (if requested), but the subsequent WIFEXITED notification will not be delivered until all other threads exit. As explained above, if one of other threads calls execve(2), the death of the thread group leader will never be reported. If the execed thread is not traced by this tracer, the tracer will never know that execve(2) happened. One possible workaround is to PTRACE_DETACH the thread group leader instead of restarting it in this case. Last confirmed on 2.6.38.6.

A SIGKILL signal may still cause a PTRACE_EVENT_EXIT stop before actual signal death. This may be changed in the future; SIGKILL is meant to always immediately kill tasks even under ptrace. Last confirmed on Linux 3.13.

Some system calls return with EINTR if a signal was sent to a tracee, but delivery was suppressed by the tracer. (This is very typical operation: it is usually done by debuggers on every attach, in order to not introduce a bogus SIGSTOP). As of Linux 3.2.9, the following system calls are affected (this list is likely incomplete): epoll_wait(2), and read(2) from an inotify(7) file descriptor. The usual symptom of this bug is that when you attach to a quiescent process with the command


strace -p <process-ID>

then, instead of the usual and expected one-line output such as


restart_syscall(<... resuming interrupted call ...>

or


select(6, [5], NULL, [5], NULL

('_' denotes the cursor position), you observe more than one line. For example:


    clock_gettime(CLOCK_MONOTONIC, {15370, 690928118}) = 0
    epoll_wait(4,_

What is not visible here is that the process was blocked in epoll_wait(2) before strace(1) has attached to it. Attaching caused epoll_wait(2) to return to user space with the error EINTR. In this particular case, the program reacted to EINTR by checking the current time, and then executing epoll_wait(2) again. (Programs which do not expect such "stray" EINTR errors may behave in an unintended way upon an strace(1) attach.)

Contrary to the normal rules, the glibc wrapper for ptrace() can set errno to zero.
