NOM

pt-archiver - Archive les lignes d'une table MySQL dans une autre table ou un fichier.

SYNTAXE

Usage : pt-archiver [OPTIONS] --source DSN --where CONDITION

pt-archiver supprime des enregistrements ligne par ligne d'une table MySQL. Les arguments --source et --dest utilisent la syntaxe DSN ; si COPY est oui, --dest prend par défaut la valeur de la clé de --source.

Exemples :

Archiver toutes les lignes de oltp_server vers olap_server et vers un fichier :

pt-archiver --source h=oltp_server,D=test,t=tbl --dest h=olap_server \
  --file '/var/log/archive/%Y-%m-%d-%D.%t'                           \
  --where "1=1" --limit 1000 --commit-each

Nettoyer (supprimer) les lignes orphelines de la table enfant :

pt-archiver --source h=host,D=db,t=child --purge \
  --where 'NOT EXISTS(SELECT * FROM parent WHERE col=child.col)'

RISQUES

Percona Toolkit est mature, éprouvé en production et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Consulter les " BUGS " connus de l'outil
  • Tester l'outil sur un serveur non-production
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

DESCRIPTION

pt-archiver est l'outil pour archiver des tables comme décrit dans https://web.archive.org/web/20071014031743/http://www.xaprb.com/blog/2006/05/02/how-to-write-efficient-archiving-and-purging-jobs-in-sql. L'objectif est un travail à faible impact, orienté vers l'avant, pour supprimer les vieilles données de la table sans impacter significativement les requêtes OLTP. Vous pouvez insérer les données dans une autre table, qui n'a pas besoin d'être sur le même serveur. Vous pouvez également les écrire dans un fichier dans un format adapté pour LOAD DATA INFILE. Ou vous ne faites ni l'un ni l'autre, auquel cas c'est juste une suppression incrémentale.

pt-archiver est extensible via un mécanisme de plugins. Vous pouvez injecter votre propre code pour ajouter une logique d'archivage avancée qui pourrait être utile pour archiver des données dépendantes, appliquer des règles métier complexes, ou construire un entrepôt de données pendant le processus d'archivage.

Vous devez choisir soigneusement les valeurs pour certaines options. Les plus importantes sont "--limit", "--retries", et "--txn-size".

La stratégie consiste à trouver la ou les premières lignes, puis à parcourir un index en lecture seule pour trouver d'autres lignes efficacement. Chaque requête subséquente ne doit pas parcourir toute la table ; elle doit rechercher dans l'index, puis parcourir jusqu'à ce qu'elle trouve d'autres lignes archivables. Spécifier l'index avec la partie 'i' de l'argument "--source" peut être crucial pour cela ; utilisez "--dry-run" pour examiner les requêtes générées et assurez-vous de les EXPLAIN pour voir si elles sont efficaces (la plupart du temps, vous voudrez probablement parcourir la clé PRIMAIRE, qui est la valeur par défaut). Mieux encore, examinez la différence dans les compteurs d'état Handler avant et après l'exécution de la requête, et assurez-vous qu'elle ne parcourt pas toute la table à chaque requête.

Vous pouvez désactiver partiellement ou totalement les optimisations de recherche puis de parcours avec "--no-ascend" et "--ascend-first". Parfois, cela peut être plus efficace pour les clés multi-colonnes. Soyez conscient que pt-archiver est conçu pour commencer au début de l'index qu'il choisit et le parcourir en lecture seule. Cela pourrait entraîner de longs parcours de table si vous essayez de supprimer de la fin de la table par un index autre que celui préféré. Voir "--source" et lire la documentation sur la partie "i" si cela s'applique à vous.

Percona XtraDB Cluster

pt-archiver fonctionne avec Percona XtraDB Cluster (PXC) 5.5.28-23.7 et plus récent, mais trois limitations sont à considérer avant d'archiver sur un cluster :

Erreur lors du commit
pt-archiver ne vérifie pas les erreurs lors de la validation des transactions. Les validations sur PXC peuvent échouer, mais l'outil ne vérifie pas encore et ne retente pas la transaction lorsque cela se produit. Si cela arrive, l'outil s'arrêtera.
Tables MyISAM
L'archivage des tables MyISAM fonctionne, mais le support MyISAM dans PXC est encore expérimental au moment de cette publication. Il existe plusieurs bugs connus avec PXC, les tables MyISAM et les colonnes "AUTO_INCREMENT". Par conséquent, vous devez vous assurer que l'archivage ne résultera pas directement ou indirectement dans l'utilisation des valeurs par défaut "AUTO_INCREMENT" pour une table MyISAM. Par exemple, cela se produit avec "--dest" si "--columns" est utilisé et que la colonne "AUTO_INCREMENT" n'est pas incluse. L'outil ne vérifie pas cela !
Options non-cluster
Certaines options peuvent fonctionner ou non. Par exemple, si un nœud de cluster n'est pas également une réplique, alors "--check-replica-lag" ne fonctionne pas. Et comme les tables PXC sont généralement InnoDB, mais que InnoDB ne supporte pas "INSERT DELAYED", alors "--delayed-insert" ne fonctionne pas. D'autres options peuvent également ne pas fonctionner, mais l'outil ne les vérifie pas. Par conséquent, vous devriez tester l'archivage sur un cluster de test avant d'archiver sur votre vrai cluster.

SORTIE

Si vous spécifiez "--progress", la sortie est une ligne d'en-tête, plus une sortie de statut à intervalles réguliers. Chaque ligne de la sortie de statut indique la date et l'heure actuelles, combien de secondes pt-archiver est en cours d'exécution, et combien de lignes il a archivées.

Si vous spécifiez "--statistics", "pt-archiver" affiche des informations de temporisation et autres pour vous aider à identifier quelle partie de votre processus d'archivage prend le plus de temps.

GESTION DES ERREURS

pt-archiver essaie de capturer les signaux et de sortir proprement ; par exemple, si vous lui envoyez SIGTERM (Ctrl-C sur les systèmes de type UNIX), il capturera le signal, affichera un message à propos du signal, et sortira relativement normalement. Il n'exécutera pas "--analyze" ou "--optimize", car ceux-ci peuvent prendre beaucoup de temps à terminer. Il exécutera tout autre code normalement, y compris l'appel de after_finish() sur tous les plugins (voir "EXTENSIBILITY").

Autrement dit, un signal, s'il est capturé, interrompra la boucle principale d'archivage et sautera l'optimisation/analyse.

OPTIONS

Spécifiez au moins une des options "--dest", "--file", ou "--purge".

"--ignore" et "--replace" s'excluent mutuellement.

"--txn-size" et "--commit-each" s'excluent mutuellement.

"--low-priority-insert" et "--delayed-insert" s'excluent mutuellement.

"--share-lock" et "--for-update" s'excluent mutuellement.

"--analyze" et "--optimize" s'excluent mutuellement.

"--no-ascend" et "--no-delete" s'excluent mutuellement.

Les valeurs DSN dans "--dest" prennent par défaut les valeurs de "--source" si COPY est oui.

--analyze
type : chaîne

Exécuter ANALYZE TABLE ensuite sur "--source" et/ou "--dest".

Exécute ANALYZE TABLE après l'achèvement. L'argument est une chaîne arbitraire. S'il contient la lettre 's', la source sera analysée. S'il contient 'd', la destination sera analysée. Vous pouvez spécifier l'un ou l'autre ou les deux. Par exemple, ce qui suit analysera les deux :

--analyze=ds

Voir http://dev.mysql.com/doc/en/analyze-table.html pour des détails sur ANALYZE TABLE.

--ascend-first
Parcourir uniquement la première colonne de l'index.

Si vous souhaitez utiliser l'optimisation de l'index ascendant (voir "--no-ascend"), mais que vous ne souhaitez pas supporter le coût supplémentaire de parcours d'un index multi-colonnes volumineux, vous pouvez utiliser cette option pour indiquer à pt-archiver de parcourir uniquement la colonne la plus à gauche de l'index. Cela peut fournir une significati

ant performance boost par rapport à la non-ascension de l'index, tout en évitant le coût de l'ascension de l'index complet.

Voir "EXTENDING" pour une discussion sur la manière dont cela interagit avec les plugins.

--ask-pass
Demander un mot de passe lors de la connexion à MySQL.
--buffer
Mettre en mémoire tampon la sortie vers "--file" et la vider lors du commit.

Désactive la vidange automatique vers "--file" et vide "--file" sur disque uniquement lorsqu'une transaction est validée. Cela signifie généralement que le fichier est vidé par blocs par le système d'exploitation, de sorte qu'il peut y avoir des vidanges implicites sur disque entre les commits. Par défaut, "--file" est vidé sur disque après chaque ligne.

Le danger est qu'un crash puisse entraîner une perte de données.

L'augmentation des performances que j'ai constatée en utilisant "--buffer" est d'environ 5 à 15 %. Vos résultats peuvent varier.

--bulk-delete
Supprimer chaque lot avec une seule instruction (implique "--commit-each").

Supprimer chaque lot de lignes en masse avec une seule instruction "DELETE". L'instruction supprime chaque ligne entre la première et la dernière ligne du lot, inclus. Elle implique "--commit-each", car il serait déconseillé d'"INSERT" des lignes une par une et de les valider avant la suppression en masse "DELETE".

La méthode normale consiste à supprimer chaque ligne par sa clé primaire. Les suppressions en masse peuvent être beaucoup plus rapides. Elles ne le sont pas forcément si vous avez une clause "WHERE" complexe.

Cette option reporte complètement tout le traitement "DELETE" jusqu'à ce que le lot de lignes soit terminé. Si vous avez un plugin sur la source, sa méthode "before_delete" ne sera pas appelée. À la place, sa méthode "before_bulk_delete" sera appelée plus tard.

AVERTISSEMENT : si vous avez un plugin sur la source qui ne renvoie parfois pas true depuis is_archivable(), vous ne devriez utiliser cette option que si vous comprenez ce qu'elle fait. Si le plugin demande à "pt-archiver" de ne pas archiver une ligne, elle sera quand même supprimée par la suppression en masse !

--[no]bulk-delete-limit
par défaut : yes

Ajoute "--limit" à l'instruction "--bulk-delete".

Ceci est une option avancée et vous ne devriez pas la désactiver sauf si vous savez ce que vous faites et pourquoi ! Par défaut, "--bulk-delete" ajoute une clause "--limit" à l'instruction SQL de suppression en masse. Dans certains cas, cette clause peut être omise en spécifiant "--no-bulk-delete-limit". "--limit" doit toujours être spécifié.

--bulk-insert
Insère chaque lot avec LOAD DATA INFILE (implique "--bulk-delete" et "--commit-each").

Insère chaque lot de lignes avec "LOAD DATA LOCAL INFILE". Cela peut être beaucoup plus rapide que d'insérer une ligne à la fois avec des instructions "INSERT". C'est implémenté en créant un fichier temporaire pour chaque lot de lignes, et en écrivant les lignes dans ce fichier au lieu de les insérer. Lorsque le lot est terminé, il télécharge les lignes.

Pour protéger la sécurité de vos données, cette option force l'utilisation de suppressions en masse. Il serait dangereux de supprimer chaque ligne au fur et à mesure qu'elle est trouvée, avant d'insérer les lignes dans la destination en premier. Forcer les suppressions en masse garantit que la suppression attend le succès de l'insertion.

Les options "--low-priority-insert", "--replace", et "--ignore" fonctionnent avec cette option, mais "--delayed-insert" ne fonctionne pas.

Si "LOAD DATA LOCAL INFILE" génère une erreur du type "The used command is not allowed with this MySQL version", référez-vous à la documentation de l'option DSN "L".

--channel
type: string

Nom du canal utilisé lors de la connexion à un serveur utilisant des canaux de réplication. Supposons que vous ayez deux sources, source_a au port 12345, source_b au port 1236 et une réplique connectée aux deux sources à l'aide des canaux chan_source_a et chan_source_b. Si vous souhaitez exécuter pt-archiver pour synchroniser la réplique par rapport à source_a, pt-archiver ne sera pas en mesure de déterminer quelle est la bonne source car SHOW REPLICA STATUS renverra 2 lignes. Dans ce cas, vous pouvez utiliser --channel=chan_source_a pour spécifier le nom du canal à utiliser dans la commande SHOW REPLICA STATUS.

--charset
forme courte : -A ; type : string

Jeu de caractères par défaut. Si la valeur est utf8, définit le mode binaire de Perl sur STDOUT en utf8, transmet l'option mysql_enable_utf8 à DBD::mysql et exécute SET NAMES UTF8 après la connexion à MySQL. Toute autre valeur définit le mode binaire sur STDOUT sans la couche utf8, et exécute SET NAMES après la connexion à MySQL.

Notez que seuls les jeux de caractères reconnus par MySQL sont acceptés ; ainsi, par exemple, "UTF8" fonctionnera, mais "UTF-8" ne fonctionnera pas.

Voir aussi "--[no]check-charset".

--[no]check-charset
par défaut : yes

Assure que les jeux de caractères de connexion et de table sont identiques. Désactiver cette vérification peut entraîner une conversion erronée de texte d'un jeu de caractères à un autre (généralement de utf8 vers latin1), ce qui peut causer une perte de données ou du mojibake. Désactiver cette vérification peut être utile ou nécessaire lorsque des conversions de jeux de caractères sont intentionnelles.

--[no]check-columns
par défaut : yes

Assure que "--source" et "--dest" ont les mêmes colonnes.

Activé par défaut ; demande à pt-archiver de vérifier que les tables source et destination ont les mêmes colonnes. Il ne vérifie pas l'ordre des colonnes, le type de données, etc. Il vérifie simplement que toutes les colonnes de la source existent dans la destination et inversement. S'il y a des différences, pt-archiver se terminera avec une erreur.

Pour désactiver cette vérification, spécifiez --no-check-columns.

--check-interval
type: temps ; par défaut : 1s

Si "--check-replica-lag" est donné, ceci définit la durée pendant laquelle l'outil fait une pause à chaque fois qu'il découvre qu'une réplique est en retard.
Cette vérification est effectuée toutes les 100 lignes.

--check-replica-lag
type: string ; répétable : yes

Suspend l'archivage jusqu'à ce que le retard de la réplique du DSN spécifié soit inférieur à "--max-lag". Cette option peut être spécifiée plusieurs fois pour vérifier plus d'une réplique.

--check-slave-lag
type: string ; répétable : yes

Cette option est obsolète et sera supprimée dans les futures versions. Utilisez "--check-replica-lag" à la place.

--columns
forme courte : -c ; type : tableau

Liste des colonnes à archiver, séparées par des virgules.

Spécifie une liste de colonnes, séparées par des virgules, à récupérer, écrire dans le fichier et insérer dans la table de destination. Si spécifié, pt-archiver ignore les autres colonnes sauf si nécessaire pour les ajouter à l'instruction "SELECT" pour ascensionner un index ou supprimer des lignes. Il récupère et utilise ces colonnes supplémentaires en interne, mais ne les écrit pas dans le fichier ni dans la table de destination. Il les transmet aux plugins.

Voir aussi "--primary-key-only".

--commit-each
Valide chaque ensemble de lignes récupérées et archivées (désactive "--txn-size").

Valide les transactions et vide "--file" après que chaque ensemble de lignes a été archivé, avant de récupérer le prochain ensemble de lignes, et avant de dormir si "--sleep" est spécifié. Désactive "--txn-size" ; utilisez "--limit" pour contrôler la taille de la transaction avec "--commit-each".

Cette option est utile comme raccourci pour faire en sorte que "--limit" et "--txn-size" aient la même valeur, mais surtout, elle évite que les transactions restent ouvertes pendant la recherche d'autres lignes. Par exemple, imaginez que vous archivez de vieilles lignes du début d'une très grande table, avec "--limit" 1000 et "--txn-size" 1000. Après avoir trouvé et archivé 1000 lignes à la fois pendant un certain temps, pt-archiver trouve les 999 dernières lignes et les archive, puis exécute le prochain SELECT pour trouver d'autres lignes. Cela scanne le reste de la table, mais ne trouve jamais d'autres lignes. Il a maintenu une transaction ouverte pendant très longtemps, juste pour déterminer qu'elle est terminée de toute façon. Vous pouvez utiliser "--commit-each" pour éviter cela.

--config
type: Tableau

Lit cette liste de fichiers de configuration, séparés par des virgules ; si spécifié, cela doit être la première option sur la ligne de commande.

--database
forme courte : -D ; type : string

Se connecter à cette base de données.

--delayed-insert
Ajoute le modificateur DELAYED aux instructions INSERT.

Ajoute le modificateur DELAYED aux instructions INSERT ou REPLACE. Voir http://dev.mysql.com/doc/en/insert.html pour plus de détails.

--dest
type: DSN

DSN spécifiant la table à archiver.

Cet élément spécifie une table dans laquelle pt-archiver insérera les lignes archivées depuis "--source". Il utilise le même format d'arguments clé=val que "--source". La plupart des valeurs manquantes par défaut sont les mêmes que pour "--source", vous n'avez donc pas besoin de répéter les options qui sont identiques dans "--source" et "--dest". Utilisez l'option "--help" pour voir quelles valeurs sont copiées depuis "--source".

AVERTISSEMENT : L'utilisation d'une option DSN de fichier d'options par défaut (F) qui définit un socket pour "--source" oblige pt-archiver à se connecter à "--dest" en utili

ng that socket unless another socket for "--dest" is specified. This means that pt-archiver may incorrectly connect to "--source" when it connects to "--dest". For example:

--source F=host1.cnf,D=db,t=tbl --dest h=host2

When pt-archiver connects to "--dest", host2, it will connect via the "--source", host1, socket defined in host1.cnf.

--dry-run
Affiche les requêtes et quitte sans rien faire.

Fait en sorte que pt-archiver quitte après avoir affiché le nom du fichier et les instructions SQL qu'il utilisera.

--file
type : string

Fichier dans lequel archiver, avec un formatage similaire à DATE_FORMAT().

Nom du fichier dans lequel écrire les lignes archivées. Un sous-ensemble des codes de formatage DATE_FORMAT() de MySQL est autorisé dans le nom de fichier, comme suit :

%d    Jour du mois, numérique (01..31)
%H    Heure (00..23)
%i    Minutes, numérique (00..59)
%m    Mois, numérique (01..12)
%s    Secondes (00..59)
%Y    Année, numérique, quatre chiffres

Vous pouvez également utiliser les codes de format supplémentaires suivants :

%D    Nom de la base de données
%t    Nom de la table

Exemple :

--file '/var/log/archive/%Y-%m-%d-%D.%t'

Le contenu du fichier est dans le même format que celui utilisé par SELECT INTO OUTFILE, comme documenté dans le manuel MySQL : les lignes sont terminées par des sauts de ligne, les colonnes sont séparées par des tabulations, les caractères NULL sont représentés par "\N", et les caractères spéciaux sont échappés par "\". Cela vous permet de recharger un fichier avec les paramètres par défaut de LOAD DATA INFILE.

Si vous souhaitez un en-tête de colonne en haut du fichier, consultez "--header". Le fichier est automatiquement vidé par défaut ; consultez "--buffer".

--for-update
Ajoute le modificateur FOR UPDATE aux instructions SELECT.

Pour plus de détails, voir http://dev.mysql.com/doc/en/innodb-locking-reads.html.

--header
Affiche l'en-tête de colonne en haut du fichier "--file".

Écrit les noms de colonnes comme première ligne dans le fichier spécifié par "--file". Si le fichier existe, il n'écrit pas d'en-têtes ; cela permet de garder le fichier chargeable avec LOAD DATA INFILE au cas où vous y ajouteriez plus de sorties.

--help
Affiche l'aide et quitte.
--high-priority-select
Ajoute le modificateur HIGH_PRIORITY aux instructions SELECT.

Voir http://dev.mysql.com/doc/en/select.html pour les détails.

--host
forme courte : -h; type : string

Se connecter à l'hôte.

--ignore
Utilise IGNORE pour les instructions INSERT.

Fait en sorte que les INSERTs vers "--dest" soient des INSERT IGNORE.

--limit
type : int; par défaut : 1

Nombre de lignes à récupérer et archiver par instruction.

Limite le nombre de lignes retournées par les instructions SELECT qui récupèrent les lignes à archiver. La valeur par défaut est une ligne. Il peut être plus efficace d'augmenter la limite, mais soyez prudent si vous archivez de manière sporadique, en sautant de nombreuses lignes ; cela peut potentiellement causer plus de contention avec d'autres requêtes, en fonction du moteur de stockage, du niveau d'isolation de la transaction et des options telles que "--for-update".

--local
Ne pas écrire les requêtes OPTIMIZE ou ANALYZE dans le binlog.

Ajoute le modificateur NO_WRITE_TO_BINLOG aux requêtes ANALYZE et OPTIMIZE. Voir "--analyze" pour les détails.

--low-priority-delete
Ajoute le modificateur LOW_PRIORITY aux instructions DELETE.

Voir http://dev.mysql.com/doc/en/delete.html pour les détails.

--low-priority-insert
Ajoute le modificateur LOW_PRIORITY aux instructions INSERT ou REPLACE.

Voir http://dev.mysql.com/doc/en/insert.html pour les détails.

--max-flow-ctl
type : float

Un peu similaire à --max-lag mais pour les clusters PXC. Vérifie le temps moyen passé par le cluster en pause à cause du contrôle de flux et fait pauser l'outil s'il dépasse le pourcentage indiqué dans l'option. La valeur par défaut est aucune vérification de contrôle de flux. Cette option est disponible pour les versions PXC 5.6 ou supérieures.

--max-lag
type : temps; par défaut : 1s

Pause l'archivage si la réplique indiquée par "--check-replica-lag" est en retard.

Cette option fait en sorte que pt-archiver examine la réplique à chaque fois qu'il est sur le point de récupérer une autre ligne. Si le retard de la réplique est supérieur à la valeur de l'option, ou si la réplique ne fonctionne pas (donc son retard est NULL), pt-archiver dort pendant "--check-interval" secondes puis examine à nouveau le retard. Il répète jusqu'à ce que la réplique soit à jour, puis procède à la récupération et à l'archivage de la ligne.

Cette option peut éliminer le besoin de "--sleep" ou "--sleep-coef".

--no-ascend
Ne pas utiliser l'optimisation d'index ascendant.

L'optimisation d'index ascendant par défaut permet à "pt-archiver" d'optimiser les requêtes "SELECT" répétées de manière à ce qu'elles se placent dans l'index où la requête précédente s'est arrêtée, puis qu'elles le parcourent, plutôt que de parcourir la table entière à chaque fois. Ceci est activé par défaut car c'est généralement une bonne stratégie pour les accès répétés.

Les index volumineux et multi-colonnes peuvent entraîner une clause WHERE suffisamment complexe pour que cela soit en fait moins efficace. Considérez, par exemple, une clé PRIMAIRE à quatre colonnes sur (a, b, c, d). La clause WHERE pour commencer là où la dernière requête s'est arrêtée est la suivante :

WHERE (a > ?)
   OR (a = ? AND b > ?)
   OR (a = ? AND b = ? AND c > ?)
   OR (a = ? AND b = ? AND c = ? AND d >= ?)

Remplir les espaces réservés avec des valeurs utilise de la mémoire et du CPU, ajoute du trafic réseau et une surcharge d'analyse, et peut rendre la requête plus difficile à optimiser pour MySQL. Une clé à quatre colonnes n'est pas un gros problème, mais une clé à dix colonnes dans laquelle chaque colonne autorise "NULL" pourrait l'être.

L'ascension de l'index pourrait ne pas être nécessaire si vous savez que vous supprimez simplement des lignes du début de la table par blocs, sans laisser de trous, de sorte que commencer au début de la table est en fait la chose la plus efficace à faire.

Voir également "--ascend-first". Voir "EXTENDING" pour une discussion sur la manière dont cela interagit avec les plugins.

--no-delete
Ne pas supprimer les lignes archivées.

Fait en sorte que "pt-archiver" ne supprime pas les lignes après les avoir traitées. Cela interdit "--no-ascend", car leur activation simultanée créerait une boucle infinie.

S'il y a un plugin sur le DSN source, sa méthode "before_delete" est appelée de toute façon, même si "pt-archiver" n'exécute pas la suppression. Voir "EXTENDING" pour en savoir plus sur les plugins.

--optimize
type : string

Exécute OPTIMIZE TABLE ensuite sur "--source" et/ou "--dest".

Exécute OPTIMIZE TABLE après l'achèvement. Voir "--analyze" pour la syntaxe de l'option et http://dev.mysql.com/doc/en/optimize-table.html pour les détails sur OPTIMIZE TABLE.

--output-format
type : string

Utilisé avec "--file" pour spécifier le format de sortie.

Les formats valides sont :

- dump : Format de dump MySQL utilisant des tabulations comme séparateur de champ (par défaut)

- csv : Dump des lignes en utilisant ',' comme séparateur et éventuellement en entourant les champs avec '"'.
Ce format est équivalent à FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'.

--password
forme courte : -p; type : string

Mot de passe à utiliser lors de la connexion. Si le mot de passe contient des virgules, elles doivent être échappées avec une barre oblique inverse : "exam\,ple"

--pid
type : string

Crée le fichier PID donné. L'outil ne démarrera pas si le fichier PID existe déjà et que le PID qu'il contient est différent du PID actuel. Cependant, si le fichier PID existe et que le PID qu'il contient n'est plus en cours d'exécution, l'outil écrasera le fichier PID avec le PID actuel. Le fichier PID est supprimé automatiquement à la sortie de l'outil.

type : string

Spécifie le nom du module Perl d'un plugin généraliste. Il est actuellement utilisé uniquement pour les statistiques (voir "--statistics") et doit avoir une méthode new() et une méthode statistics().

Considérez attentivement ce que vous souhaitez qu'il se passe lorsque vous archivez entre un mélange de moteurs de stockage transactionnels et non transactionnels. --source
type : DSN

DSN spécifiant la table à archiver (requis). Cet argument est un DSN. Voir "OPTIONS DSN" pour la syntaxe. La plupart des options contrôlent la façon dont pt-archiver se connecte à MySQL, mais il existe des options DSN étendues dans la syntaxe de cet outil. Les options D, t et i sélectionnent une table à archiver :

--source h=mon_serveur,D=ma_base,t=ma_table

L'option a spécifie la base de données à définir comme par défaut de la connexion avec USE. Si l'option b est vraie, elle désactive la journalisation binaire avec SQL_LOG_BIN. L'option m spécifie des actions remplaçables, qu'un module Perl externe peut fournir. La seule partie requise est la table ; d'autres parties peuvent être lues à partir de divers endroits de l'environnement (comme les fichiers d'options).

La partie 'i' mérite une mention spéciale. Elle indique à pt-archiver quel index il doit parcourir pour archiver. Elle apparaît dans une indication FORCE INDEX ou USE INDEX dans les instructions SELECT utilisées pour récupérer les lignes archivables. Si vous ne spécifiez rien, pt-archiver découvrira automatiquement un bon index, préférant une "PRIMARY KEY" si elle existe. D'après mon expérience, cela fonctionne généralement bien, donc la plupart du temps, vous pouvez probablement omettre la partie 'i'.

L'index est utilisé pour optimiser les accès répétés à la table ; pt-archiver se souvient de la dernière ligne qu'il récupère de chaque instruction SELECT, et l'utilise pour construire une clause WHERE, utilisant les colonnes de l'index spécifié, qui devrait permettre à MySQL de démarrer le SELECT suivant là où le précédent s'est arrêté, plutôt que de potentiellement parcourir la table entière à chaque SELECT successif. Si vous utilisez des plugins externes, veuillez voir "EXTENSIONS" pour une discussion sur la façon dont ils interagissent avec les index ascendants.

Les options 'a' et 'b' vous permettent de contrôler le flux des instructions dans le journal binaire. Si vous spécifiez l'option 'b', la journalisation binaire sera désactivée sur la connexion spécifiée. Si vous spécifiez l'option 'a', la connexion utilisera "USE" la base de données spécifiée, ce que vous pouvez utiliser pour empêcher les répliques d'exécuter les événements du journal binaire avec les options "--replicate-ignore-db". Ces deux options peuvent être utilisées comme différentes méthodes pour atteindre le même objectif : archiver les données de la source de réplication, mais les laisser sur la réplique. Par exemple, vous pouvez exécuter un travail de purge sur la source de réplication et empêcher qu'il ne se produise sur la réplique en utilisant la méthode de votre choix.

AVERTISSEMENT : L'utilisation d'une option DSN de fichier d'options par défaut (F) qui définit un socket pour "--source" amène pt-archiver à se connecter à "--dest" en utilisant ce socket, sauf si un autre socket est spécifié pour "--dest". Cela signifie que pt-archiver peut se connecter incorrectement à "--source" lorsqu'il est censé se connecter à "--dest". Par exemple :

--source F=host1.cnf,D=db,t=tbl --dest h=host2

Lorsque pt-archiver se connecte à "--dest", host2, il se connectera via le socket de "--source", host1, défini dans host1.cnf.

--statistics
Collecte et affiche les statistiques de temps.

Indique à pt-archiver de collecter des statistiques de temps sur ce qu'il fait. Ces statistiques sont disponibles pour le plugin spécifié par "--plugin"

Sauf si vous spécifiez "--quiet", "pt-archiver" affiche les statistiques lorsqu'il se termine. Les statistiques ressemblent à ceci :

Started at 2008-07-18T07:18:53, ended at 2008-07-18T07:18:53
Source: D=db,t=table
SELECT 4
INSERT 4
DELETE 4
Action         Count       Time        Pct
commit            10     0.1079      88.27
select             5     0.0047       3.87
deleting           4     0.0028       2.29
inserting          4     0.0028       2.28
other              0     0.0040       3.29

Les deux (ou trois) premières lignes montrent les temps ainsi que les tables source et destination. Les trois lignes suivantes montrent combien de lignes ont été récupérées, insérées et supprimées.

Les lignes restantes montrent les comptages et les temps. Les colonnes sont l'action, le nombre total de fois où cette action a été chronométrée, le temps total qu'elle a pris et le pourcentage du temps d'exécution total du programme. Les lignes sont triées par ordre décroissant de temps total. La dernière ligne représente le reste du temps non explicitement attribué à quelque chose. Les actions varieront en fonction de la comm

options en ligne de commande.

Si "--why-quit" est donné, son comportement est légèrement modifié. Cette option fait qu'il affiche la raison de la sortie même lorsqu'il s'agit simplement de l'épuisement des lignes.

Cette option nécessite le module standard Time::HiRes, qui fait partie du noyau Perl dans les versions raisonnablement récentes de Perl.

--stop
Arrête les instances en cours d'exécution en créant le fichier sentinelle.

Force pt-archiver à créer le fichier sentinelle spécifié par "--sentinel" et à quitter. Cela devrait avoir pour effet d'arrêter toutes les instances en cours d'exécution qui surveillent le même fichier sentinelle. Voir aussi "--unstop".

--txn-size
type : entier ; par défaut : 1

Nombre de lignes par transaction.

Spécifie la taille, en nombre de lignes, de chaque transaction. Zéro désactive complètement les transactions. Après avoir traité ce nombre de lignes, pt-archiver valide à la fois la source ("--source") et la destination ("--dest") si elles sont spécifiées, et vide le fichier donné par "--file".

Ce paramètre est crucial pour les performances. Si vous archivez depuis un serveur actif, qui effectue par exemple un travail intensif d'OLTP, vous devez choisir un bon équilibre entre la taille de la transaction et les frais généraux de validation. Des transactions plus importantes créent la possibilité de plus de contention de verrous et de blocages, mais des transactions plus petites entraînent des frais généraux de validation plus fréquents, qui peuvent être importants. Pour donner une idée, sur un petit ensemble de tests manipulé lors de la rédaction de pt-archiver, une valeur de 500 a fait que l'archivage a pris environ 2 secondes pour 1000 lignes sur une instance MySQL autrement silencieuse sur une machine de bureau, en archivage sur disque et vers une autre table. Désactiver les transactions avec une valeur de zéro, ce qui active l'auto-validation, a réduit les performances à 38 secondes par millier de lignes.

Si vous n'archivez pas depuis ou vers un moteur de stockage transactionnel, vous voudrez peut-être désactiver les transactions afin que pt-archiver n'essaie pas de valider.

EXTENSION

pt-archiver est extensible en branchant des modules Perl externes pour gérer une partie de la logique et/ou des actions. Vous pouvez spécifier un module à la fois pour la source ("--source") et la destination ("--dest"), avec la partie 'm' de la spécification. Par exemple :

--source D=test,t=test1,m=My::Module1 --dest m=My::Module2,t=test2

Cela forcera pt-archiver à charger les packages My::Module1 et My::Module2, à créer des instances d'entre eux, puis à les appeler pendant le processus d'archivage.

Vous pouvez également spécifier un plugin avec "--plugin".

Le module doit fournir cette interface :

new(dbh => $dbh, db => $db_name, tbl => $tbl_name)
Le constructeur du plugin reçoit une référence au handle de base de données, au nom de la base de données et au nom de la table. Le plugin est créé juste après que pt-archiver a ouvert la connexion, et avant qu'il n'examine la table donnée dans les arguments. Cela donne au plugin une chance de créer et de remplir des tables temporaires, ou d'effectuer d'autres travaux de configuration.
before_begin(cols => \@cols, allcols => \@allcols)
Cette méthode est appelée juste avant que pt-archiver ne commence à itérer sur les lignes et à les archiver, mais après qu'il ait effectué tous les autres travaux de configuration (examen des structures de table, conception des requêtes SQL, etc.). C'est la seule fois où pt-archiver communique au plugin les noms des colonnes pour les lignes qu'il passera au plugin pendant l'archivage.

L'argument "cols" contient les noms des colonnes que l'utilisateur a demandé à archiver, soit par défaut, soit par l'option "--columns". L'argument "allcols" est la liste des noms de colonnes pour chaque ligne que pt-archiver va récupérer de la table source. Il peut récupérer plus de colonnes que celles demandées par l'utilisateur, car il a besoin de certaines colonnes pour son propre usage. Lorsque les fonctions de plugin ultérieures reçoivent une ligne, c'est la ligne complète contenant toutes les colonnes supplémentaires, le cas échéant, ajoutées à la fin.

is_archivable(row => \@row)
Cette méthode est appelée pour chaque ligne afin de déterminer si elle est archivable. Ceci s'applique uniquement à la source ("--source"). L'argument est la ligne elle-même, sous forme d'arrayref. Si la méthode renvoie vrai, la ligne sera archivée ; sinon, elle sera ignorée.

Ignorer une ligne ajoute des complications pour les non-

Indexes uniques. Normalement, pt-archiver utilise une clause WHERE conçue pour cibler la dernière ligne traitée comme point de départ de l'analyse pour l'instruction SELECT suivante. Si vous avez sauté la ligne en retournant false depuis is_archivable(), pt-archiver pourrait entrer dans une boucle infinie car la ligne existe toujours. Par conséquent, lorsque vous spécifiez un plugin pour l'argument "--source", pt-archiver modifiera légèrement sa clause WHERE. Au lieu de commencer par "supérieur ou égal à" la dernière ligne traitée, il commencera par "strictement supérieur à". Cela fonctionnera bien sur les index uniques tels que les clés primaires, mais cela peut sauter des lignes (laisser des trous) sur les index non uniques ou lors de l'ascension de la première colonne d'un index.

"pt-archiver" modifiera la clause de la même manière si vous spécifiez "--no-delete", car là encore, une boucle infinie est possible.

Si vous spécifiez l'option "--bulk-delete" et retournez false de cette méthode, "pt-archiver" peut ne pas faire ce que vous attendez. La ligne ne sera pas archivée, mais elle sera supprimée, car les suppressions en bloc opèrent sur des plages de lignes et ne savent pas quelles lignes le plugin a sélectionnées pour être conservées.

Si vous spécifiez l'option "--bulk-insert", la valeur de retour de cette méthode influencera si la ligne est écrite dans le fichier temporaire pour l'insertion en bloc, de sorte que les insertions en bloc fonctionneront comme prévu. Cependant, les insertions en bloc nécessitent des suppressions en bloc.

before_delete(row => \@row)
Cette méthode est appelée pour chaque ligne juste avant sa suppression. Cela s'applique uniquement à "--source". C'est un bon endroit pour gérer les dépendances, telles que la suppression d'éléments qui ont des clés étrangères vers la ligne que vous êtes sur le point de supprimer. Vous pourriez également l'utiliser pour archiver récursivement toutes les tables dépendantes.

Cette méthode de plugin est appelée même si "--no-delete" est donné, mais pas si "--bulk-delete" est donné.

before_bulk_delete(first_row => \@row, last_row => \@row)
Cette méthode est appelée juste avant qu'une suppression en bloc ne soit exécutée. Elle est similaire à la méthode "before_delete", sauf que ses arguments sont la première et la dernière ligne de la plage à supprimer. Elle est appelée même si "--no-delete" est donné.
before_insert(row => \@row)
Cette méthode est appelée pour chaque ligne juste avant son insertion. Cela s'applique uniquement à "--dest". Vous pourriez l'utiliser pour insérer la ligne dans plusieurs tables, peut-être avec une clause ON DUPLICATE KEY UPDATE pour construire des tables récapitulatives dans un entrepôt de données.

Cette méthode n'est pas appelée si "--bulk-insert" est donné.

before_bulk_insert(first_row => \@row, last_row => \@row, filename => bulk_insert_filename)
Cette méthode est appelée juste avant qu'une insertion en bloc ne soit exécutée. Elle est similaire à la méthode "before_insert", sauf que ses arguments sont la première et la dernière ligne de la plage à supprimer.
custom_sth(row => \@row, sql => $sql)
Cette méthode est appelée juste avant l'insertion de la ligne, mais après "before_insert()". Elle permet au plugin de spécifier une instruction "INSERT" différente si désiré. La valeur de retour (le cas échéant) doit être un descripteur de requête DBI. Le paramètre "sql" est le texte SQL utilisé pour préparer l'instruction "INSERT" par défaut. Cette méthode n'est pas appelée si vous spécifiez "--bulk-insert".

Si aucune valeur n'est retournée, le descripteur de requête "INSERT" par défaut est utilisé.

Cette méthode s'applique uniquement au plugin spécifié pour "--dest". Ainsi, si votre plugin ne fonctionne pas comme prévu, vérifiez que vous l'avez spécifié pour la destination et non pour la source.

custom_sth_bulk(first_row => \@row, last_row => \@row, sql => $sql, filename => $bulk_insert_filename)
Si vous avez spécifié "--bulk-insert", cette méthode est appelée juste avant l'insertion en bloc, mais après "before_bulk_insert()", et les arguments sont différents.

La valeur de retour de cette méthode, etc., est similaire à celle de la méthode "custom_sth()".

after_finish()
Cette méthode est appelée après que pt-archiver a terminé la boucle d'archivage, validé toutes les poignées de base de données, fermé le "--file" et affiché les statistiques finales, mais avant que pt-archiver n'exécute ANALYZE ou OPTIMIZE (voir "--analyze" et "--optimize").

Si vous spécifiez un plugin pour "--source" et "--dest", pt-archiver construit, appelle before_begin(), et appelle after_finish() sur les deux plugins dans l'ordre "--source", "--dest".

pt-archiver suppose qu'il contrôle les transactions et que le plugin NE validera ni n'annulera la poignée de base de données. La poignée de base de données passée au constructeur du plugin est la même poignée que pt-archiver utilise lui-même. N'oubliez pas que "--source" et "--dest" sont des poignées séparées.

Un module d'exemple pourrait ressembler à ceci :

package My::Module;
sub new {
   my ( $class, %args ) = @_;
   return bless(\%args, $class);
}
sub before_begin {
   my ( $self, %args ) = @_;
   # Sauvegarder les noms de colonnes pour plus tard
   $self->{cols} = $args{cols};
}
sub is_archivable {
   my ( $self, %args ) = @_;
   # Faire une logique avancée avec $args{row}
   return 1;
}
sub before_delete {} # Ne rien faire
sub before_insert {} # Ne rien faire
sub custom_sth    {} # Ne rien faire
sub after_finish  {} # Ne rien faire
1;

ENVIRONNEMENT

La variable d'environnement "PTDEBUG" active une sortie de débogage détaillée sur STDERR. Pour activer le débogage et capturer toute la sortie dans un fichier, exécutez l'outil comme suit :

PTDEBUG=1 pt-archiver ... > FICHIER 2>&1

Attention : la sortie de débogage est volumineuse et peut générer plusieurs mégaoctets de sortie.

ATTENTION

L'utilisation de <PTDEBUG> peut exposer des mots de passe. Lorsque le débogage est activé, tous les paramètres de la ligne de commande sont affichés dans la sortie.
