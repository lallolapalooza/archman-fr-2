NOM

pt-online-schema-change - ALTER des tables sans les verrouiller.

SYNTAXE

Utilisation : pt-online-schema-change [OPTIONS] DSN

pt-online-schema-change modifie la structure d'une table sans bloquer les lectures ou écritures. Spécifiez la base de données et la table dans le DSN. N'utilisez pas cet outil avant d'avoir lu sa documentation et vérifié attentivement vos sauvegardes.

Ajouter une colonne à sakila.actor :

pt-online-schema-change --alter "ADD COLUMN c1 INT" D=sakila,t=actor

Changer sakila.actor en InnoDB, effectuant effectivement OPTIMIZE TABLE de manière non bloquante car il s'agit déjà d'une table InnoDB :

pt-online-schema-change --alter "ENGINE=InnoDB" D=sakila,t=actor

RISQUES

Percona Toolkit est mature, éprouvé dans le monde réel et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Consulter les "BUGS" connus de l'outil
  • Tester l'outil sur un serveur non-production
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

DESCRIPTION

pt-online-schema-change émule la manière dont MySQL modifie les tables en interne, mais il fonctionne sur une copie de la table que vous souhaitez modifier. Cela signifie que la table d'origine n'est pas verrouillée, et les clients peuvent continuer à lire et modifier les données qu'elle contient.

pt-online-schema-change fonctionne en créant une copie vide de la table à modifier, en la modifiant comme souhaité, puis en copiant les lignes de la table d'origine dans la nouvelle table. Une fois la copie terminée, il déplace la table d'origine et la remplace par la nouvelle. Par défaut, il supprime également la table d'origine.

Le processus de copie des données est effectué par petits morceaux de données, qui sont variés pour tenter de les exécuter dans un délai spécifique (voir "--chunk-time"). Ce processus est très similaire à la manière dont fonctionnent d'autres outils, tels que pt-table-checksum. Toutes les modifications apportées aux données dans les tables d'origine pendant la copie seront reflétées dans la nouvelle table, car l'outil crée des déclencheurs sur la table d'origine pour mettre à jour les lignes correspondantes dans la nouvelle table. L'utilisation de déclencheurs signifie que l'outil ne fonctionnera pas si des déclencheurs sont déjà définis sur la table.

Lorsque l'outil a fini de copier les données dans la nouvelle table, il utilise une opération atomique "RENAME TABLE" pour renommer simultanément la table d'origine et la nouvelle table. Une fois cela terminé, l'outil supprime la table d'origine.

Les clés étrangères compliquent le fonctionnement de l'outil et introduisent des risques supplémentaires. La technique de renommage atomique de la table d'origine et de la nouvelle table ne fonctionne pas lorsque les clés étrangères font référence à la table. L'outil doit mettre à jour les clés étrangères pour qu'elles fassent référence à la nouvelle table une fois le changement de schéma terminé. L'outil prend en charge deux méthodes pour y parvenir. Vous pouvez en savoir plus à ce sujet dans la documentation de "--alter-foreign-keys-method".

Les clés étrangères entraînent également certains effets secondaires. La table finale aura les mêmes clés étrangères et index que la table d'origine (sauf si vous spécifiez différemment dans votre instruction ALTER), mais les noms des objets peuvent être légèrement modifiés pour éviter les collisions de noms d'objets dans MySQL et InnoDB.

Par sécurité, l'outil ne modifie pas la table à moins que vous ne spécifiiez l'option "--execute", qui n'est pas activée par défaut. L'outil prend en charge une variété d'autres mesures pour empêcher une charge indésirable ou d'autres problèmes, notamment la détection automatique des répliques, la connexion à celles-ci et l'utilisation des contrôles de sécurité suivants :

  • Dans la plupart des cas, l'outil refusera d'opérer à moins qu'une clé PRIMAIRE ou un INDEX UNIQUE ne soit présent dans la table. Voir "--alter" pour plus de détails.
  • L'outil refuse d'opérer s'il détecte des filtres de réplication. Voir "--[no]check-replication-filters" pour plus de détails.
  • L'outil suspend l'opération de copie des données s'il observe des répliques en retard de réplication. Voir "--max-lag" pour plus de détails.
  • L'outil suspend ou interrompt son opération s'il détecte une charge excessive sur le serveur. Voir "--max-load" et "--critical-load" pour plus de détails.
  • L'outil définit "innodb_lock_wait_timeout=1" et (pour MySQL 5.5 et plus récent) "lock_wait_timeout=60" afin qu'il soit plus susceptible d'être victime de toute contention de verrou, et moins susceptible de perturber d'autres transactions. Ces valeurs peuvent être modifiées en spécifiant "--set-vars".
  • L'outil refuse de modifier la table si des contraintes de clé étrangère y font référence, à moins que vous ne spécifiiez "--alter-foreign-keys-method".
  • L'outil ne peut pas modifier les tables MyISAM sur les nœuds "Percona XtraDB Cluster".

Percona XtraDB Cluster

pt-online-schema-change fonctionne avec Percona XtraDB Cluster (PXC) 5.5.28-23.7 et plus récent, mais il y a deux limitations : seules les tables InnoDB peuvent être modifiées, et "wsrep_OSU_method" doit être réglé sur "TOI" (total order isolation). L'outil se termine avec une erreur si l'hôte est un nœud de cluster et que la table est MyISAM ou est en cours de conversion en MyISAM ("ENGINE=MyISAM"), ou si "wsrep_OSU_method" n'est pas "TOI". Il n'y a aucun moyen de désactiver ces vérifications.

MySQL 5.7 + Colonnes générées

Les outils ignorent les colonnes "GENERATED" de MySQL 5.7+ car la valeur de ces colonnes est générée selon l'expression utilisée pour calculer les valeurs des colonnes.

SORTIE

L'outil imprime des informations sur ses activités sur STDOUT afin que vous puissiez voir ce qu'il fait. Pendant la phase de copie des données, il imprime des rapports "--progress" sur STDERR. Vous pouvez obtenir des informations supplémentaires en spécifiant "--print".

Si "--statistics" est spécifié, un rapport de divers comptages d'événements internes est imprimé à la fin, comme suit :

# Événement  Nombre
# ====== =====
# INSERT     1

OPTIONS

"--dry-run" et "--execute" sont mutuellement exclusifs.

Cet outil accepte des arguments de ligne de commande supplémentaires. Reportez-vous à la "SYNTAXE" et aux informations d'utilisation pour plus de détails.

--alter
type : chaîne de caractères

La modification du schéma, sans les mots-clés ALTER TABLE. Vous pouvez effectuer plusieurs modifications sur la table en les spécifiant avec des virgules. Veuillez vous référer au manuel MySQL pour la syntaxe de ALTER TABLE.

Les limitations suivantes s'appliquent et, si elles sont tentées, provoqueront un échec imprévisible de l'outil :

  • Dans presque tous les cas, une clé PRIMAIRE ou un INDEX UNIQUE doit être présent dans la table. Ceci est nécessaire car l'outil crée un déclencheur DELETE pour maintenir la nouvelle table à jour pendant que le processus est en cours.

    Une exception notable est lorsqu'une clé PRIMAIRE ou un INDEX UNIQUE est créé à partir de colonnes existantes dans le cadre de la clause ALTER ; dans ce cas, il utilisera cette (ces) colonne(s) pour le déclencheur DELETE.

  • La clause "RENAME" ne peut pas être utilisée pour renommer la table.
  • Les colonnes ne peuvent pas être renommées en les supprimant et en les recréant avec le nouveau nom. L'outil ne copiera pas les données de la colonne d'origine vers la nouvelle colonne.
  • Si vous ajoutez une colonne sans valeur par défaut et la rendez NON NULLE, l'outil échouera, car il n'essaiera pas de deviner une valeur par défaut pour vous ; vous devez spécifier la valeur par défaut.
  • "DROP FOREIGN KEY constraint_name" nécessite de spécifier "_constraint_name" plutôt que le nom réel "constraint_name". En raison d'une limitation dans MySQL, pt-online-schema-change ajoute un trait de soulignement initial aux noms de contraintes de clé étrangère lors de la création de la nouvelle table. Par exemple, pour supprimer cette contrainte : 
    CONSTRAINT `fk_foo` FOREIGN KEY (`foo_id`) REFERENCES `bar` (`foo_id`)

    Vous devez spécifier "LOCK IN SHARE MODE" avec MySQL 5.0 car cela peut provoquer une erreur de réplication qui casse la réplication : 

    Query caused different errors on master and slave. Error on master:
'Deadlock found when trying to get lock; try restarting transaction' (1213),
Error on slave: 'no error' (0). Default database: 'pt_osc'.
Query: 'INSERT INTO pt_osc.t (id, c) VALUES ('730', 'new row')'

    L'erreur se produit lors de la conversion d'une table MyISAM en InnoDB car MyISAM n'est pas transactionnel alors qu'InnoDB l'est. MySQL 5.1 et versions ultérieures gèrent ce cas correctement, mais les tests reproduisent l'erreur dans 5 % des cas avec MySQL 5.0.

    Il s'agit d'un bug MySQL, similaire à http://bugs.mysql.com/bug.php?id=45694, mais il n'y a pas de correctif ni de solution de contournement dans MySQL 5.0. Sans "LOCK IN SHARE MODE", les tests réussissent dans 100 % des cas, le risque de perte de données ou de rupture de la réplication devrait donc être négligeable.

    Assurez-vous de vérifier la nouvelle table si vous utilisez MySQL 5.0 et que vous effectuez une conversion de MyISAM vers InnoDB !

--alter-foreign-keys-method
type : string

Comment modifier les clés étrangères pour qu'elles référencent la nouvelle table. Les clés étrangères qui référencent la table à modifier doivent être traitées spécialement pour garantir qu'elles continuent à référencer la bonne table. Lorsque l'outil renomme la table d'origine pour laisser la nouvelle prendre sa place, les clés étrangères « suivent » la table renommée et doivent être modifiées pour référencer la nouvelle table à la place.

L'outil prend en charge deux techniques pour y parvenir. Il trouve automatiquement les « tables enfants » qui référencent la table à modifier.

auto
Détermine automatiquement la meilleure méthode. L'outil utilise "rebuild_constraints" si possible (voir la description de cette méthode pour plus de détails), et sinon, il utilise "drop_swap".
rebuild_constraints
Cette méthode utilise "ALTER TABLE" pour supprimer et ré-ajouter les contraintes de clé étrangère qui référencent la nouvelle table. C'est la technique préférée, sauf si une ou plusieurs des tables « enfants » sont si volumineuses que l'"ALTER" prendrait trop de temps. L'outil détermine cela en comparant le nombre de lignes dans la table enfant au rythme auquel l'outil est capable de copier les lignes de l'ancienne table vers la nouvelle. Si l'outil estime que la table enfant peut être modifiée en moins de temps que le « --chunk-time », il utilisera cette technique. Pour estimer le temps nécessaire à la modification de la table enfant, l'outil multiplie le taux de copie des lignes par « --chunk-size-limit », car "ALTER TABLE" de MySQL est généralement beaucoup plus rapide que le processus externe de copie des lignes.

En raison d'une limitation de MySQL, les clés étrangères n'auront pas les mêmes noms après l'ALTER qu'avant. L'outil doit renommer la clé étrangère lorsqu'il la redéfinit, ce qui ajoute un trait de soulignement au début du nom. Dans certains cas, MySQL renomme également automatiquement les index requis pour la clé étrangère.

drop_swap
Désactive les vérifications de clés étrangères (FOREIGN_KEY_CHECKS=0), puis supprime la table d'origine avant de renommer la nouvelle table à sa place. Ceci est différent de la méthode normale d'échange des tables, qui utilise un "RENAME" atomique indétectable par les applications clientes.

Cette méthode est plus rapide et ne bloque pas, mais elle est plus risquée pour deux raisons. Premièrement, pendant un court instant entre la suppression de la table d'origine et le renommage de la table temporaire, la table à modifier n'existe tout simplement pas, et les requêtes contre elle entraîneront une erreur. Deuxièmement, s'il y a une erreur et que la nouvelle table ne peut pas être renommée à la place de l'ancienne, il est trop tard pour annuler, car l'ancienne table a disparu définitivement.

Cette méthode force "--no-swap-tables" et "--no-drop-old-table".

none
Cette méthode est similaire à "drop_swap" sans le « swap ». Toutes les clés étrangères qui référençaient la table d'origine référenceront désormais une table inexistante. Cela provoquera généralement des violations de clés étrangères visibles dans "SHOW ENGINE INNODB STATUS", similaires à ce qui suit : 
Trying to add to index `idx_fk_staff_id` tuple:
DATA TUPLE: 2 fields;
0: len 1; hex 05; asc  ;;
1: len 4; hex 80000001; asc     ;;
But the parent table `sakila`.`staff_old`
or its .ibd file does not currently exist!

C'est parce que la table d'origine (dans ce cas, sakila.staff) a été renommée en sakila.staff_old puis supprimée. Cette méthode de gestion des contraintes de clé étrangère est fournie pour que l'administrateur de la base de données puisse désactiver la fonctionnalité intégrée de l'outil si désiré.

--[no]analyze-before-swap
défaut : oui

Exécute ANALYZE TABLE sur la nouvelle table avant l'échange avec l'ancienne. Par défaut, cela se produit uniquement lors de l'exécution de MySQL 5.6 et versions ultérieures, et lorsque "innodb_stats_persistent" est activé. Spécifiez l'option explicitement pour l'activer ou la désactiver indépendamment de la version de MySQL et de "innodb_stats_persistent".

Cela contourne un problème potentiellement grave lié aux statistiques de l'optimiseur InnoDB. Si la table en cours de modification est très sollicitée et que l'outil se termine rapidement, la nouvelle table n'aura pas de statistiques d'optimiseur après l'échange. Cela peut entraîner des requêtes rapides utilisant des index à effectuer des analyses complètes de tables jusqu'à ce que les statistiques de l'optimiseur soient mises à jour (généralement après 10 secondes). Si la table est volumineuse et le serveur très sollicité, cela peut provoquer une interruption de service.

--ask-pass
Demande un mot de passe lors de la connexion à MySQL.
--binary-index
Cette option modifie le comportement de « --history » de telle sorte que les colonnes de limite supérieure et inférieure de la table d'historique soient créées avec le type de données BLOB. Ceci est utile lorsque vous modifiez de grandes tables avec des clés qui incluent un type de données binaires ou qui ont des jeux de caractères non standard. Voir « --history » et « --resume ».
--channel
type : string

Nom du canal utilisé lors de la connexion à un serveur utilisant des canaux de réplication. Supposons que vous ayez deux sources de réplication, source_a au port 12345, source_b au port 1236 et une réplique connectée aux deux sources en utilisant les canaux chan_source_a et chan_source_b. Vous pouvez utiliser --channel=chan_source_a pour spécifier le nom du canal à utiliser dans la commande SHOW REPLICA STATUS que pt-online-schema-change utilise pour calculer le décalage de réplication.

--charset
forme courte : -A ; type : string

Jeu de caractères par défaut. Si la valeur est utf8, active Perl's binmode sur STDOUT pour utf8, passe l'option mysql_enable_utf8 à DBD::mysql et exécute SET NAMES UTF8 après la connexion à MySQL. Toute autre valeur active binmode sur STDOUT sans la couche utf8, et exécute SET NAMES après la connexion à MySQL.

--[no]check-alter
défaut : oui

Analyse le « --alter » spécifié et essaie de signaler un comportement involontaire possible. Actuellement, il vérifie :

Renommages de colonnes
Dans les versions précédentes de l'outil, le renommage d'une colonne avec "CHANGE COLUMN name new_name" entraînait la perte des données de cette colonne. L'outil analyse maintenant l'instruction alter et essaie de détecter ces cas, de sorte que les colonnes renommées devraient avoir les mêmes données que les originales. Cependant, le code qui fait cela n'est pas un analyseur SQL complet, vous devriez donc d'abord exécuter l'outil avec "--dry-run" et "--print" et vérifier qu'il détecte correctement les colonnes renommées.
DROP PRIMARY KEY
Si « --alter » contient "DROP PRIMARY KEY" (insensible à la casse et aux espaces), un avertissement est affiché et l'outil se termine à moins que « --dry-run » ne soit spécifié. La modification de la clé primaire peut être dangereuse, mais l'outil peut la gérer. Les déclencheurs de l'outil, en particulier le déclencheur DELETE, sont les plus affectés par la modification de la clé primaire car l'outil préfère utiliser la clé primaire pour ses déclencheurs. Vous devriez d'abord exécuter l'outil avec « --dry-run » et « --print » et vérifier que les déclencheurs sont corrects.
--[no]check-foreign-keys
défaut : oui

Vérifie les clés étrangères auto-référencées. Actuellement, les clés étrangères auto-référencées ne sont pas entièrement prises en charge, donc pour éviter les erreurs, ce programme ne s'exécutera pas si la table a des clés étrangères auto-référencées. Utilisez ce paramètre pour désactiver les vérifications des clés étrangères auto-référencées.

--check-interval
type : temps ; défaut : 1

Temps de veille entre les vérifications de « --max-lag ».

--[no]check-plan
défaut : oui

Vérifie les plans d'exécution des requêtes pour la sécurité. Par défaut, cette option amène l'outil à exécuter EXPLAIN avant d'exécuter des requêtes censées accéder à une petite quantité de données, mais qui pourraient accéder à de nombreuses lignes si MySQL choisit un mauvais plan d'exécution. Celles-ci incluent les requêtes pour déterminer les limites des morceaux et les requêtes de morceaux elles-mêmes. S'il apparaît que MySQL utilisera un mauvais plan d'exécution de requête, l'outil arrêtera la copie des lignes et mourra.

L'outil utilise plusieurs heuristiques pour déterminer si un plan d'exécution est mauvais. La première est de savoir si EXPLAIN signale que MySQL a l'intention d'utiliser l'index souhaité pour accéder aux lignes. Si MySQL choisit un index différent, l'outil considère la requête comme non sécurisée.

L'outil vérifie également quelle partie de l'index MySQL signale qu'il utilisera pour la requête. La sortie EXPLAIN montre cela dans la colonne key_len. L'outil mémorise la plus grande key_len vue et se termine si MySQL signale qu'il utilisera un préfixe plus petit de l'index.

Cette option ajoute une certaine

--[no]chunk-tables

Lorsque cette option est activée, le tableau est découpé en morceaux pour minimiser la perte d'informations sur le serveur. Cela peut ralentir la copie de données car chaque morceau nécessite une requête supplémentaire. La réduction des morceaux à une taille trop petite provoquera une surcharge de trafic réseau plus importante. Il est donc recommandé de ne pas réduire la taille des morceaux de manière excessive afin d'éviter un temps d'exécution très long.

--[no]check-replication-filters
par défaut : yes

Interrompt l'opération si un filtre de réplication est défini sur un serveur. L'outil recherche les options de serveur qui filtrent la réplication, telles que binlog_ignore_db et replicate_do_db. S'il trouve de tels filtres, il s'arrête avec une erreur.

Si les répliques sont configurées avec des options de filtrage, vous devez faire attention à ne pas modifier les bases de données ou les tables qui existent sur la source de réplication et non sur les répliques, car cela pourrait entraîner une défaillance de la réplication. Pour plus d'informations sur les règles de réplication, consultez http://dev.mysql.com/doc/en/replication-rules.html.

--check-replica-lag
type : string

Suspend la copie des données jusqu'à ce que le retard de cette réplique soit inférieur à "--max-lag". La valeur est un DSN qui hérite des propriétés des options de connexion ("--port", "--user", etc.). Cette option remplace le comportement normal de recherche et de surveillance continue du retard de réplication sur TOUTES les répliques connectées. Si vous ne souhaitez pas surveiller TOUTES les répliques, mais que vous souhaitez en surveiller plus d'une, utilisez l'option DSN de l'option "--recursion-method" au lieu de cette option.

--check-slave-lag
type : string

Cette option est obsolète et sera supprimée dans les futures versions. Utilisez "--check-replica-lag" à la place.

--chunk-index
type : string

Préfère cet index pour le découpage des tables. Par défaut, l'outil choisit l'index le plus approprié pour le découpage. Cette option vous permet de spécifier l'index que vous préférez. Si l'index n'existe pas, l'outil revient à son comportement par défaut de choix d'un index. L'outil ajoute l'index aux instructions SQL dans une clause "FORCE INDEX". Soyez prudent lors de l'utilisation de cette option ; un mauvais choix d'index pourrait entraîner de mauvaises performances.

--chunk-index-columns
type : int

Utilise seulement ce nombre de colonnes de gauche d'un "--chunk-index". Ceci ne fonctionne que pour les index composites, et est utile dans les cas où un bug dans l'optimiseur de requêtes (planificateur) de MySQL lui fait analyser une large plage de lignes au lieu d'utiliser l'index pour localiser précisément les points de départ et de fin. Ce problème se produit parfois sur des index comportant de nombreuses colonnes, par exemple 4 ou plus. Si cela se produit, l'outil peut afficher un avertissement concernant l'option "--[no]check-plan". Demander à l'outil d'utiliser seulement les N premières colonnes de l'index est une solution de contournement pour le bug dans certains cas.

--chunk-size
type : size; par défaut : 1000

Nombre de lignes à sélectionner pour chaque morceau copié. Les suffixes autorisés sont k, M, G.

Cette option peut remplacer le comportement par défaut, qui consiste à ajuster dynamiquement la taille des morceaux pour essayer de faire en sorte que les morceaux s'exécutent en exactement "--chunk-time" secondes. Lorsque cette option n'est pas explicitement définie, sa valeur par défaut est utilisée comme point de départ, mais après cela, l'outil ignore la valeur de cette option. Si vous définissez explicitement cette option, cela désactive le comportement d'ajustement dynamique et essaie de faire en sorte que tous les morceaux aient exactement le nombre de lignes spécifié.

--chunk-size-limit
type : float; par défaut : 4.0

Ne copie pas les morceaux dont la taille est supérieure à la taille de morceau souhaitée, multipliée par cette limite.

Lorsqu'une table n'a pas d'index unique, les tailles des morceaux peuvent être inexactes. Cette option spécifie une limite maximale tolérable à l'inexactitude. L'outil utilise <EXPLAIN> pour estimer le nombre de lignes dans le morceau. Si cette estimation dépasse la taille de morceau souhaitée multipliée par la limite, l'outil arrête de copier les lignes et s'arrête.

La valeur minimale pour cette option est 1, ce qui signifie qu'aucun morceau ne peut être plus grand que "--chunk-size". Vous ne voudrez probablement pas spécifier 1, car les lignes rapportées par EXPLAIN sont des estimations, qui peuvent différer du nombre réel de lignes dans le morceau. Vous pouvez désactiver la vérification des morceaux surdimensionnés en spécifiant une valeur de 0.

L'outil utilise également cette option pour déterminer comment gérer les clés étrangères qui référencent la table à modifier. Voir "--alter-foreign-keys-method" pour plus de détails.

--chunk-time
type : float; par défaut : 0.5

Ajuste dynamiquement la taille des morceaux pour que chaque requête de copie de données prenne ce temps pour s'exécuter. L'outil suit le taux de copie (lignes par seconde) et ajuste la taille des morceaux après chaque requête de copie de données, de sorte que la requête suivante prenne ce temps (en secondes) pour s'exécuter. Il maintient une moyenne mobile exponentiellement décroissante des requêtes par seconde, de sorte que si les performances du serveur changent en raison des modifications de la charge du serveur, l'outil s'adapte rapidement.

Si cette option est définie sur zéro, la taille des morceaux n'est pas ajustée automatiquement, de sorte que les temps de requête varient, mais pas les tailles des morceaux de requête. Une autre façon de faire la même chose est de spécifier une valeur pour "--chunk-size" explicitement, au lieu de la laisser à sa valeur par défaut.

--config
type : Array

Lit cette liste de fichiers de configuration séparés par des virgules ; si spécifié, cela doit être la première option sur la ligne de commande.

--history-table
type : string; par défaut : percona.pt_osc_history

Crée la base de données et la table "--history" si elles n'existent pas. La structure de la table d'historique est la même que la table suggérée mentionnée dans "--history".

Par défaut, "--history" crée automatiquement la base de données et la table spécifiées par cette option si elles n'existent pas.

--critical-load
type : Array; par défaut : Threads_running=50

Examine SHOW GLOBAL STATUS après chaque morceau, et s'arrête si la charge est trop élevée. L'option accepte une liste de variables de statut MySQL et de seuils, séparés par des virgules. --[no]check-unique-key-change
par défaut : yes

Empêchez "pt-online-schema-change" de s'exécuter si l'instruction spécifiée pour "--alter" tente d'ajouter un index unique. Puisque "pt-online-schema-change" utilise "INSERT IGNORE" pour copier les lignes vers la nouvelle table, si la ligne écrite produit une clé dupliquée, elle échouera silencieusement et des données seront perdues.

Exemple :

CREATE DATABASE test;
USE test;
CREATE TABLE `a` (
  `id` int(11) NOT NULL,
  `unique_id` varchar(32) DEFAULT NULL,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=latin1;
insert into a values (1, "a");
insert into a values (2, "b");
insert into a values (3, "");
insert into a values (4, "");
insert into a values (5, NULL);
insert into a values (6, NULL);

L'utilisation de "pt-online-schema-change" pour ajouter un index unique sur le champ "unique_id", entraînera la perte de certaines lignes en raison de l'utilisation de "INSERT IGNORE" pour copier les lignes de la table source. Pour cette raison, "pt-online-schema-change" échouera s'il détecte que le paramètre "--alter" tente d'ajouter une clé unique et affichera une requête d'exemple à exécuter pour détecter s'il existe des lignes qui produiront des index dupliqués.

Même si vous exécutez la requête et qu'il n'y a pas de lignes qui produiront des index dupliqués, gardez à l'esprit qu'après avoir exécuté cette requête, des modifications peuvent être apportées à la table qui peuvent produire des lignes dupliquées et ces données seront perdues.

Met en pause la copie des données jusqu'à ce que le décalage de toutes les répliques soit inférieur à cette valeur. --max-load
type : Tableau ; par défaut : Threads_running=25

Examine SHOW GLOBAL STATUS après chaque bloc, et fait une pause si des variables de statut sont supérieures à leurs seuils. L'option accepte une liste de variables de statut MySQL séparées par des virgules. Une valeur facultative "=MAX_VALUE" (ou ":MAX_VALUE") peut suivre chaque variable. Si elle n'est pas fournie, l'outil détermine un seuil en examinant la valeur actuelle et en l'augmentant de 20 %.

Par exemple, si vous souhaitez que l'outil fasse une pause lorsque Threads_connected devient trop élevé, vous pouvez spécifier "Threads_connected", et l'outil vérifiera la valeur actuelle lorsqu'il commencera à travailler et ajoutera 20 % à cette valeur. Si la valeur actuelle est de 100, alors l'outil fera une pause lorsque Threads_connected dépassera 120, et reprendra le travail lorsqu'il sera à nouveau inférieur à 120. Si vous souhaitez spécifier un seuil explicite, tel que 110, vous pouvez utiliser soit "Threads_connected:110", soit "Threads_connected=110".

Le but de cette option est d'empêcher l'outil d'ajouter trop de charge au serveur. Si les requêtes de copie de données sont intrusives, ou si elles provoquent des attentes de verrouillage, alors d'autres requêtes sur le serveur auront tendance à être bloquées et mises en file d'attente. Cela provoquera généralement une augmentation de Threads_running, et l'outil peut le détecter en exécutant SHOW GLOBAL STATUS immédiatement après la fin de chaque requête. Si vous spécifiez un seuil pour cette variable, vous pouvez alors demander à l'outil d'attendre que les requêtes s'exécutent normalement à nouveau. Cela n'empêchera pas la mise en file d'attente, cependant ; cela donnera seulement au serveur une chance de récupérer de la mise en file d'attente. Si vous remarquez une mise en file d'attente, il est préférable de diminuer le temps de bloc.

--preserve-triggers
Préserve les anciens déclencheurs lorsqu'ils sont spécifiés. Depuis MySQL 5.7.2, il est possible de définir plusieurs déclencheurs pour une table donnée qui ont le même événement de déclencheur et le même moment d'action. Cela nous permet d'ajouter les déclencheurs nécessaires pour "pt-online-schema-change" même si la table a déjà ses propres déclencheurs. Si cette option est activée, "pt-online-schema-change" tentera de copier tous les déclencheurs existants vers la nouvelle table AVANT de commencer à copier les lignes de la table d'origine pour s'assurer que les anciens déclencheurs peuvent être appliqués après la modification de la table.

Exemple.

CREATE TABLE test.t1 (
     id INT NOT NULL AUTO_INCREMENT,
     f1 INT,
     f2 VARCHAR(32),
     PRIMARY KEY (id)
);
CREATE TABLE test.log (
   ts  TIMESTAMP,
   msg VARCHAR(255)
);
CREATE TRIGGER test.after_update
 AFTER
   UPDATE ON test.t1
   FOR EACH ROW
     INSERT INTO test.log VALUES (NOW(), CONCAT("updated row row with id ", OLD.id, " old f1:", OLD.f1, " new f1: ", NEW.f1 ));

Pour cette combinaison de table et de déclencheurs, il n'est pas possible d'utiliser --preserve-triggers avec un --alter comme ceci : "DROP COLUMN f1" car le déclencheur fait référence à la colonne supprimée et cela ferait échouer le déclencheur.

Après avoir testé que les déclencheurs fonctionneront sur la nouvelle table, les déclencheurs sont supprimés de la nouvelle table jusqu'à ce que toutes les lignes aient été copiées, puis ils sont réappliqués.

--preserve-triggers ne peut pas être utilisé avec ces autres paramètres, --no-drop-triggers, --no-drop-old-table et --no-swap-tables puisque --preserve-triggers implique que les anciens déclencheurs doivent être supprimés et recréés dans la nouvelle table. Puisqu'il n'est pas possible d'avoir plus d'un déclencheur portant le même nom, les anciens déclencheurs doivent être supprimés afin de pouvoir les recréer dans la nouvelle table.

L'utilisation de "--preserve-triggers" avec "--no-swap-tables" entraînera le maintien des déclencheurs sur la table d'origine. Veuillez lire la documentation de --swap-tables

Si "--no-swap-tables" et "--no-drop-new-table" sont tous deux définis, le déclencheur restera sur la table d'origine et sera dupliqué sur la nouvelle table (le déclencheur aura un suffixe aléatoire car aucun nom de déclencheur n'est unique).

NOM

pt-online-schema-change

changez le schéma de table sans temps d'arrêt

SYNOPSIS

pt-online-schema-change [OPTIONS] [DSN=connection_string] [SQL=SQL_statement]
pt-online-schema-change --alter-foreign-keys-method=... [OPTIONS] [DSN=connection_string] [SQL=SQL_statement]
pt-online-schema-change --dry-run [OPTIONS] [DSN=connection_string] [SQL=SQL_statement]

RISQUES

pt-online-schema-change est un outil puissant. En bref, il effectue les opérations suivantes :

  • Il crée une nouvelle table vide avec le schéma souhaité.
  • Il copie les données de la table d'origine vers la nouvelle table.
  • Il crée des déclencheurs sur la table d'origine pour capturer les modifications apportées pendant que les données sont copiées.
  • Il applique les modifications en attente à la nouvelle table.
  • Il renomme la table d'origine pour qu'elle soit la nouvelle table.
  • Il renomme la nouvelle table pour qu'elle ait le nom d'origine.
  • Il supprime l'ancienne table d'origine.

Cependant, en dépit de ses précautions, il existe des risques. Il est impératif de comprendre ces risques avant d'utiliser cet outil. Lisez la section « RISQUES » du fichier README.

DESCRIPTION

pt-online-schema-change réécrit les tables de base de données en créant une nouvelle table avec le schéma souhaité, en copiant les données et en utilisant des déclencheurs pour synchroniser les données pendant que l'opération est en cours. Il s'agit de l'un des nombreux outils qui peuvent être utilisés pour effectuer des modifications de schéma en ligne sur MySQL. L'objectif est de minimiser ou d'éliminer les temps d'arrêt pour les applications qui dépendent des tables modifiées.

Il est conçu pour être utilisé sur de grandes tables où une opération `ALTER TABLE` normale prendrait trop de temps et bloquerait la table, rendant l'application indisponible. L'outil tente de minimiser la charge sur le serveur et le temps pendant lequel le verrouillage de la table est nécessaire.

Cet outil n'est pas une solution miracle. Il existe des situations où il ne peut pas être utilisé et d'autres où ses opérations peuvent affecter les performances. Il est essentiel de comprendre comment il fonctionne et ce qu'il fait avant de l'utiliser sur une table en production.

NE JAMAIS UTILISER CET OUTIL SANS L'AVOIR COMPRIS COMPLÈTEMENT.

Percona XtraDB Cluster

pt-online-schema-change est entièrement compatible avec Percona XtraDB Cluster. Il le détectera et désactivera les déclencheurs pour éviter une surcharge du cluster.

MySQL 5.7 + Colonnes générées

pt-online-schema-change fonctionne avec les colonnes générées par MySQL 5.7 et les versions ultérieures. Il peut modifier les colonnes générées et les colonnes normales dans le même `ALTER TABLE`. Il peut également ajouter des colonnes générées.

OUTPUT

Par défaut, l'outil effectue une journalisation verbale sur STDOUT. Il peut produire des dizaines de mégaoctets de sortie sur de grandes tables.

Il est fortement recommandé d'utiliser le paramètre --print ou --execute pour exécuter l'outil, ce qui vous permet de contrôler la quantité de sortie et de la transmettre à d'autres utilitaires comme pv ou grep.

Voici un exemple typique de sortie lorsqu'il est utilisé avec --print :

# pt-online-schema-change --print --alter "ADD COLUMN c INT" h=localhost,D=test,t=tbl_name
USE `test`;
ALTER TABLE `test`.`tbl_name` ADD COLUMN `c` INT;
-- et d'autres commandes SQL pour créer la nouvelle table, copier les données, définir des déclencheurs, etc.

La sortie peut être volumineuse et générer plusieurs mégaoctets de sortie.

OPTIONS

La plupart des options sont décrites dans le fichier README. Les plus importantes incluent :

--alter string
La chaîne ALTER TABLE valide que vous souhaitez appliquer à la table. Par exemple : "ADD COLUMN c INT", "DROP INDEX i_col1", "CHANGE COLUMN c1 c1 BIGINT".
--dry-run
Imprime la commande SQL qui serait exécutée, mais ne l'exécute pas. Utile pour tester.
--execute
Exécute les commandes SQL.
--print
Imprime les commandes SQL qui seraient exécutées, mais ne les exécute pas. Utile pour l'utiliser avec d'autres outils.
--alter-foreign-keys-method string
La méthode à utiliser pour gérer les clés étrangères sur la table cible. Les valeurs valides sont auto, drop_swap, rebuild_constraints, disable_fk.
--victim-master-delay secondes
Le délai maximum d'un esclave par rapport à son maître avant que l'outil ne soit arrêté. Défaut à 1 seconde.

PLUGIN

Cet outil est un plugin Perl qui fonctionne avec la base de données MySQL. Il doit être installé sur le serveur MySQL.

DSN OPTIONS

Les options DSN sont utilisées pour spécifier la connexion à la base de données. Elles incluent :

--host ou -h string
Nom d'hôte du serveur MySQL.

Port du serveur MySQL.
--user ou -u string
Nom d'utilisateur pour la connexion à MySQL.
--password ou -p string
Mot de passe pour la connexion à MySQL.
--database ou -D string
Nom de la base de données.
--table ou -t string
Nom de la table.

SYSTEM REQUIREMENTS

Vous avez besoin de Perl, DBI, DBD::mysql et de certains packages de base qui devraient être installés dans toute version raisonnablement récente de Perl.

Cet outil ne fonctionne qu'avec MySQL 5.0.2 et les versions ultérieures, car les versions antérieures ne prennent pas en charge les déclencheurs. Un certain nombre de permissions doivent également être définies sur MySQL pour que pt-online-schema-change fonctionne comme prévu. Les privilèges globaux PROCESS, SUPER, REPLICATION SLAVE, ainsi que les privilèges de table SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, ALTER et TRIGGER doivent être accordés sur le serveur. La réplique n'a besoin que des privilèges REPLICATION SLAVE et REPLICATION CLIENT.
