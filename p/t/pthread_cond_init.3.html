pthread_cond_init(3) Manuel des fonctions de bibliothèque pthread_cond_init(3)

NOM

pthread_cond_init, pthread_cond_signal, pthread_cond_broadcast, pthread_cond_wait, pthread_cond_timedwait, pthread_cond_destroy - opérations sur les conditions

SYNOPSIS

#include <pthread.h>
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;
int pthread_cond_init(pthread_cond_t *cond,
                      pthread_condattr_t *cond_attr);
int pthread_cond_signal(pthread_cond_t *cond);
int pthread_cond_broadcast(pthread_cond_t *cond);
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);
int pthread_cond_timedwait(pthread_cond_t *cond, pthread_mutex_t *mutex,
                      const struct timespec *abstime);
int pthread_cond_destroy(pthread_cond_t *cond);

DESCRIPTION

Une condition (abrégé pour "variable de condition") est un dispositif de synchronisation qui permet aux threads de suspendre leur exécution et de céder le processeur jusqu'à ce qu'un certain prédicat sur des données partagées soit satisfait. Les opérations de base sur les conditions sont : signaler la condition (lorsque le prédicat devient vrai) et attendre la condition, suspendant l'exécution du thread jusqu'à ce qu'un autre thread signale la condition.

Une variable de condition doit toujours être associée à un mutex, pour éviter la condition de concurrence où un thread se prépare à attendre sur une variable de condition et un autre thread signale la condition juste avant que le premier thread n'attende réellement dessus.

pthread_cond_init() initialise la variable de condition cond, en utilisant les attributs de condition spécifiés dans cond_attr, ou les attributs par défaut si cond_attr est NULL. L'implémentation LinuxThreads ne prend en charge aucun attribut pour les conditions, par conséquent le paramètre cond_attr est effectivement ignoré.

Les variables de type pthread_cond_t peuvent également être initialisées statiquement, en utilisant la constante PTHREAD_COND_INITIALIZER.

pthread_cond_signal() redémarre l'un des threads qui attendent sur la variable de condition cond. Si aucun thread n'attend sur cond, rien ne se passe. Si plusieurs threads attendent sur cond, exactement un est redémarré, mais il n'est pas spécifié lequel.

pthread_cond_broadcast() redémarre tous les threads qui attendent sur la variable de condition cond. Rien ne se passe si aucun thread n'attend sur cond.

pthread_cond_wait() déverrouille atomiquement le mutex (conformément à pthread_unlock_mutex()) et attend que la variable de condition cond soit signalée. L'exécution du thread est suspendue et ne consomme aucun temps processeur jusqu'à ce que la variable de condition soit signalée. Le mutex doit être verrouillé par le thread appelant à l'entrée de pthread_cond_wait(). Avant de retourner au thread appelant, pthread_cond_wait() réacquiert le mutex (conformément à pthread_mutex_lock()).

Le déverrouillage du mutex et la mise en attente sur la variable de condition sont effectués atomiquement. Ainsi, si tous les threads acquièrent toujours le mutex avant de signaler la condition, cela garantit que la condition ne peut pas être signalée (et donc ignorée) entre le moment où un thread verrouille le mutex et le moment où il attend sur la variable de condition. Voir CAVEATS ci-dessous.

pthread_cond_timedwait() déverrouille atomiquement le mutex et attend sur cond, comme le fait pthread_cond_wait(), mais il limite également la durée de l'attente. Si cond n'a pas été signalé dans le délai spécifié par abstime, le mutex mutex est réacquis et pthread_cond_timedwait() retourne l'erreur ETIMEDOUT. Le paramètre abstime spécifie une heure absolue, avec la même origine que time(2) et gettimeofday(2) : un abstime de 0 correspond à 00:00:00 GMT, le 1er janvier 1970.

pthread_cond_destroy() détruit une variable de condition, libérant les ressources qu'elle pourrait détenir. Aucun thread ne doit attendre sur la variable de condition à l'entrée de pthread_cond_destroy(). Dans l'implémentation LinuxThreads, aucune ressource n'est associée aux variables de condition, donc pthread_cond_destroy() ne fait rien d'autre que de vérifier que la condition n'a pas de threads en attente.

ANNULATION

pthread_cond_wait() et pthread_cond_timedwait() sont des points d'annulation. Si un thread est annulé alors qu'il est suspendu dans l'une de ces fonctions, le thread reprend immédiatement son exécution, puis reverrouille le mutex argument de pthread_cond_wait() et pthread_cond_timedwait(), et exécute finalement l'annulation. Par conséquent, les gestionnaires de nettoyage sont assurés que le mutex est verrouillé lorsqu'ils sont appelés.

SURETÉ EN CAS DE SIGNAUX ASSYNCHRONES

Les fonctions de condition ne sont pas sûres en cas de signaux asynchrones, et ne doivent pas être appelées depuis un gestionnaire de signaux. En particulier, l'appel de pthread_cond_signal() ou pthread_cond_broadcast() depuis un gestionnaire de signaux peut provoquer un blocage du thread appelant.

VALEUR DE RETOUR

Toutes les fonctions de variable de condition retournent 0 en cas de succès et un code d'erreur non nul en cas d'erreur.

ERREURS

pthread_cond_init(), pthread_cond_signal(), pthread_cond_broadcast(), et pthread_cond_wait() ne retournent jamais de code d'erreur.

La fonction pthread_cond_timedwait() retourne les codes d'erreur suivants en cas d'erreur :

ETIMEDOUT
La variable de condition n'a pas été signalée dans le délai spécifié par abstime .

La fonction pthread_cond_destroy() retourne le code d'erreur suivant en cas d'erreur :

EBUSY
Certains threads attendent actuellement sur cond .

VOIR AUSSI

CAVEATS

L'implémentation des fonctions fournies jusqu'à glibc 2.25 utilisait un verrou de données interne. Ce verrou ne supportait pas l'héritage de priorité et était sujet à une inversion de priorité illimitée, visible sur un système temps réel.

Après la réécriture de l'implémentation dans glibc 2.25, l'utilisation du verrou interne a changé. Le verrou interne est toujours acquis par les fonctions de signalement pthread_cond_signal() et pthread_cond_broadcast(). La fonction d'attente acquiert le verrou si le processus en attente a été interrompu. L'interruption peut être causée par exemple par un délai d'attente spécifié, et dénotée par la valeur d'erreur ETIMEDOUTA, ou par un signal reçu, qui est dénoté par la valeur d'erreur EINTR.

EXEMPLE

Considérez deux variables partagées x et y , protégées par le mutex mut, et une variable de condition cond qui doit être signalée lorsque x devient supérieur à y.

int x,y;
pthread_mutex_t mut = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;

L'attente jusqu'à ce que x soit supérieur à y est effectuée comme suit :

pthread_mutex_lock(&mut);
while (x <= y) {
        pthread_cond_wait(&cond, &mut);
}
/* opérer sur x et y */
pthread_mutex_unlock(&mut);

Les modifications sur x et y qui peuvent entraîner x à être supérieur à y devraient signaler la condition si nécessaire :

pthread_mutex_lock(&mut);
/* modifier x et y */
if (x > y) pthread_cond_broadcast(&cond);
pthread_mutex_unlock(&mut);

CAVEATS

Une fois qu'un thread est réveillé (par exemple, s'il n'y a que deux threads communiquant via x et y), pthread_cond_signal() peut être utilisé comme une alternative légèrement plus efficace à pthread_cond_broadcast(). En cas de doute, utilisez pthread_cond_broadcast().

Pour attendre que x devienne supérieur à y avec un délai d'attente de 5 secondes, faites ceci :

struct timeval now;
struct timespec timeout;
int retcode;
pthread_mutex_lock(&mut);
gettimeofday(&now);
timeout.tv_sec = now.tv_sec + 5;
timeout.tv_nsec = now.tv_usec * 1000;
retcode = 0;
while (x <= y && retcode != ETIMEDOUT) {
        retcode = pthread_cond_timedwait(&cond, &mut, &timeout);
}
if (retcode == ETIMEDOUT) {
        /* expiration du délai d'attente */
} else {
        /* opérer sur x et y */
}
pthread_mutex_unlock(&mut);
