NOM

pt-visual-explain - Formate la sortie EXPLAIN sous forme d'arbre.

SYNTAXE

Utilisation : pt-visual-explain [OPTIONS] [FICHIERS]

pt-visual-explain transforme la sortie EXPLAIN en une représentation arborescente du plan de requête. Si FICHIER est donné, l'entrée est lue à partir des fichiers. Sans FICHIER, ou lorsque FICHIER est -, lit l'entrée standard.

Exemples :

pt-visual-explain <fichier_contenant_sortie_explain>
pt-visual-explain -c <fichier_contenant_requête>
mysql -e "explain select * from mysql.user" | pt-visual-explain

RISQUES

Percona Toolkit est mature, éprouvé en conditions réelles et bien testé, mais tous les outils de base de données peuvent présenter un risque pour le système et le serveur de base de données. Avant d'utiliser cet outil, veuillez :

  • Lire la documentation de l'outil
  • Vérifier les "BUGS" connus de l'outil
  • Tester l'outil sur un serveur non-production
  • Sauvegarder votre serveur de production et vérifier les sauvegardes

DESCRIPTION

pt-visual-explain fait de l'ingénierie inverse de la sortie EXPLAIN de MySQL en un plan d'exécution de requête, qu'il formate ensuite en un arbre gauche-profond -- de la même manière que le plan est représenté à l'intérieur de MySQL. Il est possible de le faire à la main, ou de lire directement la sortie d'EXPLAIN, mais cela demande patience et expertise. Beaucoup de gens trouvent une représentation arborescente plus compréhensible.

Vous pouvez rediriger l'entrée vers pt-visual-explain ou spécifier un nom de fichier sur la ligne de commande, y compris le nom de fichier magique '-', qui lira depuis l'entrée standard. Il peut faire deux choses avec l'entrée : l'analyser à la recherche de quelque chose qui ressemble à une sortie EXPLAIN, ou se connecter à une instance MySQL et exécuter EXPLAIN sur l'entrée.

Lors de l'analyse de son entrée, pt-visual-explain comprend trois formats : tabulaire comme celui montré dans le client en ligne de commande mysql, vertical comme celui créé en utilisant le terminateur de ligne \G dans le client en ligne de commande mysql, et séparé par des tabulations. Il ignore toutes les lignes qu'il ne sait pas analyser.

Lors de l'exécution de l'entrée, pt-visual-explain remplace tout dans l'entrée jusqu'au premier mot-clé SELECT par 'EXPLAIN SELECT,' puis exécute le résultat. Vous devez spécifier "--connect" pour exécuter l'entrée comme une requête.

Dans les deux cas, il construit un arbre à partir de l'ensemble de résultats et l'imprime sur la sortie standard. Pour la requête suivante,

select * from sakila.film_actor join sakila.film using(film_id);

pt-visual-explain génère ce plan de requête :

JOIN
+- Recherche de signet
|  +- Table
|  |  table          film_actor
|  |  possible_keys  idx_fk_film_id
|  +- Recherche d'index
|     key            film_actor->idx_fk_film_id
|     possible_keys  idx_fk_film_id
|     key_len        2
|     ref            sakila.film.film_id
|     rows           2
+- Scan de table
   rows           952
   +- Table
      table          film
      possible_keys  PRIMARY

Le plan de requête est en recherche en profondeur gauche, et la racine de l'arbre est le nœud de sortie -- la dernière étape du plan d'exécution. En d'autres termes, lisez-le comme suit :

1.
Scan de la table 'film', qui accède à une estimation de 952 lignes.
2.
Pour chaque ligne, trouver les lignes correspondantes en effectuant une recherche d'index dans l'index film_actor->idx_fk_film_id avec la valeur de sakila.film.film_id, puis une recherche de signet dans la table film_actor.

Pour plus d'informations sur la lecture de la sortie EXPLAIN, veuillez consulter http://dev.mysql.com/doc/en/explain.html.

MODULES

Ce programme est en fait un module exécutable, pas seulement un script Perl ordinaire. En fait, il y a deux modules intégrés. Cela facilite les tests unitaires, mais il est également facile pour vous d'utiliser la fonctionnalité d'analyse et de construction d'arbres si vous le souhaitez.

Le package ExplainParser accepte une chaîne et analyse tout ce qui ressemble à une sortie EXPLAIN à partir de celle-ci. La syntaxe est la suivante :

require "pt-visual-explain";
my $p    = ExplainParser->new();
my $rows = $p->parse("some text");
# $rows est un arrayref de hashrefs.

Le package ExplainTree accepte un ensemble de lignes et les transforme en un arbre. Pour plus de commodité, vous pouvez également lui faire déléguer à ExplainParser et analyser le texte pour vous. Voici la syntaxe :

require "pt-visual-explain";
my $e      = ExplainTree->new();
my $tree   = $e->parse("some text", \%options);
my $output = $e->pretty_print($tree);
print $tree;

ALGORITHME

Cette section explique l'algorithme qui convertit EXPLAIN en un arbre. Vous pourriez être intéressé de lire ceci si vous voulez comprendre EXPLAIN plus en profondeur, ou essayer de comprendre comment cela fonctionne, mais sinon cette section n'enrichira probablement pas votre vie.

L'arbre peut être construit en examinant les colonnes id, select_type et table de chaque ligne.

La colonne id est le numéro séquentiel de la sélection. Cela n'indique pas le niveau d'imbrication ; elle provient simplement du comptage des SELECT à partir de la gauche de l'instruction SQL. C'est comme capturer des parenthèses dans une expression régulière.

Si deux lignes adjacentes ont la même valeur d'id, elles sont jointes avec la méthode standard de jointure multiple à balayage unique.

La colonne select_type indique a) qu'un nouveau sous-scope a été ouvert b) quel type de relation la ligne a avec la ligne précédente c) quel type d'opération la ligne représente.

  • SIMPLE signifie qu'il n'y a pas de sous-requêtes ou d'unions dans toute la requête.
  • PRIMARY signifie qu'il y en a, mais c'est le SELECT le plus externe.
  • [DEPENDENT] UNION signifie que ce résultat est combiné avec le résultat précédent (pas une ligne ; un résultat peut englober plus d'une ligne).
  • UNION RESULT termine un ensemble de résultats combinés.
  • [DEPENDENT|UNCACHEABLE] SUBQUERY signifie qu'un nouveau sous-scope s'ouvre. C'est le type de sous-requête qui se produit dans une clause WHERE, une liste SELECT ou autre ; il ne retourne pas une table dite "dérivée".
  • DERIVED est une sous-requête dans la clause FROM.

Les tables qui sont JOINées ont toutes le même select_type. Par exemple, si vous JOIN trois tables dans une sous-requête dépendante, elles diront toutes la même chose : DEPENDENT SUBQUERY.

La colonne table spécifie généralement le nom de la table ou l'alias, mais peut également dire <derivedN> ou <unionN,N...N>. Si elle dit <derivedN>, la ligne représente un accès à la table temporaire qui contient le résultat de la sous-requête dont l'id est N. Si elle dit <unionN,..N> c'est la même chose, mais elle fait référence aux résultats qu'elle combine.

Enfin, l'ordre compte. Si l'id d'une ligne est inférieur à celui de la ligne précédente, cela signifie qu'elle dépend de quelque chose d'autre que la ligne précédente. Par exemple,

explain select
   (select 1 from sakila.film),
   (select 2 from sakila.film_actor),
   (select 3 from sakila.actor);
| id | select_type | table      |
+----+-------------+------------+
|  1 | PRIMARY     | NULL       |
|  4 | SUBQUERY    | actor      |
|  3 | SUBQUERY    | film_actor |
|  2 | SUBQUERY    | film       |

Si les résultats étaient dans l'ordre 2-3-4, cela signifierait que 3 est une sous-requête de 2, 4 est une sous-requête de 3. Tel quel, cela signifie que 4 est une sous-requête de la ligne récente précédente la plus proche avec un id plus petit, qui est 1. De même pour 3 et 2.

Cette structure est difficile à construire programmatiquement en arbre pour la même raison qu'elle est difficile à comprendre par inspection : il y a à la fois des références avant et arrière. <derivedN> est une référence avant vers selectN, tandis que <unionM,N> est une référence arrière vers selectM et selectN. Cela rend la récursion et d'autres algorithmes de construction d'arbres difficiles à réaliser correctement (NOTE : après implémentation, je vois maintenant comment il serait possible de gérer les références avant et arrière, mais je n'ai aucune motivation pour changer quelque chose qui fonctionne). select * from (

DESCRIPTION

The pt-visual-explain utility takes the output of MySQL's EXPLAIN command and turns it into a tree. This is useful for visualizing how MySQL plans to execute a query.

The primary difficulty in parsing the EXPLAIN output is that MySQL doesn't explicitly state the parent-child relationships between rows in the output. The id column, which is incremented for each row, is the key to figuring this out. The id value is assigned to SELECTs in the order they appear in the query, but subqueries have their ids assigned after the enclosing query's id. This means that in the EXPLAIN output, subqueries may appear after the queries that use them.

The EXPLAIN output is a flat list. The goal is to turn this into a tree. To do this, we need to identify the parent-child relationships. The id column is the key. A row with a higher id than the previous row is a child of the previous row. Rows with the same id are siblings. Rows with a lower id mark the end of a scope.

UNION statements are a special case. They are listed with a select_type of UNION RESULT, and refer to the ids of the individual SELECTs that make up the UNION. The rows for the individual SELECTs will have the same id as each other, and the UNION RESULT row will have an id that refers to the next scope.

Consider this example:

explain select 1 from t1 union select 2 from t2;
+------+--------------+------------+
| id   | select_type  | table      |
+------+--------------+------------+
|    1 | SIMPLE       | t1         |
| NULL | UNION RESULT | <union1,2> |
|    2 | SIMPLE       | t2         |
+------+--------------+------------+

Here, the first SELECT has id 1. The second SELECT has id 2. The UNION RESULT row tells us that the UNION is composed of SELECTs with ids 1 and 2. The fact that the UNION RESULT row has a NULL id and appears after the first SELECT means that the second SELECT is a sibling of the first SELECT, and both are part of the UNION.

MySQL also uses the <derivedN> and <unionN,M> notations to refer to derived tables and UNIONs, respectively. These notations are important for understanding the structure of the query plan.

MySQL generates rows in the EXPLAIN output in the order that they are executed. This means that the id column is not necessarily sequential. However, the id column does indicate the nesting of subqueries. A higher id means a subquery that is nested inside a query with a lower id.

The challenge is to correctly identify the scope of each query part. We can think of the EXPLAIN output as a list of rows, and we want to build a tree from it. The root of the tree is the outermost query (usually with id=1). Child nodes are subqueries or UNIONs. Siblings are parts of the same query level.

Let's re-examine the first example, this time with the id column bracketed to show the scope:

| id   | select_type  | table      |
+------+--------------+------------+
| [1]  | UNION RESULT | <union1,4> |
|  1   | PRIMARY      | <derived2> |
| [2]  | UNION RESULT | <union2,3> |
|  2   | DERIVED      | actor_1    |
|  3   | UNION        | actor_2    |
|  4   | UNION        | <derived5> |
| [5]  | UNION RESULT | <union5,6> |
|  5   | DERIVED      | actor_3    |
|  6   | UNION        | actor_4    |

In fact, why not re-number all the ids, so the PRIMARY row becomes 2, and so on? That would make it even easier to read. Unfortunately that would also have the effect of destroying the meaning of the id column, which is important to preserve in the final tree. Also, though it makes it easier to read, it doesn't make it easier to manipulate programmatically; so it's fine to leave them numbered as they are.

The goal of re-ordering is to make it easier to figure out which rows are children of which rows in the execution plan. Given the reordered list and some row whose table is <union...> or <derived>, it is easy to find the beginning of the slice of rows that should be child nodes in the tree: you just look for the first row whose ID is the same as the first number in the table.

The next question is how to find the last row that should be a child node of a UNION or DERIVED. We'll start with DERIVED, because the solution makes UNION easy.

Consider how MySQL numbers the SELECTs sequentially according to their position in the SQL, left-to-right. Since a DERIVED table encloses everything within it in a scope, which becomes a temporary table, there are only two things to think about: its child subqueries and unions (if any), and its next siblings in the scope that encloses it. Its children will all have an id greater than it does, by definition, so any later rows with a smaller id terminate the scope.

Here's an example. The middle derived table here has a subquery and a UNION to make it a little more complex for the example.

explain select 1
from (
   select film_id from sakila.film limit 1
) as der_1
join (
   select film_id, actor_id, (select count(*) from sakila.rental) as r
   from sakila.film_actor limit 1
   union all
   select 1, 1, 1 from sakila.film_actor as dummy
) as der_2 using (film_id)
join (
   select actor_id from sakila.actor limit 1
) as der_3 using (actor_id);

Here's the output of EXPLAIN:

| id   | select_type  | table      |
|  1   | PRIMARY      | <derived2> |
|  1   | PRIMARY      | <derived6> |
|  1   | PRIMARY      | <derived3> |
|  6   | DERIVED      | actor      |
|  3   | DERIVED      | film_actor |
|  4   | SUBQUERY     | rental     |
|  5   | UNION        | dummy      |
| NULL | UNION RESULT | <union3,5> |
|  2   | DERIVED      | film       |

The siblings all have id 1, and the middle one we care about is derived3. (Notice MySQL doesn't execute them in the order they are defined, which is fine). Now notice that MySQL prints out the rows in the opposite order the subqueries were defined: 6, 3, 2. It always seems to do this, and there might be other methods of finding the scope boundaries including looking for the lower boundary of the next largest sibling, but this is a good enough heuristic. We are forced to rely on it for non-DERIVED subqueries, so we rely on it here too. Therefore, we decide that everything greater than or equal to 3 belongs to the DERIVED scope.

The rule for UNION is simple: they consume the entire enclosing scope, and to find the component parts of each one, you find each part's beginning as referred to in the <unionN,...> definition, and its end is either just before the next one, or if it's the last part, the end is the end of the scope.

This is only simple because UNION consumes the entire scope, which is either the entire statement, or the scope of a DERIVED table. This is because a UNION cannot be a sibling of another UNION or a table, DERIVED or not. (Try writing such a statement if you don't see it intuitively). Therefore, you can just find the enclosing scope's boundaries, and the rest is easy. Notice in the example above, the UNION is over <union3,5>, which includes the row with id 4 -- it includes every row between 3 and 5.

Finally, there are non-derived subqueries to deal with as well. In this case we can't look at siblings to find the end of the scope as we did for DERIVED. We have to trust that MySQL executes depth-first. Here's an example:

explain
select actor_id,
(
   select count(film_id)
   + (select count(*) from sakila.film)
   from sakila.film join sakila.film_actor using(film_id)
   where exists(
      select * from sakila.actor
      where sakila.actor.actor_id = sakila.film_actor.actor_id
   )
)
from sakila.actor;
+----+-------------+------------+
| id | select_type | table      |
+----+-------------+------------+
|  1 | PRIMARY     | actor      |
|  2 | SUBQUERY    | film       |
|  2 | SUBQUERY    | film_actor |
|  4 | DEPENDENT SUBQUERY | actor      |
|  3 | SUBQUERY    | film       |
+----+-------------+------------+

In order, the tree should be built like this:

  • See row 1.
  • See row 2. It's a higher id than 1, so it's a subquery, along with every other row whose id is greater than 2.
  • Inside this scope, see 2 and 2 and JOIN them. See 4. It's a higher id than 2, so it's again a subquery; recurse. After that, see 3, which is also higher; recurse.

But the only reason the nested subquery didn't include select 3 is because select 4 came first. In other words, if EXPLAIN looked like this,

| id | select_type        | table      |
|  1 | PRIMARY            | actor      |
|  2 | SUBQUERY           | film       |
|  2 | SUBQUERY           | film_actor |
|  3 | SUBQUERY           | film       |
|  4 | DEPENDENT SUBQUERY | actor      |

I would be forced to assume upon seeing select 3 that select 4 is a subquery of it, rather than just being the next sibling in the enclosing scope.

UNION is a little more complicated than just "the entire scope is a UNION," because the UNION might itself be inside an enclosing scope that's only indicated by the first item inside the UNION. There are only three kinds of enclosing scopes: UNION, DERIVED, and SUBQUERY. A UNION can't enclose a UNION, and a DERIVED has its own "scope markers," but a SUBQUERY in earlier versions could wholly enclose a UNION, like this strange example on the empty table t1:

explain select * from t1 where not exists(
   (select t11.i from t1 t11) union (select t12.i from t1 t12));
+----+--------------+------------+--------------------------------+
| id | select_type  | table      | Extra                          |
+----+--------------+------------+--------------------------------+
|  1 | PRIMARY      | t1         | const row not found            |
|  2 | SUBQUERY     | NULL       | No tables used                 |
|  3 | SUBQUERY     | NULL       | no matching row in const table |
|  4 | UNION        | t12        | const row not found            |
| NULL | UNION RESULT | <union2,4> |                                |
+----+--------------+------------+--------------------------------+

The UNION's backward references might make it look like the UNION encloses the subquery, but studying the query makes it clear this isn't the case. So when a UNION's first row says SUBQUERY, it is this special case that we cannot repeat starting from MySQL 5.7.

Armed with this knowledge, it's possible to use recursion to turn the parent-child relationship between all the rows into a tree representing the execution plan.

MySQL prints the rows in execution order, even the forward and backward references. At any given scope, the rows are processed as a left-deep tree. MySQL does not do "bushy" execution plans. It begins with a table, finds a matching row in the next table, and continues till the last table, when it emits a row. When it runs out, it backtracks till it can find the next row and repeats. There are subtleties of course, but this is the basic plan. This is why MySQL transforms all RIGHT OUTER JOINs into LEFT OUTER JOINs and cannot do FULL OUTER JOIN.

This means in any given scope, say

| id   | select_type  | table      |
|  1   | SIMPLE       | tbl1       |
|  1   | SIMPLE       | tbl2       |
|  1   | SIMPLE       | tbl3       |

The execution plan looks like a depth-first traversal of this tree:

      JOIN
     /    \
   JOIN  tbl3
  /    \
tbl1   tbl2

The JOIN might not be a JOIN. It might be a subquery, for example. This comes from the type column of EXPLAIN. The documentation says this is a "join type," but "access type" may be more accurate, because it's "how MySQL accesses rows."

pt-visual-explain decorates the tree significantly more than just turning rows into nodes. Each node may get a series of transformations that turn it into a subtree of more than one node. For example, an index scan not marked with 'Using index' must do a bookmark lookup into the table rows; that is a three-node subtree. However, after the above node-ordering and scoping stuff, the rest of the process is pretty simple.

ENVIRONNEMENT

La variable d'environnement "PTDEBUG" active une sortie de débogage verbeuse sur STDERR. Pour activer le débogage et capturer toute la sortie dans un fichier, exécutez l'outil comme suit :

PTDEBUG=1 pt-visual-explain ... > FICHIER 2>&1

Attention : la sortie de débogage est volumineuse et peut générer plusieurs mégaoctets de données.

ATTENTION

L'utilisation de <PTDEBUG> peut exposer les mots de passe. Lorsque le débogage est activé, tous les paramètres de la ligne de commande sont affichés dans la sortie.

Vous avez besoin de Perl, DBI, DBD::mysql, et de certains packages de base qui devraient être installés dans toute version raisonnablement récente de Perl.
