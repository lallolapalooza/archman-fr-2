NOM

provider - Fournisseurs d'implémentations d'opérations OpenSSL

SYNTAXE

#include <openssl/provider.h>

DESCRIPTION

Généralités

Cette page contient des informations utiles aux auteurs de fournisseurs.

Un fournisseur, dans le jargon OpenSSL, est une unité de code qui fournit une ou plusieurs implémentations pour diverses opérations pour différents algorithmes que l'on pourrait vouloir effectuer.

Une opération est quelque chose que l'on veut faire, comme le chiffrement et le déchiffrement, la dérivation de clé, le calcul de MAC, la signature et la vérification, etc.

Un algorithme est une méthode nommée pour effectuer une opération. Très souvent, les algorithmes sont liés aux opérations cryptographiques, mais peuvent également concerner d'autres types d'opérations, comme la gestion de certains types d'objets.

Voir crypto(7) pour plus de détails.

Fournisseur

Un fournisseur offre une fonction d'initialisation, sous la forme d'un ensemble de fonctions de base sous la forme d'un tableau OSSL_DISPATCH(3), et par extension, d'un ensemble d'OSSL_ALGORITHM(3) (voir openssl-core.h(7)). Il peut s'agir d'un module chargeable dynamiquement, ou peut être intégré, dans les bibliothèques OpenSSL ou dans l'application. S'il s'agit d'un module chargeable dynamiquement, la fonction d'initialisation doit s'appeler "OSSL_provider_init" et doit être exportée. S'il est intégré, la fonction d'initialisation peut avoir n'importe quel nom.

La fonction d'initialisation doit avoir la signature suivante :

int NOM(const OSSL_CORE_HANDLE *handle,
         const OSSL_DISPATCH *in, const OSSL_DISPATCH **out,
         void **provctx);

handle est l'objet de la bibliothèque OpenSSL pour le fournisseur, et sert de descripteur pour tout ce que les bibliothèques OpenSSL doivent savoir sur le fournisseur. Pour le fournisseur lui-même, il est passé à certaines des fonctions fournies dans le tableau de dispatch in.

in est un tableau de dispatch des fonctions de base offertes par les bibliothèques OpenSSL, et les fonctions disponibles sont décrites plus en détail dans provider-base(7).

*out doit recevoir l'affectation d'un tableau de dispatch des fonctions de base que le fournisseur offre aux bibliothèques OpenSSL. Les fonctions qui peuvent être offertes sont décrites plus en détail dans provider-base(7), et elles sont le moyen central de communication entre les bibliothèques OpenSSL et le fournisseur.

*provctx doit recevoir l'affectation d'un contexte spécifique au fournisseur pour permettre au fournisseur des utilisations simultanées multiples. Ce pointeur sera passé à diverses fonctions d'opération offertes par le fournisseur.

Notez que le fournisseur ne sera pas rendu disponible pour être utilisé par les applications tant que la fonction d'initialisation n'aura pas terminé et n'aura pas retourné succès.

L'une des fonctions que le fournisseur offre aux bibliothèques OpenSSL est le mécanisme central permettant aux bibliothèques OpenSSL d'accéder aux implémentations d'opérations pour divers algorithmes. Elle est référencée par le numéro OSSL_FUNC_PROVIDER_QUERY_OPERATION et a la signature suivante :

const OSSL_ALGORITHM *provider_query_operation(void *provctx,
                                               int operation_id,
                                               const int *no_store);

provctx est le contexte spécifique au fournisseur qui a été renvoyé par la fonction d'initialisation.

operation_id est un identifiant d'opération (voir "Opérations" ci-dessous).

no_store est un indicateur renvoyé aux bibliothèques OpenSSL qui, lorsqu'il est non nul, signifie que les bibliothèques OpenSSL ne stockeront pas de référence aux données renvoyées dans leur magasin interne d'implémentations.

Le OSSL_ALGORITHM(3) renvoyé est la base de toute API de bibliothèque OpenSSL qui utilise des fournisseurs pour leur implémentation, le plus souvent dans les fonctions de type récupération (voir "RÉCUPÉRATION D'ALGORITHME" dans crypto(7)).

Opérations

Les opérations sont référencées par des nombres, via des macros dont les noms commencent par "OSSL_OP_".

À chaque opération correspond un ensemble de types de fonctions qu'un fournisseur peut offrir ou non, en fonction de ses besoins.

Les opérations actuellement disponibles sont :

Hachages
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est EVP_MD. Le numéro de cette opération est OSSL_OP_DIGEST. Les fonctions que le fournisseur peut offrir sont décrites dans provider-digest(7).
Chiffres symétriques
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est EVP_CIPHER. Le numéro de cette opération est OSSL_OP_CIPHER. Les fonctions que le fournisseur peut offrir sont décrites dans provider-cipher(7).
Code d'authentification de message (MAC)
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est EVP_MAC. Le numéro de cette opération est OSSL_OP_MAC. Les fonctions que le fournisseur peut offrir sont décrites dans provider-mac(7).
Fonction de dérivation de clé (KDF)
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est EVP_KDF. Le numéro de cette opération est OSSL_OP_KDF. Les fonctions que le fournisseur peut offrir sont décrites dans provider-kdf(7).
Échange de clés
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est EVP_KEYEXCH. Le numéro de cette opération est OSSL_OP_KEYEXCH. Les fonctions que le fournisseur peut offrir sont décrites dans provider-keyexch(7).
Chiffres asymétriques
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est EVP_ASYM_CIPHER. Le numéro de cette opération est OSSL_OP_ASYM_CIPHER. Les fonctions que le fournisseur peut offrir sont décrites dans provider-asym_cipher(7).
Encapsulation de clé asymétrique
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est EVP_KEM. Le numéro de cette opération est OSSL_OP_KEM. Les fonctions que le fournisseur peut offrir sont décrites dans provider-kem(7).
Encodage
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est OSSL_ENCODER. Le numéro de cette opération est OSSL_OP_ENCODER. Les fonctions que le fournisseur peut offrir sont décrites dans provider-encoder(7).
Décodage
Dans les bibliothèques OpenSSL, l'objet méthode correspondant est OSSL_DECODER. Le numéro de cette opération est OSSL_OP_DECODER. Les fonctions que le fournisseur peut offrir sont décrites dans provider-decoder(7).
Génération de nombres aléatoires
Le numéro de cette opération est OSSL_OP_RAND. Les fonctions que le fournisseur peut offrir pour la génération de nombres aléatoires sont décrites dans provider-rand(7).
Gestion de clés
Le numéro de cette opération est OSSL_OP_KEYMGMT. Les fonctions que le fournisseur peut offrir pour la gestion de clés sont décrites dans provider-keymgmt(7).
Signature et vérification de signature
Le numéro de cette opération est OSSL_OP_SIGNATURE. Les fonctions que le fournisseur peut offrir pour les signatures numériques sont décrites dans provider-signature(7).

NOM

provider - Le système de fournisseurs OpenSSL

SYNOPSIS

Une description brève et générale de ce que fait le programme.

DESCRIPTION

Le système de fournisseurs OpenSSL a été introduit dans OpenSSL 3.0. Il vise à fournir un cadre pour le chargement et la gestion de diverses fonctionnalités cryptographiques dans OpenSSL.

Un fournisseur est une bibliothèque logicielle qui implémente des algorithmes cryptographiques et d'autres fonctionnalités. OpenSSL peut charger plusieurs fournisseurs, chacun fournissant potentiellement des implémentations différentes des mêmes algorithmes.

Ce comportement est contrôlé par un fichier de configuration OpenSSL (voir config(7)). Le fichier de configuration peut spécifier quels fournisseurs doivent être chargés et sous quelles conditions. Les propriétés peuvent également être utilisées pour contrôler quel fournisseur et quelle implémentation spécifique sont choisis.

Des informations plus détaillées sur les fournisseurs individuels, leurs fonctionnalités et leurs propriétés sont fournies dans les pages de manuel correspondantes.

<code>provider-storemgmt(7)</code>
La gestion des magasins de fournisseurs.

Nommage des algorithmes

Les noms d'algorithmes ne sont pas sensibles à la casse. Un algorithme particulier peut avoir plusieurs alias qui lui sont associés. Le schéma de nommage canonique d'OpenSSL suit ce format :

ALGNAME[VERSION?][-SUBNAME[VERSION?]?][-SIZE?][-MODE?]

VERSION n'est présent que s'il existe plusieurs versions d'un algorithme (par exemple, MD2, MD4, MD5). Il peut être omis s'il n'y a qu'une seule version.

SUBNAME peut être présent lorsque plusieurs algorithmes sont combinés ensemble, par exemple MD5-SHA1.

SIZE n'est présent que si plusieurs versions d'un algorithme existent avec différentes tailles (par exemple, AES-128-CBC, AES-256-CBC)

MODE n'est présent que lorsque cela est applicable.

D'autres alias peuvent exister, par exemple lorsque les organismes de normalisation ou la pratique courante utilisent des noms alternatifs ou des noms qu'OpenSSL a utilisés historiquement.

Dépendances des fournisseurs

Les fournisseurs peuvent dépendre d'autres fournisseurs pour leur bon fonctionnement (fonctionnalité implémentée dans d'autres fournisseurs). Comme il n'existe aucun mécanisme pour exprimer de telles dépendances vis-à-vis du noyau OpenSSL, les auteurs de fournisseurs doivent veiller à ce que ces dépendances soient soit complètement évitées, soit rendues visibles aux utilisateurs, par exemple par la documentation et/ou une programmation défensive, par exemple en affichant des messages d'erreur si les dépendances externes requises ne sont pas disponibles, par exemple lorsqu'aucun fournisseur implémentant la fonctionnalité requise n'a été activé. En particulier, l'initialisation des fournisseurs ne doit pas dépendre de l'initialisation préalable d'autres fournisseurs.

Remarque sur les conflits de nommage

Il est possible d'enregistrer le même nom d'algorithme depuis différents fournisseurs. Les utilisateurs doivent noter que si aucune requête de propriétés n'est spécifiée, ou si plus d'une implémentation correspond à la requête de propriétés, alors il n'est pas spécifié quelle implémentation d'un algorithme particulier sera retournée. De tels conflits de nommage peuvent également survenir si les algorithmes ne diffèrent que par la capitalisation, car le « nommage des algorithmes » n'est pas sensible à la casse.

FOURNISSEURS OPENSSL

OpenSSL fournit un certain nombre de ses propres fournisseurs. Ce sont les fournisseurs par défaut, de base, fips, legacy et null. Voir crypto(7) pour un aperçu de ces fournisseurs.
