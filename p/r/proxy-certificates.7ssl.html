NOM

proxy-certificates - Certificats proxy dans OpenSSL

DESCRIPTION

Les certificats proxy sont définis dans la RFC 3820. Ils sont utilisés pour étendre des droits à une autre entité (un processus informatique, typiquement, ou parfois à l'utilisateur lui-même). Cela permet à l'entité d'effectuer des opérations pour le compte du propriétaire du certificat d'EE (Entité Finale).

Les exigences pour un certificat proxy valide sont :

  • Ils sont émis par une Entité Finale, soit un certificat EE normal, soit un autre certificat proxy.
  • Ils ne doivent pas avoir les extensions subjectAltName ou issuerAltName.
  • Ils doivent avoir l'extension proxyCertInfo.
  • Ils doivent avoir le sujet de leur émetteur, avec un commonName ajouté.

Activer la vérification des certificats proxy

OpenSSL s'attend à ce que les applications qui souhaitent utiliser des certificats proxy en soient spécialement conscientes et le rendent explicite. Ceci est fait en définissant un indicateur de vérification X509 :

X509_STORE_CTX_set_flags(ctx, X509_V_FLAG_ALLOW_PROXY_CERTS);

ou

X509_VERIFY_PARAM_set_flags(param, X509_V_FLAG_ALLOW_PROXY_CERTS);

Voir "NOTES" pour une discussion sur cette exigence.

Créer des certificats proxy

La création de certificats proxy peut être faite en utilisant la commande openssl-x509(1), avec des extensions supplémentaires :

[ proxy ]
basicConstraints = CA:FALSE
authorityKeyIdentifier = keyid,issuer:always
proxyCertInfo = critical,language:id-ppl-anyLanguage,pathlen:1,policy:text:AB

Il est également possible de spécifier l'extension proxy dans une section séparée :

proxyCertInfo = critical,@proxy_ext
[ proxy_ext ]
language = id-ppl-anyLanguage
pathlen = 0
policy = text:BC

La valeur de la politique a une syntaxe spécifique, syntag:string, où le syntag détermine ce qui sera fait avec la chaîne. Les syntags suivants sont reconnus :

text
indique que la chaîne est une séquence d'octets, sans aucun encodage : 
policy=text:räksmörgås
hex
indique que la chaîne est une donnée binaire encodée en hexadécimal, avec des deux-points entre chaque octet (tous les deux chiffres hexadécimaux) : 
policy=hex:72:E4:6B:73:6D:F6:72:67:E5:73
file
indique que le texte de la politique doit être pris à partir d'un fichier. La chaîne est alors un nom de fichier. Ceci est utile pour les politiques qui sont plus longues que quelques lignes, comme XML ou d'autres balisages.

Notez que la valeur de la politique proxy est ce qui détermine les droits accordés au processus pendant le certificat proxy, et il appartient à l'application d'interpréter et de combiner ces politiques.

Avec une extension proxy, la création d'un certificat proxy est une affaire de deux commandes :

openssl req -new -config proxy.cnf \
    -out proxy.req -keyout proxy.key \
    -subj "/DC=org/DC=openssl/DC=users/CN=proxy"
openssl x509 -req -CAcreateserial -in proxy.req -out proxy.crt \
    -CA user.crt -CAkey user.key -days 7 \
    -extfile proxy.cnf -extensions proxy

Vous pouvez également créer un certificat proxy en utilisant un autre certificat proxy comme émetteur. Notez que cet exemple utilise une section de configuration différente pour les extensions proxy :

openssl req -new -config proxy.cnf \
    -out proxy2.req -keyout proxy2.key \
    -subj "/DC=org/DC=openssl/DC=users/CN=proxy/CN=proxy 2"
openssl x509 -req -CAcreateserial -in proxy2.req -out proxy2.crt \
    -CA proxy.crt -CAkey proxy.key -days 7 \
    -extfile proxy.cnf -extensions proxy_2

Utiliser les certificats proxy dans les applications

Pour interpréter les politiques proxy, l'application commencerait normalement avec certains droits par défaut (peut-être aucun), puis calculerait les droits résultants en vérifiant les droits par rapport à la chaîne de certificats proxy, au certificat utilisateur et aux certificats CA.

La partie compliquée est de déterminer comment passer des données entre votre application et la procédure de validation de certificat.

Les ingrédients suivants sont nécessaires pour un tel traitement :

  • une fonction de rappel qui sera appelée pour chaque certificat validé. Le rappel est appelé plusieurs fois pour chaque certificat, vous devez donc faire attention à effectuer l'interprétation de la politique proxy au bon moment. Vous devez également définir les valeurs par défaut lors de la vérification du certificat EE.
  • une structure de données partagée entre votre code applicatif et le rappel.
  • une fonction wrapper qui configure tout.
  • une fonction d'indexation ex_data qui crée un index pour le magasin ex_data générique attaché à un contexte de validation X509.

Le squelette de code suivant peut servir de point de départ :

#include <string.h>
#include <netdb.h>
#include <openssl/x509.h>
#include <openssl/x509v3.h>
#define total_rights 25
/*
 * Dans cet exemple, j'utiliserai une vue des droits accordés comme un tableau
 * de bits, un bit pour chaque droit possible.
 */
typedef struct your_rights {
    unsigned char rights[(total_rights + 7) / 8];
} YOUR_RIGHTS;
/*
 * La procédure suivante créera un index pour le magasin ex_data
 * dans le contexte de validation X509 lors de son premier appel.
 * Les appels ultérieurs retourneront le même index.
 */
static int get_proxy_auth_ex_data_idx(X509_STORE_CTX *ctx)
{
    static volatile int idx = -1;
    if (idx < 0) {
        X509_STORE_lock(X509_STORE_CTX_get0_store(ctx));
        if (idx < 0) {
            idx = X509_STORE_CTX_get_ex_new_index(0,
                                                  "for verify callback",
                                                  NULL,NULL,NULL);
        }
        X509_STORE_unlock(X509_STORE_CTX_get0_store(ctx));
    }
    return idx;
}
/* Callback à donner à la procédure de validation X509.  */
static int verify_callback(int ok, X509_STORE_CTX *ctx)
{
    if (ok == 1) {
        /*
         * Il est TRÈS important de garder la vérification de la politique proxy
         * dans cette section. Il est important de savoir que lorsque
         * ok est 1, les certificats sont vérifiés de haut en
         * bas. Vous obtenez d'abord la racine CA, suivie par la
         * chaîne possible des CA intermédiaires, suivie par le certificat EE,
         * suivie par les certificats proxy possibles.
         */
        X509 *xs = X509_STORE_CTX_get_current_cert(ctx);
        if (X509_get_extension_flags(xs) & EXFLAG_PROXY) {
            YOUR_RIGHTS *rights =
                (YOUR_RIGHTS *)X509_STORE_CTX_get_ex_data(ctx,
                    get_proxy_auth_ex_data_idx(ctx));
            PROXY_CERT_INFO_EXTENSION *pci =
                X509_get_ext_d2i(xs, NID_proxyCertInfo, NULL, NULL);
            switch (OBJ_obj2nid(pci->proxyPolicy->policyLanguage)) {
            case NID_Independent:
                /*
                 * Faites tout ce que vous avez à faire pour accorder des droits explicites
                 * à ce certificat proxy particulier, généralement
                 * en les récupérant dans une base de données. S'il n'y en a pas à trouver,
                 * effacez tous les droits (rendant ce certificat et tout certificat proxy
                 * ultérieur sans aucun droit).
                 */
                memset(rights->rights, 0, sizeof(rights->rights));
                break;
            case NID_id_ppl_inheritAll:
                /*
                 * Ceci est essentiellement un NOP, nous laissons simplement
                 * les droits actuels tels quels.
                 */
                break;
            default:
                /*
                 * C'est généralement la section de code la plus complexe.
                 * Vous faites vraiment ce que vous voulez tant que vous
                 * suivez la RFC 3820. Dans l'exemple que nous utilisons
                 * ici, la chose la plus simple à faire est de construire
                 * un autre tableau de bits temporaire et de le remplir avec
                 * les droits accordés par le certificat proxy actuel, puis de
                 * l'utiliser comme masque sur le tableau de bits accumulé, et voilà,
                 * vous avez maintenant un nouveau tableau de bits accumulé.
                 */
                {
                    int i;
                    YOUR_RIGHTS tmp_rights;
                    memset(tmp_rights.rights, 0,
                           sizeof(tmp_rights.rights));
                    /*
                     * process_rights() est censé être un
 */
                    break;
                }
            }
            PROXY_CERT_INFO_EXTENSION_free(pci);
        }
    }
    return ok;
}
/*
 * Wrapper pour configurer le contexte de validation.
 */
int setup_proxy_validation(X509_STORE *store, X509_VERIFY_PARAM *param)
{
    YOUR_RIGHTS *rights;
    int idx;
    if (!param)
        return 0;
    /*
     * Indiquer que les certificats proxy sont autorisés.
     */
    X509_VERIFY_PARAM_set_flags(param, X509_V_FLAG_ALLOW_PROXY_CERTS);
    /*
     * Créer un index pour le stockage des données supplémentaires.
     */
    idx = get_proxy_auth_ex_data_idx(NULL);
    if (idx < 0)
        return 0;
    /*
     * Créer la structure des droits initiaux. Pour cet exemple,
     * nous supposons qu'il n'y a aucun droit par défaut.
     */
    rights = OPENSSL_malloc(sizeof(YOUR_RIGHTS));
    if (!rights)
        return 0;
    memset(rights->rights, 0, sizeof(rights->rights));
    /*
     * Stocker les droits dans le contexte de validation X509.
     */
    if (!X509_VERIFY_PARAM_set_ex_data(param, idx, rights)) {
        OPENSSL_free(rights);
        return 0;
    }
    /*
     * Installer le rappel de vérification.
     */
    X509_VERIFY_PARAM_set_verify_callback(param, verify_callback);
    return 1;
}

NOTES

Une des choses étranges dans le RFC 3820 est la nécessité de l'indicateur X509_V_FLAG_ALLOW_PROXY_CERTS. Sans cela, le certificat proxy sera traité comme un certificat normal, et la vérification échouera car il ne sera pas une autorité de certification.

C'est intentionnel, et conçu pour empêcher OpenSSL de se comporter comme un serveur proxy par défaut. Les applications doivent explicitement indiquer qu'elles souhaitent prendre en charge les certificats proxy.

Le rôle de la fonction de rappel est de combiner les droits. Elle est appelée pour chaque certificat de la chaîne de confiance. Comme les certificats sont vérifiés de haut en bas, la fonction de rappel est appelée avec le certificat de niveau supérieur en premier. Les certificats proxy sont généralement situés près du bas de la chaîne, le certificat EE est le dernier avant les certificats proxy.

L'exemple de code suppose que les droits sont représentés par un tableau de bits. Les droits sont combinés en utilisant un OU bit à bit, ou un masque bit à bit, selon le type de politique.

Les valeurs de politique telles que language:id-ppl-anyLanguage, language:id-ppl-inheritAll, et language:id-ppl-independent sont définies dans la RFC 3820. L'utilisation de ces valeurs de politique est soumise à l'interprétation de l'application.

L'exemple de code fourni est une ébauche et ne doit pas être utilisé en production sans une révision et une adaptation approfondies.

SSL_CTX_set_cert_verify_callback(s_ctx, my_X509_verify_cert,
                                 &needed_rights);

NOTES

À ce jour, il semble que les certificats proxy n'aient été utilisés que dans des environnements qui les connaissent, et personne ne semble avoir étudié comment ils peuvent être utilisés ou mal utilisés en dehors d'un tel environnement.

Pour cette raison, OpenSSL exige que les applications qui connaissent les certificats proxy doivent également le rendre explicite.

subjectAltName et issuerAltName sont interdits dans les certificats proxy, et cela est appliqué dans OpenSSL. Le sujet doit être le même que l'émetteur, avec un commonName ajouté.
