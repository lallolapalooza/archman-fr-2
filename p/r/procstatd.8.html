NOM

procstatd - fournit des informations anonymes pour permettre la surveillance efficace à distance des postes de travail d'un réseau, en particulier dans le contexte d'un cluster Beowulf ou d'un sous-réseau LAN.

SYNTAXE


procstatd [-v] [-d port] [-i port]

DESCRIPTION

Le démon procstatd est conçu pour fournir des statistiques et des informations système à des hôtes ou des programmes de surveillance sur le réseau via une API simple et facilement analysable.

En mode démon ([-d port]), il écoute sur le port suggéré (qui doit être libre) et, à la demande de connexion, l'accepte et crée une copie de lui-même pour gérer la connexion. La connexion n'est authentifiée d'aucune manière, mais devrait être sûre et efficace sur un cluster protégé comme un cluster Beowulf ou un LAN protégé par un pare-feu.

En mode démon uniquement, le démon peut être appelé depuis une ligne de commande en mode verbeux ([-v]) pour obtenir des informations de débogage. -v n'a aucun effet en mode inetd.

En mode inetd ([-i port]), une entrée appropriée pour procstatd doit être ajoutée dans /etc/services sur un port ouvert, par exemple :

procstatd 7885/tcp # Connexion privée procstatd

et une ligne appropriée ajoutée à /etc/inetd.conf :

procstatd stream tcp nowait nobody /usr/sbin/tcpd /usr/local/sbin/procstatd/procstatd -i 7885

Le port 7885 utilisé dans cet exemple est le port par défaut utilisé par l'application accompagnatrice "watchman".

Dans ce mode, les wrappers TCP, avec /etc/hosts.[allow,deny], fournissent une couche de sécurité raisonnable. De plus, le démon devrait fonctionner sans problème en tant qu'utilisateur non privilégié comme guest. Enfin, le démon lui-même a été écrit avec soin pour se protéger contre les attaques de dépassement de tampon. Ce mode de fonctionnement devrait donc être acceptable sur des clusters ou des LAN ordinaires, et peut être suffisamment sûr pour permettre la surveillance à distance d'un LAN via un réseau étendu intermédiaire.

FONCTIONNEMENT ET API

Une fois la connexion établie, le démon accepte trois commandes :


init Initialise toutes les structures. DOIT être la première commande.
send Déclenche l'envoi des statistiques du nœud/des clients.
quit Termine la connexion -- l'instance du démon meurt.

Il est prévu que d'autres commandes soient éventuellement prises en charge, mais ces trois commandes resteront probablement en place.

Après réception d'une commande send, le démon renvoie un message de la forme générale suivante sur l'interface :

rgb=152.16.67.32 0.00|version=2.2.5-22 0.00|cpu 4.27|cpu_user 48.20|...

L'API est donc très simple : toute statistique ou donnée système prise en charge que procstatd peut trouver sur le système et évaluer est ajoutée à la chaîne dans un ordre déterminé par une liste énumérée dans les sources. Si ce n'est pas dans la chaîne, le système n'a pas pu la trouver ou l'évaluer. Notez que le démon peut être exécuté sur de nombreuses architectures système différentes avec des statistiques différentes sur chacune, c'est donc une caractéristique, pas un bug ! (Note : il faut collecter les noms de champs de toutes les statistiques actuellement prises en charge dans cette page de manuel -- en attendant, il est probablement plus simple de regarder la sortie ou de lire procstatd.h et les divers modules de source de statistiques, désolé.)

Chaque entrée se compose du nom de la statistique, qui peut également contenir des données traitées séparées par un "=", comme dans l'identité du système (première entrée toujours) et les champs de temps et de disponibilité. Après un espace, il y a un nombre au format %.2f qui peut être une donnée brute (charge moyenne) ou un taux ou une statistique dérivée (eth0_rx). Enfin, l'entrée est terminée par un "|".

Pour analyser cela, c'est extrêmement simple. Les champs sont séparés par des "|". Les noms de champs sont séparés des données de champs par un " ". Les données auxiliaires sont séparées d'un nom de champ par un "=". Une interface vers ce démon n'a pas besoin de savoir quels champs sont disponibles sur un hôte donné et peut être écrite facilement pour ne pas échouer si de nouveaux champs sont ajoutés ou si des champs attendus sont indisponibles. L'API est donc évolutive et extensible indépendamment des outils qui l'utilisent, et le démon ainsi que les outils devraient être facilement portables sur un large éventail de plates-formes ou de révisions de noyau.

INSTALLATION

procstatd doit être installé SOIT dans un chemin accessible par l'utilisateur (par exemple, /usr/local/bin est un bon choix) SOIT dans un chemin accessible par root dans un endroit où les démons publics sont couramment stockés (par exemple, /usr/local/sbin ou /usr/local/etc).

Dans le premier cas, procstatd peut être appelé par des utilisateurs sans privilèges spéciaux. Voir les notes sur la sécurité, la propriété et suid ci-dessous.

Dans le second cas, le démon doit être démarré au démarrage via un fragment ressemblant à :

if [ -x /usr/local/sbin/procstatd ] then


/usr/local/bin/procstatd

fi

dans rc.local ou l'équivalent sur votre système. Voir les notes sur la sécurité, la propriété et suid ci-dessous. Attention, watchman (l'interface de gestion système accompagnatrice) sera mécontent s'il ne trouve pas de procstatd à connecter et ne peut pas en redémarrer automatiquement un. C'est un logiciel alpha, donc le démon risque de planter de temps en temps !

FIABILITÉ, SÉCURITÉ ET DÉBOGAGE

Il s'agit d'une version ALPHA du démon - sa stabilité n'est pas garantie. Il a été écrit avec un soin raisonnable pour être sécurisé contre les attaques de dépassement de tampon et ne fournit que, mais sa sécurité ne peut être garantie.

Il existe plusieurs façons de le rendre suffisamment sécurisé. La première consiste à l'exécuter en mode démon (mode -d) uniquement dans un cluster Beowulf protégé ou derrière un pare-feu, car il s'agit d'un mode promiscuo principalement destiné au débogage ou (dans un cluster Beowulf) aux meilleures performances. Pour utiliser procstatd dans un LAN ou un cluster ouvert, utilisez la forme inetd, attribuez la propriété du démon à nobody (comme dans l'exemple ci-dessus) et utilisez hosts.allow pour autoriser l'accès uniquement aux hôtes autorisés à accéder au démon. Le mode multicast (lorsqu'il sera pris en charge) devrait limiter automatiquement l'accès aux informations au domaine de diffusion/multicast, mais si le multicast est initié via une commande donnée via une interface de démon (comme c'est une possibilité prévue), les mêmes principes s'appliquent.

Dans le cas où procstatd planterait sérieusement, il dispose d'un mode verbeux qui peut être exécuté s'il s'agit d'un démon (et a donc accès à stderr) pour le débogage. Pour l'activer, utilisez le drapeau -v :


procstatd -v -d port_quelconque

Connectez-vous ensuite avec telnet au port :


telnet hôte_procstatd port_quelconque

et entrez


init
send
send
...
quit

pour voir une trace de son activité. Si vous ne parvenez pas à trouver ce qui ne va pas, envoyez-moi un message et j'essaierai de vous aider. Comme le logiciel est alpha et que je présume donc que vous êtes un programmeur système, vous pourriez au moins ESSAYER de regarder le code un peu (et ajouter quelques instructions de sortie, etc.) pour voir où j'ai fait une erreur en premier, mais je suis accommodant dans tous les cas.

Des suggestions supplémentaires, en particulier celles accompagnées de code ou de correctifs, sont accueillies avec gratitude. N'hésitez pas à inclure la paternité des correctifs dans les commentaires des correctifs -- ils resteront dans le code source pour immortaliser vos contributions. Ils vous donneront également le droit de bénéficier de la clause "boisson" de la GPL modifiée, mais dans l'autre sens... je vous offrirai une bière.

FICHIERS ET VOIR AUSSI

Les binaires, scripts et le fichier de démarrage public se trouvent dans (en supposant que vous ou votre personne système les avez installés dans /usr/local, bien sûr) :


/usr/local/[bin,sbin]/procstatd

Il y a également une documentation supplémentaire dans le package source, principalement utile aux développeurs. Ce produit, il faut le souligner, est en phase ALPHA et est DESTINÉ à être modifié et amélioré à mesure qu'il progresse vers la bêta. Il y a probablement d'autres fichiers /proc à surveiller associés à des réseaux ou des modules particuliers ; il serait bien d'ajouter les décomptes d'octets réseau des 2.2.x (au lieu de seulement les taux de paquets) par exemple. Je mettrai bientôt une liste TODO dans les sources.
