NOM

procps_pids - API pour accéder aux informations des processus dans le système de fichiers /proc

SYNOPSIS

#include <libproc2/pids.h>
int procps_pids_new   (struct pids_info **info, enum pids_item *items, int numitems);
int procps_pids_ref   (struct pids_info  *info);
int procps_pids_unref (struct pids_info **info);
struct pids_stack *procps_pids_get (
    struct pids_info *info,
    enum pids_fetch_type which);
struct pids_fetch *procps_pids_reap (
    struct pids_info *info,
    enum pids_fetch_type which);
struct pids_fetch *procps_pids_select (
    struct pids_info *info,
    unsigned *these,
    int numthese,
    enum pids_select_type which);
struct pids_stack **procps_pids_sort (
    struct pids_info *info,
    struct pids_stack *stacks[],
    int numstacked,
    enum pids_item sortitem,
    enum pids_sort_order order);
int procps_pids_reset (
    struct pids_info *info,
    enum pids_item *newitems,
    int newnumitems);
struct pids_stack *fatal_proc_unmounted (
    struct pids_info *info,
    int return_self);

Lier avec -lproc2.

DESCRIPTION

Aperçu

Au centre de cette interface se trouve une structure simple de « résultat » reflétant un « élément » plus sa valeur (dans une union avec des types C standard comme membres). Toutes les structures de « résultat » sont allouées automatiquement et fournies par la bibliothèque.

En spécifiant un tableau d'« éléments », ces structures peuvent être organisées en une « pile », produisant potentiellement de nombreux résultats avec un seul appel de fonction. Ainsi, une « pile » peut être vue comme un enregistrement de longueur variable dont le contenu et l'ordre sont déterminés uniquement par l'utilisateur.

Dans le cadre de cette interface, il existe deux énumérateurs uniques. Les éléments « noop » et « extra » existent pour contenir des valeurs utilisateur. Ils ne sont jamais définis par la bibliothèque, mais le résultat « extra » sera remis à zéro à chaque interaction de la bibliothèque.

Le fichier pids.h sera un document essentiel lors du développement de programmes utilisateur. Vous y trouverez les éléments disponibles, leur type de retour (le nom du membre de la structure « result ») et la source de ces valeurs. Des énumérateurs et structures supplémentaires y sont également documentés.

Utilisation

La séquence d'appels suivante serait typique pour cette interface.

1. fatal_proc_unmounted()
2. procps_pids_new()
3. procps_pids_get(), procps_pids_reap() ou procps_pids_select()
4. procps_pids_unref()

La fonction get est un itérateur pour les PID/TID successifs, retournant les « éléments » précédemment identifiés via new ou reset.

Deux fonctions prennent en charge les résultats variables imprévisibles. La fonction reap collecte des données pour tous les processus, tandis que la fonction select traite des PID ou UID spécifiques. Les deux peuvent retourner plusieurs « piles » contenant chacune plusieurs structures de « résultat ». Optionnellement, un utilisateur peut choisir de trier ces résultats.

Pour exploiter n'importe quelle « pile », et accéder aux structures de « résultat » individuelles, un *relative_enum* est requis, comme montré dans la macro VAL définie dans le fichier d'en-tête. De telles valeurs pourraient être codées en dur comme : 0 à numitems-1. Cependant, ce besoin est généralement satisfait en créant vos propres énumérateurs correspondant à l'ordre du tableau d'« éléments ».

Mises en garde

L'API <pids> diffère des autres en ce que les éléments d'intérêt doivent être fournis au moment de new ou reset, ce dernier étant unique à cette API. Si le paramètre *items* ou *numitems* est zéro au moment de new, alors reset devient obligatoire avant d'émettre tout autre appel. Sinon, procps_pids_reset() ne doit être appelé que lorsque l'ordre ou le nombre d'éléments dans vos piles est modifié.

Pour les fonctions new et unref, l'adresse d'un pointeur de structure *info* doit être fournie. Avec new, il doit avoir été initialisé à NULL. Avec unref, il sera réinitialisé à NULL si le compteur de références atteint zéro.

Les fonctions get et reap utilisent le paramètre *which* pour spécifier si seulement les tâches ou les tâches et les threads doivent être récupérés.

La fonction select nécessite un tableau de PID ou d'UID comme *these* ainsi que *numthese* pour identifier quels processus doivent être récupérés. Cette fonction fonctionne alors comme un sous-ensemble de reap.

Lors de l'utilisation de la fonction sort, les paramètres *stacks* et *numstacked* seraient normalement ceux retournés dans la structure 'pids_fetch'.

Enfin, une fonction fatal_proc_unmounted peut être appelée avant toute autre fonction pour s'assurer que le répertoire /proc/ est monté. À ce titre, le paramètre *info* serait NULL et le paramètre *return_self* serait zéro. Si, cependant, certains éléments sont désirés pour le programme émetteur (un *return_self* autre que zéro), alors l'appel new doit le précéder pour identifier les *items* et obtenir le pointeur *info* requis.

VALEUR DE RETOUR

Fonctions retournant un « int »

Une erreur sera indiquée par un nombre négatif qui est toujours l'inverse d'une valeur bien connue de errno.h.

Le succès est indiqué par une valeur de retour zéro. Cependant, les fonctions ref et unref retournent le compteur de références de la structure *info* actuelle.

Fonctions retournant une « adresse »

Une erreur sera indiquée par un pointeur NULL avec la raison trouvée dans la valeur formelle errno.

Le succès est indiqué par un pointeur vers la structure nommée. Cependant, si l'on survit à l'appel fatal_proc_unmounted, NULL est toujours retourné lorsque *return_self* est zéro.

DÉBOGAGE

Pour aider au développement de programmes, il existe deux dispositions de procps-ng qui peuvent être exploitées.

La première est un fichier fourni nommé 'libproc.supp' qui peut être utile lors du développement d'une application *multi-threadée*. Lorsqu'il est utilisé avec l'option '--suppressions=' de valgrind, les avertissements associés à la bibliothèque procps elle-même sont évités.

Ces avertissements surviennent car la bibliothèque gère les allocations basées sur le tas de manière thread-safe. Une application *mono-threadée* ne recevra pas ces avertissements.

La seconde disposition peut aider à garantir que les références aux membres de « result » correspondent aux attentes de la bibliothèque. Elle suppose qu'une macro fournie dans le fichier d'en-tête est utilisée pour accéder à la valeur de « result ».

Cette fonctionnalité peut être activée par l'une des méthodes suivantes et toute divergence sera écrite sur stderr.

1)
Ajoutez CFLAGS='-DXTRA_PROCPS_DEBUG' à toute autre option ./configure que votre projet pourrait employer.
2)
Ajoutez #include <libproc2/xtra-procps-debug.h> à tout programme *après* le #include <libproc2/pids.h>.

Cette fonctionnalité de vérification entraîne des surcoûts substantiels. Par conséquent, il est important qu'elle ne soit *pas* activée pour une construction de production/libération.

VARIABLE(S) D'ENVIRONNEMENT

La valeur définie pour ce qui suit n'a pas d'importance, seule sa présence.

LIBPROC_HIDE_KERNEL
Ceci masquera les threads du noyau qui seraient autrement retournés avec un appel procps_pids_get, procps_pids_select ou procps_pids_reap.
