PROVE(1perl) Guide de référence du programmeur Perl PROVE(1perl)

NOM

prove - Exécute des tests via un système de gestion TAP.

UTILISATION

prove [options] [fichiers ou répertoires]

OPTIONS

Options booléennes :

-v,  --verbose         Affiche toutes les lignes de test. Définit également TEST_VERBOSE
-l,  --lib             Ajoute 'lib' au chemin d'accès pour vos tests (-Ilib).
-b,  --blib            Ajoute 'blib/lib' et 'blib/arch' au chemin d'accès pour
                       vos tests
-s,  --shuffle         Exécute les tests dans un ordre aléatoire.
-c,  --color           Sortie de test colorée (par défaut).
     --nocolor         Ne pas colorer la sortie de test.
     --count           Affiche le compte de tests X/Y lorsque ce n'est pas verbeux
                       (par défaut)
     --nocount         Désactive le compte de tests X/Y.
-D   --dry             Simulation. Affiche les tests qui auraient dû être exécutés.
-f,  --failures        Affiche les tests échoués.
-o,  --comments        Affiche les commentaires.
     --ignore-exit     Ignore le code de sortie des scripts de test.
-m,  --merge           Fusionne la sortie d'erreur standard (STDERR) des scripts de test avec leur sortie standard (STDOUT).
-r,  --recurse         Descend récursivement dans les répertoires.
     --reverse         Exécute les tests dans l'ordre inverse.
-q,  --quiet           Supprime une partie de la sortie des tests pendant leur exécution.
-Q,  --QUIET           N'affiche que les résultats résumés.
-p,  --parse           Affiche la liste complète des erreurs d'analyse TAP, le cas échéant.
     --directives      Affiche uniquement les résultats avec des directives TODO ou SKIP.
     --timer           Affiche le temps écoulé après chaque test.
     --trap            Intercepte Ctrl-C et affiche un résumé en cas d'interruption.
     --normalize       Normalise la sortie TAP en sortie verbeuse
-T                     Active les vérifications de salissure (tainting).
-t                     Active les avertissements de salissure (tainting).
-W                     Active les avertissements fatals.
-w                     Active les avertissements.
-h,  --help            Affiche cette aide
-?,                    Affiche cette aide
-V,  --version         Affiche la version
-H,  --man             Manuel plus long pour prove
     --norc            Ne pas traiter le fichier .proverc par défaut

Options qui prennent des arguments :

-I                     Chemins de bibliothèques à inclure.
-P                     Charge un plugin (recherche App::Prove::Plugin::*).
-M                     Charge un module.
-e,  --exec            Interpréteur pour exécuter les tests ('' pour les tests compilés).
     --ext             Définit l'extension pour les tests (par défaut '.t')
     --harness         Définit le système de gestion de tests à utiliser. Voir TAP::Harness.
     --formatter       Formateur de résultats à utiliser. Voir FORMATTERS.
     --source          Charge et/ou configure un gestionnaire de source. Voir GESTIONNAIRES DE SOURCE.
-a,  --archive out.tgz Stocke le TAP résultant dans un fichier archive.
-j,  --jobs N          Exécute N tâches de test en parallèle (essayez 9).
     --state=opts      Contrôle l'état persistant de prove.
     --statefile=file  Utilise `file` au lieu de `.prove` pour l'état
     --rc=rcfile       Traite les options à partir du fichier rc
     --rules           Règles pour le traitement parallèle ou séquentiel.

NOTES

.proverc

Si ~/.proverc ou ./.proverc existent, ils seront lus et toutes les options qu'ils contiennent seront traitées avant les options de la ligne de commande. Les options dans .proverc sont spécifiées de la même manière que les options de la ligne de commande :

# .proverc
--state=hot,fast,save
-j9

Des fichiers d'options supplémentaires peuvent être spécifiés avec l'option "--rc". Le traitement du fichier d'options par défaut est désactivé par l'option "--norc".

Sous Windows et VMS, le fichier d'options est nommé _proverc au lieu de .proverc et n'est recherché que dans le répertoire courant.

Lecture depuis "STDIN"

Si vous avez une liste de tests (ou d'URL, ou quoi que ce soit d'autre que vous voulez tester) dans un fichier, vous pouvez les ajouter à vos tests en utilisant un '-' :

prove - < ma_liste_de_choses_a_tester.txt

Voir le fichier "README" dans le répertoire "examples" de cette distribution.

Répertoire de tests par défaut

Si aucun fichier ou répertoire n'est fourni, "prove" recherche tous les fichiers correspondant au motif "t/*.t".

Sortie de tests colorée

La sortie de test colorée utilisant TAP::Formatter::Color est la valeur par défaut, mais si la sortie n'est pas destinée à un terminal, la couleur est désactivée. Vous pouvez outrepasser cela en ajoutant le commutateur "--color".

Le support de la couleur nécessite Term::ANSIColor et, sur les plateformes Windows, également Win32::Console::ANSI. Si le(s) module(s) nécessaire(s) ne sont pas installés, la sortie colorée ne sera pas disponible.

Code de sortie

Si les tests échouent, "prove" se terminera avec un statut non nul.

Arguments pour les tests

Il est possible de fournir des arguments aux tests. Pour ce faire, séparez-les des propres arguments de prove par le symbole deux-points, '::'. Par exemple :

prove -v t/mon_test.t :: --url http://exemple.com

exécutera t/mon_test.t avec les options '--url http://example.com'. Lors de l'exécution de plusieurs tests, chacun recevra les mêmes arguments.

"--exec"

Normalement, vous pouvez simplement passer une liste de tests Perl et le système de gestion saura comment les exécuter. Cependant, si vos tests ne sont pas écrits en Perl ou si vous voulez que tous les tests soient appelés exactement de la même manière, utilisez le commutateur "-e" ou "--exec" :

prove --exec '/usr/bin/ruby -w' t/
prove --exec '/usr/bin/perl -Tw -mstrict -Ilib' t/
prove --exec '/chemin/vers/mon/exec/client'

"--merge"

Si vous avez besoin de vous assurer que vos diagnostics sont affichés dans le bon ordre par rapport aux résultats des tests, vous pouvez utiliser l'option "--merge" pour fusionner la sortie d'erreur standard (STDERR) des scripts de test avec leur sortie standard (STDOUT).

Cela garantit que STDOUT (où apparaissent les résultats des tests) et STDERR (où apparaissent les diagnostics) resteront synchronisés. Le système de gestion affichera tous les diagnostics que vos tests émettent sur STDERR.

Attention : c'est un peu un pis-aller. Notez en particulier que si quelque chose qui apparaît sur STDERR ressemble à un résultat de test, le système de gestion de tests sera confus. Utilisez cette option uniquement si vous comprenez les conséquences et pouvez vivre avec le risque.

"--trap"

L'option "--trap" tentera d'intercepter SIGINT (Ctrl-C) pendant une exécution de test et d'afficher le résumé des tests même si l'exécution est interrompue.

"--state"

Vous pouvez demander à "prove" de se souvenir de l'état des exécutions de test précédentes et de sélectionner et/ou d'ordonner les tests à exécuter en fonction de cet état sauvegardé.

Le commutateur "--state" nécessite un argument qui doit être une liste séparée par des virgules d'une ou plusieurs des options suivantes.

"last"
Exécute les mêmes tests que la dernière fois où l'état a été sauvegardé. Cela rend possible, par exemple, de recréer l'ordre d'un test mélangé. 
# Exécute tous les tests dans un ordre aléatoire
$ prove -b --state=save --shuffle
# Exécute-les à nouveau dans le même ordre
$ prove -b --state=last
"failed"
Exécute uniquement les tests qui ont échoué lors de la dernière exécution. 
# Exécute tous les tests
$ prove -b --state=save
# Exécute les échecs
$ prove -b --state=failed

Si vous spécifiez également l'option "save", les tests nouvellement réussis seront exclus des exécutions ultérieures.

# Répéter jusqu'à ce qu'il n'y ait plus d'échecs
$ prove -b --state=failed,save
"passed"
Exécute uniquement les tests réussis de la dernière fois. Utile pour s'assurer qu'aucun nouveau problème n'a été introduit.
"all"

prove(1perl) — Arch Linux manual pages

NAME

prove - A harness for running tests.

USAGE

prove [options] [files ...]

OPTIONS

prove understands the following command-line switches.

-b
Run tests in a subdirectory. By default, prove runs tests in the current directory and all subdirectories. This flag means that prove only runs tests in subdirectories. If a specific list of files are passed to prove as arguments, then this flag has no effect.
--state
The "--state" option is used to control the order in which tests are run. The option may be specified more than once, and the order matters. The arguments to "--state" are processed as follows:
"normal"
Run all tests in normal order. Multiple options may be specified, so to run all tests with the failures from last time first: 
$ prove -b --state=failed,all,save
"hot"
Run the tests that most recently failed first. The last failure time of each test is stored. The "hot" option causes tests to be run in most-recent- failure order. 
$ prove -b --state=hot,save

Tests that have never failed will not be selected. To run all tests with the most recently failed first use

$ prove -b --state=hot,all,save

This combination of options may also be specified thus

$ prove -b --state=adrian
"todo"
Run any tests with todos.
"slow"
Run the tests in slowest to fastest order. This is useful in conjunction with the "-j" parallel testing switch to ensure that your slowest tests start running first. 
$ prove -b --state=slow -j9
"fast"
Run test tests in fastest to slowest order.
"new"
Run the tests in newest to oldest order based on the modification times of the test scripts.
"old"
Run the tests in oldest to newest order.
"fresh"
Run those test scripts that have been modified since the last test run.
"save"
Save the state on exit. The state is stored in a file called .prove (_prove on Windows and VMS) in the current directory.

The "--state" switch may be used more than once.

$ prove -b --state=hot --state=all,save

--rules

The "--rules" option is used to control which tests are run sequentially and which are run in parallel, if the "--jobs" option is specified. The option may be specified multiple times, and the order matters.

The most practical use is likely to specify that some tests are not "parallel-ready". Since mentioning a file with --rules doesn't cause it to be selected to run as a test, you can "set and forget" some rules preferences in your .proverc file. Then you'll be able to take maximum advantage of the performance benefits of parallel testing, while some exceptions are still run in parallel.

--rules examples

# All tests are allowed to run in parallel, except those starting with "p"
--rules='seq=t/p*.t' --rules='par=**'
# All tests must run in sequence except those starting with "p", which should be run parallel
--rules='par=t/p*.t'

--rules resolution

  • By default, all tests are eligible to be run in parallel. Specifying any of your own rules removes this one.
  • "First match wins". The first rule that matches a test will be the one that applies.
  • Any test which does not match a rule will be run in sequence at the end of the run.
  • The existence of a rule does not imply selecting a test. You must still specify the tests to run.
  • Specifying a rule to allow tests to run in parallel does not make them run in parallel. You still need specify the number of parallel "jobs" in your Harness object.

--rules Glob-style pattern matching

We implement our own glob-style pattern matching for --rules. Here are the supported patterns:

** is any number of characters, including /, within a pathname
* is zero or more characters within a filename/directory name
? is exactly one character within a filename/directory name
{foo,bar,baz} is any of foo, bar or baz.
\ is an escape character

More advanced specifications for parallel vs sequence run rules

If you need more advanced management of what runs in parallel vs in sequence, see the associated 'rules' documentation in TAP::Harness and TAP::Parser::Scheduler. If what's possible directly through "prove" is not sufficient, you can write your own harness to access these features directly.

@INC

prove introduces a separation between "options passed to the perl which runs prove" and "options passed to the perl which runs tests"; this distinction is by design. Thus the perl which is running a test starts with the default @INC. Additional library directories can be added via the "PERL5LIB" environment variable, via -Ifoo in "PERL5OPT" or via the "-Ilib" option to prove.

Taint Mode

Normally when a Perl program is run in taint mode the contents of the "PERL5LIB" environment variable do not appear in @INC.

Because "PERL5LIB" is often used during testing to add build directories to @INC prove passes the names of any directories found in "PERL5LIB" as -I switches. The net effect of this is that "PERL5LIB" is honoured even when prove is run in taint mode.

FORMATTERS

You can load a custom TAP::Parser::Formatter:

prove --formatter MyFormatter

SOURCE HANDLERS

You can load custom TAP::Parser::SourceHandlers, to change the way the parser interprets particular sources of TAP.

prove --source MyHandler --source YetAnother t

If you want to provide config to the source you can use:

prove --source MyCustom \
      --source Perl --perl-option 'foo=bar baz' --perl-option avg=0.278 \
      --source File --file-option extensions=.txt --file-option extensions=.tmp t
      --source pgTAP --pgtap-option pset=format=html --pgtap-option pset=border=2

Each "--$source-option" option must specify a key/value pair separated by an "=". If an option can take multiple values, just specify it multiple times, as with the "extensions=" examples above. If the option should be a hash reference, specify the value as a second pair separated by a "=", as in the "pset=" examples above (escape "=" with a backslash).

All "--sources" are combined into a hash, and passed to "new" in TAP::Harness's "sources" parameter.

See TAP::Parser::IteratorFactory for more details on how configuration is passed to SourceHandlers.

PLUGINS

Plugins can be loaded using the "-Pplugin" syntax, eg:

prove -PMyPlugin

This will search for a module named "App::Prove::Plugin::MyPlugin", or failing that, "MyPlugin". If the plugin can't be found, "prove" will complain & exit.

You can pass arguments to your plugin by appending "=arg1,arg2,etc" to the plugin name:

prove -PMyPlugin=fou,du,fafa

Please check individual plugin documentation for more details.

Available Plugins

For an up-to-date list of plugins available, please check CPAN:

https://metacpan.org/search?q=App%3A%3AProve+Plugin

Writing Plugins

Please see "PLUGINS" in App::Prove.
