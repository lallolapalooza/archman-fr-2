proc_pid_fd(5) Manuel des formats de fichiers proc_pid_fd(5)

NOM

/proc/pid/fd/ - descripteurs de fichiers

DESCRIPTION

/proc/pid/fd/
Ceci est un sous-répertoire contenant une entrée pour chaque fichier que le processus a ouvert, nommé par son descripteur de fichier, et qui est un lien symbolique vers le fichier réel. Ainsi, 0 est l'entrée standard, 1 la sortie standard, 2 l'erreur standard, et ainsi de suite.
Pour les descripteurs de fichiers de tuyaux (pipes) et de sockets, les entrées seront des liens symboliques dont le contenu est le type de fichier avec l'inode. Un appel à readlink(2) sur ce fichier retourne une chaîne au format :

type:[inode]

Par exemple, socket:[2248868] sera un socket et son inode est 2248868. Pour les sockets, cet inode peut être utilisé pour trouver plus d'informations dans un des fichiers sous /proc/net/.
Pour les descripteurs de fichiers n'ayant pas d'inode correspondant (par exemple, les descripteurs de fichiers produits par bpf(2), epoll_create(2), eventfd(2), inotify_init(2), perf_event_open(2), signalfd(2), timerfd_create(2), et userfaultfd(2)), l'entrée sera un lien symbolique dont le contenu est de la forme

anon_inode:file-type

Dans de nombreux cas (mais pas tous), le file-type est entouré de crochets.
Par exemple, un descripteur de fichier epoll aura un lien symbolique dont le contenu est la chaîne anon_inode:[eventpoll].
Dans un processus multithreadé, le contenu de ce répertoire n'est pas disponible si le thread principal est déjà terminé (typiquement en appelant pthread_exit(3)).
Les programmes qui prennent un nom de fichier comme argument de ligne de commande, mais qui ne prennent pas d'entrée depuis l'entrée standard si aucun argument n'est fourni, et les programmes qui écrivent dans un fichier nommé comme argument de ligne de commande, mais qui n'envoient pas leur sortie vers la sortie standard si aucun argument n'est fourni, peuvent néanmoins être utilisés pour utiliser l'entrée standard ou la sortie standard en utilisant les fichiers /proc/pid/fd comme arguments de ligne de commande. Par exemple, en supposant que -i est le drapeau désignant un fichier d'entrée et -o est le drapeau désignant un fichier de sortie :

$ foobar -i /proc/self/fd/0 -o /proc/self/fd/1 ...

et vous avez un filtre fonctionnel.
/proc/self/fd/N est approximativement la même chose que /dev/fd/N sur certains systèmes UNIX et UNIX-like. La plupart des scripts MAKEDEV Linux lient symboliquement /dev/fd à /proc/self/fd, en fait.
La plupart des systèmes fournissent des liens symboliques /dev/stdin, /dev/stdout, et /dev/stderr, qui lient respectivement aux fichiers 0, 1, et 2 dans /proc/self/fd. Ainsi la commande exemple ci-dessus pourrait être écrite comme :

$ foobar -i /dev/stdin -o /dev/stdout ...

La permission de déréférencer ou de lire (readlink(2)) les liens symboliques dans ce répertoire est régie par une vérification du mode d'accès ptrace PTRACE_MODE_READ_FSCREDS ; voir ptrace(2).
Notez que pour les descripteurs de fichiers se référant à des inodes (tuyaux et sockets, voir ci-dessus), ces inodes ont toujours des bits de permission et des informations de propriété distincts de ceux de l'entrée /proc/pid/fd, et que le propriétaire peut différer des IDs utilisateur et groupe du processus. Un processus non privilégié peut manquer de permissions pour les ouvrir, comme dans cet exemple :

$ echo test | sudo -u nobody cat
test
$ echo test | sudo -u nobody cat /proc/self/fd/0
cat: /proc/self/fd/0: Permission denied

Le descripteur de fichier 0 se réfère au tuyau créé par le shell et appartenant à l'utilisateur de ce shell, qui n'est pas nobody, donc cat n'a pas la permission de créer un nouveau descripteur de fichier pour lire à partir de cet inode, même s'il peut toujours lire à partir de son descripteur de fichier 0 existant.
