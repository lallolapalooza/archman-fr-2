NOM

pkcs11-provider - Un fournisseur OpenSSL qui permet une interface directe avec les pilotes pkcs11.

DESCRIPTION

À partir de la version 3.0, le projet OpenSSL a introduit un nouveau système modulaire pour étendre OpenSSL, remplaçant les modules obsolètes dits "Engines".

Les Fournisseurs (Providers, voir Providers(1)) sont chargés via des directives de configuration dans le fichier de configuration openssl (ou chargés directement par les applications).

Le fournisseur pkcs11 permet aux applications liées à openssl d'utiliser des clés et des opérations cryptographiques à partir d'un jeton matériel ou logiciel via leur pilote PKCS#11 (voir PKCS11(2)) et l'utilisation d'URIs pkcs11 (voir URIS(3)).

Le fournisseur pkcs11 peut être configuré pour être chargé automatiquement via openssl.cnf

CONFIGURATION

Options de configuration reconnues par le fournisseur.

pkcs11-module-path

Un chemin de fichier vers le pilote pkcs11 à utiliser.

Par défaut : Si compilé avec p11-kit, utilise son pilote proxy ; sinon, aucun.

NOTE : Voir aussi PKCS11_PROVIDER_MODULE dans la section des variables d'environnement.

Exemple :

pkcs11-module-path = /usr/lib64/opensc-pkcs11.so

pkcs11-module-init-args

Arguments d'initialisation non standard dont certains pilotes pkcs11 peuvent avoir besoin. Généralement non utilisé, mais certains jetons logiciels comme le softokn de NSS le nécessitent.

Par défaut : Aucun

Exemple :

pkcs11-module-init-args = configDir=/etc/pki/token

pkcs11-module-token-pin

Le PIN utilisateur à utiliser avec le jeton. Si un PIN n'est pas défini dans la configuration, il peut être demandé interactivement (si l'application utilise des inviteurs), ou il peut être spécifié directement avec les identifiants de clé dans l'URI pkcs11. Lorsqu'un fichier est spécifié, le fichier doit être un fichier texte contenant uniquement le PIN sur la première ligne et un terminateur.

Par défaut : Aucun

Exemple :

pkcs11-module-token-pin = file:/etc/pki/pin.txt

cat /etc/pki/pin.txt
123456

pkcs11-module-allow-export

Indique si le fournisseur pkcs11 permet l'exportation des clés publiques via OpenSSL. OpenSSL tente souvent d'exporter les clés publiques des fournisseurs non par défaut vers le fournisseur par défaut, puis utilise les fonctions propres d'OpenSSL pour gérer l'opération associée à la clé publique. Cette option peut être utile pour forcer l'exécution des opérations sur clé publique sur le jeton, par exemple si le pkcs11 est un accélérateur offrant de meilleures performances pour la vérification de signature ou le chiffrement asymétrique que le code d'OpenSSL.

Par défaut : 0 (Autoriser l'exportation)

Exemple :

pkcs11-module-allow-export = 1 (Ceci interdit l'exportation des clés publiques)

pkcs11-module-cache-keys

Indique si le fournisseur pkcs11 doit demander au jeton de mettre en cache les clés du jeton dans la session. Ceci est utilisé dans certains jetons comme optimisation de performance. Par exemple, les jetons logiciels qui stockent les clés chiffrées peuvent conserver une copie de la clé dans la session pour accélérer l'accès. Ou les HSM en réseau qui autorisent l'exportation du matériel de clé peuvent mettre en cache la clé dans la session au lieu de la redemander sur le réseau.

Deux options sont disponibles : * true * false

Par défaut : true (Note : si le jeton ne prend pas en charge la mise en cache de session, la mise en cache sera automatiquement désactivée après la première tentative)

Exemple :

pkcs11-module-cache-keys = false (Désactive toute tentative de mise en cache des clés dans la session)

pkcs11-module-cache-pins

Indique si le fournisseur pkcs11 doit mettre en cache un PIN saisi interactivement. Ceci est utile pour permettre le démarrage d'un service et la fourniture du PIN uniquement manuellement, tout en laissant le service effectuer plusieurs connexions si nécessaire, par exemple après un fork.

Une seule option est actuellement disponible : * cache : Met en cache le PIN

Par défaut : non défini (Pas de mise en cache)

Exemple :

pkcs11-module-cache-pins = cache (Mettra en cache un PIN qui a été saisi manuellement)

pkcs11-module-cache-sessions

Permet d'ajuster combien de sessions pkcs11 peuvent rester ouvertes et mises en cache pour une utilisation rapide. Ce paramètre est ajusté en fonction du nombre maximum de sessions que le jeton déclare comme supportées. Notez que la session de connexion est toujours mise en cache pour maintenir le jeton opérationnel.

Par défaut : 5

Exemple :

pkcs11-module-cache-sessions = 0 (Désactive la mise en cache)

pkcs11-module-login-behavior

Indique si le fournisseur pkcs11 tentera de se connecter au jeton lorsqu'une clé publique est demandée.

Trois options sont disponibles : * auto : Essaye sans se connecter, mais revient au comportement de connexion si aucune clé n'est trouvée. * always : Se connecte toujours avant d'essayer de charger les clés publiques (requis par certains HSM). * never : Ne se connecte jamais pour les clés publiques.

Par défaut : "auto"

Exemple :

pkcs11-module-login-behavior = always (Essaie toujours de se connecter avant de charger les clés publiques)

pkcs11-module-load-behavior

Indique si le fournisseur pkcs11 charge et initialise immédiatement le module pkcs11 dès qu'OpenSSL charge le fournisseur (généralement au démarrage de l'application), ou s'il diffère l'initialisation jusqu'à la première fois qu'une clé pkcs11 est chargée (ou qu'une autre opération nécessitant explicitement le fournisseur pkcs11 est demandée).

Une seule option est disponible : * early : Charge le module pkcs11 immédiatement.

Par défaut : non défini (Charge uniquement à la première utilisation)

Exemple :

pkcs11-module-load-behavior = early (Charge le module pkcs11 immédiatement au démarrage de l'application)

pkcs11-module-quirks

Solutions de contournement qui peuvent être nécessaires pour traiter certains jetons et qui ne peuvent pas encore être détectées automatiquement ou qui ne sont pas des valeurs par défaut appropriées.

no-deinit

Empêche la désinitialisation lorsque OpenSSL arrête le fournisseur. NOTE : cette option peut entraîner des fuites de mémoire et faire mal fonctionner certains modules si l'application les décharge et les recharge intentionnellement.

no-operation-state

Par défaut, OpenSSL suppose que les contextes avec des opérations en cours peuvent être facilement dupliqués. Ceci n'est possible que si les jetons prennent en charge l'obtention et la définition de l'état de l'opération. Si cette correction est activée, la duplication de contexte n'est pas effectuée.

no-session-callbacks

Certaines implémentations de PKCS11 ne permettent pas de définir les fonctions de rappel pApplication et Notify dans C_OpenSession. Cette option définit des valeurs NULL pour les deux rappels.

no-allowed-mechanisms

Certaines implémentations de PKCS11 ne prennent pas en charge l'attribut CKA_ALLOWED_MECHANISMS sur les clés. L'activation de cette correction empêche le fournisseur de tenter de définir et de lire cet attribut.

Par défaut : aucun

Exemple :

pkcs11-module-quirks = no-deinit no-operation-state (Désactive la désinitialisation, bloque la duplication de contexte)

pkcs11-module-block-operations

Permet de bloquer des « opérations de fournisseur » spécifiques, même si le jeton prend en charge les mécanismes nécessaires. Ceci est utile pour contourner les cas où l'on souhaite forcer l'utilisation du jeton pour toutes les opérations en définissant ?provider=pkcs11 dans les propriétés par défaut, mais où l'on souhaite une exception pour un type d'opération spécifique comme les digests. NOTE : certaines opérations peuvent dépendre d'autres ou être fondamentales au bon fonctionnement du fournisseur, de sorte que toutes les configurations de ce paramètre ne fonctionneront pas. À utiliser avec prudence.

Par défaut : aucun

Exemple : pkcs11-module-block-operations = digest (Désactive les mécanismes de digest, qui seront plutôt routés vers le fournisseur par défaut d'OpenSSL dans la plupart des configurations)

pkcs11-module-assume-fips

Suppose que le jeton utilisé par le module PKCS#11 est certifié FIPS.

En raison de la spécification incomplète pour la signalisation de la certification par les modules pkcs11, cela ne peut pas être déterminé automatiquement. Si vous savez que votre jeton est certifié FIPS, vous devez définir cette option de configuration à true. Sinon, le fournisseur pkcs11 ne fonctionnera pas en mode FIPS.

Par défaut : False

Exemple :

pkcs11-module-assume-fips = true

VARIABLES D'ENVIRONNEMENT

Variables d'environnement reconnues par le fournisseur

PKCS11_PROVIDER_MODULE

Cette variable peut être utilisée pour définir un pilote pkcs11 différent à utiliser. Elle est utile lorsqu'une application a besoin d'utiliser un pilote différent de celui du reste du système. Cette variable d'environnement **remplace** l'option pkcs11-module-path définie dans openssl.cnf.

Exemple :

PKCS11_PROVIDER_MODULE = /usr/lib64/opensc-pkcs11.so

PKCS11_PROVIDER_DEBUG

Cette variable peut être définie pour obtenir des informations de débogage. Deux sous-options peuvent être spécifiées : file, level.

Le niveau de débogage normal est 1, si un niveau supérieur est fourni, des informations supplémentaires (comme tous les mécanismes pris en charge pour chaque slot) sont imprimées dans le fichier de débogage spécifié. Le caractère virgule sépare les options, et le caractère deux-points est utilisé pour séparer une option et sa valeur. Il n'y a pas de caractère d'échappement, donc les caractères `,' et `:' ne peuvent pas être utilisés dans les valeurs.

Exemples :

PKCS11_PROVIDER_DEBUG=file:/tmp/debug.log

PKCS11_PROVIDER_DEBUG=file:/dev/stderr,level:2

UTILISATION DANS LES ANCIENNES APPLICATIONS (URI dans les fichiers PEM)

Il est fortement suggéré de mettre à jour les applications pour utiliser la nouvelle API OSSL_STORE fournie par OpenSSL 3.0, qui accepte les URI pour charger de manière transparente les clés à partir de fichiers ou de tout autre mécanisme pris en charge, y compris les URI PKCS#11.

Cependant, pour les applications qui ne peuvent pas encore être modifiées, il existe un outil pour générer un fichier PEM « wrapper » qui contient l'URI PKCS#11 nécessaire pour identifier une clé sur un jeton.

Ce fichier PEM peut être chargé via les méthodes classiques utilisées pour analyser les représentations PEM/DER des clés et déclenchera l'utilisation des décodeurs du fournisseur pkcs11 lorsque le fournisseur sera chargé. Une erreur sera renvoyée si le fournisseur n'est pas pré-chargé ou si une version plus ancienne d'OpenSSL est utilisée.

Dans tools/uri2pem.py, il existe un script python d'exemple qui peut prendre un URI de clé et produire un fichier PEM qui y fait référence. Notez que le stockage des PIN dans ces fichiers PEM n'est pas sécurisé. Ces fichiers ne sont pas chiffrés.

La commande suivante peut être utilisée pour lister toutes les clés d'un jeton et afficher leur URI d'identification :

openssl storeutl -keys -text pkcs11:

EXEMPLES

openssl.cnf :

HOME = .
# Utiliser ceci afin de charger automatiquement les fournisseurs.
openssl_conf = openssl_init
[openssl_init]
providers = provider_sect
[provider_sect]
default = default_sect
pkcs11 = pkcs11_sect
[default_sect]
activate = 1
[pkcs11_sect]
module = /usr/lib64/ossl-modules/pkcs11.so
pkcs11-module-path = /usr/lib64/pkcs11/vendor_pkcs11.so
pkcs11-module-token-pin = /etc/ssl/pinfile.txt
activate = 1
