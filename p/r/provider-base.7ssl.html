DESCRIPTION

Toutes les "fonctions" mentionnées ici sont passées sous forme de pointeurs de fonction entre libcrypto et le fournisseur dans des tableaux OSSL_DISPATCH(3), lors de l'appel de la fonction d'initialisation du fournisseur. Voir "Fournisseur" dans provider(7) pour une description de la fonction d'initialisation. Elles sont connues sous le nom de "appels sortants".

Toutes ces "fonctions" ont une définition de type de fonction correspondante nommée OSSL_FUNC_{name}_fn, et une fonction d'aide pour récupérer le pointeur de fonction à partir d'un élément OSSL_DISPATCH(3) nommé OSSL_FUNC_{name}. Par exemple, la "fonction" core_gettable_params() a les éléments suivants :

typedef OSSL_PARAM *
    (OSSL_FUNC_core_gettable_params_fn)(const OSSL_CORE_HANDLE *handle);
static ossl_inline OSSL_NAME_core_gettable_params_fn
    OSSL_FUNC_core_gettable_params(const OSSL_DISPATCH *opf);

Fonctions principales

core_gettable_params() renvoie un tableau constant de descripteurs OSSL_PARAM(3), pour les paramètres que core_get_params() peut gérer.

core_get_params() récupère les paramètres du noyau pour le handle donné. Voir « Paramètres du noyau » ci-dessous pour une description des paramètres actuellement connus.

La fonction core_thread_start() informe le noyau que le fournisseur s'est intéressé au thread actuel. Le noyau informera le fournisseur lorsque le thread s'arrêtera finalement. Elle doit recevoir le handle pour ce fournisseur, ainsi qu'un rappel handfn qui sera appelé lorsque le thread s'arrêtera. Le rappel sera ensuite appelé, avec l'argument fourni arg, à partir du thread qui s'arrête et recevra le contexte du fournisseur comme argument. Ceci peut être utile pour effectuer un nettoyage spécifique au thread, tel que la libération de variables locales au thread.

core_get_libctx() récupère le contexte du noyau dans lequel l'objet bibliothèque pour le fournisseur actuel est stocké, accessible via le handle. Cette fonction est utile uniquement pour les fournisseurs intégrés tels que le fournisseur par défaut. Ne jamais caster cela en OSSL_LIB_CTX dans un fournisseur qui n'est pas intégré, car l'OSSL_LIB_CTX de la bibliothèque qui charge le fournisseur pourrait être une structure complètement différente de l'OSSL_LIB_CTX de la bibliothèque à laquelle le fournisseur est lié. Utiliser OSSL_LIB_CTX_new_child(3) à la place pour obtenir un contexte bibliothèque approprié qui est lié au contexte bibliothèque de l'application.

core_new_error(), core_set_error_debug() et core_vset_error() sont des blocs de construction pour signaler une erreur au noyau, avec référence au handle.

core_new_error()
alloue un nouvel enregistrement d'erreur spécifique au thread.

Ceci correspond à la fonction OpenSSL ERR_new(3).

core_set_error_debug()
définit des informations de débogage dans l'enregistrement d'erreur actuel spécifique au thread. Les informations de débogage incluent le nom du fichier file, le numéro de ligne line et le nom de la fonction func où l'erreur s'est produite.

Ceci correspond à la fonction OpenSSL ERR_set_debug(3).

core_vset_error()
définit la raison de l'erreur, avec toute donnée supplémentaire. La raison est un nombre défini par le fournisseur et utilisé pour indexer la table des chaînes de raisons renvoyée par provider_get_reason_strings(). Les données supplémentaires sont fournies sous forme de chaîne de format fmt et d'un ensemble d'arguments args, qui sont traités de la même manière qu'avec BIO_vsnprintf(). file et line peuvent également être transmis pour indiquer exactement où l'erreur s'est produite ou a été signalée.

Ceci correspond à la fonction OpenSSL ERR_vset_error(3).

core_set_error_mark()
définit une marque sur l'enregistrement d'erreur supérieur actuel s'il y en a un.

Ceci correspond à la fonction OpenSSL ERR_set_mark(3).

core_clear_last_error_mark()
supprime la dernière marque ajoutée s'il y en a une.

Ceci correspond à la fonction OpenSSL ERR_clear_last_mark(3).

core_pop_error_to_mark()
dépile les entrées de la pile d'erreurs jusqu'à ce qu'une marque soit trouvée. La marque est ensuite supprimée. S'il n'y a pas de marque, toute la pile est vidée.

Ceci correspond à la fonction OpenSSL ERR_pop_to_mark(3).

core_count_to_mark()
renvoie le nombre d'entrées sur la pile d'erreurs au-dessus de l'entrée marquée la plus récente, sans inclure cette entrée. S'il n'y a pas de marque dans la pile d'erreurs, le nombre d'entrées dans la pile d'erreurs est renvoyé.

Ceci correspond à la fonction OpenSSL ERR_count_to_mark(3).

La fonction core_obj_create() enregistre un nouvel OID et son nom court sn et nom long ln associés pour le handle donné. Elle est similaire à la fonction OpenSSL OBJ_create(3), sauf qu'elle renvoie 1 en cas de succès ou 0 en cas d'échec. Elle traitera comme succès le cas où l'OID existe déjà (même si le nom court sn ou le nom long ln fournis comme arguments diffèrent de ceux associés à l'OID existant, auquel cas les nouveaux noms ne sont pas associés).

La fonction core_obj_add_sigid() enregistre un nouvel algorithme de signature composite (sign_name) constitué d'un algorithme de signature sous-jacent (pkey_name) et d'un algorithme de digest (digest_name) pour le handle donné. Elle suppose que les OID pour l'algorithme de signature composite ainsi que pour les algorithmes de signature et de digest sous-jacents sont soit déjà connus d'OpenSSL, soit ont été enregistrés via un appel à core_obj_create(). Elle correspond à la fonction OpenSSL OBJ_add_sigid(3), sauf que les objets sont identifiés par nom plutôt que par un NID numérique. N'importe quel nom (OID, nom court ou nom long) peut être utilisé pour identifier l'objet. Elle traitera comme succès le cas où l'algorithme de signature composite existe déjà (même s'il est enregistré contre un algorithme de signature ou de digest sous-jacent différent). Pour digest_name, NULL ou une chaîne vide est permissible pour les algorithmes de signature qui n'ont pas besoin de digest pour fonctionner correctement. La fonction renvoie 1 en cas de succès ou 0 en cas d'échec.

CRYPTO_malloc(), CRYPTO_zalloc(), CRYPTO_free(), CRYPTO_clear_free(), CRYPTO_realloc(), CRYPTO_clear_realloc(), CRYPTO_secure_malloc(), CRYPTO_secure_zalloc(), CRYPTO_secure_free(), CRYPTO_secure_clear_free(), CRYPTO_secure_allocated(), BIO_new_file(), BIO_new_mem_buf(), BIO_read_ex(), BIO_write_ex(), BIO_up_ref(), BIO_free(), BIO_vprintf(), BIO_vsnprintf(), BIO_gets(), BIO_puts(), BIO_ctrl(), OPENSSL_cleanse() et OPENSSL_hexstr2buf() correspondent exactement aux fonctions publiques du même nom. En fait, les pointeurs dans le tableau OSSL_DISPATCH(3) sont généralement des pointeurs directs vers ces fonctions publiques. Notez que les fonctions BIO prennent un type OSSL_CORE_BIO plutôt que le type BIO standard. Ceci afin de s'assurer qu'un fournisseur ne mélange pas les BIO du noyau avec les BIO utilisés côté fournisseur (les deux ne sont pas compatibles). OSSL_SELF_TEST_set_callback() est utilisé pour définir un rappel optionnel qui peut être passé à un fournisseur. Ceci peut être ignoré par un fournisseur.

get_entropy() récupère du matériel d'amorçage auprès du système d'exploitation. Le matériel d'amorçage aura au moins entropy octets d'aléatoire et la sortie aura au moins min_len et au plus max_len octets. L'adresse du tampon est stockée dans *pout et la longueur du tampon est renvoyée à l'appelant. En cas d'erreur, zéro est renvoyé.

get_user_entropy() est identique à get_entropy() sauf qu'il tentera de collecter du matériel d'amorçage via la source d'amorçage spécifiée par un appel à RAND_set_seed_source_type(3) ou via la « Configuration aléatoire » dans config(5).

cleanup_entropy() est utilisé pour nettoyer et libérer le tampon renvoyé par get_entropy(). Le pointeur d'entropie renvoyé par get_entropy() est passé dans buf et sa longueur dans len.

cleanup_user_entropy() est utilisé pour nettoyer et libérer le tampon renvoyé par get_user_entropy(). Le pointeur d'entropie renvoyé par get_user_entropy() est passé dans buf et sa longueur dans len.

get_nonce() récupère un nonce en utilisant le paramètre salt fourni de longueur salt_len et des informations spécifiques au système d'exploitation. Le salt doit contenir des informations d'identification uniques et celles-ci sont incluses, d'une manière non spécifiée, dans la sortie. La sortie est stockée dans un tampon qui contient au moins min_len et au plus max_len octets. L'adresse du tampon est stockée dans *pout et la longueur du tampon est renvoyée à l'appelant. En cas d'erreur, zéro est renvoyé.

get_user_nonce() est identique à get_nonce() sauf qu'il tentera de collecter du matériel d'amorçage via la source d'amorçage spécifiée par un appel à RAND_set_seed_source_type(3) ou via la « Configuration aléatoire » dans config(5).

cleanup_nonce() est utilisé pour nettoyer et libérer le tampon renvoyé par get_nonce(). Le pointeur de nonce renvoyé par get_nonce() est passé dans buf et sa longueur dans len.

cleanup_user_nonce() est utilisé pour nettoyer et libérer le bu

ffer retourné par get_user_nonce(). Le pointeur nonce retourné par get_user_nonce() est passé dans buf et sa longueur dans len.

provider_register_child_cb() enregistre des callbacks pour être informé du chargement et du déchargement des fournisseurs dans le contexte de la bibliothèque de l'application. handle est le handle de ce fournisseur et cbdata sont les données de ce fournisseur qui seront renvoyées aux callbacks. Il retourne 1 en cas de succès ou 0 sinon. Ces callbacks peuvent être appelés tout en détenant des verrous dans libcrypto. Afin d'éviter les interblocages, l'implémentation des callbacks ne doit pas être longue et ne doit pas appeler d'autres fonctions API OpenSSL ou d'appels ascendants.

create_cb est un callback qui sera appelé lorsqu'un nouveau fournisseur est chargé dans le contexte de la bibliothèque de l'application. Il est également appelé pour tous les fournisseurs déjà chargés au moment de l'enregistrement de ce callback. Le callback reçoit le handle utilisé pour le nouveau fournisseur chargé et les données de ce fournisseur dans cbdata. Il doit retourner 1 en cas de succès ou 0 en cas d'échec.

remove_cb est un callback qui sera appelé lorsqu'un nouveau fournisseur est déchargé du contexte de la bibliothèque de l'application. Il reçoit le handle utilisé pour le fournisseur déchargé et les données de ce fournisseur dans cbdata. Il doit retourner 1 en cas de succès ou 0 en cas d'échec.

global_props_cb est un callback qui sera appelé lorsque les propriétés globales du contexte de la bibliothèque parente sont modifiées. Il doit retourner 1 en cas de succès ou 0 en cas d'échec.

provider_deregister_child_cb() désenregistre les callbacks précédemment enregistrés via provider_register_child_cb(). Si provider_register_child_cb() a été appelé, alors provider_deregister_child_cb() doit être appelé au moment ou avant le point où la fonction de nettoyage de ce fournisseur est appelée.

provider_name() retourne une chaîne de caractères donnant le nom du fournisseur identifié par handle.

provider_get0_provider_ctx() retourne le contexte du fournisseur associé au fournisseur identifié par prov.

provider_get0_dispatch() récupère la table de distribution enregistrée par le fournisseur identifié par prov lors de son initialisation.

provider_up_ref() incrémente le compteur de références sur le fournisseur prov. Si activate est non nul, le fournisseur est également chargé s'il n'est pas déjà chargé. Il retourne 1 en cas de succès ou 0 en cas d'échec.

provider_free() décrémente le compteur de références sur le fournisseur prov. Si deactivate est non nul, le fournisseur est également déchargé s'il n'est pas déjà déchargé. Il retourne 1 en cas de succès ou 0 en cas d'échec.

Fonctions de fournisseur

provider_teardown() est appelé lorsqu'un fournisseur est arrêté et retiré du magasin de fournisseurs du noyau. Il doit libérer le provctx passé.

provider_gettable_params() doit retourner un tableau constant de descripteurs OSSL_PARAM(3), pour les paramètres que provider_get_params() peut gérer.

provider_get_params() doit traiter le tableau OSSL_PARAM(3) params, en définissant les valeurs des paramètres qu'il comprend.

provider_query_operation() doit retourner un OSSL_ALGORITHM(3) constant correspondant à l'`operation_id` donnée. Il doit indiquer si le noyau peut stocker une référence à ce tableau en mettant *no_store à 0 (le noyau peut stocker une référence) ou 1 (le noyau ne peut pas stocker de référence).

provider_unquery_operation() informe le fournisseur que le résultat d'un appel à provider_query_operation() n'est plus directement requis et que les pointeurs de fonction ont été copiés. L'`operation_id` doit correspondre à celui passé à provider_query_operation() et algs doit être sa valeur de retour.

provider_get_reason_strings() doit retourner un tableau constant OSSL_ITEM(3) fournissant des chaînes de raison pour les codes de raison que le fournisseur peut utiliser lors de la signalisation d'erreurs en utilisant core_put_error().

La fonction provider_get_capabilities() doit appeler le callback cb en lui passant un ensemble de OSSL_PARAM(3) et l'argument arg fourni par l'appelant. Les OSSL_PARAM(3) devraient fournir des détails sur la capacité dont le nom est donné dans l'argument capability, pertinent pour le contexte du fournisseur provctx. Si un fournisseur prend en charge plusieurs capacités portant le même nom, il peut appeler le callback plusieurs fois (une fois pour chaque capacité). Les capacités peuvent être utiles pour décrire les services qu'un fournisseur peut offrir. Pour plus de détails, voir la section "CAPABILITIES" ci-dessous. Elle doit retourner 1 en cas de succès ou 0 en cas d'erreur.

La fonction provider_self_test() doit effectuer des tests de réponse connue sur un sous-ensemble des algorithmes qu'elle utilise, et peut également vérifier l'intégrité du module fournisseur. Elle doit retourner 1 en cas de succès ou 0 en cas d'erreur. Elle retournera 1 si cette fonction n'est pas utilisée.

Aucune de ces fonctions n'est obligatoire, mais un fournisseur est assez inutile sans au moins provider_query_operation(), et provider_gettable_params() est assez inutile si elle n'est pas accompagnée de provider_get_params().

Paramètres fournisseur

provider_get_params() peut retourner les paramètres de fournisseur suivants au noyau :

"name" (OSSL_PROV_PARAM_NAME) <pointeur UTF8>
Ceci pointe vers une chaîne qui doit donner un nom unique pour le fournisseur.
"version" (OSSL_PROV_PARAM_VERSION) <pointeur UTF8>
Ceci pointe vers une chaîne qui est un numéro de version associé à ce fournisseur. Les fournisseurs intégrés à OpenSSL utilisent OPENSSL_VERSION_STR, mais cela peut être différent pour tout fournisseur tiers. Cette chaîne est à titre informatif uniquement.
"buildinfo" (OSSL_PROV_PARAM_BUILDINFO) <pointeur UTF8>
Ceci pointe vers une chaîne qui est une information de construction associée à ce fournisseur. Les fournisseurs intégrés à OpenSSL utilisent OPENSSL_FULL_VERSION_STR, mais cela peut être différent pour tout fournisseur tiers.
"status" (OSSL_PROV_PARAM_STATUS) <entier signé>
Retourne 0 si le fournisseur est entré dans un état d'erreur, sinon il retourne 1.

provider_gettable_params() doit retourner les paramètres ci-dessus.

Paramètres noyau

core_get_params() peut récupérer les paramètres du noyau suivants pour chaque fournisseur :

"openssl-version" (OSSL_PROV_PARAM_CORE_VERSION) <pointeur chaîne UTF8>
Ceci pointe vers la chaîne de version complète des bibliothèques OpenSSL, c'est-à-dire la chaîne développée à partir de la macro OPENSSL_VERSION_STR.
"provider-name" (OSSL_PROV_PARAM_CORE_PROV_NAME) <pointeur chaîne UTF8>
Ceci pointe vers l'idée que les bibliothèques OpenSSL se font du nom du fournisseur appelant.
"module-filename" (OSSL_PROV_PARAM_CORE_MODULE_FILENAME) <pointeur chaîne UTF8>
Ceci pointe vers une chaîne contenant le nom de fichier complet du module fournisseur.

De plus, des paramètres de configuration spécifiques au fournisseur provenant du fichier de configuration sont disponibles, sous forme de nom en points. La forme de nom en points est une concaténation de noms de sections et du nom final de commande de configuration séparés par des points.

Par exemple, supposons l'exemple de configuration suivant :

config_diagnostics = 1
openssl_conf = openssl_init
[openssl_init]
providers = providers_sect
[providers_sect]
foo = foo_sect
[foo_sect]
activate = 1
data1 = 2
data2 = str
more = foo_more
[foo_more]
data3 = foo,bar

Le fournisseur aura les paramètres supplémentaires suivants disponibles :

"activate"
pointant vers la chaîne "1"
"data1"
pointant vers la chaîne "2"
"data2"
pointant vers la chaîne "str"
"more.data3"
pointant vers la chaîne "foo,bar"

Pour plus d'informations sur la gestion des paramètres, voir OSSL_PARAM(3) comme OSSL_PARAM_int(3).

CAPACITÉS

Les capacités décrivent certains des services qu'un fournisseur peut offrir. Les applications peuvent interroger les capacités pour découvrir ces services.

Capacité "TLS-GROUP"

La capacité "TLS-GROUP" peut être interrogée par libssl pour découvrir la liste des groupes TLS que peut prendre en charge un fournisseur. Chaque groupe pris en charge peut être utilisé pour l'échange de clés (KEX) ou la méthode d'encapsulation de clés (KEM) lors d'une négociation TLS. Les clients TLS peuvent annoncer la liste des groupes TLS qu'ils prennent en charge dans l'extension supported_groups, et les serveurs TLS peuvent sélectionner un groupe dans la liste proposée qu'ils prennent également en charge. De cette manière, un fournisseur peut ajouter à la liste des groupes que libssl prend déjà en charge des groupes supplémentaires.

Chaque groupe TLS pris en charge par un fournisseur doit être décrit via le callback passé par la fonction provider_get_capabilities. Chaque groupe doit avoir les détails suivants (tous sont obligatoires, sauf OSSL_CAPABILITY_TLS_GROUP_IS_KEM) :

"tls-group-name" (OSSL_CAPABILITY_TLS_GROUP_NAME) <chaîne UTF8>
Le nom du groupe tel qu'indiqué dans le registre IANA des groupes pris en charge par TLS https://www.iana.org/assignments/tls-parameters/tls-parameters.xhtml#tls-parameters-8.
"tls-group-name-internal" (OSSL_CAPABILITY_TLS_GROUP_NAME_INTERNAL) <chaîne UTF8>
Le nom du groupe tel que connu par le fournisseur. Cela peut être le même que "tls-group-name", mais ce n'est pas obligatoire.
"tls-group-id" (OSSL_CAPABILITY_TLS_GROUP_ID) <entier non signé>
La valeur de l'identifiant du groupe TLS telle qu'indiquée dans le registre IANA des groupes pris en charge par TLS.

Il est possible d'enregistrer le même identifiant de groupe à partir de différents fournisseurs. Les utilisateurs doivent noter que si aucune requête de propriété n'est spécifiée, ou si plus d'une implémentation correspond à la requête de propriété, alors il n'est pas spécifié quelle implémentation pour un identifiant de groupe particulier sera utilisée.

"tls-group-alg" (OSSL_CAPABILITY_TLS_GROUP_ALG) <chaîne UTF8>
Le nom d'un algorithme de gestion de clés qui
t le fournisseur propose et qui doivent être utilisés avec ce groupe. Les clés créées doivent pouvoir prendre en charge la négociation de clés ou la méthode d'encapsulation de clés (KEM), comme le suggère l'indicateur facultatif OSSL_CAPABILITY_TLS_GROUP_IS_KEM. L'algorithme doit prendre en charge la génération de clés et de paramètres, ainsi que le paramètre de génération de clés/paramètres, OSSL_PKEY_PARAM_GROUP_NAME. Le nom du groupe donné via "tls-group-name-internal" ci-dessus sera passé via OSSL_PKEY_PARAM_GROUP_NAME lorsque libssl souhaitera générer des clés/paramètres.
"tls-group-sec-bits" (OSSL_CAPABILITY_TLS_GROUP_SECURITY_BITS) <entier non signé>
Le nombre de bits de sécurité offerts par les clés de ce groupe. Le nombre de bits doit être comparable à ceux donnés dans les tableaux 2 et 3 du document NIST SP800-57.
"tls-group-is-kem" (OSSL_CAPABILITY_TLS_GROUP_IS_KEM) <entier non signé>
Indicateur booléen pour décrire si le groupe doit être utilisé en mode négociation de clés (KEX) (0, par défaut) ou en mode méthode d'encapsulation de clés (KEM) (1).

Ce paramètre est facultatif : s'il n'est pas spécifié, le mode KEX est supposé comme mode par défaut pour le groupe.

En mode KEX, de manière typique à la Diffie-Hellman, les deux parties exécutent keygen puis derive par rapport à la clé publique du pair. Pour fonctionner en mode KEX, l'implémentation du groupe doit prendre en charge les fonctions du fournisseur telles que décrites dans provider-keyexch(7).

En mode KEM, le client exécute keygen et envoie sa clé publique, le serveur exécute encapsulate en utilisant la clé publique du client et renvoie le chiffrement résultant, enfin le client exécute decapsulate pour récupérer le même secret partagé généré par l'*encapsulate* du serveur. Pour fonctionner en mode KEM, l'implémentation du groupe doit prendre en charge les fonctions du fournisseur telles que décrites dans provider-kem(7).

En mode KEX comme en mode KEM, le secret partagé résultant est ensuite utilisé conformément à la spécification du protocole.

"tls-min-tls" (OSSL_CAPABILITY_TLS_GROUP_MIN_TLS) <entier>
"tls-max-tls" (OSSL_CAPABILITY_TLS_GROUP_MAX_TLS) <entier>
"tls-min-dtls" (OSSL_CAPABILITY_TLS_GROUP_MIN_DTLS) <entier>
"tls-max-dtls" (OSSL_CAPABILITY_TLS_GROUP_MAX_DTLS) <entier>
Ces paramètres peuvent être utilisés pour décrire les versions minimale et maximale de TLS et DTLS prises en charge par le groupe. Les valeurs correspondent à l'encodage sur le réseau des différentes versions TLS. Par exemple, TLSv1.3 est 0x0304 (772 décimal), et TLSv1.2 est 0x0303 (771 décimal). Un 0 indique qu'il n'y a pas de minimum ou de maximum défini. Un -1 indique que le groupe ne doit pas être utilisé dans ce protocole.

Capacité "TLS-SIGALG"

La capacité "TLS-SIGALG" peut être interrogée par libssl pour découvrir la liste des algorithmes de signature TLS qu'un fournisseur peut prendre en charge. Chaque signature prise en charge peut être utilisée pour l'authentification client ou serveur en plus des algorithmes de signature intégrés. Les clients TLS1.3 peuvent annoncer la liste des algorithmes de signature TLS qu'ils prennent en charge dans l'extension signature_algorithms, et les serveurs TLS peuvent sélectionner un algorithme dans la liste proposée qu'ils prennent également en charge. De cette manière, un fournisseur peut ajouter à la liste des algorithmes de signature que libssl prend déjà en charge avec d'autres.

Chaque algorithme de signature TLS pris en charge par un fournisseur doit être décrit via la fonction de rappel passée par la fonction provider_get_capabilities. Chaque algorithme peut avoir les détails suivants fournis :

"iana-name" (OSSL_CAPABILITY_TLS_SIGALG_IANA_NAME) <chaîne UTF8>
Le nom de l'algorithme de signature tel que donné dans le registre IANA des schémas de signature TLS sous "Description" : https://www.iana.org/assignments/tls-parameters/tls-parameters.xhtml#tls-signaturescheme. Cette valeur doit être fournie.
"iana-code-point" (OSSL_CAPABILITY_TLS_SIGALG_CODE_POINT) <entier non signé>
La valeur de l'ID d'algorithme TLS telle que donnée dans le registre IANA des schémas de signature TLS. Cette valeur doit être fournie.

Il est possible d'enregistrer le même point de code à partir de différents fournisseurs. Les utilisateurs doivent noter que si aucune requête de propriété n'est spécifiée, ou si plus d'une implémentation correspond à la requête de propriété, il est indéterminé quelle implémentation pour un point de code particulier sera utilisée.

"sigalg-name" (OSSL_CAPABILITY_TLS_SIGALG_NAME) <chaîne UTF8>
Un nom pour l'algorithme de signature complet (éventuellement composite de hachage et de signature). Le fournisseur peut, mais n'est pas obligé, de fournir une implémentation de signature portant ce nom ; s'il ne le fait pas, cela est supposé être un composite d'un algorithme de signature pur et d'un algorithme de hachage, qui doivent être donnés avec les paramètres "sig-name" et "hash-name". Cette valeur doit être fournie.
"sigalg-oid" (OSSL_CAPABILITY_TLS_SIGALG_OID) <chaîne UTF8>
L'OID de l'algorithme "sigalg-name" sous forme de texte numérique canonique. Si ce paramètre est donné, OBJ_create() sera utilisé pour créer un OBJ et un NID pour cet OID, en utilisant le paramètre "sigalg-name" pour son nom (court). Sinon, il est supposé exister déjà dans la base de données d'objets, possiblement fait par le fournisseur avec l'appel de rappel core_obj_create(). Cette valeur est facultative.
"sig-name" (OSSL_CAPABILITY_TLS_SIGALG_SIG_NAME) <chaîne UTF8>
Le nom de l'algorithme de signature pure qui fait partie d'un "sigalg-name" composite. Si "sigalg-name" est implémenté par le fournisseur, ce paramètre est redondant et ne doit pas être donné. Cette valeur est facultative.
"sig-oid" (OSSL_CAPABILITY_TLS_SIGALG_SIG_OID) <chaîne UTF8>
L'OID de l'algorithme "sig-name" sous forme de texte numérique canonique. Si ce paramètre est donné, OBJ_create() sera utilisé pour créer un OBJ et un NID pour cet OID, en utilisant le paramètre "sig-name" pour son nom (court). Sinon, il est supposé exister déjà dans la base de données d'objets. Cela peut être fait par le fournisseur en utilisant l'appel de rappel core_obj_create(). Cette valeur est facultative.
"hash-name" (OSSL_CAPABILITY_TLS_SIGALG_HASH_NAME) <chaîne UTF8>
Le nom de l'algorithme de hachage qui fait partie d'un "sigalg-name" composite. Si "sigalg-name" est implémenté par le fournisseur, ce paramètre est redondant et ne doit pas être donné. Cette valeur est facultative.
"hash-oid" (OSSL_CAPABILITY_TLS_SIGALG_HASH_OID) <chaîne UTF8>
L'OID de l'algorithme "hash-name" sous forme de texte numérique canonique. Si ce paramètre est donné, OBJ_create() sera utilisé pour créer un OBJ et un NID pour cet OID, en utilisant le paramètre "hash-name" pour son nom (court). Sinon, il est supposé exister déjà dans la base de données d'objets, possiblement fait par le fournisseur avec l'appel de rappel core_obj_create(). Cette valeur est facultative.
"key-type" (OSSL_CAPABILITY_TLS_SIGALG_KEYTYPE) <chaîne UTF8>
Le type de clé de la clé publique des certificats applicables. Si ce paramètre n'est pas présent, il est supposé être le même que "sig-name" s'il est présent, sinon "sigalg-name". Cette valeur est facultative.
"key-type-oid" (OSSL_CAPABILITY_TLS_SIGALG_KEYTYPE_OID) <chaîne UTF8>
L'OID de "key-type" sous forme de texte numérique canonique. Si ce paramètre est donné, OBJ_create() sera utilisé pour créer un OBJ et un NID pour cet OID, en utilisant le paramètre "key-type" pour son nom (court). Sinon, il est supposé exister déjà dans la base de données d'objets, possiblement fait par le fournisseur avec l'appel de rappel core_obj_create(). Cette valeur est facultative.
"sec-bits" (OSSL_CAPABILITY_TLS_SIGALG_SECURITY_BITS) <entier non signé>
Le nombre de bits de sécurité offerts par les clés de cet algorithme. Le nombre de bits doit être comparable à ceux donnés dans les tableaux 2 et 3 du document NIST SP800-57. Ce nombre est utilisé pour déterminer la force de sécurité de l'algorithme si aucun algorithme de hachage n'a été enregistré qui définit autrement la force de sécurité. Si l'algorithme de signature implémente son propre hachage en interne, cette valeur doit être définie pour refléter correctement la force de sécurité globale. Cette valeur doit être fournie.
"tls-min-tls" (OSSL_CAPABILITY_TLS_SIGALG_MIN_TLS) <entier>
"tls-max-tls" (OSSL_CAPABILITY_TLS_SIGALG_MAX_TLS) <entier>
"tls-min-dtls" (OSSL_CAPABILITY_TLS_SIGALG_MIN_DTLS) <entier>
"tls-max-dtls" (OSSL_CAPABILITY_TLS_SIGALG_MAX_DTLS) <entier>
Ces paramètres peuvent être utilisés pour décrire les versions minimale et maximale de TLS et DTLS prises en charge par l'algorithme de signature. Les valeurs correspondent à l'encodage sur le réseau des différentes versions TLS. Par exemple, TLSv1.3 est 0x0304 (772 décimal), et TLSv1.2 est 0x0303 (771 décimal). Un 0 indique qu'il n'y a pas de minimum ou de maximum défini. Un -1 dans le champ min ou max indique que l'algorithme de signature ne doit pas être utilisé dans ce protocole. Actuellement, les algorithmes de signature de fournisseur sont utilisés uniquement avec TLS 1.3, s'il est inclus dans la plage spécifiée.

NOTES

Les fonctions core_obj_create() et core_obj_add_sigid() n'étaient pas thread-safe dans OpenSSL 3.0.

EXEMPLES

Voici un exemple de fournisseur simple rendu disponible en tant que module chargeable dynamiquement. Il implémente l'algorithme fictif "FOO" pour l'opération fictive "BAR".
