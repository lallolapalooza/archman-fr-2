NOM

PCRE - Expressions régulières compatibles Perl

DIFFÉRENCES ENTRE PCRE ET PERL

Ce document décrit les différences dans la manière dont PCRE et Perl traitent les expressions régulières. Les différences décrites ici concernent les versions 5.10 et supérieures de Perl.

1. PCRE n'a qu'un sous-ensemble du support Unicode de Perl. Les détails de ce qui est supporté sont donnés dans la page pcreunicode.

2. PCRE n'autorise les quantificateurs de répétition que sur les assertions entre parenthèses, mais elles n'ont pas le sens que l'on pourrait croire. Par exemple, (?!a){3} n'affirme pas que les trois caractères suivants ne sont pas « a ». Il affirme juste que le caractère suivant n'est pas « a » trois fois (en théorie : PCRE optimise cela pour exécuter l'assertion une seule fois). Perl autorise les quantificateurs de répétition sur d'autres assertions comme \b, mais celles-ci ne semblent pas avoir d'utilité.

3. Les sous-modèles de capture qui se trouvent à l'intérieur d'assertions de non-regard avant (negative lookahead) sont comptés, mais leurs entrées dans le vecteur des décalages ne sont jamais définies. Perl définit parfois (mais pas toujours) ses variables numériques à partir d'assertions négatives.

4. Bien que les caractères nuls binaires soient supportés dans la chaîne sujet, ils ne sont pas autorisés dans une chaîne de modèle car elle est passée en tant que chaîne C normale, terminée par un zéro. La séquence d'échappement \0 peut être utilisée dans le modèle pour représenter un zéro binaire.

5. Les séquences d'échappement Perl suivantes ne sont pas supportées : \l, \u, \L, \U, et \N lorsqu'il est suivi d'un nom de caractère ou d'une valeur Unicode. (\N seul, correspondant à un caractère autre qu'une nouvelle ligne, est supporté.) En fait, ceux-ci sont implémentés par la gestion générale des chaînes de Perl et ne font pas partie de son moteur de correspondance de motifs. Si l'un d'eux est rencontré par PCRE, une erreur est générée par défaut. Cependant, si l'option PCRE_JAVASCRIPT_COMPAT est définie, \U et \u sont interprétés comme JavaScript les interprète.

6. Les séquences d'échappement Perl \p, \P, et \X ne sont supportées que si PCRE est compilé avec le support des propriétés de caractères Unicode. Les propriétés qui peuvent être testées avec \p et \P sont limitées aux propriétés de catégorie générale comme Lu et Nd, aux noms de scripts comme Greek ou Han, et aux propriétés dérivées Any et L&. PCRE supporte la propriété Cs (surligneurs), que Perl ne supporte pas ; la documentation Perl dit « Comme Perl masque le besoin pour l'utilisateur de comprendre la représentation interne des caractères Unicode, il n'est pas nécessaire d'implémenter le concept quelque peu désordonné des surligneurs. »

7. PCRE supporte la séquence d'échappement \Q...\E pour mettre des sous-chaînes entre guillemets. Les caractères intermédiaires sont traités comme des littéraux. C'est légèrement différent de Perl dans la mesure où $ et @ sont également traités comme des littéraux à l'intérieur des guillemets. Dans Perl, ils provoquent une interpolation de variable (mais PCRE n'a bien sûr pas de variables). Notez les exemples suivants :


Modèle PCRE correspond à Perl correspond à


\Qabc$xyz\E abc$xyz abc suivi du
contenu de $xyz
\Qabc\$xyz\E abc\$xyz abc\$xyz
\Qabc\E\$\Qxyz\E abc$xyz abc$xyz

La séquence \Q...\E est reconnue à l'intérieur et à l'extérieur des classes de caractères.

8. Assez évidemment, PCRE ne supporte pas les constructions (?{code}) et (??{code}). Cependant, il y a un support pour les motifs récursifs. Ce n'est pas disponible dans Perl 5.8, mais ça l'est dans Perl 5.10. De plus, la fonctionnalité « callout » de PCRE permet à une fonction externe d'être appelée pendant la correspondance de motifs. Voir la documentation pcrecallout pour plus de détails.

9. Les sous-modèles qui sont appelés comme sous-routines (qu'ils soient récursifs ou non) sont toujours traités comme des groupes atomiques dans PCRE. C'est similaire à Python, mais différent de Perl. Les valeurs capturées qui sont définies à l'extérieur d'un appel de sous-routine peuvent être référencées depuis l'intérieur dans PCRE, mais pas dans Perl. Il y a une discussion qui explique ces différences plus en détail dans la section sur les différences de récursion par rapport à Perl dans la page pcrepattern.

10. Si l'un des verbes de contrôle de backtracking est utilisé dans un sous-modèle appelé comme sous-routine (qu'il soit récursif ou non), son effet est confiné à ce sous-modèle ; il ne s'étend pas au modèle environnant. Ce n'est pas toujours le cas dans Perl. En particulier, si (*THEN) est présent dans un groupe appelé comme sous-routine, son action est limitée à ce groupe, même si le groupe ne contient pas de caractères |. Notez que de tels sous-modèles sont traités comme ancrés au point où ils sont testés.

11. Si un motif contient plus d'un verbe de contrôle de backtracking, le premier sur lequel le backtracking se pose agit. Par exemple, dans le motif A(*COMMIT)B(*PRUNE)C, un échec dans B déclenche (*COMMIT), mais un échec dans C déclenche (*PRUNE). Le comportement de Perl est plus complexe ; dans de nombreux cas, il est le même que PCRE, mais il existe des exemples où il diffère.

12. La plupart des verbes de backtracking dans les assertions ont leurs actions normales. Ils ne sont pas confinés à l'assertion.

13. Il existe certaines différences concernant les paramètres des chaînes capturées lorsque tout ou partie d'un motif est répété. Par exemple, la correspondance de « aba » avec le motif /^(a(b)?)+$/ dans Perl laisse $2 non défini, mais dans PCRE, il est défini à « b ».

14. La gestion par PCRE des numéros de sous-modèles dupliqués et des noms de sous-modèles dupliqués n'est pas aussi générale que celle de Perl. C'est une conséquence du fait que PCRE travaille en interne uniquement avec des numéros, en utilisant une table externe pour traduire entre les numéros et les noms. En particulier, un motif tel que (?|(?<a>A)|(?<b>B), où les deux parenthèses de capture ont le même numéro mais des noms différents, n'est pas supporté et provoque une erreur à la compilation. Si cela était autorisé, il serait impossible de distinguer quelles parenthèses ont correspondu, car les deux noms correspondent au sous-modèle de capture numéro 1. Pour éviter cette situation confuse, une erreur est donnée à la compilation.

15. Perl reconnaît les commentaires dans certains endroits que PCRE ne reconnaît pas, par exemple, entre le ( et le ? au début d'un sous-modèle. Si le modificateur /x est défini, Perl autorise les espaces blancs entre ( et ? (bien que les Perl actuels avertissent que c'est déprécié) mais PCRE ne le fait jamais, même si l'option PCRE_EXTENDED est définie.

16. Perl, lorsqu'il est en mode d'avertissement, donne des avertissements pour les classes de caractères comme [A-\d] ou [a-[:digit:]]. Il traite ensuite les tirets comme des littéraux. PCRE n'a pas de fonctionnalités d'avertissement, il donne donc une erreur dans ces cas car ce sont presque certainement des erreurs d'utilisateur.

17. Dans PCRE, les propriétés de caractères majuscules/minuscules Lu et Ll ne sont pas affectées lorsque la correspondance insensible à la casse est spécifiée. Par exemple, \p{Lu} correspond toujours à une lettre majuscule. Je pense que Perl a changé à cet égard ; dans la version au moment de la rédaction (5.16), \p{Lu} et \p{Ll} correspondent à toutes les lettres, quelle que soit la casse, lorsque l'insensibilité à la casse est spécifiée.

18. PCRE fournit certaines extensions aux fonctionnalités d'expressions régulières Perl. Perl 5.10 inclut de nouvelles fonctionnalités qui ne sont pas présentes dans les versions antérieures de Perl, dont certaines (comme les parenthèses nommées) sont dans PCRE depuis un certain temps. Cette liste est par rapport à Perl 5.10 :

(a) Bien que les assertions de regard en arrière (lookbehind) dans PCRE doivent correspondre à des chaînes de longueur fixe, chaque branche alternative d'une assertion de regard en arrière peut correspondre à une chaîne de longueur différente. Perl exige qu'elles aient toutes la même longueur.

(b) Si PCRE_DOLLAR_ENDONLY est défini et que PCRE_MULTILINE ne l'est pas, le méta-caractère $ ne correspond qu'à la toute fin de la chaîne.

(c) Si PCRE_EXTRA est défini, une barre oblique inverse suivie d'une lettre sans signification spéciale génère une erreur. Sinon, comme Perl, la barre oblique inverse est ignorée silencieusement. (Perl peut être amené à émettre un avertissement.)

(d) Si PCRE_UNGREEDY est défini, la « cupidité » des quantificateurs de répétition est inversée, c'est-à-dire que par défaut, ils ne sont pas cupides, mais s'ils sont suivis d'un point d'interrogation, ils le sont.

(e) PCRE_ANCHORED peut être utilisé au moment de la correspondance pour forcer un motif à n'être essayé qu'à la première position correspondante dans la chaîne sujet.

(f) Les options PCRE_NOTBOL, PCRE_NOTEOL, PCRE_NOTEMPTY, PCRE_NOTEMPTY_ATSTART et PCRE_NO_AUTO_CAPTURE pour pcre_exec() n'ont pas d'équivalents Perl.

(g) La séquence d'échappement \R peut être limitée à ne correspondre qu'à CR, LF ou CRLF par l'option PCRE_BSR_ANYCRLF.

(h) La fonctionnalité d'appel (callout) est spécifique à PCRE.

(i) La fonctionnalité de correspondance partielle (partial matching) est spécifique à PCRE.

(j) Les motifs compilés par PCRE peuvent être enregistrés et réutilisés ultérieurement, même sur d'autres hôtes ayant une autre endianness. Cependant, cela ne s'applique pas aux données optimisées créées par le compilateur just-in-time.

(k) Les fonctions de correspondance alternatives (pcre_dfa_exec(), pcre16_dfa_exec() et pcre32_dfa_exec()) correspondent d'une manière différente et ne sont pas compatibles avec Perl.

(l) PCRE reconnaît certaines séquences spéciales comme (*CR) au début d'un motif qui définissent des options globales qui ne peuvent pas être modifiées à l'intérieur de t

pcrecompat(3) — pcrecompat — Documentation Arch Linux

NAME

pcrecompat — PCRE compatibility library.

DIFFERENCES BETWEEN PCRE AND PERL

This library is a compatibility layer for PCRE that supports Perl-compatible regular
expressions. It aims to emulate the Perl regular expression interface.
For differences between PCRE and Perl's regular expressions, see the pcre(3)
manual page, specifically the section "DIFFERENCES BETWEEN PCRE AND PERL".
The PCRE library itself is a set of functions that implement a regular expression
engine, which is compatible with Perl, version 5.005. PCRE is maintained
separately from Perl. The differences between PCRE and Perl are documented
in the pcre(3) man page. This library provides a wrapper around PCRE to
provide a more Perl-like interface.

The primary purpose of this library is to provide a Perl-like interface to
the PCRE functions. It doesn't introduce any new regular expression syntax
or features beyond what PCRE already supports. All regular expression
processing is still handled by the underlying PCRE library.

The pcrecompat library aims to make it easier for developers familiar with
Perl's regex functions to use PCRE in their C or C++ applications. It
simplifies the calling conventions and data handling to be more similar
to Perl's.

Key points:
- It uses simpler function signatures compared to the raw PCRE API.
- It may handle memory management or string manipulation in a way that
  more closely resembles Perl's behavior, reducing the burden on the
  C/C++ programmer.
- The goal is to provide a "drop-in" replacement or a more intuitive
  interface for those transitioning from Perl.

Refer to the pcre(3) man page for details on the regular expression
syntax and features supported by PCRE, as this library relies entirely
on PCRE for its regex processing capabilities. The differences section
in pcre(3) covers features and behaviors that are not supported or
differ from Perl's regex engine.

The pcrecompat library itself does not have a separate set of differences
to document regarding Perl or PCRE, as its function is to bridge the gap
and make PCRE behave more like Perl's regex interface. Any differences
a user encounters would stem from the underlying PCRE engine's
implementation or limitations as described in pcre(3). The library
abstracts away some of the complexity of the PCRE API but not the regex
engine's core behavior or limitations.
