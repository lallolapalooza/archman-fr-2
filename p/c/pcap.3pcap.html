NOM

pcap - Bibliothèque de capture de paquets

SYNTAXE

#include <pcap/pcap.h>

DESCRIPTION

La bibliothèque de capture de paquets (Packet Capture library) fournit une interface de haut niveau aux systèmes de capture de paquets. Tous les paquets sur le réseau, même ceux destinés à d'autres hôtes, sont accessibles via ce mécanisme. Elle prend également en charge la sauvegarde des paquets capturés dans un « savefile », et la lecture de paquets à partir d'un « savefile ».

Initialisation

pcap_init() initialise la bibliothèque. Elle prend un argument donnant des options ; actuellement, les options sont :

PCAP_CHAR_ENC_LOCAL
Traiter toutes les chaînes de caractères fournies en tant qu'arguments, et retourner toutes les chaînes de caractères à l'appelant, comme étant dans le codage de caractères local.
PCAP_CHAR_ENC_UTF_8
Traiter toutes les chaînes de caractères fournies en tant qu'arguments, et retourner toutes les chaînes de caractères à l'appelant, comme étant en UTF-8.

Sur les systèmes de type UNIX, le codage de caractères local est supposé être UTF-8, donc aucune transformation de codage de caractères n'est effectuée.

Sous Windows, le codage de caractères local est la page de codes ANSI locale.

Si pcap_init() est appelée, la routine obsolète pcap_lookupdev() échoue toujours, elle ne doit donc pas être utilisée, et, sous Windows, pcap_create() ne tente pas de gérer les chaînes UTF-16LE.

Si pcap_init() n'est pas appelée, les chaînes sont traitées comme étant dans la page de codes ANSI locale sous Windows, pcap_lookupdev() réussira s'il existe un périphérique sur lequel capturer, et pcap_create() tente de vérifier si la chaîne passée en argument est une chaîne UTF-16LE - notez que cette tentative est dangereuse, car elle peut dépasser la fin de la chaîne - pour gérer le retour d'une chaîne UTF-16LE par pcap_lookupdev(). Les programmes qui n'appellent pas pcap_init() doivent, sous Windows, appeler pcap_wsockinit() pour initialiser Winsock ; ce n'est pas nécessaire si pcap_init() est appelée, car pcap_init() initialisera Winsock elle-même sous Windows.

Ouverture d'un handle de capture pour lecture

Pour ouvrir un handle pour une capture en direct, étant donné le nom du réseau ou de l'interface sur laquelle la capture doit être effectuée, appelez pcap_create(), définissez les options appropriées sur le handle, puis activez-le avec pcap_activate(). Si pcap_activate() échoue, le handle doit être fermé avec pcap_close().

Pour obtenir une liste des périphériques pouvant être ouverts pour une capture en direct, appelez pcap_findalldevs() ; pour libérer la liste retournée par pcap_findalldevs(), appelez pcap_freealldevs(). pcap_lookupdev() retournera le premier périphérique de cette liste qui n'est pas une interface réseau de type « loopback ».

Pour ouvrir un handle pour un « savefile » à partir duquel lire des paquets, étant donné le chemin d'accès au « savefile », appelez pcap_open_offline() ; pour configurer un handle pour un « savefile », étant donné un FILE * faisant référence à un fichier déjà ouvert en lecture, appelez pcap_fopen_offline().

Afin d'obtenir un `pcap_t` « factice » à utiliser dans les routines qui nécessitent un pcap_t comme argument, telles que les routines pour ouvrir un « savefile » en écriture et pour compiler une expression de filtre, appelez pcap_open_dead().

pcap_create(), pcap_open_offline(), pcap_fopen_offline(), et pcap_open_dead() retournent un pointeur vers un pcap_t, qui est le handle utilisé pour lire les paquets du flux de capture ou du « savefile », et pour trouver des informations sur le flux de capture ou le « savefile ». Pour fermer un handle, utilisez pcap_close().

Les options qui peuvent être définies sur un handle de capture incluent :

longueur du instantané
Si, lors de la capture, vous capturez le contenu entier du paquet, cela nécessite plus de temps CPU pour copier le paquet vers votre application, plus de bande passante disque et potentiellement réseau pour écrire les données du paquet dans un fichier, et plus d'espace disque pour sauvegarder les données du paquet. Si vous n'avez pas besoin du contenu entier du paquet – par exemple, si vous n'êtes intéressé que par les en-têtes TCP des paquets – vous pouvez définir la « longueur de l'instantané » pour la capture à une valeur appropriée. Si la longueur de l'instantané est définie sur snaplen, et si snaplen est inférieure à la taille d'un paquet capturé, seuls les premiers snaplen octets de ce paquet seront capturés et fournis en tant que données de paquet.
Une longueur d'instantané de 65535 devrait être suffisante, sur la plupart des réseaux, voire tous, pour capturer toutes les données disponibles du paquet.
La longueur de l'instantané est définie avec pcap_set_snaplen().
mode promiscuous
Sur les réseaux locaux diffusés (LAN) comme Ethernet, si le réseau n'est pas commuté, ou si l'adaptateur est connecté à un « port miroir » sur un commutateur vers lequel tous les paquets passant par le commutateur sont envoyés, une carte réseau reçoit tous les paquets sur le réseau local, y compris les paquets unicast ou multicast qui ne sont pas destinés à une adresse réseau que la carte réseau n'est pas configurée pour reconnaître.
Normalement, la carte écartera ces paquets ; cependant, de nombreuses cartes réseau prennent en charge le « mode promiscuous », qui est un mode dans lequel tous les paquets, même s'ils ne sont pas destinés à une adresse que la carte reconnaît, sont fournis à l'hôte. Ceci est utile pour capturer passivement le trafic entre deux ou plusieurs autres hôtes à des fins d'analyse.
Notez que même si une application ne configure pas le mode promiscuous, la carte pourrait très bien être en mode promiscuous pour une autre raison.
Pour l'instant, cela ne fonctionne pas sur le périphérique « any » ; si un argument de « any » ou NULL est fourni, le réglage du mode promiscuous est ignoré.
Le mode promiscuous est défini avec pcap_set_promisc().
mode moniteur
Sur les réseaux locaux sans fil IEEE 802.11, même si une carte est en mode promiscuous, elle ne fournira à l'hôte que les trames du réseau auquel elle est associée. Elle pourrait également ne fournir que les trames de données, et non les trames de gestion ou de contrôle, et pourrait ne pas fournir l'en-tête 802.11 ou un pseudo-en-tête d'informations radio pour ces trames.
En « mode moniteur », parfois aussi appelé « mode rfmon » (pour « Radio Frequency MONitor »), la carte fournira toutes les trames qu'elle reçoit, avec les en-têtes 802.11, et pourrait fournir un pseudo-en-tête avec des informations radio sur la trame.
Notez qu'en mode moniteur, la carte peut se désassocier du réseau auquel elle est associée, de sorte que vous ne pourrez pas utiliser de réseaux sans fil avec cette carte. Cela pourrait empêcher l'accès aux fichiers sur un serveur réseau, ou la résolution de noms d'hôtes ou d'adresses réseau, si vous capturez en mode moniteur et que vous n'êtes pas connecté à un autre réseau avec une autre carte.
Le mode moniteur est défini avec pcap_set_rfmon(), et pcap_can_set_rfmon() peut être utilisé pour déterminer si une carte peut être mise en mode moniteur.
délai d'attente du tampon de paquets
Si, lors de la capture, les paquets sont livrés dès leur arrivée, l'application qui capture les paquets sera réveillée pour chaque paquet à son arrivée, et pourrait avoir à effectuer un ou plusieurs appels au système d'exploitation pour récupérer chaque paquet.
Si, au lieu de cela, les paquets ne sont pas livrés dès leur arrivée, mais sont livrés après un court délai (appelé un « délai d'attente du tampon de paquets »), plusieurs paquets peuvent être accumulés avant que les paquets ne soient livrés, de sorte qu'un seul réveil serait effectué pour plusieurs paquets, et chaque ensemble d'appels effectués au système d'exploitation fournirait plusieurs paquets, plutôt qu'un seul paquet. Cela réduit la charge CPU par paquet si les paquets arrivent à un taux élevé, augmentant le nombre de paquets par seconde pouvant être capturés.

Toutes les plates-formes ne prennent pas en charge un délai d'attente pour le tampon de paquets ; sur les plates-formes qui n'en prennent pas en charge, le délai d'attente du tampon de paquets est ignoré. Une valeur zéro pour le délai d'attente, sur les plates-formes qui prennent en charge un délai d'attente pour le tampon de paquets, fera que la lecture attendra éternellement pour permettre l'arrivée d'assez de paquets, sans délai d'attente. Une valeur négative est invalide ; le résultat de la définition du délai d'attente à une valeur négative est imprévisible.
NOTE : le délai d'attente du tampon de paquets ne peut pas être utilisé pour faire en sorte que les appels qui lisent des paquets retournent dans un délai limité, car, sur certaines plates-formes, le délai d'attente du tampon de paquets n'est pas pris en charge, et, sur d'autres plates-formes, le minuteur ne démarre qu'après l'arrivée d'au moins un paquet. Cela signifie que le délai d'attente du tampon de paquets ne doit PAS être utilisé, par exemple, dans une application interactive pour permettre à la boucle de capture de paquets de « sonder » les entrées utilisateur périodiquement, car il n'y a aucune garantie qu'un appel de lecture de paquets retournera après l'expiration du délai d'attente, même si aucun paquet n'est arrivé.
Le délai d'attente du tampon de paquets est défini avec pcap_set_timeout().
mode immédiat
En mode immédiat, les paquets sont toujours livrés dès leur arrivée, sans mise en mémoire tampon. Le mode immédiat est défini avec pcap_set_immediate_mode().
taille du tampon
Les paquets qui arrivent pour une capture sont stockés dans un tampon, de sorte qu'ils n'ont pas à être lus par l'application dès leur arrivée. Sur certaines plates-formes, la taille du tampon peut être définie ; une taille trop petite pourrait signifier que, si trop de paquets sont capturés et que la longueur de capture ne limite pas la quantité de données mise en mémoire tampon, des paquets pourraient être perdus si le tampon se remplit avant que l'application ne puisse en lire, tandis qu'une taille trop grande pourrait utiliser plus de mémoire système non paginable que nécessaire pour éviter la perte de paquets.
La taille du tampon est définie avec pcap_set_buffer_size().
type d'horodatage
Sur certaines plates-formes, l'horodatage donné aux paquets lors des captures en direct peut provenir de différentes sources qui peuvent avoir des résolutions différentes ou qui peuvent avoir des relations différentes avec les valeurs temporelles de l'heure actuelle fournies par les routines du système d'exploitation natif. Voir pcap-tstamp(7) pour une liste des types d'horodatage.
Le type d'horodatage est défini avec pcap_set_tstamp_type().

La lecture de paquets à partir d'une interface réseau peut nécessiter que vous disposiez de privilèges spéciaux :

Sous SunOS 3.x ou 4.x avec NIT ou BPF :
Vous devez avoir un accès en lecture à /dev/nit ou /dev/bpf*.
Sous Solaris avec DLPI :
Vous devez avoir un accès en lecture/écriture au pseudo-périphérique réseau, par exemple /dev/le. Sur au moins certaines versions de Solaris, cependant, cela n'est pas suffisant pour permettre à tcpdump de capturer en mode promiscuous ; sur ces versions de Solaris, vous devez être root, ou l'application capturant les paquets doit être installée setuid root, afin de capturer en mode promiscuous. Notez que, sur de nombreuses (peut-être toutes) interfaces, si vous ne capturez pas en mode promiscuous, vous ne verrez aucun paquet sortant, donc une capture non effectuée en mode promiscuous peut ne pas être très utile.
Dans les versions plus récentes de Solaris, vous devez avoir reçu le privilège net_rawaccess ; c'est à la fois nécessaire et suffisant pour vous donner accès au pseudo-périphérique réseau - il n'est pas nécessaire de changer les privilèges sur ce périphérique. Un utilisateur peut recevoir ce privilège en, par exemple, ajoutant ce privilège à la clé defaultpriv de l'utilisateur avec la commande usermod(8).
Sous HP-UX avec DLPI :
Vous devez être root ou l'application capturant les paquets doit être installée setuid root.
Sous IRIX avec snoop :
Vous devez être root ou l'application capturant les paquets doit être installée setuid root.
Sous Linux :
Vous devez être root ou l'application capturant les paquets doit être installée setuid root, sauf si votre distribution a un noyau qui prend en charge les bits de capacité tels que CAP_NET_RAW et un code pour permettre que ces bits de capacité soient attribués à des comptes particuliers et que ces bits soient définis sur les processus initiaux d'un utilisateur lorsqu'il se connecte, auquel cas vous devez avoir CAP_NET_RAW afin de capturer.
Sous ULTRIX et Digital UNIX/Tru64 UNIX :
Tout utilisateur peut capturer le trafic réseau. Cependant, aucun utilisateur (pas même le super-utilisateur) ne peut capturer en mode promiscuous sur une interface à moins que le super-utilisateur n'ait activé le fonctionnement en mode promiscuous sur cette interface en utilisant pfconfig(8), et aucun utilisateur (pas même le super-utilisateur) ne peut capturer le trafic unicast reçu par ou envoyé par la machine sur une interface à moins que le super-utilisateur n'ait activé le fonctionnement en mode copy-all sur cette interface en utilisant pfconfig, donc une capture de paquets utile sur une interface nécessite probablement que le fonctionnement en mode promiscuous ou en mode copy-all, ou les deux modes de fonctionnement, soient activés sur cette interface.
Sous BSD (y compris macOS) :
Vous devez avoir un accès en lecture à /dev/bpf* sur les systèmes qui n'ont pas de périphérique BPF clonable, ou à /dev/bpf sur les systèmes qui en ont un. Sur les BSD avec un devfs (y compris macOS), cela peut impliquer plus que le simple fait d'avoir quelqu'un avec un accès super-utilisateur définissant la propriété ou les permissions sur les périphériques BPF - cela peut impliquer la configuration de devfs pour définir la propriété ou les permissions à chaque démarrage du système, si le système prend même en charge cela ; s'il ne le prend pas en charge, vous devrez peut-être trouver un autre moyen pour que cela se produise au démarrage.

La lecture d'un fichier de paquets enregistré ne nécessite pas de privilèges spéciaux.

Les paquets lus à partir du handle peuvent inclure un « pseudo-en-tête » contenant diverses formes de métadonnées de paquet, et probablement un en-tête de couche de liaison dont le contenu peut différer pour différentes interfaces réseau. Pour déterminer le format des paquets fournis par le handle, appelez pcap_datalink() ; https://www.tcpdump.org/linktypes.html liste les valeurs qu'il renvoie et décrit les formats de paquet qui correspondent à ces valeurs.

Ne supposez PAS que les paquets pour une capture donnée ou un « fichier enregistré » auront un type d'en-tête de couche de liaison donné, tel que DLT_EN10MB pour Ethernet. Par exemple, le périphérique « any » sous Linux aura un type d'en-tête de couche de liaison de DLT_LINUX_SLL ou DLT_LINUX_SLL2 même si tous les périphériques du système au moment où le périphérique « any » est ouvert ont un autre type de liaison de données, tel que DLT_EN10MB pour Ethernet.

Pour obtenir le FILE * correspondant à un pcap_t ouvert pour un « fichier enregistré », appelez pcap_file().

Lecture des paquets

Les paquets sont lus avec pcap_dispatch() ou pcap_loop(), qui traitent un ou plusieurs paquets en appelant une routine de rappel pour chaque paquet, ou avec pcap_next() ou pcap_next_ex(), qui renvoient le paquet suivant. La routine de rappel pour pcap_dispatch() et pcap_loop() reçoit un pointeur vers une struct pcap_pkthdr, qui contient les membres suivants :

ts
une struct timeval contenant l'heure à laquelle le paquet a été capturé
caplen
un bpf_u_int32 indiquant le nombre d'octets du paquet disponibles à partir de la capture
len
un bpf_u_int32 indiquant la longueur du paquet, en octets (qui peut être supérieure au nombre d'octets disponibles à partir de la capture, si la longueur du paquet est supérieure au nombre maximal d'octets à capturer).

La routine de rappel reçoit également un pointeur const u_char vers les premiers caplen octets de données du paquet (comme indiqué dans la struct pcap_pkthdr mentionnée ci-dessus). Il ne s'agit pas nécessairement du paquet entier ; pour capturer le paquet entier, vous devrez fournir une valeur pour snaplen dans votre appel à pcap_set_snaplen() qui soit suffisamment grande pour obtenir toutes les données du paquet - une valeur de 65535 devrait suffire sur la plupart des réseaux, voire tous). Lors de la lecture à partir d'un ``savefile'', la longueur de capture spécifiée lors de la capture limitera la quantité de données de paquet disponibles.

pcap_next() reçoit un argument qui pointe vers une structure struct pcap_pkthdr et la remplit avec les valeurs d'estampille temporelle et de longueur du paquet. Elle renvoie un pointeur const u_char * vers les premiers octets caplen du paquet en cas de succès, et NULL en cas d'erreur.

pcap_next_ex() reçoit deux arguments de pointeur, dont l'un pointe vers une struct pcap_pkthdr * et l'autre pointe vers un const u_char *. Elle définit le premier pointeur pour pointer vers une structure struct pcap_pkthdr avec les valeurs d'estampille temporelle et de longueur du paquet, et définit le second pointeur pour pointer vers les premiers octets caplen du paquet.

Pour forcer la boucle dans pcap_dispatch() ou pcap_loop() à se terminer, appelez pcap_breakloop().

Par défaut, lors de la lecture de paquets à partir d'une interface ouverte pour une capture en direct, pcap_dispatch(), pcap_next() et pcap_next_ex() bloqueront, s'il n'y a pas de paquets disponibles à lire, en attendant que des paquets deviennent disponibles. Sur certaines plateformes, mais pas toutes, si un délai d'attente du tampon de paquets a été spécifié, l'attente se terminera après l'expiration du délai d'attente du tampon de paquets ; les applications doivent s'y préparer, car cela se produit sur certaines plateformes, mais ne doivent pas s'y fier, car cela ne se produit pas sur d'autres plateformes. Notez que l'attente peut, ou peut ne pas, se terminer même si aucun paquet n'est disponible ; les applications doivent s'y préparer, mais ne doivent pas s'y fier.

Un descripteur peut être mis en mode ``non bloquant'', de sorte que ces routines, au lieu de bloquer, renvoient une indication qu'aucun paquet n'est disponible à lire. Appelez pcap_setnonblock() pour mettre un descripteur en mode non bloquant ou pour le sortir du mode non bloquant ; appelez pcap_getnonblock() pour déterminer si un descripteur est en mode non bloquant. Notez que le mode non bloquant ne fonctionne pas correctement sous Mac OS X 10.6.

Le mode non bloquant est souvent combiné avec des routines telles que select(2) ou poll(2) ou d'autres routines qu'une plateforme propose pour attendre que l'un des descripteurs d'un ensemble soit prêt à être lu. Pour obtenir, pour un descripteur, un descripteur qui peut être utilisé dans ces routines, appelez pcap_get_selectable_fd(). Si la routine indique que des données sont disponibles à lire sur le descripteur, une tentative doit être faite pour lire à partir du périphérique.

Tous les descripteurs n'ont pas un tel descripteur disponible ; pcap_get_selectable_fd() renverra -1 si aucun tel descripteur n'est disponible. S'il n'y a pas de tel descripteur disponible, cela peut être parce que le périphérique doit être interrogé périodiquement pour les paquets ; dans ce cas, pcap_get_required_select_timeout() renverra un pointeur vers une struct timeval dont la valeur peut être utilisée comme délai d'attente dans ces routines. Lorsque la routine renvoie, une tentative doit être faite pour lire des paquets à partir du périphérique. Si pcap_get_required_select_timeout() renvoie NULL, aucun délai d'attente de ce type n'est disponible, et ces routines ne peuvent pas être utilisées avec le périphérique.

De plus, pour diverses raisons, une ou plusieurs de ces routines ne fonctionneront pas correctement avec le descripteur ; la documentation de pcap_get_selectable_fd() donne des détails. Notez que, tout comme une tentative de lecture de paquets à partir d'un pcap_t peut ne pas renvoyer de paquets si le délai d'attente du tampon de paquets expire, un appel select(), poll(), ou autre peut, si le délai d'attente du tampon de paquets expire, indiquer qu'un descripteur est prêt à lire même s'il n'y a pas de paquets disponibles à lire.

Routines
pcap_dispatch(3PCAP)
lit un tampon de paquets à partir d'un pcap_t ouvert pour une capture en direct ou l'ensemble complet de paquets à partir d'un pcap_t ouvert pour un ``savefile''
pcap_loop(3PCAP)
lit des paquets à partir d'un pcap_t jusqu'à ce qu'une interruption ou une erreur se produise
pcap_next(3PCAP)
lit le paquet suivant à partir d'un pcap_t sans indication si une erreur s'est produite
pcap_next_ex(3PCAP)

pcap_breakloop(3PCAP)

Mode non bloquant

Pour retourner immédiatement de pcap_dispatch() ou pcap_loop() quand aucun paquet n'est arrivé, ou pour sortir immédiatement de pcap_read() si aucun paquet n'est arrivé, on peut mettre le descripteur de fichier associé au périphérique d'interface réseau en mode non bloquant, ou utiliser pcap_setnonblock(). Les appels susmentionnés, dans ce cas, peuvent retourner 0 si aucun paquet n'est arrivé.

Le mode non bloquant peut être activé ou désactivé avec pcap_setnonblock(), et son état peut être vérifié avec pcap_getnonblock(). Le descripteur de fichier sous-jacent associé à un handle pcap_t, qui peut être utilisé dans des appels tels que select() et poll(), peut être obtenu avec pcap_get_selectable_fd(). Le timeout requis pour utiliser un handle pcap_t dans des appels tels que select() et poll() peut être obtenu avec pcap_get_required_select_timeout().

pcap_setnonblock(3PCAP)
mettre ou effacer le mode non bloquant sur un pcap_t
pcap_getnonblock(3PCAP)
obtenir l'état du mode non bloquant pour un pcap_t
pcap_get_selectable_fd(3PCAP)
tenter d'obtenir un descripteur pour un pcap_t qui peut être utilisé dans des appels tels que select() et poll()
pcap_get_required_select_timeout(3PCAP)
tenter d'obtenir un timeout requis pour l'utilisation d'un pcap_t dans des appels tels que select() et poll()

Filtres

Afin de ne renvoyer que certains paquets lors de la lecture des paquets, un filtre peut être défini sur un handle. Pour une capture en direct, le filtrage sera effectué en mode noyau, si possible, pour éviter de copier les paquets ``non intéressants'' du noyau vers l'espace utilisateur.

Un filtre peut être spécifié sous forme de chaîne de caractères ; la syntaxe et la sémantique de la chaîne sont décrites dans pcap-filter(7). Une chaîne de filtre est compilée en un programme en langage pseudo-machine par pcap_compile() et le programme résultant peut être appliqué comme filtre à un handle avec pcap_setfilter(). Le résultat de pcap_compile() peut être libéré par un appel à pcap_freecode(). pcap_compile() peut nécessiter un masque réseau pour certaines expressions dans la chaîne de filtre ; pcap_lookupnet() peut être utilisé pour trouver l'adresse réseau et le masque réseau pour un périphérique de capture donné.

Un filtre compilé peut également être appliqué directement à un paquet qui a été lu à l'aide de pcap_offline_filter().

Routines
pcap_compile(3PCAP)
compiler une expression de filtre en un programme en langage pseudo-machine
pcap_freecode(3PCAP)
libérer un programme de filtre
pcap_setfilter(3PCAP)
définir un filtre pour un pcap_t
pcap_lookupnet(3PCAP)
obtenir l'adresse réseau et le masque réseau pour un périphérique de capture
pcap_offline_filter(3PCAP)
appliquer un programme de filtre à un paquet

Paquets entrants et sortants

Par défaut, libpcap tentera de capturer à la fois les paquets envoyés par la machine et les paquets reçus par la machine. Pour limiter la capture aux seuls paquets reçus par la machine ou, si possible, aux seuls paquets envoyés par la machine, appelez pcap_setdirection().

Ouverture d'un handle pour écrire des paquets capturés

Pour ouvrir un « fichier de sauvegarde » dans lequel écrire les paquets, étant donné le chemin du « fichier de sauvegarde », appelez pcap_dump_open(). Pour ouvrir un « fichier de sauvegarde » dans lequel écrire les paquets, étant donné le chemin du « fichier de sauvegarde », appelez pcap_dump_open() ; pour configurer un handle pour un « fichier de sauvegarde », étant donné un FILE * faisant référence à un fichier déjà ouvert en écriture, appelez pcap_dump_fopen(). Chacun renvoie des pointeurs vers un pcap_dumper_t, qui est le handle utilisé pour écrire les paquets dans le « fichier de sauvegarde ». En cas de succès, il aura créé le fichier s'il n'existait pas et tronqué le fichier s'il existait déjà. Pour fermer un pcap_dumper_t, appelez pcap_dump_close().

Écriture de paquets

Pour écrire un paquet dans un pcap_dumper_t, appelez pcap_dump(). Les paquets écrits avec pcap_dump() peuvent être mis en mémoire tampon, plutôt que d'être immédiatement écrits dans le « fichier de sauvegarde ». La fermeture du pcap_dumper_t forcera l'écriture de tous les paquets mis en mémoire tampon mais non encore écrits dans le « fichier de sauvegarde ». Pour forcer l'écriture de tous les paquets écrits dans le pcap_dumper_t, et pas encore dans le « fichier de sauvegarde » parce qu'ils sont mis en mémoire tampon par le pcap_dumper_t, sans fermer le pcap_dumper_t, appelez pcap_dump_flush().

pcap_dump(3PCAP)
écrire un paquet dans un pcap_dumper_t
pcap_dump_flush(3PCAP)

obtenir la position actuelle du fichier pour un pcap_dumper_t

COMPATIBILITÉ ASCENDANTE

Dans les versions de libpcap antérieures à 1.0, le fichier d'en-tête pcap.h ne se trouvait pas dans un répertoire pcap sur la plupart des plateformes ; si vous écrivez une application qui doit fonctionner sur des versions de libpcap antérieures à 1.0, incluez <pcap.h>, qui inclura <pcap/pcap.h> pour vous, plutôt que d'inclure <pcap/pcap.h>.

pcap_create() et pcap_activate() n'étaient pas disponibles dans les versions de libpcap antérieures à 1.0 ; si vous écrivez une application qui doit fonctionner sur des versions de libpcap antérieures à 1.0, utilisez soit pcap_open_live() pour obtenir un handle pour une capture en direct, soit, si vous voulez pouvoir utiliser les capacités supplémentaires offertes par l'utilisation de pcap_create() et pcap_activate(), utilisez un script autoconf(1) ou un autre script de configuration pour vérifier si les API de libpcap 1.0 sont disponibles et utilisez-les uniquement si elles le sont.
