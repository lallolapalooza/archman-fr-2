NOM

pcap-filter - syntaxe du filtre de paquets

DESCRIPTION

pcap_compile(3PCAP) est utilisé pour compiler une chaîne en un programme de filtre. Le programme de filtre résultant peut ensuite être appliqué à un flux de paquets pour déterminer quels paquets seront fournis à pcap_loop(3PCAP), pcap_dispatch(3PCAP), pcap_next(3PCAP) ou pcap_next_ex(3PCAP).

L'expression de filtre est composée d'un ou plusieurs primitives. Les primitives sont généralement constituées d'un id (nom ou numéro) précédé d'un ou plusieurs qualificateurs. Il existe trois types différents de qualificateurs :

type
Les qualificateurs de type indiquent à quel genre de chose l'id (nom ou numéro) fait référence. Les types possibles sont host, net, port et portrange. Par exemple, `host foo', `net 128.3', `port 20', `portrange 6000-6008'. S'il n'y a pas de qualificateur de type, host est supposé.
dir
Les qualificateurs de dir spécifient une direction de transfert particulière vers et/ou depuis id. Les directions possibles sont src, dst, src or dst, src and dst, ra, ta, addr1, addr2, addr3 et addr4. Par exemple, `src foo', `dst net 128.3', `src or dst port ftp-data'. S'il n'y a pas de qualificateur de direction, `src or dst' est supposé. Les qualificateurs ra, ta, addr1, addr2, addr3 et addr4 ne sont valides que pour les couches de liaison sans fil IEEE 802.11.
proto
Les qualificateurs de proto limitent la correspondance à un protocole particulier. Les protocoles possibles sont : ether, fddi, tr, wlan, ip, ip6, arp, rarp, decnet, sctp, tcp et udp. Par exemple, `ether src foo', `arp net 128.3', `tcp port 21', `udp portrange 7000-7009', `wlan addr2 0:2:3:4:5:6'. S'il n'y a pas de qualificateur proto, tous les protocoles compatibles avec le type sont supposés. Par exemple, `src foo' signifie `(ip6 or ip or arp or rarp) src foo', `net bar' signifie `(ip or arp or rarp) net bar' et `port 53' signifie `(tcp or udp or sctp) port 53' (notez que ces exemples utilisent une syntaxe invalide pour illustrer le principe).

[fddi est en fait un alias pour ether ; l'analyseur les traite de manière identique, signifiant « le niveau de liaison de données utilisé sur l'interface réseau spécifiée ». Les en-têtes FDDI contiennent des adresses source et destination de type Ethernet, et contiennent souvent des types de paquets de type Ethernet, de sorte que vous pouvez filtrer sur ces champs FDDI comme avec les champs Ethernet analogues. Les en-têtes FDDI contiennent également d'autres champs, mais vous ne pouvez pas les nommer explicitement dans une expression de filtre.

De même, tr et wlan sont des alias pour ether ; les affirmations du paragraphe précédent concernant les en-têtes FDDI s'appliquent également aux en-têtes Token Ring et sans fil 802.11. Pour les en-têtes 802.11, l'adresse de destination est le champ DA et l'adresse source est le champ SA ; les champs BSSID, RA et TA ne sont pas vérifiés.]

En plus de ce qui précède, il existe quelques mots-clés spéciaux « primitifs » qui ne suivent pas le modèle : gateway, broadcast, less, greater et expressions arithmétiques. Tous ceux-ci sont décrits ci-dessous.

Les expressions de filtre plus complexes sont construites en utilisant les mots and, or et not (ou de manière équivalente : `&&', `||' et `!' respectivement) pour combiner les primitives. Par exemple, `host foo and not port ftp and not port ftp-data'. Pour éviter de taper, des listes de qualificateurs identiques peuvent être omises. Par exemple, `tcp dst port ftp or ftp-data or domain' est exactement la même chose que `tcp dst port ftp or tcp dst port ftp-data or tcp dst port domain'.

Les primitives autorisées sont :

dst host hostnameaddr
Vrai si le champ de destination IPv4/v6 du paquet est hostnameaddr, qui peut être une adresse ou un nom.
src host hostnameaddr
Vrai si le champ source IPv4/v6 du paquet est hostnameaddr.
host hostnameaddr
Vrai si la source ou la destination IPv4/v6 du paquet est hostnameaddr.
N'importe laquelle des expressions hôtes ci-dessus peut être précédée des mots-clés ip, arp, rarp ou ip6 comme dans : 
ip host hostnameaddr

ce qui est équivalent à : 
ether proto \ip and host hostnameaddr

Si hostnameaddr est un nom avec plusieurs adresses IPv4/v6, chaque adresse sera vérifiée pour une correspondance.
ether dst ethernameaddr
Vrai si l'adresse de destination Ethernet est ethernameaddr. ethernameaddr peut être un nom du fichier /etc/ethers ou une adresse MAC numérique de la forme "xx:xx:xx:xx:xx:xx", "xx.xx.xx.xx.xx.xx", "xx-xx-xx-xx-xx-xx", "xxxx.xxxx.xxxx", "xxxxxxxxxxxx", ou divers mélanges de ':', '.', et '-', où chaque "x" est un chiffre hexadécimal (0-9, a-f, ou A-F).
ether src ethernameaddr
Vrai si l'adresse source Ethernet est ethernameaddr.
ether host ethernameaddr
Vrai si l'adresse source ou destination Ethernet est ethernameaddr.
gateway host
Vrai si le paquet a utilisé host comme passerelle. C'est-à-dire, si l'adresse source ou destination Ethernet était host mais ni la source IP ni la destination IP n'était host. Host doit être un nom et doit être trouvé à la fois par les mécanismes de résolution de nom d'hôte en adresse IP de la machine (fichier de nom d'hôte, DNS, NIS, etc.) et par le mécanisme de résolution de nom d'hôte en adresse Ethernet de la machine (/etc/ethers, etc.). (Une expression équivalente est 
ether host ethernameaddr and not host hostnameaddr

qui peut être utilisée avec des noms ou des numéros pour hostnameaddr / ethernameaddr.) Cette syntaxe ne fonctionne pas actuellement dans une configuration activant IPv6.
dst net netnameaddr
Vrai si l'adresse réseau de destination IPv4/v6 du paquet correspond au numéro de réseau de netnameaddr. Net peut être un nom de la base de données des réseaux (/etc/networks, etc.) ou un numéro de réseau. Un numéro de réseau IPv4 peut être écrit sous forme de quad pointillé (par exemple, 192.168.1.0), triple pointillé (par exemple, 192.168.1), paire pointillée (par exemple, 172.16) ou nombre unique (par exemple, 10) ; le masque de réseau est 255.255.255.255 pour un quad pointillé (ce qui signifie qu'il s'agit en fait d'une correspondance d'hôte), 255.255.255.0 pour un triple pointillé, 255.255.0.0 pour une paire pointillée, ou 255.0.0.0 pour un nombre unique. Un numéro de réseau IPv6 doit être écrit en entier ; le masque de réseau est ffff:ffff:ffff:ffff:ffff:ffff:ffff:ffff, donc les correspondances de "réseau" IPv6 sont toujours des correspondances d'hôte, et une correspondance de réseau nécessite une longueur de masque.
src net netnameaddr
Vrai si l'adresse réseau source IPv4/v6 du paquet correspond au numéro de réseau de netnameaddr.
net netnameaddr
Vrai si l'adresse source ou destination IPv4/v6 du paquet correspond au numéro de réseau de netnameaddr.
net netaddr mask netmask
Vrai si l'adresse IPv4 correspond à netaddr avec le netmask spécifique. Peut être qualifié avec src ou dst. Notez que cette syntaxe n'est pas valide pour netaddr IPv6.
net netaddr/len
Vrai si l'adresse IPv4/v6 correspond à netaddr avec un masque de réseau de largeur len bits. Peut être qualifié avec src ou dst.
dst port portnamenum
Vrai si le paquet est IPv4/v6 TCP, UDP ou SCTP et a une valeur de port de destination portnamenum. Le portnamenum peut être un numéro ou un nom utilisé dans /etc/services (voir tcp(4P) et udp(4P) pour une liste).

>udp(4P)). Si un nom est utilisé, le numéro de port et le protocole sont tous deux vérifiés. Si un nombre ou un nom ambigu est utilisé, seul le numéro de port est vérifié (par exemple, `dst port 513' affichera à la fois le trafic tcp/login et udp/who, et `port domain' affichera à la fois le trafic tcp/domain et udp/domain .
src port portnamenum
Vrai si le paquet a une valeur de port source de portnamenum.
port portnamenum
Vrai si le port source ou destination du paquet est portnamenum.
dst portrange portnamenum1-portnamenum2
Vrai si le paquet est TCP, UDP ou SCTP IPv4/v6 et a une valeur de port de destination entre portnamenum1 et portnamenum2 (inclus). portnamenum1 et portnamenum2 sont interprétés de la même manière que le paramètre portnamenum pour port.
src portrange portnamenum1-portnamenum2
Vrai si le paquet a une valeur de port source entre portnamenum1 et portnamenum2 (inclus).
portrange portnamenum1-portnamenum2
Vrai si le port source ou destination du paquet est entre portnamenum1 et portnamenum2 (inclus).
N'importe laquelle des expressions de port ou de plage de ports ci-dessus peut être précédée des mots-clés tcp, udp ou sctp, comme dans : 
tcp src port portnamenum

qui ne correspond qu'aux paquets TCP dont le port source est portnamenum.
less length
Vrai si le paquet a une longueur inférieure ou égale à length. Ceci est équivalent à : 
len <= length

greater length
Vrai si le paquet a une longueur supérieure ou égale à length. Ceci est équivalent à : 
len >= length

ip proto protocol
Vrai si le paquet est un paquet IPv4 (voir ip(4P)) de type de protocole protocol. Protocol peut être un nombre ou l'un des noms reconnus par getprotobyname(3) (comme dans, par exemple, `getent(1) protocols'), typiquement à partir d'une entrée dans /etc/protocols, par exemple : ah, esp, eigrp (uniquement sous Linux, FreeBSD, NetBSD, DragonFly BSD et macOS), icmp, igmp, igrp (uniquement sous OpenBSD), pim, sctp, tcp, udp ou vrrp. Notez que la plupart de ces identifiants d'exemple sont aussi des mots-clés et doivent être échappés avec une barre oblique inverse (\). Notez que cette primitive ne suit pas la chaîne d'en-têtes de protocole.
icmp
Abréviation pour : 
ip proto 1

ip6 proto protocol
Vrai si le paquet est un paquet IPv6 de type de protocole protocol. (Voir `ip proto' ci-dessus pour la signification de protocol.) Notez que la variante IPv6 de ICMP utilise un numéro de protocole différent, nommé ipv6-icmp sous AIX, FreeBSD, illumos, Linux, macOS, NetBSD, OpenBSD, Solaris et Windows. Notez que cette primitive ne suit pas la chaîne d'en-têtes de protocole.
icmp6
Abréviation pour : 
ip6 proto 58

proto protocol
Vrai si le paquet est un paquet IPv4 ou IPv6 de type de protocole protocol. (Voir `ip proto' ci-dessus pour la signification de protocol.) Notez que cette primitive ne suit pas la chaîne d'en-têtes de protocole.
ah, esp, pim, sctp, tcp, udp
Abréviations pour : 
proto \protocol

où protocol est l'un des protocoles ci-dessus.
ip6 protochain protocol
Vrai si le paquet est un paquet IPv6, et contient un en-tête de protocole de type protocol dans sa chaîne d'en-têtes de protocole. (Voir `ip proto' ci-dessus pour la signification de protocol.) Par exemple, 
ip6 protochain 6

correspond à n'importe quel paquet IPv6 avec un en-tête de protocole TCP dans la chaîne d'en-têtes de protocole. Le paquet peut contenir, par exemple, un en-tête d'authentification, un en-tête de routage, ou un en-tête d'option hop-by-hop, entre l'en-tête IPv6 et l'en-tête TCP. Le code BPF émis par cette primitive est complexe et ne peut pas être optimisé par le code d'optimisation BPF, et n'est pas supporté par les moteurs de filtrage dans le noyau, donc cela peut être quelque peu lent et peut entraîner la perte de plus de paquets.
ip protochain protocol
Équivalent à ip6 protochain protocol, mais ceci est pour IPv4. (Voir `ip proto' ci-dessus pour la signification de protocol.)
protochain protocol
Vrai si le paquet est un paquet IPv4 ou IPv6 de type de protocole protocol. (Voir `ip proto' ci-dessus pour la signification de protocol.) Notez que cette primitive suit la chaîne d'en-têtes de protocole.
ether broadcast
Vrai si le paquet est un paquet Ethernet broadcast. Le mot-clé ether est facultatif.
ip broadcast
Vrai si le paquet est un paquet IPv4 broadcast. Il vérifie les deux conventions de diffusion tout-zéro et tout-un, et recherche le masque de sous-réseau sur l'interface sur laquelle la capture est effectuée.
Si le masque de sous-réseau de l'interface sur laquelle la capture est effectuée n'est pas disponible, soit parce que l'interface sur laquelle la capture est effectuée n'a pas de netmask, soit parce que la capture est effectuée sur l'interface Linux "any", qui peut capturer sur plus d'une interface, cette vérification ne fonctionnera pas correctement.
ether multicast
Vrai si le paquet est un paquet Ethernet multicast. Le mot-clé ether est facultatif. Ceci est un raccourci pour `ether[0] & 1 != 0'.
ip multicast
Vrai si le paquet est un paquet IPv4 multicast.
ip6 multicast
Vrai si le paquet est un paquet IPv6 multicast.
ether proto protocol
Vrai si le paquet est de type Ethernet protocol. Protocol peut être un nombre ou l'un des noms aarp, arp, atalk, decnet, ip, ip6, ipx, iso, lat, loopback, mopdl, moprc, netbeui, rarp, sca ou stp. Notez que ces identifiants (sauf loopback) sont aussi des mots-clés et doivent être échappés avec une barre oblique inverse (\).
[Dans le cas de FDDI (par exemple, `fddi proto \arp'), Token Ring (par exemple, `tr proto \arp'), et les réseaux locaux sans fil IEEE 802.11 (par exemple, `wlan proto \arp'), pour la plupart de ces protocoles, l'identification du protocole provient de l'en-tête 802.2 Logical Link Control (LLC), qui est généralement superposé sur l'en-tête FDDI, Token Ring ou 802.11.
Lors du filtrage pour la plupart des identifiants de protocole sur FDDI, Token Ring ou 802.11, le filtre ne vérifie que le champ d'identification du protocole d'un en-tête LLC sous forme SNAP avec un Identifiant d'Unité Organisationnelle (OUI) de 0x000000, pour Ethernet encapsulé ; il ne vérifie pas si le paquet est sous forme SNAP avec un OUI de 0x000000. Les exceptions sont :
iso
le filtre vérifie les champs DSAP (Destination Service Access Point) et SSAP (Source Service Access Point) de l'en-tête LLC ;
stp et netbeui
le filtre vérifie le DSAP de l'en-tête LLC ;
atalk
le filtre recherche un paquet au format SNAP avec un OUI de 0x080007 et l'etype AppleTalk.
Dans le cas d'Ethernet, le filtre vérifie le champ type Ethernet pour la plupart de ces protocoles. Les exceptions sont :
iso, stp, et netbeui
le filtre recherche une trame 802.3 puis vérifie l'en-tête LLC comme il le fait pour FDDI, Token Ring et 802.11 ;
atalk
le filtre recherche à la fois l'etype AppleTalk dans une trame Ethernet et un paquet au format SNAP comme il le fait pour FDDI, Token Ring et 802.11 ;
aarp
le filtre recherche l'etype ARP AppleTalk dans une trame Ethernet ou une trame SNAP 802.2 avec un OUI de 0x000000 ;
ipx
le filtre recherche l'etype IPX dans une trame Ethernet, le DSAP IPX dans l'en-tête LLC, l'encapsulation IPX sans en-tête LLC 802.3, et l'etype IPX dans une trame SNAP.
ip, ip6, arp, rarp, atalk, aarp, decnet, iso, stp, ipx, netbeui
Abréviations pour : 
ether proto \protocol

où protocol est l'un des protocoles ci-dessus.
lat, moprc, mopdl
Abréviations pour : 
ether proto \protocol

où protocol est l'un des protocoles ci-dessus. Notez que toutes les applications utilisant pcap(3PCAP) ne savent pas actuellement comment analyser ces protocoles.
decnet src decnetaddr
Vrai si l'adresse source DECnet est decnetaddr, qui peut être une adresse de la forme ``10.123'', ou un nom d'hôte DECnet. [La prise en charge des noms d'hôtes DECnet n'est disponible que sur les systèmes ULTRIX configurés pour exécuter DECnet.]
decnet dst decnetaddr
Vrai si l'adresse de destination DECnet est decnetaddr.
decnet host decnetaddr
Vrai si l'adresse source ou destination DECnet est decnetaddr.
llc
Vrai si le paquet possède un en-tête LLC 802.2. Cela inclut :
Les paquets Ethernet avec un champ de longueur plutôt qu'un champ de type qui ne sont pas des paquets NetWare sur 802.3 bruts ;
Les paquets de données IEEE 802.11 ;
Les paquets Token Ring (aucun contrôle n'est effectué sur les trames LLC) ;
Les paquets FDDI (aucun contrôle n'est effectué sur les trames LLC) ;
Les paquets encapsulés en LLC sur ATM, pour SunATM sur Solaris.
llc type
Vrai si le paquet possède un en-tête LLC 802.2 et correspond au type spécifié. type peut être l'un des suivants :
i
PDUs d'Information (I)
s
PDUs de Supervision (S)
u
PDUs non numérotées (U)
rr
PDUs S de Récepteur Prêt (RR)
rnr
PDUs S de Récepteur Non Prêt (RNR)
rej
PDUs S de Rejet (REJ)
ui
PDUs U d'Information Non Numérotée (UI)
ua
PDUs U d'Accusé de Réception Non Numéroté (UA)
disc
PDUs U de Déconnexion (DISC)
sabme
PDUs U de Définition de Mode Équilibré Asynchrone Étendu (SABME)
test
PDUs U de Test (TEST)
xid
PDUs U d'Échange d'Identification (XID)
frmr
PDUs U de Rejet de Trame (FRMR)
inbound
Le paquet a été reçu par l'hôte effectuant la capture plutôt qu'envoyé par cet hôte. Ceci n'est pris en charge que pour certains types de couche liaison, tels que SLIP et le mode de capture Linux "cooked" utilisé pour le périphérique "any" et pour certains autres types de périphériques.
outbound
Le paquet a été envoyé par l'hôte effectuant la capture plutôt que reçu par cet hôte. Ceci n'est pris en charge que pour certains types de couche liaison, tels que SLIP et le mode de capture Linux "cooked" utilisé pour le périphérique "any" et pour certains autres types de périphériques.
ifindex interface_index
Vrai si le paquet a été enregistré via l'interface spécifiée (s'applique uniquement aux paquets enregistrés par l'interface Linux "any" cooked v2).
ifname interface
Vrai si le paquet a été enregistré comme provenant de l'interface spécifiée (s'applique uniquement aux paquets enregistrés par le pf(4) d'OpenBSD ou de FreeBSD).
on interface
Synonyme du modificateur ifname.
rnr num
Vrai si le paquet a été enregistré comme correspondant au numéro de règle PF spécifié (s'applique uniquement aux paquets enregistrés par le pf(4) d'OpenBSD ou de FreeBSD).
rulenum num
Synonyme du modificateur rnr.
reason code
Vrai si le paquet a été enregistré avec le code de raison PF spécifié. Les codes connus sont : match, bad-offset, fragment, short, normalize et memory (s'applique uniquement aux paquets enregistrés par le pf(4) d'OpenBSD ou de FreeBSD).
rset name
Vrai si le paquet a été enregistré comme correspondant au nom de jeu de règles PF spécifié d'une règle ancrée (s'applique uniquement aux paquets enregistrés par le pf(4) d'OpenBSD ou de FreeBSD).
ruleset name
Synonyme du modificateur rset.
srnr num
Vrai si le paquet a été enregistré comme correspondant au numéro de règle PF spécifié d'une règle ancrée (s'applique uniquement aux paquets enregistrés par le pf(4) d'OpenBSD ou de FreeBSD).
subrulenum num
Synonyme du modificateur srnr.
action act
Vrai si PF a effectué l'action spécifiée lors de l'enregistrement du paquet. Les actions connues sont : pass et block et, avec les versions ultérieures de pf(4), nat, rdr, binat et scrub (s'applique uniquement aux paquets enregistrés par le pf(4) d'OpenBSD ou de FreeBSD).
wlan ra ehost
Vrai si le RA IEEE 802.11 est ehost. Le champ RA est utilisé dans toutes les trames sauf les trames de gestion.
wlan ta ehost
Vrai si le TA IEEE 802.11 est ehost. Le champ TA est utilisé dans toutes les trames sauf les trames de gestion et les trames de contrôle CTS (Clear To Send) et ACK (Acknowledgment).
wlan addr1 ehost
Vrai si la première adresse IEEE 802.11 est ehost.
wlan addr2 ehost
Vrai si la deuxième adresse IEEE 802.11, si elle est présente, est ehost. Le deuxième champ d'adresse est utilisé dans toutes les trames sauf les trames de contrôle CTS (Clear To Send) et ACK (Acknowledgment).
wlan addr3 ehost
Vrai si la troisième adresse IEEE 802.11, si elle est présente, est ehost. Le troisième champ d'adresse est utilisé dans les trames de gestion et de données, mais pas dans les trames de contrôle.
wlan addr4 ehost
Vrai si la quatrième adresse IEEE 802.11, si elle est présente, est ehost. Le quatrième champ d'adresse est uniquement utilisé pour les trames WDS (Wireless Distribution System).
type wlan_type
Vrai si le type de trame IEEE 802.11 correspond au wlan_type spécifié. Les wlan_type valides sont : mgt, ctl et data.
type wlan_type subtype wlan_subtype
Vrai si le type de trame IEEE 802.11 correspond au wlan_type spécifié et si le sous-type de trame correspond au wlan_subtype spécifié.
Si le wlan_type spécifié est mgt, alors les wlan_subtype valides sont : assoc-req, assoc-resp, reassoc-req, reassoc-resp, probe-req, probe-resp, beacon, atim, disassoc, auth et deauth.
Si le wlan_type spécifié est ctl, alors les wlan_subtype valides sont : ps-poll, rts, cts, ack, cf-end et cf-end-ack.
Si le wlan_type spécifié est data, alors les wlan_subtype valides sont : data, data-cf-ack, data-cf-poll, data-cf-ack-poll, null, cf-ack, cf-poll, cf-ack-poll, qos-data, qos-data-cf-ack, qos-data-cf-poll, qos-data-cf-ack-poll, qos, qos-cf-poll et qos-cf-ack-poll.
subtype wlan_subtype
Vrai si le sous-type de trame IEEE 802.11 correspond au wlan_subtype spécifié et si la trame a le type auquel appartient le wlan_subtype spécifié.
dir direction
Vrai si la direction de la trame IEEE 802.11 correspond à la direction spécifiée. Les directions valides sont : nods, tods, fromds, dstods, ou une valeur numérique.
vlan [vlan_id]
Vrai si le paquet est un paquet VLAN IEEE 802.1Q. Si le vlan_id optionnel est spécifié, vrai uniquement si le paquet possède le vlan_id spécifié. Notez que le premier mot-clé vlan rencontré dans une expression modifie les décalages de décodage pour le reste de l'expression en supposant que le paquet est un paquet VLAN. Le mot-clé `vlan [vlan_id]` peut être utilisé plusieurs fois, pour filtrer sur des hiérarchies VLAN. Chaque utilisation de ce mot-clé incrémente les décalages du filtre de 4.
Par exemple : 
vlan 100 && vlan 200

filtre sur le VLAN 200 encapsulé dans le VLAN 100, et 
vlan && vlan 300 && ip

filtre sur le protocole IPv4 encapsulé dans le VLAN 300 encapsulé dans un VLAN de niveau supérieur quelconque.
mpls [label_num]
Vrai si le paquet est un paquet MPLS. Si le label_num optionnel est spécifié, vrai uniquement si le paquet possède le label_num spécifié. Notez que le premier mot-clé mpls rencontré dans une expression modifie les décalages de décodage pour le reste de l'expression en supposant que le paquet est un paquet IP encapsulé dans MPLS. Le mot-clé `mpls [label_num]` peut être utilisé plusieurs fois, pour filtrer sur des hiérarchies MPLS. Chaque utilisation de ce mot-clé incrémente les décalages du filtre de 4.
Par exemple : 
mpls 100000 && mpls 1024

filtre les paquets avec une étiquette externe de 100000 et une étiquette interne de 1024, et 
mpls && mpls 1024 && host 192.9.200.1

filtre les paquets vers ou depuis 192.9.200.1 avec une étiquette interne de 1024 et n'importe quelle étiquette externe.
pppoed
Vrai si le paquet est un paquet de découverte PPP sur Ethernet (type Ethernet 0x886
3).
pppoes [session_id]
Vrai si le paquet est un paquet de session PPP-over-Ethernet (type Ethernet 0x8864). Si le paramètre optionnel session_id est spécifié, alors cette condition n'est vraie que si le paquet a l'session_id spécifié. Notez que le premier mot-clé pppoes rencontré dans une expression modifie les décalages de décodage pour le reste de l'expression, en supposant que le paquet est un paquet de session PPPoE.
Par exemple : 
pppoes 0x27 && ip

filtre le protocole IPv4 encapsulé dans l'ID de session PPPoE 0x27.
geneve [vni]
Vrai si le paquet est un paquet Geneve (port UDP 6081). Si le paramètre optionnel vni est spécifié, alors cette condition n'est vraie que si le paquet a le vni spécifié. Notez que lorsque le mot-clé geneve est rencontré dans une expression, il modifie les décalages de décodage pour le reste de l'expression, en supposant que le paquet est un paquet Geneve.
Par exemple : 
geneve 0xb && ip

filtre le protocole IPv4 encapsulé dans Geneve avec le VNI 0xb. Cela correspondra à la fois à l'IPv4 directement encapsulé dans Geneve, ainsi qu'à l'IPv4 contenu dans une trame Ethernet.
iso proto protocol
Vrai si le paquet est un paquet OSI de type de protocole protocol. Protocol peut être un nombre ou l'un des noms clnp, esis, ou isis.
clnp, esis, isis
Abréviations pour : 
iso proto \protocol

où protocol est l'un des protocoles ci-dessus.
l1, l2, iih, lsp, snp, csnp, psnp

vpi n
Vrai si le paquet est un paquet ATM, pour SunATM sur Solaris, avec un identifiant de chemin virtuel de n.

Vrai si le paquet est un paquet ATM, pour SunATM sur Solaris, avec un identifiant de canal virtuel de n.
lane
Vrai si le paquet est un paquet ATM, pour SunATM sur Solaris, et est un paquet ATM LANE. Notez que le premier mot-clé lane rencontré dans une expression modifie les tests effectués dans le reste de l'expression, en supposant que le paquet est soit un paquet Ethernet émulé par LANE, soit un paquet de contrôle LE LANE. Si lane n'est pas spécifié, les tests sont effectués en supposant que le paquet est un paquet encapsulé LLC.

expr1 relop expr2
Vrai si la relation est vraie. Relop est l'un de {>, <, >=, <=, =, ==, !=} (où = signifie la même chose que ==). Chacun de expr1 et expr2 est une expression arithmétique composée de constantes entières (exprimées en syntaxe C standard), des opérateurs binaires normaux {+, -, *, /, %, &, |, ^, <<, >>}, un opérateur de longueur, et des accesseurs spéciaux de données de paquet. Notez que toutes les comparaisons sont non signées, donc par exemple, 0x80000000 et 0xffffffff sont > 0.
Les opérateurs % et ^ ne sont actuellement pris en charge que pour le filtrage dans le noyau sur certains systèmes d'exploitation (par exemple : FreeBSD, Linux avec les noyaux 3.7 et ultérieurs, NetBSD) ; sur tous les autres systèmes (par exemple : AIX, illumos, Solaris, OpenBSD), si ces opérateurs sont utilisés, le filtrage sera effectué en mode utilisateur, ce qui augmentera la surcharge de capture des paquets et risque de faire tomber plus de paquets.
L'opérateur de longueur, indiqué par le mot-clé len, donne la longueur du paquet.
Pour accéder aux données à l'intérieur du paquet, utilisez la syntaxe suivante : 
proto [ expr : size ]

Proto est l'un de arp, atalk, carp, decnet, ether, fddi, icmp, icmp6, igmp, igrp, ip, ip6, lat, link, mopdl, moprc, pim, ppp, radio, rarp, sca, sctp, slip, tcp, tr, udp, vrrp ou wlan, et indique la couche de protocole pour l'opération d'indexation. (ether, fddi, link, ppp, slip, tr et wlan font tous référence à la couche de liaison. radio fait référence à « l'en-tête radio » ajouté à certaines captures 802.11.) Notez que tcp, udp et d'autres types de protocoles de couche supérieure ne s'appliquent qu'à IPv4, pas à IPv6 (cela sera corrigé à l'avenir). Le décalage en octets, par rapport à la couche de protocole indiquée, est donné par expr. Size est facultatif et indique le nombre d'octets dans le champ d'intérêt ; il peut être de un, deux ou quatre, et vaut un par défaut.

Par exemple, `ether[0] & 1 != 0' capture tout le trafic multicast. L'expression `ip[0] & 0xf != 5' capture tous les paquets IPv4 avec des options. L'expression `ip[6:2] & 0x1fff = 0' ne capture que les datagrammes IPv4 non fragmentés et le fragment zéro des datagrammes IPv4 fragmentés. Cette vérification est appliquée implicitement aux opérations d'indexation tcp et udp. Par exemple, tcp[0] signifie toujours le premier octet de l'en-tête TCP, et jamais le premier octet d'un fragment intermédiaire.

Certains décalages et valeurs de champ peuvent être exprimés sous forme de noms plutôt que de valeurs numériques. Les décalages de champ d'en-tête de protocole suivants sont disponibles : icmptype (champ de type ICMP), icmp6type (champ de type ICMPv6), icmpcode (champ de code ICMP), icmp6code (champ de code ICMPv6) et tcpflags (champ de drapeaux TCP).
Les valeurs de champ de type ICMP suivantes sont disponibles : icmp-echoreply, icmp-unreach, icmp-sourcequench, icmp-redirect, icmp-echo, icmp-routeradvert, icmp-routersolicit, icmp-timxceed, icmp-paramprob, icmp-tstamp, icmp-tstampreply, icmp-ireq, icmp-ireqreply, icmp-maskreq, icmp-maskreply.
Les valeurs de champ de type ICMPv6 suivantes sont disponibles : icmp6-destinationunreach, icmp6-packettoobig, icmp6-timeexceeded, icmp6-parameterproblem, icmp6-echo, icmp6-echoreply, icmp6-multicastlistenerquery, icmp6-multicastlistenerreportv1, icmp6-multicastlistenerdone, icmp6-routersolicit, icmp6-routeradvert, icmp6-neighborsolicit, icmp6-neighboradvert, icmp6-redirect, icmp6-routerrenum, icmp6-nodeinformationquery, icmp6-nodeinformationresponse, icmp6-ineighbordiscoverysolicit, icmp6-ineighbordiscoveryadvert, icmp6-multicastlistenerreportv2, icmp6-homeagentdiscoveryrequest, icmp6-homeagentdiscoveryreply, icmp6-mobileprefixsolicit, icmp6-mobileprefixadvert, icmp6-certpathsolicit, icmp6-certpathadvert, icmp6-multicastrouteradvert, icmp6-multicastroutersolicit, icmp6-multicastrouterterm.
Les valeurs de champ de drapeaux TCP suivantes sont disponibles : tcp-fin, tcp-syn, tcp-rst, tcp-push, tcp-ack, tcp-urg, tcp-ece, tcp-cwr.

Les primitives peuvent être combinées en utilisant :

Un groupe entre parenthèses de primitives et d'opérateurs.
Négation (`!' ou `not').
Concaténation (`&&' ou `and').
Alternative (`||' ou `or').

La négation a la priorité la plus élevée. L'alternative et la concaténation ont la même priorité et s'associent de gauche à droite.

Si un identifiant est donné sans mot-clé, le mot-clé le plus récent est supposé. Par exemple, 

not host vs and ace
est une abréviation pour 
not host vs and host ace
ce qui ne doit pas être confondu avec 
not (host vs or ace)

NOM

pcap-filter — syntaxe des expressions de filtre de paquets

DESCRIPTION

Ce document décrit la syntaxe des expressions de filtre utilisées par tcpdump et par les applications qui utilisent la bibliothèque libpcap.

Les expressions de filtre sont composées de divers opérateurs, prédicats, et expressions arithmétiques. Les prédicats peuvent être le nom d'une constante (par exemple, magic) ou une expression arithmétique. Les opérateurs peuvent être logiques (and, or, not), relationnels (==, !=, >, >=, <, <=), arithmétiques (+, -, *, /) ou des opérations sur les bits (&, |).

Les expressions peuvent être regroupées entre parenthèses pour contrôler l'ordre d'évaluation.

Les identificateurs et les noms de types sont insensibles à la casse.

Les noms de types, de protocoles et de ports peuvent être représentés par des noms ou des nombres entiers. Par exemple, `icmp' est équivalent à `(proto icmp)'. `tcp port 53' est équivalent à `(proto tcp and port 53)'.

Les valeurs entières peuvent être spécifiées en notation décimale, hexadécimale (avec le préfixe 0x) ou octale (avec le préfixe 0).

Les filtres sont évalués de droite à gauche. Par exemple, `a | b & c' est interprété comme `a | (b & c)'.

Il existe plusieurs types de prédicats:

  • Type: ether, fddi, tr, wlan, ip, ip6, arp, rarp, decnet, tcp, udp, icmp, icmp6, pio, pppoe, ppp, slip, cooked, link, etherip, mux, snmp, atm, bluetooth, rx, net, eon, ipnip, ldp, mtp, pgm, q931, sctp, sunrpc, tcpdump, vlan, genve. Ces prédicats sélectionnent les paquets appartenant à un type de réseau spécifique. Par exemple, `ether' sélectionne les paquets Ethernet.
  • Direction: src, dst, src or dst, src and dst. Ces prédicats sélectionnent les paquets dont la source ou la destination correspond à un critère donné. Par exemple, `src host 1.2.3.4' sélectionne les paquets dont la source est 1.2.3.4.
  • Host: host. Ce prédicat sélectionne les paquets dont l'expéditeur ou le destinataire est un hôte donné. Par exemple, `host 1.2.3.4' sélectionne les paquets où l'adresse source ou destination est 1.2.3.4.
  • Réseau: net. Ce prédicat sélectionne les paquets dont la source ou la destination appartient à un réseau donné. Par exemple, `net 128.0.0.0/8' sélectionne les paquets où l'adresse source ou destination est dans le réseau 128.0.0.0/8.
  • Port: port. Ce prédicat sélectionne les paquets dont la source ou la destination est un port donné. Par exemple, `port ssh' sélectionne les paquets où le port source ou destination est 22.
  • Gateway: gateway. Ce prédicat sélectionne les paquets dont la passerelle est celle spécifiée. Par exemple, `gateway router' sélectionne les paquets dont la passerelle est `router'.
  • Ethertype: ether proto. Ce prédicat sélectionne les paquets dont l'Ethertype est celui spécifié. Par exemple, `ether proto 0x806' sélectionne les paquets ARP.
  • Protocole IP: ip proto. Ce prédicat sélectionne les paquets IP dont le protocole est celui spécifié. Par exemple, `ip proto 6' sélectionne les paquets TCP.
  • TCP flags: tcp[tcpflags]. Ce prédicat sélectionne les paquets TCP dont les flags spécifiés sont définis. Par exemple, `tcp[tcpflags] & tcp-syn != 0' sélectionne les paquets SYN.
  • Taille des paquets: len. Ce prédicat sélectionne les paquets dont la taille est inférieure ou supérieure à la valeur spécifiée. Par exemple, `len > 100' sélectionne les paquets de plus de 100 octets.
  • Index d'interface: ifindex. Ce prédicat sélectionne les paquets qui sont arrivés ou ont été envoyés sur l'interface spécifiée par son index. Par exemple, `ifindex 2' sélectionne les paquets sur l'interface avec l'index 2.

EXEMPLES

Pour sélectionner tous les paquets entre `ace' et `helios':

host ace and host helios

Pour sélectionner tous les paquets entre `helios' et l'un des hôtes `hot' ou `ace':

host helios and (hot or ace)

Pour sélectionner tous les paquets IPv4 entre `ace' et tout hôte sauf `helios':

ip host ace and not helios

Pour sélectionner tout le trafic entre les hôtes locaux et les hôtes de Berkeley:

net ucb-ether

Pour sélectionner tout le trafic FTP passant par la passerelle Internet `snup':

gateway snup and (port ftp or ftp-data)

Pour sélectionner le trafic IPv4 qui n'est ni émis ni reçu par les hôtes locaux (si vous passez par un autre réseau, ces paquets ne devraient jamais arriver sur votre réseau local).

ip and not net localnet

Pour sélectionner les paquets de début et de fin (les paquets SYN et FIN) de chaque conversation TCP impliquant un hôte non local.

tcp[tcpflags] & (tcp-syn|tcp-fin) != 0 and not src and dst net localnet

Pour sélectionner les paquets TCP avec les flags RST et ACK définis. (c'est-à-dire, sélectionner uniquement les flags RST et ACK dans le champ des flags, et si le résultat est "RST et ACK tous deux définis", alors faire correspondre)


tcp[tcpflags] & (tcp-rst|tcp-ack) == (tcp-rst|tcp-ack)

Pour sélectionner tous les paquets HTTP IPv4 vers et depuis le port 80, c'est-à-dire, n'afficher que les paquets contenant des données, et non, par exemple, les paquets SYN et FIN, ni les paquets ACK uniquement. (IPv6 est laissé en exercice pour le lecteur.)

tcp port 80 and (((ip[2:2] - ((ip[0]&0xf)<<2)) - ((tcp[12]&0xf0)>>2)) != 0)

Pour sélectionner les paquets IPv4 de plus de 576 octets envoyés via la passerelle `snup':

gateway snup and ip[2:2] > 576

Pour sélectionner les paquets de broadcast ou multicast IPv4 qui n'ont *pas* été envoyés via broadcast ou multicast Ethernet:

ether[0] & 1 = 0 and ip[16] >= 224

Pour sélectionner tous les paquets ICMP qui ne sont pas des requêtes/réponses d'écho (c'est-à-dire, pas des paquets ping):


icmp[icmptype] != icmp-echo and icmp[icmptype] != icmp-echoreply

icmp6[icmp6type] != icmp6-echo and icmp6[icmp6type] != icmp6-echoreply

COMPATIBILITE ASCENDANTE

Les noms de types de code ICMPv6, ainsi que les noms de flags TCP tcp-ece et tcp-cwr sont disponibles depuis libpcap 1.9.0.

Le mot-clé geneve est disponible depuis libpcap 1.8.0.

Le mot-clé ifindex est disponible depuis libpcap 1.10.0.

BOGUES

Pour signaler un problème de sécurité, veuillez envoyer un e-mail à security@tcpdump.org.

Pour signaler des bogues et d'autres problèmes, contribuer des correctifs, demander une fonctionnalité, fournir des commentaires généraux, etc., veuillez consulter le fichier CONTRIBUTING.md à la racine de l'arborescence source de libpcap.

Les expressions de filtre sur des champs autres que ceux des en-têtes Token Ring ne géreront pas correctement les paquets Token Ring routés par source.

Les expressions de filtre sur des champs autres que ceux des en-têtes 802.11 ne géreront pas correctement les paquets de données 802.11 avec les bits To DS et From DS tous deux définis.

`ip6 proto' devrait suivre la chaîne d'en-têtes, mais ce n'est pas le cas actuellement. `ip6 protochain' est fourni pour ce comportement. Par exemple, pour faire correspondre les fragments IPv6 : `ip6 protochain 44'

Les expressions arithmétiques sur les en-têtes de couche transport, comme tcp[0], ne fonctionnent pas sur les paquets IPv6. Elles ne regardent que les paquets IPv4.
