NOM

PCRE2 - Expressions régulières compatibles Perl (API révisée)

PCRE2 PERFORMANCE

Deux aspects de la performance sont discutés ci-dessous : l'utilisation de la mémoire et le temps de traitement. La manière dont vous exprimez votre modèle en tant qu'expression régulière peut affecter les deux.

UTILISATION MÉMOIRE MODÈLE COMPILÉ

Les modèles sont compilés par PCRE2 en un code interprétatif raisonnablement efficace, de sorte que la plupart des modèles simples n'utilisent pas beaucoup de mémoire pour stocker la version compilée. Cependant, il existe un cas où l'utilisation de la mémoire d'un modèle compilé peut être inattendument grande. Si un groupe entre parenthèses a un quantificateur avec un minimum supérieur à 1 et/ou un maximum limité, tout le groupe est répété dans le code compilé. Par exemple, le modèle


(abc|def){2,4}

est compilé comme s'il était


(abc|def)(abc|def)((abc|def)(abc|def)?)?

(Note technique : C'est fait ainsi afin que les points de retour en arrière au sein de chacune des répétitions puissent être maintenus indépendamment.)

Pour les expressions régulières dont les quantificateurs n'utilisent que de petits nombres, ce n'est généralement pas un problème. Cependant, si les nombres sont grands, et particulièrement si de telles répétitions sont imbriquées, l'utilisation de la mémoire peut devenir embarrassante. Par exemple, le modèle très simple


((ab){1,1000}c){1,3}

utilise plus de 50 Ko lorsqu'il est compilé avec la bibliothèque 8 bits. Lorsque PCRE2 est compilé avec sa taille de pointeur interne par défaut de deux octets, la limite de taille d'un modèle compilé est de 65535 unités de code dans les bibliothèques 8 bits et 16 bits, et celle-ci est atteinte avec le modèle ci-dessus si la répétition externe est augmentée de 3 à 4. PCRE2 peut être compilé pour utiliser des pointeurs internes plus grands et ainsi gérer des modèles compilés plus grands, mais il est préférable d'essayer de réécrire votre modèle pour utiliser moins de mémoire si vous le pouvez.

Une façon de réduire l'utilisation de la mémoire pour de tels modèles est d'utiliser la fonction « sous-routine » de PCRE2. Réécrire le modèle ci-dessus comme


((ab)(?2){0,999}c)(?1){0,2}

réduit les besoins en mémoire à environ 16 Ko, et elle reste en fait inférieure à 20 Ko même avec la répétition externe augmentée à 100. Cependant, ce type de modèle n'est pas toujours exactement équivalent, car toutes les captures à l'intérieur des appels de sous-routine sont perdues lorsque la sous-routine se termine. Si cela n'est pas un problème, ce type de réécriture vous permettra de traiter des modèles que PCRE2 ne peut pas autrement gérer. La performance de correspondance des deux versions différentes du modèle est à peu près la même. (Ceci s'applique à partir de la version 10.30 - les choses étaient différentes dans les versions antérieures.)

UTILISATION PILE ET TAS À L'EXÉCUTION

À partir de la version 10.30, la version interprétative (non-JIT) de pcre2_match() utilise très peu de pile système à l'exécution. Dans les versions antérieures, les appels de fonctions récursifs pouvaient utiliser une grande quantité de pile, ce qui pouvait causer des problèmes, mais cette utilisation a été éliminée. Les positions de retour arrière sont maintenant explicitement mémorisées dans des cadres de mémoire contrôlés par le code.

La taille de chaque cadre dépend de la taille des variables pointeurs et du nombre de groupes capturants entre parenthèses dans le modèle en cours de correspondance. Sur un système 64 bits, la taille du cadre pour un modèle sans captures est de 128 octets. Pour chaque groupe capturant, la taille augmente de 16 octets.

Jusqu'à la version 10.41, un vecteur initial de 20 Ko de cadres était alloué sur la pile système, mais cela causait encore quelques problèmes pour les applications multi-thread où chaque thread a une pile très petite. À partir de la version 10.41, les cadres de mémoire de retour arrière sont toujours maintenus dans la mémoire du tas. Une allocation initiale de tas est obtenue la première fois qu'un bloc de données de correspondance est passé à pcre2_match(). Ceci est mémorisé avec le bloc de données de correspondance et réutilisé si ce bloc est utilisé pour une autre correspondance. Il est libéré lorsque le bloc de données de correspondance lui-même est libéré.

La taille du bloc initial est la plus grande des valeurs suivantes : 20 Ko ou dix fois la taille du cadre du modèle, sauf si la limite du tas est inférieure à cela, auquel cas la limite du tas est utilisée. Si le bloc initial s'avère trop petit pendant la correspondance, il est remplacé par un bloc plus grand, sous réserve de la limite du tas. La limite du tas n'est vérifiée que lorsqu'un nouveau bloc doit être alloué. La réduction de la limite du tas entre les appels à pcre2_match() avec le même bloc de données de correspondance n'affecte pas le bloc sauvegardé.

Contrairement à pcre2_match(), pcre2_dfa_match() utilise des appels de fonctions récursifs, mais uniquement pour le traitement des groupes atomiques, des assertions de lookaround, et de la récursion dans le modèle. La version originale du code allouait des vecteurs de travail internes assez grands sur la pile, ce qui causait des problèmes pour certains modèles dans des environnements avec de petites piles. À partir de la version 10.32, le code de pcre2_dfa_match() a été refactorisé pour utiliser la mémoire du tas si nécessaire pour le travail interne lors de la récursion, bien que les appels de fonctions récursifs soient toujours utilisés.

Le paramètre « profondeur de correspondance » peut être utilisé pour limiter la profondeur de la récursion des fonctions, et le paramètre « tas de correspondance » pour limiter la mémoire du tas dans pcre2_dfa_match().

TEMPS DE TRAITEMENT

Certains éléments dans les expressions régulières sont traités plus efficacement que d'autres. Il est plus efficace d'utiliser une classe de caractères comme [aeiou] qu'un ensemble d'alternatives de caractères uniques comme (a|e|i|o|u). En général, la construction la plus simple qui fournit le comportement requis est généralement la plus efficace. Le livre de Jeffrey Friedl contient beaucoup de discussions générales utiles sur l'optimisation des expressions régulières pour une performance efficace. Ce document contient quelques observations sur PCRE2.

L'utilisation des propriétés de caractères Unicode (les échappements \p, \P et \X) est lente, car PCRE2 doit utiliser une recherche dans une table en plusieurs étapes chaque fois qu'il a besoin de la propriété d'un caractère. Si vous pouvez trouver un modèle alternatif qui n'utilise pas de propriétés de caractères, il sera probablement plus rapide.

Par défaut, les séquences d'échappement \b, \d, \s et \w, ainsi que les classes de caractères POSIX comme [:alpha:] n'utilisent pas les propriétés Unicode, en partie pour des raisons de compatibilité ascendante et en partie pour des raisons de performance. Cependant, vous pouvez définir l'option PCRE2_UCP ou commencer le modèle par (*UCP) si vous souhaitez que les propriétés de caractères Unicode soient utilisées. Cela peut doubler le temps de correspondance pour des éléments comme \d, lorsqu'il est comparé avec pcre2_match() ; la perte de performance est moindre avec une fonction de correspondance DFA, et dans les deux cas, il n'y a pas beaucoup de différence pour \b.

Lorsqu'un modèle commence par .* non contenu dans des parenthèses atomiques, ni dans des parenthèses qui font l'objet d'une référence arrière, et que l'option PCRE2_DOTALL est définie, le modèle est implicitement ancré par PCRE2, car il ne peut correspondre qu'au début d'une chaîne sujet. Si le modèle a plusieurs branches de haut niveau, elles doivent toutes être ancrables. L'optimisation peut être désactivée par l'option PCRE2_NO_DOTSTAR_ANCHOR, et elle est automatiquement désactivée si le modèle contient (*PRUNE) ou (*SKIP).

Si PCRE2_DOTALL n'est pas défini, PCRE2 ne peut pas effectuer cette optimisation, car le métacaractère point ne correspond pas à un saut de ligne, et si la chaîne sujet contient des sauts de ligne, le modèle peut correspondre à partir du caractère immédiatement après l'un d'eux au lieu de tout début. Par exemple, le modèle


.*second

correspond au sujet « first\nand second » (où \n représente un caractère de saut de ligne), la correspondance commençant au septième caractère. Pour ce faire, PCRE2 doit réessayer la correspondance en commençant après chaque saut de ligne dans le sujet.

Si vous utilisez un tel modèle avec des chaînes sujet qui ne contiennent pas de sauts de ligne, la meilleure performance est obtenue en définissant PCRE2_DOTALL, ou en commençant le modèle par ^.* ou ^.*? pour indiquer un ancrage explicite. Cela évite à PCRE2 de devoir parcourir le sujet à la recherche d'un saut de ligne pour redémarrer.

Méfiez-vous des modèles qui contiennent des répétitions indéfinies imbriquées. Celles-ci peuvent prendre beaucoup de temps à s'exécuter lorsqu'elles sont appliquées à une chaîne qui ne correspond pas. Considérez le fragment de modèle


^(a+)*

Cela peut correspondre à « aaaa » de 16 manières différentes, et ce nombre augmente très rapidement à mesure que la chaîne s'allonge. (La répétition * peut correspondre 0, 1, 2, 3 ou 4 fois, et pour chacun de ces cas sauf 0 ou 4, les répétitions + peuvent correspondre à différents nombres de fois.) Lorsque le reste du modèle est tel que la correspondance entière va échouer, PCRE2 doit en principe essayer chaque variation possible, et cela peut prendre un temps extrêmement long, même pour des chaînes relativement courtes.

NOM

pcre2perform - PCRE2 performance considerations

PERFORMANCE DE PCRE2

This document describes some aspects of PCRE2 performance.

OPTIMISATION DE LA VITESSE DE CORRESPONDANCE

PCRE2 has a number of internal optimizations that help to speed up matching. However, there are times when a particular pattern may run slowly, and it is useful to understand why this happens, and how to avoid it.

An optimization catches some of the more simple cases such as


(a+)*b

where a literal character follows. Before embarking on the standard matching procedure, PCRE2 checks that there is a "b" later in the subject string, and if there is not, it fails the match immediately. However, when there is no following literal this optimization cannot be used. You can see the difference by comparing the behaviour of


(a+)*\d

with the pattern above. The former gives a failure almost instantly when applied to a whole line of "a" characters, whereas the latter takes an appreciable time with strings longer than about 20 characters.

In many cases, the solution to this kind of performance issue is to use an atomic group or a possessive quantifier. This can often reduce memory requirements as well. As another example, consider this pattern:


([^<]|<(?!inet))+

It matches from wherever it starts until it encounters "<inet" or the end of the data, and is the kind of pattern that might be used when processing an XML file. Each iteration of the outer parentheses matches either one character that is not "<" or a "<" that is not followed by "inet". However, each time a parenthesis is processed, a backtracking position is passed, so this formulation uses a memory frame for each matched character. For a long string, a lot of memory is required. Consider now this rewritten pattern, which matches exactly the same strings:


([^<]++|<(?!inet))+

This runs much faster, because sequences of characters that do not contain "<" are "swallowed" in one item inside the parentheses, and a possessive quantifier is used to stop any backtracking into the runs of non-"<" characters. This version also uses a lot less memory because entry to a new set of parentheses happens only when a "<" character that is not followed by "inet" is encountered (and we assume this is relatively rare).

This example shows that one way of optimizing performance when matching long subject strings is to write repeated parenthesized subpatterns to match more than one character whenever possible.

DÉFINITION DES LIMITES DE RESSOURCES

You can set limits on the amount of processing that takes place when matching, and on the amount of heap memory that is used. The default values of the limits are very large, and unlikely ever to operate. They can be changed when PCRE2 is built, and they can also be set when pcre2_match() or pcre2_dfa_match() is called. For details of these interfaces, see the pcre2build documentation and the section entitled "The match context" in the pcre2api documentation.

The pcre2test test program has a modifier called "find_limits" which, if applied to a subject line, causes it to find the smallest limits that allow a pattern to match. This is done by repeatedly matching with different limits.
