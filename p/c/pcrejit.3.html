NOM

PCRE - Expressions régulières compatibles Perl

SUPPORT DU COMPILATEUR JUST-IN-TIME PCRE

La compilation juste-à-temps (JIT) est une optimisation lourde qui peut accélérer considérablement la correspondance de motifs. Cependant, elle entraîne un traitement supplémentaire avant que la correspondance ne soit effectuée. Par conséquent, elle est plus bénéfique lorsque le même motif doit être recherché plusieurs fois. Cela ne signifie pas nécessairement de nombreux appels à une fonction de correspondance ; si le motif n'est pas ancré, les tentatives de correspondance peuvent avoir lieu de nombreuses fois à diverses positions dans le sujet, même pour un seul appel. Par conséquent, si la chaîne de sujet est très longue, il peut toujours être utile d'utiliser le JIT pour des correspondances uniques.

Le support JIT ne s'applique qu'à la fonction de correspondance traditionnelle compatible avec Perl. Il ne s'applique pas lorsque la fonction de correspondance DFA est utilisée. Le code pour ce support a été écrit par Zoltan Herczeg.

SUPPORT 8-BIT, 16-BIT ET 32-BIT

Le support JIT est disponible pour toutes les bibliothèques PCRE 8 bits, 16 bits et 32 bits. Pour simplifier cette documentation, seule l'interface 8 bits est décrite ci-après. Si vous utilisez la bibliothèque 16 bits, remplacez les fonctions 16 bits et les structures 16 bits (par exemple, pcre16_jit_stack au lieu de pcre_jit_stack). Si vous utilisez la bibliothèque 32 bits, remplacez les fonctions 32 bits et les structures 32 bits (par exemple, pcre32_jit_stack au lieu de pcre_jit_stack).

DISPONIBILITÉ DU SUPPORT JIT

Le support JIT est une fonctionnalité optionnelle de PCRE. L'option de configuration --enable-jit (ou l'option CMake équivalente) doit être définie lors de la compilation de PCRE si vous souhaitez utiliser le JIT. Le support est limité aux plateformes matérielles suivantes :


ARM v5, v7 et Thumb2
Intel x86 32 bits et 64 bits
MIPS 32 bits
Power PC 32 bits et 64 bits
SPARC 32 bits (expérimental)

Si --enable-jit est défini sur une plateforme non prise en charge, la compilation échoue.

Un programme lié à PCRE 8.20 ou ultérieur peut vérifier si le support JIT est disponible en appelant pcre_config() avec l'option PCRE_CONFIG_JIT. Le résultat est 1 lorsque le JIT est disponible, et 0 sinon. Cependant, un programme simple n'a pas besoin de vérifier cela pour utiliser le JIT. L'API normale est implémentée de manière à revenir au code interprétatif si le JIT n'est pas disponible. Pour les programmes qui nécessitent les meilleures performances possibles, il existe également une API "fast path" spécifique au JIT.

Si votre programme peut parfois être lié à des versions de PCRE antérieures à 8.20, mais que vous souhaitez utiliser le JIT lorsqu'il est disponible, vous pouvez tester les valeurs de PCRE_MAJOR et PCRE_MINOR, ou l'existence d'une macro JIT telle que PCRE_CONFIG_JIT, pour un contrôle du temps de compilation de votre code. Attention également, la fonction pcre_jit_exec() n'était pas du tout disponible avant la version 8.32, et peut ne pas être du tout disponible si PCRE n'est pas compilé avec --enable-jit. Voir la section "API JIT FAST PATH" ci-dessous pour plus de détails.

UTILISATION SIMPLE DU JIT

Vous devez faire deux choses pour utiliser le support JIT de la manière la plus simple :


(1) Appeler pcre_study() avec l'option PCRE_STUDY_JIT_COMPILE pour
chaque motif compilé, et passer le bloc pcre_extra résultant à
pcre_exec().


(2) Utiliser pcre_free_study() pour libérer le bloc pcre_extra lorsqu'il
n'est plus nécessaire, au lieu de le libérer vous-même. Cela garantit que
toutes les données JIT sont également libérées.

Pour un programme qui peut être lié à des versions de PCRE antérieures à 8.20, vous pouvez insérer


#ifndef PCRE_STUDY_JIT_COMPILE
#define PCRE_STUDY_JIT_COMPILE 0
#endif

afin qu'aucune option ne soit passée à pcre_study(), puis utiliser quelque chose comme ceci pour libérer les données d'étude :


#ifdef PCRE_CONFIG_JIT
pcre_free_study(study_ptr);
#else
pcre_free(study_ptr);
#endif

PCRE_STUDY_JIT_COMPILE demande au compilateur JIT de générer du code pour des correspondances complètes. Si vous souhaitez exécuter des correspondances partielles à l'aide des options PCRE_PARTIAL_HARD ou PCRE_PARTIAL_SOFT de pcre_exec(), vous devez définir une ou les deux options suivantes en plus, ou à la place, de PCRE_STUDY_JIT_COMPILE lors de l'appel à pcre_study() :


PCRE_STUDY_JIT_PARTIAL_HARD_COMPILE
PCRE_STUDY_JIT_PARTIAL_SOFT_COMPILE

Si vous utilisez pcre_jit_exec() et supportez une version de PCRE antérieure à 8.32, vous pouvez insérer :


#if PCRE_MAJOR >= 8 && PCRE_MINOR >= 32
pcre_jit_exec(...);
#else
pcre_exec(...)
#endif

mais comme décrit dans la section "API JIT FAST PATH" ci-dessous, cela suppose que les versions 8.32 et ultérieures sont compilées avec --enable-jit, ce qui peut poser problème.

Le compilateur JIT génère différents codes optimisés pour chacun des trois modes (normal, partiel soft, partiel hard). Lorsque pcre_exec() est appelé, le code approprié est exécuté s'il est disponible. Sinon, le motif est recherché en utilisant le code interprétatif.

Dans certaines circonstances, vous devrez peut-être appeler des fonctions supplémentaires. Celles-ci sont décrites dans la section "Contrôle de la pile JIT" ci-dessous.

Si le support JIT n'est pas disponible, PCRE_STUDY_JIT_COMPILE etc. sont ignorés, et aucune donnée JIT n'est créée. Sinon, le motif compilé est passé au compilateur JIT, qui le transforme en code machine qui s'exécute beaucoup plus rapidement que le code interprétatif normal. Lorsque pcre_exec() reçoit un bloc pcre_extra contenant un pointeur vers du code JIT du mode approprié (normal ou partiel hard/soft), il respecte ce code au lieu d'exécuter l'interpréteur. Le résultat est identique, mais le code JIT compilé s'exécute beaucoup plus rapidement.

Il existe certaines options de pcre_exec() qui ne sont pas prises en charge pour l'exécution JIT. Il existe également certains éléments de motif que le JIT ne peut pas gérer. Les détails sont donnés ci-dessous. Dans les deux cas, l'exécution revient automatiquement au code interprétatif. Si vous souhaitez savoir si le JIT a réellement été utilisé pour une correspondance particulière, vous devez organiser la configuration d'une fonction de rappel JIT comme décrit dans la section "Contrôle de la pile JIT" ci-dessous, même si vous n'avez pas besoin de fournir une pile JIT non par défaut. Une telle fonction de rappel est appelée chaque fois que le code JIT est sur le point d'être exécuté. Si les options d'exécution ne sont pas appropriées pour l'exécution JIT, la fonction de rappel n'est pas exécutée.

Si le compilateur JIT rencontre un élément non pris en charge, aucune donnée JIT n'est générée. Vous pouvez savoir si l'exécution JIT est disponible après avoir étudié un motif en appelant pcre_fullinfo() avec l'option PCRE_INFO_JIT. Un résultat de 1 signifie que la compilation JIT a réussi. Un résultat de 0 signifie que le support JIT n'est pas disponible, ou que le motif n'a pas été étudié avec PCRE_STUDY_JIT_COMPILE etc., ou que le compilateur JIT n'a pas pu gérer le motif.

Une fois qu'un motif a été étudié, avec ou sans JIT, il peut être utilisé autant de fois que vous le souhaitez pour rechercher différentes chaînes de sujet.

OPTIONS ET ÉLÉMENTS DE MOTIFS NON PRIS EN CHARGE

Les seules options de pcre_exec() prises en charge pour l'exécution JIT sont PCRE_NO_UTF8_CHECK, PCRE_NO_UTF16_CHECK, PCRE_NO_UTF32_CHECK, PCRE_NOTBOL, PCRE_NOTEOL, PCRE_NOTEMPTY, PCRE_NOTEMPTY_ATSTART, PCRE_PARTIAL_HARD et PCRE_PARTIAL_SOFT.

Les seuls éléments de motif non pris en charge sont \C (correspondre à une seule unité de données) lors de l'exécution en mode UTF, et un appel juste avant une condition d'assertion dans un groupe conditionnel.

VALEURS DE RETOUR DE L'EXÉCUTION JIT

Lorsqu'un motif est recherché à l'aide de l'exécution JIT, les valeurs de retour sont les mêmes que celles fournies par le code interprétatif de pcre_exec(), avec l'ajout d'un nouveau code d'erreur : PCRE_ERROR_JIT_STACKLIMIT. Cela signifie que la mémoire utilisée pour la pile JIT était insuffisante. Voir "Contrôle de la pile JIT" ci-dessous pour une discussion sur l'utilisation de la pile JIT. Pour la compatibilité avec le code interprétatif de pcre_exec(), pas plus des deux tiers de l'argument ovector n'est utilisé pour renvoyer les sous-chaînes capturées.

Le code d'erreur PCRE_ERROR_MATCHLIMIT est retourné par le J

IT code si la recherche dans un arbre de motifs très volumineux se prolonge trop, comme c'est le cas dans la même situation lorsque le JIT n'est pas utilisé, mais les détails de ce qui est compté exactement ne sont pas les mêmes. Le code d'erreur PCRE_ERROR_RECURSIONLIMIT n'est jamais retourné par l'exécution JIT.

SAUVEGARDE ET RESTAURATION DES MOTIFS COMPILÉS

Le code généré par le compilateur JIT est spécifique à l'architecture et dépend également de la position. Pour ces raisons, il ne peut pas être sauvegardé (dans un fichier ou une base de données) et restauré plus tard comme le bytecode et d'autres données d'un motif compilé. La sauvegarde et la restauration des motifs compilés ne sont pas quelque chose que beaucoup de gens font. Plus de détails sur cette fonctionnalité sont donnés dans la documentation pcreprecompile. Il devrait être possible d'exécuter pcre_study() sur un motif sauvegardé et restauré, et ainsi recréer les données JIT, mais comme la compilation JIT utilise des ressources importantes, il n'en vaut probablement pas la peine; autant recompiler le motif original.

CONTRÔLE DE LA PILE JIT

Lorsque le code JIT compilé s'exécute, il a besoin d'un bloc de mémoire pour l'utiliser comme pile. Par défaut, il utilise 32 Ko sur la pile machine. Cependant, certains motifs volumineux ou compliqués nécessitent plus que cela. L'erreur PCRE_ERROR_JIT_STACKLIMIT est signalée lorsqu'il n'y a pas assez de pile. Trois fonctions sont fournies pour gérer les blocs de mémoire à utiliser comme piles JIT. Il y a une discussion plus approfondie sur l'utilisation des piles JIT dans la section intitulée "FAQ sur la pile JIT" ci-dessous.

La fonction pcre_jit_stack_alloc() crée une pile JIT. Ses arguments sont une taille de départ et une taille maximale, et elle retourne un pointeur vers une structure opaque de type pcre_jit_stack, ou NULL en cas d'erreur. La fonction pcre_jit_stack_free() peut être utilisée pour libérer une pile qui n'est plus nécessaire. (Pour les techniciens: l'espace d'adressage est alloué par mmap ou VirtualAlloc.)

Le JIT utilise beaucoup moins de mémoire pour la récursion que le code interprétatif, et une taille de pile maximale de 512 Ko à 1 Mo devrait être plus que suffisante pour n'importe quel motif.

La fonction pcre_assign_jit_stack() spécifie quelle pile le code JIT doit utiliser. Ses arguments sont les suivants:


pcre_extra *extra
pcre_jit_callback callback
void *data

L'argument extra doit être le résultat de l'étude d'un motif avec PCRE_STUDY_JIT_COMPILE etc. Il existe trois cas pour les valeurs des deux autres options:


(1) Si callback est NULL et data est NULL, un bloc interne de 32 Ko
sur la pile machine est utilisé.


(2) Si callback est NULL et data n'est pas NULL, data doit être
une pile JIT valide, le résultat de l'appel à pcre_jit_stack_alloc().


(3) Si callback n'est pas NULL, il doit pointer vers une fonction qui est
appelée avec data comme argument au début de la correspondance, afin
de configurer une pile JIT. Si le retour de la fonction de rappel
est NULL, la pile interne de 32 Ko est utilisée; sinon, le
retour doit être une pile JIT valide, le résultat de l'appel à
pcre_jit_stack_alloc().

Une fonction de rappel est respectée chaque fois que le code JIT est sur le point d'être exécuté; elle n'est pas respectée lorsque pcre_exec() est appelée avec des options incompatibles pour l'exécution JIT. Une fonction de rappel peut donc être utilisée pour déterminer si une opération de correspondance a été exécutée par JIT ou par l'interpréteur.

Vous pouvez utiliser en toute sécurité la même pile JIT pour plus d'un motif (soit en l'assignant directement, soit par rappel), tant que les motifs sont tous mis en correspondance séquentiellement dans le même thread. Dans une application multithread, si vous ne spécifiez pas de pile JIT, ou si vous assignez ou retournez NULL à partir d'un rappel, cela est thread-safe, car chaque thread a sa propre pile machine. Cependant, si vous assignez ou retournez une pile JIT non nulle, cela doit être une pile différente pour chaque thread afin que l'application soit thread-safe.

Strictement parlant, même plus est autorisé. Vous pouvez assigner la même pile non nulle à un nombre quelconque de motifs tant qu'ils ne sont pas utilisés pour la correspondance par plusieurs threads simultanément. Par exemple, vous pouvez assigner la même pile à tous les motifs compilés, et utiliser un mutex global dans le rappel pour attendre que la pile soit disponible. Cependant, c'est une solution inefficace et non recommandée.

Voici une suggestion sur la façon dont un programme multithread qui doit configurer des piles JIT non par défaut pourrait fonctionner:


Lors de l'initialisation du thread
variable_locale_au_thread = pcre_jit_stack_alloc(...)


Lors de la sortie du thread
pcre_jit_stack_free(variable_locale_au_thread)


Utiliser une fonction de rappel d'une seule ligne
retourner variable_locale_au_thread

Toutes les fonctions décrites dans cette section ne font rien si le JIT n'est pas disponible, et pcre_assign_jit_stack() ne fait rien sauf si l'argument extra n'est pas NULL et pointe vers un bloc pcre_extra qui est le résultat d'une étude réussie avec PCRE_STUDY_JIT_COMPILE etc.

FAQ SUR LA PILE JIT

(1) Pourquoi avons-nous besoin de piles JIT?

PCRE (et JIT) est un moteur récursif en profondeur, il a donc besoin d'une pile où les données locales du nœud actuel sont empilées avant de vérifier ses nœuds enfants. L'allocation d'une pile machine réelle sur certaines plates-formes est difficile. Par exemple, la chaîne de piles doit être mise à jour à chaque fois si nous étendons la pile sur PowerPC. Bien que ce soit possible, le surcoût de temps de mise à jour diminue les performances. Nous effectuons donc la récursion en mémoire.

(2) Pourquoi ne pas simplement allouer des blocs de mémoire avec malloc()?

Les systèmes d'exploitation modernes ont une fonctionnalité intéressante: ils peuvent réserver un espace d'adressage au lieu d'allouer de la mémoire. Nous pouvons allouer en toute sécurité des pages de mémoire à l'intérieur de cet espace d'adressage, de sorte que la pile puisse croître sans déplacer les données mémoire (ce qui est important en raison des pointeurs). Ainsi, nous pouvons allouer un espace d'adressage de 1 Mo, et n'utiliser qu'une seule page mémoire (généralement 4 Ko) si cela suffit. Cependant, nous pouvons toujours croître jusqu'à 1 Mo à tout moment si nécessaire.

(3) Qui "possède" une pile JIT?

Le propriétaire de la pile est le programme utilisateur, pas le motif étudié par JIT ou quoi que ce soit d'autre. Le programme utilisateur doit s'assurer que si une pile est utilisée par pcre_exec() (c'est-à-dire qu'elle est assignée au motif en cours d'exécution), cette pile ne doit pas être utilisée par d'autres threads (pour éviter d'écraser la même zone mémoire). La meilleure pratique pour les programmes multithread est d'allouer une pile pour chaque thread, et de retourner cette pile via la fonction de rappel JIT.

(4) Quand une pile JIT doit-elle être libérée?

Vous pouvez libérer une pile JIT à tout moment, tant qu'elle ne sera plus utilisée par pcre_exec(). Lorsque vous assignez la pile à un motif, seul un pointeur est défini. Il n'y a pas de comptage de références ni d'autre magie. Vous pouvez libérer les motifs et les piles dans n'importe quel ordre, à tout moment. Il suffit de *ne pas* appeler pcre_exec() avec un motif pointant vers une pile déjà libérée, car cela provoquerait un SEGFAULT. (De plus, ne libérez pas une pile actuellement utilisée par pcre_exec() dans un autre thread). Vous pouvez également remplacer la pile d'un motif à tout moment. Vous pouvez même libérer la pile précédente avant d'en assigner une de remplacement.

(5) Dois-je allouer/libérer une pile à chaque fois avant/après avoir appelé pcre_exec()?

Non, car c'est trop coûteux en termes de ressources. Cependant, vous pourriez implémenter une idée astucieuse qui libère la pile si elle n'est pas utilisée pendant, disons, deux minutes. Le rappel JIT peut aider à y parvenir sans conserver une liste des motifs actuellement étudiés par JIT.

(6) OK, la pile est pour une allocation mémoire à long terme. Mais qu'arrive-t-il si un motif provoque un dépassement de pile avec une pile de 1 Mo? Ce 1 Mo est-il conservé jusqu'à ce que la pile soit libérée?

En particulier sur les systèmes embarqués, il pourrait être judicieux de libérer la mémoire parfois sans libérer la pile. Il n'y a pas d'API pour cela pour le moment. Probablement un appel de fonction qui retourne la mémoire actuellement allouée pour n'importe quelle pile et une autre qui permet de libérer de la mémoire (réduire la pile) serait une bonne idée si quelqu'un en a besoin.

(7) C'est trop compliqué. N'y a-t-il pas une meilleure solution pour la gestion des piles JIT?

Non, merci à Windows. Si les threads POSIX étaient utilisés partout, nous pourrions supprimer cette API compliquée.

EXEMPLE DE CODE

Voici un exemple mono-thread qui spécifie une pile JIT sans utiliser de rappel.


int rc;
int ovector[30];
pcre *re;
pcre_extra *extra;
pcre_jit_stack *jit_stack;


re = pcre_compile(pattern, 0, &error, &erroffset, NULL);
/* Vérifier les erreurs */
extra = pcre_study(re, PCRE_STUDY_JIT_COMPILE, &error);
jit_stack = pcre_jit_stack_alloc(32*1024, 512*1024);
/* Vérifier les erreurs (NULL) */
pcre_assign_jit_stack(extra, NULL, jit_stack);
rc = pcre_exec(re, extra, subject, length, 0, 0, ovector, 30);
/* Vérifier les résultats */
pcre_free(re);
pcre_free_study(extra);
pcre_jit_stack_free(jit_stack);

API DU CHEMIN RAPIDE JIT

Étant donné que l'API décrite ci-dessus se rabat sur l'exécution interprétée lorsque le JIT n'est pas disponible, elle est pratique pour les programmes destinés à une utilisation générale dans de nombreux environnements. Cependant, l'appel du JIT via pcre_exec() a un impact sur les performances. Les programmes écrits pour une utilisation où le JIT est connu pour être disponible, et qui nécessitent les meilleures performances possibles, peuvent utiliser à la place une API de "chemin rapide" pour appeler directement l'exécution JIT au lieu d'appeler pcre_exec() (évidemment seulement pour les motifs qui ont été étudiés avec succès par JIT).

La fonction du chemin rapide s'appelle pcre_jit_exec(), et elle prend exactement les mêmes arguments que pcre_exec(), plus un argument supplémentaire qui doit pointer vers une pile JIT. Les arrangements de pile JIT décrits ci-dessus ne s'appliquent pas. Les valeurs de retour sont les mêmes que pour pcre_exec().

Lorsque vous appelez pcre_exec(), en plus de vérifier les options invalides, un certain nombre d'autres vérifications de cohérence sont effectuées sur les arguments. Par exemple, si le pointeur du sujet est NULL, ou si sa longueur est négative, une erreur immédiate est signalée. De plus, sauf si PCRE_NO_UTF[8|16|32] est défini, une chaîne de sujet UTF est testée pour sa validité. Dans un souci de vitesse, ces vérifications n'ont pas lieu sur le chemin rapide JIT, et si des données invalides sont passées, le résultat est indéfini.

JIT FAST PATH API

Bypassing the sanity checks and the pcre_exec() wrapping can give speedups of more than 10%.

Note that the pcre_jit_exec() function is not available in versions of PCRE before 8.32 (released in November 2012). If you need to support versions that old you must either use the slower pcre_exec(), or switch between the two codepaths by checking the values of PCRE_MAJOR and PCRE_MINOR.

Due to an unfortunate implementation oversight, even in versions 8.32 and later there will be no pcre_jit_exec() stub function defined when PCRE is compiled with --disable-jit, which is the default, and there's no way to detect whether PCRE was compiled with --enable-jit via a macro.

If you need to support versions older than 8.32, or versions that may not build with --enable-jit, you must either use the slower pcre_exec(), or switch between the two codepaths by checking the values of PCRE_MAJOR and PCRE_MINOR.

Switching between the two by checking the version assumes that all the versions being targeted are built with --enable-jit. To also support builds that may use --disable-jit either pcre_exec() must be used, or a compile-time check for JIT via pcre_config() (which assumes the runtime environment will be the same), or as the Git project decided to do, simply assume that pcre_jit_exec() is present in 8.32 or later unless a compile-time flag is provided, see the "grep: un-break building with PCRE >= 8.32 without --enable-jit" commit in git.git for an example of that.
