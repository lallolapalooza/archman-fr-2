NOM

PCRE2 - expressions régulières compatibles Perl (API révisée)

DÉTAILS DE L'EXPRESSION RÉGULIÈRE PCRE2

La syntaxe et la sémantique des expressions régulières prises en charge par PCRE2 sont décrites en détail ci-dessous. Un résumé de la syntaxe de référence rapide se trouve sur la page pcre2syntax. PCRE2 essaie de correspondre à la syntaxe et à la sémantique de Perl aussi fidèlement que possible. PCRE2 prend également en charge une syntaxe d'expression régulière alternative qui n'entre pas en conflit avec la syntaxe Perl, afin d'assurer une certaine compatibilité avec les expressions régulières de Python, .NET et Oniguruma. Il existe en outre des options qui activent des syntaxes et sémantiques alternatives qui ne sont pas les mêmes qu'en Perl.

Les expressions régulières de Perl sont décrites dans sa propre documentation, et les expressions régulières en général sont couvertes par un certain nombre de livres, dont certains contiennent de nombreux exemples. Le livre de Jeffrey Friedl, "Mastering Regular Expressions", publié par O'Reilly, couvre les expressions régulières en détail. Cette description des expressions régulières de PCRE2 est destinée à servir de matériel de référence.

Ce document discute des motifs d'expressions régulières pris en charge par PCRE2 lorsque sa fonction de correspondance principale, pcre2_match(), est utilisée. PCRE2 dispose également d'une fonction de correspondance alternative, pcre2_dfa_match(), qui correspond en utilisant un algorithme différent qui n'est pas compatible avec Perl. Certaines des fonctionnalités décrites ci-dessous ne sont pas disponibles lorsque la correspondance DFA est utilisée. Les avantages et les inconvénients de la fonction alternative, et la manière dont elle diffère de la fonction normale, sont décrits sur la page pcre2matching.

CODES DES CARACTÈRES EBCDIC

La plupart des ordinateurs utilisent ASCII ou Unicode pour encoder les caractères, et PCRE2 suppose cela par défaut. Cependant, il peut être compilé pour s'exécuter dans un environnement qui utilise le code EBCDIC, ce qui est le cas pour certains systèmes d'exploitation de mainframes IBM. Dans les sections ci-dessous, les valeurs des codes de caractères sont ASCII ou Unicode ; dans un environnement EBCDIC, ces caractères peuvent avoir des valeurs de code différentes, et il n'y a pas de points de code supérieurs à 255. Les différences de comportement lorsque PCRE2 s'exécute dans un environnement EBCDIC sont décrites dans la section "Environnements EBCDIC" ci-dessous, que vous pouvez ignorer à moins que vous ne vous trouviez réellement dans un environnement EBCDIC.

ÉLÉMENTS SPÉCIAUX DE DÉBUT DE MOTIF

Un certain nombre d'options qui peuvent être passées à pcre2_compile() peuvent également être définies par des éléments spéciaux au début d'un motif. Ceux-ci ne sont pas compatibles avec Perl, mais sont fournis pour rendre ces options accessibles aux rédacteurs de motifs qui ne peuvent pas modifier le programme qui traite le motif. Un nombre quelconque de ces éléments peuvent apparaître, mais ils doivent tous être regroupés juste au début de la chaîne de motif, et les lettres doivent être en majuscules.

Support UTF

Dans les bibliothèques PCRE2 8 bits et 16 bits, les caractères peuvent être codés soit comme des unités de code uniques, soit comme plusieurs unités de code UTF-8 ou UTF-16. UTF-32 peut être spécifié pour la bibliothèque 32 bits, auquel cas il contraint les valeurs des caractères à des points de code Unicode valides. Pour traiter les chaînes UTF, PCRE2 doit être construit pour inclure la prise en charge Unicode (ce qui est le cas par défaut). Lorsque vous utilisez des chaînes UTF, vous devez soit appeler la fonction de compilation avec l'une ou les deux options PCRE2_UTF ou PCRE2_MATCH_INVALID_UTF, soit le motif doit commencer par la séquence spéciale (*UTF), ce qui équivaut à définir le PCRE2_UTF pertinent. La manière dont la définition d'un mode UTF affecte la correspondance des motifs est mentionnée à plusieurs endroits ci-dessous. Il y a également un résumé des fonctionnalités sur la page pcre2unicode.

Certaines applications qui permettent à leurs utilisateurs de fournir des motifs peuvent souhaiter les restreindre à des données non UTF pour des raisons de sécurité. Si l'option PCRE2_NEVER_UTF est passée à pcre2_compile(), (*UTF) n'est pas autorisé, et son apparition dans un motif entraîne une erreur.

Support des propriétés Unicode

Une autre séquence spéciale qui peut apparaître au début d'un motif est (*UCP). Cela a le même effet que de définir l'option PCRE2_UCP : elle fait que des séquences comme \d et \w utilisent les propriétés Unicode pour déterminer les types de caractères, au lieu de reconnaître uniquement les caractères avec des codes inférieurs à 256 via une table de recherche. Cela fait également que les opérations de mise en majuscules/minuscules utilisent les propriétés Unicode pour les caractères dont les points de code sont supérieurs à 127, même lorsque UTF n'est pas défini. Ces comportements peuvent être modifiés dans le motif ; voir la section intitulée "Définition d'options internes" ci-dessous.

Certaines applications qui permettent à leurs utilisateurs de fournir des motifs peuvent souhaiter les restreindre pour des raisons de sécurité. Si l'option PCRE2_NEVER_UCP est passée à pcre2_compile(), (*UCP) n'est pas autorisé, et son apparition dans un motif entraîne une erreur.

Blocage de la correspondance de chaînes vides

Commencer un motif par (*NOTEMPTY) ou (*NOTEMPTY_ATSTART) a le même effet que de passer l'option PCRE2_NOTEMPTY ou PCRE2_NOTEMPTY_ATSTART à la fonction de correspondance qui sera appelée ensuite pour faire correspondre le motif. Ces options bloquent la correspondance des chaînes vides, soit entièrement, soit uniquement au début du sujet.

Désactivation de l'auto-possessification

Si un motif commence par (*NO_AUTO_POSSESS), il a le même effet que de définir l'option PCRE2_NO_AUTO_POSSESS, ou d'appeler pcre2_set_optimize() avec une directive PCRE2_AUTO_POSSESS_OFF. Cela empêche PCRE2 de rendre possessifs les quantificateurs lorsque ce qui suit ne peut pas correspondre à l'élément répété. Par exemple, par défaut, a+b est traité comme a++b. Pour plus d'informations, voir la documentation pcre2api.

Désactivation des optimisations au démarrage

Si un motif commence par (*NO_START_OPT), il a le même effet que de définir l'option PCRE2_NO_START_OPTIMIZE, ou d'appeler pcre2_set_optimize() avec une directive PCRE2_START_OPTIMIZE_OFF. Cela désactive plusieurs optimisations pour obtenir rapidement des résultats de "pas de correspondance". Pour plus d'informations, voir la documentation pcre2api.

Désactivation de l'ancrage automatique

Si un motif commence par (*NO_DOTSTAR_ANCHOR), il a le même effet que de définir l'option PCRE2_NO_DOTSTAR_ANCHOR, ou d'appeler pcre2_set_optimize() avec une directive PCRE2_DOTSTAR_ANCHOR_OFF. Cela désactive les optimisations qui s'appliquent aux motifs dont les branches de haut niveau commencent toutes par .* (correspond à n'importe quel nombre de caractères arbitraires). Pour plus d'informations, voir la documentation pcre2api.

Désactivation de la compilation JIT

Si un motif commençant par (*NO_JIT) est compilé avec succès, une tentative par l'application d'appliquer l'optimisation JIT en appelant pcre2_jit_compile() est ignorée.

Définition des limites de ressources de correspondance

La fonction pcre2_match() contient un compteur qui est incrémenté à chaque passage dans sa boucle principale. L'appelant de pcre2_match() peut définir une limite pour ce compteur, qui limite ainsi la quantité de ressources informatiques utilisées pour une correspondance. La profondeur maximale de backtracking imbriqué peut également être limitée ; cela limite indirectement la quantité de mémoire du tas utilisée, mais il existe également une limite de mémoire explicite qui peut être définie.

Ces facilités sont fournies pour intercepter les correspondances incontrôlées qui sont provoquées par des motifs avec d'énormes arbres de correspondance. Un exemple courant est un motif avec des répétitions illimitées imbriquées appliqué à une longue chaîne qui ne correspond pas. Lorsque l'une de ces limites est atteinte, pcre2_match() renvoie une erreur. Les limites peuvent également être définies par des éléments au début du motif de la forme


(*LIMIT_HEAP=d)
(*LIMIT_MATCH=d)
(*LIMIT_DEPTH=d)

où d est n'importe quel nombre de chiffres décimaux. Cependant, la valeur du réglage doit être inférieure à la valeur définie (ou par défaut) par l'appelant de pcre2_match() pour qu'elle ait un effet.

fect. En d'autres termes, le compilateur peut abaisser les limites définies par le programmeur, mais pas les augmenter. S'il existe plus d'une définition pour l'une de ces limites, la valeur la plus faible est utilisée. La limite du tas est spécifiée en kibioctets (unités de 1024 octets).

Avant la version 10.30, LIMIT_DEPTH était appelée LIMIT_RECURSION. Ce nom est toujours reconnu pour des raisons de compatibilité descendante.

La limite du tas ne s'applique que lorsque les interpréteurs pcre2_match() ou pcre2_dfa_match() sont utilisés pour la correspondance. Elle ne s'applique pas au JIT. La limite de correspondance est utilisée (mais d'une manière différente) lorsque le JIT est utilisé, ou lorsque pcre2_dfa_match() est appelée, pour limiter l'utilisation des ressources informatiques par ces fonctions de correspondance. La limite de profondeur est ignorée par le JIT mais est pertinente pour la correspondance DFA, qui utilise la récursion de fonctions pour les récursions au sein du motif et pour les assertions de lookaround et les groupes atomiques. Dans ce cas, la limite de profondeur contrôle la profondeur de cette récursion.

Conventions de nouvelle ligne

PCRE2 prend en charge six conventions différentes pour indiquer les sauts de ligne dans les chaînes : un seul caractère CR (retour chariot), un seul caractère LF (saut de ligne), la séquence de deux caractères CRLF, l'une des trois précédentes, toute séquence de nouvelle ligne Unicode ou le caractère NUL (zéro binaire). La page pcre2api contient une discussion plus approfondie sur les nouvelles lignes et montre comment définir la convention de nouvelle ligne lors de l'appel de pcre2_compile().

Il est également possible de spécifier une convention de nouvelle ligne en commençant une chaîne de motif par l'une des séquences suivantes :


(*CR) retour chariot
(*LF) saut de ligne
(*CRLF) retour chariot, suivi d'un saut de ligne
(*ANYCRLF) l'une des trois ci-dessus
(*ANY) toutes les séquences de nouvelle ligne Unicode
(*NUL) le caractère NUL (zéro binaire)

Celles-ci remplacent la valeur par défaut et les options données à la fonction de compilation. Par exemple, sur un système Unix où LF est la séquence de nouvelle ligne par défaut, le motif


(*CR)a.b

modifie la convention en CR. Ce motif correspond à "a\nb" car LF n'est plus une nouvelle ligne. Si plus d'une de ces définitions est présente, la dernière est utilisée.

La convention de nouvelle ligne affecte les endroits où les assertions circonflexe et dollar sont vraies. Elle affecte également l'interprétation du métacaractère point lorsque PCRE2_DOTALL n'est pas défini, et le comportement de \N lorsqu'il n'est pas suivi d'une accolade ouvrante. Cependant, cela n'affecte pas ce que la séquence d'échappement \R correspond. Par défaut, il s'agit de toute séquence de nouvelle ligne Unicode, pour la compatibilité avec Perl. Cependant, cela peut être modifié ; voir la section suivante et la description de \R dans la section intitulée "Séquences de nouvelle ligne" ci-dessous. Une modification du paramètre \R peut être combinée avec une modification de la convention de nouvelle ligne.

Spécifier ce que \R correspond

Il est possible de restreindre \R à ne correspondre qu'à CR, LF ou CRLF (au lieu de l'ensemble complet des fins de ligne Unicode) en définissant l'option PCRE2_BSR_ANYCRLF au moment de la compilation. Cet effet peut également être obtenu en commençant un motif par (*BSR_ANYCRLF). Pour complétude, (*BSR_UNICODE) est également reconnu, correspondant à PCRE2_BSR_UNICODE.

CARACTERES ET METACARACTERES

Une expression régulière est un motif qui est mis en correspondance avec une chaîne sujet de gauche à droite. La plupart des caractères se représentent eux-mêmes dans un motif, et correspondent aux caractères correspondants dans le sujet. À titre d'exemple trivial, le motif


Le rapide renard brun

correspond à une partie d'une chaîne sujet qui lui est identique. Lorsque la correspondance insensible à la casse est spécifiée (l'option PCRE2_CASELESS ou (?i) dans le motif), les lettres sont mises en correspondance indépendamment de leur casse. Notez qu'il existe deux caractères ASCII, K et S, qui, en plus de leurs équivalents ASCII minuscules, sont équivalents en casse avec Unicode U+212A (signe Kelvin) et U+017F (s long) respectivement lorsque PCRE2_UTF ou PCRE2_UCP est défini, sauf si l'option PCRE2_EXTRA_CASELESS_RESTRICT est active (passée à pcre2_compile() ou définie par (*CASELESS_RESTRICT) ou (?r) dans le motif). Si l'option PCRE2_EXTRA_TURKISH_CASING est active (passée à pcre2_compile() ou définie par (*TURKISH_CASING) dans le motif), alors les lettres 'i' sont mises en correspondance selon les langues turque et azerbaïdjanaise.

La puissance des expressions régulières vient de la capacité d'inclure des jokers, des classes de caractères, des alternatives et des répétitions dans le motif. Ceux-ci sont codés dans le motif par l'utilisation de métacaractères, qui ne se représentent pas eux-mêmes mais sont interprétés d'une manière spéciale.

Il existe deux ensembles différents de métacaractères : ceux qui sont reconnus n'importe où dans le motif sauf à l'intérieur des crochets, et ceux qui sont reconnus à l'intérieur des crochets. En dehors des crochets, les métacaractères sont les suivants :


\ caractère d'échappement général avec plusieurs utilisations
^ assertion de début de chaîne (ou de ligne, en mode multiligne)
$ assertion de fin de chaîne (ou de ligne, en mode multiligne)
. correspond à n'importe quel caractère sauf la nouvelle ligne (par défaut)
[ début de définition de classe de caractères
| début de branche alternative
( début de groupe ou verbe de contrôle
) fin de groupe ou verbe de contrôle
* 0 ou plusieurs quantificateurs
+ 1 ou plusieurs quantificateurs ; aussi "quantificateur possessif"
? 0 ou 1 quantificateur ; aussi minimiseur de quantificateur
{ début potentiel de quantificateur min/max

Les caractères d'accolade { et } sont également utilisés pour encapsuler des données pour des constructions telles que \g{2} ou \k{nom}. Dans presque toutes les utilisations d'accolades, les espaces et/ou les tabulations horizontales qui suivent { ou précèdent } sont autorisés et sont ignorés. Dans le cas des quantificateurs, ils peuvent également apparaître avant ou après la virgule. L'exception est \u{...} qui est une fonctionnalité de compatibilité ECMAScript qui n'est reconnue que lorsque l'option PCRE2_EXTRA_ALT_BSUX est définie. ECMAScript n'ignore pas de tels espaces ; elle interprète l'élément comme littéral.

Une partie d'un motif qui est entre crochets est appelée une "classe de caractères". Dans une classe de caractères, les seuls métacaractères sont :


\ caractère d'échappement général
^ nie la classe, mais seulement si c'est le premier caractère
- indique une plage de caractères
[ classe de caractères POSIX (si suivie d'une syntaxe POSIX)
] termine la classe de caractères

Si un motif est compilé avec l'option PCRE2_EXTENDED, la plupart des espaces dans le motif, sauf dans une classe de caractères, à l'intérieur d'une séquence \Q...\E, ou entre un # en dehors d'une classe de caractères et la nouvelle ligne suivante, inclus, sont ignorés. Un antislash d'échappement peut être utilisé pour inclure un espace ou un caractère # comme partie du motif. Si l'option PCRE2_EXTENDED_MORE est définie, il en va de même, mais en plus, les espaces et les tabulations horizontales non échappés sont ignorés à l'intérieur d'une classe de caractères. Remarque : seuls ces deux caractères sont ignorés, pas l'ensemble complet des caractères d'espace du motif qui sont ignorés en dehors d'une classe de caractères. Les paramètres d'option peuvent être modifiés dans un motif ; voir la section intitulée "Réglage des options internes" ci-dessous.

Les sections suivantes décrivent l'utilisation de chacun des métacaractères.

ANTISLASH

Le caractère antislash a plusieurs utilisations. Premièrement, s'il est suivi d'un caractère qui n'est ni un chiffre ni une lettre, il supprime toute signification spéciale que ce caractère pourrait avoir. Cette utilisation de l'antislash comme caractère d'échappement s'applique aussi bien à l'intérieur qu'à l'extérieur des classes de caractères.

Par exemple, si vous voulez faire correspondre un caractère *, vous devez écrire \* dans le motif. Cette action d'échappement s'applique que le caractère suivant soit autrement interprété comme un métacaractère ou non, il est donc toujours sûr de précéder un caractère non alphanumérique avec un antislash pour spécifier qu'il se représente lui-même. En particulier, si vous voulez faire correspondre un antislash, vous écrivez \\.

Seuls les chiffres et les lettres ASCII ont une signification spéciale après un antislash. Tous les autres caractères (en particulier, ceux dont les points de code sont supérieurs à 127) sont traités comme des littéraux.

Si vous voulez traiter tous les caractères d'une séquence comme des littéraux, vous pouvez le faire en les plaçant entre \Q et \E. Notez que cela inclut les espaces même lorsque l'option PCRE2_EXTENDED est définie de sorte que la plupart des autres espaces sont ignorés. Le comportement est différent de Perl en ce sens que $ et @ sont traités comme des littéraux dans les séquences \Q...\E dans PCRE2, alors que chez Perl, $ et @ provoquent l'interpolation de variables. De plus, Perl effectue une "interpolation d'antislash de type guillemet double" sur tous les antislashs entre \Q et \E, ce qui, selon sa documentation, "peut conduire à des résultats confusants". PCRE2 traite un antislash entre \Q et \E comme n'importe quel autre caractère. Notez les exemples suivants :


Motif PCRE2 correspond Perl correspond


\Qabc$xyz\E abc$xyz abc suivi du contenu de
$xyz
\Qabc\$xyz\E abc\$xyz abc\$xyz
\Qabc\E\$\Qxyz\E abc$xyz abc$xyz
\QA\B\E A\B A\B
\Q\\E \ \\E

La séquence \Q...\E est reconnue aussi bien à l'intérieur qu'à l'extérieur des classes de caractères. Un \E isolé qui n'est pas précédé par \Q est ignoré. Si \Q n'est pas suivi par \E plus loin dans le motif, l'interprétation littérale continue jusqu'à la fin du motif (c'est-à-dire que \E est supposé à la fin). Si le \Q isolé est à l'intérieur d'une classe de caractères, cela provoque une erreur, car la classe de caractères n'est alors pas terminée par une parenthèse carrée fermante.

Une autre différence avec Perl est que toute apparition de \Q ou \E à l'intérieur de ce qui pourrait autrement être un quantificateur amène PCRE2 à ne pas reconnaître la séquence comme un quantificateur. Perl reconnaît un quantificateur si (redondamment) l'un des nombres est à l'intérieur de \Q...\E, mais pas si la virgule séparatrice l'est. Lorsqu'il n'est pas reconnu comme quantificateur, une séquence telle que {\Q1\E,2} est traitée comme la chaîne littérale "{1,2}".

Caractères non imprimables

Une deuxième utilisation de l'antislash fournit un moyen d'encoder les caractères non imprimables dans les motifs de manière visible. Il n'y a aucune restriction sur l'apparition de caractères non imprimables dans un motif, mais lorsqu'un motif est préparé par édition de texte, il est souvent plus facile d'utiliser l'une des séquences d'échappement suivantes au lieu du caractère binaire qu'elle représente. Dans un environnement ASCII ou Unicode, ces échappements sont les suivants :


\a alarme, c'est-à-dire le caractère BEL (hex 07)
\cx "contrôle-x", où x est un caractère ASCII non de contrôle
\e échappement (hex 1B)
\f saut de page (hex 0C)

Séquences d'échappement

Les séquences d'échappement sont utilisées pour représenter des caractères qui ne peuvent pas être facilement tapés ou qui ont une signification spéciale dans les expressions régulières. Voici une liste des séquences d'échappement prises en charge par PCRE2 :

\n
Saut de ligne (hex 0A)
\r
Retour chariot (hex 0D) (mais voir ci-dessous)
\t
Tabulation (hex 09)
\0dd
Caractère avec le code octal 0dd
\ddd
Caractère avec le code octal ddd, ou référence arrière
\o{ddd..}
Caractère avec le code octal ddd..
\xhh
Caractère avec le code hexadécimal hh
\x{hhh..}
Caractère avec le code hexadécimal hhh..
\N{U+hhh..}
Caractère avec le point de code hexadécimal Unicode hhh..

Une description du fonctionnement des références arrière est donnée plus loin, après la discussion des groupes entre parenthèses.

Par défaut, après \x qui n'est pas suivi de {, un ou deux chiffres hexadécimaux sont lus (les lettres peuvent être en majuscules ou en minuscules). Si le caractère qui suit \x n'est ni { ni un chiffre hexadécimal, une erreur se produit. Ceci est différent du comportement par défaut de Perl, qui génère un caractère NUL, mais est conforme au comportement du mode 'strict' de Perl en matière d'expressions régulières.

Un nombre quelconque de chiffres hexadécimaux peut apparaître entre \x{ et }. Si un caractère autre qu'un chiffre hexadécimal apparaît entre \x{ et }, ou s'il n'y a pas de } de terminaison, une erreur se produit.

Les caractères dont les points de code sont inférieurs à 256 peuvent être définis par l'une des deux syntaxes pour \x ou par une séquence octale. Il n'y a aucune différence dans la manière dont ils sont gérés. Par exemple, \xdc est exactement la même chose que \x{dc} ou \334. Cependant, l'utilisation des versions avec accolades rend ces séquences plus faciles à lire.

La prise en charge de certaines séquences d'échappement ECMAScript (également appelées JavaScript) est disponible via deux options de compilation. Si PCRE2_ALT_BSUX est défini, la séquence \x suivie de { n'est pas reconnue. Ce n'est que si \x est suivi de deux chiffres hexadécimaux qu'il est reconnu comme une séquence d'échappement de caractère. Sinon, il est interprété comme un caractère littéral "x". Dans ce mode, la prise en charge des points de code supérieurs à 256 est fournie par \u, qui doit être suivi de quatre chiffres hexadécimaux ; sinon, il est interprété comme un caractère littéral "u".

PCRE2_EXTRA_ALT_BSUX a le même effet que PCRE2_ALT_BSUX et, en outre, \u{hhh..} est reconnu comme le caractère spécifié par le point de code hexadécimal. Il peut y avoir un nombre quelconque de chiffres hexadécimaux, mais contrairement à d'autres endroits qui utilisent également des accolades, les espaces ne sont pas autorisés et entraînent l'interprétation de la chaîne comme littérale. Cette syntaxe provient d'ECMAScript 6.

La séquence d'échappement \N{U+hhh..} n'est reconnue que lorsque PCRE2 fonctionne en mode UTF. Perl utilise également \N{nom} pour spécifier des caractères par nom Unicode ; PCRE2 ne prend pas en charge cela. Notez que lorsque \N n'est pas suivi d'une accolade ouvrante, il a une signification entièrement différente, correspondant à tout caractère qui n'est pas un saut de ligne.

Il existe certaines applications héritées où la séquence d'échappement \r est censée correspondre à un saut de ligne. Si l'option PCRE2_EXTRA_ESCAPED_CR_IS_LF est définie, \r dans un modèle est converti en \n afin qu'il corresponde à un caractère LF (saut de ligne) au lieu d'un caractère CR (retour chariot).

Une erreur se produit si \c n'est pas suivi d'un caractère dont le point de code ASCII est dans la plage 32 à 126. L'effet précis de \cx est le suivant : si x est une lettre minuscule, il est converti en majuscule. Ensuite, le bit 6 du caractère (hex 40) est inversé. Ainsi, \cA à \cZ deviennent hex 01 à hex 1A (A est 41, Z est 5A), mais \c{ devient hex 3B ({ est 7B), et \c; devient hex 7B (; est 3B). Si l'unité de code suivant \c a un point de code inférieur à 32 ou supérieur à 126, une erreur de compilation se produit.

Pour connaître les différences dans la manière dont certaines séquences d'échappement se comportent dans les environnements EBCDIC, voir la section « Environnements EBCDIC » ci-dessous.

Séquences octales et références arrière

La séquence \o doit être suivie d'une séquence de chiffres octaux, entourée d'accolades. Une erreur se produit si ce n'est pas le cas. Cette séquence offre un moyen de spécifier des points de code de caractères sous forme de nombres octaux supérieurs à 0777, et elle permet également de distinguer sans ambiguïté les nombres octaux et les références arrière.

Si les accolades ne sont pas utilisées, après \0, jusqu'à deux chiffres octaux supplémentaires sont lus. Cependant, si l'option PCRE2_EXTRA_NO_BS0 est définie, au moins un chiffre octal supplémentaire doit suivre \0 (utilisez \00 pour générer un caractère NUL). Assurez-vous de fournir deux chiffres après le zéro initial si le caractère de modèle qui suit est lui-même un chiffre octal.

À l'intérieur d'une classe de caractères, lorsqu'un antislash est suivi d'un chiffre octal, jusqu'à trois chiffres octaux sont lus pour générer un point de code. Tous les chiffres suivants sont considérés comme eux-mêmes. Les séquences \8 et \9 sont traitées comme les caractères littéraux "8" et "9".

En dehors d'une classe de caractères, la gestion par Perl d'un antislash suivi d'un chiffre différent de 0 est compliquée par l'ambiguïté, et Perl a changé au fil du temps, ce qui a également entraîné des changements dans PCRE2. À partir de la version 10.45 de PCRE2, il existe une option appelée PCRE2_EXTRA_PYTHON_OCTAL qui amène PCRE2 à utiliser les règles sans ambiguïté de Python. Les deux sous-sections suivantes décrivent les deux ensembles de règles.

Pour plus de clarté et d'absence d'ambiguïté, il est préférable d'éviter de faire suivre \ d'un chiffre supérieur à zéro. Utilisez plutôt \o{...} ou \x{...} pour spécifier les points de code numériques des caractères, et \g{...} pour spécifier les références arrière.

Règles Perl pour l'antislash non-classe 1-9

Tous les chiffres qui suivent l'antislash sont lus comme un nombre décimal. Si le nombre est inférieur à 10, commence par le chiffre 8 ou 9, ou s'il y a au moins autant de groupes de capture précédents dans l'expression, la séquence entière est considérée comme une référence arrière. Sinon, jusqu'à trois chiffres octaux sont lus pour former un point de code de caractère. Par exemple :


\040 est une autre façon d'écrire un espace ASCII
\40 est la même chose, à condition qu'il y ait moins de 40
groupes de capture précédents
\7 est toujours une référence arrière
\11 peut être une référence arrière, ou une autre façon
d'écrire une tabulation
\011 est toujours une tabulation
\0113 est une tabulation suivie du caractère "3"
\113 peut être une référence arrière, sinon
le caractère avec le code octal 113
\377 peut être une référence arrière, sinon
la valeur 255 (décimal)
\81 est toujours une référence arrière

Notez que les valeurs octales de 100 ou plus spécifiées à l'aide de cette syntaxe ne doivent pas être précédées d'un zéro initial, car pas plus de trois chiffres octaux ne sont jamais lus.

Règles Python pour l'antislash non-classe 1-9

S'il y a au moins trois chiffres octaux après l'antislash, exactement trois sont lus comme un nombre de point de code octal, mais la valeur ne doit pas dépasser \377, même dans les modes où les valeurs de point de code supérieures sont prises en charge. Tous les chiffres suivants sont considérés comme eux-mêmes. S'il y a moins de trois chiffres octaux, la séquence est considérée comme une référence arrière décimale. Ainsi, par exemple, \12 est toujours une référence arrière, indépendamment du nombre de captures dans le modèle. Une erreur est générée pour une référence à un groupe de capture inexistant.

Contraintes sur les valeurs de caractères

Les caractères spécifiés à l'aide de nombres octaux ou hexadécimaux sont limités à certaines valeurs, comme suit :


Mode non-UTF 8 bits : pas plus de 0xff
Mode non-UTF 16 bits : pas plus de 0xffff
Mode non-UTF 32 bits : pas plus de 0xffffffff
Tous les modes UTF : pas plus de 0x10ffff et un point de code valide

Les points de code Unicode invalides sont tous ceux de la plage 0xd800 à 0xdfff (les soi-disant points de code "de substitution"). La vérification de ceux-ci peut être désactivée par l'appelant de pcre2_compile() en définissant l'option PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES. Cependant, cela n'est possible qu'en mode UTF-8 et UTF-32, car ces valeurs ne sont pas représentables en UTF-16.

Séquences d'échappement dans les classes de caractères

Toutes les séquences qui définissent une seule valeur de caractère peuvent être utilisées à l'intérieur et à l'extérieur des classes de caractères. De plus, à l'intérieur d'une classe de caractères, \b est interprété comme le caractère d'effacement (hex 08).

Lorsqu'il n'est pas suivi d'une accolade ouvrante, \N n'est pas autorisé dans une classe de caractères. \B, \R et \X ne sont pas spéciaux à l'intérieur d'une classe de caractères. Comme d'autres séquences d'échappement alphabétiques non reconnues, elles provoquent une erreur. En dehors d'une classe de caractères, ces séquences ont des significations différentes.

Séquences d'échappement non prises en charge

Dans Perl, les séquences \F, \l, \L, \u et \U sont reconnues par son gestionnaire de chaînes et utilisées pour modifier la casse des caractères suivants. Par défaut, PCRE2 ne prend pas en charge ces séquences d'échappement dans les modèles. Cependant, si l'une des options PCRE2_ALT_BSUX ou PCRE2_EXTRA_ALT_BSUX est définie, \U correspond à un caractère "U", et \u peut être utilisé pour définir un caractère par point de code, comme décrit ci-dessus.

Références arrière absolues et relatives

La séquence \g suivie d'un nombre signé ou non signé, éventuellement entouré d'accolades, est une référence arrière absolue ou relative. Une référence arrière nommée peut être codée sous la forme \g{nom}. Les références arrière sont discutées plus tard, après la discussion des groupes entre parenthèses.

Appels de sous-routines absolus et relatifs

Pour la compatibilité avec Oniguruma, la syntaxe non-Perl \g suivie d'un nom ou d'un nombre entouré d'accolades ou de guillemets simples, est une syntaxe alternative pour référencer un groupe de capture comme une sous-routine. Les détails sont discutés plus tard. Notez que \g{...} (syntaxe Perl) et \g<...> (syntaxe Oniguruma) ne sont *pas* synonymes. Le premier est une référence arrière ; le second est un appel de sous-routine.

PDI pop directional isolate (Isolation directionnelle Pop)
R right-to-left (Droite à gauche)
RLE right-to-left embedding (Embarquement droite à gauche)
RLI right-to-left isolate (Isolation droite à gauche)
RLO right-to-left override (Substitution droite à gauche)
S segment separator (Séparateur de segment)
WS white space (Espace blanc)

Comme dans toutes les spécifications de propriétés, un signe égal peut être utilisé à la place d'un deux-points et les noms de classe sont insensibles à la casse. Seuls les noms courts listés ci-dessus sont reconnus ; PCRE2 ne prend pas en charge actuellement d'alternatives longues.

Clusters graphes étendus

L'échappement \X correspond à un nombre quelconque de caractères Unicode formant un « cluster graphe étendu », et traite la séquence comme un groupe atomique (voir ci-dessous). Unicode prend en charge divers types de caractères composites en donnant à chaque caractère une propriété de rupture de graphe, et en ayant des règles qui utilisent ces propriétés pour définir les limites des clusters graphes étendus. Les règles sont définies dans le Unicode Standard Annex 29, « Unicode Text Segmentation ». Unicode 11.0.0 a abandonné l'utilisation de certaines propriétés précédentes qui avaient été utilisées pour les emojis. Il a introduit à la place diverses propriétés spécifiques aux emojis. PCRE2 utilise uniquement la propriété Extended_Pictographic.

\X correspond toujours à au moins un caractère. Ensuite, il décide s'il faut ajouter des caractères supplémentaires conformément aux règles suivantes pour terminer un cluster :

1. Terminer à la fin de la chaîne sujet.

2. Ne pas terminer entre CR et LF ; sinon, terminer après tout caractère de contrôle.

3. Ne pas rompre les séquences de syllabes Hangul (un script coréen). Les caractères Hangul sont de cinq types : L, V, T, LV et LVT. Un caractère L peut être suivi d'un caractère L, V, LV ou LVT ; un caractère LV ou V peut être suivi d'un caractère V ou T ; un caractère LVT ou T ne peut être suivi que d'un caractère T.

4. Ne pas terminer avant les caractères d'extension, les marques d'espacement ou le caractère ZWJ (zero-width joiner). Les caractères ayant la propriété « mark » ont toujours la propriété de rupture de graphe « extend ».

5. Ne pas terminer après les caractères de préfixe.

6. Ne pas terminer au sein des séquences de modificateurs d'emoji ou des séquences ZWJ (zero-width joiner) d'emoji. Une séquence ZWJ d'emoji consiste en un caractère possédant la propriété Extended_Pictographic, éventuellement suivi d'un ou plusieurs caractères possédant la propriété Extend, suivi du caractère ZWJ, suivi d'un autre caractère Extended_Pictographic.

7. Ne pas rompre au sein des séquences de drapeaux emoji. Autrement dit, ne pas rompre entre les caractères d'indicateur régional (RI) s'il y a un nombre impair de caractères RI avant le point de rupture.

8. Sinon, terminer le cluster.

Propriétés supplémentaires de PCRE2

En plus des propriétés Unicode standard décrites ci-dessus, PCRE2 prend en charge quatre autres propriétés qui permettent de convertir les séquences d'échappement traditionnelles telles que \w et \s en propriétés Unicode. PCRE2 utilise ces propriétés non standard et non Perl en interne lorsque PCRE2_UCP est défini. Cependant, elles peuvent également être utilisées explicitement. Ces propriétés sont :


Xan Any alphanumeric character (Tout caractère alphanumérique)
Xps Any POSIX space character (Tout caractère d'espace POSIX)
Xsp Any Perl space character (Tout caractère d'espace Perl)
Xwd Any Perl "word" character (Tout caractère « mot » Perl)

Xan correspond aux caractères qui possèdent soit la propriété L (lettre), soit la propriété N (nombre). Xps correspond aux caractères tabulation, saut de ligne, tabulation verticale, saut de page ou retour chariot, et à tout autre caractère possédant la propriété Z (séparateur) (ceci inclut le caractère espace). Xsp est identique à Xps ; en PCRE1, il excluait la tabulation verticale, pour la compatibilité avec Perl, mais Perl a changé. Xwd correspond aux mêmes caractères que Xan, plus ceux qui correspondent à Mn (marque non espacée) ou Pc (ponctuation de connexion, qui inclut le trait de soulignement).

Il existe une autre propriété non standard, Xuc, qui correspond à tout caractère pouvant être représenté par un nom de caractère universel en C++ et dans d'autres langages de programmation. Ce sont les caractères $, @, ` (accent grave), et tous les caractères dont les points de code Unicode sont supérieurs ou égaux à U+00A0, à l'exception des surrogates U+D800 à U+DFFF. Notez que la plupart des caractères de base (ASCII) sont exclus. (Les noms de caractères universels sont de la forme \uHHHH ou \UHHHHHHHH où H est un chiffre hexadécimal. Notez que la propriété Xuc ne correspond pas à ces séquences mais aux caractères qu'elles représentent.)

Réinitialisation du début de la correspondance

En utilisation normale, la séquence d'échappement \K fait que tous les caractères précédemment mis en correspondance ne soient pas inclus dans la séquence finale mise en correspondance retournée. Par exemple, le motif :


foo\Kbar

correspond à « foobar », mais indique qu'il a mis en correspondance « bar ». \K n'interagit en aucune façon avec l'ancrage. Le motif :


^foo\Kbar

ne correspond que lorsque le sujet commence par « foobar » (en mode ligne unique), bien qu'il indique à nouveau la chaîne mise en correspondance comme « bar ». Cette fonctionnalité est similaire à une assertion lookbehind (décrite ci-dessous), mais la partie du motif qui précède \K n'est pas limitée à correspondre à un nombre limité de caractères, comme requis pour une assertion lookbehind. L'utilisation de \K n'interfère pas avec la définition des sous-chaînes capturées. Par exemple, lorsque le motif


(foo)\Kbar

correspond à « foobar », la première sous-chaîne est toujours définie sur « foo ».

À partir de la version 5.32.0, Perl interdit l'utilisation de \K dans les assertions lookaround. À partir de la version 10.38, PCRE2 interdit également cela par défaut. Cependant, l'option PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK peut être utilisée lors de l'appel à pcre2_compile() pour réactiver le comportement précédent. Lorsque cette option est définie, \K est pris en compte lorsqu'il apparaît à l'intérieur d'assertions positives, mais est ignoré dans les assertions négatives. Notez que lorsqu'un motif tel que (?=ab\K) correspond, le début de la correspondance signalé peut être supérieur à la fin de la correspondance. L'utilisation de \K dans une assertion lookbehind au début d'un motif peut également entraîner des effets étranges. Par exemple, considérez ce motif :


(?<=\Kfoo)bar

Si le sujet est « foobar », un appel à pcre2_match() avec un décalage de départ de 3 réussit et rapporte la chaîne correspondante comme "foobar", c'est-à-dire que le début du motif signalé est antérieur au point où le motif a réellement commencé.

Assertions simples

La dernière utilisation de la barre oblique inverse concerne certaines assertions simples. Une assertion spécifie une condition qui doit être remplie à un point particulier d'une correspondance, sans consommer de caractères de la chaîne sujet. L'utilisation de groupes pour des assertions plus complexes est décrite ci-dessous. Les assertions précédées d'une barre oblique inverse sont :


\b correspond à une limite de mot
\B correspond lorsqu'on n'est pas à une limite de mot
\A correspond au début du sujet
\Z correspond à la fin du sujet
correspond également avant un saut de ligne à la fin du sujet
\z correspond uniquement à la fin du sujet
\G correspond à la première position de correspondance dans le sujet

À l'intérieur d'une classe de caractères, \b a une signification différente ; il correspond au caractère d'effacement arrière (backspace). Si l'une des autres assertions apparaît dans une classe de caractères, une erreur "séquence d'échappement invalide" est générée.

Une limite de mot est une position dans la chaîne sujet où le caractère courant et le caractère précédent ne correspondent pas tous deux à \w ou \W (c'est-à-dire que l'un correspond à \w et l'autre à \W), ou le début ou la fin de la chaîne si le premier ou le dernier caractère correspond à \w, respectivement. Lorsque PCRE2 est compilé avec le support Unicode, les significations de \w et \W peuvent être modifiées en définissant l'option PCRE2_UCP. Lorsque cela est fait, cela affecte également \b et \B. Ni PCRE2 ni Perl n'ont de métaséquence distincte "début de mot" ou "fin de mot". Cependant, ce qui suit \b détermine normalement lequel des deux il s'agit. Par exemple, le fragment \ba correspond à "a" au début d'un mot.

Les assertions \A, \Z et \z diffèrent des accents circonflexes et dollars traditionnels (décrits dans la section suivante) en ce qu'elles ne correspondent jamais qu'au tout début et à la toute fin de la chaîne sujet, quelles que soient les options définies. Ainsi, elles sont indépendantes du mode multiligne. Ces trois assertions ne sont pas affectées par les options PCRE2_NOTBOL ou PCRE2_NOTEOL, qui n'affectent que le comportement des méta-caractères accent circonflexe et dollar. Cependant, si l’argument startoffset de pcre2_match() est non nul, indiquant que la correspondance doit commencer à un point autre que le début du sujet, \A ne peut jamais correspondre. La différence entre \Z et \z est que \Z correspond avant un saut de ligne à la fin de la chaîne ainsi qu'à la toute fin, tandis que \z ne correspond qu'à la fin.

L'assertion \G est vraie uniquement lorsque la position de correspondance courante est au point de départ du processus de correspondance, tel que spécifié par l'argument startoffset de pcre2_match(). Elle diffère de \A lorsque la valeur de startoffset est non nulle. En appelant pcre2_match() plusieurs fois avec les arguments appropriés, vous pouvez imiter l'option /g de Perl, et c'est dans ce type d'implémentation que \G peut être utile.

Notez, cependant, que l'implémentation de \G par PCRE2, étant vraie au caractère de départ du processus de correspondance, est subtilement différente de celle de Perl, qui la définit comme vraie à la fin de la correspondance précédente. Dans Perl, ces deux points peuvent être différents lorsque la chaîne précédemment correspondante était vide. Comme PCRE2 ne fait qu'une seule correspondance à la fois, il ne peut pas reproduire ce comportement.

Si toutes les alternatives d'un motif commencent par \G, l'expression est ancrée à la position de correspondance de départ, et le drapeau "ancré" est défini dans l'expression régulière compilée.

ACCENT CIRCONFLEXE ET DOLLAR

Les méta-caractères accent circonflexe et dollar sont des assertions de largeur nulle. C'est-à-dire qu'ils testent une condition particulière sans consommer de caractères de la chaîne sujet. Ces deux méta-caractères concernent la correspondance des débuts et des fins de lignes. Si la convention de saut de ligne est définie de telle sorte que seule la séquence de deux caractères CRLF est reconnue comme saut de ligne, les caractères CR et LF isolés sont traités comme des caractères de données ordinaires et ne sont pas reconnus comme des sauts de ligne.

En dehors d'une classe de caractères, en mode de correspondance par défaut, le caractère accent circonflexe est une assertion qui n'est vraie que si le point de correspondance courant se trouve au début de la chaîne sujet. Si l'argument startoffset de pcre2_match() est non nul, ou si PCRE2_NOTBOL est défini, l'accent circonflexe ne peut jamais correspondre si l'option PCRE2_MULTILINE est désactivée. À l'intérieur d'une classe de caractères, l'accent circonflexe a une signification entièrement différente (voir ci-dessous).

L'accent circonflexe n'a pas besoin d'être le premier caractère du motif s'il y a plusieurs alternatives, mais il doit être la première chose dans chaque alternative où il apparaît si le motif doit jamais correspondre à cette branche. Si toutes les alternatives possibles commencent par un accent circonflexe, c'est-à-dire si le motif est contraint de ne correspondre qu'au début du sujet, on dit qu'il s'agit d'un motif "ancré". (Il existe également d'autres constructions qui peuvent ancrer un motif.)

Le caractère dollar est une assertion qui n'est vraie que si le point de correspondance courant se trouve à la fin de la chaîne sujet, ou immédiatement avant un saut de ligne à la fin de la chaîne (par défaut), à moins que PCRE2_NOTEOL ne soit défini. Notez, cependant, qu'il ne correspond pas réellement au saut de ligne. Le dollar n'a pas besoin d'être le dernier caractère du motif s'il y a plusieurs alternatives, mais il doit être le dernier élément dans toute branche où il apparaît. Le dollar n'a pas de signification spéciale dans une classe de caractères.

La signification du dollar peut être modifiée pour qu'il ne corresponde qu'à la toute fin de la chaîne, en définissant l'option PCRE2_DOLLAR_ENDONLY lors de la compilation. Cela n'affecte pas l'assertion \Z.

Les significations des méta-caractères accent circonflexe et dollar sont modifiées si l'option PCRE2_MULTILINE est définie. Dans ce cas, un caractère dollar correspond avant tous les sauts de ligne dans la chaîne, ainsi qu'à la toute fin, et un accent circonflexe correspond immédiatement après les sauts de ligne internes ainsi qu'au début de la chaîne sujet. Il ne correspond pas après un saut de ligne qui termine la chaîne, par souci de compatibilité avec Perl. Cependant, cela peut être modifié en définissant l'option PCRE2_ALT_CIRCUMFLEX.

Par exemple, le motif /^abc$/ correspond à la chaîne sujet "def\nabc" (où \n représente un saut de ligne) en mode multiligne, mais pas autrement. Par conséquent, les motifs qui sont ancrés en mode monoligne car toutes les branches commencent par ^ ne sont pas ancrés en mode multiligne, et une correspondance pour l'accent circonflexe est possible lorsque l'argument startoffset de pcre2_match() est non nul. L'option PCRE2_DOLLAR_ENDONLY est ignorée si PCRE2_MULTILINE est défini.

Lorsque la convention de saut de ligne (voir "Conventions de saut de ligne" ci-dessous) reconnaît la séquence de deux caractères CRLF comme un saut de ligne, celle-ci est privilégiée, même si les caractères CR et LF isolés sont également reconnus comme des sauts de ligne. Par exemple, si la convention de saut de ligne est "any", un accent circonflexe en mode multiligne correspond avant "xyz" dans la chaîne "abc\r\nxyz" plutôt qu'après CR, même si CR seul est un saut de ligne valide. (Il correspond également au tout début de la chaîne, bien sûr.)

Notez que les séquences \A, \Z et \z peuvent être utilisées pour correspondre au début et à la fin du sujet dans les deux modes, et si toutes les branches d'un motif commencent par \A, il est toujours ancré, que PCRE2_MULTILINE soit défini ou non.

POINT FINAL (POINT) ET \N

En dehors d'une classe de caractères, un point dans le motif correspond à n'importe quel caractère dans la chaîne sujet, sauf (par défaut) un caractère qui signifie la fin d'une ligne. Un ou plusieurs caractères peuvent être spécifiés comme terminateurs de ligne (voir "Conventions de saut de ligne" ci-dessus).

Le point ne correspond jamais à un caractère de fin de ligne unique. Lorsque la séquence de deux caractères CRLF est la seule fin de ligne, le point ne correspond pas à CR s'il est immédiatement suivi de LF, mais sinon il correspond à tous les caractères (y compris les CR et LF isolés). Lorsque ANYCRLF est sélectionné pour les fins de ligne, aucune occurrence de CR ou LF ne correspond au point. Lorsque toutes les fins de ligne Unicode sont reconnues, le point ne correspond pas à CR, LF ou à aucun des autres caractères de fin de ligne.

Le comportement du point vis-à-vis des sauts de ligne peut être modifié. Si l'option PCRE2_DOTALL est définie, un point correspond à n'importe quel caractère, sans exception. Si la séquence de deux caractères CRLF est présente dans la chaîne sujet, il faut deux points pour la faire correspondre.

La gestion du point est entièrement indépendante de la gestion de l'accent circonflexe et du dollar, la seule relation étant qu'ils impliquent tous deux des sauts de ligne. Le point n'a pas de signification spéciale dans une classe de caractères.

La séquence d'échappement \N, lorsqu'elle n'est pas suivie d'une accolade ouvrante, se comporte comme un point, sauf qu'elle n'est pas affectée par l'option PCRE2_DOTALL. En d'autres termes, elle correspond à n'importe quel caractère, sauf un qui signifie la fin d'une ligne.

Lorsque \N est suivi d'une accolade ouvrante, il a une signification différente. Voir la section intitulée "Caractères non imprimables" ci-dessus pour plus de détails. Perl utilise également \N{nom} pour spécifier des caractères par leur nom Unicode ; PCRE2 ne prend pas en charge cela.

CORRESPONDANCE D'UN UNIQUE UNITÉ DE CODE

En dehors d'une classe de caractères, la séquence d'échappement \C correspond à n'importe quelle unité de code, que le mode UTF soit activé ou non. Dans la bibliothèque 8 bits, une unité de code est un octet ; dans la bibliothèque 16 bits, c'est une unité de 16 bits ; dans la bibliothèque 32 bits, c'est une unité de 32 bits. Contrairement à un point, \C correspond toujours aux caractères de fin de ligne. Cette fonctionnalité est fournie dans Perl pour correspondre à des octets individuels en mode UTF-8, mais il n'est pas clair comment elle peut être utilement utilisée.

Étant donné que \C divise les caractères en unités de code individuelles, la correspondance d'une unité avec \C en mode UTF-8 ou UTF-16 signifie que le reste de la chaîne peut commencer par un caractère UTF malformé. Cela a des résultats indéfinis, car PCRE2 suppose qu'il effectue une correspondance caractère par caractère dans une chaîne UTF valide (par défaut, il vérifie la validité de la chaîne sujet au début du traitement, sauf si l'option PCRE2_NO_UTF_CHECK ou PCRE2_MATCH_INVALID_UTF est utilisée).

Une application peut interdire l'utilisation de \C en définissant l'option PCRE2_NEVER_BACKSLASH_C lors de la compilation d'un motif. Il est également possible de construire PCRE2 avec l'utilisation de \C désactivée en permanence.

PCRE2 n'autorise pas \C à apparaître dans les assertions lookbehind (décrites ci-dessous) en modes UTF-8 ou UTF-16, car cela rendrait impossible le calcul de la longueur du lookbehind. Ni la fonction de correspondance alternative pcre2_dfa_match() ni l'optimiseur JIT ne prennent en charge \C dans ces modes UTF. La première génère une erreur au moment de la correspondance ; le second ne parvient pas à optimiser et la correspondance est donc toujours exécutée à l'aide de l'interpréteur.

Cependant, dans la bibliothèque 32 bits, \C est al

ways supported (when not explicitly locked out) because it always matches a single code unit, whether or not UTF-32 is specified.

In general, the \C escape sequence is best avoided. However, one way of using it that avoids the problem of malformed UTF-8 or UTF-16 characters is to use a lookahead to check the length of the next character, as in this pattern, which could be used with a UTF-8 string (ignore white space and line breaks):


(?| (?=[\x00-\x7f])(\C) |
(?=[\x80-\x{7ff}])(\C)(\C) |
(?=[\x{800}-\x{ffff}])(\C)(\C)(\C) |
(?=[\x{10000}-\x{1fffff}])(\C)(\C)(\C)(\C))

In this example, a group that starts with (?| resets the capturing parentheses numbers in each alternative (see "Duplicate Group Numbers" below). The assertions at the start of each branch check the next UTF-8 character for values whose encoding uses 1, 2, 3, or 4 bytes, respectively. The character's individual bytes are then captured by the appropriate number of \C groups.

BRACKETS CARRÉS ET CLASSES DE CARACTÈRES

An opening square bracket introduces a character class, terminated by a closing square bracket. A closing square bracket on its own is not special by default. If a closing square bracket is required as a member of the class, it should be the first data character in the class (after an initial circumflex, if present) or escaped with a backslash. This means that, by default, an empty class cannot be defined. However, if the PCRE2_ALLOW_EMPTY_CLASS option is set, a closing square bracket at the start does end the (empty) class.

A character class matches a single character in the subject. A matched character must be in the set of characters defined by the class, unless the first character in the class definition is a circumflex, in which case the subject character must not be in the set defined by the class. If a circumflex is actually required as a member of the class, ensure it is not the first character, or escape it with a backslash.

For example, the character class [aeiou] matches any lower case English vowel, whereas [^aeiou] matches all other characters. Note that a circumflex is just a convenient notation for specifying the characters that are in the class by enumerating those that are not. A class that starts with a circumflex is not an assertion; it still consumes a character from the subject string, and therefore it fails to match if the current pointer is at the end of the string.

Characters in a class may be specified by their code points using \o, \x, or \N{U+hh..} in the usual way. When caseless matching is set, any letters in a class represent both their upper case and lower case versions, so for example, a caseless [aeiou] matches "A" as well as "a", and a caseless [^aeiou] does not match "A", whereas a caseful version would. Note that there are two ASCII characters, K and S, that, in addition to their lower case ASCII equivalents, are case-equivalent with Unicode U+212A (Kelvin sign) and U+017F (long S) respectively when either PCRE2_UTF or PCRE2_UCP is set. If you do not want these ASCII/non-ASCII case equivalences, you can suppress them by setting PCRE2_EXTRA_CASELESS_RESTRICT, either as an option in a compile context, or by including (*CASELESS_RESTRICT) or (?r) within a pattern.

Characters that might indicate line breaks are never treated in any special way when matching character classes, whatever line-ending sequence is in use, and whatever setting of the PCRE2_DOTALL and PCRE2_MULTILINE options is used. A class such as [^a] always matches one of these characters.

The generic character type escape sequences \d, \D, \h, \H, \p, \P, \s, \S, \v, \V, \w, and \W may appear in a character class, and add the characters that they match to the class. For example, [\dABCDEF] matches any hexadecimal digit. In UTF modes, the PCRE2_UCP option affects the meanings of \d, \s, \w and their upper case partners, just as it does when they appear outside a character class, as described in the section entitled "Generic character types" above. The escape sequence \b has a different meaning inside a character class; it matches the backspace character. The sequences \B, \R, and \X are not special inside a character class. Like any other unrecognized escape sequences, they cause an error. The same is true for \N when not followed by an opening brace.

The minus (hyphen) character can be used to specify a range of characters in a character class. For example, [d-m] matches any letter between d and m, inclusive. If a minus character is required in a class, it must be escaped with a backslash or appear in a position where it cannot be interpreted as indicating a range, typically as the first or last character in the class, or immediately after a range. For example, [b-d-z] matches letters in the range b to d, a hyphen character, or z.

There is some special treatment for alphabetic ranges in EBCDIC environments; see the section "EBCDIC environments" below.

Perl treats a hyphen as a literal if it appears before or after a POSIX class (see below) or before or after a character type escape such as \d or \H. However, unless the hyphen is the last character in the class, Perl outputs a warning in its warning mode, as this is most likely a user error. As PCRE2 has no facility for warning, an error is given in these cases.

It is not possible to have the literal character "]" as the end character of a range. A pattern such as [W-]46] is interpreted as a class of two characters ("W" and "-") followed by a literal string "46]", so it would match "W46]" or "-46]". However, if the "]" is escaped with a backslash it is interpreted as the end of a range, so [W-\]46] is interpreted as a class containing a range and two other characters. The octal or hexadecimal representation of "]" can also be used to end a range.

Ranges normally include all code points between the start and end characters, inclusive. They can also be used for code points specified numerically, for example [\000-\037]. Ranges can include any characters that are valid for the current mode. In any UTF mode, the so-called "surrogate" characters (those whose code points lie between 0xd800 and 0xdfff inclusive) may not be specified explicitly by default (the PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES option disables this check). However, ranges such as [\x{d7ff}-\x{e000}], which include the surrogates, are always permitted.

If a range that includes letters is used when caseless matching is set, it matches the letters in either case. For example, [W-c] is equivalent to [][\\^_`wxyzabc], matched caselessly, and in a non-UTF mode, if character tables for a French locale are in use, [\xc8-\xcb] matches accented E characters in both cases.

A circumflex can conveniently be used with the upper case character types to specify a more restricted set of characters than the matching lower case type. For example, the class [^\W_] matches any letter or digit, but not underscore, whereas [\w] includes underscore. A positive character class should be read as "something OR something OR ..." and a negative class as "NOT something AND NOT something AND NOT ...".

The metacharacters that are recognized in character classes are backslash, hyphen (when it can be interpreted as specifying a range), circumflex (only at the start), and the terminating closing square bracket. An opening square bracket is also special when it can be interpreted as introducing a POSIX class (see "Posix character classes" below), or a special compatibility feature (see "Compatibility feature for word boundaries" below. Escaping any non-alphanumeric character in a class turns it into a literal, whether or not it would otherwise be a metacharacter.

CLASSES DE CARACTÈRES ÉTENDUES PERL

From release 10.45 PCRE2 supports Perl's (?[...]) extended character class syntax. This can be used to perform set operations such as intersection on character classes.

The syntax permitted within (?[...]) is quite different to ordinary character classes. Inside the extended class, there is an expression syntax consisting of "atoms", operators, and ordinary parentheses "()" used for grouping. Such classes always have the Perl /xx modifier (PCRE2 option PCRE2_EXTENDED_MORE) turned on within them. This means that literal space and tab characters are ignored everywhere in the class.

The allowed atoms are individual characters specified by escape sequences such as \n or \x{123}, character types such as \d, POSIX classes such as [:alpha:], and nested ordinary (non-extended) character classes. For example, in (?[\d & [...]]) the nested class [...] follows the usual rules for ordinary character classes, in which parentheses are not metacharacters, and character literals and ranges are permitted.

Character literals and ranges may not appear outside a nested ordinary character class because they are not atoms in the extended syntax. The extended syntax does not introduce any additional escape sequences, so (?[\y]) is an unknown escape, as it would be in [\y].

In the extended syntax, ^ does not negate a class (except within an ordinary class nested inside an extended class); it is instead a binary operator.

The binary operators are "&" (intersection), "|" or "+" (union), "-" (subtraction) and "^" (symmetric difference). These are left-associative and "&" has higher (tighter) precedence, while the others have equal lower precedence. The one prefix unary operator is "!" (complement), with highest precedence.

CLASSES DE CARACTÈRES ÉTENDUES UTS#18

The PCRE2_ALT_EXTENDED_CLASS option enables an alternative to Perl's (?[...]) syntax, allowing instead extended class behaviour inside ordinary [...] character classes. This altered syntax for [...] classes is loosely described by the Unicode standard UTS#18. The PCRE2_ALT_EXTENDED_CLASS option does not prevent use of (?[...]) classes; it just changes the meaning of all [...] classes that are not nested inside a Perl (?[...]) class.

Firstly, in ordinary Perl [...] syntax, an expression such as "[a[]" is a character class with two literal characters "a" and "[", but in UTS#18 extended classes the "[" character becomes an additional metacharacter within classes, denoting the start of a nested class, so a literal "[" must be escaped as "\[".

Secondly, within the UTS#18 extended syntax

, il existe des opérateurs "||", "&&", "--" et "~~" qui désignent respectivement l'union, l'intersection, la soustraction et la différence symétrique des classes de caractères. En syntaxe Perl standard, il s'agirait simplement de littéraux répétitifs inutiles (à l'exception de "--" qui pourrait être le début ou la fin d'une plage). Dans les classes étendues UTS#18, ces opérateurs peuvent être utilisés dans des constructions telles que [\p{L}--[QW]] pour "lettres Unicode, autres que Q et W". Un "-" littéral au début ou à la fin d'une plage doit être échappé, de sorte que si "[--1]" en syntaxe Perl est la plage allant du tiret à "1", il doit être échappé comme "[\--1]" dans les classes étendues UTS#18.

Contrairement aux classes étendues (?[...]) de Perl, l'option PCRE2_EXTENDED_MORE pour ignorer les caractères d'espace et de tabulation n'est pas automatiquement activée pour les classes étendues UTS#18, mais elle est respectée si elle est définie.

Les classes étendues UTS#18 peuvent être imbriquées, et les classes imbriquées sont elles-mêmes des classes étendues (contrairement à Perl, où les classes imbriquées doivent être des classes simples). Par exemple, [\p{L}&&[\p{Thai}||\p{Greek}]] correspond à toute lettre qui se trouve dans les scripts thaïlandais ou grecs. Notez que cela signifie qu'aucun caractère de groupement spécial (tel que les parenthèses utilisées dans la syntaxe de classe (?[...]) de Perl) n'est nécessaire.

Les éléments de classe individuels (caractères littéraux, plages littérales, propriétés telles que \d ou \p{...}, et classes imbriquées) peuvent être combinés par juxtaposition ou par un opérateur. La juxtaposition est l'opérateur d'union implicite, et a une priorité plus élevée que tout opérateur explicite. Ainsi, une séquence de littéraux et/ou de plages se comporte comme si elle était entourée de crochets. Par exemple, [A-Z0-9&&[^E8]] est identique à [[A-Z0-9]&&[^E8]], ce qui correspond à tout caractère alphanumérique majuscule à l'exception de "E" ou "8".

La priorité entre les opérateurs explicites n'est pas définie, de sorte que le mélange d'opérateurs est une erreur de syntaxe. Par exemple, [A&&B--C] est une erreur, mais [A&&[B--C]] est valide.

Il s'agit d'une syntaxe émergente qui est progressivement adoptée dans l'écosystème des expressions régulières : par exemple, JavaScript a adopté le drapeau "/v" dans ECMAScript 2024 ; le module "re" de Python réserve la syntaxe pour une utilisation future avec un FutureWarning pour l'utilisation non échappée de "[" comme littéral dans les classes de caractères. En raison du manque de directives d'UTS#18, les moteurs interprètent la syntaxe différemment. Le crate "regex" de Rust et le module PyPi "regex" de Python implémentent tous deux les classes étendues UTS#18, mais avec de légères incompatibilités ([A||B&&C] est analysé comme [A||[B&&C]] dans "regex" de Python, mais comme [[A||B]&&C] dans "regex" de Rust).

La syntaxe de PCRE2 ajoute des restrictions syntaxiques similaires au drapeau /v d'ECMAScript, de sorte que toutes les classes étendues UTS#18 acceptées comme valides par PCRE2 ont la propriété d'être interprétées soit avec le même comportement, soit comme invalides, par tous les autres moteurs majeurs. Veuillez signaler un problème si vous êtes au courant de différences de comportement entre PCRE2 et un autre moteur majeur.

CLASSES DE CARACTÈRES POSIX

Perl prend en charge la notation POSIX pour les classes de caractères. Elle utilise des noms entourés de [: et :] à l'intérieur des crochets englobants. PCRE2 prend également en charge cette notation, dans les classes ordinaires et étendues. Par exemple,


[01[:alpha:]%]

correspond à "0", "1", toute lettre alphabétique, ou "%". Les noms de classes pris en charge sont :


alnum lettres et chiffres
alpha lettres
ascii codes de caractères 0 - 127
blank espace ou tabulation uniquement
cntrl caractères de contrôle
digit chiffres décimaux (identique à \d)
graph caractères imprimables, à l'exclusion de l'espace
lower lettres minuscules
print caractères imprimables, y compris l'espace
punct caractères imprimables, à l'exclusion des lettres et des chiffres et de l'espace
space espaces blancs (identique à \s depuis PCRE2 8.34)
upper lettres majuscules
word caractères de "mot" (identique à \w)
xdigit chiffres hexadécimaux

Les caractères "espace" par défaut sont HT (9), LF (10), VT (11), FF (12), CR (13), et espace (32). Si une correspondance locale est en cours, la liste des caractères d'espace peut être différente ; il peut y en avoir moins ou plus. "Space" et \s correspondent au même ensemble de caractères, tout comme "word" et \w.

Le nom "word" est une extension Perl, et "blank" est une extension GNU de Perl 5.8. Une autre extension Perl est la négation, indiquée par un caractère ^ après le deux-points. Par exemple,


[12[:^digit:]]

correspond à "1", "2", ou tout ce qui n'est pas un chiffre. PCRE2 (et Perl) reconnaissent également la syntaxe POSIX [.ch.] et [=ch=] où "ch" est un "élément de collation", mais ceux-ci ne sont pas pris en charge, et une erreur est signalée s'ils sont rencontrés.

Par défaut, les caractères dont la valeur est supérieure à 127 ne correspondent à aucune des classes de caractères POSIX, bien que cela puisse être différent pour les caractères de la plage 128-255 lorsque des correspondances locales sont en cours. Cependant, en mode UCP, sauf si certaines options sont définies (voir ci-dessous), certaines des classes sont modifiées de manière à utiliser les propriétés des caractères Unicode. Ceci est réalisé en remplaçant les classes POSIX par d'autres séquences, comme suit :


[:alnum:] devient \p{Xan}
[:alpha:] devient \p{L}
[:blank:] devient \h
[:cntrl:] devient \p{Cc}
[:digit:] devient \p{Nd}
[:lower:] devient \p{Ll}
[:space:] devient \p{Xps}
[:upper:] devient \p{Lu}
[:word:] devient \p{Xwd}

Les versions niées, telles que [:^alpha:], utilisent \P au lieu de \p. Quatre autres classes POSIX sont traitées spécialement en mode UCP :

[:graph:]
Correspond aux caractères qui ont des glyphes qui marquent la page lors de l'impression. En termes de propriétés Unicode, cela correspond à tous les caractères ayant les propriétés L, M, N, P, S ou Cf, à l'exception de :


U+061C Marque de lettre arabe
U+180E Séparateur de voyelle mongole
U+2066 - U+2069 Divers "isolats"

[:print:]
Correspond aux mêmes caractères que [:graph:] plus les caractères d'espace qui ne sont pas des contrôles, c'est-à-dire les caractères ayant la propriété Zs.
[:punct:]
Correspond à tous les caractères ayant la propriété Unicode P (ponctuation), plus les caractères dont les points de code sont inférieurs à 256 et qui ont la propriété S (Symbole).
[:xdigit:]
En plus des chiffres hexadécimaux ASCII, cela correspond également aux versions "pleine chasse" de ces caractères, dont les points de code Unicode commencent à U+FF10. Il s'agit d'un changement apporté dans la version 10.43 de PCRE2 pour la compatibilité avec Perl.

Les autres classes POSIX ne sont pas modifiées par PCRE2_UCP et ne correspondent qu'aux caractères dont les points de code sont inférieurs à 256.

Il existe deux options qui peuvent être utilisées pour restreindre les classes POSIX aux caractères ASCII lorsque PCRE2_UCP est défini. L'option PCRE2_EXTRA_ASCII_DIGIT affecte uniquement [:digit:] et [:xdigit:]. Dans un motif, cela peut être défini et annulé par (?aT) et (?-aT). L'option PCRE2_EXTRA_ASCII_POSIX désactive le traitement UCP pour toutes les classes POSIX, y compris [:digit:] et [:xdigit:]. Dans un motif, (?aP) et (?-aP) définissent et annulent ces deux options pour plus de cohérence.

FONCTIONNALITE DE COMPATIBILITE POUR LES LIMITES DE MOT

Dans la bibliothèque conforme POSIX.2 incluse dans le système Unix 4.4BSD, la syntaxe laide [[:<:]] et [[:>:]] est utilisée pour faire correspondre le "début de mot" et la "fin de mot". PCRE2 traite ces éléments comme suit :


[[:<:]] est converti en \b(?=\w)
[[:>:]] est converti en \b(?<=\w)

Seules ces séquences de caractères exactes sont reconnues. Une séquence telle que [a[:<:]b] provoque une erreur pour un nom de classe POSIX non reconnu. Cette prise en charge n'est pas compatible avec Perl. Elle est fournie pour aider aux migrations depuis d'autres environnements, et il est préférable de ne pas l'utiliser dans de nouveaux motifs. Notez que \b correspond au début et à la fin d'un mot (voir "Assertions simples" ci-dessus), et dans un motif de style Perl, le caractère précédant ou suivant indique normalement lequel est souhaité, sans avoir besoin des assertions utilisées ci-dessus pour donner exactement le comportement POSIX. Notez également que l'option PCRE2_UCP modifie la signification de \w (et donc de \b) par défaut, elle affecte donc également ces séquences POSIX.

BARRE VERTICALE

Les caractères de barre verticale sont utilisés pour séparer les motifs alternatifs. Par exemple, le motif


gilbert|sullivan

correspond soit à "gilbert", soit à "sullivan". Un nombre quelconque d'alternatives peut apparaître, et une alternative vide est autorisée (correspondant à la chaîne vide). Le processus de correspondance essaie chaque alternative tour à tour, de gauche à droite, et la première qui réussit est utilisée. Si les alternatives sont à l'intérieur d'un groupe (défini ci-dessous), "réussit" signifie qu'elle fait correspondre le reste du motif principal ainsi que l'alternative du groupe.

REGLEMENT DES OPTIONS INTERNES

Les paramètres de plusieurs options peuvent être modifiés à l'intérieur d'un motif par une séquence de lettres entourées de "(?" et ")". Les suivantes sont compatibles avec Perl et sont décrites en détail dans la documentation **pcre2api**. Les lettres d'option sont :


i pour PCRE2_CASELESS
m pour PCRE2_MULTILINE
n pour PCRE2_NO_AUTO_CAPTURE
s pour PCRE2_DOTALL
x pour PCRE2_EXTENDED
xx pour PCRE2_EXTENDED_MORE

Par exemple, (?im) définit la casse insensible et le mode multiligne. Il est également possible d'annuler ces options en faisant précéder les lettres pertinentes d'un trait d'union, par exemple (?-im). Les deux options "étendues" ne sont pas indépendantes ; annuler l'une ou l'autre annule les effets des deux.

Un réglage et une annulation combinés tels que (?im-sx), qui définit PCRE2_CASELESS et PCRE2_MULTILINE tout en annulant PCRE2_DOTALL et PCRE2_EXTENDED, sont également autorisés. Un seul trait d'union peut apparaître dans la chaîne d'options. Si une lettre apparaît avant et après le trait d'union, l'option est annulée. Un réglage d'options vide "(?)" est autorisé. Inutile de dire qu'il n'a aucun effet.

Si le premier caractère suivant (? est un accent circonflexe, il annule toutes les options ci-dessus. Des lettres peuvent suivre l'accent circonflexe pour réinstaurer certaines options, mais un trait d'union ne peut pas apparaître.

OPTIONS

The options described in this section are set and unset by codes embedded within the pattern itself. They affect the matching process from the point at which they occur. Options can be set using (?i), (?s), (?m), (?x), and (?u). Their opposites are (?I), (?S), (?M), (?X), and (?U), respectively. These options can be combined, for example, (?imsx). They can also be turned off using a caret: (?^i), (?^s), (?^m), (?^x), (?^u).

There is also a special option 'a' which, when set, restricts certain items to match only ASCII characters, irrespective of whether the pattern is otherwise a Unicode pattern. The ASCII-restricted items are listed below. The 'a' option can be combined with the others, for example (?ai). Its opposite is (?A).

The ASCII restriction applies to:

  • The POSIX character classes: ., \d, \D, \s, \S, \w, \W, \b, \B. When 'a' is set, these match only the ASCII characters that correspond to them. For example, \d matches only [0-9].

  • The POSIX character classes [[:alnum:]], [[:alpha:]], [[:digit:]], [[:lower:]], [[:print:]], [[:punct:]], [[:space:]], [[:upper:]], [[:word:]], and [[:xdigit:]].

  • The characters ., \s, \S, \w, and \W.

The 'a' option itself can be controlled by using pairs or individual letters:


aD for PCRE2_EXTRA_ASCII_BSD
aS for PCRE2_EXTRA_ASCII_BSS
aW for PCRE2_EXTRA_ASCII_BSW
aP for PCRE2_EXTRA_ASCII_POSIX and PCRE2_EXTRA_ASCII_DIGIT
aT for PCRE2_EXTRA_ASCII_DIGIT
r for PCRE2_EXTRA_CASELESS_RESTRICT
J for PCRE2_DUPNAMES
U for PCRE2_UNGREEDY

However, except for 'r', these are not unset by (?^), which is equivalent to (?-imnrsx). If 'a' is not followed by any of the upper case letters shown above, it sets (or unsets) all the ASCII options.

PCRE2_EXTRA_ASCII_DIGIT has no additional effect when PCRE2_EXTRA_ASCII_POSIX is set, but including it in (?aP) means that (?-aP) suppresses all ASCII restrictions for POSIX classes.

When one of these option changes occurs at top level (that is, not inside group parentheses), the change applies until a subsequent change, or the end of the pattern. An option change within a group (see below for a description of groups) affects only that part of the group that follows it. At the end of the group these options are reset to the state they were before the group. For example,


(a(?i)b)c

matches abc and aBc and no other strings (assuming PCRE2_CASELESS is not set externally). Any changes made in one alternative do carry on into subsequent branches within the same group. For example,


(a(?i)b|c)

matches "ab", "aB", "c", and "C", even though when matching "C" the first branch is abandoned before the option setting. This is because the effects of option settings happen at compile time. There would be some very weird behaviour otherwise.

As a convenient shorthand, if any option settings are required at the start of a non-capturing group (see the next section), the option letters may appear between the "?" and the ":". Thus the two patterns


(?i:saturday|sunday)
(?:(?i)saturday|sunday)

match exactly the same set of strings.

Note: There are other PCRE2-specific options, applying to the whole pattern, which can be set by the application when the compiling function is called. In addition, the pattern can contain special leading sequences such as (*CRLF) to override what the application has set or what has been defaulted. Details are given in the section entitled "Newline sequences" above. There are also the (*UTF) and (*UCP) leading sequences that can be used to set UTF and Unicode property modes; they are equivalent to setting the PCRE2_UTF and PCRE2_UCP options, respectively. However, the application can set the PCRE2_NEVER_UTF or PCRE2_NEVER_UCP options, which lock out the use of the (*UTF) and (*UCP) sequences.

GROUPES

Les groupes sont délimités par des parenthèses (rondes), qui peuvent être imbriquées. Transformer une partie d'un motif en groupe fait deux choses :

1. Il localise un ensemble d'alternatives. Par exemple, le motif


cat(aract|erpillar|)

correspond à « cataract », « caterpillar », ou « cat ». Sans les parenthèses, il correspondrait à « cataract », « erpillar » ou une chaîne vide.

2. Il crée un « groupe de capture ». Cela signifie que, lorsque le motif entier correspond, la partie de la chaîne objet qui a correspondu au groupe est renvoyée à l'appelant, séparément de la partie qui a correspondu au motif entier. (Cela ne s'applique qu'à la fonction de correspondance traditionnelle ; la fonction de correspondance DFA ne prend pas en charge la capture.)

Les parenthèses ouvrantes sont comptées de gauche à droite (en commençant par 1) pour obtenir les numéros des groupes de capture. Par exemple, si la chaîne « the red king » est mise en correspondance avec le motif


the ((red|white) (king|queen))

les sous-chaînes capturées sont « red king », « red » et « king », et sont numérotées respectivement 1, 2 et 3.

Le fait que les parenthèses simples remplissent deux fonctions n'est pas toujours utile. Il y a souvent des moments où un regroupement est requis sans capture. Si une parenthèse ouvrante est suivie d'un point d'interrogation et de deux points, le groupe ne fait aucune capture et n'est pas compté lors du calcul du nombre de groupes de capture ultérieurs. Par exemple, si la chaîne « the white queen » est mise en correspondance avec le motif


the ((?:red|white) (king|queen))

les sous-chaînes capturées sont « white queen » et « queen », et sont numérotées 1 et 2. Le nombre maximum de groupes de capture est de 65535.

Par souci de commodité, si des paramètres d'option sont requis au début d'un groupe non-capturant (voir la section suivante), les lettres d'option peuvent apparaître entre le « ? » et le « : ». Ainsi, les deux motifs


(?i:saturday|sunday)
(?:(?i)saturday|sunday)

correspondent exactement au même ensemble de chaînes. Comme les branches alternatives sont essayées de gauche à droite, et que les options ne sont pas réinitialisées avant la fin du groupe, un réglage d'option dans une branche affecte les branches suivantes, de sorte que les motifs ci-dessus correspondent à « SUNDAY » ainsi qu'à « Saturday ».

NUMÉROS DE GROUPE EN DOUBLON

Perl 5.10 a introduit une fonctionnalité permettant à chaque alternative d'un groupe d'utiliser les mêmes numéros pour ses parenthèses de capture. Un tel groupe commence par (?| et est lui-même un groupe non-capturant. Par exemple, considérez ce motif :


(?|(Sat)ur|(Sun))day

Comme les deux alternatives sont à l'intérieur d'un groupe (?|, les deux ensembles de parenthèses de capture sont numérotés un. Ainsi, lorsque le motif correspond, vous pouvez consulter la sous-chaîne capturée numéro un, quelle que soit l'alternative qui a correspondu. Cette construction est utile lorsque vous souhaitez capturer une partie, mais pas tout, d'une ou plusieurs alternatives. À l'intérieur d'un groupe (?|, les parenthèses sont numérotées comme d'habitude, mais le numéro est réinitialisé au début de chaque branche. Les numéros de toutes les parenthèses de capture qui suivent le groupe entier commencent après le numéro le plus élevé utilisé dans n'importe quelle branche. L'exemple suivant est tiré de la documentation Perl. Les numéros ci-dessous indiquent dans quel tampon le contenu capturé sera stocké.


# avant ---------------réinitialisation-branche----------- après
/ ( a ) (?| x ( y ) z | (p (q) r) | (t) u (v) ) ( z ) /x
# 1 2 2 3 2 3 4

Une référence arrière à un groupe de capture utilise la valeur la plus récente définie pour le groupe. Le motif suivant correspond à « abcabc » ou « defdef » :


/(?|(abc)|(def))\1/

En revanche, un appel de sous-routine à un groupe de capture fait toujours référence au premier groupe du motif portant ce numéro. Le motif suivant correspond à « abcabc » ou « defabc » :


/(?|(abc)|(def))(?1)/

Une référence relative comme (?-1) n'est pas différente : c'est juste un moyen pratique de calculer un numéro de groupe absolu.

Si un test conditionnel d'un groupe indiquant qu'il a correspondu fait référence à un numéro non unique, le test est vrai si un groupe portant ce numéro a correspondu.

Une approche alternative à l'utilisation de cette fonctionnalité de « réinitialisation de branche » consiste à utiliser des groupes nommés en doublon, comme décrit dans la section suivante.

GROUPES DE CAPTURE NOMMÉS

Identifier les groupes de capture par numéro est simple, mais il peut être très difficile de suivre les numéros dans des motifs compliqués. De plus, si une expression est modifiée, les numéros peuvent changer. Pour pallier cette difficulté, PCRE2 prend en charge la dénomination des groupes de capture. Cette fonctionnalité n'a été ajoutée à Perl qu'à la version 5.10. Python avait la fonctionnalité plus tôt, et PCRE1 l'a introduite à la version 4.0, en utilisant la syntaxe Python. PCRE2 prend en charge à la fois la syntaxe Perl et la syntaxe Python.

Dans PCRE2, un groupe de capture peut être nommé de l'une des trois manières suivantes : (?<nom>...) ou (?'nom'...) comme dans Perl, ou (?P<nom>...) comme dans Python. Les noms peuvent avoir jusqu'à 128 unités de code de long. Lorsque PCRE2_UTF n'est pas défini, ils ne peuvent contenir que des caractères alphanumériques ASCII et des tirets bas, mais doivent commencer par un non-chiffre. Lorsque PCRE2_UTF est défini, la syntaxe des noms de groupe est étendue pour permettre toutes les lettres Unicode ou tous les chiffres décimaux Unicode. En d'autres termes, les noms de groupe doivent correspondre à l'un de ces motifs :


^[_A-Za-z][_A-Za-z0-9]*\z lorsque PCRE2_UTF n'est pas défini
^[_\p{L}][_\p{L}\p{Nd}]*\z lorsque PCRE2_UTF est défini

Les références aux groupes de capture à partir d'autres parties du motif, telles que les références arrière, la récursion et les conditions, peuvent toutes être faites par nom ainsi que par numéro.

Les groupes de capture nommés se voient attribuer des numéros ainsi que des noms, exactement comme si les noms n'étaient pas présents. Dans PCRE2 et Perl, les groupes de capture sont principalement identifiés par des numéros ; tous les noms ne sont que des alias pour ces numéros. L'API PCRE2 fournit des appels de fonction pour extraire la table complète de traduction nom-numéro d'un motif compilé, ainsi que des fonctions pratiques pour extraire des sous-chaînes capturées par nom.

Attention : Lorsque plusieurs groupes de capture portent le même numéro, comme décrit dans la section précédente, un nom donné à l'un d'eux s'applique à tous. Perl autorise des groupes de numéros identiques à avoir des noms différents. Considérez ce motif, où il y a deux groupes de capture, tous deux numérotés 1 :


(?|(?<AA>aa)|(?<BB>bb))

Perl autorise cela, avec les deux noms AA et BB comme alias du groupe 1. Ainsi, après une correspondance réussie, les deux noms donnent la même valeur (soit « aa », soit « bb »).

Dans une tentative de réduire la confusion, PCRE2 n'autorise pas le même numéro de groupe à être associé à plus d'un nom. L'exemple ci-dessus provoque une erreur à la compilation. Cependant, il reste encore une marge de confusion. Considérez ce motif :


(?|(?<AA>aa)|(bb))

Bien que le deuxième numéro de groupe 1 ne soit pas explicitement nommé, le nom AA est toujours un alias pour tout groupe 1. Que le motif corresponde à « aa » ou à « bb », une référence par nom au groupe AA renvoie la chaîne correspondante.

Par défaut, un nom doit être unique dans un motif, à l'exception du fait que les noms en double sont autorisés pour les groupes portant le même numéro, par exemple :


(?|(?<AA>aa)|(?<AA>bb))

La contrainte de nom dupliqué peut être désactivée en définissant l'option PCRE2_DUPNAMES au moment de la compilation, ou en utilisant (?J) dans le motif, comme décrit dans la section « Réglage des options internes » ci-dessus.

Les noms dupliqués peuvent être utiles pour les motifs où une seule instance du groupe de capture nommé peut correspondre. Supposons que vous souhaitiez faire correspondre le nom d'un jour de la semaine, soit

r comme abréviation de 3 lettres ou comme nom complet, et dans les deux cas, vous voulez extraire l'abréviation. Ce motif (en ignorant les sauts de ligne) fait l'affaire :


(?J)
(?<DN>Mon|Fri|Sun)(?:day)?|
(?<DN>Tue)(?:sday)?|
(?<DN>Wed)(?:nesday)?|
(?<DN>Thu)(?:rsday)?|
(?<DN>Sat)(?:urday)?

Il y a cinq groupes de capture, mais un seul est défini après une correspondance. Les fonctions pratiques pour extraire les données par nom renvoient la sous-chaîne du premier (et dans cet exemple, le seul) groupe de ce nom qui a correspondu. Cela évite de chercher quel groupe numéroté il s'agissait. (Une autre façon de résoudre ce problème est d'utiliser un groupe de « réinitialisation de branche », comme décrit dans la section précédente.)

Si vous faites une référence arrière à un groupe nommé non unique depuis ailleurs dans le motif, les groupes auxquels le nom fait référence sont vérifiés dans l'ordre où ils apparaissent dans le motif global. Le premier qui est défini est utilisé pour la référence. Par exemple, ce motif correspond à la fois à « foofoo » et à « barbar », mais pas à « foobar » ni à « barfoo » :


(?J)(?:(?<n>foo)|(?<n>bar))\k<n>

Si vous faites un appel de sous-programme à un groupe nommé non unique, celui qui correspond à la première occurrence du nom est utilisé. En l'absence de doublons, c'est celui qui a le plus petit numéro.

Si vous utilisez une référence nommée dans un test conditionnel (voir la section sur les conditions ci-dessous), soit pour vérifier si un groupe de capture a correspondu, soit pour vérifier la récursivité, tous les groupes portant le même nom sont testés. Si la condition est vraie pour l'un d'entre eux, la condition globale est vraie. C'est le même comportement que le test par numéro. Pour plus de détails sur les interfaces de gestion des groupes de capture nommés, voir la documentation de pcre2api.

RÉPÉTITION

La répétition est spécifiée par des quantificateurs, qui peuvent suivre l'un des éléments suivants :


un caractère de données littéral
le métacaractère point
la séquence d'échappement \C
la séquence d'échappement \R
la séquence d'échappement \X
toute séquence d'échappement qui correspond à un seul caractère
une classe de caractères
une référence arrière
un groupe entre parenthèses (y compris les assertions de lookaround)
un appel de sous-programme (récursif ou autre)

Si un quantificateur ne suit pas un élément répétable, une erreur se produit. Le quantificateur de répétition général spécifie un nombre minimum et maximum de correspondances autorisées en donnant deux nombres entre accolades {}, séparés par une virgule. Les nombres doivent être inférieurs à 65536, et le premier doit être inférieur ou égal au second. Par exemple,


z{2,4}

correspond à « zz », « zzz » ou « zzzz ». Une accolade fermante isolée n'est pas un caractère spécial. Si le deuxième nombre est omis, mais que la virgule est présente, il n'y a pas de limite supérieure ; si le deuxième nombre et la virgule sont tous deux omis, le quantificateur spécifie un nombre exact de correspondances requises. Ainsi,


[aeiou]{3,}

correspond à au moins 3 voyelles successives, mais peut en correspondre beaucoup plus, tandis que


\d{8}

correspond à exactement 8 chiffres. Si le premier nombre est omis, la limite inférieure est prise comme zéro ; dans ce cas, la limite supérieure doit être présente.


X{,4} est interprété comme X{0,4}

C'est un changement de comportement qui s'est produit dans Perl 5.34.0 et PCRE2 10.43. Dans les versions antérieures, une telle séquence n'était pas interprétée comme un quantificateur. D'autres moteurs d'expressions régulières peuvent se comporter de l'une ou l'autre manière.

Si les caractères qui suivent une accolade ouvrante ne correspondent pas à la syntaxe d'un quantificateur, l'accolade est prise comme un caractère littéral. Cela signifie en particulier que {,} est une chaîne littérale de trois caractères.

Notez que toutes les accolades ouvrantes ne sont pas potentiellement le début d'un quantificateur, car les accolades sont utilisées dans d'autres éléments tels que \N{U+345} ou \k{name}.

En modes UTF, les quantificateurs s'appliquent aux caractères plutôt qu'aux unités de code individuelles. Ainsi, par exemple, \x{100}{2} correspond à deux caractères, chacun représenté par une séquence de deux octets dans une chaîne UTF-8. De même, \X{3} correspond à trois clusters de graphèmes étendus Unicode, chacun pouvant comporter plusieurs unités de code (et ils peuvent avoir des longueurs différentes).

Le quantificateur {0} est autorisé, faisant en sorte que l'expression se comporte comme si l'élément précédent et le quantificateur n'étaient pas présents. Cela peut être utile pour les groupes de capture qui sont référencés comme sous-programmes depuis ailleurs dans le motif (mais voir aussi la section intitulée « Définition de groupes de capture à utiliser par référence uniquement » ci-dessous). À l'exception des groupes entre parenthèses, les éléments ayant un quantificateur {0} sont omis du motif compilé.

Pour plus de commodité, les trois quantificateurs les plus courants ont des abréviations d'un seul caractère :


* équivaut à {0,}
+ équivaut à {1,}
? équivaut à {0,1}

Il est possible de construire des boucles infinies en faisant suivre un groupe qui ne peut correspondre à aucun caractère par un quantificateur sans limite supérieure, par exemple :


(a?)*

Les versions antérieures de Perl et PCRE1 généraient une erreur à la compilation pour de tels motifs. Cependant, comme il existe des cas où cela peut être utile, de tels motifs sont maintenant acceptés, mais chaque fois qu'une itération d'un tel groupe ne correspond à aucun caractère, la correspondance passe à l'élément suivant du motif au lieu de correspondre répétitivement à une chaîne vide. Cela n'empêche pas le retour arrière dans l'une des itérations si un élément ultérieur ne correspond pas.

Par défaut, les quantificateurs sont « gourmands », c'est-à-dire qu'ils correspondent autant que possible (jusqu'au nombre maximum de répétitions autorisées), sans provoquer l'échec du reste du motif. L'exemple classique où cela pose problème est la tentative de faire correspondre des commentaires en C. Ceux-ci apparaissent entre /* et */ et à l'intérieur du commentaire, des caractères * et / individuels peuvent apparaître. Une tentative de faire correspondre des commentaires C en appliquant le motif


/\*.*\*/

à la chaîne


/* premier commentaire */ pas commentaire /* second commentaire */

échoue, car elle correspond à toute la chaîne en raison de la gourmandise de l'élément .*. Cependant, si un quantificateur est suivi d'un point d'interrogation, il cesse d'être gourmand, et correspond plutôt au nombre minimum de fois possible, donc le motif


/\*.*?\*/

fait le bon travail avec les commentaires C. La signification des divers quantificateurs n'est pas modifiée autrement, seulement le nombre de correspondances préférées. Ne confondez pas cette utilisation du point d'interrogation avec son utilisation comme quantificateur en soi. Parce qu'il a deux usages, il peut parfois apparaître doublé, comme dans


\d??\d

qui correspond à un chiffre par préférence, mais peut en correspondre deux si c'est la seule façon pour le reste du motif de correspondre.

Si l'option PCRE2_UNGREEDY est définie (une option qui n'est pas disponible dans Perl), les quantificateurs ne sont pas gourmands par défaut, mais des quantificateurs individuels peuvent être rendus gourmands en les suivant d'un point d'interrogation. Autrement dit, cela inverse le comportement par défaut.

Lorsqu'un groupe entre parenthèses est quantifié avec un nombre minimum de répétitions supérieur à 1 ou avec un maximum limité, plus de mémoire est nécessaire pour le motif compilé, proportionnellement à la taille du minimum ou du maximum.

Si un motif commence par .* ou .{0,} et que l'option PCRE2_DOTALL (équivalent au /s de Perl) est définie, permettant ainsi au point de correspondre aux sauts de ligne, le motif est implicitement ancré, car ce qui suit sera essayé contre chaque position de caractère dans la chaîne sujet, il est donc inutile de retenter la correspondance globale à n'importe quelle position après la première. PCRE2 traite normalement un tel motif comme s'il était précédé de \A.

Dans les cas où l'on sait que la chaîne sujet ne contient pas de sauts de ligne, il est utile de définir PCRE2_DOTALL pour obtenir cette optimisation, ou alternativement, d'utiliser ^ pour indiquer explicitement l'ancrage.

Cependant, il y a des cas où l'optimisation ne peut pas être utilisée. Lorsque .* est à l'intérieur de parenthèses de capture qui sont le sujet d'une référence arrière ailleurs dans le motif, une correspondance au début peut échouer là où une correspondance ultérieure réussit. Considérez, par exemple :


(.*)abc\1

Si le sujet est « xyz123abc123 », le point de correspondance est le quatrième caractère. Pour cette raison, un tel motif n'est pas implicitement ancré.

Un autre cas où l'ancrage implicite n'est pas appliqué est lorsque le .* principal est à l'intérieur d'un groupe atomique. Encore une fois, une correspondance au début peut échouer là où une correspondance ultérieure réussit. Considérez ce motif :


(?>.*?a)b

Il correspond à « ab » dans le sujet « aab ». L'utilisation des verbes de contrôle de retour arrière (*PRUNE) et (*SKIP) désactive également cette optimisation. Pour le faire explicitement, passez l'option de compilation PCRE2_NO_DOTSTAR_ANCHOR, ou appelez pcre2_set_optimize() avec une directive PCRE2_DOTSTAR_ANCHOR_OFF.

Lorsqu'un groupe de capture est répété, la valeur capturée est la sous-chaîne qui a correspondu à la dernière itération. Par exemple, après


(tweedle[dume]{3}\s*)+

a correspondu à « tweedledum tweedledee », la valeur de la sous-chaîne capturée est « tweedledee ». Cependant, s'il y a des groupes de capture imbriqués, les valeurs capturées correspondantes peuvent avoir été définies lors des itérations précédentes. Par exemple, après


(a|(b))+

correspond à « aba », la valeur de la deuxième sous-chaîne capturée est « b ».

GROUPES ATOMIQUES ET QUANTIFICATEURS POSSESSIFS

Avec la répétition maximisante (« gourmande ») et minimisante (« non gourmande » ou « paresseuse »), l'échec de ce qui suit provoque normalement la réévaluation de l'élément répété pour voir si un nombre différent de répétitions permet au reste du motif de correspondre. Il est parfois utile d'empêcher cela, soit pour changer la nature de la correspondance, soit pour la faire échouer plus tôt qu'elle ne l'aurait fait autrement, lorsque l'auteur du motif sait qu'il est inutile de continuer.

Considérez, par exemple, le motif \d+foo appliqué à la ligne sujet


123456bar

Après avoir fait correspondre tous les 6 chiffres, puis échoué à faire correspondre « foo », l'action normale du moteur de correspondance est de réessayer avec seulement 5 chiffres correspondant à l'élément \d+, puis avec 4, et ainsi de suite, avant d'échouer finalement. Le « regroupement atomique » (un terme tiré du livre de Jeffrey Friedl) fournit le moyen de spécifier qu'une fois qu'un groupe a correspondu, il ne doit pas être réévalué de cette manière.

Si nous utilisons le groupement atomique pour l'exemple précédent, le moteur de correspondance abandonne immédiatement s'il échoue à faire correspondre "foo" la première fois. La notation est une sorte de parenthèse spéciale, commençant par (?> comme dans cet exemple :


(?>\d+)foo

Perl 5.28 a introduit une forme alphabétique expérimentale commençant par (* qui peut être plus facile à retenir :


(*atomic:\d+)foo

Ce type de groupe parenthésé "verrouille" la partie du motif qu'il contient une fois qu'il a correspondu, et un échec plus loin dans le motif est empêché de revenir en arrière. Cependant, le retour en arrière vers les éléments précédents fonctionne normalement.

Une description alternative est qu'un groupe de ce type correspond exactement à la chaîne de caractères qu'un motif autonome identique correspondrait, s'il était ancré au point actuel de la chaîne sujet.

Les groupes atomiques ne sont pas des groupes de capture. Des cas simples comme l'exemple ci-dessus peuvent être considérés comme une répétition maximisante qui doit tout engloutir. Ainsi, bien que \d+ et \d+? soient tous deux prêts à ajuster le nombre de chiffres qu'ils correspondent pour faire correspondre le reste du motif, (?>\d+) ne peut correspondre qu'à une séquence entière de chiffres.

Les groupes atomiques en général peuvent bien sûr contenir des expressions arbitrairement compliquées, et peuvent être imbriqués. Cependant, lorsque le contenu d'un groupe atomique n'est qu'un seul élément répété, comme dans l'exemple ci-dessus, une notation plus simple, appelée "quantificateur possessif", peut être utilisée. Celle-ci consiste en un caractère + supplémentaire suivant un quantificateur. En utilisant cette notation, l'exemple précédent peut être réécrit comme


\d++foo

Notez qu'un quantificateur possessif peut être utilisé avec un groupe entier, par exemple :


(abc|xyz){2,3}+

Les quantificateurs possessifs sont toujours gourmands ; le réglage de l'option PCRE2_UNGREEDY est ignoré. Ils constituent une notation pratique pour les formes les plus simples de groupe atomique. Cependant, il n'y a aucune différence dans la signification d'un quantificateur possessif et du groupe atomique équivalent, bien qu'il puisse y avoir une différence de performance ; les quantificateurs possessifs devraient être légèrement plus rapides.

La syntaxe des quantificateurs possessifs est une extension de la syntaxe Perl 5.8. Jeffrey Friedl a été à l'origine de l'idée (et du nom) dans la première édition de son livre. Mike McCloskey l'a appréciée, l'a donc implémentée lorsqu'il a construit le package Java de Sun, et PCRE1 l'a copiée à partir de là. Elle a trouvé sa place dans Perl à la version 5.10.

PCRE2 dispose d'une optimisation qui "possessifie" automatiquement certaines constructions de motifs simples. Par exemple, la séquence A+B est traitée comme A++B car il est inutile de revenir en arrière dans une séquence de A lorsque B doit suivre. Cette fonctionnalité peut être désactivée par l'option PCRE2_NO_AUTO_POSSESS, en appelant pcre2_set_optimize() avec une directive PCRE2_AUTO_POSSESS_OFF, ou en commençant le motif par (*NO_AUTO_POSSESS).

Lorsqu'un motif contient une répétition illimitée à l'intérieur d'un groupe qui peut lui-même être répété un nombre illimité de fois, l'utilisation d'un groupe atomique est le seul moyen d'éviter que certains correspondances échouées ne prennent un temps très long. Le motif


(\D+|<\d+>)*[!?]

correspond à un nombre illimité de sous-chaînes qui consistent soit en non-chiffres, soit en chiffres entourés de <>, suivis de ! ou ?. Lorsqu'il correspond, il s'exécute rapidement. Cependant, s'il est appliqué à


aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa

il faut beaucoup de temps avant de signaler un échec. C'est parce que la chaîne peut être divisée entre la répétition interne \D+ et la répétition externe * d'un grand nombre de façons, et toutes doivent être essayées. (L'exemple utilise [!?] plutôt qu'un seul caractère à la fin, car PCRE2 et Perl disposent d'une optimisation qui permet un échec rapide lorsqu'un seul caractère est utilisé. Ils se souviennent du dernier caractère unique requis pour une correspondance, et échouent tôt s'il n'est pas présent dans la chaîne.) Si le motif est modifié pour utiliser un groupe atomique, comme ceci :


((?>\D+)|<\d+>)*[!?]

les séquences de non-chiffres ne peuvent pas être décomposées, et l'échec se produit rapidement.

REFERENCES ARRIERE

En dehors d'une classe de caractères, un antislash suivi d'un chiffre supérieur à 0 (et éventuellement d'autres chiffres) est une référence arrière vers un groupe de capture précédent (c'est-à-dire, à sa gauche) dans le motif, à condition qu'il y ait eu autant de groupes de capture précédents.

Cependant, si le nombre décimal suivant l'antislash est inférieur à 8, il est toujours considéré comme une référence arrière, et ne provoque une erreur que s'il n'y a pas autant de groupes de capture dans l'ensemble du motif. En d'autres termes, le groupe auquel il est fait référence n'a pas besoin d'être à gauche de la référence pour les nombres inférieurs à 8. Une "référence arrière avant" de ce type peut avoir du sens lorsqu'une répétition est impliquée et que le groupe de droite a participé à une itération précédente.

Il n'est pas possible d'avoir une "référence arrière avant" numérique vers un groupe dont le numéro est 8 ou plus en utilisant cette syntaxe car une séquence telle que \50 est interprétée comme un caractère défini en octal. Voir la sous-section intitulée "Caractères non imprimables" ci-dessus pour plus de détails sur le traitement des chiffres suivant un antislash. D'autres formes de références arrière ne souffrent pas de cette restriction. En particulier, il n'y a aucun problème lorsque des groupes de capture nommés sont utilisés (voir ci-dessous).

Une autre façon d'éviter l'ambiguïté inhérente à l'utilisation de chiffres suivant un antislash est d'utiliser la séquence d'échappement \g. Cet échappement doit être suivi d'un nombre signé ou non signé, éventuellement entre accolades. Ces exemples sont tous identiques :


(ring), \1
(ring), \g1
(ring), \g{1}

Un nombre non signé spécifie une référence absolue sans l'ambiguïté présente dans la syntaxe plus ancienne. Il est également utile lorsque des chiffres littéraux suivent la référence. Un nombre signé est une référence relative. Considérons cet exemple :


(abc(def)ghi)\g{-1}

La séquence \g{-1} est une référence au groupe de capture dont le numéro est inférieur de un au numéro du prochain groupe qui sera démarré, donc dans cet exemple (où le prochain groupe serait numéroté 3) elle est équivalente à \2, et \g{-2} serait équivalent à \1. Notez que si cette construction se trouve à l'intérieur d'un groupe de capture, ce groupe est inclus dans le compte, donc dans cet exemple \g{-2} fait également référence au groupe 1 :


(A)(\g{-2}B)

L'utilisation de références relatives peut être utile dans les longs motifs, ainsi que dans les motifs créés en joignant des fragments qui contiennent des références en eux-mêmes.

La séquence \g{+1} est une référence au prochain groupe de capture qui est démarré après cet élément, et \g{+2} fait référence à celui d'après, et ainsi de suite. Ce type de référence avant peut être utile dans les motifs qui se répètent. Perl ne prend pas en charge l'utilisation de + de cette manière.

Une référence arrière correspond à ce qui a correspondu le plus récemment au groupe de capture dans la chaîne sujet actuelle, plutôt qu'à autre chose qui correspond au groupe (voir "Groupes comme sous-routines" ci-dessous pour une façon de faire cela). Ainsi, le motif


(sens|respons)e and \1ibility

correspond à "sense and sensibility" et "response and responsibility", mais pas à "sense and responsibility". Si la correspondance sensible à la casse est en vigueur au moment de la référence arrière, la casse des lettres est pertinente. Par exemple,


((?i)rah)\s+\1

correspond à "rah rah" et "RAH RAH", mais pas à "RAH rah", même si le groupe de capture d'origine a été mis en correspondance sans distinction de casse.

Il existe plusieurs façons d'écrire des références arrière vers des groupes de capture nommés. La syntaxe .NET est \k{name}, la syntaxe Python est (?=name), et la syntaxe Perl originale est \k<name> ou \k'name'. Toutes celles-ci sont maintenant prises en charge par Perl et PCRE2. La syntaxe unifiée de référence arrière de Perl 5.10, dans laquelle \g peut être utilisé pour les références numériques et nommées, est également prise en charge par PCRE2. Nous pourrions réécrire l'exemple ci-dessus de l'une des manières suivantes :


(?<p1>(?i)rah)\s+\k<p1>
(?'p1'(?i)rah)\s+\k{p1}
(?P<p1>(?i)rah)\s+(?P=p1)
(?<p1>(?i)rah)\s+\g{p1}

Un groupe de capture référencé par nom peut apparaître dans le motif avant ou après la référence.

Il peut y avoir plus d'une référence arrière au même groupe. Si un groupe n'a pas réellement été utilisé dans une correspondance particulière, les références arrière à celui-ci échouent toujours par défaut. Par exemple, le motif


(a|(bc))\2

échoue toujours s'il commence par correspondre à "a" plutôt qu'à "bc". Cependant, si l'option PCRE2_MATCH_UNSET_BACKREF est définie au moment de la compilation, une référence arrière à une valeur non définie correspond à une chaîne vide.

Comme il peut y avoir de nombreux groupes de capture dans un motif, tous les chiffres suivant un antislash sont considérés comme faisant partie d'un numéro de référence arrière potentiel. Si le motif continue avec un caractère numérique, un délimiteur doit être utilisé pour terminer la référence arrière. Si l'option PCRE2_EXTENDED ou PCRE2_EXTENDED_MORE est définie, cela peut être un espace blanc. Sinon, la syntaxe \g{} ou un commentaire vide (voir "Commentaires" ci-dessous) peut être utilisée.

Références arrière récursives

Une référence arrière qui se produit à l'intérieur du groupe auquel elle se réfère échoue lorsque le groupe est utilisé pour la première fois, donc, par exemple, (a\1) ne correspond jamais. Cependant, de telles références peuvent être utiles à l'intérieur de groupes répétés. Par exemple, le motif


(a|b\1)+

correspond à n'importe quel nombre de "a" et aussi à "aba", "ababbaa" etc. À chaque itération du groupe, la référence arrière correspond à la chaîne de caractères correspondant à l'itération précédente. Pour que cela fonctionne, le motif doit être tel que la première itération ne nécessite pas de faire correspondre la référence arrière. Cela peut être fait en utilisant l'alternance, comme dans l'exemple ci-dessus, ou par un quantificateur avec un minimum de zéro.

Pour les versions de PCRE2 antérieures à 10.25, les références arrière de ce type avaient pour effet de traiter le groupe auquel elles se référaient comme un groupe atomique. Cette restriction ne s'applique plus, et le retour arrière dans de tels groupes peut se produire normalement.

ASSERTIONS

Une assertion est un test qui ne consomme aucun caractère. Le test doit réussir pour que la correspondance continue. Les assertions simples codées comme \b, \B, \A, \G, \Z, \z, ^ et $ sont décrites ci-dessus.

Des assertions plus compliquées sont codées comme des groupes parenthésés. Si la correspondance d'un tel groupe réussit, la correspondance continue après lui, mais avec la position de correspondance dans le

subject string tel qu'il était avant le traitement de l'assertion.

Une sorte spéciale d'assertion, appelée assertion de "sous-chaîne de balayage", met en correspondance un sous-modèle avec une sous-chaîne capturée précédemment. Ceci est décrit dans la section intitulée "Assertions de sous-chaîne de balayage" ci-dessous. Il s'agit d'une extension PCRE2, non compatible avec Perl.

Les autres assertions basées sur des groupes sont de deux types : celles qui regardent en avant de la position actuelle dans la chaîne sujet, et celles qui regardent en arrière, et dans chaque cas une assertion peut être positive (doit correspondre pour que l'assertion soit vraie) ou négative (ne doit pas correspondre pour que l'assertion soit vraie).

Les assertions de recherche de type Perl sont atomiques. Si une assertion est vraie, mais qu'il y a un échec de correspondance ultérieur, il n'y a pas de rétroaction dans l'assertion. Cependant, il existe des cas où des assertions non atomiques peuvent être utiles. PCRE2 offre un certain support pour celles-ci, décrit dans la section intitulée "Assertions non atomiques" ci-dessous, mais elles ne sont pas compatibles avec Perl.

Une assertion de recherche peut apparaître comme condition dans un groupe conditionnel (voir ci-dessous). Dans ce cas, le résultat de la correspondance de l'assertion détermine quelle branche de la condition est suivie.

Les groupes d'assertions ne sont pas des groupes de capture. Si une assertion contient des groupes de capture, ceux-ci sont comptés pour la numérotation des groupes de capture dans le modèle entier. Au sein de chaque branche d'une assertion, les sous-chaînes capturées localement peuvent être référencées de la manière habituelle. Par exemple, une séquence telle que (.)\g{-1} peut être utilisée pour vérifier que deux caractères adjacents sont identiques.

Lorsqu'une branche au sein d'une assertion ne parvient pas à correspondre, les sous-chaînes qui ont été capturées sontDiscarded (comme cela se produit avec toute branche de modèle qui ne parvient pas à correspondre). Une assertion négative n'est vraie que lorsque toutes ses branches échouent à correspondre ; cela signifie qu'aucune sous-chaîne capturée n'est jamais conservée après une assertion négative réussie. Lorsqu'une assertion contient une branche correspondante, ce qui se passe dépend du type d'assertion.

Pour une assertion positive, les sous-chaînes capturées en interne dans la branche réussie sont conservées, et la correspondance continue avec l'élément de modèle suivant après l'assertion. Pour une assertion négative, une branche correspondante signifie que l'assertion n'est pas vraie. Si une telle assertion est utilisée comme condition dans un groupe conditionnel (voir ci-dessous), les sous-chaînes capturées sont conservées, car la correspondance continue avec la branche "non" de la condition. Pour d'autres assertions négatives échouées, le contrôle passe au point de rétroaction précédent,Discarding ainsi toutes les chaînes capturées dans l'assertion.

La plupart des groupes d'assertions peuvent être répétés ; bien qu'il soit inutile d'affirmer la même chose plusieurs fois, l'effet secondaire de capture dans les assertions positives peut parfois être utile. Cependant, une assertion qui forme la condition d'un groupe conditionnel ne peut pas être quantifiée. PCRE2 restreignait autrefois la répétition des assertions, mais depuis la version 10.35, la seule restriction est qu'une répétition maximale illimitée est modifiée pour être un de plus que le minimum. Par exemple, {3,} est traité comme {3,4}.

Noms alphabétiques d'assertion

Traditionnellement, des séquences symboliques telles que (?= et (?<= ont été utilisées pour spécifier les assertions de recherche. Perl 5.28 a introduit des alternatives alphabétiques expérimentales qui pourraient être plus faciles à retenir. Elles commencent toutes par (* au lieu de (? et doivent être écrites en lettres minuscules. PCRE2 prend en charge les synonymes suivants :


(*positive_lookahead: ou (*pla: est identique à (?=
(*negative_lookahead: ou (*nla: est identique à (?!
(*positive_lookbehind: ou (*plb: est identique à (?<=
(*negative_lookbehind: ou (*nlb: est identique à (?<!

Par exemple, (*pla:foo) est la même assertion que (?=foo). Dans les sections suivantes, les différentes assertions sont décrites en utilisant les formes symboliques originales.

Assertions de recherche avant

Les assertions de recherche avant commencent par (?= pour les assertions positives et (?! pour les assertions négatives. Par exemple,


\w+(?=;)

correspond à un mot suivi d'un point-virgule, mais n'inclut pas le point-virgule dans la correspondance, et


foo(?!bar)

correspond à toute occurrence de "foo" qui n'est pas suivie de "bar". Notez que le modèle apparemment similaire


(?!foo)bar

ne trouve pas une occurrence de "bar" qui est précédée par quelque chose d'autre que "foo" ; il trouve n'importe quelle occurrence de "bar" quoi que ce soit, car l'assertion (?!foo) est toujours vraie lorsque les trois caractères suivants sont "bar". Une assertion de recherche arrière est nécessaire pour réaliser l'autre effet.

Si vous voulez forcer un échec de correspondance à un certain point dans un modèle, le moyen le plus pratique est d'utiliser (?!) car une chaîne vide correspond toujours, donc une assertion qui exige qu'il n'y ait pas de chaîne vide doit toujours échouer. Le verbe de contrôle de rétroaction (*FAIL) ou (*F) est un synonyme de (?!).

Assertions de recherche arrière

Les assertions de recherche arrière commencent par (?<= pour les assertions positives et (?<! pour les assertions négatives. Par exemple,


(?<!foo)bar

trouve une occurrence de "bar" qui n'est pas précédée de "foo". Le contenu d'une assertion de recherche arrière est restreint de telle sorte qu'il doit y avoir un maximum connu pour les longueurs de toutes les chaînes qu'elle met en correspondance. Il y a deux cas :

Si chaque alternative de niveau supérieur correspond à une longueur fixe, par exemple


(?<=colour|color)

il y a une limite de 65535 caractères aux longueurs, qui ne doivent pas nécessairement être les mêmes, comme le démontre cet exemple. C'est le seul type de recherche arrière pris en charge par les versions de PCRE2 antérieures à 10.43 et par la fonction de correspondance alternative pcre2_dfa_match().

Dans PCRE2 10.43 et versions ultérieures, pcre2_match() prend en charge les assertions de recherche arrière dans lesquelles une ou plusieurs alternatives de niveau supérieur peuvent correspondre à plus d'une longueur de chaîne, par exemple


(?<=colou?r)

La longueur maximale de correspondance pour chaque branche de la recherche arrière est limitée à une valeur définie par le programme appelant (par défaut 255 caractères). La répétition illimitée (par exemple \d*) n'est pas prise en charge. Dans certains cas, la séquence d'échappement \K (voir ci-dessus) peut être utilisée à la place d'une assertion de recherche arrière au début d'un modèle pour contourner la restriction de limite de longueur.

En modes UTF-8 et UTF-16, PCRE2 n'autorise pas l'échappement \C (qui correspond à une seule unité de code même en mode UTF) à apparaître dans les assertions de recherche arrière, car cela rend impossible le calcul de la longueur de la recherche arrière. Les échappements \X et \R, qui peuvent correspondre à un nombre différent d'unités de code, ne sont jamais autorisés dans les recherches arrière.

"Appels de sous-routine" (voir ci-dessous) tels que (?2) ou (?&X) sont autorisés dans les recherches arrière, tant que le groupe de capture appelé correspond à une chaîne de longueur limitée. Cependant, la récursion, c'est-à-dire un appel de "sous-routine" vers un groupe déjà actif, n'est pas prise en charge.

PCRE2 prend en charge les références arrière dans les recherches arrière, mais uniquement si certaines conditions sont remplies. L'option PCRE2_MATCH_UNSET_BACKREF ne doit pas être définie, il ne doit y avoir aucune utilisation de (?| dans le modèle (cela crée des numéros de groupe dupliqués), et si la référence arrière est par nom, le nom doit être unique. Bien sûr, le groupe référencé doit lui-même correspondre à une sous-chaîne de longueur limitée. Le modèle suivant correspond aux mots contenant au moins deux caractères qui commencent et se terminent par le même caractère :


\b(\w)\w++(?<=\1)

Les quantificateurs possessifs peuvent être utilisés en conjonction avec les assertions de recherche arrière pour spécifier une correspondance efficace à la fin des chaînes sujettes. Considérons un modèle simple tel que


abcd$

lorsqu'il est appliqué à une longue chaîne qui ne correspond pas. Comme la correspondance progresse de gauche à droite, PCRE2 recherchera chaque "a" dans le sujet et verra ensuite si ce qui suit correspond au reste du modèle. Si le modèle est spécifié comme


^.*abcd$

le .* initial correspond à toute la chaîne au début, mais quand cela échoue (car il n'y a pas de "a" suivant), il rétroagit pour correspondre à toute la chaîne sauf le dernier caractère, puis toute la chaîne sauf les deux derniers caractères, et ainsi de suite. Encore une fois, la recherche de "a" couvre toute la chaîne, de droite à gauche, donc nous ne sommes pas mieux lotis. Cependant, si le modèle est écrit comme


^.*+(?<=abcd)

il ne peut y avoir de rétroaction pour l'élément .*+ en raison du quantificateur possessif ; il ne peut correspondre qu'à toute la chaîne. L'assertion de recherche arrière suivante effectue un seul test sur les quatre derniers caractères. Si cela échoue, la correspondance échoue immédiatement. Pour les longues chaînes, cette approche fait une différence significative dans le temps de traitement.

Utilisation de plusieurs assertions

Plusieurs assertions (de tout type) peuvent apparaître successivement. Par exemple,


(?<=\d{3})(?<!999)foo

correspond à "foo" précédé de trois chiffres qui ne sont pas "999". Notez que chacune des assertions est appliquée indépendamment au même point de la chaîne sujet. D'abord, il y a une vérification que les trois caractères précédents sont tous des chiffres, puis il y a une vérification que les mêmes trois caractères ne sont pas "999". Ce modèle ne correspond pas à "foo" précédé de six caractères, dont les trois premiers sont des chiffres et les trois derniers ne sont pas "999". Par exemple, il ne correspond pas à "123abcfoo". Un modèle pour faire cela est


(?<=\d{3}...)(?<!999)foo

Cette fois, la première assertion regarde les six caractères précédents, vérifiant que les trois premiers sont des chiffres, puis la seconde assertion vérifie que les trois caractères précédents ne sont pas "999".

Les assertions peuvent être imbriquées dans n'importe quelle combinaison. Par exemple,


(?<=(?<!foo)bar)baz

correspond à une occurrence de "baz" qui est précédée de "bar" qui à son tour n'est pas précédée de "foo", tandis que


(?<=\d{3}(?!999)...)foo

est un autre modèle qui correspond à "foo" précédé de trois chiffres et de n'importe quels trois caractères qui ne sont pas "999".

ASSERTIONS NON ATOMIQUES

Les assertions de recherche traditionnelles sont atomiques. C'est-à-dire que si une assertion est vraie, mais qu'il y a un

subsequent matching failure, there is no backtracking into the assertion. However, there are some cases where non-atomic positive assertions can be useful. PCRE2 provides these using the following syntax:


(*non_atomic_positive_lookahead: or (*napla: or (?*
(*non_atomic_positive_lookbehind: or (*naplb: or (?<*

Consider the problem of finding the right-most word in a string that also appears earlier in the string, that is, it must appear at least twice in total. This pattern returns the required result as captured substring 1:


^(?x)(*napla: .* \b(\w++)) (?> .*? \b\1\b ){2}

For a subject such as "word1 word2 word3 word2 word3 word4" the result is "word3". How does it work? At the start, ^(?x) anchors the pattern and sets the "x" option, which causes white space (introduced for readability) to be ignored. Inside the assertion, the greedy .* at first consumes the entire string, but then has to backtrack until the rest of the assertion can match a word, which is captured by group 1. In other words, when the assertion first succeeds, it captures the right-most word in the string.

The current matching point is then reset to the start of the subject, and the rest of the pattern match checks for two occurrences of the captured word, using an ungreedy .*? to scan from the left. If this succeeds, we are done, but if the last word in the string does not occur twice, this part of the pattern fails. If a traditional atomic lookahead (?= or (*pla: had been used, the assertion could not be re-entered, and the whole match would fail. The pattern would succeed only if the very last word in the subject was found twice.

Using a non-atomic lookahead, however, means that when the last word does not occur twice in the string, the lookahead can backtrack and find the second-last word, and so on, until either the match succeeds, or all words have been tested.

Two conditions must be met for a non-atomic assertion to be useful: the contents of one or more capturing groups must change after a backtrack into the assertion, and there must be a backreference to a changed group later in the pattern. If this is not the case, the rest of the pattern match fails exactly as before because nothing has changed, so using a non-atomic assertion just wastes resources.

There is one exception to backtracking into a non-atomic assertion. If an (*ACCEPT) control verb is triggered, the assertion succeeds atomically. That is, a subsequent match failure cannot backtrack into the assertion.

Non-atomic assertions are not supported by the alternative matching function pcre2_dfa_match(). They are supported by JIT, but only if they do not contain any control verbs such as (*ACCEPT). (This may change in future). Note that assertions that appear as conditions for conditional groups (see below) must be atomic.

ASSERTIONS DE SOUS-CHAÎNE DE BALAYAGE

A special kind of assertion, not compatible with Perl, makes it possible to check the contents of a captured substring by matching it with a subpattern. Because this involves capturing, this feature is not supported by pcre2_dfa_match().

A scan substring assertion starts with the sequence (*scan_substring: or (*scs: which is followed by a list of substring numbers (absolute or relative) and/or substring names enclosed in single quotes or angle brackets, all within parentheses. The rest of the item is the subpattern that is applied to the substring, as shown in these examples:


(*scan_substring:(1)...)
(*scs:(-2)...)
(*scs:('AB')...)
(*scs:(1,'AB',-2)...)

The list of groups is checked in the order they are given, and it is the contents of the first one that is found to be set that are scanned. When PCRE2_DUPNAMES is set and there are ambiguous group names, all groups with the same name are checked in numerical order. A scan substring assertion fails if none of the groups it references have been set.

The pattern match on the substring is always anchored, that is, it must match from the start of the substring. There is no "bumpalong" if it does not match at the start. The end of the subject is temporarily reset to be the end of the substring, so \Z, \z, and $ will match there. However, the start of the subject is not reset. This means that ^ matches only if the substring is actually at the start of the main subject, but it also means that lookbehind assertions into what precedes the substring are possible.

Here is a very simple example: find a word that contains the rare (in English) sequence of letters "rh" not at the start:


\b(\w++)(*scs:(1).+rh)

The first group captures a word which is then scanned by the second group. This example does not actually need this heavyweight feature; the same match can be achieved with:


\b\w+?rh\w*\b

When things are more complicated, however, scanning a captured substring can be a useful way to describe the required match. For exmple, there is a rather complicated pattern in the PCRE2 test data that checks an entire subject string for a palindrome, that is, the sequence of letters is the same in both directions. Suppose you want to search for individual words of two or more characters such as "level" that are palindromes:


(\b\w{2,}+\b)(*scs:(1)...palindrome-matching-pattern...)

Within a substring scanning subpattern, references to other groups work as normal. Capturing groups may appear, and will retain their values during ongoing matching if the assertion succeeds.

EXÉCUTIONS DE SCRIPT

In concept, a script run is a sequence of characters that are all from the same Unicode script such as Latin or Greek. However, because some scripts are commonly used together, and because some diacritical and other marks are used with multiple scripts, it is not that simple. There is a full description of the rules that PCRE2 uses in the section entitled "Script Runs" in the pcre2unicode documentation.

If part of a pattern is enclosed between (*script_run: or (*sr: and a closing parenthesis, it fails if the sequence of characters that it matches are not a script run. After a failure, normal backtracking occurs. Script runs can be used to detect spoofing attacks using characters that look the same, but are from different scripts. The string "paypal.com" is an infamous example, where the letters could be a mixture of Latin and Cyrillic. This pattern ensures that the matched characters in a sequence of non-spaces that follow white space are a script run:


\s+(*sr:\S+)

To be sure that they are all from the Latin script (for example), a lookahead can be used:


\s+(?=\p{Latin})(*sr:\S+)

This works as long as the first character is expected to be a character in that script, and not (for example) punctuation, which is allowed with any script. If this is not the case, a more creative lookahead is needed. For example, if digits, underscore, and dots are permitted at the start:


\s+(?=[0-9_.]*\p{Latin})(*sr:\S+)

In many cases, backtracking into a script run pattern fragment is not desirable. The script run can employ an atomic group to prevent this. Because this is a common requirement, a shorthand notation is provided by (*atomic_script_run: or (*asr:


(*asr:...) is the same as (*sr:(?>...))

Note that the atomic group is inside the script run. Putting it outside would not prevent backtracking into the script run pattern.

Support for script runs is not available if PCRE2 is compiled without Unicode support. A compile-time error is given if any of the above constructs is encountered. Script runs are not supported by the alternate matching function, pcre2_dfa_match() because they use the same mechanism as capturing parentheses.

Warning: The (*ACCEPT) control verb (see below) should not be used within a script run group, because it causes an immediate exit from the group, bypassing the script run checking.

GROUPES CONDITIONNELS

It is possible to cause the matching process to obey a pattern fragment conditionally or to choose between two alternative fragments, depending on the result of an assertion, or whether a specific capture group has already been matched. The two possible forms of conditional group are:


(?(condition)yes-pattern)
(?(condition)yes-pattern|no-pattern)

If the condition is satisfied, the yes-pattern is used; otherwise the no-pattern (if present) is used. An absent no-pattern is equivalent to an empty string (it always matches). If there are more than two alternatives in the group, a compile-time error occurs. Each of the two alternatives may itself contain nested groups of any form, including conditional groups; the restriction to two alternatives applies only at the level of the condition itself. This pattern fragment is an example where the alternatives are complex:


(?(1) (A|B|C) | (D | (?(2)E|F) | E) )

There are five kinds of condition: references to capture groups, references to recursion, two pseudo-conditions called DEFINE and VERSION, and assertions.

Vérification d'un groupe de capture utilisé par numéro

If the text between the parentheses consists of a sequence of digits, the condition is true if a capture group of that number has previously matched. If there is more than one capture group with the same number (see the earlier section about duplicate group numbers), the condition is true if any of them have matched. An alternative notation, which is a PCRE2 extension, not supported by Perl, is to precede the digits with a plus or minus sign. In this case, the group number is relative rather than absolute. The most recently opened capture group (which could be enclosing this condition) can be referenced by (?(-1), the next most recent by (?(-2), and so on. Inside loops it can also make sense to refer to subsequent groups. The next capture group to be opened can be referenced as (?(+1), and so on. The value zero in any of these forms is not used; it provokes a compile-time error.

Consider the following pattern, which contains non-significant white space to make it more readable (assume the PCRE2_EXTENDED option) and to divide it into three parts for ease of discussion:


( \( )? [^()]+ (?(1) \) )

The first part matches an opening parenthesis, capturing it in group 1. The second part matches one or more characters that are not parentheses. The third part is conditional. If group 1 has matched (i.e. the string starts with a parenthesis), it checks for a closing parenthesis. Otherwise, it matches nothing. The net effect is to match a sequence of non-parenthesis characters, optionally enclosed in parentheses.

MODÈLES CONDITIONNELS

Les modèles conditionnels permettent à un motif de s'adapter à différents sujets en fonction du fait qu'un groupe de capture précédent ait ou non correspondu.

Vérification d'un groupe de capture utilisé par numéro

Le modèle se compose de trois parties:

  • La première partie correspond à une parenthèse ouvrante optionnelle et, si ce caractère est présent, la définit comme la première sous-chaîne capturée.
  • La deuxième partie correspond à un ou plusieurs caractères qui ne sont pas des parenthèses.
  • La troisième partie est un groupe conditionnel qui teste si le premier groupe de capture a correspondu ou non. S'il l'a fait, c'est-à-dire si le sujet a commencé par une parenthèse ouvrante, la condition est vraie, et donc le motif oui est exécuté et une parenthèse fermante est requise. Sinon, comme le motif non est absent, le groupe conditionnel ne correspond à rien.

En d'autres termes, ce modèle correspond à une séquence de caractères qui ne sont pas des parenthèses, éventuellement entourés de parenthèses.

Si vous intégriez ce modèle dans un modèle plus grand, vous pourriez utiliser une référence relative :


... autre chose... ( \( )? [^()]+ (?(-1) \) ) ...

Cela rend le fragment indépendant des parenthèses dans le modèle plus grand.

Vérification d'un groupe de capture utilisé par nom

Perl utilise la syntaxe (?<name>...) ou ?('name'...) pour tester un groupe de capture utilisé par nom. Pour la compatibilité avec les versions antérieures de PCRE1, qui disposaient de cette fonctionnalité avant Perl, la syntaxe ?(name...) est également reconnue. Notez, cependant, que les noms non délimités constitués de la lettre R suivie de chiffres sont ambigus (voir la section suivante). La réécriture de l'exemple ci-dessus pour utiliser un groupe nommé donne ceci :


(?<OPEN> \( )? [^()]+ (?(<OPEN>) \) )

Si le nom utilisé dans une condition de ce type est un doublon, le test est appliqué à tous les groupes du même nom, et est vrai si l'un d'entre eux a correspondu.

Vérification de la récursion de motif

La "récursion" dans ce sens fait référence à tout appel de type sous-routine d'une partie du motif à une autre, qu'il soit réellement récursif ou non. Voir les sections intitulées "Modèles récursifs" et "Groupes en tant que sous-routines" ci-dessous pour les détails de la récursion et des appels de sous-routines.

Si une condition est la chaîne (R), et qu'il n'y a pas de groupe de capture nommé R, la condition est vraie si la correspondance est actuellement dans une récursion ou un appel de sous-routine vers l'ensemble du motif ou un groupe de capture. Si des chiffres suivent la lettre R, et qu'il n'y a pas de groupe portant ce nom, la condition est vraie si l'appel le plus récent est vers un groupe portant le numéro donné, qui doit exister quelque part dans le motif global. Ceci est un exemple artificiel qui est équivalent à a+b :


((?(R1)a+|(?1)b))

Cependant, dans les deux cas, s'il existe un groupe de capture avec un nom correspondant, la condition teste s'il est défini, comme décrit dans la section ci-dessus, au lieu de tester la récursion. Par exemple, la création d'un groupe nommé R1 en ajoutant (?<R1>) au motif ci-dessus change complètement son sens.

Si un nom précédé d'une esperluette suit la lettre R, par exemple :


(?(R&name)...)

la condition est vraie si la récursion la plus récente est dans un groupe de ce nom (qui doit exister dans le motif).

Cette condition ne vérifie pas toute la pile de récursion. Elle teste uniquement le niveau actuel. Si le nom utilisé dans une condition de ce type est un doublon, le test est appliqué à tous les groupes du même nom, et est vrai si l'un d'entre eux est la récursion la plus récente.

Au "niveau supérieur", toutes ces conditions de test de récursion sont fausses.

Définition de groupes de capture à utiliser uniquement par référence

Si la condition est la chaîne (DEFINE), la condition est toujours fausse, même s'il existe un groupe nommé DEFINE. Dans ce cas, il ne peut y avoir qu'une seule alternative dans le reste du groupe conditionnel. Elle est toujours ignorée si le contrôle atteint ce point dans le motif ; l'idée de DEFINE est qu'elle peut être utilisée pour définir des sous-routines auxquelles on peut faire référence depuis ailleurs. (L'utilisation des sous-routines est décrite ci-dessous.) Par exemple, un motif pour correspondre à une adresse IPv4 telle que "192.168.23.245" pourrait être écrit comme suit (ignorer les espaces blancs et les sauts de ligne) :


(?(DEFINE) (?<byte> 2[0-4]\d | 25[0-5] | 1\d\d | [1-9]?\d) )
\b (?&byte) (\.(?&byte)){3} \b

La première partie du motif est un groupe DEFINE à l'intérieur duquel un autre groupe nommé "byte" est défini. Celui-ci correspond à un composant individuel d'une adresse IPv4 (un nombre inférieur à 256). Lors de la correspondance, cette partie du motif est ignorée car DEFINE agit comme une condition fausse. Le reste du motif utilise des références au groupe nommé pour faire correspondre les quatre composants séparés par des points d'une adresse IPv4, en insistant sur une frontière de mot à chaque extrémité.

Vérification de la version PCRE2

Les programmes qui se lient à une bibliothèque PCRE2 peuvent vérifier la version en appelant pcre2_config() avec les arguments appropriés. Les utilisateurs d'applications qui n'ont pas accès au code sous-jacent ne peuvent pas le faire. Une "condition" spéciale appelée VERSION existe pour permettre à de tels utilisateurs de découvrir à quelle version de PCRE2 ils ont affaire en utilisant cette condition pour faire correspondre une chaîne telle que "yesno". VERSION doit être suivi de "=" ou ">=" et d'un numéro de version. Par exemple :


(?(VERSION>=10.4)yes|no)

Ce motif correspond à "yes" si la version de PCRE2 est supérieure ou égale à 10.4, ou à "no" sinon. La partie fractionnaire du numéro de version pourrait être omise.

Conditions d'assertion

Si la condition ne correspond à aucun des formats ci-dessus, elle doit être une assertion entre parenthèses. Il peut s'agir d'une assertion lookahead ou lookbehind positive ou négative. Cependant, il doit s'agir d'une assertion atomique traditionnelle, et non de l'une des assertions non atomiques.

Considérez ce motif, contenant à nouveau des espaces blancs non significatifs, et avec les deux alternatives sur la deuxième ligne :


(?(?=[^a-z]*[a-z])
\d{2}-[a-z]{3}-\d{2} | \d{2}-\d{2}-\d{2} )

La condition est une assertion lookahead positive qui correspond à une séquence optionnelle de non-lettres suivie d'une lettre. En d'autres termes, elle teste la présence d'au moins une lettre dans le sujet. Si une lettre est trouvée, le sujet est mis en correspondance avec la première alternative ; sinon, il est mis en correspondance avec la seconde. Ce motif correspond à des chaînes dans l'une des deux formes jj-aaa-jj ou jj-jj-jj, où aaa sont des lettres et jj sont des chiffres.

Lorsqu'une assertion qui est une condition contient des groupes de capture, toute capture qui se produit dans une branche correspondante est conservée par la suite, pour les assertions positives et négatives, car la correspondance continue toujours après l'assertion, qu'elle réussisse ou échoue. (Comparez avec les assertions non conditionnelles, pour lesquelles les captures ne sont conservées que pour les assertions positives qui réussissent.)

COMMENTAIRES

Il existe deux façons d'inclure des commentaires dans les motifs traités par PCRE2. Dans les deux cas, le début du commentaire ne doit pas se trouver dans une classe de caractères, ni au milieu d'une autre séquence de caractères liés tels que (?: ou un nom ou un numéro de groupe, ou un nom de propriété Unicode. Les caractères qui composent un commentaire ne jouent aucun rôle dans la correspondance du motif.

La séquence (?# marque le début d'un commentaire qui se poursuit jusqu'à la parenthèse fermante suivante. Les parenthèses imbriquées ne sont pas autorisées. Si l'option PCRE2_EXTENDED ou PCRE2_EXTENDED_MORE est définie, un caractère # non échappé introduit également un commentaire, qui dans ce cas se poursuit jusqu'immédiatement après le prochain saut de ligne ou séquence de caractères dans le motif. Les caractères qui sont interprétés comme des sauts de ligne sont contrôlés par une option passée à la fonction de compilation ou par une séquence spéciale au début du motif, comme décrit dans la section intitulée "Conventions de sauts de ligne" ci-dessus. Notez que la fin de ce type de commentaire est une séquence de saut de ligne littérale dans le motif ; les séquences d'échappement qui représentent un saut de ligne ne comptent pas. Par exemple, considérez ce motif lorsque PCRE2_EXTENDED est défini, et que la convention de saut de ligne par défaut (un seul caractère de saut de ligne) est en vigueur :


abc #comment \n toujours commentaire

En rencontrant le caractère #, pcre2_compile() avance, à la recherche d'un saut de ligne dans le motif. La séquence \n est toujours littérale à ce stade, elle ne termine donc pas le commentaire. Seul un caractère réel avec la valeur de code 0x0a (le saut de ligne par défaut) le fait.

MODÈLES RÉCURSIFS

Considérez le problème de faire correspondre une chaîne entre parenthèses, en permettant des parenthèses imbriquées illimitées. Sans l'utilisation de la récursion, le mieux que l'on puisse faire est d'utiliser un modèle qui correspond jusqu'à une profondeur d'imbrication fixe. Il n'est pas possible de gérer une profondeur d'imbrication arbitraire.

Pendant un certain temps, Perl a fourni une fonctionnalité qui permet aux expressions régulières de récurer (entre autres choses). Elle le fait en interpolant du code Perl dans l'expression au moment de l'exécution, et le code peut se référer à l'expression elle-même. Un motif Perl utilisant l'interpolation de code pour résoudre le problème des parenthèses peut être créé comme ceci :


$re = qr{\( (?: (?>[^()]+) | (?p{$re}) )* \)}x;

L'élément (?p{...}) interpole du code Perl au moment de l'exécution, et dans ce cas, fait référence récursivement au motif dans lequel il apparaît.

Évidemment, PCRE2 ne peut pas supporter l'interpolation de code Perl. Au lieu de cela, il prend en charge une syntaxe spéciale pour la récursion de l'ensemble du motif, ainsi que pour la récursion de groupes de capture individuels. Après son introduction dans PCRE1 et Python, ce type de récursion a été introduit par la suite dans Perl à la version 5.10.

Un élément spécial constitué de (? suivi d'un nombre supérieur à zéro et d'une parenthèse fermante est un appel de sous-routine récursif du groupe de capture du numéro donné, à condition qu'il se trouve à l'intérieur de ce groupe. (Sinon, c'est un appel de sous-routine non récursif, décrit dans la section suivante.) L'élément spécial (?R) ou (?0) est un appel récursif de l'expression régulière entière.

Ce motif PCRE2 résout le problème des parenthèses imbriquées (supposez que l'option PCRE2_EXTENDED est définie pour que les espaces blancs soient ignorés) :


\( ( [^()]++ | (?R) )* \)

Il fait d'abord correspondre une parenthèse ouvrante. Ensuite, il fait correspondre un nombre quelconque de sous-chaînes qui peuvent être soit une séquence

de non-parenthèses, ou une coïncidence récursive du modèle lui-même (c'est-à-dire une sous-chaîne correctement parenthésée). Enfin, il y a une parenthèse fermante. Notez l'utilisation d'un quantificateur possessif pour éviter le retour arrière dans des séquences de non-parenthèses.

Si cela faisait partie d'un modèle plus grand, vous ne voudriez pas récurser le modèle entier, vous pourriez donc utiliser ceci à la place :


( \( ( [^()]++ | (?1) )* \) )

Nous avons mis le modèle entre parenthèses et fait en sorte que la récursion se réfère à elles au lieu du modèle entier.

Dans un modèle plus grand, le suivi des numéros de parenthèses peut être délicat. Ceci est facilité par l'utilisation de références relatives. Au lieu de (?1) dans le modèle ci-dessus, vous pouvez écrire (?-2) pour faire référence aux parenthèses ouvertes les plus récentes précédant la récursion. En d'autres termes, un nombre négatif compte les parenthèses de capture vers la gauche à partir du point où il est rencontré.

Soyez conscient cependant, que si des numéros de groupes de capture dupliqués sont utilisés, les références relatives font référence au groupe le plus ancien avec le numéro approprié. Considérez, par exemple :


(?|(a)|(b)) (c) (?-2)

Les deux premiers groupes de capture (a) et (b) sont tous deux numérotés 1, et le groupe (c) est le numéro 2. Lorsque la référence (?-2) est rencontrée, les parenthèses ouvertes les plus récentes ont le numéro 1, mais c'est le premier groupe de ce type (le groupe (a)) auquel la récursion fait référence. Ce serait la même chose si une référence absolue (?1) était utilisée. En d'autres termes, les références relatives ne sont qu'un raccourci pour calculer un numéro de groupe.

Il est également possible de faire référence à des groupes de capture ultérieurs, en écrivant des références telles que (?+2). Cependant, celles-ci ne peuvent pas être récursives car la référence n'est pas à l'intérieur des parenthèses auxquelles il est fait référence. Ce sont toujours des appels de sous-routine non récursifs, comme décrit dans la section suivante.

Une approche alternative consiste à utiliser des parenthèses nommées. La syntaxe Perl pour cela est (?&name) ; la syntaxe plus ancienne de PCRE1 (?P>name) est également prise en charge. Nous pourrions réécrire l'exemple ci-dessus comme suit :


(?<pn> \( ( [^()]++ | (?&pn) )* \) )

S'il y a plus d'un groupe portant le même nom, le premier est utilisé.

Le modèle d'exemple que nous avons examiné contient des répétitions illimitées imbriquées, de sorte que l'utilisation d'un quantificateur possessif pour faire correspondre des chaînes de non-parenthèses est importante lors de l'application du modèle à des chaînes qui ne correspondent pas. Par exemple, lorsque ce modèle est appliqué à


(aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa()

il donne "pas de correspondance" rapidement. Cependant, si un quantificateur possessif n'est pas utilisé, la correspondance prend très longtemps car il existe de nombreuses façons différentes dont les répétitions + et * peuvent découper le sujet, et toutes doivent être testées avant que l'échec ne puisse être rapporté.

À la fin d'une correspondance, les valeurs des parenthèses de capture sont celles du niveau le plus externe. Si vous souhaitez obtenir des valeurs intermédiaires, une fonction d'appel peut être utilisée (voir ci-dessous et la documentation de pcre2callout). Si le modèle ci-dessus est mis en correspondance avec


(ab(cd)ef)

la valeur pour les parenthèses de capture internes (numérotées 2) est "ef", qui est la dernière valeur prise au niveau supérieur. Si un groupe de capture n'est pas mis en correspondance au niveau supérieur, sa valeur capturée finale est annulée, même si elle a été (temporairement) définie à un niveau plus profond pendant le processus de mise en correspondance.

Ne confondez pas l'élément (?R) avec la condition (R), qui teste la récursion. Considérez ce modèle, qui fait correspondre du texte entre crochets, permettant un imbrication arbitraire. Seuls les chiffres sont autorisés dans les crochets imbriqués (c'est-à-dire lors de la récursion), alors que tous les caractères sont autorisés au niveau externe.


< (?: (?(R) \d++ | [^<>]*+) | (?R)) * >

Dans ce modèle, (?(R) est le début d'un groupe conditionnel, avec deux alternatives différentes pour les cas récursifs et non récursifs. L'élément (?R) est l'appel récursif réel.

Différences de traitement de la récursion entre PCRE2 et Perl

Certaines anciennes différences entre PCRE2 et Perl n'existent plus.

Avant la version 10.30, le traitement de la récursion dans PCRE2 différait de Perl en ce qu'un appel de sous-routine récursive était toujours traité comme un groupe atomique. C'est-à-dire qu'une fois qu'il avait fait correspondre une partie de la chaîne sujet, il n'était jamais ré-entré, même s'il contenait des alternatives non essayées et qu'il y avait un échec de correspondance ultérieur. (Note historique : PCRE a implémenté la récursion avant Perl.)

À partir de la version 10.30, les appels de sous-routine récursive ne sont plus traités comme atomiques. C'est-à-dire qu'ils peuvent être ré-entré pour essayer des alternatives non utilisées en cas d'échec de correspondance plus tard dans le modèle. Ceci est maintenant compatible avec le fonctionnement de Perl. Si vous voulez qu'un appel de sous-routine soit atomique, vous devez l'enfermer explicitement dans un groupe atomique.

La prise en charge du retour arrière dans les récursions simplifie certains types de modèles récursifs. Par exemple, ce modèle fait correspondre des chaînes palindromiques :


^((.)(?1)\2|.?)$

La deuxième branche du groupe fait correspondre un seul caractère central dans le palindrome lorsqu'il y a un nombre impair de caractères, ou rien lorsqu'il y a un nombre pair de caractères, mais pour fonctionner, elle doit pouvoir essayer le deuxième cas lorsque le reste du modèle échoue. Si vous voulez faire correspondre des phrases palindromiques typiques, le modèle doit ignorer tous les caractères non mots, ce qui peut être fait comme suit :


^\W*+((.)\W*+(?1)\W*+\2|\W*+.?)\W*+$

S'il est exécuté avec l'option PCRE2_CASELESS, ce modèle fait correspondre des phrases telles que "A man, a plan, a canal: Panama !". Notez l'utilisation du quantificateur possessif *+ pour éviter le retour arrière dans des séquences de caractères non mots. Sans cela, PCRE2 prend beaucoup plus de temps (dix fois ou plus) pour faire correspondre des phrases typiques, et Perl prend tellement de temps que vous pensez qu'il est entré dans une boucle.

Une autre façon dont PCRE2 et Perl différaient dans leur traitement de la récursion est la gestion des valeurs capturées. Auparavant dans Perl, lorsqu'un groupe était appelé récursivement ou comme sous-routine (voir la section suivante), il n'avait pas accès aux valeurs capturées à l'extérieur de la récursion, alors que dans PCRE2 ces valeurs peuvent être référencées. Considérez ce modèle :


^(.)(\1|a(?2))

Ce modèle correspond à "bab". Les premières parenthèses de capture correspondent à "b", puis dans le deuxième groupe, lorsque la référence arrière \1 échoue à faire correspondre "b", la deuxième alternative correspond à "a" puis récurse. Dans la récursion, \1 correspond maintenant à "b" et ainsi la correspondance entière réussit. Cette correspondance échouait auparavant dans Perl, mais dans les versions ultérieures (j'ai essayé 5.024) elle fonctionne maintenant.

Groupes comme sous-routines

Si la syntaxe d'un appel de groupe récursif (par numéro ou par nom) est utilisée en dehors des parenthèses auxquelles elle fait référence, elle fonctionne un peu comme une sous-routine dans un langage de programmation. Plus précisément, PCRE2 traite le groupe référencé comme un sous-modèle indépendant qu'il essaie de faire correspondre à la position de correspondance actuelle. Le groupe appelé peut être défini avant ou après la référence. Une référence numérotée peut être absolue ou relative, comme dans ces exemples :


(...(absolu)...)...(?2)...
(...(relatif)...)...(?-1)...
(...(?+1)...(relatif)...

Un exemple précédent a souligné que le modèle


(sens|respons)e et \1ibility

correspond à "sense and sensibility" et "response and responsibility", mais pas à "sense and responsibility". Si au lieu de cela, le modèle


(sens|respons)e and (?1)ibility

est utilisé, il correspond à "sense and responsibility" ainsi qu'aux deux autres chaînes. Un autre exemple est donné dans la discussion de DEFINE ci-dessus.

Comme les récursions, les appels de sous-routines étaient auparavant traités comme atomiques, mais cela a changé à la version 10.30 de PCRE2, de sorte que le retour arrière dans les appels de sous-routines peut maintenant se produire. Cependant, toutes les parenthèses de capture qui sont définies pendant l'appel de sous-routine reviennent à leurs valeurs précédentes par la suite.

Les options de traitement telles que l'indépendance de la casse sont fixées lors de la définition d'un groupe, donc s'il est utilisé comme sous-routine, de telles options ne peuvent pas être modifiées pour différents appels. Par exemple, considérez ce modèle :


(abc)(?i:(?-1))

Il correspond à "abcabc". Il ne correspond pas à "abcABC" car le changement d'option de traitement n'affecte pas le groupe appelé.

Le comportement des verbes de contrôle de retour arrière dans les groupes lorsqu'ils sont appelés comme sous-routines est décrit dans la section intitulée "Verbes de retour arrière dans les sous-routines" ci-dessous.

Récursion et sous-routines avec groupes de capture retournés

Depuis PCRE2 10.46, les appels de récursion et de sous-routine peuvent également spécifier une liste de groupes de capture à retourner. Il s'agit d'une extension de syntaxe PCRE2 non prise en charge par Perl. La correspondance du modèle récurse dans l'expression référencée comme décrit ci-dessus, cependant, lorsque la récursion retourne à l'expression appelante, les sous-groupes capturés pendant la récursion peuvent être conservés lorsque le contexte de l'expression appelante est restauré.

Lorsqu'il est utilisé comme sous-routine, cela permet aux groupes de capture de la sous-routine d'être utilisés comme valeurs de retour.

Seuls les groupes de capture spécifiques listés par l'appelant seront conservés, en utilisant la syntaxe suivante :


(?R(grouplist)) récurse tout le modèle, retournant les groupes de capture
(?n(grouplist)) )
(?+n(grouplist)) )
(?-n(grouplist)) ) appelle la sous-routine, retournant les groupes de capture
(?&name(grouplist)) )
(?P>name(grouplist)) )

La liste des groupes de capture "grouplist" est une liste séparée par des virgules de numéros de groupe (absolus ou relatifs), et de noms de groupe entourés d'apostrophes ou d'angles.

Voici un exemple qui utilise d'abord la condition DEFINE pour créer une routine réutilisable pour faire correspondre un jour de la semaine, puis appelle cette sous-routine et conserve les groupes qu'elle capture pour une utilisation ultérieure :


(?x: # ignorer les espaces blancs pour plus de clarté
# Définir la routine "weekendday" qui correspond à samedi ou
# dimanche, et retourne le préfixe Sam/Dim sous forme de \k<short>.
(?(DEFINE) (?<weekendday>
(?|(?<short>Sat)urday|(?<short>Sun)day) ) )
# Appeler la routine. Correspond à "Saturday,Sat" ou "Sunday,Sun".
(?&weekendday(<short>)),\k<short> )

Cette fonctionnalité n'est pas disponible en utilisant la syntaxe Oniguruma \g<...> ou \g'...' ci-dessous.

Syntaxe de sous-routine Oniguruma

Par compatibilité avec Oniguruma, la syntaxe non-Perl \g suivie d'un nom ou d'un nombre entre crochets ou apostrophes, est une syntaxe alternative pour appeler un groupe comme une sous-routine, éventuellement de manière récursive. Voici deux des exemples utilisés ci-dessus, réécrits en utilisant cette syntaxe :


(?<pn> \( ( (?>[^()]+) | \g<pn> )* \) )
(sens|respons)e et \g'1'ibilité

PCRE2 prend en charge une extension à Oniguruma : si un nombre est précédé d'un signe plus ou moins, il est considéré comme une référence relative. Par exemple :


(abc)(?i:\g<-1>)

Notez que \g{...} (syntaxe Perl) et \g<...> (syntaxe Oniguruma) ne sont *pas* synonymes. Le premier est une réutilisation ; le second est un appel de sous-routine.

APPELS EXTERNES

Perl dispose d'une fonctionnalité où l'utilisation de la séquence (?{...}) déclenche l'exécution de code Perl arbitraire au milieu de la correspondance d'une expression régulière. Cela permet, entre autres choses, d'extraire différentes sous-chaînes qui correspondent à la même paire de parenthèses en cas de répétition.

PCRE2 propose une fonctionnalité similaire, mais bien sûr, il ne peut pas exécuter de code Perl arbitraire. Cette fonctionnalité s'appelle "appel externe" (callout). L'appelant de PCRE2 fournit une fonction externe en plaçant son point d'entrée dans un contexte de correspondance à l'aide de la fonction pcre2_set_callout(), puis en passant ce contexte à pcre2_match() ou pcre2_dfa_match(). Si aucun contexte de correspondance n'est passé, ou si le point d'entrée de l'appel externe est défini sur NULL, les points d'appel externes seront ignorés silencieusement pendant la correspondance. Pour interdire les appels externes dans la syntaxe du motif, vous pouvez utiliser l'option PCRE2_EXTRA_NEVER_CALLOUT.

Dans une expression régulière, (?C<arg>) indique un point auquel la fonction externe doit être appelée. Il existe deux types d'appels externes : ceux avec un argument numérique et ceux avec un argument de chaîne. (?C) seul, sans argument, est traité comme (?C0). Un argument numérique permet à l'application de distinguer différents appels externes. Les arguments de chaîne ont été ajoutés à partir de la version 10.20 pour permettre aux langages de script utilisant PCRE2 d'intégrer de courts scripts dans les motifs, de manière similaire à Perl.

Pendant la correspondance, lorsque PCRE2 atteint un point d'appel externe, la fonction externe est appelée. Elle reçoit l'argument numérique ou de chaîne de l'appel externe, la position dans le motif, et une donnée qui est également définie dans le bloc de correspondance. La fonction d'appel externe peut provoquer la poursuite de la correspondance, le retour arrière ou l'échec.

Par défaut, PCRE2 implémente un certain nombre d'optimisations lors de la correspondance, et l'un des effets secondaires est que les appels externes sont parfois ignorés. Si vous souhaitez que tous les appels externes possibles se produisent, vous devez définir des options qui désactivent les optimisations pertinentes. Plus de détails, y compris une description complète de l'interface de programmation de la fonction d'appel externe, sont donnés dans la documentation de pcre2callout.

Appels externes avec arguments numériques

Si vous souhaitez simplement disposer d'un moyen d'identifier différents points d'appel externes, placez un nombre inférieur à 256 après la lettre C. Par exemple, ce motif comporte deux points d'appel externes :


(?C1)abc(?C2)def

Si le drapeau PCRE2_AUTO_CALLOUT est passé à pcre2_compile(), des appels externes numériques sont automatiquement installés avant chaque élément du motif. Ils sont tous numérotés 255. S'il y a un groupe conditionnel dans le motif dont la condition est une assertion, un appel externe supplémentaire est inséré juste avant la condition. Un appel externe explicite peut également être défini à cette position, comme dans cet exemple :


(?(?C9)(?=a)abc|def)

Notez que cela ne s'applique qu'aux conditions d'assertion, pas aux autres types de conditions.

Appels externes avec arguments de chaîne

Une chaîne délimitée peut être utilisée à la place d'un nombre comme argument d'appel externe. Le délimiteur de début doit être l'un de ` ' " ^ % # $ { et le délimiteur de fin est le même que le début, sauf pour {, où le délimiteur de fin est }. Si le délimiteur de fin est nécessaire dans la chaîne, il doit être doublé. Par exemple :


(?C'ab ''c'' d')xyz(?C{any text})pqr

Le doublage est supprimé avant que la chaîne ne soit passée à la fonction d'appel externe.

CONTRÔLE DU RETOUR ARRIÈRE

Il existe un certain nombre de "Verbes de contrôle du retour arrière" spéciaux (pour utiliser la terminologie de Perl) qui modifient le comportement du retour arrière pendant la correspondance. Ils sont généralement de la forme (*VERBE) ou (*VERBE:NOM). Certains verbes acceptent les deux formes et peuvent se comporter différemment selon qu'un argument de nom est présent ou non. Les noms ne sont pas nécessairement uniques dans le motif.

Par défaut, pour assurer la compatibilité avec Perl, un nom est toute séquence de caractères qui n'inclut pas de parenthèse fermante. Le nom n'est pas traité de quelque manière que ce soit, et il n'est pas possible d'inclure une parenthèse fermante dans le nom. Cela peut être modifié en définissant l'option PCRE2_ALT_VERBNAMES, mais le résultat n'est alors plus compatible avec Perl.

Lorsque PCRE2_ALT_VERBNAMES est défini, le traitement des barres obliques inverses est appliqué aux noms de verbes et seule une parenthèse fermante non échappée termine le nom. Cependant, les seuls éléments de barre oblique inverse autorisés sont \Q, \E et les séquences telles que \x{100} qui définissent des points de code de caractère. Les échappements de type de caractère tels que \d provoquent une erreur.

Une parenthèse fermante peut être incluse dans un nom soit sous la forme \), soit entre \Q et \E. En plus du traitement des barres obliques inverses, si l'option PCRE2_EXTENDED ou PCRE2_EXTENDED_MORE est également définie, les espaces blancs non échappés dans les noms de verbes sont ignorés, et les commentaires #-sont reconnus, exactement comme dans le reste du motif. PCRE2_EXTENDED et PCRE2_EXTENDED_MORE n'affectent pas les noms de verbes à moins que PCRE2_ALT_VERBNAMES ne soit également défini.

La longueur maximale d'un nom est de 255 dans la bibliothèque 8 bits et de 65535 dans les bibliothèques 16 et 32 bits. Si le nom est vide, c'est-à-dire si la parenthèse fermante suit immédiatement le deux-points, l'effet est comme si le deux-points n'était pas là. Un nombre quelconque de ces verbes peut apparaître dans un motif. À l'exception de (*ACCEPT), ils ne peuvent pas être quantifiés.

Comme ces verbes sont spécifiquement liés au retour arrière, la plupart d'entre eux ne peuvent être utilisés que lorsque le motif doit être mis en correspondance à l'aide de la fonction de correspondance traditionnelle ou de JIT, car ils utilisent des algorithmes de retour arrière. À l'exception de (*FAIL), qui se comporte comme une assertion négative échouée, les verbes de contrôle du retour arrière provoquent une erreur s'ils sont rencontrés par la fonction de correspondance DFA.

Le comportement de ces verbes dans les groupes répétés, les assertions et les groupes de capture appelés comme sous-routines (qu'ils soient récursifs ou non) est documenté ci-dessous.

Optimisations qui affectent les verbes de retour arrière

PCRE2 contient des optimisations qui sont utilisées pour accélérer la correspondance en effectuant certaines vérifications au début de chaque tentative de correspondance. Par exemple, il peut connaître la longueur minimale du sujet correspondant, ou qu'un caractère particulier doit être présent. Lorsqu'une de ces optimisations contourne l'exécution d'une correspondance, les verbes de retour arrière inclus ne seront bien sûr pas traités. Vous pouvez supprimer les optimisations de début de correspondance en définissant l'option PCRE2_NO_START_OPTIMIZE lors de l'appel à pcre2_compile(), en appelant pcre2_set_optimize() avec une directive PCRE2_START_OPTIMIZE_OFF, ou en commençant le motif par (*NO_START_OPT). Il y a plus de discussion sur cette option dans la section intitulée "Compilation d'un motif" de la documentation pcre2api.

Les expériences avec Perl suggèrent qu'il possède également des optimisations similaires, et comme PCRE2, désactiver ces optimisations peut modifier le résultat d'une correspondance.

Verbes qui agissent immédiatement

Les verbes suivants agissent dès qu'ils sont rencontrés.


(*ACCEPT) ou (*ACCEPT:NOM)

Ce verbe provoque la fin réussie de la correspondance, en ignorant le reste du motif. Cependant, lorsqu'il se trouve à l'intérieur d'un groupe de capture appelé comme sous-routine, seul ce groupe se termine avec succès. La correspondance se poursuit ensuite au niveau supérieur. Si (*ACCEPT) est déclenché dans une assertion positive, l'assertion réussit ; dans une assertion négative, l'assertion échoue.

Si (*ACCEPT) est à l'intérieur de parenthèses de capture, les données jusqu'à présent sont capturées. Par exemple :


A((?:A|B(*ACCEPT)|C)D)

Cela correspond à "AB", "AAD", ou "ACD" ; lorsqu'il correspond à "AB", "B" est capturé par les parenthèses externes.

(*ACCEPT) est le seul verbe de retour arrière autorisé à être quantifié car une quantification non gourmande avec un minimum de zéro n'agit que lors d'un retour arrière. Considérez, par exemple,


(A(*ACCEPT)??B)C

où A, B et C peuvent être des expressions complexes. Après avoir mis en correspondance "A", le moteur de correspondance traite "BC" ; si cela échoue, provoquant un retour arrière, (*ACCEPT) est déclenché et la correspondance réussit. Dans les deux cas, tout sauf C est capturé. Alors que (*COMMIT) (voir ci-dessous) signifie "échouer au retour arrière", un (*ACCEPT) répété de ce type signifie "réussir au retour arrière".

Attention : (*ACCEPT) ne doit pas être utilisé dans un groupe d'exécution de script, car il provoque une sortie immédiate du groupe, contournant la vérification d'exécution du script.


(*FAIL) ou (*FAIL:NOM)

Ce verbe provoque un échec de correspondance, forçant un retour arrière. Il peut être abrégé en (*F). Il est équivalent à (?!) mais plus facile à lire. La documentation Perl note qu'il est probablement utile uniquement lorsqu'il est combiné avec (?{}) ou (??{}). Ce sont, bien sûr, des fonctionnalités Perl qui ne sont pas présentes dans PCRE2. L'équivalent le plus proche est la fonctionnalité d'appel externe, comme par exemple dans ce motif :


a+(?C)(*FAIL)

Une correspondance avec la chaîne "aaaa" échoue toujours, mais l'appel externe est pris avant chaque retour arrière (dans cet exemple, 10 fois).

(*ACCEPT:NOM) et (*FAIL:NOM) se comportent comme (*MARK:NOM)(*ACCEPT) et (*MARK:NOM)(*FAIL), respectivement, c'est-à-dire qu'un (*MARK) est enregistré juste avant que le verbe n'agisse.

Enregistrement du chemin emprunté

Il existe un verbe dont le but principal est de suivre le chemin emprunté pour parvenir à une correspondance, bien qu'il ait également une utilisation secondaire en conjonction avec l'avancement du point de départ de la correspondance (voir (*SKIP) ci-dessous).


(*MARK:NOM) ou (*:NOM)

Un nom est toujours requis avec ce verbe. Pour tous les autres verbes de contrôle de retour arrière, un argument NOM est facultatif.

Lorsqu'une correspondance réussit, le nom du dernier nom de marque rencontré sur le chemin de correspondance est renvoyé à l'appelant, comme décrit dans la section intitulée "Autres informations sur la correspondance" de la documentation pcre2api. Ceci s'applique à toutes les instances de (*MARK) et autres verbes, y compris ceux à l'intérieur des assertions et des groupes atomiques. Cependant, il existe des différences dans ces cas lorsque (*MARK) est utilisé en conjonction avec (*SKIP), comme décrit ci-dessous.

Le nom de marque qui a été rencontré en dernier sur le chemin de correspondance est renvoyé. Un verbe sans argument NOM est ignoré à cette fin. Voici un exemple de sortie de pcre2test, où le modificateur "mark" demande la récupération et la sortie des données (*MARK) :


re> /X(*MARK:A)Y|X(*MARK:B)Z/mark
data> XY
0: XY
MK: A
XZ
0: XZ
MK: B

Le nom (*MARK) est étiqueté avec "MK:" dans cette sortie, et dans cet exemple, il indique laquelle des deux alternatives a correspondu. C'est une manière plus efficace d'obtenir cette information que de placer chaque alternative dans ses propres parenthèses de capture.

Si un verbe avec un nom est rencontré dans une assertion positive qui est vraie, le nom est enregistré et renvoyé s'il est le dernier rencontré. Cela ne se produit pas pour les assertions négatives ou les assertions positives échouées.

Après une correspondance partielle ou une correspondance échouée, le dernier nom rencontré dans l'ensemble du processus de correspondance est retourné. Par exemple :


re> /X(*MARK:A)Y|X(*MARK:B)Z/mark
data> XP
No match, mark = B

Notez que dans cet exemple non ancré, la marque est conservée de la tentative de correspondance qui a commencé à la lettre "X" dans le sujet. Les tentatives de correspondance ultérieures commençant à "P" puis avec une chaîne vide n'atteignent pas l'élément (*MARK), mais ne le réinitialisent néanmoins pas.

Si vous êtes intéressé par les valeurs (*MARK) après des correspondances échouées, vous devriez probablement soit définir l'option PCRE2_NO_START_OPTIMIZE, soit appeler pcre2_set_optimize() avec une directive PCRE2_START_OPTIMIZE_OFF (voir ci-dessus) pour vous assurer que la correspondance est toujours tentée.

Verbes qui agissent après le retour arrière

Les verbes suivants ne font rien lorsqu'ils sont rencontrés. La correspondance continue avec ce qui suit, mais s'il y a un échec de correspondance ultérieur, provoquant un retour arrière vers le verbe, un échec est forcé. C'est-à-dire que le retour arrière ne peut pas passer à gauche du verbe. Cependant, lorsque l'un de ces verbes apparaît à l'intérieur d'un groupe atomique ou d'une assertion atomique qui est vraie, son effet est confiné à ce groupe, car une fois que le groupe a été mis en correspondance, il n'y a jamais de retour arrière dedans. Le retour arrière depuis au-delà d'une assertion ou d'un groupe atomique ignore le groupe entier et recherche un point de retour arrière précédent.

Ces verbes diffèrent dans ce qui se passe exactement lorsqu'un retour arrière atteint le verbe. Le comportement décrit ci-dessous est ce qui se produit lorsque le verbe n'est pas dans une sous-routine ou une assertion. Les sections suivantes couvrent ces cas spéciaux.


(*COMMIT) ou (*COMMIT:NOM)

Ce verbe provoque l'échec complet de la correspondance si un échec de correspondance ultérieur provoque un retour arrière vers celui-ci. Même si le motif n'est pas ancré, aucune tentative supplémentaire de trouver une correspondance en avançant le point de départ n'a lieu. Si (*COMMIT) est le seul verbe de retour arrière rencontré, une fois qu'il a été passé, pcre2_match() s'engage à trouver une correspondance au point de départ actuel, ou pas du tout. Par exemple :


a+(*COMMIT)b

Cela correspond à "xxaab" mais pas à "aacaab". On peut le considérer comme une sorte d'ancre dynamique, ou "J'ai commencé, donc je dois finir."

Le comportement de (*COMMIT:NOM) n'est pas le même que (*MARK:NOM)(*COMMIT). Il est similaire à (*MARK:NOM) en ce sens que le nom est mémorisé pour être renvoyé à l'appelant. Cependant, (*SKIP:NOM) recherche uniquement les noms définis avec (*MARK), ignorant ceux définis par les autres verbes de retour arrière.

S'il y a plus d'un verbe de retour arrière dans un motif, un autre verbe qui suit (*COMMIT) peut être déclenché en premier, donc le simple fait de passer par (*COMMIT) lors d'une correspondance ne garantit pas toujours qu'une correspondance doit avoir lieu à ce point de départ.

Notez que (*COMMIT) au début d'un motif n'est pas la même chose qu'une ancre, à moins que les optimisations de début de correspondance de PCRE2 ne soient désactivées, comme le montre cette sortie de pcre2test :


re> /(*COMMIT)abc/
data> xyzabc
0: abc
data>
re> /(*COMMIT)abc/no_start_optimize
data> xyzabc
No match

Pour le premier motif, PCRE2 sait que toute correspondance doit commencer par "a", l'optimisation saute donc le long du sujet jusqu'à "a" avant d'appliquer le motif aux premières données. La tentative de correspondance réussit alors. Le second motif désactive l'optimisation qui saute jusqu'au premier caractère. Le motif est maintenant appliqué en commençant par "x", et donc (*COMMIT) provoque l'échec de la correspondance sans essayer d'autres points de départ.


(*PRUNE) ou (*PRUNE:NOM)

Ce verbe provoque l'échec de la correspondance à la position de départ actuelle dans le sujet si un échec de correspondance ultérieur provoque un retour arrière vers celui-ci. Si le motif n'est pas ancré, l'avancement normal "bumpalong" vers le caractère suivant se produit. Un retour arrière peut se produire comme d'habitude à gauche de (*PRUNE), avant qu'il ne soit atteint, ou lors de la correspondance à droite de (*PRUNE), mais s'il n'y a pas de correspondance à droite, le retour arrière ne peut pas traverser (*PRUNE). Dans des cas simples, l'utilisation de (*PRUNE) est juste une alternative à un groupe atomique ou un quantificateur possessif, mais il existe des utilisations de (*PRUNE) qui ne peuvent pas être exprimées autrement. Dans un motif ancré, (*PRUNE) a le même effet que (*COMMIT).

Le comportement de (*PRUNE:NOM) n'est pas le même que (*MARK:NOM)(*PRUNE). Il est similaire à (*MARK:NOM) en ce sens que le nom est mémorisé pour être renvoyé à l'appelant. Cependant, (*SKIP:NOM) recherche uniquement les noms définis par (*MARK), ignorant ceux définis par d'autres verbes de retour arrière.


(*SKIP)

Ce verbe, lorsqu'il est donné sans nom, est similaire à (*PRUNE), sauf que si le motif n'est pas ancré, l'avancement "bumpalong" n'est pas au caractère suivant, mais à la position dans le sujet où (*SKIP) a été rencontré. (*SKIP) signifie que tout texte correspondant jusqu'à lui ne peut pas faire partie d'une correspondance réussie s'il y a une divergence ultérieure. Considérons :


a+(*SKIP)b

Si le sujet est "aaaac...", après que la première tentative de correspondance échoue (en commençant au premier caractère de la chaîne), le point de départ continue pour commencer la tentative suivante à "c". Notez qu'un quantificateur possessif n'a pas le même effet que cet exemple ; bien qu'il supprime le retour arrière pendant la première tentative de correspondance, la deuxième tentative commencerait au deuxième caractère au lieu de sauter jusqu'à "c".

Si (*SKIP) est utilisé pour spécifier une nouvelle position de départ qui est la même que la position de départ de la correspondance actuelle, ou (en étant à l'intérieur d'un lookbehind) antérieure, la position spécifiée par (*SKIP) est ignorée, et au lieu de cela, le "bumpalong" normal se produit.


(*SKIP:NOM)

Lorsque (*SKIP) a un nom associé, son comportement est modifié. Lorsqu'un tel (*SKIP) est déclenché, le chemin précédent à travers le motif est recherché pour la marque (*MARK) la plus récente ayant le même nom. Si une telle marque est trouvée, l'avancement "bumpalong" se fait vers la position du sujet qui correspond à cette (*MARK) au lieu de là où (*SKIP) a été rencontré. Si aucune (*MARK) avec un nom correspondant n'est trouvée, le (*SKIP) est ignoré.

La recherche d'un nom (*MARK) utilise le mécanisme de retour arrière normal, ce qui signifie qu'elle ne voit pas les paramètres (*MARK) qui se trouvent à l'intérieur de groupes atomiques ou d'assertions, car ils ne sont jamais réentrer par le retour arrière. Comparez les exemples pcre2test suivants :


re> /a(?>(*MARK:X))(*SKIP:X)(*F)|(.)/
data: abc
0: a
1: a
data:
re> /a(?:(*MARK:X))(*SKIP:X)(*F)|(.)/
data: abc
0: b
1: b

Dans le premier exemple, le paramètre (*MARK) se trouve dans un groupe atomique, il n'est donc pas vu lorsque (*SKIP:X) est déclenché, ce qui provoque l'ignorance de (*SKIP). Cela permet à la deuxième branche du motif d'être essayée à la première position de caractère. Dans le second exemple, le paramètre (*MARK) ne se trouve pas dans un groupe atomique. Cela permet à (*SKIP:X) de trouver la (*MARK) lors du retour arrière, ce qui provoque le démarrage d'une nouvelle tentative de correspondance au deuxième caractère. Cette fois, la (*MARK) n'est jamais vue car "a" ne correspond pas à "b", donc le moteur de correspondance saute immédiatement à la deuxième branche du motif.

Notez que (*SKIP:NOM) recherche uniquement les noms définis par (*MARK:NOM). Il ignore les noms définis par d'autres verbes de retour arrière.


(*THEN) ou (*THEN:NOM)

Ce verbe provoque un saut vers la prochaine alternative la plus interne lorsque le retour arrière l'atteint. C'est-à-dire qu'il annule tout retour arrière supplémentaire dans l'alternative actuelle. Son nom vient de l'observation qu'il peut être utilisé pour un bloc conditionnel basé sur un motif :


( COND1 (*THEN) FOO | COND2 (*THEN) BAR | COND3 (*THEN) BAZ ) ...

Si le motif COND1 correspond, FOO est essayé (et éventuellement des éléments supplémentaires après la fin du groupe si FOO réussit) ; en cas d'échec, le moteur de correspondance saute à la deuxième alternative et essaie COND2, sans retour arrière dans COND1. Si cela réussit et que BAR échoue, COND3 est essayé. Si par la suite BAZ échoue, il n'y a plus d'alternatives, donc il y a un retour arrière vers ce qui précède le groupe entier. Si (*THEN) n'est pas à l'intérieur d'une alternance, il agit comme (*PRUNE).

Le comportement de (*THEN:NOM) n'est pas le même que (*MARK:NOM)(*THEN). Il est similaire à (*MARK:NOM) en ce sens que le nom est mémorisé pour être renvoyé à l'appelant. Cependant, (*SKIP:NOM) recherche uniquement les noms définis par (*MARK), ignorant ceux définis par d'autres verbes de retour arrière.

Verbes de rétroaction

Certains verbes de rétroaction de PCRE2 ont un effet différent de celui de Perl dans certaines situations complexes.

Influence des alternatives externes

Considérez le modèle suivant, où A, B, etc. sont des fragments de modèle complexes ne contenant aucun caractère | à ce niveau :


A (B(*THEN)C) | D

Si A et B correspondent, mais qu'il y a un échec dans C, la correspondance ne revient pas en arrière dans A ; au lieu de cela, elle passe à l'alternative suivante, c'est-à-dire D. Cependant, si le groupe contenant (*THEN) reçoit une alternative, il se comporte différemment :


A (B(*THEN)C | (*FAIL)) | D

L'effet de (*THEN) est maintenant confiné au groupe interne. Après un échec dans C, la correspondance passe à (*FAIL), ce qui fait échouer tout le groupe car il n'y a plus d'alternatives à essayer. Dans ce cas, la correspondance revient en arrière dans A.

Notez qu'un groupe conditionnel n'est pas considéré comme ayant deux alternatives, car une seule est jamais utilisée. En d'autres termes, le caractère | dans un groupe conditionnel a une signification différente. En ignorant les espaces blancs, considérez :


^.*? (?(?=a) a | b(*THEN)c )

Si le sujet est « ba », ce modèle ne correspond pas. Parce que .*? est avide de retour arrière, il correspond initialement à zéro caractère. La condition (?=a) échoue ensuite, le caractère « b » est mis en correspondance, mais « c » ne l'est pas. À ce stade, la correspondance ne revient pas en arrière à .*? comme on pourrait s'y attendre en raison de la présence du caractère |. Le groupe conditionnel fait partie de l'unique alternative qui constitue l'ensemble du modèle, et la correspondance échoue donc. (S'il y avait un retour arrière dans .*?, lui permettant de correspondre à « b », la correspondance réussirait.)

Les verbes décrits ci-dessus fournissent quatre « forces » de contrôle différentes lorsque la correspondance ultérieure échoue. (*THEN) est le plus faible, poursuivant la correspondance à l'alternative suivante. (*PRUNE) vient ensuite, faisant échouer la correspondance à la position de départ actuelle, mais permettant une avancée au caractère suivant (pour un modèle non ancré). (*SKIP) est similaire, sauf que l'avancée peut être supérieure à un caractère. (*COMMIT) est le plus fort, provoquant l'échec complet de la correspondance.

Plusieurs verbes de rétroaction

Si plusieurs verbes de rétroaction sont présents dans un modèle, celui sur lequel le retour arrière se fait en premier agit. Par exemple, considérez ce modèle, où A, B, etc. sont des fragments de modèle complexes :


(A(*COMMIT)B(*THEN)C|ABD)

Si A correspond mais que B échoue, le retour arrière vers (*COMMIT) provoque l'échec complet de la correspondance. Cependant, si A et B correspondent, mais que C échoue, le retour arrière vers (*THEN) provoque l'essai de l'alternative suivante (ABD). Ce comportement est cohérent, mais n'est pas toujours identique à celui de Perl. Cela signifie que si deux verbes de rétroaction ou plus apparaissent successivement, tous sauf le dernier d'entre eux n'ont aucun effet. Considérez cet exemple :


...(*COMMIT)(*PRUNE)...

S'il y a un échec de correspondance à droite, le retour arrière vers (*PRUNE) provoque son déclenchement, et son action est effectuée. Il ne peut jamais y avoir de retour arrière vers (*COMMIT).

Verbes de rétroaction dans les groupes répétés

PCRE2 diffère parfois de Perl dans sa gestion des verbes de rétroaction dans les groupes répétés. Par exemple, considérez :


/(a(*COMMIT)b)+ac/

Si le sujet est « abac », Perl correspond sauf si ses optimisations sont désactivées, mais PCRE2 échoue toujours car le (*COMMIT) dans la deuxième répétition du groupe agit.

Verbes de rétroaction dans les assertions

(*FAIL) dans une assertion a son effet normal : il force un retour arrière immédiat. Le comportement des autres verbes de rétroaction dépend de si l'assertion est autonome ou agit comme condition dans un groupe conditionnel.

(*ACCEPT) dans une assertion positive autonome fait réussir l'assertion sans autre traitement ; les chaînes capturées et un nom de marque (s'il est défini) sont conservés. Dans une assertion négative autonome, (*ACCEPT) fait échouer l'assertion sans autre traitement ; les sous-chaînes capturées et tout nom de marque sont rejetés.

Si l'assertion est une condition, (*ACCEPT) fait que la condition soit vraie pour une assertion positive et fausse pour une assertion négative ; les sous-chaînes capturées sont conservées dans les deux cas.

Les verbes restants n'agissent que lorsqu'un échec ultérieur provoque un retour arrière jusqu'à eux. Cela signifie que, pour les assertions compatibles avec Perl, leur effet est confiné à l'assertion, car les assertions de lookaround de Perl sont atomiques. Un retour arrière qui se produit après qu'une telle assertion est terminée ne revient pas dans l'assertion. Notez en particulier qu'un nom (*MARK) défini dans une assertion n'est pas « vu » par une instance de (*SKIP:NAME) plus loin dans le modèle.

PCRE2 prend maintenant en charge les assertions positives non atomiques ainsi que les assertions de « sous-chaîne de balayage », comme décrit dans les sections intitulées « Assertions non atomiques » et « Assertions de sous-chaîne de balayage » ci-dessus. Ces assertions doivent être autonomes (ne pas être utilisées comme conditions). Elles ne sont pas compatibles avec Perl. Pour ces assertions, un retour arrière ultérieur revient dans l'assertion, et par conséquent des verbes comme (*COMMIT) peuvent être déclenchés par des retours arrière provenant de plus loin dans le modèle.

L'effet de (*THEN) n'est pas autorisé à s'échapper au-delà d'une assertion. S'il n'y a plus de branches à essayer, (*THEN) rend une assertion positive fausse et une assertion négative vraie. Ce comportement diffère de Perl lorsque l'assertion n'a qu'une seule branche.

Les autres verbes de rétroaction ne sont pas traités spécialement s'ils apparaissent dans une assertion positive autonome. Dans une assertion positive conditionnelle, le retour arrière (depuis l'intérieur de l'assertion) vers (*COMMIT), (*SKIP) ou (*PRUNE) rend la condition fausse. Cependant, pour les assertions négatives autonomes et conditionnelles, le retour arrière vers (*COMMIT), (*SKIP) ou (*PRUNE) rend l'assertion vraie, sans considérer d'autres branches alternatives.

Verbes de rétroaction dans les sous-programmes

Ces comportements se produisent, que le groupe soit appelé récursivement ou non.

(*ACCEPT) dans un groupe appelé comme sous-programme fait réussir la correspondance du sous-programme sans autre traitement. La correspondance continue ensuite après l'appel du sous-programme. Perl documente ce comportement. Le traitement par Perl des autres verbes dans les sous-programmes diffère dans certains cas.

(*FAIL) dans un groupe appelé comme sous-programme a son effet normal : il force un retour arrière immédiat.

(*COMMIT), (*SKIP) et (*PRUNE) font échouer la correspondance du sous-programme lorsqu'ils sont déclenchés par un retour arrière dans un groupe appelé comme sous-programme. Il y a ensuite un retour arrière au niveau externe.

(*THEN), lorsqu'il est déclenché, passe à l'alternative suivante dans le groupe le plus interne qui a des alternatives (son comportement normal). Cependant, s'il n'y a pas de tel groupe dans le groupe du sous-programme, la correspondance du sous-programme échoue et il y a un retour arrière au niveau externe.

ENVIRONNEMENTS EBCDIC

Les différences dans la façon dont PCRE se comporte lorsqu'il s'exécute dans un environnement EBCDIC sont couvertes dans cette section.

Séquences d'échappement

Lorsque PCRE2 est compilé en mode EBCDIC, \N{U+hhh..} n'est pas pris en charge. \a, \e, \f, \n, \r et \t génèrent les valeurs de code EBCDIC appropriées. L'échappement \c est traité comme spécifié pour Perl dans le document perlebcdic. Les seuls caractères autorisés après \c sont A-Z, a-z ou l'un de @, [, \, ], ^, _ ou ?. Tout autre caractère provoque une erreur de compilation. La séquence \c@ encode le caractère de code 0 ; après \c, les lettres (en majuscules ou minuscules) encodent les caractères 1-26 (hex 01 à hex 1A) ; [, \, ], ^ et _ encodent les caractères 27-31 (hex 1B à hex 1F), et \c? devient soit 255 (hex FF) soit 95 (hex 5F).

Ainsi, à l'exception de \c?, ces échappements génèrent les mêmes valeurs de code de caractère qu'ils le font dans un environnement ASCII ou Unicode, bien que les significations des valeurs diffèrent pour la plupart. Par exemple, \cG génère toujours la valeur de code 7, qui est BEL en ASCII mais DEL en EBCDIC.

La séquence \c? génère DEL (127, hex 7F) dans un environnement ASCII, mais comme 127 n'est pas un caractère de contrôle en EBCDIC, Perl le fait générer le caractère APC. Malheureusement, il existe plusieurs variantes d'EBCDIC. Dans la plupart d'entre elles, le caractère APC a la valeur 255 (hex FF), mais dans celle que Perl appelle POSIX-BC, sa valeur est 95 (hex 5F). Si certains autres caractères ont des valeurs POSIX-BC, PCRE2 fait que \c? génère 95 ; sinon, il génère 255.

Classes de caractères

Dans les classes de caractères, il y a un cas spécial dans les environnements EBCDIC pour les plages dont les points de terminaison sont tous deux spécifiés comme lettres littérales de la même casse. Par souci de compatibilité avec Perl, les points de code EBCDIC dans la plage qui ne sont pas des lettres sont omis. Par exemple, [h-k] correspond uniquement à quatre caractères, même si les codes EBCDIC de h et k sont 0x88 et 0x92, une plage de 11 points de code. Cependant, si la plage est spécifiée numériquement, par exemple, [\x88-\x92] ou [h-\x92], tous les points de code sont inclus.

NAME

pcre2pattern — PCRE2 regular expression details

PCRE2 REGULAR EXPRESSION DETAILS

This document describes the syntax of regular expressions that can be processed by the PCRE2 library.

EBCDIC CHARACTER CODES

PCRE2 can be configured to process EBCDIC character codes instead of ASCII. This is done by defining the macro PCRE2_CODE_UNIT_WIDTH to 8 when building the library and setting the PCRE2_NEWLINE configuration option appropriately. When EBCDIC is in use, the character codes mentioned in this document are the EBCDIC equivalents of the ASCII codes.

SPECIAL START-OF-PATTERN ITEMS

A pattern may begin with an optional BOM (byte order mark), followed by an optional sequence of script run items. These items specify the script run for subsequent parts of the pattern. The following items are supported:

  • \p{...}: Matches a character with the specified Unicode property.
  • \P{...}: Matches a character that does not have the specified Unicode property.
  • \u{...}: Matches a character with the specified Unicode codepoint.
  • \U{...}: Matches a character with the specified Unicode codepoint.

The PCRE2_UCP option must be set to enable these features.

CHARACTERS AND METACHARACTERS

Most characters match themselves. However, some characters have special meanings and are called metacharacters. These are:

( ) [ ] { } \ ^ $ . | * + ?

If you want to match one of these characters literally, you must escape it by preceding it with a backslash (\).

BACKSLASH

The backslash character (\) is used to escape the next character, giving it a special meaning or removing its special meaning. It is also used to introduce the following:

  • \a: Bell
  • \e: Escape
  • \f: Form feed
  • \n: Newline
  • \r: Carriage return
  • \t: Tab
  • \v: Vertical tab
  • \NNN: A decimal number (interpreted as a byte value)
  • \xHH: A hexadecimal number (interpreted as a byte value)
  • \c X: Control character X
  • \d: A digit (equivalent to [0-9] by default)
  • \D: A non-digit (equivalent to [^0-9] by default)
  • \h: A horizontal whitespace character
  • \H: A non-horizontal whitespace character
  • \s: A whitespace character
  • \S: A non-whitespace character
  • \w: A "word" character
  • \W: A non-"word" character
  • \Z: End of string
  • \z: End of string (like \Z but also matches newline at end of string)
  • \A: Start of string
  • \b: Word boundary
  • \B: Non-word boundary
  • \C: A single code unit (useful in UTF-8 mode)
  • \N{name}: Unicode character named name
  • \n: Backreference to group n
  • \g{name}: Backreference to named group name
  • \k{name}: Backreference to named group name
  • \p{...}: Unicode property
  • \P{...}: Negated Unicode property
  • \u{...}: Unicode codepoint
  • \U{...}: Unicode codepoint

CIRCUMFLEX AND DOLLAR

The circumflex (^) matches the start of the string, or the start of a line if the PCRE2_MULTILINE option is set. The dollar sign ($) matches the end of the string, or the end of a line if the PCRE2_MULTILINE option is set.

FULL STOP (PERIOD, DOT) AND \N

The full stop (.) matches any character except newline, unless the PCRE2_DOTALL option is set, in which case it matches any character including newline.

The escape sequence \N{name} matches the Unicode character named name.

MATCHING A SINGLE CODE UNIT

In UTF-8 mode, the sequence \C matches a single code unit, regardless of whether it is part of a multi-byte sequence. This can be useful for matching at arbitrary byte positions within a string.

SQUARE BRACKETS AND CHARACTER CLASSES

Square brackets are used to define a character class, which matches any single character within the brackets. For example, [abc] matches either 'a', 'b', or 'c'.

Ranges can be specified using a hyphen. For example, [a-z] matches any lowercase letter.

The caret (^) at the beginning of a character class negates it. For example, [^abc] matches any character except 'a', 'b', or 'c'.

PERL EXTENDED CHARACTER CLASSES

PCRE2 supports the following Perl-style extended character classes:

  • \d: A digit
  • \D: A non-digit
  • \w: A "word" character
  • \W: A non-"word" character
  • \s: A whitespace character
  • \S: A non-whitespace character

The exact characters matched by these classes depend on the locale and the options set.

UTS#18 EXTENDED CHARACTER CLASSES

PCRE2 supports Unicode properties as defined in UTS#18. These allow matching characters based on their Unicode properties, such as general category, script, or block.

Examples:

  • \p{Lu}: Matches any uppercase letter.
  • \p{Greek}: Matches any Greek letter.
  • \p{InBasicLatin}: Matches any character in the Basic Latin block.
  • \P{Lu}: Matches any character that is not an uppercase letter.

POSIX CHARACTER CLASSES

PCRE2 supports POSIX character classes, which are specified using square brackets and a name starting with a colon.

Examples:

  • [:alnum:]: Alphanumeric characters
  • [:alpha:]: Alphabetic characters
  • [:digit:]: Digits
  • [:lower:]: Lowercase letters
  • [:upper:]: Uppercase letters
  • [:space:]: Whitespace characters

These are equivalent to the corresponding Perl-style classes.

COMPATIBILITY FEATURE FOR WORD BOUNDARIES

The definition of a "word" character is locale-dependent. In POSIX mode, a word character is an alphanumeric character or an underscore. In Perl mode, a word character is any character that matches \w.

VERTICAL BAR

The vertical bar (|) is used to separate alternative patterns. For example, cat|dog matches either "cat" or "dog".

INTERNAL OPTION SETTING

Options can be set within the pattern using the syntax (?imsx-imsx:...) or (?imsx-imsx). The options are:

  • i: Case-insensitive matching
  • m: Multiline mode
  • s: Dotall mode
  • x: Extended mode (ignore whitespace and comments)

For example, (?i:abc) matches "abc" case-insensitively.

GROUPS

Parentheses (...) are used to group parts of the pattern. This is useful for applying quantifiers to a sequence of characters or for capturing matched substrings.

DUPLICATE GROUP NUMBERS

If a pattern contains multiple capturing groups with the same number, the most recently defined group takes precedence. This can lead to unexpected behavior.

NAMED CAPTURE GROUPS

Groups can be named using the syntax (?P<name>...) or (?'name'...). These named groups can be referenced later in the pattern using backreferences.

REPETITION

The following quantifiers can be used to specify repetition:

  • *: Zero or more times
  • +: One or more times
  • ?: Zero or one time
  • {n}: Exactly n times
  • {n,}: n or more times
  • {n,m}: Between n and m times

By default, quantifiers are greedy, meaning they match as much as possible. To make them lazy, append a question mark (?). For example, *? matches zero or more times, but as few times as possible.

ATOMIC GROUPING AND POSSESSIVE QUANTIFIERS

Atomic grouping (?>...) and possessive quantifiers (e.g., *+, ++, ?+, {n,m}+) prevent backtracking. Once a match is made within an atomic group or by a possessive quantifier, the engine will not backtrack into it, even if the overall match fails.

BACKREFERENCES

Backreferences allow you to match the same text that was previously matched by a capturing group. They are denoted by \n, where n is the number of the group.

Named groups can be backreferenced using \g{name} or \k{name}.

ASSERTIONS

Assertions are zero-width matches, meaning they do not consume any characters. They are used to check for conditions at a particular position in the string.

  • ^: Start of string/line
  • $: End of string/line
  • \b: Word boundary
  • \B: Non-word boundary
  • (?=...): Positive lookahead
  • (?!...): Negative lookahead
  • (?<=...): Positive lookbehind
  • (?<!...): Negative lookbehind

NON-ATOMIC ASSERTIONS

By default, lookbehind assertions are non-atomic, meaning the engine can backtrack within them. For atomic lookbehind assertions, use (?<=...) and (?. Note that PCRE2 does not support variable-length lookbehind assertions.

SCAN SUBSTRING ASSERTIONS

Scan substring assertions are a feature of PCRE2 that allows matching at the beginning or end of a substring. They are denoted by \K (start of match) and \R (newline).

SCRIPT RUNS

PCRE2 supports matching based on Unicode script runs. The sequences \p{...} and \P{...} can be used to match characters belonging to specific scripts.

CONDITIONAL GROUPS

Conditional groups allow you to make part of a pattern dependent on whether a previous group matched. The syntax is (?(condition)yes-pattern|no-pattern).

The condition can be a backreference or a lookaround assertion.

COMMENTS

In extended mode (x option), whitespace and characters from # to the end of the line are ignored. This allows for more readable patterns.

RECURSIVE PATTERNS

PCRE2 supports recursive patterns using the syntax (?R) or (?0), which refers to the entire pattern. This is useful for matching nested structures like balanced parentheses or HTML tags.

CALLOUTS

Callouts are a mechanism for the regular expression engine to signal back to the calling program at specific points during the matching process. They are denoted by (?C). The calling program can then perform actions, such as updating statistics or aborting the match.

BACKTRACKING CONTROL

PCRE2 provides several ways to control backtracking:

  • Possessive quantifiers (e.g., *+)
  • Atomic groups (e.g., (?>...))
  • Subroutine calls (e.g., (?R))

These features can help to improve performance by preventing unnecessary backtracking.

EBCDIC ENVIRONMENTS

When PCRE2 is compiled for EBCDIC environments, certain character classes and escape sequences may have different meanings than in ASCII environments. Refer to the PCRE2 documentation for details.
