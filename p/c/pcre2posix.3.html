PCRE2POSIX(3) Manuel des fonctions de bibliothèque PCRE2POSIX(3)

NOM

PCRE2 - expressions régulières compatibles Perl (API révisée)

SYNTAXE

#include <pcre2posix.h>

int pcre2_regcomp(regex_t *preg, const char *pattern,
     int cflags);

int pcre2_regexec(const regex_t *preg, const char *string,
     size_t nmatch, regmatch_t pmatch[], int eflags);

size_t pcre2_regerror(int errcode, const regex_t *preg,
     char *errbuf, size_t errbuf_size);

void pcre2_regfree(regex_t *preg);

DESCRIPTION

Cet ensemble de fonctions fournit une API de style POSIX pour la bibliothèque PCRE2 d'expressions régulières 8 bits. Il n'existe pas d'enveloppes de style POSIX pour les bibliothèques 16 bits et 32 bits de PCRE2. Voir la documentation pcre2api pour une description de l'API native de PCRE2, qui contient de nombreuses fonctionnalités supplémentaires.

NOTE IMPORTANTE : Les fonctions décrites ici ne sont PAS thread-safe et ne doivent pas être utilisées dans des applications multithreadées. Elles sont également limitées au traitement de sujets ne dépassant pas 2 Go. Utilisez l'API native à la place.

Ces fonctions sont des fonctions d'enveloppement qui appellent en fin de compte l'API native de PCRE2. Leurs prototypes sont définis dans le fichier d'en-tête pcre2posix.h et elles ont toutes des noms uniques commençant par pcre2_. Cependant, l'en-tête pcre2posix.h contient également des définitions de macros qui convertissent les noms POSIX standard tels que regcomp() en pcre2_regcomp() etc. Cela signifie qu'un programme peut utiliser les noms POSIX habituels sans courir le risque de lier accidentellement avec des fonctions POSIX d'une autre bibliothèque.

Sur les systèmes de type Unix, la bibliothèque POSIX de PCRE2 s'appelle libpcre2-posix, elle peut donc être accédée en ajoutant -lpcre2-posix à la commande de liaison d'une application. Étant donné que les fonctions POSIX appellent les fonctions natives, il est également nécessaire d'ajouter -lpcre2-8.

Sur les systèmes Windows, si vous liez à une version DLL de la bibliothèque, il est recommandé de définir PCRE2POSIX_SHARED avant d'inclure l'en-tête pcre2posix.h, car cela permettra une invocation plus efficace des fonctions en ajoutant le décorateur __declspec(dllimport).

Bien qu'elles n'aient pas été définies comme des prototypes dans pcre2posix.h, les versions 10.33 à 10.36 de la bibliothèque contenaient des fonctions avec les noms POSIX regcomp() etc. Celles-ci transmettaient simplement leurs arguments aux fonctions PCRE2. Ces fonctions étaient fournies pour la compatibilité descendante avec les versions antérieures de PCRE2, qui n'avaient que des noms POSIX. Cependant, cela s'est avéré problématique dans les situations où un programme lie plusieurs bibliothèques, dont certaines utilisent l'interface POSIX de PCRE2 tandis que d'autres utilisent les fonctions POSIX réelles. Pour cette raison, les noms POSIX ont été supprimés depuis la version 10.37.

L'appel du fichier d'en-tête pcre2posix.h évite tout conflit avec d'autres bibliothèques POSIX. Il peut, bien sûr, être renommé ou aliasé en regex.h, qui est le nom « correct », en l'absence de conflit. Il fournit deux types de structures, regex_t pour les formes internes compilées, et regmatch_t pour retourner les sous-chaînes capturées. Il définit également certaines constantes dont les noms commencent par "REG_ "; celles-ci sont utilisées pour définir les options et identifier les codes d'erreur.

UTILISATION DES FONCTIONS POSIX

Notez que ces fonctions ne sont que des enveloppes de style POSIX pour l'API native de PCRE2. Elles ne fournissent pas le comportement des expressions régulières POSIX, et elles ne sont ni thread-safe ni même compatibles POSIX.

Les bits d'option POSIX qui peuvent raisonnablement être mappés aux options natives de PCRE2 ont été implémentés. De plus, l'option REG_EXTENDED est définie avec la valeur zéro. Cela n'a aucun effet, mais comme les programmes écrits pour l'interface POSIX l'utilisent souvent, cela facilite l'intégration de PCRE2 comme bibliothèque de remplacement. D'autres options POSIX ne sont même pas définies.

Il existe également certaines options qui ne sont pas définies par POSIX. Celles-ci ont été ajoutées à la demande d'utilisateurs souhaitant exploiter certaines fonctionnalités spécifiques à PCRE2 via l'interface d'appel POSIX ou ajouter des fonctionnalités BSD ou GNU.

Lorsque PCRE2 est appelé via ces fonctions, seul l'API est de style POSIX. La syntaxe et la sémantique des expressions régulières elles-mêmes sont toujours celles de Perl, sous réserve de la définition de diverses options PCRE2, comme décrit ci-dessous. « De style POSIX » signifie que l'API s'approche de la définition POSIX ; elle n'est pas entièrement compatible POSIX, et dans les domaines d'encodage multi-unités, elle est probablement encore moins compatible.

Les descriptions ci-dessous utilisent les noms réels des fonctions, mais, comme décrit ci-dessus, les noms POSIX standard (sans le préfixe pcre2_) peuvent également être utilisés.

COMPILATION D'UN MOTIF

La fonction pcre2_regcomp() est appelée pour compiler un motif en une forme interne. Par défaut, le motif est une chaîne C terminée par un zéro binaire (mais voir REG_PEND ci-dessous). L'argument preg est un pointeur vers une structure regex_t qui sert de base pour stocker les informations sur l'expression régulière compilée. Elle est également utilisée comme entrée lorsque REG_PEND est défini. La structure regex_t utilisée par pcre2_regcomp() est définie dans pcre2posix.h et n'est pas la même que la structure utilisée par d'autres bibliothèques fournissant une correspondance de style POSIX.

L'argument cflags est soit zéro, soit contient un ou plusieurs des bits définis par les macros suivantes :


REG_DOTALL

L'option PCRE2_DOTALL est définie lorsque l'expression régulière est passée pour compilation à la fonction native. Notez que REG_DOTALL ne fait pas partie de la norme POSIX.


REG_ICASE

L'option PCRE2_CASELESS est définie lorsque l'expression régulière est passée pour compilation à la fonction native.


REG_NEWLINE

L'option PCRE2_MULTILINE est définie lorsque l'expression régulière est passée pour compilation à la fonction native. Notez que cela ne mime pas le comportement POSIX défini pour REG_NEWLINE (voir la section suivante).


REG_NOSPEC

L'option PCRE2_LITERAL est définie lorsque l'expression régulière est passée pour compilation à la fonction native. Cela désactive tous les méta-caractères dans le motif, le traitant comme une chaîne littérale. Les seules autres options autorisées avec REG_NOSPEC sont REG_ICASE, REG_NOSUB, REG_PEND et REG_UTF. Notez que REG_NOSPEC ne fait pas partie de la norme POSIX.


REG_NOSUB

Lorsqu'un motif compilé avec ce drapeau est passé à pcre2_regexec() pour la correspondance, les arguments nmatch et pmatch sont ignorés, et aucune chaîne capturée n'est retournée. Les versions de la bibliothèque PCRE2 antérieures à 10.22 utilisaient l'option de compilation PCRE2_NO_AUTO_CAPTURE, mais ce n'est plus le cas car cela désactive l'utilisation des références arrière.


REG_PEND

Si cette option est définie, le champ reg_endp de la structure preg (qui est de type const char *) doit être défini pour pointer vers le caractère suivant la fin du motif avant d'appeler pcre2_regcomp(). Le motif lui-même peut maintenant contenir des zéros binaires, qui sont traités comme des caractères de données. Sans REG_PEND, un zéro binaire termine le motif et le champ re_endp est ignoré. Il s'agit d'une extension GNU à la norme POSIX et doit être utilisée avec prudence dans les logiciels destinés à être portables sur d'autres systèmes.


REG_UCP

L'option PCRE2_UCP est définie lorsque l'expression régulière est passée pour compilation à la fonction native. Cela amène PCRE2 à utiliser les propriétés Unicode lors de la correspondance de \d, \w, etc., au lieu de reconnaître uniquement les valeurs ASCII. Notez que REG_UCP ne fait pas partie de la norme POSIX.


REG_UNGREEDY

L'option PCRE2_UNGREEDY est définie lorsque l'expression régulière est passée pour compilation à la fonction native. Notez que REG_UNGREEDY ne fait pas partie de la norme POSIX.


REG_UTF

L'option PCRE2_UTF est définie lorsque l'expression régulière est passée pour compilation à la fonction native. Cela amène le motif lui-même et toutes les chaînes de données utilisées pour sa correspondance à être traitées comme des chaînes UTF-8. Notez que REG_UTF ne fait pas partie de la norme POSIX.

pcre2posix(3) — pcre2 — Arch Linux

NOM

pcre2posix - Interface de style POSIX pour PCRE2

SYNTAXE

#include <pcre2.h>
#include <pcre2posix.h>

int regcomp(const char *regex, regex_t *creg, int cflags);
int regexec(const regex_t *creg, const char *string, size_t nmatch,
    regmatch_t pmatch[], int eflags);
size_t regerror(int errcode, const regex_t *creg, char *errbuf, size_t errbuf_size);
void regfree(regex_t *creg);

DESCRIPTION

PCRE2 peut être appelé via une interface de style POSIX, qui est une alternative à l'API de bas niveau fournie dans pcre2.h. Cette interface est fournie pour la compatibilité avec d'autres bibliothèques d'expressions régulières. Notez que la bibliothèque PCRE2 originale a été écrite pour soutenir Perl, et non POSIX.

Les fonctions sont :

  • regcomp : Compile une expression régulière.
  • regexec : Exécute une expression régulière compilée contre une chaîne.
  • regerror : Obtient une description textuelle d'un code d'erreur.
  • regfree : Libère la mémoire utilisée par une expression régulière compilée.

La structure regex_t est remplie par regcomp et utilisée par les autres fonctions. La structure regmatch_t contient les décalages de début et de fin d'une partie correspondante de la chaîne.

UTILISATION DES FONCTIONS POSIX

Lorsque vous utilisez cette interface, vous compilez généralement une expression régulière et l'exécutez immédiatement une ou plusieurs fois. Par exemple :

#include <stdio.h>
#include <regex.h>

int main() {
    regex_t preg;
    regmatch_t pmatch[1];
    const char *pattern = "([0-9]+)-([0-9]+)";
    const char *text = "Order number: 123-456";
    int ret;

    ret = regcomp(pattern, &preg, REG_EXTENDED);
    if (ret != 0) {
        char errbuf[256];
        regerror(ret, &preg, errbuf, sizeof(errbuf));
        fprintf(stderr, "Erreur de compilation: %s\n", errbuf);
        return 1;
    }

    ret = regexec(&preg, text, 1, pmatch, 0);
    if (ret == 0) {
        printf("Correspondance trouvée\n");
    } else if (ret == REG_NOMATCH) {
        printf("Aucune correspondance\n");
    } else {
        char errbuf[256];
        regerror(ret, &preg, errbuf, sizeof(errbuf));
        fprintf(stderr, "Erreur d'exécution: %s\n", errbuf);
        regfree(&preg);
        return 1;
    }

    regfree(&preg);
    return 0;
}

Les compilations et exécutions d'expressions régulières peuvent être coûteuses. Si vous avez besoin d'exécuter la même expression régulière à plusieurs reprises, il est préférable de la compiler une fois avec regcomp, puis d'utiliser regexec plusieurs fois avant de libérer la mémoire avec regfree.

COMPILATION D'UN MODÈLE

La fonction regcomp : compile le modèle d'expression régulière donné par regex dans la structure creg. Le modèle est traité à la lumière des indicateurs dans cflags. Les options peuvent être combinées à l'aide de l'opérateur OU binaire.

Les options de compilation sont :

  • REG_BASIC : Interprète l'expression comme une expression régulière de base POSIX.
  • REG_EXTENDED : Interprète l'expression comme une expression régulière étendue POSIX. C'est l'option par défaut.
  • REG_ICASE : Ignore la casse.
  • REG_NEWLINE : Fait correspondre le caractère de saut de ligne (\n) aux caractères de saut de ligne dans la chaîne de sujet. Sans cela, un saut de ligne dans le sujet ne correspond pas à un saut de ligne dans le modèle, sauf s'il est explicitement spécifié.
  • REG_NOSUB : Ne retourne pas les informations sur les correspondances. L'argument pmatch de regexec sera ignoré.
  • REG_UNG=[]; : Sauf indication contraire, le point (.) ne correspond à aucun caractère de saut de ligne.

La méthode de traitement des sauts de ligne par le point (.), le caractère de début de ligne (^) et le caractère de fin de ligne ($) est conforme à la façon dont Perl gère les sauts de ligne, et non à la façon dont le fait POSIX. Il faut noter que la définition de REG_NEWLINE a seulement *quelques-uns* des effets spécifiés pour REG_NEWLINE dans POSIX. Cela n'affecte pas la façon dont les sauts de ligne sont mis en correspondance par le métacaractère point (.) (ils ne le sont pas) ou par une classe négative telle que [^a] (ils le sont).

Le résultat de regcomp est zéro en cas de succès, et non-zéro sinon. La structure preg est remplie en cas de succès, et un autre membre de la structure (ainsi que re_endp) est public : re_nsub contient le nombre de sous-modèles capturés dans l'expression régulière. Divers codes d'erreur sont définis dans le fichier d'en-tête.

NOTE : Si le résultat de regcomp n'est pas nul, vous ne devez pas tenter d'utiliser le contenu de la structure preg. Si, par exemple, vous la passez à regexec, le résultat est indéfini et votre programme risque de planter.

CORRESPONDANCE DES CARACTÈRES DE SAUT DE LIGNE

Ce domaine n'est pas simple, car POSIX et Perl ont des vues différentes sur les choses. Il n'est pas possible d'obtenir que PCRE2 obéisse aux sémantiques POSIX, mais PCRE2 n'a jamais été conçu pour être un moteur POSIX. Le tableau suivant liste les différentes possibilités de mise en correspondance des sauts de ligne dans Perl et PCRE2 :


Défaut Modification avec


. correspond au saut de ligne non PCRE2_DOTALL
le saut de ligne correspond à [^a] oui non modifiable
$ correspond à \n en fin oui PCRE2_DOLLAR_ENDONLY
$ correspond à \n au milieu non PCRE2_MULTILINE
^ correspond à \n au milieu non PCRE2_MULTILINE

Ceci est le tableau équivalent pour un moteur de correspondance de modèles compatible POSIX :


Défaut Modification avec


. correspond au saut de ligne oui REG_NEWLINE
le saut de ligne correspond à [^a] oui REG_NEWLINE
$ correspond à \n en fin non REG_NEWLINE
$ correspond à \n au milieu non REG_NEWLINE
^ correspond à \n au milieu non REG_NEWLINE

Ce comportement n'est pas ce qui se passe lorsque PCRE2 est appelé via son API POSIX. Par défaut, le comportement de PCRE2 est le même que celui de Perl, sauf qu'il n'y a pas d'équivalent à PCRE2_DOLLAR_ENDONLY dans Perl. Dans PCRE2 et Perl, il n'y a aucun moyen d'empêcher le saut de ligne de correspondre à [^a].

Le traitement par défaut des sauts de ligne POSIX peut être obtenu en définissant PCRE2_DOTALL et PCRE2_DOLLAR_ENDONLY lors de l'appel direct à regcomp, mais il n'y a aucun moyen de faire en sorte que PCRE2 se comporte exactement comme pour l'action REG_NEWLINE. Lors de l'utilisation de l'API POSIX, passer REG_NEWLINE à la fonction regcomp de PCRE2 fait que PCRE2_MULTILINE est passé à regcomp, et REG_DOTALL passe PCRE2_DOTALL. Il n'y a aucun moyen de passer PCRE2_DOLLAR_ENDONLY.

CORRESPONDANCE D'UN MODÈLE

La fonction regexec est appelée pour faire correspondre un modèle compilé preg à une chaîne donnée string, qui est par défaut terminée par un octet nul (mais voir REG_STARTEND ci-dessous), sous réserve des options dans eflags. Celles-ci peuvent être :


REG_NOTBOL

L'option PCRE2_NOTBOL est définie lors de l'appel à la fonction de correspondance PCRE2 sous-jacente.


REG_NOTEMPTY

L'option PCRE2_NOTEMPTY est définie lors de l'appel à la fonction de correspondance PCRE2 sous-jacente. Notez que REG_NOTEMPTY ne fait pas partie de la norme POSIX. Cependant, la définition de cette option peut donner un comportement plus proche de POSIX dans certaines situations.


REG_NOTEOL

L'option PCRE2_NOTEOL est définie lors de l'appel à la fonction de correspondance PCRE2 sous-jacente.


REG_STARTEND

Lorsque cette option est définie, la chaîne sujet commence à string + pmatch[0].rm_so et se termine à string + pmatch[0].rm_eo, qui doit pointer vers le premier caractère après la fin de la chaîne. Il peut y avoir des zéros binaires dans la chaîne sujet, et en fait, utiliser REG_STARTEND est le seul moyen de passer une chaîne sujet contenant un zéro binaire.

Quelle que soit la valeur de pmatch[0].rm_so, les décalages de la chaîne correspondante et de toute sous-chaîne capturée sont toujours donnés par rapport au début de string lui-même. (Avant la version 10.30 de PCRE2, ceux-ci étaient donnés par rapport à string + pmatch[0].rm_so, mais cela diffère des autres implémentations.)

Ceci est une extension BSD, compatible avec mais non spécifiée par la norme IEEE 1003.2 (POSIX.2), et doit être utilisée avec prudence dans les logiciels destinés à être portables sur d'autres systèmes. Notez qu'un rm_so non nul n'implique pas REG_NOTBOL ; REG_STARTEND affecte uniquement l'emplacement et la longueur de la chaîne, pas la façon dont elle est mise en correspondance. La définition de REG_STARTEND et le passage de pmatch en tant que NULL sont mutuellement exclusifs ; l'erreur REG_INVARG est retournée.

Si le modèle a été compilé avec le drapeau REG_NOSUB, aucune donnée sur les chaînes correspondantes n'est retournée. Les arguments nmatch et pmatch de regexec sont ignorés (sauf éventuellement en tant qu'entrée pour REG_STARTEND).

La valeur de nmatch peut être zéro, et la valeur pmatch peut être NULL (sauf si REG_STARTEND est défini) ; dans ces deux cas, aucune donnée sur les chaînes correspondantes n'est retournée.

Sinon, la portion de la chaîne qui a correspondu, ainsi que toutes les sous-chaînes capturées, sont retournées via l'argument pmatch, qui pointe vers un tableau de nmatch structures de type regmatch_t, contenant les membres rm_so et rm_eo. Ceux-ci contiennent le décalage en octets du premier caractère de chaque sous-chaîne et le décalage du premier caractère après la fin de chaque sous-chaîne, respectivement. Le 0ème élément du vecteur concerne la portion entière de string qui a correspondu ; les éléments suivants concernent les sous-modèles capturés de l'expression régulière. Les entrées non utilisées dans le tableau ont les deux membres de structure définis à -1.

La structure regmatch_t, ainsi que la typedef regoff_t qu'elle utilise, sont définies dans pcre2posix.h et ne sont pas garanties d'avoir la même taille ou disposition que d'autres types de noms similaires provenant d'autres bibliothèques qui fournissent une correspondance de style POSIX.

Une correspondance réussie retourne zéro ; divers codes d'erreur sont définis dans le fichier d'en-tête, dont REG_NOMATCH est le code d'échec "attendu".

MESSAGES D'ERREUR

La fonction regerror : mappe un code d'erreur non nul de regcomp ou regexec à un message imprimable. Si preg n'est pas NULL, l'erreur doit provenir de l'utilisation de cette structure. Un message terminé par un zéro binaire est placé dans errbuf. Si le tampon est trop court, seuls les errbuf_size - 1 premiers caractères du message d'erreur sont utilisés. Le résultat de la fonction est la taille du tampon nécessaire pour contenir le message entier, y compris le zéro de terminaison. Cette valeur est supérieure à errbuf_size si le message a été tronqué.

UTILISATION DE LA MÉMOIRE

La compilation d'une expression régulière alloue de la mémoire et l'associe à la structure preg. La fonction regfree libère toute cette mémoire, après quoi preg ne peut plus être utilisée comme expression compilée.
