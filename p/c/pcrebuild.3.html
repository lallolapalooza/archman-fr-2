NOM

PCRE - Expressions régulières compatibles Perl

COMPILATION DE PCRE

PCRE est distribué avec un script configure qui peut être utilisé pour compiler la bibliothèque dans des environnements de type Unix en utilisant les applications connues sous le nom d'Autotools. Sont également inclus dans la distribution des fichiers pour supporter la compilation en utilisant CMake à la place de configure. Le fichier texte README contient des informations générales sur la compilation avec Autotools (dont certaines sont répétées ci-dessous), et contient également quelques commentaires sur la compilation sur divers systèmes d'exploitation. Il y a beaucoup plus d'informations sur la compilation de PCRE sans utiliser Autotools (y compris des informations sur l'utilisation de CMake et la compilation « à la main ») dans le fichier texte appelé NON-AUTOTOOLS-BUILD. Vous devriez consulter ce fichier ainsi que le fichier README si vous compilez dans un environnement non-Unix.

OPTIONS DE COMPILATION DE PCRE

Le reste de ce document décrit les fonctionnalités optionnelles de PCRE qui peuvent être sélectionnées lors de la compilation de la bibliothèque. Il suppose l'utilisation du script configure, où les fonctionnalités optionnelles sont sélectionnées ou désélectionnées en fournissant des options à configure avant d'exécuter la commande make. Cependant, les mêmes options peuvent être sélectionnées dans les environnements de type Unix et non-Unix en utilisant l'interface graphique de cmake-gui si vous utilisez CMake à la place de configure pour compiler PCRE.

Si vous n'utilisez pas Autotools ou CMake, la sélection des options peut se faire en modifiant le fichier config.h, ou en passant des paramètres au compilateur, comme décrit dans NON-AUTOTOOLS-BUILD.

La liste complète des options pour configure (qui inclut celles standard comme la sélection du répertoire d'installation) peut être obtenue en exécutant


./configure --help

Les sections suivantes incluent des descriptions d'options dont les noms commencent par --enable ou --disable. Ces paramètres spécifient des changements par rapport aux valeurs par défaut de la commande configure. En raison de la façon dont configure fonctionne, --enable et --disable viennent toujours par paires, donc l'option complémentaire existe toujours également, mais comme elle spécifie la valeur par défaut, elle n'est pas décrite.

COMPILATION DES BIBLIOTHÈQUES 8-BITS, 16-BITS ET 32-BITS

Par défaut, une bibliothèque appelée libpcre est compilée, contenant des fonctions qui prennent des arguments de chaîne de caractères contenus dans des vecteurs d'octets, soit comme caractères d'un octet, soit interprétés comme des chaînes UTF-8. Vous pouvez également compiler une bibliothèque séparée, appelée libpcre16, dans laquelle les chaînes sont contenues dans des vecteurs d'unités de données de 16 bits et interprétées soit comme des caractères d'une seule unité, soit comme des chaînes UTF-16, en ajoutant


--enable-pcre16

à la commande configure. Vous pouvez également compiler une autre bibliothèque séparée, appelée libpcre32, dans laquelle les chaînes sont contenues dans des vecteurs d'unités de données de 32 bits et interprétées soit comme des caractères d'une seule unité, soit comme des chaînes UTF-32, en ajoutant


--enable-pcre32

à la commande configure. Si vous ne voulez pas la bibliothèque 8 bits, ajoutez


--disable-pcre8

également. Au moins une des trois bibliothèques doit être compilée. Notez que les wrappers C++ et POSIX sont uniquement pour la bibliothèque 8 bits, et que pcregrep est un programme 8 bits. Aucun de ceux-ci n'est compilé si vous ne sélectionnez que les bibliothèques 16 bits ou 32 bits.

COMPILATION DES BIBLIOTHÈQUES PARTAGÉES ET STATIQUES

Le processus de compilation PCRE d'Autotools utilise libtool pour compiler à la fois les bibliothèques partagées et statiques par défaut. Vous pouvez en supprimer une en ajoutant l'une des options suivantes


--disable-shared
--disable-static

à la commande configure, selon les besoins.

SUPPORT C++

Par défaut, si la bibliothèque 8 bits est en cours de compilation, le script configure recherchera un compilateur C++ et des fichiers d'en-tête C++. S'il les trouve, il compile automatiquement la bibliothèque wrapper C++ (qui ne supporte que les chaînes 8 bits). Vous pouvez désactiver cela en ajoutant


--disable-cpp

à la commande configure.

SUPPORT UTF-8, UTF-16 ET UTF-32

Pour compiler PCRE avec le support des chaînes de caractères Unicode UTF, ajoutez


--enable-utf

à la commande configure. Ce paramètre s'applique aux trois bibliothèques, ajoutant le support UTF-8 à la bibliothèque 8 bits, le support UTF-16 à la bibliothèque 16 bits, et le support UTF-32 à la bibliothèque 32 bits. Il n'y a pas d'options séparées pour activer UTF-8, UTF-16 et UTF-32 indépendamment car cela permettrait des paramètres absurdes tels que demander le support UTF-16 tout en compilant uniquement la bibliothèque 8 bits. Il n'est pas possible de compiler une bibliothèque avec le support UTF et une autre sans dans la même configuration. (Pour des raisons de compatibilité ascendante, --enable-utf8 est un synonyme de --enable-utf.)

En soi, ce paramètre ne fait pas que PCRE traite les chaînes comme UTF-8, UTF-16 ou UTF-32. En plus de compiler PCRE avec cette option, vous devez également définir l'option PCRE_UTF8, PCRE_UTF16 ou PCRE_UTF32 (selon le cas) lorsque vous appelez l'une des fonctions de compilation de motifs.

Si vous définissez --enable-utf lors de la compilation dans un environnement EBCDIC, PCRE s'attend à ce que son entrée soit soit en ASCII, soit en UTF-8 (selon l'option d'exécution). Il n'est pas possible de supporter les codes EBCDIC et UTF-8 dans la même version de la bibliothèque. Par conséquent, --enable-utf et --enable-ebcdic sont mutuellement exclusifs.

SUPPORT DES PROPRIÉTÉS DES CARACTÈRES UNICODE

Le support UTF permet aux bibliothèques de traiter des points de code de caractères jusqu'à 0x10ffff dans les chaînes qu'elles manipulent. En soi, cependant, il ne fournit aucune facilité pour accéder aux propriétés de tels caractères. Si vous voulez pouvoir utiliser les échappements de motif \P, \p, et \X, qui font référence aux propriétés des caractères Unicode, vous devez ajouter


--enable-unicode-properties

à la commande configure. Cela implique le support UTF, même si vous ne l'avez pas explicitement demandé.

L'inclusion du support des propriétés Unicode ajoute environ 30 Ko de tables à la bibliothèque PCRE. Seules les propriétés de catégorie générale telles que Lu et Nd sont supportées. Les détails sont donnés dans la documentation de pcrepattern.

SUPPORT DU COMPILATEUR JUSTE-À-TEMPS

Le support du compilateur juste-à-temps (JIT) est inclus dans la compilation en spécifiant


--enable-jit

Ce support n'est disponible que pour certaines architectures matérielles. Si cette option est définie pour une architecture non supportée, une erreur de compilation se produit. Voir la documentation de pcrejit pour une discussion de l'utilisation du JIT. Lorsque le support JIT est activé, pcregrep l'utilise automatiquement, sauf si vous ajoutez


--disable-pcregrep-jit

à la commande « configure ».

VALEUR DU CODE DE NOUVELLE LIGNE

Par défaut, PCRE interprète le caractère de saut de ligne (LF) comme indiquant la fin d'une ligne. C'est le caractère de nouvelle ligne normal sur les systèmes de type Unix. Vous pouvez compiler PCRE pour utiliser le retour chariot (CR) à la place, en ajoutant


--enable-newline-is-cr

à la commande configure. Il existe également une option --enable-newline-is-lf, qui spécifie explicitement le saut de ligne comme caractère de nouvelle ligne.

Alternativement, vous pouvez spécifier que les fins de ligne sont indiquées par la séquence de deux caractères CRLF. Si vous souhaitez cela, ajoutez


--enable-newline-is-crlf

à la commande configure. Il existe une quatrième option, spécifiée par


--enable-newline-is-anycrlf

qui fait que PCRE reconnaît l'une des trois séquences CR, LF, ou CRLF comme indiquant une fin de ligne. Enfin, une cinquième option, spécifiée par


--enable-newline-is-any

fait que PCRE reconnaît tout U

SÉQUENCE DE FIN DE LIGNE UNICODE

Le caractère spécial \R est une séquence d'échappement PCRE qui correspond à n'importe quelle séquence de fin de ligne Unicode. La convention de fin de ligne utilisée est celle qui est sélectionnée lorsque PCRE est compilé, ou celle qui est sélectionnée lors de l'appel des fonctions de la bibliothèque, quel que soit le réglage de compilation. Les nouvelles lignes Unicode sont U+000D (CR), U+000A (LF), U+0085 (NEL), U+2028 (LS) et U+2029 (PS). Par défaut, PCRE suppose que les séquences CR et LF sont utilisées comme fins de ligne standard.

La séquence de fin de ligne par défaut peut être remplacée lors de la compilation de la bibliothèque en utilisant l'une des options suivantes pour la commande configure :

--enable-newline-is-cr
Seul CR est une fin de ligne.
--enable-newline-is-lf
Seul LF est une fin de ligne.
--enable-newline-is-crlf
Seule la séquence CRLF est une fin de ligne.
--enable-newline-is-anycr
CR, LF, et CRLF sont des fins de ligne.
--enable-newline-is-anycrnl
CR, LF, CRLF, NEL, LS et PS sont des fins de ligne.

L'option --enable-newline-is-anycrnl correspond au comportement par défaut pour les nouvelles lignes Unicode. Les options --enable-newline-is-cr, --enable-newline-is-lf et --enable-newline-is-crlf permettent de revenir à des comportements plus anciens pour les nouvelles lignes si nécessaire. L'option --enable-newline-is-anycr est un compromis entre les deux, ne reconnaissant que CR, LF et CRLF.

Quelle que soit la convention de fin de ligne sélectionnée lors de la compilation de PCRE, elle peut être remplacée lors de l'appel des fonctions de la bibliothèque. Au moment de la compilation, il est conventionnel d'utiliser la norme de votre système d'exploitation.

CE QUE \R CORRESPOND

Par défaut, la séquence \R dans un motif correspond à n'importe quelle séquence de fin de ligne Unicode, quelle que soit la séquence de fin de ligne sélectionnée. Si vous spécifiez


--enable-bsr-anycrlf

le défaut est modifié de sorte que \R ne corresponde qu'à CR, LF ou CRLF. Quelle que soit la valeur sélectionnée lors de la compilation de PCRE, elle peut être remplacée lors de l'appel des fonctions de la bibliothèque.

UTILISATION DE MALLOC POSIX

Lorsque la bibliothèque 8 bits est appelée via l'interface POSIX (voir la documentation pcreposix), un espace de travail supplémentaire est nécessaire pour contenir les pointeurs vers les sous-chaînes de capture, car PCRE nécessite trois entiers par sous-chaîne, tandis que l'interface POSIX n'en fournit que deux. Si le nombre de sous-chaînes attendues est faible, la fonction d'encapsulation utilise de l'espace sur la pile, car c'est plus rapide que d'utiliser malloc() pour chaque appel. Le seuil par défaut au-dessus duquel la pile n'est plus utilisée est de 10 ; il peut être modifié en ajoutant un paramètre tel que


--with-posix-malloc-threshold=20

à la commande configure.

GESTION DES MOTIFS TRÈS VOLUMINEUX

Dans un motif compilé, des valeurs d'offset sont utilisées pour pointer d'une partie à une autre (par exemple, d'une parenthèse ouvrante à un métacaractère d'alternance). Par défaut, dans les bibliothèques 8 bits et 16 bits, des valeurs de deux octets sont utilisées pour ces offsets, ce qui limite la taille maximale d'un motif compilé à environ 64 Ko. C'est suffisant pour la plupart des motifs, sauf les plus gigantesques. Néanmoins, certaines personnes souhaitent traiter des motifs véritablement énormes, il est donc possible de compiler PCRE pour utiliser des offsets de trois ou quatre octets en ajoutant un paramètre tel que


--with-link-size=3

à la commande configure. La valeur donnée doit être 2, 3 ou 4. Pour la bibliothèque 16 bits, une valeur de 3 est arrondie à 4. Dans ces bibliothèques, l'utilisation d'offsets plus longs ralentit l'opération de PCRE car il doit charger des données supplémentaires lors de leur manipulation. Pour la bibliothèque 32 bits, la valeur est toujours 4 et ne peut pas être remplacée ; la valeur de --with-link-size est ignorée.

ÉVITER UNE UTILISATION EXCESSIVE DE LA PILE

Lors de la correspondance avec la fonction pcre_exec(), PCRE implémente le retour arrière en effectuant des appels récursifs à une fonction interne appelée match(). Dans les environnements où la taille de la pile est limitée, cela peut sérieusement limiter le fonctionnement de PCRE. (L'environnement Unix ne souffre généralement pas de ce problème, mais il peut parfois être nécessaire d'augmenter la taille maximale de la pile. Une discussion se trouve dans la documentation pcrestack.) Une approche alternative à la récursion qui utilise la mémoire du tas pour se souvenir des données, au lieu d'utiliser des appels de fonction récursifs, a été implémentée pour contourner le problème de la taille limitée de la pile. Si vous souhaitez compiler une version de PCRE qui fonctionne de cette manière, ajoutez


--disable-stack-for-recursion

à la commande configure. Avec cette configuration, PCRE utilisera les variables pcre_stack_malloc et pcre_stack_free pour appeler les fonctions de gestion de la mémoire. Par défaut, celles-ci pointent vers malloc() et free(), mais vous pouvez remplacer les pointeurs pour que vos propres fonctions soient utilisées à la place.

Des fonctions distinctes sont fournies plutôt que d'utiliser pcre_malloc et pcre_free car l'utilisation est très prévisible : les tailles de blocs demandées sont toujours les mêmes, et les blocs sont toujours libérés dans l'ordre inverse. Un programme appelant pourrait être en mesure d'implémenter des fonctions optimisées qui donnent de meilleurs résultats que malloc() et free(). PCRE s'exécute sensiblement plus lentement lorsqu'il est compilé de cette manière. Cette option n'affecte que la fonction pcre_exec() ; elle n'est pas pertinente pour pcre_dfa_exec().

LIMITER L'UTILISATION DES RESSOURCES PCRE

En interne, PCRE a une fonction appelée match(), qu'il appelle de manière répétée (parfois récursivement) lors de la correspondance d'un motif avec la fonction pcre_exec(). En contrôlant le nombre maximum de fois que cette fonction peut être appelée pendant une seule opération de correspondance, une limite peut être placée sur les ressources utilisées par un seul appel à pcre_exec(). La limite peut être modifiée à l'exécution, comme décrit dans la documentation pcreapi. La valeur par défaut est de 10 millions, mais elle peut être modifiée en ajoutant un paramètre tel que


--with-match-limit=500000

à la commande configure. Ce paramètre n'a aucun effet sur la fonction de correspondance pcre_dfa_exec().

Dans certains environnements, il est souhaitable de limiter la profondeur des appels récursifs de match() plus strictement que le nombre total d'appels, afin de restreindre la quantité maximale de pile (ou de tas, si --disable-stack-for-recursion est spécifié) utilisée. Une seconde limite contrôle cela ; elle prend par défaut la valeur définie pour --with-match-limit, ce qui n'impose aucune contrainte supplémentaire. Cependant, vous pouvez définir une limite inférieure en ajoutant, par exemple,


--with-match-limit-recursion=10000

à la commande configure. Cette valeur peut également être remplacée à l'exécution.

CRÉATION DES TABLES DE CARACTÈRES AU MOMENT DE LA COMPILATION

PCRE utilise des tables fixes pour traiter les caractères dont les valeurs de code sont inférieures à 256. Par défaut, PCRE est compilé avec un ensemble de tables qui sont distribuées dans le fichier pcre_chartables.c.dist. Ces tables sont uniquement pour les codes ASCII. Si vous ajoutez


--enable-rebuild-chartables

à la commande configure, les tables distribuées ne sont plus utilisées. Au lieu de cela, un programme appelé dftables est compilé et exécuté. Celui-ci génère le code source d'un nouvel ensemble de tables, créé dans la locale par défaut de votre système d'exécution C. (Cette méthode de remplacement des tables ne fonctionne pas si vous effectuez une compilation croisée, car dftables est exécuté sur l'hôte local. Si vous avez besoin de créer des tables alternatives lors d'une compilation croisée, vous devrez le faire « à la main ».)

UTILISATION DU CODE EBCDIC

PCRE suppose par défaut qu'il s'exécutera dans un environnement où le code caractère est ASCII (ou Unicode, qui est un sur-ensemble d'ASCII). C'est le cas pour la plupart des systèmes d'exploitation informatiques. PCRE peut cependant être compilé pour s'exécuter dans un environnement EBCDIC en ajoutant


--enable-ebcdic

à la commande configure. Ce paramètre implique --enable-rebuild-chartables. Vous ne devriez l'utiliser que si vous savez que vous êtes dans un environnement EBCDIC (par exemple, un système d'exploitation de mainframe IBM). L'option --enable-ebcdic est incompatible avec --enable-utf.

Le caractère EBCDIC qui correspond à un LF ASCII est supposé avoir la valeur 0x15 par défaut. Cependant, dans certains environnements EBCDIC, 0x25 est utilisé. Dans un tel environnement, vous devriez utiliser


--enable-ebcdic-nl25

en plus de, ou à la place de, --enable-ebcdic. Le caractère EBCDIC pour CR a la même valeur qu'en ASCII, à savoir 0x0d. L'un ou l'autre des 0x15 et 0x25 qui n'est *pas* choisi comme LF est fait pour correspondre au caractère NEL Unicode (qui, en Unicode, est 0x85).

Les options qui sélectionnent le comportement des nouvelles lignes, comme --enable-newline-is-cr, et les options équivalentes d'exécution, font référence à ces valeurs de caractères dans un environnement EBCDIC.

OPTIONS DE PCREGREP POUR LE SUPPORT DES FICHIERS COMPRIMÉS

Par défaut, pcregrep lit tous les fichiers comme du texte brut. Vous pouvez le compiler de manière à ce qu'il reconnaisse les fichiers dont les noms se terminent par .gz ou .bz2, et les lise avec libz ou libbz2, respectivement, en ajoutant l'une ou les deux des options suivantes :


--enable-pcregrep-libz
--enable-pcregrep-libbz2

Ces options nécessitent naturellement que les bibliothèques pertinentes soient installées sur votre système. La configuration échouera si ce n'est pas le cas.

TAILLE DU TAMPON DE PCREGREP

pcregrep utilise un tampon interne pour contenir une « fenêtre » sur le fichier qu'il analyse, afin de pouvoir afficher les lignes « avant » et « après » lorsqu'il trouve une correspondance. La taille du tampon est contrôlée par un paramètre dont la valeur par défaut est de 20 Ko. Le tampon lui-même fait trois fois cette taille, mais en raison de la manière dont il est utilisé pour contenir les lignes « avant », la ligne la plus longue qui est garantie d'être traitable est la taille du paramètre. Vous pouvez modifier la valeur par défaut du paramètre en ajoutant, par exemple,


--with-pcregrep-bufsize=50K

à la commande configure. L'appelant de pcregrep peut cependant remplacer cette valeur en spécifiant une option d'exécution.

OPTION PCRETEST POUR LE SUPPORT DE LIBREADLINE

Si vous ajoutez


--enable-pcretest-libreadline

à la commande configure, pcretest est lié à la bibliothèque libreadline, et lorsque son entrée provient d'un terminal, il la lit en utilisant la fonction readline(). Cela fournit des fonctionnalités d'édition de ligne et d'historique. Notez que libreadline est sous licence GPL, donc si vous distribuez un binaire de pcretest lié de cette manière, il peut y avoir des problèmes de licence.

La définition de cette option provoque l'ajout de l'option -lreadline à la compilation de pcretest. Dans de nombreux environnements d'exploitation avec une libreadline installée sur le système, cela suffit. Cependant, dans certains environnements (par exemple, si une version non modifiée de readline est utilisée), une configuration supplémentaire peut être nécessaire. NAME

pcrebuild - Build and test PCRE library.

BUILDING PCRE

The PCRE library is supplied as source code, which must be built by the user. The standard procedure is:

  • Run the configure script (see README).
  • Run make.
  • Optionally, run make check to test the build.
  • Optionally, run make install to install the library and header files.

The configure script performs various checks on your system to determine the best way to build PCRE. It sets up the Makefile accordingly. You can influence the build process by setting environment variables or by passing options to configure.

PCRE BUILD-TIME OPTIONS

The configure script accepts the following options:

  • --prefix=dir
    • Install files in dir (default is /usr/local).
  • --enable-static
    • Build the static library (libpcre.a). This is the default.
  • --disable-static
    • Do not build the static library.
  • --enable-shared
    • Build the shared library (libpcre.so).
  • --disable-shared
    • Do not build the shared library. This is the default.
  • --enable-unicode-support
    • Enable support for Unicode properties and \P{} backreferences, and for UTF-8, UTF-16, and UTF-32 strings. This is the default.
  • --disable-unicode-support
    • Disable support for Unicode properties and \P{} backreferences, and for UTF-8, UTF-16, and UTF-32 strings.
  • --enable-utf8
    • Enable support for UTF-8 strings. This is now synonymous with --enable-unicode-support.
  • --disable-utf8
    • Disable support for UTF-8 strings.
  • --enable-pcre16
    • Enable support for UTF-16 strings.
  • --disable-pcre16
    • Disable support for UTF-16 strings.
  • --enable-pcre32
    • Enable support for UTF-32 strings.
  • --disable-pcre32
    • Disable support for UTF-32 strings.
  • --enable-rebuild-charts
    • Build character tables at build time instead of using precompiled tables. This is mostly useful for testing.
  • --enable-jit
    • Enable Just-In-Time compiler support. This is only available if the compiler supports it and the PCRE library is built with GCC or Clang.
  • --enable-cpp
    • Build the C++ wrapper classes.
  • --disable-cpp
    • Do not build the C++ wrapper classes. This is the default.
  • --enable-valgrind
    • Add valgrind annotations to the library. This is useful for debugging PCRE itself.
  • --enable-coverage
    • Enable code coverage reporting. This is only available if you have lcov installed and your compiler is GCC.

BUILDING 8-BIT, 16-BIT AND 32-BIT LIBRARIES

By default, PCRE is built as an 8-bit library. To build the 16-bit and/or 32-bit libraries, you need to use the --enable-pcre16 and/or --enable-pcre32 options when running configure. If you enable Unicode support (the default), you can also use --enable-utf8, which is synonymous with --enable-unicode-support.

For example, to build all three libraries with shared library support:


./configure --enable-shared --enable-pcre16 --enable-pcre32

This will create three libraries: libpcre.so (8-bit), libpcre16.so (16-bit), and libpcre32.so (32-bit).

BUILDING SHARED AND STATIC LIBRARIES

By default, only the static library is built. To build the shared library, use the --enable-shared option. To disable the static library, use --disable-static.

For example, to build only the shared library:


./configure --enable-shared --disable-static

C++ SUPPORT

To build the C++ wrapper classes, use the --enable-cpp option when running configure.


./configure --enable-cpp

This will build the C++ wrapper classes in addition to the C library.

UTF-8, UTF-16 AND UTF-32 SUPPORT

Support for UTF-8, UTF-16, and UTF-32 strings is enabled by default if you compile PCRE with GCC or Clang. To explicitly enable or disable it, use the --enable-unicode-support, --enable-utf8, --enable-pcre16, or --enable-pcre32 options. You can also use the corresponding --disable-* options.

UNICODE CHARACTER PROPERTY SUPPORT

Support for Unicode character properties (e.g. \p{L} for a letter) and the \P{} negation syntax is enabled by default when Unicode support is enabled. It can be explicitly disabled using --disable-unicode-properties. Note that disabling this option still allows UTF-8, UTF-16, and UTF-32 strings to be processed, but character properties cannot be used in patterns.

JUST-IN-TIME COMPILER SUPPORT

If you are using GCC or Clang, PCRE can be built with support for its Just-In-Time (JIT) compiler, which can significantly speed up regex matching. To enable this, use the --enable-jit option when running configure.


./configure --enable-jit

Note that the JIT compiler is only available on certain architectures and with certain compilers. If it cannot be built, PCRE will still compile and run, but without JIT support.

CODE VALUE OF NEWLINE

The code value for newline characters can be changed from the default (10, line feed) by setting the NEWLINE environment variable before running configure.


NEWLINE=13 ./configure

This sets the newline character to carriage return (13).

WHAT \R MATCHES

By default, the special sequence \R matches any Unicode newline sequence. This behaviour can be changed by setting the PCRE_NEWLINE environment variable before running configure.

  • PCRE_NEWLINE=LF (default): \R matches LF, CR, CRLF, and all Unicode line endings.
  • PCRE_NEWLINE=CRLF: \R matches CR, LF, or CRLF.
  • PCRE_NEWLINE=ANYCRLF: \R matches CR, LF, or CRLF.
  • PCRE_NEWLINE=ANY: \R matches LF, CR, CRLF, and all other Unicode line endings.

POSIX MALLOC USAGE

PCRE uses the standard malloc() function for memory allocation. If you want PCRE to use the POSIX-compliant calloc() and free() instead, you can set the environment variable PCRE_POSIX_MALLOC before running configure.


PCRE_POSIX_MALLOC=1 ./configure

HANDLING VERY LARGE PATTERNS

By default, PCRE limits the size of the compiled regex to 65536 bytes. If you need to compile very large patterns, you can increase this limit by setting the PCRE_PATTERN_SIZE_MAX environment variable before running configure.


PCRE_PATTERN_SIZE_MAX=1048576 ./configure

This sets the maximum pattern size to 1MB.

AVOIDING EXCESSIVE STACK USAGE

For very complex patterns, PCRE's internal matching algorithm can recursively call itself many times, potentially leading to stack overflow. This can be mitigated by setting the PCRE_RECURSION_DEPTH_MAX environment variable before running configure.


PCRE_RECURSION_DEPTH_MAX=1000 ./configure

This sets the maximum recursion depth to 1000.

LIMITING PCRE RESOURCE USAGE

You can limit the resources used by PCRE by setting the following environment variables before running configure:

  • PCRE_MATCH_LIMIT: Maximum number of times the matching function can be called for a single pattern.
  • PCRE_MATCH_LIMIT_RECURSION: Maximum recursion depth for matching.
  • PCRE_OPCODE_LIMIT: Maximum number of opcodes that can be executed for a single pattern.

For example:


PCRE_MATCH_LIMIT=10000 PCRE_OPCODE_LIMIT=100000 ./configure

CREATING CHARACTER TABLES AT BUILD TIME

PCRE uses precompiled character tables for efficiency. However, you can force it to build these tables at build time by using the --enable-rebuild-charts option with configure.


./configure --enable-rebuild-charts

This is mostly useful for testing purposes or if you are using a non-standard character set.

USING EBCDIC CODE

PCRE is normally built using ASCII character codes. If you are working on an EBCDIC system, you can build PCRE for EBCDIC by setting the environment variable EBCDIC before running configure.


EBCDIC=1 ./configure

PCREGREP OPTIONS FOR COMPRESSED FILE SUPPORT

The pcregrep utility supports compressed files (gzip, bzip2, xz) if the corresponding libraries (libz, libbz2, liblzma) are available on your system and linked during the build process. The configure script usually detects these libraries automatically. If not, you may need to add options such as


LIBS="-lz -lbz2 -llzma"

immediately before the configure command.

PCREGREP BUFFER SIZE

The default buffer size used by pcregrep for reading files is 20480 bytes. This can be changed by setting the PCREGREP_BUFSIZE environment variable before running configure.


PCREGREP_BUFSIZE=40960 ./configure

This sets the buffer size to 40KB.

PCRETEST OPTION FOR LIBREADLINE SUPPORT

The pcretest utility can use the readline library for command-line editing. If your system has readline installed, you may need to add support for it. You can do this by setting the environment variable LIBS to include the appropriate library, e.g.


LIBS="-lreadline"

immediately before the configure command. If your environment has not been set up so that an appropriate library is automatically included, you may need to add something like


LIBS="-ncurses"

immediately before the configure command.

DEBUGGING WITH VALGRIND SUPPORT

By adding the


--enable-valgrind

option to to the configure command, PCRE will use valgrind annotations to mark certain memory regions as unaddressable. This allows it to detect invalid memory accesses, and is mostly useful for debugging PCRE itself.

CODE COVERAGE REPORTING

If your C compiler is gcc, you can build a version of PCRE that can generate a code coverage report for its test suite. To enable this, you must install lcov version 1.6 or above. Then specify


--enable-coverage

to the configure command and build PCRE in the usual way.

Note that using ccache (a caching C compiler) is incompatible with code coverage reporting. If you have configured ccache to run automatically on your system, you must set the environment variable


CCACHE_DISABLE=1

before running make to build PCRE, so that ccache is not used.

When --enable-coverage is used, the following addition targets are added to the Makefile:


make coverage

This creates a fresh coverage report for the PCRE test suite. It is equivalent to running "make coverage-reset", "make coverage-baseline", "make check", and then "make coverage-report".


make coverage-reset

This zeroes the coverage counters, but does nothing else.


make coverage-baseline

This captures baseline coverage information.


make coverage-report

This creates the coverage report.


make coverage-clean-report

This removes the generated coverage report without cleaning the coverage data itself.


make coverage-clean-data

This removes the captured coverage data without removing the coverage files created at compile time (*.gcno).


make coverage-clean

This cleans all coverage data including the generated coverage report. For more information about code coverage, see the gcov and lcov documentation.
