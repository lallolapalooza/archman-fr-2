PCRE2TEST(1) Manuel des commandes générales PCRE2TEST(1)

NOM

pcre2test - un programme pour tester les expressions régulières compatibles Perl.

SYNTAXE

pcre2test [options] [fichier d'entrée [fichier de sortie]]

pcre2test est un programme de test pour les bibliothèques d'expressions régulières PCRE2, mais il peut également être utilisé pour expérimenter avec les expressions régulières. Ce document décrit les fonctionnalités du programme de test ; pour les détails sur les expressions régulières elles-mêmes, consultez la documentation de pcre2pattern. Pour les détails sur les appels de fonction de la bibliothèque PCRE2 et leurs options, consultez la documentation de pcre2api.

L'entrée de pcre2test est une séquence d'expressions régulières et de chaînes de sujets à faire correspondre. Il existe également des lignes de commande pour définir les valeurs par défaut et contrôler certaines actions spéciales. La sortie montre le résultat de chaque tentative de correspondance. Les modificateurs des lignes de commande externes ou internes, les motifs et les lignes de sujet spécifient les options de la fonction PCRE2, contrôlent la façon dont le sujet est traité et quelle sortie est produite.

Il existe de nombreux modificateurs obscurs, dont certains sont spécifiquement conçus pour être utilisés conjointement avec le script de test et les fichiers de données distribués avec PCRE2. Tous les modificateurs sont documentés ici, certains sans justification majeure, mais beaucoup d'entre eux sont peu susceptibles d'être utiles, sauf lors du test des bibliothèques.

BIBLIOTHÈQUES 8-BITS, 16-BITS ET 32-BITS DE PCRE2

Différentes versions de la bibliothèque PCRE2 peuvent être construites pour prendre en charge des chaînes de caractères encodées en unités de code 8 bits, 16 bits ou 32 bits. Une, deux ou les trois de ces bibliothèques peuvent être installées simultanément. Le programme pcre2test peut être utilisé pour tester toutes les bibliothèques. Cependant, son propre entrée et sortie sont toujours au format 8 bits. Lors du test des bibliothèques 16 bits ou 32 bits, les motifs et les chaînes de sujets sont convertis au format 16 bits ou 32 bits avant d'être passés aux fonctions de la bibliothèque. Les résultats sont reconvertis en unités de code 8 bits pour la sortie.

Dans le reste de ce document, les noms des fonctions et structures de bibliothèque sont donnés sous forme générique, par exemple, pcre2_compile(). Les noms réels utilisés dans les bibliothèques ont un suffixe _8, _16 ou _32, selon le cas.

ENC ODAGE D'ENTRÉE

L'entrée de pcre2test est traitée ligne par ligne, soit en appelant la fonction fgets() de la bibliothèque C, soit via la bibliothèque libreadline ou libedit. Dans certains environnements Windows, le caractère 26 (hex 1A) provoque une fin de fichier immédiate, et aucune donnée supplémentaire n'est lue, donc ce caractère doit être évité sauf si vous souhaitez réellement cette action.

L'entrée est traitée à l'aide des fonctions de chaîne de caractères C, elle ne doit donc pas contenir de zéros binaires, même si dans les environnements de type Unix, fgets() traite tous les octets autres que le saut de ligne comme des caractères de données. Une erreur est générée si un zéro binaire est rencontré. Par défaut, les lignes de sujet sont traitées pour les échappements de barre oblique inverse, ce qui rend possible l'inclusion de toute valeur de données dans les chaînes passées à la bibliothèque pour la correspondance. Pour les motifs, il existe une installation pour spécifier certains ou tous les caractères d'entrée 8 bits sous forme de paires hexadécimales, ce qui rend possible l'inclusion de zéros binaires.

Entrée pour les bibliothèques 16-bits et 32-bits

Lors du test des bibliothèques 16 bits ou 32 bits, il est nécessaire de pouvoir générer des points de code de caractère supérieurs à 255 dans les chaînes passées à la bibliothèque. Pour les lignes de sujet et certains motifs, les échappements de barre oblique inverse peuvent être utilisés. De plus, lorsque le modificateur utf (voir « Définition des options de compilation » ci-dessous) est défini, le motif et les lignes de sujet suivantes sont interprétés comme des chaînes UTF-8 et traduits en UTF-16 ou UTF-32 selon le cas.

Pour les tests non-UTF de caractères larges, le modificateur utf8_input peut être utilisé. Il est mutuellement exclusif avec utf, et n'est autorisé qu'en mode 16 bits ou 32 bits. Il fait que le motif et les lignes de sujet suivantes soient traités comme UTF-8 selon la définition originale (RFC 2279), ce qui permet des valeurs de caractères jusqu'à 0x7fffffff. Chaque caractère est placé dans une unité de code 16 bits ou 32 bits (dans le cas 16 bits, les valeurs supérieures à 0xffff provoquent une erreur).

UTF-8 (dans sa définition originale) n'est pas capable d'encoder des valeurs supérieures à 0x7fffffff, mais de telles valeurs peuvent être gérées par la bibliothèque 32 bits. Lors du test de cette bibliothèque en mode non-UTF avec utf8_input défini, si un caractère est précédé par l'octet 0xff (qui est un octet invalide en UTF-8), 0x80000000 est ajouté à la valeur du caractère. Pour les chaînes de sujet, l'utilisation d'une séquence d'échappement est préférable.

OPTIONS DE LA LIGNE DE COMMANDE

-8
Si la bibliothèque 8 bits a été construite, cette option l'utilise (c'est le défaut). Si la bibliothèque 8 bits n'a pas été construite, cette option génère une erreur.
-16
Si la bibliothèque 16 bits a été construite, cette option l'utilise. Si la bibliothèque 8 bits n'a pas été construite, c'est le défaut. Si la bibliothèque 16 bits n'a pas été construite, cette option génère une erreur.
-32
Si la bibliothèque 32 bits a été construite, cette option l'utilise. Si aucune autre bibliothèque n'a été construite, c'est le défaut. Si la bibliothèque 32 bits n'a pas été construite, cette option génère une erreur.
-ac
Agit comme si chaque motif avait le modificateur auto_callout, c'est-à-dire insère des appels automatiques dans chaque motif qui est compilé.
-AC
Comme pour -ac, mais en plus, agit comme si chaque ligne de sujet avait le modificateur callout_extra, c'est-à-dire affiche des informations supplémentaires provenant des appels.
-b
Agit comme si chaque motif avait le modificateur fullbincode ; la forme binaire interne complète du motif est affichée après compilation.
-C
Affiche le numéro de version de la bibliothèque PCRE2, et toutes les informations disponibles sur les fonctionnalités optionnelles incluses, puis sort avec un code de sortie zéro. Toutes les autres options sont ignorées. Si -C et -LM sont présents, celui qui apparaît en premier est reconnu.

code de sortie toujours 0
bsr le réglage par défaut de ce que \R correspond :
ANYCRLF ou ANY
code de sortie toujours 0

backslash-C \C est supporté (non bloqué)

Agissez comme si chaque motif avait le modificateur info ; des informations sur le motif compilé sont fournies après la compilation.

Agissez comme si chaque ligne de motif avait le modificateur jitfast ; après une compilation réussie, chaque motif est passé au compilateur juste-à-temps (just-in-time), s'il est disponible, et chaque ligne de sujet est passée directement au moteur de correspondance JIT via son "chemin rapide" (fast path).
-jitverify
Agissez comme si chaque ligne de motif avait le modificateur jitverify ; après une compilation réussie, chaque motif est passé au compilateur juste-à-temps (just-in-time), s'il est disponible, et l'utilisation du JIT pour la correspondance est vérifiée.

Liste des modificateurs : affiche une liste des modificateurs de motif et de sujet disponibles sur la sortie standard, puis quitte avec un code de sortie zéro. Toutes les autres options sont ignorées. Si les options -C et toute option -Lx sont présentes, celle qui apparaît en premier est reconnue.
-LP
Liste des propriétés : affiche une liste des propriétés Unicode reconnues sur la sortie standard, puis quitte avec un code de sortie zéro. Toutes les autres options sont ignorées. Si les options -C et toute option -Lx sont présentes, celle qui apparaît en premier est reconnue.
-LS
Liste des scripts : affiche une liste des noms de scripts Unicode reconnus sur la sortie standard, puis quitte avec un code de sortie zéro. Toutes les autres options sont ignorées. Si les options -C et toute option -Lx sont présentes, celle qui apparaît en premier est reconnue.
-malloc
Exercez les échecs de malloc() en comptant d'abord le nombre d'appels à malloc lors de la compilation et de la correspondance des motifs, puis en réexécutant la compilation et la correspondance autant de fois, exerçant un échec de chaque appel malloc().
-pattern liste-de-modificateurs
Agissez comme si chaque ligne de motif contenait les modificateurs donnés.
-q
Ne pas afficher le numéro de version de pcre2test au début de l'exécution.
-S taille
Sur les systèmes de type Unix, définissez la taille de la pile d'exécution à taille mébibytes (unités de 1024*1024 octets).
-subject liste-de-modificateurs
Agissez comme si chaque ligne de sujet contenait les modificateurs donnés.
-t
Exécutez chaque compilation et chaque correspondance plusieurs fois avec un chronomètre, et affichez les temps résultants par compilation ou par correspondance. Lorsque le JIT est utilisé, des temps distincts sont donnés pour la compilation initiale et la compilation JIT. Vous pouvez contrôler le nombre d'itérations utilisées pour le chronométrage en faisant suivre -t d'un nombre (comme un élément distinct sur la ligne de commande). Par exemple, "-t 1000" itère 1000 fois. Par défaut, il itère 500 000 fois.
-tm
Ceci est similaire à -t sauf que cela chronomètre uniquement la phase de correspondance, et non la phase de compilation.
-T -TM
Ceux-ci se comportent comme -t et -tm, mais en plus, à la fin d'une exécution, les temps totaux pour toutes les compilations et correspondances sont affichés.
-unittest
Exécutez un ensemble fixe de tests supplémentaires de l'API PCRE2 qui ne sont pas pilotés par les fichiers d'entrée de test, puis quittez.
-version
Affichez le numéro de version de PCRE2, puis quittez.

DESCRIPTION

Si pcre2test reçoit deux noms de fichiers en arguments, il lit à partir du premier et écrit dans le second. Si le premier nom est "-", l'entrée est prise à partir de l'entrée standard. Si pcre2test ne reçoit qu'un seul argument, il lit à partir de ce fichier et écrit sur stdout. Sinon, il lit depuis stdin et écrit sur stdout.

Lorsque pcre2test est compilé, une option de configuration peut spécifier qu'il doit être lié à la bibliothèque libreadline ou libedit. Lorsque cela est fait, si l'entrée provient d'un terminal, elle est lue en utilisant la fonction readline(). Cela fournit des fonctionnalités d'édition de ligne et d'historique. La sortie de l'option -help indique si readline() sera utilisé ou non.

Le programme gère un nombre quelconque de tests, chacun consistant en un ensemble de lignes d'entrée. Chaque ensemble commence par une expression régulière, suivie d'un nombre quelconque de lignes de sujet à faire correspondre à ce motif. Entre les ensembles de données de test, des lignes de commande commençant par # peuvent apparaître. Ce format de fichier, avec certaines restrictions, peut également être traité par le script perltest.sh distribué avec PCRE2, afin de vérifier que le comportement de PCRE2 et de Perl est identique. Pour une spécification de perltest.sh, consultez les commentaires près de son début. Voir également la commande #perltest ci-dessous.

Lorsque l'entrée est un terminal, pcre2test demande chaque ligne d'entrée, en utilisant "re>" pour demander les motifs d'expressions régulières, et "data>" pour demander les lignes de sujet. Les lignes de commande commençant par # ne peuvent être saisies qu'en réponse à l'invite "re>".

Chaque ligne de sujet est comparée séparément et indépendamment. Si vous souhaitez effectuer des correspondances sur plusieurs lignes, vous devez utiliser la séquence d'échappement \n (ou \r ou \r\n, etc., selon le paramètre de saut de ligne) dans une seule ligne d'entrée pour encoder les séquences de saut de ligne. Il n'y a aucune limite à la longueur des lignes de sujet ; le tampon d'entrée est automatiquement étendu s'il est trop petit. Il existe des fonctionnalités de réplication qui permettent de générer des lignes de motif ou de sujet longues et répétitives sans avoir à les fournir explicitement.

Une ligne vide ou la fin du fichier signale la fin des lignes de sujet pour un test, auquel cas un nouveau motif ou une nouvelle ligne de commande est attendu s'il reste de l'entrée à lire.

LIGNES DE COMMANDE

Entre les ensembles de données de test, une ligne commençant par # est interprétée comme une ligne de commande. Si le premier caractère est suivi d'un espace blanc ou d'un point d'exclamation, la ligne est traitée comme un commentaire et ignorée. Sinon, les commandes suivantes sont reconnues :


#forbid_utf

Les motifs suivants auront automatiquement les options PCRE2_NEVER_UTF et PCRE2_NEVER_UCP définies, ce qui bloquera l'utilisation des options PCRE2_UTF et PCRE2_UCP ainsi que l'utilisation de (*UTF) et (*UCP) en début de motif. Cette commande déclenche également une erreur si un motif ultérieur contient des occurrences de \P, \p ou \X, qui sont toujours prises en charge lorsque PCRE2_UTF n'est pas défini, mais qui nécessitent que le support des propriétés Unicode soit inclus dans la bibliothèque.

Il s'agit d'un garde de déclenchement utilisé dans les fichiers de test pour garantir que les tests UTF ou de propriétés Unicode ne soient pas accidentellement ajoutés à des fichiers utilisés lorsque le support Unicode n'est pas inclus dans la bibliothèque. La définition de PCRE2_NEVER_UTF et PCRE2_NEVER_UCP par défaut peut également être obtenue à l'aide de #pattern ; la différence est que #forbid_utf ne peut pas être désactivé, et les options automatiques ne sont pas affichées dans les informations du motif, afin d'éviter d'encombrer la sortie des tests.


#load <nom_de_fichier>

Cette commande est utilisée pour charger un ensemble de motifs précompilés à partir d'un fichier, comme décrit dans la section intitulée "Sauvegarde et restauration des motifs compilés" ci-dessous.


#loadtables <nom_de_fichier>

Cette commande est utilisée pour charger un ensemble de tables de caractères binaires auxquelles on peut accéder par le qualificateur tables=3. De telles tables peuvent être créées par le programme pcre2_dftables avec l'option -b.


#newline_default [<liste-de-sauts-de-ligne>]

Lorsque PCRE2 est compilé, une convention de saut de ligne par défaut peut être spécifiée. Cela détermine quels caractères et/ou paires de caractères sont reconnus comme indiquant un saut de ligne dans un motif ou une chaîne de sujet. La valeur par défaut peut être remplacée lors de la compilation d'un motif. Les fichiers de test standard contiennent des tests de diverses conventions de saut de ligne, mais la majorité des tests s'attendent à ce qu'un seul saut de ligne (linefeed) soit reconnu comme saut de ligne par défaut. Sans action spéciale, les tests échoueraient lorsque PCRE2 est compilé avec CR ou CRLF comme saut de ligne par défaut.

La commande #newline_default spécifie une liste de types de sauts de ligne acceptables par défaut. Les types doivent être CR, LF, CRLF, ANYCRLF, ANY ou NUL (en majuscules ou minuscules), par exemple :


#newline_default LF Any anyCRLF

Si le saut de ligne par défaut est dans la liste, cette commande n'a aucun effet. Sinon, sauf lors du test de l'API POSIX, un modificateur newline spécifiant la première convention de saut de ligne de la liste (LF dans l'exemple ci-dessus) est ajouté à tout motif qui n'a pas déjà de modificateur newline. Si la liste des sauts de ligne est vide, la fonctionnalité est désactivée. Cette commande est préfixée

envoyé un certain nombre de fichiers d'entrée de test standard.

Lorsque l'API POSIX est testée, il n'y a aucun moyen de remplacer la convention de nouvelle ligne par défaut, bien qu'il soit possible de définir la convention de nouvelle ligne à partir du modèle. Un avertissement est émis si le modificateur posix ou posix_nosub est utilisé lorsque #newline_default définirait une valeur par défaut pour l'API non POSIX.


#pattern <liste-modificateurs>

Cette commande définit une liste de modificateurs par défaut qui s'applique à tous les modèles suivants. Les modificateurs d'un modèle peuvent modifier ces paramètres.


#perltest

Cette ligne est utilisée dans les fichiers de test qui peuvent également être traités par perltest.sh pour confirmer que Perl donne les mêmes résultats que PCRE2. Les tests ultérieurs sont vérifiés pour l'utilisation de fonctionnalités pcre2test incompatibles avec le script perltest.sh.

Les modèles doivent utiliser '/' comme délimiteur, et seuls certains modificateurs sont pris en charge. Les lignes de commentaire, les commandes #pattern et les commandes #subject qui définissent ou suppriment "mark" sont reconnues et traitées. Les commandes #perltest, #forbid_utf et #newline_default, qui sont nécessaires dans les fichiers pcre2test pertinents, sont ignorées silencieusement. Toutes les autres lignes de commande sont ignorées, mais affichent un message d'avertissement. La commande #perltest aide à détecter les tests qui sont accidentellement placés dans le mauvais fichier ou qui utilisent le mauvais délimiteur. Pour plus de détails sur le script perltest.sh, consultez les commentaires qu'il contient.


#pop [<modificateurs>]
#popcopy [<modificateurs>]

Ces commandes sont utilisées pour manipuler la pile des modèles compilés, comme décrit dans la section intitulée "Sauvegarde et restauration des modèles compilés" ci-dessous.


#save <nom-de-fichier>

Cette commande est utilisée pour sauvegarder un ensemble de modèles compilés dans un fichier, comme décrit dans la section intitulée "Sauvegarde et restauration des modèles compilés" ci-dessous.


#subject <liste-modificateurs>

Cette commande définit une liste de modificateurs par défaut qui s'applique à toutes les lignes de sujet suivantes. Les modificateurs d'une ligne de sujet peuvent modifier ces paramètres.


#if CONDITION
...
#endif

Si CONDITION est vraie, la commande est imprimée, et son contenu est traité normalement, y compris l'impression des lignes de commande dans la sortie. Si CONDITION est fausse, toutes les lignes entre "#if" et "#endif" sont sautées et non imprimées. CONDITION peut être l'une des conditions testées par l'option de ligne de commande "-C" et qui définit le code de sortie de pcre2test sur une valeur booléenne. CONDITION peut également être précédée de "!" .

SYNTAXE DES MODIFICATEURS

Les listes de modificateurs sont utilisées avec les lignes de modèle et de sujet. Les éléments d'une liste sont séparés par des virgules suivies d'espaces optionnels. Les espaces de fin dans une liste de modificateurs sont ignorés. Certains modificateurs peuvent être spécifiés pour les modèles et les lignes de sujet, tandis que d'autres ne sont valides que pour l'un ou l'autre. Chaque modificateur a un nom long, par exemple "anchored", et certains d'entre eux doivent être suivis d'un signe égal et d'une valeur, par exemple, "offset=12". Les valeurs ne peuvent pas contenir de caractères virgule, mais peuvent contenir des espaces. Les modificateurs qui ne prennent pas de valeurs peuvent être précédés d'un signe moins pour désactiver un paramètre précédent.

Quelques-uns des modificateurs les plus courants peuvent également être spécifiés sous forme de lettres uniques, par exemple "i" pour "caseless". Dans la documentation, en suivant la convention Perl, ils sont écrits avec une barre oblique ("le modificateur /i") pour plus de clarté. Les modificateurs abrégés doivent tous être concaténés dans le premier élément d'une liste de modificateurs. Si le premier élément n'est pas reconnu comme un nom de modificateur long, il est interprété comme une séquence de ces abréviations. Par exemple :


/abc/ig,newline=cr,jit=3

Ceci est une ligne de modèle dont la liste de modificateurs commence par deux modificateurs d'une seule lettre (/i et /g). Les modificateurs abrégés en minuscules sont les mêmes que ceux utilisés dans Perl.

SYNTAXE DES MODÈLES

Une ligne de modèle doit commencer par l'un des caractères suivants (symboles courants, à l'exclusion des métacaractères de modèle) :


/ ! " ' ` - = _ : ; , % & @ ~

Ceci est interprété comme le délimiteur du modèle. Une expression régulière peut être étendue sur plusieurs lignes d'entrée, auquel cas les caractères de nouvelle ligne sont inclus. Il est possible d'inclure le délimiteur en tant que littéral dans le modèle en l'échappant avec une barre oblique inverse, par exemple :


/abc\/def/

Si vous faites cela, l'échappement et le délimiteur font partie du modèle, mais comme les délimiteurs sont tous non alphanumériques, l'inclusion de la barre oblique inverse n'affecte pas l'interprétation du modèle. Notez, cependant, que cette astuce ne fonctionne pas dans les crochets littéraux \Q...\E car la barre oblique inverse sera elle-même interprétée comme un littéral. Si le délimiteur de fin est immédiatement suivi d'une barre oblique inverse, par exemple :


/abc\

une barre oblique inverse est ajoutée à la fin du modèle. Ceci est fait pour fournir un moyen de tester la condition d'erreur qui survient si un modèle se termine par une barre oblique inverse, car :


/abc\/

est interprété comme la première ligne d'un modèle qui commence par "abc/", provoquant la lecture de la ligne suivante par pcre2test comme une continuation de l'expression régulière.

Un modèle peut être suivi d'une liste de modificateurs (détails ci-dessous).

SYNTAXE DES LIGNES DE SUJET

Avant que chaque ligne de sujet ne soit passée à pcre2_match(), pcre2_dfa_match() ou pcre2_jit_match(), les espaces blancs de début et de fin sont supprimés, et la ligne est analysée pour les séquences d'échappement de barre oblique inverse, sauf si le modificateur subject_literal a été défini pour le modèle. Les éléments suivants fournissent un moyen d'encoder les caractères non imprimables de manière visible :


\a alarme (BEL, \x07)
\b retour arrière (\x08)
\e échappement (\x27)
\f saut de page (\x0c)
\n nouvelle ligne (\x0a)
\N{U+hh...} caractère unicode (nombre quelconque de chiffres hexadécimaux)
\r retour chariot (\x0d)
\t tabulation (\x09)
\v tabulation verticale (\x0b)
\ddd nombre octal (jusqu'à 3 chiffres octaux) ; représente un seul
point de code sauf s'il est supérieur à 255 avec la bibliothèque 8 bits
\o{dd...} nombre octal (nombre quelconque de chiffres octaux) représentant un
caractère en mode UTF ou un point de code
\xhh octet hexadécimal (jusqu'à 2 chiffres hexadécimaux)
\x{hh...} nombre hexadécimal (jusqu'à 8 chiffres hexadécimaux) représentant un
caractère en mode UTF ou un point de code

L'invocation de \N{U+hh...} ou \x{hh...} ne nécessite pas l'utilisation du modificateur utf sur le modèle. Elle est toujours reconnue. Il peut y avoir un nombre quelconque de chiffres hexadécimaux à l'intérieur des accolades ; les valeurs invalides provoquent des messages d'erreur, mais lors de l'utilisation de \N{U+hh...} avec certains caractères unicode invalides, ils seront acceptés avec un avertissement à la place.

Notez que même en mode UTF-8, \xhh (et selon la valeur, \ddd) décrit un octet plutôt qu'un caractère ; cela permet de construire des séquences UTF-8 invalides à des fins de test. D'autre part, \x{hh...} est interprété comme un caractère UTF-8 en mode UTF-8, ne générant plus d'un octet que si la valeur est supérieure à 127. Pour éviter l'ambiguïté, il est préférable d'utiliser \N{U+hh...} lors de la description de caractères. Lors du test de la bibliothèque 8 bits non en mode UTF-8, \x{hh} génère un octet pour les valeurs qui peuvent y tenir, et provoque une erreur pour les valeurs plus grandes.

Lors du test de la bibliothèque 16 bits, non en mode UTF-16, toutes les valeurs \x{hhhh} à 4 chiffres sont acceptées. Cela permet de construire des séquences UTF-16 invalides à des fins de test.

Lors du test de la bibliothèque 32 bits, non en mode UTF-32, toutes les valeurs \x{...} de 4 à 8 chiffres sont acceptées. Cela permet de construire des séquences UTF-32 invalides à des fins de test.

Il existe une séquence de barre oblique inverse spéciale qui spécifie la réplication d'un ou plusieurs caractères :


\[<caractères>]{<nombre>}

Cela permet de tester de longues chaînes sans avoir à les fournir dans le fichier. Par exemple :


\[abc]{4}

est converti en "abcabcabcabc". Cette fonctionnalité ne prend pas en charge l'imbrication. Pour inclure une parenthèse carrée fermante dans les caractères, codez-la en \x5D.

Une barre oblique inverse suivie d'un signe égal marque la fin de la chaîne de sujet et le début d'une liste de modificateurs. Par exemple :


abc\=notbol,notempty

Si la chaîne de sujet est vide et que \= est suivi d'espaces, la ligne est traitée comme une ligne de commentaire et n'est pas utilisée pour la correspondance. Par exemple :


\= Ceci est un commentaire.
abc\= Ceci est une liste de modificateurs invalide.

Une barre oblique inverse suivie de tout autre caractère non alphanumérique échappe simplement ce caractère. Une barre oblique inverse suivie de tout autre chose provoque une erreur. Cependant, si le tout dernier caractère de la ligne est une barre oblique inverse (et qu'il n'y a pas de liste de modificateurs), elle est ignorée. Cela permet de passer une ligne vide en données, car une ligne réellement vide termine l'entrée de données.

Si le modificateur subject_literal est défini pour un modèle, toutes les lignes de sujet suivantes sont traitées comme des littéraux, sans traitement spécial des barres obliques inverses. Aucune réplication n'est possible, et tous les modificateurs de sujet doivent être définis par défaut par une commande #subject.

Gestion des nouvelles lignes et de \R

Le modificateur bsr spécifie ce que \R dans un motif doit correspondre. S'il est défini sur "anycrlf", \R correspond uniquement à CR, LF ou CRLF. S'il est défini sur "unicode", \R correspond à toute séquence de nouvelle ligne Unicode. La valeur par défaut peut être spécifiée lors de la compilation de PCRE2 ; si elle ne l'est pas, la valeur par défaut est définie sur Unicode.

Le modificateur newline spécifie quels caractères doivent être interprétés comme des nouvelles lignes, à la fois dans le motif et dans les lignes sujettes. Le type doit être l'un de CR, LF, CRLF, ANYCRLF, ANY ou NUL (en majuscules ou minuscules).

Informations sur un motif

Le modificateur debug est un raccourci pour info,fullbincode, demandant toutes les informations disponibles.

Le modificateur bincode provoque la sortie d'une représentation du code compilé après la compilation. Ces informations ne contiennent pas les valeurs de longueur et de décalage, ce qui garantit que le même résultat est généré pour différentes tailles de liaison internes et différentes largeurs d'unités de code. En utilisant bincode, les mêmes tests de régression peuvent être utilisés dans différents environnements.

Le modificateur fullbincode, en revanche, inclut les valeurs de longueur et de décalage. Il est utilisé dans quelques tests spéciaux qui ne s'exécutent que pour des largeurs d'unités de code et des tailles de liaison spécifiques, et il est également utile pour des tests uniques.

Le modificateur info demande des informations sur le motif compilé (s'il est ancré, s'il a un caractère fixe, etc.). Les informations sont obtenues à partir de la fonction pcre2_pattern_info(). Voici quelques exemples typiques :


re> /(?i)(^a|^b)/m,info
Nombre de groupes de capture = 1
Options de compilation : multiline
Options générales : caseless multiline
Premier code unité au début ou suit une nouvelle ligne
Limite inférieure de la longueur du sujet = 1


re> /(?i)abc/info
Nombre de groupes de capture = 0
Options de compilation : <aucune>
Options générales : caseless
Premier code unité = 'a' (caseless)
Dernier code unité = 'c' (caseless)
Limite inférieure de la longueur du sujet = 3

"Options de compilation" sont celles spécifiées par les modificateurs ; "options générales" ont des options ajoutées qui sont prises ou déduites du motif. Si les deux ensembles d'options sont identiques, seule une ligne "options" est affichée ; s'il n'y a pas d'options, la ligne est omise. "Premier code unité" est où toute correspondance doit commencer ; s'il y en a plus d'un, ils sont listés comme "unités de code de départ". "Dernier code unité" est le dernier code unité littéral qui doit être présent dans toute correspondance. Ce n'est pas nécessairement le dernier caractère. Ces lignes sont omises si aucun code unité de départ ou de fin n'est enregistré. La ligne de longueur du sujet est omise lorsque no_start_optimize est définie car la longueur minimale n'est pas calculée lorsqu'elle ne peut jamais être utilisée.

Le modificateur framesize affiche la taille, en octets, de chaque trame de stockage utilisée par pcre2_match() pour gérer le backtracking. La taille dépend du nombre de parenthèses de capture dans le motif. Un vecteur de ces trames est utilisé au moment de la correspondance ; sa taille globale est affichée lorsque le modificateur de sujet heaframes_size est défini.

Le modificateur callout_info demande des informations sur tous les appels dans le motif. Une liste de ceux-ci est affichée à la fin de toute autre information demandée. Pour chaque appel, soit son numéro, soit sa chaîne est donné, suivi de l'élément qui le suit dans le motif.

Passage d'un contexte NULL

Normalement, pcre2test passe un bloc de contexte à pcre2_compile(). Si le modificateur null_context est défini, cependant, NULL est passé. Ceci est pour tester que pcre2_compile() se comporte correctement dans ce cas (il utilise les valeurs par défaut).

Passage d'un motif NULL

Le modificateur null_pattern est destiné à tester le comportement de pcre2_compile() lorsque l'argument motif est NULL. La valeur de longueur passée est la valeur par défaut PCRE2_ZERO_TERMINATED à moins que use_length ne soit définie. Toute longueur autre que zéro provoque une erreur.

Spécification des caractères du motif en hexadécimal

Le modificateur hex spécifie que les caractères du motif, à l'exception des sous-chaînes délimitées par des guillemets simples ou doubles, doivent être interprétés comme des paires de chiffres hexadécimaux. Cette fonctionnalité est fournie comme moyen de créer des motifs contenant des zéros binaires et d'autres caractères non imprimables. Les espaces sont autorisés entre les paires de chiffres. Par exemple, ce motif contient trois caractères :


/ab 32 59/hex

Des parties d'un tel motif sont prises littéralement si elles sont entre guillemets. Ce motif contient neuf caractères, dont seulement deux sont spécifiés en hexadécimal :


/ab "literal" 32/hex

Soit simple

le ou les guillemets doubles peuvent être utilisés. Il n'y a aucun moyen d'inclure le délimiteur dans une sous-chaîne. Les modificateurs hex et expand sont mutuellement exclusifs.

Spécifier la longueur du motif

Par défaut, les motifs sont transmis aux fonctions de compilation sous forme de chaînes terminées par un caractère nul, mais ils peuvent être transmis par leur longueur au lieu d'être terminés par un caractère nul. Le modificateur use_length provoque cela. L'utilisation d'une longueur se produit automatiquement (que use_length soit défini ou non) lorsque hex est défini, car les motifs spécifiés en hexadécimal peuvent contenir des zéros binaires.

Si hex ou use_length est utilisé avec l'API d'encapsulation POSIX (voir « Utilisation de l'API d'encapsulation POSIX » ci-dessous), l'extension REG_PEND est utilisée pour passer la longueur du motif.

Spécifier un maximum pour les assertions lookbehind variables

Les assertions lookbehind variables ne sont prises en charge que si, pour chacune d'elles, il existe une longueur maximale (en caractères) qu'elle peut correspondre. Il existe une limite à cela, dont la valeur par défaut peut être définie au moment de la compilation, avec une valeur par défaut ultime de 255. Le modificateur max_varlookbehind utilise la fonction pcre2_set_max_varlookbehind() pour modifier la limite. Les lookbehinds dont les branches correspondent chacune à une longueur fixe sont limités à 65535 caractères par branche.

Spécifier des caractères larges en modes 16 bits et 32 bits

En modes 16 bits et 32 bits, toutes les entrées sont automatiquement traitées comme UTF-8 et traduites en UTF-16 ou UTF-32 lorsque le modificateur utf est défini. Pour tester les bibliothèques 16 bits et 32 bits en mode non-UTF, le modificateur utf8_input peut être utilisé. Il est mutuellement exclusif avec utf. Les lignes d'entrée sont interprétées comme UTF-8 comme moyen de spécifier des caractères larges. Plus de détails sont donnés dans « Encodage d'entrée » ci-dessus.

Générer de longs motifs répétitifs

Certains tests utilisent de longs motifs très répétitifs. Au lieu de créer une ligne d'entrée très longue pour un tel motif, vous pouvez utiliser une fonction de répétition spéciale, similaire à celle décrite pour les lignes de sujet ci-dessus. Si le modificateur expand est présent sur un motif, les parties du motif qui ont la forme


\[<caractères>]{<nombre>}

sont développées avant que le motif ne soit transmis à pcre2_compile(). Par exemple, \[AB]{6000} est développé en "ABAB..." 6000 fois. Cette construction ne peut pas être imbriquée. Une séquence initiale "\[" n'est reconnue que si "]{" suivi de chiffres décimaux et "}" est trouvé plus loin dans le motif. Sinon, les caractères restent dans le motif inchangés. Les modificateurs expand et hex sont mutuellement exclusifs.

Si une partie d'un motif développé ressemble à une expansion, mais fait en réalité partie du motif réel, une expansion indésirable peut être évitée en donnant deux valeurs dans le quantificateur. Par exemple, \[AB]{6000,6000} n'est pas reconnu comme un élément d'expansion.

Si le modificateur info est défini sur un motif développé, le résultat du développement est inclus dans les informations qui sont produites.

Compilation JIT

La compilation juste-à-temps (JIT) est une optimisation lourde qui peut accélérer considérablement la correspondance des motifs. Voir la documentation pcre2jit pour les détails. La compilation JIT se produit, facultativement, après qu'un motif a été compilé avec succès dans une forme interne. Le compilateur JIT convertit cela en code machine optimisé. Il doit savoir si les options de temps de correspondance PCRE2_PARTIAL_HARD et PCRE2_PARTIAL_SOFT vont être utilisées, car un code différent est généré pour les différents cas. Voir le modificateur partial dans « Modificateurs de sujet » ci-dessous pour les détails sur la façon dont ces options sont spécifiées pour chaque tentative de correspondance.

La compilation JIT est demandée par le modificateur de motif jit, qui peut éventuellement être suivi d'un signe égal et d'un nombre dans la plage 0 à 7. Les trois bits qui composent le nombre spécifient quels des trois modes de fonctionnement JIT doivent être compilés :


1 compiler du code JIT pour la correspondance non partielle
2 compiler du code JIT pour la correspondance partielle douce
4 compiler du code JIT pour la correspondance partielle stricte

Les valeurs possibles pour le modificateur jit sont donc :


0 désactiver JIT
1 correspondance normale uniquement
2 correspondance partielle douce uniquement
3 correspondance normale et partielle douce
4 correspondance partielle stricte uniquement
6 correspondance partielle douce et stricte uniquement
7 les trois modes

Si aucun nombre n'est donné, 7 est supposé. L'expression « correspondance partielle » signifie un appel à pcre2_match() avec l'option PCRE2_PARTIAL_SOFT ou PCRE2_PARTIAL_HARD définie. Notez qu'un tel appel peut retourner une correspondance complète ; les options permettent la possibilité d'une correspondance partielle, mais ne l'exigent pas. Notez également que si vous demandez une compilation JIT uniquement pour la correspondance partielle (par exemple, jit=2) mais ne définissez pas le modificateur partial sur une ligne de sujet, cette correspondance n'utilisera pas de code JIT car aucun n'a été compilé pour la correspondance non partielle.

Si la compilation JIT réussit, le code JIT compilé sera automatiquement utilisé lorsqu'un type de correspondance approprié est exécuté, sauf lorsque des options d'exécution incompatibles sont spécifiées. Pour plus de détails, voir la documentation pcre2jit. Voir aussi le modificateur jitstack ci-dessous pour une manière de définir la taille de la pile JIT.

Si le modificateur jitfast est spécifié, la correspondance est effectuée en utilisant l'interface « chemin rapide » JIT, pcre2_jit_match(), qui ignore certaines vérifications de cohérence effectuées par pcre2_match(), et bien sûr ne fonctionne pas lorsque JIT n'est pas pris en charge. Si jitfast est spécifié sans jit, jit=7 est supposé.

Si le modificateur jitverify est spécifié, les informations sur le motif compilé indiquent si la compilation JIT a réussi ou échoué. Si jitverify est spécifié sans jit, jit=7 est supposé. Si la compilation JIT réussit lorsque jitverify est défini, le texte « (JIT) » est ajouté à la première ligne de sortie après une correspondance ou une non-correspondance lorsque du code compilé par JIT a effectivement été utilisé dans la correspondance.

Définir une locale

Le modificateur locale doit spécifier le nom d'une locale, par exemple :


/motif/locale=fr_FR

La locale donnée est définie, pcre2_maketables() est appelée pour construire un ensemble de tables de caractères pour la locale, et celles-ci sont ensuite transmises à pcre2_compile() lors de la compilation de l'expression régulière. Les mêmes tables sont utilisées lors de la correspondance des lignes de sujet suivantes. Le modificateur locale ne s'applique qu'au motif sur lequel il apparaît, mais peut être donné dans une commande #pattern si une valeur par défaut est nécessaire. La définition d'une locale et de tables de caractères alternatives sont mutuellement exclusives.

Afficher la mémoire du motif

Le modificateur memory provoque l'affichage de la taille en octets de la mémoire utilisée pour stocker le motif compilé. Cela n'inclut pas la taille du bloc pcre2_code ; ce sont juste les données compilées réelles. Si le motif est ensuite transmis au compilateur JIT, la taille du code compilé par JIT est également affichée. Voici un exemple :


re> /a(b)c/jit,memory
Memory allocation (code space): 21
Memory allocation (JIT code): 1910

Limiter les parenthèses imbriquées

Le modificateur parens_nest_limit définit une limite à la profondeur des parenthèses imbriquées dans un motif. Le dépassement de la limite entraîne une erreur de compilation. La valeur par défaut de la bibliothèque est définie lors de la compilation de PCRE2, mais pcre2test définit sa propre valeur par défaut de 220, qui est nécessaire pour exécuter la suite de tests standard.

Limiter la longueur du motif

Le modificateur max_pattern_length définit une limite, en unités de code, à la longueur du motif que pcre2_compile() acceptera. Le dépassement de la limite entraîne une erreur de compilation. La valeur par défaut est le plus grand nombre qu'une variable PCRE2_SIZE puisse contenir (essentiellement illimitée).

Limiter la taille d'un motif compilé

Le modificateur max_pattern_compiled_length définit une limite, en octets, à la quantité de mémoire utilisée par un motif compilé. Le dépassement de la limite entraîne une erreur de compilation. La valeur par défaut est le plus grand nombre qu'une variable PCRE2_SIZE puisse contenir (essentiellement illimitée).

Utiliser l'API d'encapsulation POSIX

Les modificateurs posix et posix_nosub font en sorte que pcre2test appelle PCRE2 via l'API d'encapsulation POSIX plutôt que son API native. Lorsque posix_nosub est utilisé, l'option POSIX REG_NOSUB est passée à regcomp(). L'encapsulation POSIX ne prend en charge que la bibliothèque 8 bits. Notez qu'elle n'implique pas les sémantiques de correspondance POSIX ; pour plus de détails, voir la documentation pcre2posix. Les modificateurs de motif suivants définissent des options pour la fonction regcomp() :


caseless REG_ICASE
multiline REG_NEWLINE
dotall REG_DOTALL )
ungreedy REG_UNGREEDY ) Ces options ne font pas partie
ucp REG_UCP ) du standard POSIX
utf REG_UTF8 )

Le modificateur regerror_buffsize spécifie une taille pour le tampon d'erreur qui est passé à regerror() en cas d'erreur de compilation. Par exemple :


/abc/posix,regerror_buffsize=20

Cela fournit un moyen de tester le comportement de regerror() lorsque le tampon est trop petit pour le message d'erreur. Si ce modificateur n'a pas été défini, un grand tampon est utilisé.

Les modificateurs de sujet aftertext et allaftertext fonctionnent comme décrit ci-dessous. Tous les autres modificateurs sont soit ignorés, avec un message d'avertissement, soit provoquent une erreur.

Le motif est passé à regcomp() comme une chaîne terminée par un caractère nul

ated chaîne par défaut, mais si les modificateurs use_length ou hex sont définis, l'extension REG_PEND est utilisée pour la passer par longueur.

Test de la fonctionnalité de garde de pile

Le modificateur stackguard est utilisé pour tester l'utilisation de pcre2_set_compile_recursion_guard(), une fonction fournie pour permettre la vérification de la disponibilité de la pile lors de la compilation (voir la documentation pcre2api pour plus de détails). Si le nombre spécifié par le modificateur est supérieur à zéro, pcre2_set_compile_recursion_guard() est appelé pour configurer une fonction de rappel de pcre2_compile() vers une fonction locale. L'argument qu'elle reçoit est la profondeur actuelle des parenthèses imbriquées ; si celle-ci est supérieure à la valeur donnée par le modificateur, une valeur non nulle est retournée, provoquant l'abandon de la compilation.

Utilisation de tables de caractères alternatives

La valeur spécifiée pour le modificateur tables doit être l'un des chiffres 0, 1, 2 ou 3. Elle entraîne le passage d'un ensemble spécifique de tables de caractères intégrées à pcre2_compile(). Ceci est utilisé dans les tests PCRE2 pour vérifier le comportement avec différentes tables de caractères. Le chiffre spécifie les tables comme suit :


0 ne pas passer de tables de caractères spéciales
1 les tables ASCII par défaut, telles que distribuées dans
pcre2_chartables.c.dist
2 un ensemble de tables définissant des caractères ISO 8859
3 un ensemble de tables chargées par la commande #loadtables

Dans la table 2, certains caractères dont les codes sont supérieurs à 128 sont identifiés comme lettres, chiffres, espaces, etc. La table 3 ne peut être utilisée qu'après qu'une commande #loadtables les ait chargés à partir d'un fichier binaire. La définition de tables de caractères alternatives et d'une locale sont mutuellement exclusives.

Lorsqu'un motif avec le modificateur push est compilé avec succès, il est placé sur une pile de motifs compilés, et pcre2test s'attend à ce que la ligne suivante contienne un nouveau motif (ou une commande) au lieu d'une ligne de sujet. Les fonctions expérimentales de conversion de motifs étrangers dans PCRE2 peuvent être testées en définissant le modificateur convert. Son argument est une liste d'options séparées par des deux-points, qui définissent l'option équivalente pour la fonction pcre2_pattern_convert() :

Tous les autres modificateurs sont soit ignorés, avec un message d'avertissement, soit provoquent une erreur.

Afficher plus de texte

Le modificateur aftertext demande qu'en plus de la sortie de la partie de la chaîne sujet qui correspond à l'ensemble du motif, pcre2test affiche également le reste de la chaîne sujet. Ceci est utile pour les tests où le sujet contient plusieurs copies de la même sous-chaîne. Le modificateur allaftertext demande la même action pour les sous-chaînes capturées ainsi que pour la sous-chaîne principale correspondante. Dans chaque cas, le reste est affiché sur la ligne suivante avec un caractère plus suivant le numéro de capture.

Le modificateur allusedtext demande que tout le texte qui a été consulté pendant une correspondance de motif réussie par l'interpréteur soit affiché, pour les correspondances complètes et partielles. Cette fonctionnalité n'est pas prise en charge pour la correspondance JIT, et si elle est demandée avec JIT, elle est ignorée (avec un message d'avertissement). La définition de ce modificateur affecte la sortie s'il y a une recherche arrière au début d'une correspondance, ou, pour une correspondance complète, une recherche avant à la fin, ou si \K est utilisé dans le motif. Les caractères qui précèdent ou suivent le début et la fin de la correspondance réelle sont indiqués dans la sortie par des caractères '<' ou '>' en dessous d'eux. Voici un exemple :


re> /(?<=pqr)abc(?=xyz)/
data> 123pqrabcxyz456\=allusedtext
0: pqrabcxyz
<<< >>>
data> 123pqrabcxy\=ph,allusedtext
Correspondance partielle : pqrabcxy
<<<

La première correspondance complète montre que la chaîne correspondante est "abc", les chaînes précédentes et suivantes "pqr" et "xyz" ayant été consultées pendant la correspondance (lors du traitement des assertions). La correspondance partielle ne peut indiquer que la chaîne précédente.

Le modificateur startchar demande que le caractère de départ de la correspondance soit indiqué, s'il est différent du début de la chaîne correspondante. La seule fois où cela se produit est lorsque \K a été traité dans le cadre de la correspondance. Dans ce cas, la sortie pour la chaîne correspondante est affichée à partir du caractère de départ au lieu du point de correspondance, avec des caractères accent circonflexe sous les caractères précédents. Par exemple :


re> /abc\Kxyz/
data> abcxyz\=startchar
0: abcxyz
^^^

Contrairement à allusedtext, le modificateur startchar peut être utilisé avec JIT. Cependant, ces deux modificateurs sont mutuellement exclusifs.

Afficher la valeur de tous les groupes de capture

Le modificateur allcaptures demande que les valeurs de tous les parenthèses potentiellement capturées soient affichées après une correspondance. Par défaut, seules celles jusqu'à la plus élevée réellement utilisée dans la correspondance sont affichées (correspondant au code de retour de pcre2_match()). Les groupes qui n'ont pas participé à la correspondance sont affichés comme "<unset>". Ce modificateur n'est pas pertinent pour la correspondance DFA (qui n'effectue aucune capture) et ne s'applique pas lorsque replace est spécifié ; il est ignoré, avec un message d'avertissement, s'il est présent.

Afficher tout l'ovector, pour tous les résultats

Le modificateur allvector demande que tout l'ovector soit affiché, quel que soit le résultat de la correspondance. Comparer avec allcaptures, qui n'affiche que jusqu'au nombre maximum de groupes de capture pour le motif, et seulement pour une correspondance complète réussie non-DFA. Ce modificateur, qui agit après tout résultat de correspondance, et également pour la correspondance DFA, fournit un moyen de vérifier qu'il n'y a pas de modifications inattendues aux champs de l'ovector. Avant chaque tentative de correspondance, l'ovector est rempli avec une valeur spéciale, et si celle-ci est trouvée dans les deux éléments d'une paire de capture, "<unchanged>" est affiché. Après une correspondance réussie, cela s'applique à tous les groupes après le groupe de capture maximal pour le motif. Dans les autres cas, cela s'applique à l'ensemble de l'ovector. Après une correspondance partielle, les deux premiers éléments sont les seuls qui doivent être définis. Après une correspondance DFA, la quantité d'ovector utilisée dépend du nombre de correspondances trouvées.

Tester les appels de motif

Une fonction d'appel est fournie lorsque pcre2test appelle les fonctions de correspondance de la bibliothèque, à moins que callout_none ne soit spécifié. Son comportement peut être contrôlé par divers modificateurs listés ci-dessus dont les noms commencent par callout_. Les détails sont donnés dans la section intitulée "Appels" ci-dessous. Les tests d'appels à partir de pcre2_substitute() sont décrits séparément dans "Tester la fonction de substitution" ci-dessous.

Trouver toutes les correspondances dans une chaîne

La recherche de toutes les correspondances possibles dans un sujet peut être demandée par le modificateur global ou altglobal. Après avoir trouvé une correspondance, la fonction de correspondance est appelée à nouveau pour rechercher le reste du sujet. La différence entre global et altglobal est que le premier utilise l'argument start_offset de pcre2_match() ou pcre2_dfa_match() pour commencer la recherche à un nouveau point dans la chaîne entière (ce que fait Perl), tandis que le second passe au-delà d'un sujet raccourci. Cela fait une différence dans le processus de correspondance si le motif commence par une assertion de recherche arrière (y compris \b ou \B).

Si une chaîne vide est correspondue, la correspondance suivante est effectuée avec l'indicateur PCRE2_NOTEMPTY_ATSTART défini, afin de rechercher une autre correspondance, non vide, au même point dans le sujet. Ceci imite la façon dont Perl gère de tels cas lorsqu'il utilise le modificateur /g ou la fonction split().

Tester les fonctions d'extraction de sous-chaînes

Les modificateurs copy et get peuvent être utilisés pour tester les fonctions pcre2_substring_copy_xxx() et pcre2_substring_get_xxx(). Ils peuvent être spécifiés plus d'une fois, et chacun peut spécifier un nom ou un numéro de groupe de capture, par exemple :


abcd\=copy=1,copy=3,get=G1

Si la commande #subject est utilisée pour définir des listes par défaut de copie et/ou d'obtention, celles-ci peuvent être annulées en spécifiant un nombre négatif pour annuler tous les groupes numérotés et un nom vide pour annuler tous les groupes nommés.

Le modificateur getall teste pcre2_substring_list_get(), qui extrait toutes les sous-chaînes capturées.

Si la ligne sujet est correctement mise en correspondance, les sous-chaînes extraites par les fonctions de commodité sont affichées avec C, G, ou L après le numéro de chaîne au lieu d'un deux-points. Ceci est en plus de la liste complète normale. La longueur de la chaîne (c'est-à-dire le retour de la fonction d'extraction) est donnée entre parenthèses après chaque sous-chaîne, suivie du nom lorsque l'extraction était par nom.

Tester la fonction de substitution

Si le modificateur replace est défini, la fonction pcre2_substitute() est appelée au lieu d'une des fonctions de correspondance (ou après un appel de pcre2_match() dans le cas de PCRE2_SUBSTITUTE_MATCHED). Notez que les chaînes de remplacement ne peuvent pas contenir de virgules, car une virgule signifie la fin d'un modificateur. Ceci n'est pas considéré comme un problème dans un programme de test.

Spécifier une chaîne de remplacement complètement vide désactive ce modificateur. Cependant, il est possible de spécifier une chaîne de remplacement vide en fournissant une longueur de tampon, comme décrit ci-dessous, pour un remplacement autrement vide.

Contrairement aux chaînes sujet, pcre2test ne traite pas les chaînes de remplacement pour les séquences d'échappement. En mode UTF, une chaîne de remplacement est vérifiée pour voir si c'est une chaîne UTF-8 valide. Si c'est le cas, elle est correctement convertie en une chaîne UTF de la largeur de code appropriée. Si ce n'est pas une chaîne UTF-8 valide, les unités de code individuelles sont copiées directement. Ceci fournit un moyen de passer une chaîne UTF-8 invalide à des fins de test.

Après une substitution réussie, la chaîne modifiée est affichée, précédée du nombre de remplacements. Cela peut être zéro s'il n'y a pas eu de correspondances. Voici un exemple simple de test de substitution :


/abc/replace=xxx
=abc=abc=
1: =xxx=abc=
=abc=abc=\=global
2: =xxx=xxx=

Les chaînes de sujet et de remplacement doivent être maintenues relativement courtes (moins de 256 caractères) pour les tests de substitution, car des tampons de taille fixe sont utilisés. Pour faciliter les tests de dépassement de tampon, si la chaîne de remplacement commence par un nombre entre crochets, ce nombre est passé à pcre2_substitute() comme taille du tampon de sortie, la chaîne de remplacement commençant au caractère suivant. Voici un exemple qui teste le cas limite :


/abc/
123abc123\=replace=[10]XYZ
1: 123XYZ123
123abc123\=replace=[9]XYZ
Failed: error -48: no more memory

L'action par défaut de pcre2_substitute() est de retourner PCRE2_ERROR_NOMEMORY lorsque le tampon de sortie est trop petit. Cependant, si l'option PCRE2_SUBSTITUTE_OVERFLOW_LENGTH est définie (en utilisant le modificateur substitute_overflow_length), pcre2_substitute() continue de simuler la correspondance et la substitution (mais sans effectuer d'appels de rappel), afin de calculer la taille du tampon requis. Lorsque cela se produit, pcre2test affiche la longueur du tampon requis (qui inclut l'espace pour le zéro final) dans le message d'erreur. Par exemple :


/abc/substitute_overflow_length
123abc123\=replace=[9]XYZ
Failed: error -48: no more memory: 10 code units are needed

Une chaîne de remplacement est ignorée avec la correspondance POSIX et DFA. La spécification d'une correspondance partielle provoque une erreur de retour ("mauvaise valeur d'option") de la part de pcre2_substitute().

Le modificateur substitute_subject peut être utilisé pour tester l'utilisation de l'API PCRE2, dans laquelle un client appelle pcre2_match() suivi de pcre2_substitute() avec PCRE2_SUBSTITUTE_MATCHED, mais le client effectue une modification inattendue et non prise en charge du tampon sujet en place, entre la correspondance et la substitution.

Test des rappels de substitution

Si le modificateur substitute_callout est défini, une fonction de rappel de substitution est configurée. Le modificateur null_context ne doit pas être défini, car l'adresse de la fonction de rappel est passée dans un contexte de correspondance. Lorsque la fonction de rappel est appelée (après chaque substitution), des détails sur les chaînes d'entrée et de sortie sont affichés. Par exemple :


/abc/g,replace=<$0>,substitute_callout
abcdefabcpqr
1(1) Old 0 3 "abc" New 0 5 "<abc>"
2(1) Old 6 9 "abc" New 8 13 "<abc>"
2: <abc>def<abc>pqr

Le premier nombre sur chaque ligne de rappel est le nombre de correspondances. Le nombre entre parenthèses est le nombre de paires définies dans l'ovector (c'est-à-dire un de plus que le nombre de groupes capturants qui ont été définis). Ensuite sont listés les décalages de la sous-chaîne d'origine, son contenu, et la même chose pour le remplacement.

Par défaut, la fonction de rappel de substitution renvoie zéro, ce qui accepte le remplacement et permet à la correspondance de continuer si /g a été utilisé. Deux modificateurs supplémentaires peuvent être utilisés pour tester d'autres valeurs de retour. Si substitute_skip est défini sur une valeur supérieure à zéro, la fonction de rappel renvoie +1 pour la correspondance de ce nombre, et de même substitute_stop renvoie -1. Ceux-ci provoquent le rejet du remplacement, et -1 fait que aucune correspondance supplémentaire n'a lieu. Si l'un d'eux est défini, substitute_callout est supposé. Par exemple :


/abc/g,replace=<$0>,substitute_skip=1
abcdefabcpqr
1(1) Old 0 3 "abc" New 0 5 "<abc> SKIPPED"
2(1) Old 6 9 "abc" New 6 11 "<abc>"
2: abcdef<abc>pqr
abcdefabcpqr\=substitute_stop=1
1(1) Old 0 3 "abc" New 0 5 "<abc> STOPPED"
1: abcdefabcpqr

Si les deux sont définis pour le même nombre, stop a la priorité. Un seul skip ou stop est pris en charge, ce qui est suffisant pour tester que la fonctionnalité fonctionne.

Test des rappels de casse de substitution

Si le modificateur substitute_case_callout est défini, une fonction de rappel de cas de substitution est configurée. La fonction de rappel est appelée pour chaque morceau substitué qui doit être transformé en casse.

La fonction de rappel fournie est une fonction fixe avec une implémentation pour certains comportements : entrées qui rétrécissent lors de la transformation en casse ; entrées qui grandissent ; entrées avec des formes majuscules/minuscules/titres distinctes. Les caractères qui ne sont pas spécialement mis en casse à des fins de test sont laissés inchangés, comme s'ils étaient des caractères insensibles à la casse.

Définition de la taille de la pile JIT

Le modificateur jitstack fournit un moyen de définir la taille maximale de la pile utilisée par le code d'optimisation juste-à-temps. Il est ignoré si l'optimisation JIT n'est pas utilisée. La valeur est le nombre de kibioctets (unités de 1024 octets). La définition à zéro revient à la valeur par défaut de 32 Kio. Fournir une pile plus grande que la valeur par défaut n'est nécessaire que pour des motifs très compliqués. Si jitstack est défini à une valeur non nulle sur une ligne de sujet, il remplace toute valeur définie dans le motif.

Définition des limites de tas, de correspondance et de profondeur

Les modificateurs heap_limit, match_limit et depth_limit définissent les limites appropriées dans le contexte de correspondance. Ces valeurs sont ignorées lorsque les modificateurs find_limits ou find_limits_noheap sont spécifiés.

Recherche des limites minimales

Si le modificateur find_limits est présent sur une ligne de sujet, pcre2test appelle la fonction de correspondance pertinente plusieurs fois, en définissant différentes valeurs dans le contexte de correspondance via pcre2_set_heap_limit(), pcre2_set_match_limit() ou pcre2_set_depth_limit() jusqu'à ce qu'il trouve la plus petite valeur pour chaque paramètre qui permet à la correspondance de se terminer sans erreur de "limite dépassée". La correspondance elle-même peut réussir ou échouer. Un modificateur alternatif, find_limits_noheap, omet la limite de tas. Ceci est utilisé dans les tests standard, car la limite minimale de tas varie selon les systèmes. Si JIT est utilisé, seule la limite de correspondance est pertinente, et les deux autres sont automatiquement omises.

Lors de l'utilisation de ce modificateur, le motif ne doit contenir aucune limite telle que (*LIMIT_MATCH=...) en son sein. Si un tel réglage est présent et est inférieur à la valeur de correspondance minimale, la valeur minimale ne peut pas être trouvée car pcre2_set_match_limit() etc. ne peuvent que réduire la valeur d'une limite dans le motif ; elles ne peuvent pas l'augmenter.

Pour la correspondance non-DFA, le nombre depth_limit minimal est une mesure de la quantité de backtracking imbriqué qui se produit (c'est-à-dire à quelle profondeur l'arbre du motif est recherché). Dans le cas de la correspondance DFA, depth_limit contrôle la profondeur des appels récursifs de la fonction interne utilisée pour gérer la récursion de motif, les assertions lookaround et les groupes atomiques.

Pour la correspondance non-DFA, le nombre match_limit est une mesure de la quantité de backtracking qui a lieu, et connaître la valeur minimale peut être instructif. Pour la plupart des correspondances simples, le nombre est assez petit, mais pour les motifs avec un très grand nombre de possibilités de correspondance, il peut devenir grand très rapidement avec l'augmentation de la longueur de la chaîne de sujet. Dans le cas de la correspondance DFA, match_limit contrôle le nombre total d'appels, récursifs et non récursifs, à la fonction de correspondance interne, contrôlant ainsi la quantité globale de ressources informatiques utilisées.

Pour les deux types de correspondance, le nombre heap_limit, qui est en kibioctets (unités de 1024 octets), limite la quantité de mémoire de tas utilisée pour la correspondance.

Affichage des noms MARK

Le modificateur mark provoque l'affichage des noms des verbes de contrôle de backtracking renvoyés par les appels à pcre2_match(). Si une marque est renvoyée pour une correspondance, une non-correspondance ou une correspondance partielle, pcre2test l'affiche. Pour une correspondance, elle est sur une ligne séparée, étiquetée "MK :". Sinon, elle est ajoutée au message de non-correspondance.

Affichage de l'utilisation de la mémoire

Le modificateur memory provoque l'enregistrement par pcre2test des tailles de toutes les allocations de mémoire de tas et des appels de libération qui se produisent lors d'un appel à pcre2_match() ou pcre2_dfa_match(). Dans ce dernier cas, la mémoire de tas n'est utilisée que lorsqu'une correspondance nécessite plus d'espace de travail interne que l'allocation par défaut sur la pile, donc dans de nombreux cas, il n'y aura aucune sortie. Aucune mémoire de tas n'est allouée pendant la correspondance avec JIT. Pour que ce modificateur fonctionne, le modificateur null_context ne doit pas être défini à la fois sur le motif et sur le sujet, bien qu'il puisse être défini sur l'un ou l'autre.

Affichage de la taille du vecteur global des cadres de tas

Le modificateur heapframes_size est pertinent pour les correspondances utilisant pcre2_match() sans JIT. Après qu'une correspondance a été exécutée (qu'elle ait réussi ou non), la taille, en octets, du vecteur de cadres de tas alloué qui reste attaché au bloc de données de correspondance est affichée. Si l'action de correspondance impliquait plusieurs appels à pcre2_match() (par exemple, correspondance globale ou pour chronométrer), seule la valeur finale est affichée.

Ce modificateur est ignoré, avec un avertissement, pour la correspondance POSIX ou DFA. La correspondance JIT n'utilise pas le vecteur de cadres de tas, donc la taille est toujours zéro, sauf s'il y a eu une correspondance non-JIT précédente. Notez que spécifier une taille de zéro pour le vecteur de sortie (voir ci-dessous) amène pcre2test à libérer son bloc de données de correspondance (et le vecteur de cadres de tas associé) et à en allouer un nouveau.

Définition d'un décalage de départ

Définition d'un offset de départ

Le modificateur offset définit un décalage dans la chaîne sujet à partir duquel la correspondance commence. Sa valeur est un nombre d'unités de code, pas de caractères.

Définition d'une limite d'offset

Le modificateur offset_limit définit une limite pour les correspondances non ancrées. Si une correspondance ne peut pas être trouvée en commençant à ou avant cet décalage dans le sujet, un retour "pas de correspondance" est donné. La valeur des données est un nombre d'unités de code, pas de caractères. Lorsque ce modificateur est utilisé, le modificateur use_offset_limit doit avoir été défini pour le motif; sinon, une erreur est générée.

Définition de la taille du vecteur de sortie

Le modificateur ovector s'applique uniquement à la ligne de sujet dans laquelle il apparaît, bien qu'il puisse bien sûr également être utilisé pour définir une valeur par défaut dans une commande #subject. Il spécifie le nombre de paires d'offsets disponibles pour stocker les informations de correspondance. La valeur par défaut est 15.

Une valeur de zéro est utile lors du test de l'API POSIX car elle provoque l'appel de regexec() avec un vecteur de capture NULL. Lorsque l'API POSIX n'est pas testée, une valeur de zéro est utilisée pour provoquer l'appel de pcre2_match_data_create_from_pattern(), afin de créer un nouveau bloc de correspondance de la taille exacte requise pour le motif. (Il n'est pas possible de créer un bloc de correspondance avec un ovector de longueur nulle; il y a toujours au moins une paire d'offsets.) L'ancien bloc de données de correspondance est libéré.

Passage du sujet comme terminé par zéro

Par défaut, la chaîne de sujet est passée à une fonction de correspondance de l'API native avec sa longueur correcte. Afin de tester la facilité de passage d'une chaîne terminée par zéro, le modificateur zero_terminate est fourni. Il provoque le passage de la longueur en tant que PCRE2_ZERO_TERMINATED. Lors de la correspondance via l'interface POSIX, ce modificateur est ignoré, avec un avertissement.

Lors du test de pcre2_substitute(), ce modificateur a également pour effet de passer la chaîne de remplacement comme terminée par zéro.

Passage d'un contexte, sujet ou remplacement NULL

Normalement, pcre2test passe un bloc de contexte à pcre2_match(), pcre2_dfa_match(), pcre2_jit_match() ou pcre2_substitute(). Si le modificateur null_context est défini, cependant, NULL est passé. Ceci est pour tester que les fonctions de correspondance et de substitution se comportent correctement dans ce cas (elles utilisent les valeurs par défaut). Ce modificateur ne peut pas être utilisé avec les modificateurs find_limits, find_limits_noheap, ou substitute_callout.

De même, à des fins de test, si le modificateur null_subject ou null_replacement est défini, les pointeurs des chaînes de sujet ou de remplacement sont passés comme NULL, respectivement, aux fonctions pertinentes.

LA FONCTION DE CORRESPONDANCE ALTERNATIVE

Par défaut, pcre2test utilise la fonction de correspondance standard PCRE2, pcre2_match(), pour faire correspondre chaque ligne de sujet. PCRE2 prend également en charge une fonction de correspondance alternative, pcre2_dfa_match(), qui fonctionne différemment et a certaines restrictions. Les différences entre les deux fonctions sont décrites dans la documentation pcre2matching.

Si le modificateur dfa est défini, la fonction de correspondance alternative est utilisée. Cette fonction trouve toutes les correspondances possibles à un point donné du sujet. Si, cependant, le modificateur dfa_shortest est défini, le traitement s'arrête après la première correspondance trouvée. C'est toujours la correspondance la plus courte possible.

SORTIE PAR DÉFAUT DE pcre2test

Cette section décrit la sortie lorsque la fonction de correspondance normale, pcre2_match(), est utilisée.

Lorsqu'une correspondance réussit, pcre2test affiche la liste des sous-chaînes capturées, en commençant par le numéro 0 pour la chaîne qui correspond au motif entier. Sinon, il affiche "No match" lorsque le retour est PCRE2_ERROR_NOMATCH, ou "Partial match:" suivi de la sous-chaîne correspondant partiellement lorsque le retour est PCRE2_ERROR_PARTIAL. (Notez qu'il s'agit de la sous-chaîne entière qui a été inspectée lors de la correspondance partielle ; elle peut inclure des caractères avant le début réel de la correspondance si une assertion de regard en arrière, \K, \b, ou \B était impliquée.)

Pour tout autre retour, pcre2test affiche le numéro d'erreur négatif PCRE2 et une courte phrase descriptive. Si l'erreur est un contrôle de chaîne UTF échoué, l'offset de l'unité de code du début du caractère échoué est également affiché. Voici un exemple d'exécution interactive de pcre2test.


$ pcre2test
PCRE2 version 10.22 2016-07-29


re> /^abc(\d+)/
data> abc123
0: abc123
1: 123
data> xyz
No match

Les sous-chaînes de capture non définies qui ne sont pas suivies par une sous-chaîne définie ne sont pas affichées par pcre2test à moins que le modificateur allcaptures ne soit spécifié. Dans l'exemple suivant, il y a deux sous-chaînes de capture, mais lorsque la première ligne de données est mise en correspondance, la deuxième sous-chaîne non définie n'est pas affichée. Une sous-chaîne non définie "interne" est affichée comme "<unset>", comme pour la deuxième ligne de données.


re> /(a)|(b)/
data> a
0: a
1: a
data> b
0: b
1: <unset>
2: b

Si les chaînes contiennent des caractères non imprimables, ils sont affichés sous forme d'échappements \xhh si la valeur est inférieure à 256 et que le mode UTF n'est pas défini. Sinon, ils sont affichés sous forme d'échappements \x{hh...}. Voir ci-dessous pour la définition des caractères non imprimables. Si le modificateur aftertext est défini, la sortie pour la sous-chaîne 0 est suivie du reste de la chaîne de sujet, identifiée par "0+" comme ceci :


re> /cat/aftertext
data> cataract
0: cat
0+ aract

Si la correspondance globale est demandée, les résultats des tentatives de correspondance successives sont affichés en séquence, comme ceci :


re> /\Bi(\w\w)/g
data> Mississippi
0: iss
1: ss
0: iss
1: ss
0: ipp
1: pp

"No match" n'est affiché que si la première tentative de correspondance échoue. Voici un exemple de message d'échec (l'offset 4 qui est spécifié par le modificateur offset est au-delà de la fin de la chaîne de sujet) :


re> /xyz/
data> xyz\=offset=4
Error -24 (bad offset value)

Notez que si les motifs peuvent être prolongés sur plusieurs lignes (une invite simple ">" est utilisée pour les continuations), les lignes de sujet ne le peuvent pas. Cependant, les nouvelles lignes peuvent être incluses dans un sujet au moyen de l'échappement \n (ou \r, \r\n, etc., selon le réglage de la séquence de nouvelles lignes).

SORTIE DE LA FONCTION DE CORRESPONDANCE ALTERNATIVE

Lorsque la fonction de correspondance alternative, pcre2_dfa_match(), est utilisée, la sortie consiste en une liste de toutes les correspondances qui commencent au premier point du sujet où il y a au moins une correspondance. Par exemple :


re> /(tang|tangerine|tan)/
data> yellow tangerine\=dfa
0: tangerine
1: tang
2: tan

L'utilisation de la fonction de correspondance normale sur ces données ne trouve que "tang". La chaîne correspondante la plus longue est toujours donnée en premier (et numérotée zéro). Après un retour PCRE2_ERROR_PARTIAL, la sortie est "Partial match:", suivie de la sous-chaîne correspondant partiellement. Notez qu'il s'agit de la sous-chaîne entière qui a été inspectée lors de la correspondance partielle ; elle peut inclure des caractères avant le début réel de la correspondance si une assertion de regard en arrière, \b, ou \B était impliquée. (\K n'est pas pris en charge pour la correspondance DFA.)

Si la correspondance globale est demandée, la recherche de correspondances supplémentaires reprend à la fin de la correspondance la plus longue. Par exemple :


re> /(tang|tangerine|tan)/g
data> yellow tangerine and tangy sultana\=dfa
0: tangerine
1: tang
2: tan
0: tang
1: tan
0: tan

La fonction de correspondance alternative ne prend pas en charge la capture de sous-chaînes, de sorte que les modificateurs concernant les sous-chaînes capturées ne sont pas pertinents.

Redémarrage après une correspondance partielle

Lorsque la fonction de correspondance alternative a renvoyé PCRE2_ERROR_PARTIAL, indiquant que le sujet correspond partiellement au motif, vous pouvez redémarrer la correspondance avec des données de sujet supplémentaires au moyen du modificateur dfa_restart. Par exemple :


re> /^\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d$/
data> 23ja\=ps,dfa
Partial match: 23ja
data> n05\=dfa,dfa_restart
0: n05

Pour plus d'informations sur la correspondance partielle, voir la documentation pcre2partial.

Appels de fonction

Si le motif contient des requêtes d'appel de fonction, la fonction d'appel de pcre2test est appelée pendant la correspondance à moins que callout_none ne soit spécifié. Cela fonctionne avec les deux fonctions de correspondance, et avec JIT, bien qu'il y ait quelques différences de comportement. La sortie pour les appels de fonction avec des arguments numériques et ceux avec des arguments de chaîne est légèrement différente.

Appels de fonction avec arguments numériques

Par défaut, la fonction d'appel de fonction affiche le numéro d'appel, les positions de départ et actuelles dans le texte du sujet au moment de l'appel, et le prochain élément du motif à tester. Par exemple :


--->pqrabcdef
0 ^ ^ \d

Cette sortie indique que l'appel de fonction numéro 0 s'est produit pour une tentative de correspondance commençant au quatrième caractère de la chaîne de sujet, lorsque le pointeur était au septième caractère, et lorsque le prochain élément du motif était \d. Un seul accent circonflexe est affiché si les positions de départ et actuelles sont identiques, ou si la position actuelle p

recule la position de départ, ce qui peut se produire si le rappel se trouve dans une assertion lookbehind.

Les rappels numérotés 255 sont considérés comme des rappels automatiques, insérés en résultat du modificateur de motif auto_callout. Dans ce cas, au lieu d'afficher le numéro du rappel, le décalage dans le motif, précédé d'un plus, est affiché. Par exemple :


re> /\d?[A-E]\*/auto_callout
data> E*
--->E*
+0 ^ \d?
+3 ^ [A-E]
+8 ^^ \*
+10 ^ ^
0: E*

Si un motif contient des éléments (*MARK), une ligne supplémentaire est affichée chaque fois qu'un changement de la dernière marque est passé à la fonction de rappel. Par exemple :


re> /a(*MARK:X)bc/auto_callout
data> abc
--->abc
+0 ^ a
+1 ^^ (*MARK:X)
+10 ^^ b
Dernière Marque : X
+11 ^ ^ c
+12 ^ ^
0: abc

La marque change entre la correspondance de « a » et « b », mais reste la même pour le reste de la correspondance, donc rien d'autre n'est affiché. Si, à la suite d'un retour arrière, la marque redevient non définie, le texte « <unset> » est affiché.

Appels avec arguments de chaîne

La sortie pour un rappel avec un argument de chaîne est similaire, sauf qu'au lieu d'afficher un numéro de rappel avant les indicateurs de position, la chaîne de rappel et son décalage dans la chaîne de motif sont affichés avant le reflet de la chaîne sujet, et la chaîne sujet est réfléchie pour chaque rappel. Par exemple :


re> /^ab(?C'first')cd(?C"second")ef/
data> abcdefg
Rappel (7) : 'first'
--->abcdefg
^ ^ c
Rappel (20) : "second"
--->abcdefg
^ ^ e
0: abcdef

Modificateurs de rappel

La fonction de rappel dans pcre2test renvoie zéro (continuer la correspondance) par défaut, mais vous pouvez utiliser un modificateur callout_fail dans une ligne sujet pour modifier cela et d'autres paramètres du rappel (voir ci-dessous).

Si le modificateur callout_capture est défini, les groupes capturés actuels sont affichés lorsqu'un rappel se produit. Ceci n'est utile que pour les correspondances non DFA, car pcre2_dfa_match() ne prend pas en charge la capture, donc aucune capture n'est jamais affichée.

La sortie normale du rappel, montrant le numéro du rappel ou le décalage du motif (comme décrit ci-dessus) est supprimée si le modificateur callout_no_where est défini.

Lors de l'utilisation de la fonction de correspondance interprétative pcre2_match() sans JIT, la définition du modificateur callout_extra entraîne la génération d'une sortie supplémentaire de la fonction de rappel de pcre2test. Pour le premier rappel dans une tentative de correspondance à une nouvelle position de départ dans le sujet, « New match attempt » est affiché. S'il y a eu un retour arrière depuis le dernier rappel (ou le début de la correspondance s'il s'agit du premier rappel), « Backtrack » est affiché, suivi de « No other matching paths » si le retour arrière a mis fin à la tentative de correspondance précédente. Par exemple :


re> /(a+)b/auto_callout,no_start_optimize,no_auto_possess
data> aac\=callout_extra
New match attempt
--->aac
+0 ^ (
+1 ^ a+
+3 ^ ^ )
+4 ^ ^ b
Backtrack
--->aac
+3 ^^ )
+4 ^^ b
Backtrack
No other matching paths
New match attempt
--->aac
+0 ^ (
+1 ^ a+
+3 ^^ )
+4 ^^ b
Backtrack
No other matching paths
New match attempt
--->aac
+0 ^ (
+1 ^ a+
Backtrack
No other matching paths
New match attempt
--->aac
+0 ^ (
+1 ^ a+
No match

Notez que diverses optimisations doivent être désactivées si vous voulez que tous les chemins de correspondance possibles soient analysés. Si no_start_optimize n'est pas utilisé, il y a un « no match » immédiat, sans aucun rappel, car l'optimisation de départ ne parvient pas à trouver « b » dans le sujet, dont il sait qu'il doit être présent pour toute correspondance. Si no_auto_possess n'est pas utilisé, l'élément « a+ » est transformé en « a++ », ce qui réduit le nombre de retours arrière.

Le modificateur callout_extra n'a aucun effet s'il est utilisé avec la fonction de correspondance DFA, ou avec JIT.

Valeurs de retour des rappels

La valeur de retour par défaut de la fonction de rappel est zéro, ce qui permet à la correspondance de continuer. Le modificateur callout_fail peut recevoir un ou deux nombres. S'il y a un seul nombre, 1 est renvoyé au lieu de 0 (provoquant un retour arrière de la correspondance) lorsqu'un rappel de ce numéro est atteint. S'il y a deux nombres (<n>:<m>), 1 est renvoyé lorsque le rappel <n> est atteint et qu'il y a eu au moins <m> rappels. Le modificateur callout_error est similaire, sauf que PCRE2_ERROR_CALLOUT est renvoyé, ce qui provoque l'abandon de tout le processus de correspondance. Si ces deux modificateurs sont définis pour le même numéro de rappel, callout_error a la priorité. Notez que les rappels avec des arguments de chaîne reçoivent toujours le numéro zéro.

Le modificateur callout_data peut recevoir un nombre non signé ou négatif. Ceci est défini comme les « données utilisateur » qui sont passées à la fonction de correspondance, et renvoyées lorsque la fonction de rappel est invoquée. Toute valeur autre que zéro est utilisée comme retour de la fonction de rappel de pcre2test.

L'insertion de rappels peut être utile lors de l'utilisation de pcre2test pour vérifier des expressions régulières compliquées. Pour plus d'informations sur les rappels, voir la documentation de pcre2callout.

CARACTÈRES NON IMPRIMABLES

Lorsque pcre2test affiche du texte dans la version compilée d'un motif, les octets autres que 32-126 sont toujours traités comme des caractères non imprimables et sont donc affichés sous forme d'échappements hexadécimaux.

Lorsque pcre2test affiche du texte qui fait partie d'une chaîne sujet correspondante, il se comporte de la même manière, sauf si une locale différente a été définie pour le motif (à l'aide du modificateur locale). Dans ce cas, la fonction isprint() est utilisée pour distinguer les caractères imprimables et non imprimables.

SAUVEGARDE ET RESTAURATION DES MOTIFS COMPILÉS

Il est possible de sauvegarder des motifs compilés sur disque ou ailleurs, et de les recharger plus tard, sous réserve d'un certain nombre de restrictions. Les données JIT ne peuvent pas être sauvegardées. L'hôte sur lequel les motifs sont rechargés doit exécuter la même version de PCRE2, avec la même largeur d'unités de code, et doit également avoir la même valeur d'endianness, la même largeur de pointeur et le même type PCRE2_SIZE. Avant que les motifs compilés puissent être sauvegardés, ils doivent être sérialisés, c'est-à-dire convertis en un flux d'octets. Un seul flux d'octets peut contenir n'importe quel nombre de motifs compilés, mais ils doivent tous utiliser les mêmes tables de caractères. Une seule copie des tables est incluse dans le flux d'octets (sa taille est de 1088 octets).

Les fonctions dont les noms commencent par pcre2_serialize_ sont utilisées pour la sérialisation et la désérialisation. Elles sont décrites dans la documentation de pcre2serialize. Dans cette section, nous décrivons les fonctionnalités de pcre2test qui peuvent être utilisées pour tester ces fonctions.

Notez que la « sérialisation » dans PCRE2 ne convertit pas les motifs compilés en un format abstrait comme Java ou .NET. Elle crée simplement un flux d'octets rechargeable. D'où les restrictions de rechargement mentionnées ci-dessus.

Dans pcre2test, lorsqu'un motif avec le modificateur push est compilé avec succès, il est placé sur une pile de motifs compilés, et pcre2test s'attend à ce que la ligne suivante contienne un nouveau motif (ou commande) au lieu d'une ligne sujet. Par contraste, le modificateur pushcopy provoque la mise en pile d'une copie du motif compilé, laissant l'original disponible pour une correspondance immédiate. En utilisant push et/ou pushcopy, un certain nombre de motifs peuvent être compilés et conservés. Ces modificateurs sont incompatibles avec posix, et les modificateurs de contrôle qui agissent au moment de la correspondance sont ignorés (avec un message) pour les motifs empilés. Le modificateur jitverify s'applique uniquement au moment de la compilation.

La commande


#save <nom_de_fichier>

provoque la sérialisation de tous les motifs empilés et l'écriture du résultat dans le fichier nommé. Ensuite, tous les motifs empilés sont libérés. La commande


#load <nom_de_fichier>

lit les données du fichier, puis organise leur désérialisation, les motifs compilés résultants étant ajoutés à la pile de motifs. Le motif au sommet de la pile peut être récupéré par la commande #pop, qui doit être suivie de lignes de sujets à faire correspondre avec le motif, terminées comme d'habitude par une ligne vide ou la fin du fichier. Cette commande peut être suivie d'une liste de modificateurs contenant uniquement des modificateurs de contrôle qui agissent après la compilation d'un motif. En particulier, hex, posix, posix_nosub, push et pushcopy ne sont pas autorisés, pas plus que les modificateurs de définition d'options. Les modificateurs JIT sont cependant autorisés. Voici un exemple qui sauvegarde et recharge deux motifs.


/abc/push
/xyz/push
#save tempfile
#load tempfile
#pop info
xyz


#pop jit,bincode
abc

Si jitverify est utilisé avec #pop, il n'implique pas automatiquement jit, ce qui est un comportement différent de celui lorsqu'il est utilisé sur un motif.

La commande #popcopy est analogue au modificateur pushcopy en ce sens qu'elle rend active une copie du motif supérieur de la pile, laissant l'original toujours sur la pile.
