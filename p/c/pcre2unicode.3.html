NOM

PCRE2 - Expressions régulières compatibles Perl (API révisée)

SUPPORT DE UNICODE ET UTF

PCRE2 est normalement compilé avec le support Unicode, bien que si vous n'en avez pas besoin, vous puissiez le compiler sans, auquel cas la bibliothèque sera plus petite. Avec le support Unicode, PCRE2 connaît les propriétés des caractères Unicode et peut traiter des chaînes de texte aux formats UTF-8, UTF-16 et UTF-32 (selon la largeur de l'unité de code), mais ce n'est pas le comportement par défaut. Sauf demande explicite, PCRE2 traite chaque unité de code dans une chaîne comme un caractère.

Il existe deux façons de dire à PCRE2 de passer en mode UTF, où les caractères peuvent être constitués de plus d'une unité de code et où la plage de valeurs est contrainte. Le programme peut appeler pcre2_compile() avec l'option PCRE2_UTF, ou le motif peut commencer par la séquence (*UTF). Cependant, cette dernière facilité peut être bloquée par l'option PCRE2_NEVER_UTF. C'est-à-dire que le programmeur peut empêcher le fournisseur du motif de passer en mode UTF.

Notez que l'option PCRE2_MATCH_INVALID_UTF (voir ci-dessous) force la définition de PCRE2_UTF.

En mode UTF, le motif et les chaînes sujettes qui sont comparées à celui-ci sont traités comme des chaînes UTF au lieu de chaînes de caractères individuels à une unité de code. Il y a également d'autres modifications dans la manière dont les caractères sont gérés, comme documenté ci-dessous.

SUPPORT DES PROPRIÉTÉS UNICODE

Lorsque PCRE2 est compilé avec le support Unicode, les séquences d'échappement \p{..}, \P{..} et \X peuvent être utilisées. Ceci ne dépend pas du réglage PCRE2_UTF. Les propriétés Unicode qui peuvent être testées sont un sous-ensemble de celles que Perl supporte. Actuellement, elles sont limitées aux propriétés de catégorie générale comme Lu pour une lettre majuscule ou Nd pour un chiffre décimal, les propriétés dérivées Any et Lc (synonyme L&), les noms de scripts Unicode comme Arabic ou Han, Bidi_Class, Bidi_Control, et quelques propriétés binaires.

Les listes complètes sont données dans la documentation pcre2pattern et pcre2syntax. En général, seuls les noms courts des propriétés sont supportés. Par exemple, \p{L} correspond à une lettre. Son synonyme plus long, \p{Letter}, n'est pas supporté. De plus, dans Perl, de nombreuses propriétés peuvent éventuellement être préfixées par "Is", pour la compatibilité avec Perl 5.6. PCRE2 ne supporte pas cela.

CARACTÈRES LARGES ET MODES UTF

Les points de code inférieurs à 256 peuvent être spécifiés dans les motifs par des séquences d'échappement hexadécimales, avec ou sans accolades (par exemple, \x{b3} ou \xb3). Les valeurs plus grandes doivent utiliser des séquences avec accolades. Les points de code octaux sans accolades jusqu'à \777 sont également reconnus ; les plus grands peuvent être codés en utilisant \o{...}.

La séquence d'échappement \N{U+<chiffres hexadécimaux>} est reconnue comme une autre façon de spécifier un caractère Unicode par point de code en mode UTF. Elle n'est pas autorisée en mode non-UTF.

En mode UTF, les quantificateurs de répétition s'appliquent aux caractères UTF complets, et non aux unités de code individuelles.

En mode UTF, le métacaractère point correspond à un caractère UTF au lieu d'une unité de code unique.

En mode UTF, les noms des groupes de capture ne sont pas limités à l'ASCII et peuvent contenir des lettres et des chiffres décimaux Unicode, ainsi que le trait de soulignement.

La séquence d'échappement \C peut être utilisée pour faire correspondre une unité de code en mode UTF, mais son utilisation peut entraîner des effets étranges car elle sépare les caractères multi-unités (voir la description de \C dans la documentation pcre2pattern). Pour cette raison, il existe une option de compilation qui désactive complètement le support de \C. Il existe également une option de compilation moins draconienne pour bloquer l'utilisation de \C lors de la compilation d'un motif.

L'utilisation de \C n'est pas supportée par la fonction de correspondance alternative pcre2_dfa_match() en mode UTF-8 ou UTF-16, c'est-à-dire lorsque le caractère peut être constitué de plus d'une unité de code. L'utilisation de \C dans ces modes provoque une erreur lors de la correspondance. De plus, l'optimisation JIT ne supporte pas \C dans ces modes. Si l'optimisation JIT est demandée pour un motif UTF-8 ou UTF-16 qui contient \C, elle ne réussira pas, et donc lorsque pcre2_match() est appelée, la correspondance sera effectuée par la fonction interprétative.

Les séquences d'échappement de caractères \b, \B, \d, \D, \s, \S, \w et \W testent correctement les caractères de toute valeur de code, mais, par défaut, les caractères que PCRE2 reconnaît comme chiffres, espaces ou caractères de mots restent le même ensemble qu'en mode non-UTF, tous avec des points de code inférieurs à 256. Cela reste vrai même lorsque PCRE2 est compilé pour inclure le support Unicode, car faire autrement ralentirait la correspondance dans de nombreux cas courants. Notez que cela s'applique également à \b et \B, car ils sont définis en termes de \w et \w. Si vous souhaitez tester un sens plus large de, par exemple, "chiffre", vous pouvez utiliser des tests de propriétés Unicode explicites comme \p{Nd}. Alternativement, si vous définissez l'option PCRE2_UCP, la façon dont les séquences d'échappement de caractères fonctionnent est modifiée de sorte que les propriétés Unicode soient utilisées pour déterminer quels caractères correspondent, bien qu'il existe des options qui suppriment cela pour des séquences individuelles. Pour plus de détails, voir la section sur les types de caractères génériques dans la documentation pcre2pattern.

Comme les séquences d'échappement, les caractères qui correspondent aux classes de caractères nommées POSIX sont tous des caractères de faible valeur, à moins que l'option PCRE2_UCP ne soit définie, mais il existe une option pour remplacer cela.

Contrairement aux séquences d'échappement de caractères et aux classes de caractères, les séquences d'échappement spéciales pour les espaces horizontaux et verticaux (\h, \H, \v et \V) correspondent à tous les caractères Unicode appropriés, que PCRE2_UCP soit défini ou non.

ÉQUIVALENCE DES CASES UNICODE

Si PCRE2_UTF ou PCRE2_UCP est défini, le traitement des majuscules/minuscules utilise les propriétés Unicode, sauf pour les caractères dont les points de code sont inférieurs à 128 et qui ont au plus deux valeurs équivalentes en casse. Pour ceux-ci, une recherche directe dans une table est utilisée pour la vitesse. Quelques caractères Unicode comme le sigma grec ont plus de deux points de code qui sont équivalents en casse, et ceux-ci sont traités spécialement. Définir PCRE2_UCP sans PCRE2_UTF permet un traitement des casse de style Unicode pour les encodages de caractères non-UTF comme UCS-2.

Il existe deux caractères ASCII (S et K) qui, en plus de leurs équivalents minuscules ASCII, ont également un équivalent non-ASCII (S long et signe Kelvin). La reconnaissance de ces caractères non-ASCII comme équivalents en casse à leurs homologues ASCII peut être désactivée en définissant l'option PCRE2_EXTRA_CASELESS_RESTRICT. Lorsque cela est défini, tous les caractères d'une équivalence de casse doivent être soit ASCII, soit non-ASCII ; il ne peut y avoir de mélange.


Sans PCRE2_EXTRA_CASELESS_RESTRICT :
'k' = 'K' = U+212A (signe Kelvin)
's' = 'S' = U+017F (S long)
Avec PCRE2_EXTRA_CASELESS_RESTRICT :
'k' = 'K'
U+212A (signe Kelvin) uniquement équivalent en casse à lui-même
's' = 'S'
U+017F (S long) uniquement équivalent en casse à lui-même

Une famille de langues, le turc et l'azéri, a ses propres règles d'insensibilité à la casse, qui peuvent être sélectionnées en définissant PCRE2_EXTRA_TURKISH_CASING. Cela modifie le comportement des caractères 'i', 'I', U+0130 (I majuscule avec point au-dessus) et U+0131 (i minuscule sans point).


Sans PCRE2_EXTRA_TURKISH_CASING :
'i' = 'I'
U+0130 (I majuscule avec point au-dessus) uniquement équivalent en casse à lui-même
U+0131 (i minuscule sans point) uniquement équivalent en casse à lui-même
Avec PCRE2_EXTRA_TURKISH_CASING :
'i' = U+0130 (I majuscule avec point au-dessus)
U+0131 (i minuscule sans point) = 'I'

Il n'est pas permis de spécifier ensemble PCRE2_EXTRA_CASELESS_RESTRICT et PCRE2_EXTRA_TURKISH_CASING.

À partir de la version 10.45, les propriétés de lettres Unicode Lu (majuscule), Ll (minuscule) et Lt (titre) sont toutes traitées comme Lc (lettre avec casse) lorsque la correspondance sans casse est définie par l'option PCRE2_CASELESS ou par (?i) dans le motif.

SÉQUENCES DE CARACTÈRES

Les constructions de motifs (*script_run:...) et (*atomic_script_run:...), avec les synonymes (*sr:...) et (*asr:...), vérifient que la chaîne mise en correspondance à l'intérieur des parenthèses est une séquence de caractères d'un même script. En concept, une séquence de caractères d'un même script est une suite de caractères provenant tous du même script Unicode. Cependant, comme certains scripts sont couramment utilisés ensemble, et comme certaines marques diacritiques et autres sont utilisées avec plusieurs scripts, ce n'est pas aussi simple.

Chaque caractère Unicode possède une propriété Script, le plus souvent avec une valeur correspondant au nom d'un script, tel que Latin, Greek ou Cyrillic. Il existe également trois valeurs spéciales :

<

"Inconnu" est utilisé pour les points de code qui n'ont pas été attribués, ainsi que pour les points de code de substitution. Dans la bibliothèque PCRE2 32 bits, les caractères dont les points de code sont supérieurs au maximum Unicode (U+10FFFF), qui ne sont accessibles qu'en mode non UTF, se voient attribuer le script Inconnu.

"Commun" est utilisé pour les caractères qui sont utilisés avec de nombreux alphabets. Il s'agit notamment de la ponctuation, des emojis, des symboles mathématiques, musicaux et monétaires, ainsi que des chiffres ASCII de 0 à 9.

"Hérité" est utilisé pour les caractères tels que les marques diacritiques qui modifient un caractère précédent. Ceux-ci sont considérés comme prenant le script du caractère qu'ils modifient.

Certains caractères Hérités sont utilisés avec de nombreux alphabets, mais beaucoup d'entre eux ne sont normalement utilisés qu'avec un petit nombre d'alphabets. Par exemple, U+102E0 (marque copte des milliers d'éphactes) n'est utilisé qu'avec l'arabe et le copte. Afin de permettre cette vérification, une propriété Unicode appelée Extension de script existe. Sa valeur est une liste de scripts qui s'appliquent au caractère. Pour la majorité des caractères, la liste ne contient qu'un seul script, le même que la propriété Script. Cependant, pour des caractères tels que U+102E0, plusieurs scripts sont listés. Il existe également certains caractères Communs qui ont un script unique et non Commun dans leur liste d'Extension de script.

La section suivante décrit les règles de base pour décider si une chaîne de caractères donnée est une séquence de script. Notez, cependant, qu'il existe des cas particuliers impliquant le script chinois Han, et une contrainte supplémentaire pour les chiffres décimaux. Ceux-ci sont couverts dans les sections suivantes.

Règles de base pour les séquences de script

Une chaîne de moins de deux caractères est une séquence de script. C'est le seul cas où un caractère Inconnu peut faire partie d'une séquence de script. Les chaînes plus longues sont vérifiées en utilisant uniquement la propriété Extensions de script, et non la propriété Script de base.

Si la propriété Extension de script d'un caractère est la valeur unique "Hérité", elle est toujours acceptée comme faisant partie d'une séquence de script. Il en va de même pour la propriété "Commun", sous réserve de la vérification des chiffres décimaux décrite ci-dessous. Tous les caractères restants d'une séquence de script doivent avoir au moins un script en commun dans leurs listes d'Extensions de script. En termes de théorie des ensembles, l'intersection de tous les ensembles de scripts ne doit pas être vide.

Un exemple simple est un nom Internet tel que "google.com". Les lettres sont toutes dans le script Latin, et le point est Commun, donc cette chaîne est une séquence de script. Cependant, la lettre cyrillique "o" ressemble exactement à la lettre latine "o" ; une chaîne qui ressemble à la même chose, mais avec des "o" cyrilliques, n'est pas une séquence de script.

Des exemples plus intéressants impliquent des caractères avec plus d'un script dans leur Extension de script. Considérons les caractères suivants :


U+060C Virgule arabe
U+06D4 Point final arabe

Le premier a la liste d'Extension de script arabe, Hanifi Rohingya, syriaque et thaana ; le second n'a que l'arabe et le Hanifi Rohingya. Les deux peuvent apparaître dans des séquences de script soit arabes, soit Hanifi Rohingya. Le premier pourrait également apparaître dans des séquences de script syriaque ou thaana, mais le second ne le pourrait pas.

Le script chinois Han

Le script chinois Han est couramment utilisé en conjonction avec d'autres alphabets pour écrire certaines langues. Le japonais utilise les alphabets Hiragana et Katakana avec Han ; le coréen utilise le Hangul et Han ; le mandarin taïwanais utilise le Bopomofo et Han. Ces trois combinaisons sont traitées comme des cas spéciaux lors de la vérification des séquences de script et sont, en effet, des "scripts virtuels". Ainsi, une séquence de script peut contenir un mélange de Hiragana, Katakana et Han, ou un mélange de Hangul et Han, ou un mélange de Bopomofo et Han, mais pas, par exemple, un mélange de Hangul, Bopomofo et Han. PCRE2 (comme Perl) suit la norme technique 39 de Unicode ("Mécanismes de sécurité Unicode", http://unicode.org/reports/tr39/) en autorisant de tels mélanges.

Chiffres décimaux

Unicode contient de nombreux ensembles de 10 chiffres décimaux dans différentes alphabets, et certains alphabets (y compris l'alphabet Commun) en contiennent plus d'un. Certains de ces chiffres décimaux sont visuellement indiscernables des chiffres ASCII communs. En plus de la vérification de script décrite ci-dessus, si une séquence de script contient des chiffres décimaux, ils doivent tous provenir du même ensemble de 10 caractères adjacents.

VALIDITÉ DES CHAÎNES UTF

Lorsque l'option PCRE2_UTF est définie, les chaînes passées comme motifs et sujets sont (par défaut) vérifiées pour leur validité à l'entrée des fonctions pertinentes. Si une chaîne UTF invalide est passée, un code d'erreur négatif est renvoyé. Le décalage d'unité de code vers le caractère fautif peut être extrait du bloc de données de correspondance en appelant pcre2_get_startchar(), qui est utilisé à cet effet après une erreur UTF.

Dans certaines situations, vous savez peut-être déjà que vos chaînes sont valides, et souhaitez donc ignorer ces vérifications afin d'améliorer les performances, par exemple dans le cas d'une longue chaîne de sujet qui est parcourue de manière répétée. Si vous définissez l'option PCRE2_NO_UTF_CHECK au moment de la compilation ou au moment de la correspondance, PCRE2 suppose que le motif ou le sujet qu'il reçoit (respectivement) ne contient que des séquences d'unités de code UTF valides.

Si vous passez une chaîne UTF invalide alors que PCRE2_NO_UTF_CHECK est défini, le résultat est indéfini et votre programme peut planter, boucler indéfiniment ou donner des résultats incorrects. Il existe cependant un mode de correspondance qui peut gérer les chaînes de sujet UTF invalides. Celui-ci est activé en passant PCRE2_MATCH_INVALID_UTF à pcre2_compile() et est discuté ci-dessous dans la section suivante. Le reste de cette section couvre le cas où PCRE2_MATCH_INVALID_UTF n'est pas défini.

Passer PCRE2_NO_UTF_CHECK à pcre2_compile() désactive uniquement la vérification UTF pour le motif ; elle ne s'applique pas aux chaînes de sujet. Si vous souhaitez désactiver la vérification pour une chaîne de sujet, vous devez passer la même option à pcre2_match() ou pcre2_dfa_match().

Les chaînes UTF-16 et UTF-32 peuvent indiquer leur boutisme par des codes spéciaux connus sous le nom de marque d'ordre des octets (BOM). Les fonctions PCRE2 ne le gèrent pas, attendant que les chaînes soient dans l'ordre des octets de l'hôte.

Sauf si PCRE2_NO_UTF_CHECK est défini, une chaîne UTF est vérifiée avant tout autre traitement. Dans le cas des appels pcre2_match() et pcre2_dfa_match() avec un décalage de départ non nul, la vérification ne s'applique qu'à la partie du sujet qui peut être inspectée pendant la correspondance, et il y a une vérification que le décalage de départ pointe vers la première unité de code d'un caractère ou vers la fin du sujet. S'il n'y a pas d'assertions de recherche arrière dans le motif, la vérification commence au décalage de départ. Sinon, elle commence à la longueur de la recherche arrière la plus longue avant le décalage de départ, ou au début du sujet s'il n'y a pas autant de caractères avant le décalage de départ. Notez que les séquences \b et \B sont des recherches arrière d'un caractère.

En plus de vérifier le format de la chaîne, il y a une vérification pour s'assurer que tous les points de code se situent dans la plage U+0 à U+10FFFF, en excluant la zone de substitution. Les points de code dits "non caractères" ne sont pas exclus car le rectificatif Unicode #9 précise qu'ils ne devraient pas l'être.

Les caractères de la "zone de substitution" d'Unicode sont réservés à l'usage par UTF-16, où ils sont utilisés par paires pour encoder des points de code dont les valeurs sont supérieures à 0xFFFF. Les points de code qui sont encodés par des paires UTF-16 sont disponibles indépendamment dans les encodages UTF-8 et UTF-32. (En d'autres termes, toute cette affaire de substitution est une astuce pour UTF-16 qui, malheureusement, perturbe UTF-8 et UTF-32.)

Définir PCRE2_NO_UTF_CHECK au moment de la compilation ne désactive pas l'erreur qui se produit si une séquence d'échappement pour un point de code Unicode invalide est rencontrée dans le motif. Si vous souhaitez autoriser des séquences d'échappement telles que \x{d800} (un point de code de substitution), vous pouvez définir l'option supplémentaire PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES. Cependant, ce n'est possible qu'en modes UTF-8 et UTF-32, car ces valeurs ne sont pas représentables en UTF-16.

Erreurs dans les chaînes UTF-8

Les codes d'erreur négatifs suivants sont donnés pour les chaînes UTF-8 invalides :


PCRE2_ERROR_UTF8_ERR1
PCRE2_ERROR_UTF8_ERR2
PCRE2_ERROR_UTF8_ERR3
PCRE2_ERROR_UTF8_ERR4
PCRE2_ERROR_UTF8_ERR5

La chaîne se termine par un caractère UTF-8 tronqué ; le code spécifie combien d'octets manquent (1 à 5). Bien que RFC 3629 limite les caractères UTF-8 à 4 octets maximum, le schéma d'encodage (défini à l'origine par RFC 2279) autorise jusqu'à 6 octets, et c'est vérifié en premier ; d'où la possibilité de 4 ou 5 octets manquants.


PCRE2_ERROR_UTF8_ERR6
PCRE2_ERROR_UTF8_ERR7
PCRE2_ERROR_UTF8_ERR8
PCRE2_ERROR_UTF8_ERR9
PCRE2_ERROR_UTF8_ERR10

Les deux bits les plus significatifs du 2e, 3e, 4e, 5e ou 6e octet du caractère n'ont pas la valeur binaire 0b10 (c'est-à-dire que le bit le plus significatif est 0, ou le bit suivant est 1).


PCRE2_ERROR_UTF8_ERR11
PCRE2_ERROR_UTF8_ERR12

Un caractère valide selon les règles RFC 2279 est soit de 5, soit de 6 octets ; ces points de code sont exclus par RFC 3629.


PCRE2_ERROR_UTF8_ERR13

Un caractère de 4 octets a une valeur supérieure à 0x10ffff ; ces points de code sont exclus par RFC 3629.


PCRE2_ERROR_UTF8_ERR14

Un caractère de 3 octets a une valeur dans la plage 0xd800 à 0xdfff ; cette plage de points de code est réservée par RFC 3629 pour l'usage avec UTF-16, et est donc exclue de UTF-8.


PCRE2_ERROR_UTF8_ERR15
PCRE2_ERROR_UTF8_ERR16
PCRE2_ERROR_UTF8_ERR17
PCRE2_ERROR_UTF8_ERR18
PCRE2_ERROR_UTF8_ERR19

Un caractère de 2, 3, 4, 5 ou 6 octets est "sur-encodé", c'est-à-dire qu'il code pour une valeur qui peut être représentée par moins d'octets, ce qui est invalide. Par exemple, les deux octets 0xc0, 0xae donnent la valeur 0x2e, dont le codage correct utilise un seul octet.


PCRE2_ERROR_UTF8_ERR20

Les deux bits les plus significatifs du premier octet d'un caractère ont la valeur binaire 0b10 (c'est-à-dire que le bit le plus significatif est 1 et le second est 0). Un tel octet ne peut apparaître que valablement comme deuxième octet ou octet suivant d'un caractère multi-octets.


PCRE2_ERROR_UTF8_ERR21

Le premier octet d'un caractère a la valeur 0xfe ou 0xff. Ces valeurs ne peuvent jamais apparaître dans une chaîne UTF-8 valide.

Erreurs dans les chaînes UTF-16

Les codes d'erreur négatifs suivants sont donnés pour les chaînes UTF-16 invalides :


PCRE2_ERROR_UTF16_ERR1 Bas substitut manquant en fin de chaîne
PCRE2_ERROR_UTF16_ERR2 Bas substitut invalide suit un haut substitut
PCRE2_ERROR_UTF16_ERR3 Bas substitut isolé

Erreurs dans les chaînes UTF-32

Les codes d'erreur négatifs suivants sont donnés pour les chaînes UTF-32 invalides :


PCRE2_ERROR_UTF32_ERR1 Caractère substitut (0xd800 à 0xdfff)
PCRE2_ERROR_UTF32_ERR2 Point de code supérieur à 0x10ffff

RECHERCHE DANS DES CHAÎNES UTF INVALIDES

Vous pouvez effectuer des recherches de motifs sur des chaînes de sujet pouvant contenir des séquences UTF invalides si vous appelez pcre2_compile() avec l'option PCRE2_MATCH_INVALID_UTF. Ceci est pris en charge par pcre2_match(), y compris la recherche JIT, mais pas par pcre2_dfa_match(). Lorsque PCRE2_MATCH_INVALID_UTF est définie, elle force également la définition de PCRE2_UTF. Notez cependant que le motif lui-même doit être une chaîne UTF valide.

Si vous ne définissez pas PCRE2_MATCH_INVALID_UTF lors de l'appel de pcre2_compile, et que vous n'êtes pas certain que vos chaînes de sujet sont des séquences UTF valides, vous ne devriez pas utiliser la fonction "chemin rapide" JIT pcre2_jit_match() car elle contourne les vérifications de validité, y compris celle de la validité UTF. Une chaîne invalide peut entraîner un comportement indéfini, y compris des boucles, des plantages ou des résultats incorrects.

La définition de PCRE2_MATCH_INVALID_UTF n'affecte pas ce que pcre2_compile() génère, mais si pcre2_jit_compile() est appelé par la suite, il génère un code différent. Si JIT n'est pas utilisé, l'option affecte le comportement du code interprétatif dans pcre2_match(). Lorsque PCRE2_MATCH_INVALID_UTF est définie au moment de la compilation, PCRE2_NO_UTF_CHECK est ignorée au moment de la recherche.

Dans ce mode, une séquence d'unités de code invalide dans le sujet ne correspond jamais à aucun élément du motif. Elle ne correspond pas au point, elle ne correspond pas à \p{Any}, elle ne correspond même pas aux éléments négatifs tels que [^X]. Une assertion lookbehind échoue si elle rencontre une séquence invalide en se déplaçant vers l'arrière du point courant. En d'autres termes, une séquence d'unités de code UTF invalide agit comme une barrière que aucune recherche ne peut franchir.

Vous pouvez également considérer cela comme le sujet étant divisé en fragments d'UTF valides, délimités en interne par des séquences d'unités de code invalides. Le motif est recherché fragment par fragment. Le résultat d'une recherche réussie est cependant donné en tant que décalages d'unités de code dans la chaîne de sujet entière, comme d'habitude. Il y a quelques points à considérer :

Les frontières internes ne sont pas interprétées comme les débuts ou fins de lignes et ne correspondent donc pas aux caractères circonflexes ou dollar dans le motif.

Si pcre2_match() est appelé avec un décalage qui pointe vers une séquence UTF invalide, cette séquence est ignorée, et la recherche commence au prochain caractère UTF valide, ou à la fin du sujet.

Aux frontières de fragments internes, \b et \B se comportent de la même manière qu'au début et à la fin du sujet. Par exemple, une séquence telle que \bMOT\b correspondrait à une instance de MOT entourée d'unités de code UTF invalides.

En utilisant PCRE2_MATCH_INVALID_UTF, une application peut effectuer des recherches sur des données arbitraires, en sachant que toutes les chaînes correspondantes renvoyées sont des UTF valides. Cela peut être utile lors de la recherche de texte UTF dans des fichiers exécutables ou d'autres fichiers binaires.

Notez cependant que les bibliothèques PCRE2 16 bits et 32 bits traitent les chaînes comme des séquences de points de code uint16_t ou uint32_t. Elles ne peuvent pas trouver de séquences UTF valides dans une chaîne d'octets arbitraire à moins que ces séquences ne soient correctement alignées.
