CORRESPONDANCE PARTIELLE DANS PCRE

Dans l'utilisation normale de PCRE, si la chaîne sujet passée à une fonction de correspondance correspond jusqu'à un certain point, mais est trop courte pour correspondre entièrement au motif, PCRE_ERROR_NOMATCH est renvoyé. Il peut être utile dans certaines circonstances de distinguer ce cas des autres cas où il n'y a pas de correspondance.

Considérez, par exemple, une application où un humain doit saisir des données pour un champ avec des exigences de formatage spécifiques. Un exemple pourrait être une date sous la forme jjmmaaa, définie par ce motif :


^\d?\d(jan|fév|mar|avr|mai|jui|jui|aoû|sep|oct|nov|déc)\d\d$

Si l'application voit les frappes de l'utilisateur une par une, et peut vérifier que ce qui a été tapé jusqu'à présent est potentiellement valide, elle est capable de lever une erreur dès qu'une erreur est commise, en émettant un bip et en ne reflétant pas le caractère qui a été tapé, par exemple. Ce retour d'information immédiat est susceptible d'être une meilleure interface utilisateur qu'une vérification retardée jusqu'à ce que toute la chaîne soit entrée. La correspondance partielle peut également être utile lorsque la chaîne sujet est très longue et n'est pas entièrement disponible à la fois.

PCRE prend en charge la correspondance partielle au moyen des options PCRE_PARTIAL_SOFT et PCRE_PARTIAL_HARD, qui peuvent être définies lors de l'appel à l'une des fonctions de correspondance. Pour des raisons de compatibilité ascendante, PCRE_PARTIAL est synonyme de PCRE_PARTIAL_SOFT. La différence essentielle entre les deux options est de savoir si une correspondance partielle est préférée à une correspondance complète alternative, bien que les détails diffèrent entre les deux types de fonctions de correspondance. Si les deux options sont définies, PCRE_PARTIAL_HARD prend le dessus.

Si vous souhaitez utiliser la correspondance partielle avec du code optimisé à la volée, vous devez appeler pcre_study(), pcre16_study() ou pcre32_study() avec l'une ou l'autre de ces options :


PCRE_STUDY_JIT_PARTIAL_SOFT_COMPILE
PCRE_STUDY_JIT_PARTIAL_HARD_COMPILE

PCRE_STUDY_JIT_COMPILE doit également être défini si vous allez effectuer des correspondances non partielles sur le même motif. Si le mode d'étude JIT approprié n'a pas été défini pour une correspondance, le code de correspondance interprétatif est utilisé.

La définition d'une option de correspondance partielle désactive deux des optimisations standard de PCRE. PCRE se souvient de la dernière unité de données littérales dans un motif, et abandonne immédiatement la correspondance si elle n'est pas présente dans la chaîne sujet. Cette optimisation ne peut pas être utilisée pour une chaîne sujet qui pourrait ne correspondre que partiellement. Si le motif a été étudié, PCRE connaît la longueur minimale d'une chaîne correspondante, et ne prend pas la peine d'exécuter la fonction de correspondance sur des chaînes plus courtes. Cette optimisation est également désactivée pour la correspondance partielle.

CORRESPONDANCE PARTIELLE UTILISANT pcre_exec() OU pcre[16|32]_exec()

Une correspondance partielle se produit lors d'un appel à pcre_exec() ou pcre[16|32]_exec() lorsque la fin de la chaîne sujet est atteinte avec succès, mais que la correspondance ne peut pas se poursuivre car des caractères supplémentaires sont nécessaires. Cependant, au moins un caractère du sujet doit avoir été inspecté. Ce caractère n'a pas besoin de faire partie de la chaîne finale correspondante ; les assertions lookbehind et la séquence d'échappement \K fournissent des moyens d'inspecter les caractères précédant le début d'une sous-chaîne correspondante. La condition d'inspecter au moins un caractère existe car une chaîne vide peut toujours être mise en correspondance ; sans une telle restriction, il y aurait toujours une correspondance partielle d'une chaîne vide à la fin du sujet.

S'il y a au moins deux emplacements dans le vecteur des décalages lorsqu'une correspondance partielle est renvoyée, le premier emplacement est défini à l'offset du caractère le plus précoce qui a été inspecté. Pour plus de commodité, le deuxième décalage pointe vers la fin du sujet afin qu'une sous-chaîne puisse être facilement identifiée. S'il y a au moins trois emplacements dans le vecteur des décalages, le troisième emplacement est défini à l'offset du caractère où la correspondance a commencé.

Pour la majorité des motifs, le contenu du premier et du troisième emplacement sera le même. Cependant, pour les motifs qui contiennent des assertions lookbehind, ou qui commencent par \b ou \B, des caractères avant celui où la correspondance a commencé peuvent avoir été inspectés lors de l'exécution de la correspondance. Par exemple, considérez ce motif :


/(?<=abc)123/

Ce motif correspond à "123", mais uniquement s'il est précédé par "abc". Si la chaîne sujet est "xyzabc12", les deux premiers décalages après une correspondance partielle sont pour la sous-chaîne "abc12", car tous ces caractères ont été inspectés. Cependant, le troisième décalage est défini à 6, car c'est l'offset où la correspondance a commencé.

Ce qui se passe lorsqu'une correspondance partielle est identifiée dépend de l'option de correspondance partielle définie.

PCRE_PARTIAL_SOFT AVEC pcre_exec() OU pcre[16|32]_exec()

Si PCRE_PARTIAL_SOFT est défini lorsque pcre_exec() ou pcre[16|32]_exec() identifie une correspondance partielle, la correspondance partielle est mémorisée, mais la correspondance se poursuit normalement, et d'autres alternatives dans le motif sont essayées. Si aucune correspondance complète ne peut être trouvée, PCRE_ERROR_PARTIAL est renvoyé au lieu de PCRE_ERROR_NOMATCH.

Cette option est "douce" car elle préfère une correspondance complète à une correspondance partielle. Tous les différents éléments de correspondance dans un motif se comportent comme si la chaîne sujet était potentiellement complète. Par exemple, \z, \Z, et $ correspondent à la fin du sujet, comme d'habitude, et pour \b et \B la fin du sujet est traitée comme un non-alphanumérique.

S'il y a plus d'une correspondance partielle, la première qui a été trouvée fournit les données renvoyées. Considérez ce motif :


/123\w+X|dogY/

S'il est mis en correspondance avec la chaîne sujet "abc123dog", les deux alternatives échouent à correspondre, mais la fin du sujet est atteinte pendant la correspondance, donc PCRE_ERROR_PARTIAL est renvoyé. Les décalages sont définis à 3 et 9, identifiant "123dog" comme la première correspondance partielle trouvée. (Dans cet exemple, il y a deux correspondances partielles, car "dog" seul correspond partiellement à la deuxième alternative.)

PCRE_PARTIAL_HARD AVEC pcre_exec() OU pcre[16|32]_exec()

Si PCRE_PARTIAL_HARD est défini pour pcre_exec() ou pcre[16|32]_exec(), PCRE_ERROR_PARTIAL est renvoyé dès qu'une correspondance partielle est trouvée, sans continuer à rechercher d'éventuelles correspondances complètes. Cette option est "dure" car elle préfère une correspondance partielle antérieure à une correspondance complète ultérieure. Pour cette raison, on suppose que la fin de la chaîne sujet fournie peut ne pas être la véritable fin des données disponibles, et donc, si \z, \Z, \b, \B, ou $ sont rencontrés à la fin du sujet, le résultat est PCRE_ERROR_PARTIAL, à condition qu'au moins un caractère du sujet ait été inspecté.

La définition de PCRE_PARTIAL_HARD affecte également la manière dont les chaînes sujets UTF-8 et UTF-16 sont vérifiées pour leur validité. Normalement, une séquence invalide provoque l'erreur PCRE_ERROR_BADUTF8 ou PCRE_ERROR_BADUTF16. Cependant, dans le cas spécial d'un caractère tronqué à la fin du sujet, PCRE_ERROR_SHORTUTF8 ou PCRE_ERROR_SHORTUTF16 est renvoyé lorsque PCRE_PARTIAL_HARD est défini.

Comparaison des correspondances partielles dure et douce

La différence entre les deux options de correspondance partielle peut être illustrée par un motif tel que :


/dog(sbody)?/

Cela correspond soit à "dog", soit à "dogsbody", de manière gloutonne (c'est-à-dire qu'il préfère la chaîne la plus longue si possible). S'il est mis en correspondance avec la chaîne "dog" avec PCRE_PARTIAL_SOFT, il produit une correspondance complète pour "dog". Cependant, si PCRE_PARTIAL_HARD est défini, le résultat est PCRE_ERROR_PARTIAL. D'autre part, si le motif est rendu non glouton, le résultat est différent :


/dog(sbody)??/

Dans ce cas, le résultat est toujours une correspondance complète car elle est trouvée en premier, et la correspondance ne se poursuit jamais après avoir trouvé une correspondance complète. Il pourrait être plus facile de suivre cette explication en pensant aux deux motifs comme suit :


/dog(sbody)?/ équivaut à /dogsbody|dog/
/dog(sbody)??/ équivaut à /dog|dogsbody/

CORRESPONDANCE PARTIELLE AVEC PCRE_DFA_EXEC() OU PCRE[16|32]_DFA_EXEC()

Les fonctions DFA parcourent la chaîne sujet caractère par caractère, sans retour arrière, recherchant simultanément toutes les correspondances possibles. Si la fin du sujet est atteinte avant la fin du motif, il existe une possibilité de correspondance partielle, à condition qu'au moins un caractère ait été inspecté.

Lorsque PCRE_PARTIAL_SOFT est défini, PCRE_ERROR_PARTIAL n'est renvoyé que s'il n'y a eu aucune correspondance complète. Sinon, les correspondances complètes sont renvoyées. Cependant, si PCRE_PARTIAL_HARD est défini, une correspondance partielle a la priorité sur toutes les correspondances complètes. La portion de la chaîne qui a été inspectée lors de la découverte de la correspondance partielle la plus longue est définie comme la première chaîne correspondante, à condition qu'il y ait au moins deux emplacements dans le vecteur d'offsets.

Étant donné que les fonctions DFA recherchent toujours toutes les correspondances possibles, et qu'il n'y a pas de différence entre la répétition gourmande et non gourmande, leur comportement est différent de celui des fonctions standard lorsque PCRE_PARTIAL_HARD est défini. Prenons la chaîne "dog" mise en correspondance avec le motif non gourmand présenté ci-dessus :


/dog(sbody)??/

Alors que les fonctions standard s'arrêtent dès qu'elles trouvent la correspondance complète pour "dog", les fonctions DFA trouvent également la correspondance partielle pour "dogsbody", et la renvoient donc lorsque PCRE_PARTIAL_HARD est défini.

CORRESPONDANCE PARTIELLE ET LIMITES DE MOT

Si un motif se termine par l'une des séquences \b ou \B, qui testent les limites de mots, la correspondance partielle avec PCRE_PARTIAL_SOFT peut donner des résultats contre-intuitifs. Considérons ce motif :


/\bcat\b/

Cela met en correspondance "cat", à condition qu'il y ait une limite de mot à chaque extrémité. Si la chaîne sujet est "the cat", la comparaison du dernier "t" avec le caractère suivant ne peut pas avoir lieu, donc une correspondance partielle est trouvée. Cependant, la correspondance normale continue, et \b correspond à la fin du sujet lorsque le dernier caractère est une lettre, donc une correspondance complète est trouvée. Le résultat n'est donc *pas* PCRE_ERROR_PARTIAL. L'utilisation de PCRE_PARTIAL_HARD dans ce cas produit effectivement PCRE_ERROR_PARTIAL, car alors la correspondance partielle a la priorité.

MOTIFS ANCIENNEMENT RESTREINTS

Pour les versions de PCRE antérieures à la 8.00, en raison de la manière dont certaines optimisations internes étaient implémentées dans la fonction pcre_exec(), l'option PCRE_PARTIAL (prédécesseur de PCRE_PARTIAL_SOFT) ne pouvait pas être utilisée avec tous les motifs. À partir de la version 8.00, les restrictions ne s'appliquent plus, et la correspondance partielle peut être demandée pour n'importe quel motif.

Les éléments qui étaient autrefois restreints étaient les caractères singuliers répétés et les métaséquences répétées. Si PCRE_PARTIAL était défini pour un motif qui ne respectait pas les restrictions, pcre_exec() renvoyait le code d'erreur PCRE_ERROR_BADPARTIAL (-13). Ce code d'erreur n'est plus utilisé. L'appel PCRE_INFO_OKPARTIAL à pcre_fullinfo() pour savoir si un motif compilé peut être utilisé pour une correspondance partielle renvoie désormais toujours 1.

EXEMPLE DE CORRESPONDANCE PARTIELLE AVEC PCRETEST

Si la séquence d'échappement \P est présente dans une ligne de données pcretest, l'option PCRE_PARTIAL_SOFT est utilisée pour la correspondance. Voici une exécution de pcretest qui utilise l'exemple de date cité ci-dessus :


re> /^\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d$/
data> 25jun04\P
0: 25jun04
1: jun
data> 25dec3\P
Partial match: 23dec3
data> 3ju\P
Partial match: 3ju
data> 3juj\P
No match
data> j\P
No match

La première chaîne de données est mise en correspondance complètement, donc pcretest affiche les sous-chaînes mises en correspondance. Les quatre chaînes restantes ne correspondent pas au motif complet, mais les deux premières sont des correspondances partielles. Une sortie similaire est obtenue si la correspondance DFA est utilisée.

Si la séquence d'échappement \P est présente plus d'une fois dans une ligne de données pcretest, l'option PCRE_PARTIAL_HARD est définie pour la correspondance.

CORRESPONDANCE MULTI-SEGMENTS AVEC PCRE_DFA_EXEC() OU PCRE[16|32]_DFA_EXEC()

Lorsqu'une correspondance partielle a été trouvée à l'aide d'une fonction de correspondance DFA, il est possible de continuer la correspondance en fournissant des données sujet supplémentaires et en appelant à nouveau la fonction avec la même expression régulière compilée, en définissant cette fois l'option PCRE_DFA_RESTART. Vous devez passer le même espace de travail qu'auparavant, car c'est là que sont stockés les détails de la correspondance partielle précédente. Voici un exemple utilisant pcretest, avec la séquence d'échappement \R pour définir l'option PCRE_DFA_RESTART (\D spécifie l'utilisation de la fonction de correspondance DFA) :


re> /^\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d$/
data> 23ja\P\D
Partial match: 23ja
data> n05\R\D
0: n05

Le premier appel a "23ja" comme sujet, et demande une correspondance partielle ; le second appel a "n05" comme sujet pour la correspondance continuée (redémarrée). Notez que lorsque la correspondance est complète, seule la dernière partie est affichée ; PCRE ne conserve pas la chaîne partiellement correspondante précédente. Il incombe au programme appelant de le faire s'il en a besoin.

Cela signifie que, pour un motif non ancré, si une correspondance continuée échoue, il n'est pas possible de réessayer à un nouveau point de départ. Tout ce que cette facilité peut faire est de continuer la tentative de correspondance précédente. Dans l'exemple précédent, si le deuxième jeu de données est "ug23", le résultat est aucune correspondance, même s'il y aurait une correspondance pour "aug23" si toute la chaîne était fournie en une seule fois. Selon l'application, cela peut être ce que vous voulez ou non. La seule façon de permettre de recommencer au caractère suivant est de conserver la partie correspondante du sujet et d'essayer une nouvelle correspondance complète.

Vous pouvez définir les options PCRE_PARTIAL_SOFT ou PCRE_PARTIAL_HARD avec PCRE_DFA_RESTART pour continuer la correspondance partielle sur plusieurs segments. Cette facilité peut être utilisée pour passer de très longues chaînes sujet aux fonctions de correspondance DFA.

CORRESPONDANCE MULTI-SEGMENTS AVEC PCRE_EXEC() OU PCRE[16|32]_EXEC()

À partir de la version 8.00, les fonctions de correspondance standard peuvent également être utilisées pour effectuer des correspondances multi-segments. Contrairement aux fonctions DFA, il n'est pas possible de redémarrer la correspondance précédente avec un nouveau segment de données. Au lieu de cela, de nouvelles données doivent être ajoutées à la chaîne sujet précédente, et le processus de correspondance complet doit être relancé, en partant du point où la correspondance partielle s'est produite. Les données antérieures peuvent être supprimées.

Il est préférable d'utiliser PCRE_PARTIAL_HARD dans cette situation, car elle ne traite pas la fin d'un segment comme la fin du sujet lors de la correspondance de \z, \Z, \b, \B et $. Considérons un motif non ancré qui correspond aux dates :


re> /\d?\d(jan|feb|mar|apr|may|jun|jul|aug|sep|oct|nov|dec)\d\d/
data> The date is 23ja\P\P
Partial match: 23ja

À ce stade, une application pourrait supprimer le texte précédant "23ja", ajouter du texte du segment suivant, et appeler à nouveau la fonction de correspondance. Contrairement aux fonctions de correspondance DFA, toute la chaîne de correspondance doit toujours être disponible, et le processus de correspondance complet se déroule pour chaque appel, nécessitant donc plus de mémoire et plus de temps de traitement.

Note: Si le motif contient des assertions de recherche en arrière (lookbehind), ou \K, ou commence par \b ou \B, la chaîne qui est renvoyée pour une correspondance partielle inclut des caractères qui précèdent le début de ce qui serait renvoyé pour une correspondance complète, car elle contient tous les caractères qui ont été inspectés pendant la correspondance partielle.

PROBLÈMES AVEC LA CORRESPONDANCE MULTI-SEGMENTS

Certains types de motifs peuvent poser des problèmes avec la correspondance multi-segments, quelle que soit la fonction de correspondance utilisée.

1. Si le motif contient un test pour le début d'une ligne, vous devez transmettre l'option PCRE_NOTBOL lorsque la chaîne sujet de n'importe quel appel commence effectivement au début d'une ligne. Il existe également une option PCRE_NOTEOL, mais en pratique, lors de la correspondance multi-segments, vous devriez utiliser PCRE_PARTIAL_HARD, qui inclut l'effet de PCRE_NOTEOL.

2. Les assertions de recherche en arrière qui ont déjà été respectées sont prises en compte dans les offsets renvoyés pour une correspondance partielle. Cependant, une assertion de recherche en arrière plus loin dans le motif pourrait nécessiter l'inspection de caractères encore plus en arrière. Vous pouvez gérer ce cas en utilisant l'option PCRE_INFO_MAXLOOKBEHIND des fonctions pcre_fullinfo() ou pcre[16|32]_fullinfo() pour obtenir la longueur du plus long lookbehind dans le motif. Cette longueur est donnée en caractères, pas en octets. Si vous conservez toujours au moins ce nombre de caractères avant la chaîne partiellement correspondante, tout devrait bien se passer. (Bien sûr, près du début du sujet, moins de caractères peuvent être présents ; dans ce cas, tous les caractères doivent être conservés.)

À partir de la version 8.33, il existe une manière plus précise de décider quels caractères conserver. Au lieu de soustraire la longueur du plus long lookbehind du premier caractère inspecté (offsets[0]), la position de départ de la correspondance (offsets[2]) doit être utilisée, et la tentative de correspondance suivante doit être démarrée au caractère offsets[2] en définissant l'argument startoffset de pcre_exec() ou pcre_dfa_exec().

Par exemple, si le motif "(?<=123)abc" est mis en correspondance partielle avec la chaîne "xx123a", les trois valeurs d'offset renvoyées sont 2, 6 et 5. Cela indique que le processus de correspondance qui a donné une correspondance partielle a commencé à l'offset 5, mais que les caractères "123a" ont tous été inspectés. Le lookbehind maximum pour ce motif est de 3, donc en le soustrayant de 5, on constate que nous devons seulement conserver "123a", et la tentative de correspondance suivante peut être démarrée à l'offset 3 (c'est-à-dire à "a") lorsque des caractères supplémentaires ont été ajoutés. NAME

pcrepartial - Partial matching in PCRE

PARTIAL MATCHING IN PCRE

When PCRE is used for matching a subject string, it can operate in two modes: a standard mode and a partial matching mode. In the standard mode, a match is only reported if the whole pattern matches some substring of the subject. In partial matching mode, a match is reported if the pattern matches a substring that starts at the beginning of the subject, but does not necessarily end there.

There are two kinds of partial matching:

  • PCRE_PARTIAL_HARD: In this mode, a match is reported if the pattern matches any substring of the subject, starting at the beginning of the subject, and ending at any position within the subject. This is the default for pcre_exec() and pcre_dfa_exec() when no completed match is found that starts at the beginning of the subject.
  • PCRE_PARTIAL_SOFT: In this mode, a match is only reported if the pattern matches a substring that starts at the beginning of the subject and ends at the end of the subject. If a completed match is found that starts at the beginning of the subject, but does not end at the end of the subject, it is not reported. This mode is intended for use with DFA matching functions only.

The pcretest utility uses partial matching in order to allow the user to type the subject string piece by piece. The pcretest output conventions are:

  • Partial match: ... means that the option PCRE_PARTIAL_SOFT was set, and a partial match was found.
  • No match means that no partial match was found.

The following sections describe the behaviour of partial matching in more detail.

PARTIAL MATCHING USING pcre_exec() OR pcre[16|32]_exec()

When pcre_exec() (or its 16-bit or 32-bit counterparts) is called with the PCRE_PARTIAL flag set, it checks for matches that start at the beginning of the subject string. If a completed match is found, it is returned. If no completed match is found, it checks for a partial match. A partial match is one that starts at the beginning of the subject string, but does not necessarily end there. If a partial match is found, the function returns PCRE_ERROR_PARTIAL, and the substring that matched is returned in the match vector.

If the pattern contains lookarounds, the behaviour can be subtle. Consider the pattern /abc(?<=123)/ applied to the subject string "xx123abc". The lookbehind (?<=123) asserts that the preceding characters are 123. The pattern itself requires that the characters following the lookbehind are abc. In this case, the pattern matches the substring "abc" starting at offset 5. However, the lookbehind requires that the string preceding the match is "123". Since the match starts at offset 5, the preceding characters are "xx123". The lookbehind fails, and no match is found.

If the subject string is "123abc", the pattern matches "abc" starting at offset 3. The preceding characters are "123", which satisfies the lookbehind. A match is found.

If the subject string is "123a" and the PCRE_PARTIAL flag is set, the function searches for a partial match. The pattern /abc(?<=123)/ does not match at the beginning of the string. However, if we consider the lookbehind, it matches "123" at offset 0. The pattern itself requires abc to follow. Since only a follows, the pattern does not match. However, the function returns PCRE_ERROR_PARTIAL because there is a potential match starting at offset 0, but it is not a completed match.

If the subject string is "123" and the pattern is /abc(?<=123)/, the lookbehind matches "123" at offset 0. However, there are no characters following the lookbehind, so the pattern abc cannot match. The function returns PCRE_ERROR_PARTIAL.

Partial matches are only possible if the pattern contains lookarounds. If the pattern does not contain lookarounds, then a partial match is only reported if the pattern matches a substring starting at the beginning of the subject string.

PARTIAL MATCHING USING pcre_dfa_exec() OR pcre[16|32]_dfa_exec()

When pcre_dfa_exec() (or its 16-bit or 32-bit counterparts) is called with the PCRE_PARTIAL flag set, it behaves similarly to pcre_exec(). It searches for matches starting at the beginning of the subject string. If a completed match is found, it is returned. If no completed match is found, it checks for a partial match. A partial match is one that starts at the beginning of the subject string, but does not necessarily end there. If a partial match is found, the function returns PCRE_ERROR_PARTIAL, and the substring that matched is returned in the match vector.

The PCRE_PARTIAL_SOFT option is intended for use with DFA matching only. When this option is set, a partial match is only reported if the pattern matches a substring that starts at the beginning of the subject string and ends at the end of the subject string. If a completed match is found that starts at the beginning of the subject string but does not end at the end of the subject string, it is not reported.

PARTIAL MATCHING AND WORD BOUNDARIES

When matching with the PCRE_PARTIAL flag, problems can arise if the pattern ends with a word boundary assertion, such as \b or \B. A word boundary occurs at the position between a word character and a non-word character, or at the beginning/end of the string if the first/last character is a word character.

Consider the pattern /word\b/ and the subject string "wordA". A partial match is found, consisting of "word". The word boundary assertion is met because the character following "word" is 'A', which is a non-word character.

Now consider the pattern /word\b/ and the subject string "word". A partial match is found, consisting of "word". The word boundary assertion is met because the match ends at the end of the string, and the last character 'd' is a word character.

However, if the subject string is split into multiple segments, problems can arise. For example, if the subject is "word" and is presented in two parts: "wor" and "d". When matching the first part, "wor", no partial match is found. When matching the second part, "d", a partial match is found consisting of "d". The word boundary assertion is met because the match ends at the end of the string, and the last character 'd' is a word character.

This behaviour is inconsistent with matching the entire string "word" as a single unit. To ensure consistent behaviour when matching multi-segment data, it is recommended to use PCRE_PARTIAL_HARD.

FORMERLY RESTRICTED PATTERNS

In earlier versions of PCRE, patterns containing certain constructs were restricted when partial matching was enabled. These restrictions have now been removed.

The restrictions were related to lookarounds and word boundaries. Specifically, patterns that contained lookarounds or word boundary assertions at the end of the pattern were not allowed to be used with partial matching. This was because it was difficult to determine whether a partial match could be extended to a full match.

These restrictions have now been lifted, and such patterns can be used with partial matching. However, it is important to understand the behaviour of partial matching in these cases.

EXAMPLE OF PARTIAL MATCHING USING PCRETEST

The following example demonstrates the use of partial matching with pcretest.


re> /dog(sbody)?/
data> dogsb\P
0: dog
data> do\P\D
Partial match: do
data> gsb\R\P\D
0: g
data> dogsbody\D
0: dogsbody
1: dog

In this example, the pattern is /dog(sbody)?/. The subject string is "dogsb". The pcretest utility is used to interactively test the pattern against the subject. The \P represents a newline character, and \D represents the end of the input.

When the input is "dogsb", a complete match is found: "dog".

When the input is "do", a partial match is found: "do". This is because the pattern can potentially match "dog", but it has not yet reached the end of the pattern.

When the input is "gsb", a complete match is found: "gsb". This is because the pattern can match "dog" followed by "sbody", and the input provides the "sbody" part.

When the input is "dogsbody", two matches are found: "dogsbody" and "dog".

MULTI-SEGMENT MATCHING WITH pcre_dfa_exec() OR pcre[16|32]_dfa_exec()

When matching a subject string that is split into multiple segments, especially when using PCRE_PARTIAL_SOFT, the results may differ from matching a single, contiguous string. This is because the DFA matching algorithm stops as soon as the shortest possible match is found. If a partial match is found, the algorithm cannot continue to find longer matches or matches in subsequent segments.

For example, consider the pattern /dog(sbody)?/ and the subject string "dogsb". If this string is presented in multiple segments, the DFA algorithm might find a partial match for "dog" early on. Since this is a complete match, the algorithm stops and does not continue to search for potential longer matches like "dogsbody".

This can lead to unexpected results when processing data that is received in chunks or streams.

MULTI-SEGMENT MATCHING WITH pcre_exec() OR pcre[16|32]_exec()

When using the standard matching function pcre_exec() with partial matching, the behaviour is generally more predictable than with the DFA matching functions. However, issues can still arise, particularly when dealing with lookarounds and word boundaries.

For instance, if a pattern ends with \b or \B, and the subject string is split across multiple segments, the word boundary check might yield different results depending on where the segment break occurs. This is because the definition of a word boundary depends on the characters immediately surrounding the match position.

If the pattern contains alternatives that do not share a common prefix, and PCRE_DFA_RESTART is used, it may not work as expected. This is because the DFA matching algorithm might find a partial match for one alternative, and then fail to find a match for another alternative starting at the same position.

ISSUES WITH MULTI-SEGMENT MATCHING

Matching a subject string that is split into multiple segments can introduce complexities, especially when using partial matching. The core issue stems from how the matching engine interprets the boundaries between segments.

1. Word Boundaries:

As discussed, patterns ending in \b or \B can behave unpredictably. A word boundary depends on the adjacent character. If a segment break occurs at that point, the character might be missing or different, leading to a different outcome.

2. Alternatives with Different Starting Items:

Consider a pattern like /abc|def/. If the subject starts with "ab", a partial match for the first alternative (abc) is found. If the next segment starts with "c", the match for abc is completed. However, if the next segment starts with "xyz", and the pattern was actually /abc|xyz/, the match for abc might be abandoned, and the engine might then try to match xyz from the beginning of the second segment. This behaviour can be complex to manage.

3. Partial match of an empty string:

A partial match must always contain at least one character. This means that what might seem like a partial match of an empty string will result in "no match". For example:


re> /c(?<=abc)x/
data> ab\P
No match

If the next segment starts with "cx", a match should be found. This requires that characters from the previous segment are retained. Therefore, a "no match" result should be interpreted as a "partial match of an empty string" when the pattern contains lookbehinds.

4. Matching behaviour differences between standard and DFA matching:

Matching a multi-segment subject string may not yield the same results as matching a single, long string, particularly with PCRE_PARTIAL_SOFT. The section "Partial Matching and Word Boundaries" above describes an issue with patterns ending in \b or \B. Another difference can occur with multiple matching possibilities. With PCRE_PARTIAL_SOFT, a partial match result is only given if there are no completed matches. This means that as soon as the shortest match is found, continuation to a new subject segment is not possible.

Consider this pcretest example:


re> /dog(sbody)?/
data> dogsb\P
0: dog
data> do\P\D
Partial match: do
data> gsb\R\P\D
0: g
data> dogsbody\D
0: dogsbody
1: dog

The first data line passes "dogsb" to a standard matching function with PCRE_PARTIAL_SOFT. Although "dogsb" is a partial match for "dogsbody", the result is not PCRE_ERROR_PARTIAL, because the shorter string "dog" is a complete match. Similarly, when the subject is presented to a DFA matching function in several parts ("do" and "gsb" being the first two), the match stops when "dog" has been found, and it is not possible to continue. On the other hand, if "dogsbody" is presented as a single string, a DFA matching function finds both matches.

Because of these issues, it is best to use PCRE_PARTIAL_HARD when matching multi-segment data. The example above then behaves differently:


re> /dog(sbody)?/
data> dogsb\P\P
Partial match: dogsb
data> do\P\D
Partial match: do
data> gsb\R\P\P\D
Partial match: gsb

5. Patterns with alternatives not starting with the same item:

Patterns that contain alternatives at the top level which do not all start with the same pattern item may not work as expected when PCRE_DFA_RESTART is used. For example, consider this pattern:


1234|3789

If the first part of the subject is "ABC123", a partial match of the first alternative is found at offset 3. There is no partial match for the second alternative, because such a match does not start at the same point in the subject string. Attempting to continue with the string "7890" does not yield a match because only those alternatives that match at one point in the subject are remembered. The problem arises because the start of the second alternative matches within the first alternative. There is no problem with anchored patterns or patterns such as:


1234|ABCD

where no string can be a partial match for both alternatives. This is not a problem if a standard matching function is used, because the entire match has to be rerun each time:


re> /1234|3789/
data> ABC123\P\P
Partial match: 123
data> 1237890
0: 3789

Of course, instead of using PCRE_DFA_RESTART, the same technique of re-running the entire match can also be used with the DFA matching functions. Another possibility is to work with two buffers. If a partial match at offset n in the first buffer is followed by "no match" when PCRE_DFA_RESTART is used on the second buffer, you can then try a new match starting at offset n+1 in the first buffer.
