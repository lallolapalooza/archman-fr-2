PCREPOSIX(3) Manuel des fonctions de bibliothèque PCREPOSIX(3)

NOM

PCREPOSIX - expressions régulières compatibles Perl.

SYNTAXE

#include <pcreposix.h>

int regcomp(regex_t *preg, const char *pattern,
     int cflags);

int regexec(regex_t *preg, const char *string,
     size_t nmatch, regmatch_t pmatch[], int eflags);
     size_t regerror(int errcode, const regex_t *preg,
     char *errbuf, size_t errbuf_size);

void regfree(regex_t *preg);

DESCRIPTION

Cet ensemble de fonctions fournit une API de style POSIX pour la bibliothèque d'expressions régulières PCRE 8 bits. Voir la documentation de pcreapi pour une description de l'API native de PCRE, qui contient de nombreuses fonctionnalités supplémentaires. Il n'y a pas de wrapper de style POSIX pour la bibliothèque PCRE 16 bits et 32 bits.

Les fonctions décrites ici ne sont que des fonctions d'enrobage qui appellent finalement l'API native de PCRE. Leurs prototypes sont définis dans le fichier d'en-tête pcreposix.h, et sur les systèmes Unix, la bibliothèque elle-même s'appelle pcreposix.a, elle peut donc être accédée en ajoutant -lpcreposix à la commande de liaison d'une application qui les utilise. Comme les fonctions POSIX appellent les fonctions natives, il est également nécessaire d'ajouter -lpcre.

Je n'ai implémenté que les bits d'option POSIX qui peuvent être raisonnablement mappés aux options natives de PCRE. De plus, l'option REG_EXTENDED est définie avec la valeur zéro. Cela n'a aucun effet, mais comme les programmes écrits pour l'interface POSIX l'utilisent souvent, cela facilite l'intégration de PCRE comme bibliothèque de remplacement. D'autres options POSIX ne sont même pas définies.

Il existe également d'autres options qui ne sont pas définies par POSIX. Celles-ci ont été ajoutées à la demande d'utilisateurs qui souhaitent utiliser certaines fonctionnalités spécifiques à PCRE via l'interface d'appel POSIX.

Lorsque PCRE est appelé via ces fonctions, seule l'API est de style POSIX. La syntaxe et la sémantique des expressions régulières elles-mêmes restent celles de Perl, sous réserve du réglage de diverses options PCRE, comme décrit ci-dessous. « De style POSIX » signifie que l'API s'approxime à la définition POSIX ; elle n'est pas entièrement compatible POSIX, et dans les domaines d'encodage multi-octets, elle est probablement encore moins compatible.

L'en-tête pour ces fonctions est fourni sous le nom pcreposix.h afin d'éviter tout conflit potentiel avec d'autres bibliothèques POSIX. Il peut, bien sûr, être renommé ou aliasé en regex.h, qui est le nom « correct ». Il fournit deux types de structures, regex_t pour les formes internes compilées, et regmatch_t pour retourner les sous-chaînes capturées. Il définit également certaines constantes dont les noms commencent par « REG_ » ; ceux-ci sont utilisés pour définir les options et identifier les codes d'erreur.

COMPILATION D'UN MOTIF

La fonction regcomp() est appelée pour compiler un motif en une forme interne. Le motif est une chaîne C terminée par un zéro binaire, et est passé dans l'argument pattern. L'argument preg est un pointeur vers une structure regex_t qui est utilisée comme base pour stocker les informations sur l'expression régulière compilée.

L'argument cflags est soit zéro, soit contient un ou plusieurs des bits définis par les macros suivantes :


REG_DOTALL

L'option PCRE_DOTALL est définie lorsque l'expression régulière est passée pour compilation à la fonction native. Notez que REG_DOTALL ne fait pas partie de la norme POSIX.


REG_ICASE

L'option PCRE_CASELESS est définie lorsque l'expression régulière est passée pour compilation à la fonction native.


REG_NEWLINE

L'option PCRE_MULTILINE est définie lorsque l'expression régulière est passée pour compilation à la fonction native. Notez que cela ne reproduit pas le comportement POSIX défini pour REG_NEWLINE (voir la section suivante).


REG_NOSUB

L'option PCRE_NO_AUTO_CAPTURE est définie lors de la compilation de l'expression régulière dans la fonction native. De plus, lorsqu'un motif compilé avec ce drapeau est passé à regexec() pour une correspondance, les arguments nmatch et pmatch sont ignorés, et aucune chaîne capturée n'est retournée.


REG_UCP

L'option PCRE_UCP est définie lors de la compilation de l'expression régulière pour la fonction native. Cela amène PCRE à utiliser les propriétés Unicode lors de la correspondance de \d, \w, etc., au lieu de ne reconnaître que les valeurs ASCII. Notez que REG_UTF8 ne fait pas partie de la norme POSIX.


REG_UNGREEDY

L'option PCRE_UNGREEDY est définie lors de la compilation de l'expression régulière pour la fonction native. Notez que REG_UNGREEDY ne fait pas partie de la norme POSIX.


REG_UTF8

L'option PCRE_UTF8 est définie lors de la compilation de l'expression régulière pour la fonction native. Cela amène le motif lui-même et toutes les chaînes de données utilisées pour le faire correspondre à être traités comme des chaînes UTF-8. Notez que REG_UTF8 ne fait pas partie de la norme POSIX.

En l'absence de ces drapeaux, aucune option n'est passée à la fonction native. Cela signifie que l'expression régulière est compilée avec la sémantique par défaut de PCRE. En particulier, la façon dont elle gère les caractères de nouvelle ligne dans la chaîne sujet est la manière Perl, pas la manière POSIX. Notez que le réglage de PCRE_MULTILINE n'a que certains des effets spécifiés pour REG_NEWLINE. Il n'affecte pas la façon dont les sauts de ligne sont mis en correspondance par . (ils ne le sont pas) ou par une classe négative comme [^a] (ils le sont).

Le rendement de regcomp() est zéro en cas de succès, et non nul sinon. La structure preg est remplie en cas de succès, et un membre de la structure est public : re_nsub contient le nombre de sous-motifs de capture dans l'expression régulière. Divers codes d'erreur sont définis dans le fichier d'en-tête.

NOTE : Si le rendement de regcomp() est non nul, vous ne devez pas tenter d'utiliser le contenu de la structure preg. Si, par exemple, vous la passez à regexec(), le résultat est indéfini et votre programme risque de planter.

MISE EN CORRESPONDANCE DES CARACTÈRES DE NOUVELLE LIGNE

Ce domaine n'est pas simple, car POSIX et Perl ont des vues différentes sur les choses. Il n'est pas possible d'amener PCRE à obéir à la sémantique POSIX, mais PCRE n'a jamais été conçu pour être un moteur POSIX. Le tableau suivant répertorie les différentes possibilités de mise en correspondance des caractères de nouvelle ligne dans PCRE :


Par défaut Changement avec


. met en correspondance une nouvelle ligne non PCRE_DOTALL
nouvelle ligne met en correspondance [^a] oui non modifiable
$ met en correspondance \n à la fin oui PCRE_DOLLARENDONLY
$ met en correspondance \n au milieu non PCRE_MULTILINE
^ met en correspondance \n au milieu non PCRE_MULTILINE

Ceci est le tableau équivalent pour POSIX :


Par défaut Changement avec


. met en correspondance une nouvelle ligne oui REG_NEWLINE
nouvelle ligne met en correspondance [^a] oui REG_NEWLINE
$ met en correspondance \n à la fin non REG_NEWLINE
$ met en correspondance \n au milieu non REG_NEWLINE
^ met en correspondance \n au milieu non REG_NEWLINE

Le comportement de PCRE est le même que celui de Perl, sauf qu'il n'y a pas d'équivalent pour PCRE_DOLLAR_ENDONLY dans Perl. Dans PCRE et Perl, il n'y a aucun moyen d'empêcher la nouvelle ligne de correspondre à [^a].

La gestion par défaut des nouvelles lignes POSIX peut être obtenue en définissant PCRE_DOTALL et PCRE_DOLLARENDONLY, mais il n'y a aucun moyen de faire en sorte que PCRE se comporte exactement comme pour l'action REG_NEWLINE.

MISE EN CORRESPONDANCE D'UN MOTIF

La fonction regexec() est appelée pour faire correspondre un motif compilé preg à une chaîne donnée, qui est par défaut terminée par un octet nul (mais voir REG_STARTEND ci-dessous), sous réserve des options dans eflags. Celles-ci peuvent être :


REG_NOTBOL

L'option PCRE_NOTBOL est définie lors de l'appel de la fonction de correspondance PCRE sous-jacente.


REG_NOTEMPTY

L'option PCRE_NOTEMPTY est définie lors de l'appel de la fonction de correspondance PCRE sous-jacente. Notez que REG_NOTEMPTY ne fait pas partie de la norme POSIX. Cependant, définir cette option peut donner un comportement plus proche de POSIX dans certaines situations.


REG_NOTEOL

L'option PCRE_NOTEOL est définie lors de l'appel de la fonction de correspondance PCRE sous-jacente.


REG_STARTEND

La chaîne est considérée comme commençant à string + pmatch[0].rm_so et ayant une terminaison

pcreposix

This is a manual page for the PCRE library, which is a set of C functions that provide Perl-compatible regular expression matching. PCRE is a re-entrant, modular library that can be linked to or loaded in dynamically.

The PCRE library is a popular, powerful, and widely used library for handling regular expressions. It aims to provide Perl-compatible regular expression syntax and semantics. This man page (specifically `pcreposix`) is part of the PCRE documentation and focuses on the POSIX-like API provided by the library.

Key Sections and Concepts:

regcomp(): Compiling a pattern.
This section would describe how to compile a regular expression string into an internal representation that can be used for matching. It likely involves a structure (e.g., `regex_t`) to hold the compiled pattern and various compilation flags.
regexec(): Matching a pattern.
This section details the function used to match a compiled regular expression against a given string. It would explain parameters like the compiled pattern, the string to search, the maximum number of matches, and where to store the results (e.g., an array of `regmatch_t` structures).
regmatch_t: Structure for match results.
This structure (with members `rm_so` and `rm_eo`) is used to report the start and end offsets of matched substrings within the input string. The `rm_so` member indicates the offset to the first character of a substring, and `rm_eo` indicates the offset to the first character *after* the end of the substring.
REG_NOSUB: Flag for disabling substring captures.
When this flag is used during compilation or execution, the function will not return information about captured substrings, simplifying the process if only a match/no-match result is needed.
REG_STARTEND: Flag for start and end anchors.
This flag affects how the beginning and end of the string are treated for anchoring purposes (like `^` and `$`), but it does not change the *location* of the string itself. It's noted as a BSD extension and should be used cautiously for portability.
regerror(): Getting error messages.
This function translates error codes returned by `regcomp` or `regexec` into human-readable error messages. It takes an error code, a buffer to store the message, and the buffer size.
regfree(): Freeing memory.
After a compiled regular expression is no longer needed, `regfree` should be called to release the memory allocated during compilation. Using the compiled pattern after calling `regfree` results in undefined behavior.
Author and Revision: Standard man page information.
Details about the author(s) and the last revision date of the manual page, along with copyright information.

Example Snippet Interpretation:

The provided text specifically discusses the behavior of `regexec` when `REG_STARTEND` is used:

  • It clarifies that `REG_STARTEND` (if supported and enabled) allows the `rm_so` and `rm_eo` members of the `regmatch_t` structure to specify the start and end of the substring *within the original input string*.
  • It emphasizes that `rm_eo` points to the position *after* the matched substring, and the *actual* location of a NUL terminator isn't relevant; the offset is what matters.
  • It mentions that `REG_STARTEND` is a BSD extension and might affect portability.
  • It clarifies that `REG_STARTEND` does *not* imply `REG_NOTBOL`; it only affects the reported location, not how anchors like `^` behave.

It also covers scenarios where no substring data is returned:

  • If the pattern was compiled with `REG_NOSUB`.
  • If `nmatch` is zero or `pmatch` is NULL.

Otherwise, it explains that `pmatch` (an array of `regmatch_t`) will be populated with the offsets for the entire match (element 0) and captured subpatterns (subsequent elements). Unused entries are set to -1.

A successful match returns 0, while `REG_NOMATCH` is the expected return value for a failed match.

Error Messages

The `regerror()` function converts error codes into printable strings, storing them in a provided buffer (`errbuf`) up to a specified size (`errbuf_size`). The return value indicates the required buffer size.

Memory Usage

Compiling a regex allocates memory associated with the `regex_t` structure. `regfree()` must be used to deallocate this memory when it's no longer needed.
