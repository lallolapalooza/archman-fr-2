BIBLIOTHÈQUES PCRE 8 BIT, 16 BIT, ET 32 BIT

En plus de la prise en charge des chaînes de caractères 8 bits, PCRE prend également en charge les chaînes 16 bits (à partir de la version 8.30) et 32 bits (à partir de la version 8.32), au moyen de deux bibliothèques supplémentaires. Elles peuvent être construites en même temps que, ou à la place de, la bibliothèque 8 bits. Pour éviter trop de complications, ce document décrit les versions 8 bits des fonctions, avec seulement des références occasionnelles aux bibliothèques 16 bits et 32 bits.

Les fonctions 16 bits et 32 bits fonctionnent de la même manière que leurs homologues 8 bits ; elles utilisent simplement des types de données différents pour leurs arguments et leurs résultats, et leurs noms commencent par pcre16_ ou pcre32_ au lieu de pcre_. Pour chaque option dont le nom contient UTF8 (par exemple, PCRE_UTF8), il existe des noms 16 bits et 32 bits correspondants avec UTF8 remplacé par UTF16 ou UTF32, respectivement. Cette fonctionnalité est en fait juste cosmétique ; les noms d'options 16 bits et 32 bits définissent les mêmes valeurs de bits.

Les références aux octets et à UTF-8 dans ce document doivent être lues comme des références aux unités de données 16 bits et UTF-16 lors de l'utilisation de la bibliothèque 16 bits, ou aux unités de données 32 bits et UTF-32 lors de l'utilisation de la bibliothèque 32 bits, sauf indication contraire. Plus de détails sur les différences spécifiques pour les bibliothèques 16 bits et 32 bits sont donnés dans les pages pcre16 et pcre32.

APERÇU DE L'API PCRE

PCRE possède sa propre API native, qui est décrite dans ce document. Il existe également des fonctions d'encapsulation (pour la bibliothèque 8 bits uniquement) qui correspondent à l'API d'expressions régulières POSIX, mais elles ne donnent pas accès à toutes les fonctionnalités. Elles sont décrites dans la documentation pcreposix. Ces deux API définissent un ensemble d'appels de fonction C. Un wrapper C++ (également pour la bibliothèque 8 bits uniquement) est également distribué avec PCRE. Il est documenté dans la page pcrecpp.

Les prototypes de fonctions C de l'API native sont définis dans le fichier d'en-tête pcre.h, et sur les systèmes de type Unix, la bibliothèque (8 bits) s'appelle normalement libpcre. Elle peut normalement être accessible en ajoutant -lpcre à la commande de liaison d'une application qui utilise PCRE. Le fichier d'en-tête définit les macros PCRE_MAJOR et PCRE_MINOR pour contenir les numéros de version majeure et mineure de la bibliothèque. Les applications peuvent les utiliser pour inclure la prise en charge de différentes versions de PCRE.

Dans un environnement Windows, si vous souhaitez lier statiquement un programme d'application à un fichier pcre.a non-dll, vous devez définir PCRE_STATIC avant d'inclure pcre.h ou pcrecpp.h, car sinon les fonctions exportées pcre_malloc() et pcre_free() seront déclarées __declspec(dllimport), avec des résultats indésirables.

Les fonctions pcre_compile(), pcre_compile2(), pcre_study() et pcre_exec() sont utilisées pour compiler et faire correspondre des expressions régulières de manière compatible avec Perl. Un exemple de programme qui démontre la manière la plus simple de les utiliser est fourni dans le fichier appelé pcredemo.c dans la distribution source de PCRE. Une liste de ce programme est donnée dans la documentation pcredemo, et la documentation pcresample décrit comment le compiler et l'exécuter.

Le support du compilateur juste-à-temps est une fonctionnalité optionnelle de PCRE qui peut être intégrée dans des environnements matériels appropriés. Il accélère considérablement les performances de correspondance de nombreux modèles. Les programmes simples peuvent facilement demander son utilisation si elle est disponible, en définissant une option qui est ignorée lorsqu'elle n'est pas pertinente. Les programmes plus complexes peuvent avoir besoin d'utiliser les fonctions pcre_jit_stack_alloc(), pcre_jit_stack_free() et pcre_assign_jit_stack() afin de contrôler l'utilisation de la mémoire du code JIT.

À partir de la version 8.32, il existe également une interface directe pour l'exécution JIT, qui améliore les performances. Les fonctions spécifiques au JIT sont discutées dans la documentation pcrejit.

Une deuxième fonction de correspondance, pcre_dfa_exec(), qui n'est pas compatible Perl, est également fournie. Elle utilise un algorithme différent pour la correspondance. L'algorithme alternatif trouve toutes les correspondances possibles (à un point donné du sujet), et analyse le sujet une seule fois (sauf s'il y a des assertions lookbehind). Cependant, cet algorithme ne renvoie pas de sous-chaînes capturées. Une description des deux algorithmes de correspondance et de leurs avantages et inconvénients est donnée dans le document pcrematching.

FONCTIONS

En plus des fonctions principales de compilation et de mise en correspondance, il existe des fonctions pratiques pour extraire les sous-chaînes capturées d'une chaîne sujet mise en correspondance par pcre_exec(). Ce sont:


pcre_copy_substring()
pcre_copy_named_substring()
pcre_get_substring()
pcre_get_named_substring()
pcre_get_substring_list()
pcre_get_stringnumber()
pcre_get_stringtable_entries()

pcre_free_substring() et pcre_free_substring_list() sont également fournis, pour libérer la mémoire utilisée pour les chaînes extraites.

La fonction pcre_maketables() est utilisée pour construire un ensemble de tables de caractères dans la locale courante, à passer à pcre_compile(), pcre_exec(), ou pcre_dfa_exec(). Ceci est une fonctionnalité optionnelle fournie pour un usage spécialisé. Le plus souvent, aucune table spéciale n'est passée, dans quel cas les tables internes générées lors de la construction de PCRE sont utilisées.

La fonction pcre_fullinfo() est utilisée pour obtenir des informations sur un motif compilé. La fonction pcre_version() renvoie un pointeur vers une chaîne contenant la version de PCRE et sa date de publication.

La fonction pcre_refcount() maintient un compteur de références dans un bloc de données contenant un motif compilé. Ceci est fourni au bénéfice des applications orientées objet.

Les variables globales pcre_malloc et pcre_free contiennent initialement les points d'entrée des fonctions standard malloc() et free(), respectivement. PCRE appelle les fonctions de gestion de mémoire via ces variables, donc un programme appelant peut les remplacer s'il souhaite intercepter les appels. Ceci doit être fait avant d'appeler toute fonction PCRE.

Les variables globales pcre_stack_malloc et pcre_stack_free sont également des indirections vers des fonctions de gestion de mémoire. Ces fonctions spéciales sont utilisées uniquement lorsque PCRE est compilé pour utiliser le tas (heap) pour mémoriser des données, au lieu d'appels de fonction récursifs, lors de l'exécution de la fonction pcre_exec(). Voir la documentation de pcrebuild pour les détails sur comment faire cela. C'est une manière non standard de construire PCRE, pour une utilisation dans des environnements qui ont des piles (stacks) limitées. En raison d'une utilisation accrue de la gestion de mémoire, cela s'exécute plus lentement. Des fonctions séparées sont fournies afin que du code externe à usage spécifique puisse être utilisé pour ce cas. Lorsqu'elles sont utilisées, ces fonctions allouent toujours des blocs de mémoire de même taille. Il y a une discussion sur l'utilisation de la pile par PCRE dans la documentation de pcrestack.

La variable globale pcre_callout contient initialement NULL. Elle peut être définie par l'appelant à une fonction "d'appel" (callout), que PCRE appellera ensuite à des points spécifiés pendant une opération de mise en correspondance. Les détails sont donnés dans la documentation de pcrecallout.

La variable globale pcre_stack_guard contient initialement NULL. Elle peut être définie par l'appelant à une fonction qui est appelée par PCRE chaque fois qu'il commence à compiler une partie parenthésée d'un motif. Lorsque les parenthèses sont imbriquées, PCRE utilise des appels de fonction récursifs, qui consomment la pile système. Cette fonction est fournie afin que les applications avec des piles restreintes puissent forcer une erreur de compilation si la pile est épuisée. La fonction doit renvoyer zéro si tout va bien, ou une valeur non nulle pour forcer une erreur.

NOUVELLES LIGNES

PCRE prend en charge cinq conventions différentes pour indiquer les sauts de ligne dans les chaînes: un seul caractère CR (retour chariot), un seul caractère LF (saut de ligne), la séquence de deux caractères CRLF, l'une des trois précédentes, ou toute séquence de nouvelle ligne Unicode. Les séquences de nouvelle ligne Unicode sont les trois mentionnées ci-dessus, plus les caractères uniques VT (tabulation verticale, U+000B), FF (saut de page, U+000C), NEL (nouvelle ligne, U+0085), LS (séparateur de ligne, U+2028), et PS (séparateur de paragraphe, U+2029).

Chacune des trois premières conventions est utilisée par au moins un système d'exploitation comme séquence de nouvelle ligne standard. Lors de la construction de PCRE, une valeur par défaut peut être spécifiée. La valeur par défaut par défaut est LF, qui est la norme Unix. Lors de l'exécution de PCRE, la valeur par défaut peut être outrepassée, soit lors de la compilation d'un motif, soit lors de sa mise en correspondance.

Au moment de la compilation, la convention de nouvelle ligne peut être spécifiée par l'argument options de pcre_compile(), ou elle peut être spécifiée par du texte spécial au début du motif lui-même; cela outrepasse tous les autres paramètres. Voir la page pcrepattern pour les détails sur les séquences de caractères spéciales.

Dans la documentation PCRE, le mot "nouvelle ligne" est utilisé pour signifier "le caractère ou la paire de caractères qui indique un saut de ligne". Le choix de la convention de nouvelle ligne affecte la gestion des métacaractères point, circonflexe et dollar, la gestion des commentaires # dans le mode /x, et, lorsque CRLF est une séquence de fin de ligne reconnue, l'avancement de la position de correspondance pour un motif non ancré. Il y a plus de détails à ce sujet dans la section sur les options de pcre_exec() ci-dessous.

Le choix de la convention de nouvelle ligne n'affecte pas l'interprétation des séquences d'échappement \n ou \r, ni ce que \R met en correspondance, qui est contrôlé de manière similaire, mais par des options séparées.

MULTITHREADING

Les fonctions PCRE peuvent être utilisées dans des applications multithreads, à la condition que les fonctions de gestion de mémoire pointées par pcre_malloc, pcre_free, pcre_stack_malloc, et pcre_stack_free, ainsi que les fonctions d'appel et de vérification de pile pointées par pcre_callout et pcre_stack_guard, soient partagées par tous les threads.

La forme compilée d'une expression régulière n'est pas modifiée pendant la mise en correspondance, donc le même motif compilé peut être utilisé en toute sécurité par plusieurs threads simultanément.

Si la fonctionnalité d'optimisation juste-à-temps (JIT) est utilisée, elle nécessite des zones de pile mémoire séparées pour chaque thread. Voir la documentation de pcrejit pour plus de détails.

SAUVEGARDE DES MOTIFS PRÉCOMPILÉS POUR UNE UTILISATION ULTÉRIEURE

La forme compilée d'une expression régulière peut être sauvegardée et réutilisée ultérieurement, potentiellement par un programme différent, et même sur un hôte autre que celui sur lequel elle a été compilée. Les détails sont donnés dans la documentation de pcreprecompile, qui inclut une description de la fonction pcre_pattern_to_host_byte_order(). Cependant, compiler une expression régulière avec une version de PCRE pour une utilisation avec une version différente n'est pas garanti de fonctionner et peut provoquer des plantages.

VÉRIFICATION DES OPTIONS DE COMPILATION

int pcre_config(int what, void *where);

La fonction pcre_config() permet à un client PCRE de découvrir quelles fonctionnalités optionnelles ont été compilées dans la bibliothèque PCRE. La documentation de pcrebuild contient plus de détails sur ces fonctionnalités optionnelles.

Le premier argument de pcre_config() est un entier, spécifiant quelles informations sont requises ; le second argument est un pointeur vers une variable dans laquelle les informations sont placées. La valeur renvoyée est zéro en cas de succès, ou le code d'erreur négatif PCRE_ERROR_BADOPTION si la valeur du premier argument n'est pas reconnue. Les informations suivantes sont disponibles :


PCRE_CONFIG_UTF8

La sortie est un entier qui est mis à un si le support UTF-8 est disponible ; sinon, il est mis à zéro. Cette valeur doit normalement être donnée à la version 8 bits de cette fonction, pcre_config(). Si elle est donnée à la version 16 bits ou 32 bits de cette fonction, le résultat est PCRE_ERROR_BADOPTION.


PCRE_CONFIG_UTF16

La sortie est un entier qui est mis à un si le support UTF-16 est disponible ; sinon, il est mis à zéro. Cette valeur doit normalement être donnée à la version 16 bits de cette fonction, pcre16_config(). Si elle est donnée à la version 8 bits ou 32 bits de cette fonction, le résultat est PCRE_ERROR_BADOPTION.


PCRE_CONFIG_UTF32

La sortie est un entier qui est mis à un si le support UTF-32 est disponible ; sinon, il est mis à zéro. Cette valeur doit normalement être donnée à la version 32 bits de cette fonction, pcre32_config(). Si elle est donnée à la version 8 bits ou 16 bits de cette fonction, le résultat est PCRE_ERROR_BADOPTION.


PCRE_CONFIG_UNICODE_PROPERTIES

La sortie est un entier qui est mis à un si le support des propriétés de caractères Unicode est disponible ; sinon, il est mis à zéro.


PCRE_CONFIG_JIT

La sortie est un entier qui est mis à un si le support de la compilation juste-à-temps (JIT) est disponible ; sinon, il est mis à zéro.


PCRE_CONFIG_JITTARGET

La sortie est un pointeur vers une chaîne "const char *" terminée par un zéro. Si le support JIT est disponible, la chaîne contient le nom de l'architecture pour laquelle le compilateur JIT est configuré, par exemple "x86 32bit (little endian + unaligned)". Si le support JIT n'est pas disponible, le résultat est NULL.


PCRE_CONFIG_NEWLINE

La sortie est un entier dont la valeur spécifie la séquence de caractères par défaut qui est reconnue comme signifiant "nouvelle ligne". Les valeurs qui sont prises en charge dans les environnements ASCII/Unicode sont : 10 pour LF, 13 pour CR, 3338 pour CRLF, -2 pour ANYCRLF, et -1 pour ANY. Dans les environnements EBCDIC, CR, ANYCRLF et ANY donnent les mêmes valeurs. Cependant, la valeur pour LF est normalement 21, bien que certains environnements EBCDIC utilisent 37. Les valeurs correspondantes pour CRLF sont 3349 et 3365. La valeur par défaut doit normalement correspondre à la séquence standard de votre système d'exploitation.


PCRE_CONFIG_BSR

La sortie est un entier dont la valeur indique quelles séquences de caractères la séquence d'échappement \R met en correspondance par défaut. Une valeur de 0 signifie que \R met en correspondance toute séquence de fin de ligne Unicode ; une valeur de 1 signifie que \R met en correspondance uniquement CR, LF, ou CRLF. La valeur par défaut peut être outrepassée lors de la compilation ou de la mise en correspondance d'un motif.


PCRE_CONFIG_LINK_SIZE

La sortie est un entier qui contient le nombre d'octets utilisés pour le chaînage interne dans les expressions régulières compilées. Pour la bibliothèque 8 bits, la valeur peut être 2, 3 ou 4. Pour la bibliothèque 16 bits, la valeur est soit 2 soit 4 et représente toujours un nombre d'octets. Pour la bibliothèque 32 bits, la valeur est soit 2 soit 4 et représente toujours un nombre d'octets. La valeur par défaut de 2 est suffisante pour tous les motifs sauf les plus massifs, car elle permet au motif compilé d'avoir une taille allant jusqu'à 64 Ko. Des valeurs plus grandes permettent de compiler des expressions régulières plus grandes, au détriment d'une mise en correspondance plus lente.


PCRE_CONFIG_POSIX_MALLOC_THRESHOLD

La sortie

est un entier qui contient le seuil au-dessus duquel l'interface POSIX utilise malloc() pour les vecteurs de sortie. Plus de détails sont donnés dans la documentation de pcreposix.


PCRE_CONFIG_PARENS_LIMIT

La sortie est un entier long qui donne la profondeur maximale d'imbrication des parenthèses (de quelque type que ce soit) dans un motif. Cette limite est imposée pour plafonner la quantité de pile système utilisée lors de la compilation d'un motif. Elle est spécifiée lors de la construction de PCRE ; la valeur par défaut est 250. Cette limite ne prend pas en compte la pile qui peut déjà être utilisée par l'application appelante. Pour un contrôle plus fin de l'utilisation de la pile de compilation, vous pouvez définir un pointeur vers une fonction de vérification externe dans pcre_stack_guard.


PCRE_CONFIG_MATCH_LIMIT

La sortie est un entier long qui donne la limite par défaut pour le nombre d'appels de fonction de correspondance interne lors d'une exécution de pcre_exec(). Plus de détails sont donnés avec pcre_exec() ci-dessous.


PCRE_CONFIG_MATCH_LIMIT_RECURSION

La sortie est un entier long qui donne la limite par défaut pour la profondeur de récursion lors de l'appel de la fonction de correspondance interne lors d'une exécution de pcre_exec(). Plus de détails sont donnés avec pcre_exec() ci-dessous.


PCRE_CONFIG_STACKRECURSE

La sortie est un entier qui est mis à un si la récursion interne lors de l'exécution de pcre_exec() est implémentée par des appels de fonction récursifs qui utilisent la pile pour se souvenir de leur état. C'est la manière habituelle dont PCRE est compilé. La sortie est zéro si PCRE a été compilé pour utiliser des blocs de données sur le tas au lieu d'appels de fonction récursifs. Dans ce cas, pcre_stack_malloc et pcre_stack_free sont appelés pour gérer les blocs de mémoire sur le tas, évitant ainsi l'utilisation de la pile.

COMPILATION D'UN MOTIF

pcre *pcre_compile(const char *pattern, int options,
     const char **errptr, int *erroffset,
     const unsigned char *tableptr);

pcre *pcre_compile2(const char *pattern, int options,
     int *errorcodeptr,
     const char **errptr, int *erroffset,
     const unsigned char *tableptr);

L'une ou l'autre des fonctions pcre_compile() ou pcre_compile2() peut être appelée pour compiler un motif dans une forme interne. La seule différence entre les deux interfaces est que pcre_compile2() a un argument supplémentaire, errorcodeptr, via lequel un code d'erreur numérique peut être retourné. Pour éviter trop de répétitions, nous nous référerons uniquement à pcre_compile() ci-dessous, mais l'information s'applique également à pcre_compile2().

Le motif est une chaîne C terminée par un zéro binaire, et est passé dans l'argument pattern. Un pointeur vers un seul bloc de mémoire obtenu via pcre_malloc est retourné. Il contient le code compilé et les données associées. Le type pcre est défini pour le bloc retourné ; il s'agit d'un typedef pour une structure dont le contenu n'est pas défini extérieurement. Il incombe à l'appelant de libérer la mémoire (via pcre_free) lorsqu'elle n'est plus nécessaire.

Bien que le code compilé d'une expression régulière PCRE soit déplaçable, c'est-à-dire qu'il ne dépend pas de l'emplacement mémoire, le bloc de données complet pcre n'est pas entièrement déplaçable, car il peut contenir une copie de l'argument tableptr, qui est une adresse (voir ci-dessous).

L'argument options contient divers réglages de bits qui affectent la compilation. Il doit être zéro si aucune option n'est requise. Les options disponibles sont décrites ci-dessous. Certaines d'entre elles (en particulier celles qui sont compatibles avec Perl, mais aussi d'autres) peuvent également être définies et annulées à partir du motif lui-même (voir la description détaillée dans la documentation de pcrepattern). Pour les options qui peuvent être différentes dans différentes parties du motif, le contenu de l'argument options spécifie leurs réglages au début de la compilation et de l'exécution. Les options PCRE_ANCHORED, PCRE_BSR_xxx, PCRE_NEWLINE_xxx, PCRE_NO_UTF8_CHECK et PCRE_NO_START_OPTIMIZE peuvent être définies au moment de la correspondance, ainsi qu'au moment de la compilation.

Si errptr est NULL, pcre_compile() retourne NULL immédiatement. Sinon, si la compilation d'un motif échoue, pcre_compile() retourne NULL et définit la variable pointée par errptr pour pointer vers un message d'erreur textuel. Il s'agit d'une chaîne statique qui fait partie de la bibliothèque. Vous ne devez pas essayer de la libérer. Normalement, le décalage par rapport au début du motif jusqu'à l'unité de données qui était en cours de traitement lorsque l'erreur a été découverte est placé dans la variable pointée par erroffset, qui ne doit pas être NULL (si c'est le cas, une erreur immédiate est donnée). Cependant, pour une chaîne UTF-8 ou UTF-16 invalide, le décalage est celui de la première unité de données du caractère défaillant.

Certaines erreurs ne sont pas détectées tant que tout le motif n'a pas été analysé ; dans ces cas, le décalage retourné est la longueur du motif. Notez que le décalage est en unités de données, et non en caractères, même en mode UTF. Il peut parfois pointer au milieu d'un caractère UTF-8 ou UTF-16.

Si pcre_compile2() est utilisé à la place de pcre_compile(), et que l'argument errorcodeptr n'est pas NULL, un numéro de code d'erreur non nul est retourné via cet argument en cas d'erreur. Ceci s'ajoute au message d'erreur textuel. Les codes d'erreur et les messages sont listés ci-dessous.

Si le dernier argument, tableptr, est NULL, PCRE utilise un ensemble par défaut de tables de caractères qui sont construites lors de la compilation de PCRE, en utilisant la locale C par défaut. Sinon, tableptr doit être une adresse qui est le résultat d'un appel à pcre_maketables(). Cette valeur est stockée avec le motif compilé, et utilisée à nouveau par pcre_exec() et pcre_dfa_exec() lors de la correspondance du motif. Pour plus de discussions, voir la section sur le support des locales ci-dessous.

Ce fragment de code montre un appel typique et simple à pcre_compile() :


pcre *re;
const char *error;
int erroffset;
re = pcre_compile(
"^A.*Z", /* le motif */
0, /* options par défaut */
&error, /* pour le message d'erreur */
&erroffset, /* pour le décalage d'erreur */
NULL); /* utiliser les tables de caractères par défaut */

Les noms suivants pour les bits d'option sont définis dans le fichier d'en-tête pcre.h :


PCRE_ANCHORED

Si ce bit est défini, le motif est forcé d'être « ancré », c'est-à-dire qu'il est contraint de ne correspondre qu'au premier point de correspondance dans la chaîne qui est recherchée (la « chaîne sujet »). Cet effet peut également être obtenu par des constructions appropriées dans le motif lui-même, ce qui est la seule façon de le faire en Perl.


PCRE_AUTO_CALLOUT

Si ce bit est défini, pcre_compile() insère automatiquement des éléments de rappel, tous avec le numéro 255, avant chaque élément de motif. Pour une discussion sur la facilité de rappel, voir la documentation de pcrecallout.


PCRE_BSR_ANYCRLF
PCRE_BSR_UNICODE

Ces options (qui sont mutuellement exclusives) contrôlent ce que la séquence d'échappement \R correspond. Le choix est soit de correspondre uniquement à CR, LF, ou CRLF, soit de correspondre à toute séquence de fin de ligne Unicode. La valeur par défaut est spécifiée lors de la construction de PCRE. Elle peut être remplacée à partir du motif lui-même, ou en définissant une option lors de la correspondance d'un motif compilé.


PCRE_CASELESS

Si ce bit est défini, les lettres du motif correspondent aux lettres majuscules et minuscules. Il est équivalent à l'option /i de Perl, et il peut être modifié à l'intérieur d'un motif par un réglage d'option (?i). En mode UTF-8, PCRE comprend toujours le concept de casse pour les caractères dont les valeurs sont inférieures à 128, donc une correspondance sans casse est toujours possible. Pour les caractères de valeurs supérieures, le concept de casse est pris en charge si PCRE est compilé avec le support des propriétés Unicode, mais pas sinon. Si vous souhaitez utiliser une correspondance sans casse pour les caractères 128 et supérieurs, vous devez vous assurer que PCRE est compilé avec le support des propriétés Unicode ainsi qu'avec le support UTF-8.


PCRE_DOLLAR_ENDONLY

Si ce bit est défini, un métacaractère dollar dans le motif ne correspond qu'à la fin de la chaîne sujet. Sans cette option, un dollar correspond également immédiatement avant une fin de ligne à la fin de la chaîne (mais pas avant toute autre fin de ligne). L'option PCRE_DOLLAR_ENDONLY est ignorée si PCRE_MULTILINE est défini. Il n'y a pas d'équivalent à cette option dans Perl, et aucun moyen de la définir à l'intérieur d'un motif.


PCRE_DOTALL

Si ce bit est défini, un métacaractère point dans le motif correspond à un caractère de n'importe quelle valeur, y compris un caractère qui indique une fin de ligne. Cependant, il ne correspond jamais qu'à un seul caractère, même si les fins de ligne sont codées en CRLF. Sans cette option, un point ne correspond pas lorsque la position actuelle est à une fin de ligne. Cette option est équivalente à l'option /s de Perl, et elle peut être modifiée à l'intérieur d'un motif par un réglage d'option (?s). Une classe négative telle que [^a] correspond toujours aux caractères de fin de ligne, indépendamment du réglage de cette option.


PCRE_DUPNAMES

Si ce bit est défini, les noms utilisés pour identifier les sous-motifs de capturation n'ont pas besoin d'être uniques. Cela peut être utile pour certains types de motifs lorsqu'il est connu qu'une seule instance du sous-motif nommé ne peut jamais correspondre. Il y a plus de détails sur les sous-motifs nommés ci-dessous ; voir également la documentation de pcrepattern.


PCRE_EXTENDED

Si ce bit est défini, la plupart des caractères d'espace blanc dans le motif sont totalement ignorés sauf lorsqu'ils sont échappés ou à l'intérieur d'une classe de caractères. Cependant, les espaces blancs ne sont pas autorisés dans les séquences telles que (?> qui introduisent divers sous-motifs entre parenthèses, ni dans un quantificateur numérique tel que {1,3}. Cependant, des espaces blancs ignorables sont permis entre un élément et un quantificateur suivant, et entre un quantificateur et un suivi de + qui indique la possessivité.

Les espaces blancs n'incluaient pas auparavant le caractère VT (code 11), car Perl ne traitait pas ce caractère comme un espace blanc. Cependant, Perl a changé lors de la sortie 5.18, donc PCRE a suivi lors de la sortie 8.34, et VT est maintenant traité comme un espace blanc.

PCRE_EXTENDED ignore également les caractères entre un # non échappé en dehors d'une classe de caractères et la prochaine fin de ligne, incluse. PCRE_EXTENDED est équivalent à l'option /x de Perl, et il peut être modifié à l'intérieur d'un motif par un réglage d'option (?x).

Les caractères qui sont interprétés comme des fins de ligne sont contrôlés par les options passées à pcre_compile() ou par une séquence spéciale au début du motif, comme décrit dans la section intitulée « Conventions de fin de ligne » de la documentation de pcrepattern. Notez que la fin de ce type de commentaire est une séquence de fin de ligne littérale dans le motif ; les séquences d'échappement qui représentent une fin de ligne ne comptent pas.

OPTIONS

This section describes the options that can be passed to pcre_compile(), pcre_compile2(), pcre_exec(), pcre_dfa_exec(), and pcre_study(). Some options are only relevant to compilation, some only to execution, and some apply to both. They are listed here alphabetically.

When PCRE is compiled, a set of default newline characters can be chosen. These defaults can be overridden by options that are passed to the compilation functions. However, the newline character settings used by pcre_exec() and pcre_dfa_exec() can be overridden by options that are passed to them.

Most of the options are represented by a symbolic name starting with PCRE_. In the C API, these are defined in the pcre.h header file. They can also be set within a pattern by using the (?opt:...) syntax, where opt is one or more letters representing the option. Options can be turned off within a pattern by preceding the letter with a hyphen, for example, (?-m). It is also possible to turn options on and off within a pattern by using (?om:...) syntax, for example, (?om-p:...) turns on o and m, and turns off p.

The options that can be set within a pattern are:

A: PCRE_ANCHOR

S: PCRE_NO_START_OPTIMIZE

U: PCRE_UNGREEDY

X: PCRE_EXTENDED

m: PCRE_MULTILINE

s: PCRE_DOTALL

u: PCRE_UTF8

x: PCRE_EXTENDED

Note that the x option is available only when PCRE has been compiled with Unicode support.

The following options are relevant only when PCRE is running in an environment that supports Unicode, that is, when it has been compiled with Unicode support and the u option is set:

U: PCRE_UNGREEDY

u: PCRE_UTF8

Options can be combined by using the bitwise OR operator (|).


PCRE_ANCHOR

By default, the start-of-string special character (^), matches only at the very start of the subject string. If this option is set, the start-of-string meta-character is additionally recognized at the start of the subject string, immediately following any newline characters. This is equivalent to Perl's /A option, and can also be set using the (?A) syntax within a pattern.


PCRE_CASELESS

By default, matching is case-sensitive. If this option is set, the matching is case-insensitive, so that, for example, the pattern aBc would match AbC. This is equivalent to Perl's /i option, and can also be set using the (?i) syntax within a pattern.


PCRE_DOLLAR_ENDONLY

By default, the end-of-string special character ($) matches at the very end of the subject string, or just before a newline at the very end of the subject string. If this option is set, $ matches only at the very end of the string. It does not match before a newline. This is equivalent to Perl's /Z option, and can also be set using the (?Z) syntax within a pattern.


PCRE_DOTALL

By default, the metacharacter . matches any character except a newline. If this option is set, the metacharacter . matches any character whatsoever, including newlines. This is equivalent to Perl's /s option, and can also be set using the (?s) syntax within a pattern.


PCRE_EXTENDED

If this option is set, whitespace characters in the pattern are ignored, and characters are treated as ' Perl extended regular expressions'. This is equivalent to Perl's /x option, and can also be set using the (?x) syntax within a pattern. Whitespace characters are, by default, space, tab, vertical tab, form feed, carriage return, and line feed. In addition, when the PCRE_UTF8 option is set, all Unicode characters defined as whitespace are also ignored. Comments are allowed in the pattern that start with # and continue until the next newline character. Whitespace and comments are ignored except when they appear inside a character class ([...]) or when they are escaped with a backslash.

Note, however, that this applies only to data characters. White space characters may never appear within special character sequences in a pattern, for example within the sequence (?( that introduces a conditional subpattern.


PCRE_EXTRA

This option was invented in order to turn on additional functionality of PCRE that is incompatible with Perl, but it is currently of very little use. When set, any backslash in a pattern that is followed by a letter that has no special meaning causes an error, thus reserving these combinations for future expansion. By default, as in Perl, a backslash followed by a letter with no special meaning is treated as a literal. (Perl can, however, be persuaded to give an error for this, by running it with the -w option.) There are at present no other features controlled by this option. It can also be set by a (?X) option setting within a pattern.


PCRE_FIRSTLINE

If this option is set, an unanchored pattern is required to match before or at the first newline in the subject string, though the matched text may continue over the newline.


PCRE_JAVASCRIPT_COMPAT

If this option is set, PCRE's behaviour is changed in some ways so that it is compatible with JavaScript rather than Perl. The changes are as follows:

(1) A lone closing square bracket in a pattern causes a compile-time error, because this is illegal in JavaScript (by default it is treated as a data character). Thus, the pattern AB]CD becomes illegal when this option is set.

(2) At run time, a back reference to an unset subpattern group matches an empty string (by default this causes the current matching alternative to fail). A pattern such as (\1)(a) succeeds when this option is set (assuming it can find an "a" in the subject), whereas it fails by default, for Perl compatibility.

(3) \U matches an upper case "U" character; by default \U causes a compile time error (Perl uses \U to upper case subsequent characters).

(4) \u matches a lower case "u" character unless it is followed by four hexadecimal digits, in which case the hexadecimal number defines the code point to match. By default, \u causes a compile time error (Perl uses it to upper case the following character).

(5) \x matches a lower case "x" character unless it is followed by two hexadecimal digits, in which case the hexadecimal number defines the code point to match. By default, as in Perl, a hexadecimal number is always expected after \x, but it may have zero, one, or two digits (so, for example, \xz matches a binary zero character followed by z).


PCRE_MULTILINE

By default, for the purposes of matching "start of line" and "end of line", PCRE treats the subject string as consisting of a single line of characters, even if it actually contains newlines. The "start of line" metacharacter (^) matches only at the start of the string, and the "end of line" metacharacter ($) matches only at the end of the string, or before a terminating newline (except when PCRE_DOLLAR_ENDONLY is set). Note, however, that unless PCRE_DOTALL is set, the "any character" metacharacter (.) does not match at a newline. This behaviour (for ^, $, and dot) is the same as Perl.

When PCRE_MULTILINE it is set, the "start of line" and "end of line" constructs match immediately following or immediately before internal newlines in the subject string, respectively, as well as at the very start and end. This is equivalent to Perl's /m option, and it can be changed within a pattern by a (?m) option setting. If there are no newlines in a subject string, or no occurrences of ^ or $ in a pattern, setting PCRE_MULTILINE has no effect.


PCRE_NEVER_UTF

This option locks out interpretation of the pattern as UTF-8 (or UTF-16 or UTF-32 in the 16-bit and 32-bit libraries). In particular, it prevents the creator of the pattern from switching to UTF interpretation by starting the pattern with (*UTF). This may be useful in applications that process patterns from external sources. The combination of PCRE_UTF8 and PCRE_NEVER_UTF also causes an error.


PCRE_NEWLINE_CR
PCRE_NEWLINE_LF
PCRE_NEWLINE_CRLF
PCRE_NEWLINE_ANYCRLF
PCRE_NEWLINE_ANY

These options override the default newline definition that was chosen when PCRE was built. Setting the first or the second specifies that a newline is indicated by a single character (CR or LF, respectively). Setting PCRE_NEWLINE_CRLF specifies that a newline is indicated by the two-character CRLF sequence. Setting PCRE_NEWLINE_ANYCRLF specifies that any of the three preceding sequences should be recognized. Setting PCRE_NEWLINE_ANY specifies that any Unicode newline sequence should be recognized.

In an ASCII/Unicode environment, the Unicode newline sequences are the three just mentioned, plus the single characters VT (vertical tab, U+000B), FF (form feed, U+000C), NEL (next line, U+0085), LS (line separator, U+2028), and PS (paragraph separator, U+2029). For the 8-bit library, the last two are recognized only in UTF-8 mode.

When PCRE is compiled to run in an EBCDIC (mainframe) environment, the code for CR is 0x0d, the same as ASCII. However, the character code for LF is normally 0x15, though in some EBCDIC environments 0x25 is used. Whichever of these is not LF is made to correspond to Unicode's NEL character. EBCDIC codes are all less than 256. For more details, see the pcrebuild documentation.

The newline setting in the options word uses three bits that are treated as a number, giving eight possibilities. Currently only six are used (default plus the five values above). This means that if you set more than one newline option, the combination may or may not be sensible. For example, PCRE_NEWLINE_CR with PCRE_NEWLINE_LF is equivalent to PCRE_NEWLINE_CRLF, but other combinations may yield unused numbers and cause an error.

The only time that a line break in a pattern is specially recognized when compiling is when PCRE_EXTENDED is set. CR and LF are white space characters, and so are ignored in this mode. Also, an unescaped # outside a character class indicates a comment that lasts until after the next line break sequence. In other circumstances, line break sequences in patterns are treated as literal data.

The newline option that is set at compile time becomes the default that is used for pcre_exec() and pcre_dfa_exec(), but it can be overridden.


PCRE_NO_AUTO_CAPTURE

If this option is set, it disables the use of numbered capturing parentheses in the pattern. Any opening parenthesis that is not followed by ? behaves as if it were followed by ?: but named parentheses can still be used for capturing (and they acquire numbers in the usual way). There is no equivalent of this option in Perl.


PCRE_NO_AUTO_POSSESS

If this option is set, it disables "auto-possessification". This is an optimization that, for example, turns a+b into a++b in order to avoid backtracks into a+ that can never be successful. However, if callouts are in use, auto-possessification means that some of them are never taken. You can set this option if you want the matching functions to do a full unoptimized search and run all the callouts, but it is mainly provided for testing purposes.


PCRE_NO_START_OPTIMIZE

This is an option that acts at matching time; that is, it is really an option for pcre_exec() or pcre_dfa_exec(). If it is set at compile time, it is remembered with the compiled pattern and assumed at matching time. This is necessary if you want to use JIT execution, because the JIT compiler needs to know whether or not this option is set. For details see the discussion of PCRE_NO_START_OPTIMIZE below.


PCRE_UCP

This option changes the way PCRE processes \B, \b, \D, \d, \S, \s, \W, \w, and some of the POSIX character classes. By default, only ASCII characters are recognized, but if PCRE_UCP is set, Unicode properties are used instead to classify characters. More details are given in the section on generic character types in the pcrepattern page. If you set PCRE_UCP, matching one of the items it affects takes much longer. The option is available only if PCRE has been compiled with Unicode property support.


PCRE_UNGREEDY

This option inverts the "greediness" of the quantifiers so that they are not greedy by default, but become greedy if followed by "?". It is not compatible with Perl. It can also be set by a (?U) option setting within the pattern.


PCRE_UTF8

This option causes PCRE to regard both the pattern and the subject as strings of UTF-8 characters instead of single-byte strings. However, it is available only when PCRE is built to include UTF support. If not, the use of this option provokes an error. Details of how this option changes the behaviour of PCRE are given in the pcreunicode page.


PCRE_NO_UTF8_CHECK

When PCRE_UTF8 is set, the validity of the pattern as a UTF-8 string is automatically checked. There is a discussion about the validity of UTF-8 strings in the pcreunicode page. If an invalid UTF-8 sequence is found, pcre_compile() returns an error. If you already know that your pattern is valid, and you want to skip this check for performance reasons, you can set the PCRE_NO_UTF8_CHECK option. When it is set, the effect of passing an invalid UTF-8 string as a pattern is undefined. It may cause your program to crash or loop. Note that this option can also be passed to pcre_exec() and pcre_dfa_exec(), to suppress the validity checking of subject strings only. If the same string is being matched many times, the option can be safely set for the second and subsequent matchings to improve performance.

ÉTUDE D'UN MOTIF

pcre_extra *pcre_study(const pcre *code, int options,
     const char **errptr);

Si un motif compilé doit être utilisé plusieurs fois, il est judicieux de passer plus de temps à l'analyser afin d'accélérer le temps de correspondance. La fonction pcre_study() prend un pointeur vers un motif compilé comme premier argument. Si l'étude du motif produit des informations supplémentaires qui aideront à accélérer la correspondance, pcre_study() renvoie un pointeur vers un bloc pcre_extra, dans lequel le champ study_data pointe vers les résultats de l'étude.

La valeur renvoyée par pcre_study() peut être passée directement à pcre_exec() ou pcre_dfa_exec(). Cependant, un bloc pcre_extra contient également d'autres champs qui peuvent être définis par l'appelant avant que le bloc ne soit passé ; ceux-ci sont décrits ci-dessous dans la section sur la correspondance d'un motif.

Si l'étude du motif ne produit aucune information utile, pcre_study() renvoie NULL par défaut. Dans ce cas, si le programme appelant souhaite passer l'un des autres champs à pcre_exec() ou pcre_dfa_exec(), il doit configurer son propre bloc pcre_extra. Cependant, si pcre_study() est appelé avec l'option PCRE_STUDY_EXTRA_NEEDED, il renvoie un bloc pcre_extra même si l'étude n'a trouvé aucune information supplémentaire. Il peut toujours renvoyer NULL, cependant, si une erreur se produit dans pcre_study().

Le deuxième argument de pcre_study() contient des bits d'options. Il y a trois options supplémentaires en plus de PCRE_STUDY_EXTRA_NEEDED :


PCRE_STUDY_JIT_COMPILE
PCRE_STUDY_JIT_PARTIAL_HARD_COMPILE
PCRE_STUDY_JIT_PARTIAL_SOFT_COMPILE

Si l'une de ces options est définie, et que le compilateur juste-à-temps est disponible, le motif est davantage compilé en code machine qui s'exécute beaucoup plus rapidement que la fonction de correspondance interprétative pcre_exec(). Si le compilateur juste-à-temps n'est pas disponible, ces options sont ignorées. Tous les bits non définis dans l'argument options doivent être zéro.

La compilation JIT est une optimisation lourde. Il peut falloir un certain temps pour analyser les motifs, et pour les correspondances ponctuelles et les motifs simples, le bénéfice d'une exécution plus rapide pourrait être compensé par un temps d'étude beaucoup plus long. Tous les motifs ne peuvent pas être optimisés par le compilateur JIT. Pour ceux qui ne peuvent pas être gérés, la correspondance se rabat automatiquement sur l'interpréteur pcre_exec(). Pour plus de détails, voir la documentation pcrejit.

Le troisième argument de pcre_study() est un pointeur pour un message d'erreur. Si l'étude réussit (même si aucune donnée n'est renvoyée), la variable à laquelle il pointe est mise à NULL. Sinon, elle est mise pour pointer vers un message d'erreur textuel. Il s'agit d'une chaîne statique qui fait partie de la bibliothèque. Vous ne devez pas essayer de la libérer. Vous devriez tester le pointeur d'erreur pour NULL après avoir appelé pcre_study(), pour être sûr qu'il s'est exécuté avec succès.

Lorsque vous avez terminé avec un motif, vous pouvez libérer la mémoire utilisée pour les données d'étude en appelant pcre_free_study(). Cette fonction a été ajoutée à l'API pour la version 8.20. Pour les versions antérieures, la mémoire pouvait être libérée avec pcre_free(), tout comme le motif lui-même. Cela fonctionnera toujours dans les cas où l'optimisation JIT n'est pas utilisée, mais il est conseillé de passer à la nouvelle fonction dès que possible.

Voici une façon typique d'utiliser pcre_study() (sauf que dans une application réelle, il devrait y avoir des tests pour les erreurs) :


int rc;
pcre *re;
pcre_extra *sd;
re = pcre_compile("motif", 0, &error, &erroroffset, NULL);
sd = pcre_study(
re, /* résultat de pcre_compile() */
0, /* pas d'options */
&error); /* mis à NULL ou pointe vers un message */
rc = pcre_exec( /* voir ci-dessous pour les détails des options de pcre_exec() */
re, sd, "sujet", 7, 0, 0, ovector, 30);
...
pcre_free_study(sd);
pcre_free(re);

L'étude d'un motif fait deux choses : premièrement, une borne inférieure pour la longueur de la chaîne de sujet nécessaire pour faire correspondre le motif est calculée. Cela ne signifie pas qu'il existe des chaînes de cette longueur qui correspondent, mais cela garantit qu'aucune chaîne plus courte ne correspond. La valeur est utilisée pour éviter de perdre du temps à essayer de faire correspondre des chaînes plus courtes que la borne inférieure. Vous pouvez connaître la valeur dans un programme appelant via la fonction pcre_fullinfo().

L'étude d'un motif est également utile pour les motifs non ancrés qui n'ont pas un seul caractère de départ fixe. Une table de hachage des octets de départ possibles est créée. Cela accélère la recherche d'une position dans le sujet à partir de laquelle commencer la correspondance. (En mode 16 bits, la table de hachage est utilisée pour les valeurs 16 bits inférieures à 256. En mode 32 bits, la table de hachage est utilisée pour les valeurs 32 bits inférieures à 256.)

Ces deux optimisations s'appliquent à pcre_exec() et pcre_dfa_exec(), et les informations sont également utilisées par le compilateur JIT. Les optimisations peuvent être désactivées en définissant l'option PCRE_NO_START_OPTIMIZE. Vous pourriez vouloir faire cela si votre motif contient des appels ou (*MARK) et que vous souhaitez utiliser ces fonctionnalités lorsque la correspondance échoue.

PCRE_NO_START_OPTIMIZE peut être spécifié au moment de la compilation ou de l'exécution. Cependant, si PCRE_NO_START_OPTIMIZE est passé à pcre_exec(), (c'est-à-dire après toute compilation JIT), l'exécution JIT est désactivée. Pour que l'exécution JIT fonctionne avec PCRE_NO_START_OPTIMIZE, l'option doit être définie au moment de la compilation.

Il y a une discussion plus longue sur PCRE_NO_START_OPTIMIZE ci-dessous.

SUPPORT DES LOCALES

PCRE gère la correspondance sans tenir compte de la casse, et détermine si les caractères sont des lettres, des chiffres, ou autre chose, en se référant à un ensemble de tables, indexées par le code du caractère. Lors de l'exécution en mode UTF-8, ou dans les bibliothèques 16 ou 32 bits, cela s'applique uniquement aux caractères dont le code est inférieur à 256. Par défaut, les codes de caractères plus élevés ne correspondent jamais aux échappements tels que \w ou \d. Cependant, si PCRE est compilé avec le support des propriétés Unicode, tous les caractères peuvent être testés avec \p et \P, ou, alternativement, l'option PCRE_UCP peut être définie lors de la compilation d'un motif ; cela fait que \w et ses amis utilisent le support des propriétés Unicode au lieu des tables internes.

L'utilisation des locales avec Unicode est déconseillée. Si vous manipulez des caractères dont les codes sont supérieurs à 128, vous devriez soit utiliser le support Unicode, soit utiliser les locales, mais pas essayer de mélanger les deux.

PCRE contient un ensemble de tables internes qui sont utilisées lorsque le dernier argument de pcre_compile() est NULL. Celles-ci sont suffisantes pour de nombreuses applications. TABLES DE CARACTÈRES

PCRE utilise des tables internes pour traduire les caractères dans différentes plages de valeurs, par exemple pour déterminer si un caractère est une lettre ou un chiffre. Ces tables sont construites en fonction des paramètres régionaux par défaut du système local, ce qui peut entraîner des différences.

Les tables internes peuvent toujours être remplacées par des tables fournies par l'application qui appelle PCRE. Celles-ci peuvent être créées dans une locale différente de celle par défaut. À mesure que de plus en plus d'applications adoptent l'Unicode, le besoin de ce support de locale devrait diminuer.

Les tables externes sont construites en appelant la fonction pcre_maketables(), qui n'a pas d'arguments, dans la locale pertinente. Le résultat peut ensuite être passé à pcre_compile() aussi souvent que nécessaire. Par exemple, pour construire et utiliser des tables appropriées pour la locale française (où les caractères accentués ayant des valeurs supérieures à 128 sont traités comme des lettres), le code suivant peut être utilisé :


setlocale(LC_CTYPE, "fr_FR");
tables = pcre_maketables();
re = pcre_compile(..., tables);

Le nom de locale "fr_FR" est utilisé sous Linux et d'autres systèmes de type Unix ; si vous utilisez Windows, le nom de la locale française est "french".

Lorsque pcre_maketables() s'exécute, les tables sont construites dans la mémoire obtenue via pcre_malloc. Il incombe à l'appelant de s'assurer que la mémoire contenant les tables reste disponible aussi longtemps que nécessaire.

Le pointeur passé à pcre_compile() est sauvegardé avec le motif compilé, et les mêmes tables sont utilisées via ce pointeur par pcre_study() ainsi que par pcre_exec() et pcre_dfa_exec(). Ainsi, pour un motif unique, la compilation, l'étude et la correspondance se font toutes dans la même locale, mais des motifs différents peuvent être traités dans des locales différentes.

Il est possible de passer un pointeur de table ou NULL (indiquant l'utilisation des tables internes) à pcre_exec() ou pcre_dfa_exec() (voir la discussion ci-dessous dans la section sur la correspondance d'un motif). Cette fonctionnalité est fournie pour être utilisée avec des motifs précompilés qui ont été sauvegardés et rechargés. Les tables de caractères ne sont pas sauvegardées avec les motifs, donc si une table non standard a été utilisée au moment de la compilation, elle doit être fournie à nouveau lors de la correspondance du motif rechargé. Tenter d'utiliser cette fonctionnalité pour faire correspondre un motif dans une locale différente de celle dans laquelle il a été compilé est susceptible d'entraîner des résultats anormaux (généralement incorrects).

INFORMATIONS SUR UN MOTIF

int pcre_fullinfo(const pcre *code, const pcre_extra *extra,
     int what, void *where);

La fonction pcre_fullinfo() renvoie des informations sur un motif compilé. Elle remplace la fonction pcre_info(), qui a été retirée de la bibliothèque à la version 8.30, après plus de 10 ans d'obsolescence.

Le premier argument de pcre_fullinfo() est un pointeur vers le motif compilé. Le second argument est le résultat de pcre_study(), ou NULL si le motif n'a pas été étudié. Le troisième argument spécifie quelle information est requise, et le quatrième argument est un pointeur vers une variable pour recevoir les données. La valeur de retour de la fonction est zéro en cas de succès, ou l'un des nombres négatifs suivants :


PCRE_ERROR_NULL l'argument code était NULL
l'argument where était NULL
PCRE_ERROR_BADMAGIC le "nombre magique" n'a pas été trouvé
PCRE_ERROR_BADENDIANNESS le motif a été compilé avec une endianness
différente
PCRE_ERROR_BADOPTION la valeur de what était invalide
PCRE_ERROR_UNSET le champ demandé n'est pas défini

Le "nombre magique" est placé au début de chaque motif compilé comme une simple vérification contre le passage d'un pointeur de mémoire arbitraire. L'erreur d'endianness peut se produire si un motif compilé est sauvegardé et rechargé sur un hôte différent. Voici un appel typique à pcre_fullinfo(), pour obtenir la taille du motif compilé :


int rc;
size_t length;
rc = pcre_fullinfo(
re, /* résultat de pcre_compile() */
sd, /* résultat de pcre_study(), ou NULL */
PCRE_INFO_SIZE, /* ce qui est requis */
&length); /* où mettre les données */

Les valeurs possibles pour le troisième argument sont définies dans pcre.h, et sont les suivantes :


PCRE_INFO_BACKREFMAX

Renvoie le numéro de la référence arrière la plus élevée dans le motif. Le quatrième argument doit pointer vers une variable de type int. Zéro est renvoyé s'il n'y a pas de références arrière.


PCRE_INFO_CAPTURECOUNT

Renvoie le nombre de sous-motifs capturants dans le motif. Le quatrième argument doit pointer vers une variable de type int.


PCRE_INFO_DEFAULT_TABLES

Renvoie un pointeur vers les tables de caractères par défaut internes de PCRE. Le quatrième argument doit pointer vers une variable de type unsigned char *. Cet appel d'information est fourni pour une utilisation interne par la fonction pcre_study(). Les appelants externes peuvent faire en sorte que PCRE utilise ses tables internes en passant un pointeur de table NULL.


PCRE_INFO_FIRSTBYTE (obsolète)

Renvoie des informations sur la première unité de données de toute chaîne correspondante, pour un motif non ancré. Le nom de cette option fait référence à la bibliothèque 8 bits, où les unités de données sont des octets. Le quatrième argument doit pointer vers une variable de type int. Des valeurs négatives sont utilisées pour des cas spéciaux. Cependant, cela signifie que lorsque la bibliothèque 32 bits est en mode non-UTF-32, la plage complète de 32 bits des caractères ne peut pas être renvoyée. Pour cette raison, cette valeur est obsolète ; utilisez plutôt PCRE_INFO_FIRSTCHARACTERFLAGS et PCRE_INFO_FIRSTCHARACTER.

S'il existe une première valeur fixe, par exemple, la lettre "c" d'un motif tel que (cat|cow|coyote), sa valeur est renvoyée. Dans la bibliothèque 8 bits, la valeur est toujours inférieure à 256. Dans la bibliothèque 16 bits, la valeur peut aller jusqu'à 0xffff. Dans la bibliothèque 32 bits, la valeur peut aller jusqu'à 0x10ffff.

S'il n'y a pas de première valeur fixe, et si soit

(a) le motif a été compilé avec l'option PCRE_MULTILINE, et chaque branche commence par "^", soit

(b) chaque branche du motif commence par ".*" et PCRE_DOTALL n'est pas défini (s'il était défini, le motif serait ancré),

-1 est renvoyé, indiquant que le motif ne correspond qu'au début d'une chaîne sujet ou après toute nouvelle ligne dans la chaîne. Sinon, -2 est renvoyé. Pour les motifs ancrés, -2 est renvoyé.


PCRE_INFO_FIRSTCHARACTER

Renvoie la valeur de la première unité de données (caractère non UTF) de toute chaîne correspondante dans la situation où PCRE_INFO_FIRSTCHARACTERFLAGS renvoie 1 ; sinon, renvoie 0. Le quatrième argument doit pointer vers une variable de type uint_t.

Dans la bibliothèque 8 bits, la valeur est toujours inférieure à 256. Dans la bibliothèque 16 bits, la valeur peut aller jusqu'à 0xffff. Dans la bibliothèque 32 bits en mode UTF-32, la valeur peut aller jusqu'à 0x10ffff, et jusqu'à 0xffffffff lorsqu'elle n'utilise pas le mode UTF-32.


PCRE_INFO_FIRSTCHARACTERFLAGS

Renvoie des informations sur la première unité de données de toute chaîne correspondante, pour un motif non ancré. Le quatrième argument doit pointer vers une variable de type int.

S'il existe une première valeur fixe, par exemple, la lettre "c" d'un motif tel que (cat|cow|coyote), 1 est renvoyé, et la valeur du caractère peut être récupérée à l'aide de PCRE_INFO_FIRSTCHARACTER. S'il n'y a pas de première valeur fixe, et si soit

(a) le motif a été compilé avec l'option PCRE_MULTILINE, et chaque branche commence par "^", soit

(b) chaque branche du motif commence par ".*" et PCRE_DOTALL n'est pas défini (s'il était défini, le motif serait ancré),

2 est renvoyé, indiquant que le motif ne correspond qu'au début d'une chaîne sujet ou après toute nouvelle ligne dans la chaîne. Sinon, 0 est renvoyé. Pour les motifs ancrés, 0 est renvoyé.


PCRE_INFO_FIRSTTABLE

Si le motif a été étudié, et que cela a abouti à la construction d'une table de 256 bits indiquant un ensemble fixe de valeurs pour la première unité de données de toute chaîne correspondante, un pointeur vers la table est renvoyé. Sinon, NULL est renvoyé. Le quatrième argument doit pointer vers une variable de type unsigned char *.


PCRE_INFO_HASCRORLF

Renvoie 1 si le motif contient des correspondances explicites pour les caractères CR ou LF, sinon 0. Le quatrième argument doit pointer vers une variable de type int. Une correspondance explicite est soit un caractère CR ou LF littéral, soit \r ou \n.


PCRE_INFO_JCHANGED

Renvoie 1 si le réglage de l'option (?J) ou (?-J) est utilisé dans le motif, sinon 0. Le quatrième argument doit pointer vers une variable de type int. (?J) et (?-J) activent et désactivent respectivement l'option locale PCRE_DUPNAMES.


PCRE_INFO_JIT

Renvoie 1 si le motif a été étudié avec l'une des options JIT, et que la compilation juste-à-temps a réussi. Le quatrième argument doit pointer vers une variable de type int. Une valeur de retour de 0 signifie que le support JIT n'est pas disponible dans cette version de PCRE, ou que le motif n'a pas été étudié avec une option JIT, ou que le compilateur JIT n'a pas pu gérer ce motif particulier. Voir la documentation de pcrejit pour les détails sur ce qui peut et ne peut pas être géré.


PCRE_INFO_JITSIZE

Si le motif a été étudié avec succès avec une option JIT, renvoie la taille du code compilé JIT, sinon renvoie zéro. Le quatrième argument doit pointer vers une variable de type size_t.


PCRE_INFO_LASTLITERAL

Renvoie la valeur de la dernière unité de données littérale qui doit exister dans toute chaîne correspondante, autre qu'à son début, si une telle valeur a été enregistrée. Le quatrième argument doit pointer vers une variable de type int. S'il n'y a pas de telle valeur, -1 est renvoyé. Pour les motifs ancrés, une valeur littérale finale n'est enregistrée que si elle suit quelque chose de longueur variable. Par exemple, pour le motif /^a\d+z\d+/, la valeur renvoyée est "z", mais pour /^a\dz\d/, la valeur renvoyée est -1.

Étant donné que pour la bibliothèque 32 bits utilisant le mode non-UTF-32, cette fonction ne peut pas renvoyer la plage complète de 32 bits des caractères, cette valeur est obsolète ; les valeurs PCRE_INFO_REQUIREDCHARFLAGS et PCRE_INFO_REQUIREDCHAR doivent plutôt être utilisées.


PCRE_INFO_MATCH_EMPTY

Renvoie 1 si le motif peut correspondre à une chaîne vide, sinon 0. Le quatrième argument doit pointer vers une variable de type int.


PCRE_INFO_MATCHLIMIT

Si le motif a défini une limite de correspondance en incluant un élément de la forme (*LIMIT_MATCH=nnnn) au début, la valeur est renvoyée. Le quatrième argument doit pointer vers un entier non signé 32 bits. Si aucune valeur de ce type n'a été définie, l'appel à pcre_fullinfo() renvoie l'erreur PCRE_ERROR_UNSET.


PCRE_INFO_MAXLOOKBEHIND

Renvoie le nombre de caractères

cters (NB not data units) dans la plus longue assertion lookbehind du motif. Ces informations sont utiles lors de la correspondance multi-segments à l'aide des installations de correspondance partielle. Notez que les assertions simples \b et \B nécessitent un lookbehind d'un caractère. \A enregistre également un lookbehind d'un caractère, bien qu'il n'inspecte pas réellement le caractère précédent. Ceci est fait pour s'assurer qu'au moins un caractère de l'ancien segment est conservé lorsqu'un nouveau segment est traité. Sinon, s'il n'y a pas de lookbehinds dans le motif, \A pourrait correspondre incorrectement au début d'un nouveau segment.


PCRE_INFO_MINLENGTH

Si le motif a été étudié et qu'une longueur minimale pour les chaînes sujettes correspondantes a été calculée, sa valeur est retournée. Sinon, la valeur retournée est -1. La valeur est un nombre de caractères, qui en mode UTF peut être différent du nombre d'unités de données. Le quatrième argument doit pointer vers une variable de type int. Une valeur non négative est une borne inférieure à la longueur de toute chaîne correspondante. Il peut ne pas y avoir de chaînes de cette longueur qui correspondent réellement, mais toutes les chaînes qui correspondent sont au moins aussi longues.


PCRE_INFO_NAMECOUNT
PCRE_INFO_NAMEENTRYSIZE
PCRE_INFO_NAMETABLE

PCRE prend en charge l'utilisation de parenthèses capturantes nommées ainsi que numérotées. Les noms sont juste un moyen supplémentaire d'identifier les parenthèses, qui acquièrent toujours des numéros. Plusieurs fonctions pratiques telles que pcre_get_named_substring() sont fournies pour extraire les sous-chaînes capturées par nom. Il est également possible d'extraire les données directement, en convertissant d'abord le nom en numéro afin d'accéder aux pointeurs corrects dans le vecteur de sortie (décrit avec pcre_exec() ci-dessous). Pour effectuer la conversion, vous devez utiliser la table de correspondance nom-numéro, qui est décrite par ces trois valeurs.

La table se compose d'un certain nombre d'entrées de taille fixe. PCRE_INFO_NAMECOUNT donne le nombre d'entrées, et PCRE_INFO_NAMEENTRYSIZE donne la taille de chaque entrée ; ces deux valeurs retournent un entier. La taille de l'entrée dépend de la longueur du nom le plus long. PCRE_INFO_NAMETABLE retourne un pointeur vers la première entrée de la table. Il s'agit d'un pointeur vers char dans la bibliothèque 8 bits, où les deux premiers octets de chaque entrée sont le numéro de la parenthèse capturante, octet de poids fort en premier. Dans la bibliothèque 16 bits, le pointeur pointe vers des unités de données 16 bits, la première contenant le numéro de la parenthèse. Dans la bibliothèque 32 bits, le pointeur pointe vers des unités de données 32 bits, la première contenant le numéro de la parenthèse. Le reste de l'entrée est le nom correspondant, terminé par un zéro.

Les noms sont par ordre alphabétique. Si (?| est utilisé pour créer plusieurs groupes avec le même numéro, comme décrit dans la section sur les numéros de sous-motifs en double de la page pcrepattern, les groupes peuvent recevoir le même nom, mais il n'y a qu'une seule entrée dans la table. Des noms différents pour des groupes du même numéro ne sont pas autorisés. Des noms dupliqués pour des sous-motifs avec des numéros différents sont autorisés, mais seulement si PCRE_DUPNAMES est défini. Ils apparaissent dans la table dans l'ordre où ils ont été trouvés dans le motif. En l'absence de (?| ce n'est pas nécessairement le cas, car les sous-motifs ultérieurs peuvent avoir des numéros inférieurs.

À titre d'exemple simple de la table nom/numéro, considérons le motif suivant après compilation par la bibliothèque 8 bits (supposons que PCRE_EXTENDED soit défini, de sorte que les espaces blancs - y compris les sauts de ligne - soient ignorés) :


(?<date> (?<year>(\d\d)?\d\d) -
(?<month>\d\d) - (?<day>\d\d) )

Il y a quatre sous-motifs nommés, donc la table a quatre entrées, et chaque entrée de la table a huit octets de long. La table est la suivante, avec les octets non imprimables montrés en hexadécimal, et les octets indéfinis montrés comme ?? :


00 01 d a t e 00 ??
00 05 d a y 00 ?? ??
00 04 m o n t h 00
00 02 y e a r 00 ??

Lors de la rédaction de code pour extraire des données de sous-motifs nommés à l'aide de la table de correspondance nom-numéro, n'oubliez pas que la longueur des entrées sera probablement différente pour chaque motif compilé.


PCRE_INFO_OKPARTIAL

Retourne 1 si le motif peut être utilisé pour une correspondance partielle avec pcre_exec(), sinon 0. Le quatrième argument doit pointer vers une variable de type int. À partir de la version 8.00, cela retourne toujours 1, car les restrictions qui s'appliquaient auparavant à la correspondance partielle ont été levées. La documentation pcrepartial donne les détails sur la correspondance partielle.


PCRE_INFO_OPTIONS

Retourne une copie des options avec lesquelles le motif a été compilé. Le quatrième argument doit pointer vers une variable de type unsigned long int. Ces bits d'options sont ceux spécifiés dans l'appel à pcre_compile(), modifiés par tous les paramètres d'options de haut niveau au début du motif lui-même. En d'autres termes, ce sont les options qui seront en vigueur au début de la correspondance. Par exemple, si le motif /(?im)abc(?-i)d/ est compilé avec l'option PCRE_EXTENDED, le résultat est PCRE_CASELESS, PCRE_MULTILINE, et PCRE_EXTENDED.

Un motif est automatiquement ancré par PCRE si toutes ses alternatives de haut niveau commencent par l'un des éléments suivants :


^ sauf si PCRE_MULTILINE est défini
\A toujours
\G toujours
.* si PCRE_DOTALL est défini et qu'il n'y a pas de références arrière
au sous-motif dans lequel .* apparaît

Pour de tels motifs, le bit PCRE_ANCHORED est défini dans les options retournées par pcre_fullinfo().


PCRE_INFO_RECURSIONLIMIT

Si le motif a défini une limite de récursion en incluant un élément de la forme (*LIMIT_RECURSION=nnnn) au début, la valeur est retournée. Le quatrième argument doit pointer vers un entier non signé 32 bits. Si aucune valeur de ce type n'a été définie, l'appel à pcre_fullinfo() retourne l'erreur PCRE_ERROR_UNSET.


PCRE_INFO_SIZE

Retourne la taille du motif compilé en octets (pour les trois bibliothèques). Le quatrième argument doit pointer vers une variable de type size_t. Cette valeur n'inclut pas la taille de la structure pcre qui est retournée par pcre_compile(). La valeur passée comme argument à pcre_malloc() lorsque pcre_compile() obtient de la mémoire pour y placer les données compilées est la valeur retournée par cette option plus la taille de la structure pcre. L'étude d'un motif compilé, avec ou sans JIT, ne modifie pas la valeur retournée par cette option.


PCRE_INFO_STUDYSIZE

Retourne la taille en octets (pour les trois bibliothèques) du bloc de données pointé par le champ study_data dans un bloc pcre_extra. Si pcre_extra est NULL, ou s'il n'y a pas de données d'étude, zéro est retourné. Le quatrième argument doit pointer vers une variable de type size_t. Le champ study_data est défini par pcre_study() pour enregistrer des informations qui accéléreront la correspondance (voir la section intitulée "Étudier un motif" ci-dessus). Le format du bloc study_data est privé, mais sa longueur est mise à disposition via cette option afin qu'il puisse être sauvegardé et restauré (voir la documentation pcreprecompile pour les détails).


PCRE_INFO_REQUIREDCHARFLAGS

Retourne 1 s'il existe une unité de données littérale la plus à droite qui doit exister dans toute chaîne correspondante, autre qu'à son début. Le quatrième argument doit pointer vers une variable de type int. S'il n'existe pas de telle valeur, 0 est retourné. Si 1 est retourné, la valeur du caractère elle-même peut être récupérée en utilisant PCRE_INFO_REQUIREDCHAR.

Pour les motifs ancrés, une dernière valeur littérale n'est enregistrée que si elle suit quelque chose de longueur variable. Par exemple, pour le motif /^a\d+z\d+/ la valeur retournée est 1 (avec "z" retourné par PCRE_INFO_REQUIREDCHAR), mais pour /^a\dz\d/ la valeur retournée est 0.


PCRE_INFO_REQUIREDCHAR

Retourne la valeur de l'unité de données littérale la plus à droite qui doit exister dans toute chaîne correspondante, autre qu'à son début, si une telle valeur a été enregistrée. Le quatrième argument doit pointer vers une variable de type uint32_t. S'il n'y a pas de telle valeur, 0 est retourné.

COMPTES DE RÉFÉRENCE

int pcre_refcount(pcre *code, int adjust);

La fonction pcre_refcount() est utilisée pour maintenir un compteur de références dans le bloc de données qui contient un motif compilé. Elle est fournie pour les applications qui fonctionnent de manière orientée objet, où différentes parties de l'application peuvent utiliser le même motif compilé, mais vous voulez libérer le bloc lorsqu'elles ont toutes terminé.

Lorsqu'un motif est compilé, le champ du compteur de références est initialisé à zéro. Il n'est modifié qu'en appelant cette fonction, dont l'action est d'ajouter la valeur adjust (qui peut être positive ou négative) à celui-ci. Le résultat de la fonction est la nouvelle valeur. Cependant, la valeur du compteur est limitée à se situer entre 0 et 65535, inclus. Si la nouvelle valeur est en dehors de ces limites, elle est forcée à la limite appropriée.

Sauf lorsqu'il est nul, le compteur de références n'est pas correctement préservé si un motif est compilé sur un hôte et ensuite transféré à un hôte dont l'ordre des octets est différent. (Cela semble un scénario très improbable.)

CORRESPONDANCE D'UN MOTIF : LA FONCTION TRADITIONNELLE

int pcre_exec(const pcre *code, const pcre_extra *extra,
     const char *subject, int length, int startoffset,
     int options, int *ovector, int ovecsize);

La fonction pcre_exec() est appelée pour faire correspondre une chaîne sujette à un motif compilé, qui est passé dans l'argument code. Si le motif a été étudié, le résultat de l'étude doit être passé dans l'argument extra. Vous pouvez appeler pcre_exec() avec les mêmes arguments code et extra autant de fois que vous le souhaitez, afin de faire correspondre différentes chaînes sujettes avec le même motif.

Cette fonction est la principale fonctionnalité de correspondance de la bibliothèque, et elle fonctionne de manière similaire à Perl. Pour un usage spécialisé, il existe également une fonction de correspondance alternative, qui est décrite ci-dessous dans la section concernant la fonction pcre_dfa_exec().

Dans la plupart des applications, le motif aura été compilé (et optionnellement étudié) dans le même processus qui appelle pcre_exec(). Cependant, il est possible de sauvegarder les motifs compilés et les données d'étude, puis de les utiliser plus tard dans différents processus, potentiellement même sur différents hôtes. Pour une discussion à ce sujet, voir la documentation pcreprecompile.

Voici un exemple d'appel simple à pcre_exec() :


int rc;
int ovector[30];
rc = pcre_exec(
re, /* résultat de pcre_compile() */
NULL, /* nous

/* ne pas avoir étudié le schéma */
"une chaîne quelconque", /* la chaîne sujet */
11, /* la longueur de la chaîne sujet */
0, /* commencer à l'offset 0 dans le sujet */
0, /* options par défaut */
ovector, /* vecteur d'entiers pour les informations de sous-chaîne */
30); /* nombre d'éléments (PAS la taille en octets) */

Données supplémentaires pour pcre_exec()

Si l'argument extra n'est pas NULL, il doit pointer vers un bloc de données pcre_extra. La fonction pcre_study() renvoie un tel bloc (lorsqu'elle ne renvoie pas NULL), mais vous pouvez également en créer un vous-même et y passer des informations supplémentaires. Le bloc pcre_extra contient les champs suivants (pas nécessairement dans cet ordre) :


unsigned long int flags;
void *study_data;
void *executable_jit;
unsigned long int match_limit;
unsigned long int match_limit_recursion;
void *callout_data;
const unsigned char *tables;
unsigned char **mark;

Dans la version 16 bits de cette structure, le champ mark a le type "PCRE_UCHAR16 **".

Dans la version 32 bits de cette structure, le champ mark a le type "PCRE_UCHAR32 **".

Le champ flags est utilisé pour spécifier quels autres champs sont définis. Les bits de drapeau sont :


PCRE_EXTRA_CALLOUT_DATA
PCRE_EXTRA_EXECUTABLE_JIT
PCRE_EXTRA_MARK
PCRE_EXTRA_MATCH_LIMIT
PCRE_EXTRA_MATCH_LIMIT_RECURSION
PCRE_EXTRA_STUDY_DATA
PCRE_EXTRA_TABLES

Les autres bits de drapeau doivent être mis à zéro. Les champs study_data et parfois executable_jit sont définis dans le bloc pcre_extra renvoyé par pcre_study(), avec les bits de drapeau appropriés. Vous ne devez pas les définir vous-même, mais vous pouvez ajouter au bloc en définissant d'autres champs et leurs bits de drapeau correspondants.

Le champ match_limit fournit un moyen d'empêcher PCRE d'utiliser une énorme quantité de ressources lors de l'exécution de motifs qui ne correspondront pas, mais qui ont un très grand nombre de possibilités dans leurs arbres de recherche. L'exemple classique est un motif qui utilise des répétitions illimitées imbriquées.

En interne, pcre_exec() utilise une fonction appelée match(), qu'il appelle de manière répétée (parfois récursivement). La limite définie par match_limit est imposée au nombre de fois que cette fonction est appelée pendant une correspondance, ce qui a pour effet de limiter la quantité de retour arrière qui peut avoir lieu. Pour les motifs non ancrés, le compteur redémarre à zéro pour chaque position dans la chaîne sujet.

Lorsque pcre_exec() est appelée avec un motif qui a été étudié avec succès avec une option JIT, la manière dont la correspondance est exécutée est complètement différente. Cependant, il y a toujours la possibilité de correspondances incontrôlées qui durent très longtemps, et donc la valeur match_limit est également utilisée dans ce cas (mais d'une manière différente) pour limiter la durée de la correspondance.

La valeur par défaut de la limite peut être définie lors de la compilation de PCRE ; la valeur par défaut est de 10 millions, ce qui gère tous les cas sauf les plus extrêmes. Vous pouvez remplacer la valeur par défaut en fournissant à pcre_exec() un bloc pcre_extra dans lequel match_limit est défini, et PCRE_EXTRA_MATCH_LIMIT est défini dans le champ flags. Si la limite est dépassée, pcre_exec() renvoie PCRE_ERROR_MATCHLIMIT.

Une valeur pour la limite de correspondance peut également être fournie par un élément au début d'un motif de la forme


(*LIMIT_MATCH=d)

où d est un nombre décimal. Cependant, un tel réglage est ignoré à moins que d ne soit inférieur à la limite définie par l'appelant de pcre_exec() ou, si aucune limite n'est définie, inférieur à la valeur par défaut.

Le champ match_limit_recursion est similaire à match_limit, mais au lieu de limiter le nombre total d'appels à match(), il limite la profondeur de la récursion. La profondeur de la récursion est un nombre plus petit que le nombre total d'appels, car tous les appels à match() ne sont pas récursifs. Cette limite n'est utile que si elle est définie plus petite que match_limit.

La limitation de la profondeur de récursion limite la quantité de pile machine qui peut être utilisée, ou, lorsque PCRE a été compilé pour utiliser la mémoire du tas au lieu de la pile, la quantité de mémoire du tas qui peut être utilisée. Cette limite n'est pas pertinente et est ignorée lorsque la correspondance est effectuée à l'aide de code compilé JIT.

La valeur par défaut pour match_limit_recursion peut être définie lors de la compilation de PCRE ; la valeur par défaut est la même que celle par défaut pour match_limit. Vous pouvez remplacer la valeur par défaut en fournissant à pcre_exec() un bloc pcre_extra dans lequel match_limit_recursion est défini, et PCRE_EXTRA_MATCH_LIMIT_RECURSION est défini dans le champ flags. Si la limite est dépassée, pcre_exec() renvoie PCRE_ERROR_RECURSIONLIMIT.

Une valeur pour la limite de récursion peut également être fournie par un élément au début d'un motif de la forme


(*LIMIT_RECURSION=d)

où d est un nombre décimal. Cependant, un tel réglage est ignoré à moins que d ne soit inférieur à la limite définie par l'appelant de pcre_exec() ou, si aucune limite n'est définie, inférieur à la valeur par défaut.

Le champ callout_data est utilisé conjointement avec la fonctionnalité de "callout" et est décrit dans la documentation de pcrecallout.

Le champ tables est fourni pour être utilisé avec des motifs qui ont été pré-compilés à l'aide de tables de caractères personnalisées, sauvegardés sur disque ou ailleurs, puis rechargés, car les tables utilisées pour compiler un motif ne sont pas sauvegardées avec lui. Voir la documentation de pcreprecompile pour une discussion sur la sauvegarde des motifs compilés pour une utilisation ultérieure. Si NULL est passé en utilisant ce mécanisme, cela force l'utilisation des tables internes de PCRE.

Avertissement : Les tables que pcre_exec() utilise doivent être les mêmes que celles utilisées lors de la compilation du motif. Si ce n'est pas le cas, le comportement de pcre_exec() est indéfini. Par conséquent, lorsqu'un motif est compilé et mis en correspondance dans le même processus, ce champ ne doit jamais être défini. Dans ce cas (le plus courant), le pointeur de table correct est automatiquement passé de pcre_compile() à pcre_exec() avec le motif compilé.

Si PCRE_EXTRA_MARK est défini dans le champ flags, le champ mark doit être défini pour pointer vers une variable appropriée. Si le motif contient des verbes de contrôle de retour arrière tels que (*MARK:NAME), et que l'exécution aboutit à un nom à renvoyer, un pointeur vers la chaîne de nom (terminée par zéro) est placé dans la variable pointée par le champ mark. Les noms sont à l'intérieur du motif compilé ; si vous souhaitez conserver un tel nom, vous devez le copier avant de libérer la mémoire d'un motif compilé. S'il n'y a pas de nom à renvoyer, la variable pointée par le champ mark est mise à NULL. Pour plus de détails sur les verbes de contrôle de retour arrière, voir la section intitulée "Contrôle du retour arrière" dans la documentation de pcrepattern.

Bits d'options pour pcre_exec()

Les bits inutilisés de l'argument options pour pcre_exec() doivent être zéro. Les seuls bits qui peuvent être définis sont PCRE_ANCHORED, PCRE_NEWLINE_xxx, PCRE_NOTBOL, PCRE_NOTEOL, PCRE_NOTEMPTY, PCRE_NOTEMPTY_ATSTART, PCRE_NO_START_OPTIMIZE, PCRE_NO_UTF8_CHECK, PCRE_PARTIAL_HARD, et PCRE_PARTIAL_SOFT.

Si le motif a été étudié avec succès avec l'une des options de compilation juste-à-temps (JIT), les seules options prises en charge pour l'exécution JIT sont PCRE_NO_UTF8_CHECK, PCRE_NOTBOL, PCRE_NOTEOL, PCRE_NOTEMPTY, PCRE_NOTEMPTY_ATSTART, PCRE_PARTIAL_HARD, et PCRE_PARTIAL_SOFT. Si une option non prise en charge est utilisée, l'exécution JIT est désactivée et le code interprétatif normal dans pcre_exec() est exécuté.


PCRE_ANCHORED

L'option PCRE_ANCHORED limite pcre_exec() à la recherche d'une correspondance à la première position correspondante. Si un motif a été compilé avec PCRE_ANCHORED, ou s'est avéré ancré par son contenu, il ne peut pas être désancré au moment de la correspondance.


PCRE_BSR_ANYCRLF
PCRE_BSR_UNICODE

Ces options (qui sont mutuellement exclusives) contrôlent ce que la séquence d'échappement \R fait correspondre. Le choix est soit de faire correspondre uniquement CR, LF, ou CRLF, soit de faire correspondre toute séquence de nouvelle ligne Unicode. Ces options remplacent le choix qui a été fait ou par défaut lors de la compilation du motif.


PCRE_NEWLINE_CR
PCRE_NEWLINE_LF
PCRE_NEWLINE_CRLF
PCRE_NEWLINE_ANYCRLF
PCRE_NEWLINE_ANY

Ces options remplacent la définition de nouvelle ligne qui a été choisie ou par défaut lors de la compilation du motif. Pour plus de détails, voir la description de pcre_compile() ci-dessus. Pendant la correspondance, le choix de la nouvelle ligne affecte le comportement des méta-caractères point, circonflexe et dollar. Il peut également modifier la manière dont la position de correspondance est avancée après un échec de correspondance pour un motif non ancré.

Lorsque PCRE_NEWLINE_CRLF, PCRE_NEWLINE_ANYCRLF, ou PCRE_NEWLINE_ANY est défini, et qu'une tentative de correspondance pour un motif non ancré échoue alors que la position actuelle est sur une séquence CRLF, et que le motif ne contient aucune correspondance explicite pour les caractères CR ou LF, la position de correspondance est avancée de deux caractères au lieu d'un, c'est-à-dire après le CRLF.

La règle ci-dessus est un compromis qui fait fonctionner les cas les plus courants comme prévu. Par exemple, si le motif est .+A (et que l'option PCRE_DOTALL n'est pas définie), il ne correspond pas à la chaîne "\r\nA" car, après avoir échoué au début, il saute le CR et le LF avant de réessayer. Cependant, le motif [\r\n]A correspond à cette chaîne, car il contient une référence explicite à CR ou LF, et avance donc seulement d'un caractère après le premier échec.

Une correspondance explicite pour CR ou LF est soit une apparition littérale de l'un de ces caractères, soit l'une des séquences d'échappement \r ou \n. Les correspondances implicites telles que [^X] ne sont pas prises en compte, pas plus que \s (qui inclut CR et LF dans les caractères qu'il fait correspondre).

Nonobstant ce qui précède, des effets anormaux peuvent encore se produire lorsque CRLF est une séquence de nouvelle ligne valide et que des séquences d'échappement \r ou \n explicites apparaissent dans le motif.


PCRE_NOTBOL

Cette option spécifie que le premier caractère de la chaîne sujet n'est pas le début d'une ligne, de sorte que le méta-caractère circonflexe ne doit pas correspondre avant lui. Définir ceci sans PCRE_MULTILINE (au moment de la compilation) fait que le circonflexe ne correspond jamais. Cette option n'affecte que le comportement du méta-caractère circonflexe. Elle n'affecte pas \A.


PCRE_NOTEOL

Cette option spécifie que la fin de la chaîne sujet n'est pas la fin d'une ligne, de sorte que le méta-caractère dollar ne doit pas correspondre

it ni (sauf en mode multiligne) un retour à la ligne immédiatement avant. Définir ceci sans PCRE_MULTILINE (au moment de la compilation) fait que le dollar ne correspond jamais. Cette option n'affecte que le comportement du métacaractère dollar. Elle n'affecte pas \Z ou \z.


PCRE_NOTEMPTY

Une chaîne vide n'est pas considérée comme une correspondance valide si cette option est définie. S'il y a des alternatives dans le motif, elles sont essayées. Si toutes les alternatives correspondent à la chaîne vide, la correspondance entière échoue. Par exemple, si le motif


a?b?

est appliqué à une chaîne ne commençant pas par « a » ou « b », il correspond à une chaîne vide au début du sujet. Avec PCRE_NOTEMPTY défini, cette correspondance n'est pas valide, donc PCRE recherche plus loin dans la chaîne des occurrences de « a » ou « b ».


PCRE_NOTEMPTY_ATSTART

C'est similaire à PCRE_NOTEMPTY, sauf qu'une correspondance de chaîne vide qui n'est pas au début du sujet est autorisée. Si le motif est ancré, une telle correspondance ne peut se produire que si le motif contient \K.

Perl n'a pas d'équivalent direct de PCRE_NOTEMPTY ou PCRE_NOTEMPTY_ATSTART, mais il traite spécialement une correspondance de motif de chaîne vide dans sa fonction split() et lors de l'utilisation du modificateur /g. Il est possible d'émuler le comportement de Perl après avoir trouvé une chaîne nulle en essayant d'abord à nouveau la correspondance au même décalage avec PCRE_NOTEMPTY_ATSTART et PCRE_ANCHORED, puis, si cela échoue, en avançant le décalage de départ (voir ci-dessous) et en essayant à nouveau une correspondance ordinaire. Il existe du code qui démontre comment faire cela dans le programme d'exemple pcredemo. Dans le cas le plus général, vous devez vérifier si la convention de retour à la ligne reconnaît CRLF comme un retour à la ligne, et si c'est le cas, et que le caractère courant est CR suivi de LF, avancer le décalage de départ de deux caractères au lieu d'un.


PCRE_NO_START_OPTIMIZE

Il existe un certain nombre d'optimisations que pcre_exec() utilise au début d'une correspondance, afin d'accélérer le processus. Par exemple, s'il est connu qu'une correspondance non ancrée doit commencer par un caractère spécifique, il recherche ce caractère dans le sujet et échoue immédiatement s'il ne le trouve pas, sans exécuter réellement la fonction de correspondance principale. Cela signifie qu'un élément spécial tel que (*COMMIT) au début d'un motif n'est pas considéré avant qu'un point de départ approprié pour la correspondance n'ait été trouvé. De plus, lorsque des appels de rappel ou des éléments (*MARK) sont utilisés, ces optimisations de « démarrage » peuvent les faire sauter si le motif n'est jamais réellement utilisé. Les optimisations de démarrage sont, en effet, un pré-balayage du sujet qui a lieu avant que le motif ne soit exécuté.

L'option PCRE_NO_START_OPTIMIZE désactive les optimisations de démarrage, entraînant éventuellement une dégradation des performances, mais garantissant que, dans les cas où le résultat est « pas de correspondance », les appels de rappel se produisent et que des éléments tels que (*COMMIT) et (*MARK) sont pris en compte à chaque position de départ possible dans la chaîne sujet. Si PCRE_NO_START_OPTIMIZE est défini au moment de la compilation, il ne peut pas être désactivé au moment de la correspondance. L'utilisation de PCRE_NO_START_OPTIMIZE au moment de la correspondance (c'est-à-dire en le passant à pcre_exec()) désactive l'exécution JIT ; dans cette situation, la correspondance est toujours effectuée de manière interprétée.

La définition de PCRE_NO_START_OPTIMIZE peut modifier le résultat d'une opération de correspondance. Considérons le motif


(*COMMIT)ABC

Lors de sa compilation, PCRE enregistre le fait qu'une correspondance doit commencer par le caractère « A ». Supposons que la chaîne sujet soit « DEFABC ». L'optimisation de démarrage balaie le sujet, trouve « A » et lance la première tentative de correspondance à partir de là. L'élément (*COMMIT) signifie que le motif doit correspondre à la position de départ actuelle, ce qui est le cas ici. Cependant, si la même correspondance est exécutée avec PCRE_NO_START_OPTIMIZE défini, le balayage initial du sujet ne se produit pas. La première tentative de correspondance est lancée à partir de « D » et, lorsque celle-ci échoue, (*COMMIT) empêche toute autre correspondance d'être essayée, de sorte que le résultat global est « pas de correspondance ». Si le motif est étudié, d'autres optimisations de démarrage peuvent être utilisées. Par exemple, une longueur minimale pour le sujet peut être enregistrée. Considérons le motif


(*MARK:A)(X|Y)

La longueur minimale d'une correspondance est d'un caractère. Si le sujet est « ABC », des tentatives seront faites pour faire correspondre « ABC », « BC », « C », et enfin une chaîne vide. Si le motif est étudié, la dernière tentative n'a pas lieu, car PCRE sait que le sujet est trop court, et donc le (*MARK) n'est jamais rencontré. Dans ce cas, l'étude du motif n'affecte pas le résultat global de la correspondance, qui est toujours « pas de correspondance », mais elle affecte les informations auxiliaires retournées.


PCRE_NO_UTF8_CHECK

Lorsque PCRE_UTF8 est défini au moment de la compilation, la validité du sujet en tant que chaîne UTF-8 est automatiquement vérifiée lorsque pcre_exec() est appelé ultérieurement. Toute la chaîne est vérifiée avant toute autre opération. La valeur de startoffset est également vérifiée pour s'assurer qu'elle pointe vers le début d'un caractère UTF-8. Il y a une discussion sur la validité des chaînes UTF-8 dans la page pcreunicode. Si une séquence d'octets invalide est trouvée, pcre_exec() renvoie l'erreur PCRE_ERROR_BADUTF8 ou, si PCRE_PARTIAL_HARD est défini et que le problème est un caractère tronqué à la fin du sujet, PCRE_ERROR_SHORTUTF8. Dans les deux cas, des informations sur la nature précise de l'erreur peuvent également être retournées (voir les descriptions de ces erreurs dans la section intitulée Valeurs de retour d'erreur de pcre_exec() ci-dessous). Si startoffset contient une valeur qui ne pointe pas vers le début d'un caractère UTF-8 (ou vers la fin du sujet), PCRE_ERROR_BADUTF8_OFFSET est retourné.

Si vous savez déjà que votre sujet est valide et que vous souhaitez ignorer ces vérifications pour des raisons de performance, vous pouvez définir l'option PCRE_NO_UTF8_CHECK lors de l'appel à pcre_exec(). Vous pourriez vouloir le faire pour le deuxième appel et les appels suivants à pcre_exec() si vous effectuez des appels répétés pour trouver toutes les correspondances dans une seule chaîne sujet. Cependant, vous devez être sûr que la valeur de startoffset pointe vers le début d'un caractère (ou vers la fin du sujet). Lorsque PCRE_NO_UTF8_CHECK est défini, l'effet du passage d'une chaîne invalide en tant que sujet ou d'une valeur invalide de startoffset est indéfini. Votre programme peut planter ou boucler.


PCRE_PARTIAL_HARD
PCRE_PARTIAL_SOFT

Ces options activent la fonctionnalité de correspondance partielle. Pour des raisons de compatibilité descendante, PCRE_PARTIAL est synonyme de PCRE_PARTIAL_SOFT. Une correspondance partielle se produit si la fin de la chaîne sujet est atteinte avec succès, mais qu'il n'y a pas assez de caractères sujet pour compléter la correspondance. Si cela se produit lorsque PCRE_PARTIAL_SOFT (mais pas PCRE_PARTIAL_HARD) est défini, la correspondance continue en testant les alternatives restantes. Ce n'est que si aucune correspondance complète ne peut être trouvée que PCRE_ERROR_PARTIAL est renvoyé au lieu de PCRE_ERROR_NOMATCH. En d'autres termes, PCRE_PARTIAL_SOFT indique que l'appelant est prêt à gérer une correspondance partielle, mais uniquement si aucune correspondance complète ne peut être trouvée.

Si PCRE_PARTIAL_HARD est défini, il remplace PCRE_PARTIAL_SOFT. Dans ce cas, si une correspondance partielle est trouvée, pcre_exec() renvoie immédiatement PCRE_ERROR_PARTIAL, sans examiner d'autres alternatives. En d'autres termes, lorsque PCRE_PARTIAL_HARD est défini, une correspondance partielle est considérée comme plus importante qu'une correspondance complète alternative.

Dans les deux cas, la partie de la chaîne qui a été inspectée lors de la découverte de la correspondance partielle est définie comme la première chaîne correspondante. Il y a une discussion plus détaillée sur les correspondances partielles et multi-segments, avec des exemples, dans la documentation pcrepartial.

La chaîne à faire correspondre par pcre_exec()

La chaîne sujet est passée à pcre_exec() sous forme de pointeur dans subject, une longueur dans length, et un décalage de départ dans startoffset. Les unités pour length et startoffset sont des octets pour la bibliothèque 8 bits, des éléments de données 16 bits pour la bibliothèque 16 bits, et des éléments de données 32 bits pour la bibliothèque 32 bits.

Si startoffset est négatif ou supérieur à la longueur du sujet, pcre_exec() renvoie PCRE_ERROR_BADOFFSET. Lorsque le décalage de départ est zéro, la recherche d'une correspondance commence au début du sujet, et c'est de loin le cas le plus courant. En mode UTF-8 ou UTF-16, le décalage doit pointer vers le début d'un caractère, ou vers la fin du sujet (en mode UTF-32, une unité de données égale un caractère, donc tous les décalages sont valides). Contrairement à la chaîne de motif, le sujet peut contenir des zéros binaires.

Un décalage de départ non nul est utile lors de la recherche d'une autre correspondance dans le même sujet en appelant à nouveau pcre_exec() après un succès précédent. Définir startoffset diffère de simplement passer outre une chaîne raccourcie et de définir PCRE_NOTBOL dans le cas d'un motif commençant par un type quelconque de recherche arrière. Par exemple, considérons le motif


\Biss\B

qui trouve des occurrences de « iss » au milieu de mots. (\B ne correspond que si la position actuelle dans le sujet n'est pas une limite de mot.) Lorsqu'il est appliqué à la chaîne « Mississippi », le premier appel à pcre_exec() trouve la première occurrence. Si pcre_exec() est appelé à nouveau avec seulement le reste du sujet, à savoir « issippi », il ne correspond pas, car \B est toujours faux au début du sujet, qui est considéré comme une limite de mot. Cependant, si pcre_exec() est passé à nouveau avec la chaîne entière, mais avec startoffset défini sur 4, il trouve la deuxième occurrence de « iss » car il peut regarder derrière le point de départ pour découvrir qu'il est précédé par une lettre.

Trouver toutes les correspondances dans un sujet est délicat lorsque le motif peut correspondre à une chaîne vide. Il est possible d'émuler le comportement /g de Perl en essayant d'abord à nouveau la correspondance au même décalage, avec les options PCRE_NOTEMPTY_ATSTART et PCRE_ANCHORED, puis, si cela échoue, en avançant le décalage de départ et en essayant à nouveau une correspondance ordinaire. Il existe du code qui démontre comment faire cela dans le programme d'exemple pcredemo. Dans le cas le plus général, vous devez vérifier si la convention de retour à la ligne reconnaît CRLF comme un retour à la ligne, et si c'est le cas, et que le caractère courant est CR suivi de LF, avancez le décalage de départ de deux caractères au lieu d'un.

Si un décalage de départ non nul est passé lorsque le motif est ancré, une tentative de correspondance au décalage donné est effectuée. Cela ne peut réussir que si le motif n'exige pas que la correspondance soit au début du sujet.

Comment pcre_exec() renvoie les sous-chaînes capturées

Comment pcre_exec() renvoie les sous-chaînes capturées

En général, un motif correspond à une certaine portion de la chaîne sujet, et de plus, d'autres sous-chaînes de la chaîne sujet peuvent être extraites par des parties du motif. En suivant l'usage du livre de Jeffrey Friedl, cela est appelé « capturer » dans ce qui suit, et l'expression « sous-motif capturant » est utilisée pour un fragment de motif qui extrait une sous-chaîne. PCRE prend en charge plusieurs autres types de sous-motifs entre parenthèses qui ne provoquent pas la capture de sous-chaînes.

Les sous-chaînes capturées sont renvoyées à l'appelant via un vecteur d'entiers dont l'adresse est passée dans ovector. Le nombre d'éléments dans le vecteur est passé dans ovecsize, qui doit être un nombre non négatif. Note : cet argument n'est PAS la taille de ovector en octets.

Les deux premiers tiers du vecteur sont utilisés pour renvoyer les sous-chaînes capturées, chaque sous-chaîne utilisant une paire d'entiers. Le tiers restant du vecteur est utilisé comme espace de travail par pcre_exec() lors de la correspondance des sous-motifs capturants, et n'est pas disponible pour renvoyer des informations. Le nombre passé dans ovecsize doit toujours être un multiple de trois. S'il ne l'est pas, il est arrondi à la baisse.

Lorsqu'une correspondance est réussie, les informations sur les sous-chaînes capturées sont renvoyées dans des paires d'entiers, en commençant au début de ovector, et se poursuivant jusqu'aux deux tiers de sa longueur au maximum. Le premier élément de chaque paire est défini à l'offset du premier caractère d'une sous-chaîne, et le second est défini à l'offset du premier caractère après la fin d'une sous-chaîne. Ces valeurs sont toujours des offsets d'unité de données, même en mode UTF. Ce sont des offsets en octets dans la bibliothèque 8 bits, des offsets d'élément de données 16 bits dans la bibliothèque 16 bits, et des offsets d'élément de données 32 bits dans la bibliothèque 32 bits. Note : ce ne sont pas des comptes de caractères.

La première paire d'entiers, ovector[0] et ovector[1], identifie la partie de la chaîne sujet correspondant à l'ensemble du motif. La paire suivante est utilisée pour le premier sous-motif capturant, et ainsi de suite. La valeur renvoyée par pcre_exec() est un de plus que la paire de plus haut numéro qui a été définie. Par exemple, si deux sous-chaînes ont été capturées, la valeur renvoyée est 3. S'il n'y a pas de sous-motifs capturants, la valeur renvoyée pour une correspondance réussie est 1, indiquant que seule la première paire d'offsets a été définie.

Si un sous-motif capturant est trouvé plusieurs fois, c'est la dernière partie de la chaîne qu'il a trouvée qui est renvoyée.

Si le vecteur est trop petit pour contenir tous les offsets des sous-chaînes capturées, il est utilisé autant que possible (jusqu'à deux tiers de sa longueur), et la fonction renvoie une valeur de zéro. Si ni la chaîne effectivement trouvée ni aucune sous-chaîne capturée n'intéresse, pcre_exec() peut être appelée avec ovector passé en NULL et ovecsize à zéro. Cependant, si le motif contient des références arrière et que ovector n'est pas assez grand pour mémoriser les sous-chaînes associées, PCRE doit allouer de la mémoire supplémentaire pour une utilisation pendant la correspondance. Il est donc généralement conseillé de fournir un ovector de taille raisonnable.

Il y a certains cas où zéro est renvoyé (indiquant un débordement de vecteur) alors qu'en fait, le vecteur est exactement de la bonne taille pour la correspondance finale. Par exemple, considérez le motif


(a)(?:(b)c|bd)

Si un vecteur de 6 éléments (permettant seulement 1 sous-chaîne capturée) est donné avec la chaîne sujet « abd », pcre_exec() essaiera de définir la deuxième chaîne capturée, enregistrant ainsi un débordement de vecteur, avant de ne pas pouvoir faire correspondre « c » et de revenir en arrière pour essayer la deuxième alternative. Le retour zéro, cependant, indique correctement que le nombre maximum d'emplacements (à savoir 2) a été rempli. Dans des cas similaires où il y a un débordement temporaire, mais que le nombre final d'emplacements utilisés est en fait inférieur au maximum, une valeur non nulle est renvoyée.

La fonction pcre_fullinfo() peut être utilisée pour savoir combien de sous-motifs capturants il y a dans un motif compilé. La plus petite taille pour ovector qui permettra de prendre en charge n sous-chaînes capturées, en plus des offsets de la sous-chaîne correspondante trouvée par tout le motif, est de (n+1)*3.

Il est possible que le sous-motif capturant numéro n+1 corresponde à une partie du sujet alors que le sous-motif n n'a pas été utilisé du tout. Par exemple, si la chaîne « abc » est trouvée contre le motif (a|(z))(bc) le retour de la fonction est 4, et les sous-motifs 1 et 3 sont trouvés, mais le 2 ne l'est pas. Lorsque cela se produit, les deux valeurs dans les paires d'offsets correspondant aux sous-motifs inutilisés sont définies à -1.

Les valeurs d'offset qui correspondent aux sous-motifs inutilisés à la fin de l'expression sont également définies à -1. Par exemple, si la chaîne « abc » est trouvée contre le motif (abc)(x(yz)?)? les sous-motifs 2 et 3 ne sont pas trouvés. Le retour de la fonction est 2, car le sous-motif capturant utilisé le plus élevé est le numéro 1, et les offsets pour les deuxième et troisième sous-motifs capturants (en supposant que le vecteur est assez grand, bien sûr) sont définis à -1.

Note : Les éléments dans les deux premiers tiers de ovector qui ne correspondent pas à des parenthèses de capture dans le motif ne sont jamais modifiés. C'est-à-dire que si un motif contient n parenthèses de capture, pas plus que ovector[0] à ovector[2n+1] ne sont définis par pcre_exec(). Les autres éléments (dans les deux premiers tiers) conservent les valeurs qu'ils avaient précédemment.

Certaines fonctions pratiques sont fournies pour extraire les sous-chaînes capturées sous forme de chaînes distinctes. Celles-ci sont décrites ci-dessous.

Valeurs de retour d'erreur de pcre_exec()

Si pcre_exec() échoue, elle renvoie un nombre négatif. Les éléments suivants sont définis dans le fichier d'en-tête :


PCRE_ERROR_NOMATCH (-1)

La chaîne sujet n'a pas correspondu au motif.


PCRE_ERROR_NULL (-2)

Soit code, soit subject a été passé en tant que NULL, soit ovector était NULL et ovecsize n'était pas zéro.


PCRE_ERROR_BADOPTION (-3)

Un bit non reconnu a été défini dans l'argument options.


PCRE_ERROR_BADMAGIC (-4)

PCRE stocke un nombre magique de 4 octets au début du code compilé, pour intercepter le cas où un pointeur invalide lui est passé et pour détecter quand un motif compilé dans un environnement d'une certaine endianness est exécuté dans un environnement d'une autre endianness. C'est l'erreur que PCRE donne lorsque le nombre magique est absent.


PCRE_ERROR_UNKNOWN_OPCODE (-5)

Pendant l'exécution de la recherche de motif, un élément inconnu a été rencontré dans le motif compilé. Cette erreur peut être causée par un bug dans PCRE ou par une écrasement du motif compilé.


PCRE_ERROR_NOMEMORY (-6)

Si un motif contient des références arrière, mais que ovector passé à pcre_exec() n'est pas assez grand pour mémoriser les sous-chaînes référencées, PCRE obtient un bloc de mémoire au début de la recherche à cet effet. Si l'appel via pcre_malloc() échoue, cette erreur est donnée. La mémoire est automatiquement libérée à la fin de la recherche.

Cette erreur est également donnée si pcre_stack_malloc() échoue dans pcre_exec(). Cela ne peut se produire que lorsque PCRE a été compilé avec --disable-stack-for-recursion.


PCRE_ERROR_NOSUBSTRING (-7)

Cette erreur est utilisée par les fonctions pcre_copy_substring(), pcre_get_substring() et pcre_get_substring_list() (voir ci-dessous). Elle n'est jamais renvoyée par pcre_exec().


PCRE_ERROR_MATCHLIMIT (-8)

La limite de backtracking, spécifiée par le champ match_limit dans une structure pcre_extra (ou par défaut) a été atteinte. Voir la description ci-dessus.


PCRE_ERROR_CALLOUT (-9)

Cette erreur n'est jamais générée par pcre_exec() elle-même. Elle est fournie pour être utilisée par les fonctions de rappel (callout) qui souhaitent produire un code d'erreur distinctif. Voir la documentation pcrecallout pour plus de détails.


PCRE_ERROR_BADUTF8 (-10)

Une chaîne contenant une séquence d'octets UTF-8 invalide a été passée comme sujet, et l'option PCRE_NO_UTF8_CHECK n'était pas définie. Si la taille du vecteur de sortie (ovecsize) est d'au moins 2, l'offset en octets vers le début du caractère UTF-8 invalide est placé dans le premier élément, et un code de raison est placé dans le second élément. Les codes de raison sont listés dans la section suivante. Par souci de compatibilité ascendante, si PCRE_PARTIAL_HARD est défini et que le problème est un caractère UTF-8 tronqué à la fin du sujet (codes de raison 1 à 5), PCRE_ERROR_SHORTUTF8 est renvoyé au lieu de PCRE_ERROR_BADUTF8.


PCRE_ERROR_BADUTF8_OFFSET (-11)

La séquence d'octets UTF-8 qui a été passée comme sujet a été vérifiée et trouvée valide (l'option PCRE_NO_UTF8_CHECK n'était pas définie), mais la valeur de startoffset ne pointait pas vers le début d'un caractère UTF-8 ou vers la fin du sujet.


PCRE_ERROR_PARTIAL (-12)

La chaîne sujet n'a pas correspondu, mais elle a correspondu partiellement. Voir la documentation pcrepartial pour les détails de la correspondance partielle.


PCRE_ERROR_BADPARTIAL (-13)

Ce code n'est plus utilisé. Il était anciennement renvoyé lorsque l'option PCRE_PARTIAL était utilisée avec un motif compilé contenant des éléments qui n'étaient pas pris en charge pour la correspondance partielle. À partir de la version 8.00, il n'y a plus de restrictions sur la correspondance partielle.


PCRE_ERROR_INTERNAL (-14)

Une erreur interne inattendue s'est produite. Cette erreur pourrait être causée par un bug dans PCRE ou par une écrasement du motif compilé.


PCRE_ERROR_BADCOUNT (-15)

Cette erreur est donnée si la valeur de l'argument ovecsize est négative.


PCRE_ERROR_RECURSIONLIMIT (-21)

La limite de récursion interne, spécifiée par le champ match_limit_recursion dans une structure pcre_extra (ou par défaut) a été atteinte. Voir la description ci-dessus.


PCRE_ERROR_BADNEWLINE (-23)

Une combinaison invalide d'options PCRE_NEWLINE_xxx a été donnée.


PCRE_ERROR_BADOFFSET (-24)

La valeur de startoffset était négative ou supérieure à la longueur du sujet, c'est-à-dire la valeur dans length.


PCRE_ERROR_SHORTUTF8 (-25)

Cette erreur est renvoyée au lieu de PCRE_ERROR_BADUTF8 lorsque la chaîne sujet se termine par un caractère UTF-8 tronqué et que l'option PCRE_PARTIAL_HARD est définie. Les informations sur l'échec sont renvoyées comme pour PCRE_ERROR_BADUTF8. Il suffit en fait de détecter ce cas, mais

ce code d'erreur spécial PCRE_PARTIAL_HARD précède l'implémentation des informations retournées ; il est conservé pour des raisons de compatibilité ascendante.


PCRE_ERROR_RECURSELOOP (-26)

Cette erreur est renvoyée lorsque pcre_exec() détecte une boucle de récursion dans le motif. Plus précisément, cela signifie que le motif entier ou un sous-motif a été appelé de manière récursive pour la deuxième fois à la même position dans la chaîne sujet. Certains motifs simples qui pourraient faire cela sont détectés et éliminés au moment de la compilation, mais des cas plus compliqués, en particulier des récursions mutuelles entre deux sous-motifs différents, ne peuvent être détectés qu'au moment de l'exécution.


PCRE_ERROR_JIT_STACKLIMIT (-27)

Cette erreur est renvoyée lorsqu'un motif qui a été étudié avec succès en utilisant une option de compilation JIT est en cours de correspondance, mais que la mémoire disponible pour la pile de traitement juste-à-temps n'est pas assez grande. Voir la documentation pcrejit pour plus de détails.


PCRE_ERROR_BADMODE (-28)

Cette erreur est signalée si un motif compilé par la bibliothèque 8 bits est passé à une fonction de bibliothèque 16 bits ou 32 bits, ou vice versa.


PCRE_ERROR_BADENDIANNESS (-29)

Cette erreur est signalée si un motif qui a été compilé et sauvegardé est rechargé sur un hôte avec une endianness différente. La fonction utilitaire pcre_pattern_to_host_byte_order() peut être utilisée pour convertir un tel motif afin qu'il s'exécute sur le nouvel hôte.


PCRE_ERROR_JIT_BADOPTION

Cette erreur est renvoyée lorsqu'un motif qui a été étudié avec succès en utilisant une option de compilation JIT est en cours de correspondance, mais que le mode de correspondance (correspondance partielle ou complète) ne correspond à aucun mode de compilation JIT. Lorsque la fonction de chemin rapide JIT est utilisée, cette erreur peut également être signalée pour des options invalides. Voir la documentation pcrejit pour plus de détails.


PCRE_ERROR_BADLENGTH (-32)

Cette erreur est signalée si pcre_exec() est appelé avec une valeur négative pour l'argument length.

Les numéros d'erreur -16 à -20, -22 et 30 ne sont pas utilisés par pcre_exec().

Codes de raison pour les chaînes UTF-8 invalides

Cette section s'applique uniquement à la bibliothèque 8 bits. Les informations correspondantes pour les bibliothèques 16 bits et 32 bits se trouvent dans les pages pcre16 et pcre32.

Lorsque pcre_exec() renvoie PCRE_ERROR_BADUTF8 ou PCRE_ERROR_SHORTUTF8, et que la taille du vecteur de sortie (ovecsize) est au moins égale à 2, le décalage du début du caractère UTF-8 invalide est placé dans le premier élément du vecteur de sortie (ovector[0]) et un code de raison est placé dans le second élément (ovector[1]). Les codes de raison sont nommés dans le fichier d'en-tête pcre.h :


PCRE_UTF8_ERR1
PCRE_UTF8_ERR2
PCRE_UTF8_ERR3
PCRE_UTF8_ERR4
PCRE_UTF8_ERR5

La chaîne se termine par un caractère UTF-8 tronqué ; le code spécifie le nombre d'octets manquants (de 1 à 5). Bien que RFC 3629 limite les caractères UTF-8 à 4 octets au maximum, le schéma d'encodage (défini à l'origine par RFC 2279) autorise jusqu'à 6 octets, et c'est ce qui est vérifié en premier ; d'où la possibilité de 4 ou 5 octets manquants.


PCRE_UTF8_ERR6
PCRE_UTF8_ERR7
PCRE_UTF8_ERR8
PCRE_UTF8_ERR9
PCRE_UTF8_ERR10

Les deux bits les plus significatifs du 2ème, 3ème, 4ème, 5ème ou 6ème octet du caractère n'ont pas la valeur binaire 0b10 (c'est-à-dire que soit le bit le plus significatif est 0, soit le bit suivant est 1).


PCRE_UTF8_ERR11
PCRE_UTF8_ERR12

Un caractère qui est valide selon les règles de la RFC 2279 a soit 5, soit 6 octets de longueur ; ces points de code sont exclus par la RFC 3629.


PCRE_UTF8_ERR13

Un caractère de 4 octets a une valeur supérieure à 0x10fff ; ces points de code sont exclus par la RFC 3629.


PCRE_UTF8_ERR14

Un caractère de 3 octets a une valeur dans la plage 0xd800 à 0xdfff ; cette plage de points de code est réservée par RFC 3629 pour être utilisée avec UTF-16, et est donc exclue de UTF-8.


PCRE_UTF8_ERR15
PCRE_UTF8_ERR16
PCRE_UTF8_ERR17
PCRE_UTF8_ERR18
PCRE_UTF8_ERR19

Un caractère de 2, 3, 4, 5 ou 6 octets est « trop long », c'est-à-dire qu'il code pour une valeur qui peut être représentée par moins d'octets, ce qui est invalide. Par exemple, les deux octets 0xc0, 0xae donnent la valeur 0x2e, dont l'encodage correct utilise un seul octet.


PCRE_UTF8_ERR20

Les deux bits les plus significatifs du premier octet d'un caractère ont la valeur binaire 0b10 (c'est-à-dire que le bit le plus significatif est 1 et le second est 0). Un tel octet ne peut apparaître valablement que comme deuxième octet ou octet suivant d'un caractère multi-octets.


PCRE_UTF8_ERR21

Le premier octet d'un caractère a la valeur 0xfe ou 0xff. Ces valeurs ne peuvent jamais apparaître dans une chaîne UTF-8 valide.


PCRE_UTF8_ERR22

Ce code d'erreur était anciennement utilisé lorsque la présence d'un soi-disant « non-caractère » provoquait une erreur. Le rectificatif Unicode #9 indique clairement que de tels caractères ne doivent pas provoquer le rejet d'une chaîne, et donc ce code n'est plus utilisé et n'est jamais renvoyé.

EXTRACTION DES SOUS-CHAÎNES CAPTURÉES PAR NUMÉRO

int pcre_copy_substring(const char *subject, int *ovector,
     int stringcount, int stringnumber, char *buffer,
     int buffersize);

int pcre_get_substring(const char *subject, int *ovector,
     int stringcount, int stringnumber,
     const char **stringptr);

int pcre_get_substring_list(const char *subject,
     int *ovector, int stringcount, const char ***listptr);

Les sous-chaînes capturées peuvent être accédées directement en utilisant les décalages renvoyés par pcre_exec() dans ovector. Pour plus de commodité, les fonctions pcre_copy_substring(), pcre_get_substring() et pcre_get_substring_list() sont fournies pour extraire les sous-chaînes capturées sous forme de nouvelles chaînes séparées et terminées par un zéro. Ces fonctions identifient les sous-chaînes par leur numéro. La section suivante décrit les fonctions pour extraire les sous-chaînes nommées.

Une sous-chaîne qui contient un zéro binaire est correctement extraite et a un zéro supplémentaire ajouté à la fin, mais le résultat n'est, bien sûr, pas une chaîne C. Cependant, vous pouvez traiter une telle chaîne en vous référant à la longueur renvoyée par pcre_copy_substring() et pcre_get_substring(). Malheureusement, l'interface de pcre_get_substring_list() n'est pas adéquate pour gérer les chaînes contenant des zéros binaires, car la fin de la dernière chaîne n'est pas indiquée indépendamment.

Les trois premiers arguments sont les mêmes pour ces trois fonctions : subject est la chaîne sujet qui vient d'être correctement mise en correspondance, ovector est un pointeur vers le vecteur de décalages entiers qui a été passé à pcre_exec(), et stringcount est le nombre de sous-chaînes qui ont été capturées par la mise en correspondance, y compris la sous-chaîne qui a correspondu à l'expression régulière entière. C'est la valeur renvoyée par pcre_exec() si elle est supérieure à zéro. Si pcre_exec() a renvoyé zéro, indiquant qu'il a manqué d'espace dans ovector, la valeur passée comme stringcount doit être le nombre d'éléments du vecteur divisé par trois.

Les fonctions pcre_copy_substring() et pcre_get_substring() extraient une seule sous-chaîne, dont le numéro est donné par stringnumber. Une valeur de zéro extrait la sous-chaîne qui a correspondu au motif entier, tandis que des valeurs plus élevées extraient les sous-chaînes capturées. Pour pcre_copy_substring(), la chaîne est placée dans buffer, dont la longueur est donnée par buffersize, tandis que pour pcre_get_substring() un nouveau bloc de mémoire est obtenu via pcre_malloc, et son adresse est renvoyée via stringptr. Le résultat de la fonction est la longueur de la chaîne, sans inclure le zéro de terminaison, ou l'un des codes d'erreur suivants :


PCRE_ERROR_NOMEMORY (-6)

Le tampon était trop petit pour pcre_copy_substring(), ou la tentative d'obtenir de la mémoire a échoué pour pcre_get_substring().


PCRE_ERROR_NOSUBSTRING (-7)

Il n'y a pas de sous-chaîne dont le numéro est stringnumber.

La fonction pcre_get_substring_list() extrait toutes les sous-chaînes disponibles et construit une liste de pointeurs vers celles-ci. Tout cela est fait dans un seul bloc de mémoire obtenu via pcre_malloc. L'adresse du bloc de mémoire est renvoyée via listptr, qui est également le début de la liste des pointeurs de chaînes. La fin de la liste est marquée par un pointeur NULL. Le résultat de la fonction est zéro si tout s'est bien passé, ou le code d'erreur


PCRE_ERROR_NOMEMORY (-6)

si la tentative d'obtention du bloc de mémoire a échoué.

Lorsque l'une de ces fonctions rencontre une sous-chaîne qui n'est pas définie, ce qui peut arriver lorsque le sous-motif de capture numéro n+1 correspond à une partie du sujet, mais que le sous-motif n n'a pas été utilisé du tout, elles renvoient une chaîne vide. Cela peut être distingué d'une véritable sous-chaîne de longueur zéro en inspectant le décalage approprié dans ovector, qui est négatif pour les sous-chaînes non définies.

Les deux fonctions pratiques pcre_free_substring() et pcre_free_substring_list() peuvent être utilisées pour libérer la mémoire renvoyée par un appel précédent de pcre_get_substring() ou pcre_get_substring_list(), respectivement. Elles ne font rien de plus que d'appeler la fonction pointée par pcre_free, qui pourrait bien sûr être appelée directement à partir d'un programme C. Cependant, PCRE est utilisé dans certaines situations où il est lié via une interface spéciale à un autre langage de programmation qui ne peut pas utiliser pcre_free directement ; c'est pour ces cas que les fonctions sont fournies.

(a+)b(?<xxx>\d+)...

le numéro de la sous-structure nommée « xxx » est 2. Premièrement, au lieu d'un numéro de sous-chaîne, un nom de sous-chaîne est donné. Deuxièmement, il y a un argument supplémentaire, donné au début, qui est un pointeur vers le modèle compilé. Ceci est nécessaire pour accéder à la table de traduction nom-à-numéro.

Le processus de correspondance n'utilise que des numéros. Pour cette raison, l'utilisation de noms différents pour des sous-structures de même numéro provoque une erreur au moment de la compilation.

NOMS DE SOUS-STRUCTURES EN DOUBLE

     const char *name, char **first, char **last);

Lorsqu'un modèle est compilé avec l'option PCRE_DUPNAMES, les noms des sous-structures ne sont pas obligés d'être uniques. (Les noms en double sont toujours autorisés pour des sous-structures ayant le même numéro, créées en utilisant la fonctionnalité (?|. En fait, si de telles sous-structures sont nommées, elles doivent utiliser les mêmes noms.)

Normalement, les modèles avec des noms en double sont tels que lors de chaque correspondance, seule l'une des sous-structures nommées participe. Un exemple est montré dans la documentation pcrepattern.

Lorsqu'il y a des doublons, pcre_copy_named_substring() et pcre_get_named_substring() renvoient la première sous-chaîne correspondant au nom donné qui est définie. Si aucune n'est définie, PCRE_ERROR_NOSUBSTRING (-7) est renvoyé ; aucune donnée n'est renvoyée. La fonction pcre_get_stringnumber() renvoie l'un des numéros associés au nom, mais il n'est pas défini lequel.

Si vous souhaitez obtenir tous les détails sur toutes les sous-chaînes capturées pour un nom donné, vous devez utiliser la fonction pcre_get_stringtable_entries(). Le premier argument est le modèle compilé, et le second est le nom. Les troisième et quatrième sont des pointeurs vers des variables qui sont mises à jour par la fonction. Après son exécution, ils pointent vers la première et la dernière entrée dans la table nom-à-numéro pour le nom donné. La fonction elle-même renvoie la longueur de chaque entrée, ou PCRE_ERROR_NOSUBSTRING (-7) s'il n'y en a aucune. Le format de la table est décrit ci-dessus dans la section intitulée *Informations sur un modèle* ci-dessus. Étant donné toutes les entrées pertinentes pour le nom, vous pouvez extraire chacun de leurs numéros, et donc les données capturées, le cas échéant.

TROUVER TOUTES LES CORRESPONDANCES POSSIBLES

La fonction de correspondance traditionnelle utilise un algorithme similaire à celui de Perl, qui s'arrête lorsqu'il trouve la première correspondance, en partant d'un point donné dans le sujet. Si vous souhaitez trouver toutes les correspondances possibles, ou la correspondance la plus longue possible, envisagez plutôt d'utiliser la fonction de correspondance alternative (voir ci-dessous). Si vous ne pouvez pas utiliser la fonction alternative, mais que vous avez toujours besoin de trouver toutes les correspondances possibles, vous pouvez la contourner en utilisant la facilité de rappel (callout), décrite dans la documentation pcrecallout.

Ce que vous devez faire est d'insérer un rappel juste à la fin du modèle. Lorsque votre fonction de rappel est appelée, extrayez et enregistrez la sous-chaîne correspondante actuelle. Ensuite, renvoyez 1, ce qui force pcre_exec() à faire un retour arrière et à essayer d'autres alternatives. Finalement, lorsqu'il n'y a plus de correspondances, pcre_exec() renverra PCRE_ERROR_NOMATCH.

OBTENIR UNE ESTIMATION DE L'UTILISATION DE LA PILE

La correspondance de certains modèles à l'aide de pcre_exec() peut utiliser une grande partie de la pile de processus, qui, dans certains environnements, peut être assez limitée en taille. Certains utilisateurs trouvent utile d'avoir une estimation de la quantité de pile utilisée par pcre_exec(), pour les aider à définir les limites de récursion, comme décrit dans la documentation pcrestack. L'estimation renvoyée par pcretest lorsqu'il est appelé avec les options -m et -C est obtenue en appelant pcre_exec avec les valeurs NULL, NULL, NULL, -999 et -999 pour ses cinq premiers arguments.

Normalement, si son premier argument est NULL, pcre_exec() renvoie immédiatement le code d'erreur négatif PCRE_ERROR_NULL, mais avec cette combinaison spéciale d'arguments, il renvoie à la place un nombre négatif dont la valeur absolue est la taille approximative de la trame de pile en octets. (Un nombre négatif est utilisé pour qu'il soit clair qu'aucune correspondance n'a eu lieu.) La valeur est approximative car dans certains cas, des appels récursifs à pcre_exec() se produisent lorsqu'il y a une ou deux variables supplémentaires sur la pile.

Si PCRE a été compilé pour utiliser le tas au lieu de la pile pour la récursion, la valeur renvoyée est la taille de chaque bloc obtenu à partir du tas.

La fonction pcre_dfa_exec() est appelée pour faire correspondre une chaîne sujet à un modèle compilé, en utilisant un algorithme de correspondance qui scanne la chaîne sujet une seule fois, et ne fait pas de retour arrière. Cela a des caractéristiques différentes de l'algorithme normal, et n'est pas compatible avec Perl. Certaines des fonctionnalités des modèles PCRE ne sont pas prises en charge. Néanmoins, il existe des situations où ce type de correspondance peut être utile. Pour une discussion sur les deux algorithmes de correspondance, et une liste des fonctionnalités non prises en charge par pcre_dfa_exec(), voir la documentation pcrematching.

Les arguments de la fonction pcre_dfa_exec() sont les mêmes que pour pcre_exec(), plus deux arguments supplémentaires. L'argument ovector est utilisé d'une manière différente, et ceci est décrit ci-dessous. Les autres arguments courants sont utilisés de la même manière que pour pcre_exec(), de sorte que leur description n'est pas répétée ici.

Les deux arguments supplémentaires fournissent un espace de travail pour la fonction. Le vecteur d'espace de travail doit contenir au moins 20 éléments. Il est utilisé pour suivre plusieurs chemins dans l'arbre du modèle. Plus d'espace de travail sera nécessaire pour les modèles et les sujets où il y a beaucoup de correspondances potentielles.

PCRE_PARTIAL_HARD

Lorsque PCRE_PARTIAL_HARD est défini pour pcre_dfa_exec(), il renvoie PCRE_ERROR_PARTIAL si la fin du sujet est atteinte et qu'il reste au moins une possibilité de correspondance qui nécessite des caractères supplémentaires. Cela se produit même si des correspondances complètes ont déjà été trouvées. Lorsque PCRE_PARTIAL_SOFT est défini, le code de retour PCRE_ERROR_NOMATCH est converti en PCRE_ERROR_PARTIAL si la fin du sujet est atteinte, qu'il n'y a eu aucune correspondance complète, mais qu'il reste au moins une possibilité de correspondance. PCRE API APERÇU

Le PCRE C'est une bibliothèque pour la correspondance de motif d'expressions régulières, implémentant un sous-ensemble de la syntaxe de Perl. Le PCRE contient un ensemble de fonctions pour compiler et exécuter des expressions régulières. Cette page de manuel décrit les fonctions de l'interface API de PCRE.

Le PCRE est distribué sous forme de code source, qui peut être compilé en une bibliothèque 8 bits, 16 bits ou 32 bits. Les fonctions sont les mêmes pour les trois, mais les types de données des chaînes et des caractères sont différents. Cette page de manuel utilise des types génériques pour les chaînes et les caractères, qui doivent être interprétés comme des 8 bits, 16 bits ou 32 bits selon la bibliothèque qui est liée.

Toutes les fonctions de PCRE traitent les chaînes de caractères comme des séquences d'octets. Elles ne comprennent pas les caractères multi-octets UTF-8 ou autres. Si vous avez besoin de correspondre à des chaînes qui contiennent des caractères multi-octets, vous devriez utiliser les bibliothèques UTF-8 de PCRE, qui sont décrites dans la page de manuel pcre16(3) et pcre32(3).

FONCTIONS DE BASE DE L'API NATIVE DE PCRE

La fonction principale pour la compilation d'une expression régulière est pcre_compile(). Elle prend une chaîne de caractères contenant l'expression régulière et un certain nombre d'options, et renvoie un pointeur vers une structure regex_t qui contient la forme compilée de l'expression régulière. Des erreurs pendant la compilation sont signalées par le retour de NULL et la mise d'un code d'erreur dans une variable pointée par le troisième argument.

La fonction pcre_study() peut être appelée après la compilation d'une expression régulière pour effectuer des recherches supplémentaires afin d'optimiser les correspondances. La fonction renvoie un pointeur vers une structure study_data_t qui contient les informations d'optimisation. Si aucune optimisation ne peut être effectuée, ou si la fonction ne peut pas être exécutée pour une autre raison, NULL est renvoyé.

La fonction pcre_exec() exécute une expression régulière compilée contre une chaîne de caractères sujet. Elle renvoie le nombre de correspondances trouvées. Les détails des correspondances sont renvoyés dans un vecteur d'entiers appelé ovector. Les deux premiers éléments du vecteur contiennent le décalage de début et la longueur de la correspondance entière. Les paires d'éléments suivantes contiennent les décalages de début et de fin des sous-chaînes capturées.

La fonction pcre_dfa_exec() est une alternative à pcre_exec() qui utilise un algorithme différent pour la correspondance. Elle est généralement plus lente, mais elle peut trouver plus d'une correspondance pour une expression régulière donnée, même si les autres fonctions ne le peuvent pas. Elle est particulièrement utile pour les expressions régulières qui correspondent à des motifs ambigus.

La fonction pcre_free() libère la mémoire allouée par pcre_compile() et pcre_study(). La fonction pcre_free_study() libère la mémoire allouée par pcre_study().

FONCTIONS D'EXTRACTION DE CHAÎNES DE L'API NATIVE DE PCRE

PCRE fournit plusieurs fonctions pour extraire des sous-chaînes capturées d'une correspondance.

pcre_get_substring() renvoie un pointeur vers une copie de la sous-chaîne spécifiée par son indice dans le vecteur ovector. La mémoire de cette copie doit être libérée en utilisant pcre_free_substring().

pcre_get_substring_list() renvoie un tableau de pointeurs vers des copies de toutes les sous-chaînes capturées. La mémoire de ce tableau et des copies doit être libérée en utilisant pcre_free_substring_list().

pcre_get_named_substring() renvoie un pointeur vers une copie de la sous-chaîne capturée par un nom spécifié. La mémoire de cette copie doit être libérée en utilisant pcre_free_substring().

pcre_copy_substring() est une autre façon d'extraire des sous-chaînes. Elle copie la sous-chaîne spécifiée dans un tampon fourni par l'appelant.

pcre_copy_named_substring() est l'équivalent de pcre_copy_substring() pour les sous-chaînes nommées.

FONCTIONS AUXILIAIRES DE L'API NATIVE DE PCRE

PCRE fournit plusieurs fonctions auxiliaires pour obtenir des informations sur les correspondances et l'API.

pcre_version() renvoie la chaîne de version de la bibliothèque PCRE.

pcre_config() renvoie des informations sur les options de configuration de la bibliothèque PCRE. Elle peut être utilisée pour vérifier si certaines fonctionnalités sont activées, telles que le support UTF-8 ou le support du rappel.

pcre_stack_guard() définit une garde pour la pile d'appels. Elle est utilisée pour éviter les dépassements de pile lors de l'utilisation de motifs récursifs.

pcre_callout() est une fonction de rappel qui peut être appelée pendant le processus de correspondance. Elle peut être utilisée pour déboguer ou pour contrôler le processus de correspondance.

pcre_assign_adaptor() est utilisée pour assigner une fonction d'adaptation pour gérer l'encodage des caractères.

FONCTIONS INDIRECTÉES DE L'API NATIVE DE PCRE

PCRE fournit également un ensemble de fonctions indirectées qui peuvent être utilisées pour accéder aux fonctionnalités de PCRE de manière plus flexible.

pcre_assign_wrapper() assigne une fonction wrapper pour les opérations de PCRE.

pcre_wrapper_exec() exécute une expression régulière à l'aide d'une fonction wrapper.

pcre_wrapper_free_study() libère la mémoire allouée par une fonction wrapper pour l'étude.

BIBLIOTHÈQUES PCRE 8-BITS, 16-BITS ET 32-BITS

Le PCRE peut être compilé en trois variantes : 8 bits, 16 bits et 32 bits. Celles-ci sont destinées à être utilisées avec des chaînes de caractères de taille correspondante. Le code source PCRE prend en charge la construction des trois bibliothèques à partir d'une seule base de code. Par défaut, la bibliothèque 8 bits est construite.

La construction des bibliothèques 16 bits et 32 bits est contrôlée par les options de ligne de commande --enable-utf16 et --enable-utf32 lors de la configuration. La construction des trois bibliothèques à la fois est possible en utilisant les deux options.

Lorsque vous liez votre application avec la bibliothèque PCRE, vous devez vous assurer que vous liez avec la variante appropriée. Par exemple, pour lier avec la bibliothèque 16 bits, vous utiliseriez -lpcre16 (ou le nom approprié pour votre système).

Les fonctions API sont les mêmes pour les trois variantes, mais elles opèrent sur des types de caractères différents : char pour 8 bits, pcresChar16 pour 16 bits et pcresChar32 pour 32 bits. Les types de données génériques utilisés dans cette page de manuel doivent être interprétés comme suit :

  • string : char *, pcresChar16 *, ou pcresChar32 *
  • character : char, pcresChar16, ou pcresChar32
  • pcre_uintptr : unsigned int, unsigned long, ou unsigned long long

Les fonctions d'erreur spécifiques aux variantes, telles que PCRE_ERROR_UTF16_... ou PCRE_ERROR_UTF32_..., ne sont pas décrites dans cette page de manuel.

OBJECTIFS DES MODIFICATIONS DES FONCTIONS DE PCRE

Le PCRE est un projet en évolution continue. Ces dernières années, un effort considérable a été fait pour améliorer la flexibilité et la puissance de la bibliothèque PCRE, en particulier dans le domaine de la correspondance de motifs. Voici un aperçu des objectifs de ces modifications :

  • Correspondance plus flexible : permettre à PCRE de trouver plus d'une correspondance pour une expression régulière donnée, même si les correspondances se chevauchent. Ceci est particulièrement utile pour les applications qui doivent extraire toutes les occurrences d'un motif à partir d'une chaîne de caractères.
  • Support UTF-8 : fournir un support complet pour Unicode, y compris la correspondance de caractères multi-octets et les propriétés des caractères Unicode.
  • Meilleure performance : optimiser les algorithmes de correspondance pour améliorer les performances, en particulier pour les expressions régulières complexes et les grandes chaînes de caractères.
  • API plus simple : simplifier l'API PCRE pour la rendre plus facile à utiliser et à comprendre.

Ces modifications ont été mises en œuvre dans les nouvelles versions de PCRE. Si vous utilisez une version antérieure de PCRE, vous devrez peut-être mettre à jour votre bibliothèque pour tirer parti de ces nouvelles fonctionnalités.

NOUVELLES LIGNES

PCRE considère que les caractères de nouvelle ligne sont : LF (line feed, `\n`, code ASCII 10), VT (vertical tab, `\v`, code ASCII 11), FF (form feed, `\f`, code ASCII 12), CR (carriage return, `\r`, code ASCII 13), et NEL (next line, U+0085). Les caractères CR et LF consécutifs sont traités comme une seule nouvelle ligne.

Si l'option PCRE_NEWLINE_CR est activée, le seul caractère CR est traité comme nouvelle ligne.

Si l'option PCRE_NEWLINE_LF est activée, le seul caractère LF est traité comme nouvelle ligne.

Si l'option PCRE_NEWLINE_CRLF est activée, la séquence CR LF est traitée comme une seule nouvelle ligne.

Si l'option PCRE_NEWLINE_ANY est activée, tout caractère de nouvelle ligne est traité comme une nouvelle ligne.

Si aucune de ces options n'est activée, la seule nouvelle ligne est LF. Cependant, les options PCRE_NEWLINE_CR, PCRE_NEWLINE_LF et PCRE_NEWLINE_CRLF sont utilisées pour modifier le comportement de la séquence spéciale `.` dans les expressions régulières qui devraient correspondre à une nouvelle ligne.

Le comportement par défaut est le même que celui de PCRE_NEWLINE_ANY.

MULTITHREADING

PCRE est thread-safe. Les différentes fonctions peuvent être appelées simultanément à partir de différents threads sans conflit.

Cependant, l'utilisation d'une structure regex_t compilée à partir de différents threads sans mutex peut entraîner des conditions de concurrence. Si vous partagez des motifs compilés entre des threads, vous devez vous assurer que l'accès à ces motifs est correctement synchronisé.

SAUVEGARDE DES MOTIFS PRÉCOMPILÉS POUR UNE UTILISATION ULTÉRIEURE

PCRE fournit des fonctions pour sauvegarder et restaurer des motifs compilés.

pcre_serialize_to_file() sérialise un motif compilé dans un fichier. La fonction pcre_deserialize_from_file() restaure un motif compilé à partir d'un fichier.

Ces fonctions peuvent être utiles pour réduire le temps de démarrage d'une application qui utilise de manière répétée les mêmes motifs. En précompilant les motifs et en les sauvegardant dans un fichier, vous pouvez éviter le coût de la compilation à chaque fois que l'application démarre.

VÉRIFICATION DES OPTIONS DE COMPILATION

La fonction pcre_config() peut être utilisée pour interroger la bibliothèque PCRE sur ses options de compilation. Cela vous permet de vérifier si certaines fonctionnalités sont activées, telles que le support UTF-8 ou les options de rappel.

Les options de configuration sont renvoyées sous forme de valeurs entières. Par exemple, pour vérifier si le support UTF-8 est activé, vous pouvez appeler pcre_config(PCRE_CONFIG_UTF8, &value). Si value est 1, le support UTF-8 est activé.

La fonction pcre_compile() est utilisée pour compiler une expression régulière. Elle prend en arguments la chaîne de l'expression régulière, un ensemble d'options, et un pointeur vers une variable où sera stocké un code d'erreur en cas d'échec. Elle renvoie un pointeur vers une structure regex_t qui représente le motif compilé.

Les options de compilation courantes incluent :

PCRE_DOTALL

PCRE_EXTENDED
Permet des espaces blancs et des commentaires dans le motif pour une meilleure lisibilité.

Des exemples d'utilisation de pcre_compile() sont disponibles dans la documentation PCRE.

ÉTUDE D'UN MOTIF

La fonction pcre_study() peut être appelée après la compilation d'une expression régulière pour effectuer des analyses supplémentaires afin d'optimiser la recherche. Elle renvoie un pointeur vers une structure study_data_t qui contient les informations d'optimisation. Si aucune optimisation n'est possible, ou si la fonction échoue pour une autre raison, NULL est renvoyé. La mémoire allouée par pcre_study() doit être libérée en utilisant pcre_free_study().

L'étude d'un motif peut considérablement accélérer les recherches, en particulier pour les motifs complexes. Elle fonctionne en analysant le motif et en déterminant les meilleurs chemins de recherche. Par exemple, si un motif commence par un caractère spécifique, l'étude peut identifier cette information et éviter de tester des correspondances qui ne commencent pas par ce caractère.

PRISE EN CHARGE DES LOCALES

PCRE prend en charge les locales POSIX pour la correspondance des caractères. Lorsque la prise en charge des locales est activée (par la compilation de PCRE avec l'option --enable-locale), les classes de caractères telles que [[:digit:]] et \d correspondent aux caractères appropriés dans la locale actuelle.

Pour utiliser la prise en charge des locales, vous devez définir la variable d'environnement LC_ALL ou LC_CTYPE avant d'appeler les fonctions PCRE. Par exemple :


setlocale(LC_ALL, "");

Notez que la prise en charge des locales peut avoir un impact sur les performances, car elle implique des recherches supplémentaires pour déterminer les propriétés des caractères.

Les informations obtenues à l'aide de pcre_info() peuvent être utiles pour des optimisations personnalisées ou pour mieux comprendre le comportement d'un motif.

CHIFFRES DE RÉFÉRENCE

PCRE utilise des chiffres de référence pour gérer la mémoire des motifs compilés. Chaque fois qu'un motif est compilé, son chiffre de référence est incrémenté. Lorsque le chiffre de référence atteint zéro, le motif est libéré de la mémoire.

Les fonctions pcre_ref_count_add() et pcre_ref_count_remove() peuvent être utilisées pour manipuler manuellement les chiffres de référence, bien que cela soit rarement nécessaire.

CORRESPONDANCE D'UN MOTIF : LA FONCTION TRADITIONNELLE

La fonction pcre_exec() exécute une expression régulière compilée contre une chaîne sujet. Elle renvoie le nombre de correspondances trouvées. Les détails des correspondances sont renvoyés dans un vecteur d'entiers appelé ovector. Les deux premiers éléments du vecteur contiennent le décalage de début et la longueur de la correspondance entière. Les paires d'éléments suivantes contiennent les décalages de début et de fin des sous-chaînes capturées.

Si ovector est NULL, aucun détail de correspondance n'est renvoyé. Si la taille du vecteur ovector est trop petite pour contenir tous les détails de correspondance, le nombre renvoyé est PCRE_ERROR_OVECTOR_SHORTAGE, et les éléments de ovector sont remplis avec autant de correspondances que possible.

La fonction pcre_exec() peut également renvoyer :

0
Aucune correspondance trouvée.
Un entier positif
Le nombre de correspondances trouvées (généralement 1 pour pcre_exec()).
Un entier négatif
Un code d'erreur.

Les codes d'erreur courants incluent :

PCRE_ERROR_NOMATCH
Aucune correspondance trouvée.
PCRE_ERROR_NULL_POINTER
Un pointeur nul a été fourni comme argument.
PCRE_ERROR_BADOFFSET
Le décalage de départ spécifié n'est pas valide.
PCRE_ERROR_PARTIAL
La chaîne sujet est incomplète.
PCRE_ERROR_INTERNAL
Erreur interne de PCRE.

Il existe également des codes d'erreur spécifiques au mode de correspondance DFA, décrits dans la section sur pcre_dfa_exec().

EXTRACTION DES SOUS-CHAÎNES CAPTURES PAR NUMÉRO

La fonction pcre_get_substring() renvoie un pointeur vers une copie de la sous-chaîne capturée spécifiée par son indice dans le vecteur ovector. L'indice 0 correspond à la correspondance entière, et les indices suivants correspondent aux groupes de capture dans l'ordre où ils apparaissent dans le motif.

La mémoire allouée par pcre_get_substring() doit être libérée en utilisant pcre_free_substring().

La fonction pcre_get_substring_list() renvoie un tableau de pointeurs vers des copies de toutes les sous-chaînes capturées. La mémoire de ce tableau et des copies doit être libérée en utilisant pcre_free_substring_list().

La fonction pcre_copy_substring() copie la sous-chaîne capturée spécifiée dans un tampon fourni par l'appelant.

EXTRACTION DES SOUS-CHAÎNES CAPTURES PAR NOM

Si le motif contient des groupes de capture nommés (par exemple, (?...)), vous pouvez utiliser la fonction pcre_get_named_substring() pour extraire la sous-chaîne correspondant à un nom donné.

La mémoire allouée par pcre_get_named_substring() doit être libérée en utilisant pcre_free_substring().

La fonction pcre_copy_named_substring() copie la sous-chaîne capturée nommée spécifiée dans un tampon fourni par l'appelant.

Pour obtenir une liste des noms de groupes de capture disponibles, vous pouvez utiliser la fonction pcre_string_to_array().

DUPLICATE NOMS DE SOUS-MOTIFS

PCRE autorise les noms de groupe de capture dupliqués. Si plusieurs groupes portent le même nom, pcre_get_named_substring() renverra la sous-chaîne correspondant au groupe nommé le plus récent.

Pour accéder aux groupes nommés précédents, vous devrez utiliser la fonction pcre_get_string_range(), qui renvoie la plage de tous les groupes capturés, y compris ceux avec des noms dupliqués.

Si vous souhaitez que chaque nom de groupe soit unique, vous pouvez définir l'option PCRE_CONFIG_DUPNAMES lors de la compilation de PCRE ou utiliser la fonction pcre_config() pour vérifier si les noms dupliqués sont autorisés.

TROUVER TOUTES LES CORRESPONDANCES POSSIBLES

La fonction pcre_exec(), dans sa forme standard, ne renvoie que la première correspondance trouvée. Pour trouver toutes les correspondances possibles, vous devez utiliser la fonction pcre_match_all().

La fonction pcre_match_all() prend le même motif et la même chaîne sujet que pcre_exec(), mais elle renvoie un tableau de structures match_data_t, chacune contenant les détails d'une correspondance.

Le nombre de correspondances renvoyées est limité par la taille du vecteur ovector fourni à pcre_exec().

Notez que la recherche de toutes les correspondances peut être beaucoup plus lente que la recherche de la première correspondance, en particulier pour les expressions régulières complexes ou les longues chaînes sujet.

OBTENIR UNE ESTIMATION DE L'UTILISATION DE LA PILE

La fonction pcre_dfa_estimate_stack_usage() fournit une estimation de l'utilisation de la pile par le moteur DFA de PCRE lors de la correspondance d'un motif donné avec une chaîne sujet. Ceci est utile pour anticiper les problèmes de dépassement de pile, en particulier avec des motifs récursifs complexes ou de longues chaînes sujet.

L'estimation n'est pas garantie d'être exacte, mais elle fournit une bonne indication de l'utilisation potentielle de la pile. Si l'estimation dépasse une limite prédéfinie, il est conseillé de modifier le motif ou la chaîne sujet, ou d'augmenter la taille de la pile d'exécution.

L'utilisation de cette fonction est particulièrement pertinente lors de l'utilisation de l'option PCRE_DFA_RECURSE dans pcre_dfa_exec().

CORRESPONDANCE D'UN MOTIF : LA FONCTION ALTERNATIVE

La fonction pcre_dfa_exec() est une alternative à pcre_exec() qui utilise un algorithme différent (basé sur les automates finis déterministes - DFA) pour la correspondance. Elle peut trouver plus d'une correspondance pour une expression régulière donnée, même si les autres fonctions ne le peuvent pas.

Lorsque pcre_dfa_exec() réussit, elle renvoie le nombre de correspondances trouvées. Ces correspondances sont toutes des sous-chaînes initiales de la chaîne sujet, commençant au même point. Les correspondances sont renvoyées dans le vecteur ovector dans l'ordre de longueur décroissante (la plus longue d'abord).

Par exemple, si le motif <.*> est appliqué à la chaîne This is <something> <something else> <something further> no more, les correspondances trouvées par pcre_dfa_exec() seront :

  • <something> <something else> <something further>
  • <something> <something else>
  • <something>

Si le vecteur ovector n'est pas assez grand pour contenir toutes les correspondances, la fonction renvoie 0 et remplit le vecteur avec les correspondances les plus longues possibles. Contrairement à pcre_exec(), pcre_dfa_exec() peut utiliser tout le vecteur ovector pour renvoyer des correspondances.

Notez que l'optimisation "auto-possessification" de PCRE, qui transforme les répétitions avides en répétitions possessives, peut limiter le nombre de correspondances trouvées par le moteur DFA. Pour obtenir plusieurs correspondances dans de tels cas, utilisez une répétition non avide (par exemple, +?) ou désactivez l'auto-possessification lors de la compilation avec l'option PCRE_NO_AUTO_POSSESS.

Retours réussis de pcre_dfa_exec()

Lorsque pcre_dfa_exec() réussit, il peut avoir trouvé plus d'une sous-chaîne dans le sujet. Notez cependant que toutes les correspondances d'une exécution de la fonction commencent au même point dans le sujet. Les correspondances les plus courtes sont toutes des sous-chaînes initiales des correspondances les plus longues. Par exemple, si le motif


<.*>

est appliqué à la chaîne


Ceci est <quelque chose> <quelque chose d'autre> <quelque chose de plus loin> plus rien

les trois chaînes correspondantes sont


<quelque chose>
<quelque chose> <quelque chose d'autre>
<quelque chose> <quelque chose d'autre> <quelque chose de plus loin>

En cas de succès, le résultat de la fonction est un nombre supérieur à zéro, qui est le nombre de sous-chaînes correspondantes. Les sous-chaînes elles-mêmes sont renvoyées dans ovector. Chaque chaîne utilise deux éléments ; le premier est le décalage du début et le second est le décalage de la fin. En fait, toutes les chaînes ont le même décalage de début. (On aurait pu économiser de l'espace en ne donnant cela qu'une seule fois, mais il a été décidé de conserver une certaine compatibilité avec la manière dont pcre_exec() renvoie les données, même si la signification des chaînes est différente.)

Les chaînes sont renvoyées dans l'ordre inverse de leur longueur ; c'est-à-dire que la chaîne correspondante la plus longue est donnée en premier. S'il y avait trop de correspondances pour tenir dans ovector, le résultat de la fonction est zéro, et le vecteur est rempli avec les correspondances les plus longues. Contrairement à pcre_exec(), pcre_dfa_exec() peut utiliser l'intégralité d' ovector pour renvoyer des chaînes correspondantes.

NOTE : L'optimisation "auto-possessification" de PCRE s'applique généralement aux répétitions de caractères à la fin d'un motif (ainsi qu'en interne). Par exemple, le motif "a\d+" est compilé comme s'il s'agissait de "a\d++" car il n'y a aucun intérêt à envisager la possibilité de revenir en arrière dans les chiffres répétés. Pour la correspondance DFA, cela signifie qu'une seule correspondance possible est trouvée. Si vous souhaitez réellement plusieurs correspondances dans de tels cas, utilisez une répétition non gourmande ("a\d+?") ou définissez l'option PCRE_NO_AUTO_POSSESS lors de la compilation.

Retours d'erreur de pcre_dfa_exec()

La fonction pcre_dfa_exec() renvoie un nombre négatif en cas d'échec. De nombreuses erreurs sont les mêmes que pour pcre_exec(), et elles sont décrites ci-dessus. Il y a en plus les erreurs suivantes qui sont spécifiques à pcre_dfa_exec() :


PCRE_ERROR_DFA_UITEM (-16)

Ce retour est donné si pcre_dfa_exec() rencontre un élément dans le motif qu'il ne prend pas en charge, par exemple, l'utilisation de \C ou d'une référence arrière.


PCRE_ERROR_DFA_UCOND (-17)

Ce retour est donné si pcre_dfa_exec() rencontre un élément conditionnel qui utilise une référence arrière pour la condition, ou un test de récursion dans un groupe spécifique. Ceux-ci ne sont pas pris en charge.


PCRE_ERROR_DFA_UMLIMIT (-18)

Ce retour est donné si pcre_dfa_exec() est appelée avec un bloc extra qui contient un réglage des champs match_limit ou match_limit_recursion. Ce n'est pas pris en charge (ces champs sont dénués de sens pour la correspondance DFA).


PCRE_ERROR_DFA_WSSIZE (-19)

Ce retour est donné si pcre_dfa_exec() manque d'espace dans le vecteur workspace.


PCRE_ERROR_DFA_RECURSE (-20)

Lorsqu'un sous-motif récursif est traité, la fonction de correspondance s'appelle elle-même récursivement, en utilisant des vecteurs privés pour ovector et workspace. Cette erreur est donnée si le vecteur de sortie n'est pas assez grand. Cela devrait être extrêmement rare, car un vecteur de taille 1000 est utilisé.


PCRE_ERROR_DFA_BADRESTART (-30)

Lorsque pcre_dfa_exec() est appelée avec l'option PCRE_DFA_RESTART, certaines vérifications de plausibilité sont effectuées sur le contenu de l'espace de travail, qui doit contenir des données sur la correspondance partielle précédente. Si l'une de ces vérifications échoue, cette erreur est signalée.
