PCP-CHECK(1) Manuel des commandes générales PCP-CHECK(1)

NOM

pcp-check - gérer la configuration des composants PCP optionnels

SYNTAXE

$pcp-check [-a] [-d] [-l] [-n] [-s] [-v] [-x] [composant ...]
$pcp-check [-a] [-c script]] [-d] [-l] [-n] [-s] [-v] [-x]
$PCP_BINADM_DIR/pmcheck ...

DESCRIPTION

Le Collecteur de Performance (PCP) comprend un certain nombre de composants de base qui sont susceptibles d'être pré-configurés et opérationnels, mais il comprend également un plus grand nombre de composants qui ne sont pas actifs par défaut. Dans le contexte de pmcheck, ces composants couvrent les services qui sont généralement démarrés dans le cadre de la procédure de démarrage du système, par exemple pmcd(1), pmlogger(1), pmproxy(1), etc., ou des agents de domaine de métriques de performance (PMDA) optionnels qui augmentent les métriques de performance disponibles exportées par pmcd(1).

pmcheck permet l'interrogation de l'état des composants avec l'option -s, --state. Les composants peuvent être activés avec l'option -a, --activate, ou désactivés avec l'option -d, --deactivate. Ces trois options sont clairement mutuellement exclusives pour toute exécution unique de pmcheck, et en l'absence de l'une d'entre elles, -s est supposée par défaut.

L'ensemble des composants à interroger ou à configurer est spécifié par le(s) nom(s) de composant depuis la ligne de commande, sinon tous les composants connus en l'absence d'arguments composant. Lorsque un ou plusieurs arguments composant sont spécifiés, ils peuvent éventuellement être des motifs sh(1) (glob) qui sont comparés aux noms des composants connus.

L'option -l, --list rapporte les composants connus. Avec un ou plusieurs composants, chacun est rapporté. Sans aucun argument composant, l'option -l liste tous les composants connus, ce qui correspond simplement à tous les scripts de composants (voir la section SCRIPTS DE COMPOSANTS ci-dessous) stockés dans le répertoire $PCP_SHARE_DIR/lib/pmcheck. Si l'option -v est également utilisée, une courte description de chaque composant demandé est également affichée.

Des composants supplémentaires peuvent être intégrés dans le cadre de pmcheck, et l'option -c, --file permet d'utiliser un script sh(1) alternatif au lieu d'un script associé à un composant connu.

En concertation avec les options -a ou -d, l'option -n, --show-me effectue une simulation à sec, montrant les commandes sh(1) qui seraient nécessaires pour effectuer la reconfiguration, mais aucune reconfiguration n'est effectuée. Les commandes qui doivent être exécutées en tant que ``root'' sont préfixées par # et les autres commandes sont préfixées par $.

L'option -v, --verbose augmente la verbosité des rapports.

L'option -x, --trace peut être utilisée pour spécifier que les scripts de composants sont exécutés avec l'option -x de sh(1). Cela peut aider au débogage de l'échec d'un script de composant ou lors du développement d'un nouveau script de composant, impliquant probablement aussi l'option -c de pmcheck.

L'option -?, --help affiche un message d'utilisation.

Par commodité, pmcheck . est un alias pour pcp-check.

SCRIPTS DE COMPOSANTS

Le cadre pmcheck est extensible, car l'ensemble des composants connus est défini par les noms des scripts de composants dans le répertoire $PCP_SHARE_DIR/lib/pmcheck.

Chaque script de composant doit respecter les règles suivantes pour une intégration correcte avec pmcheck :

  • Le script sera exécuté avec sh(1), si vous avez besoin d'un autre langage de scripting, vous devez fournir un wrapper sh(1).
  • Comme chaque script est responsable d'un composant, le nom du composant est implicite, cependant, le nom du composant est également transmis par pmcheck comme seul argument après les options. Cela permet de mettre en œuvre des scripts de composants génériques sous forme de liens physiques dans $PCP_SHARE_DIR/lib/pmcheck.
  • Lorsqu'il est appelé avec l'option -l, --list, le script ne fait rien, sauf s'il est également appelé avec une option -v, auquel cas une courte description du composant est affichée sur la sortie standard.
  • Lorsqu'il est appelé avec l'option -s, --state, le script doit se terminer avec un code de sortie qui indique l'état du composant, à savoir 0 (actif), 1 (inactif, mais pourrait être activé par pmcheck), 2 (inactif et ne peut pas être activé par pmcheck). La distinction entre les codes de sortie 1 et 2 est basée sur de nombreux facteurs, mais 1 signifie généralement que tous les paquets logiciels requis (PCP et autres) sont installés, que les services prérequis requis fonctionnent ou peuvent être démarrés en toute sécurité, et que toute configuration de composant peut supposer des paramètres par défaut ou être déduite de manière fiable, par exemple un numéro de port pour les communications. Inversement, 2 signifie que l'activation automatique du composant n'est pas possible et qu'une intervention de l'utilisateur est requise.
  • Lorsqu'il est appelé avec l'option -a, --activate, le script doit activer le composant. Cela signifie apporter toute modification de configuration requise pour qu'il soit redémarré au prochain redémarrage du système ou au redémarrage de pmcd(1), et démarrer le composant s'il est actuellement inactif.
  • Lorsqu'il est appelé avec l'option -d, --deactivate, le script doit désactiver le composant. Cela signifie arrêter le composant s'il est actuellement actif, et apporter toute modification de configuration requise pour qu'il ne soit pas redémarré au prochain redémarrage du système ou au redémarrage de pmcd(1).
  • Lorsqu'il est appelé avec l'option -n, --show-me, le script doit effectuer une simulation à sec et afficher les commandes requises sur la sortie standard conformément aux règles décrites ci-dessus pour l'option -n de pmcheck.
  • Si une option -v, --verbose est également spécifiée, le script doit fournir des explications sur la sortie standard pour aider à expliquer, en particulier dans les cas où le composant n'est pas actif ou que la reconfiguration a échoué.

Pour aider au développement de scripts de composants, le fichier $PCP_SHARE_DIR/lib/checkproc.sh peut être sourcé (après avoir sourcé $PCP_DIR/etc/pcp.env). checkproc.sh fournit les services suivants :

  • Un répertoire temporaire est créé et la variable shell $tmp est affectée au chemin complet du répertoire.
  • La variable shell $status est utilisée pour retourner le code de sortie du script [par défaut 0].
  • La variable shell $component est affectée au nom du composant associé.
  • La variable shell $prog est affectée au basename du script (donc le nom du composant dans le cas par défaut).
  • Un trap est installé pour nettoyer $tmp et se terminer avec $status.
  • Une procédure shell _do_args qui gère toute l'analyse des arguments de la commande.
  • Les variables shell $aflag, $dflag, $lflag ou $sflag ont des valeurs par défaut de false et sont définies sur true par _do_args lorsque les options -a, -d, -l ou -s sont analysées.
  • La variable shell $show_me a la valeur par défaut de false et est définie sur true par _do_args lorsque l'option -n est analysée.
  • La variable shell $verbose compte le nombre d'options -v analysées par _do_args.
  • Une procédure shell _ctl_svc qui gère les demandes d'état et toutes les opérations de reconfiguration pour les services gérés par systemctl(1) ou init(1) ou des couches d'infrastructure similaires. _ctl_svc prend 2 arguments, le premier est une action (l'une de state, start, stop, activate (activer et démarrer), ou deactivate (arrêter et désactiver), et le second est le nom du composant ; pour les composants gérés par systemctl(1), name doit être le basename du service, par exemple pmcd pour l'unité systemd(1) pmcd.service, sinon name est le nom du script init(1) ou similaire ``rc''.
  • _ctl_svc retournera une valeur (via $? lorsqu'il est appelé depuis un script shell) qui correspond aux codes de sortie définis ci-dessus pour chaque

    #!/bin/sh
. $PCP_DIR/etc/pcp.env || exit 1
. $PCP_SHARE_DIR/lib/checkproc.sh

_do_args "$@"

if $lflag
then
    [ $verbose -gt 0 ] && echo "ma description"
elif $sflag
then
    _ctl_svc state $component
    status=$?
elif $aflag
then
    _ctl_svc activate $component || status=1
elif $dflag
then
    _ctl_svc deactivate $component || status=1
fi

    DIAGNOSTICS

    Pour pmcheck (pas les scripts de composant), le statut de sortie est typiquement 0, mais des valeurs de 9 ou 99 indiquent de graves erreurs internes.

    Lorsque les options -a ou -d sont utilisées, le succès ou l'échec de la reconfiguration est rapporté sur la sortie standard.

    CAVEAT

    Certains composants ont des prérequis qui exigent que des services non-PCP supplémentaires soient installés, configurés et opérationnels, par exemple un serveur de base de données ou un serveur clé-valeur. Dans ces cas, sonder le statut du service non-PCP peut être soumis à des contrôles d'accès et si pmcheck est exécuté en tant qu'utilisateur non root, alors la sortie de -s (par défaut) peut être incomplète ou trompeuse ; dans ces circonstances, l'exécution de pmcheck en tant que root devrait fournir un rapport plus précis.

    PCP ENVIRONNEMENT

    Les variables d'environnement avec le préfixe PCP_ sont utilisées pour paramétrer les noms de fichiers et de répertoires utilisés par PCP. Lors de chaque installation, le fichier /etc/pcp.conf contient les valeurs locales pour ces variables. La variable $PCP_CONF peut être utilisée pour spécifier un fichier de configuration alternatif, comme décrit dans pcp.conf(5).

    VOIR AUSSI

    init(1), PCPIntro(1), pmcd(1), pmlogger(1), pmproxy(1), sh(1), systemctl(1), pcp.conf(5) et pcp.env(5).
