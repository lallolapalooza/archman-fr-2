BIBLIOTHÈQUES 8, 16 ET 32 BITS PCRE2

Il existe trois bibliothèques PCRE2, prenant en charge des unités de code 8, 16 et 32 bits, respectivement. Cependant, il n'y a qu'un seul fichier d'en-tête, pcre2.h. Il contient les prototypes de fonctions et autres définitions pour les trois bibliothèques. Une, deux, ou les trois peuvent être installées simultanément. Sur les systèmes de type Unix, les bibliothèques s'appellent libpcre2-8, libpcre2-16 et libpcre2-32, et elles peuvent également coexister avec les bibliothèques PCRE d'origine. Chaque fonction PCRE2 existe sous trois formes différentes, une pour chaque bibliothèque, par exemple :


pcre2_compile_8()
pcre2_compile_16()
pcre2_compile_32()

Il existe également trois ensembles de types de données distincts :


PCRE2_UCHAR8, PCRE2_UCHAR16, PCRE2_UCHAR32
PCRE2_SPTR8, PCRE2_SPTR16, PCRE2_SPTR32

Les types UCHAR définissent des unités de code non signées des largeurs appropriées. Par exemple, PCRE2_UCHAR16 est généralement défini comme `uint16_t'. Les types SPTR sont des pointeurs vers des constantes des types UCHAR équivalents, c'est-à-dire des pointeurs vers des vecteurs d'unités de code non signées.

Les chaînes de caractères sont passées à une bibliothèque PCRE2 sous forme de séquences d'entiers non signés dans des unités de code de la largeur appropriée. La longueur d'une chaîne peut être donnée par un nombre d'unités de code, ou la chaîne peut être spécifiée comme terminée par un zéro.

De nombreuses applications n'utilisent qu'une seule largeur d'unité de code. Pour leur commodité, des macros sont définies dont les noms sont les formes génériques telles que pcre2_compile() et PCRE2_SPTR. Ces macros utilisent la valeur de la macro PCRE2_CODE_UNIT_WIDTH pour générer les noms de fonctions et de macros spécifiques à la largeur appropriée. PCRE2_CODE_UNIT_WIDTH n'est pas définie par défaut. Une application doit la définir à 8, 16 ou 32 avant d'inclure pcre2.h afin d'utiliser les noms génériques.

Les applications qui utilisent plus d'une largeur d'unité de code peuvent être liées à plusieurs bibliothèques PCRE2, mais doivent définir PCRE2_CODE_UNIT_WIDTH à 0 avant d'inclure pcre2.h, puis utiliser les noms de fonctions réels. Tout code qui doit être inclus dans un environnement où la valeur de PCRE2_CODE_UNIT_WIDTH est inconnue doit également utiliser les noms de fonctions réels. (Malheureusement, il n'est pas possible en code C de sauvegarder et restaurer la valeur d'une macro.)

Si PCRE2_CODE_UNIT_WIDTH n'est pas définie avant d'inclure pcre2.h, une erreur de compilation se produit.

Lors de l'utilisation de plusieurs bibliothèques dans une application, vous devez veiller, lors du traitement d'un motif particulier, à n'utiliser que des fonctions d'une seule bibliothèque. Par exemple, si vous voulez effectuer une correspondance à l'aide d'un motif qui a été compilé avec pcre2_compile_16(), vous devez le faire avec pcre2_match_16(), et non avec pcre2_match_8() ou pcre2_match_32().

Dans les résumés de fonctions ci-dessus, ainsi que dans le reste de ce document et d'autres documents PCRE2, les fonctions et les types de données sont décrits en utilisant leurs noms génériques, sans le suffixe _8, _16 ou _32.

APERÇU DE L'API PCRE2

PCRE2 a sa propre API native, qui est décrite dans ce document. Il existe également quelques fonctions enveloppes pour la bibliothèque 8 bits qui correspondent à l'API POSIX des expressions régulières, mais elles ne donnent pas accès à toutes les fonctionnalités de PCRE2 et elles ne sont pas thread-safe. Elles sont décrites dans la documentation de pcre2posix. Ces deux API définissent un ensemble d'appels de fonctions C.

Les types de données C de l'API native, les prototypes de fonctions, les valeurs d'options et les codes d'erreur sont définis dans le fichier d'en-tête pcre2.h, qui contient également les définitions de PCRE2_MAJOR et PCRE2_MINOR, les numéros de version majeure et mineure de la bibliothèque. Les applications peuvent les utiliser pour inclure la prise en charge de différentes versions de PCRE2.

Dans un environnement Windows, si vous souhaitez lier statiquement un programme d'application à une bibliothèque PCRE2 non-dll, vous devez définir PCRE2_STATIC avant d'inclure pcre2.h.

Les fonctions pcre2_compile() et pcre2_match() sont utilisées pour compiler et faire correspondre des expressions régulières d'une manière compatible avec Perl. Un programme d'exemple démontrant la manière la plus simple de les utiliser est fourni dans le fichier appelé pcre2demo.c dans la distribution source de PCRE2. Une liste de ce programme est donnée dans la documentation de pcre2demo, et la documentation de pcre2sample décrit comment le compiler et l'exécuter.

Les fonctions de compilation et de correspondance reconnaissent diverses options qui sont passées sous forme de bits dans un argument d'options. Il existe également des paramètres plus complexes tels que des fonctions de gestion de mémoire personnalisées et des limites de ressources qui sont passées dans des "contextes" (qui ne sont que des blocs mémoire, décrits ci-dessous). Les applications simples n'ont pas besoin d'utiliser de contextes.

Le support du compilateur Just-In-Time (JIT) est une fonctionnalité optionnelle de PCRE2 qui peut être intégrée dans des environnements matériels appropriés. Il accélère considérablement les performances de correspondance de nombreux motifs. Les programmes peuvent demander son utilisation si disponible en appelant pcre2_jit_compile() après qu'un motif a été compilé avec succès par pcre2_compile(). Ceci ne fait rien si le support JIT n'est pas disponible.

Les programmes plus complexes pourraient avoir besoin d'utiliser les fonctions spécialisées pcre2_jit_stack_create(), pcre2_jit_stack_free() et pcre2_jit_stack_assign() afin de contrôler l'utilisation de la mémoire du code JIT.

La correspondance JIT est automatiquement utilisée par pcre2_match() si elle est disponible, à moins que l'option PCRE2_NO_JIT ne soit définie. Il existe également une interface directe pour la correspondance JIT, qui offre des performances améliorées au détriment d'un contrôle de cohérence moins poussé. Les fonctions spécifiques au JIT sont discutées dans la documentation de pcre2jit.

Une deuxième fonction de correspondance, pcre2_dfa_match(), qui n'est pas compatible avec Perl, est également fournie. Celle-ci utilise un algorithme différent pour la correspondance. L'algorithme alternatif trouve toutes les correspondances possibles (à un point donné du sujet), et scanne le sujet une seule fois (sauf en cas d'assertions lookaround). Cependant, cet algorithme ne renvoie pas de sous-chaînes capturées. Une description des deux algorithmes de correspondance et de leurs avantages et inconvénients est donnée dans la documentation de pcre2matching. Il n'y a pas de support JIT pour pcre2_dfa_match().

En plus des fonctions principales de compilation et de correspondance, il existe des fonctions utilitaires pour extraire les sous-chaînes capturées d'une chaîne de sujet qui a été mise en correspondance par pcre2_match(). Ce sont :


pcre2_substring_copy_byname()
pcre2_substring_copy_bynumber()
pcre2_substring_get_byname()
pcre2_substring_get_bynumber()
pcre2_substring_list_get()
pcre2_substring_length_byname()
pcre2_substring_length_bynumber()
pcre2_substring_nametable_scan()
pcre2_substring_number_ from_name()

pcre2_substring_free() et pcre2_substring_list_free() sont également fournies, pour libérer la mémoire utilisée pour les chaînes extraites. Si l'une de ces fonctions est appelée avec un argument NULL, la fonction retourne immédiatement sans rien faire.

La fonction pcre2_substitute() peut être appelée pour faire correspondre un motif et retourner une copie de la chaîne sujet avec des substitutions pour les parties qui ont correspondu.

Les fonctions dont les noms commencent par pcre2_serialize_ sont utilisées pour sauvegarder les motifs compilés sur disque ou ailleurs, et les recharger plus tard.

Enfin, il existe des fonctions pour obtenir des informations sur un motif compilé (pcre2_pattern_info()) et sur la configuration avec laquelle PCRE2 a été construit (pcre2_config()) et qu'il utilise.

Les fonctions dont les noms se terminent par _free() sont utilisées pour libérer des blocs de mémoire de divers types. Dans tous les cas, si l'une de ces fonctions est appelée avec un argument NULL, elle ne fait rien.

LONGUEURS ET DÉCALAGES DES CHAÎNES

L'API PCRE2 utilise des longueurs de chaînes et des décalages dans les chaînes d'unités de code dans plusieurs endroits. Ces valeurs sont toujours de type PCRE2_SIZE, qui est un type entier non signé, actuellement toujours défini comme size_t. La plus grande valeur qui peut être stockée dans un tel type (~(PCRE2_SIZE)0) est réservée comme indicateur spécial pour les chaînes terminées par un zéro et les décalages non définis. Par conséquent, la chaîne la plus longue qui peut être gérée est inférieure d'une unité à ce maximum. Notez que les longueurs de chaînes sont toujours données en unités de code. Seulement dans la bibliothèque 8 bits, une telle longueur est identique au nombre d'octets de la chaîne.

NOUVELLES LIGNES

PCRE2 prend en charge cinq conventions différentes pour indiquer les coupures de ligne dans les chaînes : un seul caractère CR (retour chariot), un seul caractère LF (alimentation de ligne), la séquence de deux caractères CRLF, l'un des trois précédents, ou toute séquence de nouvelle ligne Unicode. Les séquences de nouvelle ligne Unicode sont les trois mentionnées ci-dessus, plus les caractères uniques VT (tabulation verticale, U+000B), FF (saut de page, U+000C), NEL (ligne suivante, U+0085), LS (séparateur de ligne, U+2028) et PS (séparateur de paragraphe, U+2029).

Chacune des trois premières conventions est utilisée par au moins un système d'exploitation comme séquence de nouvelle ligne standard. Lorsque PCRE2 est construit, une valeur par défaut peut être spécifiée. Si elle ne l'est pas, la valeur par défaut est LF, qui est la norme Unix. Cependant, la convention de nouvelle ligne peut être modifiée par une application lors de l'appel de pcre2_compile(), ou elle peut être spécifiée par un texte spécial au début du motif lui-même ; cela remplace toutes les autres configurations. Voir la page pcre2pattern pour les détails des séquences de caractères spéciaux.

Dans la documentation PCRE2, le mot "nouvelle ligne" est utilisé pour signifier "le caractère ou la paire de caractères qui indiquent une coupure de ligne". Le choix de la convention de nouvelle ligne affecte la gestion du point, du circonflexe et du dollar métacaractères, la gestion des commentaires # dans le mode /x, et, lorsque CRLF est une séquence de fin de ligne reconnue, l'avancement de la position de correspondance pour un motif non ancré. Il y a plus de détails à ce sujet dans la section sur les options de pcre2_match() ci-dessous.

Le choix de la convention de nouvelle ligne n'affecte pas l'interprétation des séquences d'échappement \n ou \r, ni ce que \R fait correspondre ; cela a sa propre convention distincte.

MULTITHREADING

Dans une application multithreadée, il est important de maintenir les données spécifiques au thread séparées des données qui peuvent être partagées entre les threads. Le code de la bibliothèque PCRE2 est lui-même thread-safe : il ne contient pas de variables statiques ou globales. L'API est conçue pour être assez simple pour les applications non-threadées tout en garantissant que les applications multithreadées peuvent l'utiliser.

Il existe plusieurs blocs de données différents utilisés pour passer des informations entre l'application et les bibliothèques PCRE2.

Le motif compilé

Un pointeur vers la forme compilée d'un motif est retourné à l'utilisateur lorsque pcre2_compile() réussit. Les données du motif compilé sont fixes et ne changent pas lorsque le motif est mis en correspondance. Par conséquent, il est thread-safe, c'est-à-dire que le même motif compilé peut être utilisé par plusieurs threads simultanément. Par exemple, une application peut compiler tous ses motifs au début, avant de créer plusieurs threads qui les utilisent. Cependant, si la fonctionnalité d'optimisation juste-à-temps (JIT) est utilisée, elle nécessite des zones de pile mémoire distinctes pour chaque thread. Voir la documentation pcre2jit pour plus de détails.

Dans une situation plus compliquée, où les motifs ne sont compilés que lorsqu'ils sont d'abord nécessaires, mais sont toujours partagés entre les threads, les pointeurs vers les motifs compilés doivent être protégés contre l'écriture simultanée par plusieurs threads. C'est un peu délicat à faire correctement. Si vous savez que l'écriture dans un pointeur est atomique dans votre environnement, vous pouvez utiliser une logique comme celle-ci :


Obtenir un verrou en lecture seule (partagé) (mutex) pour le pointeur
if (pointeur == NULL)
{
Obtenir un verrou en écriture (unique) pour le pointeur
if (pointeur == NULL) pointeur = pcre2_compile(...
}
Libérer le verrou
Utiliser le pointeur dans pcre2_match()

Bien sûr, le test des erreurs de compilation doit également être inclus dans le code.

La raison pour laquelle le pointeur est vérifié une seconde fois est la suivante : plusieurs threads peuvent avoir acquis le verrou partagé et testé si le pointeur est NULL, mais un seul d'entre eux obtiendra le verrou en écriture, les autres restant en attente. Le thread gagnant compilera le motif et stockera le résultat. Après que ce thread libère le verrou en écriture, un autre thread l'obtiendra, et s'il ne re-teste pas si le pointeur est NULL, il recompilera le motif et écrasera le pointeur, créant une fuite de mémoire et causant potentiellement d'autres problèmes.

Dans un environnement où l'écriture dans un pointeur peut ne pas être atomique, la logique ci-dessus n'est pas suffisante. Le thread qui effectue la compilation peut être désélectionné après n'avoir écrit qu'une partie du pointeur, ce qui pourrait amener d'autres threads à utiliser une valeur invalide. Au lieu de vérifier le pointeur lui-même, un indicateur séparé "pointeur valide" (qui peut être mis à jour de manière atomique) doit être utilisé :


Obtenir un verrou en lecture seule (partagé) (mutex) pour le pointeur
if (!pointeur_est_valide)
{
Obtenir un verrou en écriture (unique) pour le pointeur
if (!pointeur_est_valide)
{
pointeur = pcre2_compile(...
pointeur_est_valide = VRAI
}
}
Libérer le verrou
Utiliser le pointeur dans pcre2_match()

Si le JIT est utilisé, mais que la compilation JIT n'est pas effectuée immédiatement (peut-être en attendant de voir si le motif est utilisé suffisamment souvent), une logique similaire est requise. La compilation JIT met à jour une valeur dans le bloc de code compilé, donc un thread doit acquérir un accès d'écriture unique au pointeur avant d'appeler pcre2_jit_compile(). Alternativement, pcre2_code_copy() ou pcre2_code_copy_with_tables() peuvent être utilisés pour obtenir une copie privée du code compilé avant d'appeler le compilateur JIT.

Blocs de contexte

La section principale suivante ci-dessous introduit l'idée de "contextes" dans lesquels les fonctions PCRE2 sont appelées. Un contexte n'est rien de plus qu'une collection de paramètres qui contrôlent le fonctionnement de PCRE2. Regrouper un certain nombre de paramètres dans un contexte est un moyen pratique de les passer à une fonction PCRE2 sans utiliser de nombreux arguments. Les paramètres stockés dans les contextes sont, en quelque sorte, des "fonctionnalités avancées" de l'API. De nombreuses applications simples n'auront pas besoin d'utiliser de contextes.

Dans une application multithreadée, si les paramètres d'un contexte sont des valeurs qui ne sont jamais modifiées, le même contexte peut être utilisé par tous les threads. Cependant, si un thread a besoin de modifier une valeur dans un contexte, il doit créer sa propre copie spécifique au thread.

Blocs de correspondance

Les fonctions de correspondance nécessitent un bloc de mémoire pour stocker les résultats d'une correspondance. Cela inclut les détails de ce qui a été mis en correspondance, ainsi que des informations supplémentaires telles que le nom d'un réglage (*MARK). Chaque thread doit fournir sa propre copie de cette mémoire.

CONTEXTES PCRE2

Certaines fonctions PCRE2 ont beaucoup de paramètres, dont beaucoup ne sont utilisés que par des applications spécialisées, par exemple, celles qui utilisent une gestion de mémoire personnalisée ou des tables de caractères non standard. Pour maintenir des listes d'arguments de fonctions de taille raisonnable, et en même temps pour garder l'API extensible, les paramètres "peu courants" sont passés à certaines fonctions dans un contexte au lieu de directement. Un contexte est juste un bloc de mémoire qui contient les valeurs des paramètres. Les applications qui n'ont pas besoin d'ajuster les paramètres du contexte peuvent passer NULL lorsqu'un pointeur de contexte est requis.

Il existe trois types de contextes différents : un contexte général pertinent pour plusieurs opérations PCRE2, un contexte de compilation et un contexte de correspondance.

Le contexte général

Actuellement, ce contexte contient uniquement des pointeurs vers les fonctions de gestion de mémoire externes (et leurs données) qui sont appelées depuis plusieurs endroits de la bibliothèque PCRE2. Le contexte est nommé `général' plutôt que spécifiquement `mémoire' car à l'avenir d'autres champs pourraient être ajoutés. Si vous ne souhaitez pas fournir vos propres fonctions de gestion de mémoire personnalisées, vous n'avez pas besoin de vous soucier d'un contexte général. Un contexte général est créé par :

pcre2_general_context *pcre2_general_context_create(
  void *(*private_malloc)(PCRE2_SIZE, void *),
  void (*private_free)(void *, void *), void *memory_data);

Les deux pointeurs de fonction spécifient des fonctions de gestion de mémoire personnalisées, dont les prototypes sont :


void *private_malloc(PCRE2_SIZE, void *);
void private_free(void *, void *);

Chaque fois qu'un code dans PCRE2 appelle ces fonctions, le dernier argument est la valeur de memory_data. L'un des deux premiers arguments de la fonction de création peut être NULL, auquel cas les fonctions de gestion de mémoire système malloc() et free() sont utilisées. (Ce n'est pas actuellement utile, car il n'y a pas d'autres champs dans un contexte général, mais il pourrait y en avoir à l'avenir.) La fonction private_malloc() est utilisée (si fournie) pour obtenir de la mémoire pour stocker le conte

xt, et les trois valeurs sont enregistrées dans le contexte.

Chaque fois que PCRE2 crée un bloc de données, ce bloc contient un pointeur vers la fonction free() qui correspond à la fonction malloc() qui a été utilisée. Lorsque le moment est venu de libérer le bloc, cette fonction est appelée.

Un contexte général peut être copié en appelant :

pcre2_general_context *pcre2_general_context_copy(
  pcre2_general_context *gcontext);

La mémoire utilisée par un contexte général doit être libérée en appelant :

void pcre2_general_context_free(pcre2_general_context *gcontext);

Si cette fonction reçoit un argument NULL, elle retourne immédiatement sans rien faire.

Le contexte de compilation

Un contexte de compilation est requis si vous souhaitez fournir une fonction externe pour la vérification de la pile pendant la compilation ou pour modifier les valeurs par défaut des paramètres de compilation suivants :


Ce que \R correspond (nouvelles lignes Unicode ou uniquement CR, LF, CRLF)
Tables de caractères de PCRE2
La séquence de caractères de nouvelle ligne
La limite de parenthèses imbriquées au moment de la compilation
La longueur maximale de la chaîne de motif
Les bits d'options supplémentaires (aucun défini par défaut)
Quelles optimisations de performance le compilateur doit appliquer

Un contexte de compilation est également requis si vous utilisez une gestion de mémoire personnalisée. Si rien de tout cela ne s'applique, passez simplement NULL comme argument de contexte de pcre2_compile().

Un contexte de compilation est créé, copié et libéré par les fonctions suivantes :

pcre2_compile_context *pcre2_compile_context_create(
  pcre2_general_context *gcontext);

pcre2_compile_context *pcre2_compile_context_copy(
  pcre2_compile_context *ccontext);

void pcre2_compile_context_free(pcre2_compile_context *ccontext);

Un contexte de compilation est créé avec des valeurs par défaut pour ses paramètres. Celles-ci peuvent être modifiées en appelant les fonctions suivantes, qui retournent 0 en cas de succès, ou PCRE2_ERROR_BADDATA si des données invalides sont détectées.

int pcre2_set_bsr(pcre2_compile_context *ccontext,
  uint32_t value);

La valeur doit être PCRE2_BSR_ANYCRLF, pour spécifier que \R correspond uniquement à CR, LF ou CRLF, ou PCRE2_BSR_UNICODE, pour spécifier que \R correspond à toute séquence de fin de ligne Unicode. La valeur est utilisée par le compilateur JIT et par les deux fonctions de correspondance interprétées, pcre2_match() et pcre2_dfa_match().

int pcre2_set_character_tables(pcre2_compile_context *ccontext,
  const uint8_t *tables);

La valeur doit être le résultat d'un appel à pcre2_maketables(), dont le seul argument est un contexte général. Cette fonction construit un ensemble de tables de caractères dans la locale actuelle.

int pcre2_set_compile_extra_options(pcre2_compile_context *ccontext,
  uint32_t extra_options);

Au fur et à mesure du développement de PCRE2, presque tous les 32 bits d'options disponibles dans l'argument options de pcre2_compile() ont été utilisés. Pour éviter d'en manquer, le contexte de compilation contient un ensemble de bits d'options supplémentaires qui sont utilisés pour certaines options plus récentes, supposées plus rares. Cette fonction définit ces bits. Elle définit toujours tous les bits (activés ou désactivés). Elle ne modifie aucun réglage existant. Les options disponibles sont définies dans la section intitulée "Options de compilation supplémentaires" ci-dessous.

int pcre2_set_max_pattern_length(pcre2_compile_context *ccontext,
  PCRE2_SIZE value);

Ceci définit une longueur maximale, en unités de code, pour toute chaîne de motif compilée avec ce contexte. Si le motif est plus long, une erreur est générée. Cette fonctionnalité est fournie afin que les applications qui acceptent des motifs provenant de sources externes puissent limiter leur taille. La valeur par défaut est le plus grand nombre qu'une variable PCRE2_SIZE peut contenir, ce qui est effectivement illimité.

int pcre2_set_max_pattern_compiled_length(
  pcre2_compile_context *ccontext, PCRE2_SIZE value);

Ceci définit une taille maximale, en octets, pour la mémoire nécessaire à stocker la version compilée d'un motif compilé avec ce contexte. Si le motif nécessite plus de mémoire, une erreur est générée. Cette fonctionnalité est fournie afin que les applications qui acceptent des motifs provenant de sources externes puissent limiter la quantité de mémoire qu'elles utilisent. La valeur par défaut est le plus grand nombre qu'une variable PCRE2_SIZE peut contenir, ce qui est effectivement illimité.

int pcre2_set_max_varlookbehind(pcre2_compile_contest *ccontext,
  uint32_t value);

Ceci définit une longueur maximale pour le nombre de caractères correspondant à une assertion lookbehind de longueur variable. La valeur par défaut est définie lors de la compilation de PCRE2, la valeur par défaut ultime étant 255, identique à celle de Perl. Les assertions lookbehind sans longueur bornée ne sont pas prises en charge.

int pcre2_set_newline(pcre2_compile_context *ccontext,
  uint32_t value);

Ceci spécifie quels caractères ou séquences de caractères doivent être reconnus comme nouvelles lignes. La valeur doit être l'une des suivantes : PCRE2_NEWLINE_CR (retour chariot uniquement), PCRE2_NEWLINE_LF (saut de ligne uniquement), PCRE2_NEWLINE_CRLF (la séquence de deux caractères CR suivie de LF), PCRE2_NEWLINE_ANYCRLF (l'un des éléments ci-dessus), PCRE2_NEWLINE_ANY (toute séquence de nouvelle ligne Unicode), ou PCRE2_NEWLINE_NUL (le caractère NUL, c'est-à-dire un zéro binaire).

Un motif peut remplacer la valeur définie dans le contexte de compilation en commençant par une séquence telle que (*CRLF). Voir la page pcre2pattern pour plus de détails.

Lorsqu'un motif est compilé avec l'option PCRE2_EXTENDED ou PCRE2_EXTENDED_MORE, la convention de nouvelle ligne affecte la reconnaissance de la fin des commentaires internes commençant par #. La valeur est enregistrée avec le motif compilé pour une utilisation ultérieure par le compilateur JIT et par les deux fonctions de correspondance interprétées, pcre2_match() et pcre2_dfa_match().

int pcre2_set_parens_nest_limit(pcre2_compile_context *ccontext,
  uint32_t value);

Ce paramètre ajuste la limite, définie lors de la compilation de PCRE2 (par défaut 250), sur la profondeur d'imbrication des parenthèses dans un motif. Cette limite empêche les motifs défectueux d'utiliser trop de pile système lors de leur compilation. La limite s'applique aux parenthèses de toutes sortes, pas seulement aux parenthèses capturantes.

int pcre2_set_compile_recursion_guard(pcre2_compile_context *ccontext,
  int (*guard_function)(uint32_t, void *), void *user_data);

Il existe au moins une application qui exécute PCRE2 dans des threads avec une pile système très limitée, où il faut absolument éviter de manquer de pile. La limite de parenthèses ci-dessus ne peut pas tenir compte de la pile réellement disponible pendant la compilation. Pour un contrôle plus fin, vous pouvez fournir une fonction qui est appelée chaque fois que pcre2_compile() commence à compiler une partie parenthésée d'un motif. Cette fonction peut vérifier la taille réelle de la pile (ou tout ce qu'elle souhaite, bien sûr).

Le premier argument de la fonction de rappel donne la profondeur actuelle d'imbrication, et le second est une donnée utilisateur définie par le dernier argument de pcre2_set_compile_recursion_guard(). La fonction de rappel doit retourner zéro si tout va bien, ou une valeur non nulle pour forcer une erreur.

int pcre2_set_optimize(pcre2_compile_context *ccontext,
  uint32_t directive);

PCRE2 peut appliquer diverses optimisations de performance lors de la compilation, afin de rendre la correspondance plus rapide. Par exemple, le compilateur peut convertir certaines constructions regex en une construction équivalente que pcre2_match() peut exécuter plus rapidement. Par défaut, toutes les optimisations disponibles sont activées. Cependant, dans de rares cas, on pourrait souhaiter désactiver des optimisations spécifiques. Par exemple, s'il est connu que certaines optimisations ne peuvent pas bénéficier à un certain regex, il pourrait être souhaitable de les désactiver, afin d'accélérer la compilation.

Les valeurs permises pour directive sont les suivantes :


PCRE2_OPTIMIZATION_FULL

Active toutes les optimisations de performance optionnelles. C'est la valeur par défaut.


PCRE2_OPTIMIZATION_NONE

Désactive toutes les optimisations de performance optionnelles.


PCRE2_AUTO_POSSESS
PCRE2_AUTO_POSSESS_OFF

Active/désactive la "possessification automatique" des quantificateurs variables tels que * et +. Cette optimisation, par exemple, transforme a+b en a++b afin d'éviter les backtracking dans a+ qui ne peuvent jamais réussir. Cependant, si des callouts sont utilisés, la possessification automatique signifie que certains callouts ne sont jamais pris. Vous pouvez désactiver cette optimisation si vous voulez que les fonctions de correspondance effectuent une recherche complète, non optimisée, et exécutent tous les callouts.


PCRE2_DOTSTAR_ANCHOR
PCRE2_DOTSTAR_ANCHOR_OFF

Active/désactive une optimisation appliquée lorsque .* est le premier élément significatif dans une branche de niveau supérieur d'un motif, et que toutes les autres branches commencent également par .* ou par \A ou \G ou ^. Un tel motif est automatiquement ancré si PCRE2_DOTALL est défini pour tous les éléments .* et que PCRE2_MULTILINE n'est pas défini pour aucun des éléments ^. Sinon, le fait que toute correspondance doit commencer soit au début du sujet, soit après une nouvelle ligne est mémorisé. Comme d'autres optimisations, cela peut entraîner le saut de certains callouts.

L'optimisation d'ancrage dotstar est automatiquement désactivée pour .* s'il est à l'intérieur d'un groupe atomique ou d'un groupe de capture qui est le sujet d'une référence arrière, ou si le motif contient (*PRUNE) ou (*SKIP).


PCRE2_START_OPTIMIZE
PCRE2_START_OPTIMIZE_OFF

Active/désactive les optimisations qui font que les fonctions de correspondance scannent la chaîne de sujet à la recherche de valeurs d'unités de code spécifiques avant de tenter une correspondance. Par exemple, s'il est connu qu'une correspondance non ancrée doit commencer par une valeur spécifique, le code de correspondance recherche cette valeur dans le sujet et échoue immédiatement si elle ne la trouve pas, sans exécuter réellement la fonction de correspondance principale. Cela signifie qu'un élément spécial tel que (*COMMIT) au début d'un motif n'est pas pris en compte avant qu'un point de départ approprié pour la correspondance n'ait été trouvé. De plus, lorsque des callouts ou des éléments (*MARK) sont utilisés, ces optimisations de "démarrage" peuvent les faire sauter si le motif n'est jamais réellement utilisé. Les optimisations de démarrage sont effectivement un pré-scan du sujet qui a lieu avant que le motif ne soit exécuté.

La désactivation des optimisations de démarrage garantit que dans les cas où le résultat est "aucune correspondance", les callouts se produisent, et que des éléments tels que (*COMMIT) et (*MARK) sont considérés à chaque position de départ possible dans la chaîne de sujet.

La désactivation des optimisations de démarrage peut modifier le résultat d'une opération de correspondance. Considérons le motif


(*COMMIT)ABC

Lorsqu'il est compilé, PCRE2 enregistre le fait qu'une correspondance doit commencer par le caractère "A". Supposons que la chaîne de sujet soit "DEFABC". L'optimisation de démarrage scanne alo

ng the subject, finds "A" et lance la première tentative de correspondance à partir de là. L'élément (*COMMIT) signifie que le modèle doit correspondre à la position de départ actuelle, ce qui est le cas ici. Cependant, si la même correspondance est effectuée sans optimisations de démarrage, le balayage initial de la chaîne sujette ne se produit pas. La première tentative de correspondance est effectuée à partir de "D" et lorsque celle-ci échoue, (*COMMIT) empêche toute autre correspondance d'être essayée, de sorte que le résultat global est "aucune correspondance".

Une autre optimisation de démarrage utilise une longueur minimale pour un sujet correspondant, qui est enregistrée lorsque cela est possible. Considérez le modèle


(*MARK:1)B(*MARK:2)(X|Y)

La longueur minimale pour une correspondance est de deux caractères. Si le sujet est "XXBB", l'optimisation "caractère de départ" saute "XX", puis essaie de faire correspondre "BB", ce qui est assez long. Dans ce processus, (*MARK:2) est rencontré et mémorisé. Lorsque la tentative de correspondance échoue, le "B" suivant est trouvé, mais il ne reste qu'un seul caractère, il n'y a donc plus de tentatives, et "aucune correspondance" est retourné avec la "dernière marque vue" définie sur "2". Sans optimisation de démarrage, cependant, les correspondances sont essayées à chaque position de départ possible, y compris à la fin du sujet, où (*MARK:1) est rencontré, mais il n'y a pas de "B", donc la "dernière marque vue" qui est retournée est "1". Dans ce cas, les optimisations n'affectent pas le résultat global de la correspondance, qui est toujours "aucune correspondance", mais elles affectent les informations auxiliaires qui sont retournées.

Le contexte de correspondance

Un contexte de correspondance est requis si vous souhaitez :


Configurer une fonction de rappel (callout)
Définir une limite de décalage pour la correspondance d'un modèle non ancré
Modifier la limite sur la quantité de tas (heap) utilisée lors de la correspondance
Modifier la limite de correspondance de rétroaction (backtracking)
Modifier la limite de profondeur de rétroaction (backtracking)
Définir une gestion de mémoire personnalisée spécifiquement pour la correspondance

Si aucune de ces conditions ne s'applique, passez simplement NULL comme argument de contexte de pcre2_match(), pcre2_dfa_match(), ou pcre2_jit_match().

Un contexte de correspondance est créé, copié et libéré par les fonctions suivantes :

pcre2_match_context *pcre2_match_context_create(
  pcre2_general_context *gcontext);

pcre2_match_context *pcre2_match_context_copy(
  pcre2_match_context *mcontext);

void pcre2_match_context_free(pcre2_match_context *mcontext);

Un contexte de correspondance est créé avec des valeurs par défaut pour ses paramètres. Ceux-ci peuvent être modifiés en appelant les fonctions suivantes, qui retournent 0 en cas de succès, ou PCRE2_ERROR_BADDATA si des données invalides sont détectées.

int pcre2_set_callout(pcre2_match_context *mcontext,
  int (*callout_function)(pcre2_callout_block *, void *),
  void *callout_data);

Ceci configure une fonction de rappel pour que PCRE2 l'appelle à des points spécifiés pendant une opération de correspondance. Les détails sont donnés dans la documentation pcre2callout.

int pcre2_set_substitute_callout(pcre2_match_context *mcontext,
  int (*callout_function)(pcre2_substitute_callout_block *, void *),
  void *callout_data);

Ceci configure une fonction de rappel pour que PCRE2 l'appelle après chaque substitution effectuée par pcre2_substitute(). Les détails sont donnés dans la section intitulée "Créer une nouvelle chaîne avec des substitutions" ci-dessous.

int pcre2_set_substitute_case_callout(pcre2_match_context *mcontext,
  PCRE2_SIZE (*callout_function)(PCRE2_SPTR, PCRE2_SIZE,
                                 PCRE2_UCHAR *, PCRE2_SIZE,
                                 int, void *),
  void *callout_data);

Ceci configure une fonction de rappel pour que PCRE2 l'appelle lors de transformations de casse effectuées dans pcre2_substitute(). Les détails sont donnés dans la section intitulée "Créer une nouvelle chaîne avec des substitutions" ci-dessous.

int pcre2_set_offset_limit(pcre2_match_context *mcontext,
  PCRE2_SIZE value);

Le paramètre offset_limit limite la distance à laquelle une recherche non ancrée peut avancer dans la chaîne sujette. La valeur par défaut est PCRE2_UNSET. Les fonctions pcre2_match() et pcre2_dfa_match() retournent PCRE2_ERROR_NOMATCH si une correspondance avec un point de départ avant ou au décalage donné n'est pas trouvée. La fonction pcre2_substitute() ne fait plus de substitutions.

Par exemple, si le modèle /abc/ est mis en correspondance avec "123abc" avec une limite de décalage inférieure à 3, le résultat est PCRE2_ERROR_NOMATCH. Une correspondance ne peut jamais être trouvée si l'argument startoffset de pcre2_match(), pcre2_dfa_match(), ou pcre2_substitute() est supérieur à la limite de décalage définie dans le contexte de correspondance.

Lors de l'utilisation de cette fonctionnalité, vous devez définir l'option PCRE2_USE_OFFSET_LIMIT lors de l'appel à pcre2_compile() afin que, lorsque le JIT est utilisé, un code différent puisse être compilé. Si une correspondance est démarrée avec une limite de correspondance non défaut alors que PCRE2_USE_OFFSET_LIMIT n'est pas définie, une erreur est générée.

La fonctionnalité de limite de décalage peut être utilisée pour suivre la progression lors de la recherche de grandes chaînes sujettes ou pour limiter l'étendue des substitutions globales. Voir également l'option PCRE2_FIRSTLINE, qui nécessite qu'une correspondance commence avant ou au premier saut de ligne qui suit le début de la correspondance dans le sujet. Si cela est défini avec une limite de décalage, une correspondance doit se produire dans la première ligne et également dans la limite de décalage. En d'autres termes, quelle que soit la limite qui vient en premier est utilisée.

int pcre2_set_heap_limit(pcre2_match_context *mcontext,
  uint32_t value);

Le paramètre heap_limit spécifie, en unités de kibioctets (1024 octets), la quantité maximale de mémoire tas (heap) que pcre2_match() peut utiliser pour conserver les informations de rétroaction lors de l'exécution d'une correspondance interprétée. Cette limite s'applique également à pcre2_dfa_match(), qui peut utiliser le tas lors du traitement de modèles avec beaucoup de récursion de modèle imbriquée ou de groupes atomiques ou d'assertions lookaround. Cette limite ne s'applique pas à la correspondance avec l'optimisation JIT, qui a ses propres arrangements de contrôle de mémoire (voir la documentation pcre2jit pour plus de détails). Si la limite est atteinte, le code d'erreur négatif PCRE2_ERROR_HEAPLIMIT est retourné. La limite par défaut peut être définie lors de la compilation de PCRE2 ; si elle ne l'est pas, la valeur par défaut est très grande et est essentiellement illimitée.

Une valeur pour la limite du tas peut également être fournie par un élément au début d'un modèle de la forme


(*LIMIT_HEAP=ddd)

où ddd est un nombre décimal. Cependant, un tel réglage est ignoré à moins que ddd ne soit inférieur à la limite définie par l'appelant de pcre2_match() ou, si aucune limite n'est définie, inférieur à la valeur par défaut.

La fonction pcre2_match() a toujours besoin d'un peu de mémoire tas, donc la définition d'une valeur de zéro garantit une erreur "limite du tas dépassée". Les détails sur la façon dont pcre2_match() utilise le tas sont donnés dans la documentation pcre2perform.

Pour pcre2_dfa_match(), un vecteur sur la pile système est utilisé lors du traitement des récursions de modèle, des lookarounds ou des groupes atomiques, et ce n'est que si celui-ci n'est pas assez grand que la mémoire tas est utilisée. Dans ce cas, la définition d'une valeur de zéro désactive l'utilisation du tas.

int pcre2_set_match_limit(pcre2_match_context *mcontext,
  uint32_t value);

Le paramètre match_limit fournit un moyen d'empêcher PCRE2 d'utiliser trop de ressources informatiques lors du traitement de modèles qui ne vont pas correspondre, mais qui ont un très grand nombre de possibilités dans leurs arbres de recherche. L'exemple classique est un modèle qui utilise des répétitions imbriquées illimitées.

Il y a un compteur interne dans pcre2_match() qui est incrémenté à chaque tour de sa boucle de correspondance principale. Si cette valeur atteint la limite de correspondance, pcre2_match() retourne la valeur négative PCRE2_ERROR_MATCHLIMIT. Cela a pour effet de limiter la quantité de rétroaction qui peut avoir lieu. Pour les modèles qui ne sont pas ancrés, le compte redémarre à zéro pour chaque position dans la chaîne sujette. Cette limite s'applique également à pcre2_dfa_match(), bien que le comptage soit effectué d'une manière différente.

Lorsque pcre2_match() est appelée avec un modèle qui a été traité avec succès par pcre2_jit_compile(), la manière dont la correspondance est exécutée est complètement différente. Cependant, il existe toujours la possibilité d'une correspondance incontrôlée qui dure très longtemps, et donc la valeur match_limit est également utilisée dans ce cas (mais d'une manière différente) pour limiter la durée de la correspondance.

La valeur par défaut de la limite peut être définie lors de la compilation de PCRE2 ; la valeur par défaut est de 10 millions, ce qui gère tous les cas, sauf les plus extrêmes. Une valeur pour la limite de correspondance peut également être fournie par un élément au début d'un modèle de la forme


(*LIMIT_MATCH=ddd)

où ddd est un nombre décimal. Cependant, un tel réglage est ignoré à moins que ddd ne soit inférieur à la limite définie par l'appelant de pcre2_match() ou pcre2_dfa_match() ou, si aucune limite n'est définie, inférieur à la valeur par défaut.

int pcre2_set_depth_limit(pcre2_match_context *mcontext,
  uint32_t value);

Ce paramètre limite la profondeur de la rétroaction imbriquée dans pcre2_match(). Chaque fois qu'un point de rétroaction imbriqué est passé, une nouvelle trame de mémoire est utilisée pour se souvenir de l'état de la correspondance à ce point. Ainsi, ce paramètre limite indirectement la quantité de mémoire utilisée dans une correspondance. Cependant, comme la taille de chaque trame de mémoire dépend du nombre de parenthèses de capture, la limite de mémoire réelle varie d'un modèle à l'autre. Cette limite était plus utile dans les versions antérieures à 10.30, où la récursion de fonction était utilisée pour la rétroaction.

La limite de profondeur n'est pas pertinente, et est ignorée, lorsque la correspondance est effectuée à l'aide de code compilé par JIT. Cependant, elle est prise en charge par pcre2_dfa_match(), qui l'utilise pour limiter la profondeur des appels de fonction récursifs internes imbriqués qui implémentent les groupes atomiques, les assertions lookaround et les récursions de modèle. Cela limite, indirectement, la quantité de pile système utilisée. Elle était plus utile dans les versions antérieures à 10.32, lorsque la mémoire de pile était utilisée pour les vecteurs d'espace de travail locaux pour les appels de fonction récursifs. À partir de la version 10.32, seules les variables locales sont allouées sur la pile et comme chaque appel utilise seulement quelques centaines d'octets, même une petite pile peut supporter une quantité de récursion assez importante.

Si la profondeur des appels de fonction récursifs internes est suffisamment grande, les vecteurs d'espace de travail locaux sont alloués sur le tas à partir de la version 10.32, de sorte que la limite de profondeur limite également indirectement la quantité de mémoire tas utilisée. Un modèle récursif tel que /(.(?2))((?1)|)/, lorsqu'il est mis en correspondance avec une très longue chaîne à l'aide de pcre2_dfa_match(), peut utiliser une grande quantité de mémoire. Cependant, il est probablement préférable de limiter directement l'utilisation du tas en appelant pcre2_set_heap_limit().

La valeur par défaut pour la limite de profondeur peut être définie lors de la compilation de PCRE2 ; si ce n'est pas le cas, la valeur par défaut est égale à la valeur par défaut de la limite de correspondance. Si la limite est dépassée, pcre2_match() ou pcre2_dfa_match() retourne PCRE2_ERROR_DEPTHLIMIT. Une valeur pour la limite de profondeur peut également être fournie par un élément au début d'un motif de la forme


(*LIMIT_DEPTH=ddd)

où ddd est un nombre décimal. Cependant, un tel réglage est ignoré à moins que ddd ne soit inférieur à la limite définie par l'appelant de pcre2_match() ou pcre2_dfa_match() ou, si aucune telle limite n'est définie, inférieur à la valeur par défaut.

VERIFICATION DES OPTIONS DE COMPILATION

int pcre2_config(uint32_t what, void *where);

La fonction pcre2_config() permet à un client PCRE2 de connaître la valeur de certains paramètres de configuration et de découvrir quelles fonctionnalités optionnelles ont été compilées dans la bibliothèque PCRE2. La documentation pcre2build contient plus de détails sur ces fonctionnalités.

Le premier argument de pcre2_config() spécifie les informations requises. Le second argument est un pointeur vers la mémoire où les informations sont placées. Si NULL est passé, la fonction retourne la quantité de mémoire nécessaire pour les informations demandées. Pour les appels qui retournent des valeurs numériques, la valeur est en octets ; lors de la demande de ces valeurs, where doit pointer vers une mémoire appropriément alignée. Pour les appels qui retournent des chaînes, la longueur requise est donnée en unités de code, sans compter le zéro terminateur.

Lors de la demande d'informations, la valeur retournée par pcre2_config() est non négative en cas de succès, ou le code d'erreur négatif PCRE2_ERROR_BADOPTION si la valeur du premier argument n'est pas reconnue. Les informations suivantes sont disponibles :


PCRE2_CONFIG_BSR

La sortie est un entier uint32_t dont la valeur indique quelles séquences de caractères la séquence d'échappement \R fait correspondre par défaut. Une valeur de PCRE2_BSR_UNICODE signifie que \R fait correspondre toute séquence de fin de ligne Unicode ; une valeur de PCRE2_BSR_ANYCRLF signifie que \R ne fait correspondre que CR, LF ou CRLF. La valeur par défaut peut être remplacée lors de la compilation d'un motif.


PCRE2_CONFIG_COMPILED_WIDTHS

La sortie est un entier uint32_t dont les bits inférieurs indiquent quelles largeurs d'unités de code ont été sélectionnées lors de la compilation de PCRE2. Le bit 1 indique le support 8 bits, et les bits 2 et 4 indiquent le support 16 bits et 32 bits, respectivement.


PCRE2_CONFIG_DEPTHLIMIT

La sortie est un entier uint32_t qui donne la limite par défaut de la profondeur de la rétroaction imbriquée dans pcre2_match() ou de la profondeur des récursions imbriquées, des lookarounds et des groupes atomiques dans pcre2_dfa_match(). Plus de détails sont donnés avec pcre2_set_depth_limit() ci-dessus.


PCRE2_CONFIG_EFFECTIVE_LINKSIZE

La sortie est un entier uint32_t qui contient le nombre d'octets utilisé par la bibliothèque pour le lien interne dans les expressions régulières compilées. Sa valeur est dérivée de la valeur qui a été fournie au moment de la compilation et qui est décrite ci-dessous par PCRE2_CONFIG_LINKSIZE.


PCRE2_CONFIG_HEAPLIMIT

La sortie est un entier uint32_t qui donne, en kibioctets, la limite par défaut de la quantité de mémoire du tas utilisée par pcre2_match() ou pcre2_dfa_match(). Plus de détails sont donnés avec pcre2_set_heap_limit() ci-dessus.


PCRE2_CONFIG_JIT

La sortie est un entier uint32_t qui est mis à un si le support de la compilation juste-à-temps est inclus dans la bibliothèque ; sinon, il est mis à zéro. Notez que la présence du support dans la bibliothèque ne garantit pas que le JIT sera utilisé pour une correspondance donnée, ni qu'il pourra effectivement fonctionner, car il pourrait ne pas être en mesure d'allouer de la mémoire exécutable dans certains environnements. Il existe un appel spécial à pcre2_jit_compile() qui peut être utilisé pour vérifier cela. Voir la documentation pcre2jit pour plus de détails.


PCRE2_CONFIG_JITTARGET

L'argument where doit pointer vers un tampon d'au moins 64 unités de code. (La longueur exacte requise peut être trouvée en appelant pcre2_config() avec where défini à NULL.) Le tampon est rempli d'une chaîne contenant le nom de l'architecture pour laquelle le compilateur JIT est configuré, par exemple "x86 32bit (little endian + unaligned)". Si le support JIT n'est pas disponible, PCRE2_ERROR_BADOPTION est retourné, sinon le nombre d'unités de code utilisées est retourné. Il s'agit de la longueur de la chaîne, plus une unité pour le zéro terminateur.


PCRE2_CONFIG_LINKSIZE

La sortie est un entier uint32_t qui contient le nombre d'octets que la bibliothèque a reçu pour instruction d'utiliser pour le lien interne dans les expressions régulières compilées. Lors de la configuration de PCRE2, la valeur peut être définie à 2, 3 ou 4, la valeur par défaut étant 2 pour la plupart des bibliothèques.

Le nombre réel d'octets utilisés dépend de la taille des unités de code prises en charge par la bibliothèque et peut être plus élevé. Voir PCRE2_CONFIG_EFFECTIVE_LINKSIZE ci-dessus pour plus de détails.

La valeur par défaut de 2 pour les bibliothèques 8 bits et 16 bits est suffisante pour tous les motifs, sauf les plus massifs, car elle permet à la taille du motif compilé d'atteindre 65535 unités de code. Des valeurs plus grandes permettent de compiler des expressions régulières plus grandes avec ces deux bibliothèques, mais au détriment d'une correspondance plus lente.


PCRE2_CONFIG_MATCHLIMIT

La sortie est un entier uint32_t qui donne la limite de correspondance par défaut pour pcre2_match(). Plus de détails sont donnés avec pcre2_set_match_limit() ci-dessus.


PCRE2_CONFIG_NEWLINE

La sortie est un entier uint32_t dont la valeur spécifie la séquence de caractères par défaut qui signifie "nouvelle ligne". Les valeurs sont :


PCRE2_NEWLINE_CR Retour chariot (CR)
PCRE2_NEWLINE_LF Saut de ligne (LF)
PCRE2_NEWLINE_CRLF Retour chariot, saut de ligne (CRLF)
PCRE2_NEWLINE_ANY Toute fin de ligne Unicode
PCRE2_NEWLINE_ANYCRLF N'importe quel CR, LF ou CRLF
PCRE2_NEWLINE_NUL Le caractère NUL (zéro binaire)

La valeur par défaut doit normalement correspondre à la séquence standard de votre système d'exploitation.


PCRE2_CONFIG_NEVER_BACKSLASH_C

La sortie est un entier uint32_t qui est mis à un si l'utilisation de \C a été définitivement désactivée lors de la compilation de PCRE2 ; sinon, elle est mise à zéro.


PCRE2_CONFIG_PARENSLIMIT

La sortie est un entier uint32_t qui donne la profondeur maximale de imbrication des parenthèses (de tout type) dans un motif. Cette limite est imposée pour limiter la quantité de pile système utilisée lors de la compilation d'un motif. Elle est spécifiée lors de la compilation de PCRE2 ; la valeur par défaut est 250. Cette limite ne tient pas compte de la pile qui peut déjà être utilisée par l'application appelante. Pour un contrôle plus fin de l'utilisation de la pile de compilation, voir pcre2_set_compile_recursion_guard().


PCRE2_CONFIG_STACKRECURSE

Ce paramètre est obsolète et ne doit pas être utilisé dans du code nouveau. La sortie est un entier uint32_t qui est toujours mis à zéro.


PCRE2_CONFIG_TABLES_LENGTH

La sortie est un entier uint32_t qui donne la longueur des tables de traitement des caractères de PCRE2 en octets. Pour plus de détails sur ces tables, voir la section sur le support de la locale ci-dessous.


PCRE2_CONFIG_UNICODE_VERSION

L'argument where doit pointer vers un tampon d'au moins 24 unités de code. (La longueur exacte requise peut être trouvée en appelant pcre2_config() avec where défini à NULL.) Si PCRE2 a été compilé sans support Unicode, le tampon est rempli du texte "Unicode not supported". Sinon, la chaîne de version Unicode (par exemple, "8.0.0") est insérée. Le nombre d'unités de code utilisées est retourné. Il s'agit de la longueur de la chaîne plus une unité pour le zéro terminateur.


PCRE2_CONFIG_UNICODE

La sortie est un entier uint32_t qui est mis à un si le support Unicode est disponible ; sinon, il est mis à zéro. Le support Unicode implique le support UTF.


PCRE2_CONFIG_VERSION

L'argument where doit pointer vers un tampon d'au moins 24 unités de code. (La longueur exacte requise peut être trouvée en appelant pcre2_config() avec where défini à NULL.) Le tampon est rempli de la chaîne de version de PCRE2, terminée par un zéro. Le nombre d'unités de code utilisées est retourné. Il s'agit de la longueur de la chaîne plus une unité pour le zéro terminateur.

COMPILATION D'UN MOTIF

pcre2_code *pcre2_compile(PCRE2_SPTR pattern, PCRE2_SIZE length,
  uint32_t options, int *errorcode, PCRE2_SIZE *erroroffset,
  pcre2_compile_context *ccontext);

void pcre2_code_free(pcre2_code *code);

pcre2_code *pcre2_code_copy(const pcre2_code *code);

pcre2_code *pcre2_code_copy_with_tables(const pcre2_code *code);

La fonction pcre2_compile() compile un motif dans une forme interne. Le motif est défini par un pointeur vers une chaîne d'unités de code et une longueur en unités de code. Si le motif est terminé par un zéro, la longueur peut être spécifiée comme PCRE2_ZERO_TERMINATED. Un pointeur de motif NULL avec une longueur de zéro est traité comme une chaîne vide (NULL avec une longueur non nulle provoque un retour d'erreur). La fonction retourne un pointeur vers un bloc de mémoire contenant le motif compilé et les données associées, ou NULL en cas d'erreur.

Si l'argument de contexte de compilation ccontext est NULL, la mémoire pour le motif compilé est obtenue en appelant malloc(). Sinon, elle est obtenue à partir de la même fonction de mémoire que celle utilisée pour le contexte de compilation. L'appelant doit libérer la mémoire en appelant pcre2_code_free() lorsqu'elle n'est plus nécessaire. Si pcre2_code_free() est appelé avec un argument NULL, il retourne immédiatement, sans rien faire.

La fonction pcre2_code_copy() crée une copie du code compilé dans une nouvelle mémoire, en utilisant le même allocateur mémoire que celui utilisé pour l'original. Cependant, si le code a été traité par le compilateur JIT (voir ci-dessous), les informations JIT ne peuvent pas être copiées (car elles dépendent de la position). La nouvelle copie ne peut initialement être utilisée que pour des correspondances non-JIT, bien qu'elle puisse être passée à pcre2_jit_compile() si nécessaire. Si pcre2_code_copy() est appelé avec un argument NULL, il retourne NULL.

La fonction pcre2_code_copy() permet à des threads individuels dans une application multithread d'acquérir une copie privée du code compilé partagé. Cependant, elle ne crée pas de copie des tables de caractères utilisées par le motif compilé ; le nouveau motif coqui pointe vers les mêmes tables que le code original. (Voir "Prise en charge des locales" ci-dessous pour les détails de ces tables de caractères.) Dans de nombreuses applications, les mêmes tables sont utilisées tout au long, donc ce comportement est approprié. Néanmoins, il y a des cas où une copie d'un motif compilé et les tables pertinentes sont nécessaires. La fonction pcre2_code_copy_with_tables() fournit cette facilité. Des copies du code et des tables sont effectuées, le nouveau code pointant vers les nouvelles tables. La mémoire des nouvelles tables est automatiquement libérée lorsque pcre2_code_free() est appelée pour la nouvelle copie du code compilé. Si pcre2_code_copy_with_tables() est appelée avec un argument NULL, elle retourne NULL.

NOTE : Lorsque l'une des fonctions de correspondance est appelée, des pointeurs vers le motif compilé et la chaîne sujet sont définis dans le bloc de données de correspondance afin qu'ils puissent être référencés par les fonctions d'extraction de sous-chaînes après une correspondance réussie. Après avoir exécuté une correspondance, vous ne devez pas libérer un motif compilé ou une chaîne sujet jusqu'à ce que toutes les opérations sur le bloc de données de correspondance aient eu lieu, sauf si, dans le cas de la chaîne sujet, vous avez utilisé l'option PCRE2_COPY_MATCHED_SUBJECT, qui est décrite dans la section intitulée "Bits d'option pour pcre2_match()" ci-dessous.

L'argument options pour pcre2_compile() contient divers réglages de bits qui affectent la compilation. Il doit être zéro si aucun d'entre eux n'est requis. Les options disponibles sont décrites ci-dessous. Certaines d'entre elles (en particulier celles qui sont compatibles avec Perl, mais aussi d'autres) peuvent également être définies et désactivées depuis le motif lui-même (voir la description détaillée dans la documentation de pcre2pattern).

Pour les options qui peuvent être différentes dans différentes parties du motif, le contenu de l'argument options spécifie leurs réglages au moment de la compilation. Les options PCRE2_ANCHORED, PCRE2_ENDANCHORED et PCRE2_NO_UTF_CHECK peuvent être définies au moment de la correspondance ainsi qu'au moment de la compilation.

Certaines options supplémentaires et des paramètres de compilation moins fréquemment requis (par exemple, le réglage des nouvelles lignes) peuvent être fournis dans un contexte de compilation (comme décrit ci-dessus).

Si errorcode ou erroroffset est NULL, pcre2_compile() retourne NULL immédiatement. Sinon, les variables vers lesquelles ils pointent sont définies avec un code d'erreur et un décalage (nombre d'unités de code) dans le motif, respectivement, lorsque pcre2_compile() retourne NULL en raison d'une erreur de compilation.

Il existe plus de 100 codes d'erreur positifs que pcre2_compile() peut retourner si elle trouve une erreur dans le motif. Il existe également des codes d'erreur négatifs qui sont utilisés pour les chaînes UTF invalides lorsque la vérification de validité est activée. Ceux-ci sont les mêmes que ceux retournés par pcre2_match() et pcre2_dfa_match(), et sont décrits dans la documentation de pcre2unicode. Il n'y a pas de documentation séparée pour les codes d'erreur positifs, car les messages d'erreur textuels obtenus en appelant la fonction pcre2_get_error_message() (voir "Obtention d'un message d'erreur textuel" ci-dessous) devraient être auto-explicatifs. Les noms de macros commençant par PCRE2_ERROR_ sont définis pour les codes d'erreur positifs et négatifs dans pcre2.h. Lorsque la compilation réussit, errorcode est défini sur une valeur qui retourne le message "no error" si elle est passée à pcre2_get_error_message().

La valeur retournée dans erroroffset est une indication de l'endroit dans le motif où une erreur s'est produite. En l'absence d'erreur, zéro est retourné. Une valeur non nulle n'est pas nécessairement le point le plus éloigné du motif qui a été lu. Par exemple, après l'erreur "lookbehind assertion is not fixed length", le décalage d'erreur pointe vers le début de l'assertion défaillante. Pour une chaîne UTF-8 ou UTF-16 invalide, le décalage est celui de la première unité de code du caractère défaillant.

Certaines erreurs ne sont détectées que lorsque tout le motif a été parcouru ; dans ces cas, le décalage retourné est la longueur du motif. Notez que le décalage est en unités de code, pas en caractères, même en mode UTF. Il peut parfois pointer au milieu d'un caractère UTF-8 ou UTF-16.

Ce fragment de code montre un appel typique et direct à pcre2_compile() :


pcre2_code *re;
PCRE2_SIZE erroffset;
int errorcode;
re = pcre2_compile(
"^A.*Z", /* le motif */
PCRE2_ZERO_TERMINATED, /* le motif est terminé par zéro */
0, /* options par défaut */
&errorcode, /* pour le code d'erreur */
&erroffset, /* pour le décalage d'erreur */
NULL); /* pas de contexte de compilation */

Options principales de compilation

Les noms suivants pour les bits d'option sont définis dans le fichier d'en-tête pcre2.h :


PCRE2_ANCHORED

Si ce bit est défini, le motif est forcé d'être "ancré", c'est-à-dire qu'il est contraint de ne correspondre qu'au premier point de correspondance dans la chaîne qui est recherchée (la "chaîne sujet"). Cet effet peut également être obtenu par des constructions appropriées dans le motif lui-même, ce qui est la seule façon de le faire en Perl.


PCRE2_ALLOW_EMPTY_CLASS

Par défaut, pour la compatibilité avec Perl, une parenthèse carrée fermante qui suit immédiatement une parenthèse carrée ouvrante est traitée comme un caractère de données pour la classe. Lorsque PCRE2_ALLOW_EMPTY_CLASS est défini, il termine la classe, qui ne contient donc aucun caractère et ne peut par conséquent jamais correspondre.


PCRE2_ALT_BSUX

Cette option demande une gestion alternative de trois séquences d'échappement, ce qui rend le comportement de PCRE2 plus proche de celui d'ECMAScript (alias JavaScript). Lorsqu'elle est définie :

(1) \U correspond à un caractère "U" majuscule ; par défaut, \U provoque une erreur de compilation (Perl utilise \U pour mettre en majuscules les caractères suivants).

(2) \u correspond à un caractère "u" minuscule sauf s'il est suivi de quatre chiffres hexadécimaux, auquel cas le nombre hexadécimal définit le point de code à faire correspondre. Par défaut, \u provoque une erreur de compilation (Perl l'utilise pour mettre en majuscules le caractère suivant).

(3) \x correspond à un caractère "x" minuscule sauf s'il est suivi de deux chiffres hexadécimaux, auquel cas le nombre hexadécimal définit le point de code à faire correspondre. Par défaut, comme en Perl, un nombre hexadécimal est toujours attendu après \x, mais il peut avoir un ou deux chiffres.

ECMAScript 6 a ajouté des fonctionnalités supplémentaires à \u. Celles-ci peuvent être accessibles en utilisant l'option supplémentaire PCRE2_EXTRA_ALT_BSUX (voir "Options de compilation supplémentaires" ci-dessous). Notez que cette gestion alternative des échappements ne s'applique qu'aux motifs. Aucune de ces options n'affecte le traitement des chaînes de remplacement passées à pcre2_substitute().


PCRE2_ALT_CIRCUMFLEX

En mode multiligne (lorsque PCRE2_MULTILINE est défini), le métacaractère circonflexe correspond au début du sujet (sauf si PCRE2_NOTBOL est défini), et également après toute nouvelle ligne interne. Cependant, il ne correspond pas après une nouvelle ligne à la fin du sujet, pour la compatibilité avec Perl. Si vous voulez qu'un circonflexe multiligne corresponde également après une nouvelle ligne de fin, vous devez définir PCRE2_ALT_CIRCUMFLEX.


PCRE2_ALT_EXTENDED_CLASS

Modifie l'analyse des classes de caractères pour suivre la syntaxe étendue décrite par Unicode UTS#18. L'option PCRE2_ALT_EXTENDED_CLASS n'a aucun impact sur le comportement de la syntaxe Perl spécifique "(?[...])" pour les classes étendues, mais active plutôt la syntaxe alternative du comportement des classes étendues à l'intérieur des classes de caractères ordinaires "[...]". Voir la documentation de pcre2pattern pour les détails des classes de caractères prises en charge.


PCRE2_ALT_VERBNAMES

Par défaut, pour la compatibilité avec Perl, le nom dans toute séquence de verbe telle que (*MARK:NOM) est toute séquence de caractères qui ne contient pas de parenthèse fermante. Le nom n'est traité d'aucune manière, et il n'est pas possible d'inclure une parenthèse fermante dans le nom. Cependant, si l'option PCRE2_ALT_VERBNAMES est définie, le traitement normal des antislashs est appliqué aux noms de verbes et seule une parenthèse fermante non échappée termine le nom. Une parenthèse fermante peut être incluse dans un nom soit comme \) soit entre \Q et \E. Si l'option PCRE2_EXTENDED ou PCRE2_EXTENDED_MORE est définie avec PCRE2_ALT_VERBNAMES, les espaces blancs non échappés dans les noms de verbes sont ignorés et les commentaires # sont reconnus, exactement comme dans le reste du motif.


PCRE2_AUTO_CALLOUT

Si ce bit est défini, pcre2_compile() insère automatiquement des éléments d'appel (callout), tous avec le numéro 255, avant chaque élément du motif, sauf immédiatement avant ou après un appel explicite dans le motif. Pour une discussion sur la facilité d'appel, voir la documentation de pcre2callout.


PCRE2_CASELESS

Si ce bit est défini, les lettres du motif correspondent aux lettres majuscules et minuscules du sujet. C'est l'équivalent de l'option /i de Perl, et cela peut être modifié dans un motif par un réglage d'option (?i). Si PCRE2_UTF ou PCRE2_UCP est défini, les propriétés Unicode sont utilisées pour tous les caractères ayant plus d'une autre casse, et pour tous les caractères dont les points de code sont supérieurs à U+007F.

Notez qu'il existe deux caractères ASCII, K et S, qui, en plus de leurs équivalents ASCII minuscules, sont équivalents en casse avec U+212A (signe Kelvin) et U+017F (s long) respectivement. Si vous ne souhaitez pas cette équivalence de casse, vous pouvez la supprimer en définissant PCRE2_EXTRA_CASELESS_RESTRICT.

Une famille de langues, le turc et l'azéri, a ses propres règles d'insensibilité à la casse, qui peuvent être sélectionnées en définissant PCRE2_EXTRA_TURKISH_CASING. Cela modifie le comportement des caractères 'i', 'I', U+0130 (I majuscule avec point au-dessus), et U+0131 (i minuscule sans point).

Pour les caractères de valeur inférieure avec une seule autre casse, une table de correspondance est utilisée pour la vitesse. Lorsque ni PCRE2_UTF ni PCRE2_UCP n'est défini, une table de correspondance est utilisée pour tous les points de code inférieurs à 256, et les points de code plus élevés (disponibles uniquement en mode 16 bits ou 32 bits) sont traités comme n'ayant pas d'autre casse.

Depuis la version 10.45, PCRE2_CASELESS affecte également ce à quoi correspondent certaines échappements de propriétés Unicode liées aux lettres (\p et \P). Les propriétés Lu (lettre majuscule), Ll (lettre minuscule) et Lt (lettre en casse de titre) sont toutes traitées comme LC (lettre avec casse) lorsque PCRE2_CASELESS est défini.


PCRE2_DOLLAR_ENDONLY

Si ce bit est défini, un métacaractère dollar dans le motif ne correspond qu'à la fin de la chaîne sujet. Sans cette option, un dollar correspond également immédiatement avant une nouvelle ligne à la fin de la chaîne (mais pas avant toute autre nouvelle ligne). L'option PCRE2_DOLLAR_ENDONLY est ignorée si PCRE2_MULTILINE est défini. Il n'y a pas d'équivalent à cette option en Perl, et aucun moyen de la définir dans un motif.


PCRE2_DOTALL

Si ce bit est défini, un métacaractère point dans le motif correspond à n'importe quel caractère, y compris un caractère indiquant

\n est un saut de ligne. Cependant, il ne correspond jamais qu'à un seul caractère, même si les sauts de ligne sont codés en CRLF. Sans cette option, un point ne correspond pas lorsque la position actuelle dans le sujet est sur un saut de ligne. Cette option est équivalente à l'option /s de Perl, et elle peut être modifiée dans un motif par un réglage d'option (?s). Une classe négative telle que [^a] correspond toujours aux caractères de saut de ligne, et la séquence d'échappement \N correspond toujours à un caractère autre qu'un saut de ligne, indépendamment du réglage de PCRE2_DOTALL.


PCRE2_DUPNAMES

Si ce bit est défini, les noms utilisés pour identifier les groupes de capture n'ont pas besoin d'être uniques. Cela peut être utile pour certains types de motifs lorsqu'il est connu qu'une seule instance du groupe nommé peut jamais être mise en correspondance. Il y a plus de détails sur les groupes de capture nommés ci-dessous ; voir également la documentation pcre2pattern.


PCRE2_ENDANCHORED

Si ce bit est défini, la fin de toute correspondance de motif doit se trouver exactement à la fin de la chaîne recherchée (la "chaîne sujet"). Si la correspondance du motif réussit en atteignant (*ACCEPT), mais n'atteint pas la fin du sujet, la correspondance échoue au point de départ actuel. Pour les motifs non ancrés, une nouvelle correspondance est ensuite tentée au point de départ suivant. Cependant, si la correspondance réussit en atteignant la fin du motif, mais pas la fin du sujet, un retour arrière se produit et une correspondance alternative peut être trouvée. Considérons ces deux motifs :


.(*ACCEPT)|..
.|..

S'ils sont mis en correspondance avec "abc" avec PCRE2_ENDANCHORED défini, le premier fait correspondre "c" tandis que le second fait correspondre "bc". L'effet de PCRE2_ENDANCHORED peut également être obtenu par des constructions appropriées dans le motif lui-même, ce qui est la seule façon de le faire en Perl.

Pour la correspondance DFA avec pcre2_dfa_match(), PCRE2_ENDANCHORED ne s'applique qu'à la première (c'est-à-dire la plus longue) chaîne mise en correspondance. D'autres correspondances parallèles, qui sont nécessairement des sous-chaînes de la première, doivent évidemment se terminer avant la fin du sujet.


PCRE2_EXTENDED

Si ce bit est défini, la plupart des caractères d'espacement dans le motif sont totalement ignorés, sauf lorsqu'ils sont échappés, à l'intérieur d'une classe de caractères, ou à l'intérieur d'une séquence \Q...\E. Cependant, l'espacement n'est pas autorisé dans des séquences telles que (?> qui introduisent divers groupes entre parenthèses, ni dans des quantificateurs numériques tels que {1,3}. L'espacement ignoré est autorisé entre un élément et un quantificateur suivant, et entre un quantificateur et un + suivant qui indique la possessivité. PCRE2_EXTENDED est équivalent à l'option /x de Perl, et il peut être modifié dans un motif par un réglage d'option (?x).

Lorsque PCRE2 est compilé sans prise en charge Unicode, PCRE2_EXTENDED ne reconnaît comme espace que les caractères dont le point de code est inférieur à 256 et qui sont marqués comme espace dans sa table de caractères bas. La table est normalement créée par pcre2_maketables(), qui utilise la fonction isspace() pour identifier les caractères d'espacement. Dans la plupart des environnements ASCII, les caractères pertinents sont ceux dont le point de code est 0x0009 (tabulation), 0x000A (saut de ligne), 0x000B (tabulation verticale), 0x000C (saut de page), 0x000D (retour chariot) et 0x0020 (espace).

Lorsque PCRE2 est compilé avec la prise en charge Unicode, en plus de ces caractères, cinq autres caractères "Espace de motif" Unicode sont reconnus par PCRE2_EXTENDED. Il s'agit de U+0085 (nouvelle ligne), U+200E (marque gauche à droite), U+200F (marque droite à gauche), U+2028 (séparateur de ligne) et U+2029 (séparateur de paragraphe). Cet ensemble de caractères est le même que celui reconnu par l'option /x de Perl. Notez que les caractères d'espacement horizontal et vertical qui sont mis en correspondance par les échappements \h et \v dans les motifs constituent un ensemble beaucoup plus vaste.

En plus d'ignorer la plupart des espaces, PCRE2_EXTENDED fait également ignorer les caractères situés entre un # non échappé à l'extérieur d'une classe de caractères et le prochain saut de ligne, inclus, ce qui permet d'inclure des commentaires dans des motifs complexes. Notez que la fin de ce type de commentaire est une séquence de saut de ligne littérale dans le motif ; les séquences d'échappement qui représentent accidentellement un saut de ligne ne comptent pas.

Les caractères interprétés comme des sauts de ligne peuvent être spécifiés par un réglage dans le contexte de compilation passé à pcre2_compile() ou par une séquence spéciale au début du motif, comme décrit dans la section intitulée "Conventions de saut de ligne" de la documentation pcre2pattern. Une valeur par défaut est définie lors de la construction de PCRE2.


PCRE2_EXTENDED_MORE

Cette option a l'effet de PCRE2_EXTENDED, mais, en plus, les caractères d'espace et de tabulation horizontale non échappés sont ignorés à l'intérieur d'une classe de caractères. Remarque : seuls ces deux caractères sont ignorés, pas l'ensemble complet des caractères d'espacement de motif qui sont ignorés à l'extérieur d'une classe de caractères. PCRE2_EXTENDED_MORE est équivalent à l'option /xx de Perl, et il peut être modifié dans un motif par un réglage d'option (?xx).


PCRE2_FIRSTLINE

Si cette option est définie, le début d'une correspondance de motif non ancrée doit se situer avant ou sur le premier saut de ligne dans la chaîne sujet suivant le début de la mise en correspondance, bien que le texte mis en correspondance puisse se poursuivre après le saut de ligne. Si startoffset est non nul, le saut de ligne limitant n'est pas nécessairement le premier saut de ligne dans le sujet. Par exemple, si la chaîne sujet est "abc\nxyz" (où \n représente un seul caractère de saut de ligne), une correspondance de motif pour "yz" réussit avec PCRE2_FIRSTLINE si startoffset est supérieur à 3. Voir également PCRE2_USE_OFFSET_LIMIT, qui fournit une facilité de limitation plus générale. Si PCRE2_FIRSTLINE est défini avec une limite de décalage, une correspondance doit se produire sur la première ligne et également dans la limite de décalage. En d'autres termes, quelle que soit la limite qui vient en premier est utilisée. Cette option n'a aucun effet pour les motifs ancrés.


PCRE2_LITERAL

Si cette option est définie, tous les méta-caractères du motif sont désactivés et il est traité comme une chaîne littérale. La mise en correspondance de chaînes littérales avec un moteur d'expressions régulières n'est pas la manière la plus efficace de le faire. Si vous effectuez beaucoup de correspondances littérales et que vous vous souciez de l'efficacité, vous devriez envisager d'autres approches. Les seules autres options principales autorisées avec PCRE2_LITERAL sont : PCRE2_ANCHORED, PCRE2_ENDANCHORED, PCRE2_AUTO_CALLOUT, PCRE2_CASELESS, PCRE2_FIRSTLINE, PCRE2_MATCH_INVALID_UTF, PCRE2_NO_START_OPTIMIZE, PCRE2_NO_UTF_CHECK, PCRE2_UTF et PCRE2_USE_OFFSET_LIMIT. Les options supplémentaires PCRE2_EXTRA_MATCH_LINE et PCRE2_EXTRA_MATCH_WORD sont également prises en charge. Toute autre option provoque une erreur.


PCRE2_MATCH_INVALID_UTF

Cette option force PCRE2_UTF (voir ci-dessous) et active également la prise en charge de la correspondance par pcre2_match() dans des chaînes sujet contenant des séquences UTF invalides. Notez cependant que les bibliothèques PCRE2 16 bits et 32 bits traitent les chaînes comme des séquences de points de code uint16_t ou uint32_t. Elles ne peuvent pas trouver de séquences UTF valides dans une chaîne d'octets arbitraire à moins que de telles séquences ne soient correctement alignées. Cette fonctionnalité n'est pas prise en charge pour la correspondance DFA. Pour plus de détails, voir la documentation pcre2unicode.


PCRE2_MATCH_UNSET_BACKREF

Si cette option est définie, une référence arrière à un groupe de capture non défini correspond à une chaîne vide (par défaut, cela provoque l'échec de l'alternative de correspondance actuelle). Un motif tel que (\1)(a) réussit lorsque cette option est définie (en supposant qu'il puisse trouver un "a" dans le sujet), tandis qu'il échoue par défaut, pour la compatibilité avec Perl. La définition de cette option rend PCRE2 plus similaire à ECMAscript (alias JavaScript).


PCRE2_MULTILINE

Par défaut, aux fins de correspondance du "début de ligne" et de la "fin de ligne", PCRE2 traite la chaîne sujet comme consistant en une seule ligne de caractères, même si elle contient réellement des sauts de ligne. Le métacaractère "début de ligne" (^) ne correspond qu'au début de la chaîne, et le métacaractère "fin de ligne" ($) ne correspond qu'à la fin de la chaîne, ou avant un saut de ligne terminal (sauf lorsque PCRE2_DOLLAR_ENDONLY est défini). Notez cependant que, sauf si PCRE2_DOTALL est défini, le métacaractère "n'importe quel caractère" (.) ne correspond pas à un saut de ligne. Ce comportement (pour ^, $, et le point) est le même qu'en Perl.

Lorsque PCRE2_MULTILINE est défini, les constructions "début de ligne" et "fin de ligne" correspondent immédiatement après ou immédiatement avant les sauts de ligne internes dans la chaîne sujet, respectivement, ainsi qu'au début et à la fin mêmes. Ceci est équivalent à l'option /m de Perl, et il peut être modifié dans un motif par un réglage d'option (?m). Notez que le métacaractère "début de ligne" ne correspond pas après un saut de ligne à la fin du sujet, pour la compatibilité avec Perl. Cependant, vous pouvez changer cela en définissant l'option PCRE2_ALT_CIRCUMFLEX. S'il n'y a pas de sauts de ligne dans une chaîne sujet, ou pas d'occurrences de ^ ou $ dans un motif, la définition de PCRE2_MULTILINE n'a aucun effet.


PCRE2_NEVER_BACKSLASH_C

Cette option bloque l'utilisation de \C dans le motif qui est en cours de compilation. Cet échappement peut entraîner un comportement imprévisible en modes UTF-8 ou UTF-16, car il peut laisser le point de correspondance actuel au milieu d'un caractère multi-unités. Cette option peut être utile dans les applications qui traitent des motifs provenant de sources externes. Notez qu'il existe également une option au moment de la compilation qui bloque de manière permanente l'utilisation de \C.


PCRE2_NEVER_UCP

Cette option bloque l'utilisation des propriétés Unicode pour gérer \B, \b, \D, \d, \S, \s, \W, \w, et certaines classes de caractères POSIX, comme décrit pour l'option PCRE2_UCP ci-dessous. En particulier, elle empêche le créateur du motif d'activer cette fonctionnalité en commençant le motif par (*UCP). Cette option peut être utile dans les applications qui traitent des motifs provenant de sources externes. La combinaison d'options PCRE2_UCP et PCRE2_NEVER_UCP provoque une erreur.


PCRE2_NEVER_UTF

Cette option bloque l'interprétation du motif comme UTF-8, UTF-16 ou UTF-32, selon la bibliothèque utilisée. En particulier, elle empêche le créateur du motif de passer à l'interprétation UTF en commençant le motif par (*UTF). Cette option peut être utile dans les applications qui traitent des motifs provenant de sources externes. La combinaison de PCRE2_UTF et PCRE2_NEVER_UTF provoque une erreur.


PCRE2_NO_AUTO_CAPTURE

Si cette option est définie, elle désactive l'utilisation des parenthèses de capture numérotées dans le motif. Toute parenthèse ouvrante qui n'est pas suivie de ? se comporte comme si elle était suivie de ?: mais les parenthèses nommées peuvent toujours être utilisées pour la capture (et elles acquièrent des numéros de la manière habituelle). Ceci est identique à l'option /n de Perl. Notez que, lorsque cette option est définie, les références aux groupes de capture (références arrière ou appels de récursion/sous-routine) ne peuvent faire référence qu'à des groupes nommés, bien que la référence puisse être par nom ou par numéro.


PCRE2_NO_AUTO_POSSESS

Si cette option (obsolète) est définie, elle désactive "l'auto-possessification", qui est une optimisation qui, par exemple, transforme a+b en a++b afin d'éviter les retours arrière dans

Options de compilation

Les options suivantes peuvent être passées à la fonction pcre2_compile() pour modifier son comportement. Elles peuvent aussi être définies dans un contexte de compilation à l'aide de pcre2_set_option().


PCRE2_AUTO_CALLOUT

Si cette option est activée, un point d'appel est inséré avant chaque élément du schéma qui est susceptible d'être sauté. Voir la section sur les points d'appel pour plus de détails. Le principal inconvénient de cette option est qu'elle peut rendre certains schémas incapables d'être réussis. Cependant, si des points d'appel sont utilisés, l'auto-possession implique que certains points d'appel ne sont jamais atteints. Vous pouvez définir cette option si vous souhaitez que les fonctions de mise en correspondance effectuent une recherche complète non optimisée et exécutent tous les points d'appel, mais elle est principalement fournie à des fins de test.

Si un contexte de compilation est disponible, il est recommandé d'utiliser pcre2_set_optimize() avec la directive PCRE2_AUTO_POSSESS_OFF plutôt que l'option de compilation PCRE2_NO_AUTO_POSSESS. Notez que PCRE2_NO_AUTO_POSSESS a la priorité sur les directives d'optimisation PCRE2_AUTO_POSSESS et PCRE2_AUTO_POSSESS_OFF de pcre2_set_optimize().


PCRE2_NO_DOTSTAR_ANCHOR

Si cette option (obsolète) est définie, elle désactive une optimisation qui est appliquée lorsqu'un `.*` est le premier élément significatif dans une branche de niveau supérieur d'un schéma, et que toutes les autres branches commencent également par `.*` ou par `\A` ou `\G` ou `^`. L'optimisation est automatiquement désactivée pour `.*` s'il se trouve à l'intérieur d'un groupe atomique ou d'un groupe capturant qui fait l'objet d'une référence arrière, ou si le schéma contient `(*PRUNE)` ou `(*SKIP)`. Lorsque l'optimisation n'est pas désactivée, un tel schéma est automatiquement ancré si PCRE2_DOTALL est défini pour tous les éléments `.*` et si PCRE2_MULTILINE n'est pas défini pour les éléments `^`. Sinon, le fait que toute correspondance doive commencer soit au début du sujet, soit après une nouvelle ligne est mémorisé. Comme les autres optimisations, cela peut entraîner le saut de certains points d'appel. (Si un contexte de compilation est disponible, il est recommandé d'utiliser pcre2_set_optimize() avec la directive PCRE2_DOTSTAR_ANCHOR_OFF à la place.)


PCRE2_NO_START_OPTIMIZE

Il s'agit d'une option dont l'effet principal se situe au moment de la mise en correspondance. Elle ne modifie pas ce que génère pcre2_compile(), mais elle affecte la sortie du compilateur JIT. La définition de cette option est équivalente à l'appel de pcre2_set_optimize() avec le paramètre directive défini sur PCRE2_START_OPTIMIZE_OFF.

Il existe un certain nombre d'optimisations qui peuvent survenir au début d'une mise en correspondance, afin d'accélérer le processus. Par exemple, s'il est connu qu'une mise en correspondance non ancrée doit commencer par une valeur d'unité de code spécifique, le code de mise en correspondance recherche cette valeur dans le sujet et échoue immédiatement si elle ne peut pas la trouver, sans exécuter la fonction de mise en correspondance principale. Les optimisations de démarrage sont essentiellement une pré-analyse du sujet qui a lieu avant l'exécution du schéma.

La désactivation des optimisations de démarrage peut nuire aux performances. Cependant, cela peut être souhaitable pour les schémas qui contiennent des points d'appel ou des éléments tels que `(*COMMIT)` et `(*MARK)`. Voir la description ci-dessus de PCRE2_START_OPTIMIZE_OFF pour plus de détails.


PCRE2_NO_UTF_CHECK

Lorsque PCRE2_UTF est défini, la validité du schéma en tant que chaîne UTF est automatiquement vérifiée. Il existe des discussions sur la validité des chaînes UTF-8, UTF-16 et UTF-32 dans le document pcre2unicode. Si une séquence UTF invalide est trouvée, pcre2_compile() renvoie un code d'erreur négatif.

Si vous savez que votre schéma est une chaîne UTF valide et que vous souhaitez ignorer cette vérification pour des raisons de performance, vous pouvez définir l'option PCRE2_NO_UTF_CHECK. Lorsqu'elle est définie, l'effet de passer une chaîne UTF invalide comme schéma est indéfini. Cela peut entraîner le crash ou une boucle de votre programme.

Notez que cette option peut également être passée à pcre2_match() et pcre2_dfa_match(), pour supprimer la vérification de validité UTF de la chaîne sujet.

Notez également que la définition de PCRE2_NO_UTF_CHECK au moment de la compilation ne désactive pas l'erreur qui est donnée si une séquence d'échappement pour un point de code Unicode invalide est rencontrée dans le schéma. En particulier, les points de code dits "de substitution" (0xd800 à 0xdfff) sont invalides. Si vous souhaitez autoriser des séquences d'échappement telles que `\x{d800}`, vous pouvez définir l'option supplémentaire PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES, comme décrit dans la section intitulée "Options de compilation supplémentaires" ci-dessous. Cependant, cela n'est possible qu'en modes UTF-8 et UTF-32, car ces valeurs ne sont pas représentables en UTF-16.


PCRE2_UCP

Cette option a deux effets. Premièrement, elle modifie la façon dont PCRE2 traite `\B`, `\b`, `\D`, `\d`, `\S`, `\s`, `\W`, `\w`, et certaines des classes de caractères POSIX. Par défaut, seuls les caractères ASCII sont reconnus, mais si PCRE2_UCP est défini, les propriétés Unicode sont utilisées pour classifier les caractères. Il existe certaines options PCRE2_EXTRA (voir ci-dessous) qui ajoutent un contrôle plus fin à ce comportement. Plus de détails sont donnés dans la section sur les types de caractères génériques de la page pcre2pattern.

Le second effet de PCRE2_UCP est de forcer l'utilisation des propriétés Unicode pour les opérations de mise en majuscules/minuscules, même lorsque PCRE2_UTF n'est pas défini. Cela permet de traiter des chaînes dans le code UCS-2 à 16 bits. Cette option n'est disponible que si PCRE2 a été compilé avec le support Unicode (ce qui est le défaut).

L'option PCRE2_EXTRA_CASELESS_RESTRICT (voir ci-dessus) restreint la mise en correspondance insensible à la casse de telle sorte que les caractères ASCII ne correspondent qu'à des caractères ASCII et les caractères non-ASCII ne correspondent qu'à des caractères non-ASCII. L'option PCRE2_EXTRA_TURKISH_CASING (voir ci-dessus) modifie la mise en correspondance des caractères 'i' pour suivre leur comportement dans les langues turque et azérie. Pour plus de détails sur PCRE2_EXTRA_CASELESS_RESTRICT et PCRE2_EXTRA_TURKISH_CASING, voir la page pcre2unicode.


PCRE2_UNGREEDY

Cette option inverse la "gourmandise" des quantificateurs de telle sorte qu'ils ne soient pas gourmands par défaut, mais qu'ils le deviennent s'ils sont suivis de "?". Elle n'est pas compatible avec Perl. Elle peut également être définie par un réglage d'option (?U) dans le schéma.


PCRE2_USE_OFFSET_LIMIT

Cette option doit être définie pour pcre2_compile() si pcre2_set_offset_limit() va être utilisé pour définir une limite de décalage non par défaut dans un contexte de mise en correspondance pour les mises en correspondance qui utilisent ce schéma. Une erreur est générée si une limite de décalage est définie sans cette option. Pour plus de détails, voir la description de pcre2_set_offset_limit() dans la section qui décrit les contextes de mise en correspondance. Voir également l'option PCRE2_FIRSTLINE ci-dessus.


PCRE2_UTF

Cette option amène PCRE2 à considérer à la fois le schéma et les chaînes sujet qui sont traitées par la suite comme des chaînes de caractères UTF au lieu de chaînes d'une seule unité de code. Elle est disponible lorsque PCRE2 est construit pour inclure le support Unicode (ce qui est le défaut). Si le support Unicode n'est pas disponible, l'utilisation de cette option provoque une erreur. Les détails sur la façon dont PCRE2_UTF modifie le comportement de PCRE2 sont donnés dans la page pcre2unicode. En particulier, notez qu'elle modifie la façon dont PCRE2_CASELESS fonctionne.

Options de compilation supplémentaires

Les bits d'option qui peuvent être définis dans un contexte de compilation en appelant la fonction pcre2_set_compile_extra_options() sont les suivants :


PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK

Depuis la version 10.38, PCRE2 interdit l'utilisation de `\K` dans les assertions lookaround, suivant l'exemple de Perl. Cette option est fournie pour réactiver le comportement précédent (agit dans les lookarounds positifs, ignoré dans les négatifs) au cas où quelqu'un s'y fierait.


PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES

Cette option s'applique lors de la compilation d'un schéma en mode UTF-8 ou UTF-32. Elle est interdite en mode UTF-16 et ignorée en mode non-UTF. Les points de code Unicode "de substitution" dans la plage 0xd800 à 0xdfff sont utilisés par paires en UTF-16 pour coder des points de code dont les valeurs sont dans la plage 0x10000 à 0x10ffff. Les substituts ne peuvent donc pas être représentés en UTF-16. Ils peuvent être représentés en UTF-8 et UTF-32, mais sont définis comme des points de code invalides, et provoquent des erreurs s'ils sont rencontrés dans une chaîne UTF-8 ou UTF-32 dont la validité est vérifiée par PCRE2.

Ces valeurs provoquent également des erreurs si elles sont rencontrées dans des séquences d'échappement telles que `\x{d912}` dans un schéma. Cependant, il semble que certaines applications, lorsqu'elles utilisent PCRE2 pour vérifier la présence de caractères indésirables dans des chaînes UTF-8, testent explicitement les substituts à l'aide de séquences d'échappement. L'option PCRE2_NO_UTF_CHECK ne désactive pas l'erreur qui se produit, car elle s'applique uniquement à la vérification de la validité UTF des chaînes d'entrée.

Si l'option supplémentaire PCRE2_EXTRA_ALLOW_SURROGATE_ESCAPES est définie, les valeurs des points de code de substitution dans les schémas UTF-8 et UTF-32 ne provoquent plus d'erreurs et sont incorporées dans le schéma compilé. Cependant, elles ne peuvent correspondre à des caractères sujet que si la fonction de mise en correspondance est appelée avec PCRE2_NO_UTF_CHECK défini.


PCRE2_EXTRA_ALT_BSUX

L'option originale PCRE2_ALT_BSUX amène PCRE2 à traiter `\U`, `\u`, et `\x` de la manière dont le fait ECMAscript (alias JavaScript). Une fonctionnalité supplémentaire a été définie par ECMAscript 6 ; la définition de PCRE2_EXTRA_ALT_BSUX a l'effet de PCRE2_ALT_BSUX, mais en plus elle reconnaît `\u{hhh..}` comme un code de caractère hexadécimal, où hhh.. est n'importe quel nombre de chiffres hexadécimaux.


PCRE2_EXTRA_ASCII_BSD

Cette option force `\d` à ne correspondre qu'aux chiffres ASCII, même lorsque PCRE2_UCP est défini. Elle peut être modifiée dans un schéma au moyen du réglage d'option (?aD).


PCRE2_EXTRA_ASCII_BSS

Cette option force `\s` à ne correspondre qu'aux caractères d'espacement ASCII, même lorsque PCRE2_UCP est défini. Elle peut être modifiée dans un schéma au moyen du réglage d'option (?aS).


PCRE2_EXTRA_ASCII_BSW

Cette option force `\w` à ne correspondre qu'aux caractères de mot ASCII, même lorsque PCRE2_UCP est défini. Elle peut être modifiée dans un schéma au moyen du réglage d'option (?aW).


PCRE2_EXTRA_ASCII_DIGIT

Cette option force les classes de caractères POSIX [:digit:] et [:xdigit:] à ne correspondre qu'aux chiffres ASCII, même lorsque PCRE2_UCP est défini. Elle peut être modifiée dans un schéma au moyen du réglage d'option (?aT).


PCRE2_EXTRA_ASCII_POSIX

Cette option force toutes les classes de caractères POSIX, y compris [:digit:] et [:xdigit:], à ne correspondre qu'aux caractères ASCII, même lorsque PCRE2_UCP est défini. Elle peut être modifiée dans un schéma au moyen du réglage d'option (?aP), mais notez que cela définit également PCRE2_EXTRA_ASCII_DIGIT afin de garantir que (?-aP) annule toutes les restrictions ASCII pour les classes POSIX.


PCRE2_EXTRA_BAD_ESCAPE_IS_LITERAL

Ceci est une option dangereuse. À utiliser avec prudence. Par défaut, un échappement non reconnu tel que `\j` ou un échappement mal formé tel que `\x{2z}` provoque une erreur de compilation lorsqu'il est détecté par pcre2_compile(). Perl est quelque peu incohérent dans le traitement de ces éléments : par exemple, `\j` est traité comme un littéral "j", et les chiffres non hexadécimaux dans `\x{}` sont simplement ignorés, bien que des avertissements soient donnés dans les deux cas si le commutateur d'avertissement de Perl est activé. Cependant, un nombre octal mal formé après `\o{` provoque toujours une erreur dans Perl.

Si l'option supplémentaire PCRE2_EXTRA_BAD_ESCAPE_IS_LITERAL est passée à pcre2_compile(), toutes les séquences d'échappement non reconnues ou mal formées sont traitées comme des littéraux à une seule caractère.

OPTIONS SUPPLÉMENTAIRES

Il existe une gamme d'options supplémentaires qui peuvent être spécifiées à l'aide de la fonction pcre2_set_extra_options(). Ces options ne sont pas utilisées avec la fonction pcre2_compile(), mais plutôt avec pcre2_match() et ses variantes.

L'ensemble complet des options supplémentaires disponibles est défini dans le fichier d'en-tête PCRE2, sous la forme de drapeaux commençant par PCRE2_EXTRA_.

Voici les options disponibles :


PCRE2_EXTRA_ALLOW_LOOKAROUND_GREEDY

Si cette option est définie, les quantificateurs avides peuvent être utilisés avec des assertions de longueur zéro, telles que les aperçus avant ou arrière, et les assertions de début ou de fin de ligne. Normalement, un quantificateur avide ne peut pas être appliqué à une assertion de longueur zéro.


PCRE2_EXTRA_ALLOW_UNESCAPED_CR

Si cette option est définie, un caractère CR littéral non échappé dans le motif correspond à un caractère CR (retour chariot). Normalement, il correspond à un caractère LF (saut de ligne) si l'option PCRE2_LF est définie, ou échoue si le motif est compilé à l'aide de PCRE2_LITERAL.


PCRE2_EXTRA_ALT_VERBNAME

Cette option active la reconnaissance des noms de verbes alternatifs pour les options de motif, comme (*VERB:options) au lieu de seulement (*VERB). Par exemple, (*NO_UTF8:F) est maintenant reconnu. Cette option est principalement destinée à la compatibilité avec d'anciennes versions de PCRE, mais peut également être utilisée pour la clarté.


PCRE2_EXTRA_DONT_INTERRUPT

L'exécution de motifs complexes peut parfois prendre beaucoup de temps, même avec des chaînes d'entrée courtes. Dans de tels cas, le noyau PCRE2 peut être configuré pour répondre aux signaux du système d'exploitation (par exemple, SIGINT) pendant l'exécution du motif, ce qui permet au processus de se terminer prématurément. Cette option désactive cette possibilité. Cela peut être utile dans les environnements où la gestion des signaux est problématique ou lorsque l'on souhaite garantir que la recherche se termine même si elle prend beaucoup de temps.


PCRE2_EXTRA_ESCAPED_NL_IS_CR

Il existe certaines applications héritées où la séquence d'échappement \n dans un motif est censée correspondre à un retour chariot. Si cette option est définie, \n dans un motif est converti en \r afin qu'il corresponde à un caractère CR (retour chariot) au lieu d'un caractère LF (saut de ligne). L'option n'affecte pas un LF littéral dans le motif, ni un LF spécifié comme point de code explicite tel que \x{0A}.


PCRE2_EXTRA_ESCAPED_WHITESPACE_IS_UNICODE_WHITESPACE

Si cette option est définie, les séquences d'échappement d'espace blanc telles que \s correspondent à tous les caractères Unicode considérés comme des espaces blancs. Par défaut, \s ne correspond qu'aux espaces ASCII, aux tabulations, aux nouvelles lignes, etc.


PCRE2_EXTRA_MATCH_DIGIT_AS_NON

Si cette option est définie, le caractère \d correspond à des caractères non numériques ainsi qu'à des chiffres. Cela peut être utile dans certains cas où un motif doit correspondre à une plus grande variété de caractères.


PCRE2_EXTRA_NO_UTF8_INVALID_ACTION

Si cette option est définie, le comportement par défaut lors de la rencontre de séquences UTF-8 invalides est modifié. Au lieu de provoquer une erreur, PCRE2 traitera la séquence invalide comme une chaîne littérale, correspondant ainsi aux caractères tels quels. Cela peut être utile pour gérer des données potentiellement corrompues ou mal formées.


PCRE2_EXTRA_OLD_BACKSLASH_INTERPRETATION

Si cette option est définie, PCRE2 utilise une ancienne interprétation des séquences d'échappement d'antislash. Cela signifie que certaines séquences, qui sont maintenant considérées comme des caractères spéciaux, peuvent être traitées comme des caractères littéraux. Par exemple, `\l` et `\u` peuvent être interprétés comme des caractères littéraux `l` et `u` au lieu d'affecter la casse du caractère suivant. L'utilisation de cette option est déconseillée car elle peut entraîner un comportement inattendu.


PCRE2_EXTRA_REVERT_GROUP_ANCHORS

Si cette option est définie, les ancres de début (^ et $) à l'intérieur des groupes de capture sont inversées. Normalement, ^ correspond au début de la chaîne ou après un saut de ligne (si PCRE2_MULTILINE est défini), et $ correspond à la fin de la chaîne ou avant un saut de ligne. Avec cette option, ^ correspondra à la fin d'une ligne et $ au début d'une ligne. Cela peut être utile pour des motifs de correspondance spécifiques dans des contextes multilingues.


PCRE2_EXTRA_STRICT_ESCAPES

Si cette option est définie, PCRE2 interprète strictement toutes les séquences d'échappement d'antislash. Cela signifie que toute séquence d'échappement non reconnue sera traitée comme une erreur de syntaxe. Par exemple, `\j` sera une erreur, car `j` n'est pas une séquence d'échappement valide. De même, `\x{2z}` sera traité comme la chaîne littérale `"x{2z}"`. L'activation de cette option peut entraîner une détection plus précoce des erreurs de frappe dans les motifs, mais elle peut également rendre les motifs plus difficiles à écrire, car même les séquences apparemment inoffensives peuvent être rejetées.

Il est important de noter que l'option PCRE2_LITERAL, lorsqu'elle est utilisée avec PCRE2_EXTRA_STRICT_ESCAPES, se comporte différemment. Dans ce cas, PCRE2_EXTRA_STRICT_ESCAPES désactive l'interprétation des caractères d'échappement tels que `\n` et `\t`. Par exemple, `\n` sera traité comme un caractère littéral 'n' au lieu d'une nouvelle ligne. De même, `\x{2z}` est traité comme la chaîne littérale `"x{2z}"`. L'activation de cette option signifie que les erreurs de frappe dans les motifs peuvent passer inaperçues et avoir des résultats inattendus. Notez également qu'une séquence telle que `[\N{]` est interprétée comme une tentative mal formée de `[\N{...}]` et est donc traitée comme `[N{]`, tandis que `[\N]` provoque une erreur car un `\N` non qualifié est une séquence d'échappement valide mais non prise en charge dans une classe de caractères. Pour réitérer : il s'agit d'une option dangereuse. Utilisez avec une extrême prudence.


PCRE2_EXTRA_CASELESS_RESTRICT

Lorsque PCRE2_UCP ou PCRE2_UTF est défini, la mise en correspondance sans distinction de casse suit les règles Unicode, qui permettent plus de deux cas par caractère. Il existe deux ensembles de caractères de casse équivalente qui contiennent à la fois des caractères ASCII et non ASCII. La lettre ASCII S est équivalente en casse à U+017f (S long) et la lettre ASCII K est équivalente en casse à U+212a (signe Kelvin). Cette option désactive la reconnaissance des équivalences de casse qui traversent la frontière ASCII/non ASCII. Dans une mise en correspondance sans distinction de casse, les deux caractères doivent être soit ASCII, soit non ASCII. L'option peut être modifiée dans un motif par les paramètres d'option (*CASELESS_RESTRICT) ou (?r).


PCRE2_EXTRA_ESCAPED_CR_IS_LF

Il existe certaines applications héritées où la séquence d'échappement \r dans un motif est censée correspondre à un saut de ligne. Si cette option est définie, \r dans un motif est converti en \n afin qu'il corresponde à un caractère LF (saut de ligne) au lieu d'un caractère CR (retour chariot). L'option n'affecte pas un CR littéral dans le motif, ni un CR spécifié comme point de code explicite tel que \x{0D}.


PCRE2_EXTRA_MATCH_LINE

Cette option est fournie pour être utilisée par l'option -x de pcre2grep. Elle permet au motif de ne correspondre qu'à des lignes complètes. Ceci est réalisé en insérant automatiquement le code pour `"^(?:"` au début du motif compilé et `")$"` à la fin. Ainsi, lorsque PCRE2_MULTILINE est défini, la ligne correspondante peut se trouver au milieu de la chaîne sujet. Cette option peut être utilisée avec PCRE2_LITERAL.


PCRE2_EXTRA_MATCH_WORD

Cette option est fournie pour être utilisée par l'option -w de pcre2grep. Elle permet au motif de ne correspondre qu'à des chaînes qui ont une limite de mot au début et à la fin. Ceci est réalisé en insérant automatiquement le code pour `"\b(?:"` au début du motif compilé et `")\b"` à la fin. L'option peut être utilisée avec PCRE2_LITERAL. Cependant, elle est ignorée si PCRE2_EXTRA_MATCH_LINE est également définie.


PCRE2_EXTRA_NO_BS0

Si cette option est définie (notez que son dernier caractère est le chiffre 0) elle bloque l'utilisation de la séquence \0 à moins qu'au moins un autre chiffre octal ne suive.


PCRE2_EXTRA_PYTHON_OCTAL

Si cette option est définie, PCRE2 suit les règles de Python pour interpréter les séquences d'échappement octales. Les règles pour gérer des séquences telles que \14, qui pourraient être un nombre octal ou une référence arrière, sont différentes. Les détails sont donnés dans la documentation pcre2pattern.


PCRE2_EXTRA_NEVER_CALLOUT

Si cette option est définie, PCRE2 traite les appels dans le motif comme une erreur de syntaxe, renvoyant PCRE2_ERROR_CALLOUT_CALLER_DISABLED. Ceci est utile si l'application sait qu'un appel ne sera pas fourni à pcre2_match(), de sorte que les appels dans le motif ne soient pas silencieusement ignorés.


PCRE2_EXTRA_TURKISH_CASING

Cette option modifie l'équivalence en casse des lettres 'i' pour suivre l'alphabet utilisé par les langues turque et azerbaïdjanaise. L'option peut être modifiée dans un motif par le paramètre de début de motif (*TURKISH_CASING). Les options UTF ou UCP doivent être définies. Dans la bibliothèque 8 bits, UTF doit être défini. Cette option ne peut pas être combinée avec PCRE2_EXTRA_CASELESS_RESTRICT.

COMPILATION JUSTE-À-TEMPS (JIT)

int pcre2_jit_compile(pcre2_code *code, uint32_t options);

int pcre2_jit_match(const pcre2_code *code, PCRE2_SPTR subject,
  PCRE2_SIZE length, PCRE2_SIZE startoffset,
  uint32_t options, pcre2_match_data *match_data,
  pcre2_match_context *mcontext);

void pcre2_jit_free_unused_memory(pcre2_general_context *gcontext);

pcre2_jit_stack *pcre2_jit_stack_create(size_t startsize,
  size_t maxsize, pcre2_general_context *gcontext);

void pcre2_jit_stack_assign(pcre2_match_context *mcontext,
  pcre2_jit_callback callback_function, void *callback_data);

void pcre2_jit_stack_free(pcre2_jit_stack *jit_stack);

Ces fonctions fournissent le support pour la compilation JIT, qui, si le compilateur juste-à-temps est disponible, traite davantage un motif compilé en code machine qui s'exécute beaucoup plus rapidement que la fonction de mise en correspondance interprétative pcre2_match(). Les détails complets sont donnés dans la documentation pcre2jit.

La compilation JIT est une optimisation lourde. L'analyse des motifs peut prendre un certain temps, et pour les correspondances uniques et les motifs simples, le bénéfice d'une exécution plus rapide pourrait être compensé par un temps de compilation beaucoup plus lent. La plupart (mais pas tous) des motifs peuvent être optimisés par le compilateur JIT.

SUPPORT LOCALES

const uint8_t *pcre2_maketables(pcre2_general_context *gcontext);

void pcre2_maketables_free(pcre2_general_context *gcontext,
  const uint8_t *tables);

PCRE2 gère la correspondance sans distinction de casse et détermine si les caractères sont des lettres, des chiffres ou autre chose, en se référant à un ensemble de tables, indexées par point de code caractère. Cependant, cela ne s'applique qu'aux caractères dont les points de code sont inférieurs à 256. Par défaut, les points de code de valeur supérieure ne correspondent jamais aux séquences d'échappement telles que \w ou \d.

Lorsque PCRE2 est compilé avec le support Unicode (par défaut), certaines propriétés des caractères Unicode peuvent être testées avec \p et \P, ou, alternativement, l'option PCRE2_UCP peut être définie lors de la compilation d'un motif ; cela fait que \w et les fonctions similaires utilisent le support des propriétés Unicode au lieu des tables intégrées. PCRE2_UCP provoque également que les opérations de mise en majuscules/minuscules sur les caractères dont les points de code sont supérieurs à 127 utilisent les propriétés Unicode. Ces effets s'appliquent même lorsque PCRE2_UTF n'est pas défini. Il existe cependant certaines options PCRE2_EXTRA (voir ci-dessus) qui peuvent être utilisées pour les modifier ou les supprimer.

L'utilisation de locales avec Unicode est déconseillée. Si vous manipulez des caractères dont les points de code sont supérieurs à 127, vous devriez soit utiliser le support Unicode, soit utiliser des locales, mais pas essayer de mélanger les deux.

PCRE2 contient un ensemble intégré de tables de caractères utilisé par défaut. Celles-ci sont suffisantes pour de nombreuses applications. Normalement, les tables internes ne reconnaissent que les caractères ASCII. Cependant, lorsque PCRE2 est compilé, il est possible de faire reconstruire les tables internes dans la locale "C" par défaut du système local, ce qui peut entraîner des différences.

Les tables intégrées peuvent être remplacées par des tables fournies par l'application qui appelle PCRE2. Celles-ci peuvent être créées dans une locale différente de celle par défaut. Alors que de plus en plus d'applications adoptent Unicode, le besoin de ce support de locale devrait disparaître.

Les tables externes sont construites en appelant la fonction pcre2_maketables(), dans la locale pertinente. Le seul argument de cette fonction est un contexte général, qui peut être utilisé pour passer un alloueur de mémoire personnalisé. Si l'argument est NULL, le malloc() du système est utilisé. Le résultat peut être passé à pcre2_compile() aussi souvent que nécessaire, en créant un contexte de compilation et en appelant pcre2_set_character_tables() pour définir le pointeur des tables dans ce contexte.

Par exemple, pour construire et utiliser des tables appropriées pour la locale française (où les caractères accentués dont la valeur est supérieure à 127 sont traités comme des lettres), le code suivant pourrait être utilisé :


setlocale(LC_CTYPE, "fr_FR");
tables = pcre2_maketables(NULL);
ccontext = pcre2_compile_context_create(NULL);
pcre2_set_character_tables(ccontext, tables);
re = pcre2_compile(..., ccontext);

Le nom de locale "fr_FR" est utilisé sur Linux et d'autres systèmes de type Unix ; si vous utilisez Windows, le nom de la locale française est "french".

Le pointeur qui est passé (via le contexte de compilation) à pcre2_compile() est sauvegardé avec le motif compilé, et les mêmes tables sont utilisées par les fonctions de mise en correspondance. Ainsi, pour n'importe quel motif unique, la compilation et la mise en correspondance se font dans la même locale, mais différents motifs peuvent être traités dans des locales différentes.

Il incombe à l'appelant de s'assurer que la mémoire contenant les tables reste disponible tant qu'elle est utilisée. Lorsqu'elles ne sont plus nécessaires, vous pouvez les supprimer en utilisant pcre2_maketables_free(), qui devrait passer comme premier paramètre le même contexte global qui a été utilisé pour créer les tables.

Sauvegarde des tables de locale

Les tables décrites ci-dessus ne sont qu'une séquence d'octets binaires, ce qui les rend indépendantes des caractéristiques matérielles telles que l'endianness ou si le processeur est 32 bits ou 64 bits. Une copie du résultat de pcre2_maketables() peut donc être sauvegardée dans un fichier ou ailleurs et réutilisée plus tard, même dans un autre programme ou sur un autre ordinateur. La taille des tables (nombre d'octets) doit être obtenue en appelant pcre2_config() avec l'option PCRE2_CONFIG_TABLES_LENGTH car pcre2_maketables() ne renvoie pas cette valeur. Notez que le programme pcre2_dftables, qui fait partie du système de build PCRE2, peut être utilisé autonomement pour créer un fichier contenant un ensemble de tables binaires. Voir la documentation pcre2build pour plus de détails.

INFORMATIONS SUR UN MOTIF COMPILÉ

int pcre2_pattern_info(const pcre2 *code, uint32_t what, void *where);

La fonction pcre2_pattern_info() renvoie des informations générales sur un motif compilé. Pour les informations sur les appels, voir la section suivante. Le premier argument de pcre2_pattern_info() est un pointeur vers le motif compilé. Le deuxième argument spécifie quelle information est requise, et le troisième argument est un pointeur vers une variable pour recevoir les données. Si le troisième argument est NULL, le premier argument est ignoré, et la fonction renvoie la taille en octets de la variable nécessaire pour l'information demandée. Sinon, le résultat de la fonction est zéro en cas de succès, ou l'un des nombres négatifs suivants :


PCRE2_ERROR_NULL l'argument code était NULL
PCR

E2_ERROR_BADMAGIC le "nombre magique" n'a pas été trouvé
PCRE2_ERROR_BADOPTION la valeur de what était invalide
PCRE2_ERROR_UNSET le champ demandé n'est pas défini

Le "nombre magique" est placé au début de chaque motif compilé comme vérification simple contre le passage d'un pointeur mémoire arbitraire. Voici un appel typique de pcre2_pattern_info(), pour obtenir la longueur du motif compilé :


int rc;
size_t length;
rc = pcre2_pattern_info(
re, /* résultat de pcre2_compile() */
PCRE2_INFO_SIZE, /* ce qui est requis */
&length); /* où mettre les données */

Les valeurs possibles pour le deuxième argument sont définies dans pcre2.h, et sont les suivantes :


PCRE2_INFO_ALLOPTIONS
PCRE2_INFO_ARGOPTIONS
PCRE2_INFO_EXTRAOPTIONS

Retourne des copies des options du motif. Le troisième argument doit pointer vers une variable de type uint32_t. PCRE2_INFO_ARGOPTIONS retourne exactement les options qui ont été passées à pcre2_compile(), tandis que PCRE2_INFO_ALLOPTIONS retourne les options de compilation telles que modifiées par tout paramètre d'option (*XXX) de niveau supérieur comme (*UTF) au début du motif lui-même. PCRE2_INFO_EXTRAOPTIONS retourne les options supplémentaires qui ont été définies dans le contexte de compilation en appelant la fonction pcre2_set_compile_extra_options().

Par exemple, si le motif /(*UTF)abc/ est compilé avec l'option PCRE2_EXTENDED, le résultat pour PCRE2_INFO_ALLOPTIONS est PCRE2_EXTENDED et PCRE2_UTF. Les paramètres d'option tels que (?i) qui peuvent changer au sein d'un motif n'affectent pas le résultat de PCRE2_INFO_ALLOPTIONS, même s'ils apparaissent juste au début du motif. (Cela était différent dans certaines versions antérieures.)

Un motif compilé sans PCRE2_ANCHORED est automatiquement ancré par PCRE2 si le premier élément significatif de chaque branche de niveau supérieur est l'un des éléments suivants :


^ sauf si PCRE2_MULTILINE est défini
\A toujours
\G toujours
.* parfois - voir ci-dessous

Lorsque .* est le premier élément significatif, l'ancrage n'est possible que lorsque toutes les conditions suivantes sont remplies :


.* n'est pas dans un groupe atomique
.* n'est pas dans un groupe de capture qui est le sujet
d'une référence arrière
PCRE2_DOTALL est actif pour .*
Ni (*PRUNE) ni (*SKIP) n'apparaissent dans le motif
PCRE2_NO_DOTSTAR_ANCHOR n'est pas défini
L'ancrage Dotstar n'a pas été désactivé avec PCRE2_DOTSTAR_ANCHOR_OFF

Pour les motifs qui sont auto-ancrés, le bit PCRE2_ANCHORED est défini dans les options retournées pour PCRE2_INFO_ALLOPTIONS.


PCRE2_INFO_BACKREFMAX

Retourne le numéro de la référence arrière la plus élevée dans le motif. Le troisième argument doit pointer vers une variable de type uint32_t. Les groupes de capture nommés acquièrent des numéros ainsi que des noms, et ceux-ci comptent dans le total des références arrière les plus élevées. Les références arrière comme \4 ou \g{12} correspondent aux caractères capturés du groupe donné, mais en plus, la vérification qu'un groupe de capture est défini dans un groupe conditionnel comme (?(3)a|b) est aussi une référence arrière. Zéro est retourné s'il n'y a pas de références arrière.


PCRE2_INFO_BSR

La sortie est un entier de type uint32_t dont la valeur indique quelles séquences de caractères la séquence d'échappement \R correspond. Une valeur de PCRE2_BSR_UNICODE signifie que \R correspond à toute séquence de fin de ligne Unicode ; une valeur de PCRE2_BSR_ANYCRLF signifie que \R correspond uniquement à CR, LF, ou CRLF.


PCRE2_INFO_CAPTURECOUNT

Retourne le numéro le plus élevé du groupe de capture dans le motif. Dans les motifs où (?| n'est pas utilisé, c'est aussi le nombre total de groupes de capture. Le troisième argument doit pointer vers une variable de type uint32_t.


PCRE2_INFO_DEPTHLIMIT

Si le motif a défini une limite de profondeur de backtracking en incluant un élément de la forme (*LIMIT_DEPTH=nnnn) au début, la valeur est retournée. Le troisième argument doit pointer vers un entier de type uint32_t. Si aucune valeur de ce type n'a été définie, l'appel à pcre2_pattern_info() retourne l'erreur PCRE2_ERROR_UNSET. Notez que cette limite ne sera utilisée lors de la correspondance que si elle est inférieure à la limite définie ou par défaut par l'appelant de la fonction de correspondance.


PCRE2_INFO_FIRSTBITMAP

En l'absence d'une seule première unité de code pour un motif non ancré, pcre2_compile() peut construire une table de 256 bits qui définit un ensemble fixe de valeurs pour la première unité de code dans toute correspondance. Par exemple, un motif qui commence par [abc] résulte en une table avec trois bits définis. Lorsque les valeurs d'unité de code supérieures à 255 sont prises en charge, le bit de drapeau pour 255 signifie "toute unité de code de valeur 255 ou supérieure". Si une telle table a été construite, un pointeur vers celle-ci est retourné. Sinon, NULL est retourné. Le troisième argument doit pointer vers une variable de type const uint8_t *.


PCRE2_INFO_FIRSTCODETYPE

Retourne des informations sur la première unité de code de toute chaîne correspondante, pour un motif non ancré. Le troisième argument doit pointer vers une variable de type uint32_t. S'il existe une valeur fixe pour la première unité, par exemple, la lettre "c" d'un motif tel que (cat|cow|coyote), 1 est retourné, et la valeur peut être récupérée en utilisant PCRE2_INFO_FIRSTCODEUNIT. S'il n'y a pas de valeur fixe pour la première unité, mais qu'il est connu qu'une correspondance peut se produire uniquement au début du sujet ou après une nouvelle ligne dans le sujet, 2 est retourné. Sinon, et pour les motifs ancrés, 0 est retourné.


PCRE2_INFO_FIRSTCODEUNIT

Retourne la valeur de la première unité de code de toute chaîne correspondante pour un motif où PCRE2_INFO_FIRSTCODETYPE retourne 1 ; sinon, retourne 0. Le troisième argument doit pointer vers une variable de type uint32_t. Dans la bibliothèque 8 bits, la valeur est toujours inférieure à 256. Dans la bibliothèque 16 bits, la valeur peut aller jusqu'à 0xffff. Dans la bibliothèque 32 bits en mode UTF-32, la valeur peut aller jusqu'à 0x10ffff, et jusqu'à 0xffffffff lorsque le mode UTF-32 n'est pas utilisé.


PCRE2_INFO_FRAMESIZE

Retourne la taille (en octets) des trames de données qui sont utilisées pour se souvenir des positions de backtracking lorsque le motif est traité par pcre2_match() sans utiliser JIT. Le troisième argument doit pointer vers une variable de type size_t. La taille de la trame dépend du nombre de parenthèses de capture dans le motif. Chaque groupe de capture supplémentaire ajoute deux variables PCRE2_SIZE.


PCRE2_INFO_HASBACKSLASHC

Retourne 1 si le motif contient des instances de \C, sinon 0. Le troisième argument doit pointer vers une variable de type uint32_t.


PCRE2_INFO_HASCRORLF

Retourne 1 si le motif contient des correspondances explicites pour les caractères CR ou LF, sinon 0. Le troisième argument doit pointer vers une variable de type uint32_t. Une correspondance explicite est soit un caractère CR ou LF littéral, soit \r ou \n ou l'une des séquences d'échappement hexadécimales ou octales équivalentes.


PCRE2_INFO_HEAPLIMIT

Si le motif a défini une limite de mémoire du tas en incluant un élément de la forme (*LIMIT_HEAP=nnnn) au début, la valeur est retournée. Le troisième argument doit pointer vers un entier de type uint32_t. Si aucune valeur de ce type n'a été définie, l'appel à pcre2_pattern_info() retourne l'erreur PCRE2_ERROR_UNSET. Notez que cette limite ne sera utilisée lors de la correspondance que si elle est inférieure à la limite définie ou par défaut par l'appelant de la fonction de correspondance.


PCRE2_INFO_JCHANGED

Retourne 1 si le paramètre d'option (?J) ou (?-J) est utilisé dans le motif, sinon 0. Le troisième argument doit pointer vers une variable de type uint32_t. (?J) et (?-J) définissent et annulent respectivement l'option locale PCRE2_DUPNAMES.


PCRE2_INFO_JITSIZE

Si le motif compilé a été traité avec succès par pcre2_jit_compile(), retourne la taille du code JIT compilé, sinon retourne zéro. Le troisième argument doit pointer vers une variable de type size_t.


PCRE2_INFO_LASTCODETYPE

Retourne 1 s'il existe une unité de code littérale la plus à droite qui doit exister dans toute chaîne correspondante, autre qu'à son début. Le troisième argument doit pointer vers une variable de type uint32_t. S'il n'y a pas de telle valeur, 0 est retourné. Lorsque 1 est retourné, la valeur de l'unité de code elle-même peut être récupérée en utilisant PCRE2_INFO_LASTCODEUNIT. Pour les motifs ancrés, une dernière valeur littérale n'est enregistrée que si elle suit quelque chose de longueur variable. Par exemple, pour le motif /^a\d+z\d+/ la valeur retournée est 1 (avec "z" retourné par PCRE2_INFO_LASTCODEUNIT), mais pour /^a\dz\d/ la valeur retournée est 0.


PCRE2_INFO_LASTCODEUNIT

Retourne la valeur de l'unité de code littérale la plus à droite qui doit exister dans toute chaîne correspondante, autre qu'à son début, pour un motif où PCRE2_INFO_LASTCODETYPE retourne 1. Sinon, retourne 0. Le troisième argument doit pointer vers une variable de type uint32_t.


PCRE2_INFO_MATCHEMPTY

Retourne 1 si le motif peut correspondre à une chaîne vide, sinon 0. Le troisième argument doit pointer vers une variable de type uint32_t. Lorsqu'un motif contient des appels de sous-routines récursifs, il n'est pas toujours possible de déterminer s'il peut correspondre à une chaîne vide ou non. PCRE2 adopte une approche prudente et retourne 1 dans ces cas.


PCRE2_INFO_MATCHLIMIT

Si le motif a défini une limite de correspondance en incluant un élément de la forme (*LIMIT_MATCH=nnnn) au début, la valeur est retournée. Le troisième argument doit pointer vers un entier de type uint32_t. Si aucune valeur de ce type n'a été définie, l'appel à pcre2_pattern_info() retourne l'erreur PCRE2_ERROR_UNSET. Notez que cette limite ne sera utilisée lors de la correspondance que si elle est inférieure à la limite définie ou par défaut par l'appelant de la fonction de correspondance.


PCRE2_INFO_MAXLOOKBEHIND

Une assertion de recherche arrière (lookbehind) se déplace vers l'arrière d'un certain nombre de caractères (pas d'unités de code) lorsqu'elle commence à traiter chacune de ses branches. Cette requête retourne le plus grand de ces déplacements arrière. Le troisième argument doit pointer vers un entier de type uint32_t. Les assertions simples \b et \B nécessitent une recherche arrière d'un caractère et font que PCRE2_INFO_MAXLOOKBEHIND retourne 1 en l'absence de quelque chose de plus long. \A enregistre également une recherche arrière d'un caractère, bien qu'elle n'inspecte pas réellement le caractère précédent.

Notez que ces informations sont utiles pour la correspondance multi-segments uniquement si le motif ne contient pas de recherches arrière imbriquées. Par exemple, le motif (?<=a(?<=ba)c) retourne une recherche arrière maximale de 2, mais lorsqu'il est traité, la première recherche arrière recule de deux caractères, correspond à un caractère, puis la recherche arrière imbriquée recule également de deux caractères. Cela place le point de correspondance trois caractères plus tôt qu'il ne l'était au début. PCRE2_INFO_MAXLOOKBEHIND est vraiment utile uniquement comme outil de débogage. Voir la documentation pcre2partial pour une discussion sur la correspondance multi-segments.


PCRE2_INFO_MINLENGTH

Si une longueur minimale pour la correspondance des chaînes de sujet a été calculée, sa valeur est retournée. Sinon, la valeur retournée est 0. Cette valeur n'est pas calculée par

hen PCRE2_NO_START_OPTIMIZE est défini. La valeur est un nombre de caractères qui, en mode UTF, peut être différent du nombre d'unités de code. Le troisième argument doit pointer vers une variable de type uint32_t. La valeur est une borne inférieure de la longueur de toute chaîne correspondante. Il peut ne pas y avoir de chaînes de cette longueur qui correspondent effectivement, mais chaque chaîne qui correspond est au moins aussi longue.


PCRE2_INFO_NAMECOUNT
PCRE2_INFO_NAMEENTRYSIZE
PCRE2_INFO_NAMETABLE

PCRE2 prend en charge l'utilisation de parenthèses capturantes nommées ainsi que numérotées. Les noms sont juste un moyen supplémentaire d'identifier les parenthèses, qui acquièrent toujours des numéros. Plusieurs fonctions pratiques telles que pcre2_substring_get_byname() sont fournies pour extraire des sous-chaînes capturantes par nom. Il est également possible d'extraire les données directement, en convertissant d'abord le nom en numéro afin d'accéder aux pointeurs corrects dans le vecteur de sortie (décrit avec pcre2_match() ci-dessous). Pour effectuer la conversion, vous devez utiliser la carte nom-à-numéro, qui est décrite par ces trois valeurs.

La carte se compose d'un certain nombre d'entrées de taille fixe. PCRE2_INFO_NAMECOUNT donne le nombre d'entrées, et PCRE2_INFO_NAMEENTRYSIZE donne la taille de chaque entrée en unités de code ; ces deux valeurs retournent un uint32_t. La taille de l'entrée dépend de la longueur du nom le plus long.

PCRE2_INFO_NAMETABLE renvoie un pointeur vers la première entrée de la table. Il s'agit d'un pointeur PCRE2_SPTR vers un bloc d'unités de code. Dans la bibliothèque 8 bits, les deux premiers octets de chaque entrée sont le numéro de la parenthèse capturante, octet de poids fort en premier. Dans la bibliothèque 16 bits, le pointeur pointe vers des unités de code 16 bits, la première contenant le numéro de la parenthèse. Dans la bibliothèque 32 bits, le pointeur pointe vers des unités de code 32 bits, la première contenant le numéro de la parenthèse. Le reste de l'entrée est le nom correspondant, terminé par un zéro.

Les noms sont en ordre alphabétique. Si (?| est utilisé pour créer plusieurs groupes de capture avec le même numéro, comme décrit dans la section sur les numéros de groupe dupliqués de la page pcre2pattern, les groupes peuvent recevoir le même nom, mais il n'y a qu'une seule entrée dans la table. Des noms différents pour des groupes du même numéro ne sont pas autorisés.

Les noms dupliqués pour des groupes de capture avec des numéros différents sont autorisés, mais uniquement si PCRE2_DUPNAMES est défini. Ils apparaissent dans la table dans l'ordre où ils ont été trouvés dans le modèle. En l'absence de (?| cela correspond à l'ordre des numéros croissants ; lorsque (?| est utilisé, ce n'est pas nécessairement le cas car les groupes de capture ultérieurs peuvent avoir des numéros inférieurs.

À titre d'exemple simple de la table nom/numéro, considérez le modèle suivant après compilation par la bibliothèque 8 bits (supposez que PCRE2_EXTENDED est défini, de sorte que les espaces blancs - y compris les sauts de ligne - sont ignorés) :


(?<date> (?<year>(\d\d)?\d\d) -
(?<month>\d\d) - (?<day>\d\d) )

Il y a quatre groupes de capture nommés, donc la table a quatre entrées, et chaque entrée de la table a une taille de huit octets. La table est la suivante, avec les octets non imprimables affichés en hexadécimal, et les octets indéfinis affichés sous forme de ?? :


00 01 d a t e 00 ??
00 05 d a y 00 ?? ??
00 04 m o n t h 00
00 02 y e a r 00 ??

Lorsque vous écrivez du code pour extraire des données de groupes de capture nommés en utilisant la carte nom-à-numéro, n'oubliez pas que la longueur des entrées est susceptible d'être différente pour chaque modèle compilé.


PCRE2_INFO_NEWLINE

La sortie est l'une des valeurs uint32_t suivantes :


PCRE2_NEWLINE_CR Retour chariot (CR)
PCRE2_NEWLINE_LF Saut de ligne (LF)
PCRE2_NEWLINE_CRLF Retour chariot, saut de ligne (CRLF)
PCRE2_NEWLINE_ANY N'importe quelle fin de ligne Unicode
PCRE2_NEWLINE_ANYCRLF N'importe lequel de CR, LF ou CRLF
PCRE2_NEWLINE_NUL Le caractère NUL (zéro binaire)

Ceci identifie la séquence de caractères qui sera reconnue comme signifiant "nouvelle ligne" pendant la correspondance.


PCRE2_INFO_SIZE

Retourne la taille du modèle compilé en octets (pour les trois bibliothèques). Le troisième argument doit pointer vers une variable de type size_t. Cette valeur inclut la taille du bloc de données général qui précède les unités de code du modèle compilé lui-même. La valeur utilisée lorsque pcre2_compile() alloue de la mémoire pour placer le modèle compilé peut être légèrement supérieure à la valeur retournée par cette option, car il existe des cas où le code qui calcule la taille doit surestimer. Le traitement d'un modèle avec le compilateur JIT ne modifie pas la valeur retournée par cette option.

INFORMATIONS SUR LES APPELS DE RETOUR D'UN MODÈLE

int pcre2_callout_enumerate(const pcre2_code *code,
  int (*callback)(pcre2_callout_enumerate_block *, void *),
  void *user_data);

Un langage de script qui prend en charge l'utilisation d'arguments de chaîne dans les appels de retour pourrait vouloir scanner tous les appels de retour dans un modèle avant d'exécuter la correspondance. Ceci peut être fait en appelant pcre2_callout_enumerate(). Le premier argument est un pointeur vers un modèle compilé, le second pointe vers une fonction de rappel, et le troisième est des données utilisateur arbitraires. La fonction de rappel est appelée pour chaque appel de retour dans le modèle, dans l'ordre où ils apparaissent. Son premier argument est un pointeur vers un bloc d'énumération d'appels de retour, et son second argument est la valeur user_data qui a été passée à pcre2_callout_enumerate(). Le contenu du bloc d'énumération d'appels de retour est décrit dans la documentation pcre2callout, qui donne également plus de détails sur les appels de retour.

SÉRIALISATION ET PRÉCOMPILATION

Il est possible de sauvegarder des modèles compilés sur disque ou ailleurs, et de les recharger plus tard, sous réserve d'un certain nombre de restrictions. L'hôte sur lequel les modèles sont rechargés doit exécuter la même version de PCRE2, avec la même largeur d'unités de code, et doit également avoir la même endianness, la même largeur de pointeur et le même type PCRE2_SIZE. Avant que les modèles compilés puissent être sauvegardés, ils doivent être convertis dans une forme "sériée", qui dans le cas de PCRE2 n'est qu'un vidage d'octets. Les fonctions dont les noms commencent par pcre2_serialize_ sont utilisées pour convertir depuis et vers la forme sérialisée. Elles sont décrites dans la documentation pcre2serialize. Notez que la sérialisation PCRE2 ne convertit pas les modèles compilés en un format abstrait comme la sérialisation Java ou .NET.

LE BLOC DE DONNÉES DE CORRESPONDANCE

pcre2_match_data *pcre2_match_data_create(uint32_t ovecsize,
  pcre2_general_context *gcontext);

pcre2_match_data *pcre2_match_data_create_from_pattern(
  const pcre2_code *code, pcre2_general_context *gcontext);

void pcre2_match_data_free(pcre2_match_data *match_data);

Les informations sur une correspondance réussie ou échouée sont placées dans un bloc de données de correspondance, qui est une structure opaque accessible par des appels de fonction. En particulier, le bloc de données de correspondance contient un vecteur d'offsets dans la chaîne sujet qui définissent les parties correspondantes du sujet. C'est ce qu'on appelle l' ovector.

Avant d'appeler pcre2_match(), pcre2_dfa_match(), ou pcre2_jit_match(), vous devez créer un bloc de données de correspondance en appelant l'une des fonctions de création ci-dessus. Pour pcre2_match_data_create(), le premier argument est le nombre de paires d'offsets dans l' ovector.

Lors de l'utilisation de pcre2_match(), une paire d'offsets est requise pour identifier la chaîne qui correspond au modèle complet, avec une paire supplémentaire pour chaque sous-chaîne capturée. Par exemple, une valeur de 4 crée suffisamment d'espace pour enregistrer la partie correspondante du sujet plus trois sous-chaînes capturées.

Lors de l'utilisation de pcre2_dfa_match(), il peut y avoir plusieurs sous-chaînes correspondantes de différentes longueurs au même point du sujet. L'ovector doit être suffisamment grand pour contenir autant de correspondances que prévu.

Un minimum d'au moins 1 paire est imposé par pcre2_match_data_create(), il est donc toujours possible de retourner la chaîne globalement correspondante dans le cas de pcre2_match() ou la correspondance la plus longue dans le cas de pcre2_dfa_match(). Le nombre maximum de paires est de 65535 ; si le premier argument de pcre2_match_data_create() est supérieur à cela, 65535 est utilisé.

Le deuxième argument de pcre2_match_data_create() est un pointeur vers un contexte général, qui peut spécifier une gestion de mémoire personnalisée pour obtenir la mémoire du bloc de données de correspondance. Si vous n'utilisez pas de gestion de mémoire personnalisée, passez NULL, ce qui fait que malloc() soit utilisé.

Pour pcre2_match_data_create_from_pattern(), le premier argument est un pointeur vers un modèle compilé. L'ovector est créé pour être exactement de la bonne taille pour contenir toutes les sous-chaînes qu'un modèle peut capturer lorsqu'il est mis en correspondance à l'aide de pcre2_match(). Vous ne devez pas utiliser cet appel lors de la mise en correspondance avec pcre2_dfa_match(). Le second argument est à nouveau un pointeur vers un contexte général, mais dans ce cas, si NULL est passé, la mémoire est obtenue en utilisant le même allocateur que celui utilisé pour le modèle compilé (personnalisé ou par défaut).

Un bloc de données de correspondance peut être utilisé plusieurs fois, avec les mêmes ou différents modèles compilés. Vous pouvez extraire des informations d'un bloc de données de correspondance après la fin d'une opération de correspondance, en utilisant des fonctions décrites dans les sections sur les chaînes correspondantes et autres données de correspondance ci-dessous.

Lorsqu'un appel de pcre2_match() échoue, des données valides sont disponibles dans le bloc de correspondance uniquement lorsque l'erreur est PCRE2_ERROR_NOMATCH, PCRE2_ERROR_PARTIAL, ou l'un des codes d'erreur pour une chaîne UTF invalide. Exactement ce qui est disponible dépend de l'erreur, et est détaillé ci-dessous.

Lorsque l'une des fonctions de correspondance est appelée, les pointeurs vers le modèle compilé et la chaîne sujet sont définis dans le bloc de données de correspondance afin qu'ils puissent être référencés par les fonctions d'extraction après une correspondance réussie. Après avoir exécuté une correspondance, vous ne devez pas libérer un modèle compilé ou une chaîne sujet tant que toutes les opérations sur le bloc de données de correspondance (pour cette correspondance) n'ont pas eu lieu, sauf si, dans le cas de la chaîne sujet, vous avez utilisé l'option PCRE2_COPY_MATCHED_SUBJECT, qui est décrite dans la section intitulée "Bits d'option pour pcre2_match()" ci-dessous.

Lorsque le bloc de données de correspondance lui-même n'est plus nécessaire, il doit être libéré en appelant pcre2_match_data_free(). Si cette fonction est appelée avec un argument NULL, elle retourne immédiatement, sans rien faire.

UTILISATION DE LA MÉMOIRE POUR LES BLOCS DE DONNÉES DE CORRESPONDANCE

PCRE2_SIZE pcre2_get_match_data_size(pcre2_match_data *match_data);

PCRE2_SIZE pcre2_get_match_data_heapframes_size(
  pcre2_match_data *match_data);

La taille d'un bloc de données de correspondance dépend de la taille de l'ovector qu'il contient. La fonction pcre2_get_match_data_size() renvoie la taille, en octets, du bloc qui est son argument.

Lorsque pcre2_match() s'exécute de manière interprétative (c'est-à-dire sans utiliser JIT), elle utilise un vecteur de trames de données pour se souvenir des positions de retour sur trace. La taille de chaque trame individuelle dépend du nombre de parenthèses de capture dans le modèle et peut être obtenue en appelant pcre2_pattern_info() avec l'option PCRE2_INFO_FRAMESIZE (voir la section intitulée "Informations sur un modèle compilé" ci-dessus).

La mémoire du tas est utilisée pour le vecteur de trames ; si le bloc de mémoire initial s'avère trop petit pendant la correspondance, il est automatiquement étendu. Lorsque pcre2_match() revient, la mémoire n'est pas libérée, mais reste attachée au bloc de données de correspondance, pour être utilisée par toutes les correspondances ultérieures qui utilisent le même bloc. Elle est automatiquement libérée lorsque le bloc de données de correspondance lui-même est libéré.

Vous pouvez connaître la taille actuelle du vecteur de trames que possède un bloc de données de correspondance en appelant pcre2_get_match_data_heapframes_size(). Pour un bloc de données de correspondance nouvellement créé, la taille sera nulle. Certains types de correspondance peuvent nécessiter beaucoup de trames et donc un grand vecteur ; les applications qui s'exécutent dans des environnements à mémoire limitée peuvent vérifier cela et libérer le bloc de données de correspondance si le vecteur de trames du tas est devenu trop grand.

CORRESPONDANCE D'UN MODÈLE : LA FONCTION TRADITIONNELLE

int pcre2_match(const pcre2_code *code, PCRE2_SPTR subject,
  PCRE2_SIZE length, PCRE2_SIZE startoffset,
  uint32_t options, pcre2_match_data *match_data,
  pcre2_match_context *mcontext);

La fonction pcre2_match() est appelée pour faire correspondre une chaîne sujet à un modèle compilé, qui est passé dans l'argument code. Vous pouvez appeler pcre2_match() avec le même argument code autant de fois que vous le souhaitez, afin de trouver plusieurs correspondances dans la chaîne sujet ou de faire correspondre différentes chaînes sujet avec le même modèle.

Cette fonction est la principale installation de correspondance de la bibliothèque, et elle fonctionne de manière similaire à Perl. Pour un usage spécialisé, il existe également une fonction de correspondance alternative, décrite ci-dessous dans la section concernant la fonction pcre2_dfa_match().

Voici un exemple d'appel simple à pcre2_match() :


pcre2_match_data *md = pcre2_match_data_create(4, NULL);
int rc = pcre2_match(
re, /* résultat de pcre2_compile() */
"some string", /* la chaîne sujet */
11, /* la longueur de la chaîne sujet */
0, /* commence à l'offset 0 dans le sujet */
0, /* options par défaut */
md, /* le bloc de données de correspondance */
NULL); /* un contexte de correspondance ; NULL signifie utiliser les défauts */

Si la chaîne sujet est terminée par zéro, la longueur peut être donnée comme PCRE2_ZERO_TERMINATED. Un contexte de correspondance doit être fourni si certains paramètres de correspondance moins courants doivent être modifiés. Pour plus de détails, voir la section sur le contexte de correspondance ci-dessus.

La chaîne à faire correspondre par pcre2_match()

La chaîne sujet est passée à pcre2_match() sous forme de pointeur dans subject, d'une longueur dans length, et d'un décalage de départ dans startoffset. La longueur et le décalage sont en unités de code, pas en caractères. C'est-à-dire qu'ils sont en octets pour la bibliothèque 8 bits, en unités de code 16 bits pour la bibliothèque 16 bits, et en unités de code 32 bits pour la bibliothèque 32 bits, que le traitement UTF soit activé ou non. Dans le cas spécial où subject est NULL et length est zéro, le sujet est supposé être une chaîne vide. Si length est non nul, une erreur se produit si subject est NULL.

Si startoffset est supérieur à la longueur du sujet, pcre2_match() renvoie PCRE2_ERROR_BADOFFSET. Lorsque le décalage de départ est zéro, la recherche d'une correspondance commence au début du sujet, et c'est de loin le cas le plus courant. En mode UTF-8 ou UTF-16, le décalage de départ doit pointer vers le début d'un caractère, ou vers la fin du sujet (en mode UTF-32, une unité de code est égale à un caractère, donc tous les décalages sont valides). Comme la chaîne de modèle, le sujet peut contenir des zéros binaires.

Un décalage de départ non nul est utile lors de la recherche d'une autre correspondance dans le même sujet en appelant à nouveau pcre2_match() après un succès précédent. Le réglage de startoffset diffère du passage d'une chaîne raccourcie et du réglage de PCRE2_NOTBOL dans le cas d'un modèle qui commence par un quelconque lookbehind. Par exemple, considérez le modèle


\Biss\B

qui trouve des occurrences de "iss" au milieu des mots. (\B ne correspond que si la position actuelle dans le sujet n'est pas une limite de mot.) Lorsqu'il est appliqué à la chaîne "Mississippi", le premier appel à pcre2_match() trouve la première occurrence. Si pcre2_match() est appelé à nouveau avec seulement le reste du sujet, à savoir "issippi", il ne correspond pas, car \B est toujours faux au début du sujet, qui est considéré comme une limite de mot. Cependant, si pcre2_match() est passé à nouveau avec la chaîne entière, mais avec startoffset réglé sur 4, il trouve la deuxième occurrence de "iss" car il peut regarder derrière le point de départ pour découvrir qu'il est précédé par une lettre.

Trouver toutes les correspondances dans un sujet est délicat lorsque le modèle peut correspondre à une chaîne vide. PCRE2 inclut une API d'aide pour faciliter cela ; voir la section intitulée "Itérer sur toutes les correspondances" ci-dessous pour plus de détails.

Si un décalage de départ non nul est passé lorsque le modèle est ancré, une seule tentative de correspondance au décalage donné est effectuée. Cela ne peut réussir que si le modèle ne nécessite pas que la correspondance soit au début du sujet. En d'autres termes, l'ancrage doit être le résultat du réglage de l'option PCRE2_ANCHORED ou de l'utilisation de .* avec PCRE2_DOTALL, et non pas en commençant le modèle par ^ ou \A.

Bits d'option pour pcre2_match()

Les bits inutilisés de l'argument options pour pcre2_match() doivent être zéro. Les seuls bits qui peuvent être réglés sont PCRE2_ANCHORED, PCRE2_COPY_MATCHED_SUBJECT, PCRE2_DISABLE_RECURSELOOP_CHECK, PCRE2_ENDANCHORED, PCRE2_NOTBOL, PCRE2_NOTEOL, PCRE2_NOTEMPTY, PCRE2_NOTEMPTY_ATSTART, PCRE2_NO_JIT, PCRE2_NO_UTF_CHECK, PCRE2_PARTIAL_HARD, et PCRE2_PARTIAL_SOFT. Leur action est décrite ci-dessous.

Le réglage de PCRE2_ANCHORED ou PCRE2_ENDANCHORED au moment de la correspondance n'est pas pris en charge par le compilateur just-in-time (JIT). S'il est réglé, la correspondance JIT est désactivée et le code interprétatif de pcre2_match() est exécuté. PCRE2_DISABLE_RECURSELOOP_CHECK est ignoré par JIT, mais à l'exception de PCRE2_NO_JIT (évidemment), les autres options sont prises en charge pour la correspondance JIT.


PCRE2_ANCHORED

L'option PCRE2_ANCHORED limite pcre2_match() à une correspondance à la première position correspondante. Si un modèle a été compilé avec PCRE2_ANCHORED, ou s'est avéré être ancré de par son contenu, il ne peut pas être rendu non ancré au moment de la correspondance. Notez que le réglage de l'option au moment de la correspondance désactive la correspondance JIT.


PCRE2_COPY_MATCHED_SUBJECT

Par défaut, un pointeur vers le sujet est mémorisé dans le bloc de données de correspondance afin que, après une correspondance réussie, il puisse être référencé par les fonctions d'extraction de sous-chaîne. Cela signifie que la mémoire du sujet ne doit pas être libérée tant que toutes ces opérations ne sont pas terminées. Pour certaines applications où la durée de vie de la chaîne sujet n'est pas garantie, il peut être nécessaire de faire une copie de la chaîne sujet, mais il est inutile de le faire sauf si la correspondance réussit. Après une correspondance réussie, si PCRE2_COPY_MATCHED_SUBJECT est réglé, le sujet est copié et le nouveau pointeur est mémorisé dans le bloc de données de correspondance au lieu du pointeur sujet d'origine. L'allocateur mémoire qui a été utilisé pour le bloc de correspondance lui-même est utilisé. La copie est automatiquement libérée lorsque pcre2_match_data_free() est appelée pour libérer le bloc de données de correspondance. Elle est également automatiquement libérée si le bloc de données de correspondance est réutilisé pour une autre opération de correspondance.


PCRE2_DISABLE_RECURSELOOP_CHECK

Cette option n'est pertinente que pour pcre2_match() pour la correspondance interprétative. Elle est ignorée lorsque JIT est utilisé et est interdite pour pcre2_dfa_match().

L'utilisation de la récursion dans les modèles peut entraîner des boucles infinies. Dans le moteur interprétatif, celles-ci seraient finalement interceptées par les limites de correspondance ou de tas, mais cela pourrait prendre du temps et/ou utiliser beaucoup de mémoire si les limites sont importantes. Il y a donc une vérification au début de chaque récursion. Si le même groupe est toujours actif depuis un appel précédent, et que le pointeur sujet actuel est le même qu'au début de ce groupe, et que le caractère le plus loin inspecté du sujet n'a pas changé, une erreur est générée.

Il existe de rares cas de correspondances qui s'achèveraient, mais qui déclencheraient néanmoins cette erreur. Cette option désactive la vérification. Elle est principalement fournie pour les tests lors de la comparaison du comportement JIT et interprétatif.


PCRE2_ENDANCHORED

Si l'option PCRE2_ENDANCHORED est réglée, toute chaîne que pcre2_match() fait correspondre doit se trouver exactement à la fin de la chaîne sujet. Notez que le réglage de l'option au moment de la correspondance désactive la correspondance JIT.


PCRE2_NOTBOL

Cette option spécifie que le premier caractère de la chaîne sujet n'est pas le début d'une ligne, donc le métacaractère circonflexe ne doit pas correspondre avant lui. Le réglage de ceci sans avoir réglé PCRE2_MULTILINE à la compilation fait que le circonflexe ne correspond jamais. Cette option n'affecte que le comportement du métacaractère circonflexe. Elle n'affecte pas \A.


PCRE2_NOTEOL

Cette option spécifie que la fin de la chaîne sujet n'est pas la fin d'une ligne, donc le métacaractère dollar ne doit pas y correspondre ni (sauf en mode multiligne) un saut de ligne immédiatement avant. Le réglage de ceci sans avoir réglé PCRE2_MULTILINE à la compilation fait que le dollar ne correspond jamais. Cette option n'affecte que le comportement du métacaractère dollar. Elle n'affecte pas \Z ni \z.


PCRE2_NOTEMPTY

Une chaîne vide n'est pas considérée comme une correspondance valide si cette option est réglée. S'il y a des alternatives dans le modèle, elles sont essayées. Si toutes les alternatives correspondent à la chaîne vide, la correspondance entière échoue. Par exemple, si le modèle


a?b?

est appliqué à une chaîne ne commençant pas par

"a" ou "b", il correspond à une chaîne vide au début du sujet. Avec PCRE2_NOTEMPTY défini, cette correspondance n'est pas valide, donc pcre2_match() recherche plus loin dans la chaîne des occurrences de "a" ou "b".


PCRE2_NOTEMPTY_ATSTART

Ceci est similaire à PCRE2_NOTEMPTY, sauf qu'il exclut une correspondance de chaîne vide uniquement à la première position de correspondance, c'est-à-dire au début du sujet plus le décalage de départ. Une correspondance de chaîne vide plus loin dans le sujet est autorisée. Si le motif est ancré, une telle correspondance ne peut se produire que si le motif contient \K.


PCRE2_NO_JIT

Par défaut, si un motif a été traité avec succès par pcre2_jit_compile(), le JIT est automatiquement utilisé lorsque pcre2_match() est appelé avec des options prises en charge par le JIT. Définir PCRE2_NO_JIT désactive l'utilisation du JIT ; cela force la correspondance à être effectuée par l'interpréteur.


PCRE2_NO_UTF_CHECK

Lorsque PCRE2_UTF est défini au moment de la compilation, la validité du sujet en tant que chaîne UTF est vérifiée sauf si PCRE2_NO_UTF_CHECK est passé à pcre2_match() ou si PCRE2_MATCH_INVALID_UTF a été passé à pcre2_compile(). Ce dernier cas particulier est discuté en détail dans la documentation pcre2unicode.

Dans le cas par défaut, si un décalage de départ non nul est donné, la vérification s'applique uniquement à la partie du sujet qui pourrait être inspectée pendant la correspondance, et il y a une vérification que le décalage de départ pointe vers la première unité de code d'un caractère ou vers la fin du sujet. S'il n'y a pas d'assertions lookbehind dans le motif, la vérification commence au décalage de départ. Sinon, elle commence à la longueur du plus long lookbehind avant le décalage de départ, ou au début du sujet s'il n'y a pas autant de caractères avant le décalage de départ. Notez que les séquences \b et \B sont des lookbehinds d'un caractère.

La vérification est effectuée avant toute autre opération, et un code d'erreur négatif est renvoyé si la vérification échoue. Il existe plusieurs codes d'erreur UTF pour chaque largeur d'unité de code, correspondant à différents problèmes avec la séquence d'unités de code. Des discussions sur la validité des chaînes UTF-8, UTF-16 et UTF-32 se trouvent dans la documentation pcre2unicode.

Si vous savez que votre sujet est valide et que vous souhaitez ignorer cette vérification pour des raisons de performance, vous pouvez définir l'option PCRE2_NO_UTF_CHECK lors de l'appel à pcre2_match(). Vous pourriez vouloir le faire pour le deuxième appel et les appels suivants à pcre2_match() si vous effectuez des appels répétés pour trouver plusieurs correspondances dans la même chaîne sujet.

Attention : Sauf si PCRE2_MATCH_INVALID_UTF a été défini au moment de la compilation, lorsque PCRE2_NO_UTF_CHECK est défini au moment de la correspondance, l'effet de passer une chaîne invalide comme sujet, ou une valeur invalide de startoffset, est indéfini. Votre programme peut planter, boucler indéfiniment ou donner des résultats incorrects.


PCRE2_PARTIAL_HARD
PCRE2_PARTIAL_SOFT

Ces options activent la fonctionnalité de correspondance partielle. Une correspondance partielle se produit si la fin de la chaîne sujet est atteinte avec succès, mais qu'il n'y a pas assez de caractères sujet pour compléter la correspondance. De plus, au moins un caractère doit avoir été inspecté ou le motif doit contenir un lookbehind, ou le motif doit pouvoir correspondre à une chaîne vide.

Si cette situation survient lorsque PCRE2_PARTIAL_SOFT (mais pas PCRE2_PARTIAL_HARD) est défini, la correspondance continue en testant les alternatives restantes. Ce n'est que si aucune correspondance complète ne peut être trouvée que PCRE2_ERROR_PARTIAL est renvoyé au lieu de PCRE2_ERROR_NOMATCH. En d'autres termes, PCRE2_PARTIAL_SOFT spécifie que l'appelant est prêt à gérer une correspondance partielle, mais uniquement si aucune correspondance complète ne peut être trouvée.

Si PCRE2_PARTIAL_HARD est défini, il remplace PCRE2_PARTIAL_SOFT. Dans ce cas, si une correspondance partielle est trouvée, pcre2_match() renvoie immédiatement PCRE2_ERROR_PARTIAL, sans considérer d'autres alternatives. En d'autres termes, lorsque PCRE2_PARTIAL_HARD est défini, une correspondance partielle est considérée comme plus importante qu'une correspondance complète alternative.

Une discussion plus détaillée sur les correspondances partielles et multi-segments, avec des exemples, se trouve dans la documentation pcre2partial.

GESTION DES NOUVELLES LIGNES LORS DE LA CORRESPONDANCE

Lorsque PCRE2 est compilé, une convention de nouvelle ligne par défaut est définie ; il s'agit généralement de la convention standard du système d'exploitation. La valeur par défaut peut être remplacée dans un contexte de compilation en appelant pcre2_set_newline(). Elle peut également être remplacée en commençant une chaîne de motif par, par exemple, (*CRLF), comme décrit dans la section sur les conventions de nouvelle ligne de la page pcre2pattern. Lors de la correspondance, le choix de la nouvelle ligne affecte le comportement des métacaractères point, circonflexe et dollar. Il peut également modifier la façon dont la position de début de correspondance est avancée après un échec de correspondance pour un motif non ancré.

Lorsque PCRE2_NEWLINE_CRLF, PCRE2_NEWLINE_ANYCRLF ou PCRE2_NEWLINE_ANY est défini comme convention de nouvelle ligne, et qu'une tentative de correspondance pour un motif non ancré échoue lorsque la position de départ actuelle se trouve sur une séquence CRLF, et que le motif ne contient aucune correspondance explicite pour les caractères CR ou LF, la position de correspondance est avancée de deux caractères au lieu d'un, c'est-à-dire après le CRLF.

La règle ci-dessus est un compromis qui fait fonctionner les cas les plus courants comme prévu. Par exemple, si le motif est .+A (et que l'option PCRE2_DOTALL n'est pas définie), il ne correspond pas à la chaîne "\r\nA" car, après avoir échoué au début, il saute à la fois le CR et le LF avant de retenter. Cependant, le motif [\r\n]A correspond à cette chaîne, car il contient une référence explicite CR ou LF, et avance donc d'un seul caractère après le premier échec.

Une correspondance explicite pour CR ou LF est soit une apparition littérale de l'un de ces caractères dans le motif, soit l'une des séquences d'échappement \r, \n ou leurs équivalents octaux ou hexadécimaux. Les correspondances implicites comme [^X] ne comptent pas, ni \s, même s'il inclut CR et LF parmi les caractères qu'il correspond.

Nonobstant ce qui précède, des effets anormaux peuvent encore se produire lorsque CRLF est une séquence de nouvelle ligne valide et que des échappements explicites \r ou \n apparaissent dans le motif.

COMMENT PCRE2_MATCH() RENVOIE UNE CHAÎNE ET DES SOUS-CHAÎNES CAPTURES

uint32_t pcre2_get_ovector_count(pcre2_match_data *match_data);

PCRE2_SIZE *pcre2_get_ovector_pointer(pcre2_match_data *match_data);

En général, un motif correspond à une certaine partie du sujet, et en outre, d'autres sous-chaînes du sujet peuvent être extraites par des parties entre parenthèses du motif. Suivant l'usage dans le livre de Jeffrey Friedl, cela est appelé "capture" dans ce qui suit, et l'expression "groupe de capture" (terminologie Perl) est utilisée pour un fragment d'un motif qui extrait une sous-chaîne. PCRE2 prend en charge plusieurs autres types de groupes entre parenthèses qui ne provoquent pas la capture de sous-chaînes. La fonction pcre2_pattern_info() peut être utilisée pour savoir combien de groupes de capture il y a dans un motif compilé.

Vous pouvez utiliser des fonctions auxiliaires pour accéder aux sous-chaînes capturées par numéro ou par nom, comme décrit dans les sections ci-dessous.

Alternativement, vous pouvez utiliser directement le vecteur de valeurs PCRE2_SIZE, appelé ovector, qui contient les décalages des chaînes capturées. Il fait partie du bloc de données de correspondance. La fonction pcre2_get_ovector_pointer() renvoie l'adresse de l'ovector, et pcre2_get_ovector_count() renvoie le nombre de paires de valeurs qu'il contient.

Dans l'ovector, la première de chaque paire de valeurs est définie sur le décalage de la première unité de code d'une sous-chaîne, et la seconde est définie sur le décalage de la première unité de code après la fin d'une sous-chaîne. Ces valeurs sont toujours des décalages d'unités de code, pas des décalages de caractères. C'est-à-dire qu'il s'agit de décalages d'octets dans la bibliothèque 8 bits, de décalages de 16 bits dans la bibliothèque 16 bits et de décalages de 32 bits dans la bibliothèque 32 bits.

Après une correspondance partielle (code de retour PCRE2_ERROR_PARTIAL), seule la première paire de décalages (c'est-à-dire ovector[0] et ovector[1]) est définie. Elle identifie la partie du sujet qui a été partiellement mise en correspondance. Voir la documentation pcre2partial pour plus de détails sur la correspondance partielle.

Après une correspondance complète réussie, la première paire de décalages identifie la portion de la chaîne sujet qui a été mise en correspondance par l'ensemble du motif. La paire suivante est utilisée pour la première sous-chaîne capturée, et ainsi de suite. La valeur renvoyée par pcre2_match() est supérieure de un au numéro de paire le plus élevé qui a été défini. Par exemple, si deux sous-chaînes ont été capturées, la valeur renvoyée est 3. S'il n'y a pas de sous-chaînes capturées, la valeur renvoyée par une correspondance réussie est 1, indiquant que seule la première paire de décalages a été définie.

Si un motif utilise la séquence d'échappement \K dans une assertion de lookahead positive, le début signalé d'une correspondance réussie peut être supérieur à la fin de la correspondance. Par exemple, si le motif (?=ab\K) est mis en correspondance avec "ab", les valeurs de décalage de début et de fin pour la correspondance sont 2 et 0.

Si un groupe de capture est mis en correspondance de manière répétée au cours d'une seule opération de correspondance, c'est la dernière partie du sujet qu'il a mise en correspondance qui est renvoyée.

Si l'ovector est trop petit pour contenir tous les décalages des sous-chaînes capturées, autant que possible est rempli, et la fonction renvoie une valeur de zéro. Si les sous-chaînes capturées ne sont pas d'intérêt, pcre2_match() peut être appelé avec un bloc de données de correspondance dont l'ovector a une taille minimale (c'est-à-dire une paire).

Il est possible que le groupe de capture numéro n+1 corresponde à une partie du sujet alors que le groupe n n'a pas été utilisé du tout. Par exemple, si la chaîne "abc" est mise en correspondance avec le motif (a|(z))(bc), le retour de la fonction est 4, et les groupes 1 et 3 sont mis en correspondance, mais le 2 ne l'est pas. Lorsque cela se produit, les deux valeurs des paires de décalages correspondant aux groupes non utilisés sont définies sur PCRE2_UNSET.

Les valeurs de décalage qui correspondent aux groupes non utilisés à la fin de l'expression sont également définies sur PCRE2_UNSET. Par exemple, si la chaîne "abc" est mise en correspondance avec le motif (abc)(x(yz)?)?, les groupes 2 et 3 ne sont pas mis en correspondance. Le retour de la fonction est 2, car le numéro de groupe de capture le plus élevé utilisé est 1. Les décalages pour les deuxième et troisième groupes de capture (en supposant que le vecteur est assez grand, bien sûr) sont définis sur PCRE2_UNSET.

Les éléments de l'ovector qui ne correspondent pas à des parenthèses de capture dans le motif ne sont jamais modifiés. C'est-à-dire, si un motif contient n parenthèses de capture, pas plus de ovector[0] à ovector[2n+1] ne sont définis par pcre2_match(). Les autres éléments conservent les valeurs qu'ils avaient précédemment. Après une tentative de correspondance échouée, les contenus de l'ovector sont inchangés.

AUTRES INFORMATIONS SUR UNE CORRESPONDANCE

PCRE2_SPTR pcre2_get_mark(pcre2_match_data *match_data);

PCRE2_SIZE pcre2_get_startchar(pcre2_match_data *match_data);

En plus des décalages dans l'ovector, d'autres informations sur une correspondance sont conservées dans le bloc de données de correspondance et peuvent être récupérées par les fonctions ci-dessus dans des circonstances appropriées. Si elles sont appelées à d'autres moments, le résultat est indéfini.

Après une correspondance réussie, une correspondance partielle (PCRE2_ERROR_PARTIAL) ou un échec de correspondance (PCRE2_ERROR_NOMATCH), un nom de marque peut être disponible. La fonction pcre2_get_mark() peut être appelée pour accéder à ce nom, qui peut être spécifié dans le motif par n'importe lequel des verbes de contrôle de retour sur trace, pas seulement (*MARK). La même fonction s'applique à tous les verbes. Elle renvoie un pointeur vers le nom terminé par un zéro, qui se trouve dans le motif compilé. Si aucun nom n'est disponible, NULL est renvoyé. La longueur du nom (excluant le zéro de terminaison) est stockée dans l'unité de code qui précède le nom. Vous devriez utiliser cette longueur au lieu de vous fier au zéro de terminaison si le nom peut contenir un zéro binaire.

Après une correspondance réussie, le nom renvoyé est le dernier nom de marque rencontré sur le chemin de correspondance à travers le motif. Les occurrences de verbes de retour sur trace sans nom ne comptent pas. Ainsi, par exemple, si le chemin de correspondance contient (*MARK:A)(*PRUNE), le nom "A" est renvoyé. Après un "pas de correspondance" ou une correspondance partielle, le dernier nom rencontré est renvoyé. Par exemple, considérez ce motif :


^(*MARK:A)((*MARK:B)a|b)c

Lorsqu'il correspond à "bc", le nom renvoyé est A. La marque B est "vue" dans la première branche du groupe, mais elle n'est pas sur le chemin de correspondance. D'autre part, lorsque ce motif échoue à correspondre à "bx", le nom renvoyé est B.

Avertissement : Par défaut, certaines optimisations de début de correspondance sont utilisées pour donner un résultat rapide de "pas de correspondance" dans certaines situations. Par exemple, si l'ancrage est supprimé du motif ci-dessus, il y a une vérification initiale de la présence de "c" dans le sujet avant d'exécuter le moteur de correspondance. Cette vérification échoue pour "bx", provoquant un échec de correspondance sans voir de marques. Vous pouvez désactiver les optimisations de début de correspondance en définissant l'option PCRE2_NO_START_OPTIMIZE pour pcre2_compile() ou en commençant le motif par (*NO_START_OPT).

Après une correspondance réussie, une correspondance partielle, ou l'une des erreurs UTF invalides (par exemple, PCRE2_ERROR_UTF8_ERR5), pcre2_get_startchar() peut être appelée. Après une correspondance réussie ou partielle, elle renvoie le décalage de l'unité de code du caractère où la correspondance a commencé. Pour une correspondance non partielle, cela peut être différent de la valeur de ovector[0] si le motif contient la séquence d'échappement \K. Après une correspondance partielle, cependant, cette valeur est toujours la même que ovector[0] car \K n'affecte pas le résultat d'une correspondance partielle.

Après un échec de vérification UTF, pcre2_get_startchar() peut être utilisé pour obtenir le décalage de l'unité de code du caractère UTF invalide. Les détails sont donnés dans la page pcre2unicode.

RETOURS D'ERREUR DE pcre2_match()

Si pcre2_match() échoue, elle renvoie un nombre négatif. Celui-ci peut être converti en une chaîne de texte en appelant la fonction pcre2_get_error_message() (voir ci-dessous "Obtenir un message d'erreur textuel"). Les codes d'erreur négatifs sont également renvoyés par d'autres fonctions et sont documentés avec elles. Les codes sont nommés dans le fichier d'en-tête. Si la vérification UTF est active et qu'une chaîne de sujet UTF invalide est détectée, l'un des nombreux codes d'erreur négatifs spécifiques à UTF est renvoyé. Les détails sont donnés dans la page pcre2unicode. Les erreurs suivantes peuvent être renvoyées par pcre2_match() :


PCRE2_ERROR_NOMATCH

La chaîne de sujet ne correspond pas au motif.


PCRE2_ERROR_PARTIAL

La chaîne de sujet ne correspond pas, mais elle a partiellement correspondé. Voir la documentation pcre2partial pour les détails sur la correspondance partielle.


PCRE2_ERROR_BADMAGIC

PCRE2 stocke un "nombre magique" de 4 octets au début du code compilé, pour détecter le cas où il reçoit un pointeur incorrect. C'est l'erreur renvoyée lorsque le nombre magique est absent.


PCRE2_ERROR_BADMODE

Cette erreur est donnée lorsqu'un motif compilé est passé à une fonction d'une bibliothèque de largeur d'unités de code différente, par exemple, un motif compilé par la bibliothèque 8 bits est passé à une fonction de bibliothèque 16 bits ou 32 bits.


PCRE2_ERROR_BADOFFSET

La valeur de startoffset était supérieure à la longueur du sujet.


PCRE2_ERROR_BADOPTION

Un bit non reconnu était défini dans l'argument options.


PCRE2_ERROR_BADUTFOFFSET

La séquence d'unités de code UTF passée comme sujet a été vérifiée et s'est avérée valide (l'option PCRE2_NO_UTF_CHECK n'était pas définie), mais la valeur de startoffset ne pointait pas vers le début d'un caractère UTF ou la fin du sujet.


PCRE2_ERROR_CALLOUT

Cette erreur n'est jamais générée par pcre2_match() elle-même. Elle est fournie pour être utilisée par les fonctions de rappel (callout) qui souhaitent amener pcre2_match() ou pcre2_callout_enumerate() à renvoyer un code d'erreur distinctif. Voir la documentation pcre2callout pour les détails.


PCRE2_ERROR_DEPTHLIMIT

La limite de profondeur de retour sur trace imbriquée a été atteinte.


PCRE2_ERROR_HEAPLIMIT

La limite du tas (heap) a été atteinte.


PCRE2_ERROR_INTERNAL

Une erreur interne inattendue s'est produite. Cette erreur pourrait être causée par un bug dans PCRE2 ou par l'écrasement du motif compilé.


PCRE2_ERROR_JIT_STACKLIMIT

Cette erreur est renvoyée lorsqu'un motif qui a été étudié avec succès à l'aide de JIT est en cours de correspondance, mais que la mémoire disponible pour la pile de traitement juste-à-temps n'est pas suffisamment grande. Voir la documentation pcre2jit pour plus de détails.


PCRE2_ERROR_MATCHLIMIT

La limite de retour sur trace des correspondances a été atteinte.


PCRE2_ERROR_NOMEMORY

La mémoire du tas est utilisée pour se souvenir des points de retour sur trace. Cette erreur est donnée lorsque la fonction d'allocation mémoire (par défaut ou personnalisée) échoue. Notez qu'une erreur différente, PCRE2_ERROR_HEAPLIMIT, est donnée si la quantité de mémoire nécessaire dépasse la limite du tas. PCRE2_ERROR_NOMEMORY est également renvoyé si PCRE2_COPY_MATCHED_SUBJECT est défini et que l'allocation mémoire échoue.


PCRE2_ERROR_NULL

Soit l'argument code, subject, ou match_data a été passé en tant que NULL.


PCRE2_ERROR_RECURSELOOP

Cette erreur est renvoyée lorsque pcre2_match() détecte une boucle de récursion dans le motif. Plus précisément, cela signifie que soit le motif entier, soit un groupe de capture a été appelé de manière récursive pour la deuxième fois à la même position dans la chaîne de sujet. Certains motifs simples qui pourraient faire cela sont détectés et échouent à la compilation, mais des cas plus compliqués, en particulier les récursions mutuelles entre deux groupes différents, ne peuvent pas être détectés avant que la correspondance ne soit tentée.

OBTENIR UN MESSAGE D'ERREUR TEXTUEL

int pcre2_get_error_message(int errorcode, PCRE2_UCHAR *buffer,
  PCRE2_SIZE bufflen);

Un message texte pour un code d'erreur de n'importe quelle fonction PCRE2 (compilation, correspondance ou auxiliaire) peut être obtenu en appelant pcre2_get_error_message(). Le code est passé comme premier argument, les deux arguments restants spécifiant un tampon d'unités de code et sa longueur en unités de code, dans lequel le message texte est placé. Le message est renvoyé en unités de code de la largeur appropriée pour la bibliothèque utilisée.

Le message renvoyé est terminé par un zéro final, et la fonction renvoie le nombre d'unités de code utilisées, excluant le zéro final. Si le numéro d'erreur est inconnu, le code d'erreur négatif PCRE2_ERROR_BADDATA est renvoyé. Si le tampon est trop petit, le message est tronqué (mais toujours avec un zéro final), et le code d'erreur négatif PCRE2_ERROR_NOMEMORY est renvoyé. Aucun des messages n'est très long ; une taille de tampon de 120 unités de code est suffisante.

ITÉRATION SUR TOUTES LES CORRESPONDANCES

int pcre2_next_match(pcre2_match_data *match_data,
  PCRE2_SIZE *pstart_offset, uint32_t *poptions);

Une tâche courante pour les applications est d'implémenter un comportement de correspondance "global", par exemple, remplacer toutes les correspondances dans le sujet ; diviser le sujet sur toutes les correspondances ; ou simplement compter le nombre de correspondances. La fonction pcre2_next_match() aide à cette tâche en fournissant les paramètres appropriés pour la prochaine tentative de correspondance (disponible depuis PCRE2 10.46).

D'abord, une tentative de correspondance doit être effectuée en utilisant l'une des fonctions de correspondance (pcre2_match(), pcre2_dfa_match(), ou pcre2_jit_match()). Ensuite, pcre2_next_match() peut être appelée, en fournissant le même paramètre match_data.

Elle renvoie 0 ("faux") s'il n'est pas nécessaire de faire une autre tentative de correspondance, ou 1 ("vrai") si une autre correspondance doit être tentée. Renvoi de 1 n'implique pas qu'il y a une autre correspondance, seulement qu'une autre correspondance doit être tentée (qui pourrait renvoyer PCRE2_ERROR_NOMATCH).

Les *pstart_offset et *poptions sont définis si la fonction renvoie 1. Le *pstart_offset doit être passé à la prochaine tentative de correspondance directement, et le *poptions doit être passé à la prochaine tentative de correspondance en le combinant avec les options de correspondance de l'application à l'aide de OR.

Il y a du code qui montre comment faire cela dans le programme d'exemple pcre2demo. Le schéma général est :

  uint32_t app_options = ...;
  uint32_t global_options = 0;
  PCRE2_SIZE start_offset = 0;
  while (1)
    {
    int rc = pcre2_match(re, subject, subject_len, start_offset,
                         app_options | global_options, match_data,
                         match_context);
    if (rc == PCRE2_ERROR_NOMATCH) break; /* pas de correspondance, et plus de tentatives */
    if (rc < 0) { ... exit }
    ...gérer la correspondance
    if (!pcre2_next_match(match_data, &start_offset, &global_options))
      break; /* plus de tentatives */
    }

Les garanties fournies par pcre2_next_match() sont que l'offset de début avancera, de sorte que la boucle se terminera définitivement. Les conditions qui assurent cela sont que soit : (a) pcre2_next_match() renvoie 0 (faux) ; soit (b) l'*pstart_offset renvoyé est strictement supérieur à l'offset de début précédent ; soit (c) si la correspondance précédente était une correspondance réussie de la chaîne vide, alors l'*pstart_offset renvoyé est égal à l'ovector[1] précédent, et *poptions sera défini sur PCRE2_NOTEMPTY_ATSTART pour empêcher une autre correspondance vide d'être renvoyée.

Une boucle implémentée comme ci-dessus se terminera toujours, à moins qu'il y ait un bug dans PCRE2. À titre de mesure de "programmation défensive", il est encouragé aux applications d'ajouter une assertion ou une vérification pour interrompre leur boucle si elle ne progresse pas (et de signaler le problème comme un bug).

Si une application n'utilise pas le drapeau PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK, alors chaque correspondance est "bien élevée" et satisfait :


start_offset <= ovector[0] <= ovector[1].

Dans ce cas, les correspondances trouvées par pcre2_match() avec pcre2_next_match() seront triées, non chevauchantes (pouvant se toucher) et sans doublons.

Sinon, si PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK est utilisé, les garanties sont considérablement plus faibles. Nous ne garantissons pas que les correspondances avanceront toujours : seulement que l'offset de début avancera. Les correspondances trouvées par pcre2_match() avec pcre2_next_match() seront une séquence finie (car pcre2_next_match() assure que l'offset de début avance, donc la recherche se terminera). Les correspondances peuvent cependant être chevauchantes, contenir des doublons et (dans des exemples vraiment pathologiques) ne pas même être triées par ovector[0]. De plus, chaque correspondance peut se terminer avant de commencer (ovector[1] < ovector[0]). Nous recommandons aux applications de ne pas définir PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK.

EXTRACTION DES SOUS-CHAÎNES CAPTURÉES PAR NUMÉRO

int pcre2_substring_length_bynumber(pcre2_match_data *match_data,
  uint32_t number, PCRE2_SIZE *length);

int pcre2_substring_copy_bynumber(pcre2_match_data *match_data,
  uint32_t number, PCRE2_UCHAR *buffer,
  PCRE2_SIZE *bufflen);

int pcre2_substring_get_bynumber(pcre2_match_data *match_data,
  uint32_t number, PCRE2_UCHAR **bufferptr,
  PCRE2_SIZE *bufflen);

void pcre2_substring_free(PCRE2_UCHAR *buffer);

Les sous-chaînes capturées peuvent être accessibles directement en utilisant l'ovector comme décrit ci-dessus. Par commodité, des fonctions auxiliaires sont fournies pour extraire les sous-chaînes capturées sous forme de nouvelles chaînes distinctes et terminées par un zéro. Une sous-chaîne qui contient un zéro binaire est correctement extraite et se voit ajouter un zéro à la fin, mais le résultat n'est bien sûr pas une chaîne C.

Les fonctions de cette section identifient les sous-chaînes par leur numéro. Le numéro zéro fait référence à la sous-chaîne entièrement capturée, les numéros supérieurs faisant référence aux sous-chaînes capturées par des groupes entre parenthèses. Après une correspondance partielle, seule la sous-chaîne zéro est disponible. Une tentative d'extraction de toute autre sous-chaîne renvoie l'erreur PCRE2_ERROR_PARTIAL. La section suivante décrit des fonctions similaires pour extraire les sous-chaînes capturées par nom.

Si un motif utilise la séquence d'échappement \K dans une assertion lookahead positive, le début signalé d'une correspondance réussie peut être supérieur à la fin de la correspondance. Par exemple, si le motif (?=ab\K) est appliqué à "ab", les valeurs d'offset de début et de fin pour la correspondance sont 2 et 0. Dans cette situation, l'appel de ces fonctions avec un numéro de sous-chaîne zéro extrait une chaîne vide de longueur zéro.

Vous pouvez trouver la longueur en unités de code d'une sous-chaîne capturée sans l'extraire en appelant pcre2_substring_length_bynumber(). Le premier argument est un pointeur vers le bloc de données de correspondance, le second est le numéro du groupe, et le troisième est un pointeur vers une variable dans laquelle la longueur est placée. Si vous voulez juste savoir si la sous-chaîne a été capturée ou non, vous pouvez passer le troisième argument comme NULL.

La fonction pcre2_substring_copy_bynumber() copie une sous-chaîne capturée dans un tampon fourni, tandis que pcre2_substring_get_bynumber() la copie dans une nouvelle mémoire, obtenue en utilisant la même fonction d'allocation mémoire qui a été utilisée pour le bloc de données de correspondance. Les deux premiers arguments de ces fonctions sont un pointeur vers le bloc de données de correspondance et un numéro de groupe de capture.

Les arguments finaux de pcre2_substring_copy_bynumber() sont un pointeur vers le tampon et un pointeur vers une variable qui contient sa longueur en unités de code. Celle-ci est mise à jour pour contenir le nombre réel d'unités de code utilisées pour la sous-chaîne extraite, à l'exclusion du zéro de terminaison.

Pour pcre2_substring_get_bynumber(), le troisième et le quatrième arguments pointent vers des variables qui sont mises à jour avec un pointeur vers la nouvelle mémoire et le nombre d'unités de code qui composent la sous-chaîne, excluant à nouveau le zéro de terminaison. Lorsque la sous-chaîne n'est plus nécessaire, la mémoire doit être libérée en appelant pcre2_substring_free().

La valeur de retour de toutes ces fonctions est zéro en cas de succès, ou un code d'erreur négatif. Si la correspondance du motif a échoué, le code d'échec de la correspondance est renvoyé. Si un numéro de sous-chaîne supérieur à zéro est utilisé après une correspondance partielle, PCRE2_ERROR_PARTIAL est renvoyé. Les autres codes d'erreur possibles sont :


PCRE2_ERROR_NOMEMORY

Le tampon était trop petit pour pcre2_substring_copy_bynumber(), ou la tentative d'obtention de mémoire a échoué pour pcre2_substring_get_bynumber().


PCRE2_ERROR_NOSUBSTRING

Il n'y a pas de sous-chaîne avec ce numéro dans le motif, c'est-à-dire que le numéro est supérieur au nombre de parenthèses de capture.


PCRE2_ERROR_UNAVAILABLE

Le numéro de sous-chaîne, bien que n'étant pas supérieur au nombre de captures dans le motif, est supérieur au nombre d'emplacements dans l'ovector, de sorte que la sous-chaîne n'a pas pu être capturée.


PCRE2_ERROR_UNSET

La sous-chaîne n'a pas participé à la correspondance. Par exemple, si le motif est (abc)|(def) et le sujet est "def", et que l'ovector contient au moins deux emplacements de capture, la sous-chaîne numéro 1 est non définie.

EXTRACTION D'UNE LISTE DE TOUTES LES SOUS-CHAÎNES CAPTURÉES

int pcre2_substring_list_get(pcre2_match_data *match_data,
  PCRE2_UCHAR ***listptr, PCRE2_SIZE **lengthsptr);

void pcre2_substring_list_free(PCRE2_UCHAR **list);

La fonction pcre2_substring_list_get() extrait toutes les sous-chaînes disponibles et construit une liste de pointeurs vers celles-ci. Elle construit également (facultativement) une seconde liste contenant leurs longueurs (en unités de code), excluant un zéro de terminaison qui leur est ajouté. Tout cela est fait dans un seul bloc de mémoire obtenu en utilisant la même fonction d'allocation mémoire qui a été utilisée pour obtenir le bloc de données de correspondance.

Cette fonction ne doit être appelée qu'après une correspondance réussie. Si elle est appelée après une correspondance partielle, le code d'erreur PCRE2_ERROR_PARTIAL est renvoyé.

L'adresse du bloc mémoire est renvoyée via listptr, qui est également le début de la liste des pointeurs de chaînes. La fin de la liste est marquée par un pointeur NULL. L'adresse de la liste des longueurs est renvoyée via lengthsptr. Si vos chaînes ne contiennent pas de zéros binaires et que vous n'avez donc pas besoin des longueurs, vous pouvez fournir NULL comme argument lengthsptr pour désactiver la création d'une liste de longueurs. Le rendement de la fonction est zéro si tout s'est bien passé, ou PCRE2_ERROR_NOMEMORY si le bloc mémoire n'a pas pu être obtenu. Lorsque la liste n'est plus nécessaire, elle doit être libérée en appelant pcre2_substring_list_free().

Si cette fonction rencontre une sous-chaîne non définie, ce qui peut se produire lorsque le groupe de capture numéro n+1 correspond à une partie du sujet, mais que le groupe n n'a pas été utilisé du tout, elle renvoie une chaîne vide. Cela peut être distingué d'une véritable sous-chaîne de longueur zéro en inspectant l'offset approprié dans l'ovector, qui contient PCRE2_UNSET pour les sous-chaînes non définies, ou en appelant pcre2_substring_length_bynumber().

  PCRE2_SPTR name, PCRE2_SIZE *length);

int pcre2_substring_copy_byname(pcre2_match_data *match_data,

Pour extraire une sous-chaîne par nom, vous devez d'abord trouver son numéro associé. Par exemple, pour ce motif :


(a+)b(?<xxx>\d+)...

le numéro du groupe de capture appelé "xxx" est 2. Si le nom est connu pour être unique (PCRE2_DUPNAMES n'a pas été défini), vous pouvez trouver le numéro à partir du nom en appelant pcre2_substring_number_from_name(). Le premier argument est le motif compilé, et le second est le nom. Le rendement de la fonction est le numéro du groupe, PCRE2_ERROR_NOSUBSTRING s'il n'y a pas de groupe portant ce nom, ou PCRE2_ERROR_NOUNIQUESUBSTRING s'il y a plus d'un groupe portant ce nom. Étant donné le numéro, vous pouvez extraire la sous-chaîne directement de l'ovector, ou utiliser l'une des fonctions "bynumber" décrites ci-dessus.

Par commodité, il existe également des fonctions "byname" qui correspondent aux fonctions "bynumber", la seule différence étant que le deuxième argument est un nom au lieu d'un numéro. Si PCRE2_DUPNAMES est défini et qu'il existe des noms dupliqués, ces fonctions parcourent tous les groupes portant le nom donné et renvoient la sous-chaîne capturée du premier groupe nommé qui est défini.

S'il n'y a pas de groupes portant le nom donné, PCRE2_ERROR_NOSUBSTRING est renvoyé. Si tous les groupes portant le nom ont des numéros supérieurs au nombre d'emplacements dans l'ovector, PCRE2_ERROR_UNAVAILABLE est renvoyé. S'il y a au moins un groupe avec un emplacement dans l'ovector, mais qu'aucun groupe n'est trouvé comme étant défini, PCRE2_ERROR_UNSET est renvoyé.

Attention : Si le motif utilise la fonctionnalité (?| pour définir plusieurs groupes de capture avec le même numéro, comme décrit dans la section sur les numéros de groupe dupliqués de la page pcre2pattern, vous ne pouvez pas utiliser de noms pour distinguer les différents groupes de capture, car les noms ne sont pas

incluse dans le code compilé. Le processus de correspondance n'utilise que des nombres. Pour cette raison, l'utilisation de noms différents pour des groupes portant le même numéro provoque une erreur à la compilation.

CRÉATION D'UNE NOUVELLE CHAÎNE AVEC DES SUBSTITUTIONS

int pcre2_substitute(const pcre2_code *code, PCRE2_SPTR subject,
  PCRE2_SIZE length, PCRE2_SIZE startoffset,
  uint32_t options, pcre2_match_data *match_data,
  pcre2_match_context *mcontext, PCRE2_SPTR replacement,
  PCRE2_SIZE rlength, PCRE2_UCHAR *outputbuffer,
  PCRE2_SIZE *outlengthptr);

Cette fonction appelle éventuellement pcre2_match() puis effectue une copie de la chaîne sujet dans outputbuffer, en remplaçant les parties qui ont correspondu par la chaîne replacement, dont la longueur est fournie dans rlength, qui peut être donnée comme PCRE2_ZERO_TERMINATED pour une chaîne terminée par un zéro. Comme cas spécial, si replacement est NULL et rlength est zéro, le remplacement est supposé être une chaîne vide. Si rlength est non nul, une erreur se produit si replacement est NULL.

Il existe une option (voir PCRE2_SUBSTITUTE_REPLACEMENT_ONLY ci-dessous) pour retourner uniquement la ou les chaînes de remplacement. L'action par défaut est d'effectuer une seule substitution si le motif correspond, mais il existe une option qui demande plusieurs substitutions (voir PCRE2_SUBSTITUTE_GLOBAL ci-dessous).

En cas de succès, pcre2_substitute() retourne le nombre de substitutions effectuées. Cela peut être zéro si aucune correspondance n'est trouvée, et n'est jamais supérieur à un, sauf si PCRE2_SUBSTITUTE_GLOBAL est défini. Une valeur négative est retournée si une erreur est détectée.

Les correspondances dans lesquelles un élément \K dans un lookahead dans le motif provoque la fin de la correspondance avant son début ne sont pas prises en charge et entraînent un retour d'erreur. Pour les remplacements globaux, les correspondances dans lesquelles \K dans un lookbehind provoque le début de la correspondance avant le point atteint lors de l'itération précédente ne sont pas non plus prises en charge. (Ces cas ne sont possibles que si le motif a été compilé avec l'option de rétrocompatibilité PCRE2_EXTRA_ALLOW_LOOKAROUND_BSK.)

Les sept premiers arguments de pcre2_substitute() sont les mêmes que pour pcre2_match(), à l'exception des options de correspondance partielle qui ne sont pas autorisées, et match_data peut être passé comme NULL, auquel cas un bloc de données de correspondance est obtenu et libéré dans cette fonction, en utilisant les fonctions de gestion de mémoire du contexte de correspondance, si fournies, ou sinon celles utilisées pour allouer la mémoire du code compilé.

Si match_data n'est pas NULL et que PCRE2_SUBSTITUTE_MATCHED n'est pas défini, le bloc fourni est utilisé pour tous les appels à pcre2_match(), et son contenu ultérieur est le résultat du dernier appel effectué en interne par pcre2_substitute() à la fonction de correspondance. Pour les remplacements globaux, il s'agira toujours d'une erreur de non-correspondance. Le contenu de l'ovector dans le bloc de données de correspondance peut ou non avoir été modifié.

En plus des options habituelles pour pcre2_match(), un certain nombre d'options supplémentaires peuvent être définies dans l'argument options de pcre2_substitute(). L'une de ces options est PCRE2_SUBSTITUTE_MATCHED. Lorsqu'elle est définie, un bloc match_data externe doit être fourni, et il doit déjà avoir été utilisé pour un appel externe à pcre2_match() (ou pcre2_jit_match()) avec le même motif, pointeur sujet, longueur effective du sujet, décalage de départ et arguments d'option de correspondance (des options spécifiques à la substitution peuvent être ajoutées à l'argument options). Si l'un de ces paramètres est modifié, pcre2_substitute() retourne une erreur. Les données du bloc match_data (code de retour, vecteur d'offsets) sont utilisées pour la première substitution au lieu d'appeler pcre2_match() depuis pcre2_substitute(). Cela permet à une application de vérifier une correspondance avant de choisir de substituer, sans avoir à répéter la correspondance.

Si le contenu du tampon sujet est modifié entre pcre2_match() et un appel à pcre2_substitute() avec PCRE2_SUBSTITUTE_MATCHED, le comportement est dangereux ; en particulier, dans ce cas, PCRE2 ne peut pas garantir que les décalages dans l'ovector pointent vers le début des caractères (avec une entrée codée en UTF).

Le contenu du bloc de données de correspondance fourni en externe n'est pas modifié lorsque PCRE2_SUBSTITUTE_MATCHED est défini, et le bloc de correspondance est donc autorisé pour une utilisation dans un autre appel utilisant PCRE2_SUBSTITUTE_MATCHED. Si PCRE2_SUBSTITUTE_GLOBAL est également défini, pcre2_match() est appelé après la première substitution pour vérifier les correspondances ultérieures, mais cela est fait à l'aide d'un bloc de données de correspondance obtenu en interne, laissant ainsi toujours le bloc externe inchangé.

L'argument code n'est pas utilisé pour la correspondance avant la première substitution lorsque PCRE2_SUBSTITUTE_MATCHED est défini, mais il doit être fourni, même lorsque PCRE2_SUBSTITUTE_GLOBAL n'est pas défini, car il contient des informations telles que le réglage UTF et le nombre de parenthèses de capture dans le motif.

Lors de l'utilisation de PCRE2_SUBSTITUTE_MATCHED, vous ne devez pas modifier la chaîne sujet entre l'appel précédent à pcre2_match() et pcre2_substitute(), car la substitution suppose que l'ovector passé est compatible avec la chaîne sujet. Bien que PCRE2 vérifie que le sujet est un pointeur vers le même tampon, il ne peut en général pas vérifier si le contenu du tampon a changé. Par exemple, si le tampon sujet est modifié d'une chaîne UTF-8 valide à une autre chaîne valide, de même longueur en unités de code, les décalages de l'ovector ne sont plus garantis de pointer vers le début d'un caractère. Attention, avec PCRE2_SUBSTITUTE_MATCHED en mode UTF, la chaîne sujet n'est pas réanalysée pour sa validité UTF lorsque pcre2_substitute() l'utilise pour la première fois.

L'action par défaut de pcre2_substitute() est de retourner une copie de la chaîne sujet avec les sous-chaînes correspondantes remplacées. Cependant, si PCRE2_SUBSTITUTE_REPLACEMENT_ONLY est défini, seuls les sous-chaînes de remplacement sont retournées. Dans le cas global, plusieurs remplacements sont concaténés dans le tampon de sortie. Les appels de substitution (voir ci-dessous) peuvent être utilisés pour les séparer si nécessaire.

L'argument outlengthptr de pcre2_substitute() doit pointer vers une variable contenant la longueur, en unités de code, du tampon de sortie. Si la fonction réussit, la valeur est mise à jour pour contenir la longueur en unités de code de la nouvelle chaîne, en excluant le zéro final qui est automatiquement ajouté.

Si la fonction échoue, la valeur définie via outlengthptr dépend du type d'erreur. Pour les erreurs de syntaxe dans la chaîne de remplacement, la valeur est le décalage dans la chaîne de remplacement où l'erreur a été détectée. Pour les autres erreurs, la valeur est PCRE2_UNSET par défaut. Cela inclut le cas où le tampon de sortie est trop petit, sauf si PCRE2_SUBSTITUTE_OVERFLOW_LENGTH est défini.

PCRE2_SUBSTITUTE_OVERFLOW_LENGTH modifie le comportement lorsque le tampon de sortie est trop petit. L'action par défaut est de retourner PCRE2_ERROR_NOMEMORY immédiatement. Si cette option est définie, cependant, pcre2_substitute() continue à simuler la correspondance et la substitution (sans écrire quoi que ce soit, bien sûr) afin de calculer la taille du tampon nécessaire, qui inclura l'espace supplémentaire pour le NUL de terminaison. Cette valeur est renvoyée via la variable outlengthptr, le résultat de la fonction étant toujours PCRE2_ERROR_NOMEMORY.

Passer une taille de tampon de zéro est un moyen autorisé de savoir quelle quantité de mémoire est nécessaire pour une substitution donnée. Cependant, cela implique que toute l'opération est effectuée deux fois. Selon l'application, il peut être plus efficace d'allouer un grand tampon et de libérer l'excédent par la suite, au lieu d'utiliser PCRE2_SUBSTITUTE_OVERFLOW_LENGTH.

La chaîne de remplacement, interprétée comme une chaîne UTF en mode UTF, est vérifiée pour sa validité UTF, sauf si PCRE2_NO_UTF_CHECK est défini. Une chaîne de remplacement UTF invalide provoque un retour immédiat avec le code d'erreur UTF approprié.

Si PCRE2_SUBSTITUTE_LITERAL est défini, la chaîne de remplacement n'est interprétée d'aucune manière. Par défaut, cependant, le caractère dollar est un caractère d'échappement qui peut spécifier l'insertion de caractères de groupes de capture et de noms de (*MARK) ou d'autres verbes de contrôle dans le motif. Le dollar est le seul caractère d'échappement (la barre oblique inverse est traitée comme littérale). Les formes suivantes sont reconnues :


$$ insère un caractère dollar
$n ou ${n} insère le contenu du groupe n
$0 ou $& insère la sous-chaîne entière correspondante
$` insère la sous-chaîne qui précède la correspondance
$' insère la sous-chaîne qui suit la correspondance
$_ insère la chaîne d'entrée entière
$+ insère le groupe de capture de numéro le plus élevé qui a correspondu
$*MARK ou ${*MARK} insère un nom de verbe de contrôle

Soit un numéro de groupe, soit un nom de groupe peut être donné pour n, par exemple $2 ou $NOM. Les accolades ne sont nécessaires que si le caractère suivant serait interprété comme faisant partie du numéro ou du nom. Le numéro peut être zéro pour inclure la chaîne entière correspondante. Par exemple, si le motif a(b)c est mis en correspondance avec "=abc=" et la chaîne de remplacement "+$1$0$1+", le résultat est "=+babcb+=".

La forme JavaScript $<nom>, où les chevrons font partie de la syntaxe, est également reconnue pour les noms de groupes, mais pas pour les numéros de groupe ou *MARK.

$*MARK insère le nom du dernier verbe de contrôle de backtracking rencontré sur le chemin de correspondance qui a un nom. (*MARK) doit toujours inclure un nom, mais les autres verbes n'ont pas besoin. Par exemple, dans le cas de (*MARK:A)(*PRUNE), le nom inséré est "A", mais pour (*MARK:A)(*PRUNE:B), le nom pertinent est "B". Cette facilité peut être utilisée pour effectuer des substitutions simultanées simples, comme le montre cet exemple pcre2test :


/(*MARK:pomme)pomme|(*MARK:orange)citron/g,remplacer=${*MARK}
pomme citron
2: pomme orange

PCRE2_SUBSTITUTE_GLOBAL fait en sorte que la fonction itère sur la chaîne sujet, remplaçant chaque sous-chaîne correspondante. Si cette option n'est pas définie, seule la première sous-chaîne correspondante est remplacée. La recherche de correspondances s'effectue dans la chaîne sujet d'origine (c'est-à-dire que les remplacements précédents ne l'affectent pas). L'itération est implémentée en avançant la valeur startoffset pour chaque recherche, qui reçoit toujours la chaîne sujet entière. Si une limite d'offset est définie dans le contexte de correspondance, la recherche s'arrête lorsque cette limite est atteinte.

Étant donné que les substitutions globales appliquent le motif de manière répétée à la chaîne sujet, et itèrent toujours sur des correspondances non chevauchantes, les substitutions effectuées par pcre2_substitute() ne correspondent pas et ne substituent pas le texte à l'intérieur des chaînes de remplacement elles-mêmes (pas de substitution récursive/itérative). Cependant, les applications peuvent facilement implémenter d'autres stratégies de remplacement alternatives, telles que le remplacement itératif, puis la correspondance et renant sur le résultat. La boucle de remplacement à l'intérieur de pcre2_substitute() est simple et peut être émulée dans le code client en allouant un tampon, en recherchant les correspondances dans une boucle, et en appelant pcre2_substitute() avec PCRE2_SUBSTITUTE_REPLACEMENT_ONLY et PCRE2_SUBSTITUTE_MATCHED, et sans PCRE2_SUBSTITUTE_GLOBAL.

Vous pouvez limiter l'effet d'une substitution globale à une partie de la chaîne sujet en définissant soit ou les deux de startoffset et une limite d'offset. Voici un exemple de pcre2test :


/B/g,replace=!,use_offset_limit
ABC ABC ABC ABC\=offset=3,offset_limit=12
2: ABC A!C A!C ABC

Lorsque l'on continue avec des substitutions globales après avoir trouvé une sous-chaîne de longueur zéro, une tentative de trouver une correspondance non vide au même décalage est effectuée. Si cela échoue, le décalage est avancé d'un caractère sauf lorsque CRLF est une séquence de nouvelle ligne valide et que les deux caractères suivants sont CR, LF. Dans ce cas, le décalage est avancé de deux caractères.

PCRE2_SUBSTITUTE_UNKNOWN_UNSET fait que les références à des groupes de capture qui n'apparaissent pas dans le motif sont traitées comme des groupes non définis. Cette option doit être utilisée avec précaution, car elle signifie qu'une faute de frappe dans un nom ou un numéro de groupe ne génère plus l'erreur PCRE2_ERROR_NOSUBSTRING.

PCRE2_SUBSTITUTE_UNSET_EMPTY fait que les groupes de capture non définis (y compris les groupes inconnus lorsque PCRE2_SUBSTITUTE_UNKNOWN_UNSET est défini) sont traités comme des chaînes vides lors de leur insertion comme décrit ci-dessus. Si cette option n'est pas définie, une tentative d'insertion d'un groupe non défini provoque l'erreur PCRE2_ERROR_UNSET. Cette option n'influence pas la syntaxe de substitution étendue décrite ci-dessous.

PCRE2_SUBSTITUTE_EXTENDED applique un traitement supplémentaire à la chaîne de remplacement. Sans cette option, seul le caractère dollar est spécial, et seules les formes d'insertion de groupe listées ci-dessus sont valides. Lorsque PCRE2_SUBSTITUTE_EXTENDED est défini, plusieurs choses changent :

Premièrement, le backslash dans une chaîne de remplacement est interprété comme un caractère d'échappement. Les formes habituelles telles que \x{ddd} peuvent être utilisées pour spécifier des codes de caractères particuliers, et un backslash suivi de n'importe quel caractère non alphanumérique met ce caractère entre guillemets. La mise entre guillemets étendue peut être codée à l'aide de \Q...\E, exactement comme dans les chaînes de motif. Les échappements \b et \v sont interprétés comme les caractères backspace et tabulation verticale, respectivement.

L'interprétation d'un backslash suivi d'un ou plusieurs chiffres est la même que dans un motif, ce qui, en Perl, présente certaines ambiguïtés. Les détails sont donnés dans la page pcre2pattern.

La forme Python \g<n>, où les chevrons font partie de la syntaxe et n est un nom ou un numéro de groupe, est reconnue comme un moyen alternatif d'insérer le contenu d'un groupe, par exemple \g<3>.

Il existe également quatre séquences d'échappement pour forcer la casse des lettres insérées. Le forçage de la casse s'applique à tous les caractères insérés, y compris ceux des groupes de capture et les lettres dans les séquences mises entre guillemets \Q...\E. Le mécanisme d'insertion a trois états : pas de forçage de casse, forçage en majuscules, et forçage en minuscules. Les séquences d'échappement changent l'état actuel : \U et \L passent au forçage en majuscules ou en minuscules, respectivement, et \E (lorsqu'il ne termine pas une séquence entre guillemets \Q) revient à l'absence de forçage de casse. Les séquences \u et \l forcent le caractère suivant (s'il s'agit d'une lettre) en majuscule ou en minuscule, respectivement, puis l'état revient automatiquement à l'absence de forçage de casse.

Cependant, si \u est immédiatement suivi de \L ou si \l est immédiatement suivi de \U, la casse du caractère suivant est forcée par la première séquence d'échappement, et les caractères suivants par la seconde. Cela fournit une installation de "mise en majuscules initiales" qui peut être appliquée aux captures de groupe. Par exemple, si le groupe 1 a capturé "heLLo", la chaîne de remplacement "\u\L$1" devient "Hello".

Si PCRE2_UTF ou PCRE2_UCP a été défini lors de la compilation du motif, les propriétés Unicode sont utilisées pour forcer la casse des caractères dont les points de code sont supérieurs à 127. Cependant, seule la mise en minuscule simple, telle que déterminée par le fichier Unicode CaseFolding.txt, est prise en charge. PCRE2 ne prend pas en charge les règles de mise en minuscule spécifiques à une langue, telles que l'utilisation de sigmas minuscules différents au milieu et à la fin des mots (tels que définis dans le fichier Unicode SpecialCasing.txt).

Notez que les séquences de forçage de casse telles que \U...\E ne s'imbriquent pas. Par exemple, le résultat du traitement de "\Uaa\LBB\Ecc\E" est "AAbbcc" ; le \E final n'a aucun effet. Notez également que les options PCRE2_ALT_BSUX et PCRE2_EXTRA_ALT_BSUX ne s'appliquent pas aux chaînes de remplacement.

L'effet final de la définition de PCRE2_SUBSTITUTE_EXTENDED est d'ajouter plus de flexibilité à la substitution de groupe de capture. La syntaxe est similaire à celle utilisée par Bash :


${n:-chaîne}
${n:+chaîne1:chaîne2}

Comme dans le cas simple, n peut être un numéro de groupe ou un nom. La première forme spécifie une valeur par défaut. Si le groupe n est défini, sa valeur est insérée ; sinon, la chaîne est développée et le résultat est inséré. La seconde forme spécifie des chaînes qui sont développées et insérées lorsque le groupe n est défini ou non défini, respectivement. La première forme n'est qu'un raccourci pratique pour


${n:+${n}:chaîne}

Le backslash peut être utilisé pour échapper les deux-points et les accolades fermantes dans les chaînes de remplacement. Un changement de l'état de forçage de la casse à l'intérieur d'une chaîne de remplacement reste en vigueur par la suite, comme le montre cet exemple de pcre2test :


/(some)?(body)/substitute_extended,replace=${1:+\U:\L}HeLLo
body
1: hello
somebody
1: HELLO

L'option PCRE2_SUBSTITUTE_UNSET_EMPTY n'affecte pas ces substitutions étendues. Cependant, PCRE2_SUBSTITUTE_UNKNOWN_UNSET fait que les groupes inconnus dans les formes de syntaxe étendue sont traités comme non définis.

Si PCRE2_SUBSTITUTE_LITERAL est défini, PCRE2_SUBSTITUTE_UNKNOWN_UNSET, PCRE2_SUBSTITUTE_UNSET_EMPTY, et PCRE2_SUBSTITUTE_EXTENDED sont sans importance et sont ignorés.

Erreurs de substitution

En cas d'erreur, pcre2_substitute() renvoie un code d'erreur négatif. À l'exception de PCRE2_ERROR_NOMATCH (qui n'est jamais retourné), les erreurs de pcre2_match() sont directement renvoyées.

PCRE2_ERROR_NOSUBSTRING est renvoyé pour une insertion de sous-chaîne inexistante, sauf si PCRE2_SUBSTITUTE_UNKNOWN_UNSET est défini.

PCRE2_ERROR_UNSET est renvoyé pour une insertion de sous-chaîne non définie (y compris une sous-chaîne inconnue lorsque PCRE2_SUBSTITUTE_UNKNOWN_UNSET est défini) lorsque la syntaxe simple (non étendue) est utilisée et que PCRE2_SUBSTITUTE_UNSET_EMPTY n'est pas définie.

PCRE2_ERROR_NOMEMORY est renvoyé si le tampon de sortie n'est pas assez grand. Si l'option PCRE2_SUBSTITUTE_OVERFLOW_LENGTH est définie, la taille du tampon nécessaire est renvoyée via outlengthptr. Notez que cela ne se produit pas par défaut.

PCRE2_ERROR_NULL est renvoyé si PCRE2_SUBSTITUTE_MATCHED est défini mais que l'argument match_data est NULL, ou si les arguments subject ou replacement sont NULL. Pour des raisons de compatibilité ascendante, une exception est faite pour l'argument replacement si l'argument rlength est également 0.

PCRE2_ERROR_BADREPLACEMENT est utilisé pour diverses erreurs de syntaxe dans la chaîne de remplacement, avec des erreurs plus spécifiques étant PCRE2_ERROR_BADREPESCAPE (séquence d'échappement invalide), PCRE2_ERROR_REPMISSINGBRACE (accolade fermante non trouvée), PCRE2_ERROR_BADSUBSTITUTION (erreur de syntaxe dans la substitution de groupe étendue), et PCRE2_ERROR_BADSUBSPATTERN (la correspondance du motif s'est terminée avant de commencer ou la correspondance a commencé plus tôt que la position actuelle dans le sujet, ce qui peut se produire si \K est utilisé dans une assertion lookaround).

Comme pour toutes les erreurs PCRE2, un message textuel décrivant l'erreur peut être obtenu en appelant la fonction pcre2_get_error_message() (voir "Obtenir un message d'erreur textuel" ci-dessus).

Appels de retour de substitution

int pcre2_set_substitute_callout(pcre2_match_context *mcontext,
  int (*callout_function)(pcre2_substitute_callout_block *, void *),
  void *callout_data);

La fonction pcre2_set_substitute_callout() peut être utilisée pour spécifier une fonction d'appel de retour pour pcre2_substitute(). Ces informations sont passées dans un contexte de correspondance. La fonction d'appel de retour est appelée après que chaque substitution a été traitée, mais elle peut empêcher le remplacement de se produire.

La fonction d'appel de retour n'est pas appelée pour les substitutions simulées qui se produisent à la suite de l'option PCRE2_SUBSTITUTE_OVERFLOW_LENGTH. Dans ce mode, lorsque le traitement de la substitution dépasse l'espace tampon fourni par l'appelant, le traitement continue en comptant les unités de code. La simulation ne peut pas remplir le bloc d'appel de retour, et donc la simulation est pessimiste quant à la taille du tampon requise. Le plus grand des deux, la substitution acceptée ou rejetée, est rapporté comme la taille requise. Par conséquent, la longueur du tampon renvoyé peut être une surestimation (sans appel de retour de substitution, c'est normalement une mesure exacte).

Le premier argument de la fonction d'appel de retour est un pointeur vers une structure de bloc d'appel de retour de substitution, qui contient les champs suivants, pas nécessairement dans cet ordre :


uint32_t version;
uint32_t subscount;
PCRE2_SPTR input;
PCRE2_SPTR output;
PCRE2_SIZE *ovector;
uint32_t oveccount;
PCRE2_SIZE output_offsets[2];

Le champ version contient le numéro de version du format du bloc. La version actuelle est 0. Le numéro de version augmentera à l'avenir si des champs sont ajoutés, mais l'intention est de ne jamais supprimer aucun des champs existants.

Le champ subscount est le numéro de la correspondance actuelle. Il vaut 1 pour le premier appel de retour, 2 pour le second, et ainsi de suite. Les pointeurs input et output sont des copies des valeurs passées à pcre2_substitute().

Le champ ovector pointe vers l'ovector, qui contient le résultat de la correspondance la plus récente. Le champ oveccount contient le nombre de paires définies dans l'ovector, et est toujours supérieur à zéro.

Le vecteur output_offsets contient les décalages du remplacement dans la chaîne de sortie. Celui-ci a déjà été traité pour les substitutions dollar et (si demandé) backslash comme décrit ci-dessus.

Le second argument de la fonction d'appel de retour est la valeur passée comme callout_data lorsque la fonction a été enregistrée. La valeur renvoyée par la fonction d'appel de retour est interprétée comme suit :

Si la valeur est zéro, le remplacement est accepté et, si PCRE2_SUBSTITUTE_GLOBAL est défini, le traitement continue avec la recherche de la correspondance suivante. Si la valeur n'est pas zéro, le remplacement actuel n'est pas accepté. Si le

la valeur est supérieure à zéro, le traitement se poursuit lorsque PCRE2_SUBSTITUTE_GLOBAL est défini. Sinon (la valeur est inférieure à zéro ou PCRE2_SUBSTITUTE_GLOBAL n'est pas défini), le reste de l'entrée est copié vers la sortie et l'appel à pcre2_substitute() se termine, renvoyant le nombre de correspondances jusqu'à présent.

Appels de rappel de substitution de cas

int pcre2_set_substitute_case_callout(pcre2_match_context *mcontext,
  PCRE2_SIZE (*callout_function)(PCRE2_SPTR, PCRE2_SIZE,
                                 PCRE2_UCHAR *, PCRE2_SIZE,
                                 int, void *),
  void *callout_data);

La fonction pcre2_set_substitute_case_callout() peut être utilisée pour spécifier une fonction d'appel de rappel que pcre2_substitute() utilisera lors des transformations de casse. Cela n'affecte pas le comportement insensible à la casse lors d'une correspondance, mais uniquement les transformations visibles par l'utilisateur lors du traitement d'une substitution telle que :


pcre2_substitute(..., "\\U$1", ...)

Les transformations de casse par défaut appliquées par PCRE2 sont raisonnablement complètes et, en mode UTF ou UCP, effectuent les transformations de casse simples et invariantes par locale comme spécifié par Unicode. Ceci est adapté aux procédures internes (invisibles) d'équivalence de casse utilisées pendant la mise en correspondance des motifs, mais une application peut souhaiter utiliser un traitement plus sophistiqué et sensible à la locale pour les transformations de substitution visibles par l'utilisateur.

Un exemple d'implémentation de la callout_function utilisant la bibliothèque ICU serait :

    PCRE2_SIZE
    icu_case_callout(
      PCRE2_SPTR input, PCRE2_SIZE input_len,
      PCRE2_UCHAR *output, PCRE2_SIZE output_cap,
      int to_case, void *data_ptr)
    {
      UErrorCode err = U_ZERO_ERROR;
      int32_t r = to_case == PCRE2_SUBSTITUTE_CASE_LOWER
        ? u_strToLower(output, output_cap, input, input_len, NULL, &err)
        : to_case == PCRE2_SUBSTITUTE_CASE_UPPER
        ? u_strToUpper(output, output_cap, input, input_len, NULL, &err)
        : u_strToTitle(output, output_cap, input, input_len, &first_char_only,
                       NULL, &err);
      if (U_FAILURE(err)) return (~(PCRE2_SIZE)0);
      return r;
    }

Les premier et deuxième arguments de la fonction d'appel de casse sont la chaîne Unicode à transformer.

Les troisième et quatrième arguments sont le tampon de sortie et sa capacité.

Le cinquième est l'une des constantes PCRE2_SUBSTITUTE_CASE_LOWER, PCRE2_SUBSTITUTE_CASE_UPPER ou PCRE2_SUBSTITUTE_CASE_TITLE_FIRST. PCRE2_SUBSTITUTE_CASE_LOWER et PCRE2_SUBSTITUTE_CASE_UPPER sont passés à l'appel de rappel pour indiquer que la casse de l'intégralité de l'entrée de l'appel de rappel doit être transformée. PCRE2_SUBSTITUTE_CASE_TITLE_FIRST est passé pour indiquer que seul le premier caractère ou glyphe doit être transformé en casse de titre Unicode et le reste en casse basse Unicode (notez que la casse de titre utilise parfois des propriétés Unicode pour mettre en casse chaque mot dans une chaîne ; mais PCRE2 demande que seul le caractère initial soit mis en casse de titre).

Le sixième argument est le callout_data fourni à pcre2_set_substitute_case_callout().

La chaîne résultante dans le tampon de destination peut être plus grande ou plus petite que l'entrée, si les règles de casse fusionnent ou divisent des caractères. La valeur de retour est la longueur requise pour la chaîne de sortie. Si un tampon de taille suffisante a été fourni à l'appel de rappel, le résultat doit être écrit dans le tampon et le nombre d'unités de code renvoyé. Si le résultat ne rentre pas dans le tampon fourni, la capacité requise doit être renvoyée et PCRE2 n'utilisera pas le tampon de sortie. PCRE2 fournit des tampons d'entrée et de sortie qui se chevauchent, de sorte que l'appel de rappel doit prendre en charge cela par un tampon interne approprié.

Alternativement, si l'appel de rappel souhaite indiquer une erreur, il peut renvoyer (~(PCRE2_SIZE)0). Dans ce cas, pcre2_substitute() échouera immédiatement avec l'erreur PCRE2_ERROR_REPLACECASE.

Lorsqu'un appel de rappel de casse est combiné avec l'option PCRE2_SUBSTITUTE_OVERFLOW_LENGTH, il existe des situations où pcre2_substitute() renverra une sous-estimation de la taille du tampon requis. Si vous appelez pcre2_substitute() une fois avec PCRE2_SUBSTITUTE_OVERFLOW_LENGTH, et que le tampon d'entrée est trop petit pour que la chaîne de remplacement soit construite, alors au lieu d'appeler l'appel de rappel de casse, pcre2_substitute() estimera la taille du tampon requis. Le deuxième appel doit également passer PCRE2_SUBSTITUTE_OVERFLOW_LENGTH, car ce deuxième appel n'est pas garanti de réussir non plus, si l'appel de rappel de casse nécessite plus d'espace tampon que prévu. L'appelant doit effectuer des tentatives répétées dans une boucle.

NOMS DE GROUPES DE CAPTURAGE DUPLIQUES

int pcre2_substring_nametable_scan(const pcre2_code *code,
  PCRE2_SPTR name, PCRE2_SPTR *first, PCRE2_SPTR *last);

Lorsqu'un motif est compilé avec l'option PCRE2_DUPNAMES, les noms des groupes de capture ne sont pas obligés d'être uniques. Les noms dupliqués sont toujours autorisés pour les groupes ayant le même numéro, créés en utilisant la fonctionnalité (?| . En effet, si de tels groupes sont nommés, ils doivent utiliser les mêmes noms.

Normalement, les motifs qui utilisent des noms dupliqués sont tels que, lors d'une seule correspondance, seul l'un de chaque ensemble de groupes de noms identiques participe. Un exemple est montré dans la documentation de pcre2pattern.

Lorsque des doublons sont présents, pcre2_substring_copy_byname() et pcre2_substring_get_byname() renvoient la première sous-chaîne correspondant au nom donné qui est définie. Ce n'est que si aucune n'est définie que PCRE2_ERROR_UNSET est renvoyé. La fonction pcre2_substring_number_from_name() renvoie l'erreur PCRE2_ERROR_NOUNIQUESUBSTRING lorsqu'il existe des noms dupliqués.

Si vous souhaitez obtenir les détails complets de toutes les sous-chaînes capturées pour un nom donné, vous devez utiliser la fonction pcre2_substring_nametable_scan(). Le premier argument est le motif compilé, et le second est le nom. Si les troisième et quatrième arguments sont NULL, la fonction renvoie un numéro de groupe pour un nom unique, ou PCRE2_ERROR_NOUNIQUESUBSTRING sinon.

Lorsque les troisième et quatrième arguments ne sont pas NULL, ils doivent pointer vers des variables qui sont mises à jour par la fonction. Après son exécution, ils pointeront vers la première et la dernière entrée de la table nom-numéro pour le nom donné, et la fonction renverra la longueur de chaque entrée en unités de code. Dans les deux cas, PCRE2_ERROR_NOSUBSTRING est renvoyé s'il n'y a pas d'entrées pour le nom donné.

Le format de la table des noms est décrit ci-dessus dans la section intitulée Informations sur un motif. Étant donné toutes les entrées pertinentes pour le nom, vous pouvez extraire chacun de leurs numéros, et par conséquent les données capturées.

TROUVER TOUTES LES CORRESPONDANCES POSSIBLES À UNE POSITION

La fonction de correspondance traditionnelle utilise un algorithme similaire à celui de Perl, qui s'arrête lorsqu'il trouve la première correspondance à un point donné du sujet. Si vous souhaitez trouver toutes les correspondances possibles, ou la correspondance la plus longue possible à une position donnée, envisagez plutôt d'utiliser la fonction de correspondance alternative (voir ci-dessous). Si vous ne pouvez pas utiliser la fonction alternative, vous pouvez la contourner en utilisant le mécanisme d'appel de rappel, qui est décrit dans la documentation de pcre2callout.

Ce que vous devez faire est d'insérer un appel de rappel juste à la fin du motif. Lorsque votre fonction d'appel de rappel est appelée, extrayez et sauvegardez la sous-chaîne actuellement mise en correspondance. Ensuite, renvoyez 1, ce qui force pcre2_match() à revenir en arrière et à essayer d'autres alternatives. Finalement, lorsqu'il n'y a plus de correspondances, pcre2_match() produira PCRE2_ERROR_NOMATCH.

int pcre2_dfa_match(const pcre2_code *code, PCRE2_SPTR subject,

La fonction pcre2_dfa_match() est appelée pour faire correspondre une chaîne sujet à un motif compilé, en utilisant un algorithme de correspondance qui parcourt la chaîne sujet une seule fois (sans compter les assertions lookaround), et ne revient pas en arrière (sauf lors du traitement des assertions lookaround). Cela a des caractéristiques différentes de l'algorithme normal et n'est pas compatible avec Perl. Certaines des fonctionnalités des motifs PCRE2 ne sont pas prises en charge. Néanmoins, il y a des moments où ce type de correspondance peut être utile. Pour une discussion des deux algorithmes de correspondance, et une liste des fonctionnalités que pcre2_dfa_match() ne prend pas en charge, voir la documentation de pcre2matching.

Les arguments de la fonction pcre2_dfa_match() sont les mêmes que pour pcre2_match(), plus deux arguments supplémentaires. L'ovector dans le bloc de données de correspondance est utilisé différemment, et cela est décrit ci-dessous. Les autres arguments communs sont utilisés de la même manière que pour pcre2_match(), de sorte que leur description n'est pas répétée ici.

Les deux arguments supplémentaires fournissent un espace de travail pour la fonction. Le vecteur d'espace de travail doit contenir au moins 20 éléments. Il est utilisé pour suivre plusieurs chemins à travers l'arbre du motif. Plus d'espace de travail est nécessaire pour les motifs et les sujets où il y a beaucoup de correspondances potentielles.

Voici un exemple d'appel simple à pcre2_dfa_match() :


int wspace[20];
pcre2_match_data *md = pcre2_match_data_create(4, NULL);
int rc = pcre2_dfa_match(
re, /* résultat de pcre2_compile() */
"some string", /* la chaîne sujet */
11, /* la longueur de la chaîne sujet */
0, /* commencer à l'offset 0 dans le sujet */
0, /* options par défaut */
md, /* le bloc de données de correspondance */
NULL, /* un contexte de correspondance ; NULL signifie utiliser les valeurs par défaut */
wspace, /* vecteur d'espace de travail */
20); /* nombre d'éléments (PAS la taille en octets) */

PCRE2 NATIVE API AUXILIARY MATCH FUNCTIONS

Les fonctions auxiliaires de correspondance sont celles qui effectuent des opérations de mise en correspondance mais ne sont pas la fonction principale de mise en correspondance principale. Elles sont décrites ci-dessous.

PCRE2_DFA_MATCH

La fonction pcre2_dfa_match() est une fonction de mise en correspondance alternative qui utilise l'algorithme de recherche de toutes les correspondances possible, basé sur un automate fini déterministe (DFA). Elle est plus lente que l'algorithme de recherche d'une seule correspondance (voir pcre2matching(3)) mais elle peut trouver des correspondances qui sont négligées par l'autre algorithme, et elle peut retrouver des correspondances partielles. Il existe une discussion plus détaillée sur la correspondance DFA et sa relation avec la correspondance à deux segments dans le manuel pcre2partial(3).

Les options disponibles sont définies comme suit :

PCRE2_PARTIAL_HARD
Lorsque ce drapeau est défini, si la fin du sujet est atteinte alors qu'il reste au moins une possibilité de correspondance qui nécessite des caractères supplémentaires, la fonction renvoie PCRE2_ERROR_PARTIAL. Ceci se produit même si des correspondances complètes ont déjà été trouvées. La partie de la chaîne qui a été inspectée lors de la découverte de la correspondance partielle la plus longue est définie comme la première chaîne correspondante dans le vecteur ovector.
PCRE2_PARTIAL_SOFT
Lorsque ce drapeau est défini, si la fin du sujet est atteinte, qu'aucune correspondance complète n'a été trouvée, mais qu'il reste au moins une possibilité de correspondance, le code de retour PCRE2_ERROR_NOMATCH est converti en PCRE2_ERROR_PARTIAL. La partie de la chaîne qui a été inspectée lors de la découverte de la correspondance partielle la plus longue est définie comme la première chaîne correspondante dans le vecteur ovector.

Ces options fonctionnent de manière similaire à celles utilisées pour pcre2_match(), mais les détails sont légèrement différents. Lorsque PCRE2_PARTIAL_HARD est défini pour pcre2_dfa_match(), il renvoie PCRE2_ERROR_PARTIAL si la fin du sujet est atteinte et qu'il reste au moins une possibilité de correspondance qui nécessite des caractères supplémentaires. Cela se produit même si des correspondances complètes ont déjà été trouvées. Lorsque PCRE2_PARTIAL_SOFT est défini, le code de retour PCRE2_ERROR_NOMATCH est converti en PCRE2_ERROR_PARTIAL si la fin du sujet est atteinte, qu'aucune correspondance complète n'a été trouvée, mais qu'il reste au moins une possibilité de correspondance. La partie de la chaîne qui a été inspectée lors de la découverte de la correspondance partielle la plus longue est définie comme la première chaîne correspondante dans les deux cas. Il y a une discussion plus détaillée sur la correspondance partielle et multi-segments, avec des exemples, dans la documentation de pcre2partial(3).


PCRE2_DFA_SHORTEST

La définition de l'option PCRE2_DFA_SHORTEST amène l'algorithme de mise en correspondance à s'arrêter dès qu'il a trouvé une correspondance. En raison de la façon dont fonctionne l'algorithme alternatif, il s'agit nécessairement de la correspondance la plus courte possible au premier point de correspondance possible dans la chaîne sujet.


PCRE2_DFA_RESTART

Lorsque pcre2_dfa_match() renvoie une correspondance partielle, il est possible de l'appeler à nouveau, avec des caractères sujet supplémentaires, et de la faire continuer avec la même correspondance. L'option PCRE2_DFA_RESTART demande cette action ; lorsqu'elle est définie, les options workspace et wscount doivent faire référence au même vecteur qu'auparavant car les données sur la correspondance jusqu'à présent y sont laissées après une correspondance partielle. Il y a plus de discussion sur cette fonctionnalité dans la documentation de pcre2partial(3).

Retours réussis de pcre2_dfa_match()

Lorsque pcre2_dfa_match() réussit, il peut avoir trouvé plus d'une sous-chaîne dans le sujet. Notez cependant que toutes les correspondances d'une seule exécution de la fonction commencent au même point dans le sujet. Les correspondances les plus courtes sont toutes des sous-chaînes initiales des correspondances les plus longues. Par exemple, si le motif


<.*>

est mis en correspondance avec la chaîne


This is <something> <something else> <something further> no more

les trois chaînes correspondantes sont


<something> <something else> <something further>
<something> <something else>
<something>

En cas de succès, le résultat de la fonction est un nombre supérieur à zéro, qui est le nombre de sous-chaînes correspondantes. Les décalages des sous-chaînes sont renvoyés dans le vecteur ovector, et peuvent être extraits par numéro de la même manière que pour pcre2_match(), mais les numéros n'ont aucun lien avec les groupes de capture qui peuvent exister dans le motif, car la mise en correspondance DFA ne prend pas en charge la capture.

Les appels aux fonctions utilitaires qui extraient des sous-chaînes par nom renvoient l'erreur PCRE2_ERROR_DFA_UFUNC (fonction non prise en charge) si elles sont utilisées après une mise en correspondance DFA. Les fonctions utilitaires qui extraient des sous-chaînes par numéro ne renvoient jamais PCRE2_ERROR_NOSUBSTRING.

Les chaînes correspondantes sont stockées dans le vecteur ovector dans l'ordre inverse de leur longueur ; c'est-à-dire que la chaîne la plus longue est la première. S'il y avait trop de correspondances pour tenir dans le vecteur ovector, le résultat de la fonction est zéro, et le vecteur est rempli avec les correspondances les plus longues.

NOTE : L'optimisation "auto-possessification" de PCRE2 s'applique généralement aux répétitions de caractères à la fin d'un motif (ainsi qu'en interne). Par exemple, le motif "a\\d+" est compilé comme s'il s'agissait de "a\\d++". Pour la mise en correspondance DFA, cela signifie qu'une seule correspondance possible est trouvée. Si vous souhaitez réellement plusieurs correspondances dans de tels cas, utilisez soit une répétition non gourmande comme "a\\d+?", soit définissez l'option PCRE2_NO_AUTO_POSSESS lors de la compilation.

Retours d'erreur de pcre2_dfa_match()

La fonction pcre2_dfa_match() renvoie un nombre négatif en cas d'échec. Beaucoup d'erreurs sont les mêmes que pour pcre2_match(), comme décrit ci-dessus. Il existe en outre les erreurs suivantes qui sont spécifiques à pcre2_dfa_match() :


PCRE2_ERROR_DFA_UITEM

Ce retour est donné si pcre2_dfa_match() rencontre un élément dans le motif qu'il ne prend pas en charge, par exemple, l'utilisation de \C dans un mode UTF ou une référence arrière.


PCRE2_ERROR_DFA_UCOND

Ce retour est donné si pcre2_dfa_match() rencontre un élément de condition qui utilise une référence arrière pour la condition, ou un test de récursion dans un groupe de capture spécifique. Ceux-ci ne sont pas pris en charge.


PCRE2_ERROR_DFA_UINVALID_UTF

Ce retour est donné si pcre2_dfa_match() est appelé pour un motif qui a été compilé avec PCRE2_MATCH_INVALID_UTF. Ceci n'est pas pris en charge pour la mise en correspondance DFA.


PCRE2_ERROR_DFA_WSSIZE

Ce retour est donné si pcre2_dfa_match() manque d'espace dans le vecteur workspace.


PCRE2_ERROR_DFA_RECURSE

Lorsqu'une récursion ou un appel de sous-routine est traité, la fonction de mise en correspondance s'appelle récursivement, en utilisant une mémoire privée pour le vecteur ovector et l'workspace. Cette erreur est donnée si le vecteur ovector interne n'est pas assez grand. Cela devrait être extrêmement rare, car un vecteur de taille 1000 est utilisé.


PCRE2_ERROR_DFA_BADRESTART

Lorsque pcre2_dfa_match() est appelé avec l'option PCRE2_DFA_RESTART, des contrôles de plausibilité sont effectués sur le contenu du vecteur workspace, qui devrait contenir des données sur la correspondance partielle précédente. Si l'un de ces contrôles échoue, cette erreur est donnée.

NOM

pcre2api — Interface de la bibliothèque PCRE2

SYNTAXE

#include <pcre2.h>

DESCRIPTION

Cette page de manuel décrit l'interface de programmation d'application (API) de la bibliothèque PCRE2, qui implémente la logique des expressions régulières compatibles avec Perl. PCRE2 est une bibliothèque qui peut être utilisée par des programmes informatiques pour vérifier si une chaîne de caractères correspond à un modèle d'expression régulière, et pour extraire des sous-chaînes de la chaîne qui correspondent à des parties du modèle. Elle peut également être utilisée pour modifier des chaînes en utilisant des substitutions basées sur des expressions régulières.

Les fonctions de cette bibliothèque sont divisées en plusieurs catégories :

  • Compilation d'expressions régulières.
  • Exécution de la correspondance d'expressions régulières.
  • Gestion des informations sur les correspondances.
  • Traitement des erreurs.
  • Manipulation des chaînes avec des substitutions.

Les fonctions qui effectuent une correspondance sont :

  • pcre2_match() : La fonction principale de correspondance.
  • pcre2_dfa_match() : Une variante DFA de la correspondance.
  • pcre2_jit_match() : Une variante JIT (Just-In-Time) de la correspondance.

Les fonctions pour obtenir des informations sur une correspondance ou des sous-chaînes capturées sont :

  • pcre2_get_ovector_pointer() : Obtient le pointeur vers le tableau des vecteurs de correspondance.
  • pcre2_get_capture_count() : Obtient le nombre de groupes de capture.
  • pcre2_substring_list_get_size() : Obtient la taille de la liste des sous-chaînes capturées.
  • pcre2_substring_get_byname() : Obtient une sous-chaîne capturée par son nom.
  • pcre2_substring_get_bynumber() : Obtient une sous-chaîne capturée par son numéro.
  • pcre2_substring_free() : Libère la mémoire allouée pour une sous-chaîne.
  • pcre2_get_error_message() : Obtient un message d'erreur textuel.
  • pcre2_match_data_create_from_pattern() : Crée une structure de données pour les résultats de la correspondance.
  • pcre2_match_data_free() : Libère la mémoire allouée pour les données de correspondance.
  • pcre2_get_mark() : Obtient la position du marqueur dans le modèle.

Les fonctions pour effectuer des substitutions sont :

  • pcre2_substitute() : La fonction principale de substitution.

Les fonctions pour gérer les noms de groupes de capture :

  • pcre2_pattern_info() : Obtient diverses informations sur le modèle compilé, y compris les noms de groupes de capture.

FONCTIONS

COMMENT PCRE2_MATCH() RETOURNE UNE CHAÎNE ET DES SOUS-CHAÎNES CAPTURÉES

La fonction pcre2_match() recherche une correspondance du modèle compilé dans la chaîne d'entrée. Si une correspondance est trouvée, elle retourne 0. Sinon, elle retourne un code d'erreur.

Les informations sur la correspondance sont retournées via un pointeur vers une structure pcre2_match_data. Cette structure contient un tableau appelé ovector (pour offsets vector) qui stocke les décalages de début et de fin de chaque sous-chaîne capturée. L'élément ovector[0] et ovector[1] contiennent les décalages de la correspondance entière. Les éléments suivants contiennent les décalages des groupes de capture, dans l'ordre où ils apparaissent dans le modèle.

La taille du tableau ovector est déterminée par le nombre de groupes de capture dans le modèle. Si un modèle n'a pas de groupes de capture, seul ovector[0] et ovector[1] sont utilisés.

AUTRES INFORMATIONS SUR UNE CORRESPONDANCE

En plus des informations sur les sous-chaînes capturées, pcre2_match() peut retourner d'autres informations, selon les options utilisées lors de la compilation du modèle et lors de l'appel de la fonction de correspondance. Ces informations peuvent inclure :

  • La position du marqueur dans le modèle (utilisé pour les assertions de type (*MARK)).
  • La longueur de la correspondance.
  • Des informations sur les correspondances multiples à la même position (utilisé avec des motifs alternatifs).

Ces informations sont accessibles via des fonctions dédiées, telles que pcre2_get_mark().

RETours d'erreur de pcre2_match()

Si pcre2_match() ne trouve pas de correspondance, elle retourne un code d'erreur qui indique pourquoi la correspondance a échoué. Ces codes d'erreur sont des entiers positifs et sont définis dans le fichier d'en-tête pcre2.h. Certains codes d'erreur courants incluent :

  • PCRE2_ERROR_NOMATCH : Aucune correspondance n'a été trouvée.
  • PCRE2_ERROR_PARTIAL : La chaîne d'entrée a été complètement parcourue, mais la correspondance n'est pas terminée (par exemple, un motif se terminant par .*).
  • PCRE2_ERROR_NULL : Un pointeur nul a été passé à la fonction.
  • PCRE2_ERROR_BADOFFSET : Un décalage invalide a été spécifié.

Il existe également des codes d'erreur liés à des problèmes internes de la bibliothèque, tels que des erreurs de mémoire.

OBTENIR UN MESSAGE D'ERREUR TEXTUEL

Pour obtenir une description textuelle plus lisible d'un code d'erreur retourné par pcre2_match() ou d'autres fonctions PCRE2, vous pouvez utiliser la fonction pcre2_get_error_message(). Cette fonction prend un code d'erreur et un tampon de caractères comme arguments, et remplit le tampon avec une chaîne décrivant l'erreur.

int pcre2_get_error_message(int errorcode, PCRE2_UCHAR *buffer, size_t buffersize);

errorcode est le code d'erreur retourné par la fonction PCRE2.

buffer est un pointeur vers le tampon dans lequel le message d'erreur sera écrit.

buffersize est la taille du tampon.

ITÉRER SUR TOUTES LES CORRESPONDANCES

Pour trouver toutes les occurrences d'un modèle dans une chaîne, vous pouvez utiliser une boucle. Commencez par appeler pcre2_match() avec un décalage de départ de 0. Si une correspondance est trouvée, utilisez le décalage de fin de la correspondance comme nouveau décalage de départ pour l'appel suivant de pcre2_match(). Continuez ce processus jusqu'à ce que pcre2_match() retourne PCRE2_ERROR_NOMATCH.

Il est important de gérer correctement les décalages, en particulier avec les correspondances vides (longueur zéro) pour éviter les boucles infinies. Si une correspondance a une longueur de zéro, le décalage de départ pour l'appel suivant doit être incrémenté d'au moins un.

EXTRAIRE LES SOUS-CHAÎNES CAPTURÉES PAR NUMÉRO

Une fois qu'une correspondance a été trouvée et que les informations de correspondance sont disponibles dans la structure pcre2_match_data, vous pouvez extraire les sous-chaînes capturées par leur numéro. Le groupe de capture numéro 0 correspond à la correspondance entière. Les groupes de capture suivants sont numérotés dans l'ordre où ils apparaissent dans le modèle.

La fonction pcre2_substring_get_bynumber() peut être utilisée pour cela :

PCRE2_SPTR pcre2_substring_get_bynumber(const pcre2_match_data *match_data, PCRE2_SIZE index, PCRE2_SPTR *start, PCRE2_SIZE *length);

index est le numéro du groupe de capture à extraire.

start est un pointeur vers une variable où sera stocké le décalage de début de la sous-chaîne.

length est un pointeur vers une variable où sera stockée la longueur de la sous-chaîne.

La fonction retourne un pointeur vers la sous-chaîne correspondante dans la chaîne d'origine. Vous devrez libérer la mémoire allouée pour la sous-chaîne avec pcre2_substring_free() lorsque vous n'en avez plus besoin.

EXTRAIRE UNE LISTE DE TOUTES LES SOUS-CHAÎNES CAPTURÉES

Pour obtenir une liste de toutes les sous-chaînes capturées, vous pouvez utiliser la fonction pcre2_substring_list_get_size() pour déterminer combien de sous-chaînes sont disponibles, puis itérer en utilisant pcre2_substring_get_bynumber(). Alternativement, vous pouvez utiliser des fonctions spécifiques (si disponibles) pour obtenir directement une liste.

EXTRAIRE LES SOUS-CHAÎNES CAPTURÉES PAR NOM

Si votre modèle utilise des groupes de capture nommés (par exemple, (?<name>...)), vous pouvez extraire ces sous-chaînes par leur nom en utilisant la fonction pcre2_substring_get_byname() :

PCRE2_SPTR pcre2_substring_get_byname(const pcre2_match_data *match_data, PCRE2_SPTR name, PCRE2_SIZE *start, PCRE2_SIZE *length);

name est le nom du groupe de capture à rechercher.

Les arguments start et length fonctionnent de la même manière que pour pcre2_substring_get_bynumber().

La fonction retourne un pointeur vers la sous-chaîne correspondante. Vous devrez utiliser pcre2_substring_free() pour libérer la mémoire associée.

CRÉER UNE NOUVELLE CHAÎNE AVEC DES SUBSTITUTIONS

La fonction pcre2_substitute() est utilisée pour remplacer les parties d'une chaîne qui correspondent à un modèle par une autre chaîne. Elle prend en compte les références aux sous-chaînes capturées dans la chaîne de remplacement (par exemple, $1, ${name}).

int pcre2_substitute(const pcre2_code *code, PCRE2_SPTR subject, PCRE2_SIZE subject_length, PCRE2_SIZE start_offset, uint32_t options, pcre2_match_data *match_data, PCRE2_SPTR replacement, PCRE2_SIZE replacement_length, PCRE2_SPTR *output_string, PCRE2_SIZE *output_length);

Elle retourne le nombre de substitutions effectuées ou un code d'erreur.

NOMS DE GROUPES DE CAPTURE DUPLIQUÉS

PCRE2 autorise les noms de groupes de capture dupliqués. Si plusieurs groupes ont le même nom, les fonctions comme pcre2_substring_get_byname() peuvent retourner la correspondance du premier groupe rencontré avec ce nom, ou il peut y avoir des options pour spécifier quel groupe récupérer.

Pour obtenir des informations détaillées sur les groupes de capture, y compris leurs noms et numéros, utilisez la fonction pcre2_pattern_info() avec les codes d'information appropriés.

TROUVER TOUTES LES CORRESPONDANCES POSSIBLES À UNE POSITION

Certains motifs peuvent avoir plusieurs correspondances possibles à la même position dans la chaîne d'entrée (par exemple, (a|b)c peut correspondre à ac ou bc si le texte est ac). PCRE2 peut être configuré pour trouver toutes ces correspondances alternatives.

La fonction pcre2_match() peut retourner un code d'erreur PCRE2_ERROR_RECURSION ou PCRE2_ERROR_ENDOFINPUT dans certains cas liés à des correspondances multiples. L'utilisation de pcre2_dfa_match() peut être plus adaptée pour explorer toutes les possibilités à une position donnée.

FAIRE CORRESPONDRE UN MODÈLE : LA FONCTION ALTERNATIVE

Outre pcre2_match(), PCRE2 fournit les fonctions pcre2_dfa_match() et pcre2_jit_match(). pcre2_dfa_match() utilise un analyseur déterministe fini (DFA) et est généralement plus rapide pour la recherche de motifs simples, mais peut consommer plus de mémoire. pcre2_jit_match() utilise la compilation Just-In-Time (JIT) pour compiler le modèle en code machine natif, ce qui peut offrir des performances considérablement améliorées pour les modèles complexes et les grands ensembles de données.
