PDNSD.CONF(5) Manuel des formats de fichier PDNSD.CONF(5)

NOM

pdnsd.conf - Le fichier de configuration de pdnsd

DESCRIPTION

Cette page de manuel décrit la structure du fichier de configuration de pdnsd(8) et les options de configuration disponibles. L'emplacement par défaut du fichier est /etc/pdnsd.conf. Ceci peut être changé avec l'option de ligne de commande -c. Un exemple de pdnsd.conf est fourni avec la distribution pdnsd dans le répertoire de documentation ou dans /etc/pdnsd.conf.sample.

FORMAT DU FICHIER

Le fichier de configuration est divisé en sections. Chaque section est précédée du nom de la section et des accolades ouvrantes ({) et fermée par des accolades fermantes (}). Dans chaque section, les options de configuration peuvent être données sous la forme

nom_option=valeur_option;

La valeur de l'option peut être une chaîne littérale, un nombre, une spécification de temps ou une constante. Dans les versions précédentes de pdnsd, les chaînes devaient être entourées de guillemets ("), mais depuis la version 1.1.10, ce n'est plus nécessaire, sauf si une chaîne contient un caractère spécial tel qu'un espace blanc, un jeton qui commence normalement un commentaire, ou l'un des caractères ",;{{}. Depuis la version 1.2.9, un antislash (\) à l'intérieur d'une chaîne est interprété comme un caractère d'échappement, il est donc possible d'inclure des caractères spéciaux dans les chaînes (quotées ou non) en les faisant précéder d'un antislash. Certaines séquences d'échappement sont interprétées comme dans le langage de programmation C, par exemple \t devient une tabulation, \0 devient un caractère de contrôle de nouvelle ligne.
Une spécification de temps consiste en une séquence de chiffres suivie d'un suffixe d'une lettre. Les suffixes suivants sont reconnus : s (secondes), m (minutes), h (heures), d (jours) et w (semaines). Si le suffixe est manquant, les secondes sont supposées. Si plusieurs spécifications de temps sont concaténées, leurs valeurs sont additionnées ; par exemple, 2h30m est interprété comme 2*60*60 + 30*60 = 9000 secondes.
Certaines options prennent plusieurs valeurs ; dans ce cas, les valeurs sont séparées par des virgules.
Si vous pouvez fournir l'une des valeurs possibles à une option, cela est indiqué dans la documentation sous la forme (option1|option2|option3|...)
Les constantes true|false et yes|no sont acceptées comme synonymes des constantes on|off.
Les commentaires peuvent être entourés de /* et */, les commentaires imbriqués sont possibles. Si le signe # ou deux barres obliques (//) apparaissent dans le fichier de configuration, tout ce qui suit ces signes jusqu'à la fin de la ligne courante est considéré comme un commentaire et ignoré.
Il y a des exemples pour presque toutes les options dans le fichier de configuration exemple.

Section global

La section globale spécifie les paramètres qui affectent le comportement général du serveur. Si vous spécifiez plusieurs sections globales, les réglages des sections ultérieures écraseront les valeurs données précédemment.
Voici les options possibles :

cache_permanent=(nombre|désactivé);
Désactive le cache sur disque ou fournit une taille maximale de cache en Ko. Si le cache sur disque est désactivé, 8 octets seront quand même écrits sur le disque. Le cache mémoire est toujours 10 Ko plus grand que le cache de fichier. Cette valeur est de 2048 (2 Mo) par défaut.
repertoire_cache=chaîne;
Définit le répertoire où vous souhaitez conserver le cache. Le défaut est "/var/cache/pdnsd" (sauf si pdnsd a été compilé avec une valeur par défaut différente).
port_serveur=nombre;
Définit le port du serveur. Ceci est particulièrement utile lorsque vous souhaitez démarrer le serveur et que vous n'êtes pas root. Notez que vous ne pouvez pas non plus spécifier uptest=ping dans la section serveur si vous n'êtes pas root.
Le port par défaut est 53, celui standard selon la RFC. Notez que vous ne devriez utiliser des ports non standard que si vous souhaitez que les clients de votre machine communiquent uniquement avec le serveur ; les autres risquent d'échouer s'ils essaient de contacter le serveur sur la base d'un enregistrement NS, car l'enregistrement A qui fournit l'adresse des serveurs de noms (entre autres) n'a pas de spécification de numéro de port.
ip_serveur=chaîne;
ou
interface=chaîne;
Définit l'adresse IP sur laquelle pdnsd écoute les requêtes. Ceci peut être utile lorsque l'hôte a plusieurs interfaces et que vous ne voulez pas que pdnsd écoute sur toutes les interfaces. Par exemple, il est possible de lier pdnsd pour qu'il écoute sur 127.0.0.2 afin de permettre à pdnsd d'être un transmetteur pour BIND. Le réglage par défaut pour cette option est ip_serveur=any, ce qui signifie que pdnsd écoutera sur toutes vos interfaces locales. Actuellement, vous ne pouvez spécifier qu'une seule adresse ici ; si vous voulez que pdnsd écoute sur plusieurs interfaces mais pas toutes, vous devrez spécifier ip_serveur=any et utiliser des règles de pare-feu pour restreindre l'accès.
L'adresse IP avait besoin d'être entourée de guillemets, mais depuis la version 1.1.10, ce n'est plus nécessaire.
Si pdnsd a été compilé avec le support IPv4 et IPv6, et que vous souhaitez spécifier une adresse IPv6 ici, alors à moins que pdnsd n'ait été compilé pour démarrer en mode IPv6 par défaut, vous devrez utiliser l'option de ligne de commande -6 ou définir run_ipv4=désactivé d'abord (voir ci-dessous) afin de garantir que l'adresse IPv6 est correctement analysée.
Si pdnsd fonctionne en mode IPv6 et que vous spécifiez une adresse IPv4 ici, elle sera automatiquement mappée à une adresse IPv6.
Nouveau depuis la version 1.2 : Vous pouvez également donner le nom d'une interface comme "lo" ou "eth0" ici, au lieu d'une adresse IP (cela a été testé sur Linux, et peut fonctionner ou non sur d'autres plateformes). pdnsd ne se liera pas au nom de l'interface, mais recherchera l'adresse de l'interface au démarrage et écoutera sur cette adresse. Si l'adresse de l'interface change pendant que pdnsd est en cours d'exécution, pdnsd ne s'en apercevra pas. Vous devrez redémarrer pdnsd dans ce cas.
ip_sortante=chaîne;
ou
interface_exterieure=chaîne;
Nouveau depuis la version 1.2.9 : Définit l'adresse IP de l'interface utilisée par pdnsd pour les requêtes sortantes. Ceci peut être utile lorsque l'hôte a plusieurs interfaces et que vous souhaitez que pdnsd envoie les requêtes sortantes via une seule d'entre elles. Par exemple, si pdnsd fonctionne sur un hôte avec une interface avec l'adresse IP 192.168.1.1 connectée au réseau local, et une autre avec l'adresse IP 123.xxx.yyy.zzz connectée à Internet, vous pouvez spécifier ip_serveur=192.168.1.1 et ip_sortante=123.xxx.yyy.zzz pour forcer pdnsd à ne répondre qu'aux requêtes reçues du réseau local, et à n'envoyer les requêtes sortantes que via l'interface connectée à Internet.
Le réglage par défaut pour cette option est any, ce qui signifie que le noyau est libre de décider quelle interface utiliser. Comme avec l'option ip_serveur, vous pouvez également donner le nom d'une interface ici, au lieu d'une adresse IP.
kluge_lien_mort=(activé|désactivé);
Cette option active un "kluge" dont certaines personnes pourraient avoir besoin : lorsque tous les serveurs sont marqués comme inactifs, avec cette option activée, le cache n'est même pas utilisé lorsqu'une requête est reçue, et une erreur DNS est retournée dans tous les cas. La seule exception est que les enregistrements locaux (tels que spécifiés dans les sections rr et source) sont toujours servis normalement. En général, vous voudrez probablement obtenir des entrées mises en cache même lorsque le réseau est en panne, donc cela est désactivé par défaut.
ttl_max=spécification_temps;
Cette option définit le temps maximum pendant lequel un enregistrement est conservé dans le cache. Tous les enregistrements de ressources DNS ont un champ "time to live" qui indique pendant quelle période l'enregistrement peut être mis en cache avant d'être à nouveau interrogé. Si c'est plus long que la valeur donnée avec ttl_max, cette valeur "time to live" sera définie à ttl_max. Ceci est fait pour éviter que les enregistrements ne soient mis en cache pendant une période de temps inappropriée, car c'est presque jamais une bonne chose à faire. Le défaut est 604800s (une semaine).
ttl_min=spécification_temps;
Cette option définit le temps minimum pendant lequel un enregistrement est conservé dans le cache. Tous les enregistrements de ressources DNS ont un champ "time to live" qui indique pendant quelle période l'enregistrement peut être mis en cache avant d'être à nouveau interrogé. S'il est inférieur à la valeur donnée avec ttl_min, cette valeur "time to live" sera définie à ttl_min. Le défaut est 120 secondes.
ttl_negatif=spécification_temps;
Cette option définit le temps pendant lequel les enregistrements mis en cache négativement resteront valides dans le cache si aucun "time to live" ne peut être déterminé. C'est toujours le cas lorsque des domaines entiers sont mis en cache négativement, et en plus lorsque des types d'enregistrements sont mis en cache négativement

neg_rrs_pol=(on|off|auth|default);
Définit la politique de mise en cache des enregistrements négatifs ; cela indique à pdnsd dans quelles circonstances il doit mettre en cache un type d'enregistrement négativement pour un domaine donné. 'off' désactivera la mise en cache des types d'enregistrements négatifs, 'on' ajoutera toujours une entrée de cache négative lorsqu'un serveur de noms n'a pas retourné le type d'enregistrement demandé, et 'auth' n'ajoutera de telles entrées que si la réponse provenait d'un serveur de noms faisant autorité pour ce domaine.
Nouveau dans la version 1.2.8 : Le paramètre 'default' ajoutera un enregistrement mis en cache négativement si la réponse était faisant autorité ou si la réponse indiquait que le serveur de noms disposait de la "récursion disponible" tandis que la requête demandait explicitement une telle récursion.
Le réglage prédéfini est "default" (c'était 'auth' auparavant).
neg_domain_pol=(on|off|auth);
Ceci est analogue à neg_rrs_pol pour la mise en cache négative de domaines entiers. Il devrait être sûr de le régler sur 'on', car je n'ai pas vu de serveur de mise en cache qui prétende faussement qu'un domaine n'existe pas.
La valeur par défaut est 'auth'.
run_as=chaîne;
Cette option permet à pdnsd de changer son identifiant utilisateur et groupe après les opérations qui nécessitaient des privilèges. Cela contribue à minimiser les risques de sécurité et est donc recommandé. La chaîne fournie donne un nom d'utilisateur dont l'identifiant utilisateur et l'identifiant de groupe principal sont utilisés.
Quelques détails supplémentaires : après avoir lu le fichier de configuration, être devenu un daemon (si spécifié) et démarré le thread de statut du serveur, le thread principal change son gid et uid, tout comme tous les nouveaux threads créés par la suite. En prenant un autre uid et gid, ces threads s'exécutent avec les privilèges de l'utilisateur spécifié. Sous Linux et FreeBSD, le thread de statut du serveur s'exécute avec les privilèges d'origine uniquement lorsque l'option strict_setuid est définie sur 'off' (voir ci-dessous, activée par défaut), car ceux-ci peuvent être nécessaires pour les uptests d'exécution. Le thread du gestionnaire conserve également ses privilèges d'origine dans ce cas. Vous devez veiller à ce que l'utilisateur que vous spécifiez ait les permissions d'écriture sur votre fichier de cache et votre pipe de statut (si vous avez besoin d'un pipe de statut). Vous devriez rechercher des messages d'erreur tels que "permission denied" et "operation not permitted" pour découvrir les problèmes de permission.
strict_setuid=(on|off);
Lorsqu'elle est utilisée avec l'option run_as, cette option vous permet de spécifier que tous les threads du programme s'exécuteront avec les privilèges de l'utilisateur run_as. Cela offre une sécurité plus élevée que l'option run_as normale, mais n'est pas toujours possible. Voir l'option run_as pour plus de discussion.
Cette option est activée par défaut.
Notez que cette option n'a aucun effet sur les systèmes autres que Linux.
paranoid=(on|off);
Normalement, pdnsd interroge tous les serveurs en mode récursif (c'est-à-dire qu'il demande aux serveurs d'interroger d'autres serveurs si possible, et de renvoyer des réponses pour les domaines qui ne sont peut-être pas sous son autorité), et accepte des enregistrements supplémentaires avec des informations sur les serveurs qui ne sont pas sous l'autorité du serveur interrogé. Cela ouvre la possibilité de ce qu'on appelle l'empoisonnement du cache : un attaquant malveillant pourrait mettre en place un serveur DNS qui, lorsqu'il est interrogé, renvoie des enregistrements supplémentaires falsifiés. De cette façon, il pourrait remplacer les serveurs de confiance par les siens en faisant en sorte que votre serveur DNS renvoie de mauvaises adresses IP. Cette option vous protège de l'empoisonnement du cache en rejetant les enregistrements supplémentaires qui ne décrivent pas les domaines dans l'espace d'autorité des serveurs interrogés et en n'effectuant plus de requêtes récursives. Une exception à cette règle concerne les serveurs que vous spécifiez dans votre fichier de configuration, qui sont considérés comme fiables.
La contrepartie est une éventuelle diminution des performances, en particulier, plus de requêtes pourraient être nécessaires pour la même opération.
Vous devriez également noter qu'il peut y avoir d'autres problèmes de sécurité similaires, qui sont essentiellement des problèmes du DNS, c'est-à-dire que tout serveur "traditionnel" les a (les extensions de sécurité DNS résolvent ces problèmes, mais ne sont pas largement prises en charge). L'une de ces vulnérabilités est qu'un attaquant peut vous bombarder de réponses falsifiées dans l'espoir que l'une d'elles corresponde à une requête que vous avez effectuée. Si vous avez effectué une telle requête, une réponse falsifiée sur 65536 sera réussie (c'est-à-dire qu'une moyenne de 32768 paquets est nécessaire pour cette attaque). pdnsd peut utiliser le protocole TCP pour les requêtes, ce qui a une surcharge légèrement plus élevée, mais est beaucoup moins vulnérable à de telles attaques sur des systèmes d'exploitation sains. De plus, pdnsd choisit des identifiants de requête aléatoires, de sorte qu'un attaquant ne puisse pas prendre de raccourci. Si l'attaquant est capable d'écouter votre trafic réseau, cette attaque est relativement facile, cependant.
Cette vulnérabilité n'est pas la faute de pdnsd, et elle est possible avec n'importe quel serveur de noms conventionnel (pdnsd est peut-être un peu plus sécurisé contre ce type d'attaques si vous le faites utiliser TCP).
L'option paranoid est désactivée par défaut.
ignore_cd=(on|off);
Nouveau dans la version 1.2.8 : Cette option vous permet de spécifier que le bit CD d'une requête DNS sera ignoré. Sinon, pdnsd répondra FORMERR aux clients qui définissent ce bit dans une requête. Il est sûr d'activer cette option, car le bit CD signifie 'Checking Disabled' (Vérification désactivée), ce qui signifie que le client acceptera des données non authentifiées.
Cette option est activée par défaut. Désactivez-la si vous souhaitez l'ancien comportement (avant la version 1.2.8).
scheme_file=chaîne;
En plus des uptests normaux, vous pouvez spécifier que certains serveurs ne doivent être interrogés que lorsqu'un certain schéma pcmcia-cs est actif (uniquement sous Linux). Pour cela, pdnsd a besoin de connaître l'emplacement du fichier qui contient les informations de schéma pcmcia. Normalement, il s'agit de /var/lib/pcmcia/scheme ou /var/state/pcmcia/scheme.
status_ctl=(on|off);
Ceci a le même effet que l'option de ligne de commande -s : le contrôle de statut est activé lorsque 'on' est spécifié.
Ajouté par Paul Rombouts : Notez que pdnsd-ctl permet la configuration à chaud de pdnsd, même les adresses IP des serveurs de noms peuvent être modifiées. Si vous n'utilisez pas pdnsd-ctl et que vous souhaitez une sécurité maximale, vous ne devriez pas activer cette option. Elle est désactivée par défaut.
daemon=(on|off);
Ceci a le même effet que l'option de ligne de commande -d : le mode daemon est activé lorsque 'on' est spécifié.
La valeur par défaut est 'off'.
tcp_server=(on|off);
tcp_server=on a le même effet que l'option de ligne de commande -t ou --tcp : elle active le service TCP. De même, tcp_server=off équivaut à l'option de ligne de commande --notcp.
La valeur par défaut est 'on'.
pid_file=chaîne;
Ceci a le même effet que l'option de ligne de commande -p : vous pouvez spécifier un fichier dans lequel pdnsd écrira son pid lors de son démarrage en mode daemon.
verbosity=nombre;
Ceci a le même effet que l'option de ligne de commande -v : vous pouvez définir la verbosité des messages de pdnsd avec cette option. L'argument est un nombre compris entre 0 (peu de messages) et 3 (la plupart des messages).
query_method=(tcp_only|udp_only|tcp_udp|udp_tcp);
Ceci a le même effet que l'option de ligne de commande -m. Lisez la documentation de l'option de ligne de commande à ce sujet. tcp_only correspond à l'argument to, udp_only à uo, tcp_udp à tu et udp_tcp à ut de l'option de ligne de commande.
Si vous utilisez query_method=tcp_udp, il est recommandé de régler également l'option de délai d'attente globale à au moins le double du délai d'attente du serveur le plus long.
run_ipv4=(on|off);
Ceci a le même effet que l'option de ligne de commande -4 ou -6 : si 'on' est spécifié, le support IPv4 est activé et le support IPv6 est désactivé (si disponible). Si 'off' est spécifié, IPv4 sera désactivé et IPv6 sera activé. Pour que cette option soit significative, pdnsd doit être compilé avec le support du protocole que vous choisissez. Si pdnsd a été compilé avec le support IPv4 et IPv6, et que vous souhaitez inclure des adresses IPv6 dans le fichier de configuration, vous devrez probablement spécifier run_ipv4=off en premier pour vous assurer que les adresses IPv6 sont correctement analysées.
debug=(on|off);
Ceci a le même effet que l'option de ligne de commande -g : les messages de débogage sont activés lorsque 'on' est spécifié.
ctl_perms=nombre;
Cette option vous permet de définir les permissions du fichier du socket de contrôle de statut de pdnsd. Ce sont les mêmes que les permissions de fichier. Le propriétaire du fichier sera l'utilisateur run_as, ou, si aucun n'est spécifié, l'utilisateur qui a démarré pdnsd. Si vous souhaitez spécifier les permissions en octal (comme d'habitude), n'oubliez pas le zéro initial (0600 au lieu de 600 !). Pour utiliser le contrôle de statut, un accès en écriture est nécessaire. La valeur par défaut est 0600 (seul le propriétaire peut lire ou écrire).
Veuillez noter que le socket est conservé dans le répertoire de cache, et que les permissions du répertoire de cache pourraient également devoir être ajustées. Veuillez vous assurer que le répertoire de cache n'est pas accessible en écriture par des utilisateurs non fiables.
proc_limit=nombre;
Avec cette option, vous pouvez définir une limite sur les threads pdnsd qui seront actifs simultanément. Si ce nombre est dépassé, les requêtes sont mises en file d'attente et peuvent être retardées pendant un certain temps. Voir également l'option procq_limit.
La valeur par défaut pour cette option est 40.
procq_limit=nombre;
Lorsque la limite de threads de requête proc_limit est dépassée, les tentatives de connexion à pdnsd sont mises en file d'attente. Avec cette option, vous pouvez définir la longueur maximale de la file d'attente. Si cette longueur est également dépassée, les requêtes entrantes seront abandonnées. Cela signifie que les connexions TCP seront fermées et les requêtes UDP seront simplement abandonnées, ce qui provoquera probablement le délai d'attente du résolveur interrogateur en attendant une réponse.
Voir également l'option proc_limit. Un maximum de proc_limit + procq_limit threads de requête existera à un moment donné (plus 3 à 6 threads qui w
ill always être présent en fonction de votre configuration).
La valeur par défaut pour cette option est 60.
tcp_qtimeout=timespec;
Cette option définit un délai d'attente pour les requêtes TCP. Si aucune requête complète n'a été reçue sur une connexion TCP après expiration de ce délai, la connexion sera fermée. La valeur par défaut est définie à l'aide de l'option --with-tcp-qtimeout lors de la compilation.
par_queries=nombre;
Cette option était utilisée pour définir le nombre maximum de serveurs distants qui seraient interrogés simultanément, pour chaque requête que pdnsd reçoit.
Depuis la version 1.1.11, la signification de cette option a légèrement changé. Elle représente maintenant l'incrément avec lequel le nombre de requêtes parallèles est augmenté lorsque l'ensemble précédent de serveurs a expiré. Par exemple, si nous avons une liste serveur1, serveur2, serveur3, etc. de serveurs disponibles et que par_queries=2, alors pdnsd enverra d'abord des requêtes à serveur1 et serveur2, et écoutera les réponses de ces serveurs.
Si ces serveurs ne renvoient pas de réponse dans leur période de délai d'attente, pdnsd enverra des requêtes supplémentaires à serveur3 et serveur4, et écoutera les réponses de serveur1, serveur2, serveur3 et serveur4, et ainsi de suite jusqu'à ce qu'une réponse utile soit reçue ou que la liste soit épuisée.
Dans le pire des cas, il y aura des requêtes en attente pour tous les serveurs de la liste des serveurs disponibles. Nous pourrions utiliser plus de ressources système de cette manière (mais seulement si les premiers serveurs de la liste sont lents ou ne répondent pas), mais l'avantage est que nous avons une plus grande chance d'obtenir une réponse. Après tout, si nous attendons plus longtemps de toute façon, pourquoi pas pour plus de serveurs.
Voir aussi l'explication de l'option de délai d'attente globale ci-dessous.
1 ou 2 sont de bonnes valeurs pour cette option. La valeur par défaut est définie lors de la compilation à l'aide de l'option --with-par-queries lors de la configuration.
timeout=timespec;
C'est le paramètre de délai d'attente global pour les requêtes DNS. Il spécifie la période de temps minimale pendant laquelle pdnsd attendra après l'envoi de la première requête à un serveur distant avant d'abandonner sans avoir reçu de réponse. Les options de délai d'attente dans le fichier de configuration ne sont maintenant que des intervalles de délai d'attente minimum. La définition de l'option de délai d'attente globale permet de spécifier des intervalles de délai d'attente assez courts dans les sections serveur (voir ci-dessous). Cela aura pour effet que pdnsd commencera à interroger des serveurs supplémentaires assez rapidement si les premiers serveurs répondent lentement (mais continuera toujours à écouter les réponses des premiers). Cela peut permettre à pdnsd d'obtenir une réponse plus rapidement dans certaines situations.
Si vous utilisez query_method=tcp_udp, il est recommandé que le délai d'attente global soit au moins deux fois plus long que le plus grand délai d'attente du serveur, sinon pdnsd pourrait ne pas avoir le temps d'essayer une requête UDP si une connexion TCP expire.
La valeur par défaut est 0.
randomize_recs=(on|off);
Si cette option est activée, pdnsd réorganisera aléatoirement les enregistrements mis en cache d'un type lors de la création d'une réponse. Cela prend en charge les schémas DNS de type round-robin et augmente la sécurité en cas de défaillance pour les hôtes ayant plusieurs adresses IP, c'est donc généralement une bonne idée.
Activé par défaut.
query_port_start=(nombre|none);
Si un nombre est donné, il définit le début de la plage de ports utilisée pour les requêtes de pdnsd. La valeur donnée doit être supérieure ou égale à 1024. Le but de cette option est d'aider certaines configurations de pare-feu basées sur le port source. Veuillez garder à l'esprit qu'une autre application peut réserver un port dans cette plage, donc un pare-feu avec état utilisant le port de destination et/ou l'UID du processus peut être plus efficace. Si un port de début de requête est donné, pdnsd utilise ce port comme premier port d'une plage de ports spécifiée (voir query_port_end) utilisée pour les requêtes. pdnsd essaiera de sélectionner aléatoirement un port libre de cette plage comme port local pour la requête.
Pour garantir qu'il y a suffisamment de ports pour pdnsd, la plage entre query_port_start et query_port_end doit être ajustée à au moins (par_queries * proc_limit). Une plage plus grande est fortement recommandée pour des raisons de sécurité, et aussi parce que d'autres applications peuvent allouer des ports dans cette plage. Si possible, cette plage doit être exclue de l'espace que d'autres applications utilisent habituellement.
La valeur par défaut pour cette option est 1024. Associée à la valeur par défaut de query_port_end, cela rend plus difficile pour un attaquant de deviner le port source utilisé par le résolveur pdnsd. Si vous spécifiez none ici, pdnsd laissera le noyau choisir le port source, mais cela pourrait rendre pdnsd plus vulnérable à une attaque.
query_port_end=nombre;
Utilisé si query_port_start n'est pas none. Définit le dernier port de la plage commençant par query_port_start, utilisé pour les requêtes par pdnsd. La valeur par défaut est 65535, qui est également la valeur légale maximale pour cette option. Pour plus de détails, voir la description de query_port_start.
delegation_only=chaîne;
Ajouté par Paul Rombouts: Cette option spécifie une zone "délégation uniquement". Cela signifie que si pdnsd reçoit une requête pour un nom qui se trouve dans un sous-domaine d'une zone "délégation uniquement" mais que le serveur de noms distant renvoie une réponse avec une section d'autorité ne contenant aucun RR NS pour les sous-domaines de cette zone, pdnsd répondra NXDOMAIN (domaine inconnu). Cette fonctionnalité peut être utilisée pour annuler les effets indésirables des "wildcards" DNS. Plusieurs zones "délégation uniquement" peuvent être spécifiées ensemble. Si vous spécifiez des serveurs racine dans une section serveur, il est important de définir root_server=on dans une telle section.
Exemple:

delegation_only="com","net";

Cette fonctionnalité est désactivée par défaut. Il est recommandé de ne l'utiliser que si vous en avez réellement besoin, car il y a un risque que certains noms légitimes soient bloqués, surtout si les serveurs de noms distants interrogés par pdnsd renvoient des réponses avec des sections d'autorité vides.

ipv4_6_prefix=chaîne;
Cette option a le même effet que l'option de ligne de commande -i. Lorsque pdnsd s'exécute en mode IPv6, cette option spécifie le préfixe que pdnsd utilise pour convertir les adresses IPv4 dans le fichier de configuration (ou les adresses spécifiées avec pdnsd-ctl) en adresses mappées IPv6. La chaîne doit être une adresse IPv6 valide. Seuls les 96 premiers bits sont utilisés. Notez que cela n'affecte que l'analyse des adresses IPv4 listées après cette option.
La valeur par défaut est "::ffff.0.0.0.0".
use_nss=(on|off);
Si cette option est activée, pdnsd appellera initgroups() pour configurer la liste d'accès aux groupes, chaque fois que pdnsd changera son ID utilisateur et groupe (voir l'option run_as). Il y a cependant un inconvénient potentiel, si initgroups() utilise NSS (Name Service Switch) et que NSS utilise à son tour le DNS. Dans un tel cas, vous pourriez rencontrer de longs délais d'attente et des blocages. En définissant use_nss=off, vous pouvez désactiver l'appel initgroups() (uniquement possible dans les versions 1.2.5 et ultérieures).
Cette option a été contribuée par Jan-Marek Glogowski.
Activé par défaut.
udpbufsize=nombre;
Nouveau dans la version 1.2.9: Cette option définit la limite supérieure de la taille des messages DNS UDP. La valeur par défaut est 1024.
Voir aussi l'option serveur edns_query ci-dessous.

Section server

Chaque section serveur spécifie un ensemble de serveurs de noms à partir desquels pdnsd doit essayer d'obtenir des enregistrements de ressources ou des informations de serveur de noms faisant autorité. Les serveurs sont interrogés dans l'ordre de leur apparition (ou en parallèle dans une certaine mesure). Si l'un échoue, le suivant est utilisé, et ainsi de suite.
Vous voudrez probablement spécifier le serveur DNS de votre réseau local, les serveurs DNS de mise en cache de votre fournisseur d'accès à Internet, ou même une liste de serveurs racine dans une ou plusieurs sections serveur.
Les options prises en charge dans cette section sont:

label=chaîne;
Spécifie une étiquette pour la section serveur. Cela peut être utilisé pour faire référence à cette section lors de l'utilisation de pdnsd-ctl, l'utilitaire de contrôle de pdnsd.
Vous pouvez donner à plusieurs sections serveur la même étiquette, mais si vous souhaitez modifier les adresses d'une section serveur (voir l'option ip ci-dessous) pendant l'exécution avec "pdnsd-ctl server label up dns1,dns2,...", l'étiquette doit être unique.
ip=chaîne;
Donne l'adresse IP (l'adresse, *pas* le nom d'hôte) du serveur.
Plusieurs adresses IP peuvent être données par section serveur. Cela peut être fait en entrant plusieurs lignes de la forme ip=chaîne; ou une seule ligne comme celle-ci:

ip=chaîne,chaîne,chaîne;

Les adresses IP ne doivent pas nécessairement être spécifiées dans le fichier de configuration. Une section serveur sans adresses IP restera inactive jusqu'à ce qu'elle se voie attribuer une ou plusieurs adresses avec pdnsd-ctl, l'utilitaire de contrôle de pdnsd.
Si pdnsd a été compilé avec le support IPv4 et IPv6, toute adresse IPv6 que vous spécifiez ici sera ignorée avec un message d'avertissement, sauf si pdnsd s'exécute en mode IPv6. Ainsi, sauf si pdnsd a été compilé pour démarrer en mode IPv6 par défaut, vous devez utiliser l'option de ligne de commande -6 ou définir d'abord run_ipv4=off (voir la section globale) afin de garantir que les adresses IPv6 sont correctement analysées.
Si pdnsd s'exécute en mode IPv6 et que vous spécifiez une adresse IPv4 ici, elle sera automatiquement mappée à une adresse IPv6.

file=chaîne;
Nouveau dans la version 1.2: Cette option vous permet de spécifier le nom d'un fichier de style resolv.conf. Parmi les lignes commençant par le mot-clé nameserver, le second champ sera analysé comme une adresse IP, comme s'il était spécifié avec l'option ip=. Les lignes restantes seront ignorées. Si le contenu du fichier change pendant que pdnsd s'exécute, vous pouvez en informer pdnsd à l'aide de pdnsd-ctl, l'utilitaire de contrôle de pdnsd. Cela se fait généralement le plus commodément en plaçant la commande "pdnsd-ctl config" dans un script qui est automatiquement exécuté chaque fois que la configuration DNS change.
Par exemple, supposons que vous ayez un client ppp qui écrit la configuration DNS de votre FAI dans le fichier /etc/ppp/resolv.conf et exécute le script /etc/ppp/ip-u

port=nombre ;
Spécifie le port sur lequel le serveur de noms distant écoute. La valeur par défaut est 53 (le port DNS officiel)
uptest=(ping|none|if|dev|diald|exec|query) ;
Détermine la méthode pour vérifier si le serveur est disponible. Les méthodes actuellement définies sont :
• ping : Envoie une requête ICMP_ECHO au serveur. S'il ne répond pas dans le délai imparti, il est considéré comme indisponible jusqu'à la prochaine sonde.
• none : Le statut de disponibilité n'est pas modifié, seule l'horodatage est mis à jour.
• if : Vérifie si l'interface (spécifiée dans l'option interface=) existe, est active et fonctionne. Cela fonctionne actuellement pour toutes les interfaces réseau « ordinaires », les interfaces qui disparaissent lorsqu'elles sont inactives (par exemple, ppp ?), et en outre pour les interfaces ISDN Linux (à partir du noyau 2.2). Notez que vous avez besoin d'un fichier de périphérique /dev/isdninfo (majeur n° 45, mineur n° 255), sinon le test de disponibilité ISDN échouera toujours.
• dev et diald : Effectue un test de disponibilité « if » et, si celui-ci a réussi, vérifie en outre si un programme est en cours d'exécution qui a verrouillé un périphérique (modem) donné. Les paramètres nécessaires sont une interface (spécifiée comme pour le test de disponibilité « if », par exemple « ppp0 ») et un périphérique relatif à /dev (par exemple, « modem » pour /dev/modem spécifié à l'aide de l'option device= . pdnsd recherchera alors un fichier pid pour l'interface donnée dans /var/lock (par exemple, /var/run/ppp0.pid) et un fichier de verrouillage pour le périphérique donné (par exemple, /var/lock/LCK..modem), puis vérifiera si le processus de verrouillage est le processus qui a créé le fichier pid et si ce processus est toujours actif. Si tel est le cas, le test « if » normal est exécuté pour l'interface donnée.
L'option dev est pour le pppd à composition à la demande, diald est la même chose pour les utilisateurs de diald.
• exec : Exécute une commande donnée dans le shell /bin/sh (comme /bin/sh -c <commande>) et évalue le résultat (le code de retour de la dernière commande) de la manière dont le shell gère les codes de retour, c'est-à-dire 0 indique le succès, tous les autres indiquent l'échec. Le nom du processus du shell sera uptest_sh. La commande est fournie avec l'option uptest_cmd (voir ci-dessous). Pour des raisons de sécurité, consultez également cette entrée.
• query : Nouveau dans la version 1.2 : Ceci fonctionne comme le test ping, sauf qu'il envoie une requête DNS (vide) au serveur distant. Si le serveur renvoie une réponse bien formée dans le délai imparti (sauf SERVFAIL), il sera considéré comme disponible. Ce test est utile si un serveur distant ne répond pas du tout aux requêtes ICMP_ECHO, ce qui est malheureusement assez courant de nos jours. Il peut également arriver qu'un serveur distant soit en ligne mais ignore les requêtes DNS vides. Dans ce cas, vous devrez définir l'option query_test_name (voir ci-dessous). Dans de nombreux cas, ce test sera un indicateur de disponibilité plus fiable que ceux mentionnés précédemment.

La valeur par défaut est none.

NOTE : Si vous utilisez la composition à la demande, utilisez none, if, dev, diald ou exec, car ping ou query enverront des paquets dans l'intervalle spécifié et l'interface composera ainsi fréquemment !

ping_timeout=nombre ;
Définit le délai d'attente pour le test ping en dixièmes de seconde (cette unité est utilisée pour des raisons d'héritage ; en fait, l'implémentation actuelle n'est précise qu'à la seconde près).
La valeur par défaut est 600 (une minute).
ping_ip=chaîne ;
L'adresse IP pour le test ping. La valeur par défaut est l'IP du serveur de noms.
query_test_name=chaîne ;
Nouveau dans la version 1.2.9 : Définit le nom à interroger lors de l'utilisation du test de disponibilité uptest=query. Si la chaîne est la constante non citée none, une requête vide est utilisée (c'est la valeur par défaut), sinon une requête de type A sera envoyée pour le nom de domaine spécifié ici. Il n'est pas nécessaire que le nom de domaine existe ou ait un enregistrement de type A pour que le test de disponibilité réussisse.
Si le serveur distant ignore les requêtes vides, vous voudrez probablement définir query_test_name="." (le domaine racine).
uptest_cmd=chaîne,chaîne ;
ou
uptest_cmd=chaîne ;
Définit la commande pour la fonction uptest=exec à la première chaîne. Si la deuxième chaîne est fournie, elle spécifie un utilisateur dont l'ID utilisateur et l'ID de groupe principal sont utilisés pour exécuter la commande.
Ceci est particulièrement utile si vous exécutez le serveur en tant que root, mais que vous ne souhaitez pas que le test de disponibilité soit effectué avec des privilèges root. En fait, vous ne devriez jamais exécuter le test de disponibilité en tant que root si vous pouvez l'éviter.
Si le serveur est exécuté en mode setuid ou setgid, les privilèges ainsi obtenus sont supprimés avant même de changer d'identité pour l'utilisateur spécifié afin d'éviter les failles de sécurité setuid/gid (sinon, n'importe quel utilisateur pourrait exécuter des commandes en tant que root si vous rendez l'exécutable setuid).
Notez que ce n'est pas toujours possible, et que pdnsd ne doit jamais être installé en mode setuid ou setgid. La commande est exécutée à l'aide de /bin/sh, vous devriez donc pouvoir utiliser les commandes intégrées du shell.
interval=(timespec|onquery|ontimeout) ;
Définit l'intervalle pour le test de disponibilité du serveur. La valeur par défaut est de 900 secondes ; cependant, un test est forcé lorsqu'une requête expire et que l'horodatage est alors réinitialisé.
Si vous spécifiez onquery au lieu d'un délai d'attente, l'interface sera testée avant chaque requête. Ceci afin d'éviter que les interfaces à composition automatique (diald/pppd ou ippp) ne composent lors des requêtes DNS. Il est destiné à être utilisé en conjonction avec un test de disponibilité d'interface ;-)
Notez qu'en utilisant uptest=exec, vous pourriez rencontrer des problèmes de performance sur des machines lentes lorsque vous utilisez cette option. N'UTILISEZ PAS onquery avec uptest=ping ou uptest=query, car cela pourrait entraîner des retards si le serveur ne répond pas (soit dit en passant, cela n'a pas de sens de toute façon). Notez également que l'utilisation de onquery ne garantit pas que l'interface ne sera pas utilisée. Lorsqu'un autre serveur DNS (accessible) indique à pdnsd d'interroger un troisième serveur DNS pour obtenir des données, pdnsd le fera et n'aura aucun moyen de vérifier si cela va activer l'interface ou non. Cependant, cela devrait être une situation rare.
Nouveau dans la version 1.2.3 : Une troisième possibilité est de spécifier interval=ontimeout. Dans ce cas, le serveur n'est pas testé au démarrage/reconfiguration, ni à intervalles réguliers, mais seulement après qu'une requête DNS vers un serveur ait expiré. Certains types de problèmes réseau, tels qu'une connexion refusée, entraîneront également la prise en compte du serveur comme indisponible. Cependant, une fois qu'un serveur est déclaré mort, il n'est plus jamais pris en compte, sauf s'il est rétabli à l'aide d'une commande pdnsd-ctl config ou server. L'idée derrière cette option est de minimiser les tests de disponibilité en supposant que tous les serveurs sont disponibles jusqu'à ce qu'il y ait des raisons de croire le contraire.
interface=chaîne ;
L'interface réseau (ou le périphérique réseau, par exemple « eth0 ») pour l'option uptest=if. Doit être spécifié si uptest=if est donné.
device=chaîne ;
Le périphérique (modem) utilisé pour le test de disponibilité dev. Si vous utilisez ceci pour un test de disponibilité ppp à composition à la demande (avec uptest=dev), vous devez y entrer le périphérique que vous utilisez pour votre pppd, par exemple modem pour /dev/modem.
Doit être spécifié si uptest=dev est donné.
timeout=timespec ;
Définit le délai d'attente pour la requête DNS. La valeur par défaut est de 120 secondes. Vous voudrez probablement définir une valeur plus basse.
Les délais d'attente spécifiés dans le fichier de configuration ne sont traités que comme la période minimale à attendre pour une réponse. Les requêtes vers un serveur distant ne sont pas annulées tant qu'une réponse utile n'a pas été reçue, ou que toutes les autres requêtes n'ont pas expiré ou échoué.
Si vous avez également défini l'option timeout globale, vous pourriez envisager de définir une valeur assez petite ici. Voir l'explication de l'option timeout dans la section globale pour ce que cela signifie.
purge_cache=(on|off) ;
Dans chaque enregistrement DNS récupéré, il y a un délai de mise en cache, qui spécifie combien de temps les données récupérées peuvent être mises en cache avant d'être rechargées. Si purge_cache est défini sur off, les enregistrements obsolètes ne sont pas purgés (sauf si la taille du cache est dépassée, dans ce cas, les enregistrements les plus anciens sont purgés). Au lieu de cela, ils sont toujours servis s'ils ne peuvent pas être mis à jour avec succès (par exemple, parce que tous les serveurs sont hors service).
La valeur par défaut est off.
caching=(on|off) ;
Spécifie si la mise en cache doit être effectuée pour ce serveur ou non. La valeur par défaut est on.
lean_query=(on|off) ;
Spécifie s'il faut utiliser le mode de requête « lean ». Dans ce mode, seules les informations effectivement interrogées auprès de pdnsd sont résolues et mises en cache. Cela présente l'avantage d'utiliser généralement moins d'espace de cache et la requête est généralement plus rapide. Dans 90 % des cas, seuls les enregistrements d'adresse (A) sont nécessaires de toute façon. S'il est désactivé, pdnsd mettra toujours en cache toutes les données sur un hôte qu'il peut trouver et demandera spécifiquement tous les enregistrements disponibles (enfin, c'est au moins une bonne approximation de ce qu'il fait réellement ;-) Cela augmentera bien sûr la taille des paquets de réponse.
Certains serveurs de noms bogués peuvent ne pas fournir les enregistrements CNAME s'ils ne demandent pas tous les enregistrements. Je ne sais pas s'il existe de tels serveurs, mais si vous avez des problèmes pour résoudre certains noms d'hôtes, essayez de désactiver cette option.
Une dernière note : si vous utilisez plusieurs pdnsd qui accèdent les uns aux autres, activer cette option est probablement un grand avantage.
Ceci est activé par défaut.
edns_query=(on|off) ;
Nouveau dans la version 1.2.9 : Spécifie s'il faut utiliser EDNS (Extensions mécanismes pour DNS) pour les requêtes sortantes. Actuellement, cela est seulement utile pour autoriser des tailles de messages UDP supérieures à 512 octets. Notez que la définition de cette option sur « on » peut poser des problèmes en combinaison avec certains systèmes ou logiciels hérités, y compris, de manière embarrassante, les versions précédentes de pdnsd.
La valeur par défaut est off, mais si votre réseau
peut gérer des charges utiles UDP nettement plus grandes que 512 octets, la valeur recommandée est activée.
Notez que cette option n'affecte que les requêtes sortantes. Si pdnsd reçoit une requête utilisant EDNS, il répondra en utilisant EDNS quelle que soit la valeur de cette option.

Voir aussi l'option udpbufsize ci-dessus.

scheme=chaîne ;
Vous pouvez spécifier un schéma pcmcia-cs qui est utilisé en plus des tests de disponibilité (uptests). Si vous spécifiez un schéma ici, le serveur concerné par cette section ne sera interrogé que si le schéma donné est actif. Les jokers shell (* et ?) sont autorisés dans la chaîne avec leur signification spéciale. Vous devez utiliser l'option scheme_file dans la section globale pour que cette option fonctionne.
preset=(activé|désactivé) ;
Cela vous permet de spécifier l'état initial d'un serveur avant qu'un test de disponibilité (uptest) ne soit effectué. 'activé' spécifie que le serveur est considéré comme disponible. La valeur par défaut est 'activé'. Ceci est particulièrement utile lorsque vous définissez uptest=none ; et que vous voulez changer l'état d'un serveur uniquement via pdnsd-ctl.
proxy_only=(activé|désactivé) ;
Lorsque cette option est définie sur 'activé', les réponses données par les serveurs sont toujours acceptées, et aucun autre serveur (comme, par exemple, spécifié dans les enregistrements NS du domaine de la requête) n'est interrogé. Si vous n'activez pas cette option, pdnsd effectuera de telles requêtes dans certains cas (notamment lors du traitement des requêtes ANY).
Cette option est utile lorsque vous ne souhaitez pas que pdnsd établisse de connexions avec des serveurs externes pour quelque raison que ce soit (par exemple, lorsqu'un pare-feu bloque de telles requêtes).
Je recommande d'activer lean_query lorsque vous utilisez cette option.
La valeur par défaut est 'désactivé'.
root_server=(activé|désactivé|découvrir) ;
Définissez cette option sur 'activé' si les serveurs spécifiés dans une section sont des serveurs racine. Un serveur racine ne donnera généralement que les serveurs de noms pour le domaine de premier niveau dans sa réponse. Définir root_server=activé amènera pdnsd à essayer d'utiliser les informations mémorisées dans le cache concernant les domaines de premier niveau pour réduire le nombre de requêtes aux serveurs racine, rendant la résolution de nouveaux noms plus efficace. Vous pouvez obtenir une liste des serveurs racine disponibles en exécutant la commande « dig . ns ».
Cette option est également nécessaire si vous utilisez l'option delegation_only.
Nouveau dans la version 1.2.8 : Cette option peut également être définie sur « découvrir ». Cela amènera pdnsd à interroger les serveurs fournis avec l'option ip= pour obtenir la liste complète des serveurs racine. Les adresses des serveurs racine remplaceront les adresses spécifiées avec l'option ip=. Cela ne sera fait qu'une seule fois au démarrage, ou après une commande « pdnsd-ctl config ». Dans ce cas, les serveurs de noms spécifiés avec l'option ip= n'ont pas besoin d'être des serveurs racine, ils doivent simplement connaître les noms et les adresses des serveurs racine. Après la découverte des serveurs racine, pdnsd se comportera comme si root_server=activé avait été spécifié.
La valeur par défaut est 'désactivé'.
randomize_servers=(activé|désactivé) ;
Nouveau dans la version 1.2.6 : Définissez cette option sur 'activé' pour donner à chaque serveur de noms de cette section une chance égale d'être interrogé. Si cette option est définie sur 'désactivé', les serveurs de noms sont toujours interrogés en commençant par le premier spécifié. Même avec cette option activée, l'ordre des requêtes n'est pas vraiment aléatoire. Seul le premier serveur est sélectionné aléatoirement ; les suivants sont interrogés dans un ordre consécutif, revenant au début de la liste lorsque la fin est atteinte. Notez que cette option n'affecte que l'ordre au sein d'une section. Les serveurs de la première section (active) sont toujours interrogés avant ceux de la seconde, etc.
La valeur par défaut est 'désactivé', mais si vous résolvez à partir de serveurs racine, activer cette option est fortement recommandé. Si root_server=activé, cette option affecte également l'ordre des requêtes des serveurs de noms pour les domaines de premier niveau.
reject=chaîne ;
Nouveau dans la version 1.2.6 : Cette option peut être utilisée pour faire en sorte que pdnsd rejette les réponses contenant certaines adresses IP. Vous pouvez spécifier une seule adresse IP, qui sera exactement correspondante, ou une plage d'adresses à l'aide d'une paire adresse/masque. Le masque peut être spécifié comme un simple entier, indiquant le nombre de bits initiaux à 1 dans le masque, ou dans la notation IP habituelle. Les adresses IP peuvent être IPv4 ou IPv6 (à condition qu'il y ait un support suffisant dans les bibliothèques C et que le support des enregistrements AAAA n'ait pas été désactivé). Lorsque les adresses de la liste de rejet sont comparées à celles d'une réponse, seuls les bits correspondant à ceux définis dans le masque réseau sont significatifs, les autres sont ignorés.
Plusieurs adresses ou paires adresse/masque peuvent être spécifiées ; cela peut être fait en entrant plusieurs lignes de la forme reject=chaîne ; ou une seule ligne comme ceci :

reject=chaîne,chaîne,chaîne ;

La façon dont pdnsd réagit lorsqu'une adresse dans la réponse correspond à celle de la liste de rejet dépend de l'option reject_policy, voir ci-dessous.

reject_policy=(échec|négation) ;
Nouveau dans la version 1.2.6 : Cette option détermine ce que fait pdnsd lorsqu'une adresse dans la réponse d'un serveur de noms correspond à la liste de rejet (voir ci-dessus). Si cette option est définie sur 'échec', pdnsd essaiera un autre serveur, ou, s'il n'y a plus de serveurs à essayer, retournera la réponse SERVFAIL. Si cette option est définie sur 'négation', pdnsd retournera immédiatement la réponse NXDOMAIN (domaine inconnu) sans interroger d'autres serveurs. Le réglage 'échec' est utile si vous ne faites pas toujours confiance aux serveurs de cette section, mais que vous faites confiance aux serveurs de la section suivante. Le réglage 'négation' peut être utilisé pour censurer complètement certaines adresses IP. Dans ce cas, vous devriez placer la même liste de rejet dans chaque section de serveur, et également définir l'option reject_recursively (voir ci-dessous) sur 'vrai'.
La valeur par défaut est 'échec'.
reject_recursively=(activé|désactivé) ;
Nouveau dans la version 1.2.6 : Normalement, pdnsd vérifie la présence d'adresses dans la liste de rejet (voir ci-dessus) uniquement lorsque la réponse provient directement d'un serveur de noms listé dans le fichier de configuration. Avec cette option définie sur 'activé', pdnsd effectuera également cette vérification pour les serveurs de noms obtenus à partir des enregistrements NS de la section d'autorité d'une réponse précédente (qui était incomplète et non faisant autorité).
La valeur par défaut est 'désactivé'.
policy=(inclus|exclus|simple_seulement|fqdn_seulement) ;
pdnsd prend en charge les listes d'inclusion/exclusion pour les sections de serveur : avec include= et exclude= (voir ci-dessous), vous pouvez spécifier des noms de domaine pour lesquels ce serveur sera utilisé ou ne sera pas utilisé. La première correspondance compte (c'est-à-dire que la première règle d'inclusion ou d'exclusion dans une section de serveur qui correspond à un nom de domaine est appliquée, et la recherche des autres règles est terminée). Si aucune règle ne correspond à un nom de domaine donné, l'option policy= détermine si ce serveur est utilisé pour la recherche de ce nom de domaine ; lorsque 'inclus' est donné, le serveur sera interrogé, et lorsque 'exclus' est donné, il ne le sera pas. Si 'simple_seulement' est donné, le serveur sera utilisé si le nom à rechercher est un nom de domaine simple (à un seul label), tandis que si 'fqdn_seulement' est donné, le serveur ne sera utilisé que pour les noms composés de deux étiquettes ou plus (c'est-à-dire que le nom contient au moins un point).
Si aucun serveur n'est disponible pour un domaine interrogé, pdnsd renverra un message d'erreur au client qui interrompra généralement les tentatives du client de résoudre un domaine spécifique à partir de ce serveur (le résolveur libc renverra par exemple une erreur à l'application qui a tenté de résoudre le domaine si aucun autre serveur n'est disponible dans resolv.conf). Cela peut être utile parfois.
Note : les constantes simple_seulement et fqdn_seulement ont été ajoutées par Paul Rombouts. Elles sont utiles pour contrôler quels serveurs de noms (le cas échéant) seront utilisés par pdnsd pour résoudre les noms d'hôte simples (à un seul label). fqdn_seulement signifiait autrefois « nom de domaine entièrement qualifié uniquement », mais c'est en fait un abus de langage. Les noms dans les requêtes reçues par pdnsd sont toujours considérés comme entièrement qualifiés. Si vous ne comprenez pas exactement à quoi servent les options simple_seulement et fqdn_seulement, il est probablement préférable de ne pas les utiliser.
La valeur par défaut pour cette option est 'inclus'.
include=chaîne ;
Cette option ajoute une entrée à la liste d'exclusion/inclusion. Si un domaine correspond au nom donné sous forme de chaîne, le serveur est interrogé si c'était la première règle correspondante (voir aussi l'entrée pour policy).
Si le nom donné commence par un point, tout le sous-domaine du nom donné, y compris celui de ce nom, sera mis en correspondance, par exemple « .foo.bar. » correspondra aux noms de domaine a.foo.bar., a.b.c.foo.bar. et foo.bar.
S'il ne commence pas par un point, seul le nom donné exactement (en ignorant la casse, bien sûr) sera mis en correspondance (astuce : si vous voulez inclure tous les sous-domaines, mais pas le domaine du nom donné lui-même, placez une règle d'exclusion à correspondance exacte avant la règle d'inclusion, par exemple : exclude=« foo.bar. » ; include=« .foo.bar. » ;
Les versions précédentes de pdnsd nécessitaient que les noms donnés avec cette option et la suivante se terminent par un point, mais depuis la version 1.1.8b1-par8, pdnsd ajoute automatiquement un point à la fin s'il manque.
pdnsd accepte maintenant également une notation plus compacte pour ajouter plusieurs entrées « include » sur une seule ligne, par exemple :

include=« .foo »,« .bar »,« .my.dom » ;

exclude=chaîne ;
Cette option ajoute une entrée à la liste d'exclusion/inclusion. Si un domaine correspond au nom donné sous forme de chaîne, le serveur n'est pas interrogé si c'était la première règle correspondante (voir aussi l'entrée pour policy).
Si le nom donné commence par un point, tout le sous-domaine du nom donné, y compris celui de ce nom, sera mis en correspondance, par exemple « .foo.bar. » correspondra aux noms de domaine a.foo.bar., a.b.c.foo.bar. et foo.bar.
S'il ne commence pas par un point, seul le nom donné exactement (en ignorant la casse, bien sûr) sera mis en correspondance (astuce : si vous voulez exclure tous les sous-domaines, mais pas le domaine du nom donné lui-même, placez une règle d'inclusion à correspondance exacte avant la règle d'exclusion, par exemple : include=« foo.bar. » ; exclude=« .foo.bar. » ;

exclude=« .foo »,« .bar »,« .my.dom » ;

rr Section

Chaque section rr spécifie un enregistrement de ressource DNS qui est stocké localement. Elle vous permet de spécifier vos propres enregistrements DNS qui sont servis par pdnsd de manière limitée. Seuls les enregistrements A, PTR, CNAME, MX, NS et SOA sont implémentés.
Cette option est destinée à vous permettre de définir des RR pour 1.0.0.127.in-addr.arpa. et localhost. (et peut-être même un ou deux hôtes) sans avoir à démarrer un serveur nommé supplémentaire si vos serveurs de noms mis en cache ne servent pas ces enregistrements. Elle n'est PAS destinée et n'est pas capable de fonctionner comme un serveur de noms complet.

name=chaîne;
Spécifie le nom des enregistrements de ressources, c'est-à-dire le nom de domaine de la ressource que l'enregistrement décrit. Cette option doit être spécifiée avant tout enregistrement a, ptr, cname, mx, ns ou soa. Les noms sont interprétés comme des noms de domaine absolus (c'est-à-dire que pdnsd suppose qu'ils se terminent par le domaine racine). Pour ceci et tous les arguments suivants qui prennent des noms de domaine, vous devez spécifier les noms de domaine en notation pointée (exemple venera.isi.edu.).
Les versions précédentes de pdnsd exigeaient que les noms de domaine donnés dans le fichier de configuration se terminent par un point, mais depuis la version 1.1.8b1-par8, pdnsd suppose automatiquement un point à la fin s'il est manquant.
Nouveau dans la version 1.2 : Il est également possible de spécifier un nom commençant par le libellé *. Un tel nom est appelé un wildcard. Le * dans un wildcard peut correspondre à un ou plusieurs libellés dans un nom interrogé, mais seulement à des libellés entiers. Tout autre caractère * dans un wildcard, à part celui du début, ne correspondra qu'à un * littéral.
Par exemple, *.mydomain correspondra à a.mydomain ou www.a.mydomain, mais pas à mydomain. *.a*.mydomain correspondra à www.a*.mydomain, mais pas à www.ab.mydomain. *a.mydomain ne correspondra qu'à lui-même.
Avant de pouvoir spécifier une section rr avec name=*.mydomain, vous devez définir certains enregistrements pour mydomain, typiquement des enregistrements NS et/ou SOA. Exemple :


rr {
name = mydomain;
ns = localhost;
soa = localhost, root.localhost, 42, 86400, 900, 86400, 86400;
}
rr {
name = *.mydomain;
a = 192.168.1.10;
}

Dans cet exemple, www.mydomain et ftp.mydomain seront résolus à l'adresse numérique 192.168.1.10 (sauf si vous ajoutez des sections rr spécifiant explicitement des adresses différentes pour www.mydomain ou ftp.mydomain). Si vous voulez que mydomain soit également résolu à une adresse numérique, ajoutez un enregistrement A à la première section rr.

ttl=timespec;
Spécifie le ttl (durée de vie) pour tous les enregistrements de ressources de cette section après cette entrée. Ceci peut être redéfini. La valeur par défaut est de 86400 secondes (=1 jour).
authrec=(on|off);
Si cela est activé, pdnsd créera des enregistrements locaux faisant autorité pour cette section rr. Cela signifie que pdnsd marque l'enregistrement du domaine de sorte que les enregistrements de ce domaine qui ne sont pas présents dans le cache sont traités comme inexistants, c'est-à-dire qu'aucun autre serveur n'est interrogé pour ce type d'enregistrement, et une réponse ne contenant aucun de ces enregistrements est retournée. C'est généralement ce que les gens veulent : si vous ajoutez un enregistrement A pour un hôte, et qu'il n'a pas d'enregistrement AAAA (donc pas d'adresse IPv6), vous ne voulez normalement pas que d'autres serveurs de noms soient interrogés à ce sujet.
C'est activé par défaut.
Veuillez noter que cela n'a d'effet que si cela précède l'option name !
reverse=(on|off);
Nouveau dans la version 1.2 : Si vous souhaitez qu'un nom défini localement soit résolu en une adresse numérique et vice versa, vous pouvez y parvenir en définissant reverse=on avant de définir l'enregistrement A (voir ci-dessous). L'alternative est de définir un enregistrement PTR séparé, mais vous trouverez probablement cette option beaucoup plus pratique.
La valeur par défaut est off.
a=chaîne;
Définit un enregistrement A (adresse hôte). L'argument est une adresse IPv4 en notation pointée. pdnsd servira cette adresse pour le nom d'hôte donné dans l'option name.
Sous réserve d'un support suffisant dans les bibliothèques C et que le support des enregistrements AAAA n'ait pas été désactivé, la chaîne d'argument peut également être une adresse IPv6, auquel cas un enregistrement AAAA sera défini.
Cette option peut être utilisée plusieurs fois au sein d'une section rr, entraînant la définition de plusieurs adresses pour le nom. Cependant, si vous placez différentes adresses dans différentes sections rr pour le même nom, la définition de la dernière section rr annulera les définitions des sections précédentes.
ptr=chaîne;
Définit un enregistrement PTR (pointeur de nom de domaine). L'argument est un nom d'hôte en notation pointée (voir name). L'enregistrement ptr sert à résoudre des adresses en noms. Par exemple, si vous voulez que l'adresse 127.0.0.1 soit résolue en localhost, et localhost en 127.0.0.1, vous avez besoin de quelque chose comme les sections suivantes :


rr {
name = localhost;
a = 127.0.0.1;
owner = localhost;
soa = localhost, root.localhost, 42, 86400, 900, 86400, 86400;
}
rr {
name = 1.0.0.127.in-addr.arpa;
ptr = localhost;
owner = localhost;
soa = localhost, root.localhost, 42, 86400, 900, 86400, 86400;
}

La deuxième section est pour la résolution inverse et utilise l'option ptr. Notez que vous pouvez obtenir le même effet en spécifiant uniquement la première section rr avec reverse=on.
Il y a quelque chose de spécial dans le nom de la deuxième section : lorsqu'un résolveur veut obtenir un nom d'hôte à partir d'une adresse Internet, il compose une adresse construite à partir de l'adresse IP dans l'ordre des octets inversé (1.0.0.127 au lieu de 127.0.0.1) où chaque octet de l'adresse écrit sous forme de nombre constitue un sous-domaine sous le domaine in-addr.arpa.
Donc, si vous voulez composer une adresse pour la résolution inverse, prenez votre IP en notation pointée (par exemple, 1.2.3.4), inversez l'ordre des octets (4.3.2.1) et ajoutez in-addr.arpa. (4.3.2.1.in-addr.arpa.) Ensuite, définissez une section rr donnant cette adresse comme nom et le nom de domaine correspondant à cette IP dans l'option ptr.

cname=chaîne;
Définit un enregistrement CNAME (nom canonique). L'argument doit être un nom d'hôte entièrement qualifié en notation pointée (voir name). Un CNAME est l'équivalent DNS d'un alias ou d'un lien symbolique.
Une utilisation utile des CNAME est de donner des surnoms courts et faciles à retenir à des hôtes ayant des noms compliqués. Par exemple, vous pourriez vouloir que le nom "news" fasse référence au serveur de news de votre FAI "nntp2.myisp.com". Au lieu d'ajouter un enregistrement A pour "news" avec la même adresse que "nntp2.myisp.com", vous pourriez insérer un CNAME pointant vers "nntp2.myisp.com", de sorte que si l'adresse IP du serveur de news change, il n'est pas nécessaire de mettre à jour l'enregistrement pour "news".
Pour implémenter cela avec pdnsd, vous pourriez ajouter la section suivante à votre fichier de configuration :


rr {
name = news;
cname = nntp2.myisp.com;
owner = localhost;
}

mx=chaîne,nombre;
Définit un enregistrement MX (échange de courrier). La chaîne est le nom d'hôte du serveur de messagerie en notation pointée (voir name). Le nombre spécifie le niveau de préférence.
Lorsque vous envoyez un e-mail à quelqu'un, votre e-mail va généralement de votre client de messagerie à un serveur SMTP. Le serveur SMTP recherche ensuite l'enregistrement MX du domaine dans l'adresse e-mail. Par exemple, avec joe@example.com, il rechercherait l'enregistrement MX pour example.com et découvrirait que le nom du serveur de messagerie pour ce domaine est, disons, mail.example.com. Le serveur SMTP obtient ensuite l'enregistrement A pour mail.example.com et se connecte au serveur de messagerie.
S'il existe plusieurs enregistrements MX, le serveur SMTP en choisira un en fonction du niveau de préférence (en commençant par le numéro de préférence le plus bas, puis en augmentant).
Ne définissez pas d'enregistrements MX avec pdnsd sauf si vous savez ce que vous faites.
owner=chaîne;
ou
ns=chaîne;
Définit un enregistrement NS (serveur de noms). Spécifie le nom de l'hôte qui doit faire autorité pour les enregistrements que vous avez définis dans la section rr. C'est typiquement l'hôte sur lequel pdnsd s'exécute.
Remarque : Dans les versions précédentes de pdnsd, cette option devait être spécifiée avant tout enregistrement a, ptr, cname, mx ou soa. Dans la version 1.2, les restrictions sur cette option sont les mêmes que pour les options mentionnées ci-dessus, et elle doit être listée après l'option name=. Cela peut être gênant si vous souhaitez utiliser un ancien fichier de configuration qui spécifie owner= avant name= (désolé pour cela). Outre une plus grande cohérence, l'avantage est que vous pouvez désormais spécifier autant d'enregistrements NS que vous le souhaitez (y compris zéro).
soa=chaîne,chaîne,nombre,timespec,timespec,timespec,timespec;
Ceci définit un enregistrement soa (début d'autorité). La première chaîne est le nom de domaine du serveur et doit être égale au nom que vous avez spécifié comme propriétaire.
La deuxième chaîne spécifie l'adresse e-mail du responsable du serveur de noms. Elle est également spécifiée comme un nom de domaine, vous devrez donc remplacer le signe @ dans le nom par un point (.) pour obtenir le nom que vous devez spécifier ici. Le paramètre suivant (le premier nombre) est le numéro de série de l'enregistrement. Vous devriez incrémenter ce nombre si vous modifiez l'enregistrement.
Le 4ème paramètre est le délai de rafraîchissement. Il spécifie après combien de temps un serveur de cache doit tenter de rafraîchir l'enregistrement mis en cache.
Le 5ème paramètre spécifie un temps après lequel un serveur de cache doit tenter de rafraîchir l'enregistrement après un échec de rafraîchissement.
Le 6ème paramètre définit le délai après lequel un enregistrement mis en cache expire s'il n'a pas été rafraîchi.
Le 7ème paramètre est le ttl spécifié dans chaque rr et doit être le même que celui donné avec l'option ttl (si vous ne spécifiez pas de ttl, utilisez la valeur par défaut 86400).
txt=chaîne,...,chaîne;
Nouveau dans la version 1.2.9 : Définit un enregistrement TXT. Vous pouvez y spécifier une ou plusieurs chaînes.

NAME

pdnsd.conf — configuration file for pdnsd

DESCRIPTION

The configuration file for pdnsd is divided into several section types. Sections are delimited by keywords followed by curly braces. Keywords are case-insensitive, but section names are case-sensitive. Within a section, options are specified as keyword=value pairs, terminated by a semicolon. Order of sections matters for some options. Options are case-insensitive, except for strings.

global Section

This section contains global settings for pdnsd. It may only occur once.

records_in_a_file=timespec;
Specifies the ttl (time to live) for all resource records that are read from a file. The default is 86400 seconds (=1 day).
perm_at_startup=(on|off);
If this is turned on, pdnsd will try to load its cache from the file specified by the cache_file option on startup. It will also dump its cache to that file on shutdown. This feature is off by default.
cache_file=string;
The string specifies a file name. If perm_at_startup is on, this file is used to store the cache. The default is /var/cache/pdnsd.plist.
max_cache_entries=int;
Specifies the maximum number of entries in the cache. The default is 1000.
max_total_ttl=timespec;
Specifies the maximum ttl for all records in the cache. This applies to records read from files, and records received from servers. It does not apply to records defined in the configuration file using neg or rr sections. The default is 86400 seconds (=1 day).
cleanup_interval=timespec;
Specifies how often the cache is cleaned up to remove expired records. The default is 1 hour.
pid_file=string;
Specifies the file name to write the process ID to. The default is /var/run/pdnsd.pid.
port=int;
Specifies the port pdnsd listens on for DNS queries. The default is 53.
bind_address=string;
Specifies the IP address to bind to. This can be an IP address or a hostname. If it is a hostname, pdnsd will resolve it and bind to the first IP address it gets. If it is empty, pdnsd will bind to all available network interfaces. The default is empty.
enable_syslog=(on|off);
Specifies whether to log messages to syslog. The default is on.
verbose=(on|off);
If this is turned on, pdnsd will be more verbose in its logging. This is off by default.
log_query=(on|off);
If this is turned on, pdnsd will log all queries it receives. This is off by default.
timeout=timespec;
Specifies the timeout for queries to upstream servers. The default is 5 seconds.
max_recursive_queries=int;
Specifies the maximum number of recursive queries pdnsd will perform. The default is 20.
neg_domain_wildcard=(on|off);
If this is turned on, negating a domain will also negate all subdomains. This is on by default since version 1.1.11.
allow_from=(ip_address_list);
Specifies a list of IP addresses or networks that are allowed to query pdnsd. If empty, all IP addresses are allowed. The list uses CIDR notation (e.g. 192.168.1.0/24). Default is empty.
deny_from=(ip_address_list);
Specifies a list of IP addresses or networks that are denied to query pdnsd. This option is checked after allow_from. The list uses CIDR notation (e.g. 10.0.0.0/8). Default is empty.

server Section

Each server section specifies a DNS server that pdnsd should use for resolving queries. You may specify multiple server sections. They are tried in order.

ip=string;
Specifies the IP address of the DNS server. This option must be specified before any file entries. Names are interpreted as absolute domain names (i.e. pdnsd assumes they end in the root domain).
port=int;
Specifies the port the DNS server listens on. The default is 53.
root=string;
Specifies the root domain for this server. This is used for recursive queries. The default is the root domain.

neg Section

Every neg section specifies a dns resource record or a dns domain that should be cached negatively locally. Queries for negatively cached records are always answered immediatley with an error or an empty answer without querying other hosts as long as the record is valid. The records defined with neg sections remain valid until they are explicitely invalidated or deleted by the user using pdnsd-ctl.
This is useful if a certain application asks periodically for nonexisting hosts or RR types and you do not want a query to go out every time the cached record has timed out. Example: Netscape Communicator will ask for the servers news and mail on startup if unconfigured. If you do not have a dns search list for your network, you can inhibit outgoing queries for these by specifying


neg {
name = news;
types = domain;
}
neg {
name = mail;
types = domain;
}

in your config file. If you have a search list, you have to repeat that for any entry in your search list in addition to the entries given above!
In versions 1.1.11 and later, if you negate whole domains this way, all subdomains will be negated as well. Thus if you specify
neg {name=example.com; types=domain;} in the config file, this will also negate www.example.com, xxx.adserver.example.com, etc.

name=string;
Specifies the name of the domain for which negative cache entries are created. This option must be specified before the types option. Names are interpreted as absolute domain names (i.e. pdnsd assumes they end in the root domain). You need to specify domain names in dotted notation (example venera.isi.edu.).
Previous versions of pdnsd required that domain names given in the configuration file ended in a dot, but since version 1.1.8b1-par8, pdnsd automatically assumes a dot at the end if it is missing.
ttl=timespec;
Specifies the ttl (time to live) for all resource records in this section after this entry. This may be redefined. The default is 86400 seconds (=1 day).
types=(domain|rr_type[,rr_type[,rr_type[,...]]]);
Specifies what is to be cached negatively: domain will cache the whole domain negatively; alternatively, you can specify a comma-separated list of RR types which are to be cached negatively. You may specify multiple types options, but domain and the RR types are mutually exclusive.
The RR types are specified using their official names from the RFC's in capitals, e.g. A, CNAME, NS, PTR, MX, AAAA, ...
The command pdnsd-ctl list-rrtypes will give you a complete list of those types. pdnsd-ctl is built along with pdnsd and will be installed in the same directory as the pdnsd binary during make install.

source Section

Every source section allows you to let pdnsd read the records from a file in an /etc/hosts-like format. pdnsd will generate records to resolve the entries address from its host name and vice versa for every entry in the file. This is normally easier than defining an rr for every of your addresses, since localhost and your other FQDNs are normally given in /etc/hosts.
The accepted format is as follows: The #-sign initiates a comment, the rest of the line from the first occurence of this character on is ignored. Empty lines are tolerated.
The first entry on a line (preceded by an arbitrary number of tabs and spaces) is the IP in dotted notation, the second entry on one line (separated by the first by an arbitrary number of tabs and spaces) is the FQDN (fully qualified domain name) for that ip. The rest of the line is ignored by default (in the original /etc/hosts, it may contain information not needed by pdnsd).

owner=string;
Specifies the name of the host pdnsd runs on and that are specified in dns answers (specifically, nameserver records). Must be specified before any file entries.
Names are interpreted as absolute domain names (i.e. pdnsd assumes they end in the root domain). You need to specify domain names in dotted notation (example venera.isi.edu.).
Previous versions of pdnsd required that domain names given in the configuration file ended in a dot, but since version 1.1.8b1-par8, pdnsd automatically assumes a dot at the end if it is missing.
ttl=timespec;
Specifies the ttl (time to live) for all resource records in this section after this entry. This may be redefined. The default is 86400 seconds (=1 day).
file=string;
The string specifies a file name. For every file entry in a source section, pdnsd will try to load the given file as described above. Failure is indicated only when the file cannot be opened, malformed entries will be ignored.
serve_aliases=(on|off);
If this is turned on pdnsd will serve the aliases given in a hosts-style file. These are the third entry in a line of a hosts-style file, which usually give a "short name" for the host. This may be used to support broken clients without a proper domain-search option. If no aliases are given in a line of the file, pdnsd behaves as without this option for this line.
This feature was suggested by Bert Frederiks.
It is off by default.
authrec=(on|off);
If this is turned on, pdnsd will create authoritative local records with the data from the hosts file. Please see the description of the option of the same name in the rr section for a closer description of what this means. Please note that this only has an effect for files sourced with file options subsequent to this option.
This is on by default.

include Section

A configuration file may include other configuration files. However, only the top-level configuration file may contain global and server sections, thus include files are effectively limited to sections that add local definitions to the cache.
Include sections currently only have one type of option, which may be given multiple times within a single section.

file=string;
The string specifies a file name. For every file option in an include section, pdnsd will parse the given file as described above. The file may contain include sections itself, but as a precaution pdnsd checks that a certain maximum depth is not exceeded to guard against the possibility of infinite recursion.

Le fichier de configuration de pdnsd est divisé en plusieurs types de sections. Les sections sont délimitées par des mots-clés suivis d'accolades. Les mots-clés ne sont pas sensibles à la casse, mais les noms de sections le sont. Dans une section, les options sont spécifiées sous forme de paires mot-clé=valeur, terminées par un point-virgule. L'ordre des sections est important pour certaines options. Les options ne sont pas sensibles à la casse, sauf pour les chaînes de caractères.

Section global

Cette section contient les paramètres globaux pour pdnsd. Elle ne peut apparaître qu'une seule fois.

records_in_a_file=timespec;
Spécifie le TTL (durée de vie) pour tous les enregistrements de ressources lus à partir d'un fichier. La valeur par défaut est 86400 secondes (=1 jour).
perm_at_startup=(on|off);
Si cette option est activée, pdnsd tentera de charger son cache à partir du fichier spécifié par l'option cache_file au démarrage. Il exportera également son cache dans ce fichier à l'arrêt. Cette fonctionnalité est désactivée par défaut.
cache_file=string;
La chaîne spécifie un nom de fichier. Si perm_at_startup est activé, ce fichier est utilisé pour stocker le cache. La valeur par défaut est /var/cache/pdnsd.plist.
max_cache_entries=int;
Spécifie le nombre maximum d'entrées dans le cache. La valeur par défaut est 1000.
max_total_ttl=timespec;
Spécifie le TTL maximum pour tous les enregistrements du cache. Cela s'applique aux enregistrements lus à partir de fichiers et aux enregistrements reçus des serveurs. Cela ne s'applique pas aux enregistrements définis dans le fichier de configuration en utilisant les sections neg ou rr. La valeur par défaut est 86400 secondes (=1 jour).
cleanup_interval=timespec;
Spécifie la fréquence à laquelle le cache est nettoyé pour supprimer les enregistrements expirés. La valeur par défaut est 1 heure.
pid_file=string;
Spécifie le nom du fichier dans lequel écrire l'ID du processus. La valeur par défaut est /var/run/pdnsd.pid.
port=int;
Spécifie le port sur lequel pdnsd écoute les requêtes DNS. La valeur par défaut est 53.
bind_address=string;
Spécifie l'adresse IP à laquelle se lier. Il peut s'agir d'une adresse IP ou d'un nom d'hôte. S'il s'agit d'un nom d'hôte, pdnsd le résoudra et se liera à la première adresse IP qu'il obtiendra. S'il est vide, pdnsd se liera à toutes les interfaces réseau disponibles. La valeur par défaut est vide.
enable_syslog=(on|off);
Spécifie si les messages doivent être enregistrés dans syslog. La valeur par défaut est activée.
verbose=(on|off);
Si cette option est activée, pdnsd sera plus verbeux dans ses journaux. Elle est désactivée par défaut.
log_query=(on|off);
Si cette option est activée, pdnsd enregistrera toutes les requêtes qu'il reçoit. Elle est désactivée par défaut.
timeout=timespec;
Spécifie le délai d'attente pour les requêtes aux serveurs en amont. La valeur par défaut est de 5 secondes.
max_recursive_queries=int;
Spécifie le nombre maximum de requêtes récursives que pdnsd effectuera. La valeur par défaut est de 20.
neg_domain_wildcard=(on|off);
Si cette option est activée, la négation d'un domaine niera également tous ses sous-domaines. Elle est activée par défaut depuis la version 1.1.11.
allow_from=(liste_d_adresses_ip);
Spécifie une liste d'adresses IP ou de réseaux autorisés à interroger pdnsd. Si elle est vide, toutes les adresses IP sont autorisées. La liste utilise la notation CIDR (par exemple, 192.168.1.0/24). La valeur par défaut est vide.
deny_from=(liste_d_adresses_ip);
Spécifie une liste d'adresses IP ou de réseaux interdits d'interroger pdnsd. Cette option est vérifiée après allow_from. La liste utilise la notation CIDR (par exemple, 10.0.0.0/8). La valeur par défaut est vide.

Section server

Chaque section server spécifie un serveur DNS que pdnsd doit utiliser pour résoudre les requêtes. Vous pouvez spécifier plusieurs sections server. Elles sont essayées dans l'ordre.

ip=string;
Spécifie l'adresse IP du serveur DNS. Cette option doit être spécifiée avant toute entrée de fichier. Les noms sont interprétés comme des noms de domaine absolus (c'est-à-dire que pdnsd suppose qu'ils se terminent par le domaine racine).
port=int;
Spécifie le port sur lequel le serveur DNS écoute. La valeur par défaut est 53.
root=string;
Spécifie le domaine racine pour ce serveur. Il est utilisé pour les requêtes récursives. La valeur par défaut est le domaine racine.

Section neg

Chaque section neg spécifie un enregistrement de ressource DNS ou un domaine DNS qui doit être mis en cache négativement localement. Les requêtes pour les enregistrements mis en cache négativement reçoivent toujours une réponse immédiate avec une erreur ou une réponse vide, sans interroger d'autres hôtes tant que l'enregistrement est valide. Les enregistrements définis avec les sections neg restent valides jusqu'à ce qu'ils soient explicitement invalidés ou supprimés par l'utilisateur à l'aide de pdnsd-ctl.
Ceci est utile si une certaine application demande périodiquement des hôtes inexistants ou des types d'enregistrements inexistants et que vous ne voulez pas qu'une requête soit envoyée à chaque fois que l'enregistrement mis en cache a expiré. Exemple : Netscape Communicator demandera les serveurs news et mail au démarrage s'ils ne sont pas configurés. Si vous n'avez pas de liste de recherche DNS pour votre réseau, vous pouvez inhiber les requêtes sortantes pour ceux-ci en spécifiant


neg {
name = news;
types = domain;
}
neg {
name = mail;
types = domain;
}

dans votre fichier de configuration. Si vous avez une liste de recherche, vous devez répéter cela pour chaque entrée de votre liste de recherche en plus des entrées données ci-dessus !
Dans les versions 1.1.11 et ultérieures, si vous niez des domaines entiers de cette manière, tous les sous-domaines seront également niés. Ainsi, si vous spécifiez
neg {name=example.com; types=domain;} dans le fichier de configuration, cela niera également www.example.com, xxx.adserver.example.com, etc.

name=string;
Spécifie le nom du domaine pour lequel les entrées de cache négatif sont créées. Cette option doit être spécifiée avant l'option types. Les noms sont interprétés comme des noms de domaine absolus (c'est-à-dire que pdnsd suppose qu'ils se terminent par le domaine racine). Vous devez spécifier les noms de domaine en notation pointée (exemple venera.isi.edu.).
Les versions précédentes de pdnsd exigeaient que les noms de domaine donnés dans le fichier de configuration se terminent par un point, mais depuis la version 1.1.8b1-par8, pdnsd suppose automatiquement un point à la fin s'il est manquant.
ttl=timespec;
Spécifie le TTL (durée de vie) pour tous les enregistrements de ressources dans cette section après cette entrée. Ceci peut être redéfini. La valeur par défaut est 86400 secondes (=1 jour).
types=(domain|rr_type[,rr_type[,rr_type[,...]]]);
Spécifie ce qui doit être mis en cache négativement : domain mettra en cache le domaine entier négativement ; alternativement, vous pouvez spécifier une liste de types d'enregistrements séparés par des virgules qui doivent être mis en cache négativement. Vous pouvez spécifier plusieurs options types, mais domain et les types d'enregistrements sont mutuellement exclusifs.
Les types d'enregistrements sont spécifiés en utilisant leurs noms officiels des RFC en majuscules, par exemple A, CNAME, NS, PTR, MX, AAAA, ...
La commande pdnsd-ctl list-rrtypes vous donnera une liste complète de ces types. pdnsd-ctl est compilé avec pdnsd et sera installé dans le même répertoire que le binaire pdnsd lors de make install.

Section source

Chaque section source vous permet de faire lire à pdnsd les enregistrements d'un fichier au format similaire à /etc/hosts. pdnsd générera des enregistrements pour résoudre l'adresse des entrées à partir de son nom d'hôte et vice versa pour chaque entrée du fichier. C'est normalement plus facile que de définir un enregistrement pour chacune de vos adresses, puisque localhost et vos autres FQDN sont normalement donnés dans /etc/hosts.
Le format accepté est le suivant : Le signe # initie un commentaire, le reste de la ligne à partir de la première occurrence de ce caractère est ignoré. Les lignes vides sont tolérées.
La première entrée sur une ligne (précédée d'un nombre arbitraire de tabulations et d'espaces) est l'adresse IP en notation pointée, la deuxième entrée sur une ligne (séparée de la première par un nombre arbitraire de tabulations et d'espaces) est le FQDN (nom de domaine pleinement qualifié) pour cette adresse IP. Le reste de la ligne est ignoré par défaut (dans le /etc/hosts original, il peut contenir des informations dont pdnsd n'a pas besoin).

owner=string;
Spécifie le nom de l'hôte sur lequel pdnsd s'exécute et qui est spécifié dans les réponses DNS (spécifiquement, les enregistrements de serveurs de noms). Doit être spécifié avant toute entrée de fichier.
Les noms sont interprétés comme des noms de domaine absolus (c'est-à-dire que pdnsd suppose qu'ils se terminent par le domaine racine). Vous devez spécifier les noms de domaine en notation pointée (exemple venera.isi.edu.).
Les versions précédentes de pdnsd exigeaient que les noms de domaine donnés dans le fichier de configuration se terminent par un point, mais depuis la version 1.1.8b1-par8, pdnsd suppose automatiquement un point à la fin s'il est manquant.
ttl=timespec;
Spécifie le TTL (durée de vie) pour tous les enregistrements de ressources dans cette section après cette entrée. Ceci peut être redéfini. La valeur par défaut est 86400 secondes (=1 jour).
file=string;
La chaîne spécifie un nom de fichier. Pour chaque entrée de fichier dans une section source, pdnsd tentera de charger le fichier donné comme décrit ci-dessus. L'échec n'est indiqué que lorsque le fichier ne peut pas être ouvert, les entrées malformées seront ignorées.
serve_aliases=(on|off);
Si cette option est activée, pdnsd servira les alias donnés dans un fichier de style hosts. Ce sont la troisième entrée d'une ligne d'un fichier de style hosts, qui donne généralement un "nom court" pour l'hôte. Ceci peut être utilisé pour supporter des clients défectueux sans option de recherche de domaine appropriée. Si aucun alias n'est donné sur une ligne du fichier, pdnsd se comporte comme sans cette option pour cette ligne.
Cette fonctionnalité a été suggérée par Bert Frederiks.
Elle est désactivée par défaut.
authrec=(on|off);
Si cette option est activée, pdnsd créera des enregistrements locaux autoritaires avec les données du fichier hosts. Veuillez consulter la description de l'option du même nom dans la section rr pour une description plus détaillée de ce que cela signifie. Veuillez noter que cela n'a d'effet que pour les fichiers sourcés avec des options file ultérieures à cette option.
Cette option est activée par défaut.

Section include

Un fichier de configuration peut inclure d'autres fichiers de configuration. Cependant, seul le fichier de configuration de niveau supérieur peut contenir des sections globales et serveur, ainsi les fichiers inclus sont effectivement limités aux sections qui ajoutent des définitions locales au cache.
Les sections include n'ont actuellement qu'un seul type d'option, qui peut être donné plusieurs fois dans une seule section.

file=string;
La chaîne spécifie un nom de fichier. Pour chaque option file dans une section include, pdnsd analysera le fichier donné comme décrit ci-dessus. Le fichier peut lui-même contenir des sections include, mais par mesure de précaution, pdnsd vérifie qu'une profondeur maximale donnée n'est pas dépassée pour se prémunir contre la possibilité de récursion infinie.
