NOM

pimsync-migration — guide de migration de vdirsyncer vers pimsync

DESCRIPTION

Ce guide de migration couvre les changements à prendre en compte lors de la migration de vdirsyncer vers pimsync. Il s'adresse aux utilisateurs ayant une configuration fonctionnelle de l'implémentation précédente.

FONCTIONNALITÉS MANQUANTES

Les fonctionnalités suivantes sont implémentées par vdirsyncer 0.19.3, mais ne sont actuellement pas disponibles dans pimsync :

  • auth digest Ceci doit être implémenté en tant que middleware ‘tower-service’. Ne devrait pas être trop compliqué.
  • partial_sync Ce paramètre de configuration ne reviendra probablement pas de la même manière. Un « miroir » est le successeur le plus probable. Avec cette directive définie, pimsync(1) ferait de B un miroir de A. Dans ce mode, un seul stockage DOIT être défini comme read_only.
  • post_hook paramètre de configuration. Les futures versions pourraient diffuser des événements, de sorte que des gestionnaires externes puissent y réagir à la place.
  • start_date, end_date, et item_types paramètres de configuration pour les stockages CalDav. Ceux-ci sont prévus, mais sans calendrier précis.
  • Le stockage singlefile, qui sauvegarde tous les événements d'un calendrier dans un seul fichier.

Les fonctionnalités suivantes ne sont pas présentes et il est peu probable qu'elles soient implémentées sans un cas d'utilisation convaincant. Veuillez nous contacter si vous avez besoin de certaines d'entre elles :

  • Encodages autres que UTF-8
  • Toutes les métadonnées sont synchronisées. La sélection de champs individuels n'est pas actuellement possible.
  • Le paramètre de configuration fileignoreext.

FORMAT DU FICHIER DE CONFIGURATION

Le format de configuration a changé. L'approche générale est la même, mais la syntaxe a été grandement simplifiée pour être écrite par des humains. Techniquement, le format est le format *scfg*. Il est documenté en détail dans pimsync.conf(5).

Ce qui suit :

[pair.contacts]
a = "contacts_local"
b = "contacts_fastmail"
collections = "all"
conflict_resolution = ["nvim", "-d"]

Devient :

pair contacts {
	storage_a contacts_local
	storage_b contacts_fastmail
	collections all
	conflict_resolution nvim -d
}

Et ce qui suit :

[storage.contacts_local]
type = "filesystem"
path = "~/.local/share/contacts/"
fileext = "vcf"

Devient ceci :

storage contacts_local {
	type vdir/vcard
	path ~/.local/share/contacts/
	fileext vcf
}

MÉCANISMES DE RÉCUPÉRATION

Le mécanisme prompt pour récupérer les mots de passe a été supprimé.

Une définition fetch avec une command ressemblait auparavant à ceci :

password.fetch = ["command", "hiq", "-dFpassword", "proto=carddavs", "username=…"]

Maintenant, un bloc est fourni à password avec une seule directive cmd spécifiant la commande et ses arguments.

password {
	cmd hiq -dFpassword proto=carddavs username=…
}

Une définition fetch avec un shell utilise maintenant une syntaxe similaire :

password {
	shell pass show communication/migadu.com | head -1
}

MIGRATION FETCH / PROMPT

Utilisez plutôt un inviteur externe. Pour un inviteur graphique, envisagez d'utiliser :

password {
	cmd zenity --password
}

pimsync(1) demandera les mots de passe en séquence, donc aucune considération spéciale n'est requise pour éviter les invites concurrentes.

LA DÉCOUVERTE MANUELLE N'EST PLUS REQUISE

La découverte des collections à l'avance n'est plus nécessaire. Les collections sont découvertes automatiquement si nécessaire. La commande discover imprime simplement les collections découvertes à titre de commodité pour configurer manuellement les collections. Elle n'affecte pas l'état interne de pimsync. Voir pimsync(1) pour les détails.

CRÉATION AUTOMATIQUE DES COLLECTIONS

Si une paire est configurée pour synchroniser toutes les collections depuis a et qu'une nouvelle collection est trouvée sur le stockage A, alors la collection sera automatiquement créée sur le stockage B. Pour les scénarios où la création automatique de collections est indésirable, des collections individuelles devraient être explicitement spécifiées à la place.

LES ESSAIS À BLANC SONT MAINTENANT POSSIBLES

Il est maintenant possible d'exécuter un essai à blanc, qui imprime uniquement le plan provisoire sans l'exécuter. La sortie est quelque peu concise à ce stade et pas dans sa forme finale. Cela peut être utilisé pour auditer de nouvelles configurations et s'assurer que les actions planifiées sont sensées.

LES STOCKAGES FILESYSTEM ONT ÉTÉ RENOMMÉS EN VDIR

Les collections du système de fichiers ont été renommées en vdir. Elles doivent maintenant spécifier le type d'éléments qu'elles contiennent.

Un répertoire avec des fichiers icalendar devrait spécifier :

type = "vdir/icalendar"

Un répertoire avec des fichiers vcard devrait spécifier :

type vdir/vcard

ENCODAGES PERSONNALISÉS POUR LE STOCKAGE VDIR

Le stockage vdir enregistre les fichiers en UTF-8. Si un autre encodage est requis pour un scénario quelconque, veuillez ouvrir un problème à l'adresse : https://todo.sr.ht/~whynothugo/pimsync

CHAMP FILESYSTEM FILEEXT

Le champ fileext pour les stockages du système de fichiers nécessitait un point initial. Ce n'est plus le cas ; le point n'est pas considéré comme faisant partie des extensions et doit être omis. Omettez le point initial lors de la portabilité des configurations.

LES COLLECTIONS SONT DÉCLARÉES DANS UN FORMAT DIFFÉRENT

Pour synchroniser toutes les collections des deux côtés, utilisez :

collections all

Pour synchroniser toutes les collections présentes sur un stockage spécifique, utilisez :

collections from b

SPÉCIFICATION DES COLLECTIONS INDIVIDUELLES

Les collections individuelles peuvent être spécifiées par id ou par href: file ... id est le nom du processus de découverte. file ... href est le chemin complet à l'intérieur du stockage.

pimsync-migration(7) — pimsync

NAME

pimsync-migration — migration guide for pimsync

DESCRIPTION

This page describes the changes in pimsync, and how to migrate your configuration.

MISSING FEATURES

The following features have been removed:

  • The mirror directive has been removed. Use dry_run instead.
  • The max_items directive has been removed.
  • The search_limit directive has been removed.
  • The auto_create_folders directive has been removed.
  • The autodetect_collections directive has been removed.

CONFIGURATION FILE FORMAT

The configuration file format has changed to scfg. You can find more information about it in the pimsync.conf(5) manual page.

FETCH MECHANISMS

The fetch mechanisms have been simplified. You no longer need to specify how to fetch collections. Pimsync will now automatically detect the fetch mechanism based on the storage type.

MANUAL DISCOVERY IS NO LONGER REQUIRED

Automatic discovery of collections is now the default. You no longer need to specify the autodetect_collections directive.

AUTOMATIC CREATION OF COLLECTIONS

The automatic creation of collections is now handled by the auto_create_folders directive, which has been removed. Pimsync will now automatically create collections if they do not exist.

DRY RUNS ARE NOW POSSIBLE

A new dry_run directive has been added, which allows you to test your configuration without making any changes.

FILESYSTEM STORAGES HAVE BEEN RENAMED TO VDIR

The filesystem storage type has been renamed to vdir. This reflects the underlying vdir format used by pimsync.

CUSTOM ENCODINGS FOR VDIR STORAGE

You can now specify custom encodings for vdir storage using the encoding directive.

storage my_vdir {
	type vdir
	path /path/to/vdir/
	encoding utf-8
}

FILESYSTEM FILEEXT FIELD

The fileext field is now specific to the vdir storage. It is used to specify the file extension for the vdir files.

COLLECTIONS ARE DECLARED IN A DIFFERENT FORMAT

Generally, using an id is recommended. Using href is intended for situations where discovery is not possible or where multiple collections have the same id. To specify a single collection by id, use:

collection c037725e-e4fd-4b3e-b73d-d5e27d5a90a9

The above will find synchronise collections with the given id between both storages.

Two different collections can mapped on each side:

pair my_pair {
	# other fields here

	# first collection
	collection {
			alias personal
			href_a /calendars/hugo/c037725e-e4fd-4b3e-b73d-d5e27d5a90a9/
			href_b /personal/
	}

	# another collection
	collection {
			alias work
			id_a work
			href_b /calendars/work/
	}
}

Specifying collection null is no longer allowed; configuration should point to an explicitly collection instead.

HTTP STORAGE IS NOW CALLED WEBCAL

The type of the http storage is now webcal, to better reflect its nature; other storages also use HTTP internally.

WEBCAL COLLECTION ID

Due to its nature, the WebCal storage has a single collection. However, this collection has no id. A collection id must be provided for it explicitly. This simplifies configurations where it must be synchronised to another calendar with the same collection id.

storage calendars_lessons {
	type http
	collection_id lessons
	url {
		cmd hiq -dFurl proto=webcal alias=lessons
	}
}

READ ONLY

The read_only takes no values. Its presence makes a storage read only. To make a storage read-write, remove the directive.

STATUS

Vdirsyncer keeps a status database in order to distinguish whether an item has changed on one side or both. Pimsync does not import this status database in any way. If you are migrating and have existing remote and local storages, makes sure that they are in sync before switching over. After the first run, pimsync will build its own status database.

Migrating with out-of-sync storages will result in conflicts during the first run.

TLS CONFIGURATION

The verify configuration directive is now named tls_root.

The verify_fingerprint configuration directive is now named tls_fingerprint.

ISSUES

Please report issues at: https://todo.sr.ht/~whynothugo/vdirsyncer-rs

If you have a working vdirsyncer configuration, and this page is missing details necessary when upgrading, please reach out so this documentation can be improved.
