pidfd_open(2) Manuel des appels système pidfd_open(2)

NOM

pidfd_open - obtenir un descripteur de fichier qui référence une tâche

BIBLIOTHÉQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/syscall.h>      /* Définition des constantes SYS_* */
#include <unistd.h>
int syscall(SYS_pidfd_open, pid_t pid, unsigned int flags);

Note: glibc ne fournit pas d'enveloppe pour pidfd_open(), nécessitant l'utilisation de syscall(2).

DESCRIPTION

L'appel système pidfd_open() crée un descripteur de fichier qui référence la tâche référencée par pid. Le descripteur de fichier est retourné comme résultat de la fonction ; le drapeau close-on-exec est défini sur le descripteur de fichier.

L'argument flags a soit la valeur 0, soit contient les indicateurs suivants :

PIDFD_NONBLOCK (depuis Linux 5.10)
Retourne un descripteur de fichier non bloquant. Si la tâche référencée par le descripteur de fichier n'a pas encore terminé, alors une tentative d'attendre sur le descripteur de fichier en utilisant waitid(2) retournera immédiatement l'erreur EAGAIN au lieu de bloquer.
PIDFD_THREAD (depuis Linux 6.9)
Crée un descripteur de fichier qui référence un thread spécifique, plutôt qu'un processus (leader de groupe de threads). Si cet indicateur n'est pas défini, pid doit référencer un processus.

VALEUR DE RETOUR

En cas de succès, pidfd_open() retourne un descripteur de fichier (un entier non négatif). En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

ERREURS

EINVAL
flags n'est pas valide.
EINVAL
pid n'est pas valide.
EMFILE
La limite par processus sur le nombre de descripteurs de fichiers ouverts a été atteinte (voir la description de RLIMIT_NOFILE dans getrlimit(2)).
ENFILE
La limite système sur le nombre total de fichiers ouverts a été atteinte.
ENODEV
Le système de fichiers inode anonyme n'est pas disponible dans ce noyau.
ENOMEM
Une quantité insuffisante de mémoire noyau était disponible.
ESRCH
Le processus spécifié par pid n'existe pas.

NORMES

Linux.

HISTORIQUE

Linux 5.3.

NOTES

La séquence de code suivante peut être utilisée pour obtenir un descripteur de fichier pour l'enfant de fork(2) :


pid = fork();
if (pid > 0) {     /* Si parent */
    pidfd = pidfd_open(pid, 0);
    ...
}

Même si l'enfant a déjà terminé au moment de l'appel pidfd_open(), son PID n'aura pas été recyclé et le descripteur de fichier retourné fera référence au processus zombie résultant. Notez, cependant, que ceci n'est garanti que si les conditions suivantes sont remplies :

•
la disposition de SIGCHLD n'a pas été explicitement définie sur SIG_IGN (voir sigaction(2)) ;
•
l'indicateur SA_NOCLDWAIT n'a pas été spécifié lors de l'établissement d'un gestionnaire pour SIGCHLD ou lors de la définition de la disposition de ce signal sur SIG_DFL (voir sigaction(2)) ; et
•
le processus zombie n'a pas été récupéré ailleurs dans le programme (par exemple, soit par un gestionnaire de signal exécuté de manière asynchrone, soit par wait(2) ou similaire dans un autre thread).

Si l'une de ces conditions n'est pas remplie, alors le processus enfant (ainsi qu'un descripteur de fichier PID qui y fait référence) doit plutôt être créé en utilisant clone(2) avec l'indicateur CLONE_PIDFD.

Cas d'utilisation des descripteurs de fichier PID

Un descripteur de fichier PID retourné par pidfd_open() (ou par clone(2) avec l'indicateur CLONE_PID) peut être utilisé aux fins suivantes :

•
L'appel système pidfd_send_signal(2) peut être utilisé pour envoyer un signal au processus référencé par un descripteur de fichier PID.
•
Un descripteur de fichier PID peut être surveillé en utilisant poll(2), select(2), et epoll(7).
Lorsque la tâche à laquelle il fait référence se termine et devient un zombie, ces interfaces indiquent que le descripteur de fichier est lisible (EPOLLIN). Lorsque la tâche est récupérée, ces interfaces produisent un événement de raccrochage (EPOLLHUP).
Notez, cependant, que dans l'implémentation actuelle, rien ne peut être lu du descripteur de fichier (read(2) sur le descripteur de fichier échoue avec l'erreur EINVAL). Le comportement de sondage dépend de si l'indicateur PIDFD_THREAD a été utilisé lors de l'obtention du descripteur de fichier :
•
Avec PIDFD_THREAD, le descripteur de fichier devient lisible lorsque la tâche se termine et devient un zombie, même si le groupe de threads n'est pas vide.
•
Sans PIDFD_THREAD, le descripteur de fichier ne devient lisible que lorsque le dernier thread du groupe de threads se termine.
•
Si le descripteur de fichier PID fait référence à un enfant du processus appelant, alors il peut être attendu en utilisant waitid(2).
•
L'appel système pidfd_getfd(2) peut être utilisé pour obtenir une copie d'un descripteur de fichier d'un autre processus référencé par un descripteur de fichier PID.
•
Un descripteur de fichier PID peut être utilisé comme argument de setns(2) afin de passer dans un ou plusieurs des mêmes espaces de noms que le processus référencé par le descripteur de fichier.
•
Un descripteur de fichier PID peut être utilisé comme argument de process_madvise(2) afin de fournir des conseils sur les modèles d'utilisation de la mémoire du processus référencé par le descripteur de fichier.

L'appel système pidfd_open() est la manière préférée d'obtenir un descripteur de fichier PID pour un processus déjà existant. L'alternative est d'obtenir un descripteur de fichier en ouvrant un répertoire /proc/pid. Cependant, cette dernière technique n'est possible que si le système de fichiers proc(5) est monté ; de plus, le descripteur de fichier obtenu de cette manière n'est pas sondable et ne peut pas être attendu avec waitid(2).

pidfd_open(2) - Arch manual pages

NOM

pidfd_open - ouvrir un descripteur de fichier pour un processus

BIBLIOTHQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <sys/syscall.h>
#include <linux/pid.h>

int pidfd_open(pid_t pid, unsigned int flags);

DESCRIPTION

L'appel système pidfd_open() crée un descripteur de fichier qui fait référence à un processus spécifié par pid. Ce descripteur de fichier est un pidfd.

Les pidfds sont une amélioration par rapport aux PIDs (identifiants de processus). Alors qu'un PID est simplement un nombre qui peut être réutilisé après qu'un processus se termine, un pidfd est un descripteur de fichier qui reste valide tant que le processus référencé existe.

Les pidfds peuvent être utilisés avec plusieurs appels système pour obtenir des informations sur le processus ou pour le signaler. Les principaux avantages sont qu'ils permettent de surveiller un processus spécifique sans risque de réutilisation du PID et qu'ils peuvent être utilisés avec des appels système qui prennent un descripteur de fichier, comme poll(2), epoll(7), select(2), pidfd_getfd(2) et pidfd_send_signal(2).

Actuellement, le seul flags pris en charge est 0.

Le pid spécifié doit être celui d'un processus existant. Par défaut, pidfd_open() ne peut être appelé qu'avec un pidfd pour le processus courant (0) ou pour un processus enfant direct du processus appelant. La permission d'obtenir un pidfd pour un autre processus est accordée par le capability CAP_SYS_PTRACE ou si le processus appelant est en mode débogage du processus cible (par exemple, via ptrace).

Les pidfds ne peuvent être ni dupliqués ni utilisés avec dup(2), fork(2), ou pidfd_open(2).

VALEUR RENVOYÉE

En cas de succès, pidfd_open() renvoie un nouveau pidfd (un descripteur de fichier non négatif). En cas d'échec, -1 est renvoyé et errno est défini pour indiquer l'erreur.

ERREURS

Les erreurs suivantes peuvent être définies pour errno :

EINVAL
Les flags ne sont pas 0, ou le pid est 0 mais la cible n'est pas le processus courant, ou un appel système est en cours d'arrêt.
ESRCH
Aucun processus ne correspond au pid spécifié.
EPERM
Le processus appelant n'a pas la permission d'obtenir un pidfd pour le processus spécifié (voir la description de CAP_SYS_PTRACE).

NORMES

Cette fonctionnalité est spécifique à Linux et a été introduite dans le noyau 5.1.

HISTOIRE

Introduit dans le noyau Linux 5.1.

NOTES

L'utilisation la plus courante d'un pidfd est avec poll(2) ou epoll(7). Lorsqu'un processus se termine, le pidfd associé devient prêt pour la lecture. Cela permet de savoir quand un processus est terminé sans avoir à utiliser waitpid(2), ce qui peut bloquer si aucun enfant n'est terminé.

Pour obtenir le pidfd du processus courant, vous pouvez appeler pidfd_open(0, 0).

Le noyau Linux peut modifier la sémantique des pidfds de manière rétrocompatible. Cela signifie que des appels système plus récents peuvent être ajoutés pour fonctionner avec des pidfds.

EXEMPLES

Le programme suivant ouvre un pidfd pour le processus dont le PID est passé en argument de la ligne de commande, puis utilise poll pour attendre la fin du processus.

#include <errno.h>
#include <poll.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <sys/syscall.h>
#include <unistd.h>

#ifndef __NR_pidfd_open
#define __NR_pidfd_open __NR_pidfd_open
#endif

int main(int argc, char *argv[])
{
    int pidfd;
    struct pollfd pollfd;
    int ready;

    if (argc != 2) {
        fprintf(stderr, "Usage: %s <pid>\n", argv[0]);
        exit(EXIT_FAILURE);
    }

    pidfd = syscall(__NR_pidfd_open, atoi(argv[1]), 0);
    if (pidfd == -1) {
        perror("pidfd_open");
        exit(EXIT_FAILURE);
    }

    pollfd.fd = pidfd;
    pollfd.events = POLLIN;
    ready = poll(&pollfd, 1, -1);
    if (ready == -1) {
        perror("poll");
        exit(EXIT_FAILURE);
    }

    printf("Events (%#x): POLLIN is %sset\n", pollfd.revents,
           (pollfd.revents & POLLIN) ? "" : "not ");

    close(pidfd);
    exit(EXIT_SUCCESS);
}
