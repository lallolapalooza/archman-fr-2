NOM

pid_namespaces - aperçu des namespaces PID Linux

DESCRIPTION

Pour un aperçu des namespaces, voir namespaces(7).

Les namespaces PID isolent l'espace des identifiants de processus (PID), ce qui signifie que des processus dans différents namespaces PID peuvent avoir le même PID. Les namespaces PID permettent aux conteneurs de fournir des fonctionnalités telles que la suspension/reprise de l'ensemble des processus du conteneur et la migration du conteneur vers un nouvel hôte tout en conservant les mêmes PIDs pour les processus à l'intérieur du conteneur.

Les PIDs dans un nouveau namespace PID commencent à 1, un peu comme sur un système autonome, et les appels à fork(2), vfork(2), ou clone(2) produiront des processus avec des PIDs uniques au sein du namespace.

L'utilisation des namespaces PID nécessite un noyau configuré avec l'option CONFIG_PID_NS.

Le processus init du namespace

Le premier processus créé dans un nouveau namespace (c'est-à-dire le processus créé à l'aide de clone(2) avec le drapeau CLONE_NEWPID, ou le premier enfant créé par un processus après un appel à unshare(2) utilisant le drapeau CLONE_NEWPID) a le PID 1, et est le processus "init" pour le namespace (voir init(1)). Ce processus devient le parent de tout processus enfant qui est orphelin car un processus résidant dans ce namespace PID s'est terminé (voir ci-dessous pour plus de détails).

Si le processus "init" d'un namespace PID se termine, le noyau termine tous les processus du namespace via un signal SIGKILL. Ce comportement reflète le fait que le processus "init" est essentiel au bon fonctionnement d'un namespace PID. Dans ce cas, un appel ultérieur à fork(2) dans ce namespace PID échouera avec l'erreur ENOMEM ; il n'est pas possible de créer un nouveau processus dans un namespace PID dont le processus "init" s'est terminé. De tels scénarios peuvent survenir lorsque, par exemple, un processus utilise un descripteur de fichier ouvert pour un fichier /proc/pid/ns/pid correspondant à un processus qui était dans un namespace pour faire un setns(2) dans ce namespace après que le processus "init" se soit terminé. Un autre scénario possible peut survenir après un appel à unshare(2) : si le premier enfant créé subséquemment par un fork(2) se termine, alors les appels ultérieurs à fork(2) échoueront avec ENOMEM.

Seuls les signaux pour lesquels le processus "init" a établi un gestionnaire de signal peuvent être envoyés au processus "init" par d'autres membres du namespace PID. Cette restriction s'applique même aux processus privilégiés, et empêche les autres membres du namespace PID de tuer accidentellement le processus "init".

De même, un processus dans un namespace parent peut — sous réserve des vérifications de permission habituelles décrites dans kill(2) — envoyer des signaux au processus "init" d'un namespace PID enfant uniquement si le processus "init" a établi un gestionnaire pour ce signal. (Dans le gestionnaire, le champ si_pid de siginfo_t décrit dans sigaction(2) sera zéro.) SIGKILL ou SIGSTOP sont traités exceptionnellement : ces signaux sont délivrés de force lorsqu'ils sont envoyés depuis un namespace PID parent. Aucun de ces signaux ne peut être capturé par le processus "init", et entraînera donc les actions usuelles associées à ces signaux (respectivement, terminer et arrêter le processus).

Depuis Linux 3.4, l'appel système reboot(2) provoque l'envoi d'un signal au processus "init" du namespace. Voir reboot(2) pour plus de détails.

Anidations des namespaces PID

Les namespaces PID peuvent être imbriqués : chaque namespace PID a un parent, sauf le namespace PID initial ("racine"). Le parent d'un namespace PID est le namespace PID du processus qui a créé le namespace en utilisant clone(2) ou unshare(2). Les namespaces PID forment ainsi un arbre, toutes les ascendances remontant ultimement au namespace racine. Depuis Linux 3.7, le noyau limite la profondeur d'imbrication maximale pour les namespaces PID à 32.

Un processus est visible par les autres processus dans son namespace PID, et par les processus dans chaque namespace PID parent direct remontant jusqu'au namespace PID racine. Dans ce contexte, "visible" signifie qu'un processus peut être la cible d'opérations par un autre processus en utilisant des appels système qui spécifient un identifiant de processus. Inversement, les processus d'un namespace PID enfant ne peuvent pas voir les processus des namespaces parents et plus éloignés. Plus succinctement : un processus peut voir (par exemple, envoyer des signaux avec kill(2), définir des valeurs de priorité avec setpriority(2), etc.) uniquement les processus contenus dans son propre namespace PID et dans les descendants de ce namespace.

Un processus a un identifiant de processus dans chaque couche de la hiérarchie des namespaces PID dans laquelle il est visible, et en remontant par chaque namespace parent direct jusqu'au namespace PID racine. Les appels système qui opèrent sur des identifiants de processus opèrent toujours en utilisant l'identifiant de processus visible dans le namespace PID de l'appelant. Un appel à getpid(2) renvoie toujours le PID associé au namespace dans lequel le processus a été créé.

Certains processus dans un namespace PID peuvent avoir des parents qui sont à l'extérieur du namespace. Par exemple, le parent du processus initial dans le namespace (c'est-à-dire le processus init(1) avec le PID 1) réside nécessairement dans un autre namespace. De même, les enfants directs d'un processus qui utilise setns(2) pour faire rejoindre ses enfants à un namespace PID sont dans un namespace PID différent de celui de l'appelant de setns(2). Les appels à getppid(2) pour de tels processus renvoient 0.

Bien que les processus puissent descendre librement dans les namespaces PID enfants (par exemple, en utilisant setns(2) avec un descripteur de fichier de namespace PID), ils ne peuvent pas se déplacer dans l'autre direction. C'est-à-dire que les processus ne peuvent pas entrer dans des namespaces parents (parent, grand-parent, etc.). Changer de namespace PID est une opération à sens unique.

L'opération NS_GET_PARENT de ioctl(2) peut être utilisée pour découvrir la relation parentale entre les namespaces PID ; voir ioctl_nsfs(2).

sémantique de setns(2) et unshare(2)

Les appels à setns(2) qui spécifient un descripteur de fichier de namespace PID et les appels à unshare(2) avec le drapeau CLONE_NEWPID font que les enfants créés par l'appelant par la suite sont placés dans un namespace PID différent de celui de l'appelant. (Depuis Linux 4.12, ce namespace PID est montré via le fichier /proc/pid/ns/pid_for_children, comme décrit dans namespaces(7).) Ces appels ne changent cependant pas le namespace PID du processus appelant, car cela changerait la perception de son propre PID par l'appelant (tel que rapporté par getpid()), ce qui casserait de nombreuses applications et bibliothèques.

Pour dire les choses autrement : l'appartenance d'un processus à un namespace PID est déterminée lors de la création du processus et ne peut pas être modifiée par la suite. Entre autres choses, cela signifie que la relation parentale entre les processus reflète la relation parentale entre les namespaces PID : le parent d'un processus se trouve soit dans le même namespace, soit réside dans le namespace PID parent immédiat.

Un processus ne peut appeler unshare(2) avec le drapeau CLONE_NEWPID qu'une seule fois. Après avoir effectué cette opération, son lien symbolique /proc/pid/ns/pid_for_children sera vide jusqu'à ce que le premier enfant soit créé dans le namespace.

Adoption des enfants orphelins

Lorsque le processus "init" d'un namespace PID se termine, le noyau fait en sorte que tous les processus encore vivants dans ce namespace PID soient adoptés par le processus "init" du namespace PID parent. Ce mécanisme permet d'éviter que les processus orphelins ne soient adoptés par le processus avec PID 1 du namespace racine (voir init(1)), ce qui pourrait révéler des informations sur le namespace racine à des processus confinés dans des namespaces enfants.

Dans les versions du noyau antérieures à 3.4, le processus parent de tous les processus orphelins dans un namespace PID était le processus avec PID 1 du namespace racine. Depuis Linux 3.4, le processus parent de ces processus orphelins est le processus qui a créé le namespace PID enfant.

EXEMPLES

Exemple d'utilisation de namespaces PID avec unshare(2) :

#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int main() {
    pid_t pid;

    pid = fork();
    if (pid == -1) {
        perror("fork");
        exit(EXIT_FAILURE);
    }

    if (pid == 0) { /* Child process */
        /* Create a new PID namespace */
        if (unshare(CLONE_NEWPID) == -1) {
            perror("unshare");
            exit(EXIT_FAILURE);
        }

        /* Now, the child is the init process in its own PID namespace */
        printf("Inside new PID namespace: PID=%d, PPID=%d\n", getpid(), getppid());

        /* Spawn a child process */
        pid = fork();
        if (pid == -1) {
            perror("fork");
            exit(EXIT_FAILURE);
        }

        if (pid == 0) { /* Grandchild process */
            printf("Inside grandchild: PID=%d, PPID=%d\n", getpid(), getppid());
            sleep(5); /* Keep the process alive for observation */
        } else { /* Child process */
            printf("Child process waiting for grandchild...\n");
            wait(NULL);
            printf("Grandchild finished.\n");
        }
        exit(EXIT_SUCCESS);
    } else { /* Parent process */
        printf("Parent process: PID=%d, Child PID=%d\n", getpid(), pid);
        wait(NULL); /* Wait for the child to exit */
        printf("Parent process finished.\n");
    }

    return 0;
}

Compilez et exécutez ce programme. La sortie devrait ressembler à ceci :

Parent process: PID=12345, Child PID=12346
Inside new PID namespace: PID=1, PPID=0
Child process waiting for grandchild...
Inside grandchild: PID=2, PPID=1
Grandchild finished.
Parent process finished.

Notez que le processus enfant obtient le PID 1 dans son nouveau namespace, et que le petit-fils obtient le PID 2. Le PPID du processus enfant est 0 car il est le processus init de son namespace.

Lorsqu'un processus enfant devient orphelin, il est re-parenté au processus « init » dans l'espace de noms PID de son parent (sauf si l'un des ancêtres plus proches du parent a utilisé la commande prctl(2) PR_SET_CHILD_SUBREAPER pour se marquer comme le récupérateur des processus descendants orphelins). Notez qu'en raison des sémantiques setns(2) et unshare(2) décrites ci-dessus, il peut s'agir du processus « init » dans l'espace de noms PID qui est le *parent* de l'espace de noms PID de l'enfant, plutôt que le processus « init » dans l'espace de noms PID de l'enfant lui-même.

Compatibilité de CLONE_NEWPID avec d'autres flags CLONE_*

Dans les versions actuelles de Linux, CLONE_NEWPID ne peut pas être combiné avec CLONE_THREAD. Les threads doivent être dans le même espace de noms PID afin que les threads d'un processus puissent s'envoyer des signaux. De même, il doit être possible de voir tous les threads d'un processus dans le système de fichiers proc(5). De plus, si deux threads se trouvaient dans des espaces de noms PID différents, l'identifiant du processus qui envoie un signal ne pourrait pas être codé de manière significative lorsqu'un signal est envoyé (voir la description du type siginfo_t dans sigaction(2)). Comme ceci est calculé lorsqu'une file d'attente de signaux est créée, une file d'attente de signaux partagée par des processus dans plusieurs espaces de noms PID irait à l'encontre de cela.

Dans les versions antérieures de Linux, CLONE_NEWPID était également interdit (échouant avec l'erreur EINVAL) en combinaison avec CLONE_SIGHAND (avant Linux 4.3) ainsi qu'avec CLONE_VM (avant Linux 3.12). Les modifications qui ont levé ces restrictions ont également été portées sur les noyaux stables plus anciens.

Systèmes de fichiers /proc et espaces de noms PID

Un système de fichiers /proc affiche (dans les répertoires /proc/pid) uniquement les processus visibles dans l'espace de noms PID du processus qui a effectué le montage, même si le système de fichiers /proc est consulté depuis des processus dans d'autres espaces de noms.

Après avoir créé un nouvel espace de noms PID, il est utile que l'enfant change son répertoire racine et monte une nouvelle instance procfs sur /proc afin que des outils tels que ps(1) fonctionnent correctement. Si un nouvel espace de noms de montage est créé simultanément en incluant CLONE_NEWNS dans l'argument flags de clone(2) ou unshare(2), alors il n'est pas nécessaire de changer le répertoire racine : une nouvelle instance procfs peut être montée directement sur /proc.

Depuis un shell, la commande pour monter /proc est :


$ mount -t proc proc /proc

Appeler readlink(2) sur le chemin /proc/self renvoie l'identifiant du processus de l'appelant dans l'espace de noms PID du montage procfs (c'est-à-dire l'espace de noms PID du processus qui a monté le procfs). Cela peut être utile à des fins d'introspection, lorsqu'un processus souhaite découvrir son PID dans d'autres espaces de noms.

Fichiers /proc

/proc/sys/kernel/ns_last_pid (depuis Linux 3.3)
Ce fichier (qui est virtualisé par espace de noms PID) affiche le dernier PID qui a été alloué dans cet espace de noms PID. Lorsque le prochain PID sera alloué, le noyau recherchera le plus petit PID non alloué qui est supérieur à cette valeur, et lorsque ce fichier sera lu ultérieurement, il affichera ce PID.
Ce fichier est accessible en écriture par un processus qui possède la capacité CAP_SYS_ADMIN ou (depuis Linux 5.9) CAP_CHECKPOINT_RESTORE à l'intérieur de l'espace de noms utilisateur qui possède l'espace de noms PID. Cela permet de déterminer le PID qui est alloué au prochain processus créé à l'intérieur de cet espace de noms PID.

Divers

Lorsqu'un identifiant de processus est passé via un socket de domaine UNIX à un processus dans un espace de noms PID différent (voir la description de SCM_CREDENTIALS dans unix(7)), il est traduit en la valeur PID correspondante dans l'espace de noms PID du processus récepteur.
