PIMSYNC.CONF(5) Manuel des formats de fichier PIMSYNC.CONF(5)

NOM

pimsync.conf — fichier de configuration pour pimsync(1)

DESCRIPTION

pimsync.conf est divisé en trois types principaux de sections :

CONFIGURATION GLOBALE
Paramètres globaux pour pimsync.
SECTIONS DE STOCKAGE
Configuration pour des stockages individuels.
SECTIONS DE PAIRES
Règles pour synchroniser des paires de stockages.

Voir pimsync(1) pour les détails sur le chemin par défaut du fichier de configuration, et comment spécifier un chemin alternatif.

CONFIGURATION GLOBALE

Les paramètres suivants peuvent être définis globalement :

status_path chemin
Chemin vers un répertoire qui contiendra la base de données d'état utilisée en interne par pimsync.

SECTIONS DE STOCKAGE

Un stockage décrit un emplacement où des calendriers ou des contacts sont stockés. Chaque stockage est déclaré dans sa propre section, et chaque section de stockage commence par la déclaration du nom du stockage.

stockage nom {…}
Déclare un stockage avec le nom nom.

Les directives sont déclarées entre les accolades pour chaque section, une par ligne. Les directives suivantes s'appliquent à tous les types de stockage :

type type
Où type peut être l'un des suivants :
vdir/icalendar
Un répertoire où chaque sous-répertoire représente un calendrier. Chacun de ces sous-répertoires contient des fichiers icalendar individuels, chacun représentant un événement (ou une série d'événements récurrents), une tâche ou une entrée de journal.
vdir/vcard
Un répertoire où chaque sous-répertoire représente un carnet d'adresses. Chacun de ces sous-répertoires contient des fichiers vcard individuels, chacun représentant un contact.
caldav
Un serveur CalDAV, contenant des calendriers avec des événements, des tâches et/ou des entrées de journal.
carddav
Un serveur CardDAV contenant des carnets d'adresses avec des contacts.
webcal
Une ressource HTTP ou HTTPS exposant un seul fichier iCalendar qui peut contenir zéro ou plusieurs événements, tâches ou entrées de journal. Ce stockage est en lecture seule.
jmap/icalendar
Un serveur JMAP avec support Calendrier. Ce stockage est expérimental et peut encore contenir de graves bugs !
jmap/vcard
Un serveur JMAP avec support Calendrier. Ce stockage est expérimental et peut encore contenir de graves bugs !
interval secondes
Lorsqu'il n'est pas possible de surveiller un stockage, vérifiez les changements toutes les secondes spécifiées. La valeur par défaut est 300 secondes.
readonly
N'effectue aucune opération d'écriture sur ce stockage. Cette directive ne prend aucun paramètre.

Les stockages de type vdir acceptent les directives suivantes :

path chemin
Chemin vers un répertoire stockant un vdir. Un tilde initial sera développé pour correspondre au répertoire personnel de l'utilisateur courant.

Supporte les PARAMÈTRES DYNAMIQUES (voir ci-dessous).

fileext extension
Optionnel. Extension de fichier pour les éléments sauvegardés dans ce vdir. Si non spécifié, ics est utilisé pour les stockages de calendrier et vcf est utilisé pour les stockages de carnet d'adresses.

Les stockages de type caldav ou carddav acceptent les directives suivantes :

url url
URL du serveur Dav. Si cette URL ne rapporte pas les capacités DAV appropriées, une découverte de service sera effectuée pour cette URL et son domaine afin de trouver l'emplacement exact du serveur et la collection du home set.

Les URLs doivent spécifier le schéma http, https. ou unix. Les URLs commençant par unix:// seront traitées comme un chemin vers une socket de domaine Unix.

Supporte les PARAMÈTRES DYNAMIQUES (voir ci-dessous).

username nom_utilisateur
Optionnel. Nom d'utilisateur à utiliser pour l'authentification HTTP Basic.

Supporte les PARAMÈTRES DYNAMIQUES (voir ci-dessous).

password mot_de_passe
Optionnel. Mot de passe à utiliser pour l'authentification HTTP Basic.

Supporte les PARAMÈTRES DYNAMIQUES (voir ci-dessous).

collection_id_segment last | second-last
Optionnel. Segment du chemin URL à utiliser comme identifiant de collection. Les valeurs valides sont last (par défaut) ou second-last. Voir la documentation d'utilisation avancée pour plus de détails.

Les stockages de type webcal acceptent les directives suivantes :

url url
URL d'un fichier icalendar. Ce fichier peut contenir plusieurs éléments de calendrier. Le schéma doit être http ou https.

Supporte les PARAMÈTRES DYNAMIQUES (voir ci-dessous).

collection_id nom
Nom à utiliser lors du mappage de cette collection à une autre sur le stockage opposé.

Les stockages de type jmap acceptent les directives suivantes :

url url
URL de base du serveur JMAP.

Supporte les PARAMÈTRES DYNAMIQUES (voir ci-dessous).

username nom_utilisateur
Optionnel. Nom d'utilisateur à utiliser pour l'authentification HTTP Basic.

Supporte les PARAMÈTRES DYNAMIQUES (voir ci-dessous).

password mot_de_passe
Optionnel. Mot de passe à utiliser pour l'authentification HTTP Basic.

Supporte les PARAMÈTRES DYNAMIQUES (voir ci-dessous).

Les stockages de type caldav, carddav, webcal et jmap acceptent également les directives suivantes :

PARAMÈTRES GLOBAUX

Les directives suivantes peuvent être utilisées dans la section globale ou dans des sections spécifiques pour les surcharger.

user_agent user_agent
Optionnel. Définir l'en-tête User-Agent à user_agent pour les requêtes HTTP sortantes. Par défaut, utilise “pimsync/” suivi du numéro de version actuel. Par exemple : pimsync/1.0.0.
tls_root path
Optionnel. Utiliser le magasin de certificats racine à path lors de la vérification du certificat TLS du serveur. Désactive la vérification du certificat par rapport aux autorités de certification du système. Voir tls_fingerprint ci-dessous.
tls_fingerprint fingerprint
Optionnel. Accepter le certificat si son empreinte correspond à fingerprint. Si spécifié avec la directive tls_root, le certificat est vérifié avec la racine spécifiée. Si tls_root n'est pas spécifié, le certificat du serveur n'est pas validé par rapport à une racine et seule une vérification d'empreinte est effectuée.
auth_cert certificate key
Optionnel. Utiliser le certificate et la key fournis pour l'authentification client TLS.
auth_cert pem_bundle
Optionnel. Utiliser le certificat et la clé du bundle spécifié pour l'authentification client TLS.

PARAMÈTRES DYNAMIQUES

url, username, password et path peuvent être définis dans le fichier de configuration ou spécifier un bloc avec une commande pour récupérer cette valeur à partir d'un système externe. Lors de la spécification d'une commande externe, au lieu de définir une valeur pour la directive, spécifiez un nouveau bloc avec une seule directive cmd.

Par exemple, pour lire un mot de passe via la commande externe secret-store --get-caldav-password, utilisez la syntaxe suivante :

password {
	cmd secret-store --get-caldav-password
}

Il est également possible de spécifier un script shell, qui est exécuté via ‘sh -c’. Par exemple :

password {
	shell pass show communication/migadu.com | head -1
}

Il est recommandé de stocker les identifiants et autres valeurs sensibles dans un service de stockage sécurisé.

SECTIONS DE PAIRES

Une paire déclare comment deux stockages doivent être synchronisés l'un avec l'autre. Chaque section de paire commence par une déclaration du nom de la paire :

pair name {…}
Déclare une paire nommée name.

Chaque paire est définie par un bloc de directives, une par ligne, entre accolades :

storage_a name
Le nom name du premier stockage à synchroniser avec un autre.
storage_b name
Le nom name du second stockage à synchroniser avec l'autre.
collections all
Synchronise toutes les collections trouvées dans les deux stockages. Les collections seront synchronisées avec d'autres ayant un identifiant correspondant de l'autre côté. C'est la valeur recommandée si vous souhaitez simplement synchroniser toutes les collections des deux stockages.
collections from a
Synchronise toutes les collections trouvées dans storage_a. Chaque collection sera synchronisée avec la collection ayant le même identifiant de collection sur storage_b.
collections from b
Synchronise toutes les collections trouvées dans storage_b. Chaque collection sera synchronisée avec la collection ayant le même identifiant de collection sur storage_a.
collection id
Synchronise la collection avec l'identifiant id. Peut être spécifié plusieurs fois.
collection file ... {…}
Synchronise la collection définie par les règles données. Voir SECTIONS DE COLLECTIONS ci-dessous. Peut être spécifié plusieurs fois.
on_empty skip
Lorsqu'une collection est complètement vidée d'un côté, elle est ignorée. C'est le comportement par défaut.
on_empty sync
Lorsqu'une collection est complètement vidée d'un côté, son homologue est vidé de l'autre côté. Soyez prudent lors de l'utilisation de cette option. Si vous supprimez complètement une collection d'un côté, pimsync.conf ne la restaurera pas. Au lieu de cela, elle supprimera la même collection (et tous ses éléments) de l'autre côté.
on_delete sync
Lorsqu'une collection elle-même est supprimée d'un côté, elle est supprimée de l'autre côté. Ceci ne s'applique que si la collection est déjà vide. C'est le comportement par défaut. Ceci est généralement sûr, surtout lorsqu'il est combiné avec on_empty skip.
on_delete skip
Lorsqu'une collection elle-même est supprimée d'un côté, elle est ignorée.

La directive conflict_resolution spécifie l'action à entreprendre si un élément a été modifié des deux côtés :

conflict_resolution cmd command [args]
Exécute command pour résoudre les conflits entre les deux côtés. args seront passés comme arguments, suivis des chemins vers deux fichiers ; l'un contenant les données sur le stockage a, et l'autre contenant les données sur le stockage b. Le conflit sera considéré comme résolu si et seulement si les deux fichiers sont identiques à la sortie de la commande et que la commande se termine avec le code de sortie zéro.
conflict_resolution keep a
En cas de conflit, conserve la version du stockage a.
conflict_resolution keep b
En cas de conflit, conserve la version du stockage b.

SECTIONS DE COLLECTIONS

Un bloc de collections définit un mappage entre deux collections à synchroniser ; l'une dans storage_a et l'autre dans storage_b.

Ces sections ne sont utilisées que dans les configurations avancées qui nécessitent de mapper des collections existantes entre elles sans modifier leur emplacement de chaque côté.

Chaque bloc doit inclure un alias :

alias name
Un alias pour cette paire de collections qui sera utilisé pour toute sortie.

Une référence à une collection dans storage_a doit être incluse exactement une fois :

id_a id
Utilise la collection avec l'identifiant id.
href_a href
Utilise la collection avec le chemin href.

Une référence à une collection dans storage_b doit être incluse exactement une fois :

id_b id
Utilise la collection avec l'identifiant id.
href_b href
Utilise la collection avec le chemin href.

Par exemple, pour synchroniser une collection avec l'identifiant work avec une autre au chemin /calendars/mine/work/, utilisez :

collection {
	alias work
	id_a work
	href_b /calendars/mine/work/
}
Spécifier un id et un href pour le même stockage n'est pas autorisé.

IDENTIFIANT DE COLLECTION

L'identifiant d'une collection est un concept spécifique à pimsync(1) et vdirsyncer(1).

Pour les stockages vdir, l'identifiant d'une collection est le nom du répertoire qui y correspond.

Pour les stockages caldav ou carddav, l'identifiant d'une collection est le dernier composant de son URL par défaut. Cela peut être changé pour utiliser l'avant-dernier composant via la directive de configuration collection_id_segment.

Pour les stockages webcal, l'identifiant doit être spécifié explicitement via la directive de configuration collection_id.

Sauf configuration contraire, les collections ayant le même identifiant des deux côtés sont synchronisées entre elles.

EXEMPLES

MPLES

Cet exemple synchronise deux stockages avec des annuaires. Le premier est un ensemble local de répertoires contenant des fichiers vCard, le second est un serveur CardDAV distant. Les identifiants sont fournis via l'outil en ligne de commande hiq(1).

status_path "~/.local/share/pimsync/status/"

pair contacts {
	storage_a contacts_local
	storage_b contacts_remote
	collections all
	conflict_resolution cmd nvim -d
}

storage contacts_local {
	type vdir/vcard
	path ~/.local/share/contacts/cards/
	fileext vcf
	interval 30
}

storage contacts_remote {
	type carddav
	url https://carddav.example.com/
	username hugo@example.com
	password {
		cmd hiq -dFpassword proto=carddavs username=hugo@example.com
	}
	interval 30
}

L'exemple suivant synchronise deux stockages avec des données de calendrier. Le premier est un répertoire local avec des fichiers iCalendar, le second est un serveur CalDAV distant.

status_path "~/.local/share/pimsync/status/"

pair calendars {
	storage_a calendars_local
	storage_b calendars_remote
	collections from b
	conflict_resolution cmd nvim -d
}

storage calendars_local {
	type vdir/icalendar
	path ~/.local/share/calendars/
	fileext ics
	interval 30
}

storage calendars_remote {
	type caldav
	url https://caldav.example.com/
	username hugo@example.com
	password {
	 cmd hiq -dFpassword proto=caldavs username=hugo@example.com
	}
	interval 30
}

L'exemple suivant synchronise deux stockages avec des données de calendrier. Le premier est un répertoire local nommé "italki" avec des fichiers de calendrier, le second est un serveur http publiant un fichier iCalendar.

Notez que le premier stockage est identique à celui ci-dessus et ne devrait être spécifié qu'une seule fois si les deux configurations étaient spécifiées dans le même fichier.

L'URL exacte du fichier iCalendar exposé via http est récupérée via l'outil hiq(1), utilisé pour interroger le magasin de secrets himitsu(7).

status_path "~/.local/share/pimsync/status/"

pair study_calendars {
	storage_a calendars_local
	storage_b calendars_italki
	collection italki
}

storage calendars_local {
	type vdir/icalendar
	path ~/.local/share/calendars/
	fileext ics
	interval 30
}

storage calendars_italki {
	type webcal
	collection_id italki
	url {
		cmd hiq -dFurl proto=webcal alias=italki-mine
	}
}

Cet exemple synchronise deux stockages avec des données de calendrier. Le premier est un serveur CardDAV, accessible via un socket de domaine Unix. Le second stockage utilise un système de fichiers local avec des fichiers vCard.

status_path "~/.local/share/pimsync/status/"

pair unixtest {
	storage_a unix_a
	storage_b unix_b
	collections all
}

storage unix_a {
	type carddav
	url unix:///tmp/xandikos.sock
}

storage unix_b {
	type vdir/vcard
	path /tmp/test_storage/
	fileext vcf
}
