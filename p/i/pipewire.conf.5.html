pipewire.conf(5) Manuel des formats de fichiers pipewire.conf(5)

NOM

pipewire.conf - pipewire.conf

DESCRIPTION

Le fichier de configuration du serveur PipeWire

SYNTAXE

$XDG_CONFIG_HOME/pipewire/pipewire.conf

/etc/pipewire/pipewire.conf

/usr/share/pipewire/pipewire.conf

/usr/share/pipewire/pipewire.conf.d/

/etc/pipewire/pipewire.conf.d/

$XDG_CONFIG_HOME/pipewire/pipewire.conf.d/

DESCRIPTION

PipeWire est un service qui facilite le partage de contenu multimédia entre appareils et applications.

Au démarrage, le démon lit un fichier de configuration principal pour se configurer. Il exécute une série de commandes listées dans le fichier de configuration.

Le fichier de configuration est recherché dans l'ordre indiqué dans la SYNTAXE. Les variables d'environnement PIPEWIRE_CONFIG_DIR, PIPEWIRE_CONFIG_PREFIX et PIPEWIRE_CONFIG_NAME peuvent être utilisées pour spécifier respectivement un répertoire de configuration, un sous-répertoire et un fichier alternatifs.

Les autres fichiers de configuration PipeWire suivent généralement la même logique de recherche, en remplaçant pipewire.conf par le nom du fichier de configuration particulier.

FICHIERS DE CONFIGURATION ADDITIONNELS

Tous les fichiers *.conf dans les répertoires pipewire.conf.d/ sont chargés et fusionnés dans la configuration. Les sections de dictionnaire sont fusionnées, en remplaçant les propriétés si elles existaient déjà, et les sections de tableau sont ajoutées. Les fichiers additionnels ont le même format que le fichier de configuration principal, mais ne contiennent que les paramètres à modifier.

Comme le fichier de configuration pipewire.conf contient diverses parties qui doivent être présentes pour un fonctionnement correct, l'utilisation de fichiers additionnels pour la configuration est recommandée.

Exemple

Un fichier de configuration ~/.config/pipewire/pipewire.conf.d/custom.conf pour modifier la valeur du réglage default.clock.min-quantum dans pipewire.conf :

# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.properties = {
    default.clock.min-quantum = 128
}

FORMAT DU FICHIER DE CONFIGURATION

Le fichier de configuration est au format JSON "SPA".

Le fichier de configuration contient des clés de premier niveau, qui sont les sections. La valeur d'une section est soit un dictionnaire, { }, soit un tableau, [ ]. Les déclarations de section et d'élément de dictionnaire ont la forme CLE = VALEUR, et sont séparées par des espaces. Par exemple :

context.properties = {  # section de dictionnaire de premier niveau
    key1 = value  # une valeur simple
    key2 = { key1 = value1 key2 = value2 }  # un dictionnaire avec deux entrées
    key3 = [ value1 value2 ]  # un tableau avec deux entrées
    key4 = [ { k = v1 } { k = v2 } ]  # un tableau de dictionnaires
}
context.modules = [  # section de tableau de premier niveau
    value1
    value2
]

Les fichiers de configuration peuvent également être écrits en syntaxe JSON standard, mais pour une édition manuelle plus facile, la variante détendue "SPA" est autorisée. En JSON "SPA" :

  • : pour délimiter les clés et les valeurs peuvent être substituées par = ou un espace.
  • " autour des clés et des chaînes peuvent être omis tant qu'aucun caractère spécial n'est utilisé dans les chaînes.
  • , pour séparer les objets peut être remplacé par un espace blanc.
  • # peut être utilisé pour commencer un commentaire jusqu'à la fin de la ligne

SECTIONS DU FICHIER DE CONFIGURATION

context.properties

Dictionnaire. Ces propriétés configurent l'instance PipeWire.

context.spa-libs

Dictionnaire. Mappe les fonctionnalités de plugin avec des jokers vers une bibliothèque spa.

context.modules

Tableau de dictionnaires. Chaque entrée du tableau est un dictionnaire contenant le nom du module à charger, incluant des arguments et des indicateurs optionnels. La plupart des modules supportent d'être chargés plusieurs fois.

context.objects

Tableau de dictionnaires. Chaque entrée du tableau est un dictionnaire contenant la factory pour créer un objet à partir de et des arguments supplémentaires optionnels spécifiques à cette factory.

context.exec

Tableau de dictionnaires. Chaque entrée du tableau est un dictionnaire contenant le chemin d'un programme à exécuter au démarrage et des arguments optionnels.

Ce tableau contenait auparavant une entrée pour démarrer le gestionnaire de session, mais ce mode de fonctionnement a depuis été déclassé en aide au développement. Évitez de démarrer un gestionnaire de session de cette manière dans un environnement de production.

node.rules

Tableau de dictionnaires. Règles de correspondance pour modifier les propriétés des nœuds sur le serveur.

device.rules

Tableau de dictionnaires. Règles de correspondance pour modifier les propriétés des périphériques sur le serveur.

PROPRIÉTÉS DU CONTEXTE

Propriétés PipeWire disponibles dans context.properties et valeurs par défaut possibles.

clock.power-of-two-quantum = true

Les demandes de quantum des clients et le quantum final du graphe sont arrondis à la puissance de deux inférieure. Un quantum de puissance de deux peut être plus efficace pour de nombreuses tâches de traitement.

context.data-loop.library.name.system

Le nom de la bibliothèque partagée à utiliser pour les fonctions système du thread de traitement des données. Cela peut généralement être modifié si le thread de données s'exécute sur un noyau temps réel comme EVL.

loop.rt-prio = -1

La priorité des boucles de données. Les boucles de données sont utilisées pour planifier les nœuds dans le graphe. Une valeur de -1 utilise la priorité temps réel par défaut du module-rt. Une valeur de 0 désactive la planification temps réel pour les boucles de données.

loop.class = [ data.rt .. ]

Un tableau de classes des boucles de données. Normalement, les nœuds sont assignés à une boucle par nom ou par classe. Les nœuds sont assignés par défaut à la classe data.rt, il est donc bon d'avoir également une boucle de données de cette classe.

context.num-data-loops = 1

Le nombre de boucles de données à créer. Par défaut, 1 boucle de données est créée et tous les nœuds sont planifiés dans ce thread. Une valeur de 0 désactive les boucles de données temps réel et planifie tous les nœuds dans le thread principal. Une valeur de -1 crée autant de threads de données qu'il y a de cœurs CPU.

context.data-loops = [ ... ]

Ceci contrôle les boucles de données qui seront créées pour le contexte. C'est un tableau de spécifications de boucles de données, une entrée pour chaque boucle de données à démarrer : 
# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.data-loops = [
    {
         #library.name.system = support/libspa-support
         loop.rt-prio = -1
         loop.class = [ data.rt .. ]
         thread.name = data-loop.0
         thread.affinity = [ 0 1 ]
    }
    ...
]


Une priorité spécifique, des classes et un nom peuvent être donnés avec respectivement loop.rt-prio, loop.class et thread.name. Il est également possible de lier la boucle de données à des cœurs CPU spécifiques avec la propriété thread.affinity.

core.daemon = false

Fait du processus PipeWire, démarré avec cette configuration, un processus démon. Cela signifie qu'il gérera et planifiera un graphe pour les clients. Vous voudrez également configurer un core.name pour lui donner un nom bien connu.

core.name = pipewire-0

Le nom du contexte PipeWire. Ce sera également le nom de la socket PipeWire à laquelle les clients pourront se connecter.

cpu.zero.denormals = false

Configure le CPU pour mettre automatiquement les dénormaux à zéro. Ceci sera activé uniquement pour le thread de traitement des données, lorsqu'il est activé.

cpu.vm.name = null

Ceci sera automatiquement défini lors de la création du contexte et contiendra le nom de la VM. Il est généralement utilisé pour écrire des règles de correspondance afin de définir des propriétés supplémentaires.

default.clock.rate = 48000

Le taux d'horloge par défaut détermine la durée en temps réel des quantums min/max/défaut. Vous pourriez vouloir changer les quantums lorsque vous changez le taux d'horloge par défaut pour maintenir la même durée pour les quantums.

default.clock.min-quantum = 32

Quantum minimum par défaut.

default.clock.max-quantum = 8192

Quantum maximum par défaut.

default.clock.quantum = 1024

Quantum par défaut utilisé lorsqu'aucun client n'en spécifie un.

default.clock.quantum-limit = 8192

Limite maximale du quantum pour réserver de l'espace. C'est la taille de tampon maximale utilisée dans le graphique, quel que soit le taux d'échantillonnage.

default.clock.quantum-floor = 4

Quantum minimum pour réserver de l'espace. C'est la taille de tampon minimale utilisée dans le graphique, quel que soit le taux d'échantillonnage.

default.video.width

Largeur vidéo par défaut

default.video.height

Hauteur vidéo par défaut

default.video.rate.num

Numérateur du taux vidéo par défaut

Dénominateur du taux vidéo par défaut

library.name.system = support/libspa-support

Le nom de la bibliothèque partagée à utiliser pour les fonctions système du thread principal.

link.max-buffers = 64

Le nombre maximum de tampons à négocier entre les nœuds. Notez que les clients de version < 3 ne peuvent supporter que 16 tampons. Plus de tampons est presque toujours pire que moins, en termes de latence et de mémoire.

log.level = 2

Le niveau de journalisation par défaut utilisé par le processus.

mem.allow-mlock = true

Essayer de verrouiller la mémoire pour les processus temps réel. La mémoire verrouillée ne sera pas échangée par le noyau et évitera les interruptions dans les threads de traitement.

mem.warn-mlock = false

Avertir en cas d'échec du verrouillage de la mémoire.

mem.mlock-all = false

Essayer de verrouiller toute la mémoire actuelle et future du processus.

settings.check-quantum = false

Vérifier si le quantum dans la mise à jour des métadonnées des paramètres est compatible avec les limites configurées.

settings.check-rate = false

Vérifier si le taux dans la mise à jour des métadonnées des paramètres est compatible avec les limites configurées.

support.dbus = true

Activer le support DBus. Cela activera le support DBus dans les différents modules qui en ont besoin. Désactivez ceci si vous souhaitez désactiver globalement le support DBus dans le processus.

vm.overrides = { default.clock.min-quantum = 1024 }

Toute propriété dans l'objet de propriété vm.overrides remplacera la propriété dans context.properties lorsque PipeWire détecte qu'il fonctionne dans une VM. Ceci est déprécié, utilisez plutôt context.properties.rules.

context.modules.allow-empty = false

Par défaut, un avertissement est enregistré lorsqu'aucun module context.modules n'est chargé car cela indique probablement un problème. Certaines applications peuvent charger elles-mêmes les modules et lorsqu'elles définissent cette propriété sur true, aucun avertissement ne sera enregistré.

Les propriétés de contexte peuvent également contenir des valeurs personnalisées. Par exemple, les sections context.modules et context.objects peuvent déclarer des conditions supplémentaires qui contrôlent si un module ou un objet est chargé en fonction des propriétés présentes.

BIBLIOTHÈQUES SPA

Les plugins SPA sont chargés en fonction de leur nom d'usine. C'est un nom bien connu qui décrit de manière unique les fonctionnalités que le plugin doit avoir. La section context.spa-libs fournit une correspondance entre le nom d'usine et le plugin où l'usine peut être trouvée.

Les noms d'usine peuvent contenir un caractère générique pour regrouper plusieurs usines apparentées dans un seul plugin. Le plugin est chargé à partir du premier nom d'usine correspondant.

Exemple

# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.spa-libs = {
    audio.convert.* = audioconvert/libspa-audioconvert
    avb.*           = avb/libspa-avb
    api.alsa.*      = alsa/libspa-alsa
    api.v4l2.*      = v4l2/libspa-v4l2
    api.libcamera.* = libcamera/libspa-libcamera
    api.bluez5.*    = bluez5/libspa-bluez5
    api.vulkan.*    = vulkan/libspa-vulkan
    api.jack.*      = jack/libspa-jack
    support.*       = support/libspa-support
    video.convert.* = videoconvert/libspa-videoconvert
}

MODULES

Modules PipeWire à charger. Voir libpipewire-modules(7).

# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.modules = [
    #{ name = NOM_MODULE
    #    ( args  = { CLE = VALEUR ... } )
    #    ( flags = [ ( ifexists ) ( nofail ) ] )
    #    ( condition = [ { CLE = VALEUR ... } ... ] )
    #}
    #
]

name

Nom du module à charger

args = { }

Arguments passés au module

flags = [ ]

Indicateurs de chargement. ifexists pour charger le module uniquement s'il existe, et nofail pour ne pas échouer au démarrage de PipeWire si le module ne parvient pas à se charger.

condition = [ ]

Une règle de correspondance correspond à la condition. Le module est chargé uniquement si l'une des expressions du tableau correspond à une propriété de contexte.

OBJETS DE CONTEXTE

La section context.objects vous permet de créer certains objets à partir d'usines (généralement créés en chargeant des modules dans context.modules).

# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.objects = [
    #{ factory = <nom-usine>
    #    ( args  = { <clé> = <valeur> ... } )
    #    ( flags = [ ( nofail ) ] )
    #    ( condition = [ { <clé> = <valeur> ... } ... ] )
    #}
]


Cette section peut être utilisée pour créer des nœuds ou des liens entre des nœuds.

factory

Nom de l'usine pour créer l'objet.

args = { }

Arguments passés à l'usine.

flags = [ ]

Indicateur nofail pour ne pas échouer au démarrage de PipeWire si l'objet ne parvient pas à se charger.

condition = [ ]

Une règle de correspondance correspond à la condition. L'objet est créé uniquement si l'une des expressions du tableau correspond à une propriété de contexte.

Exemple

Ce fragment crée un nouveau nœud de pilote factice, mais uniquement si la propriété core.daemon est vraie :

# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.objects = [
    { factory = spa-node-factory
      args = {
          factory.name    = support.node.driver
          node.name       = Dummy-Driver
          node.group      = pipewire.dummy
          priority.driver = 20000
      },
      condition = [ { core.daemon = true } ]
    }
]

EXÉCUTION DE COMMANDES

La section context.exec peut être utilisée pour démarrer des commandes arbitraires dans le cadre de l'initialisation du programme PipeWire.

# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.exec = [
    #{   path = <nom-programme>
    #    ( args = "<arguments>" | [ <arg1> <arg2> ... ] )
    #    ( condition = [ { <clé> = <valeur> ... } ... ] )
    #}
]

path

Programme à exécuter.

args

Arguments du programme.

condition

Une règle de correspondance correspond à la condition. L'objet est créé uniquement si l'une des expressions du tableau correspond à une propriété de contexte.

Exemple

Le fragment suivant exécute une commande pactl avec les arguments donnés :

# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.exec = [
    { path = "pactl" args = "load-module module-always-sink" }
]

RÈGLES DE CORRESPONDANCE

Certaines sections du fichier de configuration contiennent des règles de correspondance. Cela permet d'effectuer une action lorsqu'un objet (généralement un nœud ou un flux) est créé/mis à jour et correspond à certaines propriétés.

Les règles générales suivent le modèle suivant :

<règles> = [
    {
        matches = [
            # n'importe lequel des ensembles de propriétés suivants est mis en correspondance, si
            # l'un d'eux correspond, les actions sont exécutées
            {
                # <clé> = <valeur>
                # toutes les clés doivent correspondre à la valeur. ! nie. ~ commence une regex.
                #application.process.binary = "teams"
                #application.name = "~speech-dispatcher.*"
                # L'absence de propriété peut être testée en comparant à null
                #pipewire.sec.flatpak = null
            }
            {
                # plus de correspondances ici...
            }
            ...
        ]
        actions = {
            <nom-action> = <valeur-action>
            ...
        }
    }
]


Les règles de correspondance sont un tableau de règles.

Une règle est toujours un objet JSON avec deux clés : matches et actions. La clé matches est utilisée pour définir les conditions qui doivent être remplies pour que la règle soit évaluée comme vraie, et la clé actions définit les actions effectuées lorsque la règle est évaluée comme vraie.

La clé matches est toujours un tableau JSON d'objets, où chaque objet définit une condition qui doit être remplie. Chaque condition est une liste de paires clé-valeur, où la clé est le nom de la propriété qui est mise en correspondance, et la valeur est la valeur que la propriété doit avoir. Au sein d'une condition, toutes les paires clé-valeur sont combinées par un ET logique, et toutes les conditions du tableau matches sont combinées par un OU logique.

La clé actions est toujours un objet JSON, où chaque paire clé-valeur définit une action effectuée lorsque la règle est évaluée comme vraie. Le nom de l'action est spécifique à la règle et est défini par la documentation de la règle, mais vous verrez le plus souvent l'action update-props, qui est utilisée pour mettre à jour les propriétés de l'objet mis en correspondance.

pipewire.conf.5 - Manual Page

NOM

pipewire.conf - configuration de PipeWire

DESCRIPTION

PipeWire est un serveur multimédia qui permet aux applications d'accéder à des flux audio et vidéo. Il est conçu pour être utilisé sur les systèmes Linux modernes.

Ce fichier de configuration définit le comportement du serveur PipeWire.

SYNTAXE

Le fichier de configuration est écrit dans le format JSON.

FICHIERS DE CONFIGURATION

Les fichiers de configuration sont recherchés dans les répertoires suivants, par ordre de priorité :

  • $XDG_CONFIG_HOME/pipewire/pipewire.conf
  • /etc/pipewire/pipewire.conf
  • /usr/share/pipewire/pipewire.conf

Les fichiers de configuration dans pipewire.conf.d/ sont lus par ordre alphabétique.

SECTIONS DE CONFIGURATION

Le fichier de configuration est divisé en plusieurs sections, chacune contrôlant un aspect différent de PipeWire.

context.properties
Configure les propriétés globales du contexte PipeWire.
context.modules
Charge les modules PipeWire.
context.objects
Configure les objets globaux du contexte PipeWire.
context.exec
Exécute des commandes au démarrage de PipeWire.
context.properties.rules
Définit des règles pour mettre à jour dynamiquement les propriétés du contexte.
node.rules
Définit des règles pour mettre à jour dynamiquement les propriétés des nœuds.
device.rules
Définit des règles pour mettre à jour dynamiquement les propriétés des périphériques.

PROPRIÉTÉS DU CONTEXTE

La section context.properties permet de configurer les propriétés globales du serveur PipeWire. Par exemple :

context.properties = {
    log.level = 3
    default.clock.rate = 48000
}

BIBLIOTHÈQUES SPA

La section context.modules permet de charger les modules PipeWire. Chaque module est défini par son nom et ses arguments.

context.modules = [
    {   name = libpipewire-module-foo
        args = {
            # arguments du module
        }
    }
]

Les bibliothèques SPA (Simple Plugin API) sont des modules pluggables utilisés par PipeWire.

MODULES

Les modules fournissent des fonctionnalités supplémentaires à PipeWire. Les modules couramment utilisés incluent :

  • libpipewire-module-protocol-native : module natif de PipeWire.
  • libpipewire-module-protocol-raop : module de diffusion audio sans fil (AirPlay).
  • libpipewire-module-jack : module de compatibilité JACK.
  • libpipewire-module-pulse : module de compatibilité PulseAudio.

OBJETS DU CONTEXTE

La section context.objects permet de définir des objets globaux du contexte PipeWire. Ces objets peuvent être utilisés pour exposer des fonctionnalités spécifiques du serveur aux clients.

EXÉCUTION DE COMMANDES

La section context.exec permet d'exécuter des commandes externes au démarrage de PipeWire. Ceci est utile pour démarrer des démons ou des scripts nécessaires au bon fonctionnement de PipeWire.

context.exec = [
    { path = /usr/bin/my-daemon }
    { path = /usr/bin/my-script, args = [ --foo, --bar ] }
]

RÈGLES DE CORRESPONDANCE

Les règles de correspondance sont utilisées dans plusieurs sections de configuration (par exemple, context.properties.rules, node.rules, device.rules) pour appliquer des actions basées sur les propriétés des objets PipeWire.

Une règle de correspondance est composée d'une liste de conditions (matches) et d'une liste d'actions (actions).

Les conditions vérifient les valeurs des propriétés. Par exemple, pour correspondre à tous les nœuds dont le nom commence par my_, vous pouvez utiliser la condition suivante :

matches = [
  {
    node.name = "~my_.*"
  }
]

Le caractère ~ signifie que la valeur est une expression régulière. La syntaxe exacte des expressions régulières est la syntaxe POSIX étendue, telle que décrite dans la page de manuel regex(7).

En plus des expressions régulières, vous pouvez également utiliser le caractère ! pour nier une condition. Par exemple, pour correspondre à tous les nœuds dont le nom ne commence pas par my_, vous pouvez utiliser la condition suivante :

matches = [
  {
    node.name = "!~my_.*"
  }
]

Le caractère ! peut être utilisé avec ou sans expression régulière. Par exemple, pour correspondre à tous les nœuds dont le nom n'est pas égal à my_node, vous pouvez utiliser la condition suivante :

matches = [
  {
    node.name = "!my_node"
  }
]

La valeur null a une signification spéciale ; elle vérifie si la propriété n'est pas disponible (ou non définie). Pour vérifier si une propriété n'est pas définie :

matches = [
  {
    node.name = null
  }
]

Pour vérifier l'existence d'une propriété, on peut utiliser la condition !null, par exemple :

matches = [
  {
    node.name = "!null"
  }
  {
    node.name = !null            # syntaxe simplifiée
  }
]


Pour gérer la chaîne de caractères « null », il faut échapper la chaîne. Par exemple, pour vérifier si une propriété a la valeur de chaîne « null », utilisez :

matches = [
  {
    node.name = "null"
  }
]


Pour gérer autre chose que la chaîne « null », utilisez :

matches = [
  {
    node.name = "!\"null\""
  }
  {
    node.name = !"null"      # syntaxe simplifiée
  }
]

RÈGLES DES PROPRIÉTÉS DU CONTEXTE

context.properties.rules peut être utilisé pour mettre à jour dynamiquement les propriétés en fonction d'autres propriétés.

Un cas typique est la mise à jour des paramètres personnalisés lors de l'exécution dans une VM. La propriété cpu.vm.name est automatiquement définie lors de l'exécution dans une VM avec le nom de la VM. Une règle de correspondance peut être écrite pour définir des propriétés personnalisées comme suit :

# ~/.config/pipewire/pipewire.conf.d/custom.conf
context.properties.rules = [
    {   matches = [ { cpu.vm.name = !null } ]
        actions = {
            update-props = {
                # Ces remplacements ne sont appliqués que lors de l'exécution dans une VM.
                default.clock.min-quantum = 1024
            }
        }
    }
]

RÈGLES DE NŒUD

Les règles node.rules sont évaluées chaque fois que les propriétés d'un nœud sont définies ou mises à jour. Cela peut être utilisé côté serveur pour remplacer les propriétés définies par le client sur des nœuds arbitraires.

node.rules fournit une action update-props qui prend un objet contenant les propriétés à mettre à jour sur l'objet nœud.

Ajoutez une section node.rules dans le fichier de configuration comme suit :

# ~/.config/pipewire/pipewire.conf.d/custom.conf
node.rules = [
    {
        matches = [
            {
                # toutes les clés doivent correspondre à la valeur. ! nie. ~ démarre une regex.
                client.name = "jack_simple_client"
            }
        ]
        actions = {
            update-props = {
                node.force-quantum = 512
            }
        }
    }
]

Définira la propriété node.force-quantum de jack_simple_client à 512.

RÈGLES DE PÉRIPHÉRIQUE

Les règles device.rules sont évaluées chaque fois que les propriétés d'un périphérique sont définies ou mises à jour. Cela peut être utilisé côté serveur pour remplacer les propriétés définies par le client sur des périphériques arbitraires.

device.rules fournit une action update-props qui prend un objet contenant les propriétés à mettre à jour sur l'objet périphérique.

Ajoutez une section device.rules dans le fichier de configuration comme suit :

# ~/.config/pipewire/pipewire.conf.d/custom.conf
device.rules = [
    {
        matches = [
            {
                # toutes les clés doivent correspondre à la valeur. ! nie. ~ démarre une regex.
                device.name = ""v4l2_device.pci-0000_00_14.0-usb-0_1.2_1.0
            }
        ]
        actions = {
            update-props = {
                device.description = "Ma Webcam"
            }
        }
    }
]

Définira la propriété device.description du périphérique avec le nom de périphérique donné à « Ma Webcam ». »
