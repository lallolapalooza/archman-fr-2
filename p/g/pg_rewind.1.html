PG_REWIND(1) Documentation PostgreSQL 18.1 PG_REWIND(1)

NOM

pg_rewind — synchronise un répertoire de données PostgreSQL avec un autre répertoire de données qui en a été dérivé

SYNTAXE

pg_rewind [option...] {-D | --target-pgdata} répertoire {--source-pgdata=répertoire | --source-server=chaine_connexion}

DESCRIPTION

pg_rewind est un outil pour synchroniser un cluster PostgreSQL avec une autre copie du même cluster, après que les lignes de temps des clusters aient divergé. Un scénario typique est de remettre en ligne un ancien serveur primaire après un basculement, en tant que réplica qui suit le nouveau serveur primaire.

Après une opération de rewind réussie, l'état du répertoire de données cible est analogue à une sauvegarde de base du répertoire de données source. Contrairement à la prise d'une nouvelle sauvegarde de base ou à l'utilisation d'un outil comme rsync, pg_rewind ne nécessite pas de comparer ou de copier des blocs de relation inchangés dans le cluster. Seuls les blocs modifiés des fichiers de relation existants sont copiés ; tous les autres fichiers, y compris les nouveaux fichiers de relation, les fichiers de configuration et les segments WAL, sont copiés intégralement. Ainsi, l'opération de rewind est considérablement plus rapide que d'autres approches lorsque la base de données est volumineuse et qu'une petite fraction seulement des blocs diffère entre les clusters.

pg_rewind examine les historiques des lignes de temps des clusters source et cible pour déterminer le point où ils ont divergé, et s'attend à trouver des WAL dans le répertoire pg_wal du cluster cible remontant jusqu'au point de divergence. Le point de divergence peut être trouvé soit sur la ligne de temps cible, soit sur la ligne de temps source, soit sur leur ancêtre commun. Dans le scénario typique de basculement où le cluster cible a été arrêté peu après la divergence, ce n'est pas un problème, mais si le cluster cible a fonctionné longtemps après la divergence, ses anciens fichiers WAL pourraient ne plus être présents. Dans ce cas, vous pouvez les copier manuellement de l'archive WAL vers le répertoire pg_wal, ou exécuter pg_rewind avec l'option -c pour les récupérer automatiquement de l'archive WAL. L'utilisation de pg_rewind ne se limite pas au basculement, par exemple, un serveur réplica peut être promu, exécuter quelques transactions d'écriture, puis être "rewound" pour redevenir un réplica.

Après avoir exécuté pg_rewind, la relecture des WAL doit être terminée pour que le répertoire de données soit dans un état cohérent. Lorsque le serveur cible redémarre, il entrera en mode de récupération et relira tous les WAL générés sur le serveur source depuis le dernier checkpoint avant le point de divergence. Si certains des WAL n'étaient plus disponibles sur le serveur source lorsque pg_rewind a été exécuté, et n'ont donc pas pu être copiés par la session pg_rewind, ils doivent être rendus disponibles lorsque le serveur cible démarre. Ceci peut être fait en créant un fichier recovery.signal dans le répertoire de données cible et en configurant une commande restore_command appropriée dans postgresql.conf.

pg_rewind exige que le serveur cible ait l'option wal_log_hints activée dans postgresql.conf ou des sommes de contrôle de données activées lors de l'initialisation du cluster avec initdb. Aucune de ces options n'est activée par défaut actuellement. full_page_writes doit également être réglé sur on, mais il est activé par défaut.


Attention : Échecs pendant le Rewind

Si pg_rewind échoue pendant le traitement, le répertoire de données de la cible n'est probablement pas dans un état récupérable. Dans un tel cas, il est recommandé de prendre une nouvelle sauvegarde fraîche.

Comme pg_rewind copie intégralement les fichiers de configuration du serveur source, il peut être nécessaire de corriger la configuration utilisée pour la récupération avant de redémarrer le serveur cible, surtout si la cible est réintroduite en tant que réplica du serveur source. Si vous redémarrez le serveur après la fin de l'opération de rewind mais sans configurer la récupération, la cible pourrait de nouveau diverger du serveur primaire.

pg_rewind échouera immédiatement s'il trouve des fichiers sur lesquels il ne peut pas écrire directement. Cela peut se produire, par exemple, lorsque le serveur source et le serveur cible utilisent la même cartographie de fichiers pour les clés et certificats SSL en lecture seule. Si de tels fichiers sont présents sur le serveur cible, il est recommandé de les supprimer avant d'exécuter pg_rewind. Après avoir effectué le rewind, certains de ces fichiers peuvent avoir été copiés depuis la source, auquel cas il peut être nécessaire de supprimer les données copiées et de restaurer l'ensemble des liens utilisés avant le rewind.

OPTIONS

pg_rewind accepte les arguments de ligne de commande suivants :

-D répertoire
--target-pgdata=répertoire

Cette option spécifie le répertoire de données cible qui est synchronisé avec la source. Le serveur cible doit être arrêté proprement avant d'exécuter pg_rewind.

--source-pgdata=répertoire

Spécifie le chemin d'accès au répertoire de données du serveur source avec lequel synchroniser la cible. Cette option nécessite que le serveur source soit arrêté proprement.

--source-server=chaine_connexion

Spécifie une chaîne de connexion libpq pour se connecter au serveur PostgreSQL source afin de synchroniser la cible. La connexion doit être une connexion normale (non de réplication) avec un rôle disposant des permissions suffisantes pour exécuter les fonctions utilisées par pg_rewind sur le serveur source (voir la section Notes pour plus de détails) ou un rôle superutilisateur. Cette option nécessite que le serveur source soit en cours d'exécution et accepte les connexions.

-R
--write-recovery-conf

Crée standby.signal et ajoute les paramètres de connexion à postgresql.auto.conf dans le répertoire de sortie. Le nom de la base de données (dbname) ne sera enregistré que si dbname a été spécifié explicitement dans la chaîne de connexion ou la variable d'environnement. --source-server est obligatoire avec cette option.

-n
--dry-run

Fait tout sauf modifier réellement le répertoire cible.

-N
--no-sync

Par défaut, pg_rewind attendra que tous les fichiers soient écrits en toute sécurité sur le disque. Cette option fait que pg_rewind retourne sans attendre, ce qui est plus rapide, mais signifie qu'un plantage ultérieur du système d'exploitation peut laisser le répertoire de données corrompu. Généralement, cette option est utile pour les tests mais ne doit pas être utilisée sur une installation de production.

-P
--progress

Active le rapport de progression. L'activation de cette option fournira un rapport de progression approximatif lors de la copie des données depuis le cluster source.

-c
--restore-target-wal

Utilise la restore_command définie dans la configuration du cluster cible pour récupérer les fichiers WAL de l'archive WAL si ces fichiers ne sont plus disponibles dans le répertoire pg_wal.

--config-file=nom_fichier

Utilise le fichier de configuration principal du serveur spécifié pour le cluster cible. Ceci affecte pg_rewind lorsqu'il utilise en interne la commande postgres pour l'opération de rewind sur ce cluster (lors de la récupération de restore_command avec l'option -c/--restore-target-wal et lors de la finalisation forcée d'une récupération après arrêt brutal).

--debug

Affiche une sortie de débogage détaillée, principalement utile pour les développeurs qui déboguent pg_rewind.

--no-ensure-shutdown

pg_rewind exige que le serveur cible soit arrêté proprement avant le rewind. Par défaut, si le serveur cible n'est pas arrêté proprement, pg_rewind démarre le serveur cible en mode mono-utilisateur pour terminer d'abord la récupération après arrêt brutal, puis l'arrête. En passant cette option, pg_rewind saute cette étape et génère une erreur immédiatement si le serveur n'est pas arrêté proprement. Les utilisateurs sont alors censés gérer la situation eux-mêmes.

--sync-method=méthode

Lorsqu'elle est réglée sur fsync, ce qui est la valeur par défaut, pg_rewind ouvrira et synchronisera récursivement tous les fichiers du répertoire de données. La recherche de fichiers suivra les liens symboliques pour le répertoire WAL et chaque tablespace configuré.

Sous Linux, syncfs peut être utilisé à la place pour demander au système d'exploitation de synchroniser l'ensemble des systèmes de fichiers contenant le répertoire de données, les fichiers WAL, et chaque tablespace. Voir recovery_init_sync_method pour des informations sur les mises en garde à prendre en compte lors de l'utilisation de syncfs.

Cette option n'a aucun effet lorsque --no-sync est utilisé.

-V
--version

Affiche les informations de version, puis quitte.

-?
--help

Affiche l'aide, puis quitte.

NOTES

Lors de l'exécution de pg_rewind en utilisant un cluster en ligne comme source, un rôle ayant des autorisations suffisantes pour exécuter les fonctions utilisées par pg_rewind sur le cluster source peut être utilisé à la place d'un superutilisateur. Voici comment créer un tel rôle, nommé rewind_user ici :

CREATE USER rewind_user LOGIN;
GRANT EXECUTE ON function pg_catalog.pg_ls_dir(text, boolean, boolean) TO rewind_user;
GRANT EXECUTE ON function pg_catalog.pg_stat_file(text, boolean) TO rewind_user;
GRANT EXECUTE ON function pg_catalog.pg_read_binary_file(text) TO rewind_user;
GRANT EXECUTE ON function pg_catalog.pg_read_binary_file(text, bigint, bigint, boolean) TO rewind_user;

Comment ça marche

L'idée de base est de copier toutes les modifications au niveau du système de fichiers du cluster source vers le cluster cible :

1. Scanner le journal WAL du cluster cible, en commençant par le dernier point de contrôle avant le moment où l'historique de la chronologie du cluster source s'est séparé de celui du cluster cible. Pour chaque enregistrement WAL, enregistrer tous les blocs de données qui ont été touchés. Cela produit une liste de tous les blocs de données qui ont été modifiés dans le cluster cible après la séparation du cluster source. Si certains fichiers WAL ne sont plus disponibles, essayez de relancer pg_rewind avec l'option -c pour rechercher les fichiers manquants dans l'archive WAL.
2. Copier tous ces blocs modifiés du cluster source vers le cluster cible, soit en utilisant l'accès direct au système de fichiers (--source-pgdata), soit via SQL (--source-server). Les fichiers de relations sont maintenant dans un état équivalent au moment du dernier point de contrôle complété avant le moment où les chronologies WAL de la source et de la cible ont divergé, plus l'état actuel sur la source de tout bloc modifié sur la cible après cette divergence.
3. Copier tous les autres fichiers, y compris les nouveaux fichiers de relations, les segments WAL, pg_xact et les fichiers de configuration du cluster source vers le cluster cible. Similairement aux sauvegardes de base, le contenu des répertoires pg_dynshmem/, pg_notify/, pg_replslot/, pg_serial/, pg_snapshots/, pg_stat_tmp/ et pg_subtrans/ est omis des données copiées depuis le cluster source. Les fichiers backup_label, tablespace_map, pg_internal.init, postmaster.opts, postmaster.pid et .DS_Store, ainsi que tout fichier ou répertoire commençant par pgsql_tmp, sont omis.
4. Créer un fichier backup_label pour commencer la relecture WAL au point de contrôle créé lors du basculement et configurer le fichier pg_control avec un LSN de cohérence minimum défini comme le résultat de pg_current_wal_insert_lsn() lors du rewind à partir d'une source vivante ou du dernier LSN de point de contrôle lors du rewind à partir d'une source arrêtée.
5. Lors du démarrage de la cible, PostgreSQL relit tous les WAL nécessaires, ce qui donne un répertoire de données dans un état cohérent.
