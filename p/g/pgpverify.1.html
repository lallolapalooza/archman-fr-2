NOM

pgpverify - Vérifie cryptographiquement les messages de contrôle Usenet

SYNTAXE

pgpverify [--findid=chaine] [--test] < message

DESCRIPTION

Le programme pgpverify lit (sur l'entrée standard) un message de contrôle Usenet qui a été signé cryptographiquement à l'aide du programme signcontrol (ou d'un autre programme produisant un format compatible). pgpverify utilise ensuite une implémentation PGP pour déterminer qui a signé le message de contrôle. Si le message de contrôle a une signature valide, pgpverify affiche (sur la sortie standard) l'identifiant utilisateur de la clé qui a signé le message. Sinon, il se termine avec un code de sortie non nul.

Si pgpverify est installé dans le cadre d'INN, il utilise la configuration d'INN pour déterminer quel programme de vérification de signature utiliser, comment enregistrer les erreurs, quel répertoire temporaire utiliser et quelle keyring utiliser. Sinon, tous ces paramètres peuvent être définis en modifiant le début de ce script.

Par défaut, lors de l'exécution dans le cadre d'INN, pgpverify s'attend à ce que la keyring PGP se trouve dans pathetc/pgp (soit sous le nom pubring.pgp, soit pubring.gpg, selon que PGP ou GnuPG est utilisé pour vérifier les signatures). Si ce répertoire n'existe pas, il utilisera la keyring par défaut, qui se trouve dans un sous-répertoire .pgp ou .gnupg du répertoire personnel de l'utilisateur exécutant le programme.

INN, lors de l'utilisation de GnuPG, configure pgpverify pour utiliser gpg ou gpgv, qui par défaut s'attend à ce que les clés se trouvent dans une keyring nommée trustedkeys.gpg, car il n'implémente pas directement la vérification de confiance. pgpverify utilise ce fichier s'il est présent mais se rabat sur pubring.gpg s'il n'est pas trouvé. Cela contourne le modèle de confiance pour la vérification des clés, mais est compatible avec la manière dont pgpverify se comportait auparavant. Bien sûr, si une keyring est trouvée dans pathetc/pgp ou configurée en haut du script, cela remplace tout ce comportement.

Notez que quelques hiérarchies Usenet envoient encore des articles de contrôle signés avec d'anciennes clés PGP utilisant un algorithme de hachage faible (MD5). Les versions modernes de GnuPG (2.1.0+) ne valident plus ces signatures, vous devriez donc utiliser GnuPG 1.x ou 2.0.x si vous avez besoin de vérifier ces articles de contrôle.

OPTIONS

--findid=chaine
L'option --findid fait que pgpverify recherche explicitement chaine dans la sortie de l'analyse du message par PGP. Cette option est utile lorsque plusieurs UIDs sont définis sur une seule clé PGP, et que l'appelant de pgpverify a besoin de vérifier si une uid donnée est définie sur cette clé. Si la signature est valide mais ne contient pas chaine, pgpverify se termine avec le code de sortie 4.
--test
L'option --test fait que pgpverify affiche l'entrée qu'il passe à PGP (qui est une version reconstruite de l'entrée qui est censée avoir créé le message de contrôle) ainsi que la sortie de l'analyse du message par PGP.

CODE DE SORTIE

pgpverify peut se terminer avec les codes de sortie suivants :

0
Le message de contrôle avait une bonne signature PGP.
1
Le message de contrôle n'avait pas de signature PGP.
2
Le message de contrôle avait une signature PGP inconnue.
3
Le message de contrôle avait une mauvaise signature PGP.
4
Le message de contrôle avait une bonne signature PGP mais l'argument donné à l'option --findid n'a pas été trouvé dans la sortie de l'analyse du message par PGP.
255
Un problème est survenu, non directement lié à l'analyse PGP de la signature.

ENVIRONNEMENT

pgpverify ne modifie pas ou n'altère pas l'environnement avant d'invoquer le programme pgp, gpgv ou gpg. Il incombe à la personne qui installe pgpverify de s'assurer que lorsque pgp, gpgv ou gpg s'exécute, il a la capacité de localiser et de lire un fichier de clés PGP contenant les clés publiques PGP pour les administrateurs de la hiérarchie Usenet appropriée. pgpverify peut être pointé vers une keyring appropriée en modifiant les variables au début de ce script.

NOTES

Historiquement, les administrateurs de serveurs de news Usenet ont configuré leurs serveurs de news pour honorer automatiquement les messages de contrôle Usenet en fonction de l'origine des messages de contrôle et des hiérarchies auxquelles les messages de contrôle s'appliquaient. Par exemple, dans le passé, David Lawrence publiait toujours des messages de contrôle pour les hiérarchies "Big 8" (comp, humanities, misc, news, rec, sci, soc, talk). Les administrateurs de news Usenet configuraient leur logiciel serveur de news pour honorer automatiquement les messages de contrôle newgroup et rmgroup provenant de David Lawrence et s'appliquant à n'importe laquelle des hiérarchies Big 8.

Malheureusement, les articles de news Usenet (y compris les messages de contrôle) sont notoirement faciles à falsifier. Bientôt, les utilisateurs malveillants ont réalisé qu'ils pouvaient créer ou supprimer (du moins temporairement) n'importe quel groupe de news Big 8 en falsifiant simplement un message de contrôle approprié au nom de David Lawrence. Alors que Usenet devenait plus largement utilisé, les falsifications devenaient plus courantes.

Le programme pgpverify a été conçu pour permettre aux administrateurs de news Usenet de configurer leurs serveurs pour vérifier cryptographiquement les messages de contrôle avant d'agir automatiquement sur eux. Dans le système pgpverify, un responsable de hiérarchie Usenet crée une paire de clés publique/privée PGP et diffuse la clé publique. Chaque fois que le responsable de la hiérarchie publie un message de contrôle, il utilise le programme signcontrol pour signer le message de contrôle avec la clé privée PGP. Les administrateurs de news Usenet configurent leurs serveurs de news pour exécuter le programme pgpverify sur les messages de contrôle appropriés, et agissent en fonction de l'identifiant utilisateur de la clé PGP qui a signé le message de contrôle, et non du nom et de l'adresse qui apparaissent dans les en-têtes From: ou Sender: du message de contrôle.

Ainsi, l'utilisation appropriée des programmes signcontrol et pgpverify élimine essentiellement la possibilité pour les utilisateurs malveillants de falsifier des messages de contrôle Usenet sur lesquels les sites agiront, car ces utilisateurs devraient obtenir la clé privée PGP afin de falsifier un message de contrôle qui passerait la vérification cryptographique. Si les responsables de hiérarchie protègent adéquatement leurs clés privées PGP, la seule façon pour un utilisateur malveillant de falsifier un message de contrôle valablement signé serait de briser l'algorithme de chiffrement à clé publique, ce qui (du moins à l'heure actuelle) est considéré comme prohibitif pour les clés PGP d'une longueur de bits suffisante.
