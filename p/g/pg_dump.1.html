NOM

pg_dump - exporter une base de données PostgreSQL sous forme de script SQL ou vers d'autres formats

SYNTAXE

pg_dump [option-connexion...] [option...] [nom_bdd]

DESCRIPTION

pg_dump est un utilitaire d'exportation d'une base de données PostgreSQL. Il effectue des exportations cohérentes même si la base de données est utilisée simultanément. pg_dump ne bloque pas les autres utilisateurs accédant à la base de données (lecteurs ou écrivains). Notez cependant que, sauf dans des cas simples, pg_dump n'est généralement pas le bon choix pour effectuer des sauvegardes régulières de bases de données de production. Voir le chapitre 25 pour plus de discussions.

pg_dump n'exporte qu'une seule base de données. Pour exporter un cluster entier, ou pour exporter des objets globaux communs à toutes les bases de données d'un cluster (tels que les rôles et les tablespaces), utilisez pg_dumpall(1).

Les exportations peuvent être produites au format script ou au format fichier archive. Les exportations script sont des fichiers texte brut contenant les commandes SQL nécessaires pour reconstruire la base de données à l'état où elle se trouvait au moment de son enregistrement. Pour restaurer à partir d'un tel script, alimentez-le à psql(1). Les fichiers script peuvent être utilisés pour reconstruire la base de données même sur d'autres machines et d'autres architectures ; avec quelques modifications, même sur d'autres produits de base de données SQL.

Les formats de fichiers archive alternatifs doivent être utilisés avec pg_restore(1) pour reconstruire la base de données. Ils permettent à pg_restore d'être sélectif quant à ce qui est restauré, ou même de réorganiser les éléments avant d'être restaurés. Les formats de fichiers archive sont conçus pour être portables entre architectures.

Lorsqu'il est utilisé avec l'un des formats de fichiers archive et combiné avec pg_restore, pg_dump fournit un mécanisme d'archivage et de transfert flexible. pg_dump peut être utilisé pour exporter une base de données entière, puis pg_restore peut être utilisé pour examiner l'archive et/ou sélectionner les parties de la base de données à restaurer. Les formats de fichiers de sortie les plus flexibles sont les formats « personnalisé » (-Fc) et « répertoire » (-Fd). Ils permettent la sélection et la réorganisation de tous les éléments archivés, prennent en charge la restauration parallèle et sont compressés par défaut. Le format « répertoire » est le seul format qui prend en charge les exportations parallèles.

Pendant l'exécution de pg_dump, il convient d'examiner la sortie pour tout avertissement (imprimé sur l'erreur standard), en particulier compte tenu des limitations énumérées ci-dessous.


Avertissement

La restauration d'une sauvegarde entraîne l'exécution de code arbitraire choisi par les superutilisateurs sources sur la destination. Les sauvegardes partielles et les restaurations partielles ne limitent pas cela. Si les superutilisateurs sources ne sont pas fiables, les instructions SQL sauvegardées doivent être inspectées avant la restauration. Les sauvegardes non texte brut peuvent être inspectées en utilisant l'option --file de pg_restore. Notez que le client exécutant la sauvegarde et la restauration n'a pas besoin de faire confiance aux superutilisateurs sources ou de destination.

OPTIONS

Les options de ligne de commande suivantes contrôlent le contenu et le format de la sortie.

nom_bdd

Spécifie le nom de la base de données à exporter. Si cela n'est pas spécifié, la variable d'environnement PGDATABASE est utilisée. Si celle-ci n'est pas définie, le nom d'utilisateur spécifié pour la connexion est utilisé.

-a
--data-only

Exporter uniquement les données, pas le schéma (définitions de données) ni les statistiques. Les données de table, les objets volumineux et les valeurs de séquence sont exportés.

Cette option est similaire à, mais pour des raisons historiques non identique à, la spécification de --section=data.

-b
--large-objects
--blobs (obsolète)

Inclure les objets volumineux dans l'exportation. C'est le comportement par défaut, sauf lorsque --schema, --table, --schema-only, --statistics-only ou --no-data est spécifié. Le commutateur -b est donc utile uniquement pour ajouter des objets volumineux aux exportations où un schéma ou une table spécifique a été demandé. Notez que les objets volumineux sont considérés comme des données et seront donc inclus lorsque --data-only est utilisé, mais pas lorsque --schema-only ou --statistics-only est utilisé.

-B
--no-large-objects
--no-blobs (obsolète)

Exclure les objets volumineux de l'exportation.

Lorsque -b et -B sont donnés, le comportement est d'exporter les objets volumineux, lorsque les données sont exportées, voir la documentation de -b.

-c
--clean

Produire des commandes pour DROP tous les objets de la base de données exportés avant de produire les commandes pour les créer. Cette option est utile lorsque la restauration doit écraser une base de données existante. Si l'un des objets n'existe pas dans la base de données de destination, des messages d'erreur ignorables seront rapportés lors de la restauration, sauf si --if-exists est également spécifié.

Cette option est ignorée lors de la génération d'un fichier de sortie d'archive (non texte). Pour les formats d'archive, vous pouvez spécifier l'option lors de l'appel de pg_restore.

-C
--create

Commencer la sortie avec une commande pour créer la base de données elle-même et se reconnecter à la base de données créée. (Avec un script de cette forme, peu importe à quelle base de données de l'installation de destination vous vous connectez avant d'exécuter le script.) Si --clean est également spécifié, le script supprime et recrée la base de données cible avant de s'y reconnecter.

Avec --create, la sortie inclut également le commentaire de la base de données, le cas échéant, et les paramètres de configuration spécifiques à cette base de données, c'est-à-dire les commandes ALTER DATABASE ... SET ... et ALTER ROLE ... IN DATABASE ... SET ... qui mentionnent cette base de données. Les privilèges d'accès à la base de données elle-même sont également exportés, sauf si --no-acl est spécifié.

Cette option est ignorée lors de la génération d'un fichier de sortie d'archive (non texte). Pour les formats d'archive, vous pouvez spécifier l'option lors de l'appel de pg_restore.

-e modèle
--extension=modèle

Exporter uniquement les extensions correspondant au modèle. Lorsque cette option n'est pas spécifiée, toutes les extensions non système de la base de données cible seront exportées. Plusieurs extensions peuvent être sélectionnées en écrivant plusieurs commutateurs -e. Le paramètre modèle est interprété comme un modèle selon les mêmes règles utilisées par les commandes \d de psql (voir Modèles), de sorte que plusieurs extensions peuvent également être sélectionnées en écrivant des caractères génériques dans le modèle. Lors de l'utilisation de caractères génériques, veillez à citer le modèle si nécessaire pour éviter que le shell n'interprète les caractères génériques.

Toute relation de configuration enregistrée par pg_extension_config_dump est incluse dans l'exportation si son extension est spécifiée par --extension.


Note
Lorsque -e est spécifié, pg_dump ne tente pas d'exporter les autres objets de base de données dont les extensions sélectionnées pourraient dépendre. Par conséquent, il n'y a aucune garantie que les résultats d'une exportation d'extension spécifique puissent être restaurés seuls dans une base de données propre.

-E encodage
--encoding=encodage

Créer l'exportation dans le jeu de caractères d'encodage spécifié. Par défaut, l'exportation est créée dans l'encodage de la base de données. (Une autre façon d'obtenir le même résultat est de définir la variable d'environnement PGCLIENTENCODING sur l'encodage d'exportation souhaité.) Les encodages pris en charge sont décrits dans la section 23.3.1.

-f fichier
--file=fichier

Envoyer la sortie vers le fichier spécifié. Ce paramètre peut être omis pour les formats de sortie basés sur des fichiers, auquel cas la sortie standard est utilisée. Il doit cependant être donné pour le format de sortie répertoire, où il spécifie le répertoire cible au lieu d'un fichier. Dans ce cas, le répertoire est créé par pg_dump et ne doit pas exister au préalable.

-F format
--format=format

Sélectionne le format de la sortie. format peut être l'un des suivants :

p
plain

Produire un fichier script SQL en texte brut (par défaut).

c
custom

Produire une archive au format personnalisé adaptée pour l'entrée dans pg_restore. Avec le format de sortie répertoire, c'est le format de sortie le plus flexible en ce sens qu'il permet la sélection manuelle et la réorganisation des éléments archivés

lors de la restauration. Ce format est également compressé par défaut.

d
directory

Produit une archive au format répertoire adaptée à l'entrée pour pg_restore. Ceci créera un répertoire avec un fichier pour chaque table et grand objet vidé, plus un fichier dit de table des matières décrivant les objets vidés dans un format lisible par machine que pg_restore peut lire. Une archive au format répertoire peut être manipulée avec les outils Unix standards ; par exemple, les fichiers d'une archive non compressée peuvent être compressés avec les outils gzip, lz4, ou zstd. Ce format est compressé par défaut en utilisant gzip et prend également en charge les vidages parallèles.

t
tar

Produit une archive au format tar adaptée à l'entrée pour pg_restore. Le format tar est compatible avec le format répertoire : l'extraction d'une archive au format tar produit une archive valide au format répertoire. Cependant, le format tar ne prend pas en charge la compression. De plus, lors de l'utilisation du format tar, l'ordre relatif des éléments de données des tables ne peut pas être modifié lors de la restauration.

-j njobs
--jobs=njobs

Exécute le vidage en parallèle en vidant njobs tables simultanément. Cette option peut réduire le temps nécessaire pour effectuer le vidage, mais elle augmente également la charge sur le serveur de base de données. Vous ne pouvez utiliser cette option qu'avec le format de sortie répertoire car c'est le seul format de sortie où plusieurs processus peuvent écrire leurs données en même temps.

pg_dump ouvrira njobs + 1 connexions à la base de données, alors assurez-vous que votre paramètre max_connections est suffisamment élevé pour accueillir toutes les connexions.

Demander des verrous exclusifs sur les objets de base de données lors de l'exécution d'un vidage parallèle pourrait faire échouer le vidage. La raison est que le processus leader de pg_dump demande des verrous partagés (ACCESS SHARE) sur les objets que les processus workers vont vider plus tard afin de s'assurer que personne ne les supprime et ne les fasse disparaître pendant que le vidage est en cours. Si un autre client demande alors un verrou exclusif sur une table, ce verrou ne sera pas accordé mais sera mis en file d'attente en attendant la libération du verrou partagé du processus leader. Par conséquent, tout autre accès à la table ne sera pas non plus accordé et sera mis en file d'attente après la demande de verrou exclusif. Ceci inclut le processus worker essayant de vider la table. Sans précautions, ce serait une situation de blocage classique. Pour détecter ce conflit, le processus worker de pg_dump demande un autre verrou partagé en utilisant l'option NOWAIT. Si le processus worker ne obtient pas ce verrou partagé, quelqu'un d'autre a dû demander un verrou exclusif entre-temps et il n'y a aucun moyen de continuer le vidage, donc pg_dump n'a d'autre choix que d'avorter le vidage.

Pour effectuer un vidage parallèle, le serveur de base de données doit prendre en charge les instantanés synchronisés, une fonctionnalité qui a été introduite dans PostgreSQL 9.2 pour les serveurs primaires et 10 pour les répliques. Avec cette fonctionnalité, les clients de base de données peuvent s'assurer qu'ils voient le même ensemble de données même s'ils utilisent des connexions différentes. pg_dump -j utilise plusieurs connexions de base de données ; il se connecte à la base de données une fois avec le processus leader et une fois de plus pour chaque tâche worker. Sans la fonctionnalité d'instantané synchronisé, les différents processus workers ne seraient pas garantis de voir les mêmes données dans chaque connexion, ce qui pourrait entraîner une sauvegarde incohérente.

-n pattern
--schema=pattern

Ne vider que les schémas correspondant à pattern ; cela sélectionne à la fois le schéma lui-même et tous ses objets contenus. Lorsque cette option n'est pas spécifiée, tous les schémas non système dans la base de données cible seront vidés. Plusieurs schémas peuvent être sélectionnés en écrivant plusieurs commutateurs -n. Le paramètre pattern est interprété comme un motif selon les mêmes règles que celles utilisées par les commandes \d de psql (voir Motifs), de sorte que plusieurs schémas peuvent également être sélectionnés en écrivant des caractères génériques dans le motif. Lors de l'utilisation de caractères génériques, faites attention à citer le motif si nécessaire pour empêcher le shell d'étendre les caractères génériques ; voir Exemples ci-dessous.

Note
Lorsque -n est spécifié, pg_dump ne fait aucune tentative pour vider d'autres objets de base de données dont le(s) schéma(s) sélectionné(s) pourraient dépendre. Par conséquent, il n'y a aucune garantie que les résultats d'un vidage de schéma spécifique puissent être restaurés avec succès par eux-mêmes dans une base de données propre.

Note
Les objets non-schéma tels que les grands objets ne sont pas vidés lorsque -n est spécifié. Vous pouvez rajouter les grands objets au vidage avec le commutateur --large-objects.

-N pattern
--exclude-schema=pattern

Ne pas vider les schémas correspondant à pattern. Le motif est interprété selon les mêmes règles que pour -n. -N peut être donné plus d'une fois pour exclure les schémas correspondant à plusieurs motifs.

Lorsque -n et -N sont donnés, le comportement est de vider seulement les schémas qui correspondent à au moins un commutateur -n mais à aucun commutateur -N. Si -N apparaît sans -n, alors les schémas correspondant à -N sont exclus de ce qui est autrement un vidage normal.

-O
--no-owner

Ne pas produire de commandes pour définir la propriété des objets afin de correspondre à la base de données d'origine. Par défaut, pg_dump émet des instructions ALTER OWNER ou SET SESSION AUTHORIZATION pour définir la propriété des objets de base de données créés. Ces instructions échoueront lorsque le script sera exécuté à moins qu'il ne soit démarré par un superutilisateur (ou le même utilisateur qui possède tous les objets dans le script). Pour créer un script qui peut être restauré par n'importe quel utilisateur, mais qui donnera à cet utilisateur la propriété de tous les objets, spécifiez -O.

Cette option est ignorée lors de la production d'une archive (format non texte). Pour les formats d'archive, vous pouvez spécifier l'option lorsque vous appelez pg_restore.

-R
--no-reconnect

Cette option est obsolète mais toujours acceptée pour la compatibilité ascendante.

-s
--schema-only

Ne vider que les définitions d'objets (schéma), pas les données ou les statistiques.

Cette option ne peut pas être utilisée avec --data-only ou --statistics-only. Elle est similaire à, mais pour des raisons historiques non identique à, spécifier --section=pre-data --section=post-data.

(Ne pas confondre avec l'option --schema, qui utilise le mot « schéma » dans un sens différent.)

Pour exclure les données de tables pour seulement un sous-ensemble de tables dans la base de données, voir --exclude-table-data.

-S username
--superuser=username

Spécifiez le nom d'utilisateur superutilisateur à utiliser lors de la désactivation des déclencheurs. Ceci n'est pertinent que si --disable-triggers est utilisé. (Généralement, il est préférable de laisser cela de côté, et plutôt de démarrer le script résultant en tant que superutilisateur.)

-t pattern
--table=pattern

Ne vider que les tables dont les noms correspondent à pattern. Plusieurs tables peuvent être sélectionnées en écrivant plusieurs commutateurs -t. Le paramètre pattern est interprété comme un motif selon les mêmes règles que celles utilisées par les commandes \d de psql (voir Motifs), de sorte que plusieurs tables peuvent également être sélectionnées en écrivant des caractères génériques dans le motif. Lors de l'utilisation de caractères génériques, faites attention à citer le motif si nécessaire pour empêcher le shell d'étendre les caractères génériques ; voir Exemples ci-dessous.

En plus des tables, cette option peut être utilisée pour vider la définition des vues, vues matérialisées, tables étrangères et séquences correspondantes. Elle ne videra pas le contenu des vues ou des vues matérialisées, et le contenu des tables étrangères ne sera vidé que si le serveur étranger correspondant est spécifié avec --include-foreign-data.

Les commutateurs -n et -N n'ont aucun effet lorsque -t est utilisé, car les tables sélectionnées par -t seront vidées indépendamment de ces commutateurs, et les objets non-tables ne seront pas vidés.


Note
Lorsque -t est spécifié, pg_dump ne fait aucune tentative pour vider d'autres objets de base de données dont la ou les tables sélectionnée(s) pourraient dépendre. Par conséquent, il n'y a aucune garantie que les résultats d'un vidage de table spécifique puissent être restaurés avec succès par eux-mêmes dans une base de données propre.

-T pattern
--exclude-table=pattern

Ne pas vider les tables correspondant à pattern. Le motif est interprété selon les mêmes règles que pour -t. -T peut être donné plus d'une fois pour exclure les tables correspondant à plusieurs motifs.

Lorsque -t et -T sont donnés, le comportement est de vider seulement les tables qui correspondent à au moins un commutateur -t mais à aucun commutateur -T. Si -T apparaît sans -t, alors les tables correspondant à -T sont exclues de ce qui est autrement un vidage normal.

-v
--verbose

Spécifie le mode verbeux. Ceci fera en sorte que pg_dump produise des commentaires d'objets détaillés et des heures de début/arrêt dans le fichier de vidage, ainsi que des messages de progression sur la sortie d'erreur standard. Répéter l'option fait apparaître des messages supplémentaires de niveau débogage sur la sortie d'erreur standard.

-V
--version

Affiche la version de pg_dump et quitte.

-x
--no-privileges
--no-acl

Empêche le vidage des privilèges d'accès (commandes grant/revoke).

-Z level
-Z method[:detail]
--compress=level
--compress=method[:detail]

Spécifie la méthode de compression et/ou le niveau de compression à utiliser. La méthode de compression peut être définie sur gzip, lz4, zstd, ou none pour aucune compression. Une chaîne de détail de compression peut être spécifiée optionnellement. Si la chaîne de détail est un entier, elle spécifie le niveau de compression. Sinon, elle doit être une liste d'éléments séparés par des virgules, chacun de la forme keyword ou keyword=value. Actuellement, les mots-clés pris en charge sont level et long.

Si aucun niveau de compression n'est spécifié, le niveau de compression par défaut sera utilisé. Si seul un niveau est spécifié sans mentionner d'algorithme, la compression gzip sera utilisée si le niveau est supérieur à 0, et aucune compression ne sera utilisée si le niveau est 0.

Pour les formats d'archive personnalisés et répertoire, ceci spécifie la compression des segments individuels de données de table, et par défaut, la compression utilise gzip à un niveau modéré. Pour la sortie en texte brut, la définition d'un niveau de compression non nul provoque la compression de l'ensemble du fichier de sortie, comme s'il avait été passé à travers gzip, lz4, ou zstd ; mais par défaut, il n'y a pas de compression. Avec la compression zstd, le mode long peut améliorer le ratio de compression, au détriment d'une augmentation de l'utilisation de la mémoire.

Le format d'archive tar ne prend actuellement en charge aucune compression.

--binary-upgrade

Cette option est réservée aux utilitaires de mise à niveau sur place. Son utilisation à d'autres fins n'est pas recommandée ni prise en charge. Le comportement de l'option peut changer dans les futures versions sans préavis.

--column-inserts
--attribute-inserts

Sauvegarde les données sous forme de commandes INSERT avec des noms de colonnes explicites (INSERT INTO table (colonne, ...) VALUES ...). Cela rendra la restauration très lente ; c'est principalement utile pour créer des sauvegardes qui peuvent être chargées dans des bases de données autres que PostgreSQL. Toute erreur pendant la restauration entraînera la perte uniquement des lignes faisant partie de l'INSERT problématique, plutôt que du contenu entier de la table.

--disable-dollar-quoting

Cette option désactive l'utilisation du délimiteur de chaînes dollar pour les corps de fonctions, et les force à être délimités en utilisant la syntaxe standard SQL pour les chaînes.

--disable-triggers

Cette option n'est pertinente que lors de la création d'une sauvegarde qui inclut des données mais pas le schéma. Elle demande à pg_dump d'inclure des commandes pour désactiver temporairement les déclencheurs (triggers) sur les tables cibles pendant la restauration des données. Utilisez cette option si vous avez des vérifications d'intégrité référentielle ou d'autres déclencheurs sur les tables que vous ne souhaitez pas activer lors de la restauration des données.

Actuellement, les commandes émises pour --disable-triggers doivent être exécutées par un superutilisateur. Par conséquent, vous devriez également spécifier un nom de superutilisateur avec -S, ou de préférence faire attention à démarrer le script résultant en tant que superutilisateur.

Cette option est ignorée lors de la génération d'un fichier de sortie d'archive (non texte). Pour les formats d'archive, vous pouvez spécifier l'option lors de l'appel de pg_restore.

--enable-row-security

Cette option n'est pertinente que lors de la sauvegarde du contenu d'une table qui a la sécurité au niveau des lignes activée. Par défaut, pg_dump désactive la sécurité au niveau des lignes (row_security), pour s'assurer que toutes les données sont sauvegardées à partir de la table. Si l'utilisateur n'a pas les privilèges suffisants pour contourner la sécurité au niveau des lignes, une erreur est alors générée. Ce paramètre demande à pg_dump d'activer la sécurité au niveau des lignes (row_security) à la place, permettant à l'utilisateur de sauvegarder les parties du contenu de la table auxquelles il a accès.

Notez que si vous utilisez cette option actuellement, vous voudrez probablement que la sauvegarde soit au format INSERT, car la commande COPY FROM lors de la restauration ne prend pas en charge la sécurité au niveau des lignes.

--exclude-extension=pattern

Ne sauvegarde aucune extension correspondant au pattern. Le modèle est interprété selon les mêmes règles que pour -e. --exclude-extension peut être spécifié plusieurs fois pour exclure des extensions correspondant à plusieurs modèles.

Lorsque -e et --exclude-extension sont tous deux donnés, le comportement est de sauvegarder uniquement les extensions qui correspondent à au moins un commutateur -e mais à aucun commutateur --exclude-extension. Si --exclude-extension apparaît sans -e, alors les extensions correspondant à --exclude-extension sont exclues de ce qui est par ailleurs une sauvegarde normale.

--exclude-table-and-children=pattern

Ceci est identique à l'option -T/--exclude-table, sauf qu'il exclut également toutes les partitions ou tables filles par héritage des tables correspondant au pattern.

--exclude-table-data=pattern

Ne sauvegarde pas les données de toute table correspondant au pattern. Le modèle est interprété selon les mêmes règles que pour -t. --exclude-table-data peut être spécifié plusieurs fois pour exclure des tables correspondant à plusieurs modèles. Cette option est utile lorsque vous avez besoin de la définition d'une table particulière bien que vous n'ayez pas besoin de ses données.

Pour exclure les données de toutes les tables de la base de données, consultez --schema-only ou --statistics-only.

--exclude-table-data-and-children=pattern

Ceci est identique à l'option --exclude-table-data, sauf qu'il exclut également les données de toutes les partitions ou tables filles par héritage des tables correspondant au pattern.

--extra-float-digits=ndigits

Utilise la valeur spécifiée de extra_float_digits lors de la sauvegarde des données à virgule flottante, au lieu de la précision maximale disponible. Les sauvegardes de routine effectuées à des fins de sauvegarde ne doivent pas utiliser cette option.

--filter=filename

Spécifie un nom de fichier à partir duquel lire les modèles pour les objets à inclure ou exclure de la sauvegarde. Les modèles sont interprétés selon les mêmes règles que les options correspondantes : -t/--table, --table-and-children, -T/--exclude-table et --exclude-table-and-children pour les tables, -n/--schema et -N/--exclude-schema pour les schémas, --include-foreign-data pour les données sur les serveurs étrangers, --exclude-table-data et --exclude-table-data-and-children pour les données de tables, et -e/--extension et --exclude-extension pour les extensions. Pour lire depuis STDIN, utilisez - comme nom de fichier. L'option --filter peut être spécifiée en conjonction avec les options listées ci-dessus pour inclure ou exclure des objets, et peut également être spécifiée plusieurs fois pour plusieurs fichiers de filtre.

Le fichier liste un modèle d'objet par ligne, avec le format suivant :

{ include | exclude } { extension | foreign_data | table | table_and_children | table_data | table_data_and_children | schema } PATTERN

Le premier mot-clé spécifie si les objets correspondant au modèle doivent être inclus ou exclus. Le second mot-clé spécifie le type d'objet à filtrer en utilisant le modèle :

•extension : extensions. Fonctionne comme l'option -e/--extension ou --exclude-extension.
•foreign_data : données sur les serveurs étrangers. Fonctionne comme l'option --include-foreign-data. Ce mot-clé ne peut être utilisé qu'avec le mot-clé include.
•table : tables. Fonctionne comme l'option -t/--table ou -T/--exclude-table.
•table_and_children : tables, y compris toute partition ou table fille par héritage. Fonctionne comme l'option --table-and-children ou --exclude-table-and-children.
•table_data : données de table de toute table correspondant au pattern. Fonctionne comme l'option --exclude-table-data. Ce mot-clé ne peut être utilisé qu'avec le mot-clé exclude.
•table_data_and_children : données de table de toute table correspondant au pattern, ainsi que toute partition ou table fille par héritage de la (des) table(s). Fonctionne comme l'option --exclude-table-data-and-children. Ce mot-clé ne peut être utilisé qu'avec le mot-clé exclude.
•schema : schémas. Fonctionne comme l'option -n/--schema ou -N/--exclude-schema.

Les lignes commençant par # sont considérées comme des commentaires et ignorées. Les commentaires peuvent également être placés après une ligne de modèle d'objet. Les lignes vides sont également ignorées. Voir Patterns pour savoir comment effectuer l'échappement dans les modèles.

Des exemples de fichiers sont listés ci-dessous dans la section Examples.

--if-exists

Utilise des commandes DROP ... IF EXISTS pour supprimer des objets en mode --clean. Cela supprime les erreurs “n'existe pas” qui pourraient autrement être signalées. Cette option n'est valide que si --clean est également spécifié.

--include-foreign-data=foreignserver

Sauvegarde les données de toute table étrangère dont le serveur étranger correspond au modèle foreignserver. Plusieurs serveurs étrangers peuvent être sélectionnés en écrivant plusieurs commutateurs --include-foreign-data. De plus, le paramètre foreignserver est interprété comme un modèle selon les mêmes règles utilisées par les commandes \d de psql (voir Patterns), de sorte que plusieurs serveurs étrangers peuvent également être sélectionnés en écrivant des caractères génériques dans le modèle. Lors de l'utilisation de caractères génériques, faites attention à échapper le modèle si nécessaire pour empêcher le shell d'étendre les caractères génériques ; voir les exemples ci-dessous. La seule exception est qu'un modèle vide est interdit.

Note
L'utilisation de caractères génériques dans --include-foreign-data peut entraîner un accès à des serveurs étrangers inattendus. De plus, pour utiliser cette option en toute sécurité, assurez-vous que le serveur nommé doit avoir un propriétaire de confiance.

Note
Lorsque --include-foreign-data est spécifié, pg_dump ne vérifie pas que la table étrangère est accessible en écriture. Par conséquent, il n'y a aucune garantie que les résultats d'une sauvegarde de table étrangère puissent être restaurés avec succès.

--inserts

Sauvegarde les données sous forme de commandes INSERT (plutôt que COPY). Cela rendra la restauration très lente ; c'est principalement utile pour créer des sauvegardes qui peuvent être chargées dans des bases de données autres que PostgreSQL. Toute erreur pendant la restauration entraînera la perte uniquement des lignes faisant partie de l'INSERT problématique, plutôt que du contenu entier de la table. Notez que la restauration pourrait échouer complètement si vous avez réorganisé l'ordre des colonnes. L'option --column-inserts est plus sûre contre les changements d'ordre des colonnes, bien qu'encore plus lente.

--load-via-partition-root

Lors de la sauvegarde des données d'une partition de table, fait que les instructions COPY ou INSERT ciblent la racine de la hiérarchie de partitionnement qui la contient, plutôt que la partition elle-même. Cela entraîne la rédétermination de la partition appropriée pour chaque ligne lors du chargement des données. Cela peut être utile lors de la restauration de données sur un serveur où les lignes ne tombent pas toujours dans les mêmes partitions qu'elles le faisaient sur le serveur d'origine. Cela pourrait se produire, par exemple, si la colonne de partitionnement est de type text et que les deux systèmes ont des définitions différentes de la collation utilisée pour trier la colonne de partitionnement.

--lock-wait-timeout=timeout

N'attendez pas indéfiniment pour acquérir des verrous de table partagés au début de la sauvegarde. Échouez plutôt si vous ne parvenez pas à verrouiller une table dans le délai spécifié timeout. Le délai peut être spécifié dans l'un des formats acceptés par SET statement_timeout. (Les formats autorisés varient en fonction de la version du serveur à partir de laquelle vous effectuez la sauvegarde, mais un nombre entier de millisecondes est accepté par toutes les versions.)

--no-comments

Ne sauvegarde pas les commandes COMMENT.

--no-data

Ne sauvegarde pas les données.

--no-policies

Ne sauvegarde pas les politiques de sécurité au niveau des lignes.

--no-publications

Ne sauvegarde pas les publications.

--no-schema

Ne sauvegarde pas le schéma (définitions de données).

--no-security-labels

Ne sauvegarde pas les étiquettes de sécurité.

--no-statistics

Ne sauvegarde pas les statistiques. C'est le comportement par défaut.

--no-subscriptions

Ne sauvegarde pas les abonnements.

--no-sync

Par défaut, pg_dump attend que tous les fichiers soient correctement écrits sur disque. Cette option fait que pg_dump retourne sans attendre, ce qui est plus rapide, mais signifie qu'un plantage ultérieur du système d'exploitation peut laisser la sauvegarde corrompue. Généralement, cette option est utile pour les tests, mais ne doit pas être utilisée lors de la sauvegarde de données d'une installation de production.

--no-table-access-method

Ne pas émettre les commandes pour sélectionner les méthodes d'accès aux tables. Avec cette option, tous les objets seront créés avec la méthode d'accès aux tables qui est la valeur par défaut lors de la restauration.

Cette option est ignorée lors de l'émission d'un fichier de sortie d'archive (non texte). Pour les formats d'archive, vous pouvez spécifier l'option lorsque vous appelez pg_restore.

--no-tablespaces

Ne pas émettre les commandes pour sélectionner les tablespaces. Avec cette option, tous les objets seront créés dans le tablespace qui est la valeur par défaut lors de la restauration.

Cette option est ignorée lors de l'émission d'un fichier de sortie d'archive (non texte). Pour les formats d'archive, vous pouvez spécifier l'option lorsque vous appelez pg_restore.

--no-toast-compression

Ne pas émettre les commandes pour définir les méthodes de compression TOAST. Avec cette option, toutes les colonnes seront restaurées avec le réglage de compression par défaut.

--no-unlogged-table-data

Ne pas sauvegarder le contenu des tables et séquences non enregistrées (unlogged). Cette option n'a aucun effet sur le fait que les définitions de tables et de séquences (schéma) soient sauvegardées ou non ; elle supprime uniquement la sauvegarde des données des tables et des séquences. Les données des tables et séquences non enregistrées sont toujours exclues lors d'une sauvegarde à partir d'un serveur standby.

--on-conflict-do-nothing

Ajouter ON CONFLICT DO NOTHING aux commandes INSERT. Cette option n'est pas valide à moins que --inserts, --column-inserts ou --rows-per-insert ne soient également spécifiés.

--quote-all-identifiers

Forcer la mise entre guillemets de tous les identificateurs. Cette option est recommandée lors de la sauvegarde d'une base de données depuis un serveur dont la version majeure de PostgreSQL est différente de celle de pg_dump, ou lorsque la sortie est destinée à être chargée dans un serveur d'une version majeure différente. Par défaut, pg_dump ne met entre guillemets que les identificateurs qui sont des mots réservés dans sa propre version majeure. Cela entraîne parfois des problèmes de compatibilité lors de la gestion de serveurs d'autres versions qui peuvent avoir des ensembles de mots réservés légèrement différents. L'utilisation de --quote-all-identifiers évite de tels problèmes, au prix d'un script de sauvegarde plus difficile à lire.

--restrict-key=cle_restreinte

Utiliser la chaîne fournie comme clé \restrict de psql dans la sortie de la sauvegarde. Ceci ne peut être spécifié que pour les sauvegardes en texte brut, c'est-à-dire lorsque --format est défini sur plain ou que l'option --format est omise. Si aucune clé restreinte n'est spécifiée, pg_dump en générera une aléatoire si nécessaire. Les clés ne peuvent contenir que des caractères alphanumériques.

Cette option est principalement destinée à des fins de test et à d'autres scénarios nécessitant une sortie reproductible (par exemple, la comparaison des fichiers de sauvegarde). Elle n'est pas recommandée pour une utilisation générale, car un serveur malveillant ayant une connaissance préalable de la clé pourrait être capable d'injecter du code arbitraire qui sera exécuté sur la machine qui exécute psql avec la sortie de la sauvegarde.

--rows-per-insert=nb_lignes

Sauvegarder les données sous forme de commandes INSERT (plutôt que COPY). Contrôle le nombre maximum de lignes par commande INSERT. La valeur spécifiée doit être un nombre supérieur à zéro. Toute erreur lors de la restauration ne fera perdre que les lignes faisant partie de l'INSERT problématique, plutôt que le contenu entier de la table.

--section=nom_section

Ne sauvegarder que la section nommée. Le nom de la section peut être pre-data, data, ou post-data. Cette option peut être spécifiée plusieurs fois pour sélectionner plusieurs sections. Par défaut, toutes les sections sont sauvegardées.

La section de données contient les données réelles des tables, les contenus des objets volumineux, les valeurs des séquences et les statistiques pour les tables, les vues matérialisées et les tables étrangères. Les éléments post-données comprennent les définitions des index, des déclencheurs (triggers), des règles, des statistiques pour les index et des contraintes autres que les contraintes CHECK et NOT NULL validées. Les éléments pré-données comprennent tous les autres éléments de définition de données.

--sequence-data

Inclure les données de séquence dans la sauvegarde. C'est le comportement par défaut, sauf lorsque --no-data, --schema-only ou --statistics-only sont spécifiés.

--serializable-deferrable

Utiliser une transaction sérialisable pour la sauvegarde, afin de garantir que le snapshot utilisé est cohérent avec les états ultérieurs de la base de données ; mais le faire en attendant un point dans le flux de transactions où aucune anomalie ne peut être présente, de sorte qu'il n'y ait pas de risque que la sauvegarde échoue ou que d'autres transactions soient annulées avec une serialization_failure. Voir le Chapitre 13 pour plus d'informations sur l'isolation des transactions et le contrôle de la concurrence.

Cette option n'est pas bénéfique pour une sauvegarde destinée uniquement à la reprise après sinistre. Elle pourrait être utile pour une sauvegarde utilisée pour charger une copie de la base de données à des fins de reporting ou d'autres partages de charge en lecture seule pendant que la base de données originale continue d'être mise à jour. Sans elle, la sauvegarde peut refléter un état qui n'est pas cohérent avec une exécution sérielle des transactions finalement validées. Par exemple, si des techniques de traitement par lots sont utilisées, un lot peut apparaître comme fermé dans la sauvegarde sans que tous les éléments qui le composent n'apparaissent.

Cette option ne fera aucune différence s'il n'y a pas de transactions en lecture-écriture actives lorsque pg_dump est démarré. Si des transactions en lecture-écriture sont actives, le démarrage de la sauvegarde peut être retardé pendant une durée indéterminée. Une fois en cours d'exécution, les performances avec ou sans l'option sont les mêmes.

--snapshot=nom_snapshot

Utiliser le snapshot synchronisé spécifié lors de la création d'une sauvegarde de la base de données (voir le Tableau 9.100 pour plus de détails).

Cette option est utile lorsque l'on doit synchroniser la sauvegarde avec un slot de réplication logique (voir le Chapitre 47) ou avec une session concurrente.

Dans le cas d'une sauvegarde parallèle, le nom du snapshot défini par cette option est utilisé au lieu de prendre un nouveau snapshot.

--statistics

Sauvegarder les statistiques.

--statistics-only

Sauvegarder uniquement les statistiques, pas le schéma (définitions de données) ni les données. Les statistiques pour les tables, les vues matérialisées, les tables étrangères et les index sont sauvegardées.

--strict-names

Exiger que chaque extension (-e/--extension), schéma (-n/--schema) et table (-t/--table) corresponde à au moins une extension/schéma/table dans la base de données à sauvegarder. Cela s'applique également aux filtres utilisés avec --filter. Notez que si aucun des modèles d'extension/schéma/table ne trouve de correspondance, pg_dump générera une erreur même sans --strict-names.

Cette option n'a aucun effet sur --exclude-extension, -N/--exclude-schema, -T/--exclude-table, ou --exclude-table-data. Un modèle d'exclusion ne correspondant à aucun objet n'est pas considéré comme une erreur.

--sync-method=méthode

Lorsqu'il est défini sur fsync, ce qui est la valeur par défaut, pg_dump --format=directory ouvrira et synchronisera récursivement tous les fichiers dans le répertoire d'archive.

Sous Linux, syncfs peut être utilisé à la place pour demander au système d'exploitation de synchroniser l'intégralité du système de fichiers qui contient le répertoire d'archive. Voir recovery_init_sync_method pour des informations sur les mises en garde à connaître lors de l'utilisation de syncfs.

Cette option n'a aucun effet lorsque --no-sync est utilisé ou lorsque --format n'est pas défini sur directory.

--table-and-children=motif

C'est la même chose que l'option -t/--table, sauf qu'elle inclut également toutes les partitions ou tables filles par héritage des tables correspondant au motif.

--use-set-session-authorization

Émettre des commandes SQL standard SET SESSION AUTHORIZATION au lieu de commandes ALTER OWNER pour déterminer la propriété des objets. Cela rend la sauvegarde plus compatible avec les standards, mais en fonction de l'historique des objets dans la sauvegarde, cela pourrait ne pas se restaurer correctement. De plus, une sauvegarde utilisant SET SESSION AUTHORIZATION nécessitera certainement des privilèges superutilisateur pour être restaurée correctement, alors que ALTER OWNER nécessite des privilèges moindres.

-?
--help

Afficher l'aide sur les arguments de la ligne de commande de pg_dump et quitter.

Les options de ligne de commande suivantes contrôlent les paramètres de connexion à la base de données.

-d nom_base
--dbname=nom_base

Spécifie le nom de la base de données à laquelle se connecter. Cela équivaut à spécifier nom_base comme premier argument non optionnel sur la ligne de commande. Le nom_base peut être une chaîne de connexion. Si c'est le cas, les paramètres de la chaîne de connexion outrepasseront toute option de ligne de commande conflictuelle.

-h hote
--host=hote

Spécifie le nom de l'hôte de la machine sur laquelle le serveur est en cours d'exécution. Si la valeur commence par une barre oblique, elle est utilisée comme répertoire pour le socket de domaine Unix. La valeur par défaut est tirée de la variable d'environnement PGHOST, si elle est définie, sinon une connexion par socket de domaine Unix est tentée.

-p port
--port=port

Spécifie le port TCP ou l'extension du fichier de socket de domaine local sur lequel le serveur écoute les connexions. Par défaut, c'est la variable d'environnement PGPORT, si elle est définie, ou une valeur par défaut compilée.

-U nom_utilisateur
--username=nom_utilisateur

Nom d'utilisateur pour se connecter.

-w
--no-password

Ne jamais demander de mot de passe. Si le serveur requiert une authentification par mot de passe et qu'un mot de passe n'est pas disponible par d'autres moyens, comme un fichier .pgpass, la tentative de connexion échouera. Cette option peut être utile dans les travaux par lots et les scripts où aucun utilisateur n'est présent pour entrer un mot de passe.

-W
--password

Force pg_dump à demander un mot de passe avant de se connecter à une base de données.

Cette option n'est jamais essentielle, car pg_dump demandera automatiquement un mot de passe si le serveur exige une authentification par mot de passe. Cependant, pg_dump gaspillera une tentative de connexion pour découvrir que le serveur veut un mot de passe. Dans certains cas, il est utile de taper -W pour éviter la connexion supplémentaire.

--role=nom_role

Spécifie un nom de rôle à utiliser pour créer la sauvegarde. Cette option amène pg_dump à émettre une commande SET ROLE nom_role en communnd après la connexion à la base de données. C'est utile lorsque l'utilisateur authentifié (spécifié par -U) manque des privilèges nécessaires à pg_dump, mais peut basculer vers un rôle disposant des droits requis. Certaines installations ont une politique interdisant la connexion directe en tant que superutilisateur, et l'utilisation de cette option permet de réaliser des sauvegardes sans enfreindre cette politique.

DIAGNOSTICS

pg_dump exécute en interne des instructions SELECT. Si vous rencontrez des problèmes pour exécuter pg_dump, assurez-vous que vous pouvez sélectionner des informations de la base de données en utilisant, par exemple, psql(1). De plus, tous les paramètres de connexion par défaut et les variables d'environnement utilisés par la bibliothèque frontale libpq s'appliqueront.

L'activité de la base de données de pg_dump est normalement collectée par le système de statistiques cumulatives. Si cela est indésirable, vous pouvez définir le paramètre track_counts sur false via PGOPTIONS ou la commande ALTER USER.

NOTES

Si votre cluster de bases de données a des ajouts locaux à la base de données template1, veillez à restaurer la sortie de pg_dump dans une base de données véritablement vide ; sinon, vous risquez d'obtenir des erreurs dues à des définitions dupliquées des objets ajoutés. Pour créer une base de données vide sans aucun ajout local, copiez depuis template0 et non template1, par exemple :

CREATE DATABASE foo WITH TEMPLATE template0;

Lorsqu'une sauvegarde sans schéma est choisie et que l'option --disable-triggers est utilisée, pg_dump émet des commandes pour désactiver les déclencheurs sur les tables utilisateur avant d'insérer les données, puis des commandes pour les réactiver après l'insertion des données. Si la restauration est arrêtée en cours de processus, les catalogues système pourraient se retrouver dans un état incorrect.

Si --statistics est spécifié, pg_dump inclura la plupart des statistiques de l'optimiseur dans le fichier de sauvegarde résultant. Cependant, certaines statistiques pourraient ne pas être incluses, comme celles créées explicitement avec CREATE STATISTICS (CREATE_STATISTICS(7)) ou des statistiques personnalisées ajoutées par une extension. Par conséquent, il peut être utile d'exécuter ANALYZE après avoir restauré à partir d'un fichier de sauvegarde pour garantir des performances optimales ; voir Section 24.1.3 et Section 24.1.6 pour plus d'informations.

Étant donné que pg_dump est utilisé pour transférer des données vers des versions plus récentes de PostgreSQL, la sortie de pg_dump peut être chargée dans des versions de serveur PostgreSQL plus récentes que la version de pg_dump. pg_dump peut également sauvegarder à partir de serveurs PostgreSQL plus anciens que sa propre version. (Actuellement, les serveurs jusqu'à la version 9.2 sont pris en charge.) Cependant, pg_dump ne peut pas sauvegarder à partir de serveurs PostgreSQL plus récents que sa propre version majeure ; il refusera même d'essayer, plutôt que de risquer de faire une sauvegarde invalide. De plus, il n'est pas garanti que la sortie de pg_dump puisse être chargée dans un serveur d'une version majeure antérieure — pas même si la sauvegarde a été effectuée à partir d'un serveur de cette version. Charger un fichier de sauvegarde dans un serveur plus ancien peut nécessiter une édition manuelle du fichier de sauvegarde pour supprimer la syntaxe non comprise par le serveur plus ancien. L'utilisation de l'option --quote-all-identifiers est recommandée dans les cas inter-versions, car elle peut empêcher les problèmes découlant des listes de mots réservés variables dans différentes versions de PostgreSQL.

Lors de la sauvegarde des abonnements de réplication logique, pg_dump générera des commandes CREATE SUBSCRIPTION utilisant l'option connect = false, de sorte que la restauration de l'abonnement ne crée pas de connexions distantes pour créer un slot de réplication ou pour la copie initiale des tables. Ainsi, la sauvegarde peut être restaurée sans nécessiter d'accès réseau aux serveurs distants. Il incombe alors à l'utilisateur de réactiver les abonnements d'une manière appropriée. Si les hôtes impliqués ont changé, les informations de connexion pourraient devoir être modifiées. Il pourrait également être approprié de tronquer les tables cibles avant d'initier une nouvelle copie complète des tables. Si les utilisateurs ont l'intention de copier les données initiales lors du rafraîchissement, ils doivent créer le slot avec two_phase = false. Après la synchronisation initiale, l'option two_phase sera automatiquement activée par l'abonné si l'abonnement avait été initialement créé avec l'option two_phase = true.

Il est généralement recommandé d'utiliser l'option -X (--no-psqlrc) lors de la restauration d'une base de données à partir d'un script pg_dump en texte brut pour garantir un processus de restauration propre et empêcher des conflits potentiels avec des configurations psql non par défaut.

EXEMPLES

Pour sauvegarder une base de données nommée mydb dans un fichier de script SQL :

$ pg_dump mydb > db.sql

Pour recharger un tel script dans une base de données (fraîchement créée) nommée newdb :

$ psql -X -d newdb -f db.sql

Pour sauvegarder une base de données dans un fichier d'archive au format personnalisé :

$ pg_dump -Fc mydb > db.dump

Pour sauvegarder une base de données dans une archive au format répertoire :

$ pg_dump -Fd mydb -f dumpdir

Pour sauvegarder une base de données dans une archive au format répertoire en parallèle avec 5 tâches d'ouvrier :

$ pg_dump -Fd mydb -j 5 -f dumpdir

Pour recharger un fichier d'archive dans une base de données (fraîchement créée) nommée newdb :

$ pg_restore -d newdb db.dump

Pour recharger un fichier d'archive dans la même base de données dont il a été sauvegardé, en supprimant le contenu actuel de cette base de données :

$ pg_restore -d postgres --clean --create db.dump

Pour sauvegarder une seule table nommée mytab :

$ pg_dump -t mytab mydb > db.sql

Pour sauvegarder toutes les tables dont les noms commencent par emp dans le schéma detroit, à l'exception de la table employee_log :

$ pg_dump -t 'detroit.emp*' -T detroit.employee_log mydb > db.sql

Pour sauvegarder tous les schémas dont les noms commencent par east ou west et se terminent par gsm, en excluant tout schéma dont les noms contiennent le mot test :

$ pg_dump -n 'east*gsm' -n 'west*gsm' -N '*test*' mydb > db.sql

La même chose, en utilisant la notation d'expressions régulières pour consolider les options :

$ pg_dump -n '(east|west)*gsm' -N '*test*' mydb > db.sql

Pour sauvegarder tous les objets de la base de données à l'exception des tables dont les noms commencent par ts_ :

$ pg_dump -T 'ts_*' mydb > db.sql

Pour spécifier un nom en majuscules ou en casse mixte dans -t et les options associées, vous devez mettre le nom entre guillemets doubles ; sinon, il sera converti en minuscules (voir Patterns). Mais les guillemets doubles sont spéciaux pour le shell, ils doivent donc à leur tour être cités. Ainsi, pour sauvegarder une seule table avec un nom en casse mixte, vous avez besoin de quelque chose comme

$ pg_dump -t "\"MixedCaseName\"" mydb > mytab.sql

Pour sauvegarder toutes les tables dont les noms commencent par mytable, à l'exception de la table mytable2, spécifiez un fichier de filtre filter.txt comme suit :

include table mytable*
exclude table mytable2
$ pg_dump --filter=filter.txt mydb > db.sql
