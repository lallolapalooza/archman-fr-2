PG_RESETWAL(1) Documentation PostgreSQL 18.1 PG_RESETWAL(1)

NOM

pg_resetwal - réinitialise le journal d'écriture anticipée (write-ahead log) et d'autres informations de contrôle d'un cluster de bases de données PostgreSQL

SYNTAXE

pg_resetwal [-f | --force] [-n | --dry-run] [option...] [-D | --pgdata]datadir

DESCRIPTION

pg_resetwal efface le journal d'écriture anticipée (WAL) et, éventuellement, réinitialise d'autres informations de contrôle stockées dans le fichier pg_control. Cette fonction est parfois nécessaire si ces fichiers sont corrompus. Elle ne doit être utilisée qu'en dernier recours, lorsque le serveur ne démarre pas en raison d'une telle corruption.

Certaines options, comme --wal-segsize (voir ci-dessous), peuvent également être utilisées pour modifier certains paramètres globaux d'un cluster de bases de données sans avoir à réexécuter initdb. Cela peut être fait en toute sécurité sur un cluster de bases de données autrement sain, si aucun des modes dangereux mentionnés ci-dessous n'est utilisé.

Si pg_resetwal est utilisé sur un répertoire de données où le serveur a été arrêté proprement et où le fichier de contrôle est sain, il n'aura aucun effet sur le contenu du système de base de données, à l'exception du nettoyage des fichiers WAL qui ne sont plus utilisés. Toute autre utilisation est potentiellement dangereuse et doit être effectuée avec une grande prudence. pg_resetwal exigera que l'option -f (force) soit spécifiée avant de travailler sur un répertoire de données dans un état d'arrêt non propre ou avec un fichier de contrôle corrompu.

Après avoir exécuté cette commande sur un répertoire de données avec un WAL corrompu ou un fichier de contrôle corrompu, il devrait être possible de démarrer le serveur, mais gardez à l'esprit que la base de données peut contenir des données incohérentes en raison de transactions partiellement validées. Vous devriez immédiatement sauvegarder vos données, exécuter initdb et restaurer. Après la restauration, vérifiez les incohérences et réparez si nécessaire.

Si pg_resetwal signale qu'il ne peut pas déterminer des données valides pour pg_control, vous pouvez le forcer à continuer en spécifiant l'option -f (force). Dans ce cas, des valeurs plausibles seront substituées pour les données manquantes. La plupart des champs devraient correspondre, mais une assistance manuelle peut être nécessaire pour les champs suivants : prochain OID, prochain ID de transaction et époque, prochain ID multitransaction et décalage, et emplacement de début du WAL. Ces champs peuvent être définis en utilisant les options décrites ci-dessous. Si vous n'êtes pas en mesure de déterminer les valeurs correctes pour tous ces champs, -f peut toujours être utilisé, mais la base de données récupérée doit être traitée avec encore plus de suspicion que d'habitude : une sauvegarde et une restauration immédiates sont impératives. *N'exécutez aucune opération modifiant les données dans la base de données avant d'effectuer la sauvegarde*, car toute action de ce type risque d'aggraver la corruption.

Cet utilitaire ne peut être exécuté que par l'utilisateur qui a installé le serveur, car il nécessite un accès en lecture/écriture au répertoire de données.

OPTIONS

datadir
-D datadir
--pgdata=datadir

Spécifie l'emplacement du répertoire de données. Pour des raisons de sécurité, vous devez spécifier le répertoire de données dans la ligne de commande. pg_resetwal n'utilise pas la variable d'environnement PGDATA.

-f
--force

Force pg_resetwal à continuer même dans des situations où cela pourrait être dangereux, comme expliqué ci-dessus. Plus précisément, cette option est nécessaire pour continuer si le serveur n'a pas été arrêté proprement ou si pg_resetwal ne peut pas déterminer de données valides pour pg_control.

-n
--dry-run

L'option -n/--dry-run demande à pg_resetwal d'afficher les valeurs reconstruites à partir de pg_control et les valeurs sur le point d'être modifiées, puis de quitter sans rien modifier. Il s'agit principalement d'un outil de débogage, mais il peut être utile comme vérification de sanity avant de permettre à pg_resetwal de continuer réellement.

-V
--version

Affiche les informations de version, puis quitte.

-?
--help

Affiche l'aide, puis quitte.

Les options suivantes ne sont nécessaires que lorsque pg_resetwal n'est pas en mesure de déterminer les valeurs appropriées en lisant pg_control. Des valeurs sûres peuvent être déterminées comme décrit ci-dessous. Pour les valeurs qui prennent des arguments numériques, les valeurs hexadécimales peuvent être spécifiées en utilisant le préfixe 0x. Notez que ces instructions ne s'appliquent qu'avec la taille de bloc par défaut de 8 Ko.

-c xid,xid
--commit-timestamp-ids=xid,xid

Définit manuellement les identifiants de transaction les plus anciens et les plus récents pour lesquels l'horodatage de validation peut être récupéré.

Une valeur sûre pour l'identifiant de transaction le plus ancien pour lequel l'horodatage de validation peut être récupéré (première partie) peut être déterminée en recherchant le nom de fichier numériquement le plus petit dans le répertoire pg_commit_ts sous le répertoire de données. Inversement, une valeur sûre pour l'identifiant de transaction le plus récent pour lequel l'horodatage de validation peut être récupéré (deuxième partie) peut être déterminée en recherchant le nom de fichier numériquement le plus grand dans le même répertoire. Les noms de fichiers sont en hexadécimal.

-e xid_epoch
--epoch=xid_epoch

Définit manuellement l'époque du prochain identifiant de transaction.

L'époque de l'identifiant de transaction n'est en fait stockée nulle part dans la base de données, sauf dans le champ défini par pg_resetwal, donc n'importe quelle valeur fonctionnera en ce qui concerne la base de données elle-même. Vous pourriez avoir besoin d'ajuster cette valeur pour garantir que les systèmes de réplication tels que Slony-I et Skytools fonctionnent correctement — si tel est le cas, une valeur appropriée devrait être obtenable à partir de l'état de la base de données répliquée en aval.

-l walfile
--next-wal-file=walfile

Définit manuellement l'emplacement de début du WAL en spécifiant le nom du prochain fichier segment WAL.

Le nom du prochain fichier segment WAL doit être supérieur à tout nom de fichier segment WAL existant actuellement dans le répertoire pg_wal sous le répertoire de données. Ces noms sont également en hexadécimal et ont trois parties. La première partie est l'identifiant de la chronologie (timeline ID) et doit généralement rester la même. Par exemple, si 00000001000000320000004A est la plus grande entrée dans pg_wal, utilisez -l 00000001000000320000004B ou une valeur supérieure.

Notez que lors de l'utilisation de tailles de segments WAL non par défaut, les nombres dans les noms de fichiers WAL sont différents des LSN rapportés par les fonctions système et les vues système. Cette option prend un nom de fichier WAL, pas un LSN.


Note
pg_resetwal examine lui-même les fichiers dans pg_wal et choisit un réglage par défaut pour -l supérieur au dernier nom de fichier existant. Par conséquent, un ajustement manuel de -l ne devrait être nécessaire que si vous êtes au courant de fichiers segments WAL qui ne sont pas actuellement présents dans pg_wal, tels que des entrées dans une archive hors ligne ; ou si le contenu de pg_wal a été entièrement perdu.

-m mxid,mxid
--multixact-ids=mxid,mxid

Définit manuellement le prochain ID multitransaction et l'ID multitransaction le plus ancien.

Une valeur sûre pour le prochain ID multitransaction (première partie) peut être déterminée en recherchant le nom de fichier numériquement le plus grand dans le répertoire pg_multixact/offsets sous le répertoire de données, en ajoutant un, puis en multipliant par 65536 (0x10000). Inversement, une valeur sûre pour l'ID multitransaction le plus ancien (deuxième partie de -m) peut être déterminée en recherchant le nom de fichier numériquement le plus petit dans le même répertoire et en multipliant par 65536. Les noms de fichiers sont en hexadécimal, donc le moyen le plus simple est de spécifier la valeur de l'option en hexadécimal et d'ajouter quatre zéros.

-o oid
--next-oid=oid

Définit manuellement le prochain OID.

Il n'y a pas de moyen comparablement simple de déterminer un prochain OID qui soit supérieur au plus grand de la base de données, mais heureusement, il n'est pas critique d'obtenir le réglage du prochain OID correctement.

-O mxoff
--multixact-offset=mxoff

Définit manuellement le prochain décalage multitransaction.

Une valeur sûre peut être déterminée en recherchant le nom de fichier numériquement le plus grand dans le répertoire pg_multixact/members sous le répertoire de données, en ajoutant un, puis en multipliant par 52352 (0xCC80). Les noms de fichiers sont en hexadécimal. Il n'y a pas de recette simple comme pour les autres options d'ajout de zéros.

-u xid
--oldest-transaction-id=xid

Définit manuellement le plus ancien ID de transaction non gelé.

Un valeur sûre pour ce champ peut être déterminée en examinant le champ oldest_xid dans le fichier pg_control et en prenant la valeur la plus petite qui est dans le répertoire pg_xact sous le répertoire de données. Si vous ne pouvez pas déterminer une telle valeur, vous pouvez utiliser une valeur de 1, mais cela rendra votre base de données plus sujette à des problèmes liés à l'ancienneté des transactions (voir la documentation de PostgreSQL).

--wal-segsize=bytes

Définit la taille du segment WAL en octets. La taille par défaut est 16 Mo. Cette valeur ne peut être modifiée que lorsque le cluster est arrêté. Après avoir changé cette option, vous devrez probablement recréer les fichiers de WAL existants pour que la nouvelle taille soit prise en compte. Le redémarrage du serveur générera de nouveaux fichiers WAL avec la taille spécifiée.

EXEMPLES

Pour forcer la réinitialisation d'un cluster de bases de données qui s'est arrêté de manière anormale et dont le fichier pg_control est potentiellement corrompu :

$ pg_resetwal -f /var/lib/postgresql/data

Pour effectuer une exécution à sec sur le même répertoire de données :

$ pg_resetwal -n /var/lib/postgresql/data

Pour spécifier manuellement le prochain OID et le prochain ID multitransaction :

$ pg_resetwal -o 181234 -m 0,54321000000000000000 -D /var/lib/postgresql/data

NOTES

Cet utilitaire ne doit être utilisé que si vous êtes certain qu'il est nécessaire. Il est conçu pour des situations de récupération d'urgence. L'utilisation incorrecte peut entraîner une perte de données irréversible.

Il est toujours recommandé de faire une sauvegarde complète du répertoire de données avant d'utiliser pg_resetwal.

Si possible, récupérez les valeurs correctes pour les options manuelles à partir de sauvegardes ou d'autres informations fiables. Si vous spécifiez des valeurs incorrectes, cela pourrait entraîner une corruption supplémentaire ou une perte de données.

--char-signedness=option

Définit manuellement la signature par défaut des caractères. Les valeurs possibles sont signed et unsigned.

Pour un cluster de base de données que pg_upgrade a mis à niveau à partir d'une version de PostgreSQL antérieure à la version 18, la valeur sûre serait la signature par défaut des caractères de la plateforme qui exécutait le cluster avant cette mise à niveau. Pour tous les autres clusters, signed serait la valeur sûre. Cependant, cette option est exclusivement destinée à être utilisée avec pg_upgrade et ne doit normalement pas être utilisée manuellement.

--wal-segsize=wal_segment_size

Définit la nouvelle taille des segments WAL, en mégaoctets. La valeur doit être une puissance de 2 comprise entre 1 et 1024 (mégaoctets). Voir la même option de initdb(1) pour plus d'informations.

Cette option peut également être utilisée pour modifier la taille des segments WAL d'un cluster de base de données existant, évitant ainsi le besoin de re-initdb.


Note
Bien que pg_resetwal définisse l'adresse de départ WAL au-delà du dernier fichier de segment WAL existant, certains changements de taille de segment peuvent entraîner la réutilisation des anciens noms de fichiers WAL. Il est recommandé d'utiliser -l conjointement avec cette option pour définir manuellement l'adresse de départ WAL si le chevauchement des noms de fichiers WAL pose des problèmes à votre stratégie d'archivage.

ENVIRONNEMENT

PG_COLOR

Spécifie si la couleur doit être utilisée dans les messages de diagnostic. Les valeurs possibles sont always, auto et never.

NOTES

Cette commande ne doit pas être utilisée lorsque le serveur est en cours d'exécution. pg_resetwal refusera de démarrer s'il trouve un fichier de verrouillage du serveur dans le répertoire de données. Si le serveur a planté, un fichier de verrouillage pourrait avoir été laissé ; dans ce cas, vous pouvez supprimer le fichier de verrouillage pour permettre à pg_resetwal de s'exécuter. Mais avant de le faire, assurez-vous bien qu'aucun processus serveur n'est encore actif.

pg_resetwal ne fonctionne qu'avec des serveurs de la même version majeure.
