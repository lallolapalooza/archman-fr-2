PG_CREATESUBSCRIBER(1) Documentation PostgreSQL 18.1 PG_CREATESUBSCRIBER(1)

NOM

pg_createsubscriber - convertir une réplique physique en une nouvelle réplique logique

SYNTAXE

pg_createsubscriber [option...] {-d | --database}nom_base {-D | --pgdata}repertoire_donnees {-P | --publisher-server}chaine_connexion

DESCRIPTION

pg_createsubscriber crée une nouvelle réplique logique à partir d'un serveur de réplique physique (standby). Toutes les tables de la base de données spécifiée sont incluses dans la configuration de la réplication logique. Une paire d'objets publication et abonnement est créée pour chaque base de données. Cela doit être exécuté sur le serveur cible.

Après une exécution réussie, l'état du serveur cible est analogue à une configuration de réplication logique fraîche. La principale différence entre la configuration de réplication logique et pg_createsubscriber réside dans la manière dont la synchronisation des données est effectuée. pg_createsubscriber ne copie pas les données initiales des tables. Il effectue uniquement la phase de synchronisation, qui garantit que chaque table est amenée à un état synchronisé.

pg_createsubscriber cible les grands systèmes de bases de données car dans une configuration de réplication logique, la majeure partie du temps est consacrée à la copie initiale des données. De plus, un effet secondaire de ce long temps consacré à la synchronisation des données est généralement une grande quantité de modifications à appliquer (qui ont été produites pendant la copie initiale des données), ce qui augmente encore le temps nécessaire pour que la réplique logique soit disponible. Pour les bases de données plus petites, il est recommandé de configurer la réplication logique avec synchronisation initiale des données. Pour plus de détails, voir l'option copy_data de CREATE SUBSCRIPTION.

OPTIONS

pg_createsubscriber accepte les arguments de ligne de commande suivants :

-a
--all

Crée un abonnement par base de données sur le serveur cible. Les exceptions sont les bases de données modèles et les bases de données qui n'autorisent pas les connexions. Pour découvrir la liste de toutes les bases de données, connectez-vous au serveur source en utilisant le nom de base de données spécifié dans la chaîne de connexion --publisher-server, ou si non spécifié, la base de données postgres sera utilisée, ou si celle-ci n'existe pas, template1 sera utilisée. Des noms générés automatiquement pour les abonnements, les publications et les slots de réplication sont utilisés lorsque cette option est spécifiée. Cette option ne peut pas être utilisée conjointement avec --database, --publication, --replication-slot, ou --subscription.

-d nom_base
--database=nom_base

Le nom de la base de données dans laquelle créer un abonnement. Plusieurs bases de données peuvent être sélectionnées en écrivant plusieurs options -d. Cette option ne peut pas être utilisée avec -a. Si l'option -d n'est pas fournie, le nom de la base de données sera obtenu à partir de l'option -P. Si le nom de la base de données n'est spécifié ni dans l'option -d, ni dans l'option -P, et que l'option -a n'est pas spécifiée, une erreur sera signalée.

-D repertoire
--pgdata=repertoire

Le répertoire cible contenant un répertoire de cluster provenant d'une réplique physique.

-n
--dry-run

Fait tout sauf modifier réellement le répertoire cible.

-p port
--subscriber-port=port

Le numéro de port sur lequel le serveur cible écoute les connexions. Par défaut, le serveur cible tourne sur le port 50432 pour éviter les connexions client non intentionnelles.

-P chaine_connexion
--publisher-server=chaine_connexion

La chaîne de connexion vers l'éditeur (publisher). Pour les détails, voir la Section 32.1.1.

-s dir
--socketdir=dir

Le répertoire à utiliser pour les sockets postmaster sur le serveur cible. Par défaut, c'est le répertoire courant.

-t secondes
--recovery-timeout=secondes

Le nombre maximum de secondes à attendre pour que la récupération se termine. Le réglage à 0 désactive. Par défaut, c'est 0.

-T
--enable-two-phase

Active la validation en deux phases (two_phase commit) pour l'abonnement. Lorsque plusieurs bases de données sont spécifiées, cette option s'applique uniformément à tous les abonnements créés sur ces bases de données. Par défaut, c'est faux.

-U nom_utilisateur
--subscriber-username=nom_utilisateur

Le nom d'utilisateur pour se connecter sur le serveur cible. Par défaut, c'est le nom d'utilisateur du système d'exploitation courant.

-v
--verbose

Active le mode verbeux. Cela fera afficher à pg_createsubscriber les messages de progression et des informations détaillées sur chaque étape vers la sortie d'erreur standard. Répéter l'option fait apparaître des messages supplémentaires de niveau débogage dans la sortie d'erreur standard.

--clean=type_objet

Supprime tous les objets du type spécifié des bases de données spécifiées sur le serveur cible.
•publications : Les publications FOR ALL TABLES établies pour cet abonné sont toujours supprimées ; spécifier ce type d'objet entraîne la suppression de toutes les autres publications répliquées à partir du serveur source.

Les objets sélectionnés pour être supprimés sont individuellement enregistrés, y compris lors d'un --dry-run. Il n'y a aucune possibilité d'influencer ou d'arrêter la suppression des objets sélectionnés, alors envisagez d'en faire une sauvegarde en utilisant pg_dump.

--config-file=nom_fichier

Utilise le fichier de configuration du serveur principal spécifié pour le répertoire de données cible. pg_createsubscriber utilise en interne la commande pg_ctl pour démarrer et arrêter le serveur cible. Il vous permet de spécifier le fichier de configuration postgresql.conf réel s'il est stocké en dehors du répertoire de données.

--publication=nom

Le nom de la publication pour configurer la réplication logique. Plusieurs publications peuvent être spécifiées en écrivant plusieurs options --publication. Le nombre de noms de publications doit correspondre au nombre de bases de données spécifiées, sinon une erreur sera signalée. L'ordre des options de nom de publication multiples doit correspondre à l'ordre des options de base de données. Si cette option n'est pas spécifiée, un nom généré est attribué au nom de la publication. Cette option ne peut pas être utilisée conjointement avec --all.

--replication-slot=nom

Le nom du slot de réplication pour configurer la réplication logique. Plusieurs slots de réplication peuvent être spécifiés en écrivant plusieurs options --replication-slot. Le nombre de noms de slots de réplication doit correspondre au nombre de bases de données spécifiées, sinon une erreur sera signalée. L'ordre des options de nom de slot de réplication multiples doit correspondre à l'ordre des options de base de données. Si cette option n'est pas spécifiée, le nom de l'abonnement est attribué au nom du slot de réplication. Cette option ne peut pas être utilisée conjointement avec --all.

--subscription=nom

Le nom de l'abonnement pour configurer la réplication logique. Plusieurs abonnements peuvent être spécifiés en écrivant plusieurs options --subscription. Le nombre de noms d'abonnements doit correspondre au nombre de bases de données spécifiées, sinon une erreur sera signalée. L'ordre des options de nom d'abonnement multiples doit correspondre à l'ordre des options de base de données. Si cette option n'est pas spécifiée, un nom généré est attribué au nom de l'abonnement. Cette option ne peut pas être utilisée conjointement avec --all.

-V
--version

Affiche la version de pg_createsubscriber et quitte.

-?
--help

Affiche l'aide concernant les arguments de ligne de commande de pg_createsubscriber et quitte.

NOTES

Prérequis

Certains prérequis doivent être remplis pour que pg_createsubscriber puisse convertir le serveur cible en réplique logique. Si ceux-ci ne sont pas remplis, une erreur sera signalée. Les serveurs source et cible doivent avoir la même version majeure que pg_createsubscriber. Le répertoire de données cible donné doit avoir le même identifiant système que le répertoire de données source. L'utilisateur de base de données donné pour le répertoire de données cible doit avoir les privilèges nécessaires pour créer des abonnements et utiliser pg_replication_origin_advance().

Le serveur cible doit être utilisé comme réplique physique (standby). Le serveur cible doit avoir max_active_replication_origins et max_logical_replication_worker

s configuré à une valeur supérieure ou égale au nombre de bases de données spécifiées. Le serveur cible doit avoir max_worker_processes configuré à une valeur supérieure au nombre de bases de données spécifiées. Le serveur cible doit accepter les connexions locales. Si vous envisagez d'utiliser l'option --enable-two-phase, vous devrez également définir max_prepared_transactions de manière appropriée.

Le serveur source doit accepter les connexions du serveur cible. Le serveur source ne doit pas être en mode de récupération. Le serveur source doit avoir wal_level défini sur logical. Le serveur source doit avoir max_replication_slots configuré à une valeur supérieure ou égale au nombre de bases de données spécifiées plus les slots de réplication existants. Le serveur source doit avoir max_wal_senders configuré à une valeur supérieure ou égale au nombre de bases de données spécifiées et aux processus d'envoi WAL existants.

Avertissements

Si pg_createsubscriber échoue après la promotion du serveur cible, alors le répertoire de données n'est probablement pas dans un état récupérable. Dans un tel cas, il est recommandé de créer un nouveau serveur de secours.

pg_createsubscriber démarre généralement le serveur cible avec des paramètres de connexion différents pendant la transformation. Par conséquent, les connexions au serveur cible devraient échouer.

Étant donné que les commandes DDL ne sont pas répliquées par la réplication logique, évitez d'exécuter des commandes DDL qui modifient le schéma de la base de données pendant l'exécution de pg_createsubscriber. Si le serveur cible a déjà été converti en réplique logique, les commandes DDL pourraient ne pas être répliquées, ce qui pourrait provoquer une erreur.

Si pg_createsubscriber échoue pendant le traitement, les objets (publications, slots de réplication) créés sur le serveur source sont supprimés. La suppression peut échouer si le serveur cible ne parvient pas à se connecter au serveur source. Dans un tel cas, un message d'avertissement indiquera les objets restants. Si le serveur cible est en cours d'exécution, il sera arrêté.

Si la réplication utilise primary_slot_name, il sera supprimé du serveur source après la configuration de la réplication logique.

Si le serveur cible est une réplique synchrone, les commits de transaction sur le primaire pourraient attendre la réplication pendant l'exécution de pg_createsubscriber.

Sauf si l'option --enable-two-phase est spécifiée, pg_createsubscriber configure la réplication logique avec le commit en deux phases désactivé. Cela signifie que toutes les transactions préparées seront répliquées au moment de COMMIT PREPARED, sans préparation préalable. Une fois la configuration terminée, vous pouvez supprimer manuellement et recréer la ou les abonnements avec l'option two_phase activée.

pg_createsubscriber modifie l'identifiant système en utilisant pg_resetwal. Il évitera les situations dans lesquelles le serveur cible pourrait utiliser des fichiers WAL du serveur source. Si le serveur cible a une copie de secours, la réplication sera rompue et une nouvelle copie de secours devra être créée.

Des échecs de réplication peuvent survenir si les fichiers WAL requis sont manquants. Pour éviter cela, le serveur source doit définir max_slot_wal_keep_size sur -1 pour garantir que les fichiers WAL requis ne soient pas supprimés prématurément.

Comment cela fonctionne

L'idée de base est de disposer d'un point de départ de réplication depuis le serveur source et de configurer une réplication logique pour démarrer à partir de ce point :

1.Démarrez le serveur cible avec les options de ligne de commande spécifiées. Si le serveur cible est déjà en cours d'exécution, pg_createsubscriber se terminera avec une erreur.
2.Vérifiez si le serveur cible peut être converti. Quelques vérifications sont également effectuées sur le serveur source. Si l'une des prérequis n'est pas remplie, pg_createsubscriber se terminera avec une erreur.
3.Créez une publication et un slot de réplication pour chaque base de données spécifiée sur le serveur source. Chaque publication est créée en utilisant FOR ALL TABLES. Si l'option --publication n'est pas spécifiée, la publication suit le modèle de nom : “pg_createsubscriber_%u_%x” (paramètres : oid de la base de données, entier aléatoire). Si l'option --replication-slot n'est pas spécifiée, le slot de réplication suit le modèle de nom : “pg_createsubscriber_%u_%x” (paramètres : oid de la base de données, entier aléatoire). Ces slots de réplication seront utilisés par les abonnements dans une étape ultérieure. Le dernier LSN du slot de réplication est utilisé comme point d'arrêt dans le paramètre recovery_target_lsn et comme point de départ de réplication par les abonnements. Il garantit qu'aucune transaction ne sera perdue.
4.Écrivez les paramètres de récupération dans le répertoire de données cible et redémarrez le serveur cible. Il spécifie un LSN (recovery_target_lsn) de l'emplacement du journal d'écriture anticipée jusqu'où la récupération se poursuivra. Il spécifie également la promotion comme action que le serveur doit entreprendre une fois la cible de récupération atteinte. Des paramètres de récupération supplémentaires sont ajoutés pour éviter les comportements inattendus pendant le processus de récupération, tels que la fin de la récupération dès qu'un état cohérent est atteint (le WAL doit être appliqué jusqu'à l'emplacement de début de réplication) et plusieurs cibles de récupération pouvant entraîner un échec. Cette étape se termine une fois que le serveur sort du mode veille et accepte les transactions en lecture-écriture. Si l'option --recovery-timeout est définie, pg_createsubscriber se termine si la récupération ne se termine pas dans le nombre de secondes donné.
5.Créez un abonnement pour chaque base de données spécifiée sur le serveur cible. Si l'option --subscription n'est pas spécifiée, l'abonnement suit le modèle de nom : “pg_createsubscriber_%u_%x” (paramètres : oid de la base de données, entier aléatoire). Il ne copie pas les données existantes du serveur source. Il ne crée pas de slot de réplication. Au lieu de cela, il utilise le slot de réplication qui a été créé dans l'étape précédente. L'abonnement est créé mais il n'est pas encore activé. La raison est que la progression de la réplication doit être définie au point de départ de la réplication avant de démarrer la réplication.
6.Supprimez les publications sur le serveur cible qui ont été répliquées car elles ont été créées avant l'emplacement de début de réplication. Elles n'ont aucune utilité sur le souscripteur.
7.Définissez la progression de la réplication au point de départ de la réplication pour chaque abonnement. Lorsque le serveur cible démarre le processus de récupération, il rattrape le point de départ de la réplication. C'est le LSN exact à utiliser comme emplacement de réplication initial pour chaque abonnement. Le nom de l'origine de réplication est obtenu depuis la création de l'abonnement. Le nom de l'origine de réplication et le point de départ de la réplication sont utilisés dans pg_replication_origin_advance() pour configurer l'emplacement de réplication initial.
8.Activez l'abonnement pour chaque base de données spécifiée sur le serveur cible. L'abonnement commence à appliquer les transactions à partir du point de départ de la réplication.
9.Si le serveur de secours utilisait primary_slot_name, il n'a plus d'utilité et est donc supprimé.
10.Si le serveur de secours contient des slots de réplication de basculement (failover), ils ne peuvent plus être synchronisés et sont donc supprimés.
11.Mettez à jour l'identifiant système sur le serveur cible. pg_resetwal(1) est exécuté pour modifier l'identifiant système. Le serveur cible est arrêté, comme requis par pg_resetwal.

EXEMPLES

Pour créer une réplique logique pour les bases de données hr et finance à partir d'une réplique physique sur foo :

$ pg_createsubscriber -D /usr/local/pgsql/data -P "host=foo" -d hr -d finance
