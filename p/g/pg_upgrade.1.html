pg_upgrade(1)

Paquet: postgresql

Licences: PostgreSQL

PG_UPGRADE(1) Documentation PostgreSQL 18.1 PG_UPGRADE(1)

NOM

pg_upgrade — met à niveau une instance de serveur PostgreSQL

SYNTAXE

pg_upgrade -b ancien_repertoire_bin [-B nouveau_repertoire_bin] -d ancien_repertoire_config -D nouveau_repertoire_config [option...]

DESCRIPTION

pg_upgrade (anciennement appelé pg_migrator) permet de mettre à niveau les données stockées dans les fichiers de données PostgreSQL vers une version majeure PostgreSQL ultérieure sans avoir à effectuer de vidage/restauration des données, ce qui est généralement requis pour les mises à niveau de version majeure, par exemple, de 12.14 à 13.10 ou de 14.9 à 15.5. Il n'est pas nécessaire pour les mises à niveau de version mineure, par exemple, de 12.7 à 12.8 ou de 14.1 à 14.5.

Les versions majeures de PostgreSQL ajoutent régulièrement de nouvelles fonctionnalités qui modifient souvent la structure des tables systèmes, mais le format de stockage des données internes change rarement. pg_upgrade utilise ce fait pour effectuer des mises à niveau rapides en créant de nouvelles tables système et en réutilisant simplement les anciens fichiers de données utilisateur. Si une future version majeure modifie le format de stockage des données d'une manière qui rend le format de données ancien illisible, pg_upgrade ne sera pas utilisable pour de telles mises à niveau. (La communauté tentera d'éviter de telles situations.)

pg_upgrade fait de son mieux pour s'assurer que les anciens et les nouveaux clusters sont binaires compatibles, par exemple, en vérifiant les paramètres de compilation compatibles, y compris les binaires 32/64 bits. Il est important que les modules externes soient également binaires compatibles, bien que cela ne puisse pas être vérifié par pg_upgrade.

pg_upgrade prend en charge les mises à niveau de 9.2.X et versions ultérieures vers la version majeure actuelle de PostgreSQL, y compris les versions snapshot et bêta.


Attention

La mise à niveau d'un cluster entraîne l'exécution de code arbitraire choisi par les superutilisateurs sources. Assurez-vous que les superutilisateurs sources sont fiables avant la mise à niveau.

OPTIONS

pg_upgrade accepte les arguments de ligne de commande suivants :

-b repertoire_bin
--ancien-repertoire-bin=repertoire_bin

l'ancien répertoire des exécutables PostgreSQL ; variable d'environnement PGBINOLD

-B repertoire_bin
--nouveau-repertoire-bin=repertoire_bin

le nouveau répertoire des exécutables PostgreSQL ; par défaut, c'est le répertoire où réside pg_upgrade ; variable d'environnement PGBINNEW

-c
--verifier

vérifier uniquement les clusters, ne modifier aucune donnée

-d repertoire_config
--ancien-repertoire-donnees=repertoire_config

l'ancien répertoire de configuration du cluster de bases de données ; variable d'environnement PGDATAOLD

-D repertoire_config
--nouveau-repertoire-donnees=repertoire_config

le nouveau répertoire de configuration du cluster de bases de données ; variable d'environnement PGDATANEW

-j n_taches
--taches=n_taches

nombre de connexions et de processus/threads simultanés à utiliser

-k
--liens

utiliser des liens physiques au lieu de copier les fichiers vers le nouveau cluster

-N
--pas-de-synchro

Par défaut, pg_upgrade attend que tous les fichiers du cluster mis à niveau soient écrits en toute sécurité sur le disque. Cette option fait que pg_upgrade retourne sans attendre, ce qui est plus rapide, mais signifie qu'un crash ultérieur du système d'exploitation peut corrompre le répertoire de données. Généralement, cette option est utile pour les tests, mais ne doit pas être utilisée sur une installation de production.

-o options
--anciennes-options options

options à passer directement à la commande postgres ancienne ; plusieurs invocations d'option sont ajoutées

-O options
--nouvelles-options options

options à passer directement à la commande postgres nouvelle ; plusieurs invocations d'option sont ajoutées

-p port
--ancien-port=port

le numéro de port de l'ancien cluster ; variable d'environnement PGPORTOLD

-P port
--nouveau-port=port

le numéro de port du nouveau cluster ; variable d'environnement PGPORTNEW

-r
--conserver

conserver les fichiers SQL et journaux même après l'achèvement réussi

-s dir
--repertoire-sockets=dir

répertoire à utiliser pour les sockets postmaster pendant la mise à niveau ; par défaut, c'est le répertoire de travail actuel ; variable d'environnement PGSOCKETDIR

-U nom_utilisateur
--nom-utilisateur=nom_utilisateur

nom d'utilisateur d'installation du cluster ; variable d'environnement PGUSER

-v
--verbeux

activer la journalisation interne détaillée

-V
--version

afficher les informations de version, puis quitter

--cloner

Utiliser le clonage de fichiers efficace (également appelé “reflinks” sur certains systèmes) au lieu de copier les fichiers vers le nouveau cluster. Cela peut entraîner une copie quasi instantanée des fichiers de données, offrant les avantages de vitesse de -k/--liens tout en laissant l'ancien cluster intact.

Le clonage de fichiers n'est pris en charge que sur certains systèmes d'exploitation et systèmes de fichiers. S'il est sélectionné mais non pris en charge, l'exécution de pg_upgrade échouera. Actuellement, il est pris en charge sous Linux (noyau 4.5 ou ultérieur) avec Btrfs et XFS (sur les systèmes de fichiers créés avec le support reflink), et sous macOS avec APFS.

--copier

Copier les fichiers vers le nouveau cluster. C'est le comportement par défaut. (Voir également --liens, --cloner, --copier-range-fichier et --permuter.)

--copier-range-fichier

Utiliser l'appel système copy_file_range pour une copie efficace. Sur certains systèmes de fichiers, cela donne des résultats similaires à --cloner, partageant des blocs de disque physiques, tandis que sur d'autres, cela peut toujours copier des blocs, mais le faire via un chemin optimisé. Actuellement, il est pris en charge sous Linux et FreeBSD.

--pas-de-statistiques

Ne pas restaurer les statistiques de l'ancien cluster dans le nouveau cluster.

--definir-char-signe=option

Définir manuellement la signature de caractère par défaut des nouveaux clusters. Les valeurs possibles sont signed et unsigned.

Dans le langage C, la signature par défaut du type char (lorsqu'elle n'est pas explicitement spécifiée) varie selon les plateformes. Par exemple, char est signé par défaut sur les processeurs x86 mais non signé par défaut sur les processeurs ARM.

À partir de PostgreSQL 18, les clusters de bases de données conservent leur propre paramètre de signature de caractère par défaut, ce qui permet d'assurer un comportement cohérent sur les plateformes avec des signatures de caractère par défaut différentes. Par défaut, pg_upgrade conserve le paramètre de signature de caractère lors de la mise à niveau à partir d'un cluster existant. Cependant, lors de la mise à niveau depuis PostgreSQL 17 ou une version antérieure, pg_upgrade adopte la signature de caractère de la plateforme sur laquelle il a été construit.

Cette option vous permet de définir explicitement la signature de caractère par défaut pour le nouveau cluster, remplaçant toute valeur héritée. Il existe deux scénarios spécifiques où cette option est pertinente :

•Si vous prévoyez de migrer vers une plateforme différente après la mise à niveau, vous ne devez pas utiliser cette option. Le comportement par défaut est correct dans ce cas. Effectuez plutôt la mise à niveau sur la plateforme d'origine sans ce drapeau, puis migrez le cluster ensuite. C'est l'approche recommandée et la plus sûre.
•Si vous avez déjà migré le cluster vers une plateforme avec une signature de caractère différente (par exemple, d'un système basé sur x86 vers un système basé sur ARM), vous devez utiliser cette option pour spécifier la signature correspondant à la signature de caractère par défaut de la plateforme d'origine. De plus, il est essentiel de ne pas modifier les fichiers de données entre la migration des fichiers de données et l'exécution de pg_upgrade. pg_upgrade doit être la première opération qui démarre le cluster sur la nouvelle plateforme.

--permuter

Déplacer les répertoires de données de l'ancien cluster vers le nouveau cluster. Ensuite, remplacer les fichiers catalogue par ceux générés pour le nouveau cluster. Ce mode peut surpasser --liens, --cloner, --copier et --copier-range-fichier, en particulier sur les clusters comportant de nombreuses relations.

Cependant, ce mode crée de nombreux fichiers indésirables dans l'ancien cluster, ce qui peut prolonger l'étape de synchronisation des fichiers si --methode-synchro=syncfs est utilisé. Par conséquent, il est recommandé d'utiliser --methode-synchro=fsync avec --permuter.

De plus, une fois que l'étape de transfert de fichiers commence, l'ancien cluster sera modifié de manière destructive et ne pourra donc plus être démarré en toute sécurité. Voir l'étape 17 pour plus de détails.

--sync-method=méthode

Lorsqu'il est défini sur fsync, ce qui est le défaut, pg_upgrade ouvrira et synchronisera récursivement tous les fichiers du répertoire de données du cluster mis à niveau. La recherche de fichiers suivra les liens symboliques pour le répertoire WAL et chaque tablespace configuré.

Sous Linux, syncfs peut être utilisé à la place pour demander au système d'exploitation de synchroniser l'intégralité des systèmes de fichiers qui contiennent le répertoire de données du cluster mis à niveau, ses fichiers WAL et chaque tablespace. Voir recovery_init_sync_method pour des informations sur les mises en garde à prendre en compte lors de l'utilisation de syncfs.

Cette option n'a aucun effet lorsque --no-sync est utilisé.

-?
--help

afficher l'aide, puis quitter

UTILISATION

Voici les étapes pour effectuer une mise à niveau avec pg_upgrade :


Note

Les étapes pour la mise à niveau des clusters de réplication logique ne sont pas abordées ici ; reportez-vous à la section 29.13 pour plus de détails.

1.Déplacer éventuellement l'ancien cluster : Si vous utilisez un répertoire d'installation spécifique à la version, par exemple /opt/PostgreSQL/18, vous n'avez pas besoin de déplacer l'ancien cluster. Les installateurs graphiques utilisent tous des répertoires d'installation spécifiques à la version.

Si votre répertoire d'installation n'est pas spécifique à la version, par exemple /usr/local/pgsql, il est nécessaire de déplacer le répertoire d'installation PostgreSQL actuel afin qu'il n'interfère pas avec la nouvelle installation PostgreSQL. Une fois le serveur PostgreSQL actuel arrêté, il est sûr de renommer le répertoire d'installation PostgreSQL ; en supposant que l'ancien répertoire est /usr/local/pgsql, vous pouvez faire :

mv /usr/local/pgsql /usr/local/pgsql.old

pour renommer le répertoire.

2.Pour les installations à partir des sources, compiler la nouvelle version : Compiler la nouvelle source PostgreSQL avec des indicateurs configure compatibles avec l'ancien cluster. pg_upgrade vérifiera pg_controldata pour s'assurer que tous les paramètres sont compatibles avant de commencer la mise à niveau.
3.Installer les binaires PostgreSQL de la nouvelle version : Installer les binaires et les fichiers de support du nouveau serveur. pg_upgrade est inclus dans une installation par défaut.

Pour les installations à partir des sources, si vous souhaitez installer le nouveau serveur dans un emplacement personnalisé, utilisez la variable prefix :

make prefix=/usr/local/pgsql.new install
4.Initialiser le nouveau cluster PostgreSQL : Initialiser le nouveau cluster à l'aide de initdb. Là encore, utilisez des indicateurs initdb compatibles qui correspondent à l'ancien cluster. De nombreux installateurs pré-compilés effectuent cette étape automatiquement. Il n'est pas nécessaire de démarrer le nouveau cluster.
5.Installer les fichiers d'objets partagés d'extension : De nombreuses extensions et modules personnalisés, qu'ils proviennent de contrib ou d'une autre source, utilisent des fichiers d'objets partagés (ou DLL), par exemple, pgcrypto.so. Si l'ancien cluster utilisait ces fichiers, des fichiers d'objets partagés correspondant aux binaires du nouveau serveur doivent être installés dans le nouveau cluster, généralement via des commandes du système d'exploitation. Ne chargez pas les définitions de schéma, par exemple, CREATE EXTENSION pgcrypto, car elles seront dupliquées depuis l'ancien cluster. Si des mises à jour d'extension sont disponibles, pg_upgrade le signalera et créera un script qui pourra être exécuté plus tard pour les mettre à jour.
6.Copier les fichiers personnalisés de recherche en texte intégral : Copier tous les fichiers personnalisés de recherche en texte intégral (dictionnaire, synonymes, thésaurus, mots vides) de l'ancien vers le nouveau cluster.
7.Ajuster l'authentification : pg_upgrade se connectera aux anciens et nouveaux serveurs plusieurs fois, vous pourriez donc vouloir définir l'authentification sur peer dans pg_hba.conf ou utiliser un fichier ~/.pgpass (voir section 32.16).
8.Arrêter les deux serveurs : Assurez-vous que les deux serveurs de base de données sont arrêtés en utilisant, sur Unix, par exemple : 
pg_ctl -D /opt/PostgreSQL/12 stop
pg_ctl -D /opt/PostgreSQL/18 stop

ou sous Windows, en utilisant les noms de service appropriés :

NET STOP postgresql-12
NET STOP postgresql-18

Les serveurs de réplication en flux et de réexpédition de journaux doivent être en cours d'exécution pendant cet arrêt afin qu'ils reçoivent toutes les modifications.

9.Préparation pour la mise à niveau des serveurs esclaves : Si vous mettez à niveau des serveurs esclaves en utilisant les méthodes décrites à l'étape 11, vérifiez que les anciens serveurs esclaves sont à jour en exécutant pg_controldata sur les clusters primaires et esclaves anciens. Vérifiez que les valeurs de "Dernier emplacement de point de contrôle" correspondent dans tous les clusters. Assurez-vous également que wal_level n'est pas défini sur minimal dans le fichier postgresql.conf sur le nouveau cluster primaire.
10.Exécuter pg_upgrade : Exécutez toujours le binaire pg_upgrade du nouveau serveur, pas celui de l'ancien. pg_upgrade nécessite la spécification des répertoires de données et exécutables (bin) des anciens et nouveaux clusters. Vous pouvez également spécifier les valeurs d'utilisateur et de port, et si vous souhaitez que les fichiers de données soient liés, clonés ou échangés au lieu du comportement de copie par défaut.

Si vous utilisez le mode lien, la mise à niveau sera beaucoup plus rapide (pas de copie de fichiers) et utilisera moins d'espace disque, mais vous ne pourrez pas accéder à votre ancien cluster une fois que vous aurez démarré le nouveau cluster après la mise à niveau. Le mode lien nécessite également que les répertoires de données des anciens et nouveaux clusters soient sur le même système de fichiers. (Les tablespaces et pg_wal peuvent être sur des systèmes de fichiers différents.) Le mode clonage offre les mêmes avantages en termes de vitesse et d'espace disque, mais ne rend pas l'ancien cluster inutilisable une fois que le nouveau cluster est démarré. Le mode clonage nécessite également que les répertoires de données des anciens et nouveaux clusters soient sur le même système de fichiers. Ce mode n'est disponible que sur certains systèmes d'exploitation et systèmes de fichiers. Le mode échange peut être le plus rapide s'il y a de nombreuses relations, mais vous ne pourrez pas accéder à votre ancien cluster une fois que l'étape de transfert de fichiers commencera. Le mode échange nécessite également que les répertoires de données des anciens et nouveaux clusters soient sur le même système de fichiers.

Le réglage de --jobs à 2 ou plus permet à pg_upgrade de traiter plusieurs bases de données et tablespaces en parallèle. Un bon point de départ est le nombre de cœurs CPU de la machine. Cette option peut réduire substantiellement le temps de mise à niveau pour les serveurs multi-bases de données et multi-tablespaces.

Pour les utilisateurs Windows, vous devez être connecté en tant que compte administrateur, puis exécuter pg_upgrade avec des répertoires entre guillemets, par exemple :

pg_upgrade.exe
        --old-datadir "C:/Program Files/PostgreSQL/12/data"
        --new-datadir "C:/Program Files/PostgreSQL/18/data"
        --old-bindir "C:/Program Files/PostgreSQL/12/bin"
        --new-bindir "C:/Program Files/PostgreSQL/18/bin"

Une fois démarré, pg_upgrade vérifiera la compatibilité des deux clusters, puis effectuera la mise à niveau. Vous pouvez utiliser pg_upgrade --check pour effectuer uniquement les vérifications, même si l'ancien serveur est toujours en cours d'exécution. pg_upgrade --check décrira également tous les ajustements manuels que vous devrez apporter après la mise à niveau. Si vous comptez utiliser le mode lien, clone, copie-plage-de-fichiers ou échange, vous devriez utiliser l'option --link, --clone, --copy-file-range ou --swap avec --check pour activer les vérifications spécifiques au mode. pg_upgrade nécessite une permission d'écriture dans le répertoire courant.

Évidemment, personne ne devrait accéder aux clusters pendant la mise à niveau. pg_upgrade utilise par défaut des serveurs en cours d'exécution sur le port 50432 pour éviter les connexions clients involontaires. Vous pouvez utiliser le même numéro de port pour les deux clusters lors d'une mise à niveau car les anciens et nouveaux clusters ne seront pas en cours d'exécution en même temps. Cependant, lors de la vérification d'un ancien serveur en cours d'exécution, les anciens et nouveaux numéros de port doivent être différents.

Si une erreur se produit lors de la restauration du schéma de la base de données, pg_upgrade se terminera et vous devrez revenir à l'ancien cluster comme décrit à l'étape 17 ci-dessous. Pour réessayer pg_upgrade, vous devrez modifier l'ancien cluster afin que la restauration du schéma par pg_upgrade réussisse. Si le problème concerne un module contrib, vous devrez peut-être désinstaller le module contrib de l'ancien cluster et l'installer dans le nouveau cluster après la mise à niveau, en supposant que le module n'est pas utilisé pour stocker des données utilisateur.

11.Mise à niveau des serveurs de réplication en flux et de réexpédition de journaux : Si vous avez utilisé le mode lien et disposez de serveurs esclaves en réplication en flux (voir section 26.2.5) ou par réexpédition de journaux (voir section 26.2), vous pouvez suivre ces étapes pour les mettre à niveau rapidement. Vous n'exécuterez pas pg_upgrade sur les serveurs esclaves, mais plutôt rsync sur le primaire. Ne démarrez aucun serveur pour l'instant.

Si vous n'avez pas utilisé le mode lien, que vous n'avez pas ou ne voulez pas utiliser rsync, ou que vous souhaitez une solution plus simple, sautez les instructions de cette section et recréez simplement les serveurs esclaves une fois que pg_upgrade est terminé et que le nouveau primaire est en cours d'exécution.

1.Installer les binaires PostgreSQL de la nouvelle version sur les serveurs esclaves : Assurez-vous que les nouveaux binaires et les fichiers de support sont installés sur tous les serveurs esclaves.
2.Assurez-vous que les nouveaux répertoires de données des serveurs esclaves n'existent pas : Assurez-vous que les nouveaux répertoires de données des serveurs esclaves n'existent pas ou sont vides. Si initdb a été exécuté, supprimez les nouveaux répertoires de données des serveurs esclaves.
3.Installer les fichiers d'objets partagés d'extension : Installez les mêmes fichiers d'objets partagés d'extension sur les nouveaux esclaves que ceux que vous avez installés dans le nouveau cluster primaire.
4.Arrêter les serveurs esclaves : Si les serveurs esclaves sont toujours en cours d'exécution, arrêtez-les maintenant en utilisant les instructions ci-dessus.
5.Sauvegarder les fichiers de configuration : Sauvegardez tous les fichiers de configuration des anciens répertoires de configuration des esclaves que vous souhaitez conserver, par exemple, postgresql.conf (et tous les fichiers qu'il inclut), postgresql.auto.conf, pg_hba.conf, car ils seront écrasés ou supprimés à l'étape suivante.
6.Exécuter rsync : Lors de l'utilisation du mode lien, les serveurs esclaves peuvent être rapidement mis à niveau à l'aide de rsync. Pour ce faire, depuis un répertoire sur le serveur primaire qui se trouve au-dessus des répertoires de clusters de base de données anciens et nouveaux, exécutez ceci sur le primaire pour chaque serveur esclave : 
rsync --archive --delete --hard-links --size-only --no-inc-recursive ancien_cluster nouveau_cluster repertoire_distant

où ancien_cluster et nouveau_cluster sont relatifs au répertoire courant sur le primaire, et repertoire_distant est au-dessus des répertoires des anciens et nouveaux clusters sur l'esclave. La structure des répertoires sous les répertoires spécifiés sur le primaire et les esclaves doit correspondre. Consultez la page de manuel rsync pour plus de détails sur la spécification du répertoire distant, par exemple :

rsync --archive --delete --hard-links --size-only --no-inc-recursive /opt/PostgreSQL/12 \
      /opt/PostgreSQL/18 standby.example.com:/opt/PostgreSQL

Vous pouvez vérifier ce que la commande fera en utilisant l'option --dry-run de rsync. Bien que rsync doive être exécuté sur le primaire pour au moins un esclave, il est possible d'exécuter rsync sur un esclave mis à niveau pour mettre à niveau o

ther standbys, tant que le standby mis à niveau n'a pas été démarré.

Cela permet d'enregistrer les liens créés par le mode link de pg_upgrade qui connectent les fichiers des anciens et des nouveaux clusters sur le serveur maître. Il trouve ensuite les fichiers correspondants dans l'ancien cluster du standby et crée des liens pour ceux-ci dans le nouveau cluster du standby. Les fichiers qui n'ont pas été liés sur le maître sont copiés du maître vers le standby. (Ils sont généralement petits.) Cela permet des mises à niveau rapides des standbys. Malheureusement, rsync copie inutilement les fichiers associés aux tables temporaires et non journalisées car ces fichiers n'existent normalement pas sur les serveurs standbys.

Si vous avez des tablespaces, vous devrez exécuter une commande rsync similaire pour chaque répertoire de tablespace, par exemple :

rsync --archive --delete --hard-links --size-only --no-inc-recursive /vol1/pg_tblsp/PG_12_201909212 \
      /vol1/pg_tblsp/PG_18_202307071 standby.example.com:/vol1/pg_tblsp

Si vous avez déplacé pg_wal en dehors des répertoires de données, rsync doit également être exécuté sur ces répertoires.

7.Configurer les serveurs standbys en streaming replication et log-shipping : Configurez les serveurs pour le log-shipping. (Vous n'avez pas besoin d'exécuter pg_backup_start() et pg_backup_stop() ni de faire une sauvegarde du système de fichiers car les standbys sont toujours synchronisés avec le maître.) Si l'ancien maître est antérieur à la version 17.0, alors aucune slot sur le maître n'est copiée vers le nouveau standby, donc toutes les slots sur l'ancien standby doivent être recréées manuellement. Si l'ancien maître est de la version 17.0 ou ultérieure, alors seules les slots logiques sur le maître sont copiées vers le nouveau standby, mais les autres slots sur l'ancien standby ne sont pas copiées, donc elles doivent être recréées manuellement.
12.Restaurer pg_hba.conf : Si vous avez modifié pg_hba.conf, restaurez ses paramètres d'origine. Il peut également être nécessaire d'ajuster d'autres fichiers de configuration dans le nouveau cluster pour qu'ils correspondent à l'ancien cluster, par exemple, postgresql.conf (et tous les fichiers qu'il inclut), postgresql.auto.conf.
13.Démarrer le nouveau serveur : Le nouveau serveur peut maintenant être démarré en toute sécurité, puis tous les serveurs standbys mis à jour par rsync.
14.Traitement post-mise à niveau : Si un traitement post-mise à niveau est requis, pg_upgrade émettra des avertissements à la fin de son exécution. Il générera également des fichiers de script qui devront être exécutés par l'administrateur. Les fichiers de script se connecteront à chaque base de données nécessitant un traitement post-mise à niveau. Chaque script doit être exécuté en utilisant : 
psql --username=postgres --file=script.sql postgres

Les scripts peuvent être exécutés dans n'importe quel ordre et peuvent être supprimés une fois qu'ils ont été exécutés.


Attention
En général, il est dangereux d'accéder aux tables référencées dans les scripts de reconstruction avant que les scripts de reconstruction n'aient terminé leur exécution ; le faire pourrait donner des résultats incorrects ou de mauvaises performances. Les tables non référencées dans les scripts de reconstruction peuvent être accessibles immédiatement.
15.Statistiques : Sauf si l'option --no-statistics est spécifiée, pg_upgrade transférera la plupart des statistiques de l'optimiseur de l'ancien cluster vers le nouveau cluster. Cependant, certaines statistiques peuvent ne pas être transférées, comme celles créées explicitement avec CREATE STATISTICS (CREATE_STATISTICS(7)) ou les statistiques personnalisées ajoutées par une extension.

Étant donné que toutes les statistiques ne sont pas transférées par pg_upgrade, vous serez invité à exécuter des commandes pour régénérer ces informations à la fin de la mise à niveau. Vous pourriez avoir besoin de définir des paramètres de connexion pour qu'ils correspondent à votre nouveau cluster.

Tout d'abord, utilisez vacuumdb --all --analyze-in-stages --missing-stats-only pour générer rapidement des statistiques minimales de l'optimiseur pour les relations sans aucune. Ensuite, utilisez vacuumdb --all --analyze-only pour vous assurer que toutes les relations ont des statistiques cumulées mises à jour pour déclencher le vacuum et l'analyse. Pour les deux commandes, l'utilisation de --jobs peut accélérer le processus. Si vacuum_cost_delay est défini sur une valeur non nulle, cela peut être remplacé pour accélérer la génération des statistiques à l'aide de PGOPTIONS, par exemple, PGOPTIONS='-c vacuum_cost_delay=0' vacuumdb ....

16.Supprimer l'ancien cluster : Une fois que vous êtes satisfait de la mise à niveau, vous pouvez supprimer les répertoires de données de l'ancien cluster en exécutant le script mentionné lors de la fin de l'exécution de pg_upgrade. (La suppression automatique n'est pas possible si vous avez des tablespaces définis par l'utilisateur dans l'ancien répertoire de données.) Vous pouvez également supprimer les répertoires d'installation anciens (par exemple, bin, share).
17.Revenir à l'ancien cluster : Si, après avoir exécuté pg_upgrade, vous souhaitez revenir à l'ancien cluster, plusieurs options s'offrent à vous :
•Si l'option --check a été utilisée, l'ancien cluster n'a pas été modifié ; il peut être redémarré.
•Si ni --link ni --swap n'ont été utilisés, l'ancien cluster n'a pas été modifié ; il peut être redémarré.
•Si l'option --link a été utilisée, les fichiers de données peuvent être partagés entre l'ancien et le nouveau cluster :
•Si pg_upgrade s'est arrêté avant que la liaison ne commence, l'ancien cluster n'a pas été modifié ; il peut être redémarré.
•Si vous n'avez pas démarré le nouveau cluster, l'ancien cluster n'a pas été modifié, sauf que, lorsque la liaison a commencé, un suffixe .old a été ajouté à $PGDATA/global/pg_control. Pour réutiliser l'ancien cluster, supprimez le suffixe .old de $PGDATA/global/pg_control ; vous pouvez alors redémarrer l'ancien cluster.
•Si vous avez démarré le nouveau cluster, il a écrit dans des fichiers partagés et il n'est pas sûr d'utiliser l'ancien cluster. L'ancien cluster devra être restauré à partir d'une sauvegarde dans ce cas.
•Si l'option --swap a été utilisée, l'ancien cluster peut être modifié de manière destructive :
•Si pg_upgrade s'arrête avant d'indiquer que l'ancien cluster n'est plus sûr à démarrer, l'ancien cluster n'a pas été modifié ; il peut être redémarré.
•Si pg_upgrade a indiqué que l'ancien cluster n'est plus sûr à démarrer, l'ancien cluster a été modifié de manière destructive. L'ancien cluster devra être restauré à partir d'une sauvegarde dans ce cas.

NOTES

pg_upgrade crée divers fichiers de travail, tels que des dumps de schéma, stockés dans pg_upgrade_output.d dans le répertoire du nouveau cluster. Chaque exécution crée un nouveau sous-répertoire nommé avec un horodatage formaté selon la norme ISO 8601 (%Y%m%dT%H%M%S), où tous ses fichiers générés sont stockés. pg_upgrade_output.d et son contenu seront supprimés automatiquement si pg_upgrade se termine avec succès ; mais en cas de problème, les fichiers qu'il contient peuvent fournir des informations de débogage utiles.

pg_upgrade lance des postmasters de courte durée dans les répertoires de données anciens et nouveaux. Les fichiers de socket Unix temporaires pour la communication avec ces postmasters sont, par défaut, créés dans le répertoire de travail courant. Dans certaines situations, le nom de chemin du répertoire courant pourrait être trop long pour être un nom de socket valide. Dans ce cas, vous pouvez utiliser l'option -s pour placer les fichiers de socket dans un répertoire avec un nom de chemin plus court. Pour des raisons de sécurité, assurez-vous que ce répertoire n'est lisible ou inscriptible par aucun autre utilisateur. (Ce n'est pas pris en charge sous Windows.)

Tous les cas d'échec, de reconstruction et de réindexation seront signalés par pg_upgrade s'ils affectent votre installation ; des scripts post-mise à niveau pour reconstruire les tables et les index seront générés automatiquement. Si vous essayez d'automatiser la mise à niveau de nombreux clusters, vous devriez constater que les clusters avec des schémas de base de données identiques nécessitent les mêmes étapes post-mise à niveau pour toutes les mises à niveau de cluster ; ceci est dû au fait que les étapes post-mise à niveau sont basées sur les schémas de base de données, et non sur les données utilisateur.

Pour tester le déploiement, créez une copie seule du schéma de l'ancien cluster, insérez des données factices et mettez-la à niveau.

pg_upgrade ne prend pas en charge la mise à niveau des bases de données contenant des colonnes de table utilisant ces types de données système référençant des OID reg* :

regcollation
regconfig
regdictionary
regnamespace
regoper
regoperator
regproc
regprocedure
(regclass, regrole et regtype peuvent être mis à niveau.)

Si vous souhaitez utiliser le mode link et que vous ne souhaitez pas que votre ancien cluster soit modifié lors du démarrage du nouveau cluster, envisagez d'utiliser le mode clone. Si celui-ci n'est pas disponible, faites une copie de l'ancien cluster et mettez-la à niveau en mode link. Pour faire une copie valide de l'ancien cluster, utilisez rsync pour créer une copie sale de l'ancien cluster pendant que le serveur est en cours d'exécution, puis arrêtez l'ancien serveur et exécutez à nouveau rsync --checksum pour mettre à jour la copie avec les modifications afin de la rendre cohérente. (--checksum est nécessaire car rsync n'a qu'une granularité de modification de fichier d'une seconde.) Vous pourriez vouloir exclure certains fichiers, par exemple, postmaster.pid, comme documenté dans la section 25.3.4. Si votre système de fichiers prend en charge les instantanés de système de fichiers ou les copies de fichiers copy-on-write, vous pouvez l'utiliser pour faire une sauvegarde de l'ancien cluster et des tablespaces, bien que l'instantané et les copies doivent être créés simultanément ou pendant que le serveur de base de données est arrêté.
