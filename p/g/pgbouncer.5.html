NOM

pgbouncer.ini - fichier de configuration de pgbouncer

DESCRIPTION

Le fichier de configuration est au format “ini”. Les noms de section sont entre “[" et "]”. Les lignes commençant par “;” ou “#” sont considérées comme des commentaires et ignorées. Les caractères “;” et “#” ne sont pas reconnus comme spéciaux lorsqu'ils apparaissent plus loin dans la ligne.

RÈGLEMENTS GÉNÉRAUX

logfile

Spécifie le fichier journal. Pour la démonisation (-d), soit celui-ci, soit syslog doit être configuré.

Le fichier journal reste ouvert, donc après rotation, un kill -HUP ou sur console RELOAD; devrait être effectué. Sous Windows, le service doit être arrêté et redémarré.

Notez que la définition de logfile n'arrête pas en soi la journalisation vers stderr. Utilisez l'option en ligne de commande -q ou -d pour cela.

Par défaut : non défini

pidfile

Spécifie le fichier PID. Sans pidfile défini, la démonisation (-d) n'est pas autorisée.

Par défaut : non défini

listen_addr

Spécifie une liste (séparée par des virgules) d'adresses sur lesquelles écouter les connexions TCP. Vous pouvez également utiliser * signifiant “écouter sur toutes les adresses”. Lorsque non défini, seules les connexions par socket Unix sont acceptées.

Les adresses peuvent être spécifiées numériquement (IPv4/IPv6) ou par nom.

Par défaut : non défini

listen_port

Quel port écouter. S'applique aux connexions TCP et aux sockets Unix.

Par défaut : 6432

unix_socket_dir

Spécifie l'emplacement des sockets Unix. S'applique à la fois au socket d'écoute et aux connexions serveur. Si défini sur une chaîne vide, les sockets Unix sont désactivés. Une valeur commençant par @ spécifie qu'un socket Unix dans l'espace de noms abstrait doit être créé (actuellement pris en charge sous Linux et Windows).

Pour que le redémarrage en ligne (-R) fonctionne, un socket Unix doit être configuré, et il doit être dans l'espace de noms du système de fichiers.

Par défaut : /tmp (vide sous Windows)

unix_socket_mode

Mode de fichier pour le socket Unix. Ignoré pour les sockets dans l'espace de noms abstrait. Non pris en charge sous Windows.

Par défaut : 0777

unix_socket_group

Nom du groupe à utiliser pour le socket Unix. Ignoré pour les sockets dans l'espace de noms abstrait. Non pris en charge sous Windows.

Par défaut : non défini

user

Si défini, spécifie l'utilisateur Unix vers lequel changer après le démarrage. Ne fonctionne que si PgBouncer est démarré en tant que root ou si il s'exécute déjà en tant qu'utilisateur donné. Non pris en charge sous Windows.

Par défaut : non défini

pool_mode

Spécifie quand une connexion serveur peut être réutilisée par d'autres clients.

session
Le serveur est renvoyé au pool après la déconnexion du client. Par défaut.
transaction
Le serveur est renvoyé au pool après la fin de la transaction.
statement
Le serveur est renvoyé au pool après la fin de la requête. Les transactions couvrant plusieurs instructions sont interdites dans ce mode.

max_client_conn

Nombre maximum de connexions client autorisées.

Lorsque ce paramètre est augmenté, les limites de descripteurs de fichier dans le système d'exploitation pourraient également devoir être augmentées. Notez que le nombre de descripteurs de fichier potentiellement utilisés est supérieur à max_client_conn. Si chaque utilisateur se connecte sous son propre nom d'utilisateur au serveur, le maximum théorique utilisé est :

max_client_conn + (max pool_size * total databases * total users)

Si un utilisateur de base de données est spécifié dans la chaîne de connexion (tous les utilisateurs se connectent sous le même nom d'utilisateur), le maximum théorique est :

max_client_conn + (max pool_size * total databases)

Le maximum théorique ne devrait jamais être atteint, sauf si quelqu'un crée délibérément une charge spéciale pour cela. Néanmoins, cela signifie que vous devriez définir le nombre de descripteurs de fichier à un nombre raisonnablement élevé.

Recherchez ulimit dans la page de manuel de votre shell préféré. Note : ulimit ne s'applique pas dans un environnement Windows.

Par défaut : 100

default_pool_size

Nombre de connexions serveur à autoriser par paire utilisateur/base de données. Peut être remplacé dans la configuration par base de données.

Par défaut : 20

min_pool_size

Ajouter des connexions serveur supplémentaires au pool si en dessous de ce nombre. Améliore le comportement lorsque la charge normale revient soudainement après une période d'inactivité totale. La valeur est effectivement limitée à la taille du pool.

Uniquement appliqué aux pools pour lesquels au moins une des conditions suivantes est vraie :

•
l'entrée dans la section [database] pour le pool a une valeur définie pour la clé utilisateur (également appelé utilisateur forcé)
•
il y a au moins un client connecté au pool

Par défaut : 0 (désactivé)

reserve_pool_size

Combien de connexions supplémentaires autoriser à un pool (voir reserve_pool_timeout). 0 désactive.

Par défaut : 0 (désactivé)

reserve_pool_timeout

Si un client n'a pas été servi pendant ce temps, utiliser des connexions supplémentaires du pool de réserve. 0 désactive. [secondes]

Par défaut : 5.0

max_db_connections

Ne pas autoriser plus de connexions serveur par base de données (quel que soit l'utilisateur). Ceci considère la base de données PgBouncer à laquelle le client s'est connecté, pas la base de données PostgreSQL de la connexion sortante.

Ceci peut également être défini par base de données dans la section [databases].

Notez que lorsque vous atteignez la limite, fermer une connexion client à un pool ne permettra pas immédiatement d'établir une connexion serveur pour un autre pool, car la connexion serveur pour le premier pool est toujours ouverte. Une fois la connexion serveur fermée (en raison d'un délai d'inactivité), une nouvelle connexion serveur sera immédiatement ouverte pour le pool en attente.

Par défaut : 0 (illimité)

max_user_connections

Ne pas autoriser plus de connexions serveur par utilisateur (quelle que soit la base de données). Ceci considère l'utilisateur PgBouncer associé à un pool, qui est soit l'utilisateur spécifié pour la connexion serveur, soit, en son absence, l'utilisateur sous lequel le client s'est connecté.

Ceci peut également être défini par utilisateur dans la section [users].

Notez que lorsque vous atteignez la limite, fermer une connexion client à un pool ne permettra pas immédiatement d'établir une connexion serveur pour un autre pool, car la connexion serveur pour le premier pool est toujours ouverte. Une fois la connexion serveur fermée (en raison d'un délai d'inactivité), une nouvelle connexion serveur sera immédiatement ouverte pour le pool en attente.

Par défaut : 0 (illimité)

server_round_robin

Défaut : 0

track_extra_parameters

Par défaut, PgBouncer suit les paramètres client_encoding, datestyle, timezone, standard_conforming_strings et application_name par client. Pour permettre le suivi d'autres paramètres, ils peuvent être spécifiés ici, afin que PgBouncer sache qu'ils doivent être conservés dans le cache des variables client et restaurés sur le serveur chaque fois que le client devient actif.

Si vous devez spécifier plusieurs valeurs, utilisez une liste séparée par des virgules (par exemple, default_transaction_readonly, IntervalStyle)

Note : La plupart des paramètres ne peuvent pas être suivis de cette manière. Les seuls paramètres qui peuvent être suivis sont ceux que Postgres rapporte au client. Postgres a une liste officielle des paramètres qu'il rapporte au client (https://www.postgresql.org/docs/15/protocol-flow.html#PROTOCOL-ASYNC). Les extensions Postgres peuvent cependant modifier cette liste, elles peuvent elles-mêmes ajouter des paramètres qu'elles rapportent, et elles peuvent commencer à rapporter des paramètres déjà existants que Postgres ne rapporte pas. Notamment, Citus 12.0+ amène Postgres à rapporter également search_path.

Le protocole Postgres permet de spécifier les paramètres, soit directement comme paramètre dans le paquet de démarrage, soit dans le paquet de démarrage des options (https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-OPTIONS). Les paramètres spécifiés par ces deux méthodes sont pris en charge par track_extra_parameters. Cependant, il n'est pas possible d'inclure les options elles-mêmes dans track_extra_parameters, uniquement les paramètres contenus dans options.

Défaut : IntervalStyle

ignore_startup_parameters

Par défaut, PgBouncer n'autorise que les paramètres qu'il peut suivre dans les paquets de démarrage : client_encoding, datestyle, timezone et standard_conforming_strings. Tous les autres paramètres provoqueront une erreur. Pour autoriser d'autres paramètres, ils peuvent être spécifiés ici, afin que PgBouncer sache qu'ils sont gérés par l'administrateur et qu'il puisse les ignorer.

Si vous devez spécifier plusieurs valeurs, utilisez une liste séparée par des virgules (par exemple, options,extra_float_digits)

Le protocole Postgres permet de spécifier les paramètres, soit directement comme paramètre dans le paquet de démarrage, soit dans le paquet de démarrage des options (https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-OPTIONS). Les paramètres spécifiés par ces deux méthodes sont pris en charge par ignore_startup_parameters. Il est même possible d'inclure les options elles-mêmes dans track_extra_parameters, ce qui a pour effet d'ignorer tous les paramètres inconnus contenus dans options.

Défaut : vide

peer_id

L'identifiant de pair utilisé pour identifier ce processus PgBouncer dans un groupe de processus PgBouncer qui sont jumelés. La valeur de peer_id doit être unique au sein d'un groupe de processus PgBouncer jumelés. Lorsqu'il est réglé sur 0, le jumelage de pgbouncer est désactivé. Voir la documentation de la section [peers] pour plus d'informations. La valeur maximale utilisable pour peer_id est 16383.

Défaut : 0

disable_pqexec

Désactive le protocole Simple Query (PQexec). Contrairement au protocole Extended Query, Simple Query autorise plusieurs requêtes dans un seul paquet, ce qui permet certaines classes d'attaques par injection SQL. Le désactiver peut améliorer la sécurité. Évidemment, cela signifie que seuls les clients qui utilisent exclusivement le protocole Extended Query continueront à fonctionner.

Défaut : 0

application_name_add_host

Ajoute l'adresse IP et le port de l'hôte client au paramètre application_name défini au début de la connexion. Cela aide à identifier la source des mauvaises requêtes, etc. Cette logique ne s'applique qu'au début d'une connexion. Si application_name est modifié ultérieurement avec SET, PgBouncer ne le modifie pas à nouveau.

Défaut : 0

conffile

Affiche l'emplacement du fichier de configuration actuel. Le modifier fera en sorte que PgBouncer utilise un autre fichier de configuration pour le prochain RELOAD / SIGHUP.

Défaut : fichier fourni en ligne de commande

service_name

Utilisé lors de l'enregistrement d'un service sous win32.

Défaut : pgbouncer

job_name

Alias pour service_name.

stats_period

Définit la fréquence de mise à jour des moyennes affichées dans les diverses commandes SHOW et la fréquence d'écriture des statistiques agrégées dans le journal (mais voir log_stats). [secondes]

Défaut : 60

max_prepared_statements

Lorsque cette valeur est définie sur une valeur non nulle, PgBouncer suit les commandes liées aux instructions préparées nommées au niveau du protocole envoyées par le client en mode transaction et pool d'instructions. PgBouncer s'assure que toute instruction préparée par un client est disponible sur la connexion serveur sous-jacente. Même si l'instruction a été initialement préparée sur une autre connexion serveur.

PgBouncer examine en interne toutes les requêtes envoyées en tant que instruction préparée par les clients et attribue à chaque chaîne de requête unique un nom interne au format PGBOUNCER_{unique_id}. Si la même chaîne de requête est préparée plusieurs fois (potentiellement par différents clients), alors ces requêtes partagent le même nom interne. PgBouncer ne prépare l'instruction sur le serveur PostgreSQL réel qu'en utilisant le nom interne (donc pas le nom fourni par le client). PgBouncer conserve une trace du nom que le client a donné à chaque instruction préparée. Il réécrit ensuite chaque commande qui utilise une instruction préparée en remplaçant le nom côté client par le nom interne (par exemple, en remplaçant my_prepared_stamenent par PGBOUNCER_123) avant de transmettre cette commande au serveur. Plus important encore, si l'instruction préparée que le client souhaite exécuter n'est pas encore préparée sur le serveur (par exemple, parce qu'un autre serveur est maintenant attribué au client que lorsqu'il a préparé l'instruction), alors PgBouncer prépare transparenmment l'instruction avant de l'exécuter.

Note : Ce suivi et cette réécriture des commandes d'instructions préparées ne fonctionnent pas pour les commandes d'instructions préparées au niveau SQL, donc PREPARE, EXECUTE et DEALLOCATE sont transmis directement à Postgres. L'exception à cette règle concerne les commandes DEALLOCATE ALL et DISCARD ALL, celles-ci fonctionnent comme prévu et videront les instructions préparées que PgBouncer a suivies pour le client qui envoie cette commande.

La valeur réelle de ce paramètre contrôle le nombre d'instructions préparées maintenues actives dans un cache LRU sur une seule connexion serveur. Lorsque le paramètre est défini sur 0, la prise en charge des instructions préparées pour les modes transaction et pool d'instructions est désactivée. Pour obtenir les meilleures performances, vous devriez essayer de vous assurer que ce paramètre est supérieur au nombre d'instructions préparées couramment utilisées dans votre application. Gardez à l'esprit que plus cette valeur est élevée, plus l'empreinte mémoire de chaque connexion PgBouncer sera importante sur votre serveur PostgreSQL, car il gardera plus de requêtes préparées sur ces connexions. Cela augmente également l'empreinte mémoire de PgBouncer lui-même, car il doit maintenant suivre les chaînes de requêtes.

Cependant, l'impact sur la mémoire de PgBouncer n'est pas si important : - Chaque requête unique est stockée une seule fois dans un cache de requêtes global. - Chaque connexion client conserve un tampon qu'elle utilise pour réécrire les paquets. Sa taille est au maximum 4 fois celle de pkt_buf. Cette limite n'est cependant souvent pas atteinte, elle ne se produit que lorsque les requêtes dans vos instructions préparées sont entre 2 et 4 fois la taille de pkt_buf.

Ainsi, si l'on considère le scénario suivant à titre d'exemple : - Il y a 1000 clients actifs - Les clients préparent 200 requêtes uniques - La taille moyenne d'une requête est de 5 Ko - Le paramètre pkt_buf est réglé sur la valeur par défaut de 4096 (4 Ko)

Alors PgBouncer a besoin au maximum de la quantité de mémoire suivante pour gérer ces instructions préparées :

200 x 5 Ko + 1000 x 4 x 4 Ko = ~17 Mo de mémoire.

Le suivi des instructions préparées a non seulement un coût en mémoire, mais aussi une augmentation de l'utilisation du CPU, car PgBouncer doit inspecter et réécrire les requêtes. Plusieurs instances de PgBouncer peuvent écouter sur le même port pour utiliser plus d'un cœur pour le traitement, voir la documentation de l'option so_reuseport pour plus de détails.

Mais bien sûr, il y a aussi des avantages en termes de performances pour les instructions préparées. Tout comme lors de la connexion directe à PostgreSQL, en préparant une requête qui est exécutée de nombreuses fois, cela réduit la quantité totale d'analyse et de planification qui doit être effectuée. La manière dont PgBouncer suit les instructions préparées est particulièrement bénéfique pour les performances lorsque plusieurs clients préparent les mêmes requêtes. Parce que les connexions client réutilisent automatiquement une instruction préparée sur une connexion serveur même si elle a été préparée par un autre client. Par exemple, si vous avez une pool_size de 20 et que vous avez 100 clients qui préparent tous exactement la même requête, alors la requête est préparée (et donc analysée) seulement 20 fois sur le serveur PostgreSQL.

La réutilisation des instructions préparées a un inconvénient. Si les types de retour ou d'arguments d'une instruction préparée changent entre les exécutions, PostgreSQL génère actuellement une erreur telle que :

ERREUR : le plan mis en cache ne doit pas changer le type de résultat

Vous pouvez éviter de telles erreurs en évitant que plusieurs clients n'utilisent exactement la même chaîne de requête dans une instruction préparée, tout en s'attendant à des types d'arguments ou de résultats différents. L'une des façons les plus courantes de rencontrer ce problème est lors d'une migration DDL où vous ajoutez une nouvelle colonne ou modifiez le type d'une colonne sur une table existante. Dans ces cas, vous pouvez exécuter RECONNECT sur la console d'administration PgBouncer après avoir effectué la migration pour forcer une re-préparation de la requête et faire disparaître l'erreur.

Défaut : 0

PARAMÈTRES D'AUTHENTIFICATION

PgBouncer gère sa propre authentification client et possède sa propre base de données d'utilisateurs. Ces paramètres contrôlent cela.

auth_type

Comment authentifier les utilisateurs.

cert
Le client doit se connecter via une connexion TLS avec un certificat client valide. Le nom d'utilisateur est ensuite extrait du champ CommonName du certificat.
md5
Utilise une vérification de mot de passe basée sur MD5. C'est la méthode d'authentification par défaut. Le fichier auth_file peut contenir des mots de passe chiffrés MD5 et en texte clair. Si md5 est configuré et qu'un utilisateur a un secret SCRAM, l'authentification SCRAM est utilisée automatiquement à la place.
scram-sha-256
Utilise une vérification de mot de passe avec SCRAM-SHA-256. Le fichier auth_file doit contenir des secrets SCRAM ou des mots de passe en texte clair.
plain
Le mot de passe en clair est envoyé sur le réseau. Obsolète.
trust
Aucune authentification n'est effectuée. Le nom d'utilisateur doit toujours exister dans auth_file.
any
Comme la méthode trust, mais le nom d'utilisateur fourni est ignoré. Nécessite que toutes les bases de données soient configurées pour se connecter en tant qu'utilisateur spécifique. De plus, la base de données console permet à n'importe quel utilisateur de se connecter en tant qu'administrateur.
hba
Le type d'authentification réel est chargé depuis auth_hba_file. Cela permet des méthodes d'authentification différentes pour différents chemins d'accès, par exemple : les connexions via socket Unix utilisent la méthode d'authentification peer, les connexions via TCP doivent utiliser TLS.
pam
PAM est utilisé pour authentifier les utilisateurs, auth_file est ignoré. Cette méthode n'est pas compatible avec les bases de données utilisant l'option auth_user. Le nom du service rapporté à PAM est « pgouncer ». pam n'est pas pris en charge dans le fichier de configuration HBA.

auth_hba_file

Fichier de configuration HBA à utiliser lorsque auth_type est hba.

Par défaut : non défini

auth_file

Le nom du fichier à partir duquel charger les noms d'utilisateur et les mots de passe. Voir la section Format du fichier d'authentification ci-dessous pour plus de détails.

La plupart des types d'authentification (voir ci-dessus) nécessitent que auth_file ou auth_user soit défini ; sinon, aucun utilisateur ne serait défini.

Par défaut : non défini

auth_user

Si auth_user est défini, tout utilisateur non spécifié dans auth_file sera interrogé via la requête auth_query de pg_shadow dans la base de données, en utilisant auth_user. Le mot de passe de auth_user sera pris dans auth_file. (Si auth_user ne nécessite pas de mot de passe, il n'a pas besoin d'être défini dans auth_file.)

L'accès direct à pg_shadow nécessite des droits d'administrateur. Il est préférable d'utiliser un non-superutilisateur qui appelle une fonction SECURITY DEFINER à la place.

Par défaut : non défini

auth_query

Requête pour charger le mot de passe de l'utilisateur depuis la base de données.

L'accès direct à pg_shadow nécessite des droits d'administrateur. Il est préférable d'utiliser un non-superutilisateur qui appelle une fonction SECURITY DEFINER à la place.

Notez que la requête est exécutée dans la base de données cible. Donc, si une fonction est utilisée, elle doit être installée dans chaque base de données.

Par défaut : SELECT usename, passwd FROM pg_shadow WHERE usename=$1

auth_dbname

Nom de la base de données dans la section [database] à utiliser à des fins d'authentification. Cette option peut être globale ou remplacée dans la chaîne de connexion si ce paramètre est spécifié.

VÉRIFICATIONS DE SAINSSE CONNEXION, TEMPS MORTS

server_reset_query

Requête envoyée au serveur lors de la libération de la connexion, avant de la rendre disponible à d'autres clients. À ce moment, aucune transaction n'est en cours, donc la valeur ne doit pas inclure ABORT ou ROLLBACK.

La requête est censée nettoyer toutes les modifications apportées à la session de la base de données afin que le client suivant obtienne la connexion dans un état bien défini. La valeur par défaut est DISCARD ALL, qui nettoie tout, mais laisse au client suivant aucun état pré-mis en cache. Cela peut être allégé, par exemple, DEALLOCATE ALL pour supprimer uniquement les instructions préparées, si l'application ne plante pas lorsque certains états sont conservés.

Lorsque le pooling de transactions est utilisé, server_reset_query n'est pas utilisé, car dans ce mode, les clients ne doivent utiliser aucune fonctionnalité basée sur la session, puisque chaque transaction se retrouve dans une connexion différente et obtient donc un état de session différent.

Par défaut : DISCARD ALL

server_reset_query_always

Indique si server_reset_query doit être exécuté dans tous les modes de pooling. Lorsque ce paramètre est désactivé (par défaut), server_reset_query ne sera exécuté que dans les pools en mode session-pooling. Les connexions en mode transaction-pooling n'ont normalement pas besoin de requête de réinitialisation.

Ce paramètre sert à contourner des configurations défectueuses qui exécutent des applications utilisant des fonctionnalités de session via un PgBouncer en transaction-pooling. Il transforme des pannes non déterministes en pannes déterministes : les clients perdent toujours leur état après chaque transaction.

Par défaut : 0

server_check_delay

Combien de temps garder les connexions libérées disponibles pour une réutilisation immédiate, sans exécuter server_check_query dessus. Si 0, la vérification est toujours exécutée.

Par défaut : 30.0

server_check_query

Requête simple sans effet pour vérifier si la connexion serveur est vivante.

Si la chaîne est vide, la vérification de cohérence est désactivée.

Par défaut : select 1

server_fast_close

Déconnecte un serveur en mode session pooling immédiatement ou après la fin de la transaction en cours s'il est en mode « close_needed » (défini par RECONNECT, RELOAD qui modifie les paramètres de connexion, ou changement DNS), plutôt que d'attendre la fin de la session. En mode statement ou transaction pooling, cela n'a aucun effet car c'est le comportement par défaut.

Si, en raison de ce paramètre, une connexion serveur est fermée avant la fin de la session client, la connexion client est également fermée. Cela garantit que le client constate que la session a été interrompue.

Ce paramètre permet aux changements de configuration de connexion de prendre effet plus rapidement si le pooling de session et les sessions de longue durée sont utilisés. Le revers de la médaille est que les sessions client peuvent être interrompues par un changement de configuration, de sorte que les applications clientes auront besoin d'une logique pour se reconnecter et rétablir l'état de la session. Mais notez que aucune transaction ne sera perdue, car les transactions en cours ne sont pas interrompues, seulement les sessions inactives.

Par défaut : 0

Pour plus de détails, consultez la documentation de l'option de configuration `peer_id` et de la section de configuration `peers`. SECTION [DATABASES]

La section [databases] définit les noms des bases de données auxquelles les clients de PgBouncer peuvent se connecter et spécifie où ces connexions seront acheminées. La section contient des lignes clé=valeur comme

dbname = chaîne de connexion

où la clé sera prise comme nom de base de données et la valeur comme chaîne de connexion, composée de paires clé=valeur de paramètres de connexion, décrites ci-dessous (similaire à libpq, mais libpq n'est pas réellement utilisé et l'ensemble des fonctionnalités disponibles est différent). Exemple :

foodb = host=host1.example.com port=5432
bardb = host=localhost dbname=bazdb

Le nom de la base de données peut contenir les caractères _0-9A-Za-z sans guillemets. Les noms contenant d'autres caractères doivent être mis entre guillemets avec des guillemets doubles standards pour les identifiants SQL, avec "" pour une instance unique de guillemets doubles.

Le nom de la base de données « pgbouncer » est réservé à la console d'administration et ne peut pas être utilisé comme clé ici.

« * » agit comme une base de données de secours : si le nom exact n'existe pas, sa valeur est prise comme chaîne de connexion pour la base de données demandée. Par exemple, s'il existe une entrée (et aucune autre entrée prédominante)

* = host=foo

alors une connexion à PgBouncer spécifiant une base de données « bar » se comportera effectivement comme si une entrée

bar = host=foo dbname=bar

existait (tirant parti du défaut pour `dbname` étant le nom de la base de données côté client ; voir ci-dessous).

Ces entrées de base de données automatiquement créées sont nettoyées si elles restent inactives plus longtemps que le temps spécifié par le paramètre `autodb_idle_timeout`.

dbname

Nom de la base de données de destination.

Défaut: identique au nom de la base de données côté client

host

Nom d'hôte ou adresse IP à laquelle se connecter. Les noms d'hôtes sont résolus au moment de la connexion, le résultat est mis en cache par `dns_max_ttl`. Lorsqu'une résolution de nom d'hôte change, les connexions serveur existantes sont automatiquement fermées lorsqu'elles sont libérées (conformément au mode de pooling), et les nouvelles connexions serveur utilisent immédiatement la nouvelle résolution. Si DNS renvoie plusieurs résultats, ils sont utilisés de manière aléatoire. Si la valeur commence par /, alors un socket Unix dans l'espace de noms du système de fichiers est utilisé. Si la valeur commence par @, alors un socket Unix dans l'espace de noms abstrait est utilisé. Une liste de noms d'hôtes ou d'adresses séparés par des virgules peut être spécifiée. Dans ce cas, les connexions sont établies de manière aléatoire. (Si une liste d'hôtes contient des noms d'hôtes qui se résolvent à leur tour via DNS en plusieurs adresses, les systèmes aléatoires fonctionnent indépendamment. Il s'agit d'une dépendance d'implémentation susceptible de changer.) Notez que dans une liste, tous les hôtes doivent être disponibles

à tout moment : Il n'existe aucun mécanisme pour sauter les hôtes inaccessibles ou pour sélectionner uniquement les hôtes disponibles dans une liste ou similaire. (Ceci est différent de ce que signifie une liste d'hôtes dans libpq.) Notez également que cela n'affecte que la manière dont les destinations de nouvelles connexions sont choisies. Voir également le paramètre server_round_robin pour la manière dont les clients sont attribués à des connexions serveur déjà établies.

SECTION [PAIRS]

La section [peers] définit les pairs auxquels PgBouncer peut transférer les demandes d'annulation et où ces demandes d'annulation seront acheminées.

Les processus PgBouncer peuvent être mis en miroir ensemble dans un groupe en définissant une valeur peer_id et une section [peers] dans les configurations de tous les processus PgBouncer. Ces processus PgBouncer peuvent alors transférer les demandes d'annulation au processus dont elles proviennent. Ceci est nécessaire pour que les annulations fonctionnent lorsque plusieurs processus PgBouncer (éventuellement sur des serveurs différents) sont derrière le même répartiteur de charge TCP. Les demandes d'annulation sont envoyées via des connexions TCP différentes de celles de la requête qu'elles annulent, de sorte qu'un répartiteur de charge TCP puisse envoyer la connexion de demande d'annulation à un processus différent de celui auquel elle était destinée. En les jumelant, ces demandes d'annulation finissent par atteindre le bon processus. Une explication plus approfondie est fournie dans cet enregistrement d'une conférence (https://www.youtube.com/watch?v=M585FfbboNA).

La section contient des lignes clé=valeur comme

peer_id = chaîne de connexion

Où la clé sera prise comme un peer_id et la valeur comme une chaîne de connexion, composée de paires clé=valeur de paramètres de connexion, décrits ci-dessous (similaire à libpq, mais le libpq réel n'est pas utilisé et l'ensemble des fonctionnalités disponibles est différent). Exemple :

1 = host=host1.example.com
2 = host=/tmp/pgbouncer-2  port=5555

Note 1 : Pour que le jumelage fonctionne, le peer_id de chaque processus PgBouncer du groupe doit être unique au sein du groupe jumelé. Et la section [peers] doit contenir des entrées pour chacun de ces peer_ids. Un exemple peut être trouvé dans la section exemples de cette documentation. Il est autorisé, mais pas nécessaire, que la section [peers] contienne le peer_id du PgBouncer pour lequel la configuration est destinée. Une telle entrée sera ignorée, mais elle est autorisée pour faciliter la gestion de la configuration. Car elle permet d'utiliser exactement la même section [peers] pour plusieurs configurations.

Note 2 : Le jumelage inter-versions est pris en charge tant que tous les pairs sont du même côté de la frontière de la version v1.21.0. Dans la version v1.21.0, des changements incompatibles ont été apportés à la manière dont nous encodons les jetons d'annulation, les rendant incompatibles avec ceux créés par les versions antérieures.

host

Nom d'hôte ou adresse IP pour se connecter. Les noms d'hôte sont résolus au moment de la connexion, le résultat est mis en cache par rapport au paramètre dns_max_ttl. Si DNS renvoie plusieurs résultats, ils sont utilisés de manière circulaire. Mais en général, il n'est pas recommandé d'utiliser un nom d'hôte qui résout en plusieurs IPs, car la demande d'annulation pourrait toujours être transférée au mauvais nœud et devrait être à nouveau transférée (ce qui n'est autorisé que jusqu'à trois fois).

Si la valeur commence par /, alors un socket Unix dans l'espace de noms du système de fichiers est utilisé. Si la valeur commence par @, alors un socket Unix dans l'espace de noms abstrait est utilisé.

Exemples :

host=localhost
host=127.0.0.1
host=2001:0db8:85a3:0000:0000:8a2e:0370:7334
host=/var/run/pgbouncer-1

port

Par défaut : 6432

pool_size

Définit le nombre maximum de demandes d'annulation qui peuvent être en cours simultanément avec le pair. Il est tout à fait normal que les demandes d'annulation arrivent par rafales, par exemple lorsque le serveur Postgres sous-jacent est lent ou en panne. Il est donc important que pool_size ne soit pas si bas qu'il ne puisse pas gérer ces rafales.

Si non défini, le default_pool_size est utilisé.

DIRECTIVE INCLUDE

Le fichier de configuration PgBouncer peut contenir des directives include, qui spécifient un autre fichier de configuration à lire et à traiter. Cela permet de diviser le fichier de configuration en parties physiquement séparées. Les directives include ressemblent à ceci :

%include nom_de_fichier

Si le nom de fichier n'est pas un chemin absolu, il est considéré comme relatif au répertoire de travail courant.

FORMAT FICHIER AUTHENTIFICATION

Cette section décrit le format du fichier spécifié par le réglage auth_file. C'est un fichier texte au format suivant :

"nomutilisateur1" "motdepasse" ...
"nomutilisateur2" "md5abcdef012342345" ...
"nomutilisateur2" "SCRAM-SHA-256$<iterations>:<salt>$<storedkey>:<serverkey>"

Il doit y avoir au moins 2 champs, entourés de guillemets doubles. Le premier champ est le nom d'utilisateur et le second est soit un mot de passe en texte brut, haché en MD5, soit un secret SCRAM. PgBouncer ignore le reste de la ligne. Les guillemets doubles dans une valeur de champ peuvent être échappés en écrivant deux guillemets doubles.

Format de mot de passe haché MD5 de PostgreSQL :

"md5" + md5(motdepasse + nomutilisateur)

Donc, l'utilisateur admin avec le mot de passe 1234 w

ill avoir un mot de passe haché MD5 md545f2603610af569b6155c45067268c6b.

Format de secret PostgreSQL SCRAM :

SCRAM-SHA-256$<iterations>:<salt>$<storedkey>:<serverkey>

Voir la documentation PostgreSQL et RFC 5803 pour plus de détails à ce sujet.

Les mots de passe ou secrets stockés dans le fichier d'authentification servent deux objectifs. Premièrement, ils sont utilisés pour vérifier les mots de passe des connexions client entrantes, si une méthode d'authentification basée sur un mot de passe est configurée. Deuxièmement, ils sont utilisés comme mots de passe pour les connexions sortantes vers le serveur backend, si le serveur backend exige une authentification basée sur un mot de passe (sauf si le mot de passe est spécifié directement dans la chaîne de connexion de la base de données). Ce dernier fonctionne si le mot de passe est stocké en texte brut ou haché MD5. Les secrets SCRAM ne peuvent être utilisés pour se connecter à un serveur que si l'authentification du client utilise également SCRAM, que la définition de la base de données PgBouncer ne spécifie pas de nom d'utilisateur, et que les secrets SCRAM sont identiques dans PgBouncer et le serveur PostgreSQL (même salt et même itérations, pas seulement le même mot de passe). Ceci est dû à une propriété de sécurité inhérente à SCRAM : le secret SCRAM stocké ne peut pas, en soi, être utilisé pour dériver des identifiants de connexion.

Le fichier d'authentification peut être écrit à la main, mais il est également utile de le générer à partir d'une autre liste d'utilisateurs et de mots de passe. Voir ./etc/mkauth.py pour un script d'exemple permettant de générer le fichier d'authentification à partir de la table système pg_shadow. Alternativement, utilisez auth_query au lieu de auth_file pour éviter de devoir maintenir un fichier d'authentification séparé.

FORMAT DU FICHIER HBA

L'emplacement du fichier HBA est spécifié par le paramètre auth_hba_file. Il n'est utilisé que si auth_type est défini sur hba.

Le fichier suit le format du fichier pg_hba.conf de PostgreSQL (voir https://www.postgresql.org/docs/current/auth-pg-hba-conf.html).

•
Types d'enregistrements pris en charge : local, host, hostssl, hostnossl.
•
Champ base de données : prend en charge all, sameuser, @file, plusieurs noms. Non pris en charge : replication, samerole, samegroup.
•
Champ nom d'utilisateur : prend en charge all, @file, plusieurs noms. Non pris en charge : +groupname.
•
Champ adresse : prend en charge IPv4, IPv6. Non pris en charge : noms DNS, préfixes de domaine.
•
Champ méthode d'authentification : seules les méthodes prises en charge par auth_type de PgBouncer sont prises en charge, ainsi que peer et reject, mais à l'exception de any et pam, qui ne fonctionnent qu'au niveau mondial. Le paramètre de mappage des noms d'utilisateur (map=) n'est pas pris en charge.

Exemple de fonction sécurisée pour auth_query :

CREATE OR REPLACE FUNCTION pgbouncer.user_lookup(in i_username text, out uname text, out phash text)
RETURNS record AS $$
BEGIN
    SELECT usename, passwd FROM pg_catalog.pg_shadow
    WHERE usename = i_username INTO uname, phash;
    RETURN;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
REVOKE ALL ON FUNCTION pgbouncer.user_lookup(text) FROM public, pgbouncer;
GRANT EXECUTE ON FUNCTION pgbouncer.user_lookup(text) TO pgbouncer;
