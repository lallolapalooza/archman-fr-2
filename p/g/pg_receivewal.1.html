PG_RECEIVEWAL(1) Documentation PostgreSQL 18.1 PG_RECEIVEWAL(1)

NOM

pg_receivewal - diffuser les journaux d'écriture anticipée (WAL) depuis un serveur PostgreSQL

SYNOPIS

pg_receivewal [option...]

DESCRIPTION

pg_receivewal est utilisé pour diffuser les journaux d'écriture anticipée (WAL) d'un cluster PostgreSQL en cours d'exécution. Le WAL est diffusé en utilisant le protocole de réplication en flux (streaming replication), et est écrit dans un répertoire local de fichiers. Ce répertoire peut être utilisé comme emplacement d'archivage pour une restauration en utilisant la récupération à un instant T (voir Section 25.3).

pg_receivewal diffuse le WAL en temps réel au fur et à mesure de sa génération sur le serveur, et n'attend pas que les segments soient complétés, contrairement à archive_command et archive_library. Pour cette raison, il n'est pas nécessaire de définir archive_timeout lors de l'utilisation de pg_receivewal.

Contrairement au récepteur WAL d'un serveur standby PostgreSQL, pg_receivewal, par défaut, vide les données WAL uniquement lorsqu'un fichier WAL est fermé. L'option --synchronous doit être spécifiée pour vider les données WAL en temps réel. Comme pg_receivewal n'applique pas le WAL, vous ne devez pas le laisser devenir un standby synchrone lorsque synchronous_commit est défini sur remote_apply. Si c'est le cas, il apparaîtra comme un standby qui ne rattrape jamais son retard, et provoquera le blocage des validations de transaction. Pour éviter cela, vous devriez soit configurer une valeur appropriée pour synchronous_standby_names, soit spécifier application_name pour pg_receivewal qui ne correspond pas, soit modifier la valeur de synchronous_commit pour autre chose que remote_apply.

Le WAL est diffusé via une connexion PostgreSQL normale et utilise le protocole de réplication. La connexion doit être établie avec un utilisateur ayant les permissions REPLICATION (voir Section 21.2) ou un superutilisateur, et pg_hba.conf doit autoriser la connexion de réplication. Le serveur doit également être configuré avec max_wal_senders suffisamment élevé pour laisser au moins une session disponible pour le flux.

Le point de départ de la diffusion du WAL est calculé lorsque pg_receivewal démarre :

1.Premièrement, parcourir le répertoire où les fichiers de segment WAL sont écrits et trouver le fichier de segment complété le plus récent, en utilisant comme point de départ le début du fichier de segment WAL suivant.
2.Si un point de départ ne peut pas être calculé avec la méthode précédente, et si un slot de réplication est utilisé, une commande supplémentaire READ_REPLICATION_SLOT est émise pour récupérer le restart_lsn du slot à utiliser comme point de départ. Cette option n'est disponible que lors de la diffusion de WAL à partir de PostgreSQL 15 et supérieur.
3.Si un point de départ ne peut pas être calculé avec la méthode précédente, la dernière position de vidage WAL est utilisée telle que rapportée par le serveur lors d'une commande IDENTIFY_SYSTEM.

Si la connexion est perdue, ou si elle ne peut pas être établie initialement, avec une erreur non fatale, pg_receivewal tentera de rétablir la connexion indéfiniment, et rétablira la diffusion dès que possible. Pour éviter ce comportement, utilisez le paramètre -n.

En l'absence d'erreurs fatales, pg_receivewal s'exécutera jusqu'à ce qu'il soit terminé par le signal SIGINT (Control+C) ou SIGTERM.

OPTIONS

-D répertoire
--directory=répertoire

Répertoire où écrire la sortie.

Ce paramètre est requis.

-E lsn
--endpos=lsn

Arrête automatiquement la réplication et quitte avec le statut de sortie normal 0 lorsque la réception atteint le LSN spécifié.

S'il existe un enregistrement avec un LSN exactement égal à lsn, cet enregistrement sera traité.

--if-not-exists

Ne pas générer d'erreur lorsque --create-slot est spécifié et qu'un slot du nom spécifié existe déjà.

-n
--no-loop

Ne pas boucler en cas d'erreurs de connexion. Quitter immédiatement avec une erreur.

--no-sync

Cette option fait que pg_receivewal ne force pas le vidage des données WAL sur disque. C'est plus rapide, mais signifie qu'un crash ultérieur du système d'exploitation peut laisser les segments WAL corrompus. Généralement, cette option est utile pour les tests mais ne doit pas être utilisée lors de l'archivage WAL dans un déploiement de production.

Cette option est incompatible avec --synchronous.

-s intervalle
--status-interval=intervalle

Spécifie le nombre de secondes entre les paquets de statut envoyés au serveur. Cela permet de surveiller plus facilement la progression depuis le serveur. Une valeur de zéro désactive complètement les mises à jour de statut périodiques, bien qu'une mise à jour soit toujours envoyée lorsque demandée par le serveur, pour éviter les déconnexions dues aux délais d'attente. La valeur par défaut est de 10 secondes.

-S nom_slot
--slot=nom_slot

Exige que pg_receivewal utilise un slot de réplication existant (voir Section 26.2.6). Lorsque cette option est utilisée, pg_receivewal rapportera une position de vidage au serveur, indiquant quand chaque segment a été synchronisé sur disque afin que le serveur puisse supprimer ce segment s'il n'est pas nécessaire autrement.

Lorsque le client de réplication de pg_receivewal est configuré sur le serveur comme un standby synchrone, l'utilisation d'un slot de réplication rapportera la position de vidage au serveur, mais seulement lorsqu'un fichier WAL est fermé. Par conséquent, cette configuration entraînera l'attente des transactions sur le primaire pendant une longue période et ne fonctionnera pas de manière satisfaisante. L'option --synchronous (voir ci-dessous) doit être spécifiée en plus pour que cela fonctionne correctement.

--synchronous

Vide les données WAL sur disque immédiatement après leur réception. Envoie également un paquet de statut au serveur immédiatement après le vidage, indépendamment de --status-interval.

Cette option doit être spécifiée si le client de réplication de pg_receivewal est configuré sur le serveur comme un standby synchrone, afin de garantir que des retours d'information rapides soient envoyés au serveur.

-v
--verbose

Active le mode verbeux.

-Z niveau
-Z methode[:detail]
--compress=niveau
--compress=methode[:detail]

Active la compression des journaux d'écriture anticipée.

La méthode de compression peut être définie sur gzip, lz4 (si PostgreSQL a été compilé avec --with-lz4) ou none pour aucune compression. Une chaîne de détails de compression peut être spécifiée en option. Si la chaîne de détails est un entier, elle spécifie le niveau de compression. Sinon, elle doit être une liste d'éléments séparés par des virgules, chacun de la forme mot-clé ou mot-clé=valeur. Actuellement, le seul mot-clé pris en charge est level.

Si aucun niveau de compression n'est spécifié, le niveau de compression par défaut sera utilisé. Si seul un niveau est spécifié sans mentionner d'algorithme, la compression gzip sera utilisée si le niveau est supérieur à 0, et aucune compression ne sera utilisée si le niveau est 0.

Le suffixe .gz sera automatiquement ajouté à tous les noms de fichiers lors de l'utilisation de gzip, et le suffixe .lz4 sera ajouté lors de l'utilisation de lz4.

Les options de ligne de commande suivantes contrôlent les paramètres de connexion à la base de données.

-d chaine_connexion
--dbname=chaine_connexion

Spécifie les paramètres utilisés pour se connecter au serveur, sous forme de chaîne de connexion ; ceux-ci remplaceront toute option de ligne de commande conflictuelle.

Cette option est appelée --dbname par souci de cohérence avec d'autres applications clientes, mais comme pg_receivewal ne se connecte à aucune base de données particulière du cluster, tout nom de base de données inclus dans la chaîne de connexion sera ignoré par le serveur. Cependant, un nom de base de données fourni de cette manière remplace le nom de base de données par défaut (replication) aux fins de recherche du mot de passe de connexion de réplication dans ~/.pgpass. De même, les intergiciels ou les proxys utilisés pour se connecter à PostgreSQL pourraient utiliser le nom à des fins telles que le routage de connexion.

--host=hote

Spécifie le nom d'hôte de la machine sur laquelle le serveur est en cours d'exécution. Si la valeur commence par une barre oblique, elle est utilisée comme répertoire pour le socket de domaine Unix. La valeur par défaut est prise de la variable d'environnement PGHOST, si elle est définie, sinon une connexion par socket de domaine Unix est tentée.

pg_receivewal(1) — PostgreSQL 18.1

NAME

pg_receivewal

stream WAL data from a PostgreSQL server

SYNOPSIS

pg_receivewal [-D directory] [-f filename] [-X method] [-L] [-p port] [-s seconds] [-S slotname] [-U username] [-w | -W] [--create-slot] [--drop-slot] [-V] [-?]

DESCRIPTION

pg_receivewal is a client utility to stream the Write-Ahead Log (WAL) from a PostgreSQL server. It can be used to set up a standby server or for backup purposes. It is designed to be a replacement for a WAL archival program used by the server, or it can be used in conjunction with other backup tools. It connects to the server using the streaming replication protocol and writes the received WAL data into files in a specified directory.

The utility requires a replication connection to the server. This means that the server must be configured with appropriate settings in postgresql.conf (like wal_level = replica or higher) and in pg_hba.conf to allow replication connections from the user running pg_receivewal.

When pg_receivewal is started, it connects to the server and requests WAL data starting from the current WAL location or a specified position. It writes the received WAL data into files in the specified directory. The files are named according to their WAL location, e.g., 000000010000000000000001. It continues to run, receiving and writing WAL data until interrupted.

It is strongly recommended to use replication slots (see -S option) with pg_receivewal. Replication slots ensure that WAL data is not removed by the server before it has been received by pg_receivewal. Without a replication slot, if pg_receivewal fails or is stopped, the server might recycle WAL files that have not yet been transferred, leading to data loss.

OPTIONS

pg_receivewal accepts the following command-line arguments:

-D directory
--directory=directory

Specifies the directory in which to store the received WAL files and any temporary files. This option is mandatory.

-f filename
--outfile=filename

Stream WAL data into a single file named filename instead of segment files. This option is only useful for streaming WAL data to standard output. This option is mutually exclusive with -D.

-X method
--wal-method=method

Specifies how to receive WAL files. method can be one of stream (default) or fetch.

-L
--pull

Enable fetch mode. This means WAL files are requested by the client. Without this option, WAL files are streamed by the server.

-s seconds
--status-interval=seconds

Specifies the time interval, in seconds, between status messages sent to the server. A value of 0 disables periodic status messages. Defaults to 10 seconds.

-S slotname
--slot=slotname

Specifies the name of the replication slot to use. If this option is given, pg_receivewal will create the slot if it doesn't exist and drop it if the --drop-slot option is used.

-p port
--port=port

Specifies the TCP port on which the server is listening for connections. Defaults to the PGPORT environment variable, if set, or a compiled-in default.

-U username
--username=username

User name to connect as.

-w
--no-password

Never issue a password prompt. If the server requires password authentication and a password is not available by other means such as a .pgpass file, the connection attempt will fail. This option can be useful in batch jobs and scripts where no user is present to enter a password.

-W
--password

Force pg_receivewal to prompt for a password before connecting to a database.

This option is never essential, since pg_receivewal will automatically prompt for a password if the server demands password authentication. However, pg_receivewal will waste a connection attempt finding out that the server wants a password. In some cases it is worth typing -W to avoid the extra connection attempt.

pg_receivewal can perform one of the two following actions in order to control physical replication slots:

--create-slot

Create a new physical replication slot with the name specified in --slot, then exit.

--drop-slot

Drop the replication slot with the name specified in --slot, then exit.

Other options are also available:

-V
--version

Print the pg_receivewal version and exit.

-?
--help

Show help about pg_receivewal command line arguments, and exit.

EXIT STATUS

pg_receivewal will exit with status 0 when terminated by the SIGINT or SIGTERM signal. (That is the normal way to end it. Hence it is not an error.) For fatal errors or other signals, the exit status will be nonzero.

ENVIRONMENT

This utility, like most other PostgreSQL utilities, uses the environment variables supported by libpq (see Section 32.15).

The environment variable PG_COLOR specifies whether to use color in diagnostic messages. Possible values are always, auto and never.

NOTES

When using pg_receivewal instead of archive_command or archive_library as the main WAL backup method, it is strongly recommended to use replication slots. Otherwise, the server is free to recycle or remove write-ahead log files before they are backed up, because it does not have any information, either from archive_command or archive_library or the replication slots, about how far the WAL stream has been archived. Note, however, that a replication slot will fill up the server's disk space if the receiver does not keep up with fetching the WAL data.

pg_receivewal will preserve group permissions on the received WAL files if group permissions are enabled on the source cluster.

EXAMPLES

To stream the write-ahead log from the server at mydbserver and store it in the local directory /usr/local/pgsql/archive:

$ pg_receivewal -h mydbserver -D /usr/local/pgsql/archive
