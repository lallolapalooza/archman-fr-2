PGBENCH(1) Documentation PostgreSQL 18.1 PGBENCH(1)

NOM

pgbench - exécute un test de référence sur PostgreSQL

SYNTAXE

pgbench -i [option...] [dbname]

pgbench [option...] [dbname]

DESCRIPTION

pgbench est un programme simple pour exécuter des tests de référence sur PostgreSQL. Il exécute la même séquence de commandes SQL encore et encore, éventuellement dans plusieurs sessions de base de données concurrentes, puis calcule le taux de transactions moyen (transactions par seconde). Par défaut, pgbench teste un scénario basé vaguement sur TPC-B, impliquant cinq commandes SELECT, UPDATE et INSERT par transaction. Cependant, il est facile de tester d'autres cas en écrivant vos propres fichiers de script de transaction.

Une sortie typique de pgbench ressemble à ceci :

type de transaction : <intégré : TPC-B (en quelque sorte)>
facteur d'échelle : 10
mode de requête : simple
nombre de clients : 10
nombre de threads : 1
nombre maximum d'essais : 1
nombre de transactions par client : 1000
nombre de transactions réellement traitées : 10000/10000
nombre de transactions échouées : 0 (0.000%)
latence moyenne = 11.013 ms
écart type latence = 7.351 ms
temps de connexion initial = 45.758 ms
tps = 896.967014 (sans le temps de connexion initial)

Les sept premières lignes rapportent certains des paramètres les plus importants. La sixième ligne rapporte le nombre maximum d'essais pour les transactions avec des erreurs de sérialisation ou d'interblocage (voir Échecs et Retentatives de sérialisation/interblocage pour plus d'informations). La huitième ligne rapporte le nombre de transactions terminées et prévues (cette dernière étant simplement le produit du nombre de clients et du nombre de transactions par client) ; celles-ci seront égales sauf si l'exécution a échoué avant l'achèvement ou si une ou plusieurs commandes SQL ont échoué. (En mode -T, seul le nombre réel de transactions est imprimé.) La ligne suivante rapporte le nombre de transactions échouées en raison d'erreurs de sérialisation ou d'interblocage (voir Échecs et Retentatives de sérialisation/interblocage pour plus d'informations). La dernière ligne rapporte le nombre de transactions par seconde.

Le test de transaction par défaut de type TPC-B nécessite que des tables spécifiques soient configurées au préalable. pgbench doit être appelé avec l'option -i (initialiser) pour créer et remplir ces tables. (Lorsque vous testez un script personnalisé, vous n'avez pas besoin de cette étape, mais vous devrez plutôt effectuer la configuration nécessaire à votre test.) L'initialisation ressemble à ceci :

pgbench -i [ autres-options ] dbname

où dbname est le nom de la base de données déjà créée dans laquelle tester. (Vous pourriez également avoir besoin des options -h, -p et/ou -U pour spécifier comment se connecter au serveur de base de données.)


Attention

pgbench -i crée quatre tables pgbench_accounts, pgbench_branches, pgbench_history et pgbench_tellers, détruisant toute table existante portant ces noms. Soyez très prudent pour utiliser une autre base de données si vous avez des tables portant ces noms !

Avec le “facteur d'échelle” par défaut de 1, les tables contiennent initialement ce nombre de lignes :

table                   # de lignes
---------------------------------
pgbench_branches        1
pgbench_tellers         10
pgbench_accounts        100000
pgbench_history         0

Vous pouvez (et, pour la plupart des usages, vous devriez probablement) augmenter le nombre de lignes en utilisant l'option -s (facteur d'échelle). L'option -F (fillfactor) peut également être utilisée à ce moment.

Une fois que vous avez effectué la configuration nécessaire, vous pouvez exécuter votre référence avec une commande qui n'inclut pas -i, c'est-à-dire

pgbench [ options ] dbname

Dans presque tous les cas, vous aurez besoin de certaines options pour effectuer un test utile. Les options les plus importantes sont -c (nombre de clients), -t (nombre de transactions), -T (limite de temps) et -f (spécifier un fichier script personnalisé). Voir ci-dessous pour une liste complète.

OPTIONS

Ce qui suit est divisé en trois sous-sections. Différentes options sont utilisées pendant l'initialisation de la base de données et lors de l'exécution des tests de référence, mais certaines options sont utiles dans les deux cas.

Options d'initialisation

pgbench accepte les arguments d'initialisation en ligne de commande suivants :

[-d] dbname
[--dbname=]dbname

Spécifie le nom de la base de données dans laquelle tester. Si cela n'est pas spécifié, la variable d'environnement PGDATABASE est utilisée. Si celle-ci n'est pas définie, le nom d'utilisateur spécifié pour la connexion est utilisé.

-i
--initialize

Requis pour invoquer le mode d'initialisation.

-I init_steps
--init-steps=init_steps

Effectue uniquement un ensemble sélectionné des étapes d'initialisation normales. init_steps spécifie les étapes d'initialisation à effectuer, en utilisant un caractère par étape. Chaque étape est invoquée dans l'ordre spécifié. Par défaut, dtgvp. Les étapes disponibles sont :

d (Drop / Supprimer)

Supprime toutes les tables pgbench existantes.

t (create Tables / Créer des tables)

Crée les tables utilisées par le scénario pgbench standard, à savoir pgbench_accounts, pgbench_branches, pgbench_history et pgbench_tellers.

g ou G (Generate data / Générer des données, côté client ou côté serveur)

Génère des données et les charge dans les tables standard, en remplaçant toutes les données déjà présentes.

Avec g (génération de données côté client), les données sont générées dans le client pgbench puis envoyées au serveur. Ceci utilise intensivement la bande passante client/serveur via un COPY. pgbench utilise l'option FREEZE pour charger les données dans des tables ordinaires (non partitionnées) avec les versions 14 ou ultérieures de PostgreSQL afin d'accélérer le VACUUM ultérieur. L'utilisation de g provoque l'impression d'un message par 100 000 lignes lors de la génération de données pour toutes les tables.

Avec G (génération de données côté serveur), seules de petites requêtes sont envoyées depuis le client pgbench et les données sont ensuite effectivement générées dans le serveur. Aucune bande passante significative n'est requise pour cette variante, mais le serveur effectuera plus de travail. L'utilisation de G empêche l'impression de message de progression lors de la génération de données.

Le comportement d'initialisation par défaut utilise la génération de données côté client (équivalent à g).

v (Vacuum / Vidage)

Invoque VACUUM sur les tables standard.

p (create Primary keys / Créer des clés primaires)

Crée des index de clé primaire sur les tables standard.

f (create Foreign keys / Créer des clés étrangères)

Crée des contraintes de clé étrangère entre les tables standard. (Notez que cette étape n'est pas effectuée par défaut.)

-F fillfactor
--fillfactor=fillfactor

Crée les tables pgbench_accounts, pgbench_tellers et pgbench_branches avec le fillfactor donné. Par défaut, il est de 100.

-n
--no-vacuum

N'effectue aucun vidage lors de l'initialisation. (Cette option supprime l'étape d'initialisation v, même si elle a été spécifiée dans -I.)

-q
--quiet

Passe le mode de journalisation en mode silencieux, produisant un seul message de progression toutes les 5 secondes. La journalisation par défaut imprime un message par 100 000 lignes, ce qui produit souvent de nombreuses lignes par seconde (surtout sur du bon matériel).

Ce réglage n'a aucun effet si G est spécifié dans -I.

-s scale_factor
--scale=scale_factor

Multiplie le nombre de lignes générées par le facteur d'échelle. Par exemple, -s 100 créera 10 000 000 de lignes dans la table pgbench_accounts. Par défaut, il est de 1. Lorsque l'échelle est de 20 000 ou plus, les colonnes utilisées pour stocker les identifiants de compte (colonnes aid) passeront à l'utilisation d'entiers plus grands (bigint), afin d'être suffisamment grands pour contenir la plage des identifiants de compte.

--foreign-keys

Crée des contraintes de clé étrangère entre les tables standard. (Cette option ajoute l'étape f à la séquence des étapes d'initialisation, si elle n'est pas déjà présente.)

--index-tablespace=index_tablespace

Crée des index dans l'espace de table spécifié, plutôt que dans l'espace de table par défaut.

--partition-method=NAME

Crée une table pgbench_accounts partitionnée avec la méthode NAME. Les valeurs attendues sont range ou hash. Cette option nécessite que --partitions soit défini sur

non nul. Si non spécifié, la valeur par défaut est plage.

--partitions=NUM

Crée une table pgbench_accounts partitionnée avec NUM partitions de taille quasi égale pour le nombre d'éléments mis à l'échelle. La valeur par défaut est 0, ce qui signifie aucune partition.

--tablespace=tablespace

Crée les tables dans le tablespace spécifié, plutôt que dans le tablespace par défaut.

--unlogged-tables

Crée toutes les tables en tant que tables non enregistrées (unlogged), plutôt que des tables permanentes.

Options de benchmarking

pgbench accepte les arguments de ligne de commande de benchmarking suivants :

-b nom_script[@poids]
--builtin=nom_script[@poids]

Ajoute le script intégré spécifié à la liste des scripts à exécuter. Les scripts intégrés disponibles sont : tpcb-like, simple-update et select-only. Les préfixes non ambigus des noms intégrés sont acceptés. Avec le nom spécial list, affiche la liste des scripts intégrés et quitte immédiatement.

Optionnellement, écrivez un entier de poids après @ pour ajuster la probabilité de sélectionner ce script par rapport aux autres. Le poids par défaut est 1. Voir ci-dessous pour plus de détails.

-c clients
--client=clients

Nombre de clients simulés, c'est-à-dire le nombre de sessions de base de données concurrentes. La valeur par défaut est 1.

-C
--connect

Établit une nouvelle connexion pour chaque transaction, plutôt que de le faire une seule fois par session client. Ceci est utile pour mesurer la surcharge de connexion.

-D varname=valeur
--define=varname=valeur

Définit une variable à utiliser par un script personnalisé (voir ci-dessous). Plusieurs options -D sont autorisées.

-f nom_fichier[@poids]
--file=nom_fichier[@poids]

Ajoute un script de transaction lu depuis nom_fichier à la liste des scripts à exécuter.

Optionnellement, écrivez un entier de poids après @ pour ajuster la probabilité de sélectionner ce script par rapport aux autres. Le poids par défaut est 1. (Pour utiliser un nom de fichier de script incluant un caractère @, ajoutez un poids afin qu'il n'y ait aucune ambiguïté, par exemple filen@me@1.) Voir ci-dessous pour plus de détails.

-j threads
--jobs=threads

Nombre de threads de travail dans pgbench. L'utilisation de plus d'un thread peut être utile sur les machines multi-CPU. Les clients sont distribués aussi uniformément que possible entre les threads disponibles. La valeur par défaut est 1.

-l
--log

Écrit des informations sur chaque transaction dans un fichier journal. Voir ci-dessous pour plus de détails.

-L limite
--latency-limit=limite

Les transactions qui durent plus de limite millisecondes sont comptées et signalées séparément, comme étant en retard.

Lorsqu'une limitation est utilisée (--rate=...), les transactions qui prennent du retard par rapport à la planification de plus de limite ms, et qui n'ont donc aucun espoir d'atteindre la limite de latence, ne sont pas envoyées au serveur. Elles sont comptées et signalées séparément comme ignorées.

Lorsque l'option --max-tries est utilisée, une transaction qui échoue en raison d'une anomalie de sérialisation ou d'un interblocage ne sera pas retentée si le temps total de toutes ses tentatives est supérieur à limite ms. Pour limiter uniquement le temps des tentatives et non leur nombre, utilisez --max-tries=0. Par défaut, l'option --max-tries est définie sur 1 et les transactions avec des erreurs de sérialisation/interblocage ne sont pas retentées. Voir Échecs et Réessais de sérialisation/interblocage pour plus d'informations sur la réessai de telles transactions.

-M mode_requete
--protocol=mode_requete

Protocole à utiliser pour soumettre les requêtes au serveur :
•simple : utilise le protocole de requête simple.
•extended : utilise le protocole de requête étendu.
•prepared : utilise le protocole de requête étendu avec des instructions préparées.

En mode préparé, pgbench réutilise le résultat de l'analyse syntaxique à partir de la deuxième itération de requête, donc pgbench s'exécute plus rapidement que dans les autres modes.

La valeur par défaut est le protocole de requête simple. (Voir Chapitre 54 pour plus d'informations.)

-n
--no-vacuum

Ne pas effectuer de vacuum avant d'exécuter le test. Cette option est *nécessaire* si vous exécutez un scénario de test personnalisé qui n'inclut pas les tables standard pgbench_accounts, pgbench_branches, pgbench_history et pgbench_tellers.

-N
--skip-some-updates

Exécute le script intégré simple-update. Raccourci pour -b simple-update.

-P sec
--progress=sec

Affiche le rapport de progression toutes les sec secondes. Le rapport comprend le temps écoulé depuis le début de l'exécution, le TPS depuis le dernier rapport, et la latence moyenne des transactions, l'écart type, et le nombre de transactions échouées depuis le dernier rapport. Sous limitation (-R), la latence est calculée par rapport à l'heure de début prévue de la transaction, et non à l'heure de début réelle de la transaction, elle inclut donc également le temps de décalage moyen de la planification. Lorsque --max-tries est utilisé pour activer les réessais de transactions après des erreurs de sérialisation/interblocage, le rapport inclut le nombre de transactions retentées et la somme de tous les réessais.

-r
--report-per-command

Rapporte les statistiques suivantes pour chaque commande après la fin du benchmark : la latence moyenne par instruction (temps d'exécution du point de vue du client), le nombre d'échecs, et le nombre de réessais après des erreurs de sérialisation ou d'interblocage pour cette commande. Le rapport affiche les statistiques de réessai uniquement si l'option --max-tries n'est pas égale à 1.

-R taux
--rate=taux

Exécute les transactions en visant le taux spécifié au lieu de s'exécuter aussi vite que possible (par défaut). Le taux est donné en transactions par seconde. Si le taux cible est supérieur au taux maximum possible, la limite de taux n'aura pas d'impact sur les résultats.

Le taux est ciblé en démarrant les transactions le long d'une ligne de temps de planification distribuée selon Poisson. L'heure de début prévue avance en fonction du moment où le client a commencé pour la première fois, et non du moment où la transaction précédente s'est terminée. Cette approche signifie que lorsque les transactions dépassent leur heure de fin initialement prévue, il est possible que des transactions ultérieures les rattrapent à nouveau.

Lorsque la limitation est active, la latence de transaction signalée à la fin de l'exécution est calculée à partir des heures de début prévues, elle inclut donc le temps que chaque transaction a dû attendre que la transaction précédente se termine. Le temps d'attente est appelé temps de décalage de planification, et sa moyenne et son maximum sont également signalés séparément. La latence de transaction par rapport à l'heure de début réelle de la transaction, c'est-à-dire le temps passé à exécuter la transaction dans la base de données, peut être calculée en soustrayant le temps de décalage de planification de la latence signalée.

Si --latency-limit est utilisé avec --rate, une transaction peut prendre tellement de retard qu'elle dépasse déjà la limite de latence à la fin de la transaction précédente, car la latence est calculée à partir des heures de début prévues. De telles transactions ne sont pas envoyées au serveur, mais sont complètement ignorées et comptées séparément.

Un temps de décalage de planification élevé indique que le système ne peut pas traiter les transactions au taux spécifié, avec le nombre de clients et de threads choisi. Lorsque le temps d'exécution moyen des transactions est plus long que l'intervalle prévu entre chaque transaction, chaque transaction successive prendra de plus en plus de retard, et le temps de décalage de planification augmentera de plus en plus pendant l'exécution du test. Lorsque cela se produit, vous devrez réduire le taux de transaction spécifié.

-s facteur_echelle
--scale=facteur_echelle

Rapporte le facteur d'échelle spécifié dans la sortie de pgbench. Avec les tests intégrés, cela n'est pas nécessaire ; le facteur d'échelle correct sera détecté en comptant le nombre de lignes dans la table pgbench_branches. Cependant, lors du test uniquement des benchmarks personnalisés (option -f), le facteur d'échelle sera rapporté comme 1 sauf si cette option est utilisée.

-S
--select-only

Exécute le script intégré select-only. Raccourci pour -b select-only.

-t transactions
--transactions=transactions

Nombre de transactions que chaque client exécute. La valeur par défaut est 10.

-T secondes
--time=secondes

Exécute le test pendant ce nombre de secondes, plutôt qu'un nombre fixe de transactions par client. -t et -T sont mutuellement exclusifs.

-v
--vacuum-all

Applique un vacuum sur les quatre tables standard avant d'exécuter le test. Sans -n ni -v, pgbench appliquera un vacuum sur les tables pgbench_tellers et pgbench_branches, et tronquera pgbench_history.

--aggregate-interval=secondes

Durée de l'intervalle d'agrégation (en secondes). Peut être utilisé uniquement avec l'option -l. Avec cette option, le journal contient des données récapitulatives par intervalle, comme décrit ci-dessous.

--exit-on-abort

Quitte immédiatement lorsqu'un client est avorté en raison d'une erreur. Sans cette option, même lorsqu'un client est avorté, d'autres clients peuvent continuer leur exécution comme spécifié par l'option -t ou -T, et pgbench affichera dans ce cas des résultats incomplets.

Notez que les échecs de sérialisation ou d'interblocage n'avortent pas le client, ils ne sont donc pas affectés par cette option. Voir Échecs et Réessais de sérialisation/interblocage pour plus d'informations.

--failures-detailed

Rapporte les échecs dans les journaux par transaction et agrégés, ainsi que dans les rapports principaux et par script, regroupés par les types suivants :
•échecs de sérialisation ;
•échecs d'interblocage ;

Voir Échecs et Réessais de sérialisation/interblocage pour plus d'informations.

--log-prefix=préfixe

Définit le préfixe du nom de fichier pour les journaux créés par --log. La valeur par défaut est pgbench_log.

--max-tries=nombre_de_tentatives

Active les réessais pour les transactions avec des erreurs de sérialisation/interblocage et définit le nombre maximum de ces tentatives. Cette option peut être combinée avec l'option --latency-limit qui limite le temps total de toutes les tentatives de transaction ; de plus, vous ne pouvez pas utiliser une valeur illimitée
d nombre d'essais (--max-tries=0) sans --latency-limit ou --time. La valeur par défaut est 1 et les transactions avec des erreurs de sérialisation/interblocage ne sont pas retentées. Voir Échecs et Réessais de sérialisation/interblocage pour plus d'informations sur le retentissement de ces transactions.

--progress-timestamp

Lors de l'affichage de la progression (option -P), utiliser un horodatage (époque Unix) au lieu du nombre de secondes depuis le début de l'exécution. L'unité est en secondes, avec une précision milliseconde après le point. Ceci aide à comparer les journaux générés par divers outils.

--random-seed=graine

Définir la graine du générateur aléatoire. Ensemence le générateur de nombres aléatoires du système, qui produit ensuite une séquence d'états générateurs initiaux, un pour chaque thread. Les valeurs pour graine peuvent être : time (la valeur par défaut, la graine est basée sur l'heure actuelle), rand (utiliser une source aléatoire forte, échouant si aucune n'est disponible), ou une valeur entière décimale non signée. Le générateur aléatoire est invoqué explicitement depuis un script pgbench (fonctions random...) ou implicitement (par exemple, l'option --rate l'utilise pour planifier les transactions). Lorsqu'elle est explicitement définie, la valeur utilisée pour l'ensemencement est affichée sur le terminal. Toute valeur autorisée pour graine peut également être fournie via la variable d'environnement PGBENCH_RANDOM_SEED. Pour s'assurer que la graine fournie impacte toutes les utilisations possibles, placez cette option en premier ou utilisez la variable d'environnement.

Définir explicitement la graine permet de reproduire une exécution pgbench exactement, en ce qui concerne les nombres aléatoires. Comme l'état aléatoire est géré par thread, cela signifie que la même exécution pgbench pour une invocation identique si il y a un client par thread et qu'il n'y a pas de dépendances externes ou de données. D'un point de vue statistique, reproduire les exécutions exactement est une mauvaise idée car cela peut masquer la variabilité des performances ou améliorer indûment les performances, par exemple, en accédant aux mêmes pages qu'une exécution précédente. Cependant, cela peut aussi être d'une grande aide pour le débogage, par exemple, en rejouant un cas délicat qui conduit à une erreur. À utiliser judicieusement.

--sampling-rate=taux

Taux d'échantillonnage, utilisé lors de l'écriture des données dans le journal, pour réduire la quantité de journal générée. Si cette option est donnée, seule la fraction spécifiée de transactions est enregistrée. 1.0 signifie que toutes les transactions seront enregistrées, 0.05 signifie que seulement 5% des transactions seront enregistrées.

N'oubliez pas de prendre en compte le taux d'échantillonnage lors du traitement du fichier journal. Par exemple, lors du calcul des valeurs TPS, vous devez multiplier les nombres en conséquence (par exemple, avec un taux d'échantillonnage de 0.01, vous n'obtiendrez que 1/100 des TPS réels).

--show-script=nomscript

Afficher le code réel du script intégré nomscript sur stderr, et quitter immédiatement.

--verbose-errors

Imprimer des messages sur toutes les erreurs et tous les échecs (erreurs sans retentissement) y compris quelle limite de retentissement a été dépassée et de combien elle a été dépassée pour les échecs de sérialisation/interblocage. (Notez que dans ce cas, la sortie peut être considérablement augmentée.) Voir Échecs et Réessais de sérialisation/interblocage pour plus d'informations.

Statut de Sortie

Une exécution réussie se terminera avec le statut 0. Le statut de sortie 1 indique des problèmes statiques tels que des options de ligne de commande invalides ou des erreurs internes qui sont censées ne jamais se produire. Les erreurs précoces qui surviennent au démarrage du benchmark, comme les échecs de connexion initiaux, se terminent également avec le statut 1. Les erreurs pendant l'exécution, comme les erreurs de base de données ou les problèmes dans le script, entraîneront le statut de sortie 2. Dans ce dernier cas, pgbench affichera des résultats partiels si l'option --exit-on-abort n'est pas spécifiée.

Notes

Quelle est la “Transaction” réellement effectuée dans pgbench ?

pgbench exécute des scripts de test choisis aléatoirement parmi une liste spécifiée. Les scripts peuvent inclure des scripts intégrés spécifiés avec -b et des scripts fournis par l'utilisateur spécifiés avec -f. Chaque script peut se voir attribuer un poids relatif spécifié après un @ afin de modifier sa probabilité de sélection. Le poids par défaut est 1. Les scripts avec un poids de 0 sont ignorés.

Le script de transaction intégré par défaut (également appelé avec -b tpcb-like) émet sept commandes par transaction sur des aid, tid, bid et delta choisis aléatoirement. Le scénario est inspiré du benchmark TPC-B, mais n'est pas réellement TPC-B, d'où son nom.

1.BEGIN;
2.UPDATE pgbench_accounts SET abalance = abalance + :delta WHERE aid = :aid;
3.SELECT abalance FROM pgbench_accounts WHERE aid = :aid;
4.UPDATE pgbench_tellers SET tbalance = tbalance + :delta WHERE tid = :tid;
5.UPDATE pgbench_branches SET bbalance = bbalance + :delta WHERE bid = :bid;
6.INSERT INTO pgbench_history (tid, bid, aid, delta, mtime) VALUES (:tid, :bid, :aid, :delta, CURRENT_TIMESTAMP);
7.END;

Si vous sélectionnez le script simple-update intégré (également -N), les étapes 4 et 5 ne sont pas incluses dans la transaction. Cela évitera la contention de mise à jour sur ces tables, mais cela rend le cas de test encore moins similaire à TPC-B.

Si vous sélectionnez le script select-only intégré (également -S), seul le SELECT est émis.

Scripts Personnalisés

pgbench prend en charge l'exécution de scénarios de benchmark personnalisés en remplaçant le script de transaction par défaut (décrit ci-dessus) par un script de transaction lu à partir d'un fichier (option -f). Dans ce cas, une “transaction” compte comme une exécution d'un fichier script.

Un fichier script contient une ou plusieurs commandes SQL terminées par des points-virgules. Les lignes vides et les lignes commençant par -- sont ignorées. Les fichiers script peuvent également contenir des “méta-commandes”, qui sont interprétées par pgbench lui-même, comme décrit ci-dessous.


Note

Avant PostgreSQL 9.6, les commandes SQL dans les fichiers script étaient terminées par des sauts de ligne, et ne pouvaient donc pas être poursuivies sur plusieurs lignes. Désormais, un point-virgule est requis pour séparer les commandes SQL consécutives (bien qu'une commande SQL n'en ait pas besoin si elle est suivie d'une méta-commande). Si vous devez créer un fichier script qui fonctionne avec les anciennes et les nouvelles versions de pgbench, assurez-vous d'écrire chaque commande SQL sur une seule ligne se terminant par un point-virgule.

On suppose que les scripts pgbench ne contiennent pas de blocs incomplets de transactions SQL. Si au moment de l'exécution le client atteint la fin du script sans avoir complété le dernier bloc de transaction, il sera avorté.

Il existe une installation simple de substitution de variables pour les fichiers script. Les noms de variables doivent être composés de lettres (y compris des lettres non latines), de chiffres et de traits de soulignement, le premier caractère n'étant pas un chiffre. Les variables peuvent être définies par l'option de ligne de commande -D, expliquée ci-dessus, ou par les méta-commandes expliquées ci-dessous. En plus des variables prédéfinies par les options de ligne de commande -D, il existe quelques variables qui sont prédéfinies automatiquement, listées dans le Tableau 301. Une valeur spécifiée pour ces variables à l'aide de -D l'emporte sur les prédéfinitions automatiques. Une fois définie, la valeur d'une variable peut être insérée dans une commande SQL en écrivant :nomvariable. Lors de l'exécution de plus d'une session client, chaque session a son propre ensemble de variables. pgbench prend en charge jusqu'à 255 utilisations de variables dans une seule instruction.

La
fonction random génère des valeurs en utilisant une distribution uniforme, c'est-à-dire que toutes les valeurs sont tirées dans la plage spécifiée avec une probabilité égale. Les fonctions random_exponential, random_gaussian et random_zipfian nécessitent un paramètre double supplémentaire qui détermine la forme précise de la distribution.

•Pour une distribution exponentielle, parameter contrôle la distribution en tronquant une distribution exponentielle qui décroît rapidement à parameter, puis en projetant sur des entiers entre les bornes. Pour être précis, avec 
f(x) = exp(-parameter * (x - min) / (max - min + 1)) / (1 - exp(-parameter))

Alors la valeur i entre min et max inclus est tirée avec la probabilité : f(i) - f(i + 1).

Intuitivement, plus le parameter est élevé, plus fréquemment les valeurs proches de min sont accédées, et moins fréquemment les valeurs proches de max sont accédées. Plus le parameter est proche de 0, plus la distribution d'accès est plate (plus uniforme). Une approximation grossière de la distribution est que les 1% de valeurs les plus fréquentes dans la plage, proches de min, sont tirées parameter% du temps. La valeur parameter doit être strictement positive.

•Pour une distribution Gaussienne, l'intervalle est mappé sur une distribution normale standard (la courbe Gaussienne classique en forme de cloche) tronquée à -parameter à gauche et +parameter à droite. Les valeurs au milieu de l'intervalle sont plus susceptibles d'être tirées. Pour être précis, si PHI(x) est la fonction de distribution cumulative de la distribution normale standard, avec la moyenne mu définie comme (max + min) / 2.0, avec 
f(x) = PHI(2.0 * parameter * (x - mu) / (max - min + 1)) /
       (2.0 * PHI(parameter) - 1)

alors la valeur i entre min et max inclus est tirée avec la probabilité : f(i + 0.5) - f(i - 0.5). Intuitivement, plus le parameter est élevé, plus fréquemment les valeurs proches du milieu de l'intervalle sont tirées, et moins fréquemment les valeurs proches des bornes min et max sont tirées. Environ 67% des valeurs sont tirées à partir du 1.0 / parameter du milieu, c'est-à-dire une portion relative de 0.5 / parameter autour de la moyenne, et 95% à partir du 2.0 / parameter du milieu, c'est-à-dire une portion relative de 1.0 / parameter autour de la moyenne ; par exemple, si parameter est de 4.0, 67% des valeurs sont tirées à partir du quart central (1.0 / 4.0) de l'intervalle (c'est-à-dire de 3.0 / 8.0 à 5.0 / 8.0) et 95% à partir de la moitié centrale (2.0 / 4.0) de l'intervalle (deuxième et troisième quartiles). La valeur minimale autorisée pour parameter est de 2.0.

•random_zipfian génère une distribution de Zipf bornée. parameter définit à quel point la distribution est asymétrique. Plus le parameter est élevé, plus fréquemment les valeurs proches du début de l'intervalle sont tirées. La distribution est telle que, en supposant que la plage commence à 1, le rapport de la probabilité de tirer k versus tirer k+1 est ((k+1)/k)**parameter. Par exemple, random_zipfian(1, ..., 2.5) produit la valeur 1 environ 5,66 fois plus fréquemment que 2, qui lui-même est produit 2,76 fois plus fréquemment que 3, et ainsi de suite.

L'implémentation de pgbench est basée sur "Non-Uniform Random Variate Generation", Luc Devroye, p. 550-551, Springer 1986. En raison des limitations de cet algorithme, la valeur parameter est limitée à la plage [1.001, 1000].


Note

Lors de la conception d'un benchmark qui sélectionne des lignes de manière non uniforme, soyez conscient que les lignes choisies peuvent être corrélées avec d'autres données telles que des ID d'une séquence ou l'ordre physique des lignes, ce qui peut fausser les mesures de performance.

Pour éviter cela, vous pourriez souhaiter utiliser la fonction permute, ou une autre étape supplémentaire avec un effet similaire, pour mélanger les lignes sélectionnées et supprimer de telles corrélations.

Les fonctions de hachage hash, hash_murmur2 et hash_fnv1a acceptent une valeur d'entrée et un paramètre de graine optionnel. Si la graine n'est pas fournie, la valeur de :default_seed est utilisée, qui est initialisée aléatoirement sauf si elle est définie par l'option -D de la ligne de commande.

permute accepte une valeur d'entrée, une taille et un paramètre de graine optionnel. Elle génère une permutation pseudo-aléatoire d'entiers dans la plage [0, size), et retourne l'indice de la valeur d'entrée dans les valeurs permutées. La permutation choisie est paramétrée par la graine, qui est par défaut :default_seed, si elle n'est pas spécifiée. Contrairement aux fonctions de hachage, permute garantit qu'il n'y a pas de collisions ou de trous dans les valeurs de sortie. Les valeurs d'entrée en dehors de l'intervalle sont interprétées modulo la taille. La fonction lève une erreur si la taille n'est pas positive. permute peut être utilisée pour disperser la distribution des fonctions aléatoires non uniformes telles que random_zipfian ou random_exponential afin que les valeurs tirées plus souvent ne soient pas trivialement corrélées. Par exemple, le script pgbench suivant simule une charge de travail réaliste typique des plateformes de médias sociaux et de blogs où quelques comptes génèrent une charge excessive :

\set size 1000000
\set r random_zipfian(1, :size, 1.07)
\set k 1 + permute(:r, :size)

Dans certains cas, plusieurs distributions distinctes sont nécessaires qui ne sont pas corrélées entre elles, et c'est là que le paramètre de graine optionnel est utile :

\set k1 1 + permute(:r, :size, :default_seed + 123)
\set k2 1 + permute(:r, :size, :default_seed + 321)

Un comportement similaire peut également être approximé avec hash :

\set size 1000000
\set r random_zipfian(1, 100 * :size, 1.07)
\set k 1 + abs(hash(:r)) % :size

Cependant, comme hash génère des collisions, certaines valeurs ne seront pas accessibles et d'autres seront plus fréquentes que prévu à partir de la distribution d'origine.

À titre d'exemple, la définition complète de la transaction intégrée de type TPC-B est :

\set aid random(1, 100000 * :scale)
\set bid random(1, 1 * :scale)
\set tid random(1, 10 * :scale)
\set delta random(-5000, 5000)
BEGIN;
UPDATE pgbench_accounts SET abalance = abalance + :delta WHERE aid = :aid;
SELECT abalance FROM pgbench_accounts WHERE aid = :aid;
UPDATE pgbench_tellers SET tbalance = tbalance + :delta WHERE tid = :tid;
UPDATE pgbench_branches SET bbalance = bbalance + :delta WHERE bid = :bid;
INSERT INTO pgbench_history (tid, bid, aid, delta, mtime) VALUES (:tid, :bid, :aid, :delta, CURRENT_TIMESTAMP);
END;

Ce script permet à chaque itération de la transaction de référencer des lignes différentes, choisies aléatoirement. (Cet exemple montre également pourquoi il est important que chaque session client ait ses propres variables – sinon elles ne toucheraient pas indépendamment différentes lignes.)

Journalisation par transaction

Avec l'option -l (mais sans l'option --aggregate-interval), pgbench écrit des informations sur chaque transaction dans un fichier journal. Le fichier journal sera nommé prefix.nnn, où prefix est par défaut pgbench_log, et nnn est le PID du processus pgbench. Le préfixe peut être modifié en utilisant l'option --log-prefix. Si l'option -j est 2 ou supérieure, donc qu'il y a plusieurs threads de travail, chacun aura son propre fichier journal. Le premier travailleur utilisera le même nom pour son fichier journal que dans le cas standard à un seul travailleur. Les fichiers journaux supplémentaires pour les autres travailleurs seront nommés prefix.nnn.mmm, où mmm est un numéro séquentiel pour chaque travailleur commençant par 1.

Chaque ligne d'un fichier journal décrit une transaction. Elle contient les champs suivants séparés par des espaces :

client_id

identifie la session client qui a exécuté la transaction

transaction_no

compte le nombre de transactions exécutées par cette session

time

temps écoulé de la transaction, en microsecondes

script_no

identifie le fichier script utilisé pour la transaction (utile lorsque plusieurs scripts sont spécifiés avec -f ou -b)

time_epoch

heure d'achèvement de la transaction, sous forme d'horodatage Unix-epoch

time_us

partie fractionnaire de seconde de l'heure d'achèvement de la transaction, en microsecondes

schedule_lag

délai de début de transaction, c'est-à-dire la différence entre l'heure de début prévue de la transaction et l'heure à laquelle elle a effectivement commencé, en microsecondes (présent seulement si --rate est spécifié)

retries

nombre de réessais après des erreurs de sérialisation ou de verrouillage mort pendant la transaction (présent seulement si --max-tries n'est pas égal à un)

Lorsque --rate et --latency-limit sont tous deux utilisés, le time d'une transaction ignorée sera rapporté comme ignoré. Si la transaction se termine par un échec, son time sera rapporté comme échec. Si vous utilisez l'option --failures-detailed, le time de la transaction échouée sera rapporté comme sérialisation ou verrouillage mort en fonction du type d'échec (voir Échecs et Réessais de Sérialisation/Verrouillage Mort pour plus d'informations).

Per-Statement Report

With the -r option, pgbench collects the following statistics for each statement:

•latency — elapsed transaction time for each statement. pgbench reports an average value of all successful runs of the statement.
•The number of failures in this statement. See Failures and Serialization/Deadlock Retries for more information.
•The number of retries after a serialization or a deadlock error in this statement. See Failures and Serialization/Deadlock Retries for more information.

The report displays retry statistics only if the --max-tries option is not equal to 1.

All values are computed for each statement executed by every client and are reported after the benchmark has finished.

Failures and Serialization/Deadlock Retries

When executing pgbench, there are three main types of errors:

•Errors of the main program. They are the most serious and always result in an immediate exit from pgbench with the corresponding error message. They include:
•errors at the beginning of pgbench (e.g. an invalid option value);
•errors in the initialization mode (e.g. the query to create tables for built-in scripts fails);
•errors before starting threads (e.g. could not connect to the database server, syntax error in the meta command, thread creation failure);
•internal pgbench errors (which are supposed to never occur...).
•Errors when the thread manages its clients (e.g. the client could not start a connection to the database server / the socket for connecting the client to the database server has become invalid). In such cases all clients of this thread stop while other threads continue to work. However, --exit-on-abort is specified, all of the threads stop immediately in this case.
•Direct client errors. They lead to immediate exit from pgbench with the corresponding error message in the case of an internal pgbench error (which are supposed to never occur...) or when --exit-on-abort is specified. Otherwise in the worst case they only lead to the abortion of the failed client while other clients continue their run (but some client errors are handled without an abortion of the client and reported separately, see below). Later in this section it is assumed that the discussed errors are only the direct client errors and they are not internal pgbench errors.

A client's run is aborted in case of a serious error; for example, the connection with the database server was lost or the end of script was reached without completing the last transaction. In addition, if execution of an SQL or meta command fails for reasons other than serialization or deadlock errors, the client is aborted. Otherwise, if an SQL command fails with serialization or deadlock errors, the client is not aborted. In such cases, the current transaction is rolled back, which also includes setting the client variables as they were before the run of this transaction (it is assumed that one transaction script contains only one transaction; see What Is the "Transaction" Actually Performed in pgbench? for more information). Transactions with serialization or deadlock errors are repeated after rollbacks until they complete successfully or reach the maximum number of tries (specified by the --max-tries option) /

la durée maximale des nouvelles tentatives (spécifiée par l'option --latency-limit) / la fin du benchmark (spécifiée par l'option --time). Si la dernière tentative échoue, cette transaction sera signalée comme échouée mais le client ne sera pas interrompu et continuera à fonctionner.


Note

Sans spécifier l'option --max-tries, une transaction ne sera jamais rejouée après une erreur de sérialisation ou d'interblocage car sa valeur par défaut est 1. Utilisez un nombre illimité de tentatives (--max-tries=0) et l'option --latency-limit pour limiter uniquement la durée maximale des tentatives. Vous pouvez également utiliser l'option --time pour limiter la durée du benchmark sous un nombre illimité de tentatives.

Soyez prudent lors de la répétition de scripts contenant plusieurs transactions : le script est toujours rejoué dans son intégralité, ainsi les transactions réussies peuvent être exécutées plusieurs fois.

Soyez prudent lors de la répétition de transactions avec des commandes shell. Contrairement aux résultats des commandes SQL, les résultats des commandes shell ne sont pas annulés, sauf pour la valeur de la variable de la commande \setshell.

La latence d'une transaction réussie inclut toute la durée de l'exécution de la transaction avec les annulations et les nouvelles tentatives. La latence est mesurée uniquement pour les transactions et les commandes réussies, mais pas pour les transactions ou commandes échouées.

Le rapport principal contient le nombre de transactions échouées. Si l'option --max-tries n'est pas égale à 1, le rapport principal contient également des statistiques relatives aux nouvelles tentatives : le nombre total de transactions rejouées et le nombre total de nouvelles tentatives. Le rapport par script hérite de tous ces champs du rapport principal. Le rapport par instruction affiche les statistiques de nouvelles tentatives uniquement si l'option --max-tries n'est pas égale à 1.

Si vous souhaitez regrouper les échecs par types de base dans les journaux transactionnels et d'agrégation, ainsi que dans les rapports principaux et par script, utilisez l'option --failures-detailed. Si vous souhaitez également distinguer toutes les erreurs et échecs (erreurs sans nouvelles tentatives) par type, y compris la limite pour les nouvelles tentatives qui a été dépassée et de combien elle a été dépassée pour les échecs de sérialisation/interblocage, utilisez l'option --verbose-errors.

Méthodes d'accès aux tables

Vous pouvez spécifier la méthode d'accès aux tables pour les tables pgbench. La variable d'environnement PGOPTIONS spécifie les options de configuration de la base de données qui sont transmises à PostgreSQL via la ligne de commande (voir la Section 19.1.4). Par exemple, une méthode d'accès aux tables hypothétique par défaut pour les tables créées par pgbench, nommée wuzza, peut être spécifiée avec :

PGOPTIONS='-c default_table_access_method=wuzza'

Bonnes pratiques

Il est très facile d'utiliser pgbench pour produire des chiffres complètement dénués de sens. Voici quelques directives pour vous aider à obtenir des résultats utiles.

Tout d'abord, ne croyez jamais aucun test qui ne dure que quelques secondes. Utilisez l'option -t ou -T pour que l'exécution dure au moins quelques minutes, afin de moyenner le bruit. Dans certains cas, vous pourriez avoir besoin de plusieurs heures pour obtenir des chiffres reproductibles. Il est bon d'essayer d'exécuter le test plusieurs fois pour savoir si vos chiffres sont reproductibles ou non.

Pour le scénario de test par défaut similaire à TPC-B, le facteur d'échelle d'initialisation (-s) doit être au moins égal au plus grand nombre de clients que vous avez l'intention de tester (-c) ; sinon, vous mesurerez principalement la contention des mises à jour. Il n'y a que -s lignes dans la table pgbench_branches, et chaque transaction veut en mettre à jour une, donc des valeurs de -c supérieures à -s entraîneront sans aucun doute de nombreuses transactions bloquées en attente d'autres transactions.

Le scénario de test par défaut est également très sensible à la durée écoulée depuis l'initialisation des tables : l'accumulation de lignes mortes et d'espace mort dans les tables modifie les résultats. Pour comprendre les résultats, vous devez suivre le nombre total de mises à jour et quand les opérations de vacuum se produisent. Si autovacuum est activé, cela peut entraîner des changements imprévisibles dans les performances mesurées.

Une limitation de pgbench est qu'il peut lui-même devenir le goulot d'étranglement lors de la tentative de test d'un grand nombre de sessions client. Cela peut être atténué en exécutant pgbench sur une machine différente de celle du serveur de base de données, bien qu'une faible latence réseau sera essentielle. Il peut même être utile d'exécuter plusieurs instances pgbench simultanément, sur plusieurs machines clientes, contre le même serveur de base de données.

Sécurité

Si des utilisateurs non fiables ont accès à une base de données qui n'a pas adopté un schéma d'utilisation sécurisé, n'exécutez pas pgbench dans cette base de données. pgbench utilise des noms non qualifiés et ne manipule pas le chemin de recherche.
