PG_BASEBACKUP(1) Documentation PostgreSQL 18.1 PG_BASEBACKUP(1)

NOM

pg_basebackup - Effectuer une sauvegarde de base d'un cluster PostgreSQL

SYNOPIS

pg_basebackup [option...]

DESCRIPTION

pg_basebackup est utilisé pour effectuer une sauvegarde de base d'un cluster de bases de données PostgreSQL en cours d'exécution. La sauvegarde est effectuée sans affecter les autres clients de la base de données et peut être utilisée à la fois pour la récupération à un instant T (voir la Section 25.3) et comme point de départ pour un serveur de réplication en attente par envoi de journaux (log-shipping) ou par streaming (voir la Section 26.2).

pg_basebackup peut effectuer une sauvegarde de base complète ou incrémentielle de la base de données. Lorsqu'il est utilisé pour effectuer une sauvegarde complète, il fait une copie exacte des fichiers du cluster de bases de données. Lorsqu'il est utilisé pour effectuer une sauvegarde incrémentielle, certains fichiers qui auraient fait partie d'une sauvegarde complète peuvent être remplacés par des versions incrémentielles des mêmes fichiers, ne contenant que les blocs qui ont été modifiés depuis la sauvegarde de référence. Une sauvegarde incrémentielle ne peut pas être utilisée directement ; au lieu de cela, pg_combinebackup(1) doit d'abord être utilisé pour la combiner avec les sauvegardes précédentes dont elle dépend. Voir la Section 25.3.3 pour plus d'informations sur les sauvegardes incrémentielles, et la Section 25.3.5 pour les étapes de récupération à partir d'une sauvegarde.

Dans tous les modes, pg_basebackup s'assure que le serveur est automatiquement mis en et hors mode de sauvegarde. Les sauvegardes portent toujours sur l'ensemble du cluster de bases de données ; il n'est pas possible de sauvegarder des bases de données individuelles ou des objets de base de données. Pour des sauvegardes sélectives, un autre outil tel que pg_dump(1) doit être utilisé.

La sauvegarde est effectuée via une connexion PostgreSQL régulière utilisant le protocole de réplication. La connexion doit être établie avec un ID d'utilisateur disposant des permissions REPLICATION (voir la Section 21.2) ou un superutilisateur, et pg_hba.conf doit autoriser la connexion de réplication. Le serveur doit également être configuré avec max_wal_senders suffisamment élevé pour fournir au moins un walsender pour la sauvegarde plus un pour le streaming WAL (si utilisé).

Il peut y avoir plusieurs pg_basebackup en cours d'exécution simultanément, mais il est généralement préférable du point de vue des performances de n'effectuer qu'une seule sauvegarde et de copier le résultat.

pg_basebackup peut effectuer une sauvegarde de base non seulement à partir d'un serveur primaire, mais aussi d'un serveur en attente (standby). Pour effectuer une sauvegarde à partir d'un serveur en attente, configurez ce dernier de manière à ce qu'il puisse accepter les connexions de réplication (c'est-à-dire, définissez max_wal_senders et hot_standby, et configurez son pg_hba.conf de manière appropriée). Vous devrez également activer full_page_writes sur le serveur primaire.

Notez qu'il existe certaines limitations lors de la prise d'une sauvegarde à partir d'un serveur en attente :

•Le fichier d'historique de sauvegarde n'est pas créé dans le cluster de bases de données sauvegardé.
•pg_basebackup ne peut pas forcer le serveur en attente à passer à un nouveau fichier WAL à la fin de la sauvegarde. Lorsque vous utilisez -X none, si l'activité d'écriture sur le serveur primaire est faible, pg_basebackup peut devoir attendre longtemps que le dernier fichier WAL requis pour la sauvegarde soit passé et archivé. Dans ce cas, il peut être utile d'exécuter pg_switch_wal sur le serveur primaire pour déclencher un changement immédiat de fichier WAL.
•Si le serveur en attente est promu en serveur primaire pendant la sauvegarde, la sauvegarde échoue.
•Tous les enregistrements WAL requis pour la sauvegarde doivent contenir suffisamment de écritures de page complètes (full-page writes), ce qui nécessite d'activer full_page_writes sur le serveur primaire.

Chaque fois que pg_basebackup effectue une sauvegarde de base, la vue pg_stat_progress_basebackup du serveur indique la progression de la sauvegarde. Voir la Section 27.4.6 pour plus de détails.

OPTIONS

Les options de ligne de commande suivantes contrôlent l'emplacement et le format de la sortie :

-D répertoire
--pgdata=répertoire

Définit le répertoire cible où écrire la sortie. pg_basebackup créera ce répertoire (et tous les répertoires parents manquants) s'il n'existe pas. S'il existe déjà, il doit être vide.

Lorsque la sauvegarde est au format tar, le répertoire cible peut être spécifié comme - (tiret), ce qui fait que le fichier tar sera écrit sur stdout.

Cette option est obligatoire.

-F format
--format=format

Sélectionne le format pour la sortie. format peut être l'un des suivants :

p
plain

Écrit la sortie sous forme de fichiers simples, avec la même structure que le répertoire de données et les tablespaces du serveur source. Lorsque le cluster n'a pas de tablespaces supplémentaires, l'ensemble de la base de données sera placé dans le répertoire cible. Si le cluster contient des tablespaces supplémentaires, le répertoire de données principal sera placé dans le répertoire cible, mais tous les autres tablespaces seront placés dans le même chemin absolu qu'ils ont sur le serveur source. (Voir --tablespace-mapping pour changer cela.)

C'est le format par défaut.

t
tar

Écrit la sortie sous forme de fichiers tar dans le répertoire cible. Le contenu du répertoire de données principal sera écrit dans un fichier nommé base.tar, et chaque autre tablespace sera écrit dans un fichier tar séparé portant le nom de l'OID de ce tablespace.

Si le répertoire cible est spécifié comme - (tiret), le contenu du tar sera écrit sur la sortie standard, adapté pour être redirigé vers (par exemple) gzip. Ceci n'est autorisé que si le cluster n'a pas de tablespaces supplémentaires et que le streaming WAL n'est pas utilisé.

-i ancien_fichier_manifeste
--incremental=ancien_fichier_manifeste

Effectue une sauvegarde incrémentielle. Le manifeste de sauvegarde pour la sauvegarde de référence doit être fourni, et sera téléchargé sur le serveur, qui répondra en envoyant la sauvegarde incrémentielle demandée.

-R
--write-recovery-conf

Crée un fichier standby.signal

et ajoute les paramètres de connexion au fichier postgresql.auto.conf dans le répertoire cible (ou dans le fichier d'archive de base lors de l'utilisation du format tar). Cela facilite la configuration d'un serveur en attente utilisant les résultats de la sauvegarde.

Le fichier postgresql.auto.conf enregistrera les paramètres de connexion et, si spécifié, l'emplacement de réplication que pg_basebackup utilise, de sorte que la réplication en streaming et la synchronisation des emplacements de réplication logique utiliseront les mêmes paramètres plus tard. Le nom de la base de données sera enregistré uniquement si le nom de la base de données a été explicitement spécifié dans la chaîne de connexion ou la variable d'environnement.

-t cible
--target=cible

Indique au serveur où placer la sauvegarde de base. La cible par défaut est client, ce qui spécifie que la sauvegarde doit être envoyée à la machine où pg_basebackup est en cours d'exécution. Si la cible est plutôt définie sur server:/quelque/chemin, la sauvegarde sera stockée sur la machine où se trouve le serveur dans le répertoire /quelque/chemin. Le stockage d'une sauvegarde sur le serveur nécessite des privilèges de superutilisateur ou les privilèges du rôle pg_write_server_files. Si la cible est définie sur blackhole, le contenu est supprimé et n'est stocké nulle part. Ceci ne doit être utilisé qu'à des fins de test, car vous n'obtiendrez pas de sauvegarde réelle.

Comme le streaming WAL est implémenté par pg_basebackup plutôt que par le serveur, cette option ne peut pas être utilisée conjointement avec -Xstream. Comme c'est le cas par défaut, lorsque cette option est spécifiée, vous devez également spécifier soit -Xfetch soit -Xnone.

-T ancien_chemin=nouveau_chemin
--tablespace-mapping=ancien_chemin=nouveau_chemin

Déplace le tablespace situé dans le répertoire ancien_chemin vers nouveau_chemin pendant la sauvegarde. Pour être efficace, ancien_chemin doit correspondre exactement à la spécification du chemin du tablespace tel qu'il est défini sur le serveur source. (Mais ce n'est pas une erreur s'il n'y a pas de tablespace dans ancien_chemin sur le serveur source.) Pendant ce temps, nouveau_chemin est un répertoire dans le système de fichiers de l'hôte récepteur. Comme pour le répertoire cible principal, nouveau_chemin n'a pas besoin d'exister déjà, mais s'il existe, il doit être vide. ancien_chemin et nouveau_chemin doivent être des chemins absolus. Si l'un des chemins doit contenir un signe égal (=), faites-le précéder d'une barre oblique inverse. Cette option peut être spécifiée plusieurs fois pour plusieurs tablespaces.

Si un tablespace est déplacé de cette manière, les liens symboliques à l'intérieur du répertoire de données principal sont mis à jour pour pointer vers le nouvel emplacement. Ainsi, le nouveau répertoire de données est prêt à être utilisé pour une nouvelle instance de serveur avec tous les tablespaces dans les emplacements mis à jour.

Actuellement, cette option ne fonctionne qu'avec le format de sortie plain ; elle est ignorée si le format tar est sélectionné.

--waldir=repertoire_wal

Définit le répertoire dans lequel écrire les fichiers WAL (write-ahead log). Par défaut, les fichiers WAL sont placés dans le sous-répertoire pg_wal du répertoire cible, mais cette option permet de les placer ailleurs. waldir doit être un chemin absolu. Comme pour le répertoire cible principal, waldir n'a pas besoin d'exister au préalable, mais s'il existe, il doit être vide. Cette option ne peut être spécifiée que lorsque la sauvegarde est au format texte brut.

-X méthode
--wal-method=méthode

Inclut les fichiers WAL (write-ahead log) requis dans la sauvegarde. Cela inclura tous les journaux d'écriture anticipée générés pendant la sauvegarde. Sauf si la méthode none est spécifiée, il est possible de démarrer un postmaster dans le répertoire cible sans avoir besoin de consulter l'archive WAL, rendant ainsi la sortie une sauvegarde complètement autonome.

Les méthodes suivantes pour collecter les journaux d'écriture anticipée sont prises en charge :

n
none

Ne pas inclure les journaux d'écriture anticipée dans la sauvegarde.

f
fetch

Les fichiers journaux d'écriture anticipée sont collectés à la fin de la sauvegarde. Par conséquent, il est nécessaire que le paramètre wal_keep_size du serveur source soit suffisamment élevé pour que les données de journal requises ne soient pas supprimées avant la fin de la sauvegarde. Si les données de journal requises ont été recyclées avant leur transfert, la sauvegarde échouera et sera inutilisable.

Lorsque le format tar est utilisé, les fichiers journaux d'écriture anticipée seront inclus dans le fichier base.tar.

s
stream

Diffuse les données des journaux d'écriture anticipée pendant que la sauvegarde est en cours. Cette méthode ouvrira une deuxième connexion au serveur et commencera à diffuser le journal d'écriture anticipée en parallèle tout en exécutant la sauvegarde. Par conséquent, elle nécessitera deux connexions de réplication et non une seule. Tant que le client peut suivre les données du journal d'écriture anticipée, l'utilisation de cette méthode ne nécessite pas de journaux d'écriture anticipée supplémentaires à sauvegarder sur le serveur source.

Lorsque le format tar est utilisé, les fichiers journaux d'écriture anticipée seront écrits dans un fichier séparé nommé pg_wal.tar (si le serveur est une version antérieure à 10, le fichier sera nommé pg_xlog.tar).

Cette valeur est la valeur par défaut.

-z
--gzip

Active la compression gzip des fichiers tar de sortie, avec le niveau de compression par défaut. La compression n'est disponible que lors de l'utilisation du format tar, et le suffixe .gz sera automatiquement ajouté à tous les noms de fichiers tar.

-Z niveau
-Z [{client|server}-]méthode[:détail]
--compress=niveau
--compress=[{client|server}-]méthode[:détail]

Demande la compression de la sauvegarde. Si client ou serveur est inclus, cela spécifie où la compression doit être effectuée. La compression côté serveur réduira la bande passante de transfert mais augmentera la consommation CPU du serveur. La valeur par défaut est client, sauf lorsque --target est utilisé. Dans ce cas, la sauvegarde n'est pas envoyée au client, donc seule la compression côté serveur est logique. Lorsque -Xstream, qui est la valeur par défaut, est utilisé, la compression côté serveur ne sera pas appliquée au WAL. Pour compresser le WAL, utilisez la compression côté client ou spécifiez -Xfetch.

La méthode de compression peut être définie sur gzip, lz4, zstd, none pour aucune compression ou un entier (aucune compression si 0, gzip si supérieur à 0). Une chaîne de détails de compression peut éventuellement être spécifiée. Si la chaîne de détails est un entier, elle spécifie le niveau de compression. Sinon, elle doit être une liste d'éléments séparés par des virgules, chacun sous la forme mot-clé ou mot-clé=valeur. Actuellement, les mots-clés pris en charge sont level, long et workers. La chaîne de détails ne peut pas être utilisée lorsque la méthode de compression est spécifiée comme un simple entier.

Si aucun niveau de compression n'est spécifié, le niveau de compression par défaut sera utilisé. Si seul un niveau est spécifié sans mentionner d'algorithme, la compression gzip sera utilisée si le niveau est supérieur à 0, et aucune compression ne sera utilisée si le niveau est 0.

Lorsque le format tar est utilisé avec gzip, lz4 ou zstd, le suffixe .gz, .lz4 ou .zst, respectivement, sera automatiquement ajouté à tous les noms de fichiers tar. Lorsque le format texte brut est utilisé, la compression côté client ne peut pas être spécifiée, mais il est toujours possible de demander une compression côté serveur. Si cela est fait, le serveur compressera la sauvegarde pour la transmission, et le client la décompressera et l'extraira.

Lorsque cette option est utilisée en combinaison avec -Xstream, pg_wal.tar sera compressé à l'aide de gzip si la compression gzip côté client est sélectionnée, mais ne sera pas compressé si un autre algorithme de compression est sélectionné, ou si la compression côté serveur est sélectionnée.

Les options de ligne de commande suivantes contrôlent la génération de la sauvegarde et l'invocation du programme :

-c {fast|spread}
--checkpoint={fast|spread}

Définit le mode de point de contrôle sur fast (immédiat) ou spread (la valeur par défaut) (voir Section 25.3.4).

-C
--create-slot

Spécifie que le slot de réplication nommé par l'option --slot doit être créé avant de démarrer la sauvegarde. Une erreur est générée si le slot existe déjà.

-l étiquette
--label=étiquette

Définit l'étiquette de la sauvegarde. Si aucune n'est spécifiée, une valeur par défaut de « pg_basebackup base backup » sera utilisée.

-n
--no-clean

Par défaut, lorsque pg_basebackup s'arrête avec une erreur, il supprime tous les répertoires qu'il aurait pu créer avant de découvrir qu'il ne peut pas terminer le travail (par exemple, le répertoire cible et le répertoire des journaux d'écriture anticipée). Cette option empêche le nettoyage et est donc utile pour le débogage.

Notez que les répertoires de tablespaces ne sont nettoyés dans aucun des cas.

-N
--no-sync

Par défaut, pg_basebackup attend que tous les fichiers soient écrits en toute sécurité sur le disque. Cette option fait que pg_basebackup revient sans attendre, ce qui est plus rapide, mais signifie qu'un crash ultérieur du système d'exploitation peut laisser la sauvegarde de base corrompue. En général, cette option est utile pour les tests mais ne doit pas être utilisée lors de la création d'une installation de production.

-P
--progress

Active le rapport de progression. L'activer fournira un rapport de progression approximatif pendant la sauvegarde. Comme la base de données peut changer pendant la sauvegarde, il ne s'agit que d'une approximation et elle peut ne pas se terminer exactement à 100%. En particulier, lorsque le journal WAL est inclus dans la sauvegarde, la quantité totale de données ne peut pas être estimée à l'avance, et dans ce cas, la taille cible estimée augmentera une fois qu'elle dépassera l'estimation totale sans WAL.

-r taux
--max-rate=taux

Définit le taux de transfert maximum auquel les données sont collectées à partir du serveur source. Cela peut être utile pour limiter l'impact de pg_basebackup sur le serveur. Les valeurs sont en kilooctets par seconde. Utilisez un suffixe M pour indiquer des mégaoctets par seconde. Un suffixe k est également accepté et n'a aucun effet. Les valeurs valides sont comprises entre 32 kilooctets par seconde et 1024 mégaoctets par seconde.

Cette option affecte toujours le transfert du répertoire de données. Le transfert des fichiers WAL n'est affecté que si la méthode de collecte est fetch.

-S nom_slot
--slot=nom_slot

Cette option ne peut être utilisée qu'en conjonction avec -X stream. Elle fait en sorte que le streaming WAL utilise le slot de réplication spécifié. Si la sauvegarde de base est destinée à être utilisée comme un standby de réplication en continu à l'aide d'un slot de réplication, le standby devrait alors utiliser le même nom de slot de réplication que primary_slot_name. Cela garantit que le serveur primaire ne supprime aucune donnée WAL nécessaire entre la fin de la sauvegarde de base et le début de la réplication en continu sur le nouveau standby.

Le slot de réplication spécifié doit exister, sauf si l'option -C est également utilisée.

Si cette option n'est pas spécifiée et que le serveur prend en charge les slots de réplication temporaires (version 10 et ultérieures), un slot de réplication temporaire est automatiquement utilisé pour le streaming WAL.

--sync-method=méthode

Lorsqu'elle est définie sur fsync, ce qui est la valeur par défaut, pg_basebackup ouvrira et synchronisera récursivement tous les fichiers du répertoire de sauvegarde. Lorsque le format texte brut est utilisé, la recherche de fichiers suivra les liens symboliques pour le répertoire WAL et chaque tablespace configuré.

Sous Linux, syncfs peut être utilisé à la place pour demander au système d'exploitation de synchroniser l'intégralité du système de fichiers contenant le répertoire de sauvegarde. Lorsque le format texte brut est utilisé, pg_basebackup synchronisera également les systèmes de fichiers contenant les fichiers WAL et chaque tablespace. Voir recovery_init_sync_method pour des informations sur les mises en garde à prendre en compte lors de l'utilisation de syncfs.

Cette option n'a aucun effet lorsque --no-sync est utilisé.

-v
--verbose

Active le mode verbeux. Affichera des étapes supplémentaires pendant le démarrage et l'arrêt, ainsi que le nom exact du fichier en cours de traitement si le rapport de progression est également activé.

--manifest-checksums=algorithme

Spécifie l'algorithme de somme de contrôle qui doit être appliqué à chaque fichier inclus dans le manifeste de sauvegarde. Actuellement, les algorithmes disponibles sont NONE, CRC32C, SHA224, SHA256, SHA384 et SHA512. La valeur par défaut est CRC32C.

Si NONE est sélectionné, le manifeste de sauvegarde ne contiendra aucune somme de contrôle. Sinon, il contiendra une somme de contrôle de chaque fichier de la sauvegarde en utilisant l'algorithme spécifié. De plus, le manifeste contiendra toujours une somme de contrôle SHA256 de son propre contenu. Les algorithmes SHA sont considérablement plus gourmands en CPU que CRC32C, donc la sélection de l'un d'entre eux peut augmenter le temps nécessaire pour terminer la sauvegarde.

L'utilisation d'une fonction de hachage SHA fournit un condensé cryptographiquement sûr de chaque fichier pour les utilisateurs qui souhaitent vérifier que la sauvegarde n'a pas été altérée, tandis que l'algorithme CRC-32C fournit une somme de contrôle beaucoup plus rapide à calculer ; il est efficace pour détecter les erreurs dues à des modifications accidentelles, mais il n'est pas résistant aux modifications malveillantes. Notez que, pour être utile contre un adversaire ayant accès à la sauvegarde, le manifeste de sauvegarde devrait être stocké en toute sécurité ailleurs ou vérifié d'une autre manière pour ne pas avoir été modifié depuis la prise de la sauvegarde.

pg_verifybackup(1) peut être utilisé pour vérifier l'intégrité d'une sauvegarde par rapport au manifeste de sauvegarde.

--manifest-force-encode

Force l'encodage hexadécimal de tous les noms de fichiers dans le manifeste de sauvegarde. Si cette option n'est pas spécifiée, seuls les noms de fichiers non-UTF8 sont encodés en hexadécimal. Cette option est principalement destinée à tester si les outils qui lisent un fichier manifeste de sauvegarde fonctionnent correctement.

GÉRER CE CAS

--no-estimate-size

Empêche le serveur d'estimer la quantité totale de données de sauvegarde qui sera transmise en flux, ce qui entraîne la valeur NULL pour la colonne `backup_total` dans la vue `pg_stat_progress_basebackup`.

Sans cette option, la sauvegarde commencera par énumérer la taille de la base de données entière, puis reviendra pour envoyer le contenu réel. Cela peut prolonger légèrement la durée de la sauvegarde, et en particulier, il faudra plus de temps avant que les premières données ne soient envoyées. Cette option est utile pour éviter ce temps d'estimation s'il est trop long.

Cette option n'est pas autorisée lorsque l'on utilise --progress.

--no-manifest

Désactive la génération d'un manifeste de sauvegarde. Si cette option n'est pas spécifiée, le serveur générera et enverra un manifeste de sauvegarde qui pourra être vérifié à l'aide de pg_verifybackup(1). Le manifeste est une liste de tous les fichiers présents dans la sauvegarde, à l'exception des fichiers WAL qui pourraient être inclus. Il stocke également la taille, l'heure de dernière modification et une somme de contrôle facultative pour chaque fichier.

--no-slot

Empêche la création d'une slot de réplication temporaire pour la sauvegarde.

Par défaut, si le streaming des journaux est sélectionné mais qu'aucun nom de slot n'est fourni avec l'option -S, alors un slot de réplication temporaire est créé (s'il est supporté par le serveur source).

L'objectif principal de cette option est de permettre de prendre une sauvegarde de base lorsqu'il n'y a pas de slots de réplication libres sur le serveur. L'utilisation d'un slot de réplication est presque toujours préférable, car elle empêche que les WAL nécessaires ne soient supprimés par le serveur pendant la sauvegarde.

--no-verify-checksums

Désactive la vérification des sommes de contrôle, si elles sont activées sur le serveur à partir duquel la sauvegarde de base est prise.

Par défaut, les sommes de contrôle sont vérifiées et les échecs de sommes de contrôle entraîneront un statut de sortie non nul. Cependant, la sauvegarde de base ne sera pas supprimée dans un tel cas, comme si l'option --no-clean avait été utilisée. Les échecs de vérification des sommes de contrôle seront également signalés dans la vue `pg_stat_database`.

Les options de ligne de commande suivantes contrôlent la connexion au serveur source :

-d connstr
--dbname=connstr

Spécifie les paramètres utilisés pour se connecter au serveur, sous forme de chaîne de connexion ; ceux-ci remplaceront toute option de ligne de commande conflictuelle.

Cette option est appelée `--dbname` par souci de cohérence avec d'autres applications clientes, mais comme `pg_basebackup` ne se connecte à aucune base de données particulière du cluster, tout nom de base de données inclus dans la chaîne de connexion sera ignoré par le serveur. Cependant, un nom de base de données fourni de cette manière remplace le nom de base de données par défaut (`replication`) aux fins de recherche du mot de passe de la connexion de réplication dans `~/.pgpass`. De même, les intergiciels ou les proxys utilisés pour se connecter à PostgreSQL pourraient utiliser ce nom à des fins telles que le routage des connexions. Le nom de la base de données peut également être utilisé par la synchronisation des slots de réplication logique.

-h host
--host=host

Spécifie le nom d'hôte de la machine sur laquelle le serveur s'exécute. Si la valeur commence par une barre oblique, elle est utilisée comme répertoire pour un socket de domaine Unix. La valeur par défaut est prise de la variable d'environnement PGHOST, si elle est définie, sinon une tentative de connexion via un socket de domaine Unix est effectuée.

-p port
--port=port

Spécifie le port TCP ou l'extension du fichier de socket de domaine Unix local sur lequel le serveur écoute les connexions. Par défaut, la variable d'environnement PGPORT, si elle est définie, ou une valeur par défaut compilée.

-s interval
--status-interval=interval

Spécifie le nombre de secondes entre les paquets de statut envoyés au serveur source. Des valeurs plus petites permettent une surveillance plus précise de la progression de la sauvegarde depuis le serveur. Une valeur de zéro désactive complètement les mises à jour de statut périodiques, bien qu'une mise à jour soit toujours envoyée lorsqu'elle est demandée par le serveur, pour éviter les déconnexions basées sur un délai d'attente. La valeur par défaut est de 10 secondes.

-U username
--username=username

Spécifie le nom d'utilisateur pour se connecter.

-w
--no-password

Empêche la demande de mot de passe. Si le serveur nécessite une authentification par mot de passe et qu'un mot de passe n'est pas disponible par d'autres moyens, tels qu'un fichier .pgpass, la tentative de connexion échouera. Cette option peut être utile dans les travaux par lots et les scripts où aucun utilisateur n'est présent pour entrer un mot de passe.

-W
--password

Force `pg_basebackup` à demander un mot de passe avant de se connecter au serveur source.

Cette option n'est jamais essentielle, car `pg_basebackup` demandera automatiquement un mot de passe si le serveur exige une authentification par mot de passe. Cependant, `pg_basebackup` gaspillera une tentative de connexion pour découvrir que le serveur veut un mot de passe. Dans certains cas, il est utile de taper -W pour éviter la tentative de connexion supplémentaire.

D'autres options sont également disponibles :

-V
--version

Affiche la version de `pg_basebackup` et quitte.

-?
--help

Affiche l'aide sur les arguments de la ligne de commande de `pg_basebackup` et quitte.

ENVIRONNEMENT

Cet utilitaire, comme la plupart des autres utilitaires PostgreSQL, utilise les variables d'environnement supportées par libpq (voir la Section 32.15).

La variable d'environnement PG_COLOR spécifie s'il faut utiliser la couleur dans les messages de diagnostic. Les valeurs possibles sont `always`, `auto` et `never`.

NOTES

Au début de la sauvegarde, un point de contrôle doit être effectué sur le serveur source. Cela peut prendre un certain temps (surtout si l'option `--checkpoint=fast` n'est pas utilisée), pendant lequel `pg_basebackup` semblera inactif.

La sauvegarde inclura tous les fichiers du répertoire de données et des tablespaces, y compris les fichiers de configuration et tous les fichiers supplémentaires placés dans le répertoire par des tiers, à l'exception de certains fichiers temporaires gérés par PostgreSQL et des fichiers du système d'exploitation. Cependant, seuls les fichiers et répertoires réguliers sont copiés, à l'exception des liens symboliques utilisés pour les tablespaces qui sont préservés. Les liens symboliques pointant vers certains répertoires connus de PostgreSQL sont copiés comme des répertoires vides. Les autres liens symboliques et les fichiers de périphériques spéciaux sont ignorés. Voir la Section 54.4 pour les détails précis.

En format simple (`plain`), les tablespaces seront sauvegardés dans le même chemin qu'ils ont sur le serveur source, à moins que l'option `--tablespace-mapping` ne soit utilisée. Sans cette option, l'exécution d'une sauvegarde de base en format simple sur le même hôte que le serveur ne fonctionnera pas si des tablespaces sont utilisés, car la sauvegarde devrait être écrite aux mêmes emplacements de répertoire que les tablespaces d'origine.

Lorsque le format tar est utilisé, il incombe à l'utilisateur de décompresser chaque fichier tar avant de démarrer un serveur PostgreSQL qui utilise les données. S'il y a des tablespaces supplémentaires, les fichiers tar pour ceux-ci doivent être décompressés aux bons endroits. Dans ce cas, les liens symboliques pour ces tablespaces seront créés par le serveur selon le contenu du fichier `tablespace_map` inclus dans le fichier `base.tar`.

`pg_basebackup` fonctionne avec des serveurs de la même version majeure ou d'une version antérieure, jusqu'à la 9.1. Cependant, le mode de streaming WAL (`-X stream`) ne fonctionne qu'avec les serveurs de version 9.3 et ultérieures, le format tar (`--format=tar`) ne fonctionne qu'avec les serveurs de version 9.5 et ultérieures, et la sauvegarde incrémentielle (`--incremental`) ne fonctionne qu'avec les serveurs de version 17 et ultérieures.

`pg_basebackup` conservera les permissions de groupe pour les fichiers de données si les permissions de groupe sont activées sur le cluster source.

EXEMPLES

Pour créer une sauvegarde de base du serveur `mydbserver` et la stocker dans le répertoire local `/usr/local/pgsql/data` :

$ pg_basebackup -h mydbserver -D /usr/local/pgsql/data

Pour créer une sauvegarde du serveur local avec un fichier tar compressé pour chaque tablespace, et la stocker dans le répertoire `backup`, en affichant un rapport de progression pendant l'exécution :

$ pg_basebackup -D backup -Ft -z -P

Pour créer une sauvegarde d'une base de données locale à tablespace unique et la compresser avec bzip2 :

$ pg_basebackup -D - -Ft -X fetch | bzip2 > backup.tar.bz2

(Cette commande échouera s'il y a plusieurs tablespaces dans la base de données.)

Pour créer une sauvegarde d'une base de données locale où le tablespace dans `/opt/ts` est déplacé vers `./backup/ts` :

$ pg_basebackup -D backup/data -T /opt/ts=$(pwd)/backup/ts

Pour créer une sauvegarde du serveur local avec un fichier tar pour chaque tablespace, compressé avec gzip au niveau 9, stocké dans le répertoire `backup` :

$ pg_basebackup -D backup -Ft --compress=gzip:9

NOM

pg_basebackup — sauvegarde de base de données PostgreSQL en ligne

SYNTAXE

pg_basebackup [-a | --progress] [-B | --wal-method=method] [-D | --dir=directory] [-e | --replication] [-E | --encoding=encoding] [-f | --format=format] [-F | --write-recovery-conf] [-i | --ignore-missing-on-error] [-J | --jobs=num-jobs] [-P | --progress] [-R | --write-recovery-conf] [-v | --verbose] [-V | --version] [-w | --no-password] [-W | --password] [--connect=connstr] [--create-slot] [--slot=slotname] [--stop-backup] [--sync-option=option] [--take-emptyset] [--target-gp-session=session] [--target-gp-conn=connstr] [--target-gp-mode=mode] [--target-gp-copy=copy] [-X | --wal-method=method] [-z | --compress=level] [-Z | --compress=level] [connection-option...] [option...]

DESCRIPTION

pg_basebackup est un utilitaire PostgreSQL qui permet de créer une copie physique de tous les fichiers de données de PostgreSQL, ainsi que tous les journaux de transactions (WAL) nécessaires pour rendre cette sauvegarde cohérente. La sauvegarde est envoyée via la connexion de réplication. Le serveur doit être démarré et les paramètres de réplication doivent être correctement configurés.

Les fichiers de la sauvegarde sont écrits dans le répertoire spécifié par l'option -D. Si ce répertoire n'existe pas, il sera créé. La configuration du serveur PostgreSQL (postgresql.conf, pg_hba.conf, etc.) n'est pas copiée. Si vous avez besoin de ces fichiers, copiez-les manuellement.

pg_basebackup est un outil conçu pour être utilisé dans le cadre de la réplication physique. Pour plus d'informations sur la réplication, consultez le manuel PostgreSQL.

OPTIONS

-D directory
--dir=directory
Spécifie le répertoire de destination où les fichiers de sauvegarde seront écrits. Ce répertoire doit être vide ou inexistant. S'il est inexistant, il sera créé.
-F format
--format=format
Spécifie le format des fichiers de sauvegarde. Les formats possibles sont :
  • p (plain) : format non compressé (par défaut).
  • t (tar) : format tar, qui peut être compressé.
-X method
--wal-method=method
Spécifie comment les fichiers WAL nécessaires à la récupération de la sauvegarde seront inclus. Les méthodes possibles sont :
  • n (none) : aucun fichier WAL n'est inclus. La sauvegarde peut ne pas être récupérable.
  • f (fetch) : les fichiers WAL sont récupérés après la création de la sauvegarde.
  • s (stream) : les fichiers WAL sont transmis en continu pendant la création de la sauvegarde.
La méthode stream est généralement préférable car elle garantit que tous les WAL sont sauvegardés.
-c method
--compress=level
Spécifie le niveau de compression pour le format tar. La valeur level doit être comprise entre 0 (pas de compression) et 9 (compression maximale).
-v
--verbose
Active le mode verbeux, affichant plus d'informations pendant l'exécution.
-P
--progress
Affiche la progression de la sauvegarde.
-w
--no-password
Ne jamais demander de mot de passe. Si le serveur exige une authentification par mot de passe, l'opération échouera.
-W
--password
Demander un mot de passe avant de se connecter au serveur.
--connect=connstr
Chaîne de connexion pour se connecter au serveur PostgreSQL.
--create-slot
Crée un slot de réplication sur le serveur avant de démarrer la sauvegarde. Nécessite que le slot spécifié par --slot n'existe pas.
--slot=slotname
Spécifie le nom du slot de réplication à utiliser ou à créer.
--stop-backup
Arrête une sauvegarde en cours sur le serveur.

Les options de connexion standard de PostgreSQL sont également disponibles (-h host, -p port, -U user, etc.).

EXEMPLES

Sauvegarder la base de données sur le serveur local dans le répertoire /chemin/vers/sauvegarde en utilisant la méthode de streaming WAL : 

pg_basebackup -D /chemin/vers/sauvegarde -P -X stream

Sauvegarder la base de données sur un serveur distant et la compresser au format tar : 

pg_basebackup -h serveur.exemple.com -U utilisateur -D /chemin/vers/sauvegarde -F t -z -v
