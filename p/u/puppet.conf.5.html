Paramètres de configuration

  • Chacun de ces paramètres peut être spécifié dans puppet.conf ou en ligne de commande.
  • Puppet Enterprise (PE) et Puppet open source partagent les paramètres de configuration documentés ici. Cependant, les valeurs par défaut du PE diffèrent des valeurs par défaut de l'open source pour certains paramètres, tels que node_terminus, storeconfigs, always_retry_plugins, disable18n, environment_timeout (lorsque Code Manager est activé), et le paramètre JRuby max-active-instances du serveur Puppet. Pour vérifier les valeurs par défaut de la configuration du PE, consultez le fichier puppet.conf ou pe-puppet-server.conf après l'installation.
  • Lorsque vous utilisez des paramètres booléens en ligne de commande, utilisez --setting et --no-setting au lieu de --setting (true|false). (Utiliser --setting false entraîne l'erreur "Error: Could not parse application options: needless argument".)
  • Les paramètres peuvent être interpolés comme $variables dans d'autres paramètres ; $environment est spécial, en ce sens que puppet master interpolera l'environnement de chaque nœud agent au lieu du sien.
  • Les valeurs multiples doivent être spécifiées sous forme de listes séparées par des virgules ; les répertoires multiples doivent être séparés par le séparateur de chemin système (généralement un deux-points).
  • Les paramètres représentant des intervalles de temps doivent être spécifiés au format durée : un entier immédiatement suivi de l'une des unités 'y' (années de 365 jours), 'd' (jours), 'h' (heures), 'm' (minutes) ou 's' (secondes). L'unité ne peut pas être combinée avec d'autres unités et vaut secondes par défaut si omise. Exemples : '3600' équivaut à '1h' (une heure), et '1825d' équivaut à '5y' (5 ans).
  • Si vous utilisez le paramètre splay, notez que la période d'attente change à chaque redémarrage de l'agent Puppet.
  • Les paramètres qui prennent un seul fichier ou répertoire peuvent éventuellement définir le propriétaire, le groupe et le mode de leur valeur : rundir = $vardir/run { owner = puppet, group = puppet, mode = 644 }
  • Les exécutables Puppet ignorent tout paramètre qui n'est pas pertinent pour leur fonction.

Voir le guide de configuration https://puppet.com/docs/puppet/latest/config_about_settings.html pour plus de détails.

allow_duplicate_certs

Permet ou non à une nouvelle demande de certificat d'écraser une demande de certificat existante. Si vrai, l'ancien certificat doit être nettoyé à l'aide de puppetserver ca clean, et la nouvelle demande signée à l'aide de puppetserver ca sign.

•
Par défaut : false

allow_pson_serialization

Permet ou non la sérialisation PSON. Lorsqu'il ne parvient pas à sérialiser en JSON ou dans d'autres formats, Puppet se rabat sur PSON. Cette option affecte les réponses du service de gestion de configuration de Puppet Server et le processus par lequel l'agent enregistre son catalogue mis en cache. Avec une valeur par défaut de false, cette option est utile pour empêcher la perte de données car les données riches ne peuvent pas être sérialisées via PSON.

•
Par défaut : false

always_retry_plugins

Affecte la manière dont nous mettons en cache les tentatives de chargement des types de ressources et des fonctionnalités Puppet. Si vrai, les appels à Puppet.type.<type>? et Puppet.feature.<feature>? tenteront toujours de charger le type ou la fonctionnalité (ce qui peut être une opération coûteuse) à moins qu'il n'ait déjà été chargé avec succès. Cela permet à une seule exécution d'agent, par exemple, d'installer un paquet qui fournit les capacités sous-jacentes pour un type ou une fonctionnalité, puis de charger ce type ou cette fonctionnalité plus tard pendant la même exécution (même si le type ou la fonctionnalité avait été testé précédemment et n'était pas disponible).

Si ce paramètre est défini sur faux, les types et les fonctionnalités ne seront vérifiés qu'une seule fois, et s'ils ne sont pas disponibles, le résultat négatif sera mis en cache et retourné pour toutes les tentatives ultérieures de chargement du type ou de la fonctionnalité. Ce comportement est presque toujours approprié pour le serveur et peut entraîner une amélioration significative des performances pour les types et les fonctionnalités qui sont vérifiés fréquemment.

•
Par défaut : true

autosign

Indique si (et comment) les demandes de certificats doivent être automatiquement signées. Ce paramètre n'est pertinent que sur un serveur Puppet agissant en tant qu'autorité de certification (CA).

Les valeurs valides sont true (signe automatiquement toutes les demandes de certificat ; non recommandé), false (désactive la signature automatique des certificats) ou le chemin absolu vers un fichier.

Le fichier spécifié dans ce paramètre peut être soit un fichier de configuration, soit un exécutable de politique personnalisée. Puppet déterminera automatiquement de quoi il s'agit : si l'utilisateur Puppet (voir le paramètre user) peut exécuter le fichier, il sera traité comme un exécutable de politique ; sinon, il sera traité comme un fichier de configuration.

Si un exécutable de politique personnalisée est configuré, le serveur Puppet CA l'exécutera chaque fois qu'il recevra une CSR. L'exécutable recevra le CN du sujet de la demande comme argument de ligne de commande, et le contenu de la CSR au format PEM sur stdin. Il doit se terminer avec le statut 0 si le certificat doit être signé automatiquement et un statut non nul s'il ne doit pas l'être.

Si une demande de certificat n'est pas signée automatiquement, elle persistera pour examen. Un utilisateur administrateur peut utiliser la commande puppetserver ca sign pour la signer manuellement, ou peut supprimer la demande.

Pour plus d'informations sur les fichiers de configuration d'autosign, consultez le guide des fichiers de configuration de Puppet https://puppet.com/docs/puppet/latest/config_file_autosign.html.

•
Par défaut : $confdir/autosign.conf

ca_refresh_interval

À quelle fréquence l'agent Puppet rafraîchit ses certificats CA locaux. Par défaut, les certificats CA sont rafraîchis toutes les 24 heures. Si un intervalle différent est spécifié, l'agent rafraîchit ses certificats CA lors de la prochaine exécution de l'agent si le temps écoulé depuis le dernier rafraîchissement des certificats dépasse la durée spécifiée.

En général, l'intervalle doit être supérieur à la valeur de runinterval. Définir la valeur de ca_refresh_interval à 0 ou à une valeur égale ou inférieure à runinterval provoque le rafraîchissement des certificats CA à chaque exécution.

Si l'agent télécharge de nouveaux certificats CA, il les utilise pour les requêtes réseau ultérieures. Si la requête de rafraîchissement échoue ou si les certificats CA n'ont pas changé sur le serveur, alors l'exécution de l'agent continuera à utiliser les certificats CA locaux qu'il possède déjà. Ce réglage peut être un intervalle de temps en secondes (30 ou 30s), minutes (30m), heures (6h), jours (2d), ou années (5y).

certificate_revocation

Indique si la vérification de la révocation des certificats doit être activée et quel niveau de vérification doit être effectué.

Lorsque la révocation des certificats est activée, Puppet s'attend à ce que le contenu de sa CRL soit une ou plusieurs CRLs encodées en PEM concaténées. Lors de l'utilisation d'un bundle de certificats, les CRLs de toutes les CA dans la chaîne de confiance doivent être incluses dans le fichier crl. La chaîne doit être ordonnée de la moins autoritaire à la plus autoritaire, la première CRL listée étant pour la racine de la chaîne et la dernière pour la CA feuille.

Lorsque certificate_revocation est défini sur ´true´ ou ´chain´, Puppet s'assure que chaque CA dans la chaîne de confiance n'a pas été révoquée par sa CA émettrice.

Lorsque certificate_revocation est défini sur ´leaf´, Puppet vérifie les certificats par rapport à la liste de révocation de la CA émettrice, mais il ne vérifie pas le statut de révocation de la CA émettrice ou de toute CA supérieure dans la chaîne de confiance.

Lorsque certificate_revocation est défini sur ´false´, Puppet désactive toute vérification de révocation de certificat et ne tente pas de télécharger la CRL.

•
Défaut: chain

certname

Le nom à utiliser lors du traitement des certificats. Lorsqu'un nœud demande un certificat au serveur CA Puppet, il utilise la valeur du réglage certname comme CN Sujet demandé.

C'est le nom utilisé lors de la gestion des permissions d'un nœud dans le fichier auth.conf de Puppet Server https://puppet.com/docs/puppetserver/latest/config_file_auth.html. Dans la plupart des cas, il est également utilisé comme nom du nœud lors de la mise en correspondance des définitions de nœuds https://puppet.com/docs/puppet/latest/lang_node_definitions.html et lors de la demande de données à un ENC. (Ceci peut être modifié avec les réglages node_name_value et node_name_fact, bien que vous ne devriez le faire que si vous avez une raison impérieuse.)

Le certname d'un nœud est disponible dans les manifests Puppet sous la forme $trusted[´certname´]. (Voir Facts et Variables Intégrées https://puppet.com/docs/puppet/latest/lang_facts_and_builtin_vars.html pour plus de détails.)

  • Pour une meilleure compatibilité, vous devriez limiter la valeur de certname à n'utiliser que des lettres minuscules, des chiffres, des points, des tirets bas et des traits d'union. (C'est-à-dire qu'il doit correspondre à /A[a-z0-9._-]+Z/.)
  • La valeur spéciale ca est réservée et ne peut pas être utilisée comme certname pour un nœud normal.
Note : Vous devez définir le certname dans la section principale du fichier puppet.conf. Le définir dans une section différente provoque des erreurs.

Par défaut, le nom de domaine complet du nœud.

Fréquence à laquelle Puppet agent rafraîchit sa liste locale de révocation de certificats (CRL). Par défaut, la CRL est rafraîchie toutes les 24 heures. csr_attributes

Un fichier facultatif contenant des attributs personnalisés à ajouter aux demandes de signature de certificat (CSR). Vous devez vous assurer que ce fichier n'existe pas sur votre serveur Puppet CA ; s'il existe, des extensions de certificat indésirables peuvent fuir dans les certificats créés avec la commande puppetserver ca generate.

S'il est présent, ce fichier doit être un hachage YAML contenant une clé custom_attributes et/ou une clé extension_requests. La valeur de chaque clé doit être un hachage, où chaque clé est un OID valide et chaque valeur est un objet qui peut être converti en chaîne.

Les attributs personnalisés peuvent être utilisés par la CA pour décider de signer ou non le certificat, mais sont ensuite supprimés. Les OID d'attributs peuvent être n'importe quelle valeur OID, à l'exception des attributs CSR standard (c'est-à-dire les attributs décrits dans la RFC 2985 section 5.4). Ceci est utile pour intégrer une clé pré-partagée pour les exécutables de politique d'autosignature (voir le paramètre autosign), souvent en utilisant l'OID 1.2.840.113549.1.9.7 ("mot de passe de défi").

Les demandes d'extension seront intégrées de manière permanente dans le certificat final. Les OID d'extension doivent être dans les arcs OID "ppRegCertExt" (1.3.6.1.4.1.34380.1.1), "ppPrivCertExt" (1.3.6.1.4.1.34380.1.2) ou "ppAuthCertExt" (1.3.6.1.4.1.34380.1.3). L'arc ppRegCertExt est réservé à quatre des données les plus courantes à intégrer : pp_uuid (.1), pp_instance_id (.2), pp_image_name (.3) et pp_preshared_key (.4) - dans le fichier YAML, ceux-ci peuvent être référencés par leurs noms descriptifs courts au lieu de leur OID complet. L'arc ppPrivCertExt n'est pas réglementé et peut être utilisé pour des extensions spécifiques au site. L'arc ppAuthCert est réservé à deux éléments de données à intégrer : pp_authorization (.1) et pp_auth_role (.13). Comme avec ppRegCertExt, dans le fichier YAML, ceux-ci peuvent être référencés par leur nom descriptif court au lieu de leur OID complet.

Indique s'il faut appliquer les catalogues en mode noop, ce qui permet à Puppet de simuler partiellement une exécution normale. Ce paramètre affecte puppet agent et puppet apply.

strict

Le niveau de stricte de puppet. Les valeurs autorisées sont :

  • warning - effectuer une validation supplémentaire, signaler comme avertissement

Le niveau de stricte concerne à la fois la sémantique du langage et la validation de l'évaluation à l'exécution. En plus de contrôler le comportement avec ce commutateur serveur principal, certains avertissements individuels peuvent également être contrôlés par le paramètre disable_warnings.

  • Retourner un hachage JSON avec les faits de confiance externes pour ce nœud.

waitforcert

À quelle fréquence puppet agent doit demander un certificat signé.

Lors du premier démarrage, puppet agent soumettra une demande de signature de certificat (CSR) au serveur nommé dans le paramètre ca_server (généralement le serveur Puppet principal) ; celle-ci peut être auto-signée, ou nécessiter une approbation humaine, selon la configuration du serveur CA.

Puppet agent ne peut pas appliquer de configurations tant que son certificat approuvé n'est pas disponible. Étant donné que le certificat peut ou non être disponible immédiatement, puppet agent essaiera de le récupérer à répétition à cet intervalle. Vous pouvez désactiver l'attente des certificats en spécifiant une durée de 0, ou une durée maximale d'attente dans le paramètre maxwaitforcert, auquel cas puppet agent se terminera s'il ne peut pas obtenir de certificat. Ce paramètre peut être un intervalle de temps en secondes (30 ou 30s), minutes (30m), heures (6h), jours (2d), ou années (5y).

Par défaut: 2m
