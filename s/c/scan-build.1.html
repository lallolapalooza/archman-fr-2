SCAN-BUILD(1) Manuel des commandes générales SCAN-BUILD(1)

NOM

scan-build — Analyseur statique Clang

SYNTAXE

scan-build [-ohkvV] [-analyze-headers] [-enable-checker [nom_du_verificateur]] [-disable-checker [nom_du_verificateur]] [--help] [--help-checkers] [--html-title [=titre]] [--keep-going] [-plist] [-plist-html] [--status-bugs] [--use-c++ [=chemin_compilateur]] [--use-cc [=chemin_compilateur]] [--view] [-constraints [modèle]] [-maxloop N] [-no-failure-reports] [-stats] [-store [modèle]] commande_de_construction [options_de_construction]

DESCRIPTION

scan-build est un script Perl qui invoque l'analyseur statique Clang. Les options utilisées par scan-build ou par l'analyseur apparaissent en premier, suivies de la commande_de_construction et de toutes les options_de_construction normalement utilisées pour construire le système cible.

L'analyseur statique utilise une longue liste d'algorithmes de vérification, voir VERIFICATEURS. La sortie peut être écrite au format standard .plist et/ou HTML.

Les options suivantes sont prises en charge :

-analyze-headers
Analyser également les fonctions dans les fichiers #inclus.
-enable-checker nom_du_verificateur, -disable-checker nom_du_verificateur
Activer/désactiver le nom_du_verificateur. Voir VERIFICATEURS.
-h, --help
Afficher ce message.
--help-checkers
Lister les vérificateurs par défaut, voir VERIFICATEURS.
--html-title[=titre]
Spécifier le titre utilisé sur les pages HTML générées. Un titre par défaut est généré si le titre n'est pas spécifié.
-k, --keep-going
Ajouter une option « continuer » à la commande_de_construction. Prend actuellement en charge make et xcodebuild. Il s'agit d'une option de commodité ; on peut spécifier ce comportement directement à l'aide des options de construction.
-o
Répertoire cible pour les fichiers de rapport HTML. Des sous-répertoires seront créés au besoin pour représenter des invocations distinctes de l'analyseur. Si cette option n'est pas spécifiée, un répertoire est créé dans /tmp (TMPDIR sur Mac OS X) pour stocker les rapports.
-plist
Exporter les résultats sous forme d'un ensemble de fichiers .plist. (Par défaut, la sortie de scan-build est un ensemble de fichiers HTML.)
-plist-html
Exporter les résultats sous forme d'un ensemble de fichiers HTML et .plist.
--status-bugs
Définir le code de sortie à 1 s'il a trouvé des bugs potentiels et 0 sinon. Par défaut, le code de sortie de scan-build est celui renvoyé par la commande_de_construction.
--use-c++[=chemin_compilateur]
Deviner le compilateur par défaut pour votre code C++ et Objective-C++. Utilisez cette option pour spécifier un compilateur alternatif.
--use-cc[=chemin_compilateur]
Deviner le compilateur par défaut pour votre code C et Objective-C. Utilisez cette option pour spécifier un compilateur alternatif.
-v
Sortie verbale de scan-build et de l'analyseur. Un deuxième et troisième v augmentent la verbosité.
-V, --view
Afficher les résultats de l'analyse dans un navigateur Web une fois la construction terminée.
-constraints [modèle]
Spécifier le moteur de contraintes utilisé par l'analyseur. Par défaut, le modèle « range » est utilisé. Spécifier « basic » utilise un modèle de contraintes plus simple et moins puissant, utilisé par checker-0.160 et versions antérieures.
-maxloop N
Spécifier le nombre de fois qu'un bloc peut être visité avant d'abandonner. La valeur par défaut est 4. Augmentez pour une couverture plus complète au détriment de la vitesse.
-no-failure-reports
Ne pas créer de sous-répertoire « failures » qui inclut les rapports de plantage de l'analyseur et les fichiers source prétraités.
-stats
Génère des statistiques de visite pour le projet en cours d'analyse.
-store [modèle]
Spécifier le modèle de stockage utilisé par l'analyseur. Par défaut, le modèle de stockage « region » est utilisé. « region » spécifie un modèle de stockage sensible aux champs. Les utilisateurs peuvent également spécifier « basic » qui est beaucoup moins précis mais peut analyser le code plus rapidement. « basic » était le modèle de stockage par défaut pour checker-0.221 et versions antérieures.

CODE DE SORTIE

scan-build renvoie la valeur renvoyée par la commande_de_construction, sauf si --status-bugs ou --keep-going est utilisé.

VERIFICATEURS

Les vérificateurs listés ci-dessous peuvent être activés/désactivés à l'aide des options -enable-checker et -disable-checker. Un groupe de vérificateurs par défaut est exécuté sauf s'il est explicitement désactivé. Le groupe de vérificateurs exact qui constitue le groupe par défaut dépend du système d'exploitation utilisé ; ils sont listés avec --help-checkers.

core.AdjustedReturnValue
Vérifie si la valeur de retour d'un appel de fonction est différente de celle attendue par l'appelant (par exemple, depuis des appels via des pointeurs de fonction).
core.AttributeNonNull
Vérifie les pointeurs nuls passés en arguments à une fonction dont les arguments sont marqués avec l'attribut « nonnull ».
core.CallAndMessage
Vérifie les erreurs logiques pour les appels de fonction et les expressions de message Objective-C (par exemple, arguments non initialisés, pointeurs de fonction nuls).
core.DivideZero
Vérifie les divisions par zéro.
core.NullDereference
Vérifie les déréférencements de pointeurs nuls.
core.StackAddressEscape
Vérifie que les adresses de la mémoire de la pile ne s'échappent pas de la fonction.
core.UndefinedBinaryOperatorResult
Vérifie les résultats indéfinis des opérateurs binaires.
core.VLASize
Vérifie les déclarations de VLA de taille indéfinie ou nulle.
core.builtin.BuiltinFunctions
Évalue les fonctions intégrées du compilateur, par exemple alloca

NOM

scan-build ― analyse le code source avec Clang Static Analyzer

SYNOPSIS

scan-build [options] make [make options]

DESCRIPTION

scan-build est un script wrapper qui exécute le compilateur Clang, analyse le code source et génère des rapports HTML des erreurs potentielles trouvées.

Il intercepte les appels à make et modifie la façon dont les compilations sont exécutées pour permettre au Clang Static Analyzer d'analyser le code. Les résultats sont généralement placés dans un répertoire nommé .scan-build dans le répertoire courant, ou dans un autre répertoire spécifié par l'option -o.

L'analyse peut prendre beaucoup de temps et produire beaucoup de données. Il est recommandé de l'exécuter dans un répertoire de construction isolé et potentiellement de spécifier des options de parallélisation pour make (par exemple, -j4) pour accélérer le processus de construction.

OPTIONS

Les options suivantes sont disponibles pour scan-build:

--clean
Supprime le répertoire des résultats de l'analyse (par défaut, .scan-build).
--enable-checker checker
Active l'analyse spécifique checker. Ceci est utile pour activer des analyseurs qui sont désactivés par défaut.
--disable-checker checker
Désactive l'analyse spécifique checker. Ceci est utile pour désactiver des analyseurs qui sont activés par défaut.
--config fichier
Charge la configuration d'analyse à partir du fichier.
-o répertoire
Définit le répertoire où seront stockés les rapports HTML. Si non spécifié, les rapports sont stockés dans le sous-répertoire .scan-build du répertoire courant.
-v
Augmente la verbosité de la sortie.
-h
Affiche un message d'aide.

EXIT STATUS

Le code de sortie de scan-build est celui de la commande make sous-jacente, sauf en cas d'erreur interne de scan-buildlui-même, auquel cas il renvoie 1.

CHECKERS

Voici une liste des analyseurs couramment disponibles. Certains d'entre eux peuvent être désactivés par défaut.

core.CallAndMessage
Détecte les appels de méthode et de fonction invalides.
core.DivideZero
Détecte les divisions par zéro potentielles.
core.DynamicMemoryAnalysis
Effectue une analyse de la mémoire dynamique.
core.Nonnull
Détecte l'utilisation de pointeurs nuls là où ils ne sont pas autorisés.
core.NullDereference
Détecte la déréférencement de pointeurs nuls.
core.StackAddressEscapes
Détecte les adresses de la pile qui s'échappent.
core.UndefinedBehavior
Détecte les comportements indéfinis selon la norme C/C++.
core.VlaBound
Détecte les tableaux de taille variable avec des limites invalides.
core.builtin.NoReturnFunctions
Évalue les fonctions « panic » qui sont connues pour ne pas retourner à l'appelant.
core.uninitialized.ArraySubscript
Vérifie les valeurs non initialisées utilisées comme indices de tableau.
core.uninitialized.Assign
Vérifie l'assignation de valeurs non initialisées.
core.uninitialized.Branch
Vérifie les valeurs non initialisées utilisées comme conditions de branchement.
core.uninitialized.CapturedBlockVariable
Vérifie les blocs qui capturent des valeurs non initialisées.
core.uninitialized.UndefReturn
Vérifie que les valeurs non initialisées ne sont pas retournées à l'appelant.
deadcode.DeadStores
Vérifie les valeurs stockées dans des variables qui ne sont jamais lues après.
debug.DumpCFG
Affiche les graphes de flot de contrôle (Control-Flow Graphs).
debug.DumpCallGraph
Affiche le graphe d'appels (Call Graph).
debug.DumpDominators
Imprime l'arbre de dominance pour un graphe de flot de contrôle donné.
debug.DumpLiveVars
Imprime les résultats de l'analyse des variables vivantes.
debug.Stats
Émet des avertissements avec des statistiques d'analyseur.
debug.TaintTest
Marque les symboles contaminés comme tels.
debug.ViewCFG
Visualise les graphes de flot de contrôle à l'aide de GraphViz.
debug.ViewCallGraph
Visualise le graphe d'appels à l'aide de GraphViz.
llvm.Conventions
Vérifie le code pour les conventions de la base de code LLVM.
osx.API
Vérifie l'utilisation correcte de diverses API Mac OS X.
osx.AtomicCAS
Évalue les appels aux fonctions OSAtomic.
osx.SecKeychainAPI
Vérifie l'utilisation correcte des API Secure Keychain.
osx.cocoa.AtSync
Vérifie les pointeurs nuls utilisés comme mutexes pour @synchronized.
osx.cocoa.ClassRelease
Vérifie l'envoi de « retain », « release » ou « autorelease » directement à une Classe.
osx.cocoa.IncompatibleMethodTypes
Avertit sur les signatures de méthodes Objective-C avec des incompatibilités de type.
osx.cocoa.NSAutoreleasePool
Avertit sur les utilisations sous-optimales de NSAutoreleasePool en mode GC Objective-C.
osx.cocoa.NSError
Vérifie l'utilisation des paramètres NSError**.
osx.cocoa.NilArg
Vérifie les arguments nil interdits aux appels de méthodes Objective-C.
osx.cocoa.RetainCount
Vérifie les fuites et la gestion incorrecte des comptes de référence.
osx.cocoa.SelfInit
Vérifie que « self » est correctement initialisé dans une méthode d'initialisation.
osx.cocoa.UnusedIvars
Avertit sur les variables membres privées qui ne sont jamais utilisées.
osx.cocoa.VariadicMethodTypes
Vérifie le passage de types non-Objective-C à des méthodes variadiques qui attendent uniquement des types Objective-C.
osx.coreFoundation.CFError
Vérifie l'utilisation des paramètres CFErrorRef*.
osx.coreFoundation.CFNumber
Vérifie l'utilisation correcte de CFNumberCreate().
osx.coreFoundation.CFRetainRelease
Vérifie les arguments nuls passés à CFRetain(), CFRelease(), et CFMakeCollectable().
osx.coreFoundation.containers.OutOfBounds
Vérifie les dépassements d'indices lors de l'utilisation de l'API CFArray.
osx.coreFoundation.containers.PointerSizedValues
Avertit si CFArray, CFDictionary, ou CFSet sont créés avec des valeurs dont la taille n'est pas celle d'un pointeur.
security.FloatLoopCounter
Avertit sur l'utilisation d'une valeur flottante comme compteur de boucle (CERT: FLP30-C, FLP30-CPP).
security.insecureAPI.UncheckedReturn
Avertit sur l'utilisation de fonctions dont les valeurs de retour doivent toujours être vérifiées.
security.insecureAPI.getpw
Avertit sur l'utilisation de getpw().
security.insecureAPI.gets
Avertit sur l'utilisation de gets().

EXEMPLE

scan-build -o /tmp/monrepertoirehtml make -j4

L'exemple ci-dessus dépose les rapports d'analyse dans un sous-répertoire de /tmp/monrepertoirehtml et exécute make avec l'option -j4. Un sous-répertoire différent est créé à chaque fois que scan-build analyse un projet. L'analyseur devrait supporter la plupart des constructions parallèles, mais pas les constructions distribuées.
