NOM

scgcheck - vérifier et valider l'ABI de libscg

SYNOPSIS

scgcheck [ options ]

DESCRIPTION

Scgcheck est utilisé pour vérifier et valider l'Interface Binaire d'Application (ABI) de libscg.

Nommage des périphériques

La plupart des utilisateurs n'ont pas besoin de se soucier du nommage des périphériques, car en mode -auto, scgcheck implémente le support cible automatique et trouve automatiquement un lecteur de test si un seul lecteur de type CD-ROM est disponible dans le système.

OPTIONS

-version
Affiche les informations de version et quitte.
-auto
Au lieu de demander confirmation avant chaque test, scgcheck tente d'effectuer un test entièrement automatisé.
dev=cible
Définit la cible SCSI pour le périphérique, voir les notes ci-dessus. Une spécification typique de périphérique cible est dev=1,6,0. Si un nom de fichier doit être fourni avec la spécification numérique de la cible, le nom de fichier dépend de l'implémentation. Le nom de fichier correct dans ce cas peut être trouvé dans les manuels spécifiques au système d'exploitation cible. Sur un système FreeBSD sans support CAM, vous devez utiliser le périphérique de contrôle (par exemple, /dev/rcd0.ctl). Une spécification de périphérique correcte dans ce cas peut être dev=/dev/rcd0.ctl:@.

Adressage SCSI général
Le périphérique cible de l'option dev= fait référence à scsibus/cible/lun du périphérique. La communication sur SunOS se fait avec le pilote général SCSI scg. D'autres systèmes d'exploitation utilisent une simulation de bibliothèque de ce pilote. La syntaxe possible est : dev= scsibus,cible,lun ou dev= cible,lun. Dans ce dernier cas, le périphérique doit être connecté au bus SCSI par défaut de la machine. Scsibus, cible et lun sont des nombres entiers. Certains systèmes d'exploitation ou implémentations de transport SCSI peuvent nécessiter de spécifier un nom de fichier en plus. Dans ce cas, la syntaxe correcte pour le périphérique est : dev= nom_du_périphérique:scsibus,cible,lun ou dev= nom_du_périphérique:cible,lun. Si le nom du nœud de périphérique spécifié sur un tel système fait référence à exactement un périphérique SCSI, une forme abrégée sous la forme dev= nom_du_périphérique:@ ou dev= nom_du_périphérique:@,lun peut être utilisée à la place de dev= nom_du_périphérique:scsibus,cible,lun.

Adressage SCSI distant
Pour accéder aux périphériques SCSI distants, vous devez préfixer le nom du périphérique SCSI par un indicateur de périphérique distant. L'indicateur de périphérique distant est soit REMOTE:utilisateur@hôte: soit REMOTE:hôte: Un nom de périphérique SCSI distant valide peut être : REMOTE:utilisateur@hôte: pour autoriser le balayage du bus SCSI distant ou REMOTE:utilisateur@hôte:1,0,0 pour accéder au périphérique SCSI sur hôte connecté au bus SCSI # 1, cible 0, lun 0. Afin d'autoriser l'accès distant à un hôte spécifique, le programme rscsi(1) doit être présent et configuré sur l'hôte.

Transports SCSI alternatifs
Les lecteurs ATAPI sont simplement des lecteurs SCSI qui utilisent intrinsèquement l'interface de paquets ATA comme couche de transport de commandes SCSI intégrée au transport IDE (ATA). Vous devrez peut-être spécifier une couche de transport alternative sur la ligne de commande si votre OS n'implémente pas un sous-système de pilotes noyau entièrement intégré qui permet d'accéder à n'importe quel lecteur en utilisant des commandes SCSI via une interface utilisateur unique.

Pour accéder aux périphériques SCSI via des couches de transport alternatives, vous devez préfixer le nom du périphérique SCSI par un indicateur de couche de transport. L'indicateur de couche de transport peut être quelque chose comme USCSI: ou ATAPI:. Pour obtenir une liste des couches de transport prises en charge pour votre plateforme, utilisez dev= HELP:

Contexte de portabilité
Pour rendre scgcheck portable sur toutes les plateformes UNIX, la syntaxe dev= nom_du_périphérique:scsibus,cible,lun est préférée car elle masque les connaissances spécifiques à l'OS sur les noms de périphériques à l'utilisateur. Un OS spécifique peut ne pas nécessairement prendre en charge un moyen de spécifier un nom de fichier de périphérique réel ni un moyen de spécifier scsibus,cible,lun.

Scsibus 0 est le bus SCSI par défaut sur la machine. Observez les messages de démarrage pour plus d'informations ou consultez /var/adm/messages pour plus d'informations sur la configuration SCSI de votre machine. Si vous avez des difficultés à déterminer quelles valeurs pour scsibus,cible,lun doivent être utilisées, essayez l'option -scanbus de scgcheck décrite ci-dessous.

Mode cible automatique
Si aucune option dev= n'est présente, ou si elle ne contient qu'un spécificateur de transport mais aucune notation d'adresse, scgcheck tente de scanner l'espace d'adresses SCSI pour les lecteurs de CD-ROM. Si un seul est trouvé, celui-ci est utilisé par défaut.

timeout=#
Définit la valeur du délai d'attente par défaut des commandes SCSI à # secondes. Le délai d'attente par défaut des commandes SCSI est le délai minimum utilisé pour envoyer des commandes SCSI. Si une commande SCSI échoue en raison d'un délai d'attente, vous pouvez essayer d'augmenter le délai d'attente par défaut des commandes SCSI au-delà de la valeur du délai d'attente de la commande échouée. Si la commande s'exécute correctement avec un délai d'attente de commande augmenté, veuillez signaler la meilleure valeur de délai d'attente et la commande correspondante à l'auteur du programme. Si aucune option timeout n'est présente, un délai d'attente par défaut de 40 secondes est utilisé.
debug=#, -d
Définit la valeur de débogage divers à # (avec debug=#) ou incrémente le niveau de débogage divers de un (avec -d). Si vous spécifiez -dd, cela équivaut à debug=2. Cela peut aider à résoudre les problèmes lors de l'ouverture d'un pilote pour libscg, ainsi qu'avec les tailles et types de secteurs. L'utilisation de -debug ralentit le processus et peut être la cause d'un sous-dépassement de tampon.
kdebug=#, kd=#
Indique au pilote scg de modifier la valeur de débogage du noyau pendant l'exécution des commandes SCSI.
scgopts=liste
Une liste d'options SCSI séparées par des virgules qui sont gérées par libscg. Les options implémentées peuvent être mises à jour indépendamment des applications. Actuellement, une option : ignore-resid est prise en charge pour contourner un bug du noyau Linux.
-silent, -s
Ne pas imprimer de rapport d'état pour les commandes SCSI échouées.
-v
Incrémente le niveau de verbosité générale de un. Ceci est utilisé par exemple pour afficher la progression du processus.
-V
Incrémente le niveau de verbosité concernant le transport des commandes SCSI de un. Cela aide à déboguer les problèmes pendant le processus, qui surviennent dans le graveur de CD. Si vous obtenez des messages d'erreur incompréhensibles, vous devriez utiliser ce drapeau pour obtenir une sortie plus détaillée. -VV montrera en plus le contenu du tampon de données. L'utilisation de -V ou -VV ralentit le processus.
f=fichier
Spécifie le fichier journal à utiliser à la place de check.log.

NOTES

Lors de l'utilisation de scgcheck avec le pilote générique SCSI de Linux défectueux. Vous devez noter que scgcheck utilise un contournement (hack) qui tente d'émuler la fonctionnalité du pilote scg. Unf

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Heureusement, le pilote sg sur Linux présente plusieurs bogues graves :

•
Il ne peut pas détecter si une commande SCSI n'a pas pu être envoyée du tout.
•
Il ne peut pas obtenir l'octet de statut SCSI. Scgcheck ne peut donc pas signaler les commandes SCSI défaillantes dans certaines situations.
•
Il ne peut pas obtenir le nombre réel de DMA pour le transfert. Scgcheck ne peut pas vous indiquer s'il y a un compte résiduel DMA.
•
Il ne peut pas obtenir le nombre d'octets valides dans les données de demande automatique. Scgcheck ne peut pas vous indiquer si le périphérique ne transfère aucune donnée de demande.
•
Il récupère trop peu de données lors de la demande automatique (CCS/SCSI-2/SCSI-3 nécessite >= 18).

DIAGNOSTICS

Un message d'erreur typique pour une commande SCSI ressemble à ceci :

scgcheck: I/O error. test unit ready: scsi sendcmd: no error
CDB:  00 20 00 00 00 00
status: 0x2 (CHECK CONDITION)
Sense Bytes: 70 00 05 00 00 00 00 0A 00 00 00 00 25 00 00 00 00 00
Sense Key: 0x5 Illegal Request, Segment 0
Sense Code: 0x25 Qual 0x00 (logical unit not supported) Fru 0x0
Sense flags: Blk 0 (not valid)
cmd finished after 0.002s timeout 40s
La première ligne donne des informations sur le transport de la commande. Le texte après le premier deux-points donne le message d'erreur pour l'appel système du point de vue du noyau. Il est généralement : I/O error, sauf si d'autres problèmes surviennent. Les mots suivants contiennent une courte description de la commande SCSI qui échoue. Le reste de la ligne indique s'il y a eu des problèmes pour le transport de la commande sur le bus SCSI. fatal error signifie qu'il n'a pas été possible de transporter la commande (par exemple, aucun périphérique présent à l'adresse SCSI demandée).

La deuxième ligne affiche le descripteur de commande SCSI pour la commande défaillante.

La troisième ligne donne des informations sur le code d'état SCSI renvoyé par la commande, si le transport de la commande réussit. Il s'agit d'informations d'erreur du périphérique SCSI.

La quatrième ligne est une représentation hexadécimale des informations de demande automatique pour la commande.

La cinquième ligne est le texte d'erreur pour la clé de demande si disponible, suivi du numéro de segment qui n'est valide que si la commande était une commande de copie. Si le message d'erreur n'est pas directement lié à la commande actuelle, le texte deferred error est ajouté.

La sixième ligne est le texte d'erreur pour le code de demande et le qualificateur de demande si disponible. Si le type de périphérique est connu, les données de demande sont décodées à partir de tables dans scsierrs.c. Le texte est suivi de la valeur d'erreur pour une unité remplaçable sur site.

La septième ligne affiche le numéro de bloc lié à la commande défaillante et le texte pour plusieurs indicateurs d'erreur. Le numéro de bloc peut ne pas être valide.

La huitième ligne indique le délai d'attente défini pour cette commande et le temps réellement nécessaire pour la compléter.
