SCGSKELETON(1L) COMMANDES UTILISATEUR de Schily SCGSKELETON(1L)

NOM

scgskeleton - Programme squelette pour le transport SCSI avec libscg

SYNTAXE

scgskeleton dev=périphérique [ options ]

DESCRIPTION

Scgskeleton est un programme squelette pour démontrer les interfaces et les capacités de la bibliothèque de transport SCSI libscg.

Nommage des périphériques

Pour obtenir une liste des paramètres de noms de périphériques possibles, exécutez scgskeleton -scanbus ou scgskeleton dev=help, puis utilisez le bon paramètre dev= basé sur la liste des périphériques.

OPTIONS

-help
Imprime un bref résumé des options et quitte.
-version
Imprime les informations de version et quitte.
dev=cible
Définit la cible SCSI pour le graveur CD/DVD/Blu-ray, voir les notes ci-dessus. Une spécification typique de périphérique cible est dev=1,6,0. Si un nom de fichier doit être fourni avec la spécification numérique de la cible, le nom de fichier dépend de l'implémentation. Le nom de fichier correct dans ce cas se trouve dans les manuels spécifiques au système d'exploitation cible. Sur un système FreeBSD sans support CAM, vous devez utiliser le périphérique de contrôle (par exemple, /dev/rcd0.ctl). Une spécification de périphérique correcte dans ce cas peut être dev=/dev/rcd0.ctl:@.

Adressage SCSI général
Le périphérique cible de l'option dev= fait référence au busscsi/cible/lun du graveur CD/DVD/Blu-ray. La communication sous SunOS se fait avec le pilote général SCSI scg. D'autres systèmes d'exploitation utilisent une simulation de bibliothèque de ce pilote. La syntaxe possible est : dev=busscsi,cible,lun ou dev=cible,lun. Dans ce dernier cas, le graveur CD/DVD/Blu-ray doit être connecté au bus SCSI par défaut de la machine. Busscsi, cible et lun sont des nombres entiers. Certains systèmes d'exploitation ou implémentations de transport SCSI peuvent nécessiter de spécifier un nom de fichier en plus. Dans ce cas, la syntaxe correcte pour le périphérique est : dev=nomdevic:busscsi,cible,lun ou dev=nomdevic:cible,lun. Si le nom du nœud de périphérique spécifié sur un tel système fait référence à un seul appareil SCSI, une forme abrégée sous la forme dev=nomdevic:@ ou dev=nomdevic:@,lun peut être utilisée à la place de dev=nomdevic:busscsi,cible,lun.

Adressage SCSI distant
Pour accéder aux périphériques SCSI distants, vous devez préfixer le nom du périphérique SCSI par un indicateur de périphérique distant. L'indicateur de périphérique distant est soit REMOTE:utilisateur@hôte: soit REMOTE:hôte:. Un nom de périphérique SCSI distant valide peut être : REMOTE:utilisateur@hôte: pour autoriser le scan du bus SCSI à distance, ou REMOTE:utilisateur@hôte:1,0,0 pour accéder au périphérique SCSI sur hôte connecté au bus SCSI n° 1, cible 0, lun 0. Afin d'autoriser l'accès à distance à un hôte spécifique, le programme rscsi(1) doit être présent et configuré sur l'hôte.

Transports SCSI alternatifs
Les lecteurs ATAPI ne sont que des lecteurs SCSI qui utilisent intrinsèquement l'interface de paquet ATA comme couche de transport de commandes SCSI intégrée au transport IDE (ATA). Vous pourriez avoir besoin de spécifier une couche de transport alternative sur la ligne de commande si votre système d'exploitation n'implémente pas un sous-système de pilotes noyau entièrement intégré qui permet d'accéder à n'importe quel lecteur en utilisant des commandes SCSI via une interface utilisateur unique.

Pour accéder aux périphériques SCSI via des couches de transport alternatives, vous devez préfixer le nom du périphérique SCSI par un indicateur de couche de transport. L'indicateur de couche de transport peut être quelque chose comme USCSI: ou ATAPI:. Pour obtenir une liste des couches de transport prises en charge pour votre plateforme, utilisez dev= HELP :

Contexte de portabilité
Pour rendre scgskeleton portable sur toutes les plateformes UNIX, la syntaxe dev=nomdevic:busscsi,cible,lun est préférée car elle masque les connaissances spécifiques au système d'exploitation concernant les noms de périphériques à l'utilisateur. Un système d'exploitation spécifique peut ne pas nécessairement prendre en charge un moyen de spécifier un nom de fichier de périphérique réel ni un moyen de spécifier busscsi,cible,lun.

Busscsi 0 est le bus SCSI par défaut sur la machine. Observez les messages de démarrage pour plus d'informations ou consultez /var/adm/messages pour plus d'informations sur la configuration SCSI de votre machine. Si vous avez des difficultés à déterminer quelles valeurs pour busscsi,cible,lun doivent être utilisées, essayez l'option -scanbus de scgskeleton décrite ci-dessous.

Utilisation de noms logiques pour les périphériques
Si aucune option dev n'est présente, scgskeleton tentera d'obtenir le périphérique depuis l'environnement CDR_DEVICE.

Si un fichier /etc/default/cdrecord existe, et si l'argument de l'option dev= ou l'environnement CDR_DEVICE ne contient pas les caractères ',', '/', '@' ou ':', il est interprété comme un nom d'étiquette de périphérique défini dans le fichier /etc/default/cdrecord (voir la section FICHIERS).

Mode Autotarget
Si aucune option dev= et aucun environnement CDR_DEVICE n'est présent, ou s'il ne contient qu'un spécificateur de transport mais aucune notation d'adresse, scgskeleton tente de scanner l'espace d'adresses SCSI pour les lecteurs CD-ROM. Si un seul est trouvé, il est utilisé par défaut.

timeout=#
Définit la valeur de délai d'attente par défaut des commandes SCSI à # secondes. Le délai d'attente par défaut des commandes SCSI est le délai minimum utilisé pour l'envoi des commandes SCSI. Si une commande SCSI échoue en raison d'un délai d'attente, vous pouvez essayer d'augmenter le délai d'attente par défaut des commandes SCSI au-dessus de la valeur de délai d'attente de la commande échouée. Si la commande s'exécute correctement avec un délai d'attente de commande augmenté, veuillez signaler la meilleure valeur de délai d'attente et la commande correspondante à l'auteur du programme. Si aucune option timeout n'est présente, un délai d'attente par défaut de 40 secondes est utilisé.
debug=#, -d
Définit la valeur de débogage divers à # (avec debug=#) ou incrémente le niveau de débogage divers de un (avec -d). Si vous spécifiez -dd, cela équivaut à debug=2. Cela peut aider à trouver des problèmes lors de l'ouverture d'un pilote pour libscg, ainsi qu'avec les tailles et les types de secteurs. L'utilisation de -debug ralentit le processus et peut être la cause d'un sous-dépassement de tampon.
kdebug=#, kd=#
Demande au pilote scg de modifier la valeur de débogage du noyau lorsque les commandes SCSI sont en cours d'exécution.
-silent, -s
N'imprime pas de rapport d'état pour les commandes SCSI échouées.
-v
Incrémente le niveau de verbosité générale de un. Ceci est utilisé par exemple pour afficher la progression du processus.
-V
Incrémente le niveau de verbosité concernant le transport des commandes SCSI de un. Ceci aide à déboguer les problèmes pendant le processus qui se produisent dans le graveur de CD. Si vous obtenez des messages d'erreur incompréhensibles, vous devriez utiliser ce drapeau pour obtenir une sortie plus détaillée. -VV affichera le contenu du tampon de données en plus. L'utilisation de -V ou -VV ralentit le processus. -scanbus Scan tous les périphériques SCSI sur tous les bus SCSI et imprime les chaînes d'interrogation. Cette option peut être utilisée pour trouver l'adresse SCSI des périphériques sur un système. Les nombres imprimés comme étiquettes sont calculés par : bus * 100 + target
scgopts=liste
Une liste séparée par des virgules d'options SCSI gérées par libscg. Les options implémentées peuvent être mises à jour indépendamment des applications. Actuellement, une option : ignore-resid est prise en charge pour contourner un bug du noyau Linux.
ts=#
Définit la taille de transfert maximale pour un seul co SCSI

mmand vers #. La syntaxe pour l'option ts= est la même que pour cdrecord fs=# ou sdd bs=#.

Si aucune option ts= n'a été spécifiée, scgskeleton par défaut à une taille de transfert de 256 Ko. Si libscg obtient des valeurs inférieures du système d'exploitation, la valeur est réduite à la valeur maximale possible avec le système d'exploitation actuel. Parfois, il peut être utile de réduire davantage la taille de transfert ou de l'augmenter, mais notez que cela peut prendre beaucoup de temps pour trouver une meilleure valeur en expérimentant avec la option ts=.

EXEMPLES

ENVIRONNEMENT

RSH
Si l'environnement RSH est présent, la connexion à distance ne sera pas créée via rcmd(3) mais en appelant le programme pointé par RSH. Utilisez par ex. RSH=/usr/bin/ssh pour créer une connexion shell sécurisée.

Notez que cela force cdrecord à créer un tuyau vers le programme rsh(1) et empêche cdrecord d'accéder directement au socket réseau du serveur distant. Cela rend impossible la configuration des paramètres de performance et ralentit la connexion par rapport à une connexion initiée par root via rcmd(3).

RSCSI
Si l'environnement RSCSI est présent, le serveur SCSI distant ne sera pas le programme /opt/schily/sbin/rscsi mais le programme pointé par RSCSI. Notez que le nom du programme serveur SCSI distant sera ignoré si vous vous connectez en utilisant un compte qui a été créé avec un programme serveur SCSI distant comme shell de connexion.

VOIR AUSSI

cdrecord(1), scg(7), rcmd(3), ssh(1).

NOTES

DIAGNOSTICS

Un message d'erreur typique pour une commande SCSI ressemble à :

scgskeleton: I/O error. test unit ready: scsi sendcmd: no error
CDB:  00 20 00 00 00 00
status: 0x2 (CHECK CONDITION)
Sense Bytes: 70 00 05 00 00 00 00 0A 00 00 00 00 25 00 00 00 00 00
Sense Key: 0x5 Illegal Request, Segment 0
Sense Code: 0x25 Qual 0x00 (logical unit not supported) Fru 0x0
Sense flags: Blk 0 (not valid)
cmd finished after 0.002s timeout 40s
La première ligne donne des informations sur le transport de la commande. Le texte après le premier double point donne le message d'erreur pour l'appel système du point de vue du noyau. Il est généralement : I/O error sauf si d'autres problèmes surviennent. Les mots suivants contiennent une courte description de la commande SCSI qui échoue. Le reste de la ligne indique s'il y a eu des problèmes lors du transport de la commande sur le bus SCSI. fatal error signifie qu'il n'a pas été possible de transporter la commande (c'est-à-dire qu'aucun périphérique n'est présent à l'adresse SCSI demandée).

La deuxième ligne imprime le bloc descripteur de commande SCSI pour la commande échouée.

La troisième ligne donne des informations sur le code d'état SCSI renvoyé par la commande, si le transport de la commande réussit. Il s'agit d'informations d'erreur du périphérique SCSI.

La quatrième ligne est un dump hexadécimal des informations de requête de sens automatique pour la commande.

La cinquième ligne est le texte d'erreur pour la clé de sens si elle est disponible, suivi du numéro de segment qui n'est valide que si la commande était une commande de copie. Si le message d'erreur n'est pas directement lié à la commande actuelle, le texte deferred error est ajouté.

La sixième ligne est le texte d'erreur pour le code de sens et le qualificateur de sens s'ils sont disponibles. Si le type de périphérique est connu, les données de sens sont décodées à partir de tables dans scsierrs.c. Le texte est suivi de la valeur d'erreur pour une unité remplaçable sur le terrain.

La septième ligne imprime le numéro de bloc lié à la commande échouée et le texte de plusieurs indicateurs d'erreur. Le numéro de bloc peut ne pas être valide.

La huitième ligne rapporte le délai d'attente configuré pour cette commande et le temps que la commande a réellement mis pour s'achever.
