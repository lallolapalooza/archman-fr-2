NOM

swanctl.conf - fichier de configuration de swanctl

DESCRIPTION

swanctl.conf est le fichier de configuration utilisé par l'outil swanctl(8) pour charger les configurations et les identifiants dans le démon IKE de strongSwan.

Pour une description de la syntaxe de base du fichier, y compris les formats de nombres/temps, ou comment référencer des sections ou diviser la configuration en plusieurs fichiers en incluant d'autres fichiers, référez-vous à strongswan.conf(5).

PARAMÈTRES

Les paramètres suivants peuvent être utilisés pour configurer les connexions, les identifiants et les pools.

connections

Section définissant les configurations de connexion IKE.

La section connections définit les configurations de connexion IKE, chacune dans ses propres sous-sections. Dans la description des mots-clés ci-dessous, la connexion est nommée <conn>, mais un nom de connexion arbitraire mais unique peut être choisi pour chaque sous-section de connexion.

connections.<conn>

Section pour une connexion IKE nommée <conn>.
connections.<conn>.version [0]
Version majeure IKE à utiliser pour la connexion. 1 utilise IKEv1 alias ISAKMP, 2 utilise IKEv2. Une connexion utilisant la valeur par défaut de 0 accepte IKEv1 et IKEv2 en tant que répondeur, et initie activement la connexion avec IKEv2.
connections.<conn>.local_addrs [%any]
Adresse(s) locale(s) à utiliser pour la communication IKE, séparées par des virgules. Accepte des adresses IPv4/IPv6 uniques, des noms DNS, des sous-réseaux CIDR ou des plages d'adresses IP.

En tant qu'initiateur, la première adresse non-plage/non-sous-réseau est utilisée pour initier la connexion. En tant que répondeur, l'adresse de destination locale doit correspondre à au moins une des adresses, sous-réseaux ou plages spécifiés.

Si des FQDN sont assignés, ils sont résolus à chaque fois qu'une recherche de configuration est effectuée. Si la résolution DNS expire, la recherche est retardée de cette durée.

connections.<conn>.remote_addrs [%any]
Adresse(s) distante(s) à utiliser pour la communication IKE, séparées par des virgules. Accepte des adresses IPv4/IPv6 uniques, des noms DNS, des sous-réseaux CIDR ou des plages d'adresses IP.

En tant qu'initiateur, la première adresse non-plage/non-sous-réseau est utilisée pour initier la connexion. En tant que répondeur, l'adresse source de l'initiateur doit correspondre à au moins une des adresses, sous-réseaux ou plages spécifiés.

Si des FQDN sont assignés, ils sont résolus à chaque fois qu'une recherche de configuration est effectuée. Si la résolution DNS expire, la recherche est retardée de cette durée.

Pour initier une connexion, au moins une adresse spécifique ou un nom DNS doit être spécifié.

connections.<conn>.local_port [500]
Port UDP local pour la communication IKE. Par défaut, le port du backend de socket est utilisé, qui est généralement 500. Si le port 500 est utilisé, le flottement automatique du port IKE vers le port 4500 est utilisé pour contourner les problèmes de NAT.

L'utilisation d'un port IKE local non standard nécessite le support du backend de socket utilisé (socket-dynamic).

connections.<conn>.remote_port [500]
Port UDP distant pour la communication IKE. Si la valeur par défaut du port 500 est utilisée, le flottement automatique du port IKE vers le port 4500 est utilisé pour contourner les problèmes de NAT.
connections.<conn>.proposals [default]
Une proposition est un ensemble d'algorithmes. Pour les propositions IKE non-AEAD, cela comprend un algorithme de chiffrement, un algorithme d'intégrité, une fonction pseudo-aléatoire et une méthode d'échange de clés. Pour les propositions AEAD, au lieu des algorithmes de chiffrement et d'intégrité, un algorithme de mode combiné est utilisé.

Avec des pairs qui supportent plusieurs échanges de clés IKEv2 (RFC 9370), jusqu'à sept échanges de clés supplémentaires peuvent être négociés. Ils peuvent être configurés en préfixant le mot-clé de l'algorithme avec keX_ (où X est un nombre compris entre 1 et 7).

Pour IKEv2, plusieurs algorithmes du même type peuvent être spécifiés dans une seule proposition, parmi lesquels un sera sélectionné. Pour IKEv1, un seul algorithme par type est autorisé par proposition, les algorithmes supplémentaires seront implicitement tronqués. Utilisez plusieurs propositions pour offrir différentes combinaisons d'algorithmes avec IKEv1.

Les mots-clés d'algorithme sont séparés par des tirets. Plusieurs propositions peuvent être séparées par des virgules. La valeur spéciale default forme une proposition par défaut d'algorithmes supportés considérés comme sûrs, et est généralement un bon choix pour l'interopérabilité.

connections.<conn>.vips []
Liste d'adresses IP virtuelles séparées par des virgules à demander dans les payloads de configuration IKEv2 ou le Mode Config IKEv1. Les adresses génériques 0.0.0.0 et :: demandent une adresse arbitraire, des adresses spécifiques peuvent être définies. Le répondeur peut cependant retourner une adresse différente, ou aucune.
connections.<conn>.aggressive [no]
Active le Mode Agressif au lieu du Mode Principal avec Protection d'Identité. Le Mode Agressif est considéré comme moins sûr, car les payloads ID et HASH sont échangés sans protection. Cela permet à un attaquant passif d'espionner les identités des pairs, et pire encore, de lancer des attaques par dictionnaire sur la clé pré-partagée.
connections.<conn>.pull [yes]
Si la valeur par défaut yes est utilisée, le Mode Config fonctionne en mode pull, où l'initiateur demande activement une adresse IP virtuelle. Avec no, le mode push est utilisé, où le répondeur pousse une adresse IP virtuelle vers le pair initiateur.

Le mode push est actuellement supporté pour IKEv1, mais pas en IKEv2. Il n'est utilisé que par quelques implémentations, le mode pull est recommandé.

connections.<conn>.dscp [000000]
Le champ du Codepoint des services différenciés (DSCP) à définir sur les paquets IKE sortants pour cette connexion. La valeur est une chaîne binaire codée sur six chiffres spécifiant le Codepoint à définir, comme défini dans la RFC 2474.
connections.<conn>.encap [no]
Pour forcer l'encapsulation UDP des paquets ESP, le démon IKE peut simuler les payloads de détection NAT. Cela fait croire au pair que le NAT a lieu sur le chemin, le forçant à encapsuler les paquets ESP dans UDP.

Généralement, cela n'est pas nécessaire, mais cela peut aider à contourner les problèmes de connectivité avec des pare-feux intermédiaires trop restrictifs.

connections.<conn>.mobike [yes]
Active MOBIKE sur les connexions IKEv2. MOBIKE est activé par défaut sur les connexions IKEv2, et permet la mobilité des clients et le multi-homing sur les serveurs en migrant les tunnels IPsec actifs.

En général, laisser MOBIKE activé ne pose pas de problème, car il n'est pas utilisé si le pair n'indique pas le supporter. Cependant, en raison de la conception de MOBIKE, IKEv2 flotte toujours vers le port 4500 à partir du second échange. Certaines implémentations n'apprécient pas ce comportement, il peut donc être désactivé.

connections.<conn>.dpd_delay [0s]
Intervalle pour vérifier la vivacité d'un pair activement en utilisant des échanges INFORMATION IKEv2 ou des messages R_U_THERE IKEv1. La vérification active du DPD n'est appliquée que si aucun paquet IKE ou ESP/AH n'a été reçu pendant le délai DPD configuré.
connections.<conn>.dpd_timeout [0s]
Charon utilise par défaut le mécanisme normal de retransmission et les timeouts pour vérifier la vivacité d'un pair, comme

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Tous les messages sont utilisés pour la vérification de la vivacité. Pour des raisons de compatibilité, avec IKEv1, un intervalle personnalisé peut être spécifié ; cette option n'a aucun effet sur les connexions utilisant IKE2.
connections.<conn>.fragmentation [oui]
Utilise la fragmentation IKE (extension propriétaire IKEv1 ou fragmentation RFC 7383 IKEv2). Les valeurs acceptables sont oui (par défaut), accepter, forcer et non. Si défini sur oui, et si le pair le prend en charge, les messages IKE de taille excessive seront envoyés en fragments. Si défini sur accepter, la prise en charge de la fragmentation est annoncée au pair, mais le démon n'envoie pas ses propres messages fragmentés. Si défini sur forcer (uniquement pris en charge pour IKEv1), le message IKE initial sera déjà fragmenté si nécessaire. Enfin, définir l'option sur non désactivera l'annonce de la prise en charge de cette fonctionnalité.

Notez que les messages IKE fragmentés envoyés par un pair sont toujours acceptés quelle que soit la valeur de cette option (même lorsqu'elle est définie sur non).

connections.<conn>.childless [autoriser]
Utilise l'initiation CHILDLESS IKE_SA (RFC 6023) pour IKEv2, avec le premier CHILD_SA créé via un échange CREATE_CHILD_SA séparé (par exemple, pour utiliser un échange de clés indépendant pour tous les CHILD_SA). Les valeurs acceptables sont autoriser (par défaut), préférer, forcer et jamais. Si défini sur autoriser, les répondeurs accepteront les IKE_SA sans enfant (comme indiqué via une notification dans la réponse IKE_SA_INIT) tandis que les initiateurs continueront à créer des IKE_SA réguliers avec le premier CHILD_SA créé pendant IKE_AUTH, sauf si l'IKE_SA est initié explicitement sans aucun enfant (ce qui échouera si le répondeur ne prend pas en charge ou a désactivé cette extension). L'effet de préférer est le même que autoriser sur les répondeurs, mais en tant qu'initiateur, un IKE_SA sans enfant est initié si le répondeur le prend en charge. Si défini sur forcer, seule l'initiation sans enfant est acceptée dans les deux rôles. Enfin, définir l'option sur jamais désactive la prise en charge des IKE_SA sans enfant en tant que répondeur.
connections.<conn>.send_certreq [oui]
Envoie des charges utiles de demande de certificat pour proposer des certificats de CA racine de confiance au pair. Les demandes de certificat aident le pair à choisir un certificat/une clé privée approprié pour l'authentification et sont activées par défaut.

La désactivation des demandes de certificat peut être utile si trop de certificats de CA racine de confiance sont installés, car chaque demande de certificat augmente la taille des paquets IKE initiaux.

connections.<conn>.send_cert [si_demandé]
Envoie des charges utiles de certificat lors de l'utilisation de l'authentification par certificat. Avec la valeur par défaut si_demandé, le démon envoie des charges utiles de certificat uniquement si des demandes de certificat ont été reçues. jamais désactive l'envoi des charges utiles de certificat, toujours entraîne l'envoi inconditionnel des charges utiles de certificat chaque fois que l'authentification par certificat est utilisée.
connections.<conn>.ocsp [répondre]
Envoie des demandes de statut OCSP dans les charges utiles de demande de certificat et/ou envoie des réponses de statut OCSP dans les charges utiles de certificat lors de l'utilisation de l'authentification par certificat. Avec la valeur par défaut répondre, le démon envoie des réponses de statut OCSP dans les charges utiles de certificat si une demande de statut OCSP a été reçue dans une demande de certificat, jamais désactive l'envoi des demandes et réponses de statut OCSP, demander entraîne l'envoi de demandes de statut OCSP dans les charges utiles de demande de certificat chaque fois que l'authentification par certificat est utilisée, les deux combinent répondre et demander.
connections.<conn>.ppk_id []
Chaîne identifiant la clé prépartagée post-quantique (PPK) à utiliser.
connections.<conn>.ppk_required [non]
Indique si une clé prépartagée post-quantique (PPK) est requise pour cette connexion.
connections.<conn>.keyingtries [1]
Nombre de séquences de retransmission à effectuer lors de la connexion initiale. Au lieu d'abandonner l'initiation après la première séquence de retransmission avec la valeur par défaut de 1, des séquences supplémentaires peuvent être démarrées conformément à la valeur configurée. Une valeur de 0 lance une nouvelle séquence jusqu'à ce que la connexion s'établisse ou échoue avec une erreur permanente.
connections.<conn>.unique [non]
Politique d'unicité de connexion à appliquer. Pour éviter plusieurs connexions du même utilisateur, une politique d'unicité peut être appliquée. La valeur jamais n'applique jamais une telle politique, même si un pair a inclus des messages de notification INITIAL_CONTACT, tandis que non remplace les connexions existantes pour la même identité si une nouvelle a la notification INITIAL_CONTACT. garder rejette les nouvelles tentatives de connexion si le même utilisateur a déjà une connexion active, remplacer supprime toute connexion existante si une nouvelle pour le même utilisateur est établie.

Pour comparer les connexions pour l'unicité, l'identité IKE distante est utilisée. Si l'authentification EAP ou XAuth est impliquée, l'identité EAP ou le nom d'utilisateur XAuth est utilisé pour appliquer la politique d'unicité à la place.

Sur les initiateurs, ce paramètre spécifie si une notification INITIAL_CONTACT est envoyée pendant IKE_AUTH si aucune connexion existante n'est trouvée avec le pair distant (déterminé par les identités du premier tour d'authentification). Sauf si défini sur jamais, le client enverra une notification.

connections.<conn>.reauth_time [0s]
Heure de planification de la réauthentification IKE. La réauthentification IKE recrée le SA IKE/ISAKMP à partir de zéro et réévalue les informations d'identification. Dans les configurations asymétriques (avec EAP ou des charges utiles de configuration), il peut ne pas être possible de réauthentifier activement en tant que répondeur. La négociation de la durée de vie de réauthentification IKEv2 peut demander au client d'effectuer une réauthentification.

La réauthentification est désactivée par défaut. L'activer peut généralement entraîner de courtes interruptions de connexion, même lors de l'utilisation de la réauthentification make-before-break, qui est maintenant par défaut. Cependant, elles sont nettement plus courtes qu'avec l'approche héritée break-before-make.

connections.<conn>.rekey_time [4h]
Le rekeying IKE rafraîchit le matériel clé en utilisant un échange Diffie-Hellman, mais ne vérifie pas les informations d'identification associées. Il est pris en charge uniquement dans IKEv2 ; IKEv1 effectue une procédure de réauthentification à la place.

Avec la valeur par défaut, le rekeying IKE est planifié toutes les 4 heures, moins le rand_time configuré. Si un reauth_time est configuré, rekey_time est défini par défaut sur zéro, désactivant le rekeying ; définissez explicitement les deux pour forcer le rekeying et la réauthentification.

connections.<conn>.over_time [10% de rekey_time/reauth_time]
Durée de vie maximale stricte de l'IKE_SA si le rekey/réauthentification n'est pas terminée, en tant que temps. Pour éviter qu'un IKE/ISAKMP ne soit maintenu en vie si la réauthentification ou le rekeying IKE échoue perpétuellement, une durée de vie maximale stricte peut être spécifiée. Si l'IKE_SA ne parvient pas à effectuer le rekeying ou la réauthentification dans le délai spécifié, l'IKE_SA sera fermé.

Contrairement au rekeying de CHILD_SA, over_time est relatif dans le temps aux valeurs de rekey_time et reauth_time, car il s'applique aux deux.

La valeur par défaut est 10 % de la plus longue des valeurs de rekey_time et reauth_time.

connections.<conn>.rand_time [over_time]
Plage de temps à partir de laquelle choisir une valeur aléatoire à soustraire des temps de rekey/réauthentification. Pour éviter que les deux pairs n'initient la procédure de rekey/réauthentification simultanément, un temps aléatoire est soustrait des temps de rekey/réauthentification.

La valeur par défaut est égale à la valeur configurée de over_time.

connections.<conn>.pools []
Liste séparée par des virgules de pools nommés à partir desquels allouer des adresses IP virtuelles et d'autres attributs de configuration. Chaque nom référence un pool par son nom, soit dans la section pools, soit dans un pool externe.
connections.<conn>.if_id_in [0]
ID d'interface XFRM défini sur les politiques/SA entrantes, peut être remplacé par la configuration enfant, voir là pour plus de détails.

La valeur spéciale %unique alloue un ID d'interface unique par IKE_SA, qui est hérité par tous ses CHILD_SA (sauf s'il est remplacé là), au-delà de cela, la valeur %unique-dir attribue un ID d'interface unique différent pour chaque direction (entrée/sortie).

connections.<conn>.if_id_out [0]
ID d'interface XFRM défini sur les politiques/SA sortantes, peut être remplacé par la configuration enfant, voir là pour plus de détails.

La valeur spéciale %unique alloue un ID d'interface unique par IKE_SA, qui est hérité par tous ses CHILD_SA (sauf s'il est remplacé là), au-delà de cela, la valeur %unique-dir attribue un ID d'interface unique différent pour chaque direction (entrée/sortie).

connections.<conn>.mediation [non]
Indique si cette connexion est une connexion de médiation, c'est-à-dire si cette connexion est utilisée pour médiatiser d'autres connexions en utilisant l'extension de médiation IKEv2. Les connexions de médiation ne créent aucun CHILD_SA.
connections.<conn>.mediated_by []
Le nom de la connexion par laquelle cette connexion sera médiatisée. Si spécifié, la connexion sera médiatisée via la connexion de médiation nommée. La connexion de médiation doit avoir mediation activée.
connections.<conn>.mediation_peer []
Identité sous laquelle le pair est enregistré auprès du serveur de médiation, c'est-à-dire l'identité IKE que l'autre extrémité de cette connexion utilise comme identité locale lors de sa connexion au serveur de médiation. C'est l'identité avec laquelle nous demandons au serveur de médiation de nous mettre en relation. Uniquement pertinent pour les connexions qui définissent mediated_by. Si elle n'est pas spécifiée, l'identité IKE distante du premier tour d'authentification de cette connexion sera utilisée.
connections.<conn>.local<suffix>

Section pour un tour d'authentification local. Un tour d'authentification local définit les règles de la manière dont l'authentification est effectuée pour le pair local. Plusieurs tours peuvent être définis pour utiliser l'authentification multiple RFC 4739 d'IKEv2 ou XAuth d'IKEv1.

Chaque tour est défini dans une section dont le préfixe est local, et un suffixe unique optionnel. Pour définir un seul tour d'authentification, le suffixe peut être omis.

connections.<conn>.local<suffix>.round [0]
Identifiant numérique optionnel par lequel les tours d'authentification sont triés. Si non spécifié, les tours sont ordonnés par leur position dans le fichier de configuration/message VICI.
connections.<conn>.local<suffix>.certs []
Liste séparée par des virgules de candidats certificats à utiliser pour l'authentification. Les certificats peuvent utiliser un chemin relatif du répertoire x509 de swanctl ou un chemin absolu.

Le certificat utilisé pour l'authentification est sélectionné en fonction des charges utiles de demande de certificat reçues. Si aucune CA appropriée ne peut être trouvée, le premier certificat est utilisé.

connections.<conn>.local<suffix>.cert<suffix> []
Section pour un candidat certificat à utiliser pour l'authentification. Les certificats dans certs sont transmis sous forme de blobs binaires, ces sections offrent plus de flexibilité.
connections.<conn>.local<suffix>.cert<suffix>.file []
Chemin absolu vers le certificat à charger. Passé tel quel au démon, il doit donc être lisible par celui-ci.

Configurez soit celui-ci, soit handle, mais pas les deux, dans une seule section.

connections.<conn>.local<suffix>.cert<suffix>.handle []
CKA_ID encodé en hexadécimal du certificat sur un token.

Configurez soit celui-ci, soit file, mais pas les deux, dans une seule section.

connections.<conn>.local<suffix>.cert<suffix>.slot []
Numéro de slot optionnel du token qui stocke le certificat.
connections.<conn>.local<suffix>.cert<suffix>.module []
Nom de module PKCS#11 optionnel.
connections.<conn>.local<suffix>.pubkeys []
Liste séparée par des virgules de candidats clés publiques brutes à utiliser pour l'authentification. Les clés publiques peuvent utiliser un chemin relatif du répertoire pubkey de swanctl ou un chemin absolu.

Bien que plusieurs clés publiques locales puissent être définies en principe, seule la première clé publique de la liste est utilisée pour l'authentification.

connections.<conn>.local<suffix>.auth [pubkey]
Authentification à effectuer localement. pubkey utilise l'authentification par clé publique avec une clé privée associée à un certificat utilisable. psk utilise l'authentification par clé pré-partagée. Le spécifique d'IKEv1 xauth est utilisé pour l'authentification XAuth ou Hybride, tandis que le mot-clé spécifique d'IKEv2 eap définit l'authentification EAP.

Pour xauth, un nom de backend spécifique peut être ajouté, séparé par un trait d'union. Le backend xauth approprié est sélectionné pour effectuer l'échange XAuth. Pour XAuth traditionnel, la méthode xauth est généralement définie dans le deuxième tour d'authentification après un premier tour pubkey (ou psk). Utiliser xauth dans le premier tour effectue l'authentification client en mode Hybride.

Pour eap, un nom de méthode EAP spécifique peut être ajouté, séparé par un trait d'union. Un module EAP implémentant la méthode appropriée est sélectionné pour effectuer la conversation EAP.

Si les deux pairs prennent en charge RFC 7427 ("Signature Authentication in IKEv2"), des algorithmes de hachage spécifiques à utiliser pendant l'authentification IKEv2 peuvent être configurés. Pour ce faire, utilisez ike: suivi d'une contrainte de schéma de signature de chaîne de confiance (voir la description du mot-clé auth de la section remote). Par exemple, avec ike:pubkey-sha384-sha256, un schéma de signature de clé publique avec SHA-384 ou SHA-256 serait utilisé pour l'authentification, dans cet ordre et en fonction des algorithmes de hachage supportés par le pair. Si aucun algorithme de hachage spécifique n'est configuré, la valeur par défaut est de préférer un algorithme qui correspond ou dépasse la force de la clé de signature. Si aucune contrainte avec le préfixe ike: n'est configurée, toute contrainte de schéma de signature (sans préfixe ike:) s'appliquera également à l'authentification IKEv2, sauf si cela est désactivé dans strongswan.conf(5). Pour utiliser les signatures RSASSA-PSS, utilisez rsa/pss au lieu de pubkey ou rsa, comme par exemple dans ike:rsa/pss-sha256. Si des contraintes pubkey ou rsa sont configurées, les signatures RSASSA-PSS ne seront utilisées que si elles sont activées dans strongswan.conf(5).

connections.<conn>.local<suffix>.id []
Identité IKE à utiliser pour le tour d'authentification. Lors de l'utilisation de l'authentification par certificat, l'identité IKE doit être contenue dans le certificat, soit comme sujet, soit comme subjectAltName.

L'identité peut être une adresse IP, un nom de domaine entièrement qualifié, une adresse e-mail ou un nom distinctif pour lequel le type d'ID est déterminé automatiquement et la chaîne est convertie dans le codage approprié. Pour forcer un type d'identité spécifique, un préfixe peut être utilisé, suivi d'un deux-points (:). Si le signe dièse (#) suit le deux-points, les données restantes sont interprétées comme un codage hexadécimal, sinon la chaîne est utilisée telle quelle comme données d'identification. Notez que cela implique qu'aucune conversion n'est effectuée pour les identités non-chaînes. Par exemple, ipv4:10.0.0.1 ne crée pas une identité IKE valide ID_IPV4_ADDR, car elle n'est pas convertie en binaire 0x0a000001. Au lieu de cela, on pourrait utiliser ipv4:#0a000001 pour obtenir une identité valide, mais utiliser simplement le type implicite avec conversion automatique est généralement plus simple. Il en va de même pour les types codés ASN1. Les préfixes suivants sont connus : ipv4, ipv6, rfc822, email, userfqdn, fqdn, dns, asn1dn, asn1gn et keyid. Des préfixes de type personnalisés peuvent être spécifiés en entourant la valeur numérique du type par des accolades.

connections.<conn>.local<suffix>.eap_id [id]
Identité EAP client à utiliser dans l'échange EAP-Identity et la méthode EAP.
connections.<conn>.local<suffix>.aaa_id [remote-id]
Identité EAP côté serveur à attendre dans la méthode EAP. Certaines méthodes EAP, comme EAP-TLS, utilisent une identité pour que le serveur effectue l'authentification mutuelle. Cette identité peut différer de l'identité IKE, en particulier lorsque l'authentification EAP est déléguée du répondeur IKE à un backend AAA.

Pour EAP-(T)TLS, ceci définit l'identité pour laquelle le serveur doit fournir un certificat dans l'échange TLS.

connections.<conn>.local<suffix>.xauth_id [id]
Nom d'utilisateur XAuth client utilisé dans l'échange XAuth.
connections.<conn>.remote<suffix>

Section pour un tour d'authentification distant. Un tour d'authentification distant définit les contraintes sur la manière dont les pairs doivent s'authentifier pour utiliser cette connexion. Plusieurs tours peuvent être définis pour utiliser l'authentification multiple RFC 4739 d'IKEv2 ou XAuth d'IKEv1.

Chaque tour est défini dans une section dont le préfixe est remote, et un suffixe unique optionnel. Pour définir un seul tour d'authentification, le suffixe peut être omis.

connections.<conn>.remote<suffix>.round [0]
Identifiant numérique optionnel par lequel les tours d'authentification sont triés. Si non spécifié, les tours sont ordonnés par leur position dans le fichier de configuration/message VICI.
connections.<conn>.remote<suffix>.id [%any]

Il est possible d'utiliser des jokers pour faire correspondre les identités distantes (par exemple, *@strongswan.org, *.strongswan.org, ou C=CH,O=strongSwan,CN=*). Les connexions avec des correspondances exactes sont préférées. Lors de l'utilisation de noms distinctifs avec des jokers, l'option charon.rdn_matching dans strongswan.conf(5) spécifie comment les RDN sont comparés.

Les expressions régulières POSIX étendues sont également prises en charge pour la correspondance des identités distantes. Elles doivent commencer par un préfixe de type explicite, suivi d'un caractère d'accent circonflexe ('^'), et se terminer par un signe dollar ('$') pour indiquer un motif ancré. connections.<conn>.children.<child>.ah_proposals []
Propositions AH à offrir pour le CHILD_SA. Une proposition est un ensemble d'algorithmes. Pour AH, cela inclut un algorithme d'intégrité et une méthode d'échange de clés optionnelle. Si une méthode KE est spécifiée, le rekeying CHILD_SA/Quick Mode et la négociation initiale utilisent un échange de clés séparé en utilisant la méthode négociée (voir esp_proposals pour les détails).

Avec des pairs prenant en charge plusieurs échanges de clés IKEv2 (RFC 9370), jusqu'à sept échanges de clés supplémentaires peuvent être négociés. Ils peuvent être configurés en préfixant le mot-clé de l'algorithme avec keX_ (où X est un nombre compris entre 1 et 7).

connections.<conn>.children.<child>.ah_proposals [default]
AH proposals to offer for the CHILD_SA. A proposal is a set of algorithms. For IKEv2, multiple algorithms of the same kind can be specified in a single proposal, from which one gets selected. For IKEv1, only one algorithm per kind is allowed per proposal, more algorithms get implicitly stripped. Use multiple proposals to offer different algorithm combinations with IKEv1.

Algorithm keywords get separated using dashes. Multiple proposals may be separated by commas. The special value default forms a default proposal of supported algorithms considered safe, and is usually a good choice for interoperability. By default no AH proposals are included, instead ESP is proposed.

connections.<conn>.children.<child>.esp_proposals [default]
ESP proposals to offer for the CHILD_SA. A proposal is a set of algorithms. For non-AEAD ESP proposals, this includes an integrity algorithm, an encryption algorithm, an optional key exchange method and an optional Extended Sequence Number Mode indicator. For AEAD proposals, a combined mode algorithm is used instead of the separate encryption/integrity algorithms.

If a key exchange method is negotiated, CHILD_SA/Quick Mode rekeying and initial negotiation use a separate key exchange using the specified method. However, for IKEv2, the keys of the CHILD_SA created implicitly with the IKE_SA will always be derived from the IKE_SA's key material. So any key exchange method specified here will only apply when the CHILD_SA is later rekeyed or is created with a separate CREATE_CHILD_SA exchange. A proposal mismatch might, therefore, not immediately be noticed when the SA is established, but may later cause rekeying to fail. If one or more key exchange methods are configured in a proposal, the key exchange can be made optional by also adding none.

With peers that support multiple IKEv2 key exchanges (RFC 9370), up to seven additional key exchanges may be negotiated. They can be configured by prefixing the algorithm keyword with keX_ (where X is a number between 1 and 7). Additional key exchanges can be made optional by adding keX_none to a proposal.

Extended Sequence Number support may be indicated with the esn and noesn values, both may be included to indicate support for both modes. If omitted, noesn is assumed.

For IKEv2, multiple algorithms of the same kind can be specified in a single proposal, from which one gets selected. For IKEv1, only one algorithm per kind is allowed per proposal, more algorithms get implicitly stripped. Use multiple proposals to offer different algorithm combinations with IKEv1.

Algorithm keywords get separated using dashes. Multiple proposals may be separated by commas. The special value default forms a default proposal of supported algorithms considered safe, and is usually a good choice for interoperability. If no algorithms are specified for AH nor ESP, the default set of algorithms for ESP is included.

connections.<conn>.children.<child>.local_ts [dynamic]
Comma separated list of local traffic selectors to include in CHILD_SA. Each selector is a CIDR subnet definition, followed by an optional proto/port selector. The special value dynamic may be used instead of a subnet definition, which gets replaced by the tunnel outer address or the virtual IP, if negotiated. This is the default.

A protocol/port selector is surrounded by opening and closing square brackets. Between these brackets, a numeric or getservent(3) protocol name may be specified. After the optional protocol restriction, an optional port restriction may be specified, separated by a slash. The port restriction may be numeric, a getservent(3) service name, or the special value opaque for RFC 4301 OPAQUE selectors. Port ranges may be specified as well, none of the kernel backends currently support port ranges, though. If the protocol is icmp or ipv6-icmp, the port is interpreted as ICMP message type if it is less than 256 or as type and code if it is greater or equal to 256, with the type in the most significant 8 bits and the code in the least significant 8 bits.

When IKEv1 is used only the first selector is interpreted, except if the Cisco Unity extension plugin is used. This is due to a limitation of the IKEv1 protocol, which only allows a single pair of selectors per CHILD_SA. So to tunnel traffic matched by several pairs of selectors when using IKEv1 several children (CHILD_SAs) have to be defined that cover the selectors.

The IKE daemon uses traffic selector narrowing for IKEv1, the same way it is standardized and implemented for IKEv2. However, this may lead to problems with other implementations. To avoid that, configure identical selectors in such scenarios.

Controls how the IPsec policy is managed. When set to ike, the policy is installed using the IKE daemon's security policy database. This allows the IPsec policy to be managed by the IKE daemon and enables automatic policy installation and removal.

connections.<conn>.children.<child>.label

Installs a security label on the CHILD_SA, which can be used for policy matching and fine-grained access control. The label is used as an optional identifier/selector on the IKEv2 level when negotiating CHILD_SAs and selecting configs, labels are not installed in the kernel and received labels have to match exactly.

If set to selinux, which is only allowed if SELinux is usable on the system, the configured label is expected to be a generic context (e.g. system_u:object_r:ipsec_spd_t:s0) for which flows, whose context match it via association:polmatch, will trigger an acquire if no SA exists yet for the flow's specific context. The configured label is installed on (trap) policies, so this should generally be combined with trap in start_action. The default value of 0 disables TFC padding, the special value mtu adds TFC padding to create a packet size equal to the Path Maximum Transfer Unit.

connections.<conn>.children.<child>.replay_window IPsec replay window to configure for this CHILD_SA. Larger values than the default of 32 are supported using the Netlink backend only, a value of 0 disables IPsec replay protection. connections.<conn>.children.<child>.per_cpu_sas Enable per-CPU CHILD_SAs. Requires trap in start_action.

The value encap enables a special type of UDP encapsulation (requires enabling encap for the connection if there is no NAT), where a random source port is used for each outbound per-CPU SA (the destination port for all of them remains 4500). This allows using the port for RSS if the SPI can't be used. Note that this type of behavior is not standardized and not negotiated. So regardless of whether the option is enabled, inbound per-CPU SAs with UDP-encapsulation always have the source port set to 0 as the peer's random port is unknown if it has this option enabled.

connections.<conn>.children.<child>.hw_offload Enable hardware offload for this CHILD_SA, if supported by the IPsec implementation. The values crypto or packet enforce crypto or full packet offloading and the installation will fail if the selected mode is not supported by either kernel or device. On Linux, packet also offloads policies, including trap policies. The value auto enables full packet or crypto offloading, if either is supported, but the installation does not fail otherwise. connections.<conn>.children.<child>.copy_df Whether to copy the DF bit to the outer IPv4 header in tunnel mode. This effectively disables Path MTU discovery (PMTUD). Controlling this behavior is not supported by all kernel interfaces. connections.<conn>.children.<child>.copy_ecn Whether to copy the ECN (Explicit Congestion Notification) header field to/from the outer IP header in tunnel mode. Controlling this behavior is not supported by all kernel interfaces. connections.<conn>.children.<child>.copy_dscp Whether to copy the DSCP (Differentiated Services Field Codepoint) header field to/from the outer IP header in tunnel mode. The value out only copies the field from the inner to the outer header, the value in does the opposite and only copies the field from the outer to the inner header when decapsulating, the value yes copies the field in both directions, and the value no disables copying the field altogether. Setting this to yes or in could allow an attacker to adversely affect other traffic at the receiver, which is why the default is out. Controlling this behavior is not supported by all kernel interfaces. connections.<conn>.children.<child>.start_action Action to perform after loading the configuration. The default of none loads the connection only, which then can be manually initiated or used as a responder configuration.

The value trap installs a trap policy, which triggers the tunnel as soon as matching traffic has been detected. The value start initiates the connection actively. These two modes can be combined with trap|start, to immediately initiate a connection for which trap policies have been installed.

When unloading or replacing a CHILD_SA configuration having a start_action different from none, the inverse action is performed. Configurations with start get closed, while such with trap get uninstalled (both happens for connections with trap|start).

connections.<conn>.children.<child>.close_action Action to perform after a CHILD_SA gets closed by the peer. The default of none does not take any action, trap installs a trap policy for the CHILD_SA (note that this is redundant if start_action includes trap). start tries to immediately re-create the CHILD_SA.

close_action does not provide any guarantee that the CHILD_SA is kept alive. It acts on explicit close messages only, but not on negotiation failures. Use trap policies to reliably re-create failed CHILD_SAs.

secrets Section defining secrets for IKE/EAP/XAuth authentication and private key decryption. The secrets section takes sub-sections having a specific prefix which defines the secret type.

It is not recommended to define any private key decryption passphrases, as then there is no real security benefit in having encrypted keys. Either store the key unencrypted or enter the keys manually when loading credentials.

secrets.eap<suffix> EAP secret section for a specific secret. Each EAP secret is defined in a unique section having the eap prefix. EAP secrets are used for XAuth authentication as well. secrets.eap<suffix>.secret Value of the EAP/XAuth secret. It may either be an ASCII string, a hex encoded string if it has a 0x prefix or a Base64 encoded string if it has a 0s prefix in its value. secrets.eap<suffix>.id<suffix> Identity the EAP/XAuth secret belongs to. Multiple unique identities may be specified, each having an id prefix, if a secret is shared between multiple users. secrets.xauth<suffix> XAuth secret section for a specific secret. xauth is just an alias for eap, secrets under both section prefixes are used for both EAP and XAuth authentication. secrets.ntlm<suffix> NTLM secret section for a specific secret. Each NTLM secret is defined in a unique section having the ntlm prefix. NTLM secrets may only be used for EAP-MSCHAPv2 authentication. secrets.ntlm<suffix>.secret Value of the NTLM secret, which is the NT Hash of the actual secret, that is, MD4(UTF-16LE(secret)). The resulting 16-byte value may either be given as a hex encoded string with a 0x prefix or as a Base64 encoded string with a 0s prefix. secrets.ntlm<suffix>.id<suffix> Identity the NTLM secret belongs to. Multiple unique identities may be specified, each having an id prefix, if a secret is shared between multiple users. secrets.ike<suffix> IKE preshared secret section for a specific secret. Each IKE PSK is defined in a unique section having the ike prefix. secrets.ike<suffix>.secret Value of the IKE preshared secret. It may either be an ASCII string, a hex encoded string if it has a 0x prefix or a Base64 encoded string if it has a 0s prefix in its value. secrets.ike<suffix>.id<suffix> IKE identity the IKE preshared secret belongs to. Multiple unique identities may be specified, each having an id prefix, if a secret is shared between multiple peers. secrets.ppk<suffix> Postquantum Preshared Key (PPK) section for a specific secret. Each PPK is defined in a unique section having the ppk prefix.

NAME

swanctl.conf - swanctl configuration file

DESCRIPTION

The swanctl.conf file contains configuration information for swanctl(8). It is an INI-style file organized into sections.

The configuration file defines multiple secrets, named pools, and certification authorities.

SETTINGS

secrets.ppk<suffix>.secret []
Valeur de la PPK. Il peut s'agir d'une chaîne ASCII, d'une chaîne encodée en hexadécimal si elle a un préfixe 0x ou d'une chaîne encodée en Base64 si elle a un préfixe 0s dans sa valeur. Devrait avoir au moins 256 bits d'entropie pour une sécurité de 128 bits.
secrets.ppk<suffix>.id<suffix> []

Section définissant un pool unique avec un nom distinctif.
pools.<name>.addrs []
Sous-réseau ou plage définissant les adresses allouées dans le pool. Accepte un seul sous-réseau CIDR définissant le pool à partir duquel allouer des adresses ou une plage d'adresses (<de>-<à>). Si l'adresse en notation CIDR n'est pas l'ID réseau du sous-réseau (par exemple, 10.1.0.5/24 au lieu de 10.1.0.0/24), les adresses inférieures ne seront pas allouées aux clients (elles pourraient, par exemple, être attribuées manuellement à des hôtes internes comme le serveur VPN lui-même).
