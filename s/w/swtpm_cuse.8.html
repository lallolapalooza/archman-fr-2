NOM

swtpm - Émulateur TPM pour TPM 1.2 et 2.0

SYNTAXE

swtpm socket [OPTIONS]

swtpm chardev [OPTIONS]

swtpm cuse [OPTIONS]

DESCRIPTION

swtpm implémente un émulateur logiciel TPM basé sur libtpms. Il fournit un accès aux fonctionnalités TPM via une interface de socket TCP/IP, ou il peut écouter les commandes sur un périphérique caractère, ou créer une interface CUSE (périphérique caractère en espace utilisateur) pour recevoir les commandes TPM.

Sauf si les paramètres de ligne de commande correspondants sont utilisés, la version socket de swtpm nécessite que la variable d'environnement TPM_PORT soit définie sur le port TCP/IP sur lequel le processus doit écouter les messages de requête TPM.

De même, la variable d'environnement TPM_PATH peut être définie et contenir le nom d'un répertoire où le TPM peut stocker son état persistant.

Le processus swtpm peut être terminé gracieusement en lui envoyant un signal SIGTERM.

La version cuse de swtpm nécessite des droits root pour démarrer le TPM.

Options pour l'interface socket

Les options suivantes sont prises en charge si l'interface socket est choisie :

-p|--port <port>
Utiliser le port donné plutôt que la variable d'environnement TPM_PORT.
-t|--terminate
Terminer le TPM après que le client a fermé la connexion du canal de données (TCP uniquement).
--server [type=tcp][,port=<port>[,bindaddr=<adresse> [,ifname=<nom_interface>]]][,fd=<descripteur>][,disconnect]
Attend des connexions TCP sur le port donné ; si aucun port n'est fourni, un descripteur de fichier doit être passé avec le paramètre fd et les commandes sont lues à partir de ce descripteur de fichier. Si un port est fourni, l'adresse de liaison sur laquelle écouter les connexions TCP peut également être fournie ; l'adresse de liaison par défaut est 127.0.0.1. Si une adresse IPv6 locale de lien est fournie, le nom de l'interface sur laquelle se lier doit être fourni avec ifname.

Ce paramètre active une connexion persistante par défaut, sauf si l'option disconnect est donnée. Ce paramètre doit être utilisé plutôt que les options -p et --fd.

--server type=unixio[,path=<chemin>][,fd=<descripteur>] [,mode=<0...>][,uid=<uid>][,gid=<gid>]
Attend des connexions UnixIO sur le chemin donné. Si aucun chemin n'est fourni, un descripteur de fichier doit être passé à la place. Le paramètre mode permet à un utilisateur de définir les bits de mode du fichier du chemin UnixIO. La valeur des bits de mode doit être donnée sous forme de nombre octal commençant par un '0'. La valeur par défaut est 0770. uid et gid définissent la propriété du chemin du socket UnixIO. Cette opération nécessite des privilèges root.

Options pour l'interface de périphérique caractère

Les options suivantes sont prises en charge si l'interface chardev est choisie :

-c|--chardev <chemin_périphérique >
Utiliser le périphérique donné pour écouter les commandes TPM et envoyer les réponses.
--vtpm-proxy
Créer une instance de périphérique proxy vTPM Linux et lire les commandes TPM à partir de son périphérique backend.

Options pour l'interface CUSE

Les options suivantes sont prises en charge si l'interface cuse est choisie :

-n|--name <NOM>
Le TPM utilisera un périphérique avec le nom donné. Un périphérique avec le nom donné sera créé dans /dev. Ceci est une option obligatoire.
-M|--maj <MAJEUR>
Créer le périphérique avec le numéro majeur donné.
-m|--min <MINEUR>
Créer le périphérique avec le numéro mineur donné.

Options pour les interfaces socket et périphérique caractère :

Les options suivantes sont prises en charge par les interfaces socket et périphérique caractère :

-f|--fd <descripteur >
Utiliser le descripteur de fichier de socket ou le descripteur de fichier de périphérique caractère donné pour recevoir les commandes TPM et envoyer les réponses. Pour l'interface socket, cette option suppose automatiquement -t.
-d|--daemon
Démoniser le processus.
--ctrl type=[unixio|tcp][,path=<chemin>] [,port=<port>[,bindaddr=<adresse>[,ifname=<nom_interface>]]] [,fd=<descripteur_fichier>|clientfd=<descripteur_fichier>] [,mode=<0...>][,uid=<uid>][,gid=<gid>][,terminate]
Cette option ajoute un canal de contrôle au TPM. Le canal de contrôle peut utiliser soit un socket UnixIO avec un chemin ou un descripteur de fichier donné, soit il peut utiliser un socket TCP sur le port ou le descripteur de fichier donné. Si un port est fourni, l'adresse de liaison sur laquelle écouter les connexions TCP peut également être fournie ; l'adresse de liaison par défaut est 127.0.0.1. Si une adresse IPv6 locale de lien est fournie, le nom de l'interface sur laquelle se lier doit être fourni avec ifname.

Le paramètre mode permet à un utilisateur de définir les bits de mode du fichier du chemin UnixIO. La valeur des bits de mode doit être donnée sous forme de nombre octal commençant par un '0'. La valeur par défaut est 0770. uid et gid définissent la propriété du chemin du socket UnixIO. Cette opération nécessite des privilèges root.

Le paramètre terminate active la terminaison automatique de swtpm lorsque la connexion du canal de contrôle a été perdue. Ceci est utile dans les scénarios où la connexion du canal de contrôle est maintenue en permanence, par exemple par QEMU, et que swtpm doit se terminer en cas de terminaison anormale du client qui ne peut plus envoyer CMD_SHUTDOWN via le canal de contrôle.

Le canal de contrôle permet un contrôle hors bande du TPM, tel que la réinitialisation du TPM.

Options pour toutes les interfaces

Les options suivantes sont prises en charge par toutes les interfaces :

--tpmstate dir=<répertoire>|backend-uri=<uri>[,mode=<0...>][,lock]
Utiliser le chemin donné plutôt que la variable d'environnement TPM_PATH.

Si dir est spécifié, les fichiers d'état TPM seront écrits dans le répertoire avec les bits de mode de fichier donnés. Cette valeur doit être donnée sous forme de nombre octal commençant par un '0'. La valeur par défaut est 0640.

Si backend-uri est spécifié, les données d'état TPM seront stockées dans l'URI. Actuellement, backend-uri=dir://<chemin_vers_répertoire> et backend-uri=file://<chemin_vers_répertoire> sont disponibles. Pour 'dir://', l'URI doit spécifier le chemin du répertoire où les fichiers sont stockés. Si chemin_vers_répertoire commence par un '/' alors le chemin est interprété comme un chemin absolu, sinon c'est un chemin relatif au répertoire courant. Pour 'file://', l'URI doit spécifier un seul fichier ou périphérique bloc où l'état TPM sera stocké. Un périphérique bloc doit exister au préalable et être suffisamment grand pour stocker tout l'état. (depuis v0.7)

Si lock est spécifié, le backend de stockage TPM verrouillera le fichier d'état TPM pour éviter son accès concurrent par une autre instance swtpm. La valeur par défaut, si ce paramètre d'option est manquant, dépend du backend de stockage. Pour le backend de répertoire, la valeur par défaut est que le verrouillage est toujours activé, et par conséquent ce paramètre d'option n'a pas besoin d'être fourni. Pour le backend de fichier, il est requis car la valeur par défaut est que le verrouillage n'est pas automatiquement activé. Pour éviter le verrouillage, lock=false peut être utilisé.

--tpm2
Choisissez la fonctionnalité TPM 2 ; par défaut, un TPM 1.2 est choisi.
--log [fd=<descripteur de fichier>|file=<chemin>][,level=<n>] [,prefix=<préfixe>][,truncate]
Active la journalisation vers un fichier donné par son descripteur de fichier ou son chemin. Utilisez '-' pour le chemin afin de supprimer la journalisation.

Le paramètre level permet à l'utilisateur de choisir le niveau de journalisation. À partir du niveau de journalisation 5, la journalisation de débogage de libtpms est activée.

Toutes les lignes journalisées seront préfixées par prefix. Par défaut, aucun préfixe n'est ajouté.

Si truncate est passé, le fichier journal sera tronqué.

--locality reject-locality-4[,allow-set-locality]
Le paramètre reject-locality-4 provoquera le renvoi de messages d'erreur TPM pour les requêtes visant à définir le TPM en localité 4.

Le paramètre allow-set-locality permet au swtpm de recevoir les commandes TPM/TPM2_SetLocality. Ce paramètre est utile si l'accès au pilote proxy VTPM Linux est activé par passage de descripteur de fichier. Cette option est implicite avec l'option --vtpm-proxy et n'a donc pas besoin d'être explicitement définie si cette option est passée. Dans tous les autres cas, il convient de faire attention à qui peut envoyer la commande TPM/TPM2_SetLocality.

--key file=<fichier clé>|fd=<descripteur de fichier> [,format=<hex|binaire>][,mode=aes-cbc|aes-256-cbc], [remove[=true|false]]
Active le chiffrement des fichiers d'état du TPM. Le fichier clé doit contenir une clé AES de taille prise en charge ; les clés de 128 bits (16 octets) et de 256 bits (32 octets) sont prises en charge.

La clé peut être au format binaire, auquel cas la taille du fichier doit être de 16 ou 32 octets. Si la clé est au format hexadécimal (par défaut), la clé peut être composée de 32 ou 64 chiffres hexadécimaux commençant par un '0x' optionnel.

Le paramètre mode indique quel mode de chaînage de blocs doit être utilisé. Actuellement, aes-cbc (aes-128-cbc) et aes-256-cbc sont pris en charge. Les données chiffrées sont protégées en intégrité à l'aide de encrypt-then-mac.

Le paramètre remove tentera de supprimer le fichier clé donné une fois la clé lue.

--key pwdfile=<fichier de mot de passe>|pwdfd=<descripteur de fichier> [,mode=aes-cbc|aes-256-cbc][remove[=true|false]][,kdf=sha512|pbkdf2]
Cette variante du paramètre key permet à un utilisateur de fournir une phrase secrète dans un fichier. Le fichier est lu et une clé en est dérivée à l'aide d'un hachage SHA512 ou de PBKDF2. Par défaut, PBKDF2 est utilisé.
--migration-key file=<fichier clé>|fd=<descripteur de fichier> [,format=<hex|binaire>][,mode=aes-cbc|aes-256-cbc] [,remove[=true|false]]
La disponibilité d'une clé de migration garantit que l'état du TPM ne sera pas révélé sous forme non chiffrée lorsque les blobs d'état du TPM sont récupérés via l'interface ioctl. La clé de migration n'est pas utilisée pour chiffrer l'état du TPM écrit dans les fichiers, c'est à cela que sert le paramètre --key.

La clé de migration et la clé utilisée pour chiffrer les fichiers d'état du TPM peuvent être identiques.

Alors que la clé pour les fichiers d'état du TPM doit rester avec les fichiers qu'elle chiffre, la clé de migration doit rester avec les blobs d'état du TPM. Si, par exemple, l'état du TPM est migré entre des hôtes dans un centre de données, alors la clé de migration du TPM doit être disponible à toutes les destinations. Elle peut donc effectivement être une clé partagée entre toutes les machines du centre de données. En revanche, la clé utilisée pour chiffrer les fichiers d'état du TPM peut être différente pour chaque TPM et n'a besoin d'être disponible que sur l'hôte où réside l'état du TPM.

La clé de migration permet le chiffrement des blobs d'état du TPM. Le fichier clé doit contenir une clé AES de taille prise en charge ; les clés de 128 bits (16 octets) et de 256 bits (32 octets) sont prises en charge.

La clé peut être au format binaire, auquel cas la taille du fichier doit être de 16 ou 32 octets. Si la clé est au format hexadécimal (par défaut), la clé peut être composée de 32 ou 64 chiffres hexadécimaux commençant par un '0x' optionnel.

Le paramètre mode indique quel mode de chaînage de blocs doit être utilisé. Actuellement, aes-cbc (aes-128-cbc) et aes-256-cbc sont pris en charge. Les données chiffrées sont protégées en intégrité à l'aide de encrypt-then-mac.

Le paramètre remove tentera de supprimer le fichier clé donné une fois la clé lue.

--migration-key pwdfile=<fichier de phrase secrète>|pwdfd=<descripteur de fichier> [,mode=aes-cbc|aes-256-cbc][,remove[=true|false]][,pdf=sha512|pbkdf2]
Cette variante du paramètre key permet à un utilisateur de fournir une phrase secrète dans un fichier. Le fichier est lu et une clé en est dérivée à l'aide d'un hachage SHA512 ou de PBKDF2. Par défaut, PBKDF2 est utilisé.
--pid file=<fichier pid>|fd=<descripteur de fichier>
Cette option permet à un utilisateur de définir le nom du fichier dans lequel l'ID de processus (pid) du TPM sera écrit. Il est également possible de passer un descripteur de fichier vers un fichier qui a été ouvert en écriture.
-r|--runas <propriétaire>
Passe à l'utilisateur donné. Cette option ne peut être utilisée que lorsque swtpm est démarré en tant que root.
-R|--chroot <chemin<gt>
Chroot vers le répertoire donné au démarrage. Cette option ne peut être utilisée que lorsque swtpm est démarré en tant que root.
--seccomp action=none|log|kill (depuis v0.2)
Cette option permet à un utilisateur de sélectionner l'action à entreprendre par le profil seccomp lorsqu'un appel système est exécuté et qu'il n'est pas autorisé. Par défaut, l'action est kill. Pour désactiver le profil seccomp, choisissez none. L'action log journalise les appels système fautifs. L'action log n'est disponible que si libseccomp prend en charge la journalisation.

Cette option n'est disponible que sur Linux et uniquement si swtpm a été compilé avec le support de libseccomp.

--flags [not-need-init][,startup-clear|startup-state|startup-deactivated|startup-none][,disable-auto-shutdown]
Le drapeau not-need-init permet au TPM d'accepter les commandes TPM immédiatement après le démarrage sans nécessiter d'INIT envoyée via le canal de commande (voir l'option '-i' de swtpm_ioctl).

Les options startup provoquent l'envoi automatique d'une commande TPM_Startup ou TPM2_Startup. L'option startup-deactivated n'est valide que pour un TPM 1.2. Ces options impliquent not-need-init, à l'exception de l'option startup-none, qui n'entraîne l'envoi d'aucune commande.

Si --vtpm-proxy est utilisé, startup-clear est automatiquement choisi, mais cela peut être modifié avec cette option.

Le drapeau disable-auto-shutdown empêche swtpm d'envoyer automatiquement une commande TPM2_Shutdown() avant la réinitialisation d'un TPM 2 ou avant la terminaison du processus swtpm. Lorsque ce drapeau n'est pas fourni, swtpm envoie cette commande pour éviter d'augmenter le compteur de verrouillage par attaque par dictionnaire (DA) et finalement un verrouillage DA par le TPM 2 en raison de l'omission de l'envoi d'une commande TPM2_Shutdown() requise avant la réinitialisation du TPM 2 ou la terminaison du processus swtpm.

--migration [incoming][,release-lock-outgoing]
Cette option permet de contrôler le verrouillage du stockage NVRAM afin de prendre en charge la migration entre des hôtes disposant d'une configuration de stockage partagé pour le répertoire d'état de swtpm et si le stockage est pris en charge par le backend. Le backend de stockage de répertoire, par exemple, prend en charge le verrouillage et nécessite donc l'utilisation de cette option en cas de stockage partagé. En fournissant le paramètre d'option incoming, swtpm diffère le verrouillage de la NVRAM jusqu'à ce que les blobs d'état soient reçus ou jusqu'à ce que la première commande TPM soit traitée si aucun blob d'état n'a été reçu. Le paramètre d'option release-lock-outgoing fait en sorte que swtpm libère tout verrou NVRAM une fois que le blob 'savestate' du TPM est reçu de swtpm. Pour éviter de libérer le verrou trop tôt, les blobs d'état 'permanent' et 'volatile' doivent être reçus avant le blob 'savestate'.
--profile name=<profile-name>|profile=<json-profile>|file=<filename>|fd=<fd>[,remove-disabled=check|fips-host] (since v0.10)
Cette option permet de définir un profil pour un TPM 2. Un profil intégré peut être sélectionné par son nom en utilisant le paramètre d'option name=. Avec le paramètre d'option profile=, un profil formaté en JSON peut être passé directement. Avec le paramètre d'option file=, un profil formaté en JSON sera lu à partir d'un fichier. Le paramètre d'option fd= permet de le lire à partir d'un descripteur de fichier.

Les profils doivent référencer le nom d'un profil intégré. Notez que seul le profil 'custom', ou les profils dont le nom commence par 'custom:', peuvent être modifiés et fournir une liste d'algorithmes, de commandes ou d'attributs qui contrôlent les algorithmes cryptographiques qu'un TPM 2 active. Si l'une de ces listes n'est pas fournie, la liste correspondante du profil intégré 'custom' est utilisée.

L'option de ligne de commande suivante sélectionne le profil 'custom' sous le nouveau nom 'custom:test' avec l'attribut 'fips-host' défini :

[...] --profile '{"Name":"custom:test", "Attributes":"fips-host"}'

Le profil ne peut être défini que lors du tout premier démarrage d'une instance de TPM 2 et tant qu'aucun fichier d'état n'existe. Le profil ne peut plus être modifié par la suite et, s'il est passé à nouveau en utilisant cette option, une erreur se produira.

Le paramètre d'option remove-disabled indique à swtpm de supprimer du profil les algorithmes qui sont désactivés lorsque FIPS est activé sur un hôte (paramètre fips-host ; référence RHEL 9.4+ mode FIPS) et que l'accès d'OpenSSL aux algorithmes cryptographiques est restreint. Le paramètre check peut être utilisé pour vérifier qu'un algorithme est effectivement désactivé avant de le supprimer. Cette option n'est prise en charge que si le profil custom est choisi. Dans ce cas, il effectuera (actuellement) les actions suivantes :

  • supprimer camellia, tdes et rsaes (chiffrement RSA avec padding PKCS#1 v1.5)
  • désactiver le support de signature (RSA et EC) sur SHA1
  • désactiver le chiffrement RSA sans padding
  • définir la taille minimale des clés RSA à 2048 bits
  • définir la taille minimale des clés EC à 224 bits

Tous les autres algorithmes restent activés, y compris ceux que FIPS n'autorise normalement pas, tels que ecdaa et ecschnorr, entre autres. La liste des algorithmes désactivés sera étendue à l'avenir lorsque le mode FIPS sur l'hôte désactivera davantage d'algorithmes. Comme swtpm peut ajouter des Attributs au profil qui nécessitent un certain StateFormatLevel, il est recommandé d'omettre le champ StateFormatLevel du profil.

Pour voir la liste des algorithmes pris en charge et pouvant être désactivés, on peut utiliser swtpm comme suit.

NAME


swtpm_cuse — interface to the TPM character device CUSE driver






SYNOPSIS


swtpm_cuse [options] --tpmstate dir


swtpm_cuse [options] --tpm2 --tpmstate dir






DESCRIPTION


The swtpm_cuse utility provides access to a TPM
    (Trusted Platform Module) by emulating the TPM device character device
    interface using the CUSE (Character device USERSPACE) driver. It allows
    userspace applications to interact with the emulated TPM without requiring
    direct kernel module access.


The TPM state is stored in a specified directory (--tpmstate dir). This directory is created
    if it does not exist.


The swtpm_cuse utility can be used for both TPM 1.2
    and TPM 2.0.


By default, the utility creates a character device node under
    /dev/cuse/ (e.g. /dev/cuse/vtpm0). The name
    of the device node can be influenced by the --device
    option.


If the --tpm2 option is used, then the utility
    will emulate a TPM 2.0 device. Otherwise it emulates a TPM 1.2 device.


The --tpmstate option specifies the directory
    where the TPM state (like NVRAM contents) is stored. If the directory does
    not exist, it will be created.




Options for
    socket interface



  
--log MASK

  
Set the trace level mask. See swtpm_setup(8) for
      details.

  
--log-file FILE

  
Write log messages to the specified FILE instead of
      stderr.








Options for
    character device interface



  
--device NAME

  
Use the given NAME for the character device node. The
      default is vtpm0.








Options for the CUSE interface



  
--cuse-dir DIR

  
Use the specified directory DIR for the CUSE device
      node. The default is /dev/cuse.








Options for
    socket and character device interfaces:



  
--tpmstate DIR

  
Store the TPM state in the directory DIR. If the
      directory does not exist, it will be created. This option is mandatory.

  
--tpm2

  
Emulate a TPM 2.0 device. Without this option, a TPM 1.2 device is
      emulated.

  
--virq

  
Enable virtual IRQ. This allows the TPM to signal the host.

  
--pid PIDFILE

  
Write the PID of the swtpm_cuse process to the file
      PIDFILE.

  
--transfer

  
Enable transfer of TPM state to the guest. This is useful when the guest
      needs to access the TPM state persisted by a previous instance of
      swtpm_cuse.

  
--init MASK

  
Initialize the TPM state according to the specified mask. See
      swtpm_setup(8) for details.

  
--predefined PROFILE

  
Use a predefined profile for the TPM state initialization. The available
      profiles are:
    

      
null

      
No commands or algorithms are enabled. Use with caution.

      
previous

      
The profile that was used the last time the TPM state was initialized.

      
compat

      
Profile enabling commands and algorithms that were enabled in
          libtpms v0.9. This profile is automatically
          used when the state does not have a profile, for example when it was
          created by libtpms v0.9 or before.

      
custom

      
This profile allows customization of enabled algorithms and commands.
          This profile requires at least libtpms
          v0.10.

      
default

      
This profile enables all currently supported commands and algorithms.
          It is applied when the user chooses no profile.

    

  

  
--profile PROFILE

  
Set the TPM profile to use. This option can be used multiple times to
      define a custom profile. It can also be used to override the default
      profile.

  
--ordinal HEX

  
Set the TPM version ordinal. This is used to select the TPM version if
      not specified by --tpm2. The default is TPM
      1.2.








Options for
    all interfaces



  
--print-profiles

  
Display the profiles supported by libtpms.

  
--print-info

  
Display information about the TPM from libtpms TPMLIB_GetInfo call and
      exit. Use the --tpm2 option for information
      about TPM 2. If the --tpmstate option is also
      provided then the output will show information about the profile as
      well. Note that with this option a TPM state may be created if none
      existed before.
    
The following values can be provided. All of the values can be
        or'ed (or added) together to get information about all of them in one
        query.

  






    
  
  • 0x1: information about the specification the TPM implementation
    followed
    • 
  
  • 0x2: information about the manufacturer, model and version of the TPM
    • 
  
  • 0x4: lists supported RSA and Camellia key sizes
    • 
  
  • 0x8: describes supported and enabled algorithms
    • 
  
  • 0x10: describes supported and enabled commands
    • 
  
  • 0x20: describes the active profile
    • 
  
  • 0x40: lists all built-in profiles
    • 
  
  • 0x80: describes supported attributes
    • 






  
-h|--help

  
Display usage info.










NOTES


If a TPM 2 is used, the user is typically required to send a
    TPM2_Shutdown() command to a TPM 2 to avoid possibly increasing the
    TPM_PT_LOCKOUT_COUNTER that may lead to a dictionary attack (DA) lockout
    upon next startup (TPM2_Startup()) of the TPM 2. Whether the
    TPM_PT_LOCKOUT_COUNTER is increased depends on previous commands sent to the
    TPM 2 as well as internal state of the TPM 2. One example that will trigger
    the counter to increase is the omission of a password when trying to access
    a password-protected object or NVRAM location that has the DA attribute set,
    followed by termination of swtpm without sending TPM2_Shutdown(). To
    avoid a DA lockout swtpm will make a best-effort and send a
    TPM2_Shutdown(SU_STATE) or TPM2_Shutdown(SU_CLEAR) if found necessary.
