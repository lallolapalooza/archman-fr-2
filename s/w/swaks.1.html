NOM

Swaks - Swiss Army Knife SMTP, le testeur de transactions SMTP tout usage

DESCRIPTION

L'objectif principal de conception de Swaks est d'être un outil de test SMTP flexible, scriptable et orienté transaction. Il gère les fonctionnalités et extensions SMTP telles que TLS, l'authentification et le pipelining ; plusieurs versions du protocole SMTP, y compris SMTP, ESMTP et LMTP ; et plusieurs méthodes de transport, y compris les sockets de domaine UNIX, les sockets de domaine internet et les pipes vers des processus lancés. Les options peuvent être spécifiées dans des variables d'environnement, des fichiers de configuration et la ligne de commande, permettant une configurabilité maximale et une facilité d'utilisation pour les opérateurs et les scripteurs.

DÉMARRAGE RAPIDE

Livrer un email de test standard à user@example.com sur le port 25 de test-server.example.net :

swaks --to user@example.com --server test-server.example.net

Livrer un email de test standard, nécessitant l'authentification CRAM-MD5 en tant qu'utilisateur me@example.com. Un en-tête "X-Test" sera ajouté au corps de l'email. Le mot de passe d'authentification sera demandé s'il ne peut pas être obtenu à partir de votre fichier .netrc.

swaks --to user@example.com --from me@example.com --auth CRAM-MD5 --auth-user me@example.com --header-X-Test "email de test"

Tester un antivirus utilisant EICAR dans une pièce jointe. Ne pas afficher la partie MESSAGE DATA :

swaks -t user@example.com --attach - --server test-server.example.com --suppress-data </path/to/eicar.txt

Tester un filtre anti-spam utilisant GTUBE dans le corps d'un email, acheminé via les enregistrements MX de example.com :

swaks --to user@example.com --body @/path/to/gtube/file

Livrer un email de test standard à user@example.com en utilisant le protocole LMTP via un fichier socket de domaine UNIX

swaks --to user@example.com --socket /var/lda.sock --protocol LMTP

Rapporter tous les destinataires d'un fichier texte qui ne sont pas vérifiables sur un serveur de test :

for E in `cat /path/to/email/file`
do
    swaks --to $E --server test-server.example.com --quit-after RCPT --hide-all
    [ $? -ne 0 ] && echo $E
done

TERMES ET CONVENTIONS

Ce document essaie d'être cohérent et précis dans son utilisation des termes suivants afin de réduire la confusion.

Cible
La cible d'une transaction est l'élément auquel Swaks se connecte. Ce terme générique est utilisé tout au long de la documentation car la plupart des autres termes impliquent incorrectement quelque chose sur le transport utilisé.
Transport
Le transport est la méthode sous-jacente utilisée pour se connecter à la cible.
Transaction
Une transaction est l'établissement d'une connexion via un transport vers une cible et l'utilisation d'un protocole de messagerie pour tenter de livrer un message.
Protocole
Le protocole est le langage d'application utilisé pour communiquer avec la cible. Ce document utilise le terme générique SMTP pour parler des trois protocoles pris en charge, sauf lorsqu'il indique qu'il parle du protocole spécifique 'SMTP' et exclut les autres.
Message
Les protocoles SMTP existent pour transférer des messages, un ensemble d'octets dans un format convenu qui a un expéditeur et un destinataire.
Enveloppe
L'enveloppe d'un message contient l'expéditeur et le destinataire "réels" d'un message. Elle peut également être désignée par ses composants, expéditeur-enveloppe et destinataires-enveloppe. Il est important de noter que l'enveloppe d'un message ne doit pas nécessairement correspondre à ses en-têtes "À" et "De".
DATA
La partie DATA d'une transaction SMTP est le message réel qui est transporté. Elle comprend à la fois les en-têtes et le corps du message. DATA et corps sont parfois utilisés de manière synonyme, mais ce sont toujours deux choses distinctes dans ce document.
En-têtes
Les en-têtes d'un message sont définis comme toutes les lignes de la section DATA du message avant la première ligne vide. Ils contiennent des informations sur l'email qui seront affichées au destinataire, telles que "À", "De", "Objet", etc. Dans ce document, les en-têtes seront toujours écrits avec une première lettre capitale et deux-points à la fin.
Corps
Le corps d'un message est la partie de sa section DATA qui suit la première ligne vide.
Option
Une option est un drapeau qui modifie le comportement de Swaks. Toujours appelée option, quelle que soit la manière dont elle est fournie. Par exemple, "--no-data-fixup" est une option.
Argument
Lorsqu'une option prend des données supplémentaires en plus de l'option elle-même, ces données supplémentaires sont appelées un argument. Dans "--quit-after <stop-point>'", "<stop-point>" est l'argument de l'option "--quit-after".
<chaîne-littérale>
Lorsqu'il est utilisé dans la définition d'une option, le texte à l'intérieur d'angles ("<>") indique une étiquette descriptive pour une valeur que l'utilisateur doit fournir. Par exemple, "--quit-after <stop-point>" indique que "<stop-point>" doit être remplacé par une valeur de point d'arrêt valide.
[<valeur-optionnelle>]
Lorsqu'il est utilisé dans la définition d'une option, le texte entre crochets ([]) indique que la valeur est optionnelle et peut être omise. Par exemple, "--to [<destinataire>]" indique que l'option "--to" peut être utilisée avec ou sans destinataire spécifié.

TRAITEMENT DES OPTIONS

Pour éviter toute confusion potentielle dans ce document, un drapeau pour Swaks est toujours désigné par le terme "option". Si l'option prend des données supplémentaires, ces données supplémentaires sont désignées comme un argument de l'option. Par exemple, "--from fred@example.com" peut être fourni à Swaks sur la ligne de commande, "--from" étant l'option et "fred@example.com" étant l'argument de "--from".

Les options et leurs arguments sont les seuls moyens de fournir des informations à Swaks. Si Swaks trouve des données lors du traitement des options qui ne sont ni une option ni un argument d'option, il générera une erreur et quittera. Par exemple, si "--no-data-fixup 1" était trouvé sur la ligne de commande, cela entraînerait une erreur car "--no-data-fixup" ne prend pas d'argument et Swaks ne saurait donc pas quoi faire de 1.

Les options peuvent être fournies à Swaks de trois manières : dans un fichier de configuration, dans des variables d'environnement et sur la ligne de commande. Selon l'option spécifique et si un argument lui est donné, Swaks peut demander à l'utilisateur l'argument.

Lorsque Swaks évalue ses options, il recherche d'abord un fichier de configuration (soit à un emplacement par défaut, soit spécifié avec "--config"). Ensuite, il évalue les options dans les variables d'environnement. Enfin, il évalue les options de la ligne de commande. À chaque tour de traitement, les options définies précédemment seront remplacées. De plus, toute option peut être précédée de "no-" pour que Swaks oublie que la variable avait été précédemment définie (soit lors d'un tour précédent, soit plus tôt dans le même tour). Cette capacité est nécessaire car de nombreuses options traitent une valeur définie-mais-sans-argument différemment d'une valeur non définie.

En règle générale, si la même option est fournie plusieurs fois, la dernière fois qu'elle est fournie est celle qui sera utilisée. Cela s'applique aussi bien à l'interne d'une méthode (si "--from user1@example.com --from user2@example.com" est donné, "user2@example.com" sera utilisé) qu'entre les méthodes (si &quo t;depuis user1@example.com" est donné dans un fichier de configuration et "--from user2@example.com" est donné sur la ligne de commande, "user2@example.com" sera utilisé)

Chaque définition d'option se termine par un synopsis entre parenthèses expliquant le comportement de l'option. Les codes suivants peuvent être utilisés

Arg-None, Arg-Optional, Arg-Required
Ces trois codes sont mutuellement exclusifs et décrivent si l'option prend ou non un argument. Notez que cela ne décrit pas nécessairement si l'argument doit être spécifié directement, mais plutôt si un argument est requis à terme. Par exemple, "--to" est étiqueté comme Arg-Required, mais il est légal de spécifier "--to" sur la ligne de commande sans argument. C'est parce que Swaks peut demander l'argument requis s'il n'est pas fourni directement.
From-Prompt
Une option étiquetée From-Prompt demandera interactivement à l'utilisateur l'argument si aucun n'est fourni.
From-File
Une option étiquetée From-File traitera les arguments comme des fichiers dans certaines situations.

Si l'argument initial est "-", l'argument final est le contenu de "STDIN". Plusieurs options peuvent toutes spécifier "STDIN", mais le même contenu sera utilisé pour chacune d'elles.

Si l'argument initial est précédé de "@", l'argument sera traité comme un chemin vers un fichier. Le fichier sera ouvert et son contenu sera utilisé comme argument final. Si le contenu du fichier ne peut pas être lu, Swaks s'arrêtera. Pour spécifier une chaîne littérale commençant par un "@", utilisez deux "@". Le premier sera retiré. Il n'est pas possible d'inclure un fichier non qualifié commençant par un signe "@" (comme "--attach @file.txt" ou "--attach @@file.txt"), mais si vous incluez un chemin vers le fichier qui sépare les deux "@", cela fonctionnera (par exemple "--attach @./@file.txt" inclura le contenu du fichier @file.txt).

Sensitive
Si une option marquée Sensitive tente de demander à l'utilisateur un argument et que l'option "--protect-prompt" est définie, Swaks tentera de masquer la saisie de l'utilisateur pour qu'elle ne soit pas affichée sur le terminal. Swaks essaie de masquer la saisie de plusieurs manières, mais si aucune d'entre elles ne fonctionne, le programme continuera avec une saisie non masquée.
Deprecated
Une option marquée Deprecated a été officiellement dépréciée et sera supprimée dans une future version. Voir la section "DEPRECATIONS" de cette documentation pour plus de détails sur les dépréciations.

Le mécanisme exact et le format d'utilisation de chaque type sont listés ci-dessous.

FICHIERS DE CONFIGURATION
Un fichier de configuration peut être utilisé pour définir des options couramment utilisées ou anormalement verbeuses. Par défaut, Swaks recherche dans l'ordre $SWAKS_HOME/.swaksrc, $HOME/.swaksrc, et $LOGDIR/.swaksrc. Si l'un d'eux est trouvé existant (et que "--config" n'a pas été utilisé) ce fichier est utilisé comme fichier de configuration.

De plus, un fichier de configuration dans un emplacement non standard peut être spécifié en utilisant "--config". Si cela est défini et qu'aucun argument n'est donné, Swaks n'utilisera aucun fichier de configuration, y compris les fichiers par défaut. Si "--config" pointe vers un fichier lisible, il est utilisé comme fichier de configuration, remplaçant tout défaut qui pourrait exister. S'il pointe vers un fichier illisible, une erreur sera affichée et Swaks s'arrêtera.

Un ensemble de valeurs par défaut "portables" peut également être créé en ajoutant des options à la fin du fichier programme Swaks. Tel qu'il est distribué, la dernière ligne de Swaks devrait être "__END__". Toutes les lignes ajoutées après "__END__" seront traitées comme le contenu d'un fichier de configuration. Cela permet à un ensemble de préférences utilisateur d'être automatiquement copié de serveur en serveur dans un seul fichier.

Si les fichiers de configuration n'ont pas été explicitement désactivés, la configuration "__END__" est toujours lue. Un seul autre fichier de configuration sera jamais utilisé par invocation de Swaks, même si plusieurs fichiers de configuration sont spécifiés. Si la configuration "__END__" et une autre configuration doivent être lues, la configuration "__END__" sera traitée en premier. Spécifier l'option "--config" sans argument désactive le traitement de la configuration "__END__" et des fichiers de configuration réels.

Dans un fichier de configuration, les lignes commençant par un dièse ("#") sont ignorées. Toutes les autres lignes sont supposées être une option pour Swaks, avec le trait d'union ou les traits d'union initiaux facultatifs. Tout ce qui suit la première espace de la ligne d'option est supposé être l'argument de l'option et n'est pas traité par le shell. Par conséquent, les guillemets sont généralement inutiles et seront inclus littéralement dans l'argument.

Il y a une différence subtile entre fournir une option sans argument et fournir une option avec un argument vide. Si une ligne d'option n'a pas d'espace, la ligne entière est traitée comme une option et il n'y a pas d'argument. Si la ligne se termine par une seule espace, elle sera traitée comme une option avec un argument vide. Donc, "apt" sera traité comme "--apt", mais "apt " sera traité comme "--apt ''".

Voici un exemple du contenu d'un fichier de configuration :

# utiliser toujours cet expéditeur, quel que soit le serveur ou l'utilisateur connecté
--from fred@example.com
# Je préfère que mes e-mails de test aient un en-tête From agréable. Notez
# l'absence de traits d'union sur l'option et l'absence de guillemets autour
# de l'argument entier.
h-From: "Fred Example" <fred@example.com>

Options spécifiques au fichier de configuration :

--config [<config-file>]
Cette option fournit un chemin vers un fichier de configuration spécifique à utiliser. Si elle est spécifiée sans argument, aucun fichier de configuration trouvé automatiquement (via $HOME, etc., ou "__END__") ne sera traité. Si l'argument est un fichier valide, ce fichier sera utilisé comme fichier de configuration (après la configuration "__END__"). Si l'argument n'est pas un fichier valide et lisible, Swaks générera une erreur et s'arrêtera. Cette option peut être spécifiée plusieurs fois, mais seule la première fois où elle est spécifiée (dans l'ordre de recherche des variables d'environnement et de la ligne de commande) sera utilisée. (Arg-Optional)
VARIABLES D'ENVIRONNEMENT DE CONFIGURATION
Les options peuvent être fournies via des variables d'environnement. Les variables sont sous la forme $SWAKS_OPT_name, où "name" est le nom de l'option qui serait spécifiée sur la ligne de commande. Comme les traits d'union ne sont pas autorisés dans les noms de variables d'environnement dans la plupart des shells de type UNIX, aucun trait d'union initial ne doit être utilisé et tout trait d'union dans le nom de l'option doit être remplacé par des underscores. Les exemples suivants créeraient les mêmes options que celles montrées dans l'exemple de fichier de configuration : 
$ SWAKS_OPT_from='fred@example.com'
$ SWAKS_OPT_h_From='"Fred Example" <fred@example.com>'

Définir une variable à une valeur vide équivaut à la spécifier sur la ligne de commande sans argument. Par exemple, définir <SWAKS_OPT_server=""> demanderait à Swaks de solliciter l'utilisateur pour le serveur auquel se connecter à chaque invocation. Sous Windows, il n'est pas possible de définir des variables d'environnement vides. Le comportement peut être simulé en définissant la variable d'environnement sur "<>" à la place. De plus, intégrer le nom de l'en-tête dans l'option d'en-tête via une variable d'environnement n'est pas autorisé sous Windows (par exemple "SWAKS_OPT_header_Foo=bar" entraînera une erreur, mais "SWAKS_OPT_header="Foo: bar"" fonctionnera.)

Comme il n'y a pas d'ordre intrinsèque dans les options fournies en définissant des variables d'environnement, les options sont triées avant d'être traitées. Ce n'est pas une excellente solution, mais elle définit au moins le comportement, qui serait autrement indéfini. Par exemple, si à la fois $SWAKS_OPT_from et $SWAKS_OPT_f étaient définis, la valeur de $SWAKS_OPT_from serait utilisée, car elle est triée après $SWAKS_OPT_f. De plus, en raison de l'absence d'ordre intrinsèque dans le traitement de l'environnement, la désactivation des options avec le préfixe "no-" n'est pas fiable. Cela fonctionne si l'option désactivée est triée avant "no-", mais échoue si elle est triée après. Comme "no-" est principalement destiné à fonctionner entre les types de configuration (par exemple, désactiver en ligne de commande une option définie dans un fichier de configuration), cela ne devrait pas poser de problème.

En plus de définir l'équivalent des options de ligne de commande, $SWAKS_HOME peut être défini sur un répertoire contenant le .swaksrc par défaut à utiliser.

OPTIONS DE LIGNE DE COMMANDE
La dernière méthode pour fournir des options à Swaks est via la ligne de commande. Les options se comportent d'une manière cohérente avec la plupart des programmes de ligne de commande de type UNIX. De nombreuses options ont à la fois une forme courte et une forme longue (par exemple "-s" et "--server"). Par convention, les options courtes ooptions sont spécifiés avec un trait d'union simple et les options longues avec un double trait d'union. Ceci n'est qu'une convention et l'un ou l'autre préfixe fonctionnera avec l'un ou l'autre type.

L'exemple suivant illustre celui montré dans les sections fichiers de configuration et variables d'environnement :

$ swaks --from fred@example.com --h-From: '"Fred Example" <fred@example.com>'

TRANSPORTS

Swaks peut se connecter à une cible via des tuyaux UNIX (« pipes »), des sockets de domaine UNIX (« sockets UNIX ») ou des sockets de domaine Internet (« sockets réseau »). La connexion via des sockets réseau est le comportement par défaut. En raison de la nature singulière du transport utilisé, chaque ensemble d'options dans la section suivante est mutuellement exclusif. La spécification de plus d'une des options "--server", "--pipe" ou "--socket" entraînera une erreur. Le mélange d'autres options entre les types de transport ne fera qu'ignorer les options non pertinentes. Vous trouverez ci-dessous une brève description de chaque type de transport et des options qui lui sont spécifiques.

SOCKETS RÉSEAU
Ce transport tente de délivrer un message via TCP/IP, la méthode standard de délivrance SMTP. C'est le transport par défaut pour Swaks. Si aucune des options "--server", "--pipe" ou "--socket" n'est fournie, alors ce transport est utilisé et le serveur cible est déterminé à partir du domaine du destinataire (voir "--server" ci-dessous pour plus de détails).

Ce transport nécessite le module IO::Socket::IP pour les sockets IPv4 et IPv6. Si ce module ne peut pas être chargé, Swaks tentera d'utiliser la bibliothèque IO::Socket pour IPv4 et IO::Socket::INET6 pour le support IPv6. Tenter d'utiliser ce transport sans aucune de ces bibliothèques disponibles entraînera une erreur et l'arrêt du programme.

Le recours à IO::Socket et IO::Socket::INET6 est déprécié et sera supprimé dans une future version. Voir DÉPRÉCATIONS ci-dessous.

-s, --server [<serveur-cible>[:<port>]]
Indique explicitement à Swaks d'utiliser des sockets réseau et spécifie le nom d'hôte ou l'adresse IP à laquelle se connecter, ou demande si aucun argument n'est donné. Si cette option n'est pas fournie et qu'aucune autre option de transport n'est fournie, le serveur de messagerie cible est déterminé à partir des enregistrements DNS appropriés pour le domaine de l'adresse e-mail du destinataire en utilisant le module Net::DNS. Si Net::DNS n'est pas disponible, Swaks tentera de se connecter à localhost pour la délivrance. Le port cible peut être défini en option ici. Les formats pris en charge incluent SERVER:PORT (prenant en charge les noms et les adresses IPv4) ; [SERVER]:PORT et SERVER/PORT (prenant en charge les noms, les adresses IPv4 et IPv6). Un port défini via cette option ne sera utilisé que si l'option "--port" n'est pas utilisée. Voir également "--copy-routing". (Arg-Requis, Demande-Si-Absence)
-p, --port [<port>]
Spécifie le port TCP à utiliser sur la cible, ou demande si aucun argument n'est fourni. L'argument peut être un nom de service (tel que récupéré par getservbyname(3)) ou un numéro de port. Le port par défaut est smtp/25, sauf influence des options "--protocol" ou "--tls-on-connect". (Arg-Requis, Demande-Si-Absence)
-li, --local-interface [<interface-locale>[:<port>]]
Utilise l'argument comme interface locale pour la connexion SMTP sortante, ou demande à l'utilisateur si aucun argument n'est donné. L'argument peut être une adresse IP ou un nom d'hôte. L'action par défaut est de laisser le système d'exploitation choisir l'interface locale. Voir "--server" pour des commentaires supplémentaires sur le format :<port>. Un port défini via cette option ne sera utilisé que si l'option "--port" n'est pas utilisée. (Arg-Requis, Demande-Si-Absence)
-lp, --local-port, --lport [<port>]
Spécifie le port sortant à partir duquel initier la transaction. L'argument peut être un nom de service (tel que récupéré par getservbyname(3)) ou un numéro de port. Si cette option n'est pas spécifiée, le système choisira un port éphémère. Notez que les utilisateurs ordinaires ne peuvent pas spécifier certains ports. (Arg-Requis, Demande-Si-Absence)
--copy-routing <domaine>
L'argument est interprété comme la partie domaine d'une adresse e-mail et il est utilisé pour trouver le serveur cible en utilisant la même logique qui serait utilisée pour rechercher le serveur cible d'une adresse e-mail de destinataire. Voir l'option "--to" pour plus de détails sur la façon dont la cible est déterminée à partir du domaine de l'e-mail. (Arg-Requis)
-4, -6
Forcer IPv4 ou IPv6. (Arg-Aucun)
SOCKETS UNIX
Cette méthode de transport tente de délivrer des messages via un fichier de socket de domaine UNIX. Ceci est utile pour tester les MTA/MDA qui écoutent sur des fichiers de socket (par exemple, tester la livraison LMTP à Cyrus). Ce transport nécessite le module IO::Socket::UNIX qui fait partie de la distribution standard de Perl. Si ce module ne peut pas être chargé, tenter d'utiliser ce transport entraînera une erreur et l'arrêt du programme.
--socket [<fichier-socket>]
Cette option prend comme argument un fichier de socket de domaine UNIX. Si Swaks ne parvient pas à ouvrir ce socket, il affichera une erreur et s'arrêtera. (Arg-Requis, Demande-Si-Absence)
PIPES
Ce transport tente de lancer un processus et de communiquer avec lui via des tuyaux. Le programme lancé doit être prêt à se comporter comme un serveur de messagerie sur "STDIN"/"STDOUT". Tout MTA conçu pour fonctionner à partir d'inet/xinet devrait supporter cela. De plus, certains MTA fournissent des modes de test avec lesquels on peut communiquer via "STDIN"/"STDOUT". Ce transport peut être utilisé pour automatiser ces tests. Par exemple, si vous avez implémenté la vérification DNSBL avec Exim et que vous vouliez vous assurer qu'elle fonctionnait, vous pourriez exécuter "swaks --pipe "exim -bh 127.0.0.2"". Idéalement, le processus auquel vous parlez devrait se comporter exactement comme un serveur SMTP sur "STDIN" et "STDOUT". Tout débogage devrait être envoyé à "STDERR", qui sera dirigé vers votre terminal. En pratique, Swaks peut généralement gérer une certaine quantité de débogage sur le "STDOUT" de l'enfant, mais il n'y a aucune garantie sur la quantité qu'il peut gérer.

Ce transport nécessite le module IPC::Open2 qui fait partie de la distribution standard de Perl. Si ce module ne peut pas être chargé, tenter d'utiliser ce transport entraînera une erreur et l'arrêt du programme.

--pipe [<commande-et-arguments>]
Fournit un nom de processus et des arguments au processus. Swaks tentera de lancer le processus et de communiquer avec lui via des tuyaux. Si l'argument n'est pas exécutable, Swaks affichera une erreur et s'arrêtera. (Arg-Requis, Demande-Si-Absence)

OPTIONS DE PROTOCOLE

Ces options sont liées à la couche protocolaire.

-t, --to [<adresse-e-mail>[,<adresse-e-mail>[,...]]]
--cc [<adresse-e-mail>[,<adresse-e-mail>[,...]]]
--bcc [<adresse-e-mail>[,<adresse-e-mail>[,...]]]
Toutes ces options indiquent à Swaks d'utiliser l'argument (les arguments) comme destinataire de l'enveloppe pour l'e-mail. Il existe des différences subtiles entre ces trois options, détaillées ci-dessous. Si une option est spécifiée mais sans arguments, Swaks demandera à l'utilisateur un argument.

"--to" est spécial car c'est la seule option requise par Swaks. Il n'y a pas de valeur par défaut pour cette option. Si aucun destinataire n'est fourni par quelque moyen que ce soit, l'utilisateur sera invité à en fournir un interactivement. La seule exception est si une valeur "--quit-after" est fournie, ce qui provoquera la terminaison de la transaction SMTP avant que le destinataire ne soit nécessaire. Si plusieurs destinataires sont fournis et que le domaine du destinataire est nécessaire pour déterminer le routage, le domaine du dernier destinataire dans la liste d'arguments "--to" est utilisé.

La principale distinction entre ces options réside dans la façon dont leurs arguments sont traités lors de la génération de la partie DATA de l'e-mail. Elles ont chacune leurs propres jetons de remplacement ("%TO_ADDRESS%", "%CC_ADDRESS%" et "%BCC_ADDRESS%" respectivement) qui peuvent être utilisés par quiconque crée une donnée personnalisée. Dans le message par défaut de Swaks, "%TO_ADDRESS%" sera utilisé pour l'en-tête To : et, s'il est renseigné, "%CC_HEADER%" sera utilisé pour un en-tête Cc :. "%BCC_ADDRESS%" n'est pas utilisé dans la donnée par défaut. (Arg-Requis, Demande-Si-Absence)

-f, --from [<adresse-e-mail>]
Utilise l'argument comme expéditeur de l'enveloppe pour l'e-mail, ou demande à l'utilisateur si aucun argument n'est spécifié. La chaîne "<>" peut être fournie pour signifier l'expéditeur nul. TLS / CHIFFREMENT

Ce sont des options relatives au chiffrement de la transaction. Celles-ci ont été testées et confirmées pour fonctionner avec les trois méthodes de transport. Le module Net::SSLeay est utilisé pour effectuer le chiffrement lorsqu'il est demandé. Si ce module n'est pas chargeable, Swaks ignorera la demande TLS ou générera une erreur, selon que la demande était facultative. STARTTLS est défini comme une extension dans le protocole ESMTP et ne sera pas disponible si "--protocol" est défini sur une variation de SMTP brut. Parce qu'il n'est pas défini dans le protocole lui-même, "--tls-on-connect" est disponible pour tout type de protocole si la cible le prend en charge.

Un certificat local n'est pas requis pour qu'une connexion TLS soit négociée. Cependant, certains serveurs utilisent la vérification du certificat client pour s'assurer que le client est autorisé à se connecter. Swaks peut être configuré pour utiliser un certificat local spécifique à l'aide des options "--tls-cert" et "--tls-key", et éventuellement utiliser une chaîne de certificats à l'aide de l'option "--tls-chain".

-tls
Exiger que la connexion utilise STARTTLS. Quitter si TLS n'est pas disponible pour une raison quelconque (non annoncé, négociations échouées, etc.). (Arg-Aucun)
-tlso, --tls-optional
Tenter d'utiliser STARTTLS si disponible, continuer avec la transaction normale si TLS n'a pas pu être négocié pour une raison quelconque. Notez qu'il s'agit d'une option semi-inutile telle qu'implémentée actuellement car après un échec de négociation, l'état de la connexion est inconnu. Dans certains cas, comme une incompatibilité de version, la connexion devrait rester en texte brut. Dans d'autres, comme un échec de vérification, le serveur peut penser qu'il doit continuer à parler TLS tandis que le client pense qu'il s'agit de texte brut. Une tentative d'ajout d'une détection d'état plus granulaire pourrait être faite à l'avenir, mais pour l'instant, soyez simplement conscient que les choses étranges
gs peut se produire avec cette option si la négociation TLS est tentée et échoue. (Arg-None)
-tlsos, --tls-optional-strict
Tente d'utiliser STARTTLS s'il est disponible. Poursuit la transaction si TLS est négocié avec succès ou si STARTTLS n'est pas annoncé. Si STARTTLS est annoncé mais que les négociations TLS échouent, traite cela comme une erreur et abandonne la transaction. En raison de la mise en garde notée ci-dessus, c'est une option beaucoup plus saine que "--tls-optional". (Arg-None)
-tlsc, --tls-on-connect
Initie une connexion TLS immédiatement à la connexion. Suivant la convention commune, si cette option est spécifiée, le port par défaut passe de 25 à 465, bien que cela puisse toujours être remplacé par l'option --port. (Arg-None)
-tlsp, --tls-protocol <tls-version-specification>
Spécifie quels protocoles utiliser (ou ne pas utiliser) lors de la négociation TLS. Au moment de la rédaction, les protocoles disponibles sont sslv2, sslv3, tlsv1, tlsv1_1, tlsv1_2 et tlsv1_3. La disponibilité de ces protocoles dépend de votre bibliothèque OpenSSL sous-jacente, donc tous ne peuvent pas être disponibles. La liste des protocoles disponibles est affichée dans la sortie de "--dump" (en supposant que TLS est disponible).

La chaîne de spécification est une liste de protocoles séparés par des virgules qui peuvent être utilisés ou non. Par exemple, 'tlsv1,tlsv1_1' ne réussira que si l'un de ces deux protocoles est disponible sur le client et le serveur. Inversement, 'no_sslv2,no_sslv3' tentera de négocier tout protocole sauf sslv2 et sslv3. Les deux formes de spécification ne peuvent pas être mélangées. (Arg-Required)

--tls-cipher <cipher-string>
L'argument de cette option est passé à la bibliothèque OpenSSL sous-jacente pour définir la liste des chiffrements acceptables à utiliser pour la connexion. Le format de cette chaîne est opaque pour Swaks et est défini dans https://www.openssl.org/docs/manmaster/man1/openssl-ciphers.html#CIPHER-LIST-FORMAT. Un bref exemple serait "--tls-cipher '3DES:+RSA'". (Arg-Required)
--tls-verify
Indique à Swaks de tenter de vérifier le certificat du serveur. Cette option est identique à la spécification des options "--tls-verify-ca" et "--tls-verify-host". Voir ces options pour des descriptions détaillées sur la façon d'affiner chaque type de vérification.

Par défaut, la vérification TLS n'est pas requise. Si la vérification TLS est requise par "--tls-verify", "--tls-verify-ca" ou "--tls-verify-host" et que le type de vérification demandé échoue, la négociation TLS ne réussira pas. (Arg-None)

--tls-verify-ca
Exige que le certificat du serveur soit signé par une autorité de certification connue et ne soit pas expiré. Par défaut, la liste des AC connues sera celle disponible via le client sur lequel Swaks s'exécute. Pour fournir une AC personnalisée, voir "--tls-ca-path". (Arg-None)
--tls-verify-host
Exige que la cible de la connexion actuelle soit listée dans le nom alternatif du sujet (SAN) ou le nom commun (CN) du certificat du serveur.

La cible que Swaks utilise pour la vérification variera. Il peut s'agir d'un nom d'hôte, fourni directement via l'option "--server" ou recherché via les enregistrements MX. Dans ce cas, la vérification fonctionne comme prévu. Si la cible est une adresse IP, l'adresse IP sera recherchée dans le certificat, ce qui est possible mais inhabituel. Si le transport est "--pipe" ou "--socket", il n'y aura pas de cible significative à vérifier dans le certificat et la vérification échouera. Dans cette situation, il est préférable d'utiliser uniquement "--tls-verify-ca" ou de remplacer la cible utilisée pour la vérification avec l'option "--tls-verify-target". (Arg-None)

--tls-verify-target <verification-string>
Lorsqu'il est défini, l'argument de cette option sera utilisé comme nom d'hôte à vérifier pour "--tls-verify-host". Ceci est nécessaire lors de l'utilisation de "--tls-verify-host" avec les transports "--pipe" ou "--socket", qui n'ont pas de cible vérifiable par défaut. Il peut également être utilisé pour remplacer la cible par défaut lors de l'utilisation du transport "--server". Par exemple, il peut être utilisé pour vérifier que le certificat d'un serveur auquel on s'est connecté explicitement via IP contient un certificat spécifique. (Arg-Required)
--tls-ca-path <ca-location>
Spécifie un emplacement alternatif pour les informations d'AC pour vérifier les certificats serveur. L'argument peut pointer vers un fichier ou un répertoire. Le comportement par défaut est d'utiliser les informations par défaut de la bibliothèque OpenSSL sous-jacente. (Arg-Required)
--tls-cert <cert-file>
Fournit un chemin vers un fichier contenant le certificat local que Swaks doit utiliser si TLS est négocié. Si une chaîne de certificats doit être fournie, elle peut être fournie via ce fichier ou via un fichier séparé avec "--tls-chain". Le chemin du fichier est requis. Tel qu'implémenté actuellement, le certificat dans le fichier doit être au format PEM. Contactez l'auteur s'il existe un besoin impérieux pour l'ASN1. Si cette option est définie, "--tls-key" est également requis. (Arg-Required)
--tls-key <key-file>
Fournit un chemin vers un fichier contenant la clé privée locale que Swaks doit utiliser si TLS est négocié. Le chemin du fichier est requis. Tel qu'implémenté actuellement, le certificat dans le fichier doit être au format PEM. Contactez l'auteur s'il existe un besoin impérieux pour l'ASN1. Si cette option est définie, "--tls-cert" est également requis. (Arg-Required)
--tls-chain <chain-file>
Fournit un chemin vers un fichier contenant la chaîne de certificats locale que Swaks doit utiliser si TLS est négocié. Le chemin du fichier est requis. Tel qu'implémenté actuellement, le certificat dans le fichier doit être au format PEM. Contactez l'auteur s'il existe un besoin impérieux pour l'ASN1. Si cette option est définie, "--tls-cert" et "--tls-key" sont également requis. (Arg-Required)
--tls-get-peer-cert [<output-file>]
Obtient une copie du certificat du pair TLS. Si aucun argument n'est donné, il sera affiché sur "STDOUT". Si un argument est donné, il est supposé être un chemin de système de fichiers spécifiant où le certificat doit être écrit. Le certificat enregistré peut alors être examiné à l'aide d'outils standard tels que la commande openssl. Si un fichier est spécifié, son contenu sera écrasé. Cette option ne renverra jamais qu'un seul certificat. Pour obtenir chaque certificat envoyé par le serveur, voir "--tls-get-peer-chain". (Arg-Optional)
--tls-get-peer-chain [<output-file>]
Obtient une copie de la chaîne de certificats TLS envoyée par le serveur. Si aucun argument n'est donné, elle sera affichée sur "STDOUT". Si un argument est donné, il est supposé être un chemin de système de fichiers spécifiant où le certificat doit être écrit. La chaîne enregistrée peut alors être examinée à l'aide d'outils standard tels que la commande openssl. Si un fichier est spécifié, son contenu sera écrasé. Voir également "--tls-get-peer-cert". AUTHENTICATION

Swaks tentera de s'authentifier auprès du serveur de messagerie cible s'il y est invité. Cette section détaille les types d'authentification disponibles, les exigences, les options et leurs interactions, ainsi que d'autres points fins dans l'utilisation de l'authentification. Comme l'authentification est définie comme une extension dans le protocole ESMTP, elle sera indisponible si "--protocol" est défini sur une variation de SMTP.

Toutes les méthodes d'authentification nécessitent un encodage base64. Si le module Perl MIME::Base64 peut être chargé, Swaks tente de l'utiliser pour effectuer ces encodages. Si MIME::Base64 n'est pas disponible, Swaks utilisera ses propres routines base64 intégrées. Celles-ci sont plus lentes que les routines MIME::Base64 et moins revues, bien qu'elles aient été testées en profondeur. L'utilisation du module MIME::Base64 est encouragée.

Si l'authentification est requise (voir les options ci-dessous pour quand elle est requise et quand elle ne l'est pas) et que les exigences ne sont pas satisfaites pour le type d'authentification disponible, Swaks affiche une erreur et se termine. Deux façons dont cela peut se produire incluent le fait de forcer Swaks à utiliser un type d'authentification spécifique que Swaks ne peut pas utiliser en raison d'exigences manquantes, ou de permettre à Swaks d'utiliser n'importe quel type d'authentification, mais le serveur n'annonce que des types que Swaks ne peut pas prendre en charge. Dans le premier cas, Swaks se termine lors du traitement des options car il sait à l'avance qu'il ne pourra pas s'authentifier. Dans le second cas, Swaks se terminera lors de l'étape d'authentification de la transaction SMTP, car Swaks ne sera pas conscient qu'il ne pourra pas s'authentifier avant ce moment.

Voici les types d'authentification pris en charge, y compris toutes les notes et exigences individuelles.

Les options suivantes affectent l'utilisation de l'authentification par Swaks. Ces options sont toutes interdépendantes. Par exemple, spécifier "--auth-user" implique "--auth" et "--auth-password". Spécifier "--auth-optional" implique "--auth-user" et "--auth-password", etc.

-a, --auth [<auth-type>[,<auth-type>[,...]]]
Exige que Swaks s'authentifie. Si aucun argument n'est donné, tous les types d'authentification pris en charge annoncés par le serveur sont essayés jusqu'à ce que l'un réussisse ou que tous échouent. Si un ou plusieurs types d'authentification sont spécifiés comme argument, chacun que le serveur prend également en charge est essayé dans l'ordre jusqu'à ce que l'un réussisse ou que tous échouent. Cette option exige que Swaks s'authentifie, donc si aucun type d'authentification commun n'est trouvé ou si aucune identifiant ne réussit, Swaks affiche une erreur et se termine. (Arg-Optional)

AUTHENTICATION OPTIONS

LOGIN, PLAIN
Ces types d'authentification de base sont entièrement pris en charge et testés et n'ont aucune exigence supplémentaire
CRAM-MD5
L'authentificateur CRAM-MD5 nécessite le module Digest::MD5. Il est entièrement testé et est censé fonctionner avec tout serveur qui l'implémente.
DIGEST-MD5
L'authentificateur DIGEST-MD5 (RFC2831) nécessite le module Authen::SASL. Les versions 20100211.0 et antérieures utilisaient Authen::DigestMD5, qui présentait des erreurs au niveau du protocole qui empêchaient son fonctionnement avec certains serveurs. La gestion DIGEST-MD5 d'Authen::SASL est beaucoup plus robuste.

L'implémentation DIGEST-MD5 dans Swaks est assez immature. Elle ne prend actuellement en charge que le type qop "auth", par exemple. Si vous avez de l'expérience avec DIGEST-MD5 et souhaitez aider Swaks à mieux prendre en charge DIGEST-MD5, veuillez me contacter.

La valeur "realm" du protocole DIGEST-MD5 peut être définie à l'aide du mot-clé "realm" de l'option "--auth-extra". Si aucun realm n'est fourni, une valeur par défaut raisonnable sera utilisée.

Les valeurs "digest-uri" du protocole DIGEST-MD5 peuvent être définies à l'aide de l'option "--auth-extra". Par exemple, vous pourriez créer la valeur digest-uri de "lmtp/mail.example.com/example.com" avec l'option "--auth-extra dmd5-serv-type=lmtp,dmd5-host=mail.example.com,dmd5-serv-name=example.com". La chaîne "digest-uri-value" et ses composants sont définis dans la RFC2831. Si aucune de ces valeurs n'est fournie, des valeurs par défaut raisonnables seront utilisées.

CRAM-SHA1
L'authentificateur CRAM-SHA1 nécessite le module Digest::SHA. Ce type n'a été testé qu'avec une implémentation non standard sur un serveur Exim et peut donc présenter des lacunes d'implémentation.
NTLM/SPA/MSN
Ces authentificateurs nécessitent le module Authen::NTLM. Ce type a été testé avec Exim, Communigate et Exchange 2007.

En plus du nom d'utilisateur et du mot de passe standard, ce type d'authentification peut également reconnaître un "domaine". Le domaine peut être défini à l'aide du mot-clé "domain" de l'option "--auth-extra". Notez que cela n'a jamais été testé avec un serveur de messagerie qui ignore DOMAIN, cela pourrait donc être mal implémenté.

-ao, --auth-optional [<auth-type>[,<auth-type>[,...]]]
Cette option se comporte de manière identique à "--auth", sauf qu'elle demande une authentification au lieu de l'exiger. Si aucun type d'authentification commun n'est trouvé ou si aucune information d'identification ne réussit, Swaks continue comme si l'authentification n'avait pas été demandée. (Arg-Optional)
-aos, --auth-optional-strict [<auth-type>[,<auth-type>[,...]]]
Cette option est un compromis entre "--auth" et "--auth-optional". Si l'authentification n'est jamais tentée (le serveur ne propose pas d'authentification ou aucun type d'authentification commun n'est trouvé), elle se comporte comme "--auth-optional" et la transaction smtp continue. Si l'authentification est tentée mais échoue, elle se comporte comme "--auth" et se termine avec une erreur. (Arg-Optional)
-au, --auth-user [<username>]
Fournit le nom d'utilisateur à utiliser pour l'authentification. Si aucun nom d'utilisateur n'est fourni, indiquez que Swaks doit tenter de trouver le nom d'utilisateur via .netrc (nécessite le module Net::Netrc). Si aucun nom d'utilisateur n'est fourni et qu'il ne peut pas être trouvé via .netrc, l'utilisateur sera invité à en fournir un. La chaîne "<>" peut être fournie pour signifier un nom d'utilisateur vide. (Arg-Requis, Invité)
-ap, --auth-password [<password>]
Fournit le mot de passe à utiliser pour l'authentification. Si aucun mot de passe n'est fourni, indiquez que Swaks doit tenter de trouver le mot de passe via .netrc (nécessite le module Net::Netrc). Si aucun mot de passe n'est fourni et qu'il ne peut pas être trouvé via .netrc, l'utilisateur sera invité à en fournir un. La chaîne "<>" peut être fournie pour signifier un mot de passe vide. (Arg-Requis, Invité, Sensible)

Plutôt que d'ajouter une nouvelle option pour chaque détail de chaque authentificateur, l'option "--auth-extra" permet de fournir ces informations. Le format pour <key-value-pair> est CLÉ=VALEUR. Le mot-clé dmd5-host est utilisé par l'authentificateur DIGEST-MD5 et sert, en partie, à construire la chaîne digest-uri-value (voir RFC2831).
dmd5-serv-name
Le mot-clé dmd5-serv-name est utilisé par l'authentificateur DIGEST-MD5 et sert, en partie, à construire la chaîne digest-uri-value (voir RFC2831).
-am, --auth-map <key-value-pair>[,<key-value-pair>[,...]]
Fournit un moyen de mapper des noms alternatifs sur des types d'authentification de base. Utile pour tout site utilisant des noms alternatifs pour des types courants. Le format pour <key-value-pair> est AUTH-ALIAS=AUTH-TYPE. Cette fonctionnalité est en fait utilisée en interne pour mapper les types SPA et MSN sur le type de base NTLM. L'argument de ligne de commande pour simuler cela serait "--auth-map SPA=NTLM,MSN=NTLM". Tous les types d'authentification listés ci-dessus sont des cibles valides pour le mappage, à l'exception de SPA et MSN. (Arg-Requis)
-apt, --auth-plaintext
Au lieu d'afficher les chaînes AUTH encodées en base64 telles qu'elles sont transmises, les traduire en texte brut avant de les afficher à l'écran. (Arg-Aucun)
-ahp, --auth-hide-password [<replacement-string>]
Si cette option est spécifiée, chaque fois qu'un mot de passe lisible serait affiché sur le terminal (spécifiquement AUTH PLAIN et AUTH LOGIN), le mot de passe sera remplacé par la chaîne 'PROVIDED_BUT_REMOVED' (ou le contenu de <replacement-string> s'il est fourni). La chaîne factice peut être encodée ou non en base64, en fonction de l'option "--auth-plaintext".

Notez que "--auth-hide-password" est similaire, mais pas identique, à l'option "--protect-prompt". La première protège les mots de passe de l'affichage dans la transaction SMTP, quelle que soit la manière dont ils sont saisis. La seconde protège les chaînes sensibles lorsque l'utilisateur les tape au terminal, quelle que soit la manière dont la chaîne serait utilisée. (Arg-Optional)

OPTIONS XCLIENT

XCLIENT est une extension SMTP introduite par le projet Postfix. XCLIENT permet à un client (correctement autorisé) de dire à un serveur d'utiliser des informations alternatives, telles que l'adresse IP ou le nom d'hôte, pour le client. Cela permet des chemins beaucoup plus simples pour tester les configurations de serveurs de messagerie. Les détails complets du protocole sont disponibles sur http://www.postfix.org/XCLIENT_README.html.

Le verbe XCLIENT peut être passé au serveur plusieurs fois par session SMTP avec différents attributs. Par exemple, HELO et PROTO peuvent être passés dans un appel et NAME et ADDR dans un second. Parce que cela peut être utile pour les tests, Swaks offre un certain contrôle sur la façon dont les attributs sont groupés et dans quel ordre ils sont passés au serveur. Les différentes options tentent d'offrir la simplicité pour ceux qui utilisent Swaks en tant que client, et la complexité pour ceux qui utilisent Swaks pour tester des installations.

--xclient-addr [<string>]
--xclient-name [<string>]
--xclient-port [<string>]
--xclient-proto [<string>]
--xclient-destaddr [<string>]
--xclient-destport [<string>]
--xclient-helo [<string>]
--xclient-login [<string>]
--xclient-reverse-name [<string>]
Ces options spécifient les attributs XCLIENT qui doivent être envoyés au serveur cible. Si <string> n'est pas fourni, Swaks invitera l'utilisateur et lira la valeur sur "STDIN". Voir http://www.postfix.org/XCLIENT_README.html pour la documentation officielle sur la signification des attributs et leurs valeurs possibles, y compris les valeurs spéciales "[UNAVAILABLE]" et "[TEMPUNAVAIL]".

À titre d'exemple simple, la définition de "--xclient-name foo.example.com --xclient-addr 192.168.1.1" amènera Swaks à envoyer la commande SMTP "XCLIENT NAME=foo.example.com ADDR=192.168.1.1".

Notez que l'attribut "REVERSE_NAME" ne semble pas apparaître dans la documentation officielle. Il y a une discussion sur une liste de diffusion th

at documents it, viewable at http://comments.gmane.org/gmane.mail.postfix.user/192623.

Ces options peuvent toutes être mélangées entre elles, et peuvent être mélangées avec l'option "--xclient" (voir ci-dessous). Par défaut, tous les attributs seront combinés en un seul appel XCLIENT, mais voir "--xclient-delim". (Arg-Requis, Invite-Depuis)

--xclient-delim
Lorsque cette option est spécifiée, elle indique une séparation dans les attributs XCLIENT à envoyer. Par exemple, définir "--xclient-helo 'chaîne de helo' --xclient-delim --xclient-name foo.example.com --xclient-addr 192.168.1.1" amènera Swaks à envoyer deux appels XCLIENT, "XCLIENT HELO=helo+20chaîne" et "XCLIENT NAME=foo.example.com ADDR=192.168.1.1". Cette option est ignorée lorsqu'elle n'a pas de sens (au début ou à la fin des options XCLIENT, seule, consécutivement, etc.). (Arg-Aucun)
--xclient [<chaîne>]
C'est l'option XCLIENT de "forme libre". Quelle que soit la valeur fournie pour <chaîne>, elle sera envoyée telle quelle comme argument à la commande SMTP XCLIENT. Par exemple, si "--xclient 'NAME= ADDR=192.168.1.1 FOO=bar'" est utilisé, Swaks enverra la commande SMTP "XCLIENT NAME= ADDR=192.168.1.1 FOO=bar". Si aucun argument n'est passé en ligne de commande, Swaks invitera l'utilisateur à saisir la valeur sur STDIN.

L'avantage principal par rapport aux options plus spécifiques ci-dessus est qu'il n'y a aucune validation de syntaxe XCLIENT ici. Cela vous permet d'envoyer des XCLIENT invalides au serveur cible pour les tests. De plus, au moins un MTA (Message Systems' Momentum, anciennement ecelerity) implémente XCLIENT sans annoncer les attributs pris en charge. L'option "--xclient" vous permet d'ignorer la vérification des "attributs pris en charge" lors de la communication avec ce type de MTA (bien que voir aussi "--xclient-no-verify").

L'option "--xclient" peut être mélangée librement avec les options "--xclient-*" ci-dessus. L'argument de "--xclient" sera envoyé dans son propre groupe de commandes. Par exemple, si "--xclient-addr 192.168.0.1 --xclient-port 26 --xclient 'FOO=bar NAME=wind'" est donné à Swaks, "XCLIENT ADDR=192.168.0.1 PORT=26" et "XCLIENT FOO=bar NAME=wind" seront tous deux envoyés au serveur cible. (Arg-Requis, Invite-Depuis)

--xclient-no-verify
Ne pas imposer l'exigence qu'un attribut XCLIENT doit être annoncé par le serveur pour que Swaks l'envoie dans une commande XCLIENT. Ceci est pour prendre en charge les serveurs qui n'annoncent pas les attributs mais les prennent néanmoins en charge. (Arg-Aucun)
--xclient-before-starttls
Si Swaks est configuré pour tenter à la fois XCLIENT et STARTTLS, il fera d'abord STARTTLS. Si cette option est spécifiée, il tentera d'abord XCLIENT. (Arg-Aucun)
--xclient-optional
--xclient-optional-strict
En fonctionnement normal, la définition de l'une des options "--xclient*" nécessitera une transaction XCLIENT réussie pour pouvoir continuer (c'est-à-dire que XCLIENT doit être annoncé, tous les attributs demandés par l'utilisateur doivent avoir été annoncés, et le serveur doit avoir accepté la requête XCLIENT de Swaks). Ces options modifient ce comportement. "--xclient-optional" indique à Swaks de continuer inconditionnellement après l'étape XCLIENT de la transaction SMTP, qu'elle ait réussi ou non. "--xclient-optional-strict" est similaire mais plus granulaire. La version stricte continuera si XCLIENT n'a pas été annoncé, mais échouera si XCLIENT a été tenté mais n'a pas réussi. (Arg-Aucun)

OPTIONS PROXY

Swaks implémente le protocole Proxy tel que défini dans http://www.haproxy.org/download/1.5/doc/proxy-protocol.txt. Proxy permet à un équilibreur de charge d'application, tel que HAProxy, d'être placé devant un MTA tout en permettant au MTA d'accéder aux informations de l'hôte d'origine. Le support Proxy dans Swaks permet des tests directs d'un MTA configuré pour attendre des requêtes provenant d'un proxy, en contournant le proxy lui-même pendant les tests.

Swaks ne fait aucun effort pour garantir que les options Proxy utilisées sont cohérentes en interne. Par exemple, "--proxy-family" (en version 1) est attendu pour être l'une des valeurs "TCP4" ou "TCP6". Bien que cela n'ait probablement aucun sens pour le serveur cible, Swaks ne tente pas de garantir que "--proxy-source" et "--proxy-dest" appartiennent à la même famille de protocoles que "--proxy-family" ou entre eux.

L'option "--proxy" est mutuellement exclusive avec toutes les autres options "--proxy-*" sauf "--proxy-version".

Lorsque "--proxy" n'est pas utilisé, toutes les options "--proxy-family", "--proxy-source", "--proxy-source-port", "--proxy-dest", et "--proxy-dest-port" sont requises. De plus, lorsque "--proxy-version" est 2, "--proxy-protocol" et "--proxy-command" sont optionnels.

--proxy-version [ 1 | 2 ]
Indique s'il faut utiliser la version 1 (lisible par l'homme) ou la version 2 (binaire) du protocole Proxy. La version 1 est la valeur par défaut. La version 2 n'est implémentée que par le biais du "bloc d'adresses", et est à peu près équivalente aux informations fournies dans la version 1. (Arg-Requis, Invite-Depuis)
--proxy [<chaîne>]
Cette option fournit la chaîne proxy brute qui sera envoyée au serveur. Le préfixe du protocole ("PROXY " pour la version 1, l'en-tête de protocole de 12 octets pour la version 2) peut être présent ou non dans l'argument. Cette option permet d'envoyer des chaînes Proxy incomplètes ou malformées à un serveur cible pour des tests. Cette option est mutuellement exclusive avec toutes les autres options "--proxy-*" qui fournissent des informations proxy granulaires.

Étant donné que la version 2 du protocole Proxy est un protocole binaire, il existe plusieurs façons de fournir l'argument à cette option. Si l'argument commence par "base64:", ce préfixe est retiré et le reste de la chaîne est décodé en base64 avant utilisation. Si l'argument commence par "@", il sera traité comme un nom de fichier et la valeur proxy sera lue à partir du fichier. Toute autre valeur est supposée être la valeur littérale de la chaîne proxy. (Arg-Requis, Invite-Depuis, Depuis-Fichier)

--proxy-family [<chaîne>]
Pour la version 1, spécifie à la fois la famille d'adresses et le protocole de transport. Le protocole définit TCP4 et TCP6.

Pour la version 2, spécifie uniquement la famille d'adresses. Le protocole définit AF_UNSPEC, AF_INET, AF_INET6 et AF_UNIX. (Arg-Requis, Invite-Depuis)

--proxy-protocol [<chaîne>]
Pour la version 2, spécifie le protocole de transport. Le protocole définit UNSPEC, STREAM et DGRAM. La valeur par défaut est STREAM. Cette option n'est pas utilisée dans la version 1. (Arg-Requis, Invite-Depuis)
--proxy-command [<chaîne>]
Pour la version 2, spécifie le protocole de transport. Le protocole définit LOCAL et PROXY. La valeur par défaut est PROXY. Cette option n'est pas utilisée dans la version 1. (Arg-Requis, Invite-Depuis)
--proxy-source [<chaîne>]
Spécifie l'adresse source de la connexion proxifiée. (Arg-Requis, Invite-Depuis)
--proxy-source-port [<chaîne>]
Spécifie le port source de la connexion proxifiée. (Arg-Requis, Invite-Depuis)
--proxy-dest [<chaîne>]
Spécifie l'adresse de destination de la connexion proxifiée. (Arg-Requis, Invite-Depuis)
--proxy-dest-port [<chaîne>]
Spécifie le port de destination de la connexion proxifiée. (Arg-Requis, Invite-Depuis)

OPTIONS DE DONNÉES

Ces options concernent le contenu de la partie DATA de la transaction SMTP. Par défaut, un message très simple est envoyé. Si les options "--attach" ou "--attach-body" sont utilisées, Swaks tente de passer à un message MIME.

-d, --data [<portion de données>]
Utilise l'argument comme contenu entier de DATA.

Si aucun argument n'est fourni, l'utilisateur sera invité à fournir la valeur.

Si l'argument "-" est fourni, les données seront lues depuis "STDIN" sans invite.

Si l'argument commence par "@", il sera traité comme un nom de fichier. Si vous souhaitez passer un argument qui commence par "@" et qui n'est pas un nom de fichier, préfixez l'argument avec un "@" supplémentaire. Par exemple, "@file.txt" forcera le traitement de file.txt. @@data utilisera la chaîne '@data'.

Si l'argument ne contient aucun caractère de nouvelle ligne littéral (0x0a) ou représentatif (0x5c, 0x6e ou %NEWLINE%), il sera traité comme un fichier

name. Si le fichier est ouvrable, le contenu du fichier sera utilisé comme partie de données. Si le fichier ne peut pas être ouvert, Swaks générera une erreur et s'arrêtera. L'ensemble du comportement décrit dans ce paragraphe est déprécié et sera supprimé dans une future version. Utilisez plutôt un préfixe "@" pour spécifier explicitement que l'argument est un nom de fichier.

Tout autre argument sera utilisé comme contenu des DONNÉES.

La valeur peut être sur une seule ligne, avec "\n" (ASCII 0x5c, 0x6e) représentant où les sauts de ligne doivent être placés. Les points en début de ligne seront mis entre guillemets. Le point de fin n'est pas obligatoire mais est autorisé. La valeur par défaut pour cette option est "Date: %DATE%\nTo: %TO_ADDRESS%\nFrom: %FROM_ADDRESS%\nSubject: test %DATE%\nMessage-Id: <%MESSAGEID%>\nX-Mailer: swaks v%SWAKS_VERSION% jetmore.org/john/code/swaks/\n%NEW_HEADERS%\n%BODY%\n".

Un traitement très basique des jetons est effectué sur la partie DONNÉES. Le tableau suivant présente les jetons reconnus et leurs valeurs de remplacement. (Arg-Requis, Prompt-Depuis, Fichier-Depuis)

%FROM_ADDRESS%, ..FROM_ADDRESS..
Remplacé par l'expéditeur de l'enveloppe.
%TO_ADDRESS%, ..TO_ADDRESS..
Remplacé par le(s) destinataire(s) de l'enveloppe défini(s) par l'option "--to".
%CC_ADDRESS%, ..CC_ADDRESS..
Remplacé par le(s) destinataire(s) de l'enveloppe défini(s) par l'option "--cc".
%BCC_ADDRESS%, ..BCC_ADDRESS..
Remplacé par le(s) destinataire(s) de l'enveloppe défini(s) par l'option "--bcc".
%DATE%, ..DATE..
Remplacé par l'heure actuelle dans un format approprié pour l'inclusion dans l'en-tête Date:. Notez que cela tente d'utiliser le module standard POSIX pour les calculs de fuseau horaire. Si ce module n'est pas disponible ou si l'environnement actuel ne prend pas en charge le jeton de format strftime %z (comme sous Windows), la chaîne de date sera en GMT.
%MESSAGEID%, ..MESSAGEID..
Remplacé par une chaîne d'identifiant de message appropriée pour un en-tête Message-Id:. La valeur de ce jeton restera cohérente pendant la durée de vie du processus.
%SWAKS_VERSION%, ..SWAKS_VERSION..
Remplacé par la version du processus Swaks actuellement en cours d'exécution.
%NEW_HEADERS%, ..NEW_HEADERS..
Remplacé par le contenu de l'option "--add-header". Si "--add-header" n'est pas spécifié, ce jeton est simplement supprimé.
%BODY%, ..BODY..
Remplacé par la valeur spécifiée par l'option "--body". Voir "--body" pour la valeur par défaut.
%NEWLINE%, ..BODY..
Remplacé par un retour chariot, une nouvelle ligne (0x0d, 0x0a). Ceci est identique à l'utilisation de "\n" (0x5c, 0x6e), mais n'a pas les préoccupations d'échappement que la barre oblique inverse peut causer sur la nouvelle ligne.
-dab, --dump-as-body [<section>[,<section>[,...]]]
Si "--dump-as-body" est utilisé et qu'aucune autre option n'est utilisée pour modifier le corps par défaut du message, le corps est remplacé par une sortie similaire à celle fournie par "--dump". La section initiale de capacité du programme de "--dump" n'est pas affichée, et la section « data » n'est pas incluse. De plus, "--dump" inclut toujours les mots de passe. Par défaut, "--dump-as-body" n'inclut pas les mots de passe, bien que cela puisse être modifié avec "--dump-as-body-shows-password". "--dump-as-body" accepte les mêmes arguments que "--dump", à l'exception des arguments SUPPORT et DATA qui ne sont pas pris en charge. (Arg-Optionnel)
-dabsp, --dump-as-body-shows-password
Force "--dump-as-body" à inclure les mots de passe en clair. Cette option n'est pas recommandée. Cette option implique "--dump-as-body". (Arg-Aucun)
--body [<spécification-corps>]
Spécifie le corps de l'e-mail. La valeur par défaut est « This is a test mailing ». Si aucun argument n'est donné à "--body", une invite interactive est générée pour en fournir un. Si "-" est spécifié, le corps sera lu depuis l'entrée standard. Les arguments commençant par "@" seront traités comme des noms de fichiers contenant les données du corps à utiliser (voir "--data" pour plus de détails).

Si, après le traitement ci-dessus, l'argument représente un fichier ouvrable, le contenu de ce fichier est utilisé comme corps. Ceci est un comportement déprécié et sera supprimé dans une future version. Utilisez plutôt un préfixe "@" pour spécifier explicitement que l'argument est un nom de fichier.

Si le message est forcé au format MIME (voir "--attach"), "--body 'texte du corps'" est équivalent à "--attach-type text/plain --attach-body 'texte du corps'". Voir "--attach-body" pour les détails sur la création d'un corps multipart/alternative. (Arg-Requis, Prompt-Depuis, Fichier-Depuis)

--attach [<spécification-pièce-jointe>]
Lorsque une ou plusieurs options "--attach" sont fournies, le message est transformé en un message MIME multipart/mixed. Les arguments de "--attach" sont traités de la même manière que "--body" en ce qui concerne "STDIN", le contenu des fichiers, etc. "--attach" peut être fourni plusieurs fois pour créer plusieurs pièces jointes. Par défaut, chaque pièce jointe est ajoutée en tant que fichier application/octet-stream. Voir "--attach-type" pour changer ce comportement.

Si le contenu de la pièce jointe est fourni via un nom de fichier, l'encodage MIME inclura ce nom de fichier. Voir "--attach-name" pour plus de détails sur la dénomination des fichiers.

Il est légal de spécifier "-" ("STDIN") comme argument plusieurs fois (une fois pour "--body" et plusieurs fois pour "--attach"). Dans ce cas, le même contenu sera joint chaque fois qu'il est spécifié. Ceci est utile pour joindre le même contenu avec plusieurs types MIME. (Arg-Requis, Fichier-Depuis)

--attach-body [<spécification-corps>]
Ceci est une variation de "--attach" qui concerne spécifiquement la partie corps de l'e-mail. Elle se comporte de manière identique à "--attach" en ce sens qu'elle accepte les mêmes arguments et force la création d'un message MIME. Cependant, elle est différente en ce que l'argument sera toujours la première partie MIME du message, quel que soit l'ordre de traitement des options. De plus, les options "--attach-body" s'empilent pour permettre la création de corps multipart/alternative. Par exemple, "--attach-type text/plain --attach-body 'corps texte brut' --attach-type text/html --attach-body 'corps html'" créera un corps de message multipart/alternative. (Arg-Requis, Fichier-Depuis)
--attach-type <type-mime>
Par défaut, le contenu qui est attaché en MIME à un message avec l'option "--attach" est encodé en application/octet-stream (sauf pour le corps, qui est text/plain par défaut). "--attach-type" modifie le type MIME pour chaque option "--attach" qui suit. Il peut être spécifié plusieurs fois. Le type MIME actuel est réinitialisé à application/octet-stream entre le traitement des parties du corps et des autres parties. (Arg-Requis)
--attach-name [<nom>]
Cette option définit le nom de fichier qui sera inclus dans la partie MIME créée pour la prochaine option "--attach". Si aucun argument n'est défini pour cette option, aucune information de nom de fichier ne sera incluse pour la prochaine partie MIME, même si Swaks pouvait la générer à partir du nom de fichier local. (Arg-Optionnel)
-ah, --add-header <en-tete>
Cette option permet d'ajouter des en-têtes aux DONNÉES. Si "%NEW_HEADERS%" est présent dans les DONNÉES, il est remplacé par l'argument de cette option. Si "%NEW_HEADERS%" n'est pas présent, l'argument est inséré entre les deux premiers nouvelles lignes consécutives dans les DONNÉES (c'est-à-dire qu'il est inséré à la fin des en-têtes existants).

L'option peut être spécifiée plusieurs fois ou une seule fois avec plusieurs en-têtes séparés par une chaîne littérale "\n". Ainsi, "--add-header 'Foo: bar' --add-header 'Baz: foo'" et "--add-header 'Foo: bar\nBaz: foo'" ajoutent les mêmes deux en-têtes. (Arg-Requis)

--header <en-tete-et-donnees>, --h-<en-tete> <donnees>
Ces options permettent de modifier des en-têtes déjà présents dans les DONNÉES. "--header 'Subject: foo'" et "--h-Subject foo" sont équivalents. Si l'en-tête n'existe pas déjà dans les données, cet argument se comporte de manière identique à "--add-header". Cependant, si l'en-tête existe déjà, il est remplacé par celui spécifié. Nier la version de cette option avec le nom de l'en-tête dans l'option (par exemple "--no-header-Subject") supprimera toutes les options "--header" traitées précédemment, pas seulement celles utilisées pour 'Subject'. L'intégration du nom de l'en-tête dans l'option via une variable d'environnement n'est pas prise en charge sous Windows et entraînera une erreur. (Arg-Requis)
-g
Cette option est un alias direct de "--data -" (lire les DONNÉES depuis l
an class="Li">"STDIN"). Il est totalement secondaire par rapport à "--data". Toute occurrence de "--data" entraînera l'ignorance de "-g". Cette option ne peut pas être niée avec le préfixe "no-". Cette option est obsolète et sera supprimée dans une future version de Swaks. (Arg-None, Obsolète)
--no-data-fixup, -ndf
Cette option force Swaks à ne faire aucune retouche de la partie DATA de l'e-mail. Cela inclut le remplacement de jetons, la suppression de From_, l'ajout de points finaux, l'inclusion de "--body"/pièces jointes, et toute addition d'en-tête. Cette option n'est utile que lorsqu'elle est utilisée avec "--data", car la partie DATA interne par défaut utilise des jetons. (Arg-None)
--no-strip-from, -nsf
Ne pas supprimer la ligne From_ de la partie DATA, si elle est présente. (Arg-None)

OPTIONS DE SORTIE

Swaks fournit une transcription de ses transactions à son appelant ("STDOUT"/"STDERR") par défaut. Cette transcription vise à être une représentation aussi fidèle que possible de la transaction, bien qu'elle modifie cette sortie en ajoutant des préfixes d'information aux lignes et en fournissant des versions en texte brut des transactions TLS.

Les « préfixes d'information » sont appelés indices de transaction. Ces indices sont initialement composés de ceux qui marquent les lignes qui sont la sortie de Swaks lui-même, soit des messages d'information ou d'erreur, et de ceux qui indiquent une ligne de données réellement envoyée ou reçue dans une transaction. Ce tableau indique les indices et leur signification :

"==="
Indique une ligne d'information générée par Swaks.
"***"
Indique une erreur générée dans Swaks.
" ->"
Indique une ligne attendue envoyée par Swaks au serveur cible.
" ~>"
Indique une ligne attendue, cryptée en TLS, envoyée par Swaks au serveur cible.
"**>"
Indique une ligne inattendue envoyée par Swaks au serveur cible.
"*~>"
Indique une ligne inattendue, cryptée en TLS, envoyée par Swaks au serveur cible.
"  >"
Indique un bloc de texte brut envoyé par Swaks à un serveur cible (voir "--show-raw-text"). Il n'y a pas de concept de « attendu » ou « inattendu » à ce niveau.
"<- "
Indique une ligne attendue envoyée par le serveur cible à Swaks.
"<~ "
Indique une ligne attendue, cryptée en TLS, envoyée par le serveur cible à Swaks.
"<**"
Indique une ligne inattendue envoyée par le serveur cible à Swaks.
"<~*"
Indique une ligne inattendue, cryptée en TLS, envoyée par le serveur cible à Swaks.
"<  "
Indique un bloc de texte brut reçu par Swaks d'un serveur cible (voir "--show-raw-text"). Il n'y a pas de concept de « attendu » ou « inattendu » à ce niveau.

Les options suivantes contrôlent quoi et comment la sortie est affichée à l'appelant.

-n, --suppress-data
Résume la partie DATA de la transaction SMTP au lieu d'imprimer chaque ligne. Cette option est très utile, voire indispensable, lorsque vous utilisez Swaks pour envoyer certains e-mails de test. Les e-mails avec pièces jointes, par exemple, submergeront rapidement un terminal si les données ne sont pas supprimées. (Arg-None)
-stl, --show-time-lapse [i]
Affiche l'intervalle de temps entre les paires d'envoi/réception. Cette option est plus utile lorsque Time::HiRes est disponible, auquel cas l'intervalle de temps sera affiché en millièmes de seconde. Si Time::HiRes n'est pas disponible ou si « i » est donné comme argument, l'intervalle sera affiché uniquement en secondes entières. (Arg-Optionnel)

Ne pas afficher l'indice de transaction pour les transactions informatives. Ceci est particulièrement utile lorsque vous devez copier une partie des lignes d'information, par exemple la sortie du certificat de "--tls-get-peer-cert". (Arg-None)

-nih, --no-info-hints
-nsh, --no-send-hints
-nrh, --no-receive-hints
-nth, --no-hints
"--no-info-hints", "--no-send-hints" et "--no-receive-hints" suppriment les indices de transaction des lignes d'information, d'envoi et de réception, respectivement. Ceci est souvent utile lors de la copie d'une partie de la transaction à utiliser ailleurs (par exemple, "--no-send-hints --hide-receive --hide-informational" est un moyen utile d'obtenir uniquement les commandes côté client pour une transaction donnée et "--no-info-hints --tls-get-peer-cert" pour copier le certificat du pair). "--no-hints" est identique à spécifier "--no-info-hints --no-send-hints --no-receive-hints". (Arg-None)
-raw, --show-raw-text
Cette option affichera un dump hexadécimal des données brutes envoyées et reçues par Swaks. Chaque dump hexadécimal correspond au contenu d'une seule lecture ou écriture sur le réseau. Cela devrait être identique à ce qui est déjà affiché (à l'exception des caractères "\r" qui sont supprimés). Cette option est utile pour voir les détails lorsque les serveurs envoient beaucoup de données dans des paquets uniques, ou divisent des lignes individuelles en plusieurs paquets. Si vous avez vraiment besoin d'approfondir ce domaine, un analyseur de paquets est probablement préférable, mais cette option est une bonne première étape pour observer des problèmes de connexion inhabituels. (Arg-None)
--output, --output-file <chemin-fichier>
--output-file-stdout <chemin-fichier>
--output-file-stderr <chemin-fichier>
Ces options permettent à l'utilisateur d'envoyer la sortie vers des fichiers au lieu de "STDOUT"/"STDERR". La première option envoie les deux vers le même fichier. Les arguments de &STDOUT et &STDERR sont traités spécialement, faisant référence aux descripteurs de fichier « normaux », donc "--output-file-stderr '&STDOUT'" redirigerait "STDERR" vers "STDOUT". Ces options sont prises en compte pour toute la sortie, à l'exception de "--help" et "--version". (Arg-Requis)
-pp, --protect-prompt
Ne pas écho les entrées utilisateur dans les invites qui sont potentiellement sensibles (actuellement uniquement le mot de passe d'authentification). Très spécifiquement, toute option marquée comme 'Sensible' et demandant éventuellement un argument fera de son mieux pour masquer cet argument afin qu'il ne soit pas écho. Voir aussi "--auth-hide-password". (Arg-None)
-hr, --hide-receive
Ne pas afficher les lignes envoyées par le serveur distant reçues par Swaks. (Arg-None)
-hs, --hide-send
Ne pas afficher les lignes envoyées par Swaks au serveur distant. (Arg-None)
-hi, --hide-informational
Ne pas afficher les lignes informatives non erronées de Swaks lui-même. (Arg-None)
-ha, --hide-all
Ne rien afficher sur le terminal. (Arg-None)
-S, --silent [ 1 | 2 | 3 ]
Permet à Swaks d'être silencieux. Si aucun argument n'est donné ou si un argument de « 1 » est donné, n'imprime aucune sortie sauf/jusqu'à ce qu'une erreur se produise, après quoi toute la sortie est affichée. Si un argument de « 2 » est donné, n'imprime que les erreurs. Si « 3 » est donné, ne montre jamais aucune sortie. "--silent" affecte la plupart des sorties mais pas toutes. Par exemple, "--help", "--version", "--dump" et "--dump-mail" ne sont pas affectés. Pour des raisons historiques, -S n'est pas configurable via une variable d'environnement sur Windows, utilisez plutôt SWAKS_OPT_silent. (Arg-Optionnel)
--support
Imprime les capacités et quitte. Certaines fonctionnalités nécessitent des modules Perl non standard. Cette option évalue si ces modules sont présents et affiche quelles fonctionnalités sont disponibles et lesquelles ne le sont pas, et quels modules devraient être ajoutés pour obtenir la fonctionnalité manquante. (Arg-None)
--dump-mail
Force Swaks à traiter toutes les options pour générer le message qu'il enverrait, puis imprime ce message sur "STDOUT" au lieu de l'envoyer. Cette sortie est identique à la section « data » de "--dump", sauf sans le point final. (Arg-None)
--dump [<section>[,<section>[,...]]]
Cette option permet à Swaks d'imprimer les résultats du traitement des options, juste avant que le courrier ne soit envoyé. Aucun courrier ne sera envoyé lorsque "--dump" est utilisé. Notez que "--dump" est un outil de diagnostic purement interne et aucun effort n'est fait ou ne sera jamais fait pour masquer les mots de passe dans la sortie de "--dump". Si une section est fournie comme argument à cette option, seule la section demandée sera affichée. Les arguments actuellement pris en charge sont SUPPORT, APP, OUTPUT, TRANSPORT, PROTOCOLE, XCLIENT, PROXY, TLS, AUTH, DATA et ALL. Si aucun argument n'est fourni, toutes les sections sont affichées (Arg-Optionnel)
--help
Affiche cette aide et quitte. (Arg-None)
--version
Affiche les informations de version et quitte. (Arg-None)

PORTABILITÉ

SYSTÈMES D'EXPLOITATION
Ce programme était principalement destiné à être utilisé sur des systèmes d'exploitation de type UNIX, et il devrait fonctionner sur n'importe quelle version raisonnable de ceux-ci. Il a été développé et testé sur Solaris, Linux et Mac OS X et est complet sur tous ces systèmes.

Ce programme est connu pour démontrer des fonctionnalités de base sous Windows en utilisant Strawberry Perl. Dans toute la documentation, sauf indication contraire, "Windows" fait référence à l'exécution de Swaks via CMD.exe, et non WSL ou cygwin. Il n'a pas été entièrement testé, mais on sait qu'il fonctionne pour les fonctionnalités SMTP de base et les types d'authentification LOGIN, PLAIN et CRAM-MD5. La fonctionnalité TLS et les types d'authentification NTLM/SPA et DIGEST-MD5 sont inconnus. Certaines fonctionnalités sont connues pour être limitées sous Windows, notamment l'impossibilité d'intégrer le nom de l'en-tête dans les variables d'environnement (voir "VARIABLES D'ENVIRONNEMENT DE CONFIGURATION" et "--header"), l'impossibilité de générer une chaîne de date en fuseau horaire local (voir le jeton "%DATE%" sous "--data"), l'impossibilité d'utiliser l'option "-S" comme variable d'environnement (voir "--silent"), et l'impossibilité d'avoir une valeur "définie mais vide" dans une variable d'environnement (voir "VARIABLES D'ENVIRONNEMENT DE CONFIGURATION" pour une solution de contournement).

Étant donné que ce programme devrait fonctionner partout où Perl fonctionne, j'apprécierais de connaître tout nouveau système d'exploitation sur lequel vous avez utilisé Swaks de manière approfondie, ainsi que tout problème rencontré sur un nouveau système d'exploitation.

SERVEURS DE COURRIER
Ce programme a été développé presque exclusivement contre les serveurs de messagerie Exim. Il a été utilisé occasionnellement par l'auteur, bien que pas testé de manière approfondie, avec Sendmail, Smail, Exchange, Oracle Collaboration Suite, qpsmtpd et Communigate. Étant donné que toutes les fonctionnalités de Swaks sont basées sur des normes connues, il devrait fonctionner avec tout serveur de messagerie assez moderne. Si un problème est trouvé, veuillez en informer l'auteur à l'adresse ci-dessous.
