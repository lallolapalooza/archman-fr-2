NOM

swtpm - Émulateur TPM pour TPM 1.2 et 2.0

SYNTAXE

swtpm socket [OPTIONS]

swtpm chardev [OPTIONS]

swtpm cuse [OPTIONS]

DESCRIPTION

swtpm implémente un émulateur logiciel TPM basé sur libtpms. Il fournit un accès aux fonctionnalités du TPM via une interface de socket TCP/IP, ou il peut écouter les commandes sur un périphérique caractère, ou créer une interface CUSE (périphérique caractère dans l'espace utilisateur) pour recevoir les commandes TPM.

À moins que des paramètres de ligne de commande correspondants ne soient utilisés, la version socket de swtpm exige que la variable d'environnement TPM_PORT soit définie sur le port TCP/IP sur lequel le processus doit écouter les messages de requête TPM.

De même, la variable d'environnement TPM_PATH peut être définie et contenir le nom d'un répertoire où le TPM peut stocker son état persistant.

Le processus swtpm peut être terminé gracieusement en lui envoyant un signal SIGTERM.

La version CUSE de swtpm nécessite des droits root pour démarrer le TPM.

Options pour l'interface socket

Les options suivantes sont prises en charge si l'interface socket est choisie :

-p|--port <port>
Utilise le port donné plutôt que la variable d'environnement TPM_PORT.
-t|--terminate
Termine le TPM après que le client a fermé la connexion du canal de données (TCP uniquement).
--server [type=tcp][,port=<port>[,bindaddr=<adresse> [,ifname=<nom_interface>]]][,fd=<descripteur_fichier>][,disconnect]
Attend des connexions TCP sur le port donné ; si un port n'est pas fourni, un descripteur de fichier doit être passé avec le paramètre fd et les commandes sont lues à partir de ce descripteur de fichier. Si un port est fourni, l'adresse de liaison sur laquelle écouter les connexions TCP peut également être fournie ; l'adresse de liaison par défaut est 127.0.0.1. Si une adresse IPv6 locale au lien est fournie, le nom de l'interface à lier doit être fourni avec ifname.

Ce paramètre active par défaut une connexion persistante, sauf si l'option disconnect est donnée. Ce paramètre doit être utilisé à la place des options -p et --fd.

--server type=unixio[,path=<chemin>][,fd=<descripteur_fichier>] [,mode=<0...>][,uid=<uid>][,gid=<gid>]
Attend des connexions UnixIO sur le chemin donné. Si aucun chemin n'est fourni, un descripteur de fichier doit être passé à la place. Le paramètre mode permet à un utilisateur de définir les bits de mode du fichier du chemin UnixIO. La valeur des bits de mode doit être donnée sous forme de nombre octal commençant par un '0'. La valeur par défaut est 0770. uid et gid définissent la propriété du chemin du socket UnixIO. Cette opération nécessite des privilèges root.

Options pour l'interface de périphérique caractère

Les options suivantes sont prises en charge si l'interface chardev est choisie :

-c|--chardev <chemin_périphérique >
Utilise le périphérique donné pour écouter les commandes TPM et envoyer les réponses.
--vtpm-proxy
Crée une instance de périphérique proxy vTPM Linux et lit les commandes TPM depuis son périphérique backend.

Options pour l'interface CUSE

Les options suivantes sont prises en charge si l'interface cuse est choisie :

-n|--name <NOM>
Le TPM utilisera un périphérique avec le nom donné. Un périphérique avec le nom donné sera créé dans /dev. C'est une option obligatoire.
-M|--maj <NUMÉRO_MAJEUR>
Crée le périphérique avec le numéro majeur donné.
-m|--min <NUMÉRO_MINEUR>
Crée le périphérique avec le numéro mineur donné.

Options pour les interfaces socket et de périphérique caractère :

Les options suivantes sont prises en charge par les interfaces socket et de périphérique caractère :

-f|--fd <descripteur_fichier>
Utilise le descripteur de fichier de socket ou le descripteur de fichier de périphérique caractère donné pour recevoir les commandes TPM et envoyer les réponses. Pour l'interface socket, cette option suppose automatiquement -t.
-d|--daemon
Démonise le processus.
--ctrl type=[unixio|tcp][,path=<chemin>] [,port=<port>[,bindaddr=<adresse>[,ifname=<nom_interface>]]] [,fd=<descripteur_fichier>|clientfd=<descripteur_fichier>] [,mode=<0...>][,uid=<uid>][,gid=<gid>][,terminate]
Cette option ajoute un canal de contrôle au TPM. Le canal de contrôle peut utiliser soit un socket UnixIO avec un chemin ou un descripteur de fichier donné, soit utiliser un socket TCP sur le port ou le descripteur de fichier donné. Si un port est fourni, l'adresse de liaison sur laquelle écouter les connexions TCP peut également être fournie ; l'adresse de liaison par défaut est 127.0.0.1. Si une adresse IPv6 locale au lien est fournie, le nom de l'interface à lier doit être fourni avec ifname.

Le paramètre mode permet à un utilisateur de définir les bits de mode du fichier du chemin UnixIO. La valeur des bits de mode doit être donnée sous forme de nombre octal commençant par un '0'. La valeur par défaut est 0770. uid et gid définissent la propriété du chemin du socket UnixIO. Cette opération nécessite des privilèges root.

Le paramètre terminate active la terminaison automatique de swtpm lorsque la connexion du canal de contrôle a été perdue. Ceci est utile dans les scénarios où le canal de contrôle est maintenu en permanence, par exemple par QEMU, et que swtpm doit se terminer en cas de terminaison anormale du client qui ne pourrait plus envoyer de CMD_SHUTDOWN via le canal de contrôle.

Le canal de contrôle permet un contrôle hors bande du TPM, comme la réinitialisation du TPM.

Options pour toutes les interfaces

Les options suivantes sont prises en charge par toutes les interfaces :

--tpmstate dir=<répertoire>|backend-uri=<uri>[,mode=<0...>][,lock]
Utilise le chemin donné plutôt que la variable d'environnement TPM_PATH.

Si dir est spécifié, les fichiers d'état du TPM seront écrits dans le répertoire avec les bits de mode de fichier donnés. Cette valeur doit être donnée sous forme de nombre octal commençant par un '0'. La valeur par défaut est 0640.

Si backend-uri est spécifié, les données d'état du TPM seront stockées dans l'URI. Actuellement, backend-uri=dir://<chemin_vers_répertoire> et backend-uri=file://<chemin_vers_répertoire> sont disponibles. Pour 'dir://', l'URI doit spécifier le chemin du répertoire où les fichiers sont stockés. Si chemin_vers_répertoire commence par un '/' alors le chemin est interprété comme un chemin absolu, sinon c'est un chemin relatif au répertoire courant. Pour 'file://', l'URI doit spécifier un fichier unique ou un périphérique bloc où l'état du TPM sera stocké. Un périphérique bloc doit exister déjà et être suffisamment grand pour stocker tout l'état. (depuis v0.7)

Si lock est spécifié, alors le backend de stockage TPM verrouillera le fichier d'état du TPM pour éviter l'accès concurrent par une autre instance swtpm. La valeur par défaut, si ce paramètre d'option est manquant, dépend du backend de stockage. Pour le backend de répertoire, la valeur par défaut est que le verrouillage est toujours activé, et donc ce paramètre d'option n'a pas besoin d'être donné. Pour le backend de fichier, il est requis car la valeur par défaut est que le verrouillage n'est pas automatiquement activé. Pour éviter le verrouillage, lock=false peut être utilisé.

--tpm2
Choisir la fonctionnalité TPM 2 ; par défaut, un TPM 1.2 est choisi.
--log [fd=<descripteur_de_fichier>|file=<chemin>][,level=<n>] [,prefix=<préfixe>][,truncate]
Activer la journalisation dans un fichier donné par son descripteur de fichier ou son chemin. Utiliser '-' pour le chemin afin de supprimer la journalisation.

Le paramètre level permet à un utilisateur de choisir le niveau de journalisation. À partir du niveau de journalisation 5, la journalisation de débogage de libtpms est activée.

Toutes les lignes journalisées seront préfixées par prefix. Par défaut, aucun préfixe n'est ajouté.

Si truncate est passé, le fichier journal sera tronqué.

--locality reject-locality-4[,allow-set-locality]
Le paramètre reject-locality-4 provoquera le retour de messages d'erreur TPM pour les requêtes visant à définir le TPM en localité 4.

Le paramètre allow-set-locality permet à swtpm de recevoir des commandes TPM/TPM2_SetLocality. Ce paramètre est utile si l'accès au pilote proxy VTPM Linux est activé par passage de descripteur de fichier. Cette option est implicite avec l'option --vtpm-proxy et n'a donc pas besoin d'être explicitement définie si cette option est passée. Dans tous les autres cas, il faut être prudent quant à qui peut envoyer la commande TPM/TPM2_SetLocality.

--key file=<fichier_clé>|fd=<descripteur_de_fichier> [,format=<hex|binaire>][,mode=aes-cbc|aes-256-cbc], [remove[=true|false]]
Activer le chiffrement des fichiers d'état du TPM. Le fichier clé doit contenir une clé AES de taille prise en charge ; les clés de 128 bits (16 octets) et de 256 bits (32 octets) sont prises en charge.

La clé peut être au format binaire, auquel cas la taille du fichier doit être de 16 ou 32 octets. Si la clé est au format hexadécimal (par défaut), la clé peut être composée de 32 ou 64 chiffres hexadécimaux commençant par un '0x' optionnel.

Le paramètre mode indique quel mode de chaînage de blocs doit être utilisé. Actuellement, aes-cbc (aes-128-cbc) et aes-256-cbc sont pris en charge. Les données chiffrées sont protégées en intégrité à l'aide de encrypt-then-mac.

Le paramètre remove tentera de supprimer le fichier clé donné une fois que la clé a été lue.

--key pwdfile=<fichier_phrase_de_passe>|pwdfd=<descripteur_de_fichier> [,mode=aes-cbc|aes-256-cbc][remove[=true|false]][,kdf=sha512|pbkdf2]
Cette variante du paramètre clé permet à un utilisateur de fournir une phrase de passe dans un fichier. Le fichier est lu et une clé en est dérivée en utilisant soit un hachage SHA512, soit PBKDF2. Par défaut, PBKDF2 est utilisé.
--migration-key file=<fichier_clé>|fd=<descripteur_de_fichier> [,format=<hex|binaire>][,mode=aes-cbc|aes-256-cbc] [,remove[=true|false]]
La disponibilité d'une clé de migration garantit que l'état du TPM ne sera pas révélé sous forme non chiffrée lorsque les blobs d'état du TPM sont récupérés via l'interface ioctl. La clé de migration n'est pas utilisée pour chiffrer l'état du TPM écrit dans les fichiers, c'est à cela que sert le paramètre --key.

La clé de migration et la clé utilisée pour chiffrer les fichiers d'état du TPM peuvent être identiques.

Alors que la clé pour les fichiers d'état du TPM doit rester avec les fichiers qu'elle chiffre, la clé de migration doit rester avec les blobs d'état du TPM. Si, par exemple, l'état du TPM est migré entre des hôtes dans un centre de données, alors la clé de migration du TPM doit être disponible à toutes les destinations, donc en effet, elle peut devoir être une clé partagée sur toutes les machines du centre de données. Contrairement à cela, la clé utilisée pour chiffrer les fichiers d'état du TPM peut être différente pour chaque TPM et ne doit être disponible que sur l'hôte où réside l'état du TPM.

La clé de migration permet le chiffrement des blobs d'état du TPM. Le fichier clé doit contenir une clé AES de taille prise en charge ; les clés de 128 bits (16 octets) et de 256 bits (32 octets) sont prises en charge.

La clé peut être au format binaire, auquel cas la taille du fichier doit être de 16 ou 32 octets. Si la clé est au format hexadécimal (par défaut), la clé peut être composée de 32 ou 64 chiffres hexadécimaux commençant par un '0x' optionnel.

Le paramètre mode indique quel mode de chaînage de blocs doit être utilisé. Actuellement, aes-cbc (aes-128-cbc) et aes-256-cbc sont pris en charge. Les données chiffrées sont protégées en intégrité à l'aide de encrypt-then-mac.

Le paramètre remove tentera de supprimer le fichier clé donné une fois que la clé a été lue.

--migration-key pwdfile=<fichier_phrase_de_passe>|pwdfd=<descripteur_de_fichier> [,mode=aes-cbc|aes-256-cbc][,remove[=true|false]][,pdf=sha512|pbkdf2]
Cette variante du paramètre clé permet à un utilisateur de fournir une phrase de passe dans un fichier. Le fichier est lu et une clé en est dérivée en utilisant soit un hachage SHA512, soit PBKDF2. Par défaut, PBKDF2 est utilisé.
--pid file=<fichier_pid>|fd=<descripteur_de_fichier>
Cette option permet à un utilisateur de définir le nom du fichier où l'identifiant de processus (pid) du TPM sera écrit. Il est également possible de passer un descripteur de fichier vers un fichier qui a été ouvert en écriture.
-r|--runas <propriétaire>
Basculer vers l'utilisateur donné. Cette option ne peut être utilisée que lorsque swtpm est démarré en tant que root.
-R|--chroot <chemin<gt>
Chrooter dans le répertoire donné au démarrage. Cette option ne peut être utilisée que lorsque swtpm est démarré en tant que root.
--seccomp action=none|log|kill (depuis v0.2)
Cette option permet à un utilisateur de sélectionner l'action à entreprendre par le profil seccomp lorsqu'un appel système est exécuté et qu'il n'est pas autorisé. La valeur par défaut est kill. Pour désactiver le profil seccomp, choisissez none. L'action log journalise les appels système fautifs. L'action log n'est disponible que si libseccomp prend en charge la journalisation.

Cette option n'est disponible que sous Linux et uniquement si swtpm a été compilé avec le support de libseccomp.

--flags [not-need-init][,startup-clear|startup-state|startup-deactivated|startup-none][,disable-auto-shutdown]
Le drapeau not-need-init permet au TPM d'accepter les commandes TPM juste après le démarrage sans nécessiter qu'un INIT lui soit envoyé via le canal de commande (voir l'option '-i' de swtpm_ioctl).

Les options startup provoquent l'envoi automatique d'une commande TPM_Startup ou TPM2_Startup. L'option startup-deactivated n'est valide que pour un TPM 1.2. Ces options impliquent not-need-init, à l'exception de l'option startup-none, qui n'entraîne l'envoi d'aucune commande.

Si --vtpm-proxy est utilisé, startup-clear est automatiquement choisi, mais cela peut être modifié avec cette option.

Le drapeau disable-auto-shutdown empêche swtpm d'envoyer automatiquement un TPM2_Shutdown() avant la réinitialisation d'un TPM 2 ou avant que le processus swtpm ne soit terminé. Lorsque ce drapeau n'est pas fourni, swtpm enverra cette commande pour éviter d'augmenter le compteur de blocage par attaque par dictionnaire (DA) et finalement un blocage par DA par le TPM 2 en raison de l'omission de l'envoi d'un TPM2_Shutdown() requis avant la réinitialisation du TPM 2 ou la terminaison du processus swtpm.

--migration [incoming][,release-lock-outgoing]
Cette option permet de contrôler le verrouillage du stockage NVRAM afin de prendre en charge la migration entre hôtes disposant d'un stockage partagé pour le répertoire d'état de swtpm et si le verrouillage est pris en charge par le backend de stockage. Le backend de stockage par répertoire, par exemple, prend en charge le verrouillage et nécessite donc l'utilisation de cette option en cas de stockage partagé. Lors de la fourniture de l'option incoming, swtpm diffère le verrouillage de la NVRAM jusqu'à ce que les blobs d'état soient reçus ou jusqu'à ce que la première commande TPM soit traitée si aucun blob d'état n'a été reçu. Le paramètre d'option release-lock-outgoing fait en sorte que swtpm libère tout verrou NVRAM une fois que le blob 'savestate' du TPM est reçu de swtpm. Pour éviter de libérer le verrou trop tôt, les blobs d'état 'permanent' et 'volatile' doivent être reçus avant le blob 'savestate'.
--profile name=<profile-name>|profile=<json-profile>|file=<filename>|fd=<fd>[,remove-disabled=check|fips-host] (depuis v0.10)
Cette option permet de définir un profil pour un TPM 2. Un profil intégré peut être sélectionné par son nom à l'aide du paramètre d'option name=. Avec le paramètre d'option profile=, un profil formaté en JSON peut être passé directement. Avec le paramètre d'option file=, un profil formaté en JSON sera lu à partir d'un fichier. Le paramètre d'option fd= permet de le lire à partir d'un descripteur de fichier.

Les profils doivent référencer le nom d'un profil intégré. Notez que seul le profil 'custom' ou les profils dont le nom commence par 'custom:' peuvent être modifiés et fournir une liste d'algorithmes, de commandes ou d'attributs qui contrôlent quels algorithmes cryptographiques un TPM 2 active. Si l'une de ces listes n'est pas fournie, la liste correspondante du profil intégré 'custom' est utilisée.

L'option de ligne de commande suivante sélectionne le profil 'custom' sous le nouveau nom 'custom:test' avec l'attribut 'fips-host' défini :

[...] --profile '{"Name":"custom:test", "Attributes":"fips-host"}'

Le profil ne peut être défini que lors du tout premier démarrage d'une instance TPM 2 et tant qu'aucun fichier d'état n'existe. Le profil ne peut plus être modifié par la suite et, s'il est passé à nouveau via cette option, une erreur se produira.

Le paramètre d'option remove-disabled indique à swtpm de supprimer les algorithmes du profil qui sont désactivés lorsque FIPS est activé sur un hôte (paramètre fips-host ; référence RHEL 9.4+ mode FIPS) et que l'accès d'OpenSSL aux algorithmes cryptographiques est restreint. Le paramètre check peut être utilisé pour vérifier qu'un algorithme est effectivement désactivé avant de le supprimer. Cette option n'est prise en charge que si le profil custom est choisi. Dans ce cas, il effectuera (actuellement) les opérations suivantes :

  • supprime camellia, tdes et rsaes (chiffrement RSA avec remplissage PKCS#1 v1.5)
  • désactive le support de signature (RSA et EC) sur SHA1
  • désactive le chiffrement RSA non rembourré
  • définit la taille minimale des clés RSA à 2048 bits
  • définit la taille minimale des clés EC à 224 bits

Tous les autres algorithmes restent activés, y compris ceux que FIPS peut normalement ne pas autoriser, tels que ecdaa et ecschnorr, et d'autres. La liste des algorithmes désactivés sera étendue à l'avenir lorsque le mode FIPS sur l'hôte désactivera davantage d'algorithmes. Étant donné que dans ce cas swtpm peut ajouter des attributs au profil qui nécessitent un certain StateFormatLevel, il est recommandé d'omettre le champ StateFormatLevel du profil.

Pour voir la liste des algorithmes pris en charge et qui peuvent être désactivés, on peut utiliser swtpm comme suit.

Ici, l'utilisateur peut choisir de désactiver des algorithmes, des commandes et des attributs qui sont autorisés à être désactivés.     (depuis v0.10)

  
Affiche des informations sur le TPM à partir de l'appel TPMLIB_GetInfo de libtpms et quitte. Utilisez l'option --tpm2 pour des informations sur TPM 2. NOTES


Si un TPM 2 est utilisé, l'utilisateur est généralement tenu d'envoyer une commande
    TPM2_Shutdown() à un TPM 2 pour éviter d'augmenter potentiellement le
    compteur TPM_PT_LOCKOUT_COUNTER qui pourrait entraîner un verrouillage par attaque par dictionnaire (DA) lors du prochain démarrage (TPM2_Startup()) du TPM 2. La façon dont le compteur TPM_PT_LOCKOUT_COUNTER est augmenté dépend des commandes précédemment envoyées au TPM 2 ainsi que de l'état interne du TPM 2. Un exemple qui déclenchera l'augmentation du compteur est l'omission d'un mot de passe lors de la tentative d'accès à un objet protégé par mot de passe ou à un emplacement NVRAM ayant l'attribut DA défini, suivie de la terminaison de swtpm sans envoyer TPM2_Shutdown(). Pour éviter un verrouillage DA, swtpm fera de son mieux et enverra une commande
    TPM2_Shutdown(SU_STATE) ou TPM2_Shutdown(SU_CLEAR) si cela est jugé nécessaire.
