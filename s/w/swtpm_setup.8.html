NOM

swtpm_setup - Outil swtpm pour simuler la fabrication d'un TPM 1.2 ou 2.0

SYNOPIS

swtpm_setup [OPTIONS]

DESCRIPTION

swtpm_setup est un outil qui prépare l'état initial d'un TPM basé sur libtpms.

Les options suivantes sont supportées :

--runas <userid>
Utiliser cet identifiant utilisateur pour exécuter swtpm_setup. Seul 'root' peut utiliser cette option.
--config <fichier>
Chemin vers le fichier de configuration contenant l'outil à utiliser pour la création des certificats ; voir aussi swtpm_setup.conf

Si ce paramètre n'est pas fourni, le fichier de configuration par défaut sera utilisé. L'ordre de recherche pour le fichier de configuration par défaut est le suivant. Si la variable d'environnement XDG_CONFIG_HOME est définie, ${XDG_CONFIG_HOME}/swtpm_setup.conf sera utilisé s'il est disponible, sinon si la variable d'environnement HOME est définie, ${HOME}/.config/swtpm_setup.conf sera utilisé s'il est disponible. Si aucun des précédents n'est disponible, /etc/swtpm_setup.conf sera utilisé.

--tpm-state <dir> ou --tpmstate <dir>
Chemin où l'état du TPM sera écrit ; c'est un argument obligatoire. Précéder de dir:// pour utiliser le backend de répertoire, ou file:// pour utiliser un fichier linéaire.
--tpm <chemin vers l'exécutable>
Chemin vers l'exécutable du TPM ; c'est un argument optionnel et par défaut l'exécutable swtpm trouvé dans le PATH sera utilisé.
--tpm2
Effectuer la configuration sur un TPM 2 ; par défaut, un TPM 1.2 est configuré.
--createek
Créer une clé d'attestation (EK).
--allow-signing
Créer une EK qui peut signer. Cette option nécessite --tpm2.

Cette option créera une EK non standard. Lors de la recréation de l'EK, les outils TPM 2 devront utiliser le modèle d'EK qui est écrit à un index NV correspondant à l'EK créée (par exemple, index NV 0x01c00004 pour une EK RS 2048). Sinon, l'EK créée par l'outil ne correspondra pas à la clé réelle utilisée ou au module indiqué dans le certificat EK.

Notez que la spécification TCG "EK Credential Profile For TPM Family 2.0; Level 0" suggère dans sa section sur "EK Usage" que "la clé d'attestation peut être créée comme une clé de déchiffrement ou de signature." Cependant, certaines plateformes n'accepteront pas une EK comme clé de signature, ou comme clé de signature et de chiffrement, et par conséquent, cette option doit être utilisée avec une grande prudence.

--decryption
Créer une EK qui peut être utilisée pour le chiffrement de clés. C'est le défaut sauf si --allow-signing est passé. Cette option nécessite --tpm2.
--ecc
Créer des clés de cryptographie à courbe elliptique (ECC) ; par défaut, des clés RSA sont générées.
--take-ownership
Prendre possession ; cette option implique --createek. Cette option n'est disponible que pour le TPM 1.2.
--ownerpass <mot de passe>
Fournir un mot de passe propriétaire personnalisé ; par défaut 'ooo'. Cette option n'est disponible que pour le TPM 1.2.
--owner-well-known
Utiliser un mot de passe composé de zéros (20 octets de zéros) comme mot de passe propriétaire. Cette option n'est disponible que pour le TPM 1.2.
--srkpass <mot de passe>
Fournir un mot de passe SRK personnalisé ; par défaut 'sss'. Cette option n'est disponible que pour le TPM 1.2.
--srk-well-known
Utiliser un mot de passe composé de zéros (20 octets de zéros) comme mot de passe SRK. Cette option n'est disponible que pour le TPM 1.2.
--create-ek-cert
Créer un certificat EK ; cela implique --createek.
--create-platform-cert
Créer un certificat de plateforme ; cela implique --create-ek-cert.
--lock-nvram
Verrouiller l'accès NVRAM à tous les emplacements NVRAM qui ont été écrits.
--display
À la fin, afficher autant d'informations que possible sur la configuration du TPM.
--logfile <fichier journal>
Le fichier journal vers lequel journaliser. Par défaut, la journalisation va vers stdout et stderr.
--keyfile <fichier clé>
Le fichier clé contient une clé hexadécimale ASCII composée de 32 chiffres hex avec un préfixe optionnel '0x'. C'est la clé que l'émulateur TPM utilisera pour chiffrer l'état du TPM.
--keyfile-fd <descripteur de fichier>
Comme --keyfile mais la clé sera lue à partir du descripteur de fichier.
--pwdfile <fichier phrase de passe>
Le fichier phrase de passe contient une phrase de passe à partir de laquelle l'émulateur TPM dérivera la clé de chiffrement et utilisera cette clé pour chiffrer l'état du TPM.
--pwdfile-fd <descripteur de fichier>
Comme --pwdfile mais la phrase de passe sera lue à partir du descripteur de fichier.
--ciper <chiffrement>
Le chiffrement peut être soit aes-cbc soit aes-128-cbc pour un chiffrement AES de 128 bits, soit aes-256-cbc pour un chiffrement AES de 256 bits. Le même chiffrement doit être utilisé ultérieurement sur la ligne de commande swtpm.
--overwrite
Écraser l'état existant du TPM. Tout état précédent sera effacé. Si cette option n'est pas donnée et qu'un fichier d'état existant est trouvé, un code d'erreur sera retourné.
--not-overwrite
Ne pas écraser l'état existant du TPM. Si un état TPM existant est trouvé, le programme se termine sans erreur.
--vmid <ID de VM>
ID de VM optionnel qui peut être utilisé pour suivre les certificats émis pour les VM (ou conteneurs). Ce paramètre sera transmis à l'outil utilisé pour créer les certificats et peut être requis par cet outil.
--pcr-banks <banques PCR>
Liste optionnelle de banques PCR séparées par des virgules à activer. Fournir '-' permet à un utilisateur de sauter la sélection et active toutes les banques PCR. Si cette option n'est pas fournie, le fichier de configuration swtpm_setup.conf sera consulté pour l'entrée active_pcr_banks. Si aucune telle entrée n'est trouvée, alors l'ensemble par défaut des banques PCR sera activé. L'ensemble par défaut des banques PCR peut être déterminé en utilisant l'option --help.
--swtpm_ioctl <exécutable>
Passer le chemin vers l'exécutable swtpm_ioctl. Par défaut, swtpm_ioctl dans le PATH est utilisé.
--tcsd-system-ps-file <fichier>
Cette option est obsolète et n'a aucun effet (depuis v0.4).
--rsa-keysize <taille clé> (depuis v0.4)
Cette option permet de passer la taille d'une clé EK RSA TPM 2, comme 2048 ou 3072. Les tailles de clé supportées pour un TPM 2 peuvent être interrogées en utilisant l'option --print-capabilities. La taille par défaut est de 2048 bits pour le TPM 1.2 et le TPM 2. Si 'max' est passé, la plus grande taille de clé possible est utilisée.
--reconfigure (depuis v0.7)
Cette option permet la reconfiguration des banques PCR actives d'un TPM 2 en utilisant l'option --pcr-banks.
--profile <profil json> (depuis v0.10)
Configurer un TPM 2 avec le profil donné. Les exemples de profils ressemblent à ceci : 
{"Nom": "null"}
{"Nom": "default-v1"}
{
 "Nom": "custom",
 "Algorithmes":"rsa,rsa-min-size=1024,tdes-min-size=128,hmac,aes,\
               aes-min-size=128,mgf1,keyed

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

{ "hash": [ "sha256", "sha384", "sha512", "null" ], "commands": [ "rsassa", "rsaes", "rsapss", "oaep", "ecdsa", "ecdh", "ecdaa", "sm2", "ecschnorr", "ecmqv", "kdf1-sp800-56a", "kdf2", "kdf1-sp800-108", "ecc", "ecc-min-size=192", "ecc-nist", "ecc-bn", "symcipher", "camellia", "camellia-min-size=128", "cmac", "ctr", "ofb", "cbc", "cfb", "ecb" ], "name": "custom" } ```

Le profil JSON doit contenir le champ 'name' avec le nom d'un profil supporté par libtpms. Seul le profil 'custom', ou les profils dont le nom commence par 'custom:', sont modifiables et peuvent contenir les champs Algorithms, Commands, ou Attributes avec les sélections de l'utilisateur. Les champs inconnus dans le profil JSON seront ignorés. Pour plus d'informations, voir la page de manuel de swtpm.

--profile-name <nom de fichier de profil| nom de profil intégré (depuis v0.10)
Configurer un TPM 2 avec un profil chargé depuis l'un des emplacements suivants dans l'ordre indiqué, sauf s'il est qualifié par un préfixe :
  • Le répertoire des profils locaux spécifié dans swtpm_setup.conf comme 'local_profiles_dir'; pour forcer le chargement du profil depuis ce répertoire, préfixez le nom avec 'local:'.
  • Le répertoire des profils de distribution, qui est typiquement /usr/share/swtpm/profiles; pour forcer le chargement du profil depuis ce répertoire, préfixez le nom avec 'distro:'.
  • Instancier un profil intégré à libtpms; pour forcer un profil intégré, préfixez le nom avec 'builtin:'.

Tous les profils chargés depuis les répertoires mentionnés ci-dessus nécessitent que le fichier soit disponible sous le nom donné avec '.json' ajouté.

Utilisez les options --print-profiles et --tpm2 pour afficher tous les profils disponibles.

--profile-file <fichier> (depuis v0.10)
Configurer un TPM 2 avec un profil à partir d'un fichier.
--profile-file-fd <descripteur de fichier> (depuis v0.10)
Configurer un TPM 2 avec un profil lu à partir d'un descripteur de fichier.
--profile-remove-disabled check|fips-host (depuis v0.10)
Lorsque cette option est passée, swtpm supprimera les algorithmes du profil donné qu'OpenSSL ne peut pas utiliser lorsque le mode FIPS est activé sur l'hôte. Si le paramètre check est donné, les algorithmes sont testés avant d'être supprimés, tandis que le paramètre fips-host force la suppression de tous les algorithmes potentiellement désactivés sans les tester.

Cette option ne fonctionne que si le profil 'custom' est référencé en passant par exemple --profile '{"Name":"custom:test"}'.

Cette option passe le paramètre d'option remove-disable comme partie de l'option --profile à swtpm. Pour plus d'informations, voir la page de manuel de swtpm.

--print-profiles (depuis v0.10)
Affiche tous les profils trouvés dans les répertoires de profils locaux et de distribution et affiche ceux intégrés. Tous les profils stockés dans des fichiers doivent avoir l'extension .json. Les noms dans le JSON affiché montreront le nom sous lequel ces profils peuvent être chargés avec l'option --profile-name, c'est-à-dire qu'ils montreront leur nom de fichier sans l'extension .json. Par conséquent, un fichier de profil myprofile.json affichera le Name 'myprofile'. L'auteur du profil peut vouloir définir le Name dans le JSON du profil à 'custom:myprofile'.
--print-capabilities (depuis v0.2)
Affiche les capacités qui ont été ajoutées à swtpm_setup après la version 0.1. La sortie peut contenir les éléments suivants : 
{
  "type": "swtpm_setup",
  "features": [
    "tpm-1.2",
    "tpm-2.0",
    "cmdarg-keyfile-fd",
    "cmdarg-pwdfile-fd",
    "tpm12-not-need-root",
    "cmdarg-write-ek-cert-files",
    "cmdarg-create-config-files",
    "cmdarg-reconfigure-pcr-banks",
    "tpm2-rsa-keysize-2048",
    "tpm2-rsa-keysize-3072",
    "cmdarg-profile",
    "cmdarg-profile-remove-disabled"
  ],
  "version": "0.7.0"
}

Le champ version est disponible depuis v0.7.

La signification des verbes de fonctionnalités est la suivante :

cmdarg-key-fd (depuis v0.2)
L'option --keyfile-fd est supportée.
cmdarg-pwd-fd (depuis v0.2)
L'option --pwdfile-fd est supportée.
cmdarg-write-ek-cert-files (depuis v0.7)
L'option --write-ek-cert-files est supportée.
cmdarg-create-config-files (depuis v0.7)
L'option --create-config-files est supportée.
cmdarg-reconfigure-pcr-banks (depuis v0.7)
L'option --reconfigure est supportée et permet la reconfiguration des banques PCR actives.
tpm2-rsa-keysize-2048, ... (depuis v0.4)
Les tailles de clés RSA indiquées sont supportées pour la clé EK d'un TPM 2. Si aucun des verbes tpm2-rsa-keysize n'est affiché, seules les clés RSA de 2048 bits sont supportées.
tpm12-not-need-root (depuis v0.4)
Cette option implique que n'importe quel utilisateur peut configurer un TPM 1.2. Auparavant, seuls root ou l'utilisateur 'tss', selon la configuration et la disponibilité de ce compte, pouvaient le faire.
tpm-1.2 (depuis v0.7)
La configuration TPM 1.2 est supportée (libtpms est compilé avec le support TPM 1.2).
tpm-2.0 (depuis v0.7)
La configuration TPM 2 est supportée (libtpms est compilé avec le support TPM 2).
cmdarg-profile (depuis v0.10)
Les options --profile, profile-file, et --profile-file-fd sont supportées.
cmdarg-profile-remove-disabled (depuis v0.10)
L'option --profile-remove-disabled est supportée.
--write-ek-cert-files <répertoire> (depuis v0.7)
Cette option provoque l'écriture des fichiers de clé d'endossement (EK) dans le répertoire fourni. Les fichiers contiennent les EK au format DER qui ont été écrits dans les emplacements NVRAM du TPM 1.2 ou TPM 2. Les fichiers EK ont le modèle de nom de fichier ek-<type de clé>.crt. Des exemples de noms de fichiers sont ek-rsa2048.crt, ek-rsa3072.crt, et ek-secp384r1.crt.

Les clés qui sont écrites pour un TPM 2 peuvent changer avec le temps car la force par défaut des clés EK change. Cela signifie qu'il faut rechercher tous les fichiers correspondant au modèle de nom de fichier ci-dessus lors de la recherche des EK.

--create-config-files [[overwrite][,root][,skip-if-exist]] (depuis v0.7)
Cette option permet à un utilisateur de créer des fichiers de configuration pour swtpm_setup et swtpm-localca sous les répertoires $XDG_CONFIG_HOME ou $HOME/.config.

Les fichiers de configuration ne seront pas créés si l'un d'entre eux existe déjà et dans ce cas, le programme signalera le premier fichier trouvé et sortira avec un code d'erreur.

La signification des options est la suivante :

overwrite
Écrase les fichiers de configuration existants.
root
Crée les fichiers de configuration même sous le compte root. Ces fichiers de configuration peuvent alors masquer tout autre fichier de configuration existant, comme /etc/swtpm-localca.conf par exemple.
skip-if-exist
Ne fait rien si l'un des fichiers de configuration qui seraient créés existe déjà. Le programme se terminera sans code d'erreur.

Note : Le cas où un utilisateur fait partie du groupe autorisé à accéder aux chemins par défaut des fichiers de configuration n'est actuellement pas géré. Sur de nombreux systèmes, cela peut être le cas lorsqu'un utilisateur fait partie du groupe 'tss'. Dans ce cas, il est recommandé à l'utilisateur de remplacer swtpm-localca.conf créé avec cette commande par un lien symbolique vers /etc/swtpm-localca.conf.

--help, -h
Affiche l'écran d'aide

EXEMPLE D'UTILISATION

Pour simuler la fabrication d'un TPM, on exécuterait typiquement la commande suivante :

#> sudo swtpm_setup --tpmstate /tmp/mytpm1/ \
    --create-ek-cert --create-platform-cert --lock-nvram

Note : depuis v0.4, la configuration TPM 1.2 ne nécessite plus de droits root.

Tout utilisateur peut également simuler la fabrication d'un TPM en utilisant l'utilitaire swtpm_localca. L'exemple suivant suppose que l'utilisateur a défini la variable d'environnement XDG_CONFIG_HOME comme suit (en utilisant bash par exemple) :

export XDG_CONFIG_HOME=~/.config

Note : la variable XDG_CONFIG_HOME fait partie de la spécification XDG Base Directory.

Les fichiers de configuration suivants doivent être créés :

~/.config/swtpm_setup.conf :

# Programme invoqué pour la création des certificats
create_certs_tool= /usr/share/swtpm/swtpm-localca
create_certs_tool_config = ${XDG_CONFIG_HOME}/swtpm-localca.conf
create_certs_tool_options = ${XDG_CONFIG_HOME}/swtpm-localca.options

~/.config/swtpm-localca.conf :

statedir = ${XDG_CONFIG_HOME}/var/lib/swtpm-localca
signingkey = ${XDG_CONFIG_HOME}/var/lib/swtpm-localca/signkey.pem
issuercert = ${XDG_CONFIG_HOME}/var/lib/swtpm-localca/issuercert.pem
certserial = ${XDG_CONFIG_HOME}/var/lib/swtpm-localca/certserial

~/.config/swtpm-localca.options :

--platform-manufacturer Fedora
--platform-version 2.12
--platform-model QEMU

Note : l'outil swtpm-create-user-config-files peut être utilisé pour créer de tels fichiers (avec un contenu différent) :

#> /usr/share/swtpm/swtpm-create-user-config-files
Writing /home/stefanb/.config/swtpm_setup.conf.
Writing /home/stefanb/.config/swtpm-localca.conf.

NAME

swtpm_setup

setup a TPM 2 device

SYNOPSIS

swtpm_setup [-h|--help] [-V|--version]
[--tpmstate path] [--tpm2] [--create-ek-cert]
[--create-platform-cert] [--lock-nvram]

DESCRIPTION

The swtpm_setup utility can be used to initialize a TPM 2 device. The state of the TPM device is stored in a directory, which is specified by the --tpmstate option. If the directory does not exist, it will be created.

If the --tpm2 option is given, a TPM 2 device will be set up. Otherwise a TPM 1.2 device is set up.

The --create-ek-cert option requests that an endorsement key (EK) certificate is created for the TPM. The private key for the EK is generated and stored in the TPM's NVRAM. The certificate is generated based on information available from the TPM, such as the TPM's EK public key and manufacturer specific information. A self-signed certificate is generated if no other signing mechanism is available.

The --create-platform-cert option requests that a platform certificate is created. The platform certificate is used to attest the identity of the platform the TPM is running on. It is signed by a platform certificate authority (CA). For testing purposes, a self-signed certificate can be generated.

The --lock-nvram option locks the TPM's NVRAM area after setup. This prevents further modifications to the NVRAM contents.

EXAMPLE USAGE

The following commands now create a TPM 2 with an EK and platform certificate. The state of the TPM 2 will be stored in the directory ${XDG_CONFIG_HOME}/mytpm1.

#> mkdir -p ${XDG_CONFIG_HOME}/mytpm1
#> swtpm_setup --tpm2 --tpmstate ${XDG_CONFIG_HOME}/mytpm1 \
    --create-ek-cert --create-platform-cert --lock-nvram
