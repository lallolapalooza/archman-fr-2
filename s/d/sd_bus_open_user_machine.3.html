int sd_bus_open_system_machine(sd_bus **bus, const char *machine);

DESCRIPTION

sd_bus_default() acquiert un objet de connexion de bus au bus utilisateur lorsqu'il est appelé dans une tranche utilisateur (toute session sous "user-*.slice", par exemple : "user@1000.service"), ou au bus système sinon. L'objet de connexion est associé au thread appelant. Chaque fois que la fonction est appelée à partir du même thread, le même objet est retourné, mais son compteur de références est incrémenté d'une unité, tant qu'au moins une référence est conservée. Lorsque la dernière référence à la connexion est abandonnée (en utilisant l'appel sd_bus_unref(3)), la connexion est terminée. Notez que la connexion n'est pas automatiquement terminée lorsque le thread associé se termine. Il est important d'abandonner explicitement la dernière référence à la connexion de bus avant la fin du thread, car sinon, la connexion fuira. De plus, les messages mis en file d'attente mais non lus ou non écrits maintiennent une référence au bus, voir ci-dessous.

sd_bus_default_user() renvoie un objet de connexion de bus utilisateur associé au thread appelant. sd_bus_default_system() est similaire, mais se connecte au bus système. Notez que sd_bus_default() est identique à ces deux appels, selon le contexte d'exécution.

sd_bus_open() crée une nouvelle connexion de bus indépendante au bus utilisateur lorsqu'elle est appelée dans un contexte utilisateur, ou au bus système sinon. sd_bus_open_user() est similaire, mais se connecte uniquement au bus utilisateur. sd_bus_open_system() fait de même, mais se connecte au bus système. Contrairement à sd_bus_default(), sd_bus_default_user() et sd_bus_default_system(), ces appels renvoient de nouveaux objets de connexion indépendants qui ne sont pas associés au thread appelant et ne sont pas partagés entre plusieurs appels. Il est recommandé de partager les connexions par thread pour utiliser efficacement les ressources disponibles. Ainsi, il est recommandé d'utiliser sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() pour se connecter aux bus utilisateur ou système.

sd_bus_open_with_description(), sd_bus_open_user_with_description() et sd_bus_open_system_with_description() sont similaires à sd_bus_open(), sd_bus_open_user() et sd_bus_open_system(), mais permettent de définir une chaîne de description, voir sd_bus_set_description(3). description peut être NULL, auquel cas cette fonction est équivalente à sd_bus_open(). Cette chaîne de description est utilisée dans les messages de journalisation concernant l'objet bus, et l'inclusion d'un "nom" pour le bus les rend plus faciles à comprendre. Certains messages sont émis lors de l'initialisation du bus, par conséquent, l'utilisation de cette fonction est préférable à la définition de la description ultérieurement avec sd_bus_open_with_description(). L'argument est copié en interne et ne sera pas référencé après le retour de la fonction.

Si la variable d'environnement $DBUS_SESSION_BUS_ADDRESS est définie (voir environ(7)), elle sera utilisée comme adresse du bus utilisateur. Cette variable peut contenir plusieurs adresses séparées par des ";". Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance par défaut du bus D-Bus utilisateur sera utilisée.

Si la variable d'environnement $DBUS_SYSTEM_BUS_ADDRESS est définie, elle sera utilisée comme adresse du bus système. Cette variable utilise la même syntaxe que $DBUS_SESSION_BUS_ADDRESS. Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance par défaut du bus D-Bus système sera utilisée.

sd_bus_open_system_remote() se connecte au bus système sur l'hôte spécifié en utilisant ssh(1). host se compose d'un nom d'utilisateur optionnel suivi du symbole "@", et du nom d'hôte, optionnellement suivi d'un ":" et d'un port, optionnellement suivi d'un "/" et d'un nom de machine. Si le nom de machine est donné, une connexion est créée au bus système dans le conteneur spécifié sur la machine distante, et sinon une connexion au bus système sur l'hôte spécifié est créée.

Notez que l'entrée dans un conteneur est une opération privilégiée, et ne fonctionnera probablement que pour l'utilisateur root sur la machine distante.

sd_bus_open_system_machine() se connecte au bus système dans la machine spécifiée, où machine est le nom d'un conteneur local, potentiellement préfixé par un nom d'utilisateur et un séparateur "@". Si le nom du conteneur est spécifié comme la chaîne spéciale ".host" la connexion est établie au système local. Ceci est utile pour se connecter au bus système local en tant qu'utilisateur spécifique, par exemple "foobar@.host" pour se connecter au bus système local en tant qu'utilisateur local "foobar". Si la syntaxe "@" est utilisée, le côté gauche ou le côté droit peut être omis (mais pas les deux) auquel cas le nom d'utilisateur local ou ".host" est implicite. Si la syntaxe "@" n'est pas utilisée, la connexion est toujours effectuée en tant qu'utilisateur root. Voir sd_bus_set_address(3) pour une description de la syntaxe d'adresse, et machinectl(1) pour plus d'informations sur le concept de "machine". Notez que les connexions dans les conteneurs locaux ne sont actuellement disponibles que pour les processus privilégiés.

sd_bus_open_user_machine() est similaire à sd_bus_open_system_machine(), mais se connecte au bus utilisateur de l'utilisateur root, ou si la syntaxe "@" est utilisée, de l'utilisateur spécifié.

Ces appels allouent un objet de connexion de bus et initient la connexion à un bus bien connu d'une certaine forme. Une alternative à l'utilisation de ces appels de haut niveau est de créer un objet de bus non connecté avec sd_bus_new(3) et de le connecter avec sd_bus_start(3).

PROPRIÉTÉ DES RÉFÉRENCES

Les fonctions sd_bus_open(), sd_bus_open_user(), sd_bus_open_user_machine(), sd_bus_open_system(), sd_bus_open_system_remote(), et sd_bus_open_system_machine() renvoient un nouvel objet de connexion et l'appelant possède la seule référence. Lorsqu'elle n'est plus nécessaire, cette référence doit être détruite avec sd_bus_unref(3).

Les fonctions sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() ne créent pas nécessairement un nouvel objet, mais incrémentent la référence de connexion d'un objet de connexion existant d'une unité. Utilisez sd_bus_unref(3) pour abandonner la référence.

Les messages mis en file d'attente mais non écrits/non lus conservent une référence à leur objet de connexion de bus. Pour cette raison, même si une application a abandonné toutes les références à une connexion de bus, elle pourrait ne pas être détruite immédiatement. Tant que tous les messages reçus mis en file d'attente ne sont pas lus, et tant que tous les messages sortants non écrits ne sont pas écrits, l'objet de bus restera actif. sd_bus_flush() peut être utilisé pour écrire tous les messages sortants mis en file d'attente afin qu'ils abandonnent leurs références. SYNOPSIS

 #include <systemd/sd-bus.h>
 int sd_bus_open_user(sd_bus **bus);
 int sd_bus_open_system(sd_bus **bus);
 int sd_bus_open_system_remote(sd_bus **bus, const char *dest);
 int sd_bus_default_user(sd_bus **bus);
 int sd_bus_default_system(sd_bus **bus);
 int sd_bus_open_with_description(sd_bus **bus, const char *description);
 int sd_bus_open_user_with_description(sd_bus **bus, const char *description);
 int sd_bus_open_system_with_description(sd_bus **bus, const char *description);
 int sd_bus_open_system_machine(sd_bus **bus, const char *machine);
 int sd_bus_open_user_machine(sd_bus **bus, const char *machine);

DESCRIPTION

These functions provide convenient ways to obtain an sd-bus(3) object representing a connection to either the system bus or the user session bus. The returned bus object may be used to send and receive D-Bus messages. After use, the bus object should be decremented using sd_bus_unref(3).

The user and system buses are well-known D-Bus instances available on most Linux systems. The system bus is used for communication between system services and kernel interfaces, while the user bus is used for communication between user applications and services running in the user's session.

sd_bus_open_user() and sd_bus_open_system() attempt to connect to the D-Bus instance specified by the environment variables $XDG_RUNTIME_DIR (for the user bus) and $DBUS_SESSION_BUS_ADDRESS (for the user bus) or $SYSTEMD_BUS_ADDRESS (for the system bus). If these are not set, default paths are used.

sd_bus_default_user() and sd_bus_default_system() are similar to sd_bus_open_user() and sd_bus_open_system(), but they try to obtain the bus connection object that is already associated with the calling thread's default bus object, if one exists. If no default bus object is associated with the thread, they will attempt to open a new bus connection as if sd_bus_open_user() or sd_bus_open_system() were called.

sd_bus_open_system_remote() connects to a remote system bus specified by the address string dest. This is typically used to connect to the bus of a system running in a virtual machine or container.

sd_bus_open_with_description(), sd_bus_open_user_with_description(), and sd_bus_open_system_with_description() work like sd_bus_open(), sd_bus_open_user(), and sd_bus_open_system() respectively, but allow specifying an arbitrary bus address string using the description parameter. This is equivalent to setting the $DBUS_SESSION_BUS_ADDRESS or $SYSTEMD_BUS_ADDRESS environment variables.

sd_bus_open_system_machine() and sd_bus_open_user_machine() connect to the D-Bus bus of a specific systemd-nspawn container or virtual machine identified by the string machine. These functions require the systemd-machined.service(8) to be running and accessible.

It is important to note that the bus objects returned by the `_default_*` functions are associated with the calling thread. If the program uses multiple threads, care must be taken to manage the bus connection appropriately. Specifically, closing the bus connection using sd_bus_close() should only be done once for the entire process or when the thread owning the default bus connection terminates.

When closing a bus connection, it is recommended to first call sd_bus_flush() to ensure all pending messages are sent before closing the connection. This is especially important when shutting down a process or thread that has unread incoming messages.

REFERENCE OWNERSHIP

By default, bus objects returned by these functions are owned by the caller and must be explicitly closed using sd_bus_close(3) and unreferenced using sd_bus_unref(3). Slot objects created via functions like sd_bus_add_match(3) also keep a reference to their bus connection. Therefore, as long as a slot object is referenced, the bus object will remain allocated. Bus slot objects can be set to "floating" mode using sd_bus_slot_set_floating(3). In floating mode, the bus slot object's lifecycle is tied to the bus object; when the bus object is freed, the bus slot object is automatically unreferenced. Floating bus slot objects are often created by passing NULL as the slot parameter to functions like sd_bus_add_match(), indicating that the caller is not interested in explicitly managing the bus slot object.

The lifecycle of the default bus connection should be managed by the code that creates or owns the thread associated with the default bus object. Library code should avoid calling sd_bus_flush(3) or sd_bus_close(3) on default bus objects unless it is operating within its own private, self-allocated thread. Library code should only use the default bus object in other threads if it is clear that the program using the library will manage the bus connection's lifecycle, including flushing and closing it before the thread exits. In libraries where it's uncertain whether the calling program will manage the bus connection's lifecycle, it is recommended to use sd_bus_open_system() or sd_bus_open_user() instead of the `_default_*` variants.

RETURN VALUE

On success, these calls return 0 or a positive integer. On failure, these calls return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

The specified parameters are invalid.

-ENOMEDIUM

The requested bus type is not available because of invalid environment (for example the user session bus is not available because $XDG_RUNTIME_DIR is not set).

-ENOMEM

Memory allocation failed.

-ESOCKTNOSUPPORT

The protocol version required to connect to the selected bus is not supported.

In addition, other connection-related errors may be returned. See sd_bus_send(3).

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
