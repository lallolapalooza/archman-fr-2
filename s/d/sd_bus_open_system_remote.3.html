DESCRIPTION

sd_bus_default() acquiert un objet de connexion au bus utilisateur lorsque appelé depuis une tranche utilisateur (n'importe quelle session sous "user-*.slice", par exemple : "user@1000.service"), ou au bus système sinon. L'objet de connexion est associé au thread appelant. Chaque fois que la fonction est appelée depuis le même thread, le même objet est retourné, mais son compteur de références est augmenté d'une unité, tant qu'au moins une référence est conservée. Lorsque la dernière référence à la connexion est libérée (en utilisant l'appel sd_bus_unref(3)), la connexion est terminée. Notez que la connexion n'est pas automatiquement terminée lorsque le thread associé se termine. Il est important de libérer explicitement la dernière référence à la connexion bus avant que le thread ne se termine, sinon la connexion sera une fuite. De plus, les messages mis en file d'attente mais non lus ou non écrits maintiennent une référence au bus, voir ci-dessous.

sd_bus_default_user() retourne un objet de connexion au bus utilisateur associé au thread appelant. sd_bus_default_system() est similaire, mais se connecte au bus système. Notez que sd_bus_default() est identique à ces deux appels, en fonction du contexte d'exécution.

sd_bus_open() crée une nouvelle connexion bus indépendante au bus utilisateur lorsqu'elle est appelée dans le contexte utilisateur, ou au bus système sinon. sd_bus_open_user() est similaire, mais se connecte uniquement au bus utilisateur. sd_bus_open_system() fait de même, mais se connecte au bus système. Contrairement à sd_bus_default(), sd_bus_default_user() et sd_bus_default_system(), ces appels retournent de nouveaux objets de connexion indépendants qui ne sont pas associés au thread appelant et ne sont pas partagés entre plusieurs appels. Il est recommandé de partager les connexions par thread pour utiliser efficacement les ressources disponibles. Par conséquent, il est recommandé d'utiliser sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() pour se connecter aux bus utilisateur ou système.

sd_bus_open_with_description(), sd_bus_open_user_with_description() et sd_bus_open_system_with_description() sont similaires à sd_bus_open(), sd_bus_open_user() et sd_bus_open_system(), mais permettent de définir une chaîne de description, voir sd_bus_set_description(3). description peut être NULL, auquel cas cette fonction est équivalente à sd_bus_open(). Cette chaîne de description est utilisée dans les messages de journalisation concernant l'objet bus, et l'inclusion d'un "nom" pour le bus les rend plus faciles à comprendre. Certains messages sont émis lors de l'initialisation du bus, d'où l'intérêt d'utiliser cette fonction plutôt que de définir la description plus tard avec sd_bus_open_with_description(). L'argument est copié en interne et ne sera plus référencé après le retour de la fonction.

Si la variable d'environnement $DBUS_SESSION_BUS_ADDRESS est définie (cf. environ(7)), elle sera utilisée comme adresse du bus utilisateur. Cette variable peut contenir plusieurs adresses séparées par des ";". Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance D-Bus utilisateur par défaut sera utilisée.

Si la variable d'environnement $DBUS_SYSTEM_BUS_ADDRESS est définie, elle sera utilisée comme adresse du bus système. Cette variable utilise la même syntaxe que $DBUS_SESSION_BUS_ADDRESS. Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance D-Bus système par défaut sera utilisée.

sd_bus_open_system_remote() se connecte au bus système sur l'hôte spécifié en utilisant ssh(1). host se compose d'un nom d'utilisateur optionnel suivi du symbole "@", et du nom d'hôte, éventuellement suivi d'un ":" et d'un port, éventuellement suivi d'un "/" et d'un nom de machine. Si le nom de machine est donné, une connexion est créée vers le bus système dans le conteneur spécifié sur la machine distante, et sinon une connexion vers le bus système sur l'hôte spécifié est créée.

Notez que l'entrée dans un conteneur est une opération privilégiée, et ne fonctionnera probablement que pour l'utilisateur root sur la machine distante.

sd_bus_open_system_machine() se connecte au bus système dans la machine spécifiée, où machine est le nom d'un conteneur local, éventuellement préfixé par un nom d'utilisateur et un "@" séparateur. Si le nom du conteneur est spécifié comme la chaîne spéciale ".host", la connexion est établie au système local. Ceci est utile pour se connecter au bus système local en tant qu'utilisateur spécifique, par exemple "foobar@.host" pour se connecter au bus système local en tant qu'utilisateur local "foobar". Si la syntaxe "@" est utilisée, soit le côté gauche, soit le côté droit peut être omis (mais pas les deux), auquel cas le nom d'utilisateur local ou ".host" est implicite. Si la syntaxe "@" n'est pas utilisée, la connexion est toujours établie en tant qu'utilisateur root. Voir sd_bus_set_address(3) pour une description de la syntaxe d'adresse, et machinectl(1) pour plus d'informations sur le concept de "machine". Notez que les connexions dans des conteneurs locaux ne sont actuellement disponibles qu'aux processus privilégiés.

sd_bus_open_user_machine() est similaire à sd_bus_open_system_machine(), mais se connecte au bus utilisateur de l'utilisateur root, ou si la syntaxe "@" est utilisée, de l'utilisateur spécifié.

Ces appels allouent un objet de connexion bus et initient la connexion à un bus bien connu d'une certaine forme. Une alternative à l'utilisation de ces appels de haut niveau est de créer un objet bus non connecté avec sd_bus_new(3) et de le connecter avec sd_bus_start(3).

PROPRIÉTÉ DES RÉFÉRENCES

Les fonctions sd_bus_open(), sd_bus_open_user(), sd_bus_open_user_machine(), sd_bus_open_system(), sd_bus_open_system_remote() et sd_bus_open_system_machine() retournent un nouvel objet de connexion et l'appelant possède la référence unique. Lorsqu'elle n'est plus nécessaire, cette référence doit être détruite avec sd_bus_unref(3).

Les fonctions sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() ne créent pas nécessairement un nouvel objet, mais augmentent la référence de connexion d'un objet de connexion existant d'une unité. Utilisez sd_bus_unref(3) pour libérer la référence.

Les messages mis en file d'attente mais non écrits/lus conservent une référence à leur objet de connexion bus. Pour cette raison, même si une application a libéré toutes les références à une connexion bus, elle pourrait ne pas être détruite immédiatement. Tant que tous les messages entrants mis en file d'attente ne sont pas lus, et tant que tous les messages sortants non écrits ne sont pas écrits, l'objet bus restera en vie. sd_bus_flush() peut être utilisé pour écrire tous les messages sortants mis en file d'attente afin qu'ils libèrent leurs références. DESCRIPTION

These functions provide access to the D-Bus bus instances managed by systemd. The system and user service managers (PID 1 and the user instance of systemd) expose a D-Bus interface, and these functions allow clients to connect to it.

sd_bus_open_system() connects to the system instance of the D-Bus bus. This bus is used for system-wide communication, e.g. for querying hardware information, managing services, or controlling system state.

sd_bus_open_user() connects to the D-Bus bus of the calling user. This bus is used for communication between user-specific services and applications.

sd_bus_default_system(), sd_bus_default_user(), and sd_bus_default() are convenience functions that return a pointer to the default bus connection object for the system, user, or both, respectively. These default objects are created on demand and are globally unique per bus type within the process. They should generally not be closed or flushed manually. See REFERENCE OWNERSHIP for details.

sd_bus_open() is equivalent to sd_bus_open_user(). This function is deprecated.

sd_bus_open_system_remote() connects to a remote system D-Bus bus identified by destination. The destination string is typically an SSH connection string (e.g. "user@host:port"). If it specifies a local connection (e.g. "none"), it behaves like sd_bus_open_system().

sd_bus_open_system_machine() connects to the system D-Bus bus of a virtual machine or container identified by machine. The machine name should be a name registered with systemd-machined(8). If machine is NULL, it connects to the local system D-Bus bus, like sd_bus_open_system().

sd_bus_open_user_machine() connects to the user D-Bus bus of a virtual machine or container identified by machine. The machine name should be a name registered with systemd-machined(8). If machine is NULL, it connects to the local user D-Bus bus, like sd_bus_open_user().

sd_bus_open_system_with_description() and sd_bus_open_user_with_description() are similar to sd_bus_open_system() and sd_bus_open_user(), respectively, but allow specifying a connection string in description. This is mostly useful for connecting to buses other than the standard system or user buses, or for specifying connection parameters like authentication credentials.

All the sd_bus_open_* functions allocate a new bus object, increment its reference count, and return it in the bus parameter. The caller is responsible for releasing this reference with sd_bus_unref(3).

The default bus connections returned by sd_bus_default_* functions are managed internally. Their reference count is managed by the systemd library, and they should not be closed or flushed explicitly by the caller. They are automatically flushed and closed when the process exits. See REFERENCE OWNERSHIP.

REFERENCE OWNERSHIP

In all functions described here that return a `sd_bus *` object via an output parameter, a new reference to the bus object is returned. The caller is expected to take ownership of this reference and later release it using sd_bus_unref(3). If the caller does not need the bus object anymore, it should be closed using sd_bus_close(3).

The default bus objects returned by sd_bus_default_* functions are managed internally. They are automatically flushed and closed when the process exits. The caller should not invoke sd_bus_flush(3) or sd_bus_close(3) on these objects. If the caller needs to ensure that all pending outgoing messages are sent before continuing, it should use sd_bus_process(3) in a loop until it returns 0, and then read and discard any unread incoming messages, use sd_bus_close(), which will also close the bus connection. When using the default bus logic, it is a good idea to first invoke sd_bus_flush() followed by sd_bus_close() when a thread or process terminates, and thus its bus connection object should be freed.

Normally, slot objects (as created by sd_bus_add_match(3) and similar calls) keep a reference to their bus connection object, too. Thus, as long as a bus slot object remains referenced its bus object will remain allocated too. Optionally, bus slot objects may be placed in "floating" mode. When in floating mode the life cycle of the bus slot object is bound to the bus object, i.e. when the bus object is freed the bus slot object is automatically unreferenced too. The floating state of a slot object may be controlled explicitly with sd_bus_slot_set_floating(3), though usually floating bus slot objects are created by passing NULL as the slot parameter of sd_bus_add_match() and related calls, thus indicating that the caller is not directly interested in referencing and managing the bus slot object.

The life cycle of the default bus connection should be the responsibility of the code that creates/owns the thread the default bus connection object is associated with. Library code should neither call sd_bus_flush() nor sd_bus_close() on default bus objects unless it does so in its own private, self-allocated thread. Library code should not use the default bus object in other threads unless it is clear that the program using it will life cycle the bus connection object and flush and close it before exiting from the thread. In libraries where it is not clear that the calling program will life cycle the bus connection object, it is hence recommended to use sd_bus_open_system() instead of sd_bus_default_system() and related calls.

RETURN VALUE

On success, these calls return 0 or a positive integer. On failure, these calls return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

The specified parameters are invalid.

-ENOMEDIUM

The requested bus type is not available because of invalid environment (for example the user session bus is not available because $XDG_RUNTIME_DIR is not set).

-ENOMEM

Memory allocation failed.

-ESOCKTNOSUPPORT

The protocol version required to connect to the selected bus is not supported.

In addition, other connection-related errors may be returned. See sd_bus_send(3).

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
