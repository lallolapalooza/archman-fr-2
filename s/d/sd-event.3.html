NOM

sd-event - Une implémentation générique de boucle d'événements

SYNTAXE

#include <systemd/sd-event.h>

pkg-config --cflags --libs libsystemd

DESCRIPTION

sd-event.h fait partie de libsystemd(3) et fournit une implémentation générique de boucle d'événements, basée sur epoll(7) de Linux.

Voir sd_event_new(3), sd_event_run(3), sd_event_add_io(3), sd_event_add_time(3), sd_event_add_signal(3), sd_event_add_child(3), sd_event_add_inotify(3), sd_event_add_defer(3), sd_event_add_memory_pressure(3), sd_event_source_unref(3), sd_event_source_set_priority(3), sd_event_source_set_enabled(3), sd_event_source_set_userdata(3), sd_event_source_get_event(3), sd_event_source_get_pending(3), sd_event_source_set_description(3), sd_event_source_set_prepare(3), sd_event_source_set_ratelimit(3), sd_event_wait(3), sd_event_get_fd(3), sd_event_set_watchdog(3), sd_event_exit(3), sd_event_now(3) pour plus d'informations sur les fonctions disponibles.

La conception de la boucle d'événements est axée sur l'exécution d'une instance distincte de la boucle d'événements dans chaque thread ; elle n'a pas de concept de distribution d'événements à partir d'une seule instance de boucle d'événements vers plusieurs threads de travail. La distribution des événements est strictement ordonnée et soumise à des priorités configurables. Dans chaque itération de la boucle d'événements, une seule source d'événements est distribuée. Chaque fois qu'une source d'événements est distribuée, le noyau est interrogé pour de nouveaux événements, avant que la source d'événements suivante ne soit distribuée. La boucle d'événements est conçue pour respecter les priorités et assurer l'équité au sein de chaque priorité. Elle n'est pas conçue pour offrir un débit optimal, car cela contredit ces objectifs en raison des limitations des primitives epoll(7) sous-jacentes.

L'implémentation de la boucle d'événements fournit les caractéristiques suivantes :

1.Sources d'événements I/O, basées sur la surveillance des descripteurs de fichiers de epoll(7), y compris les événements déclenchés par front montant (EPOLLET). Voir sd_event_add_io(3).
2.Sources d'événements de temporisation, basées sur timerfd_create(2), prenant en charge les horloges CLOCK_MONOTONIC, CLOCK_REALTIME, CLOCK_BOOTTIME, ainsi que les horloges CLOCK_REALTIME_ALARM et CLOCK_BOOTTIME_ALARM qui peuvent réveiller le système de la veille. Lors de la création d'événements de temporisation, un paramètre de précision requis peut être spécifié, ce qui permet de regrouper les événements de temporisation pour minimiser la consommation d'énergie. Voir sd_event_add_time(3).
3.Événements de signaux de processus UNIX, basés sur signalfd(2), y compris une prise en charge complète des signaux temps réel et des paramètres mis en file d'attente. Voir sd_event_add_signal(3).
4.Événements de changement d'état des processus enfants, basés sur waitid(2). Voir sd_event_add_child(3).
5.Sources d'événements statiques, de trois types : defer, post et exit, pour invoquer des appels dans chaque boucle d'événements, après d'autres sources d'événements ou à la fin de la boucle d'événements. Voir sd_event_add_defer(3).
6.Les sources d'événements peuvent se voir attribuer une valeur de priorité de 64 bits, qui contrôle l'ordre dans lequel les sources d'événements sont distribuées si plusieurs sont en attente simultanément. Voir sd_event_source_set_priority(3).
7.La boucle d'événements peut envoyer automatiquement des messages de notification de watchdog au gestionnaire de services. Voir sd_event_set_watchdog(3).
8.La boucle d'événements peut être intégrée dans des boucles d'événements étrangères, telles que celle de GLib. Voir sd_event_get_fd(3) pour un exemple.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas sûr pour les threads multiples. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de ne faire des appels à setenv() qu'à partir d'une phase précoce du programme lorsque aucun autre thread n'a été démarré.
