DESCRIPTION

sd_pid_get_owner_uid() peut être utilisé pour déterminer l'UID Unix (identifiant utilisateur) qui possède la session de connexion ou l'unité utilisateur systemd d'un processus identifié par le PID spécifié. Pour les processus qui ne font pas partie d'une session de connexion et ne sont pas gérés par un gestionnaire utilisateur, cette fonction échouera avec -ENODATA.

sd_pid_get_session() peut être utilisé pour déterminer l'identifiant de session de connexion d'un processus identifié par l'identifiant de processus spécifié. L'identifiant de session est une chaîne courte, adaptée à une utilisation dans les chemins de système de fichiers. Veuillez noter que la session de connexion peut être limitée à un processus stub ou deux. Les processus utilisateur peuvent plutôt être démarrés à partir de leur gestionnaire utilisateur systemd, par exemple les applications GUI démarrées à l'aide de l'activation DBus, ainsi que les processus de service qui sont partagés entre plusieurs connexions du même utilisateur. Pour les processus qui ne font pas partie d'une session de connexion, cette fonction échouera avec -ENODATA. La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_user_unit() peut être utilisé pour déterminer l'identifiant d'unité utilisateur systemd (c'est-à-dire un service utilisateur ou une unité de portée) d'un processus identifié par le PID spécifié. Le nom d'unité est une chaîne courte, adaptée à une utilisation dans les chemins de système de fichiers. Pour les processus qui ne sont pas gérés par un gestionnaire utilisateur, cette fonction échouera avec -ENODATA. La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_unit() peut être utilisé pour déterminer l'identifiant d'unité système systemd (c'est-à-dire un service système ou une unité de portée) d'un processus identifié par le PID spécifié. Le nom d'unité est une chaîne courte, adaptée à une utilisation dans les chemins de système de fichiers. Notez que tous les processus ne font pas partie d'une unité/service système. Pour les processus qui ne font pas partie d'une unité système systemd, cette fonction échouera avec -ENODATA. (Plus précisément, cet appel ne fonctionnera pas pour les threads du noyau.) La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_machine_name() peut être utilisé pour déterminer le nom de la VM ou du conteneur dont un processus est membre. Le nom de la machine est une chaîne courte, adaptée à une utilisation dans les chemins de système de fichiers. La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation. Pour les processus ne faisant pas partie d'une VM ou d'un conteneur, cette fonction échoue avec -ENODATA.

sd_pid_get_slice() peut être utilisé pour déterminer l'unité de tranche dont le processus est membre. Voir systemd.slice(5) pour plus de détails sur les tranches. La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation.

De même, sd_pid_get_user_slice() renvoie la tranche utilisateur (telle que gérée par l'instance systemd de l'utilisateur) d'un processus.

sd_pid_get_cgroup() renvoie le chemin du groupe de contrôle du processus spécifié, relatif à la racine de la hiérarchie. Renvoie le chemin sans barre oblique finale, sauf pour les processus situés dans le groupe de contrôle racine, où "/" est retourné. Pour trouver le chemin réel du groupe de contrôle dans le système de fichiers, le chemin retourné doit être précédé de /sys/fs/cgroup/.

Si le paramètre pid de l'une de ces fonctions est passé à 0, l'opération est exécutée pour le processus appelant.

Les appels sd_pidfd_get_owner_uid(), sd_pidfd_get_session(), sd_pidfd_get_user_unit(), sd_pidfd_get_unit(), sd_pidfd_get_machine_name(), sd_pidfd_get_slice(), sd_pidfd_get_user_slice() et sd_pidfd_get_cgroup() fonctionnent de manière similaire à leurs homologues PID, mais acceptent un PIDFD au lieu d'un PID, ce qui signifie qu'ils ne sont pas sujets aux conditions de concurrence de recyclage car le processus est épinglé par le descripteur de fichier pendant toute la durée de l'invocation. Notez que cela nécessite un noyau qui prend en charge PIDFD. Un descripteur de fichier approprié peut être obtenu via pidfd_open(2).

Les appels sd_peer_get_owner_uid(), sd_peer_get_session(), sd_peer_get_user_unit(), sd_peer_get_unit(), sd_peer_get_machine_name(), sd_peer_get_slice(), sd_peer_get_user_slice() et sd_peer_get_cgroup() fonctionnent de manière similaire à leurs homologues PID, mais acceptent un socket AF_UNIX connecté et récupèrent des informations sur le processus pair connecté. Notez que ces champs sont récupérés via /proc/, et ne sont donc pas adaptés à des fins d'autorisation, car ils sont sujets à des conditions de concurrence.

VALEUR RENVOYÉE

En cas de succès, ces appels renvoient 0 ou un entier positif. En cas d'échec, ces appels renvoient un code d'erreur négatif de style errno.

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-ESRCH

Le PID spécifié ne correspond pas à un processus en cours d'exécution.

-EBADF

Le descripteur de fichier spécifié est invalide.

-ENODATA

Le champ spécifié n'est pas défini pour le processus ou le pair décrit.

-EINVAL

DESCRIPTION

La fonction sd_pid_get_slice() renvoie le nom du groupe de contrôle systemd auquel appartient le processus avec l'ID pid. La fonction sd_pid_get_unit() renvoie le nom de l'unité systemd à laquelle appartient le processus avec l'ID pid. Les fonctions sd_pid_get_user_slice() et sd_pid_get_user_unit() renvoient respectivement le nom du groupe de contrôle et le nom de l'unité pour le processus avec l'ID pid dans son contexte utilisateur.

Si elles réussissent, ces fonctions allouent une chaîne de caractères pour le nom renvoyé et la stockent dans le pointeur ret. Le dernier nom de groupe de contrôle ou d'unité renvoyé par l'API (voir sd_session_get_state(3)) est alors disponible en utilisant les fonctions sd_peer_*.

Les fonctions sd_peer_*() renvoient des informations sur le processus connecté via un socket de domaine UNIX spécifié par path. Le socket doit être lié à un système journalisé et doit être utilisé pour communiquer avec le démon systemd. Les fonctions sd_peer_*() renvoient des informations sur le processus qui est le pair de ce socket. sd_peer_get_cgroup() renvoie le nom du groupe de contrôle du processus pair. sd_peer_get_unit() renvoie le nom de l'unité du processus pair. sd_peer_get_session() renvoie l'identifiant de la session du processus pair. sd_peer_get_owner_uid() renvoie l'UID du propriétaire du processus pair. sd_peer_get_machine_name() renvoie le nom de la machine du processus pair. sd_peer_get_user_slice() et sd_peer_get_user_unit() renvoient le nom du groupe de contrôle utilisateur et le nom de l'unité utilisateur du processus pair.

Les fonctions sd_pidfd_*() fonctionnent de la même manière que leurs homologues sd_pid_*(), mais elles prennent un descripteur de fichier pointant vers un processus (obtenu via pidfd_open(2)) au lieu d'un PID. Cela garantit que le processus spécifié est toujours valide et évite les problèmes de concurrence liés à la durée de vie des processus.

Les fonctions qui renvoient des chaînes de caractères allouent de la mémoire pour la chaîne renvoyée et la stockent dans le pointeur ret. Le mécanisme d'allocation de mémoire est le même que celui utilisé par malloc(3). Le nom de groupe de contrôle ou d'unité renvoyé est un nom absolu, comme on peut le trouver dans le système de fichiers cgroup, par exemple `/user.slice/user-1000.slice/session-a1b2c3d4.scope`.

Les chaînes renvoyées par ces fonctions doivent être libérées par l'appelant en utilisant free(3).

L'identifiant de session renvoyé par sd_pid_get_session() et les fonctions similaires n'est pas un ID de session de processus classique (tel que renvoyé par getsid(2)), mais un identifiant de session d'ouverture de session systemd.

RETURN VALUE

Les fonctions sd_pid_*(), sd_peer_*() et sd_pidfd_*() renvoient 0 en cas de succès, ou un code d'erreur négatif en cas d'échec. Les codes d'erreur possibles sont :

-EINVAL Une entrée invalide a été fournie. Cela se produit si pid ou pidfd n'est pas valide, ou si path n'est pas un chemin de socket de domaine UNIX valide.

-ENOMEM Allocation de mémoire échouée.

-EPERM Le processus appelant n'a pas les permissions nécessaires pour accéder aux informations du processus cible.

-ESRCH Le processus spécifié par pid ou pidfd n'existe pas.

NOTES

Les fonctions décrites ici sont disponibles en tant que bibliothèque partagée, qui peut être compilée et liée avec le fichier pkg-config(1) libsystemd.

Notez que l'identifiant de session de connexion tel que renvoyé par sd_pid_get_session() n'est absolument pas lié à l'identifiant de session du processus tel que renvoyé par getsid(2).
