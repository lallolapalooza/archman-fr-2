NOM

sd-login - APIs pour le suivi des connexions

SYNTAXE

#include <systemd/sd-login.h>

pkg-config --cflags --libs libsystemd

DESCRIPTION

sd-login.h fait partie de libsystemd(3) et fournit des API pour inspecter et surveiller les informations relatives aux sièges (seats), aux sessions de connexion (logins) et à l'état des utilisateurs sur le système local.

Notez que ces API permettent uniquement un accès et une surveillance purement passifs des sièges, sessions et utilisateurs. Pour modifier activement la configuration d'un siège, terminer des sessions de connexion ou basculer une session sur un siège, vous devez utiliser l'API D-Bus de systemd-logind à la place.

Ces fonctions accèdent de manière synchrone aux données dans /proc/, /sys/fs/cgroup/ et /run/. Ce sont tous des systèmes de fichiers virtuels, par conséquent le coût d'exécution de ces accès est relativement faible.

Il est possible (et souvent un très bon choix) de mélanger les appels à l'interface synchrone de sd-login.h avec l'interface D-Bus asynchrone de systemd-logind. Cependant, si cela est fait, vous devez réfléchir un peu aux possibles conditions de concurrence (races) étant donné que le flux d'événements de D-Bus et des interfaces de sd-login.h comme le moniteur de connexion sont asynchrones et non ordonnés les uns par rapport aux autres.

Si les fonctions retournent des tableaux de chaînes, ils sont généralement terminés par NULL et doivent être libérés par l'appelant avec l'appel free(3) de la libc après utilisation, y compris les chaînes référencées. De même, les chaînes individuelles retournées doivent également être libérées.

À titre d'exception spéciale, au lieu d'un tableau de chaînes vide, NULL peut être retourné, ce qui doit être traité comme équivalent à un tableau de chaînes vide.

Voir sd_pid_get_session(3), sd_uid_get_state(3), sd_session_is_active(3), sd_seat_get_active(3), sd_get_seats(3), sd_login_monitor_new(3) pour plus d'informations sur les fonctions implémentées.

DÉFINITION DES TERMES

siège (seat)

Un siège comprend tous les périphériques matériels assignés à un lieu de travail spécifique. Il comprend au moins un périphérique graphique, et inclut généralement aussi un clavier, une souris. Il peut également inclure des caméras vidéo, des cartes son, etc. Les sièges sont identifiés par des noms de siège, qui sont des chaînes (<= 255 caractères), commençant par les quatre caractères "seat" suivis d'au moins un caractère de la plage [a-zA-Z0-9], "_" et "-". Ils conviennent pour être utilisés comme noms de fichiers. Les noms de siège peuvent ou non être stables et peuvent être réutilisés si un siège redevient disponible.

Ajouté dans la version 235.

session

Une session est définie par la période pendant laquelle un utilisateur est connecté jusqu'à ce qu'il se déconnecte. Une session est liée à un ou aucun siège (ce dernier cas pour les connexions ssh 'virtuelles'). Plusieurs sessions peuvent être attachées au même siège, mais une seule d'entre elles peut être active, les autres étant en arrière-plan. Une session est identifiée par une courte chaîne.

systemd(1) garantit que les sessions d'audit sont identiques aux sessions systemd, et utilise l'identifiant de session d'audit comme identifiant de session dans systemd (si l'audit est activé). En général, l'identifiant de session est une courte chaîne composée uniquement de [a-zA-Z0-9], "_" et "-", adaptée à une utilisation comme nom de fichier. Les identifiants de session sont uniques sur la machine locale et ne sont jamais réutilisés tant que la machine est en ligne. Un utilisateur (tel que nous le connaissons sur UNIX) correspond à la personne utilisant un ordinateur. Un seul utilisateur peut avoir plusieurs sessions ouvertes en même temps. Un utilisateur est identifié par un identifiant numérique d'utilisateur (UID) ou un nom d'utilisateur (une chaîne). Un système multi-session permet plusieurs sessions utilisateur sur le même siège en même temps. Un système multi-sièges permet plusieurs sièges indépendants qui peuvent être utilisés individuellement et simultanément par différents utilisateurs.

Ajouté dans la version 235.

Tous les périphériques matériels éligibles pour être assignés à un siège lui sont assignés. Un périphérique ne peut être assigné qu'à un seul siège à la fois. Si un périphérique n'est assigné à aucun autre siège particulier, il est implicitement assigné au siège par défaut spécial appelé "seat0".

Notez que le matériel tel que les imprimantes, les disques durs ou les cartes réseau n'est généralement pas assigné à un siège spécifique. Ils sont disponibles pour tous les sièges de manière égale. (Avec une exception : les clés USB peuvent être assignées à un siège.)

"seat0" existe toujours.

RÈGLES UDEV

L'assignation des périphériques matériels aux sièges est gérée dans la base de données udev, via des paramètres sur les périphériques :

Tag "seat"

Lorsqu'il est défini, un périphérique est éligible pour être assigné à un siège. Ce tag est défini pour les périphériques graphiques, les souris, les claviers, les cartes vidéo, les cartes son, etc. Notez que certains périphériques comme les cartes son sont composés de plusieurs sous-périphériques (par exemple, un PCM pour l'entrée et un autre pour la sortie). Ce tag sera défini uniquement pour le périphérique d'origine, pas pour les sous-périphériques individuels. Une interface utilisateur pour configurer l'assignation des périphériques aux sièges devrait énumérer et s'abonner à tous les périphériques avec ce tag défini et les afficher dans l'interface. Notez que les hubs USB peuvent également être assignés à un siège, auquel cas tous les périphériques (actuels et futurs) qui y sont branchés seront également assignés au même siège (sauf s'ils sont explicitement assignés à un autre siège).

Ajouté dans la version 235.

Tag "master-of-seat"

Lorsqu'il est défini, ce périphérique est suffisant pour qu'un siège soit considéré comme existant. Ce tag est généralement défini pour le périphérique de framebuffer des cartes graphiques. Un siège est donc composé d'un nombre arbitraire de périphériques marqués avec le tag "seat", mais (au moins) l'un de ces périphériques doit être marqué avec "master-of-seat" avant que le siège ne soit réellement considéré comme présent.

Ajouté dans la version 235.

Propriété ID_SEAT

Cette propriété spécifie le nom du siège auquel un périphérique spécifique est assigné. Si elle n'est pas définie, le périphérique est assigné à "seat0". De plus, pour accélérer l'énumération du matériel appartenant à un siège spécifique, le siège est également défini comme tag sur le périphérique. C'est-à-dire, si la propriété ID_SEAT=seat-waldo est définie pour un périphérique, le tag "seat-waldo" sera également défini. Notez que si un périphérique est assigné à "seat0", il ne portera généralement pas un tel tag et vous devrez énumérer tous les périphériques et vérifier manuellement la propriété ID_SEAT. Encore une fois, si un périphérique est assigné à seat0, cela est visible sur le périphérique de deux manières : avec la propriété ID_SEAT=seat0 et sans aucune propriété ID_SEAT définie pour lui.

Ajouté dans la version 235.

Propriété ID_AUTOSEAT

Lorsqu'elle est définie sur "1", ce périphérique génère automatiquement un siège nouveau et indépendant, nommé d'après le chemin du périphérique. Ceci est défini pour des hubs USB spécialisés comme les périphériques Pluggable, qui lorsqu'ils sont branchés devraient créer un siège hotplug sans configuration supplémentaire.

Ajouté dans la version 235.

Propriété ID_FOR_SEAT

Lors de la création de sièges supplémentaires (manuels) à partir d'un périphérique graphique, c'est un bon choix pour nommer le siège. Il est créé à partir du chemin du périphérique. Ceci est utile dans les interfaces utilisateur pour configurer les sièges : dès que vous créez un nouveau siège à partir d'un périphérique graphique, lisez cette propriété et préfixez-la avec "seat-" et utilisez-la comme nom pour le siège.

Ajouté dans la version 235.

Un siège n'existe que et exclusivement parce qu'un périphérique correctement tagué avec la bonne propriété ID_SEAT existe. En dehors des règles udev, il n'y a pas de données persistantes sur les sièges stockées sur disque.

Notez que systemd-logind(8) gère les ACL sur un certain nombre de classes de périphériques, pour permettre au code utilisateur d'accéder aux nœuds de périphériques attachés à un siège tant que l'utilisateur a une session active dessus. Ceci est largement transparent pour les applications. Comme mentionné ci-dessus, pour certains logiciels utilisateur, il pourrait être judicieux de surveiller s'ils peuvent accéder aux nœuds de périphériques au lieu de penser aux sièges.
