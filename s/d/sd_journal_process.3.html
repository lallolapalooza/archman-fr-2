NOM

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interface de notification de changement du journal

SYNTAXE

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

sd_journal_get_fd() renvoie un descripteur de fichier qui peut être interrogé de manière asynchrone dans une boucle d'événements externe et qui est signalé dès que le journal change, car de nouvelles entrées ou de nouveaux fichiers ont été ajoutés, une rotation a eu lieu, ou des fichiers ont été supprimés, etc. Le descripteur de fichier est adapté à une utilisation dans poll(2). Utilisez sd_journal_get_events() pour un masque d'événements à surveiller. L'appel prend un argument : l'objet de contexte du journal. Notez que tous les systèmes de fichiers ne sont pas capables de générer les événements nécessaires pour les réveils à partir de ce descripteur de fichier pour que les changements soient remarqués immédiatement. En particulier, les systèmes de fichiers réseau ne génèrent pas d'événements de changement de fichier appropriés dans tous les cas. Des cas comme celui-ci peuvent être détectés avec sd_journal_reliable_fd(), ci-dessous. sd_journal_get_timeout() garantira dans ces cas que les réveils se produisent suffisamment fréquemment pour que les changements soient remarqués, bien qu'avec une certaine latence.

sd_journal_get_events() renverra le masque poll() à surveiller. Cette fonction renverra une combinaison de POLLIN et POLLOUT et similaires pour être remplie dans le champ ".events" de struct pollfd.

sd_journal_get_timeout() renverra une valeur de délai d'attente pour une utilisation dans poll(). Ceci renvoie une valeur en microsecondes depuis l'époque de CLOCK_MONOTONIC pour expirer poll() dans timeout_usec. Voir clock_gettime(2) pour les détails sur CLOCK_MONOTONIC. S'il n'y a pas de délai d'attente à attendre, celle-ci remplira (uint64_t) -1 à la place. Notez que poll() prend un délai d'attente relatif en millisecondes plutôt qu'un délai d'attente absolu en microsecondes. Pour convertir le délai d'attente absolu en 'us' en délai d'attente relatif en 'ms', utilisez un code comme suit :

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

Le code ci-dessus ne fait aucun contrôle d'erreur par souci de brièveté. Le msec calculé peut être passé directement comme paramètre de délai d'attente de poll().

Après chaque réveil poll(), sd_journal_process() doit être appelé pour traiter les événements. Cet appel indiquera également quel type de changement a été détecté (voir ci-dessous ; notez que des réveils intempestifs sont possibles).

Une alternative synchrone à l'utilisation de sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() et sd_journal_process() est sd_journal_wait(). Il attendra synchrone jusqu'à ce que le journal soit modifié. Le temps maximum pendant lequel cet appel dort peut être contrôlé avec le paramètre timeout_usec. Passez (uint64_t) -1 pour attendre indéfiniment. En interne, cet appel combine simplement sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() et sd_journal_process() en un seul.

sd_journal_reliable_fd() peut être utilisé pour vérifier si les événements de réveil du descripteur de fichier renvoyé par sd_journal_get_fd() sont connus pour être déclenchés rapidement. Sur certains systèmes de fichiers où les événements de changement de fichier du système d'exploitation ne sont pas disponibles (comme NFS), les changements doivent être interrogés répétitivement, et donc ne sont détectés qu'avec une latence considérable. Cet appel renverra une valeur positive si les changements du journal sont détectés rapidement et zéro lorsqu'ils doivent être interrogés. Notez qu'il n'est généralement pas nécessaire d'appeler cette fonction directement car sd_journal_get_timeout() demandera des délais d'attente appropriés de toute façon.

Notez que toutes les interfaces de notification de changement ci-dessus ne signalent pas les changements instantanément. Des latences sont introduites pour plusieurs raisons : comme mentionné, certains backends de stockage nécessitent un sondage basé sur le temps, dans d'autres cas, les réveils sont optimisés en fusionnant les événements, et le système d'exploitation introduit des latences supplémentaires de planification d'E/S/CPU.

VALEUR RETOUR

sd_journal_get_fd() renvoie un descripteur de fichier valide en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_get_events() renvoie une combinaison de POLLIN, POLLOUT et similaires en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_reliable_fd() renvoie un entier positif si le descripteur de fichier renvoyé par sd_journal_get_fd() déclenchera des réveils immédiats pour tous les changements du journal. Renvoie 0 s'il peut y avoir une latence.

sd_journal_process() et sd_journal_wait() renvoient un code d'erreur négatif de style errno, ou l'un de SD_JOURNAL_NOP, SD_JOURNAL_APPEND ou SD_JOURNAL_INVALIDATE en cas de succès :

•Si SD_JOURNAL_NOP est renvoyé, le journal n'a pas changé depuis la dernière invocation.
•Si SD_JOURNAL_APPEND est renvoyé, de nouvelles entrées ont été ajoutées à la fin du journal. Dans ce cas, il suffit de continuer à lire à l'ancienne position de fin du journal, pour lire les entrées nouvellement ajoutées.
•Si SD_JOURNAL_INVALIDATE, des fichiers du journal ont été ajoutés ou supprimés de l'ensemble des fichiers du journal surveillés (par exemple, en raison de rotation ou de nettoyage), et donc des entrées ont pu apparaître ou disparaître à des endroits arbitraires dans le flux de journaux, potentiellement avant ou après l'ancienne fin du flux de journaux. Si SD_JOURNAL_INVALIDATE est renvoyé, les interfaces utilisateur en vue en direct qui souhaitent refléter à l'écran l'état précis des données du journal sur le disque devraient probablement rafraîchir leur affichage complet (par rapport au curseur de l'entrée de journal en haut de l'écran). Les programmes qui ne s'intéressent qu'à un flux de données de journal strictement séquentiel peuvent traiter SD_JOURNAL_INVALIDATE de la même manière que SD_JOURNAL_APPEND, ignorant ainsi toute modification de la vue du journal antérieure à l'ancienne fin du flux de journaux.

SÉCURITÉ DES SIGNALS

En général, sd_journal_get_fd(), sd_journal_get_events(), et sd_journal_get_timeout() ne sont *pas* "async signal safe" au sens de signal-safety(7). Néanmoins, seul le premier appel à l'une de ces trois fonctions effectue des opérations non sûres, donc les appels ultérieurs *sont* sûrs.

sd_journal_process() et sd_journal_wait() ne sont pas sûrs. sd_journal_reliable_fd() est sûr.

NOTES

Toutes les fonctions listées ici sont indépendantes des threads et un seul thread peut opérer sur un objet donné à la fois. Différents threads peuvent accéder au même objet à des moments différents. Plusieurs objets indépendants peuvent être utilisés à partir de différents threads en parallèle.

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

sd_journal_process(3) — systemd — Arch Linux

NAME

sd_journal_process, sd_journal_wait, sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_reliable_fd - traiter les entrées du journal système

SYNOPSIS

#include <systemd/sd-journal.h>
int sd_journal_process(sd_journal *j);
int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);
int sd_journal_get_fd(sd_journal *j);
int sd_journal_get_events(sd_journal *j);
int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);
int sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

La fonction sd_journal_process() doit être appelée chaque fois que le descripteur de fichier retourné par sd_journal_get_fd() devient signalable (par exemple, après avoir reçu une notification de poll() ou epoll()). Cela permet de signaler au journal les nouveaux événements qui se sont produits, y compris les nouveaux messages, les modifications de fichiers ou les événements de rotation. Elle doit être appelée périodiquement, même si aucun événement n'a été reçu, pour garantir que les modifications de fichiers soient traitées.

La fonction sd_journal_wait() bloque jusqu'à ce qu'un événement du journal se produise ou que le délai d'attente expire. Le paramètre timeout_usec spécifie le délai d'attente en microsecondes. S'il est défini sur (uint64_t) -1, la fonction attendra indéfiniment. Après le retour de sd_journal_wait(), il est nécessaire d'appeler sd_journal_process() pour traiter les événements reçus.

La fonction sd_journal_get_fd() retourne le descripteur de fichier qui peut être utilisé pour la surveillance des événements du journal via des appels système tels que poll(), epoll(), etc. Il est conseillé d'utiliser sd_journal_get_events() et sd_journal_get_timeout() pour déterminer les événements à surveiller et le délai d'attente maximal.

La fonction sd_journal_get_events() retourne les bits d'événements qui doivent être surveillés sur le descripteur de fichier retourné par sd_journal_get_fd(). Ces événements sont utilisés par les appels système de surveillance d'E/S comme poll().

La fonction sd_journal_get_timeout() récupère le délai d'attente maximal en microsecondes, après quoi sd_journal_process() devrait être appelé même s'il n'y a pas d'événements de fichier signalés sur le descripteur de fichier retourné par sd_journal_get_fd(). Si le délai d'attente est infini, il est retourné comme (uint64_t) -1. Ceci est utile pour les applications qui souhaitent éviter de bloquer indéfiniment dans poll() ou epoll().

La fonction sd_journal_reliable_fd() est similaire à sd_journal_get_fd(), mais elle retourne un descripteur de fichier qui garantit de ne pas échouer même si des événements de rotation de fichier se produisent.

VALEUR DE RETOUR

sd_journal_process(), sd_journal_wait(), sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() et sd_journal_reliable_fd() retournent un code d'erreur négatif en cas d'échec, ou un code d'erreur non négatif en cas de succès. Le code d'erreur non négatif retourné par sd_journal_process() et sd_journal_wait() est le nombre d'événements qui ont été traités. Si zéro est retourné, aucun événement n'a été traité.

SÉCURITÉ DES SIGNAUX

sd_journal_process() est sûr pour une utilisation dans les gestionnaires de signaux, à condition que sd_journal_get_fd(), sd_journal_get_events() et sd_journal_get_timeout() aient été appelés en dehors du gestionnaire de signaux.

NOTES

L'utilisation de sd_journal_wait() est généralement plus simple que l'utilisation de poll() car elle gère la logique de délai d'attente et d'appel de sd_journal_process() en interne.

Si vous utilisez poll() ou epoll() pour surveiller les événements du journal, vous devez appeler sd_journal_process() chaque fois que le descripteur de fichier retourné par sd_journal_get_fd() devient signalable. Il est également conseillé d'appeler sd_journal_process() périodiquement en utilisant le délai d'attente retourné par sd_journal_get_timeout() pour vous assurer que les modifications de fichiers sont traitées.

Les événements retournés par sd_journal_get_events() sont une combinaison des drapeaux suivants : POLLIN, POLLPRI, POLLERR, POLLHUP.

sd_journal_reliable_fd() est utile dans les cas où une perte d'événements ne peut pas être tolérée, par exemple, lors de la gestion de la rotation des fichiers de journal.

EXEMPLES

Traitement des événements du journal avec sd_journal_wait() :

/* SPDX-License-Identifier: MIT-0 */
#include <stdio.h>
#include <string.h>
#include <systemd/sd-journal.h>
int main(int argc, char *argv[]) {
  sd_journal *j = NULL;
  int r;
  r = sd_journal_open(&j, SD_JOURNAL_LOCAL_ONLY);
  if (r < 0) {
    fprintf(stderr, "Failed to open journal: %s\n", strerror(-r));
    return 1;
  }
  for (;;) {
    /* Attendre de nouvelles entrées ou des événements */
    r = sd_journal_wait(j, (uint64_t) -1);
    if (r < 0) {
      fprintf(stderr, "Failed to wait for journal entry: %s\n", strerror(-r));
      break;
    }
    /* Traiter toutes les nouvelles entrées */
    while ((r = sd_journal_next(j)) > 0) {
      const char *d;
      size_t l;
      /* Lire le champ MESSAGE */
      r = sd_journal_get_data(j, "MESSAGE", &d, &l);
      if (r < 0) {
        fprintf(stderr, "Failed to read message field: %s\n", strerror(-r));
        continue;
      }
      printf("%.*s\n", (int) l, d);
    }
    if (r < 0) {
      fprintf(stderr, "Failed to process journal entry: %s\n", strerror(-r));
      break;
    }
  }
  sd_journal_close(j);
  return 0;
}

Attente avec poll() (cet exemple manque de toute vérification d'erreur par souci de simplicité) :

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int wait_for_changes(sd_journal *j) {
  uint64_t t;
  int msec;
  struct pollfd pollfd;
  sd_journal_get_timeout(j, &t);
  if (t == (uint64_t) -1)
    msec = -1;
  else {
    struct timespec ts;
    uint64_t n;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
    msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
  }
  pollfd.fd = sd_journal_get_fd(j);
  pollfd.events = sd_journal_get_events(j);
  poll(&pollfd, 1, msec);
  return sd_journal_process(j);
}
