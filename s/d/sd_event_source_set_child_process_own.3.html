DESCRIPTION

sd_event_add_child() ajoute une nouvelle source d'événement de changement d'état de processus enfant à une boucle d'événements. L'objet boucle d'événements est spécifié dans le paramètre event, l'objet source d'événement est renvoyé dans le paramètre source. Le paramètre pid spécifie le PID du processus à surveiller, qui doit être un enfant direct du processus appelant. Le paramètre options détermine quels changements d'état seront surveillés. Il doit contenir un masque OU de WEXITED (surveiller la terminaison du processus enfant), WSTOPPED (surveiller l'arrêt du processus enfant par un signal) et WCONTINUED (surveiller la reprise du processus enfant par un signal). Voir waitid(2) pour plus d'informations.

Le handler doit être une fonction à appeler lorsque le processus change d'état, ou NULL. La fonction de gestionnaire recevra le pointeur userdata, qui peut être choisi librement par l'appelant. Le gestionnaire reçoit également un pointeur vers une structure siginfo_t contenant des informations sur l'événement du processus enfant. Le gestionnaire peut renvoyer une valeur négative pour signaler une erreur (voir ci-dessous), d'autres valeurs de retour sont ignorées. Si handler est NULL, un gestionnaire par défaut qui appelle sd_event_exit(3) sera utilisé.

Un seul gestionnaire peut être installé pour un processus enfant spécifique. Le gestionnaire est activé pour un seul événement (SD_EVENT_ONESHOT), mais cela peut être modifié avec sd_event_source_set_enabled(3). Si la fonction de gestionnaire renvoie un code d'erreur négatif, elle sera soit désactivée après l'invocation, même si le mode SD_EVENT_ON était demandé auparavant, soit elle provoquera la terminaison de la boucle, voir sd_event_source_set_exit_on_failure(3).

Pour détruire un objet source d'événement, utilisez sd_event_source_unref(3), mais notez que la source d'événement n'est retirée de la boucle d'événements que lorsque toutes les références à la source d'événement sont abandonnées. Pour s'assurer qu'une source d'événement ne se déclenche plus, même lorsqu'une référence y est toujours conservée, envisagez de définir la source d'événement sur SD_EVENT_OFF avec sd_event_source_set_enabled(3).

Le signal SIGCHLD doit être bloqué dans tous les threads avant d'appeler cette fonction (en utilisant sigprocmask(2) ou pthread_sigmask(3)).

Si le deuxième paramètre de sd_event_add_child() est passé comme NULL, aucune référence à l'objet source d'événement n'est renvoyée. Dans ce cas, la source d'événement est considérée comme "flottante" et sera détruite implicitement lorsque la boucle d'événements elle-même sera détruite.

Notez que la fonction handler est appelée à un moment où le processus enfant n'a pas encore été récupéré (et est donc toujours exposé comme un processus zombie par le noyau). Cependant, l'enfant sera récupéré automatiquement après le retour de la fonction. Les processus enfants pour lesquels aucune source d'événement de changement d'état de processus enfant n'est installée ne seront pas récupérés par l'implémentation de la boucle d'événements.

Si le paramètre handler de sd_event_add_child() est NULL, et que la source d'événement se déclenche, cela sera considéré comme une demande de sortie de la boucle d'événements. Dans ce cas, le paramètre userdata, converti en entier, est passé comme paramètre de code de sortie à sd_event_exit(3).

Si à la fois une source d'événement de changement d'état de processus enfant et une source d'événement de signal SIGCHLD sont installées dans la même boucle d'événements, les priorités configurées des sources d'événements décident quelle source d'événement est traitée en premier. Si le gestionnaire de signaux est traité en premier, il devrait laisser les processus enfants pour lesquels des sources d'événements de changement d'état de processus enfant sont installés non récupérés.

sd_event_add_child_pidfd() est similaire à sd_event_add_child() mais prend un descripteur de fichier référençant le processus ("pidfd") au lieu du PID numérique. Un descripteur de fichier approprié peut être obtenu via pidfd_open(2) et les appels associés. Le descripteur de fichier passé n'est pas fermé lorsque la source d'événement est libérée à nouveau, sauf si sd_event_source_set_child_pidfd_own() est utilisé pour activer ce comportement. Notez que quel que soit l'appel utilisé, sd_event_add_child() ou sd_event_add_child_pidfd(), pour allouer une source d'événement, le processus surveillé doit être un enfant direct du processus appelant. Dans les deux cas, SIGCHLD doit être bloqué dans le processus appelant.

sd_event_source_get_child_pid() récupère le PID configuré d'une source d'événement de changement d'état de processus enfant créée précédemment avec sd_event_add_child(). Elle prend l'objet source d'événement comme paramètre source et un pointeur vers une variable pid_t pour y renvoyer l'ID du processus.

sd_event_source_get_child_pidfd() récupère le descripteur de fichier référençant le processus surveillé ("pidfd"). La boucle d'événements utilise en interne des pidfd pour surveiller les processus enfants, que les sources d'événements individuelles soient allouées via sd_event_add_child() ou sd_event_add_child_pidfd(). Si ce dernier appel a été utilisé pour allouer la source d'événement, cette fonction renvoie le descripteur de fichier d'origine utilisé pour l'allocation. Cet appel prend l'objet source d'événement comme paramètre source et renvoie le descripteur de fichier numérique.

sd_event_source_get_child_pidfd_own() peut être utilisé pour interroger si le pidfd que la source d'événement encapsule doit être fermé lorsque la source d'événement est libérée. Cette fonction renvoie zéro si le pidfd doit être laissé ouvert, et une valeur positive s'il doit être fermé automatiquement. Par défaut, ce paramètre vaut un si la source d'événement a été allouée via sd_event_add_child() et zéro si elle a été allouée via sd_event_add_child_pidfd(). La fonction sd_event_source_set_child_pidfd_own() peut être utilisée pour changer ce paramètre et prend un paramètre booléen avec le nouveau réglage.

sd_event_source_get_child_process_own() peut être utilisé pour interroger si le processus surveillé par la source d'événement doit être tué (avec SIGKILL) et récupéré lorsque la source d'événement est libérée. Cette fonction renvoie zéro si le processus doit être laissé en cours d'exécution, et une valeur positive s'il doit être tué et récupéré automatiquement. Par défaut, ce paramètre vaut zéro. DESCRIPTION

These functions set up event sources that watch for the termination or stop/continue of a child process. They are useful for managing child processes and reacting to their state changes.

sd_event_add_child() sets up an event source that watches the child process specified by pid. When the child process terminates or stops/continues, the event loop will be woken up, and the specified handler function will be called.

e is the event loop to attach the source to. source is a pointer to a location where the event source object will be stored. pid is the process ID of the child to watch. sig is a bitmask of flags passed to waitid(2), typically a combination of WEXITED, WSTOPPED, and WCONTINUED. handler is the callback function to invoke on state changes. userdata is arbitrary user data to pass to the handler.

sd_event_add_child_pidfd() is similar to sd_event_add_child(), but it takes a file descriptor pidfd obtained via pidfd_open(2) instead of a process ID. This is generally preferred over using process IDs, as it is more robust against PID reuse.

The callback function sd_event_child_handler_t is invoked with the event source s, the process ID pid of the child that changed state, the status word wstatus as returned by waitid(2), and the userdata pointer.

The handler should return a negative error number on failure, or a positive value or zero to indicate success. If the handler returns a positive value, the event loop will be terminated, and this value will be used as the exit code of the event loop.

sd_event_source_get_child_pid() retrieves the process ID associated with the child event source source.

sd_event_source_get_child_pidfd() retrieves the pidfd associated with the child event source source.

sd_event_source_get_child_pidfd_own() and sd_event_source_set_child_pidfd_own() control whether the event source owns the pidfd. If it owns the pidfd, it will close it when the event source is destroyed. The default is false.

sd_event_source_get_child_process_own() and sd_event_source_set_child_process_own() control whether the event source owns the child process. If it owns the child process, it will wait for it to terminate when the event source is destroyed, and potentially reap it. This is the default behavior and necessary to prevent zombie processes. Setting this to false might be useful if the caller intends to wait for the child itself or if the child is managed by another mechanism. Note that if the calling process is terminated abnormally, the watched child process might survive even though the event source ceases to exist. This behavior might change eventually.

sd_event_source_send_child_signal() may be used to send a UNIX signal to the watched process via pidfd_send_signal(2). The specified parameters match those of the underlying system call, except that the info is never modified (and is thus declared constant). Like for the underlying system call, the flags parameter currently must be zero.

RETURN VALUE

On success, these functions return 0 or a positive integer. On failure, they return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-ENOMEM

Not enough memory to allocate an object.

-EINVAL

An invalid argument has been passed. This includes specifying an empty mask in options or a mask which contains values different than a combination of WEXITED, WSTOPPED, and WCONTINUED.

-EBUSY

A handler is already installed for this child process, or SIGCHLD is not blocked.

-ESTALE

The event loop is already terminated.

-ECHILD

The event loop has been created in a different process, library or module instance.

-EDOM

The passed event source is not a child process event source.

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.

EXAMPLE

Example 1. Exit loop when the child terminates

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <assert.h>
#include <stdio.h>
#include <unistd.h>
#include <systemd/sd-event.h>
int main(int argc, char **argv) {
  pid_t pid = fork();
  assert(pid >= 0);
  /* SIGCHLD signal must be blocked for sd_event_add_child to work */
  sigset_t ss;
  sigemptyset(&ss);
  sigaddset(&ss, SIGCHLD);
  sigprocmask(SIG_BLOCK, &ss, NULL);
  if (pid == 0)  /* child */
    sleep(1);
  else {         /* parent */
    sd_event *e = NULL;
    int r;
    /* Create the default event loop */
    sd_event_default(&e);
    assert(e);
    /* We create a floating child event source (attached to 'e').
     * The default handler will be called with 666 as userdata, which
     * will become the exit value of the loop. */
    r = sd_event_add_child(e, NULL, pid, WEXITED, NULL, (void*) 666);
    assert(r >= 0);
    r = sd_event_loop(e);
    assert(r == 666);
    sd_event_unref(e);
  }
  return 0;
}
