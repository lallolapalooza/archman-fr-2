DESCRIPTION

sd_bus_add_object_vtable() est utilisé pour déclarer les attributs du chemin d'objet path connecté à la connexion de bus bus sous l'interface interface. La table vtable peut contenir des déclarations de propriétés utilisant SD_BUS_PROPERTY() ou SD_BUS_WRITABLE_PROPERTY(), des déclarations de méthodes utilisant SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), ou SD_BUS_METHOD_WITH_NAMES_OFFSET(), et des déclarations de signaux utilisant SD_BUS_SIGNAL_WITH_NAMES() ou SD_BUS_SIGNAL(), voir ci-dessous. Le paramètre userdata contient un pointeur qui sera passé à diverses fonctions de rappel. Il peut être spécifié comme NULL si aucune valeur n'est nécessaire. Une interface peut avoir n'importe quel nombre de tables virtuelles qui lui sont attachées.

sd_bus_add_fallback_vtable() est similaire à sd_bus_add_object_vtable(), mais est utilisé pour enregistrer des attributs "de secours". Lors de la recherche d'une déclaration d'attribut, les chemins d'objets de bus enregistrés avec sd_bus_add_object_vtable() sont vérifiés en premier. Si aucune correspondance n'est trouvée, les tables virtuelles de secours sont vérifiées pour chaque préfixe du chemin d'objet de bus, c'est-à-dire avec les derniers composants séparés par des barres obliques supprimés successivement. Cela permet d'utiliser la table virtuelle pour un nombre arbitraire d'objets créés dynamiquement.

Le paramètre find est une fonction utilisée pour localiser l'objet cible en fonction du chemin d'objet de bus path. Elle doit retourner 1 et définir le paramètre de sortie ret_found si l'objet est trouvé, retourner 0 si l'objet n'a pas été trouvé, et retourner un code d'erreur négatif de style errno ou initialiser la structure d'erreur ret_error en cas d'erreur. Le pointeur passé dans ret_found sera utilisé comme paramètre userdata pour les fonctions de rappel (décalé par les décalages offset tels que spécifiés dans les entrées de la table virtuelle).

sd_bus_add_object() attache un rappel directement au chemin d'objet path. Un chemin d'objet peut avoir n'importe quel nombre de rappels qui lui sont attachés. Chaque rappel est ajouté en préfixe à la liste des rappels qui sont toujours appelés dans l'ordre. sd_bus_add_fallback() est similaire à sd_bus_add_object() mais s'applique aux chemins de secours au lieu de cela.

sd_bus_add_filter() installe un rappel qui est invoqué pour chaque message D-Bus entrant. Les filtres peuvent être utilisés pour gérer la logique commune à tous les messages reçus par un service (par exemple, authentification ou autorisation).

Lorsqu'une requête est reçue, tous les rappels associés sont appelés séquentiellement jusqu'à ce qu'un rappel retourne un entier non nul. Retournez zéro d'un rappel pour donner à d'autres rappels la chance de traiter la requête. Les rappels sont appelés dans l'ordre suivant : premièrement, les rappels globaux installés avec sd_bus_add_filter() sont appelés. Deuxièmement, les rappels attachés directement au chemin d'objet de la requête sont appelés, suivis de tous les rappels de méthode D-Bus attachés au chemin d'objet de la requête, à l'interface et au membre. Enfin, les rappels de propriété attachés au chemin d'objet de la requête, à l'interface et au membre sont appelés. Si le dernier rappel retourne zéro, une réponse d'erreur

est renvoyé à l'appelant indiquant qu'aucun objet correspondant à la demande n'a été trouvé.

Notez que vous pouvez renvoyer un entier positif à partir d'un rappel de méthode sans envoyer immédiatement de réponse. Cela informe sd-bus que ce rappel assumera la responsabilité de répondre à la demande sans forcer le rappel à produire une réponse immédiatement. Cela permet à un rappel d'effectuer autant d'opérations asynchrones que nécessaire pour construire une réponse. Cependant, si la production d'une réponse prend trop de temps, l'appel de méthode expirera côté appelant. Ceci n'est disponible que pour les méthodes et non pour les propriétés.

Si un rappel a été invoqué pour traiter une demande qui attend une réponse et que le rappel renvoie une valeur négative, la valeur est interprétée comme un code d'erreur négatif de style errno et renvoyée à l'appelant en tant qu'erreur D-Bus, comme si sd_bus_reply_method_errno(3) avait été appelé. De plus, tous les rappels prennent un paramètre de sortie sd_bus_error qui peut être utilisé pour fournir des informations d'erreur plus détaillées. Si ret_error est défini lorsque le rappel se termine, l'erreur D-Bus correspondante est renvoyée à l'appelant comme si sd_bus_reply_method_error(3) avait été appelé. Toute erreur stockée dans ret_error a la priorité sur toute valeur négative renvoyée par le même rappel pour déterminer quelle erreur renvoyer à l'appelant. Utilisez sd_bus_error_set(3) ou l'une de ses variantes pour définir ret_error et renvoyer un entier négatif à partir d'un rappel avec un unique appel de fonction. Pour envoyer une réponse d'erreur après qu'un rappel a déjà terminé, utilisez sd_bus_reply_method_errno(3) ou l'une de ses variantes.

Pour toutes les fonctions, un slot de correspondance est créé interne. Si le paramètre de sortie slot est NULL, un slot d'objet "flottant" est créé, voir sd_bus_slot_set_floating(3). Sinon, un pointeur vers l'objet slot est renvoyé. Dans ce cas, la référence à l'objet slot doit être libérée lorsque la vtable n'est plus nécessaire, voir sd_bus_slot_unref(3).

Le tableau sd_bus_vtable

Le tableau se compose des structures de type sd_bus_vtable, mais il ne doit jamais être rempli manuellement, mais via l'une des macros suivantes :

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Ceux-ci doivent toujours être le premier et le dernier élément. Le paramètre flags peut être utilisé pour définir des attributs qui s'appliquent à l'ensemble du tableau ; voir la section "Flags" ci-dessous.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Déclare une méthode D-Bus avec le nom member, les arguments args et le résultat result. args attend une séquence de paires type/nom d'argument enveloppées dans la macro SD_BUS_ARGS(). Les éléments aux indices pairs de cette liste décrivent les types des arguments de la méthode. La signature des paramètres de la méthode est la concaténation de toutes les littéraux de chaîne aux indices pairs dans args. Si une méthode n'a pas de paramètres, passez SD_BUS_NO_ARGS à args. Les éléments aux indices impairs décrivent les noms des arguments de la méthode. result attend une séquence de paires type/nom enveloppées dans la macro SD_BUS_RESULT() dans le même format que SD_BUS_ARGS(). La signature du résultat de la méthode est la concaténation de toutes les littéraux de chaîne aux indices pairs dans result. Si une méthode n'a pas de résultat, passez SD_BUS_NO_RESULT à result. Notez que les types d'arguments sont censés être des littéraux de chaîne entre guillemets et les noms d'arguments sont censés être des littéraux de chaîne sans guillemets. Voir ci-dessous pour un exemple complet.

La fonction gestionnaire handler doit être de type sd_bus_message_handler_t. Elle sera appelée pour traiter les messages entrants qui appellent cette méthode. Elle reçoit un pointeur qui est le paramètre userdata passé à la fonction d'enregistrement décalé de offset octets. Ceci peut être utilisé pour passer des pointeurs vers différents champs de la même structure de données à différentes méthodes de la même vtable. Pour envoyer une réponse depuis handler, appelez sd_bus_reply_method_return(3) avec le message avec lequel le rappel a été invoqué. Le paramètre flags est une combinaison de drapeaux, voir ci-dessous.

SD_BUS_METHOD_WITH_ARGS() est un raccourci pour appeler SD_BUS_METHOD_WITH_ARGS_OFFSET() avec un décalage de zéro.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Déclare une méthode D-Bus avec le nom member, la signature de paramètre signature, la signature de résultat result. Les paramètres in_names et out_names spécifient les noms des arguments des arguments d'entrée et de sortie dans la signature de la fonction. in_names et out_names doivent être créés en utilisant la macro SD_BUS_PARAM(), voir ci-dessous. À tous autres égards, cette macro se comporte exactement de la même manière que SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), et SD_BUS_METHOD() sont des variantes qui spécifient un décalage nul (le paramètre userdata est passé sans modification), omettent les noms (c'est-à-dire aucun nom de paramètre), ou les deux.

Privilégiez l'utilisation de SD_BUS_METHOD_WITH_ARGS_OFFSET() et SD_BUS_METHOD_WITH_ARGS() plutôt que ces macros car elles permettent de spécifier les types et les noms des arguments côte à côte, ce qui est moins sujet aux erreurs que de spécifier d'abord tous les types d'arguments suivis de tous les noms d'arguments.

SD_BUS_SIGNAL_WITH_ARGS()

Déclare un signal D-Bus avec le nom member et les arguments args. args attend une séquence de paires type/nom d'argument enveloppées dans la macro SD_BUS_ARGS(). Les éléments aux indices pairs de cette liste décrivent les types des arguments du signal. La signature des paramètres du signal est la concaténation de toutes les littéraux de chaîne aux indices pairs dans args. Si un signal n'a pas de paramètres, passez SD_BUS_NO_ARGS à args. Les éléments aux indices impairs décrivent les noms des arguments du signal. Le paramètre flags est une combinaison de drapeaux. Voir ci-dessous pour un exemple complet.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Déclare un signal D-Bus avec le nom member, la signature de paramètre signature et les noms d'arguments names. names doit être créé en utilisant la macro SD_BUS_PARAM(), voir ci-dessous. Le paramètre flags est une combinaison de drapeaux, voir ci-dessous.

SD_BUS_SIGNAL() est équivalent à SD_BUS_SIGNAL_WITH_NAMES() avec le paramètre names omis (c'est-à-dire aucun nom de paramètre).

Privilégiez l'utilisation de SD_BUS_SIGNAL_WITH_ARGS() plutôt que ces macros car elle permet de spécifier les types et les noms des arguments côte à côte, ce qui est moins sujet aux erreurs que de spécifier d'abord tous les types d'arguments suivis de tous les noms d'arguments.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Déclare une propriété D-Bus avec le nom member et la signature de valeur signature. Les paramètres get et set sont les méthodes de lecture et d'écriture. Elles sont appelées avec un pointeur qui est le paramètre userdata passé à la fonction d'enregistrement décalé de offset octets. Ceci peut être utilisé pour passer des pointeurs vers différents champs de la même structure de données à différents setters et getters de la même vtable. Le paramètre flags est une combinaison de drapeaux, voir ci-dessous.

Les méthodes de lecture (setter) et d'écriture (getter) peuvent être omis (spécifiées comme NULL), si la propriété est de l'un des types de base ou "as" dans le cas de propriétés en lecture seule. Dans ces cas, les paramètres userdata et offset doivent ensemble pointer vers une variable valide du type correspondant. Un setter et un getter par défaut seront fournis, qui copient simplement l'argument entre cette variable et le message.

SD_BUS_PROPERTY() est utilisé pour définir une propriété en lecture seule.

SD_BUS_PARAM()

Les noms de paramètres doivent être enveloppés dans cette macro, voir l'exemple ci-dessous.

Drapeaux

Le paramètre flags est utilisé pour spécifier une combinaison d'annotations D-Bus[1].

SD_BUS_VTABLE_DEPRECATED

Marque cette entrée de vtable comme obsolète en utilisant l'annotation org.freedesktop.DBus.Deprecated dans les données d'introspection. Si spécifié pour SD_BUS_VTABLE_START(), l'annotation est appliquée à l'interface englobante.

SD_BUS_VTABLE_HIDDEN

Rend cette entrée de vtable cachée. Elle ne sera pas montrée dans les données d'introspection. Si spécifié pour SD_BUS_VTABLE_START(), toutes les entrées du tableau sont cachées.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marque cette entrée de vtable comme une méthode qui ne renverra pas de réponse en utilisant l'annotation org.freedesktop.DBus.Method.NoReply dans les données d'introspection.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Ces trois drapeaux correspondent à différentes valeurs de l'annotation org.freedesktop.DBus.Property.EmitsChangedSignal, qui spécifie si le signal org.freedesktop.DBus.Properties.PropertiesChanged est émis chaque fois que la propriété change. SD_BUS_VTABLE_PROPERTY_CONST correspond à const et signifie que la propriété ne change jamais pendant la durée de vie de l'objet auquel elle appartient, donc aucun signal n'a besoin d'être émis. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE correspond à true et signifie que le signal est émis. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION correspond à invalidates et signifie que le signal est émis, mais la valeur n'est pas incluse dans le signal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marque cette entrée de propriété de vtable comme nécessitant une demande explicite pour que la valeur soit affichée (généralement parce que la valeur est grande ou lente à calculer). Cette entrée ne peut pas être combinée avec SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, et ne sera pas affichée dans les listes de propriétés par défaut (par exemple, busctl introspect). Ceci correspond à l'annotation org.freedesktop.systemd1.Explicit dans les données d'introspection.

SD_BUS_VTABLE_SENSITIVE

Marque cette entrée de méthode de vtable comme traitant des données sensibles. Lorsqu'il est défini, les messages d'appel de méthode entrants et leurs messages de réponse sortants sont marqués comme sensibles en utilisant sd_bus_message_sensitive(3), de sorte qu'ils soient effacés de la mémoire lorsqu'ils sont libérés.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

Marque cette entrée de méthode ou de propriété de vtable pour que le pointeur de données utilisateur
passed à ses fonctions de gestion associées est déterminé légèrement différemment : au lieu d'ajouter le paramètre de décalage de l'entrée au pointeur de données utilisateur spécifié lors de l'enregistrement de la vtable, le décalage est passé directement, converti en pointeur, sans prendre en compte le pointeur de données utilisateur spécifié lors de l'enregistrement de la vtable.

SD_BUS_VTABLE_CAPABILITY(capability)

L'accès à cette entrée de vtable sera autorisé si le processus appelant possède la capacité capability, comme décrit dans sd_bus_query_sender_privilege(3). Si utilisé pour SD_BUS_VTABLE_START(), fournit une valeur par défaut pour toutes les entrées du tableau. Si non spécifié, que ce soit pour une entrée individuelle ou pour tout le tableau, CAP_SYS_ADMIN est vérifié par défaut. Voir capabilities(7) pour des informations sur les capacités.

Notez que les entrées de vtable peuvent être marquées comme non privilégiées et que l'ensemble du bus peut être marqué comme approuvé, voir la discussion sur SD_BUS_VTABLE_UNPRIVILEGED ci-dessous.

SD_BUS_VTABLE_UNPRIVILEGED

Marque cette entrée de vtable comme non privilégiée. L'accès aux entrées privilégiées est limité aux utilisateurs ayant les capacités appropriées, comme décrit ci-dessus. En pratique, de nombreuses entrées de vtable sont marquées comme non privilégiées, et sont soit ouvertes à tous, soit la décision d'autoriser l'accès est prise plus tard, par exemple en déléguant à polkit[2].

L'ensemble du bus peut être marqué comme approuvé, auquel cas les annotations au niveau de l'entrée sont ignorées, voir sd_bus_set_trusted(3).

Lorsque non spécifié, l'annotation org.freedesktop.systemd1.Privileged avec la valeur "true" sera affichée dans les données d'introspection.

SD_BUS_VTABLE_UNPRIVILEGED ne peut pas être appliqué aux propriétés en lecture seule, mais l'accès en lecture (aux propriétés en lecture seule et en écriture) est toujours sans restriction.

Notez que cette page décrit les vérifications implémentées dans le client D-Bus. Le serveur D-Bus dispose d'une politique supplémentaire qui peut autoriser ou refuser les connexions, voir "FICHIER DE CONFIGURATION" dans dbus-daemon(1).

EXEMPLES

Exemple 1. Créer un écouteur simple sur le bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Appelé avec userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() a échoué : %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() a échoué : %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_VTABLE_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() a échoué : %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() a échoué : %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() a échoué : %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() a échoué : %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() a échoué : %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

VALEUR DE RETOUR

En cas de succès, sd_bus_add_object_vtable() et sd_bus_add_fallback_vtable() renvoient un entier non négatif. En cas d'échec, ils renvoient un code d'erreur négatif de style errno.

Erreurs

Les erreurs renvoyées peuvent indiquer les problèmes suivants :

-EINVAL

L'un des paramètres requis est NULL ou invalide. Une interface D-Bus réservée a été passée comme paramètre interface.

-ENOPKG

Le bus ne peut pas être résolu.

-ECHILD

Le bus a été créé dans un processus, une bibliothèque ou une instance de module différente.

-ENOMEM

Échec de l'allocation de mémoire.

-EPROTOTYPE

sd_bus_add_object_vtable() et sd_bus_add_fallback_vtable() ont tous deux été appelés pour le même chemin d'objet de bus, ce qui n'est pas autorisé.

-EEXIST

Cette vtable a déjà été enregistrée pour cette interface et ce chemin.

NAME

sd_bus_add_object, sd_bus_add_object_vtable, sd_bus_add_fallback, sd_bus_add_fallback_vtable, sd_bus_add_filter, sd_bus_object_find_t, sd_bus_property_get_t, sd_bus_property_set_t – ajouter des objets et des gestionnaires de méthodes D-Bus

SYNOPSIS

#include <systemd/sd-bus.h>

int sd_bus_add_object(sd_bus *bus, const char *path, const char *interface, sd_bus_method_handler_t handler, void *userdata);
int sd_bus_add_object_vtable(sd_bus *bus, const char *path, const char *interface, const sd_bus_vtable *vtable, void *userdata);
int sd_bus_add_fallback(sd_bus *bus, const char *path, sd_bus_message_handler_t handler, void *userdata);
int sd_bus_add_fallback_vtable(sd_bus *bus, const char *path, const sd_bus_vtable *vtable, void *userdata);
int sd_bus_add_filter(sd_bus *bus, sd_bus_message_handler_t handler, void *userdata);
int sd_bus_object_find_t(sd_bus *bus, const char *path, const char *interface, sd_bus_object_find_t **handler);
int sd_bus_property_get_t(sd_bus *bus, const char *path, const char *interface, const char *property, sd_bus_property_get_t **handler);
int sd_bus_property_set_t(sd_bus *bus, const char *path, const char *interface, const char *property, sd_bus_property_set_t **handler);

DESCRIPTION

Le bus systemd D-Bus sd-bus est une API légère et efficace pour interagir avec le système de bus D-Bus. Les fonctions décrites ici permettent d'enregistrer des objets, des gestionnaires de méthodes et des filtres sur le bus D-Bus, et d'interroger des gestionnaires de méthodes et de propriétés.

Les fonctions sd_bus_add_object() et sd_bus_add_object_vtable() enregistrent un objet D-Bus sur le bus donné bus. L'objet sera disponible à path et exposera des méthodes définies par l'interface interface. sd_bus_add_object() prend un pointeur de fonction handler qui gérera toutes les appels de méthodes pour l'objet. sd_bus_add_object_vtable() prend un pointeur vers une table de correspondance sd_bus_vtable qui associe les noms des méthodes aux gestionnaires de méthodes.

Les fonctions sd_bus_add_fallback() et sd_bus_add_fallback_vtable() enregistrent un gestionnaire de secours sur le bus bus. Ce gestionnaire sera appelé pour toutes les méthodes et propriétés D-Bus qui ne sont pas explicitement gérées par un objet enregistré. sd_bus_add_fallback() prend un pointeur de fonction handler, tandis que sd_bus_add_fallback_vtable() prend un pointeur vers une table de correspondance sd_bus_vtable.

La fonction sd_bus_add_filter() enregistre un filtre de messages sur le bus bus. Ce filtre sera appelé pour tous les messages D-Bus entrants avant qu'ils ne soient routés vers leurs gestionnaires de destination. Le filtre peut inspecter et modifier le message, ou le rejeter.

Les fonctions sd_bus_object_find_t(), sd_bus_property_get_t() et sd_bus_property_set_t() sont utilisées pour interroger le gestionnaire de méthodes D-Bus enregistré pour un objet spécifique, une interface et une méthode ou propriété donnée. Elles renvoient un pointeur vers la fonction de gestionnaire correspondante dans handler. Si aucun gestionnaire n'est trouvé, handler sera défini sur NULL.

Les paramètres userdata sont des données spécifiques à l'utilisateur qui seront transmises aux gestionnaires de méthodes ou de filtres.

EXAMPLES

Voici un exemple d'utilisation de sd_bus_add_object_vtable() pour enregistrer un objet avec plusieurs méthodes:

static int my_object_method_handler(sd_bus_message *m,
                                    void *userdata,
                                    sd_bus_error *ret_error) {
    // Implémentation de la méthode
    return sd_bus_reply_method_return(m, NULL);
}

static const sd_bus_vtable my_object_vtable[] = {
    {
        .method = SD_BUS_VTABLE_METHOD("MyMethod", "s", "s"),
        .handler = my_object_method_handler,
    },
    {
        .method = SD_BUS_VTABLE_END,
    },
};

// Dans votre fonction principale ou d'initialisation :
sd_bus *bus;
sd_bus_open_user(&bus);
sd_bus_add_object_vtable(bus, "/com/example/MyObject", "com.example.MyInterface", my_object_vtable, NULL);
// ...
sd_bus_unref(bus);

RETURN VALUE

En cas de succès, ces fonctions renvoient 0. En cas d'échec, elles renvoient un nombre entier négatif représentant un code d'erreur.

NOTES

Les fonctions sd_bus_add_object() et ses variantes enregistrent des gestionnaires pour les méthodes D-Bus. Les gestionnaires de propriétés sont généralement gérés via des interfaces spécifiques ou des mécanismes d'introspection.

L'utilisation des fonctions ici décrites nécessite que l'application soit liée à la bibliothèque libsystemd. Ceci peut être fait en utilisant le fichier pkg-config(1) libsystemd.

Le code décrit ici utilise getenv(3), qui n'est pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'appeler setenv() qu'à partir d'une phase précoce du programme lorsque aucun autre thread n'a été démarré.
