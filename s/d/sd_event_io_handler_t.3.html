SYNTAXE

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;

typedef int (*sd_event_io_handler_t)(sd_event_source *s, int fd, uint32_t revents, void *userdata);

int sd_event_add_io(sd_event *event, sd_event_source **source, int fd, uint32_t events, sd_event_io_handler_t handler, void *userdata);

int sd_event_source_get_io_events(sd_event_source *source, uint32_t *ret);

int sd_event_source_set_io_events(sd_event_source *source, uint32_t events);

int sd_event_source_get_io_revents(sd_event_source *source, uint32_t *ret);

int sd_event_source_get_io_fd(sd_event_source *source);

int sd_event_source_set_io_fd(sd_event_source *source, int fd);

int sd_event_source_get_io_fd_own(sd_event_source *source);

int sd_event_source_set_io_fd_own(sd_event_source *source, int b);

DESCRIPTION

sd_event_add_io() ajoute une nouvelle source d'événement d'E/S à une boucle d'événements. L'objet de la boucle d'événements est spécifié dans le paramètre event, l'objet de la source d'événement est retourné dans le paramètre source. Le paramètre fd prend le descripteur de fichier UNIX à surveiller, qui peut faire référence à un socket, un FIFO, une file de messages, une connexion série, un périphérique caractère, ou tout autre descripteur de fichier compatible avec epoll(7) de Linux. Le paramètre events prend un masque de bits des événements à surveiller, une combinaison des drapeaux d'événements suivants : EPOLLIN, EPOLLOUT, EPOLLRDHUP, EPOLLPRI, et EPOLLET, voir epoll_ctl(2) pour les détails. Notez que tous les descripteurs de fichiers ne sont pas compatibles avec epoll, par exemple les fichiers réguliers ou les répertoires ne le sont pas. Si cette fonction est appelée avec un descripteur de fichier qui ne prend pas en charge epoll, -EPERM est retourné (voir également ci-dessous). Dans la plupart des cas, ces descripteurs de fichiers peuvent être traités comme toujours lisibles ou toujours écrivables, de sorte que la surveillance des événements d'E/S n'est pas nécessaire.

Le handler est une fonction à appeler lorsque la source d'événement est déclenchée ou NULL. Le pointeur userdata sera passé à la fonction de gestion, et peut être choisi librement par l'appelant. La fonction de gestion recevra également le descripteur de fichier sur lequel l'événement a été vu, ainsi que les drapeaux d'événements réels. Il s'agit généralement d'un sous-ensemble des événements surveillés, mais peut inclure en plus EPOLLERR et EPOLLHUP. La fonction de gestion peut retourner une valeur négative pour signaler une erreur (voir ci-dessous), d'autres valeurs de retour sont ignorées. Si handler est NULL, une fonction de gestion par défaut qui appelle sd_event_exit(3) sera utilisée.

Par défaut, une source d'événement reste activée en permanence (SD_EVENT_ON), mais cela peut être modifié avec sd_event_source_set_enabled(3). Si la fonction de gestion retourne un code d'erreur négatif, elle sera désactivée après l'invocation, même si le mode SD_EVENT_ON était demandé auparavant, ou elle provoquera la terminaison de la boucle, voir sd_event_source_set_exit_on_failure(3). Notez qu'une source d'événement réglée sur SD_EVENT_ON se déclenchera en continu à moins que des données ne soient lues ou écrites sur le descripteur de fichier pour réinitialiser le masque des événements vus.

Définir le masque d'événements d'E/S à surveiller sur 0 ne signifie pas que la source d'événement ne sera plus déclenchée, car EPOLLHUP et EPOLLERR peuvent être déclenchés même avec un masque d'événements nul. Pour désactiver temporairement une source d'événement d'E/S, utilisez plutôt sd_event_source_set_enabled(3) avec SD_EVENT_OFF.

Pour détruire un objet source d'événement, utilisez sd_event_source_unref(3), mais notez que la source d'événement n'est retirée de la boucle d'événements que lorsque toutes les références à la source d'événement sont libérées. Pour s'assurer qu'une source d'événement ne se déclenche plus, même si elle est toujours référencée, désactivez la source d'événement en utilisant sd_event_source_set_enabled(3) avec SD_EVENT_OFF.

Si le deuxième paramètre de sd_event_add_io() est NULL, aucune référence à l'objet source d'événement n'est retournée. Dans ce cas, la source d'événement est considérée comme "flottante" et sera détruite implicitement lorsque la boucle d'événements elle-même sera détruite.

Si le handler passé à sd_event_add_io() est NULL, et que la source d'événement se déclenche, cela sera considéré comme une demande de sortie de la boucle d'événements. Dans ce cas, le paramètre userdata, converti en entier, est passé comme paramètre de code de sortie à sd_event_exit(3).

Notez que cet appel ne prend pas possession du descripteur de fichier passé, la propriété (et donc le devoir de le fermer lorsqu'il n'est plus nécessaire) reste avec l'appelant. Cependant, avec l'appel sd_event_source_set_io_fd_own() (voir ci-dessous), la source d'événement peut éventuellement prendre possession du descripteur de fichier après sa création. Dans ce cas, le descripteur de fichier est fermé automatiquement dès que la source d'événement est libérée.

Il est recommandé d'utiliser sd_event_add_io() uniquement en conjonction avec des descripteurs de fichiers ayant le mode O_NONBLOCK défini, afin de garantir que toutes les opérations d'E/S des gestionnaires invoqués soient correctement asynchrones et non bloquantes. L'utilisation de descripteurs de fichiers sans O_NONBLOCK pourrait entraîner une famine inattendue d'autres sources d'événements. Voir fcntl(2) pour les détails sur l'activation du mode O_NONBLOCK.

sd_event_source_get_io_events() récupère le masque configuré des événements d'E/S surveillés d'une source d'événement créée précédemment avec sd_event_add_io(). Il prend l'objet source d'événement et un pointeur vers une variable pour y stocker le masque.

sd_event_source_set_io_events() configure le masque des événements d'E/S surveillés d'une source d'événement créée précédemment avec sd_event_add_io(). Il prend l'objet source d'événement et le nouveau masque d'événements.

sd_event_source_get_io_revents() récupère le masque d'événements d'E/S des événements actuellement vus mais non encore dépêchés d'une source d'événement créée précédemment avec sd_event_add_io(). Il prend l'objet source d'événement et un pointeur vers une variable pour y stocker le masque d'événements. Lorsqu'elle est appelée depuis une fonction de gestion sur l'objet source d'événement de cette gestion, elle retournera le même masque que celui passé au paramètre revents de la gestion. Cet appel est principalement utile pour vérifier les événements non dépêchés d'une source d'événement depuis la gestion d'une source d'événement non liée (potentiellement de priorité supérieure). Notez la relation entre sd_event_source_get_pending() et sd_event_source_get_io_revents() : les deux fonctions signaleront des résultats non nuls lorsqu'un événement est en attente pour la source d'événement, mais la première s'applique à tous les types de sources d'événement, la seconde uniquement aux sources d'événement d'E/S.

sd_event_source_get_io_fd() récupère le descripteur de fichier UNIX d'une source d'événement créée précédemment avec sd_event_add_io(). Il prend l'objet source d'événement et retourne le descripteur de fichier non négatif ou un nombre d'erreur négatif en cas d'erreur (voir ci-dessous).

sd_event_source_set_io_fd() modifie le descripteur de fichier UNIX d'une source d'événement d'E/S créée précédemment avec sd_event_add_io(). SYNOPSIS

#include <systemd/sd-event.h>

typedef int (*sd_event_io_handler_t)(sd_event_source *source,

                                   void *userdata);

int sd_event_add_io(sd_event *event,
                    sd_event_source **source,
                    int fd,
                    uint32_t events,
                    sd_event_io_handler_t callback,
                    void *userdata);

int sd_event_source_get_io_events(sd_event_source *source,
                                  uint32_t *ret_events);

int sd_event_source_set_io_events(sd_event_source *source,
                                  uint32_t events);

int sd_event_source_get_io_revents(sd_event_source *source,
                                   uint32_t *ret_events);

int sd_event_source_get_io_fd(sd_event_source *source,
                              int *ret_fd);

int sd_event_source_set_io_fd(sd_event_source *source,
                              int fd);

int sd_event_source_get_io_fd_own(sd_event_source *source,
                                  int *ret_own);

int sd_event_source_set_io_fd_own(sd_event_source *source,
                                  int own);

DESCRIPTION

Ces fonctions permettent de créer et de gérer des gestionnaires d'événements d'entrée/sortie (I/O). Les événements d'I/O sont déclenchés par des changements dans l'état d'un descripteur de fichier (tel que la disponibilité de lecture, d'écriture, ou la déconnexion). Les événements peuvent être surveillés en utilisant epoll(7), poll(2), kqueue(2), inotify(7), et signalfd(2). Ils sont implémentés comme des sources d'événements spécifiques à l'I/O.

sd_event_add_io() enregistre un nouveau gestionnaire d'événements d'I/O auprès de la boucle d'événements event. Le descripteur de fichier fd sera surveillé pour les événements spécifiés dans events. La fonction de rappel callback sera appelée lorsque l'un de ces événements se produira. Le paramètre userdata est passé tel quel à la fonction de rappel. Si source n'est pas NULL, un pointeur vers la structure de source d'événement nouvellement créée sera stocké dans la variable pointée par source. Par défaut, le descripteur de fichier n'est pas possédé par la source de l'événement, et l'application doit le fermer elle-même si nécessaire. Si sd_event_add_io est appelé avec un événement source déjà existant, l'événement et le descripteur de fichier spécifiés seront ajoutés à l'ensemble des événements surveillés pour la source d'événement existante.

events est un masque de bits des événements d'intérêt, qui peut être une combinaison de EPOLLIN, EPOLLPRI, EPOLLOUT, EPOLLERR, EPOLLHUP, EPOLLET, et EPOLLONESHOT. La signification de ces drapeaux est décrite dans epoll(7). Si EPOLLET est utilisé, le mode "edge-triggered" sera activé pour la source d'événement. Si EPOLLONESHOT est utilisé, le gestionnaire d'événements d'I/O sera automatiquement désactivé après qu'il ait été appelé une fois.

sd_event_source_get_io_events() renvoie les événements d'I/O qui ont été demandés pour la source d'événement source. Cette valeur est celle qui a été passée à sd_event_add_io() ou sd_event_source_set_io_events().

sd_event_source_set_io_events() modifie les événements d'I/O surveillés pour la source d'événement source pour correspondre à events.

sd_event_source_get_io_revents() renvoie les événements d'I/O qui se sont réellement produits pour la source d'événement source. C'est un masque de bits des événements qui ont été déclenchés par le noyau.

sd_event_source_get_io_fd() renvoie le descripteur de fichier associé à la source d'événement source. Si la propriété du descripteur de fichier est activée, il sera fermé automatiquement lorsque la source de l'événement sera libérée ou lorsque le descripteur de fichier sera remplacé par sd_event_source_set_io_fd(). Par défaut, le descripteur de fichier n'est pas possédé par la source de l'événement, et l'application doit le fermer elle-même si nécessaire.

sd_event_source_set_io_fd() modifie le descripteur de fichier surveillé pour la source d'événement source pour correspondre à fd. Si la propriété du descripteur de fichier est activée, l'ancien descripteur de fichier sera fermé automatiquement avant que le nouveau soit attaché. Si la propriété du descripteur de fichier est désactivée, l'application est responsable de la fermeture de l'ancien descripteur de fichier si nécessaire.

sd_event_source_set_io_fd_own() active ou désactive la propriété du descripteur de fichier pour la source d'événement source. Si own est positif, le descripteur de fichier sera fermé automatiquement lorsque la source de l'événement sera libérée ou lorsque le descripteur de fichier sera remplacé par sd_event_source_set_io_fd(). Par défaut, le descripteur de fichier n'est pas possédé par la source de l'événement, et l'application doit le fermer elle-même si nécessaire.

sd_event_source_get_io_fd_own() peut être utilisé pour interroger le réglage actuel du drapeau booléen de propriété du descripteur de fichier tel que défini avec sd_event_source_set_io_fd_own(). Il renvoie une valeur positive si le descripteur de fichier est fermé automatiquement lorsque la source de l'événement est détruite, zéro sinon, et une valeur négative en cas d'erreur.

RETURN VALUE

En cas de succès, ces fonctions renvoient 0 ou un entier positif. En cas d'échec, elles renvoient un code d'erreur négatif de type errno.

Errors

Les valeurs renvoyées peuvent indiquer les problèmes suivants :

-ENOMEM

Pas assez de mémoire pour allouer un objet.

-EINVAL

Un argument invalide a été passé.

-ESTALE

La boucle d'événements est déjà terminée.

-ECHILD

La boucle d'événements a été créée dans un processus, une bibliothèque ou une instance de module différent.

-EDOM

La source d'événement passée n'est pas une source d'événement d'E/S.

-EPERM

Le descripteur de fichier passé ne prend pas en charge l'API epoll(7), par exemple parce qu'il s'agit d'un fichier ordinaire ou d'un répertoire. Voir epoll_ctl(2) pour plus de détails.

Ajouté dans la version 255.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier pkg-config(1) de libsystemd.

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'appeler setenv() qu'à une phase précoce du programme, lorsque aucun autre thread n'a encore été démarré.
