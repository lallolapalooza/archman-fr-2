DESCRIPTION

sd_pid_get_owner_uid() peut être utilisé pour déterminer l'UID Unix (identifiant utilisateur) qui possède la session de connexion ou l'unité utilisateur systemd d'un processus identifié par le PID spécifié. Pour les processus qui ne font pas partie d'une session de connexion et ne sont pas gérés par un gestionnaire d'utilisateurs, cette fonction échouera avec -ENODATA.

sd_pid_get_session() peut être utilisé pour déterminer l'identifiant de session de connexion d'un processus identifié par l'identifiant de processus spécifié. L'identifiant de session est une courte chaîne, adaptée à une utilisation dans les chemins de système de fichiers. Notez que la session de connexion peut être limitée à un processus stub ou deux. Les processus utilisateur peuvent plutôt être démarrés à partir de leur gestionnaire d'utilisateurs systemd, par exemple des applications GUI démarrées à l'aide de l'activation DBus, ainsi que des processus de service qui sont partagés entre plusieurs connexions du même utilisateur. Pour les processus qui ne font pas partie d'une session de connexion, cette fonction échouera avec -ENODATA. La chaîne renvoyée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_user_unit() peut être utilisé pour déterminer l'identifiant de l'unité utilisateur systemd (c'est-à-dire un service utilisateur ou une unité de portée) d'un processus identifié par le PID spécifié. Le nom de l'unité est une courte chaîne, adaptée à une utilisation dans les chemins de système de fichiers. Pour les processus qui ne sont pas gérés par un gestionnaire d'utilisateurs, cette fonction échouera avec -ENODATA. La chaîne renvoyée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_unit() peut être utilisé pour déterminer l'identifiant de l'unité système systemd (c'est-à-dire un service système ou une unité de portée) d'un processus identifié par le PID spécifié. Le nom de l'unité est une courte chaîne, adaptée à une utilisation dans les chemins de système de fichiers. Notez que tous les processus ne font pas partie d'une unité/service système. Pour les processus qui ne font pas partie d'une unité système systemd, cette fonction échouera avec -ENODATA. (Plus spécifiquement, cet appel ne fonctionnera pas pour les threads du noyau.) La chaîne renvoyée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_machine_name() peut être utilisé pour déterminer le nom de la VM ou du conteneur dont il fait partie. Le nom de la machine est une courte chaîne, adaptée à une utilisation dans les chemins de système de fichiers. La chaîne renvoyée doit être libérée avec l'appel free(3) de la libc après utilisation. Pour les processus qui ne font pas partie d'une VM ou d'un conteneur, cette fonction échoue avec -ENODATA.

sd_pid_get_slice() peut être utilisé pour déterminer l'unité de tranche dont le processus est membre. Voir systemd.slice(5) pour plus de détails sur les tranches. La chaîne renvoyée doit être libérée avec l'appel free(3) de la libc après utilisation.

De même, sd_pid_get_user_slice() renvoie la tranche utilisateur (telle que gérée par l'instance systemd de l'utilisateur) d'un processus.

sd_pid_get_cgroup() renvoie le chemin du groupe de contrôle du processus spécifié, relatif à la racine de la hiérarchie. Renvoie le chemin sans barre oblique finale, sauf pour les processus situés dans le groupe de contrôle racine, où "/" est renvoyé. Pour trouver le chemin réel du groupe de contrôle dans le système de fichiers, le chemin renvoyé doit être précédé de /sys/fs/cgroup/.

Si le paramètre pid de l'une de ces fonctions est passé comme 0, l'opération est exécutée pour le processus appelant.

Les appels sd_pidfd_get_owner_uid(), sd_pidfd_get_session(), sd_pidfd_get_user_unit(), sd_pidfd_get_unit(), sd_pidfd_get_machine_name(), sd_pidfd_get_slice(), sd_pidfd_get_user_slice() et sd_pidfd_get_cgroup() fonctionnent de manière similaire à leurs contreparties PID, mais acceptent un PIDFD au lieu d'un PID, ce qui signifie qu'ils ne sont pas sujets aux conditions de concurrence de recyclage car le processus est épinglé par le descripteur de fichier pendant toute la durée de l'invocation. Notez que cela nécessite un noyau qui prend en charge PIDFD. Un descripteur de fichier approprié peut être acquis via pidfd_open(2).

Les appels sd_peer_get_owner_uid(), sd_peer_get_session(), sd_peer_get_user_unit(), sd_peer_get_unit(), sd_peer_get_machine_name(), sd_peer_get_slice(), sd_peer_get_user_slice() et sd_peer_get_cgroup() fonctionnent de manière similaire à leurs contreparties PID, mais acceptent un socket AF_UNIX connecté et récupèrent des informations sur le processus pair connecté. Notez que ces champs sont récupérés via /proc/, et ne sont donc pas adaptés à des fins d'autorisation, car ils sont sujets à des conditions de concurrence.

VALEUR DE RETOUR

En cas de succès, ces appels renvoient 0 ou un entier positif. En cas d'échec, ces appels renvoient un code d'erreur négatif de style errno.

Erreurs

Les erreurs renvoyées peuvent indiquer les problèmes suivants :

-ESRCH

Le PID spécifié ne correspond pas à un processus en cours d'exécution.

-EBADF

Le descripteur de fichier spécifié est invalide.

-ENODATA

Le champ spécifié n'est pas défini pour le processus ou le pair décrit.

-EINVAL

>

Un paramètre d'entrée était invalide (hors limites, ou NULL, là où ce n'est pas accepté).

-ENOMEM

L'allocation mémoire a échoué.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

Notez que l'identifiant de session de connexion tel que retourné par sd_pid_get_session() n'est absolument pas lié à l'identifiant de session du processus tel que retourné par getsid(2).
