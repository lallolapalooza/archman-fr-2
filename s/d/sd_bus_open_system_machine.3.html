DESCRIPTION

sd_bus_default() acquiert un objet de connexion au bus utilisateur lorsqu'il est appelé depuis une tranche utilisateur ("user-*.slice", par exemple : "user@1000.service"), ou au bus système sinon. L'objet de connexion est associé au thread appelant. Chaque fois que la fonction est appelée depuis le même thread, le même objet est retourné, mais son compteur de références est incrémenté d'une unité, tant qu'au moins une référence est conservée. Lorsque la dernière référence à la connexion est libérée (en utilisant l'appel sd_bus_unref(3)), la connexion est terminée. Notez que la connexion n'est pas automatiquement terminée lorsque le thread associé se termine. Il est important de libérer la dernière référence à la connexion bus explicitement avant la fin du thread, sinon, la connexion fuira. De plus, les messages mis en file d'attente mais non lus ou non écrits maintiennent une référence au bus, voir ci-dessous.

sd_bus_default_user() retourne un objet de connexion au bus utilisateur associé au thread appelant. sd_bus_default_system() est similaire, mais se connecte au bus système. Notez que sd_bus_default() est identique à ces deux appels, selon le contexte d'exécution.

sd_bus_open() crée une nouvelle connexion de bus indépendante au bus utilisateur lorsqu'il est appelé dans un contexte utilisateur, ou au bus système sinon. sd_bus_open_user() est similaire, mais ne se connecte qu'au bus utilisateur. sd_bus_open_system() fait de même, mais se connecte au bus système. Contrairement à sd_bus_default(), sd_bus_default_user() et sd_bus_default_system(), ces appels retournent de nouveaux objets de connexion indépendants qui ne sont pas associés au thread appelant et ne sont pas partagés entre plusieurs appels. Il est recommandé de partager les connexions par thread pour utiliser efficacement les ressources disponibles. Par conséquent, il est recommandé d'utiliser sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() pour se connecter aux bus utilisateur ou système.

sd_bus_open_with_description(), sd_bus_open_user_with_description() et sd_bus_open_system_with_description() sont similaires à sd_bus_open(), sd_bus_open_user() et sd_bus_open_system(), mais permettent de définir une chaîne de description, voir sd_bus_set_description(3). description peut être NULL, auquel cas cette fonction est équivalente à sd_bus_open(). Cette chaîne de description est utilisée dans les messages de journal concernant l'objet bus, et l'inclusion d'un "nom" pour le bus les rend plus faciles à comprendre. Certains messages sont émis lors de l'initialisation du bus, par conséquent, utiliser cette fonction est préférable à la définition ultérieure de la description avec sd_bus_open_with_description(). L'argument est copié en interne et ne sera pas référencé après le retour de la fonction.

Si la variable d'environnement $DBUS_SESSION_BUS_ADDRESS est définie (cf. environ(7)), elle sera utilisée comme adresse du bus utilisateur. Cette variable peut contenir plusieurs adresses séparées par des ";". Si cette variable n'est pas définie, un défaut approprié pour l'instance D-Bus utilisateur par défaut sera utilisé.

Si la variable d'environnement $DBUS_SYSTEM_BUS_ADDRESS est définie, elle sera utilisée comme adresse du bus système. Cette variable utilise la même syntaxe que $DBUS_SESSION_BUS_ADDRESS. Si cette variable n'est pas définie, un défaut approprié pour l'instance D-Bus système par défaut sera utilisé.

sd_bus_open_system_remote() se connecte au bus système sur l'hôte spécifié en utilisant ssh(1). host se compose d'un nom d'utilisateur optionnel suivi du symbole "@", et du nom d'hôte, optionnellement suivi d'un ":" et d'un port, optionnellement suivi d'un "/" et d'un nom de machine. Si le nom de machine est donné, une connexion est créée au bus système dans le conteneur spécifié sur la machine distante, et sinon une connexion au bus système sur l'hôte spécifié est créée.

Notez que l'entrée dans un conteneur est une opération privilégiée, et ne fonctionnera probablement que pour l'utilisateur root sur la machine distante.

sd_bus_open_system_machine() se connecte au bus système dans la machine spécifiée, où machine est le nom d'un conteneur local, éventuellement préfixé par un nom d'utilisateur et un séparateur "@". Si le nom du conteneur est spécifié comme la chaîne spéciale ".host", la connexion est établie au système local. Ceci est utile pour se connecter au bus système local en tant qu'utilisateur spécifique, par exemple "foobar@.host" pour se connecter au bus système local en tant qu'utilisateur local "foobar". Si la syntaxe "@" est utilisée, le côté gauche ou le côté droit peut être omis (mais pas les deux) auquel cas le nom d'utilisateur local ou ".host" est implicite. Si la syntaxe "@" n'est pas utilisée, la connexion est toujours établie en tant qu'utilisateur root. Voir sd_bus_set_address(3) pour une description de la syntaxe d'adresse, et machinectl(1) pour plus d'informations sur le concept de "machine". Notez que les connexions dans les conteneurs locaux ne sont disponibles que pour les processus privilégiés à l'heure actuelle.

sd_bus_open_user_machine() est similaire à sd_bus_open_system_machine(), mais se connecte au bus utilisateur de l'utilisateur root, ou si la syntaxe "@" est utilisée, de l'utilisateur spécifié.

Ces appels allouent un objet de connexion de bus et initient la connexion à un bus bien connu d'une certaine forme. Une alternative à l'utilisation de ces appels de haut niveau est de créer un objet de bus non connecté avec sd_bus_new(3) et de le connecter avec sd_bus_start(3).

PROPRIÉTÉ DES RÉFÉRENCES

Les fonctions sd_bus_open(), sd_bus_open_user(), sd_bus_open_user_machine(), sd_bus_open_system(), sd_bus_open_system_remote() et sd_bus_open_system_machine() retournent un nouvel objet de connexion et l'appelant possède la seule référence. Lorsqu'elle n'est plus nécessaire, cette référence doit être détruite avec sd_bus_unref(3).

Les fonctions sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() ne créent pas nécessairement un nouvel objet, mais incrémentent la référence de connexion d'un objet de connexion existant d'une unité. Utilisez sd_bus_unref(3) pour libérer la référence.

Les messages mis en file d'attente mais non écrits/non lus conservent une référence à leur objet de connexion bus. Pour cette raison, même si une application a libéré toutes les références à une connexion bus, elle pourrait ne pas être détruite immédiatement. Tant que tous les messages entrants mis en file d'attente n'ont pas été lus, et tant que tous les messages sortants non écrits n'ont pas été envoyés, l'objet bus restera actif. sd_bus_flush() peut être utilisé pour envoyer tous les messages sortants mis en file d'attente afin qu'ils libèrent leurs références. DESCRIPTION

Ces fonctions ouvrent une connexion au bus D-Bus système ou utilisateur. La connexion peut être établie à une machine locale ou à une machine distante (voir sd_bus_open_system_remote(3)).

Les fonctions sd_bus_open_system(), sd_bus_open_user() et sd_bus_open() établissent respectivement une connexion au bus D-Bus système, au bus D-Bus utilisateur ou au bus D-Bus par défaut (défini par la variable d'environnement DBUS_SESSION_BUS_ADDRESS). Ces fonctions tentent d'établir une connexion TCP/IP avec le serveur de bus D-Bus.

Les fonctions sd_bus_default_system(), sd_bus_default_user() et sd_bus_default() sont similaires, mais elles retournent un bus par défaut qui est associé au thread courant. Si le thread courant n'a pas de bus par défaut, un nouveau bus est créé.

Les fonctions sd_bus_open_system_machine() et sd_bus_open_user_machine() établissent une connexion au bus D-Bus d'une machine spécifiée par le paramètre machine. Si machine est NULL, la machine locale est utilisée.

Les fonctions sd_bus_open_system_with_description() et sd_bus_open_user_with_description() sont similaires à sd_bus_open_system() et sd_bus_open_user(), mais elles permettent de spécifier une description de la connexion qui sera utilisée pour le débogage.

RÉFÉRENCE PROPRIÉTÉ

Les fonctions retournent un pointeur vers une structure sd_bus. Le code appelant est responsable de la libération de la connexion D-Bus en utilisant sd_bus_close(3). Après avoir appelé sd_bus_close(3), la connexion est fermée et le pointeur vers la structure sd_bus devient invalide.

Pour les bus par défaut, il est recommandé d'appeler sd_bus_flush(3) suivi de sd_bus_close(3) lorsque le thread ou le processus se termine afin de libérer correctement la connexion.

Normalement, les objets slot (créés par sd_bus_add_match(3) et appels similaires) conservent une référence à leur objet de connexion bus. Ainsi, tant qu'un objet slot bus reste référencé, son objet bus reste alloué. Optionnellement, les objets slot bus peuvent être placés en mode "flottant". En mode flottant, le cycle de vie de l'objet slot bus est lié à l'objet bus, c'est-à-dire que lorsque l'objet bus est libéré, l'objet slot bus est automatiquement déréférencé. L'état flottant d'un objet slot peut être contrôlé explicitement avec sd_bus_slot_set_floating(3), bien que généralement les objets slot bus flottants soient créés en passant NULL comme paramètre slot de sd_bus_add_match(3) et appels associés, indiquant ainsi que l'appelant n'est pas directement intéressé par la référence et la gestion de l'objet slot bus.

Le cycle de vie de la connexion bus par défaut doit être sous la responsabilité du code qui crée/possède le thread auquel l'objet de connexion bus par défaut est associé. Le code de bibliothèque ne doit ni appeler sd_bus_flush(3) ni sd_bus_close(3) sur les objets bus par défaut, sauf s'il le fait dans son propre thread privé et auto-alloué. Le code de bibliothèque ne doit pas utiliser l'objet bus par défaut dans d'autres threads, sauf s'il est clair que le programme qui l'utilise gérera le cycle de vie de l'objet de connexion bus et le videra et le fermera avant de quitter le thread. Dans les bibliothèques où il n'est pas clair que le programme appelant gérera le cycle de vie de l'objet de connexion bus, il est donc recommandé d'utiliser sd_bus_open_system(3) au lieu de sd_bus_default_system(3) et appels associés.

VALEUR DE RETOUR

En cas de succès, ces appels retournent 0 ou un entier positif. En cas d'échec, ces appels retournent un code d'erreur négatif de style errno.

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-EINVAL

Les paramètres spécifiés sont invalides.

-ENOMEDIUM

Le type de bus demandé n'est pas disponible en raison d'un environnement invalide (par exemple, le bus de session utilisateur n'est pas disponible car $XDG_RUNTIME_DIR n'est pas défini).

-ENOMEM

Échec de l'allocation de mémoire.

-ESOCKTNOSUPPORT

La version du protocole requise pour se connecter au bus sélectionné n'est pas prise en charge.

De plus, d'autres erreurs liées à la connexion peuvent être retournées. Voir sd_bus_send(3).

NOTES

Les fonctions décrites ici sont disponibles en tant que bibliothèque partagée, qui peut être compilée et liée avec le fichier pkg-config(1) de libsystemd.

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas sûr pour les threads multiples. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) depuis un thread parallèle. Il est recommandé de ne faire des appels à setenv() que lors d'une phase précoce du programme, lorsque aucun autre thread n'a été démarré.
