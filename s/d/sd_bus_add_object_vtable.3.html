DESCRIPTION

sd_bus_add_object_vtable() est utilisé pour déclarer les attributs du chemin d'objet path connecté à la connexion de bus bus sous l'interface interface. La table vtable peut contenir des déclarations de propriétés utilisant SD_BUS_PROPERTY() ou SD_BUS_WRITABLE_PROPERTY(), des déclarations de méthodes utilisant SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), ou SD_BUS_METHOD_WITH_NAMES_OFFSET(), et des déclarations de signaux utilisant SD_BUS_SIGNAL_WITH_NAMES() ou SD_BUS_SIGNAL(), voir ci-dessous. Le paramètre userdata contient un pointeur qui sera passé à diverses fonctions de rappel. Il peut être spécifié comme NULL si aucune valeur n'est nécessaire. Une interface peut avoir n'importe quel nombre de vtables qui lui sont attachées.

sd_bus_add_fallback_vtable() est similaire à sd_bus_add_object_vtable(), mais est utilisé pour enregistrer des attributs "de secours". Lors de la recherche d'une déclaration d'attribut, les chemins d'objet de bus enregistrés avec sd_bus_add_object_vtable() sont vérifiés en premier. Si aucune correspondance n'est trouvée, les vtables de secours sont vérifiées pour chaque préfixe du chemin d'objet de bus, c'est-à-dire en supprimant successivement les derniers composants séparés par des barres obliques. Cela permet d'utiliser la vtable pour un nombre arbitraire d'objets créés dynamiquement.

Le paramètre find est une fonction utilisée pour localiser l'objet cible en fonction du chemin d'objet de bus path. Elle doit renvoyer 1 et définir le paramètre de sortie ret_found si l'objet est trouvé, renvoyer 0 si l'objet n'a pas été trouvé, et renvoyer un code d'erreur négatif de style errno ou initialiser la structure d'erreur ret_error en cas d'erreur. Le pointeur passé dans ret_found sera utilisé comme paramètre userdata pour les fonctions de rappel (décalé par les décalages offset tels que spécifiés dans les entrées de la vtable).

sd_bus_add_object() attache une fonction de rappel directement au chemin d'objet path. Un chemin d'objet peut avoir n'importe quel nombre de fonctions de rappel qui lui sont attachées. Chaque fonction de rappel est ajoutée au début de la liste des fonctions de rappel qui sont toujours appelées dans l'ordre. sd_bus_add_fallback() est similaire à sd_bus_add_object() mais s'applique aux chemins de secours.

sd_bus_add_filter() installe une fonction de rappel qui est invoquée pour chaque message D-Bus entrant. Les filtres peuvent être utilisés pour gérer une logique commune à tous les messages reçus par un service (par exemple, authentification ou autorisation).

Lorsqu'une requête est reçue, toutes les fonctions de rappel associées sont appelées séquentiellement jusqu'à ce qu'une fonction de rappel renvoie un entier non nul. Renvoyer zéro d'une fonction de rappel pour donner aux autres fonctions de rappel la chance de traiter la requête. Les fonctions de rappel sont appelées dans l'ordre suivant : premièrement, les fonctions de rappel globales installées avec sd_bus_add_filter() sont appelées. Deuxièmement, les fonctions de rappel attachées directement au chemin d'objet de la requête sont appelées, suivies des fonctions de rappel de méthode D-Bus attachées au chemin d'objet de la requête, à l'interface et au membre. Enfin, les fonctions de rappel de propriété attachées au chemin d'objet de la requête, à l'interface et au membre sont appelées. Si la dernière fonction de rappel renvoie zéro, une erreur

Note that you can return a positive integer from a method callback without immediately sending a reply. This informs sd-bus this callback will take responsibility for replying to the request without forcing the callback to produce a reply immediately. This allows a callback to perform any number of asynchronous operations required to construct a reply. However, if producing a reply takes too long, the method call will time out at the caller. This is only available to methods and not properties.

If a callback was invoked to handle a request that expects a reply and the callback returns a negative value, the value is interpreted as a negative errno-style error code and sent back to the caller as a D-Bus error as if sd_bus_reply_method_errno(3) was called. Additionally, all callbacks take a sd_bus_error output parameter that can be used to provide more detailed error information. If ret_error is set when the callback finishes, the corresponding D-Bus error is sent back to the caller as if sd_bus_reply_method_error(3) was called. Any error stored in ret_error takes priority over any negative values returned by the same callback when determining which error to send back to the caller. Use sd_bus_error_set(3) or one of its variants to set ret_error and return a negative integer from a callback with a single function call. To send an error reply after a callback has already finished, use sd_bus_reply_method_errno(3) or one of its variants.

For all functions, a match slot is created internally. If the output parameter slot is NULL, a "floating" slot object is created, see sd_bus_slot_set_floating(3). Otherwise, a pointer to the slot object is returned. In that case, the reference to the slot object should be dropped when the vtable is not needed anymore, see sd_bus_slot_unref(3).

Le tableau sd_bus_vtable

Le tableau est constitué des structures de type sd_bus_vtable, mais il ne doit jamais être rempli manuellement, mais via l'une des macros suivantes :

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Celles-ci doivent toujours être le premier et le dernier élément. Le paramètre flags peut être utilisé pour définir des attributs qui s'appliquent à l'ensemble du tableau ; voir la section "Flags" ci-dessous.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Déclare une méthode D-Bus avec le nom member, les arguments args et le résultat result. args attend une séquence de paires type/nom d'arguments encapsulées dans la macro SD_BUS_ARGS(). Les éléments aux indices pairs de cette liste décrivent les types des arguments de la méthode. La signature des paramètres de la méthode est la concaténation de toutes les littéraux de chaîne aux indices pairs dans args. Si une méthode n'a pas de paramètres, passez SD_BUS_NO_ARGS à args. Les éléments aux indices impairs décrivent les noms des arguments de la méthode. result attend une séquence de paires type/nom encapsulées dans la macro SD_BUS_RESULT() dans le même format que SD_BUS_ARGS(). La signature du résultat de la méthode est la concaténation de toutes les littéraux de chaîne aux indices pairs dans result. Si une méthode n'a pas de résultat, passez SD_BUS_NO_RESULT à result. Notez que les types d'arguments sont attendus comme des littéraux de chaîne entre guillemets et les noms d'arguments comme des littéraux de chaîne non entre guillemets. Voir ci-dessous pour un exemple complet.

La fonction de traitement handler doit être de type sd_bus_message_handler_t. Elle sera appelée pour traiter les messages entrants qui appellent cette méthode. Elle reçoit un pointeur qui est le paramètre userdata passé à la fonction d'enregistrement décalé de offset octets. Cela peut être utilisé pour passer des pointeurs vers différents champs de la même structure de données à différentes méthodes de la même vtable. Pour envoyer une réponse depuis handler, appelez sd_bus_reply_method_return(3) avec le message avec lequel le callback a été appelé. Le paramètre flags est une combinaison de flags, voir ci-dessous.

SD_BUS_METHOD_WITH_ARGS() est un raccourci pour appeler SD_BUS_METHOD_WITH_ARGS_OFFSET() avec un décalage de zéro.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Déclare une méthode D-Bus avec le nom member, la signature de paramètre signature, la signature de résultat result. Les paramètres in_names et out_names spécifient les noms des arguments des arguments d'entrée et de sortie dans la signature de la fonction. in_names et out_names doivent être créés à l'aide de la macro SD_BUS_PARAM(), voir ci-dessous. À tous autres égards, cette macro se comporte exactement comme SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), et SD_BUS_METHOD() sont des variantes qui spécifient un décalage nul (paramètre userdata passé sans changement), laissent les noms non définis (c'est-à-dire pas de noms de paramètres), ou les deux.

Préférez l'utilisation de SD_BUS_METHOD_WITH_ARGS_OFFSET() et SD_BUS_METHOD_WITH_ARGS() à ces macros car elles permettent de spécifier les types et les noms des arguments côte à côte, ce qui est moins sujet aux erreurs que de spécifier d'abord tous les types d'arguments puis tous les noms d'arguments.

SD_BUS_SIGNAL_WITH_ARGS()

Déclare un signal D-Bus avec le nom member et les arguments args. args attend une séquence de paires type/nom d'arguments encapsulées dans la macro SD_BUS_ARGS(). Les éléments aux indices pairs de cette liste décrivent les types des arguments du signal. La signature des paramètres du signal est la concaténation de toutes les littéraux de chaîne aux indices pairs dans args. Si un signal n'a pas de paramètres, passez SD_BUS_NO_ARGS à args. Les éléments aux indices impairs décrivent les noms des arguments du signal. Le paramètre flags est une combinaison de flags. Voir ci-dessous pour un exemple complet.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Déclare un signal D-Bus avec le nom member, la signature de paramètre signature, et les noms d'arguments names. names doit être créé à l'aide de la macro SD_BUS_PARAM(), voir ci-dessous. Le paramètre flags est une combinaison de flags, voir ci-dessous.

SD_BUS_SIGNAL() est équivalent à SD_BUS_SIGNAL_WITH_NAMES() avec le paramètre names non défini (c'est-à-dire pas de noms de paramètres).

Préférez l'utilisation de SD_BUS_SIGNAL_WITH_ARGS() à ces macros car elle permet de spécifier les types et les noms des arguments côte à côte, ce qui est moins sujet aux erreurs que de spécifier d'abord tous les types d'arguments puis tous les noms d'arguments.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Déclare une propriété D-Bus avec le nom member et la signature de valeur signature. Les paramètres get et set sont les méthodes de lecture et d'écriture. Elles sont appelées avec un pointeur qui est le paramètre userdata passé à la fonction d'enregistrement décalé de offset octets. Cela peut être utilisé pour passer des pointeurs vers différents champs de la même structure de données à différents setters et getters de la même vtable. Le paramètre flags est une combinaison de flags, voir ci-dessous.

Les méthodes de lecture et d'écriture peuvent être omises (spécifiées comme NULL), si la propriété est de l'un des types de base ou "as" dans le cas des propriétés en lecture seule. Dans ces cas, les paramètres userdata et offset doivent ensemble pointer vers une variable valide du type correspondant. Un setter et un getter par défaut seront fournis, qui copient simplement l'argument entre cette variable et le message.

SD_BUS_PROPERTY() est utilisé pour définir une propriété en lecture seule.

SD_BUS_PARAM()

Les noms de paramètres doivent être encapsulés dans cette macro, voir l'exemple ci-dessous.

Flags

Le paramètre flags est utilisé pour spécifier une combinaison d'annotations D-Bus[1].

SD_BUS_VTABLE_DEPRECATED

Marque cette entrée vtable comme obsolète en utilisant l'annotation org.freedesktop.DBus.Deprecated dans les données d'introspection. Si spécifié pour SD_BUS_VTABLE_START(), l'annotation est appliquée à l'interface englobante.

SD_BUS_VTABLE_HIDDEN

Rend cette entrée vtable cachée. Elle ne sera pas affichée dans les données d'introspection. Si spécifié pour SD_BUS_VTABLE_START(), toutes les entrées du tableau sont cachées.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marque cette entrée vtable comme une méthode qui ne retournera pas de réponse en utilisant l'annotation org.freedesktop.DBus.Method.NoReply dans les données d'introspection.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Ces trois flags correspondent à différentes valeurs de l'annotation org.freedesktop.DBus.Property.EmitsChangedSignal, qui spécifie si le signal org.freedesktop.DBus.Properties.PropertiesChanged est émis chaque fois que la propriété change. SD_BUS_VTABLE_PROPERTY_CONST correspond à const et signifie que la propriété ne change jamais pendant la durée de vie de l'objet auquel elle appartient, donc aucun signal ne doit être émis. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE correspond à true et signifie que le signal est émis. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION correspond à invalidates et signifie que le signal est émis, mais que la valeur n'est pas incluse dans le signal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marque cette entrée de propriété vtable comme nécessitant une demande explicite pour que la valeur soit affichée (généralement parce que la valeur est volumineuse ou lente à calculer). Cette entrée ne peut pas être combinée avec SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, et ne sera pas affichée dans les listes de propriétés par défaut (par exemple, busctl introspect). Cela correspond à l'annotation org.freedesktop.systemd1.Explicit dans les données d'introspection.

SD_BUS_VTABLE_SENSITIVE

Marque cette entrée de méthode vtable comme traitant des données sensibles. Lorsqu'elle est définie, les messages d'appel de méthode entrants et leurs messages de réponse sortants sont marqués comme sensibles à l'aide de sd_bus_message_sensitive(3), de sorte qu'ils soient effacés de la mémoire lorsqu'ils sont libérés.
