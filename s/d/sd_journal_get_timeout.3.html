NOM

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interface de notification des changements du journal

SYNTAXE

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

sd_journal_get_fd() renvoie un descripteur de fichier qui peut être sondé de manière asynchrone dans une boucle d'événements externe et qui est signalé dès que le journal change, car de nouvelles entrées ou fichiers ont été ajoutés, une rotation a eu lieu, ou des fichiers ont été supprimés, etc. Le descripteur de fichier est approprié pour une utilisation dans poll(2). Utilisez sd_journal_get_events() pour un masque d'événements à surveiller. L'appel prend un argument : l'objet de contexte du journal. Notez que tous les systèmes de fichiers ne sont pas capables de générer les événements nécessaires pour que les réveils depuis ce descripteur de fichier remarquent immédiatement les changements. En particulier, les systèmes de fichiers réseau ne génèrent pas toujours les événements de modification de fichier appropriés. De tels cas peuvent être détectés avec sd_journal_reliable_fd(), ci-dessous. sd_journal_get_timeout() garantira dans ces cas que les réveils se produisent suffisamment fréquemment pour que les changements soient remarqués, bien qu'avec une certaine latence.

sd_journal_get_events() renverra le masque poll() à attendre. Cette fonction renverra une combinaison de POLLIN et POLLOUT et similaires à remplir dans le champ ".events" de struct pollfd.

sd_journal_get_timeout() renverra une valeur de délai d'attente pour utilisation dans poll(). Ceci renvoie une valeur en microsecondes depuis l'époque de CLOCK_MONOTONIC pour le délai d'attente de poll() dans timeout_usec. Voir clock_gettime(2) pour les détails sur CLOCK_MONOTONIC. S'il n'y a pas de délai d'attente à attendre, ceci remplira (uint64_t) -1 à la place. Notez que poll() prend un délai d'attente relatif en millisecondes plutôt qu'un délai d'attente absolu en microsecondes. Pour convertir le délai d'attente absolu 'us' en délai relatif 'ms', utilisez un code comme le suivant :

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

Le code ci-dessus ne fait aucun contrôle d'erreur par souci de brièveté. L'entier msec calculé peut être passé directement comme paramètre de délai d'attente de poll().

Après chaque réveil de poll(), sd_journal_process() doit être appelé pour traiter les événements. Cet appel indiquera également quel type de changement a été détecté (voir ci-dessous ; notez que les réveils fantaisistes sont possibles).

Une alternative synchrone à l'utilisation de sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() et sd_journal_process() est sd_journal_wait(). Il attendra de manière synchrone jusqu'à ce que le journal soit modifié. Le temps maximum pendant lequel cet appel dort peut être contrôlé avec le paramètre timeout_usec. Passez (uint64_t) -1 pour attendre indéfiniment. En interne, cet appel combine simplement sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() et sd_journal_process() en un seul.

sd_journal_reliable_fd() peut être utilisé pour vérifier si les événements de réveil du descripteur de fichier renvoyé par sd_journal_get_fd() sont connus pour être déclenchés rapidement. Sur certains systèmes de fichiers où les événements de modification de fichier de l'OS ne sont pas disponibles (comme NFS), les changements doivent être sondés de manière répétée, et sont donc détectés seulement avec une latence considérable. Cet appel renverra une valeur positive si les changements du journal sont détectés rapidement et zéro si un sondage est nécessaire. Notez qu'il n'est généralement pas nécessaire d'invoquer cette fonction directement, car sd_journal_get_timeout() demandera des délais d'attente appropriés de toute façon.

Notez que toutes les interfaces de notification de changement ci-dessus ne rapportent pas les changements instantanément. Des latences sont introduites pour plusieurs raisons : comme mentionné, certains backends de stockage nécessitent un sondage basé sur le temps, dans d'autres cas, les réveils sont optimisés en regroupant les événements, et l'OS introduit des latences de planification d'IO/CPU supplémentaires.

VALEUR DE RETOUR

sd_journal_get_fd() renvoie un descripteur de fichier valide en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_get_events() renvoie une combinaison de POLLIN, POLLOUT et similaires en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_reliable_fd() renvoie un entier positif si le descripteur de fichier renvoyé par sd_journal_get_fd() déclenchera des réveils immédiats pour tous les changements du journal. Renvoie 0 s'il peut y avoir une latence.

sd_journal_process() et sd_journal_wait() renvoient un code d'erreur négatif de style errno, ou l'un de SD_JOURNAL_NOP, SD_JOURNAL_APPEND ou SD_JOURNAL_INVALIDATE en cas de succès :

•Si SD_JOURNAL_NOP est renvoyé, le journal n'a pas changé depuis la dernière invocation.
•Si SD_JOURNAL_APPEND est renvoyé, de nouvelles entrées ont été ajoutées à la fin du journal. Dans ce cas, il suffit de continuer à lire à l'emplacement précédent de la fin du journal pour lire les entrées nouvellement ajoutées.
•Si SD_JOURNAL_INVALIDATE, des fichiers du journal ont été ajoutés ou retirés de l'ensemble des fichiers du journal surveillés (par exemple, en raison d'une rotation ou d'un nettoyage), et donc des entrées ont pu apparaître ou disparaître à des endroits arbitraires dans le flux de log, potentiellement avant ou après l'ancienne fin du flux de log. Si SD_JOURNAL_INVALIDATE est renvoyé, les interfaces utilisateur en vue en direct qui souhaitent refléter à l'écran l'état précis des données de log sur le disque devraient probablement rafraîchir leur affichage complet (par rapport au curseur de l'entrée de log en haut de l'écran). Les programmes uniquement intéressés par un flux de données de log strictement séquentiel peuvent traiter SD_JOURNAL_INVALIDATE de la même manière que SD_JOURNAL_APPEND, ignorant ainsi tout changement dans la vue de log antérieur à l'ancienne fin du flux de log.

SÉCURITÉ DES SIGNAUX

En général, sd_journal_get_fd(), sd_journal_get_events(), et sd_journal_get_timeout() ne sont pas "async signal safe" au sens de signal-safety(7). Néanmoins, seul le premier appel à l'une de ces trois fonctions effectue des opérations non sûres, donc les appels subsquents *sont* sûrs.

sd_journal_process() et sd_journal_wait() ne sont pas sûrs. sd_journal_reliable_fd() est sûr.

NOTES

Toutes les fonctions listées ici sont indépendantes des threads et un seul thread peut opérer sur un objet donné à un moment donné. Différents threads peuvent accéder au même objet à différents moments. Plusieurs objets indépendants peuvent être utilisés à partir de différents threads en parallèle.

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

NAME

sd_journal_get_timeout - Obtenir le délai avant expiration pour l'attente des nouvelles entrées

SYNOPSIS

#include <systemd/sd-journal.h>

uint64_t sd_journal_get_timeout(sd_journal *j);

DESCRIPTION

La fonction sd_journal_get_timeout() renvoie le délai avant expiration suggéré, en microsecondes, pour l'attente de nouvelles entrées dans le journal. Si la valeur renvoyée est (uint64_t) -1, cela signifie qu'il n'y a pas de délai avant expiration et que le programme doit attendre indéfiniment.

Ce délai avant expiration est destiné à être utilisé avec des appels système tels que poll(2) ou select(2) pour déterminer quand vérifier s'il y a de nouvelles entrées disponibles dans le journal avant d'attendre potentiellement indéfiniment avec sd_journal_wait(). La valeur renvoyée est le délai avant expiration le plus court parmi tous les fichiers de journal ouverts.

Si l'on utilise sd_journal_wait() pour attendre des entrées, la valeur suggérée peut être utilisée comme argument de temps pour la fonction sd_journal_wait() afin de se synchroniser avec le temps de délai avant expiration utilisé par sd_journal_get_timeout().

Utilisez sd_journal_get_events() pour obtenir les événements qui devraient être surveillés avec poll() sur le descripteur de fichier renvoyé par sd_journal_get_fd().

RETURN VALUE

En cas de succès, renvoie le délai avant expiration suggéré en microsecondes. Si la valeur est (uint64_t) -1, il n'y a pas de délai avant expiration.

SIGNAL SAFETY

sd_journal_get_timeout() est sûr à utiliser à partir de gestionnaires de signaux.

NOTES

Les fonctions sd_journal_get_timeout() et sd_journal_get_events() ont été introduites dans la version 201 du système.

La valeur renvoyée est le délai avant expiration le plus court parmi tous les fichiers de journal actuellement ouverts. Le délai avant expiration est calculé par rapport à CLOCK_MONOTONIC.

EXAMPLES

Exemple 1. Attendre des modifications avec sd_journal_wait() et poll()

Cet exemple utilise sd_journal_wait() pour attendre jusqu'à ce que de nouvelles entrées soient disponibles, ou jusqu'à ce que le délai avant expiration soit atteint.

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int main(int argc, char *argv[]) {
  sd_journal *j = NULL;
  sd_journal_open_container(&j, argv[1]);
  if (!j) {
    fprintf(stderr, "Failed to open journal\n");
    return 1;
  }
  int r = sd_journal_seek_tail(j);
  if (r < 0) {
    fprintf(stderr, "Failed to seek to tail: %s\n", strerror(-r));
    goto finish;
  }
  for (;;) {
    r = sd_journal_next(j);
    if (r < 0) {
      fprintf(stderr, "Failed to advance cursor: %s\n", strerror(-r));
      break;
    }
    if (r == 0) {
      /* At the end, let's wait for changes, and try again */
      r = sd_journal_wait(j, (uint64_t) -1);
      if (r < 0) {
        fprintf(stderr, "Failed to wait for changes: %s\n", strerror(-r));
        break;
      }
      continue;
    }
    r = sd_journal_get_data(j, "MESSAGE", &d, &l);
    if (r < 0) {
      fprintf(stderr, "Failed to read message field: %s\n", strerror(-r));
      continue;
    }
    printf("%.*s\n", (int) l, (const char*) d);
  }
finish:
  sd_journal_close(j);
  return 0;
}

Attendre avec poll() (cet exemple manque de toute vérification d'erreurs par souci de simplicité) :

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int wait_for_changes(sd_journal *j) {
  uint64_t t;
  int msec;
  struct pollfd pollfd;
  sd_journal_get_timeout(j, &t);
  if (t == (uint64_t) -1)
    msec = -1;
  else {
    struct timespec ts;
    uint64_t n;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
    msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
  }
  pollfd.fd = sd_journal_get_fd(j);
  pollfd.events = sd_journal_get_events(j);
  poll(&pollfd, 1, msec);
  return sd_journal_process(j);
}
