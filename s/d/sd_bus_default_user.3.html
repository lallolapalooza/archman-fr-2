SD_BUS_DEFAULT(3) sd_bus_default SD_BUS_DEFAULT(3)

NOM

SYNOPSIS

#include <systemd/sd-bus.h>

int sd_bus_default(sd_bus **bus);

int sd_bus_default_user(sd_bus **bus);

int sd_bus_default_system(sd_bus **bus);

int sd_bus_open(sd_bus **bus);

int sd_bus_open_with_description(sd_bus **bus, const char *description);

int sd_bus_open_user(sd_bus **bus);

int sd_bus_open_user_with_description(sd_bus **bus, const char *description);

int sd_bus_open_user_machine(sd_bus **bus, const char *machine);

int sd_bus_open_system(sd_bus **bus);

int sd_bus_open_system_with_description(sd_bus **bus, const char *description);

int sd_bus_open_system_remote(sd_bus **bus, const char *host);

int sd_bus_open_system_machine(sd_bus **bus, const char *machine);

DESCRIPTION

sd_bus_default() acquiert un objet de connexion de bus vers le bus utilisateur lorsqu'il est appelé depuis une tranche utilisateur (toute session sous "user-*.slice", par exemple : "user@1000.service"), ou vers le bus système sinon. L'objet de connexion est associé au thread appelant. Chaque fois que la fonction est invoquée depuis le même thread, le même objet est retourné, mais son compteur de références est incrémenté d'une unité, tant qu'au moins une référence est conservée. Lorsque la dernière référence à la connexion est supprimée (en utilisant l'appel sd_bus_unref(3)), la connexion est terminée. Notez que la connexion n'est pas automatiquement terminée lorsque le thread associé se termine. Il est important de supprimer explicitement la dernière référence à la connexion de bus avant la fin du thread, sinon la connexion fuira. De plus, les messages mis en file d'attente mais non lus ou non écrits conservent une référence au bus, voir ci-dessous.

sd_bus_default_user() retourne un objet de connexion de bus utilisateur associé au thread appelant. sd_bus_default_system() est similaire, mais se connecte au bus système. Notez que sd_bus_default() est identique à ces deux appels, en fonction du contexte d'exécution.

sd_bus_open() crée une nouvelle connexion de bus indépendante vers le bus utilisateur lorsqu'il est appelé dans le contexte utilisateur, ou vers le bus système sinon. sd_bus_open_user() est similaire, mais ne se connecte qu'au bus utilisateur. sd_bus_open_system() fait de même, mais se connecte au bus système. Contrairement à sd_bus_default(), sd_bus_default_user(), et sd_bus_default_system(), ces appels retournent de nouveaux objets de connexion indépendants qui ne sont pas associés au thread appelant et ne sont pas partagés entre plusieurs invocations. Il est recommandé de partager les connexions par thread pour utiliser efficacement les ressources disponibles. Par conséquent, il est recommandé d'utiliser sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() pour se connecter aux bus utilisateur ou système.

sd_bus_open_with_description(), sd_bus_open_user_with_description(), et sd_bus_open_system_with_description() sont similaires à sd_bus_open(), sd_bus_open_user(), et sd_bus_open_system(), mais permettent de définir une chaîne de description, voir sd_bus_set_description(3). description peut être NULL, dans ce cas cette fonction est équivalente à sd_bus_open(). Cette chaîne de description est utilisée dans les messages de journal concernant l'objet de bus, et inclure un "nom" pour le bus les rend plus faciles à comprendre. Certains messages sont émis lors de l'initialisation du bus, par conséquent, l'utilisation de cette fonction est préférable à la définition de la description ultérieurement avec sd_bus_open_with_description(). L'argument est copié en interne et ne sera pas référencé après le retour de la fonction.

Si la variable d'environnement $DBUS_SESSION_BUS_ADDRESS est définie (cf. environ(7)), elle sera utilisée comme adresse du bus utilisateur. Cette variable peut contenir plusieurs adresses séparées par des ";". Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance D-Bus utilisateur par défaut sera utilisée.

Si la variable d'environnement $DBUS_SYSTEM_BUS_ADDRESS est définie, elle sera utilisée comme adresse du bus système. Cette variable utilise la même syntaxe que $DBUS_SESSION_BUS_ADDRESS. Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance D-Bus système par défaut sera utilisée.

sd_bus_open_system_remote() se connecte au bus système sur la machine spécifiée en utilisant ssh(1). host consiste en un nom d'utilisateur optionnel suivi du symbole "@", et le nom d'hôte, éventuellement suivi d'un ":" et d'un port, éventuellement suivi d'un "/" et d'un nom de machine. Si le nom de machine est donné, une connexion est établie vers le bus système dans le conteneur spécifié sur la machine distante, et sinon une connexion vers le bus système sur la machine spécifiée est établie.

Notez que l'entrée dans un conteneur est une opération privilégiée, et ne fonctionnera probablement que pour l'utilisateur root sur la machine distante.

sd_bus_open_system_machine() se connecte au bus système dans la machine spécifiée, où machine est le nom d'un conteneur local, éventuellement préfixé par un nom d'utilisateur et un séparateur "@". Si le nom du conteneur est spécifié comme la chaîne spéciale ".host" la connexion est établie vers le système local. Ceci est utile pour se connecter au bus système local en tant qu'utilisateur spécifique, par exemple "foobar@.host" pour se connecter au bus système local en tant qu'utilisateur local "foobar". Si la syntaxe "@" est utilisée, soit la partie gauche, soit la partie droite peut être omise (mais pas les deux) auquel cas le nom d'utilisateur local ou ".host" est implicite. Si la syntaxe "@" n'est pas utilisée, la connexion est toujours établie en tant qu'utilisateur root. Voir sd_bus_set_address(3) pour une description de la syntaxe d'adresse, et machinectl(1) pour plus d'informations sur le concept de "machine". Notez que les connexions vers les conteneurs locaux ne sont actuellement disponibles que pour les processus privilégiés.

sd_bus_open_user_machine() est similaire à sd_bus_open_system_machine(), mais se connecte au bus utilisateur de l'utilisateur root, ou si la syntaxe "@" est utilisée, de l'utilisateur spécifié.

Ces appels allouent un objet de connexion de bus et initient la connexion à un bus bien connu d'une forme ou d'une autre. Une alternative à l'utilisation de ces appels de haut niveau est de créer un objet de bus non connecté avec sd_bus_new(3) et de le connecter avec sd_bus_start(3).

PROPRIÉTÉ DES RÉFÉRENCES

Les fonctions sd_bus_open(), sd_bus_open_user(), sd_bus_open_user_machine(), sd_bus_open_system(), sd_bus_open_system_remote(), et sd_bus_open_system_machine() retournent un nouvel objet de connexion et l'appelant détient la seule référence. Lorsque cette référence n'est plus nécessaire, elle doit être détruite avec sd_bus_unref(3).

Les fonctions sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() ne créent pas nécessairement un nouvel objet, mais incrémentent le compteur de références d'une connexion existante d'une unité. Utilisez sd_bus_unref(3) pour supprimer la référence.

Les messages mis en file d'attente mais non écrits/lus conservent une référence à leur objet de connexion de bus. Pour cette raison, même si une application a supprimé toutes les références à une connexion de bus, elle pourrait ne pas être détruite immédiatement. Jusqu'à ce que tous les messages entrants en file d'attente soient lus, et jusqu'à ce que tous les messages sortants non écrits soient envoyés, l'objet de bus restera actif. sd_bus_flush() peut être utilisé pour envoyer tous les messages sortants en file d'attente afin qu'ils libèrent leurs références. DESCRIPTION

These functions may be used to obtain a connection to a D-Bus instance. The bus instance is returned in the memory of the bus parameter, which must be a pointer to a sd_bus pointer.

The following bus instances are available:

sd_bus_default_user(), sd_bus_open_user(), sd_bus_open_user_with_description(): Connect to the user session bus instance of the calling user. This is the default bus instance used by user applications. It is automatically created when first accessed and shut down when no longer referenced.

sd_bus_default_system(), sd_bus_open_system(), sd_bus_open_system_with_description(): Connect to the system-wide message bus instance. This bus is typically used by system services and privileged applications. It is always available and is not shut down when no longer referenced.

sd_bus_default_login(), sd_bus_open_session(), sd_bus_open_session_with_description(): Connect to the session bus instance. This is similar to the user bus but is associated with a specific login session, not just a user. It may be used for inter-process communication within a login session.

sd_bus_default_machine(), sd_bus_open_system_machine(), sd_bus_open_user_machine(), sd_bus_open_system_machine_with_description(), sd_bus_open_user_machine_with_description(): Connect to the D-Bus instance of a specific systemd-nspawn container or virtual machine. This requires the machine parameter to specify the name of the container or VM. These functions are primarily intended for use by systemd itself and tools like machinectl(1).

sd_bus_default_user_blocker(), sd_bus_open_user_blocker(), sd_bus_open_user_blocker_with_description(): Connect to the user session bus instance, but specifically for blocking operations (e.g. shutdown). This bus instance is managed separately and is intended for services that need to participate in system state changes.

sd_bus_default_system_blocker(), sd_bus_open_system_blocker(), sd_bus_open_system_blocker_with_description(): Connect to the system bus instance, for blocking operations. Similar to the user blocker bus, but for system-level blocking.

sd_bus_default_kernel(), sd_bus_open_kernel(), sd_bus_open_kernel_with_description(): Connect to the kernel's netlink interface, which is exposed via a special D-Bus mechanism. This is used for low-level kernel event monitoring.

sd_bus_default_background(), sd_bus_open_background(), sd_bus_open_background_with_description(): Connect to a special "background" bus instance. This is typically used by systemd itself for internal communication and management tasks. It is not intended for general application use.

sd_bus_open(): This is a convenience function that attempts to connect to the user bus first, and if that fails, connects to the system bus. This is useful for applications that can run either as a user service or a system service.

sd_bus_open_system_remote(): Connects to the system bus of a remote host specified by the SSH_CONNECTION environment variable. This is typically used when connecting via SSH.

sd_bus_open_with_description(), sd_bus_open_user_with_description(), sd_bus_open_system_with_description(), and their variants: These functions allow specifying a custom description string for the bus connection. This description is primarily used for logging and debugging purposes.

sd_bus_new(): This is a generic function to create a new, uninitialized sd_bus object. It is usually not used directly, but rather as a base for more specific functions like sd_bus_open().

These functions return a reference to a sd_bus object. This reference must be released by calling sd_bus_unref(3).

If you use the default bus connection provided by the library (i.e., by calling sd_bus_default_*()), you should be aware of the bus connection's lifecycle. The default bus connection is automatically managed by the library. You should not call sd_bus_close(3) on these connections unless you are managing the bus connection's lifecycle yourself, for example, in a dedicated thread.

For libraries, it is generally recommended to use sd_bus_open_system() or sd_bus_open_user() instead of the sd_bus_default_*() functions. This gives the calling application full control over the bus connection's lifecycle.

REFERENCE OWNERSHIP

The bus connection objects returned by the functions described here are reference counted. You should call sd_bus_ref(3) to increment the reference count and sd_bus_unref(3) to decrement it. When the reference count reaches zero, the bus connection object is destroyed and the underlying D-Bus connection is closed.

When a thread or process terminates, its bus connection object should be properly closed and freed. It is recommended to first invoke sd_bus_flush(3) followed by sd_bus_close(3).

Normally, slot objects (as created by sd_bus_add_match(3) and similar calls) keep a reference to their bus connection object, too. Thus, as long as a bus slot object remains referenced its bus object will remain allocated too. Optionally, bus slot objects may be placed in "floating" mode. When in floating mode the life cycle of the bus slot object is bound to the bus object, i.e. when the bus object is freed the bus slot object is automatically unreferenced too. The floating state of a slot object may be controlled explicitly with sd_bus_slot_set_floating(3), though usually floating bus slot objects are created by passing NULL as the slot parameter of sd_bus_add_match() and related calls, thus indicating that the caller is not directly interested in referencing and managing the bus slot object.

The life cycle of the default bus connection should be the responsibility of the code that creates/owns the thread the default bus connection object is associated with. Library code should neither call sd_bus_flush() nor sd_bus_close() on default bus objects unless it does so in its own private, self-allocated thread. Library code should not use the default bus object in other threads unless it is clear that the program using it will life cycle the bus connection object and flush and close it before exiting from the thread. In libraries where it is not clear that the calling program will life cycle the bus connection object, it is hence recommended to use sd_bus_open_system() instead of sd_bus_default_system() and related calls.

RETURN VALUE

On success, these calls return 0 or a positive integer. On failure, these calls return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

The specified parameters are invalid.

-ENOMEDIUM

The requested bus type is not available because of invalid environment (for example the user session bus is not available because $XDG_RUNTIME_DIR is not set).

-ENOMEM

Memory allocation failed.

-ESOCKTNOSUPPORT

The protocol version required to connect to the selected bus is not supported.

In addition, other connection-related errors may be returned. See sd_bus_send(3).

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
