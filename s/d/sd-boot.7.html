NOM

systemd-boot, sd-boot - Un gestionnaire de démarrage UEFI simple

DESCRIPTION

systemd-boot (abrégé : sd-boot) est un gestionnaire de démarrage UEFI simple. Il fournit un menu textuel pour sélectionner l'entrée à démarrer et un éditeur pour la ligne de commande du noyau. systemd-boot prend en charge uniquement les systèmes avec un firmware UEFI.

systemd-boot charge les informations d'entrée de démarrage à partir de la partition système EFI (ESP), généralement montée sur /efi/, /boot/, ou /boot/efi/ au moment de l'exécution du système d'exploitation, ainsi que depuis la partition Extended Boot Loader (XBOOTLDR) si elle existe (généralement montée sur /boot/). Les fragments de fichiers de configuration, les noyaux, les initrds et autres images EFI à démarrer doivent généralement résider sur l'ESP ou la partition Extended Boot Loader. Les noyaux Linux doivent être compilés avec CONFIG_EFI_STUB pour pouvoir être exécutés directement comme image EFI. Pendant le démarrage, systemd-boot assemble automatiquement une liste d'entrées de démarrage à partir des sources suivantes :

•Entrées de démarrage définies avec les fichiers de description de type #1 de la Spécification du chargeur de démarrage[1] situés dans /loader/entries/ sur l'ESP et la partition Extended Boot Loader. Ceux-ci décrivent généralement des images de noyau Linux avec des images initrd associées, mais peuvent alternativement décrire d'autres exécutables EFI arbitraires.
•Images de noyau unifiées, type #2 de la Spécification du chargeur de démarrage[1], qui sont des binaires EFI exécutables dans /EFI/Linux/ sur l'ESP et la partition Extended Boot Loader.
•Le gestionnaire de démarrage EFI de Microsoft Windows, s'il est installé.
•Le gestionnaire de démarrage EFI de Apple macOS, s'il est installé.
•Le binaire EFI Shell, s'il est installé.
•Une option « Redémarrer vers l'interface du firmware », si prise en charge par le firmware UEFI.
•L'enrôlement des variables Secure Boot si le firmware UEFI est en mode de configuration et que des fichiers sont fournis sur l'ESP.

systemd-boot prend en charge les fonctionnalités suivantes :

•Les modifications de configuration de base du gestionnaire de démarrage (telles que la configuration du délai d'attente, la sélection de l'entrée de démarrage par défaut, ...) peuvent être effectuées directement depuis l'interface utilisateur du chargeur de démarrage au moment du démarrage, ainsi qu'au moment de l'exécution du système avec les variables EFI.
•Le gestionnaire de démarrage s'intègre avec la commande systemctl pour implémenter des fonctionnalités telles que systemctl reboot --boot-loader-entry=... (pour redémarrer vers une entrée spécifique du menu de démarrage, c'est-à-dire « redémarrer vers Windows ») et systemctl reboot --boot-loader-menu=... (pour redémarrer vers le menu du chargeur de démarrage), en implémentant l'Interface du chargeur de démarrage[2]. Voir systemctl(1) pour plus de détails.
•Une variable EFI définie par le chargeur de démarrage informe le système d'exploitation de l'ESP utilisée pendant le démarrage. Ceci est ensuite utilisé pour monter automatiquement la bonne ESP sur /efi/ ou /boot/ pendant l'exécution du système d'exploitation. Voir systemd-gpt-auto-generator(8) pour plus de détails.
•Le gestionnaire de démarrage fournit des informations sur le temps de démarrage passé dans le firmware UEFI en utilisant l'Interface du chargeur de démarrage[2]. Ces informations peuvent être affichées en utilisant systemd-analyze(1).
•Le gestionnaire de démarrage implémente le comptage des démarrages et le repli automatique vers d'anciennes entrées de démarrage qui fonctionnent en cas d'échec. Voir Évaluation automatique du démarrage[3].
•Le gestionnaire de démarrage lit optionnellement une graine aléatoire depuis la partition ESP, la combine avec un 'token système' stocké dans une variable EFI persistante et dérive une graine aléatoire à utiliser par le système d'exploitation comme initialisation du pool d'entropie, fournissant un pool d'entropie complet pendant le démarrage précoce.
•Le gestionnaire de démarrage permet l'enrôlement des variables Secure Boot si le firmware UEFI est en mode de configuration. De plus, les variables peuvent être automatiquement enrôlées si configurées.

bootctl(1) peut être utilisé depuis un système en cours d'exécution pour localiser l'ESP et la partition Extended Boot Loader, lister les entrées disponibles, et installer systemd-boot lui-même.

kernel-install(8) peut être utilisé pour copier les images de noyau sur l'ESP ou la partition Extended Boot Loader et pour générer des fichiers de description conformes à la Spécification du chargeur de démarrage.

systemd-stub(7) peut être utilisé comme stub de démarrage UEFI pour les noyaux exécutés, ce qui est utile pour afficher des éclaboussures de démarrage graphiques avant de passer au monde Linux. Il est également capable de récupérer automatiquement des fichiers de justificatifs auxiliaires (pour la paramétrisation du démarrage) et des images d'extension système, en tant que fichiers compagnons aux images de noyau démarrées.

FICHIERS

Les fichiers que systemd-boot traite résident généralement sur l'ESP UEFI, qui est généralement monté sur /efi/, /boot/ ou /boot/efi/ pendant l'exécution du système d'exploitation. Il traite également les fichiers sur la partition Extended Boot Loader, qui est généralement montée sur /boot/, si elle existe.

systemd-boot lit la configuration d'exécution telle que le délai d'attente de démarrage et l'entrée par défaut à partir de /loader/loader.conf sur l'ESP (en combinaison avec les données lues à partir des variables EFI). Voir loader.conf(5).

Les fichiers de description des entrées de démarrage suivant la spécification du chargeur de démarrage[1] sont lus à partir de /loader/entries/ sur l'ESP et la partition Extended Boot Loader.

Les entrées de démarrage de noyau unifié suivant la spécification du chargeur de démarrage[1] sont lues à partir de /EFI/Linux/ sur l'ESP et la partition Extended Boot Loader.

Facultativement, une graine aléatoire pour la provision de pool d'entropie de démarrage précoce est stockée dans /loader/random-seed sur l'ESP.

Lors de l'initialisation, sd-boot charge automatiquement tous les fichiers de pilotes placés dans le répertoire /EFI/systemd/drivers/ de l'ESP. Les fichiers placés là doivent avoir une extension de l'identifiant d'architecture EFI suivi de .efi (par exemple, pour x86-64, cela signifie un suffixe de x64.efi). Cela peut être utilisé pour charger automatiquement les pilotes de système de fichiers et similaires, afin d'étendre le support natif du firmware.

L'inscription des variables de démarrage sécurisé peut être effectuée manuellement ou automatiquement si des fichiers sont disponibles sous /loader/keys/NOM/{db,dbx,KEK,PK}.auth, NOM étant le nom d'affichage de l'ensemble de variables dans le menu. Si l'un des ensembles est nommé auto, il peut être inscrit automatiquement en fonction de si "secure-boot-enroll" est défini sur force ou non.

VARIABLES EFI

Les variables EFI suivantes sont définies et peuvent être définies ou lues par systemd-boot pour la communication entre le chargeur de démarrage et le système d'exploitation. L'UUID du fournisseur "4a67b082-0a4c-41cf-b6c7-440b29bb8c4f" est utilisé dans tous les cas.

LoaderBootCountPath

Si le comptage des démarrages est activé, contient le chemin d'accès au fichier dans le nom duquel les compteurs de démarrage sont encodés. Défini par le chargeur de démarrage. systemd-bless-boot.service(8) utilise ces informations pour marquer un démarrage comme réussi, tel que déterminé par l'activation réussie de l'unité cible boot-complete.target.

Ajouté dans la version 240.

LoaderConfigTimeout, LoaderConfigTimeoutOneShot

Le délai d'attente du menu en secondes. Lu par le chargeur de démarrage. LoaderConfigTimeout est maintenu de manière persistante, tandis que LoaderConfigTimeoutOneShot est une substitution unique qui est lue une fois (auquel cas elle a la priorité sur LoaderConfigTimeout) puis supprimée. LoaderConfigTimeout peut être manipulé avec les touches t/T, voir ci-dessus.

Ajouté dans la version 240.

LoaderConfigConsoleMode

Le mode console numérique du menu. Lu par le chargeur de démarrage. LoaderConfigConsoleMode est maintenu de manière persistante. LoaderConfigConsoleMode peut être manipulé avec les touches r/R, voir ci-dessus.

Ajouté dans la version 250.

LoaderDevicePartUUID

Contient l'UUID de la partition à partir de laquelle le chargeur de démarrage a été démarré lors du démarrage actuel (généralement une partition système EFI). Défini par le chargeur de démarrage. (Notez que systemd-stub(7) définira également ceci, s'il n'est pas encore défini, pour prendre en charge les systèmes qui démarrent directement dans une image de noyau unifiée, contournant tout chargeur de démarrage.) systemd-gpt-auto-generator(8) utilise ces informations pour trouver automatiquement le disque à partir duquel il a démarré, afin de découvrir automatiquement diverses autres partitions sur le même disque.

Ajouté dans la version 220.

LoaderDeviceURL

Si le chargeur de démarrage a été invoqué via un démarrage réseau, cette variable contient l'URL d'origine. Ceci peut être utilisé pour acquérir automatiquement des ressources supplémentaires de la même source.

Ajouté dans la version 258.

LoaderEntries

Une liste des identifiants de toutes les entrées du chargeur de démarrage découvertes. Défini par le chargeur de démarrage.

Ajouté dans la version 240.

LoaderEntryDefault, LoaderEntrySysFail, LoaderEntryOneShot

L'identifiant de l'entrée de chargeur de démarrage par défaut. Peut être défini dans le système d'exploitation et le chargeur de démarrage. LoaderEntryOneShot définit l'entrée par défaut uniquement pour le prochain démarrage, tandis que LoaderEntryDefault la définit de manière persistante pour tous les démarrages futurs. Les commandes set-default et set-oneshot de bootctl(1) utilisent ces variables. Le chargeur de démarrage modifie LoaderEntryDefault sur demande, lorsque la touche d est utilisée, voir ci-dessus.

Ajouté dans la version 240.

LoaderEntryLastBooted

L'identifiant de l'entrée du chargeur de démarrage tentée en dernier. Défini et lu par le chargeur de démarrage, uniquement lorsque /loader/loader.conf a la valeur par défaut définie sur "@saved". Voir loader.conf(5).

Le chargeur de démarrage s'assurera que LoaderEntryLastBooted est à jour pour chaque démarrage, le mettant à jour si nécessaire et omettra de le modifier entièrement lorsque LoaderEntryOneShot est défini.

Le chargeur de démarrage lit la variable, qui a une priorité plus élevée que LoaderEntryDefault. La variable est ignorée lorsque LoaderEntryOneShot est défini.

LoaderEntryLastBooted ne peut pas être utilisé comme indication que le dernier démarrage a réussi ou non.

Ajouté dans la version 250.

LoaderEntrySelected

L'identifiant de l'entrée du chargeur de démarrage en cours de démarrage. Défini par le chargeur de démarrage.

Ajouté dans la version 240.

Un ensemble d'indicateurs indiquant les fonctionnalités prises en charge par le chargeur de démarrage. Défini par le chargeur de démarrage. Utilisez bootctl(1) pour afficher ces données.

Ajouté dans la version 240.

LoaderFirmwareInfo, LoaderFirmwareType

Si aucun support TPM2 ou aucune banque active n'a été détecté, sera défini sur 0. Défini par le chargeur de démarrage. Utilisez systemd-analyze(1) pour afficher ces données.

Le chemin d'accès au système de fichiers de l'exécutable EFI du chargeur de démarrage pour le démarrage actuel, relatif au répertoire racine de la partition (c'est-à-dire relatif à la partition indiquée par LoaderDevicePartUUID, voir ci-dessus). Défini par le chargeur de démarrage. (Notez que systemd-stub définira également ceci, s'il n'est pas encore défini, pour prendre en charge les systèmes qui démarrent directement dans une image de noyau unifiée, contournant tout chargeur de démarrage.) Utilisez bootctl(1) pour afficher ces données.

LoaderInfo

Informations succinctes sur le chargeur de démarrage. Défini par le chargeur de démarrage. Utilisez bootctl(1) pour afficher ces données.

LoaderTimeExecUSec, LoaderTimeInitUSec, LoaderTimeMenuUsec

Informations sur le temps passé dans diverses parties du chargeur de démarrage. Défini par le chargeur de démarrage. Utilisez systemd-analyze(1) pour afficher ces données.

Ajouté dans la version 240.

LoaderSystemToken

Un champ de données aléatoires binaires, utilisé pour générer la graine aléatoire à passer au système d'exploitation (voir ci-dessus). Notez que ces données aléatoires ne sont généralement générées qu'une seule fois, lors de l'installation du système d'exploitation, et ne sont jamais mises à jour par la suite.

CHAÎNES SMBIOS TYPE 11

systemd-boot peut être configuré à l'aide des chaînes SMBIOS de type 11. Les chaînes applicables consistent en un nom, suivi de "=", suivi de la valeur. À moins que systemd-boot ne détecte qu'il s'exécute dans un environnement de calcul confidentiel, systemd-boot recherchera dans la table une chaîne portant un nom spécifique, et si elle est trouvée, utilisera sa valeur. Les chaînes suivantes sont lues :

io.systemd.boot.kernel-cmdline-extra

Si elle est définie, la valeur de cette chaîne est ajoutée à la liste des arguments de ligne de commande du noyau pour les entrées de la spécification du chargeur de démarrage de type 1 qui sont mesurées dans PCR12 et transmises au noyau.

Ajouté dans la version 256.

io.systemd.boot-entries.extra:ID=DÉFINITION

Ceci permet d'insérer des entrées supplémentaires dans le menu systemd-boot. Prenez une paire identifiant d'entrée de menu et chaîne de définition d'entrée de menu. Le premier doit être utilisable comme nom de fichier d'une entrée de la spécification du chargeur de démarrage de type 1 (notez qu'il est utilisé à des fins d'identification uniquement, aucun fichier de ce nom n'est réellement accédé), le second doit suivre la syntaxe du contenu d'une entrée de type 1. Toute entrée de menu ainsi définie est traitée et affichée de manière quasi identique à une entrée de type 1 lue depuis l'ESP ou la partition XBOOTLDR. Exemple : 
io.systemd.boot-entries.extra:fooos-current.conf=title FooOS (Current)
uki-url http://example.com/somedir/fooos.efi

Notez que cet exemple contient un caractère de nouvelle ligne. Lors de la génération de cette chaîne à partir d'un shell, il faut veiller à l'encoder correctement.

Passez plusieurs chaînes formatées de cette manière pour générer plusieurs entrées de menu.

Ajouté dans la version 258.

COMPTAGE DE DÉMARRAGES

systemd-boot implémente un mécanisme simple de comptage de démarrages par-dessus le Boot Loader Specification[1], pour un retour automatique et sans intervention à d'anciennes versions du noyau/entrées du chargeur de démarrage lorsque une entrée spécifique échoue continuellement. Tout fichier d'entrée du chargeur de démarrage et fichier d'image noyau unifiée qui contient un "+" suivi d'un ou deux nombres (si deux, ils doivent être séparés par un "-"), avant le suffixe .conf ou .efi, est soumis au comptage de démarrages : le premier des deux nombres ('essais restants') est diminué d'un à chaque tentative de démarrage, le second des deux nombres ('essais effectués') est augmenté d'un (si 'essais effectués' est absent, il est considéré comme équivalent à 0). Selon la valeur actuelle de ces deux compteurs, l'entrée de démarrage est considérée dans l'un des trois états suivants :

1. Si le compteur 'essais restants' d'une entrée est supérieur à zéro, l'entrée est considérée dans un état 'indéterminé'. Cela signifie que l'entrée n'a pas encore terminé son démarrage avec succès, mais il n'a pas non plus été déterminé qu'elle ne fonctionne pas.
2. Si le compteur 'essais restants' d'une entrée est à zéro, elle est considérée dans un état 'mauvais'. Cela signifie qu'aucune autre tentative de démarrage de cet élément ne sera effectuée (sauf si toutes les autres entrées de démarrage sont également dans un état 'mauvais'), car toutes les tentatives de démarrage de cette entrée n'ont pas abouti.
3. Si les compteurs 'essais restants' et 'essais effectués' d'une entrée sont absents, elle est considérée dans un état 'bon'. Cela signifie que le comptage de démarrages pour l'entrée est désactivé, car elle a réussi à démarrer au moins une fois avec succès. Le service systemd-bless-boot.service(8) déplace l'entrée actuellement démarrée de l'état 'indéterminé' à l'état 'bon' lorsqu'une tentative de démarrage s'est terminée avec succès.

En général, lorsque de nouvelles entrées sont ajoutées au chargeur de démarrage, elles commencent d'abord dans un état 'indéterminé', c'est-à-dire avec un compteur 'essais restants' supérieur à zéro. L'entrée de démarrage reste dans cet état jusqu'à ce qu'elle parvienne à terminer un démarrage complet avec succès au moins une fois (auquel cas elle sera dans un état 'bon') - ou que le compteur 'essais restants' atteigne zéro (auquel cas elle sera dans un état 'mauvais').

Exemple : supposons qu'un fichier d'entrée de chargeur de démarrage foo.conf soit configuré pour 3 tentatives de démarrage. L'installateur le créera donc sous le nom foo+3.conf. Lors du premier démarrage, le chargeur de démarrage le renommera en foo+2-1.conf. Si ce démarrage ne se termine pas avec succès, le chargeur de démarrage le renommera en foo+1-2.conf lors du démarrage suivant. Si cela échoue également, il sera finalement renommé en foo+0-3.conf par le chargeur de démarrage lors du prochain démarrage, après quoi il sera considéré comme 'mauvais'. Si le démarrage réussit cependant, le fichier d'entrée sera renommé en foo.conf par le système d'exploitation, de sorte qu'il soit considéré comme 'bon' à partir de ce moment-là.

Le menu de démarrage prend en compte le compteur 'essais restants' lors du tri des entrées du menu : les entrées dans un état 'mauvais' sont classées au début de la liste, et les entrées dans un état 'bon' ou 'indéterminé' à la fin. L'utilisateur peut choisir librement de démarrer n'importe quelle entrée du menu, y compris celles déjà marquées comme 'mauvaises'. Si l'entrée de menu à démarrer est déterminée automatiquement, cela signifie que les entrées 'bonnes' ou 'indéterminées' sont généralement préférées (car l'élément inférieur du menu est celui qui est démarré par défaut), et les entrées 'mauvaises' ne seront prises en compte que s'il ne reste plus d'entrées 'bonnes' ou 'indéterminées'.

Le framework d'installation du noyau kernel-install(8) définit éventuellement le compteur initial 'essais restants' à la valeur spécifiée dans /etc/kernel/tries lors de la première création d'une entrée du chargeur de démarrage.

UTILISATION DE SYSTEMD-BOOT DANS LES MACHINES VIRTUELLES

Lors de l'utilisation de qemu avec OVMF (Firmware UEFI pour machines virtuelles), le commutateur -kernel fonctionne non seulement pour les noyaux Linux, mais pour tout binaire EFI, y compris sd-boot et les noyaux Linux unifiés. Exemple de ligne de commande pour charger systemd-boot sur x64 :

qemu-system-x86_64 [ ... ] -kernel /usr/lib/systemd/boot/efi/systemd-bootx64.efi

systemd-boot détectera qu'il a été démarré directement au lieu d'être chargé depuis ESP et recherchera l'ESP dans ce cas, en tenant compte des informations d'ordre de démarrage de l'hyperviseur (si disponibles).
