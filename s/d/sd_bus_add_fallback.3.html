DESCRIPTION

sd_bus_add_object_vtable() est utilisé pour déclarer les attributs du chemin d'objet path connecté à la connexion de bus bus sous l'interface interface. La table vtable peut contenir des déclarations de propriétés utilisant SD_BUS_PROPERTY() ou SD_BUS_WRITABLE_PROPERTY(), des déclarations de méthodes utilisant SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), ou SD_BUS_METHOD_WITH_NAMES_OFFSET(), et des déclarations de signaux utilisant SD_BUS_SIGNAL_WITH_NAMES() ou SD_BUS_SIGNAL(), voir ci-dessous. Le paramètre userdata contient un pointeur qui sera passé à diverses fonctions de rappel. Il peut être spécifié comme NULL si aucune valeur n'est nécessaire. Une interface peut avoir un nombre quelconque de vtables qui lui sont attachées.

sd_bus_add_fallback_vtable() est similaire à sd_bus_add_object_vtable(), mais est utilisé pour enregistrer les attributs "de secours". Lors de la recherche d'une déclaration d'attribut, les chemins d'objets de bus enregistrés avec sd_bus_add_object_vtable() sont vérifiés en premier. Si aucune correspondance n'est trouvée, les vtables de secours sont vérifiées pour chaque préfixe du chemin de l'objet bus, c'est-à-dire en supprimant successivement les derniers composants séparés par des slash. Cela permet d'utiliser la vtable pour un nombre arbitraire d'objets créés dynamiquement.

Le paramètre find est une fonction utilisée pour localiser l'objet cible en fonction du chemin de l'objet bus path. Elle doit retourner 1 et définir le paramètre de sortie ret_found si l'objet est trouvé, retourner 0 si l'objet n'a pas été trouvé, et retourner un code d'erreur de style errno négatif ou initialiser la structure d'erreur ret_error en cas d'erreur. Le pointeur passé dans ret_found sera utilisé comme paramètre userdata pour les fonctions de rappel (décalé par les décalages offset tels que spécifiés dans les entrées vtable).

sd_bus_add_object() attache un rappel directement au chemin d'objet path. Un chemin d'objet peut avoir un nombre quelconque de rappels qui lui sont attachés. Chaque rappel est ajouté au début de la liste des rappels qui sont toujours appelés dans l'ordre. sd_bus_add_fallback() est similaire à sd_bus_add_object() mais s'applique plutôt aux chemins de secours.

sd_bus_add_filter() installe une fonction de rappel qui est invoquée pour chaque message D-Bus entrant. Les filtres peuvent être utilisés pour gérer une logique commune à tous les messages reçus par un service (par exemple, authentification ou autorisation).

Lorsqu'une requête est reçue, les rappels associés sont appelés séquentiellement jusqu'à ce qu'un rappel retourne un entier non nul. Retournez zéro d'un rappel pour donner à d'autres rappels la chance de traiter la requête. Les rappels sont appelés dans l'ordre suivant : d'abord, les rappels globaux installés avec sd_bus_add_filter() sont appelés. Ensuite, les rappels attachés directement au chemin de l'objet de la requête sont appelés, suivis de tous les rappels de méthodes D-Bus attachés au chemin de l'objet de la requête, à l'interface et au membre. Enfin, les rappels de propriétés attachés au chemin de l'objet de la requête, à l'interface et au membre sont appelés. Si le dernier rappel retourne zéro, une erreur est renvoyée.

Notez que vous pouvez retourner un entier positif d'une fonction de rappel de *méthode* sans envoyer immédiatement une réponse. Cela informe sd-bus que la fonction de rappel prendra la responsabilité de répondre à la demande sans forcer la fonction de rappel à produire une réponse immédiate. Cela permet à une fonction de rappel d'effectuer le nombre d'opérations asynchrones nécessaires pour construire une réponse. Cependant, si la production d'une réponse prend trop de temps, l'appel de méthode expirera chez l'appelant. Ceci n'est disponible que pour les méthodes et non pour les propriétés.

Si une fonction de rappel a été invoquée pour gérer une demande qui attend une réponse et que la fonction de rappel retourne une valeur négative, la valeur est interprétée comme un code d'erreur négatif de style errno et renvoyée à l'appelant en tant qu'erreur D-Bus, comme si sd_bus_reply_method_errno(3) avait été appelé. De plus, toutes les fonctions de rappel prennent un paramètre de sortie sd_bus_error qui peut être utilisé pour fournir des informations d'erreur plus détaillées. Si *ret_error* est défini lorsque la fonction de rappel se termine, l'erreur D-Bus correspondante est renvoyée à l'appelant comme si sd_bus_reply_method_error(3) avait été appelé. Toute erreur stockée dans *ret_error* a priorité sur toute valeur négative retournée par la même fonction de rappel pour déterminer quelle erreur renvoyer à l'appelant. Utilisez sd_bus_error_set(3) ou l'une de ses variantes pour définir *ret_error* et retourner un entier négatif à partir d'une fonction de rappel avec un seul appel de fonction. Pour envoyer une réponse d'erreur après qu'une fonction de rappel a déjà terminé, utilisez sd_bus_reply_method_errno(3) ou l'une de ses variantes.

Pour toutes les fonctions, un slot de correspondance est créé interne. Si le paramètre de sortie *slot* est NULL, un objet de slot "flottant" est créé, voir sd_bus_slot_set_floating(3). Sinon, un pointeur vers l'objet de slot est retourné. Dans ce cas, la référence à l'objet de slot doit être libérée lorsque le vtable n'est plus nécessaire, voir sd_bus_slot_unref(3).

Le tableau sd_bus_vtable

Le tableau se compose des structures de type sd_bus_vtable, mais il ne doit jamais être rempli manuellement, mais via l'une des macros suivantes :

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Ceux-ci doivent toujours être le premier et le dernier élément. Le paramètre *flags* peut être utilisé pour définir des attributs qui s'appliquent à l'ensemble du tableau ; voir la section "Flags" ci-dessous.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Déclare une méthode D-Bus avec le nom *member*, les arguments *args* et le résultat *result*. *args* attend une séquence de paires type/nom d'argument encapsulées dans la macro SD_BUS_ARGS(). Les éléments aux indices pairs de cette liste décrivent les types des arguments de la méthode. La signature des paramètres de la méthode est la concaténation de toutes les littéraux de chaîne aux indices pairs dans *args*. Si une méthode n'a pas de paramètres, passez SD_BUS_NO_ARGS à *args*. Les éléments aux indices impairs décrivent les noms des arguments de la méthode. *result* attend une séquence de paires type/nom encapsulées dans la macro SD_BUS_RESULT() dans le même format que SD_BUS_ARGS(). La signature du résultat de la méthode est la concaténation de toutes les littéraux de chaîne aux indices pairs dans *result*. Si une méthode n'a pas de résultat, passez SD_BUS_NO_RESULT à *result*. Notez que les types d'arguments sont censés être des littéraux de chaîne entre guillemets et les noms d'arguments sont censés être des littéraux de chaîne non cités. Voir ci-dessous pour un exemple complet.

La fonction de rappel *handler* doit être de type sd_bus_message_handler_t. Elle sera appelée pour gérer les messages entrants qui appellent cette méthode. Elle reçoit un pointeur qui est le paramètre *userdata* passé à la fonction d'enregistrement décalé de *offset* octets. Cela peut être utilisé pour passer des pointeurs vers différents champs dans la même structure de données à différentes méthodes de la même vtable. Pour envoyer une réponse depuis *handler*, appelez sd_bus_reply_method_return(3) avec le message avec lequel la fonction de rappel a été invoquée. Le paramètre *flags* est une combinaison de drapeaux, voir ci-dessous.

SD_BUS_METHOD_WITH_ARGS() est un raccourci pour appeler SD_BUS_METHOD_WITH_ARGS_OFFSET() avec un décalage de zéro.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Déclare une méthode D-Bus avec le nom *member*, la signature de paramètre *signature*, la signature de résultat *result*. Les paramètres *in_names* et *out_names* spécifient les noms d'arguments des arguments d'entrée et de sortie dans la signature de la fonction. *in_names* et *out_names* doivent être créés à l'aide de la macro SD_BUS_PARAM(), voir ci-dessous. Pour tout le reste, cette macro se comporte exactement de la même manière que SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), et SD_BUS_METHOD() sont des variantes qui spécifient un décalage nul (*userdata* le paramètre est passé sans modification), laissent les noms non définis (c'est-à-dire aucun nom de paramètre), ou les deux.

Préférez utiliser SD_BUS_METHOD_WITH_ARGS_OFFSET() et SD_BUS_METHOD_WITH_ARGS() plutôt que ces macros car elles permettent de spécifier les types et les noms des arguments côte à côte, ce qui est moins sujet aux erreurs que de spécifier d'abord tous les types d'arguments suivis de la spécification de tous les noms d'arguments.

SD_BUS_SIGNAL_WITH_ARGS()

Déclare un signal D-Bus avec le nom *member* et les arguments *args*. *args* attend une séquence de paires type/nom d'argument encapsulées dans la macro SD_BUS_ARGS(). Les éléments aux indices pairs de cette liste décrivent les types des arguments du signal. La signature des paramètres du signal est la concaténation de toutes les littéraux de chaîne aux indices pairs dans *args*. Si un signal n'a pas de paramètres, passez SD_BUS_NO_ARGS à *args*. Les éléments aux indices impairs décrivent les noms des arguments du signal. Le paramètre *flags* est une combinaison de drapeaux. Voir ci-dessous pour un exemple complet.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Déclare un signal D-Bus avec le nom *member*, la signature de paramètre *signature*, et les noms d'arguments *names*. *names* doit être créé à l'aide de la macro SD_BUS_PARAM(), voir ci-dessous. Le paramètre *flags* est une combinaison de drapeaux, voir ci-dessous.

SD_BUS_SIGNAL() est équivalent à SD_BUS_SIGNAL_WITH_NAMES() avec le paramètre *names* non défini (c'est-à-dire aucun nom de paramètre).

Préférez utiliser SD_BUS_SIGNAL_WITH_ARGS() plutôt que ces macros car elle permet de spécifier les types et les noms des arguments côte à côte, ce qui est moins sujet aux erreurs que de spécifier d'abord tous les types d'arguments suivis de la spécification de tous les noms d'arguments.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Déclare une propriété D-Bus avec le nom *member* et la signature de valeur *signature*. Les paramètres *get* et *set* sont les méthodes de récupération et de définition. Elles sont appelées avec un pointeur qui est le paramètre *userdata* passé à la fonction d'enregistrement décalé de *offset* octets. Cela peut être utilisé pour passer des pointeurs vers différents champs dans la même structure de données à différents définisseurs et récupérateurs de la même vtable. Le paramètre *flags* est une combinaison de drapeaux, voir ci-dessous.

Le définisseur et le récupérateur peuvent être omis (spécifiés comme NULL), si la propriété est l'un des types de base ou "as" dans le cas des propriétés en lecture seule. Dans ces cas, les paramètres *userdata* et *offset* doivent ensemble pointer vers une variable valide du type correspondant. Un définisseur et un récupérateur par défaut seront fournis, qui copient simplement l'argument entre cette variable et le message.

SD_BUS_PROPERTY() est utilisé pour définir une propriété en lecture seule.

SD_BUS_PARAM()

Les noms de paramètres doivent être encapsulés dans cette macro, voir l'exemple ci-dessous.

Flags

Le paramètre *flags* est utilisé pour spécifier une combinaison d'annotations D-Bus[1].

SD_BUS_VTABLE_DEPRECATED

Marque cette entrée vtable comme obsolète en utilisant l'annotation org.freedesktop.DBus.Deprecated dans les données d'introspection. Si spécifié pour SD_BUS_VTABLE_START(), l'annotation est appliquée à l'interface parente.

SD_BUS_VTABLE_HIDDEN

Rend cette entrée vtable cachée. Elle ne sera pas affichée dans les données d'introspection. Si spécifié pour SD_BUS_VTABLE_START(), toutes les entrées du tableau sont cachées.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marque cette entrée vtable comme une méthode qui ne renverra pas de réponse en utilisant l'annotation org.freedesktop.DBus.Method.NoReply dans les données d'introspection.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Ces trois drapeaux correspondent à différentes valeurs de l'annotation org.freedesktop.DBus.Property.EmitsChangedSignal, qui spécifie si le signal org.freedesktop.DBus.Properties.PropertiesChanged est émis chaque fois que la propriété change. SD_BUS_VTABLE_PROPERTY_CONST correspond à const et signifie que la propriété ne change jamais pendant la durée de vie de l'objet auquel elle appartient, donc aucun signal ne doit être émis. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE correspond à true et signifie que le signal est émis. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION correspond à invalidates et signifie que le signal est émis, mais la valeur n'est pas incluse dans le signal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marque cette entrée de propriété vtable comme nécessitant une demande explicite pour que la valeur soit affichée (généralement parce que la valeur est volumineuse ou lente à calculer). Cette entrée ne peut pas être combinée avec SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, et ne sera pas affichée dans les listes de propriétés par défaut (par exemple, busctl introspect). Ceci correspond à l'annotation org.freedesktop.systemd1.Explicit dans les données d'introspection.

SD_BUS_VTABLE_SENSITIVE

Marque cette entrée de méthode vtable comme traitant des données sensibles. Lorsqu'il est défini, les messages d'appel de méthode entrants et leurs messages de réponse sortants sont marqués comme sensibles à l'aide de sd_bus_message_sensitive(3), de sorte qu'ils soient effacés de la mémoire lorsqu'ils sont libérés.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

Marque cette entrée de méthode ou de propriété vtable pour que le pointeur de données utilisateur
er est transmis à ses fonctions de gestion associées de manière légèrement différente : au lieu d'ajouter le paramètre d'offset de l'entrée au pointeur de données utilisateur spécifié lors de l'enregistrement de la vtable, l'offset est transmis directement, converti en pointeur, sans tenir compte du pointeur de données utilisateur spécifié lors de l'enregistrement de la vtable.

SD_BUS_VTABLE_CAPABILITY(capability)

L'accès à cette entrée de vtable sera autorisé si le processus appelant possède la capacité capability, comme décrit dans sd_bus_query_sender_privilege(3). Si utilisé pour SD_BUS_VTABLE_START(), fournit une valeur par défaut pour toutes les entrées du tableau. Si non spécifié, que ce soit pour une entrée individuelle ou pour l'ensemble du tableau, CAP_SYS_ADMIN est vérifié par défaut. Voir capabilities(7) pour plus d'informations sur les capacités.

Notez que les entrées de vtable peuvent être marquées comme non privilégiées et que l'ensemble du bus peut être marqué comme fiable, voir la discussion sur SD_BUS_VTABLE_UNPRIVILEGED ci-dessous.

SD_BUS_VTABLE_UNPRIVILEGED

Marquez cette entrée de vtable comme non privilégiée. L'accès aux entrées privilégiées est limité aux utilisateurs ayant les capacités appropriées, comme décrit ci-dessus. En pratique, de nombreuses entrées de vtable sont marquées comme non privilégiées et sont soit ouvertes à tous, soit la décision d'autoriser l'accès est prise ultérieurement, par exemple en déléguant à polkit[2].

L'ensemble du bus peut être marqué comme fiable, auquel cas les annotations au niveau de l'entrée sont ignorées, voir sd_bus_set_trusted(3).

Lorsqu'il n'est pas spécifié, l'annotation org.freedesktop.systemd1.Privileged avec la valeur « true » sera affichée dans les données d'introspection.

SD_BUS_VTABLE_UNPRIVILEGED ne peut pas être appliqué aux propriétés en lecture seule, mais l'accès en lecture (aux propriétés en lecture seule et en écriture) est toujours sans restriction.

Notez que cette page décrit les vérifications implémentées dans le client D-Bus. Le serveur D-Bus dispose d'une politique supplémentaire qui peut autoriser ou refuser les connexions, voir « FICHIER DE CONFIGURATION » dans dbus-daemon(1).

EXEMPLES

Exemple 1. Créer un écouteur simple sur le bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_VTABLE_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

VALEUR DE RETOUR

En cas de succès, sd_bus_add_object_vtable() et sd_bus_add_fallback_vtable() renvoient un entier non négatif. En cas d'échec, ils renvoient un code d'erreur négatif de type errno.

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-EINVAL

L'un des paramètres requis est NULL ou invalide. Une interface D-Bus réservée a été passée comme paramètre interface.

-ENOPKG

Le bus ne peut pas être résolu.

-ECHILD

Le bus a été créé dans un processus, une bibliothèque ou une instance de module différent.

-ENOMEM

L'allocation de mémoire a échoué.

-EPROTOTYPE

sd_bus_add_object_vtable() et sd_bus_add_fallback_vtable() ont tous deux été appelés pour le même chemin d'objet de bus, ce qui n'est pas autorisé.

-EEXIST

Cette vtable a déjà été enregistrée pour cette interface et ce chemin.

NOTES

Les fonctions décrites ici sont disponibles

adaptée en tant que bibliothèque partagée, qui peut être compilée et liée avec le fichier pkg-config(1) de libsystemd.

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas sûr pour un usage multi-thread. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'appeler setenv() que dès la première phase du programme, lorsqu'aucun autre thread n'a été démarré.
