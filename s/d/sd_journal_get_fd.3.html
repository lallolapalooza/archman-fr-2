SD_JOURNAL_GET_FD(3) sd_journal_get_fd SD_JOURNAL_GET_FD(3)

NOM

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interface de notification de changement du journal

SYNOPIS

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

sd_journal_get_fd() renvoie un descripteur de fichier qui peut être interrogé de manière asynchrone dans une boucle d'événements externe et qui est signalé dès que le journal change, car de nouvelles entrées ou de nouveaux fichiers ont été ajoutés, une rotation a eu lieu, ou des fichiers ont été supprimés, et ainsi de suite. Le descripteur de fichier est adapté à une utilisation dans poll(2). Utilisez sd_journal_get_events() pour un masque d'événements à surveiller. L'appel prend un argument : l'objet de contexte du journal. Notez que tous les systèmes de fichiers ne sont pas capables de générer les événements nécessaires pour des réveils à partir de ce descripteur de fichier pour que les changements soient remarqués immédiatement. En particulier, les systèmes de fichiers réseau ne génèrent pas d'événements de changement de fichier appropriés dans tous les cas. Ces cas peuvent être détectés avec sd_journal_reliable_fd(), ci-dessous. sd_journal_get_timeout() garantira dans ces cas que les réveils se produisent suffisamment fréquemment pour que les changements soient remarqués, bien qu'avec une certaine latence.

sd_journal_get_events() renverra le masque de poll() à attendre. Cette fonction renverra une combinaison de POLLIN et POLLOUT et similaires à insérer dans le champ ".events" de struct pollfd.

sd_journal_get_timeout() renverra une valeur de timeout pour une utilisation dans poll(). Elle renvoie une valeur en microsecondes depuis l'époque de CLOCK_MONOTONIC pour temporiser poll() dans timeout_usec. Voir clock_gettime(2) pour les détails sur CLOCK_MONOTONIC. S'il n'y a pas de timeout à attendre, elle remplira à la place (uint64_t) -1. Notez que poll() prend un timeout relatif en millisecondes plutôt qu'un timeout absolu en microsecondes. Pour convertir le timeout absolu 'us' en 'ms' relatif, utilisez du code comme ce qui suit :

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

Le code ci-dessus ne fait aucun contrôle d'erreur par souci de brièveté. L'entier msec calculé peut être passé directement comme paramètre de timeout de poll().

Après chaque réveil de poll(), sd_journal_process() doit être appelé pour traiter les événements. Cet appel indiquera également quel type de changement a été détecté (voir ci-dessous ; notez que des réveils parasites sont possibles).

Une alternative synchrone pour utiliser sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() et sd_journal_process() est sd_journal_wait(). Elle attendra de manière synchrone jusqu'à ce que le journal soit modifié. Le temps maximum pendant lequel cet appel dort peut être contrôlé avec le paramètre timeout_usec. Passez (uint64_t) -1 pour attendre indéfiniment. En interne, cet appel combine simplement sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() et sd_journal_process() en un seul.

sd_journal_reliable_fd() peut être utilisé pour vérifier si les événements de réveil du descripteur de fichier retourné par sd_journal_get_fd() sont connus pour être déclenchés rapidement. Sur certains systèmes de fichiers où les événements de changement de fichier de l'OS ne sont pas disponibles (comme NFS), les changements doivent être interrogés de manière répétée, et sont donc détectés seulement avec une latence considérable. Cet appel renverra une valeur positive si les changements du journal sont détectés rapidement et zéro lorsqu'ils doivent être interrogés. Notez qu'il n'est généralement pas nécessaire d'invoquer cette fonction directement car sd_journal_get_timeout() demandera des timeouts appropriés de toute façon.

Notez que toutes les interfaces de notification de changement ci-dessus ne signalent pas les changements instantanément. Des latences sont introduites pour plusieurs raisons : comme mentionné, certains backends de stockage nécessitent une interrogation basée sur le temps, dans d'autres cas les réveils sont optimisés par la coalescence des événements, et l'OS introduit des latences supplémentaires de planification IO/CPU.

VALEUR RENVOYÉE

sd_journal_get_fd() renvoie un descripteur de fichier valide en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_get_events() renvoie une combinaison de POLLIN, POLLOUT et similaires en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_reliable_fd() renvoie un entier positif si le descripteur de fichier renvoyé par sd_journal_get_fd() déclenchera des réveils immédiats pour tous les changements du journal. Renvoie 0 s'il peut y avoir une latence.

sd_journal_process() et sd_journal_wait() renvoient un code d'erreur négatif de style errno, ou l'un de SD_JOURNAL_NOP, SD_JOURNAL_APPEND ou SD_JOURNAL_INVALIDATE en cas de succès :

•Si SD_JOURNAL_NOP est renvoyé, le journal n'a pas changé depuis la dernière invocation.
•Si SD_JOURNAL_APPEND est renvoyé, de nouvelles entrées ont été ajoutées à la fin du journal. Dans ce cas, il suffit de continuer à lire à l'emplacement précédent de la fin du journal pour lire les entrées nouvellement ajoutées.
•Si SD_JOURNAL_INVALIDATE, des fichiers du journal ont été ajoutés ou supprimés de l'ensemble des fichiers du journal surveillés (par exemple, suite à une rotation ou un nettoyage), et donc des entrées ont pu apparaître ou disparaître à des endroits arbitraires dans le flux du log, potentiellement avant ou après l'ancienne fin du flux du log. Si SD_JOURNAL_INVALIDATE est renvoyé, les interfaces utilisateur en vue en direct qui souhaitent refléter à l'écran l'état précis des données du log sur disque devraient probablement rafraîchir leur affichage complet (par rapport au curseur de l'entrée du log en haut de l'écran). Les programmes uniquement intéressés par un flux de données de log strictement séquentiel peuvent traiter SD_JOURNAL_INVALIDATE de la même manière que SD_JOURNAL_APPEND, ignorant ainsi tout changement de la vue du log antérieur à l'ancienne fin du flux du log.

SÉCURITÉ DES SIGNAUX

En général, sd_journal_get_fd(), sd_journal_get_events(), et sd_journal_get_timeout() ne sont *pas* "async signal safe" au sens de signal-safety(7). Néanmoins, seul le premier appel à l'une de ces trois fonctions effectue des opérations non sûres, donc les appels subséquents *sont* sûrs.

sd_journal_process() et sd_journal_wait() ne sont pas sûrs. sd_journal_reliable_fd() est sûr.

NOTES

Toutes les fonctions décrites ici sont indépendantes des threads et un seul thread peut opérer sur un objet donné à un moment donné. Différents threads peuvent accéder au même objet à des moments différents. Plusieurs objets indépendants peuvent être utilisés à partir de différents threads en parallèle.

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée contre et liée avec le fichier libsystemd pkg-config(1).

Attente avec poll() (cet exemple manque de tout contrôle d'erreur par souci de simplicité) :

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int wait_for_changes(sd_journal *j) {
  uint64_t t;
  int msec;
  struct pollfd pollfd;
  sd_journal_get_timeout(j, &t);
  if (t == (uint64_t) -1)
    msec = -1;
  else {
    struct timespec ts;
    uint64_t n;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
    msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
  }
  pollfd.fd = sd_journal_get_fd(j);
  pollfd.events = sd_journal_get_events(j);
  poll(&pollfd, 1, msec);
  return sd_journal_process(j);
}
