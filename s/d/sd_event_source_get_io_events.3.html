NOM

SYNTAXE

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;

typedef int (*sd_event_io_handler_t)(sd_event_source *s, int fd, uint32_t revents, void *userdata);

int sd_event_add_io(sd_event *event, sd_event_source **source, int fd, uint32_t events, sd_event_io_handler_t handler, void *userdata);

int sd_event_source_get_io_events(sd_event_source *source, uint32_t *ret);

int sd_event_source_set_io_events(sd_event_source *source, uint32_t events);

int sd_event_source_set_io_fd(sd_event_source *source, int fd);

int sd_event_source_get_io_fd_own(sd_event_source *source);

int sd_event_source_set_io_fd_own(sd_event_source *source, int b);

DESCRIPTION

sd_event_add_io() ajoute une nouvelle source d'événements d'E/S à une boucle d'événements. L'objet boucle d'événements est spécifié par le paramètre event, l'objet source d'événements est renvoyé dans le paramètre source. Le paramètre fd prend le descripteur de fichier UNIX à surveiller, qui peut faire référence à un socket, un FIFO, une file de messages, une connexion série, un périphérique caractère, ou tout autre descripteur de fichier compatible avec epoll(7) de Linux. Le paramètre events prend un masque de bits des événements à surveiller, une combinaison des indicateurs d'événement suivants : EPOLLIN, EPOLLOUT, EPOLLRDHUP, EPOLLPRI, et EPOLLET, voir epoll_ctl(2) pour plus de détails. Notez que tous les descripteurs de fichier ne sont pas compatibles avec epoll, par exemple les fichiers réguliers ou les répertoires ne le sont pas. Si cette fonction est appelée avec un descripteur de fichier qui ne supporte pas epoll, -EPERM est retourné (voir aussi ci-dessous). Dans la plupart des cas, de tels descripteurs de fichier peuvent être traités comme toujours lisibles ou toujours écrivables, de sorte que la surveillance des événements d'E/S n'est pas nécessaire.

Le handler est une fonction à appeler lorsque la source d'événements est déclenchée ou NULL. Le pointeur userdata sera passé à la fonction de traitement, et peut être choisi librement par l'appelant. Le gestionnaire recevra également le descripteur de fichier sur lequel l'événement a été vu, ainsi que les indicateurs d'événement réels. C'est généralement un sous-ensemble des événements surveillés, mais peut inclure en plus EPOLLERR et EPOLLHUP. Le gestionnaire peut retourner une valeur négative pour signaler une erreur (voir ci-dessous), les autres valeurs de retour sont ignorées. Si handler est NULL, un gestionnaire par défaut qui appelle sd_event_exit(3) sera utilisé.

Par défaut, une source d'événements reste activée en permanence (SD_EVENT_ON), mais cela peut être modifié avec sd_event_source_set_enabled(3). Si la fonction de traitement renvoie un code d'erreur négatif, elle sera désactivée après l'invocation, même si le mode SD_EVENT_ON était demandé auparavant, ou elle provoquera la terminaison de la boucle, voir sd_event_source_set_exit_on_failure(3). Notez qu'une source d'événements définie sur SD_EVENT_ON se déclenchera en continu à moins que des données ne soient lues ou écrites sur le descripteur de fichier pour réinitialiser le masque des événements vus.

Définir le masque d'événements d'E/S à surveiller sur 0 ne signifie pas que la source d'événements ne sera plus déclenchée, car EPOLLHUP et EPOLLERR peuvent être déclenchés même avec un masque d'événement nul. Pour désactiver temporairement une source d'événements d'E/S, utilisez sd_event_source_set_enabled(3) avec SD_EVENT_OFF à la place.

Pour détruire un objet source d'événements, utilisez sd_event_source_unref(3), mais notez que la source d'événements n'est retirée de la boucle d'événements que lorsque toutes les références à la source d'événements sont supprimées. Pour s'assurer qu'une source d'événements ne se déclenche plus, même si elle est toujours référencée, désactivez la source d'événements en utilisant sd_event_source_set_enabled(3) avec SD_EVENT_OFF.

Si le deuxième paramètre de sd_event_add_io() est NULL, aucune référence à l'objet source d'événements n'est retournée. Dans ce cas, la source d'événements est considérée comme "flottante" et sera détruite implicitement lorsque la boucle d'événements elle-même sera détruite.

Si le handler de sd_event_add_io() est NULL, et que la source d'événements se déclenche, cela sera considéré comme une demande de sortie de la boucle d'événements. Dans ce cas, le paramètre userdata, converti en entier, est passé comme paramètre de code de sortie à sd_event_exit(3).

Notez que cet appel ne prend pas possession du descripteur de fichier passé, la propriété (et donc le devoir de le fermer lorsqu'il n'est plus nécessaire) reste à l'appelant. Cependant, avec l'appel sd_event_source_set_io_fd_own() (voir ci-dessous), la source d'événements peut éventuellement prendre possession du descripteur de fichier après la création de la source d'événements. Dans ce cas, le descripteur de fichier est fermé automatiquement dès que la source d'événements est libérée.

Il est recommandé d'utiliser sd_event_add_io() uniquement en conjonction avec des descripteurs de fichiers ayant O_NONBLOCK défini, pour s'assurer que toutes les opérations d'E/S des gestionnaires invoqués sont correctement asynchrones et non bloquantes. L'utilisation de descripteurs de fichiers sans O_NONBLOCK pourrait entraîner une famine inattendue d'autres sources d'événements. Voir fcntl(2) pour plus de détails sur l'activation du mode O_NONBLOCK.

sd_event_source_get_io_events() récupère le masque configuré des événements d'E/S surveillés d'une source d'événements créée précédemment avec sd_event_add_io(). Elle prend l'objet source d'événements et un pointeur vers une variable pour stocker le masque.

sd_event_source_set_io_events() configure le masque des événements d'E/S surveillés d'une source d'événements créée précédemment avec sd_event_add_io(). Elle prend l'objet source d'événements et le nouveau masque d'événements.

sd_event_source_get_io_revents() récupère le masque des événements d'E/S actuellement vus mais non dépêchés d'une source d'événements créée précédemment avec sd_event_add_io(). Elle prend l'objet source d'événements et un pointeur vers une variable pour stocker le masque d'événements. Lorsqu'elle est appelée depuis une fonction de traitement sur l'objet source d'événements du traitement, elle renverra le même masque que celui passé au paramètre revents du traitement. Cet appel est principalement utile pour vérifier les événements non dépêchés d'une source d'événements à partir du traitement d'une source d'événements non liée (potentiellement de plus haute priorité). Notez la relation entre sd_event_source_get_pending() et sd_event_source_get_io_revents() : les deux fonctions signaleront des résultats non nuls lorsqu'un événement est en attente pour la source d'événements, mais la première s'applique à tous les types de sources d'événements, la seconde uniquement aux sources d'événements d'E/S.

sd_event_source_get_io_fd() récupère le descripteur de fichier UNIX d'une source d'événements créée précédemment avec sd_event_add_io(). Elle prend l'objet source d'événements et renvoie le descripteur de fichier non négatif ou un nombre d'erreur négatif en cas d'erreur (voir ci-dessous).

sd_event_source_set_io_fd() modifie le descripteur de fichier UNIX d'une source d'événements d'E/S créée précédemment avec sd_event_add_io(). Elle prend l'objet source d'événements et le nouveau descripteur de fichier comme paramètres. Si la source d'événements possédait le descripteur de fichier précédent, c'est-à-dire si sd_event_source_set_io_fd_own() avait été appelée pour la source d'événements avec une valeur non nulle, alors le descripteur de fichier précédent sera fermé et la source d'événements prendra également possession du nouveau descripteur de fichier en cas de succès.

sd_event_source_set_io_fd_own() contrôle si le descripteur de fichier de la source d'événements doit prendre possession du descripteur de fichier. Prend un paramètre booléen b. Lorsque vrai (non nul)

, le descripteur de fichier sera fermé automatiquement lorsque la source d'événements sera libérée ou lorsque le descripteur de fichier sera remplacé par sd_event_source_set_io_fd(). Par défaut, le descripteur n'est pas possédé par la source d'événements, et l'application doit le fermer elle-même si nécessaire.

sd_event_source_get_io_fd_own() peut être utilisé pour interroger le réglage actuel du drapeau booléen de possession du descripteur de fichier tel que défini avec sd_event_source_set_io_fd_own(). Il retourne une valeur positive si le descripteur de fichier est fermé automatiquement lors de la destruction de la source d'événements, zéro s'il ne l'est pas, et une valeur négative en cas d'erreur.

VALEUR DE RETOUR

En cas de succès, ces fonctions retournent 0 ou un entier positif. En cas d'échec, elles retournent un code d'erreur négatif de style errno.

Erreurs

Les valeurs retournées peuvent indiquer les problèmes suivants :

-ENOMEM

Pas assez de mémoire pour allouer un objet.

-EINVAL

Un argument invalide a été passé.

-ESTALE

La boucle d'événements est déjà terminée.

-ECHILD

La boucle d'événements a été créée dans un autre processus, une autre bibliothèque ou une autre instance de module.

-EDOM

La source d'événements passée n'est pas une source d'événements d'E/S.

-EPERM

Le descripteur de fichier passé ne prend pas en charge l'API epoll(7), par exemple parce qu'il s'agit d'un fichier régulier ou d'un répertoire. Voir epoll_ctl(2) pour plus de détails.

Ajouté dans la version 255.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'appeler setenv() qu'à partir d'une phase précoce du programme, lorsque aucun autre thread n'a été démarré.
