DESCRIPTION

sd_event_add_child() ajoute une nouvelle source d'événement de changement d'état de processus enfant à une boucle d'événements. L'objet boucle d'événements est spécifié dans le paramètre event, l'objet source d'événement est retourné dans le paramètre source. Le paramètre pid spécifie l'ID du processus à surveiller, qui doit être un processus enfant direct du processus appelant. Le paramètre options détermine quels changements d'état seront surveillés. Il doit contenir un masque OR de WEXITED (surveiller la terminaison du processus enfant), WSTOPPED (surveiller l'arrêt du processus enfant par un signal), et WCONTINUED (surveiller la reprise du processus enfant par un signal). Voir waitid(2) pour plus d'informations.

Le handler doit être une fonction à appeler lorsque le processus change d'état ou NULL. La fonction handler recevra le pointeur userdata, qui peut être choisi librement par l'appelant. Le handler reçoit également un pointeur vers une structure siginfo_t contenant des informations sur l'événement du processus enfant. Le handler peut retourner une valeur négative pour signaler une erreur (voir ci-dessous), d'autres valeurs de retour sont ignorées. Si handler est NULL, un handler par défaut qui appelle sd_event_exit(3) sera utilisé.

Un seul handler peut être installé pour un processus enfant spécifique. Le handler est activé pour un seul événement (SD_EVENT_ONESHOT), mais cela peut être modifié avec sd_event_source_set_enabled(3). Si la fonction handler retourne un code d'erreur négatif, elle sera soit désactivée après l'invocation, même si le mode SD_EVENT_ON avait été demandé précédemment, soit elle entraînera la terminaison de la boucle, voir sd_event_source_set_exit_on_failure(3).

Pour détruire un objet source d'événement, utilisez sd_event_source_unref(3), mais notez que la source d'événement n'est retirée de la boucle d'événements que lorsque toutes les références à la source d'événement sont libérées. Pour s'assurer qu'une source d'événement ne se déclenche plus, même lorsqu'une référence est toujours conservée, envisagez de définir la source d'événement sur SD_EVENT_OFF avec sd_event_source_set_enabled(3).

Le signal SIGCHLD doit être bloqué dans tous les threads avant que cette fonction ne soit appelée (en utilisant sigprocmask(2) ou pthread_sigmask(3)).

Si le deuxième paramètre de sd_event_add_child() est passé comme NULL, aucune référence à l'objet source d'événement n'est retournée. Dans ce cas, la source d'événement est considérée comme « flottante » et sera détruite implicitement lorsque la boucle d'événements elle-même sera détruite.

Notez que la fonction handler est invoquée à un moment où le processus enfant n'a pas encore été récupéré (et est donc encore exposé comme un processus zombie par le noyau). Cependant, l'enfant sera récupéré automatiquement après le retour de la fonction. Les processus enfants pour lesquels aucune source d'événement de changement d'état de processus enfant n'est installée ne seront pas récupérés par l'implémentation de la boucle d'événements.

Si le paramètre handler de sd_event_add_child() est NULL, et que la source d'événement se déclenche, cela sera considéré comme une demande de sortie de la boucle d'événements. Dans ce cas, le paramètre userdata, converti en entier, est passé comme paramètre de code de sortie à sd_event_exit(3).

Si à la fois une source d'événement de changement d'état de processus enfant et une source d'événement de signal SIGCHLD sont installées dans la même boucle d'événements, les priorités configurées des sources d'événements déterminent quelle source d'événement est traitée en premier. Si le gestionnaire de signaux est traité en premier, il devrait laisser les processus enfants pour lesquels des sources d'événements de changement d'état de processus enfants sont installées non récupérés.

sd_event_add_child_pidfd() est similaire à sd_event_add_child() mais prend un descripteur de fichier référençant le processus (« pidfd ») au lieu de l'ID numérique du processus. Un descripteur de fichier approprié peut être obtenu via pidfd_open(2) et les appels associés. Le descripteur de fichier passé n'est pas fermé lorsque la source d'événement est à nouveau libérée, à moins que sd_event_source_set_child_pidfd_own() ne soit utilisé pour activer ce comportement. Notez que, quelle que soit la fonction utilisée pour allouer une source d'événement, sd_event_add_child() ou sd_event_add_child_pidfd(), le processus surveillé doit être un processus enfant direct du processus appelant. De plus, dans les deux cas, SIGCHLD doit être bloqué dans le processus appelant.

sd_event_source_get_child_pid() récupère l'ID du processus configuré d'une source d'événement de changement d'état de processus enfant créée précédemment avec sd_event_add_child(). Il prend l'objet source d'événement comme paramètre source et un pointeur vers une variable pid_t pour y retourner l'ID du processus.

sd_event_source_get_child_pidfd() récupère le descripteur de fichier référençant le processus surveillé (« pidfd »). La boucle d'événements utilise en interne des pidfds pour surveiller les processus enfants, que les sources d'événements individuelles soient allouées via sd_event_add_child() ou sd_event_add_child_pidfd(). Si le dernier appel a été utilisé pour allouer la source d'événement, cette fonction retourne le descripteur de fichier original utilisé pour l'allocation. Cet appel prend l'objet source d'événement comme paramètre source et retourne le numéro du descripteur de fichier.

sd_event_source_get_child_pidfd_own() peut être utilisé pour interroger si le pidfd que la source d'événement encapsule doit être fermé lorsque la source d'événement est libérée. Cette fonction retourne zéro si le pidfd doit être laissé ouvert, et une valeur positive s'il doit être fermé automatiquement. Par défaut, ce paramètre vaut 1 si la source d'événement a été allouée via sd_event_add_child() et 0 si elle a été allouée via sd_event_add_child_pidfd(). La fonction sd_event_source_set_child_pidfd_own() peut être utilisée pour modifier le paramètre et prend un paramètre booléen avec le nouveau paramètre.

sd_event_source_get_child_process_own() peut être utilisé pour interroger si le processus que la source d'événement surveille doit être tué (avec SIGKILL) et récupéré lorsque la source d'événement est libérée. Cette fonction retourne zéro si le processus doit être laissé en cours d'exécution, et une valeur positive s'il doit être tué et récupéré automatiquement. Par défaut, ce paramètre vaut 0. #include <systemd/sd-event.h>

DESCRIPTION

La fonction sd_event_add_child() enregistre une nouvelle source d'événement dans la boucle d'événements event qui surveille le processus enfant avec le PID pid. La source d'événement est liée au processus enfant spécifié.

La fonction sd_event_add_child_pidfd() est similaire à sd_event_add_child(), mais elle accepte un descripteur de fichier pidfd pointant vers le processus enfant au lieu du PID. L'utilisation d'un pidfd est plus fiable car il garantit que le descripteur de fichier fait toujours référence au même processus, même s'il est recréé après la fin du processus d'origine.

Lorsque le processus enfant surveillé se termine ou est arrêté, le gestionnaire handler est appelé avec event, le PID de l'enfant, le statut de retour wstatus (comme retourné par waitid(2)), et userdata.

Les events sont un masque de draveaux qui spécifie les événements à surveiller, tirés de waitid(2). Actuellement, seuls WEXITED, WSTOPPED, et WCONTINUED sont pris en charge. Si WEXITED est spécifié, le gestionnaire sera appelé lorsque le processus enfant se termine. Si WSTOPPED est spécifié, le gestionnaire sera appelé lorsque le processus enfant est arrêté par un signal. Si WCONTINUED est spécifié, le gestionnaire sera appelé lorsque le processus enfant arrêté est continué. Il est recommandé de spécifier au moins WEXITED.

Si handler est NULL, un gestionnaire par défaut sera utilisé qui se contente d'arrêter la boucle d'événements avec le statut de retour de l'enfant comme code de sortie.

Si source n'est pas NULL, un pointeur vers la nouvelle source d'événement sera stocké dans *source. L'appelant est responsable de la libération de la source d'événement en appelant sd_event_source_unref(3). Si la source est attachée à la boucle d'événements par défaut, elle devient "flottante" par défaut, c'est-à-dire qu'elle n'empêche pas la boucle de se terminer si la boucle n'a pas d'autres sources actives. Utilisez sd_event_source_set_floating(3) pour changer ce comportement.

Les fonctions sd_event_source_get_child_pid() et sd_event_source_get_child_pidfd() renvoient le PID et le pidfd de l'enfant surveillé, respectivement, pour une source d'événement donnée.

Les fonctions sd_event_source_get_child_process_own() et sd_event_source_set_child_process_own() contrôlent si l'appelant est responsable de la fermeture du descripteur de fichier pidfd (et donc de la fin de la surveillance du processus enfant) lorsque la source d'événement est détruite. Par défaut, la source d'événement ne possède pas le pidfd et ne le ferme pas à sa destruction.

Les fonctions sd_event_source_get_child_pidfd_own() et sd_event_source_set_child_pidfd_own() contrôlent si l'appelant est responsable de la fermeture du descripteur de fichier pidfd (et donc de la fin de la surveillance du processus enfant) lorsque la source d'événement est détruite. Par défaut, la source d'événement ne possède pas le pidfd et ne le ferme pas à sa destruction.

Notez que si la source d'événement est créée avec sd_event_add_child() en utilisant un PID, le processus enfant ne sera pas automatiquement suivi lorsque la source d'événement est détruite. Pour s'assurer que le processus enfant soit effectivement arrêté de la surveillance (et que le descripteur de fichier associé soit fermé), il faut définir le drapeau sd_event_source_set_child_process_own() à true. Si la source d'événement est créée avec sd_event_add_child_pidfd(), vous devez explicitement appeler sd_event_source_set_child_pidfd_own(source, true) si vous souhaitez que la source d'événement ferme le descripteur de fichier pidfd lorsqu'elle est détruite.

Notez que actuellement si le processus appelant est terminé anormalement, le processus surveillé pourrait survivre même si la source d'événement cesse d'exister. Ce comportement pourrait changer éventuellement.

sd_event_source_send_child_signal() peut être utilisé pour envoyer un signal UNIX au processus surveillé via pidfd_send_signal(2). Les paramètres spécifiés correspondent à ceux de l'appel système sous-jacent, à l'exception que info n'est jamais modifié (et est donc déclaré constant). Comme pour l'appel système sous-jacent, le paramètre flags doit actuellement être zéro.

RETURN VALUE

En cas de succès, ces fonctions renvoient 0 ou un entier positif. En cas d'échec, elles renvoient un code d'erreur négatif de style errno.

Errors

Les erreurs renvoyées peuvent indiquer les problèmes suivants :

-ENOMEM

Pas assez de mémoire pour allouer un objet.

-EINVAL

Un argument invalide a été passé. Cela inclut la spécification d'un masque vide dans options ou d'un masque qui contient des valeurs autres qu'une combinaison de WEXITED, WSTOPPED, et WCONTINUED.

-EBUSY

Un gestionnaire est déjà installé pour ce processus enfant, ou SIGCHLD n'est pas bloqué.

-ESTALE

La boucle d'événements est déjà terminée.

-ECHILD

La boucle d'événements a été créée dans un processus, une bibliothèque ou une instance de module différente.

-EDOM

La source d'événement passée n'est pas une source d'événement de processus enfant.

NOTES

Les fonctions décrites ici sont disponibles en tant que bibliothèque partagée, qui peut être compilée et liée avec le fichier pkg-config(1) de libsystemd.

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'appeler setenv() que lors d'une phase précoce du programme, lorsqu'aucun autre thread n'a été démarré.

EXAMPLE

Exemple 1. Arrêter la boucle lorsque l'enfant se termine

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <assert.h>
#include <stdio.h>
#include <unistd.h>
#include <systemd/sd-event.h>
int main(int argc, char **argv) {
  pid_t pid = fork();
  assert(pid >= 0);
  /* SIGCHLD signal must be blocked for sd_event_add_child to work */
  sigset_t ss;
  sigemptyset(&ss);
  sigaddset(&ss, SIGCHLD);
  sigprocmask(SIG_BLOCK, &ss, NULL);
  if (pid == 0)  /* child */
    sleep(1);
  else {         /* parent */
    sd_event *e = NULL;
    int r;
    /* Create the default event loop */
    sd_event_default(&e);
    assert(e);
    /* We create a floating child event source (attached to 'e').
     * The default handler will be called with 666 as userdata, which
     * will become the exit value of the loop. */
    r = sd_event_add_child(e, NULL, pid, WEXITED, NULL, (void*) 666);
    assert(r >= 0);
    r = sd_event_loop(e);
    assert(r == 666);
    sd_event_unref(e);
  }
  return 0;
}
