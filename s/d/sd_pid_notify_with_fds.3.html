NOM

sd_notify, sd_notifyf, sd_pid_notify, sd_pid_notifyf, sd_pid_notify_with_fds, sd_pid_notifyf_with_fds, sd_notify_barrier, sd_pid_notify_barrier - Notifier le gestionnaire de services de l'achèvement du démarrage et d'autres changements d'état du service

SYNOPSIS

#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);

int sd_notifyf(int unset_environment, const char *format, ...);

int sd_pid_notify(pid_t pid, int unset_environment, const char *state);

int sd_pid_notifyf(pid_t pid, int unset_environment, const char *format, ...);

int sd_pid_notify_with_fds(pid_t pid, int unset_environment, const char *state, const int *fds, unsigned n_fds);

int sd_pid_notifyf_with_fds(pid_t pid, int unset_environment, const int *fds, size_t n_fds, const char *format, ...);

int sd_notify_barrier(int unset_environment, uint64_t timeout);

int sd_pid_notify_barrier(pid_t pid, int unset_environment, uint64_t timeout);

DESCRIPTION

sd_notify() peut être appelée par un service pour notifier le gestionnaire de services des changements d'état. Elle peut être utilisée pour envoyer des informations arbitraires, encodées dans une chaîne similaire à un bloc d'environnement. Plus important encore, elle peut être utilisée pour les notifications d'achèvement de démarrage ou de rechargement.

Si le paramètre unset_environment est non nul, sd_notify() annulera la variable d'environnement $NOTIFY_SOCKET avant de retourner (indépendamment du succès ou de l'échec de l'appel de fonction lui-même). Les appels ultérieurs à sd_notify() ne feront alors rien silencieusement, et la variable ne sera plus héritée par les processus enfants.

Le paramètre state doit contenir une liste d'affectations de variables séparées par des sauts de ligne, similaire à un bloc d'environnement. Un saut de ligne final est implicite s'il n'y en a pas. La chaîne peut contenir tout type d'affectations de variables, mais voir la section suivante pour une liste des affectations comprises par le gestionnaire de services.

Notez que systemd acceptera les données de statut envoyées par un service uniquement si l'option NotifyAccess= est correctement définie dans le fichier de définition du service. Voir systemd.service(5) pour les détails.

Notez que les notifications sd_notify() ne peuvent être attribuées correctement aux unités que si le processus d'envoi est toujours en vie au moment où PID 1 traite le message, ou si le processus d'envoi est explicitement suivi à l'exécution par le gestionnaire de services. Ce dernier cas se produit si le gestionnaire de services a initialement bifurqué le processus, c'est-à-dire pour tous les processus correspondant à NotifyAccess=main ou NotifyAccess=exec. Inversement, si un processus auxiliaire de l'unité envoie un message sd_notify() et se termine immédiatement, le gestionnaire de services pourrait ne pas être en mesure d'attribuer correctement le message à l'unité, et donc l'ignorer, même si NotifyAccess=all est défini pour celui-ci.

Par conséquent, pour éliminer toutes les conditions de concurrence liées à la recherche de l'unité du client et à l'attribution correcte des notifications aux unités, sd_notify_barrier() peut être utilisé. Cet appel agit comme un point de synchronisation et garantit que toutes les notifications envoyées avant cet appel ont été prises en compte par le gestionnaire de services lorsqu'il retourne avec succès. L'utilisation de sd_notify_barrier() est nécessaire pour les clients qui ne sont pas invoqués par le gestionnaire de services, sinon ce mécanisme de synchronisation est inutile pour l'attribution des notifications à l'unité.

sd_notifyf() est similaire à sd_notify() mais accepte une chaîne de format printf() et des arguments.

sd_pid_notify() et sd_pid_notifyf() sont similaires à sd_notify() et sd_notifyf() mais acceptent un ID de processus (PID) à utiliser comme PID d'origine pour le message en tant que premier argument. Ceci est utile pour envoyer des messages de notification au nom d'autres processus, à condition que les privilèges appropriés soient disponibles. Effectivement, cela signifie qu'une invocation privilégiée de sd_pid_notify() peut contourner les restrictions NotifyAccess=main ou NotifyAccess=exec appliquées à un service. Si l'argument PID est spécifié comme 0, l'ID de processus du processus appelant est utilisé, auquel cas les appels sont entièrement équivalents à sd_notify() et sd_notifyf().

sd_pid_notify_with_fds() est similaire à sd_pid_notify() mais accepte un tableau supplémentaire de descripteurs de fichiers. Ces descripteurs de fichiers sont envoyés avec le message de notification au gestionnaire de services. Ceci est particulièrement utile pour envoyer des messages "FDSTORE=1", comme décrit ci-dessus. Les arguments supplémentaires sont un pointeur vers le tableau de descripteurs de fichiers plus le nombre de descripteurs de fichiers dans le tableau. Si le nombre de descripteurs de fichiers est passé à 0, l'appel est entièrement équivalent à sd_pid_notify(), c'est-à-dire qu'aucun descripteur de fichier n'est passé. Notez que les descripteurs de fichiers envoyés au gestionnaire de services sur un message sans "FDSTORE=1" sont immédiatement fermés à la réception.

sd_pid_notifyf_with_fds() est une combinaison de sd_pid_notify_with_fds() et sd_notifyf(), c'est-à-dire qu'il accepte à la fois un PID et un ensemble de descripteurs de fichiers en entrée, et traite une chaîne de format pour générer la chaîne d'état.

sd_notify_barrier() permet à l'appelant de se synchroniser par rapport à la réception des messages de notification précédemment envoyés et utilise la commande BARRIER=1. Il accepte une valeur de timeout relative en microsecondes qui est passée à ppoll(2). Une valeur de UINT64_MAX est interprétée comme un délai d'attente infini.

sd_pid_notify_barrier() est identique à sd_notify_barrier(), mais permet de spécifier le PID d'origine pour le message de notification.

AFFECTATIONS BIEN CONNUES

Les affectations suivantes ont une signification définie :

READY=1

Indique au gestionnaire de services que le démarrage du service est terminé, ou que le service a terminé le rechargement de sa configuration. Ceci n'est utilisé par systemd que si le fichier de définition du service a Type=notify ou Type=notify-reload défini. Comme il y a peu d'intérêt à signaler la non-préparation, la seule valeur que les services doivent envoyer est "READY=1" (c'est-à-dire "READY=0" n'est pas défini).

RELOADING=1

Indique au gestionnaire de services que le service commence à recharger sa configuration. Ceci est utile pour permettre au gestionnaire de services de suivre l'état interne du service et de le présenter à l'utilisateur. Notez qu'un service qui envoie cette notification doit également envoyer une notification "READY=1" lorsqu'il a terminé le rechargement de sa configuration. Les rechargements dont le gestionnaire de services est notifié par ces mécanismes sont propagés de la même manière que lorsqu'ils sont initialement initiés par le gestionnaire de services. Ce message est particulièrement pertinent pour les services Type=notify-reload, afin d'informer le gestionnaire de services que la demande de rechargement du service a été reçue et est en cours de traitement.

Ajouté dans la version 217.

STOPPING=1

Indique au gestionnaire de services que le service commence sa fermeture. Ceci est utile pour permettre au gestionnaire de services de suivre l'état interne du service et de le présenter à l'utilisateur.

Ajouté dans la version 217.

MONOTONIC_USEC=...

Un champ transportant l'horodatage monotone (selon CLOCK_MONOTONIC) formaté en décimal en μs, lorsque le message de notification a été généré par le client. Ceci est généralement utilisé en combinaison avec "RELOADING=1", pour permettre au gestionnaire de services de synchroniser correctement les cycles de rechargement. Voir systemd.service(5) pour les détails, spécifiquement "Type=notify-reload".

Ajouté dans la version 253.

STATUS=...

Passe une chaîne de statut en UTF-8 sur une seule ligne au gestionnaire de services qui décrit l'état du service. Ceci est de forme libre et peut être utilisé à diverses fins : les programmes de type fsck pourraient passer des pourcentages d'achèvement et les programmes défaillants pourraient passer un message lisible par l'homme

NOTIFICATIONS

Les messages de notification envoyés par les services sont interprétés par le gestionnaire de services. Les assignations inconnues sont ignorées. Ainsi, il est sûr (mais souvent sans effet) d'envoyer des assignations qui ne figurent pas dans cette liste. Le protocole est extensible, mais il faut veiller à ce que les extensions privées soient reconnaissables comme telles. En particulier, il est recommandé de les préfixer par "X_" suivi d'un identifiant d'espace de noms. Le gestionnaire de services envoie également certains messages à son socket de notification, qui peuvent ensuite être consommés par une machine supervisant ou un gestionnaire de conteneurs plus haut dans la pile. Le gestionnaire de services envoie un certain nombre de champs d'extension, par exemple X_SYSTEMD_UNIT_ACTIVE=, pour plus de détails voir systemd(1).

Les assignations suivantes sont prises en charge :

STATUS=...
Une chaîne d'état lisible par l'homme qui sera affichée dans la sortie de systemctl(1). Exemple : "STATUS=66% des vérifications du système de fichiers terminées..."
Ajouté dans la version 233.
NOTIFYACCESS=...
Réinitialise l'accès au socket de notification d'état du service pendant l'exécution, en remplaçant le paramètre NotifyAccess= dans le fichier d'unité du service. Voir systemd.service(5) pour les détails, en particulier "NotifyAccess=" pour une liste des valeurs acceptées.
Ajouté dans la version 254.
ERRNO=...
Si un service échoue, le code d'erreur de style errno, formaté sous forme de chaîne. Exemple : "ERRNO=2" pour ENOENT.
Ajouté dans la version 233.
BUSERROR=...
Si un service échoue, le code d'erreur de style D-Bus. Exemple : "BUSERROR=org.freedesktop.DBus.Error.TimedOut".
Ajouté dans la version 233.
VARLINKERROR=...
Si un service échoue, le code d'erreur de style Varlink. Exemple : "VARLINKERROR=org.varlink.service.InvalidParameter".
Ajouté dans la version 257.
EXIT_STATUS=...
Le code de sortie d'un service ou du gestionnaire lui-même. Notez que systemd ne consomme actuellement pas cette valeur lorsqu'elle est envoyée par les services, donc cette assignation est uniquement informative. Le gestionnaire enverra cette notification à son socket de notification, qui peut être utilisé pour collecter un code de sortie du système (un conteneur ou une VM) lors de son arrêt. Par exemple, mkosi(1) en tire parti. La valeur à retourner peut être définie via le verbe exit de systemctl(1).
Ajouté dans la version 254.
MAINPID=...
Change l'identifiant du processus principal (PID) du service. Ceci est particulièrement utile dans le cas où le véritable processus principal n'est pas directement créé par le gestionnaire de services. Exemple : "MAINPID=4711".
Ajouté dans la version 233.
MAINPIDFDID=...
L'identifiant de l'inode du pidfd du nouveau processus principal (spécifié via MAINPID=). Ces informations peuvent être acquises via sd_pidfd_get_inode_id(3) sur le pidfd et sont utilisées pour identifier le processus de manière sans compétition. Alternativement, un pidfd peut être envoyé directement au gestionnaire de services (voir MAINPIDFD=1 ci-dessous).
Ajouté dans la version 257.
MAINPIDFD=1
Similaire à MAINPID= avec MAINPIDFDID=, mais le processus est référencé directement par le pidfd passé au gestionnaire de services. Ceci est utile si l'identifiant de pidfd n'est pas pris en charge sur le système. Exactement un descripteur de fichier est attendu pour cette notification.
Ajouté dans la version 257.
WATCHDOG=1
Indique au gestionnaire de services de mettre à jour l'horodatage du chien de garde. Il s'agit du ping de maintien en vie que les services doivent émettre à intervalles réguliers si WatchdogSec= est activé pour eux. Voir systemd.service(5) pour savoir comment activer cette fonctionnalité et sd_watchdog_enabled(3) pour les détails sur la façon dont le service peut vérifier si le chien de garde est activé.
WATCHDOG=trigger
Indique au gestionnaire de services que le service a détecté une erreur interne qui doit être gérée par les options de chien de garde configurées. Cela déclenchera le même comportement que si WatchdogSec= était activé et que le service n'avait pas envoyé "WATCHDOG=1" à temps. Notez que WatchdogSec= n'a pas besoin d'être activé pour que "WATCHDOG=trigger" déclenche l'action du chien de garde. Voir systemd.service(5) pour des informations sur le comportement du chien de garde.
Ajouté dans la version 243.
WATCHDOG_USEC=...
Réinitialise la valeur watchdog_usec pendant l'exécution. Notez que ce n'est pas disponible lors de l'utilisation de sd_event_set_watchdog() ou sd_watchdog_enabled(). Exemple : "WATCHDOG_USEC=20000000"
Ajouté dans la version 233.
EXTEND_TIMEOUT_USEC=...
Indique au gestionnaire de services d'étendre le délai de démarrage, d'exécution ou d'arrêt du service correspondant à l'état actuel. La valeur spécifiée est un temps en microsecondes pendant lequel le service doit envoyer un nouveau message. Un délai d'attente du service se produira si le message n'est pas reçu, mais uniquement si la durée d'exécution de l'état actuel dépasse les temps maximums d'origine de TimeoutStartSec=, RuntimeMaxSec= et TimeoutStopSec=. Voir systemd.service(5) pour les effets sur les délais d'attente du service.
Ajouté dans la version 236.
RESTART_RESET=1
Réinitialise le compteur de redémarrage du service, ce qui a pour effet de restaurer la durée de redémarrage à RestartSec= si RestartSteps= et RestartMaxDelaySec= sont utilisés. Pour plus d'informations, reportez-vous à systemd.service(5).
Ajouté dans la version 258.
FDSTORE=1
Stocke les descripteurs de fichiers dans le gestionnaire de services. Les descripteurs de fichiers envoyés de cette manière seront conservés pour le service par le gestionnaire de services et seront renvoyés plus tard en utilisant la logique habituelle de passage de descripteurs de fichiers lors du prochain démarrage ou redémarrage du service, voir sd_listen_fds(3). Tous les sockets ouverts et autres descripteurs de fichiers qui ne doivent pas être fermés pendant un redémarrage peuvent être stockés de cette manière. Lorsqu'un service est arrêté, son stockage de descripteurs de fichiers est supprimé et tous les descripteurs de fichiers qu'il contient sont fermés, sauf s'ils sont remplacés par FileDescriptorStorePreserve=, voir systemd.service(5).
Le gestionnaire de services acceptera les messages pour un service uniquement si son paramètre FileDescriptorStoreMax= est différent de zéro (par défaut zéro, voir systemd.service(5)). Le gestionnaire de services définira la variable d'environnement $FDSTORE pour les services pour lesquels le stockage de descripteurs de fichiers est activé, voir systemd.exec(5).
Si FDPOLL=0 n'est pas défini et que les descripteurs de fichiers sont sondables (voir epoll_ctl(2)), tout événement EPOLLHUP ou EPOLLERR constaté sur eux entraînera leur suppression automatique du stockage.
Plusieurs ensembles de descripteurs de fichiers peuvent être envoyés dans des messages séparés, auquel cas les ensembles sont combinés. Le gestionnaire de services supprime les descripteurs de fichiers en double (ceux pointant vers le même objet) avant de les passer au service.
Cette fonctionnalité doit être utilisée pour implémenter des services qui peuvent redémarrer après une demande explicite ou un crash sans perdre leur état. L'état de l'application peut être sérialisé dans un fichier dans /run/, ou mieux, stocké dans un descripteur de fichier mémoire memfd_create(2). Utilisez sd_pid_notify_with_fds() pour envoyer des messages avec "FDSTORE=1". Il est recommandé de combiner FDSTORE= avec FDNAME= pour faciliter la gestion des descripteurs de fichiers stockés.
Pour plus d'informations sur le stockage des descripteurs de fichiers, voir l'aperçu Stockage des descripteurs de fichiers[1].
Ajouté dans la version 219.
FDSTOREREMOVE=1
Supprime les descripteurs de fichiers du stockage des descripteurs de fichiers. Ce champ doit être combiné avec FDNAME= pour spécifier le nom des descripteurs de fichiers à supprimer.
Ajouté dans la version 236.
FDNAME=...
Lorsqu'il est utilisé en combinaison avec FDSTORE=1, spécifie un nom pour les descripteurs de fichiers soumis. Lorsqu'il est utilisé avec FDSTOREREMOVE=1, spécifie le nom des descripteurs de fichiers à supprimer. Ce nom est transmis au service lors de l'activation et peut être interrogé à l'aide de sd_listen_fds_with_names(3). Les descripteurs de fichiers soumis sans ce champ seront appelés "stockés".
Le nom peut contenir des caractères ASCII arbitraires à l'exception des caractères de contrôle ou de ":". Il ne peut pas dépasser 255 caractères. Si un nom soumis ne respecte pas ces restrictions, il est ignoré.
Notez que si plusieurs descripteurs de fichiers sont soumis dans un seul message, le nom spécifié sera utilisé pour tous. Afin d'attribuer des noms différents aux descripteurs de fichiers soumis, soumettez-les dans des messages séparés.
Ajouté dans la version 233.
FDPOLL=0
Lorsqu'il est utilisé en combinaison avec FDSTORE=1, désactive le sondage des descripteurs de fichiers soumis, qu'ils soient sondables ou non. Comme cette option désactive le nettoyage automatique des descripteurs de fichiers soumis sur EPOLLERR et EPOLLHUP, il faut veiller à assurer un nettoyage manuel approprié. L'utilisation de cette option n'est généralement pas recommandée, sauf lorsque le nettoyage automatique a un comportement indésirable, comme la suppression prématurée de descripteurs de fichiers du stockage.
Ajouté dans la version 246.
BARRIER=1
Indique au gestionnaire de services que le client demande explicitement une synchronisation en fermant le descripteur de fichier envoyé avec cette commande. Le gestionnaire de services garantit que le traitement d'une commande BARRIER=1 n'aura lieu qu'après le traitement de tous les messages de notification envoyés avant cette commande. Par conséquent, cette commande accompagnée d'un seul descripteur de fichier peut être utilisée pour synchroniser la réception de tous les messages d'état précédents. Notez que cette commande ne peut pas être mélangée avec d'autres notifications, et doit être envoyée dans un message séparé au gestionnaire de services, sinon toutes les assignations seront ignorées. Notez que l'envoi de 0 ou plus d'un descripteur de fichier avec cette commande constitue une violation du protocole.
Ajouté dans la version 246.

NAME

sd_notify, sd_notifyf - send notification message to systemd

SYNOPSIS

#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);

int sd_notifyf(int unset_environment, const char *fmt, ...);

DESCRIPTION

The function sd_notify() may be called by systemd service managers (like systemd.service(5)) or any other process to send a notification message to the systemd manager. This is primarily used to signal service readiness, status changes, or other runtime information.

The service manager listens on the socket specified by the $NOTIFY_SOCKET environment variable. If this variable is not set, sd_notify() does nothing and returns success. If the variable is set, a datagram is sent to the socket specified. The format of the socket path determines the type of socket used:

  • If the path starts with a slash "/", an AF_UNIX socket is assumed.
  • If the path starts with "@", an abstract namespace AF_UNIX socket is assumed (Linux-specific).
  • If the path starts with "vsock:", a AF_VSOCK socket is assumed. The format is "vsock:CID:PORT" or "vsock:[<transport>:]CID:PORT". The transport may be "stream", "dgram", or "seqpacket", defaulting to SOCK_DGRAM.

The message payload is the string passed in the state parameter. The string is a list of parameter-value pairs, separated by newlines. Parameter names are case-sensitive. The following parameter names are recognized by systemd:

  • READY=1: The service is ready and has finished initializing.
  • RELOADING=1: The service is reloading its configuration.
  • STOPPING=1: The service is stopping.
  • STATUS=...: A string describing the current status of the service.
  • BUSNAME=...: The D-Bus name the service is using.
  • ERRNO=...: The errno(3) value from a recent operation that failed. This is useful for the service to report the reason for a failure.
  • MAINPID=...: The PID of the main process of the service.
  • CHILDPID=...: The PID of a child process that the service spawned.
  • WATCHDOG=1: Used in conjunction with the watchdog functionality. The service signals that it is alive and kicking.

The sd_notifyf() function is similar to sd_notify() but takes a printf-style format string and variable arguments to construct the message payload.

The unset_environment parameter controls whether the $NOTIFY_SOCKET environment variable should be unset after the notification is sent. If non-zero, it is unset. This is useful to prevent child processes from inheriting the socket, unless explicitly desired.

If the socket is successfully connected and the message sent, sd_notify() returns a positive value. If the $NOTIFY_SOCKET environment variable is not set, it returns 0. If an error occurs, it returns a negative error code.

The following error codes are commonly returned:

  • -EINVAL: The message string is invalid (e.g., contains invalid characters or is too long).
  • -EACCES: Permission denied to access the socket.
  • -ENOENT: The socket file does not exist.
  • -ECONNREFUSED: The connection to the socket was refused.
  • -EPIPE: The socket is closed.
  • -EAFNOSUPPORT: The socket type specified in $NOTIFY_SOCKET is not supported.

Note that systemd itself does not strictly enforce the format of the messages, but it recognizes the specific parameter names listed above. Other parameters are ignored.

It is recommended to send state transitions like READY and STOPPING only once. Sending multiple READY messages is harmless, but sending multiple STOPPING messages might lead to unexpected behavior.

It is possible to send file descriptors along with the notification message using the FDSTORE=1 option in the message string, and passing the file descriptors via ancillary data. This allows a service to hand over control of resources to systemd. See sd_bus_send(3) for details on sending file descriptors. Note that not all services are configured to permit storing of file descriptors, and attempting to do so when not permitted will result in an error. A specific error is not returned when a file descriptor is attempted to be stored using FDSTORE=1 but the service is not actually configured to permit storing of file descriptors (see above).

Errors

Returned errors may indicate the following problems:

-E2BIG

More file descriptors passed at once than the system allows. On Linux the number of file descriptors that may be passed across AF_UNIX sockets at once is 253, see unix(7) for details.

Added in version 257.

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.

These functions send a single datagram with the state string as payload to the socket referenced in the $NOTIFY_SOCKET environment variable. If the first character of $NOTIFY_SOCKET is "/" or "@", the string is understood as an AF_UNIX or Linux abstract namespace socket (respectively), and in both cases the datagram is accompanied by the process credentials of the sending service, using SCM_CREDENTIALS. If the string starts with "vsock:" then the string is understood as an AF_VSOCK address, which is useful for hypervisors/VMMs or other processes on the host to receive a notification when a virtual machine has finished booting. Note that in case the hypervisor does not support SOCK_DGRAM over AF_VSOCK, SOCK_SEQPACKET will be used instead. "vsock-stream", "vsock-dgram" and "vsock-seqpacket" can be used instead of "vsock" to force usage of the corresponding socket type. The address should be in the form: "vsock:CID:PORT". Note that unlike other uses of vsock, the CID is mandatory and cannot be "VMADDR_CID_ANY". Note that PID1 will send the VSOCK packets from a privileged port (i.e.: lower than 1024), as an attempt to address concerns that unprivileged processes in the guest might try to send malicious notifications to the host, driving it to make destructive decisions based on them.

Standalone Implementations

Note that, while using this library should be preferred in order to avoid code duplication, it is also possible to reimplement the simple readiness notification protocol without external dependencies, as demonstrated in the following self-contained examples from several languages:

C 

/* SPDX-License-Identifier: MIT-0 */
/* Implement the systemd notify protocol without external dependencies.
 * Supports both readiness notification on startup and on reloading,
 * according to the protocol defined at:
 * https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html
 * This protocol is guaranteed to be stable as per:
 * https://systemd.io/PORTABILITY_AND_STABILITY/ */
#define _GNU_SOURCE 1
#include <errno.h>
#include <inttypes.h>
#include <signal.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/un.h>
#include <time.h>
#include <unistd.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
static void closep(int *fd) {
  if (!fd || *fd < 0)
    return;
  close(*fd);
  *fd = -1;
}
static int notify(const char *message) {
  union sockaddr_union {
    struct sockaddr sa;
    struct sockaddr_un sun;
  } socket_addr = {
    .sun.sun_family = AF_UNIX,
  };
  size_t path_length, message_length;
  _cleanup_(closep) int fd = -1;
  const char *socket_path;
  /* Verify the argument first */
  if (!message)
    return -EINVAL;
  message_length = strlen(message);
  if (message_length == 0)
    return -EINVAL;
  /* If the variable is not set, the protocol is a noop */
  socket_path = getenv("NOTIFY_SOCKET");
  if (!socket_path)
    return 0; /* Not set? Nothing to do */
  /* Only AF_UNIX is supported, with path or abstract sockets */
  if (socket_path[0] != '/' && socket_path[0] != '@')
    return -EAFNOSUPPORT;
  path_length = strlen(socket_path);
  /* Ensure there is room for NUL byte */
  if (path_length >= sizeof(socket_addr.sun.sun_path))
    return -E2BIG;
  memcpy(socket_addr.sun.sun_path, socket_path, path_length);
  /* Support for abstract socket */
  if (socket_addr.sun.sun_path[0] == '@')
    socket_addr.sun.sun_path[0] = 0;
  fd = socket(AF_UNIX, SOCK_DGRAM|SOCK_CLOEXEC, 0);
  if (fd < 0)
    return -errno;
  if (connect(fd, &socket_addr.sa, offsetof(struct sockaddr_un, sun_path) + path_length) != 0)
    return -errno;
  ssize_t written = write(fd, message, message_length);
  if (written != (ssize_t) message_length)
    return written < 0 ? -errno : -EPROTO;
  return 1; /* Notified! */
}
static int notify_ready(void) {
  return notify("READY=1");
}
static int notify_reloading(void) {
  /* A buffer with length sufficient to format the maximum UINT64 value. */
  char reload_message[sizeof("RELOADING=1\nMONOTONIC_USEC=18446744073709551615")];
  struct timespec ts;
  uint64_t now;
  /* Notify systemd that we are reloading, including a CLOCK_MONOTONIC timestamp in usec
   * so that the program is compatible with a Type=notify-reload service. */
  if (clock_gettime(CLOCK_MONOTONIC, &ts) < 0)
    return -errno;
  if (ts.tv_sec < 0 || ts.tv_nsec < 0 ||
      (uint64_t) ts.tv_sec > (UINT64_MAX - (ts.tv_nsec / 1000ULL)) / 1000000ULL)
    return -EINVAL;
  now = (uint64_t) ts.tv_sec * 1000000ULL + (uint64_t) ts.tv_nsec / 1000ULL;
  if (snprintf(reload_message, sizeof(reload_message), "RELOADING=1\nMONOTONIC_USEC=%" PRIu64, now) < 0)
    return -EINVAL;
  return notify(reload_message);
}
static int notify_stopping(void) {
  return notify("STOPPING=1");
}
static volatile sig_atomic_t reloading = 0;
static volatile sig_atomic_t terminating = 0;
static void signal_handler(int sig) {
  if (sig == SIGHUP)
    reloading = 1;
  else if (sig == SIGINT || sig == SIGTERM)
    terminating = 1;
}
int main(int argc, char **argv) {
  struct sigaction sa = {
    .sa_handler = signal_handler,
    .sa_flags = SA_RESTART,
  };
  int r;
  /* Setup signal handlers */
  sigemptyset(&sa.sa_mask);
  sigaction(SIGHUP, &sa, NULL);
  sigaction(SIGINT, &sa, NULL);
  sigaction(SIGTERM, &sa, NULL);
  /* Do more service initialization work here ... */
  /* Now that all the preparations steps are done, signal readiness */
  r = notify_ready();
  if (r < 0) {
    fprintf(stderr, "Failed to notify readiness to $NOTIFY_SOCKET: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  while (!terminating) {
    if (reloading) {
      reloading = false;
      /* As a separate but related feature, we can also notify the manager
       * when reloading configuration. This allows accurate state-tracking,
       * and also automated hook-in of 'systemctl reload' without having to
       * specify manually an ExecReload= line in the unit file. */
      r = notify_reloading();
      if (r < 0) {
        fprintf(stderr, "Failed to notify reloading to $NOTIFY_SOCKET: %s\n", strerror(-r));
        return EXIT_FAILURE;
      }
      /* Do some reconfiguration work here ... */
      r = notify_ready();
      if (r < 0) {
        fprintf(stderr, "Failed to notify readiness to $NOTIFY_SOCKET: %s\n", strerror(-r));
        return EXIT_FAILURE;
      }
    }
    /* Do some daemon work here ... */
    sleep(5);
  }
  r = notify_stopping();
  if (r < 0) {
    fprintf(stderr, "Failed to report termination to $NOTIFY_SOCKET: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  /* Do some shutdown work here ... */
  return EXIT_SUCCESS;
}

Python 

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
#
# Implement the systemd notify protocol without external dependencies.
# Supports both readiness notification on startup and on reloading,
# according to the protocol defined at:
# https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html
# This protocol is guaranteed to be stable as per:
# https://systemd.io/PORTABILITY_AND_STABILITY/
import errno
import os
import signal
import socket
import sys
import time
reloading = False
terminating = False
def notify(message):
    if not message:
        raise ValueError("notify() requires a message")
    socket_path = os.environ.get("NOTIFY_SOCKET")
    if not socket_path:
        return
    if socket_path[0] not in ("/", "@"):
        raise OSError(errno.EAFNOSUPPORT, "Unsupported socket type")
    # Handle abstract socket.
    if socket_path[0] == "@":
        socket_path = "\0" + socket_path[1:]
    with socket.socket(socket.AF_UNIX, socket.SOCK_DGRAM | socket.SOCK_CLOEXEC) as sock:
        sock.connect(socket_path)
        sock.sendall(message)
def notify_ready():
    notify(b"READY=1")
def notify_reloading():
    microsecs = time.clock_gettime_ns(time.CLOCK_MONOTONIC) // 1000
    notify(f"RELOADING=1\nMONOTONIC_USEC={microsecs}".encode())
def notify_stopping():
    notify(b"STOPPING=1")
def reload(signum, frame):
    global reloading
    reloading = True
def terminate(signum, frame):
    global terminating
    terminating = True
def main():
    print("Doing initial setup")
    global reloading, terminating
    # Set up signal handlers.
    print("Setting up signal handlers")
    signal.signal(signal.SIGHUP, reload)
    signal.signal(signal.SIGINT, terminate)
    signal.signal(signal.SIGTERM, terminate)
    # Do any other setup work here.
    # Once all setup is done, signal readiness.
    print("Done setting up")
    notify_ready()
    print("Starting loop")
    while not terminating:
        if reloading:
            print("Reloading")
            reloading = False
            # Support notifying the manager when reloading configuration.
            # This allows accurate state tracking as well as automatically
            # enabling 'systemctl reload' without needing to manually
            # specify an ExecReload= line in the unit file.
            notify_reloading()
            # Do some reconfiguration work here.
            print("Done reloading")
            notify_ready()
        # Do the real work here ...
        print("Sleeping for five seconds")
        time.sleep(5)
    print("Terminating")
    notify_stopping()
if __name__ == "__main__":
    sys.stdout.reconfigure(line_buffering=True)
    print("Starting app")
    main()
    print("Stopped app")

ENVIRONNEMENT

$NOTIFY_SOCKET

Défini par le gestionnaire de services pour les processus supervisés afin d'obtenir des notifications d'état et d'achèvement du démarrage. Cette variable d'environnement spécifie le socket auquel sd_notify() communique. Voir ci-dessus pour plus de détails.

EXEMPLES

Exemple 1. Notification de démarrage

Lorsqu'un service a fini de démarrer, il peut émettre l'appel suivant pour notifier le gestionnaire de services :

sd_notify(0, "READY=1");

Exemple 2. Notification de démarrage étendue

Un service pourrait envoyer ce qui suit après avoir terminé l'initialisation :

sd_notifyf(0, "READY=1\n"
              "STATUS=Processing requests...\n"
              "MAINPID=%lu",
           (unsigned long) getpid());

Exemple 3. Notification de la cause de l'erreur

Un service pourrait envoyer ce qui suit peu avant de quitter, en cas d'échec :

sd_notifyf(0, "STATUS=Failed to start up: %s\n"
              "ERRNO=%i",
           strerror_r(errnum, (char[1024]){}, 1024),
           errnum);

Exemple 4. Stocker un descripteur de fichier dans le gestionnaire de services

Pour stocker un descripteur de fichier ouvert dans le gestionnaire de services, afin de continuer l'opération après un redémarrage du service sans perdre d'état, utilisez "FDSTORE=1" :

sd_pid_notify_with_fds(0, 0, "FDSTORE=1\nFDNAME=foobar", &fd, 1);

Exemple 5. Éliminer les conditions de concurrence

Lorsque le client envoyant les notifications n'est pas généré par le gestionnaire de services, il peut se terminer trop rapidement et le gestionnaire de services peut ne pas réussir à les attribuer correctement à l'unité. Pour éviter de telles courses, utilisez sd_notify_barrier() pour vous synchroniser sur la réception de toutes les notifications envoyées avant cet appel.

sd_notify(0, "READY=1");
/* définir le délai d'attente à 5 secondes */
sd_notify_barrier(0, 5 * 1000000);

HISTORIQUE

sd_pid_notify(), sd_pid_notifyf(), et sd_pid_notify_with_fds() ont été ajoutés dans la version 219.

sd_notify_barrier() a été ajouté dans la version 246.

sd_pid_notifyf_with_fds() et sd_pid_notify_barrier() ont été ajoutés dans la version 254.
