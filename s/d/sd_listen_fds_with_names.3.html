SD_LISTEN_FDS(3) sd_listen_fds SD_LISTEN_FDS(3)

NOM

sd_listen_fds, sd_listen_fds_with_names, SD_LISTEN_FDS_START - Vérifier les descripteurs de fichiers passés par le gestionnaire système

SYNTAXE

#include <systemd/sd-daemon.h>
#define SD_LISTEN_FDS_START 3

int sd_listen_fds(int unset_environment);

int sd_listen_fds_with_names(int unset_environment, char*** names);

DESCRIPTION

sd_listen_fds() peut être appelée par un démon pour vérifier les descripteurs de fichiers passés par le gestionnaire de services dans le cadre de l'activation basée sur les sockets et de la logique de stockage des descripteurs de fichiers. Elle retourne le nombre de descripteurs de fichiers reçus. Si aucun descripteur de fichier n'a été reçu, zéro est retourné. Le premier descripteur de fichier peut être trouvé au numéro de descripteur de fichier 3 (c'est-à-dire SD_LISTEN_FDS_START), les descripteurs supplémentaires suivent à 4, 5, 6, ..., s'il y en a.

Les descripteurs de fichiers passés de cette manière peuvent être fermés à volonté par les processus qui les reçoivent : il appartient aux processus eux-mêmes de les fermer après utilisation ou de les laisser ouverts jusqu'à ce que le processus se termine (auquel cas le noyau les ferme automatiquement). Notez que les descripteurs de fichiers reçus par les démons sont des duplicatas des descripteurs de fichiers que le gestionnaire de services a initialement alloués et liés et dont il conserve en permanence une copie (sauf si Accept=yes est utilisé). Cela signifie que toute modification des options de socket et autres changements apportés aux sockets sera également visible par le gestionnaire de services. Plus important encore, il n'est généralement pas une bonne idée d'invoquer shutdown(2) sur de tels sockets, car cela fermera la communication sur le descripteur de fichier que le gestionnaire de services détient pour le même socket. Notez également que si un démon est redémarré (et ses sockets associés ne le sont pas), il recevra des descripteurs de fichiers pour les mêmes sockets que les invocations précédentes, donc toutes les options de socket appliquées précédemment s'appliqueront toujours.

Si un démon reçoit plus d'un descripteur de fichier, ils seront passés dans le même ordre que configuré dans le fichier d'unité de socket systemd (voir systemd.socket(5) pour les détails) — s'il n'y en a qu'un seul tel fichier (voir ci-dessous). Néanmoins, il est recommandé de vérifier les types de sockets corrects avant de les utiliser. Pour simplifier cette vérification, les fonctions sd_is_fifo(3), sd_is_socket(3), sd_is_socket_inet(3), sd_is_socket_unix(3) sont fournies. Afin de maximiser la flexibilité, il est recommandé de rendre ces vérifications aussi lâches que possible sans permettre des configurations incorrectes. C'est-à-dire, souvent, le numéro de port réel auquel un socket est lié importe peu pour le bon fonctionnement du service, il ne devrait donc pas être vérifié. En revanche, le fait qu'un socket soit un socket datagramme ou un socket de flux importe beaucoup pour la logique la plus courante des programmes et devrait être vérifié.

Cet appel de fonction définira le drapeau FD_CLOEXEC pour tous les descripteurs de fichiers passés afin d'éviter leur héritage ultérieur aux enfants du processus appelant.

Si plusieurs unités de socket activent le même service, l'ordre des descripteurs de fichiers passés à son processus principal est indéfini. Si des descripteurs de fichiers supplémentaires ont été passés au gestionnaire de services en utilisant les messages "FDSTORE=1" de sd_pid_notify_with_fds(3), ces descripteurs de fichiers sont passés en dernier, dans un ordre arbitraire, et avec les doublons supprimés.

Si le paramètre unset_environment est différent de zéro, sd_listen_fds() désactivera les variables d'environnement $LISTEN_FDS, $LISTEN_PID et $LISTEN_FDNAMES avant de retourner (indépendamment du succès ou de l'échec de l'appel de fonction lui-même). Les appels ultérieurs à sd_listen_fds() retourneront alors zéro, mais les variables ne seront plus héritées par les processus enfants.

sd_listen_fds_with_names() est identique à sd_listen_fds(), mais retourne en option un tableau de chaînes avec des noms d'identification pour les descripteurs de fichiers passés, si cela est disponible et que le paramètre names n'est pas NULL. Ces informations sont lues à partir de la variable $LISTEN_FDNAMES, qui peut contenir une liste de noms séparés par des deux-points. Pour les services activés par socket, ces noms peuvent être configurés avec le paramètre FileDescriptorName= dans les fichiers d'unité de socket, voir systemd.socket(5) pour les détails. Pour les descripteurs de fichiers poussés dans le stockage de descripteurs de fichiers (voir ci-dessus), le nom est défini via le champ FDNAME= transmis via sd_pid_notify_with_fds(). L'utilisation principale de ces noms concerne les services qui acceptent une variété de descripteurs de fichiers qui ne sont pas reconnaissables uniquement avec des fonctions comme sd_is_socket(), et qui nécessitent donc une identification via un nom. Il est recommandé de ne s'appuyer sur des descripteurs de fichiers nommés que si l'identification via sd_is_socket() et les appels associés ne suffit pas. Notez que les noms utilisés ne sont en aucun cas uniques. Le tableau de chaînes renvoyé a autant d'entrées que de descripteurs de fichiers reçus, plus un pointeur NULL final terminant le tableau. L'appelant doit libérer le tableau lui-même et chacun de ses éléments avec l'appel free() de libc après utilisation. Si le paramètre names est NULL, l'appel est entièrement équivalent à sd_listen_fds().

Dans des conditions spécifiques, les noms spéciaux de descripteurs de fichiers suivants sont retournés :

Tableau 1.  Noms spéciaux

Nom Description
"unknown" Le processus n'a reçu aucun nom pour le descripteur de fichier spécifique du gestionnaire de services.
"stored" Le descripteur de fichier provient du stockage de descripteurs de fichiers du gestionnaire de services par service, et le champ FDNAME= était absent lorsque le descripteur de fichier a été soumis au gestionnaire de services.
"connection" Le service a été activé en mode par connexion en utilisant Accept=yes dans le fichier d'unité de socket, et le descripteur de fichier est le socket de connexion.

Pour plus d'informations sur le stockage des descripteurs de fichiers, voir l'aperçu du
Stockage des descripteurs de fichiers[1].

VALEUR DE RETOUR

En cas d'échec, ces appels retournent un code d'erreur négatif de type errno. Si $LISTEN_FDS/$LISTEN_PID n'était pas défini ou n'était pas correctement défini pour ce démon et donc aucun descripteur de fichier n'a été reçu, 0 est retourné. Sinon, le nombre de descripteurs de fichiers passés est retourné. L'application peut les trouver à partir du descripteur de fichier SD_LISTEN_FDS_START, c'est-à-dire le descripteur de fichier 3.

NOTES

Les fonctions décrites ici sont disponibles en tant que bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) depuis un thread parallèle. Il est recommandé de ne faire des appels à setenv() que depuis une phase précoce du programme lorsque aucun autre thread n'a été démarré.

Internement, sd_listen_fds() vérifie si la variable d'environnement $LISTEN_PID correspond au PID du démon. Sinon, elle retourne immédiatement. Sinon, elle analyse le nombre passé dans la variable d'environnement $LISTEN_FDS, puis définit le drapeau FD_CLOEXEC pour le nombre analysé de descripteurs de fichiers commençant à SD_LISTEN_FDS_START. Enfin, elle retourne le nombre analysé. sd_listen_fds_with_names() fait la même chose mais analyse également $LISTEN_FDNAMES s'il est défini.

Ces fonctions ne sont pas conçues pour les services qui spécifient StandardInput=socket car la variable $LISTEN_FDS n'est pas définie dans leur environnement.

ENVIRONNEMENT

$LISTEN_PID, $LISTEN_FDS, $LISTEN_FDNAMES

Défini par le gestionnaire de services pour les processus supervisés qui utilisent l'activation basée sur les sockets. Cette variable d'environnement spécifie les données que sd_listen_fds() et sd_listen_fds_with_names() analysent. Voir ci-dessus pour les détails.
