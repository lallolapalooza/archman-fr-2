NOM

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interface de notification de changement du journal

SYNTAXE

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

sd_journal_get_fd() renvoie un descripteur de fichier qui peut être interroger de manière asynchrone dans une boucle d'événements externe et qui est signalé dès que le journal change, car de nouvelles entrées ou de nouveaux fichiers ont été ajoutés, une rotation a eu lieu, ou des fichiers ont été supprimés, etc. Le descripteur de fichier est adapté à une utilisation avec poll(2). Utilisez sd_journal_get_events() pour un masque d'événements à surveiller. L'appel prend un argument : l'objet de contexte du journal. Notez que tous les systèmes de fichiers ne sont pas capables de générer les événements nécessaires pour des réveils à partir de ce descripteur de fichier pour que les changements soient remarqués immédiatement. En particulier, les systèmes de fichiers réseau ne génèrent pas d'événements de changement de fichier appropriés dans tous les cas. Les cas comme celui-ci peuvent être détectés avec sd_journal_reliable_fd(), ci-dessous. sd_journal_get_timeout() garantira dans ces cas que les réveils se produisent suffisamment fréquemment pour que les changements soient remarqués, bien qu'avec une certaine latence.

sd_journal_get_events() renverra le masque poll() à attendre. Cette fonction renverra une combinaison de POLLIN et POLLOUT et similaires pour remplir le champ ".events" de struct pollfd.

sd_journal_get_timeout() renverra une valeur de délai d'attente pour une utilisation dans poll(). Elle renvoie une valeur en microsecondes depuis l'époque de CLOCK_MONOTONIC pour expirer l'appel poll() dans timeout_usec. Voir clock_gettime(2) pour les détails sur CLOCK_MONOTONIC. S'il n'y a pas de délai d'attente à attendre, elle remplira (uint64_t) -1 à la place. Notez que poll() prend un délai d'attente relatif en millisecondes plutôt qu'un délai d'attente absolu en microsecondes. Pour convertir le délai d'attente absolu en 'us' en délai relatif en 'ms', utilisez un code comme le suivant :

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

Le code ci-dessus ne fait aucune vérification d'erreur par souci de brièveté. L'entier msec calculé peut être passé directement comme paramètre de délai d'attente de poll().

Après chaque réveil de poll(), sd_journal_process() doit être appelé pour traiter les événements. Cet appel indiquera également quel type de changement a été détecté (voir ci-dessous ; notez que les réveils factices sont possibles).

Une alternative synchrone pour utiliser sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() et sd_journal_process() est sd_journal_wait(). Elle attendra de manière synchrone jusqu'à ce que le journal soit modifié. Le temps maximum pendant lequel cet appel dort peut être contrôlé avec le paramètre timeout_usec. Passez (uint64_t) -1 pour attendre indéfiniment. En interne, cet appel combine simplement sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() et sd_journal_process() en un seul.

sd_journal_reliable_fd() peut être utilisé pour vérifier si les événements de réveil du descripteur de fichier renvoyé par sd_journal_get_fd() sont connus pour être rapidement déclenchés. Sur certains systèmes de fichiers où les événements de changement de fichier du système d'exploitation ne sont pas disponibles (comme NFS), les changements doivent être interrogés de manière répétée, et sont donc détectés avec une latence considérable. Cet appel renverra une valeur positive si les changements du journal sont détectés rapidement et zéro lorsqu'ils doivent être interrogés. Notez qu'il n'est généralement pas nécessaire d'invoquer cette fonction directement, car sd_journal_get_timeout() demandera des délais d'attente appropriés de toute façon.

Notez que toutes les interfaces de notification de changement ci-dessus ne signalent pas les changements instantanément. Des latences sont introduites pour plusieurs raisons : comme mentionné, certains backends de stockage nécessitent un interogation basée sur le temps, dans d'autres cas, les réveils sont optimisés en regroupant les événements, et le système d'exploitation introduit des latences supplémentaires de planification d'E/S/CPU.

VALEUR DE RETOUR

sd_journal_get_fd() renvoie un descripteur de fichier valide en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_get_events() renvoie une combinaison de POLLIN, POLLOUT et similaires en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_reliable_fd() renvoie un entier positif si le descripteur de fichier renvoyé par sd_journal_get_fd() générera des réveils immédiats pour tous les changements du journal. Renvoie 0 s'il peut y avoir une latence.

sd_journal_process() et sd_journal_wait() renvoient un code d'erreur négatif de style errno, ou l'un de SD_JOURNAL_NOP, SD_JOURNAL_APPEND ou SD_JOURNAL_INVALIDATE en cas de succès :

•Si SD_JOURNAL_NOP est renvoyé, le journal n'a pas changé depuis la dernière invocation.
•Si SD_JOURNAL_APPEND est renvoyé, de nouvelles entrées ont été ajoutées à la fin du journal. Dans ce cas, il suffit de continuer à lire à l'emplacement précédent de la fin du journal pour lire les nouvelles entrées ajoutées.
•Si SD_JOURNAL_INVALIDATE, des fichiers du journal ont été ajoutés ou supprimés de l'ensemble des fichiers du journal surveillés (par exemple, en raison d'une rotation ou d'un nettoyage), et donc des entrées pourraient être apparues ou avoir disparu à des endroits arbitraires dans le flux de journalisation, potentiellement avant ou après la fin précédente du flux de journalisation. Si SD_JOURNAL_INVALIDATE est renvoyé, les interfaces utilisateur de visualisation en direct qui souhaitent refléter à l'écran l'état précis des données du journal sur le disque devraient probablement rafraîchir leur affichage entier (par rapport au curseur de l'entrée de journal en haut de l'écran). Les programmes uniquement intéressés par un flux de données de journal strictement séquentiel peuvent traiter SD_JOURNAL_INVALIDATE de la même manière que SD_JOURNAL_APPEND, ignorant ainsi les changements dans la vue du journal antérieurs à l'ancienne fin du flux de journalisation.

SURETE SIGNAL

En général, sd_journal_get_fd(), sd_journal_get_events() et sd_journal_get_timeout() ne sont *pas* "async signal safe" dans le sens de signal-safety(7). Néanmoins, seul le premier appel à l'une de ces trois fonctions effectue des opérations non sûres, donc les appels suivants *sont* sûrs.

sd_journal_process() et sd_journal_wait() ne sont pas sûrs. sd_journal_reliable_fd() est sûr.

NOTES

Toutes les fonctions listées ici sont indépendantes des threads et seul un thread peut opérer sur un objet donné à un moment donné. Différents threads peuvent accéder au même objet à différents moments. Plusieurs objets indépendants peuvent être utilisés à partir de différents threads en parallèle.

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd de pkg-config(1).

sd_journal_wait(3) — systemd

NAME

sd_journal_wait, sd_journal_process, sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_reliable_fd - Wait for journal changes, process journal data, get journal file descriptor, events, timeout, and reliability status

SYNOPSIS

#include <systemd/sd-journal.h>
int sd_journal_wait(sd_journal *j, uint64_t timeout);
int sd_journal_process(sd_journal *j);
int sd_journal_get_fd(sd_journal *j);
uint64_t sd_journal_get_events(sd_journal *j);
int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout);
int sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

The sd_journal_wait() function may be used to block until new data is available in the journal, or until the specified timeout elapses.

The timeout parameter specifies the maximum time in microseconds to wait. If timeout is (uint64_t)-1, the call will block indefinitely until new data is available. If timeout is 0, the call will return immediately without blocking.

The sd_journal_process() function should be called after sd_journal_wait() returns with a positive value, or after any other event that might indicate new journal data is available. It processes all newly available journal entries, making them available for reading via functions like sd_journal_get_data(3). It returns the number of new entries added to the journal, or a negative error code on failure.

The sd_journal_get_fd() function returns the file descriptor that can be used with poll(2) or epoll(7) to wait for new journal entries. This file descriptor should only be used for waiting for new entries and not for reading or writing data. Note that this file descriptor might change over time, so it should be re-queried using sd_journal_get_fd() before each blocking call to poll(2) or epoll(7).

The sd_journal_get_events() function returns the event mask that should be used when polling the file descriptor returned by sd_journal_get_fd(). This mask should be used in the events field of the struct pollfd when calling poll(2).

The sd_journal_get_timeout() function returns the maximum time in microseconds the caller should wait for new journal data. This is useful for integrating with existing event loops, like those provided by poll(2) or epoll(7). If the journal is configured to block indefinitely, the timeout will be (uint64_t)-1. This value can be passed directly to sd_journal_wait() or used as the timeout argument in poll(2).

The sd_journal_reliable_fd() function returns a file descriptor that is guaranteed to be valid even across journal rotation. This file descriptor is less efficient than the one returned by sd_journal_get_fd(), as it requires more complex handling. It should only be used when absolute reliability across journal rotation is required. It is recommended to use sd_journal_get_fd() and sd_journal_process() whenever possible.

RETURN VALUE

sd_journal_wait(): Returns a positive integer representing the number of new entries available in the journal upon success. If the timeout expires, it returns 0. On failure, it returns a negative errno-like value.

sd_journal_process(): Returns the number of new entries added to the journal on success, or a negative errno-like value on failure.

sd_journal_get_fd(): Returns the file descriptor on success, or -1 on failure.

sd_journal_get_events(): Returns the event mask on success, or 0 on failure.

sd_journal_get_timeout(): Returns 0 on success, or a negative errno-like value on failure.

sd_journal_reliable_fd(): Returns the file descriptor on success, or -1 on failure.

SIGNAL SAFETY

The functions listed here are not async-signal-safe. They must not be called from signal handlers.

NOTES

The file descriptor returned by sd_journal_get_fd() is only valid as long as the sd_journal object is valid and has not been closed or re-initialized. It is recommended to call sd_journal_get_fd() before each call to poll(2).

The file descriptor returned by sd_journal_get_fd() might be changed by sd_journal_open(), sd_journal_close(), or other journal control operations. Therefore, it is crucial to re-query the file descriptor and event mask whenever you are about to wait for journal events.

The timeout value returned by sd_journal_get_timeout() is an approximation and may not be perfectly accurate. It is intended for use with poll(2) or similar functions to avoid busy-waiting.

sd_journal_wait() and sd_journal_process() are mutually exclusive. You should use either sd_journal_wait() followed by sd_journal_process(), or poll(2)/epoll(7) on the file descriptor obtained from sd_journal_get_fd() followed by sd_journal_process().

EXAMPLES

Reading journal entries with sd_journal_wait()

int r;
sd_journal *j = NULL;
r = sd_journal_open(&j, SD_JOURNAL_LOCAL_ONLY);
if (r < 0) {
  fprintf(stderr, "Failed to open journal: %s\n", strerror(-r));
  return 1;
}
for (;;) {
  /* Wait for new entries, block indefinitely */
  r = sd_journal_wait(j, (uint64_t) -1);
  if (r < 0) {
    fprintf(stderr, "Failed to wait for journal changes: %s\n", strerror(-r));
    break;
  }
  /* Process all new entries */
  while ((r = sd_journal_process(j)) > 0) {
    const char *d;
    size_t l;
    /* Read and print the MESSAGE field */
    r = sd_journal_get_data(j, "MESSAGE", &d, &l);
    if (r < 0) {
      fprintf(stderr, "Failed to read message field: %s\n", strerror(-r));
      continue;
    }
    printf("%.*s\n", (int) l, (const char*) d);
  }
  if (r < 0) {
    fprintf(stderr, "Failed to process journal entry: %s\n", strerror(-r));
    break;
  }
}
sd_journal_close(j);
return 0;

Waiting with poll() (this example lacks all error checking for the sake of simplicity):

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int wait_for_changes(sd_journal *j) {
  uint64_t t;
  int msec;
  struct pollfd pollfd;
  sd_journal_get_timeout(j, &t);
  if (t == (uint64_t) -1)
    msec = -1;
  else {
    struct timespec ts;
    uint64_t n;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
    msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
  }
  pollfd.fd = sd_journal_get_fd(j);
  pollfd.events = sd_journal_get_events(j);
  poll(&pollfd, 1, msec);
  return sd_journal_process(j);
}
