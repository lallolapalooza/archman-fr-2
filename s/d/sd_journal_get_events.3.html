NOM

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interface de notification de changement du journal

SYNTAXE

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

sd_journal_get_fd() retourne un descripteur de fichier qui peut être interrogé de manière asynchrone dans une boucle d'événements externe et qui est signalé dès que le journal change, car de nouvelles entrées ou de nouveaux fichiers ont été ajoutés, une rotation a eu lieu, ou des fichiers ont été supprimés, et ainsi de suite. Le descripteur de fichier est adapté à une utilisation dans poll(2). Utilisez sd_journal_get_events() pour un masque d'événements à surveiller. L'appel prend un argument : l'objet de contexte du journal. Notez que tous les systèmes de fichiers ne sont pas capables de générer les événements nécessaires pour des réveils depuis ce descripteur de fichier pour que les changements soient immédiatement remarqués. En particulier, les systèmes de fichiers réseau ne génèrent pas d'événements de changement de fichier adaptés dans tous les cas. Des cas comme ceux-ci peuvent être détectés avec sd_journal_reliable_fd(), ci-dessous. sd_journal_get_timeout() garantira dans ces cas que les réveils se produisent assez fréquemment pour que les changements soient remarqués, bien qu'avec une certaine latence.

sd_journal_get_events() retournera le masque de poll() à attendre. Cette fonction retournera une combinaison de POLLIN et POLLOUT et similaires à remplir dans le champ ".events" de struct pollfd.

sd_journal_get_timeout() retournera une valeur de délai d'attente pour une utilisation dans poll(). Ceci retourne une valeur en microsecondes depuis l'époque de CLOCK_MONOTONIC pour expirer poll() dans timeout_usec. Voir clock_gettime(2) pour les détails sur CLOCK_MONOTONIC. S'il n'y a pas de délai d'attente à attendre, ceci remplira (uint64_t) -1 à la place. Notez que poll() prend un délai d'attente relatif en millisecondes plutôt qu'un délai d'attente absolu en microsecondes. Pour convertir le délai absolu 'us' en délai relatif 'ms', utilisez un code comme suit :

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

Le code ci-dessus ne fait aucune vérification d'erreur par souci de brièveté. L'entier msec calculé peut être passé directement comme paramètre de délai d'attente de poll().

Après chaque réveil de poll(), sd_journal_process() doit être appelé pour traiter les événements. Cet appel indiquera également quel type de changement a été détecté (voir ci-dessous ; notez que les réveils erronés sont possibles).

Une alternative synchrone pour utiliser sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() et sd_journal_process() est sd_journal_wait(). Elle attendra de manière synchrone jusqu'à ce que le journal soit modifié. Le temps maximum pendant lequel cet appel dort peut être contrôlé avec le paramètre timeout_usec. Passez (uint64_t) -1 pour attendre indéfiniment. Internement, cet appel combine simplement sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() et sd_journal_process() en un seul.

sd_journal_reliable_fd() peut être utilisé pour vérifier si les événements de réveil du descripteur de fichier retourné par sd_journal_get_fd() sont connus pour être déclenchés rapidement. Sur certains systèmes de fichiers où les événements de changement de fichier de l'OS ne sont pas disponibles (comme NFS), les changements doivent être sondés à plusieurs reprises, et sont donc détectés seulement avec une latence considérable. Cet appel retournera une valeur positive si les changements du journal sont détectés rapidement et zéro lorsqu'ils doivent être sondés. Notez qu'il n'est généralement pas nécessaire d'invoquer cette fonction directement car sd_journal_get_timeout() demandera des délais d'attente appropriés de toute façon.

Notez que toutes les interfaces de notification de changement ci-dessus ne rapportent pas les changements instantanément. Des latences sont introduites pour plusieurs raisons : comme mentionné, certains backends de stockage nécessitent un sondage basé sur le temps, dans d'autres cas, les réveils sont optimisés en fusionnant les événements, et l'OS introduit des latences supplémentaires de planification IO/CPU.

VALEUR DE RETOUR

sd_journal_get_fd() retourne un descripteur de fichier valide en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_get_events() retourne une combinaison de POLLIN, POLLOUT et similaires en cas de succès ou un code d'erreur négatif de style errno.

sd_journal_reliable_fd() retourne un entier positif si le descripteur de fichier retourné par sd_journal_get_fd() générera des réveils immédiatement pour tous les changements du journal. Retourne 0 s'il peut y avoir une latence.

sd_journal_process() et sd_journal_wait() retournent un code d'erreur négatif de style errno, ou l'un des SD_JOURNAL_NOP, SD_JOURNAL_APPEND ou SD_JOURNAL_INVALIDATE en cas de succès :

•Si SD_JOURNAL_NOP est retourné, le journal n'a pas changé depuis la dernière invocation.
•Si SD_JOURNAL_APPEND est retourné, de nouvelles entrées ont été ajoutées à la fin du journal. Dans ce cas, il suffit de continuer à lire à l'emplacement de fin précédent du journal pour lire les entrées nouvellement ajoutées.
•Si SD_JOURNAL_INVALIDATE, des fichiers du journal ont été ajoutés ou supprimés de l'ensemble des fichiers du journal surveillés (par exemple, en raison de la rotation ou du nettoyage), et donc des entrées peuvent être apparues ou disparues à des endroits arbitraires dans le flux de logs, potentiellement avant ou après l'ancienne fin du flux de logs. Si SD_JOURNAL_INVALIDATE est retourné, les interfaces utilisateur de vue en direct qui souhaitent refléter à l'écran l'état précis des données du journal sur disque devraient probablement rafraîchir leur affichage complet (par rapport au curseur de l'entrée de journal en haut de l'écran). Les programmes qui ne s'intéressent qu'à un flux de données de log strictement séquentiel peuvent traiter SD_JOURNAL_INVALIDATE de la même manière que SD_JOURNAL_APPEND, ignorant ainsi les changements apportés à la vue du journal antérieurs à l'ancienne fin du flux de logs.

SÉCURITÉ DES SIGNAUX

En général, sd_journal_get_fd(), sd_journal_get_events(), et sd_journal_get_timeout() ne sont pas "async signal safe" dans le sens de signal-safety(7). Néanmoins, seul le premier appel à l'une de ces trois fonctions effectue des opérations non sûres, donc les appels suivants le sont.

sd_journal_process() et sd_journal_wait() ne sont pas sûrs. sd_journal_reliable_fd() est sûr.

NOTES

Toutes les fonctions listées ici sont indépendantes des threads et seul un thread peut opérer sur un objet donné à un moment donné. Différents threads peuvent accéder au même objet à différents moments. Plusieurs objets indépendants peuvent être utilisés à partir de différents threads en parallèle.

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd de pkg-config(1).

sd_journal_get_events(3) — systemd manual pages

NAME

sd_journal_get_events, sd_journal_get_fd, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd - Get file descriptor and events for journal updates

SYNOPSIS

#include <systemd/sd-journal.h>

sd_journal_get_fd(sd_journal *j);

sd_journal_get_events(sd_journal *j);

sd_journal_get_timeout(sd_journal *j, uint64_t *usec);

sd_journal_process(sd_journal *j);

sd_journal_wait(sd_journal *j, uint64_t usec);

sd_journal_reliable_fd(sd_journal *j);

DESCRIPTION

These functions allow an application to monitor the systemd journal for new entries without polling.

sd_journal_get_fd() returns a file descriptor that the caller may monitor using poll(2) or similar mechanisms. When this file descriptor is ready for reading (i.e. the return value of poll(2) indicates `POLLIN`), it means that new journal entries are available, or that the journal has been rotated, or that some other event has occurred.

sd_journal_get_events() returns the set of events that should be monitored on the file descriptor returned by sd_journal_get_fd(). This is typically a combination of POLLIN and potentially other flags.

sd_journal_get_timeout() returns the maximum time in microseconds to wait for the file descriptor to become ready, in usec. If the journal is configured to rotate on shutdown, or if the journal is known to be finalized, this value may be 0. If the timeout is indefinite, the value is set to (uint64_t) -1. This value may be used as the timeout argument to poll(2).

sd_journal_process() should be called after the file descriptor returned by sd_journal_get_fd() becomes ready. It processes any pending journal events and returns the number of new entries read, or a negative error code.

sd_journal_wait() is a convenience function that combines sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll(2), and sd_journal_process(). It waits until the file descriptor becomes ready or the timeout expires, and then processes the journal. It returns the number of new entries read, or a negative error code.

sd_journal_reliable_fd() returns a file descriptor that is guaranteed to be ready for reading when sd_journal_process() can be called successfully. This is the same file descriptor as returned by sd_journal_get_fd(), but it may be used in situations where sd_journal_get_fd() might return a file descriptor that is not ready for reading, but still valid.

RETURN VALUE

On success, sd_journal_get_fd() returns the file descriptor, and 0 on error. sd_journal_get_events() returns the event mask. sd_journal_get_timeout() returns 0 on success, or a negative value on error. sd_journal_process() and sd_journal_wait() return the number of new entries read, or a negative error code on failure.

The error code returned by these functions might be ECHILD, EINVAL, ENOMEM, ENOTTY, EPIPE, ESTALE, ETIMEDOUT, or EXDEV.

SIGNAL SAFETY

sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), sd_journal_process(), sd_journal_wait(), and sd_journal_reliable_fd() are thread-safe.

If these functions are called from a signal handler, the file descriptor returned by sd_journal_get_fd() or sd_journal_reliable_fd() may be used safely for read operations. However, sd_journal_process() and sd_journal_wait() should not be called directly from a signal handler, as they may block.

NOTES

The file descriptor returned by sd_journal_get_fd() is only valid as long as the sd_journal object exists. After sd_journal_close() is called, the file descriptor is no longer valid.

The return value of sd_journal_process() is the number of journal entries that have been appended to the current journal cursor. It does not necessarily mean that new entries have been written to the journal. For example, if the journal has been rotated, sd_journal_process() may return 0 even though new entries are available.

The sd_journal_wait() function is a convenience wrapper around poll(2) and sd_journal_process(). It is not signal-safe, as poll(2) may block indefinitely.

EXAMPLES

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <systemd/sd-journal.h>

int main(int argc, char *argv[]) {
  sd_journal *j = NULL;
  sd_journal_open(&j, SD_JOURNAL_LOCAL_ONLY);
  /* ... skip previous entries ... */
  sd_journal_seek_tail(j);
  while (sd_journal_next(j) >= 0)
    ;
  /* Now wait for new entries */
  for (;;) {
    int r;
    /* Wait for new entries */
    r = sd_journal_wait(j, (uint64_t) -1);
    if (r < 0) {
      fprintf(stderr, "Failed to wait for next entry: %s\n", strerror(-r));
      break;
    }
    /* Process the new entries */
    r = sd_journal_process(j);
    if (r < 0) {
      fprintf(stderr, "Failed to process journal: %s\n", strerror(-r));
      break;
    }
    if (r == 0)
      /* No new entries, wait again */
      continue;

    /* Print the message of the new entries */
    const void *d;
    size_t l;
    while (sd_journal_get_data(j, "MESSAGE", &d, &l) > 0) {
      printf("%.*s\n", (int) l, (const char*) d);
    }
  }
  sd_journal_close(j);
  return 0;
}

Waiting with poll() (this example lacks all error checking for the sake of simplicity):

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int wait_for_changes(sd_journal *j) {
  uint64_t t;
  int msec;
  struct pollfd pollfd;
  sd_journal_get_timeout(j, &t);
  if (t == (uint64_t) -1)
    msec = -1;
  else {
    struct timespec ts;
    uint64_t n;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
    msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
  }
  pollfd.fd = sd_journal_get_fd(j);
  pollfd.events = sd_journal_get_events(j);
  poll(&pollfd, 1, msec);
  return sd_journal_process(j);
}
