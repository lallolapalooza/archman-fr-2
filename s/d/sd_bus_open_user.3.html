DESCRIPTION

sd_bus_default() acquiert un objet de connexion au bus utilisateur lorsqu'il est appelé depuis une slice utilisateur (toute session sous "user-*.slice", par exemple : "user@1000.service"), ou au bus système sinon. L'objet de connexion est associé au thread appelant. Chaque fois que la fonction est appelée depuis le même thread, le même objet est renvoyé, mais son compteur de références est incrémenté d'une unité, tant qu'au moins une référence est conservée. Lorsque la dernière référence à la connexion est libérée (en utilisant l'appel sd_bus_unref(3)), la connexion est terminée. Notez que la connexion n'est pas automatiquement terminée lorsque le thread associé se termine. Il est important de libérer explicitement la dernière référence à la connexion bus avant la fin du thread, sinon la connexion fuira. De plus, les messages mis en file d'attente mais non lus ou non écrits maintiennent une référence au bus, voir ci-dessous.

sd_bus_default_user() renvoie un objet de connexion au bus utilisateur associé au thread appelant. sd_bus_default_system() est similaire, mais se connecte au bus système. Notez que sd_bus_default() est identique à ces deux appels, en fonction du contexte d'exécution.

sd_bus_open() crée une nouvelle connexion bus indépendante au bus utilisateur lorsqu'elle est appelée dans un contexte utilisateur, ou au bus système sinon. sd_bus_open_user() est similaire, mais ne se connecte qu'au bus utilisateur. sd_bus_open_system() fait de même, mais se connecte au bus système. Contrairement à sd_bus_default(), sd_bus_default_user() et sd_bus_default_system(), ces appels renvoient de nouveaux objets de connexion indépendants qui ne sont pas associés au thread appelant et ne sont pas partagés entre plusieurs invocations. Il est recommandé de partager les connexions par thread pour utiliser efficacement les ressources disponibles. Ainsi, il est recommandé d'utiliser sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() pour se connecter aux bus utilisateur ou système.

sd_bus_open_with_description(), sd_bus_open_user_with_description() et sd_bus_open_system_with_description() sont similaires à sd_bus_open(), sd_bus_open_user() et sd_bus_open_system(), mais permettent de définir une chaîne de description, voir sd_bus_set_description(3). description peut être NULL, auquel cas cette fonction est équivalente à sd_bus_open(). Cette chaîne de description est utilisée dans les messages de journal concernant l'objet bus, et l'inclusion d'un "nom" pour le bus les rend plus faciles à comprendre. Certains messages sont émis pendant l'initialisation du bus, donc l'utilisation de cette fonction est préférable à la définition de la description ultérieurement avec sd_bus_open_with_description(). L'argument est copié en interne et ne sera pas référencé après le retour de la fonction.

Si la variable d'environnement $DBUS_SESSION_BUS_ADDRESS est définie (cf. environ(7)), elle sera utilisée comme adresse du bus utilisateur. Cette variable peut contenir plusieurs adresses séparées par des ";". Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance D-Bus utilisateur par défaut sera utilisée.

Si la variable d'environnement $DBUS_SYSTEM_BUS_ADDRESS est définie, elle sera utilisée comme adresse du bus système. Cette variable utilise la même syntaxe que $DBUS_SESSION_BUS_ADDRESS. Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance D-Bus système par défaut sera utilisée.

sd_bus_open_system_remote() se connecte au bus système sur l'hôte spécifié en utilisant ssh(1). host est constitué d'un nom d'utilisateur optionnel suivi du symbole "@", et du nom d'hôte, optionnellement suivi d'un ":" et d'un port, optionnellement suivi d'un "/" et d'un nom de machine. Si le nom de machine est donné, une connexion est créée vers le bus système dans le conteneur spécifié sur la machine distante, et sinon une connexion vers le bus système sur l'hôte spécifié est créée.

Notez que l'entrée dans un conteneur est une opération privilégiée, et ne fonctionnera probablement que pour l'utilisateur root sur la machine distante.

sd_bus_open_system_machine() se connecte au bus système dans la machine spécifiée, où machine est le nom d'un conteneur local, potentiellement préfixé par un nom d'utilisateur et un "@" séparateur. Si le nom du conteneur est spécifié comme la chaîne spéciale ".host", la connexion est établie vers le système local. Ceci est utile pour se connecter au bus système local en tant qu'utilisateur spécifique, par exemple "foobar@.host" pour se connecter au bus système local en tant qu'utilisateur local "foobar". Si la syntaxe "@" est utilisée, soit la partie gauche, soit la partie droite peut être omise (mais pas les deux) auquel cas le nom d'utilisateur local ou ".host" est implicite. Si la syntaxe "@" n'est pas utilisée, la connexion est toujours établie en tant qu'utilisateur root. Voir sd_bus_set_address(3) pour une description de la syntaxe d'adresse, et machinectl(1) pour plus d'informations sur le concept de "machine". Notez que les connexions dans les conteneurs locaux ne sont actuellement disponibles que pour les processus privilégiés.

sd_bus_open_user_machine() est similaire à sd_bus_open_system_machine(), mais se connecte au bus utilisateur de l'utilisateur root, ou si la syntaxe "@" est utilisée, de l'utilisateur spécifié.

Ces appels allouent un objet de connexion bus et initient la connexion à un bus bien connu sous une forme ou une autre. Une alternative à l'utilisation de ces appels de haut niveau est de créer un objet bus non connecté avec sd_bus_new(3) et de le connecter avec sd_bus_start(3).

PROPRIETE DES REFERENCES

Les fonctions sd_bus_open(), sd_bus_open_user(), sd_bus_open_user_machine(), sd_bus_open_system(), sd_bus_open_system_remote() et sd_bus_open_system_machine() renvoient un nouvel objet de connexion et l'appelant en possède la seule référence. Lorsqu'elle n'est plus nécessaire, cette référence doit être détruite avec sd_bus_unref(3).

Les fonctions sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() ne créent pas nécessairement un nouvel objet, mais incrémentent la référence de connexion d'un objet de connexion existant d'une unité. Utilisez sd_bus_unref(3) pour libérer la référence.

Les messages mis en file d'attente mais non écrits/non lus conservent une référence à leur objet de connexion bus. Pour cette raison, même si une application a libéré toutes les références à une connexion bus, elle pourrait ne pas être détruite immédiatement. Tant que tous les messages entrants mis en file d'attente n'auront pas été lus, et tant que tous les messages sortants non écrits n'auront pas été écrits, l'objet bus restera actif. sd_bus_flush() peut être utilisé pour écrire tous les messages sortants mis en file d'attente afin qu'ils libèrent leurs références. DESCRIPTION

These functions establish a connection to a D-Bus bus instance. The connection object is returned in the memory location pointed to by bus. This object should be later passed to sd_bus_unref(3).

sd_bus_open_user() connects to the user session bus of the current user. This is the same bus that is made available via the environment variable $DBUS_SESSION_BUS_ADDRESS.

sd_bus_open_system() connects to the system bus. This is the same bus that is available via the environment variable $DBUS_SYSTEM_BUS_ADDRESS.

sd_bus_default_user() and sd_bus_default_system() are equivalent to sd_bus_open_user() and sd_bus_open_system(), respectively, but are intended for use when accessing the "default" bus object of the process, as described in sd-bus(3). Only one default bus connection per process is allowed.

sd_bus_open() is an alias for sd_bus_default_system(). It is provided for backward compatibility.

sd_bus_open_system_remote() connects to a remote system bus identified by host. The connection is established using the specified protocol described by path. This is typically used for connecting to a bus via ssh(1). Use "ssh://user@host/path" for the path. For details, see sd_bus_set_proxy(3). If host is NULL, the connection is attempted via the settings in the $DBUS_SESSION_BUS_ADDRESS environment variable.

sd_bus_open_system_machine() connects to the system bus of a local system container or virtual machine identified by machine. The connection is established using native socket activation. This is useful for connecting to the bus inside a systemd-driven container or VM managed by systemd-machined.service(8). If machine is NULL, the connection is attempted via the settings in the $DBUS_SYSTEM_BUS_ADDRESS environment variable.

sd_bus_open_user_machine() is similar to sd_bus_open_system_machine(), but connects to the user bus within the specified container or virtual machine.

sd_bus_open_with_description(), sd_bus_open_user_with_description(), and sd_bus_open_system_with_description() are similar to sd_bus_open(), sd_bus_open_user(), and sd_bus_open_system(), respectively, but allow the connection to be configured via a description string. See sd_bus_add_proxy(3) for details on the format of the description string.

REFERENCE OWNERSHIP

The returned bus object is owned by the caller. It should be unreferenced using sd_bus_unref(3) when no longer needed. When using the default bus objects (see sd-bus(3)), the reference count is implicitly managed. You should not call sd_bus_ref(3) or sd_bus_unref(3) on these. Instead, when the program terminates, the bus connection should be closed by calling sd_bus_flush(3) followed by sd_bus_close(). When using the default bus logic, it is a good idea to first invoke sd_bus_flush() followed by sd_bus_close() when a thread or process terminates, and thus its bus connection object should be freed.

Normally, slot objects (as created by sd_bus_add_match(3) and similar calls) keep a reference to their bus connection object, too. Thus, as long as a bus slot object remains referenced its bus object will remain allocated too. Optionally, bus slot objects may be placed in "floating" mode. When in floating mode the life cycle of the bus slot object is bound to the bus object, i.e. when the bus object is freed the bus slot object is automatically unreferenced too. The floating state of a slot object may be controlled explicitly with sd_bus_slot_set_floating(3), though usually floating bus slot objects are created by passing NULL as the slot parameter of sd_bus_add_match() and related calls, thus indicating that the caller is not directly interested in referencing and managing the bus slot object.

The life cycle of the default bus connection should be the responsibility of the code that creates/owns the thread the default bus connection object is associated with. Library code should neither call sd_bus_flush() nor sd_bus_close() on default bus objects unless it does so in its own private, self-allocated thread. Library code should not use the default bus object in other threads unless it is clear that the program using it will life cycle the bus connection object and flush and close it before exiting from the thread. In libraries where it is not clear that the calling program will life cycle the bus connection object, it is hence recommended to use sd_bus_open_system() instead of sd_bus_default_system() and related calls.

RETURN VALUE

On success, these calls return 0 or a positive integer. On failure, these calls return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

The specified parameters are invalid.

-ENOMEDIUM

The requested bus type is not available because of invalid environment (for example the user session bus is not available because $XDG_RUNTIME_DIR is not set).

-ENOMEM

Memory allocation failed.

-ESOCKTNOSUPPORT

The protocol version required to connect to the selected bus is not supported.

In addition, other connection-related errors may be returned. See sd_bus_send(3).

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
