NOM

sd_notify, sd_notifyf, sd_pid_notify, sd_pid_notifyf, sd_pid_notify_with_fds, sd_pid_notifyf_with_fds, sd_notify_barrier, sd_pid_notify_barrier - Notifier le gestionnaire de services de l'achèvement du démarrage et d'autres changements d'état du service

SYNTAXE

#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);

int sd_notifyf(int unset_environment, const char *format, ...);

int sd_pid_notify(pid_t pid, int unset_environment, const char *state);

int sd_pid_notifyf(pid_t pid, int unset_environment, const char *format, ...);

int sd_pid_notify_with_fds(pid_t pid, int unset_environment, const char *state, const int *fds, unsigned n_fds);

int sd_pid_notifyf_with_fds(pid_t pid, int unset_environment, const int *fds, size_t n_fds, const char *format, ...);

int sd_notify_barrier(int unset_environment, uint64_t timeout);

int sd_pid_notify_barrier(pid_t pid, int unset_environment, uint64_t timeout);

DESCRIPTION

sd_notify() peut être appelée par un service pour notifier au gestionnaire de services des changements d'état. Elle peut être utilisée pour envoyer des informations arbitraires, encodées dans une chaîne de caractères ressemblant à un bloc d'environnement. Le plus important, elle peut être utilisée pour les notifications d'achèvement du démarrage ou du rechargement.

Si le paramètre unset_environment est non nul, sd_notify() désactivera la variable d'environnement $NOTIFY_SOCKET avant de retourner (indépendamment du fait que l'appel de fonction lui-même ait réussi ou non). Les appels ultérieurs à sd_notify() ne feront alors rien silencieusement, et la variable ne sera plus héritée par les processus enfants.

Le paramètre state doit contenir une liste d'affectations de variables séparées par des sauts de ligne, similaire dans le style à un bloc d'environnement. Un saut de ligne final est implicite si aucun n'est spécifié. La chaîne peut contenir tout type d'affectations de variables, mais voir la section suivante pour une liste des affectations comprises par le gestionnaire de services.

Notez que systemd acceptera les données d'état envoyées par un service uniquement si l'option NotifyAccess= est correctement définie dans le fichier de définition du service. Voir systemd.service(5) pour les détails.

Notez que les notifications sd_notify() ne peuvent être attribuées correctement aux unités que si soit le processus envoyant est toujours actif au moment où PID 1 traite le message, soit si le processus envoyant est explicitement suivi à l'exécution par le gestionnaire de services. Ce dernier cas se produit si le gestionnaire de services a initialement lancé le processus, c'est-à-dire pour tous les processus qui correspondent à NotifyAccess=main ou NotifyAccess=exec. Inversement, si un processus auxiliaire de l'unité envoie un message sd_notify() et se termine immédiatement, le gestionnaire de services peut ne pas être en mesure d'attribuer correctement le message à l'unité, et donc l'ignorera, même si NotifyAccess=all est défini pour elle.

Par conséquent, pour éliminer toutes les conditions de concurrence impliquant la recherche de l'unité du client et l'attribution correcte des notifications aux unités, sd_notify_barrier() peut être utilisée. Cet appel agit comme un point de synchronisation et garantit que toutes les notifications envoyées avant cet appel ont été prises en compte par le gestionnaire de services lorsqu'il retourne avec succès. L'utilisation de sd_notify_barrier() est nécessaire pour les clients qui ne sont pas invoqués par le gestionnaire de services, sinon ce mécanisme de synchronisation est inutile pour l'attribution des notifications à l'unité.

sd_notifyf() est similaire à sd_notify() mais prend une chaîne de format printf() et des arguments.

sd_pid_notify() et sd_pid_notifyf() sont similaires à sd_notify() et sd_notifyf() mais prennent un identifiant de processus (PID) à utiliser comme PID d'origine pour le message comme premier argument. Ceci est utile pour envoyer des messages de notification au nom d'autres processus, à condition que les privilèges appropriés soient disponibles. Effectivement, cela signifie qu'une invocation privilégiée de sd_pid_notify() peut contourner les restrictions NotifyAccess=main ou NotifyAccess=exec appliquées à un service. Si l'argument PID est spécifié comme 0, l'identifiant du processus appelant est utilisé, auquel cas les appels sont entièrement équivalents à sd_notify() et sd_notifyf().

sd_pid_notify_with_fds() est similaire à sd_pid_notify() mais prend un tableau supplémentaire de descripteurs de fichiers. Ces descripteurs de fichiers sont envoyés avec le message de notification au gestionnaire de services. Ceci est particulièrement utile pour envoyer des messages "FDSTORE=1", comme décrit ci-dessus. Les arguments supplémentaires sont un pointeur vers le tableau de descripteurs de fichiers plus le nombre de descripteurs de fichiers dans le tableau. Si le nombre de descripteurs de fichiers est passé à 0, l'appel est entièrement équivalent à sd_pid_notify(), c'est-à-dire qu'aucun descripteur de fichier n'est passé. Notez que les descripteurs de fichiers envoyés au gestionnaire de services sur un message sans "FDSTORE=1" sont immédiatement fermés à la réception.

sd_pid_notifyf_with_fds() est une combinaison de sd_pid_notify_with_fds() et sd_notifyf(), c'est-à-dire qu'elle accepte à la fois un PID et un ensemble de descripteurs de fichiers en entrée, et traite une chaîne de format pour générer la chaîne d'état.

sd_notify_barrier() permet à l'appelant de se synchroniser avec la réception des messages de notification précédemment envoyés et utilise la commande BARRIER=1. Elle prend une valeur de timeout relative en microsecondes qui est passée à ppoll(2). Une valeur de UINT64_MAX est interprétée comme un timeout infini.

sd_pid_notify_barrier() est identique à sd_notify_barrier(), mais permet de spécifier le PID d'origine pour le message de notification.

AFFECTATIONS BIEN CONNUES

Les affectations suivantes ont une signification définie :

READY=1

Indique au gestionnaire de services que le démarrage du service est terminé, ou que le service a terminé le rechargement de sa configuration. Ceci n'est utilisé par systemd que si le fichier de définition du service a Type=notify ou Type=notify-reload défini. Comme il y a peu d'intérêt à signaler une non-disponibilité, la seule valeur que les services devraient envoyer est "READY=1" (c'est-à-dire que "READY=0" n'est pas défini).

RELOADING=1

Indique au gestionnaire de services que le service commence à recharger sa configuration. Ceci est utile pour permettre au gestionnaire de services de suivre l'état interne du service et de le présenter à l'utilisateur. Notez qu'un service qui envoie cette notification doit également envoyer une notification "READY=1" lorsqu'il a terminé le rechargement de sa configuration. Les rechargements dont le gestionnaire de services est informé par ce mécanisme sont propagés de la même manière qu'ils le sont lorsqu'ils sont initialement initiés via le gestionnaire de services. Ce message est particulièrement pertinent pour les services Type=notify-reload, pour informer le gestionnaire de services que la demande de rechargement du service a été reçue et est en cours de traitement.

Ajouté dans la version 217.

STOPPING=1

Indique au gestionnaire de services que le service commence sa fermeture. Ceci est utile pour permettre au gestionnaire de services de suivre l'état interne du service et de le présenter à l'utilisateur.

Ajouté dans la version 217.

MONOTONIC_USEC=...

Un champ transportant l'horodatage monotone (conformément à CLOCK_MONOTONIC) formaté en décimal en μs, lorsque le message de notification a été généré par le client. Ceci est généralement utilisé en combinaison avec "RELOADING=1", pour permettre au gestionnaire de services de synchroniser correctement les cycles de rechargement. Voir systemd.service(5) pour les détails, notamment "Type=notify-reload".

Ajouté dans la version 253.

STATUS=...

Transmet une chaîne d'état UTF-8 sur une seule ligne au gestionnaire de services qui décrit l'état du service. Ceci est de forme libre et peut être utilisé à diverses fins : les programmes de type fsck pourraient passer des pourcentages d'achèvement et les programmes défaillants pourraient passer une description lisible par l'homme d'er

Ajouté dans la version 233.

NOTIFYACCESS=...

Réinitialise l'accès à la socket de notification d'état du service pendant l'exécution, en remplaçant le paramètre NotifyAccess= dans le fichier d'unité du service. Voir systemd.service(5) pour plus de détails, en particulier "NotifyAccess=" pour une liste des valeurs acceptées.

Ajouté dans la version 254.

ERRNO=...

Si un service échoue, le code d'erreur de style errno, formaté en chaîne de caractères. Exemple : "ERRNO=2" pour ENOENT.

Ajouté dans la version 233.

BUSERROR=...

Si un service échoue, le code d'erreur de style D-Bus. Exemple : "BUSERROR=org.freedesktop.DBus.Error.TimedOut".

Ajouté dans la version 233.

VARLINKERROR=...

Si un service échoue, le code d'erreur de style Varlink. Exemple : "VARLINKERROR=org.varlink.service.InvalidParameter".

Ajouté dans la version 257.

EXIT_STATUS=...

L'état de sortie d'un service ou du gestionnaire lui-même. Notez que systemd ne consomme actuellement pas cette valeur lorsqu'elle est envoyée par les services, cette affectation est donc uniquement informative. Le gestionnaire envoie cette notification à sa socket de notification, qui peut être utilisée pour collecter un état de sortie du système (un conteneur ou une VM) lors de son arrêt. Par exemple, mkosi(1) utilise ceci. La valeur à retourner peut être définie via le verbe exit de systemctl(1).

Ajouté dans la version 254.

MAINPID=...

Modifie l'identifiant du processus principal (PID) du service. Ceci est particulièrement utile dans le cas où le véritable processus principal n'est pas directement issu d'un fork du gestionnaire de services. Exemple : "MAINPID=4711".

Ajouté dans la version 233.

MAINPIDFDID=...

Le numéro d'inode du pidfd du nouveau processus principal (spécifié via MAINPID=). Ces informations peuvent être obtenues via sd_pidfd_get_inode_id(3) sur le pidfd et sont utilisées pour identifier le processus de manière sans concurrence. Alternativement, un pidfd peut être envoyé directement au gestionnaire de services (voir MAINPIDFD=1 ci-dessous).

Ajouté dans la version 257.

MAINPIDFD=1

Similaire à MAINPID= avec MAINPIDFDID=, mais le processus est référencé directement par le pidfd passé au gestionnaire de services. Ceci est utile si l'ID du pidfd n'est pas pris en charge sur le système. Exactement un descripteur de fichier est attendu pour cette notification.

Ajouté dans la version 257.

WATCHDOG=1

Indique au gestionnaire de services de mettre à jour l'horodatage du chien de garde. Il s'agit du ping de maintien en vie que les services doivent émettre à intervalles réguliers si WatchdogSec= est activé pour eux. Voir systemd.service(5) pour savoir comment activer cette fonctionnalité et sd_watchdog_enabled(3) pour les détails sur la façon dont le service peut vérifier si le chien de garde est activé.

WATCHDOG=trigger

Indique au gestionnaire de services que le service a détecté une erreur interne qui doit être gérée par les options de chien de garde configurées. Cela déclenchera le même comportement que si WatchdogSec= est activé et que le service n'a pas envoyé "WATCHDOG=1" à temps. Notez que WatchdogSec= n'a pas besoin d'être activé pour que "WATCHDOG=trigger" déclenche l'action du chien de garde. Voir systemd.service(5) pour des informations sur le comportement du chien de garde.

Ajouté dans la version 243.

WATCHDOG_USEC=...

Réinitialise la valeur watchdog_usec pendant l'exécution. Notez que cela n'est pas disponible lors de l'utilisation de sd_event_set_watchdog() ou sd_watchdog_enabled(). Exemple : "WATCHDOG_USEC=20000000"

Ajouté dans la version 233.

EXTEND_TIMEOUT_USEC=...

Indique au gestionnaire de services d'étendre le délai d'attente de démarrage, d'exécution ou d'arrêt du service correspondant à l'état actuel. La valeur spécifiée est un temps en microsecondes pendant lequel le service doit envoyer un nouveau message. Un délai d'attente du service se produira si le message n'est pas reçu, mais seulement si la durée d'exécution de l'état actuel dépasse les temps maximums d'origine de TimeoutStartSec=, RuntimeMaxSec=, et TimeoutStopSec=. Voir systemd.service(5) pour les effets sur les délais d'attente des services.

Ajouté dans la version 236.

RESTART_RESET=1

Réinitialise le compteur de redémarrage du service, ce qui a pour effet de rétablir la durée de redémarrage à RestartSec= si RestartSteps= et RestartMaxDelaySec= sont utilisés. Pour plus d'informations, reportez-vous à systemd.service(5).

Ajouté dans la version 258.

FDSTORE=1

Stocke les descripteurs de fichiers dans le gestionnaire de services. Les descripteurs de fichiers envoyés de cette manière seront conservés pour le service par le gestionnaire de services et seront rendus plus tard en utilisant la logique habituelle de passage de descripteurs de fichiers lors du prochain démarrage ou redémarrage du service, voir sd_listen_fds(3). Tous les sockets ouverts et autres descripteurs de fichiers qui ne doivent pas être fermés lors d'un redémarrage peuvent être stockés de cette manière. Lorsqu'un service est arrêté, son magasin de descripteurs de fichiers est supprimé et tous les descripteurs de fichiers qu'il contient sont fermés, sauf si cela est remplacé par FileDescriptorStorePreserve=, voir systemd.service(5).

Le gestionnaire de services acceptera les messages pour un service uniquement si son paramètre FileDescriptorStoreMax= est différent de zéro (par défaut zéro, voir systemd.service(5)). Le gestionnaire de services définira la variable d'environnement $FDSTORE pour les services pour lesquels le magasin de descripteurs de fichiers est activé, voir systemd.exec(5).

Si FDPOLL=0 n'est pas défini et que les descripteurs de fichiers sont pollables (voir epoll_ctl(2)), tout événement EPOLLHUP ou EPOLLERR observé sur eux entraînera leur suppression automatique du magasin.

Plusieurs ensembles de descripteurs de fichiers peuvent être envoyés dans des messages distincts, auquel cas les ensembles sont combinés. Le gestionnaire de services supprime les descripteurs de fichiers dupliqués (ceux pointant vers le même objet) avant de les passer au service.

Cette fonctionnalité doit être utilisée pour implémenter des services qui peuvent redémarrer après une demande explicite ou un crash sans perte d'état. L'état de l'application peut être sérialisé dans un fichier dans /run/, ou mieux, stocké dans un descripteur de fichier mémoire memfd_create(2). Utilisez sd_pid_notify_with_fds() pour envoyer des messages avec "FDSTORE=1". Il est recommandé de combiner FDSTORE= avec FDNAME= pour faciliter la gestion des descripteurs de fichiers stockés.

Pour plus d'informations sur le magasin de descripteurs de fichiers, voir l'aperçu du magasin de descripteurs de fichiers[1].

Ajouté dans la version 219.

FDSTOREREMOVE=1

Supprime les descripteurs de fichiers du magasin de descripteurs de fichiers. Ce champ doit être combiné avec FDNAME= pour spécifier le nom des descripteurs de fichiers à supprimer.

Ajouté dans la version 236.

FDNAME=...

Lorsqu'il est utilisé en combinaison avec FDSTORE=1, spécifie un nom pour les descripteurs de fichiers soumis. Lorsqu'il est utilisé avec FDSTOREREMOVE=1, spécifie le nom des descripteurs de fichiers à supprimer. Ce nom est passé au service lors de l'activation et peut être interrogé en utilisant sd_listen_fds_with_names(3). Les descripteurs de fichiers soumis sans ce champ seront appelés "stockés".

Le nom peut contenir des caractères ASCII arbitraires à l'exception des caractères de contrôle ou de ":". Il ne peut pas dépasser 255 caractères. Si un nom soumis ne respecte pas ces restrictions, il est ignoré.

Notez que si plusieurs descripteurs de fichiers sont soumis dans un seul message, le nom spécifié sera utilisé pour tous. Afin d'attribuer des noms différents aux descripteurs de fichiers soumis, soumettez-les dans des messages séparés.

Ajouté dans la version 233.

FDPOLL=0

Lorsqu'il est utilisé en combinaison avec FDSTORE=1, désactive l'interrogation des descripteurs de fichiers soumis, qu'ils soient ou non polables. Comme cette option désactive le nettoyage automatique des descripteurs de fichiers soumis lors de EPOLLERR et EPOLLHUP, il faut veiller à assurer un nettoyage manuel approprié. L'utilisation de cette option n'est généralement pas recommandée, sauf lorsque le nettoyage automatique a un comportement indésirable, comme la suppression prématurée de descripteurs de fichiers du magasin.

Ajouté dans la version 246.

BARRIER=1

Indique au gestionnaire de services que le client demande explicitement une synchronisation en fermant le descripteur de fichier envoyé avec cette commande. Le gestionnaire de services garantit que le traitement d'une commande BARRIER=1 n'aura lieu qu'après que tous les messages de notification envoyés avant cette commande aient été traités. Par conséquent, cette commande accompagnée d'un seul descripteur de fichier peut être utilisée pour synchroniser la réception de tous les messages d'état précédents. Notez que cette commande ne peut pas être mélangée avec d'autres notifications et doit être envoyée dans un message séparé au gestionnaire de services, sinon toutes les affectations seront ignorées. Notez que l'envoi de 0 ou plus d'un descripteur de fichier avec cette commande constitue une violation du protocole.

Ajouté dans la version 246.

Les messages de notification envoyés par les services sont interprétés par le gestionnaire de services. Les affectations inconnues sont ignorées. Il est donc sûr (mais souvent sans effet) d'envoyer des affectations qui ne figurent pas dans cette liste. Le protocole est extensible, mais il faut veiller à ce que les extensions privées soient reconnaissables comme telles. En particulier, il est recommandé de les préfixer avec "X_" suivi d'un identifiant d'espace de noms. Le gestionnaire de services envoie également certains messages à sa socket de notification, qui peuvent ensuite être consommés par une machine supervisant ou un gestionnaire de conteneurs plus haut dans la pile. Le gestionnaire de services envoie un certain nombre de champs d'extension, par exemple X_SYSTEMD_UNIT_ACTIVE=, pour plus de détails, voir systemd(1).

VALEUR DE RETOUR

En cas d'échec, ces appels retournent un code d'erreur négatif de style errno. Si $NOTIFY_SOCKET n'était pas défini et qu'aucun message d'état n'a donc pu être envoyé, 0 est retourné. Si l'état a été envoyé, ces fonctions retournent une valeur positive. Afin de prendre en charge à la fois les gestionnaires de services qui implémentent ce schéma et ceux qui ne le font pas, il est généralement recommandé d'ignorer la valeur de retour de cet appel. Notez que la valeur de retour indique simplement si le message de notification a été correctement mis en file d'attente, elle ne reflète pas si le le message a pu être traité avec succès. Spécifiquement, aucune erreur n'est retournée lorsqu'un descripteur de fichier est tenté d'être stocké avec FDSTORE=1 mais que le service n'est pas réellement configuré pour autoriser le stockage de descripteurs de fichiers (voir ci-dessus).

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-E2BIG

Plus de descripteurs de fichiers passés en une fois que le système n'en autorise. Sous Linux, le nombre de descripteurs de fichiers pouvant être transmis via les sockets AF_UNIX en une fois est de 253, voir unix(7) pour plus de détails.

Ajouté dans la version 257.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) depuis un thread parallèle. Il est recommandé de ne faire des appels à setenv() qu'à partir d'une phase précoce du programme, lorsque aucun autre thread n'a été lancé.

Ces fonctions envoient un datagramme unique avec la chaîne d'état comme charge utile au socket référencé dans la variable d'environnement $NOTIFY_SOCKET. Si le premier caractère de $NOTIFY_SOCKET est "/" ou "@", la chaîne est comprise comme un socket AF_UNIX ou un socket du namespace abstrait Linux (respectivement), et dans les deux cas, le datagramme est accompagné des identifiants du processus du service expéditeur, en utilisant SCM_CREDENTIALS. Si la chaîne commence par "vsock:", alors la chaîne est comprise comme une adresse AF_VSOCK, ce qui est utile pour les hyperviseurs/VMM ou d'autres processus sur l'hôte afin de recevoir une notification lorsqu'une machine virtuelle a fini de démarrer. Notez qu'au cas où l'hyperviseur ne prend pas en charge SOCK_DGRAM sur AF_VSOCK, SOCK_SEQPACKET sera utilisé à la place. "vsock-stream", "vsock-dgram" et "vsock-seqpacket" peuvent être utilisés à la place de "vsock" pour forcer l'utilisation du type de socket correspondant. L'adresse doit être sous la forme : "vsock:CID:PORT". Notez que, contrairement aux autres utilisations de vsock, le CID est obligatoire et ne peut pas être "VMADDR_CID_ANY". Notez que PID1 envoie les paquets VSOCK depuis un port privilégié (c'est-à-dire inférieur à 1024), pour tenter de répondre aux préoccupations selon lesquelles des processus non privilégiés dans l'invité pourraient essayer d'envoyer des notifications malveillantes à l'hôte, le poussant à prendre des décisions destructrices basées sur celles-ci.

Implémentations autonomes

Notez que, bien que l'utilisation de cette bibliothèque soit préférable afin d'éviter la duplication de code, il est également possible de réimplémenter le protocole simple de notification de disponibilité sans dépendances externes, comme démontré dans les exemples autonomes suivants de plusieurs langues :

C 

/* SPDX-License-Identifier: MIT-0 */
/* Implémenter le protocole systemd notify sans dépendances externes.
 * Prend en charge la notification de disponibilité au démarrage et lors du rechargement,
 * conformément au protocole défini à :
 * https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html
 * Ce protocole est garanti stable conformément à :
 * https://systemd.io/PORTABILITY_AND_STABILITY/ */
#define _GNU_SOURCE 1
#include <errno.h>
#include <inttypes.h>
#include <signal.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/un.h>
#include <time.h>
#include <unistd.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
static void closep(int *fd) {
  if (!fd || *fd < 0)
    return;
  close(*fd);
  *fd = -1;
}
static int notify(const char *message) {
  union sockaddr_union {
    struct sockaddr sa;
    struct sockaddr_un sun;
  } socket_addr = {
    .sun.sun_family = AF_UNIX,
  };
  size_t path_length, message_length;
  _cleanup_(closep) int fd = -1;
  const char *socket_path;
  /* Vérifier d'abord l'argument */
  if (!message)
    return -EINVAL;
  message_length = strlen(message);
  if (message_length == 0)
    return -EINVAL;
  /* Si la variable n'est pas définie, le protocole est une opération nulle */
  socket_path = getenv("NOTIFY_SOCKET");
  if (!socket_path)
    return 0; /* Non défini ? Rien à faire */
  /* Seuls AF_UNIX sont pris en charge, avec des sockets de chemin ou abstraits */
  if (socket_path[0] != '/' && socket_path[0] != '@')
    return -EAFNOSUPPORT;
  path_length = strlen(socket_path);
  /* Assurer qu'il y a de la place pour le caractère nul */
  if (path_length >= sizeof(socket_addr.sun.sun_path))
    return -E2BIG;
  memcpy(socket_addr.sun.sun_path, socket_path, path_length);
  /* Prise en charge des sockets abstraits */
  if (socket_addr.sun.sun_path[0] == '@')
    socket_addr.sun.sun_path[0] = 0;
  fd = socket(AF_UNIX, SOCK_DGRAM|SOCK_CLOEXEC, 0);
  if (fd < 0)
    return -errno;
  if (connect(fd, &socket_addr.sa, offsetof(struct sockaddr_un, sun_path) + path_length) != 0)
    return -errno;
  ssize_t written = write(fd, message, message_length);
  if (written != (ssize_t) message_length)
    return written < 0 ? -errno : -EPROTO;
  return 1; /* Notifié ! */
}
static int notify_ready(void) {
  return notify("READY=1");
}
static int notify_reloading(void) {
  /* Un tampon d'une longueur suffisante pour formater la valeur maximale de UINT64. */
  char reload_message[sizeof("RELOADING=1\nMONOTONIC_USEC=18446744073709551615")];
  struct timespec ts;
  uint64_t now;
  /* Notifier systemd que nous rechargeons, y compris un horodatage CLOCK_MONOTONIC en microsecondes
   * afin que le programme soit compatible avec un service Type=notify-reload. */
  if (clock_gettime(CLOCK_MONOTONIC, &ts) < 0)
    return -errno;
  if (ts.tv_sec < 0 || ts.tv_nsec < 0 ||
      (uint64_t) ts.tv_sec > (UINT64_MAX - (ts.tv_nsec / 1000ULL)) / 1000000ULL)
    return -EINVAL;
  now = (uint64_t) ts.tv_sec * 1000000ULL + (uint64_t) ts.tv_nsec / 1000ULL;
  if (snprintf(reload_message, sizeof(reload_message), "RELOADING=1\nMONOTONIC_USEC=%" PRIu64, now) < 0)
    return -EINVAL;
  return notify(reload_message);
}
static int notify_stopping(void) {
  return notify("STOPPING=1");
}
static volatile sig_atomic_t reloading = 0;
static volatile sig_atomic_t terminating = 0;
static void signal_handler(int sig) {
  if (sig == SIGHUP)
    reloading = 1;
  else if (sig == SIGINT || sig == SIGTERM)
    terminating = 1;
}
int main(int argc, char **argv) {
  struct sigaction sa = {
    .sa_handler = signal_handler,
    .sa_flags = SA_RESTART,
  };
  int r;
  /* Configuration des gestionnaires de signaux */
  sigemptyset(&sa.sa_mask);
  sigaction(SIGHUP, &sa, NULL);
  sigaction(SIGINT, &sa, NULL);
  sigaction(SIGTERM, &sa, NULL);
  /* Effectuer d'autres travaux d'initialisation du service ici... */
  /* Maintenant que toutes les étapes de préparation sont terminées, signaler la disponibilité */
  r = notify_ready();
  if (r < 0) {
    fprintf(stderr, "Échec de la notification de disponibilité à $NOTIFY_SOCKET : %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  while (!terminating) {
    if (reloading) {
      reloading = false;
      /* En tant que fonctionnalité séparée mais connexe, nous pouvons également notifier le gestionnaire
       * lors du rechargement de la configuration. Cela permet un suivi précis de l'état,
       * et également l'intégration automatisée de 'systemctl reload' sans avoir à
       * spécifier manuellement une ligne ExecReload= dans le fichier d'unité. */
      r = notify_reloading();
      if (r < 0) {
        fprintf(stderr, "Échec de la notification de rechargement à $NOTIFY_SOCKET : %s\n", strerror(-r));
        return EXIT_FAILURE;
      }
      /* Effectuer un travail de reconfiguration ici... */
      r = notify_ready();
      if (r < 0) {
        fprintf(stderr, "Échec de la notification de disponibilité à $NOTIFY_SOCKET : %s\n", strerror(-r));
        return EXIT_FAILURE;
      }
    }
    /* Effectuer un travail de démon ici... */
    sleep(5);
  }
  r = notify_stopping();
  if (r < 0) {
    fprintf(stderr, "Échec du rapport de terminaison à $NOTIFY_SOCKET : %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  /* Effectuer un travail d'arrêt ici... */
  return EXIT_SUCCESS;
}

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
#
# Implémenter le protocole systemd notify sans dépendances externes.
# Prend en charge la notification de disponibilité au démarrage et lors du rechargement,
# conformément au protocole défini à :
# https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html
# Ce protocole est garanti stable conformément à :
# https://systemd.io/PORTABILITY_AND_STABILITY/
import errno
import os
import signal
import socket
import sys
import time
reloading = False
terminating = False
def notify(message):
    if not message:
        raise ValueError("notify() requires a message")
    socket_path = os.environ.get("NOTIFY_SOCKET")
    if not socket_path:
        return
    if socket_path[0] not in ("/", "@"):
        raise OSError(errno.EAFNOSUPPORT, "Unsupported socket type")
    # Gérer le socket abstrait.
    if socket_path[0] == "@":
        socket_path = "\0" + socket_path[1:]
    with socket.socket(socket.AF_UNIX, socket.SOCK_DGRAM | socket.SOCK_CLOEXEC) as sock:
        sock.connect(socket_path)
        sock.sendall(message)
def notify_ready():
    notify(b"READY=1")
def notify_reloading():
    microsecs = time.clock_gettime_ns(time.CLOCK_MONOTONIC) // 1000
    notify(f"RELOADING=1\nMONOTONIC_USEC={microsecs}".encode())
def notify_stopping():
    notify(b"STOPPING=1")
def reload(signum, frame):
    global reloading
    reloading = True
def terminate(signum, frame):
    global terminating
    terminating = True
def main():
    print("Effectuer la configuration initiale")
    global reloading, terminating
    # Configurer les gestionnaires de signaux.
    print("Configuration des gestionnaires de signaux")
    signal.signal(signal.SIGHUP, reload)
    signal.signal(signal.SIGINT, terminate)
    signal.signal(signal.SIGTERM, terminate)
    # Effectuer tout autre travail de configuration ici.
    # Une fois toute la configuration terminée, signaler la disponibilité.
    print("Configuration terminée")
    notify_ready()
    print("Démarrage de la boucle")
    while not terminating:
        if reloading:
            print("Rechargement")
            reloading = False
            # Prendre en charge la notification du gestionnaire lors du rechargement de la configuration.
            # Cela permet un suivi précis de l'état ainsi que l'activation automatique de
            # 'systemctl reload' sans avoir besoin de spécifier manuellement
            # une ligne ExecReload= dans le fichier d'unité.
            notify_reloading()
            # Effectuer un travail de reconfiguration ici.
            print("Rechargement terminé")
            notify_ready()
        # Effectuer le vrai travail ici...
        print("Endormissement pendant cinq secondes")
        time.sleep(5)
    print("Terminaison")
    notify_stopping()
if __name__ == "__main__":
    sys.stdout.reconfigure(line_buffering=True)
    print("Démarrage de l'application")
    main()
    print("Application arrêtée")
sd_notify_barrier(3) — systemd — Arch Linux

NAME

sd_notify, sd_notifyf, sd_pid_notify, sd_pid_notifyf, sd_notify_with_fds, sd_pid_notify_with_fds, sd_notify_barrier, sd_pid_notify_barrier, sd_notify_barrier_with_fds, sd_pid_notify_barrier_with_fds — notify systemd about service status

SYNOPSIS

#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);

int sd_notifyf(int unset_environment, const char *fmt, ...);

int sd_pid_notify(pid_t pid, int unset_environment, const char *state);

int sd_pid_notifyf(pid_t pid, int unset_environment, const char *fmt, ...);

int sd_notify_with_fds(int unset_environment, const char *state, int *fds, unsigned int n_fds);

int sd_pid_notify_with_fds(pid_t pid, int unset_environment, const char *state, int *fds, unsigned int n_fds);

int sd_notify_barrier(int unset_environment, uint64_t timeout_us);

int sd_pid_notify_barrier(pid_t pid, int unset_environment, uint64_t timeout_us);

int sd_notify_barrier_with_fds(int unset_environment, uint64_t timeout_us, int *fds, unsigned int n_fds);

int sd_pid_notify_barrier_with_fds(pid_t pid, int unset_environment, uint64_t timeout_us, int *fds, unsigned int n_fds);

DESCRIPTION

These functions allow a service process to send asynchronous notifications to the systemd service manager. The notifications are sent via a local datagram socket passed via the environment variable $NOTIFY_SOCKET. If this environment variable is not set, or if the socket cannot be opened, these functions will fail.

The primary use case is to signal service startup completion, status changes, or other runtime information. The systemd service manager listens on this socket and updates the status of the service accordingly.

The sd_notify, sd_notifyf, sd_notify_with_fds, and sd_notify_barrier functions operate on the service process that is currently running. The sd_pid_notify, sd_pid_notifyf, sd_pid_notify_with_fds, and sd_pid_notify_barrier functions allow notifying about the status of an arbitrary process specified by pid, provided that the calling process has the necessary privileges.

The unset_environment parameter controls whether the $NOTIFY_SOCKET environment variable should be unset in the child process after a fork. If it is non-zero, the environment variable is unset.

The state parameter is a string containing arbitrary, NUL-terminated key-value pairs, separated by newlines. The keys and values are typically URL-encoded. Keys should generally be restricted to ASCII characters, while values may contain a broader range. Values must not contain newline characters. If the string is empty, it is ignored. See WELL-KNOWN ASSIGNMENTS for a list of special keys.

The sd_notifyf and sd_pid_notifyf functions are equivalent to sd_notify and sd_pid_notify respectively, but use the printf-style format string fmt to construct the message.

The sd_notify_with_fds and sd_pid_notify_with_fds functions additionally take an array of file descriptors fds of size n_fds. These file descriptors are passed to the service manager, which may store them for later use (see FDSTORE=1 below). The caller must ensure that the file descriptors passed are valid and remain open for the duration of the call. The service manager may close these file descriptors after receiving them.

The sd_notify_barrier and sd_pid_notify_barrier functions allow a client to synchronize with the service manager. They send a notification and then block until the service manager acknowledges receipt of all notifications sent before the barrier, or until the specified timeout_us (in microseconds) elapses. This is useful to avoid race conditions where the client exits before the service manager has processed all its notifications.

The sd_notify_barrier_with_fds and sd_pid_notify_barrier_with_fds functions combine the functionality of sending file descriptors and performing a barrier synchronization.

WELL-KNOWN ASSIGNMENTS

The following assignments are recognized by systemd:

READY=1
Signals that the service has completed its initialization and is ready to accept connections or perform its main task. If a service sends this message, systemd will mark it as activated.
RELOADING=1
Signals that the service is reloading its configuration. While reloading, the service should continue to serve requests.
STOPPING=1
Signals that the service is shutting down. This should be sent just before the service exits.
STATUS=...
Provides a human-readable status string for the service, which may be displayed by systemd tools.
MAINPID=...
Informs systemd about the main process ID (PID) of the service. This is useful for services that fork and create child processes. By default, systemd tracks the PID of the process that it started. If the service forks, the original process might exit and a child process might become the main process. This notification helps systemd track the correct PID. The value must be a numerical PID.
FDSTORE=1
Signals that the service is providing file descriptors that should be stored by the service manager. This is used for service restartability without losing state. The file descriptors to be stored are passed via the sd_notify_with_fds or related functions. Specific file descriptors can be named using FDNAME=... assignments. See also https://systemd.io/FILE_DESCRIPTOR_STORE.
FDNAME=...
Assigns a name to a file descriptor being passed via sd_notify_with_fds. This name can be used later to retrieve the file descriptor from the service manager using sd_listen_fds_with_names(3). Multiple FDNAME=... assignments can be used to name multiple file descriptors, corresponding to the order they are passed in the fds array.

RETURN VALUE

On success, these functions return a non-negative integer. On failure, they return a negative error number.

The return values are:

0
The service manager did not exist, or the $NOTIFY_SOCKET was not set, or the socket could not be opened. In this case, the notification was not sent.
-EINVAL
An invalid argument was provided (e.g., NULL pointer for state or fmt).
-EPIPE
The socket is closed or broken. No more notifications can be sent.
-ECONNREFUSED
The service manager rejected the connection (e.g., if the service is not supervised).
-ENOMEM
Out of memory.
-EPROTO
The message format is invalid.

NOTES

It is recommended to check the return value of these functions and handle errors appropriately. For example, if the service manager is not running or the service is not supervised, the notification might be ignored.

When using sd_notifyf or sd_pid_notifyf, be careful with format string vulnerabilities. Ensure that the format string and its arguments are properly sanitized if they come from untrusted sources.

The sd_notify_barrier* functions are essential for preventing race conditions when the client process might exit before the service manager has finished processing notifications. The timeout parameter provides a safeguard against deadlocks.

ENVIRONMENT

$NOTIFY_SOCKET

Set by the service manager for supervised processes for status and start-up completion notification. This environment variable specifies the socket sd_notify() talks to. See above for details.

EXAMPLES

Example 1. Start-up Notification

When a service finished starting up, it might issue the following call to notify the service manager:

sd_notify(0, "READY=1");

Example 2. Extended Start-up Notification

A service could send the following after completing initialization:

sd_notifyf(0, "READY=1\n"
              "STATUS=Processing requests...\n"
              "MAINPID=%lu",
           (unsigned long) getpid());

Example 3. Error Cause Notification

A service could send the following shortly before exiting, on failure:

sd_notifyf(0, "STATUS=Failed to start up: %s\n"
              "ERRNO=%i",
           strerror_r(errnum, (char[1024]){}, 1024),
           errnum);

Example 4. Store a File Descriptor in the Service Manager

To store an open file descriptor in the service manager, in order to continue operation after a service restart without losing state, use "FDSTORE=1":

sd_pid_notify_with_fds(0, 0, "FDSTORE=1\nFDNAME=foobar", &fd, 1);

Example 5. Eliminating race conditions

When the client sending the notifications is not spawned by the service manager, it may exit too quickly and the service manager may fail to attribute them correctly to the unit. To prevent such races, use sd_notify_barrier() to synchronize against reception of all notifications sent before this call is made.

sd_notify(0, "READY=1");
/* set timeout to 5 seconds */
sd_notify_barrier(0, 5 * 1000000);
