sd_event_add_exit(3)

Paquet: systemd-libs

Licences: LGPL-2.1-or-later, CC0-1.0, GPL-2.0-or-later WITH Linux-syscall-note

SD_EVENT_ADD_DEFER(3) sd_event_add_defer SD_EVENT_ADD_DEFER(3)

NOM

sd_event_add_defer, sd_event_add_post, sd_event_add_exit, sd_event_handler_t - Ajouter des sources d'événements statiques à une boucle d'événements

SYNTAXE

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;

typedef int (*sd_event_handler_t)(sd_event_source *s, void *userdata);

int sd_event_add_defer(sd_event *event, sd_event_source **source, sd_event_handler_t handler, void *userdata);

int sd_event_add_post(sd_event *event, sd_event_source **source, sd_event_handler_t handler, void *userdata);

int sd_event_add_exit(sd_event *event, sd_event_source **source, sd_event_handler_t handler, void *userdata);

DESCRIPTION

Ces trois fonctions ajoutent de nouvelles sources d'événements statiques à une boucle d'événements. L'objet boucle d'événements est spécifié dans le paramètre event, l'objet source d'événements est retourné dans le paramètre source. Les sources d'événements sont activées statiquement et seront "déclenchées" lorsque la boucle d'événements sera exécutée et que les conditions décrites ci-dessous seront remplies.

Le handler est une fonction à appeler ou NULL. La fonction handler recevra le pointeur userdata, qui peut être choisi librement par l'appelant. Le handler peut retourner une valeur négative pour signaler une erreur (voir ci-dessous), d'autres valeurs de retour sont ignorées. Si handler est NULL, un handler par défaut qui appelle sd_event_exit(3) sera utilisé.

sd_event_add_defer() ajoute une nouvelle source d'événement qui sera déclenchée instantanément, avant que la boucle d'événements ne se mette à dormir à nouveau et n'attende de nouveaux événements. Par défaut, le handler sera appelé une fois (SD_EVENT_ONESHOT). Notez que si la source d'événement est définie sur SD_EVENT_ON, la boucle d'événements ne se mettra jamais en veille, mais appellera continuellement le handler, potentiellement en alternance avec d'autres sources d'événements.

sd_event_add_post() ajoute une nouvelle source d'événement qui est exécutée avant que la boucle d'événements ne se mette en veille et n'attende de nouveaux événements, mais seulement après qu'au moins une autre source d'événement non-post ait été déclenchée. Par défaut, la source est activée en permanence (SD_EVENT_ON). Notez que ce type de source d'événement permettra toujours à la boucle d'événements de se mettre en veille, même si elle est définie sur SD_EVENT_ON, tant qu'aucune autre source d'événement n'est déclenchée.

sd_event_add_exit() ajoute une nouvelle source d'événement qui sera déclenchée lorsque la boucle d'événements sera terminée avec sd_event_exit(3).

La fonction sd_event_source_set_enabled(3) peut être utilisée pour activer la source d'événement en permanence (SD_EVENT_ON) ou pour la faire se déclencher une seule fois (SD_EVENT_ONESHOT).

Si la fonction handler retourne un code d'erreur négatif, elle sera soit désactivée après l'invocation, même si le mode SD_EVENT_ON avait été demandé auparavant, soit elle provoquera la terminaison de la boucle, voir sd_event_source_set_exit_on_failure(3).

Pour détruire un objet source d'événement, utilisez sd_event_source_unref(3), mais notez que la source d'événement n'est retirée de la boucle d'événements que lorsque toutes les références à la source d'événement sont libérées. Pour s'assurer qu'une source d'événement ne se déclenche plus, même s'il y a encore une référence à celle-ci, envisagez de définir la source d'événement sur SD_EVENT_OFF avec sd_event_source_set_enabled(3).

Si le deuxième paramètre de ces fonctions est passé en tant que NULL, aucune référence à l'objet source d'événement n'est retournée. Dans ce cas, la source d'événement est considérée comme "flottante" et sera détruite implicitement lorsque la boucle d'événements elle-même sera détruite.

Si le paramètre handler pour sd_event_add_defer() ou sd_event_add_post() est NULL, et que la source d'événement se déclenche, cela sera considéré comme une demande de sortie de la boucle d'événements. Dans ce cas, le paramètre userdata, converti en entier, est passé en tant que paramètre de code de sortie à sd_event_exit(3). Une fonctionnalité similaire n'est pas disponible pour sd_event_add_exit(), car ces types de sources d'événements ne sont déclenchées qu'au moment de la sortie.

VALEUR DE RETOUR

En cas de succès, ces fonctions retournent 0 ou un entier positif. En cas d'échec, elles retournent un code d'erreur négatif de style errno.

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-ENOMEM

Pas assez de mémoire pour allouer un objet.

-EINVAL

Un argument invalide a été passé.

-ESTALE

La boucle d'événements est déjà terminée.

-ECHILD

La boucle d'événements a été créée dans un processus, une bibliothèque ou une instance de module différente.

NOTES

Les fonctions décrites ici sont disponibles en tant que bibliothèque partagée, qui peut être compilée et liée avec le fichier pkg-config(1) de libsystemd.

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) depuis un thread parallèle. Il est recommandé de ne faire des appels à setenv() qu'à partir d'une phase précoce du programme, lorsqu'aucun autre thread n'a été démarré.

HISTORIQUE

sd_event_add_defer(), sd_event_add_post(), sd_event_add_exit(), et sd_event_handler_t() ont été ajoutés dans la version 217.

sd_event_add_exit(3) — Arch Linux

Nom

sd_event_add_exit - Ajouter un gestionnaire d'événement pour la sortie du gestionnaire d'événements

Syntaxe

#include <systemd/sd-event.h>

int sd_event_add_exit(sd_event *event, sd_event_source **source,
                      sd_event_handler_t handler, void *userdata);

Description

La fonction sd_event_add_exit enregistre une nouvelle fonction de rappel (handler) handler qui sera appelée lorsque le gestionnaire d'événements event sera arrêté. La fonction handler sera appelée avec l'argument userdata.

Au plus un gestionnaire de sortie peut être enregistré pour un gestionnaire d'événements donné. Si un gestionnaire de sortie est déjà enregistré, la fonction échouera et retournera -EEXIST.

Pour désenregistrer un gestionnaire de sortie, il suffit d'appeler sd_event_source_disable sur la source retournée.

La fonction handler doit retourner un entier de type int. Si elle retourne une valeur strictement positive, le gestionnaire d'événements s'arrêtera immédiatement. Si elle retourne zéro ou une valeur strictement négative, le gestionnaire d'événements continuera son exécution normale.

Paramètres

event
Le gestionnaire d'événements cible.
source
Un pointeur vers une variable de type sd_event_source*. La nouvelle source d'événement est stockée dans cette variable. Si NULL est passé, aucune référence à la source n'est retournée.
handler
La fonction de rappel à exécuter lorsque le gestionnaire d'événements est arrêté. Doit être une fonction de type sd_event_handler_t.
userdata
Données utilisateur arbitraires qui seront passées à la fonction de rappel.

Valeur de retour

En cas de succès, 0 est retourné. En cas d'échec, un code d'erreur strictement négatif est retourné.

-EINVAL
Le gestionnaire d'événements event n'est pas valide, ou le pointeur handler est nul.
-ENOMEM
Pas assez de mémoire pour allouer la nouvelle source d'événement.
-EEXIST
Un gestionnaire de sortie est déjà enregistré pour ce gestionnaire d'événements.

NOTES

La fonction handler est garantie d'être appelée avec userdata et une référence à la source d'événement retournée. Le pointeur de la source d'événement sera nul lorsqu'elle sera appelée si NULL a été passé à source.

HISTORIQUE

La fonction sd_event_add_exit a été introduite dans systemd v236.
