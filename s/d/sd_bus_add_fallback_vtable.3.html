DESCRIPTION

sd_bus_add_object_vtable() est utilisée pour déclarer les attributs du chemin d'objet path connecté à la connexion de bus bus sous l'interface interface. La table vtable peut contenir des déclarations de propriétés utilisant SD_BUS_PROPERTY() ou SD_BUS_WRITABLE_PROPERTY(), des déclarations de méthodes utilisant SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), ou SD_BUS_METHOD_WITH_NAMES_OFFSET(), et des déclarations de signaux utilisant SD_BUS_SIGNAL_WITH_NAMES() ou SD_BUS_SIGNAL(), voir ci-dessous. Le paramètre userdata contient un pointeur qui sera passé à diverses fonctions de rappel. Il peut être spécifié comme NULL si aucune valeur n'est nécessaire. Une interface peut avoir un nombre illimité de vtables qui lui sont attachées.

sd_bus_add_fallback_vtable() est similaire à sd_bus_add_object_vtable(), mais est utilisée pour enregistrer des attributs "de secours". Lors de la recherche d'une déclaration d'attribut, les chemins d'objet de bus enregistrés avec sd_bus_add_object_vtable() sont vérifiés en premier. Si aucune correspondance n'est trouvée, les vtables de secours sont vérifiées pour chaque préfixe du chemin d'objet de bus, c'est-à-dire en supprimant successivement les derniers composants séparés par des barres obliques. Cela permet d'utiliser la vtable pour un nombre illimité d'objets créés dynamiquement.

Le paramètre find est une fonction utilisée pour localiser l'objet cible en fonction du chemin d'objet de bus path. Elle doit retourner 1 et définir le paramètre de sortie ret_found si l'objet est trouvé, retourner 0 si l'objet n'a pas été trouvé, et retourner un code d'erreur de style errno négatif ou initialiser la structure d'erreur ret_error en cas d'erreur. Le pointeur passé dans ret_found sera utilisé comme paramètre userdata pour les fonctions de rappel (décalé par les décalages offset tels que spécifiés dans les entrées de la vtable).

sd_bus_add_object() attache un rappel directement au chemin d'objet path. Un chemin d'objet peut avoir un nombre illimité de rappels qui lui sont attachés. Chaque rappel est ajouté en tête de la liste des rappels qui sont toujours appelés dans l'ordre. sd_bus_add_fallback() est similaire à sd_bus_add_object() mais s'applique aux chemins de secours.

sd_bus_add_filter() installe un rappel qui est appelé pour chaque message D-Bus entrant. Les filtres peuvent être utilisés pour gérer une logique commune à tous les messages reçus par un service (par exemple, authentification ou autorisation).

Lorsqu'une requête est reçue, tous les rappels associés sont appelés séquentiellement jusqu'à ce qu'un rappel retourne un entier non nul. Retournez zéro d'un rappel pour donner aux autres rappels la chance de traiter la requête. Les rappels sont appelés dans l'ordre suivant : d'abord, les rappels globaux installés avec sd_bus_add_filter() sont appelés. Deuxièmement, les rappels attachés directement au chemin d'objet de la requête sont appelés, suivis des rappels de méthode D-Bus attachés au chemin d'objet de la requête, à l'interface et au membre. Enfin, les rappels de propriété attachés au chemin d'objet de la requête, à l'interface et au membre sont appelés. Si le dernier rappel retourne zéro, un err

or reply is sent back to the caller indicating no matching object for the request was found.

Note that you can return a positive integer from a method callback without immediately sending a reply. This informs sd-bus this callback will take responsibility for replying to the request without forcing the callback to produce a reply immediately. This allows a callback to perform any number of asynchronous operations required to construct a reply. However, if producing a reply takes too long, the method call will time out at the caller. This is only available to methods and not properties.

If a callback was invoked to handle a request that expects a reply and the callback returns a negative value, the value is interpreted as a negative errno-style error code and sent back to the caller as a D-Bus error as if sd_bus_reply_method_errno(3) was called. Additionally, all callbacks take a sd_bus_error output parameter that can be used to provide more detailed error information. If ret_error is set when the callback finishes, the corresponding D-Bus error is sent back to the caller as if sd_bus_reply_method_error(3) was called. Any error stored in ret_error takes priority over any negative values returned by the same callback when determining which error to send back to the caller. Use sd_bus_error_set(3) or one of its variants to set ret_error and return a negative integer from a callback with a single function call. To send an error reply after a callback has already finished, use sd_bus_reply_method_errno(3) or one of its variants.

For all functions, a match slot is created internally. If the output parameter slot is NULL, a "floating" slot object is created, see sd_bus_slot_set_floating(3). Otherwise, a pointer to the slot object is returned. In that case, the reference to the slot object should be dropped when the vtable is not needed anymore, see sd_bus_slot_unref(3).

Le tableau sd_bus_vtable

Le tableau est constitué de structures de type sd_bus_vtable, mais il ne doit jamais être rempli manuellement, mais via l'une des macros suivantes :

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Ceux-ci doivent toujours être le premier et le dernier élément. Le paramètre flags peut être utilisé pour définir des attributs qui s'appliquent à l'ensemble du tableau ; voir la section "Flags" ci-dessous.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Déclare une méthode D-Bus avec le nom member, les arguments args et le résultat result. args attend une séquence de paires type/nom d'argument encapsulées dans la macro SD_BUS_ARGS(). Les éléments aux indices pairs de cette liste décrivent les types des arguments de la méthode. La signature du paramètre de la méthode est la concaténation de toutes les littéraux de chaîne aux indices pairs dans args. Si une méthode n'a pas de paramètres, passez SD_BUS_NO_ARGS à args. Les éléments aux indices impairs décrivent les noms des arguments de la méthode. result attend une séquence de paires type/nom encapsulées dans la macro SD_BUS_RESULT() dans le même format que SD_BUS_ARGS(). La signature du résultat de la méthode est la concaténation de toutes les littéraux de chaîne aux indices pairs dans result. Si une méthode n'a pas de résultat, passez SD_BUS_NO_RESULT à result. Notez que les types d'arguments sont censés être des littéraux de chaîne entre guillemets et les noms d'arguments sont censés être des littéraux de chaîne sans guillemets. Voir ci-dessous pour un exemple complet.

La fonction de gestion handler doit être de type sd_bus_message_handler_t. Elle sera appelée pour gérer les messages entrants qui appellent cette méthode. Elle reçoit un pointeur qui est le paramètre userdata passé à la fonction d'enregistrement décalé de offset octets. Cela peut être utilisé pour passer des pointeurs vers différents champs de la même structure de données à différentes méthodes de la même vtable. Pour envoyer une réponse depuis handler, appelez sd_bus_reply_method_return(3) avec le message avec lequel le callback a été appelé. Le paramètre flags est une combinaison de flags, voir ci-dessous.

SD_BUS_METHOD_WITH_ARGS() est un raccourci pour appeler SD_BUS_METHOD_WITH_ARGS_OFFSET() avec un décalage de zéro.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Déclare une méthode D-Bus avec le nom member, la signature de paramètre signature, la signature de résultat result. Les paramètres in_names et out_names spécifient les noms des arguments des arguments d'entrée et de sortie dans la signature de la fonction. in_names et out_names doivent être créés à l'aide de la macro SD_BUS_PARAM(), voir ci-dessous. À tous autres égards, cette macro se comporte exactement de la même manière que SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), et SD_BUS_METHOD() sont des variantes qui spécifient un décalage nul (le paramètre userdata est passé sans modification), laissent les noms non définis (c'est-à-dire aucun nom de paramètre), ou les deux.

Préférez utiliser SD_BUS_METHOD_WITH_ARGS_OFFSET() et SD_BUS_METHOD_WITH_ARGS() à ces macros car elles permettent de spécifier les types et les noms des arguments côte à côte, ce qui est moins sujet aux erreurs que de spécifier d'abord tous les types d'arguments suivis de tous les noms d'arguments.

SD_BUS_SIGNAL_WITH_ARGS()

Déclare un signal D-Bus avec le nom member et les arguments args. args attend une séquence de paires type/nom d'argument encapsulées dans la macro SD_BUS_ARGS(). Les éléments aux indices pairs de cette liste décrivent les types des arguments du signal. La signature du paramètre du signal est la concaténation de toutes les littéraux de chaîne aux indices pairs dans args. Si un signal n'a pas de paramètres, passez SD_BUS_NO_ARGS à args. Les éléments aux indices impairs décrivent les noms des arguments du signal. Le paramètre flags est une combinaison de flags. Voir ci-dessous pour un exemple complet.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Déclare un signal D-Bus avec le nom member, la signature de paramètre signature et les noms d'arguments names. names doit être créé à l'aide de la macro SD_BUS_PARAM(), voir ci-dessous. Le paramètre flags est une combinaison de flags, voir ci-dessous.

SD_BUS_SIGNAL() équivaut à SD_BUS_SIGNAL_WITH_NAMES() avec le paramètre names non défini (c'est-à-dire aucun nom de paramètre).

Préférez utiliser SD_BUS_SIGNAL_WITH_ARGS() à ces macros car elle permet de spécifier les types et les noms des arguments côte à côte, ce qui est moins sujet aux erreurs que de spécifier d'abord tous les types d'arguments suivis de tous les noms d'arguments.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Déclare une propriété D-Bus avec le nom member et la signature de valeur signature. Les paramètres get et set sont les méthodes de lecture et d'écriture. Elles sont appelées avec un pointeur qui est le paramètre userdata passé à la fonction d'enregistrement décalé de offset octets. Cela peut être utilisé pour passer des pointeurs vers différents champs de la même structure de données à différents définisseurs et lecteurs dans la même vtable. Le paramètre flags est une combinaison de flags, voir ci-dessous.

Les méthodes de définition et de lecture peuvent être omises (spécifiées comme NULL), si la propriété est l'un des types de base ou "as" dans le cas de propriétés en lecture seule. Dans ces cas, les paramètres userdata et offset doivent ensemble pointer vers une variable valide du type correspondant. Un définisseur et un lecteur par défaut seront fournis, qui copient simplement l'argument entre cette variable et le message.

SD_BUS_PROPERTY() est utilisé pour définir une propriété en lecture seule.

SD_BUS_PARAM()

Les noms de paramètres doivent être encapsulés dans cette macro, voir l'exemple ci-dessous.

Flags

Le paramètre flags est utilisé pour spécifier une combinaison d'annotations D-Bus[1].

SD_BUS_VTABLE_DEPRECATED

Marque cette entrée de vtable comme obsolète en utilisant l'annotation org.freedesktop.DBus.Deprecated dans les données d'introspection. Si spécifié pour SD_BUS_VTABLE_START(), l'annotation est appliquée à l'interface englobante.

SD_BUS_VTABLE_HIDDEN

Rend cette entrée de vtable cachée. Elle ne sera pas montrée dans les données d'introspection. Si spécifié pour SD_BUS_VTABLE_START(), toutes les entrées du tableau sont cachées.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marque cette entrée de vtable comme une méthode qui ne retournera pas de réponse en utilisant l'annotation org.freedesktop.DBus.Method.NoReply dans les données d'introspection.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Ces trois flags correspondent à différentes valeurs de l'annotation org.freedesktop.DBus.Property.EmitsChangedSignal, qui spécifie si le signal org.freedesktop.DBus.Properties.PropertiesChanged est émis chaque fois que la propriété change. SD_BUS_VTABLE_PROPERTY_CONST correspond à const et signifie que la propriété ne change jamais pendant la durée de vie de l'objet auquel elle appartient, donc aucun signal ne doit être émis. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE correspond à true et signifie que le signal est émis. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION correspond à invalidates et signifie que le signal est émis, mais la valeur n'est pas incluse dans le signal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marque cette entrée de propriété de vtable comme nécessitant une demande explicite pour que la valeur soit affichée (généralement parce que la valeur est grande ou lente à calculer). Cette entrée ne peut pas être combinée avec SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, et ne sera pas affichée dans les listes de propriétés par défaut (par exemple, busctl introspect). Cela correspond à l'annotation org.freedesktop.systemd1.Explicit dans les données d'introspection.

SD_BUS_VTABLE_SENSITIVE

Marque cette entrée de méthode de vtable comme traitant des données sensibles. Lorsqu'elle est définie, les messages d'appel de méthode entrants et leurs messages de réponse sortants sont marqués comme sensibles à l'aide de sd_bus_message_sensitive(3), de sorte qu'ils sont effacés de la mémoire lorsqu'ils sont libérés.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

Marque cette entrée de méthode ou de propriété de vtable pour que l'utilisateur dat
un pointeur passé à ses fonctions de gestion associées est déterminé légèrement différemment : au lieu d'ajouter le paramètre de décalage de l'entrée au pointeur de données utilisateur spécifié lors de l'enregistrement de la vtable, le décalage est passé directement, converti en pointeur, sans tenir compte du pointeur de données utilisateur spécifié lors de l'enregistrement de la vtable.

SD_BUS_VTABLE_CAPABILITY(capability)

L'accès à cette entrée de vtable sera autorisé si le processus appelant possède la capacité capability, comme décrit dans sd_bus_query_sender_privilege(3). Si elle est utilisée pour SD_BUS_VTABLE_START(), elle fournit une valeur par défaut pour toutes les entrées du tableau. Si elle n'est pas spécifiée, que ce soit pour une entrée individuelle ou pour l'ensemble du tableau, CAP_SYS_ADMIN est vérifiée par défaut. Voir capabilities(7) pour des informations sur les capacités.

Notez que les entrées de vtable peuvent être marquées comme non privilégiées et que l'ensemble du bus peut être marqué comme approuvé, voir la discussion sur SD_BUS_VTABLE_UNPRIVILEGED ci-dessous.

SD_BUS_VTABLE_UNPRIVILEGED

Marque cette entrée de vtable comme non privilégiée. L'accès aux entrées privilégiées est limité aux utilisateurs disposant des capacités appropriées, comme décrit ci-dessus. En pratique, de nombreuses entrées de vtable sont marquées comme non privilégiées et sont soit ouvertes à tous, soit la décision d'autoriser l'accès est prise ultérieurement, par exemple en déléguant à polkit[2].

L'ensemble du bus peut être marqué comme approuvé, auquel cas les annotations au niveau de l'entrée sont ignorées, voir sd_bus_set_trusted(3).

Lorsque non spécifié, l'annotation org.freedesktop.systemd1.Privileged avec la valeur "true" sera affichée dans les données d'introspection.

SD_BUS_VTABLE_UNPRIVILEGED ne peut pas être appliqué aux propriétés en lecture seule, mais l'accès en lecture (aux propriétés en lecture seule et en écriture) est toujours illimité.

Notez que cette page décrit les vérifications implémentées dans le client D-Bus. Le serveur D-Bus dispose d'une politique supplémentaire qui peut autoriser ou refuser les connexions, voir "FICHIER DE CONFIGURATION" dans dbus-daemon(1).

EXEMPLES

Exemple 1. Créer un écouteur simple sur le bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_VTABLE_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

VALEUR DE RETOUR

En cas de succès, sd_bus_add_object_vtable() et sd_bus_add_fallback_vtable() retournent un entier positif. En cas d'échec, ils retournent un code d'erreur négatif de type errno.

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-EINVAL

L'un des paramètres requis est NULL ou invalide. Une interface D-Bus réservée a été passée comme paramètre interface.

-ENOPKG

Le bus ne peut pas être résolu.

-ECHILD

Le bus a été créé dans un processus, une bibliothèque ou une instance de module différente.

-ENOMEM

Échec de l'allocation de mémoire.

-EPROTOTYPE

sd_bus_add_object_vtable() et sd_bus_add_fallback_vtable() ont tous deux été appelés pour le même chemin d'objet de bus, ce qui n'est pas autorisé.

-EEXIST

Cette vtable a déjà été enregistrée pour cette interface et ce chemin.

DESCRIPTION

The D-Bus message bus is a system for inter-process communication. It allows applications to send messages to each other, export methods, and receive signals.

sd_bus_add_object(), sd_bus_add_object_vtable(), sd_bus_add_fallback(), sd_bus_add_fallback_vtable(), and sd_bus_add_filter() are functions that allow you to add simple object implementations to a bus.

Objects are identified by a unique object path (e.g. "/org/example/MyObject"). Methods and properties are organized by interfaces (e.g. "org.example.MyInterface").

sd_bus_add_object_vtable() adds a set of methods and properties for a given object path and interface, defined by a sd_bus_vtable structure. The sd_bus_vtable structure contains an array of sd_bus_slot entries, each describing a method or property.

sd_bus_add_object() is a simplified version of sd_bus_add_object_vtable() that allows adding a single method handler for a given object path and interface.

sd_bus_add_fallback_vtable() and sd_bus_add_fallback() are similar to their non-fallback counterparts, but they are only invoked if no other object can handle the request. This is useful for implementing generic error handling or default behavior.

sd_bus_add_filter() adds a message handler that is called for all messages that match the specified object path. This can be used for logging, authentication, or other cross-cutting concerns.

The sd_bus_vtable structure is used to define a set of methods and properties for an object. It contains an array of sd_bus_vtable_entry structures, each of which describes a single method or property.

The sd_bus_vtable_entry structure has the following members:

.method
The name of the method or property.
.signature
The D-Bus signature of the method or property.
.handler
A pointer to the handler function for the method or property.
.offset
An offset into the userdata structure for property access.
.flags
Flags that control the behavior of the method or property.

The handler functions are responsible for processing incoming messages and sending replies. They receive a pointer to the incoming message, a pointer to the reply message, and a pointer to the userdata provided when the object was added.

sd_bus_property_get_t is a type for getter functions for properties. sd_bus_property_set_t is a type for setter functions for properties. sd_bus_object_find_t is a type for functions that find objects on the bus.

The functions described here use getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.

EXAMPLES

Example 1. Adding a simple object with one method:

static int my_method_handler(sd_bus_message *message, void *userdata) {
    // Handle the method call
    return sd_bus_reply_method_return(message, "");
}

static const sd_bus_vtable my_vtable[] = {
    {
        .method = SD_BUS_VTABLE_Lu(my_method_handler),
        .signature = "s",
        .handler = my_method_handler,
    },
    SD_BUS_VTABLE_END
};

int ret = sd_bus_add_object_vtable(bus, "/org/example/MyObject", "org.example.MyInterface", my_vtable, NULL);
if (ret < 0) {
    // Handle error
}

Example 2. Adding a fallback object:

static int fallback_handler(sd_bus_message *message, void *userdata) {
    // Handle the request as a fallback
    return sd_bus_reply_method_error(message, "org.example.Error", "Object not found");
}

int ret = sd_bus_add_fallback(bus, "/org/example", fallback_handler, NULL);
if (ret < 0) {
    // Handle error
}

RETURN VALUE

On success, these functions return 0 or a positive integer. On failure, they return a negative error number.
