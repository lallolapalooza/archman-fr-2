SD_EVENT_ADD_MEMORY_PRESSURE(3) sd_event_add_memory_pressure SD_EVENT_ADD_MEMORY_PRESSURE(3)

NOM

sd_event_add_memory_pressure, sd_event_source_set_memory_pressure_type, sd_event_source_set_memory_pressure_period, sd_event_trim_memory - Ajoute et configure une source d'événements fonctionnant en résultat de la pression mémoire

SYNOPSIS

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;

int sd_event_add_memory_pressure(sd_event *event, sd_event_source **ret_source, sd_event_handler_t handler, void *userdata);

int sd_event_source_set_memory_pressure_type(sd_event_source *source, const char *type);

int sd_event_source_set_memory_pressure_period(sd_event_source *source, uint64_t threshold_usec, uint64_t window_usec);

int sd_event_trim_memory(void);

DESCRIPTION

sd_event_add_memory_pressure() ajoute une nouvelle source d'événements qui est déclenchée chaque fois qu'une pression mémoire est détectée. Cette fonctionnalité est basée sur la logique Pressure Stall Information (PSI)[1] du noyau Linux.

Attend un objet de boucle d'événements comme premier paramètre, et retourne l'objet source d'événements alloué dans le second paramètre, en cas de succès. Le paramètre handler est une fonction à appeler lorsque la pression mémoire est détectée, ou NULL. La fonction handler recevra le pointeur userdata, qui peut être choisi librement par l'appelant. Le handler peut retourner une valeur négative pour signaler une erreur (voir ci-dessous), d'autres valeurs de retour sont ignorées. Si handler est NULL, un handler par défaut qui compresse les caches d'allocation maintenus par libsystemd ainsi que glibc (via malloc_trim(3)) sera utilisé.

Pour détruire un objet source d'événements, utilisez sd_event_source_unref(3), mais notez que la source d'événements n'est retirée de la boucle d'événements que lorsque toutes les références à la source d'événements sont libérées. Pour s'assurer qu'une source d'événements ne se déclenche plus, même si elle est toujours référencée, désactivez la source d'événements en utilisant sd_event_source_set_enabled(3) avec SD_EVENT_OFF.

Si le second paramètre de sd_event_add_memory_pressure() est NULL, aucune référence à l'objet source d'événements n'est retournée. Dans ce cas, la source d'événements est considérée comme "flottante" et sera détruite implicitement lorsque la boucle d'événements elle-même sera détruite.

La source d'événements se déclenchera selon la logique suivante :

1.Si les variables d'environnement $MEMORY_PRESSURE_WATCH/$MEMORY_PRESSURE_WRITE sont définies au moment où la source d'événements est établie, elle surveillera le fichier, FIFO ou socket AF_UNIX spécifié via $MEMORY_PRESSURE_WATCH (qui doit contenir un nom de chemin absolu) pour les événements POLLPRI (s'il s'agit d'un fichier régulier) ou POLLIN (sinon). Après avoir ouvert l'inode, il écrira les données Base64 (décodées) fournies via $MEMORY_PRESSURE_WRITE dedans avant de commencer à les interroger (la variable peut être non définie, auquel cas cela est ignoré). Généralement, si elle est utilisée, $MEMORY_PRESSURE_WATCH contiendra un chemin tel que /proc/pressure/memory ou un chemin vers un fichier spécifique memory.pressure dans le système de fichiers de groupe de contrôle (cgroupfs).
2.Si ces variables d'environnement ne sont pas définies, le fichier d'interface PSI local memory.pressure du groupe de contrôle dans lequel le processus appelant s'exécute est utilisé.
3.Si ce fichier n'existe pas, le fichier d'interface PSI système /proc/pressure/memory est surveillé à la place.

Ou en d'autres termes : de préférence, toute configuration explicite fournie par un gestionnaire de service (ou similaire) est utilisée comme source de notification, avant de se rabattre sur les notifications locales du service, et enfin sur les notifications globales du système.

Il est recommandé aux services et applications bien conçus de réagir aux événements de pression mémoire en exécutant une ou plusieurs des opérations suivantes, afin d'assurer un comportement optimal même sur des systèmes chargés et contraints en ressources :

•Libérer les caches d'allocation tels que malloc_trim() ou similaires, à la fois implémentés dans les bibliothèques utilisées par le programme et dans les caches d'allocation privés du programme lui-même.
•Libérer toute autre forme de caches en mémoire qui peuvent être facilement récupérés si nécessaire (par exemple, les caches de navigateur).
•Terminer les threads ou processus de travail inactifs, ou similaires.
•Même quitter complètement le programme s'il est inactif et peut être démarré automatiquement lorsque nécessaire (par exemple via une activation par socket ou bus).

Toute opération suggérée devrait aider à atténuer les situations de pression mémoire et permettre au système de progresser en récupérant la mémoire à d'autres fins.

Cette source d'événements se déclenche généralement lors des arrêts de pression mémoire, c'est-à-dire lorsque des latences opérationnelles supérieures à un seuil configuré ont déjà été observées. Cela doit être pris en compte lors de la discussion pour savoir si les latences ultérieures pour réacquérir des ressources libérées sont acceptables : il est généralement plus important de penser aux latences qui se sont déjà produites qu'à celles qui surviendront à l'avenir.

Les fonctions sd_event_source_set_memory_pressure_type() et sd_event_source_set_memory_pressure_period() peuvent être utilisées pour affiner les paramètres PSI pour les notifications de pression. La première prend soit "some", soit "full" comme second paramètre, la seconde prend les seuils et périodes en microsecondes comme paramètres. Pour plus de détails sur ces trois paramètres, voir la documentation PSI. Notez que ces deux appels doivent être effectués immédiatement après l'allocation de la source d'événements, car ils doivent être configurés avant que l'interrogation ne commence. Notez également que ces appels échoueront si la paramétrisation de la pression mémoire a été fournie via les variables d'environnement $MEMORY_PRESSURE_WATCH/$MEMORY_PRESSURE_WRITE (ou en d'autres termes : la configuration fournie par un gestionnaire de service l'emporte sur les paramètres internes).

La fonction sd_event_trim_memory() libère divers caches d'allocation internes maintenus par libsystemd, puis appelle malloc_trim(3) de glibc. Cela rend l'opération exécutée lorsque le paramètre de fonction handler de sd_event_add_memory_pressure est passé comme NULL directement accessible pour invocation à tout moment (voir ci-dessus). Cette fonction affichera un message de journal structuré au niveau LOG_DEBUG (avec l'ID de message f9b0be465ad540d0850ad32172d57c21) concernant l'opération de pression mémoire.

Pour plus de détails, voir Gestion de la pression mémoire dans systemd[2].

VALEUR RENVOYÉE

En cas de succès, ces fonctions retournent 0 ou un entier positif. En cas d'échec, elles retournent un code d'erreur négatif de style errno.

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-ENOMEM

Pas assez de mémoire pour allouer un objet.

Ajouté dans la version 254.

-EINVAL

Un argument invalide a été passé.

Ajouté dans la version 254.

-EHOSTDOWN

La variable $MEMORY_PRESSURE_WATCH a été définie sur la chaîne littérale /dev/null, afin de désactiver explicitement la gestion de la pression mémoire.

Ajouté dans la version 254.

-EBADMSG

La variable $MEMORY_PRESSURE_WATCH a été définie sur une chaîne invalide, par exemple un chemin relatif plutôt qu'absolu.

Ajouté dans la version 254.

-ENOTTY

La variable $MEMORY_PRESSURE_WATCH pointe vers un fichier régulier en dehors des systèmes de fichiers procfs ou cgroupfs.

Ajouté dans la version 254.

-EOPNOTSUPP

Aucune configuration via $MEMORY_PRESSURE_WATCH n'a été spécifiée et le noyau local ne prend pas en charge l'interface PSI.

Ajouté dans la version 254.

-EBUSY

Ceci est retourné par sd_event_source_set_memory_pressure_type() et sd_event_source_set_memory_pressure_period() si invoqué sur des sources d'événements à un moment ultérieur qu'immédiatement après leur allocation.

Ajouté dans la version 254.

-ESTALE

La boucle d'événements est déjà terminée.

Ajouté dans la version 254.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas sûr pour les threads multiples. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'appeler setenv() qu'à partir d'une phase précoce du programme, lorsque aucun autre thread n'a été démarré.
