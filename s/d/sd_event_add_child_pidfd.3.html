DESCRIPTION

sd_event_add_child() ajoute une nouvelle source d'événement d'état de processus enfant à une boucle d'événements. L'objet boucle d'événements est spécifié dans le paramètre event, l'objet source d'événement est retourné dans le paramètre source. Le paramètre pid spécifie le PID du processus à surveiller, qui doit être un processus enfant direct du processus appelant. Le paramètre options détermine quels changements d'état seront surveillés. Il doit contenir un masque OR de WEXITED (surveiller la terminaison du processus enfant), WSTOPPED (surveiller l'arrêt du processus enfant par un signal), et WCONTINUED (surveiller la reprise du processus enfant par un signal). Voir waitid(2) pour plus d'informations.

Le handler doit être une fonction à appeler lorsque le processus change d'état, ou NULL. La fonction de rappel recevra le pointeur userdata, qui peut être choisi librement par l'appelant. Le gestionnaire reçoit également un pointeur vers une structure siginfo_t contenant des informations sur l'événement du processus enfant. Le gestionnaire peut retourner une valeur négative pour signaler une erreur (voir ci-dessous), d'autres valeurs de retour sont ignorées. Si handler est NULL, un gestionnaire par défaut qui appelle sd_event_exit(3) sera utilisé.

Une seule fonction de rappel peut être installée pour un processus enfant spécifique. La fonction de rappel est activée pour un seul événement (SD_EVENT_ONESHOT), mais cela peut être modifié avec sd_event_source_set_enabled(3). Si la fonction de rappel retourne un code d'erreur négatif, elle sera soit désactivée après l'invocation, même si le mode SD_EVENT_ON avait été demandé auparavant, soit elle provoquera la fin de la boucle, voir sd_event_source_set_exit_on_failure(3).

Pour détruire un objet source d'événement, utilisez sd_event_source_unref(3), mais notez que la source d'événement n'est retirée de la boucle d'événements que lorsque toutes les références à la source d'événement sont libérées. Pour vous assurer qu'une source d'événement ne se déclenche plus, même si une référence est toujours conservée, envisagez de définir la source d'événement sur SD_EVENT_OFF avec sd_event_source_set_enabled(3).

Le signal SIGCHLD doit être bloqué dans tous les threads avant que cette fonction ne soit appelée (en utilisant sigprocmask(2) ou pthread_sigmask(3)).

Si le deuxième paramètre de sd_event_add_child() est passé comme NULL, aucune référence à l'objet source d'événement n'est retournée. Dans ce cas, la source d'événement est considérée comme "flottante", et sera détruite implicitement lorsque la boucle d'événements elle-même sera détruite.

Notez que la fonction handler est appelée à un moment où le processus enfant n'a pas encore été "récolté" (et est donc toujours exposé comme un processus zombie par le noyau). Cependant, l'enfant sera automatiquement récolté après le retour de la fonction. Les processus enfants pour lesquels aucune source d'événement d'état de processus enfant n'est installée ne seront pas récoltés par l'implémentation de la boucle d'événements.

Si le paramètre handler de sd_event_add_child() est NULL, et que la source d'événement se déclenche, cela sera considéré comme une demande de sortie de la boucle d'événements. Dans ce cas, le paramètre userdata, converti en entier, est passé comme paramètre de code de sortie à sd_event_exit(3).

Si à la fois une source d'événement d'état de processus enfant et une source d'événement de signal SIGCHLD sont installées dans la même boucle d'événements, les priorités configurées des sources d'événements décident quelle source d'événement est traitée en premier. Si la fonction de rappel du signal est traitée en premier, elle doit laisser les processus enfants pour lesquels des sources d'événements d'état de processus enfant sont installées non récoltés.

sd_event_add_child_pidfd() est similaire à sd_event_add_child() mais prend un descripteur de fichier référençant le processus ("pidfd") au lieu du PID numérique. Un descripteur de fichier approprié peut être obtenu via pidfd_open(2) et les appels associés. Le descripteur de fichier passé n'est pas fermé lorsque la source d'événement est à nouveau libérée, sauf si sd_event_source_set_child_pidfd_own() est utilisé pour activer ce comportement. Notez que quelle que soit la fonction utilisée, sd_event_add_child() ou sd_event_add_child_pidfd() pour allouer une source d'événement, le processus surveillé doit être un processus enfant direct du processus appelant. Dans les deux cas, SIGCHLD doit être bloqué dans le processus appelant.

sd_event_source_get_child_pid() récupère le PID configuré d'une source d'événement d'état de processus enfant créée précédemment avec sd_event_add_child(). Elle prend l'objet source d'événement comme paramètre source et un pointeur vers une variable pid_t pour y retourner l'ID du processus.

sd_event_source_get_child_pidfd() récupère le descripteur de fichier référençant le processus surveillé ("pidfd"). La boucle d'événements utilise en interne des pidfds pour surveiller les processus enfants, que les sources d'événements individuelles soient allouées via sd_event_add_child() ou sd_event_add_child_pidfd(). Si le dernier appel a été utilisé pour allouer la source d'événement, cette fonction retourne le descripteur de fichier original utilisé pour l'allocation. Cet appel prend l'objet source d'événement comme paramètre source et retourne le descripteur de fichier numérique.

sd_event_source_get_child_pidfd_own() peut être utilisé pour interroger si le pidfd que la source d'événement encapsule doit être fermé lorsque la source d'événement est libérée. Cette fonction retourne zéro si le pidfd doit rester ouvert, et une valeur positive s'il doit être fermé automatiquement. Par défaut, ce réglage est activé si la source d'événement a été allouée via sd_event_add_child() et désactivé si elle a été allouée via sd_event_add_child_pidfd(). La fonction sd_event_source_set_child_pidfd_own() peut être utilisée pour modifier le réglage et prend un paramètre booléen avec le nouveau réglage.

sd_event_source_get_child_process_own() peut être utilisé pour interroger si le processus que la source d'événement surveille doit être tué (avec SIGKILL) et récolté lorsque la source d'événement est libérée. Cette fonction retourne zéro si le processus doit rester en cours d'exécution, et une valeur positive s'il doit être tué et récolté automatiquement. Par défaut, ce réglage est désactivé. DESCRIPTION

Ces fonctions sont utilisées pour enregistrer un nouveau type de source d'événement de boucle d'événements, qui surveille la terminaison d'un processus enfant. Le descripteur de fichier de processus, ou pidfd, est obtenu en appelant pidfd_open(2) sur le pid du processus enfant. Cela est utilisé avec sd_event_add_child_pidfd. Le descripteur de fichier de processus pidfd est automatiquement fermé lors de la destruction de la source de l'événement. Le pidfd est généralement passé à l'aide de pidfd_open(2).

La fonction sd_event_add_child enregistre une nouvelle source d'événement pour le processus enfant pid. Lorsque le processus enfant pid se termine, le gestionnaire handler est appelé. Le argument userdata est passé au gestionnaire. Le argument event est la boucle d'événements.

Les fonctions sd_event_source_get_child_pidfd_own et sd_event_source_set_child_pidfd_own peuvent être utilisées pour obtenir ou définir si la source d'événement doit prendre possession du pidfd donné. Si la source possède le pidfd, elle le fermera automatiquement lorsqu'elle sera détruite. Par défaut, la source de l'événement n'a pas la propriété du pidfd.

Les fonctions sd_event_source_get_child_process_own et sd_event_source_set_child_process_own peuvent être utilisées pour obtenir ou définir si la source d'événement doit prendre possession du processus enfant donné. Si la source prend possession du processus enfant, elle tentera d'appeler waitid(2) pour le processus enfant lors de la destruction de la source de l'événement.

L'argument wstatus_flags contient des drapeaux qui sont passés à waitid(2). Les valeurs possibles sont WEXITED, WSTOPPED et WCONTINUED. Si aucun drapeau n'est spécifié, le comportement par défaut est d'attendre la terminaison du processus enfant. Si WEXITED est spécifié, le gestionnaire est appelé uniquement lorsque le processus enfant se termine. Si WSTOPPED est spécifié, le gestionnaire est appelé lorsque le processus enfant est arrêté. Si WCONTINUED est spécifié, le gestionnaire est appelé lorsque le processus enfant continue après avoir été arrêté.

Notez que si le processus appelant se termine anormalement, le processus surveillé peut survivre même si la source d'événement cesse d'exister. Ce comportement pourrait changer à terme.

sd_event_source_send_child_signal() peut être utilisé pour envoyer un signal UNIX au processus surveillé via pidfd_send_signal(2). Les paramètres spécifiés correspondent à ceux de l'appel système sous-jacent, à l'exception du fait que info n'est jamais modifié (et est donc déclaré constant). Comme pour l'appel système sous-jacent, le paramètre flags doit actuellement être zéro.

VALEUR DE RETOUR

En cas de succès, ces fonctions retournent 0 ou un entier positif. En cas d'échec, elles retournent un code d'erreur négatif de style errno.

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-ENOMEM

Pas assez de mémoire pour allouer un objet.

-EINVAL

Un argument invalide a été passé. Cela inclut la spécification d'un masque vide dans options ou d'un masque contenant des valeurs autres qu'une combinaison de WEXITED, WSTOPPED et WCONTINUED.

-EBUSY

Un gestionnaire est déjà installé pour ce processus enfant, ou SIGCHLD n'est pas bloqué.

-ESTALE

La boucle d'événements est déjà terminée.

-ECHILD

La boucle d'événements a été créée dans un processus, une bibliothèque ou une instance de module différent.

-EDOM

La source d'événement passée n'est pas une source d'événement de processus enfant.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée à l'aide du fichier pkg-config(1) de libsystemd.

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'effectuer des appels à setenv() qu'à partir d'une phase précoce du programme, lorsque aucun autre thread n'a été démarré.

EXEMPLE

Exemple 1. Sortir de la boucle lorsque l'enfant se termine

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <assert.h>
#include <stdio.h>
#include <unistd.h>
#include <systemd/sd-event.h>
int main(int argc, char **argv) {
  pid_t pid = fork();
  assert(pid >= 0);
  /* Le signal SIGCHLD doit être bloqué pour que sd_event_add_child fonctionne */
  sigset_t ss;
  sigemptyset(&ss);
  sigaddset(&ss, SIGCHLD);
  sigprocmask(SIG_BLOCK, &ss, NULL);
  if (pid == 0)  /* enfant */
    sleep(1);
  else {         /* parent */
    sd_event *e = NULL;
    int r;
    /* Créer la boucle d'événements par défaut */
    sd_event_default(&e);
    assert(e);
    /* Nous créons une source d'événement enfant flottante (attachée à 'e').
     * Le gestionnaire par défaut sera appelé avec 666 comme userdata, ce qui
     * deviendra la valeur de sortie de la boucle. */
    r = sd_event_add_child(e, NULL, pid, WEXITED, NULL, (void*) 666);
    assert(r >= 0);
    r = sd_event_loop(e);
    assert(r == 666);
    sd_event_unref(e);
  }
  return 0;
}
