SD_EVENT_ADD_MEMORY_PRESSURE(3) sd_event_add_memory_pressure SD_EVENT_ADD_MEMORY_PRESSURE(3)

NOM

sd_event_add_memory_pressure, sd_event_source_set_memory_pressure_type, sd_event_source_set_memory_pressure_period, sd_event_trim_memory - Ajouter et configurer une source d'événement déclenchée par une pression mémoire

SYNTAXE

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;

int sd_event_add_memory_pressure(sd_event *event, sd_event_source **ret_source, sd_event_handler_t handler, void *userdata);

int sd_event_source_set_memory_pressure_type(sd_event_source *source, const char *type);

int sd_event_source_set_memory_pressure_period(sd_event_source *source, uint64_t threshold_usec, uint64_t window_usec);

int sd_event_trim_memory(void);

DESCRIPTION

sd_event_add_memory_pressure() ajoute une nouvelle source d'événement qui est déclenchée chaque fois qu'une pression mémoire est détectée. Cette fonctionnalité est basée sur la logique Pressure Stall Information (PSI)[1] du noyau Linux.

Elle attend un objet de boucle d'événements comme premier paramètre, et renvoie l'objet source d'événement alloué dans le second paramètre en cas de succès. Le paramètre handler est une fonction à appeler lorsqu'une pression mémoire est détectée, ou NULL. La fonction handler recevra le pointeur userdata, qui peut être choisi librement par l'appelant. Le handler peut retourner une valeur négative pour signaler une erreur (voir ci-dessous), les autres valeurs de retour sont ignorées. Si handler est NULL, un handler par défaut qui compresse les caches d'allocation maintenus par libsystemd ainsi que par glibc (via malloc_trim(3)) sera utilisé.

Pour détruire un objet source d'événement, utilisez sd_event_source_unref(3), mais notez que la source d'événement n'est retirée de la boucle d'événements que lorsque toutes les références à la source d'événement sont supprimées. Pour vous assurer qu'une source d'événement ne se déclenche plus, même si elle est toujours référencée, désactivez la source d'événement en utilisant sd_event_source_set_enabled(3) avec SD_EVENT_OFF.

Si le second paramètre de sd_event_add_memory_pressure() est NULL, aucune référence à l'objet source d'événement n'est renvoyée. Dans ce cas, la source d'événement est considérée comme "flottante" et sera détruite implicitement lorsque la boucle d'événements elle-même sera détruite.

La source d'événement se déclenchera selon la logique suivante :

1.Si les variables d'environnement $MEMORY_PRESSURE_WATCH/$MEMORY_PRESSURE_WRITE sont définies lorsque la source d'événement est établie, elle surveillera le fichier, le FIFO ou le socket AF_UNIX spécifié via $MEMORY_PRESSURE_WATCH (qui doit contenir un nom de chemin absolu) pour les événements POLLPRI (s'il s'agit d'un fichier régulier) ou POLLIN (sinon). Après avoir ouvert l'inode, il écrira les données Base64 (décodées) fournies via $MEMORY_PRESSURE_WRITE dedans avant de commencer à interroger (la variable peut être désactivée, auquel cas cela est ignoré). Typiquement, si elle est utilisée, $MEMORY_PRESSURE_WATCH contiendra un chemin tel que /proc/pressure/memory ou un chemin vers un fichier memory.pressure spécifique dans le système de fichiers de groupe de contrôle (cgroupfs).
2.Si ces variables d'environnement ne sont pas définies, le fichier d'interface PSI local memory.pressure du groupe de contrôle auquel le processus appelant appartient est utilisé.
3.Si ce fichier n'existe pas, le fichier d'interface PSI global /proc/pressure/memory est surveillé à la place.

Autrement dit : de préférence, toute configuration explicite fournie par un gestionnaire de services (ou similaire) est utilisée comme source de notification, avant de se rabattre sur les notifications locales du service, et enfin sur les notifications globales du système.

Il est recommandé aux services et applications bien conçus de réagir aux événements de pression mémoire en exécutant une ou plusieurs des opérations suivantes, afin d'assurer un comportement optimal même sur les systèmes chargés et contraints en ressources :

•Libérer les caches d'allocation tels que malloc_trim() ou similaires, implémentés à la fois dans les bibliothèques utilisées par le programme et dans les caches d'allocation privés du programme lui-même.
•Libérer toute autre forme de caches en mémoire qui peuvent être facilement récupérés si nécessaire (par exemple, les caches de navigateur).
•Terminer les threads ou processus de travail inactifs, ou similaires.
•Même quitter complètement le programme s'il est inactif et peut être démarré automatiquement si nécessaire (par exemple, via une activation par socket ou par bus).

Toute opération suggérée devrait aider à atténuer les situations de pression mémoire et permettre au système de progresser en récupérant la mémoire à d'autres fins.

Cette source d'événement se déclenche généralement lors de périodes de forte pression mémoire, c'est-à-dire lorsque une latence opérationnelle supérieure à un seuil configuré a déjà été observée. Cela doit être pris en compte lors de la discussion de savoir si une latence ultérieure pour réacquérir des ressources libérées est acceptable : il est généralement plus important de penser aux latences qui se sont déjà produites que celles qui surviendront à l'avenir.

Les fonctions sd_event_source_set_memory_pressure_type() et sd_event_source_set_memory_pressure_period() peuvent être utilisées pour affiner les paramètres PSI pour les notifications de pression. La première prend soit "some", soit "full" comme second paramètre, la seconde prend les délais de seuil et de période en microsecondes comme paramètres. Pour plus de détails sur ces trois paramètres, consultez la documentation PSI. Notez que ces deux appels doivent être invoqués immédiatement après l'allocation de la source d'événement, car ils doivent être configurés avant que l'interrogation ne commence. Notez également que ces appels échoueront si la paramétrisation de la pression mémoire a été transmise via les variables d'environnement $MEMORY_PRESSURE_WATCH/$MEMORY_PRESSURE_WRITE (ou en d'autres termes : la configuration fournie par un gestionnaire de services l'emporte sur les paramètres internes).

La fonction sd_event_trim_memory() libère divers caches d'allocation internes maintenus par libsystemd, puis invoque malloc_trim(3) de glibc. Cela rend l'opération exécutée lorsque le paramètre de la fonction handler de sd_event_add_memory_pressure est passé comme NULL directement accessible pour invocation à tout moment (voir ci-dessus). Cette fonction enregistrera un message de journal structuré au niveau LOG_DEBUG (avec l'ID de message f9b0be465ad540d0850ad32172d57c21) concernant l'opération de pression mémoire.

Pour plus de détails, voir Memory Pressure Handling in systemd[2].

VALEUR RENVOYÉE

En cas de succès, ces fonctions renvoient 0 ou un entier positif. En cas d'échec, elles renvoient un code d'erreur négatif de style errno.

Erreurs

Les erreurs renvoyées peuvent indiquer les problèmes suivants :

-ENOMEM

Pas assez de mémoire pour allouer un objet.

Ajouté dans la version 254.

-EINVAL

Un argument invalide a été passé.

Ajouté dans la version 254.

-EHOSTDOWN

La variable $MEMORY_PRESSURE_WATCH a été définie sur la chaîne littérale /dev/null, afin de désactiver explicitement la gestion de la pression mémoire.

Ajouté dans la version 254.

-EBADMSG

La variable $MEMORY_PRESSURE_WATCH a été définie sur une chaîne invalide, par exemple un chemin relatif plutôt qu'absolu.

Ajouté dans la version 254.

-ENOTTY

La variable $MEMORY_PRESSURE_WATCH pointe vers un fichier régulier en dehors des systèmes de fichiers procfs ou cgroupfs.

Ajouté dans la version 254.

-EOPNOTSUPP

Aucune configuration via $MEMORY_PRESSURE_WATCH n'a été spécifiée et le noyau local ne prend pas en charge l'interface PSI.

Ajouté dans la version 254.

-EBUSY

Ceci est renvoyé par sd_event_source_set_memory_pressure_type() et sd_event_source_set_memory_pressure_period() si invoqué sur des sources d'événements à un moment ultérieur qu'immédiatement après leur allocation.

Ajouté dans la version 254.

-ESTALE

La boucle d'événements est déjà terminée.

Ajouté dans la version 254.

-ECHILD

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas sûr pour les threads multiples. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'appeler setenv() que depuis une phase précoce du programme, lorsque aucun autre thread n'a été démarré.
