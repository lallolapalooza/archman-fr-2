SD_BUS_DEFAULT(3) sd_bus_default SD_BUS_DEFAULT(3)

NOM

sd_bus_default, sd_bus_default_user, sd_bus_default_system, sd_bus_open, sd_bus_open_with_description, sd_bus_open_user, sd_bus_open_user_with_description, sd_bus_open_user_machine, sd_bus_open_system, sd_bus_open_system_with_description, sd_bus_open_system_remote, sd_bus_open_system_machine - Acquérir une connexion à un bus système ou utilisateur

SYNTAXE

#include <systemd/sd-bus.h>

int sd_bus_default(sd_bus **bus);

int sd_bus_default_user(sd_bus **bus);

int sd_bus_default_system(sd_bus **bus);

int sd_bus_open(sd_bus **bus);

int sd_bus_open_with_description(sd_bus **bus, const char *description);

int sd_bus_open_user(sd_bus **bus);

int sd_bus_open_user_with_description(sd_bus **bus, const char *description);

int sd_bus_open_user_machine(sd_bus **bus, const char *machine);

int sd_bus_open_system(sd_bus **bus);

int sd_bus_open_system_with_description(sd_bus **bus, const char *description);

int sd_bus_open_system_remote(sd_bus **bus, const char *host);

int sd_bus_open_system_machine(sd_bus **bus, const char *machine);

DESCRIPTION

sd_bus_default() acquiert un objet de connexion au bus utilisateur lorsque appelé depuis une tranche utilisateur (toute session sous "user-*.slice", par exemple : "user@1000.service"), ou au bus système sinon. L'objet de connexion est associé au thread appelant. Chaque fois que la fonction est appelée depuis le même thread, le même objet est renvoyé, mais son compteur de références est incrémenté d'une unité, tant qu'au moins une référence est conservée. Lorsque la dernière référence à la connexion est libérée (en utilisant l'appel sd_bus_unref(3)), la connexion est terminée. Notez que la connexion n'est pas automatiquement terminée lorsque le thread associé se termine. Il est important de libérer explicitement la dernière référence à la connexion bus avant la fin du thread, car sinon, la connexion fuira. De plus, les messages mis en file d'attente mais non lus ou non écrits maintiennent une référence au bus, voir ci-dessous.

sd_bus_default_user() renvoie un objet de connexion au bus utilisateur associé au thread appelant. sd_bus_default_system() est similaire, mais se connecte au bus système. Notez que sd_bus_default() est identique à ces deux appels, selon le contexte d'exécution.

sd_bus_open() crée une nouvelle connexion de bus indépendante au bus utilisateur lorsqu'elle est appelée dans le contexte utilisateur, ou au bus système sinon. sd_bus_open_user() est similaire, mais se connecte uniquement au bus utilisateur. sd_bus_open_system() fait de même, mais se connecte au bus système. Contrairement à sd_bus_default(), sd_bus_default_user() et sd_bus_default_system(), ces appels renvoient de nouveaux objets de connexion indépendants qui ne sont pas associés au thread appelant et ne sont pas partagés entre plusieurs invocations. Il est recommandé de partager les connexions par thread pour utiliser efficacement les ressources disponibles. Par conséquent, il est recommandé d'utiliser sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() pour se connecter aux bus utilisateur ou système.

sd_bus_open_with_description(), sd_bus_open_user_with_description() et sd_bus_open_system_with_description() sont similaires à sd_bus_open(), sd_bus_open_user() et sd_bus_open_system(), mais permettent de définir une chaîne de description, voir sd_bus_set_description(3). description peut être NULL, auquel cas cette fonction est équivalente à sd_bus_open(). Cette chaîne de description est utilisée dans les messages de journal concernant l'objet bus, et inclure un "nom" pour le bus les rend plus faciles à comprendre. Certains messages sont émis lors de l'initialisation du bus, c'est pourquoi l'utilisation de cette fonction est préférable à la définition de la description ultérieurement avec sd_bus_open_with_description(). L'argument est copié en interne et ne sera pas référencé après le retour de la fonction.

Si la variable d'environnement $DBUS_SESSION_BUS_ADDRESS est définie (cf. environ(7)), elle sera utilisée comme adresse du bus utilisateur. Cette variable peut contenir plusieurs adresses séparées par des ";". Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance D-Bus utilisateur par défaut sera utilisée.

Si la variable d'environnement $DBUS_SYSTEM_BUS_ADDRESS est définie, elle sera utilisée comme adresse du bus système. Cette variable utilise la même syntaxe que $DBUS_SESSION_BUS_ADDRESS. Si cette variable n'est pas définie, une valeur par défaut appropriée pour l'instance D-Bus système par défaut sera utilisée.

sd_bus_open_system_remote() se connecte au bus système sur l'hôte spécifié en utilisant ssh(1). host se compose d'un nom d'utilisateur optionnel suivi du symbole "@", et du nom d'hôte, optionnellement suivi d'un ":" et d'un port, optionnellement suivi d'un "/" et d'un nom de machine. Si le nom de la machine est donné, une connexion est créée au bus système dans le conteneur spécifié sur la machine distante, et sinon une connexion au bus système sur l'hôte spécifié est créée.

Notez que l'entrée dans un conteneur est une opération privilégiée, et ne fonctionnera probablement que pour l'utilisateur root sur la machine distante.

sd_bus_open_system_machine() se connecte au bus système dans la machine spécifiée, où machine est le nom d'un conteneur local, potentiellement préfixé par un nom d'utilisateur et un "@" séparateur. Si le nom du conteneur est spécifié comme la chaîne spéciale ".host", la connexion est établie au système local. Ceci est utile pour se connecter au bus système local en tant qu'utilisateur spécifique, par exemple "foobar@.host" pour se connecter au bus système local en tant qu'utilisateur local "foobar". Si la syntaxe "@" est utilisée, soit le côté gauche, soit le côté droit peut être omis (mais pas les deux), auquel cas le nom d'utilisateur local ou ".host" est implicite. Si la syntaxe "@" n'est pas utilisée, la connexion est toujours établie en tant qu'utilisateur root. Voir sd_bus_set_address(3) pour une description de la syntaxe d'adresse, et machinectl(1) pour plus d'informations sur le concept de "machine". Notez que les connexions dans les conteneurs locaux ne sont actuellement disponibles que pour les processus privilégiés.

sd_bus_open_user_machine() est similaire à sd_bus_open_system_machine(), mais se connecte au bus utilisateur de l'utilisateur root, ou si la syntaxe "@" est utilisée, de l'utilisateur spécifié.

Ces appels allouent un objet de connexion bus et initient la connexion à un bus bien connu d'une certaine forme. Une alternative à l'utilisation de ces appels de haut niveau est de créer un objet bus non connecté avec sd_bus_new(3) et de le connecter avec sd_bus_start(3).

PROPRIÉTÉ DES RÉFÉRENCES

Les fonctions sd_bus_open(), sd_bus_open_user(), sd_bus_open_user_machine(), sd_bus_open_system(), sd_bus_open_system_remote() et sd_bus_open_system_machine() renvoient un nouvel objet de connexion et l'appelant détient la référence unique. Lorsqu'elle n'est plus nécessaire, cette référence doit être détruite avec sd_bus_unref(3).

Les fonctions sd_bus_default(), sd_bus_default_user() et sd_bus_default_system() ne créent pas nécessairement un nouvel objet, mais incrémentent la référence de connexion d'un objet de connexion existant d'une unité. Utilisez sd_bus_unref(3) pour abandonner la référence.

Les messages mis en file d'attente mais non écrits/lus conservent une référence à leur objet de connexion bus. Pour cette raison, même si une application a abandonné toutes ses références à une connexion bus, elle pourrait ne pas être détruite immédiatement. Tant que tous les messages entrants mis en file d'attente ne sont pas lus, et tant que tous les messages sortants non écrits ne sont pas écrits, l'objet bus restera en vie. sd_bus_flush() peut être utilisé pour écrire tous les messages sortants mis en file d'attente afin qu'ils libèrent leurs références. sd_bus_default_system(3) — systemd manual pages

NAME

sd_bus_default_system, sd_bus_default_user, sd_bus_default — get connection to the system or user message bus

SYNOPSIS

#include <systemd/sd-bus.h>
int sd_bus_default_system(sd_bus **bus);
int sd_bus_default_user(sd_bus **bus);
int sd_bus_default(sd_bus **bus);

DESCRIPTION

These functions return a reference to the default connection object to the system message bus (sd_bus_default_system), the user message bus (sd_bus_default_user), or the bus determined by the environment (sd_bus_default). The latter is equivalent to sd_bus_default_user unless the $SYSTEMD_USER_WANTS environment variable is set, in which case it is equivalent to sd_bus_default_system.

These functions are intended for simple use cases where only one connection to the bus is needed. The bus object returned is shared between all callers that request the same bus type. The reference count of the bus object is increased by these calls.

Use sd_bus_unref(3) to decrease the reference count when done. The bus object will be destroyed when the last reference is dropped.

It is generally recommended to use sd_bus_open_system(3) or sd_bus_open_user(3) instead, as this allows for better control over the bus connection object's lifecycle and makes it easier to manage multiple connections.

REFERENCE OWNERSHIP

The bus connection object returned by these functions is a shared resource. When the last reference to the bus object is dropped using sd_bus_unref(), the bus connection will be closed and the object freed.

When using the default bus logic, it is a good idea to first invoke sd_bus_flush() followed by sd_bus_close() when a thread or process terminates, and thus its bus connection object should be freed.

Normally, slot objects (as created by sd_bus_add_match(3) and similar calls) keep a reference to their bus connection object, too. Thus, as long as a bus slot object remains referenced its bus object will remain allocated too. Optionally, bus slot objects may be placed in "floating" mode. When in floating mode the life cycle of the bus slot object is bound to the bus object, i.e. when the bus object is freed the bus slot object is automatically unreferenced too. The floating state of a slot object may be controlled explicitly with sd_bus_slot_set_floating(3), though usually floating bus slot objects are created by passing NULL as the slot parameter of sd_bus_add_match() and related calls, thus indicating that the caller is not directly interested in referencing and managing the bus slot object.

The life cycle of the default bus connection should be the responsibility of the code that creates/owns the thread the default bus connection object is associated with. Library code should neither call sd_bus_flush() nor sd_bus_close() on default bus objects unless it does so in its own private, self-allocated thread. Library code should not use the default bus object in other threads unless it is clear that the program using it will life cycle the bus connection object and flush and close it before exiting from the thread. In libraries where it is not clear that the calling program will life cycle the bus connection object, it is hence recommended to use sd_bus_open_system() instead of sd_bus_default_system() and related calls.

RETURN VALUE

On success, these calls return 0 or a positive integer. On failure, these calls return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

The specified parameters are invalid.

-ENOMEDIUM

The requested bus type is not available because of invalid environment (for example the user session bus is not available because $XDG_RUNTIME_DIR is not set).

-ENOMEM

Memory allocation failed.

-ESOCKTNOSUPPORT

The protocol version required to connect to the selected bus is not supported.

In addition, other connection-related errors may be returned. See sd_bus_send(3).

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
