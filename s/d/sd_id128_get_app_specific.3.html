SD_ID128_GET_MACHINE(3) sd_id128_get_machine SD_ID128_GET_MACHINE(3)

NOM

sd_id128_get_machine, sd_id128_get_app_specific, sd_id128_get_machine_app_specific, sd_id128_get_boot, sd_id128_get_boot_app_specific, sd_id128_get_invocation - Récupérer des identifiants 128 bits

SYNOPIS

#include <systemd/sd-id128.h>

int sd_id128_get_machine(sd_id128_t *ret);

int sd_id128_get_app_specific(sd_id128_t base, sd_id128_t app_id, sd_id128_t *ret);

int sd_id128_get_machine_app_specific(sd_id128_t app_id, sd_id128_t *ret);

int sd_id128_get_boot(sd_id128_t *ret);

int sd_id128_get_boot_app_specific(sd_id128_t app_id, sd_id128_t *ret);

int sd_id128_get_invocation(sd_id128_t *ret);

int sd_id128_get_invocation_app_specific(sd_id128_t app_id, sd_id128_t *ret);

DESCRIPTION

sd_id128_get_machine() renvoie l'identifiant machine de l'hôte en cours d'exécution. Ceci lit et analyse le fichier machine-id(5). Cette fonction met en cache l'identifiant machine en interne pour que sa récupération soit une opération peu coûteuse. Cet identifiant peut être utilisé partout où un identifiant unique pour le système local est nécessaire. Cependant, il est recommandé d'utiliser cet identifiant tel quel uniquement dans des environnements de confiance. Dans des environnements non fiables, il est recommandé de dériver un identifiant spécifique à l'application à partir de cet identifiant machine, d'une manière irréversible (cryptographiquement sécurisée). Pour faciliter cela, sd_id128_get_machine_app_specific() est fournie, voir ci-dessous.

sd_id128_get_app_specific() renvoie un identifiant machine qui est une combinaison des paramètres base et app_id. En interne, cette fonction calcule HMAC-SHA256 du paramètre app_id en utilisant le paramètre base comme clé, et tronque ce résultat pour qu'il tienne dans sd_id128_t et le transforme en un UUID valide de variante 1, version 4, conformément à la RFC 4122[1]. Ni l'un ni l'autre des deux paramètres d'entrée ne peut être calculé à partir du paramètre de sortie ret.

sd_id128_get_machine_app_specific() est similaire à sd_id128_get_machine(), mais récupère un identifiant machine qui est spécifique à l'application identifiée par l'identifiant d'application indiqué. Il est recommandé d'utiliser cette fonction plutôt que sd_id128_get_machine() lors du passage d'un identifiant à des environnements non fiables, afin de s'assurer que l'identifiant machine d'origine ne puisse pas être déterminé extérieurement. De cette façon, l'identifiant utilisé par l'application reste stable sur une machine donnée, mais ne peut pas être facilement corrélé avec les identifiants utilisés dans d'autres applications sur la même machine. L'identifiant spécifique à l'application doit être généré via un outil tel que systemd-id128 new, et peut être compilé dans l'application. Cette fonction renverra le même identifiant spécifique à l'application pour chaque combinaison d'identifiant machine et d'identifiant d'application. En interne, cette fonction appelle sd_id128_get_app_specific() avec le résultat de sd_id128_get_machine() et le paramètre app_id.

sd_id128_get_boot() renvoie l'identifiant de démarrage du noyau en cours d'exécution. Ceci lit et analyse le fichier /proc/sys/kernel/random/boot_id exposé par le noyau. Il est généré aléatoirement tôt au démarrage et est unique pour chaque instance de noyau en cours d'exécution. Voir random(4) pour plus d'informations. Cette fonction met également en cache en interne l'identifiant renvoyé pour que cet appel soit une opération peu coûteuse. Il est recommandé d'utiliser cet identifiant tel quel uniquement dans des environnements de confiance. Dans des environnements non fiables, il est recommandé de dériver un identifiant spécifique à l'application en utilisant sd_id128_get_boot_app_specific(), voir ci-dessous.

sd_id128_get_boot_app_specific() est analogue à sd_id128_get_machine_app_specific(), mais renvoie un identifiant qui change entre les démarrages. Certaines machines peuvent être utilisées pendant une longue période sans redémarrer, donc l'identifiant de démarrage peut rester constant pendant longtemps, et a des propriétés similaires à l'identifiant machine pendant cette période.

sd_id128_get_invocation() renvoie l'identifiant d'invocation du service actuellement exécuté. Dans son implémentation actuelle, cela tente de lire et d'analyser les éléments suivants :

•La variable d'environnement $INVOCATION_ID que le gestionnaire de services définit lors de l'activation d'un service.
•Une entrée dans la clé du noyau que le gestionnaire de services système définit lors de l'activation d'un service.

Voir systemd.exec(5) pour plus de détails. L'identifiant est mis en cache en interne. À l'avenir, un mécanisme différent pour déterminer l'identifiant d'invocation pourra être ajouté.

sd_id128_get_invocation_app_specific() dérive un identifiant spécifique à l'application à partir de l'identifiant d'invocation.

Notez que sd_id128_get_machine_app_specific(), sd_id128_get_boot(), sd_id128_get_boot_app_specific(), sd_id128_get_invocation() et sd_id128_get_invocation_app_specific renvoient toujours des identifiants compatibles avec les UUID Variante 1 Version 4. sd_id128_get_machine() renverra également un identifiant compatible avec les UUID Variante 1 Version 4 lors de nouvelles installations, mais pourrait ne pas le faire sur des anciennes. Il est possible de convertir l'identifiant machine de manière non réversible en un identifiant compatible avec les UUID Variante 1 Version 4. Pour plus d'informations, voir machine-id(5). Il est donc garanti que ces fonctions ne renverront jamais l'identifiant constitué uniquement de zéros ou uniquement de uns (SD_ID128_NULL, SD_ID128_ALLF) — à l'exception possible de sd_id128_get_machine(), comme mentionné.

Pour plus d'informations sur le type "sd_id128_t" voir sd-id128(3).

VALEUR RENVOYÉE

Ces appels renvoient 0 en cas de succès (auquel cas ret est rempli), ou un code d'erreur négatif de style errno.

Erreurs

Les erreurs renvoyées peuvent indiquer les problèmes suivants :

-ENOENT

Renvoyé par sd_id128_get_machine() et sd_id128_get_machine_app_specific() lorsque /etc/machine-id est manquant.

Ajouté dans la version 242.

-ENOMEDIUM

Renvoyé par sd_id128_get_machine() et sd_id128_get_machine_app_specific() lorsque /etc/machine-id est vide ou tous des zéros. Également renvoyé par sd_id128_get_invocation() lorsque l'identifiant d'invocation est tous des zéros.

Ajouté dans la version 242.

-ENOPKG

Renvoyé par sd_id128_get_machine() et sd_id128_get_machine_app_specific() lorsque le contenu de /etc/machine-id est "non initialisé".

Ajouté dans la version 253.

-ENOSYS

Renvoyé par sd_id128_get_boot() et sd_id128_get_boot_app_specific() lorsque /proc/ n'est pas monté.

Ajouté dans la version 253.

-ENXIO

Renvoyé par sd_id128_get_invocation() si aucun identifiant d'invocation n'est défini. Également renvoyé par sd_id128_get_app_specific(), sd_id128_get_machine_app_specific(), et sd_id128_get_boot_app_specific() lorsque le paramètre app_id est constitué uniquement de zéros.

Ajouté dans la version 242.

-EUCLEAN

Renvoyé par l'une des fonctions décrites ici lorsque la valeur configurée a un format invalide.

Ajouté dans la version 253.

-EPERM

Les informations demandées n'ont pas pu être récupérées en raison d'autorisations insuffisantes.

Ajouté dans la version 242.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée avec et liée à l'aide du fichier libsystemd pkg-config(1).

Le code décrit ici utilise getenv(3), qui est déclaré comme n'étant pas thread-safe. Cela signifie que le code appelant les fonctions décrites ici ne doit pas appeler setenv(3) à partir d'un thread parallèle. Il est recommandé de n'effectuer des appels à setenv() que dès le début du programme, lorsqu'aucun autre thread n'a été démarré.

EXEMPLES

Exemple 1. Identifiant machine spécifique à l'application

D'abord, générez l'identifiant d'application :

    $ systemd-id128 new
    auto:a3bb3b8e-00c4-45a5-ac11-e643c089828c

Ensuite, compilez l'application C :

    $ cat app-id.c
    #include <stdio.h>
    #include <systemd/sd-id128.h>

    int main(void) {
        sd_id128_t id;
        const char *app_id_str = "a3bb3b8e-00c4-45a5-ac11-e643c089828c";
        sd_id128_t app_id;
        int r;

        r = sd_id128_get_machine_app_specific(SD_ID128_CONST(app_id_str), &id);
        if (r < 0) {
            fprintf(stderr, "Failed to get machine-specific ID: %s\n", strerror(-r));
            return 1;
        }

        sd_id128_to_string(id, output_buffer);
        printf("Machine-specific ID: %s\n", output_buffer);

        return 0;
    }

Compilez et exécutez :

    $ gcc app-id.c -o app-id -lsystemd
    $ ./app-id
    Machine-specific ID: 8b34c37f-f37c-4f9d-90e1-92372509a778

Si vous exécutez la même commande sur une autre machine, vous obtiendrez probablement un identifiant différent.

#include <stdio.h>

  sd_id128_get_machine_app_specific(OUR_APPLICATION_ID, &id);
  printf("Our application ID: " SD_ID128_FORMAT_STR "\n", SD_ID128_FORMAT_VAL(id));
  return 0;
}
