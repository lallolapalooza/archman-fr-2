DESCRIPTION

sd_pid_get_owner_uid() peut être utilisée pour déterminer l'UID Unix (identifiant utilisateur) qui possède la session de connexion ou l'unité utilisateur systemd d'un processus identifié par le PID spécifié. Pour les processus qui ne font pas partie d'une session de connexion et ne sont pas gérés par un gestionnaire utilisateur, cette fonction échouera avec -ENODATA.

sd_pid_get_session() peut être utilisée pour déterminer l'identifiant de la session de connexion d'un processus identifié par l'identifiant de processus spécifié. L'identifiant de session est une chaîne courte, adaptée à une utilisation dans les chemins de systèmes de fichiers. Notez que la session de connexion peut être limitée à un processus stub ou deux. Les processus utilisateur peuvent plutôt être démarrés depuis leur gestionnaire utilisateur systemd, par exemple des applications graphiques démarrées en utilisant l'activation DBus, ainsi que des processus de service qui sont partagés entre plusieurs connexions du même utilisateur. Pour les processus qui ne font pas partie d'une session de connexion, cette fonction échouera avec -ENODATA. La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_user_unit() peut être utilisée pour déterminer l'identifiant de l'unité utilisateur systemd (c'est-à-dire un service utilisateur ou une unité de portée) d'un processus identifié par le PID spécifié. Le nom de l'unité est une chaîne courte, adaptée à une utilisation dans les chemins de systèmes de fichiers. Pour les processus qui ne sont pas gérés par un gestionnaire utilisateur, cette fonction échouera avec -ENODATA. La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_unit() peut être utilisée pour déterminer l'identifiant de l'unité système systemd (c'est-à-dire un service système ou une unité de portée) d'un processus identifié par le PID spécifié. Le nom de l'unité est une chaîne courte, adaptée à une utilisation dans les chemins de systèmes de fichiers. Notez que tous les processus ne font pas partie d'une unité/service système. Pour les processus ne faisant pas partie d'une unité système systemd, cette fonction échouera avec -ENODATA. (Plus spécifiquement, cet appel ne fonctionnera pas pour les threads du noyau.) La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation.

sd_pid_get_machine_name() peut être utilisée pour déterminer le nom de la VM ou du conteneur dont le processus est membre. Le nom de la machine est une chaîne courte, adaptée à une utilisation dans les chemins de systèmes de fichiers. La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation. Pour les processus qui ne font pas partie d'une VM ou d'un conteneur, cette fonction échoue avec -ENODATA.

sd_pid_get_slice() peut être utilisée pour déterminer la tranche (slice unit) dont le processus est membre. Voir systemd.slice(5) pour les détails sur les tranches. La chaîne retournée doit être libérée avec l'appel free(3) de la libc après utilisation.

De même, sd_pid_get_user_slice() retourne la tranche utilisateur (telle que gérée par l'instance systemd de l'utilisateur) d'un processus.

sd_pid_get_cgroup() retourne le chemin du groupe de contrôle du processus spécifié, relatif à la racine de la hiérarchie. Retourne le chemin sans slash final, sauf pour les processus situés dans le groupe de contrôle racine, où "/" est retourné. Pour trouver le chemin réel du groupe de contrôle dans le système de fichiers, le chemin retourné doit être préfixé par /sys/fs/cgroup/.

Si le paramètre pid de l'une de ces fonctions est passé comme 0, l'opération est exécutée pour le processus appelant.

Les appels sd_pidfd_get_owner_uid(), sd_pidfd_get_session(), sd_pidfd_get_user_unit(), sd_pidfd_get_unit(), sd_pidfd_get_machine_name(), sd_pidfd_get_slice(), sd_pidfd_get_user_slice() et sd_pidfd_get_cgroup() fonctionnent de manière similaire à leurs homologues PID, mais acceptent un PIDFD au lieu d'un PID, ce qui signifie qu'ils ne sont pas sujets aux conditions de concurrence de recyclage, car le processus est épinglé par le descripteur de fichier pendant toute la durée de l'invocation. Notez que cela nécessite un noyau qui prend en charge les PIDFD. Un descripteur de fichier approprié peut être obtenu via pidfd_open(2).

Les appels sd_peer_get_owner_uid(), sd_peer_get_session(), sd_peer_get_user_unit(), sd_peer_get_unit(), sd_peer_get_machine_name(), sd_peer_get_slice(), sd_peer_get_user_slice() et sd_peer_get_cgroup() fonctionnent de manière similaire à leurs homologues PID, mais acceptent un socket AF_UNIX connecté et récupèrent des informations sur le processus pair connecté. Notez que ces champs sont récupérés via /proc/, et ne conviennent donc pas à des fins d'autorisation, car ils sont sujets à des conditions de concurrence.

VALEUR DE RETOUR

En cas de succès, ces appels retournent 0 ou un entier positif. En cas d'échec, ces appels retournent un code d'erreur négatif de style errno.

Erreurs

Les erreurs retournées peuvent indiquer les problèmes suivants :

-ESRCH

Le PID spécifié ne correspond pas à un processus en cours d'exécution.

-EBADF

Le descripteur de fichier spécifié est invalide.

-ENODATA

Le champ spécifié n'est pas défini pour le processus ou le pair décrit.

-EINVAL

Un argument invalide a été fourni.

-EFAULT

Un pointeur invalide a été fourni.

NOTES

Les fonctions décrites ici sont disponibles sous forme de bibliothèque partagée, qui peut être compilée et liée avec le fichier libsystemd pkg-config(1).

Notez que l'identifiant de session de connexion tel que retourné par sd_pid_get_session() n'est absolument pas lié à l'identifiant de session de processus tel que retourné par getsid(2).
