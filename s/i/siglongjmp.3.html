setjmp(3) Manuel des fonctions de bibliothèque setjmp(3)

NOM

setjmp, sigsetjmp, longjmp, siglongjmp - effectuer un got nonlocal

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <setjmp.h>
int setjmp(jmp_buf env);
int sigsetjmp(sigjmp_buf env, int savesigs);
[[noreturn]] void longjmp(jmp_buf env, int val);
[[noreturn]] void siglongjmp(sigjmp_buf env, int val);
Conditions pour les macros de test de fonctionnalités pour glibc (voir feature_test_macros(7)):

setjmp(): voir HISTORIQUE.

sigsetjmp():

    _POSIX_C_SOURCE

DESCRIPTION

Les fonctions décrites sur cette page sont utilisées pour effectuer des "gotos non locaux" : transférer l'exécution d'une fonction vers un emplacement prédéterminé dans une autre fonction. La fonction setjmp() établit dynamiquement la cible vers laquelle le contrôle sera transféré plus tard, et longjmp() effectue le transfert d'exécution.

La fonction setjmp() sauvegarde diverses informations sur l'environnement d'appel (typiquement, le pointeur de pile, le pointeur d'instruction, éventuellement les valeurs d'autres registres et le masque de signaux) dans le tampon env pour une utilisation ultérieure par longjmp(). Dans ce cas, setjmp() retourne 0.

La fonction longjmp() utilise les informations sauvegardées dans env pour transférer le contrôle vers le point où setjmp() a été appelée et pour restaurer ("rembobiner") la pile à son état au moment de l'appel à setjmp(). De plus, et en fonction de l'implémentation (voir NOTES et HISTORIQUE), les valeurs d'autres registres et le masque de signaux du processus peuvent être restaurés à leur état au moment de l'appel à setjmp().

Après un longjmp() réussi, l'exécution continue comme si setjmp() avait retourné pour la seconde fois. Ce retour "factice" peut être distingué d'un appel réel à setjmp() car le retour "factice" retourne la valeur fournie dans val. Si le programmeur passe par erreur la valeur 0 dans val, le retour "factice" retournera plutôt 1.

sigsetjmp() et siglongjmp()

sigsetjmp() et siglongjmp() effectuent également des gotos non locaux, mais fournissent une gestion prévisible du masque de signaux du processus.

Si, et seulement si, l'argument savesigs fourni à sigsetjmp() est non nul, le masque de signaux actuel du processus est sauvegardé dans env et sera restauré si un siglongjmp() est ultérieurement effectué avec cet env.

VALEUR DE RETOUR

setjmp() et sigsetjmp() retournent 0 lorsqu'ils sont appelés directement ; lors du retour "factice" qui se produit après longjmp() ou siglongjmp(), la valeur non nulle spécifiée dans val est retournée.

Les fonctions longjmp() ou siglongjmp() ne retournent pas.

longjmp (), siglongjmp () Sécurité des threads MT-Safe

POSIX.1-2001.

POSIX ne spécifie pas si setjmp() sauvegardera le masque de signaux (à restaurer lors du longjmp()). Dans System V, ce ne sera pas le cas. Dans 4.3BSD, ce sera le cas, et il existe une fonction _setjmp() qui ne le fera pas. Le comportement sous Linux dépend de la version de glibc et du réglage des macros de test de fonctionnalités. Avant glibc 2.19, setjmp() suit le comportement de System V par défaut, mais le comportement BSD est fourni si la macro de test de fonctionnalité _BSD_SOURCE est explicitement définie et si aucune des macros _POSIX_SOURCE, _POSIX_C_SOURCE, _XOPEN_SOURCE, _GNU_SOURCE ou _SVID_SOURCE n'est définie. Depuis glibc 2.19, <setjmp.h> n'expose que la version System V de setjmp(). Les programmes qui ont besoin de la sémantique BSD doivent remplacer les appels à setjmp() par des appels à sigsetjmp() avec un argument savesigs non nul.

NOTES

setjmp() et longjmp() peuvent être utiles pour traiter des erreurs dans des appels de fonctions profondément imbriqués ou pour permettre à un gestionnaire de signaux de passer le contrôle à un point spécifique du programme, plutôt que de retourner au point où le gestionnaire a interrompu le programme principal. Dans ce dernier cas, si vous souhaitez sauvegarder et restaurer les masques de signaux de manière portable, utilisez sigsetjmp() et siglongjmp(). Voir également la discussion sur la lisibilité du programme ci-dessous.

MISE EN GARDE

Le compilateur peut optimiser les variables dans des registres, et longjmp() peut restaurer les valeurs d'autres registres en plus du pointeur de pile et du compteur de programme. Par conséquent, les valeurs des variables automatiques sont indéterminées après un appel à longjmp() si elles satisfont tous les critères suivants :

•
elles sont locales à la fonction qui a effectué l'appel correspondant à setjmp() ;
•
leurs valeurs sont modifiées entre les appels à setjmp() et longjmp() ; et
•
elles ne sont pas déclarées comme volatile.

Des remarques analogues s'appliquent à siglongjmp().

Gotoss non locaux et lisibilité du programme

Bien qu'il puisse être mal utilisé, l'instruction C traditionnelle "goto" a au moins l'avantage que les indices lexicaux (l'instruction goto et l'étiquette cible) permettent au programmeur de percevoir facilement le flux de contrôle. Les gotos non locaux n'offrent aucun indice de ce type : plusieurs appels à setjmp() peuvent utiliser la même variable jmp_buf, de sorte que le contenu de la variable peut changer au cours de la durée de vie de l'application. Par conséquent, le programmeur peut être obligé de lire en détail le code pour déterminer la cible dynamique d'un appel particulier à longjmp(). (Pour faciliter la vie du programmeur, chaque appel à setjmp() devrait utiliser une variable jmp_buf unique.)

Ajoutant encore à la difficulté, les appels à setjmp() et longjmp() peuvent ne même pas se trouver dans le même module source.

En résumé, les gotos non locaux peuvent rendre les programmes plus difficiles à comprendre et à maintenir, et une alternative devrait être utilisée si possible.

Comportement indéfini

Si la fonction qui a appelé setjmp() retourne avant que longjmp() ne soit appelée, le comportement est indéfini. Une sorte de chaos subtil ou non subtil ne manquera pas de résulter.

Dans un programme multithreadé, si un appel à longjmp() utilise un tampon env qui a été initialisé par un appel à setjmp() dans un autre thread, le comportement est indéfini.

siglongjmp(3) — Manual page

NAME

siglongjmp, longjmp — non-local goto

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS 

#include <setjmp.h>

void longjmp(jmp_buf env, int val);
void siglongjmp(sigjmp_buf env, int val);

DESCRIPTION

The longjmp() function restores the stack environment saved by a previous call to setjmp() or sigsetjmp() with the buffer env. Execution continues as if the corresponding setjmp() or sigsetjmp() call had returned the value val. If val is zero, the call to setjmp() or sigsetjmp() will return 1; otherwise, it will return val.

The siglongjmp() function is similar to longjmp(), but it also restores the signal mask that was in effect when the corresponding sigsetjmp() call was made. The signal mask is restored by setting the process's signal mask to the value that was saved in the env buffer.

If val is zero, the corresponding call to sigsetjmp() will return 1; otherwise, it will return val.

If the buffer env was not initialized by a call to setjmp() or sigsetjmp(), or if longjmp() or siglongjmp() is called after the buffer has been overwritten by a subsequent call to setjmp() or sigsetjmp(), the behavior is undefined.

A call to longjmp() or siglongjmp() is referred to as a "long jump".

RETURN VALUE

longjmp() and siglongjmp() never return. Execution restarts at the point where setjmp() or sigsetjmp() was called.

ATTRIBUTES

For an explanation of the terms used in this section, see attributes(7).

+--------------------------------+---------------+
     | Interface                      | Attribute     |
     +--------------------------------+---------------+
     | longjmp(), siglongjmp()        | No-fork behavior|
     +--------------------------------+---------------+

STANDARDS

The longjmp() function is described in C99 and POSIX.1-2001. The siglongjmp() function is described in POSIX.1-2001.

HISTORY

C99, POSIX.1-2001.

NOTES

The use of longjmp() and siglongjmp() can make program logic difficult to follow and can be error-prone. They should be used with caution.

It is unsafe to call longjmp() or siglongjmp() from a signal handler unless the handler was established using sigsetjmp() with a non-zero value for the second argument. Even then, there are restrictions.

POSIX.1-2008 Technical Corrigendum 2 adds longjmp() and siglongjmp() to the list of async-signal-safe functions. However, the standard recommends avoiding the use of these functions from signal handlers and goes on to point out that if these functions are called from a signal handler that interrupted a call to a non-async-signal-safe function (or some equivalent, such as the steps equivalent to exit(3) that occur upon a return from the initial call to main()), the behavior is undefined if the program subsequently makes a call to a non-async-signal-safe function. The only way of avoiding undefined behavior is to ensure one of the following:

•
After long jumping from the signal handler, the program does not call any non-async-signal-safe functions and does not return from the initial call to main().
•
Any signal whose handler performs a long jump must be blocked during every call to a non-async-signal-safe function and no non-async-signal-safe functions are called after returning from the initial call to main().

CAVEATS

Using longjmp() or siglongjmp() from within a signal handler is generally unsafe unless the handler was set up with sigsetjmp() and the program adheres to the restrictions described in the NOTES section.
