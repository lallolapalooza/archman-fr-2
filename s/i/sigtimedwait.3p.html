SIGTIMEDWAIT(3P) Manuel du programmeur POSIX SIGTIMEDWAIT(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consulter la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

sigtimedwait, sigwaitinfo — attendre des signaux mis en file d'attente

SYNTAXE

#include <signal.h>
int sigtimedwait(const sigset_t *restrict set,
    siginfo_t *restrict info,
    const struct timespec *restrict timeout);
int sigwaitinfo(const sigset_t *restrict set,
    siginfo_t *restrict info);

DESCRIPTION

La fonction sigtimedwait() est équivalente à sigwaitinfo() sauf que si aucun des signaux spécifiés par set n'est en attente, sigtimedwait() attendra l'intervalle de temps spécifié dans la structure timespec référencée par timeout. Si la structure timespec pointée par timeout a une valeur nulle et si aucun des signaux spécifiés par set n'est en attente, alors sigtimedwait() retournera immédiatement avec une erreur. Si timeout est un pointeur nul, le comportement n'est pas spécifié. Si l'option Horloge Monotone est supportée, l'horloge CLOCK_MONOTONIC sera utilisée pour mesurer l'intervalle de temps spécifié par l'argument timeout.

La fonction sigwaitinfo() sélectionne le signal en attente parmi l'ensemble spécifié par set. Si plusieurs signaux en attente dans la plage SIGRTMIN à SIGRTMAX sont sélectionnés, ce sera celui dont le numéro est le plus bas. L'ordre de sélection entre les signaux temps réel et non temps réel, ou entre plusieurs signaux non temps réel en attente, n'est pas spécifié. Si aucun signal dans set n'est en attente au moment de l'appel, le thread appelant sera suspendu jusqu'à ce qu'un ou plusieurs signaux dans set deviennent en attente ou jusqu'à ce qu'il soit interrompu par un signal non bloqué et capturé.

La fonction sigwaitinfo() est équivalente à la fonction sigwait(), sauf que la valeur de retour et la méthode de signalement d'erreur sont différentes (voir VALEUR DE RETOUR), et que si l'argument info n'est pas NULL, le numéro du signal sélectionné sera stocké dans le membre si_signo, et la cause du signal sera stockée dans le membre si_code. Si une valeur est mise en file d'attente pour le signal sélectionné, la première valeur mise en file d'attente sera dépilée et, si l'argument info n'est pas NULL, la valeur sera stockée dans le membre si_value de info. La ressource système utilisée pour mettre en file d'attente le signal sera libérée et retournée au système pour une autre utilisation. Si aucune valeur n'est mise en file d'attente, le contenu du membre si_value est indéfini. Si aucun autre signal n'est mis en file d'attente pour le signal sélectionné, l'indication d'attente pour ce signal sera réinitialisée.

VALEUR DE RETOUR

En cas de succès (c'est-à-dire, si l'un des signaux spécifiés par set est en attente ou est généré), sigwaitinfo() et sigtimedwait() retourneront le numéro du signal sélectionné. Sinon, la fonction retournera une valeur de -1 et définira errno pour indiquer l'erreur.

ERREURS

La fonction sigtimedwait() échouera si :

EAGAIN
Aucun signal spécifié par set n'a été généré dans le délai imparti.

Les fonctions sigtimedwait() et sigwaitinfo() peuvent échouer si :

EINTR
L'attente a été interrompue par un signal capturé non bloqué. Il doit être documenté dans la documentation du système si cette erreur provoque l'échec de ces fonctions.

La fonction sigtimedwait() peut également échouer si :

EINVAL
L'argument timeout spécifiait une valeur tv_nsec inférieure à zéro ou supérieure ou égale à 1000 millions.

Une implémentation ne devrait vérifier cette erreur que si aucun signal n'est en attente dans set et qu'il est nécessaire d'attendre.

Les sections suivantes sont informatives.

EXEMPLES

Aucun.

UTILISATION PAR L'APPLICATION

La fonction sigtimedwait() expire et retourne une erreur [EAGAIN]. Les développeurs d'applications doivent noter que cela est incohérent avec d'autres fonctions comme pthread_cond_timedwait() qui retournent [ETIMEDOUT].

Notez que pour s'assurer que les signaux générés sont mis en file d'attente et que les valeurs de signal passées à sigqueue() sont disponibles dans si_value, les applications qui utilisent sigwaitinfo() ou sigtimedwait() doivent définir le drapeau SA_SIGINFO pour chaque signal dans l'ensemble (voir Section 2.4, Concepts de signal). Cela signifie définir chaque signal pour qu'il soit géré par une fonction de capture de signal à trois arguments, même si le gestionnaire n'est jamais appelé. Il n'est pas possible (de manière portable) de définir un gestionnaire de signal sur SIG_DFL tout en définissant le drapeau SA_SIGINFO, car l'affectation au membre sa_handler de struct sigaction au lieu du membre sa_sigaction entraînerait un comportement non défini, et SIG_DFL ne doit pas être compatible par affectation avec sa_sigaction. Même si une affectation de SIG_DFL à sa_sigaction est acceptée par le compilateur, l'implémentation ne doit pas traiter cette valeur comme spéciale—elle pourrait simplement être prise comme l'adresse d'une fonction de capture de signal.

JUSTIFICATION

La pratique de programmation existante sur les systèmes temps réel utilise la capacité de pause en attendant un ensemble d'événements sélectionnés et de gérer le premier événement qui se produit en ligne au lieu d'une fonction de gestion de signal. Cela permet aux applications d'être écrites dans un style dirigé par les événements, similaire à une machine à états. Ce style de programmation est utile pour le traitement de transactions à grande échelle où le débit global d'une application et la capacité à suivre clairement les états sont plus importants que la capacité à minimiser le temps de réponse du traitement d'événements individuels.

Il est possible de construire une fonction macro d'attente de signal à partir du mécanisme de fonction de signal temps réel défini dans ce volume de POSIX.1‐2017. Cependant, une telle macro doit inclure la définition d'un gestionnaire généralisé pour tous les signaux sur lesquels il faut attendre. Une partie importante de la surcharge du traitement du gestionnaire peut être évitée si la fonction d'attente de signal est fournie par le noyau. Ce volume de POSIX.1‐2017 fournit donc deux fonctions d'attente de signal — une qui attend indéfiniment et une avec un délai d'attente — dans le cadre de la spécification globale de la fonction de signal temps réel.

La spécification d'une fonction avec un délai d'attente permet d'écrire une application qui peut être sortie d'une attente après une période définie si aucun événement ne s'est produit. Il a été soutenu que la définition d'un événement de temporisateur avant l'attente et la reconnaissance de l'événement de temporisateur dans l'attente implémenteraient également la même fonctionnalité, mais à un niveau de performance inférieur. En raison de la dégradation des performances associée à la spécification au niveau utilisateur d'un événement de temporisateur et à l'annulation ultérieure de cet événement de temporisateur après que l'attente se soit terminée pour un événement valide, et de la complexité associée à la gestion des conditions de concurrence potentielles liées à la méthode au niveau utilisateur, la fonction distincte a été incluse.

Notez que les sémantiques de la fonction sigwaitinfo() sont quasiment identiques à celles de la fonction sigwait() définie par ce volume de POSIX.1‐2017. La seule différence est que sigwaitinfo() retourne la valeur du signal mis en file d'attente dans l'argument value. Le retour de la valeur mise en file d'attente est nécessaire pour que les applications puissent différencier plusieurs événements mis en file d'attente avec le même numéro de signal.

Les deux fonctions distinctes sont maintenues car certaines implémentations peuvent choisir d'implémenter les fonctions d'extension POSIX Threads et de ne pas implémenter les extensions de signaux mis en file d'attente. Notez cependant que sigwaitinfo() ne retourne pas la valeur mise en file d'attente si l'argument value est NULL, de sorte que la fonction POSIX Threads sigwait() peut être implémentée comme une macro sur sigwaitinfo().

This manual page is a translation of the original Sigwaitinfo(3p) man page, which is part of the POSIX.1-2017 standard. It was generated by the man-pages project.

NAME

sigwaitinfo, sigtimedwait - wait for signals

SYNOPSIS

     #include <signal.h>

     int sigwaitinfo(const sigset_t *restrict set,
         siginfo_t *restrict info);
     int sigtimedwait(const sigset_t *restrict set,
         siginfo_t *restrict info, const struct timespec *restrict timeout);

DESCRIPTION

The sigwaitinfo() function shall suspend the calling thread until at least one signal is generated which is a member of the set specified by set. Upon successful return, the set of pending signals that are members of set shall be returned in the location referenced by info->si_signo. The corresponding siginfo_t structure (pointed to by info) shall be filled in with details about the signal. If info is a null pointer, the information about the signal shall be lost. If more than one signal is pending in set, the signal returned is implementation-dependent. The signal indicated by info->si_signo shall be removed from the set of pending signals for the calling thread.

The sigtimedwait() function is equivalent to sigwaitinfo(), except that a timeout is applied. If the timeout parameter is not a null pointer, it specifies the maximum amount of time the caller is willing to wait. If the structure pointed to by timeout specifies a timeout of zero seconds and zero nanoseconds, the function shall return immediately. If the structure pointed to by timeout specifies a negative value, the behavior is undefined. If the timeout interval expires before the condition is met, sigtimedwait() shall return an error with errno set to [ETIME].

A signal that is handled (i.e., a signal for which a signal disposition has been set using sigaction() other than SIG_DFL or SIG_IGN) shall not be waited for by sigwaitinfo() or sigtimedwait(). If a signal that is handled is generated for the thread, it shall be delivered to the thread according to its disposition. The presence of a signal in the set argument to sigwaitinfo() or sigtimedwait() only affects the behavior of these functions; it does not affect the disposition of the signal.

A signal that is not handled (i.e., a signal for which the disposition is SIG_DFL and is not SIG_IGN) shall be waited for by sigwaitinfo() or sigtimedwait(). If such a signal is generated for the thread, and the signal is a member of set, the signal shall be removed from the set of pending signals for the calling thread, and sigwaitinfo() or sigtimedwait() shall return the signal number in info->si_signo.

If a signal is generated for the process, it shall be delivered to exactly one thread in the process. If the signal is targeted to a specific thread, it is delivered to that thread. Otherwise, if the signal is not blocked by the signal mask of any thread, it is delivered to an arbitrary thread that does not block the signal. If the signal is blocked by the signal mask of all threads, it is delivered to an arbitrary thread that is not blocking the signal. If all threads are blocking the signal, it is delivered to an arbitrary thread.

If the signal is to be delivered to a thread that is suspended in a call to sigwaitinfo() or sigtimedwait() for that signal, the signal shall be removed from the set of pending signals for the calling thread, and the function shall return the signal number in info->si_signo. If other threads are also suspended in calls to sigwaitinfo() or sigtimedwait() for the same signal, they shall remain suspended. If a signal is delivered to a thread which is suspended in a call to sigwaitinfo() or sigtimedwait() for a different signal, the signal shall be removed from the set of pending signals for the calling thread and the call shall return the signal number in info->si_signo.

The sigwaitinfo() and sigtimedwait() functions shall remove the specified signal from the set of pending signals for the calling thread.

The set of signals pending for the calling thread is the intersection of the signals specified by set and the signals that have been delivered to the thread but not yet processed by the application.

The behavior of sigwaitinfo() and sigtimedwait() is affected by the signal mask of the calling thread. These functions shall return only when an unblocked signal that is a member of set is delivered to the thread. Any signals that are blocked by the thread's signal mask are not delivered until they are unblocked. The signal mask of the calling thread is not changed by these functions.

If the info argument is not NULL, the structure pointed to by info shall be filled with signal information corresponding to the signal that caused the function to return. For signals delivered by sigwaitinfo() or sigtimedwait(), info->si_signo is set to the signal number, and info->si_code is set to SI_USER or SI_KERNEL.

A thread that is suspended in a call to sigwaitinfo() or sigtimedwait() is awakened if any signal is delivered to the thread, regardless of whether that signal is a member of the set specified by set. If the awakened signal is a member of set and is not blocked, the function returns the signal number in info->si_signo. If the awakened signal is not a member of set or is blocked, the function returns the signal number in info->si_signo.

RETURN VALUE

On successful completion, sigwaitinfo() and sigtimedwait() return the signal number of the signal that was returned.

If sigtimedwait() times out, it returns an error with errno set to [ETIME].

On failure, these functions return -1 and set errno to indicate the error.

ERRORS

The sigtimedwait() function shall fail if:

[ETIME]
The timeout interval expired before the condition was met.
[EINVAL]
The value specified by timeout is invalid.

The sigwaitinfo() and sigtimedwait() functions may fail if:

[EINTR]
A signal was delivered to the thread while it was blocked waiting for another signal, and the signal was not masked.

EXAMPLES

None.

APPLICATION USAGE

None.

RATIONALE

The sigtimedwait() function was introduced to allow the use of the timeout pointer to address concerns regarding the overloading of the timeout pointer to indicate indefinite wait (no timeout), timed wait, and immediate return, and concerns regarding consistency with other functions where the conditional and timed waits were separate functions from the pure blocking function. The semantics of sigtimedwait() are specified such that sigwaitinfo() could be implemented as a macro with a null pointer for timeout.

The sigwait functions provide a synchronous mechanism for threads to wait for asynchronously-generated signals. One important question was how many threads that are suspended in a call to a sigwait() function for a signal should return from the call when the signal is sent. Four choices were considered:

1.
Return an error for multiple simultaneous calls to sigwait functions for the same signal.
2.
One or more threads return.
3.
All waiting threads return.
4.
Exactly one thread returns.

Prohibiting multiple calls to sigwait() for the same signal was felt to be overly restrictive. The ``one or more'' behavior made implementation of conforming packages easy at the expense of forcing POSIX threads clients to protect against multiple simultaneous calls to sigwait() in application code in order to achieve predictable behavior. There was concern that the ``all waiting threads'' behavior would result in ``signal broadcast storms'', consuming excessive CPU resources by replicating the signals in the general case. Furthermore, no convincing examples could be presented that delivery to all was either simpler or more powerful than delivery to one.

Thus, the consensus was that exactly one thread that was suspended in a call to a sigwait function for a signal should return when that signal occurs. This is not an onerous restriction as:

*
A multi-way signal wait can be built from the single-way wait.
*
Signals should only be handled by application-level code, as library routines cannot guess what the application wants to do with signals generated for the entire process.
*
Applications can thus arrange for a single thread to wait for any given signal and call any needed routines upon its arrival.

In an application that is using signals for interprocess communication, signal processing is typically done in one place. Alternatively, if the signal is being caught so that process cleanup can be done, the signal handler thread can call separate process cleanup routines for each portion of the application. Since the application main line started each portion of the application, it is at the right abstraction level to tell each portion of the application to clean up.

Certainly, there exist programming styles where it is logical to consider waiting for a single signal in multiple threads. A simple sigwait_multiple() routine can be constructed to achieve this goal. A possible implementation would be to have each sigwait_multiple() caller registered as having expressed interest in a set of signals. The caller then waits on a thread-specific condition variable. A single server thread calls a sigwait() function on the union of all registered signals. When the sigwait() function returns, the appropriate state is set and condition variables are broadcast. New sigwait_multiple() callers may cause the pending sigwait() call to be canceled and reissued in order to update the set of signals being waited for.
