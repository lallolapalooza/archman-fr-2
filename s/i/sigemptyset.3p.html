PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation de cette interface sous Linux peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

sigemptyset — initialiser et vider un ensemble de signaux

SYNOPSIS

#include <signal.h>
int sigemptyset(sigset_t *set);

DESCRIPTION

La fonction sigemptyset() initialise l'ensemble de signaux pointé par set de telle sorte que tous les signaux définis dans POSIX.1‐2008 soient exclus.

VALEUR RENVOYÉE

En cas de succès, sigemptyset() renvoie 0 ; sinon, elle renvoie -1 et définit errno pour indiquer l'erreur.

ERREURS

Aucune erreur n'est définie.

RATIONALE

L'implémentation de la fonction sigemptyset() (ou sigfillset()) pourrait très trivialement effacer (ou définir) tous les bits dans l'ensemble de signaux. Alternativement, il serait raisonnable d'initialiser une partie de la structure, telle qu'un champ de version, pour permettre la compatibilité binaire entre les versions où la taille de l'ensemble varie. Pour de telles raisons, sigemptyset() ou sigfillset() doit être appelée avant toute autre utilisation de l'ensemble de signaux, même si cette utilisation est en lecture seule (par exemple, comme argument de sigpending()). Cette fonction n'est pas destinée à l'allocation dynamique.

Les fonctions sigfillset() et sigemptyset() exigent que l'ensemble de signaux résultant inclue (ou exclue) tous les signaux définis dans ce volume de POSIX.1‐2017. Bien qu'il soit hors de portée de ce volume de POSIX.1‐2017 d'imposer cette exigence aux signaux qui sont implémentés comme extensions, il est recommandé que les signaux définis par l'implémentation soient également affectés par ces fonctions. Cependant, il peut y avoir une bonne raison pour qu'un signal particulier ne soit pas affecté. Par exemple, bloquer ou ignorer un signal défini par l'implémentation peut avoir des effets secondaires indésirables, tandis que l'action par défaut pour ce signal est inoffensive. Dans un tel cas, il serait préférable qu'un tel signal soit exclu de l'ensemble de signaux renvoyé par sigfillset().

Dans les premières propositions, il n'y avait pas de distinction entre les signaux invalides et non pris en charge (les noms des signaux optionnels qui n'étaient pas pris en charge par une implémentation n'étaient pas définis par cette implémentation). L'erreur [EINVAL] était donc spécifiée comme une erreur requise pour les signaux invalides. Avec cette distinction, il n'est pas nécessaire d'exiger des implémentations de ces fonctions qu'elles déterminent si un signal optionnel est réellement pris en charge, car cela pourrait avoir un impact significatif sur les performances pour peu de valeur. L'erreur aurait pu être requise pour les signaux invalides et optionnelle pour les signaux non pris en charge, mais cela semblait inutilement complexe. Ainsi, l'erreur est facultative dans les deux cas.
