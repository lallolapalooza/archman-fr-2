signalfd(2) Manuel des appels système signalfd(2)

NOM

signalfd - créer un descripteur de fichier pour accepter des signaux

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/signalfd.h>
int signalfd(int fd, const sigset_t *mask, int flags);

DESCRIPTION

signalfd() crée un descripteur de fichier qui peut être utilisé pour accepter les signaux destinés à l'appelant. Ceci fournit une alternative à l'utilisation d'un gestionnaire de signaux ou de sigwaitinfo(2), et a l'avantage que le descripteur de fichier peut être surveillé par select(2), poll(2) et epoll(7).

L'argument mask spécifie l'ensemble des signaux que l'appelant souhaite accepter via le descripteur de fichier. Cet argument est un ensemble de signaux dont le contenu peut être initialisé à l'aide des macros décrites dans sigsetops(3). Normalement, l'ensemble des signaux à recevoir via le descripteur de fichier doit être bloqué à l'aide de sigprocmask(2), afin d'éviter que les signaux ne soient traités conformément à leurs dispositions par défaut. Il n'est pas possible de recevoir les signaux SIGKILL ou SIGSTOP via un descripteur de fichier signalfd ; ces signaux sont ignorés silencieusement s'ils sont spécifiés dans mask.

Si l'argument fd est -1, alors l'appel crée un nouveau descripteur de fichier et associe l'ensemble de signaux spécifié dans mask à ce descripteur de fichier. Si fd n'est pas -1, alors il doit spécifier un descripteur de fichier signalfd existant et valide, et mask est utilisé pour remplacer l'ensemble de signaux associé à ce descripteur de fichier.

À partir de Linux 2.6.27, les valeurs suivantes peuvent être combinées par OU bit à bit dans flags pour modifier le comportement de signalfd():

SFD_NONBLOCK
Définit le drapeau d'état de fichier O_NONBLOCK sur la description de fichier ouverte (voir open(2)) référencée par le nouveau descripteur de fichier. L'utilisation de ce drapeau évite des appels supplémentaires à fcntl(2) pour obtenir le même résultat.
SFD_CLOEXEC
Définit le drapeau close-on-exec (FD_CLOEXEC) sur le nouveau descripteur de fichier. Voir la description du drapeau O_CLOEXEC dans open(2) pour connaître les raisons pour lesquelles cela peut être utile.

Jusqu'à Linux 2.6.26, l'argument flags n'est pas utilisé et doit être spécifié comme zéro.

signalfd() renvoie un descripteur de fichier qui prend en charge les opérations suivantes :

read(2)
Si un ou plusieurs des signaux spécifiés dans mask est en attente pour le processus, alors le tampon fourni à read(2) est utilisé pour retourner une ou plusieurs structures signalfd_siginfo (voir ci-dessous) qui décrivent les signaux. Le read(2) retourne des informations pour autant de signaux qu'il y en a en attente et qui tiennent dans le tampon fourni. Le tampon doit être au moins de taille sizeof(struct signalfd_siginfo) octets. La valeur de retour de read(2) est le nombre total d'octets lus.
Par conséquent, la lecture de read(2) consomme les signaux, de sorte qu'ils ne sont plus en attente pour le processus (c'est-à-dire qu'ils ne seront pas interceptés par les gestionnaires de signaux et ne pourront pas être acceptés à l'aide de sigwaitinfo(2)).
Si aucun des signaux dans mask n'est en attente pour le processus, alors read(2) bloque soit jusqu'à ce qu'un des signaux dans mask soit généré pour le processus, soit échoue avec l'erreur EAGAIN si le descripteur de fichier a été rendu non bloquant.
poll(2)
select(2)
(et similaires)
Le descripteur de fichier est lisible (l'argument readfds de select(2) ; le drapeau POLLIN de poll(2)) si un ou plusieurs des signaux dans mask est en attente pour le processus.
Le descripteur de fichier signalfd prend également en charge les autres API de multiplexage de descripteurs de fichiers : pselect(2), ppoll(2), et epoll(7).
close(2)
Lorsque le descripteur de fichier n'est plus nécessaire, il doit être fermé. Lorsque tous les descripteurs de fichiers associés au même objet signalfd ont été fermés, les ressources de l'objet sont libérées par le noyau.

La structure signalfd_siginfo

Le format des structures signalfd_siginfo retournées par les lectures (read(2)) depuis un descripteur de fichier signalfd est le suivant :


struct signalfd_siginfo {
    uint32_t ssi_signo;    /* Numéro du signal */
    int32_t  ssi_errno;    /* Numéro d'erreur (non utilisé) */
    int32_t  ssi_code;     /* Code du signal */
    uint32_t ssi_pid;      /* PID de l'expéditeur */
    uint32_t ssi_uid;      /* UID réel de l'expéditeur */
    int32_t  ssi_fd;       /* Descripteur de fichier (SIGIO) */
    uint32_t ssi_tid;      /* ID de temporisateur du noyau (timers POSIX)
    uint32_t ssi_band;     /* Événement de bande (SIGIO) */
    uint32_t ssi_overrun;  /* Compteur de dépassement de délai POSIX */
    uint32_t ssi_trapno;   /* Numéro de piège ayant causé le signal */
    int32_t  ssi_status;   /* Statut de sortie ou signal (SIGCHLD) */
    int32_t  ssi_int;      /* Entier envoyé par sigqueue(3) */
    uint64_t ssi_ptr;      /* Pointeur envoyé par sigqueue(3) */
    uint64_t ssi_utime;    /* Temps CPU utilisateur consommé (SIGCHLD) */
    uint64_t ssi_stime;    /* Temps CPU système consommé
                              (SIGCHLD) */
    uint64_t ssi_addr;     /* Adresse ayant généré le signal
                              (pour les signaux générés par le matériel) */
    uint16_t ssi_addr_lsb; /* Bit le moins significatif de l'adresse
                              (SIGBUS ; depuis Linux 2.6.37) */
    uint8_t  pad[X];       /* Taille du remplissage à 128 octets (permettant
                              des champs supplémentaires à l'avenir) */
};

Chacun des champs de cette structure est analogue au champ portant le même nom dans la structure siginfo_t. La structure siginfo_t est décrite dans sigaction(2). Tous les champs de la structure signalfd_siginfo retournée ne seront pas valides pour un signal spécifique ; l'ensemble des champs valides peut être déterminé à partir de la valeur retournée dans le champ ssi_code. Ce champ est l'analogue du champ si_code de siginfo_t ; voir sigaction(2) pour les détails.

Sémantique de fork(2)

Après un fork(2), l'enfant hérite d'une copie du descripteur de fichier signalfd. Une lecture (read(2)) à partir du descripteur de fichier dans l'enfant retournera des informations sur les signaux mis en file d'attente pour l'enfant.

Sémantique du passage de descripteurs de fichier

Comme pour les autres descripteurs de fichiers, les descripteurs de fichier signalfd peuvent être passés à un autre processus via un socket de domaine UNIX (voir unix(7)). Dans le processus récepteur, une lecture (read(2)) à partir du descripteur de fichier reçu retournera des informations sur les signaux mis en file d'attente pour ce processus.

Sémantique de execve(2)

NAME

signalfd — create a file descriptor to accept signals

SYNOPSIS

#include <sys/signalfd.h>
int signalfd(int fd, const sigset_t *mask, int flags);

DESCRIPTION

The signalfd() system call creates a new file descriptor that collects and delivers signals. This can be used in applications that prefer to handle signals using I/O multiplexing (e.g., using select(2), poll(2), or epoll(7)) instead of traditional signal handlers.

The mask argument specifies the set of signals that the caller wishes to receive via the returned file descriptor. Signals specified in mask are not delivered by default; instead, they are collected and made available for reading from the signalfd file descriptor. Any signals that are blocked (using sigprocmask(2) or pthread_sigmask(3)) and are present in the mask argument will be delivered to the signalfd file descriptor.

The flags argument is a bit mask that controls the behavior of the signalfd file descriptor. The following flags are supported:

SFD_CLOEXEC
Set the close-on-exec (FD_CLOEXEC) flag on the new file descriptor. This flag is useful in the presence of fork(2) and execve(2). If this flag is set, the signalfd file descriptor will be automatically closed in the child process after a successful execve(2). If this flag is not set, the file descriptor will remain open across execve(2) calls.
SFD_NONBLOCK
Set the non-blocking flag on the new file descriptor. If this flag is set, reads from the signalfd file descriptor will not block. If no signal is available, read operations will return -1 and set errno to EAGAIN.
SFD_DISPATCH
(Since Linux 4.10) Use signalfd dispatching semantics. Normally, when a signal is received and read from a signalfd, the signal is considered to have been delivered. If SFD_DISPATCH is specified, the signal is not considered delivered until the read operation completes. This means that if the program receives multiple signals of the same type, and the first read returns before SFD_DISPATCH is processed, the program might enter signal handler code before the signalfd has consumed the signal.

If fd is -1, then signalfd() creates a new signalfd file descriptor. If fd is a valid existing signalfd file descriptor, then signalfd() replaces the signal mask and flags of that existing signalfd file descriptor with mask and flags, and returns fd. This allows modifying the set of signals being monitored without creating a new file descriptor.

When one or more signals specified in mask are delivered to the calling thread, an event is made available on the signalfd file descriptor. Reading from the signalfd file descriptor retrieves one struct signalfd_siginfo structure for each signal read. The struct signalfd_siginfo structure is similar to the siginfo_t structure used with signal handlers.

The reading thread consumes the signal. This means that if a signal is read from the signalfd, it is no longer pending for the process or thread, and will not be delivered by default signal handling mechanisms (e.g., to a signal handler).

The structure is defined as follows:

struct signalfd_siginfo {
    uint32_t    ssi_signo;   /* Signal number */
    int32_t     ssi_errno;   /* Error number */
    int32_t     ssi_isrtim;  /* Real-time timer expired */
    uint16_t    ssi_setlen;  /* Size of notification values */
    uint16_t    __pad1;      /* Will be populated */
    pid_t       ssi_pid;     /* PID of sender */
    uid_t       ssi_uid;     /* UID of sender */
    int         ssi_fd;      /* File descriptor associated with signal */
    uint32_t    ssi_tid;     /* Timer ID (only foritimers) */
    int32_t     ssi_overrun; /* Timer overrun count (only foritimers) */
    int322_t    ssi_val;     /* Notification value (SIGIO) */
    void        *ssi_ptr;    /* Pointer to data with signal (sigqueue()) */
    int32_t     ssi_status;  /* Exit value or signal number */
    // other fields reserved for future use
};

The fields ssi_signo, ssi_errno, ssi_pid, ssi_uid, and ssi_status are always filled in.

Other fields are filled in depending on the signal. For example, if the signal was sent by sigqueue(3), then ssi_int and ssi_ptr contain the data sent with the signal.

If the SFD_NONBLOCK flag is not set for the signalfd file descriptor, then a read(2) call will block until at least one signal is available. If SFD_NONBLOCK is set, then a read(2) call will return immediately. If no signals are pending, it returns -1 and sets errno to EAGAIN. Otherwise, it returns the number of bytes read, which will always be equal to the size of a struct signalfd_siginfo.

The signal mask for a signalfd file descriptor can be changed using signalfd() with a valid fd value.

Thread semantics

The semantics of signalfd file descriptors in a multithreaded program mirror the standard semantics for signals. In other words, when a thread reads from a signalfd file descriptor, it will read the signals that are directed to the thread itself and the signals that are directed to the process (i.e., the entire thread group). (A thread will not be able to read signals that are directed to other threads in the process.)

epoll(7) semantics

If a process adds (via epoll_ctl(2)) a signalfd file descriptor to an epoll(7) instance, then epoll_wait(2) returns events only for signals sent to that process. In particular, if the process then uses fork(2) to create a child process, then the child will be able to read(2) signals that are sent to it using the signalfd file descriptor, but epoll_wait(2) will not indicate that the signalfd file descriptor is ready. In this scenario, a possible workaround is that after the fork(2), the child process can close the signalfd file descriptor that it inherited from the parent process and then create another signalfd file descriptor and add it to the epoll instance. Alternatively, the parent and the child could delay creating their (separate) signalfd file descriptors and adding them to the epoll instance until after the call to fork(2).

RETURN VALUE

On success, signalfd() returns a signalfd file descriptor; this is either a new file descriptor (if fd was -1), or fd if fd was a valid signalfd file descriptor. On error, -1 is returned and errno is set to indicate the error.

ERRORS

EBADF
The fd file descriptor is not a valid file descriptor.
EINVAL
fd is not a valid signalfd file descriptor.
EINVAL
flags is invalid; or, in Linux 2.6.26 or earlier, flags is nonzero.
EMFILE
The per-process limit on the number of open file descriptors has been reached.
ENFILE
The system-wide limit on the total number of open files has been reached.
ENODEV
Could not mount (internal) anonymous inode device.
ENOMEM
There was insufficient memory to create a new signalfd file descriptor.

VERSIONS

C library/kernel differences

The underlying Linux system call requires an additional argument, size_t sizemask, which specifies the size of the mask argument. The glibc signalfd() wrapper function does not include this argument, since it provides the required value for the underlying system call.

There are two underlying Linux system calls: signalfd() and the more recent signalfd4(). The former system call does not implement a flags argument. The latter system call implements the flags values described above. Starting with glibc 2.9, the signalfd() wrapper function will use signalfd4() where it is available.

STANDARDS

Linux.

HISTORY

NOTES

A process can create multiple signalfd file descriptors. This makes it possible to accept different signals on different file descriptors. (This may be useful if monitoring the file descriptors using select(2), poll(2), or epoll(7): the arrival of different signals will make different file descriptors ready.) If a signal appears in the mask of more than one of the file descriptors, then occurrences of that signal can be read (once) from any one of the file descriptors.

Attempts to include SIGKILL and SIGSTOP in mask are silently ignored.

The signal mask employed by a signalfd file descriptor can be viewed via the entry for the corresponding file descriptor in the process's /proc/pid/fdinfo directory. See proc(5) for further details.

Limitations

The signalfd mechanism can't be used to receive signals that are synchronously generated, such as the SIGSEGV signal that results from accessing an invalid memory address or the SIGFPE signal that results from an arithmetic error. Such signals can be caught only via signal handler.

As described above, in normal usage one blocks the signals that will be accepted via signalfd(). If spawning a child process to execute a helper program (that does not need the signalfd file descriptor), then, after the call to fork(2), you will normally want to unblock those signals before calling execve(2), so that the helper program can see any signals that it expects to see. Be aware, however, that this won't be possible in the case of a helper program spawned behind the scenes by any library function that the program may call. In such cases, one must fall back to using a traditional signal handler that writes to a file descriptor monitored by select(2), poll(2), or epoll(7).

BUGS

Before Linux 2.6.25, the ssi_ptr and ssi_int fields are not filled in with the data accompanying a signal sent by sigqueue(3).

EXAMPLES

The program below accepts the signals SIGINT and SIGQUIT via a signalfd file descriptor. The program terminates after accepting a SIGQUIT signal. The following shell session demonstrates the use of the program:


$ ./signalfd_demo
^C                   # Control-C generates SIGINT
Got SIGINT
^C
Got SIGINT
^\                    # Control-\ generates SIGQUIT
Got SIGQUIT
$

Program source

#include <err.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/signalfd.h>
#include <sys/types.h>
#include <unistd.h>
int
main(void)
{
    int                      sfd;
    ssize_t                  s;
    sigset_t                 mask;
    struct signalfd_siginfo  fdsi;
    sigemptyset(&mask);
    sigaddset(&mask, SIGINT);
    sigaddset(&mask, SIGQUIT);
    /* Block signals so that they aren't handled
       according to their default dispositions.  */
    if (sigprocmask(SIG_BLOCK, &mask, NULL) == -1)
        err(EXIT_FAILURE, "sigprocmask");
    sfd = signalfd(-1, &mask, 0);
    if (sfd == -1)
        err(EXIT_FAILURE, "signalfd");
    for (;;) {
        s = read(sfd, &fdsi, sizeof(fdsi));
        if (s != sizeof(fdsi))
            err(EXIT_FAILURE, "read");
        if (fdsi.ssi_signo == SIGINT) {
            printf("Got SIGINT\n");
        } else if (fdsi.ssi_signo == SIGQUIT) {
            printf("Got SIGQUIT\n");
            exit(EXIT_SUCCESS);
        } else {
            printf("Read unexpected signal\n");
        }
    }
}
