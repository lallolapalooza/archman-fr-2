SIGACTION(3P) Manuel du programmeur POSIX SIGACTION(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

sigaction — examiner et modifier une action de signal

SYNOPIS

#include <signal.h>
int sigaction(int sig, const struct sigaction *restrict act,
    struct sigaction *restrict oact);

DESCRIPTION

La fonction sigaction() permet au processus appelant d'examiner et/ou de spécifier l'action à associer à un signal spécifique. L'argument sig spécifie le signal ; les valeurs acceptables sont définies dans <signal.h>.

La structure sigaction, utilisée pour décrire une action à entreprendre, est définie dans l'en-tête <signal.h> pour inclure au moins les membres suivants :

Type de membre Nom du membre Description
void(*) (int) sa_handler Pointeur vers une fonction de capture de signal ou l'une des macros SIG_IGN ou SIG_DFL.
sigset_t sa_mask Ensemble supplémentaire de signaux à bloquer pendant l'exécution de la fonction de capture de signal.
int sa_flags Indicateurs spéciaux pour modifier le comportement du signal.
void(*) (int,   siginfo_t *, void *) sa_sigaction Pointeur vers une fonction de capture de signal.

L'espace occupé par sa_handler et sa_sigaction peut se chevaucher, et une application conforme ne doit pas utiliser les deux simultanément.

Si l'argument act n'est pas un pointeur nul, il pointe vers une structure spécifiant l'action à associer au signal spécifié. Si l'argument oact n'est pas un pointeur nul, l'action précédemment associée au signal est stockée à l'emplacement pointé par l'argument oact. Si l'argument act est un pointeur nul, la gestion du signal n'est pas modifiée ; ainsi, l'appel peut être utilisé pour interroger la gestion actuelle d'un signal donné. Les signaux SIGKILL et SIGSTOP ne doivent pas être ajoutés au masque de signaux via ce mécanisme ; cette restriction doit être appliquée par le système sans provoquer d'erreur.

Si l'indicateur SA_SIGINFO (voir ci-dessous) est effacé dans le champ sa_flags de la structure sigaction, le champ sa_handler identifie l'action à associer au signal spécifié. Si l'indicateur SA_SIGINFO est défini dans le champ sa_flags, le champ sa_sigaction spécifie une fonction de capture de signal.

Le champ sa_flags peut être utilisé pour modifier le comportement du signal spécifié.

Les indicateurs suivants, définis dans l'en-tête <signal.h>, peuvent être définis dans sa_flags :

SA_NOCLDSTOP
Ne pas générer SIGCHLD lorsque des processus fils s'arrêtent ou que des processus fils arrêtés reprennent.

Si sig est SIGCHLD et que l'indicateur SA_NOCLDSTOP n'est pas défini dans sa_flags, et que l'implémentation prend en charge le signal SIGCHLD, alors un signal SIGCHLD sera généré pour le processus appelant chaque fois que l'un de ses processus fils s'arrête et un signal SIGCHLD peut être généré pour le processus appelant chaque fois que l'un de ses processus fils arrêtés reprend. Si sig est SIGCHLD et que l'indicateur SA_NOCLDSTOP est défini dans sa_flags, alors l'implémentation ne générera pas de signal SIGCHLD de cette manière.

SA_ONSTACK
Si défini et si une pile de signaux alternative a été déclarée avec sigaltstack(), le signal sera délivré au processus appelant sur cette pile. Sinon, le signal sera délivré sur la pile actuelle.
SA_RESETHAND
Si défini, la disposition du signal sera réinitialisée à SIG_DFL et l'indicateur SA_SIGINFO sera effacé lors de l'entrée dans le gestionnaire de signal.
Note :
SIGILL et SIGTRAP ne peuvent pas être réinitialisés automatiquement lors de leur délivrance ; le système applique silencieusement cette restriction.

Sinon, la disposition du signal ne sera pas modifiée à l'entrée dans le gestionnaire de signal.

De plus, si cet indicateur est défini, sigaction() peut se comporter comme si l'indicateur SA_NODEFER était également défini.

SA_RESTART
Cet indicateur affecte le comportement des fonctions interruptibles ; c'est-à-dire celles qui sont spécifiées pour échouer avec errno défini à [EINTR]. S'il est défini, et qu'une fonction spécifiée comme interruptible est interrompue par ce signal, la fonction sera redémarrée et n'échouera pas avec [EINTR] sauf spécification contraire. Si une fonction interruptible utilisant un délai d'attente est redémarrée, la durée du délai d'attente après le redémarrage est définie à une valeur non spécifiée qui ne dépasse pas la valeur du délai d'attente d'origine. Si l'indicateur n'est pas défini, les fonctions interruptibles interrompues par ce signal échoueront avec errno défini à [EINTR].
SA_SIGINFO
Si effacé et que le signal est capturé, la fonction de capture de signal sera appelée comme suit :
void func(int signo);

où signo est le seul argument de la fonction de capture de signal. Dans ce cas, l'application utilisera le membre sa_handler pour décrire la fonction de capture de signal et l'application ne modifiera pas le membre sa_sigaction.

Si SA_SIGINFO est défini et que le signal est capturé, la fonction de capture de signal sera appelée comme suit :

void func(int signo, siginfo_t *info, void *context);

où deux arguments supplémentaires sont passés à la fonction de capture de signal. Le deuxième argument pointera vers un objet de type siginfo_t expliquant la raison pour laquelle le signal a été généré ; le troisième argument peut être converti en pointeur vers un objet de type ucontext_t pour faire référence au contexte du thread récepteur qui a été interrompu lorsque le signal a été délivré. Dans ce cas, l'application utilisera le membre sa_sigaction pour décrire la fonction de capture de signal et l'application ne modifiera pas le membre sa_handler.

Le membre si_signo contient le numéro du signal généré par le système.

Le membre si_errno peut contenir des informations d'erreur supplémentaires spécifiques à l'implémentation ; si non nul, il contient un numéro d'erreur identifiant la condition qui a causé la génération du signal.

Le membre si_code contient un code identifiant la cause du signal, tel que décrit dans la Section 2.4.3, Actions de signal.

SA_NOCLDWAIT
Si sig n'est pas égal à SIGCHLD, le comportement est indéterminé. Sinon, le comportement de l'indicateur SA_NOCLDWAIT est tel que spécifié dans Conséquences de la terminaison d'un processus.
SA_NODEFER
Si défini et que sig est capturé, sig ne sera pas ajouté au masque de signaux du thread à l'entrée du gestionnaire de signal, sauf s'il est inclus dans sa_mask. Sinon, sig sera toujours ajouté au masque de signaux du thread à l'entrée du gestionnaire de signal.

Lorsqu'un signal est capturé par une fonction de capture de signal installée par sigaction(), un nouveau masque de signaux est calculé et installé pour la durée de la fonction de capture de signal (ou jusqu'à ce qu'un appel à sigprocmask() ou sigsuspend() soit effectué). Ce masque est formé en prenant l'union du masque de signaux actuel et de la valeur de sa_mask pour le signal délivré, et en débloquant

ss SA_NODEFER ou SA_RESETHAND est défini, y compris le signal en cours de délivrance. Si le gestionnaire de signaux de l'utilisateur retourne normalement, le masque de signaux d'origine est restauré.

Une fois qu'une action est installée pour un signal spécifique, elle reste installée jusqu'à ce qu'une autre action soit explicitement demandée (par un autre appel à sigaction()), jusqu'à ce que le drapeau SA_RESETHAND provoque la réinitialisation du gestionnaire, ou jusqu'à ce qu'une des fonctions exec soit appelée.

Si l'action précédente pour sig avait été établie par signal(), les valeurs des champs retournés dans la structure pointée par oact ne sont pas spécifiées, et en particulier oact->sa_handler n'est pas nécessairement la même valeur que celle passée à signal(). Cependant, si un pointeur vers la même structure ou une copie de celle-ci est passé à un appel ultérieur à sigaction() via l'argument act, le traitement du signal sera comme si l'appel initial à signal() était répété.

Si sigaction() échoue, aucun nouveau gestionnaire de signaux n'est installé.

Il n'est pas spécifié si une tentative de définition de l'action pour un signal qui ne peut être intercepté ou ignoré à SIG_DFL est ignorée ou provoque une erreur retournée avec errno défini à [EINVAL].

Si SA_SIGINFO n'est pas défini dans sa_flags, alors la disposition des occurrences ultérieures de sig lorsqu'il est déjà en attente est définie par l'implémentation ; la fonction d'interception de signal sera appelée avec un seul argument. Si SA_SIGINFO est défini dans sa_flags, alors les occurrences ultérieures de sig générées par sigqueue() ou résultant de toute fonction générant des signaux qui prend en charge la spécification d'une valeur définie par l'application (lorsque sig est déjà en attente) seront mises en file d'attente dans l'ordre FIFO jusqu'à leur délivrance ou acceptation ; la fonction d'interception de signal sera appelée avec trois arguments. La valeur spécifiée par l'application est passée à la fonction d'interception de signal en tant que membre si_value de la structure siginfo_t.

Le résultat de l'utilisation concurrente de sigaction() et d'une fonction sigwait() au sein d'un processus sur le même signal n'est pas spécifié.

VALEUR DE RETOUR

En cas de succès, sigaction() retourne 0 ; sinon, -1 est retourné, errno est défini pour indiquer l'erreur, et aucune nouvelle fonction d'interception de signaux n'est installée.

ERREURS

La fonction sigaction() échoue si :

EINVAL
L'argument sig n'est pas un numéro de signal valide ou une tentative est faite pour intercepter un signal qui ne peut être intercepté ou ignorer un signal qui ne peut être ignoré.

La fonction sigaction() peut échouer si :

EINVAL
Une tentative a été faite pour définir l'action à SIG_DFL pour un signal qui ne peut être intercepté ou ignoré (ou les deux).

De plus, sur les systèmes qui ne prennent pas en charge l'option XSI, la fonction sigaction() peut échouer si le drapeau SA_SIGINFO est défini dans le champ sa_flags de la structure sigaction pour un signal en dehors de la plage SIGRTMIN à SIGRTMAX.

Les sections suivantes sont informatives.

EXEMPLES

Établir un Gestionnaire de Signaux

L'exemple suivant démontre l'utilisation de sigaction() pour établir un gestionnaire pour le signal SIGINT.

#include <signal.h>
static void handler(int signum)
{
    /* Take appropriate actions for signal delivery */
}
int main()
{
    struct sigaction sa;
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART; /* Restart functions if
                                 interrupted by handler */
    if (sigaction(SIGINT, &sa, NULL) == -1)
        /* Handle error */;
    /* Further code */
}

USAGE APPLICATIF

La fonction sigaction() remplace la fonction signal() et doit être utilisée de préférence. En particulier, sigaction() et signal() ne doivent pas être utilisés dans le même processus pour contrôler le même signal. Le comportement des fonctions sûres en cas d'interruption par signal asynchrone, tel que défini dans leurs sections DESCRIPTION respectives, est tel que spécifié par ce volume de POSIX.1‐2017, indépendamment de l'invocation depuis une fonction d'interception de signal. C'est le seul sens voulu de l'affirmation selon laquelle les fonctions sûres en cas d'interruption par signal asynchrone peuvent être utilisées dans les fonctions d'interception de signal sans restrictions. Les applications doivent toujours tenir compte de tous les effets de telles fonctions sur les structures de données, les fichiers et l'état du processus. En particulier, les développeurs d'applications doivent tenir compte des restrictions sur les interactions lors de l'interruption de sleep() et des interactions entre plusieurs gestionnaires pour une description de fichier. Le fait qu'une fonction spécifique soit répertoriée comme sûre en cas d'interruption par signal asynchrone ne signifie pas nécessairement que l'invocation de cette fonction depuis une fonction d'interception de signal est recommandée.

Afin de prévenir les erreurs résultant de l'interruption d'appels de fonctions non sûres en cas d'interruption par signal asynchrone, les applications doivent protéger les appels à ces fonctions soit en bloquant les signaux appropriés, soit en utilisant un sémaphore programmatique (voir semget(), sem_init(), sem_open(), etc.). Notez en particulier que même les fonctions « sûres » peuvent modifier errno ; la fonction d'interception de signal, si elle ne s'exécute pas comme un fil d'exécution indépendant, doit sauvegarder et restaurer sa valeur afin d'éviter la possibilité que la délivrance d'un signal entre un retour d'erreur d'une fonction qui définit errno et l'examen ultérieur de errno puisse entraîner la modification de la valeur de errno par la fonction d'interception de signal. Naturellement, les mêmes principes s'appliquent à la sûreté en cas d'interruption par signal asynchrone des routines d'application et à l'accès asynchrone aux données. Notez que longjmp() et siglongjmp() ne font pas partie de la liste des fonctions sûres en cas d'interruption par signal asynchrone. En effet, le code s'exécutant après longjmp() et siglongjmp() peut appeler n'importe quelle fonction non sûre avec le même danger que l'appel de ces fonctions non sûres directement depuis le gestionnaire de signaux. Les applications qui utilisent longjmp() et siglongjmp() depuis des gestionnaires de signaux nécessitent une protection rigoureuse pour être portables. Bon nombre des autres fonctions exclues de la liste sont traditionnellement implémentées à l'aide des fonctions malloc() ou free() ou de la bibliothèque d'E/S standard, qui utilisent toutes deux traditionnellement des structures de données d'une manière non sûre en cas d'interruption par signal asynchrone. Étant donné que toute combinaison de fonctions différentes utilisant une structure de données commune peut causer des problèmes de sûreté en cas d'interruption par signal asynchrone, ce volume de POSIX.1‐2017 ne définit pas le comportement lorsqu'une fonction non sûre est appelée dans un gestionnaire de signaux qui interrompt une fonction non sûre.

En général, le signal est exécuté sur la pile qui était effective avant la délivrance du signal. Une pile alternative peut être spécifiée pour recevoir un sous-ensemble des signaux interceptés.

Lorsque le gestionnaire de signaux retourne, le thread receveur reprend l'exécution au point où il a été interrompu, sauf si le gestionnaire de signaux prend d'autres dispositions. Si longjmp() ou _longjmp() est utilisé pour quitter le gestionnaire de signaux, le masque de signaux doit être explicitement restauré.

Ce volume de POSIX.1‐2017 définit le troisième argument d'une fonction de gestion de signaux lorsque SA_SIGINFO est défini comme un void * au lieu d'un ucontext_t *, mais sans exiger de vérification de type. Les nouvelles applications doivent explicitement caster le troisième argument de la fonction de gestion de signaux en ucontext_t *.

La fonction de gestion de signaux à quatre arguments optionnelle BSD n'est pas prise en charge par ce volume de POSIX.1‐2017. La déclaration BSD serait :

void handler(int sig, int code, struct sigcontext *scp,
    char *addr);

où sig est le numéro de signal, code est des informations supplémentaires sur certains signaux, scp est un pointeur vers la structure sigcontext, et addr est des informations d'adresse supplémentaires. Beaucoup des mêmes informations sont disponibles dans les objets pointés par le deuxième argument du gestionnaire de signaux spécifié lorsque SA_SIGINFO est défini.

Comme la fonction sigaction() est autorisée mais pas obligée de définir SA_NODEFER lorsque l'application définit le drapeau SA_RESETHAND, les applications qui dépendent de la fonctionnalité SA_RESETHAND pour le nouveau gestionnaire de signaux installé doivent toujours explicitement définir SA_NODEFER lorsqu'elles définissent SA_RESETHAND afin d'être portables.

Voir également la justification pour la génération et la délivrance de signaux temps réel dans le volume Rationale (Informatif) de POSIX.1‐2017, Section B.2.4.2, Signal Generation and Delivery.

RATIONALE

Bien que ce volume de POSIX.1‐2017 exige que les signaux qui ne peuvent être ignorés ne soient pas ajoutés au masque de signaux lors de l'entrée dans une fonction d'interception de signaux, il n'y a aucune exigence explicite que les appels ultérieurs à sigaction() reflètent cela dans les informations retournées dans l'argument oact. En d'autres termes, si SIGKILL est inclus dans le champ sa_mask de act, il n'est pas spécifié si un appel ultérieur à sigaction() retourne avec SIGKILL inclus dans le champ sa_mask de oact.

Le drapeau SA_NOCLDSTOP, lorsqu'il est fourni dans le paramètre act->sa_flags, permet de surcharger SIGCHLD avec la sémantique System V selon laquelle chaque signal SIGCLD indique un enfant terminé unique. La plupart des applications conformes qui interceptent SIGCHLD sont censées installer des fonctions d'interception de signaux qui appellent de manière répétée la fonction waitpid() avec le drapeau WNOHANG défini, agissant sur chaque enfant pour lequel un statut est retourné, jusqu'à ce que waitpid() retourne zéro. Si les enfants arrêtés ne sont pas d'intérêt, l'utilisation du drapeau SA_NOCLDSTOP peut éviter la surcharge liée à l'invocation de la routine de signal lorsqu'ils s'arrêtent.

Certaines implémentations historiques définissent également d'autres mécanismes d'arrêt de processus, tels que la fonction ptrace(). Ces implémentations ne génèrent généralement pas de signal SIGCHLD lorsque les processus s'arrêtent en raison de ce mécanisme ; cependant, cela dépasse la portée de ce volume de POSIX.1‐2017.

This page is a manual page for the POSIX Programmer's Interface (POSIX.1-2017).

NAME

sigaction, sigprocmask, sigpending, sigsuspend, sigsetops — examine and change signal disposition

SYNOPSIS

#include <signal.h>

int sigaction(int sig, const struct sigaction *restrict act,
       struct sigaction *restrict oact);
int sigprocmask(int how, const sigset_t *restrict set,
       sigset_t *restrict oset);
int sigpending(sigset_t *set);
int sigsuspend(const sigset_t *mask);
int sigsetops(int cmd, int sig, sigset_t *set);

DESCRIPTION

The POSIX.1‐2017 standard defines the following functions for manipulating signal masks and signal actions:

  • sigaction() examines and changes the action taken on a specific signal.
  • sigprocmask() examines and changes the signal mask of the calling thread.
  • sigpending() examines the set of signals that are pending for delivery to the calling thread.
  • sigsuspend() replaces the signal mask of the calling thread with a specified mask and then suspends the thread until a signal is delivered.
  • sigsetops() provides a way to manipulate signal sets (add, remove, or check for membership of signals).

The structure sigaction is defined in <signal.h> and contains at least the following members:

       void (*sa_handler)(int);
       sigset_t sa_mask;
       int sa_flags;
       void (*sa_sigaction)(int, siginfo_t *, void *);

The sa_handler field specifies the action to be taken upon delivery of the signal. It can be set to SIG_DFL (default action), SIG_IGN (ignore the signal), or a pointer to a signal-catching function. The sa_mask field specifies a set of signals to be blocked during the execution of the signal-catching function. The sa_flags field specifies various options that modify the behavior of the signal handling. The sa_sigaction field can be used instead of sa_handler when the SA_SIGINFO flag is set in sa_flags, providing more detailed information to the signal-catching function.

The functions sigprocmask(), sigpending(), and sigsuspend() operate on signal masks, which are sets of signals. The functions sigemptyset(), sigfillset(), sigaddset(), sigdelset(), and sigismember() are used to manipulate these sets.

RETURN VALUE

These functions return 0 on success, or -1 if an error occurs.

ERRORS

These functions can return the following errors:

  • [EINVAL]: An invalid signal number or argument was provided.
  • [ENOTSUP]: The requested operation is not supported for the specified signal (e.g., trying to change the disposition of SIGKILL or SIGSTOP).

EXAMPLES

The following example demonstrates how to use sigaction() to set up a signal handler for SIGINT:

#include <signal.h>
#include <stdio.h>
#include <unistd.h>

void handler(int sig) {
    printf("Received signal %d\n", sig);
}

int main() {
    struct sigaction sa;
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;

    if (sigaction(SIGINT, &sa, NULL) == -1) {
        perror("sigaction");
        return 1;
    }

    printf("Waiting for SIGINT...\n");
    pause(); // Wait for a signal

    return 0;
}

APPLICATION USAGE

Applications should use sigaction() for setting signal handlers, as it is more portable and provides more features than the older signal() function. When using sigaction(), it is recommended to avoid using both signal() and sigaction() for the same signal within the same process, as this can lead to undefined behavior.

RATIONALE

The sigaction() function provides a more robust and feature-rich interface for signal handling compared to the older signal() function. It allows for more precise control over signal dispositions, including the ability to block additional signals during the execution of a signal handler and to receive detailed information about the signal. The POSIX.1‐2017 standard requires that sigaction() properly handles signals set up by the ISO C standard signal() function, but the reverse is not guaranteed. Therefore, it is recommended to use sigaction() exclusively for signal handling in new applications.

The POSIX Realtime Extension further enhances sigaction() by allowing applications to request that extra parameters, including an application-defined signal value, be passed to the signal-catching function. This is achieved through an additional flag in the sa_flags field.

The System V signal() and BSD sigvec() functions may return [EINVAL] if an attempt is made to change the disposition of signals that cannot be caught or ignored (that is, SIGKILL or SIGSTOP). The behavior of sigaction() in these cases may vary from these older functions.

It was intended that the signal() function should be implementable as a library routine using sigaction().
