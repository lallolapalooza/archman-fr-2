SIGNAL(3P) Manuel du programmeur POSIX SIGNAL(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation de cette interface sous Linux peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

signal — gestion des signaux

SYNTAXE

#include <signal.h>
void (*signal(int sig, void (*func)(int)))(int);

DESCRIPTION

La fonctionnalité décrite sur cette page de référence est alignée sur la norme ISO C. Tout conflit entre les exigences décrites ici et la norme ISO C est involontaire. Ce volume de POSIX.1‐2017 renvoie à la norme ISO C.

La fonction signal() choisit l'une des trois manières dont la réception du numéro de signal sig doit être traitée par la suite. Si la valeur de func est SIG_DFL, le traitement par défaut pour ce signal sera effectué. Si la valeur de func est SIG_IGN, le signal sera ignoré. Sinon, l'application doit s'assurer que func pointe vers une fonction à appeler lorsque ce signal se produit. Une invocation d'une telle fonction à cause d'un signal, ou (récursivement) de toute autre fonction appelée par cette invocation (autre que les fonctions de la bibliothèque standard), est appelée un « gestionnaire de signaux ».

Lorsqu'un signal se produit, et que func pointe vers une fonction, il est défini par l'implémentation que l'équivalent d'un :

signal(sig, SIG_DFL);

est exécuté ou que l'implémentation empêche un ensemble de signaux définis par l'implémentation (incluant au moins sig) de se produire jusqu'à ce que le traitement actuel du signal soit terminé. (Si la valeur de sig est SIGILL, l'implémentation peut alternativement définir qu'aucune action n'est prise.) Ensuite, l'équivalent de :

(*func)(sig);

est exécuté. Si et quand la fonction retourne, si la valeur de sig était SIGFPE, SIGILL, SIGSEGV ou toute autre valeur définie par l'implémentation correspondant à une exception de calcul, le comportement est indéfini. Sinon, le programme reprendra son exécution au point où il a été interrompu. La norme ISO C impose une restriction aux applications concernant l'utilisation de raise() à partir des gestionnaires de signaux. Cette restriction ne s'applique pas aux applications POSIX, car POSIX.1‐2008 exige que raise() soit asynchrone et sûr (voir Section 2.4.3, Actions de Signal).

Si le processus est multithreadé, ou si le processus est monothreadé et qu'un gestionnaire de signaux est exécuté autrement qu'à la suite de :

*
l'appel par le processus de abort(), raise(), kill(), pthread_kill(), ou sigqueue() pour générer un signal qui n'est pas bloqué
*
un signal en attente qui est débloqué et délivré avant le retour de l'appel qui l'a débloqué

le comportement est indéfini si le gestionnaire de signaux référence un objet autre que errno avec une durée de vie statique, sauf par l'assignation d'une valeur à un objet déclaré comme volatile sig_atomic_t, ou si le gestionnaire de signaux appelle une fonction définie dans cette norme autre qu'une des fonctions listées dans Section 2.4, Concepts de Signal.

Au démarrage du programme, l'équivalent de :

signal(sig, SIG_IGN);

est exécuté pour certains signaux, et l'équivalent de :

signal(sig, SIG_DFL);

est exécuté pour tous les autres signaux (voir exec).

La fonction signal() ne doit pas modifier la valeur de errno en cas de succès.

VALEUR RENVOYÉE

Si la requête peut être honorée, signal() renvoie la valeur de func pour l'appel le plus récent à signal() pour le signal spécifié sig. Sinon, SIG_ERR est renvoyé et une valeur positive est stockée dans errno.

ERREURS

La fonction signal() échouera si :

EINVAL
L'argument sig n'est pas un numéro de signal valide ou une tentative est faite pour attraper un signal qui ne peut pas être attrapé ou ignorer un signal qui ne peut pas être ignoré.

La fonction signal() peut échouer si :

EINVAL
Une tentative a été faite pour définir l'action sur SIG_DFL pour un signal qui ne peut pas être attrapé ou ignoré (ou les deux).

UTILISATION PAR L'APPLICATION

La fonction sigaction() fournit un mécanisme plus complet et fiable pour contrôler les signaux ; les nouvelles applications devraient utiliser sigaction() plutôt que signal().
