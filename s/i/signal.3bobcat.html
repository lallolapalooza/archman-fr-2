FBB::Signal(3bobcat) gestionnaire de signal FBB::Signal(3bobcat)

NOM

FBB::Signal - Gestionnaire de signal

SYNOPSIS

#include <bobcat/signal>
Option de liaison : -lbobcat

DESCRIPTION

Les signaux ont l'inconvénient bien connu d'arriver sans contexte. Par exemple, supposons qu'un programme exécute une boucle de contrôle de flux comme celle-ci :

void Class::run()
{
    while (d_continue)
        handleTasks();
    cleanup();
}

Si le programme doit reconnaître un signal de terminaison, le gestionnaire de signal typique ressemble à ceci :

void signalHandler(int signal)
{
    // effectuer les actions requises
}

Étant donné que le signalHandler est appelé de manière asynchrone, aucun contexte n'est disponible, et la manière habituelle de communiquer entre les objets et les gestionnaires de signaux passe par des variables statiques, comme ceci :

// déclaré comme booléen statique s_continue;
bool Class::s_continue = true;
void Class::run()
{
    while (s_continue)
        handleTasks();
    cleanup();
}
// déclaré comme void signalHander(int signal) statique;
void Class::signalHandler(int signal)
{
    s_continue = false;
}

La classe Signal permet au gestionnaire de signaux d'opérer dans le contexte d'une classe. L'avantage est que les membres de données statiques ne sont plus requis et que le signal peut être utilisé pour contrôler les membres de données d'objets individuels.

Le signal est maintenant géré par un objet, dont la classe doit définir un membre

    void signalHandler(size_t signum) override;
et cette fonction est responsable de la gestion du signal reçu. Puisqu'il s'agit d'une fonction membre, elle peut affecter les variables locales de son objet et appeler les fonctions membres de son objet. Les membres de données statiques ne sont plus requis (voir ci-dessous pour un exemple).

Notez que, comme le signal peut arriver à des moments imprévisibles, les membres de données qui peuvent être modifiés par signalHandler doivent être déclarés en utilisant le modificateur volatile. De plus, les données qui peuvent être modifiées par le membre signalHandler et par d'autres membres de classe doivent être protégées par des mutex (voir la classe std::mutex de C++-11 ou pthread_mutex_lock(3posix)).

ESPACE DE NOMMAGE

FBB
Tous les constructeurs, membres, opérateurs et manipulateurs mentionnés dans cette page de manuel sont définis dans l'espace de noms FBB.

HERITE DE

Signal n'est pas dérivé d'autres classes, mais les classes pour lesquelles les signaux doivent être gérés par Signal doivent elles-mêmes être publiquement dérivées de la classe FBB::SignalHandler et doivent implémenter un membre

    void signalHandler(size_t signum) override;

gérant le signal reçu.

CONSTRUCTEURS ET OPERATEURS SURCHARGES

Signal est défini comme un singleton, et n'offre pas de constructeurs publics ou protégés, ni d'opérateurs surchargés.

FONCTION MEMBRE STATIQUE

o
static Signal &instance():
Ce membre statique peut être utilisé pour accéder à une référence à l'unique objet Signal du programme.

FONCTIONS MEMBRES

Toutes les fonctions membres de Signal ne peuvent être appelées qu'à travers une référence à l'objet Signal du programme, retournant une référence à l'unique objet Signal du programme :

o
void add(size_t signum, SignalHandler &object):
SignalHandler object est activé à l'arrivée du signal signum. Si plusieurs objets SignalHandler doivent être appelés, plusieurs appels Signal::add peuvent être fournis, et les différents membres SignalHandler::signalHandler sont appelés dans le même ordre que leurs appels respectifs Signal::add. Si l'un des membres signalHandler précédents termine le programme, les membres signalHandler ultérieurs ne sont plus activés. Si Signal::add est appelé par, par exemple, le constructeur d'un objet, son destructeur doit appeler Signal::remove pour empêcher que le gestionnaire de signal de l'objet ne soit appelé après sa destruction.
o
void remove(size_t signum, SignalHandler &object):
L'objet SignalHandler pour le signal signum est retiré de l'objet Signal. Il incombe à object de se désenregistrer de Signal juste avant que object ne sorte de sa portée. Les objets ne peuvent se désenregistrer que s'ils se sont précédemment enregistrés en utilisant add.
o
void ignore(size_t signum):
Tout objet SignalHandler précédemment installé n'est plus activé à l'arrivée du signal signum. De plus, si possible, le signal signum est complètement ignoré (certains signaux ne peuvent être interceptés, bloqués ou ignorés, comme SIGKILL et SIGSTOP (voir signal(7))).
o
void reset(size_t signum):
Tout objet SignalHandler précédemment installé n'est plus activé à l'arrivée du signal signum. De plus, l'action par défaut que le programme effectue à l'arrivée du signal signum est réinstallée (voir signal(7)).

Si la valeur signum passée aux membres de Signal n'est pas une valeur de signal définie, une exception FBB::Exception est levée.

EXEMPLE

#include <sys/types.h>
#include <unistd.h>
#include <iostream>
#include "../signal"
class SignalDemo: public FBB::SignalHandler
{
    volatile size_t d_signal;
    volatile bool d_continue;
    pid_t d_pid;
    public:
        SignalDemo();
        void run();
    private:
        void signalHandler(size_t signum) override;
};
using namespace std;
using namespace FBB;
SignalDemo::SignalDemo()
:
    d_signal(0),
    d_continue(true),
    d_pid(getpid())
{}
void SignalDemo::run()
{
    while (d_continue)
    {
        cout << "Envoyez un SIGINT (2) ou SIGTERM (15) ... au processus " <<
                    d_pid << endl;
        sleep(1);
    }
    cout << "Fin de `run’ après réception du signal " << d_signal << endl;
}
void SignalDemo::signalHandler(size_t signal)
{
    if (signal == SIGINT)
        cout << "Le processus " << d_pid << " a reçu SIGINT" << endl;
    else if (signal == SIGTERM)
    {
        cout << "Le processus " << d_pid << " a reçu SIGTERM" << endl;
        d_signal = SIGTERM;
        d_continue = false;
    }
}
int main()
{
    SignalDemo signalDemo;
    Signal::instance().add(SIGINT, signalDemo);
    Signal::instance().add(SIGTERM, signalDemo);
    signalDemo.run();
}
