Signature(access) Signature(access)
La bibliothèque go.podman.io/image/v5 supporte les signatures implémentées comme des blobs “attachés” à une image. Certains transports d'images (formats de stockage locaux et protocoles distants) implémentent ces signatures nativement ou trivialement ; pour d'autres, les extensions de protocole décrites ci-dessous sont nécessaires.

Registres docker/distribution — Stockage séparé

Usage

Tout registre docker/distribution existant, qu'il supporte ou non nativement les signatures, peut être augmenté avec un stockage de signatures séparé en configurant une URL de stockage de signatures dans ⟨containers-registries.d.md⟩. registries.d peut être configuré pour utiliser une URL de stockage pour un serveur docker/distribution entier, ou aussi des URL séparées pour des espaces de noms plus petits ou des dépôts individuels au sein du serveur (ce qui, par exemple, permet aux auteurs d'images de gérer leur propre stockage de signatures tout en publiant les images sur le serveur public docker.io).

L'URL de stockage des signatures définit la racine d'une hiérarchie de chemins. Il peut s'agir d'une URL file:///…, pointant vers une structure de répertoire locale, ou d'une URL http/https, pointant vers un serveur distant. Le stockage de signatures file:/// peut être lu et écrit, tandis que http/https ne supporte que la lecture.

La même hiérarchie de chemins est utilisée dans les deux cas, de sorte que le serveur HTTP/HTTPS peut être un simple serveur web statique servant une structure de répertoires créée en écrivant dans un stockage de signatures file:///. (Cela n'empêche bien sûr pas d'autres implémentations de serveurs, par exemple un serveur HTTP lisant les signatures à partir d'une base de données.)

Le flux de travail habituel pour produire et distribuer des images en utilisant le mécanisme de stockage séparé consiste à configurer le dépôt dans registries.d avec une URL lookaside-staging pointant vers une zone de staging privée file:///, et une URL lookaside pointant vers un serveur web public. Pour publier une image, l'auteur de l'image signerait l'image si nécessaire (par exemple en utilisant skopeo copy), puis copierait la structure de répertoires créée à partir de la zone de staging file:/// vers un sous-répertoire de la racine web du serveur web public afin qu'elle soit accessible via l'URL publique lookaside. L'auteur indiquerait aux consommateurs de l'image de configurer une URL lookaside pointant vers le serveur web public, ou fournirait un fichier de configuration registries.d pour cela.

Structure des chemins

Étant donné une URL de stockage de signatures de base base configurée dans registries.d comme mentionné ci-dessus, et une image conteneur stockée dans un registre docker/distribution en utilisant le nom complètement développé hostname/namespaces/name{@digest,:tag} (par exemple, pour docker.io/library/busybox:latest, namespaces est library, même si l'utilisateur fait référence à l'image en utilisant la syntaxe plus courte comme busybox:latest), les signatures sont accessibles en utilisant des URL de la forme :

base/namespaces/name@digest-algo=digest-value/signature-index

où digest-algo:digest-value est une empreinte de manifeste utilisable pour référencer le manifeste d'image pertinent (c'est-à-dire que même si l'utilisateur a référencé l'image en utilisant une étiquette, le stockage des signatures est toujours désambiguïsé en utilisant des références d'empreinte). Notez que dans les URL utilisées pour les signatures, digest-algo et digest-value sont séparés par le caractère =, et non par : comme lors de l'accès au manifeste via l'API docker/distribution.

Au sein de l'URL, index est un entier décimal (sous forme canonique), commençant par 1. Les signatures sont stockées aux URL avec des valeurs d'index successives ; pour toutes les lire, commencez par index=1, et continuez à lire les signatures en augmentant index tant que les signatures avec ces valeurs d'index existent. De même, pour ajouter une signature supplémentaire à une image, trouvez le premier index qui n'existe pas, puis stockez la nouvelle signature en utilisant cette valeur d'index.

Il n'y a aucun moyen de lister les signatures existantes autre qu'en itérant sur les valeurs d'index successives, et aucun moyen de télécharger toutes les signatures en une seule fois.

Exemples

Pour une image docker/distribution disponible sous busybox@sha256:817a12c32a39bbe394944ba49de563e085f1d3c5266eb8e9723256bc4448680e (ou sous busybox:latest si l'étiquette latest pointe vers un manifeste avec la même empreinte), et avec une configuration registries.d spécifiant une URL lookaside https://example.com/lookaside pour la même image, les URL suivantes seraient accédées pour télécharger toutes les signatures :

- https://example.com/lookaside/library/busybox@sha256=817a12c32a39bbe394944ba49de563e085f1d3c5266eb8e9723256bc4448680e/signature-1

- https://example.com/lookaside/library/busybox@sha256=817a12c32a39bbe394944ba49de563e085f1d3c5266eb8e9723256bc4448680e/signature-2

- …

Pour une image docker/distribution disponible sous example.com/ns1/ns2/ns3/repo@somedigest:digestvalue et la même URL lookaside, les signatures seraient disponibles à :

https://example.com/lookaside/ns1/ns2/ns3/repo@somedigest=digestvalue/signature-1

et ainsi de suite.

Extension de l'API docker/distribution (OpenShift)

Depuis https://github.com/openshift/origin/pull/12504/, le registre embarqué d'OpenShift fournit également une extension de l'API docker/distribution qui permet un accès plus simple aux signatures, en utilisant uniquement le point d'accès de l'API docker/distribution.

Cette API n'est pas intrinsèquement spécifique à OpenShift (par exemple, le client n'a pas besoin de connaître le point d'accès de l'API OpenShift, et les identifiants suffisants pour accéder au serveur de l'API docker/distribution suffisent pour accéder également aux signatures), et c'est la manière préférée d'implémenter le stockage des signatures dans les registres.

Voir https://github.com/openshift/openshift-docs/pull/3556 pour la documentation amont de l'API.

Pour lire la signature, tout utilisateur ayant accès à une image peut utiliser le chemin /extensions/v2/…/signatures/… pour lire un tableau de signatures. Utilisez uniquement les objets de signature dont la version est égale à 2, le type est égal à atomic, et lisez la signature à partir du content ; ignorez les autres champs de l'objet de signature.

Pour ajouter une signature unique, effectuez un PUT d'un nouvel objet avec la version définie sur 2, le type défini sur atomic, et le content défini sur la signature. Définissez également le name sur un nom unique de forme digest@per-image-name, où digest est une empreinte de manifeste d'image (également utilisée dans l'URL), et per-image-name est un identifiant unique.

Pour ajouter plusieurs signatures, ajoutez-les une par une. Cette API ne permet pas de supprimer des signatures.

Notez que comme les signatures sont stockées dans les objets d'image globaux du cluster, c'est-à-dire que différents espaces de noms ne peuvent pas associer différents ensembles de signatures à la même image, la mise à jour des signatures nécessite un accès global au cluster à la ressource imagesignatures (disponible par défaut pour le rôle system:image-signer).

Registres embarqués OpenShift

Le registre embarqué d'OpenShift implémente l'API docker/distribution ordinaire, et il expose également les images via l'API REST d'OpenShift (accessible via les serveurs "API master").

5 | PROTOCOLS

NAME

signature-protocols - Signing and verification of container images

SYNOPSIS

The Image and ImageStreamImage resources have a Signatures array. The ImageSignature object contains a Type field and a Content field. The Type is a string which represents the signature type. The Content is a string representing the signature.

The ImageSignature object includes a Content field which can be used to store signature content. The Type field identifies the type of the signature.

The atomic signature type is used to store signatures generated by Atomic Host or by the atomic command.

To view the signature, use the ImageStreamImage resource. For example, to get the signature for a specific image from a specific registry, use the following command:

    $ oc get imagestreamimages <image-name>:<tag> -n <namespace> -o jsonpath='{.status.import.imagestatus.signatures}'

This command retrieves the signatures associated with an image stream tag. The signatures are stored in the status.import.imagestatus.signatures field.

To add or remove signatures, use the ImageSignature resource. For example, to add a signature to an image:

    $ oc create -f - <<EOF
    apiVersion: "atomic.openshift.io/v1"
    kind: ImageSignature
    metadata:
      name: <digest>@<per-image-name>
    spec:
      type: "atomic"
      content: <signature-content>
    EOF

This command creates a new ImageSignature resource. The metadata.name field must be in the format digest@per-image-name. The spec.type field must be set to atomic, and the spec.content field should contain the signature content.

To remove a signature, delete the corresponding ImageSignature resource:

    $ oc delete imagesignature <digest>@<per-image-name> -n <namespace>

Note that deleting a signature removes it for all namespaces that contain the same image. This is because signatures are stored with the cluster-wide image object, not within individual namespaces.

Updating signatures requires cluster-wide access to the ImageSignature resource, which is typically granted to the system:image-signer role.

DESCRIPTION

This document describes the protocol for signing and verifying container images using OpenShift. It covers the use of the ImageStreamImage and ImageSignature resources for managing image signatures.

The signature protocol allows users to verify the integrity and authenticity of container images. Signatures are stored as part of the image metadata within OpenShift.

Key components of the signature protocol include:

  • ImageStreamImage resource: Used to retrieve signatures associated with an image. It allows users to inspect the signatures applied to an image.
  • ImageSignature resource: Used to manage (add or remove) signatures. Signatures are associated with a specific image digest and an optional per-image name.
  • Signature Type (atomic): Specifies the type of signature. The atomic type is used for signatures generated by Atomic Host or the atomic command.
  • Signature Content: The actual signature data, stored as a string.

When retrieving signatures using ImageStreamImage, users should focus on signatures of Type atomic and read the signature from the Content field. Other fields within the ImageSignature object should be ignored for signature verification purposes.

Adding or removing signatures requires using the cluster-wide (non-namespaced) ImageSignature resource. The signature name must follow the format digest@per-image-name, where digest is the image manifest digest and per-image-name is a unique identifier.

It is important to note that signatures are stored at the cluster level. This means that a signature applied to an image is available globally, regardless of the namespace. Consequently, updating signatures requires cluster-wide permissions (typically granted to the system:image-signer role), and deleting signatures is strongly discouraged as it affects all namespaces containing that image.

For detailed information on interacting with the OpenShift API, refer to the OpenShift API documentation. Specifically, understanding the URLs for both the docker/distribution and the OpenShift API master endpoints is crucial.

To read the signature, any user with access to an image can use the imagestreamimages namespaced resource to read an Image object and its Signatures array. Use only the ImageSignature objects which have Type equal to atomic, and read the signature from Content; ignore the other fields of the ImageSignature object.

To add or remove signatures, use the cluster-wide (non-namespaced) imagesignatures resource, with Type set to atomic and Content set to the signature. Signature names must have the form digest@per-image-name, where digest is an image manifest digest (OpenShift “image name”), and per-image-name is any unique identifier.

Note that because signatures are stored within the cluster-wide image objects, i.e. different namespaces can not associate different sets of signatures to the same image, updating signatures requires a cluster-wide access to the imagesignatures resource (by default available to the system:image-signer role), and deleting signatures is strongly discouraged (it deletes the signature from all namespaces which contain the same image).
