DESCRIPTION

La bibliothèque sndio permet aux processus utilisateurs d'accéder au matériel audio(4) et au serveur audio sndiod(8) de manière uniforme.

Ouverture et fermeture d'un périphérique audio

L'application doit d'abord appeler la fonction sio_open() pour obtenir un descripteur du périphérique ; celui-ci sera ensuite passé comme argument hdl à la plupart des autres fonctions. Le paramètre name donne la chaîne de périphérique discutée dans sndio(7). Dans la plupart des cas, il devrait être défini à SIO_DEVANY pour permettre à l'utilisateur de le sélectionner en utilisant la variable d'environnement AUDIODEVICE.

Les valeurs suivantes du paramètre mode sont supportées:

SIO_PLAY
Mode lecture seule : les données écrites seront jouées par le périphérique.
SIO_REC
Mode enregistrement seul : les échantillons sont enregistrés par le périphérique et doivent être lus.
SIO_PLAY | SIO_REC
Le périphérique joue et enregistre de manière synchrone ; cela signifie que le n-ième échantillon enregistré a été physiquement échantillonné exactement au moment où le n-ième échantillon joué a été effectivement joué.

Si l'argument nbio_flag est vrai (c'est-à-dire non nul), alors les fonctions sio_read() et sio_write() (voir ci-dessous) seront non bloquantes.

La fonction sio_close() arrête le périphérique comme si sio_stop() était appelée et libère le descripteur. Ainsi, aucun échantillon soumis avec sio_write() n'est discardé.

Négociation des paramètres audio

Les échantillons audio sont entrelacés. Une trame consiste en un échantillon pour chaque canal. Par exemple, un encodage stéréo de 16 bits a deux échantillons par trame et, deux octets par échantillon (donc 4 octets par trame).

L'ensemble des paramètres du périphérique qui peuvent être contrôlés est donné par la structure suivante :

struct sio_par {
	unsigned int bits;	/* bits par échantillon */
	unsigned int bps;	/* octets par échantillon */
	unsigned int sig;	/* 1 = signé, 0 = non signé */
	unsigned int le;	/* 1 = LE, 0 = BE ordre des octets */
	unsigned int msb;	/* 1 = MSB, 0 = LSB aligné */
	unsigned int rchan;	/* nombre de canaux pour l'enregistrement */
	unsigned int pchan;	/* nombre de canaux pour la lecture */
	unsigned int rate;	/* trames par seconde */
	unsigned int appbufsz;	/* taille minimum du tampon sans xruns */
	unsigned int bufsz;	/* taille du tampon de bout en bout (lecture seule) */
	unsigned int round;	/* diviseur de taille de tampon optimal */
#define SIO_IGNORE	0	/* pause pendant xrun */
#define SIO_SYNC	1	/* resynchronisation après xrun */
#define SIO_ERROR	2	/* terminaison sur xrun */
	unsigned int xrun;	/* quoi faire en cas de dépassement/sous-dépassement */
};

Les paramètres sont les suivants :

bits
Nombre de bits par échantillon : doit être compris entre 1 et 32.
bps
Octets par échantillon ; si spécifié, il doit être suffisamment grand pour contenir tous les bits. Par défaut, il est défini à la plus petite puissance de deux suffisamment grande pour contenir bits.
sig
Si défini (c'est-à-dire non nul), les échantillons sont signés, sinon non signés.
le
>
S'il est défini, l'ordre des octets est little endian, sinon big endian ; cela n'a de sens que si bps > 1.
msb
S'il est défini, les bits sont alignés dans le paquet sur le bit le plus significatif (c'est-à-dire que les bits de poids faible sont complétés), sinon sur le bit le moins significatif (c'est-à-dire que les bits de poids fort sont complétés) ; cela n'a de sens que si bits < bps * 8.
rchan
Le nombre de canaux enregistrés ; cela n'a de sens que si le mode SIO_REC a été sélectionné.
pchan
Le nombre de canaux lus ; cela n'a de sens que si le mode SIO_PLAY a été sélectionné.
rate
La fréquence d'échantillonnage en Hz.
appbufsz
Taille du tampon en images que l'application doit maintenir non vide (du côté lecture) ou non pleine (du côté enregistrement) en appelant sio_write() ou sio_read() suffisamment rapidement pour éviter les dépassements ou les sous-dépassements. Le sous-système audio peut utiliser un tampon supplémentaire, par conséquent ce paramètre ne peut pas être utilisé pour le calcul de la latence.
bufsz
Le nombre maximum d'images pouvant être mises en tampon. Ce paramètre prend en compte tous les tampons et peut être utilisé pour le calcul de la latence. Il est en lecture seule.
round
Nombre optimal d'images dont les tampons de l'application doivent être un multiple, pour obtenir les meilleures performances. Les applications peuvent utiliser ce paramètre pour arrondir leur taille de bloc.
xrun
L'action lorsque le client n'accepte pas les données enregistrées ou ne fournit pas de données à lire assez rapidement ; il peut être défini sur l'une des constantes SIO_IGNORE, SIO_SYNC ou SIO_ERROR.

L'approche suivante est recommandée pour négocier les paramètres du périphérique :

  • Initialisez une structure sio_par en utilisant sio_initpar() et remplissez-la avec les paramètres souhaités. Appelez ensuite sio_setpar() pour demander au périphérique de les utiliser. Les paramètres non définis dans la structure sio_par seront définis sur les valeurs par défaut spécifiques au périphérique.
  • Appelez sio_getpar() pour récupérer les paramètres réels du périphérique et vérifier qu'ils sont utilisables. S'ils ne le sont pas, échouez ou configurez une couche de conversion. Parfois, la fréquence définie peut être légèrement différente de celle demandée. Une différence d'environ 0,5 % est inaudible et doit être ignorée.

Les paramètres ne peuvent pas être modifiés après l'appel de sio_start() ; il faut appeler sio_stop() ou sio_flush() avant que les paramètres ne puissent être modifiés.

Si le périphérique est exposé par le serveur sndiod(8), ce qui est la configuration par défaut, une couche d'émulation transparente sera automatiquement mise en place, et dans ce cas toute combinaison de fréquence, d'encodage et de nombre de canaux est prise en charge.

Pour faciliter le remplissage de la structure sio_par, les macros suivantes peuvent être utilisées :

SIO_BPS(bits)
Retourne la plus petite valeur pour bps qui est une puissance de deux et qui est suffisamment grande pour contenir bits.
SIO_LE_NATIVE
Peut être utilisé pour définir le paramètre le lorsque l'ordre des octets natif est requis. Il vaut 1 si l'ordre des octets natif est little endian ou 0 sinon.

Obtenir les capacités du périphérique

Il n'y a aucun moyen d'obtenir une liste exhaustive de toutes les combinaisons de paramètres que le périphérique prend en charge. Les applications qui ont besoin d'un ensemble de combinaisons de paramètres fonctionnelles à l'avance peuvent utiliser la fonction sio_getcap(). Cependant, pour la plupart des nouvelles applications, il n'est généralement pas recommandé d'utiliser sio_getcap(). Suivez plutôt les recommandations pour la négociation des paramètres du périphérique (voir ci-dessus).

La structure sio_cap contient la liste des configurations de paramètres. Chaque configuration contient plusieurs ensembles de paramètres. L'application doit examiner toutes les configurations et choisir son ensemble de paramètres parmi une des configurations. Les paramètres de différentes configurations ne sont pas utilisables ensemble.

struct sio_cap {
	struct sio_enc {		/* encodages autorisés */
		unsigned int bits;
		unsigned int bps;
		unsigned int sig;
		unsigned int le;
		unsigned int msb;
	} enc[SIO_NENC];
	unsigned int rchan[SIO_NCHAN];	/* rchans autorisés */
	unsigned int pchan[SIO_NCHAN];	/* pchans autorisés */
	unsigned int rate[SIO_NRATE];	/* taux autorisés */
	unsigned int nconf;		/* nb. de confs[] */
	struct sio_conf {
		unsigned int enc;	/* masque de bits des index enc[] */
		unsigned int rchan;	/* masque de bits des index rchan[] */
		unsigned int pchan;	/* masque de bits des index pchan[] */
		unsigned int rate;	/* masque de bits des index rate[] */
	} confs[SIO_NCONF];
};

Les paramètres sont les suivants :

enc[SIO_NENC]
Tableau des encodages pris en charge. Le tuple des paramètres bits, bps, sig, le et msb est utilisable dans les paramètres correspondants de la structure sio_par.
rchan[SIO_NCHAN]
Tableau des nombres de canaux pris en charge pour l'enregistrement utilisable dans la structure sio_par.
pchan[SIO_NCHAN]
Tableau des nombres de canaux pris en charge pour la lecture utilisable dans la structure sio_par.
rate[SIO_NRATE]
Tableau des fréquences d'échantillonnage prises en charge utilisable dans la structure sio_par.
nconf
Nombre de configurations différentes disponibles, c'est-à-dire le nombre d'éléments remplis du tableau confs[].
confs[SIO_NCONF]
Tableau des configurations disponibles. Chaque configuration contient des masques de bits indiquant quels éléments des tableaux de paramètres ci-dessus sont valides pour la configuration donnée. Par exemple, si le deuxième bit de rate est défini, dans la structure sio_conf, alors le deuxième élément du tableau rate[SIO_NRATE] de la structure sio_cap est valide pour cette configuration. Ainsi, lors de la lecture des éléments du tableau dans la structure sio_cap, les masques de bits correspondants de sio_conf doivent toujours être utilisés.

Démarrer et arrêter le périphérique

La fonction sio_start() prépare le périphérique au démarrage. Une fois le tampon de lecture plein, c'est-à-dire que sio_par.bufsz échantillons sont mis en file d'attente avec sio_write(), la lecture démarre automatiquement. Si le mode lecture seule est sélectionné, alors sio_start() démarre l'enregistrement immédiatement. En mode duplex intégral, la lecture et l'enregistrement commenceront de manière synchrone dès que le tampon de lecture sera plein.

La fonction sio_stop() remet le sous-système audio dans le même état qu'avant l'appel de sio_start(). Elle arrête l'enregistrement, vide le tampon de lecture, puis arrête la lecture. Si des échantillons à lire sont mis en file d'attente mais que la lecture n'a pas encore commencé, la lecture est forcée immédiatement ; la lecture s'arrêtera réellement une fois le tampon vidé. En aucun cas les échantillons dans le tampon de lecture ne sont rejetés.

La fonction sio_flush() arrête immédiatement la lecture et l'enregistrement, potentiellement en rejetant le contenu du tampon de lecture, et remet le sous-système audio dans le même état qu'avant l'appel de sio_start().

Lecture et enregistrement

Lorsque le mode enregistrement est sélectionné, la fonction sio_read() doit être appelée pour récupérer les données enregistrées ; elle doit être appelée suffisamment souvent pour garantir que les tampons internes ne dépasseront pas. Elle stockera au maximum nbytes octets à l'emplacement addr et retournera le nombre d'octets stockés. Sauf si l'indicateur nbio_flag est défini, elle se bloquera jusqu'à ce que des données soient disponibles et ne retournera zéro qu'en cas d'erreur.

De même, lorsque le mode lecture est sélectionné, la fonction sio_write() doit être appelée pour fournir des données à lire. Sauf si l'indicateur nbio_flag est défini, sio_write() se bloquera jusqu'à ce que la quantité de données demandée soit écrite.

Opération en mode non bloquant

Si l'indicateur nbio_flag est défini sur sio_open(), alors les fonctions sio_read() et sio_write() ne se bloqueront jamais ; si aucune donnée n'est disponible, elles retourneront immédiatement zéro.

L'appel système poll(2) peut être utilisé pour vérifier si des données peuvent être lues ou écrites sur le périphérique. La fonction sio_pollfd() remplit le tableau pfd de structures pollfd, utilisé par poll(2), avec events ; ce dernier est un bit-

masque de POLLIN et POLLOUT constantes ; se référer à poll(2) pour plus détails. La fonction sio_revents() retourne le masque de bits défini par poll(2) dans le tableau pfd de structures pollfd. Si POLLIN est défini, des échantillons enregistrés sont disponibles dans le tampon du périphérique et peuvent être lus avec sio_read(). Si POLLOUT est défini, de l'espace est disponible dans le tampon du périphérique et de nouveaux échantillons à jouer peuvent être soumis avec sio_write(). POLLHUP peut être défini si une erreur se produit, même s'il n'est pas sélectionné avec sio_pollfd().

La taille du tableau pfd, que l'appelant doit pré-allouer, est fournie par la fonction sio_nfds().

Synchronisation des événements non audio avec le flux audio en temps réel

Afin d'effectuer des actions à des positions précises du flux audio, telles que l'affichage vidéo synchronisé avec le flux audio, l'application doit être notifiée en temps réel de la position exacte dans le flux que le matériel est en train de traiter.

La fonction sio_onmove() peut être utilisée pour enregistrer la fonction de rappel cb() appelée à intervalles de temps réguliers. L'argument delta contient le nombre d'images que le matériel a jouées et/ou enregistrées depuis le dernier appel de cb(). Elle est appelée par sio_read(), sio_write(), et sio_revents(). Lorsque le premier échantillon est joué et/ou enregistré, juste après le démarrage du périphérique, le rappel est appelé avec un argument delta nul. La valeur du pointeur arg est passée au rappel et peut contenir n'importe quoi.

Si désiré, l'application peut maintenir la position actuelle en partant de zéro (lorsque sio_start() est appelé) et en ajoutant delta à la position actuelle à chaque fois que cb() est appelé.

Mesure de la latence et de l'utilisation des tampons

La latence de lecture est le délai qui s'écoulera avant que l'image qui vient d'être écrite ne devienne audible, exprimé en nombre d'images. La latence de lecture exacte peut être obtenue en soustrayant la position actuelle du nombre d'images écrites. Une fois la lecture réellement commencée (premier échantillon audible), la latence ne dépassera jamais le paramètre bufsz (voir les sections ci-dessus). Il existe une phase pendant laquelle sio_write() met uniquement des données en file d'attente ; une fois qu'il y a suffisamment de données, la lecture réelle commence. Pendant cette phase, parler de latence n'a pas de sens.

Dans tous les cas, au plus bufsz images sont tamponnées. Cette valeur prend en compte tous les tampons. Le nombre d'images stockées est égal au nombre d'images écrites moins la position actuelle.

La latence d'enregistrement est obtenue de manière similaire, en soustrayant le nombre d'images lues de la position actuelle.

Notez que sio_write() peut se bloquer même s'il reste de l'espace dans le tampon ; utiliser l'utilisation du tampon pour deviner si sio_write() se bloquerait est faux et conduit à des programmes peu fiables – envisagez d'utiliser poll(2) pour cela.

Gestion des dépassements de tampons et des pannes de tampons

Lorsque l'application ne peut pas accepter les données enregistrées assez rapidement, le tampon d'enregistrement (de taille appbufsz) peut déborder ; dans ce cas, les données enregistrées sont perdues. De même, si l'application ne peut pas fournir de données à jouer assez rapidement, le tampon de lecture déborde et du silence est joué à la place. Selon le paramètre xrun de la structure sio_par, le sous-système audio se comportera comme suit :

SIO_IGNORE
Le périphérique s'arrête pendant les dépassements et les pannes, donc la position actuelle (obtenue via sio_onmove()) cesse d'être incrémentée. Une fois la condition de dépassement et/ou de panne disparue, le périphérique reprend ; la lecture et l'enregistrement restent toujours synchronisés. Avec ce mode, l'application ne peut pas remarquer les pannes et/ou les dépassements et ne devrait pas s'en soucier.

Ce mode est le mode par défaut. Il convient aux applications, telles que les lecteurs audio et la téléphonie, où le temps n'est pas important et où les dépassements ou les pannes ne sont pas courts.

SIO_SYNC
Si le tampon de lecture déborde, du silence est joué, mais afin d'atteindre la bonne position dans le temps, la même quantité d'échantillons écrits sera rejetée une fois que l'application sera débloquée. De même, si le tampon d'enregistrement déborde, des échantillons sont rejetés, mais la même quantité de silence sera retournée plus tard. La position actuelle (obtenue via sio_onmove()) est toujours incrémentée. Lorsque le tampon de lecture déborde, la latence de lecture peut devenir négative ; lorsque le tampon d'enregistrement déborde, la latence d'enregistrement peut devenir supérieure à bufsz.

Ce mode convient aux applications, telles que la production musicale, où le temps est important et où les pannes ou les dépassements sont courts et rares.

SIO_ERROR
Avec ce mode, lors du premier débordement du tampon de lecture ou du dépassement du tampon d'enregistrement, la lecture et/ou l'enregistrement est terminé et aucune autre fonction que sio_close() ne réussira.

Ce mode est principalement utile pour les tests.

Contrôle du volume

La fonction sio_setvol() peut être utilisée pour régler l'atténuation de lecture. Le paramètre vol prend une valeur comprise entre 0 (atténuation maximale) et SIO_MAXVOL (pas d'atténuation). Il spécifie le poids que le sous-système audio donnera à ce flux. Il n'est pas destiné à contrôler les paramètres matériels tels que le gain des haut-parleurs ; l'interface mixerctl(8) doit être utilisée à cette fin.

Une application peut utiliser la fonction sio_onvol() pour enregistrer une fonction de rappel qui sera appelée chaque fois que le volume est modifié, y compris lorsque sio_setvol() est utilisé. Le rappel est toujours appelé lorsque sio_onvol() est appelé afin de fournir le volume initial. Une application peut supposer en toute sécurité qu'une fois que sio_onvol() a retourné une valeur non nulle, le rappel a été appelé et donc le volume actuel est disponible. S'il n'y a pas de réglage de volume disponible, sio_onvol() retourne 0 et le rappel n'est jamais appelé, et les appels à sio_setvol() sont ignorés.

La fonction sio_onvol() peut être appelée avec un argument NULL pour vérifier si un potentiomètre de volume est disponible.

Gestion des erreurs

Les erreurs liées au sous-système audio (telles que les erreurs matérielles, les connexions perdues) et les erreurs de programmation (par exemple, appel à sio_read() sur un flux de lecture uniquement) sont considérées comme fatales. Une fois qu'une erreur se produit, toutes les fonctions prenant un argument sio_hdl, à l'exception de sio_close() et sio_eof(), cessent de fonctionner (c'est-à-dire qu'elles retournent toujours 0). La fonction sio_eof() peut être utilisée à tout moment.

VALEURS DE RETOUR

La fonction sio_open() retourne le handle nouvellement créé en cas de succès ou NULL en cas d'échec.

Les fonctions sio_setpar(), sio_getpar(), sio_getcap(), sio_start(), sio_stop(), sio_flush(), et sio_setvol() retournent 1 en cas de succès et 0 en cas d'échec.

La fonction sio_pollfd() retourne le nombre de structures pollfd remplies. La fonction sio_nfds() retourne le nombre de structures pollfd que l'appelant doit pré-allouer afin d'être sûr que sio_pollfd() ne dépassera jamais.

Les fonctions sio_read() et sio_write() retournent le nombre d'octets transférés.

La fonction sio_eof() retourne 0 s'il n'y a pas d'erreur en attente, et une valeur non nulle s'il y a une erreur.

BOGUES

Le pilote audio(4) ne vide pas les tampons de lecture, donc si sndio est utilisé pour accéder directement à un périphérique audio(4), la fonction sio_stop() arrêtera la lecture immédiatement.

Si l'application ne consomme pas les données enregistrées assez rapidement, les « messages de contrôle » du serveur sndiod(8) sont retardés et par conséquent la fonction de rappel sio_onmove() ou les changements de volume peuvent être retardés.

Les fonctions sio_open(), sio_setpar(), sio_getpar(), sio_getcap(), sio_start(), sio_stop(), et sio_flush() peuvent bloquer pendant une très courte période, elles doivent donc être évitées dans les sections de code où le blocage n'est pas souhaitable.
