sigaction(2) Manuel des appels système sigaction(2)

NOM

sigaction, rt_sigaction - examiner et modifier une action de signal

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <signal.h>
int sigaction(int signum,
              const struct sigaction *_Nullable restrict act,
              struct sigaction *_Nullable restrict oldact);
Exigences pour les macros de test de fonctionnalité dans glibc (voir feature_test_macros(7)):

sigaction():

    _POSIX_C_SOURCE

siginfo_t:

    _POSIX_C_SOURCE >= 199309L

DESCRIPTION

L'appel système sigaction() est utilisé pour changer l'action effectuée par un processus lors de la réception d'un signal spécifique. (Voir signal(7) pour un aperçu des signaux.)

signum spécifie le signal et peut être n'importe quel signal valide, sauf SIGKILL et SIGSTOP.

Si act n'est pas NUL, la nouvelle action pour le signal signum est installée à partir de act. Si oldact n'est pas NUL, l'action précédente est sauvegardée dans oldact.

La structure sigaction est définie comme suit :


struct sigaction {
    void     (*sa_handler)(int);
    void     (*sa_sigaction)(int, siginfo_t *, void *);
    sigset_t   sa_mask;
    int        sa_flags;
    void     (*sa_restorer)(void);
};

Sur certaines architectures, il y a une union : n'assignez pas à la fois sa_handler et sa_sigaction.

Le champ sa_restorer n'est pas destiné à être utilisé par les applications. (POSIX ne spécifie pas de champ sa_restorer.) Des détails supplémentaires sur le but de ce champ peuvent être trouvés dans sigreturn(2).

sa_handler spécifie l'action à associer à signum et peut être l'une des suivantes :

•
SIG_DFL pour l'action par défaut.
•
SIG_IGN pour ignorer ce signal.
•
Un pointeur vers une fonction de gestion de signal. Cette fonction reçoit le numéro de signal comme seul argument.

Si SA_SIGINFO est spécifié dans sa_flags, alors sa_sigaction (au lieu de sa_handler) spécifie la fonction de gestion de signal pour signum. Cette fonction reçoit trois arguments, comme décrit ci-dessous.

sa_mask spécifie un masque de signaux qui doivent être bloqués (c'est-à-dire ajoutés au masque de signaux du thread dans lequel le gestionnaire de signal est invoqué) pendant l'exécution du gestionnaire de signal. De plus, le signal qui a déclenché le gestionnaire sera bloqué, sauf si le drapeau SA_NODEFER est utilisé.

sa_flags spécifie un ensemble de drapeaux qui modifient le comportement du signal. Il est formé par le OU bit à bit de zéro ou plusieurs des éléments suivants :

SA_NOCLDSTOP
Si signum est SIGCHLD, ne pas recevoir de notification lorsque les processus enfants s'arrêtent (c'est-à-dire lorsqu'ils reçoivent l'un de SIGSTOP, SIGTSTP, SIGTTIN, ou SIGTTOU) ou recommencent (c'est-à-dire lorsqu'ils reçoivent SIGCONT) (voir wait(2)). Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire pour SIGCHLD.
SA_NOCLDWAIT (depuis Linux 2.6)
Si signum est SIGCHLD, ne pas transformer les enfants en zombies lorsqu'ils se terminent. Voir aussi waitpid(2). Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire pour SIGCHLD, ou lors de la définition de la disposition de ce signal à SIG_DFL.
Si le drapeau SA_NOCLDWAIT est défini lors de l'établissement d'un gestionnaire pour SIGCHLD, POSIX.1 laisse non spécifié si un signal SIGCHLD est généré lorsqu'un processus enfant se termine. Sur Linux, un signal SIGCHLD est généré dans ce cas ; sur certaines autres implémentations, ce n'est pas le cas.
SA_NODEFER
Ne pas ajouter le signal au masque de signaux du thread pendant que le gestionnaire s'exécute, sauf si le signal est spécifié dans act.sa_mask. Par conséquent, une autre instance du signal peut être délivrée au thread pendant qu'il exécute le gestionnaire. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal.
SA_NOMASK est un synonyme obsolète et non standard pour ce drapeau.
SA_ONSTACK
Appeler le gestionnaire de signal sur une pile de signaux alternatifs fournie par sigaltstack(2). Si une pile alternative n'est pas disponible, la pile par défaut sera utilisée. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal.
SA_RESETHAND
Restaurer l'action du signal à la valeur par défaut lors de l'entrée dans le gestionnaire de signal. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal.
SA_ONESHOT est un synonyme obsolète et non standard pour ce drapeau.
SA_RESTART
Fournir un comportement compatible avec la sémantique des signaux BSD en rendant certains appels système redémarrables après des signaux. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal. Voir signal(7) pour une discussion sur le redémarrage des appels système.
SA_RESTORER
Non destiné à être utilisé par les applications. Ce drapeau est utilisé par les bibliothèques C pour indiquer que le champ sa_restorer contient l'adresse d'un "saut de signal". Voir sigreturn(2) pour plus de détails.
SA_SIGINFO (depuis Linux 2.2)
Le gestionnaire de signal prend trois arguments, pas un. Dans ce cas, sa_sigaction doit être défini au lieu de sa_handler. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal.
SA_UNSUPPORTED (depuis Linux 5.11)
Utilisé pour sonder dynamiquement le support des bits de drapeau.
Si une tentative d'enregistrement d'un gestionnaire réussit avec ce drapeau défini dans act->sa_flags aux côtés d'autres drapeaux potentiellement non pris en charge par le noyau, et qu'un appel sigaction() immédiatement ultérieur spécifiant le même numéro de signal et avec un argument oldact non NUL renvoie SA_UNSUPPORTED effacé dans oldact->sa_flags, alors oldact->sa_flags peut être utilisé comme masque de bits décrivant quels des drapeaux potentiellement non pris en charge sont, en fait, pris en charge. Voir la section "Sondage dynamique pour le support des bits de drapeau" ci-dessous pour plus de détails.
SA_EXPOSE_TAGBITS (depuis Linux 5.11)
Normalement, lors de la délivrance d'un signal, un ensemble de bits d'étiquette spécifique à l'architecture est effacé du champ si_addr de siginfo_t. Si ce drapeau est défini, un sous-ensemble spécifique à l'architecture des bits d'étiquette sera préservé dans si_addr.
Les programmes qui doivent être compatibles avec les versions de Linux antérieures à 5.11 doivent utiliser SA_UNSUPPORTED pour sonder le support.

L'argument siginfo_t à un gestionnaire SA_SIGINFO

Lorsque le drapeau SA_SIGINFO est spécifié dans act.sa_flags, l'adresse du gestionnaire de signal est passée via le champ act.sa_sigaction. Ce gestionnaire prend trois arguments, comme suit :


void
handler(int sig, siginfo_t *info, void *ucontext)
{
    ...
}

Ces trois arguments sont les suivants :

siginfo, siginfo_t - signal information

SYNOPSIS

#include <signal.h>
void handler(int sig, siginfo_t *info, void *ucontext);

DESCRIPTION

When a signal is delivered to a process, the kernel can invoke a user-space signal handler. The handler function is invoked with three arguments:

sig
Le numéro du signal qui a provoqué l'invocation du gestionnaire.
info
Un pointeur vers une structure siginfo_t, qui contient des informations supplémentaires sur le signal, comme décrit ci-dessous.
ucontext
Il s'agit d'un pointeur vers une structure ucontext_t, transtypé en void *. La structure pointée par ce champ contient des informations de contexte de signal qui ont été sauvegardées dans la pile de l'espace utilisateur par le noyau ; pour plus de détails, voir sigreturn(2). Des informations supplémentaires sur la structure ucontext_t se trouvent dans getcontext(3) et signal(7). Couramment, la fonction de gestion n'utilise pas le troisième argument.

Le type de données siginfo_t est une structure avec les champs suivants :


siginfo_t {
    int      si_signo;     /* Numéro du signal */
    int      si_errno;     /* Une valeur errno */
    int      si_code;      /* Code du signal */
    int      si_trapno;    /* Numéro de piège ayant provoqué
                              le signal généré par le matériel
                              (inutilisé sur la plupart des architectures) */
    pid_t    si_pid;       /* ID du processus émetteur */
    uid_t    si_uid;       /* ID utilisateur réel du processus émetteur */
    int      si_status;    /* Valeur de sortie ou signal */
    clock_t  si_utime;     /* Temps utilisateur consommé */
    clock_t  si_stime;     /* Temps système consommé */
    union sigval si_value; /* Valeur du signal */
    int      si_int;       /* Signal POSIX.1b */
    void    *si_ptr;       /* Signal POSIX.1b */
    int      si_overrun;   /* Compteur de dépassement de délai ;
                              timers POSIX.1b */
    int      si_timerid;   /* ID du timer ; timers POSIX.1b */
    void    *si_addr;      /* Emplacement mémoire ayant provoqué l'échec */
    long     si_band;      /* Événement de bande (était int dans
                              glibc 2.3.2 et antérieur) */
    int      si_fd;        /* Descripteur de fichier */
    short    si_addr_lsb;  /* Bit le moins significatif de l'adresse
                              (depuis Linux 2.6.32) */
    void    *si_lower;     /* Borne inférieure lors de l'occurrence de la violation d'adresse
                              (depuis Linux 3.19) */
    void    *si_upper;     /* Borne supérieure lors de l'occurrence de la violation d'adresse
                              (depuis Linux 3.19) */
    int      si_pkey;      /* Clé de protection sur le PTE ayant provoqué
                              l'échec (depuis Linux 4.6) */
    void    *si_call_addr; /* Adresse de l'instruction d'appel système
                              (depuis Linux 3.5) */
    int      si_syscall;   /* Numéro de l'appel système tenté
                              (depuis Linux 3.5) */
    unsigned int si_arch;  /* Architecture de l'appel système tenté
                              (depuis Linux 3.5) */
}

si_signo, si_errno et si_code sont définis pour tous les signaux. (si_errno est généralement inutilisé sous Linux.) Le reste de la structure peut être une union, de sorte qu'il ne faut lire que les champs qui ont un sens pour le signal donné :

•
Les signaux envoyés avec kill(2) et sigqueue(3) remplissent si_pid et si_uid. De plus, les signaux envoyés avec sigqueue(3) remplissent si_int et si_ptr avec les valeurs spécifiées par l'expéditeur du signal ; voir sigqueue(3) pour plus de détails.
•
Les signaux envoyés par les timers POSIX.1b (depuis Linux 2.6) remplissent si_overrun et si_timerid. Le champ si_timerid est un ID interne utilisé par le noyau pour identifier le timer ; ce n'est pas le même que l'ID du timer renvoyé par timer_create(2). Le champ si_overrun est le compteur de dépassement de délai du timer ; il s'agit des mêmes informations que celles obtenues par un appel à timer_getoverrun(2). Ces champs sont des extensions non standard de Linux.
•
Les signaux envoyés pour la notification de files de messages (voir la description de SIGEV_SIGNAL dans mq_notify(3)) remplissent si_int/si_ptr, avec la valeur sigev_value fournie à mq_notify(3) ; si_pid, avec l'ID du processus de l'expéditeur du message ; et si_uid, avec l'ID utilisateur réel de l'expéditeur du message.
•
SIGCHLD remplit si_pid, si_uid, si_status, si_utime et si_stime, fournissant des informations sur l'enfant. Le champ si_pid est l'ID du processus de l'enfant ; si_uid est l'ID utilisateur réel de l'enfant. Le champ si_status contient la valeur de sortie de l'enfant (si si_code est CLD_EXITED), ou le numéro du signal qui a provoqué le changement d'état du processus. Les champs si_utime et si_stime contiennent le temps CPU utilisateur et système utilisé par le processus enfant ; ces champs n'incluent pas les temps utilisés par les enfants attendus (contrairement à getrusage(2) et times(2)). Jusqu'à Linux 2.6, et depuis Linux 2.6.27, ces champs rapportent le temps CPU dans des unités de sysconf(_SC_CLK_TCK). Dans les noyaux Linux 2.6 avant Linux 2.6.27, un bug signifiait que ces champs rapportaient le temps dans des unités du jiffy système (configurable) (voir time(7)).
•
SIGILL, SIGFPE, SIGSEGV, SIGBUS et SIGTRAP remplissent si_addr avec l'adresse de l'échec. Sur certaines architectures, ces signaux remplissent également le champ si_trapno.
Certaines sous-erreurs de SIGBUS, en particulier BUS_MCEERR_AO et BUS_MCEERR_AR, remplissent également si_addr_lsb. Ce champ indique le bit le moins significatif de l'adresse rapportée et donc l'étendue de la corruption. Par exemple, si une page entière a été corrompue, si_addr_lsb contient log2(sysconf(_SC_PAGESIZE)). Lorsque SIGTRAP est délivré en réponse à un événement ptrace(2) (PTRACE_EVENT_foo), si_addr n'est pas renseigné, mais si_pid et si_uid sont renseignés avec l'ID de processus et l'ID utilisateur respectifs responsables de la délivrance du piège. Dans le cas de seccomp(2), le tracee sera affiché comme délivrant l'événement. BUS_MCEERR_* et si_addr_lsb sont des extensions spécifiques à Linux.
La sous-erreur SEGV_BNDERR de SIGSEGV remplit si_lower et si_upper.
La sous-erreur SEGV_PKUERR de SIGSEGV remplit si_pkey.
•
SIGIO/SIGPOLL (les deux noms sont synonymes sous Linux) remplit si_band et si_fd. L'événement si_band est un masque de bits contenant les mêmes valeurs que celles remplies dans le champ revents par poll(2). Le champ si_fd indique le descripteur de fichier pour lequel l'événement d'E/S s'est produit ; pour plus de détails, voir la description de F_SETSIG dans fcntl(2).
•
SIGSYS, généré (depuis Linux 3.5) lorsqu'un filtre seccomp renvoie SECCOMP_RET_TRAP, remplit si_call_addr, si_syscall, si_arch, si_errno, et d'autres champs comme décrit dans seccomp(2).

Le champ si_code

Le champ si_code dans l'argument siginfo_t passé à un gestionnaire de signaux SA_SIGINFO est une valeur (pas un masque de bits) indiquant pourquoi ce signal a été envoyé. Pour un événement ptrace(2), si_code contiendra SIGTRAP et aura l'événement ptrace dans l'octet de poids fort :


(SIGTRAP | PTRACE_EVENT_foo << 8).

Pour un événement autre que ptrace(2), les valeurs qui peuvent apparaître dans si_code sont décrites dans le reste de cette section. Depuis glibc 2.20, les définitions de la plupart de ces symboles sont obtenues à partir de <signal.h> en définissant des macros de test de fonctionnalité (avant d'inclure n'importe quel fichier d'en-tête) comme suit :

•
_XOPEN_SOURCE avec la valeur 500 ou supérieure ;
•
_XOPEN_SOURCE et _XOPEN_SOURCE_EXTENDED ; ou
•
_POSIX_C_SOURCE avec la valeur 200809L ou supérieure.

Pour les constantes TRAP_*, les définitions de symboles ne sont fournies que dans les deux premiers cas. Avant glibc 2.20, aucune macro de test de fonctionnalité n'était requise pour obtenir ces symboles.

Pour un signal régulier, la liste suivante montre les valeurs qui peuvent être placées dans si_code pour n'importe quel signal, ainsi que la raison pour laquelle le signal a été généré.

SI_USER

SI_KERNEL
Envoyé par le noyau.
SI_QUEUE
sigqueue(3).
SI_TIMER
Timer POSIX, ou setitimer(2) ou alarm(2) expiré.
SI_MESGQ (depuis Linux 2.6.6)
État de la file de messages POSIX changé ; voir mq_notify(3).
SI_ASYNCIO
AIO terminé.
SI_SIGIO
SIGIO mis en file d'attente (seulement jusqu'à Linux 2.2 ; à partir de Linux 2.4, SIGIO/SIGPOLL remplit si_code comme décrit ci-dessous).
SI_TKILL (depuis Linux 2.4.19)
tkill(2) ou tgkill(2).
SI_ASYNCNL
Fin de recherche de nom asynchrone.

Les valeurs suivantes peuvent être placées dans si_code pour un signal SIGILL :

ILL_ILLOPC
Opcode illégal.
ILL_ILLOPN
Opérande illégal.
ILL_ILLADR
Mode d'adressage illégal.
ILL_ILLTRP
Piège illégal.
ILL_PRVOPC
Opcode privilégié.

DESCRIPTION

The sigaction() system call is used to examine and change the action taken by a process for a specific signal. The action consists of a function to be called (a signal-catching function), a set of flags, and long-term signal mask (blocking all signals during the execution of the signal-catching function).

The signum argument is the signal number for which the action is to be changed. It must be a non-zero signal number.

The act argument points to a structure that specifies the new action to be taken when the signal signum is delivered. If act is NULL, then the current action is not changed.

The oldact argument points to a structure where the previous action for the signal is to be stored. If oldact is NULL, then the previous action is not saved.

The structure pointed to by act (and oldact) is of type sigaction and has at least the following members:

void (*sa_handler)(int);
Signal handler function. For this argument, you must provide either a pointer to a function that accepts a single integer argument (the signal number), or one of the special values SIG_DFL (default action) or SIG_IGN (ignore signal).
void (*sa_sigaction)(int, siginfo_t *, void *);
Signal handler function. If the SA_SIGINFO flag is set in sa_flags, this function is called instead of sa_handler. This function takes three arguments: the signal number, a pointer to a siginfo_t structure containing information about the signal, and a pointer to the process's context.
sigset_t sa_mask;
An additional set of signals to be blocked during the execution of the signal-catching function. Signals in this set are blocked in addition to the signal being caught.
int sa_flags;
A set of flags that modify the behavior of the signal handling. See Signal flags below.
void (*sa_restorer)(void);
This member is not portable. If set, it must point to a signal trampoline function. This is used by some C libraries to implement signal handling. It is normally set to NULL.

The siginfo_t structure is described in siginfo(7). The si_signo member contains the signal number. The si_code member contains a code indicating the cause of the signal. The meaning of si_code depends on the signal number.

Dynamically probing for flag bit support

The sigaction() call on Linux accepts unknown bits set in act->sa_flags without error. The behavior of the kernel starting with Linux 5.11 is that a second sigaction() will clear unknown bits from oldact->sa_flags. However, historically, a second sigaction() call would typically leave those bits set in oldact->sa_flags.

This means that support for new flags cannot be detected simply by testing for a flag in sa_flags, and a program must test that SA_UNSUPPORTED has been cleared before relying on the contents of sa_flags.

Since the behavior of the signal handler cannot be guaranteed unless the check passes, it is wise to either block the affected signal while registering the handler and performing the check in this case, or where this is not possible, for example if the signal is synchronous, to issue the second sigaction() in the signal handler itself.

In kernels that do not support a specific flag, the kernel's behavior is as if the flag was not set, even if the flag was set in act->sa_flags.

The flags SA_NOCLDSTOP, SA_NOCLDWAIT, SA_SIGINFO, SA_ONSTACK, SA_RESTART, SA_NODEFER, SA_RESETHAND, and, if defined by the architecture, SA_RESTORER may not be reliably probed for using this mechanism, because they were introduced before Linux 5.11. However, in general, programs may assume that these flags are supported, since they have all been supported since Linux 2.6, which was released in the year 2003.

See EXAMPLES below for a demonstration of the use of SA_UNSUPPORTED.

RETURN VALUE

sigaction() returns 0 on success; on error, -1 is returned, and errno is set to indicate the error.

ERRORS

EFAULT
act or oldact points to memory which is not a valid part of the process address space.
EINVAL
An invalid signal was specified. This will also be generated if an attempt is made to change the action for SIGKILL or SIGSTOP, which cannot be caught or ignored.

VERSIONS

C library/kernel differences

The glibc wrapper function for sigaction() gives an error (EINVAL) on attempts to change the disposition of the two real-time signals used internally by the NPTL threading implementation. See nptl(7) for details.

On architectures where the signal

trampoline réside dans la bibliothèque C. La fonction wrapper glibc pour sigaction() place l'adresse du code trampoline dans le champ act.sa_restorer et définit le drapeau SA_RESTORER dans le champ act.sa_flags. Voir sigreturn(2).

L'appel système original de Linux s'appelait sigaction(). Cependant, avec l'ajout des signaux temps réel dans Linux 2.2, le type sigset_t de taille fixe et 32 bits supporté par cet appel système n'était plus adapté. Par conséquent, un nouvel appel système, rt_sigaction(), a été ajouté pour supporter un type sigset_t agrandi. Le nouvel appel système prend un quatrième argument, size_t sigsetsize, qui spécifie la taille en octets des ensembles de signaux dans act.sa_mask et oldact.sa_mask. Cet argument doit actuellement avoir la valeur sizeof(sigset_t) (ou une erreur EINVAL en résulte). La fonction wrapper glibc sigaction() nous cache ces détails, appelant de manière transparente rt_sigaction() lorsque le noyau le fournit.

NORMES

POSIX.1-2024.

HISTORIQUE

POSIX.1-2001, SVr4.

POSIX.1-1990 interdisait de définir l'action pour SIGCHLD à SIG_IGN. POSIX.1-2001 et plus tard autorisent cette possibilité, de sorte qu'ignorer SIGCHLD peut être utilisé pour empêcher la création de zombies (voir wait(2)). Néanmoins, les comportements historiques de BSD et System V pour ignorer SIGCHLD diffèrent, de sorte que la seule méthode complètement portable pour s'assurer que les enfants terminés ne deviennent pas des zombies est d'intercepter le signal SIGCHLD et d'effectuer un appel à wait(2) ou similaire.

POSIX.1-1990 ne spécifiait que SA_NOCLDSTOP. POSIX.1-2001 a ajouté SA_NOCLDWAIT, SA_NODEFER, SA_ONSTACK, SA_RESETHAND, SA_RESTART et SA_SIGINFO en tant qu'extensions XSI. POSIX.1-2008 a déplacé SA_NODEFER, SA_RESETHAND, SA_RESTART et SA_SIGINFO dans les spécifications de base. L'utilisation de ces dernières valeurs dans sa_flags peut être moins portable dans les applications destinées aux anciennes implémentations UNIX.

Le drapeau SA_RESETHAND est compatible avec le drapeau SVr4 du même nom.

Le drapeau SA_NODEFER est compatible avec le drapeau SVr4 du même nom sous les noyaux 1.3.9 et ultérieurs. Sur les anciens noyaux, l'implémentation Linux permettait la réception de tout signal, pas seulement celui que nous installons (remplaçant effectivement les paramètres sa_mask).

NOTES

Un enfant créé via fork(2) hérite d'une copie des dispositions de signaux de son parent. Lors d'un execve(2), les dispositions des signaux gérés sont réinitialisées aux valeurs par défaut ; les dispositions des signaux ignorés restent inchangées.

Selon POSIX, le comportement d'un processus est indéfini après avoir ignoré un signal SIGFPE, SIGILL ou SIGSEGV qui n'a pas été généré par kill(2) ou raise(3). La division entière par zéro a un résultat indéfini. Sur certaines architectures, cela générera un signal SIGFPE. (La division de l'entier le plus négatif par -1 peut également générer SIGFPE.) Ignorer ce signal pourrait entraîner une boucle infinie.

sigaction() peut être appelé avec un argument second NULL pour interroger le gestionnaire de signaux actuel. Il peut également être utilisé pour vérifier si un signal donné est valide pour la machine actuelle en l'appelant avec des arguments seconds et troisièmes NULL.

Il n'est pas possible de bloquer SIGKILL ou SIGSTOP (en les spécifiant dans sa_mask). Les tentatives de le faire sont silencieusement ignorées.

Voir sigsetops(3) pour les détails sur la manipulation des ensembles de signaux.

Voir signal-safety(7) pour une liste des fonctions sûres pour les signaux asynchrones qui peuvent être appelées en toute sécurité depuis l'intérieur d'un gestionnaire de signaux.

POSIX ne garantit que SI_TIMER pour les signaux créés par timer_create(2). Les implémentations sont libres de les fournir également pour d'autres types de minuteurs. Le comportement de Linux correspond à celui de NetBSD.

Non documenté

Avant l'introduction de SA_SIGINFO, il était également possible d'obtenir des informations supplémentaires sur le signal. Cela se faisait en fournissant un gestionnaire de signaux sa_handler avec un deuxième argument de type struct sigcontext, qui est la même structure que celle passée dans le champ uc_mcontext de la structure ucontext qui est passée (via un pointeur) dans le troisième argument du gestionnaire sa_sigaction. Voir les sources pertinentes du noyau Linux pour les détails. Cette utilisation est obsolète maintenant.

BOGUES

Lors de la livraison d'un signal résultant d'une exception matérielle avec un gestionnaire SA_SIGINFO, le noyau ne fournit pas toujours des valeurs significatives pour tous les champs de siginfo_t qui sont pertinents pour ce signal. Par exemple, lorsque l'instruction int x86 est appelée avec un argument interdit (tout nombre différent de 3 ou 128), un signal SIGSEGV est délivré, mais siginfo_t passé au gestionnaire de signaux a tous ses champs, sauf si_signo et si_code, mis à zéro, même si d'autres champs devraient être définis (par exemple, si_addr devrait être non nul pour tous les signaux SIGSEGV).

Jusqu'à et y compris Linux 2.6.13, la spécification de SA_NODEFER dans sa_flags empêche non seulement le signal délivré d'être masqué pendant l'exécution du gestionnaire, mais aussi les signaux spécifiés dans sa_mask. Ce bogue a été corrigé dans Linux 2.6.14.

EXEMPLES

Voir mprotect(2).

Sondage pour la prise en charge des drapeaux

L'exemple de programme suivant se termine avec le statut EXIT_SUCCESS si SA_EXPOSE_TAGBITS est déterminé comme étant pris en charge, et EXIT_FAILURE sinon.

#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
static void
handler(int signo, siginfo_t *info, void *context)
{
    struct sigaction oldact;
    if (sigaction(SIGSEGV, NULL, &oldact) == -1
        || (oldact.sa_flags & SA_UNSUPPORTED)
        || !(oldact.sa_flags & SA_EXPOSE_TAGBITS))
    {
        _exit(EXIT_FAILURE);
    }
    _exit(EXIT_SUCCESS);
}
int
main(void)
{
    struct sigaction act = { 0 };
    act.sa_flags = SA_SIGINFO | SA_UNSUPPORTED | SA_EXPOSE_TAGBITS;
    act.sa_sigaction = &handler;
    if (sigaction(SIGSEGV, &act, NULL) == -1) {
        perror("sigaction");
        exit(EXIT_FAILURE);
    }
    raise(SIGSEGV);
}

sigaction(2)

sigaction

Nom

sigaction – Examiner ou modifier la gestion d'un signal

Syntaxe

#include <signal.h>

int sigaction(int sig, const struct sigaction *restrict act,
              struct sigaction *restrict oldact);

Description

La fonction sigaction() permet de modifier la façon dont un processus reçoit et gère un signal spécifique. Elle permet de changer l'action associée à un signal, de bloquer ou de débloquer des signaux, et de définir des options supplémentaires pour la gestion des signaux.

  • sig : Le numéro du signal à gérer.
  • act : Un pointeur vers une structure sigaction qui spécifie la nouvelle action à effectuer lors de la réception du signal. Si act est NULL, aucune modification n'est apportée à la gestion du signal.
  • oldact : Un pointeur vers une structure sigaction où la précédente action associée au signal sera stockée. Si oldact est NULL, l'ancienne action n'est pas récupérée.

La structure sigaction est définie comme suit :

struct sigaction {
    void (*sa_handler)(int);
    void (*sa_sigaction)(int, siginfo_t *, void *);
    sigset_t sa_mask;
    int sa_flags;
    void (*sa_restorer)(void);
};
  • sa_handler : Un pointeur vers une fonction (gestionnaire) qui sera appelée lorsque le signal est reçu. Elle peut également être SIG_DFL pour l'action par défaut ou SIG_IGN pour ignorer le signal.
  • sa_sigaction : Utilisée lorsque SA_SIGINFO est spécifié dans sa_flags. Elle fournit des informations supplémentaires sur le signal reçu.
  • sa_mask : Un ensemble de signaux qui seront bloqués pendant l'exécution du gestionnaire de signal.
  • sa_flags : Options supplémentaires pour la gestion du signal.
  • sa_restorer : Généralement pas utilisé directement par l'utilisateur.

Valeur de retour

En cas de succès, sigaction() retourne 0. En cas d'erreur, elle retourne -1 et définit errno pour indiquer la raison de l'erreur.

Erreurs

  • EINVAL : sig n'est pas un signal valide, ou act et oldact sont NULL.

Conformité

POSIX.1-2001, POSIX.1-2008, SUSv2, SVr4, 4.3BSD.

Notes

La fonction sigaction() est la manière recommandée pour modifier la gestion des signaux sous les systèmes POSIX, car elle offre plus de contrôle et de fiabilité que l'ancienne fonction signal().

Exemple

#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <unistd.h>

void handler(int sig) {
    printf("Signal %d reçu !\n", sig);
}

int main() {
    struct sigaction sa;

    // Initialisation de la structure sigaction
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask); // Pas de signaux bloqués supplémentaires
    sa.sa_flags = 0;            // Pas de flags spéciaux

    // Enregistrement du gestionnaire pour SIGINT (Ctrl+C)
    if (sigaction(SIGINT, &sa, NULL) == -1) {
        perror("sigaction");
        exit(EXIT_FAILURE);
    }

    printf("Appuyez sur Ctrl+C pour envoyer SIGINT...\n");
    while (1) {
        pause(); // Attend un signal
    }

    return 0;
}
