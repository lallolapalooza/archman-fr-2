signal(7) Manuel d'informations diverses signal(7)

NOM

signal - aperçu des signaux

DESCRIPTION

Linux prend en charge à la fois les signaux fiables POSIX (ci-après « signaux standard ») et les signaux temps réel POSIX.

Dispositions des signaux

Chaque signal a une disposition actuelle, qui détermine comment le processus se comporte lorsqu'il reçoit le signal.

Les entrées dans la colonne « Action » du tableau ci-dessous spécifient la disposition par défaut pour chaque signal, comme suit :

Term
L'action par défaut est de terminer le processus.
Ign
L'action par défaut est d'ignorer le signal.
Core
L'action par défaut est de terminer le processus et de créer un vidage mémoire (voir core(5)).
Stop
L'action par défaut est d'arrêter le processus.
Cont
L'action par défaut est de continuer le processus s'il est actuellement arrêté.

Un processus peut modifier la disposition d'un signal en utilisant sigaction(2) ou signal(2). (Ce dernier est moins portable lors de l'établissement d'un gestionnaire de signaux ; voir signal(2) pour les détails.) En utilisant ces appels système, un processus peut choisir l'un des comportements suivants lors de la réception du signal : effectuer l'action par défaut ; ignorer le signal ; ou intercepter le signal avec un gestionnaire de signaux, une fonction définie par le programmeur qui est automatiquement appelée lorsque le signal est reçu.

Par défaut, un gestionnaire de signaux est appelé sur la pile de processus normale. Il est possible de faire en sorte que le gestionnaire de signaux utilise une pile alternative ; voir sigaltstack(2) pour une discussion sur la manière de le faire et quand cela pourrait être utile.

La disposition du signal est un attribut par processus : dans une application multithread, la disposition d'un signal particulier est la même pour tous les threads.

Un enfant créé via fork(2) hérite d'une copie des dispositions de signaux de son parent. Lors d'un execve(2), les dispositions des signaux gérés sont réinitialisées à la valeur par défaut ; les dispositions des signaux ignorés ne sont pas modifiées.

Envoi d'un signal

Les appels système et fonctions de bibliothèque suivants permettent à l'appelant d'envoyer un signal :

raise(3)
Envoie un signal au thread appelant.
kill(2)
Envoie un signal à un processus spécifié, à tous les membres d'un groupe de processus spécifié, ou à tous les processus du système.
pidfd_send_signal(2)
Envoie un signal à un processus identifié par un descripteur de fichier PID.
killpg(3)
Envoie un signal à tous les membres d'un groupe de processus spécifié.
pthread_kill(3)
Envoie un signal à un thread POSIX spécifié dans le même processus que l'appelant.
tgkill(2)
Envoie un signal à un thread spécifié dans un processus spécifique. (C'est l'appel système utilisé pour implémenter pthread_kill(3).)
sigqueue(3)
Envoie un signal temps réel avec des données associées à un processus spécifié.

Attente de la réception d'un signal

Les appels système suivants suspendent l'exécution du thread appelant jusqu'à ce qu'un signal soit intercepté (ou qu'un signal non géré termine le processus) :

pause(2)
Suspend l'exécution jusqu'à ce que n'importe quel signal soit intercepté.
sigsuspend(2)
Change temporairement le masque de signaux (voir ci-dessous) et suspend l'exécution jusqu'à ce qu'un des signaux non masqués soit intercepté.

Acceptation synchrone d'un signal

Plutôt que d'intercepter un signal de manière asynchrone via un gestionnaire de signaux, il est possible d'accepter le signal de manière synchrone, c'est-à-dire de bloquer l'exécution jusqu'à ce que le signal soit reçu, auquel cas le noyau renvoie des informations sur le signal à l'appelant. Il existe deux manières générales de procéder :

•
sigwaitinfo(2), sigtimedwait(2), et sigwait(3) suspendent l'exécution jusqu'à ce qu'un des signaux d'un ensemble spécifié soit reçu. Chacun de ces appels renvoie des informations sur le signal reçu.
•
signalfd(2) renvoie un descripteur de fichier qui peut être utilisé pour lire des informations sur les signaux reçus par l'appelant. Chaque read(2) depuis ce descripteur de fichier bloque jusqu'à ce qu'un des signaux de l'ensemble spécifié dans l'appel signalfd(2) soit reçu par l'appelant. Le tampon renvoyé par read(2) contient une structure décrivant le signal.

Masque de signaux et signaux en attente

Un signal peut être bloqué, ce qui signifie qu'il ne sera pas délivré tant qu'il ne sera pas débloqué ultérieurement. Entre le moment où il est généré et celui où il est délivré, un signal est dit « en attente ».

Chaque thread d'un processus possède un masque de signaux indépendant, qui indique l'ensemble des signaux que le thread bloque actuellement. Un thread peut manipuler son masque de signaux en utilisant pthread_sigmask(3). Dans une application traditionnelle monothread, sigprocmask(2) peut être utilisé pour manipuler le masque de signaux.

Un enfant créé via fork(2) hérite d'une copie du masque de signaux de son parent ; le masque de signaux est conservé lors d'un execve(2).

Un signal peut être dirigé vers un processus ou vers un thread. Un signal dirigé vers un processus est un signal destiné à (et donc en attente pour) l'ensemble du processus. Un signal peut être dirigé vers un processus car il a été généré par le noyau pour des raisons autres qu'une exception matérielle, ou parce qu'il a été envoyé en utilisant kill(2) ou sigqueue(3). Un signal dirigé vers un thread est un signal destiné à un thread spécifique. Un signal peut être dirigé vers un thread car il a été généré suite à l'exécution d'une instruction machine spécifique qui a déclenché une exception matérielle (par exemple, SIGSEGV pour un accès mémoire invalide, ou SIGFPE pour une erreur mathématique), ou parce qu'il était destiné à un thread spécifique en utilisant des interfaces telles que tgkill(2) ou pthread_kill(3).

Un signal dirigé vers un processus peut être délivré à l'un des threads qui n'a pas actuellement le signal bloqué. Si plus d'un des threads a le signal débloqué, alors le noyau choisit un thread arbitraire auquel délivrer le signal.

Un thread peut obtenir l'ensemble des signaux qui lui sont actuellement en attente en utilisant sigpending(2)

/a>. Cet ensemble sera constitué de l'union de l'ensemble des signaux en attente dirigés vers le processus et de l'ensemble des signaux en attente pour le thread appelant.

Un enfant créé via fork(2) a initialement un ensemble de signaux en attente vide ; l'ensemble des signaux en attente est préservé lors d'un appel à execve(2).

Exécution des gestionnaires de signaux

Chaque fois qu'il y a une transition du mode noyau au mode utilisateur (par exemple, au retour d'un appel système ou lors de la planification d'un thread sur le CPU), le noyau vérifie s'il existe un signal en attente non bloqué pour lequel le processus a établi un gestionnaire de signaux. S'il existe un tel signal en attente, les étapes suivantes se produisent :

(1)
Le noyau effectue les étapes préparatoires nécessaires à l'exécution du gestionnaire de signaux :
(1.1)
Le signal est retiré de l'ensemble des signaux en attente.
(1.2)
Si le gestionnaire de signaux a été installé par un appel à sigaction(2) qui a spécifié le drapeau SA_ONSTACK et que le thread a défini une pile de signaux alternative (en utilisant sigaltstack(2)), alors cette pile est installée.
(1.3)
Divers éléments du contexte lié aux signaux sont sauvegardés dans une trame spéciale créée sur la pile. Les informations sauvegardées incluent :
•
le registre du compteur de programme (c'est-à-dire l'adresse de la prochaine instruction dans le programme principal qui devrait être exécutée lors du retour du gestionnaire de signaux) ;
•
l'état des registres spécifique à l'architecture requis pour reprendre le programme interrompu ;
•
le masque de signaux actuel du thread ;
•
les paramètres de la pile de signaux alternative du thread.
Si le gestionnaire de signaux a été installé en utilisant le drapeau SA_SIGINFO de sigaction(2), alors les informations ci-dessus sont accessibles via l'objet ucontext_t pointé par le troisième argument du gestionnaire de signaux. Cet objet reflète l'état au moment de la livraison du signal, plutôt que dans le gestionnaire ; par exemple, le masque des signaux bloqués stocké dans cet objet ne contiendra pas le masque des nouveaux signaux bloqués via sigaction(2).
(1.4)
Tous les signaux spécifiés dans act->sa_mask lors de l'enregistrement du gestionnaire avec sigaction(2) sont ajoutés au masque de signaux du thread. Le signal délivré est également ajouté au masque de signaux, sauf si SA_NODEFER a été spécifié lors de l'enregistrement du gestionnaire. Ces signaux sont ainsi bloqués pendant l'exécution du gestionnaire.
(2)
Le noyau construit une trame pour le gestionnaire de signaux sur la pile. Le noyau configure le compteur de programme du thread pour qu'il pointe vers la première instruction de la fonction de gestionnaire de signaux, et configure l'adresse de retour de cette fonction pour qu'elle pointe vers un morceau de code en espace utilisateur connu sous le nom de trampoline de signal (décrit dans sigreturn(2)).
(3)
Le noyau renvoie le contrôle à l'espace utilisateur, où l'exécution commence au début de la fonction de gestionnaire de signaux.
(4)
Lorsque le gestionnaire de signaux retourne, le contrôle est transféré au code du trampoline de signal.
(5)
Le trampoline de signal appelle sigreturn(2), un appel système qui utilise les informations de la trame de pile créée à l'étape 1 pour restaurer le thread à son état avant que le gestionnaire de signaux ne soit appelé. Le masque de signaux du thread et les paramètres de la pile de signaux alternative sont restaurés dans le cadre de cette procédure. À la fin de l'appel à sigreturn(2), le noyau transfère le contrôle à l'espace utilisateur, et le thread reprend son exécution à l'endroit où il a été interrompu par le gestionnaire de signaux.

Notez que si le gestionnaire de signaux ne retourne pas (par exemple, le contrôle est transféré hors du gestionnaire à l'aide de siglongjmp(3), ou le gestionnaire exécute un nouveau programme avec execve(2)), alors la dernière étape n'est pas effectuée. En particulier, dans de tels scénarios, il est de la responsabilité du programmeur de restaurer l'état du masque de signaux (en utilisant sigprocmask(2)), si l'on souhaite débloquer les signaux qui étaient bloqués à l'entrée du gestionnaire de signaux. (Notez que siglongjmp(3) peut ou peut ne pas restaurer le masque de signaux, en fonction de la valeur savesigs spécifiée dans l'appel correspondant à sigsetjmp(3).)

Du point de vue du noyau, l'exécution du code du gestionnaire de signaux est exactement la même que l'exécution de tout autre code en espace utilisateur. C'est-à-dire que le noyau n'enregistre aucune information d'état spéciale indiquant que le thread est actuellement en train d'exécuter un gestionnaire de signaux. Toutes les informations d'état nécessaires sont maintenues dans les registres de l'espace utilisateur et la pile de l'espace utilisateur. La profondeur à laquelle les gestionnaires de signaux imbriqués peuvent être invoqués est donc limitée uniquement par la pile de l'espace utilisateur (et une conception logicielle raisonnable !).

Les signaux SIGKILL et SIGSTOP ne peuvent être interceptés, bloqués ou ignorés.

Jusqu'à Linux 2.2 inclus, le comportement par défaut pour SIGSYS, SIGXCPU, SIGXFSZ, et (sur les architectures autres que SPARC et MIPS) SIGBUS était de terminer le processus (sans vidage de mémoire). (Sur certains autres systèmes UNIX, l'action par défaut pour SIGXCPU et SIGXFSZ est de terminer le processus sans vidage de mémoire.) Linux 2.4 est conforme aux exigences de POSIX.1-2001 pour ces signaux, terminant le processus avec un vidage de mémoire.

SIGEMT n'est pas spécifié dans POSIX.1-2001, mais apparaît néanmoins sur la plupart des autres systèmes UNIX, où son action par défaut est typiquement de terminer le processus avec un vidage de mémoire.

SIGPWR (qui n'est pas spécifié dans POSIX.1-2001) est typiquement ignoré par défaut sur les autres systèmes UNIX où il apparaît.

SIGIO (qui n'est pas spécifié dans POSIX.1-2001) est ignoré par défaut sur plusieurs autres systèmes UNIX.

Semantiques de mise en file d'attente et de livraison pour les signaux standard

Si plusieurs signaux standard sont en attente pour un processus, l'ordre dans lequel les signaux sont livrés n'est pas spécifié.

Les signaux standard ne sont pas mis en file d'attente. Si plusieurs instances d'un signal standard sont générées pendant que ce signal est bloqué, alors une seule instance du signal est marquée comme en attente (et le signal ne sera livré qu'une seule fois lorsqu'il sera débloqué). Dans le cas où un signal standard est déjà en attente, la structure siginfo_t (voir sigaction(2)) associée à ce signal n'est pas écrasée à l'arrivée d'instances ultérieures du même signal. Ainsi, le processus recevra les informations associées à la première instance du signal.

Signaux temps réel

À partir de Linux 2.2, Linux prend en charge les signaux temps réel tels qu'originellement définis dans les extensions temps réel de POSIX.1b (et maintenant inclus dans POSIX.1-2001). La plage des signaux temps réel supportés est définie par les macros SIGRTMIN et SIGRTMAX. POSIX.1-2001 exige qu'une implémentation supporte au moins _POSIX_RTSIG_MAX (8) signaux temps réel.

Le noyau Linux prend en charge une plage de 33 signaux temps réel différents, numérotés de 32 à 64. Cependant, l'implémentation des threads POSIX de glibc utilise en interne deux (pour NPTL) ou trois (pour LinuxThreads) signaux temps réel (voir pthreads(7)), et ajuste la valeur de SIGRTMIN en conséquence (à 34 ou 35). Parce que la plage des signaux temps réel disponibles varie selon l'implémentation des threads de glibc (et cette variation peut survenir à l'exécution en fonction du noyau et de glibc disponibles), et en fait, la plage des signaux temps réel varie selon les systèmes UNIX, les programmes ne doivent jamais faire référence aux signaux temps réel à l'aide de nombres codés en dur, mais doivent toujours faire référence aux signaux temps réel en utilisant la notation SIGRTMIN+n, et inclure des vérifications appropriées (à l'exécution) que SIGRTMIN+n ne dépasse pas SIGRTMAX.

Contrairement aux signaux standard, les signaux temps réel n'ont pas de significations prédéfinies : l'ensemble complet des signaux temps réel peut être utilisé à des fins définies par l'application.

L'action par défaut pour un signal temps réel non géré est de terminer le processus récepteur.

Les signaux temps réel se distinguent par les points suivants :

•
Plusieurs instances de signaux temps réel peuvent être mises en file d'attente. En revanche, si plusieurs instances d'un signal standard sont délivrées pendant que ce signal est actuellement bloqué, une seule instance est mise en file d'attente.
•
Si le signal est envoyé à l'aide de sigqueue(3), une valeur accompagnatrice (un entier ou un pointeur) peut être envoyée avec le signal. Si le processus récepteur établit un gestionnaire pour ce signal en utilisant le drapeau SA_SIGINFO de sigaction(2), alors il peut obtenir ces données via le champ si_value de la structure siginfo_t passée en deuxième argument au gestionnaire. De plus, les champs si_pid et si_uid de cette structure peuvent être utilisés pour obtenir le PID et l'ID utilisateur réel du processus envoyant le signal.
•
Les signaux temps réel sont délivrés dans un ordre garanti. Plusieurs signaux temps réel du même type sont délivrés dans l'ordre où ils ont été envoyés. Si différents signaux temps réel sont envoyés à un processus, ils sont délivrés en commençant par le signal de plus petit numéro. (C'est-à-dire, les signaux de petit numéro ont la priorité la plus élevée.) En revanche, si plusieurs signaux standard sont en attente pour un processus, l'ordre dans lequel ils sont délivrés n'est pas spécifié.

Si des signaux standard et temps réel sont en attente pour un processus, POSIX laisse non spécifié lequel est délivré en premier. Linux, comme de nombreuses autres implémentations, donne la priorité aux signaux standard dans ce cas.

Selon POSIX, une implémentation devrait permettre de mettre en file d'attente au moins _POSIX_SIGQUEUE_MAX (32) signaux temps réel pour un processus. Cependant, Linux fait les choses différemment. Jusqu'à et y compris Linux 2.6.7, Linux impose une limite globale au nombre de signaux temps réel mis en file d'attente pour tous les processus. Cette limite peut être consultée et (avec privilège) modifiée via le fichier /proc/sys/kernel/rtsig-max. Un fichier connexe, /proc/sys/kernel/rtsig-nr, peut être utilisé pour savoir combien de signaux temps réel sont actuellement mis en file d'attente. Dans Linux 2.6.8, ces interfaces /proc ont été remplacées par la limite de ressources RLIMIT_SIGPENDING, qui spécifie une limite par utilisateur pour les signaux mis en file d'attente ; voir setrlimit(2) pour plus de détails.

L'ajout des signaux temps réel a nécessité l'élargissement de la structure de jeu de signaux (sigset_t) de 32 à 64 bits. Par conséquent, divers appels système ont été remplacés par de nouveaux appels système qui supportaient les jeux de signaux plus grands. Les anciens et nouveaux appels système sont les suivants :

Linux 2.0 et antérieur Linux 2.2 et ultérieur
sigaction(2) rt_sigaction(2)
sigpending(2) rt_sigpending(2)
sigprocmask(2) rt_sigprocmask(2)
sigreturn(2) rt_sigreturn(2)
sigsuspend(2) rt_sigsuspend(2)
sigtimedwait(2) rt_sigtimedwait(2)

Interruption des appels système et des fonctions de bibliothèque par les gestionnaires de signaux

Si un gestionnaire de signaux est invoqué pendant qu'un appel système ou un appel de fonction de bibliothèque est bloqué, alors soit :

•
l'appel est automatiquement redémarré après le retour du gestionnaire de signaux ; soit
•
l'appel échoue avec l'erreur EINTR.

Le comportement entre ces deux options dépend de l'interface et du fait que le gestionnaire de signaux ait été établi ou non en utilisant le drapeau SA_RESTART (voir sigaction(2)). Les détails varient selon les systèmes UNIX ; ci-dessous, les détails pour Linux.

Si un appel bloqué à l'une des interfaces suivantes est interrompu par un gestionnaire de signaux, alors l'appel est automatiquement redémarré après le retour du gestionnaire de signaux si le drapeau SA_RESTART a été utilisé ; sinon, l'appel échoue avec l'erreur EINTR :

•
Appels read(2), readv(2), write(2), writev(2), et ioctl(2) sur des périphériques « lents ». Un périphérique « lent » est un périphérique où l'appel d'E/S peut se bloquer indéfiniment, par exemple, un terminal, un pipe ou une socket. Si un appel d'E/S sur un périphérique lent a déjà transféré des données au moment où il est interrompu par un gestionnaire de signaux, alors l'appel retournera un statut de succès (normalement, le nombre d'octets transférés). Notez qu'un disque (local) n'est pas un périphérique lent selon cette définition ; les opérations d'E/S sur les périphériques de disque ne sont pas interrompues par des signaux.
•
open(2), s'il peut se bloquer (par exemple, lors de l'ouverture d'un FIFO ; voir fifo(7)).
•
wait(2), wait3(2), wait4(2), waitid(2), et waitpid(2).
•
Interfaces de sockets : accept(2), connect(2), recv(2), recvfrom(2), recvmmsg(2), recvmsg(2), send(2), sendto(2), et sendmsg(2), à moins qu'un délai d'attente n'ait été défini sur la socket (voir ci-dessous).
•
Interfaces de verrouillage de fichiers : flock(2) et les opérations F_SETLKW et F_OFD_SETLKW de fcntl(2)
•
Interfaces de files d'attente de messages POSIX : mq_receive(3), mq_timedreceive(3), mq_send(3), et mq_timedsend(3).
•

).

Les interfaces suivantes ne sont jamais redémarrées après avoir été interrompues par un gestionnaire de signaux, quelle que soit l'utilisation de SA_RESTART ; elles échouent toujours avec l'erreur EINTR lorsqu'elles sont interrompues par un gestionnaire de signaux :

•
Interfaces de socket "d'entrée", lorsqu'un délai d'attente (SO_RCVTIMEO) a été défini sur le socket à l'aide de setsockopt(2) : accept(2), recv(2), recvfrom(2), recvmmsg(2) (également avec un argument timeout non NULL), et recvmsg(2).
•
Interfaces de socket "de sortie", lorsqu'un délai d'attente (SO_RCVTIMEO) a été défini sur le socket à l'aide de setsockopt(2) : connect(2), send(2), sendto(2), et sendmsg(2).
•
Interfaces utilisées pour attendre des signaux : pause(2), sigsuspend(2), sigtimedwait(2), et sigwaitinfo(2).
•
Interfaces de multiplexage de descripteurs de fichiers : epoll_wait(2), epoll_pwait(2), poll(2), ppoll(2), select(2), et pselect(2).
•
Interfaces IPC System V : msgrcv(2), msgsnd(2), semop(2), et semtimedop(2).
•
Interfaces de veille : clock_nanosleep(2), nanosleep(2), et usleep(3).
•
io_getevents(2).

La fonction sleep(3) n'est jamais redémarrée si elle est interrompue par un gestionnaire, mais retourne un succès : le nombre de secondes restantes à dormir.

Dans certaines circonstances, la fonctionnalité de notification utilisateur de seccomp(2) peut entraîner le redémarrage d'appels système qui ne seraient normalement jamais redémarrés par SA_RESTART ; pour plus de détails, voir seccomp_unotify(2).

Interruption des appels système et des fonctions de bibliothèque par les signaux d'arrêt

Sous Linux, même en l'absence de gestionnaires de signaux, certaines interfaces bloquantes peuvent échouer avec l'erreur EINTR après que le processus a été arrêté par l'un des signaux d'arrêt et ensuite repris via SIGCONT. Ce comportement n'est pas sanctionné par POSIX.1 et ne se produit pas sur d'autres systèmes.

Les interfaces Linux qui présentent ce comportement sont :

•
Interfaces de socket "d'entrée", lorsqu'un délai d'attente (SO_RCVTIMEO) a été défini sur le socket à l'aide de setsockopt(2) : accept(2), recv(2), recvfrom(2), recvmmsg(2) (également avec un argument timeout non NULL), et recvmsg(2).
•
Interfaces de socket "de sortie", lorsqu'un délai d'attente (SO_RCVTIMEO) a été défini sur le socket à l'aide de setsockopt(2) : connect(2), send(2), sendto(2), et sendmsg(2), si un délai d'attente d'envoi (SO_SNDTIMEO) a été défini.
•
epoll_wait(2), epoll_pwait(2).
•
semop(2), semtimedop(2).
•
sigtimedwait(2), sigwaitinfo(2).
•
Linux 3.7 et antérieurs : read(2) à partir d'un descripteur de fichier inotify(7)
•
Linux 2.6.21 et antérieurs : futex(2) FUTEX_WAIT, sem_timedwait(3), sem_wait(3).
•
Linux 2.6.8 et antérieurs : msgrcv(2), msgsnd(2).
•
Linux 2.4 et antérieurs : nanosleep(2).

NORMES

POSIX.1, sauf indication contraire.

NOTES

Pour une discussion sur les fonctions sûres pour les signaux asynchrones, voir signal-safety(7).

Le fichier /proc/pid/task/tid/status contient divers champs qui montrent les signaux que un thread est en train de bloquer (SigBlk), de recevoir (SigCgt), ou d'ignorer (SigIgn). (L'ensemble des signaux reçus ou ignorés sera le même pour tous les threads d'un processus.) D'autres champs montrent l'ensemble des signaux en attente qui sont dirigés vers le thread (SigPnd) ainsi que l'ensemble des signaux en attente qui sont dirigés vers le processus dans son ensemble (ShdPnd). Les champs correspondants dans /proc/pid/status montrent les informations pour le thread principal. Voir proc(5) pour plus de détails.

BOGUES

Il existe six signaux qui peuvent être délivrés à la suite d'une exception matérielle : SIGBUS, SIGEMT, SIGFPE, SIGILL, SIGSEGV, et SIGTRAP. Lequel de ces signaux est délivré, pour une exception matérielle donnée, n'est pas documenté et ne fait pas toujours sens.

Par exemple, un accès mémoire invalide qui provoque la livraison de SIGSEGV sur une architecture de CPU peut provoquer la livraison de SIGBUS sur une autre architecture, ou vice versa.

Pour un autre exemple, l'utilisation de l'instruction int x86 avec un argument interdit (tout nombre autre que 3 ou 128) provoque la livraison de SIGSEGV, même si SIGILL serait plus logique, en raison de la manière dont le CPU signale l'opération interdite au noyau.
