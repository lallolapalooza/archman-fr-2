signalfd(2) Manuel des appels système signalfd(2)

NOM

signalfd - créer un descripteur de fichier pour accepter les signaux

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/signalfd.h>
int signalfd(int fd, const sigset_t *mask, int flags);

DESCRIPTION

signalfd() crée un descripteur de fichier qui peut être utilisé pour accepter les signaux adressés à l'appelant. Ceci offre une alternative à l'utilisation d'un gestionnaire de signaux ou de sigwaitinfo(2), et présente l'avantage que le descripteur de fichier peut être surveillé par select(2), poll(2) et epoll(7).

L'argument mask spécifie l'ensemble des signaux que l'appelant souhaite accepter via le descripteur de fichier. Cet argument est un ensemble de signaux dont le contenu peut être initialisé à l'aide des macros décrites dans sigsetops(3). Normalement, l'ensemble des signaux à recevoir via le descripteur de fichier devrait être bloqué à l'aide de sigprocmask(2), afin d'empêcher les signaux d'être gérés selon leurs dispositions par défaut. Il n'est pas possible de recevoir les signaux SIGKILL ou SIGSTOP via un descripteur de fichier signalfd ; ces signaux sont ignorés silencieusement s'ils sont spécifiés dans mask.

Si l'argument fd est -1, l'appel crée un nouveau descripteur de fichier et associe l'ensemble de signaux spécifié dans mask à ce descripteur de fichier. Si fd n'est pas -1, il doit spécifier un descripteur de fichier signalfd existant et valide, et mask est utilisé pour remplacer l'ensemble de signaux associé à ce descripteur de fichier.

Depuis Linux 2.6.27, les valeurs suivantes peuvent être ORées bit à bit dans flags pour modifier le comportement de signalfd():

SFD_NONBLOCK
Définit le drapeau d'état de fichier O_NONBLOCK sur la description de fichier (voir open(2)) référencée par le nouveau descripteur de fichier. L'utilisation de ce drapeau permet d'éviter des appels supplémentaires à fcntl(2) pour obtenir le même résultat.
SFD_CLOEXEC
Définit le drapeau close-on-exec (FD_CLOEXEC) sur le nouveau descripteur de fichier. Voir la description du drapeau O_CLOEXEC dans open(2) pour connaître les raisons pour lesquelles cela peut être utile.

Jusqu'à Linux 2.6.26, l'argument flags est inutilisé et doit être spécifié comme zéro.

signalfd() retourne un descripteur de fichier qui prend en charge les opérations suivantes :

read(2)
Si un ou plusieurs des signaux spécifiés dans mask sont en attente pour le processus, alors le tampon fourni à read(2) est utilisé pour retourner une ou plusieurs structures signalfd_siginfo (voir ci-dessous) qui décrivent les signaux. La lecture de read(2) retourne des informations pour autant de signaux qu'il y en a en attente et qui tiennent dans le tampon fourni. Le tampon doit être d'au moins sizeof(struct signalfd_siginfo) octets. La valeur de retour de read(2) est le nombre total d'octets lus.
En conséquence de la lecture de read(2), les signaux sont consommés, de sorte qu'ils ne sont plus en attente pour le processus (c'est-à-dire qu'ils ne seront pas capturés par les gestionnaires de signaux et ne pourront pas être acceptés à l'aide de sigwaitinfo(2)).
Si aucun des signaux dans mask n'est en attente pour le processus, alors la lecture de read(2) bloque jusqu'à ce qu'un des signaux dans mask soit généré pour le processus, ou échoue avec l'erreur EAGAIN si le descripteur de fichier a été rendu non bloquant.
poll(2)
select(2)
(et similaires)
Le descripteur de fichier est lisible (l'argument readfds de select(2) ; le drapeau POLLIN de poll(2)) si un ou plusieurs des signaux dans mask sont en attente pour le processus.
Le descripteur de fichier signalfd prend également en charge les autres API de multiplexage de descripteurs de fichiers : pselect(2), ppoll(2) et epoll(7).
close(2)
Lorsque le descripteur de fichier n'est plus nécessaire, il doit être fermé. Lorsque tous les descripteurs de fichiers associés au même objet signalfd ont été fermés, les ressources de l'objet sont libérées par le noyau.

La structure signalfd_siginfo

Le format de la structure signalfd_siginfo (ou des structures) retournée par les lectures (read(2)) d'un descripteur de fichier signalfd est la suivante :


struct signalfd_siginfo {
    uint32_t ssi_signo;    /* Signal number */
    int32_t  ssi_errno;    /* Error number (unused) */
    int32_t  ssi_code;     /* Signal code */
    uint32_t ssi_pid;      /* PID of sender */
    uint32_t ssi_uid;      /* Real UID of sender */
    int32_t  ssi_fd;       /* File descriptor (SIGIO) */
    uint32_t ssi_tid;      /* Kernel timer ID (POSIX timers)
    uint32_t ssi_band;     /* Band event (SIGIO) */
    uint32_t ssi_overrun;  /* POSIX timer overrun count */
    uint32_t ssi_trapno;   /* Trap number that caused signal */
    int32_t  ssi_status;   /* Exit status or signal (SIGCHLD) */
    int32_t  ssi_int;      /* Integer sent by sigqueue(3) */
    uint64_t ssi_ptr;      /* Pointer sent by sigqueue(3) */
    uint64_t ssi_utime;    /* User CPU time consumed (SIGCHLD) */
    uint64_t ssi_stime;    /* System CPU time consumed
                              (SIGCHLD) */
    uint64_t ssi_addr;     /* Address that generated signal
                              (for hardware-generated signals) */
    uint16_t ssi_addr_lsb; /* Least significant bit of address
                              (SIGBUS; since Linux 2.6.37) */
    uint8_t  pad[X];       /* Pad size to 128 bytes (allow for
                              additional fields in the future) */
};

Chacun des champs de cette structure est analogue au champ portant le même nom dans la structure siginfo_t. La structure siginfo_t est décrite dans sigaction(2). Tous les champs de la structure signalfd_siginfo retournée ne seront pas valides pour un signal spécifique ; l'ensemble des champs valides peut être déterminé à partir de la valeur retournée dans le champ ssi_code. Ce champ est l'analogue du champ si_code de siginfo_t ; voir sigaction(2) pour les détails.

sémantique de fork(2)

Après un fork(2), l'enfant hérite d'une copie du descripteur de fichier signalfd. Une lecture (read(2)) à partir du descripteur de fichier dans l'enfant retournera des informations sur les signaux mis en attente pour l'enfant.

Sémantique du passage de descripteurs de fichiers

Comme pour les autres descripteurs de fichiers, les descripteurs de fichier signalfd peuvent être passés à un autre processus via un socket de domaine UNIX (voir unix(7)). Dans le processus récepteur, une lecture (read(2)) à partir du descripteur de fichier reçu retournera des informations sur les signaux mis en attente pour ce processus.

sémantique de execve(2)

Tout comme n'importe quel autre descripteur de fichier, un descripteur de fichier signalfd reste ouvert lors d'un execve(2), à moins qu'il n'ait été marqué pour close-on-exec (voir fcntl(2)). Les signaux qui étaient disponibles pour la lecture avant l' execve(2) restent disponibles pour le programme nouvellement chargé. (Ceci est analogue aux sémantiques traditionnelles des signaux, où un signal bloqué qui est en attente reste en attente lors d'un execve(2).)

Sémantique des threads

Les signaux délivrés à un thread spécifique d'un processus multi-threadé peuvent être capturés par un descripteur de fichier signalfd associé à ce thread. Si un signal est délivré à l'ensemble du processus (c'est-à-dire qu'il n'est pas spécifiquement dirigé vers un thread), il peut être capturé par n'importe quel descripteur de fichier signalfd d'un thread ayant ce signal dans son masque. Cependant, si un thread a créé un descripteur de fichier signalfd, et qu'un autre thread dans le même processus crée un autre descripteur de fichier signalfd qui est configuré pour accepter le même signal, alors le premier descripteur de fichier reçoit le signal.

Si un signal est en attente, la première lecture (read(2)) sur l'un des descripteurs de fichiers signalfd qui acceptent ce signal le consommera.

Lorsque vous utilisez signalfd, il est généralement recommandé de créer le descripteur de fichier dans le thread principal, de bloquer les signaux souhaités dans ce thread principal à l'aide de sigprocmask(2), puis de créer le descripteur de fichier signalfd à l'aide de ces signaux bloqués. Si vous souhaitez que d'autres threads puissent recevoir des signaux, ils peuvent également avoir le signal bloqué dans leur propre masque de signal et lire à partir du même descripteur de fichier signalfd. Notez que les signaux sont consommés par la première lecture (read(2)) qui les récupère, quelle que soit la lecture provenant d'un thread différent.

ERREURS

En cas de succès, signalfd() retourne le nouveau descripteur de fichier. En cas d'échec, il retourne -1 et errno est défini pour indiquer l'erreur.

Les erreurs suivantes peuvent survenir :

EBADF
L'argument fd n'est pas un descripteur de fichier valide.
EINVAL
L'argument fd spécifié n'est pas un descripteur de fichier signalfd, ou l'argument mask est invalide.
EMFILE
Le processus a atteint la limite sur le nombre de descripteurs de fichiers ouverts.
ENFILE
Le système a atteint la limite sur le nombre de descripteurs de fichiers ouverts par le système.
ENOMEM
Mémoire insuffisante pour allouer les ressources nécessaires.

Les erreurs suivantes peuvent également survenir :

EFAULT
L'adresse spécifiée par mask est hors de l'espace d'adressage de l'espace utilisateur.

VERSIONS

signalfd() est disponible depuis le noyau Linux 2.6.22. Le support pour les drapeaux flags (SFD_NONBLOCK et SFD_CLOEXEC) a été ajouté dans le noyau Linux 2.6.27.

CONFORMITÉ

signalfd() est une fonctionnalité spécifique à Linux.

NAME

signalfd - create a file descriptor that collects signals

SYNOPSIS

#include <sys/signalfd.h>
int signalfd(int fd, const sigset_t *mask, int flags);

DESCRIPTION

The signalfd() system call creates a new file descriptor that draws from the set of signals specified by the mask argument. This allows signal handling to be implemented using the I/O event notification mechanism (e.g., poll(2), epoll(7)).

The mask argument is a pointer to a signal set that specifies the signals to be received by the returned file descriptor. These signals must also be blocked by the calling thread using sigprocmask(2) or pthread_sigmask(3); otherwise, the behavior is undefined. If a signal in mask is delivered to the calling thread, the signal will be placed in the buffer associated with the signalfd file descriptor.

The flags argument specifies the behavior of the signalfd file descriptor. The following flags are supported:

SFD_NONBLOCK
Set the fcntl(2) O_NONBLOCK flag on the new file descriptor. That is, open the file description in nonblocking mode. If set, a read(2) from the signalfd file descriptor will return -1 and set errno to EAGAIN if no signals are available to be returned.
SFD_CLOEXEC
Set the fcntl(2) FD_CLOEXEC flag on the new file descriptor. This can be used by the calling process to ensure that the file descriptor is automatically closed after a call to one of the execve(2) family of functions.

If fd is -1, then a new signalfd file descriptor is created. If fd is a valid signalfd file descriptor, then the signal mask and flags are updated for that signalfd file descriptor, and the original fd is returned.

When a signal is delivered to a thread, and that signal is included in the mask associated with a signalfd file descriptor, the signal is consumed and placed into the signalfd's buffer. The signal is not delivered to its default disposition (e.g., termination for SIGTERM) or to any registered signal handler.

A thread can read from the signalfd file descriptor using read(2). Each read(2) call returns a structure of type struct signalfd_siginfo (defined in <sys/signalfd.h>). This structure contains the same information as would be passed to a signal handler registered using sigaction(2) with the SA_SIGINFO flag set.

The fields of struct signalfd_siginfo are:

  • ssi_signo: The signal number.
  • ssi_errno: If the signal was sent with an associated error number (e.g., SIGIO), this field contains that error number. Otherwise, it is 0.
  • ssi_pid: The process ID of the sender (available for real-time signals).
  • ssi_uid: The real UID of the sender (available for real-time signals).
  • ssi_fd: If the signal was sent by eventfd(2) or signalfd(2), this field contains the file descriptor associated with the event.
  • ssi_int: An integer value sent with the signal (available for real-time signals sent using sigqueue(3)).
  • ssi_ptr: A pointer value sent with the signal (available for real-time signals sent using sigqueue(3)).
  • ssi_tid: The thread ID of the sender (available for real-time signals).
  • ssi_band: Event flags (available for SIGIO).
  • ssi_overrun: Timer overrun count (available for timer signals).

A read(2) call will return as many signal information structures as are available, up to the size of the buffer provided. If no signals are available, and the signalfd file descriptor is in nonblocking mode (see SFD_NONBLOCK), read(2) returns -1 and sets errno to EAGAIN. Otherwise, read(2) blocks until a signal is received.

Thread semantics

The semantics of signalfd file descriptors in a multithreaded program mirror the standard semantics for signals. In other words, when a thread reads from a signalfd file descriptor, it will read the signals that are directed to the thread itself and the signals that are directed to the process (i.e., the entire thread group). (A thread will not be able to read signals that are directed to other threads in the process.)

epoll(7) semantics

If a process adds (via epoll_ctl(2)) a signalfd file descriptor to an epoll(7) instance, then epoll_wait(2) returns events only for signals sent to that process. In particular, if the process then uses fork(2) to create a child process, then the child will be able to read(2) signals that are sent to it using the signalfd file descriptor, but epoll_wait(2) will not indicate that the signalfd file descriptor is ready. In this scenario, a possible workaround is that after the fork(2), the child process can close the signalfd file descriptor that it inherited from the parent process and then create another signalfd file descriptor and add it to the epoll instance. Alternatively, the parent and the child could delay creating their (separate) signalfd file descriptors and adding them to the epoll instance until after the call to fork(2).

RETURN VALUE

On success, signalfd() returns a signalfd file descriptor; this is either a new file descriptor (if fd was -1), or fd if fd was a valid signalfd file descriptor. On error, -1 is returned and errno is set to indicate the error.

ERRORS

EBADF
The fd file descriptor is not a valid file descriptor.
EINVAL
fd is not a valid signalfd file descriptor.
EINVAL
flags is invalid; or, in Linux 2.6.26 or earlier, flags is nonzero.
EMFILE
The per-process limit on the number of open file descriptors has been reached.
ENFILE
The system-wide limit on the total number of open files has been reached.
ENODEV
Could not mount (internal) anonymous inode device.
ENOMEM
There was insufficient memory to create a new signalfd file descriptor.

VERSIONS

C library/kernel differences

The underlying Linux system call requires an additional argument, size_t sizemask, which specifies the size of the mask argument. The glibc signalfd() wrapper function does not include this argument, since it provides the required value for the underlying system call.

There are two underlying Linux system calls: signalfd() and the more recent signalfd4(). The former system call does not implement a flags argument. The latter system call implements the flags values described above. Starting with glibc 2.9, the signalfd() wrapper function will use signalfd4() where it is available.

STANDARDS

Linux.

NOTES

A process can create multiple signalfd file descriptors. This makes it possible to accept different signals on different file descriptors. (This may be useful if monitoring the file descriptors using select(2), poll(2), or epoll(7): the arrival of different signals will make different file descriptors ready.) If a signal appears in the mask of more than one of the file descriptors, then occurrences of that signal can be read (once) from any one of the file descriptors.

Attempts to include SIGKILL and SIGSTOP in mask are silently ignored.

The signal mask employed by a signalfd file descriptor can be viewed via the entry for the corresponding file descriptor in the process's /proc/pid/fdinfo directory. See proc(5) for further details.

Limitations

The signalfd mechanism can't be used to receive signals that are synchronously generated, such as the SIGSEGV signal that results from accessing an invalid memory address or the SIGFPE signal that results from an arithmetic error. Such signals can be caught only via signal handler.

As described above, in normal usage one blocks the signals that will be accepted via signalfd(). If spawning a child process to execute a helper program (that does not need the signalfd file descriptor), then, after the call to fork(2), you will normally want to unblock those signals before calling execve(2), so that the helper program can see any signals that it expects to see. Be aware, however, that this won't be possible in the case of a helper program spawned behind the scenes by any library function that the program may call. In such cases, one must fall back to using a traditional signal handler that writes to a file descriptor monitored by select(2), poll(2), or epoll(7).

BUGS

Before Linux 2.6.25, the ssi_ptr and ssi_int fields are not filled in with the data accompanying a signal sent by sigqueue(3).

EXAMPLES

The program below accepts the signals SIGINT and SIGQUIT via a signalfd file descriptor. The program terminates after accepting a SIGQUIT signal. The following shell session demonstrates the use of the program:


$ ./signalfd_demo
^C                   # Control-C generates SIGINT
Got SIGINT
^C
Got SIGINT
^\                    # Control-\ generates SIGQUIT
Got SIGQUIT
$

Program source

#include <err.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/signalfd.h>
#include <sys/types.h>
#include <unistd.h>
int
main(void)
{
    int                      sfd;
    ssize_t                  s;
    sigset_t                 mask;
    struct signalfd_siginfo  fdsi;
    sigemptyset(&mask);
    sigaddset(&mask, SIGINT);
    sigaddset(&mask, SIGQUIT);
    /* Block signals so that they aren't handled
       according to their default dispositions.  */
    if (sigprocmask(SIG_BLOCK, &mask, NULL) == -1)
        err(EXIT_FAILURE, "sigprocmask");
    sfd = signalfd(-1, &mask, 0);
    if (sfd == -1)
        err(EXIT_FAILURE, "signalfd");
    for (;;) {
        s = read(sfd, &fdsi, sizeof(fdsi));
        if (s != sizeof(fdsi))
            err(EXIT_FAILURE, "read");
        if (fdsi.ssi_signo == SIGINT) {
            printf("Got SIGINT\n");
        } else if (fdsi.ssi_signo == SIGQUIT) {
            printf("Got SIGQUIT\n");
            exit(EXIT_SUCCESS);
        } else {
            printf("Read unexpected signal\n");
        }
    }
}
