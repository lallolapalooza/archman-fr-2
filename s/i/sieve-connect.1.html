NOM

sieve-connect - client en ligne de commande managesieve

SYNTAXE

sieve-connect [-s <nom_hôte>] [-p <spécification_port>] [-u <utilisateur>] [a <authzid>]
              [-m <mécanisme_auth>] [-r domaine] [-e script_exécuté]
              [... options_longues ...]
sieve-connect [--localsieve <script>] [--remotesieve <script>]
              [--debug] [--dumptlsinfo]
              [--server <nom_hôte>] [--port <spécification_port>] [--4|--6]
              [--user <id_authentification>] [--authzid <authzid>]
              [--realm <domaine>] [--passwordfd <n>]
              [--clientkey <fichier> --clientcert <fichier>]|[--clientkeycert <fichier>]
              [--notlsverify|--nosslverify]
              [--tlscertfingerprint|--sslcertfingerprint <type_empreinte:empreinte>]
              [--tlscapath <répertoire_ca>]|[--tlscafile <fichier_ca>]
              [--tlshostname <nom_hôte>]
              [--noclearauth] [--noclearchan] [--clearchan]
              [--authmech <mécanisme>]
              [--ignoreserverversion]
              [--upload|--download|--list|--delete|--checkscript|--edit|
               --activate|--deactivate]|[--exec <script>]
              [--help|--man]

DESCRIPTION

sieve-connect est un client pour le protocole "MANAGESIEVE", qui est spécifié par RFC pour la manipulation des scripts "Sieve" dans un dépôt. Plus simplement, sieve-connect vous permet de contrôler vos fichiers de règles de filtrage de courrier sur un serveur de messagerie.

sieve-connect peut être invoqué avec une action depuis la ligne de commande pour faciliter la création de scripts d'actions ponctuelles, il peut être fourni avec un fichier de script ou peut entrer dans une boucle de commandes interactive, où il supporte la complétion par tabulation (si le module Perl de support est disponible) et la navigation de base dans le système de fichiers local à la manière des clients "FTP".

sieve-connect supporte l'utilisation de "TLS" via la commande "STARTTLS", y compris l'authentification par certificats clients. "sieve-connect" supporte également tous les mécanismes "SASL" que votre bibliothèque Authen::SASL::Perl fournit, tant qu'ils ne nécessitent pas de couches de protection SASL.

En mode interactif, une commande "help" est disponible. Les paramètres de commande contenant un "%" sont examinés pour voir s'ils correspondent à %MOTCLÉ, où "MOTCLÉ" est toujours en majuscules. La liste des mots-clés peut être récupérée avec la commande "keywords" et inclut des éléments tels que %DATE, %USER, etc.

OPTIONS

Les noms d'options peuvent être indiqués par le préfixe unique le plus court.

Le nom du script sieve distant par défaut est le même que le nom du script sieve local, donc spécifiez juste celui du local si un seul est nécessaire ; ce fut une décision délibérée d'avoir les valeurs par défaut dans cet ordre, pour faire réfléchir les gens aux noms dans le système de fichiers local. Il n'y a pas de nom de script par défaut.

L'option --debug active les traces diagnostiques. L'option --debugsasl demande des informations de débogage à la bibliothèque SASL. L'option --dumptlsinfo affiche les informations TLS (SSL) du pair ; si elle est spécifiée avec --debug, le certificat PEM du serveur sera fourni comme trace de débogage.

Les options --version affichent les informations de version. Combinée avec --debug, elle affichera les versions des dépendances d'implémentation. Les options --help et --man fournissent des informations d'utilisation.

Le serveur peut être un hôte ou une adresse IP, IPv4 ou IPv6.

Si un serveur est fourni par --server, celui-ci a la priorité. Si cette option n'est pas présente, la variable d'environnement $IMAP_SERVER est vérifiée et, s'il ne s'agit pas d'un chemin de socket Unix, elle est utilisée avec toute spécification de port retirée.

Pour la vérification TLS, c'est le nom par défaut utilisé pour les noms d'hôtes (à la fois SNI et vérification) ; aucune information dérivée du DNS n'est actuellement utilisée comme identifiant de nom d'hôte de confiance. (Ceci est susceptible de changer à l'avenir, compte tenu de DNSSEC). L'option --tlshostname peut être utilisée pour remplacer le nom utilisé pour TLS.

Ensuite, à moins que --nosrv ne soit spécifié, des vérifications sont effectuées pour les enregistrements SRV afin de rechercher un serveur par défaut ; si le module Perl Mozilla::PublicSuffix est disponible, ces vérifications sont effectuées pour chaque niveau du nom d'hôte jusqu'au suffixe public (exclu). Si ce module n'est pas disponible, une heuristique grossière est utilisée : tant qu'il y a trois points dans le nom d'hôte, les enregistrements SRV pour la partie du nom d'hôte après le premier point sont essayés. Si cela est inapproprié, installez Mozilla::PublicSuffix.

Si aucun enregistrement SRV n'est trouvé qui pointe vers un service de protocole 'sieve', 'imaps' ou 'imap', ou si un enregistrement est trouvé qui dit "aucun tel service dans ce domaine" (en ayant une cible de "."), alors le serveur par défaut final est localhost.

Le port peut être n'importe quelle spécification de port Perl, par défaut c'est sieve(4190). Un port d'un enregistrement SRV aura la priorité. La spécification Perl fournit un nom à rechercher dans la base de données des services système (/etc/services) suivi entre parenthèses d'une valeur par défaut à utiliser si le nom n'est pas trouvé. Ainsi, cette valeur par défaut honorera une valeur de 2000 de /etc/services.

Les options --4 ou --6 peuvent être utilisées pour forcer IPv4 ou IPv6.

Par défaut, le serveur est considéré comme un domaine, pour lequel les enregistrements SRV sont recherchés ; utilisez --nosrv pour inhiber la recherche d'enregistrements SRV.

L'option --user sera requise sauf si vous êtes sur un système Unix avec getpwuid() disponible et que votre nom de compte Cyrus correspond à votre nom de compte système. --authmech peut être utilisé pour forcer un mécanisme d'authentification particulier. --authzid peut être utilisé pour demander l'autorisation d'agir en tant qu'ID spécifié. --realm peut être utilisé pour essayer de passer des informations de domaine au mécanisme d'authentification. Si vous souhaitez fournir un mot de passe par programme, utilisez --passwordfd pour indiquer quel descripteur de fichier (généralement 0) le mot de passe peut être lu. Tout jusqu'au retour à la ligne avant EOF est le mot de passe, il peut donc contenir des retours à la ligne intégrés. Ne fournissez pas de mots de passe sur la ligne de commande ou dans l'environnement du processus.

Sauf modification lors de l'installation/empaquetage, par défaut les certificats de l'autorité de certification SSL sont recherchés. La première tentative consiste à essayer, tour à tour, les variables d'environnement $SSL_CERT_DIR & $SSL_CERT_FILE qui sont les noms pris en charge par la bibliothèque OpenSSL et donc souvent pris en charge par les commandes clients. Ensuite, si la commande OpenSSL "version" est disponible et que la sortie "OPENSSLDIR" peut être analysée et que le répertoire "certs" existe dans ce répertoire, alors cet emplacement sera utilisé. Enfin, une liste fixe d'emplacements courants est recherchée et le premier qui existe est utilisé. L'invocation avec --debug montrera plus de détails pendant la phase "setup:".

La priorité par rapport à ces valeurs par défaut est donnée à l'option --tlscafile si elle est fournie, sinon à l'option --tlscapath si elle est fournie. La première est un fichier contenant des certificats, la seconde est un répertoire.

Alternativement, si vous êtes prêt à accepter le risque d'attaques actives de type homme du milieu et que vous ne parvenez pas à faire en sorte que le certificat de l'autorité de certification pertinent soit disponible, vous pouvez réduire votre sécurité avec l'option --notlsverify, également épelée --nosslverify.

Si la vérification est demandée (par défaut) mais que TLS n'est pas disponible, nous ne nous rabattons pas sur des communications claires et non sécurisées. Utilisez --clearchan pour changer cela, ou définissez $SIEVECONNECT_INSECURE_CLEARTEXT_FALLBACK comme non vide dans l'environnement.

Si vous ne souhaitez pas vous fier (uniquement) aux systèmes d'AC, vous pouvez explicitement définir une empreinte de certificat serveur attendue à l'aide de l'option --tlscertfingerprint, également épelée --sslcertfingerprint. Si vous souhaitez ignorer la validation de l'AC, vous devez toujours la désactiver explicitement (voir ci-dessus), car la valeur par défaut consiste à ajouter une contrainte supplémentaire (épinglage, dans le cadre des certificats d'AC valides). Cette option spécifie l'empreinte du certificat X.509 (pas une empreinte de clé publique), telle que fournie par OpenSSL. La première partie de la valeur doit être un nom d'algorithme, tel que "

Pour l'authentification par certificat client SSL, soit --clientkeycert peut être utilisé pour faire référence à un fichier contenant la clé et le certificat, soit les deux options --clientkey et --clientcert doivent pointer vers les fichiers pertinents. Les données doivent être au format fichier PEM.

L'option --noclearauth empêchera l'utilisation des mécanismes d'authentification en clair sauf si ceux-ci sont protégés par TLS. L'option --noclearchan imposera l'utilisation d'une couche de confidentialité ; à l'heure actuelle, seul TLS est pris en charge.

Par défaut, la capacité « VERSION » du serveur sera utilisée pour filtrer les commandes disponibles. Utilisez --ignoreserverversion pour éviter cela.

Les options restantes dénotent des actions. Une seule action, et une seule, peut être présente. Si aucune action n'est présente, le mode interactif est lancé. Si l'action exec est présente, les commandes sont lues depuis le script.

--upload téléversera un script sur le serveur.
--download téléchargera un script depuis le serveur.
--list listera les scripts existants sur le serveur. L'un de ces scripts pourrait être marqué comme ACTIF.
--delete supprimera un script du serveur.
--checkscript demandera au serveur de valider le fichier local fourni.
--edit téléchargera un script, ouvrira un éditeur pour celui-ci, demandera au serveur de vérifier les résultats (et proposera de rééditer si le serveur le rejette) et enfin téléversera le résultat.
--activate marquera le script distant spécifié comme étant le script actif.
--deactivate supprimera la marque active du script distant spécifié sans activer de remplacement.
--exec prendra un nom de fichier contenant des commandes comme s'il était donné dans la boucle normale de lecture-évaluation-impression.

Notez que --check et --edit nécessitent un serveur qui annonce une capacité « VERSION », voir --ignoreserverversion pour outrepasser.

(Si --server n'est pas explicitement indiqué, il peut être fourni à la fin de la ligne de commande pour la compatibilité avec sieveshell.)

EXEMPLES

Se connecter à un serveur Sieve et entrer en mode interactif, lorsque vous avez déjà un ticket Kerberos et que GSSAPI/Kerberos est disponible :

$ sieve-connect --server imap.example.org
Prise en charge de la lecture de ligne activée.
>

Faire de même, mais avec $IMAP_SERVER défini dans l'environnement :

$ sieve-connect
Prise en charge de la lecture de ligne activée.
>

Téléverser un script depuis le répertoire courant, en étant invité à s'authentifier ; notez que le script ne sera pas activé (le téléversement le rend juste disponible, potentiellement après que le serveur l'ait vérifié pour les erreurs) :

$ sieve-connect --server imap.example.org --user fred@example.org \
     --localsieve fred.siv --upload
Mot de passe Sieve/IMAP : [mot de passe ici, non affiché]
$

Voir une grande partie de ce qui se passe sous le capot :

$ sieve-connect --debug
[ extrait 30 lignes environ ]
>

Utiliser --passwordfd pour fournir le mot de passe via stdio au lieu d'argv ou d'environ, où il pourrait apparaître dans les listes de processus ; cet exemple suppose un shell avec des « here-strings », comme zsh ou bash :

$   password='...'
$ sieve-connect --authmech digest-md5 --passwordfd=5 5<<"$password"
Prise en charge de la lecture de ligne activée.
>

ENVIRONNEMENT

$IMAP_SERVER pour un serveur IMAP par défaut.

$USERNAME et $LOGNAME là où la fonction "getpwuid()" n'est pas disponible.

$SSL_CERT_DIR et $SSL_CERT_FILE pour localiser les points d'ancrage de confiance des autorités de certification par défaut.

$SIEVECONNECT_INSECURE_CLEARTEXT_FALLBACK pour préserver l'ancienne mauvaise pratique concernant le repli de TLS.

$VISUAL, sinon $EDITOR, pour l'action d'édition.

BOGUES

Si le protocole d'authentification négocie une couche de protection, les choses vont rapidement mal tourner. Un facteur atténuant est qu'aucune couche de protection ne devrait être négociée sous la protection STARTTLS. Utilisez simplement TLS !

Lors de la liste des scripts, le format est basé sur la sortie brute du serveur, en supposant que le serveur utilise des chaînes entre guillemets pour les noms de scripts. La sortie est simplement renvoyée sous prétexte que c'est une interface assez bonne à passer à un programme. Mais un serveur pourrait choisir d'utiliser des chaînes littérales, même si les résultats sont définis comme séparés par des sauts de ligne, ce qui signifierait que certains sauts de ligne seraient spéciaux. On espère qu'aucun serveur ne fera cela.

Si sieve-connect échoue à se connecter à un serveur IPv4 sans que l'option -4 ne soit explicitement passée, alors vous avez rencontré un problème de portabilité dans la bibliothèque Perl IO::Socket::INET6 et vous devez la mettre à jour.

La plupart des implémentations historiques utilisaient le port 2000 pour ManageSieve. RFC5804 alloue le port 4190. Cet outil utilise une spécification de port de "sieve(4190)" comme port par défaut, ce qui signifie qu'une entrée /etc/services (ou substitut) pour « sieve » en tant que service TCP a la priorité, mais si celle-ci n'est pas présente, supposera 4190 comme défaut. Ce changement signifie que si vous utilisez toujours le port 2000 et que vous n'avez pas d'entrée /etc/services, la mise à jour vers ou au-delà de la version 0.75 de cet outil cassera les invocations qui ne spécifient pas de port. La spécification du port par défaut a été déplacée dans la section configurable par l'utilisateur en haut du script et les administrateurs souhaiteront peut-être remplacer le défaut fourni. Vous pouvez contourner tout ce désordre en publiant des enregistrements SRV, conformément à RFC5804.

Le module Perl Net::DNS ne fournit pas (au moment de la rédaction) un support complet pour les enregistrements SRV priorisés pondérés et je n'ai fait aucun effort pour corriger cela ; quel que soit l'algorithme de tri par défaut pour SRV, c'est ce qui est utilisé pour l'ordonnancement.

Si vous ne spécifiez pas de serveur et n'exportez pas $IMAP_SERVER dans l'environnement, le mécanisme de recherche est plus sûr et plus complet si le module Perl Mozilla::PublicSuffix est installé. En particulier, si votre nom d'hôte est également votre nom de domaine et que le domaine parent est administré par quelqu'un en qui vous n'avez pas confiance, alors vous regretterez de ne pas avoir installé ce module.

Il faut probablement s'asseoir et examiner la RFC finale pour voir si des fonctionnalités manquent encore.

NON-BOGUES

Utilise réellement STARTTLS. Peut gérer des noms de scripts avec des espaces intégrés. L'auteur a besoin d'un accès à un serveur qui gère correctement les caractères de guillemets intégrés pour terminer les tests sur ce point.

HISTORIQUE

sieve-connect a été écrit comme une démonstration pour la liste de diffusion "info-cyrus", le 14/11/2006. C'était un script à action unique et sortie pour des besoins de script. La boucle de commande a été écrite (deux jours) plus tard et délibérément conçue pour être compatible avec sieveshell.

Les versions antérieures à 0.85 ne vérifiaient pas réellement l'identité du certificat du pair, bien que cet auteur ait stupidement cru que c'était le cas. Incompatibilité API/attentes.

Les versions antérieures à 0.88 revenaient par défaut au texte clair en l'absence de STARTTLS si les informations CA étaient configurées localement et que la vérification était demandée (par défaut). Aujourd'hui, cela n'est plus acceptable pour les communications client-serveur ; soit vérifier et exiger TLS, soit ne pas vérifier et revenir au texte clair. C'est la nouvelle politique à venir ; utilisez --clearchan pour autoriser le retour en arrière tout en essayant de vérifier TLS (mais pourquoi ?) ou --notlsverify pour ignorer la vérification. Ou ajoutez $SIEVECONNECT_INSECURE_CLEARTEXT_FALLBACK non vide dans l'environnement pour éviter le `noclearchan-when-verify-enabled` implicite.
