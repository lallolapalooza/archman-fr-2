sane-sharp(5) Accès Facile aux Scanners SANE sane-sharp(5)

NOM

sane-sharp - Backend SANE pour scanners SHARP

DESCRIPTION

La bibliothèque sane-sharp implémente un backend SANE (Scanner Access Now Easy) qui fournit un accès aux scanners SCSI Sharp. Ce backend doit être considéré comme un logiciel de qualité bêta ! Dans son état actuel, il est connu pour fonctionner avec les scanners JX-610 et JX-250. Il est préparé pour une utilisation avec les scanners de la série JX-330, mais nous ne sommes pas en mesure de le tester avec ces appareils.

Pour d'autres scanners Sharp, cela peut fonctionner ou non.

Actuellement, les scanners suivants sont connus pour fonctionner avec ce backend.

Vendeur  ID produit :
-----   -----------
Sharp   JX-610
Sharp   JX-250
Sharp   JX-320
Sharp   JX-330
Sharp   JX-350

Les scanners suivants sont détectés par le backend, mais non testés :

Vendeur  ID produit :
-----   -----------
Sharp   JX-325

NOMS DE PÉRIAUT

Ce backend s'attend à des noms de périphériques de la forme :

spécial

où spécial est le nom du chemin du périphérique spécial correspondant à un scanner SCSI. Le nom du périphérique spécial doit être un périphérique SCSI générique ou un lien symbolique vers un tel périphérique. Sous Linux, un tel nom de périphérique pourrait être /dev/sga ou /dev/sge, par exemple. Voir sane-scsi(5) pour plus de détails.

OPTIONS DE SCAN

--mode
Mode de scan. Les réglages possibles sont : Lineart (scans 1 bit noir et blanc), Gray (scans 8 bits en niveaux de gris), Lineart Color (scans couleur bi-niveaux) et Color (scans couleur 8 bits RGB). La valeur par défaut est Color.
--halftone-pattern
Motif de tramage. Disponible uniquement pour les scanners de la série JX-330. Les réglages possibles sont : none, Dither Bayer, Dither Spiral, Dither Dispersed et Error Diffusion. La valeur par défaut est none.
--source
Source de papier. Cette option n'est disponible que si un chargeur automatique de documents ou un adaptateur de transparence est installé. Les réglages possibles sont : Flatbed, Automatic Document Feeder et Transparency Adapter. Si un chargeur automatique de documents ou un adaptateur de transparence est installé, son utilisation est la sélection par défaut.
--custom-gamma
Gamma personnalisée. Cette option détermine si une table de gamma intégrée ou personnalisée est utilisée. Les réglages possibles sont : yes (active les tables de gamma personnalisées) ou no (active une table de gamma intégrée).
--gamma
Gamma. Cette option n'est disponible que si Custom Gamma est réglé sur no. Les valeurs possibles sont : 1.0 ou 2.2. La valeur par défaut est 2.2. (Le JX-250 et le JX-350 n'ont pas de correction gamma intégrée ; pour ces scanners, une table gamma est téléchargée dans le scanner par le backend.)
--gamma-table
Table gamma. Valeurs autorisées : 0..255 ; 256 nombres doivent être définis. Les valeurs par défaut sont 0, 1, 2, .. 255 (c'est-à-dire, gamma == 1). Cette table n'est utilisée que pour les scans en niveaux de gris.
--red-gamma-table
Table gamma rouge. Valeurs autorisées : 0..255 ; 256 nombres doivent être définis. Les valeurs par défaut sont 0, 1, 2, .. 255 (c'est-à-dire, gamma == 1).
--green-gamma-table
Table gamma verte. Valeurs autorisées : 0..255 ; 256 nombres doivent être définis. Les valeurs par défaut sont 0, 1, 2, .. 255 (c'est-à-dire, gamma == 1).
--blue-gamma-table
Table gamma bleue. Valeurs autorisées : 0..255 ; 256 nombres doivent être définis. Les valeurs par défaut sont 0, 1, 2, .. 255 (c'est-à-dire, gamma == 1).
--resolution
Sélectionne la résolution de l'image numérisée. Valeurs autorisées : 30..600 (JX-330, JX-350 et JX-610) et 30..400 (JX-250). La valeur par défaut est 150.
-l, -t, -x, -y
Fenêtre de scan. Position x du coin supérieur gauche de la zone de scan (-l), position y du coin supérieur gauche de la zone de scan (-t), position x du coin inférieur droit de la zone de scan (-x) et position y du coin inférieur droit de la zone de scan (-y). Les réglages possibles dépendent du modèle de scanner et, pour le JX-250 et le JX-350, également de l'utilisation du chargeur automatique de documents respectivement de l'adaptateur de transparence. Veuillez vous référer aux valeurs autorisées par xscanimage(1) ou xsane(1). Avec scanimage(1), entrez l'une des commandes suivantes afin de voir les valeurs de paramètres autorisées pour la fenêtre de scan :
scanimage -d sharp --source "Automatic Document Feeder" --help

scanimage -d sharp --source Flatbed --help

scanimage -d sharp --source "Transparency Adapter" --help

--edge emphasis
Accentuation des bords. Cette option n'est pas disponible pour le JX-250 et le JX-350. Les réglages possibles sont : None, Middle, Strong et Blur. La valeur par défaut est None.
--threshold
Définit le seuil pour les pixels noirs et blancs en mode lineart. Les valeurs possibles sont 1..255. La valeur par défaut est 128. Cette option n'est disponible qu'en mode de scan lineart.
--threshold-red
Définit le seuil pour la composante rouge d'un pixel en mode de scan couleur lineart. Les valeurs possibles sont 1..255. La valeur par défaut est 128. Cette option n'est disponible qu'en mode de scan couleur lineart.
--threshold-green
Définit le seuil pour la composante verte d'un pixel en mode de scan couleur lineart. Les valeurs possibles sont 1..255. La valeur par défaut est 128. Cette option n'est disponible qu'en mode de scan couleur lineart.
--threshold-blue
Définit le seuil pour la composante bleue d'un pixel en mode de scan couleur lineart. Les valeurs possibles sont 1..255. La valeur par défaut est 128. Cette option n'est disponible qu'en mode de scan couleur lineart.
--lightcolor
Définit la couleur de la source lumineuse. Les valeurs possibles sont white, red, green et blue. La valeur par défaut est white. Cette option n'est disponible qu'en modes de scan lineart color et color.

UTILISATION DU CHARGEUR AUTO

Si un bourrage papier se produit, le capot de maintenance *doit* être ouvert puis fermé, même si le papier bourré peut être retiré sans ouvrir le capot de maintenance. Sinon, l'état d'erreur ne sera pas effacé.

CONFIGURATION

Le contenu du fichier sharp.conf est une liste d'options et de noms de périphériques qui correspondent aux scanners Sharp. Les lignes vides et les lignes commençant par un dièse (#) sont ignorées. Voir sane-scsi(5) pour les détails sur les noms de périphériques.

Les lignes définissant une option commencent par le mot-clé option, suivi du nom de l'option et de sa valeur. Actuellement, trois options sont définies : buffers, buffersize, et readqueue.

Les options définies au début de sharp.conf s'appliquent à tous les périphériques ; les options définies après un nom de périphérique s'appliquent à ce périphérique.

Les options buffers et readqueue ne sont significatives que si le backend a été compilé de manière à ce que pour chaque scan, un second processus soit bifurqué (commutateur USE_FORK dans sharp.c ). Ce processus lit les données de scan à partir du scanner et écrit ces données dans un bloc de mémoire partagée. Le processus parent lit les données de ce bloc de mémoire et les transmet au frontend. Considérations sur les performances

Cette section se concentre sur le problème des arrêts du chariot du scanner pendant une numérisation. Les arrêts du chariot se produisent principalement avec le JX-250. Ce scanner n'a manifestement qu'un petit tampon interne par rapport à sa vitesse. Cela signifie que le backend doit lire les données aussi rapidement que possible à partir du scanner afin d'éviter les arrêts du chariot.

Même le JX-250 ne met que moins de 10 secondes pour une numérisation en niveaux de gris A4 à 400 dpi, ce qui se traduit par un débit de transfert de données supérieur à 1,6 Mo par seconde. Cela signifie que les données produites par le scanner doivent être traitées assez rapidement. En raison du petit tampon interne du JX-250, le backend doit émettre une demande de lecture pour le prochain bloc de données dès que possible après la lecture d'un bloc de données afin d'éviter les arrêts du chariot.

Les arrêts du chariot peuvent être causés par les raisons suivantes :

- trop de « trafic » sur le bus SCSI,
- réponses lentes du backend au scanner,
- un programme qui traite les données acquises par le backend est trop lent.

Trop de « trafic » sur le bus SCSI : cela se produit par exemple si des disques durs sont connectés au même bus SCSI que le scanner, et lorsque le transfert de données depuis/vers ces disques durs nécessite une partie considérable de la bande passante SCSI pendant une numérisation. Si c'est le cas, vous devriez envisager de connecter le scanner à un adaptateur SCSI séparé.

Réponses lentes du backend au scanner : Malheureusement, les systèmes d'exploitation de type UNIX n'ont généralement pas de capacités en temps réel. Ainsi, il n'y a aucune garantie que le backend soit en mesure, en toutes circonstances, de communiquer avec le scanner aussi rapidement que requis. Pour minimiser ce problème, le backend doit être compilé de manière à ce qu'un processus de lecture séparé soit généré : assurez-vous que USE_FORK est défini lors de la compilation de sharp.c. Si les réponses lentes du backend demeurent problématiques, vous pourriez essayer de réduire la charge du système. Même si le backend et le processus de lecture ne nécessitent qu'une petite quantité de temps processeur, d'autres processus en cours peuvent augmenter le délai entre deux tranches de temps allouées au processus de lecture. Sur les systèmes plus lents, un délai accru peut être suffisant pour provoquer un arrêt du chariot avec le JX-250. Pour Linux, l'utilisation du pilote SG version 2.1.36 ou supérieure est recommandée, car il prend en charge, en combinaison avec la bibliothèque SCSI de Sane version 1.0.2, la mise en file d'attente des commandes dans le noyau. Cette implémentation de la mise en file d'attente, combinée à une taille de tampon d'au moins 128 kB, devrait éviter la plupart des arrêts du chariot.

Traitement lent des données numérisées : un exemple de cette situation est l'accès au scanner via un réseau Ethernet 10 MBit, ce qui est nettement trop lent pour transférer les données numérisées aussi rapidement qu'elles sont produites par le scanner. Si vous disposez de suffisamment de mémoire, vous pouvez augmenter option buffers, afin qu'une image entière puisse être stockée dans ces tampons.

Pour savoir si le backend est trop lent ou si le traitement ultérieur des données est trop lent, définissez la variable d'environnement SANE_DEBUG_SHARP à 1. Lorsqu'une numérisation est terminée, le backend écrit la ligne « buffer full conditions: nn » sur stderr. Si nn est zéro, les arrêts du chariot sont causés par des réponses trop lentes du backend ou trop de « trafic » sur le bus SCSI. Si nn est supérieur à zéro, le backend a dû attendre nn fois qu'un tampon soit traité par le frontend. (Veuillez noter que option buffers doit être supérieur à option readqueue pour obtenir une sortie utile pour les « buffer full conditions ».)

FICHIERS

/etc/sane.d/sharp.conf
Le fichier de configuration du backend.
/usr/lib/sane/libsane-sharp.a
La bibliothèque statique implémentant ce backend.
/usr/lib/sane/libsane-sharp.so
La bibliothèque partagée implémentant ce backend (présente sur les systèmes qui prennent en charge le chargement dynamique).

ENVIRONNEMENT

SANE_DEBUG_SHARP
Si la bibliothèque a été compilée avec le support de débogage activé, cette variable d'environnement contrôle le niveau de débogage pour ce backend. Par exemple, une valeur de 128 demande l'affichage de toutes les sorties de débogage. Des niveaux plus bas réduisent la verbosité.

PROBLÈMES CONNUS

1. Mode ADF

Après plusieurs numérisations ADF, le scanner déplace le chariot vers la position de repos et revient à la position de numérisation ADF, avant qu'une numérisation ne commence. Nous ne savons pas si c'est un problème du scanner, ou si c'est un bug du backend. Actuellement, le scanner doit être éteint et rallumé pour arrêter ce comportement gênant.

2. Le niveau de seuil ne fonctionne pas (JX-610 uniquement)

3. La résolution maximale est limitée à 600 dpi (JX-610 pris en charge jusqu'à 1200 dpi) resp. 400 dpi (JX-250)

4. Si le JX-250 est utilisé avec un ADF, la situation suivante peut survenir : Après plusieurs numérisations, le scanner déplace, après avoir chargé une nouvelle feuille de papier, le chariot vers la position de repos, puis de retour à la position utilisée pour les numérisations ADF. Cela se produit pour chaque numérisation, contrairement à l'étalonnage, qui est effectué après 10 numérisations. (Pour l'étalonnage, le chariot est également déplacé vers la position de repos.) Nous ne savons pas si ce comportement est causé par le backend, ou s'il s'agit d'un bug dans le firmware du scanner.

5. L'utilisation d'un adaptateur de transparence (unité de numérisation de film) est prise en charge, mais non testée.
