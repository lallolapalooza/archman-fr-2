NOM

safe - Création et manipulation d'interpréteurs sûrs

SYNTAXE

::safe::interpCreate ?child? ?options...?

::safe::interpInit child ?options...?

::safe::interpConfigure child ?options...?

::safe::interpDelete child

::safe::interpAddToAccessPath child directory

::safe::interpFindInAccessPath child directory

::safe::setLogCmd ?cmd arg...?

OPTIONS

?-accessPath pathList? ?-statics boolean? ?-noStatics? ?-nested boolean? ?-nestedLoadOk? ?-deleteHook script?

DESCRIPTION

Safe Tcl est un mécanisme pour exécuter des scripts Tcl non fiables en toute sécurité et pour fournir un accès médiatisé par ces scripts à des fonctionnalités potentiellement dangereuses.

Safe Tcl garantit que les scripts Tcl non fiables ne peuvent pas nuire à l'application hôte. Il empêche les attaques d'intégrité et de vie privée. Les scripts Tcl non fiables sont empêchés de corrompre l'état de l'application hôtesse ou de l'ordinateur. Les scripts non fiables sont également empêchés de divulguer des informations stockées sur l'ordinateur hôte ou dans l'application hôte à quiconque.

Safe Tcl permet à un interpréteur parent de créer des interpréteurs sûrs et restreints contenant un ensemble d'alias prédéfinis pour les commandes source, load, file, encoding et exit et qui sont capables d'utiliser les mécanismes d'auto-chargement et de paquet.

Aucune connaissance de la structure du système de fichiers n'est divulguée à l'interpréteur sûr, car il n'a accès qu'à un chemin virtualisé contenant des jetons. Lorsque l'interpréteur sûr demande à sourcer un fichier, il utilise le jeton dans le chemin virtuel comme partie du nom du fichier à sourcer ; l'interpréteur parent traduit de manière transparente le jeton en un nom de répertoire réel et exécute l'opération demandée (voir la section SÉCURITÉ ci-dessous pour plus de détails). Différents niveaux de sécurité peuvent être sélectionnés en utilisant les drapeaux optionnels des commandes décrites ci-dessous.

Toutes les commandes fournies dans l'interpréteur parent par Safe Tcl résident dans l'espace de noms safe.

COMMANDES

Les commandes suivantes sont fournies dans l'interpréteur parent :

::safe::interpCreate ?child? ?options...?
Crée un interpréteur sûr, installe les alias décrits dans la section ALIAS et initialise le mécanisme d'auto-chargement et de paquet selon les options fournies. Voir la section OPTIONS ci-dessous pour une description des arguments optionnels. Si l'argument child est omis, un nom sera généré. ::safe::interpCreate retourne toujours le nom de l'interpréteur.

Le nom de l'interpréteur child peut inclure des séparateurs d'espace de noms, mais ne peut pas avoir de séparateurs d'espace de noms en tête ou en queue, ni de caractères deux-points excessifs dans les séparateurs d'espace de noms. Le nom de l'interpréteur est qualifié par rapport à l'espace de noms global ::, et non par rapport à l'espace de noms dans lequel la commande ::safe::interpCreate est évaluée.

::safe::interpInit child ?options...?
Cette commande est similaire à interpCreate sauf qu'elle ne crée pas l'interpréteur sûr. child doit avoir été créé par un autre moyen, comme interp create -safe. Le nom de l'interpréteur child peut inclure des séparateurs d'espace de noms, sous réserve des mêmes restrictions que pour interpCreate.
::safe::interpConfigure child ?options...?
Si aucune option n'est donnée, renvoie les paramètres de toutes les options pour l'interpréteur sûr nommé sous forme de liste d'options et de leurs valeurs actuelles pour ce child. Si un seul argument supplémentaire est fourni, il renverra une liste de 2 éléments nom et valeur où nom est le nom complet de cette option et valeur la valeur actuelle pour cette option et ce child. Si plus de deux arguments supplémentaires sont fournis, il reconfigurera l'interpréteur sûr et changera chacune et seulement les options fournies. Voir la section sur les OPTIONS ci-dessous pour la description des options. Exemple d'utilisation :
# Créer un nouvel interpréteur avec la même configuration que "$i0" :
set i1 [safe::interpCreate {*}[safe::interpConfigure $i0]]
# Obtenir le deleteHook actuel
set dh [safe::interpConfigure $i0  -del]
# Changer (seulement) l'attribut statics loading ok d'un
# interpréteur et son deleteHook (en laissant le reste inchangé) :
safe::interpConfigure $i0  -delete {foo bar} -statics 0
::safe::interpDelete child
Supprime l'interpréteur sûr et nettoie les structures de données correspondantes de l'interpréteur parent. Si un script deleteHook a été spécifié pour cet interpréteur, il est évalué avant la suppression de l'interpréteur, avec le nom de l'interpréteur comme argument supplémentaire.
::safe::interpFindInAccessPath child directory
Cette commande trouve et renvoie le jeton du répertoire réel directory dans le chemin d'accès virtuel actuel de l'interpréteur sûr. Elle génère une erreur si le répertoire n'est pas trouvé. Exemple d'utilisation :
$child eval [list set tk_library \
      [::safe::interpFindInAccessPath $name $tk_library]]
::safe::interpAddToAccessPath child directory
Cette commande ajoute directory au chemin virtuel maintenu pour l'interpréteur sûr dans le parent, et renvoie le jeton qui peut être utilisé dans l'interpréteur sûr pour obtenir l'accès aux fichiers dans ce répertoire. Si le répertoire est déjà dans le chemin virtuel, elle ne renvoie que le jeton sans ajouter à nouveau le répertoire au chemin virtuel. Exemple d'utilisation :
$child eval [list set tk_library \
      [::safe::interpAddToAccessPath $name $tk_library]]
::safe::setLogCmd ?cmd arg...?
Cette commande installe un script qui sera appelé lorsque des événements intéressants du cycle de vie se produiront pour un interpréteur sûr. Lorsqu'elle est appelée sans arguments, elle renvoie le script actuellement installé. Lorsqu'elle est appelée avec un argument, une chaîne vide, le script actuellement installé est supprimé et la journalisation est désactivée. Le script sera appelé avec un argument supplémentaire, une chaîne décrivant l'événement d'intérêt. Le but principal est d'aider au débogage des interpréteurs sûrs. En utilisant cette fonctionnalité, vous pouvez obtenir des messages d'erreur complets tandis que l'interpréteur sûr ne reçoit que des messages d'erreur génériques. Cela empêche un interpréteur sûr de voir des messages concernant des échecs et d'autres événements qui pourraient contenir des informations sensibles telles que de vrais noms de répertoires.

Exemple d'utilisation :

::safe::setLogCmd puts stderr

Ci-dessous se trouve la sortie d'une session d'exemple dans laquelle un interpréteur sûr a tenté de sourcer un fichier non trouvé dans son chemin d'accès virtuel. Notez que l'interpréteur sûr n'a reçu qu'un message d'erreur indiquant que le fichier était introuvable :

NOTICE for child interp10 : Created
NOTICE for child interp10 : Setting accessPath=(/foo/bar) staticsok=1 nestedok=0 deletehook=()
NOTICE for child interp10 : auto_path in interp10 has been set to {$p(:0:)}
ERROR for child interp10 : /foo/bar/init.tcl: no such file or directory

OPTIONS

Les options suivantes sont communes à ::safe::interpCreate, ::safe::interpInit et ::safe::interpConfigure. Toute option peut être abrégée en son nom minimal non ambigu. Les noms d'options ne sont pas sensibles à la casse.

-accessPath directoryList
Cette option définit la liste des répertoires à partir desquels l'interpréteur sûr peut source et load des fichiers. Si cette option n'est pas spécifiée, ou si elle est donnée comme liste vide, l'interpréteur sûr utilisera les mêmes répertoires que son parent pour l'auto-chargement. Voir la section SÉCURITÉ ci-dessous pour plus de détails sur les chemins virtuels, les jetons et le contrôle d'accès.
-statics boolean
Cette option spécifie si l'interpréteur sûr sera autorisé à charger des paquets liés statiquement (

comme load {} Tk). La valeur par défaut est true : les interpréteurs sûrs sont autorisés à charger des paquets liés statiquement.
-noStatics
Cette option est un raccourci pratique pour -statics false et spécifie donc que l'interpréteur sûr ne sera pas autorisé à charger des paquets liés statiquement.
-nested booléen
Cette option spécifie si l'interpréteur sûr sera autorisé à charger des paquets dans ses propres sous-interpréteurs. La valeur par défaut est false : les interpréteurs sûrs ne sont pas autorisés à charger des paquets dans leurs propres sous-interpréteurs.
-nestedLoadOk
Cette option est un raccourci pratique pour -nested true et spécifie donc que l'interpréteur sûr sera autorisé à charger des paquets dans ses propres sous-interpréteurs.
-deleteHook script
Lorsque cette option se voit attribuer un script non vide, elle sera évaluée dans le parent avec le nom de l'interpréteur sûr comme argument supplémentaire juste avant de supprimer effectivement l'interpréteur sûr. Attribuer une valeur vide supprime tout script de rappel de suppression actuellement installé pour cet interpréteur sûr. La valeur par défaut ({}) est de ne pas avoir de rappel de suppression.

ALIASES

Les alias suivants sont fournis dans un interpréteur sûr :

source nomFichier
Le fichier demandé, un fichier source Tcl, est sourcé dans l'interpréteur sûr s'il est trouvé. L'alias source ne peut sourcer que des fichiers provenant de répertoires dans le chemin virtuel de l'interpréteur sûr. L'alias source exige que l'interpréteur sûr utilise l'un des noms de jeton de son chemin virtuel pour désigner le répertoire dans lequel le fichier à sourcer peut être trouvé. Voir la section sur la SÉCURITÉ pour plus de discussion sur les restrictions relatives aux noms de fichiers valides.
load nomFichier
Le fichier demandé, un fichier d'objet partagé, est chargé dynamiquement dans l'interpréteur sûr s'il est trouvé. Le nom du fichier doit contenir un nom de jeton mentionné dans le chemin virtuel de l'interpréteur sûr pour qu'il soit trouvé avec succès. De plus, le fichier d'objet partagé doit contenir un point d'entrée sûr ; voir la page de manuel de la commande load pour plus de détails.
file ?sousCommande arguments...?
L'alias file fournit l'accès à un sous-ensemble sûr des sous-commandes de la commande file ; il n'autorise que les sous-commandes dirname, join, extension, root, tail, pathtype et split. Pour plus de détails sur ce que font ces sous-commandes, voir la page de manuel de la commande file.
encoding ?sousCommande arguments...?
L'alias encoding fournit l'accès à un sous-ensemble sûr des sous-commandes de la commande encoding ; il interdit la définition de l'encodage système, mais autorise toutes les autres sous-commandes, y compris system, pour vérifier l'encodage actuel.
exit
L'interpréteur appelant est supprimé et son calcul est arrêté, mais le processus Tcl dans lequel cet interpréteur existe n'est pas terminé.

SÉCURITÉ

Safe Tcl n'essaie pas d'empêcher complètement les attaques d'ennui et de déni de service. Ces formes d'attaque empêchent l'application ou l'utilisateur d'utiliser temporairement l'ordinateur pour effectuer un travail utile, par exemple en consommant tout le temps CPU disponible ou tout l'espace écran disponible. Ces attaques, bien qu'aggravantes, sont jugées d'une moindre importance générale que les attaques d'intégrité et de confidentialité que Safe Tcl est censé prévenir.

Les commandes disponibles dans un interpréteur sûr, en plus de l'ensemble sûr tel que défini dans la page de manuel interp, sont des alias médiatisés pour source, load, exit, et des sous-ensembles sûrs de file et encoding. L'interpréteur sûr peut également charger du code automatiquement et demander le chargement de paquets.

Étant donné que certaines de ces commandes accèdent au système de fichiers local, il existe un risque de fuite d'informations sur sa structure de répertoires. Pour éviter cela, les commandes qui prennent des noms de fichiers comme arguments dans un interpréteur sûr utilisent des jetons au lieu des noms de répertoires réels. Ces jetons sont traduits en noms de répertoires réels lors d'une demande, par exemple, de sourcer un fichier, qui est médiatisée par l'interpréteur parent. Ce système de chemin virtuel est maintenu dans l'interpréteur parent pour chaque interpréteur sûr créé par ::safe::interpCreate ou initialisé par ::safe::interpInit, et le chemin mappe les jetons accessibles dans l'interpréteur sûr vers des noms de chemins réels sur le système de fichiers, empêchant ainsi les interpréteurs sûrs d'acquérir des connaissances sur la structure du système de fichiers de l'hôte sur lequel l'interpréteur s'exécute. Les seuls noms de fichiers valides pour les alias source et load fournis à l'enfant sont des chemins sous la forme [file join jeton nomFichier] (c'est-à-dire en utilisant les formats de chemin de fichier natifs : jeton/nomFichier sur Unix et jeton\nomFichier sur Windows), où jeton représente l'un des répertoires de la liste accessPath et nomFichier est un fichier dans ce répertoire (aucun accès aux sous-répertoires n'est autorisé).

Lorsqu'un jeton est utilisé dans un interpréteur sûr dans une demande pour sourcer ou charger un fichier, le jeton est vérifié et traduit en un nom de chemin réel, et le fichier à sourcer ou charger est localisé sur le système de fichiers. L'interpréteur sûr n'acquiert jamais la connaissance du nom de chemin réel sous lequel le fichier est stocké sur le système de fichiers.

Pour empêcher davantage les fuites d'informations potentielles de fichiers sensibles inclus accidentellement dans l'ensemble des fichiers qui peuvent être sourcés par un interpréteur sûr, l'alias source restreint l'accès aux fichiers répondant aux contraintes suivantes : le nom du fichier doit faire quatorze caractères ou moins, ne doit pas contenir plus d'un point (« . »), doit se terminer par l'extension (« .tcl ») ou être nommé (« tclIndex »).

Chaque élément de la liste de chemins d'accès initiale se verra attribuer un jeton qui sera défini dans auto_path de l'enfant et le premier élément de cette liste sera défini comme tcl_library pour cet enfant.

Si l'argument accessPath n'est pas donné ou est une liste vide, le comportement par défaut est de laisser l'enfant accéder aux mêmes paquets que le parent y a accès (ou pour être plus précis : uniquement aux paquets écrits en Tcl (qui, par définition, ne peuvent pas être dangereux car ils s'exécutent dans l'interpréteur enfant) et aux extensions C qui fournissent un point d'entrée _SafeInit). À cette fin, le auto_path du parent sera utilisé pour construire le chemin d'accès de l'enfant. Afin que l'enfant charge avec succès les fichiers de la bibliothèque Tcl (qui incluent le mécanisme d'auto-chargement lui-même), tcl_library sera ajouté ou déplacé en première position si nécessaire, dans le chemin d'accès de l'enfant, de sorte que le tcl_library de l'enfant sera le même que celui du parent (son chemin réel restera néanmoins invisible pour l'enfant). Afin que l'auto-chargement fonctionne de la même manière pour l'enfant et le parent dans ce cas par défaut, les sous-répertoires de premier niveau de chaque répertoire dans l'auto_path du parent seront également ajoutés (s'ils ne sont pas déjà inclus) au chemin d'accès de l'enfant. Vous pouvez toujours spécifier un chemin plus restrictif pour lequel les sous-répertoires ne seront jamais recherchés en spécifiant explicitement votre liste de répertoires avec le drapeau -accessPath au lieu de vous fier à ce mécanisme par défaut.

Lorsque accessPath est modifié après la première création ou initialisation (c'est-à-dire via interpConfigure -accessPath liste), un auto_reset est automatiquement évalué dans l'interpréteur sûr pour synchroniser son auto_index avec la nouvelle liste de jetons.
