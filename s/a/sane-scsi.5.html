sane-scsi(5) SANE Scanner Access Now Easy sane-scsi(5)

NOM

sane-scsi - Conseils sur les adaptateurs SCSI pour les scanners

DESCRIPTION

Cette page de manuel contient divers conseils et astuces spécifiques au système d'exploitation sur la manière de faire fonctionner les scanners avec une interface SCSI.

INFORMATIONS GÉNÉRALES

Pour les scanners dotés d'une interface SCSI, il peut être nécessaire de modifier le fichier de configuration du backend approprié avant d'utiliser SANE pour la première fois. Pour la plupart des systèmes, le fichier de configuration doit lister le nom du périphérique SCSI générique auquel le scanner est connecté (par exemple, sous Linux, /dev/sg4 ou /dev/sge est un tel périphérique SCSI générique). Il est d'usage de créer un lien symbolique de /dev/scanner vers le périphérique SCSI générique auquel le scanner est connecté. Dans ce cas, le fichier de configuration liste simplement la ligne /dev/scanner. Pour une description détaillée du fichier de configuration de chaque backend, veuillez vous référer à la page de manuel du backend concerné (par exemple, sane-epson(5) pour les scanners Epson, sane-hp(5) pour les scanners HP, etc.).

Pour certains systèmes d'exploitation (par exemple, Linux et OS/2), il existe une autre manière de spécifier les périphériques de scanner. Cette méthode alternative permet d'identifier les scanners par la chaîne de nom de fournisseur et de modèle SCSI et/ou par l'adresse du périphérique SCSI (composée du numéro de bus, du numéro de canal, de l'ID et du numéro d'unité logique). La syntaxe pour spécifier un scanner de cette manière est :

scsi FOURNISSEUR MODELE TYPE BUS CANAL ID LUN

où FOURNISSEUR est la chaîne de nom de fournisseur SCSI, MODELE est la chaîne de nom de modèle SCSI, TYPE est la chaîne de type de périphérique SCSI, BUS est le numéro de bus SCSI (appelé "host" dans /proc/scsi/scsi), CANAL est le numéro de canal SCSI, ID est l'ID SCSI, et LUN est le numéro d'unité logique du périphérique scanner. Les deux premiers champs sont des chaînes qui doivent être entourées de guillemets doubles si elles contiennent des espaces. Les quatre champs restants sont des nombres entiers non négatifs. Les valeurs correctes pour ces champs peuvent être trouvées en utilisant des outils spécifiques au système d'exploitation, par exemple, pour Linux en examinant la sortie de la commande cat /proc/scsi/scsi. Pour simplifier la configuration, la valeur d'un champ peut être remplacée par un symbole astérisque (``*''). Un astérisque a pour effet que toute valeur est autorisée pour ce champ particulier. Cela peut avoir pour effet qu'une seule ligne scsi corresponde à plusieurs périphériques. Lorsque cela se produit, chaque périphérique correspondant sera interrogé par le backend un par un et enregistré si le backend pense qu'il s'agit d'un périphérique compatible. Par exemple, la ligne

scsi MUSTEK MFS-06000CX Scanner 0 00 03 00

attacherait le scanner SCSI Mustek avec l'entrée /proc/scsi/scsi suivante :

Host: scsi0 Channel: 00 Id: 03 Lun: 00
  Vendor: MUSTEK   Model: MFS-06000CX Rev: 4.04
  Type:   Scanner  ANSI SCSI revision: 0

Généralement, il suffit d'utiliser uniquement les chaînes de fournisseur et de modèle, voire seulement la chaîne de fournisseur. L'exemple suivant

scsi MUSTEK * * * * * *

aurait pour effet que tous les périphériques SCSI du système dont la chaîne de fournisseur est MUSTEK seraient interrogés et reconnus par le backend.

Si le reste d'une chaîne scsi ne contient que des astérisques, les astérisques peuvent être omis. Par exemple, la ligne suivante est équivalente à celle spécifiée précédemment :

scsi MUSTEK

Sur certaines plateformes (par exemple, OpenStep), les noms de périphériques SANE prennent une forme spéciale. Ceci est expliqué ci-dessous dans la section spécifique à la plateforme concernée.

Lors de l'utilisation d'un scanner SCSI, assurez-vous que la permission d'accès au périphérique SCSI générique est correctement définie. Nous recommandons d'ajouter un groupe "scanner" à /etc/group qui contient tous les utilisateurs devant avoir accès au scanner. La permission du périphérique doit alors être définie pour autoriser l'accès en lecture et écriture au groupe. Par exemple, si le scanner se trouve sur le périphérique SCSI générique /dev/sg0, les deux commandes suivantes définiraient correctement la permission :

$ chgrp scanner /dev/sg0
$ chmod 660 /dev/sg0

Lorsque votre système utilise le système de fichiers de périphériques (devfs), vous devez éditer /etc/devfs/perms. Vous y recherchez la ligne

REGISTER ^sg[^/]* PERMISSIONS root.root 0600

et ajoutez une nouvelle ligne (par exemple, pour changer les permissions de sg4) :

REGISTER ^sg4 PERMISSIONS root.scanner 0660

INFORMATIONS FREEBSD

La configuration automatique utilisant les lignes "scsi *" dans les fichiers de configuration ne fonctionne que si l'utilisateur exécutant le frontend a un accès en lecture/écriture à /dev/xpt0. Sinon, vous pouvez également définir un lien /dev/scanner vers le périphérique /dev/uk approprié.

Adaptec AHA1542CF
Rapporté comme fonctionnant bien sous FreeBSD 2.2.2R avec le pilote aha.
Adaptec 2940
Rapporté comme fonctionnant bien sous FreeBSD 2.2.2.
Adaptec 1522
Le scanner est interrogé correctement mais toute tentative d'y accéder *bloque* l'ensemble du système. Il semble que quelque chose désactive les interruptions puis ne les réactive pas, ce qui ressemble à un bug dans le pilote FreeBSD aic.
Adaptec 1505
Fonctionne sur FreeBSD 2.2.5R et 3.0 en utilisant le pilote aic, à condition que la prise en charge Plug-and-Play soit désactivée sur la carte. S'il n'y a pas de périphériques uk, exécutez simplement sh MAKEDEV uk0 dans le répertoire /dev. Le scanner devrait alors être accessible en tant que /dev/uk0 s'il a été interrogé lors du démarrage.
Tekram DC390
Rapporté comme fonctionnant bien sous FreeBSD 2.2.2R avec le pilote amd.

INFORMATIONS LINUX

Tout d'abord, assurez-vous que votre noyau dispose de la prise en charge générique SCSI activée. Dans make xconfig, cela apparaît sous ``SCSI support->SCSI generic support''.

Pour minimiser les temps de numérisation, il est fortement recommandé d'utiliser une grande taille de tampon pour le pilote SCSI générique. À partir de la version 2.0 du pilote SG, la taille maximale du tampon peut être modifiée au moment de l'exécution du programme, et il n'y a aucune restriction de taille. Cette version du pilote fait partie des noyaux Linux à partir de la version 2.2.7. Si le nouveau pilote SG est disponible, certains backends (par exemple, sane-umax(5), sane-mustek(5), sane-sharp(5)) demandent automatiquement des tampons SCSI plus grands. Si un backend ne demande pas automatiquement un tampon SCSI plus grand, définissez la variable d'environnement SANE_SG_BUFFERSIZE à la taille de tampon souhaitée en octets. Il n'est pas recommandé d'utiliser plus de 1 Mo, car pour les grandes valeurs, la probabilité augmente que le pilote SG ne puisse pas allouer les tampons nécessaires. Pour les cartes ISA, même 1 Mo pourrait être une valeur trop importante. Pour une discussion détaillée du pilote SCSI SG Linux, voir : https://tldp.org/HOWTO/SCSI-Generic-HOWTO.

Pour les noyaux Linux avant la version 2.2.7, la taille du tampon est de seulement 32 Ko. Cela fonctionne, mais pour de nombreux scanners moins chers, cela rend la numérisation environ quatre fois plus lente que lorsqu'on utilise une taille de 127 Ko. Linux définit la taille de ce tampon par la macro SG_BIG_BUFF dans le fichier d'en-tête /usr/include/scsi/sg.h. À moins qu'un système ne manque gravement de mémoire, il est recommandé d'augmenter cette valeur à la valeur légale maximale de 128*1024-512=130560 octets. Après avoir modifié cette valeur, il est nécessaire de recompiler à la fois le noyau (ou le module générique SCSI) et les backends SCSI. Gardez à l'esprit que cela n'est nécessaire qu'avec les anciens noyaux Linux.

Un problème courant avec les scanners SCSI est quoi faire lorsque vous avez démarré le système alors que le scanner était éteint. Dans ce cas, le scanner ne sera pas reconnu par le noyau et SANE ne pourra pas y accéder. Heureusement, Linux fournit un mécanisme simple pour interroger un périphérique SCSI à la demande. Supposons que vous ayez un scanner connecté au bus SCSI 2 et que le scanner ait un ID SCSI de 5. Lorsque le système est en cours d'exécution et que le scanner est allumé, vous pouvez émettre la commande :

echo "scsi add-single-device 2 0 5 0" > /proc/scsi/scsi

et le noyau interrogera et reconnaîtra votre scanner (cela doit être fait en tant que root). C'est

possible de supprimer dynamiquement un périphérique SCSI en utilisant la commande ``remove-single-device''. Pour plus de détails, veuillez vous référer au SCSI-2.4-HOWTO.

Les scanners sont connus pour fonctionner avec les adaptateurs SCSI suivants sous Linux. Cette liste n'est pas exhaustive, généralement tout adaptateur SCSI pris en charge par Linux devrait fonctionner.

Adaptateurs SCSI Acard/Advance
Certaines anciennes versions du pilote du noyau (atp870u.c) coupent les informations d'interrogation. Par conséquent, le scanner ne pouvait pas être détecté correctement. Utilisez un noyau récent.
Adaptec AHA-1505/AHA-1542/AHA-2940
Signalé comme fonctionnant correctement avec Linux depuis la v2.0. Si vous rencontrez des blocages du noyau ou d'autres comportements inattendus, obtenez le dernier noyau Linux (2.2.17 semble fonctionner) ou réduisez la taille du tampon SCSI à 32 Ko.
ASUS SC200
Signalé comme fonctionnant correctement avec Linux v2.0.
BusLogic BT958
Pour configurer la carte BusLogic, vous devrez peut-être suivre ces instructions (contribuées par Jeremy <jeremy@xxedgexx.com>) : Lors du démarrage, lorsque votre adaptateur BusLogic est en cours d'initialisation, appuyez sur Ctrl-B pour accéder à la configuration de votre adaptateur BusLogic. Choisissez l'adresse où se trouve votre BusLogic contenant votre scanner. Choisissez ``SCSI Device Configuration''. Choisissez ``Scan SCSI Bus''. Choisissez l'ID SCSI qui contient votre scanner, puis choisissez ``View/Modify SCSI configuration''. Changez ``Negotiation'' en ``async'' et changez ``Disconnect'' en ``off''. Appuyez sur Échap, enregistrez, et appuyez à nouveau sur Échap jusqu'à ce qu'on vous demande de redémarrer.
Carte SCSI ISA NCR/Symbios 53c400/53c400a ou Domex DTC3181E/L/LE (DTCT436/436P)
Cette carte est fournie par Mustek (et d'autres fournisseurs). Elle est prise en charge depuis Linux 2.2. Les cartes SCSI sont prises en charge par le module g_NCR5380. Il est nécessaire d'indiquer au noyau le port d'E/S et le type de carte. Exemple pour un 53c400a : modprobe g_NCR5380 ncr_addr=0x280 ncr_53c400a=1 . Une fois que le noyau détecte la carte, elle devrait fonctionner correctement. Cependant, même si elle devrait fonctionner, ne vous attendez pas à de bonnes performances de cette carte - elle n'a pas de ligne d'interruption et donc, pendant qu'un scan est en cours, le système devient presque inutilisable. Vous pouvez modifier les valeurs des macros USLEEP dans drivers/scsi/g_NCR5380.c. Une documentation se trouve dans ce fichier et dans NCR5380.c.
NCR/Symbios 810
Pour certains scanners, il peut être nécessaire de désactiver la déconnexion/reconnexion. Pour ce faire, utilisez l'option ncr53c8xx="disc:n". Certaines personnes ont signalé que leur scanner ne fonctionnait qu'avec le pilote 53c7,8xx, pas le ncr53c8xx. Essayez les deux si vous avez des problèmes.
Pour les noyaux Linux antérieurs à 2.0.33, il peut être nécessaire d'augmenter le délai d'attente SCSI. Le délai d'attente par défaut pour les noyaux Linux antérieurs à 2.0.33 est de 10 secondes, ce qui est beaucoup trop court lors de la numérisation d'une grande zone. Si vous recevez des messages de la forme ``restart (ncr dead ?)'' dans votre fichier /var/log/messages ou sur la console système, c'est une indication que le délai d'attente est trop court. Dans ce cas, trouvez la ligne ``if (np->latetime>10)'' dans le fichier ncr53c8xx.c (normalement dans le répertoire /usr/src/linux/drivers/scsi) et changez la constante 10 en, disons, 60 (une minute). Ensuite, reconstruisez le noyau/module et réessayez.
Tekram DC315
Le pilote peut être téléchargé à partir de http://www.garloff.de/kurt/linux/dc395/. Pour certains scanners plus anciens, il peut être nécessaire de désactiver toutes les fonctionnalités avancées en utilisant par exemple modprobe dc395x_trm dc395x_trm=7,5,1,32.
Tekram DC390
La version 1.11 du pilote Tekram semble fonctionner correctement la plupart du temps, sauf que le scan ne se termine pas correctement (il provoque un délai d'attente SCSI après 10 minutes). Le pilote générique AM53C974 semble également fonctionner correctement et ne souffre pas des problèmes de délai d'attente.

INFORMATIONS SOLARIS, OPENSTEP ET NEXTSTEP

Sous Solaris, OpenStep et NeXTStep, le nom de périphérique SCSI générique fait référence à un bus SCSI, et non à un périphérique individuel. Par exemple, /dev/sg0 fait référence au premier bus SCSI. Pour indiquer à SANE quel périphérique utiliser, ajoutez le caractère 'a'+target-id au nom de périphérique spécial. Par exemple, le périphérique SCSI connecté au premier contrôleur SCSI et avec l'ID cible 0 serait appelé /dev/sg0a, et le périphérique avec l'ID cible 1 sur le même bus serait appelé /dev/sg0b, et ainsi de suite.

ENVIRONNEMENT

SANE_DEBUG_SANEI_SCSI
Si la bibliothèque a été compilée avec le support de débogage activé, cette variable d'environnement contrôle le niveau de débogage pour le sous-système d'E/S SCSI générique. Par exemple, une valeur de 128 demande l'affichage de toutes les sorties de débogage par le backend. Une valeur de 255 affiche également les messages du noyau provenant du sous-système SCSI (lorsqu'ils sont disponibles). Des niveaux plus bas réduisent la verbosité.
SANE_SCSICMD_TIMEOUT
définit la valeur du délai d'attente pour les commandes SCSI en secondes. Il ne devrait être nécessaire de remplacer la valeur par défaut de 120 secondes que pour les scanners très lents.
