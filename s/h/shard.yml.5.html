NOM

shard.yml - métadonnées pour les projets gérés par shards(1)

DESCRIPTION

Le fichier shard.yml est un fichier YAML contenant des métadonnées sur un projet géré par shards, appelé un shard. Il doit contenir au moins les attributs name et version, ainsi que des attributs supplémentaires optionnels.

Les bibliothèques et les applications bénéficieront de shard.yml.

Les métadonnées des bibliothèques sont censées contenir plus d'informations (par exemple, la liste des auteurs, la description, la licence) que les applications qui peuvent seulement avoir un nom, une version et des dépendances.

FORMAT

Le fichier doit s'appeler shard.yml et être un fichier YAML valide avec un encodage UTF-8. Il ne doit pas contenir d'attributs dupliqués dans aucune carte. Il doit utiliser une indentation de 2 espaces. Il ne doit pas utiliser de fonctionnalités YAML avancées, seulement des mappages simples, des séquences et des chaînes de caractères (Schéma Failsafe).

ATTRIBUTS REQUIS

name

Le nom du projet (chaîne de caractères, requis).
•Il doit être unique.
•Il doit faire 50 caractères ou moins.
•Il doit être en minuscules (a-z).
•Il ne doit pas contenir crystal.
•Il peut contenir des chiffres (0-9) mais ne doit pas commencer par un.
•Il peut contenir des tirets bas ou des tirets, mais ne doit pas commencer/finir par l'un d'eux.
•Il ne doit pas contenir de tirets bas ou de tirets consécutifs.

Exemples : minitest, mysql2, battery-horse.

version

Le numéro de version du projet (chaîne de caractères, requis).
•Il doit contenir des chiffres.
•Il peut contenir des points et des tirets, mais pas consécutifs.
•Il peut contenir une lettre pour en faire une 'pré-version'.

Exemples : 1.2.3, 2.0.0.1, 1.0.0.alpha 2.0.0-rc1 ou 2016.09.

Bien que Shards ne l'impose pas, il est fortement recommandé de suivre un schéma de versionnement rationnel comme Semantic Versioning http://semver.org/ ou Calendar Versioning http://calver.org/.

ATTRIBUTS OPTIONNELS

authors

Une liste d'auteurs, ainsi que leur adresse e-mail de contact (optionnel) (séquence de chaînes de caractères).
•Chaque auteur doit avoir un nom.
•Chaque auteur peut avoir une adresse e-mail, entre des crochets (caractères < et >).

Exemple :

authors:
- Ary
- Julien Portalier <julien@example.org>

crystal

Une restriction pour indiquer quelles sont les versions de crystal prises en charge. Cela exprimera généralement des contraintes de borne inférieure et supérieure (chaîne de caractères, recommandé).

Lors de la résolution des dépendances, ces informations ne sont pas utilisées. Après que les dépendances ont été déterminées, shards vérifie qu'elles sont toutes censées fonctionner avec la version actuelle de crystal. Sinon, un avertissement apparaît pour les dépendances concernées. Les versions résolues sont installées et peuvent être utilisées à vos propres risques.

Les valeurs valides sont pour la plupart les mêmes que pour dependencies.version :

•Un numéro de version précédé d'un opérateur : <, <=, >, >=, != ou ~>.
•Juste "*" si n'importe quelle version convient (c'est la valeur par défaut si non spécifié).
•Plusieurs exigences peuvent être séparées par des virgules.

Il existe un comportement spécial hérité (son utilisation est déconseillée) lorsqu'un simple numéro de version est utilisé comme valeur : il fonctionne exactement comme une vérification >= : x.y.z est interprété comme ">= x.y.z"

Vous êtes invité à spécifier également la borne supérieure pour qu'elle soit inférieure à la prochaine version majeure (future) de Crystal, car il n'y a aucune garantie qu'elle ne cassera pas votre bibliothèque.

Exemple :

crystal: ">= 0.35, < 2.0"

dependencies

Une liste des dépendances requises (mappage).

Chaque dépendance commence par le nom de la dépendance en tant que clé (chaîne de caractères) puis une liste d'attributs (mappage) qui dépendent du type de résolveur.

Exemple :

dependencies:
  minitest:
    github: ysbaddaden/minitest.cr
    version: 0.1.0

development_dependencies

Une liste de dépendances requises pour travailler sur le projet, mais pas nécessaires pour construire et exécuter le projet (mappage).

Elles seront installées pour le projet principal ou la bibliothèque elle-même. Lorsque la bibliothèque est installée comme dépendance pour un autre projet, les dépendances de développement ne seront jamais installées.

Les dépendances de développement suivent le même schéma que les dépendances.

Exemple :

development_dependencies:
  minitest:
    github: ysbaddaden/minitest.cr
    version: ~> 0.1.3

description

Une description du projet sur une seule ligne (chaîne de caractères, recommandée).

documentation

L'URL d'un site web fournissant la documentation du projet pour une consultation en ligne (chaîne de caractères).

executables

Une liste d'exécutables à installer (séquence).

Les exécutables peuvent être de tout type ou langue (par exemple, shell, binaire, ruby), doivent exister dans le dossier bin du Shard, et avoir le bit exécutable activé (sur les plateformes POSIX). Lorsqu'ils sont installés comme dépendance pour un autre projet, les exécutables seront copiés dans le dossier bin de ce projet.

Les exécutables sont toujours installés en dernier, après l'exécution du script postinstall, afin que les bibliothèques puissent construire les exécutables lorsqu'ils sont installés par Shards. L'installation peut être désactivée en passant le drapeau --skip-executables.

Exemple :

executables:
- micrate
- icr

homepage

L'URL de la page d'accueil du projet (chaîne de caractères).

libraries

Une liste de bibliothèques partagées auxquelles le shard tente de se lier (mappage).

Ce champ est purement informatif. Il sert de moyen canonique pour découvrir les dépendances non Crystal dans les shards, tant pour les outils que pour les humains.

Un shard ne doit lister que les bibliothèques auxquelles il se lie directement, il ne doit pas inclure les bibliothèques qui ne sont référencées que par des dépendances. Il doit inclure toutes les bibliothèques auxquelles il se lie directement, qu'une dépendance le fasse aussi ou non.

Il doit mapper depuis le soname sans extension, chemin ou version, par exemple libsqlite3 pour /usr/lib/libsqlite3.so.0.8.6, vers une contrainte de version.

La contrainte de version a le format suivant :

•Il peut s'agir d'un numéro de version.
•Il peut être "*" si n'importe quelle version convient.
•Le numéro de version peut être précédé d'un opérateur : <, <=, >, >=, != ou ~>.
libraries:
  libQt5Gui: "*"
  libQt5Help: "~> 5.7"
  libQtBus: ">= 4.8"

license

Une expression de licence SPDX https://spdx.github.io/spdx-spec/v3.0.1/annexes/spdx-license-expressions/ ou une URL vers un fichier de licence (chaîne de caractères, recommandée).

L'OSI publie une liste https://opensource.org/licenses-old/category de licences open source et leurs identifiants SPDX correspondants.

Exemples : Apache-2.0, GPL-3.0-or-later, Apache-2.0 OR MIT, Apache-2.0 WITH Swift-exception, https://example.com/LICENSE.

repository

L'URL du dépôt canonique du projet (chaîne de caractères, recommandée).

L'URL doit être compatible avec les outils VCS typiques sans modi

scripts

Scripts à exécuter. Seul postinstall est pris en charge.

Shards peut exécuter des scripts automatiquement après certaines actions. Les scripts eux-mêmes ne sont que des commandes shell.

postinstall

Le hook postinstall d'une dépendance sera exécuté chaque fois que cette dépendance est installée ou mise à niveau dans un projet qui l'exige. Cela peut être utilisé pour compiler une bibliothèque C, pour construire des outils pour aider à travailler sur le projet, ou tout autre chose.

Le script sera exécuté depuis le répertoire d'installation de la dépendance, par exemple lib/foo pour un Shard nommé foo.

Exemple :

scripts:
  postinstall: cd src/libfoo && make

targets

Une liste de cibles à construire (mapping).

Chaque cible commence par le nom de la cible comme clé (chaîne de caractères), puis une liste d'attributs (mapping). Le nom de la cible est le nom du binaire construit, créé dans le dossier bin du projet.

Exemple :

targets:
  server:
    main: src/server/cli.cr
  worker:
    main: src/worker.cr

L'exemple ci-dessus construira bin/server à partir de src/server/cli.cr et bin/worker à partir de src/worker.cr.

main

Un chemin vers le fichier source à compiler (chaîne de caractères).

ATTRIBUTS DES DÉPENDANCES

Chaque dépendance nécessite au moins un attribut qui définit le résolveur pour cette dépendance. Il peut s'agir de path, git, github, gitlab, bitbucket, codeberg.

path

Un chemin local (chaîne de caractères).

La bibliothèque sera installée sous forme de lien symbolique vers le chemin local. L'attribut version n'est pas requis mais sera utilisé s'il est présent pour valider la dépendance.

git

Une URL de dépôt Git (chaîne de caractères).

L'URL peut être n'importe quel protocole https://git-scm.com/docs/git-clone#_git_urls pris en charge par Git, y compris SSH, GIT et HTTPS.

Le dépôt Git sera cloné, la liste des versions (et le shard.yml associé) sera extraite des tags Git (par exemple, v1.2.3).

L'un des autres attributs (version, tag, branch ou commit) est requis. En cas d'absence, Shards installera les références HEAD.

Exemple : git: git://git.example.org/crystal-library.git

github

URL du dépôt GitHub sous la forme utilisateur/dépôt (chaîne de caractères)

Étends le résolveur git et agit exactement comme lui.

Exemple : github: ysbaddaden/minitest.cr

gitlab

URL du dépôt GitLab sous la forme utilisateur/dépôt (chaîne de caractères).

Étends le résolveur git et agit exactement comme lui.

Ne correspond qu'aux dépendances hébergées sur gitlab.com. Pour les installations GitLab personnelles, vous devez utiliser le résolveur générique git.

Exemple : gitlab: thelonlyghost/minitest.cr

bitbucket

URL du dépôt Bitbucket sous la forme utilisateur/dépôt (chaîne de caractères).

Étends le résolveur git et agit exactement comme lui.

Exemple : bitbucket: tom/library

codeberg

URL du dépôt Codeberg sous la forme utilisateur/dépôt (chaîne de caractères).

Étends le résolveur git et agit exactement comme lui.

Exemple : codeberg: tom/library

hg

Une URL de dépôt Mercurial (chaîne de caractères).

L'URL peut être n'importe quel protocole https://www.mercurial-scm.org/repo/hg/help/clone pris en charge par Mercurial, y compris SSH et HTTPS.

Le dépôt Mercurial sera cloné, la liste des versions (et le shard.yml associé) sera extraite des tags Mercurial (par exemple, v1.2.3).

L'un des autres attributs (version, tag, branch, bookmark ou commit) est requis. En cas d'absence, Shards installera le bookmark @ ou tip.

Exemple : hg: https://hg.example.org/crystal-library

fossil

Une URL de dépôt Fossil https://www.fossil-scm.org (chaîne de caractères).

L'URL peut être n'importe quel protocole https://fossil-scm.org/home/help/clone pris en charge par Fossil, y compris SSH et HTTPS.

Le dépôt Fossil sera cloné, la liste des versions (et le shard.yml associé) sera extraite des tags Fossil (par exemple, v1.2.3).

L'un des autres attributs (version, tag, branch ou commit) est requis. En cas d'absence, Shards installera trunk.

Exemple : fossil: https://fossil.example.org/crystal-library

version

Une exigence de version (chaîne de caractères).
•Il peut s'agir d'un numéro de version explicite.
•Il peut s'agir du caractère générique "*" si n'importe quelle version convient (c'est la valeur par défaut). Shards installera alors la dernière version taguée (ou HEAD s'il n'y a pas de version taguée disponible).
•Le numéro de version peut être préfixé par un opérateur : <, <=, >, >=, != ou ~>.
•Plusieurs exigences peuvent être séparées par des virgules.

Exemples : 1.2.3, >= 1.0.0, >= 1.0.0, < 2.0 ou ~> 2.0.

La plupart des opérateurs de version, comme >= 1.0.0, sont auto-explicatifs, mais l'opérateur ~> a une signification spéciale. Il spécifie une version minimale, mais permet au dernier chiffre spécifié d'augmenter, en excluant le numéro de version majeure :

•~> 0.3.5 est identique à >= 0.3.5 et < 0.4.0.
•~> 2.0.3 est identique à >= 2.0.3 et < 2.1.
•~> 2.1 est identique à >= 2.1 et < 3.0.
•~> 0.3 est identique à >= 0.3 et < 1.0.
•~> 1 est identique à >= 1.0 et < 2.0.

Note

Même si 2.1.0-dev est strictement antérieur à 2.1.0, une contrainte de version comme ~> 2.0.3
ne l'installera pas, car seul le .3 peut changer, mais la partie 2.0 est fixe.

branch

Installe la branche spécifiée d'une dépendance git, ou la branche nommée d'une dépendance mercurial ou fossil (chaîne de caractères).

commit

Installe le commit spécifié d'une dépendance git, mercurial ou fossil (chaîne de caractères).

tag

Installe le tag spécifié d'une dépendance git, mercurial ou fossil (chaîne de caractères).

bookmark

Installe le bookmark spécifié d'une dépendance mercurial (chaîne de caractères).

EXEMPLE :

Voici un exemple de shard.yml pour une bibliothèque nommée shards à la version 1.2.3 avec quelques dépendances :

name: shards
version: 1.2.3
crystal: '>= 0.35.0'
authors:
- Julien Portalier <julien@example.com>
license: MIT
description: |
  Gestionnaire de dépendances pour le langage Crystal
dependencies:
  openssl:
    github: datanoise/openssl.cr
    branch: master
development_dependencies:
  minitest:
    git: https://github.com/ysbaddaden/minitest.cr.git
    version: "~> 0.1.0"
libraries:
  libgit2: ~> 0.24
scripts:
  postinstall: make ext
targets:
  shards:
    main: src/shards.cr

shard.yml(5)

shard.yml - Fichier de configuration du gestionnaire de paquets Shard

DESCRIPTION

Le fichier shard.yml est utilisé par Shard, le gestionnaire de paquets pour le langage Crystal, pour définir les métadonnées d'un projet et spécifier ses dépendances. Ce fichier est généralement placé à la racine d'un projet Crystal.

SYNTAXE

Le fichier shard.yml est écrit en YAML. Voici les clés couramment utilisées :

name
Le nom du projet.
version
La version du projet. Il est recommandé d'utiliser un versionnement sémantique (SemVer).
authors
Une liste des auteurs du projet.
description
Une courte description du projet.
license
Le type de licence sous lequel le projet est distribué (par exemple, MIT, Apache-2.0).
dependencies
Un bloc définissant les dépendances du projet. Chaque clé est le nom d'une autre Shard, et la valeur spécifie la version requise (par exemple, ~> 1.0 pour la version 1.0 ou supérieure mais inférieure à 2.0).
development_dependencies
Similaire à dependencies, mais ces dépendances ne sont requises que pour le développement (par exemple, pour les tests ou les outils de build).
crystal
La version de Crystal requise pour ce projet.

Voici un exemple simple de shard.yml : 

name: mon_projet
version: 0.1.0
authors:
  - Votre Nom <votre.email@example.com>
description: |
  Une description détaillée de mon projet.
license: MIT
crystal: ">= 1.0.0"

dependencies:
  logger:
    github: crystal-lang/crystal-log
    branch: master

development_dependencies:
  spec:
    github: manastee/crystal-spec
    version: "~> 0.8"

COMMANDES SHARD LIÉES

Les commandes Shard qui interagissent avec shard.yml incluent :

  • shard install : Installe les dépendances spécifiées dans shard.yml.
  • shard build : Construit le projet en utilisant les informations de shard.yml.
  • shard update : Met à jour les dépendances vers les versions les plus récentes autorisées par shard.yml.
