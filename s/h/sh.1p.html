PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

sh — shell, l'interpréteur de langage de commande standard

SYNTAXE

sh [-abCefhimnuvx] [-o option]... [+abCefhimnuvx] [+o option]...
    [fichier_commande [argument...]]
sh -c [-abCefhimnuvx] [-o option]... [+abCefhimnuvx] [+o option]...
    chaine_commande [nom_commande [argument...]]
sh -s [-abCefhimnuvx] [-o option]... [+abCefhimnuvx] [+o option]...
    [argument...]

DESCRIPTION

L'utilitaire sh est un interpréteur de langage de commande qui exécute les commandes lues depuis une chaîne de ligne de commande, l'entrée standard ou un fichier spécifié. L'application doit s'assurer que les commandes à exécuter sont exprimées dans le langage décrit au Chapitre 2, Langage de commande shell.

L'expansion des noms de chemin ne doit pas échouer en raison de la taille d'un fichier.

Les redirections d'entrée et de sortie du shell ont un décalage maximal défini par l'implémentation qui est établi dans la description de fichier ouverte.

OPTIONS

L'utilitaire sh doit être conforme au volume Définitions de base de POSIX.1‐2017, Section 12.2, Lignes directrices de syntaxe des utilitaires, avec une extension pour la prise en charge d'un signe <plus> ('+') en tête, comme indiqué ci-dessous.

Les options -a, -b, -C, -e, -f, -m, -n, -o option, -u, -v et -x sont décrites comme faisant partie de l'utilitaire set dans la Section 2.14, Utilitaires intégrés spéciaux. Les lettres d'option dérivées de l'utilitaire intégré spécial set doivent également être acceptées avec un signe <plus> ('+') en tête au lieu d'un <trait d'union-moins> (ce qui signifie le cas inverse de l'option tel que décrit dans ce volume de POSIX.1‐2017).

Les options supplémentaires suivantes doivent être prises en charge :

-c
Lire les commandes à partir de l'opérande chaine_commande. Définir la valeur du paramètre spécial 0 (voir Section 2.5.2, Paramètres spéciaux) à partir de la valeur de l'opérande nom_commande et les paramètres positionnels ($1, $2, etc.) en séquence à partir des opérandes argument restants. Aucune commande ne doit être lue depuis l'entrée standard.
-i
Indiquer que le shell est interactif ; voir ci-dessous. Une implémentation peut considérer la spécification de l'option -i comme une erreur si l'ID utilisateur réel du processus appelant n'est pas égal à l'ID utilisateur effectif ou si l'ID groupe réel n'est pas égal à l'ID groupe effectif.
-s
Lire les commandes depuis l'entrée standard.

S'il n'y a pas d'opérandes et que l'option -c n'est pas spécifiée, l'option -s sera présumée.

Si l'option -i est présente, ou s'il n'y a pas d'opérandes et que l'entrée standard et la sortie d'erreur du shell sont connectées à un terminal, le shell est considéré comme interactif.

OPÉRANDES

Les opérandes suivants doivent être pris en charge :

-
Un seul <trait d'union-moins> sera traité comme le premier opérande puis ignoré. Si '-' et "--" sont tous deux donnés comme arguments, ou si d'autres opérandes précèdent le seul <trait d'union-moins>, les résultats sont indéfinis.
argument
Les paramètres positionnels ($1, $2, etc.) seront définis aux arguments, le cas échéant.
fichier_commande
Le nom de chemin d'un fichier contenant des commandes. Si le nom de chemin contient un ou plusieurs caractères <barre oblique> (/), l'implémentation tente de lire ce fichier ; le fichier n'a pas besoin d'être exécutable. Si le nom de chemin ne contient pas de caractère <barre oblique> (/):
*
L'implémentation tentera de lire ce fichier depuis le répertoire de travail courant ; le fichier n'a pas besoin d'être exécutable.
*
Si le fichier n'est pas dans le répertoire de travail courant, l'implémentation peut effectuer une recherche de fichier exécutable en utilisant la valeur de PATH, comme décrit dans la Section 2.9.1.1, Recherche et exécution de commande.

Le paramètre spécial 0 (voir Section 2.5.2, Paramètres spéciaux) sera défini à la valeur de fichier_commande. Si sh est appelé en utilisant une forme de syntaxe qui omet fichier_commande, le paramètre spécial 0 sera défini à la valeur du premier argument passé à sh depuis son parent (par exemple, argv[0] pour un programme C), qui est normalement un nom de chemin utilisé pour exécuter l'utilitaire sh.

nom_commande

Une chaîne assignée au paramètre spécial 0 lors de l'exécution des commandes dans chaine_commande. Si nom_commande n'est pas spécifié, le paramètre spécial 0 sera défini à la valeur du premier argument passé à sh depuis son parent (par exemple, argv[0] pour un programme C), qui est normalement un nom de chemin utilisé pour exécuter l'utilitaire sh.
chaine_commande

Une chaîne qui sera interprétée par le shell comme une ou plusieurs commandes, comme si la chaîne était l'argument de la fonction system() définie dans le volume Interfaces système de POSIX.1‐2017. Si l'opérande chaine_commande est une chaîne vide, sh se terminera avec un statut de sortie nul.

ENTRÉE STANDARD

L'entrée standard ne sera utilisée que si l'une des conditions suivantes est remplie :

*
L'option -s est spécifiée.
*
L'option -c n'est pas spécifiée et aucun opérande n'est spécifié.
*
Le script exécute une ou plusieurs commandes qui nécessitent une entrée depuis l'entrée standard (comme une commande read qui ne redirige pas son entrée).

Voir la section FICHIERS D'ENTRÉE.

Lorsque le shell utilise l'entrée standard et qu'il invoque une commande qui utilise également l'entrée standard, le shell doit s'assurer que le pointeur de fichier de l'entrée standard pointe directement après la commande qu'il a lue lorsque la commande commence son exécution. Il ne doit pas lire à l'avance d'une manière telle que des caractères destinés à être lus par la commande invoquée soient consommés par le shell (qu'ils soient interprétés par le shell ou non) ou que des caractères qui ne sont pas lus par la commande invoquée ne soient pas vus par le shell. Lorsque la commande attendant de lire l'entrée standard est lancée de manière asynchrone par un shell interactif, il est indéterminé si les caractères sont lus par la commande ou interprétés par le shell.

Si l'entrée standard vers sh est un FIFO ou un périphérique terminal et est réglée sur des lectures non bloquantes, alors sh activera les lectures bloquantes sur l'entrée standard. Ceci restera effectif à la fin de la commande.

FICHIERS D'ENTRÉE

Le fichier d'entrée doit être un fichier texte, à l'exception du fait que les longueurs de ligne doivent être illimitées. Si le fichier d'entrée ne contient que zéro ou plusieurs lignes vides et commentaires, sh se terminera avec un statut de sortie nul.

Les variables d'environnement suivantes doivent avoir un sens pour le utilitaire sh :

ENV
Ce nom de variable, lorsqu'il est développé par le shell, doit déterminer le fichier qui sera lu après l'initialisation, mais avant que le shell n'execute les commandes. Le fichier doit être lu seulement s'il existe et est lisible. Le shell doit lire et exécuter les commandes de ce fichier comme s'ils étaient tapés au début, avant toute autre commande ou script. Les résultats ne sont pas spécifiés si la valeur développée de ENV n'est pas un chemin absolu. FCEDIT
Cette variable, lorsqu'elle est développée par le shell, doit déterminer la valeur par défaut pour l'argument d'option editor de l'option -e editor. Si FCEDIT est vide ou non défini, ed doit être utilisé comme éditeur.
HISTFILE
Détermine un chemin de fichier nommant un fichier d'historique de commandes. Si la variable HISTFILE n'est pas définie, le shell peut tenter d'accéder ou de créer un fichier .sh_history dans le répertoire référencé par la variable d'environnement HOME. Si le shell ne peut pas obtenir l'accès en lecture et en écriture, ou créer, le fichier d'historique, il doit utiliser un mécanisme non spécifié qui permet à l'historique de fonctionner correctement. (Les références à l'historique « fichier » dans cette section doivent être comprises comme ce mécanisme non spécifié dans de tels cas.) Une implémentation peut choisir d'accéder à cette variable uniquement lors de l'initialisation du fichier d'historique ; cette initialisation doit se produire lorsque fc ou sh tentent pour la première fois de récupérer des entrées, ou d'ajouter des entrées à, le fichier, suite à des commandes émises par l'utilisateur, le fichier nommé par la variable ENV, ou des fichiers de démarrage système définis par l'implémentation. Les implémentations peuvent choisir de désactiver le mécanisme de liste d'historique pour les utilisateurs disposant des privilèges appropriés qui ne définissent pas HISTFILE ; les circonstances spécifiques dans lesquelles cela se produit sont définies par l'implémentation. Si plusieurs instances du shell utilisent le même fichier d'historique, il n'est pas spécifié comment les mises à jour du fichier d'historique de ces shells interagissent. Au fur et à mesure que les entrées sont supprimées du fichier d'historique, elles doivent être supprimées dans l'ordre le plus ancien d'abord. Il n'est pas spécifié quand les entrées du fichier d'historique sont physiquement supprimées du fichier d'historique.
HISTSIZE
Détermine un nombre décimal représentant la limite du nombre de commandes précédentes accessibles. Si cette variable n'est pas définie, une valeur par défaut non spécifiée supérieure ou égale à 128 doit être utilisée. Le nombre maximum de commandes dans la liste d'historique n'est pas spécifié, mais doit être d'au moins 128. Une implémentation peut choisir d'accéder à cette variable uniquement lors de l'initialisation du fichier d'historique, comme décrit sous HISTFILE. Par conséquent, il n'est pas spécifié si les modifications apportées à HISTSIZE après l'initialisation du fichier d'historique sont effectives.
HOME
Détermine le chemin du répertoire personnel de l'utilisateur. Le contenu de HOME est utilisé dans l'expansion du tilde tel que décrit dans la Section 2.6.1, Expansion du Tilde.
LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. Si défini sur une chaîne de caractères non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_COLLATE

Détermine le comportement des expressions de plage, des classes d'équivalence et des éléments de collation multicaractères dans la mise en correspondance de motifs.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles en caractères (par exemple, caractères mono-octet par opposition à multi-octets dans les arguments et les fichiers d'entrée), quels caractères sont définis comme lettres (classe de caractères alpha), et le comportement des classes de caractères dans la mise en correspondance de motifs.

Détermine la locale qui devrait être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur la sortie standard d'erreur.

Détermine un chemin du fichier de boîte aux lettres de l'utilisateur à des fins de notification de courrier entrant. Si cette variable est définie, le shell doit informer l'utilisateur si le fichier nommé par la variable est créé ou si son heure de modification a changé. L'information de l'utilisateur doit être réalisée en écrivant une chaîne de format non spécifié sur la sortie standard d'erreur avant l'écriture de la prochaine chaîne d'invite principale. Une telle vérification doit être effectuée uniquement après l'achèvement de l'intervalle défini par la variable MAILCHECK après la dernière vérification. L'utilisateur ne doit être informé que si MAIL est définie et MAILPATH n'est pas définie.
MAILCHECK

Établit une valeur entière décimale qui spécifie à quelle fréquence (en secondes) le shell doit vérifier l'arrivée du courrier dans les fichiers spécifiés par les variables MAILPATH ou MAIL. La valeur par défaut doit être de 600 secondes. Si elle est définie sur zéro, le shell doit vérifier avant d'émettre chaque invite principale.
MAILPATH
Fournit une liste de chemins et de messages optionnels séparés par des caractères <deux-points>. Si cette variable est définie, le shell doit informer l'utilisateur si l'un des fichiers nommés par la variable est créé ou si l'une de ses heures de modification change. (Voir l'entrée précédente pour MAIL pour les descriptions de l'arrivée du courrier et de l'information de l'utilisateur.) Chaque chemin peut être suivi de '%' et d'une chaîne qui sera soumise à une expansion de paramètre et écrite sur la sortie standard d'erreur lorsque l'heure de modification change. Si un caractère '%' dans le chemin est précédé d'une barre oblique inverse <backslash>, il doit être traité comme un '%' littéral dans le chemin. Le message par défaut n'est pas spécifié.

La variable d'environnement MAILPATH a la priorité sur la variable MAIL.

NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.
PATH
Établit une chaîne formatée comme décrit dans le volume des Définitions de Base de POSIX.1-2017, Chapitre 8, Variables d'Environnement, utilisée pour interpréter les commandes ; voir la Section 2.9.1.1, Recherche et Exécution de Commandes.
PWD
Cette variable doit représenter un chemin absolu du répertoire de travail courant. Les affectations à cette variable peuvent être ignorées.

ÉVÉNEMENTS ASYNCHRONES

L'utilitaire sh doit prendre l'action standard pour tous les signaux (voir la Section 1.4, Défauts de Description des Utilitaires) à l'exception des suivants.

Si le shell est interactif, les signaux SIGINT reçus pendant l'édition de la ligne de commande doivent être traités comme décrit dans la DESCRIPTION ÉTENDUE, et les signaux SIGINT reçus à d'autres moments doivent être interceptés mais aucune action ne doit être effectuée.

Si le shell est interactif :

*
Les signaux SIGQUIT et SIGTERM doivent être ignorés.
*
Si l'option -m est active, les signaux SIGTTIN, SIGTTOU et SIGTSTP doivent être ignorés.
*
Si l'option -m n'est pas active, il n'est pas spécifié si les signaux SIGTTIN, SIGTTOU et SIGTSTP sont ignorés, définis sur l'action par défaut, ou interceptés. S'ils sont interceptés, le shell doit, dans la fonction de capture de signal, définir le signal à l'action par défaut et lever le signal (après avoir pris les mesures appropriées, telles que la restauration des paramètres du terminal).

Les actions standard, et les actions décrites ci-dessus pour les shells interactifs, peuvent être outrepassées en utilisant l'utilitaire spécial intégré trap (voir trap et la Section 2.11, Signaux et Gestion des Erreurs).

DESCRIPTION

The sh utility shall be an interactive command language interpreter. It shall execute commands read by standard input, from a file, or from the command line arguments. When invoked as an interactive login shell, sh shall first read commands from the file $HOME/.profile (if it exists and is readable). It shall then read commands from the file specified by the $ENV environment variable (if it exists and is readable).

When sh is invoked from a non-interactive parent process (for example, via a pipe or redirection), it shall not read any startup files. When sh is invoked in the following ways, it shall behave as a non-interactive shell:

  • With arguments, the first argument is the name of a file that contains shell commands. If the -c option is present, the first argument is the name of the shell command.
  • The -t option is present.

In interactive mode, sh shall accept commands from standard input. It shall use the value of the PS1 environment variable as the primary prompt string and the value of the PS2 environment variable as the secondary prompt string. If PS1 is unset, a default prompt string is used. The default primary prompt string shall be the string "$" followed by a space. The default secondary prompt string shall be the string "> " followed by a space.

Interactive startup files are read only by interactive shells.

The sh utility shall support command line editing. Command line editing is enabled by default unless the -f option is used, or if standard input is not a terminal. The default editing mode is emacs editing mode.

The editing mode can be set by the set -o command to vi or emacs. If the editing mode is not explicitly set, the default shall be emacs editing mode. The default editing mode can also be influenced by the VISUAL and EDITOR environment variables.

The sh utility recognizes the following signals: SIGCHLD, SIGINT, SIGQUIT, SIGTERM, and SIGWINCH. When sh catches SIGINT or SIGQUIT, it shall terminate any currently executing foreground process, display the primary prompt string, and begin reading another command. If sh is in the middle of reading a command line when SIGINT or SIGQUIT is caught, the line shall be immediately discarded, the prompt reissued, and no other processing shall occur.

If sh catches SIGWINCH, it shall update the window size information. If the shell is interactive, it shall re-evaluate the prompt strings. (This is a common extension and not part of the POSIX standard.)

When sh is reading commands from standard input or from a file, and it receives an end-of-file character, it shall terminate unless it is processing a here-document. When processing a here-document, an end-of-file character terminates the here-document. The default end-of-file character is implementation-defined (usually D).

If sh is reading commands from a file specified with the -c option, and the file contains an end-of-file character, it shall terminate. If sh is processing a here-document and receives an end-of-file character, it shall terminate the here-document.

The following characters shall have special meaning to the shell when they are read from the terminal unless quoted or part of a quoted string:

alias
The shell built-in command that allows the creation of shell aliases.
backup
The character specified by the BACKSLASH_ESCAPE shell variable. This character is used to escape the next character typed.
erase
The character specified by the ERASE shell variable. This character deletes the character immediately preceding the cursor.
eof
The character specified by the EOF shell variable. This character signals the end of input from a terminal.
eol
The character specified by the EOL shell variable. This character signals the end of the current line for the purpose of line editing.
escape
The character specified by the ESCAPE shell variable. This character is used to escape the next character typed.
history
The character specified by the HISTORY shell variable. If this character is typed, the shell shall perform history expansion.
interrupt
The character specified by the INTERRUPT shell variable. Typing this character shall cause the shell to send the SIGINT signal to the currently executing foreground process group.
kill
The character specified by the KILL shell variable. This character deletes all characters from the beginning of the line up to the cursor.
newl
The newline character. This character terminates the current command line and initiates its execution.
quit
The character specified by the QUIT shell variable. Typing this character shall cause the shell to send the SIGQUIT signal to the currently executing foreground process group.
reprint
The character specified by the REPRINT shell variable. This character causes the current line to be reprinted.
start
The character specified by the START shell variable. This character shall restart the terminal output.
stop
The character specified by the STOP shell variable. This character shall suspend the terminal output.
suspend
The character specified by the SUSPEND shell variable. This character shall send the SIGTSTP signal to the currently executing foreground process group.
transpose-chars
The character specified by the TRANSPOSE_CHARS shell variable. This character shall transpose the two characters preceding the cursor.
transpose-words
The character specified by the TRANSPOSE_WORDS shell variable. This character shall transpose the two words preceding the cursor.
word-rewind
The character specified by the WORD_REWIND shell variable. This character shall move the cursor to the beginning of the previous word.

These special characters are defined by the POSIX standard shell builtins stty, ERASE, KILL, INTERRUPT, QUIT, SUSPEND, and EOF. The default values for these special characters are determined by the terminal settings when the shell starts.

If the shell is invoked with arguments, the first argument is assumed to be the name of a file containing shell commands. The shell shall read commands from this file and shall not take any further arguments as commands. This mode of operation is called *sh* script mode. The shell shall exit with the exit status of the last command executed. If the shell reads EOF, it exits with status 0.

If the -c option is present, the shell shall read commands from the string following the option. It shall not take any further arguments as commands. The shell shall exit with the exit status of the last command executed. If the shell reads EOF, it exits with status 0.

If the -t option is present, the shell shall read commands from standard input and exit after executing that one command. This mode is called *sh* one-shot mode.

If the -i option is present, the shell shall be an interactive shell. This is the default if standard input is a terminal and the -c and -t options are not present.

The shell shall support job control. When job control is enabled, the shell shall provide facilities for managing multiple processes.

The shell shall support shell variables. Shell variables can be assigned values using the syntax: 

name=value

Positional parameters are named $1, $2, $3, etc. $0 is the name of the shell invocation. $# is the number of positional parameters.

The following built-in commands shall be supported:

:
Do nothing. Exit status is zero.
. file
Read and execute commands from file in the current shell environment. Exit status is the exit status of the last command in file. If file cannot be read, the exit status is non-zero. If the last command in file is not found, the exit status is non-zero.
alias [name[=value] ...]
Provide alias definitions. If no arguments are given, the shell shall write to standard output an alias definition for each alias introduced in the current shell environment. If one or more arguments are given, then for each argument, any existing definition shall be replaced by a new definition formed by the argument. The alias shall be defined as name is the first word of the argument and value is the rest of the argument.
bg [job ...]
Place the specified jobs into the background. If no jobs are specified, the current job is placed into the background.
bind
Display or modify the key bindings for the shell's line editor.
break [n]
Exit from the innermost n enclosing shell compound commands or for loops. If n is omitted, it defaults to 1.
caller [expression]
Display the call stack of the current shell script.
cd [arg ...]
Change the current directory to the specified directory. If only one argument is given, that argument becomes the new current directory. If no argument is given, the shell shall change the current directory to the home directory specified by the HOME environment variable. The cd command shall return a non-zero exit status if the directory change fails.
command command [arg ...]
Execute command without invoking a file name search. This is useful to override built-ins or aliases.
continue [n]
Continue execution after the n-th enclosing compound command or for loop. If n is omitted, it defaults to 1.
declare [option ...] [name[=value] ...]
Declare variables and assign them attributes. Options include -a (array), -f (function), -i (integer), -r (readonly), and -x (export).
dirs [-clpv] [+N] [-N]
Display the list of currently remembered directories. The default behavior is to display them in the order they were added.
do
Execute commands in a loop.
echo [option ...] [string ...]
Write arguments to standard output. The -n option suppresses the trailing newline. The -e option enables interpretation of backslash escapes.
enable [-a] [-dnf] [-p] [-u] [name ...]

Command Line Editing (vi-mode)

In vi editing mode, there shall be a distinguished line, the edit line. All the editing operations which modify a line affect the edit line. The edit line is always the newest line in the command history buffer.

With vi-mode enabled, sh can be switched between insert mode and command mode.

When in insert mode, an entered character shall be inserted into the command line, except as noted in vi Line Editing Insert Mode. Upon entering sh and after termination of the previous command, sh shall be in insert mode.

Typing an escape character shall switch sh into command mode (see vi Line Editing Command Mode). In command mode, an entered character shall either invoke a defined operation, be used as part of a multi-character operation, or be treated as an error. A character that is not recognized as part of an editing command shall terminate any specific editing command and shall alert the terminal. If sh receives a SIGINT signal in command mode (whether generated by typing the interrupt character or by other means), it shall terminate command line editing on the current command line, reissue the prompt on the next line of the terminal, and reset the command history (see fc) so that the most recently executed command is the previous command (that is, the command that was being edited when it was interrupted is not re-entered into the history).

In the following sections, the phrase ``move the cursor to the beginning of the word'' shall mean ``move the cursor to the first character of the current word'' and the phrase ``move the cursor to the end of the word'' shall mean ``move the cursor to the last character of the current word''. The phrase ``beginning of the command line'' indicates the point between the end of the prompt string issued by the shell (or the beginning of the terminal line, if there is no prompt string) and the first character of the command text.

Delete the character previous to the current cursor position and move the current cursor position back one character. In insert mode, characters shall be erased from both the screen and the buffer when backspacing.

vi Line Editing Command Mode

In command mode for the command line editing feature, decimal digits not beginning with 0 that precede a command letter shall be remembered. Some commands use these decimal digits as a count number that affects the operation.

The term motion command represents one of the commands:

<space>  0  b  F  l  W  ^  $  ;  E  f  T  w  |  ,  B  e  h  t

If the current line is not the edit line, any command that modifies the current line shall cause the content of the current line to replace the content of the edit line, and the current line shall become the edit line. This replacement cannot be undone (see the u and U commands below). The modification requested shall then be performed to the edit line. When the current line is the edit line, the modification shall be done directly to the edit line.

Any command that is preceded by count shall take a count (the numeric value of any preceding decimal digits). Unless otherwise noted, this count shall cause the specified operation to repeat by the number of times specified by the count. Also unless otherwise noted, a count that is out of range is considered an error condition and shall alert the terminal, but neither the cursor position, nor the command line, shall change.

Si le count est supérieur au nombre de caractères entre la position actuelle du curseur et la fin de la ligne de commande vers laquelle la commande de mouvement déplacerait le curseur, cela ne sera pas considéré comme une erreur ; tous les caractères restants dans la plage susmentionnée seront supprimés. Les caractères supprimés seront placés dans le tampon de sauvegarde.
D
Supprime tous les caractères de la position actuelle du curseur jusqu'à la fin de la ligne. Les caractères supprimés seront placés dans le tampon de sauvegarde.
[count]ymotion

Copie (yank) les caractères de la position actuelle du curseur à la position résultant de la commande de mouvement dans le tampon de sauvegarde. Un nombre count s'appliquera à la commande de mouvement. Si la commande de mouvement se déplace vers le début de la ligne de commande, le caractère sous la position actuelle du curseur ne sera pas inclus dans l'ensemble des caractères copiés. Si la commande de mouvement est y, toute la ligne de commande actuelle sera copiée dans le tampon de sauvegarde. La position actuelle du curseur ne sera pas modifiée. Si le count est supérieur au nombre de caractères entre la position actuelle du curseur et la fin de la ligne de commande vers laquelle la commande de mouvement déplacerait le curseur, cela ne sera pas considéré comme une erreur ; tous les caractères restants dans la plage susmentionnée seront copiés.
Y
Copie les caractères de la position actuelle du curseur jusqu'à la fin de la ligne dans le tampon de sauvegarde. La position actuelle du caractère ne sera pas modifiée.
[count]p
Colle une copie du contenu actuel du tampon de sauvegarde après la position actuelle du curseur. La position actuelle du curseur sera avancée au dernier caractère collé du tampon de sauvegarde. Un count indiquera combien de copies du tampon de sauvegarde doivent être collées.
[count]P
Colle une copie du contenu actuel du tampon de sauvegarde avant la position actuelle du curseur. La position actuelle du curseur sera déplacée au dernier caractère collé du tampon de sauvegarde. Un count indiquera combien de copies du tampon de sauvegarde doivent être collées.
u
Annule la dernière commande qui a modifié la ligne d'édition. Cette opération n'annulera pas la copie d'une ligne de commande vers la ligne d'édition.
U
Annule toutes les modifications apportées à la ligne d'édition. Cette opération n'annulera pas la copie d'une ligne de commande vers la ligne d'édition.
[count]k
[count]-
Définit la ligne de commande actuelle comme étant la countème ligne de commande précédente dans l'historique des commandes du shell. Si count n'est pas spécifié, il vaut par défaut 1. Le curseur sera placé sur le premier caractère de la nouvelle commande. Si une commande k ou - devait remonter au-delà du nombre maximum de commandes en vigueur pour ce shell (affecté par la variable d'environnement HISTSIZE), le terminal sera alerté et la commande n'aura aucun effet.
[count]j
[count]+
Définit la ligne de commande actuelle comme étant la countème ligne de commande suivante dans l'historique des commandes du shell. Si count n'est pas spécifié, il vaut par défaut 1. Le curseur sera placé sur le premier caractère de la nouvelle commande. Si une commande j ou + avance au-delà de la ligne d'édition, la ligne de commande actuelle sera restaurée à la ligne d'édition et le terminal sera alerté.
[number]G
Définit la ligne de commande actuelle comme étant la ligne de commande la plus ancienne stockée dans l'historique des commandes du shell. Avec un nombre number, définit la ligne de commande actuelle comme étant la numberème ligne de commande dans l'historique. Si la ligne de commande number n'existe pas, le terminal sera alerté et la ligne de commande ne sera pas modifiée.
/pattern<newline>

Remonte dans l'historique des commandes, en recherchant le motif spécifié, en commençant par la ligne de commande précédente. Les motifs utilisent la notation de correspondance de motifs décrite dans la Section 2.13, Notation de correspondance de motifs, à l'exception du fait que le caractère '^' a une signification spéciale lorsqu'il apparaît comme premier caractère de pattern. Dans ce cas, le '^' est ignoré et les caractères après le '^' ne seront mis en correspondance qu'au début d'une ligne. Les commandes de l'historique des commandes sont traitées comme des chaînes de caractères, et non comme des noms de fichiers. Si le motif n'est pas trouvé, la ligne de commande actuelle ne sera pas modifiée et le terminal sera alerté. S'il est trouvé dans une ligne précédente, la ligne de commande actuelle sera définie sur cette ligne et le curseur sera placé sur le premier caractère de la nouvelle ligne de commande.

Si pattern est vide, le dernier motif non vide fourni à / ou ? sera utilisé. S'il n'y a pas de motif non vide précédent, le terminal sera alerté et la ligne de commande actuelle restera inchangée.

?pattern<newline>

Avance dans l'historique des commandes, en recherchant le motif spécifié, en commençant par la ligne de commande suivante. Les motifs utilisent la notation de correspondance de motifs décrite dans la Section 2.13, Notation de correspondance de motifs, à l'exception du fait que le caractère '^' a une signification spéciale lorsqu'il apparaît comme premier caractère de pattern. Dans ce cas, le '^' est ignoré et les caractères après le '^' ne seront mis en correspondance qu'au début d'une ligne. Les commandes de l'historique des commandes sont traitées comme des chaînes de caractères, et non comme des noms de fichiers. Si le motif n'est pas trouvé, la ligne de commande actuelle ne sera pas modifiée et le terminal sera alerté. S'il est trouvé dans une ligne suivante, la ligne de commande actuelle sera définie sur cette ligne et le curseur sera placé sur le premier caractère de la nouvelle ligne de commande.

Si pattern est vide, le dernier motif non vide fourni à / ou ? sera utilisé. S'il n'y a pas de motif non vide précédent, le terminal sera alerté et la ligne de commande actuelle restera inchangée.

n
Répète la commande / ou ? la plus récente. S'il n'y a pas de commande / ou ? précédente, le terminal sera alerté et la ligne de commande actuelle restera inchangée.
N
Répète la commande / ou ? la plus récente, en inversant la direction de la recherche. S'il n'y a pas de commande / ou ? précédente, le terminal sera alerté et la ligne de commande actuelle restera inchangée.

Les valeurs de sortie suivantes seront retournées :

    0
Le script à exécuter ne consistait qu'en zéro ou plusieurs lignes vides ou commentaires, ou les deux.
1‐125
Un shell non interactif a détecté une erreur autre que la non-trouvée ou la non-exécutabilité du fichier_commande, y compris, mais sans s'y limiter, des erreurs de syntaxe, de redirection ou d'affectation de variable.
  126

UTILISATION PAR L'APPLICATION

L'entrée standard et la sortie d'erreur sont les fichiers qui déterminent si un shell est interactif lorsque -i n'est pas spécifié. Par exemple :

sh > fichier

et :

sh 2> fichier

créent respectivement des shells interactifs et non interactifs. Bien que les deux acceptent l'entrée du terminal, les résultats des conditions d'erreur sont différents, comme décrit dans la Section 2.8.1, Conséquences des erreurs du shell ; dans le second exemple, une erreur de redirection rencontrée par un utilitaire interne spécial abandonne le shell.

Une application conforme doit protéger son premier opérande, s'il commence par un <signe plus>, en le faisant précéder de l'argument "--" qui dénote la fin des options.

Les applications doivent noter que le PATH standard du shell ne peut pas être supposé être soit /bin/sh, soit /usr/bin/sh, et doit être déterminé en interrogeant le PATH renvoyé par getconf PATH, en s'assurant que le chemin renvoyé est un chemin absolu et non un shell intégré.

Par exemple, pour déterminer l'emplacement de l'utilitaire standard sh :

command -v sh

Sur certaines implémentations, cela pourrait renvoyer :

/usr/xpg4/bin/sh

De plus, sur les systèmes qui prennent en charge les scripts exécutables (la construction "#!"), il est recommandé que les applications utilisant des scripts exécutables les installent en utilisant getconf PATH pour déterminer le chemin du shell et mettent à jour le script "#!" de manière appropriée lors de son installation (par exemple, avec sed). Par exemple :

# # Script d'installation pour installer le chemin du shell POSIX correct # # Obtenir la liste des chemins à vérifier # Sifs=$IFS Sifs_set=${IFS+y} IFS=: set -- $(getconf PATH) if [ "$Sifs_set" = y ] then IFS=$Sifs else unset IFS fi # # Vérifier chaque chemin pour 'sh' # for i do if [ -x "${i}"/sh ] then Pshell=${i}/sh fi done # # C'est la liste des scripts à mettre à jour. Ils devraient être de la # forme '${nom}.source' et seront transformés en '${nom}'. # Chaque script devrait commencer par : # # #!CHEMIN_INSTALL_SHELL # scripts="a b c" # # Transformer chaque script # for i in ${scripts} do sed -e "s|INSTALLSHELLPATH|${Pshell}|" < ${i}.source > ${i} done

EXEMPLES

1.
Exécuter une commande shell à partir d'une chaîne :
sh -c "cat monfichier"
2.
Exécuter un script shell à partir d'un fichier dans le répertoire courant :
sh mes_commandes_shell

RATIONALE

L'utilitaire sh et l'utilitaire intégré spécial set partagent un ensemble commun d'options.

Le nom IFS était à l'origine une abréviation de « Input Field Separators » (Séparateurs de champs d'entrée) ; cependant, ce nom est trompeur car les caractères IFS sont en fait utilisés comme terminateurs de champs. Une justification pour ignorer le contenu de IFS lors de l'entrée dans le script, au-delà des considérations de sécurité, est d'aider d'éventuels futurs compilateurs de shell. Autoriser IFS à être importé de l'environnement empêche de nombreuses optimisations qui pourraient autrement être effectuées via l'analyse du flux de données du script lui-même.

Le texte dans la section STDIN concernant les lectures non bloquantes concerne une instance de sh qui a été invoquée, probablement par un programme en langage C, avec une entrée standard qui a été ouverte en utilisant le drapeau O_NONBLOCK ; voir open() dans le volume des Interfaces Système de POSIX.1‐2017. Si le shell ne réinitialisait pas ce drapeau, il se terminerait immédiatement car aucune donnée d'entrée ne serait encore disponible et cela serait considéré comme équivalent à la fin de fichier.

Les options associées à un shell restreint (nom de commande rsh et option -r) ont été exclues car les développeurs du standard estimaient que le niveau de sécurité implicite ne pouvait pas être atteint et qu'ils ne voulaient pas susciter de fausses attentes.

Sur les systèmes qui prennent en charge les scripts set-user-ID, une porte dérobée historique consistait à lier un script au nom -i. Lorsqu'il est appelé par une séquence telle que :

sh -

ou par :

#! /usr/bin/sh -

les systèmes historiques supposaient qu'aucune lettre d'option ne suivait. Ainsi, ce volume de POSIX.1‐2017 autorise le simple <trait d'union> à marquer la fin des options, en plus de l'utilisation de l'argument régulier "--", car on considérait que la pratique plus ancienne était trop répandue. Une approche alternative est adoptée par le KornShell, où les identifiants d'utilisateur/groupe réels et effectifs doivent correspondre pour un shell interactif ; ce comportement est spécifiquement autorisé par ce volume de POSIX.1‐2017.

Note :
Il existe d'autres problèmes avec les scripts set-user-ID que les deux approches décrites ici ne résolvent pas.

Le processus d'initialisation du fichier d'historique peut dépendre des fichiers de démarrage du système, en ce sens qu'ils peuvent contenir des commandes qui préemptent effectivement les paramètres utilisateur de HISTFILE et HISTSIZE. Par exemple, les commandes de définition de fonction sont enregistrées dans le fichier d'historique, à moins que l'option set -o nolog ne soit définie. Si l'administrateur système inclut des définitions de fonction dans un fichier de démarrage du système appelé avant le fichier ENV, le fichier d'historique est initialisé avant que l'utilisateur n'ait la possibilité d'influencer ses caractéristiques. Dans certains shells historiques, le fichier d'historique est initialisé juste après le traitement du fichier ENV. Par conséquent, il est défini par l'implémentation si les modifications apportées à HISTFILE après l'initialisation du fichier d'historique sont effectives.

Les messages par défaut pour les différents messages liés à MAIL sont non spécifiés car ils varient selon les implémentations. Les messages typiques sont :

"vous avez du courrier\n"

ou :

"vous avez du nouveau courrier\n"

Il est important que les descriptions de l'édition de ligne de commande fassent référence au même shell que celui de POSIX.1‐2008 afin que les utilisateurs interactifs puissent également être des programmeurs d'applications sans avoir à traiter les différences programmatiques dans leurs deux environnements. Il est également essentiel que le nom de l'utilitaire sh soit spécifié car ce nom d'utilitaire explicite est trop solidement ancré dans la pratique historique des programmes d'application pour qu'il puisse changer.

La possibilité de définir un message diagnostique lors de la tentative de définition du mode vi sur des terminaux qui ne prennent pas en charge l'édition de ligne de commande a été envisagée. Cependant, il n'est pas de pratique historique que le shell soit conscient de tous les types de terminaux et qu'il puisse ainsi détecter les terminaux inappropriés dans tous les cas. Il est encouragé que les implémentations fournissent des diagnostics dans ce cas chaque fois que possible, plutôt que de laisser l'utilisateur dans un état où les commandes d'édition fonctionnent incorrectement.

Dans les premières propositions, le mode d'édition de ligne de commande emacs dérivé du KornShell était inclus, même si l'éditeur emacs lui-même ne l'était pas. La communauté des partisans d'emacs était catégorique quant au fait que l'éditeur emacs complet ne devait pas être standardisé car ils craignaient qu'une tentative de standardisation de cet environnement très puissant n'encourage les vendeurs à expédier des versions strictement conformes mais dépourvues de l'extensibilité requise par la communauté. L'auteur du programme emacs original a également exprimé son désir d'omettre le programme. De plus, il existait un certain nombre de systèmes historiques qui n'incluaient pas emacs, ou l'incluaient sans le prendre en charge, mais il y en avait très peu qui n'incluaient pas et ne prenaient pas en charge vi. Le mode d'édition de ligne de commande emacs du shell a finalement été omis car il est devenu évident que la version du KornShell et l'éditeur distribué avec le système GNU avaient divergé à certains égards. L'auteur d'emacs a demandé que le mode emacs de POSIX soit soit supprimé, soit qu'il contienne un nombre significatif de conditions non spécifiées. Bien que l'auteur du KornShell ait accepté d'envisager des changements pour aligner le shell, les développeurs du standard ont décidé de reporter la spécification à ce moment-là. À l'époque, on supposait qu'une convergence vers une définition acceptable se produirait pour une proposition ultérieure, mais cela ne s'est pas produit, et il semble n'y avoir aucune impulsion pour le faire. Dans tous les cas, les implémentations sont libres d'offrir des modes d'édition de ligne de commande supplémentaires basés sur les modèles exacts des éditeurs avec lesquels leurs utilisateurs sont les plus à l'aise.

Les premières propositions contenaient l'entrée de liste suivante dans le Mode d'insertion d'édition de ligne vi :

\
S'il est suivi du caractère d'effacement (erase) ou de mise à l'écart (kill), ce caractère sera inséré dans la ligne d'entrée. Sinon, le caractère <barre oblique inverse> lui-même sera inséré dans la ligne d'entrée.

Cependant, ce n'est pas réellement une fonctionnalité du mode d'insertion d'édition de ligne de sh, mais une des fonctionnalités de certains pilotes de ligne de terminal historiques. Certaines implémentations conformes continuent de le faire lorsque le drapeau stty iexten est défini.

Dans les shells interactifs, SIGTERM est ignoré afin que kill 0 ne tue pas le shell, et SIGINT est intercepté afin que wait soit interrompible. Si le shell n'ignore pas les signaux SIGTTIN, SIGTTOU et SIGTSTP lorsqu'il est interactif et que l'option -m n'est pas en vigueur, ces signaux suspendent le shell s'il ne s'agit pas d'un leader de session. S'il s'agit d'un leader de session, les signaux sont ignorés s'ils devaient arrêter le processus, comme requis par le volume des Interfaces Système de POSIX.1‐2017, Section 2.4.3, Actions de signal pour les groupes de processus orphelins.
