LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNTAXE

ld [options] fichier-objet ...

DESCRIPTION

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références de symboles. Généralement, la dernière étape de compilation d'un programme est l'exécution de ld.

ld accepte des fichiers de langage de commande de l'éditeur de liens écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens AT&T, afin de fournir un contrôle explicite et total sur le processus d'édition de liens.

Cette page man ne décrit pas le langage de commande ; consultez l'entrée ld dans "info" pour les détails complets sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques générales BFD pour opérer sur les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents — par exemple, COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que d'autres éditeurs de liens en fournissant des informations diagnostiques. De nombreux éditeurs de liens abandonnent l'exécution immédiatement en cas d'erreur ; chaque fois que possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec d'autres éditeurs de liens. Par conséquent, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options en ligne de commande, mais en pratique peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standard sur un système Unix standard et supporté. Sur un tel système, pour lier un fichier "hello.o" :

ld -o <sortie> /lib/crt0.o hello.o -lc

Cela indique à ld de produire un fichier appelé sortie en résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion sur l'option -l ci-dessous.)

Certaines des options en ligne de commande de ld peuvent être spécifiées à n'importe quel endroit de la ligne de commande. Cependant, les options qui font référence à des fichiers, comme -l ou -T, provoquent la lecture du fichier à l'endroit où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et aux autres options de fichiers. Répéter des options non liées à un fichier avec un argument différent n'aura aucun effet supplémentaire, ou remplacera les occurrences précédentes (celles plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être significativement spécifiées plus d'une fois sont notées dans les descriptions ci-dessous.

Les arguments qui ne sont pas des options sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de la ligne de commande, sauf qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Généralement, l'éditeur de liens est appelé avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R, et le langage de script de commande. Si *aucun* fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et affiche le message No input files.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière augmente le script d'éditeur de liens principal utilisé pour la liaison (soit le script d'éditeur de liens par défaut, soit celui spécifié en utilisant -T). Cette fonctionnalité permet à l'éditeur de liens de se lier à un fichier qui ressemble à un objet ou à une archive, mais qui ne fait que définir certaines valeurs de symboles, ou qui utilise "INPUT" ou "GROUP" pour charger d'autres objets. La spécification d'un script de cette manière ne fait qu'augmenter le script d'éditeur de liens principal, avec les commandes supplémentaires placées après le script principal ; utilisez l'option -T pour remplacer complètement le script d'éditeur de liens par défaut, mais notez l'effet de la commande "INSERT".

Pour les options dont le nom est une seule lettre, les arguments des options doivent soit suivre la lettre de l'option sans espace blanc intermédiaire, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert.

Pour les options dont le nom est constitué de plusieurs lettres, un seul tiret ou deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez qu'il y a une exception à cette règle. Les options à plusieurs lettres qui commencent par une lettre minuscule 'o' ne peuvent être précédées que de deux tirets. Ceci afin de réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie sur magic, tandis que --omagic définit l'indicateur NMAGIC sur la sortie.

Les arguments des options à plusieurs lettres doivent soit être séparés du nom de l'option par un signe égal, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Des abréviations uniques des noms des options à plusieurs lettres sont acceptées.

Notez que si l'éditeur de liens est appelé indirectement, via un pilote de compilateur (par exemple, gcc), alors toutes les options de la ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote de compilateur particulier), comme suit :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Ceci est important, car sinon le programme pilote de compilateur peut silencieusement ignorer les options de l'éditeur de liens, entraînant une mauvaise liaison. La confusion peut également survenir lors du passage d'options qui requièrent des valeurs à travers un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et amène le pilote à passer uniquement l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à lettre unique et à plusieurs lettres, telles que :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Voici un tableau des commutateurs génériques de ligne de commande acceptés par l'éditeur de liens GNU :

@fichier
Lire les options de ligne de commande depuis fichier. Les options lues sont insérées à la place de l'option @fichier d'origine. Si fichier n'existe pas, ou ne peut pas être lu, alors l'option sera traitée littéralement, et non supprimée.

Les options dans fichier sont séparées par des espaces blancs. Un caractère d'espace blanc peut être inclus dans une option en entourant l'option entière d'apostrophes simples ou doubles. N'importe quel caractère (y compris une barre oblique inverse) peut être inclus en faisant précéder le caractère à inclure d'une barre oblique inverse. Le fichier peut lui-même contenir des options @fichier supplémentaires ; toutes ces options seront traitées récursivement.

-a mot-clé
Cette option est supportée pour la compatibilité HP/UX. L'argument mot-clé doit être l'une des chaînes archive, shared, ou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée un nombre quelconque de fois.
--audit AUDITLIB
Ajoute AUDITLIB à l'entrée "DT_AUDIT" de la section dynamique. AUDITLIB n'est pas vérifié quant à son existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. Si spécifié plusieurs fois, "DT_AUDIT" contiendra une liste d'interfaces d'audit à utiliser, séparée par des deux-points. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée "DT_DEPAUDIT" correspondante dans le fichier de sortie. Cette option n'est significative que sur les plateformes ELF supportant l'interface rtld-audit.
-b format-entrée
--format=format-entrée
ld peut être configuré pour supporter plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire des fichiers objets qui suivent cette option sur la ligne de commande. Même lorsque ld est configuré pour supporter des formats d'objets alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour attendre par défaut un format donné.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

format d'entrée par défaut, le format le plus courant sur chaque machine. format-entrée est une chaîne de texte, le nom d'un format particulier pris en charge par les bibliothèques BFD. (Vous pouvez lister les formats binaires disponibles avec objdump -i.)

Vous pourriez vouloir utiliser cette option si vous liez des fichiers avec un format binaire inhabituel. Vous pouvez également utiliser -b pour changer explicitement de format (lors de la liaison de fichiers objets de formats différents), en incluant -b format-entrée avant chaque groupe de fichiers objets dans un format particulier.

Le format par défaut est tiré de la variable d'environnement "GNUTARGET".

Vous pouvez également définir le format d'entrée à partir d'un script, en utilisant la commande "TARGET" ;

-c fichier-commande-MRI
--mri-script=fichier-commande-MRI
Pour la compatibilité avec les linkers produits par MRI, ld accepte des fichiers script écrits dans un langage de commande alternatif et restreint, décrit dans la section Fichiers script compatibles MRI de la documentation GNU ld. Introduisez les fichiers script MRI avec l'option -c ; utilisez l'option -T pour exécuter des scripts de linker écrits dans le langage de script ld généraliste. Si fichier-commande-MRI n'existe pas, ld le recherche dans les répertoires spécifiés par toute option -L.
-d
-dc
-dp
Ces trois options sont équivalentes ; plusieurs formes sont prises en charge pour la compatibilité avec d'autres linkers. Elles assignent de l'espace aux symboles communs même si un fichier de sortie relocalisable est spécifié (avec -r). La commande script "FORCE_COMMON_ALLOCATION" a le même effet.
--depaudit BIBLIB
-P BIBLIB
Ajoute BIBLIB à l'entrée "DT_DEPAUDIT" de la section dynamique. BIBLIB n'est pas vérifié pour son existence, et n'utilisera pas non plus le DT_SONAME spécifié dans la bibliothèque. Si spécifié plusieurs fois, "DT_DEPAUDIT" contiendra une liste d'interfaces d'audit séparée par des deux-points à utiliser. Cette option n'est significative que sur les plateformes ELF prenant en charge l'interface rtld-audit. L'option -P est fournie pour la compatibilité Solaris.
--enable-linker-version
Active la directive de script de linker "LINKER_VERSION", décrite dans Données de section de sortie. Si cette directive est utilisée dans un script de linker et que cette option a été activée, une chaîne contenant la version du linker sera insérée au point actuel.

Notez que l'emplacement de cette option sur la ligne de commande du linker est significatif. Elle n'affectera que les scripts de linker qui la suivent sur la ligne de commande, ou qui sont intégrés au linker.

--disable-linker-version
Désactive la directive de script de linker "LINKER_VERSION", de sorte qu'elle n'insère pas de chaîne de version. C'est le comportement par défaut.
--enable-non-contiguous-regions
Cette option évite de générer une erreur si une section d'entrée ne correspond pas à une section de sortie correspondante. Le linker essaie d'allouer la section d'entrée aux sections de sortie correspondantes subséquentes, et ne génère une erreur que si aucune section de sortie n'est suffisamment grande. Ceci est utile lorsque plusieurs régions de mémoire non contiguës sont disponibles et que la section d'entrée ne nécessite pas l'une d'elles en particulier. L'ordre dans lequel les sections d'entrée sont évaluées ne change pas, par exemple : 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

avec les sections d'entrée :
.data.1: taille 8
.data.2: taille 0x10
.data.3: taille 4

résulte en .data.1 attribué à mem1, et .data.2 et .data.3
attribués à mem2, même si .data.3 tiendrait dans mem3.

Cette option est incompatible avec les instructions INSERT car elle modifie la manière dont les sections d'entrée sont mappées aux sections de sortie.

--enable-non-contiguous-regions-warnings
Cette option active les avertissements lorsque "--enable-non-contiguous-regions" permet des correspondances potentiellement inattendues dans le mappage des sections, conduisant potentiellement à ignorer silencieusement une section au lieu d'échouer parce qu'elle ne correspond à aucune région de sortie.
-e point-d-entrée
--entry=point-d-entrée
Utilise point-d-entrée comme symbole explicite pour commencer l'exécution de votre programme, plutôt que le point d'entrée par défaut. S'il n'y a pas de symbole nommé point-d-entrée, le linker essaiera d'analyser point-d-entrée comme un nombre et de l'utiliser comme adresse d'entrée (le nombre sera interprété en base 10 ; vous pouvez utiliser un préfixe 0x pour la base 16, ou un préfixe 0 pour la base 8).
--exclude-libs lib,lib,...
Spécifie une liste de bibliothèques d'archives dont les symboles ne doivent pas être exportés automatiquement. Les noms de bibliothèques peuvent être délimités par des virgules ou des deux-points. Spécifier "--exclude-libs ALL" exclut les symboles de toutes les bibliothèques d'archives de l'exportation automatique. Cette option n'est disponible que pour le port ciblé i386 PE du linker et pour les ports ciblés ELF. Pour i386 PE, les symboles explicitement listés dans un fichier .def sont toujours exportés, indépendamment de cette option. Pour les ports ciblés ELF, les symboles affectés par cette option seront traités comme cachés.
--exclude-modules-for-implib module,module,...
Spécifie une liste de fichiers objets ou de membres d'archive, à partir desquels les symboles ne doivent pas être exportés automatiquement, mais qui doivent être copiés tels quels dans la bibliothèque d'importation générée lors de la liaison. Les noms de modules peuvent être délimités par des virgules ou des deux-points, et doivent correspondre exactement aux noms de fichiers utilisés par ld pour ouvrir les fichiers ; pour les membres d'archive, il s'agit simplement du nom du membre, mais pour les fichiers objets, le nom listé doit inclure et correspondre précisément à tout chemin utilisé pour spécifier le fichier d'entrée sur la ligne de commande du linker. Cette option n'est disponible que pour le port ciblé i386 PE du linker. Les symboles explicitement listés dans un fichier .def sont toujours exportés, indépendamment de cette option.
-E
--export-dynamic
--no-export-dynamic
Lors de la création d'un exécutable lié dynamiquement, l'utilisation de l'option -E ou de l'option --export-dynamic fait que le linker ajoute tous les symboles à la table des symboles dynamiques. La table des symboles dynamiques est l'ensemble des symboles qui sont visibles depuis les objets dynamiques à l'exécution.

Si vous n'utilisez aucune de ces options (ou utilisez l'option --no-export-dynamic pour rétablir le comportement par défaut), la table des symboles dynamiques contiendra normalement uniquement les symboles qui sont référencés par un objet dynamique mentionné dans la liaison.

Si vous utilisez "dlopen" pour charger un objet dynamique qui doit faire référence aux symboles définis par le programme, plutôt qu'à un autre objet dynamique, vous devrez probablement utiliser cette option lors de la liaison du programme lui-même.

Vous pouvez également utiliser la liste dynamique pour contrôler quels symboles doivent être ajoutés à la table des symboles dynamiques si le format de sortie le prend en charge. Voir la description de --dynamic-list.

Notez que cette option est spécifique aux ports ciblés ELF. Les cibles PE prennent en charge une fonction similaire pour exporter tous les symboles d'une DLL ou d'un EXE ; voir la description de --export-all-symbols ci-dessous.

--export-dynamic-symbol=glob
Lors de la création d'un exécutable lié dynamiquement, les symboles correspondant à glob seront ajoutés à la table des symboles dynamiques. Lors de la création d'une bibliothèque partagée, les références aux symboles correspondant à glob ne seront pas liées aux définitions au sein de la bibliothèque partagée. Cette option est inopérante lors de la création d'une bibliothèque partagée et que -Bsymbolic ou --dynamic-list ne sont pas spécifiés. Cette option n'est significative que sur les plateformes ELF qui prennent en charge les bibliothèques partagées.
--export-dynamic-symbol-list=fichier
Spécifie un --export-dynamic-symbol pour chaque motif dans le fichier. Le format du fichier est le même que celui du nœud de version sans portée ni nom de nœud. Voir VERSION pour plus d'informations.
-EB
Lie des objets big-endian. Cela affecte le format de sortie par défaut.
-EL
Lie des objets little-endian. Cela affecte le format de sortie par défaut.
-f nom
--auxiliary=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_AUXILIARY au nom spécifié. Cela indique au linker dynamique que la table des symboles de l'objet partagé doit être utilisée comme un filtre auxiliaire sur la table des symboles de l'objet partagé nom.

Si vous liez ultérieurement un programme contre cet objet filtre, lorsque vous exécuterez le programme, le linker dynamique verra le champ DT_AUXILIARY. Si le linker dynamique résout des symboles à partir de l'objet filtre, il vérifiera d'abord s'il existe une définition dans l'objet partagé nom. S'il y en a une, elle sera utilisée à la place de la définition dans l'objet filtre. L'objet partagé nom n'a pas besoin d'exister. Ainsi, l'objet partagé nom peut être utilisé pour fournir une implémentation alternative de certaines fonctions, peut-être pour le débogage ou pour des performances spécifiques à la machine.

Cette option peut être spécifiée plusieurs fois. Les entrées DT_AUXILIARY seront créées dans l'ordre où elles apparaissent sur la ligne de commande.

-F nom
--filter=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_FILTER sur le nom spécifié. Cela indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé qui est en cours de création doit être utilisée comme filtre sur la table des symboles de l'objet partagé nom.

Si vous liez ultérieurement un programme à cet objet filtre, lorsque vous exécutez le programme, l'éditeur de liens dynamique verra le champ DT_FILTER. L'éditeur de liens dynamique résoudra les symboles conformément à la table des symboles de l'objet filtre comme d'habitude, mais il se liera en réalité aux définitions trouvées dans l'objet partagé nom. Ainsi, l'objet filtre peut être utilisé pour sélectionner un sous-ensemble des symboles fournis par l'objet nom.

Certains éditeurs de liens plus anciens utilisaient l'option -F tout au long d'une chaîne d'outils de compilation pour spécifier le format du fichier objet pour les fichiers objets d'entrée et de sortie. L'éditeur de liens GNU utilise d'autres mécanismes à cette fin : les options -b, --format, --oformat, la commande "TARGET" dans les scripts de l'éditeur de liens, et la variable d'environnement "GNUTARGET". L'éditeur de liens GNU ignorera l'option -F lorsqu'il ne crée pas un objet partagé ELF.

-fini=nom
Lors de la création d'un exécutable ELF ou d'un objet partagé, appelle NOM lors du déchargement de l'exécutable ou de l'objet partagé, en définissant DT_FINI sur l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_fini" comme fonction à appeler.
-g
Ignoré. Fourni pour la compatibilité avec d'autres outils.
-G valeur
--gpsize=valeur
Définit la taille maximale des objets à optimiser à l'aide du registre GP à taille. Ceci n'est pertinent que pour les formats de fichiers objets tels que MIPS ELF qui prennent en charge la mise des objets grands et petits dans des sections différentes. Ceci est ignoré pour d'autres formats de fichiers objets.
-h nom
-soname=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_SONAME sur le nom spécifié. Lorsqu'un exécutable est lié à un objet partagé qui a un champ DT_SONAME, alors lors de l'exécution de l'exécutable, l'éditeur de liens dynamique tentera de charger l'objet partagé spécifié par le champ DT_SONAME plutôt que d'utiliser le nom de fichier donné à l'éditeur de liens.
-i
Effectue une liaison incrémentielle (identique à l'option -r).
-init=nom
Lors de la création d'un exécutable ELF ou d'un objet partagé, appelle NOM lors du chargement de l'exécutable ou de l'objet partagé, en définissant DT_INIT sur l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_init" comme fonction à appeler.
-l spécification_nom
--library=spécification_nom
Ajoute l'archive ou le fichier objet spécifié par spécification_nom à la liste des fichiers à lier. Cette option peut être utilisée un nombre quelconque de fois. Si spécification_nom est de la forme :nomfichier, ld recherchera dans le chemin des bibliothèques un fichier nommé nomfichier, sinon il recherchera dans le chemin des bibliothèques un fichier nommé libspécification_nom.a.

Sur les systèmes qui prennent en charge les bibliothèques partagées, ld peut également rechercher des fichiers autres que libspécification_nom.a. Spécifiquement, sur les systèmes ELF et SunOS, ld recherchera dans un répertoire une bibliothèque nommée libspécification_nom.so avant de rechercher une nommée libspécification_nom.a. (Par convention, une extension ".so" indique une bibliothèque partagée.) Notez que ce comportement ne s'applique pas à :nomfichier, qui spécifie toujours un fichier nommé nomfichier.

L'éditeur de liens recherchera dans une archive une seule fois, à l'emplacement où elle est spécifiée dans la ligne de commande. Si l'archive définit un symbole qui était indéfini dans certains objets qui apparaissaient avant l'archive dans la ligne de commande, l'éditeur de liens inclura les fichiers appropriés de l'archive. Cependant, un symbole indéfini dans un objet apparaissant plus tard dans la ligne de commande ne provoquera pas une nouvelle recherche de l'archive par l'éditeur de liens.

Voir l'option -( pour une façon de forcer l'éditeur de liens à rechercher les archives plusieurs fois.

Vous pouvez spécifier la même archive plusieurs fois sur la ligne de commande.

Ce type de recherche d'archive est standard pour les éditeurs de liens Unix. Cependant, si vous utilisez ld sur AIX, notez que cela diffère du comportement de l'éditeur de liens AIX.

-L répertoire_recherche
--library-path=répertoire_recherche
Ajoute le chemin répertoire_recherche à la liste des chemins que ld recherchera pour les bibliothèques d'archives et les scripts de contrôle de ld. Vous pouvez utiliser cette option un nombre quelconque de fois. Les répertoires sont recherchés dans l'ordre où ils sont spécifiés sur la ligne de commande. Les répertoires spécifiés sur la ligne de commande sont recherchés avant les répertoires par défaut. Toutes les options -L s'appliquent à toutes les options -l, quel que soit l'ordre dans lequel les options apparaissent. Les options -L n'affectent pas la manière dont ld recherche un script d'éditeur de liens, sauf si l'option -T est spécifiée.

Si répertoire_recherche commence par "=" ou $SYSROOT, alors ce préfixe sera remplacé par le préfixe sysroot, contrôlé par l'option --sysroot, ou spécifié lors de la configuration de l'éditeur de liens.

L'ensemble par défaut des chemins recherchés (sans être spécifié avec -L) dépend du mode d'émulation que ld utilise, et dans certains cas également de la manière dont il a été configuré.

Les chemins peuvent également être spécifiés dans un script de lien avec la commande "SEARCH_DIR". Les répertoires spécifiés de cette manière sont recherchés au point où le script de lien apparaît dans la ligne de commande.

-m émulation
Émule l'éditeur de liens émulation. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.

Si l'option -m n'est pas utilisée, l'émulation est prise à partir de la variable d'environnement "LDEMULATION", si celle-ci est définie.

Sinon, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

--remap-inputs=motif=nomfichier
--remap-inputs-file=fichier
Ces options permettent de modifier les noms des fichiers d'entrée avant que l'éditeur de liens ne tente de les ouvrir. L'option --remap-inputs=foo.o=bar.o fera en sorte que toute tentative de chargement d'un fichier nommé foo.o tente plutôt de charger un fichier nommé bar.o. Les motifs génériques sont autorisés dans le premier nom de fichier, donc --remap-inputs=foo*.o=bar.o renommera tout fichier d'entrée correspondant à foo*.o en bar.o.

Une forme alternative de l'option --remap-inputs-file=nomfichier permet de lire les remappages à partir d'un fichier. Chaque ligne du fichier peut contenir un seul remappage. Les lignes vides sont ignorées. Tout ce qui suit un caractère dièse (#) jusqu'à la fin de la ligne est considéré comme un commentaire et est également ignoré. Le motif de mappage peut être séparé du nom de fichier par un espace blanc ou un caractère égal (=).

Les options peuvent être spécifiées plusieurs fois. Leur contenu s'accumule. Les remappages seront traités dans l'ordre où ils apparaissent dans la ligne de commande, et s'ils proviennent d'un fichier, dans l'ordre où ils apparaissent dans le fichier. Si une correspondance est trouvée, aucune vérification supplémentaire pour ce nom de fichier ne sera effectuée.

Si le nom de fichier de remplacement est /dev/null ou simplement NUL, alors le remappage provoquera en fait l'ignorance du fichier d'entrée. Cela peut être un moyen pratique d'expérimenter la suppression de fichiers d'entrée dans un environnement de construction compliqué.

Notez que cette option dépend de la position et n'affecte que les noms de fichiers qui la suivent dans la ligne de commande. Ainsi :

ld foo.o --remap-inputs=foo.o=bar.o

N'aura aucun effet, alors que :

ld --remap-inputs=foo.o=bar.o foo.o

Renommera le fichier d'entrée foo.o en bar.o.

Notez que ces options affectent également les fichiers référencés par les instructions INPUT dans les scripts de l'éditeur de liens. Mais comme les scripts de l'éditeur de liens sont traités après que toute la ligne de commande a été lue, la position des options de remappage dans la ligne de commande n'est pas significative.

Si l'option verbose est activée, tous les remappages correspondants seront signalés, bien que là encore l'option verbose doive être activée dans la ligne de commande avant l'apparition des noms de fichiers remappés.

Si les options -Map ou --print-map sont activées, la liste de remappage sera incluse dans la sortie de la carte.

-M
--print-map
Imprime une carte de liaison sur la sortie standard. Une carte de liaison fournit des informations sur la liaison, notamment :
  • Où les fichiers objets sont mappés en mémoire.
  • Comment les symboles communs sont alloués.
  • Tous les membres d'archive inclus dans la liaison, avec une mention du symbole qui a causé l'inclusion du membre d'archive.
  • Les valeurs attribuées aux symboles.

    Notez que les symboles dont les valeurs sont calculées par une expression qui implique une référence à une valeur précédente du même symbole peuvent ne pas avoir le résultat correct affiché dans la carte de liaison. En effet, l'éditeur de liens ignore les résultats intermédiaires et ne conserve que la valeur finale d'une expression. Dans de telles circonstances, l'éditeur de liens affichera la valeur finale entre crochets. Ainsi, par exemple, un script de liaison contenant :

    foo = 1
foo = foo * 4
foo = foo + 8

    Produira la sortie suivante dans la carte de liaison si l'option -M est utilisée :

    0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

This section describes some of the options to ld which are related to the information reported in the link map.

  • --info

    Prints information about linker script expressions.

  • How GNU properties are merged.

    When the linker merges input .note.gnu.property sections into one output .note.gnu.property section, some properties are removed or updated. These actions are reported in the link map. For example:

    Removed property 0xc0000002 to merge foo.o (0x1) and bar.o (not found)

    This indicates that property 0xc0000002 is removed from output when merging properties in foo.o, whose property 0xc0000002 value is 0x1, and bar.o, which doesn't have property 0xc0000002.

    Updated property 0xc0010001 (0x1) to merge foo.o (0x1) and bar.o (0x1)

    This indicates that property 0xc0010001 value is updated to 0x1 in output when merging properties in foo.o, whose 0xc0010001 property value is 0x1, and bar.o, whose 0xc0010001 property value is 0x1.

  • On some ELF targets, a list of fixups inserted by --relax 
    foo.o: Adjusting branch at 0x00000008 towards "far" in section .text

    This indicates that the branch at 0x00000008 in foo.o, targeting the symbol "far" in section .text, has been replaced by a trampoline.

The --push-state allows one to preserve the current state of the flags which govern the input file handling so that they can all be restored with one corresponding --pop-state option.

Les archives doivent être une liste de fichiers d'archives. Ils peuvent être des noms de fichiers explicites ou des options -l.

Les archives spécifiées sont recherchées de manière répétée jusqu'à ce qu'aucune nouvelle référence non résolue ne soit créée. Normalement, une archive n'est recherchée qu'une seule fois dans l'ordre où elle est spécifiée sur la ligne de commande. --warn-constructors
Avertir si des constructeurs globaux sont utilisés. Ceci n'est utile que pour quelques formats de fichiers objets. Pour des formats comme COFF ou ELF, l'éditeur de liens ne peut pas détecter l'utilisation de constructeurs globaux.
--warn-execstack
--warn-execstack-objects
--no-warn-execstack
Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il est demandé de créer un fichier de sortie contenant une pile exécutable. Il y a trois états possibles :
1.
Ne générer aucun avertissement.
2.
Générer toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
3.
Générer un avertissement uniquement si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa construction. L'option --no-warn-execstack place toujours l'éditeur de liens dans l'état sans avertissement. L'option --warn-execstack place l'éditeur de liens dans l'état d'avertissement permanent. L'option --warn-execstack-objects place l'éditeur de liens dans l'état d'avertissement uniquement pour les fichiers objets.

Note : les fichiers d'entrée au format ELF peuvent spécifier qu'ils nécessitent une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable activé dans ses drapeaux de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit d'exécution activé. Si un fichier d'entrée n'a pas de section .note.GNU-stack, le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable est requise. C'est souvent un problème pour les fichiers assembleurs créés à la main.

--error-execstack
--no-error-execstack
Si l'éditeur de liens est sur le point de générer un message d'avertissement concernant une pile exécutable, l'option --error-execstack transformera cet avertissement en une erreur. Remarque : cette option ne modifie pas l'état de génération des avertissements execstack de l'éditeur de liens. Utilisez --warn-execstack ou --warn-execstack-objects pour définir un état d'avertissement spécifique.

L'option --no-error-execstack rétablira le comportement par défaut de génération de messages d'avertissement.

--warn-multiple-gp
Avertir si plusieurs valeurs de pointeur global sont nécessaires dans le fichier de sortie. Ceci n'est significatif que pour certains processeurs, comme l'Alpha. Spécifiquement, certains processeurs placent les constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe au milieu de cette section, de sorte que les constantes peuvent être chargées efficacement via un mode d'adressage relatif au registre de base. Étant donné que le décalage en mode relatif au registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les grands programmes, il est souvent nécessaire d'utiliser plusieurs valeurs de pointeur global afin de pouvoir adresser toutes les constantes possibles. Cette option provoque un avertissement chaque fois que ce cas se produit.
--warn-once
Avertir une seule fois pour chaque symbole non défini, plutôt qu'une fois par module qui y fait référence.
--warn-rwx-segments
--no-warn-rwx-segments
Avertir si l'éditeur de liens crée un segment chargeable de taille non nulle qui a les trois drapeaux de permission lecture, écriture et exécution définis. Un tel segment représente une vulnérabilité de sécurité potentielle. De plus, des avertissements seront générés si un segment de stockage thread local est créé avec le drapeau de permission d'exécution défini, qu'il ait ou non les drapeaux de lecture et/ou d'écriture définis.

Ces avertissements sont activés par défaut. Ils peuvent être désactivés via l'option --no-warn-rwx-segments et réactivés via l'option --warn-rwx-segments.

L'option --no-error-rwx-segments rétablira le comportement par défaut de génération de messages d'avertissement.

Note : l'option --error-rwx-segments n'active pas en soi les avertissements concernant ces segments. Ces avertissements sont soit activés par défaut, si l'éditeur de liens a été configuré ainsi, soit via l'option de ligne de commande --warn-rwx-segments.

--whole-archive
Pour chaque archive mentionnée sur la ligne de commande après l'option --whole-archive, inclure chaque fichier objet de l'archive dans la liaison, plutôt que de rechercher l'archive pour les fichiers objets requis. Ceci est normalement utilisé pour transformer un fichier archive en une bibliothèque partagée, forçant chaque objet à être inclus dans la bibliothèque partagée résultante. Cette option peut être utilisée plusieurs fois.

Deux notes lors de l'utilisation de cette option depuis gcc : Premièrement, gcc ne connaît pas cette option, vous devez donc utiliser -Wl,-whole-archive. Deuxièmement, n'oubliez pas d'utiliser -Wl,-no-whole-archive après votre liste d'archives, car gcc ajoutera sa propre liste d'archives à votre liaison et vous ne voudrez peut-être pas que ce drapeau affecte celles-ci également.

--wrap=symbole
Utiliser une fonction d'enveloppement pour symbole. Toute référence non définie à symbole sera résolue en "__wrap_symbole". Toute référence non définie à "__real_symbole" sera résolue en symbole.

Ceci peut être utilisé pour fournir un enveloppement pour une fonction système. La fonction d'enveloppement doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

Voici un exemple trivial :

void *
__wrap_malloc (size_t c)
{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

Si vous liez un autre code avec ce fichier en utilisant --wrap malloc, tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc" appellera la fonction « malloc » réelle.

Vous voudrez peut-être fournir également une fonction « __real_malloc », afin que les liens sans l'option --wrap réussissent. Si vous le faites, vous ne devez pas mettre la définition de « __real_malloc » dans le même fichier que « __wrap_malloc » ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens n'ait la chance de le remplacer par « malloc ».

Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à l'unité de traduction vers symbol ne sont pas résolues en « __wrap_ symbol ». Dans l'exemple suivant, l'appel à « f » dans « g » n'est pas résolu en « __wrap_f ».

int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}

--enable-new-dtags
--disable-new-dtags
Cet éditeur de liens peut créer les nouvelles balises dynamiques dans ELF. Mais les anciens systèmes ELF peuvent ne pas les comprendre. Si vous spécifiez --enable-new-dtags, les nouvelles balises dynamiques seront créées au besoin et les anciennes balises dynamiques seront omises. Notez que ces options ne sont disponibles que pour les systèmes ELF.
--hash-size=nombre
Définit la taille par défaut des tables de hachage de l'éditeur de liens à un nombre premier proche de nombre. Augmenter cette valeur peut réduire le temps nécessaire à l'éditeur de liens pour effectuer ses tâches, au détriment d'une augmentation des besoins en mémoire de l'éditeur de liens. Inversement, réduire cette valeur peut réduire les besoins en mémoire au détriment de la vitesse.
--hash-style=style
Définit le type des tables de hachage de l'éditeur de liens. style peut être soit « sysv » pour la section classique ELF « .hash », « gnu » pour la nouvelle section GNU « .gnu.hash », ou « both » pour les tables de hachage classique ELF « .hash » et nouvelle GNU « .gnu.hash ». La valeur par défaut dépend de la manière dont l'éditeur de liens a été configuré, mais pour la plupart des systèmes basés sur Linux, ce sera « both ».
--compress-debug-sections=none
--compress-debug-sections=zlib
--compress-debug-sections=zlib-gnu
--compress-debug-sections=zlib-gabi
--compress-debug-sections=zstd
Sur les plateformes ELF, ces options contrôlent la compression des sections de débogage DWARF à l'aide de zlib.

--compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour commencer par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, elle définit l'indicateur SHF_COMPRESSED dans les en-têtes des sections.

L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

--compress-debug-sections=zstd compresse les sections de débogage DWARF à l'aide de zstd.

Notez que cette option remplace toute compression dans les sections de débogage d'entrée, donc si un binaire est lié avec --compress-debug-sections=none par exemple, alors toutes les sections de débogage compressées dans les fichiers d'entrée seront décompressées avant d'être copiées dans le binaire de sortie.

Le comportement de compression par défaut varie en fonction de la cible impliquée et des options de configuration utilisées pour construire la chaîne d'outils. La valeur par défaut peut être déterminée en examinant la sortie de l'option --help de l'éditeur de liens.

--reduce-memory-overheads
Cette option réduit les besoins en mémoire à l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération de fichiers de carte de liens, plutôt que le nouvel algorithme O(n) qui utilise environ 40 % de mémoire en plus pour le stockage des symboles.

Un autre effet de cette option est de définir la taille par défaut de la table de hachage à 1021, ce qui permet d'économiser de la mémoire au prix d'un temps d'exécution plus long pour l'éditeur de liens. Cependant, cela n'est pas fait si l'option --hash-size a été utilisée.

L'option --reduce-memory-overheads peut également être utilisée pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

--max-cache-size=taille
ld met normalement en cache les informations de relocalisation et les tables de symboles des fichiers d'entrée en mémoire avec une taille illimitée. Cette option définit la taille maximale du cache à taille.
--build-id
--build-id=style
Demande la création d'une section de note ELF « .note.gnu.build-id » ou d'une section COFF « .buildid ». Le contenu de la note identifie de manière unique ce fichier lié. style peut être « uuid » pour utiliser 128 bits aléatoires, « sha1 » pour utiliser un hachage SHA1 de 160 bits sur les parties normatives du contenu de sortie, « md5 » pour utiliser un hachage MD5 de 128 bits sur les parties normatives du contenu de sortie, ou « 0xchainehex » pour utiliser une chaîne de bits choisie spécifiée sous forme d'un nombre pair de chiffres hexadécimaux (les caractères « - » et « : » entre les paires de chiffres sont ignorés). Si style est omis, « sha1 » est utilisé.

Les styles « md5 » et « sha1 » produisent un identifiant qui est toujours le même dans un fichier de sortie identique, mais qui sera unique parmi tous les fichiers de sortie non identiques. Il n'est pas destiné à être comparé comme une somme de contrôle du contenu du fichier. Un fichier lié peut être modifié ultérieurement par d'autres outils, mais la chaîne de bits d'identification de construction identifiant le fichier lié d'origine ne change pas.

Passer « none » pour style désactive le paramètre de toute option « --build-id » antérieure sur la ligne de commande.

--package-metadata=JSON
Demande la création d'une section de note ELF « .note.package ». Le contenu de la note est au format JSON, conformément à la spécification des métadonnées de paquet. Pour plus d'informations, voir : https://systemd.io/ELF_PACKAGE_METADATA/ Si l'argument JSON est manquant/vide, cela désactivera la création de la note de métadonnées, si elle avait été activée par une occurrence antérieure de l'option --package-metadata. Si l'éditeur de liens a été construit avec libjansson, la chaîne JSON sera validée.

L'éditeur de liens PE i386 prend en charge l'option -shared, qui fait que la sortie est une bibliothèque liée dynamiquement (DLL) au lieu d'un exécutable normal. Vous devez nommer la sortie « *.dll » lorsque vous utilisez cette option. De plus, l'éditeur de liens prend en charge entièrement les fichiers standard « *.def », qui peuvent être spécifiés sur la ligne de commande de l'éditeur de liens comme un fichier objet (en fait, il doit précéder les archives dont il exporte des symboles, pour s'assurer qu'ils sont liés, tout comme un fichier objet normal).

En plus des options communes à toutes les cibles, l'éditeur de liens PE i386 prend en charge des options de ligne de commande supplémentaires spécifiques à la cible PE i386. Les options qui prennent des valeurs peuvent être séparées de leurs valeurs par un espace ou un signe égal.

--add-stdcall-alias
Si donné, les symboles avec un suffixe stdcall (@nn) seront exportés tels quels et également avec le suffixe retiré. [Cette option est spécifique au port ciblé PE i386 de l'éditeur de liens]

Crée une DLL au lieu d'un exécutable régulier. Vous pouvez également utiliser -shared ou spécifier une « LIBRARY » dans un fichier « .def » donné. [Cette option est spécifique au port ciblé PE i386 de l'éditeur de liens]
--enable-long-section-names
--disable-long-section-names
Les variantes PE du format objet COFF ajoutent une extension qui permet l'utilisation de noms de section plus longs que huit caractères, la limite normale pour COFF. Par défaut, ces noms sont seulement une
autorisé dans les fichiers objets, car les images exécutables entièrement liées ne transportent pas la table de chaînes COFF requise pour prendre en charge les noms plus longs. En tant qu'extension GNU, il est possible de permettre leur utilisation dans les images exécutables, ou de les interdire (probablement inutilement !) dans les fichiers objets, en utilisant ces deux options. Les images exécutables générées avec ces noms de section longs sont légèrement non standard, car elles transportent une table de chaînes, et peuvent générer une sortie confuse lorsqu'elles sont examinées avec des outils non-GNU sensibles aux PE, tels que des visualiseurs de fichiers et des dumpers. Cependant, GDB s'appuie sur l'utilisation des noms de section PE longs pour trouver les sections d'informations de débogage Dwarf-2 dans une image exécutable à l'exécution, et donc si aucune des options n'est spécifiée sur la ligne de commande, ld activera les noms de section longs, remplaçant le comportement par défaut et techniquement correct, lorsqu'il trouve la présence d'informations de débogage lors de la liaison d'une image exécutable et sans dépouiller les symboles. [Cette option est valide pour tous les ports cibles PE de l'éditeur de liens]
--enable-stdcall-fixup
--disable-stdcall-fixup

Par exemple, le symbole indéfini « _foo » pourrait être lié à la fonction « _foo@12 », ou le symbole indéfini « _bar@16 » pourrait être lié à la fonction « _bar ». Si vous spécifiez --enable-stdcall-fixup, cette fonctionnalité est entièrement activée et les avertissements ne sont pas imprimés. Si vous spécifiez --disable-stdcall-fixup, cette fonctionnalité est désactivée et de telles divergences sont considérées comme des erreurs. Note : L'utilisation de l'extension 'auto-import' rendra la section texte du fichier image inscriptible. Ceci n'est pas conforme à la spécification du format PE-COFF publiée par Microsoft.

Note - l'utilisation de l'extension 'auto-import' entraînera également le placement des données en lecture seule qui seraient normalement placées dans la section .rdata dans la section .data à la place. Ceci afin de contourner un problème avec les constantes qui est décrit ici : http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

L'utilisation de 'auto-import' fonctionnera généralement 'juste bien' -- mais parfois vous pourriez voir ce message :

"la variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de ld pour "--enable-auto-import" pour plus de détails."

Ce message survient lorsque certaines (sous-)expressions accèdent à une adresse donnée ultimement par la somme de deux constantes (les tables d'importation Win32 n'en autorisent qu'une). Les instances où cela peut se produire incluent les accès aux champs de membres de variables struct importées d'une DLL, ainsi que l'utilisation d'un indice constant dans une variable tableau importée d'une DLL. Toute variable multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, indépendamment du type de données exact de la variable exportée fautive, ld la détectera toujours, émettra l'avertissement et se terminera.

Il existe plusieurs façons de résoudre cette difficulté, indépendamment du type de données de la variable exportée :

Une façon est d'utiliser l'interrupteur --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client à l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution supporte cette fonctionnalité.

Une deuxième solution est de forcer l'une des 'constantes' à être une variable -- c'est-à-dire, inconnue et non optimisable au moment de la compilation. Pour les tableaux, il y a deux possibilités : a) faire de l'indexé (l'adresse du tableau) une variable, ou b) faire de l'indice 'constant' une variable. Donc :

extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

ou

extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

Pour les structures (et la plupart des autres types de données multi-mots), la seule option est de faire de la structure elle-même (ou du long long, ou du ...) une variable :

extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

ou

extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

Une troisième méthode pour traiter cette difficulté est d'abandonner 'auto-import' pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #define au moment de la compilation pour indiquer si vous construisez une DLL, si vous construisez du code client qui se liera à la DLL, ou si vous construisez/liez simplement à une bibliothèque statique. Lors du choix entre les différentes méthodes de résolution du problème 'adresse directe avec décalage constant', vous devriez considérer l'utilisation réelle typique :

Original :

--foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

Solution 1 :

--foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

Solution 2 :

--foo.h
/* Note : auto-export est supposé (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

Une quatrième façon d'éviter ce problème est de recoder votre bibliothèque pour utiliser une interface fonctionnelle plutôt qu'une interface de données pour les variables fautives (par exemple, des fonctions d'accès set_foo() et get_foo()).

-N
--omagic
Marque la sortie comme "OMAGIC" (0407) dans l'en-tête a.out pour indiquer que le segment de texte ne doit pas être protégé en écriture et partagé. Étant donné que les segments de texte et de données sont tous deux lisibles et inscriptibles, le segment de données est alloué immédiatement après le segment de texte. -n
--nmagic
Marque la sortie comme "NMAGIC" (0410) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie sera exécuté, la partie texte sera en lecture seule et partageable entre tous les processus exécutant le même fichier. -z
--imagic
Marque la sortie comme "IMAGIC" (0411) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie sera exécuté, les zones de texte et de données du programme seront chargées dans des espaces d'adressage séparés en utilisant la fonction de division des instructions et des données de l'unité de gestion de mémoire dans les modèles plus grands du PDP11. ENVIRONNEMENT

Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

"GNUTARGET" détermine le format d'objet des fichiers d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini à "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers d'entrée binaires ; cette méthode réussit souvent, mais il existe des ambiguïtés potentielles, car il n'y a pas de méthode pour garantir que le nombre magique utilisé pour spécifier les formats de fichiers objet est unique. Cependant, la procédure de configuration pour BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

"LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement de l'éditeur de liens, en particulier le script de l'éditeur de liens par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

Normalement, l'éditeur de liens par défaut désangglobe les symboles. Cependant, si "COLLECT_NO_DEMANGLE

" est définie dans l'environnement, alors elle sera par défaut à ne pas démangler les symboles. Cette variable d'environnement est utilisée de manière similaire par le programme d'enveloppement de l'éditeur de liens "gcc". La valeur par défaut peut être remplacée par les options --demangle et --no-demangle.
