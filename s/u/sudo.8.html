sudo(8)

Paquet: sudo

Licences: custom

SUDO(8) Manuel du gestionnaire système SUDO(8)

NOM

sudo, sudoedit — exécuter une commande en tant qu'un autre utilisateur

SYNTAXE

sudo -h | -K | -k | -V

sudo -v [-ABkNnS] [-g groupe] [-h hôte] [-p invite] [-u utilisateur]

sudo -l [-ABkNnS] [-g groupe] [-h hôte] [-p invite] [-U utilisateur] [-u utilisateur] [commande [arg ...]]

sudo [-ABbEHnPS] [-C num] [-D répertoire] [-g groupe] [-h hôte] [-p invite] [-R répertoire] [-T délai] [-u utilisateur] [VAR=valeur] [-i | -s] [commande [arg ...]]

sudoedit [-ABkNnS] [-C num] [-D répertoire] [-g groupe] [-h hôte] [-p invite] [-R répertoire] [-T délai] [-u utilisateur] fichier ...

DESCRIPTION

sudo permet à un utilisateur autorisé d'exécuter une commande en tant que superutilisateur ou un autre utilisateur, comme spécifié par la politique de sécurité. L'ID utilisateur réel de l'utilisateur appelant (et non l'ID utilisateur effectif) est utilisé pour déterminer le nom d'utilisateur avec lequel interroger la politique de sécurité.

sudo prend en charge une architecture de plugins pour les politiques de sécurité, l'audit et la journalisation des entrées/sorties. Des tiers peuvent développer et distribuer leurs propres plugins pour fonctionner de manière transparente avec le frontal sudo. La politique de sécurité par défaut est sudoers, configurée via le fichier /etc/sudoers, ou via LDAP. Voir la section Plugins pour plus d'informations.

La politique de sécurité détermine quels privilèges, le cas échéant, un utilisateur a pour exécuter sudo. La politique peut exiger que les utilisateurs s'authentifient avec un mot de passe ou un autre mécanisme d'authentification. Si l'authentification est requise, sudo se terminera si le mot de passe de l'utilisateur n'est pas entré dans un délai limite configurable. Cette limite est spécifique à la politique ; le délai limite par défaut pour l'invite de mot de passe pour la politique de sécurité sudoers est de 5 minutes.

Les politiques de sécurité peuvent prendre en charge la mise en cache des identifiants pour permettre à l'utilisateur d'exécuter à nouveau sudo pendant une période donnée sans nécessiter d'authentification. Par défaut, la politique sudoers met en cache les identifiants par terminal pendant 5 minutes. Voir les options timestamp_type et timestamp_timeout dans sudoers(5) pour plus d'informations. En exécutant sudo avec l'option -v, un utilisateur peut mettre à jour les identifiants en cache sans exécuter de commande.

Sur les systèmes où sudo est la méthode principale pour obtenir des privilèges de superutilisateur, il est impératif d'éviter les erreurs de syntaxe dans les fichiers de configuration de la politique de sécurité. Pour la politique de sécurité par défaut, sudoers(5), les modifications des fichiers de configuration doivent être effectuées à l'aide de l'utilitaire visudo(8), qui garantira qu'aucune erreur de syntaxe n'est introduite.

Lorsqu'il est invoqué sous le nom sudoedit, l'option -e (décrite ci-dessous) est implicite.

Les politiques de sécurité et les plugins d'audit peuvent enregistrer les tentatives réussies et échouées d'exécution de sudo. Si un plugin d'E/S est configuré, l'entrée et la sortie de la commande en cours d'exécution peuvent également être enregistrées.

Les options sont les suivantes :

-A, --askpass
Normalement, si sudo nécessite un mot de passe, il le lit depuis le terminal de l'utilisateur. Si l'option -A (askpass) est spécifiée, un programme d'aide (éventuellement graphique) est exécuté pour lire le mot de passe de l'utilisateur et l'afficher sur la sortie standard. Si la variable d'environnement SUDO_ASKPASS est définie, elle spécifie le chemin vers le programme d'aide. Sinon, si sudo.conf(5) contient une ligne spécifiant le programme askpass, cette valeur sera utilisée. Par exemple : 
# Chemin vers le programme d'aide askpass
Path askpass /usr/X11R6/bin/ssh-askpass

Si aucun programme askpass n'est disponible, sudo se terminera avec une erreur.

-B, --bell
Sonner la cloche dans le cadre de l'invite de mot de passe lorsqu'un terminal est présent. Cette option n'a aucun effet si un programme askpass est utilisé.
-b, --background
Exécuter la commande spécifiée en arrière-plan. Il n'est pas possible d'utiliser le contrôle de job du shell pour manipuler les processus d'arrière-plan démarrés par sudo. La plupart des commandes interactives ne fonctionneront pas correctement en mode arrière-plan.
-C num, --close-from=num
Fermer tous les descripteurs de fichiers supérieurs ou égaux à num avant d'exécuter une commande. Les valeurs inférieures à trois ne sont pas autorisées. Par défaut, sudo fermera tous les descripteurs de fichiers ouverts autres que l'entrée standard, la sortie standard et l'erreur standard lors de l'exécution d'une commande. La politique de sécurité peut restreindre la capacité de l'utilisateur à utiliser cette option. La politique sudoers n'autorise l'utilisation de l'option -C que lorsque l'administrateur a activé l'option closefrom_override.
-D répertoire, --chdir=répertoire
Exécuter la commande dans le répertoire spécifié au lieu du répertoire de travail actuel. La politique de sécurité peut renvoyer une erreur si l'utilisateur n'a pas la permission de spécifier le répertoire de travail.
-E, --preserve-env
Indique à la politique de sécurité que l'utilisateur souhaite conserver ses variables d'environnement existantes. La politique de sécurité peut renvoyer une erreur si l'utilisateur n'a pas la permission de conserver l'environnement.
=list">--preserve-env=list
Indique à la politique de sécurité que l'utilisateur souhaite ajouter la liste de variables d'environnement séparées par des virgules à celles préservées de l'environnement de l'utilisateur. La politique de sécurité peut renvoyer une erreur si l'utilisateur n'a pas l'autorisation de préserver l'environnement. Cette option peut être spécifiée plusieurs fois.
-e, --edit
Modifier un ou plusieurs fichiers (file) au lieu d'exécuter une commande (command). Au lieu d'un nom de chemin, la chaîne « sudoedit » est utilisée lors de la consultation de la politique de sécurité. Si l'utilisateur est autorisé par la politique, les étapes suivantes sont suivies :
  1. Des copies temporaires des fichiers à modifier sont créées avec le propriétaire défini sur l'utilisateur appelant.
  2. L'éditeur spécifié par la politique est exécuté pour modifier les fichiers temporaires. La politique sudoers utilise les variables d'environnement SUDO_EDITOR, VISUAL et EDITOR (dans cet ordre). Si aucune des variables SUDO_EDITOR, VISUAL ou EDITOR n'est définie, le premier programme listé dans l'option editor de sudoers(5) est utilisé.
  3. S'ils ont été modifiés, les fichiers temporaires sont copiés à leur emplacement d'origine et les versions temporaires sont supprimées.

Pour aider à prévenir la modification de fichiers non autorisés, les restrictions suivantes sont appliquées, sauf autorisation explicite de la politique de sécurité :

  • Les liens symboliques ne peuvent pas être modifiés (version 1.8.15 et supérieures).
  • Les liens symboliques sur le chemin à modifier ne sont pas suivis lorsque le répertoire parent est inscriptible par l'utilisateur appelant, sauf si cet utilisateur est root (version 1.8.16 et supérieures).
  • Les fichiers situés dans un répertoire inscriptible par l'utilisateur appelant ne peuvent pas être modifiés, sauf si cet utilisateur est root (version 1.8.16 et supérieures).

Les utilisateurs ne sont jamais autorisés à modifier les fichiers spéciaux de périphériques.

Si le fichier spécifié n'existe pas, il sera créé. Contrairement à la plupart des commandes (command) exécutées par sudo, l'éditeur est exécuté avec l'environnement de l'utilisateur appelant non modifié. Si le fichier temporaire devient vide après modification, l'utilisateur sera invité avant qu'il ne soit installé. Si, pour une raison quelconque, sudo ne parvient pas à mettre à jour un fichier avec sa version modifiée, l'utilisateur recevra un avertissement et la copie modifiée restera dans un fichier temporaire.

-g group, --group=group
Exécute la commande (command) avec le groupe principal défini sur group au lieu du groupe principal spécifié dans l'entrée de la base de données de mots de passe de l'utilisateur cible. Le group peut être soit un nom de groupe, soit un identifiant de groupe numérique (GID) précédé du caractère « # » (par exemple, « #0 » pour le GID 0). Lors de l'exécution d'une commande (command) en tant que GID, de nombreux shells exigent que le « # » soit échappé avec une barre oblique inverse (« \ »). Si aucune option -u n'est spécifiée, la commande (command) sera exécutée en tant qu'utilisateur appelant. Dans les deux cas, le groupe principal sera défini sur group. La politique sudoers permet que n'importe lequel des groupes de l'utilisateur cible soit spécifié via l'option -g tant que l'option -P n'est pas utilisée.
-H, --set-home
Demande à la politique de sécurité de définir la variable d'environnement HOME sur le répertoire personnel spécifié dans l'entrée de la base de données de mots de passe de l'utilisateur cible. Selon la politique, cela peut être le comportement par défaut.
-h, --help
Affiche un court message d'aide sur la sortie standard et quitte.
-h host, --host=host
Exécute la commande (command) sur l'hôte (host) spécifié si le plugin de politique de sécurité prend en charge les commandes distantes (command). Le plugin sudoers ne prend pas actuellement en charge l'exécution de commandes distantes (command). Ceci peut également être utilisé en conjonction avec l'option -l pour lister les privilèges d'un utilisateur pour l'hôte distant.
-i, --login
Exécute le shell spécifié dans l'entrée de la base de données de mots de passe de l'utilisateur cible en tant que shell de connexion. Cela signifie que les fichiers de ressources spécifiques à la connexion tels que .profile, .bash_profile, ou .login seront lus par le shell. Si une commande (command) est spécifiée, elle est passée au shell en tant que simple commande (command) en utilisant l'option -c. La commande (command) et ses éventuels arguments (arg) sont concaténés, séparés par des espaces, après échappement de chaque caractère (y compris les espaces blancs) avec une barre oblique inverse (« \ ») à l'exception des alphanumériques, des underscores, des tirets et des signes dollar. Si aucune commande (command) n'est spécifiée, un shell interactif est exécuté. sudo tente de se déplacer dans le répertoire personnel de cet utilisateur avant d'exécuter le shell. La commande (command) est exécutée avec un environnement similaire à celui qu'un utilisateur recevrait lors de la connexion. La plupart des shells se comportent différemment lorsqu'une commande (command) est spécifiée par rapport à une session interactive ; consultez le manuel du shell pour plus de détails. La section Environnement de commande du manuel sudoers(5) documente comment l'option -i affecte l'environnement dans lequel une commande (command) est exécutée lorsque la politique sudoers est utilisée.
-K, --remove-timestamp
Similaire à l'option -k, sauf qu'elle supprime tous les identifiants mis en cache pour l'utilisateur, indépendamment du terminal ou de l'identifiant du processus parent. La prochaine fois que sudo sera exécuté, un mot de passe devra être saisi si la politique de sécurité l'exige. Il n'est pas possible d'utiliser l'option -K en conjonction avec une commande (command) ou une autre option. Cette option ne requiert pas de mot de passe. Toutes les politiques de sécurité ne prennent pas en charge la mise en cache des identifiants.
-k, --reset-timestamp
Lorsqu'elle est utilisée sans commande (command), invalide les identifiants mis en cache de l'utilisateur pour la session courante. La prochaine fois que sudo sera exécuté dans la session, un mot de passe devra être saisi si la politique de sécurité l'exige. Par défaut, la politique sudoers utilise un enregistrement séparé dans le cache d'identifiants pour chaque terminal (ou identifiant de processus parent s'il n'y a pas de terminal). Cela empêche l'option -k d'interférer avec les commandes sudo exécutées dans une autre session de terminal. Voir l'option timestamp_type dans sudoers(5) pour plus d'informations. Cette option ne requiert pas de mot de passe et a été ajoutée pour permettre à un utilisateur de révoquer les autorisations sudo à partir d'un fichier .logout.

Lorsqu'elle est utilisée en conjonction avec une commande (command) ou une option qui peut nécessiter un mot de passe, cette option amène sudo à ignorer les identifiants mis en cache de l'utilisateur. Par conséquent, sudo demandera un mot de passe (si la politique de sécurité l'exige) et ne mettra pas à jour les identifiants mis en cache de l'utilisateur.

Toutes les politiques de sécurité ne prennent pas en charge la mise en cache des identifiants.

-l, --list
Si aucune commande (command) n'est spécifiée, liste les privilèges de l'utilisateur appelant (ou de l'utilisateur (user) spécifié par l'option -U) sur l'hôte actuel. Un format de liste plus long est utilisé si cette option est spécifiée plusieurs fois et que la politique de sécurité prend en charge un format de sortie détaillé.

Si une commande (command) est spécifiée et est autorisée par la politique de sécurité pour l'utilisateur appelant (ou l'utilisateur (user) spécifié par l'option -U) sur l'hôte actuel, le chemin d'accès complet à la commande (command) est affiché ainsi que tous les arguments (arg). Si -l est spécifié plusieurs fois (et que la politique de sécurité le prend en charge), la règle correspondante est affichée dans un format détaillé avec la commande (command). Si une commande (command) est spécifiée mais non autorisée par la politique, sudo quittera avec un statut de 1.

-N, --no-update
Ne met pas à jour les identifiants mis en cache de l'utilisateur, même si l'utilisateur s'authentifie avec succès. Contrairement au drapeau -k, les identifiants mis en cache existants sont utilisés s'ils sont valides. Pour détecter quand les identifiants mis en cache de l'utilisateur sont valides (ou quand aucune authentification n'est requise), ce qui suit peut être utilisé : 
sudo -Nnv

Toutes les politiques de sécurité ne prennent pas en charge la mise en cache des identifiants.

-n, --non-interactive
Évite de demander à l'utilisateur une saisie de quelque type que ce soit. Si un mot de passe est requis pour exécuter la commande (command), sudo affichera un message d'erreur et quittera.
-P, --preserve-groups
Préserver le vecteur de groupe de l'utilisateur appelant sans modification. Par défaut, la politique sudoers initialisera le vecteur de groupe avec la liste des groupes dont l'utilisateur cible est membre. Les identifiants réels et effectifs de groupe, cependant, seront toujours définis pour correspondre à l'utilisateur cible.
-p prompt, --prompt=prompt
Utiliser une invite de mot de passe personnalisée avec des séquences d'échappement optionnelles. Les séquences d'échappement suivantes avec un signe de pourcentage (‘%’) sont supportées par la politique sudoers :
%H
développé en nom d'hôte incluant le nom de domaine (uniquement si le nom d'hôte de la machine est entièrement qualifié ou si l'option fqdn est définie dans sudoers(5))
%h
développé en nom d'hôte local sans le nom de domaine
%p
développé en nom de l'utilisateur dont le mot de passe est demandé (respecte les drapeaux rootpw, targetpw, et runaspw dans sudoers(5))
%U
développé en nom de connexion de l'utilisateur pour lequel la commande sera exécutée (par défaut root sauf si l'option -u est également spécifiée)
%u
développé en nom de connexion de l'utilisateur appelant
%%
deux caractères ‘%’ consécutifs sont fusionnés en un seul caractère ‘%’

L'invite personnalisée remplacera l'invite par défaut spécifiée par la politique de sécurité ou la variable d'environnement SUDO_PROMPT. Sur les systèmes utilisant PAM, l'invite personnalisée remplacera également l'invite spécifiée par un module PAM, sauf si le drapeau passprompt_override est désactivé dans sudoers.

-R répertoire, --chroot=répertoire
Changer pour le répertoire racine spécifié (voir chroot(8)) avant d'exécuter la commande. La politique de sécurité peut retourner une erreur si l'utilisateur n'a pas la permission de spécifier le répertoire racine.

Cette option est obsolète et sera supprimée dans une future version de sudo.

-S, --stdin
Écrire l'invite sur la sortie d'erreur standard et lire le mot de passe depuis l'entrée standard au lieu d'utiliser le périphérique terminal.
-s, --shell
Exécuter le shell spécifié par la variable d'environnement SHELL s'il est défini ou le shell spécifié dans l'entrée de la base de données du mot de passe de l'utilisateur appelant. Si une commande est spécifiée, elle est passée au shell comme une commande simple en utilisant l'option -c. La commande et tous ses arguments sont concaténés, séparés par des espaces, après l'échappement de chaque caractère (y compris les espaces blancs) avec une barre oblique inversée (‘\’) à l'exception des alphanumériques, des soulignements, des tirets et des signes dollar. Si aucune commande n'est spécifiée, un shell interactif est exécuté. La plupart des shells se comportent différemment lorsqu'une commande est spécifiée par rapport à une session interactive ; consultez le manuel du shell pour plus de détails.
-U utilisateur, --other-user=utilisateur
Utilisé en conjonction avec l'option -l pour lister les privilèges de utilisateur au lieu de ceux de l'utilisateur appelant. La politique de sécurité peut restreindre la liste des privilèges d'autres utilisateurs. Lors de l'utilisation de la politique sudoers, l'option -U est limitée à l'utilisateur root et aux utilisateurs ayant soit le privilège « list » pour l'utilisateur spécifié, soit la capacité d'exécuter n'importe quelle commande en tant que root ou utilisateur sur l'hôte actuel.
-T délai, --command-timeout=délai
Utilisé pour définir un délai pour la commande. Si le délai expire avant que la commande ne soit terminée, la commande sera terminée. La politique de sécurité peut restreindre la capacité de l'utilisateur à définir des délais. La politique sudoers exige que les délais spécifiés par l'utilisateur soient explicitement activés.
-u utilisateur, --user=utilisateur
Exécuter la commande en tant qu'utilisateur autre que l'utilisateur cible par défaut (généralement root). L'utilisateur peut être soit un nom d'utilisateur, soit un identifiant utilisateur (UID) numérique précédé du caractère ‘#’ (par exemple, ‘#0’ pour l'UID 0). Lors de l'exécution de commandes avec un UID, de nombreux shells exigent que le ‘#’ soit échappé avec une barre oblique inversée (‘\’). Certaines politiques de sécurité peuvent restreindre les UID à ceux listés dans la base de données des mots de passe. La politique sudoers autorise les UID qui ne sont pas dans la base de données des mots de passe tant que l'option targetpw n'est pas définie. D'autres politiques de sécurité peuvent ne pas supporter cela.
-V, --version
Afficher la chaîne de version de sudo ainsi que la chaîne de version de tous les plugins configurés. Si l'utilisateur appelant est déjà root, l'option -V affichera les options passées à configure lors de la compilation de sudo ; les plugins peuvent afficher des informations supplémentaires telles que les options par défaut.
-v, --validate
Mettre à jour les informations d'identification mises en cache de l'utilisateur, en authentifiant l'utilisateur si nécessaire. Pour le plugin sudoers, cela prolonge le délai sudo de 5 minutes supplémentaires par défaut, mais n'exécute pas de commande. Toutes les politiques de sécurité ne prennent pas en charge les informations d'identification mises en cache.
--
Le -- est utilisé pour délimiter la fin des options de sudo. Les options suivantes sont passées à la commande.

Les options qui prennent une valeur ne peuvent être spécifiées qu'une seule fois, sauf indication contraire dans la description. Ceci vise à se protéger contre les problèmes causés par des scripts mal écrits qui invoquent sudo avec une entrée contrôlée par l'utilisateur.

Les variables d'environnement à définir pour la commande peuvent également être passées comme options à sudo sous la forme VAR=valeur, par exemple LD_LIBRARY_PATH=/usr/local/pkg/lib. Les variables d'environnement peuvent être soumises à des restrictions imposées par le plugin de politique de sécurité. La politique sudoers soumet les variables d'environnement passées comme options aux mêmes restrictions que les variables d'environnement existantes, avec une différence importante. Si l'option setenv est définie dans sudoers, que la commande à exécuter a le tag SETENV défini ou que la commande correspondante est ALL, l'utilisateur peut définir des variables qui seraient autrement interdites. Voir sudoers(5) pour plus d'informations.

EXÉCUTION DES COMMANDES

Lorsque sudo exécute une commande, la politique de sécurité spécifie l'environnement d'exécution de la commande. Typiquement, les identifiants utilisateur et groupe réels et effectifs sont définis pour correspondre à ceux de l'utilisateur cible, tels que spécifiés dans la base de données des mots de passe, et le vecteur de groupe est initialisé en fonction de la base de données des groupes (sauf si l'option -P a été spécifiée).

Les paramètres suivants peuvent être spécifiés par la politique de sécurité :

  • identifiant utilisateur réel et effectif
  • identifiant groupe réel et effectif
  • identifiants de groupe supplémentaires
  • la liste d'environnement
  • répertoire de travail courant
  • masque de création de fichier (umask)
  • priorité de planification (alias valeur nice)

Modèle de processus

Il existe deux manières distinctes pour sudo d'exécuter une commande.

Si un plugin de journalisation d'E/S est configuré pour journaliser les E/S du terminal, ou si la politique de sécurité le demande explicitement, un nouveau pseudo-terminal (pty) est alloué et fork(2) est utilisé pour créer un second processus sudo, appelé le moniteur. Le moniteur crée une nouvelle session de terminal avec lui-même comme leader et le pty comme son terminal de contrôle, appelle à nouveau fork(2), configure l'environnement d'exécution comme décrit ci-dessus, puis utilise l'appel système execve(2) pour exécuter la commande dans le processus enfant. Le moniteur existe pour relayer les signaux de contrôle de tâche entre le terminal de l'utilisateur et le pty dans lequel la commande est exécutée. Cela permet de suspendre et de reprendre normalement la commande. Sans le moniteur, la commande serait dans ce que POSIX appelle un « groupe de processus orphelin » et ne recevrait aucun signal de contrôle de tâche du noyau. Lorsque la >commande se termine ou est terminée par un signal, le moniteur transmet le statut de sortie de la commande au processus sudo principal et se termine. Après avoir reçu le statut de sortie de la commande, le processus sudo principal transmet le statut de sortie de la commande à la fonction de fermeture de la politique de sécurité, ainsi qu'à la fonction de fermeture de tout plugin d'audit configuré, et se termine. Ce mode est le mode par défaut pour les versions de sudo 1.9.14 et supérieures lors de l'utilisation de la politique sudoers.

Si aucun pty n'est utilisé, sudo appelle fork(2), configure l'environnement d'exécution comme décrit ci-dessus, et utilise l'appel système execve(2) pour exécuter la commande dans le processus enfant. Le processus sudo principal attend que la commande soit terminée, puis transmet le statut de sortie de la commande à la fonction de fermeture de la politique de sécurité, ainsi qu'à la fonction de fermeture de tout plugin d'audit configuré, et se termine. Dans un cas spécial, si le plugin de politique ne définit pas de fonction de fermeture, sudo exécutera directement la commande au lieu d'appeler d'abord fork(2). Le plugin de politique sudoers ne définira une fonction de fermeture que lorsque la journalisation I/O est activée, qu'un pty est requis, qu'un rôle SELinux est spécifié, que la commande a un délai d'attente associé, ou que les options pam_session ou pam_setcred sont activées. Les deux pam_session et pam_setcred sont activés par défaut sur les systèmes utilisant PAM. Ce mode est le mode par défaut pour les versions de sudo antérieures à 1.9.14 lors de l'utilisation de la politique sudoers.

Sur les systèmes qui utilisent PAM, la fonction de fermeture de la politique de sécurité est responsable de la fermeture de la session PAM. Elle peut également enregistrer le statut de sortie de la commande.

Gestion des signaux

Lorsque la commande est exécutée en tant qu'enfant du processus sudo, sudo relaye les signaux qu'il reçoit à la commande. Les signaux SIGINT et SIGQUIT ne sont relayés que lorsque la commande est exécutée dans un nouveau pty ou lorsque le signal a été envoyé par un processus utilisateur, et non par le noyau. Cela empêche la commande de recevoir SIGINT deux fois chaque fois que l'utilisateur entre Ctrl+C. Certains signaux, tels que SIGSTOP et SIGKILL, ne peuvent pas être interceptés et ne seront donc pas relayés à la commande. En règle générale, SIGTSTP doit être utilisé à la place de SIGSTOP lorsque vous souhaitez suspendre une commande exécutée par sudo.

Dans un cas spécial, sudo ne relaye pas les signaux qui ont été envoyés par la commande qu'il exécute. Cela empêche la commande de se tuer accidentellement. Sur certains systèmes, l'utilitaire reboot(8) envoie SIGTERM à tous les processus non système autres que lui-même avant de redémarrer le système. Cela empêche sudo de relayer le signal SIGTERM qu'il a reçu à reboot(8), qui pourrait alors se terminer avant que le système ne soit réellement redémarré, le laissant dans un état semi-mort similaire au mode mono-utilisateur. Notez, cependant, que cette vérification ne s'applique qu'à la commande exécutée par sudo et non à tout autre processus que la commande pourrait créer. Par conséquent, exécuter un script qui appelle reboot(8) ou shutdown(8) via sudo peut entraîner le système dans cet état indéfini, sauf si reboot(8) ou shutdown(8) sont exécutés à l'aide de la famille de fonctions exec() au lieu de system() (qui interpose un shell entre la commande et le processus appelant).

Plugins

Les plugins peuvent être spécifiés via les directives Plugin dans le fichier sudo.conf(5). Ils peuvent être chargés en tant qu'objets partagés dynamiques (sur les systèmes qui les prennent en charge), ou compilés directement dans le binaire sudo. Si aucun fichier sudo.conf(5) n'est présent, ou s'il ne contient aucune ligne Plugin, sudo utilisera sudoers(5) pour les plugins de politique, d'audit et de journalisation I/O. Voir le manuel sudo.conf(5) pour les détails du fichier /etc/sudo.conf et le manuel sudo_plugin(5) pour plus d'informations sur l'architecture des plugins de sudo.

VALEUR DE SORTIE

Lors de l'exécution réussie d'une commande, le statut de sortie de sudo sera le statut de sortie du programme qui a été exécuté. Si la commande s'est terminée suite à la réception d'un signal, sudo s'enverra le même signal qui a terminé la commande.

Si l'option -l a été spécifiée sans commande, sudo se terminera avec une valeur de 0 si l'utilisateur est autorisé à exécuter sudo et s'il s'est authentifié avec succès (comme requis par la politique de sécurité). Si une commande est spécifiée avec l'option -l, la valeur de sortie ne sera 0 que si la commande est autorisée par la politique de sécurité, sinon elle sera 1.

En cas d'échec d'authentification, de problème de configuration/permission, ou si la commande donnée ne peut être exécutée, sudo se termine avec une valeur de 1. Dans ce dernier cas, la chaîne d'erreur est imprimée sur la sortie d'erreur standard. Si sudo ne parvient pas à stat(2) une ou plusieurs entrées dans le PATH de l'utilisateur, une erreur est imprimée sur la sortie d'erreur standard. (Si le répertoire n'existe pas ou s'il ne s'agit pas réellement d'un répertoire, l'entrée est ignorée et aucune erreur n'est imprimée.) Cela ne devrait pas arriver dans des circonstances normales. La raison la plus courante pour laquelle stat(2) renvoie « permission refusée » est si vous utilisez un automonteur et que l'un des répertoires de votre PATH se trouve sur une machine qui est actuellement inaccessible.

NOTES DE SÉCURITÉ

sudo essaie d'être sûr lors de l'exécution de commandes externes.

Pour empêcher l'usurpation de commande, sudo vérifie le répertoire courant (« . ») et la chaîne vide (« ») en dernier lors de la recherche d'une commande dans le PATH de l'utilisateur (si l'un ou les deux sont présents dans le PATH). Selon la politique de sécurité, la variable d'environnement PATH de l'utilisateur peut être modifiée, remplacée, ou transmise inchangée au programme que sudo exécute.

Les utilisateurs ne devraient jamais se voir accorder des privilèges sudo pour exécuter des fichiers qui sont modifiables par l'utilisateur ou qui résident dans un répertoire modifiable par l'utilisateur. Si l'utilisateur peut modifier ou remplacer la commande, il n'y a aucun moyen de limiter les commandes supplémentaires qu'il peut exécuter.

Par défaut, sudo n'enregistrera que la commande qu'il exécute explicitement. Si un utilisateur exécute une commande telle que « sudo su » ou « sudo sh », les commandes ultérieures exécutées depuis ce shell ne sont pas soumises à la politique de sécurité de sudo. Il en va de même pour les commandes qui offrent des échappées de shell (y compris la plupart des éditeurs). Si la journalisation I/O est activée, les commandes ultérieures auront leur entrée et/ou leur sortie enregistrées, mais il n'y aura pas de journaux traditionnels pour ces commandes. Pour cette raison, il faut être prudent lors de l'octroi d'accès aux utilisateurs aux commandes via sudo afin de vérifier que la commande ne donne pas involontairement à l'utilisateur un shell root effectif. Pour des informations sur les moyens de résoudre ce problème, voir la section Prévention des échappées de shell dans sudoers(5).

Pour empêcher la divulgation d'informations potentiellement sensibles, sudo désactive les vidages de noyau par défaut pendant son exécution (ils sont réactivés pour la commande exécutée). Cette pratique historique remonte à une époque où la plupart des systèmes d'exploitation autorisaient par défaut les processus set-user-ID à vider le noyau. Pour faciliter le débogage des plantages de sudo, vous voudrez peut-être réactiver les vidages de noyau en définissant « disable_coredump » sur false dans le fichier sudo.conf(5) comme suit :

Set disable_coredump false

Voir le manuel sudo.conf(5) pour plus d'informations.

ENVIRONNEMENT

sudo utilise les variables d'environnement suivantes. La politique de sécurité a le contrôle sur le contenu réel de l'environnement de la commande.

EDITOR
Éditeur par défaut à utiliser en mode -e (sudoedit) si ni SUDO_EDITOR ni VISUAL n'est défini.

VARIABLES

MAIL
Défini sur la boîte aux lettres de l'utilisateur cible lorsque l'option -i est spécifiée, ou lorsque env_reset est activé dans sudoers (sauf si MAIL est présent dans la liste env_keep).
HOME
Défini sur le répertoire personnel de l'utilisateur cible lorsque les options -i ou -H sont spécifiées, lorsque l'option -s est spécifiée et que set_home est défini dans sudoers, lorsque always_set_home est activé dans sudoers, ou lorsque env_reset est activé dans sudoers et que HOME n'est pas présent dans la liste env_keep.
LOGNAME
Défini sur le nom de connexion de l'utilisateur cible lorsque l'option -i est spécifiée, lorsque l'option set_logname est activée dans sudoers, ou lorsque l'option env_reset est activée dans sudoers (sauf si LOGNAME est présent dans la liste env_keep).
PATH
Peut être remplacé par la politique de sécurité.
SHELL
Utilisé pour déterminer le shell à exécuter avec l'option -s.
SUDO_ASKPASS
Spécifie le chemin d'un programme auxiliaire utilisé pour lire le mot de passe s'il n'y a pas de terminal disponible ou si l'option -A est spécifiée.
SUDO_COMMAND
Défini sur la commande exécutée par sudo, y compris tous les arguments. Les arguments sont tronqués à 4096 caractères pour éviter une erreur d'exécution potentielle.
SUDO_EDITOR
Éditeur par défaut à utiliser en mode -e (sudoedit).
SUDO_GID
Défini sur l'ID du groupe de l'utilisateur qui a invoqué sudo.
SUDO_HOME
Défini sur le répertoire personnel de l'utilisateur qui a invoqué sudo.
SUDO_PROMPT
Utilisé comme invite de mot de passe par défaut, sauf si l'option -p a été spécifiée.
SUDO_PS1
Si défini, PS1 sera défini à sa valeur pour le programme en cours d'exécution.
SUDO_TTY
Défini sur le périphérique terminal de l'utilisateur qui a invoqué sudo, s'il est présent.
SUDO_UID
Défini sur l'ID utilisateur de l'utilisateur qui a invoqué sudo.
SUDO_USER
Défini sur le nom de connexion de l'utilisateur qui a invoqué sudo.
USER
Défini sur la même valeur que LOGNAME, décrit ci-dessus.
VISUAL
Éditeur par défaut à utiliser en mode -e (sudoedit) si SUDO_EDITOR n'est pas défini.

EXEMPLES

Les exemples suivants supposent une politique de sécurité correctement configurée.

Pour obtenir une liste de fichiers d'un répertoire illisible :

$ sudo ls /usr/local/protected

Pour lister le répertoire personnel de l'utilisateur yaz sur une machine où le système de fichiers contenant ~yaz n'est pas exporté en tant que root :

$ sudo -u yaz ls ~yaz

Pour modifier le fichier index.html en tant qu'utilisateur www :

$ sudoedit -u www ~www/htdocs/index.html

Pour afficher les journaux système accessibles uniquement à root et aux utilisateurs du groupe adm :

$ sudo -g adm more /var/log/syslog

Pour éditer un fichier en tant que jim avec un groupe primaire différent :

$ sudoedit -u jim -g audio ~jim/sound.txt

Pour arrêter une machine :

$ sudo shutdown -r +15 "redémarrage rapide"

Pour faire un listing d'utilisation des répertoires dans la partition /home. Les commandes sont exécutées dans un sous-shell pour permettre à la commande ‘cd’ et à la redirection de fichiers de fonctionner.

$ sudo sh -c "cd /home ; du -s * | sort -rn > UTILISATION"

DIAGNOSTICS

Les messages d'erreur produits par sudo incluent :

l'édition de fichiers dans un répertoire inscriptible n'est pas permise

Par défaut, sudoedit n'autorise pas l'édition d'un fichier si l'un des répertoires parents est inscriptible par l'utilisateur qui invoque. Cela évite une condition de concurrence qui pourrait permettre à l'utilisateur de remplacer un fichier arbitraire. Voir l'option sudoedit_checkdir dans sudoers(5) pour plus d'informations.

l'édition de liens symboliques n'est pas permise

Par défaut, sudoedit ne suit pas les liens symboliques lors de l'ouverture des fichiers. Voir l'option sudoedit_follow dans sudoers(5) pour plus d'informations.

l'UID effectif n'est pas 0, sudo est-il installé avec setuid root ?

sudo n'a pas été exécuté avec les privilèges root. Le binaire sudo doit appartenir à l'utilisateur root et avoir le bit set-user-ID activé. De plus, il ne doit pas être situé sur un système de fichiers monté avec l'option ‘nosuid’ ou sur un système de fichiers NFS qui mappe l'uid 0 à un uid non privilégié.

l'UID effectif n'est pas 0, sudo est-il sur un système de fichiers avec l'option 'nosuid' activée ou un système de fichiers NFS sans privilèges root ?

sudo n'a pas été exécuté avec les privilèges root. Le binaire sudo a le bon propriétaire et les bonnes permissions, mais il n'a pas été exécuté avec les privilèges root. La raison la plus fréquente est que le système de fichiers sur lequel se trouve le binaire sudo est monté avec l'option ‘nosuid’ ou qu'il s'agit d'un système de fichiers NFS qui mappe l'uid 0 à un uid non privilégié.

erreur fatale, impossible de charger les plugins

Une erreur s'est produite lors du chargement ou de l'initialisation des plugins spécifiés dans sudo.conf(5).

nom de variable d'environnement invalide

Une ou plusieurs variables d'environnement spécifiées via l'option -E contenaient un signe égal (‘=’). Les arguments de l'option -E doivent être des noms de variables d'environnement sans valeur associée.

aucun mot de passe n'a été fourni

Lorsque sudo a tenté de lire le mot de passe, il n'a reçu aucun caractère. Cela peut se produire si aucun terminal n'est disponible (ou si l'option -S est spécifiée) et que l'entrée standard a été redirigée depuis /dev/null.

un terminal est requis pour lire le mot de passe

sudo doit lire le mot de passe, mais aucun mécanisme n'est disponible pour le faire. Les commandes distantes exécutées via ssh(1) n'ont pas de terminal disponible par défaut ; passer l'option -t à ssh(1) entraînera l'allocation d'un terminal, ce qui devrait permettre à sudo de lire le mot de passe. Pour permettre à sudo d'exécuter des commandes locales sans terminal, l'option -S peut être utilisée pour lire un mot de passe depuis l'entrée standard, ou un programme auxiliaire askpass peut être configuré via le fichier sudo.conf(5) ou en définissant la variable d'environnement SUDO_ASKPASS.

aucun répertoire temporaire inscriptible trouvé

sudoedit n'a pas pu trouver de répertoire temporaire utilisable dans lequel stocker ses fichiers intermédiaires.

le drapeau « no new privileges » est défini, ce qui empêche sudo de s'exécuter en tant que root

sudo a été exécuté par un processus qui a le drapeau Linux « no new privileges » défini. Cela a pour effet d'ignorer le bit set-user-ID lors de l'exécution d'un exécutable, ce qui empêchera sudo de fonctionner. La cause la plus probable est l'exécution de sudo dans un conteneur qui définit ce drapeau. Consultez la documentation pour voir s'il est possible de configurer le conteneur de manière à ce que le drapeau ne soit pas défini.

sudo doit appartenir à l'uid 0 et avoir le bit setuid défini

sudo n'a pas été exécuté avec les privilèges root. Le binaire sudo n'a pas le bon propriétaire ou les bonnes permissions. Il doit appartenir à l'utilisateur root et avoir le bit set-user-ID activé.

sudoedit n'est pas supporté sur cette plateforme

Il n'est possible d'exécuter sudoedit que sur les systèmes qui supportent la définition de l'ID utilisateur effectif.

lecture du mot de passe expirée

L'utilisateur n'a pas entré de mot de passe avant que le délai d'expiration du mot de passe (5 minutes par défaut) ne soit dépassé.

vous n'existez pas dans la base de données passwd

Votre utilisateur
-ID n'apparaît pas dans la base de données du système passwd.

vous ne pouvez pas spécifier de variables d'environnement en mode édition

Il n'est possible de spécifier des variables d'environnement que lors de l'exécution d'une commande. Lors de l'édition d'un fichier, l'éditeur est exécuté avec l'environnement de l'utilisateur inchangé.

AVERTISSEMENTS

Il n'existe aucun moyen simple d'empêcher un utilisateur d'obtenir un shell root si cet utilisateur est autorisé à exécuter des commandes arbitraires via sudo. De plus, de nombreux programmes (comme les éditeurs) permettent à l'utilisateur d'exécuter des commandes via des évasions de shell, évitant ainsi les vérifications de sudo. Cependant, sur la plupart des systèmes, il est possible d'empêcher les évasions de shell avec la fonctionnalité sudoers(5) noexec du plugin.

Il n'est pas judicieux d'exécuter la commande ‘cd’ directement via sudo, par exemple,

$ sudo cd /usr/local/protected

car lorsque la commande se termine, le processus parent (votre shell) restera le même. L'option -D peut être utilisée pour exécuter une commande dans un répertoire spécifique.

L'exécution de scripts shell via sudo peut exposer les mêmes bugs du noyau qui rendent les scripts shell set-user-ID dangereux sur certains systèmes d'exploitation (si votre OS possède un répertoire /dev/fd/, les scripts shell set-user-ID sont généralement sûrs).
