SUPERMIN(1) Support de la virtualisation SUPERMIN(1)

NOM

supermin - Outil pour créer et construire des appliances supermin

SYNOPSIS

supermin --prepare -o REPERTOIRE_SORTIE PAQUET [PAQUET ...]
supermin --build -o REPERTOIRE_SORTIE -f chroot|ext2 ENTREE [ENTREE ...]

EXEMPLE

supermin --prepare bash util-linux -o /tmp/supermin.d

cat > init <<EOF
#!/bin/sh
mount -t proc /proc /proc
mount -t sysfs /sys /sys
echo Bienvenue dans supermin
bash -i
EOF

chmod +x init
tar zcf /tmp/supermin.d/init.tar.gz ./init

supermin --build /tmp/supermin.d -f ext2 -o /tmp/appliance.d

qemu-kvm -nodefaults -nographic \
         -kernel /tmp/appliance.d/kernel \
         -initrd /tmp/appliance.d/initrd \
         -hda /tmp/appliance.d/root \
         -serial stdio -append "console=ttyS0 root=/dev/sda"
...
Bienvenue dans supermin
bash-4.3#

DESCRIPTION

Supermin est un outil de construction d'appliances supermin. Ce sont de minuscules appliances (similaires à des machines virtuelles), généralement d'une taille d'environ 100 Ko, qui sont entièrement instanciées à la volée en une fraction de seconde lorsque vous avez besoin d'en démarrer une.

Ce programme s'appelait autrefois febootstrap. Cette page de manuel documente supermin 5.x qui est une réécriture complète et assez différente de febootstrap 2.x. Si vous recherchez les outils febootstrap 2.x, ce n'est pas le bon endroit.

FONCTIONNEMENT DE BASE

L'outil supermin peut être utilisé en deux modes : préparation d'une minuscule appliance supermin, qui est effectuée sur un système de construction, et construction, qui prend l'appliance supermin et construit une appliance complète et démarrable, ce qui est effectué sur le système de l'utilisateur final.

Supermin n'a pas besoin d'être exécuté en tant que root, et généralement il ne devrait pas être exécuté en tant que root. Il n'affecte pas le système hôte ni les paquets installés sur le système hôte.

MODE PRÉPARATION

--prepare crée la minuscule appliance supermin dans le répertoire de sortie donné. Vous lui fournissez une liste de paquets à installer, et supermin trouvera automatiquement les dépendances. La liste des paquets doit être installée sur la machine hôte.

Par exemple :

supermin --prepare bash coreutils -o supermin.d

crée une appliance supermin contenant les paquets "bash" et "coreutils". Plus précisément, il crée certains fichiers dans le répertoire supermin.d. Ce répertoire est l'appliance supermin. (Voir "APPLIANCES SUPERMIN" ci-dessous).

Il est prévu que l'étape --prepare soit effectuée sur une machine de construction centrale, et que l'appliance supermin soit distribuée aux utilisateurs finaux (ce qui est facile car les appliances supermin sont si petites).

MODE CONSTRUCTION

--build (précédemment un programme distinct appelé "supermin-helper") construit l'appliance complète à partir de l'appliance supermin :

supermin --build --format ext2 supermin.d -o appliance.d

Cela créera des fichiers appelés appliance.d/kernel, appliance.d/root etc, qui est l'appliance démarrable de taille complète.

Il est prévu que l'étape --build soit effectuée sur la machine de l'utilisateur final à la dernière seconde avant que l'appliance ne soit nécessaire. Les paquets de l'appliance supermin (ceux spécifiés lors de la préparation de l'appliance supermin) doivent être installés sur la machine de l'utilisateur final.

Construction et cache

Généralement, vous souhaitez reconstruire l'appliance sur la machine de l'utilisateur final uniquement sur demande. Supermin dispose d'options supplémentaires pour faciliter cela :

supermin --build \
  --if-newer --lock /run/user/`id -u`/supermin.lock \
  --format ext2 supermin.d -o appliance.d

Si plusieurs programmes exécutent cette commande en parallèle, les instances attendront sur le fichier de verrouillage. L'appliance complète ne sera reconstruite que si elle n'existe pas ou si elle est plus ancienne que les fichiers d'entrée et la base de données des paquets hôtes.

Notez que le fichier de verrouillage ne doit pas être stocké dans le répertoire -o.

PAQUETS

Par "paquet", nous entendons le paquet RPM, Debian, (etc.), par exemple "coreutils", "perl".

Dans tous les cas, supermin ne peut construire une appliance supermin qui soit identique en distribution, version et architecture à l'hôte. Il ne fait pas de constructions croisées.

OPTIONS

--help
Affiche l'utilisation brève de la ligne de commande et quitte.
--build
Construit l'appliance complète à partir de l'appliance supermin. C'était auparavant un programme distinct appelé "supermin-helper".
--copy-kernel
(mode --build uniquement)

Copie le noyau (et l'arborescence des périphériques, s'il est créé) au lieu de créer un lien symbolique vers le noyau dans /boot.

C'est légèrement plus lent, mais nécessaire si vous souhaitez modifier les permissions ou le label SELinux sur le noyau ou l'arborescence des périphériques.

-f FORMAT
--format FORMAT
(mode --build uniquement)

Sélectionne le format de sortie pour l'appliance complète.

Il n'y a pas de valeur par défaut. Lorsque vous utilisez --build, vous devez spécifier l'option --format.

Les formats possibles sont :

chroot
Une arborescence de fichiers dans le système de fichiers hôte.

L'arborescence du système de fichiers est écrite dans REPERTOIRE_SORTIE (c'est-à-dire l'option -o).

Ceci est appelé un "chroot" car vous pourriez littéralement faire un chroot(1) dans ce répertoire ensuite, bien qu'il soit préférable d'utiliser une technologie de conteneurisation (LXC, etc.).

Aucun noyau ou initrd n'est généré dans ce mode car il est supposé que vous exécuterez l'appliance en utilisant le noyau hôte.

ext2
Une image de système de fichiers ext2.

Le noyau de sortie est écrit dans REPERTOIRE_SORTIE/kernel, un petit initramfs qui peut monter l'appliance dans REPERTOIRE_SORTIE/initrd, et l'image du système de fichiers ext2 dans REPERTOIRE_SORTIE/root. (Où REPERTOIRE_SORTIE est spécifié par l'option -o).

Le système de fichiers (REPERTOIRE_SORTIE/root) a une taille par défaut de 4 Go (voir aussi l'option --size).

--host-cpu CPU
(mode --build uniquement)

Spécifie le CPU hôte (par ex. "i686", "x86_64"). Ceci est utilisé comme une correspondance de sous-chaîne lors de la recherche de noyaux compatibles. S'il n'est pas spécifié, il prend par défaut le CPU hôte sur lequel supermin a été compilé.

--if-newer
(mode --build uniquement)

Le répertoire de sortie est vérifié et il n'est pas reconstruit sauf si cela est nécessaire.

Ceci est fait en consultant les dates de la base de données des paquets hôtes (/var/lib/rpm etc.), les fichiers supermin d'entrée, et le répertoire de sortie. L'opération n'est effectuée que si la base de données des paquets hôtes ou les fichiers supermin d'entrée sont plus récents que le répertoire de sortie.

Voir aussi --lock ci-dessous.

--include-packagelist
(mode --build uniquement)

Ajoute un fichier /packagelist à l'intérieur du chroot ou du système de fichiers ext2 généré, contenant une liste triée de tous les paquets utilisés pour construire l'appliance.

Principalement utile pour le débogage, car il est plus facile de déterminer, par exemple, quelle version d'un paquet a été copiée dans l'appliance.

--list-drivers
Liste les pilotes de gestionnaires de paquets compilés dans supermin, et si le gestionnaire de paquets correspondant est détecté sur le système actuel.
--lock FICHIER_VERROU
(mode --build uniquement)

Si plusieurs exécutions parallèles de supermin doivent construire une appliance complète, alors

vous pouvez utiliser l'option --lock pour vous assurer qu'ils ne se marchent pas dessus.

Le fichier de verrouillage est utilisé pour fournir une exclusion mutuelle afin qu'une seule instance de supermin s'exécute à la fois.

Notez que le fichier de verrouillage ne doit pas être stocké dans le répertoire de sortie.

-o DIR_SORTIE
Sélectionnez le répertoire de sortie.

Lors de l'utilisation de --prepare, c'est le répertoire où l'appliance supermin sera écrite. Lors de l'utilisation de --build, c'est le répertoire où l'appliance complète, le noyau, etc. seront écrits.

Tout contenu précédent du répertoire de sortie est supprimé, et un nouveau répertoire de sortie est créé.

Le répertoire de sortie est créé (presque) atomiquement en construisant un répertoire temporaire appelé quelque chose comme DIR_SORTIE.abc543, puis en renommant l'ancien répertoire de sortie (si présent) et en le supprimant, puis en renommant le répertoire temporaire en DIR_SORTIE. En combinant cette option avec --lock, vous pouvez vous assurer que plusieurs exécutions parallèles de supermin n'entrent pas en conflit les unes avec les autres.

--packager-config FICHIER_CONFIG
(mode --prepare uniquement)

Définir le fichier de configuration pour le gestionnaire de paquets. Cela vous permet de spécifier des dépôts de logiciels alternatifs.

Pour ArchLinux, cela définit le fichier de configuration pacman (par défaut /etc/pacman.conf). Voir pacman.conf(5).

Pour les distributions Yum/RPM, cela définit le fichier de configuration yum (par défaut /etc/yum.conf). Voir yum.conf(5).

--prepare
Préparer l'appliance supermin.
--use-installed
(mode --prepare uniquement)

Si les paquets sont déjà installés, utiliser le contenu (depuis le système de fichiers local) au lieu de les télécharger.

Notez que cela peut entraîner des appliances malformées si les fichiers locaux ont été modifiés par rapport à ce qui était initialement dans le paquet. C'est particulièrement problématique pour les fichiers de configuration.

Cependant, cette option est utile dans certaines situations contrôlées : par exemple, lors de l'utilisation de supermin à l'intérieur d'un chroot fraîchement installé, ou si vous n'avez pas d'accès réseau pendant la construction.

--size TAILLE
(mode --build uniquement)

Sélectionnez la taille du système de fichiers ext2 de sortie, où la taille peut être spécifiée à l'aide de noms courants tels que "32G" (32 gigaoctets), etc.

Si la taille n'est pas spécifiée, une taille par défaut de 4 Go est utilisée.

Pour spécifier la taille en octets, le nombre doit être suivi de la lettre minuscule b, par exemple : "--size 10737418240b".

-v
--verbose
Activer les messages détaillés.

Vous pouvez donner cette option plusieurs fois pour activer encore plus de messages :

-v
Débogage des étapes globales.
-v -v
Informations détaillées au sein de chaque étape.
-v -v -v
Quantité massive de débogage (beaucoup trop pour une utilisation normale, mais utile si vous essayez de diagnostiquer un bug dans supermin).
-V
--version
Affiche le nom et le numéro de version du paquet, puis quitte.

APPLIANCES SUPERMIN

Les appliances supermin consistent en juste assez d'informations pour pouvoir construire une appliance contenant le même système d'exploitation (version Linux, distribution, version, etc.) que le système hôte. Étant donné que l'hôte et l'appliance partagent de nombreux fichiers communs tels que /bin/bash et /lib/libc.so, il n'y a aucune raison de distribuer ces fichiers dans l'appliance. Ils peuvent simplement être lus depuis l'hôte à la demande lors du lancement de l'appliance. Par conséquent, pour économiser de l'espace, nous stockons uniquement les noms des paquets que nous voulons de l'hôte, et les copions (plus les dépendances) au moment de la construction.

Il existe certains fichiers qui ne peuvent pas simplement être copiés de l'hôte de cette manière. Cela inclut les fichiers de configuration que l'administrateur de l'hôte pourrait avoir modifiés. Ainsi, avec la liste des fichiers de l'hôte, nous stockons également une image de base squelette qui contient ces fichiers et la structure de répertoires esquissée.

Par conséquent, l'appliance supermin se compose normalement d'au moins deux fichiers de contrôle (packages et base.tar.gz).

packages
La liste des paquets à copier depuis l'hôte. Les dépendances sont résolues automatiquement.

Le fichier est en texte brut, un nom de paquet par ligne.

base.tar
base.tar.gz
Ce fichier tar (qui peut être compressé) contient le système de fichiers squelette. Il contient principalement des répertoires et quelques fichiers de configuration.

Tous les chemins dans le fichier tar doivent être relatifs au répertoire racine de l'appliance.

hostfiles
Tous les autres fichiers qui doivent être copiés depuis l'hôte. C'est un fichier texte brut avec un nom de chemin par ligne.

Les chemins peuvent contenir des jokers, qui sont développés lors de la création de l'appliance, par exemple :

/etc/yum.repos.d/*.repo

copierait tous les fichiers *.repo dans l'appliance.

Chaque nom de chemin dans le fichier doit commencer par un caractère "/".

Supermin lui-même ne crée pas de hostfiles (bien que, avant la version 5, ce fût le mécanisme principal utilisé pour créer l'appliance complète). Cependant, vous pouvez déposer un ou plusieurs de ces fichiers dans le répertoire supermin si vous souhaitez copier des fichiers aléatoires non empaquetés dans l'appliance complète.

excludefiles
Une liste de noms de fichiers, de noms de répertoires ou de jokers préfixés par "-" qui sont exclus de l'appliance finale.

C'est assez brutal car cela supprime simplement des choses, potentiellement en cassant des paquets. Cependant, cela peut être utilisé comme un moyen pratique de minimiser la taille de l'appliance finale.

Supermin lui-même ne crée pas de excludefiles. Cependant, vous pouvez déposer un ou plusieurs de ces fichiers dans le répertoire supermin pour empêcher que des fichiers empaquetés ne soient copiés dans l'appliance complète.

Notez que les noms ci-dessus ne sont que des suggestions. Vous pouvez utiliser les noms que vous voulez, car supermin détecte le contenu de chaque fichier lors de la reconstruction de l'appliance. Vous pouvez également avoir plusieurs fichiers de chaque type.

RECONSTRUCTION DE L'APPLIANCE

Le mode séparé "supermin --build" est utilisé pour reconstruire une appliance à partir des fichiers de l'appliance supermin.

Ce programme itère en fait récursivement sur les fichiers et les répertoires qui lui sont passés. Une disposition courante pourrait ressembler à ceci :

supermin.d/
supermin.d/base.tar.gz
supermin.d/extra.tar.gz
supermin.d/packages
supermin.d/zz-hostfiles

De cette manière, des fichiers supplémentaires peuvent être ajoutés à l'appliance simplement en créant un autre fichier tar (extra.tar.gz dans l'exemple ci-dessus) et en le déposant dans le répertoire, et des fichiers hôtes supplémentaires peuvent être ajoutés (zz-hostfiles dans l'exemple ci-dessus). Lorsque l'appliance est construite, les fichiers supplémentaires apparaîtront dans l'appliance.

MINIMISATION DE L'APPLIANCE SUPERMIN

Vous pourriez vouloir "minimiser" l'appliance supermin afin de gagner du temps et de l'espace lors de son instanciation. Typiquement, vous pourriez vouloir supprimer la documentation, les fichiers d'information, les pages de manuel et les locales.

Vous pouvez le faire en créant un fichier `excludefiles` qui liste les fichiers, répertoires ou jokers que vous ne souhaitez pas inclure. Ils sont ignorés lors de la construction de l'appliance complète.

-/boot/*
-/lib/modules/*
-/usr/share/doc/*
-/usr/share/info/*
-/usr/share/man/*

Faites attention à ce que vous supprimez, car certains fichiers peuvent être nécessaires au bon fonctionnement de l'appliance.

NOYAU ET MODULES DU NOYAU

Habituellement, le noyau et les modules du noyau ne sont pas inclus dans l'appliance supermin.

Lorsque l'appliance complète est construite, les modules du noyau de l'hôte sont copiés, et elle est démarrée en utilisant le noyau de l'hôte.

UTILISATION D'UN NOYAU ET DE MODULES PERSONNALISÉS

Supermin est capable de choisir le meilleur noyau hôte disponible pour démarrer l'appliance. Cependant, vous pouvez outrepasser cela en définissant des variables d'environnement (voir "VARIABLES D'ENVIRONNEMENT" ci-dessous).

Si vous construisez un noyau personnalisé (par exemple, en compilant Linux à partir des sources), vous devriez faire quelque chose comme ceci :

mkdir /tmp/kmods
make bzImage
make modules
make modules_install INSTALL_MOD_PATH=/tmp/kmods

export SUPERMIN_KERNEL=/chemin/vers/linux.git/arch/x86/boot/bzImage
export SUPERMIN_MODULES=/tmp/kmods/lib/modules/3.xx.yy

supermin --build -f ext2 [etc]

GARANTIR LA DISPONIBILITÉ DES PAQUETS

Supermin construit l'appliance en copiant les paquets listés dans packages. Pour que cela fonctionne, ces paquets doivent être disponibles. Nous garantissons généralement cela en ajoutant des exigences (par exemple, des lignes de Requires: RPM) au paquet qui utilise l'appliance supermin, de sorte que ce paquet ne puisse pas être installé sans entraîner les paquets dépendants et donc s'assurer que les paquets sont installés pour que supermin les utilise.

VARIABLES D'ENVIRONNEMENT

SUPERMIN_KERNEL
Si cette variable d'environnement est définie, la sélection automatique du noyau est contournée et ce noyau est utilisé.

La variable d'environnement doit pointer vers un fichier de noyau, par exemple /boot/vmlinuz-3.0.x86_64

SUPERMIN_MODULES
Ceci spécifie le répertoire des modules du noyau à utiliser.

La variable d'environnement doit pointer vers un répertoire de modules, par exemple /lib/modules/3.0.x86_64/

SUPERMIN_KERNEL_VERSION
Sur les architectures non-x86, vous devrez peut-être définir cette variable d'environnement si supermin ne parvient pas à déterminer la version du noyau de "SUPERMIN_KERNEL" simplement en examinant le fichier.
