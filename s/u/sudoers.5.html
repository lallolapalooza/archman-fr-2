NOM

sudoers — module de politique de sécurité sudo par défaut

DESCRIPTION

Le module de politique sudoers détermine les privilèges sudo d'un utilisateur. C'est le module de politique sudo par défaut. La politique est pilotée par le fichier /etc/sudoers ou, optionnellement, par LDAP. Le format de la politique est décrit en détail dans la section FORMAT DU FICHIER SUDOERS. Pour des informations sur le stockage des informations de politique sudoers dans LDAP, consultez sudoers.ldap(5).

Configuration de sudo.conf pour sudoers

sudo consulte le fichier sudo.conf(5) pour déterminer quels modules charger. S'il n'y a pas de fichier sudo.conf(5) ou s'il ne contient aucune ligne Plugin, sudoers sera utilisé pour l'audit, les décisions de politique et la journalisation des E/S. Pour configurer explicitement sudo.conf(5) pour utiliser le module sudoers, la configuration suivante peut être utilisée.

Plugin sudoers_audit sudoers.so
Plugin sudoers_policy sudoers.so
Plugin sudoers_io sudoers.so

À partir de sudo 1.8.5, il est possible de spécifier des arguments optionnels au module sudoers dans le fichier sudo.conf(5). Les arguments du module, s'il y en a, doivent être listés après le chemin d'accès au module (c'est-à-dire après sudoers.so). Les arguments ne sont efficaces que pour le module qui ouvre (et analyse) le fichier sudoers.

Pour sudo version 1.9.1 et plus récente, il s'agit du module sudoers_audit. Pour les versions plus anciennes, il s'agit du module sudoers_policy. Plusieurs arguments peuvent être spécifiés, séparés par des espaces blancs. Par exemple :

Plugin sudoers_audit sudoers.so sudoers_mode=0400 error_recovery=false

Les arguments de module suivants sont pris en charge :

error_recovery=bool
L'argument error_recovery peut être utilisé pour contrôler si sudoers doit tenter de récupérer des erreurs de syntaxe dans le fichier sudoers. S'il est défini sur true (la valeur par défaut), sudoers tentera de récupérer une erreur de syntaxe en ignorant la partie de la ligne contenant l'erreur jusqu'à la fin de la ligne. Une valeur de false désactivera la récupération d'erreur. Avant la version 1.9.3, aucune récupération d'erreur n'était effectuée.
ignore_perms=bool
L'argument ignore_perms peut être utilisé pour désactiver les vérifications de sécurité lors du chargement du fichier sudoers. S'il est activé, le fichier sudoers sera chargé indépendamment du propriétaire ou du mode de fichier. Cet argument est destiné à être utilisé à des fins de test et ne doit pas être activé sur les systèmes de production.
ldap_conf=chemin
L'argument ldap_conf peut être utilisé pour remplacer le chemin par défaut vers le fichier ldap.conf.
ldap_secret=chemin
L'argument ldap_secret peut être utilisé pour remplacer le chemin par défaut vers le fichier ldap.secret.
sudoers_file=chemin
L'argument sudoers_file peut être utilisé pour remplacer le chemin par défaut du fichier sudoers.
sudoers_uid=ID-utilisateur
L'argument sudoers_uid peut être utilisé pour remplacer le propriétaire par défaut du fichier sudoers. Il doit être spécifié comme un ID utilisateur numérique.
sudoers_gid=ID-groupe
L'argument sudoers_gid peut être utilisé pour remplacer le groupe par défaut du fichier sudoers. Il doit être spécifié comme un ID de groupe numérique (pas un nom de groupe).
sudoers_mode=mode
L'argument sudoers_mode peut être utilisé pour remplacer le mode de fichier par défaut pour le fichier sudoers. Il doit être spécifié comme une valeur octale.

Pour plus d'informations sur la configuration de sudo.conf(5), référez-vous à sa manuel.

Authentification utilisateur

La politique de sécurité sudoers exige que la plupart des utilisateurs s'authentifient avant de pouvoir utiliser sudo. Un mot de passe n'est pas requis si l'utilisateur appelant est root, si l'utilisateur cible est le même que l'utilisateur appelant, ou si la politique a désactivé l'authentification pour l'utilisateur ou la commande. Contrairement à su(1), lorsque sudoers exige une authentification, il valide les identifiants de l'utilisateur appelant, et non ceux de l'utilisateur cible (ou de root). Ceci peut être modifié via les drapeaux rootpw, targetpw et runaspw, décrits plus loin.

Si un utilisateur qui n'est pas listé dans la politique essaie d'exécuter une commande via sudo, un courrier est envoyé aux autorités compétentes. L'adresse utilisée pour un tel courrier est configurable via l'entrée Defaults mailto (décrite plus loin) et est par défaut root.

Aucun courrier ne sera envoyé si un utilisateur non autorisé essaie d'exécuter sudo avec l'option -l ou -v, sauf s'il y a une erreur d'authentification et que les drapeaux mail_always ou mail_badpass sont activés. Cela permet aux utilisateurs de déterminer eux-mêmes s'ils sont autorisés ou non à utiliser sudo. Par défaut, toutes les tentatives d'exécution de sudo (réussies ou non) sont enregistrées, que du courrier soit envoyé ou non.

Si sudo est exécuté par root et que la variable d'environnement SUDO_USER est définie, la politique sudoers utilisera cette valeur pour déterminer qui est l'utilisateur réel. Cela peut être utilisé par un utilisateur pour enregistrer des commandes via sudo même lorsqu'un shell root a été invoqué. Cela permet également à l'option -e de rester utile même lorsqu'elle est invoquée via un script ou un programme exécuté par sudo. Notez cependant que la recherche dans le fichier sudoers est toujours effectuée pour root, et non pour l'utilisateur spécifié par SUDO_USER.

sudoers utilise des fichiers horodatés par utilisateur pour la mise en cache des identifiants. Une fois qu'un utilisateur a été authentifié, un enregistrement est écrit contenant l'ID utilisateur utilisé pour l'authentification, l'ID de session du terminal, l'heure de début du leader de la session (ou du processus parent) et un horodatage (en utilisant une horloge monotone si disponible). L'utilisateur peut alors utiliser sudo sans mot de passe pendant une courte période (5 minutes, sauf indication contraire de l'option timestamp_timeout). Par défaut, sudoers utilise un enregistrement séparé pour chaque terminal, ce qui signifie que les sessions de connexion d'un utilisateur sont authentifiées séparément. L'option timestamp_type peut être utilisée pour sélectionner le type d'enregistrement horodaté que sudoers utilisera.

L'utilitaire tsdump, inclus dans la distribution source de sudo, peut être utilisé pour afficher le contenu d'un fichier horodaté. Consultez sudoers_timestamp(5) pour les détails du format du fichier horodaté.

Environnement de commande

Étant donné que les variables d'environnement peuvent influencer le comportement du programme, sudoers fournit un moyen de restreindre les variables de l'environnement de l'utilisateur qui seront héritées par la commande à exécuter. Il existe deux manières distinctes dont sudoers peut gérer les variables d'environnement.

Par défaut, l'indicateur env_reset est activé. Cela entraîne l'exécution des commandes avec un nouvel environnement minimal. Sur les systèmes AIX (et Linux sans PAM), l'environnement est initialisé avec le contenu du fichier /etc/environment. Les variables d'environnement HOME, MAIL, SHELL, LOGNAME et USER sont initialisées en fonction de l'utilisateur cible et les variables SUDO_* sont définies en fonction de l'utilisateur appelant. D'autres variables, telles que DISPLAY, PATH et TERM, sont conservées à partir de l'environnement de l'utilisateur appelant si elles sont autorisées par les options env_check ou env_keep. Quelques variables d'environnement sont traitées spécialement. Si les variables PATH et TERM ne sont pas conservées de l'environnement de l'utilisateur, elles seront définies sur des valeurs par défaut. Les variables LOGNAME et USER sont traitées comme une entité unique. Si l'une d'elles est conservée (ou supprimée) de l'environnement de l'utilisateur, l'autre le sera également. Si LOGNAME et USER doivent être conservées mais que seule l'une d'elles est présente dans l'environnement de l'utilisateur, l'autre sera définie sur la même valeur. Cela évite un environnement incohérent où l'une des variables décrivant le nom d'utilisateur est définie sur l'utilisateur appelant et l'autre sur l'utilisateur cible. Les variables d'environnement dont la valeur commence par ‘()’ sont supprimées, sauf si le nom et la valeur correspondent à env_keep ou env_check, car elles peuvent être interprétées comme des fonctions par le shell bash. Avant la version 1.8.11, ces variables étaient toujours supprimées.

Si, cependant, l'indicateur env_reset est désactivé, toutes les variables non explicitement refusées par les options env_check et env_delete sont autorisées et leurs valeurs sont héritées du processus appelant. Avant la version 1.8.21, les variables d'environnement dont la valeur commence par ‘()’ étaient toujours supprimées. À partir de la version 1.8.21, un motif dans env_delete est utilisé pour faire correspondre les fonctions du shell bash à la place. Comme il n'est pas possible de bloquer toutes les variables d'environnement potentiellement dangereuses, l'utilisation du comportement par défaut env_reset est encouragée.

Les variables d'environnement spécifiées par env_check, env_delete, ou env_keep peuvent inclure un ou plusieurs caractères ‘*’ qui correspondront à zéro ou plusieurs caractères. Aucun autre caractère générique n'est pris en charge.

Par défaut, les variables d'environnement sont mises en correspondance par nom. Cependant, si le motif inclut un signe égal (‘=’), le nom et la valeur de la variable doivent correspondre. Par exemple, une fonction shell bash peut être mise en correspondance comme suit :

env_keep += "BASH_FUNC_my_func%%=()*"

Sans le suffixe ‘=()*’, cela ne correspondrait pas, car les fonctions shell bash ne sont pas conservées par défaut.

La liste complète des variables d'environnement qui sont conservées ou supprimées, telles que modifiées par les paramètres Defaults globaux dans sudoers, est affichée lorsque sudo est exécuté par root avec l'option -V. La liste des variables d'environnement à supprimer varie en fonction du système d'exploitation sur lequel sudo s'exécute.

D'autres paramètres peuvent influencer l'environnement de commande :

  • sudoers options telles que always_set_home, secure_path, set_logname, set_home, et setenv.
  • Balises de commande, telles que SETENV et NOSETENV. Notez que SETENV est implicite si la commande correspondante est ALL.
  • Options sudo, telles que -E et -i.

Sur les systèmes qui prennent en charge PAM où le module pam_env est activé pour sudo, les variables de l'environnement PAM peuvent être fusionnées dans l'environnement. Si une variable de l'environnement PAM est déjà présente dans l'environnement de l'utilisateur, la valeur ne sera remplacée que si la variable n'a pas été conservée par sudoers. Lorsque env_reset est activé, les variables conservées de l'environnement de l'utilisateur appelant par la liste env_keep ont la priorité sur celles de l'environnement PAM. Lorsque env_reset est désactivé, les variables présentes dans l'environnement de l'utilisateur appelant ont la priorité sur celles de l'environnement PAM, sauf si elles correspondent à un motif de la liste env_delete.

Le lieur dynamique de la plupart des systèmes d'exploitation supprime les variables qui peuvent contrôler la liaison dynamique de l'environnement des exécutables set-user-ID, y compris sudo. Selon le système d'exploitation, cela peut inclure _RLD*, DYLD_*, LD_*, LDR_*, LIBPATH, SHLIB_PATH, et d'autres. Ces types de variables sont supprimés de l'environnement avant même que sudo ne commence son exécution et, en tant que tels, il n'est pas possible pour sudo de les conserver.

À titre exceptionnel, si l'option -i (connexion initiale) est spécifiée, sudoers initialisera l'environnement quelle que soit la valeur de env_reset. Les variables DISPLAY, PATH et TERM restent inchangées ; HOME, MAIL, SHELL, USER, et LOGNAME sont définies en fonction de l'utilisateur cible. Sur les systèmes AIX (et Linux sans PAM), le contenu de /etc/environment est également inclus. Toutes les autres variables d'environnement sont supprimées, sauf autorisation par env_keep ou env_check, décrites ci-dessus.

Enfin, les fichiers restricted_env_file et env_file sont appliqués, s'ils sont présents. Les variables de restricted_env_file sont appliquées en premier et sont soumises aux mêmes restrictions que l'environnement de l'utilisateur appelant, comme détaillé ci-dessus. Les variables de env_file sont appliquées en dernier et ne sont pas soumises à ces restrictions. Dans les deux cas, les variables présentes dans les fichiers ne seront définies sur leurs valeurs spécifiées que si elles n'entrent pas en conflit avec une variable d'environnement existante.

FORMAT DU FICHIER SUDOERS

Le fichier sudoers est composé de deux types d'entrées : les alias (essentiellement des variables) et les spécifications d'utilisateur (qui définissent qui peut exécuter quoi).

Lorsque plusieurs entrées correspondent à un utilisateur, elles sont appliquées dans l'ordre. En cas de plusieurs correspondances, la dernière correspondance est utilisée (ce qui n'est pas nécessairement la correspondance la plus spécifique).

La grammaire du fichier sudoers sera décrite ci-dessous en forme étendu de Backus-Naur (EBNF). Ne désespérez pas si vous ne connaissez pas l'EBNF ; c'est assez simple, et les définitions ci-dessous sont annotées.

Limites de ressources

Par défaut, sudoers utilise la méthode native du système d'exploitation pour définir les limites de ressources pour l'utilisateur cible. Sur les systèmes Linux, les limites de ressources sont généralement définies par le module PAM pam_limits.so. Sur certains systèmes BSD, le fichier /etc/login.conf spécifie les limites de ressources pour l'utilisateur. Sur les systèmes AIX, les limites de ressources sont configurées dans le fichier /etc/security/limits. S'il n'existe aucun mécanisme système pour définir des limites de ressources par utilisateur, la commande sera exécutée avec les mêmes limites que l'utilisateur appelant. La seule exception concerne la taille du fichier de vidage du cœur (core dump), qui est définie par défaut à 0 par sudoers. La désactivation par défaut des vidages de cœur permet d'éviter des problèmes de sécurité potentiels où le fichier de vidage est traité comme une entrée de confiance.

Les limites de ressources peuvent également être définies dans le fichier sudoers lui-même, auquel cas elles remplacent celles définies par le système. Voir rlimit_as, rlimit_core, rlimit_cpu et rlimit_data pour plus de détails.

Deux valeurs séparées par une virgule. La limite douce est définie à la première valeur et la limite dure est définie à la seconde. Guide rapide EBNF

L'EBNF est une manière concise et exacte de décrire la grammaire d'un langage. Chaque définition EBNF est composée de règles de production. Par exemple :

symbole ::= définition | alternate1 | alternate2 ...

Chaque règle de production référence d'autres règles et constitue ainsi une grammaire pour le langage. L'EBNF contient également les opérateurs suivants, que de nombreux lecteurs reconnaîtront dans les expressions régulières. Ne les confondez cependant pas avec les caractères « génériques », qui ont des significations différentes.

?
Signifie que le symbole précédent (ou le groupe de symboles) est facultatif. C'est-à-dire qu'il peut apparaître une fois ou pas du tout.
*
Signifie que le symbole précédent (ou le groupe de symboles) peut apparaître zéro fois ou plus.
+
Signifie que le symbole précédent (ou le groupe de symboles) peut apparaître une fois ou plus.

Les parenthèses peuvent être utilisées pour grouper des symboles. Pour plus de clarté, nous utiliserons des apostrophes ('') pour désigner une chaîne de caractères littérale (par opposition à un nom de symbole).

Alias

Il existe quatre types d'alias : User_Alias, Runas_Alias, Host_Alias et Cmnd_Alias. À partir de sudo 1.9.0, Cmd_Alias peut être utilisé à la place de Cmnd_Alias si désiré.

Alias ::= 'User_Alias'  User_Alias_Spec (':' User_Alias_Spec)* |
          'Runas_Alias' Runas_Alias_Spec (':' Runas_Alias_Spec)* |
          'Host_Alias'  Host_Alias_Spec (':' Host_Alias_Spec)* |
          'Cmnd_Alias'  Cmnd_Alias_Spec (':' Cmnd_Alias_Spec)* |
          'Cmd_Alias'   Cmnd_Alias_Spec (':' Cmnd_Alias_Spec)*

User_Alias ::= NAME

User_Alias_Spec ::= User_Alias '=' User_List

Runas_Alias ::= NAME

Runas_Alias_Spec ::= Runas_Alias '=' Runas_List

Host_Alias ::= NAME

Host_Alias_Spec ::= Host_Alias '=' Host_List

Cmnd_Alias ::= NAME

Cmnd_Alias_Spec ::= Cmnd_Alias '=' Cmnd_List

NAME ::= [A–Z]([A–Z][0–9]_)*

Chaque définition d'alias est de la forme

Alias_Type NAME = item1, item2, ...

où Alias_Type est l'un de User_Alias, Runas_Alias, Host_Alias, ou Cmnd_Alias. Un NAME est une chaîne de lettres majuscules, de chiffres et de caractères de soulignement (‘_’). Un NAME doit commencer par une lettre majuscule. Il est possible de mettre plusieurs définitions d'alias du même type sur une seule ligne, reliées par un deux-points (‘:’). Par exemple :

Alias_Type NAME = item1, item2, item3 : NAME = item4, item5

C'est une erreur de syntaxe de redéfinir un alias existant. Il est possible d'utiliser le même nom pour des alias de types différents, mais ce n'est pas recommandé.

User_List ::= User |
              User ',' User_List

User ::= '!'* nom d'utilisateur |
         '!'* #id utilisateur |
         '!'* %groupe |
         '!'* %#id groupe |
         '!'* +netgroup |
         '!'* %:groupe_non_unix |
         '!'* %:#id_groupe_non_unix |

Une User_List est composée d'un ou plusieurs noms d'utilisateur, id utilisateur (précédés de ‘#’), noms et id de groupe système (précédés de ‘%’ et ‘%#’ respectivement), netgroups (précédés de ‘+’), noms et id de groupe non-Unix (précédés de ‘%:’ et ‘%:#’ respectivement), et User_Alias. Chaque élément de la liste peut être précédé de zéro ou plusieurs opérateurs ‘!’>. Un nombre impair de opérateurs ‘!’ inverse la valeur de l'élément ; un nombre pair s'annule simplement. Les netgroups d'utilisateurs sont comparés en utilisant uniquement les membres utilisateur et domaine ; le membre hôte n'est pas utilisé lors de la comparaison.

Un nom d'utilisateur, id utilisateur, groupe, id groupe, netgroup, groupe_non_unix ou id_groupe_non_unix peut être entouré de guillemets doubles pour éviter d'avoir à échapper les caractères spéciaux. Alternativement, les caractères spéciaux peuvent être spécifiés en mode hexadécimal échappé, par exemple, \x20 pour un espace. Lors de l'utilisation de guillemets doubles, tous les caractères de préfixe doivent être inclus entre les guillemets.

La syntaxe réelle pour les groupe_non_unix et id_groupe_non_unix dépend du plugin fournisseur de groupe sous-jacent. Par exemple, le plugin QAS AD prend en charge les formats suivants :

  • Groupe dans le même domaine : "%:Nom du groupe"
  • Groupe dans n'importe quel domaine : "%:Nom du groupe@DOMAINE.COMPLET.QUALIFIÉ"
  • SID du groupe : "%:S-1-2-34-5678901234-5678901234-5678901234-567"

Une Runas_List est similaire à une User_List, sauf qu'au lieu de User_Aliases, elle peut contenir des Runas_Aliases. Les noms d'utilisateur et les groupes sont comparés en tant que chaînes de caractères. Autrement dit, deux utilisateurs (groupes) avec le même id utilisateur (groupe) sont considérés comme distincts. Si vous souhaitez comparer tous les noms d'utilisateur ayant le même id utilisateur (par exemple, root et toor), vous pouvez utiliser un id utilisateur au lieu d'un nom (#0 dans l'exemple donné). L'id utilisateur ou l'id groupe spécifié dans un Runas_Member n'a pas besoin d'être répertorié dans la base de données du mot de passe ou des groupes.

Host_List ::= Host |

Host ::= '!'* nom d'hôte |
         '!'* adresse_ip |

Une Host_List est composée d'un ou plusieurs noms d'hôtes, adresses IP, numéros de réseau, netgroups (précédés de ‘+’), et autres alias. Encore une fois, la valeur d'un élément peut être niée avec l'opérateur ‘!’. Les netgroups d'hôtes sont comparés en utilisant uniquement les membres hôtes (qualifiés et non qualifiés) et domaine ; le membre utilisateur n'est pas utilisé lors de la comparaison. Si vous spécifiez un numéro de réseau sans masque réseau, sudo interrogera chacune des interfaces réseau de l'hôte local et, si le numéro de réseau correspond à l'une des interfaces réseau de l'hôte, utilisera le masque réseau de cette interface. digest ::= [A-Fa-f0-9]+ |
           [A-Za-z0-9\+/=]+

Digest_Spec ::= "sha224" ':' digest |
                "sha256" ':' digest |
                "sha384" ':' digest |
                "sha512" ':' digest

Digest_List ::= Digest_Spec |
                Digest_Spec ',' Digest_List

Cmnd_List ::= Cmnd |
              Cmnd ',' Cmnd_List

nom_commande ::= regex |
                 nom_fichier

commande ::= nom_commande |
            nom_commande args |
            nom_commande regex |
            nom_commande "" |
            ALL

Edit_Spec ::= "sudoedit" nom_fichier+ |
              "sudoedit" regex |
              "sudoedit"

List_Spec ::= "list"

Cmnd ::= Digest_List? '!'* commande |
         '!'* repertoire |
         '!'* Edit_Spec |
         '!'* List_Spec |
         '!'* Cmnd_Alias

Une Cmnd_List est une liste d'une ou plusieurs commandes, répertoires ou alias. Une commande est un nom de fichier entièrement qualifié, qui peut inclure des caractères génériques de style shell (voir la section Wildcards ci-dessous), ou une expression régulière commençant par « ^ » et se terminant par « $ » (voir la section Expressions régulières ci-dessous). Un répertoire est un chemin d'accès entièrement qualifié se terminant par « / ». Lorsque vous spécifiez un répertoire dans une Cmnd_List, l'utilisateur pourra exécuter n'importe quel fichier de ce répertoire (mais pas dans les sous-répertoires de celui-ci). Si aucun argument de ligne de commande n'est spécifié, l'utilisateur peut exécuter la commande avec les arguments de son choix. Les arguments de ligne de commande peuvent inclure des caractères génériques ou être une expression régulière commençant par « ^ » et se terminant par « $ ». Si les arguments de ligne de commande consistent en « "" », la commande ne peut être exécutée qu'avec aucun argument.

Si une Cmnd a des arguments de ligne de commande associés, les arguments de la Cmnd doivent correspondre à ceux fournis par l'utilisateur sur la ligne de commande. Si les arguments d'une Cmnd commencent par le caractère « ^ », ils seront interprétés comme une expression régulière et comparés en conséquence. Sinon, des caractères génériques de style shell sont utilisés lors de la comparaison. Sauf si une expression régulière est spécifiée, les caractères suivants doivent être échappés avec un « \ » s'ils sont utilisés dans les arguments de commande : « , », « : », « = », « \ ». Pour empêcher les arguments d'une Cmnd commençant par un caractère « ^ » d'être interprétés comme une expression régulière, le « ^ » doit être échappé avec un « \ ».

Il existe deux commandes intégrées à sudo lui-même : « list » et « sudoedit ». Contrairement aux autres commandes, ces deux doivent être spécifiées dans le fichier sudoers sans chemin d'accès initial.

L'utilitaire intégré « list » peut être utilisé pour autoriser un utilisateur à lister les privilèges d'un autre utilisateur avec l'option -U de sudo. Par exemple, « sudo -l -U autreutilisateur ». Un utilisateur ayant le privilège « list » est capable de lister les privilèges d'un autre utilisateur même s'il n'a pas la permission d'exécuter des commandes en tant que cet utilisateur. Par défaut, seul root ou un utilisateur ayant la capacité d'exécuter n'importe quelle commande en tant que root ou en tant que l'utilisateur spécifié sur l'hôte actuel peut utiliser l'option -U. Aucun argument de ligne de commande ne peut être spécifié avec l'utilitaire intégré « list ».

L'utilitaire intégré « sudoedit » est utilisé pour autoriser un utilisateur à exécuter sudo avec l'option -e (ou en tant que sudoedit). Il peut accepter des arguments de ligne de commande comme une commande normale. Contrairement aux autres commandes, « sudoedit » est intégré à sudo lui-même et doit être spécifié dans le fichier sudoers sans chemin d'accès initial. Si un chemin d'accès initial est présent, par exemple /usr/bin/sudoedit, le nom du chemin sera silencieusement converti en « sudoedit ». Un chemin d'accès complet pour sudoedit est traité comme une erreur par visudo.

Une commande peut être précédée d'une Digest_List, une liste séparée par des virgules d'une ou plusieurs entrées Digest_Spec. Si une Digest_List est présente, la commande ne correspondra avec succès que si elle peut être vérifiée à l'aide d'un des digests SHA-2 de la liste. À partir de la version 1.9.0, le mot réservé ALL peut être utilisé conjointement avec une Digest_List. Les formats de digest suivants sont pris en charge : sha224, sha256, sha384 et sha512. La chaîne peut être spécifiée au format hexadécimal ou base64 (base64 est plus compact). Il existe plusieurs utilitaires capables de générer des digests SHA-2 au format hexadécimal tels que openssl, shasum, sha224sum, sha256sum, sha384sum, sha512sum.

Par exemple, en utilisant openssl :

$ openssl dgst -sha224 /bin/ls
SHA224(/bin/ls)= 118187da8364d490b4a7debbf483004e8f3e053ec954309de2c41a25

Il est également possible d'utiliser openssl pour générer une sortie base64 :

$ openssl dgst -binary -sha224 /bin/ls | openssl base64
EYGH2oNk1JC0p9679IMATo8+BT7JVDCd4sQaJQ==

Attention, si l'utilisateur a un droit d'écriture sur la commande elle-même (directement ou via une commande sudo), il pourrait être possible pour l'utilisateur de remplacer la commande après que la vérification du digest ait été effectuée mais avant que la commande ne soit exécutée. Une condition de concurrence similaire existe sur les systèmes qui ne disposent pas de l'appel système fexecve(2) lorsque le répertoire dans lequel se trouve la commande est accessible en écriture par l'utilisateur. Voir la description du paramètre fdexec pour plus d'informations sur la manière dont sudo exécute les commandes qui ont un digest associé.

Les digests de commande ne sont pris en charge qu'à partir de la version 1.8.7.

Defaults

Certaines options de configuration peuvent être modifiées par rapport à leurs valeurs par défaut au moment de l'exécution via une ou plusieurs lignes Default_Entry. Celles-ci peuvent affecter tous les utilisateurs sur n'importe quel hôte (« Defaults »), tous les utilisateurs sur un hôte spécifique (« Defaults@host »), un utilisateur spécifique (« Defaults:user »), une commande spécifique (« Defaults!cmnd »), ou les commandes exécutées par un utilisateur spécifique (« Defaults>runasuser »).

Les espaces blancs ne sont pas autorisés entre « Defaults » et les caractères « @ », « : », « ! » ou « > ». Bien qu'une liste séparée par des virgules puisse être utilisée à la place d'une valeur unique après le caractère « @ », « : », « ! » ou « > », utiliser un alias au lieu d'une liste améliore souvent la lisibilité. Les entrées par commande ne peuvent pas inclure d'arguments de ligne de commande. Si vous avez besoin de spécifier des arguments, définissez un Cmnd_Alias et référencez-le à la place.

Default_Type ::= 'Defaults' |
                 'Defaults@' Host_List |
                 'Defaults:' User_List |
                 'Defaults!' Cmnd_List |
                 'Defaults>' Runas_List

Default_Entry ::= Default_Type Parameter_List

Parameter_List ::= Parameter |
                   Parameter ',' Parameter_List

Parameter ::= Parameter '=' Value |
              Parameter '+=' Value |
              Parameter '-=' Value |
              '!'* Parameter

Les paramètres peuvent être des flags, des valeurs entières, des chaînes ou des listes. Les flags sont implicitement booléens et peuvent être désactivés via l'opérateur « ! ». Certains paramètres entiers, chaînes et listes peuvent également être utilisés dans un contexte booléen pour les désactiver. Les valeurs peuvent être entourées de guillemets doubles (« "" ») lorsqu'elles contiennent plusieurs mots. Les caractères spéciaux peuvent être échappés avec un antislash (« \ »).

Pour inclure un caractère antislash littéral dans un argument de ligne de commande, vous devez échapper l'antislash deux fois. Par exemple, pour faire correspondre « \n » comme faisant partie d'un argument de ligne de commande, vous devez utiliser « \\\\n » dans le fichier sudoers. Ceci est dû au fait qu'il y a deux niveaux d'échappement, un dans l'analyseur sudoers lui-même et un autre lors de la mise en correspondance des arguments de ligne de commande par la fonction fnmatch(3) ou regexec(3).

Les listes ont deux opérateurs d'affectation supplémentaires, « += » et « -= ». Ces opérateurs sont utilisés pour ajouter et supprimer respectivement des éléments d'une liste. Ce n'est pas une erreur d'utiliser l'opérateur « -= » pour supprimer un élément qui n'existe pas dans une liste.

En général, les paramètres Defaults sont appliqués dans l'ordre, les entrées ultérieures remplaçant les précédentes. Cependant, les paramètres Defaults spécifiques à une commande sont appliqués plus tard, une fois que le chemin de la commande est connu. De plus, les paramètres Defaults suivants doivent être appliqués avant tous les autres car ils peuvent affecter les entrées ultérieures : fqdn, group_plugin, ignore_unknown_defaults, match_group_by_gid, runas_default, sudoers_locale.

Voir OPTIONS SUDOERS pour une liste des paramètres Defaults pris en charge.

Spécification de l'utilisateur

User_Spec ::= User_List Host_List '=' Cmnd_Spec_List \
              (':' Host_List '=' Cmnd_Spec_List)*

Cmnd_Spec_List ::= Cmnd_Spec |
                   Cmnd_Spec ',' Cmnd_Spec_List

Cmnd_Spec ::= Runas_Spec? Option_Spec* (Tag_Spec ':')* Cmnd

Runas_Spec ::= '(' Runas_List? (':' Runas_List)? ')'

Option_Spec ::= (Date_Spec | Timeout_Spec | Chdir_Spec | Chroot_Spec)

Date_Spec ::= ('NOTBEFORE=timestamp' | 'NOTAFTER=timestamp')

Timeout_Spec ::= 'TIMEOUT=timeout'

Chdir_Spec ::= 'CWD=directory'

Chroot_Spec ::= 'CHROOT=directory'

Tag_Spec ::= ('EXEC' | 'NOEXEC' | 'FOLLOW' | 'NOFOLLOW' |
              'LOG_INPUT' | 'NOLOG_INPUT' | 'LOG_OUTPUT' |
              'NOLOG_OUTPUT' | 'MAIL' | 'NOMAIL' | 'INTERCEPT' |
              'NOINTERCEPT' | 'PASSWD' | 'NOPASSWD' | 'SETENV' |
              'NOSETENV')

Une spécification d'utilisateur détermine quelles commandes un utilisateur peut exécuter (et en tant que quel utilisateur) sur les hôtes spécifiés. Par défaut, les commandes sont exécutées en tant que root (sauf si runas_default a été défini sur une autre valeur), mais cela peut également être modifié commande par commande.

La structure de base d'une spécification d'utilisateur est "qui où = (en tant que qui) quoi". Décomposons cela en ses parties constitutives :

Runas_Spec

Un Runas_Spec détermine l'utilisateur et/ou le groupe sous lesquels une commande peut être exécutée. Un Runas_Spec entièrement spécifié se compose de deux Runas_Lists (telles que définies ci-dessus) séparées par un deux-points (‘:’) et entourées de parenthèses. La première Runas_List indique sous quels utilisateurs la commande peut être exécutée via l'option -u. La seconde définit une liste de groupes qui peuvent être spécifiés via l'option -g (en plus de tous les groupes de l'utilisateur cible). Si les deux Runas_Lists sont spécifiées, la commande peut être exécutée avec n'importe quelle combinaison d'utilisateurs et de groupes listés dans leurs Runas_Lists respectives. Si seule la première est spécifiée, la commande peut être exécutée en tant que n'importe quel utilisateur de la liste et, éventuellement, avec n'importe quel groupe auquel l'utilisateur cible appartient. Si la première Runas_List est vide mais que la seconde est spécifiée, la commande peut être exécutée en tant qu'utilisateur appelant avec le groupe défini sur n'importe lequel de la Runas_List. Si les deux Runas_Lists sont vides, la commande ne peut être exécutée qu'en tant qu'utilisateur appelant et le groupe, s'il est spécifié, doit être un groupe auquel l'utilisateur appelant est membre. Si aucun Runas_Spec n'est spécifié, la commande ne peut être exécutée qu'en tant qu'utilisateur runas_default (root par défaut) et le groupe, s'il est spécifié, doit être un groupe auquel l'utilisateur runas_default est membre.

Un Runas_Spec définit la valeur par défaut pour les commandes qui le suivent. Ce que cela signifie, c'est que pour l'entrée :

dgb	boulder = (operator) /bin/ls, /bin/kill, /usr/bin/lprm

L'utilisateur dgb peut exécuter /bin/ls, /bin/kill et /usr/bin/lprm sur l'hôte boulder — mais uniquement en tant que operator. Par exemple :

$ sudo -u operator /bin/ls

Il est également possible de remplacer un Runas_Spec plus tard dans une entrée. Si nous modifions l'entrée comme suit :

dgb	boulder = (operator) /bin/ls, (root) /bin/kill, /usr/bin/lprm

Alors l'utilisateur dgb est maintenant autorisé à exécuter /bin/ls en tant que operator, mais /bin/kill et /usr/bin/lprm en tant que root.

Nous pouvons étendre cela pour permettre à dgb d'exécuter /bin/ls avec l'utilisateur ou le groupe défini sur operator :

dgb	boulder = (operator : operator) /bin/ls, (root) /bin/kill,\
	/usr/bin/lprm

Alors que la partie groupe du Runas_Spec permet à l'utilisateur d'exécuter la commande avec ce groupe, cela ne le force pas à le faire. Si aucun groupe n'est spécifié sur la ligne de commande, la commande sera exécutée avec le groupe répertorié dans l'entrée de la base de données de mots de passe de l'utilisateur cible. Les commandes suivantes seraient toutes autorisées par l'entrée sudoers ci-dessus :

$ sudo -u operator /bin/ls
$ sudo -u operator -g operator /bin/ls
$ sudo -g operator /bin/ls

Dans l'exemple suivant, l'utilisateur tcm peut exécuter des commandes qui accèdent à un fichier de périphérique modem avec le groupe dialer.

tcm	boulder = (:dialer) /usr/bin/tip, /usr/bin/cu,\
	/usr/local/bin/minicom

Dans cet exemple, seul le groupe sera défini, la commande s'exécutera toujours sous l'utilisateur tcm. Par exemple :

$ sudo -g dialer /usr/bin/cu

Plusieurs utilisateurs et groupes peuvent être présents dans un Runas_Spec, auquel cas l'utilisateur peut sélectionner n'importe quelle combinaison d'utilisateurs et de groupes via les options -u et -g. Dans cet exemple :

alan	ALL = (root, bin : operator, system) ALL

l'utilisateur alan peut exécuter n'importe quelle commande en tant qu'utilisateur root ou bin, en définissant éventuellement le groupe sur operator ou system.

Option_Spec

Un Cmnd peut avoir zéro ou plusieurs options associées. Les options peuvent être constituées de dates de début et/ou de fin et de délais d'exécution de commande. Une fois qu'une option est définie pour un Cmnd, les Cmnds suivants dans le Cmnd_Spec_List héritent de cette option, sauf si elle est remplacée par une autre option. Les noms d'options sont des mots réservés dans sudoers. Cela signifie qu'aucun des noms d'options valides (voir ci-dessous) ne peut être utilisé lors de la déclaration d'un alias.

Date_Spec

Les règles sudoers peuvent être spécifiées avec une date de début et de fin via les paramètres NOTBEFORE et NOTAFTER. L'horodatage doit être spécifié en "Temps généralisé" tel que défini par la RFC 4517. Le format est effectivement ‘aaaajjhhMMssZ’ où les minutes et les secondes sont facultatives. Le suffixe ‘Z’ indique que l'horodatage est en temps universel coordonné (UTC). Il est également possible de spécifier un décalage de fuseau horaire par rapport à l'UTC en heures et minutes au lieu d'un ‘Z’. Par exemple, ‘-0500’ correspondrait à l'heure normale de l'Est aux États-Unis. En tant qu'extension, si aucun ‘Z’ ou décalage de fuseau horaire n'est spécifié, l'heure locale sera utilisée.

Les horodatages suivants sont tous valides :

20170214083000Z
2017021408Z
20160315220000-0500
20151201235900

Timeout_Spec

Une commande peut avoir un délai d'expiration associé. Si le délai expire avant que la commande n'ait terminé, la commande sera terminée. Le délai d'expiration peut être spécifié en combinaisons de jours, d'heures, de minutes et de secondes avec un suffixe unique insensible à la casse indiquant l'unité de temps. Par exemple, un délai de 7 jours, 8 heures, 30 minutes et 10 secondes s'écrirait ‘7d8h30m10s’. Si un nombre est spécifié sans unité, les secondes sont supposées. N'importe lequel des jours, minutes, heures ou secondes peut être omis. L'ordre doit être de la plus grande à la plus petite unité et une unité ne peut pas être spécifiée plus d'une fois.

Les valeurs de délai suivantes sont toutes valides : ‘7d8h30m10s’, ‘14d’, ‘8h30m’, ‘600s’, ‘3600’. Les valeurs suivantes sont invalides : ‘12m2w1d’, ‘30s10m4h’, ‘1d2d3h’.

Ce paramètre n'est pris en charge que par la version 1.8.20 ou ultérieure.

Chdir_Spec

Le répertoire de travail dans lequel la commande sera exécutée peut être spécifié à l'aide du paramètre CWD. Le répertoire doit être un chemin d'accès complet commençant par un caractère ‘/’ ou ‘~’, ou la valeur spéciale “*”. Une valeur de “*” indique que l'utilisateur peut spécifier le répertoire de travail en exécutant sudo avec l'option -D. Par défaut, les commandes sont exécutées à partir du répertoire de travail actuel de l'utilisateur appelant, sauf si l'option -i est donnée. Les chemins du type ~utilisateur/chemin/nom sont interprétés comme étant relatifs au répertoire personnel de l'utilisateur nommé. Si le nom d'utilisateur est omis, le chemin sera relatif au répertoire personnel de l'utilisateur à exécuter.

Ce paramètre n'est pris en charge que par la version 1.9.3 ou ultérieure.

Chroot_Spec

La prise en charge de la définition du répertoire racine est dépréciée et sera supprimée dans une future version de sudo.

Le répertoire racine dans lequel la commande sera exécutée peut être spécifié à l'aide du paramètre CHROOT. Le répertoire doit être un chemin d'accès complet commençant par un caractère ‘/’ ou ‘~’, ou la valeur spéciale “*”. Une valeur de “*” indique que l'utilisateur peut spécifier le répertoire racine en exécutant sudo avec l'option -R. Ce paramètre peut être utilisé pour exécuter la commande dans un "bac à sable" chroot(2) similaire à l'utilitaire chroot(8). Les chemins du type ~utilisateur/chemin/nom sont interprétés comme étant relatifs au répertoire personnel de l'utilisateur nommé. Si le nom d'utilisateur est omis, le chemin sera relatif au répertoire personnel de l'utilisateur à exécuter.

Ce paramètre n'est pris en charge que par la versi

en 1.9.3 ou version ultérieure.

Tag_Spec

Une commande peut avoir zéro ou plusieurs balises qui lui sont associées. Les valeurs de balises suivantes sont prises en charge : EXEC, NOEXEC, FOLLOW, NOFOLLOW, LOG_INPUT, NOLOG_INPUT, LOG_OUTPUT, NOLOG_OUTPUT, MAIL, NOMAIL, INTERCEPT, NOINTERCEPT, PASSWD, NOPASSWD, SETENV, et NOSETENV. Une fois qu'une balise est définie sur une Cmnd, les Cmnds subséquentes dans la Cmnd_Spec_List héritent de la balise sauf si elle est remplacée par la balise opposée (en d'autres termes, PASSWD remplace NOPASSWD et NOEXEC remplace EXEC).

EXEC et NOEXEC

Si sudo a été compilé avec la prise en charge noexec et que le système d'exploitation sous-jacent la prend en charge, la balise NOEXEC peut être utilisée pour empêcher un exécutable lié dynamiquement d'exécuter d'autres commandes lui-même.

Dans l'exemple suivant, l'utilisateur aaron peut exécuter /usr/bin/more et /usr/bin/vi sur l'hôte shanty, mais les échappements de shell seront désactivés.

aaron	shanty = NOEXEC: /usr/bin/more, /usr/bin/vi

Voir la section Prévention des échappements de shell ci-dessous pour plus de détails sur le fonctionnement de NOEXEC et s'il fonctionnera sur votre système.

FOLLOW et NOFOLLOW

À partir de la version 1.8.15, sudoedit n'ouvrira pas un fichier qui est un lien symbolique à moins que le drapeau sudoedit_follow ne soit activé. Les balises FOLLOW et NOFOLLOW remplacent la valeur de sudoedit_follow et peuvent être utilisées pour permettre (ou interdire) l'édition de liens symboliques sur une base par commande. Ces balises ne sont efficaces que pour la commande sudoedit et sont ignorées pour toutes les autres commandes.

LOG_INPUT et NOLOG_INPUT

Ces balises remplacent la valeur du drapeau log_input sur une base par commande. Pour plus d'informations, voir JOURNAUX D'E/S.

LOG_OUTPUT et NOLOG_OUTPUT

Ces balises remplacent la valeur du drapeau log_output sur une base par commande. Pour plus d'informations, voir JOURNAUX D'E/S.

MAIL et NOMAIL

Ces balises fournissent un contrôle granulaire sur la question de savoir si un courriel sera envoyé lorsqu'un utilisateur exécute une commande en remplaçant la valeur du drapeau mail_all_cmnds sur une base par commande. Elles n'ont aucun effet lorsque sudo est exécuté avec les options -l ou -v. Une balise NOMAIL remplacera également les options mail_always et mail_no_perms. Pour plus d'informations, voir les descriptions de mail_all_cmnds, mail_always, et mail_no_perms dans la section OPTIONS SUDOERS ci-dessous.

PASSWD et NOPASSWD

Par défaut, sudo exige qu'un utilisateur s'authentifie avant d'exécuter une commande. Ce comportement peut être modifié via la balise NOPASSWD. Comme un Runas_Spec, la balise NOPASSWD définit une valeur par défaut pour les commandes qui la suivent dans la Cmnd_Spec_List. Inversement, la balise PASSWD peut être utilisée pour inverser les choses. Par exemple :

ray	rushmore = NOPASSWD: /bin/kill, /bin/ls, /usr/bin/lprm

permettrait à l'utilisateur ray d'exécuter /bin/kill, /bin/ls, et /usr/bin/lprm en tant que root sur la machine « rushmore » sans s'authentifier. Si nous voulons seulement que ray puisse exécuter /bin/kill sans mot de passe, l'entrée serait :

ray	rushmore = NOPASSWD: /bin/kill, PASSWD: /bin/ls, /usr/bin/lprm

Notez, cependant, que la balise PASSWD n'a aucun effet sur les utilisateurs qui font partie du groupe spécifié par le réglage exempt_group.

Par défaut, si la balise NOPASSWD est appliquée à l'une des entrées d'un utilisateur pour l'hôte actuel, l'utilisateur pourra exécuter « sudo -l » sans mot de passe. De plus, un utilisateur ne peut exécuter « sudo -v » sans mot de passe que si toutes les entrées de l'utilisateur pour l'hôte actuel ont la balise NOPASSWD. Ce comportement peut être remplacé via les options verifypw et listpw.

SETENV et NOSETENV

Ces balises remplacent la valeur du drapeau setenv sur une base par commande. Si SETENV a été défini pour une commande, l'utilisateur peut désactiver le drapeau env_reset depuis la ligne de commande via l'option -E. De plus, les variables d'environnement définies sur la ligne de commande ne sont pas soumises aux restrictions imposées par env_check, env_delete, ou env_keep. En tant que tel, seuls les utilisateurs de confiance devraient être autorisés à définir des variables de cette manière. Si la commande correspondante est ALL, la balise SETENV est implicite pour cette commande ; cette valeur par défaut peut être remplacée par l'utilisation de la balise NOSETENV.

INTERCEPT et NOINTERCEPT

Si sudo a été compilé avec la prise en charge de l'intercept et que le système d'exploitation sous-jacent la prend en charge, la balise INTERCEPT peut être utilisée pour faire valider les programmes lancés par une commande contre sudoers et les enregistrer comme s'ils étaient exécutés directement via sudo. Ceci est utile en conjonction avec des commandes qui autorisent les échappements de shell tels que les éditeurs, les shells et les paginators. Il y a un surcoût supplémentaire dû à la vérification de la politique qui peut ajouter de la latence lors de l'exécution de commandes telles que des scripts shell qui exécutent un grand nombre de sous-commandes. Pour les commandes interactives, telles qu'un shell ou un éditeur, le surcoût n'est généralement pas perceptible.

Dans l'exemple suivant, l'utilisateur chuck peut exécuter n'importe quelle commande sur la machine « research » en mode intercept.

chuck	research = INTERCEPT: ALL

Voir la section Prévention des échappements de shell ci-dessous pour plus de détails sur le fonctionnement de INTERCEPT et s'il fonctionnera sur votre système.

Wildcards

sudo autorise les wildcards de style shell (également appelés méta-caractères ou caractères glob) à être utilisés dans les noms d'hôtes, les noms de chemins et les arguments de ligne de commande dans le fichier sudoers. La correspondance des wildcards se fait via les fonctions glob(3) et fnmatch(3) telles que spécifiées par la norme IEEE Std 1003.1 (« POSIX.1 »).

*
Correspond à n'importe quelle séquence de zéro ou plusieurs caractères (y compris les espaces blancs).
?
Correspond à n'importe quel caractère unique (y compris les espaces blancs).
[...]
Correspond à n'importe quel caractère de la plage spécifiée.
[!...]
Correspond à n'importe quel caractère qui n'est pas dans la plage spécifiée.
\x
Pour n'importe quel caractère « x », évalue à « x ». Ceci est utilisé pour échapper les caractères spéciaux tels que : « * », « ? », « [ », et « ] ».
Ce ne sont pas des expressions régulières.
Contrairement à une expression régulière, il n'y a aucun moyen de faire correspondre un ou plusieurs caractères dans une plage.

Les classes de caractères peuvent être utilisées si les fonctions glob(3) et fnmatch(3) de votre système les prennent en charge. Cependant, comme le caractère « : » a une signification spéciale dans sudoers, il doit être échappé. Par exemple :

/bin/ls [[\:alpha\:]]*

Correspondrait à n'importe quel nom de fichier commençant par une lettre.

Une barre oblique (« / ») ne sera pas mise en correspondance par les wildcards utilisés dans la partie nom de fichier de la commande. Ceci afin de rendre un chemin comme :

/usr/bin/*

correspondre à /usr/bin/who mais pas à /usr/bin/X11/xterm.

Cependant, lors de la correspondance des arguments de la ligne de commande, une barre oblique est effectivement mise en correspondance par des jokers, car les arguments de la ligne de commande peuvent contenir des chaînes arbitraires et non pas seulement des noms de chemin.

Utilisez les jokers dans les arguments de la ligne de commande avec prudence.
Les jokers peuvent correspondre à n'importe quel caractère, y compris les espaces. Dans la plupart des cas, il est plus sûr d'utiliser une expression régulière pour faire correspondre les arguments de la ligne de commande. Pour plus d'informations, voir Jokers dans les arguments de commande ci-dessous.

Exceptions aux règles des jokers

Les exceptions suivantes s'appliquent aux règles ci-dessus :

""
Si la chaîne vide ‘""’ est le seul argument de la ligne de commande dans l'entrée du fichier sudoers, cela signifie que la commande n'est pas autorisée à être exécutée avec aucun argument.
sudoedit
Les arguments de la ligne de commande de la commande intégrée sudoedit doivent toujours être des noms de chemin, donc une barre oblique (‘/’) ne sera pas mise en correspondance par un joker.

Expressions régulières

À partir de la version 1.9.10, il est possible d'utiliser des expressions régulières pour les noms de chemin et les arguments de la ligne de commande. Les expressions régulières sont plus expressives que les jokers de style shell et sont généralement plus sûres car elles offrent un plus grand degré de contrôle lors de la mise en correspondance. Le type d'expressions régulières pris en charge par sudoers sont les expressions régulières étendues POSIX, similaires à celles utilisées par l'utilitaire egrep(1). Elles sont généralement documentées dans le manuel regex(7) ou re_format(7), selon le système. En tant qu'extension, si l'expression régulière commence par “(?i)”, elle sera mise en correspondance de manière insensible à la casse.

Dans sudoers, les expressions régulières doivent commencer par un caractère ‘^’ et se terminer par un caractère ‘$’. Cela rend explicite ce qui est, ou n'est pas, une expression régulière. Le nom du chemin, les arguments de la ligne de commande ou les deux peuvent être des expressions régulières. Comme le nom du chemin et les arguments sont mis en correspondance séparément, il est même possible d'utiliser des jokers pour le nom du chemin et des expressions régulières pour les arguments. Il n'est pas possible d'utiliser une seule expression régulière pour mettre en correspondance à la fois la commande et ses arguments. Les expressions régulières dans sudoers sont limitées à 1024 caractères.

Il n'est pas nécessaire d'échapper les caractères spéciaux de sudoers dans une expression régulière, à l'exception du signe dièse (‘#’).

Dans l'exemple suivant, l'utilisateur john peut exécuter la commande passwd(1) en tant que root sur n'importe quel hôte, mais n'est pas autorisé à modifier le mot de passe de root. Ce type de règle est impossible à exprimer en toute sécurité à l'aide de jokers.

john	ALL = /usr/bin/passwd ^[a-zA-Z0-9_]+$,\
              !/usr/bin/passwd root

Il est également possible d'utiliser une expression régulière en conjonction avec les règles de sudoedit. La règle suivante donnerait à l'utilisateur bob la possibilité d'éditer uniquement les fichiers /etc/motd, /etc/issue et /etc/hosts.

bob    ALL = sudoedit ^/etc/(motd|issue|hosts)$

Les expressions régulières peuvent également être utilisées pour faire correspondre la commande elle-même. Dans cet exemple, une expression régulière est utilisée pour permettre à l'utilisateur sid d'exécuter les commandes /usr/sbin/groupadd, /usr/sbin/groupmod, /usr/sbin/groupdel, /usr/sbin/useradd, /usr/sbin/usermod et /usr/sbin/userdel en tant que root.

sid    ALL = ^/usr/sbin/(group|user)(add|mod|del)$

Un inconvénient de l'utilisation d'une expression régulière pour faire correspondre le nom de la commande est qu'il n'est pas possible de faire correspondre des chemins relatifs tels que ./useradd ou ../sbin/useradd. Cela a des implications de sécurité lorsqu'une expression régulière est utilisée pour le nom de la commande en conjonction avec l'opérateur de négation, ‘!’, car de telles règles peuvent être facilement contournées. Pour cette raison, l'utilisation d'une expression régulière niée pour le nom de la commande est fortement déconseillée. Cela ne s'applique pas aux commandes niées qui utilisent uniquement une expression régulière pour faire correspondre les arguments de la commande. Voir Expressions régulières dans les noms de commande ci-dessous pour plus d'informations.

Inclusion d'autres fichiers depuis sudoers

Il est possible d'inclure d'autres fichiers sudoers à partir du fichier sudoers en cours d'analyse à l'aide des directives @include et @includedir. Pour assurer la compatibilité avec les versions de sudo antérieures à 1.9.1, #include et #includedir sont également acceptés.

Un fichier d'inclusion peut être utilisé, par exemple, pour conserver un fichier sudoers à l'échelle du site en plus d'un fichier local par machine. Pour l'exemple, le fichier sudoers à l'échelle du site sera /etc/sudoers et celui par machine sera /etc/sudoers.local. Pour inclure /etc/sudoers.local depuis /etc/sudoers, vous utiliseriez la ligne suivante dans /etc/sudoers :

@include /etc/sudoers.local

Lorsque sudo atteint cette ligne, il suspend le traitement du fichier courant (/etc/sudoers) et passe à /etc/sudoers.local. À la fin de /etc/sudoers.local, le reste de /etc/sudoers sera traité. Les fichiers inclus peuvent eux-mêmes inclure d'autres fichiers. Une limite stricte de 128 fichiers d'inclusion imbriqués est appliquée pour éviter les boucles de fichiers d'inclusion.

À partir de la version 1.9.1, le chemin du fichier d'inclusion peut contenir des espaces s'il est échappé avec une barre oblique inversée (‘\’). Alternativement, le chemin entier peut être entouré de guillemets doubles (""), auquel cas aucun échappement n'est nécessaire. Pour inclure une barre oblique inversée littérale dans le chemin, ‘\\’ doit être utilisé.

Si le chemin du fichier d'inclusion n'est pas entièrement qualifié (ne commence pas par une barre oblique ‘/’), il doit se trouver dans le même répertoire que le fichier sudoers dont il a été inclus. Par exemple, si /etc/sudoers contient la ligne :

@include sudoers.local

le fichier qui sera inclus est /etc/sudoers.local.

Le nom de fichier peut également inclure l'échappement ‘%h’, signifiant la forme courte du nom d'hôte. Autrement dit, si le nom d'hôte de la machine est “xerxes”, alors

@include /etc/sudoers.%h

fera en sorte que sudo inclue le fichier /etc/sudoers.xerxes. Tous les caractères séparateurs de noms de chemin (barres obliques ‘/’) présents dans le nom d'hôte seront remplacés par un trait de soulignement (‘_’) lors de l'expansion.

La directive @includedir peut être utilisée pour créer un répertoire sudoers.d dans lequel le gestionnaire de paquets système peut déposer des règles de fichiers sudoers dans le cadre de l'installation de paquets. Par exemple, étant donné :

@includedir /etc/sudoers.d

sudo suspendra le traitement du fichier courant et lira chaque fichier dans /etc/sudoers.d, en ignorant les noms de fichiers se terminant par ‘~’ ou contenant un caractère ‘.’ pour éviter de causer des problèmes avec les fichiers temporaires/de sauvegarde du gestionnaire de paquets ou de l'éditeur.

Les fichiers sont analysés dans l'ordre lexical trié. C'est-à-dire que /etc/sudoers.d/01_first sera analysé avant /etc/sudoers.d/10_second. Soyez conscient qu'en raison du tri lexical et non numérique, /etc/sudoers.d/1_whoops serait chargé après /etc/sudoers.d/10_second. L'utilisation d'un nombre constant de zéros initiaux dans les noms de fichiers peut être utilisée pour éviter de tels problèmes. Après avoir analysé les fichiers du répertoire, le contrôle revient au fichier qui contenait la directive @includedir.

Contrairement aux fichiers inclus via @include, visudo n'éditera pas les fichiers dans un répertoire @includedir à moins que l'un d'eux ne contienne une erreur de syntaxe. Il est toujours possible d'exécuter visudo avec le drapeau -f pour éditer les fichiers directement, mais cela ne détectera pas la redéfinition d'un alias qui est également présent dans un fichier différent.

Autres caractères spéciaux et mots réservés

Le signe dièse (‘#’) est utilisé pour indiquer un commentaire (sauf s'il fait partie d'une directive #include ou s'il apparaît dans le contexte d'un nom d'utilisateur et est suivi d'un ou plusieurs chiffres, auquel cas il est traité comme un identifiant utilisateur). Le caractère de commentaire et tout texte après lui, jusqu'à la fin de la ligne, sont ignorés.

Le mot réservé ALL est un alias intégré qui réussit toujours une mise en correspondance. Il peut être utilisé partout où l'on pourrait utiliser un Cmnd_Alias, un User_

Alias, Runas_Alias, ou Host_Alias. Tenter de définir un alias nommé ALL entraînera une erreur de syntaxe. L'utilisation de ALL peut être dangereuse car, dans un contexte de commande, elle permet à l'utilisateur d'exécuter toute commande sur le système.

Les noms d'options suivants autorisés dans une Option_Spec sont également considérés comme des mots réservés : CHROOT, TIMEOUT, CWD, NOTBEFORE et NOTAFTER. Tenter de définir un alias portant le même nom que l'une des options entraînera une erreur de syntaxe.

Un point d'exclamation (‘!’) peut être utilisé comme opérateur logique non dans une liste ou un alias, ainsi qu'en préfixe d'un Cmnd. Cela permet d'exclure certaines valeurs. Pour que l'opérateur ‘!’ soit efficace, il doit y avoir quelque chose à exclure. Par exemple, pour correspondre à tous les utilisateurs sauf root, on utiliserait :

ALL, !root

Si ALL est omis, comme dans :

!root

cela refuserait explicitement root mais ne correspondrait à aucun autre utilisateur. Ceci est différent d'un véritable opérateur de « négation ».

Notez, cependant, que l'utilisation d'un ‘!’ en conjonction avec l'alias intégré ALL pour permettre à un utilisateur d'exécuter « toutes les commandes sauf quelques-unes » fonctionne rarement comme prévu (voir NOTES DE SÉCURITÉ ci-dessous).

Les lignes longues peuvent être continuées avec une barre oblique inverse (‘\’) comme dernier caractère de la ligne.

Les espaces blancs entre les éléments d'une liste, ainsi que les caractères syntaxiques spéciaux dans une User Specification (‘=’, ‘:’, ‘(’, ‘)’) sont optionnels.

Les caractères suivants doivent être échappés avec une barre oblique inverse (‘\’) lorsqu'ils sont utilisés comme partie d'un mot (par exemple, un nom d'utilisateur ou un nom d'hôte) : ‘!’, ‘=’, ‘:’, ‘,’, ‘(’, ‘)’, ‘\’.

OPTIONS SUDOERS

sudo's behavior can be modified by Default_Entry lines, as explained earlier. A list of all supported Defaults parameters, grouped by type, are listed below.

Indicateurs Booléens :

always_query_group_plugin
Si un group_plugin est configuré, utilisez-le pour résoudre les groupes de la forme ‘%group’ tant qu'il n'existe pas également de groupe système du même nom. Normalement, seuls les groupes de la forme ‘%:group’ sont passés au group_plugin. Cet indicateur est désactivé par défaut.
always_set_home
Si activé, sudo définira la variable d'environnement HOME sur le répertoire personnel de l'utilisateur cible (qui est l'utilisateur runas_default, sauf si l'option -u est utilisée). Cet indicateur est largement obsolète et n'a aucun effet à moins que l'indicateur env_reset n'ait été désactivé ou que HOME ne soit présent dans la liste env_keep, ce qui est fortement déconseillé. Cet indicateur est désactivé par défaut.
authenticate
S'il est défini, les utilisateurs doivent s'authentifier (via un mot de passe ou un autre moyen) avant de pouvoir exécuter des commandes. Cette valeur par défaut peut être remplacée via les balises PASSWD et NOPASSWD. Cet indicateur est activé par défaut.
case_insensitive_group
S'il est activé, les noms de groupes dans sudoers seront comparés de manière insensible à la casse. Cela peut être nécessaire lorsque les utilisateurs sont stockés dans LDAP ou AD. Cet indicateur est activé par défaut.
case_insensitive_user
S'il est activé, les noms d'utilisateurs dans sudoers seront comparés de manière insensible à la casse. Cela peut être nécessaire lorsque les groupes sont stockés dans LDAP ou AD. Cet indicateur est activé par défaut.
closefrom_override
S'il est défini, l'utilisateur peut utiliser l'option -C qui remplace le point de départ par défaut à partir duquel sudo commence à fermer les descripteurs de fichiers ouverts. Cet indicateur est désactivé par défaut.
compress_io
S'il est défini et que sudo est configuré pour enregistrer l'entrée ou la sortie d'une commande, les journaux d'E/S seront compressés à l'aide de zlib. Cet indicateur est activé par défaut lorsque sudo est compilé avec le support zlib.
exec_background
Par défaut, sudo exécute une commande en tant que processus de premier plan tant que sudo lui-même s'exécute en premier plan. Lorsque l'indicateur exec_background est activé et que la commande est exécutée dans un pseudo-terminal (en raison de la journalisation des E/S ou de l'indicateur use_pty), la commande sera exécutée en tant que processus d'arrière-plan. Les tentatives de lecture du terminal de contrôle (ou de modification des paramètres du terminal) entraîneront la suspension de la commande avec le signal SIGTTIN (ou SIGTTOU dans le cas des paramètres du terminal). Si cela se produit alors que sudo est un processus de premier plan, la commande se verra accorder le terminal de contrôle et sera reprise au premier plan sans intervention de l'utilisateur. L'avantage de l'exécution initiale de la commande en arrière-plan est que sudo n'a pas besoin de lire depuis le terminal à moins que la commande ne le demande explicitement. Sinon, toute entrée du terminal doit être transmise à la commande, qu'elle l'ait demandée ou non (le noyau met en mémoire tampon les terminaux, il n'est donc pas possible de savoir si la commande souhaite réellement l'entrée). Ceci est différent du comportement historique de sudo ou lorsque la commande n'est pas exécutée dans un pseudo-terminal.

Pour que cela fonctionne de manière transparente, le système d'exploitation doit prendre en charge le redémarrage automatique des appels système. Malheureusement, tous les systèmes d'exploitation ne le font pas par défaut, et même ceux qui le font peuvent avoir des bugs. Par exemple, macOS ne redémarre pas les fonctions tcgetattr(3) et tcsetattr(3) (c'est un bug dans macOS). De plus, comme ce comportement dépend de l'arrêt des programmes avec les signaux SIGTTIN ou SIGTTOU et qu'ils se suspendent avec un signal différent (généralement SIGTOP), ils ne seront pas automatiquement mis au premier plan. Certaines versions de la commande Linux su(1) se comportent de cette manière. Cet indicateur est désactivé par défaut.

Ce réglage n'est pris en charge que par la version 1.8.7 ou supérieure. Il n'a aucun effet à moins que la journalisation des E/S ne soit activée ou que l'indicateur use_pty ne soit activé.

env_editor
S'il est défini, visudo utilisera la valeur des variables d'environnement SUDO_EDITOR, VISUAL ou EDITOR avant de recourir à la liste des éditeurs par défaut. visudo est généralement exécuté en tant que root, donc cet indicateur peut permettre à un utilisateur disposant des privilèges visudo d'exécuter des commandes arbitraires en tant que root sans journalisation. Une alternative consiste à placer une liste d'éditeurs « sûrs », séparés par des deux-points, dans le paramètre editor. visudo n'utilisera alors SUDO_EDITOR, VISUAL ou EDITOR que s'ils correspondent à une valeur spécifiée dans editor. Si l'indicateur env_reset est activé, les variables d'environnement SUDO_EDITOR, VISUAL et/ou EDITOR doivent être présentes dans la liste env_keep pour que l'indicateur env_editor fonctionne lorsque visudo est invoqué via sudo. Cet indicateur est activé par défaut.
env_reset
S'il est défini, sudo exécutera la commande dans un environnement minimal contenant les variables TERM, PATH, HOME, MAIL, SHELL, LOGNAME, USER et SUDO_*. Les variables de l'environnement de l'appelant ou du fichier spécifié par le paramètre restricted_env_file qui correspondent aux listes env_keep et env_check sont ensuite ajoutées, suivies des variables présentes dans le fichier spécifié par le paramètre env_file (le cas échéant). Le contenu des listes env_keep et env_check, tel que modifié par les paramètres Defaults globaux dans sudoers, est affiché lorsque sudo est exécuté par root avec l'option -V. Si le paramètre secure_path est activé, sa valeur sera utilisée pour la variable d'environnement PATH. Cet indicateur est activé par défaut.
fast_glob
Normalement, sudo utilise la fonction glob(3) pour effectuer une correspondance de noms de chemins de type shell. Cependant, comme elle accède au système de fichiers, glob(3) peut prendre beaucoup de temps à se terminer pour certains motifs, en particulier lorsque le motif référence un système de fichiers réseau monté à la demande (montage automatique). L'indicateur fast_glob fait en sorte que sudo utilise la fonction fnmatch(3), qui n'accède pas au
file system pour effectuer sa correspondance. Le désavantage de fast_glob est qu'il ne peut pas correspondre aux chemins relatifs tels que ./ls ou ../bin/ls. Cela a des implications de sécurité lorsque des noms de chemins incluant des caractères de globbing sont utilisés avec l'opérateur de négation, ‘!’, car de telles règles peuvent être trivialement contournées. Par conséquent, ce drapeau ne doit pas être utilisé lorsque le fichier sudoers contient des règles contenant des noms de chemins négatifs incluant des caractères de globbing. Ce drapeau est désactivé par défaut.
log_passwords
La plupart des programmes qui nécessitent le mot de passe d'un utilisateur désactivent l'écho avant de lire le mot de passe pour éviter d'afficher le mot de passe en clair à l'écran. Cependant, si l'entrée du terminal est enregistrée (voir ENREGISTREMENT DES E/S), le mot de passe sera toujours présent dans le journal des E/S. Si l'option log_passwords est désactivée, sudoers tentera d'empêcher l'enregistrement des mots de passe. Pour ce faire, il utilise les expressions régulières de passprompt_regex pour faire correspondre une invite de mot de passe dans le tampon de sortie du terminal. Lorsqu'une correspondance est trouvée, les caractères d'entrée dans le journal des E/S seront remplacés par ‘*’ jusqu'à ce qu'un saut de ligne ou un retour chariot soit trouvé dans l'entrée du terminal ou qu'un nouveau tampon de sortie de terminal soit reçu. Si, toutefois, un programme affiche des caractères au fur et à mesure que l'utilisateur tape (comme sudo lorsque pwfeedback est défini), seul le premier caractère du mot de passe sera remplacé dans le journal des E/S. Cette option n'a aucun effet sauf si log_input ou log_ttyin sont également définis. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.9.10 ou supérieure.

fqdn
Définissez ce drapeau si vous souhaitez utiliser des noms d'hôte entièrement qualifiés dans le fichier sudoers lorsque le nom d'hôte local (tel que retourné par la commande ‘hostname’) ne contient pas le nom de domaine. En d'autres termes, au lieu de monhote, vous utiliseriez monhote.mondomaine.edu. Vous pouvez toujours utiliser la forme courte si vous le souhaitez (et même mélanger les deux). Ce drapeau n'est effectif que lorsque le nom d'hôte « canonique », tel que retourné par la fonction getaddrinfo(3) ou gethostbyname(3), est un nom de domaine entièrement qualifié. C'est généralement le cas lorsque le système est configuré pour utiliser DNS pour la résolution des noms d'hôte.

Si le système est configuré pour utiliser le fichier /etc/hosts de préférence à DNS, le nom d'hôte « canonique » peut ne pas être entièrement qualifié. L'ordre dans lequel les sources sont interrogées pour la résolution des noms d'hôte est généralement spécifié dans le fichier /etc/nsswitch.conf, /etc/netsvc.conf, /etc/host.conf, ou, dans certains cas, /etc/resolv.conf. Dans le fichier /etc/hosts, le premier nom d'hôte de l'entrée est considéré comme le nom « canonique » ; les noms suivants sont des alias qui ne sont pas utilisés par sudoers. Par exemple, la ligne suivante du fichier hosts pour la machine « xyzzy » a le nom de domaine entièrement qualifié comme nom d'hôte « canonique », et la version courte comme alias.

192.168.1.1 xyzzy.sudo.ws xyzzy

Si l'entrée du fichier hosts de la machine n'est pas formatée correctement, le drapeau fqdn ne sera pas effectif s'il est interrogé avant DNS.

Attention, lorsque vous utilisez DNS pour la résolution des noms d'hôte, l'activation de fqdn oblige sudoers à effectuer des recherches DNS, ce qui rend sudo inutilisable si DNS cesse de fonctionner (par exemple, si la machine est déconnectée du réseau). Comme avec le fichier hosts, vous devez utiliser le nom « canonique » tel que DNS le connaît. C'est-à-dire que vous ne pouvez pas utiliser un alias d'hôte (entrée CNAME) en raison de problèmes de performance et du fait qu'il n'y a aucun moyen d'obtenir tous les alias de DNS.

Ce drapeau est désactivé par défaut.

ignore_audit_errors
Permet l'exécution des commandes même si sudoers ne peut pas écrire dans le journal d'audit. Si activé, une erreur d'écriture dans le journal d'audit n'est pas traitée comme une erreur fatale. Si désactivé, une commande ne peut être exécutée qu'après que l'événement d'audit a été écrit avec succès. Ce drapeau n'est effectif que sur les systèmes pour lesquels sudoers prend en charge l'enregistrement d'audit, y compris FreeBSD, Linux, macOS et Solaris. Ce drapeau est activé par défaut.
ignore_dot
S'il est défini, sudo ignorera « . » ou « » (les deux désignant le répertoire courant) dans la variable d'environnement PATH ; le PATH lui-même n'est pas modifié. Ce drapeau est activé par défaut.
ignore_iolog_errors
Permet l'exécution des commandes même si sudoers ne peut pas écrire dans le journal des E/S (local ou distant). S'il est activé, une erreur d'écriture dans le journal des E/S n'est pas traitée comme une erreur fatale. S'il est désactivé, la commande sera terminée si le journal des E/S ne peut pas être écrit. Ce drapeau est désactivé par défaut.
ignore_logfile_errors
Permet l'exécution des commandes même si sudoers ne peut pas écrire dans le fichier journal. S'il est activé, une erreur d'écriture dans le fichier journal n'est pas traitée comme une erreur fatale. S'il est désactivé, une commande ne peut être exécutée qu'après que l'entrée du fichier journal a été écrite avec succès. Ce drapeau n'a d'effet que lorsque sudoers est configuré pour utiliser la journalisation basée sur des fichiers via le paramètre logfile. Ce drapeau est activé par défaut.
ignore_local_sudoers
S'il est défini via LDAP, l'analyse de /etc/sudoers sera ignorée. Ceci est destiné aux sites qui souhaitent empêcher l'utilisation des fichiers sudoers locaux afin que seul LDAP soit utilisé. Cela déjoue les efforts des opérateurs malveillants qui tenteraient d'ajouter des rôles à /etc/sudoers. Lorsque ce drapeau est activé, /etc/sudoers n'a même pas besoin d'exister. Étant donné que ce drapeau indique à sudo comment se comporter lorsqu'aucune entrée LDAP spécifique n'a été trouvée, cette option sudo n'est significative que pour la section ‘cn=defaults’. Ce drapeau est désactivé par défaut.
ignore_unknown_defaults
S'il est défini, sudo ne produira pas d'avertissement s'il rencontre une entrée Defaults inconnue dans le fichier sudoers ou une sudoOption inconnue dans LDAP. Ce drapeau est désactivé par défaut.
insults
S'il est défini, sudo insultera les utilisateurs lorsqu'ils entreront un mot de passe incorrect. Ce drapeau est désactivé par défaut.
log_allowed
S'il est défini, sudoers enregistrera les commandes autorisées par la politique dans le journal d'audit du système (lorsqu'il est pris en charge) ainsi que dans syslog et/ou un fichier journal. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.8.29 ou supérieure.

log_denied
S'il est défini, sudoers enregistrera les commandes refusées par la politique dans le journal d'audit du système (lorsqu'il est pris en charge) ainsi que dans syslog et/ou un fichier journal. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.8.29 ou supérieure.

log_exit_status
S'il est défini, sudoers enregistrera la valeur de sortie des commandes exécutées dans syslog et/ou un fichier journal. Si une commande a été terminée par un signal, le nom du signal est également enregistré. Ce drapeau est désactivé par défaut.

Ce paramètre n'est pris en charge que par la version 1.9.8 ou supérieure.

log_host
S'il est défini, le nom d'hôte sera inclus dans les entrées de journal écrites dans le fichier configuré par le paramètre logfile. Ce drapeau est désactivé par défaut.
log_input
S'il est défini, sudo exécutera la commande dans un pseudo-terminal (si sudo a été exécuté à partir d'un terminal) et enregistrera toute entrée utilisateur. Si l'entrée standard n'est pas connectée au terminal de l'utilisateur, en raison d'une redirection d'E/S ou parce que la commande fait partie d'un pipeline, cette entrée est également enregistrée. Pour plus d'informations sur l'enregistrement des E/S, voir la section ENREGISTREMENT DES E/S. Ce drapeau est désactivé par défaut.
log_output
S'il est défini, sudo exécutera la commande dans un pseudo-terminal (si sudo a été exécuté à partir d'un terminal) et enregistrera toute sortie envoyée au terminal de l'utilisateur, à la sortie standard ou à l'erreur standard. Si la sortie standard ou l'erreur standard n'est pas connectée au terminal de l'utilisateur, en raison d'une redirection d'E/S ou parce que la commande fait partie d'un pipeline, cette sortie est également enregistrée. Pour plus d'informations sur l'enregistrement des E/S, voir la section ENREGISTREMENT DES E/S. Ce drapeau est désactivé par défaut.
log_server_keepalive
S'il est défini, sudo activera l'option de socket TCP keepalive sur la connexion au serveur de journalisation. Cela permet la transmission périodique de messages keepalive au serveur. Si le serveur ne répond pas à un message, la connexion sera fermée et la commande en cours d'exécution sera terminée, sauf si le drapeau ignore_iolog_errors (journalisation des E/S activée) ou le drapeau ignore_log_errors (journalisation des E/S désactivée) est défini. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.9.0 ou supérieure.

log_server_verify
S'il est défini, le certificat serveur reçu lors de la négociation TLS doit être valide et contenir soit le nom du serveur (provenant de log_servers), soit son adresse IP. Si l'une de ces conditions n'est pas remplie, la négociation TLS échouera. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.9.0 ou supérieure.

log_stderr
S'il est défini, sudo enregistrera l'erreur standard si elle n'est pas connectée au terminal de l'utilisateur. Ceci peut être utilisé pour enregistrer la sortie vers un pipe ou redirigée vers un fichier. Ce drapeau est désactivé par défaut mais est activé lorsque le drapeau log_output ou la balise de commande LOG_OUTPUT est défini.
log_stdin
S'il est défini, sudo enregistrera l'entrée standard si elle n'est pas connectée à le terminal de l'utilisateur. Cela peut être utilisé pour enregistrer les entrées d'un tube ou redirigées depuis un fichier. Ce drapeau est désactivé par défaut, mais il est activé lorsque le drapeau log_input ou l'étiquette de commande LOG_INPUT est définie.
log_stdout
S'il est défini, sudo enregistrera la sortie standard si elle n'est pas connectée au terminal de l'utilisateur. Cela peut être utilisé pour enregistrer la sortie dans un tube ou redirigée vers un fichier. Ce drapeau est désactivé par défaut, mais il est activé lorsque le drapeau log_output ou l'étiquette de commande LOG_OUTPUT est définie.
log_subcmds
S'il est défini, sudoers enregistrera lorsqu'une commande lance un processus enfant et exécute un programme à l'aide des fonctions de bibliothèque execve(2), execl(3), execle(3), execlp(3), execv(3), execvp(3), execvpe(3), ou system(3). Par exemple, si un shell est lancé par sudo, les commandes individuelles exécutées via le shell seront enregistrées. Ce drapeau est désactivé par défaut.

Le drapeau log_subcmds utilise le même mécanisme sous-jacent que le réglage intercept. Certaines commandes peuvent ne pas fonctionner correctement lorsque log_subcmds est activé, en raison de la manière dont il intercepte les sous-commandes. Voir Prévenir les évasions de shell pour plus d'informations sur les systèmes qui prennent en charge cette option et ses limitations. Ce réglage n'est pris en charge que par la version 1.9.8 ou supérieure et est incompatible avec la prise en charge RBAC de SELinux, sauf si le système prend en charge le mode filtre seccomp(2).

log_ttyin
S'il est défini, sudo exécutera la commande dans un pseudo-terminal et enregistrera les frappes de l'utilisateur envoyées au terminal de l'utilisateur, s'il y en a un. Ce drapeau est désactivé par défaut, mais il est activé lorsque le drapeau log_input ou l'étiquette LOG_INPUT est définie. S'il n'y a pas de terminal, par exemple lors de l'exécution d'une commande à distance à l'aide de ssh(1), ce drapeau n'aura aucun effet.
log_ttyout
S'il est défini, sudo exécutera la commande dans un pseudo-terminal et enregistrera toutes les sorties affichées sur le terminal de l'utilisateur, s'il y en a un. Ce drapeau est désactivé par défaut, mais il est activé lorsque le drapeau log_output ou l'étiquette LOG_OUTPUT est définie. S'il n'y a pas de terminal, par exemple lors de l'exécution d'une commande à distance à l'aide de ssh(1), ce drapeau n'aura aucun effet.
log_year
S'il est défini, l'année à quatre chiffres sera enregistrée dans le fichier journal sudo (non syslog). Ce drapeau est désactivé par défaut.
long_otp_prompt
Lors de la validation avec un schéma de mot de passe à usage unique (OTP) tel que S/Key ou OPIE, une invite à deux lignes est utilisée pour faciliter le copier-coller du défi vers une fenêtre locale. Ce n'est pas aussi joli que par défaut, mais certains trouvent cela plus pratique. Ce drapeau est désactivé par défaut.
mail_all_cmnds
Envoyer un e-mail à l'utilisateur mailto chaque fois qu'un utilisateur tente d'exécuter une commande via sudo (cela inclut sudoedit). Aucun e-mail ne sera envoyé si l'utilisateur exécute sudo avec les options -l ou -v, sauf en cas d'erreur d'authentification et si le drapeau mail_badpass est également défini. Ce drapeau est désactivé par défaut.
mail_always
Envoyer un e-mail à l'utilisateur mailto chaque fois qu'un utilisateur exécute sudo. Ce drapeau est désactivé par défaut.
mail_badpass
Envoyer un e-mail à l'utilisateur mailto si l'utilisateur exécutant sudo ne saisit pas le bon mot de passe. Si la commande que l'utilisateur tente d'exécuter n'est pas autorisée par sudoers et que l'un des drapeaux mail_all_cmnds, mail_always, mail_no_host, mail_no_perms ou mail_no_user est défini, ce drapeau n'aura aucun effet. Ce drapeau est désactivé par défaut.
mail_no_host
S'il est défini, un e-mail sera envoyé à l'utilisateur mailto si l'utilisateur appelant existe dans le fichier sudoers, mais n'est pas autorisé à exécuter des commandes sur l'hôte actuel. Ce drapeau est désactivé par défaut.
mail_no_perms
S'il est défini, un e-mail sera envoyé à l'utilisateur mailto si l'utilisateur appelant est autorisé à utiliser sudo mais que la commande qu'il essaie d'exécuter n'est pas répertoriée dans leur entrée sudoers ou est explicitement refusée. Ce drapeau est désactivé par défaut.
mail_no_user
S'il est défini, un e-mail sera envoyé à l'utilisateur mailto si l'utilisateur appelant n'est pas dans le fichier sudoers. Ce drapeau est activé par défaut.
match_group_by_gid
Par défaut, sudoers recherche chaque groupe dont l'utilisateur est membre par identifiant de groupe pour déterminer le nom du groupe (cela n'est fait qu'une seule fois). La liste résultante des noms de groupe de l'utilisateur est utilisée lors de la comparaison des groupes répertoriés dans le fichier sudoers. Cela fonctionne bien sur les systèmes où le nombre de groupes répertoriés dans le fichier sudoers est supérieur au nombre de groupes auxquels un utilisateur typique appartient. Sur les systèmes où les recherches de groupe sont lentes, où les utilisateurs peuvent appartenir à un grand nombre de groupes, ou où le nombre de groupes répertoriés dans le fichier sudoers est relativement petit, cela peut être prohibitif et l'exécution de commandes via sudo peut prendre plus de temps que la normale. Sur de tels systèmes, il peut être plus rapide d'utiliser le drapeau match_group_by_gid pour éviter de résoudre les identifiants de groupe des utilisateurs en noms de groupe. Dans ce cas, sudoers doit rechercher tout nom de groupe répertorié dans le fichier sudoers et utiliser l'identifiant de groupe au lieu du nom du groupe pour déterminer si l'utilisateur est membre du groupe.

Si match_group_by_gid est activé, les recherches dans la base de données des groupes effectuées par sudoers seront indexées par nom de groupe par opposition à l'identifiant de groupe. Sur les systèmes où il existe plusieurs sources pour la base de données des groupes, il est possible d'avoir des noms de groupe ou des identifiants de groupe conflictuels dans le fichier local /etc/group et la base de données des groupes distante. Sur de tels systèmes, l'activation ou la désactivation de match_group_by_gid peut être utilisée pour choisir si les requêtes de base de données de groupe sont effectuées par nom (activé) ou par ID (désactivé), ce qui peut aider à contourner les conflits d'entrées de groupe.

Le drapeau match_group_by_gid n'a aucun effet lorsque les données sudoers sont stockées dans LDAP. Ce drapeau est désactivé par défaut.

Ce réglage n'est pris en charge que par la version 1.8.18 ou supérieure.

intercept
S'il est défini, toutes les commandes exécutées via sudo se comporteront comme si l'étiquette INTERCEPT était définie, sauf si elle est remplacée par une étiquette NOINTERCEPT. Certaines commandes peuvent ne pas fonctionner correctement lorsque intercept est activé, en raison de la manière dont il intercepte les sous-commandes. Voir la description de INTERCEPT et NOINTERCEPT ci-dessus ainsi que la section Prévenir les évasions de shell à la fin de ce manuel. Ce drapeau est désactivé par défaut.

Ce réglage n'est pris en charge que par la version 1.9.8 ou supérieure et est incompatible avec la prise en charge RBAC de SELinux, sauf si le système prend en charge le mode filtre seccomp(2).

intercept_allow_setid
Sur la plupart des systèmes, le chargeur dynamique ignore LD_PRELOAD (ou son équivalent) lors de l'exécution de programmes set-user-ID et set-group-ID, désactivant ainsi efficacement le mode d'interception. Pour éviter que cela ne se produise, sudoers n'autorisera pas l'exécution d'un programme set-user-ID ou set-group-ID en mode d'interception, sauf si intercept_allow_setid est activé. Ce drapeau n'a aucun effet sauf si le drapeau intercept est activé ou si l'étiquette INTERCEPT a été définie pour la commande. Ce drapeau est activé par défaut lorsque l'option intercept_type est définie sur trace, sinon il est désactivé par défaut.

Ce réglage n'est pris en charge que par la version 1.9.8 ou supérieure.

intercept_authenticate
S'il est défini, les commandes exécutées par un processus intercepté doivent être authentifiées lorsque le tampon temporel de l'utilisateur n'est pas actuel. Par exemple, si un shell est exécuté avec intercept activé, dès que le tampon temporel de l'utilisateur est obsolète, les commandes ultérieures devront être authentifiées. Ce drapeau n'a aucun effet sauf si le drapeau intercept est activé ou si l'étiquette INTERCEPT a été définie pour la commande. Ce drapeau est désactivé par défaut.

Ce réglage n'est pris en charge que par la version 1.9.8 ou supérieure.

intercept_verify
S'il est défini, sudo tentera de vérifier que la commande exécutée en mode d'interception a le nom de chemin, les arguments de ligne de commande et l'environnement attendus.

Le processus sera arrêté après l'exécution de execve(2) mais avant que la nouvelle commande n'ait eu la possibilité de s'exécuter. Pour vérifier la commande, sudo lira le chemin de la commande à partir de /proc/PID/exe, les arguments de ligne de commande et l'environnement à partir de la mémoire du processus, et les comparera aux arguments qui ont été passés à execve(2). En cas de discordance, la commande recevra un signal SIGKILL et sera terminée.

Cela peut aider à prévenir un problème de type "time of check versus time of use" avec l'interce

pt où les arguments d'execve(2) pouvaient être modifiés après la vérification de la politique sudoers. Les vérifications ne peuvent être effectuées que si le système de fichiers proc(5) est disponible. Ce drapeau n'a aucun effet à moins que le drapeau intercept ne soit activé ou que la balise INTERCEPT n'ait été définie pour la commande et que l'option intercept_type ne soit définie sur trace.

Ce paramètre est incompatible avec les programmes qui changent leur répertoire racine via chroot(2). Si un programme change son répertoire racine, les noms de chemin ne correspondront plus à ceux vus par le processus parent sudo et les sous-commandes seront terminées avant d'avoir une chance de s'exécuter. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.9.12 ou supérieure.

netgroup_tuple
S'il est défini, les recherches de netgroup seront effectuées en utilisant le tuple netgroup complet : nom d'hôte, nom d'utilisateur et domaine (si l'un est défini). Historiquement, sudo ne faisait correspondre que le nom d'utilisateur et le domaine pour les netgroups utilisés dans une User_List et ne faisait correspondre que le nom d'hôte et le domaine pour les netgroups utilisés dans une Host_List. Ce drapeau est désactivé par défaut.
noexec
S'il est défini, toutes les commandes exécutées via sudo se comporteront comme si la balise NOEXEC était définie, sauf si elle est remplacée par une balise EXEC. Voir la description de EXEC et NOEXEC ci-dessus ainsi que la section Prévention des évasions de shell à la fin de ce manuel. Ce drapeau est désactivé par défaut.
noninteractive_auth
S'il est défini, une tentative d'authentification sera effectuée même en mode non interactif (lorsque l'option -n de sudo est spécifiée). Cela permet aux méthodes d'authentification qui ne nécessitent pas d'interaction utilisateur de réussir. Les méthodes d'authentification qui nécessitent une entrée du terminal de l'utilisateur échoueront toujours. S'il est désactivé, l'authentification ne sera pas tentée en mode non interactif. Ce drapeau est désactivé par défaut.

Ce paramètre n'est pris en charge que par la version 1.9.10 ou supérieure.

pam_acct_mgmt
Sur les systèmes qui utilisent PAM pour l'authentification, sudo effectuera la validation de compte PAM pour l'utilisateur appelant par défaut. Les vérifications effectuées dépendent des modules PAM configurés. S'il est activé, la validation de compte sera effectuée, qu'un mot de passe soit requis ou non. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.8.28 ou supérieure.

pam_rhost
Sur les systèmes qui utilisent PAM pour l'authentification, sudo définira la valeur de l'hôte distant PAM sur le nom de l'hôte local lorsque le drapeau pam_rhost est activé. Sur les systèmes Linux, l'activation de pam_rhost peut entraîner des recherches DNS du nom d'hôte local lorsque PAM est initialisé. Sur les versions Solaris antérieures à Solaris 8, pam_rhost doit être activé si pam_ruser est également activé pour éviter un crash dans l'implémentation PAM de Solaris.

Ce drapeau est désactivé par défaut sur les systèmes autres que Solaris.

Ce paramètre n'est pris en charge que par la version 1.9.0 ou supérieure.

pam_ruser
Sur les systèmes qui utilisent PAM pour l'authentification, sudo définira la valeur de l'utilisateur distant PAM sur le nom de l'utilisateur qui a invoqué sudo lorsque le drapeau pam_ruser est activé. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.9.0 ou supérieure.

pam_session
Sur les systèmes qui utilisent PAM pour l'authentification, sudo créera une nouvelle session PAM pour la commande à exécuter. Sauf si sudo reçoit les options -i ou -s, les modules de session PAM sont exécutés avec le drapeau « silencieux » activé. Cela empêche l'affichage des informations de dernière connexion pour chaque commande sur certains systèmes. La désactivation de pam_session peut être nécessaire sur des implémentations PAM plus anciennes ou sur des systèmes d'exploitation où l'ouverture d'une session PAM modifie les fichiers utmp ou wtmp. Si le support de session PAM est désactivé, les limites de ressources peuvent ne pas être mises à jour pour la commande en cours d'exécution. Si pam_session, pam_setcred et use_pty sont désactivés, log_servers n'a pas été défini et la journalisation des E/S n'a pas été configurée, sudo exécutera la commande directement au lieu de l'exécuter en tant que processus enfant. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.8.7 ou supérieure.

pam_setcred
Sur les systèmes qui utilisent PAM pour l'authentification, sudo tentera d'établir les identifiants pour l'utilisateur cible par défaut, si cela est pris en charge par le système d'authentification sous-jacent. Un exemple d'identifiant est un ticket Kerberos. Si pam_session, pam_setcred et use_pty sont désactivés, log_servers n'a pas été défini et la journalisation des E/S n'a pas été configurée, sudo exécutera la commande directement au lieu de l'exécuter en tant que processus enfant. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.8.8 ou supérieure.

pam_silent
S'il est défini, l'authentification PAM sera effectuée en mode silencieux. Cela empêche les modules d'authentification PAM de générer une sortie. Dans certains cas, cela peut masquer des informations importantes sur la raison pour laquelle l'authentification a échoué. Par exemple, les modules PAM tels que pam_faillock n'afficheront qu'un avertissement si pam_silent est désactivé. Ce drapeau est activé par défaut.

Ce paramètre n'est pris en charge que par la version 1.9.16 ou supérieure.

passprompt_override
S'il est défini, l'invite spécifiée par passprompt ou la variable d'environnement SUDO_PROMPT sera toujours utilisée et remplacera l'invite fournie par un module PAM ou une autre méthode d'authentification. Ce drapeau est désactivé par défaut.
path_info
Normalement, sudo indiquera à l'utilisateur si une commande n'a pas été trouvée dans sa variable d'environnement PATH. Certains sites peuvent souhaiter désactiver cela car cela pourrait être utilisé pour recueillir des informations sur l'emplacement des exécutables auxquels l'utilisateur normal n'a pas accès. L'inconvénient est que si l'exécutable n'est tout simplement pas dans le PATH de l'utilisateur, sudo indiquera à l'utilisateur qu'il n'est pas autorisé à l'exécuter, ce qui peut être source de confusion. Ce drapeau est activé par défaut.
preserve_groups
Par défaut, sudo initialisera le vecteur de groupes avec la liste des groupes auxquels appartient l'utilisateur cible. Lorsque preserve_groups est défini, le vecteur de groupes existant de l'utilisateur reste inchangé. Les identifiants de groupe réels et effectifs, cependant, sont toujours définis pour correspondre à l'utilisateur cible. Ce drapeau est désactivé par défaut.
pwfeedback
Par défaut, sudo lit le mot de passe comme la plupart des autres programmes Unix, en désactivant l'écho jusqu'à ce que l'utilisateur appuie sur la touche retour (ou entrée). Certains utilisateurs peuvent être déconcertés par cela car il leur semble que sudo est bloqué à ce stade. Lorsque pwfeedback est défini, sudo fournira un retour visuel lorsque l'utilisateur appuie sur une touche. Cela a un impact sur la sécurité car un observateur pourrait déterminer la longueur du mot de passe saisi. Ce drapeau est désactivé par défaut.
requiretty
S'il est défini, sudo ne s'exécutera que lorsque l'utilisateur est connecté à un vrai tty. Lorsque ce drapeau est défini, sudo ne peut être exécuté qu'à partir d'une session de connexion et non par d'autres moyens tels que cron(8) ou des scripts cgi-bin. Ce drapeau est désactivé par défaut.
root_sudo
S'il est défini, root est autorisé à exécuter sudo également. Désactiver cela empêche les utilisateurs de « chaîner » les commandes sudo pour obtenir un shell root en faisant quelque chose comme ‘sudo sudo /bin/sh’. Notez cependant que désactiver root_sudo empêchera également root d'exécuter sudoedit. La désactivation de root_sudo n'apporte aucune sécurité supplémentaire réelle ; elle existe purement pour des raisons historiques. Ce drapeau est activé par défaut.
rootpw
S'il est défini, sudo demandera le mot de passe de root au lieu du mot de passe de l'utilisateur appelant lors de l'exécution d'une commande ou de l'édition d'un fichier. Ce drapeau est désactivé par défaut.
runas_allow_unknown_id
S'il est activé, autorise la correspondance des identifiants d'utilisateur et de groupe runas qui ne sont pas présents dans les bases de données de mots de passe ou de groupes. En plus de faire correspondre explicitement les identifiants d'utilisateur ou de groupe inconnus dans une Runas_List, cette option permet également à l'alias ALL de faire correspondre les identifiants inconnus. Ce drapeau est désactivé par défaut.

Ce paramètre n'est pris en charge que par la version 1.8.30 ou supérieure. Les versions antérieures de sudo autorisaient toujours la correspondance des identifiants d'utilisateur et de groupe inconnus.

runas_check_shell
S'il est activé, sudo n'exécutera les commandes qu'en tant qu'utilisateur dont le shell apparaît dans le fichier /etc/shells, même si la Runas_List de l'utilisateur appelant le permettrait autrement. Si aucun fichier /etc/shells n'est présent, une liste de shells par défaut intégrés dépendante du système est utilisée. Sur de nombreux systèmes d'exploitation, les utilisateurs système tels que « bin » n'ont pas de shell valide et ce drapeau peut être utilisé pour empêcher l'exécution de commandes en tant que ces utilisateurs. Ce drapeau est désactivé par défaut.

Ce paramètre n'est pris en charge que par la version 1.8.30 ou supérieure.

runaspw
S'il est défini, sudo demandera le mot de passe de l'utilisateur défini par l'option runas_default (par défaut root) au lieu du mot de passe de l'utilisateur appelant wh
en en cours d'exécution d'une commande ou de modification d'un fichier. Cet indicateur est désactivé par défaut.
set_home
S'il est activé et que sudo est invoqué avec l'option -s, la variable d'environnement HOME sera définie sur le répertoire personnel de l'utilisateur cible (qui est l'utilisateur runas_default sauf si l'option -u est utilisée). Cet indicateur est largement obsolète et n'a aucun effet à moins que l'indicateur env_reset n'ait été désactivé ou que HOME ne soit présent dans la liste env_keep, deux situations fortement déconseillées. Cet indicateur est désactivé par défaut.
set_logname
Normalement, sudo définit les variables d'environnement LOGNAME et USER sur le nom de l'utilisateur cible (l'utilisateur spécifié par runas_default sauf si l'option -u est donnée). Cependant, comme certains programmes (y compris le système de contrôle de révision RCS) utilisent LOGNAME pour déterminer l'identité réelle de l'utilisateur, il peut être souhaitable de modifier ce comportement. Cela peut être fait en niant l'option set_logname. L'option set_logname n'aura aucun effet si l'option env_reset n'a pas été désactivée et que la liste env_keep contient LOGNAME ou USER. Cet indicateur est activé par défaut.
set_utmp
Lorsqu'il est activé, sudo créera une entrée dans le fichier utmp (ou utmpx) lorsqu'un pseudo-terminal est alloué. Un pseudo-terminal est alloué par sudo lorsqu'il s'exécute dans un terminal et qu'un ou plusieurs des indicateurs log_input, log_output, log_stdin, log_stdout, log_stderr, log_ttyin, log_ttyout, ou use_pty sont activés. Par défaut, la nouvelle entrée sera une copie de l'entrée utmp existante de l'utilisateur (le cas échéant), avec les champs tty, time, type et pid mis à jour. Cet indicateur est activé par défaut.
setenv
Permet à l'utilisateur de désactiver l'option env_reset depuis la ligne de commande via l'option -E. De plus, les variables d'environnement définies via la ligne de commande ne sont pas soumises aux restrictions imposées par env_check, env_delete, ou env_keep. En tant que tel, seuls les utilisateurs de confiance devraient être autorisés à définir des variables de cette manière. Cet indicateur est désactivé par défaut.
shell_noargs
S'il est défini et que sudo est invoqué sans arguments, il agit comme si l'option -s avait été donnée. C'est-à-dire qu'il exécute un shell en tant que root (le shell est déterminé par la variable d'environnement SHELL si elle est définie, sinon par le shell listé dans l'entrée /etc/passwd de l'utilisateur appelant). Cet indicateur est désactivé par défaut.
stay_setuid
Normalement, lorsque sudo exécute une commande, les UID réels et effectifs sont définis sur l'utilisateur cible (root par défaut). Cette option modifie ce comportement de telle sorte que l'UID réel reste l'UID de l'utilisateur appelant. En d'autres termes, cela fait de sudo un wrapper set-user-ID. Cela peut être utile sur les systèmes qui désactivent certaines fonctionnalités potentiellement dangereuses lorsqu'un programme est exécuté set-user-ID. Cette option n'est effective que sur les systèmes qui prennent en charge l'appel système setreuid(2) ou setresuid(2). Cet indicateur est désactivé par défaut.
sudoedit_checkdir
S'il est défini, sudoedit vérifiera tous les composants du répertoire du chemin à modifier pour s'assurer qu'ils sont écrivables par l'utilisateur appelant. Les liens symboliques ne seront pas suivis dans les répertoires accessibles en écriture et sudoedit refusera de modifier un fichier situé dans un répertoire accessible en écriture. Ces restrictions ne sont pas appliquées lorsque sudoedit est exécuté par root. Sur certains systèmes, si tous les composants du répertoire du chemin à modifier ne sont pas lisibles par l'utilisateur cible, sudoedit sera incapable de modifier le fichier. Cet indicateur est activé par défaut.

Ce paramètre a été introduit pour la première fois dans la version 1.8.15 mais souffrait initialement d'une condition de concurrence. La vérification des liens symboliques dans les répertoires intermédiaires accessibles en écriture a été ajoutée dans la version 1.8.16.

sudoedit_follow
Par défaut, sudoedit ne suivra pas les liens symboliques lors de l'ouverture des fichiers. L'option sudoedit_follow peut être activée pour permettre à sudoedit d'ouvrir les liens symboliques. Elle peut être remplacée sur une base par commande par les balises FOLLOW et NOFOLLOW. Cet indicateur est désactivé par défaut.

Ce paramètre n'est pris en charge que par les versions 1.8.15 ou supérieures.

syslog_pid
Lors de la journalisation via syslog(3), inclure l'identifiant du processus dans l'entrée de journal. Cet indicateur est désactivé par défaut.

Ce paramètre n'est pris en charge que par les versions 1.8.21 ou supérieures.

targetpw
S'il est défini, sudo demandera le mot de passe de l'utilisateur spécifié par l'option -u (par défaut la valeur de runas_default) au lieu du mot de passe de l'utilisateur appelant lors de l'exécution d'une commande ou de la modification d'un fichier. Cet indicateur exclut l'utilisation d'un ID utilisateur non listé dans la base de données passwd comme argument de l'option -u. Cet indicateur est désactivé par défaut.
tty_tickets
S'il est défini, les utilisateurs doivent s'authentifier par terminal. Avec cet indicateur activé, sudo utilisera un enregistrement séparé dans le fichier d'horodatage pour chaque terminal. S'il est désactivé, un seul enregistrement est utilisé pour toutes les sessions de connexion.

Cette option a été remplacée par l'option timestamp_type.

umask_override
S'il est défini, sudo définira l'umask comme spécifié dans le fichier sudoers sans modification. Cela permet de spécifier une umask dans le fichier sudoers qui est plus permissive que l'umask de l'utilisateur et correspond au comportement historique. Si umask_override n'est pas défini, sudo définira l'umask comme étant l'union de l'umask de l'utilisateur et de ce qui est spécifié dans sudoers. Cet indicateur est désactivé par défaut.
use_netgroups
S'il est défini, les netgroups (précédés de ‘+’), peuvent être utilisés à la place d'un utilisateur ou d'un hôte. Pour les sudoers basés sur LDAP, le support des netgroups nécessite une coûteuse correspondance de sous-chaîne sur le serveur, sauf si la directive NETGROUP_BASE est présente dans le fichier /etc/openldap/ldap.conf. Si les netgroups ne sont pas nécessaires, cette option peut être désactivée pour réduire la charge sur le serveur LDAP. Cet indicateur est activé par défaut.
use_pty
S'il est défini, et que sudo s'exécute dans un terminal, la commande sera exécutée dans un nouveau pseudo-terminal. Si le processus sudo n'est pas attaché à un terminal, use_pty n'a aucun effet.

Un programme malveillant exécuté sous sudo peut être capable d'injecter des commandes dans le terminal de l'utilisateur ou d'exécuter un processus en arrière-plan qui conserve l'accès au périphérique de terminal de l'utilisateur même après que le programme principal ait terminé son exécution. En exécutant la commande dans un pseudo-terminal séparé, cette attaque n'est plus possible.

Un effet secondaire de l'exécution de la commande dans un nouveau pseudo-terminal est que les entrées seront transmises à la commande même si elle est non interactive. Cela signifie que, par exemple, les touches pressées pendant qu'une commande non interactive est en cours d'exécution seront consommées par sudo au lieu d'être transmises au shell après la fin de la commande.

Cet indicateur est activé par défaut pour sudo 1.9.14 et versions ultérieures.

user_command_timeouts
S'il est défini, l'utilisateur peut spécifier un délai d'attente sur la ligne de commande. Si le délai d'attente expire avant que la commande ne soit terminée, la commande sera terminée. Si un délai est spécifié à la fois dans le fichier sudoers et sur la ligne de commande, le plus petit des deux délais sera utilisé. Voir la section Timeout_Spec pour une description de la syntaxe du délai d'attente. Cet indicateur est désactivé par défaut.

Ce paramètre n'est pris en charge que par les versions 1.8.20 ou supérieures.

utmp_runas
S'il est défini, sudo stockera le nom de l'utilisateur runas lors de la mise à jour du fichier utmp (ou utmpx). Par défaut, sudo stocke le nom de l'utilisateur appelant. Cet indicateur est désactivé par défaut.
visiblepw
Par défaut, sudo refusera de s'exécuter si l'utilisateur doit entrer un mot de passe mais qu'il n'est pas possible de désactiver l'écho sur le terminal. Si l'indicateur visiblepw est défini, sudo demandera un mot de passe même lorsqu'il sera visible à l'écran. Cela permet d'exécuter des choses comme ‘ssh somehost sudo ls’ car par défaut, ssh(1) n'alloue pas de tty lors de l'exécution d'une commande. Cet indicateur est désactivé par défaut.

Entiers :

closefrom
Avant d'exécuter une commande, sudo fermera tous les descripteurs de fichiers ouverts autres que l'entrée standard, la sortie standard et l'erreur standard (descripteurs de fichiers 0 à 2). L'option closefrom peut être utilisée pour spécifier un descripteur de fichier différent à partir duquel commencer la fermeture. La valeur par défaut est 3.
command_timeout
La durée maximale pendant laquelle une commande est autorisée à s'exécuter avant d'être terminée. Voir la section Timeout_Spec pour une description de la syntaxe du délai d'attente.

Ce paramètre n'est pris en charge que par les versions 1.8.20 ou supérieures.

log_server_timeout
La durée maximale d'attente lors de la connexion à un serveur de journalisation ou lors de l'attente d'une réponse du serveur. Voir la section Timeout_Spec pour une description de la syntaxe du délai d'attente. La valeur par défaut t secondes.

Ce paramètre n'est pris en charge que par la version 1.9.0 ou une version ultérieure.

maxseq
Le numéro de séquence maximum qui sera substitué à l'échappatoire ‘%{seq}’ dans le fichier journal I/O (voir la description de iolog_dir ci-dessous pour plus d'informations). Bien que la valeur substituée pour ‘%{seq}’ soit en base 36, maxseq lui-même doit être exprimé en décimal. Les valeurs supérieures à 2176782336 (qui correspond au numéro de séquence en base 36 “ZZZZZZ”) seront silencieusement tronquées à 2176782336. La valeur par défaut est 2176782336.

Une fois que le numéro de séquence local atteint la valeur de maxseq, il "bouclera" à zéro, après quoi sudoers tronquera et réutilisera les noms de chemins de journaux I/O existants.

Ce paramètre n'est pris en charge que par la version 1.8.7 ou une version ultérieure.

passwd_tries
Le nombre de tentatives qu'un utilisateur a pour entrer son mot de passe avant que sudo n'enregistre l'échec et ne quitte. La valeur par défaut est 3.
syslog_maxlen
Sur de nombreux systèmes, syslog(3) a un tampon de journal relativement petit. L'IETF RFC 5424 stipule que les serveurs syslog doivent prendre en charge les messages d'au moins 480 octets et devraient prendre en charge les messages jusqu'à 2048 octets. Par défaut, sudoers crée des messages de journal allant jusqu'à 980 octets, ce qui correspond à l'implémentation historique de BSD syslog qui utilisait un tampon de 1024 octets pour stocker le message, la date, le nom d'hôte et le nom du programme. Pour éviter que les messages syslog ne soient tronqués, sudoers divisera les messages de journal plus grands que syslog_maxlen octets. Lorsqu'un message est divisé, des parties supplémentaires incluront la chaîne “(command continued)” après le nom d'utilisateur et avant les arguments de ligne de commande continués.

Ce paramètre n'est pris en charge que par la version 1.8.19 ou une version ultérieure.

Entiers pouvant être utilisés dans un contexte booléen :

loglinelen
Nombre de caractères par ligne pour le journal de fichiers. Cette valeur est utilisée pour décider quand passer à la ligne pour de plus beaux fichiers journaux. Cela n'a aucun effet sur le fichier journal syslog, uniquement sur le journal de fichiers. La valeur par défaut est 80 (utiliser 0 ou nier l'option pour désactiver le retour à la ligne).
passwd_timeout
Nombre de minutes avant que l'invite de mot de passe de sudo n'expire, ou 0 pour aucune expiration. L'expiration peut inclure un composant fractionnaire si la granularité en minutes est insuffisante, par exemple 2,5. La valeur par défaut est 5.
timestamp_timeout
Nombre de minutes qui peuvent s'écouler avant que sudo ne redemande le mot de passe. L'expiration peut inclure un composant fractionnaire si la granularité en minutes est insuffisante, par exemple 2,5. La valeur par défaut est 5. Réglez-la sur 0 pour toujours demander un mot de passe. Si elle est définie sur une valeur inférieure à 0, l'horodatage de l'utilisateur n'expirera pas avant le redémarrage du système. Cela peut être utilisé pour permettre aux utilisateurs de créer ou de supprimer leurs propres horodatages via ‘sudo -v’ et ‘sudo -k’ respectivement.
umask
Masque de création de mode de fichier à utiliser lors de l'exécution de la commande. Niez cette option ou définissez-la sur 0777 pour empêcher sudoers de modifier l'umask. Sauf si le drapeau umask_override est défini, l'umask réelle sera l'union de l'umask de l'utilisateur et de la valeur du paramètre umask, qui par défaut est 0022. Cela garantit que sudo n'abaisse jamais l'umask lors de l'exécution d'une commande.

Si umask est explicitement défini dans sudoers, il remplacera tout paramètre d'umask dans PAM ou login.conf. Si umask n'est pas défini dans sudoers, l'umask spécifiée par PAM ou login.conf aura la priorité. Le paramètre d'umask dans PAM n'est pas utilisé pour sudoedit, qui ne crée pas de nouvelle session PAM.

Chaînes de caractères :

cmddenial_message
S'il est défini, sudo affichera ce message lorsqu'un utilisateur se voit refuser l'accès à l'exécution de la commande spécifiée, mais est listé dans le fichier sudoers pour l'hôte. Cela peut être utilisé pour fournir des informations supplémentaires, spécifiques au site, à l'utilisateur lorsqu'une commande est refusée par la politique de sécurité. Cela ne remplace pas l'avertissement standard que l'utilisateur reçoit lorsqu'une commande est refusée.
authfail_message
Message affiché après qu'un utilisateur a échoué à s'authentifier. Le message peut inclure l'échappatoire ‘%d’ qui se développera en nombre de tentatives de mot de passe échouées. S'il est défini, il remplace le message par défaut, “%d incorrect password attempt(s)”.
badpass_message
Message affiché si un utilisateur entre un mot de passe incorrect. Le message par défaut est “Sorry, try again.” sauf si les insultes sont activées.
editor
Une liste d'éditeurs séparés par des deux-points (‘:’) utilisée par sudoedit et visudo. Pour sudoedit, cette liste est utilisée pour trouver un éditeur lorsqu'aucune des variables d'environnement SUDO_EDITOR, VISUAL ou EDITOR n'est définie sur un éditeur qui existe et est exécutable. Pour visudo, elle est utilisée comme liste blanche d'éditeurs autorisés ; visudo choisira l'éditeur qui correspond à la variable d'environnement de l'utilisateur SUDO_EDITOR, VISUAL ou EDITOR si possible, ou le premier éditeur de la liste qui existe et est exécutable si ce n'est pas le cas. Sauf s'il est invoqué en tant que sudoedit, sudo ne préserve pas les variables d'environnement SUDO_EDITOR, VISUAL ou EDITOR à moins qu'elles ne soient présentes dans la liste env_keep ou que l'option env_reset ne soit désactivée. La valeur par défaut est ~.
intercept_type
Le mécanisme sous-jacent utilisé par les options intercept et log_subcmds. Il a les valeurs possibles suivantes :
dso
Précharger un objet dynamique partagé (bibliothèque partagée) qui intercepte les fonctions de bibliothèque execve(2), execl(3), execle(3), execlp(3), execv(3), execvp(3), execvpe(3), et system(3). Une valeur de dso est incompatible avec le support RBAC SELinux de sudo.
trace
Utiliser ptrace(2) pour intercepter l'appel système execve(2). Ceci n'est pris en charge que sur les systèmes Linux où le filtrage seccomp(2) est activé. Si le fichier /proc/sys/kernel/seccomp/actions_avail est manquant ou ne contient pas l'élément “trap”, la définition de intercept_type à trace n'aura aucun effet et dso sera utilisé à la place.

La valeur par défaut est d'utiliser trace s'il est pris en charge par le système et dso s'il ne l'est pas.

iolog_dir
Le répertoire de niveau supérieur à utiliser lors de la construction du nom de chemin pour le répertoire de journalisation d'entrée/sortie. Utilisé uniquement si les options log_input ou log_output sont activées ou lorsque les balises LOG_INPUT ou LOG_OUTPUT sont présentes pour une commande. Le numéro de séquence de session, le cas échéant, est stocké dans le répertoire. La valeur par défaut est /var/log/sudo-io.

Les séquences d'échappement de pourcentage (‘%’) suivantes sont prises en charge :

%{seq}
développé en un numéro de séquence en base 36 qui augmente de manière monotone, tel que 0100A5, où toutes les deux chiffres sont utilisés pour former un nouveau répertoire, par exemple, 01/00/A5
%{user}
développé en le nom de connexion de l'utilisateur appelant
%{group}
développé en le nom du groupe réel de l'utilisateur appelant
%{runas_user}
développé en le nom de connexion de l'utilisateur sous lequel la commande sera exécutée (par exemple, root)
%{runas_group}
développé en le nom du groupe sous lequel la commande sera exécutée (par exemple, wheel)
%{hostname}
développé en le nom d'hôte local sans le nom de domaine
%{command}
développé en le nom de base de la commande exécutée

De plus, toutes les séquences d'échappement prises en charge par la fonction strftime(3) du système seront développées.

Pour inclure un caractère littéral ‘%’, la chaîne ‘%%’ doit être utilisée.

Tous les caractères séparateurs de nom de chemin (‘/’) présents dans le nom d'utilisateur, de groupe ou d'hôte seront remplacés par un tiret bas (‘_’) lors de l'expansion.

iolog_file
Le nom de chemin, relatif à iolog_dir, dans lequel stocker les journaux d'entrée/sortie lorsque les options log_input ou log_output sont activées ou lorsque les balises LOG_INPUT ou LOG_OUTPUT sont présentes pour une commande. iolog_file peut contenir des composants de répertoire. La valeur par défaut est ‘%{seq}’.

Voir l'option iolog_dir ci-dessus pour une liste des séquences d'échappement de pourcentage (‘%’) prises en charge.

En plus des séquences d'échappement, les noms de chemin se terminant par six ou plus X seront remplacés par une combinaison unique de chiffres et de lettres, similaire à la fonction mktemp(3).

Si le chemin créé en concaténant iolog_dir et i

olog_file existe déjà, le fichier journal des E/S existant sera tronqué et écrasé, sauf si iolog_file se termine par six ou plus de X.
iolog_flush
Si défini, sudo videra les données du journal des E/S sur le disque après chaque écriture au lieu de les mettre en mémoire tampon. Cela permet de consulter les journaux en temps réel pendant l'exécution du programme, mais peut réduire considérablement l'efficacité de la compression des journaux des E/S. Ce drapeau est désactivé par défaut.

Ce paramètre n'est pris en charge que par la version 1.8.20 ou supérieure.

iolog_group
Le nom du groupe à rechercher lors de la définition de l'ID de groupe sur les nouveaux fichiers et répertoires journaux des E/S. Si iolog_group n'est pas défini, l'ID du groupe principal de l'utilisateur spécifié par iolog_user est utilisé. Si ni iolog_group ni iolog_user ne sont définis, les fichiers et répertoires journaux des E/S sont créés avec l'ID de groupe 0.

Ce paramètre n'est pris en charge que par la version 1.8.19 ou supérieure.

iolog_mode
Le mode de fichier à utiliser lors de la création des fichiers journaux des E/S. Les bits de mode pour les permissions de lecture et d'écriture pour le propriétaire, le groupe ou les autres sont honorés, tout le reste est ignoré. Les permissions du fichier incluront toujours les bits de lecture et d'écriture du propriétaire, même s'ils ne sont pas présents dans le mode spécifié. Lors de la création de répertoires journaux des E/S, les bits de recherche (exécution) sont ajoutés pour correspondre aux bits de lecture et d'écriture spécifiés par iolog_mode. Par défaut, 0600 (lecture et écriture par l'utilisateur uniquement).

Ce paramètre n'est pris en charge que par la version 1.8.19 ou supérieure.

iolog_user
Le nom d'utilisateur à rechercher lors de la définition des ID utilisateur et groupe sur les nouveaux fichiers et répertoires journaux des E/S. Si iolog_group est défini, il sera utilisé à la place de l'ID du groupe principal de l'utilisateur. Par défaut, les fichiers et répertoires journaux des E/S sont créés avec les ID utilisateur et groupe 0.

Ce paramètre peut être utile lorsque les journaux des E/S sont stockés sur un partage de système de fichiers réseau (NFS). Avoir un utilisateur dédié propriétaire des fichiers journaux des E/S signifie que sudoers n'écrit pas dans les fichiers journaux en tant qu'utilisateur ID 0, ce qui n'est généralement pas autorisé par NFS.

Ce paramètre n'est pris en charge que par la version 1.8.19 ou supérieure.

lecture_status_dir
Le répertoire dans lequel sudo stocke les fichiers d'état de lecture par utilisateur. Une fois qu'un utilisateur a reçu la lecture, un fichier de longueur nulle est créé dans ce répertoire afin que sudo ne relise pas l'utilisateur. Ce répertoire ne doit pas être effacé lors du redémarrage du système. Par défaut, il s'agit de /var/db/sudo/lectured.
log_server_cabundle
Le chemin vers un fichier de bundle d'autorité de certification, au format PEM, à utiliser à la place de la base de données d'autorités de certification par défaut du système lors de l'authentification du serveur de journalisation. Par défaut, c'est la base de données d'autorités de certification par défaut du système. Ce paramètre n'a aucun effet sauf si log_servers est défini et que le serveur de journalisation distant est sécurisé avec TLS.

Ce paramètre n'est pris en charge que par la version 1.9.0 ou supérieure.

log_server_peer_cert
Le chemin vers le fichier de certificat du client sudo, au format PEM. Ce paramètre est requis lorsque le serveur de journalisation distant est sécurisé avec TLS et que la validation du certificat client est activée. Pour sudo_logsrvd, la validation du certificat client est contrôlée par l'option tls_checkpeer, qui est désactivée par défaut (false).

Ce paramètre n'est pris en charge que par la version 1.9.0 ou supérieure.

log_server_peer_key
Le chemin vers le fichier de clé privée du client sudo, au format PEM. Ce paramètre est requis lorsque le serveur de journalisation distant est sécurisé avec TLS et que la validation du certificat client est activée. Pour sudo_logsrvd, la validation du certificat client est contrôlée par le drapeau tls_checkpeer, qui est désactivé par défaut (false).

Ce paramètre n'est pris en charge que par la version 1.9.0 ou supérieure.

mailsub
Objet de l'e-mail envoyé à l'utilisateur mailto. Le code d'échappement ‘%h’ sera remplacé par le nom d'hôte de la machine. Par défaut, “*** Informations de sécurité pour %h ***”.
noexec_file
Depuis la version 1.8.1 de sudo, cette option n'est plus prise en charge. Le chemin du fichier noexec doit maintenant être défini dans le fichier sudo.conf(5).
pam_askpass_service
Sur les systèmes qui utilisent PAM pour l'authentification, c'est le nom du service utilisé lorsque l'option -A est spécifiée. La valeur par défaut est soit ‘sudo’ soit ‘sudo’, selon que l'option -i est également spécifiée ou non. Voir la description de pam_service pour plus d'informations.

Ce paramètre n'est pris en charge que par la version 1.9.9 ou supérieure.

pam_login_service
Sur les systèmes qui utilisent PAM pour l'authentification, c'est le nom du service utilisé lorsque l'option -i est spécifiée. La valeur par défaut est ‘sudo’. Voir la description de pam_service pour plus d'informations.

Ce paramètre n'est pris en charge que par la version 1.8.8 ou supérieure.

pam_service
Sur les systèmes qui utilisent PAM pour l'authentification, le nom du service spécifie la politique PAM à appliquer. Cela correspond généralement à une entrée dans le fichier pam.conf ou un fichier dans le répertoire /etc/pam.d. La valeur par défaut est ‘sudo’.

Ce paramètre n'est pris en charge que par la version 1.8.8 ou supérieure.

passprompt
L'invite par défaut à utiliser lors de la demande d'un mot de passe ; peut être remplacée par l'option -p ou la variable d'environnement SUDO_PROMPT. Les séquences d'échappement suivantes utilisant le signe dollar (‘%’) sont prises en charge :
%H
développé en nom d'hôte local, y compris le nom de domaine (seulement si le nom d'hôte de la machine est entièrement qualifié ou si l'option fqdn est définie)
%h
développé en nom d'hôte local sans le nom de domaine
%p
développé en nom d'utilisateur dont le mot de passe est demandé (respecte les indicateurs rootpw, targetpw et runaspw dans sudoers)
%U
développé en nom de connexion de l'utilisateur sous lequel la commande sera exécutée (par défaut root)
%u
développé en nom de connexion de l'utilisateur appelant
%%
deux caractères ‘%’ consécutifs sont réduits en un seul caractère ‘%’

Sur les systèmes qui utilisent PAM pour l'authentification, passprompt ne sera utilisé que si l'invite fournie par le module PAM correspond à la chaîne “Password: ” ou “username's Password: ”. Cela garantit que le paramètre passprompt n'interfère pas avec l'authentification de type défi-réponse. L'indicateur passprompt_override peut être utilisé pour modifier ce comportement.

La valeur par défaut est ‘[sudo] password for %p: ’.

runas_default
L'utilisateur par défaut pour exécuter les commandes si l'option -u n'est pas spécifiée sur la ligne de commande. Par défaut, il s'agit de root.
sudoers_locale
Locale à utiliser lors de l'analyse du fichier sudoers, de la journalisation des commandes et de l'envoi d'e-mails. Le changement de locale peut affecter la façon dont sudoers est interprété. Par défaut, ‘C’.
timestamp_type
sudoers utilise des fichiers d'horodatage par utilisateur pour la mise en cache des identifiants. L'option timestamp_type peut être utilisée pour spécifier le type d'enregistrement d'horodatage utilisé. Elle a les valeurs possibles suivantes :
global
Un seul enregistrement d'horodatage est utilisé pour toutes les sessions de connexion d'un utilisateur, quel que soit le terminal ou l'ID du processus parent. Un enregistrement supplémentaire est utilisé pour sérialiser les invites de mot de passe lorsque sudo est utilisé plusieurs fois dans un pipeline, mais cela n'affecte pas l'authentification.
ppid
Un seul enregistrement d'horodatage est utilisé pour tous les processus ayant le même ID de processus parent (généralement le shell). Les commandes exécutées à partir du même shell (ou d'un autre processus parent commun) ne nécessiteront pas de mot de passe pendant timestamp_timeout minutes (5 par défaut). Les commandes exécutées via sudo avec un ID de processus parent différent, par exemple à partir d'un script shell, seront authentifiées séparément.
tty
Un enregistrement d'horodatage est utilisé pour chaque terminal, ce qui signifie que les sessions de connexion d'un utilisateur sont authentifiées séparément. Si aucun terminal n'est présent, le comportement est le même que pour ppid. Les commandes exécutées à partir du même terminal ne nécessiteront pas de mot de passe pendant timestamp_timeout minutes (5 par défaut).
kernel
L'horodatage est stocké dans le noyau en tant qu'attribut du périphérique terminal. S'il n'y a pas de terminal, le comportement est le même que pour ppid. Les valeurs négatives de timestamp_timeout ne sont pas prises en charge et les valeurs positives sont limitées à un maximum de 60 minutes. Ceci n'est actuellement pris en charge que sur OpenBSD.

La valeur par défaut est tty.

Ce paramètre n'est pris en charge que par la version 1.8.21 ou supérieure.

timestampdir
Le répertoire dans lequel sudo stocke ses fichiers d'horodatage. Ce répertoire doit être effacé lors du redémarrage du système. Par défaut, il s'agit de /run/sudo/ts.
timestampowner
Le propriétaire du répertoire d'état de lecture, du répertoire d'horodatage et de tous les fichiers qui y sont stockés. Par défaut, il s'agit de root.

Chaînes pouvant être utilisées dans un contexte booléen :

admin_flag
L'option admin_flag spécifie le chemin d'un fichier qui est créé la première fois qu'un utilisateur est membre des groupes sudo ou admin exécute sudo. Disponible uniquement si sudo est configuré avec l'option --enable-admin-flag. La valeur par défaut est ~/.sudo_as_admin_successful.
env_file
L'option env_file spécifie le chemin d'accès complet à un fichier contenant les variables à définir dans l'environnement du programme en cours d'exécution. Les entrées de ce fichier doivent être soit de la forme ‘VARIABLE=valeur’ soit ‘export VARIABLE=valeur’. La valeur peut éventuellement être entourée de guillemets simples ou doubles. Les variables de ce fichier ne sont ajoutées que si la variable n'existe pas déjà dans l'environnement. Ce fichier est considéré comme faisant partie de la politique de sécurité ; son contenu n'est pas soumis aux autres restrictions d'environnement de sudo telles que env_keep et env_check.
exempt_group
Les utilisateurs appartenant à ce groupe sont exemptés des exigences de mot de passe et de PATH. Le nom du groupe spécifié ne doit pas inclure de préfixe ‘%’. Ce n'est pas défini par défaut.
fdexec
Détermine si sudo exécutera une commande par son chemin d'accès ou par un descripteur de fichier ouvert. Il peut prendre les valeurs suivantes :
always
Toujours exécuter par descripteur de fichier.
never
Ne jamais exécuter par descripteur de fichier.
digest_only
Exécuter par descripteur de fichier uniquement si la commande a un résumé associé dans le fichier sudoers.

La valeur par défaut est digest_only. Cela évite une condition de concurrence « moment de la vérification versus moment de l'utilisation » lorsque la commande est située dans un répertoire accessible en écriture par l'utilisateur appelant.

fdexec modifiera le premier élément du vecteur d'arguments pour les scripts ($0 dans le shell) en raison de la manière dont le noyau exécute les interpréteurs de scripts. Au lieu d'être un chemin d'accès normal, il fera référence à un descripteur de fichier. Par exemple, /dev/fd/4 sur Solaris et /proc/self/fd/4 sur Linux. Une solution de contournement consiste à utiliser la variable d'environnement SUDO_COMMAND à la place.

Le réglage fdexec n'est utilisé que lorsque la commande est trouvée par son nom de chemin. Il n'a aucun effet si la commande est trouvée par l'alias intégré ALL.

Ce réglage n'est pris en charge que par la version 1.8.20 ou supérieure. Si le système d'exploitation ne prend pas en charge l'appel système fexecve(2), ce réglage n'a aucun effet.

group_plugin
Une chaîne contenant un plugin de groupe sudoers avec des arguments optionnels. La chaîne doit se composer du chemin du plugin, soit qualifié complet, soit relatif au répertoire /usr/lib/sudo, suivi des éventuels arguments de configuration requis par le plugin. Ces arguments (s'il y en a) seront passés à la fonction d'initialisation du plugin. S'il y a des arguments, la chaîne doit être entourée de guillemets doubles ("").

Sur les systèmes 64 bits, si le plugin est présent mais ne peut pas être chargé, sudoers recherchera une version 64 bits et, si elle existe, la chargera en secours. Les règles exactes varient selon le système. Sur Solaris, si le plugin est stocké dans un répertoire se terminant par “lib”, sudoers créera un chemin de secours en ajoutant “/64” au nom du répertoire ; /usr/lib/group_plugin.so devient /usr/lib/64/group_plugin.so. Sur Linux, un répertoire se terminant par “lib” sera transformé en “lib64” comme chemin de secours ; /usr/lib/group_plugin.so devient /usr/lib64/group_plugin.so. Sur tous les autres systèmes, le chemin de secours est généré en ajoutant un “64” avant l'extension du fichier ; group_plugin.so devient group_plugin64.so.

Sur les systèmes AIX, le plugin peut être soit un objet partagé se terminant par ‘.so’, soit un fichier archive contenant un objet partagé se terminant par ‘.a’ avec le nom de l'objet partagé à la fin entre parenthèses.

Pour plus d'informations, voir PLUGINS FOURNISSEURS DE GROUPES.

lecture
Cette option contrôle quand une courte conférence sera affichée avec l'invite de mot de passe. Elle peut prendre les valeurs suivantes :
always
Toujours faire une conférence à l'utilisateur.
never
Ne jamais faire de conférence à l'utilisateur.
once
Ne faire une conférence à l'utilisateur que la première fois qu'il exécute sudo.

Si aucune valeur n'est spécifiée, la valeur once est implicite. La négation de l'option donne la valeur never. La valeur par défaut est once.

lecture_file
Chemin d'accès à un fichier contenant une conférence sudo alternative qui sera utilisée à la place de la conférence standard si le fichier nommé existe. Par défaut, sudo utilise une conférence intégrée.
listpw
Cette option contrôle quand un mot de passe sera requis lorsqu'un utilisateur exécute sudo avec l'option -l. Elle peut prendre les valeurs suivantes :
all
Toutes les entrées du fichier sudoers de l'utilisateur pour l'hôte actuel doivent avoir le drapeau NOPASSWD défini pour éviter de saisir un mot de passe.
always
L'utilisateur doit toujours entrer un mot de passe pour utiliser l'option -l.
any
Au moins une des entrées du fichier sudoers de l'utilisateur pour l'hôte actuel doit avoir le drapeau NOPASSWD défini pour éviter de saisir un mot de passe.
never
L'utilisateur n'a jamais besoin d'entrer un mot de passe pour utiliser l'option -l.

Si aucune valeur n'est spécifiée, la valeur any est implicite. La négation de l'option donne la valeur never. La valeur par défaut est any.

log_format
Le format du journal d'événements. Les formats de journal pris en charge sont :
json
Actuellement, c'est un alias pour json_pretty. Dans une future version de sudo, json sera équivalent à json_compact. Les entrées du journal JSON contiennent les détails complets de l'utilisateur ainsi que l'environnement d'exécution si la commande a été autorisée.
json_compact
Enregistre les événements au format JSON « compact » (minifié). Chaque événement est écrit comme un objet JSON distinct sur une seule ligne sans espaces blancs superflus. En raison des limitations du protocole, les événements JSON envoyés via syslog peuvent être tronqués.
json_pretty
Enregistre les événements au format JSON « joli ». Lors de l'enregistrement dans un fichier, l'ensemble du fichier est traité comme un seul objet JSON composé de plusieurs événements, chaque événement s'étendant sur plusieurs lignes. Lors de l'enregistrement via syslog, il n'y a pas de différence entre les formats json_pretty et json_compact.
sudo
Enregistre les événements dans le format traditionnel de sudo, voir JOURNAL DES ÉVÉNEMENTS pour plus de détails.

Ce réglage affecte les journaux envoyés via syslog(3) ainsi que le fichier spécifié par le réglage logfile, le cas échéant. La valeur par défaut est sudo.

logfile
Chemin d'accès au fichier journal de sudo (pas le fichier journal syslog). La définition d'un chemin active la journalisation dans un fichier ; la négation de cette option la désactive. Par défaut, sudo journalise via syslog.
mailerflags
Indicateurs à utiliser lors de l'appel du programme de messagerie. Par défaut : -t.
mailerpath
Chemin d'accès au programme de messagerie utilisé pour envoyer des e-mails d'avertissement (nier pour empêcher sudo d'envoyer des e-mails). Par défaut, le chemin de sendmail trouvé lors de la configuration.
mailfrom
Adresse à utiliser pour l'adresse « de » lors de l'envoi d'e-mails d'avertissement et d'erreur. L'adresse doit être entourée de guillemets doubles ("") pour éviter que sudo n'interprète le signe ‘@’. Par défaut, c'est le nom de l'utilisateur exécutant sudo.
mailto
Adresse à laquelle envoyer les e-mails d'avertissement et d'erreur (nier pour empêcher sudo d'envoyer des e-mails). L'adresse doit être entourée de guillemets doubles ("") pour éviter que sudo n'interprète le signe ‘@’. Par défaut, c'est root.
rlimit_as
La taille maximale à laquelle l'espace d'adressage du processus peut croître (en octets), si pris en charge par le système d'exploitation. Voir Limites de ressources pour plus d'informations.
rlimit_core
La taille maximale des fichiers de vidage de cœur qui peuvent être créés (en octets). Voir Limites de ressources pour plus d'informations. Par défaut, 0 (aucun vidage de cœur créé).
rlimit_cpu
La durée maximale du temps CPU que le processus peut utiliser (en secondes). Voir Limites de ressources pour plus d'informations.
rlimit_data
La taille maximale du segment de données pour le processus (en octets). Voir Limites de ressources pour plus d'informations.
rlimit_fsize
La taille maximale de fichier que le processus peut créer (en octets). Voir Limites de ressources pour plus d'informations.
rlimit_locks
Le nombre maximal de verrous que le processus peut établir, si pris en charge par le système d'exploitation. Voir Limites de ressources pour plus d'informations.
rlimit_memlock
La taille maximale que le processus peut verrouiller en mémoire (en octets), si pris en charge par le système d'exploitation. Voir Reso

Pour plus d'informations, reportez-vous à la section Limites de ressources.

rlimit_nofile
Nombre maximal de fichiers qu'un processus peut avoir ouverts. Pour plus d'informations, reportez-vous à la section Limites de ressources.
rlimit_nproc
Nombre maximal de processus qu'un utilisateur peut exécuter simultanément. Pour plus d'informations, reportez-vous à la section Limites de ressources.
rlimit_rss
Taille maximale à laquelle le jeu de résident d'un processus peut croître (en octets). Pour plus d'informations, reportez-vous à la section Limites de ressources.
rlimit_stack
Taille maximale à laquelle la pile d'un processus peut croître (en octets). Pour plus d'informations, reportez-vous à la section Limites de ressources.
restricted_env_file
L'option restricted_env_file spécifie le chemin complet d'un fichier contenant les variables à définir dans l'environnement du programme exécuté. Les entrées de ce fichier doivent être des assignations sous la forme « VARIABLE=valeur » ou « export VARIABLE=valeur », séparées par des sauts de ligne. La valeur peut éventuellement être entourée de guillemets simples ou doubles. La substitution de variables de style shell n'est pas prise en charge. Les lignes vides et les commentaires commençant par un dièse (« # ») sont ignorés. Les variables de ce fichier ne sont ajoutées que si la variable n'existe pas déjà dans l'environnement. Contrairement à env_file, le contenu du fichier n'est pas considéré comme fiable et est traité de manière similaire à l'environnement de l'utilisateur appelant. Si env_reset est activé, les variables du fichier ne seront ajoutées que si elles correspondent à la liste env_check ou env_keep. Si env_reset est désactivé, les variables du fichier sont ajoutées tant qu'elles ne correspondent pas à la liste env_delete. Dans les deux cas, le contenu de restricted_env_file est traité avant le contenu de env_file.
runchroot
Si défini, sudo utilisera cette valeur pour le répertoire racine lors de l'exécution d'une commande. La valeur spéciale « * » permettra à l'utilisateur de spécifier le répertoire racine via l'option -R de sudo. Voir la section Spécification chroot pour plus de détails.

Il n'est possible d'utiliser runchroot comme paramètre par défaut spécifique à une commande que si la commande existe avec le même chemin à l'intérieur et à l'extérieur de la prison chroot. Cette restriction ne s'applique pas aux paramètres par défaut globaux, d'hôte ou d'utilisateur, ni à une Spécification de commande qui inclut une Spécification chroot.

Ce paramètre n'est pris en charge que par la version 1.9.3 ou supérieure.

La prise en charge de la définition du répertoire racine est obsolète et sera supprimée dans une future version de sudo.

runcwd
Si défini, sudo utilisera cette valeur pour le répertoire de travail lors de l'exécution d'une commande. La valeur spéciale « * » permettra à l'utilisateur de spécifier le répertoire de travail via l'option -D de sudo. Voir la section Spécification chdir pour plus de détails.

Ce paramètre n'est pris en charge que par la version 1.9.3 ou supérieure.

secure_path
S'il est défini, sudo utilisera cette valeur à la place de la variable d'environnement PATH de l'utilisateur. Il existe deux cas d'utilisation principaux pour secure_path :
  1. Pour permettre à sudo de trouver les commandes d'administrateur système situées dans des répertoires qui pourraient ne pas se trouver dans le chemin par défaut de l'utilisateur, comme /usr/sbin.
  2. Pour aider à protéger les scripts et les programmes qui exécutent d'autres commandes sans d'abord définir PATH sur une valeur sûre. Sinon, un utilisateur avec des privilèges limités pourrait être en mesure d'exécuter des commandes arbitraires en manipulant PATH si la commande exécutée appelle d'autres commandes sans utiliser de nom de chemin complet.

Les utilisateurs du groupe spécifié par l'option exempt_group ne sont pas affectés par secure_path. Cette option est désactivée par défaut.

syslog
Installation syslog si syslog est utilisée pour la journalisation (négativer pour désactiver la journalisation syslog). Par défaut : auth.

Les installations syslog suivantes sont prises en charge : authpriv (si votre système d'exploitation le prend en charge), auth, daemon, user, local0, local1, local2, local3, local4, local5, local6, et local7.

syslog_badpri
Priorité syslog à utiliser lorsque l'utilisateur n'est pas autorisé à exécuter une commande ou lorsque l'authentification échoue. Par défaut : alert.

Les priorités syslog suivantes sont prises en charge : alert, crit, debug, emerg, err, info, notice, warning, et none. Négativer l'option ou la définir à la valeur none désactivera la journalisation des commandes échouées.

syslog_goodpri
Priorité syslog à utiliser lorsque l'utilisateur est autorisé à exécuter une commande et que l'authentification réussit. Par défaut : notice.

Voir syslog_badpri pour la liste des priorités syslog prises en charge. Négativer l'option ou la définir à la valeur none désactivera la journalisation des commandes réussies.

verifypw
Cette option contrôle quand un mot de passe est requis lorsque l'utilisateur exécute sudo avec l'option -v. Elle peut prendre les valeurs suivantes :
all
Toutes les entrées du fichier sudoers de l'utilisateur pour l'hôte actuel doivent avoir le drapeau NOPASSWD défini pour éviter de saisir un mot de passe.
always
L'utilisateur doit toujours saisir un mot de passe pour utiliser l'option -v.
any
Au moins une des entrées du fichier sudoers de l'utilisateur pour l'hôte actuel doit avoir le drapeau NOPASSWD défini pour éviter de saisir un mot de passe.
never
L'utilisateur n'a jamais besoin de saisir de mot de passe pour utiliser l'option -v.

Si aucune valeur n'est spécifiée, la valeur all est implicite. Négativer l'option a pour résultat l'utilisation de la valeur never. La valeur par défaut est all.

Listes pouvant être utilisées dans un contexte booléen :

env_check
Variables d'environnement à supprimer de l'environnement de l'utilisateur, sauf si elles sont considérées comme « sûres ». Pour toutes les variables sauf TZ, « sûr » signifie que la valeur de la variable ne contient aucun caractère « % » ou « / ». Cela peut être utilisé pour se prémunir contre les vulnérabilités de type format printf dans des programmes mal écrits. La variable TZ est considérée comme non sûre si l'une des conditions suivantes est remplie :
  • Elle consiste en un nom de chemin complet, éventuellement préfixé par deux-points (« : »), qui ne correspond pas à l'emplacement du répertoire zoneinfo.
  • Elle contient un élément de chemin ...
  • Elle contient des espaces blancs ou des caractères non imprimables.
  • Elle est plus longue que la valeur de PATH_MAX.

L'argument peut être une liste séparée par des espaces, entre guillemets doubles, ou une valeur unique sans guillemets. La liste peut être remplacée, ajoutée, supprimée ou désactivée à l'aide des opérateurs « = », « += », « -= » et « ! » respectivement. Que l'option env_reset soit activée ou désactivée, les variables spécifiées par env_check seront préservées dans l'environnement si elles passent les vérifications susmentionnées. La liste globale des variables d'environnement à vérifier est affichée lorsque sudo est exécuté par root avec l'option -V.

env_delete
Variables d'environnement à supprimer de l'environnement de l'utilisateur lorsque l'option env_reset n'est pas effective. L'argument peut être une liste séparée par des espaces, entre guillemets doubles, ou une valeur unique sans guillemets. La liste peut être remplacée, ajoutée, supprimée ou désactivée à l'aide des opérateurs « = », « += », « -= » et « ! » respectivement. La liste globale des variables d'environnement à supprimer est affichée lorsque sudo est exécuté par root avec l'option -V. De nombreux systèmes d'exploitation supprimeront les variables potentiellement dangereuses de l'environnement de tout processus set-user-ID (tel que sudo).
env_keep
Variables d'environnement à préserver dans l'environnement de l'utilisateur lorsque l'option env_reset est effective. Cela permet un contrôle granulaire de l'environnement spawned parsudo. L'argument peut être une liste séparée par des espaces entre guillemets doubles ou une valeur unique sans guillemets doubles. La liste peut être remplacée, ajoutée, supprimée ou désactivée en utilisant respectivement les opérateurs ‘=’, ‘+=’, ‘-=’ et ‘!’. La liste globale des variables à conserver est affichée lorsque sudo est exécuté par root avec l'option -V.

La conservation de la variable d'environnement HOME a des implications de sécurité car de nombreux programmes l'utilisent lors de la recherche de fichiers de configuration ou de données. L'ajout de HOME à env_keep peut permettre à un utilisateur d'exécuter des commandes sans restriction via sudo et est fortement déconseillé. Les utilisateurs souhaitant modifier des fichiers avec sudo doivent exécuter sudoedit (ou sudo -e) pour obtenir leur configuration d'éditeur habituelle au lieu d'invoquer l'éditeur directement.

log_servers
Une liste d'un ou plusieurs serveurs à utiliser pour le stockage distant des journaux d'événements et d'E/S, séparés par des espaces blancs. Les serveurs de journaux doivent exécuter sudo_logsrvd ou un autre service qui implémente le protocole décrit par sudo_logsrv.proto(5).

Les adresses des serveurs doivent être de la forme “hôte[:port][(tls)]”. La partie hôte peut être un nom d'hôte, une adresse IPv4 ou une adresse IPv6 entre crochets.

Si le drapeau facultatif tls est présent, la connexion sera sécurisée avec la couche de transport (TLS) version 1.2 ou 1.3. Les versions de TLS antérieures à 1.2 ne sont pas prises en charge.

Si un port est spécifié, il peut s'agir d'un numéro de port ou d'un nom de service bien connu tel que défini par la base de données des noms de services du système. Si aucun port n'est spécifié, le port 30343 sera utilisé pour les connexions en texte brut et le port 30344 sera utilisé pour les connexions TLS.

Lorsque log_servers est défini, les données du journal d'événements seront enregistrées localement (voir les paramètres syslog et log_file) ainsi qu'à distance, mais les données du journal d'E/S ne seront enregistrées qu'à distance. Si plusieurs hôtes sont spécifiés, ils seront tentés dans l'ordre inverse. Si aucun serveur de journal n'est disponible, l'utilisateur ne pourra pas exécuter de commande à moins que le drapeau ignore_iolog_errors (journalisation des E/S activée) ou le drapeau ignore_log_errors (journalisation des E/S désactivée) ne soit défini. De même, si la connexion au serveur de journal est interrompue pendant l'exécution de sudo, la commande sera terminée à moins que le drapeau ignore_iolog_errors (journalisation des E/S activée) ou le drapeau ignore_log_errors (journalisation des E/S désactivée) ne soit défini.

Ce paramètre n'est pris en charge que par la version 1.9.0 ou ultérieure.

passprompt_regex
Une liste d'expressions régulières étendues POSIX utilisées pour faire correspondre les invites de mot de passe dans la sortie du terminal. Par extension, si l'expression régulière commence par “(?i)”, elle sera mise en correspondance de manière insensible à la casse. Chaque expression régulière est limitée à 1024 caractères. Cette option n'est utilisée que lorsque log_passwords a été désactivé. La valeur par défaut est “[Pp]assword[: ]*”

Ce paramètre n'est pris en charge que par la version 1.9.10 ou ultérieure.

PLUGINS FOURNISSEURS DE GROUPES

Le plugin sudoers prend en charge sa propre interface de plugin pour permettre les recherches de groupes non-Unix qui peuvent interroger une source de groupe autre que la base de données de groupes Unix standard. Cela peut être utilisé pour implémenter la prise en charge de la syntaxe nonunix_group décrite précédemment.

Les plugins fournisseurs de groupes sont spécifiés via le paramètre group_plugin. L'argument de group_plugin doit se composer du chemin du plugin, soit entièrement qualifié, soit relatif au répertoire /usr/lib/sudo, suivi des options de configuration dont le plugin a besoin. Ces options (si elles sont spécifiées) seront passées à la fonction d'initialisation du plugin. Si des options sont présentes, la chaîne doit être entourée de guillemets doubles ("").

Les plugins fournisseurs de groupes suivants sont installés par défaut :

group_file
Le plugin group_file prend en charge un fichier de groupe alternatif qui utilise la même syntaxe que le fichier /etc/group. Le chemin du fichier de groupe doit être spécifié comme une option du plugin. Par exemple, si le fichier de groupe à utiliser est /etc/sudo-group : 
Defaults group_plugin="group_file.so /etc/sudo-group"
system_group
Le plugin system_group prend en charge les recherches de groupes via les fonctions standard de la bibliothèque C getgrnam(3) et getgrid(3). Ce plugin peut être utilisé dans les cas où l'utilisateur appartient à des groupes qui ne sont pas présents dans le vecteur de groupes supplémentaires de l'utilisateur. Ce plugin ne prend aucune option : 
Defaults group_plugin=system_group.so

L'API du plugin fournisseur de groupes est décrite en détail dans sudo_plugin(5).

JOURNALISATION DES ÉVÉNEMENTS

sudoers peut enregistrer les événements au format JSON ou au format sudo. Cette section décrit le format de journalisation sudo. Selon la configuration de sudoers, sudoers peut enregistrer les événements via syslog(3), dans un fichier journal local, ou les deux. Le format du journal est presque identique dans les deux cas. Tous les caractères de contrôle présents dans les données du journal sont formatés en octal avec un caractère ‘#’ en préfixe. Par exemple, une tabulation horizontale est stockée sous forme de ‘#011’ et un retour chariot intégré est stocké sous forme de ‘#015’. De plus, les espaces dans le chemin de commande sont stockés sous forme de ‘#040’. Les arguments de ligne de commande contenant des espaces sont entourés d'apostrophes (''). Cela permet de distinguer plusieurs arguments de ligne de commande d'un seul argument contenant des espaces. Les apostrophes littérales et les caractères antislash (‘\’) dans les arguments de ligne de commande sont échappés avec un antislash.

Entrées de journal de commandes acceptées

Les commandes exécutées par sudo sont enregistrées en utilisant le format suivant (divisé en plusieurs lignes pour plus de lisibilité) :

date hostname progname: username : TTY=ttyname ; CHROOT=chroot ; \
    PWD=cwd ; USER=runasuser ; GROUP=runasgroup ; TSID=logid ; \
    ENV=env_vars COMMAND=command

Où les champs sont les suivants :

date
La date à laquelle la commande a été exécutée. Généralement, elle est au format “MMM, DD, HH:MM:SS”. En cas de journalisation via syslog(3), le format de date réel est contrôlé par le démon syslog. En cas de journalisation dans un fichier et si l'option log_year est activée, la date inclura également l'année.
hostname
Le nom de l'hôte sur lequel sudo a été exécuté. Ce champ n'est présent que lors de la journalisation via syslog(3).
progname
Le nom du programme, généralement sudo ou sudoedit. Ce champ n'est présent que lors de la journalisation via syslog(3).
username
Le nom de connexion de l'utilisateur qui a exécuté sudo.
ttyname
Le nom court du terminal (par exemple, “console”, “tty01”, ou “pts/0”) sur lequel sudo a été exécuté, ou “unknown” s'il n'y avait pas de terminal.
chroot
Le répertoire racine dans lequel la commande a été exécutée, si un répertoire a été spécifié.
cwd
Le répertoire de travail actuel dans lequel sudo a été exécuté.
runasuser
L'utilisateur sous lequel la commande a été exécutée.
runasgroup
Le groupe sous lequel la commande a été exécutée si un groupe a été spécifié sur la ligne de commande.
logid
Un identifiant de journalisation d'E/S qui peut être utilisé pour rejouer la sortie de la commande. Ceci n'est présent que lorsque l'option log_input ou log_output est activée.
env_vars
Une liste des variables d'environnement spécifiées sur la ligne de commande, si elles sont spécifiées.
command
La commande réelle qui a été exécutée, y compris tous les arguments de ligne de commande.

Les messages sont enregistrés en utilisant la locale spécifiée par sudoers_locale, qui par défaut est la locale ‘C’.

Entrées de journal de commandes refusées

Si l'utilisateur n'est pas autorisé à exécuter la commande, la raison du refus suit le nom d'utilisateur. Les raisons possibles incluent :

user NOT in sudoers
L'utilisateur n'est pas listé dans le fichier sudoers.
user NOT authorized on host
L'utilisateur est listé dans le fichier sudoers mais n'est pas autorisé à exécuter de commandes sur l'hôte.
command not allowed
L'utilisateur est listé dans le fichier sudoers pour l'hôte mais il n'est pas autorisé à exécuter la commande spécifiée.
3 incorrect password attempts
L'utilisateur n'a pas réussi à saisir son mot de passe après 3 tentatives. Le nombre réel de tentatives variera en fonction du nombre de tentatives échouées et de la valeur de l'option passwd_tries.
a password is required
L'option -n a été spécifiée mais un mot de passe était requis.
sorry, you are not allowed to set the following environment variables
L'utilisateur a spécifié des variables d'environnement sur la ligne de commande qui n'étaient pas autorisées par sudoers.

Entrées du journal d'erreurs

En cas d'erreur, sudoers enregistrera un message et, dans la plupart des cas, enverra un message à l'administrateur par courrier électronique. Les erreurs possibles incluent :

erreur d'analyse dans /etc/sudoers près de la ligne N
sudoers a rencontré une erreur lors de l'analyse du fichier spécifié. Dans certains cas, l'erreur réelle peut se situer une ligne au-dessus ou en dessous du numéro de ligne indiqué, en fonction du type d'erreur.
problème avec les entrées par défaut
Le fichier sudoers contient un ou plusieurs paramètres Defaults inconnus. Cela n'empêche pas sudo de fonctionner, mais le fichier sudoers doit être vérifié à l'aide de visudo.
propriétaire du tampon temporel (nom d'utilisateur) : Utilisateur introuvable
Le propriétaire du répertoire de tampons temporels, tel que spécifié par le paramètre timestampowner, n'a pas pu être trouvé dans la base de données des mots de passe.
impossible d'ouvrir/lire /etc/sudoers
Le fichier sudoers n'a pas pu être ouvert en lecture. Cela peut se produire lorsque le fichier sudoers se trouve sur un système de fichiers distant qui mappe l'ID utilisateur 0 à une valeur différente. Normalement, sudoers tente d'ouvrir le fichier sudoers en utilisant les permissions de groupe pour éviter ce problème. Envisagez de changer la propriété de /etc/sudoers ou d'ajouter un argument tel que « sudoers_uid=N » (où « N » est l'ID utilisateur qui possède le fichier sudoers) à la fin de la ligne sudoers Plugin dans le fichier sudo.conf(5).
impossible d'ouvrir /etc/sudoers
Le fichier /etc/sudoers est manquant.
/etc/sudoers n'est pas un fichier régulier
Le fichier /etc/sudoers existe mais n'est pas un fichier régulier ni un lien symbolique.
/etc/sudoers appartient à uid N, devrait être 0
Le fichier sudoers a le mauvais propriétaire. Si vous souhaitez changer le propriétaire du fichier sudoers, ajoutez « sudoers_uid=N » (où « N » est l'ID utilisateur qui possède le fichier sudoers) à la ligne sudoers Plugin dans le fichier sudo.conf(5).
/etc/sudoers est accessible en écriture par tous
Les permissions sur le fichier sudoers permettent à tous les utilisateurs d'y écrire. Le fichier sudoers ne doit pas être accessible en écriture par tous ; le mode de fichier par défaut est 0440 (lisible par le propriétaire et le groupe, inscriptible par personne). Le mode par défaut peut être modifié via l'option « sudoers_mode » de la ligne sudoers Plugin dans le fichier sudo.conf(5).
/etc/sudoers appartient à gid N, devrait être 1
Le fichier sudoers a la mauvaise propriété de groupe. Si vous souhaitez changer la propriété de groupe du fichier sudoers, ajoutez « sudoers_gid=N » (où « N » est l'ID de groupe qui possède le fichier sudoers) à la ligne sudoers Plugin dans le fichier sudo.conf(5).
impossible d'ouvrir /run/sudo/ts/user-ID
sudoers n'a pas pu lire ou créer le fichier de tampon temporel de l'utilisateur. Cela peut se produire lorsque timestampowner est défini sur un utilisateur autre que root et que le mode de /run/sudo n'est pas accessible en parcours par le groupe ou par les autres. Le mode par défaut pour /run/sudo est 0711.
impossible d'écrire dans /run/sudo/ts/user-ID
sudoers n'a pas pu écrire dans le fichier de tampon temporel de l'utilisateur.
/run/sudo/ts appartient à uid X, devrait être Y
Le répertoire de tampons temporels appartient à un utilisateur autre que timestampowner. Cela peut se produire lorsque la valeur de timestampowner a été modifiée. sudoers ignorera le répertoire de tampons temporels jusqu'à ce que le propriétaire soit corrigé.
/run/sudo/ts est accessible en écriture par le groupe
Le répertoire de tampons temporels est accessible en écriture par le groupe ; il ne devrait être accessible en écriture que par timestampowner. Le mode par défaut pour le répertoire de tampons temporels est 0700. sudoers ignorera le répertoire de tampons temporels jusqu'à ce que le mode soit corrigé.

Notes sur la journalisation via syslog

Par défaut, sudoers journalise les messages via syslog(3). Les champs date, hostname et progname sont ajoutés par la fonction syslog(3) du système, et non par sudoers lui-même. Par conséquent, leur format peut varier sur les différents systèmes.

La taille maximale des messages syslog varie d'un système à l'autre. Le paramètre syslog_maxlen peut être utilisé pour modifier la taille maximale des messages syslog par rapport à la valeur par défaut de 980 octets. Pour plus d'informations, consultez la description de syslog_maxlen.

Notes sur la journalisation dans un fichier

Si l'option logfile est définie, sudoers journalisera dans un fichier local, tel que /var/log/sudo. Lors de la journalisation dans un fichier, sudoers utilise un format similaire à syslog(3), avec quelques différences importantes :

  1. Le champ progname n'est pas présent.
  2. Le champ hostname n'est enregistré que si l'option log_host est activée.
  3. La date n'inclut pas l'année sauf si l'option log_year est activée.
  4. Les lignes plus longues que loglinelen caractères (80 par défaut) sont coupées et continuées sur la ligne suivante avec une indentation de quatre caractères. Cela rend les entrées plus faciles à lire pour un être humain, mais rend plus difficile l'utilisation de grep(1) sur les fichiers journaux. Si l'option loglinelen est définie sur 0 (ou niée avec un « ! »), la coupure de ligne sera désactivée.

JOURNALISATION DES E/S

Lorsque la journalisation des E/S est activée, sudo exécute la commande dans un pseudo-terminal, enregistrant les entrées et/ou sorties utilisateur, en fonction des indicateurs sudoers activés. Il existe cinq types distincts d'E/S pouvant être journalisés, chacun avec un indicateur sudoers correspondant.

Type Indicateur Description
entrée du terminal log_ttyin frappes clavier saisies par l'utilisateur
sortie du terminal log_ttyout sortie de commande affichée à l'écran
entrée standard log_stdin entrée provenant d'un tube ou d'un fichier
sortie standard log_stdout sortie vers un tube ou un fichier
erreur standard log_stderr sortie vers un tube ou un fichier

En plus des indicateurs décrits ci-dessus, l'indicateur log_input et l'ensemble de balises de commande LOG_INPUT définissent à la fois log_ttyin et log_stdin. L'indicateur log_output et l'ensemble de balises de commande LOG_OUTPUT définissent log_ttyout, log_stdout et log_stderr.

Pour capturer l'entrée et la sortie du terminal, sudo exécute la commande dans un pseudo-terminal, enregistrant l'entrée et la sortie avant de la transmettre à l'utilisateur. Pour capturer l'entrée standard, la sortie standard ou l'erreur standard, sudo utilise un tube pour s'interposer entre le flux d'entrée ou de sortie, enregistrant les E/S avant de les transmettre à l'autre extrémité du tube.

Les E/S peuvent être journalisées soit sur la machine locale, soit sur un serveur de journalisation distant. Pour les journaux locaux, les E/S sont journalisées dans le répertoire spécifié par l'option iolog_dir (/var/log/sudo-io par défaut) en utilisant un identifiant de session unique qui est inclus dans la ligne de journalisation de sudo, préfixé par « TSID= ». L'option iolog_file peut être utilisée pour contrôler le format de l'identifiant de session. Pour les journaux distants, le paramètre log_servers est utilisé pour spécifier un ou plusieurs serveurs de journalisation exécutant sudo_logsrvd ou un autre serveur implémentant le protocole décrit par sudo_logsrv.proto(5).

Pièges de la journalisation des E/S

Lors de la journalisation de l'entrée standard, tout ce qui est envoyé à l'entrée standard sera consommé, indépendamment du fait que la commande exécutée via sudo lise activement l'entrée standard ou non. Cela peut avoir des résultats inattendus lors de l'utilisation de sudo dans un script shell qui s'attend à traiter l'entrée standard. Par exemple, étant donné le script shell suivant :

#!/bin/sh
sudo echo testing
echo done

Il se comportera comme prévu lorsque le script est passé au shell comme argument :

$ sh test.sh
testing
done

Cependant, si le script est passé au shell sur l'entrée standard, la commande « sudo echo testing » consommera le reste du script. Cela signifie que l'instruction « echo done » n'est jamais exécutée.

$ sh -s < test.sh
testing

Il existe plusieurs façons de contourner ce problème :

  1. Redirigez l'entrée standard depuis /dev/null lors de l'exécution d'une commande via sudo

    OPTIONS DE CONFIGURATION

    Il est possible de désactiver l'enregistrement de l'entrée standard pour les commandes qui n'en ont pas besoin.

    • Redirigez l'entrée standard vers un fichier qui ne nécessite pas de lire l'entrée standard. 
      sudo echo testing < /dev/null
    • Passez le script au shell par son nom de chemin au lieu de passer par l'entrée standard. 
      sh test.sh
    • Désactivez l'enregistrement de l'entrée standard pour les commandes qui n'ont pas besoin de lire l'entrée standard. 
      Defaults!/bin/echo !log_stdin

    Selon la commande, il peut ne pas être souhaitable d'enregistrer l'entrée ou la sortie standard. Par exemple, l'enregistrement des entrées/sorties de commandes qui envoient ou reçoivent de grandes quantités de données via la sortie ou l'entrée standard, comme rsync(1) et tar(1), pourrait remplir le fichier journal du système avec des données superflues. Il est possible de désactiver l'enregistrement de l'entrée et de la sortie standard pour de telles commandes comme suit :

    Cmnd_Alias COPY_CMDS = /usr/bin/tar, /usr/bin/cpio, /usr/bin/rsync

# Enregistre l'entrée et la sortie mais omet stdin et stdout lors de la copie de fichiers.
Defaults log_input, log_output
Defaults!COPY_CMDS !log_stdin, !log_stdout

    Cependant, gardez à l'esprit que l'utilisation de l'indicateur log_input ou de la balise de commande LOG_INPUT activera également log_stdin. De même, l'indicateur log_ouput ou la balise de commande LOG_OUTPUT activera log_stdout et log_stderr. Un ordre judicieux des règles peut être nécessaire pour obtenir les résultats que vous attendez.

FORMAT DES LOGS ENTRÉES/SORTIES

Pour les journaux d'E/S locaux et distants, chaque journal est stocké dans un répertoire distinct qui contient les fichiers suivants :

log
Un fichier texte contenant des informations sur la commande. La première ligne se compose des champs suivants délimités par des deux-points : l'heure à laquelle la commande a été exécutée, le nom de l'utilisateur qui a exécuté sudo, le nom de l'utilisateur cible, le nom du groupe cible (facultatif), le terminal depuis lequel sudo a été exécuté, et le nombre de lignes et de colonnes du terminal. La deuxième et la troisième ligne contiennent le répertoire de travail à partir duquel la commande a été exécutée et le nom du chemin de la commande elle-même (avec les arguments s'ils sont présents).
log.json
Un fichier au format JSON contenant des informations sur la commande. Il est similaire au fichier log mais contient des informations supplémentaires et est facilement extensible. Le fichier log.json sera utilisé par sudoreplay(8) de préférence au fichier log s'il existe. Le fichier peut contenir les éléments suivants :
timestamp
Un objet JSON contenant l'heure à laquelle la commande a été exécutée. Il se compose de deux valeurs, seconds et nanoseconds.
columns
Le nombre de colonnes du terminal sur lequel la commande a été exécutée, ou zéro s'il n'y avait pas de terminal.
command
Le chemin d'accès complet de la commande qui a été exécutée.
lines
Le nombre de lignes du terminal sur lequel la commande a été exécutée, ou zéro s'il n'y avait pas de terminal.
runargv
Un tableau JSON représentant le vecteur d'arguments de la commande tel que passé à l'appel système execve(2).
runenv
Un tableau JSON représentant l'environnement de la commande tel que passé à l'appel système execve(2).
rungid
L'identifiant du groupe sous lequel la commande a été exécutée. Cet élément n'est présent que lorsque l'utilisateur spécifie un groupe sur la ligne de commande.
rungroup
Le nom du groupe sous lequel la commande a été exécutée. Cet élément n'est présent que lorsque l'utilisateur spécifie un groupe sur la ligne de commande.
runuid
L'identifiant de l'utilisateur sous lequel la commande a été exécutée.
runuser
Le nom de l'utilisateur sous lequel la commande a été exécutée.
submitcwd
Le répertoire de travail courant au moment où sudo a été exécuté.
submithost
Le nom de l'hôte sur lequel la commande a été exécutée.
submituser
Le nom de l'utilisateur qui a exécuté la commande via sudo.
ttyname
Le nom du chemin du terminal depuis lequel l'utilisateur a invoqué sudo. Si la commande a été exécutée dans un pseudo-terminal, ttyname sera différent du terminal dans lequel la commande s'est réellement exécutée.
timing
Informations de synchronisation utilisées pour rejouer la session. Chaque ligne se compose du type d'entrée du journal d'E/S et du temps écoulé depuis la dernière entrée, suivi de données spécifiques au type. Les types d'entrée de journal d'E/S et leurs données spécifiques correspondantes sont :
0
entrée standard, nombre d'octets dans l'entrée
1
sortie standard, nombre d'octets dans l'entrée
2
erreur standard, nombre d'octets dans l'entrée
3
entrée de terminal, nombre d'octets dans l'entrée
4
sortie de terminal, nombre d'octets dans l'entrée
5
changement de fenêtre, nouveau nombre de lignes et de colonnes
6
compatibilité bug pour la sortie de terminal de sudo 1.8.7
7
suspension ou reprise de commande, signal reçu
ttyin
Entrée brute provenant du terminal de l'utilisateur, telle qu'elle a été reçue. Ce fichier n'est présent que si les indicateurs log_input ou log_ttyin sont définis et que sudo a été exécuté depuis un terminal. Aucun post-traitement n'est effectué. Pour une visualisation manuelle, vous pourriez vouloir convertir les caractères de retour chariot dans le journal en sauts de ligne. Par exemple : ‘gunzip -c ttyin | tr "\r" "\n"’
stdin
L'entrée standard lorsqu'aucun terminal n'est présent, ou une entrée redirigée depuis un pipe ou un fichier. Ce fichier n'est présent que si les indicateurs log_input ou log_stdin sont définis et que l'entrée standard n'est pas connectée à un terminal.
ttyout
Sortie du pseudo-terminal (ce que la commande écrit à l'écran). Un post-traitement spécifique au terminal est effectué avant que les données ne soient enregistrées. Cela signifie que, par exemple, les sauts de ligne sont généralement convertis en paires saut de ligne/retour chariot et les tabulations peuvent être développées en espaces. Ce fichier n'est présent que si les indicateurs log_output ou log_ttyout sont définis et que sudo a été exécuté depuis un terminal.
stdout
La sortie standard lorsqu'aucun terminal n'est présent, ou une sortie redirigée vers un pipe ou un fichier. Ce fichier n'est présent que si les indicateurs log_output ou log_stdout sont définis et que la sortie standard n'est pas connectée à un terminal.
stderr
L'erreur standard lorsqu'aucun terminal n'est présent, ou une sortie redirigée vers un pipe ou un fichier. Ce fichier n'est présent que si les indicateurs log_output ou log_stderr sont définis et que l'erreur standard n'est pas connectée à un terminal.

Tous les fichiers autres que log sont compressés au format gzip à moins que l'indicateur compress_io n'ait été désactivé. En raison de la mise en mémoire tampon, il n'est normalement pas possible d'afficher les journaux d'E/S en temps réel pendant l'exécution du programme. Les données du journal d'E/S ne seront complètes que lorsque le programme exécuté par sudo sera terminé ou aura été terminé par un signal. L'indicateur iolog_flush peut être utilisé pour désactiver la mise en mémoire tampon, auquel cas les données du journal d'E/S sont écrites sur le disque dès qu'elles sont disponibles. La partie sortie d'un fichier journal d'E/S peut être consultée avec l'utilitaire sudoreplay(8), qui peut également être utilisé pour lister ou rechercher les journaux disponibles.

L'entrée utilisateur peut contenir des informations sensibles telles que des mots de passe (même s'ils ne sont pas affichés à l'écran), qui seront stockés dans le fichier journal sans cryptage. Dans la plupart des cas, l'enregistrement de la sortie de la commande via log_output ou LOG_OUTPUT est suffisant. Lors de l'enregistrement de l'entrée, envisagez de désactiver l'indicateur log_passwords.

Étant donné que les journaux d'E/S de chaque session sont stockés dans un répertoire distinct, les utilitaires de rotation de journaux traditionnels ne peuvent pas être utilisés pour limiter le nombre de journaux d'E/S. Le moyen le plus simple de limiter le nombre d'E/S est de définir l'option maxseq sur le nombre maximum de journaux que vous souhaitez stocker. Une fois que le numéro de séquence du journal d'E/S atteint maxseq, il sera réinitialisé à zéro et sudoers tronquera et réutilisera tous les journaux d'E/S existants.

NOTES DE SÉCURITÉ

Limitations de l'opérateur '!'

Il est généralement inefficace de "soustraire" des commandes à TOUT en utilisant l'opérateur '!'. Un utilisateur peut facilement contourner cela en copiant la commande souhaitée sous un autre nom, puis en l'exécutant. Par exemple :

bill	ALL = ALL, !SU, !SHELLS

N'empêche pas réellement bill d'exécuter les commandes listées dans SU ou SHELLS, car il peut simplement copier ces commandes sous un autre nom, ou utiliser une évasion de shell depuis un éditeur ou un autre programme. Par conséquent, ces types de restrictions doivent être considérés au mieux comme consultatifs (et renforcés par la politique).

En général, si un utilisateur a sudo ALL, rien ne l'empêche de créer son propre programme qui lui donne un shell root (ou de faire sa propre copie d'un shell), quelles que soient les conditions '!' dans la spécification de l'utilisateur.

Implications de sécurité de fast_glob

Si l'option fast_glob est utilisée, il n'est pas possible de nier de manière fiable les commandes dont le nom de chemin contient des caractères de globbing (alias jokers). Ceci est dû au fait que la fonction fnmatch(3) de la bibliothèque C ne peut pas résoudre les chemins relatifs. Bien que ce soit généralement une simple gêne pour les règles qui accordent des privilèges, cela peut entraîner un problème de sécurité pour les règles qui soustraient ou révoquent des privilèges.

Par exemple, compte tenu de l'entrée suivante dans le fichier sudoers :

john	ALL = /usr/bin/passwd [a-zA-Z0-9]*, /usr/bin/chsh [a-zA-Z0-9]*,\
              /usr/bin/chfn [a-zA-Z0-9]*, !/usr/bin/* root

L'utilisateur john peut toujours exécuter '/usr/bin/passwd root' si fast_glob est activé en se déplaçant vers /usr/bin et en exécutant './passwd root' à la place.

Un autre problème potentiel est que lorsque sudo exécute la commande, il doit utiliser la commande ou le chemin spécifié par l'utilisateur au lieu d'un chemin listé dans le fichier sudoers. Cela peut entraîner une condition de concurrence "time of check versus time of use" (TOCTOU).

Caractères jokers dans les arguments de commande

Les arguments de la ligne de commande sont comparés comme une seule chaîne concaténée. Cela signifie qu'un caractère joker tel que '?' ou '*' correspondra aux limites des mots, ce qui peut être inattendu. Par exemple, alors qu'une entrée sudoers comme :

%operator ALL = /bin/cat /var/log/messages*

autorisera des commandes comme :

$ sudo cat /var/log/messages.1

Elle autorisera également :

$ sudo cat /var/log/messages /etc/shadow

ce qui n'était probablement pas l'intention. Une alternative plus sûre consiste à utiliser une expression régulière pour faire correspondre les arguments de la ligne de commande. L'exemple ci-dessus peut être réécrit comme une expression régulière :

%operator ALL = /bin/cat ^/var/log/messages[^[:space:]]*$

L'expression régulière ne fera correspondre qu'un seul fichier avec un nom qui commence par /var/log/messages et ne contient aucun espace blanc dans le nom. Il est souvent préférable de traiter la ligne de commande en dehors du fichier sudoers dans un langage de script pour tout ce qui est non trivial.

Expressions régulières dans les noms de commande

L'utilisation d'une expression régulière pour faire correspondre un nom de commande a les mêmes implications de sécurité que l'utilisation de l'option fast_glob :

  • Il n'est pas possible de nier de manière fiable les commandes lorsque le nom de chemin est une expression régulière.
  • Lorsque sudo exécute la commande, il doit utiliser la commande ou le chemin spécifié par l'utilisateur au lieu d'un chemin listé dans le fichier sudoers. Cela peut entraîner une condition de concurrence "time of check versus time of use" (TOCTOU).

Ces problèmes ne s'appliquent pas aux règles où seuls les options de la ligne de commande sont comparées à l'aide d'une expression régulière.

Prévention des évasions de shell

Une fois que sudo exécute un programme, ce programme est libre de faire ce qu'il veut, y compris exécuter d'autres programmes. Cela peut être un problème de sécurité, car il n'est pas rare qu'un programme permette des évasions de shell, ce qui permet à un utilisateur de contourner le contrôle d'accès et la journalisation de sudo. Les programmes courants qui permettent les évasions de shell incluent les shells (évidemment), les éditeurs, les paginateurs, les courriels et les programmes de terminaux.

Il existe quatre approches de base à ce problème :

restreindre
Évitez de donner aux utilisateurs l'accès à des commandes qui leur permettent d'exécuter des commandes arbitraires. De nombreux éditeurs ont un mode restreint où les évasions de shell sont désactivées, bien que sudoedit soit une meilleure solution pour exécuter des éditeurs via sudo. En raison du grand nombre de programmes offrant des évasions de shell, limiter les utilisateurs à l'ensemble des programmes qui n'en offrent pas est souvent irréalisable.
intercepter
Sur la plupart des systèmes, la fonctionnalité intercept de sudo peut être utilisée pour intercepter de manière transparente une tentative d'exécution d'une nouvelle commande, l'autoriser ou la refuser en fonction des règles sudoers, et enregistrer le résultat. Par exemple, cela peut être utilisé pour restreindre les commandes exécutées depuis un shell ou un éditeur privilégié. Cependant, tous les programmes ne fonctionnent pas correctement lorsque intercept est activé.

Il existe deux mécanismes sous-jacents qui peuvent être utilisés pour implémenter le mode intercept : dso et trace. Le paramètre intercept_type peut être utilisé pour choisir entre eux.

Le premier mécanisme, dso, remplace les fonctions standard de la bibliothèque C utilisées pour exécuter une commande. Il le fait en définissant une variable d'environnement (généralement LD_PRELOAD) vers le chemin d'un objet partagé dynamique, ou une bibliothèque partagée, contenant des versions personnalisées des fonctions de bibliothèque execve(2), execl(3), execle(3), execlp(3), execv(3), execvp(3), execvpe(3) et system(3) qui se reconnectent à sudo pour une décision de politique. Notez, cependant, que cela s'applique uniquement aux exécutables liés dynamiquement. Il n'est pas possible d'intercepter les commandes pour les exécutables liés statiquement ou les exécutables qui s'exécutent sous émulation binaire de cette manière. Comme la plupart des chargeurs dynamiques ignorent LD_PRELOAD (ou l'équivalent) lors de l'exécution de programmes set-user-ID et set-group-ID, sudoers ne permet pas par défaut l'exécution de tels programmes en mode intercept. Le mécanisme dso est incompatible avec le support RBAC SELinux de sudo (voir ci-dessous). SELinux désactive LD_PRELOAD par défaut et interfère avec l'héritage des descripteurs de fichiers, dont sudo dépend.

Le second mécanisme, trace, est disponible sur les systèmes Linux qui prennent en charge le filtrage seccomp(2). Il utilise ptrace(2) et seccomp(2) pour intercepter l'appel système execve(2) au lieu de précharger un objet partagé dynamique. Les exécutables statiques et dynamiques sont pris en charge et il est compatible avec le mode RBAC SELinux de sudo. Les fonctions utilisant l'appel système execveat(2), comme fexecve(3), ne sont pas actuellement interceptées. Les programmes qui dépendent de ptrace(2), comme les débogueurs et les traceurs d'appels système (comme strace(1) et truss(1)) ne pourront pas fonctionner si intercept est activé en mode trace. Cette même restriction s'applique à l'option sudoers log_subcmds.

La fonctionnalité intercept est connue pour fonctionner sur Solaris, *BSD, Linux, macOS, HP-UX 11.x et AIX 5.3 et supérieurs. Elle devrait être prise en charge sur la plupart des systèmes d'exploitation qui prennent en charge la variable d'environnement LD_PRELOAD ou un équivalent. Il n'est pas possible d'intercepter les commandes intégrées au shell ni de restreindre la capacité de lire ou d'écrire des fichiers sensibles depuis un shell.

Pour activer le mode d'interception commande par commande, utilisez la balise INTERCEPT telle que documentée dans la section Spécification de l'utilisateur ci-dessus. Voici cet exemple à nouveau :

chuck	research = INTERCEPT: ALL

Cela permet à l'utilisateur chuck d'exécuter n'importe quelle commande sur la machine "research" en mode d'interception. Toutes les commandes exécutées via des évasions de shell seront validées et journalisées par sudo. Si vous n'êtes pas sûr que votre système soit capable de prendre en charge intercept, vous pouvez toujours essayer et vérifier si les commandes externes exécutées via un shell sont journalisées lorsque intercept est activé.

Il est également possible de configurer l'interception au niveau mondial dans le fichier sudoers via la directive Defaults intercept. Par défaut, l'interception est désactivée.

Veuillez noter que l'interception des sous-commandes via l'option log_subcmds (voir ci-dessous) est une alternative qui ne nécessite pas le mode intercept et qui peut être plus facile à configurer. Cependant, elle est moins complète car elle ne peut pas intercepter les programmes qui utilisent déjà ptrace(2).

Si vous accordez des privilèges sur le système entier à un utilisateur, il peut être très difficile de l'empêcher de trouver un moyen d'exécuter un shell arbitraire. Si un utilisateur peut exécuter un programme qui lui permet d'exécuter d'autres programmes, il peut souvent trouver un moyen de s'échapper vers un shell.

En raison de la complexité de la prévention des évasions de shell, il est souvent préférable de limiter les privilèges accordés aux utilisateurs au minimum nécessaire pour leur tâche.

intercept_verify
Il existe une condition de concurrence intrinsèque entre le moment où une commande est vérifiée par rapport aux règles sudoers et le moment où elle est effectivement exécutée. Si un utilisateur est autorisé à exécuter des commandes arbitraires, il peut être en mesure de modifier les arguments de execve(2) dans le programme après que la vérification de la politique sudoers soit terminée mais avant que la nouvelle commande ne soit exécutée. À partir de la version 1.9.12, la méthode trace vérifiera que la commande et ses arguments n'ont pas été modifiés après la fin de execve(2) mais avant que l'exécution du nouveau programme ait eu une chance de démarrer. Ce n'est pas le cas avec la méthode dso. Voir la description du réglage intercept_verify pour plus d'informations.

log
Il existe deux manières distinctes mais liées de journaliser des commandes supplémentaires. La première consiste à activer la journalisation des E/S à l'aide de l'indicateur log_output. Cela journalisera la sortie de la commande mais ne créera pas d'entrée de journal d'événements lorsque la commande supplémentaire sera exécutée. La seconde consiste à activer l'indicateur log_subcmds dans sudoers, ce qui créera une entrée de journal d'événements chaque fois qu'une nouvelle commande sera exécutée. Si la journalisation des E/S est également activée, l'entrée de journal inclura un décalage temporel dans le journal des E/S pour indiquer quand la commande a été exécutée. Ce décalage peut être passé à l'utilitaire sudoreplay(8) pour rejouer le journal des E/S au moment exact où la commande a été exécutée. L'indicateur log_subcmds utilise le même mécanisme que intercept (voir ci-dessus) et a les mêmes limitations.
noexec
La fonctionnalité noexec de sudo peut être utilisée pour empêcher un programme exécuté par sudo d'exécuter d'autres programmes. Sur la plupart des systèmes, elle utilise le même mécanisme LD_PRELOAD que intercept (voir ci-dessus) et donc les mêmes mises en garde s'appliquent. La fonctionnalité noexec est capable de bloquer l'exécution de commandes exécutées via les fonctions execve(2), execl(3), execle(3), execlp(3), exect(3), execv(3), execveat(3), execvP(3), execvp(3), execvpe(3), fexecve(3), popen(3), posix_spawn(3), posix_spawnp(3), system(3) et wordexp(3). Sous Linux, un filtre seccomp(2) est utilisé pour implémenter noexec. Sur Solaris 10 et supérieur, noexec utilise les privilèges Solaris au lieu de la variable d'environnement LD_PRELOAD.

Pour activer noexec pour une commande, utilisez la balise NOEXEC comme documenté dans la section User Specification ci-dessus. Voici à nouveau cet exemple :

aaron	shanty = NOEXEC: /usr/bin/more, /usr/bin/vi

Cela permet à l'utilisateur aaron d'exécuter /usr/bin/more et /usr/bin/vi avec noexec activé. Cela empêchera ces deux commandes d'exécuter d'autres commandes (comme un shell). Si vous n'êtes pas sûr que votre système puisse prendre en charge noexec, vous pouvez toujours essayer et vérifier si les évasions de shell fonctionnent lorsque noexec est activé.

Restreindre les évasions de shell n'est pas une panacée. Les programmes exécutés en tant que root sont toujours capables de nombreuses opérations potentiellement dangereuses (comme modifier ou écraser des fichiers) qui pourraient conduire à une escalade de privilèges involontaire. Dans le cas spécifique d'un éditeur, une approche plus sûre consiste à donner à l'utilisateur l'autorisation d'exécuter sudoedit (voir ci-dessous).

Édition sécurisée

Le plugin sudoers inclut le support de sudoedit qui permet aux utilisateurs d'éditer des fichiers en toute sécurité avec l'éditeur de leur choix. Comme sudoedit est une commande intégrée, elle doit être spécifiée dans le fichier sudoers sans chemin d'accès. Cependant, elle peut prendre des arguments de ligne de commande comme une commande normale. Les caractères génériques utilisés dans les arguments de ligne de commande de sudoedit sont censés être des noms de chemin, de sorte qu'une barre oblique ('/') ne sera pas mise en correspondance par un caractère générique.

Contrairement aux autres commandes sudo, l'éditeur est exécuté avec les permissions de l'utilisateur appelant et avec l'environnement non modifié. Plus d'informations peuvent être trouvées dans la description de l'option -e dans sudo(8).

Par exemple, pour permettre à l'utilisateur operator d'éditer le fichier « message du jour » sur n'importe quelle machine :

operator ALL = sudoedit /etc/motd

L'utilisateur operator exécute alors sudoedit comme suit :

$ sudoedit /etc/motd

L'éditeur s'exécutera en tant qu'utilisateur operator, pas root, sur une copie temporaire de /etc/motd. Une fois le fichier édité, /etc/motd sera mis à jour avec le contenu de la copie temporaire.

Les utilisateurs ne devraient jamais se voir accorder la permission sudoedit d'éditer un fichier qui réside dans un répertoire auquel l'utilisateur a un accès en écriture, directement ou via un caractère générique. Si l'utilisateur a un accès en écriture au répertoire, il est possible de remplacer le fichier légitime par un lien vers un autre fichier, permettant l'édition de fichiers arbitraires. Pour éviter cela, à partir de la version 1.8.16, les liens symboliques ne seront pas suivis dans les répertoires inscriptibles et sudoedit refusera d'éditer un fichier situé dans un répertoire inscriptible à moins que l'option sudoedit_checkdir n'ait été désactivée ou que l'utilisateur appelant ne soit root. De plus, dans les versions 1.8.15 et supérieures, sudoedit refusera d'ouvrir un lien symbolique à moins que l'option sudoedit_follow ne soit activée ou que la commande sudoedit ne soit préfixée par la balise FOLLOW dans le fichier sudoers.

Vérifications des fichiers d'horodatage

sudoers vérifiera la propriété de son répertoire d'horodatage (/run/sudo/ts par défaut) et ignorera le contenu du répertoire s'il n'est pas la propriété de root ou s'il est accessible en écriture par un utilisateur autre que root. Les anciennes versions de sudo stockaient les fichiers d'horodatage dans /tmp ; ce n'est plus recommandé car il pourrait être possible pour un utilisateur de créer lui-même l'horodatage sur les systèmes qui permettent aux utilisateurs non privilégiés de modifier la propriété des fichiers qu'ils créent.

Bien que le répertoire d'horodatage devrait être effacé à chaque redémarrage, tous les systèmes ne contiennent pas de répertoire /run ou /var/run. Pour éviter des problèmes potentiels, sudoers ignorera les fichiers d'horodatage datant d'avant le démarrage de la machine sur les systèmes où l'heure de démarrage est disponible.

Certains systèmes avec des environnements de bureau graphiques permettent aux utilisateurs non privilégiés de modifier l'horloge système. Étant donné que sudoers s'appuie sur l'horloge système pour la validation des horodatages, il pourrait être possible sur de tels systèmes pour un utilisateur de faire fonctionner sudo plus longtemps que timestamp_timeout en reculant l'horloge. Pour lutter contre cela, sudoers utilise une horloge monotone (qui ne recule jamais) pour ses horodatages si le système le prend en charge.

sudoers n'honorera pas les horodatages définis bien dans le futur. Les horodatages avec une date supérieure à current_time + 2 * TIMEOUT seront ignorés et sudoers journalisera et se plaindra.

Si l'option timestamp_type est définie sur “tty”, l'enregistrement de l'horodatage inclut le numéro de périphérique du terminal avec lequel l'utilisateur s'est authentifié. Cela offre une granularité par terminal, mais les enregistrements d'horodatage peuvent toujours survivre à la session de l'utilisateur.

Sauf si l'option timestamp_type est définie sur “global”, l'enregistrement de l'horodatage inclut également l'ID de session du processus qui s'est authentifié en dernier. Cela empêche les processus de différentes sessions de terminal d'utiliser le même enregistrement d'horodatage. Sur les systèmes où l'heure de démarrage d'un processus peut être interrogée, l'heure de démarrage du leader de session est enregistrée dans l'enregistrement d'horodatage. Si aucun terminal n'est présent ou si l'option timestamp_type est définie sur “ppid”, l'heure de démarrage du processus parent est utilisée à la place. Dans la plupart des cas, cela empêchera un enregistrement d'horodatage d'être réutilisé sans que l'utilisateur ne saisisse de mot de passe lors de la déconnexion et de la reconnexion.

ATTENTION

Le fichier sudoers doit toujours être édité par l'utilitaire visudo qui verrouille le fichier et vérifie les erreurs de syntaxe. Si sudoers contient des erreurs de syntaxe, sudo peut refuser de s'exécuter, ce qui est un problème grave si sudo est votre seule méthode pour obtenir les privilèges de superutilisateur. Les versions récentes de sudoers tenteront de récupérer après une erreur de syntaxe en ignorant le reste de la ligne après avoir rencontré une erreur. Les versions plus anciennes de sudo ne s'exécuteront pas si sudoers contient une erreur de syntaxe.

Lors de l'utilisation de netgroups de machines (par opposition aux utilisateurs), si vous stockez le nom d'hôte entièrement qualifié dans le netgroup (comme c'est généralement le cas), vous devez soit avoir le nom d'hôte de la machine entièrement qualifié tel que retourné par la commande hostname, soit utiliser l'option fqdn dans sudoers.

BOGUES

Si vous pensez avoir trouvé un bogue dans sudoers, vous pouvez soit signaler le bogue dans la base de données des bogues sudo, https://bugzilla.sudo.ws/, soit ouvrir un ticket sur https://github.com/sudo-project/sudo/issues. Si vous préférez utiliser l'e-mail, des messages peuvent être envoyés à la liste de diffusion sudo-workers, https://www.sudo.ws/mailman/listinfo/sudo-workers (publique) ou <sudo@sudo.ws> (privée).

Veuillez ne pas signaler de vulnérabilités de sécurité via les tickets GitHub publics, Bugzilla ou les listes de diffusion. Signalez-les plutôt par e-mail à <Todd.Miller@sudo.ws>. Vous pouvez chiffrer votre message avec PGP si vous le souhaitez, en utilisant la clé trouvée à https://www.sudo.ws/dist/PGPKEYS.
