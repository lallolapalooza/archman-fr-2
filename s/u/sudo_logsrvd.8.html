SUDO_LOGSRVD(8) Manuel du gestionnaire système SUDO_LOGSRVD(8)

NOM

sudo_logsrvd — serveur de journalisation des événements et des E/S de sudo

SYNOPIS

sudo_logsrvd [-hnV] [-f fichier] [-R pourcentage]

DESCRIPTION

sudo_logsrvd est un serveur de journalisation haute performance qui accepte les journaux d'événements et d'E/S de sudo. Il peut être utilisé pour implémenter une journalisation centralisée des journaux de sudo. Le serveur dispose de deux modes de fonctionnement : local et relais. Par défaut, sudo_logsrvd stocke les journaux localement, mais il peut également être configuré pour les relayer vers un autre serveur prenant en charge le protocole sudo_logsrv.proto(5).

Lorsqu'il n'effectue pas de relais, les entrées du journal d'événements peuvent être enregistrées soit via syslog(3), soit dans un fichier local. Les journaux d'E/S stockés localement par sudo_logsrvd peuvent être rejoués via l'utilitaire sudoreplay(8) de la même manière que les journaux générés directement par le plugin sudoers.

Le serveur prend également en charge la reprise des transferts de journaux interrompus. Pour distinguer les journaux d'E/S terminés des journaux incomplets, le fichier de chronométrage des journaux d'E/S est défini comme étant en lecture seule lorsque le journal est complet.

Les paramètres de configuration pour sudo_logsrvd peuvent être spécifiés dans le fichier sudo_logsrvd.conf(5) ou dans le fichier spécifié via l'option -f.

sudo_logsrvd relit son fichier de configuration lorsqu'il reçoit SIGHUP et écrit l'état du serveur dans le fichier de débogage (s'il y en a un configuré) lorsqu'il reçoit SIGUSR1.

Les options sont les suivantes :

-f fichier, --file=fichier
Lire la configuration depuis le fichier fichier au lieu de celle par défaut, /etc/sudo_logsrvd.conf.
-h, --help
Afficher un court message d'aide sur la sortie standard et quitter.
-n, --no-fork
Exécuter sudo_logsrvd au premier plan au lieu de se détacher du terminal et de devenir un démon.
-R pourcentage, --random-drop=pourcentage
Pour chaque message, il y a une chance de pourcentage que le serveur abandonne la connexion. Ceci est uniquement destiné au débogage de la capacité d'un client à redémarrer une connexion.
-V, --version
Afficher la version de sudo_logsrvd et quitter.

Sécurisation des connexions serveur

Les données du journal d'E/S envoyées à sudo_logsrvd peuvent contenir des informations sensibles telles que des mots de passe et doivent être sécurisées à l'aide de Transport Layer Security (TLS). Cela nécessite d'avoir un certificat signé sur le serveur et, si tls_checkpeer est activé dans sudo_logsrvd.conf(5), un certificat signé sur le client également.

Les certificats peuvent être signés par une autorité de certification (AC) bien connue, ou une AC privée peut être utilisée. Les instructions pour créer une AC privée sont incluses ci-dessous dans la section EXEMPLES.

Débogage de sudo_logsrvd

sudo_logsrvd prend en charge un framework de débogage flexible qui est configuré via des lignes Debug dans le fichier sudo.conf(5).

Pour plus d'informations sur la configuration de sudo.conf(5), référez-vous à son manuel.

FICHIERS

Fichier de configuration du serveur de journaux Sudo

Fichier PID pour sudo_logsrvd

EXEMPLES

Création de certificats auto-signés

Sauf si vous utilisez des certificats signés par une autorité de certification (AC) bien connue (ou une AC d'entreprise locale), vous devrez créer votre propre AC capable de signer les certificats utilisés par sudo_logsrvd, sudo_sendlog et le plugin sudoers. Les étapes suivantes utilisent la commande openssl(1) pour créer des clés et des certificats.

Configuration initiale

Tout d'abord, nous devons créer une structure de répertoires pour stocker les fichiers de l'AC. Nous allons créer une nouvelle hiérarchie de répertoires dans /etc/ssl/sudo à cet effet.

# mkdir /etc/ssl/sudo
# cd /etc/ssl/sudo
# mkdir certs csr newcerts private
# chmod 700 private
# touch index.txt
# echo 1000 > serial

Les fichiers serial et index.txt sont utilisés pour garder une trace des certificats signés.

Ensuite, nous devons copier le fichier openssl.conf et le personnaliser pour notre nouvelle AC. Le chemin vers openssl.cnf dépend du système, mais /etc/ssl/openssl.cnf est l'emplacement le plus courant. Vous devrez peut-être ajuster l'exemple ci-dessous s'il se trouve à un autre endroit sur votre système.

# cp /etc/ssl/openssl.cnf .

Modifiez maintenant le fichier openssl.cnf dans le répertoire courant et assurez-vous qu'il contient les sections “ca”, “CA_default”, “v3_ca”, et “usr_cert”. Ces sections doivent inclure au moins les paramètres suivants :

[ ca ]
default_ca              = CA_default

[ CA_default ]
dir                     = /etc/ssl/sudo
certs                   = $dir/certs
database                = $dir/index.txt
certificate             = $dir/cacert.pem
serial                  = $dir/serial

[ v3_ca ]
subjectKeyIdentifier    = hash
authorityKeyIdentifier  = keyid:always,issuer
basicConstraints        = critical,CA:true
keyUsage                = cRLSign, keyCertSign

[ usr_cert ]
basicConstraints        = CA:FALSE
keyUsage                = nonRepudiation, digitalSignature, \
                          keyEncipherment
subjectKeyIdentifier    = hash
authorityKeyIdentifier  = keyid,issuer

Si votre fichier openssl.conf contient déjà une section “CA_default”, vous devrez peut-être seulement modifier le paramètre “dir” et activer les paramètres “keyUsage” s'ils sont commentés.

Création de la clé et du certificat de l'AC

Afin de créer et signer nos propres certificats, nous devons créer une clé privée et un certificat pour la racine de l'AC. D'abord, créez la clé privée et protégez-la avec une phrase secrète :

# openssl

sudo_logsrvd.8.en

NAME

sudo_logsrvd

sudo logging server

SYNOPSIS

sudo_logsrvd [-d] [-f config_file]

DESCRIPTION

The sudo_logsrvd daemon listens for logging connections from sudo(8) on a specified network port. It accepts connections using either plain TCP or TLS. Log records are written to a file specified in the sudo_logsrvd.conf configuration file.

The sudo_logsrvd daemon is typically started from the system's init scripts. When run from the command line, it runs in the foreground unless the -d option is specified, in which case it runs in the background as a daemon.

Configuration is performed via the sudo_logsrvd.conf file, located at /etc/sudo_logsrvd.conf by default.

FILES

/etc/sudo_logsrvd.conf
Configuration file for sudo_logsrvd.
/var/log/sudo.log
Default log file if not otherwise specified in the configuration.
/etc/ssl/sudo/
Default directory for TLS-related files (CA certificate, server certificate, and server key).

EXAMPLES

This example demonstrates how to set up TLS for sudo_logsrvd and the sudo client.

First, create a directory structure to hold the certificates and keys:

# mkdir -p /etc/ssl/sudo/{private,certs,csr}

Next, generate a private key and the root certificate for the Certificate Authority (CA).

# openssl genrsa -aes256 -out private/cakey.pem 4096
# chmod 400 private/cakey.pem

Next, generate the root certificate, using appropriate values for the site-specific fields:

# openssl req -config openssl.cnf -key private/cakey.pem \
    -new -x509 -days 7300 -sha256 -extensions v3_ca \
    -out cacert.pem

Creating and signing certificates

The server and client certificates will be signed by the previously created root CA. Usually, the root CA is not used to sign server/client certificates directly. Instead, intermediate certificates are created and signed with the root CA and the intermediate certs are used to sign CSRs (Certificate Signing Request). In this example we'll skip this part for simplicity's sake and sign the CSRs with the root CA.

First, generate the private key without a pass phrase.

# openssl genrsa -out private/logsrvd_key.pem 2048
# chmod 400 private/logsrvd_key.pem

Next, create a certificate signing request (CSR) for the server's certificate. The organization name must match the name given in the root certificate. The common name should be either the server's IP address or a fully qualified domain name.

# openssl req -config openssl.cnf -key private/logsrvd_key.pem -new \
    -sha256 -out csr/logsrvd_csr.pem

To generate a client certificate, repeat the process above using a different file name.

Configuring sudo_logsrvd to use TLS

To use TLS for client/server communication, both sudo_logsrvd and the sudoers plugin need to be configured to use TLS. Configuring sudo_logsrvd for TLS requires the following settings, assuming the same path names used earlier:

# Listen on port 30344 for TLS connections to any address.
listen_address = *:30344(tls)

# Path to the certificate authority bundle file in PEM format.
tls_cacert = /etc/ssl/sudo/cacert.pem

# Path to the server's certificate file in PEM format.
tls_cert = /etc/ssl/sudo/certs/logsrvd_cert.pem

# Path to the server's private key file in PEM format.
tls_key = /etc/ssl/sudo/private/logsrvd_key.pem

The root CA cert (cacert.pem) must be installed on the system running sudo_logsrvd. If peer authentication is enabled on the client, a copy of cacert.pem must be present on the client system too.
