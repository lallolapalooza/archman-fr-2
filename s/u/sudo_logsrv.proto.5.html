NOM

sudo_logsrv.proto — Protocole du serveur de logs Sudo

DESCRIPTION

À partir de la version 1.9.0, sudo prend en charge l'envoi des journaux d'événements et d'E/S à un serveur de logs. Le protocole utilisé est écrit dans le langage dédié de Google Protocol Buffers. La section EXEMPLES inclut une description complète du protocole au format Protocol Buffers.

Comme il n'y a aucun moyen de déterminer les frontières des messages lors de l'utilisation de Protocol Buffers, la taille brute de chaque message est envoyée immédiatement avant le message lui-même sous la forme d'un entier non signé de 32 bits en ordre d'octets réseau. Ceci est appelé “encadrement par préfixe de longueur” et c'est ainsi que Google suggère de gérer l'absence de délimiteurs de messages.

Le protocole est composé de deux messages de base, ClientMessage et ServerMessage, décrits ci-dessous. Le serveur doit accepter les messages jusqu'à deux mégaoctets. Le serveur peut renvoyer une erreur si le client tente d'envoyer un message plus grand que deux mégaoctets.

Messages Client

Un ClientMessage est un conteneur utilisé pour encapsuler tous les types de messages possibles qu'un client peut envoyer au serveur.

message ClientMessage {
  oneof type {
    AcceptMessage accept_msg = 1;
    RejectMessage reject_msg = 2;
    ExitMessage exit_msg = 3;
    RestartMessage restart_msg = 4;
    AlertMessage alert_msg = 5;
    IoBuffer ttyin_buf = 6;
    IoBuffer ttyout_buf = 7;
    IoBuffer stdin_buf = 8;
    IoBuffer stdout_buf = 9;
    IoBuffer stderr_buf = 10;
    ChangeWindowSize winsize_event = 11;
    CommandSuspend suspend_event = 12;
    ClientHello hello_msg = 13;
  }
}

Les différents sous-messages ClientMessage que le client peut envoyer au serveur sont décrits ci-dessous.

TimeSpec

message TimeSpec {
    int64 tv_sec = 1;
    int32 tv_nsec = 2;
}

Un TimeSpec est l'équivalent d'une struct timespec POSIX, contenant des membres pour les secondes et les nanosecondes. Le membre tv_sec est un entier de 64 bits pour prendre en charge les dates après 2038.

InfoMessage

message InfoMessage {
  message StringList {
    repeated string strings = 1;
  }
  message NumberList {
    repeated int64 numbers = 1;
  }
  string key = 1;
  oneof value {
    int64 numval = 2;
    string strval = 3;
    StringList strlistval = 4;
    NumberList numlistval = 5;
  }
}

Un InfoMessage est utilisé pour représenter des informations sur l'utilisateur appelant ainsi que sur l'environnement d'exécution de la commande sous forme de paires clé-valeur. La clé est toujours une chaîne de caractères, mais la valeur peut être un entier de 64 bits, une chaîne de caractères, un tableau de chaînes de caractères ou un tableau d'entiers de 64 bits. Les données du journal d'événements sont composées d'entrées InfoMessage. Voir la section VARIABLES DU JOURNAL D'ÉVÉNEMENTS pour plus d'informations.

ClientHello hello_msg

message ClientHello {
  string client_id = 1;
}

Un message ClientHello contient des informations sur le client qui peuvent être envoyées au serveur lorsque le client se connecte pour la première fois.

client_id
Une description libre du client. Cela inclut généralement le nom et la version de l'implémentation client.

AcceptMessage accept_msg

message AcceptMessage {
  TimeSpec submit_time = 1;
  repeated InfoMessage info_msgs = 2;
  bool expect_iobufs = 3;
}

Un AcceptMessage est envoyé par le client lorsqu'une commande est autorisée par la politique de sécurité. Il contient les membres suivants :

submit_time
L'heure de l'horloge murale à laquelle la commande a été soumise à la politique de sécurité.
info_msgs
Un tableau de InfoMessage décrivant l'utilisateur qui a soumis la commande ainsi que l'environnement d'exécution de la commande. Ces informations sont utilisées pour générer une entrée de journal d'événement et peuvent également être utilisées par le serveur pour déterminer où et comment le journal d'E/S est stocké.
expect_iobufs
Mis à vrai si le serveur doit s'attendre à recevoir des messages IoBuffer par la suite (pour la journalisation des E/S) ou à faux si le serveur ne doit stocker que le journal d'événements.

Si un AcceptMessage est envoyé, le client ne doit pas envoyer de RejectMessage ou de RestartMessage.

RejectMessage reject_msg

message RejectMessage {
  TimeSpec submit_time = 1;
  string reason = 2;
  repeated InfoMessage info_msgs = 3;
}

Un RejectMessage est envoyé par le client lorsqu'une commande est refusée par la politique de sécurité. Il contient les membres suivants :

submit_time
L'heure de l'horloge murale à laquelle la commande a été soumise à la politique de sécurité.
reason
La raison invoquée par la politique de sécurité pour refuser la commande.
info_msgs
Un tableau de InfoMessage décrivant l'utilisateur qui a soumis la commande ainsi que l'environnement d'exécution de la commande. Ces informations sont utilisées pour générer une entrée de journal d'événement.

Si un RejectMessage est envoyé, le client ne doit pas envoyer d'AcceptMessage ou de RestartMessage.

ExitMessage exit_msg

message ExitMessage {
  TimeSpec run_time = 1;
  int32 exit_value = 2;
  bool dumped_core = 3;
  string signal = 4;
  string error = 5;
}

Un ExitMessage est envoyé par le client après que la commande a quitté ou a été terminée par un signal. Il contient les membres suivants :

run_time
La durée totale écoulée depuis le démarrage de la commande, calculée en utilisant une horloge monotone si possible. Ce n'est pas l'heure de l'horloge murale.
exit_value
La valeur de sortie de la commande dans la plage 0-255.
dumped_core
Vrai si la commande a été terminée par un signal et a généré un vidage de noyau (core dump).
signal
Si la commande a été terminée par un signal, ceci est défini sur le nom du signal sans le préfixe “SIG”. Par exemple, INT, TERM, KILL, SEGV.
error
Un message du client indiquant que la commande a été terminée de manière inattendue en raison d'une erreur.

Lors de la journalisation des E/S, le client doit attendre un commit_point correspondant au dernier IoBuffer avant de fermer la connexion, sauf si le dernier commit_point a déjà été reçu.

RestartMessage restart_msg

message RestartMessage {
  string log_id = 1;
  TimeSpec resume_point = 2;
}

Un RestartMessage est envoyé par le client pour reprendre l'envoi d'un journal d'E/S existant qui a été précédemment interrompu. Il contient les membres suivants :

log_id
Le nom côté serveur d'un journal d'E/S qui a été précédemment envoyé au client par le serveur. Il peut s'agir d'un nom de chemin sur le serveur ou d'un autre type d'identifiant côté serveur.
resume_point
Le point dans le temps après lequel reprendre le journal d'E/S. Ceci est sous la forme d'un TimeSpec représentant le temps écoulé depuis le démarrage de la commande, et non l'heure de l'horloge murale. Le resume_point doit correspondre à un commit_point précédemment envoyé au client par le serveur. Si le serveur reçoit un RestartMessage contenant un resume_point qu'il n'a pas vu auparavant, une erreur sera renvoyée au client et la connexion sera fermée.

Si le serveur ne peut pas reprendre le journal d'E/S pour une raison quelconque, il renverra un RejectMessage avec la raison appropriée dans le champ reason. Si le serveur peut reprendre, il renverra un AcceptMessage.

AlertMessage alert_msg

message AlertMessage {
  TimeSpec alert_time = 1;
  string alert_msg = 2;
}

Un AlertMessage est envoyé par le client en cas d'événement qui doit être signalé au responsable de la politique de sécurité. Il contient les membres suivants :

alert_time
L'heure de l'horloge murale à laquelle l'alerte s'est produite.
alert_msg
Le message d'alerte.

IoBuffer

message IoBuffer {
  TimeSpec event_time = 1;
  bytes buffer = 2;
  bool commit_point = 3;
}

Un IoBuffer est utilisé pour envoyer des données lues ou écrites à partir d'un flux d'E/S. Il contient les membres suivants :

event_time
L'heure à laquelle les données ont été lues ou écrites, calculée à l'aide d'une horloge monotone lorsque cela est possible.
buffer
Les données d'E/S elles-mêmes. La taille maximale de ce champ est de 64 kilo-octets.
commit_point
Si mis à vrai, cela indique que la fin du flux d'E/S a été atteinte. Le client doit s'assurer que tous les tampons précédents ont été envoyés avant d'envoyer un IoBuffer avec commit_point=true. Le serveur doit confirmer la réception du tampon en renvoyant un message (par exemple, AcceptMessage ou RejectMessage) lorsque commit_point est vrai.

ChangeWindowSize

message ChangeWindowSize {
  TimeSpec event_time = 1;
  uint32 width = 2;
  uint32 height = 3;
}

Un ChangeWindowSize est envoyé par le client pour signaler que la taille de la fenêtre du terminal a changé. Il contient les membres suivants :

event_time
L'heure à laquelle le changement de taille de la fenêtre s'est produit.
width
La nouvelle largeur de la fenêtre en caractères.
height
La nouvelle hauteur de la fenêtre en lignes.

CommandSuspend

message CommandSuspend {
  TimeSpec event_time = 1;
  bool suspended = 2;
}

Un CommandSuspend est envoyé par le client pour signaler que la commande a été suspendue ou reprise. Il contient les membres suivants :

event_time
L'heure à laquelle la suspension ou la reprise s'est produite.
suspended
Vrai si la commande a été suspendue, faux si elle a été reprise.

Messages Serveur

Un ServerMessage est un conteneur utilisé pour encapsuler tous les types de messages qu'un serveur peut envoyer à un client.

message ServerMessage {
  oneof type {
    ServerChallenge challenge_msg = 1;
    ServerReject reject_msg = 2;
    ServerAccept accept_msg = 3;
    CommitPoint commit_point_msg = 4;
    CloseConnection close_msg = 5;
  }
}

Les différents sous-messages ServerMessage que le serveur peut envoyer au client sont décrits ci-dessous.

ServerChallenge challenge_msg

message ServerChallenge {
  string log_id = 1;
}

Un ServerChallenge est envoyé par le serveur pour demander un redémarrage d'un journal d'E/S existant. Ceci est généralement fait lorsque le serveur est redémarré et que les journaux d'E/S sont conservés. Le champ log_id est le nom côté serveur du journal d'E/S.

ServerReject reject_msg

message ServerReject {
  string reason = 1;
}

Un ServerReject est envoyé par le serveur pour indiquer que le client a été rejeté. Le champ reason contient un message expliquant la raison du rejet.

ServerAccept accept_msg

message ServerAccept {
  TimeSpec accept_time = 1;
}

Un ServerAccept est envoyé par le serveur pour indiquer que le client est accepté. Ceci est généralement envoyé en réponse à un ClientHello ou à un RestartMessage. Le champ accept_time est l'heure à laquelle la commande a été acceptée.

CommitPoint commit_point_msg

message CommitPoint {
  TimeSpec commit_time = 1;
}

Un CommitPoint est envoyé par le serveur pour indiquer qu'un point de synchronisation a été atteint dans le journal d'E/S. Ceci est généralement envoyé en réponse à un IoBuffer avec commit_point=true. Le champ commit_time est l'heure à laquelle le point de synchronisation a été atteint.

CloseConnection close_msg

message CloseConnection {
  string reason = 1;
}

Un CloseConnection est envoyé par le serveur pour indiquer que la connexion doit être fermée. Le champ reason contient un message expliquant la raison de la fermeture.

VARIABLES DU JOURNAL D'ÉVÉNEMENTS

Les variables suivantes peuvent être utilisées dans les messages InfoMessage pour fournir des informations sur l'utilisateur, l'environnement et la commande exécutée.

Variables relatives à l'utilisateur :

  • USERlogin : Nom de connexion de l'utilisateur.
  • USERid : ID utilisateur (UID) de l'utilisateur.
  • USERgroups : Liste des groupes dont fait partie l'utilisateur.
  • USERhomedir : Répertoire personnel de l'utilisateur.
  • USERshell : Shell par défaut de l'utilisateur.
  • USERrealgroups : Liste des groupes réels dont fait partie l'utilisateur.
  • USERrealgroupschecked : Indique si les groupes réels ont été vérifiés.

Variables relatives à l'environnement :

  • SHELL : Valeur de la variable d'environnement SHELL.
  • TERM : Valeur de la variable d'environnement TERM.
  • PATH : Valeur de la variable d'environnement PATH.
  • PWD : Répertoire de travail actuel.
  • HOME : Répertoire personnel de l'utilisateur.
  • LANG : Valeur de la variable d'environnement LANG.
  • LC_CTYPE : Valeur de la variable d'environnement LC_CTYPE.
  • LC_NUMERIC : Valeur de la variable d'environnement LC_NUMERIC.
  • LC_TIME : Valeur de la variable d'environnement LC_TIME.
  • LC_COLLATE : Valeur de la variable d'environnement LC_COLLATE.
  • LC_MONETARY : Valeur de la variable d'environnement LC_MONETARY.
  • LC_MESSAGES : Valeur de la variable d'environnement LC_MESSAGES.
  • TZ : Valeur de la variable d'environnement TZ.
  • HOST : Nom d'hôte de la machine.
  • COMMANDRUN : Commande exécutée.
  • NLSPATH : Valeur de la variable d'environnement NLSPATH.

Variables relatives à la commande :

  • ARGV : Tableau des arguments de la commande.
  • CMND : Chemin complet de la commande exécutée.
  • SETENV : Indique si la commande a modifié les variables d'environnement.
  • IOMMU : Informations sur l'I/O MMU.
  • CORE : Informations sur le core dump.

Variables spécifiques à Sudo :

  • SUDOcmd : Chemin de l'exécutable sudo.
  • SUDOversion : Version de sudo.
  • SUDOtty : Terminal pseudo du client sudo.
  • SUDOargs : Arguments passés à sudo.
  • SUDO_UID : ID utilisateur du propriétaire du tty.
  • SUDO_USER : Nom d'utilisateur du propriétaire du tty.
  • SUDO_PS : ID du processus de sudo.
  • SUDO_GID : ID groupe du propriétaire du tty.
  • SUDO_PROMPT : Invite sudo.
  • SUDO_LOGIN : Nom de connexion sudo.

EXEMPLES

Le fichier /etc/sudo_logsrv.proto contient la définition du protocole en format Protocol Buffers.

syntax = "proto3";

import "google/protobuf/timestamp.proto";

package sudo;

// Message global pour les clients
message ClientMessage {
  oneof type {
    AcceptMessage accept_msg = 1;
    RejectMessage reject_msg = 2;
    ExitMessage exit_msg = 3;
    RestartMessage restart_msg = 4;
    AlertMessage alert_msg = 5;
    IoBuffer ttyin_buf = 6;
    IoBuffer ttyout_buf = 7;
    IoBuffer stdin_buf = 8;
    IoBuffer stdout_buf = 9;
    IoBuffer stderr_buf = 10;
    ChangeWindowSize winsize_event = 11;
    CommandSuspend suspend_event = 12;
    ClientHello hello_msg = 13;
  }
}

// Message global pour les serveurs
message ServerMessage {
  oneof type {
    ServerChallenge challenge_msg = 1;
    ServerReject reject_msg = 2;
    ServerAccept accept_msg = 3;
    CommitPoint commit_point_msg = 4;
    CloseConnection close_msg = 5;
  }
}

// Spécification de temps POSIX
message TimeSpec {
    int64 tv_sec = 1;
    int32 tv_nsec = 2;
}

// Message d'information (clé-valeur)
message InfoMessage {
  message StringList {
    repeated string strings = 1;
  }
  message NumberList {
    repeated int64 numbers = 1;
  }
  string key = 1;
  oneof value {
    int64 numval = 2;
    string strval = 3;
    StringList strlistval = 4;
    NumberList numlistval = 5;
  }
}

// Message de salut du client
message ClientHello {
  string client_id = 1;
}

// Message d'acceptation de commande
message AcceptMessage {
  TimeSpec submit_time = 1;
  repeated InfoMessage info_msgs = 2;
  bool expect_iobufs = 3;
}

// Message de refus de commande
message RejectMessage {
  TimeSpec submit_time = 1;
  string reason = 2;
  repeated InfoMessage info_msgs = 3;
}

// Message de sortie de commande
message ExitMessage {
  TimeSpec run_time = 1;
  int32 exit_value = 2;
  bool dumped_core = 3;
  string signal = 4;
  string error = 5;
}

// Message de redémarrage de journal
message RestartMessage {
  string log_id = 1;
  TimeSpec resume_point = 2;
}

// Message d'alerte
message AlertMessage {
  TimeSpec alert_time = 1;
  string alert_msg = 2;
}

// Tampon d'E/S
message IoBuffer {
  TimeSpec event_time = 1;
  bytes buffer = 2;
  bool commit_point = 3;
}

// Changement de taille de fenêtre
message ChangeWindowSize {
  TimeSpec event_time = 1;
  uint32 width = 2;
  uint32 height = 3;
}

// Suspension de commande
message CommandSuspend {
  TimeSpec event_time = 1;
  bool suspended = 2;
}

// Défi du serveur
message ServerChallenge {
  string log_id = 1;
}

// Rejet du serveur
message ServerReject {
  string reason = 1;
}

// Acceptation du serveur
message ServerAccept {
  TimeSpec accept_time = 1;
}

// Point de validation du serveur
message CommitPoint {
  TimeSpec commit_time = 1;
}

// Fermeture de connexion du serveur
message CloseConnection {
  string reason = 1;
}

CLIENT MESSAGES

Un ClientMessage est un conteneur utilisé pour encapsuler tous les types de messages possibles que le client peut envoyer au serveur.

message ClientMessage {
  oneof type {
    ClientHello hello = 1;
    AcceptMessage accept = 2;
    RejectMessage reject = 3;
    RestartMessage restart = 4;
    AlertMessage alert = 5;
    IoBuffer ttyin = 6;
    IoBuffer ttyout = 7;
    IoBuffer stdin = 8;
    IoBuffer stdout = 9;
    IoBuffer stderr = 10;
    ChangeWindowSize resize = 11;
    CommandSuspend suspend = 12;
    ExitMessage exit = 13;

Les différents sous-messages ClientMessage que le client peut envoyer au serveur sont décrits ci-dessous.

ClientHello hello

message ClientHello {
  string client_id = 1;
}

Le message ClientHello est envoyé par le client immédiatement après la connexion au serveur. Il contient les membres suivants :

client_id
Une description libre du client. Il s'agit généralement du nom et de la version de l'implémentation s'exécutant sur le client.

AcceptMessage accept

message AcceptMessage {
  TimeSpec accept_time = 1;
  string log_id = 2;
  bool expect_iobufs = 3;
  repeated InfoMessage info_msgs = 4;
}

Un AcceptMessage est envoyé par le client pour indiquer que la commande est autorisée à s'exécuter. Il contient les membres suivants :

accept_time
L'heure de réception du message par le serveur.
log_id
L'identifiant du journal d'E/S, généré par le serveur.
expect_iobufs
Indique si le serveur attend des messages IoBuffer. Si cette valeur est définie, le client doit envoyer les données d'E/S sous forme de messages IoBuffer.
info_msgs
Un tableau facultatif de InfoMessage décrivant l'utilisateur qui a soumis la commande ainsi que l'environnement d'exécution de la commande. Ces informations sont utilisées pour générer une entrée dans le journal d'événements.

Un RejectMessage est envoyé par le client pour indiquer que la commande n'est pas autorisée à s'exécuter. Il contient les membres suivants :

reject_time
L'heure de réception du message par le serveur.
reason
La raison pour laquelle la commande a été rejetée.
info_msgs
Un tableau facultatif de InfoMessage décrivant l'utilisateur qui a soumis la commande ainsi que l'environnement d'exécution de la commande. Ces informations sont utilisées pour générer une entrée dans le journal d'événements.

  TimeSpec restart_time = 1;
  string reason = 2;
  string host = 3;
  int32 port = 4;
}

Un RestartMessage est envoyé par le client pour demander au serveur de redémarrer la session de journalisation sur un autre serveur. Il contient les membres suivants :

restart_time
L'heure de réception du message par le serveur.
reason
La raison pour laquelle le redémarrage est demandé.
host
Le nom d'hôte du nouveau serveur.
port
Le port du nouveau serveur.

message AlertMessage {
  TimeSpec alert_time = 1;
  string reason = 2;
  repeated InfoMessage info_msgs = 3;
}

Un AlertMessage est envoyé par le client pour indiquer un problème détecté par la politique de sécurité pendant l'exécution de la commande qui doit être stocké dans le journal d'événements. Il contient les membres suivants :

alert_time
L'heure de l'horloge murale à laquelle l'alerte s'est produite.
reason
La raison de l'alerte.
info_msgs
Un tableau facultatif de InfoMessage décrivant l'utilisateur qui a soumis la commande ainsi que l'environnement d'exécution de la commande. Ces informations sont utilisées pour générer une entrée dans le journal d'événements.

IoBuffer ttyin_buf | ttyout_buf | stdin_buf | stdout_buf | stderr_buf

message IoBuffer {
  TimeSpec delay = 1;

Un IoBuffer est utilisé pour représenter les données d'entrée du terminal, de sortie du terminal, d'entrée standard, de sortie standard ou d'erreur standard. Il contient les membres suivants :

data
Les données binaires du journal d'E/S provenant de l'entrée du terminal, de la sortie du terminal, de l'entrée standard, de la sortie standard ou de l'erreur standard.

Un message ExitMessage est envoyé par le client lorsque la commande se termine. Il contient les membres suivants :

delay
Le temps écoulé depuis le dernier enregistrement sous la forme d'un TimeSpec. Le delay doit être calculé à l'aide d'une horloge monotone si possible.
signal
Le nom du signal, le cas échéant, qui a provoqué la terminaison de la commande. S'il n'y a pas eu de signal, ce champ sera vide.
exit_status
Le code de sortie de la commande. Si la commande a été terminée par un signal, ce champ contiendra la valeur 128 plus le numéro du signal.

Server Messages

Un ServerMessage est un conteneur utilisé pour encapsuler tous les types de messages possibles que le serveur peut envoyer à un client.

message ServerMessage {
  oneof type {
    ServerHello hello = 1;
    TimeSpec commit_point = 2;
    string log_id = 3;
    string error = 4;
    string abort = 5;
  }
}

Les différents sous-messages ServerMessage que le serveur peut envoyer au client sont décrits ci-dessous.

ServerHello hello

message ServerHello {
  string server_id = 1;
  string redirect = 2;
  repeated string servers = 3;
  bool subcommands = 4;
}

Le message ServerHello consiste en des informations du serveur envoyées lorsque le client se connecte pour la première fois. Il contient les membres suivants :

server_id
Une description libre du serveur. Cela inclut généralement le nom et la version de l'implémentation exécutée sur le serveur de journalisation. Ce membre est toujours présent.
redirect
Un hôte et un port séparés par deux-points (‘’) : auquel le client doit se connecter à la place. L'hôte peut être un nom d'hôte, une adresse IPv4 ou une adresse IPv6 entre crochets. Cela peut être utilisé pour l'équilibrage de charge du serveur. Le serveur se déconnectera après l'envoi de ServerHello lorsqu'il inclut un redirect.
servers
Une liste d'autres serveurs de journalisation connus. Cela peut être utilisé pour implémenter la redondance des serveurs de journalisation et permet au client de découvrir tous les autres serveurs de journalisation simplement en se connectant à un serveur connu. Ce membre peut être omis lorsqu'il n'y a qu'un seul serveur de journalisation.
subcommands
Si défini, le serveur prend en charge la journalisation des commandes supplémentaires pendant une session. Le client peut envoyer un AcceptMessage ou un RejectMessage lorsque sudo est exécuté en mode intercept. Dans ce mode, les commandes lancées à partir de la commande initiale autorisée par sudo sont soumises à des restrictions de politique et/ou sont journalisées. Si subcommands est faux, le client ne doit pas tenter de journaliser des commandes supplémentaires.

TimeSpec commit_point

Un horodatage périodique envoyé par le serveur pour indiquer quand les tampons de journal d'E/S ont été validés dans le stockage. Ce message n'est pas envoyé après chaque IoBuffer mais plutôt à un intervalle configurable par le serveur. Lorsque le serveur reçoit un ExitMessage, il répondra avec un commit_point correspondant au dernier IoBuffer reçu avant de fermer la connexion.

string log_id

L'identifiant côté serveur du journal d'E/S en cours de stockage, envoyé en réponse à un AcceptMessage où expect_iobufs est vrai.

string error

Une erreur fatale côté serveur. Le serveur fermera la connexion après l'envoi du message error.

string abort

Un message abort du serveur indique que le client doit tuer la commande et terminer la session. Il peut être utilisé pour implémenter une politique simple côté serveur. Le serveur fermera la connexion après l'envoi du message abort.

Protocol flow of control

Le flux de protocole attendu est le suivant :

  1. Le client se connecte au premier serveur disponible. Si le client est configuré pour utiliser TLS, une négociation TLS sera tentée.
  2. Le client envoie ClientHello. Ceci est facultatif pour le moment, mais permet au serveur de détecter une connexion non TLS sur le port TLS.
  3. Le serveur envoie ServerHello.
  4. Le client répond avec AcceptMessage, RejectMessage, ou RestartMessage.
  5. Si le client a envoyé un AcceptMessage avec expect_iobufs défini, le serveur crée un nouveau journal d'E/S et répond avec un log_id.
  6. Le client envoie zéro ou plusieurs messages IoBuffer.
  7. Le serveur répond périodiquement aux messages IoBuffer avec un commit_point.
  8. Le client envoie un ExitMessage lorsque la commande se termine ou est tuée.
  9. Le serveur envoie le commit_point final s'il y en a un en attente.
  10. Le serveur ferme la connexion. Après avoir reçu le commit_point final, le client arrête sa partie de la connexion TLS, si TLS est utilisé, et ferme la connexion.
  11. Le serveur arrête sa partie de la connexion TLS, si TLS est utilisé, et ferme la connexion.

À tout moment, le serveur peut envoyer un message error ou abort au client, auquel cas le serveur fermera la connexion. Si un message abort est reçu, le client doit terminer la commande en cours d'exécution.

EVENT LOG VARIABLES

AcceptMessage, AlertMessage et RejectMessage contiennent un tableau de InfoMessage qui devraient contenir des informations sur l'utilisateur ayant soumis la commande ainsi que des informations sur l'environnement d'exécution de la commande si elle a été acceptée.

Certaines variables ont un préfixe client, run ou submit. Ces préfixes sont utilisés pour éliminer l'ambiguïté des variables qui pourraient s'appliquer au programme client, à l'utilisateur soumettant la commande, ou à la commande en cours d'exécution. Les variables avec un préfixe client concernent le programme effectuant la connexion au serveur de journalisation, par exemple sudo. Les variables avec un préfixe run concernent la commande que l'utilisateur a demandé d'exécuter. Les variables avec un préfixe submit concernent l'utilisateur soumettant la requête (l'utilisateur exécutant sudo).

Les entrées InfoMessage suivantes sont obligatoires :

Key Type Description
client_name string Nom d'hôte du client.
client_tty string Terminal du client.
command string Commande exécutée.
login_name string Nom de connexion de l'utilisateur.
submit_host string Hôte depuis lequel la commande a été soumise.
submit_tty string Terminal depuis lequel la commande a été soumise.

Les entrées InfoMessage suivantes sont facultatives :

accept_time TimeSpec Heure d'acceptation de la commande.
cols int32 Nombre de colonnes dans le terminal.
rows int32 Nombre de lignes dans le terminal.
env map<string, string> Variables d'environnement.
exit_status int32 Code de sortie de la commande.
run_as_login_name string Nom de connexion sous lequel la commande sera exécutée.
run_as_uid int32 ID utilisateur sous lequel la commande sera exécutée.
run_as_gid int32 ID groupe sous lequel la commande sera exécutée.
signal string Signal ayant terminé la commande.
umask int32 Umask de l'utilisateur au moment de la soumission.
cwd string Répertoire de travail actuel.
tty_present bool Indique si une E/S de type TTY est présente.

En plus des variables ci-dessus, les messages d'AlertMessage et de RejectMessage peuvent contenir une variable reason expliquant pourquoi l'alerte ou le rejet a eu lieu.

Le serveur de journalisation peut également injecter des variables supplémentaires dans le journal d'événements. Le nom de ces variables est précédé du préfixe server_ pour éviter toute ambiguïté.

Le format exact des journaux d'événements n'est pas défini ici. Il est à la discrétion de l'implémentation du serveur et du client.

Description

The following InfoMessage entries are recognized, but not required:

Clé Type Description
clientargv StringList Vecteur d'arguments d'origine du client
clientpid int64 ID de processus du client
clientppid int64 ID du processus parent du client
clientsid int64 ID de session du terminal du client
columns int64 nombre de colonnes dans le terminal
lines int64 nombre de lignes dans le terminal
runargv StringList vecteur d'arguments de la commande à exécuter
runchroot string répertoire racine de la commande à exécuter
runcwd string répertoire de travail de la commande en cours d'exécution
runenv StringList environnement de la commande en cours d'exécution
rungid int64 ID du groupe principal de la commande
rungids NumberList IDs des groupes supplémentaires pour la commande
rungroup string nom du groupe principal de la commande
rungroups StringList noms des groupes supplémentaires pour la commande
runuid int64 ID utilisateur de l'utilisateur qui exécute
submitcwd string répertoire de travail de l'utilisateur soumettant
submitenv StringList environnement de l'utilisateur soumettant
submitgid int64 ID du groupe principal de l'utilisateur soumettant
submitgids NumberList IDs des groupes supplémentaires de l'utilisateur soumettant
submitgroup string nom du groupe principal de l'utilisateur soumettant
submitgroups StringList noms des groupes supplémentaires de l'utilisateur soumettant
submituid int64 ID utilisateur de l'utilisateur soumettant
ttyname string terminal depuis lequel la commande a été soumise

Le serveur doit accepter d'autres variables non listées ci-dessus mais peut les ignorer.

Exemples

La description des Protocol Buffers du protocole de serveur de logs, utilisant la syntaxe « proto3 », est incluse ci-dessous dans son intégralité.

syntax = "proto3";

/*
 * Message client au serveur. Les messages sur le fil sont
 * précédés d'une taille de 32 bits en ordre d'octets réseau.
 */
message ClientMessage {
  oneof type {
    AcceptMessage accept_msg = 1;
    RejectMessage reject_msg = 2;
    ExitMessage exit_msg = 3;
    RestartMessage restart_msg = 4;
    AlertMessage alert_msg = 5;
    IoBuffer ttyin_buf = 6;
    IoBuffer ttyout_buf = 7;
    IoBuffer stdin_buf = 8;
    IoBuffer stdout_buf = 9;
    IoBuffer stderr_buf = 10;
    ChangeWindowSize winsize_event = 11;
    CommandSuspend suspend_event = 12;
  }
}

/* Équivalent de la structure POSIX timespec */
message TimeSpec {
    int64 tv_sec = 1;		/* secondes */
    int32 tv_nsec = 2;		/* nanosecondes */
}

/* Buffer d'E/S avec données de frappe */
message IoBuffer {
  TimeSpec delay = 1;		/* temps écoulé depuis le dernier enregistrement */
  bytes data = 2;		/* données de frappe */
}

/*
 * Paires clé/valeur, comme les informations de la structure Privilege Manager.
 * La valeur peut être un nombre, une chaîne ou une liste de chaînes.
 */
message InfoMessage {
  message StringList {
    repeated string strings = 1;
  }
  message NumberList {
    repeated int64 numbers = 1;
  }
  string key = 1;
  oneof value {
    int64 numval = 2;
    string strval = 3;
    StringList strlistval = 4;
    NumberList numlistval = 5;
  }
}

/*
 * Données de journalisation d'événements pour la commande acceptée par la politique.
 */
message AcceptMessage {
  TimeSpec submit_time = 1;		/* heure à laquelle la commande a été soumise */
  repeated InfoMessage info_msgs = 2;	/* données de journalisation d'événements clé, valeur */
  bool expect_iobufs = 3;		/* vrai si la journalisation des E/S est activée */
}

/*
 * Données de journalisation d'événements pour la commande rejetée par la politique.
 */
message RejectMessage {
  TimeSpec submit_time = 1;		/* heure à laquelle la commande a été soumise */
  string reason = 2;			/* raison du rejet de la commande */
  repeated InfoMessage info_msgs = 3;	/* données de journalisation d'événements clé, valeur */
}

/* Message envoyé par le client lorsque la commande se termine. */
/* On pourrait revoir runtime et utiliser end_time à la place */
message ExitMessage {
  TimeSpec run_time = 1;	/* temps d'exécution écoulé total */
  int32 exit_value = 2;		/* 0-255 */
  bool dumped_core = 3;		/* vrai si la commande a généré un core dump */
  string signal = 4;		/* nom du signal si la commande a été tuée par un signal */
  string error = 5;		/* si tuée pour une autre raison */
}

/* Message d'alerte, spécifique au module de politique. */
message AlertMessage {
  TimeSpec alert_time = 1;		/* heure à laquelle le message d'alerte s'est produit */
  string reason = 2;			/* chaîne d'erreur d'alerte de politique */
  repeated InfoMessage info_msgs = 3;	/* données de journalisation d'événements clé, valeur */
}

/* Utilisé pour redémarrer un journal d'E/S existant sur le serveur. */
message RestartMessage {
  string log_id = 1;		/* ID du journal en cours de redémarrage */
  TimeSpec resume_point = 2;	/* point de reprise (temps écoulé) */
}

/* Événement de changement de taille de fenêtre. */
message ChangeWindowSize {
  TimeSpec delay = 1;		/* temps écoulé depuis le dernier enregistrement */
  int32 rows = 2;		/* nouveau nombre de lignes */
  int32 cols = 3;		/* nouveau nombre de colonnes */
}

/* Événement de suspension/reprise de commande. */
message CommandSuspend {
  TimeSpec delay = 1;		/* temps écoulé depuis le dernier enregistrement */
  string signal = 2;		/* signal qui a causé la suspension/reprise */
}

/*
 * Messages serveur au client. Les messages sur le fil sont
 * précédés d'une taille de 32 bits en ordre d'octets réseau.
 */
message ServerMessage {
  oneof type {
    ServerHello hello = 1;	/* message hello du serveur */
    TimeSpec commit_point = 2;	/* temps cumulé des enregistrements stockés */
    string log_id = 3;		/* ID du journal d'E/S côté serveur */
    string error = 4;		/* message d'erreur du serveur */
    string abort = 5;		/* message d'abandon, tuer la commande */
  }
}

/* Message Hello du serveur lors de la connexion du client. */
message ServerHello {
  string server_id = 1;		/* description libre du serveur */
  string redirect = 2;		/* redirection optionnelle si occupé */
  repeated string servers = 3;	/* liste optionnelle de serveurs connus */
}
