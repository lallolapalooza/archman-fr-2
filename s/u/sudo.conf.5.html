SUDO.CONF(5) Manuel des formats de fichiers SUDO.CONF(5)

NOM

sudo.conf — configuration du frontal sudo

DESCRIPTION

Le fichier sudo.conf est utilisé pour configurer le frontal sudo. Il est utilisé pour configurer les plugins sudo, les chemins d'accès indépendants des plugins, les indicateurs de débogage et d'autres paramètres.

Le fichier sudo.conf prend en charge les directives suivantes, décrites en détail ci-dessous.

Plugin
un plugin d'approbation, d'audit, de journalisation des E/S ou de politique de sécurité
Path
un chemin d'accès indépendant des plugins
Set
un paramètre du frontal, tel que disable_coredump ou group_source
Debug
des indicateurs de débogage pour aider au débogage de sudo, sudoreplay, visudo, et du plugin sudoers.

Le signe dièse (‘#’) est utilisé pour indiquer un commentaire. Le caractère de commentaire et tout texte après celui-ci, jusqu'à la fin de la ligne, sont ignorés.

Les lignes longues peuvent être poursuivies avec une barre oblique inversée (‘\’) comme dernier caractère de la ligne. Les espaces blancs en début de ligne sont supprimés, même lorsqu'un caractère de continuation est utilisé.

Les lignes qui ne sont pas des commentaires et qui ne commencent pas par Plugin, Path, Debug, ou Set sont ignorées silencieusement.

Le fichier sudo.conf est toujours analysé dans l'environnement local ‘C’.

Configuration des plugins

sudo prend en charge une architecture de plugins pour les politiques de sécurité et la journalisation des entrées/sorties. Des tiers peuvent développer et distribuer leurs propres plugins de politique et de journalisation E/S pour fonctionner de manière transparente avec le frontal sudo. Les plugins sont chargés dynamiquement en fonction du contenu de sudo.conf.

Une ligne Plugin se compose du mot-clé Plugin, suivi du nom_symbole et du chemin d'accès à l'objet partagé dynamique contenant le plugin. Le nom_symbole est le nom de la struct approval_plugin, struct audit_plugin, struct io_plugin, ou struct policy_plugin définie par le plugin. Si un plugin implémente plusieurs types de plugins, il doit y avoir une ligne Plugin pour chaque nom de symbole unique. Le chemin d'accès peut être qualifié entièrement ou relatif. S'il n'est pas qualifié entièrement, il est relatif au répertoire spécifié par le paramètre plugin_dir Path, qui par défaut est /usr/lib/sudo. En d'autres termes :

Plugin sudoers_policy sudoers.so

est équivalent à :

Plugin sudoers_policy /usr/lib/sudo/sudoers.so

Si le plugin a été compilé statiquement dans le binaire sudo au lieu d'être installé comme objet partagé dynamique, le chemin d'accès doit être spécifié sans répertoire de tête, car il n'existe pas réellement dans le système de fichiers. Par exemple :

Plugin sudoers_policy sudoers.so

Sur les systèmes AIX, le plugin peut être soit un objet partagé se terminant par ‘.so’, soit un fichier archive contenant un objet partagé se terminant par ‘.a’ avec le nom de l'objet partagé entre parenthèses à la fin.

À partir de sudo 1.8.5, tous les paramètres supplémentaires après le chemin d'accès sont passés comme arguments à la fonction open du plugin. Par exemple, pour remplacer le mode par défaut du fichier sudoers défini à la compilation :

Plugin sudoers_policy sudoers.so sudoers_mode=0440

Voir le manuel sudoers(5) pour une liste des arguments pris en charge.

Le même objet partagé dynamique peut contenir plusieurs plugins, chacun avec un nom de symbole différent. Le fichier doit appartenir à l'utilisateur ID 0 et être inscriptible uniquement par son propriétaire. En raison des ambiguïtés qui surviennent avec les politiques composites, un seul plugin de politique peut être spécifié. Cette limitation ne s'applique pas aux plugins E/S.

Si aucun fichier sudo.conf n'est présent, ou s'il ne contient aucune ligne Plugin, le plugin sudoers sera utilisé comme politique de sécurité par défaut, pour la journalisation des E/S (si activée par la politique) et pour l'audit. Ceci est équivalent à ce qui suit :

Plugin sudoers_policy sudoers.so
Plugin sudoers_io sudoers.so
Plugin sudoers_audit sudoers.so

À partir de sudo version 1.9.1, une partie de la fonctionnalité de journalisation du plugin sudoers a été déplacée du plugin de politique vers un plugin d'audit. Pour maintenir la compatibilité avec les fichiers sudo.conf des versions plus anciennes de sudo, si sudoers est configuré comme politique de sécurité, il sera également utilisé comme plugin d'audit. Cela garantit que le comportement de journalisation sera cohérent avec celui des versions de sudo 1.9.0 et inférieures.

Pour plus d'informations sur l'architecture des plugins sudo, voir le manuel sudo_plugin(5).

Paramètres de chemin

Une ligne Path se compose du mot-clé Path, suivi du nom du chemin à définir et de sa valeur. Par exemple :

Path intercept /usr/lib/sudo/sudo_intercept.so
Path noexec /usr/lib/sudo/sudo_noexec.so
Path askpass /usr/X11R6/bin/ssh-askpass

Si aucun nom de chemin n'est spécifié, les fonctionnalités qui dépendent du paramètre spécifié seront désactivées. La désactivation des paramètres Path n'est prise en charge qu'à partir de sudo version 1.8.16 et supérieure.

Les chemins d'accès suivants, indépendants des plugins, peuvent être définis dans le fichier /etc/sudo.conf :

askpass
Le chemin d'accès complet à un programme auxiliaire utilisé pour lire le mot de passe de l'utilisateur lorsqu'aucun terminal n'est disponible. Cela peut être le cas lorsque sudo est exécuté à partir d'une application graphique (par opposition à une application textuelle). Le programme spécifié par askpass doit afficher l'argument qui lui est passé comme invite et écrire le mot de passe de l'utilisateur sur la sortie standard. La valeur de askpass peut être remplacée par la variable d'environnement SUDO_ASKPASS.
devsearch
Un chemin de recherche ordonné et séparé par des deux-points des répertoires à rechercher pour trouver les nœuds de périphériques. Ceci est utilisé lors du mappage du numéro de périphérique tty du processus à un nom de périphérique sur les systèmes qui ne fournissent pas un tel mécanisme. Sudo ne récursera pas dans les sous-répertoires. Si les périphériques terminaux peuvent être situés dans un sous-répertoire de /dev, ce chemin doit être explicitement listé dans devsearch. La valeur par défaut est /dev/pts:/dev/vt:/dev/term:/dev/zcons:/dev/pty:/dev

Cette option est ignorée sur les systèmes qui prennent en charge les fonctions devname() ou _ttyname_dev(), par exemple BSD, macOS et Solaris.

intercept
Le chemin d'accès à une bibliothèque partagée contenant des wrappers pour les fonctions de bibliothèque execve(2), execl(3), execle(3), execlp(3), execv(3), execvp(3), execvpe(3), et system(3) qui intercepte

Le chemin intercept peut être défini sur un chemin unique entièrement qualifié, ou, pour les systèmes qui prennent en charge des variables d'environnement LD_PRELOAD distinctes pour les exécutables 32 bits et 64 bits, il peut éventuellement être défini sur deux chemins entièrement qualifiés séparés par deux points (‘:’). Le premier chemin doit être la version 32 bits et le second la version 64 bits. Cette forme à deux chemins n'est actuellement prise en charge que sur les systèmes AIX et Solaris. La valeur par défaut est /usr/lib/sudo/sudo_intercept.so.

noexec
Le chemin vers une bibliothèque partagée contenant des wrappers pour les fonctions de bibliothèque execve(2), execl(3), execle(3), execlp(3), exect(3), execv(3), execveat(3), execvP(3), execvp(3), execvpe(3), fexecve(3), popen(3), posix_spawn(3), posix_spawnp(3), system(3) et wordexp(3) qui empêchent l'exécution d'autres commandes. Ceci est utilisé pour implémenter la fonctionnalité noexec sur les systèmes qui prennent en charge LD_PRELOAD ou son équivalent.

Le chemin noexec peut être défini sur un chemin unique entièrement qualifié, ou, pour les systèmes qui prennent en charge des variables d'environnement LD_PRELOAD distinctes pour les exécutables 32 bits et 64 bits, il peut éventuellement être défini sur deux chemins entièrement qualifiés séparés par deux points (‘:’). Le premier chemin doit être la version 32 bits et le second la version 64 bits. Cette forme à deux chemins n'est actuellement prise en charge que sur les systèmes AIX et Solaris. La valeur par défaut est /usr/lib/sudo/sudo_noexec.so.

plugin_dir
Le répertoire par défaut à utiliser lors de la recherche de plugins spécifiés sans nom de chemin entièrement qualifié. La valeur par défaut est /usr/lib/sudo.

Autres paramètres

Le fichier sudo.conf prend également en charge les paramètres frontaux suivants :

disable_coredump
Les vidages de mémoire de sudo lui-même sont désactivés par défaut pour éviter la divulgation d'informations potentiellement sensibles. Pour faciliter le débogage des plantages de sudo, vous pourriez souhaiter réactiver les vidages de mémoire en définissant « disable_coredump » sur false dans sudo.conf comme suit : 
Set disable_coredump false

Tous les systèmes d'exploitation modernes imposent des restrictions sur les vidages de mémoire des processus set-user-ID comme sudo, cette option peut donc être activée sans compromettre la sécurité. Pour réellement obtenir un fichier de vidage de mémoire de sudo, vous devrez probablement activer les vidages de mémoire pour les processus set-user-ID. Sur les systèmes BSD et Linux, cela est accompli avec la commande sysctl(8). Sur Solaris, la commande coreadm(1m) est utilisée pour configurer le comportement des vidages de mémoire.

Ce paramètre n'est disponible que dans la version sudo 1.8.4 et supérieure.

group_source
sudo transmet la liste des groupes de l'utilisateur appelant aux plugins de stratégie et d'E/S. Sur la plupart des systèmes, il existe une limite supérieure au nombre de groupes auxquels un utilisateur peut appartenir simultanément (typiquement 16 pour la compatibilité avec NFS). Sur les systèmes dotés de l'utilitaire getconf(1), l'exécution de :
getconf NGROUPS_MAX
renverra le nombre maximum de groupes.

Cependant, il est toujours possible d'être membre d'un plus grand nombre de groupes ; ils ne seront simplement pas inclus dans la liste des groupes renvoyée par le noyau pour l'utilisateur. À partir de la version sudo 1.8.7, si la liste des groupes du noyau de l'utilisateur contient le nombre maximum d'entrées, sudo consultera directement la base de données des groupes pour déterminer la liste des groupes. Cela permet à la politique de sécurité d'effectuer une correspondance par nom de groupe même lorsque l'utilisateur est membre de plus que le nombre maximum de groupes.

Le paramètre group_source permet à l'administrateur de modifier ce comportement par défaut. Les valeurs prises en charge pour group_source sont :

static
Utiliser la liste statique des groupes renvoyée par le noyau. La récupération de la liste des groupes de cette manière est très rapide mais elle est soumise à une limite supérieure comme décrit ci-dessus. Elle est "statique" dans le sens où elle ne reflète pas les modifications apportées à la base de données des groupes après la connexion de l'utilisateur. C'était le comportement par défaut avant sudo 1.8.7.
dynamic
Interroger systématiquement la base de données des groupes directement. Elle est "dynamique" dans le sens où les modifications apportées à la base de données des groupes après la connexion de l'utilisateur seront reflétées dans la liste des groupes. Sur certains systèmes, l'interrogation de la base de données des groupes pour tous les groupes d'un utilisateur peut prendre du temps lors de l'interrogation d'une base de données de groupes basée sur le réseau. La plupart des systèmes d'exploitation fournissent une méthode efficace pour effectuer de telles requêtes. Actuellement, sudo prend en charge les requêtes de groupes efficaces sur AIX, BSD, Linux, macOS et Solaris. C'est le comportement par défaut sur macOS dans sudo 1.9.6 et supérieur.
adaptive
Interroger uniquement la base de données des groupes si la liste statique des groupes renvoyée par le noyau contient le nombre maximum d'entrées. C'est le comportement par défaut sur les systèmes autres que macOS dans sudo 1.8.7 et supérieur.

Par exemple, pour que sudo utilise uniquement la liste statique des groupes du noyau pour l'utilisateur :

Set group_source static

Ce paramètre n'est disponible que dans la version sudo 1.8.7 et supérieure.

max_groups
Le nombre maximum de groupes d'utilisateurs à récupérer de la base de données des groupes. Les valeurs inférieures à un ou supérieures à 1024 seront ignorées. Ce paramètre n'est utilisé que lors de l'interrogation de la base de données des groupes directement. Il est destiné à être utilisé sur les systèmes où il n'est pas possible de détecter quand le tableau à remplir avec les entrées de groupe n'est pas suffisamment grand. Par défaut, sudo allouera quatre fois le nombre maximum de groupes du système (voir ci-dessus) et réessaiera avec le double de ce nombre si la requête de base de données de groupes échoue.

Ce paramètre n'est disponible que dans la version sudo 1.8.7 et supérieure. Il ne devrait pas être nécessaire dans les versions sudo 1.8.24 et supérieures et pourrait être supprimé dans une future version.

probe_interfaces
Par défaut, sudo interroge les interfaces réseau du système et transmet l'adresse IP de chaque interface activée au plugin de politique. Cela permet au plugin de faire correspondre des règles basées sur l'adresse IP sans avoir à interroger DNS. Sur les systèmes Linux avec un grand nombre d'interfaces virtuelles, cela peut prendre un temps non négligeable. Si la correspondance basée sur IP n'est pas requise, l'interrogation des interfaces réseau peut être désactivée comme suit : 
Set probe_interfaces false

Ce paramètre n'est disponible que dans la version sudo 1.8.10 et supérieure.

Paramètres de débogage

sudo versions 1.8.4 et supérieures prennent en charge un cadre de débogage flexible qui peut enregistrer ce que sudo fait en interne en cas de problème.

Une ligne Debug se compose du mot-clé Debug, suivi du nom du programme, du plugin ou de l'objet partagé à déboguer, du nom du fichier de débogage et d'une liste séparée par des virgules de drapeaux de débogage. La syntaxe du drapeau de débogage utilisée par sudo, le plugin sudoers ainsi que ses programmes et objets partagés associés est subsystem@priority mais un plugin tiers est libre d'utiliser un format différent tant qu'il n'inclut pas de virgule (‘,’).

Sur les systèmes AIX, une ligne Debug correspondra à un plugin spécifié comme étant soit le nom d'un fichier d'objet partagé de style SVR4 se terminant par ‘.so’, un fichier archive se terminant par ‘.a’, soit un fichier archive se terminant par ‘.a’ avec le nom de l'objet partagé entre parenthèses.

Exemples :

Debug sudo /var/log/sudo_debug all@warn,plugin@info

enregistrerait toutes les instructions de débogage au niveau warn et supérieur, en plus de celles au niveau info pour le sous-système plugin.

Debug sudo_intercept.so /var/log/intercept_debug all@debug

enregistrerait toutes les instructions de débogage, quel que soit le niveau, pour la bibliothèque partagée sudo_intercept.so qui implémente la fonctionnalité d'interception de sudo sur certains systèmes.

Debug sudoers.so /var/log/sudoers_debug all@debug

enregistrerait toutes les instructions de débogage, quel que soit le niveau, pour le plugin sudoers. Voir sudoers(5) pour la liste complète des sous-systèmes pris en charge par le sudoers

Configuration

Le fichier de configuration de sudo est /etc/sudo.conf. Ce fichier est utilisé pour configurer le sudo(8) front-end, et non le plugin sudoers(5).

Depuis sudo 1.8.12, plusieurs entrées Debug peuvent être spécifiées par programme. Les versions plus anciennes de sudo ne prennent en charge qu'une seule entrée Debug par programme. Les entrées Debug spécifiques aux plugins sont également prises en charge à partir de sudo 1.8.12 et correspondent soit au nom de base du plugin chargé (par exemple sudoers.so), soit au nom de chemin complet du plugin. Auparavant, le plugin sudoers partageait la même entrée Debug que le front-end sudo et ne pouvait pas être configuré séparément.

Les priorités suivantes sont prises en charge, par ordre de gravité décroissante : crit, err, warn, notice, diag, info, trace, et debug. Chaque priorité, lorsqu'elle est spécifiée, inclut également toutes les priorités supérieures. Par exemple, une priorité de notice inclurait les messages de débogage enregistrés à la priorité notice et supérieure.

Les priorités trace et debug incluent également le traçage des appels de fonctions, qui enregistre quand une fonction est entrée et quand elle retourne. Par exemple, le traçage suivant concerne la fonction get_user_groups() située dans src/sudo.c :

sudo[123] -> get_user_groups @ src/sudo.c:385
sudo[123] <- get_user_groups @ src/sudo.c:429 := groups=10,0,5

Lorsqu'une fonction est entrée, indiqué par une flèche vers la droite ‘->’, le programme, l'ID du processus, la fonction, le fichier source et le numéro de ligne sont enregistrés. Lorsqu'une fonction retourne, indiqué par une flèche vers la gauche ‘<-’, les mêmes informations sont enregistrées avec la valeur de retour. Dans ce cas, la valeur de retour est une chaîne de caractères.

Les sous-systèmes suivants sont utilisés par le front-end de sudo :

all
correspond à tous les sous-systèmes
args
traitement des arguments de la ligne de commande
conv
conversation avec l'utilisateur
edit
sudoedit
event
sous-système d'événements
exec
exécution de commandes
main
fonction principale de sudo
netif
gestion des interfaces réseau
pcomm
communication avec le plugin
plugin
configuration du plugin
pty
code lié aux pseudo-terminaux
selinux
gestion spécifique à SELinux
util
fonctions utilitaires
utmp
gestion de utmp

Le plugin sudoers(5) inclut la prise en charge de sous-systèmes supplémentaires.

FICHIERS

/etc/sudo.conf
configuration du front-end de sudo

EXEMPLES

#
# Fichier /etc/sudo.conf par défaut
#
# Plugins Sudo :
#   Plugin nom_plugin chemin_plugin options_plugin ...
#
# Le chemin_plugin est relatif à /usr/lib/sudo à moins qu'il ne soit
#   entièrement qualifié.
# Le nom_plugin correspond à un symbole global dans le plugin
#   qui contient la structure d'interface du plugin.
# Les options_plugin sont facultatives.
#
# Le plugin sudoers est utilisé par défaut si aucune ligne Plugin n'est présente.
#Plugin sudoers_policy sudoers.so
#Plugin sudoers_io sudoers.so
#Plugin sudoers_audit sudoers.so

#
# Sudo askpass :
#   Path askpass /chemin/vers/askpass
#
# Un programme d'assistance askpass peut être spécifié pour fournir une invite
# graphique de mot de passe pour la prise en charge de "sudo -A". Sudo ne fournit pas
# son propre programme askpass mais peut utiliser l'askpass d'OpenSSH.
#
# Utiliser l'askpass d'OpenSSH
#Path askpass /usr/X11R6/bin/ssh-askpass
#
# Utiliser l'askpass Gnome d'OpenSSH
#Path askpass /usr/libexec/openssh/gnome-ssh-askpass

#
# Chemin de recherche de périphérique Sudo :
#   Path devsearch /dev/path1:/dev/path2:/dev
#
# Une liste de chemins séparés par des deux-points à vérifier lors de la recherche
# de l'appareil terminal d'un utilisateur.
#
#Path devsearch /dev/pts:/dev/vt:/dev/term:/dev/zcons:/dev/pty:/dev

#
# Interception de commandes Sudo :
#   Path intercept /chemin/vers/sudo_intercept.so
#
# Chemin vers une bibliothèque partagée contenant des remplacements pour les
# fonctions de bibliothèque execv(), execve() et fexecve(), qui effectuent une
# vérification de politique pour s'assurer que la commande est autorisée et
# retournent simplement une erreur si ce n'est pas le cas. Ceci est utilisé pour
# implémenter la fonctionnalité "intercept" sur les systèmes qui prennent en
# charge LD_PRELOAD ou son équivalent.
#
# La valeur compilée est généralement suffisante et ne devrait être modifiée que
# si vous renommez ou déplacez le fichier sudo_intercept.so.
#
#Path intercept /usr/lib/sudo/sudo_intercept.so

#
# Sudo noexec :
#   Path noexec /chemin/vers/sudo_noexec.so
#
# Chemin vers une bibliothèque partagée contenant des remplacements pour la
# famille de fonctions de bibliothèque execv() qui retournent simplement une
# erreur. Ceci est utilisé pour implémenter la fonctionnalité "noexec" sur les
# systèmes qui prennent en charge LD_PRELOAD ou son équivalent.
#
# La valeur compilée est généralement suffisante et ne devrait être modifiée que
# si vous renommez ou déplacez le fichier sudo_noexec.so.
#
#Path noexec /usr/lib/sudo/sudo_noexec.so

#
# Répertoire des plugins Sudo :
#   Path plugin_dir /chemin/vers/plugins
#
# Le répertoire par défaut à utiliser lors de la recherche de plugins qui sont
# spécifiés sans nom de chemin complet.
#
#Path plugin_dir /usr/lib/sudo

#
# Vidages de coredump :
#   Set disable_coredump true|false
#
# Par défaut, sudo désactive les vidages de coredump pendant son exécution
# (ils sont réactivés pour la commande exécutée).
# Pour aider au débogage des problèmes de sudo, vous pourriez vouloir activer
# les vidages de coredump en réglant "disable_coredump" à false.
#
#Set disable_coredump false

#
# Groupes d'utilisateurs :
#   Set group_source static|dynamic|adaptive
#
# Sudo transmet la liste des groupes de l'utilisateur au plugin de politique.
# Si l'utilisateur fait partie du nombre maximum de groupes (généralement 16),
# sudo interrogera directement la base de données des groupes pour s'assurer
# d'inclure la liste complète des groupes.
#
# Sur certains systèmes, cela peut être coûteux, donc le comportement est configurable.
# Le paramètre "group_source" a trois valeurs possibles :
#   static   - utiliser la liste des groupes de l'utilisateur retournée par le noyau.
#   dynamic  - interroger la base de données des groupes pour trouver la liste des groupes.
#   adaptive - si l'utilisateur fait partie de moins que le nombre maximum de groupes.
#	       utiliser la liste du noyau, sinon interroger la base de données des groupes.
#
#Set group_source static

#
# Sonde des interfaces Sudo :
#   Set probe_interfaces true|false
#
# Par défaut, sudo sonde les interfaces réseau du système et transmet
# l'adresse IP de chaque interface activée au plugin de politique.
# Sur les systèmes avec un grand nombre d'interfaces virtuelles, cela peut prendre
# un temps notable.
#
#Set probe_interfaces false

#
# Fichiers de débogage Sudo :
#   Debug programme /chemin/vers/debug_log sous_système@priorité[,sous_système@priorité]
#
# Sudo et les programmes associés prennent en charge l'enregistrement d'informations
# de débogage dans un fichier. Le programme est généralement sudo, sudoers.so,
# sudoreplay ou visudo.
#
# Les sous-systèmes varient en fonction du programme ; "all" correspond à tous les
# sous-systèmes. La priorité peut être crit, err, warn, notice, diag, info, trace
# ou debug. Plusieurs sous-système@priorité peuvent être spécifiés, séparés par
# une virgule.
#
#Debug sudo /var/log/sudo_debug all@debug
#Debug sudoers.so /var/log/sudoers_debug all@debug

BOGUES

Si vous pensez avoir trouvé un bogue dans sudo.conf, vous pouvez soit signaler un rapport de bogue dans la base de données des bogues de sudo, https://bugzilla.sudo.ws/, soit ouvrir un ticket sur https://github.com/sudo-project/sudo/issues. Si vous préférez utiliser l'e-mail, les messages peuvent être envoyés à la liste de diffusion sudo-workers, https://www.sudo.ws/mailman/listinfo/sudo-workers (publique) ou <sudo@sudo.ws> (privée).

Veuillez ne pas signaler les vulnérabilités de sécurité via les tickets GitHub publics, Bugzilla ou les listes de diffusion. Au lieu de cela, rapportez-les par e-mail à <Todd.Miller@sudo.ws>. Vous pouvez chiffrer votre message avec PGP si vous le souhaitez, en utilisant la clé trouvée sur https://www.sudo.ws/dist/PGPKEYS.
