NOM

sudo_plugin — API des plugins Sudo

DESCRIPTION

À partir de la version 1.8, sudo prend en charge une API de plugins pour la politique et la journalisation de session. Les plugins peuvent être compilés en objets partagés dynamiques (par défaut sur les systèmes qui les prennent en charge) ou compilés statiquement dans le binaire sudo lui-même. Par défaut, le plugin sudoers fournit les capacités de journalisation d'audit, de politique de sécurité et d'E/S. Via l'API des plugins, sudo peut être configuré pour utiliser des plugins alternatifs fournis par des tiers. Les plugins à utiliser sont spécifiés dans le fichier sudo.conf(5).

L'API est versionnée avec un numéro de version majeur et mineur. Le numéro de version mineur est incrémenté lorsque des ajouts sont effectués. Le numéro de version majeur est incrémenté lorsque des modifications incompatibles sont apportées. Un plugin doit vérifier la version qui lui est passée et s'assurer que la version majeure correspond.

L'API des plugins est définie par le fichier d'en-tête <sudo_plugin.h>.

API du plugin de politique

Un plugin de politique doit déclarer et peupler une structure policy_plugin dans la portée globale. Cette structure contient des pointeurs vers les fonctions qui implémentent les vérifications de politique de sudo. Le nom du symbole doit être spécifié dans sudo.conf(5) ainsi qu'un chemin d'accès au plugin afin que sudo puisse le charger.

struct policy_plugin {
#define SUDO_POLICY_PLUGIN     1
    unsigned int type; /* toujours SUDO_POLICY_PLUGIN */
    unsigned int version; /* toujours SUDO_API_VERSION */
    int (*open)(unsigned int version, sudo_conv_t conversation,
        sudo_printf_t sudo_plugin_printf, char * const settings[],
        char * const user_info[], char * const user_env[],
        char * const plugin_options[], const char **errstr);
    void (*close)(int exit_status, int error);
    int (*show_version)(int verbose);
    int (*check_policy)(int argc, char * const argv[],
        char *env_add[], char **command_info[],
        char **argv_out[], char **user_env_out[], const char **errstr);
    int (*list)(int argc, char * const argv[], int verbose,
        const char *user, const char **errstr);
    int (*validate)(const char **errstr);
    void (*invalidate)(int rmcred);
    int (*init_session)(struct passwd *pwd, char **user_env[],
        const char **errstr);
    void (*register_hooks)(int version,
       int (*register_hook)(struct sudo_hook *hook));
    void (*deregister_hooks)(int version,
       int (*deregister_hook)(struct sudo_hook *hook));
    struct sudo_plugin_event * (*event_alloc)(void);
};

Une structure policy_plugin a les champs suivants :

type
Le champ type doit toujours être défini sur SUDO_POLICY_PLUGIN.
version
Le champ version doit être défini sur SUDO_API_VERSION.

Cela permet à sudo de déterminer la version de l'API avec laquelle le plugin a été compilé.

open
int (*open)(unsigned int version, sudo_conv_t conversation,
    sudo_printf_t sudo_plugin_printf, char * const settings[],
    char * const user_info[], char * const user_env[],
    char * const plugin_options[], const char **errstr);

Retourne 1 en cas de succès, 0 en cas d'échec, -1 en cas d'erreur générale, ou -2 en cas d'erreur d'utilisation. Dans ce dernier cas, sudo affichera un message d'utilisation avant de se terminer. En cas d'erreur, le plugin peut éventuellement appeler la fonction conversation() ou sudo_plugin_printf() avec SUDO_CONF_ERROR_MSG pour présenter des informations d'erreur supplémentaires à l'utilisateur.

Les arguments de la fonction sont les suivants :

version
La version passée par sudo permet au plugin de déterminer le numéro de version majeur et mineur de l'API des plugins prise en charge par sudo.
conversation
Un pointeur vers la fonction conversation() qui peut être utilisée par le plugin pour interagir avec l'utilisateur (voir API de conversation pour plus de détails). Retourne 0 en cas de succès et -1 en cas d'échec.
sudo_plugin_printf
Un pointeur vers une fonction de style printf() qui peut être utilisée pour afficher des messages informatifs ou d'erreur (voir API de conversation pour plus de détails). Retourne le nombre de caractères imprimés en cas de succès et -1 en cas d'échec.
settings
Un vecteur de paramètres sudo fournis par l'utilisateur sous forme de chaînes “nom=valeur”. Le vecteur est terminé par un pointeur NULL. Ces paramètres correspondent aux options que l'utilisateur a spécifiées lors de l'exécution de sudo. En tant que tels, ils ne seront présents que lorsque l'option correspondante a été spécifiée sur la ligne de commande.

Lors de l'analyse de settings, le plugin doit diviser sur le **premier** signe égal (‘=’) car le champ nom n'en contiendra jamais, mais la valeur pourrait en contenir.

Les valeurs suivantes peuvent être définies par sudo :

bsdauth_type=chaîne
Type d'authentification, s'il est spécifié par l'option -a, à utiliser sur les systèmes où l'authentification BSD est prise en charge.
closefrom=nombre
Si spécifié, l'utilisateur a demandé via l'option -C que sudo ferme tous les descripteurs de fichiers d'une valeur de nombre ou supérieure. Le plugin peut facultativement renvoyer cette valeur, ou une autre, dans la liste command_info.
cmnd_chroot=chaîne
Le répertoire racine (voir chroot(2)) dans lequel exécuter la commande, tel que spécifié par l'utilisateur via l'option -R. Le plugin peut ignorer ou restreindre la capacité de l'utilisateur à spécifier une nouvelle racine. Uniquement disponible à partir de la version 1.16 de l'API.
cmnd_cwd=chaîne
Le répertoire de travail dans lequel exécuter la commande, tel que spécifié par l'utilisateur via l'option -D. Le plugin peut ignorer ou restreindre la capacité de l'utilisateur à spécifier un nouveau répertoire de travail. Uniquement disponible à partir de la version 1.16 de l'API.
debug_flags=chaîne
Un nom de chemin de fichier de débogage suivi d'un espace et d'une liste séparée par des virgules de drapeaux de débogage qui correspondent à l'entrée Debug du plugin dans sudo.conf(5), s'il en existe une. Les drapeaux sont passés au plugin exactement tels qu'ils apparaissent dans sudo.conf(5). La syntaxe utilisée par sudo et le plugin sudoers est sous-système@priorité mais un plugin est libre d'utiliser un format différent tant qu'il n'inclut pas de virgule (‘,’). Avant sudo 1.8.12, il n'y avait aucun moyen de spécifier des debug_flags spécifiques au plugin, donc la valeur était toujours la même que celle utilisée par le front-end sudo et n'incluait pas de nom de chemin, uniquement les drapeaux eux-mêmes. Depuis la version 1.7 de l'interface des plugins, sudo ne passera les debug_flags que si sudo.conf(5) contient une
plugin-specific Debug entry.
ignore_ticket=bool
Défini sur true si l'utilisateur a spécifié l'option -k avec une commande, indiquant que l'utilisateur souhaite ignorer toute information d'authentification mise en cache. implied_shell à true. Ceci permet d'utiliser sudo sans arguments de manière similaire à su(1). Si le plugin ne prend pas en charge cette utilisation, il peut retourner une valeur de -2 depuis la fonction check_policy(), ce qui amènera sudo à afficher un message d'utilisation et à quitter.
implied_shell=bool
Si l'utilisateur ne spécifie pas de programme sur la ligne de commande, sudo transmettra au plugin le chemin vers le shell de l'utilisateur et définira implied_shell.
intercept_ptrace=bool
Indique si le système prend en charge le mode d'interception en utilisant ptrace(2). Ceci est actuellement vrai uniquement pour les systèmes Linux qui prennent en charge le filtrage seccomp(2) et l'action "trap". Les autres systèmes utiliseront un objet partagé dynamique pour implémenter l'interception. Uniquement disponible à partir de la version d'API 1.19.
intercept_setid=bool
Indique si le système prend en charge l'exécution de binaires set-user-ID et set-group-ID en mode d'interception. Ceci est actuellement vrai uniquement pour les systèmes Linux qui prennent en charge le filtrage seccomp(2) et l'action "trap". Sur les systèmes qui utilisent un objet partagé dynamique pour implémenter l'interception, l'éditeur de liens dynamique (ld.so ou l'équivalent) désactivera le préchargement des objets partagés lors de l'exécution d'un binaire set-user-ID ou set-group-ID. Ceci désactivera le mode d'interception pour ce programme et tous les autres programmes qu'il exécute. Le plugin de politique peut refuser d'exécuter un binaire set-user-ID ou set-group-ID en mode d'interception pour éviter cela. Uniquement disponible à partir de la version d'API 1.19.
login_class=string
Classe de connexion BSD à utiliser lors de la définition des limites de ressources et de la valeur de "nice", si spécifié par l'option -c.
login_shell=bool
Défini sur true si l'utilisateur a spécifié l'option -i, indiquant que l'utilisateur souhaite exécuter un shell de connexion.
max_groups=int
Le nombre maximum de groupes auxquels un utilisateur peut appartenir. Ceci sera présent uniquement s'il y a un réglage correspondant dans sudo.conf(5).
network_addrs=list
Une liste séparée par des espaces d'adresses réseau IP et de masques réseau sous la forme "addr/netmask", par exemple, "192.168.1.2/255.255.255.0". Les paires adresse et masque réseau peuvent être IPv4 ou IPv6, en fonction de ce que prend en charge le système d'exploitation. Si l'adresse contient un deux-points (':' ), c'est une adresse IPv6, sinon c'est une adresse IPv4.
noninteractive=bool
Défini sur true si l'utilisateur a spécifié l'option -n, indiquant que sudo doit fonctionner en mode non interactif. Le plugin peut rejeter une commande exécutée en mode non interactif si une interaction utilisateur est requise.
plugin_dir=string
Le répertoire de plugin par défaut utilisé par le frontend sudo. Il s'agit du répertoire par défaut défini au moment de la compilation et il peut ne pas correspondre au répertoire à partir duquel le plugin en cours d'exécution a été chargé. Il peut être utilisé par un plugin pour localiser des fichiers de support.
plugin_path=string
Le nom du chemin du plugin chargé par le frontend sudo. Le nom du chemin sera entièrement qualifié, sauf si le plugin a été compilé statiquement dans sudo.
preserve_environment=bool
Défini sur true si l'utilisateur a spécifié l'option -E, indiquant que l'utilisateur souhaite préserver l'environnement.
preserve_groups=bool
Défini sur true si l'utilisateur a spécifié l'option -P, indiquant que l'utilisateur souhaite préserver le vecteur de groupes au lieu de le définir en fonction de l'utilisateur d'exécution.
progname=string
Le nom de la commande avec laquelle sudo a été exécuté, généralement "sudo" ou "sudoedit".
prompt=string
Le prompt à utiliser lors de la demande d'un mot de passe, s'il est spécifié via l'option -p.
remote_host=string
Le nom de l'hôte distant sur lequel exécuter la commande, s'il est spécifié via l'option -h. La prise en charge de l'exécution de la commande sur un hôte distant est destinée à être implémentée via un programme d'assistance exécuté à la place de la commande spécifiée par l'utilisateur. Le frontend sudo est uniquement capable d'exécuter des commandes sur l'hôte local. Uniquement disponible à partir de la version d'API 1.4.
run_shell=bool
Défini sur true si l'utilisateur a spécifié l'option -s, indiquant que l'utilisateur souhaite exécuter un shell.
runas_group=string
Le nom du groupe ou l'ID du groupe avec lequel exécuter la commande, s'il est spécifié via l'option -g.
runas_user=string
Le nom de l'utilisateur ou l'ID de l'utilisateur avec lequel exécuter la commande, s'il est spécifié via l'option -u.
selinux_role=string
Le rôle SELinux à utiliser lors de l'exécution de la commande, s'il est spécifié par l'option -r.
selinux_type=string
Le type SELinux à utiliser lors de l'exécution de la commande, s'il est spécifié par l'option -t.
set_home=bool
Défini sur true si l'utilisateur a spécifié l'option -H. Si true, définit la variable d'environnement HOME sur le répertoire personnel de l'utilisateur cible.
sudoedit=bool
Défini sur true lorsque l'option -e est spécifiée ou si invoqué en tant que sudoedit. Le plugin doit substituer un éditeur à argv dans la fonction check_policy() ou retourner -2 avec une erreur d'utilisation si le plugin ne prend pas en charge sudoedit. Pour plus d'informations, voir la section check_policy().
timeout=string
Le délai d'expiration de la commande spécifié par l'utilisateur via l'option -T. Tous les plugins ne prennent pas en charge les délais d'expiration des commandes et la capacité de l'utilisateur à définir un délai d'expiration peut être restreinte par la politique. Le format de la chaîne de délai d'expiration est spécifique au plugin.
update_ticket=bool
Défini sur false si l'utilisateur a spécifié l'option -N, indiquant que l'utilisateur souhaite éviter de mettre à jour toute information d'authentification mise en cache. Uniquement disponible à partir de la version d'API 1.20.

D'autres paramètres peuvent être ajoutés à l'avenir, le plugin doit donc ignorer silencieusement les paramètres qu'il ne reconnaît pas.

user_info
Un vecteur d'informations sur l'utilisateur exécutant la commande sous la forme de chaînes "name=value". Le vecteur est terminé par un pointeur NULL.

Lors de l'analyse de user_info, le plugin doit découper sur le premier signe égal ('=') car le champ name n'en contiendra jamais lui-même, mais la valeur value pourrait.

Les valeurs suivantes peuvent être définies par sudo:

cols=int
Le nombre de colonnes supportées par le terminal de l'utilisateur. S'il n'y a pas de périphérique de terminal disponible, une valeur par défaut de 80 est utilisée.
cwd=string
Le répertoire de travail courant de l'utilisateur.
egid=gid_t
L'ID de groupe effectif de l'utilisateur qui invoque sudo.
euid=uid_t
L'ID utilisateur effectif de l'utilisateur qui invoque sudo.
gid=gid_t
L'ID de groupe réel de l'utilisateur qui invoque sudo.
groups=list
La liste des groupes supplémentaires de l'utilisateur formatée en une chaîne d'ID de groupe séparés par des virgules.
host=string
Le nom d'hôte de la machine locale tel que retourné par l'appel système gethostname(2).
lines=int
Le nombre de lignes supportées par le terminal de l'utilisateur. S'il n'y a pas de périphérique de terminal disponible, une valeur par défaut de 24 est utilisée.
pgid=int
L'ID du groupe de processus dont le processus sudo en cours d'exécution est membre. Uniquement disponible à partir de la version d'API 1.2.
pid=int
L'ID de processus du processus sudo en cours d'exécution. Uniquement disponible à partir de la version d'API 1.2.
ppid=int
L'ID du processus parent du processus sudo en cours d'exécution. Uniquement disponible à partir de la version d'API 1.2.
rlimit_as=soft,hard
La taille maximale à laquelle l'espace d'adressage du processus peut croître (en octets), si cela est pris en charge par le système d'exploitation. Les limites souple et stricte sont séparées par une virgule. Une valeur de "infinity" indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version d'API 1.16.
rlimit_core=soft,hard
La plus grande taille de fichier de vidage de cœur qui peut être créée (en octets). Les limites souple et stricte sont séparées par une virgule. Une valeur de "infinity" indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version d'API 1.16.
rlimit_cpu=soft,hard
Le temps CPU maximum que le processus peut utiliser (en secondes). Les limites souple et stricte sont séparées par une virgule. Une valeur de « infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
rlimit_data=souple,strict
La taille maximale du segment de données pour le processus (en octets). Les limites souple et stricte sont séparées par une virgule. Une valeur de « infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
rlimit_fsize=souple,strict
La plus grande taille de fichier que le processus peut créer (en octets). Les limites souple et stricte sont séparées par une virgule. Une valeur de « infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
rlimit_locks=souple,strict
Le nombre maximal de verrous que le processus peut établir, si pris en charge par le système d'exploitation. Les limites souple et stricte sont séparées par une virgule. Une valeur de « infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
rlimit_memlock=souple,strict
La taille maximale que le processus peut verrouiller en mémoire (en octets), si pris en charge par le système d'exploitation. Les limites souple et stricte sont séparées par une virgule. Une valeur de «  infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
rlimit_nofile=souple,strict
Le nombre maximal de fichiers que le processus peut ouvrir. Les limites souple et stricte sont séparées par une virgule. Une valeur de «  infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
rlimit_nproc=souple,strict
Le nombre maximal de processus que l'utilisateur peut exécuter simultanément. Les limites souple et stricte sont séparées par une virgule. Une valeur de «  infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
rlimit_rss=souple,strict
La taille maximale que le jeu résident du processus peut atteindre (en octets). Les limites souple et stricte sont séparées par une virgule. Une valeur de «  infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
rlimit_stack=souple,strict
La taille maximale que la pile du processus peut atteindre (en octets). Les limites souple et stricte sont séparées par une virgule. Une valeur de «  infini » indique qu'il n'y a pas de limite. Uniquement disponible à partir de la version 1.16 de l'API.
sid=int
L'ID de session du processus sudo en cours d'exécution ou 0 si sudo ne fait pas partie d'une session POSIX de contrôle de travaux. Uniquement disponible à partir de la version 1.2 de l'API.
tcpgid=int
L'ID du groupe de processus en avant associé au terminal associé au processus sudo ou 0 s'il n'y a pas de terminal présent. Uniquement disponible à partir de la version 1.2 de l'API.
tty=string
Le chemin vers le périphérique terminal de l'utilisateur, s'il en existe un. Cette entrée est présente uniquement si l'utilisateur dispose d'un périphérique terminal associé à la session.
ttydev=dev_t
Le numéro du périphérique terminal de l'utilisateur, s'il en existe un, formaté comme une valeur long long. Cette entrée est présente uniquement si l'utilisateur dispose d'un périphérique terminal associé à la session. Uniquement disponible à partir de la version 1.22 de l'API.
uid=uid_t
L'ID utilisateur réel de l'utilisateur qui invoque sudo.
umask=octal
Le masque de création de fichiers de l'utilisateur appelant. Uniquement disponible à partir de la version 1.10 de l'API.
user=string
Le nom de l'utilisateur qui invoque sudo.
user_env
L'environnement de l'utilisateur sous la forme d'un vecteur terminé par NULL de chaînes « nom=valeur ».

Lors de l'analyse de user_env, le plugin doit diviser sur le premier signe égal (« = ») car le champ nom n'en contiendra jamais, mais la valeur pourrait en contenir.

plugin_options
Toutes les chaînes (non commentées) immédiatement après le chemin du plugin sont transmises comme arguments au plugin. Ces arguments sont divisés par une limite d'espacement blanc et sont transmis au plugin sous la forme d'un tableau de chaînes terminé par NULL. Si aucun argument n'a été spécifié, plugin_options sera le pointeur NULL.

Le paramètre plugin_options est uniquement disponible à partir de la version 1.2 de l'API. Un plugin doit vérifier la version de l'API spécifiée par le frontend sudo avant d'utiliser plugin_options. Ne pas le faire peut entraîner un plantage.

errstr
Si la fonction open() renvoie une valeur autre que 1, le plugin peut stocker un message décrivant l'échec ou l'erreur dans errstr. Le frontend sudo transmettra alors cette valeur à tous les plugins d'audit enregistrés. La chaîne stockée dans errstr doit rester valide jusqu'à ce que la fonction close() du plugin soit appelée.

Le paramètre errstr est uniquement disponible à partir de la version 1.15 de l'API. Un plugin doit vérifier la version de l'API spécifiée par le frontend sudo avant d'utiliser errstr. Ne pas le faire peut entraîner un plantage.

close
void (*close)(int exit_status, int error);

La fonction close() est appelée lorsque sudo a terminé, peu avant sa sortie. À partir de la version 1.15 de l'API, close() est appelée, qu'une commande ait été effectivement exécutée ou non. Cela permet aux plugins d'effectuer un nettoyage même lorsqu'aucune commande n'a été exécutée. Il n'est pas possible de déterminer si une commande a été exécutée en se basant uniquement sur les arguments passés à la fonction close(). Pour déterminer si une commande a réellement été exécutée, le plugin doit suivre si la fonction check_policy() s'est terminée avec succès ou non.

Les arguments de la fonction sont les suivants :

exit_status
Le statut de sortie de la commande, tel que renvoyé par l'appel système wait(2), ou zéro si aucune commande n'a été exécutée. La valeur de exit_status est indéfinie si error est non nul.
error
Si la commande n'a pas pu être exécutée, cette valeur est définie sur la valeur de errno définie par l'appel système execve(2). Le plugin est responsable de l'affichage des informations d'erreur via la fonction conversation() ou sudo_plugin_printf(). Si la commande a été exécutée avec succès, la valeur de error est zéro.

Si aucune fonction close() n'est définie, qu'aucun plugin de journalisation d'E/S n'est chargé, et que ni l'option timeout ni l'option use_pty ne sont définies dans la liste command_info, le frontend sudo peut exécuter la commande directement au lieu de l'exécuter en tant que processus enfant.

show_version
int (*show_version)(int verbose);

La fonction show_version() est appelée par sudo lorsque l'utilisateur spécifie l'option -V. Le plugin peut afficher ses informations de version à l'utilisateur via la fonction conversation() ou sudo_plugin_printf() en utilisant SUDO_CONV_INFO_MSG. Si l'utilisateur demande des informations de version détaillées, le drapeau verbose ne sera pas nul.

Renvoie 1 en cas de succès, 0 en cas d'échec, -1 en cas d'erreur générale, ou -2 en cas d'erreur d'utilisation, bien que la valeur de retour soit actuellement ignorée.

check_policy
int (*check_policy)(int argc, char * const argv[], char *env_add[],
    char **command_info[], char **argv_out[], char **user_env_out[],
    const char **errstr);

La fonction check_policy() est appelée par sudo pour déterminer si l'utilisateur est autorisé à exécuter les commandes spécifiées.

Si l'option sudoedit était activée dans le tableau settings passé à la fonction open(), l'utilisateur a demandé le mode sudoedit. sudoedit est un mécanisme pour modifier un ou plusieurs fichiers où un éditeur est exécuté avec les identifiants de l'utilisateur au lieu de avec des privilèges élevés. sudo y parvient en créant des copies temporaires des fichiers à modifier, inscriptibles par l'utilisateur, puis en remplaçant les originaux par les copies temporaires une fois l'édition terminée. Si le plugin prend en charge sudoedit, il doit définir sudoedit=true dans la liste command_info. Le plugin

est responsable du choix de l'éditeur à utiliser, potentiellement à partir d'une variable de l'environnement utilisateur, telle que EDITOR, et doit être stocké dans argv_out (les variables d'environnement peuvent inclure des options de ligne de commande). Les fichiers à éditer doivent être copiés de argv vers argv_out, séparés de l'éditeur et de ses arguments par un élément ‘--’. Le ‘--’ sera supprimé par sudo avant l'exécution de l'éditeur. Le plugin peut également définir sudoedit_nfiles au nombre de fichiers à éditer dans la liste command_info ; ceci ne sera utilisé par le frontend sudo qu'à partir de la version API 1.21.

La fonction check_policy() renvoie 1 si la commande est autorisée, 0 si elle n'est pas autorisée, -1 en cas d'erreur générale, ou -2 en cas d'erreur d'utilisation ou si sudoedit a été spécifié mais n'est pas pris en charge par le plugin. Dans ce dernier cas, sudo affichera un message d'utilisation avant de se terminer. En cas d'erreur, le plugin peut facultativement appeler la fonction conversation() ou sudo_plugin_printf() avec SUDO_CONF_ERROR_MSG pour présenter des informations d'erreur supplémentaires à l'utilisateur.

Les arguments de la fonction sont les suivants :

argc
Le nombre d'éléments dans argv, sans compter le pointeur NULL final.
argv

exec_background=bool
Par défaut, sudo exécute une commande en tant que processus de premier plan tant que sudo lui-même est exécuté en premier plan. Lorsque exec_background est activé et que la commande est exécutée dans un pseudo-terminal (en raison de l'enregistrement des E/S ou du paramètre use_pty), la commande sera exécutée en tant que processus d'arrière-plan. Les tentatives de lecture du terminal de contrôle (ou de modification des paramètres du terminal) entraîneront la suspension de la commande avec le signal SIGTTIN (ou SIGTTOU dans le cas des paramètres du terminal). Si cela se produit lorsque sudo est un processus de premier plan, la commande se verra accorder le terminal de contrôle et reprendra en premier plan sans intervention de l'utilisateur. L'avantage d'exécuter initialement la commande en arrière-plan est que sudo n'a pas besoin de lire du terminal à moins que la commande ne le demande explicitement. Sinon, toute entrée du terminal doit être transmise à la commande, qu'elle l'ait demandée ou non (le noyau met en mémoire tampon les terminaux, il est donc impossible de savoir si la commande souhaite réellement l'entrée). Ceci est différent du comportement historique de sudo ou lorsque la commande n'est pas exécutée dans un pseudo-terminal.

Pour que cela fonctionne de manière transparente, le système d'exploitation doit prendre en charge le redémarrage automatique des appels système. Malheureusement, tous les systèmes d'exploitation ne le font pas par défaut, et même ceux qui le font peuvent avoir des bogues. Par exemple, macOS ne redémarre pas les appels système tcgetattr() et tcsetattr() (c'est un bogue dans macOS). De plus, comme ce comportement dépend de l'arrêt de la commande avec les signaux SIGTTIN ou SIGTTOU, les programmes qui interceptent ces signaux et se suspendent avec un signal différent (généralement SIGTOP) ne seront pas automatiquement mis en premier plan. Certaines versions de la commande Linux su(1) se comportent ainsi. Pour cette raison, un plugin ne devrait pas définir exec_background à moins qu'il ne soit explicitement activé par l'administrateur et qu'il devrait y avoir un moyen de l'activer ou de le désactiver pour chaque commande.

Ce paramètre n'a aucun effet si l'enregistrement des E/S n'est pas activé ou si use_pty n'est pas activé.

Lorsqu'un plugin d'E/S est chargé, sudo exécute la commande dans un pseudo-terminal. Cela permet d'enregistrer les entrées et sorties de la session de l'utilisateur. Si l'une des entrées standard, sorties standard ou erreurs standard ne correspond pas à un tty, sudo ouvrira un tuyau pour capturer les E/S à des fins d'enregistrement avant de les transmettre.

La fonction log_ttyin() reçoit l'entrée brute de l'utilisateur depuis le périphérique terminal (cela inclura les entrées même lorsque l'écho est désactivé, comme lors de la lecture d'un mot de passe). La fonction log_ttyout() reçoit la sortie du pseudo-terminal qui convient à la relecture de la session de l'utilisateur ultérieurement. Les fonctions log_stdin(), log_stdout() et log_stderr() ne sont appelées que si l'entrée standard, la sortie standard ou l'erreur standard correspondent respectivement à autre chose qu'un tty.

N'importe laquelle des fonctions d'enregistrement peut être définie sur le pointeur NULL si aucun enregistrement ne doit être effectué. Si la fonction open renvoie 0, aucune E/S ne sera envoyée au plugin.

Si une fonction d'enregistrement renvoie une erreur (-1), la commande en cours sera terminée et toutes les fonctions d'enregistrement du plugin seront désactivées. D'autres plugins d'enregistrement d'E/S recevront toujours les entrées ou sorties restantes qui n'ont pas encore été traitées.

Si une fonction d'enregistrement d'entrée rejette les données en retournant 0, la commande sera terminée et les données ne seront pas transmises à la commande, bien qu'elles soient toujours envoyées à tous les autres plugins d'enregistrement d'E/S. Si une fonction d'enregistrement de sortie rejette les données en retournant 0, la commande sera terminée et les données ne seront pas écrites sur le terminal, bien qu'elles soient toujours envoyées à tous les autres plugins d'enregistrement d'E/S.

Policy plugin API

An audit plugin can be used to reject or accept users based on arbitrary policy. Only one policy plugin may be specified in sudo.conf(5).

A struct sudo_plugin has the following fields:

type
The type field should always be set to SUDO_POLICY_PLUGIN.
version
The version field should be set to SUDO_API_VERSION.

This allows sudo to determine the API version the plugin was built against.

open
int (*open)(unsigned int version, sudo_conv_t conversation,
    sudo_printf_t sudo_plugin_printf, char * const settings[],
    char * const user_info[], int submit_optind,
    char * const submit_argv[], char * const submit_envp[],
    char * const plugin_options[], const char **errstr);

The policy open() function is run before any other plugin API functions. It is used to initialize the plugin and check that sudo is using a supported API version. It returns 1 on success, 0 on failure, -1 if a general error occurred, or -2 if there was a usage error. In the latter case, sudo will print a usage message before it exits. If an error occurs, the plugin may optionally call the conversation() or plugin_printf() function with SUDO_CONF_ERROR_MSG to present additional error information to the user.

The function arguments are as follows:

version
The version passed in by sudo allows the plugin to determine the major and minor version number of the plugin API supported by sudo.
conversation
A pointer to the conversation() function that may be used by the plugin for prompting the user for information. The conversation() function may also be used to display additional error messages to the user. The conversation() function returns 0 on success, and -1 on failure.
plugin_printf
A pointer to a printf()-style function that may be used by the plugin to display informational messages to the user. The plugin_printf() function returns number of characters printed on success and -1 on failure.
settings
A vector of user-supplied sudo settings in the form of “name=value” strings. The vector is terminated by a NULL pointer. These settings correspond to options the user specified when running sudo. As such, they will only be present when the corresponding option has been specified on the command line.

When parsing settings, the plugin should split on the first equal sign (‘=’)

user_info

Gestionnaires de signaux

Le système sudo installe des gestionnaires de signaux par défaut pour intercepter les signaux courants pendant l'exécution des fonctions du plugin. Les signaux suivants sont interceptés par défaut avant l'exécution de la commande :

  • SIGALRM
  • SIGHUP
  • SIGINT
  • SIGPIPE
  • SIGQUIT
  • SIGTERM
  • SIGTSTP
  • SIGUSR1
  • SIGUSR2

Si un signal fatal est reçu avant l'exécution de la commande, sudo appellera la fonction close() du plugin avec un statut de sortie de 128 plus la valeur du signal reçu. Cela permet une journalisation cohérente des commandes arrêtées par un signal pour les plugins qui enregistrent de telles informations dans leur fonction close(). Une exception à cela est SIGPIPE, qui est ignoré jusqu'à ce que la commande soit exécutée.

Un plugin peut installer temporairement ses propres gestionnaires de signaux, mais doit restaurer le gestionnaire d'origine avant que la fonction du plugin ne retourne.

API des fonctions de hook

Depuis la version 1.2 de l'API des plugins, il est possible d'installer des hooks pour certaines fonctions appelées par le système sudo.

Actuellement, les seuls hooks pris en charge concernent la gestion des variables d'environnement. Les hooks peuvent être utilisés pour intercepter les tentatives d'obtention, de définition ou de suppression de variables d'environnement afin que ces modifications puissent être reflétées dans la version de l'environnement utilisée pour exécuter une commande. Une future version de l'API permettra également de hooker les fonctions internes du système sudo.

Structure des hooks

Les hooks dans sudo sont décrits par la structure suivante :

typedef int (*sudo_hook_fn_t)();

struct sudo_hook {
    unsigned int hook_version;
    unsigned int hook_type;
    sudo_hook_fn_t hook_fn;
    void *closure;
};

Une struct sudo_hook a les champs suivants :

hook_version
Le champ hook_version doit être défini sur SUDO_HOOK_VERSION.
hook_type
Le champ hook_type peut être l'un des types de hooks pris en charge suivants :
SUDO_HOOK_SETENV
La fonction de la bibliothèque C setenv(3). Tous les hooks enregistrés s'exécuteront avant l'implémentation de la bibliothèque C. Le champ hook_fn doit être une fonction correspondant au typedef suivant : 
typedef int (*sudo_hook_fn_setenv_t)(const char *name,
   const char *value, int overwrite, void *closure);

Si le hook enregistré ne correspond pas au typedef, les résultats ne sont pas spécifiés.

SUDO_HOOK_UNSETENV
La fonction de la bibliothèque C unsetenv(3). Tous les hooks enregistrés s'exécuteront avant l'implémentation de la bibliothèque C. Le champ hook_fn doit être une fonction correspondant au typedef suivant : 
typedef int (*sudo_hook_fn_unsetenv_t)(const char *name,
   void *closure);
SUDO_HOOK_GETENV
La fonction de la bibliothèque C getenv(3). Tous les hooks enregistrés s'exécuteront avant l'implémentation de la bibliothèque C. Le champ hook_fn doit être une fonction correspondant au typedef suivant : 
typedef int (*sudo_hook_fn_getenv_t)(const char *name,
   char **value, void *closure);

Si le hook enregistré ne correspond pas au typedef, les résultats ne sont pas spécifiés.

SUDO_HOOK_PUTENV
La fonction de la bibliothèque C putenv(3). Tous les hooks enregistrés s'exécuteront avant l'implémentation de la bibliothèque C. Le champ hook_fn doit être une fonction correspondant au typedef suivant : 
typedef int (*sudo_hook_fn_putenv_t)(char *string,
   void *closure);

Si le hook enregistré ne correspond pas au typedef, les résultats ne sont pas spécifiés.

hook_fn
sudo_hook_fn_t hook_fn;

Le champ hook_fn doit être défini sur l'implémentation du hook du plugin. Les arguments réels de la fonction varieront en fonction de la hook_type (voir hook_type ci-dessus). Dans tous les cas, le champ closure de struct sudo_hook est passé comme dernier paramètre de la fonction. Cela peut être utilisé pour passer des données arbitraires à l'implémentation du hook du plugin.

La valeur de retour de la fonction peut être l'une des suivantes :

SUDO_HOOK_RET_ERROR
La fonction hook a rencontré une erreur.
SUDO_HOOK_RET_NEXT
Le hook s'est terminé sans erreur, passez au hook suivant (y compris l'implémentation système si applicable). Par exemple, un hook getenv(3) pourrait retourner SUDO_HOOK_RET_NEXT si la variable spécifiée n'a pas été trouvée dans la copie privée de l'environnement.
SUDO_HOOK_RET_STOP
Le hook s'est terminé sans erreur, arrêtez le traitement des hooks pour cette invocation. Cela peut être utilisé pour remplacer l'implémentation système. Par exemple, un hook setenv qui opère sur une copie privée de l'environnement mais laisse environ inchangé.

Il faut être prudent lors de l'interception des fonctions de la bibliothèque C, il est très facile de créer une boucle infinie. Par exemple, un hook getenv(3) qui appelle la fonction snprintf(3) peut créer une boucle si l'implémentation de snprintf(3) appelle getenv(3) pour vérifier la locale. Pour éviter cela, vous pouvez utiliser une variable statique dans la fonction hook pour vous prémunir contre les appels imbriqués. Par exemple :

static int in_progress = 0; /* éviter la récursion */
if (in_progress)
    return SUDO_HOOK_RET_NEXT;
in_progress = 1;
...
in_progress = 0;
return SUDO_HOOK_RET_STOP;

API d'événements

Lorsque sudo exécute une commande, il utilise une boucle d'événements pour gérer les signaux et les E/S. Les événements peuvent être déclenchés en fonction du temps, d'un descripteur de fichier ou de socket prêt, ou en raison de la réception d'un signal. À partir de la version 1.15 de l'API, il est possible pour un plugin de participer à cette boucle d'événements en appelant la fonction event_alloc().

Une struct sudo_plugin_event contient les pointeurs de fonction suivants :

set
int (*set)(struct sudo_plugin_event *pev, int fd, int events,
    sudo_plugin_ev_callback_t callback, void *closure);

La fonction set() prend les arguments suivants :

struct sudo_plugin_event *pev
Un pointeur vers la struct sudo_plugin_event elle-même.
fd
Le descripteur de fichier ou de socket pour les événements basés sur les E/S ou le numéro de signal pour les événements de signal. Pour les événements basés sur le temps, fd doit être -1.
events
Les valeurs suivantes déterminent ce qui déclenchera le rappel d'événement :
SUDO_PLUGIN_EV_TIMEOUT
le rappel est exécuté après l'expiration du délai spécifié
SUDO_PLUGIN_EV_READ
le rappel est exécuté lorsque le descripteur de fichier est lisible
SUDO_PLUGIN_EV_WRITE
le rappel est exécuté lorsque le descripteur de fichier est accessible en écriture
SUDO_PLUGIN_EV_PERSIST
l'événement est persistant et reste activé jusqu'à sa suppression explicite
SUDO_PLUGIN_EV_SIGNAL
le rappel est exécuté lorsqu'un signal spécifié est reçu

Le drapeau SUDO_PLUGIN_EV_PERSIST peut être combiné avec l'opérateur OR avec l'un des types d'événements. Il est également possible de combiner SUDO_PLUGIN_EV_READ et SUDO_PLUGIN_EV_WRITE pour exécuter le rappel lorsqu'un descripteur est prêt à être lu ou écrit. Toutes les autres valeurs d'événement sont mutuellement exclusives.

sudo_plugin_ev_callback_t callback
typedef void (*sudo_plugin_ev_callback_t)(int fd, int what,
    void *closure);

La fonction à appeler lorsqu'un événement est déclenché. La fonction callback() est exécutée avec les arguments suivants :

fd
Le descripteur de fichier ou de socket pour les événements basés sur les E/S ou le numéro de signal pour les événements de signal.
what
Le type d'événement qui a déclenché ce rappel. Pour les événements ayant plusieurs types (par exemple SUDO_PLUGIN_EV_READ et SUDO_PLUGIN_EV_WRITE) ou ayant un délai d'attente associé, what peut être utilisé pour déterminer pourquoi le rappel a été exécuté.
closure
Le pointeur générique qui a été spécifié dans la fonction set().
closure
Un pointeur générique qui sera passé à la fonction de rappel.

La fonction set() retourne 1 en cas de succès, et -1 en cas d'erreur.

add
int (*add)(struct sudo_plugin_event *pev, struct timespec *timeout);

La fonction add() ajoute l'événement pev à la boucle d'événements de sudo. L'événement doit avoir été préalablement initialisé via la fonction set(). Si l'argument timeout n'est pas NULL, il doit spécifier un délai d'attente (relatif) après lequel l'événement sera déclenché si le critère principal de l'événement n'a pas été satisfait. Ceci est souvent utilisé pour implémenter un délai d'attente pour les E/S, où l'événement se déclenchera si un descripteur n'est pas prêt dans un certain délai. Si l'événement est déjà présent dans la boucle d'événements, son timeout sera ajusté pour correspondre à la nouvelle valeur, le cas échéant.

La fonction add() retourne 1 en cas de succès, et -1 en cas d'erreur.

del
int (*del)(struct sudo_plugin_event *pev);

La fonction del() supprime l'événement pev de la boucle d'événements de sudo. Les événements supprimés peuvent être rajoutés via la fonction add().

La fonction del() renvoie 1 en cas de succès, et -1 si une erreur s'est produite.

pending
int (*pending)(struct sudo_plugin_event *pev, int events,
    struct timespec *ts);

La fonction pending() peut être utilisée pour déterminer si un ou plusieurs événements sont en attente. L'argument events spécifie les événements à vérifier. Voir la fonction set() pour une liste des types d'événements valides. Si SUDO_PLUGIN_EV_TIMEOUT est spécifié dans events, l'événement a un délai d'expiration associé et le pointeur ts n'est pas NULL, il sera rempli avec le temps restant.

fd
int (*fd)(struct sudo_plugin_event *pev);

La fonction fd() renvoie le descripteur ou le numéro de signal associé à l'événement pev.

setbase
void (*setbase)(struct sudo_plugin_event *pev, void *base);

La fonction setbase() définit la base d'événement sous-jacente pour pev à la valeur spécifiée. Ceci peut être utilisé pour déplacer un événement créé via event_alloc() vers une nouvelle boucle d'événements allouée par le sous-système d'événements de sudo. Si base est NULL, la base d'événements de pev est réinitialisée à la valeur par défaut, qui correspond à la boucle d'événements principale de sudo. L'utilisation de cette fonction nécessite de lier le plugin à la bibliothèque sudo_util. Il est peu probable qu'elle soit utilisée en dehors du plugin sudoers.

loopbreak
void (*loopbreak)(struct sudo_plugin_event *pev);

La fonction loopbreak() provoque la sortie immédiate de la boucle d'événements de sudo et la terminaison de la commande en cours d'exécution.

free
void (*free)(struct sudo_plugin_event *pev);

La fonction free() supprime l'événement pev de la boucle d'événements et libère la mémoire qui lui est associée.

Exécution de commande à distance

La façade sudo ne prend pas en charge l'exécution de commandes distantes. Cependant, à partir de sudo 1.8.8, l'option -h peut être utilisée pour spécifier un hôte distant qui est passé au plugin de stratégie. Un plugin peut également accepter un utilisateur d'exécution sous la forme "utilisateur@nom_hote" qui fonctionnera avec les anciennes versions de sudo. Il est prévu que les commandes distantes soient prises en charge en exécutant un programme "assistant". Le plugin de stratégie devrait configurer l'environnement d'exécution de telle sorte que la façade sudo exécute l'assistant qui, à son tour, se connectera à l'hôte distant et exécutera la commande.

Par exemple, le plugin de stratégie pourrait utiliser ssh pour exécuter des commandes à distance. Le programme assistant serait responsable de l'exécution de ssh avec les options appropriées pour utiliser une clé privée ou un certificat que l'hôte distant acceptera et exécutera un programme sur l'hôte distant qui configurerait l'environnement d'exécution en conséquence.

La fonctionnalité sudoedit à distance doit être gérée par le plugin de stratégie, et non par sudo lui-même, car la façade n'a aucune connaissance de l'exécution d'une commande à distance. Cela pourrait être abordé dans une future révision de l'API des plugins.

API de conversation

Si le plugin a besoin d'interagir avec l'utilisateur, il peut le faire via la fonction conversation(). Un plugin ne doit pas tenter de lire directement depuis l'entrée standard ou le terminal de l'utilisateur (aucun des deux n'est garanti d'exister). L'appelant doit inclure un saut de ligne final dans msg si un saut de ligne doit être imprimé.

Une fonction de style printf() est également disponible, qui peut être utilisée pour afficher des messages d'information ou d'erreur à l'utilisateur, ce qui est généralement plus pratique pour les messages simples où aucune saisie utilisateur n'est requise.

Structures de fonction de conversation

La fonction de conversation prend en arguments des pointeurs vers les structures suivantes :

struct sudo_conv_message {
#define SUDO_CONV_PROMPT_ECHO_OFF  0x0001 /* ne pas faire écho à l'entrée utilisateur */
#define SUDO_CONV_PROMPT_ECHO_ON   0x0002 /* faire écho à l'entrée utilisateur */
#define SUDO_CONV_ERROR_MSG        0x0003 /* message d'erreur */
#define SUDO_CONV_INFO_MSG         0x0004 /* message informatif */
#define SUDO_CONV_PROMPT_MASK      0x0005 /* masquer l'entrée utilisateur */
#define SUDO_CONV_PROMPT_ECHO_OK   0x1000 /* drapeau : autoriser l'écho s'il n'y a pas de tty */
#define SUDO_CONV_PREFER_TTY       0x2000 /* drapeau : utiliser le tty si possible */
    int msg_type;
    int timeout;
    const char *msg;
};

#define SUDO_CONV_REPL_MAX      1023

struct sudo_conv_reply {
    char *reply;
};

typedef int (*sudo_conv_callback_fn_t)(int signo, void *closure);
struct sudo_conv_callback {
    unsigned int version;
    void *closure;
    sudo_conv_callback_fn_t on_suspend;
    sudo_conv_callback_fn_t on_resume;
};

Les pointeurs vers les fonctions conversation() et de style printf() sont passés à la fonction open() du plugin lors de l'initialisation du plugin. Les définitions de type suivantes peuvent être utilisées dans la déclaration de la fonction open() :

typedef int (*sudo_conv_t)(int num_msgs,
    const struct sudo_conv_message msgs[],
    struct sudo_conv_reply replies[], struct sudo_conv_callback *callback);

typedef int (*sudo_printf_t)(int msg_type, const char * restrict fmt, ...);

Pour utiliser la fonction conversation(), le plugin doit passer un tableau de struct sudo_conv_message et struct sudo_conv_reply. Il doit y avoir une struct sudo_conv_message et une struct sudo_conv_reply pour chaque message de la conversation, c'est-à-dire que les deux tableaux doivent avoir le même nombre d'éléments. Chaque struct sudo_conv_reply doit avoir son membre reply initialisé à NULL. Le pointeur struct sudo_conv_callback, s'il n'est pas NULL, doit contenir des pointeurs de fonction à appeler lorsque le processus sudo est suspendu et/ou repris pendant l'entrée de la conversation. Les fonctions on_suspend et on_resume sont appelées avec le signal qui a provoqué la suspension de sudo et le pointeur closure de la struct sudo_conv_callback. Ces fonctions doivent renvoyer 0 en cas de succès et -1 en cas d'erreur. En cas d'erreur, la conversation se terminera et la fonction de conversation renverra la valeur -1. L'utilisation prévue est de permettre au plugin de libérer des ressources, telles que des verrous, qui ne doivent pas être détenues indéfiniment pendant la suspension, puis de les réacquérir lorsque le processus est repris. Les fonctions ne sont pas réellement invoquées depuis un gestionnaire de signaux.

La variable msg_type doit être définie sur l'une des valeurs suivantes :

SUDO_CONV_PROMPT_ECHO_OFF
Inviter l'utilisateur à saisir avec l'écho désactivé ; ceci est généralement utilisé pour les mots de passe. La réponse sera stockée dans le tableau replies, et elle ne sera jamais NULL.
SUDO_CONV_PROMPT_ECHO_ON
Inviter l'utilisateur à saisir avec l'écho activé. La réponse sera stockée dans le tableau replies, et elle ne sera jamais NULL.
SUDO_CONV_ERROR_MSG
Afficher un message d'erreur. Le message est écrit sur la sortie d'erreur standard, sauf si le drapeau SUDO_CONV_PREFER_TTY est défini, auquel cas il est écrit sur le terminal de l'utilisateur si possible.
SUDO_CONV_INFO_MSG
Afficher un message. Le message est écrit sur la sortie standard, sauf si le drapeau SUDO_CONV_PREFER_TTY est défini, auquel cas il est écrit sur le terminal de l'utilisateur si possible.
SUDO_CONV_PROMPT_MASK
Inviter l'utilisateur à saisir, mais faire écho d'un astérisque pour chaque caractère lu. La réponse sera stockée dans le tableau replies, et elle ne sera jamais NULL. Ceci peut être utilisé pour fournir un retour visuel à l'utilisateur lors de la lecture d'informations sensibles qui ne devraient pas être affichées.

En plus des valeurs ci-dessus, les bits de drapeau suivants peuvent également être définis :

SUDO_CONV_PROMPT_ECHO_OK
Autoriser la lecture de l'entrée lorsque l'écho ne peut pas être désactivé lorsque le type de message est SUDO_CONV_PROMPT_ECHO_OFF ou SUDO_CONV_PROMPT_MASK. Par défaut, sudo refusera de lire l'entrée si l'écho ne peut pas être désactivé pour ces types de messages.
SUDO_CONV_PREFER_TTY
Lors de l'affichage d'un message via SUDO_CONV_ERROR
_MSG ou SUDO_CONV_INFO_MSG, essayez d'écrire le message dans le terminal de l'utilisateur. Si le terminal n'est pas disponible, le flux d'erreur standard ou le flux de sortie standard sera utilisé, selon que SUDO_CONV_ERROR_MSG ou SUDO_CONV_INFO_MSG a été utilisé. Le terminal de l'utilisateur est toujours utilisé lorsque cela est possible pour l'entrée, ce drapeau n'est utilisé que pour la sortie.

Le timeout en secondes pendant lequel la requête attendra l'absence d'entrée. Une valeur nulle implique un délai d'attente infini.

Le plugin est responsable de la libération du tampon de réponse situé dans chaque struct sudo_conv_reply, s'il n'est pas NULL. SUDO_CONV_REPL_MAX représente la longueur maximale du tampon de réponse (sans inclure le caractère NUL final). En pratique, il s'agit du mot de passe le plus long que sudo supportera.

La fonction de style printf() utilise le même mécanisme sous-jacent que la fonction conversation() mais ne prend en charge que SUDO_CONV_INFO_MSG et SUDO_CONV_ERROR_MSG pour le paramètre msg_type. Elle peut être plus pratique que d'utiliser la fonction conversation() si aucune réponse de l'utilisateur n'est nécessaire et prend en charge les séquences d'échappement standard de printf().

Voir le plugin d'exemple pour un exemple d'utilisation de la fonction conversation().

Ordre d'invocation des plugins

À partir de sudo 1.9.0, les fonctions open() et close() du plugin sont appelées dans l'ordre suivant :

  1. ouverture audit
  2. ouverture politique
  3. ouverture approbation
  4. fermeture approbation
  5. ouverture journalisation E/S
  6. exécution de la commande
  7. sortie de la commande
  8. fermeture journalisation E/S
  9. fermeture politique
  10. fermeture audit
  11. sortie de sudo

Avant sudo 1.9.0, la fonction close() du journal d'E/S était appelée après la fonction close() de la politique.

API des plugins de groupe sudoers

Le plugin sudoers prend en charge sa propre interface de plugin pour permettre la recherche de groupes non-Unix. Cela peut être utilisé pour interroger une source de groupe autre que la base de données de groupes Unix standard. Deux exemples de plugins de groupe sont fournis avec sudo, group_file et system_group, sont détaillés dans sudoers(5). Les plugins de groupe tiers incluent un plugin QAS AD disponible auprès de Quest Software.

Un plugin de groupe doit déclarer et peupler une struct sudoers_group_plugin dans la portée globale. Cette structure contient des pointeurs vers les fonctions qui implémentent l'initialisation, le nettoyage et la recherche de groupe du plugin.

struct sudoers_group_plugin {
    unsigned int version;
    int (*init)(int version, sudo_printf_t sudo_plugin_printf,
        char *const argv[]);
    void (*cleanup)(void);
    int (*query)(const char *user, const char *group,
        const struct passwd *pwd);
};

Une struct sudoers_group_plugin a les champs suivants :

version
Le champ version doit être défini sur GROUP_API_VERSION.

Cela permet à sudoers de déterminer la version de l'API pour laquelle le plugin de groupe a été compilé.

init
int (*init)(int version, sudo_printf_t sudo_plugin_printf,
    char *const argv[]);

La fonction init() est appelée après l'analyse de sudoers mais avant toutes les vérifications de politique. Elle renvoie 1 en cas de succès, 0 en cas d'échec (ou si le plugin n'est pas configuré), et -1 en cas d'erreur. Si une erreur se produit, le plugin peut appeler la fonction plugin_printf() avec SUDO_CONF_ERROR_MSG pour présenter des informations d'erreur supplémentaires à l'utilisateur.

Les arguments de la fonction sont les suivants :

version
La version transmise par sudoers permet au plugin de déterminer le numéro de version majeure et mineure de l'API de plugin de groupe prise en charge par sudoers.
plugin_printf
Un pointeur vers une fonction de style printf() qui peut être utilisée pour afficher des messages informatifs ou des messages d'erreur à l'utilisateur. Renvoie le nombre de caractères imprimés en cas de succès et -1 en cas d'échec.
argv
Un tableau d'arguments se terminant par NULL, généré à partir de l'option group_plugin dans sudoers. Si aucun argument n'a été donné, argv sera NULL.
cleanup
void (*cleanup)();

La fonction cleanup() est appelée lorsque sudoers a terminé ses vérifications de groupe. Le plugin doit libérer toute mémoire qu'il a allouée et fermer les descripteurs de fichiers ouverts.

query
int (*query)(const char *user, const char *group,
    const struct passwd *pwd);

La fonction query() est utilisée pour demander au plugin de groupe si user est membre de group.

Les arguments de la fonction sont les suivants :

user
Le nom de l'utilisateur recherché dans la base de données de groupe externe.
group
Le nom du groupe interrogé.
pwd
L'entrée de la base de données des mots de passe pour user, le cas échéant. Si user n'est pas présent dans la base de données des mots de passe, pwd sera NULL.

DESCRIPTION

The sudo program supports plug-ins that can be used to extend its functionality. The plug-in API is described in this manual page.

New plug-ins can be written to implement authentication, command authorization, logging, or other functionality. The plug-in API is designed to be extensible and versioned, so that plug-ins can be updated independently of the sudo binary.

This man page documents the plug-in API as it exists in the current version of sudo. For information on older versions, see the PLUGIN API CHANGELOG section.
