SUDOERS.LDAP(5) Manuel des formats de fichiers SUDOERS.LDAP(5)

NOM

sudoers.ldap — Configuration LDAP de sudo

DESCRIPTION

En plus du fichier sudoers standard, sudo peut être configuré via LDAP. Cela peut être particulièrement utile pour synchroniser sudoers dans un environnement distribué et de grande taille.

L'utilisation de LDAP pour sudoers présente plusieurs avantages :

  • sudo n'a plus besoin de lire sudoers dans son intégralité. Lorsque LDAP est utilisé, il n'y a que deux ou trois requêtes LDAP par invocation. Cela le rend particulièrement rapide et utilisable dans les environnements LDAP.
  • Il est possible de spécifier des options par entrée qui remplacent les options globales par défaut. /etc/sudoers ne prend en charge que les options globales et des options limitées associées aux utilisateurs/hôtes/commandes/alias. La syntaxe est compliquée et peut être difficile à comprendre pour les utilisateurs. Placer les options directement dans l'entrée est plus naturel.
  • Le programme visudo n'est plus nécessaire. visudo assure le verrouillage et la vérification de la syntaxe du fichier /etc/sudoers. Étant donné que les mises à jour LDAP sont atomiques, le verrouillage n'est plus nécessaire. Comme la syntaxe est vérifiée lors de l'insertion des données dans LDAP, il n'y a pas besoin d'un outil spécialisé pour vérifier la syntaxe.

Conteneur LDAP SUDOers

La configuration de sudoers est contenue dans le conteneur LDAP ‘ou=SUDOers’.

Sudo recherche d'abord l'entrée ‘cn=defaults’ dans le conteneur SUDOers. Si elle est trouvée, l'attribut multi-valeur sudoOption est analysé de la même manière qu'une ligne Defaults globale dans /etc/sudoers. Dans l'exemple suivant, la variable SSH_AUTH_SOCK sera conservée dans l'environnement pour tous les utilisateurs.

dn: cn=defaults,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: defaults
description: Default sudoOption's go here
sudoOption: env_keep+=SSH_AUTH_SOCK

L'équivalent d'un sudoer dans LDAP est un sudoRole. Il se compose des attributs suivants :

sudoUser
Un nom d'utilisateur, un identifiant utilisateur (précédé de ‘#’), un nom de groupe Unix ou un identifiant (précédé de ‘%’ ou ‘%#’ respectivement), un netgroup d'utilisateurs (précédé de ‘+’), ou un nom de groupe non-Unix ou un identifiant (précédé de ‘%:’ ou ‘%:#’ respectivement). Les netgroups d'utilisateurs sont comparés en utilisant uniquement les membres utilisateur et domaine ; le membre hôte n'est pas utilisé lors de la comparaison. Le support des groupes non-Unix n'est disponible que lorsqu'un group_plugin approprié est défini dans l'objet defaults global sudoRole. Si une entrée sudoUser est précédée d'un point d'exclamation, ‘!’, et que l'entrée correspond, le sudoRole dans lequel elle se trouve sera ignoré. Les entrées sudoUser niées ne sont prises en charge que par la version 1.9.9 ou supérieure.
sudoHost
Un nom d'hôte, une adresse IP, un réseau IP ou un netgroup d'hôtes (précédé d'un ‘+’). La valeur spéciale ALL correspondra à n'importe quel hôte. Les netgroups d'hôtes sont comparés en utilisant uniquement les membres hôte (qualifiés et non qualifiés) et domaine ; le membre utilisateur n'est pas utilisé lors de la comparaison. Si une entrée sudoHost est précédée d'un point d'exclamation, ‘!’, et que l'entrée correspond, le sudoRole dans lequel elle se trouve sera ignoré. Les entrées sudoHost niées ne sont prises en charge que par la version 1.8.18 ou supérieure.
sudoCommand
Un nom de commande Unix entièrement qualifié avec des arguments de ligne de commande optionnels, incluant potentiellement des caractères jokers (aussi appelés wildcards). Si un nom de commande est précédé d'un point d'exclamation, ‘!’, l'utilisateur sera interdit d'exécuter cette commande.

La commande intégrée “sudoedit” est utilisée pour permettre à un utilisateur d'exécuter sudo avec l'option -e (ou comme sudoedit). Elle peut prendre des arguments de ligne de commande comme une commande normale. Contrairement aux autres commandes, “sudoedit” est intégré dans sudo lui-même et doit être spécifié sans chemin d'accès.

La valeur spéciale ALL correspondra à n'importe quelle commande.

Si un nom de commande est précédé d'une empreinte SHA-2, il ne sera autorisé que si l'empreinte correspond. Cela peut être utile dans les situations où l'utilisateur qui invoque sudo a un accès en écriture à la commande ou à son répertoire parent. Les formats d'empreinte suivants sont pris en charge : sha224, sha256, sha384 et sha512. Le nom de l'empreinte doit être suivi d'un deux-points (‘:’) puis de l'empreinte réelle, au format hexadécimal ou base64. Par exemple, étant donné la valeur suivante pour sudoCommand :

sha224:0GomF8mNN3wlDt1HD9XldjJ3SNgpFdbjO1+NsQ /bin/ls

L'utilisateur ne pourra exécuter /bin/ls que si son empreinte sha224 correspond à la valeur spécifiée. Les empreintes de commande ne sont prises en charge que par la version 1.8.7 ou supérieure.

sudoOption
Identique en fonction aux options globales décrites ci-dessus, mais spécifique au sudoRole dans lequel il réside.
sudoRunAsUser
Un nom d'utilisateur ou un identifiant utilisateur (précédé de ‘#’) sous lequel les commandes peuvent être exécutées ou un groupe Unix (précédé d'un ‘%’) ou un netgroup d'utilisateurs (précédé d'un ‘+’) contenant une liste d'utilisateurs sous lesquels les commandes peuvent être exécutées. La valeur spéciale ALL correspondra à n'importe quel utilisateur. Si une entrée sudoRunAsUser est précédée d'un point d'exclamation, ‘!’, et que l'entrée correspond, le sudoRole dans lequel elle se trouve sera ignoré. Si sudoRunAsUser est spécifié mais vide, il correspondra à l'utilisateur appelant. Si ni sudoRunAsUser ni sudoRunAsGroup ne sont présents, la valeur de l'option runas_default sudoOption est utilisée (par défaut, root).

L'attribut sudoRunAsUser n'est disponible que dans les versions 1.7.0 et supérieures de sudo. Les versions antérieures de sudo utilisent l'attribut sudoRunAs à la place. Les entrées sudoRunAsUser niées ne sont prises en charge que par la version 1.8.26 ou supérieure.

sudoRunAsGroup
Un groupe Unix ou un identifiant de groupe (précédé de ‘#’) sous lequel les commandes peuvent être exécutées. La valeur spéciale ALL correspondra à n'importe quel groupe. Si une entrée sudoRunAsGroup est précédée d'un point d'exclamation, ‘!’, et que l'entrée correspond, le sudoRole dans lequel elle se trouve sera ignoré.

L'attribut sudoRunAsGroup n'est disponible que dans les versions 1.7.0 et supérieures de sudo. Les entrées sudoRunAsGroup niées ne sont prises en charge que par la version 1.8.26 ou supérieure.

LDAP sudoers

The sudo utility can be configured to read its rules from an LDAP directory. This allows for centralized rule management and is useful in larger environments or when rules need to be shared across multiple hosts.

Sudoers attributes

The following attributes are used to represent sudo rules in LDAP:

sudoUser
A user name or a group name (prefixed with a `%` character) for which the rule applies. Wildcards are allowed. If multiple sudoUser entries are present, the rule applies if the user matches any of them.
sudoHost
A host name or a netgroup name (prefixed with a `+` character) for which the rule applies. Wildcards are allowed. If multiple sudoHost entries are present, the rule applies if the host matches any of them.
sudoCommand
A command path or a command pattern for which the rule applies. Wildcards are allowed. Commands may be negated by prefixing with a `!` character. If multiple sudoCommand entries are present, the rule applies if the command matches any of them (respecting negation).
sudoRunAsUser
A user name or a user pattern for which the command may be run. Wildcards are allowed. A special value of `ALL` matches any user. If multiple sudoRunAsUser entries are present, the rule applies if the user matches any of them.
sudoRunAsGroup
A group name or a group pattern for which the command may be run. Wildcards are allowed. A special value of `ALL` matches any group. If multiple sudoRunAsGroup entries are present, the rule applies if the group matches any of them.
sudoOption
A sudo option to be applied to this rule. For example, `!authenticate` to disable authentication for this rule. If multiple sudoOption entries are present, all are applied.
sudoOrder
An integer that determines the order of evaluation for rules. Lower values are evaluated first. If multiple rules match, the one with the lowest sudoOrder value is used. If sudoOrder is not specified, a default value is used.
sudoNotBefore
A timestamp in the form ‘yyyymmddHHMMSSZ’ that indicates a start date/time, before which the sudoRole is not valid. If multiple sudoNotBefore entries are present, the earliest is used. Timestamps must be in Coordinated Universal Time (UTC), not the local timezone. The minute and seconds portions are optional, but some LDAP servers require that they be present (contrary to the RFC).

The sudoNotBefore attribute is only available in sudo versions 1.7.5 and higher and must be explicitly enabled via the SUDOERS_TIMED option in /etc/openldap/ldap.conf.

sudoNotAfter
A timestamp in the form ‘yyyymmddHHMMSSZ’ that indicates an expiration date/time, after which the sudoRole will no longer be valid. If multiple sudoNotAfter entries are present, the last one is used. Timestamps must be in Coordinated Universal Time (UTC), not the local timezone. The minute and seconds portions are optional, but some LDAP servers require that they be present (contrary to the RFC).

The sudoNotAfter attribute is only available in sudo versions 1.7.5 and higher and must be explicitly enabled via the SUDOERS_TIMED option in /etc/openldap/ldap.conf.

sudoOrder
The sudoRole entries retrieved from the LDAP directory have no inherent order. The sudoOrder attribute is an integer (or floating point value for LDAP servers that support it) that is used to sort the matching entries. This allows LDAP-based sudoers entries to more closely mimic the behavior of the sudoers file, where the order of the entries influences the result. If multiple entries match, the entry with the highest sudoOrder attribute is chosen. This corresponds to the “last match” behavior of the sudoers file. If the sudoOrder attribute is not present, a value of 0 is assumed.

The sudoOrder attribute is only available in sudo versions 1.7.5 and higher.

Each attribute listed above should contain a single value, but there may be multiple instances of each attribute type. A sudoRole must contain at least one sudoUser, sudoHost, and sudoCommand.

The following example allows users in group wheel to run any command on any host via sudo:

dn: cn=%wheel,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: %wheel
sudoUser: %wheel
sudoHost: ALL
sudoCommand: ALL

Anatomy of LDAP sudoers lookup

When looking up a sudoer using LDAP there are only two or three LDAP queries per invocation. The first query is to parse the global options. The second is to match against the user's name and the groups that the user belongs to. (The special ALL tag is matched in this query too.) If no match is returned for the user's name and groups, a third query returns all entries containing user netgroups and other non-Unix groups and checks to see if the user belongs to any of them.

If timed entries are enabled with the SUDOERS_TIMED parameter, the LDAP queries include a sub-filter that limits retrieval to entries that satisfy the time constraints, if any.

If the NETGROUP_BASE parameter is present and NETGROUP_QUERY has not been disabled (see Configuring ldap.conf below), queries are performed to determine the list of netgroups the user belongs to before the sudoers query. This makes it possible to include netgroups in the sudoers query string in the same manner as Unix groups. The third query mentioned above is not performed unless a group provider plugin is also configured. The actual LDAP queries performed by sudo are as follows:

  1. Match all nisNetgroup records with a nisNetgroupTriple containing the user, host, and NIS domain. The query will match nisNetgroupTriple entries with either the short or long form of the host name or no host name specified in the tuple. If the NIS domain is set, the query will only match entries that include the domain or for which there is no domain present. If the NIS domain is not set, a wildcard is used to match any domain name but be aware that the NIS schema used by some LDAP servers may not support wild cards for nisNetgroupTriple.
  2. Repeated queries are performed to find any nested nisNetgroup records with a memberNisNetgroup entry that refers to an already-matched record.

For sites with a large number of netgroups, using NETGROUP_BASE can significantly speed up sudo's execution time as long as the LDAP server supports querying the nisNetgroup object by its nisNetgroupTriple attribute.

Differences between LDAP and non-LDAP sudoers

One of the major differences between LDAP and file-based sudoers is that in LDAP, sudo-specific Aliases are not supported.

For the most part, there is little need for sudo-specific Aliases. Unix groups, non-Unix groups (via the group_plugin), or user netgroups can be used in place of User_Aliases and Runas_Aliases. Host netgroups can be used in place of Host_Aliases. Since groups and netgroups can also be stored in LDAP there is no real need for sudo-specific aliases.

There are also some subtle differences in the way sudoers is handled once in LDAP. Probably the biggest is that according to the RFC, LDAP ordering is arbitrary and you cannot expect that Attributes and Entries are returned in any specific order.

The order in which different entries are applied can be controlled using the sudoOrder attribute, but there is no way to guarantee the order of attributes within a specific entry. If there are conflicting command rules in an entry, the negative takes precedence. This is called paranoid behavior (not necessarily the most specific match).

Here is an example:

# /etc/sudoers:
# Allow all commands except shell
johnny  ALL=(root) ALL,!/bin/sh
# Always allows all commands because ALL is matched last
puddles ALL=(root) !/bin/sh,ALL

# LDAP equivalent of johnny
# Allows all commands except shell
dn: cn=role1,ou=Sudoers,dc=my-domain,dc=com
objectClass: sudoRole
objectClass: top
cn: role1
sudoUser: johnny
sudoHost: ALL
sudoCommand: ALL
sudoCommand: !/bin/sh

# LDAP equivalent of puddles
# Notice that even though ALL comes last, it still behaves like
# role1 since the LDAP code assumes the more paranoid configuration
dn: cn=role2,ou=Sudoers,dc=my-domain,dc=com
objectClass: sudoRole
objectClass: top
cn: role2
sudoUser: puddles
sudoHost: ALL
sudoCommand: !/bin/sh
sudoCommand: ALL

Converting between file-based and LDAP sudoers

The cvtsudoers(1) utility can be used to convert between file-based and LDAP sudoers. However, there are features in the file-based sudoers that have no equivalent in LDAP-based sudoers (and vice versa). These cannot be converted automatically.

For example, a Cmnd_Alias in a sudoers file may be converted to a sudoRole that contains multiple commands. Multiple users and/or groups may be assigned to the sudoRole.

Also, host, user, runas, and command-based Defaults entries are not supported. However, a sudoRole may contain one or more sudoOption attributes which can often serve the same purpose.

Consider the following sudoers lines:

Cmnd_Alias PAGERS = /usr/bin/more, /usr/bin/pg, /usr/bin/less
Defaults!PAGERS noexec
alice, bob ALL = ALL

In this example, alice and bob are allowed to run all commands, but the commands listed in PAGERS will have the noexec flag set, preventing shell escapes.

When converting this to LDAP, two sudoRole objects can be used:

dn: cn=PAGERS,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: PAGERS
sudoUser: alice
sudoUser: bob
sudoHost: ALL
sudoCommand: /usr/bin/more
sudoCommand: /usr/bin/pg
sudoCommand: /usr/bin/less
sudoOption: noexec
sudoOrder: 900

dn: cn=ADMINS,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: ADMINS
sudoUser: alice
sudoUser: bob
sudoHost: ALL
sudoCommand: ALL
sudoOrder: 100

In the LDAP version, the sudoOrder attribute is used to guarantee that the PAGERS sudoRole with noexec has precedence. Unlike the sudoers version, the LDAP version requires that all users for whom the restriction should apply be assigned to the PAGERS sudoRole. Using a Unix group or netgroup in PAGERS rather than listing each user would make this easier to maintain.

Per-user Defaults entries can be emulated by using one or more sudoOption attributes in a sudoRole. Consider the following sudoers lines:

User_Alias ADMINS = john, sally
Defaults:ADMINS !authenticate
ADMINS ALL = (ALL:ALL) ALL

In this example, john and sally are allowed to run any command as any user or group.

When converting this to LDAP, we can use a Unix group instead of the User_Alias.

dn: cn=admins,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: admins
sudoUser: %admin
sudoHost: ALL
sudoRunAsUser: ALL
sudoRunAsGroup: ALL
sudoCommand: ALL
sudoOption: !authenticate

This assumes that users john and sally are members of the “admins” Unix group.

Sudoers schema

To use LDAP as a backend for sudo, you will need to define the sudoers schema in your LDAP directory. The schema defines the object classes and attributes used to store sudo rules. A typical sudoers schema includes the sudoRole object class and attributes such as sudoUser, sudoHost, sudoCommand, etc.

You can find example sudoers schemas in the sudo distribution package, typically in a file named sudo.schema. You will need to adapt this schema to your specific LDAP server and environment.

Configuration de ldap.conf

Sudo lit le fichier /etc/openldap/ldap.conf pour la configuration spécifique à LDAP. Généralement, ce fichier est partagé entre différents clients conscients de LDAP. À ce titre, la plupart des paramètres ne sont pas spécifiques à sudo. Le fichier /etc/openldap/ldap.conf est analysé par sudo lui-même et peut prendre en charge des options qui diffèrent de celles décrites dans le manuel du système ldap.conf(5). Le chemin d'accès à ldap.conf peut être remplacé via l'argument du plugin ldap_conf dans sudo.conf(5).

Sur les systèmes utilisant les bibliothèques OpenLDAP, les valeurs par défaut spécifiées dans /etc/openldap/ldap.conf ou les fichiers .ldaprc de l'utilisateur ne sont pas utilisées.

sudo prend en charge une variété d'implémentations de bibliothèques LDAP, y compris OpenLDAP, dérivées de Netscape (également utilisées par Solaris et HP-UX), et IBM LDAP (également appelé Tivoli). Certaines options sont spécifiques à certaines implémentations LDAP ou ont un comportement spécifique à l'implémentation. Ces différences sont notées ci-dessous le cas échéant.

Seules les options explicitement répertoriées dans /etc/openldap/ldap.conf comme étant prises en charge par sudo sont honorées. Les options de configuration sont listées ci-dessous en majuscules mais sont analysées de manière indépendante de la casse.

Les lignes commençant par un signe dièse (‘#’) sont ignorées. Les espaces blancs en début de ligne sont supprimés.

BIND_TIMELIMIT secondes
Le paramètre BIND_TIMELIMIT spécifie le temps, en secondes, à attendre lors de la tentative de connexion à un serveur LDAP. Si plusieurs URI ou HOST sont spécifiés, c'est le temps à attendre avant d'essayer le suivant dans la liste.
BINDDN DN
Le paramètre BINDDN spécifie l'identité, sous la forme d'un Nom Distingué (DN), à utiliser lors de l'exécution d'opérations LDAP. S'il n'est pas spécifié, les opérations LDAP sont effectuées avec une identité anonyme. Par défaut, la plupart des serveurs LDAP autorisent l'accès anonyme.
BINDPW secret
Le paramètre BINDPW spécifie le mot de passe à utiliser lors de l'exécution d'opérations LDAP. Ceci est généralement utilisé en conjonction avec le paramètre BINDDN. Le secret peut être un mot de passe en clair ou une chaîne encodée en base64 avec un préfixe “base64:”. Par exemple : 
BINDPW base64:dGVzdA==

Si un mot de passe en clair est utilisé, il doit s'agir d'une chaîne simple sans guillemets. Les mots de passe en clair ne peuvent pas contenir le caractère de commentaire (‘#’) et l'échappement des caractères spéciaux avec une barre oblique inversée (‘\’) n'est pas pris en charge.

DEREF jamais/en_recherche/en_trouvant/toujours
Comment le déréférencement des alias doit être effectué lors de la recherche. Voir le manuel ldap.conf(5) pour une description complète de cette option.
HOST nom[:port] ...
Si aucune URI n'est spécifiée (voir ci-dessous), le paramètre HOST spécifie une liste de serveurs LDAP délimitée par des espaces blancs à connecter. Chaque hôte peut inclure un port optionnel séparé par un deux-points (‘:’). Le paramètre HOST est déprécié au profit de la spécification URI et n'est inclus que pour la compatibilité ascendante.
KRB5_CCNAME nom_de_fichier
Le chemin d'accès au cache d'informations d'identification Kerberos 5 à utiliser lors de l'authentification auprès du serveur distant.

Cette option n'est pertinente que lors de l'utilisation de l'authentification SASL (voir ci-dessous).

LDAP_VERSION nombre
La version du protocole LDAP à utiliser lors de la connexion au serveur. La valeur par défaut est le protocole version 3.
NETGROUP_BASE base
Le DN de base à utiliser lors de l'exécution de requêtes LDAP de netgroup. Typiquement, il s'agit de la forme ‘ou=netgroup,dc=mon-domaine,dc=com’ pour le domaine mon-domaine.com. Plusieurs lignes NETGROUP_BASE peuvent être spécifiées, auquel cas elles sont interrogées dans l'ordre spécifié.

Lorsque cette option est activée, sudo interrogera directement le serveur LDAP lors de la correspondance des netgroups présentes dans un sudoRole au lieu de s'appuyer sur la fonction innetgr() de la bibliothèque C.

De plus, si le paramètre NETGROUP_QUERY (qui est activé par défaut) n'a pas été désactivé, les netgroups de l'utilisateur seront directement interrogées via LDAP pour être utilisées dans la requête sudoers principale. C'est généralement plus rapide que de récupérer chaque objet sudoRole contenant un sudoUser commençant par un préfixe ‘+’ et de vérifier si l'utilisateur en est membre. Le schéma NIS utilisé par certains serveurs LDAP nécessite une modification pour prendre en charge l'interrogation de l'objet nisNetgroup par son attribut nisNetgroupTriple. Par exemple, slapd d'OpenLDAP nécessite la modification suivante de l'attribut nisNetgroupTriple :

attributetype ( 1.3.6.1.1.1.1.14 NAME 'nisNetgroupTriple'
   DESC 'Triple de Netgroup'
   EQUALITY caseIgnoreIA5Match
   SUBSTR caseIgnoreIA5SubstringsMatch
   SYNTAX 1.3.6.1.4.1.1466.115.121.1.26 )

Avant d'activer NETGROUP_BASE, vous devez vérifier que votre serveur LDAP prend en charge la correspondance de nisNetgroupTriple. Par exemple, en utilisant ldapsearch :

$ ldapsearch -b $NETGROUP_BASE \
  '(&(objectClass=nisNetgroup)(nisNetgroupTriple=\28*,UTILISATEUR,\29))'

où vos données nisNetgroup incluent un objet avec le nisNetgroupTriple suivant :

nisNetgroupTriple: (,UTILISATEUR,)
NETGROUP_QUERY activé/vrai/oui/désactivé/faux/non
Le paramètre NETGROUP_QUERY indique si le serveur LDAP prend en charge l'interrogation des objets nisNetgroup en faisant correspondre les attributs nisNetgroupTriple. Par défaut, sudoers s'attend à pouvoir effectuer des requêtes qui correspondent aux attributs nisNetgroupTriple lorsque NETGROUP_BASE est défini, mais tous les serveurs LDAP ne le prennent pas en charge.

Si NETGROUP_QUERY est désactivé, sudoers ne tentera pas de déterminer la liste des netgroups dont l'utilisateur fait partie, mais utilisera toujours NETGROUP_BASE directement lors de la correspondance des netgroups. Cela peut être utilisé pour prendre en charge les netgroups sur les systèmes qui n'ont pas la fonction de bibliothèque C innetgr(). Voir la description du paramètre NETGROUP_BASE pour plus d'informations.

NETGROUP_SEARCH_FILTER filtre_ldap
Un filtre LDAP utilisé pour restreindre l'ensemble des enregistrements retournés lors de l'exécution d'une requête LDAP de netgroup. Typiquement, il s'agit de la forme ‘attribut=valeur’ ou ‘(&(attribut=valeur)(attribut2=valeur2))’. Le filtre de recherche par défaut est : ‘objectClass=nisNetgroup’. Si ldap_filter est omis, aucun filtre de recherche ne sera utilisé.

Cette option n'est utilisée que lors de l'interrogation directe des netgroups via LDAP.

NETWORK_TIMEOUT secondes
Un alias pour BIND_TIMELIMIT fourni pour la compatibilité OpenLDAP.
PORT numéro_de_port
Si aucune URI n'est spécifiée, le paramètre PORT spécifie le port par défaut auquel se connecter sur le serveur LDAP si un paramètre HOST ne spécifie pas lui-même le port. S'il n'y a pas de sudoPORT défini, le port LDAP par défaut (généralement 389) est utilisé.
PORT port
Le paramètre PORT spécifie le port LDAP à utiliser. Si le paramètre URI est spécifié, ce paramètre est ignoré. Le port par défaut est le port 389 pour LDAP et le port 636 pour LDAP sur TLS (SSL). Le paramètre PORT est obsolète en faveur de la spécification URI et n'est conservé que pour la compatibilité ascendante.
ROOTBINDDN DN
Le paramètre ROOTBINDDN spécifie l'identité, sous forme de Nom Distinctif (DN), à utiliser lors de l'exécution d'opérations LDAP privilégiées, telles que les requêtes sudoers. Le mot de passe correspondant à l'identité doit être stocké dans le fichier spécifié par l'argument de plugin ldap_secret dans sudo.conf(5), qui est par défaut /etc/ldap.secret. Si aucun ROOTBINDDN n'est spécifié, l'identité BINDDN est utilisée (le cas échéant).
ROOTUSE_SASL on/true/yes/off/false/no
Activez ROOTUSE_SASL pour activer l'authentification SASL lors de la connexion à un serveur LDAP depuis un processus privilégié, tel que sudo.
SASL_AUTH_ID identité
Le nom d'utilisateur SASL à utiliser lors de la connexion au serveur LDAP. Par défaut, sudo utilisera une connexion anonyme.

Cette option n'est pertinente que lorsque l'authentification SASL est utilisée.

SASL_MECH mécanismes
Une liste d'espaces délimités des mécanismes d'authentification SASL à utiliser. Par défaut, sudo utilisera l'authentification GSSAPI.
SASL_SECPROPS none/propriétés
Propriétés de sécurité SASL ou none pour aucune propriété. Voir le manuel du programmeur SASL pour plus de détails.

Cette option n'est pertinente que lorsque l'authentification SASL est utilisée.

SSL on/true/yes/off/false/no
Si le paramètre SSL est défini sur on, true, ou yes, le chiffrement TLS (SSL) est toujours utilisé lors de la communication avec le serveur LDAP. Typiquement, cela implique de se connecter au serveur sur le port 636 (ldaps).
SSL start_tls
Si le paramètre SSL est défini sur start_tls, la connexion au serveur LDAP est initiée normalement et le chiffrement TLS est commencé avant l'envoi des identifiants de liaison. Cela présente l'avantage de ne pas nécessiter un port dédié pour les communications chiffrées. Ce paramètre n'est pris en charge que par les serveurs LDAP qui respectent l'extension start_tls, tels que les serveurs OpenLDAP et IBM Tivoli Directory.
SUDOERS_BASE base
Le DN de base à utiliser lors de l'exécution de requêtes LDAP sudo. Généralement, il se présente sous la forme ‘ou=SUDOers,dc=mon-domaine,dc=com’ pour le domaine mon-domaine.com. Plusieurs lignes SUDOERS_BASE peuvent être spécifiées, auquel cas elles sont interrogées dans l'ordre spécifié.
SUDOERS_DEBUG niveau_debug
Ceci définit le niveau de débogage pour les requêtes LDAP de sudo. Les informations de débogage sont imprimées sur la sortie d'erreur standard. Une valeur de 1 produit une quantité modérée d'informations de débogage. Une valeur de 2 montre les résultats des correspondances elles-mêmes. Ce paramètre ne doit pas être défini dans un environnement de production car les informations supplémentaires sont susceptibles de confondre les utilisateurs.

Le paramètre SUDOERS_DEBUG est obsolète et sera supprimé dans une future version. Les mêmes informations sont maintenant enregistrées via le framework de débogage de sudo en utilisant le sous-système “ldap” aux priorités diag et info pour les valeurs de niveau_debug 1 et 2 respectivement. Voir le manuel de sudo.conf(5) pour plus de détails sur la configuration du débogage de sudo.

SUDOERS_SEARCH_FILTER filtre_ldap
Un filtre LDAP utilisé pour restreindre l'ensemble des enregistrements retournés lors de l'exécution d'une requête LDAP sudo. Typiquement, il se présente sous la forme ‘attribut=valeur’ ou ‘(&(attribut=valeur)(attribut2=valeur2))’. Le filtre de recherche par défaut est : ‘objectClass=sudoRole’. Si filtre_ldap est omis, aucun filtre de recherche ne sera utilisé.
SUDOERS_TIMED on/true/yes/off/false/no
Indique si les attributs sudoNotBefore et sudoNotAfter, qui implémentent les entrées sudoers dépendantes du temps, doivent être évalués ou non.
TIMELIMIT secondes
Le paramètre TIMELIMIT spécifie le temps, en secondes, à attendre pour une réponse à une requête LDAP.
TIMEOUT secondes
Le paramètre TIMEOUT spécifie le temps, en secondes, à attendre pour une réponse des différentes API LDAP.
TLS_CACERT nom_fichier
Un alias pour TLS_CACERTFILE pour la compatibilité OpenLDAP.
TLS_CACERTFILE nom_fichier
Le chemin d'accès à un paquet d'autorité de certification qui contient les certificats de toutes les autorités de certification que le client sait être valides, par exemple, /etc/ssl/ca-bundle.pem.

Cette option n'est prise en charge que par les bibliothèques OpenLDAP. Les bibliothèques LDAP dérivées de Netscape utilisent la même base de données de certificats pour les certificats CA et client (voir TLS_CERT).

TLS_CACERTDIR répertoire
Similaire à TLS_CACERTFILE mais au lieu d'un fichier, c'est un répertoire contenant des certificats d'autorité de certification individuels, par exemple, /etc/ssl/certs. Le répertoire spécifié par TLS_CACERTDIR est vérifié après TLS_CACERTFILE.

Cette option n'est prise en charge que par les bibliothèques OpenLDAP.

TLS_CERT nom_fichier
Le chemin d'accès à un fichier contenant le certificat client qui peut être utilisé pour authentifier le client auprès du serveur LDAP. Le type de certificat dépend des bibliothèques LDAP utilisées.
OpenLDAP:
‘tls_cert /etc/ssl/client_cert.pem’
Dérivé de Netscape:
‘tls_cert /var/ldap/cert7.db’
LDAP IBM:
Non utilisé, la base de données de clés spécifiée par TLS_KEY contient les clés et les certificats.

Lors de l'utilisation de bibliothèques dérivées de Netscape, ce fichier peut également contenir des certificats d'autorité de certification.

TLS_CHECKPEER on/true/yes/off/false/no
Si activé, TLS_CHECKPEER entraînera la vérification du certificat TLS du serveur LDAP. Si le certificat TLS du serveur ne peut pas être vérifié (généralement parce qu'il est signé par une autorité de certification inconnue), sudo ne pourra pas s'y connecter. Si TLS_CHECKPEER est désactivé, aucune vérification n'est effectuée. La désactivation de cette vérification crée une opportunité d'attaques man-in-the-middle car l'identité du serveur ne sera pas authentifiée. Si possible, le certificat de l'AC devrait être installé localement afin qu'il puisse être vérifié.

Cette option n'est pas prise en charge par les bibliothèques LDAP IBM.

TLS_KEY nom_fichier
Le chemin d'accès à un fichier contenant la clé privée qui correspond au certificat spécifié par TLS_CERT. La clé privée ne doit pas être protégée par un mot de passe. Le type de clé dépend des bibliothèques LDAP utilisées.
OpenLDAP:
‘tls_key /etc/ssl/client_key.pem’
Dérivé de Netscape:
‘tls_key /var/ldap/key3.db’
LDAP IBM:
‘tls_key /usr/ldap/ldapkey.kdb’

Lors de l'utilisation de bibliothèques LDAP IBM, ce fichier peut également contenir des certificats d'autorité de certification et clients et peut être chiffré.

TLS_CIPHERS liste_chiffrements
Le paramètre TLS_CIPHERS permet à l'administrateur de restreindre les algorithmes de chiffrement qui peuvent être utilisés pour les connexions TLS (SSL). Voir le manuel d'OpenLDAP ou d'IBM Tivoli Directory Server pour une liste des chiffrements valides.

Cette option n'est pas prise en charge par les bibliothèques dérivées de Netscape.

TLS_KEYPW secret
Le TLS_KEYPW contient le mot de passe utilisé pour décrypter la base de données de clés sur les clients utilisant la bibliothèque LDAP IBM. Le secret peut être un mot de passe en clair ou un
Motif codé en base64 avec un préfixe « base64 : ». Par exemple : 
TLS_KEYPW base64:dGVzdA==

Si un mot de passe en clair est utilisé, il doit s'agir d'une chaîne simple sans guillemets. Les mots de passe en clair ne peuvent pas inclure le caractère de commentaire (« # ») et l'échappement des caractères spéciaux avec une barre oblique inverse (« \ ») n'est pas pris en charge. Si cette option est utilisée, /etc/openldap/ldap.conf ne doit pas être lisible par tous afin d'éviter d'exposer le mot de passe. Alternativement, un fichier de stash peut être utilisé pour stocker le mot de passe sous forme chiffrée (voir ci-dessous).

Si aucun TLS_KEYPW n'est spécifié, un fichier de stash sera utilisé s'il existe. Le fichier de stash doit avoir le même chemin que le fichier spécifié par TLS_KEY, mais utiliser une extension de fichier « .sth » au lieu de « .kdb », par exemple « ldapkey.sth ». Le fichier par défaut « ldapkey.kdb » fourni avec IBM Tivoli Directory Server est chiffré avec le mot de passe « ssl_password ». L'utilitaire gsk8capicmd peut être utilisé pour gérer la base de données de clés et créer un fichier de stash.

Cette option n'est prise en charge que par les bibliothèques IBM LDAP.

TLS_REQCERT niveau
Le paramètre TLS_REQCERT contrôle comment le certificat TLS du serveur LDAP sera vérifié (le cas échéant). Si le certificat TLS du serveur ne peut pas être vérifié (généralement parce qu'il est signé par une autorité de certification inconnue), sudo ne pourra pas s'y connecter. Les valeurs de niveau suivantes sont prises en charge :
jamais
Le certificat du serveur ne sera ni demandé ni vérifié.
autoriser
Le certificat du serveur sera demandé. Un certificat manquant ou invalide est ignoré et n'est pas considéré comme une erreur.
essayer
Le certificat du serveur sera demandé. Un certificat manquant est ignoré, mais un certificat invalide entraînera une erreur de connexion.
exiger | dure
Le certificat du serveur sera demandé. Un certificat manquant ou invalide entraînera une erreur de connexion. C'est le comportement par défaut.

Cette option n'est prise en charge que par les bibliothèques OpenLDAP. Les autres bibliothèques LDAP ne prennent en charge que le paramètre TLS_CHECKPEER.

TLS_RANDFILE nom de fichier
Le paramètre TLS_RANDFILE spécifie le chemin d'un source d'entropie pour les systèmes qui manquent d'un périphérique aléatoire. Il est généralement utilisé en conjonction avec prngd ou egd.

Cette option n'est prise en charge que par les bibliothèques OpenLDAP.

URI ldap[s]://[nom d'hôte[:port]] ...
Spécifie une liste d'une ou plusieurs URIs séparées par des espaces décrivant le(s) serveur(s) LDAP à contacter. Le protocole peut être soit ldap ldaps, ce dernier étant pour les serveurs qui prennent en charge le chiffrement TLS (SSL). Si aucun port n'est spécifié, le port par défaut est 389 pour « ldap:// » ou le port 636 pour « ldaps:// ». Si aucun nom d'hôte n'est spécifié, sudo se connectera à localhost. Plusieurs lignes URI sont traitées de la même manière qu'une ligne URI contenant plusieurs entrées. Seuls les systèmes utilisant les bibliothèques OpenSSL prennent en charge le mélange des URIs « ldap:// » et « ldaps:// ». Les bibliothèques LDAP dérivées de Netscape et les bibliothèques IBM LDAP utilisées sur la plupart des versions commerciales d'Unix ne sont capables de prendre en charge qu'un ou l'autre.
USE_SASL activé/vrai/oui/désactivé/faux/non
Active USE_SASL pour les serveurs LDAP qui prennent en charge l'authentification SASL.
ROOTSASL_AUTH_ID identité
Le nom d'utilisateur SASL à utiliser lorsque ROOTUSE_SASL est activé.

Voir l'entrée ldap.conf dans la section EXEMPLES.

Configuration de nsswitch.conf

Sauf si elle est désactivée au moment de la compilation, sudo consulte le fichier Name Service Switch, /etc/nsswitch.conf, pour spécifier l'ordre de recherche des sudoers. Sudo recherche une ligne commençant par sudoers : et utilise cela pour déterminer l'ordre de recherche. Par défaut, sudo n'arrête pas de rechercher après la première correspondance et les correspondances ultérieures ont la priorité sur les précédentes (sauf si « [SUCCESS=return] » est utilisé, voir ci-dessous). Les sources suivantes sont reconnues :

fichiers
lire les sudoers depuis /etc/sudoers
ldap
lire les sudoers depuis LDAP

De plus, un sous-ensemble des instructions d'action de style nsswitch.conf est pris en charge, spécifiquement « [SUCCESS=return] » et « [NOTFOUND=return] ». Celles-ci mettront fin inconditionnellement à la recherche si l'utilisateur a été trouvé « [SUCCESS=return] » ou non trouvé « [NOTFOUND=return] » dans la source immédiatement précédente. D'autres jetons d'instructions d'action ne sont pas pris en charge, pas plus que la négation de test avec « ! ».

Pour consulter LDAP d'abord, puis le fichier sudoers local (s'il existe), utilisez :

sudoers: ldap files

Pour consulter LDAP uniquement lorsqu'aucune correspondance n'est trouvée dans le fichier sudoers local (s'il existe), utilisez :

sudoers: files [SUCCESS=return] ldap

Le fichier sudoers local peut être complètement ignoré en utilisant :

sudoers: ldap

Si le fichier /etc/nsswitch.conf n'est pas présent ou s'il n'y a pas de ligne sudoers, le défaut suivant est supposé :

sudoers: files

Le fichier /etc/nsswitch.conf est pris en charge même lorsque le système d'exploitation sous-jacent ne le prend pas en charge, sauf sur AIX (voir ci-dessous).

Configuration de netsvc.conf

Sur les systèmes AIX, le fichier /etc/netsvc.conf est consulté à la place de /etc/nsswitch.conf. sudo traite simplement netsvc.conf comme une variante de nsswitch.conf ; les informations de la section précédente non liées au format de fichier lui-même s'appliquent toujours.

Pour consulter LDAP d'abord, puis le fichier sudoers local (s'il existe), utilisez :

sudoers = ldap, files

Le fichier sudoers local peut être complètement ignoré en utilisant :

sudoers = ldap

Pour considérer LDAP comme faisant autorité et n'utiliser le fichier sudoers local que si l'utilisateur n'est pas présent dans LDAP, utilisez :

sudoers = ldap = auth, files

Dans l'exemple ci-dessus, le qualificateur auth n'affecte que les recherches d'utilisateurs ; LDAP et sudoers seront interrogés pour les entrées Defaults.

Si le fichier /etc/netsvc.conf n'est pas présent ou s'il n'y a pas de ligne sudoers, le défaut suivant est supposé :

sudoers = files

Intégration avec sssd

Sur les systèmes dotés du System Security Services Daemon (SSSD) et où sudo a été compilé avec le support SSSD, il est possible d'utiliser SSSD pour mettre en cache les règles sudoers LDAP. Pour utiliser SSSD comme source des sudoers, vous devez utiliser sss au lieu de ldap pour l'entrée sudoers dans /etc/nsswitch.conf. Le fichier /etc/openldap/ldap.conf n'est pas utilisé par le backend SSSD de sudo. Voir sssd-sudo(5) pour plus d'informations sur la configuration de sudo pour fonctionner avec SSSD.

FILES

/etc/openldap/ldap.conf
Fichier de configuration LDAP
/etc/nsswitch.conf
détermine l'ordre des sources sudoers
/etc/netsvc.conf
détermine l'ordre des sources sudoers sur AIX
