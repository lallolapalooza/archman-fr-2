NOM

sudoers - configuration de sécurité compatible avec sudo

DESCRIPTION

La politique de sudo-rs détermine les privilèges sudo d'un utilisateur. La politique est pilotée par le fichier /etc/sudoers. Le format de la politique est décrit en détail dans la section FORMAT DU FICHIER SUDOERS.

Le format utilisé par sudo-rs est un sous-ensemble de celui utilisé par le projet sudo tel que maintenu par Todd Miller, mais compatible syntaxiquement.

Authentification de l'utilisateur

La politique de sécurité sudoers exige que la plupart des utilisateurs s'authentifient avant de pouvoir utiliser sudo. Un mot de passe n'est pas requis si l'utilisateur appelant est root, si l'utilisateur cible est le même que l'utilisateur appelant, ou si la politique a désactivé l'authentification pour l'utilisateur ou la commande. Contrairement à su, lorsque sudo-rs exige une authentification, il valide les identifiants de l'utilisateur appelant, et non ceux de l'utilisateur cible (ou de root). Cela peut être modifié via le drapeau rootpw, décrit plus loin.

sudo-rs utilise des fichiers d'horodatage par utilisateur pour la mise en cache des identifiants. Une fois qu'un utilisateur a été authentifié, un enregistrement est écrit contenant l'ID utilisateur qui a été utilisé pour l'authentification, l'ID de la session du terminal, l'heure de début du leader de la session (ou du processus parent) et un horodatage (en utilisant une horloge monotone si disponible). L'utilisateur peut alors utiliser sudo sans mot de passe pendant une courte période (15 minutes, sauf si remplacé par l'option timestamp_timeout). Par défaut, sudo-rs utilise un enregistrement séparé pour chaque terminal, ce qui signifie que les sessions de connexion d'un utilisateur sont authentifiées séparément. L'option timestamp_type peut être utilisée pour sélectionner le type d'enregistrement d'horodatage que sudoers utilisera.

Journalisation

Par défaut, sudo-rs enregistre les tentatives réussies et infructueuses (ainsi que les erreurs). Les messages sont enregistrés dans syslog(3).

Environnement de commande

Étant donné que les variables d'environnement peuvent influencer le comportement des programmes, sudo-rs restreint les variables de l'environnement de l'utilisateur qui sont héritées par la commande à exécuter.

Dans sudo-rs, le drapeau env_reset ne peut pas être désactivé. Cela amène les commandes à être exécutées avec un environnement nouveau et minimal. Les variables d'environnement HOME, MAIL, SHELL, LOGNAME et USER sont initialisées en fonction de l'utilisateur cible et les variables SUDO_* sont définies en fonction de l'utilisateur appelant. Des variables supplémentaires, telles que DISPLAY, PATH et TERM, sont conservées de l'environnement de l'utilisateur appelant si cela est autorisé par les options env_check ou env_keep. Quelques variables d'environnement sont traitées spécialement. Si les variables PATH et TERM ne sont pas conservées de l'environnement de l'utilisateur, elles seront définies sur des valeurs par défaut. LOGNAME et USER sont traités comme une seule entité. Si l'un d'eux est conservé (ou supprimé) de l'environnement de l'utilisateur, l'autre le sera également. Si LOGNAME et USER doivent être conservés mais que seul l'un d'eux est présent dans l'environnement de l'utilisateur, l'autre sera défini avec la même valeur. Cela évite un environnement incohérent où l'une des variables décrivant le nom d'utilisateur est définie sur l'utilisateur appelant et l'autre sur l'utilisateur cible. Les variables d'environnement dont la valeur commence par () sont supprimées, car elles peuvent être interprétées comme des fonctions par le shell bash.

Les variables d'environnement spécifiées par env_check ou env_keep peuvent inclure un ou plusieurs caractères de pourcentage ('%') qui correspondront à zéro ou plusieurs caractères. Aucun autre caractère joker n'est pris en charge. D'autres options sudoers peuvent influencer l'environnement de commande, telles que secure_path.

Les variables de l'environnement PAM peuvent être fusionnées dans l'environnement. Si une variable de l'environnement PAM est déjà présente dans l'environnement de l'utilisateur, la valeur ne sera remplacée que si la variable n'a pas été conservée par sudo-rs. Les variables conservées de l'environnement de l'utilisateur appelant par la liste env_keep ont la priorité sur celles de l'environnement PAM.

Notez que le lieur dynamique sur la plupart des systèmes d'exploitation supprimera les variables qui peuvent contrôler le chaînage dynamique de l'environnement des exécutables définis avec le bit setuid, y compris sudo. Selon le système d'exploitation, cela peut inclure _RLD*, DYLD_*, LD_*, LDR_*, LIBPATH, SHLIB_PATH, et d'autres. Ces types de variables sont supprimés de l'environnement avant même que sudo ne commence son exécution et, par conséquent, il n'est pas possible pour sudo de les conserver.

Limites de ressources

sudo utilise la méthode native du système d'exploitation pour définir les limites de ressources pour l'utilisateur cible. Sur les systèmes Linux, les limites de ressources sont généralement définies par le module PAM pam_limits.so. Sur certains systèmes BSD, le fichier /etc/login.conf spécifie les limites de ressources pour l'utilisateur. S'il n'existe aucun mécanisme système pour définir des limites de ressources par utilisateur, la commande s'exécutera avec les mêmes limites que l'utilisateur appelant.

FORMAT DU FICHIER SUDOERS

Le fichier sudoers est composé de deux types d'entrées : les alias (essentiellement des variables) et les spécifications utilisateur (qui spécifient qui peut exécuter quoi).

Lorsque plusieurs entrées correspondent pour un utilisateur, elles sont appliquées dans l'ordre. Lorsqu'il y a plusieurs correspondances, la dernière correspondance est utilisée (qui n'est pas nécessairement la correspondance la plus spécifique).

La grammaire du fichier sudoers sera décrite ci-dessous en Forme de Backus-Naur étendue (EBNF), empruntée à la documentation de sudoers de Todd Miller.

Guide rapide de l'EBNF

L'EBNF est un moyen concis et exact de décrire la grammaire d'un langage. Chaque définition EBNF est composée de règles de production. Par exemple,

 symbole ::= définition | alternate1 | alternate2 ...

Chaque règle de production fait référence à d'autres et constitue ainsi une grammaire pour le langage. L'EBNF contient également les opérateurs suivants, que de nombreux lecteurs reconnaîtront des expressions régulières. Ne les confondez cependant pas avec les caractères « joker », qui ont des significations différentes.

 ?     Signifie que le symbole (ou le groupe de symboles) précédent est optionnel. C'est-à-dire qu'il peut apparaître une fois ou pas du tout.
 *     Signifie que le symbole (ou le groupe de symboles) précédent peut apparaître zéro fois ou plus.
 +     Signifie que le symbole (ou le groupe de symboles) précédent peut apparaître une fois ou plus.

Les parenthèses peuvent être utilisées pour regrouper des symboles. Pour plus de clarté, nous utiliserons des guillemets simples (’’) pour désigner ce qui est une chaîne de caractères littérale (par opposition à un nom de symbole).

Alias

Il existe quatre types d'alias : User_Alias, Runas_Alias, Host_Alias et Cmnd_Alias.

 Alias ::= 'User_Alias'  User_Alias_Spec (':' User_Alias_Spec)* |
           'Runas_Alias' Runas_Alias_Spec (':' Runas_Alias_Spec)* |
           'Host_Alias'  Host_Alias_Spec (':' Host_Alias_Spec)* |
           'Cmnd_Alias'  Cmnd_Alias_Spec (':' Cmnd_Alias_Spec)* |
           'Cmd_Alias'   Cmnd_Alias_Spec (':' Cmnd_Alias_Spec)*
 User_Alias ::= NAME
 User_Alias_Spec ::= User_Alias '=' User_List
 Runas_Alias ::= NAME
 Runas_Alias_Spec ::= Runas_Alias '=' Runas_List
 Host_Alias ::= NAME
 Host_Alias_Spec ::= Host_Alias '=' Host_List
 Cmnd_Alias ::= NAME
 Cmnd_Alias_Spec ::= Cmnd_Alias '=' Cmnd_List
 NAME ::= [A-Z]([A-Z][0-9]_)*

Chaque définition d'alias est de la forme

 Alias_Type NAME = item1, item2, ...

où Alias_Type est l'un des User_Alias, Runas_Alias, Host_Alias, ou Cmnd_A

lias. Un NOM est une chaîne de lettres majuscules, de chiffres et de caractères de soulignement ('_'). Un NOM doit commencer par une lettre majuscule. Il est possible de placer plusieurs définitions d'alias du même type sur une seule ligne, séparées par un deux-points (`:'). Par exemple :

 Alias_Type NOM = element1, element2, element3 : NOM = element4, element5

Les définitions de ce qui constitue un membre d'alias valide suivent.

 User_List ::= User |
               User ',' User_List
 User ::= '!'* nom d'utilisateur |
          '!'* #user-ID |
          '!'* %groupe |
          '!'* %#group-ID |
          '!'* Alias_Utilisateur

Une User_List est composée d'un ou plusieurs noms d'utilisateur, identifiants d'utilisateur (précédés de `#'), noms et identifiants de groupes système (précédés respectivement de `%` et `%#') et Alias_Utilisateurs. Chaque élément de la liste peut être précédé de zéro ou plusieurs opérateurs `!`. Un nombre impair d'opérateurs `!` nie la valeur de l'élément ; un nombre pair les annule simplement.

 Runas_List ::= Runas_Member |
                Runas_Member ',' Runas_List
 Runas_Member ::= '!'* nom d'utilisateur |
                  '!'* #user-ID |
                  '!'* %groupe |
                  '!'* %#group-ID |
                  '!'* Alias_Runas

Une Runas_List est similaire à une User_List, sauf qu'au lieu de Alias_Utilisateurs, elle peut contenir des Alias_Runas. Notez que les noms d'utilisateur et les groupes sont comparés en tant que chaînes de caractères. En d'autres termes, deux utilisateurs (groupes) ayant le même identifiant d'utilisateur (groupe) sont considérés comme distincts. Si vous souhaitez faire correspondre tous les noms d'utilisateur ayant le même identifiant d'utilisateur (par exemple, root et toor), vous pouvez utiliser un identifiant d'utilisateur au lieu d'un nom (#0 dans l'exemple donné).

 Host_List ::= Host |
               Host ',' Host_List
 Host ::= '!'* nom d'hôte |
          '!'* Alias_Hôte

Une Host_List est composée d'un ou plusieurs noms d'hôtes. Encore une fois, la valeur d'un élément peut être niée avec l'opérateur `!`.

 Cmnd_List ::= Cmnd |
               Cmnd ',' Cmnd_List
 nom de commande ::= nom de fichier |
                  nom de fichier arguments |
                  nom de fichier '""'
 Cmnd ::= '!'* nom de commande |
          '!'* répertoire |
          '!'* Alias_Cmnd
          '!'* "list"
          '!'* "sudoedit" [nom de fichier]

Une Cmnd_List est une liste d'un ou plusieurs noms de commandes, répertoires et autres alias. Un nom de commande est un nom de fichier entièrement qualifié qui peut inclure des caractères génériques de style shell (voir la section Caractères génériques ci-dessous). Un nom de fichier simple permet à l'utilisateur d'exécuter la commande avec tous les arguments qu'il souhaite. Cependant, vous pouvez également spécifier des arguments de ligne de commande (qui dans sudo-rs ne peuvent *pas* inclure de caractères génériques). Alternativement, vous pouvez spécifier `""` pour indiquer que la commande ne peut être exécutée qu'en l'absence d'arguments de ligne de commande. Un répertoire est un chemin d'accès entièrement qualifié se terminant par un `/`. Lorsque vous spécifiez un répertoire dans une Cmnd_List, l'utilisateur pourra exécuter n'importe quel fichier de ce répertoire (mais pas dans ses sous-répertoires).

Si un Cmnd a des arguments de ligne de commande associés, alors les arguments du Cmnd doivent correspondre exactement à ceux fournis par l'utilisateur sur la ligne de commande. Notez que les caractères suivants doivent être échappés avec un `\` s'ils sont utilisés dans les arguments de commande : `,', `:', `=`, `\'.

Il existe deux commandes intégrées à sudo : « list » et « sudoedit ». Contrairement aux autres commandes, ces deux-là doivent être spécifiées dans le fichier sudoers sans chemin d'accès initial.

La commande intégrée « list » peut être utilisée pour autoriser un utilisateur à lister les privilèges d'un autre utilisateur avec l'option `-U` de sudo. Par exemple, « sudo -l -U autreutilisateur ». Un utilisateur disposant du privilège « list » est capable de lister les privilèges d'un autre utilisateur, même s'il n'a pas la permission d'exécuter des commandes en tant que cet utilisateur. Par défaut, seuls root ou un utilisateur ayant la capacité d'exécuter n'importe quelle commande en tant que root ou en tant qu'utilisateur spécifié sur l'hôte actuel peuvent utiliser l'option `-U`. Aucun argument de ligne de commande ne peut être spécifié avec la commande intégrée « list ».

La commande intégrée « sudoedit » est utilisée pour permettre à un utilisateur d'exécuter sudo avec l'option `-e` (ou en tant que sudoedit). Elle peut prendre des arguments de ligne de commande comme une commande normale. Contrairement aux autres commandes, « sudoedit » est intégré à sudo lui-même et doit être spécifié dans le fichier sudoers sans chemin d'accès initial. Si un chemin d'accès initial est présent, par exemple `/usr/bin/sudoedit`, cela ne donnera pas à l'utilisateur la permission d'utiliser sudoedit. Si aucun argument n'est fourni, « sudoedit » donnera à l'utilisateur la permission d'éditer n'importe quels fichiers ; si un argument est présent, il doit s'agir d'un nom de chemin absolu qui ne contient pas de liens symboliques, sinon la commande ne correspondra pas.

Defaults

Certaines options de configuration peuvent être modifiées par rapport à leurs valeurs par défaut au moment de l'exécution via une ou plusieurs lignes Default_Entry. Celles-ci peuvent affecter tous les utilisateurs sur n'importe quel hôte, tous les utilisateurs sur un hôte spécifique, un utilisateur spécifique, une commande spécifique ou des commandes exécutées en tant qu'utilisateur spécifique. Notez que les entrées par commande ne peuvent pas inclure d'arguments de ligne de commande. Si vous devez spécifier des arguments, définissez un Cmnd_Alias et référencez-le à la place.

 Default_Type ::= 'Defaults' |
                  'Defaults' '@' Host_List |
                  'Defaults' ':' User_List |
                  'Defaults' '!' Cmnd_List |
                  'Defaults' '>' Runas_List
 Default_Entry ::= Default_Type Parameter_List
 Parameter_List ::= Parameter |
                    Parameter ',' Parameter_List
 Parameter ::= Parameter '=' Value |
               Parameter '+=' Value |
               Parameter '-=' Value |
               '!'* Parameter

Les paramètres peuvent être des drapeaux, des valeurs entières, des chaînes de caractères ou des listes. Les drapeaux sont implicitement booléens et peuvent être désactivés via l'opérateur `!`. Certains paramètres entiers, de chaînes de caractères et de listes peuvent également être utilisés dans un contexte booléen pour les désactiver. Les valeurs peuvent être entourées de guillemets doubles (`"`) lorsqu'elles contiennent plusieurs mots. Les caractères spéciaux peuvent être échappés avec une barre oblique inverse (`\`).

Pour inclure un caractère barre oblique inverse littéral dans un argument de ligne de commande, vous devez échapper la barre oblique inverse deux fois. Par exemple, pour faire correspondre `\n` dans le cadre d'un argument de ligne de commande, vous devez utiliser `\\\\n` dans le fichier sudoers. Ceci est dû au fait qu'il existe deux niveaux d'échappement, un dans l'analyseur sudoers lui-même et un autre lorsque les arguments de ligne de commande sont mis en correspondance par la fonction fnmatch(3).

Les listes ont deux opérateurs d'affectation supplémentaires, += et -=. Ces opérateurs sont utilisés pour ajouter et supprimer respectivement d'une liste. Ce n'est pas une erreur d'utiliser l'opérateur `-=` pour supprimer un élément qui n'existe pas dans une liste.

Les entrées Defaults sont analysées dans l'ordre suivant : générique, hôte, utilisateur et runas. Les Defaults sont traités dans l'ordre où ils apparaissent, les Defaults par commande étant traités dans un second passage après cela.

Voir SUDOERS OPTIONS pour une liste des paramètres Defaults pris en charge.

Spécification utilisateur

 User_Spec ::= User_List Host_List '=' Cmnd_Spec_List \
               (':' Host_List '=' Cmnd_Spec_List)*
 Cmnd_Spec_List ::= Cmnd_Spec |
                    Cmnd_Spec ',' Cmnd_Spec_List
 Cmnd_Spec ::= Runas_Spec? Chdir_Spec? Tag_Spec* Cmnd
 Runas_Spec ::= '(' Runas_List? (':' Runas_List)? ')'
 Chdir_Spec ::= 'CWD=directory'
 Tag_Spec ::= ('PASSWD:' | 'NOPASSWD:' |
               'SETENV:' | 'NOSETENV:'
               'EXEC:'   | 'NOEXEC')
 AppArmor_Spec ::= 'APPARMOR_PROFILE=profile'

Une spécification utilisateur détermine quelles commandes un utilisateur peut exécuter (et en tant que quel utilisateur) sur des hôtes spécifiés. Par défaut, les commandes sont exécutées en tant que root, mais cela peut être modifié sur une base par commande.

La structure de base d'une spécification utilisateur est « qui où = (en tant que quoi) quoi ». Décomposons cela en ses parties constitutives :

Runas_Spec

Un Runas_Spec détermine l'utilisateur et/ou le groupe sous lequel une commande peut être exécutée. Un Runas_Spec entièrement spécifié se compose de deux Runas_Lists (telles que définies ci-dessus) séparées par un deux-points (`:') et entourées de parenthèses. La première Runas_List indique quels utilisateurs la commande peut être exécutée en tant qu'via l'option `-u`. La seconde définit une liste de groupes qui peuvent être spécifiés via l'option `-g` (en plus de tous les groupes de l'utilisateur cible). Si les deux Runas_Lists sont spécifiées, la commande peut être exécutée avec n'importe quelle combinaison d'utilisateurs et de groupes listés dans leurs Runas_Lists respectives. Si seule la première est spécifiée, la commande peut être exécutée en tant que n'importe quel utilisateur de la liste et, éventuellement, avec n'importe quel groupe auquel appartient l'utilisateur cible. Si la première Runas_List est vide mais que la seconde est spécifiée, la commande peut être exécutée en tant qu'utilisateur appelant avec le groupe défini sur n'importe lequel de ceux listés dans la Runas_List. Si les deux Runas_Lists sont vides, la commande ne peut être exécutée qu'en tant qu'utilisateur appelant et le groupe, s'il est spécifié, doit être un groupe dont l'utilisateur appelant est membre. Si aucun Runas_Spec n'est spécifié, la commande ne peut être exécutée qu'en tant que root et le groupe, s'il est spécifié, doit être un groupe dont root est membre.

Un Runas_Spec définit la valeur par défaut pour les commandes qui le suivent. Ce que cela signifie, c'est que pour l'entrée :

 dgb     boulder = (operator) /bin/ls, /bin/kill, /usr/bin/lprm

L'utilisateur dgb peut exécuter /bin/ls, /bin/kill et /usr/bin/lprm sur l'hôte boulder — mais uniquement en tant qu'operator. Par exemple :

 $ sudo -u operator /bin/ls

Il est également possible de remplacer un Runas_Spec plus tard dans une entrée. Si nous modifions l'entrée comme suit :

 dgb     boulder = (operator) /bin/ls, (root) /bin/kill, /usr/bin/lprm

Alors l'utilisateur dgb est maintenant autorisé à exécuter /bin/ls en tant qu'operator, mais /bin/kill et /usr/bin/lprm en tant que root.

Nous pouvons étendre cela pour permettre à dgb d'exécuter /bin/ls avec l'utilisateur ou le groupe défini sur operator :

 dgb     boulder = (operator : operator) /bin/ls, (root) /bin/kill,\
         /usr/bin/lprm

Notez que bien que la partie groupe du Runas_Spec permette à l'utilisateur d'exécuter la commande avec ce groupe, cela ne le force pas à le faire. Si aucun groupe n'est spécifié sur la ligne de commande, la commande sera exécutée avec le groupe indiqué dans l'entrée de la base de données du mot de passe de l'utilisateur cible. Les commandes suivantes seraient toutes autorisées par l'entrée sudoers ci-dessus :

 $ sudo -u operator /bin/ls
 $ sudo -u operator -g operator /bin/ls
 $ sudo -g operator /bin/ls

Dans l'exemple suivant, utilisez

r tcm peut exécuter des commandes qui accèdent à un fichier de périphérique modem avec le groupe dialer.

 tcm     boulder = (:dialer) /usr/bin/tip, /usr/bin/cu,\
         /usr/local/bin/minicom

Notez que dans cet exemple, seul le groupe sera défini, la commande s'exécute toujours en tant qu'utilisateur tcm. Par exemple :

 $ sudo -g dialer /usr/bin/cu

Plusieurs utilisateurs et groupes peuvent être présents dans un Runas_Spec, auquel cas l'utilisateur peut sélectionner n'importe quelle combinaison d'utilisateurs et de groupes via les options -u et -g. Dans cet exemple :

 alan    ALL = (root, bin : operator, system) ALL

l'utilisateur alan peut exécuter n'importe quelle commande en tant qu'utilisateur root ou bin, en définissant éventuellement le groupe sur operator ou system.

Chdir_Spec

Le répertoire de travail dans lequel la commande sera exécutée peut être spécifié à l'aide du paramètre CWD. Le répertoire doit être un chemin d'accès complet commençant par un caractère `/` ou `~`, ou la valeur spéciale “”. Une valeur de “” indique que l'utilisateur peut spécifier le répertoire de travail en exécutant sudo avec l'option -D. Par défaut, les commandes sont exécutées à partir du répertoire de travail actuel de l'utilisateur qui invoque, sauf si l'option -i est donnée. Les noms de chemin de la forme ~user/path/name sont interprétés comme étant relatifs au répertoire personnel de l'utilisateur nommé. Si le nom d'utilisateur est omis, le chemin sera relatif au répertoire personnel de l'utilisateur runas.

Tag_Spec

Une commande peut avoir zéro ou plusieurs étiquettes associées. Les valeurs d'étiquettes suivantes sont prises en charge : PASSWD, NOPASSWD, SETENV et NOSETENV. Une fois qu'une étiquette est définie sur un Cmnd, les Cmnds suivants dans le Cmnd_Spec_List héritent de l'étiquette sauf si elle est remplacée par l'étiquette opposée (en d'autres termes, PASSWD remplace NOPASSWD et NOSETENV remplace SETENV).

EXEC et NOEXEC

Sur les systèmes Linux, l'étiquette NOEXEC peut être utilisée pour empêcher un exécutable d'exécuter d'autres commandes lui-même.

Dans l'exemple suivant, l'utilisateur aaron peut exécuter /usr/bin/more et /usr/bin/vi, mais les échappements de shell seront désactivés.

    aaron   shanty = NOEXEC: /usr/bin/more, /usr/bin/vi

Consultez la section Prévention des échappements de shell ci-dessous pour plus de détails sur le fonctionnement de NOEXEC et s'il vous convient.

PASSWD et NOPASSWD

Par défaut, sudo demande à un utilisateur de s'authentifier avant d'exécuter une commande. Ce comportement peut être modifié via l'étiquette NOPASSWD. Comme un Runas_Spec, l'étiquette NOPASSWD définit une valeur par défaut pour les commandes qui la suivent dans le Cmnd_Spec_List. Inversement, l'étiquette PASSWD peut être utilisée pour inverser les choses. Par exemple :

   queen     rushmore = NOPASSWD: /bin/kill, /bin/ls, /usr/bin/lprm

permettrait à l'utilisateur queen d'exécuter /bin/kill, /bin/ls et /usr/bin/lprm en tant que root sur la machine « rushmore » sans s'authentifier. Si nous voulons seulement que queen puisse exécuter /bin/kill sans mot de passe, l'entrée serait :

   queen     rushmore = NOPASSWD: /bin/kill, PASSWD: /bin/ls, /usr/bin/lprm

Notez cependant que l'étiquette PASSWD n'a aucun effet sur les utilisateurs qui font partie du groupe spécifié par le réglage exempt_group.

Par défaut, si l'étiquette NOPASSWD est appliquée à l'une des entrées d'un utilisateur pour l'hôte actuel, l'utilisateur pourra exécuter « sudo -l » sans mot de passe. De plus, un utilisateur ne peut exécuter « sudo -v » sans mot de passe que si toutes les entrées de l'utilisateur pour l'hôte actuel ont l'étiquette NOPASSWD.

SETENV et NOSETENV

Ces étiquettes remplacent la valeur du drapeau setenv sur une base par commande. Notez que si SETENV a été défini pour une commande, l'utilisateur peut désactiver le drapeau env_reset depuis la ligne de commande via l'option -E. De plus, les variables d'environnement définies sur la ligne de commande ne sont pas soumises aux restrictions imposées par env_check, env_delete ou env_keep. Par conséquent, seuls les utilisateurs de confiance devraient être autorisés à définir des variables de cette manière. Si la commande correspondante est ALL, l'étiquette SETENV est implicite pour cette commande ; ce défaut peut être annulé en utilisant l'étiquette NOSETENV.

AppArmor_Spec

Lorsque sudo-rs est compilé avec la prise en charge d'AppArmor, les entrées du fichier sudoers peuvent spécifier un profil AppArmor qui doit être utilisé pour confiner une commande.

Si un profil AppArmor est spécifié avec la commande, il remplacera toutes les valeurs par défaut spécifiées dans sudoers. Des règles de transition de profil appropriées doivent être définies pour prendre en charge le changement de profil spécifié pour un utilisateur.

Les profils AppArmor peuvent être spécifiés de toute manière conforme aux règles de aa_change_profile(2).

Wildcards

sudo autorise l'utilisation de caractères génériques de type shell (également appelés méta-caractères ou caractères glob) dans les noms d'hôtes, les noms de chemins et les arguments de ligne de commande dans le fichier sudoers. La correspondance des caractères génériques se fait via les fonctions glob(3) et fnmatch(3) conformément à la norme IEEE Std 1003.1 (« POSIX.1 »).

 *         Correspond à n'importe quelle séquence de zéro ou plusieurs caractères (y compris les espaces blancs).
 ?         Correspond à n'importe quel caractère unique (y compris les espaces blancs).
 [...]     Correspond à n'importe quel caractère dans la plage spécifiée.
 [!...]    Correspond à n'importe quel caractère qui n'est pas dans la plage spécifiée.
 \x        Pour n'importe quel caractère 'x', s'évalue à 'x'. Ceci est utilisé pour échapper les caractères spéciaux tels que : '*', '?', '[', et ']'.

Notez qu'il ne s'agit pas d'expressions régulières. Contrairement à une expression régulière, il n'y a aucun moyen de faire correspondre un ou plusieurs caractères dans une plage.

Les caractères génériques dans les arguments de ligne de commande ne sont pas pris en charge : leur utilisation dans les versions originales de sudo était généralement un signe de mauvaise configuration et, par conséquent, sudo-rs les interdit simplement.

Inclusion d'autres fichiers à partir de sudoers

Il est possible d'inclure d'autres fichiers sudoers à partir du fichier sudoers en cours d'analyse à l'aide des directives @include et @includedir. Pour la compatibilité avec les versions de sudo de Todd Miller antérieures à 1.9.1, #include et #includedir sont également acceptés.

Un fichier d'inclusion peut être utilisé, par exemple, pour conserver un fichier sudoers à l'échelle du site en plus d'un fichier local par machine. Pour cet exemple, le fichier sudoers à l'échelle du site sera /etc/sudoers et celui par machine sera /etc/sudoers.local. Pour inclure /etc/sudoers.local à partir de /etc/sudoers, utilisez la ligne suivante dans /etc/sudoers :

     @include /etc/sudoers.local

Lorsque sudo atteint cette ligne, il suspend le traitement du fichier actuel (/etc/sudoers) et passe à /etc/sudoers.local. En atteignant la fin de /etc/sudoers.local, le reste de /etc/sudoers sera traité. Les fichiers qui sont inclus peuvent eux-mêmes inclure d'autres fichiers. Une limite stricte de 128 fichiers inclus imbriqués est appliquée pour éviter les boucles de fichiers inclus.

Le chemin du fichier d'inclusion peut contenir des espaces blancs s'il est échappé avec une barre oblique inverse (`\'). Alternativement, le chemin complet peut être entouré de guillemets doubles (« »), auquel cas aucun échappement n'est nécessaire. Pour inclure une barre oblique inverse littérale dans le chemin, il faut utiliser `\\' . Si le chemin du fichier d'inclusion n'est pas un chemin absolu (ne commence pas par `/'), il doit être situé dans le même répertoire que le fichier sudoers à partir duquel il a été inclus. Par exemple, si /etc/sudoers contient la ligne :

     @include sudoers.local

La directive @includedir peut être utilisée pour créer un répertoire sudoers.d dans lequel le gestionnaire de paquets du système peut déposer des règles de fichiers sudoers dans le cadre de l'installation d'un paquet. Par exemple, étant donné :

     @includedir /etc/sudoers.d

sudo suspendra le traitement du fichier actuel et lira chaque fichier dans /etc/sudoers.d, en ignorant les noms de fichiers se terminant par `~' ou contenant un caractère `.' pour éviter des problèmes avec les fichiers temporaires/de sauvegarde du gestionnaire de paquets ou de l'éditeur. Les fichiers sont analysés dans un ordre lexical trié. C'est-à-dire que /etc/sudoers.d/01_first sera analysé avant /etc/sudoers.d/10_second. Gardez à l'esprit que comme le tri est lexical et non numérique, /etc/sudoers.d/1_whoops serait chargé après /etc/sudoers.d/10_second. L'utilisation d'un nombre constant de zéros initiaux dans les noms de fichiers peut être utilisée pour éviter de tels problèmes. Après avoir analysé les fichiers du répertoire, le contrôle revient au fichier qui contenait la directive @includedir.

Notez que contrairement aux fichiers inclus via @include, visudo n'éditera pas les fichiers d'un répertoire @includedir, sauf si l'un d'eux contient une erreur de syntaxe. Il est toujours possible d'exécuter visudo avec l'option -f pour éditer les fichiers directement, mais cela ne détectera pas la redéfinition d'un alias qui est également présent dans un autre fichier.

Autres caractères spéciaux et mots réservés

Le signe dièse (`#') est utilisé pour indiquer un commentaire (sauf s'il fait partie d'une directive #include ou sauf s'il se produit dans le contexte d'un nom d'utilisateur et est suivi d'un ou plusieurs chiffres, auquel cas il est traité comme un ID utilisateur). Le caractère de commentaire et tout texte qui le suit, jusqu'à la fin de la ligne, sont ignorés.

Le mot réservé ALL est un alias intégré qui provoque toujours une correspondance réussie. Il peut être utilisé partout où l'on pourrait autrement utiliser un Cmnd_Alias, User_Alias, Runas_Alias ou Host_Alias. Tenter de définir un alias nommé ALL entraînera une erreur de syntaxe. Veuillez noter que l'utilisation de ALL peut être dangereuse car, dans un contexte de commande, elle permet à l'utilisateur d'exécuter n'importe quelle commande sur le système.

Un point d'exclamation (`!') peut être utilisé comme opérateur logique "non" dans une liste ou un alias ainsi que devant un Cmnd. Cela permet d'exclure certaines valeurs. Pour que l'opérateur `!' soit efficace, il doit y avoir quelque chose à exclure. Par exemple, pour ma

``` exclure tous les utilisateurs sauf root on utiliserait :

     ALL,!root

Si ALL, est omis, comme dans :

     !root

cela refuserait explicitement root mais ne correspondrait à aucun autre utilisateur. C'est différent d'un véritable opérateur de « négation ».

Notez cependant que l'utilisation de `!' en conjonction avec l'alias intégré ALL pour permettre à un utilisateur d'exécuter « toutes les commandes sauf quelques-unes » fonctionne rarement comme prévu (voir NOTES DE SÉCURITÉ ci-dessous).

Les espaces blancs entre les éléments d'une liste ainsi que les caractères syntaxiques spéciaux dans une Spécification d'utilisateur (`=', `:', `(', `)') sont facultatifs.

Les caractères suivants doivent être échappés avec une barre oblique inverse (`\') lorsqu'ils sont utilisés dans un mot (par exemple, un nom d'utilisateur ou un nom d'hôte) : `!', `=', `:', `,', `(', `)', `\'.

OPTIONS SUDOERS

Le comportement de sudo peut être modifié par des lignes Default_Entry, comme expliqué précédemment. Une liste de tous les paramètres Defaults pris en charge, groupés par type, est fournie ci-dessous.

Indicateurs booléens :

•
noexec

S'il est défini, toutes les commandes exécutées via sudo se comporteront comme si l'indicateur NOEXEC était défini, sauf indication contraire par un indicateur EXEC. Voir la description de EXEC et NOEXEC ainsi que la section Prévenir les évasions de shell à la fin de ce manuel. Cet indicateur est désactivé par défaut.

•
noninteractive_auth Si défini, une tentative d'authentification sera effectuée même en mode non interactif (lorsque l'option -n de sudo est spécifiée). Cela permet aux méthodes d'authentification qui ne nécessitent pas d'interaction utilisateur de réussir. Les méthodes d'authentification qui nécessitent une entrée depuis le terminal de l'utilisateur échoueront toujours. Si désactivé, aucune tentative d'authentification ne sera effectuée en mode non interactif. Cet indicateur est désactivé par défaut.
•
env_editor

S'il est défini, visudo utilisera la valeur des variables d'environnement SUDO_EDITOR, VISUAL ou EDITOR avant de se rabattre sur la liste des éditeurs par défaut. Notez que visudo est généralement exécuté en tant que root, donc cet indicateur peut permettre à un utilisateur disposant de privilèges visudo d'exécuter des commandes arbitraires en tant que root sans se connecter. Une alternative consiste à placer une liste d'éditeurs « sûrs », séparés par deux points, dans le paramètre editor. visudo n'utilisera alors SUDO_EDITOR, VISUAL ou EDITOR que s'ils correspondent à une valeur spécifiée dans editor. Si l'indicateur env_reset est activé, les variables d'environnement SUDO_EDITOR, VISUAL et/ou EDITOR doivent être présentes dans la liste env_keep pour que l'indicateur env_editor fonctionne lorsque visudo est invoqué via sudo. Cet indicateur est activé par défaut.

•
pwfeedback

Par défaut, sudo lit le mot de passe comme la plupart des autres programmes Unix, en désactivant l'écho jusqu'à ce que l'utilisateur appuie sur la touche retour (ou entrée). Certains utilisateurs sont confus par cela car il leur semble que sudo s'est bloqué à ce stade. Lorsque pwfeedback est défini, sudo fournira un retour visuel lorsque l'utilisateur appuie sur une touche. Notez que cela a un impact sur la sécurité car un observateur pourrait déterminer la longueur du mot de passe saisi. Cet indicateur est désactivé par défaut.

•
rootpw

S'il est défini, sudo demandera le mot de passe root au lieu du mot de passe de l'utilisateur qui l'a appelé lors de l'exécution d'une commande ou de la modification d'un fichier. Cet indicateur est désactivé par défaut.

•
setenv

Permet à l'utilisateur de définir des variables d'environnement via la ligne de commande qui ne sont pas soumises aux restrictions imposées par env_check, env_delete ou env_keep. En tant que tels, seuls les utilisateurs de confiance devraient être autorisés à définir des variables de cette manière. Cet indicateur est désactivé par défaut.

•
targetpw

S'il est défini, sudo demandera le mot de passe de l'utilisateur spécifié par l'option -u (par défaut root) au lieu du mot de passe de l'utilisateur qui l'a appelé lors de l'exécution d'une commande ou de la modification d'un fichier. Notez que cet indicateur empêche l'utilisation d'un identifiant utilisateur non listé dans la base de données passwd comme argument de l'option -u. Cet indicateur est désactivé par défaut.

•
umask_override

S'il est défini, sudo définira l'umask comme spécifié dans le fichier sudoers sans modification. Cela permet de spécifier une umask dans le fichier sudoers qui est plus permissive que l'umask de l'utilisateur. Si umask_override n'est pas défini, sudo définira l'umask comme l'union de l'umask de l'utilisateur et de ce qui est spécifié dans sudoers. Cet indicateur est désactivé par défaut.

•
use_pty

S'il est défini, et que sudo s'exécute dans un terminal, la commande sera exécutée dans un pseudo-terminal (même si aucun enregistrement d'E/S n'est effectué). Si le processus sudo n'est pas connecté à un terminal, use_pty n'a aucun effet.

Un programme malveillant exécuté sous sudo peut être capable d'injecter des commandes dans le terminal de l'utilisateur ou d'exécuter un processus en arrière-plan qui conserve l'accès au périphérique terminal de l'utilisateur même après que le programme principal ait terminé son exécution. En exécutant la commande dans un pseudo-terminal séparé, cette attaque n'est plus possible. Cet indicateur est activé par défaut.

Entiers :

•
passwd_tries

Le nombre d'essais qu'un utilisateur a pour entrer son mot de passe avant que sudo n'enregistre l'échec et ne quitte. La valeur par défaut est 3.

Entiers pouvant être utilisés dans un contexte booléen :

•
timestamp_timeout

Nombre de minutes qui peuvent s'écouler avant que sudo ne redemande un mot de passe. Le délai d'attente peut inclure une composante fractionnaire si la granularité en minutes est insuffisante, par exemple 2.5. La valeur par défaut est 15. Définissez ceci à 0 pour toujours demander un mot de passe.

•
umask

Masque de création de mode de fichier à utiliser lors de l'exécution de la commande. Négativez cette option ou définissez-la à 0777 pour empêcher sudo de modifier l'umask. Sauf si l'indicateur umask_override est défini, l'umask réelle sera l'union de l'umask de l'utilisateur et de la valeur du paramètre umask, qui par défaut est 0022. Cela garantit que sudo n'abaisse jamais l'umask lors de l'exécution d'une commande.

Si umask est explicitement défini, il remplacera tout paramètre umask dans PAM. Si umask n'est pas défini, l'umask spécifiée par PAM aura la priorité. Le paramètre umask dans PAM n'est pas utilisé pour sudoedit, qui ne crée pas de nouvelle session PAM.

Chaînes

•
editor

Une liste d'éditeurs séparés par des deux-points (`:') utilisée par sudoedit et visudo. Pour sudoedit, cette liste est utilisée pour trouver un éditeur lorsqu'aucune des variables d'environnement SUDO_EDITOR, VISUAL ou EDITOR n'est définie sur un éditeur qui existe et est exécutable. Pour visudo, elle est utilisée comme une liste blanche d'éditeurs autorisés ; visudo choisira l'éditeur qui correspond à la variable d'environnement SUDO_EDITOR, VISUAL ou EDITOR de l'utilisateur si possible, ou le premier éditeur de la liste qui existe et est exécutable sinon. Sauf s'il est invoqué en tant que sudoedit, sudo ne conserve pas les variables d'environnement SUDO_EDITOR, VISUAL ou EDITOR à moins qu'elles ne soient présentes dans la liste env_keep. La valeur par défaut sous Linux est /usr/bin/editor, sous FreeBSD /usr/vim/vi.

Chaînes pouvant être utilisées dans un contexte booléen :

•
apparmor_profile

Le profil AppArmor par défaut vers lequel transitionner lors de l'exécution d'une commande. Le profil apparmor_profile par défaut peut être remplacé pour des entrées sudoers individuelles en spécifiant l'option APPARMOR_PROFILE. Cette option n'est disponible que lorsque sudo-rs est compilé avec le support AppArmor. Cette option n'est pas définie par défaut.

•
secure_path

Si elle est définie, sudo utilisera cette valeur à la place de la variable d'environnement PATH de l'utilisateur. Cette option peut être utilisée pour réinitialiser le PATH à une valeur sûre connue qui contient les répertoires des commandes d'administration système telles que /usr/sbin. Cette option n'est pas définie par défaut.

Listes pouvant être utilisées dans un contexte booléen :

•
env_check

Variables d'environnement à supprimer de l'environnement de l'utilisateur à moins qu'elles ne soient considérées comme « sûres ». Pour toutes les variables sauf TZ, « sûr » signifie que la valeur de la variable ne contient aucun caractère '%' ou '/'. Cela peut être utilisé pour se prémunir contre les vulnérabilités de type formatage printf dans des programmes mal écrits. La variable TZ est considérée comme dangereuse si l'une des conditions suivantes est vraie :

                 •  Elle consiste en un nom de chemin absolu, éventuellement préfixé par deux-points (' :'), qui ne correspond pas à l'emplacement du répertoire zoneinfo.
                 •  Elle contient un élément de chemin ..
                 •  Elle contient des espaces blancs ou des caractères non imprimables.
                 •  Elle est plus longue que la valeur de PATH_MAX.

L'argument peut être une liste séparée par des espaces entre guillemets doubles ou une valeur unique sans guillemets. La liste peut être remplacée, complétée, supprimée ou désactivée en utilisant respectivement les opérateurs =, +=, -= et !. Que l'option env_reset soit activée ou désactivée, les variables spécifiées par env_check seront préservées dans l'environnement si elles réussissent le contrôle susmentionné. La liste globale des variables d'environnement à vérifier est affichée lorsque sudo est exécuté par root avec l'option -V.

•
env_keep

Variables d'environnement à préserver dans l'environnement de l'utilisateur lorsque l'option env_reset opt

tion est en vigueur. Cela permet un contrôle fin sur l'environnement que les processus lancés par sudo recevront. L'argument peut être une liste entre guillemets doubles, séparée par des espaces, ou une seule valeur sans guillemets doubles. La liste peut être remplacée, complétée, supprimée ou désactivée en utilisant respectivement les opérateurs =, +=, -= et !. La liste globale des variables à conserver est affichée lorsque sudo est exécuté par root avec l'option -V.

La préservation de la variable d'environnement HOME a des implications de sécurité car de nombreux programmes l'utilisent lors de la recherche de fichiers de configuration ou de données. L'ajout de HOME à env_keep peut permettre à un utilisateur d'exécuter des commandes sans restriction via sudo et est fortement déconseillé. Les utilisateurs souhaitant modifier des fichiers avec sudo devraient exécuter sudoedit (ou sudo -e) pour obtenir leur configuration d'éditeur habituelle au lieu d'invoquer l'éditeur directement.

NOTES DE SÉCURITÉ

Limitations de l'opérateur `!'

Il est généralement inefficace de « soustraire » des commandes de ALL en utilisant l'opérateur `!'. Un utilisateur peut trivialement contourner cela en copiant la commande souhaitée sous un nom différent, puis en l'exécutant. Par exemple :

 bill    ALL = ALL, !SU, !SHELLS

Cela n'empêche pas vraiment bill d'exécuter les commandes listées dans SU ou SHELLS, car il peut simplement copier ces commandes sous un autre nom, ou utiliser une évasion de shell à partir d'un éditeur ou d'un autre programme. Par conséquent, ces types de restrictions devraient être considérés comme indicatifs au mieux (et renforcés par la politique).

En général, si un utilisateur a sudo ALL, rien ne l'empêche de créer son propre programme qui lui donne un shell root (ou de créer sa propre copie d'un shell) quelles que soient les éléments `!' dans la spécification de l'utilisateur.

Implications de sécurité de fast_glob

sudo-rs utilise `fast_glob, ce qui signifie en outre qu'il n'est pas possible de nier de manière fiable les commandes dont le nom de chemin inclut des caractères de globbing (alias jokers). En effet, la fonction fnmatch de la bibliothèque Rust ne peut pas résoudre les chemins relatifs. Bien que cela ne soit généralement qu'une gêne pour les règles qui accordent des privilèges, cela peut entraîner un problème de sécurité pour les règles qui soustraient ou révoquent des privilèges.

Par exemple, étant donné l'entrée suivante dans le fichier sudoers :

 john    ALL = /usr/bin/passwd [a-zA-Z0-9]*, /usr/bin/chsh [a-zA-Z0-9]*,\
               /usr/bin/chfn [a-zA-Z0-9]*, !/usr/bin/* root

L'utilisateur john peut toujours exécuter /usr/bin/passwd root si fast_glob est activé en se déplaçant vers /usr/bin et en exécutant ./passwd root à la place.

Prévention des évasions de shell

Une fois que sudo exécute un programme, ce programme est libre de faire ce qu'il veut, y compris d'exécuter d'autres programmes. Cela peut être un problème de sécurité car il n'est pas rare qu'un programme permette des évasions de shell, ce qui permet à un utilisateur de contourner le contrôle d'accès et la journalisation de sudo. Les programmes courants qui autorisent les évasions de shell incluent les shells (évidemment), les éditeurs, les paginateurs (comme less), le courrier et les programmes de terminal.

Sur Linux, sudo-rs dispose de la fonctionnalité noexec de sudo, basée sur un filtre seccomp(). Les programmes exécutés en mode noexec ne peuvent pas exécuter d'autres programmes. L'implémentation dans sudo-rs est différente de celle du sudo de Todd Miller et devrait également fonctionner sur des binaires liés statiquement.

Notez que la restriction des évasions de shell n'est pas une panacée. Les programmes exécutés en tant que root sont toujours capables de nombreuses opérations potentiellement dangereuses (comme modifier ou écraser des fichiers) qui pourraient entraîner une escalade de privilèges involontaire. NOEXEC n'est pas non plus une protection contre les programmes malveillants. Il n'empêche pas le mappage de mémoire en tant qu'exécutable, ni ne protège contre les futurs appels système qui peuvent effectuer un exec() comme la fonctionnalité exec proposée io_uring sous Linux. Et il ne protège pas non plus contre les programmes honnêtes qui permettent intentionnellement ou non à l'utilisateur d'écrire dans /proc/self/mem pour les mêmes raisons pour lesquelles il ne protège pas contre les programmes malveillants. Vous devriez toujours essayer de vérifier si noexec empêche réellement les évasions de shell pour les programmes avec lesquels il est censé être utilisé.

Vérifications des fichiers d'horodatage

sudo-rs vérifiera la propriété de son répertoire d'horodatage (/run/sudo/ts par défaut) et ignorera le contenu du répertoire s'il n'est pas détenu par root ou s'il est inscriptible par un utilisateur autre que root.

Bien que le répertoire d'horodatage doive être vidé au redémarrage, pour éviter des problèmes potentiels, sudo-rs ignorera les fichiers d'horodatage datant d'avant le démarrage de la machine sur les systèmes où l'heure de démarrage est disponible.

Certains systèmes avec des environnements de bureau graphiques permettent aux utilisateurs non privilégiés de modifier l'horloge système. Comme sudo-rs s'appuie sur l'horloge système pour la validation des horodatages, il peut être possible sur de tels systèmes pour un utilisateur d'exécuter sudo plus longtemps que timestamp_timeout en reculant l'horloge. Pour contrer cela, sudo-rs utilise une horloge monotone (qui ne recule jamais) pour ses horodatages si le système le prend en charge. sudo-rs n'honorera pas les horodatages définis très loin dans le futur.
