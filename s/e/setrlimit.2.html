getrlimit(2) Manuel des appels système getrlimit(2)

NOM

getrlimit, setrlimit, prlimit - obtenir/définir les limites de ressources

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/resource.h>
int getrlimit(int resource, struct rlimit *rlim);
int setrlimit(int resource, const struct rlimit *rlim);
int prlimit(pid_t pid, int resource,
            const struct rlimit *_Nullable new_limit,
            struct rlimit *_Nullable old_limit);
struct rlimit {
    rlim_t  rlim_cur;  /* Limite logicielle */
    rlim_t  rlim_max;  /* Limite matérielle (plafond pour rlim_cur) */
};
typedef /* ... */  rlim_t;  /* Type entier non signé */

DESCRIPTION

Les appels système getrlimit() et setrlimit() obtiennent et définissent les limites de ressources. Chaque ressource a une limite logicielle et une limite matérielle associées, telles que définies par la structure rlimit.

La limite logicielle est la valeur que le noyau applique pour la ressource correspondante. La limite matérielle agit comme un plafond pour la limite logicielle : un processus non privilégié ne peut définir sa limite logicielle qu'à une valeur comprise entre 0 et la limite matérielle, et abaisser (de manière irréversible) sa limite matérielle. Un processus privilégié (sous Linux : celui ayant la capacité CAP_SYS_RESOURCE dans l'espace de noms utilisateur initial) peut apporter des modifications arbitraires à l'une ou l'autre des valeurs de limite.

La valeur RLIM_INFINITY signifie aucune limite sur une ressource (à la fois dans la structure renvoyée par getrlimit() et dans la structure passée à setrlimit()).

L'argument resource doit être l'un des suivants :

RLIMIT_AS
C'est la taille maximale de la mémoire virtuelle du processus (espace d'adressage). La limite est spécifiée en octets et est arrondie à la taille de page du système. Cette limite affecte les appels à brk(2), mmap(2), et mremap(2), qui échouent avec l'erreur ENOMEM en cas de dépassement de cette limite. De plus, l'expansion automatique de la pile échoue (et génère un SIGSEGV qui tue le processus si aucune pile alternative n'a été rendue disponible via sigaltstack(2)). Comme la valeur est un long, sur les machines avec un long 32 bits, soit cette limite est au plus de 2 Gio, soit cette ressource est illimitée.
RLIMIT_CORE
C'est la taille maximale d'un fichier de core dump (voir core(5)) en octets que le processus peut créer. Quand elle est à 0, aucun fichier de core dump n'est créé. Quand elle est non nulle, les dumps plus grands sont tronqués à cette taille.
RLIMIT_CPU
C'est une limite, en secondes, sur la quantité de temps CPU que le processus peut consommer. Lorsque le processus atteint la limite logicielle, il reçoit un signal SIGXCPU. L'action par défaut pour ce signal est de terminer le processus. Cependant, le signal peut être intercepté, et le gestionnaire peut renvoyer le contrôle au programme principal. Si le processus continue de consommer du temps CPU, il recevra SIGXCPU une fois par seconde jusqu'à ce que la limite matérielle soit atteinte, moment auquel il reçoit SIGKILL. (Ce dernier point décrit le comportement sous Linux. Les implémentations varient quant à la manière dont elles traitent les processus qui continuent de consommer du temps CPU après avoir atteint la limite logicielle. Les applications portables qui ont besoin d'intercepter ce signal doivent effectuer une terminaison ordonnée lors de la première réception de SIGXCPU.)
RLIMIT_DATA
C'est la taille maximale du segment de données du processus (données initialisées, données non initialisées et tas). La limite est spécifiée en octets et est arrondie à la taille de page du système. Cette limite affecte les appels à brk(2), sbrk(2), et (depuis Linux 4.7) mmap(2), qui échouent avec l'erreur ENOMEM en cas de rencontre de la limite logicielle de cette ressource.
RLIMIT_FSIZE
C'est la taille maximale en octets des fichiers que le processus peut créer. Les tentatives d'extension d'un fichier au-delà de cette limite entraînent la réception d'un signal SIGXFSZ. Par défaut, ce signal termine un processus, mais un processus peut intercepter ce signal à la place, auquel cas l'appel système pertinent (par exemple, write(2), truncate(2)) échoue avec l'erreur EFBIG.
RLIMIT_LOCKS (Linux 2.4.0 à Linux 2.4.24)
C'est une limite sur le nombre combiné de verrous flock(2) et de baux fcntl(2) que ce processus peut établir.
RLIMIT_MEMLOCK
C'est le nombre maximal d'octets de mémoire qui peuvent être verrouillés en RAM. Cette limite est arrondie à la multiple la plus proche de la taille de page du système. Cette limite affecte mlock(2), mlockall(2), et l'opération MAP_LOCKED de mmap(2). Depuis Linux 2.6.9, elle affecte également l'opération SHM_LOCK de shmctl(2), où elle établit un maximum sur les octets totaux dans les segments de mémoire partagée (voir shmget(2)) qui peuvent être verrouillés par l'ID utilisateur réel du processus appelant. Les verrous SHM_LOCK de shmctl(2) sont comptabilisés séparément des verrous mémoire par processus établis par mlock(2), mlockall(2), et l'opération MAP_LOCKED de mmap(2) ; un processus peut verrouiller des octets jusqu'à cette limite dans chacune de ces deux catégories.
Avant Linux 2.6.9, cette limite contrôlait la quantité de mémoire qui pouvait être verrouillée par un processus privilégié. Depuis Linux 2.6.9, aucune limite n'est imposée sur la quantité de mémoire qu'un processus privilégié peut verrouiller, et cette limite régit plutôt la quantité de mémoire qu'un processus non privilégié peut verrouiller.
RLIMIT_MSGQUEUE (depuis Linux 2.6.8)
C'est une limite sur le nombre d'octets qui peuvent être alloués pour les files d'attente de messages POSIX pour l'ID utilisateur réel du processus appelant. Cette limite est appliquée pour mq_open(3). Chaque file d'attente de messages que l'utilisateur crée compte (jusqu'à sa suppression) par rapport à cette limite selon la formule :
Depuis Linux 3.5 :

octets = attr.mq_maxmsg * sizeof(struct msg_msg) +
        MIN(attr.mq_maxmsg, MQ_PRIO_MAX) *
              sizeof(struct posix_msg_tree_node)+
                        /* Pour la surcharge */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Pour les données du message */

Linux 3.4 et antérieur :

octets = attr.mq_maxmsg * sizeof(struct msg_msg *) +
                        /* Pour la surcharge */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Pour les données du message */

où attr est la structure mq_attr spécifiée comme quatrième argument de mq_open(3), et les structures msg_msg et posix_msg_tree_node sont des structures internes au noyau.
Le terme de "surcharge" dans la formule prend en compte les octets de surcharge requis par l'implémentation et garantit que l'utilisateur ne peut pas créer un nombre illimité de messages de longueur nulle (de tels messages consomment néanmoins de la mémoire système pour la gestion interne).
RLIMIT_NICE (depuis Linux 2.6.12, mais voir BUGS ci-dessous)

RLIMIT_MSGQUEUE (since Linux 2.6.8)
This specifies the maximum number of bytes that can be used for POSIX message queues for the real user ID of the calling process. The soft limit for this resource is enforced only for processes without the CAP_SYS_RESOURCE capability. The hard limit is the maximum value that can be set for the soft limit; only a privileged process (CAP_SYS_RESOURCE) can raise the hard limit.
RLIMIT_NICE (since Linux 2.6.22)
This specifies a ceiling on the "nice value" (scheduling priority) that a process can set for itself using setpriority(2) or nice(2). The nice value range is thus from 1 (corresponding to a nice value of 19) to 40 (corresponding to a nice value of -20). This unusual choice of range was necessary because negative numbers cannot be specified as resource limit values, since they typically have special meanings. For example, RLIM_INFINITY typically is the same as -1. For more detail on the nice value, see sched(7).
RLIMIT_NOFILE
This specifies a value one greater than the maximum file descriptor number that can be opened by this process. Attempts (open(2), pipe(2), dup(2), etc.) to exceed this limit yield the error EMFILE. (Historically, this limit was named RLIMIT_OFILE on BSD.)
Since Linux 4.5, this limit also defines the maximum number of file descriptors that an unprivileged process (one without the CAP_SYS_RESOURCE capability) may have "in flight" to other processes, by being passed across UNIX domain sockets. This limit applies to the sendmsg(2) system call. For further details, see unix(7).
RLIMIT_NPROC
This is a limit on the number of extant process (or, more precisely on Linux, threads) for the real user ID of the calling process. So long as the current number of processes belonging to this process's real user ID is greater than or equal to this limit, fork(2) fails with the error EAGAIN.
The RLIMIT_NPROC limit is not enforced for processes that have either the CAP_SYS_ADMIN or the CAP_SYS_RESOURCE capability, or run with real user ID 0.
RLIMIT_RSS
This is a limit (in bytes) on the process's resident set (the number of virtual pages resident in RAM). This limit has effect only in Linux 2.4.x, x < 30, and there affects only calls to madvise(2) specifying MADV_WILLNEED.
RLIMIT_RTPRIO (since Linux 2.6.12, but see BUGS)
This specifies a ceiling on the real-time priority that may be set for this process using sched_setscheduler(2) and sched_setparam(2).
For further details on real-time scheduling policies, see sched(7)
RLIMIT_RTTIME (since Linux 2.6.25)
This is a limit (in microseconds) on the amount of CPU time that a process scheduled under a real-time scheduling policy may consume without making a blocking system call. For the purpose of this limit, each time a process makes a blocking system call, the count of its consumed CPU time is reset to zero. The CPU time count is not reset if the process continues trying to use the CPU but is preempted, its time slice expires, or it calls sched_yield(2).
Upon reaching the soft limit, the process is sent a SIGXCPU signal. If the process catches or ignores this signal and continues consuming CPU time, then SIGXCPU will be generated once each second until the hard limit is reached, at which point the process is sent a SIGKILL signal.
The intended use of this limit is to stop a runaway real-time process from locking up the system.
For further details on real-time scheduling policies, see sched(7)
RLIMIT_SIGPENDING (since Linux 2.6.8)
This is a limit on the number of signals that may be queued for the real user ID of the calling process. Both standard and real-time signals are counted for the purpose of checking this limit. However, the limit is enforced only for sigqueue(2); it is always possible to use kill(2) to queue one instance of any of the signals that are not already queued to the process.
RLIMIT_STACK
This is the maximum size of the process stack, in bytes. Upon reaching this limit, a SIGSEGV signal is generated. To handle this signal, a process must employ an alternate signal stack (sigaltstack(2)).
Since Linux 2.6.23, this limit also determines the amount of space used for the process's command-line arguments and environment variables; for details, see execve(2).

prlimit()

The Linux-specific prlimit() system call combines and extends the functionality of setrlimit() and getrlimit(). It can be used to both set and get the resource limits of an arbitrary process.

The resource argument has the same meaning as for setrlimit() and getrlimit().

If the new_limit argument is not NULL, then the rlimit structure to which it points is used to set new values for the soft and hard limits for resource. If the old_limit argument is not NULL, then a successful call to prlimit() places the previous soft and hard limits for resource in the rlimit structure pointed to by old_limit.

The pid argument specifies the ID of the process on which the call is to operate. If pid is 0, then the call applies to the calling process. To set or get the resources of a process other than itself, the caller must have the CAP_SYS_RESOURCE capability in the user namespace of the process whose resource limits are being changed, or the real, effective, and saved set user IDs of the target process must match the real user ID of the caller and the real, effective, and saved set group IDs of the target process must match the real group ID of the caller.

VALEUR DE RETOUR

En cas de succès, ces appels système renvoient 0. En cas d'erreur, -1 est renvoyé, et errno est défini pour indiquer l'erreur.

ERREURS

EFAULT
Un argument pointeur pointe vers un emplacement en dehors de l'espace d'adressage accessible.
EINVAL
La valeur spécifiée dans resource n'est pas valide ; ou, pour setrlimit() ou prlimit() : rlim->rlim_cur était supérieure à rlim->rlim_max.
EPERM
Un processus non privilégié a tenté d'augmenter la limite dure ; la capacité CAP_SYS_RESOURCE est requise pour ce faire.
EPERM
L'appelant a tenté d'augmenter la limite dure RLIMIT_NOFILE au-delà du maximum défini par /proc/sys/fs/nr_open (voir proc(5))
EPERM
(prlimit()) Le processus appelant n'avait pas la permission de définir les limites pour le processus spécifié par pid.
ESRCH
Impossible de trouver un processus avec l'ID spécifié dans pid.

NOTES

Un processus enfant créé via fork(2) hérite des limites de ressources de son parent. Les limites de ressources sont préservées lors de execve(2).

Les limites de ressources sont des attributs par processus qui sont partagés par tous les threads d'un processus.

La réduction de la limite souple pour une ressource en dessous de la consommation actuelle de cette ressource par le processus réussira (mais empêchera le processus d'augmenter davantage sa consommation de la ressource).

On peut définir les limites de ressources du shell en utilisant la commande intégrée ulimit (limit dans csh(1)). Les limites de ressources du shell sont héritées par les processus qu'il crée pour exécuter des commandes.

Depuis Linux 2.6.24, les limites de ressources de n'importe quel processus peuvent être inspectées via /proc/pid/limits ; voir proc(5).

Les anciens systèmes fournissaient une fonction vlimit() avec un but similaire à setrlimit(). Pour des raisons de compatibilité descendante, glibc

également fournit vlimit(). Toutes les nouvelles applications devraient être écrites en utilisant setrlimit().

Différences ABI bibliothèque C/noyau

Depuis glibc 2.13, les fonctions d'encapsulation getrlimit() et setrlimit() de glibc n'invoquent plus les appels système correspondants, mais utilisent plutôt prlimit(), pour les raisons décrites dans BUGS.

Le nom de la fonction d'encapsulation de glibc est prlimit() ; l'appel système sous-jacent est prlimit64().

BUGS

Dans les anciens noyaux Linux, les signaux SIGXCPU et SIGKILL envoyés lorsqu'un processus atteignait les limites douces et dures de RLIMIT_CPU étaient envoyés une (seconde de CPU) plus tard qu'ils n'auraient dû l'être. Ceci a été corrigé dans Linux 2.6.8.

Dans les noyaux Linux 2.6.x avant Linux 2.6.17, une limite RLIMIT_CPU de 0 est traitée à tort comme "aucune limite" (comme RLIM_INFINITY). Depuis Linux 2.6.17, définir une limite de 0 a un effet, mais est en fait traitée comme une limite de 1 seconde.

Un bug du noyau signifie que RLIMIT_RTPRIO ne fonctionne pas sous Linux 2.6.12 ; le problème est corrigé dans Linux 2.6.13.

Sous Linux 2.6.12, il y avait une incohérence d'une unité entre les plages de priorité retournées par getpriority(2) et RLIMIT_NICE. Cela avait pour effet que le plafond réel de la valeur de "nice" était calculé comme 19 - rlim_cur. Ceci a été corrigé dans Linux 2.6.13.

Depuis Linux 2.6.12, si un processus atteint sa limite douce de RLIMIT_CPU et a un gestionnaire installé pour SIGXCPU, alors, en plus d'invoquer le gestionnaire de signaux, le noyau augmente la limite douce d'une seconde. Ce comportement se répète si le processus continue de consommer du temps CPU, jusqu'à ce que la limite dure soit atteinte, moment auquel le processus est tué. D'autres implémentations ne modifient pas la limite douce de RLIMIT_CPU de cette manière, et le comportement de Linux n'est probablement pas conforme aux normes ; les applications portables devraient éviter de s'appuyer sur ce comportement spécifique à Linux. La limite spécifique à Linux RLIMIT_RTTIME présente le même comportement lorsque la limite douce est rencontrée.

Les noyaux avant Linux 2.4.22 ne diagnostiquaient pas l'erreur EINVAL pour setrlimit() lorsque rlim->rlim_cur était supérieur à rlim->rlim_max.

Linux ne retourne pas d'erreur lorsqu'une tentative de définir RLIMIT_CPU a échoué, pour des raisons de compatibilité.

Représentation des valeurs de limite de ressource "grandes" sur les plateformes 32 bits

Les fonctions d'encapsulation getrlimit() et setrlimit() de glibc utilisent un type de données rlim_t de 64 bits, même sur les plateformes 32 bits. Cependant, le type de données rlim_t utilisé dans les appels système getrlimit() et setrlimit() est un unsigned long (32 bits). De plus, sous Linux, le noyau représente les limites de ressources sur les plateformes 32 bits en tant qu'unsigned long. Cependant, un type de données 32 bits n'est pas assez large. La limite la plus pertinente ici est RLIMIT_FSIZE, qui spécifie la taille maximale à laquelle un fichier peut croître : pour être utile, cette limite doit être représentée en utilisant un type aussi large que le type utilisé pour représenter les décalages de fichier — c'est-à-dire aussi large qu'un off_t de 64 bits (en supposant un programme compilé avec _FILE_OFFSET_BITS=64).

Pour contourner cette limitation du noyau, si un programme essayait de définir une limite de ressource à une valeur supérieure à ce qui peut être représenté dans un unsigned long de 32 bits, alors la fonction d'encapsulation setrlimit() de glibc convertissait silencieusement la valeur de la limite en RLIM_INFINITY. En d'autres termes, le réglage de la limite de ressource demandé était ignoré en silence.

Depuis glibc 2.13, glibc contourne les limitations des appels système getrlimit() et setrlimit() en implémentant setrlimit() et getrlimit() comme des fonctions d'encapsulation qui appellent prlimit().

EXEMPLES

Le programme ci-dessous démontre l'utilisation de prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Usage: %s <pid> [<nouvelle-limite-douce> "
                "<nouvelle-limite-dure>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID du processus cible */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Définir la limite de temps CPU du processus cible ; récupérer et afficher
       la limite précédente */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Limites précédentes : douce=%jd; dure=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Récupérer et afficher la nouvelle limite de temps CPU */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("Nouvelles limites : douce=%jd; dure=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
