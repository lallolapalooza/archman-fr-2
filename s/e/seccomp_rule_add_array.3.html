NOM

seccomp_rule_add, seccomp_rule_add_exact - Ajouter une règle de filtre seccomp

Lier avec -lseccomp.

DESCRIPTION

Les fonctions seccomp_rule_add(), seccomp_rule_add_array(), seccomp_rule_add_exact(), et seccomp_rule_add_exact_array() ajoutent toutes une nouvelle règle de filtre au filtre seccomp actuel. Les fonctions seccomp_rule_add() et seccomp_rule_add_array() feront de leur mieux pour ajouter la règle telle que spécifiée, mais peuvent la modifier légèrement en raison des spécificités architecturales (par exemple, réécriture interne des appels système multiplexés, comme les fonctions socket et ipc sur x86). Les fonctions seccomp_rule_add_exact() et seccomp_rule_add_exact_array() tenteront d'ajouter la règle exactement telle que spécifiée, elle peut donc se comporter différemment selon les architectures. Bien qu'elle ne garantisse pas un ensemble exact de règles de filtre, seccomp_rule_add() et seccomp_rule_add_array() garantissent un comportement identique quelle que soit l'architecture.

La règle de filtre nouvellement ajoutée ne prend effet que lorsque l'ensemble du filtre est chargé dans le noyau à l'aide de seccomp_load(3). Lors de l'ajout de règles à un filtre, il est important de considérer l'impact des filtres précédemment chargés ; voir la documentation de seccomp_load(3) pour plus d'informations.

Toutes les règles de filtre fournies par l'application appelante sont combinées en une union, avec une logique supplémentaire pour éliminer les filtres d'appels système redondants. Par exemple, si une règle est ajoutée qui autorise un appel système donné avec un ensemble spécifique de valeurs d'arguments et plus tard une règle est ajoutée qui autorise le même appel système indépendamment des valeurs d'arguments, alors la première règle, plus spécifique, est effectivement supprimée du filtre par la seconde règle plus générique.

Les macros SCMP_CMP(), SCMP_CMP64(), SCMP_A{0-5}(), et SCMP_A{0-5}_64() génèrent une structure scmp_arg_cmp pour une utilisation avec les fonctions ci-dessus. Les macros SCMP_CMP() et SCMP_CMP64() permettent à l'appelant de spécifier un argument arbitraire avec l'opérateur de comparaison, le masque 64 bits et les valeurs de données 64 bits, tandis que les macros SCMP_A{0-5}() et SCMP_A{0-5}_64() sont spécifiques à un argument donné.

Les macros SCMP_CMP32() et SCMP_A{0-5}_32() sont similaires aux variantes ci-dessus, mais elles prennent des masques et des données 32 bits.

Il est recommandé, chaque fois que possible, d'éviter aux développeurs d'utiliser les macros SCMP_CMP() et SCMP_A{0-5}() et d'utiliser les variantes qui sont explicitement 32 ou 64 bits. Cela devrait aider à éliminer les problèmes causés par une extension de signe non désirée des valeurs négatives.

Si des comparaisons d'arguments d'appels système sont incluses dans la règle de filtre, toutes les comparaisons doivent être vraies pour que la règle corresponde.

Lors de l'ajout de comparaisons d'arguments d'appels système au filtre, il est important de se rappeler que bien qu'il soit possible d'avoir plusieurs comparaisons dans une seule règle, vous ne pouvez comparer chaque argument qu'une seule fois dans une seule règle. En d'autres termes, vous ne pouvez pas avoir plusieurs comparaisons du 3ème argument d'appel système dans une seule règle.

Dans un filtre contenant plusieurs architectures, il est une erreur d'ajouter une règle de filtre pour un appel système qui n'existe pas dans toutes les architectures du filtre.

Bien qu'il soit possible de spécifier directement la valeur du syscall en utilisant les valeurs standard __NR_syscall, afin d'assurer un fonctionnement correct sur plusieurs architectures, il est fortement recommandé d'utiliser plutôt la macro SCMP_SYS(). Voir la section EXEMPLES ci-dessous. Il est également important de se rappeler que, quelles que soient les architectures présentes dans le filtre, les numéros d'appels système utilisés dans les règles de filtre sont interprétés dans le contexte de l'architecture native.

À partir de Linux v4.8, il peut être nécessaire de créer une règle avec une valeur d'appel système de -1 pour permettre aux programmes de traçage de sauter une invocation d'appel système ; pour créer une règle avec une valeur d'appel système de -1, il est nécessaire de définir d'abord l'attribut SCMP_FLTATR_API_TSKIP. Voir seccomp_attr_set(3) pour plus d'informations.

Le contexte de filtre ctx est la valeur retournée par l'appel à seccomp_init(3).

Les valeurs action valides sont les suivantes :

SCMP_ACT_KILL
Le thread sera tué par le noyau lorsqu'il appellera un appel système qui correspond à la règle de filtre.
SCMP_ACT_KILL_PROCESS
Le processus sera tué par le noyau lorsqu'il appellera un appel système qui correspond à la règle de filtre.
SCMP_ACT_TRAP
Le thread lancera un signal SIGSYS lorsqu'il appellera un appel système qui correspond à la règle de filtre.
SCMP_ACT_ERRNO(uint16_t errno)
Le thread recevra une valeur de retour de errno lorsqu'il appellera un appel système qui correspond à la règle de filtre.
SCMP_ACT_TRACE(uint16_t msg_num)
Si le thread est traqué et que le processus de traçage a spécifié l'option PTRACE_O_TRACESECCOMP dans l'appel à ptrace(2), le processus de traçage sera notifié, via PTRACE_EVENT_SECCOMP, et la valeur fournie dans msg_num pourra être récupérée en utilisant l'option PTRACE_GETEVENTMSG.
f="#SCMP_ACT_LOG">SCMP_ACT_LOG
Le filtre seccomp n'aura aucun effet sur le thread appelant l'appel système s'il correspond à la règle du filtre, mais l'appel système sera consigné.
SCMP_ACT_ALLOW
Le filtre seccomp n'aura aucun effet sur le thread appelant l'appel système s'il correspond à la règle du filtre.
SCMP_ACT_NOTIFY
Un processus de surveillance sera notifié lorsqu'un processus exécutant le filtre seccomp appellera un appel système qui correspond à la règle du filtre. Le processus qui invoque l'appel système attend dans le noyau jusqu'à ce que le processus de surveillance ait répondu via seccomp_notify_respond (3).

Lorsqu'un filtre utilisant SCMP_ACT_NOTIFY est chargé dans le noyau, le noyau génère un descripteur de fichier de notification qui doit être utilisé pour communiquer entre le processus de surveillance et le(s) processus filtré(s). Voir seccomp_notif_fd (3) pour plus d'informations.

Les valeurs valides pour op sont les suivantes :

SCMP_CMP_NE
Correspond lorsque la valeur de l'argument n'est pas égale à la valeur de la donnée, exemple :

SCMP_CMP( arg , SCMP_CMP_NE , datum )

SCMP_CMP_LT
Correspond lorsque la valeur de l'argument est inférieure à la valeur de la donnée, exemple :

SCMP_CMP( arg , SCMP_CMP_LT , datum )

SCMP_CMP_LE
Correspond lorsque la valeur de l'argument est inférieure ou égale à la valeur de la donnée, exemple :

SCMP_CMP( arg , SCMP_CMP_LE , datum )

SCMP_CMP_EQ
Correspond lorsque la valeur de l'argument est égale à la valeur de la donnée, exemple :

SCMP_CMP( arg , SCMP_CMP_EQ , datum )

SCMP_CMP_GE
Correspond lorsque la valeur de l'argument est supérieure ou égale à la valeur de la donnée, exemple :

SCMP_CMP( arg , SCMP_CMP_GE , datum )

SCMP_CMP_GT
Correspond lorsque la valeur de l'argument est supérieure à la valeur de la donnée, exemple :

SCMP_CMP( arg , SCMP_CMP_GT , datum )

SCMP_CMP_MASKED_EQ
Correspond lorsque la valeur masquée de l'argument est égale à la valeur masquée de la donnée, exemple :

SCMP_CMP( arg , SCMP_CMP_MASKED_EQ , mask , datum )

VALEUR DE RETOUR

La macro SCMP_SYS() renvoie une valeur appropriée pour être utilisée comme valeur syscall dans les fonctions seccomp_rule_add*(). De manière similaire, les macros SCMP_CMP() et SCMP_A*() renvoient des valeurs appropriées pour être utilisées comme comparaisons d'arguments dans les fonctions seccomp_rule_add() et seccomp_rule_add_exact().

Les fonctions seccomp_rule_add(), seccomp_rule_add_array(), seccomp_rule_add_exact() et seccomp_rule_add_exact_array() renvoient zéro en cas de succès ou l'un des codes d'erreur suivants en cas d'échec :

-EDOM
Échec spécifique à l'architecture.
-EEXIST
La règle existe déjà.
-EACCCES
La règle entre en conflit avec le filtre (par exemple, l' action de la règle est égale à l'action par défaut du filtre).
-EFAULT
Échec interne de libseccomp.
-EINVAL
Entrée invalide, le contexte ou le jeton d'architecture est invalide.
-ENOMEM
La bibliothèque n'a pas pu allouer suffisamment de mémoire.
-EOPNOTSUPP
La bibliothèque ne prend pas en charge l'opération particulière.

EXEMPLES

#include <fcntl.h>
#include <seccomp.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <stddef.h>
#define BUF_SIZE	256
int main(int argc, char *argv[])
{
	int rc = -1;
	scmp_filter_ctx ctx;
	struct scmp_arg_cmp arg_cmp[] = { SCMP_A0(SCMP_CMP_EQ, 2) };
	int fd;
	unsigned char buf[BUF_SIZE];
	ctx = seccomp_init(SCMP_ACT_KILL);
	if (ctx == NULL)
		goto out;
	/* ... */
	fd = open("file.txt", 0);
	/* ... */
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(close), 0);
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit_group), 0);
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit), 0);
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read), 3,
			      SCMP_A0(SCMP_CMP_EQ, fd),
			      SCMP_A1(SCMP_CMP_EQ, (scmp_datum_t)buf),
			      SCMP_A2(SCMP_CMP_LE, BUF_SIZE));
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
			      SCMP_CMP(0, SCMP_CMP_EQ, fd));
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add_array(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
			            arg_cmp);
	if (rc < 0)
		goto out;
	rc = seccomp_load(ctx);
	if (rc < 0)
		goto out;
	/* ... */
out:
	seccomp_release(ctx);
	return -rc;
}

NOTES

Bien que le filtre seccomp puisse être généré indépendamment du noyau, un support du noyau est requis pour charger et appliquer le filtre seccomp généré par libseccomp.

Le site du projet libseccomp, avec plus d'informations et le dépôt de code source, se trouve à https://github.com/seccomp/libseccomp. Cet outil, ainsi que la bibliothèque libseccomp, est actuellement en cours de développement, veuillez signaler tout bug sur le site du projet ou directement à l'auteur.

BOGUES

Le comportement à l'exécution des filtres seccomp dépend de la version du noyau, de l'architecture du processeur et d'autres bibliothèques, y compris libc. Cela pourrait affecter le code de retour d'un filtre seccomp.

*
PowerPC glibc ne renverra pas un nombre négatif lorsque l'appel système getpid() est invoqué. Si un filtre seccomp a été créé où getpid() renverra un nombre négatif du noyau, alors PowerPC glibc renverra la valeur absolue de l'errno. Dans ce cas, il est très difficile pour une application de distinguer entre l'errno et un pid valide.
