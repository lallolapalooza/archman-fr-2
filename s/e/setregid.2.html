setreuid(2) Manuel des appels système setreuid(2)

NOM

setreuid, setregid - définir l'identifiant d'utilisateur ou de groupe réel et/ou effectif

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <unistd.h>
int setreuid(uid_t ruid, uid_t euid);
int setregid(gid_t rgid, gid_t egid);
Exigences pour les macros de test de fonctionnalités glibc (voir feature_test_macros(7)):

setreuid(), setregid():

    _XOPEN_SOURCE >= 500
        || /* Depuis glibc 2.19 : */ _DEFAULT_SOURCE
        || /* glibc <= 2.19 : */ _BSD_SOURCE

DESCRIPTION

setreuid() définit les identifiants d'utilisateur réels et effectifs du processus appelant.

Fournir une valeur de -1 pour l'identifiant d'utilisateur réel ou effectif laisse cet identifiant inchangé.

Les processus non privilégiés ne peuvent définir l'identifiant d'utilisateur effectif que sur l'identifiant d'utilisateur réel, l'identifiant d'utilisateur effectif ou l'identifiant d'utilisateur de jeu sauvegardé.

Les utilisateurs non privilégiés ne peuvent définir l'identifiant d'utilisateur réel que sur l'identifiant d'utilisateur réel ou l'identifiant d'utilisateur effectif.

Si l'identifiant d'utilisateur réel est défini (c'est-à-dire que ruid n'est pas -1) ou si l'identifiant d'utilisateur effectif est défini sur une valeur différente de l'identifiant d'utilisateur réel précédent, l'identifiant d'utilisateur de jeu sauvegardé sera défini sur le nouvel identifiant d'utilisateur effectif.

De manière entièrement analogue, setregid() définit les identifiants de groupe réels et effectifs du processus appelant, et tout ce qui précède s'applique avec « groupe » au lieu de « utilisateur ».

VALEUR DE RETOUR

En cas de succès, zéro est renvoyé. En cas d'erreur, -1 est renvoyé et errno est défini pour indiquer l'erreur.

Note : il existe des cas où setreuid() peut échouer même lorsque l'appelant est l'UID 0 ; omettre la vérification d'un retour d'échec de setreuid() constitue une grave erreur de sécurité.

ERREURS

EAGAIN
L'appel modifierait l'UID réel de l'appelant (c'est-à-dire que ruid ne correspond pas à l'UID réel de l'appelant), mais il y a eu un échec temporaire d'allocation des structures de données noyau nécessaires.
EAGAIN
ruid ne correspond pas à l'UID réel de l'appelant et cet appel dépasserait la limite de ressources RLIMIT_NPROC du nombre de processus appartenant à l'UID réel ruid. Depuis Linux 3.1, ce cas d'erreur ne se produit plus (mais les applications robustes devraient vérifier cette erreur) ; voir la description de EAGAIN dans execve(2).
EINVAL
Un ou plusieurs des identifiants d'utilisateur ou de groupe cibles ne sont pas valides dans cet espace de noms utilisateur.
EPERM
Le processus appelant n'est pas privilégié (sous Linux, il ne possède pas la capacité nécessaire dans son espace de noms utilisateur : CAP_SETUID dans le cas de setreuid(), ou CAP_SETGID dans le cas de setregid()) et une modification autre que (i) l'échange de l'identifiant effectif d'utilisateur (groupe) avec l'identifiant réel d'utilisateur (groupe), ou (ii) la définition de l'un sur la valeur de l'autre, ou (iii) la définition de l'identifiant effectif d'utilisateur (groupe) sur la valeur de l'identifiant d'utilisateur (groupe) de jeu sauvegardé, a été spécifiée.

VERSIONS

POSIX.1 ne spécifie pas toutes les modifications d'UID que Linux autorise pour un processus non privilégié. Pour setreuid(), l'identifiant d'utilisateur effectif peut être rendu identique à l'identifiant d'utilisateur réel ou à l'identifiant d'utilisateur de jeu sauvegardé, et il n'est pas spécifié si les processus non privilégiés peuvent définir l'identifiant d'utilisateur réel sur l'identifiant d'utilisateur réel, l'identifiant d'utilisateur effectif ou l'identifiant d'utilisateur de jeu sauvegardé. Pour setregid(), l'identifiant de groupe réel peut être changé pour la valeur de l'identifiant de groupe de jeu sauvegardé, et l'identifiant de groupe effectif peut être changé pour la valeur de l'identifiant de groupe réel ou de l'identifiant de groupe de jeu sauvegardé. Les détails précis des modifications d'identifiants autorisées varient selon les implémentations.

POSIX.1 ne spécifie rien quant à l'effet de ces appels sur l'identifiant d'utilisateur de jeu sauvegardé et l'identifiant de groupe de jeu sauvegardé.

NORMES

POSIX.1-2024.

HISTORIQUE

POSIX.1-2001, 4.3BSD (est apparu pour la première fois dans 4.2BSD).

La définition de l'identifiant d'utilisateur (groupe) effectif sur l'identifiant d'utilisateur (groupe) de jeu sauvegardé est possible depuis Linux 1.1.37 (1.1.38).

Les appels système setreuid() et setregid() d'origine sous Linux supportaient uniquement les identifiants d'utilisateur et de groupe sur 16 bits. Par la suite, Linux 2.4 a ajouté setreuid32() et setregid32(), supportant les identifiants sur 32 bits. Les fonctions d'encapsulation setreuid() et setregid() de glibc gèrent de manière transparente les variations entre les versions du noyau.

Différences bibliothèque C/noyau

Au niveau du noyau, les identifiants d'utilisateur et de groupe sont des attributs par thread. Cependant, POSIX exige que tous les threads d'un processus partagent les mêmes identifiants. L'implémentation de threading NPTL gère les exigences POSIX en fournissant des fonctions d'encapsulation pour les divers appels système qui modifient les UID et GID des processus. Ces fonctions d'encapsulation (y compris celles pour setreuid() et setregid()) utilisent une technique basée sur les signaux pour garantir que lorsqu'un thread modifie les identifiants, tous les autres threads du processus modifient également leurs identifiants. Pour plus de détails, voir nptl(7).
