NOM

/etc/ser2net/ser2net.yaml - Fichier de configuration du proxy série vers réseau

DESCRIPTION

ser2net était autrefois un programme pour connecter des connexions réseau à des ports série. C'est maintenant un programme pour connecter des accepteurs gensio à des connecteurs gensio. Voir gensio(5) pour plus de détails sur les gensios.

ser2net est configuré avec YAML, qui est flexible et facile à utiliser. Consultez la documentation YAML sur internet pour savoir comment cela fonctionne.

Cependant, il existe deux types de fichiers YAML que ser2net peut utiliser : version 1 et version 2. Les fichiers YAML version 1 ont plus de capacités que les fichiers version 2, mais ils ne sont pas au format YAML standard, un analyseur YAML standard ne peut pas les lire. ser2net détectera automatiquement la version en fonction de ce qu'il trouve.

En version 2, vous pouvez avoir plusieurs documents dans un fichier et ser2net les lira tous. YAML sépare les documents dans un fichier avec un seul « --- » seul en début de ligne. Bien que vous ne puissiez avoir qu'un seul ensemble de valeurs par défaut, de définitions, de connexions, etc. dans un document, vous pouvez avoir plusieurs documents dans un fichier pour en permettre plus d'un. Vous pourriez, par exemple, regrouper toutes les connexions avec un certain ensemble de valeurs par défaut dans leur propre document.

SPÉCIFICATION DE DÉFINITION

YAML a la capacité de créer des alias qui peuvent être utilisés ailleurs dans le fichier de configuration. Ceux-ci peuvent être utilisés pour lier des choses entre différentes parties du fichier, ou (en tant qu'extension à YAML) pour la substitution de chaînes de caractères.

Vous définissez un alias en version 1 avec ce qui suit :

define: &nom_alias texte de l'alias

Cela créera un alias avec le nom donné. Ensuite, vous pouvez l'utiliser ailleurs comme suit :

banner: *nom_alias

et la bannière sera « texte de l'alias ». Contrairement au YAML standard, vous pouvez également l'utiliser à l'intérieur des chaînes en utilisant

*(nom_alias)

donc si vous avez

banner: Ma bannière *(nom_alias) est ici

La bannière sera « Ma bannière texte de l'alias est ici ». Consultez la documentation YAML pour savoir comment les espaces sont gérés, mais notez qu'il faut utiliser des guillemets si vous n'êtes pas sûr, comme ceci :

define: &nom_alias "texte de l'alias"
banner: "Ma bannière *(nom_alias) est ici"

Si pour une raison quelconque vous avez besoin de « * ( » dans votre texte, utilisez « *(* » pour cela.

Pour les fichiers YAML version 2, la définition est :

defines:
nom_alias: texte de l'alias
nom_alias2: texte de l'alias 2

où vous pouvez lister autant d'alias que vous le souhaitez. En version 2, vous faites toujours référence à un alias avec « = » au lieu de « * », comme suit :


banner: "Ma bannière =(nom_alias) est ici"

et si pour une raison quelconque vous avez besoin de « =( » dans votre texte, utilisez « =(= » pour cela.

En version 2, conformément au YAML standard, vous ne pouvez avoir qu'une seule section de définitions, elles doivent donc être regroupées.

INCLURE D'AUTRES FICHIERS

Un fichier YAML peut inclure un autre fichier au niveau principal, avec :

include: <nom_de_fichier>

Ce nom de fichier peut inclure des jokers, et tous les fichiers référencés sont inclus. Ce doivent être des fichiers yaml complets, mais ils sont inclus dans le contexte à ce moment-là, avec toutes les définitions, noms de connexions, etc. Cela peut vous permettre d'avoir des connexions individuelles dans des fichiers individuels pour faciliter la gestion.

En version 2, vous ne pouvez avoir qu'une seule inclusion par document pour être conforme au YAML, donc si vous avez besoin de plusieurs inclusions, vous devrez avoir plusieurs documents.

UTILISER DES FICHIERS EXTERNES

Vous voudrez peut-être stocker des mots de passe et autres dans des fichiers externes pour une meilleure sécurité. Pour la version 1, mettre « *{nom_de_fichier} » dans un scalaire YAML insérera le contenu du fichier au scalaire à cet endroit. Si vous avez besoin d'un « *{ » dans la chaîne pour une raison quelconque, utilisez « *{*} ».

Pour la version 2, utilisez « ={nom_de_fichier} » à la place. Et « ={= » pour inclure un « ={ » dans un fichier.

SPÉCIFICATION DE CONNEXION

Une connexion est une structure qui décrit comment connecter un accepteur gensio à un connecteur gensio.

Une spécification de connexion en version 1 commence par :

connection: &<alias>
<définition>

En version 2, elle est spécifiée comme suit :

connections:
<alias>:
<définition>

En version 2, toutes les connexions doivent se trouver ensemble, en un seul endroit.

La <définition> d'une connexion est la même pour la version 1 et la version 2 :

accepter: <accepteur>
timeout: <nombre>
enable: on|off
connecteur: <connecteur>
options:
<nom_option>: <valeur_option>
<nom_option>: <valeur_option>...

Un <accepteur> est une spécification de gensio d'acceptation. Lorsque ser2net reçoit une connexion sur l'accepteur, il tente d'établir une connexion au gensio <connecteur>. L'alias est requis, il définit le nom utilisé pour la connexion dans l'interface d'administration et pour la référence depuis les rotators.

Si la connexion ne reçoit aucune activité pendant <timeout> secondes, ser2net la fermera. Définir <timeout> à zéro désactive le délai d'attente. Le champ timeout est facultatif et vaut zéro par défaut.

La connexion peut être activée ou désactivée avec le champ enable. Le champ enable est facultatif et vaut « on » par défaut. C'est utile pour désactiver temporairement un port en réglant enable sur « off » et en envoyant un SIGHUP. S'il y a des utilisateurs connectés et que vous désactivez un port et envoyez un SIGHUP, les utilisateurs seront déconnectés.

Une option est un paramètre de configuration qui n'a rien à voir avec des gensios spécifiques, ce sont des contrôles pour ser2net en général. La section options est facultative.

Voir gensio(5) pour de nombreuses informations sur les gensios spécifiques disponibles.

Pour permettre une connexion TCP à un port série et ignorer le contrôle du modem, vous pouvez faire :

connection: &versS0tcp
accepter: tcp,1234
connecteur: serialdev,/dev/ttyS0,local

Les gensios d'acceptation et de connexion se empilent, donc si vous voulez ajouter telnet avec le support RFC2217, vous pouvez faire :

connection: &versS0telnet
accepter: telnet(rfc2217),tcp,1234
connecteur: serialdev,/dev/ttyS0,local

Si vous souhaitez accepter une connexion telnet sur SCTP uniquement sur localhost IPv6 et vous connecter à une connexion telnet avec SSL sur tcp, vous pouvez faire :

connection: &versMonHost
accepter: telnet,sctp,::1,1234
connecteur: telnet,ssl,tcp,monhost.domaine.org,1234

Le support RFC2217 n'a de sens qu'avec un appareil capable de gérer le série comme connecteur. Notez également que l'IPv6 est entièrement pris en charge. Les accepteurs seront généralement par défaut compatibles IPv4 et IPv6, sauf indication contraire. Voir gensio(5) pour les détails.

Et oui, SCTP est pris en charge et est fortement recommandé si vous pouvez l'utiliser. Le multi-homing seul en vaut la peine.

Vous pourriez créer une connexion sécurisée avec telnet et support RFC2217 qui se connecte ensuite à une connexion IPMI sol. Remarquez comment la division de la ligne du connecteur est effectuée avec YAML.

connection: &authsol

accepter: telnet(rfc2217),mux,certauth,ssl,sctp,1234
connecteur: ipmisol,lan -U ipmiusr -P test -p 9001
ipmiserver.domaine.org,9600
options:
banner: Ma bannière

Ce sont quelques exemples. Pour SSL et certauth, j'ai ignoré la configuration d'authentification, plus à ce sujet plus tard. L'utilisation de l'authentification est fortement recommandée, c'est facile maintenant avec gtlssh et si vous devez l'utiliser à partir d'un programme, c'est facile avec gensio. Il existe même un support Python. L'ajout de support pour d'autres langages de script ne devrait pas être trop difficile.

OPTIONS DE SPECIFICATION DE CONNEXION

kickolduser: true|false configure le port de sorte que l'utilisateur précédent soit déconnecté si un nouvel utilisateur arrive. Utile si vous oubliez souvent de vous déconnecter d'un autre endroit.

banner: <chaîne de bannière> affiche la bannière donnée lorsqu'un client se connecte. Elle utilise le traitement de chaîne tel que décrit dans "TRAITEMENT SPECIAL DES CHAINES" ci-dessus.

signature: <chaîne de signature> envoie la signature RFC2217 sur demande du client. Cela peut être une chaîne vide.

openstr: <chaîne de nom openstr> Envoie la chaîne donnée à l'appareil lors de la première ouverture. Cela peut être une chaîne vide. Elle utilise le traitement de chaîne tel que décrit dans "TRAITEMENT SPECIAL DES CHAINES" ci-dessus.

closestr: <nom closestr> Envoie la chaîne donnée à l'appareil lors de la fermeture finale. Cela peut être une chaîne vide. Elle utilise le traitement de chaîne tel que décrit dans "TRAITEMENT SPECIAL DES CHAINES" ci-dessus.

closeon: <chaîne closeon> Si la chaîne donnée est détectée venant du côté connexion de la connexion, ferme la connexion. La comparaison ici est, pour simplifier, basique. Les expressions complexes avec des éléments répétitifs peuvent ne pas être comparées correctement. Par exemple, si votre chaîne closeon est "ababc" et votre chaîne d'entrée est "abababc", la comparaison échouera car l'algorithme de comparaison verra "ababa" et échouera sur le dernier "a" et recommencera à partir de "abc", ce qui ne correspondra pas. Cela ne devrait pas poser de problème dans la plupart des cas, mais si c'est le cas, contactez les auteurs et cela pourra être amélioré.

accepter-retry-time: <temps en secondes> Si l'accepteur ne démarre pas au démarrage, attendez ce nombre de secondes et réessayez .

connector-retry-time: <temps en secondes> Sur un port de connexion inverse, si le connecteur ne démarre pas ou s'arrête. Attendez ce nombre de secondes et réessayez .

trace-read: <nom de fichier> Lorsque l'accepteur est ouvert, ouvrez le fichier donné et stockez toutes les données lues depuis le périphérique physique (et donc écrites sur le port réseau/accepteur du client) dans le fichier. Si le fichier existe déjà, il est ajouté. Le fichier est fermé lorsque le port est fermé. Le nom de fichier utilise le traitement de chaîne tel que décrit dans "TRAITEMENT SPECIAL DES CHAINES" ci-dessus.

trace-write: <nom de fichier> Comme tr, mais trace les données écrites sur le gensio de connexion.

trace-both: <nom de fichier> trace les données lues et écrites dans le même fichier. Notez que ceci est indépendant de tr et tw, donc vous pouvez tracer la lecture, l'écriture et les deux vers des fichiers différents.

trace-hexdump: true|false active/désactive la sortie hexdump vers tous les fichiers de trace. Chaque ligne dans le fichier de trace sera sur 8 octets (ou moins) dans un format hexadécimal/ASCII canonique. C'est utile pour déboguer un protocole binaire.

trace-timestamp: true|false ajoute/supprime un horodatage à tous les fichiers de trace. Un horodatage est préfixé à chaque ligne si hexdump est actif pour le fichier de trace. Une ligne horodatée est également enregistrée dans le fichier de trace lorsqu'un client distant se connecte ou se déconnecte du port.

[trace-read-|trace-write-|trace-both-]hexdump: true|false active/désactive la sortie hexdump pour un seul fichier de trace. Peut être combiné avec hexdump. L'ordre est important.

[trace-read-|trace-write-|trace-both-]timestamp: true|false ajoute/supprime un horodatage à un seul fichier de trace. Peut être combiné avec [-]timestamp. L'ordre est important.

telnet-brk-on-sync: true|false provoque l'envoi d'une rupture lors d'une opération telnet sync. Par défaut, les données sont vidées jusqu'à la marque de données, mais aucune rupture n'est envoyée.

chardelay: true|false active le petit délai après chaque caractère reçu sur le gensio de connexion avant d'envoyer des données sur le gensio accepté. Normalement, ser2net attend le temps nécessaire pour recevoir 2 caractères du port série, ou au moins 1000µs, avant d'envoyer. Cela permet une utilisation plus efficace des ressources réseau lors de la réception de grandes quantités de données, mais offre une interactivité raisonnable. Par défaut : true.

Notez que cette fonctionnalité est conçue pour équilibrer l'efficacité du réseau et l'interactivité. Elle n'est pas conçue pour garantir une taille minimale de paquet de données, car la planification des tâches et les piles réseau peuvent également modifier ces éléments.

chardelay-scale: <nombre> définit le temps, mesuré en dixièmes de caractères de port série, à attendre après la réception de quoi que ce soit de la connexion avant d'envoyer des données sur le gensio accepté. Donc, régler ceci à 25 fera attendre ser2net le temps nécessaire pour recevoir 2,5 caractères de port série après avoir reçu le dernier caractère avant d'envoyer les données sur le port TCP. La valeur par défaut est 20, le maximum est 1000. Ceci est ignoré pour les gensios non série.

chardelay-min: <nombre> est identique à chardelay-scale, mais en microsecondes. Le plus grand des deux (chardelay-scale et chardelay-min) est utilisé. La valeur par défaut est 1000, le maximum est 100000.

chardelay-max: <nombre> définit le délai maximum que ser2net attendra, en microsecondes, après la réception d'un caractère, avant d'envoyer les données. La valeur par défaut est 20000, le maximum est 1000000. Ceci permet à la connexion de fonctionner correctement à des vitesses lentes.

sendon: <chaîne sendon> Si la chaîne donnée est détectée venant du côté connexion de la connexion, envoie les données tamponnées jusqu'à et incluant la chaîne. Désactivé par défaut. Par exemple, ceci peut être configuré sur \r\n avec des paramètres chardelay appropriés pour envoyer une ligne à la fois. Elle utilise le traitement de chaîne tel que décrit dans "TRAITEMENT SPECIAL DES CHAINES" ci-dessus. Voir les notes sur la chaîne closeon pour des informations importantes sur la façon dont la comparaison est effectuée.

dev-to-net-bufsize: <nombre> définit la taille du tampon de lecture depuis le gensio de connexion et d'écriture vers le gensio accepté.

net-to-dev-bufsize: <nombre> définit la taille du tampon de lecture depuis le gensio accepté et d'écriture vers le gensio de connexion.

led-tx: <alias led> utilise le LED précédemment défini pour indiquer le trafic TX série sur ce port. Pour la version 2, il doit s'agir d'un alias YAML, comme *led2. Pour la version 2, utilisez simplement le nom, comme led2.

led-rx: <alias led> utilise le LED précédemment défini pour indiquer le trafic RX série sur ce port. Pour la version 2, il doit s'agir d'un alias YAML, comme *led2. Pour la version 2, utilisez simplement le nom, comme led2.

max-connections: <nombre> définit le nombre maximum de connexions pouvant être établies sur ce port TCP particulier. Si vous effectuez plus d'une connexion sur le même port, la sortie de chaque port va vers l'appareil, et la sortie de l'appareil va vers tous les ports simultanément. Voir "CONNEXIONS MULTIPLES" ci-dessous pour plus de détails. La valeur par défaut est 1.

remaddr: <addr>[;<addr>[;...]] spécifie les connexions distantes autorisées, où addr est une adresse standard, généralement sous la forme <adresse ip>,<port>. Plusieurs adresses peuvent être séparées par des points-virgules, et vous pouvez spécifier remaddr plus d'une fois.

Si vous définissez le port pour une adresse à zéro, ser2net acceptera une connexion depuis n'importe quel port de l'hôte réseau donné.

no-con-to-acc: true|false Si vrai, ne transfère aucune donnée du connecteur à l'accepteur. Ignore toutes les données reçues du connecteur.

no-acc-to-con: true|false Si vrai, ne transfère aucune donnée de l'accepteur au connecteur. Ignore toutes les données reçues de l'accepteur.

connback: <connecteur>[;<connecteur>[;...]] spécifie les connexions inverses qui seront établies lorsque des données arrivent sur l'appareil. Lorsque des données arrivent côté appareil (le connecteur principal de la connexion), ser2net se connectera à chaque connback spécifié. Aucune connexion n'est établie tant que des données n'arrivent pas, et les délais d'attente de connexion normaux s'appliquent.

Notez que cela utilisera une des connexions du port en permanence. Vous devrez peut-être augmenter max-connections si vous en avez besoin de plus d'une ou si vous souhaitez également accepter des connexions entrantes.

Les adresses de connexion inverse doivent correspondre au format de l'adresse de l'accepteur. Donc, par exemple, si votre accepteur est "telnet,tcp,1234", votre adresse de connexion inverse doit être quelque chose comme "telnet,tcp,hostname,1123".

Le port n'enverra aucune donnée à aucun connecteur inverse tant que tous les connecteurs inverses ne seront pas connectés.

Un port de connexion inverse peut également avoir des connexions établies si vous définissez le nombre de connexions supérieur au nombre de connecteurs inverses spécifiés. Cependant, ces connexions ne recevront aucune donnée du port tant que tous les connecteurs inverses n'auront pas été établis.

connback-timeout: <temps en secondes> spécifie un délai d'attente distinct pour les ports de connexion inverse. Normalement, il utilise le délai d'attente principal, celui-ci vous permet d'en avoir un différent. Le régler à zéro, comme le délai d'attente principal, désactive le délai d'attente.

authdir: <chaîne de répertoire> spécifie le répertoire d'authentification à utiliser pour cette connexion.

pamauth: <nom du service> active l'authentification PAM et définit le nom du service PAM.

allowed-users: <liste d'espaces des noms> Les utilisateurs autorisés à utiliser cette connexion. Cela n'a aucun sens si aul'authentification n'est pas activée sur les connexions. Si cette option n'est pas définie ou a une valeur par défaut, tous les utilisateurs sont autorisés. Si elle est définie sur un ensemble vide d'utilisateurs, alors aucun utilisateur n'est autorisé. Ceci peut être spécifié plusieurs fois, chacun ajoutant des utilisateurs supplémentaires.

mdns: true|false Active/désactive le support mdns pour la connexion. Si vous définissez cela et que mdns est disponible, ser2net créera un service sur mdns pour le port.

mdns-interface: <num> Définit l'interface réseau spécifique pour annoncer l'appareil. La valeur par défaut est -1, ce qui signifie toutes les interfaces réseau.

mdns-nettype: unspec|ipv4|ipv6 Définit le type de réseau à fournir pour l'annonce de l'appareil. La valeur par défaut est unspec, ce qui signifie ipv4 et ipv6.

mdns-name: <string> Définit le nom dans l'annonce mDNS. La valeur par défaut est le nom de la connexion.

mdns-type: <string> Définit le type dans l'annonce mDNS. La valeur par défaut est "_iostream._xxx" où xxx est soit tcp, udp # # soit sctp basé sur le type gensio.

mdns-domain: <string> Définit le nom dans l'annonce mDNS. La valeur par défaut est le réglage du système. Ne définissez pas cela sauf si vous savez vraiment ce que vous faites.

mdns-host: <string> Définit l'hôte dans l'annonce mDNS. La valeur par défaut est le réglage du système. Ne définissez pas cela sauf si vous savez vraiment ce que vous faites.

mdns-txt: <string> Ajoute une chaîne de texte à l'annonce mDNS. La chaîne doit être sous la forme "nom=valeur". Vous pouvez mettre ce que vous voulez dans les chaînes. Deux chaînes par défaut sont ajoutées par ser2net : "provider=ser2net" et "gensiostack=..." où la pile de gensios est ajoutée, comme "telnet(rfc2217),tcp)". L'idée de gensiostack est que vous pouvez simplement ajouter l'adresse à la fin et établir une connexion en utilisant str_to_gensio().

mdns-sysattrs: true|false Sous Linux, ajoute les attributs système de sysfs pour les ports série USB aux champs txt mDNS. Si le port série est USB, il ajoute "devicetype=serialusb" et les attributs suivants de sysfs : bInterfaceNumber, interface, idProduct, idVendor, serial, manufacturer, product. S'ils ne sont pas présents dans sysfs, ils ne sont pas ajoutés. Si le port série n'est pas USB, alors "devicetype=serial" est ajouté.

Note : Soyez *très* prudent lorsque vous utilisez un gensiostack avec str_to_gensio(). Appeler simplement str_to_gensio() aveuglément avec cela pourrait entraîner des problèmes de sécurité importants, car il peut y inclure des pty, stdio, trace, etc. gensios. Vous devez soit valider que la pile est un ensemble sûr, soit simplement l'utiliser pour obtenir des informations. Vous êtes prévenu. Soyez prudent.

ROTATOR

Un rotateur permet à une seule connexion réseau de se connecter à l'une parmi plusieurs connexions.

Une spécification de rotateur version 1 commence par :

rotator: &<alias>
<définition>

Une spécification de rotateur version 2 commence par :

rotators:
<alias>:
<définition>

Tout comme les connexions, dans la version 2, vous devez regrouper tous les rotateurs ensemble.

La définition d'un rotateur est presque identique entre la version 1 et la version 2 :

accepter: <accepter>
connections: [
<alias de connexion>,
<alias de connexion>....
]
options:
<nom d'option>: <valeur d'option>
<nom d'option>: <valeur d'option>...

Un rotateur a quatre options possibles, "authdir", "pamauth", "allowed-users", et "accepter-retry-time", toutes identiques aux connexions.

Pour la version 1, vous devriez utiliser des alias YAML pour les connexions. Pour la version 2, utilisez simplement les noms d'alias.

Les connexions à l'accepter passeront par l'ensemble des connexions et trouveront la première non utilisée et l'utiliseront. La connexion suivante commencera après la dernière connexion utilisée. Notez que les connexions désactivées sont toujours accessibles via les rotateurs.

Notez que la sécurité de la connexion n'est **PAS** utilisée, seule la sécurité du rotateur l'est.

VALEURS PAR DÉFAUT SER2NET

Pour définir une valeur par défaut en version 1, faites :

default:

name: <nom de la valeur par défaut>
value: <valeur par défaut>
class: <classe de la valeur par défaut>

En version 2, comme les autres choses, les valeurs par défaut sont toutes regroupées au même endroit dans un document, comme suit :

defaults:
<nom>:
value: <valeur par défaut>
class: <classe de la valeur par défaut>
<nom2>:
value: <valeur par défaut>
class: <classe de la valeur par défaut>

La classe est facultative, si elle n'est pas présente, elle définit la valeur par défaut de base pour toutes les classes qui est utilisée sauf si elle est remplacée pour une classe spécifique. Si la classe est présente, elle définit la valeur par défaut pour une classe gensio spécifique. Il existe également une classe ser2net qui concerne les options spécifiques à ser2net.

La classe est utile si vous souhaitez des valeurs différentes pour différents types de gensio. Par exemple, si vous vouliez que tous les ports série fonctionnent à 9600 bauds et que toutes les connexions IPMI SOL fonctionnent à 115200 bauds, vous pourriez faire :

default:
name: speed
value: 9600
class: serialdev
default:
name: speed
value: 115200
class: ipmisol

La valeur est également facultative, si elle n'est pas présente, une valeur chaîne est définie sur NULL et une valeur entière est définie sur 0.

L'ordre dans le fichier est important, vous devez définir une valeur par défaut avant qu'elle ne soit utilisée, et vous pouvez changer la valeur de la valeur par défaut. Elle affectera toutes les utilisations suivant la définition.

Pour supprimer une valeur par défaut pour une classe (afin qu'elle utilise la valeur par défaut de base), en version 1, faites :

delete_default:
name: <nom de la valeur par défaut>,
class: <classe de la valeur par défaut>

Pour la version 2, faites :

delete_defaults:
<nom de la valeur par défaut>: [ <classe1>, <classe2>, ... ]
<nom de la valeur par défaut2>: [ <classe1>, <classe2>, ... ]
et cela supprimera les valeurs par défaut pour les classes de la liste qui suit.

Vous devez fournir la classe, vous ne pouvez pas supprimer les valeurs par défaut de base.

Les valeurs par défaut suivantes sont spécifiques à ser2net, données avec leurs valeurs par défaut :

telnet-brk-on-sync: false
Si un telnet sync est reçu, envoyer un break sur le gensio connecté (si applicable). Par défaut, les données sont vidées jusqu'au marqueur de données, mais aucun break n'est envoyé.
kickolduser: false
Si un nouvel utilisateur arrive sur une connexion qui a déjà un utilisateur, déconnecter l'utilisateur précédent.
chardelay: true
Active une petite attente après chaque caractère reçu sur le port série avant d'envoyer des données sur le port TCP. Normalement, ser2net attend le temps nécessaire pour recevoir 2 caractères du port série, ou au moins 1000us, avant d'envoyer sur le port TCP. Cela permet une utilisation plus efficace des ressources réseau lors de la réception de grandes quantités de données, tout en offrant une interactivité raisonnable.
chardelay-scale: 20
définit le nombre de caractères du port série, en dixièmes de caractère, à attendre après réception du port série et envoi vers le port TCP. Ainsi, le réglage de cette valeur à 25 entraînera ser2net à attendre le temps nécessaire pour recevoir 2,5 caractères du port série avant d'envoyer les données vers le port TCP. Cela peut varier de 1 à 1000.
chardelay-min: 1000
définit le délai minimum d'attente de ser2net, en microsecondes. Si le calcul pour chardelay-scale résulte en une valeur inférieure à ce nombre, ce nombre sera utilisé à la place. La valeur par défaut est 1000. Cela peut varier de 1 à 100000.
net-to-dev-bufsize: 64
définit la taille du tampon de lecture depuis le port réseau et d'écriture vers le périphérique série.
dev-to-net-bufsize: 64
définit la taille du tampon de lecture depuis le périphérique série et d'écriture vers le port réseau.
max-connections: 1
définit le nombre maximum de connexions qui peuvent être établies sur ce port TCP particulier. Si vous établissez plus d'une connexion sur le même port, la sortie de chaque port va vers l'appareil, et la sortie de l'appareil va vers tous les ports simultanément. Voir "CONNEXIONS MULTIPLES" ci-dessous pour plus de détails.
remaddr: [!]<addr>[;[!]<addr>[;...]]
spécifie les connexions distantes autorisées, où addr est une adresse standard sous la forme (voir "port réseau" ci-dessus). Plusieurs adresses peuvent être séparées par des points-virgules, et vous pouvez spécifier remaddr plus d'une fois. Si vous définissez le port d'une adresse sur zéro, ser2net acceptera une connexion de n'importe quel port de l'hôte réseau donné. Si un "!" est donné au début de l'adresse, l'adresse est une adresse de "rappel". Si une adresse de rappel est spécifiée, l'une des connexions réseau (voir max-connections) est réservée à cette adresse. Si des données arrivent sur l'appareil, ser2net tentera de se connecter à l'adresse. Cela fonctionne sur TCP et UDP.
authdir: /usr/share/ser2net/auth
Le répertoire d'authentification pour ser2net. Voir AUTHENTICATION pour plus de détails.
authdir-admin: /etc/ser2net/auth
Le répertoire d'authentification pour ser2net pour les connexions d'administration. Voir "CONNEXIONS ADMINISTRATEUR" pour plus de détails.
pamauth: <NULL>
Le nom du service PAM pour l'authentification PAM de ser2net (<NULL> pour désactivé).
pamauth-admin: <NULL>
Le nom du service PAM pour l'authentification des connexions d'administration ser2net (<NULL> pour désactivé). Voir "CONNEXIONS ADMINISTRATEUR" pour plus de détails.
mdns-interface: -1
La valeur par défaut
mDNS interface.
mdns-type: <NULL>
Le type mDNS par défaut.
mdns-domain: <NULL>
Le domaine mDNS par défaut.
mdns-host: <NULL>
L'hôte mDNS par défaut.

CONNEXIONS ADMINISTRATEUR

Il existe un accepteur administrateur que vous pouvez définir pour ser2net, il vous permet de vous connecter, de consulter l'état et de modifier certaines choses. Voir « INTERFACE ADMINISTRATEUR » dans ser2net(8) pour plus de détails sur son utilisation. Le format est :

admin: [&<nom>]
accepter: <accepteur>
options:
<nom d'option>: <valeur d'option>
<nom d'option>: <valeur d'option>...

Les options d'authentification disponibles sont « authdir-admin », qui définit le répertoire d'authentification pour le port administrateur, et « pamauth-admin », qui définit le nom du service PAM et active l'authentification PAM. Ces deux options sont différentes de « authdir » resp. « pamauth » pour les connexions, bien que vous puissiez les définir à la même valeur.

De plus, les mêmes options mdns sont disponibles pour les ports administrateur que pour les connexions. Et vous pouvez définir un alias optionnel qui définira également le nom mdna.

Comme pour les connexions, les options mdns par défaut fonctionnent pour « mdns-interface », « mdna-type », « mdns-domain » et « mdns-host ». Contrairement aux connexions, le booléen « mdns » ne provient pas de la valeur par défaut, vous devez le spécifier comme une option d'administration pour activer mdns pour le port administrateur. Ceci afin de permettre sa spécification séparément et de maintenir la compatibilité ascendante.

LEDS

ser2net peut faire clignoter des LEDs lors d'une activité série. Pour créer une LED en version 1, faites :

led: &<alias>
driver: sysfs
options:
<nom d'option>: <valeur d'option>
<nom d'option>: <valeur d'option>

En version 2, utilisez :

leds:
<alias>:
driver: sysfs
options:
<nom d'option>: <valeur d'option>
<nom d'option>: <valeur d'option>
<alias>:
driver: sysfs
options:
<nom d'option>: <valeur d'option>
<nom d'option>: <valeur d'option>

Le seul pilote pris en charge est sysfs. Les options prises en charge sont :

device: <nom du périphérique sysfs> donne le nom de la LED dans /sys/class/led. Ceux-ci contiennent généralement des « : », vous devrez donc mettre le nom entre guillemets. Ceci est obligatoire.

duration: <temps en ms> Le temps en millisecondes pour faire clignoter la LED. Par défaut 10.

state: <nombre> La valeur à définir pour activer la LED. Par défaut 1, mais peut nécessiter une valeur différente.

Vous référencez la LED par son alias dans la section des options de connexion, voir celle-ci pour les détails. Assurez-vous d'avoir fait « modprobe ledtrig-transient » ou les déclencheurs ne fonctionneront pas, ils nécessitent le déclencheur transitoire.

Vous aurez également probablement besoin d'un accès root pour accéder aux paramètres des LEDs.

Les noms de fichiers, les bannières, les chaînes d'ouverture/fermeture, les chaînes de fermeture (closeon) et les chaînes d'envoi (sendon) peuvent contenir des séquences d'échappement « C » normales et un grand nombre d'autres séquences d'échappement, également :

GESTION DES GUILLEMETS ET DE LA MISE EN FORME DES CHAINES

yaml traitera les séquences d'échappement « \ » entre guillemets doubles, il n'est donc pas recommandé d'utiliser des guillemets doubles pour ce qui précède. Si vous mettez les valeurs entre guillemets simples, yaml ne les traitera pas et les transmettra à la place, où elles pourront être traitées par ser2net.

ESPACES, GUILLEMETS ET INSERTION D'ESPACES DANS LES CHAINES

YAML et le traitement des accepteurs/connecteurs interagissent lors de la gestion des guillemets. Par défaut, YAML ignore le nombre d'espaces entre les éléments séparés par des espaces. Les lignes indentées après un élément sont considérées comme une continuation de l'élément, donc quelque chose comme :

connector: serialdev,/dev/ttyUSB0,
9600n81
local nobreak
rtscts
est la même chose que
connector: serialdev,/dev/ttyUSB0, 9600n81 local nobreak rtscts

YAML a ses propres mécanismes de mise entre guillemets standard, donc si vous faites :

connector: "serialdev,/dev/ttyUSB0,9600n81 local"

les deux espaces avant « local » seront préservés lorsqu'ils seront transmis au traitement du connecteur (bien que dans ce cas cela n'ait pas d'importance car le traitement du connecteur ignorera les espaces supplémentaires).

Si vous avez besoin d'un espace significatif, par exemple dans un nom de fichier passé à une clé, vous ne pouvez pas faire :

accepter: ssl(CA=/etc/ser2net/my CA/),tcp,3000

car le traitement de l'accepteur divisera les arguments à l'espace et ne reconnaîtra pas ce qu'est « CA/ ». Vous ne pouvez pas non plus faire :

accepter: ssl(CA="/etc/ser2net/my CA/"),tcp,3000

car YAML supprimera les guillemets, ceci est fonctionnellement équivalent à l'exemple précédent. Et

accepter: ssl(CA="/etc/ser2net/my\ CA/"),tcp,3000

ne fonctionnera pas non plus, à l'intérieur des guillemets doubles YAML convertira « \ » en espace. Vous avez plusieurs options. Vous pouvez faire :

accepter: ssl(CA=/etc/ser2net/my\ CA/),tcp,3000

ou

accepter: ssl(CA='/etc/ser2net/my\ CA/'),tcp,3000

car en dehors des guillemets YAML ne traitera pas le « \ » et ne le traitera pas non plus entre guillemets simples. Ou si vous avez beaucoup d'espaces ou de deux-points, vous pouvez faire :

accepter: ssl(CA="\"/etc/ser2net/my CA/\""),tcp,3000

car à l'intérieur des guillemets extérieurs YAML convertira le '\"' en '"' et le transmettra au traitement de l'accepteur qui interprétera les guillemets comme vous vous y attendez.

UDP

La gestion de l'UDP est un peu différente de ce que vous pourriez imaginer, car il est difficile pour ser2net de savoir où envoyer les données. Pour gérer cela, les ports UDP ont toujours le concept de « connexion ». Si un port UDP n'est pas connecté, alors s'il reçoit un paquet, l'adresse distante de ce paquet est définie sur l'extrémité distante de la « connexion ». Il effectuera toutes les opérations de nouvelle connexion normales. ser2net acceptera de nouvelles connexions jusqu'à « max-connections », puis ignorera les paquets provenant d'autres adresses jusqu'à ce qu'une déconnexion se produise.

Malheureusement, il n'y a pas de moyen facile de savoir quand se déconnecter. Vous avez deux options de base :

  • Définir un délai d'attente, si l'extrémité distante n'est pas contactée avant le délai d'attente, le port est déconnecté et quelqu'un d'autre peut se connecter. Cela signifie que tout ce qui utilise le port doit envoyer périodiquement un paquet (vide c'est bien) à ser2net pour maintenir la connexion active.
  • Utilisez l'option kickolduser sur le port, toute nouvelle connexion entrante remplacera la connexion précédente.

Notez que les ports UDP gèrent plusieurs connexions tout comme les ports TCP, vous pouvez donc avoir plusieurs écouteurs UDP.

Vous avez également une troisième option. Si vous définissez une adresse distante (remaddr) avec un port non nul et un port de rappel (voir la discussion sur les adresses distantes ci-dessus), ser2net prendra l'une des connexions et l'attribuera de manière permanente à ce port. C'est ce qu'on appelle une adresse distante fixe. Tout le trafic provenant du périphérique ira vers ce port. Chaque adresse distante fixe sur un port UDP doit avoir une connexion correspondante, donc si vous avez 3 adresses distantes fixes, vous devez avoir au moins 3 connexions.

CONNEXIONS MULTIPLES

Comme mentionné précédemment, vous pouvez définir max-connections=<n> sur un port pour autoriser plus d'une connexion à la fois au même port série. Ces connexions partageront tous les paramètres. Vous ne pouvez pas avoir deux ports TCP distincts se connectant au même port en même temps.

Cela a des interactions importantes avec les autres fonctionnalités :

contrôle de flux n'est pas exactement une fonctionnalité,

mais plus une interaction entre les différentes connexions. Si un port TCP cesse de recevoir des données de ser2net, tous les ports TCP connectés seront contrôlés par flux. Cela signifie qu'une seule connexion TCP peut arrêter toutes les autres.

closeon fermera toutes les connexions lorsque la séquence closeon sera vue.

openstr n'est envoyé que lorsque le port est déconnecté et que la première connexion est établie.

closestr n'est envoyé que lorsque le dernier port se déconnecte et qu'il n'y a plus de connexions au port.

Tout moniteur ("monitor start" depuis une connexion de contrôle) capturera les entrées de toutes les connexions réseau.

kickolduser déconnectera une connexion existante si une connexion arrive sur un port qui a déjà un nombre maximal de connexions. La connexion déconnectée est choisie arbitrairement et l'algorithme est sujet à modification.

tracing tracera les données de toutes les connexions réseau.

rfc2217 (contrôle série Telnet à distance) modifiera les paramètres de connexion sur l'appareil et sera accepté depuis n'importe quelle connexion réseau.

reconfig on SIGHUP Voir ser2net(8) section "SIGHUP" pour les détails.

ROTATOR ne choisira un port que s'il n'y a aucune connexion du tout sur le port. Notez que l'utilisation d'un rotateur avec un port avec max-connections > 1 entraînera un comportement indéfini.

timeout sera par port TCP et déconnectera uniquement ce port TCP en cas de timeout.

telnet_brk_on_sync enverra une rupture pour tout port TCP qui effectue une synchronisation.

showport dans l'interface d'administration montrera toutes les connexions possibles, donc si vous dites max-connections=3 vous obtiendrez trois entrées.

showshortport dans l'interface d'administration ne montrera que la première connexion active, ou s'il n'y a pas de connexion, il montrera celle qui était présente pour la dernière fois qu'une connexion était active.

AUTHENTICATION ET ENCRYPTION

TCP WRAPPERS

ser2net utilise l'interface tcp wrappers pour implémenter la sécurité basée sur l'hôte. Voir hosts_access(5) pour une description de la configuration du fichier. Deux démons sont utilisés par ser2net, "ser2net" pour les ports de données et "ser2net-control" pour les ports de contrôle.

ENCRYPTION

ser2net prend en charge le chiffrement SSL à l'aide du gensio ssl. Pour activer le chiffrement, utilisez un accepteur comme :

telnet,ssl,tcp,1234

Ensuite, vous pouvez utiliser gensiot pour vous connecter :

gensiot telnet,ssl,<serveur>,1234

ou vous pouvez installer telnet-ssl et faire

telnet -z ssl,secure <serveur> 1234

La connexion SSL est établie à l'aide des clés fournies. Dans cet exemple, ser2net utilise les clés par défaut (telles que définies dans les valeurs par défaut, voir celles ci-dessous). Vous pouvez également les définir en utilisant (key=<fichier_cle>,cert=<fichier_cert>) après ssl ci-dessus, ou modifier les valeurs par défaut.

Si vous n'avez pas de certificats authentiques d'une autorité de certification, la connexion échouera en raison d'un échec de certificat. Obtenir des certificats de cette manière est très gênant, il y a donc une autre façon. Vous pouvez faire :

gtlssh-keygen --keydir /etc/ser2net --commonname "`hostname`-ser2net" serverkey ser2net

pour générer les clés par défaut dans /etc/ser2net (ou n'importe où). Le certificat/la clé sera nommé(e) /etc/ser2net/ser2net.crt|key.

NOTE : Si vous compilez vous-même ser2net, par défaut autoconf définit le répertoire de configuration du système (normalement /etc) comme /usr/etc. C'est une nuisance majeure avec autoconf. Donc, si vous ne le changez pas, vous auriez besoin de /usr/etc là où il est écrit /etc. Cependant, en général, la bonne façon de faire est d'ajouter "--sysconfdir=/etc" à la ligne de commande de configuration lors de la configuration de ser2net. Si une distribution a compilé ser2net pour vous, cela aurait dû être fait par défaut, donc pas de souci dans ce cas.

Ensuite, copiez ser2net.crt sur le système utilisateur et fournissez-le aux commandes de connexion, comme :

gensiot telnet,ssl(CA=ser2net.crt),<serveur>,1234

ou

telnet -z ssl,secure,cacert=ser2net.crt 1234

Vous aurez alors une connexion cryptée. Assurez-vous simplement que vos certificats sont valides.

Notez que "-ser2net" à la fin de la clé est important car il rend le nom du sujet du certificat plus unique. Vous pouvez vraiment mettre n'importe quoi pour ce que vous fournissez à keygen, tant que vous le renommez correctement. Ce sera le nom du sujet du certificat.

AUTHENTICATION AVEC SSL

ser2net offre un moyen de s'authentifier avec SSL. Ce n'est pas le meilleur, mais ça fonctionne. Vous devez activer clientauth sur ssl :

telnet,ssl(clientauth),tcp,1234

ou le définir dans la valeur par défaut. Ensuite, vous devez créer un certificat avec le nom d'utilisateur comme nom commun. Vous pouvez le faire avec :

gtlssh-keygen --keydir outdir --commonname username keygen keyname

ce qui générera keyname.crt et keyname.key dans outdir. Ensuite, placez keyname.crt dans le <authdir>/username/allowed_certs de ser2net. Par défaut, <authdir> est /usr/share/ser2net/auth, mais vous pouvez le modifier avec la valeur par défaut authdir dans le fichier de configuration de ser2net ou en définissant authdir sur des connexions individuelles (au cas où vous voudriez des valeurs différentes pour différents ports). Vous devez ensuite rehacher le répertoire allowed_certs :

gtlssh-keygen rehash <authdir>/username/allowed_certs

Ensuite, redémarrez/rechargez ser2net et utilisez l'une de ces très longues lignes pour vous y connecter en telnet :

gensiot telnet,ssl(CA=ser2net.crt,cert=username.crt,key=username.key),<serveur>,1234

telnet -z ssl,secure,cacert=ser2net.crt,cert=username.crt,key=username.key serveur 1234

AUTHENTICATION AVEC CERTAUTH (GTLSSH)

Tout ce qui précède est un gros problème. Heureusement, il existe un moyen plus simple. gtlssh est un programme de type ssh, mais il fonctionne sur TLS et implémente un protocole d'authentification de type ssh utilisant le gensio certauth.

ser2net prend en charge ce système d'authentification fonctionnant au-dessus des gensios ssl et certauth. Ces gensios fournissent le cadre pour gérer l'authentification, ser2net la contrôle lui-même.

Cela utilise le même répertoire authdir et les mêmes clés autorisées qu'auparavant, et nécessite toujours un certificat serveur, mais celui auto-signé généré avec gtlssh-keygen fonctionne bien sans rien faire de spécial. Ajoutez certauth à la ligne du port :

telnet,mux,certauth,ssl,tcp,1234

et *assurez-vous* que clientauth est désactivé pour ssl (ou ssl tentera toujours d'authentifier le client). Désactivé est la valeur par défaut, mais au cas où vous l'auriez changé, la valeur par défaut...

L'entrée mux est parce que gtlssh utilise le gensio mux pour permettre plusieurs canaux sur la même session. Il n'était pas présent avec les versions plus anciennes (avant 1.2) de gtlssh, mais est requis pour les versions plus récentes. gtlssh a également une option --nomux, juste au cas où.

Le programme gtlssh gère sa propre gestion des certificats. Consultez la page de manuel de gtlssh pour plus de détails à ce sujet. Prenez le certificat pour gtlssh et placez-le dans le répertoire authdir/username/allowed_certs et rechiffrez-le comme auparavant. gtlssh *n'utilisera pas* le nom commun fourni dans le certificat, mais utilisera plutôt un nom d'utilisateur fourni par gtlssh. Ensuite, connectez-vous avec gtlssh :

gtlssh --nosctp --telnet username@serveur 1234

Le "--nosctp" empêche gtlssh d'essayer sctp, ce qui échouera car nous avons mis tcp dans la ligne du port. Vous pourriez utiliser sctp là-bas et obtenir tous ses avantages gratuitement ! Ensuite, --nosctp ne serait plus nécessaire pour éviter les rappels.

Le nom d'utilisateur est facultatif s'il est identique à votre utilisateur actuel. Si vous ne vous êtes jamais connecté à ce serveur/port auparavant, gtlssh vous demandera de le vérifier, tout comme ssh le fait. Si les certificats, l'adresse IP, etc. changent, gtlssh vous en informera.

Si vous ne souhaitez pas utiliser de certificat (les certificats sont certainement préférables, mais peuvent ne pas toujours être réalisables), vous pouvez également utiliser une connexion par mot de passe. Vous devez définir enable-password dans les options du gensio certauth pour que les mots de passe fonctionnent. Lorsque vous vous connectez avec gtlssh, si la validation du certificat échoue, vous serez invité à saisir le mot de passe. L'authentification par mot de passe peut être effectuée de deux manières différentes. Les deux sont mutuellement exclusives, selon que pamauth est défini ou non :

  • Pour vous authentifier à l'aide de la bibliothèque PAM, définissez le nom du service PAM via l'option pamauth.
  • Placez un mot de passe dans authdir/username/password. S'il correspond à la première ligne du fichier de mots de passe et que pamauth n'est pas défini, l'authentification réussira.

AUTHENTICATION ET ROTATEURS

Les rotateurs sont un cas spécial. SOYEZ PRUDENT. Un rotateur a sa propre authentification. Si vous configurez l'authentification sur un port qui fait partie d'un rotateur, l'authentification de ce port n'est pas utilisée. Seule l'authentification du rotateur est utilisée.

ENCRYPTION, AUTHENTICATION ET CERTIFICATS PAR DÉFAUT

ser2net s'attend à trouver des certificats et des clés publiques par défaut dans /etc/ser2net, et ceux-ci sont définis comme des valeurs par défaut de gensio. Cela signifie que toute connexion sortante de ser2net, que ce soit dans un connecteur ou dans un connback, utilisera ces clés. S'ils ne sont pas là ou ont expiré, vous obtiendrez des erreurs confuses indiquant que les certificats ne peuvent pas être ouverts.

Pour résoudre ce problème, vous pouvez désactiver les certificats en ajoutant "cert=" à la spécification gensio pour ssl et certauth sur les connexions sortantes. Cela désactivera les certificats pour le gensio spécifique, et c'est probablement ce que vous voulez. Si vous établissez des connexions et vous authentifiez auprès du serveur distant, le certificat et la clé privée par défaut ne sont probablement pas ce que vous voulez non plus.

S ser2net.yaml(5)

NOM

ser2net.yaml - Fichier de configuration du proxy série vers réseau

DESCRIPTION

Le fichier de configuration ser2net est écrit en YAML. Il définit les ports série à exposer sur le réseau. Il est possible d'avoir plusieurs sections dans le fichier. Chaque section est définie par une clé unique. Les sections peuvent être imbriquées.

La section de premier niveau contient les directives générales pour ser2net.

Les sections imbriquées définissent les connexions spécifiques.

Les mots clés sont sensibles à la casse.

Les commentaires commencent par un # et vont jusqu'à la fin de la ligne.

SPÉCIFICATION DE DÉFINITION

La section de définition est utilisée pour définir des variables qui peuvent être utilisées ailleurs dans le fichier. Il y a quelques variables prédéfinies:

%S
Nom du port série
%P
Numéro du port TCP
%H
Nom d'hôte
%h
Nom d'hôte sans le domaine
%D
Nom de domaine
%R
Vitesse de transmission (baud rate)
%B
Taille du tampon
%N
Bits de données
%p
Bits de parité
%s
Bits d'arrêt
%t
Type de connexion

INCLUSION D'AUTRES FICHIERS

Il est possible d'inclure d'autres fichiers de configuration en utilisant le mot clé include. Ceci est utile pour diviser le fichier de configuration en plusieurs parties.

include: /etc/ser2net/other_config.yaml

UTILISATION DE FICHIERS EXTERNES

Il est possible de lire la configuration à partir de fichiers externes. Ceci est utile pour les connexions SSL/TLS.

key_file: /etc/ser2net/ser2net.key
cert_file: /etc/ser2net/ser2net.crt

SPÉCIFICATION DE CONNEXION

Chaque connexion est définie par un bloc indenté sous la section principale. Les clés suivantes sont disponibles:

serial
Chemin du port série (ex: /dev/ttyS0)
connection
Type de connexion (ex: telnet, raw, ssh)
port
Numéro du port TCP à écouter
incoming
Paramètres pour les connexions entrantes
pty
Si le port série doit être configuré comme un pseudo-terminal (PTY)
options
Options spécifiques au port série (vitesse, bits de données, parité, bits d'arrêt)
truncate
Drapeau pour tronquer les caractères non imprimables
log_messages
Si les messages de connexion/déconnexion doivent être enregistrés
agent
Nom de l'agent à utiliser pour la connexion
fallback
Si la connexion doit être rétablie en cas d'échec
timeout
Délai d'attente pour la connexion
rtscts
Si le contrôle de flux RTS/CTS doit être utilisé
localflow
Si le contrôle de flux logiciel doit être utilisé
outgoing
Paramètres pour les connexions sortantes

ROTATOR

La section rotator est utilisée pour configurer un rotateur de port série. Elle prend les paramètres suivants:

ports
Liste des ports série à utiliser
port
Numéro du port TCP à écouter
delay
Délai entre les changements de port
default
Port série par défaut à utiliser

VALEURS PAR DÉFAUT DE SER2NET

La section ser2net_defaults est utilisée pour définir les valeurs par défaut pour toutes les connexions. Les clés suivantes sont disponibles:

connection
Type de connexion par défaut
options
Options série par défaut
incoming
Paramètres entrants par défaut
outgoing
Paramètres sortants par défaut
agent
Nom de l'agent par défaut
log_messages
Si les messages doivent être enregistrés par défaut

CONNEXIONS ADMINISTRATEUR

La section admin_connections est utilisée pour définir les connexions d'administration. Ces connexions ne sont pas destinées à un usage normal, mais plutôt à la gestion et au débogage de ser2net.

port
Numéro du port TCP à écouter
user
Nom d'utilisateur pour l'authentification
password
Mot de passe pour l'authentification

DÉLIMITATIONS ET MISE EN PLACE DES CHAÎNES

Les chaînes de caractères qui contiennent des espaces doivent être placées entre guillemets doubles ("). Les guillemets simples (') ne sont pas pris en charge.

banner: "Bienvenue sur le serveur ser2net"

ESPACES, GUILLEMETS ET MISE EN PLACE DES ESPACES DANS LES CHAÎNES

Les espaces dans les chaînes de caractères sont autorisés. Si vous avez besoin d'inclure des guillemets dans une chaîne, vous pouvez les échapper avec une barre oblique inverse (\).

banner: "Ceci est une chaîne avec des \"guillemets\"."

UDP

Il est possible de configurer ser2net pour utiliser UDP au lieu de TCP. Pour ce faire, utilisez le type de connexion udp.

udp_port: 12345

CONNEXIONS MULTIPLES

Il est possible de configurer plusieurs connexions pour le même port série. Dans ce cas, ser2net distribuera les connexions entre les ports série disponibles.

AUTHENTIFICATION ET CHIFFREMENT

ser2net prend en charge l'authentification et le chiffrement via SSL/TLS. Pour ce faire, vous devez spécifier les fichiers de clé et de certificat dans le fichier de configuration.

ssl:
  enabled: true
  key_file: /etc/ser2net/ser2net.key
  cert_file: /etc/ser2net/ser2net.crt

SIGNALS

SIGHUP
Si ser2net reçoit un SIGHUP, il relira son fichier de configuration et apportera les modifications appropriées. Si un port utilisé est modifié ou supprimé, la modification réelle n'interviendra qu'une fois le port déconnecté.

ERREURS

Presque toutes les sorties d'erreur vont à syslog, pas à la sortie standard.
