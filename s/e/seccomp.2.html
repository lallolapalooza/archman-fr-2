seccomp(2) Manuel des appels système seccomp(2)

NOM

seccomp - opérer sur l'état de Secure Computing du processus

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <linux/seccomp.h>  /* Définition des constantes SECCOMP_* */
#include <linux/filter.h>   /* Définition de struct sock_fprog */
#include <linux/audit.h>    /* Définition des constantes AUDIT_* */
#include <linux/signal.h>   /* Définition des constantes SIG* */
#include <sys/ptrace.h>     /* Définition des constantes PTRACE_* */
#include <sys/syscall.h>    /* Définition des constantes SYS_* */
#include <unistd.h>
int syscall(SYS_seccomp, unsigned int operation, unsigned int flags,
            void *args);

Note : glibc ne fournit pas d'interface pour seccomp(), nécessitant l'utilisation de syscall(2).

DESCRIPTION

L'appel système seccomp() opère sur l'état de Secure Computing (seccomp) du processus appelant.

Actuellement, Linux supporte les valeurs d'operation suivantes :

SECCOMP_SET_MODE_STRICT
Les seuls appels système que le thread appelant est autorisé à effectuer sont read(2), write(2), _exit(2) (mais pas exit_group(2)), et sigreturn(2). Les autres appels système entraînent la terminaison du thread appelant, ou la terminaison de l'ensemble du processus avec le signal SIGKILL lorsqu'il n'y a qu'un seul thread. Le mode de calcul sécurisé strict est utile pour les applications de calcul intensif qui peuvent avoir besoin d'exécuter du code binaire non approuvé, peut-être obtenu en lisant depuis un pipe ou une socket.
Notez que bien que le thread appelant ne puisse plus appeler sigprocmask(2), il peut utiliser sigreturn(2) pour bloquer tous les signaux à part SIGKILL et SIGSTOP. Cela signifie que alarm(2) (par exemple) n'est pas suffisant pour restreindre le temps d'exécution du processus. Au lieu de cela, pour terminer le processus de manière fiable, SIGKILL doit être utilisé. Cela peut être fait en utilisant timer_create(2) avec SIGEV_SIGNAL et sigev_signo défini à SIGKILL, ou en utilisant setrlimit(2) pour définir la limite dure pour RLIMIT_CPU.
Cette opération n'est disponible que si le noyau est configuré avec CONFIG_SECCOMP activé.
La valeur de flags doit être 0, et args doit être NULL.
Cette opération est fonctionnellement identique à l'appel :

prctl(PR_SET_SECCOMP, SECCOMP_MODE_STRICT);

SECCOMP_SET_MODE_FILTER
Les appels système autorisés sont définis par un pointeur vers un filtre de paquets Berkeley (BPF) passé via args. Cet argument est un pointeur vers une structure struct sock_fprog ; il peut être conçu pour filtrer des appels système et des arguments d'appels système arbitraires. Si le filtre est invalide, seccomp() échoue, retournant EINVAL dans errno.
Si fork(2) ou clone(2) est autorisé par le filtre, tout processus enfant sera soumis aux mêmes filtres d'appels système que le parent. Si execve(2) est autorisé, les filtres existants seront préservés lors d'un appel à execve(2).
Pour utiliser l'opération SECCOMP_SET_MODE_FILTER, le thread appelant doit posséder la capacité CAP_SYS_ADMIN dans son espace utilisateur, ou le thread doit déjà avoir le bit no_new_privs défini. Si ce bit n'a pas déjà été défini par un ancêtre de ce thread, le thread doit effectuer l'appel suivant :

prctl(PR_SET_NO_NEW_PRIVS, 1);

Sinon, l'opération SECCOMP_SET_MODE_FILTER échoue et retourne EACCES dans errno. Cette exigence garantit qu'un processus non privilégié ne peut pas appliquer un filtre malveillant puis invoquer un programme set-user-ID ou un autre programme privilégié via execve(2), compromettant ainsi potentiellement ce programme. (Un tel filtre malveillant pourrait, par exemple, faire en sorte qu'une tentative d'utilisation de setuid(2) pour définir les identifiants utilisateur de l'appelant à des valeurs non nulles retourne plutôt 0 sans effectuer réellement l'appel système. Ainsi, le programme pourrait être amené à croire qu'il conserve des privilèges super-utilisateur dans des circonstances où il est possible de l'influencer pour faire des choses dangereuses car il n'a pas réellement abandonné ses privilèges.)
Si prctl(2) ou seccomp() est autorisé par le filtre attaché, de nouveaux filtres peuvent être ajoutés. Cela augmentera le temps d'évaluation, mais permettra une réduction supplémentaire de la surface d'attaque pendant l'exécution d'un thread.
L'opération SECCOMP_SET_MODE_FILTER n'est disponible que si le noyau est configuré avec CONFIG_SECCOMP_FILTER activé.
Lorsque flags est 0, cette opération est fonctionnellement identique à l'appel :

prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, args);

Les flags reconnus sont :
SECCOMP_FILTER_FLAG_LOG (depuis Linux 4.14)
Toutes les actions de retour de filtre, sauf SECCOMP_RET_ALLOW, doivent être enregistrées. Un administrateur peut outrepasser ce drapeau de filtre en empêchant certaines actions d'être enregistrées via le fichier /proc/sys/kernel/seccomp/actions_logged.
SECCOMP_FILTER_FLAG_NEW_LISTENER (depuis Linux 5.0)
Après avoir installé avec succès le programme de filtre, retournez un nouveau descripteur de fichier de notification user-space. (Le drapeau close-on-exec est défini pour le descripteur de fichier.) Lorsque le filtre retourne SECCOMP_RET_USER_NOTIF, une notification sera envoyée à ce descripteur de fichier.
Au plus un filtre seccomp utilisant le drapeau SECCOMP_FILTER_FLAG_NEW_LISTENER peut être installé pour un thread.
Voir seccomp_unotify(2) pour plus de détails.
SECCOMP_FILTER_FLAG_SPEC_ALLOW (depuis Linux 4.17)
Désactive la mitigation Speculative Store Bypass.
SECCOMP_FILTER_FLAG_TSYNC
Lors de l'ajout d'un nouveau filtre, synchronise tous les autres threads du processus appelant avec le même arbre de filtres seccomp. Un "arbre de filtres" est la liste ordonnée des filtres attachés à un thread. (Attacher des filtres identiques dans des appels seccomp() séparés résulte en des filtres différents de ce point de vue.)
Si un thread ne peut pas se synchroniser au même arbre de filtres, l'appel n'attachera pas le nouveau filtre seccomp et échouera, retournant le premier ID de thread trouvé qui ne peut pas se synchroniser. La synchronisation échouera si un autre thread du même processus est en SECCOMP_MODE_STRICT ou s'il a attaché de nouveaux filtres seccomp à lui-même, divergent de l'arbre de filtres du thread appelant.
SECCOMP_GET_ACTION_AVAIL (depuis Linux 4.14)
Teste si une action est supportée par le noyau. Cette opération est utile pour confirmer que le noyau connaît une action de retour de filtre ajoutée plus récemment, car le noyau traite toutes les actions inconnues comme SECCOMP_RET_KILL_PROCESS.
La valeur de flags doit être 0, et args doit être un pointeur vers une action de retour de filtre non signée sur 32 bits.

SECCOMP_GET_NOTIF_SIZES (depuis Linux 5.0)
Obtenir les tailles des structures de notification seccomp pour l'espace utilisateur. Comme ces structures peuvent évoluer et s'agrandir avec le temps, cette commande peut être utilisée pour déterminer la quantité de mémoire à allouer pour l'envoi et la réception des notifications.
La valeur de flags doit être 0, et args doit être un pointeur vers une struct seccomp_notif_sizes, qui a la forme suivante :
struct seccomp_notif_sizes

    __u16 seccomp_notif_resp; /* Taille de la structure de réponse */
    __u16 seccomp_data;       /* Taille de 'struct seccomp_data' */
};
Voir seccomp_unotify(2) pour plus de détails.

Filtres

Lors de l'ajout de filtres via SECCOMP_SET_MODE_FILTER, args pointe vers un programme de filtre :


struct sock_fprog {
    unsigned short      len;    /* Nombre d'instructions BPF */
    struct sock_filter *filter; /* Pointeur vers un tableau d'instructions
                                   BPF */
};

Chaque programme doit contenir une ou plusieurs instructions BPF :


struct sock_filter {            /* Bloc de filtre */
    __u16 code;                 /* Code de filtre réel */
    __u8  jt;                   /* Saut si vrai */
    __u8  jf;                   /* Saut si faux */
    __u32 k;                    /* Champ générique multi-usage */
};

Lors de l'exécution des instructions, le programme BPF opère sur les informations d'appel système mises à disposition (c'est-à-dire, en utilisant le mode d'adressage BPF_ABS) sous la forme d'un tampon (en lecture seule) de la forme suivante :


struct seccomp_data {
    int   nr;                   /* Numéro d'appel système */
    __u32 arch;                 /* Valeur AUDIT_ARCH_*
                                   (voir <linux/audit.h>) */
    __u64 instruction_pointer;  /* Pointeur d'instruction CPU */
    __u64 args[6];              /* Jusqu'à 6 arguments d'appel système */
};

Étant donné que la numérotation des appels système varie entre les architectures et que certaines architectures (par exemple, x86-64) permettent au code en espace utilisateur d'utiliser les conventions d'appel de plusieurs architectures (et que la convention utilisée peut varier au cours de la vie d'un processus qui utilise execve(2) pour exécuter des binaires utilisant différentes conventions), il est généralement nécessaire de vérifier la valeur du champ arch.

Il est fortement recommandé d'utiliser une approche de liste blanche chaque fois que possible, car cette approche est plus robuste et plus simple. Une liste noire devra être mise à jour chaque fois qu'un appel système potentiellement dangereux est ajouté (ou qu'un drapeau ou une option dangereuse est ajoutée à la liste noire), et il est souvent possible de modifier la représentation d'une valeur sans en modifier la signification, ce qui conduit à un contournement de la liste noire. Voir également Caveats ci-dessous.

Le champ arch n'est pas unique pour toutes les conventions d'appel. L'ABI x86-64 et l'ABI x32 utilisent tous deux AUDIT_ARCH_X86_64 comme arch, et ils s'exécutent sur les mêmes processeurs. Au lieu de cela, le masque __X32_SYSCALL_BIT est utilisé sur le numéro d'appel système pour distinguer les deux ABI.

Cela signifie qu'une politique doit soit refuser tous les appels système avec __X32_SYSCALL_BIT, soit reconnaître les appels système avec et sans __X32_SYSCALL_BIT défini. Une liste d'appels système à refuser basée sur nr qui ne contient pas également des valeurs nr avec __X32_SYSCALL_BIT défini peut être contournée par un programme malveillant qui définit __X32_SYSCALL_BIT.

De plus, les noyaux antérieurs à Linux 5.4 permettaient incorrectement nr dans les plages 512-547 ainsi que les appels système non-x32 correspondants combinés avec __X32_SYSCALL_BIT. Par exemple, nr == 521 et nr == (101 | __X32_SYSCALL_BIT) entraînaient des invocations de ptrace(2) avec des sémantiques potentiellement confuses x32 vs x86_64 dans le noyau. Les politiques destinées à fonctionner sur les noyaux avant Linux 5.4 doivent s'assurer qu'elles refusent ou gèrent correctement ces appels système. Sur Linux 5.4 et versions ultérieures, ces appels système échoueront avec l'erreur ENOSYS, sans rien faire.

Le champ instruction_pointer fournit l'adresse de l'instruction en langage machine qui a effectué l'appel système. Cela peut être utile en conjonction avec l'utilisation de /proc/pid/maps pour effectuer des vérifications basées sur la région (mapping) du programme qui a effectué l'appel système. (Il est probablement sage de verrouiller les appels système mmap(2) et mprotect(2) pour empêcher le programme de contourner de telles vérifications.)

Lors de la vérification des valeurs de args, gardez à l'esprit que les arguments sont souvent tronqués silencieusement avant d'être traités, mais après la vérification seccomp. Par exemple, cela se produit si l'ABI i386 est utilisée sur un noyau x86-64 : bien que le noyau ne regarde normalement pas au-delà des 32 bits les moins significatifs des arguments, les valeurs des registres complets de 64 bits seront présentes dans les données seccomp. Un exemple moins surprenant est que si l'ABI x86-64 est utilisée pour effectuer un appel système qui prend un argument de type int, la moitié la plus significative du registre d'argument est ignorée par l'appel système, mais visible dans les données seccomp.

Un filtre seccomp renvoie une valeur de 32 bits composée de deux parties : les 16 bits les plus significatifs (correspondant au masque défini par la constante SECCOMP_RET_ACTION_FULL) contiennent l'une des valeurs d'"action" listées ci-dessous ; les 16 bits les moins significatifs (définis par la constante SECCOMP_RET_DATA) sont des "données" à associer à cette valeur de retour.

Si plusieurs filtres existent, ils sont tous exécutés, dans l'ordre inverse de leur ajout à l'arbre de filtres — c'est-à-dire, le filtre installé le plus récemment est exécuté en premier. (Notez que tous les filtres seront appelés même si l'un des filtres précédents renvoie SECCOMP_RET_KILL. Ceci est fait pour simplifier le code du noyau et pour fournir une légère accélération dans l'exécution d'ensembles de filtres en évitant une vérification de ce cas peu fréquent.) La valeur de retour pour l'évaluation d'un appel système donné est la première valeur d'action rencontrée de la plus haute priorité (avec ses données associées) renvoyée par l'exécution de tous les filtres.

Par ordre décroissant de priorité, les valeurs d'action qui peuvent être renvoyées par un filtre seccomp sont :

SECCOMP_RET_KILL_PROCESS (depuis Linux 4.14)
Cette valeur entraîne la terminaison immédiate du processus, avec un vidage mémoire (core dump). L'appel système n'est pas exécuté. Contrairement à SECCOMP_RET_KILL_THREAD ci-dessous, tous les threads du groupe de threads sont terminés. (Pour une discussion sur les groupes de threads, voir la description de l'indicateur CLONE_THREAD dans clone(2).)
Le processus se termine comme s'il était tué par un signal SIGSYS. Même si un gestionnaire de signal a été enregistré pour SIGSYS, le gestionnaire sera ignoré dans ce cas et le processus se terminera toujours. Pour un processus parent qui attend sur ce processus (en utilisant waitpid(2) ou similaire), le wstatus renvoyé indiquera que son enfant a été terminé comme s'il était tué par un signal SIGSYS.
SECCOMP_RET_KILL_THREAD (ou SECCOMP_RET_KILL)
Cette valeur entraîne la terminaison immédiate du thread qui a effectué l'appel système. L'appel système n'est pas exécuté. Les autres threads du même groupe de threads continueront de s'exécuter.
Le thread se termine comme s'il était tué par un signal SIGSYS. Voir SECCOMP_RET_KILL_PROCESS ci-dessus.
Avant Linux 4.11, tout processus terminé de cette manière ne déclenchait pas de vidage mémoire (même si SIGSYS est documenté dans signal(7) comme ayant une action par défaut de terminaison avec vidage mémoire). Depuis Linux 4.11, un processus mono-thread effectuera un vidage mémoire s'il est terminé de cette manière.
Avec l'ajout de SECCOMP_RET_KILL_PROCESS dans Linux 4.14, SECCOMP_RET_KILL_THREAD a été ajouté comme synonyme de SECCOMP_RET_KILL, afin de mieux distinguer les deux actions.
Note : l'utilisation de SECCOMP_RET_KILL_THREAD pour tuer un seul thread dans un processus multi-threadé est susceptible de laisser le processus dans un état irréversiblement incohérent et potentiellement corrompu.
SECCOMP_RET_TRAP
Cette valeur entraîne l'envoi par le noyau d'un signal SIGSYS dirigé vers le thread au thread déclencheur. (L'appel système n'est pas exécuté.) Divers champs seront définis dans la structure siginfo_t (voir sigaction(2)) associée au signal :
•
si_signo contiendra SIGSYS.
•
si_call_addr montrera l'adresse de l'instruction d'appel système.
•
si_syscall et si_arch indiqueront quel appel système a été tenté.
•
si_code contiendra SYS_SECCOMP.
•
si_errno contiendra la partie SECCOMP_RET_DATA de la valeur de retour du filtre.
Le compteur ordinal (program counter) sera comme si l'appel système avait eu lieu (c'est-à-dire que le compteur ordinal ne pointera pas vers l'instruction d'appel système). Le registre de valeur de retour contiendra une valeur dépendant de l'architecture ; si l'exécution reprend, définissez-le sur quelque chose d'approprié pour l'appel système. (La dépendance à l'architecture est due au fait que le remplacer par ENOSYS pourrait écraser des informations utiles.)
SECCOMP_RET_ERRNO
Cette valeur entraîne la transmission de la partie SECCOMP_RET_DATA de la valeur de retour du filtre à l'espace utilisateur en tant que valeur errno sans exécuter l'appel système.
SECCOMP_RET_USER_NOTIF (depuis Linux 5.0)
Transférer l'appel système à un processus superviseur attaché en espace utilisateur pour permettre à ce processus de décider quoi faire de l'appel système. S'il n'y a pas de superviseur attaché (soit parce que le filtre n'a pas été installé avec le drapeau SECCOMP_FILTER_FLAG_NEW_LISTENER, soit parce que le descripteur de fichier a été fermé), le filtre renvoie ENOSYS (similaire à ce qui se passe lorsqu'un filtre renvoie SECCOM
P_RET_TRACE et il n'y a pas de traceur). Voir seccomp_unotify(2) pour plus de détails.
Notez que le processus superviseur ne sera pas notifié si un autre filtre renvoie une valeur d'action avec une priorité supérieure à SECCOMP_RET_USER_NOTIF.
SECCOMP_RET_TRACE
Lorsqu'elle est retournée, cette valeur fera en sorte que le noyau tente de notifier un traceur basé sur ptrace(2) avant d'exécuter l'appel système. S'il n'y a pas de traceur présent, l'appel système n'est pas exécuté et retourne un statut d'échec avec errno défini à ENOSYS.
Un traceur sera notifié s'il demande PTRACE_O_TRACESECCOMP en utilisant ptrace(PTRACE_SETOPTIONS). Le traceur sera notifié d'un PTRACE_EVENT_SECCOMP et la partie SECCOMP_RET_DATA de la valeur de retour du filtre sera disponible pour le traceur via PTRACE_GETEVENTMSG.
Le traceur peut sauter l'appel système en changeant le numéro d'appel système à -1. Alternativement, le traceur peut changer l'appel système demandé en changeant l'appel système en un numéro d'appel système valide. Si le traceur demande à sauter l'appel système, alors l'appel système semblera retourner la valeur que le traceur place dans le registre de retour.
Avant Linux 4.8, la vérification seccomp ne sera pas exécutée à nouveau après la notification du traceur. (Cela signifie que, sur les anciens noyaux, les sandboxes seccomp ne doivent pas autoriser l'utilisation de ptrace(2) - même d'autres processus sandboxed - sans extrême prudence ; les traceurs peuvent utiliser ce mécanisme pour s'échapper de la sandbox seccomp.)
Notez qu'un processus traceur ne sera pas notifié si un autre filtre retourne une valeur d'action avec une priorité supérieure à SECCOMP_RET_TRACE.
SECCOMP_RET_LOG (depuis Linux 4.14)
Cette valeur entraîne l'exécution de l'appel système après que l'action de retour du filtre soit enregistrée. Un administrateur peut outrepasser l'enregistrement de cette action via le fichier /proc/sys/kernel/seccomp/actions_logged.
SECCOMP_RET_ALLOW
Cette valeur entraîne l'exécution de l'appel système.

Si une valeur d'action autre que l'une des ci-dessus est spécifiée, alors l'action du filtre est traitée comme soit SECCOMP_RET_KILL_PROCESS (depuis Linux 4.14) soit SECCOMP_RET_KILL_THREAD (dans Linux 4.13 et antérieur).

Interfaces /proc

Les fichiers du répertoire /proc/sys/kernel/seccomp fournissent des informations et une configuration seccomp supplémentaires :

actions_avail (depuis Linux 4.14)
Une liste ordonnée en lecture seule des actions de retour des filtres seccomp sous forme de chaîne de caractères. L'ordre, de gauche à droite, est en ordre décroissant de priorité. La liste représente l'ensemble des actions de retour des filtres seccomp supportées par le noyau.
actions_logged (depuis Linux 4.14)
Une liste ordonnée en lecture-écriture des actions de retour des filtres seccomp qui sont autorisées à être enregistrées. Les écritures dans le fichier n'ont pas besoin d'être sous forme ordonnée, mais les lectures du fichier seront ordonnées de la même manière que le fichier actions_avail.
Il est important de noter que la valeur de actions_logged n'empêche pas que certaines actions de retour de filtre soient enregistrées lorsque le sous-système d'audit est configuré pour auditer une tâche. Si l'action n'est pas trouvée dans le fichier actions_logged, la décision finale quant à savoir si l'action doit être auditée pour cette tâche est finalement laissée à la décision du sous-système d'audit pour toutes les actions de retour de filtre autres que SECCOMP_RET_ALLOW.
La chaîne "allow" n'est pas acceptée dans le fichier actions_logged car il n'est pas possible d'enregistrer les actions SECCOMP_RET_ALLOW. Tenter d'écrire "allow" dans le fichier échouera avec l'erreur EINVAL.

Enregistrement d'audit des actions seccomp

Depuis Linux 4.14, le noyau fournit la facilité d'enregistrer les actions retournées par les filtres seccomp dans le journal d'audit. Le noyau prend la décision d'enregistrer une action en fonction du type d'action, si l'action est présente ou non dans le fichier actions_logged, et si l'audit du noyau est activé (par exemple, via l'option de démarrage du noyau audit=1). Les règles sont les suivantes :

•
Si l'action est SECCOMP_RET_ALLOW, l'action n'est pas enregistrée.
•
Sinon, si l'action est soit SECCOMP_RET_KILL_PROCESS soit SECCOMP_RET_KILL_THREAD, et que cette action apparaît dans le fichier actions_logged, l'action est enregistrée.
•
Sinon, si le filtre a demandé l'enregistrement (le drapeau SECCOMP_FILTER_FLAG_LOG) et que l'action apparaît dans le fichier actions_logged, l'action est enregistrée.
•
Sinon, si l'audit du noyau est activé et que le processus est audité (autrace(8)), l'action est enregistrée.
•
Sinon, l'action n'est pas enregistrée.

VALEUR DE RETOUR

En cas de succès, seccomp() retourne 0. En cas d'erreur, si SECCOMP_FILTER_FLAG_TSYNC a été utilisé, la valeur de retour est l'ID du thread qui a causé l'échec de synchronisation. (Cet ID est un ID de thread du noyau du type retourné par clone(2) et gettid(2).) En cas d'autres erreurs, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

seccomp() peut échouer pour les raisons suivantes :

EACCES
L'appelant ne possédait pas la capacité CAP_SYS_ADMIN dans son espace de noms utilisateur, ou n'avait pas défini no_new_privs avant d'utiliser SECCOMP_SET_MODE_FILTER.
EBUSY
Lors de l'installation d'un nouveau filtre, le drapeau SECCOMP_FILTER_FLAG_NEW_LISTENER était spécifié, mais un filtre précédent avait déjà été installé avec ce drapeau.
EFAULT
args n'était pas une adresse valide.
EINVAL
operation est inconnue ou n'est pas supportée par cette version ou configuration du noyau.
EINVAL
Les flags spécifiés sont invalides pour l' operation donnée.
EINVAL
operation incluait BPF_ABS, mais le décalage spécifié n'était pas aligné sur une frontière de 32 bits ou dépassait sizeof(struct seccomp_data).
EINVAL
Un mode de calcul sécurisé a déjà été défini, et l' operation diffère du réglage existant.
EINVAL
operation a spécifié SECCOMP_SET_MODE_FILTER, mais le programme de filtre pointé par args n'était pas valide ou la longueur du programme de filtre était zéro ou dépassait BPF_MAXINSNS (4096) instructions.
ENOMEM
Mémoire insuffisante.
ENOMEM
La longueur totale de tous les programmes de filtre attachés au thread appelant dépasserait MAX_INSNS_PER_PATH (32768) instructions. Notez que pour le calcul de cette limite, chaque programme de filtre déjà existant entraîne une pénalité de surcoût de 4 instructions.
EOPNOTSUPP
operation a spécifié SECCOMP_GET_ACTION_AVAIL, mais le noyau ne supporte pas l'action de retour de filtre spécifiée par args.
ESRCH
Un autre thread a causé une défaillance lors de la synchronisation des threads, mais son ID n'a pas pu être déterminé.

NORMES

Linux.

HISTORIQUE

NOTES

Plutôt que d'écrire manuellement des filtres seccomp comme montré dans l'exemple ci-dessous, vous pourriez préférer utiliser la bibliothèque libseccomp, qui fournit une interface pour générer des filtres seccomp.

Le champ Seccomp du fichier /proc/pid/status fournit une méthode pour visualiser le mode seccomp d'un processus ; voir proc(5).

seccomp() fournit un sur-ensemble des fonctionnalités fournies par l'opération PR_SET_SECCOMP de prctl(2) (qui ne supporte pas les flags).

Depuis Linux 4.4, l'opération PTRACE_SECCOMP_GET_FILTER de ptrace(2) peut être utilisée pour exporter les filtres seccomp d'un processus.

Support architectural pour les filtres BPF seccomp

Le support architectural pour le filtrage BPF seccomp est disponible sur les architectures suivantes :

•
x86-64, i386, x32 (depuis Linux 3.5)
•
ARM (depuis Linux 3.8)
•
s390 (depuis Linux 3.8)
•
MIPS (depuis Linux 3.16)
•
ARM-64 (depuis Linux 3.19)
•
PowerPC (depuis Linux 4.3)
•
Tile (depuis Linux 4.3)
•
PA-RISC (depuis Linux 4.6)

Mises en garde

Il y a diverses subtilités à considérer lors de l'application de filtres seccomp à un programme, y compris les suivantes :

•
Certains appels système traditionnels ont des espaces utilisateur
e implémentations dans le vdso(7) sur de nombreuses architectures. Des exemples notables incluent clock_gettime(2), gettimeofday(2), et time(2). Sur de telles architectures, le filtrage seccomp pour ces appels système n'aura aucun effet. (Cependant, il existe des cas où les implémentations vdso(7) peuvent se rabattre sur l'invocation de l'appel système réel, auquel cas les filtres seccomp verraient l'appel système.)
•
Le filtrage Seccomp est basé sur les numéros d'appels système. Cependant, les applications n'invoquent généralement pas directement les appels système, mais appellent plutôt des fonctions enveloppes dans la bibliothèque C qui, à leur tour, invoquent les appels système. Par conséquent, il faut être conscient des points suivants :
•
Les enveloppes glibc pour certains appels système traditionnels peuvent réellement employer des appels système avec des noms différents dans le noyau. Par exemple, l'enveloppe de la fonction exit(2) emploie en fait l'appel système exit_group(2) , et l'enveloppe de la fonction fork(2) appelle en fait clone(2).
•
Le comportement des fonctions enveloppes peut varier selon les architectures, en fonction de la gamme d'appels système fournis sur ces architectures. En d'autres termes, la même fonction enveloppe peut invoquer différents appels système sur différentes architectures.
•
Enfin, le comportement des fonctions enveloppes peut changer entre les versions de glibc. Par exemple, dans les versions plus anciennes, la fonction enveloppe glibc pour open(2) invoquait l'appel système du même nom, mais à partir de glibc 2.26, l'implémentation a basculé vers l'appel de openat(2) sur toutes les architectures.

La conséquence des points ci-dessus est qu'il peut être nécessaire de filtrer un appel système autre que celui attendu. Diverses pages de manuel de la section 2 fournissent des détails utiles sur les différences entre les fonctions enveloppes et les appels système sous-jacents dans les sous-sections intitulées Différences entre la bibliothèque C et le noyau.

De plus, notez que l'application de filtres seccomp risque même de causer des bugs dans une application, lorsque les filtres provoquent des échecs inattendus pour des opérations légitimes que l'application pourrait avoir besoin d'effectuer. De tels bugs peuvent ne pas être facilement découverts lors des tests des filtres seccomp si les bugs se produisent dans des chemins de code d'application rarement utilisés.

Détails BPF spécifiques à Seccomp

Notez les détails BPF suivants spécifiques aux filtres seccomp :

•
Les modificateurs de taille BPF_H et BPF_B ne sont pas pris en charge : toutes les opérations doivent charger et stocker des mots (de 4 octets) (BPF_W).
•
Pour accéder au contenu du tampon seccomp_data, utilisez le modificateur de mode d'adressage BPF_ABS.
•
Le modificateur de mode d'adressage BPF_LEN donne un opérande en mode immédiat dont la valeur est la taille du tampon seccomp_data.

EXEMPLES

Le programme ci-dessous accepte quatre arguments ou plus. Les trois premiers arguments sont un numéro d'appel système, un identifiant d'architecture numérique et un numéro d'erreur. Le programme utilise ces valeurs pour construire un filtre BPF qui est utilisé à l'exécution pour effectuer les vérifications suivantes :

•
Si le programme ne s'exécute pas sur l'architecture spécifiée, le filtre BPF fait échouer les appels système avec l'erreur ENOSYS.
•
Si le programme tente d'exécuter l'appel système avec le numéro spécifié, le filtre BPF fait échouer l'appel système, avec errno défini au numéro d'erreur spécifié.

Les arguments restants de la ligne de commande spécifient le chemin du fichier et les arguments supplémentaires d'un programme que le programme d'exemple doit tenter d'exécuter à l'aide de execv(3) (une fonction de bibliothèque qui utilise l'appel système execve(2)). Certains exemples d'exécution du programme sont présentés ci-dessous.

Tout d'abord, nous affichons l'architecture sur laquelle nous nous exécutons (x86-64) puis nous construisons une fonction shell qui recherche les numéros d'appels système sur cette architecture :


$ uname -m;
x86_64
$ syscall_nr() {
    cat /usr/src/linux/arch/x86/syscalls/syscall_64.tbl | \
    awk '$2 != "x32" && $3 == "'$1'" { print $1 }'
};

Lorsque le filtre BPF rejette un appel système (cas [2] ci-dessus), il fait échouer l'appel système avec le numéro d'erreur spécifié sur la ligne de commande. Dans les expériences présentées ici, nous utiliserons le numéro d'erreur 99 :


$ errno 99;
EADDRNOTAVAIL 99 Cannot assign requested address

Dans l'exemple suivant, nous tentons d'exécuter la commande whoami(1), mais le filtre BPF rejette l'appel système execve(2), de sorte que la commande n'est même pas exécutée :


$ syscall_nr execve;
59
$ ./a.out;
Usage: ./a.out <syscall_nr> <arch> <errno> <prog> [<args>]
Hint for <arch>: AUDIT_ARCH_I386: 0x40000003
                 AUDIT_ARCH_X86_64: 0xC000003E
$ ./a.out 59 0xC000003E 99 /bin/whoami;
execv: Cannot assign requested address

Dans l'exemple suivant, le filtre BPF rejette l'appel système write(2) , de sorte que, bien qu'il soit démarré avec succès, la commande whoami(1) n'est pas en mesure d'écrire de sortie :


$ syscall_nr write;
1
$ ./a.out 1 0xC000003E 99 /bin/whoami;

Dans le dernier exemple, le filtre BPF rejette un appel système qui n'est pas utilisé par la commande whoami(1), elle peut donc s'exécuter avec succès et produire une sortie :


$ syscall_nr preadv;
295
$ ./a.out 295 0xC000003E 99 /bin/whoami;
cecilia

Source du programme

#include <linux/audit.h>
#include <linux/filter.h>
#include <linux/seccomp.h>
#include <stddef.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/prctl.h>
#include <sys/syscall.h>
#include <unistd.h>
#define X32_SYSCALL_BIT 0x40000000
#define NITEMS(arr)  (sizeof(arr) / sizeof((arr)[0]))
static int
install_filter(int syscall_nr, unsigned int t_arch, int f_errno)
{
    unsigned int upper_nr_limit = 0xffffffff;
    /* Suppose AUDIT_ARCH_X86_64 signifie l'ABI x86-64 normal
       (dans l'ABI x32, tous les appels système ont le bit 30 défini dans le
       champ 'nr', ce qui signifie que les numéros sont >= X32_SYSCALL_BIT).  */
    if (t_arch == AUDIT_ARCH_X86_64)
        upper_nr_limit = X32_SYSCALL_BIT - 1;
    struct sock_filter filter[] = {
        /* [0] Charge l'architecture du tampon 'seccomp_data' dans
               l'accumulateur.  */
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
                 (offsetof(struct seccomp_data, arch))),
        /* [1] Saute 5 instructions en avant si l'architecture ne
               correspond pas à 't_arch'.  */
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, t_arch, 0, 5),
        /* [2] Charge le numéro d'appel système du tampon 'seccomp_data' dans
               l'accumulateur.  */
        BPF_STMT(BPF_LD | BPF_W | BPF_ABS,
                 (offsetof(struct seccomp_data, nr))),
        /* [3] Vérifie l'ABI - nécessaire uniquement pour x86-64 dans les cas d'utilisation
               de liste de refus.  Utilise BPF_JGT au lieu de vérifier par rapport au masque de bits
               pour éviter de devoir recharger le numéro d'appel système.  */
        BPF_JUMP(BPF_JMP | BPF_JGT | BPF_K, upper_nr_limit, 3, 0),
        /* [4] Saute 1 instruction en avant si le numéro d'appel système
               ne correspond pas à 'syscall_nr'.  */
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, syscall_nr, 0, 1),
        /* [5] Architecture et appel système correspondants : n'exécute pas
           l'appel système et retourne 'f_errno' dans 'errno'.  */
        BPF_STMT(BPF_RET | BPF_K,
                 SECCOMP_RET_ERRNO | (f_errno & SECCOMP_RET_DATA)),
        /* [6] Destination de la non-correspondance du numéro d'appel système : autorise les autres
               appels système.  */
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
        /* [7] Destination de la non-correspondance de l'architecture : tue le processus.  */
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),
    };
    struct sock_fprog prog = {
        .len = NITEMS(filter),
        .filter = filter,
    };
    if (syscall(SYS_seccomp, SECCOMP_SET_MODE_FILTER, 0, &prog)) {
        perror("seccomp");
        return 1;
    }
    return 0;
}
int
main(int argc, char *argv[])
{
    if (argc < 5) {
        fprintf(stderr, "Usage: "
                "%s <syscall_nr> <arch> <errno> <prog> [<args>]\n"
                "Hint for <arch>: AUDIT_ARCH_I386: 0x%X\n"
                "                 AUDIT_ARCH_X86_64: 0x%X\n"
                "\n", argv[0], AUDIT_ARCH_I386, AUDIT_ARCH_X86_64);
        exit(EXIT_FAILURE);
    }
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)) {
        perror("prctl");
        exit(EXIT_FAILURE);
    }
    if (install_filter(strtol(argv[1], NULL, 0),
                       strtoul(argv[2], NULL, 0),
                       strtol(argv[3], NULL, 0)))
        exit(EXIT_FAILURE);
    execv(argv[4], &argv[4]);
    perror("execv");
    exit(EXIT_FAILURE);
}
