send(n) Commandes intégrées Tk send(n)

NOM

send - Exécute une commande dans une application différente

SYNTAXE

send ?options? app cmd ?arg arg ...?

DESCRIPTION

Cette commande organise l'exécution de cmd (et de ses arguments) dans l'application nommée par app. Elle renvoie le résultat ou l'erreur de l'exécution de cette commande. App peut être le nom d'une application dont la fenêtre principale se trouve sur l'écran contenant la fenêtre principale de l'expéditeur ; elle n'a pas besoin d'être dans le même processus. Si aucun argument arg n'est présent, alors la commande à exécuter est entièrement contenue dans l'argument cmd. S'il y a un ou plusieurs arguments arg, ils sont concaténés pour former la commande à exécuter, tout comme pour la commande eval.

Si les arguments initiaux de la commande commencent par “-”, ils sont traités comme des options. Les options suivantes sont actuellement définies :

-async
Demande une invocation asynchrone. Dans ce cas, la commande send s'achèvera immédiatement sans attendre que cmd se termine dans l'application cible ; aucun résultat ne sera disponible et les erreurs dans la commande envoyée seront ignorées. Si l'application cible se trouve dans le même processus que l'application expéditrice, l'option -async est ignorée.
-displayof pathName
Spécifie que la fenêtre principale de l'application cible se trouve sur l'écran de la fenêtre donnée par pathName, au lieu de l'écran contenant la fenêtre principale de l'application.
--
N'a aucune utilité, sauf pour terminer la liste des options. Cette option n'est nécessaire que si app pourrait contenir un caractère “-” au début.

NOMS APPLICATION

Le nom d'une application est défini initialement à partir du nom du programme ou du script qui a créé l'application. Vous pouvez interroger et modifier le nom d'une application avec la commande tk appname.

DESACTIVATION ENVOIS

Si la commande send est supprimée d'une application (par exemple avec la commande rename send {}), alors l'application ne répondra plus aux requêtes d'envoi entrantes, ni ne pourra émettre de requêtes sortantes. La communication peut être réactivée en invoquant la commande tk appname.

SÉCURITÉ

La commande send est potentiellement une faille de sécurité grave. Sous Unix, toute application capable de se connecter à votre serveur X peut envoyer des scripts à vos applications. Ces scripts entrants peuvent utiliser Tcl pour lire et écrire vos fichiers et invoquer des sous-processus en votre nom. Le contrôle d'accès basé sur l'hôte, tel que celui fourni par xhost, est particulièrement peu sûr, car il permet à toute personne ayant un compte sur des hôtes spécifiques de se connecter à votre serveur, et s'il est désactivé, il permet à quiconque, n'importe où, de se connecter à votre serveur. Afin de fournir un minimum de sécurité, Tk vérifie le contrôle d'accès utilisé par le serveur et rejette les envois entrants à moins que (a) le contrôle d'accès de type xhost ne soit activé (c'est-à-dire seuls certains hôtes peuvent établir des connexions) et (b) la liste des hôtes activés soit vide. Cela signifie que les applications ne peuvent pas se connecter à votre serveur à moins qu'elles n'utilisent une autre forme d'autorisation comme celle fournie par xauth. Sous Windows, send est actuellement désactivé. La majeure partie de la fonctionnalité est fournie par la commande dde à la place.

EXEMPLE

Ce fragment de script peut être utilisé pour faire en sorte qu'une application ne s'exécute qu'une seule fois sur un écran donné.

if {[tk appname FoobarApp] ne "FoobarApp"} {
    send -async FoobarApp RemoteStart $argv
    exit
}
# La commande qui sera appelée à distance, qui élève
# la fenêtre principale de l'application et ouvre les fichiers demandés
proc RemoteStart args {
    raise .
    foreach filename $args {
        OpenFile $filename
    }
}
