send(2) Manuel des appels système send(2)

NOM

send, sendto, sendmsg - envoyer un message sur un socket

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/socket.h>
ssize_t send(size_t size;
               int sockfd, const void buf[size], size_t size, int flags);
ssize_t sendto(size_t size;
               int sockfd, const void buf[size], size_t size, int flags,
               const struct sockaddr *dest_addr, socklen_t addrlen);
ssize_t sendmsg(int sockfd, const struct msghdr *msg, int flags);

DESCRIPTION

Les appels système send(), sendto() et sendmsg() sont utilisés pour transmettre un message à un autre socket.

La fonction send() ne peut être utilisée que lorsque le socket est dans un état connecté (de sorte que le destinataire prévu soit connu). La seule différence entre send() et write(2) est la présence de flags. Avec un argument flags nul, send() est équivalent à write(2). De plus, l'appel suivant


send(sockfd, buf, size, flags);

est équivalent à


sendto(sockfd, buf, size, flags, NULL, 0);

L'argument sockfd est le descripteur de fichier du socket d'envoi.

Si sendto() est utilisé sur un socket en mode connexion (SOCK_STREAM, SOCK_SEQPACKET), les arguments dest_addr et addrlen sont ignorés (et l'erreur EISCONN peut être retournée lorsqu'ils ne sont pas NULL et 0), et l'erreur ENOTCONN est retournée lorsque le socket n'était pas effectivement connecté. Sinon, l'adresse de la cible est donnée par dest_addr avec addrlen spécifiant sa taille. Pour sendmsg(), l'adresse de la cible est donnée par msg.msg_name, avec msg.msg_namelen spécifiant sa taille.

Pour send() et sendto(), le message se trouve dans buf et a une taille size. Pour sendmsg(), le message est pointé par les éléments du tableau msg.msg_iov. L'appel sendmsg() permet également d'envoyer des données auxiliaires (également connues sous le nom d'informations de contrôle).

Si le message est trop long pour passer de manière atomique par le protocole sous-jacent, l'erreur EMSGSIZE est retournée et le message n'est pas transmis.

Aucune indication d'échec de livraison n'est implicite dans un send(). Les erreurs détectées localement sont indiquées par une valeur de retour de -1.

Lorsque le message ne rentre pas dans le tampon d'envoi du socket, send() se bloque normalement, à moins que le socket n'ait été placé en mode E/S non bloquant. En mode non bloquant, cela échouerait avec l'erreur EAGAIN ou EWOULDBLOCK dans ce cas. L'appel select(2) peut être utilisé pour déterminer quand il est possible d'envoyer plus de données.

L'argument flags

L'argument flags est le OU bit à bit de zéro ou plusieurs des indicateurs suivants.

MSG_CONFIRM (depuis Linux 2.3.15)
Indique à la couche de liaison que le progrès a eu lieu : vous avez reçu une réponse réussie de l'autre côté. Si la couche de liaison ne reçoit pas cela, elle interrogera régulièrement le voisin (par exemple, via une ARP en unicast). Valide uniquement sur les sockets SOCK_DGRAM et SOCK_RAW et implémenté actuellement uniquement pour IPv4 et IPv6. Voir arp(7) pour plus de détails.
MSG_DONTROUTE
N'utilise pas de passerelle pour envoyer le paquet, envoie uniquement aux hôtes sur des réseaux directement connectés. Ceci est généralement utilisé uniquement par les programmes de diagnostic ou de routage. Ceci n'est défini que pour les familles de protocoles qui routent ; les sockets de paquet ne le font pas.
MSG_DONTWAIT (depuis Linux 2.2)
Active l'opération non bloquante ; si l'opération bloquait, EAGAIN ou EWOULDBLOCK est retourné. Cela fournit un comportement similaire à la définition de l'indicateur O_NONBLOCK (via l'opération fcntl(2) F_SETFL), mais diffère en ce que MSG_DONTWAIT est une option par appel, tandis que O_NONBLOCK est un paramètre sur le descripteur de fichier ouvert (voir open(2)), qui affectera tous les threads du processus appelant ainsi que d'autres processus qui détiennent des descripteurs de fichier faisant référence à la même description de fichier ouverte.
MSG_EOR (depuis Linux 2.2)
Termine un enregistrement (lorsque cette notion est prise en charge, comme pour les sockets de type SOCK_SEQPACKET).
MSG_MORE (depuis Linux 2.4.4)
L'appelant a plus de données à envoyer. Cet indicateur est utilisé avec les sockets TCP pour obtenir le même effet que l'option de socket TCP_CORK (voir tcp(7)), avec la différence que cet indicateur peut être défini par appel.
Depuis Linux 2.6, cet indicateur est également pris en charge pour les sockets UDP, et informe le noyau de regrouper toutes les données envoyées dans des appels avec cet indicateur activé en un seul datagramme qui n'est transmis que lorsqu'un appel est effectué qui ne spécifie pas cet indicateur. (Voir également l'option de socket UDP_CORK décrite dans udp(7).)
MSG_NOSIGNAL (depuis Linux 2.2)
Ne génère pas de signal SIGPIPE si le pair sur un socket orienté flux a fermé la connexion. L'erreur EPIPE est toujours retournée. Ceci fournit un comportement similaire à l'utilisation de sigaction(2) pour ignorer SIGPIPE, mais, alors que MSG_NOSIGNAL est une fonctionnalité par appel, ignorer SIGPIPE définit un attribut de processus qui affecte tous les threads du processus.
MSG_OOB
Envoie des données hors bande sur les sockets qui supportent cette notion (par exemple, de type SOCK_STREAM) ; le protocole sous-jacent doit également prendre en charge les données hors bande.
MSG_FASTOPEN (depuis Linux 3.7)
Tente TCP Fast Open (RFC7413) et envoie des données dans le SYN comme une combinaison de connect(2) et write(2), en effectuant une opération implicite de connect(2). Il bloque jusqu'à ce que les données soient mises en tampon et que la négociation soit terminée. Pour un socket non bloquant, il retourne le nombre d'octets mis en tampon et envoyés dans le paquet SYN. Si le cookie n'est pas disponible localement, il retourne EINPROGRESS, et envoie un SYN avec une demande de cookie Fast Open automatiquement. L'appelant doit réécrire les données lorsque le socket est connecté. En cas d'erreur, il définit le même errno que connect(2) si la négociation échoue. Cet indicateur nécessite l'activation du support client TCP Fast Open dans le sysctl net.ipv4.tcp_fastopen.
Référez-vous à l'option de socket TCP_FASTOPEN_CONNECT dans tcp(7) pour une approche alternative.

sendmsg()

La définition de la structure msghdr utilisée par sendmsg() est la suivante :


struct msghdr {
    void         *msg_name;       /* Adresse optionnelle */
    socklen_t     msg_namelen;    /* Taille de l'adresse */
    struct iovec *msg_iov;        /* Tableau scatter/gather */
    size_t        msg_iovlen;     /* # éléments dans msg_iov */
    void         *msg_control;    /* Données auxiliaires, voir ci-dessous */
    size_t        msg_controllen; /* Taille du tampon de données auxiliaires */
    int           msg_flags;      /* Flags (non utilisé) */
};

Le champ msg_name est utilisé sur un socket non connecté pour spécifier l'adresse cible d'un datagramme. Il pointe vers un tampon contenant l'adresse ; le champ msg_namelen doit être défini à la taille de l'adresse. Pour un socket connecté, ces champs doivent être spécifiés comme NULL et 0, respectivement.

Les champs msg_iov et msg_iovlen spécifient les emplacements scatter-gather, comme pour writev(2)

a>.

Vous pouvez envoyer des informations de contrôle (données auxiliaires) en utilisant les membres msg_control et msg_controllen. La taille maximale du tampon de contrôle que le noyau peut traiter est limitée par socket par la valeur de /proc/sys/net/core/optmem_max ; voir socket(7). Pour plus d'informations sur l'utilisation des données auxiliaires dans divers domaines de sockets, voir unix(7) et ip(7).

Le champ msg_flags est ignoré.

VALEUR DE RETOUR

En cas de succès, ces appels renvoient le nombre d'octets envoyés. En cas d'erreur, -1 est renvoyé et errno est défini pour indiquer l'erreur.

ERREURS

Voici quelques erreurs standard générées par la couche socket. Des erreurs supplémentaires peuvent être générées et renvoyées par les modules de protocole sous-jacents ; voir leurs pages de manuel respectives.

EACCES
(Pour les sockets de domaine UNIX, qui sont identifiés par un chemin) Le droit d'écriture est refusé sur le fichier socket de destination, ou le droit de recherche est refusé pour l'un des répertoires du préfixe du chemin. (Voir path_resolution(7).)
(Pour les sockets UDP) Une tentative a été faite pour envoyer à une adresse réseau/de diffusion comme s'il s'agissait d'une adresse unicast.
EAGAIN ou EWOULDBLOCK
Le socket est marqué comme non bloquant et l'opération demandée bloquerait. POSIX.1-2001 autorise l'une ou l'autre de ces erreurs pour ce cas, et ne requiert pas que ces constantes aient la même valeur, donc une application portable devrait vérifier les deux possibilités.
EAGAIN
(Sockets datagrammes du domaine Internet) Le socket référencé par sockfd n'avait pas été précédemment lié à une adresse et, lors d'une tentative de liaison à un port éphémère, il a été déterminé que tous les numéros de port dans la plage des ports éphémères sont actuellement utilisés. Voir la discussion sur /proc/sys/net/ipv4/ip_local_port_range dans ip(7).
EALREADY
Un autre Fast Open est en cours.
EBADF
sockfd n'est pas un descripteur de fichier valide et ouvert.
ECONNRESET
Connexion réinitialisée par le pair.
EDESTADDRREQ
Le socket n'est pas en mode connexion et aucune adresse de pair n'est définie.
EFAULT
Une adresse invalide de l'espace utilisateur a été spécifiée pour un argument.
EINTR
Un signal s'est produit avant la transmission de données ; voir signal(7).
EINVAL
Argument invalide passé.
EISCONN
Le socket en mode connexion était déjà connecté mais un destinataire a été spécifié. (Maintenant, soit cette erreur est renvoyée, soit la spécification du destinataire est ignorée.)
EMSGSIZE
Le type de socket nécessite que les messages soient envoyés de manière atomique, et la taille du message à envoyer a rendu cela impossible.
ENOBUFS
La file d'attente de sortie d'une interface réseau était pleine. Cela indique généralement que l'interface a arrêté d'envoyer, mais peut être causé par une congestion transitoire. (Normalement, cela ne se produit pas sous Linux. Les paquets sont simplement silencieusement abandonnés lorsqu'une file d'attente de périphérique déborde.)
ENOMEM
Aucune mémoire disponible.
ENOTCONN
Le socket n'est pas connecté et aucun destinataire n'a été spécifié.
ENOTSOCK
Le descripteur de fichier sockfd ne fait pas référence à un socket.
EOPNOTSUPP
Certains bits dans l'argument flags sont inappropriés pour le type de socket.
EPIPE
L'extrémité locale a été fermée sur un socket orienté connexion. Dans ce cas, le processus recevra également un SIGPIPE à moins que MSG_NOSIGNAL ne soit défini.

VERSIONS

Selon POSIX.1-2001, le champ msg_controllen de la structure msghdr doit être typé comme socklen_t, et le champ msg_iovlen doit être typé comme int, mais glibc les type actuellement tous deux comme size_t.

NORMES

POSIX.1-2024.

MSG_CONFIRM est une extension Linux.

HISTORIQUE

4.4BSD, SVr4, POSIX.1-2001. (est apparu pour la première fois dans 4.2BSD).

POSIX.1-2001 ne décrit que les drapeaux MSG_OOB et MSG_EOR. POSIX.1-2008 ajoute une spécification de MSG_NOSIGNAL.

NOTES

Voir sendmmsg(2) pour des informations sur un appel système spécifique à Linux qui peut être utilisé pour transmettre plusieurs datagrammes en un seul appel.

BOGUES

Linux peut renvoyer EPIPE au lieu de ENOTCONN.

EXEMPLES

Un exemple d'utilisation de sendto() est montré dans getaddrinfo(3).
