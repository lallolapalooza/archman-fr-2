NOM

seccomp_rule_add, seccomp_rule_add_exact - Ajouter une règle de filtre seccomp

SYNOPSIS

#include <seccomp.h>

typedef void * scmp_filter_ctx;

int SCMP_SYS(nom_appel_sys);

struct scmp_arg_cmp SCMP_CMP(unsigned int arg,
                             enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A0(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A1(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A2(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A3(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A4(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A5(enum scmp_compare op, ...);

struct scmp_arg_cmp SCMP_CMP64(unsigned int arg,
                             enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A0_64(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A1_64(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A2_64(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A3_64(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A4_64(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A5_64(enum scmp_compare op, ...);

struct scmp_arg_cmp SCMP_CMP32(unsigned int arg,
                             enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A0_32(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A1_32(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A2_32(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A3_32(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A4_32(enum scmp_compare op, ...);
struct scmp_arg_cmp SCMP_A5_32(enum scmp_compare op, ...);

int seccomp_rule_add(scmp_filter_ctx ctx, uint32_t action,
                     int syscall, unsigned int arg_cnt, ...);
int seccomp_rule_add_exact(scmp_filter_ctx ctx, uint32_t action,
                           int syscall, unsigned int arg_cnt, ...);

int seccomp_rule_add_array(scmp_filter_ctx ctx,
                           uint32_t action, int syscall,
                           unsigned int arg_cnt,
                           const struct scmp_arg_cmp *arg_array);
int seccomp_rule_add_exact_array(scmp_filter_ctx ctx,
                                 uint32_t action, int syscall,
                                 unsigned int arg_cnt,
                                 const struct scmp_arg_cmp *arg_array);

Lier avec -lseccomp.

DESCRIPTION

Les fonctions seccomp_rule_add(), seccomp_rule_add_array(), seccomp_rule_add_exact() et seccomp_rule_add_exact_array() ajoutent toutes une nouvelle règle de filtre au filtre seccomp courant. Les fonctions seccomp_rule_add() et seccomp_rule_add_array() feront de leur mieux pour ajouter la règle comme spécifié, mais peuvent la modifier légèrement en raison de spécificités architecturales (par exemple, réécriture interne des appels système multiplexés, comme les fonctions socket et ipc sur x86). Les fonctions seccomp_rule_add_exact() et seccomp_rule_add_exact_array() tenteront d'ajouter la règle exactement comme spécifié, elle peut donc se comporter différemment sur différentes architectures. Bien qu'elle ne garantisse pas un jeu de règles de filtre exact, seccomp_rule_add() et seccomp_rule_add_array() garantissent un comportement identique indépendamment de l'architecture.

La règle de filtre nouvellement ajoutée ne prend effet que lorsque l'ensemble du filtre est chargé dans le noyau à l'aide de seccomp_load(3). Lors de l'ajout de règles à un filtre, il est important de tenir compte de l'impact des filtres précédemment chargés ; voir la documentation de seccomp_load(3) pour plus d'informations.

Toutes les règles de filtre fournies par l'application appelante sont combinées en une union, avec une logique supplémentaire pour éliminer les filtres d'appels système redondants. Par exemple, si une règle est ajoutée qui autorise un appel système donné avec un ensemble spécifique de valeurs d'arguments et plus tard une règle est ajoutée qui autorise le même appel système quelle que soit la valeur de l'argument, alors la première règle, plus spécifique, est effectivement supprimée du filtre par la seconde règle, plus générique.

Les macros SCMP_CMP(), SCMP_CMP64(), SCMP_A{0-5}() et SCMP_A{0-5}_64() génèrent une structure scmp_arg_cmp à utiliser avec les fonctions ci-dessus. Les macros SCMP_CMP() et SCMP_CMP64() permettent à l'appelant de spécifier un argument arbitraire avec l'opérateur de comparaison, le masque 64 bits et les valeurs de données, tandis que les macros SCMP_A{0-5}() et SCMP_A{0-5}_64() sont spécifiques à un certain argument.

Les macros SCMP_CMP32() et SCMP_A{0-5}_32() sont similaires aux variantes ci-dessus, mais elles prennent des masques 32 bits et des valeurs de données 32 bits.

Il est recommandé, chaque fois que possible, d'éviter d'utiliser les macros SCMP_CMP() et SCMP_A{0-5}() et d'utiliser les variantes qui sont explicitement 32 ou 64 bits. Cela devrait aider à éliminer les problèmes causés par une extension de signe indésirable des valeurs de données négatives.

Si des comparaisons d'arguments d'appels système sont incluses dans la règle de filtre, toutes les comparaisons doivent être vraies pour que la règle corresponde.

Lors de l'ajout de comparaisons d'arguments d'appels système au filtre, il est important de se rappeler que bien qu'il soit possible d'avoir plusieurs comparaisons dans une seule règle, vous ne pouvez comparer chaque argument qu'une seule fois dans une seule règle. Autrement dit, vous ne pouvez pas avoir plusieurs comparaisons du 3ème argument d'appel système dans une seule règle.

Dans un filtre contenant plusieurs architectures, il est une erreur d'ajouter une règle de filtre pour un appel système qui n'existe pas dans toutes les architectures du filtre.

Bien qu'il soit possible de spécifier la valeur syscall directement en utilisant les valeurs standard __NR_syscall, afin d'assurer un fonctionnement correct sur plusieurs architectures, il est fortement recommandé d'utiliser plutôt la macro SCMP_SYS(). Voir la section EXEMPLES ci-dessous. Il est également important de se rappeler que quelles que soient les architectures présentes dans le filtre, les numéros d'appels système utilisés dans les règles de filtre sont interprétés dans le contexte de l'architecture native.

À partir de Linux v4.8, il peut être nécessaire de créer une règle avec une valeur d'appel système de -1 pour permettre aux programmes de traçage de sauter une invocation d'appel système ; pour créer une règle avec une valeur d'appel système de -1, il est nécessaire de définir d'abord l'attribut SCMP_FLTATR_API_TSKIP. Voir seccomp_attr_set(3) pour plus d'informations.

Le contexte de filtre ctx est la valeur retournée par l'appel à seccomp_init(3).

Les valeurs action valides sont les suivantes :

SCMP_ACT_KILL
Le thread sera tué par le noyau lorsqu'il appellera un appel système qui correspond à la règle de filtre.
SCMP_ACT_KILL_PROCESS
Le processus sera tué par le noyau lorsqu'il appellera un appel système qui correspond à la règle de filtre.
SCMP_ACT_TRAP
Le thread lancera un signal SIGSYS lorsqu'il appellera un appel système qui correspond à la règle de filtre.
SCMP_ACT_ERRNO(uint16_t errno)
Le thread recevra une valeur de retour de errno lorsqu'il appellera un appel système qui correspond à la règle de filtre.
SCMP_ACT_TRACE(uint16_t msg_num)
Si le thread est tracé et que le processus de traçage a spécifié l'option PTRACE_O_TRACESECCOMP dans l'appel à ptrace(2), le processus de traçage sera notifié, via PTRACE_EVENT_SECCOMP, et la valeur fournie dans msg_num pourra être récupérée à l'aide de l'option PTRACE_GETEVENTMSG.
seccomp_rule_add_exact_array(3) — libseccomp — Arch Linux

NAME

seccomp_rule_add_exact_array, seccomp_rule_add_array, seccomp_rule_add, seccomp_rule_add_exact - add a seccomp filter rule

SYNOPSIS

#include <seccomp.h>

int seccomp_rule_add(scmp_filter_ctx *ctx, uint32_t action, int syscall, unsigned int arg_cnt, ...);

int seccomp_rule_add_exact(scmp_filter_ctx *ctx, uint32_t action, int syscall, unsigned int arg_cnt, ...);

int seccomp_rule_add_array(scmp_filter_ctx *ctx, uint32_t action, int syscall, unsigned int arg_cnt, const struct scmp_arg_cmp *arg_array);

int seccomp_rule_add_exact_array(scmp_filter_ctx *ctx, uint32_t action, int syscall, unsigned int arg_cnt, const struct scmp_arg_cmp *arg_array);

DESCRIPTION

These functions are used to add seccomp filter rules to an existing seccomp filter context. Rules are comprised of a syscall number, an action to take when the rule matches, and a set of argument conditions that must also be met for the rule to match. The argument conditions are optional; if no argument conditions are specified, the rule will match any call to the specified syscall.

The seccomp_rule_add() and seccomp_rule_add_exact() functions take a variable number of arguments representing the argument conditions. The first argument condition corresponds to the first argument of the syscall, the second argument condition to the second argument of the syscall, and so on. The number of argument conditions is specified by the arg_cnt argument.

The seccomp_rule_add_array() and seccomp_rule_add_exact_array() functions take an array of argument conditions, specified by the arg_array argument, which must be an array of arg_cnt struct scmp_arg_cmp structures.

The difference between the _add and _add_exact variants lies in how they handle argument conditions. The _add functions allow for a broader range of comparisons, while the _add_exact functions require exact matches for the specified arguments.

The following are valid action values for the action argument:

SCMP_ACT_KILL
The seccomp filter will terminate the calling thread.
SCMP_ACT_TRAP
The seccomp filter will cause the kernel to generate a SIGSYS signal.
SCMP_ACT_ERRNO
The seccomp filter will return the specified error code to the calling thread.
SCMP_ACT_LOG
The seccomp filter will have no effect on the thread calling the syscall if it matches the filter rule but the syscall will be logged.
SCMP_ACT_ALLOW
The seccomp filter will have no effect on the thread calling the syscall if it matches the filter rule.
SCMP_ACT_NOTIFY
A monitoring process will be notified when a process running the seccomp filter calls a syscall that matches the filter rule. The process that invokes the syscall waits in the kernel until the monitoring process has responded via seccomp_notify_respond (3) .

When a filter utilizing SCMP_ACT_NOTIFY is loaded into the kernel, the kernel generates a notification fd that must be used to communicate between the monitoring process and the process(es) being filtered. See seccomp_notif_fd (3) for more information.

Valid comparison op values are as follows:

SCMP_CMP_NE
Matches when the argument value is not equal to the datum value, example:

SCMP_CMP( arg , SCMP_CMP_NE , datum )

SCMP_CMP_LT
Matches when the argument value is less than the datum value, example:

SCMP_CMP( arg , SCMP_CMP_LT , datum )

SCMP_CMP_LE
Matches when the argument value is less than or equal to the datum value, example:

SCMP_CMP( arg , SCMP_CMP_LE , datum )

SCMP_CMP_EQ
Matches when the argument value is equal to the datum value, example:

SCMP_CMP( arg , SCMP_CMP_EQ , datum )

SCMP_CMP_GE
Matches when the argument value is greater than or equal to the datum value, example:

SCMP_CMP( arg , SCMP_CMP_GE , datum )

SCMP_CMP_GT
Matches when the argument value is greater than the datum value, example:

SCMP_CMP( arg , SCMP_CMP_GT , datum )

SCMP_CMP_MASKED_EQ
Matches when the masked argument value is equal to the masked datum value, example:

SCMP_CMP( arg , SCMP_CMP_MASKED_EQ , mask , datum )

RETURN VALUE

The SCMP_SYS() macro returns a value suitable for use as the syscall value in the seccomp_rule_add*() functions. In a similar manner, the SCMP_CMP() and SCMP_A*() macros return values suitable for use as argument comparisons in the seccomp_rule_add() and seccomp_rule_add_exact() functions.

The seccomp_rule_add(), seccomp_rule_add_array(), seccomp_rule_add_exact(), and seccomp_rule_add_exact_array() functions return zero on success or one of the following error codes on failure:

-EDOM
Architecture specific failure.
-EEXIST
The rule already exists.
-EACCCES
The rule conflicts with the filter (for example, the rule action equals the default action of the filter).
-EFAULT
Internal libseccomp failure.
-EINVAL
Invalid input, either the context or architecture token is invalid.
-ENOMEM
The library was unable to allocate enough memory.
-EOPNOTSUPP
The library doesn't support the particular operation.

EXAMPLES

#include <fcntl.h>
#include <seccomp.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <stddef.h>
#define BUF_SIZE	256
int main(int argc, char *argv[])
{
	int rc = -1;
	scmp_filter_ctx ctx;
	struct scmp_arg_cmp arg_cmp[] = { SCMP_A0(SCMP_CMP_EQ, 2) };
	int fd;
	unsigned char buf[BUF_SIZE];
	ctx = seccomp_init(SCMP_ACT_KILL);
	if (ctx == NULL)
		goto out;
	/* ... */
	fd = open("file.txt", 0);
	/* ... */
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(close), 0);
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit_group), 0);
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(exit), 0);
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read), 3,
			      SCMP_A0(SCMP_CMP_EQ, fd),
			      SCMP_A1(SCMP_CMP_EQ, (scmp_datum_t)buf),
			      SCMP_A2(SCMP_CMP_LE, BUF_SIZE));
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
			      SCMP_CMP(0, SCMP_CMP_EQ, fd));
	if (rc < 0)
		goto out;
	rc = seccomp_rule_add_array(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 1,
			            arg_cmp);
	if (rc < 0)
		goto out;
	rc = seccomp_load(ctx);
	if (rc < 0)
		goto out;
	/* ... */
out:
	seccomp_release(ctx);
	return -rc;
}

NOTES

While the seccomp filter can be generated independent of the kernel, kernel support is required to load and enforce the seccomp filter generated by libseccomp.

The libseccomp project site, with more information and the source code repository, can be found at https://github.com/seccomp/libseccomp. This tool, as well as the libseccomp library, is currently under development, please report any bugs at the project site or directly to the author.

BUGS

The runtime behavior of seccomp filters is dependent upon the kernel version, the processor architecture, and other libraries including libc. This could affect the return code of a seccomp filter.

*
PowerPC glibc will not return a negative number when the getpid() syscall is invoked. If a seccomp filter has been created where getpid() will return a negative number from the kernel, then PowerPC glibc will return the absolute value of the errno. In this case, it is very difficult for an application to distinguish between the errno and a valid pid.
