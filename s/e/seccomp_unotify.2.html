NOM

seccomp_unotify - Mécanisme de notification utilisateur de Seccomp

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <linux/seccomp.h>
#include <linux/filter.h>
#include <linux/audit.h>
int seccomp(unsigned int operation, unsigned int flags, void *args);
#include <sys/ioctl.h>

          struct seccomp_notif *req);
int ioctl(int fd, SECCOMP_IOCTL_NOTIF_SEND,

DESCRIPTION

Cette page décrit le mécanisme de notification utilisateur fourni par la fonctionnalité de Calcul Sécurisé (seccomp). En plus de l'utilisation du drapeau SECCOMP_FILTER_FLAG_NEW_LISTENER, de la valeur d'action SECCOMP_RET_USER_NOTIF, et de l'opération SECCOMP_GET_NOTIF_SIZES décrits dans seccomp(2), ce mécanisme implique l'utilisation d'un certain nombre d'opérations ioctl(2) associées (décrites ci-dessous).

Aperçu

Dans l'utilisation conventionnelle d'un filtre seccomp, la décision concernant la manière de traiter un appel système est prise par le filtre lui-même. En revanche, le mécanisme de notification utilisateur permet au filtre seccomp de déléguer le traitement de l'appel système à un autre processus utilisateur. Notez que ce mécanisme n'est explicitement pas destiné à implémenter une politique de sécurité ; voir NOTES.

Dans la discussion qui suit, le ou les threads sur lesquels le filtre seccomp est installé sont désignés comme la cible, et le processus qui est notifié par le mécanisme de notification utilisateur est désigné comme le superviseur.

Un superviseur suffisamment privilégié peut utiliser le mécanisme de notification utilisateur pour effectuer des actions au nom de la cible. L'avantage du mécanisme de notification utilisateur est que le superviseur pourra généralement récupérer des informations sur la cible et l'appel système effectué que le filtre seccomp lui-même ne peut pas. (Un filtre seccomp est limité dans les informations qu'il peut obtenir et dans les actions qu'il peut effectuer car il s'exécute sur une machine virtuelle à l'intérieur du noyau.)

Un aperçu des étapes effectuées par la cible et le superviseur est le suivant :

(1)
La cible établit un filtre seccomp de la manière habituelle, mais avec deux différences :
•
L'argument flags de seccomp(2) inclut le drapeau SECCOMP_FILTER_FLAG_NEW_LISTENER. Par conséquent, la valeur de retour de l'appel (réussi) seccomp(2) est un nouveau descripteur de fichier « écoutant » qui peut être utilisé pour recevoir des notifications. Un seul filtre seccomp « écoutant » peut être installé pour un thread.
•
Dans les cas où cela est approprié, le filtre seccomp renvoie la valeur d'action SECCOMP_RET_USER_NOTIF. Cette valeur de retour déclenchera un événement de notification.
(2)
Afin que le superviseur puisse obtenir des notifications en utilisant le descripteur de fichier écoutant, (un duplicata de) ce descripteur de fichier doit être transmis de la cible au superviseur. Une façon de faire cela pourrait être de transmettre le descripteur de fichier via une connexion de socket de domaine UNIX entre la cible et le superviseur (en utilisant le type de message auxiliaire SCM_RIGHTS décrit dans unix(7)). Une autre façon de faire est d'utiliser pidfd_getfd(2).
(3)
Le superviseur recevra des événements de notification sur le descripteur de fichier écoutant. Ces événements sont retournés sous forme de structures de type seccomp_notif. Comme cette structure et sa taille peuvent évoluer au fil des versions du noyau, le superviseur doit d'abord déterminer la taille de cette structure en utilisant l'opération SECCOMP_GET_NOTIF_SIZES de seccomp(2), qui renvoie une structure de type seccomp_notif_sizes. Le superviseur alloue un tampon de taille seccomp_notif_sizes.seccomp_notif octets pour recevoir les événements de notification. De plus, le superviseur alloue un autre tampon de taille seccomp_notif_sizes.seccomp_notif_resp octets pour la réponse (une structure seccomp_notif_resp) qu'il fournira au noyau (et donc à la cible).
(4)
La cible effectue ensuite son travail, qui comprend des appels système qui seront contrôlés par le filtre seccomp. Chaque fois que l'un de ces appels système amène le filtre à renvoyer la valeur d'action SECCOMP_RET_USER_NOTIF, le noyau n'exécute pas (encore) l'appel système ; au lieu de cela, l'exécution de la cible est temporairement bloquée à l'intérieur du noyau (dans un état de sommeil interruptible par des signaux) et un événement de notification est généré sur le descripteur de fichier écoutant.
(5)
Le superviseur peut désormais surveiller de manière répétée le descripteur de fichier écoutant pour les événements déclenchés par SECCOMP_RET_USER_NOTIF. Pour ce faire, le superviseur utilise l'opération ioctl(2) SECCOMP_IOCTL_NOTIF_RECV pour lire des informations sur un événement de notification ; cette opération bloque jusqu'à ce qu'un événement soit disponible. L'opération renvoie une structure seccomp_notif contenant des informations sur l'appel système qui est tenté par la cible. (Comme décrit dans NOTES, le descripteur de fichier peut également être surveillé avec select(2), poll(2), ou epoll(7).)
(6)
La structure seccomp_notif renvoyée par l'opération SECCOMP_IOCTL_NOTIF_RECV inclut les mêmes informations (une structure seccomp_data) que celles passées au filtre seccomp. Ces informations permettent au superviseur de découvrir le numéro de l'appel système et les arguments de l'appel système de la cible. De plus, l'événement de notification contient l'ID du thread qui a déclenché la notification et une valeur de cookie unique qui est utilisée dans les opérations ultérieures SECCOMP_IOCTL_NOTIF_ID_VALID et SECCOMP_IOCTL_NOTIF_SEND.
Les informations contenues dans la notification peuvent être utilisées pour découvrir les valeurs des arguments pointeurs de l'appel système de la cible. (C'est quelque chose qui ne peut pas être fait depuis un filtre seccomp.) Une façon dont le superviseur peut faire cela est d'ouvrir le fichier /proc/tid/mem correspondant (voir proc(5)) et de lire des octets depuis l'emplacement correspondant à l'un des arguments pointeurs dont la valeur est fournie dans l'événement de notification. (Le superviseur doit faire attention à éviter une condition de concurrence qui peut se produire lors de la réalisation de cette opération ; voir la description de l'opération ioctl(2) SECCOMP_IOCTL_NOTIF_ID_VALID ci-dessous.) De plus, le superviseur peut accéder à d'autres informations système visibles en espace utilisateur mais qui ne sont pas accessibles depuis un filtre seccomp.
(7)
Après avoir obtenu des informations conformément à l'étape précédente, le superviseur peut alors choisir d'effectuer une action en réponse à l'appel système de la cible (qui, comme noté ci-dessus, n'est pas exécuté lorsque le filtre seccomp renvoie la valeur d'action SECCOMP_RET_USER_NOTIF).
Un cas d'utilisation exemple ici concerne les conteneurs. La cible peut se trouver à l'intérieur d'un conteneur où elle ne dispose pas de suffisamment de capacités pour monter un système de fichiers dans l'espace de montage du conteneur. Cependant, le superviseur peut être un processus plus privilégié qui dispose de suffisamment de capacités pour effectuer l'opération de montage.
(8)
Le superviseur envoie ensuite une réponse à la notification. Les informations de cette réponse sont utilisées par le noyau pour construire une valeur de retour pour l'appel système de la cible et fournir une valeur qui sera attribuée à la variable errno de la cible.
La réponse est envoyée en utilisant l'opération ioctl(2) SECCOMP_IOCTL_NOTIF_SEND, qui est utilisée pour transmettre une structure seccomp_notif_resp au noyau. Cette structure inclut une valeur de cookie que le superviseur a obtenue dans la structure seccomp_notif renvoyée par l'opération SECCOMP_IOCTL_NOTIF opération. Cette valeur de cookie permet au noyau d'associer la réponse à la cible. Cette structure doit inclure la valeur du cookie que le superviseur a obtenue dans la structure seccomp_notif retournée par l'opération SECCOMP_IOCTL_NOTIF_RECV ; le cookie permet au noyau d'associer la réponse à la cible.
(9)
Une fois la notification envoyée, l'appel système dans le thread cible se débloque, retournant les informations fournies par le superviseur dans la réponse de notification.

Comme variation des deux dernières étapes, le superviseur peut envoyer une réponse indiquant au noyau d'exécuter l'appel système du thread cible ; voir la discussion sur SECCOMP_USER_NOTIF_FLAG_CONTINUE, ci-dessous.

OPÉRATIONS IOCTL

Les opérations ioctl(2) suivantes sont prises en charge par le descripteur de fichier de notification en espace utilisateur seccomp. Pour chacune de ces opérations, le premier argument (descripteur de fichier) de ioctl(2) est le descripteur de fichier d'écoute retourné par un appel à seccomp(2) avec le flag SECCOMP_FILTER_FLAG_NEW_LISTENER.

SECCOMP_IOCTL_NOTIF_RECV

L'opération SECCOMP_IOCTL_NOTIF_RECV (disponible depuis Linux 5.0) est utilisée pour obtenir un événement de notification en espace utilisateur. S'il n'y a pas d'événement en attente, l'opération se bloque jusqu'à ce qu'un événement se produise. Le troisième argument ioctl(2) est un pointeur vers une structure de la forme suivante qui contient des informations sur l'événement. Cette structure doit être mise à zéro avant l'appel.


struct seccomp_notif {
    __u64  id;              /* Cookie */
    __u32  pid;             /* TID du thread cible */
    __u32  flags;           /* Actuellement non utilisé (0) */
    struct seccomp_data data;   /* Voir seccomp(2) */
};

Les champs de cette structure sont les suivants :

id
Ceci est un cookie pour la notification. Chaque cookie est garanti unique pour le filtre seccomp correspondant.
•
Le cookie peut être utilisé avec l'opération ioctl(2) SECCOMP_IOCTL_NOTIF_ID_VALID décrite ci-dessous.
•
Lors du retour d'une réponse de notification au noyau, le superviseur doit inclure la valeur du cookie dans la structure seccomp_notif_resp qui est spécifiée comme argument de l'opération SECCOMP_IOCTL_NOTIF_SEND.
pid
Ceci est l'ID du thread cible qui a déclenché l'événement de notification.
flags
Ceci est un masque de bits fournissant des informations supplémentaires sur l'événement. Dans l'implémentation actuelle, ce champ est toujours zéro.
data
Ceci est une structure seccomp_data contenant des informations sur l'appel système qui a déclenché la notification. C'est la même structure qui est passée au filtre seccomp. Voir seccomp(2) pour les détails de cette structure.

En cas de succès, cette opération retourne 0 ; en cas d'échec, -1 est retourné, et errno est défini pour indiquer l'erreur. Cette opération peut échouer avec les erreurs suivantes :

EINVAL (depuis Linux 5.5)
La structure seccomp_notif passée à l'appel contenait des champs non nuls.
ENOENT
Le thread cible a été tué par un signal lors de la génération des informations de notification, ou l'appel système (bloqué) de la cible a été interrompu par un gestionnaire de signal.

SECCOMP_IOCTL_NOTIF_ID_VALID

L'opération SECCOMP_IOCTL_NOTIF_ID_VALID (disponible depuis Linux 5.0) est utilisée pour vérifier qu'un ID de notification retourné par une opération précédente SECCOMP_IOCTL_NOTIF_RECV est toujours valide (c'est-à-dire que la cible existe toujours et que son appel système est toujours bloqué en attendant une réponse).

Le troisième argument ioctl(2) est un pointeur vers le cookie (id) retourné par l'opération SECCOMP_IOCTL_NOTIF_RECV.

Cette opération est nécessaire pour éviter les conditions de concurrence qui peuvent survenir lorsque le pid retourné par l'opération SECCOMP_IOCTL_NOTIF_RECV se termine, et que cet ID de processus est réutilisé par un autre processus. Un exemple de ce type de concurrence est le suivant :

(1)
Une notification est générée sur le descripteur de fichier d'écoute. Le seccomp_notif retourné contient le TID du thread cible (dans le champ pid de la structure).
(2)
La cible se termine.
(3)
Un autre thread ou processus est créé sur le système qui réutilise par hasard le TID libéré lors de la terminaison de la cible.
(4)
Le superviseur open(2) le fichier /proc/tid/mem pour le TID obtenu à l'étape 1, avec l'intention d'inspecter (par exemple) l'emplacement mémoire contenant les arguments de l'appel système qui a déclenché la notification à l'étape 1.

Dans le scénario ci-dessus, le risque est que le superviseur tente d'accéder à la mémoire d'un processus autre que la cible. Cette concurrence peut être évitée en suivant l'appel à open(2) avec une opération SECCOMP_IOCTL_NOTIF_ID_VALID pour vérifier que le processus qui a généré la notification est toujours en vie. (Notez que si la cible se termine après la dernière étape, une lecture ultérieure (read(2)) du descripteur de fichier peut retourner 0, indiquant la fin du fichier.)

Voir NOTES pour une discussion sur d'autres cas où des vérifications SECCOMP_IOCTL_NOTIF_ID_VALID doivent être effectuées.

En cas de succès (c'est-à-dire que l'ID de notification est toujours valide), cette opération retourne 0. En cas d'échec (c'est-à-dire que l'ID de notification n'est plus valide), -1 est retourné, et errno est défini à ENOENT.

SECCOMP_IOCTL_NOTIF_SEND

L'opération SECCOMP_IOCTL_NOTIF_SEND (disponible depuis Linux 5.0) est utilisée pour envoyer une réponse de notification au noyau. Le troisième argument ioctl(2) de cette structure est un pointeur vers une structure de la forme suivante :


struct seccomp_notif_resp {
    __u64 id;           /* Valeur du cookie */
    __s64 val;          /* Valeur de retour de succès */
    __s32 error;        /* 0 (succès) ou numéro d'erreur négatif */
    __u32 flags;        /* Voir ci-dessous */
};

Les champs de cette structure sont les suivants :

id
Ceci est la valeur du cookie obtenue à l'aide de l'opération SECCOMP_IOCTL_NOTIF_RECV. Cette valeur de cookie permet au noyau d'associer correctement cette réponse à l'appel système qui a déclenché la notification en espace utilisateur.
val
Ceci est la valeur qui sera utilisée pour un retour de succès simulé pour l'appel système de la cible ; voir ci-dessous.
error
Ceci est la valeur qui sera utilisée comme numéro d'erreur (errno) pour un retour d'erreur simulé pour l'appel système de la cible ; voir ci-dessous.
flags
Ceci est un masque de bits qui inclut zéro ou plusieurs des flags suivants :
SECCOMP_USER_NOTIF_FLAG_CONTINUE (depuis Linux 5.5)
Indiquer au noyau d'exécuter l'appel système de la cible.

Deux types de réponses sont possibles :

•
Une réponse au noyau indiquant qu'il doit exécuter l'appel système de la cible. Dans ce cas, le champ flags inclut SECCOMP_USER_NOTIF_FLAG_CONTINUE et les champs error et val doivent être zéro.
Ce type de réponse peut être utile dans les cas où le superviseur a besoin d'une analyse plus approfondie de l'appel système de la cible que ce qui est possible à partir d'un filtre seccomp (par exemple, l'examen des valeurs des arguments pointeurs), et, après avoir décidé que l'appel système ne nécessite pas d'émulation par le superviseur, le superviseur souhaite que l'appel système soit exécuté normalement dans la cible.
Le flag SECCOMP_USER_NOTIF_FLAG_CONTINUE doit être utilisé avec précaution ; voir NOTES.
•
Une valeur de retour simulée pour l'appel système de la cible. Dans ce cas, le noyau n'exécute pas l'appel système de la cible, mais provoque plutôt le retour d'une valeur simulée comme spécifié par les champs de la structure seccomp_notif_resp. Le superviseur doit définir les champs de cette structure comme suit :
•
flags ne contient pas SECCOMP_USER_NOTIF_FLAG_CONTINUE.
•
error est défini soit à 0 pour un retour de "succès" simulé, soit à un numéro d'erreur négatif pour un retour d'"échec" simulé. Dans le premier cas, le noyau provoque le retour de l'appel système de la cible avec la valeur spécifiée dans le champ val. Dans le second cas, le noyau provoque le retour de -1 pour l'appel système de la cible, et errno reçoit la valeur négative de error.
•
val est défini à une valeur qui sera utilisée comme valeur de retour pour un retour de "succès" simulé pour l'appel système de la cible. La valeur de ce champ est ignorée si le champ error contient une valeur non nulle.

En cas de succès, cette opération retourne 0 ; en cas d'échec, -1 est retourné, et errno est défini pour indiquer l'erreur. Cette opération peut échouer avec les erreurs suivantes :

EINPROGRESS
Une réponse à cette notification a déjà été envoyée.
EINVAL
Une valeur invalide a été spécifiée dans le champ flags.
EINVAL
Le champ flags contenait SECCOMP_USER_NOTIF_FLAG_CONTINUE, et le champ error ou val fi
eld n'était pas zéro.
ENOENT
L'appel système bloqué dans la cible a été interrompu par un gestionnaire de signaux ou la cible s'est terminée.

SECCOMP_IOCTL_NOTIF_ADDFD

L'opération SECCOMP_IOCTL_NOTIF_ADDFD (disponible depuis Linux 5.9) permet au superviseur d'installer un descripteur de fichier dans la table des descripteurs de fichiers de la cible. Tout comme l'utilisation des messages SCM_RIGHTS décrits dans unix(7), cette opération est sémantiquement équivalente à la duplication d'un descripteur de fichier de la table des descripteurs de fichiers du superviseur vers la table des descripteurs de fichiers de la cible.

L'opération SECCOMP_IOCTL_NOTIF_ADDFD permet au superviseur d'émuler un appel système cible (tel que socket(2) ou openat(2)) qui génère un descripteur de fichier. Le superviseur peut effectuer l'appel système qui génère le descripteur de fichier (et la description de fichier ouverte associée) puis utiliser cette opération pour allouer un descripteur de fichier qui fait référence à la même description de fichier ouverte dans la cible. (Pour une explication des descriptions de fichiers ouverts, voir open(2).)

Une fois cette opération effectuée, le superviseur peut fermer sa copie du descripteur de fichier.

Dans la cible, le descripteur de fichier reçu est soumis aux mêmes vérifications du Linux Security Module (LSM) que celles appliquées à un descripteur de fichier reçu dans un message auxiliaire SCM_RIGHTS. Si le descripteur de fichier fait référence à une socket, il hérite des paramètres du contrôleur réseau cgroup version 1 (classid et netprioidx) de la cible.

Le troisième argument ioctl(2) est un pointeur vers une structure de la forme suivante :


struct seccomp_notif_addfd {
    __u64 id;           /* Valeur du cookie */
    __u32 flags;        /* Indicateurs */
    __u32 srcfd;        /* Numéro de descripteur de fichier local */
    __u32 newfd;        /* 0 ou numéro de descripteur de fichier
                           souhaité dans la cible */
    __u32 newfd_flags;  /* Indicateurs à définir sur le descripteur de fichier
                           cible */
};

Les champs de cette structure sont les suivants :

id
Ce champ doit être défini sur l'ID de notification (valeur du cookie) obtenu via SECCOMP_IOCTL_NOTIF_RECV.
flags
Ce champ est un masque de bits d'indicateurs qui modifient le comportement de l'opération. Actuellement, un seul indicateur est pris en charge :
SECCOMP_ADDFD_FLAG_SETFD
Lors de l'allocation du descripteur de fichier dans la cible, utiliser le numéro de descripteur de fichier spécifié dans le champ newfd.
SECCOMP_ADDFD_FLAG_SEND (depuis Linux 5.14)
Effectue l'équivalent de SECCOMP_IOCTL_NOTIF_ADDFD plus SECCOMP_IOCTL_NOTIF_SEND en une seule opération atomique. Lors d'une invocation réussie, le errno du processus cible sera 0 et la valeur de retour sera le numéro du descripteur de fichier qui a été alloué dans la cible. Si l'allocation du descripteur de fichier dans la cible échoue, l'appel système de la cible continue d'être bloqué jusqu'à ce qu'une réponse réussie soit envoyée.
srcfd
Ce champ doit être défini sur le numéro du descripteur de fichier dans le superviseur qui doit être dupliqué.
newfd
Ce champ détermine quel numéro de descripteur de fichier est alloué dans la cible. Si l'indicateur SECCOMP_ADDFD_FLAG_SETFD est défini, alors ce champ spécifie quel numéro de descripteur de fichier doit être alloué. Si ce numéro de descripteur de fichier est déjà ouvert dans la cible, il est atomiquement fermé et réutilisé. Si la duplication du descripteur échoue en raison d'une vérification LSM, ou si srcfd n'est pas un descripteur de fichier valide, le descripteur de fichier newfd ne sera pas fermé dans le processus cible.
Si l'indicateur SECCOMP_ADDFD_FLAG_SETFD n'est pas défini, alors ce champ doit être 0, et le noyau alloue le plus petit numéro de descripteur de fichier inutilisé dans la cible.
newfd_flags
Ce champ est un masque de bits spécifiant les indicateurs qui doivent être définis sur le descripteur de fichier reçu dans le processus cible. Actuellement, seul l'indicateur suivant est implémenté :
O_CLOEXEC
Définir l'indicateur close-on-exec sur le descripteur de fichier reçu.

En cas de succès, cet appel ioctl(2) renvoie le numéro du descripteur de fichier alloué dans la cible. En supposant que l'appel système émulé est celui qui renvoie un descripteur de fichier comme résultat de fonction (par exemple, socket(2)), cette valeur peut être utilisée comme valeur de retour (resp.val) fournie dans la réponse envoyée ultérieurement avec l'opération SECCOMP_IOCTL_NOTIF_SEND.

En cas d'erreur, -1 est renvoyé et errno est défini pour indiquer l'erreur.

Cette opération peut échouer avec les erreurs suivantes :

EBADF
L'allocation du descripteur de fichier dans la cible dépasserait la limite RLIMIT_NOFILE de la cible (voir getrlimit(2)).
EBUSY
Si l'indicateur SECCOMP_IOCTL_NOTIF_SEND est utilisé, cela signifie que l'opération ne peut pas continuer tant que d'autres requêtes SECCOMP_IOCTL_NOTIF_ADDFD ne sont pas traitées.
EINPROGRESS
La notification en espace utilisateur spécifiée dans le champ id existe mais n'a pas encore été récupérée (par un SECCOMP_IOCTL_NOTIF_RECV) ou a déjà reçu une réponse (par un SECCOMP_IOCTL_NOTIF_SEND).
EINVAL
Un indicateur invalide a été spécifié dans le champ flags ou newfd_flags, ou le champ newfd est non nul et l'indicateur SECCOMP_ADDFD_FLAG_SETFD n'a pas été spécifié dans le champ flags.
EMFILE
Le numéro de descripteur de fichier spécifié dans newfd dépasse la limite spécifiée dans /proc/sys/fs/nr_open.
ENOENT
L'appel système bloqué dans la cible a été interrompu par un gestionnaire de signaux ou la cible s'est terminée.

Voici un exemple de code (sans gestion des erreurs) qui utilise l'opération SECCOMP_ADDFD_FLAG_SETFD (ici, pour émuler un appel à openat(2)) :

int fd, removeFd;
fd = openat(req->data.args[0], path, req->data.args[2],
                req->data.args[3]);
struct seccomp_notif_addfd addfd;
addfd.id = req->id;  /* Cookie de SECCOMP_IOCTL_NOTIF_RECV */
addfd.srcfd = fd;
addfd.newfd = 0;
addfd.flags = 0;
addfd.newfd_flags = O_CLOEXEC;
targetFd = ioctl(notifyFd, SECCOMP_IOCTL_NOTIF_ADDFD, &addfd);
close(fd);          /* Plus nécessaire dans le superviseur */
struct seccomp_notif_resp *resp;
    /* Allocation de 'resp' omise */
resp->id = req->id;
resp->error = 0;        /* "Succès" */
resp->val = targetFd;
resp->flags = 0;
ioctl(notifyFd, SECCOMP_IOCTL_NOTIF_SEND, resp);

NOTES

Un exemple d'utilisation du mécanisme de notification en espace utilisateur est de permettre à un gestionnaire de conteneurs (un processus généralement exécuté avec plus de privilèges que les processus à l'intérieur du conteneur) de monter des périphériques bloc ou de créer des nœuds de périphériques pour le conteneur. Le cas d'utilisation du montage fournit un exemple où l'opération ioctl(2) SECCOMP_USER_NOTIF_FLAG_CONTINUE est utile. Après avoir reçu une notification pour l'appel système mount(2), le gestionnaire de conteneur (le "superviseur") peut distinguer une requête pour monter un système de fichiers bloc (ce qui ne serait pas possible pour un processus "cible" à l'intérieur du conteneur) et monter ce système de fichiers. Si, en revanche, le gestionnaire de conteneur détecte que l'opération pourrait être effectuée par le processus à l'intérieur du conteneur (par exemple, un montage d'un système de fichiers tmpfs(5)), il peut notifier le noyau que l'appel système mount(2) du processus cible peut continuer.

Sémantiques select()/poll()/epoll

Le descripteur de fichier retourné lorsque seccomp(2) est employé avec l'indicateur SECCOMP_FILTER_FLAG_NEW_LISTENER peut être surveillé en utilisant poll(2), epoll(7), et select(2). Ces interfaces indiquent que le descripteur de fichier est prêt comme suit :

•
Lorsqu'une notification est en attente, ces interfaces indiquent que le descripteur de fichier est lisible. Après une telle indication, un appel subséquent à SECCOMP_IOCTL_NOTIF_RECV ioctl(2) ne bloquera pas, renvoyant soit des informations sur une notification, soit échouant avec l'erreur EINTR si la cible a été tuée par un signal ou si son appel système a été interrompu par un gestionnaire de signaux.
•
Après que la notification a été reçue (c'est-à-dire par l'opération SECCOMP_IOCTL_NOTIF_RECV ioctl(2)), ces interfaces indiquent que le descripteur de fichier est accessible en écriture, signifiant qu'une réponse de notification peut être envoyée en utilisant l'opération SECCOMP_IOCTL_NOTIF_SEND ioctl(2).
•
Après que le dernier thread utilisant le filtre a terminé et a été récupéré en utilisant waitpid(2) (ou similaire), le descripteur de fichier indique une condition de fin de fichier (lisible dans select(2) ; POLLHUP/EPOLLHUP dans poll(2)/ epoll_wait(2)).

Objectifs de conception ; utilisation de SECCOMP_USER_NOTIF_FLAG_CONTINUE

T

L'intention de la fonctionnalité de notification de l'espace utilisateur est de permettre l'exécution d'appels système pour le compte de la cible. L'appel système de la cible devrait soit être géré par le superviseur, soit être autorisé à continuer normalement dans le noyau (où les politiques de sécurité standard seront appliquées).

Remarque importante : ce mécanisme ne doit pas être utilisé pour prendre des décisions de politique de sécurité concernant l'appel système, car cela serait intrinsèquement sujet aux courses pour les raisons décrites ci-dessous.

Le drapeau SECCOMP_USER_NOTIF_FLAG_CONTINUE doit être utilisé avec précaution. S'il est défini par le superviseur, l'appel système de la cible continuera. Cependant, il existe ici une course de type "time-of-check, time-of-use" (moment de la vérification, moment de l'utilisation), car un attaquant pourrait exploiter l'intervalle de temps pendant lequel la cible est bloquée en attendant la réponse "continuer" pour effectuer des actions telles que la réécriture des arguments de l'appel système.

Notez en outre qu'un notificateur d'espace utilisateur peut être contourné si les filtres existants permettent l'utilisation de seccomp(2) ou prctl(2) pour installer un filtre qui renvoie une valeur d'action ayant une priorité plus élevée que SECCOMP_RET_USER_NOTIF (voir seccomp(2)).

Il doit donc être absolument clair que le mécanisme de notification d'espace utilisateur seccomp ne peut pas être utilisé pour implémenter une politique de sécurité ! Il ne devrait jamais être utilisé que dans des scénarios où un processus plus privilégié supervise les appels système d'une cible moins privilégiée pour contourner les restrictions de sécurité imposées par le noyau lorsque le superviseur juge cela sûr. En d'autres termes, pour continuer un appel système, le superviseur doit être sûr qu'un autre mécanisme de sécurité ou le noyau lui-même bloquera suffisamment l'appel système si ses arguments sont réécrits pour quelque chose d'insécurisé.

Mises en garde concernant l'utilisation de

/proc/tid/mem La discussion ci-dessus a noté la nécessité d'utiliser l'appel ioctl(2) SECCOMP_IOCTL_NOTIF_ID_VALID lors de l'ouverture du fichier /proc/tid/mem de la cible pour éviter la possibilité d'accéder à la mémoire du mauvais processus au cas où la cible se terminerait et son ID serait recyclé par un autre thread (non lié). Cependant, l'utilisation de cette opération ioctl(2) est également nécessaire dans d'autres situations, comme expliqué dans les paragraphes suivants.

Considérez le scénario suivant, où le superviseur tente de lire l'argument de chemin d'un appel système mount(2) bloqué de la cible :

(1)
Depuis l'une de ses fonctions (func()), la cible appelle mount(2), ce qui déclenche une notification d'espace utilisateur et bloque la cible.
(2)
Le superviseur reçoit la notification, ouvre /proc/tid/mem, et effectue (avec succès) la vérification SECCOMP_IOCTL_NOTIF_ID_VALID.
(3)
La cible reçoit un signal, qui provoque l'interruption de mount(2).
(4)
Le gestionnaire de signaux s'exécute dans la cible et retourne.
(5)
Au retour du gestionnaire, l'exécution de func() reprend, et elle retourne (et peut-être d'autres fonctions sont appelées, écrasant la mémoire qui avait été utilisée pour la pile d'appels de func()).
(6)
En utilisant l'adresse fournie dans les informations de notification, le superviseur lit depuis l'emplacement mémoire de la cible qui contenait autrefois le chemin.
(7)
Le superviseur appelle maintenant mount(2) avec des octets arbitraires obtenus à l'étape précédente.

La conclusion du scénario ci-dessus est la suivante : étant donné que l'appel système bloqué de la cible peut être interrompu par un gestionnaire de signaux, le superviseur doit être écrit pour s'attendre à ce que la cible puisse abandonner son appel système à tout moment ; dans un tel événement, toute information que le superviseur a obtenue de la mémoire de la cible doit être considérée comme invalide.

Pour éviter de tels scénarios, chaque lecture de la mémoire de la cible doit être séparée de l'utilisation des octets ainsi obtenus par une vérification SECCOMP_IOCTL_NOTIF_ID_VALID. Dans l'exemple ci-dessus, la vérification serait placée entre les deux dernières étapes. Un exemple d'une telle vérification est montré dans LES EXEMPLES.

Dans la continuité de ce qui précède, il devrait être clair qu'une écriture par le superviseur dans la mémoire de la cible ne peut jamais être considérée comme sûre.

Mises en garde concernant les appels système bloquants

Supposons que la cible effectue un appel système bloquant (par exemple, accept(2)) que le superviseur devrait gérer. Le superviseur pourrait alors à son tour exécuter le même appel système bloquant.

Dans ce scénario, il est important de noter que si l'appel système de la cible est maintenant interrompu par un signal, le superviseur n'en est pas informé. Si le superviseur ne prend pas les mesures appropriées pour découvrir activement que l'appel système de la cible a été annulé, diverses difficultés peuvent survenir. En prenant l'exemple de accept(2), le superviseur pourrait rester bloqué dans son accept(2) en détenant un numéro de port que la cible (qui, après l'interruption par le gestionnaire de signaux, a peut-être fermé son socket d'écoute) pourrait s'attendre à pouvoir réutiliser dans un appel bind(2).

Par conséquent, lorsque le superviseur souhaite émuler un appel système bloquant, il doit le faire de manière à être informé si l'appel système de la cible est interrompu par un gestionnaire de signaux. Par exemple, si le superviseur exécute lui-même le même appel système bloquant, il pourrait employer un thread séparé qui utilise l'opération SECCOMP_IOCTL_NOTIF_ID_VALID pour vérifier si la cible est toujours bloquée dans son appel système. Alternativement, dans l'exemple de accept(2), le superviseur pourrait utiliser poll(2) pour surveiller à la fois le descripteur de fichier de notification (afin de découvrir quand l'appel accept(2) de la cible a été interrompu) et le descripteur de fichier d'écoute (afin de savoir quand une connexion est disponible).

Si l'appel système de la cible est interrompu, le superviseur doit veiller à libérer les ressources (par exemple, les descripteurs de fichiers) qu'il a acquises pour le compte de la cible.

Interaction avec les gestionnaires de signaux SA_RESTART

Considérez le scénario suivant :

(1)
Le processus cible a utilisé sigaction(2) pour installer un gestionnaire de signaux avec le drapeau SA_RESTART.
(2)
La cible a effectué un appel système qui a déclenché une notification seccomp d'espace utilisateur et la cible est actuellement bloquée jusqu'à ce que le superviseur envoie une réponse de notification.
(3)
Un signal est délivré à la cible et le gestionnaire de signaux est exécuté.
(4)
Lorsque le superviseur tente (si) d'envoyer une réponse de notification, l'opération ioctl(2) SECCOMP_IOCTL_NOTIF_SEND échouera avec l'erreur ENOENT.

Dans ce scénario, le noyau redémarrera l'appel système de la cible. Par conséquent, le superviseur recevra une autre notification d'espace utilisateur. Ainsi, selon le nombre de fois où l'appel système bloqué est interrompu par un gestionnaire de signaux, le superviseur peut recevoir plusieurs notifications pour la même instance d'un appel système dans la cible.

Une particularité est que le redémarrage de l'appel système tel que décrit dans ce scénario se produira même pour les appels système bloquants listés dans signal(7) qui ne seraient jamais normalement redémarrés par le drapeau SA_RESTART.

De plus, si la réponse du superviseur est un descripteur de fichier ajouté avec SECCOMP_IOCTL_NOTIF_ADDFD, alors le drapeau SECCOMP_ADDFD_FLAG_SEND peut être utilisé pour ajouter atomiquement le descripteur de fichier et renvoyer cette valeur, en s'assurant qu'aucun descripteur de fichier n'est involontairement divulgué à la cible.

BOGUES

Si une opération ioctl(2) SECCOMP_IOCTL_NOTIF_RECV est effectuée après la terminaison de la cible, alors l'appel ioctl(2) se bloque simplement (au lieu de renvoyer une erreur pour indiquer que la cible n'existe plus).

/* Envoie le descripteur de fichier 'fd' sur le socket de domaine UNIX connecté
   'sockfd'. Retourne 0 en cas de succès, ou -1 en cas d'erreur.  */
static int
sendfd(int sockfd, int fd)
{
    int             data;
    struct iovec    iov;
    struct msghdr   msgh;
    struct cmsghdr  *cmsgp;
    /* Alloue un tableau de caractères de taille appropriée pour contenir les données auxiliaires.
       Cependant, comme ce tampon est en réalité une 'struct cmsghdr', utilisez une
       union pour garantir qu'il est correctement aligné.  */
    union {
        char   buf[CMSG_SPACE(sizeof(int))];
                        /* Espace suffisamment grand pour contenir un 'int' */
        struct cmsghdr align;
    } controlMsg;
    /* Le champ 'msg_name' peut être utilisé pour spécifier l'adresse du
       socket de destination lors de l'envoi d'un datagramme.  Cependant, nous n'avons pas
       besoin d'utiliser ce champ car 'sockfd' est un socket connecté.  */
    msgh.msg_name = NULL;
    msgh.msg_namelen = 0;
    /* Sous Linux, nous devons transmettre au moins un octet de données réelles
       pour envoyer des données auxiliaires.  Nous transmettons un entier arbitraire
       dont la valeur est ignorée par recvfd().  */
    msgh.msg_iov = &iov;
    msgh.msg_iovlen = 1;
    iov.iov_base = &data;
    iov.iov_len = sizeof(int);
    data = 12345;
    /* Définit les champs 'msghdr' qui décrivent les données auxiliaires */
    msgh.msg_control = controlMsg.buf;
    msgh.msg_controllen = sizeof(controlMsg.buf);
    /* Configure les données auxiliaires décrivant le descripteur de fichier à envoyer */
    cmsgp = CMSG_FIRSTHDR(&msgh);
    cmsgp->cmsg_level = SOL_SOCKET;
    cmsgp->cmsg_type = SCM_RIGHTS;
    cmsgp->cmsg_len = CMSG_LEN(sizeof(int));
    memcpy(CMSG_DATA(cmsgp), &fd, sizeof(int));
    /* Envoie les données réelles plus les données auxiliaires */
    if (sendmsg(sockfd, &msgh, 0) == -1)
        return -1;
    return 0;
}
/* Reçoit un descripteur de fichier sur un socket de domaine UNIX connecté. Retourne
   le descripteur de fichier reçu en cas de succès, ou -1 en cas d'erreur.  */
static int
recvfd(int sockfd)
{
    int            data, fd;
    ssize_t        nr;
    struct iovec   iov;
    struct msghdr  msgh;
    /* Alloue un tampon de caractères pour les données auxiliaires.  Voir les commentaires
       dans sendfd() */
    union {
        char   buf[CMSG_SPACE(sizeof(int))];
        struct cmsghdr align;
    } controlMsg;
    struct cmsghdr *cmsgp;
    /* Le champ 'msg_name' peut être utilisé pour obtenir l'adresse du
       socket d'envoi.  Cependant, nous n'avons pas besoin de cette information.  */
    msgh.msg_name = NULL;
    msgh.msg_namelen = 0;
    /* Spécifie le tampon pour recevoir les données réelles */
    msgh.msg_iov = &iov;
    msgh.msg_iovlen = 1;
    iov.iov_base = &data;       /* Les données réelles sont un 'int' */
    iov.iov_len = sizeof(int);
    /* Définit les champs 'msghdr' qui décrivent les données auxiliaires */
    msgh.msg_control = controlMsg.buf;
    msgh.msg_controllen = sizeof(controlMsg.buf);
    /* Reçoit les données réelles plus les données auxiliaires ; les données réelles sont ignorées */
    nr = recvmsg(sockfd, &msgh, 0);
    if (nr == -1)
        return -1;
    cmsgp = CMSG_FIRSTHDR(&msgh);
    /* Vérifie la validité du 'cmsghdr' */
    if (cmsgp == NULL
        || cmsgp->cmsg_len != CMSG_LEN(sizeof(int))
        || cmsgp->cmsg_level != SOL_SOCKET
        || cmsgp->cmsg_type != SCM_RIGHTS)
    {
        errno = EINVAL;
        return -1;
    }
    /* Retourne le descripteur de fichier reçu à notre appelant */
    memcpy(&fd, CMSG_DATA(cmsgp), sizeof(int));
    return fd;
}

   que le programme BPF s'exécute sur la bonne architecture + ABI. À l'issue
   de ces instructions, l'accumulateur contient le numéro d'appel système.  */

/* installNotifyFilter() installe un filtre seccomp qui génère des
   notifications en espace utilisateur (SECCOMP_RET_USER_NOTIF) lorsque le processus
   appelle mkdir(2) ; le filtre autorise tous les autres appels système.
   La valeur de retour de la fonction est un descripteur de fichier à partir duquel les
   notifications en espace utilisateur peuvent être récupérées.  */
static int
installNotifyFilter(void)
{
    int notifyFd;
    struct sock_filter filter[] = {
        X86_64_CHECK_ARCH_AND_LOAD_SYSCALL_NR,
        /* mkdir() déclenche la notification vers le superviseur en espace utilisateur */
        BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, SYS_mkdir, 0, 1),
        BPF_STMT(BPF_RET + BPF_K, SECCOMP_RET_USER_NOTIF),
        /* Tous les autres appels système sont autorisés */
        BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),
    };
    struct sock_fprog prog = {
        .len = NITEMS(filter),
        .filter = filter,
    };
    /* Installe le filtre avec le drapeau SECCOMP_FILTER_FLAG_NEW_LISTENER ;
       en conséquence, seccomp() retourne un descripteur de fichier de notification.  */
    notifyFd = seccomp(SECCOMP_SET_MODE_FILTER,
                       SECCOMP_FILTER_FLAG_NEW_LISTENER, &prog);
    if (notifyFd == -1)
        err(EXIT_FAILURE, "seccomp-install-notify-filter");
    return notifyFd;
}
/* Ferme une paire de sockets créés par socketpair() */
static void
closeSocketPair(int sockPair[2])
{
    if (close(sockPair[0]) == -1)
        err(EXIT_FAILURE, "closeSocketPair-close-0");
    if (close(sockPair[1]) == -1)
        err(EXIT_FAILURE, "closeSocketPair-close-1");
}
/* Implémentation du processus cible. Crée un processus enfant qui :
   (1) installe un filtre seccomp avec le
       drapeau SECCOMP_FILTER_FLAG_NEW_LISTENER ;
   (2) écrit le descripteur de notification seccomp */
n descripteur de fichier retourné par
       l'étape précédente sur le socket de domaine UNIX, 'sockPair[0]';
   (3) appelle mkdir(2) pour chaque élément de 'argv'.
   La valeur de retour de la fonction dans le processus parent est le PID du processus enfant
   ; le processus enfant ne retourne pas de cette fonction.  */
static pid_t
targetProcess(int sockPair[2], char *argv[])
{
    int    notifyFd, s;
    pid_t  targetPid;
    targetPid = fork();
    if (targetPid == -1)
        err(EXIT_FAILURE, "fork");
    if (targetPid > 0)          /* Dans le processus parent, retourne le PID de l'enfant */
        return targetPid;
    /* Le processus enfant continue ici */
    printf("T: PID = %ld\n", (long) getpid());
    /* Installer le(s) filtre(s) seccomp */
    if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0))
        err(EXIT_FAILURE, "prctl");
    notifyFd = installNotifyFilter();
    /* Passer le descripteur de fichier de notification au processus de traçage sur
       un socket de domaine UNIX */
    if (sendfd(sockPair[0], notifyFd) == -1)
        err(EXIT_FAILURE, "sendfd");
    /* Les descripteurs de fichier de notification et de socket ne sont plus nécessaires dans le processus cible */
    if (close(notifyFd) == -1)
        err(EXIT_FAILURE, "close-target-notify-fd");
    closeSocketPair(sockPair);
    /* Effectuer un appel mkdir() pour chacun des arguments de la ligne de commande */
    for (char **ap = argv; *ap != NULL; ap++) {
        printf("\nT: sur le point de mkdir(\"%s\")\n", *ap);
        s = mkdir(*ap, 0700);
        if (s == -1)
            perror("T: ERREUR: mkdir(2)");
        else
            printf("T: SUCCÈS: mkdir(2) a retourné %d\n", s);
    }
    printf("\nT: arrêt\n");
    exit(EXIT_SUCCESS);
}
/* Vérifie que l'ID de notification fourni par une opération SECCOMP_IOCTL_NOTIF_RECV
   est toujours valide. Il ne sera plus valide si le processus cible s'est terminé ou
   n'est plus bloqué dans l'appel système qui a généré la notification (parce qu'il a été interrompu par un signal).
   Cette opération peut être utilisée pour des actions telles que l'accès aux fichiers /proc/PID
   dans le processus cible afin d'éviter les conditions de concurrence TOCTOU où le PID retourné par SECCOMP_IOCTL_NOTIF_RECV
   se termine et est réutilisé par un autre processus.  */
static bool
cookieIsValid(int notifyFd, uint64_t id)
{
    return ioctl(notifyFd, SECCOMP_IOCTL_NOTIF_ID_VALID, &id) == 0;
}
/* Accède à la mémoire du processus cible afin de récupérer le
   nom de chemin auquel fait référence l'argument du système 'argNum' dans
   'req->data.args[]'. Le nom de chemin est retourné dans 'path',
   un tampon de 'size' octets alloué par l'appelant.
   Retourne true si le nom de chemin est récupéré avec succès, et false
   sinon. Pour les causes possibles d'échec, voir les commentaires ci-dessous.  */
static bool
getTargetPathname(struct seccomp_notif *req, int notifyFd,
                  int argNum, char *path, size_t size)
{
    int      procMemFd;
    char     procMemPath[PATH_MAX];
    ssize_t  nread;
    snprintf(procMemPath, sizeof(procMemPath), "/proc/%d/mem", req->pid);
    procMemFd = open(procMemPath, O_RDONLY | O_CLOEXEC);
    if (procMemFd == -1)
        return false;
    /* Vérifier que le processus dont les informations sont accédées est toujours en vie
       et bloqué dans l'appel système qui a causé la notification.
       Si l'opération SECCOMP_IOCTL_NOTIF_ID_VALID (effectuée dans
       cookieIsValid()) a réussi, nous savons que le descripteur de fichier /proc/PID/mem
       que nous avons ouvert correspondait au processus pour lequel nous avons reçu une notification.
       Si ce processus se termine ensuite, alors read() sur ce descripteur de fichier retournera 0 (EOF).  */
    if (!cookieIsValid(notifyFd, req->id)) {
        close(procMemFd);
        return false;
    }
    /* Lire les octets à l'emplacement contenant l'argument du nom de chemin */
    nread = pread(procMemFd, path, size, req->data.args[argNum]);
    close(procMemFd);
    if (nread <= 0)
        return false;
    /* Vérifier à nouveau que l'ID de notification est toujours valide. Le
       cas qui nous préoccupe particulièrement ici est que juste
       avant que nous ayons récupéré le nom de chemin, l'appel système bloqué du processus cible a été interrompu par un gestionnaire de signaux, et après le retour du gestionnaire, le processus cible a repris son exécution (au-delà de l'appel système interrompu).
       Dans ce cas, nous n'avons aucune garantie sur ce que nous lisons, car la mémoire du processus cible a pu être arbitrairement modifiée par des opérations ultérieures.  */
    if (!cookieIsValid(notifyFd, req->id)) {
        perror("\tS: la vérification de l'ID de notification a échoué !!!");
        return false;
    }
    /* Même si l'appel système du processus cible n'a pas été interrompu par un signal,
       nous n'avons aucune garantie sur ce qui se trouvait dans la mémoire du processus cible.
       (La mémoire a pu être modifiée par un autre thread, ou même par un processus attaquant externe.) Nous traitons donc
       le tampon retourné par pread() comme une entrée non fiable. Le tampon doit contenir un octet nul de terminaison ; sinon, nous déclencherons une erreur pour le processus cible.  */
    if (strnlen(path, nread) < nread)
        return true;
    return false;
}
/* Allouer des tampons pour les structures de requête et de réponse de notification seccomp en espace utilisateur.
   Il incombe à l'appelant de libérer les tampons retournés via 'req' et 'resp'.  */
static void
allocSeccompNotifBuffers(struct seccomp_notif **req,
                         struct seccomp_notif_resp **resp,
                         struct seccomp_notif_sizes *sizes)
{
    size_t  resp_size;
    /* Découvrir les tailles des structures utilisées pour recevoir
       les notifications et envoyer les réponses de notification, et allouer
       des tampons de ces tailles.  */
    if (seccomp(SECCOMP_GET_NOTIF_SIZES, 0, sizes) == -1)
        err(EXIT_FAILURE, "seccomp-SECCOMP_GET_NOTIF_SIZES");
    *req = malloc(sizes->seccomp_notif);
    if (*req == NULL)
        err(EXIT_FAILURE, "malloc-seccomp_notif");
    /* Lors de l'allocation du tampon de réponse, nous devons tenir compte du fait
       que le binaire en espace utilisateur peut avoir été construit avec des en-têtes en espace utilisateur
       où 'struct seccomp_notif_resp' est plus grand que le
       tampon de réponse attendu par le noyau (plus ancien). Par conséquent, nous
       allouons un tampon qui est le maximum des deux tailles. Ceci
       garantit que si le superviseur place des octets dans la structure de réponse
       qui sont au-delà de la taille de réponse attendue par le noyau,
       alors le superviseur ne touche pas une adresse mémoire invalide.  */
    resp_size = sizes->seccomp_notif_resp;
    if (sizeof(struct seccomp_notif_resp) > resp_size)
        resp_size = sizeof(struct seccomp_notif_resp);
    *resp = malloc(resp_size);
    if (*resp == NULL)
        err(EXIT_FAILURE, "malloc-seccomp_notif_resp");
}
/* Gérer les notifications qui arrivent via le descripteur de fichier SECCOMP_RET_USER_NOTIF,
   'notifyFd'.  */
static void
handleNotifications(int notifyFd)
{
    bool                        pathOK;
    char                        path[PATH_MAX];
    struct seccomp_notif        *req;
    struct seccomp_notif_resp   *resp;
    struct seccomp_notif_sizes  sizes;
    allocSeccompNotifBuffers(&req, &resp, &sizes);
    /* Boucle gérant les notifications */
    for (;;) {
        /* Attendre la prochaine notification, retournant les informations dans '*req' */
        memset(req, 0, sizes.seccomp_notif);
        if (ioctl(notifyFd, SECCOMP_IOCTL_NOTIF_RECV, req) == -1) {
            if (errno == EINTR)
                continue;
            err(EXIT_FAILURE, "\tS: ioctl-SECCOMP_IOCTL_NOTIF_RECV");
        }
        printf("\tS: notification reçue (ID %#llx) pour PID %d\n",
               req->id, req->pid);
        /* Le seul appel système qui peut générer un événement de notification
           est mkdir(2). Néanmoins, nous vérifions que l'appel système notifié
           est bien mkdir() comme une sorte de préparation à l'avenir de ce
           code au cas où le filtre seccomp serait modifié plus tard pour
           générer des notifications pour d'autres appels système.  */
        if (req->data.nr != SYS_mkdir) {
            printf("\tS: la notification contenait un numéro d'appel système "
                   "inattendu ; au revoir !!!\n");
            exit(EXIT_FAILURE);
        }
        pathOK = getTargetPathname(req, notifyFd, 0, path, sizeof(path));
        /* Pré-remplir certains champs de la réponse */
        resp->id = req->id;     /* La réponse inclut l'ID de notification */
        resp->flags = 0;
        resp->val = 0;
        /* Si getTargetPathname() a échoué, déclencher une réponse d'erreur EINVAL
           (l'envoi de cette réponse peut entraîner une erreur si l'échec s'est produit parce que l'ID de notification n'était plus valide) ; si le répertoire est dans /tmp, alors le créer au nom du superviseur ; si le nom de chemin commence par '.', dire au noyau de laisser le processus cible exécuter le mkdir() ;
           sinon, donner une erreur pour un nom de répertoire dans tout autre
           emplacement.  */
        if (!pathOK) {
            resp->error = -EINVAL;
            printf("\tS: usurpation d'erreur pour nom de chemin invalide (%s)\n",
                   strerror(-resp->error));
        } else if (strncmp(path, "/tmp/", strlen("/tmp/")) == 0) {
            printf("\tS: exécution : mkdir(\"%s\", %#llo)\n",
                   path, req->data.args[1]);
            if (mkdir(path, req->data.args[1]) == 0) {
                resp->error = 0;            /* "Succès" */
                resp->val = strlen(path);   /* Utilisé comme valeur de retour de
                                               mkdir() dans le processus cible */
                printf("\tS: succès ! retour usurpé = %lld\n",
                       resp->val);
            } else {
                /* Si mkdir() a échoué dans le superviseur, renvoyer l'erreur
                   au processus cible */
                resp->error = -errno;
                printf("\tS: échec ! (errno = %d; %s)\n", errno,
                       strerror(errno));
            }
        } else if (strncmp(path, "./", strlen("./")) == 0) {
            resp->error = resp->val = 0;
            resp->flags = SECCOMP_USER_NOTIF_FLAG_CONTINUE;
            printf("\tS: le processus cible peut exécuter l'appel système\n");
        } else {
            resp->error = -EOPNOTSUPP;
            printf("\tS: réponse d'erreur usurpée (%s)\n",
                   strerror(-resp->error));
        }
        /* Envoyer une réponse à la notification */
        printf("\tS: envoi de la réponse "
               "(flags = %#x; val = %lld; error = %d)\n",
               resp->flags, resp->val, resp->error);
        if (ioctl(notifyFd, SECCOMP_IOCTL_NOTIF_SEND, resp) == -1) {
            if (errno == ENOENT)
                printf("\tS: la réponse a échoué avec ENOENT ; "
                       "l'appel système du processus cible a peut-être été "
                       "interrompu par un signal ?\n");
            else
                perror("ioctl-SECCOMP_IOCTL_NOTIF_SEND");
        }
        /* Si le nom de chemin est juste "/bye", alors le superviseur sort de
           la boucle et se termine. Ceci nous permet de voir ce qui se passe
           si le processus cible effectue d'autres appels à mkdir(2).  */
        if (strcmp(path, "/bye") == 0)
            break;
    }
    free(req);
    free(resp);
    printf("\tS: arrêt **********\n");
    exit(EXIT_FAILURE);
}
