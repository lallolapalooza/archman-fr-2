srun(1) Commandes Slurm srun(1)

NOM

srun - Exécuter des jobs parallèles

SYNTAXE

srun [OPTIONS(0)... [executable(0) [args(0)...]]] [ : [OPTIONS(N)...]] executable(N) [args(N)...]

Les options définissent plusieurs jobs dans un job hétérogène co-planifié. Pour plus de détails sur les jobs hétérogènes, voir le document
https://slurm.schedmd.com/heterogeneous_jobs.html

DESCRIPTION

Exécute un job parallèle sur un cluster géré par Slurm. Si nécessaire, srun créera d'abord une allocation de ressources dans laquelle exécuter le job parallèle.

Le document suivant décrit l'influence des diverses options sur l'allocation des CPU aux jobs et aux tâches.
https://slurm.schedmd.com/cpu_management.html

VALEUR DE RETOUR

srun retournera le code de sortie le plus élevé de toutes les tâches exécutées ou le signal le plus élevé (avec le bit de poids fort défini dans un entier de 8 bits - par exemple 128 + signal) d'une tâche qui s'est terminée avec un signal.
La valeur 253 est réservée pour les erreurs de manque de mémoire.

RÉSOLUTION DU CHEMIN DE L'EXÉCUTABLE

L'exécutable est résolu dans l'ordre suivant :

1. Si l'exécutable commence par ".", alors le chemin est construit comme suit : répertoire de travail actuel / exécutable
2. Si l'exécutable commence par un "/", alors le chemin est considéré comme absolu.
3. Si l'exécutable peut être résolu via le PATH. Voir path_resolution(7).
4. Si l'exécutable se trouve dans le répertoire de travail actuel.

Le répertoire de travail actuel est le répertoire de travail du processus appelant, sauf si l'argument --chdir est passé, ce qui remplacera le répertoire de travail actuel.

OPTIONS

-A, --account=<compte>
Facturer les ressources utilisées par ce job au compte spécifié. Le compte est une chaîne arbitraire. Le nom du compte peut être modifié après la soumission du job en utilisant la commande scontrol. Cette option s'applique aux allocations de job.
--acctg-freq=<type_donnees>=<intervalle>[,<type_donnees>=<intervalle>...]
Définir les intervalles d'échantillonnage de la comptabilité et du profilage du job en secondes. Cela peut être utilisé pour remplacer le paramètre JobAcctGatherFrequency dans le fichier slurm.conf. <type_donnees>=<intervalle> spécifie l'intervalle d'échantillonnage des tâches pour le plugin jobacct_gather ou un intervalle d'échantillonnage pour un type de profilage par le plugin acct_gather_profile. Plusieurs paires <type_donnees>=<intervalle> séparées par des virgules peuvent être spécifiées. Les valeurs type_donnees supportées sont :
tache
Intervalle d'échantillonnage pour les plugins jobacct_gather et pour le profilage des tâches par le plugin acct_gather_profile.
NOTE : Cette fréquence est utilisée pour surveiller l'utilisation de la mémoire. Si les limites de mémoire sont appliquées, la fréquence la plus élevée qu'un utilisateur puisse demander est celle configurée dans le fichier slurm.conf. Elle ne peut pas être désactivée.
energie
Intervalle d'échantillonnage pour le profilage énergétique à l'aide du plugin acct_gather_energy.
reseau
Intervalle d'échantillonnage pour le profilage infiniband à l'aide du plugin acct_gather_interconnect.
systeme_de_fichiers
Intervalle d'échantillonnage pour le profilage du système de fichiers à l'aide du plugin acct_gather_filesystem.

La valeur par défaut pour l'intervalle d'échantillonnage des tâches est de 30 secondes. La valeur par défaut pour tous les autres intervalles est 0. Un intervalle de 0 désactive l'échantillonnage du type spécifié. Si l'intervalle d'échantillonnage des tâches est 0, les informations de comptabilité ne sont collectées qu'à la fin du job (réduisant l'interférence de Slurm avec le job).
Des valeurs plus petites (non nulles) ont un impact plus important sur les performances du job, mais une valeur de 30 secondes n'est probablement pas perceptible pour les applications comportant moins de 10 000 tâches. Cette option s'applique aux allocations de jobs.

--bb=<spec>
Spécification du burst buffer. La forme de la spécification dépend du système. Voir également --bbf. Cette option s'applique aux allocations de job. Lorsque l'option --bb est utilisée, Slurm analyse cette option et crée un fichier script de burst buffer temporaire qui est utilisé en interne par les plugins de burst buffer. Voir le guide du burst buffer de Slurm pour plus d'informations et d'exemples :
https://slurm.schedmd.com/burst_buffer.html
--bbf=<nom_fichier>
Chemin du fichier contenant la spécification du burst buffer. La forme de la spécification dépend du système. Voir également --bb. Cette option s'applique aux allocations de job. Voir le guide du burst buffer de Slurm pour plus d'informations et d'exemples :
https://slurm.schedmd.com/burst_buffer.html
--bcast[=<chemin_destination>]
Copier le fichier exécutable sur les nœuds de calcul alloués. Si un nom de fichier est spécifié, copier l'exécutable vers le chemin du fichier de destination spécifié. Si le chemin spécifié se termine par '/' il est traité comme un répertoire de destination, et le nom du fichier de destination sera slurm_bcast_<id_job>.<id_etape>_<nom_noeud>. Si aucun chemin_destination n'est spécifié et que le paramètre DestDir de slurm.conf est configuré, alors il est utilisé, et le nom du fichier suit le modèle ci-dessus. Si rien de ce qui précède n'est spécifié, alors --chdir est utilisé, et le nom du fichier suit également ce modèle. Par exemple, "srun --bcast=/tmp/mon_fichier -N3 a.out" copiera le fichier "a.out" de votre répertoire actuel vers le fichier "/tmp/mon_fichier" sur chacun des trois nœuds de calcul alloués et exécutera ce fichier. Cette option s'applique aux allocations d'étapes.
--bcast-exclude={AUCUN|<chemin_exclusion>[,<chemin_exclusion>...]}
Liste séparée par des virgules de chemins de répertoires absolus à exclure lors de la détection automatique et de la diffusion des dépendances d'objets partagés exécutables via --bcast. Si le mot-clé "AUCUN" est configuré, aucun chemin de répertoire ne sera exclu. La valeur par défaut est celle de BcastExclude dans slurm.conf et cette option la remplace. Voir également --bcast et --send-libs.
-b, --begin=<heure>
Retarder le démarrage de ce job jusqu'à l'heure spécifiée. Il accepte des heures de la forme HH:MM:SS pour exécuter un job à une heure spécifique de la journée (les secondes sont optionnelles). (Si cette heure est déjà passée, le lendemain est supposé.) Vous pouvez également spécifier minuit, midi, onze heures (11h), fika (15h) ou thé (16h) et vous pouvez indiquer le jour où le job sera exécuté, en spécifiant une date de la forme MMJJAA ou MM/JJ/AA AAAA-MM-JJ. Combinez date et heure en utilisant le format suivant AAAA-MM-JJ[THH:MM[:SS]]. Vous pouvez également donner des heures comme maintenant + compte unités_temps, où les unités_temps peuvent être secondes (par défaut), minutes, heures, jours, ou semaines.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

nd vous pouvez indiquer à Slurm d'exécuter le travail aujourd'hui avec le mot-clé today et de l'exécuter demain avec le mot-clé tomorrow. La valeur peut être modifiée après la soumission du travail à l'aide de la commande scontrol. Par exemple : 
   --begin=16:00
   --begin=now+1hour
   --begin=now+60           (secondes par défaut)
   --begin=2010-01-20T12:34:00

Notes sur les spécifications de date/heure :
- Bien que le champ 'secondes' de la spécification de temps HH:MM:SS soit autorisé par le code, notez que le temps de scrutation du planificateur Slurm n'est pas assez précis pour garantir le déclenchement du travail à la seconde près. Le travail sera éligible pour commencer lors de la prochaine scrutation suivant l'heure spécifiée. L'intervalle de scrutation exact dépend du planificateur Slurm (par exemple, 60 secondes avec le planificateur par défaut sched/builtin).
- Si aucune heure (HH:MM:SS) n'est spécifiée, la valeur par défaut est (00:00:00).
- Si une date est spécifiée sans année (par exemple, MM/JJ) alors l'année en cours est supposée, sauf si la combinaison MM/JJ et HH:MM:SS est déjà passée pour cette année, auquel cas l'année suivante est utilisée.
Cette option s'applique aux allocations de travaux.

-D, --chdir=<chemin>
Faire en sorte que les processus distants effectuent un chdir vers chemin avant de commencer l'exécution. Par défaut, il s'agit de faire un chdir vers le répertoire de travail actuel du processus srun. Le chemin peut être spécifié en tant que chemin absolu ou chemin relatif par rapport au répertoire où la commande est exécutée. Cette option s'applique aux allocations de travaux.
--cluster-constraint=<liste>
Spécifie les fonctionnalités qu'un cluster fédéré doit posséder pour qu'un travail frère lui soit soumis. Slurm tentera de soumettre un travail frère à un cluster s'il possède au moins une des fonctionnalités spécifiées.
-M, --clusters=<chaîne>
Clusters auxquels adresser les commandes. Plusieurs noms de clusters peuvent être séparés par des virgules. Le travail sera soumis au cluster unique qui offre le délai de début de travail le plus précoce. La valeur par défaut est le cluster actuel. Une valeur de 'all' interrogera tous les clusters pour une exécution. Notez l'option --export pour contrôler les variables d'environnement exportées entre les clusters. Cette option s'applique uniquement aux allocations de travaux. Notez que le slurmdbd doit être en cours d'exécution pour que cette option fonctionne correctement, sauf en cas de fédération configurée avec FederationParameters=fed_display.
--comment=<chaîne>
Un commentaire arbitraire. Cette option s'applique aux allocations de travaux.
--compress[=type]
Compresse le fichier avant de l'envoyer aux hôtes de calcul. L'argument optionnel spécifie la bibliothèque de compression de données à utiliser. La valeur par défaut est BcastParameters Compression= si défini ou "lz4" sinon. Les valeurs prises en charge sont "lz4". Certaines bibliothèques de compression peuvent ne pas être disponibles sur certains systèmes. À utiliser avec l'option --bcast. Cette option s'applique aux allocations d'étapes.
--consolidate-segments
Assure que tous les segments de l'allocation seront consolidés en un seul bloc agrégé de niveau supérieur.

Cette option s'applique aux allocations de travaux. NOTE : Cette option ne fonctionnera qu'avec le plugin topology/block.

-C, --constraint=<liste>
Les nœuds peuvent avoir des fonctionnalités qui leur sont assignées par l'administrateur Slurm. Les utilisateurs peuvent spécifier quelles sont ces fonctionnalités requises par leur travail en utilisant l'option de contrainte. Si vous recherchez des contraintes 'douces', consultez --prefer pour plus d'informations. Seuls les nœuds ayant des fonctionnalités correspondant aux contraintes du travail seront utilisés pour satisfaire la demande. Plusieurs contraintes peuvent être spécifiées avec ET, OU, OU correspondant, comptes de ressources, etc. (certains opérateurs ne sont pas pris en charge sur tous les types de systèmes).

NOTE : Les fonctionnalités modifiables sont des fonctionnalités définies par un plugin NodeFeatures.

Les options --constraint prises en charge incluent :

Nom Unique
Seuls les nœuds possédant la fonctionnalité spécifiée seront utilisés. Par exemple, --constraint="intel"
Nombre de Nœuds
Une demande peut spécifier le nombre de nœuds nécessaires avec une certaine fonctionnalité en ajoutant un astérisque et le nombre après le nom de la fonctionnalité. Par exemple, --nodes=16 --constraint="graphics*4" indique que le travail nécessite 16 nœuds et qu'au moins quatre de ces nœuds doivent avoir la fonctionnalité "graphics". Si vous demandez plus d'une fonctionnalité et utilisez des comptes de nœuds, la demande doit être entourée de crochets.

NOTE : Cette option n'est pas prise en charge par le plugin helpers NodeFeatures. Les travaux hétérogènes peuvent être utilisés à la place.

ET
Seuls les nœuds possédant toutes les fonctionnalités spécifiées seront utilisés. L'esperluette est utilisée pour un opérateur ET. Par exemple, --constraint="intel&gpu"
OU
Seuls les nœuds possédant au moins une des fonctionnalités spécifiées seront utilisés. La barre verticale est utilisée pour un opérateur OU. Si des fonctionnalités modifiables ne sont pas demandées, les nœuds de l'allocation peuvent avoir des fonctionnalités différentes. Par exemple, salloc -N2 --constraint="intel|amd" peut aboutir à une allocation de travail où un nœud a la fonctionnalité intel et l'autre nœud a la fonctionnalité amd. Cependant, si l'expression contient une fonctionnalité modifiable, tous les opérateurs OU sont automatiquement traités comme des OU correspondants afin que tous les nœuds de l'allocation de travail aient le même ensemble de fonctionnalités. Par exemple, salloc -N2 --constraint="foo|bar&baz" Le travail se voit allouer deux nœuds où les deux nœuds ont foo, ou bar et baz (un ou deux nœuds pourraient avoir foo, bar et baz). Le plugin helpers NodeFeatures trouve le premier ensemble de fonctionnalités de nœuds qui correspond à tous les nœuds de l'allocation de travail ; ces fonctionnalités sont définies comme des fonctionnalités actives sur le nœud et transmises à RebootProgram (voir slurm.conf(5)) et au script helper (voir helpers.conf(5)). Dans ce cas, le plugin helpers utilise le premier des "foo" ou "bar,baz" qui correspond aux deux nœuds de l'allocation de travail.
OU Correspondant
Si une seule option parmi un ensemble d'options possibles doit être utilisée pour tous les nœuds alloués, utilisez l'opérateur OU et encadrez les options de crochets. Par exemple, --constraint="[rack1|rack2|rack3|rack4]" pourrait être utilisé pour spécifier que tous les nœuds doivent être alloués sur un seul rack du cluster, mais n'importe lequel de ces quatre racks peut être utilisé.
Comptes Multiples
Des comptes spécifiques de plusieurs ressources peuvent être spécifiés en utilisant l'opérateur ET et en encadrant les options de crochets. Par exemple, --constraint="[rack1*2&rack2*4]" pourrait être utilisé pour spécifier que deux nœuds doivent être alloués parmi les nœuds ayant la fonctionnalité "rack1" et quatre nœuds doivent être alloués parmi les nœuds ayant la fonctionnalité "rack2".

NOTE : Cette option n'est pas prise en charge par le plugin helpers NodeFeatures.

NOTE : Les comptes multiples peuvent entraîner l'allocation de travaux avec une disposition réseau non optimale.

Crochets
Les crochets peuvent être utilisés pour indiquer que vous recherchez un ensemble de nœuds avec les différentes exigences contenues dans les crochets. Par exemple, --constraint="[(rack1|rack2)*1&(rack3)*2]" vous obtiendra un nœud avec les fonctionnalités "rack1" ou "rack2" et deux nœuds avec la fonctionnalité "rack3". Si vous demandez plus d'une fonctionnalité et utilisez des comptes de nœuds, la demande doit être entourée de crochets.

NOTE : Les crochets sont réservés uniquement pour la syntaxe Comptes Multiples et OU Correspondant. Les opérateurs ET nécessitent un compte pour chaque fonctionnalité à l'intérieur des crochets (c'est-à-dire " [quad*2&hemi*1]"). Slurm n'autorisera qu'un seul ensemble de contraintes entre crochets par travail.

NOTE : Les crochets ne sont pas pris en charge par le plugin helpers NodeFeatures. Le OU correspondant peut être demandé sans crochets en utilisant le caractère de barre verticale avec au moins une fonctionnalité modifiable.

Parenthèses
Les parenthèses peuvent être utilisées pour regrouper des fonctionnalités de nœuds similaires. Par exemple, --constraint="[(knl&snc4&flat)*4&haswell*1]" pourrait être utilisé pour spécifier que quatre nœuds avec les fonctionnalités "knl", "snc4" et "flat" plus un nœud avec la fonctionnalité "haswell" sont requis. Les parenthèses peuvent également être utilisées pour regrouper des opérations. Sans parenthèses, les fonctionnalités des nœuds sont analysées strictement de gauche à droite. Par exemple, --constraint="foo&bar|baz" demande des nœuds avec foo et bar, ou baz. --constraint="foo|bar&baz" demande des nœuds avec foo et baz, ou bar et baz (notez comment baz a été mis en ET avec tout). --constraint="foo&(bar|baz)" demande des nœuds avec foo et au moins un des bar ou baz. NOT E : OU dans les parenthèses ne doit pas être utilisé avec un plugin KNL NodeFeatures mais est pris en charge par les assistants du plugin NodeFeatures.
AVERTISSEMENT : Lorsque srun est exécuté depuis salloc ou sbatch, la valeur de contrainte ne peut contenir qu'un seul nom de fonctionnalité. Aucun des autres opérateurs n'est actuellement pris en charge pour les étapes de job.
Cette option s'applique aux allocations de jobs et d'étapes.
--container=<chemin_vers_conteneur>
Chemin absolu du bundle de conteneur OCI.
--container-id=<id_conteneur>
Nom unique pour le conteneur OCI.
--contiguous
Si défini, les nœuds alloués doivent former un ensemble contigu.

NOTE : Cette option ne fonctionnera qu'avec le plugin topology/flat. Les autres plugins de topologie modifient l'ordre des nœuds et empêchent cette option de prendre effet. Cette option s'applique aux allocations de jobs.

-S, --core-spec=<nombre>
Nombre de cœurs spécialisés par nœud réservés par le job pour les opérations système et non utilisés par l'application. Si AllowSpecResourcesUsage est activé, un job peut remplacer le CoreSpecCount de tous ses nœuds alloués avec cette option. Les cœurs spécialisés remplacés resteront réservés aux processus système. Le job obtiendra une allocation --exclusive implicite pour le reste des cœurs sur les nœuds, ce qui permettra aux processus du job d'utiliser (et d'être facturés pour) tous les cœurs sur les nœuds, à l'exception des cœurs spécialisés remplacés. Cette option ne peut pas être utilisée avec l'option --thread-spec.

NOTE : Définir explicitement la valeur des cœurs spécialisés d'un job active implicitement l'option --exclusive.

NOTE : Cette option peut avoir un impact implicite sur le nombre de tâches si -n n'a pas été spécifié.

Cette option s'applique aux allocations de jobs.

--cores-per-socket=<cœurs>
Restreint la sélection des nœuds aux nœuds ayant au moins le nombre spécifié de cœurs par socket. Voir les informations supplémentaires sous l'option -B ci-dessus lorsque le plugin task/affinity est activé. Cette option s'applique aux allocations de jobs.
--cpu-bind=[{quiet|verbose},]<type>
Lier les tâches aux CPU. Utilisé uniquement lorsque le plugin task/affinity est activé. NOTE : Pour que Slurm rapporte toujours le binding CPU sélectionné pour toutes les commandes exécutées dans un shell, vous pouvez activer le mode verbose en définissant la variable d'environnement SLURM_CPU_BIND sur "verbose".

Les variables d'environnement informatives suivantes sont définies lorsque --cpu-bind est utilisé :

SLURM_CPU_BIND_VERBOSE
SLURM_CPU_BIND_TYPE
SLURM_CPU_BIND_LIST

Consultez la section ENVIRONNEMENT VARIABLES pour une description plus détaillée des variables SLURM_CPU_BIND individuelles. Ces variables ne sont disponibles que si le plugin task/affinity est configuré.

Lors de l'utilisation de --cpus-per-task pour exécuter des tâches multithreads, soyez conscient que le binding CPU est hérité du parent du processus. Cela signifie que la tâche multithread devrait spécifier ou effacer elle-même le binding CPU pour éviter que tous les threads de la tâche multithread n'utilisent le même masque/CPU que le parent. Alternativement, des masques "fat" (masques qui spécifient plus d'un CPU autorisé) pourraient être utilisés pour les tâches afin de fournir plusieurs CPU pour les tâches multithreads.

Notez qu'une étape de job peut être allouée à différents nombres de CPU sur chaque nœud ou se voir allouer des CPU ne commençant pas à l'emplacement zéro. Par conséquent, l'une des options qui génèrent automatiquement le binding des tâches est recommandée. Les masques ou bindings spécifiés explicitement ne sont honorés que lorsque l'étape de job a reçu tous les CPU disponibles sur le nœud.

Lier une tâche à un domaine de localité NUMA signifie lier la tâche à l'ensemble des CPU appartenant au domaine de localité NUMA ou au "nœud NUMA". Si des options de domaine de localité NUMA sont utilisées sur des systèmes sans support NUMA, alors chaque socket est considéré comme un domaine de localité.

Si l'option --cpu-bind n'est pas utilisée, le mode de binding par défaut dépendra de la configuration de Slurm et de l'allocation des ressources de l'étape. Si tous les nœuds alloués ont le même mode CpuBind configuré, celui-ci sera utilisé. Sinon, si la Partition du job a un mode CpuBind configuré, celui-ci sera utilisé. Sinon, si Slurm a une valeur TaskPluginParam configurée, ce mode sera utilisé. Sinon, un binding automatique sera effectué comme décrit ci-dessous.

Binding automatique
S'applique uniquement lorsque task/affinity est activé. Si l'allocation de l'étape de job inclut une allocation avec un nombre de sockets, de cœurs ou de threads égal au nombre de tâches multiplié par cpus-per-task, alors les tâches seront par défaut liées aux ressources appropriées (binding automatique). Désactivez ce mode de fonctionnement en définissant explicitement "--cpu-bind=none". Utilisez TaskPluginParam=autobind=[threads|cores|sockets] pour définir un binding CPU par défaut si le "binding automatique" ne trouve pas de correspondance.
Les options prises en charge incluent :
q[uiet]
Lier silencieusement avant l'exécution de la tâche (par défaut)
v[erbose]
Rapporter verbosement le binding avant l'exécution de la tâche
no[ne]
Ne pas lier les tâches aux CPU (par défaut, sauf si le binding automatique est appliqué)
map_cpu:<liste>
Lier en définissant des masques CPU sur les tâches (ou les rangs) comme spécifié où <liste> est <cpu_id_pour_tâche_0>,<cpu_id_pour_tâche_1>,... Si le nombre de tâches (ou de rangs) dépasse le nombre d'éléments dans cette liste, les éléments de la liste seront réutilisés au besoin en commençant par le début de la liste. Pour simplifier la prise en charge des grands nombres de tâches, les listes peuvent suivre un mappage avec un astérisque et un nombre de répétitions. Par exemple "map_cpu:0*4,3*4".
mask_cpu:<liste>
Lier en définissant des masques CPU sur les tâches (ou les rangs) comme spécifié où <liste> est <masque_cpu_pour_tâche_0>,<masque_cpu_pour_tâche_1>,... Le mappage est spécifié pour un nœud et le même mappage est appliqué aux tâches sur chaque nœud (c'est-à-dire que l'ID de tâche le plus bas sur chaque nœud est mappé au premier masque spécifié dans la liste, etc.). Les masques CPU sont toujours interprétés comme des valeurs hexadécimales mais peuvent être précédés d'un '0x' optionnel. Si le nombre de tâches (ou de rangs) dépasse le nombre d'éléments dans cette liste, les éléments de la liste seront réutilisés au besoin en commençant par le début de la liste. Pour simplifier la prise en charge des grands nombres de tâches, les listes peuvent suivre un mappage avec un astérisque et un nombre de répétitions. Par exemple "mask_cpu:0x0f*4,0xf0*4".
rank_ldom
Lier à un domaine de localité NUMA par rang. Non pris en charge à moins que le nœud entier ne soit alloué au job.
map_ldom:<liste>
Lier en mappant les ID de domaine de localité NUMA aux tâches comme spécifié où <liste> est <ldom1>,<ldom2>,...<ldomN>. Les ID de domaine de localité sont interprétés comme des valeurs décimales à moins qu'ils ne soient précédés de '0x', auquel cas ils sont interprétés comme des valeurs hexadécimales. Non pris en charge à moins que le nœud entier ne soit alloué au job.
mask_ldom:<liste>
Lier en définissant des masques de domaine de localité NUMA sur les tâches comme spécifié où <liste> est <masque1>,<masque2>,...<masqueN>. Les masques de domaine de localité NUMA sont toujours interprétés comme des valeurs hexadécimales mais peuvent être précédés d'un '0x' optionnel.
sockets
Générer automatiquement des masques liant les tâches aux sockets. Seuls les CPU du socket alloué au job seront utilisés. Si le nombre de tâches diffère du nombre de sockets alloués, cela peut entraîner un binding sous-optimal.
cores
Générer automatiquement des masques liant les tâches aux cœurs. Si le nombre de tâches diffère du nombre de cœurs alloués, cela peut entraîner un binding sous-optimal.
threads
Générer automatiquement des masques liant les tâches aux threads. Si le nombre de tâches diffère du nombre de threads alloués, cela peut entraîner un binding sous-optimal.
ldoms
Générer automatiquement des masques liant les tâches aux domaines de localité NUMA. Si le nombre de tâches diffère du nombre de domaines de localité alloués, cela peut entraîner un binding sous-optimal.
dt>
aide
Afficher le message d'aide pour cpu-bind
Cette option s'applique aux allocations de travaux et d'étapes.
--cpu-freq=<p1>[-p2][:p3]

Demande que l'étape de travail initiée par cette commande srun soit exécutée à une fréquence demandée si possible, sur les CPUs sélectionnés pour l'étape sur les nœuds de calcul.

p1 peut être [#### | low | medium | high | highm1] ce qui définira la vitesse de mise à l'échelle de la fréquence à la valeur correspondante, et définira le gouverneur de mise à l'échelle de la fréquence à UserSpace. Voir ci-dessous pour la définition des valeurs.

p1 peut être [Conservative | OnDemand | Performance | PowerSave] ce qui définira le gouverneur de mise à l'échelle à la valeur correspondante. Le gouverneur doit figurer dans la liste définie par l'option slurm.conf CpuFreqGovernors.

Lorsque p2 est présent, p1 sera la fréquence minimale de mise à l'échelle et p2 sera la fréquence maximale de mise à l'échelle. Dans ce cas, le gouverneur p3 ou CpuFreqDef ne peut pas être UserSpace car il ne prend pas en charge une plage.

p2 peut être [#### | medium | high | highm1]. p2 doit être supérieur à p1 et est incompatible avec le gouverneur UserSpace.

p3 peut être [Conservative | OnDemand | Performance | PowerSave | SchedUtil | UserSpace] ce qui définira le gouverneur à la valeur correspondante.

Si p3 est UserSpace, la vitesse de mise à l'échelle de la fréquence, la fréquence maximale de mise à l'échelle et la fréquence minimale de mise à l'échelle seront définies statiquement à la valeur définie par p1.

Toute fréquence demandée inférieure à la fréquence minimale disponible sera arrondie à la fréquence minimale disponible. De même, toute fréquence demandée supérieure à la fréquence maximale disponible sera arrondie à la fréquence maximale disponible.

Le paramètre CpuFreqDef dans slurm.conf sera utilisé pour définir le gouverneur en l'absence de p3. S'il n'y a pas de CpuFreqDef, le gouverneur par défaut sera d'utiliser le gouverneur actuel du système défini dans chaque cpu. La spécification d'une plage sans CpuFreqDef ou d'un gouverneur spécifique n'est donc pas autorisée.

Les valeurs acceptables à l'heure actuelle incluent :

####
fréquence en kilohertz
Low
la fréquence la plus basse disponible
High
la fréquence la plus élevée disponible
HighM1
(high moins un) sélectionnera la fréquence disponible la plus élevée suivante
Medium
tente de définir une fréquence au milieu de la plage disponible
Conservative
tente d'utiliser le gouverneur CPU Conservative
OnDemand
tente d'utiliser le gouverneur CPU OnDemand (la valeur par défaut)
Performance
tente d'utiliser le gouverneur CPU Performance
PowerSave
tente d'utiliser le gouverneur CPU PowerSave
UserSpace
tente d'utiliser le gouverneur CPU UserSpace

La variable d'environnement informative suivante est définie dans l'étape de travail lorsque l'option --cpu-freq est demandée.

        SLURM_CPU_FREQ_REQ

Cette variable d'environnement peut également être utilisée pour fournir la valeur de la demande de fréquence CPU si elle est définie lorsque la commande 'srun' est émise. Le --cpu-freq sur la ligne de commande remplacera la valeur de la variable d'environnement. La forme dans la variable d'environnement est la même que sur la ligne de commande. Voir la section VARIABLES D'ENVIRONNEMENT pour une description de la variable SLURM_CPU_FREQ_REQ.

NOTE : Ce paramètre est traité comme une demande, pas comme une exigence. Si le nœud de l'étape de travail ne prend pas en charge la définition de la fréquence CPU, ou si la valeur demandée est en dehors des limites des fréquences légales, une erreur est enregistrée, mais l'étape de travail est autorisée à continuer.

NOTE : Définir la fréquence uniquement pour les CPUs de l'étape de travail implique que les tâches sont confinées à ces CPUs. Si le confinement des tâches (c'est-à-dire si le plugin de tâche task/affinity est activé, ou si le plugin de tâche task/cgroup est activé avec "ConstrainCores=yes" défini dans cgroup.conf) n'est pas configuré, ce paramètre est ignoré.

NOTE : Lorsque l'étape se termine, la fréquence et le gouverneur de chaque CPU sélectionné sont réinitialisés à leurs valeurs précédentes.

NOTE : Lors de la soumission de travaux avec l'option --cpu-freq avec linuxproc comme ProctrackType, les travaux peuvent s'exécuter trop rapidement avant que la comptabilité ne puisse interroger les informations du travail. Par conséquent, toutes les informations de comptabilité ne seront pas présentes.

--cpus-per-gpu=<ncpus>
Demande que ncpus processeurs soient alloués par GPU alloué. Cette option implique --exact. Non compatible avec l'option --cpus-per-task.

Cette option s'applique aux allocations de travaux et d'étapes.

-c, --cpus-per-task=<ncpus>
Demande que ncpus soient alloués par processus. Cela peut être utile si le travail est multithreadé et nécessite plus d'un CPU par tâche pour des performances optimales. Demander explicitement cette option implique --exact. La valeur par défaut est un CPU par processus et n'implique pas --exact. Si -c est spécifié sans -n, autant de tâches que possible seront allouées par nœud tout en satisfaisant la restriction -c. Par exemple, sur un cluster de 8 CPUs par nœud, une demande de travail pour 4 nœuds et 3 CPUs par tâche peut se voir allouer 3 ou 6 CPUs par nœud (1 ou 2 tâches par nœud) en fonction de la consommation des ressources par d'autres travaux. Un tel travail pourrait ne pas être en mesure d'exécuter plus d'un total de 4 tâches.

AVERTISSEMENT : Il existe des configurations et des options interprétées différemment par les demandes de travaux et d'étapes qui peuvent entraîner des incohérences pour cette option. Par exemple, srun -c2 --threads-per-core=1 prog peut allouer deux cœurs pour le travail, mais si chacun de ces cœurs contient deux threads, l'allocation du travail inclura quatre CPUs. L'allocation de l'étape de travail lancera alors deux threads par CPU pour un total de deux tâches.

AVERTISSEMENT : Lorsque srun est exécuté à partir de salloc ou sbatch, il existe des configurations et des options qui peuvent entraîner des allocations incohérentes lorsque -c a une valeur supérieure à -c sur salloc ou sbatch.

NOTE : Si --mem-per-cpu est également spécifié, le nombre de CPUs alloués peut être augmenté si MaxMemPerCPU est dépassé. Dans le cas où -n n'est pas spécifié, le nombre de tâches peut être supérieur à celui attendu.

Cette option s'applique aux allocations de travaux et d'étapes.

--deadline=<OPT>
Supprimer le travail si aucune fin n'est possible avant cette échéance (début > (échéance - temps[-min])). Par défaut, pas d'échéance. Notez que si ni DefaultTime ni MaxTime ne sont configurés sur la partition sur laquelle se trouve le travail, le travail devra spécifier une forme de limite de temps (--time[-min]) si une échéance doit être utilisée.

Les formats de temps valides sont :
HH:MM[:SS] [AM|PM]
MMDD[YY] ou MM/DD[/YY] ou MM.DD[.YY]
MM/DD[/YY]-HH:MM[:SS]
YYYY-MM-DD[THH:MM[:SS]]]
now[+compteur[secondes(défaut)|minutes|heures|jours|semaines]]

Cette option s'applique uniquement aux allocations de travaux.

--delay-boot=<minutes>
Ne pas redémarrer les nœuds pour satisfaire la spécification de caractéristiques de ce travail si le travail est éligible à l'exécution depuis moins de cette période. Si le travail a attendu moins que la période spécifiée, il n'utilisera que les nœuds qui possèdent déjà les caractéristiques spécifiées. L'argument est en unités de minutes. Une valeur par défaut peut être définie par un administrateur système en utilisant l'option delay_boot du paramètre de configuration SchedulerParameters dans le fichier slurm.conf, sinon la valeur par défaut est zéro (aucun délai).

Cette option s'applique uniquement aux allocations de travaux.

-d, --dependency=<liste_dépendances>
Reporter le démarrage de ce travail jusqu'à ce que les dépendances spécifiées soient satisfaites. Une fois qu'une dépendance est satisfaite, elle est supprimée du travail. Cette option ne s'applique pas aux étapes de travail (exécutions de srun au sein d'une allocation salloc ou sbatch existante) mais uniquement aux allocations de travaux. <liste_dépendances> est de la forme <type:job_id[:job_id][,type:job_id[:job_id]]> ou <type:job_id[:job_id][?type:job_id[:job_id]]>. Toutes les dépendances doivent être satisfaites si le séparateur "," est utilisé. N'importe quelle dépendance peut être satisfaite si le séparateur "?" est utilisé. Un seul séparateur peut être utilisé. Par exemple : 
-d aftero
k:20:21,afterany:23 signifie que le travail ne peut être exécuté qu'après un code de retour 0 des travaux 20 et 21 ET la fin du travail 23. Cependant : 
-d afterok:20:21?afterany:23
signifie que l'une des conditions (afterok:20 OU afterok:21 OU afterany:23) sera suffisante pour libérer le travail. De nombreux travaux peuvent partager la même dépendance et ces travaux peuvent même appartenir à différents utilisateurs. La valeur peut être modifiée après la soumission du travail en utilisant la commande scontrol. Les dépendances sur des travaux distants sont autorisées dans une fédération. Une fois qu'une dépendance de travail échoue en raison de l'état de terminaison d'un travail précédent, le travail dépendant ne sera jamais exécuté, même si le travail précédent est remis en file d'attente et a un état de terminaison différent lors d'une exécution ultérieure. Cette option s'applique aux allocations de travaux.
after:job_id[[+time][:jobid[+time]...]]
Après le démarrage ou l'annulation des travaux spécifiés et que 'time' en minutes à partir du démarrage ou de l'annulation du travail s'est produit, ce travail peut commencer son exécution. Si aucun 'time' n'est donné, il n'y a pas de délai après le démarrage ou l'annulation.
afterany:job_id[:jobid...]
Ce travail peut commencer son exécution après la terminaison des travaux spécifiés. C'est le type de dépendance par défaut.
afterburstbuffer:job_id[:jobid...]
Ce travail peut commencer son exécution après la terminaison des travaux spécifiés et que toutes les opérations de transfert hors du burst buffer associées sont terminées.
aftercorr:job_id[:jobid...]
Une tâche de ce tableau de travaux peut commencer son exécution après que la tâche correspondante ID dans le travail spécifié se soit terminée avec succès (exécutée jusqu'à la fin avec un code de sortie zéro). Si le travail spécifié n'est pas un tableau, cela est traité comme afterok.
afternotok:job_id[:jobid...]
Ce travail peut commencer son exécution après la terminaison des travaux spécifiés dans un état d'échec (code de sortie non nul, panne de nœud, dépassement de délai, etc.). Ce travail doit être soumis pendant que le travail spécifié est encore actif ou dans les MinJobAge secondes après la fin du travail spécifié. Si l'ID du travail dépendant n'est pas trouvé et se trouve sur le même cluster que la soumission du travail, le travail est rejeté. Si l'ID du travail dépendant n'est pas trouvé et se trouve sur un cluster différent de celui de la soumission du travail, la dépendance est marquée comme échouée.
afterok:job_id[:jobid...]
Ce travail peut commencer son exécution après que les travaux spécifiés se soient exécutés avec succès (exécutés jusqu'à la fin avec un code de sortie zéro). Ce travail doit être soumis pendant que le travail spécifié est encore actif ou dans les MinJobAge secondes après la fin du travail spécifié. Si l'ID du travail dépendant n'est pas trouvé et se trouve sur le même cluster que la soumission du travail, le travail est rejeté. Si l'ID du travail dépendant n'est pas trouvé et se trouve sur un cluster différent de celui de la soumission du travail, la dépendance est marquée comme échouée.
singleton
Ce travail peut commencer son exécution après que tous les travaux précédemment lancés partageant le même nom de travail et le même utilisateur se soient terminés. En d'autres termes, un seul travail portant ce nom et appartenant à cet utilisateur peut être en cours d'exécution ou suspendu à un moment donné. Dans une fédération, une dépendance singleton doit être satisfaite sur tous les clusters, sauf si DependencyParameters=disable_remote_singleton est utilisé dans slurm.conf.
-X, --disable-status
Désactive l'affichage de l'état des tâches lorsque srun reçoit un seul SIGINT (Ctrl-C). Au lieu de cela, transmet immédiatement le SIGINT au travail en cours d'exécution. Sans cette option, une deuxième Ctrl-C en une seconde est nécessaire pour terminer de force le travail et srun se terminera immédiatement. Peut également être défini via la variable d'environnement SLURM_DISABLE_STATUS. Cette option s'applique aux allocations de travaux.
-m, --distribution={*|block|cyclic|arbitrary|plane=<size>}[:{*|block|cyclic|fcyclic}[:{*|block|cyclic|fcyclic}]][,{Pack|NoPack}]

Spécifie des méthodes de distribution alternatives pour les processus distants. Pour l'allocation de travaux, cela définit des variables d'environnement qui seront utilisées par les requêtes srun ultérieures. La distribution des tâches affecte l'allocation de travaux au dernier stade de l'évaluation des ressources disponibles par le plugin cons_tres. Par conséquent, d'autres options (par exemple, --ntasks-per-node, --cpus-per-task) peuvent affecter la sélection des ressources avant la distribution des tâches. Pour garantir une distribution de tâches spécifique, les travaux doivent avoir accès à des nœuds entiers, ce qui peut être accompli en utilisant le flag --exclusive ou en demandant toutes les ressources sur le(s) nœud(s).

Cette option contrôle la distribution des tâches aux nœuds sur lesquels les ressources ont été allouées, et la distribution de ces ressources aux tâches pour la liaison (affinité des tâches). La première méthode de distribution (avant le premier ":") contrôle la distribution des tâches aux nœuds. La deuxième méthode de distribution (après le premier ":") contrôle la distribution des CPUs alloués sur les sockets pour la liaison aux tâches. La troisième méthode de distribution (après le deuxième ":") contrôle la distribution des CPUs alloués sur les cœurs pour la liaison aux tâches. Les deuxième et troisième distributions s'appliquent uniquement si l'affinité des tâches est activée. La troisième distribution n'est prise en charge que si le plugin task/cgroup est configuré. La valeur par défaut pour chaque type de distribution est spécifiée par *.

Notez qu'avec select/cons_tres, le nombre de CPUs alloués à chaque socket et nœud peut être différent. Reportez-vous à https://slurm.schedmd.com/mc_support.html pour plus d'informations sur l'allocation des ressources, la distribution des tâches aux nœuds et la liaison des tâches aux CPUs.

Première méthode de distribution (distribution des tâches sur les nœuds) :
*
Utilise la méthode par défaut pour distribuer les tâches aux nœuds (block).
block
La méthode de distribution par blocs distribuera les tâches à un nœud de telle sorte que les tâches consécutives partagent un nœud. Par exemple, considérez une allocation de trois nœuds avec deux CPUs chacun. Une demande de distribution par blocs de quatre tâches distribuera ces tâches aux nœuds avec les tâches un et deux sur le premier nœud, la tâche trois sur le second nœud, et la tâche quatre sur le troisième nœud. La distribution par blocs est le comportement par défaut si le nombre de tâches dépasse le nombre de nœuds alloués.
cyclic
La méthode de distribution cyclique distribuera les tâches à un nœud de telle sorte que les tâches consécutives soient distribuées sur des nœuds consécutifs (de manière circulaire). Par exemple, considérez une allocation de trois nœuds avec deux CPUs chacun. Une demande de distribution cyclique de quatre tâches distribuera ces tâches aux nœuds avec les tâches un et quatre sur le premier nœud, la tâche deux sur le deuxième nœud, et la tâche trois sur le troisième nœud. Notez que lorsque SelectType est select/cons_tres, le même nombre de CPUs peut ne pas être alloué sur chaque nœud. La distribution des tâches sera circulaire parmi tous les nœuds sur lesquels des CPUs n'ont pas encore été attribués à des tâches. La distribution cyclique est le comportement par défaut si le nombre de tâches n'est pas supérieur au nombre de nœuds alloués .
plane
Les tâches sont distribuées par blocs de taille <size>. La taille doit être donnée ou SLURM_DIST_PLANESIZE doit être défini. Le nombre de tâches distribuées à chaque nœud est le même que pour la distribution cyclique, mais les taskids attribués à chaque nœud dépendent de la taille du plan. Des spécifications de distribution supplémentaires ne peuvent pas être combinées avec cette option. Pour plus de détails (y compris des exemples et des schémas), veuillez consulter https://slurm.schedmd.com/mc_support.html et https://slurm.schedmd.com/dist_plane.html
arbitrary
La méthode de distribution arbitraire allouera les processus dans l'ordre tel qu'indiqué dans le fichier désigné par la variable d'environnement SLURM_HOSTFILE. Si cette variable est listée, elle remplacera toute autre méthode spécifiée. Si elle n'est pas définie, la méthode sera par défaut block. Le fichier d'hôtes doit contenir au minimum le nombre d'hôtes demandés et être un par ligne ou séparé par des virgules. Si vous spécifiez un nombre de tâches (-n, --ntasks=<number>), vos tâches seront réparties sur les nœuds dans l'ordre du fichier.
NOTE : L'option de distribution arbitraire sur une allocation de travaux ne contrôle que les nœuds à allouer au travail et non l'allocation des CPUs sur ces nœuds. Cette option est principalement destinée à contrôler la disposition des tâches d'un pas de travail dans une allocation de travail existante pour la commande srun.
NOTE : Si le nombre de tâches est donné et qu'une liste de nœuds demandés est également donnée, le nombre de nœuds utilisés dans cette liste sera réduit pour correspondre au nombre de tâches si le nombre de nœuds dans la liste est supérieur au nombre de tâches.

Deuxième méthode de distribution (distribution des CPUs sur les sockets pour la liaison) :

*
Utilise la méthode par défaut pour distribuer les CPUs sur les sockets (cyclic).
bloc
La méthode de distribution bloc distribuera les CPU alloués consécutivement à partir du même socket pour la liaison aux tâches, avant d'utiliser le prochain socket consécutif.
cyclique
La méthode de distribution cyclique distribuera les CPU alloués pour la liaison à une tâche donnée consécutivement à partir du même socket, et à partir du prochain socket consécutif pour la tâche suivante, de manière circulaire entre les sockets. Les tâches nécessitant plus d'un CPU auront tous ces CPU alloués sur un seul socket si possible.
NOTE : Dans les nœuds avec l'hyper-threading activé, une tâche ne demandant pas des cœurs complets peut être distribuée sur les sockets. Cela peut être évité en spécifiant --ntasks-per-core=1, ce qui force les tâches à allouer des cœurs complets.
fcyclic
La méthode de distribution fcyclic distribuera les CPU alloués pour la liaison aux tâches à partir de sockets consécutifs de manière circulaire entre les sockets. Les tâches nécessitant plus d'un CPU auront chaque CPU alloué de manière cyclique entre les sockets.

Troisième méthode de distribution (distribution des CPU entre les cœurs pour la liaison) :

*
Utilise la méthode par défaut pour distribuer les CPU entre les cœurs (héritée de la deuxième méthode de distribution).
bloc
La méthode de distribution bloc distribuera les CPU alloués consécutivement à partir du même cœur pour la liaison aux tâches, avant d'utiliser le prochain cœur consécutif.
cyclique
La méthode de distribution cyclique distribuera les CPU alloués pour la liaison à une tâche donnée consécutivement à partir du même cœur, et à partir du prochain cœur consécutif pour la tâche suivante, de manière circulaire entre les cœurs.
fcyclic
La méthode de distribution fcyclic distribuera les CPU alloués pour la liaison aux tâches à partir de cœurs consécutifs de manière circulaire entre les cœurs.

Contrôle optionnel de la distribution des tâches sur les nœuds :

Pack
Plutôt que de distribuer uniformément les tâches d'une étape de travail sur ses nœuds alloués, les regrouper aussi étroitement que possible sur les nœuds. Ceci s'applique uniquement lorsque la méthode de distribution des tâches "bloc" est utilisée.
NoPack
Plutôt que de regrouper les tâches d'une étape de travail aussi étroitement que possible sur les nœuds, les distribuer uniformément. Cette option utilisateur remplacera le paramètre de configuration CR_Pack_Nodes de SelectTypeParameters.
Cette option s'applique aux allocations de travaux et d'étapes.
--epilog={aucun|<exécutable>}
srun exécutera executable juste après la fin de l'étape de travail. La ligne de commande pour executable sera la commande et les arguments de l'étape de travail. Si aucun est spécifié, alors aucun épilogue srun ne sera exécuté. Ce paramètre remplace le paramètre SrunEpilog dans slurm.conf. Ce paramètre est complètement indépendant du paramètre Epilog dans slurm.conf. Cette option s'applique aux allocations de travaux.
-e, --error=<motif_nom_fichier>
Spécifie comment la sortie d'erreur standard doit être redirigée. Par défaut en mode interactif, srun redirige la sortie d'erreur standard vers le même fichier que la sortie standard, si un est spécifié. L'option --error est fournie pour permettre de rediriger la sortie standard et la sortie d'erreur standard vers des emplacements différents. Voir Redirection IO ci-dessous pour plus d'options. Si le fichier spécifié existe déjà, il sera écrasé. Cette option s'applique aux allocations de travaux et d'étapes.
--exact
Permet à une étape d'accéder uniquement aux ressources demandées pour l'étape. Par défaut, toutes les ressources non-GRES sur chaque nœud de l'allocation d'étape seront utilisées. Cette option ne s'applique qu'aux allocations d'étapes.
NOTE : Les étapes parallèles seront bloquées ou rejetées jusqu'à ce que les ressources d'étape demandées soient disponibles, sauf si --overlap est spécifié. Les ressources du travail peuvent être conservées après l'achèvement d'une commande srun pendant que Slurm effectue le nettoyage du travail. Les épilogues d'étape et/ou les plugins SPANK peuvent retarder davantage la libération des ressources d'étape.
-x, --exclude={<hote1[,<hote2>...]|<nom_fichier>}
Demande que la liste spécifiée d'hôtes ne soit pas incluse dans les ressources allouées à ce travail. La liste d'hôtes sera supposée être un nom de fichier si elle contient un caractère "/". Cette option s'applique aux allocations de travaux et d'étapes.
--exclusive[={user|mcs|topo}]
Cette option s'applique aux allocations de travaux et d'étapes de travaux, et a deux significations légèrement différentes pour chacune.

Lorsqu'elle est utilisée pour lancer un travail, l'allocation du travail ne peut pas partager de nœuds (ou de segment de topologie avec l'option "=topo") avec d'autres travaux en cours d'exécution (ou juste d'autres utilisateurs avec l'option "=user" ou l'option "=mcs"). Si user/mcs/topo ne sont pas spécifiés (c'est-à-dire que l'allocation du travail ne peut pas partager de nœuds avec d'autres travaux en cours d'exécution), l'allocation du travail se voit attribuer tous les CPU et GRES sur tous les nœuds de l'allocation, mais ne se voit attribuer que la quantité de mémoire demandée. Ceci est intentionnel pour prendre en charge la planification par groupes, car les travaux suspendus résident toujours en mémoire. Pour demander toute la mémoire d'un nœud, utilisez --mem=0. Le comportement par défaut de partage/exclusivité dépend de la configuration du système et l'option OverSubscribe de la partition a priorité sur l'option du travail. NOTE : Comme les GRES partagés (MPS) ne peuvent pas être alloués en même temps qu'un GRES partageant (GPU), cette option n'alloue que tous les GRES partageant et aucun GRES sous-jacent partagé.

Cette option peut également être utilisée lors du lancement de plus d'une étape de travail au sein d'une allocation de ressources existante (par défaut), où vous souhaitez que des processeurs séparés soient dédiés à chaque étape de travail. L'étape de travail ne se voit attribuer que la quantité de GRES demandée. Si suffisamment de processeurs ne sont pas disponibles pour lancer l'étape de travail, elle sera différée. Cela peut être considéré comme un mécanisme de gestion des ressources pour le travail dans son allocation (--exact implicite). L'allocation exclusive des CPU s'applique aux étapes de travail par défaut, mais --exact n'est PAS le défaut. Autrement dit, le comportement par défaut est le suivant : les étapes de travail ne partageront pas de CPU, mais elles se verront attribuer tous les CPU disponibles pour le travail sur tous les nœuds alloués aux étapes.

Afin de partager les ressources, utilisez l'option --overlap.

NOTE : Cette option est mutuellement exclusive avec --oversubscribe.

--export=AUCUNE
Aucun environnement utilisateur ne sera défini. L'utilisateur doit utiliser le chemin absolu vers le binaire à exécuter qui définira l'environnement. L'utilisateur ne peut pas spécifier de variables d'environnement explicites avec "AUCUNE".

Cette option est particulièrement importante pour les travaux qui sont soumis sur un cluster et exécutés sur un cluster différent (par exemple, avec des chemins différents). Pour éviter que les étapes n'héritent des paramètres d'exportation d'environnement (par exemple, "AUCUNE") de la commande sbatch, définissez --export=TOUT ou la variable d'environnement SLURM_EXPORT_ENV doit être définie sur "TOUT".

--export=[TOUT,]<variables_environnement>
Exporte toutes les variables d'environnement SLURM* ainsi que les variables explicitement définies. Plusieurs noms de variables d'environnement doivent être séparés par des virgules. Les noms de variables d'environnement peuvent être spécifiés pour propager la valeur actuelle (par exemple, "--export=EDITOR") ou des valeurs spécifiques peuvent être exportées (par exemple, "--export=EDITOR=/bin/emacs"). Si "TOUT" est spécifié, alors toutes les variables d'environnement utilisateur seront chargées et auront la priorité sur toutes les variables d'environnement explicitement données.
Exemple : --export=EDITOR,ARG1=test
Dans cet exemple, l'environnement propagé ne contiendra que la variable EDITOR de l'environnement de l'utilisateur, les variables d'environnement SLURM_*, et ARG1=test.
Exemple : --export=TOUT,EDITOR=/bin/emacs
Il y a deux résultats possibles pour cet exemple. Si l'appelant a la variable d'environnement EDITOR définie, alors l'environnement du travail héritera de la variable de l'environnement de l'appelant. Si l'appelant n'a pas de variable d'environnement définie pour EDITOR, alors l'environnement du travail utilisera la valeur donnée par --export.
--external-launcher
Crée une étape spéciale sur un ou plusieurs nœuds alloués qui ne consommera aucune ressource, mais aura accès à toutes les ressources allouées du travail sur les nœuds.

Les options telles que --ntasks-per-*, --mem*, --cpus*, --tres*, --gres*, seront ignorées.

Ceci est destiné à être utilisé par des implémentations MPI qui nécessitent leur propre lanceur. Ceci lance une étape avec accès à toutes les ressources et qui lancera plus tard un nombre quelconque de processus utilisateurs avec accès à toutes ces ressources.

L'utilisation des ressources dans cette étape spéciale sera toujours comptabilisée si les plugins de comptabilité sont activés. Cette étape spéciale peut être chevauchée avec toute autre étape.

NOTE : Cette option n'est pas destinée à être utilisée directement.

--extra=<string>
Une chaîne arbitraire entourée de guillemets simples ou doubles si elle contient des espaces ou des caractères spéciaux.

Si SchedulerParameters=extra_constraints est activé, cette chaîne est utilisée pour le filtrage des nœuds basé sur le champ Extra de chaque nœud.

-B, --extra-node-info=<sockets>[:cores[:threads]]
Restreint la sélection des nœuds aux nœuds ayant au moins le nombre spécifié de sockets, de cœurs par socket et/ou de threads par cœur.
NOTE : Ces options ne spécifient pas la taille de l'allocation de ressources. Chaque valeur spécifiée est considérée comme un minimum. Un astérisque (*) peut être utilisé comme espace réservé indiquant que toutes les ressources disponibles de ce type doivent être utilisées. Les valeurs peuvent également être spécifiées sous forme de min-max. Les niveaux individuels peuvent également être spécifiés dans des options séparées si désiré :
    --sockets-per-node=<sockets>
    --cores-per-socket=<cores>
    --threads-per-core=<threads>
Si le plugin task/affinity est activé, alors spécifier une allocation de cette manière définit également une option --cpu-bind par défaut de threads si l'option -B spécifie un nombre de threads, sinon une option de cores si un nombre de cœurs est spécifié, sinon une option de sockets. Si SelectType est configuré pour select/cons_tres, il doit avoir un paramètre de CR_Core, CR_Core_Memory, CR_Socket, ou CR_Socket_Memory pour que cette option soit respectée. Si non spécifié, scontrol show job affichera 'ReqS:C:T=*:*:*'. Cette option s'applique aux allocations de travaux.
NOTE : Cette option est mutuellement exclusive avec --hint, --threads-per-core et --ntasks-per-core.
NOTE : Si le nombre de sockets, de cœurs et de threads a été spécifié, le nombre de nœuds a été spécifié (comme un nombre fixe, pas une plage) et le nombre de tâches n'a PAS été spécifié, srun calculera implicitement le nombre de tâches comme une tâche par thread.

Équivalent à --tres-bind=gres/gpu:[verbose,]<type>. Voir --tres-bind pour toutes les options et la documentation.
--gpu-freq=[<type>=<value>][,<type>=<value>][,verbose]
Demande que les GPU alloués au travail soient configurés avec des valeurs de fréquence spécifiques. Cette option peut être utilisée pour configurer indépendamment la fréquence du GPU et de sa mémoire. Une fois le travail terminé, les fréquences de tous les GPU concernés seront réinitialisées aux valeurs les plus élevées possibles. Dans certains cas, les limites de puissance du système peuvent remplacer les valeurs demandées. Le champ type peut être "memory". Si type n'est pas spécifié, la fréquence du GPU est implicite. Le champ value peut être "low", "medium", "high", "highm1" ou une valeur numérique en mégahertz (MHz). Si la valeur numérique spécifiée n'est pas possible, une valeur aussi proche que possible sera utilisée. Voir ci-dessous pour la définition des valeurs. L'option verbose provoque l'enregistrement des informations actuelles sur la fréquence des GPU. Des exemples d'utilisation incluent "--gpu-freq=medium,memory=high" et "--gpu-freq=450".

Définitions des values supportées :

low
la fréquence disponible la plus basse.
medium
tente de définir une fréquence au milieu de la plage disponible.
high
la fréquence disponible la plus élevée.
highm1
(high moins un) sélectionnera la fréquence disponible immédiatement inférieure à la plus élevée.

Spécifie le nombre total de GPU requis pour le travail. Une spécification optionnelle de type de GPU peut être fournie. Voir également les options --gpus-per-node, --gpus-per-socket et --gpus-per-task.
NOTE : L'allocation doit contenir au moins un GPU par nœud, ou un de chaque type de GPU par nœud si des types sont utilisés. Utilisez des travaux hétérogènes si différents nœuds nécessitent différents types de GPU.
--gpus-per-node=[type:]<number>
Spécifie le nombre de GPU requis pour le travail sur chaque nœud inclus dans l'allocation de ressources du travail. Une spécification optionnelle de type de GPU peut être fournie. Par exemple "--gpus-per-node=volta:3". Plusieurs options peuvent être demandées dans une liste séparée par des virgules, par exemple : "--gpus-per-node=volta:3,kepler:1". Voir également les options --gpus, --gpus-per-socket et --gpus-per-task.
--gpus-per-socket=[type:]<number>
Spécifie le nombre de GPU requis pour le travail sur chaque socket inclus dans l'allocation de ressources du travail. Une spécification optionnelle de type de GPU peut être fournie. Par exemple "--gpus-per-socket=volta:3". Plusieurs options peuvent être demandées dans une liste séparée par des virgules, par exemple : "--gpus-per-socket=volta:3,kepler:1". Nécessite que le travail spécifie un nombre de sockets par nœud ( --sockets-per-node). Voir également les options --gpus, --gpus-per-node et --gpus-per-task. Cette option s'applique aux allocations de travaux.
--gpus-per-task=[type:]<number>
Spécifie le nombre de GPU requis pour le travail sur chaque tâche à lancer dans l'allocation de ressources du travail. Une spécification optionnelle de type de GPU peut être fournie. Par exemple "--gpus-per-task=volta:1". Plusieurs options peuvent être demandées dans une liste séparée par des virgules, par exemple : "--gpus-per-task=volta:3,kepler:1". Voir également les options --gpus, --gpus-per-socket et --gpus-per-node. Cette option nécessite un nombre de tâches explicite, par exemple -n, --ntasks ou "--gpus=X --gpus-per-task=Y" plutôt qu'une plage ambiguë de nœuds avec -N, --nodes. Cette option définira implicitement --tres-bind=gres/gpu:per_task:<gpus_per_task>, ou si plusieurs types de gpu sont spécifiés --tres-bind=gres/gpu:per_task:<gpus_per_task_type_sum>. Cependant, cela peut être remplacé par une spécification explicite de --tres-bind=gres/gpu.
--gres=<list>
Spécifie une liste de ressources consommables génériques délimitée par des virgules, demandée par nœud. Le format pour chaque entrée de la liste est "nom[[:type]:compte]". Le nom est le type de ressource consommable (par ex. gpu). Le type est une classification optionnelle pour la ressource (par ex. a100). Le compte est le nombre de ces ressources avec une valeur par défaut de 1. Le compte peut avoir un suffixe "k" ou "K" (multiple de 1024), "m" ou "M" (multiple de 1024 x 1024), "g" ou "G" (multiple de 1024 x 1024 x 1024), "t" ou "T" (multiple de 1024 x 1024 x 1024 x 1024), "p" ou "P" (multiple de 1024 x 1024 x 1024 x 1024 x 1024). Les ressources spécifiées seront allouées au travail sur chaque nœud. Les ressources consommables génériques disponibles sont configurables par l'administrateur système. Une liste des ressources consommables génériques disponibles sera imprimée et la commande se terminera si l'argument de l'option est "help". Exemples d'utilisation incluent "--gres=gpu:2", "--gres=gpu:kepler:2", et "--gres=help". NOTE : Cette option s'applique aux allocations de travaux et d'étapes. Par défaut, une étape de travail se voit allouer toutes les ressources génériques demandées par le travail, sauf celles demandées implicitement lorsqu'un travail est exclusif. Pour modifier ce comportement afin que chaque étape de travail ne reçoive aucune ressource générique, spécifiez explicitement la valeur de --gres pour indiquer zéro compte pour chaque ressource générique OU définissez "--gres=none" OU définissez la variable d'environnement SLURM_STEP_GRES à "none".

-H, --hold
Spécifier que le travail doit être soumis dans un état retenu (priorité nulle). Un travail retenu peut maintenant être libéré en utilisant scontrol pour réinitialiser sa priorité (par exemple, « scontrol release <job_id> »). Cette option s'applique aux allocations de travaux.
-I, --immediate[=<seconds>]
Quitter si les ressources ne sont pas disponibles dans le délai spécifié. Si aucun argument n'est donné (la valeur par défaut de secondes est 1), les ressources doivent être disponibles immédiatement pour que la requête réussisse. Si defer est configuré dans SchedulerParameters et que seconds=1, la requête d'allocation échouera immédiatement ; defer entre en conflit avec cette option et lui est prioritaire. Par défaut, --immediate est désactivé et la commande bloquera jusqu'à ce que les ressources soient disponibles. Étant donné que l'argument de cette option est facultatif, pour un analyse correcte, l'option à lettre unique doit être suivie immédiatement de la valeur et ne pas inclure d'espace entre eux. Par exemple « -I60 » et non « -I 60 ». Cette option s'applique aux allocations de travaux et d'étapes.

Contrôle si un travail doit être terminé ou non si une tâche se termine avec un code de sortie non nul. Si cette option n'est pas spécifiée, l'action par défaut sera basée sur le paramètre de configuration Slurm KillOnBadExit. Si cette option est spécifiée, elle aura la priorité sur KillOnBadExit. Par exemple « -K1 » et non « -K 1 ».

Ajouter le numéro de tâche au début des lignes de sortie standard/erreur. L'option --label ajoutera l'identifiant de tâche distant au début des lignes de sortie. Cette option s'applique aux allocations d'étapes.
-L, --licenses=<license>[@db][:count][,license[@db][:count]...]
Spécification des licences (ou d'autres ressources disponibles sur tous les nœuds du cluster) qui doivent être allouées à ce travail. Les noms de licence peuvent être suivis d'un deux-points et d'un nombre (le nombre par défaut est un). Plusieurs licences peuvent être demandées. Si elles sont séparées par une virgule (',' signifiant ET), alors toutes les licences demandées sont requises pour le travail. Par exemple, « --licenses=foo:4,bar ». Si elles sont séparées par une barre verticale ('|' signifiant OU), alors une seule des demandes de licence est requise pour le travail. Par exemple, « --licenses=foo:4|bar ». ET et OU ne peuvent pas être utilisés simultanément.

NOTE : Lorsqu'un travail demande des licences OU, Slurm tentera d'allouer les licences dans l'ordre dans lequel elles sont demandées. Cet ordre spécifié aura la priorité même si le reste des licences demandées pouvait être satisfait sur une demande

d réservation. Ceci s'applique également à la planification de remplacement lorsque SchedulerParameters=bf_licenses est configuré.

--mem=<size>[units]
Spécifie la mémoire réelle requise par nœud. Les unités par défaut sont les mégaoctets. Différentes unités peuvent être spécifiées en utilisant le suffixe [K|M|G|T]. La valeur par défaut est DefMemPerNode et la valeur maximale est MaxMemPerNode. Si elles sont configurées, les deux paramètres peuvent être consultés à l'aide de la commande scontrol show config. Ce paramètre serait généralement utilisé si des nœuds entiers sont alloués aux tâches (SelectType=select/linear). --mem-bind=[{quiet|verbose},]<type>
Lier les tâches à la mémoire. Utilisé uniquement lorsque le plugin task/affinity est activé et que les fonctions de mémoire NUMA sont disponibles. Notez que la résolution de la liaison CPU et mémoire peut différer sur certaines architectures. Par exemple, la liaison CPU peut être effectuée au niveau des cœurs d'un processeur tandis que la liaison mémoire sera effectuée au niveau des nœuds, où la définition de "nœuds" peut différer d'un système à l'autre. Par défaut, aucune liaison de mémoire n'est effectuée ; toute tâche utilisant n'importe quel CPU peut utiliser n'importe quelle mémoire. Cette option est généralement utilisée pour s'assurer que chaque tâche est liée à la mémoire la plus proche de son CPU attribué. L'utilisation de tout type autre que "none" ou "local" n'est pas recommandée. Si vous souhaitez un contrôle plus précis, essayez d'exécuter un code de test simple avec les options "--cpu-bind=verbose,none --mem-bind=verbose,none" pour déterminer la configuration spécifique.

NOTE : Pour que Slurm rapporte toujours la liaison de mémoire sélectionnée pour toutes les commandes exécutées dans un shell, vous pouvez activer le mode verbeux en définissant la variable d'environnement SLURM_MEM_BIND à "verbose".

Les variables d'environnement informatives suivantes sont définies lorsque --mem-bind est utilisé :

SLURM_MEM_BIND_LIST
SLURM_MEM_BIND_PREFER
SLURM_MEM_BIND_TYPE
SLURM_MEM_BIND_VERBOSE

Voir la section VARIABLES D'ENVIRONNEMENT pour une description plus détaillée des variables individuelles SLURM_MEM_BIND*.

Les options prises en charge incluent :

help
afficher ce message d'aide
local
Utiliser la mémoire locale au processeur utilisé
map_mem:<list>
Lier en définissant des masques de mémoire sur les tâches (ou rangs) comme spécifié où <list> est <id_numa_pour_tache_0>,<id_numa_pour_tache_1>,... La cartographie est spécifiée pour un nœud et une cartographie identique est appliquée aux tâches sur chaque nœud (c'est-à-dire que l'ID de tâche le plus bas sur chaque nœud est mappé au premier ID spécifié dans la liste, etc.). Si le nombre de tâches (ou de rangs) dépasse le nombre d'éléments dans cette liste, les éléments de la liste seront réutilisés au besoin en commençant par le début de la liste. Pour simplifier la prise en charge des grands nombres de tâches, les listes peuvent suivre une carte avec un astérisque et un compteur de répétition. Par exemple "map_mem:0x0f*4,0xf0*4". NOTE : Ceci s'applique aux CPUs alloués utilisables dans une allocation de job. Ceci est important lorsque plus d'un thread par cœur est configuré. Si un job demande --threads-per-core avec moins de threads sur un cœur que ce qui existe sur le cœur (ou --hint=nomultithread qui implique --threads-per-core=1), le job ne pourra pas utiliser ces threads supplémentaires sur le cœur et ces threads ne seront pas inclus dans le calcul de la mémoire par CPU. Mais si le job a accès à tous les threads sur le cœur, ces threads seront inclus dans le calcul de la mémoire par CPU même si le job n'a pas explicitement demandé ces threads.

Dans les exemples suivants, chaque cœur a deux threads.

Dans ce premier exemple, deux tâches peuvent s'exécuter sur des hyperthreads séparés dans le même cœur car --threads-per-core n'est pas utilisé. La troisième tâche utilise les deux threads du deuxième cœur. La mémoire allouée par cpu inclut tous les threads :

$ sacct -j $SLURM_JOB_ID -X -o jobid%7,reqtres%35,alloctres%35
  JobID                             ReqTRES                           AllocTRES
------- ----------------------------------- -----------------------------------
  17199     billing=3,cpu=3,mem=300M,node=1     billing=4,cpu=4,mem=400M,node=1

Dans ce deuxième exemple, en raison de --threads-per-core=1, chaque tâche se voit allouer un cœur entier mais ne peut utiliser qu'un seul thread par cœur. Les CPUs alloués incluent tous les threads sur chaque cœur. Cependant, la mémoire allouée par cpu n'inclut que le thread utilisable sur chaque cœur.

$ salloc -n3 --mem-per-cpu=100 --threads-per-core=1
salloc: Granted job allocation 17200
$ sacct -j $SLURM_JOB_ID -X -o jobid%7,reqtres%35,alloctres%35
  JobID                             ReqTRES                           AllocTRES
------- ----------------------------------- -----------------------------------
  17200     billing=3,cpu=3,mem=300M,node=1     billing=6,cpu=6,mem=300M,node=1

-O, --overcommit
Surengager les ressources. Cette option s'applique aux allocations de tâches et d'étapes.

Lorsqu'elle est appliquée à une allocation de tâche (sans inclure les tâches demandant un accès exclusif aux nœuds), les ressources sont allouées comme si une seule tâche par nœud était demandée. Cela signifie que le nombre demandé de cœurs par tâche (-c, --cpus-per-task) est alloué par nœud plutôt que d'être multiplié par le nombre de tâches. Les options utilisées pour spécifier le nombre de tâches par nœud, socket, cœur, etc. sont ignorées.

Lorsqu'elle est appliquée aux allocations d'étapes de tâches (la commande srun lorsqu'elle est exécutée dans une allocation de tâche existante), cette option peut être utilisée pour lancer plus d'une tâche par cœur. Normalement, srun n'alloue pas plus d'un processus par cœur. En spécifiant --overcommit, vous autorisez explicitement plus d'un processus par cœur. Cependant, pas plus de MAX_TASKS_PER_NODE tâches sont autorisées à s'exécuter par nœud. NOTE : MAX_TASKS_PER_NODE est défini dans le fichier slurm.h et n'est pas une variable, il est défini au moment de la construction de Slurm.

Par défaut, les étapes ne partagent pas de ressources avec d'autres étapes parallèles. Cette option s'applique aux allocations d'étapes.

Lier en définissant des masques gres sur les tâches (ou les rangs) comme spécifié où <liste> est <id_gres_pour_tâche_0>,<id_gres_pour_tâche_1>,... Les identifiants gres sont interprétés comme des valeurs décimales. Si le nombre de tâches (ou de rangs) dépasse le nombre d'éléments de cette liste, les éléments de la liste seront réutilisés si nécessaire en commençant par le début de la liste. Pour simplifier la prise en charge de grands nombres de tâches, les listes peuvent suivre une carte avec un astérisque et un nombre de répétitions. Par exemple "map:0*4,1*4". Si le plugin task/cgroup est utilisé et que ConstrainDevices est défini dans cgroup.conf, alors les identifiants gres sont des indices basés sur zéro par rapport aux gress alloués au travail (par exemple, le premier gres est 0, même si l'identifiant global est 3). Sinon, les identifiants gres sont des identifiants globaux, et tous les gres sur chaque nœud du travail doivent être alloués pour des résultats de liaison prévisibles.
mask:<liste>
Lier en définissant des masques gres sur les tâches (ou les rangs) comme spécifié où <liste> est <masque_gres_pour_tâche_0>,<masque_gres_pour_tâche_1>,... Le mappage est spécifié pour un nœud et un mappage identique est appliqué aux tâches sur chaque nœud (c'est-à-dire que la tâche avec l'identifiant le plus bas sur chaque nœud est mappée au premier masque spécifié dans la liste, etc.). Les masques gres sont toujours interprétés comme des valeurs hexadécimales mais peuvent être précédés d'un '0x' optionnel. Pour simplifier la prise en charge de grands nombres de tâches, les listes peuvent suivre une carte avec un astérisque et un nombre de répétitions. Par exemple "mask:0x0f*4,0xf0*4". Si le plugin task/cgroup est utilisé et que ConstrainDevices est défini dans cgroup.conf, alors les identifiants gres sont des indices basés sur zéro par rapport aux gres alloués au travail (par exemple, le premier gres est 0, même si l'identifiant global est 3). Sinon, les identifiants gres sont des identifiants globaux, et tous les gres sur chaque nœud du travail doivent être alloués pour des résultats de liaison prévisibles.
none
Ne pas lier les tâches à ce gres (désactive la liaison implicite de --tres-per-task et --gpus-per-task).
per_task:<gres_par_tâche>
Chaque tâche sera liée au nombre de gres spécifié dans <gres_par_tâche>. Les tâches se voient préférentiellement attribuer des gres ayant une affinité avec les cœurs de leur allocation, comme dans closest, bien qu'elles prennent tout gres s'il n'y en a pas de disponible. S'il n'y a pas d'affinité, la première tâche se verra attribuer les x premiers gres disponibles sur le nœud, etc. Les gres partagés préféreront lier un périphérique partagé par tâche si possible.
single:<tâches_par_gres>
Comme closest, sauf que chaque tâche ne peut être liée qu'à un seul gres, même lorsqu'elle peut être liée à plusieurs gres qui sont également proches. Le gres auquel se lier est déterminé par <tâches_par_gres>, où les <tâches_par_gres> premières tâches sont liées au premier gres disponible, les <tâches_par_gres> tâches suivantes sont liées au deuxième gres disponible, etc. Il s'agit essentiellement d'une distribution par blocs de tâches sur les gres disponibles, où les gres disponibles sont déterminés par l'affinité du socket de la tâche et l'affinité du socket du gres, comme spécifié dans le paramètre Cores de gres.conf.

NOTE : La liaison gres partagée est actuellement limitée à per_task ou none

--tres-per-task=<liste>
Spécifie une liste d'éléments séparés par des virgules de ressources traçables requises pour le travail sur chaque tâche qui sera lancée dans l'allocation de ressources du travail. Le format pour chaque entrée de la liste est "type_tres[/nom_tres]=compte". Le type_tres est le type de ressource traçable demandée (par exemple, cpu, gres, licence, etc.). Le nom_tres est le nom de la ressource traçable, tel que visible avec sacctmgr show tres. Ceci est requis lorsqu'il existe pour des types de tres tels que gres, licence, etc. (par exemple, gpu, gpu:a100). Afin de demander une licence avec cette option, la ou les licences doivent être définies dans le paramètre AccountingStorageTRES de slurm.conf. Le compte est le nombre de ces ressources.
Le compte peut avoir un suffixe de
"k" ou "K" (multiple de 1024),
"m" ou "M" (multiple de 1024 x 1024),
"g" ou "G" (multiple de 1024 x 1024 x 1024),
"t" ou "T" (multiple de 1024 x 1024 x 1024 x 1024),
"p" ou "P" (multiple de 1024 x 1024 x 1024 x 1024 x 1024).
Exemples : 
--tres-per-task=cpu=4
--tres-per-task=cpu=8,license/ansys=1
--tres-per-task=gres/gpu=1
--tres-per-task=gres/gpu:a100=2
Les ressources spécifiées seront allouées au travail sur chaque nœud. Les ressources traçables disponibles sont configurables par l'administrateur système.
NOTE : Cette option avec gres/gpu ou gres/shard définira implicitement --tres-bind=gres/[gpu|shard]:per_task:<tres_par_tâche>, ou si plusieurs types de gpu sont spécifiés --tres-bind=gres/gpu:per_task:<somme_gpu_par_tâche_par_type>. Ceci peut être écrasé par une spécification explicite de --tres-bind.
NOTE : Les TRES invalides pour --tres-per-task incluent bb,billing,energy,fs,mem,node,pages,vmem.

--wait-for-children
Attend que tous les processus de chaque tâche se terminent avant de considérer une tâche comme terminée. Le comportement par défaut sans cette option est de n'attendre que le processus parent dans chaque tâche se termine.

En fonction du réglage de --kill-on-bad-exit, la tâche peut se terminer si le processus parent se termine avec un code de sortie non nul. Si --kill-on-bad-exit=1 et que le processus parent se termine avec un code de sortie non nul, la tâche se terminera. Si --kill-on-bad-exit=0 et que le processus parent se termine avec un code de sortie non nul, la tâche continuera jusqu'à ce que tous les processus enfants soient terminés.

Cette option nécessite proctrack/cgroup et cgroup/v2.

-W, --wait=<secondes>
Spécifie combien de temps attendre après la terminaison de la première tâche avant de terminer toutes les tâches restantes. Une valeur de 0 indique une attente illimitée (un avertissement sera émis après 60 secondes). La valeur par défaut est définie par le paramètre WaitTime dans le fichier de configuration slurm (voir slurm.conf(5)). Cette option peut être utile pour s'assurer qu'une tâche est terminée en temps opportun dans le cas où une ou plusieurs tâches se terminent prématurément. Note : L'option -K, --kill-on-bad-exit a la priorité sur -W, --wait pour terminer la tâche immédiatement si une tâche se termine avec un code de sortie non nul. Cette option s'applique aux allocations de tâches.

srun soumettra la requête de tâche au contrôleur de tâches slurm, puis initialisera tous les processus sur les nœuds distants. Si la requête ne peut pas être satisfaite immédiatement, srun bloquera jusqu'à ce que les ressources soient libres pour exécuter la tâche. Si l'option -I (--immediate) est spécifiée, srun se terminera si les ressources ne sont pas immédiatement disponibles.

Lors de l'initialisation des processus distants, srun propagera le répertoire de travail courant, sauf si --chdir=<chemin> est spécifié, auquel cas chemin deviendra le répertoire de travail des processus distants.

Les options -n, -c et -N contrôlent comment les processeurs et les nœuds seront alloués à la tâche. En spécifiant uniquement le nombre de processus à exécuter avec -n, une moyenne d'un processeur par processus est allouée. En spécifiant le nombre de processeurs requis par tâche (-c), plus d'un processeur peut être alloué par processus. Si le nombre de nœuds est spécifié avec -N, srun tentera d'allouer *au moins* le nombre de nœuds spécifié.

Les combinaisons des trois options ci-dessus peuvent être utilisées pour modifier la manière dont les processus sont distribués sur les nœuds et les processeurs. Par exemple, en spécifiant à la fois le nombre de processus et le nombre de nœuds sur lesquels exécuter, le nombre de processus par nœud est implicite. Cependant, si le nombre de processeurs par processus est plus important que le nombre de processus (-n) et le nombre de processeurs par processus (-c), ceux-ci doivent être spécifiés.

srun refusera d'allouer plus d'un processus par processeur à moins que --overcommit (-O) ne soit également spécifié.

srun tentera de satisfaire les spécifications ci-dessus "au minimum". C'est-à-dire que si 16 nœuds sont demandés pour 32 processus, et que certains nœuds n'ont pas 2 processeurs, l'allocation des nœuds sera augmentée afin de satisfaire la demande de processeurs. En d'autres termes, un *minimum* de 16 nœuds est demandé. Cependant, si 16 nœuds sont demandés pour 15 processus, srun considérera cela comme une erreur, car 15 processus ne peuvent pas s'exécuter sur 16 nœuds.

Redirection d'E/S

Par défaut, stdout et stderr seront redirigés de toutes les tâches vers stdout et stderr de srun, et stdin sera redirigé depuis l'entrée standard de srun vers toutes les tâches distantes. Si stdin ne doit être lu que par un sous-ensemble des tâches lancées, spécifier un fichier à lire plutôt que de transférer stdin depuis la commande srun peut être préférable car cela évite de déplacer et de stocker des données qui ne seront jamais lues.

Pour OS X, la fonction poll() ne prend pas en charge stdin, donc l'entrée à partir d'un terminal n'est pas possible.

Ce comportement peut être modifié avec les options --output, --error et --input (-o, -e, -i). Notez que --error ne redirigera pas stderr de srun lui-même, seulement stderr des tâches. Les spécifications de format valides pour ces options sont :

all
stdout et stderr sont redirigés de toutes les tâches vers srun. stdin est diffusé à toutes les tâches distantes. (C'est le comportement par défaut)
none
stdout et stderr ne sont reçus d'aucune tâche. stdin n'est envoyé à aucune tâche (stdin est fermé).
taskid
stdout et/ou stderr sont redirigés uniquement à partir de la tâche avec l'ID relatif égal à taskid, où 0 <= taskid <= ntasks, où ntasks est le nombre total de tâches dans l'étape de tâche actuelle. stdin est redirigé depuis stdin de srun vers cette même tâche. Ce fichier sera écrit sur le nœud exécutant la tâche.
filename
srun redirigera stdout et/ou stderr vers le fichier nommé à partir de toutes les tâches. stdin sera redirigé depuis le fichier nommé et diffusé à toutes les tâches de la tâche. filename fait référence à un chemin sur l'hôte qui exécute srun. Selon la configuration du système de fichiers du cluster, cela peut entraîner l'apparition de la sortie à différents endroits selon que la tâche est exécutée en mode batch.
filename pattern
srun permet d'utiliser un motif de nom de fichier pour générer le fichier d'E/S nommé décrit ci-dessus. La liste suivante de spécificateurs de format peut être utilisée dans la chaîne de format pour générer un nom de fichier qui sera unique à un jobid, stepid, node ou task donné. Dans chaque cas, le nombre approprié de fichiers est ouvert et associé aux tâches correspondantes. Notez que toute chaîne de format contenant %t, %n et/ou %N sera écrite sur le nœud exécutant la tâche plutôt que sur le nœud où srun s'exécute.
\\
Ne traite aucun des symboles de remplacement.
%%
Le caractère "%".
%A
Numéro d'allocation de tâche principale du tableau de tâches.
%a
Numéro d'ID (index) du tableau de tâches.
%J
jobid.stepid de la tâche en cours d'exécution (par exemple, "128.0"). Le stepid n'est développé que pour les étapes régulières, pas pour les étapes spéciales comme "batch" ou "extern".
%j
jobid de la tâche en cours d'exécution.
%S
SLUID de la tâche en cours d'exécution.
%s
stepid de la tâche en cours d'exécution.
%N
Nom d'hôte court. Cela créera un fichier E/S séparé par nœud.
%n
Identifiant de nœud relatif à la tâche courante (par exemple, "0" est le premier nœud de la tâche en cours d'exécution). Cela créera un fichier E/S séparé par nœud.
%t
Identifiant de tâche (rang) relatif à la tâche courante. Cela créera un fichier E/S séparé par tâche.
%u
Nom d'utilisateur.
%x
Nom de la tâche.

Un nombre placé entre le caractère pourcentage et le spécificateur de format peut être utilisé pour ajouter des zéros au résultat dans le nom de fichier E/S jusqu'à un minimum de nombres spécifiés. Ce nombre est ignoré si le spécificateur de format correspond à des données non numériques (par exemple %N). Le nombre maximal est de 10. Si une valeur supérieure à 10 est utilisée, le résultat est un remplissage jusqu'à 10 caractères. Quelques exemples de la manière dont la chaîne de format peut être utilisée pour une tâche de 4 processus avec un JobID de 128 et un step id de 0 sont inclus ci-dessous :

job%J.out
job128.0.out
job%4j.out
job0128.out
job%2j-%2t.out
job128-00.out, job128-01.out, ...

PERFORMANCE

L'exécution de srun envoie un appel de procédure distante à slurmctld. Si un nombre suffisant d'appels provenant de srun ou d'autres commandes client Slurm qui envoient des appels de procédure distante au démon slurmctld arrivent simultanément, cela peut entraîner une dégradation des performances du démon slurmctld, entraînant potentiellement un déni de service.

Ne lancez pas srun ou d'autres commandes client Slurm qui envoient des appels de procédure distante à slurmctld à partir de boucles dans des scripts shell ou d'autres programmes. Assurez-vous que les programmes limitent les appels à srun au minimum nécessaire pour les informations que vous essayez de collecter.

SIGNaux ET SÉQUENCES D'ÉCHAPРEMENT

Les signaux envoyés à la commande srun sont automatiquement transmis aux tâches qu'elle contrôle, à quelques exceptions près. La séquence d'échappement <control-c> signalera l'état de toutes les tâches associées à la commande srun. Si <control-c> est entré deux fois en moins d'une seconde, alors le signal SIGINT associé sera envoyé à toutes les tâches et une séquence de terminaison sera lancée, envoyant SIGCONT, SIGTERM et SIGKILL à toutes les tâches générées. Si un troisième <control-c> est reçu, le programme srun sera terminé sans attendre que les tâches distantes se terminent ou que leur E/S soient complétées.

La séquence d'échappement <control-z> est actuellement ignorée.

PRISE EN CHARGE MPI

L'utilisation de MPI dépend du type de MPI utilisé. Il existe trois modes de fonctionnement fondamentalement différents utilisés par ces diverses implémentations MPI.

1. Slurm lance directement les tâches et effectue l'initialisation des communications via les API PMI2 ou PMIx. Par exemple : "srun -n16 a.out".

2. Slurm crée une allocation de ressources pour le travail, puis mpirun lance les tâches en utilisant l'infrastructure de Slurm (OpenMPI).

3. Slurm crée une allocation de ressources pour le travail, puis mpirun lance les tâches en utilisant un mécanisme autre que Slurm, tel que SSH ou RSH. Ces tâches sont initiées en dehors de la surveillance ou du contrôle de Slurm. L'épilogue de Slurm doit être configuré pour purger ces tâches lorsque l'allocation du travail est cédée, ou l'utilisation de pam_slurm_adopt est fortement recommandée.

Voir https://slurm.schedmd.com/mpi_guide.html pour plus d'informations sur l'utilisation de ces diverses implémentations MPI avec Slurm.

CONFIGURATION DE PROGRAMMES MULTIPLES

Les commentaires dans le fichier de configuration doivent commencer par un "#" dans la colonne un. Le fichier de configuration contient les champs suivants séparés par des espaces blancs :

Rang de la tâche
Un ou plusieurs rangs de tâches pour utiliser cette configuration. Plusieurs valeurs peuvent être séparées par des virgules. Des plages peuvent être indiquées avec deux nombres séparés par un "-", le plus petit nombre étant le premier (par exemple, "0-4" et non "4-0"). Pour indiquer toutes les tâches non spécifiées autrement, spécifiez un rang de '*' comme dernière ligne du fichier. Si une tentative est faite pour lancer une tâche pour laquelle aucun programme exécutable n'est défini, le message d'erreur suivant sera produit : "Aucun programme exécutable spécifié pour cette tâche".
Exécutable
Le nom du programme à exécuter. Peut être un chemin d'accès complet si désiré.
Arguments
Arguments du programme. L'expression "%t" sera remplacée par le numéro de la tâche. L'expression "%o" sera remplacée par le décalage de la tâche dans cette plage (par exemple, une valeur de rang de tâche configurée de "1-5" aurait des valeurs de décalage de "0-4"). Des guillemets simples peuvent être utilisés pour éviter que les valeurs incluses ne soient interprétées. Ce champ est facultatif. Tous les arguments pour le programme entrés sur la ligne de commande seront ajoutés aux arguments spécifiés dans le fichier de configuration.

Par exemple :

$ cat silly.conf
###################################################################
# Fichier de configuration srun pour programmes multiples
#
# srun -n8 -l --multi-prog silly.conf
###################################################################
4-6       hostname
1,7       echo  task:%t
0,2-3     echo  offset:%o
$ srun -n8 -l --multi-prog silly.conf
0: offset:0
1: task:1
2: offset:1
3: offset:2
4: linux15.llnl.gov
5: linux16.llnl.gov
6: linux17.llnl.gov
7: task:7

Cet exemple démontre comment les travaux qui ne sont pas répartis uniformément entre plusieurs nœuds peuvent rencontrer des problèmes où les tâches ne peuvent pas démarrer alors qu'il y a suffisamment de CPUs libres pour exécuter cette tâche sur un seul nœud.
