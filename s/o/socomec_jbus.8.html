NOM

socomec_jbus - Pilote pour onduleur Socomec JBUS avec connexion série Modbus RS-232.

SYNTAXE

socomec_jbus -h

socomec_jbus -a NOM_DU_PÉRIPHÉRIQUE [OPTIONS]


Note

Cette page de manuel documente uniquement les caractéristiques spécifiques au matériel du pilote socomec_jbus. Pour plus d'informations sur le pilote principal, consultez nutupsdrv(8).

MATÉRIEL SUPPORTÉ

Ce pilote prend en charge la série Socomec JBUS, onduleurs en ligne (double conversion) avec les caractéristiques suivantes.

1. Onduleurs monophasés et triphasés
2. Connexion : RS-232

Ceux-ci sont généralement fournis avec une carte de gestion Netvision WEB/SNMP / boîte externe qui serait mieux servie par le pilote snmp-ups(8). Si Netvision n'est pas disponible, vous pouvez connecter l'onduleur directement via le port série et utiliser ce pilote.

Actuellement, il n'a été testé que sur le modèle suivant.

•DIGYS 3/3 15kVA

En théorie, tout modèle Socomec JBUS devrait fonctionner. Il devrait être découvert comme « Unknown Socomec JBUS » avec un identifiant numérique que je devrai ajouter à la liste des onduleurs pris en charge.

Malheureusement, Socomec ne documente que DELPHYS MX et DELPHYS MX elite et je connais l'ID de mon propre DIGYS, donc il est probable que votre modèle ne sera pas reconnu mais fonctionnera probablement en grande partie. Veuillez signaler les résultats réussis ou infructueux au traqueur de bugs ou à la liste de diffusion. Assurez-vous d'inclure le numéro de modèle complet de votre onduleur manuellement dans votre rapport.

socomec_jbus utilise le projet libmodbus pour l'implémentation Modbus.

CABLAGE

L'onduleur possède un port RS-232 qui doit être connecté avec un câble NULL-modem à un port série du PC. L'onduleur testé a un connecteur DB9 femelle, donc si vous fabriquez le câble vous-même, notez le type de connecteur pour éviter d'utiliser des changeurs de genre.

RS-232 est pris en charge sur tous les systèmes d'exploitation, soit via un port série intégré à votre ordinateur, soit en utilisant un convertisseur USB vers RS-232 externe. Si vous prévoyez d'utiliser un convertisseur USB vers RS-232, assurez-vous qu'il est pris en charge par votre système d'exploitation.

INSTALLATION

Ce pilote devrait être compilé par défaut si libmodbus et les en-têtes de développement sont disponibles. Vous pouvez forcer le script de configuration à le compiler avec les arguments suivants :

:; ./configure --with-serial=yes --with-modbus=yes

Vous devez également accorder les permissions appropriées (R/W) sur le fichier du périphérique série local pour permettre à l'utilisateur d'exécution du pilote NUT d'y accéder. Cela peut nécessiter une configuration supplémentaire pour les scripts de démarrage, les règles udev ou upower, afin d'appliquer les droits à chaque démarrage — surtout si vos nœuds de périphérique sont suivis par un système de fichiers virtuel.

Par exemple, un convertisseur USB vers série peut être identifié comme /dev/ttyACM0 ou /dev/ttyUSB0 sous Linux, ou /dev/ttyU0 sous FreeBSD (notez le « U » majuscule). Un port série intégré peut être identifié comme /dev/ttyS0 sous Linux ou l'un des noms /dev/cua* sous FreeBSD.

COMMANDES INSTANTANÉES

Ce pilote ne prend pas (encore ?) en charge l'envoi de commandes à l'onduleur.

VARIABLES

Ce pilote ne prend pas en charge les variables d'exécution écrivables (voir upsrw(8)) : pour les mêmes raisons. Les deux devraient être triviaux à implémenter, mais comme j'ai déjà trouvé une ou deux incohérences dans la documentation, je m'abstiens d'essayer.

PROBLÈMES CONNUS ET BOGUES

Eh bien, c'est une version alpha au mieux, mais jusqu'à présent, elle semble signaler l'état de l'onduleur de manière fiable. Principalement basé sur le travail de Yifeng Li <tomli@tomli.me> sur le huawei-ups2000(8) dans le même arbre source.

Échec de lecture sur certaines adresses JBUS

Le pilote interroge toutes les adresses JBUS documentées, et il est tout à fait possible que votre modèle d'onduleur n'en prenne pas en charge une (par exemple, le Digys ne prend pas en charge l'adresse 0x1020 qui devrait fournir l'état actuel de l'onduleur). Cela devrait être enregistré avec LOG_ERR à partir de modbus_read_input_registers() ainsi que l'adresse qui a produit l'erreur.

Données obsolètes

Dans certaines circonstances, certains registres peuvent retourner des valeurs invalides et déclencher une erreur « données obsolètes ». Une fois qu'une erreur de données obsolètes s'est produite, vous devriez voir des messages d'erreur similaires à l'exemple ci-dessous dans le journal système.

socomec_jbus: modbus_read_input_registers(addr:XXXX, count:Z):
    Illegal data address
upsd: Data for UPS [socomec] is stale - check driver
upsd: UPS [socomec] data is no longer stale

Jusqu'à présent, tous les problèmes connus ont été résolus par l'auteur, mais un problème inconnu ne peut être exclu. Si vous avez rencontré des problèmes de « données obsolètes » lors d'une utilisation normale, veuillez déposer un rapport de bug avec les journaux complets joints.

Avant de dépanner ou de signaler un problème, il est important de vérifier votre journal dmesg pour les événements de connexion et de déconnexion USB afin d'éviter de perdre du temps sur le pilote NUT alors que le problème réel est USB. Par exemple, si quelqu'un retire le câble du port USB, ou si un nouvel appareil USB est branché sur un concentrateur/port USB qui peine à alimenter ses ports (courant sur les ordinateurs monocartes comme le Raspberry Pi), ou si vous avez un câblage défectueux ou du bruit EMI, le convertisseur série peut être déconnecté de l'USB, au moins brièvement. Cela crée des données obsolètes permanentes, le pilote doit être redémarré (rebrancher l'USB ne résoudra pas le problème, car le pilote utilise toujours le périphérique série inexistant). Ces problèmes USB n'ont généralement rien à voir avec NUT. Si c'est le cas, vous devriez résoudre le problème USB sous-jacent — vérifiez le câble, vérifiez le convertisseur, essayez un concentrateur USB alimenté, essayez un isolateur USB pleine vitesse, etc.
