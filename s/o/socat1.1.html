NOM

socat - Relais polyvalent (SOcket CAT)

SYNTAXE

socat [options] <adresse> <adresse>
socat -V
socat -h[h[h]] | -?[?[?]]
filan
procan

DESCRIPTION

Socat est un utilitaire en ligne de commande qui établit deux flux d'octets bidirectionnels et transfère des données entre eux. Comme les flux peuvent être construits à partir d'un grand nombre de types de sinks et de sources de données différents (voir les types d'adresses), et comme de nombreuses options d'adresse peuvent être appliquées aux flux, socat peut être utilisé à de nombreuses fins différentes.

Filan est un utilitaire qui imprime des informations sur ses descripteurs de fichiers actifs sur la sortie standard. Il a été écrit pour le débogage de socat, mais pourrait également être utile à d'autres fins. Utilisez l'option -h pour plus d'informations.

Procan est un utilitaire qui imprime des informations sur les paramètres des processus sur la sortie standard. Il a été écrit pour mieux comprendre certaines propriétés des processus UNIX et pour le débogage de socat, mais pourrait également être utile à d'autres fins.

Le cycle de vie d'une instance de socat se compose typiquement de quatre phases.

Dans la phase d'initialisation, les options de la ligne de commande sont analysées et la journalisation est initialisée.

Pendant la phase d'ouverture, socat ouvre la première adresse et ensuite la seconde adresse. Ces étapes sont généralement bloquantes ; ainsi, en particulier pour les types d'adresses complexes comme les socks, les demandes de connexion ou les dialogues d'authentification doivent être terminés avant que la prochaine étape ne soit démarrée.

Dans la phase de transfert, socat surveille les descripteurs de fichiers de lecture et d'écriture des deux flux via select(), et, lorsqu'il y a des données disponibles sur un côté et qu'elles peuvent être écrites de l'autre côté, socat les lit, effectue des conversions de caractères de nouvelle ligne si nécessaire, et écrit les données sur le descripteur de fichier d'écriture de l'autre flux, puis continue d'attendre d'autres données dans les deux directions.

Lorsqu'un des flux atteint effectivement la fin de fichier (EOF), la phase de clôture commence. Socat transfère la condition d'EOF à l'autre flux, c'est-à-dire qu'il essaie d'arrêter uniquement son flux d'écriture, lui donnant une chance de se terminer gracieusement. Pendant une durée définie, socat continue de transférer des données dans l'autre direction, mais ferme ensuite tous les canaux restants et se termine.

OPTIONS

Socat fournit quelques options en ligne de commande qui modifient le comportement du programme. Elles n'ont rien à voir avec les options dites d'adresse qui sont utilisées comme parties de spécifications d'adresse.

-V
Affiche la version et les informations sur les fonctionnalités disponibles sur la sortie standard, puis quitte.
-h | -?
Affiche un texte d'aide sur la sortie standard décrivant les options de la ligne de commande et les types d'adresses disponibles, puis quitte.
-hh | -??
Comme -h, plus une liste des noms courts de toutes les options d'adresse disponibles. Certaines options dépendent de la plateforme, donc cette sortie est utile pour vérifier l'implémentation particulière.
-hhh | -???
Comme -hh, plus une liste de tous les noms d'options d'adresse disponibles.
-d
Sans cette option, seuls les messages d'erreur fatals, d'erreur et d'avertissement sont imprimés ; l'application de cette option imprime également des messages de notification. Voir DIAGNOSTICS pour plus d'informations.
-d0
Avec cette option, seuls les messages d'erreur fatals et d'erreur sont imprimés ; ceci restaure le comportement de socat jusqu'à la version 1.7.4.
-d -d | -dd | -d2
Imprime les messages d'erreur fatals, d'erreur, d'avertissement et de notification.
-d -d -d | -ddd | -d3
Imprime les messages d'erreur fatals, d'erreur, d'avertissement, de notification et d'information.
-d -d -d -d | -dddd | -d4
Imprime les messages d'erreur fatals, d'erreur, d'avertissement, de notification, d'information et de débogage.
-D
Journalise les informations sur les descripteurs de fichiers avant de démarrer la phase de transfert.
--experimental
Les nouvelles fonctionnalités qui ne sont pas bien testées ou qui sont sujettes à modification à l'avenir doivent être explicitement activées à l'aide de cette option.
-ly[<facility>]
Écrit les messages dans syslog au lieu de stderr ; sévérité telle que définie avec l'option -d. Avec <facility> optionnel, le type syslog peut être sélectionné, le défaut est "daemon". Les bibliothèques tierces pourraient ne pas respecter cette option.
-lf <logfile>
Écrit les messages dans <logfile> [nom de fichier] au lieu de stderr. Certaines bibliothèques tierces, en particulier libwrap, pourraient ne pas respecter cette option.
-ls
Écrit les messages sur stderr (c'est le comportement par défaut). Certaines bibliothèques tierces pourraient ne pas respecter cette option, en particulier libwrap semble uniquement journaliser vers syslog.
-lp<progname>
Remplace le nom du programme affiché dans les messages d'erreur et utilisé pour construire les noms de variables d'environnement.
-lu
Éténd l'horodatage des messages d'erreur à la résolution de la microseconde. Ne fonctionne pas lors de la journalisation vers syslog.
-lm[<facility>]
Mode de journalisation mixte. Pendant le démarrage, les messages sont imprimés sur stderr ; lorsque socat démarre la boucle de phase de transfert ou le mode démon (c'est-à-dire après avoir ouvert tous les flux et avant de démarrer le transfert de données, ou, avec les sockets d'écoute avec l'option fork, avant le premier appel accept), il bascule la journalisation vers syslog. Avec <facility> optionnel, le type syslog peut être sélectionné, le défaut est "daemon".
-lh
Ajoute le nom d'hôte aux messages de journalisation. Utilise la valeur de la variable d'environnement HOSTNAME ou la valeur récupérée avec uname() si HOSTNAME n'est pas définie.
-v
Écrit les données transférées non seulement vers leurs flux cibles, mais aussi vers stderr. Le format de sortie est textuel avec quelques conversions pour la lisibilité, et précédé de "> " ou "< " indiquant les directions du flux.
-x
Écrit les données transférées non seulement vers leurs flux cibles, mais aussi vers stderr. Le format de sortie est hexadécimal, précédé de "> " ou "< " indiquant les directions du flux. Peut être combiné avec -v.
-r <fichier>
Enregistre les données brutes (binaires) circulant de l'adresse gauche à l'adresse droite dans le fichier donné. Le nom du fichier peut contenir des références aux variables d'environnement et à $$ (pid), $PROGNAME (voir l'option -lp), $TIMESTAMP (utilise le format %Y%m%dT%H%M%S), et MICROS (microsecondes de la journée). Ces références doivent bien sûr être protégées de l'expansion du shell.
-R <fichier>
Enregistre les données brutes (binaires) circulant de l'adresse droite à l'adresse gauche dans le fichier donné. Le nom du fichier peut contenir des références aux variables d'environnement et à $$ (pid), $PROGNAME (voir l'option -lp), $TIMESTAMP (utilise le format %Y%m%dT%H%M%S), et MICROS (microsecondes de la journée). Ces références doivent bien sûr être protégées de l'expansion du shell.
-s
Arrête l'exécution de socat immédiatement après l'ouverture des deux adresses, avant le transfert de données.
-S
Envoie un signal de terminaison aux processus associés après l'ouverture des deux adresses, avant le transfert de données.
-N
Ne pas envoyer le signal de terminaison, sauf s'il est spécifiquement demandé.
-k
Envoyer un signal de fin de transmission (EOF) à l'autre flux lorsque le premier flux se termine.
-K
Ne pas envoyer de signal de fin de transmission (EOF) à l'autre flux lorsque le premier flux se termine.
-F
Forcer la fermeture des deux flux lors de la réception d'un EOF.
-R
Déconnecter le socket après le transfert de données.
-T<timeout>
Définir un délai d'attente pour le transfert de données.
-t<timeout>
Définir un délai d'attente pour la connexion.
-w<timeout>
Définir un délai d'attente pour l'attente des données.
-X
Désactiver le transfert de données.
-z
Ne pas fermer les sockets après le transfert de données.
-Z
Fermer les sockets après le transfert de données.
-p
Ne pas fermer les descripteurs de fichiers après le transfert de données.
-P
Fermer les descripteurs de fichiers après le transfert de données.
-u
Désactiver la conversion des fins de ligne.
-U
Activer la conversion des fins de ligne.
-i
Ignorer les signaux d'interruption.
-I
Ne pas ignorer les signaux d'interruption.

EXEMPLES

Pour rediriger un port TCP vers un autre :

socat TCP-LISTEN:8080 TCP:localhost:80

Pour créer un serveur TCP qui exécute une commande :

socat TCP-LISTEN:21 FILE:`tty`,raw,echo=0 EXEC:'/bin/login'

Pour transférer des données entre deux pipes :

socat PIPE:/tmp/monpipe1 PIPE:/tmp/monpipe2

Pour se connecter à un serveur HTTPS avec un certificat client :

socat OPENSSL:example.com:443,cert=client.pem,key=client.key -

DIAGNOSTICS

Le niveau de journalisation peut être contrôlé avec les options -d, -dd, -ddd, -dddd.

  • -d : Affiche les messages d'avertissement et d'erreur.
  • -dd : Affiche les messages d'information en plus des avertissements et erreurs.
  • -ddd : Affiche les messages de débogage en plus des avertissements, erreurs et informations.
  • -dddd : Affiche des informations très détaillées sur le fonctionnement interne.

Les messages sont imprimés sur stderr par défaut. Ils peuvent être redirigés vers syslog avec l'option -ly ou vers un fichier avec l'option -lf.

SPÉCIFICATIONS D'ADRESSE

Avec les arguments de ligne de commande d'adresse, l'utilisateur donne à socat des instructions et les informations nécessaires à l'établissement des flux d'octets.

Une spécification d'adresse se compose généralement d'un mot-clé de type d'adresse, de zéro ou plusieurs paramètres d'adresse requis séparés par ':' du mot-clé et les uns des autres, et de zéro ou plusieurs options d'adresse séparées par ','.

Le mot-clé spécifie le type d'adresse (par exemple, TCP4, OPEN, EXEC). Pour certains mots-clés, il existe des synonymes ('-' pour STDIO, TCP pour TCP4). Les mots-clés ne sont pas sensibles à la casse. Pour quelques types d'adresses spéciaux, le mot-clé peut être omis : les spécifications d'adresse commençant par un nombre sont supposées être des adresses FD (descripteur de fichier brut) ; si un '/' est trouvé avant le premier ':' ou ',', GOPEN (ouverture de fichier générique) est supposé.

Le nombre et le type requis de paramètres d'adresse dépendent du type d'adresse. Par exemple, TCP4 nécessite une spécification de serveur (nom ou adresse), et une spécification de port (numéro ou nom de service).

Zéro ou plusieurs options d'adresse peuvent être fournies avec chaque adresse. Elles influencent l'adresse d'une certaine manière. Les options consistent en un mot-clé d'option ou un mot-clé d'option et une valeur, séparés par '='. Les mots-clés d'option ne sont pas sensibles à la casse. Pour filtrer les options utiles avec un type d'adresse, chaque option est membre d'un groupe d'options. Pour chaque type d'adresse, un ensemble de groupes d'options est autorisé. Seules les options appartenant à l'un de ces groupes d'adresses peuvent être utilisées (sauf avec l'option -g).

Les spécifications d'adresse suivant le schéma ci-dessus sont également appelées spécifications d'adresse simples. Deux adresses simples peuvent être combinées avec "!!" pour former une adresse de type double pour un canal. Ici, la première adresse est utilisée par socat pour lire des données, et la seconde adresse pour écrire des données. Il n'y a aucun moyen de spécifier une option une seule fois pour qu'elle s'applique aux deux adresses simples.

Habituellement, les adresses sont ouvertes en mode lecture/écriture. Lorsqu'une adresse fait partie d'une spécification d'adresse double, ou lorsque l'option -u ou -U est utilisée, une adresse peut être utilisée uniquement pour la lecture ou pour l'écriture. Il est important de tenir compte de cela avec certains types d'adresses.

Avec socat version 1.5.0 et supérieure, l'analyse lexicale tente de gérer les guillemets et les parenthèses de manière significative et permet l'échappement des caractères spéciaux. Si l'un des caractères ( { [ ' est trouvé, le caractère de fermeture correspondant - ) } ] ' - est recherché ; ils peuvent également être imbriqués. Dans ces constructions, les caractères et chaînes spéciaux de socat : , !! ne sont pas traités spécialement. Tous ces caractères et chaînes peuvent être échappés avec \ ou entre ""

OPTIONS D'ADRESSE

Les options d'adresse peuvent être appliquées aux spécifications d'adresse pour influencer le processus d'ouverture des adresses et les propriétés des canaux de données résultants.

Pour des raisons techniques, toutes les options ne peuvent pas être appliquées à tous les types d'adresses ; par exemple, l'application d'une option de socket à un fichier ordinaire échouera. Pour intercepter la plupart des combinaisons inutiles dès la phase d'ouverture, le concept de groupes d'options a été introduit. Chaque option appartient à un ou plusieurs groupes d'options. Les options ne peuvent être utilisées qu'avec des types d'adresses qui prennent en charge au moins un de leurs groupes d'options (mais voir l'option -g).

Les options d'adresse ont des types de données auxquels leurs valeurs doivent être conformes. Chaque option d'adresse se compose simplement d'un mot-clé ou d'un mot-clé suivi de "=valeur", où la valeur doit être conforme au type de l'option. Certaines options d'adresse manipulent

paramètres des appels système ; par exemple, l'option sync définit le drapeau O_SYNC avec l'appel open(). D'autres options provoquent un appel système ou bibliothèque ; par exemple, avec l'option `ttl=valeur’, l'appel setsockopt(fd, SOL_IP, IP_TTL, valeur, sizeof(int)) est appliqué. D'autres options définissent des variables internes de socat qui sont utilisées pendant le transfert de données ; par exemple, `crnl’ provoque des conversions de caractères explicites. Quelques options ont des implémentations plus complexes ; par exemple, su-d (substuser-delayed) interroge certaines informations d'utilisateur et de groupe, les stocke, et les applique plus tard après un éventuel appel chroot().

Si plusieurs options sont données à une adresse, leur séquence dans la spécification de l'adresse n'a (presque) aucun effet sur la séquence de leur exécution/application. Au lieu de cela, socat a un modèle de *phase d'option* intégré qui essaie de placer les options dans un ordre utile. Certaines options existent sous différentes formes (par exemple, unlink, unlink-early, unlink-late) pour contrôler le moment de leur exécution.

Si la même option est spécifiée plus d'une fois au sein d'une même spécification d'adresse, avec des valeurs égales ou différentes, l'effet dépend du type d'option. Les options entraînant des appels de fonction comme setsockopt() provoquent des invocations multiples. Avec les options qui définissent des paramètres pour un appel requis comme open() ou qui définissent des drapeaux internes, la valeur de la dernière occurrence de l'option est effective.

L'existence ou la sémantique de nombreuses options dépendent du système. Socat n'essaie généralement PAS d'émuler des fonctionnalités libc ou noyau manquantes, il fournit simplement une interface au système sous-jacent. Ainsi, si un système d'exploitation manque d'une fonctionnalité, l'option associée n'est tout simplement pas disponible sur cette plateforme.

Les paragraphes suivants introduisent uniquement les options d'adresse les plus courantes. Pour une référence plus complète et pour trouver des informations sur les noms d'options canoniques, les alias, les phases d'options et les plateformes, consultez le fichier xio.help.

Groupe d'options FD

Ce groupe d'options contient des options qui sont appliquées à un descripteur de fichier de style UN*X, quelle que soit la manière dont il a été généré. Étant donné que tous les types d'adresses socat actuels sont basés sur des descripteurs de fichiers, ces options peuvent être appliquées à n'importe quelle adresse.
Note : Certaines de ces options sont également membres d'un autre groupe d'options, qui fournit un mécanisme différent, non basé sur les descripteurs de fichiers. Pour ces options, cela dépend du type d'adresse réel et de ses groupes d'options, lequel des mécanismes est utilisé. Le second mécanisme, non basé sur les descripteurs de fichiers, est prioritaire.

cloexec[=<bool>]
Définit le drapeau FD_CLOEXEC avec l'appel système fcntl() à la valeur <bool>. S'il est défini, le descripteur de fichier est fermé lors des appels de fonction de la famille exec(). Socat gère en interne ce drapeau pour les descripteurs de fichiers qu'il contrôle, donc dans la plupart des cas, il ne sera pas nécessaire d'appliquer cette option.
setlk[=<bool>]
Tente de définir un verrou d'écriture discrétionnaire sur l'ensemble du fichier à l'aide de l'appel système fcntl(fd, F_SETLK, ...). Si le fichier est déjà verrouillé, cet appel entraîne une erreur. Sous Linux, lorsque les permissions du fichier pour le groupe sont « S » (g-x,g+s), et que le système de fichiers est monté localement avec l'option « mand », le verrou est obligatoire, c'est-à-dire qu'il empêche d'autres processus d'ouvrir le fichier.
setlkw[=<bool>]
Tente de définir un verrou d'écriture discrétionnaire en attente sur l'ensemble du fichier à l'aide de l'appel système fcntl(fd, F_SETLKW, ...). Si le fichier est déjà verrouillé, cet appel bloque. Voir l'option setlk pour des informations sur la rendue obligatoire de ce verrou.
setlk-rd[=<bool>]
Tente de définir un verrou de lecture discrétionnaire sur l'ensemble du fichier à l'aide de l'appel système fcntl(fd, F_SETLK, ...). Si le fichier est déjà verrouillé en écriture, cet appel entraîne une erreur. Voir l'option setlk pour des informations sur la rendue obligatoire de ce verrou.
setlkw-rd[=<bool>]
Tente de définir un verrou de lecture discrétionnaire en attente sur l'ensemble du fichier à l'aide de l'appel système fcntl(fd, F_SETLKW, ...). Si le fichier est déjà verrouillé en écriture, cet appel bloque. Voir l'option setlk pour des informations sur la rendue obligatoire de ce verrou.
flock-ex[=<bool>]
Tente de définir un verrou consultatif exclusif bloquant sur le fichier à l'aide de l'appel système flock(fd, LOCK_EX). Socat se bloque dans cet appel si le fichier est verrouillé par un autre processus.
flock-ex-nb[=<bool>]
Tente de définir un verrou consultatif exclusif non bloquant sur le fichier à l'aide de l'appel système flock(fd, LOCK_EX|LOCK_NB). Si le fichier est déjà verrouillé, cette option entraîne une erreur.
flock-sh[=<bool>]
Tente de définir un verrou consultatif partagé bloquant sur le fichier à l'aide de l'appel système flock(fd, LOCK_SH). Socat se bloque dans cet appel si le fichier est verrouillé par un autre processus.
flock-sh-nb[=<bool>]
Tente de définir un verrou consultatif partagé non bloquant sur le fichier à l'aide de l'appel système flock(fd, LOCK_SH|LOCK_NB). Si le fichier est déjà verrouillé, cette option entraîne une erreur.
lock[=<bool>]
Définit un verrou bloquant sur le fichier. Utilise le mécanisme setlk ou flock en fonction de la disponibilité sur la plateforme particulière. Si les deux sont disponibles, la variante POSIX (setlkw) est utilisée.
user=<utilisateur>
Définit l'<utilisateur> (propriétaire) du flux. Si l'adresse fait partie du groupe d'options NAMED, socat utilise l'appel système chown() après avoir ouvert le fichier ou s'être lié au socket de domaine UNIX (condition de concurrence !). Sans entrée de système de fichiers, socat définit l'utilisateur du flux à l'aide de l'appel système fchown(). Ces appels peuvent nécessiter des privilèges root.
user-late=<utilisateur>
Définit le propriétaire du descripteur de fichier à <utilisateur> avec l'appel système fchown() après avoir ouvert ou connecté le canal. Ceci n'est utile que sur les entrées du système de fichiers.
group=<groupe>

Si l'adresse fait partie du groupe d'options NAMED sans utiliser ces appels système, socat utilise l'appel système chmod() après avoir ouvert l'entrée du système de fichiers ou s'être lié au socket de domaine UNIX (condition de concurrence !). Modifie la méthode (dépendante de l'adresse) de fermeture de la partie écriture d'une connexion pour ne rien faire.
shut-down[=<bool>]

Appelle ioctl() avec la valeur de la requête comme deuxième argument et NULL comme troisième argument. Cette option permet d'utiliser des ioctls qui ne sont pas explicitement implémentés dans socat.

Appelle ioctl() avec la valeur de la requête comme deuxième argument et la valeur entière comme troisième argument.
ioctl-intp=<request>:<value>
Appelle ioctl() avec la valeur de la requête comme deuxième argument et un pointeur vers la valeur entière comme troisième argument.

Appelle ioctl() avec la valeur de la requête comme deuxième argument et un pointeur vers la valeur de données donnée comme troisième argument. Ces données doivent être spécifiées sous forme <dalan>.

Les adresses de type LISTEN et CONNECT prennent l'option fork pour gérer plusieurs connexions via des processus enfants.

Après l'établissement d'une connexion, gère son canal dans un processus enfant et maintient le processus parent en train d'essayer de produire plus de connexions, soit en écoutant, soit en se connectant en boucle (exemple).

Diminue la gravité des messages de journalisation produits par les processus enfants. Par exemple, avec la valeur 1, les notices sont enregistrées en tant qu'informations (ou supprimées en fonction de l'option -dX), et les erreurs sont enregistrées en tant qu'avertissements mais provoquent toujours la terminaison du processus enfant.

Cette option succède à l'option cool-write.

Groupe d'options FORK

Les adresses EXEC ou SYSTEM invoquent un programme à l'aide d'un processus enfant et transfèrent des données entre socat et le programme. Le mécanisme de communication interprocessus peut être influencé par les options suivantes. Par défaut, une paire de sockets (socketpair()) est créée et attribuée à stdin et stdout du processus enfant, tandis que stderr est hérité du processus socat, et le processus enfant utilise les descripteurs de fichiers 0 et 1 pour communiquer avec le processus socat principal.

nofork
Ne crée pas de sous-processus pour exécuter le programme, mais appelle execvp() ou system() directement depuis l'instance socat actuelle. Cela évite la surcharge d'un autre processus entre le programme et son pair, mais introduit de nombreuses restrictions :
o
cette option ne peut être appliquée qu'à la deuxième adresse socat.
o
elle ne peut pas être appliquée à une partie d'une adresse double.
o
la première adresse socat ne peut pas être OPENSSL ou READLINE
o
les options socat -b, -t, -D, -l, -v, -x deviennent inutiles
o
pour les deux adresses, les options ignoreeof, cr, et crnl deviennent inutiles
o
pour les deux adresses, la gestion de fin/arrêt spécifique à l'adresse (par exemple, arrêt de socket gracieux) et les options associées deviennent inutiles
o
pour la deuxième adresse (celle avec l'option nofork), les options append, cloexec, flock, user, group, mode, nonblock, perm-late, setlk, et setpgid ne peuvent pas être appliquées. Certaines de celles-ci pourraient cependant être utilisées sur la première adresse.
pipes
Crée une paire de tubes anonymes pour la communication interprocessus au lieu d'une paire de sockets.
openpty
Établit la communication avec le sous-processus en utilisant un terminal virtuel créé avec openpty() au lieu du défaut (socketpair ou ptmx).
ptmx
Établit la communication avec le sous-processus en utilisant un terminal virtuel créé en ouvrant /dev/ptmx ou /dev/ptc au lieu du défaut (socketpair).
pty
Établit la communication avec le sous-processus en utilisant un terminal virtuel au lieu d'une paire de sockets. Crée le pty avec un mécanisme disponible. Si openpty et ptmx sont tous deux disponibles, il utilise ptmx car c'est conforme à POSIX (exemple).
ctty
Fait du pty le terminal de contrôle du sous-processus (exemple).
stderr
Redirige stderr du sous-processus vers son canal de sortie en faisant de stderr un dup() de stdout (exemple).
fdin=<fdnum>
Attribue le canal d'entrée du sous-processus à son descripteur de fichier <fdnum> au lieu de stdin (0). Le programme démarré depuis le sous-processus doit utiliser ce fd pour lire les données de socat (exemple).
fdout=<fdnum>
Attribue le canal de sortie du sous-processus à son descripteur de fichier <fdnum> au lieu de stdout (1). Le programme démarré depuis le sous-processus doit utiliser ce fd pour écrire des données à socat (exemple).
sighup, sigint, sigquit

Groupe d'options PTY

Ces options sont destinées à être utilisées avec le type d'adresse pty.

link=<nom-de-fichier>
Génère un lien symbolique qui pointe vers le pseudo-terminal (pty) réel. Cela peut aider à résoudre le problème selon lequel les ptys sont générés avec des noms plus ou moins imprévisibles, rendant difficile l'accès direct au pty généré par socat automatiquement. Avec cette option, l'utilisateur peut spécifier un point « fixe » dans la hiérarchie des fichiers qui l'aide à accéder au pty réel (exemple). Depuis la version 1.4.3 de socat, le lien symbolique est supprimé lorsque l'adresse est fermée (mais voir l'option unlink-close).
wait-slave
Bloque la phase d'ouverture jusqu'à ce qu'un processus ouvre le côté esclave du pty. Normalement, socat continue après avoir généré le pty en ouvrant la prochaine adresse ou en entrant dans la boucle de transfert. Avec l'option wait-slave, socat attend qu'un processus ouvre le côté esclave du pty avant de continuer. Cette option ne fonctionne que si le système d'exploitation fournit l'appel système poll(). Et elle dépend d'un comportement non documenté des ptys, donc elle ne fonctionne pas sur tous les systèmes d'exploitation. Elle a été testée avec succès sous Linux, FreeBSD, NetBSD, et sous Tru64 avec openpty.
pty-interval=<secondes>
Lorsque l'option wait-slave est définie, socat vérifie périodiquement la condition HUP à l'aide de poll() pour savoir si le côté esclave du pty a été ouvert. L'intervalle de sondage par défaut est de 1 seconde. Utilisez l'option pty-interval [timeval] pour modifier cette valeur.
sitout-eio=<timeval>
Le programme de connexion sous Linux ferme son tty/pty et le rouvre pour des raisons de sécurité. Pendant ce temps, le maître pty recevrait EIO lors des opérations d'E/S et pourrait se terminer. Avec cette option, socat tolère EIO pendant la durée spécifiée. Veuillez noter que dans cet état, socat bloque le trafic dans les deux directions, même s'il n'est pas lié à ce canal.

Active le mode FIPS s'il est compilé. Pour plus d'informations sur la norme d'implémentation de chiffrement FIPS, voir http://oss-institute.org/fips-faq.html. VALEURS DE DONNÉES

Cette section explique les différents types de données que les paramètres d'adresse et les options d'adresse peuvent prendre.

plage-adresse
Actuellement implémenté uniquement pour IPv4 et IPv6. Voir l'option d'adresse `plage’
bool
"0" ou "1"; si la valeur est omise, "1" est prise.
octet
Un nombre entier non signé, lu avec strtoul() , inférieur ou égal à UCHAR_MAX .
ligne-commande
Une chaîne spécifiant un nom de programme et ses arguments, séparés par des espaces simples.
données
Il s'agit d'une spécification de données plus générale, « dalan » (langage de description de données de bas niveau). La chaîne de texte donnée contient des informations sur le type de données cible et la valeur. Généralement, un caractère de tête spécifie le type de l'élément de données suivant. Dans son contexte spécifique, un type de données par défaut peut exister.
Actuellement, seules les spécifications suivantes sont implémentées :
i
Un nombre entier signé, stocké en ordre d'octets hôte.
Exemple : i-1000 (Nombre entier -1000)
I
Un nombre entier non signé, stocké en ordre d'octets hôte.
l
Un nombre entier long signé, stocké en ordre d'octets hôte.
L
Un nombre entier long non signé, stocké en ordre d'octets hôte.
s
Un nombre entier court signé, stocké en ordre d'octets hôte.
S
Un nombre entier court non signé, stocké en ordre d'octets hôte.
b
Un octet signé (char signé).
B
Un octet non signé (char non signé).
x
Suit un nombre pair de chiffres hexadécimaux, stocké sous forme de séquence d'octets, la longueur des données étant le nombre résultant d'octets.
Exemple : x7f000001 (Adresse IP 127.0.0.1)
"
Suit une chaîne utilisée avec les conversions communes \n \r \t \f \b \a \e \0 ; la chaîne doit être fermée avec ’"’. Veuillez noter que les guillemets et les barres obliques inverses doivent être échappés du shell et de la conversion socat. Aucun \0 implicite n'est ajouté.
Exemple : "Bonjour le monde !\n"
’
Un caractère unique, avec les conversions habituelles. Veuillez noter que les guillemets et les barres obliques inverses doivent être échappés du shell et de la conversion socat.
Exemple : ’a’ Les éléments de données peuvent être séparés par des espaces blancs sans avoir à répéter le spécificateur de type.
répertoire
Une chaîne avec la sémantique habituelle des noms de répertoire UN*X.
installation
Le nom d'une installation syslog en minuscules.
descripteur-fichier
Un type entier non signé, lu avec strtoul() , spécifiant un descripteur de fichier UN*X.
nom-fichier
Une chaîne avec la sémantique habituelle des noms de fichiers UN*X.
groupe
Si le premier caractère est un chiffre décimal, la valeur est lue avec strtoul() comme un entier non signé spécifiant un identifiant de groupe. Sinon, il doit s'agir d'un nom de groupe existant.
entier
Un nombre suivant les règles de la fonction strtol() avec la base "0", c'est-à-dire un nombre décimal, un nombre octal avec un "0" préfixé, ou un nombre hexadécimal avec un "0x" préfixé. La valeur doit tenir dans un int C.
interface
Une chaîne spécifiant le nom de l'interface réseau comme montré par ifconfig ou procan, par exemple "eth0".
adresse IP
Une adresse IPv4 en notation nombres-et-points, une adresse IPv6 en notation hexadécimale entre crochets, ou un nom d'hôte qui se résout en une adresse IPv4 ou IPv6.
Exemples : 127.0.0.1, [::1], www.dest-unreach.org, dns1
adresse IPv4
Une adresse IPv4 en notation nombres-et-points ou un nom d'hôte qui se résout en une adresse IPv4.
Exemples : 127.0.0.1, www.dest-unreach.org, dns2
adresse IPv6
Une adresse IPv6 en notation nombres-hexadécimaux-et-deux-points entre crochets, ou un nom d'hôte qui se résout en une adresse IPv6.
Exemples : [::1], [1234:5678:9abc:def0:1234:5678:9abc:def0], ip6name.domain.org
long
Un nombre lu avec strtol() . La valeur doit tenir dans un long C.
long long
Un nombre lu avec strtoll() . La valeur doit tenir dans un long long C.
off_t
Un nombre signé dépendant de l'implémentation, généralement de 32 bits, lu avec strtol ou strtoll.
off64_t
Un nombre signé dépendant de l'implémentation, généralement de 64 bits, lu avec strtol ou strtoll.
mode_t
Un entier non signé, lu avec strtoul() , spécifiant les bits de mode (permissions).
pid_t
Un nombre, lu avec strtol() , spécifiant un identifiant de processus.
port
Un uint16_t (nombre non signé de 16 bits) spécifiant un port TCP ou UDP, lu avec strtoul() .
protocole
Un nombre non signé de 8 bits, lu avec strtoul() .
size_t
Un nombre non signé avec les limitations de size_t, lu avec strtoul .
nom-socket
Une adresse de socket. Voir l'option d'adresse `bind’
chaîne
Une séquence de caractères, ne contenant pas ’\0’ et, en fonction de la position dans la ligne de commande, ’:’, ’,’, ou "!!". Notez que vous pourriez devoir échapper les métacaractères du shell dans la ligne de commande.
service TCP
Un nom de service, ne commençant pas par un chiffre, qui est résolu par getservbyname() , ou un nombre entier non signé de 16 bits lu avec strtoul() .
timeval
Un nombre flottant double spécifiant des secondes ; le nombre est mappé dans une structure timeval, composée de secondes et de microsecondes.
timespec
Un nombre flottant double spécifiant des secondes ; le nombre est mappé dans une structure timespec, composée de secondes et de nanosecondes.
service UDP
Un nom de service, ne commençant pas par un chiffre, qui est résolu par getservbyname() , ou un nombre entier non signé de 16 bits lu avec strtoul() .
entier non signé
Un nombre lu avec strtoul() . La valeur doit tenir dans un unsigned int C.
utilisateur
Si le premier caractère est un chiffre décimal, la valeur est lue avec strtoul() comme un entier non signé spécifiant un identifiant utilisateur. Sinon, il doit s'agir d'un nom d'utilisateur existant.
cid VSOCK
Un uint32_t (nombre non signé de 32 bits) spécifiant un identifiant de contexte VSOCK (CID), lu avec strtoul() . Il existe plusieurs adresses spéciales : VMADDR_CID_ANY (-1U) signifie n'importe quelle adresse pour la liaison ; VMADDR_CID_HOST (2) est l'adresse bien connue de l'hôte.
port VSOCK
Un uint32_t (nombre non signé de 32 bits) spécifiant un port VSOCK, lu avec strtoul() .

EXEMPLES

socat - TCP4:www.domain.org:80
transfère les données entre STDIO (-) et une connexion TCP4 vers le port 80 de l'hôte www.domain.org. Cet exemple crée une connexion interactive similaire à telnet ou netcat. Les paramètres du terminal stdin ne sont pas modifiés, vous pouvez donc fermer le relais avec ^D ou l'interrompre avec ^C.
socat -d -d \
READLINE,history=$HOME/.http_history \ 
TCP4:www.domain.org:www,crnl
ceci est similaire à l'exemple précédent, mais vous pouvez modifier la ligne actuelle de manière similaire à bash (READLINE) et utiliser le fichier d'historique .http_history ; socat affiche des messages sur la progression (-d -d). Le port est spécifié par le nom de service (www), et les caractères de terminaison de ligne réseau corrects (crnl) au lieu de NL sont utilisés.
socat \
TCP4-LISTEN:www \ 
TCP4:www.domain.org:www
installe un simple transmetteur de port TCP. Avec TCP4-LISTEN, il écoute sur le port local "www" jusqu'à ce qu'une connexion arrive, l'accepte, puis se connecte à l'hôte distant (TCP4) et démarre le transfert de données. Il n'acceptera pas de deuxième connexion.
socat -d -d -lmlocal2 \
TCP4-LISTEN:80,bind=myaddr1,reuseaddr,fork,su=nobody,range=10.0.0.0/8 \ 
TCP4:www.domain.org:80,bind=myaddr2
transmetteur de port TCP, chaque côté lié à une adresse IP locale différente (bind). Cet exemple gère un nombre presque arbitraire de connexions parallèles ou consécutives en créant un nouveau processus après chaque accept() . Il offre une sécurité minimale en passant à l'utilisateur nobody après la création du processus ; il n'autorise que les connexions provenant du réseau privé 10 (range) ; grâce à reuseaddr, il permet un redémarrage immédiat après la terminaison du processus maître, même si certains sockets enfants ne sont pas complètement arrêtés. Avec -lmlocal2, socat journalise sur stderr jusqu'à atteindre avec succès la boucle d'acceptation. La journalisation supplémentaire est activée
rected vers syslog avec la fonctionnalité local2. 
socat \
TCP4-LISTEN:5555,fork,tcpwrap=script \ 
EXEC:/bin/myscript,chroot=/home/sandbox,su-d=sandbox,pty,stderr
un serveur simple qui accepte des connexions (TCP4-LISTEN) et crée un nouveau processus enfant pour chaque connexion (fork) ; chaque enfant agit comme un relais unique. Le client doit correspondre aux règles pour le nom de processus démon "script" dans /etc/hosts.allow et /etc/hosts.deny, sinon l'accès est refusé (voir "man 5 hosts_access"). Pour exécuter le programme, le processus enfant se place dans le chroot de /home/sandbox, se transforme en utilisateur sandbox (su), puis démarre le programme /home/sandbox/bin/myscript. Socat et myscript communiquent via un pseudo tty (pty) ; le stderr de myscript est redirigé vers stdout, donc ses messages d'erreur sont transférés via socat au client connecté.
socat \
EXEC:"mail.sh target@domain.com",fdin=3,fdout=4 \ 
TCP4:mail.relay.org:25,crnl,bind=alias1.server.org,mss=512
mail.sh est un script shell, distribué avec socat, qui implémente un client SMTP simple. Il est programmé pour "parler" SMTP sur ses descripteurs de fichiers 3 (entrée) et 4 (sortie). Les options fdin et fdout indiquent à socat d'utiliser ces descripteurs de fichiers pour la communication avec le programme. Comme mail.sh hérite de stdin et stdout alors que socat ne les utilise pas, le script peut lire le corps d'un e-mail depuis stdin. Socat fait d'alias1 votre adresse source locale (bind), assure la terminaison correcte des lignes réseau (crnl) et envoie au maximum 512 octets de données par paquet (mss).
socat \
-,escape=0x0f \ 
/dev/ttyS0,rawer,crnl
ouvre une connexion interactive via la ligne série, par exemple pour communiquer avec un modem. rawer configure les paramètres du terminal de la console et de ttyS0 sur des valeurs pratiques, crnl convertit en caractères de nouvelle ligne corrects. escape permet de terminer le processus socat avec le caractère contrôle-O. Envisagez d'utiliser READLINE à la place de la première adresse.
socat \
UNIX-LISTEN:/tmp/.X11-unix/X1,fork \ 
SOCKS4:host.victim.org:127.0.0.1:6000,socksuser=nobody,sourceport=20
avec UNIX-LISTEN, socat ouvre un socket de domaine UNIX d'écoute /tmp/.X11-unix/X1. Ce chemin correspond à l'affichage local XWindow :1 sur votre machine, donc les connexions client XWindow vers DISPLAY=:1 sont acceptées. Socat communique ensuite avec le serveur SOCKS4 host.victim.org qui pourrait autoriser les connexions à partir du port source 20 en raison d'une faiblesse liée au FTP dans ses filtres IP statiques. Socat se fait passer pour invoqué par socksuser nobody, et demande à être connecté au port de bouclage 6000 (seules les configurations sockd faibles autoriseront ceci). Ainsi, nous obtenons une connexion au serveur XWindow de la victime et, si celui-ci ne nécessite pas de cookies MIT ou d'authentification Kerberos, nous pouvons commencer à travailler. Notez qu'il ne peut y avoir qu'une seule connexion à la fois, car TCP ne peut établir qu'une seule session avec un ensemble donné d'adresses et de ports.
socat -u \
/tmp/readdata,seek-end=0,ignoreeof \
STDIO
voici un exemple de transfert de données unidirectionnel (-u). Socat transfère des données du fichier /tmp/readdata (adresse implicite GOPEN), en commençant par sa fin actuelle (seek-end=0 fait démarrer la lecture de socat à la fin actuelle du fichier ; utilisez seek=0 ou aucune option de recherche pour lire d'abord les données existantes) dans un mode similaire à "tail -f" (ignoreeof). Le "fichier" peut également être un socket de domaine UNIX en écoute (n'utilisez pas d'option de recherche alors).
(sleep 5; echo PASSWORD; sleep 5; echo ls; sleep 1) | \
socat - \
EXEC:'ssh -l user server',pty,setsid,ctty
exécute une session ssh vers le serveur. Utilise un pty pour la communication entre socat et ssh, en fait le tty de contrôle de ssh (ctty), et fait de ce pty le propriétaire d'un nouveau groupe de processus (setsid), afin que ssh accepte le mot de passe de socat.
socat -u \
TCP4-LISTEN:3334,reuseaddr,fork \ 
OPEN:/tmp/in.log,creat,append
implémente un collecteur de messages simple basé sur le réseau. Pour chaque client se connectant au port 3334, un nouveau processus enfant est généré (option fork). Toutes les données envoyées par les clients sont ajoutées au fichier /tmp/in.log. Si le fichier n'existe pas, socat le crée (creat). L'option reuseaddr permet un redémarrage immédiat du processus serveur.
socat \
READLINE,noecho='[Pp]assword:' \ 
EXEC:'ftp ftp.server.com',pty,setsid,ctty
enveloppe un historique de commandes (READLINE) autour de l'utilitaire client ftp exécuté (EXEC). Cela permet l'édition et la réutilisation des commandes FTP pour une navigation relativement confortable dans la hiérarchie des répertoires FTP. Le mot de passe est affiché ! pty est nécessaire pour que ftp affiche une invite. Néanmoins, il peut y avoir une certaine confusion avec le mot de passe et les invites FTP.
socat \
PTY,link=$HOME/dev/vmodem0,rawer,wait-slave \ 
EXEC:'"ssh modemserver.us.org socat - /dev/ttyS0,nonblock,rawer"'
génère un périphérique de terminal pseudo (PTY) sur le client qui peut être atteint sous le lien symbolique $HOME/dev/vmodem0. Une application qui attend une ligne série ou un modem peut être configurée pour utiliser $HOME/dev/vmodem0 ; son trafic sera dirigé vers un serveur modem via ssh où une autre instance socat le relie à /dev/ttyS0.
sudo socat --experimental \
TCP4-LISTEN:8000,reuseaddr,fork,netns=namespace1 \ 
TCP4-CONNECT:server2:8000
crée un écouteur dans le namespace réseau donné qui accepte les connexions TCP sur le port 8000 et les transfère vers server2.
sudo socat --experimental \
TUN:192.168.2.1/24,up \ 
TUN:192.168.2.2/24,up,netns=namespace2
crée deux interfaces réseau virtuelles, une dans l'espace de noms par défaut, l'autre dans le namespace2, et transfère les paquets entre elles, agissant comme une connexion réseau virtuelle.
socat \
TCP4-LISTEN:2022,reuseaddr,fork \ 
PROXY:proxy.local:www.domain.org:22,proxyport=3128,proxyauth=username:s3cr3t
démarre un transmetteur qui accepte les connexions sur le port 2022, et les dirige via le démon proxy écoutant sur le port 3128 (proxyport) sur l'hôte proxy.local, en utilisant la méthode CONNECT, où elles sont authentifiées comme "username" avec "s3cr3t" (proxyauth). proxy.local devrait alors établir des connexions vers l'hôte www.domain.org sur le port 22.
socat - \
SSL:server:4443,cafile=./server.crt,cert=./client.pem
est un client OpenSSL qui tente d'établir une connexion sécurisée vers un serveur SSL. L'option cafile spécifie un fichier contenant les certificats de confiance : nous faisons confiance au serveur uniquement lorsqu'il présente l'un de ces certificats et prouve qu'il possède la clé privée associée. Sinon, la connexion est terminée. Avec cert, un fichier contenant le certificat client et la clé privée associée est spécifié. Ceci est requis si le serveur souhaite une authentification client ; de nombreux serveurs Internet ne le font pas.
La première adresse ('-') peut être remplacée par presque n'importe quelle autre adresse socat.
socat \
OPENSSL-LISTEN:4443,reuseaddr,pf=ip4,fork,cert=./server.pem,cafile=./client.crt \ 
PIPE
est un serveur OpenSSL qui accepte les connexions TCP, présente le certificat du fichier server.pem et force le client à présenter un certificat vérifié par rapport à cafile.crt.
La deuxième adresse ('PIPE') peut être remplacée par presque n'importe quelle autre adresse socat.
Pour des instructions sur la génération et la distribution de clés et de certificats OpenSSL, consultez la documentation supplémentaire de socat socat-openssl.txt.
echo |
socat -u - \
FILE:/tmp/bigfile,create,largefile,seek=100000000000
crée un fichier épars de plus de 100 Go + 1 octet ; cela nécessite un type de système de fichiers qui le prend en charge (ext2, ext3, ext4, reiserfs, xfs ; pas minix, vfat). L'opération d'écriture de 1 octet peut prendre du temps (reiserfs : quelques minutes ; ext2 : "pas" de temps), et le fichier résultant peut consommer de l'espace disque rien qu'avec ses inodes (reiserfs : 2 Mo ; ext2 : 16 Ko).
socat \
TCP-L:7777,reuseaddr,fork \ 
SYSTEM:'filan -i 0 -s >&2',nofork
écoute les connexions TCP entrantes sur le port 7777. Pour chaque connexion acceptée, il invoque un shell. Ce shell a son stdin et stdout directement connectés au socket TCP (nofork). Le shell démarre filan et lui permet d'imprimer les adresses des sockets sur stderr (votre fenêtre de terminal).
echo -e "\0\14\0\0\c" |
socat -u - \
FILE:/usr/bin/squid.exe,seek=0x00074420
fonctionne comme un éditeur binaire primitif : il écrit les 4 octets 000 014 000 000 dans l'exécutable /usr/bin/squid.exe à l'offset 0x00074420 (ce fut un correctif dans le monde réel pour faire fonctionner l'exécutable squid de Cygwin sous Windows, en 2004).
socat - \
TCP:www.blackhat.org:31337,readbytes=1000
se connecte à un service inconnu et empêche d'être inondé.
socat -U \
TCP:target:9999,end-close \ 
TCP-L:8888,reuseaddr,fork
fusionne les données arrivant de différents flux TCP sur le port 8888 en un seul flux vers target:9999. L'option end-close empêche les processus enfants créés par la deuxième adresse de terminer la connexion partagée vers 9999 (close(2) délie simplement l'inode qui reste actif tant que le processus parent est vivant ; shutdown(2) terminerait activement la connexion).
socat \
TCP-LISTEN:10021,reuseaddr,socktype=6,protocol=33,fork PIPE
est un serveur DCCP simple d'écho. DCCP est maintenant directement provisionné dans socat, cependant cet exemple montre comment utiliser les procédures TCP de socat et modifier le type de socket en SOCK_DCCP=6 (sous Linux) et le protocole IP en IPPROTO_DCCP=33.
socat - \
TCP:<serveur>:10021,reuseaddr,socktype=6,protocol=33,fork
est un client DCCP simple. DCCP est maintenant directement intégré dans socat, cependant cet exemple montre comment utiliser les procédures TCP de socat, mais modifie le type de socket en SOCK_DCCP=6 (sous Linux) et le protocole IP en IPPROTO_DCCP=33.
socat - \
UDP4-DATAGRAM:192.168.1.0:123,sp=123,broadcast,range=192.168.1.0/24
envoie un broadcast au réseau 192.168.1.0/24 et reçoit les réponses des serveurs de temps. Ignore les paquets NTP provenant d'hôtes extérieurs à ce réseau.
socat - \
SOCKET-DATAGRAM:2:2:17:x007bxc0a80100x0000000000000000,bind=x007bx00000000x0000000000000000,setsockopt-int=1:6:1,range=x0000xc0a80100x0000000000000000:x0000xffffff00x0000000000000000
est sémantiquement équivalent à l'exemple précédent, mais tous les paramètres sont spécifiés sous forme générique. La valeur 6 de setsockopt-int est la valeur Linux pour SO_BROADCAST.
socat - \
IP4-DATAGRAM:255.255.255.255:44,broadcast,range=10.0.0.0/8
envoie un broadcast aux réseaux locaux en utilisant le protocole 44. Accepte les réponses uniquement des plages d'adresses privées.
socat - \
UDP4-DATAGRAM:224.255.0.1:6666,bind=:6666,ip-add-membership=224.255.0.1:eth0
transfère les données de stdin à l'adresse multicast spécifiée en utilisant UDP. Les ports local et distant sont tous deux 6666. Indique à l'interface eth0 d'accepter également les paquets multicast du groupe donné. Plusieurs hôtes sur le réseau local peuvent exécuter cette commande, de sorte que toutes les données envoyées par l'un des hôtes seront reçues par tous les autres. Notez qu'il existe de nombreuses raisons possibles d'échec, notamment les filtres IP, les problèmes de routage, la mauvaise sélection de l'interface par le système d'exploitation, les ponts ou un commutateur mal configuré.
socat \
UDP:host2:4443 \ 
TUN:192.168.255.1/24,up
établit un côté d'un réseau virtuel (mais pas privé !) avec host2 où un processus similaire pourrait s'exécuter, avec une adresse UDP-L et tun de 192.168.255.2. Ils peuvent s'atteindre en utilisant les adresses 192.168.255.1 et 192.168.255.2. Notez que le streaming, par exemple via TCP ou SSL, ne garantit pas la conservation des limites de paquets et peut donc entraîner une perte de paquets.

socat \

INTERFACE:hdlc0
contourne le problème selon lequel pppd nécessite un périphérique série et pourrait donc ne pas fonctionner sur une ligne synchrone représentée par un périphérique réseau. socat -u \
STDIO \ 
POSIXMQ-SEND:/queue1,unlink-early,mq-prio=10
Écrit les paquets lus depuis stdio (c'est-à-dire les lignes d'entrée lors de l'exécution interactive) dans une file de messages POSIX, avec une priorité de 10.

SYSTEM:"worker.sh"
Reçoit des messages (paquets) de la file de messages POSIX et, pour chaque message, crée un sous-processus qui lit et traite le message. Au maximum 3 sous-processus sont autorisés simultanément.
socat -T 1 -d -d \
TCP-L:10081,reuseaddr,fork,crlf \ 
SYSTEM:"echo -e \"\\\"HTTP/1.0 200 OK\\\nDocumentType: text/plain\\\n\\\ndate: \$\(date\)\\\nserver:\$SOCAT_SOCKADDR:\$SOCAT_SOCKPORT\\\nclient: \$SOCAT_PEERADDR:\$SOCAT_PEERPORT\\\n\\\"\"; cat; echo -e \"\\\"\\\n\\\"\""
crée un serveur d'écho HTTP très primitif : chaque client HTTP qui se connecte reçoit une réponse HTTP valide contenant des informations sur l'adresse et le port du client tels que vus par l'hôte serveur, l'adresse de l'hôte (qui peut varier sur les serveurs multihébergés), et la requête originale du client.

grep SOCAT
attend un paquet UDP entrant sur le port 9999 et imprime les variables d'environnement fournies par socat. DIAGNOSTICS

Socat utilise un mécanisme de journalisation qui permet de filtrer les messages par sévérité. Les sévités fournies sont plus ou moins compatibles avec la priorité syslog appropriée. Avec une à quatre occurrences de l'option de ligne de commande -d, la priorité la plus basse des messages émis peut être sélectionnée. Chaque message contient un seul caractère majuscule spécifiant la sévérité du message (l'un de F, E, W, N, I ou D)

FATAL:
Conditions qui nécessitent une terminaison du programme inconditionnelle et immédiate.
ERROR:
Conditions qui empêchent le traitement correct du programme. Généralement, le programme est terminé (voir l'option -s).
WARNING:
Quelque chose n'a pas fonctionné correctement ou est dans un état où un traitement ultérieur correct ne peut être garanti, mais pourrait être possible.
NOTICE:
Actions intéressantes du programme, par exemple pour la supervision de socat dans un mode serveur.
INFO:
Description de ce que fait le programme, et peut-être pourquoi cela se produit. Permet de surveiller le cycle de vie des descripteurs de fichiers.
DEBUG:
Description du fonctionnement du programme, tous les appels système ou bibliothèques et leurs résultats.

Les messages de journal peuvent être écrits sur stderr, dans un fichier ou sur syslog.

À la sortie, socat renvoie le statut 0 s'il s'est terminé en raison d'une fin de fichier (EOF) ou d'un délai d'inactivité, une valeur positive en cas d'erreur, et une valeur négative en cas d'erreur fatale.

VARIABLES D'ENVIRONNEMENT

Les variables d'entrée transmettent des informations de l'environnement à socat, les variables de sortie sont définies par socat pour être utilisées dans les scripts et programmes exécutés.

Dans les variables de sortie commençant par "SOCAT", ce préfixe est en fait remplacé par le nom en majuscules de l'exécutable ou par la valeur de l'option -lp.

SOCAT socat(1) - Linux man page

ENVIRONMENT

SOCAT_DEFAULT_LISTEN_IP (input)
(Valeurs 4 ou 6) Définit la version IP à utiliser pour les adresses d'écoute, de réception et de réception depuis si aucune option pf (protocole-famille) n'est donnée. Est remplacée par les options socat -4 ou -6.
SOCAT_PREFERRED_RESOLVE_IP (input)
(Valeurs 0, 4 ou 6) Définit la version IP à utiliser lors de la résolution des noms d'hôte cibles lorsque la version n'est pas spécifiée par le type d'adresse, l'option pf (protocole-famille) ou le format d'adresse. Si la résolution de nom ne retourne pas une entrée correspondante, le premier résultat (avec une version IP différente) est pris. Avec la valeur 0, socat sélectionne toujours le premier enregistrement et sa version IP.
SOCAT_MAIN_WAIT (input)
Spécifie le temps (secondes) d'attente du processus principal au début de main\(). Utile pour le débogage.
SOCAT_TRANSFER_WAIT (input)
Spécifie le temps (secondes) d'attente du processus après l'ouverture des adresses avant d'entrer dans la boucle de transfert. Utile pour le débogage.
SOCAT_FORK_WAIT (input)
Spécifie le temps (secondes) d'attente des processus parent et enfant après un fork() réussi. Utile pour le débogage.
SOCAT_VERSION (output)
Socat définit cette variable avec sa chaîne de version, par exemple "1.7.0.0" pour les versions publiées ou, par exemple, "1.6.0.1+envvar" pour les versions temporaires ; peut être utilisée dans les scripts invoqués par socat.
SOCAT_PID (output)
Socat définit cette variable avec son identifiant de processus. En cas d'option d'adresse fork, SOCAT_PID reçoit l'identifiant du processus enfant. Le fork pour exec, system et SHELL ne modifie pas SOCAT_PID.
SOCAT_PPID (output)
Socat définit cette variable avec son identifiant de processus. En cas de fork, SOCAT_PPID conserve le PID du processus maître.
SOCAT_PEERADDR (output)
Avec des adresses de socket passives (toutes les adresses LISTEN et RECVFROM), cette variable est définie avec une chaîne décrivant l'adresse du socket du pair. Les informations de port ne sont pas incluses.
SOCAT_PEERPORT (output)
Avec des adresses de socket passives appropriées (TCP, UDP et SCTP - LISTEN et RECVFROM), cette variable est définie avec une chaîne contenant le numéro du port du pair.
SOCAT_SOCKADDR (output)
Avec toutes les adresses LISTEN, cette variable est définie avec une chaîne décrivant l'adresse locale du socket. Les informations de port ne sont pas incluses, exemple.
SOCAT_SOCKPORT (output)
Avec les adresses TCP-LISTEN, UDP-LISTEN et SCTP-LISTEN, cette variable est définie avec le port local.
SOCAT_TIMESTAMP (output)
Avec toutes les adresses RECVFROM où l'option d'adresse so-timestamp est appliquée, socat définit cette variable avec le timestamp résultant.
SOCAT_IP_OPTIONS (output)
Avec toutes les adresses RECVFROM basées sur IPv4 où l'option d'adresse ip-recvopts est appliquée, socat remplit cette variable avec les options IP du paquet reçu.
SOCAT_IP_DSTADDR (output)
Avec toutes les adresses RECVFROM basées sur IPv4 où l'option d'adresse ip-recvdstaddr (BSD) ou ip-pktinfo (autres plateformes) est appliquée, socat définit cette variable avec l'adresse de destination du paquet reçu. Ceci est particulièrement utile pour identifier les paquets de diffusion et de multidiffusion.
SOCAT_IP_IF (output)
Avec toutes les adresses RECVFROM basées sur IPv4 où l'option d'adresse ip-recvif (BSD) ou ip-pktinfo (autres plateformes) est appliquée, socat définit cette variable avec le nom de l'interface sur laquelle le paquet a été reçu.
SOCAT_IP_LOCADDR (output)
Avec toutes les adresses RECVFROM basées sur IPv4 où l'option d'adresse ip-pktinfo est appliquée, socat définit cette variable avec l'adresse de l'interface sur laquelle le paquet a été reçu.
SOCAT_IP_TOS (output)
Avec toutes les adresses RECVFROM basées sur IPv4 où l'option d'adresse ip-recvtos est appliquée, socat définit cette variable avec le TOS (type de service) du paquet reçu.
SOCAT_IP_TTL (output)
Avec toutes les adresses RECVFROM basées sur IPv4 où l'option d'adresse ip-recvttl est appliquée, socat définit cette variable avec le TTL (durée de vie) du paquet reçu.
SOCAT_IPV6_HOPLIMIT (output)
Avec toutes les adresses RECVFROM basées sur IPv6 où l'option ipv6-recvhoplimit est appliquée, socat définit cette variable avec la valeur hoplimit du paquet reçu.
SOCAT_IPV6_DSTADDR (output)
Avec toutes les adresses RECVFROM basées sur IPv6 où l'option ipv6-recvpktinfo est appliquée, socat définit cette variable avec l'adresse de destination du paquet reçu.
SOCAT_IPV6_TCLASS (output)
Avec toutes les adresses RECVFROM basées sur IPv6 où l'option ipv6-recvtclass est appliquée, socat définit cette variable avec la classe de transfert du paquet reçu.
SOCAT_OPENSSL_X509_ISSUER (output)
Champ émetteur du certificat du pair
SOCAT_OPENSSL_X509_SUBJECT (output)
Champ sujet du certificat du pair
SOCAT_OPENSSL_X509_COMMONNAME (output)
Entrées commonName des sujets des certificats des pairs. Plusieurs valeurs sont séparées par " // ".
SOCAT_OPENSSL_X509_* (output)
Toutes les autres entrées des sujets des certificats des pairs
SOCAT_OPENSSL_X509V3_DNS (output)
Entrées DNS du champ subjectAltName des extensions des certificats des pairs. Plusieurs valeurs sont séparées par " // ".
HOSTNAME (input)
Est utilisé pour déterminer le nom d'hôte pour la journalisation (voir -lh).
LOGNAME (input)
Est utilisé comme nom d'utilisateur pour le client socks si aucun socksuser n'est donné.
Avec les options su et su-d, LOGNAME est défini avec le nom d'utilisateur donné.
USER (input)
Est utilisé comme nom d'utilisateur pour le client socks si aucun socksuser n'est donné et que LOGNAME est vide.
Avec les options su et su-d, USER est défini avec le nom d'utilisateur donné.
SHELL (output)
Avec les options su et su-d, SHELL est défini avec le shell de connexion de l'utilisateur donné.
PATH (output)
Peut être défini avec l'option path pour les adresses exec, system et SHELL.
HOME (output)
Avec les options su et su-d, HOME est défini avec le répertoire personnel de l'utilisateur donné.

BOGUES

Les adresses ne peuvent pas être imbriquées, donc un seul processus socat ne peut pas, par exemple, faire passer du ssl sur socks.

L'option d'adresse ftruncate sans valeur utilise la valeur par défaut 1 au lieu de 0.

Les modes verbeux (-x et/ou -v) affichent les caractères de fin de ligne de manière incohérente lorsque les options d'adresse cr ou crnl sont utilisées : ils montrent les données *après* la conversion dans les deux sens.

Le réglage de la taille des blocs de transfert de données (-b) est ignoré avec l'option d'adresse readline.

Signalez les bogues à <socat@dest-unreach.org>
