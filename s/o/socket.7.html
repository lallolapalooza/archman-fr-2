NOM

socket - Interface des sockets Linux

SYNTAXE

#include <sys/socket.h>
descripteur_socket = socket(int famille_socket, int type_socket, int protocole);

DESCRIPTION

Cette page de manuel décrit l'interface utilisateur de la couche de sockets réseau de Linux. Les sockets compatibles BSD sont l'interface uniforme entre le processus utilisateur et les piles de protocoles réseau dans le noyau. Les modules de protocole sont regroupés en familles de protocoles comme AF_INET, AF_IPX et AF_PACKET, et en types de sockets comme SOCK_STREAM ou SOCK_DGRAM. Voir socket(2) pour plus d'informations sur les familles et les types.

Fonctions de la couche socket

Ces fonctions sont utilisées par le processus utilisateur pour envoyer ou recevoir des paquets et pour effectuer d'autres opérations sur les sockets. Pour plus d'informations, consultez leurs pages de manuel respectives.

socket(2) crée un socket, connect(2) connecte un socket à une adresse de socket distante, la fonction bind(2) lie un socket à une adresse de socket locale, listen(2) indique au socket que de nouvelles connexions doivent être acceptées, et accept(2) est utilisé pour obtenir un nouveau socket avec une nouvelle connexion entrante. socketpair(2) renvoie deux sockets anonymes connectés (implémenté uniquement pour quelques familles locales comme AF_UNIX)

send(2), sendto(2) et sendmsg(2) envoient des données via un socket, et recv(2), recvfrom(2), recvmsg(2) reçoivent des données d'un socket. poll(2) et select(2) attendent l'arrivée de données ou la disponibilité pour envoyer des données. De plus, les opérations d'E/S standard comme write(2), writev(2), sendfile(2), read(2) et readv(2) peuvent être utilisées pour lire et écrire des données.

getsockname(2) renvoie l'adresse locale du socket et getpeername(2) renvoie l'adresse distante du socket. getsockopt(2) et setsockopt(2) sont utilisés pour définir ou obtenir des options de la couche socket ou du protocole. ioctl(2) peut être utilisé pour définir ou lire certaines autres options.

close(2) est utilisé pour fermer un socket. shutdown(2) ferme des parties d'une connexion de socket bidirectionnelle.

La recherche (seek), ou l'appel à pread(2) ou pwrite(2) avec une position non nulle n'est pas pris en charge sur les sockets.

Il est possible d'effectuer des E/S non bloquantes sur les sockets en définissant le drapeau O_NONBLOCK sur un descripteur de fichier de socket à l'aide de fcntl(2). Ensuite, toutes les opérations qui bloqueraient retourneront (généralement) EAGAIN (l'opération doit être réessayée plus tard) ; connect(2) retournera l'erreur EINPROGRESS. L'utilisateur peut alors attendre divers événements via poll(2) ou select(2).

Événements d'E/S
Événement Drapeau Poll Occurrence
Lecture POLLIN Nouvelles données arrivées.
Lecture POLLIN La configuration d'une connexion est terminée (pour les sockets orientés connexion)
Lecture POLLHUP Une demande de déconnexion a été initiée par l'autre extrémité.
Lecture POLLHUP Une connexion est rompue (uniquement pour les protocoles orientés connexion). Lorsque le socket est écrit, SIGPIPE est également envoyé.
Écriture POLLOUT Le socket dispose de suffisamment d'espace tampon d'envoi pour écrire de nouvelles données.

Une alternative à poll(2) et select(2) consiste à laisser le noyau informer l'application des événements via un signal SIGIO. Pour cela, le drapeau O_ASYNC doit être défini sur un descripteur de fichier de socket via fcntl(2) et un gestionnaire de signal valide pour SIGIO doit être installé via sigaction(2). Voir la discussion sur les Signaux ci-dessous.

Structures d'adresses de socket

Chaque domaine de socket a son propre format pour les adresses de socket, avec une structure d'adresse spécifique au domaine. Chacune de ces structures commence par un champ entier "famille" (typé comme sa_family_t) qui indique le type de la structure d'adresse. Cela permet aux différentes appels système (par exemple, connect(2), bind(2), accept(2), getsockname(2), getpeername(2)), qui sont génériques à tous les domaines de sockets, de déterminer le domaine d'une adresse de socket particulière.

Pour permettre à tout type d'adresse de socket d'être passé aux interfaces de l'API des sockets, le type struct sockaddr est défini. Le but de ce type est purement de permettre la conversion des types d'adresses de socket spécifiques au domaine en un type "générique", afin d'éviter les avertissements du compilateur concernant les incompatibilités de type dans les appels à l'API des sockets.

De plus, l'API des sockets fournit le type de données struct sockaddr_storage. Ce type est adapté pour contenir toutes les structures d'adresses de socket spécifiques au domaine supportées ; il est suffisamment grand et est correctement aligné. (En particulier, il est suffisamment grand pour contenir les adresses de socket IPv6.) La structure inclut le champ suivant, qui peut être utilisé pour identifier le type d'adresse de socket réellement stocké dans la structure :


    sa_family_t ss_family;

La structure sockaddr_storage est utile dans les programmes qui doivent gérer les adresses de socket de manière générique (par exemple, les programmes qui doivent traiter les adresses de socket IPv4 et IPv6).

Si le programme filtre renvoie une valeur non nulle inférieure à la taille des données du paquet, le paquet sera tronqué à la taille renvoyée. NOM

socket - Interfaces des prises (sockets) de bas niveau

SYN。

#include <sys/types.h>
#include <sys/socket.h>

DESCRIPTION

Les prises (sockets) sont des points de communication de bout en bout dans un réseau. L'API des prises fournit un mécanisme pour la communication entre processus, soit sur le même système d'exploitation, soit entre des systèmes d'exploitation sur un réseau. Cette page de manuel décrit les options de prise courantes pouvant être définies ou récupérées à l'aide de getsockopt(2) et setsockopt(2).

Les options sont spécifiées par un niveau et un nom d'option. Les niveaux couramment utilisés sont :

  • SOL_SOCKET : Options relatives aux prises génériques.
  • IPPROTO_IP : Options spécifiques à IPv4.
  • IPPROTO_TCP : Options spécifiques à TCP.
  • IPPROTO_UDP : Options spécifiques à UDP.

Chaque option est décrite ci-dessous avec le niveau auquel elle appartient et si elle peut être définie ou récupérée.

SO_ATTACH_FILTER
Attacher un programme BPF classique au socket. L'argument est un tableau de structures sock_filter. Le programme est exécuté pour chaque paquet reçu. Si le programme renvoie une valeur différente de zéro, le paquet est autorisé à passer. Si le programme renvoie 0, le paquet est ignoré. La taille du paquet de données est placée dans le registre 1. Si le paquet ne correspond pas à la taille maximale autorisée pour le type de socket, le paquet est ignoré. Sinon, le paquet est autorisé à passer sans modification.
L'argument pour SO_ATTACH_FILTER est une structure sock_fprog, définie dans <linux/filter.h> :

struct sock_fprog {
    unsigned short      len;
    struct sock_filter *filter;
};

L'argument pour SO_ATTACH_BPF est un descripteur de fichier renvoyé par l'appel système bpf(2) et doit faire référence à un programme de type BPF_PROG_TYPE_SOCKET_FILTER.
Ces options peuvent être définies plusieurs fois pour une prise donnée, remplaçant à chaque fois le programme de filtrage précédent. Les versions classique et étendue peuvent être appelées sur la même prise, mais le filtre précédent sera toujours remplacé de sorte qu'une prise n'ait jamais plus d'un filtre défini.
Le BPF classique et le BPF étendu sont expliqués dans le fichier source du noyau Documentation/networking/filter.txt
SO_ATTACH_REUSEPORT_CBPF
SO_ATTACH_REUSEPORT_EBPF
Pour une utilisation avec l'option SO_REUSEPORT, ces options permettent à l'utilisateur de définir un programme BPF classique (SO_ATTACH_REUSEPORT_CBPF) ou un programme BPF étendu (SO_ATTACH_REUSEPORT_EBPF) qui définit comment les paquets sont assignés aux prises du groupe reuseport (c'est-à-dire toutes les prises pour lesquelles SO_REUSEPORT est défini et qui utilisent la même adresse locale pour recevoir des paquets).
Le programme BPF doit renvoyer un index compris entre 0 et N-1 représentant la prise qui doit recevoir le paquet (où N est le nombre de prises dans le groupe). Si le programme BPF renvoie un index invalide, la sélection de la prise reviendra au mécanisme simple SO_REUSEPORT.
Les prises sont numérotées dans l'ordre où elles sont ajoutées au groupe (c'est-à-dire l'ordre des appels bind(2) pour les prises UDP ou l'ordre des appels listen(2) pour les prises TCP). Les nouvelles prises ajoutées à un groupe reuseport hériteront du programme BPF. Lorsqu'une prise est retirée d'un groupe reuseport (via close(2)), la dernière prise du groupe sera déplacée à la position de la prise fermée.
Ces options peuvent être définies de manière répétée à tout moment sur n'importe quelle prise du groupe pour remplacer le programme BPF actuel utilisé par toutes les prises du groupe.
SO_ATTACH_REUSEPORT_CBPF prend le même type d'argument que SO_ATTACH_FILTER et SO_ATTACH_REUSEPORT_EBPF prend le même type d'argument que SO_ATTACH_BPF.
Le support UDP pour cette fonctionnalité est disponible depuis Linux 4.5 ; le support TCP est disponible depuis Linux 4.6.
SO_BINDTODEVICE
Lier cette prise à un périphérique particulier comme "eth0", comme spécifié par le nom d'interface passé. Si le nom est une chaîne vide ou si la taille de l'option est zéro, la liaison de la prise au périphérique est supprimée. L'option passée est une chaîne de nom d'interface terminée par un caractère nul de taille variable avec une taille maximale de IFNAMSIZ. Si une prise est liée à une interface, seuls les paquets reçus de cette interface particulière sont traités par la prise. Notez que cela ne fonctionne qu'avec certains types de prises, notamment les prises AF_INET. Ce n'est pas supporté pour les prises paquet (utilisez le bind(2) normal dans ce cas).
Avant Linux 3.8, cette option de prise pouvait être définie, mais ne pouvait pas être récupérée avec getsockopt(2). Depuis Linux 3.8, elle est lisible. L'argument optlen doit contenir la taille du tampon disponible pour recevoir le nom du périphérique et il est recommandé qu'il soit de IFNAMSIZ octets. La longueur réelle du nom du périphérique est rapportée dans l'argument optlen.
SO_BROADCAST
Activer ou récupérer le drapeau de diffusion. Lorsque activé, les prises de datagramme sont autorisées à envoyer des paquets à une adresse de diffusion. Cette option n'a aucun effet sur les prises orientées flux.
SO_BSDCOMPAT
Activer la compatibilité BSD bug-à-bug. Ceci est utilisé par le module protocole UDP sous Linux 2.0 et 2.2. Si activé, les erreurs ICMP reçues pour une prise UDP ne seront pas transmises au programme utilisateur. Dans les versions ultérieures du noyau, le support de cette option a été progressivement supprimé : Linux 2.4 l'ignore silencieusement, et Linux 2.6 génère un avertissement du noyau (printk()) si un programme utilise cette option. Linux 2.0 activait également les options de compatibilité bug-à-bug BSD (modification aléatoire des en-têtes, saut du drapeau de diffusion) pour les prises brutes avec cette option, mais cela a été supprimé dans Linux 2.2.
SO_DEBUG
Activer le débogage des prises. Autorisé uniquement pour les processus ayant la capacité CAP_NET_ADMIN ou un ID utilisateur effectif de 0.
SO_DETACH_FILTER (depuis Linux 2.2)
SO_DETACH_BPF (depuis Linux 3.19)
Ces deux options, qui sont synonymes, peuvent être utilisées pour supprimer le programme BPF classique ou étendu attaché à une prise avec soit SO_ATTACH_FILTER, soit SO_ATTACH_BPF. La valeur de l'option est ignorée.
SO_DOMAIN (depuis Linux 2.6.32)
Récupère le domaine de la prise sous forme d'entier, renvoyant une valeur telle que AF_INET6. Voir socket(2) pour plus de détails. Cette option de prise est en lecture seule.
SO_ERROR
Récupérer et effacer l'erreur de prise en attente. Cette option de prise est en lecture seule. Attend un entier.
SO_DONTROUTE
Ne pas envoyer via une passerelle, envoyer uniquement à des hôtes directement connectés. Le même effet peut être obtenu en définissant le drapeau MSG_DONTROUTE lors d'une opération send(2) sur une prise. Attend un drapeau booléen entier.
SO_INCOMING_CPU (récupérable depuis Linux 3.19, définissable depuis Linux 4.4)
Définit ou récupère l'affinité CPU d'une prise. Attend un drapeau entier.

int cpu = 1;
setsockopt(fd, SOL_SOCKET, SO_INCOMING_CPU, &cpu,
           sizeof(cpu));

Étant donné que tous les paquets pour un même flux (c'est-à-dire tous les paquets pour le même 4-tuple) arrivent sur la même file d'attente RX associée à un CPU particulier, le cas d'utilisation typique est d'employer un processus d'écoute par file d'attente RX, le flux entrant étant géré par un écouteur sur le même CPU qui gère la file d'attente RX. Cela fournit un comportement NUMA optimal et maintient les caches CPU chauds.
SO_INCOMING_NAPI_ID (récupérable depuis Linux 4.12)
Renvoie un ID unique au niveau du système appelé ID NAPI qui est associé à une file d'attente RX sur laquelle le dernier paquet associé à cette prise a été reçu.
Cela peut être utilisé par une application pour répartir les flux entrants entre les threads de travail en fonction de la file d'attente RX sur laquelle les paquets associés aux flux sont reçus. Il permet à chaque thread de travail d'être associé à une file d'attente de réception matérielle NIC et de traiter toutes les demandes de connexion reçues sur cette file d'attente RX. Ce mappage entre un thread d'application et une file d'attente matérielle NIC rationalise le flux de données de la NIC à l'application.
SO_KEEPALIVE
Activer l'envoi de messages keep-alive sur les prises orientées connexion. Attend un drapeau booléen entier.
SO_LINGER
Définit ou récupère l'option SO_LINGER. L'argument est une structure linger.

struct linger {
    int l_onoff;    /* linger actif */
    int l_linger;   /* combien de secondes attendre */
};

Lorsque activé, un appel à close(2) ou shutdown(2) ne retournera pas tant que tous les messages mis en file d'attente pour la prise n'auront pas été envoyés avec succès ou que le délai de temporisation (linger) n'aura pas été atteint. Sinon, l'appel retourne immédiatement et la fermeture se fait en arrière-plan. Lorsque la prise est fermée dans le cadre de exit(2), elle effectue toujours la temporisation en arrière-plan.
SO_LOCK_FILTER
Lorsqu'elle est définie, cette option empêchera la modification des filtres associés à la prise. Ces filtres incluent tous ceux définis à l'aide des options de prise SO_ATTACH_FILTER, SO_ATTACH_BPF, SO_ATTACH_REUSEPORT_CBPF et SO_ATTACH_REUSEPORT_EBPF.
Le cas d'utilisation typique est pour un processus privilégié de configurer une prise brute (une opération qui nécessite la capacité CAP_NET_RAW), d'appliquer un filtre restrictif, de définir l'option SO_LOCK_FILTER, puis de supprimer ses privilèges ou de passer le descripteur de fichier de la prise à un processus non privilégié via une prise de domaine UNIX.
Une fois l'option SO_LOCK_FILTER activée, toute tentative de modification ou de suppression du filtre attaché à une prise, ou de désactivation de l'option SO_LOCK_FILTER échouera avec l'erreur EPERM.
SO_MARK (depuis Linux 2.6.25)
Définit la marque pour chaque paquet envoyé via cette prise (similaire à la cible MARK de netfilter mais basée sur la prise). La modification de la marque peut être utilisée pour le routage basé sur la marque sans netfilter ou pour le filtrage de paquets. La définition de cette option nécessite la capacité CAP_NET_ADMIN ou CAP_NET_RAW (depuis Linux 5.17).
SO_OOBINLINE
Si cette option est activée, les données hors bande sont directement placées dans le flux de données de réception. Sinon, les données hors bande ne sont transmises que lorsque le drapeau MSG_OOB est défini lors de la réception.
SO_PASSCRED
Activer ou désactiver la réception du message de contrôle SCM_CREDENTIALS. Pour plus d'informations, voir unix(7).
SO_PASSSEC
SCM_SECURITY
Activez ou désactivez la réception du message de contrôle SCM_SECURITY. Pour plus d'informations, voir unix(7).
SO_PEEK_OFF (depuis Linux 3.4)
Cette option, actuellement prise en charge uniquement pour les sockets unix(7), définit la valeur du « décalage de consultation » pour l'appel système recv(2) lorsqu'il est utilisé avec le drapeau MSG_PEEK.
Lorsque cette option est définie sur une valeur négative (elle est définie sur -1 pour tous les nouveaux sockets), le comportement traditionnel est fourni : recv(2) avec le drapeau MSG_PEEK consultera les données depuis le début de la file d'attente.
Lorsque l'option est définie sur une valeur supérieure ou égale à zéro, la prochaine consultation des données mises en file d'attente dans le socket se fera au décalage d'octet spécifié par la valeur de l'option. Dans le même temps, le « décalage de consultation » sera incrémenté du nombre d'octets qui ont été consultés dans la file d'attente, de sorte qu'une consultation ultérieure renverra les données suivantes dans la file d'attente.
Si des données sont retirées du début de la file d'attente via un appel à recv(2) (ou similaire) sans le drapeau MSG_PEEK, le « décalage de consultation » sera diminué du nombre d'octets retirés. Autrement dit, la réception de données sans le drapeau MSG_PEEK entraînera l'ajustement du « décalage de consultation » pour maintenir la position relative correcte dans les données mises en file d'attente, de sorte qu'une consultation ultérieure récupérera les données qui auraient été récupérées si les données n'avaient pas été retirées.
Pour les sockets de datagrammes, si le « décalage de consultation » pointe vers le milieu d'un paquet, les données renvoyées seront marquées avec le drapeau MSG_TRUNC.
L'exemple suivant sert à illustrer l'utilisation de SO_PEEK_OFF. Supposons qu'un socket de flux ait les données d'entrée suivantes mises en file d'attente :

aabbccddeeff

La séquence suivante d'appels recv(2) aura l'effet indiqué dans les commentaires :

int ov = 4;                  // Définit le décalage de consultation à 4
setsockopt(fd, SOL_SOCKET, SO_PEEK_OFF, &ov, sizeof(ov));
recv(fd, buf, 2, MSG_PEEK);  // Consulte "cc" ; décalage défini à 6
recv(fd, buf, 2, MSG_PEEK);  // Consulte "dd" ; décalage défini à 8
recv(fd, buf, 2, 0);         // Lit "aa" ; décalage défini à 6
recv(fd, buf, 2, MSG_PEEK);  // Consulte "ee" ; décalage défini à 8

SO_PEERCRED
Retourne les identifiants du processus pair connecté à ce socket. Pour plus de détails, voir unix(7).
SO_PEERSEC (depuis Linux 2.6.2)
Retourne le contexte de sécurité du socket pair connecté à ce socket. Pour plus de détails, voir unix(7) et ip(7).
SO_PRIORITY
Définit la priorité définie par le protocole pour tous les paquets à envoyer sur ce socket. Linux utilise cette valeur pour ordonnancer les files d'attente réseau : les paquets ayant une priorité plus élevée peuvent être traités en premier en fonction de la discipline de mise en file d'attente du périphérique sélectionnée. La définition d'une priorité en dehors de la plage 0 à 6 nécessite la capacité CAP_NET_ADMIN.
SO_PROTOCOL (depuis Linux 2.6.32)
Récupère le protocole du socket sous forme d'entier, renvoyant une valeur telle que IPPROTO_SCTP. Voir socket(2) pour plus de détails. Cette option de socket est en lecture seule.
SO_RCVBUF
Définit ou récupère la taille maximale du tampon de réception du socket en octets. Le noyau double cette valeur (pour permettre l'espace pour les frais généraux de comptabilité) lorsqu'elle est définie à l'aide de setsockopt(2), et cette valeur doublée est renvoyée par getsockopt(2). La valeur par défaut est définie par le fichier /proc/sys/net/core/rmem_default, et la valeur maximale autorisée est définie par le fichier /proc/sys/net/core/rmem_max. La valeur minimale (doublée) pour cette option est de 256.
SO_RCVBUFFORCE (depuis Linux 2.6.14)
En utilisant cette option de socket, un processus privilégié (CAP_NET_ADMIN) peut effectuer la même tâche que SO_RCVBUF, mais la limite rmem_max peut être outrepassée.
SO_RCVLOWAT
SO_SNDLOWAT
Spécifie le nombre minimum d'octets dans le tampon jusqu'à ce que la couche de socket transmette les données au protocole (SO_SNDLOWAT) ou à l'utilisateur lors de la réception (SO_RCVLOWAT). Ces deux valeurs sont initialisées à 1. SO_SNDLOWAT n'est pas modifiable sous Linux (setsockopt(2) échoue avec l'erreur ENOPROTOOPT). SO_RCVLOWAT n'est modifiable que depuis Linux 2.4.
Avant Linux 2.6.28, select(2), poll(2) et epoll(7) ne respectaient pas le réglage SO_RCVLOWAT sous Linux, et indiquaient un socket comme lisible même lorsqu'un seul octet de données était disponible. Une lecture ultérieure depuis le socket bloquait alors jusqu'à ce que SO_RCVLOWAT octets soient disponibles. Depuis Linux 2.6.28, select(2), poll(2) et epoll(7) indiquent un socket comme lisible uniquement si au moins SO_RCVLOWAT octets sont disponibles.
SO_RCVTIMEO
SO_SNDTIMEO
Spécifie les délais d'attente de réception ou d'envoi avant de signaler une erreur. L'argument est une struct timeval. Si une fonction d'entrée ou de sortie se bloque pendant cette période, et que des données ont été envoyées ou reçues, la valeur de retour de cette fonction sera la quantité de données transférées ; si aucune donnée n'a été transférée et que le délai d'attente est atteint, alors -1 est renvoyé avec errno défini sur EAGAIN ou EWOULDBLOCK, ou EINPROGRESS (pour connect(2)) comme si le socket était spécifié comme non bloquant. Si le délai d'attente est défini sur zéro (par défaut), l'opération ne dépassera jamais le délai. Les délais d'attente n'ont d'effet que pour les appels système qui effectuent des E/S de socket (par exemple, accept(2), connect(2), read(2), recvmsg(2), send(2), sendmsg(2)) ; les délais d'attente n'ont aucun effet pour select(2), poll(2), epoll_wait(2), etc.
SO_REUSEADDR
Indique que les règles utilisées pour valider les adresses fournies dans un appel à bind(2) doivent autoriser la réutilisation des adresses locales. Pour les sockets AF_INET, cela signifie qu'un socket peut être lié, sauf s'il existe un socket d'écoute actif lié à l'adresse. Lorsque le socket d'écoute est lié à INADDR_ANY avec un port spécifique, il n'est pas possible de lier ce port pour une adresse locale quelconque. L'argument est un indicateur booléen entier.
SO_REUSEPORT (depuis Linux 3.9)
Permet à plusieurs sockets AF_INET ou AF_INET6 d'être liés à une adresse de socket identique. Cette option doit être définie sur chaque socket (y compris le premier socket) avant d'appeler bind(2) sur le socket. Pour empêcher le détournement de port, tous les processus liant la même adresse doivent avoir le même UID effectif. Cette option peut être utilisée avec les sockets TCP et UDP.
Pour les sockets TCP, cette option permet d'améliorer la répartition de charge d'accept(2) dans un serveur multithread en utilisant un socket d'écoute distinct pour chaque thread. Cela offre une meilleure répartition de charge par rapport aux techniques traditionnelles telles que l'utilisation d'un seul thread d'accept(2) qui distribue les connexions, ou l'existence de plusieurs threads qui se font concurrence pour accepter depuis le même socket.
Pour les sockets UDP, l'utilisation de cette option peut fournir une meilleure distribution des datagrammes entrants à plusieurs processus (ou threads) par rapport à la technique traditionnelle consistant à faire concourir plusieurs processus pour recevoir des datagrammes sur le même socket.
SO_RXQ_OVFL (depuis Linux 2.6.33)
Indique qu'un message auxiliaire (cmsg) de 32 bits non signé doit être attaché aux skbs reçus, indiquant le nombre de paquets abandonnés par le socket depuis sa création.
SO_SELECT_ERR_QUEUE (depuis Linux 3.10)
Lorsque cette option est définie sur un socket, une condition d'erreur sur un socket entraîne une notification non seulement via l'ensemble exceptfds de select(2). De même, poll(2) renvoie également un POLLPRI chaque fois qu'un événement POLLERR est renvoyé.
Contexte : cette option a été ajoutée lorsque le réveil sur une condition d'erreur ne se produisait que via les ensembles readfds et writefds de select(2). L'option a été ajoutée pour permettre la surveillance des conditions d'erreur via l'argument exceptfds sans avoir à recevoir simultanément des notifications (via readfds) pour les données normales qui peuvent être lues à partir du socket. Après les changements sous Linux 4.16, l'utilisation de ce drapeau pour obtenir les notifications souhaitées n'est plus nécessaire. Cette option est néanmoins conservée pour des raisons de compatibilité descendante.
SO_SNDBUF
Définit ou récupère la taille maximale du tampon d'envoi du socket en octets. Le noyau double cette valeur (pour permettre l'espace pour les frais généraux de comptabilité) lorsqu'elle est définie à l'aide de setsockopt(2), et cette valeur doublée est renvoyée par getsockopt(2). La valeur par défaut est définie par le fichier /proc/sys/net/core/wmem_default et la valeur maximale autorisée est définie par le fichier /proc/sys/net/core/wmem_max. La valeur minimale (doublée) pour cette option est de 2048.

NAME

socket - operations on sockets

SYNOPSIS

#include <sys/types.h>
#include <sys/socket.h>
#include <netinet/in.h>
#include <sys/un.h>
#include <net/if.h>
#include <linux/if_packet.h>
#include <linux/if_link.h>

/* For some ioctls */
#include <sys/ioctl.h>

int socket(int domain, int type, int protocol);
int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
int connect(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
int listen(int sockfd, int backlog);
int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
int accept4(int sockfd, struct sockaddr *addr, socklen_t *addrlen, int flags);
int getsockopt(int sockfd, int level, int optname, void *optval, socklen_t *optlen);
int setsockopt(int sockfd, int level, int optname, const void *optval, socklen_t optlen);
int getsockname(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
int getpeername(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
int socketpair(int domain, int type, int protocol, int socks[2]);

DESCRIPTION

A socket is an endpoint for communication. A socket is identified by a pair of components: a protocol address and a service access point.

Sockets are created using the socket(2) system call.

socket()
creates an endpoint for communication and returns a file descriptor that refers to that endpoint. The domain argument specifies a communication domain; this selects the protocol family which will be used for communication. The currently known domains are listed in socket(2). The most common domain is AF_INET (IPv4 protocols). Other domains include AF_UNIX (local communication), AF_INET6 (IPv6 protocols), AF_PACKET (low-level packet interface), and others.
The type argument specifies the semantics of communication used by the created socket. The most common types are:
SOCK_STREAM Provides sequenced, reliable, two-way, connection-based byte streams. Within a stream, data is not returned unless it was received, and all data is delivered in order. An out-of-band data mechanism may be supported.
SOCK_DGRAM Supports datagrams (connectionless messages). Typically, this means that a process sends or receives a data, as a self-contained message, which will be delivered unreliably. Support for out-of-band data may be provided.
SOCK_SEQPACKET Provides a sequenced, reliable, two-way connection-based data transmission path. Like SOCK_STREAM, but data is taken out in messages of the size in which it was sent. (The underlying protocol might still transport data as a byte stream.)
SOCK_RAW Provides raw network protocol access. This is typically used for debugging or for specialized network protocols. A raw socket allows a process to send and receive raw packets on a network interface. The user must supply the protocol header.
The protocol argument is related to the type. It usually specifies a particular protocol to be used with the chosen domain and socket type. In many cases, this argument can be specified as 0 to indicate the “natural” protocol for the given domain and socket type.
If the call to socket(2) succeeds, it returns the lowest numbered file descriptor not currently in use by the process. Otherwise, -1 is returned, and errno is set to indicate the error.

The following socket options are supported by Linux. They are set using setsockopt(2) and read using getsockopt(2).

SO_ACCEPTCONN
Indicates whether some process has called listen(2) on the socket. This socket option is read-only.
SO_BROADCAST
Enable or disable the ability to transmit broadcast messages. This option is required to send packets to broadcast addresses.
SO_DEBUG
Enable or disable debugging information. This option is usually available only to the superuser.
SO_DONTROUTE
Do not use routing. This option can be used only by the superuser.
SO_ERROR
Get the pending error on the socket. This socket option is read-only.
SO_KEEPALIVE
Periodically send a "keep-alive" message on socket connections. If the other end is not responding, the connection will be forcibly closed. This option can be enabled or disabled.
SO_LINGER

Determine whether a close(2) call should linger when there is un-sent data in the socket buffer. It takes a pointer to a struct linger.

struct linger {
        int l_onoff;    /* controls linger exit status */
        int l_linger;   /* sets linger options */
    };

If l_onoff is non-zero, then close(2) will return if it must linger. If l_linger is zero, the option is turned off.

If l_onoff is non-zero and l_linger is non-zero, then close(2) will block until all data is sent or the linger timeout expires. If the linger timeout expires before all data is sent, the socket is discarded.

If l_onoff is non-zero and l_linger is zero, then close(2) will return immediately, and the operating system will discard any unsent data.

SO_OOBINLINE
If this option is enabled, out-of-band data will be placed in the normal data stream and delivered to the user when SO_RECVBUF ordinary data is received. If this option is disabled, out-of-band data is passed directly to the user when the message indicating its arrival is read.
SO_PASSCRED
Enable or disable the passing of credentials (real UID, effective UID, real GID, effective GID, and process ID) when sending datagrams. This is only supported for Linux Domain sockets (AF_UNIX).
SO_PEERCRED
Gets the credentials (real UID, effective UID, real GID, effective GID, and process ID) of the sender of the last datagram received on the socket. This is only supported for Linux Domain sockets (AF_UNIX). It returns a pointer to a struct which contains the credentials. The structure is defined in unix(7).
SO_RCVBUF
Set or get the maximum socket receive buffer size in bytes. The actual size is determined by the rmem_default and rmem_max values in /proc/sys/net/core/.
SO_RCVBUFFORCE (since Linux 2.6.14)
Using this socket option, a privileged (CAP_NET_ADMIN) process can perform the same task as SO_RCVBUF, but the rmem_max limit can be overridden.
SO_RCVTIMEO
Set or get a timeout value for receiving a message on a socket. The timeout value is a struct timeval. If the timeout is reached before the operation completes, it returns -1 with errno set to EAGAIN or EWOULDBLOCK. A value of zero means infinite timeout (blocking). This option is supported for most socket types.
SO_REUSEADDR
Indicates that the rules used in validating addresses supplied to bind(2) should be modified to allow reuse of local addresses. See bind(2) for details.
SO_SNDBUF
Set or get the sending buffer size. The actual size is determined by the wmem_default and wmem_max values in /proc/sys/net/core/.
SO_SNDBUFFORCE (since Linux 2.6.14)
Using this socket option, a privileged (CAP_NET_ADMIN) process can perform the same task as SO_SNDBUF, but the wmem_max limit can be overridden.
SO_TIMESTAMP
Enable or disable the receiving of the SO_TIMESTAMP control message. The timestamp control message is sent with level SOL_SOCKET and a cmsg_type of SCM_TIMESTAMP. The cmsg_data field is a struct timeval indicating the reception time of the last packet passed to the user in this call. See cmsg(3) for details on control messages.
SO_TIMESTAMPNS (since Linux 2.6.22)
Enable or disable the receiving of the SO_TIMESTAMPNS control message. The timestamp control message is sent with level SOL_SOCKET and a cmsg_type of SCM_TIMESTAMPNS. The cmsg_data field is a struct timespec indicating the reception time of the last packet passed to the user in this call. The clock used for the timestamp is CLOCK_REALTIME. See cmsg(3) for details on control messages.
A socket cannot mix SO_TIMESTAMP and SO_TIMESTAMPNS: the two modes are mutually exclusive.
SO_TYPE
Gets the socket type as an integer (e.g., SOCK_STREAM). This socket option is read-only.
SO_BUSY_POLL (since Linux 3.11)
Sets the approximate time in microseconds to busy poll on a blocking receive when there is no data. Increasing this value requires CAP_NET_ADMIN. The default for this option is controlled by the /proc/sys/net/core/busy_read file.
The value in the /proc/sys/net/core/busy_poll file determines how long select(2) and poll(2) will busy poll when they operate on sockets with SO_BUSY_POLL set and no events to report are found.
In both cases, busy polling will only be done when the socket last received data from a network device that supports this option.
While busy polling may improve latency of some applications, care must be taken when using it since this will increase both CPU utilization and power usage.

Signals

When writing onto a connection-oriented socket that has been shut down (by the local or the remote end) SIGPIPE is sent to the writing process and EPIPE is returned. The signal is not sent when the write call specified the MSG_NOSIGNAL flag.

When requested with the FIOSETOWN fcntl(2) or SIOCSPGRP ioctl(2), SIGIO is sent when an I/O event occurs. It is possible to use poll(2) or select(2) in the signal handler to find out which socket the event occurred on. An alternative (in Linux 2.2) is to set a real-time signal using the F_SETSIG fcntl(2); the handler of the real time signal will be called with the file descriptor in the si_fd field of its siginfo_t. See fcntl(2) for more information.

Under some circumstances (e.g., multiple processes accessing a single socket), the condition that caused the SIGIO may have already disappeared when the process reacts to the signal. If this happens, the process should wait again because Linux will resend the signal later.

/proc interfaces

The core socket networking parameters can be accessed via files in the directory /proc/sys/net/core/.

rmem_default
contains the default setting in bytes of the socket receive buffer.
rmem_max
contains the maximum socket receive buffer size in bytes which a user may set by using the SO_RCVBUF socket option.
wmem_default
contains the default setting in bytes of the socket send buffer.
wmem_max
contains the maximum socket send buffer size in bytes which a user may set by using the SO_SNDBUF socket option.
message_cost
message_burst
configure the token bucket filter used to load limit warning messages caused by external network events.
netdev_max_backlog
Maximum number of packets in the global input queue.
optmem_max
Maximum size of ancillary data and user control data like the iovecs per socket.

Ioctls

These operations can be accessed using ioctl(2):


error = ioctl(ip_socket, ioctl_type, &value_result);
SIOCGSTAMP
Return a struct timeval with the receive timestamp of the last packet passed to the user. This is useful for accurate round trip time measurements. See setitimer(2) for a description of struct timeval. This ioctl should be used only if the socket options SO_TIMESTAMP and SO_TIMESTAMPNS are not set on the socket. Otherwise, it returns the timestamp of the last packet that was received while SO_TIMESTAMP and SO_TIMESTAMPNS were not set, or it fails if no such packet has been received, (i.e., ioctl(2) returns -1 with errno set to ENOENT).
SIOCSPGRP
Set the process or process group that is to receive SIGIO or SIGURG signals when I/O becomes possible or urgent data is available. The argument is a pointer to a pid_t. For further details, see the description of F_SETOWN in fcntl(2).
FIOASYNC
Change the O_ASYNC flag to enable or disable asynchronous I/O mode of the socket. Asynchronous I/O mode means that the SIGIO signal or the signal set with F_SETSIG is raised when a new I/O event occurs.
Argument is an integer boolean flag. (This operation is synonymous with the use of fcntl(2) to set the O_ASYNC flag.)
SIOCGPGRP
Get the current process or process group that receives SIGIO or SIGURG signals, or 0 when none is set.

Valid fcntl(2) operations:

FIOGETOWN
The same as the SIOCGPGRP ioctl(2).
FIOSETOWN
The same as the SIOCSPGRP ioctl(2).

VERSIONS

SO_BINDTODEVICE was introduced in Linux 2.0.30. SO_PASSCRED is new in Linux 2.2. The /proc interfaces were introduced in Linux 2.2. SO_RCVTIMEO and SO_SNDTIMEO are supported since Linux 2.3.41. Earlier, timeouts were fixed to a protocol-specific setting, and could not be read or written.

NOTES

Linux assumes that half of the send/receive buffer is used for internal kernel structures; thus the values in the corresponding /proc files are twice what can be observed on the wire.

Linux will allow port reuse only with the SO_REUSEADDR option when this option was set both in the previous program that performed a bind(2) to the port and in the program that wants to reuse the port. This differs from some implementations (e.g., FreeBSD) where only the later program needs to set the SO_REUSEADDR option. Typically this difference is invisible, since, for example, a server program is designed to always set this option.
