NOM

SoX - Sound eXchange_ng, un autre couteau suisse de manipulation audio

DESCRIPTION

Ce manuel décrit les formats de fichiers et les types de périphériques audio pris en charge par SoX ; l'ensemble des manuels SoX commence par sox_ng(1).

Les types de formats que SoX peut déterminer par une extension de nom de fichier sont listés avec leurs noms précédés d'un point. Les types de formats qui sont éventuellement intégrés à SoX sont marqués comme `(optionnel)'.

Les types de formats gérés par la bibliothèque externe sndfile sont marqués comme `(avec sndfile)' et les types de formats qui ne peuvent être lus qu'en utilisant le programme externe ffmpeg sont marqués comme `(avec ffmpeg)'.

Les formats pour lesquels SoX a des pilotes internes mais qui sont également pris en charge par sndfile ou ffmpeg sont marqués (également avec -t sndfile) ou (également avec -t ffmpeg). Cela pourrait être utile si vous avez un fichier qui ne fonctionne pas avec les lecteurs et écrivains intégrés de SoX.

Pour savoir si SoX prend en charge un format ou un périphérique optionnel, tapez sox_ng -h et recherchez son nom sous `FORMATS DE FICHIERS AUDIO' ou `PILOTES DE PÉRIPHÉRIQUES AUDIO'.

Pour tout savoir sur un format - s'il le lit ou l'écrit, ou les deux, et quels encodages il peut écrire - tapez quelque chose comme --help-format wav ou, pour voir les détails de tous les formats, --help-format all.

FORMATS & PILOTES DE PÉRIPHÉRIQUES

.raw (également avec -t sndfile), .f32, .f64, .s8, .s16, .s24, .s32, .u8, .u16, .u24, .u32, .ul, .al, .lu, .la
Fichiers audio bruts (sans en-tête). Pour raw, le taux d'échantillonnage et l'encodage des données doivent être donnés en utilisant les options de format de la ligne de commande ; pour les autres types listés, le taux d'échantillonnage par défaut est de 8 kHz et l'encodage des données est défini par le suffixe donné. Ainsi, f32 et f64 indiquent des fichiers encodés en PCM flottant 32 bits et 64 bits IEEE-754 simple et double précision respectivement ; s8, s16, s24 et s32 indiquent du PCM entier signé 8, 16, 24 et 32 bits respectivement ; u8, u16, u24 et u32 indiquent du PCM entier non signé 8, 16, 24 et 32 bits respectivement ; ul indique le `μ-law' (8 bits), al indique le `A-law' (8 bits) et lu et la sont respectivement des `μ-law' et `A-law' en ordre de bits inversé. Pour tous les formats bruts, le nombre de canaux par défaut est de 1.

Les fichiers audio sans en-tête sur un ordinateur SPARC sont probablement de format ul ; sur un Mac, ils sont probablement u8 mais avec un taux d'échantillonnage de 11025 ou 22050 Hz.

Voir .ima et .vox pour les formats ADPCM bruts et .cdda pour l'audio numérique CD brut.

.f4, .f8, .s1, .s2, .s3, .s4, .u1, .u2, .u3, .u4, .sb, .sw, .sl, .ub, .uw
Alias obsolètes pour respectivement .f32, .f64, .s8, .s16, .s24, .s32, .u8, .u16, .u24, .u32, .s8, .s16, .s32, .u8 et .u16.

Format Third Generation Partnership Project.
.3g2, .3gp2, .3gpp2 (avec ffmpeg)
Format Third Generation Partnership Project 2.
.8svx (également avec -t sndfile)
Format de description d'instrument de musique Amiga 8SVX.
.aac (avec ffmpeg)
Format Advanced Audio Coding.
.ac3 (avec ffmpeg)
Format Audio Codec 3 (Dolby Digital).
.adts (avec ffmpeg)
Format Audio Data Transport Stream.
.aiff, .aif (également avec -t sndfile ou -t ffmpeg)
Fichiers AIFF tels qu'utilisés sur les anciens Mac, Apple IIc/IIgs et SGI. La prise en charge AIFF de SoX n'inclut pas les multiples blocs audio ni le format de description d'instrument de musique 8SVX. Les fichiers AIFF sont des archives multimédias et peuvent contenir plusieurs blocs audio et d'images ; vous pourriez avoir besoin d'un archiveur séparé pour les manipuler. Sur MacOS X, AIFF a été remplacé par CAF.
.aiffc, .aifc (également avec -t sndfile)
AIFF-C est basé sur AIFF mais gère également l'audio compressé. Il peut également gérer des données linéaires non compressées en little-endian, souvent appelées encodage sowt. Cet encodage est devenu le format par défaut produit par les Mac modernes ainsi que par iTunes sur n'importe quelle plateforme. Les fichiers AIFF-C produits par d'autres applications ont généralement l'extension de fichier .aif et nécessitent de consulter leur en-tête pour détecter le vrai format. sowt, a-law et u-law sont les seuls encodages que SoX peut lire et écrire nativement ; pour d'autres types de compression comme GSM, essayez -t ffmpeg.

AIFF-C est défini dans DAVIC 1.4 Part 9 Annex B. Ce format est référencé par ARIB STD-B24, qui est spécifié pour la radiodiffusion de données japonaise. Les blocs privés ne sont pas pris en charge.

alsa (optionnel)
Le pilote de périphérique Advanced Linux Sound Architecture prend en charge la lecture et l'enregistrement audio. ALSA n'est utilisé que dans les systèmes d'exploitation basés sur Linux, bien que ceux-ci prennent souvent en charge OSS (voir ci-dessous) également. Exemples : 
	sox_ng infile -t alsa
	sox_ng infile -t alsa default
	sox_ng infile -t alsa plughw:0,0
	sox_ng -b 16 -t alsa hw:1 outfile
.amb
Le format B Ambisonic est une spécialisation de .wav avec entre 3 et 16 canaux audio pour une utilisation avec un décodeur Ambisonique. Voir http://www.ambisonia.com/Members/mleese/file-format-for-b-format pour les détails. C'est à vous de rassembler les canaux dans le bon ordre et à la bonne amplitude.
.amr-nb, .amr-wb (tous deux optionnels, également avec -t ffmpeg)
Adaptive Multi Rate Narrow et Wide Band sont des formats avec perte pour la parole utilisés dans la téléphonie mobile de troisième génération et définis dans 3GPP TS 26.071 et TS 26.171.

L'audio AMR-NB a un taux d'échantillonnage fixe de 8 kHz et AMR-WB de 16 kHz et ils prennent en charge l'encodage aux débits binaires suivants, sélectionnés par l'option -C :

amr-nb   amr-wb
-C kbit/s   -C kbit/s
0 4.75   0 6.6 
1 5.15   1 8.85
2 5.9    2 12.65
3 6.7    3 14.25
4 7.4    4 15.85
5 7.95   5 18.25
6 10.2    6 19.85
7 12.2    ao (optionnel)
Le pilote de périphérique de sortie audio de Xiph.org ne fonctionne que pour la lecture audio. Il prend en charge un large éventail d'appareils et de systèmes sonores ; consultez sa documentation pour la gamme complète. Dans la plupart des cas, l'utilisation de libao par SoX ne peut pas être configurée directement ; au lieu de cela, des fichiers de configuration libao doivent être utilisés.

Le nom de fichier est utilisé pour déterminer quel plugin libao utiliser et, normalement, vous devriez spécifier `default'. Si cela ne donne pas le comportement souhaité, vous pouvez spécifier le nom court d'un plugin donné (tel que pulse pour le plugin PulseAudio ou null pour les tests. Voir http://xiph.org/ao). Exemples :

	sox_ng infile -t ao
	sox_ng infile -t ao default
	sox_ng infile -t ao pulse

.au, .snd (également avec -t sndfile ou -t ffmpeg)
Fichiers Sun Microsystems AU. Il existe de nombreux types de fichiers AU ; DEC en a inventé un propre avec un nombre magique et un ordre d'octets différents. Pour écrire un fichier DEC, utilisez l'option de fichier de sortie -L (little-endian).

Certains fichiers .au sont connus pour avoir des en-têtes AU invalides ; il s'agit probablement de fichiers Sun μ-law 8000 Hz d'origine et peuvent être traités à l'aide du format .ul.

Il est possible de remplacer les informations d'en-tête du fichier AU avec les options -r (fréquence d'échantillonnage) et -c (nombre de canaux), auquel cas SoX émettra un avertissement concernant l'incompatibilité.

.cdda, .cdr
Audio numérique de CD `Red Book' (audio brut). CDDA a deux canaux audio formatés en entiers signés 16 bits big-endian à une fréquence d'échantillonnage de 44.1 kHz. Le nombre d'échantillons stéréo dans chaque piste CDDA est toujours un multiple de 588.
coreaudio (optionnel)
Le pilote de périphérique CoreAudio de MacOS X prend en charge la lecture et l'enregistrement. Si un nom de fichier n'est pas spécifique ou si le nom est "default", l'appareil audio par défaut est sélectionné. Tout autre nom sera utilisé pour sélectionner un appareil spécifique. Les noms valides peuvent être vus dans le menu Préférences Système->Son, puis sous les onglets Sortie et Entrée.

Exemples :

	sox_ng infile -t coreaudio
	sox_ng infile -t coreaudio default
	sox_ng infile -t coreaudio "Internal Speakers"
.cvsd, .cvs
La modulation Delta à pente variable continue est un format sans en-tête utilisé pour compresser l'audio de la parole pour des applications telles que la messagerie vocale avec un débit binaire fixe de 8 kHz. Ce format est parfois utilisé avec des échantillons inversés par bits ; l'option -X peut être utilisée pour définir l'ordre des bits.
.cvu
La modulation Delta à pente variable continue non filtrée est un gestionnaire alternatif pour CVSD qui est non filtré mais peut être utilisé avec n'importe quelle fréquence d'échantillonnage. Comme il s'agit d'un format sans en-tête, vous devez spécifier la fréquence d'échantillonnage avec -r si elle est différente de 8 kHz. 
	sox_ng infile outfile.cvu rate 28k
	play -r 28k outfile.cvu sinc -3.4k
.dat
Les fichiers Text Data contiennent une représentation textuelle des données d'échantillons. Il y a une ligne au début qui contient la fréquence d'échantillonnage et une qui contient le nombre de canaux. Les lignes suivantes contiennent deux éléments de données numériques ou plus : le temps écoulé depuis le début du premier échantillon et la valeur de l'échantillon pour chaque canal.

Les valeurs sont normalisées de sorte que le maximum et le minimum soient 1 et -1. Ce format de fichier peut être utilisé pour créer des fichiers de données pour des programmes externes tels que des analyseurs FFT ou des routines graphiques. SoX peut également reconvertir un fichier dans ce format vers l'un des autres formats.

Exemple contenant seulement 2 échantillons stéréo de silence :

    ; Sample Rate 8012
    ; Channels 2
                0	0	0
    0.00012481278	0	0

.dsf, .wsd
Le format DSD Stream File est un format défini par Sony pour stocker des données DSD 1 bit, couramment utilisé pour la distribution en ligne d'enregistrements audiophiles.
.dvms, .vms
Le format Digital Voice Messaging System est utilisé en Allemagne pour compresser l'audio de la parole pour la messagerie vocale. C'est une variante auto-descriptive de cvsd.

.f4v (avec ffmpeg)

.fap (avec sndfile)
Voir .paf.
ffmpeg (optionnel)
Il s'agit d'un pseudo-type qui utilise le programme externe ffmpeg s'il est installé. Il ne peut que lire des fichiers, pas les écrire, et extraira la piste sonore de nombreux formats de fichiers vidéo. ffmpeg déduit le type de fichier réel à partir du contenu du fichier avec un algorithme beaucoup plus avancé que celui utilisé par SoX, qui ne reconnaît que jusqu'à deux séquences d'octets fixes à des décalages fixes.
.flac (optionnel ; également avec -t sndfile ou -t ffmpeg)
Codec audio compressé sans perte Xiph.org (Free Lossless Audio Codec). FLAC est un codec ouvert et sans brevet conçu pour compresser la musique. Il est similaire à MP3 et Ogg Vorbis mais sans perte, de sorte que l'audio est compressé sans aucune perte de qualité.

SoX peut lire les fichiers FLAC natifs (.flac) mais ne peut lire que les fichiers Ogg FLAC (.oga) si ffmpeg est installé.

Voir .ogg ci-dessous pour des informations relatives à la prise en charge des fichiers Ogg Vorbis.

SoX peut écrire des fichiers FLAC natifs selon un niveau de compression donné ou par défaut. 8 est le niveau de compression par défaut et offre la meilleure compression (mais la plus lente) ; 0 donne la moindre compression (mais la plus rapide). Le niveau de compression est sélectionné à l'aide de l'option -C (voir sox_ng(1)) avec un nombre entier compris entre 0 et 8.

.flv (avec ffmpeg)
Format Macromedia Flash Video.
.fssd
Format Flexible Sound Studio Data, un format brut qui utilise par défaut .u8 à 8 kHz.
.gsrt
Fichiers de sonnerie Grandstream. Bien que ce format de fichier puisse contenir de l'audio encodé en A-Law, μ-law, GSM, G.722, G.723, G.726, G.728 ou iLBC, SoX prend en charge la lecture et l'écriture uniquement en A-Law et μ-law. Par exemple : 
   sox_ng music.wav -t gsrt ring.bin
   play ring.bin
.gsm (optionnel ; également avec -t sndfile ou -t ffmpeg))
Compression vocale avec perte GSM 06.10. Un format avec perte pour compresser la parole, utilisé dans la norme mondiale des télécommunications mobiles (GSM). Il est bon pour son objectif, réduisant la taille des données audio, mais il introduira beaucoup de bruit lorsqu'un signal audio est encodé et décodé plusieurs fois. Ce format est utilisé par certaines applications de messagerie vocale et est assez gourmand en CPU.

.ircam (également avec -t sndfile ou -t ffmpeg)

.mp1, .m1a, .mp2 (facultatif, aussi avec -t sndfile ou -t ffmpeg)
Audio compressé MP1, MP2 et MP3 (MPEG 1 Layers 1, 2 et 3) font partie des normes MPEG pour la compression audio et vidéo dont les brevets ont expiré. Ce sont des formats de compression avec perte qui obtiennent de bons taux de compression avec peu de perte de qualité.

libmad, utilisé par SoX pour décoder les fichiers MPEG, ne fonctionne pas sur les fichiers avec un débit binaire supérieur à 192K, mais vous pouvez les lire avec -t sndfile ou -t ffmpeg.

SoX utilise twolame pour écrire les fichiers MP2, et le débit binaire cible est défini à l'aide de l'option -C en kbps : 32, 48, 56, 64, 80, 96, 112, 128, 160 ou 192 pour un débit binaire constant (CBR) pour les fichiers mono et le double pour les fichiers stéréo. L'encodage à débit binaire variable (VBR) est sélectionné par des valeurs de −50 à 50 (dont seulement −10 à 10 seraient utiles) ; si vous voulez vraiment du VBR avec les qualités 32 ou 48, utilisez quelque chose comme 3.01 ou 48.01.

Malheureusement, twolame produit 0,005 secondes de silence inutile au début et tronque la fin de 0,002 secondes.

SoX ne peut que lire les fichiers MP1, pas les écrire.

.mp3 (facultatif, aussi avec -t sndfile ou -t ffmpeg)
SoX utilise libmad pour décoder les fichiers MP3 ; pour décoder à l'aide de libmpg123, qui donne généralement des résultats de meilleure qualité et est meilleur pour décoder des fichiers endommagés ou corrompus, utilisez -t sndfile, tandis que -t ffmpeg utilise un autre décodeur MPEG, `mpglib'.

SoX décode les fichiers MP2 et MP3 avec une précision de 28 bits, mais par défaut il déclare une précision de 16 bits afin que le décodage des MP3 en WAV donne la qualité CD que la plupart des gens attendent. Vous pouvez spécifier une précision plus élevée pour le fichier de sortie afin de conserver ces informations supplémentaires.

SoX utilise liblame lors de l'écriture des fichiers MP3 et peut utiliser jusqu'à 25 bits de précision.

À l'heure actuelle, l'utilisation de liblame par SoX ajoute 0,01 seconde de silence inutile au début et à la fin ; l'encodage avec -t sndfile donne la bonne longueur et aucun silence.

Les paramètres de compression MP3 peuvent être sélectionnés en utilisant l'option -C de SoX comme suit :

Le paramètre principal de l'encodeur LAME MP3 est le débit binaire. Si la valeur de la valeur -C est un entier positif, elle est considérée comme le débit binaire en kbps (par exemple, si vous spécifiez 128, il utilise 128 kbps).

Le deuxième paramètre le plus important est la "qualité", qui permet d'équilibrer la vitesse d'encodage par rapport à la qualité. Dans LAME, 0 spécifie la plus haute qualité mais est très lent, tandis que 9 sélectionne une qualité médiocre, mais est rapide. (5 est la valeur par défaut et 2 est recommandé comme un bon compromis pour les encodages de haute qualité.)

Étant donné que la valeur -C est un nombre flottant, la partie fractionnaire est utilisée pour sélectionner la qualité. 128.2 sélectionne l'encodage 128 kbps avec une qualité de 2. Il y a un problème avec cette approche. Nous avons besoin de 128 pour spécifier l'encodage 128 kbps avec la qualité par défaut, donc 0 signifie utiliser la valeur par défaut. Au lieu de 0, vous devez utiliser .01 (ou .99) pour spécifier la qualité la plus élevée ou la plus basse (128.01 ou 128.99).

LAME utilise le débit binaire pour spécifier un débit binaire constant, mais une qualité supérieure peut être obtenue en utilisant le Débit Binaire Variable (VBR). La qualité VBR (vraiment la taille) est sélectionnée à l'aide d'un nombre de 0 à 9. Utilisez une valeur de 0 pour une haute qualité, des fichiers plus volumineux et 9 pour des fichiers plus petits de qualité inférieure. 4 est la valeur par défaut.

Afin de faire rentrer la sélection du VBR dans la valeur -C, nous utilisons des nombres négatifs pour sélectionner le VBR. -4.2 sélectionnerait l'encodage VBR par défaut (taille) avec une haute qualité (vitesse). Un cas spécial est 0, qui est un paramètre d'encodage VBR valide mais pas un débit binaire valide. La valeur de compression 0 est toujours traitée comme un VBR de haute qualité, par conséquent -0.2 et 0.2 sont tous deux traités comme VBR de la plus haute qualité (taille) et de haute qualité (vitesse).

Voir Ogg Vorbis et opus pour des formats similaires qui obtiennent une meilleure qualité de signal avec moins de bande passante.

.nsp (aussi avec -t ffmpeg)
SoX peut lire les fichiers NSP du Computerized Speech Lab qui peuvent contenir à la fois des données audio et bioélectriques. Typiquement, le premier canal est la pression sonore (audio) et les canaux supplémentaires sont des données telles que la cinématique laryngée ou l'aérodynamique (pression d'air ou débit d'air).

Le format de fichier NSP a également été utilisé pour la Phonetic Database (PDB) de Speech Technology Research qui disposait d'un lecteur NSP gratuit, SpeakNSP. La lecture et l'écriture des fichiers CSL NSP sont prises en charge par le package WaveSurfer.

.nut (avec ffmpeg)
NUT est un format conteneur générique à faible surcharge qui stocke des flux audio, vidéo, sous-titres et définis par l'utilisateur de manière simple mais efficace.
.oga (avec ffmpeg)
Divers formats audio Xiph.org dans un conteneur Ogg.
.ogg, .vorbis (facultatif, aussi avec -t sndfile ou -t ffmpeg))
Audio compressé Ogg Vorbis de Xiph.org ; un codec ouvert et libre de brevets conçu pour la musique et l'audio en streaming. C'est un format de compression avec perte (similaire à MP3 et AAC) qui obtient de bons taux de compression avec une perte de qualité minimale.

SoX peut décoder tous les types de fichiers Ogg Vorbis et peut encoder à différents niveaux de compression/qualités donnés par un nombre de -1 (compression la plus élevée/qualité la plus basse) à 10 (compression la plus basse, qualité la plus élevée). Par défaut, le niveau de qualité d'encodage est de 3 (ce qui donne un débit encodé d'environ 112 kbps), mais cela peut être modifié à l'aide de l'option -C avec un nombre de -1 à 10 ; les nombres fractionnaires (par exemple, 3.6) sont également autorisés. Le décodage est quelque peu intensif en CPU et l'encodage est très intensif en CPU.

Voir .mp3 pour un format similaire.

.opus (facultatif)
L'audio compressé Opus de Xiph.org est un codec ouvert, avec perte, à faible latence offrant une large gamme de débits de compression et utilise le conteneur Ogg.

SoX ne peut que lire les fichiers Opus, pas les écrire.

oss (facultatif)
Le pilote de périphérique Open Sound System /dev/dsp prend en charge la lecture et l'enregistrement audio. Le support OSS est disponible dans les systèmes d'exploitation de type Unix, parfois conjointement avec des systèmes sonores alternatifs (comme ALSA). Exemples : 
	sox_ng infile -t oss
	sox_ng infile -t oss /dev/dsp
	sox_ng -b 16 -t oss /dev/dsp outfile
.paf, .fap (avec sndfile, aussi avec -t ffmpeg)
Format de fichier Ensoniq PARIS (big-endian et little-endian respectivement).
.pls
Un format de *playlist* contenant une liste de fichiers audio. SoX peut lire, mais pas écrire ce format de fichier. Voir [2] pour les détails de ce format.

Note : Le support de SoX pour les PLS SHOUTcast repose sur wget(1) et n'est que partiellement pris en charge : il est nécessaire de spécifier manuellement le type audio, par exemple :

	play -t mp3 "http://a.server/pls?rn=265&file=filename.pls"
et SoX ne connaît pas les serveurs alternatifs - appuyez sur Ctrl-C deux fois de suite pour quitter.
.prc
Psion Record est utilisé dans les PDA Psion EPOC (Series 5, Revo et similaires) pour les alarmes système et les enregistrements effectués par l'application Record intégrée. Lors de l'écriture, SoX utilise par défaut A-law, ce qui est recommandé ; si vous devez utiliser ADPCM, utilisez le commutateur -e ima-adpcm. La qualité sonore est médiocre car Psion Record semble insister sur des trames de 800 échantillons ou moins, de sorte que le CODEC ADPCM doit être réinitialisé toutes les 800 trames, ce qui provoque des artefacts sonores toutes les dixièmes de seconde.

Toutes les fréquences d'échantillonnage sont prises en charge par le package, bien que toutes ne soient pas prises en charge par les échantillonneurs eux-mêmes. Les points de boucle sont actuellement ignorés.
.snd
Plusieurs formats de fichiers utilisent le nom .snd
> extension.

Le principal était celui de NeXT, essentiellement le même que le format .au de Sun Microsystems. Voir .au

Apple a créé un autre format .snd dans lequel les deux premiers octets sont un entier de 16 bits représentant les nombres 1 ou 2, mais qui peut souvent être lu comme un format brut.

Akai avait un format de fichier audio pour sa gamme d'échantillonneurs MPC dont le premier octet contient le nombre 1 et le second le nombre 4. Voir .mpc2k

Il existe également des fichiers Sounder et SoundTool de MS-DOS/Windows du début des années 90. Voir .sndr et .sndt.

Enfin, le nettoyage robotique HOM-BOT et le système de divertissement à domicile V.Flash utilisent des fichiers audio .snd qui sont des PCM bruts mono-canal 16 bits 16 kHz et le moteur de jeu Unity utilise un format compressé appelé .snd.

sndfile (optionnel)
Il s'agit d'un pseudo-type qui force l'utilisation de libsndfile. Pour l'écriture de fichiers, le type de fichier réel est pris du nom du fichier de sortie ; pour la lecture, il est déduit du fichier.
sndio (optionnel)
Le pilote de périphérique audio OpenBSD prend en charge la lecture et l'enregistrement audio.
.sndr
Les fichiers Sounder sont un format MS-DOS/Windows du début des années 90 qui ont généralement l'extension `.snd'.
.sndt
Les fichiers SoundTool sont un autre format MS-DOS/Windows du début des années 90 qui ont généralement l'extension `.snd'.
.sou
Un alias pour le format brut .u8.
.sox (également avec -t ffmpeg)
Le format PCM non compressé natif de SoX est destiné au stockage ou au transfert audio aux points de traitement intermédiaires entre les invocations de SoX. Il a beaucoup en commun avec les formats PCM non compressés WAV, AIFF et AU, mais présente les caractéristiques spécifiques suivantes : les échantillons PCM sont stockés sous forme d'entiers signés de 32 bits, les échantillons sont stockés (par défaut) en `boutiste native' et le nombre d'échantillons dans le fichier est enregistré sous forme d'entier de 64 bits. Les commentaires sont également pris en charge.

Voir la section `Noms de fichiers spéciaux' dans sox_ng(1) pour des exemples d'utilisation du format .sox avec des pipes.

.spdif (avec ffmpeg)
Format IEC 61937 S/PDIF.

.sph, .nist (également avec -t sndfile ou -t ffmpeg)
SPHERE (SPeech HEader REsources) est un format de fichier défini par NIST (National Institute of Standards and Technology) et utilisé pour l'audio de la parole. SoX peut lire ces fichiers lorsqu'ils contiennent des données μ-law et PCM. Il ignorera les informations d'en-tête indiquant que les données sont compressées à l'aide de la compression shorten et traitera les données comme μ-law ou PCM. SoX et le programme de ligne de commande shorten peuvent être exécutés ensemble en utilisant des pipes pour encapsuler les données, puis passer le résultat à SoX pour traitement.
.spx, .speex (avec ffmpeg)
Le format Ogg Speex est destiné à une compression élevée de la parole qui, en mode VBR, atteint une meilleure qualité que AMR ou GSM, mais est maintenant considéré comme remplacé par leur codec Opus plus récent.
sunau (optionnel)

	sox_ng infile -t sunau /dev/audio

pour le matériel Sun plus ancien.
.svcd (avec ffmpeg)

.tta (avec ffmpeg)
Format True Audio.
.vag (avec ffmpeg)
Format VAG Sony PS2.
.txw
TXW est un format de fichier du clavier échantillonneur Yamaha TX-16W qui écrivait des échantillons sur des disquettes au format IBM/PC de 3,5 pouces à des fréquences d'échantillonnage de 16 kHz, 33 kHz et 50 kHz, tous diviseurs exacts de 100 kHz. Lorsqu'il est décodé en fichiers WAV ou dans d'autres formats qui ne représentent que des fréquences d'échantillonnage entières, il est déclaré comme 16667 et 33333, mais dans les fichiers WAV, le champ du débit binaire est incorrect à 66667.

SoX gère la lecture des fichiers qui n'ont pas le champ de fréquence d'échantillonnage défini sur l'un des taux attendus en examinant d'autres octets dans les champs d'attaque/boucle et en utilisant par défaut 33 kHz si la fréquence d'échantillonnage est toujours inconnue.

.vcd (avec ffmpeg)
Un autre nom pour .mov.
.vms
Voir .dvms.
.vob (avec ffmpeg)
Un autre nom pour .mov.
.voc (également avec -t sndfile ou -t ffmpeg)
Les fichiers VOC Sound Blaster sont multi-parties et contiennent des parties de silence, des boucles et différentes fréquences d'échantillonnage pour différents blocs. En entrée, les parties de silence sont complétées, les boucles sont rejetées, et les données d'échantillons avec une nouvelle fréquence d'échantillonnage sont rejetées. Le silence avec une fréquence d'échantillonnage différente est généré appropriément. En sortie, le silence n'est pas détecté, ni les fréquences d'échantillonnage impossibles. SoX lit mais ne peut pas écrire de fichiers VOC avec plusieurs blocs et des fichiers contenant des échantillons μ-law, A-law et ADPCM 2/3/4 bits.
.vorbis
Voir .ogg.
.vox
Les fichiers sans en-tête de données audio ADPCM Dialogic/OKI sont couramment dotés de l'extension .vox. Ces données ADPCM ont une précision de 12 bits empaquetée dans seulement 4 bits.

Remarque : certains matériels Dialogic anciens ne réinitialisent pas toujours l'encodeur ADPCM au début de chaque fichier vox. Cela peut entraîner des problèmes de clipping et/ou de décalage CC lors du décodage audio. Bien que peu puisse être fait concernant le clipping, un décalage CC peut être supprimé en faisant passer l'audio décodé par un filtre passe-haut, par exemple :

	sox_ng input.vox output.wav highpass 10
.w64 (avec sndfile, également avec -t ffmpeg)
Format RIFF/WAV 64 bits de Sonic Foundry.

SoX ne peut détecter automatiquement ce type de fichier que par son extension ; s'il est lu depuis `l'entrée standard' (stdin) ou depuis un fichier dont le nom ne se termine pas par `.w64', vous devrez le préfixer avec `-t w64'.

.wav (également avec -t sndfile ou -t ffmpeg)
Les fichiers RIFF .WAV de Microsoft sont le format de fichier audio natif de Windows et sont largement utilisés pour l'audio non compressé.

Normalement, les fichiers .wav ont toutes les informations de formatage dans leurs en-têtes, donc les options de format ne doivent généralement pas être spécifiées pour les fichiers d'entrée. Si elles le sont, elles remplacent l'en-tête du fichier et vous en serez averti. Les options de format de sortie provoqueront une conversion de format et le .wav sera écrit en conséquence.

SoX peut lire et écrire des échantillons codés PCM linéaires, flottants, μ-law, A-law, MS ADPCM et IMA (ou DVI) ADPCM. Les fichiers WAV peuvent également contenir de l'audio codé d'autres manières non prises en charge actuellement par SoX (par exemple, MP3) ; dans certains cas, un tel fichier peut toujours être lu par SoX en remplaçant le type de fichier, par exemple.

   play -t mp3 mp3-encoded.wav

Nativement, SoX ne peut lire que les fichiers WAV avec une profondeur de 8, 16, 24 ou 32 bits ; les fichiers avec d'autres profondeurs de bits peuvent être lus en les précédant de -t sndfile.

Les versions Big Endian des fichiers RIFF, appelées RIFX, sont également prises en charge. Pour écrire un fichier RIFX, utilisez l'option de fichier de sortie -B.

Voir aussi .wavpcm.

waveaudio (optionnel)
Le pilote de périphérique audio natif de MS-Windows. Exemples : 
	sox_ng infile -t waveaudio
	sox_ng infile -t waveaudio default
	sox_ng infile -t waveaudio 1
	sox_ng infile -t waveaudio "High Definition Audio Device"
Si le nom du périphérique est omis, -1, ou default, vous obtenez le périphérique `Microsoft Wave Mapper'. Wave Mapper signifie `utiliser les périphériques audio par défaut du système' et vous pouvez contrôler ce que `défaut' signifie via le panneau de configuration de l'OS.

Si le nom de périphérique donné est un autre nombre, vous obtenez ce périphérique audio par son index, donc l'enregistrement avec le nom de périphérique 0 obtiendrait le premier périphérique d'entrée (peut-être le microphone), 1 le second (peut-être l'entrée ligne), etc. La lecture utilisant le nom de périphérique 0 obtiendrait le premier périphérique de sortie (généralement le seul périphérique audio).

Si le nom de périphérique donné est autre chose qu'un nombre, SoX essaie de le faire correspondre (jusqu'à un maximum de 31 caractères) aux noms des périphériques disponibles.

.wavpcm
Une variante non standard mais largement utilisée de .wav. Certaines applications ne peuvent pas lire un en-tête de fichier WAV standard pour les données codées en PCM avec une taille d'échantillon supérieure à 16 bits ou avec plus de deux canaux, mais peuvent lire un en-tête WAV non standard. Il est probable que de telles applications seront mises à jour pour prendre en charge l'en-tête standard, mais en attendant, ce format SoX peut être utilisé pour créer des fichiers avec l'en-tête non standard qui devraient fonctionner avec ces applications. SoX détecte et lit automatiquement les fichiers WAV avec un en-tête non standard.

L'utilisation la plus courante de ce type de fichier sera probablement la suivante :

	sox_ng infile.any -t wavpcm -e signed-integer outfile.wav
