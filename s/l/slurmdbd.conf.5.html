slurmdbd.conf(5) Fichier de configuration Slurm slurmdbd.conf(5)

NOM

slurmdbd.conf - Fichier de configuration du démon de base de données Slurm (SlurmDBD)

DESCRIPTION

slurmdbd.conf est un fichier ASCII qui décrit les informations de configuration du démon de base de données Slurm (SlurmDBD). Le fichier sera toujours situé dans le même répertoire que slurm.conf.

Le contenu du fichier ne respecte pas la casse, à l'exception des noms des nœuds et des fichiers. Tout texte suivant un "#" dans le fichier de configuration est traité comme un commentaire jusqu'à la fin de la ligne. Les modifications apportées au fichier de configuration prennent effet au redémarrage de SlurmDBD ou à la réception du signal SIGHUP par le démon, sauf indication contraire.

Ce fichier ne doit résider que sur la machine où s'exécute SlurmDBD, être la propriété de SlurmUser ou de root, et avoir les permissions définies sur 600 ou 640. Si le démon slurmdbd est démarré en tant qu'utilisateur root et change d'ID utilisateur, le fichier de configuration sera initialement lu en tant qu'utilisateur root, mais sera lu en tant qu'autre ID utilisateur en réponse à un signal SIGHUP. Ce fichier doit être protégé contre tout accès non autorisé car il contient un mot de passe de base de données. Les paramètres de configuration généraux disponibles comprennent :

AllowNoDefAcct
Supprime l'exigence pour les utilisateurs d'avoir un compte par défaut. Booléen, oui pour activer, non (par défaut) pour imposer des comptes par défaut.
AllResourcesAbsolute
Lors de l'ajout d'une ressource (licence), les nombres alloués/autorisés sont traités comme des nombres absolus au lieu de pourcentages. Booléen, oui pour activer, non (par défaut) pour utiliser les nombres comme pourcentages à la place.
ArchiveDir
Si ArchiveScript n'est pas défini, slurmdbd générera un fichier qui peut être lu ultérieurement avec la commande sacctmgr load filename. Ce répertoire est l'endroit où le fichier sera placé après un événement de purge et où l'archivage pour cet élément est défini sur vrai. Par défaut, il s'agit de /tmp. Le format du nom de ce fichier est $ArchiveDir/$NomCluster_$ObjetArchive_$DebutTimestamp_$FinTimestamp. Nous limitons les fichiers d'archive à MaxPurgeLimit enregistrements par fichier. S'il existe plus d'enregistrements pendant cette période, ils seront écrits dans un nouveau fichier. Les fichiers d'archive successifs pendant la même période se verront ajouter ".<nombre>" au nom du fichier, par exemple .2, le nombre augmentant de un pour chaque fichier dans la même période.
ArchiveEvents
Lors de la purge des événements, les archiver également. Booléen, oui pour archiver les données d'événements, non sinon. Par défaut, non.
ArchiveJobs
Lors de la purge des jobs, les archiver également. Booléen, oui pour archiver les données de jobs, non sinon. Par défaut, non.
ArchiveResvs
Lors de la purge des réservations, les archiver également. Booléen, oui pour archiver les données de réservations, non sinon. Par défaut, non.

Ce script est utilisé pour transférer les enregistrements de comptabilité de la base de données vers une archive. Il est utilisé à la place du processus interne d'archivage des objets. Le script est exécuté sans arguments, et les variables d'environnement suivantes sont définies.

AuthInfo
Informations supplémentaires à utiliser pour l'authentification des communications avec le démon de contrôle Slurm (slurmctld) sur chaque cluster. L'interprétation de cette option est spécifique au AuthType configuré. Plusieurs options peuvent être spécifiées dans une liste délimitée par des virgules. Si elle n'est pas spécifiée, les informations d'authentification par défaut seront utilisées.
socket
Nom du chemin d'un socket du démon MUNGE à utiliser (par exemple, "socket=/var/run/munge/munge.socket.2"). La valeur par défaut est "/var/run/munge/munge.socket.2". Utilisé par auth/munge et cred/munge.
ttl
Durée de vie du credential, en secondes (par exemple, "ttl=300"). La valeur par défaut dépend de l'installation de MUNGE, mais est généralement de 300 secondes.
use_client_ids
Permet au plugin auth/slurm d'authentifier les utilisateurs sans s'appuyer sur les informations utilisateur de LDAP ou du système d'exploitation.
AuthType
Définit la méthode d'authentification pour les communications entre les composants Slurm. SlurmDBD doit être arrêté avant de changer la valeur de AuthType et redémarré ultérieurement. Ceci doit correspondre au AuthType utilisé dans slurm.conf. Valeurs acceptables à l'heure actuelle :
auth/munge
Indique que MUNGE doit être utilisé (par défaut). (Voir "https://dun.github.io/munge/" pour plus d'informations).
auth/slurm
Utilise le plugin d'authentification interne de Slurm.
CommitDelay
Nombre de secondes entre les commits sur une connexion d'un Slurmctld. Cela accélère considérablement les insertions dans la base de données. Si vous exécutez un débit de travaux très élevé, vous devriez envisager de le définir. En test, 1 seconde améliore considérablement les performances de slurmdbd et réduit la surcharge. Il y a cependant une faible probabilité de perte de données car cela crée une fenêtre pendant laquelle, si slurmdbd s'arrête anormalement pour une raison quelconque, les données non committées pourraient être perdues. Bien que cette situation doive être très rare, elle présente un risque extrêmement faible, mais peut être la seule façon de fonctionner dans des environnements extrêmement intensifs. En toute honnêteté, le risque est assez faible, mais il est toujours présent.

Ceci affecte la plupart des connexions sortantes de slurmdbd (par exemple, entre le primaire et le secondaire, ou de slurmdbd vers slurmctld). La valeur par défaut est de 30 secondes.
DbdAddr
Nom auquel DbdHost doit être référé pour établir un chemin de communication. Ce nom sera utilisé comme argument pour la fonction getaddrinfo() à des fins d'identification. Par exemple, "elx0000" pourrait être utilisé pour désigner l'adresse Ethernet du nœud "lx0000". Par défaut, DbdAddr sera identique en valeur à DbdHost.
DbdBackupHost
Le nom court ou long de la machine où s'exécute le démon de base de données Slurm de secours (c'est-à-dire le nom renvoyé par la commande "hostname -s"). Cet hôte doit avoir accès à la même base de données sous-jacente spécifiée par les options 'Storage' mentionnées ci-dessous.
DbdHost
Le nom court ou long de la machine où s'exécute le démon de base de données Slurm (c'est-à-dire le nom renvoyé par la commande "hostname -s"). Cette valeur doit être spécifiée.
DbdPort
Le numéro de port sur lequel le démon de base de données Slurm (slurmdbd) écoute les requêtes. La valeur par défaut est SLURMDBD_PORT telle que définie au moment de la construction du système. Si aucune valeur n'est explicitement spécifiée, elle sera définie à 6819. Cette valeur doit être égale au paramètre AccountingStoragePort dans le fichier slurm.conf.

Identifie le type de plugin de hachage à utiliser pour la communication réseau. Les valeurs acceptables incluent :

LogFile

LogTimeFormat
Format de l'horodatage dans les fichiers journaux de slurmdbd. Les valeurs de format acceptées incluent "iso8601", "iso8601_ms", "rfc5424", "rfc5424_ms", "rfc3339", "clock", "short" et "thread_id". Les valeurs se terminant par "_ms" diffèrent de celles sans par le fait que les secondes fractionnaires avec précision en millisecondes sont imprimées. La valeur par défaut est "iso8601_ms". Les formats "rfc5424" sont identiques aux formats "iso8601" sauf que la valeur du fuseau horaire est également affichée. Le format "clock" affiche un horodatage en microsecondes récupéré avec la fonction C standard clock(). Le format "short" est un format de date et d'heure court. Le format "thread_id" affiche l'horodatage sous forme de fonction C standard ctime() sans l'année mais incluant les microsecondes, l'ID du processus du démon et le nom et l'ID du thread actuel.
MaxPurgeLimit
Lors de l'archivage et de la purge des enregistrements, limitez chaque opération individuelle à ce nombre de lignes. Les opérations se répéteront ensuite jusqu'à ce que toutes les lignes ciblées soient traitées. Cette limite garantit que les verrous seront périodiquement libérés, permettant à d'autres opérations de base de données de se produire. Une limite plus faible libérera les verrous plus fréquemment, ce qui peut améliorer la réactivité du système lors de la purge des enregistrements de grandes tables. Cependant, une limite plus faible augmentera également le nombre total d'opérations.

MaxQueryTimeRange
Retourne une erreur si une requête concerne un intervalle de temps trop vaste, afin d'empêcher les requêtes malformées de causer des problèmes de performance au sein de SlurmDBD. La valeur par défaut est INFINITE, ce qui permet à toutes les requêtes de se poursuivre. Les formats de temps acceptés sont les mêmes que ceux de l'option MaxTime dans slurm.conf. Les opérateurs et les utilisateurs disposant de privilèges supérieurs sont exemptés de cette restriction. Notez que les requêtes qui tentent de renvoyer plus de 3 Go de données échoueront toujours à se terminer avec ESLURM_RESULT_TOO_LARGE.
MessageTimeout
Temps autorisé pour qu'une communication aller-retour s'achève, en secondes. La valeur par défaut est de 10 secondes.
Parameters
Contient des paramètres arbitraires séparés par des virgules, utilisés pour modifier le comportement de slurmdbd.
PreserveCaseUser
Lors de la définition des utilisateurs, ne pas forcer la casse minuscule, ce qui est le comportement par défaut.
PidFile
Chemin d'accès complet à un fichier dans lequel le démon Slurm Database Daemon peut écrire son ID de processus. Ceci peut être utilisé pour un traitement automatisé des signaux. La valeur par défaut est "/var/run/slurmdbd.pid".
PluginDir
Identifie les emplacements où chercher les plugins Slurm. Il s'agit d'une liste de répertoires séparés par des deux-points, similaire à la variable d'environnement PATH. La valeur par défaut est le préfixe donné lors de la configuration + "/lib/slurm".
PrivateData
Ceci contrôle quel type d'information est caché aux utilisateurs réguliers. Par défaut, toutes les informations sont visibles par tous les utilisateurs. L'utilisateur SlurmUser, root, et les utilisateurs avec AdminLevel=Admin peuvent toujours voir toutes les informations. Plusieurs valeurs peuvent être spécifiées avec un séparateur virgule. Les valeurs acceptables incluent :
accounts
empêche les utilisateurs de voir les définitions de compte, sauf s'ils en sont les coordinateurs.
events
empêche les utilisateurs de voir les informations d'événements, sauf s'ils ont le statut d'opérateur ou supérieur.
jobs
empêche les utilisateurs de voir les enregistrements de travaux appartenant à d'autres utilisateurs, sauf s'ils sont coordinateurs du compte exécutant le travail lors de l'utilisation de sacct.

restreint l'obtention des informations de réservation aux utilisateurs ayant le statut d'opérateur et supérieur.
usage
empêche les utilisateurs de voir l'utilisation de tout autre utilisateur. Ceci s'applique à sreport.

empêche les utilisateurs de voir les informations de tout autre utilisateur qu'eux-mêmes, ce qui fait également que les utilisateurs ne peuvent voir que les associations qu'ils gèrent. Les coordinateurs peuvent voir les associations de tous les utilisateurs du compte dont ils sont coordinateurs, mais ne peuvent se voir eux-mêmes lors de la liste des utilisateurs.
PurgeEventAfter
Les événements sont purgés de la base de données après expiration de ce délai depuis leur fin. Cela inclut les indisponibilités de nœuds et autres. Le temps est une valeur numérique et représente un nombre de mois. Si vous souhaitez purgér plus fréquemment, vous pouvez inclure "hours" (heures) ou "days" (jours) derrière la valeur numérique pour obtenir des purges plus fréquentes (par exemple, une valeur de "12hours" purgerait tout ce qui est plus ancien que 12 heures). La purge a lieu au début de chaque intervalle de purge. Par exemple, si le temps de purge est de 2 mois, la purge se produira au début de chaque mois. Si non défini (par défaut), les enregistrements d'événements ne sont jamais purgés.

Le temps est une valeur numérique et représente un nombre de mois. Si vous souhaitez purger plus fréquemment, vous pouvez inclure "hours" (heures) ou "days" (jours) derrière la valeur numérique pour obtenir des purges plus fréquentes (par exemple, une valeur de "12hours" purgerait tout ce qui est plus ancien que 12 heures). La purge a lieu au début de chaque intervalle de purge. Par exemple, si le temps de purge est de 2 mois, la purge se produira au début de chaque mois. Si non défini (par défaut), les enregistrements de travaux ne sont jamais purgés.

Les enregistrements de réservation individuels sont purgés de la base de données après expiration de ce délai depuis leur fin. Les informations agrégées seront préservées jusqu'à "PurgeUsageAfter". Le temps est une valeur numérique et représente un nombre de mois. Si vous souhaitez purger plus fréquemment, vous pouvez inclure "hours" (heures) ou "days" (jours) derrière la valeur numérique pour obtenir des purges plus fréquentes (par exemple, une valeur de "12hours" purgerait tout ce qui est plus ancien que 12 heures). La purge a lieu au début de chaque intervalle de purge. Par exemple, si le temps de purge est de 2 mois, la purge se produira au début de chaque mois. Si non défini (par défaut), les enregistrements de réservation ne sont jamais purgés.

Les enregistrements de pas de travaux individuels sont purgés de la base de données après expiration de ce délai depuis leur fin. Les informations agrégées seront préservées jusqu'à "PurgeUsageAfter". Le temps est une valeur numérique et représente un nombre de mois. Si vous souhaitez purger plus fréquemment, vous pouvez inclure "hours" (heures) ou "days" (jours) derrière la valeur numérique pour obtenir des purges plus fréquentes (par exemple, une valeur de "12hours" purgerait tout ce qui est plus ancien que 12 heures). La purge a lieu au début de chaque intervalle de purge. Par exemple, si le temps de purge est de 2 mois, la purge se produira au début de chaque mois. Si non défini (par défaut), les enregistrements de pas de travaux ne sont jamais purgés.
PurgeSuspendAfter
Les enregistrements de suspension de travaux individuels sont purgés de la base de données après expiration de ce délai depuis leur fin. Les informations agrégées seront préservées jusqu'à "PurgeUsageAfter". Le temps est une valeur numérique et représente un nombre de mois. Si vous souhaitez purger plus fréquemment, vous pouvez inclure "hours" (heures) ou "days" (jours) derrière la valeur numérique pour obtenir des purges plus fréquentes (par exemple, une valeur de "12hours" purgerait tout ce qui est plus ancien que 12 heures). La purge a lieu au début de chaque intervalle de purge. Par exemple, si le temps de purge est de 2 mois, la purge se produira au début de chaque mois. Si non défini (par défaut), les enregistrements de suspension ne sont jamais purgés.
PurgeTXNAfter
Les enregistrements de transactions individuels sont purgés de la base de données après expiration de ce délai depuis leur occurrence. Le temps est une valeur numérique et représente un nombre de mois. Si vous souhaitez purger plus fréquemment, vous pouvez inclure "hours" (heures) ou "days" (jours) derrière la valeur numérique pour obtenir des purges plus fréquentes (par exemple, une valeur de "12hours" purgerait tout ce qui est plus ancien que 12 heures). La purge a lieu au début de chaque intervalle de purge. Par exemple, si le temps de purge est de 2 mois, la purge se produira au début de chaque mois. Si non défini (par défaut), les enregistrements de transactions ne sont jamais purgés.
PurgeUsageAfter
Les enregistrements d'utilisation (Cluster, Association, QOS et WCKey) sont purgés de la base de données après expiration de ce délai depuis leur création ou leur dernière modification. Ces tables sont la source des rapports générés par la commande sreport(1). Le temps est une valeur numérique et représente un nombre de mois. Si vous souhaitez purger plus fréquemment, vous pouvez inclure "hours" (heures) ou "days" (jours) derrière la valeur numérique pour obtenir des purges plus fréquentes (par exemple, une valeur de "12hours" purgerait tout ce qui est plus ancien que 12 heures). La purge a lieu au début de chaque intervalle de purge. Par exemple, si le temps de purge est de 2 mois, la purge se produira au début de chaque mois. Si non défini (par défaut), les enregistrements d'utilisation ne sont jamais purgés.
SlurmUser
Le nom de l'utilisateur sous lequel le démon slurmdbd s'exécute. Cet utilisateur doit correspondre au SlurmUser utilisé pour toutes les instances de slurmctld qui rapportent à slurmdbd. Il doit exister sur la machine exécutant le Slurm Database Daemon et avoir le même UID que les hôtes sur lesquels slurmctld s'exécute. Pour des raisons de sécurité, un utilisateur autre que "root" est recommandé. La valeur par défaut est "root".

>NOTE: Si le SlurmUser pour slurmctld est root, vous pouvez toujours utiliser un SlurmUser non-root pour slurmdbd (dans tous les autres cas, les deux SlurmUsers doivent correspondre) en définissant explicitement le niveau d'administrateur de l'utilisateur sur Admin. Après avoir ajouté un utilisateur de cette manière, vous devez redémarrer slurmctld.

StorageBackupHost
Définit le nom de l'hôte de sauvegarde sur lequel la base de données est exécutée et où nous allons stocker les données. Ceci peut être considéré comme une solution de sauvegarde lorsque le StorageHost ne répond pas. Il appartient à la solution de sauvegarde d'assurer la cohérence des informations de comptabilité entre les deux hôtes. Avec les solutions de bases de données en cluster (HA actif/passif), vous n'aurez pas besoin d'utiliser cette fonctionnalité. La valeur par défaut est none.
StorageHost
Définit le nom de l'hôte sur lequel la base de données s'exécute et où nous allons stocker les données. Il peut s'agir de l'hôte sur lequel slurmdbd s'exécute, mais pour les systèmes plus importants, nous recommandons de conserver la base de données sur une machine distincte.
StorageLoc
Spécifie le nom de la base de données comme emplacement où les enregistrements de comptabilité sont écrits. La valeur par défaut est "slurm_acct_db".
StorageParameters
Liste de paramètres clé-valeur séparés par des virgules.
SSL_CERT
Le chemin d'accès au fichier de certificat public de la clé client.
SSL_CA
Le chemin d'accès au fichier de certificat de l'autorité de certification (CA).
SSL_CAPATH
Le chemin d'accès au répertoire qui contient les fichiers de certificat CA SSL de confiance.
SSL_KEY
Le chemin d'accès au fichier de clé privée client.
SSL_CIPHER
La liste des chiffrements autorisés pour le chiffrement SSL.
token_duration
Durée en secondes pendant laquelle les mots de passe de base de données générés sont mis en cache avant de demander un nouveau mot de passe au StoragePassScript. Généralement, le jeton devrait être actualisé avant son expiration réelle ; en cas d'échec de génération du jeton, le jeton mis en cache continuera d'être utilisé pour éviter que des échecs de génération transitoires ne provoquent des échecs de connexion. La valeur par défaut est 300 secondes (5 minutes).
StoragePass
Définit le mot de passe utilisé pour accéder à la base de données afin de stocker les données de comptabilité des jobs. Le caractère '#' n'est pas autorisé dans un mot de passe.
StoragePassScript
Chemin absolu vers un script exécutable qui génère des jetons d'authentification éphémères pour les connexions à la base de données, qui sont utilisés à la place de StoragePass. Le script doit écrire le mot de passe/jeton sur stdout et se terminer avec le statut 0 en cas de succès. Cela permet la génération dynamique de mots de passe, au lieu de stocker des identifiants statiques dans les fichiers de configuration. Le script doit être la propriété de SlurmUser et être exécutable par celui-ci.
Variables d'environnement fournies au script :
SLURM_STORAGE_HOSTNAME
Nom d'hôte de la base de données
SLURM_STORAGE_PORT
Numéro de port de la base de données
SLURM_STORAGE_USER
Nom d'utilisateur de la base de données
Format de sortie attendu :
TOKEN=<authentication_token>
Le script doit se terminer avec le statut 0 en cas de succès, et non zéro en cas d'échec. Tout ce qui est envoyé sur stderr sera enregistré comme une erreur. S'il y a un hôte de sauvegarde spécifié, le script recevra toujours le nom d'hôte principal et le même jeton sera utilisé pour les deux hôtes.
StoragePort
Le numéro de port que le démon de base de données Slurm (slurmdbd) utilise pour communiquer avec la base de données. La valeur par défaut est 3306.
StorageType
Définit le type de mécanisme de stockage de comptabilité. Les valeurs acceptables à l'heure actuelle incluent "accounting_storage/mysql". La valeur "accounting_storage/mysql" indique que les enregistrements de comptabilité doivent être écrits dans une base de données MySQL ou MariaDB spécifiée par le paramètre StorageLoc. Cette valeur doit être spécifiée.
StorageUser
Définit le nom de l'utilisateur avec lequel nous allons nous connecter à la base de données pour stocker les données de comptabilité des jobs. Si aucune valeur n'est spécifiée, l'utilisateur qui a démarré slurmdbd sera utilisé.
TCPTimeout
Temps autorisé pour l'établissement d'une connexion TCP. La valeur par défaut est 2 secondes.
TLSParameters
Options séparées par des virgules identifiant les options TLS. Les valeurs prises en charge incluent :
ca_cert_file=
Chemin d'accès au certificat de l'autorité de certification (CA). Doit exister sur tous les hôtes et être accessible par tous les composants Slurm. Les permissions du fichier doivent être 644 et il doit être la propriété de SlurmUser/root.

Le chemin par défaut est "ca_cert.pem" dans le répertoire de configuration Slurm

dbd_cert_file=
Chemin d'accès au certificat utilisé par slurmdbd. Doit être chaîné au ca_cert_file. Ne devrait exister que sur l'hôte exécutant slurmdbd. Les permissions du fichier doivent être 600 et il doit être la propriété de SlurmUser.

Le chemin par défaut est "dbd_cert.pem" dans le répertoire de configuration Slurm

dbd_cert_key_file=
Chemin d'accès à la clé privée accompagnant dbd_cert_file. Ne devrait exister que sur l'hôte exécutant slurmdbd. Les permissions du fichier doivent être 600 et il doit être la propriété de SlurmUser.

Le chemin par défaut est "dbd_cert_key.pem" dans le répertoire de configuration Slurm

load_system_certificates
Charge les certificats trouvés dans les emplacements système par défaut (par exemple, /etc/ssl) dans le magasin de confiance.

Par défaut, les certificats système ne sont pas chargés, et la confiance est établie uniquement par le ca_cert_file.

security_policy_version=
Version de la politique de sécurité utilisée par s2n. Voir la documentation s2n pour plus d'informations. La politique de sécurité par défaut est "20230317", qui est conforme FIPS et inclut TLS 1.3.
TLSType
Spécifie l'implémentation TLS qui sera utilisée. Les valeurs acceptables à l'heure actuelle sont :
tls/s2n
Utilise le plugin TLS s2n.
TrackSlurmctldDown
Booléen oui ou non. Si défini, slurmdbd marquera toutes les ressources inactives du cluster comme "down" lorsqu'un slurmctld se déconnecte ou n'est plus joignable. La valeur par défaut est non.
TrackWCKey
Booléen oui ou non. Utilisé pour définir l'affichage et le suivi de la Clé de Caractérisation de la Charge de Travail (Workload Characterization Key). Doit être défini pour suivre l'utilisation des wckey. Ceci doit être défini pour générer des tables d'utilisation agrégées à partir des WCKeys. NOTE : Si TrackWCKey est défini ici et non dans vos différents fichiers slurm.conf, tous les jobs seront attribués à leur WCKey par défaut.
