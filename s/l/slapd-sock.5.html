NOM

slapd-sock - Backend/superposition socket pour slapd

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

Le backend Socket de slapd(8) utilise un programme externe pour gérer les requêtes qui écoute sur un socket de domaine Unix. Cela permet d'avoir un pool de processus, qui persistent entre les requêtes. Ceci permet une opération multithread et un haut niveau d'efficacité. Le programme externe doit être démarré indépendamment ; slapd(8) lui-même ne le démarrera pas.

Ce module peut également être utilisé comme une superposition par-dessus une autre base de données. L'utilisation en tant que superposition permet de déclencher des actions externes en réponse aux opérations sur la base de données principale.

CONFIGURATION

Ces options slapd.conf s'appliquent à la base de données backend SOCK. C'est-à-dire qu'elles doivent suivre une ligne « database sock » et précéder toute ligne « backend » ou « database » ultérieure. Les autres options de base de données sont décrites dans le manuel slapd.conf(5).

Alternativement, pour utiliser ce module comme une superposition, ces directives doivent suivre une ligne « overlay sock » dans une définition de base de données existante.

extensions [ binddn | peername | ssf | connid ]*
Active l'envoi d'attributs méta supplémentaires avec chaque requête. 
binddn: <DN lié>
peername: IP=<adresse>:<port>
ssf: <valeur SSF>
connid: <ID de connexion>
socketpath <chemin>
Donne le chemin d'un socket de domaine Unix vers lequel les commandes seront envoyées et à partir duquel les réponses seront reçues.

Lorsqu'il est utilisé comme superposition, ces directives supplémentaires sont définies :

sockops [ bind | unbind | search | compare | modify | modrdn | add | delete | extended ]*
Spécifie quels types de requêtes envoyer au programme externe. La valeur par défaut est vide (aucune requête n'est envoyée).
sockresps [ result | search ]*
Spécifie quels types de réponses envoyer au programme externe. « result » envoie uniquement les résultats d'une opération. « search » envoie toutes les entrées que la base de données a retournées pour une requête de recherche. La valeur par défaut est vide (aucune réponse n'est envoyée).
sockdnpat <regexp>
Spécifie les modèles de DN pour lesquels la superposition agira. Seules les opérations sur les DN correspondant à l'expression régulière spécifiée seront traitées. La valeur par défaut est vide (tous les DN sont traités).

PROTOCOLE

Le protocole utilise un retour à la ligne pour terminer les paramètres de commande. Les commandes suivantes sont envoyées :

ADD
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
<entrée au format LDIF>
<ligne vide>
BIND
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
dn: <DN>
method: <numéro de méthode>
credlen: <longueur des <identifiants>>
cred: <identifiants>
<ligne vide>
COMPARE
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
dn: <DN>
<attribut>: <valeur>
<ligne vide>
DELETE
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
dn: <DN>
<ligne vide>
EXTENDED
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
oid: <OID>
value: <valeur base64>
<ligne vide>
MODIFY
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
dn: <DN>
<répéter {
    <"add"/"delete"/"replace">: <attribut>
    <répéter { <attribut>: <valeur> }>
    -
}>
<ligne vide>
MODRDN
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
dn: <DN>
newrdn: <nouveau RDN>
deleteoldrdn: <0 ou 1>
<si le nouveau parent est spécifié : "newSuperior: <DN>">
<ligne vide>
SEARCH
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
base: <DN de base>
scope: <0-2, voir ldap.h>
deref: <0-3, voir ldap.h>
sizelimit: <limite de taille>
timelimit: <limite de temps>
filter: <filtre>
attrsonly: <0 ou 1>
attrs: <"tous" ou liste d'attributs séparés par des espaces>
<ligne vide>
UNBIND
msgid: <id du message>
<répéter { "suffix:" <DN du suffixe de la base de données> }>
<ligne vide>

Les commandes - sauf unbind - devraient produire :

RESULT
code: <entier>
matched: <DN correspondant>
info: <texte>
où seul RESULT est obligatoire, puis fermer le socket. Le RESULT de search devrait être précédé des entrées au format LDIF, chaque entrée suivie d'une ligne vide. Les lignes commençant par '#' ou 'DEBUG:' sont ignorées.

Lorsqu'il est utilisé comme superposition, le programme externe devrait retourner une réponse CONTINUE si le traitement de la requête doit continuer normalement, ou une réponse RESULT régulière si le programme externe souhaite contourner la base de données sous-jacente.

Si sockresps est configuré, la superposition sock ne prend pas en compte sockops ni sockdnpat pour décider quelles réponses sont transmises au programme externe, mais toutes les réponses sont actuellement transmises.

Le message RESULT étendu est similaire à celui ci-dessus, mais inclut également le msgid et les extensions configurées :

RESULT
msgid: <id du message>
code: <entier>
matched: <DN correspondant>
info: <texte>
<ligne vide>

Généralement, le msgid et le connid seront nécessaires pour faire correspondre un message de résultat à une requête. Le message ENTRY a la forme

ENTRY
msgid: <id du message>
<entrée au format LDIF>
<ligne vide>

LIMITATIONS CONNUES

Le backend sock ne traite pas les résultats d'opérations étendues d'un programme externe.

Si sockresps est configuré, la superposition sock ne prend pas en compte sockops ni sockdnpat pour décider quelles réponses sont passées au programme externe, au lieu de cela, toutes les réponses sont actuellement passées.

CONTROLE D'ACCES

Le backend sock ne respecte pas toutes les sémantiques ACL telles que décrites dans slapd.access(5). En général, l'accès aux objets est vérifié en utilisant un objet factice qui ne contient que le DN, de sorte que les règles d'accès qui dépendent du contenu de l'objet ne sont pas respectées. En détail :

L'opération add ne nécessite pas l'accès write (=w) à l'attribut pseudo-fils children de l'entrée parente.

L'opération bind nécessite l'accès auth (=x) à l'attribut pseudo-entrée entry de l'entrée dont l'identité est évaluée ; l'accès auth (=x) aux identifiants n'est pas vérifié, mais délégué au programme sous-jacent.

L'opération compare nécessite l'accès compare (=c) à l'attribut pseudo-entrée entry de l'objet dont la valeur est affirmée ; l'accès compare (=c) à l'attribut dont la valeur est affirmée n'est pas vérifié.

L'opération delete ne nécessite pas l'accès write (=w) à l'attribut pseudo-fils children de l'entrée parente.

L'opération modify nécessite l'accès write (=w) à l'attribut pseudo-entrée entry ; l'accès write (=w) aux attributs spécifiques qui sont modifiés n'est pas vérifié.

L'opération modrdn ne nécessite pas l'accès write (=w) à l'attribut pseudo-fils children de l'entrée parente, ni à celui du nouveau parent, s'il est différent ; l'accès write (=w)...

ss vers les valeurs distinguées des attributs de nommage n'est pas vérifié.

L'opération search ne nécessite pas d'accès search (=s) au pseudo-attribut entry de la rechercheBase ; l'accès search (=s) aux attributs et valeurs utilisés dans le filtre n'est pas vérifié.

L'opération extended ne nécessite aucun droit d'accès spécial. Le programme externe doit implémenter une quelconque forme de contrôle d'accès.

EXEMPLE

Il existe un script d'exemple dans le répertoire slapd/back-sock/ de l'arborescence source d'OpenLDAP.
