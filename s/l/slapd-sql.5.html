NOM

slapd-sql - Backend SQL pour slapd

SYNOPSIS

/etc/openldap/slapd.conf

DESCRIPTION

L'objectif principal de ce backend slapd(8) est de PRÉSENTER les informations stockées dans un SGBDR quelconque sous forme d'un sous-arbre LDAP sans aucune programmation (certains SQL et peut-être des procédures stockées ne peuvent pas être considérés comme de la programmation, de toute façon ;).

C'est-à-dire, par exemple, lorsque vous (un FAI) avez des informations de compte que vous utilisez dans un SGBDR, et que vous souhaitez utiliser des solutions modernes qui attendent ces informations en LDAP (pour authentifier les utilisateurs, effectuer des recherches d'e-mails, etc.). Ou vous souhaitez synchroniser ou distribuer des informations entre différents sites/applications utilisant des SGBDR et/ou LDAP. Ou quoi que ce soit d'autre...

Il n'est PAS conçu comme un backend à usage général qui utilise un SGBDR au lieu de LMDB (comme le fait le backend MDB standard), bien qu'il puisse être utilisé comme tel avec plusieurs limitations. Vous pouvez consulter http://www.openldap.org/faq/index.cgi?file=378 (OpenLDAP FAQ-O-Matic/FAQ Générale LDAP/Annuaire vs bases de données conventionnelles) pour en savoir plus à ce sujet.

L'idée (détaillée ci-dessous) est d'utiliser des métadonnées pour traduire les requêtes LDAP en requêtes SQL, en laissant le schéma relationnel intact, de sorte que les anciennes applications puissent continuer à l'utiliser sans modifications. Cela permet aux applications SQL et LDAP d'interopérer sans réplication, et d'échanger des données selon les besoins.

Le backend SQL est conçu pour être adaptable à pratiquement n'importe quel schéma relationnel sans avoir à modifier le code source (via ces métadonnées mentionnées). De plus, il utilise ODBC pour se connecter aux SGBDR, et est hautement configurable pour les dialectes SQL que les SGBDR peuvent utiliser, il peut donc être utilisé pour l'intégration et la distribution de données sur différents SGBDR, systèmes d'exploitation, hôtes, etc., en d'autres termes, dans un environnement hautement hétérogène.

Ce backend est expérimental.

CONFIGURATION

Ces options slapd.conf s'appliquent à la base de données du backend SQL, ce qui signifie qu'elles doivent suivre une ligne "database sql" et précéder toute ligne "backend" ou "database" ultérieure. Les autres options de base de données non spécifiques à ce backend sont décrites dans la page de manuel slapd.conf(5).

CONFIGURATION SOURCE DE DONNÉES

dbname <nom du source de données>
Le nom de la source de données ODBC à utiliser.

dbhost <nom d'hôte>
dbpasswd <mot de passe>
dbuser <nom d'utilisateur>

Les trois options ci-dessus sont généralement inutiles, car ces informations proviennent de la source de données spécifiée par la directive dbname. Elles permettent de remplacer les paramètres de la source de données. De plus, plusieurs pilotes SGBDR ont tendance à exiger la transmission explicite de l'utilisateur/mot de passe, même s'ils sont déjà fournis dans la source de données (Note : dbhost est actuellement ignoré).

CONFIGURATION PORTÉE

Ces options spécifient des modèles de requêtes SQL pour la portée des recherches.

subtree_cond <expression SQL>
Spécifie un modèle de clause WHERE utilisé pour former une condition de recherche de sous-arbre (dn="(.+,)?<dn>$"). Il peut différer d'un dialecte SQL à un autre (voir les exemples). Par défaut, il est construit sur la base des connaissances sur la façon de normaliser les valeurs des DN (par exemple, "<upper_func>(ldap_entries.dn) LIKE CONCAT('%',?)"); voir upper_func, upper_needs_cast, concat_pattern et strcast_func dans "CONFIGURATION D'AIDE" pour plus de détails.
children_cond <expression SQL>
Spécifie un modèle de clause WHERE utilisé pour former une condition de recherche des enfants (dn=".+,<dn>$"). Il peut différer d'un dialecte SQL à un autre (voir les exemples). Par défaut, il est construit sur la base des connaissances sur la façon de normaliser les valeurs des DN (par exemple, "<upper_func>(ldap_entries.dn) LIKE CONCAT('%,',?)"); voir upper_func, upper_needs_cast, concat_pattern et strcast_func dans "CONFIGURATION D'AIDE" pour plus de détails.
use_subtree_shortcut { OUI | non }
Ne pas utiliser la condition de sous-arbre lorsque la base de recherche est le suffixe de la base de données, et que la portée est sous-arbre ; plutôt collecter toutes les entrées.

CONFIGURATION INSTRUCTIONS

Ces options spécifient des modèles de requêtes SQL pour charger les métadonnées de mappage de schéma, ajouter et supprimer des entrées dans ldap_entries, etc. Toutes ces options, ainsi que subtree_cond, doivent avoir les valeurs par défaut données. Pour la valeur actuelle, il est recommandé de regarder les sources, ou dans la sortie du journal lorsque slapd démarre avec "-d 5" ou plus. Notez que le nombre et l'ordre des paramètres ne doivent pas être modifiés.

oc_query <expression SQL>
La requête utilisée pour collecter les données de mappage objectClass de la table ldap_oc_mappings ; voir "MÉTAINFORMATIONS UTILISÉES" pour les détails. La valeur par défaut est "SELECT id, name, keytbl, keycol, create_proc, delete_proc, expect_return FROM ldap_oc_mappings".
at_query <expression SQL>
La requête utilisée pour collecter les données de mappage attributeType de la table ldap_attr_mappings ; voir "MÉTAINFORMATIONS UTILISÉES" pour les détails. La valeur par défaut est "SELECT name, sel_expr, from_tbls, join_where, add_proc, delete_proc, param_order, expect_return FROM ldap_attr_mappings WHERE oc_map_id=?".
id_query <expression SQL>
La requête utilisée pour mapper un DN à une entrée dans la table ldap_entries ; voir "MÉTAINFORMATIONS UTILISÉES" pour les détails. La valeur par défaut est "SELECT id,keyval,oc_map_id,dn FROM ldap_entries WHERE <expression de correspondance DN>", où <expression de correspondance DN> est construite sur la base des connaissances sur la façon de normaliser les valeurs des DN (par exemple, "dn=?" si aucun moyen de mettre en majuscules les chaînes n'est disponible ; typiquement, "<upper_func>(dn)=?" est utilisé) ; voir upper_func, upper_needs_cast, concat_pattern et strcast_func dans "CONFIGURATION D'AIDE" pour plus de détails.
insentry_stmt <expression SQL>
L'instruction utilisée pour insérer une nouvelle entrée dans la table ldap_entries ; voir "MÉTAINFORMATIONS UTILISÉES" pour les détails. La valeur par défaut est "INSERT INTO ldap_entries (dn, oc_map_id, parent, keyval) VALUES (?, ?, ?, ?)".
delentry_stmt <expression SQL>
L'instruction utilisée pour supprimer une entrée existante de la table ldap_entries ; voir "MÉTAINFORMATIONS UTILISÉES" pour les détails. La valeur par défaut est "DELETE FROM ldap_entries WHERE id=?".
delobjclasses_stmt <expression SQL>
L'instruction utilisée pour supprimer l'ID d'une entrée existante de la table ldap_objclasses ; voir "MÉTAINFORMATIONS UTILISÉES" pour les détails. La valeur par défaut est "DELETE FROM ldap_entry_objclasses WHERE entry_id=?".

CONFIGURATION AIDE

Ces instructions sont utilisées pour modifier le comportement par défaut du backend conformément aux problèmes du dialecte du SGBDR. Les premières options se réfèrent essentiellement à la normalisation des chaînes et des DN lors de la construction des filtres. La normalisation LDAP va au-delà de la mise en majuscules (ou minuscules) de tout ; cependant, comme compromis raisonnable, pour les SGBDR sensibles à la casse, le backend peut être instruit de mettre en majuscules les chaînes et les DN en fournissant la directive upper_func. Si nécessaire, une fonction de transtypage de chaînes peut également être fournie, en utilisant la directive strcast_func. Enfin, un motif de concaténation de chaînes personnalisé peut être requis ; il est fourni par la directive concat_pattern.

upper_func <nom de fonction SQL>
Spécifie le nom d'une fonction qui convertit une valeur donnée en majuscules. Ceci est utilisé pour une correspondance insensible à la casse lorsque le SGBDR est sensible à la casse. Il peut différer d'un dialecte SQL à un autre (par exemple, UCASE, UPPER ou autre ; voir les exemples). Par défaut, aucune n'est utilisée, c'est-à-dire que les chaînes ne sont pas mises en majuscules, donc les correspondances peuvent être sensibles à la casse.
upper_needs_cast { NON | oui }
Définissez cette directive sur oui si upper_func a besoin d'un transtypage explicite lorsqu'elle est appliquée à des chaînes littérales. Un transtypage sous la forme CAST (<argument> AS VARCHAR(<longueur maximale du DN>)) est utilisé, où <longueur maximale du DN> est intégrée dans back-sql ; voir la macro BACKSQL_MAX_DN_LEN (actuellement 255 ; notez que la limite intégrée de slapd, dans la macro SLAP_LDAPDN_MAXLEN, est fixée à 8192). Ceci est expérimental et peut changer dans les futures versions.
strcast_func <nom de fonction SQL>
Spécifie le nom d'une fonction qui convertit une valeur donnée en une chaîne de caractères pour un tri approprié. Ceci est utilisé dans les instructions "SELECT DISTINCT" pour les SGBDR fortement typés avec peu de transtypage implicite (comme PostgreSQL), lorsqu'une chaîne littérale est spécifiée. Ceci est expérimental et peut changer dans les futures versions.
concat_pattern <motif>
Cette instruction définit le motif qui est utilisé pour concaténer des chaînes. Le motif DOIT contenir deux points d'interrogation, '?', qui seront remplacés par les deux chaînes qui doivent être concaténées. La valeur par défaut est CONCAT(?,?) ; une forme connue pour être très portable (IBM db2, PostgreSQL) est ?||?, mais un transtypage explicite peut être requis lors de l'opération sur des chaînes littérales : CAST(?||? AS VARCHAR(<longueur>)). Sur certains SGBDR (IBM db2, MSSQL) la forme ?+? est également connue pour fonctionner. Vérifiez attentivement la documentation de votre SGBDR ou restez avec les exemples pour ceux qui sont pris en charge. Ceci est expérimental et peut changer dans les futures versions.
aliasing_keyword <chaîne>
Définit le mot-clé d'alias. Certains SGBDR utilisent le mot "AS" (par défaut), d'autres n'en utilisent aucun.
aliasing_quote <chaîne>
Définit le caractère de citation du mot-clé d'alias. Certains SGBDR n'en requièrent aucun (par défaut), d'autres peuvent nécessiter des guillemets simples ou doubles.
has_ldapinfo_dn_ru { NON | oui }
Informe explicitement le backend si la colonne dn_ru (DN en forme inversée en majuscules) est présente dans la table ldap_entries. Remplace la vérification automatique (ceci est requis, par exemple, par PostgreSQL/unixODBC). Ceci est expérimental et peut changer dans les futures versions.
fail_if_no_mapping { NON | oui }
Lorsqu'il est défini sur oui, cela force les opérations d'écriture d'*attribut* à échouer s'il n'y a pas de mappage approprié entre les attributs LDAP et les données SQL disponibles. Le comportement par défaut est d'ignorer les modifications qui ne peuvent pas être mappées. Cela n'a aucun impact sur le mappage des objectClass, c'est-à-dire que si l' *structuralObjectClass* d'une entrée ne peut pas être mappée en SQL en recherchant son nom dans ldap_oc_mappings, une opération d'*ajout* échouera quel que soit le commutateur fail_if_no_mapping ; voir la section "INFORMATIONS MÉTA UTILISÉES" pour plus de détails. Ceci est expérimental et peut changer dans les futures versions.
allow_orphans { NON | oui }
Lorsqu'il est défini sur oui, les entrées orphelines (c'est-à-dire sans l'entrée parent dans la base de données) peuvent être ajoutées. Cette option doit être utilisée avec précaution, éventuellement en conjonction avec une règle spéciale côté SGBDR qui crée dynamiquement le parent manquant.
baseObject [ <nom de fichier> ]
Indique à la base de données de créer et de gérer une entrée baseObject en mémoire au lieu d'en rechercher une dans le SGBDR. Si l'argument (optionnel) <nom de fichier> est donné, l'entrée est lue à partir de ce fichier au format LDIF(5) ; sinon, une entrée avec objectClass extensibleObject est créée en fonction du contenu du RDN de l' *baseObject*. Ceci est particulièrement utile lorsque les informations *ldap_entries* sont stockées dans une vue plutôt que dans une table, et que union n'est pas pris en charge pour les vues, de sorte que la vue ne peut spécifier qu'une règle pour calculer la structure de l'entrée pour un objectClass. Ce sujet est discuté plus en détail dans la section "INFORMATIONS MÉTADONNÉES UTILISÉES". Ceci est expérimental et peut changer dans les futures versions.
create_needs_select { NON | oui }
Indique à la base de données si la création d'entrée dans la table ldap_entries nécessite ou non une sélection subséquente pour collecter l'ID attribué automatiquement, au lieu d'être retourné par une procédure stockée.

fetch_attrs <liste d'attributs>
fetch_all_attrs { NON | oui }

La première instruction permet de fournir une liste d'attributs qui doivent toujours être récupérés en plus de ceux demandés par une opération spécifique, car ils sont nécessaires à l'utilisation correcte du backend. Par exemple, tous les attributs utilisés dans les ACL devraient être listés ici. La deuxième instruction est un raccourci pour exiger que tous les attributs soient toujours chargés. Notez que les attributs générés dynamiquement, par exemple hasSubordinates, entryDN et d'autres attributs dépendants de l'implémentation ne sont **pas** générés à ce stade, par souci de cohérence avec le reste de slapd. Cela pourrait changer à l'avenir.
check_schema { OUI | non }
Indique à la base de données de vérifier la conformité du schéma des entrées après les modifications, et la chaîne d'objectClasses structurelles lors de la construction des entrées. Par défaut, il est défini sur oui.
sqllayer <nom> [...]
Charge la couche <nom> sur une pile d'assistants qui sont utilisés pour mapper les DN de LDAP à la représentation SQL et vice-versa. Les arguments ultérieurs sont passés à la routine de configuration de la couche. Ceci est extrêmement expérimental et doit être utilisé avec une extrême prudence. L'API des couches n'est pas encore figée, elle n'est donc pas publiée.
autocommit { NON | oui }
Active l'autocommit ; par défaut, il est désactivé.

INFORMATIONS MÉTADONNÉES UTILISÉES

Presque tout ce qui est mentionné ci-dessous est illustré dans les exemples situés dans le répertoire servers/slapd/back-sql/rdbms_depend/ dans l'arborescence source d'OpenLDAP, et contient des scripts pour générer des bases de données exemples pour Oracle, MS SQL Server, mySQL et plus (y compris PostgreSQL et IBM db2).

La première chose à organiser est l'ensemble des classes d'objets LDAP qui peuvent représenter vos informations SGBDR.

La manière la plus simple est de créer une classe d'objet pour chaque entité que vous aviez dans votre diagramme ER lors de la conception de votre schéma relationnel. Tout schéma relationnel, aussi normalisé soit-il, a été conçu d'après un modèle du domaine de votre application (par exemple, comptes, services, etc. dans un FAI), et est utilisé en termes de ses entités, pas seulement des tables d'un schéma normalisé. Cela signifie que pour chaque attribut de chaque instance de ce type, il existe une requête SQL effective qui charge ses valeurs.

Vous pourriez également vouloir que vos classes d'objets soient conformes à certains des schémas standards comme inetOrgPerson, etc.

Néanmoins, lorsque vous y réfléchissez, nous devons définir un moyen de traduire les requêtes d'opération LDAP en (une série de) requêtes SQL. Abordons l'opération SEARCH.

Exemple : Supposons que nous stockions des informations sur les personnes travaillant dans notre organisation dans deux tables :

  PERSONNES              PHONES
  ----------           -------------
  id integer           id integer
  first_name varchar   pers_id integer references persons(id)
  last_name varchar    phone
  middle_name varchar
  ...

(PHONES contient les numéros de téléphone associés aux personnes). Une personne peut avoir plusieurs numéros, auquel cas PHONES contient plusieurs enregistrements avec le pers_id correspondant, ou aucun numéro (et aucun enregistrement dans PHONES avec un tel pers_id). Une classe d'objet LDAP pour représenter ces informations pourrait ressembler à ceci :

  person
  -------
  MUST cn
  MAY telephoneNumber $ firstName $ lastName
  ...

Pour récupérer toutes les valeurs de l'attribut cn étant donné un ID de personne, nous construisons la requête :

  SELECT CONCAT(persons.first_name,' ',persons.last_name)
      AS cn FROM persons WHERE persons.id=?

pour telephoneNumber nous pouvons utiliser :

  SELECT phones.phone AS telephoneNumber FROM persons,phones
      WHERE persons.id=phones.pers_id AND persons.id=?

Si nous voulions servir des requêtes LDAP avec des filtres comme (telephoneNumber=123*), nous construirions quelque chose comme :

  SELECT ... FROM persons,phones
      WHERE persons.id=phones.pers_id
          AND persons.id=?
          AND phones.phone like '%1%2%3%'

(notez comment la correspondance telephoneNumber est développée en multiples jokers pour tenir compte des caractères intermédiaires non influents comme les espaces, les tirets, etc. ; cela se produit par conception car telephoneNumber est défini après une syntaxe spécialement reconnue). Donc, si nous avions des informations sur quelles tables contiennent des valeurs pour chaque attribut, comment joindre ces tables et organiser ces valeurs, nous pourrions essayer de générer automatiquement de telles instructions et de traduire les filtres de recherche en clauses WHERE SQL.

Pour stocker de telles informations, nous ajoutons trois tables de plus à notre schéma et les remplissons de données (voir les exemples) :

  ldap_oc_mappings (certaines colonnes ne sont pas listées pour plus de clarté)
  ---------------
  id=1
  name="person"
  keytbl="persons"
  keycol="id"

Cette table définit un mappage entre la classe d'objet (son nom contenu dans la colonne "name"), et une table qui contient la clé primaire pour les entités correspondantes. Par exemple, dans notre exemple, l'entité personne

NAME

back_sql - SQL database backend for slapd

SYNOPSIS

cn=config

  database sql
  ...

slapd.conf

  database sql
  ...

DESCRIPTION

The SQL backend allows slapd to use a relational database as a backend storage. This is achieved by mapping LDAP entries to rows in SQL tables, and LDAP attributes to columns in those tables.

The configuration is done via several tables that must be present in the SQL database. These tables define the schema mapping, which corresponds to the LDAP schema. The main tables are:

  • ldap_oc_mappings: defines mappings between LDAP objectclasses and specific relational tables (and other metadata).
  • ldap_attr_mappings: defines mappings between LDAP attributes and SQL queries that retrieve their values.
  • ldap_entries: maps LDAP entry DNs to corresponding relational data primary keys.

The following explanation assumes you are familiar with SQL and relational databases.

OBJECTCLASS MAPPINGS

The ldap_oc_mappings table defines how LDAP objectclasses map to the relational database schema. Each row corresponds to one objectclass mapping. An example is shown below:

  ldap_oc_mappings
  ---------------
  id=1
  name='person'
  keytbl='persons'
  keycol='id'
  ・・・

In this example, the LDAP objectclass person is mapped to the SQL table persons. The primary key for entries of this objectclass is the id column in the persons table. The backend uses this information to determine which table and column hold the primary key for a given entry.

The objectclass mapping also specifies the table and column that hold the primary key for the entity. For instance, if a person entity (which we are trying to present as "person" objectclass, resides in two tables (persons and phones), and is identified by the persons.id column (that we will call the primary key for this entity). Keytbl and keycol thus contain "persons" (name of the table), and "id" (name of the column).

ATTRIBUTE MAPPINGS

The ldap_attr_mappings table defines how LDAP attributes map to SQL queries. Here's an example:

  ldap_attr_mappings (some columns are not listed for clarity)
  -----------
  id=1
  oc_map_id=1
  name="cn"
  sel_expr="CONCAT(persons.first_name,' ',persons.last_name)"
  from_tbls="persons"
  join_where=NULL
  ************
  id=<n>
  oc_map_id=1
  name="telephoneNumber"
  sel_expr="phones.phone"
  from_tbls="persons,phones"
  join_where="phones.pers_id=persons.id"

This table defines mappings between LDAP attributes and SQL queries that load their values. Note that, unlike LDAP schema, these are not attribute types - the attribute "cn" for "person" objectclass can have its values in different tables than "cn" for some other objectclass, so attribute mappings depend on objectclass mappings (unlike attribute types in LDAP schema, which are indifferent to objectclasses). Thus, we have oc_map_id column with link to oc_mappings table.

Now we cut the SQL query that loads values for a given attribute into 3 parts. First goes into sel_expr column - this is the expression we had between SELECT and FROM keywords, which defines WHAT to load. Next is table list - text between FROM and WHERE keywords. It may contain aliases for convenience (see examples). The last is part of the where clause, which (if it exists at all) expresses the condition for joining the table containing values with the table containing the primary key (foreign key equality and such). If values are in the same table as the primary key, then this column is left NULL (as for cn attribute above).

Having this information in parts, we are able to not only construct queries that load attribute values by id of entry (for this we could store SQL query as a whole), but to construct queries that load id's of objects that correspond to a given search filter (or at least part of it). See below for examples.

ENTRY MAPPINGS

The ldap_entries table maps Distinguished Names (DNs) to the primary keys of corresponding relational data.

  ldap_entries
  ------------
  id=1
  dn=<dn you choose>
  oc_map_id=...
  parent=<parent record id>
  keyval=<value of primary key>

This table defines mappings between DNs of entries in your LDAP tree, and values of primary keys for corresponding relational data. It has recursive structure (parent column references id column of the same table), which allows you to add any tree structure(s) to your flat relational data. Having id of objectclass mapping, we can determine table and column for primary key, and keyval stores value of it, thus defining the exact tuple corresponding to the LDAP entry with this DN.

Note that such design (see exact SQL table creation query) implies one important constraint - the key must be an integer. But all that I know about well-designed schemas makes me think that it's not very narrow ;) If anyone needs support for different types for keys - he may want to write a patch, and submit it to OpenLDAP ITS, then I'll include it.

Also, several users complained that they don't really need very structured trees, and they don't want to update one more table every time they add or delete an instance in the relational schema. Those people can use a view instead of a real table for ldap_entries, something like this (by Robin Elfrink):

  CREATE VIEW ldap_entries (id, dn, oc_map_id, parent, keyval)
      AS
          SELECT 0, UPPER('o=MyCompany,c=NL'),
              3, 0, 'baseObject' FROM unixusers WHERE userid='root'
      UNION
          SELECT (1000000000+userid),
              UPPER(CONCAT(CONCAT('cn=',gecos),',o=MyCompany,c=NL')),
              1, 0, userid FROM unixusers
      UNION
          SELECT (2000000000+groupnummer),
              UPPER(CONCAT(CONCAT('cn=',groupname),',o=MyCompany,c=NL')),
              2, 0, groupnummer FROM groups;

If your RDBMS does not support unions in views, only one objectClass can be mapped in ldap_entries, and the baseObject cannot be created; in this case, see the baseObject directive for a possible workaround.

TYPICAL SQL BACKEND OPERATION

Having meta-information loaded, the SQL backend uses these tables to determine a set of primary keys of candidates (depending on search scope and filter). It tries to do it for each objectclass registered in ldap_objclasses.

Example: for our query with filter (telephoneNumber=123*) we would get the following query generated (which loads candidate IDs)

  SELECT ldap_entries.id,persons.id, 'person' AS objectClass,
         ldap_entries.dn AS dn
    FROM ldap_entries,persons,phones
   WHERE persons.id=ldap_entries.keyval
     AND ldap_entries.objclass=?
     AND ldap_entries.parent=?
     AND phones.pers_id=persons.id
     AND (phones.phone LIKE '%1%2%3%')

(for ONELEVEL search) or "... AND dn=?" (for BASE search) or "... AND dn LIKE '%?'" (for SUBTREE)

Then, for each candidate, we load the requested attributes using per-attribute queries like

  SELECT phones.phone AS telephoneNumber
    FROM persons,phones
   WHERE persons.id=? AND phones.pers_id=persons.id

Then, we use test_filter() from the frontend API to test the entry for a full LDAP search filter match (since we cannot effectively make sense of SYNTAX of corresponding LDAP schema attribute, we translate the filter into the most relaxed SQL condition to filter candidates), and send it to the user.

ADD, DELETE, MODIFY and MODRDN operations are also performed on per-attribute meta-information (add_proc etc.). In those fields one can specify an SQL statement or stored procedure call which can add, or delete given values of a given attribute, using the given entry keyval (see examples -- mostly PostgreSQL, ORACLE and MSSQL - since as of this writing there are no stored procs in MySQL).

We just add more columns to ldap_oc_mappings and ldap_attr_mappings, holding statements to execute (like create_proc, add_proc, del_proc etc.), and flags governing the order of parameters passed to those statements. Please see samples to find out what are the parameters passed, and other information on this matter - they are self-explanatory for those familiar with the concepts expressed above.

COMMON TECHNIQUES

First of all, let's recall that among other major differences to the complete LDAP data model, the above illustrated concept does not directly support such features as multiple objectclasses per entry, and referrals. Fortunately, they are easy to adopt in this scheme. The SQL backend requires that one more table is added to the schema: ldap_entry_objectclasses(entry_id,oc_name).

That table contains any number of objectclass names that corresponding entries will possess, in addition to that mentioned in mapping. The SQL backend automatically adds attribute mapping for the "objectclass" attribute to each objectclass mapping that loads values from this table. So, you may, for instance, have a mapping for inetOrgPerson, and use it for queries for "person" objectclass...

Referrals used to be implemented in a loose manner by adding an extra table that allowed any entry to host a "ref" attribute, along with a "referral" extra objectClass in table ldap_entry_objclasses. In the current implementation, referrals are treated like any other user-defined schema, since "referral" is a structural objectclass. The suggested practice is to define a "referral" entry in ldap_oc_mappings, holding a naming attribute, e.g. "ou" or "cn", a "ref" attribute, containing the url; in case multiple referrals per entry are needed, a separate table for urls can be created, where urls are mapped to the respective entries. The use of the naming attribute usually requires to add an "extensibleObject" value to ldap_entry_objclasses.

CAVEATS

As previously stated, this backend should not be considered a replacement of other data storage backends, but rather a gateway to existing RDBMS storages that need to be published in LDAP form.

The hasSubordinates operational attribute is honored by back-sql in search results and in compare operations; it is partially honored also in filtering. Owing to design limitations, a (brain-dead?) filter of the form (!(hasSubordinates=TRUE)) will give no results instead of returning all the leaf entries, because it actually expands into ... AND NOT (1=1). If you need to find all the leaf entries, please use (hasSubordinates=FALSE) instead.

A directoryString value of the form "__First___Last_" (where underscores mean spaces, ASCII 0x20 char) corresponds to its prettified counterpart "First_Last"; this is not currently honored by back-sql if non-prettified data is written via RDBMS; when non-prettified data is written through back-sql, the prettified values are actually used instead.

BUGS

When the ldap_entry_objclasses table is empty, filters on the objectClass attribute erroneously result in no candidates. A workaround consists in adding at least one row to that table, no matter if valid or not.

PROXY CACHE OVERLAY

The proxy cache overlay allows caching of LDAP search requests (queries) in a local database. See slapo-pcache(5) for details.

EXAMPLES

There are example SQL modules in the slapd/back-sql/rdbms_depend/ directory in the OpenLDAP source tree.

ACCESS CONTROL

The sql backend honors access control semantics as indicated in slapd.access(5) (including the disclose access privilege when enabled at compile time).
