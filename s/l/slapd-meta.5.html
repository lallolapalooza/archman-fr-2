NOM

slapd-meta - backend métadirectoire pour slapd

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

Le backend meta de slapd(8) effectue des opérations de proxy LDAP de base par rapport à un ensemble de serveurs LDAP distants, appelés "cibles". Les informations contenues dans ces serveurs peuvent être présentées comme appartenant à un seul Arbre d'Information des Répertoires (DIT).

Une connaissance de base du fonctionnement du backend slapd-ldap(5) est recommandée. Ce backend a été conçu comme une amélioration du backend ldap. Les deux backends partagent de nombreuses fonctionnalités (en fait, ils partagent également des portions de code). Alors que le backend ldap est destiné à proxifier les opérations dirigées vers un serveur unique, le backend meta est principalement destiné au proxy de plusieurs serveurs et éventuellement à la mise en masquerade de contextes de nommage. Ces fonctionnalités, bien qu'utiles dans de nombreux scénarios, peuvent entraîner une surcharge excessive pour certaines applications, leur utilisation doit donc être soigneusement étudiée. Dans la section exemples, certains scénarios typiques seront discutés.

L'instance proxy de slapd(8) doit contenir les informations de schéma pour les attributs et les objectClasses utilisés dans les filtres, le DN de la requête et les données relatives à la requête en général. Elle doit également contenir les informations de schéma pour les données renvoyées par le serveur proxifié. Il incombe à l'administrateur du proxy de maintenir le schéma du proxy en phase avec celui du serveur proxifié.

Remarque : Lors de boucles retournant vers la même instance de slapd(8), chaque connexion nécessite un nouveau thread ; par conséquent, le paramètre threads de slapd(8) peut nécessiter un ajustement. Dans ces cas, à moins que la fonctionnalité de cibles multiples ne soit requise, on peut envisager d'utiliser plutôt slapd-relay(5), qui effectue l'opération relaisée en interne et réutilise ainsi la même connexion.

EXEMPLES

Il y a des exemples à divers endroits de ce document, ainsi que dans le répertoire slapd/back-meta/data/ de l'arbre source d'OpenLDAP.

CONFIGURATION

Ces options slapd.conf s'appliquent à la base de données du backend META. C'est-à-dire qu'elles doivent suivre une ligne "database meta" et précéder toute ligne "backend" ou "database" ultérieure. Les autres options de base de données sont décrites dans la page du manuel slapd.conf(5).

Remarque : Dans les premières versions des backends ldap et meta, il était recommandé de toujours définir

lastmod  off

pour les bases de données ldap et meta. Ceci était nécessaire car les attributs opérationnels liés à la création et à la modification des entrées ne devaient pas être proxifiés, car ils pouvaient être écrits par erreur sur le(s) serveur(s) cible(s), générant une erreur. L'implémentation actuelle définit automatiquement lastmod à off, donc son utilisation est redondante et doit être omise.

DIRECTIVES DE CONFIGURATION SPÉCIALES

La configuration de la cible commence par la directive "uri". Toutes les directives de configuration qui ne sont pas spécifiques aux cibles doivent être définies en premier pour plus de clarté, y compris celles qui sont communes à tous les backends. Elles sont :

conn-pool-max <int>
Cette directive définit la taille maximale du pool de connexions privilégiées.
conn-ttl <temps>
Cette directive provoque la fermeture et la recréation d'une connexion mise en cache après une durée de vie donnée, qu'elle soit inactive ou non.
default-target none
Cette directive force le backend à rejeter toutes les opérations qui doivent se résoudre en une seule cible si aucune ou plusieurs cibles sont sélectionnées. Elles incluent : add, delete, modify, modrdn ; compare n'est pas inclus, tout comme bind car, comme elles n'altèrent pas les entrées, en cas de multiples correspondances, une tentative est faite pour effectuer l'opération sur n'importe quelle cible candidate, avec la contrainte qu'au plus une doit réussir. Cette directive peut également être utilisée lors du traitement des cibles pour marquer une cible spécifique comme étant par défaut.
dncache-ttl {DÉSACTIVÉ|forever|<ttl>}
Cette directive définit la durée de vie du cache DN. Ce cache enregistre la cible qui contient un DN donné pour accélérer la sélection de la cible en cas de multiples cibles résultant d'une recherche non mise en cache ; forever signifie que le cache n'expire jamais ; désactivé signifie aucun cache DN ; sinon, une durée de vie valide ( > 0 ) est requise, dans le format illustré pour la directive idle-timeout.
onerr {CONTINUE|report|stop}
Cette directive permet de sélectionner le comportement en cas d'erreur retournée par une cible lors d'une recherche. Le comportement par défaut, continue, consiste à poursuivre l'opération, en essayant de renvoyer autant de données que possible. Si la valeur est définie sur stop, la recherche est terminée dès qu'une erreur est retournée par une cible, et l'erreur est immédiatement propagée au client. Si la valeur est définie sur report, la recherche continue jusqu'à la fin mais, si au moins une cible a retourné un code d'erreur, le premier code d'erreur non succès est renvoyé.
norefs <NON|oui>
Si oui, ne pas renvoyer de réponses de référence de recherche. Par défaut, elles sont renvoyées sauf si la requête est LDAPv2. Si définie avant toute spécification de cible, elle affecte toutes les cibles, sauf si elle est remplacée par une directive par cible.
noundeffilter <NON|oui>
Si oui, renvoyer succès au lieu de rechercher si un filtre est indéfini ou contient des parties indéfinies. Par défaut, la recherche est propagée après le remplacement des parties indéfinies par (!(objectClass=*)), ce qui correspond à l'ensemble de résultats vide. Si défini avant toute spécification de cible, il affecte toutes les cibles, sauf si remplacé par une directive par cible.
protocol-version {0,2,3}
Cette directive indique quel version du protocole doit être utilisée pour contacter le serveur distant. Si définie à 0 (par défaut), le proxy utilise la même version du protocole que celle utilisée par le client, sinon la version demandée est utilisée. Le proxy renvoie unwillingToPerform si une opération incompatible avec la version du protocole demandée est tentée. Si définie avant toute spécification de cible, elle affecte toutes les cibles, sauf si remplacée par une directive par cible.
pseudoroot-bind-defer {OUI|non}
Cette directive, lorsqu'elle est définie sur oui, fait en sorte que l'authentification aux serveurs distants avec l'identité pseudo-racine (l'identité définie dans chaque directive idassert-bind) soit différée jusqu'à ce qu'elle soit réellement nécessaire par les opérations ultérieures. Sinon, toutes les liaisons en tant que rootdn sont propagées aux cibles.
quarantine <intervalle>,<nb>[;<intervalle>,<nb>[...]]
Active la quarantaine des URIs qui ont retourné LDAP_UNAVAILABLE, de sorte qu'une tentative de reconnexion ne se produise qu'à des intervalles donnés au lieu de chaque fois qu'un client demande une opération. Le modèle est le suivant : réessayer uniquement après qu'au moins intervalle secondes se soient écoulées depuis la dernière tentative, pour exactement nb fois ; ensuite, utiliser le modèle suivant. Si nb pour le dernier modèle est "+", il réessaie indéfiniment ; sinon, plus aucune réessai ne se produit. Cette directive doit apparaître avant toute spécification de cible ; elle affecte toutes les cibles avec le même modèle.
rebind-as-user <NON|oui>
Si cette option est donnée, les identifiants de liaison du client sont mémorisés pour les re-liaisons, lors de la tentative de rétablissement d'une connexion rompue, ou lors du suivi d'une référence, si chase-referrals est défini sur oui.
session-tracking-request <NON|oui>
Ajoute un contrôle de suivi de session pour toutes les requêtes. L'adresse IP et le nom d'hôte du client, ainsi que l'identité associée à chaque requête,
si connus, sont envoyés au serveur distant à des fins d'information. Cette directive est incompatible avec le réglage de protocol-version sur 2. Si elle est définie avant toute spécification de cible, elle affecte toutes les cibles, sauf si elle est remplacée par une directive par cible.
single-conn {NON|oui}
Écarte la connexion mise en cache actuelle lorsque le client se reconnecte.
use-temporary-conn {NON|oui}
lorsqu'il est défini sur oui, crée une connexion temporaire lors de la compétition avec d'autres threads pour une connexion partagée ; sinon, attend que la connexion partagée soit disponible.

SPÉCIFICATION DE CIBLE

La spécification de cible commence par une directive "uri" :

uri <protocole>://[<hôte>]/<contexte de nommage> [...]
La partie <protocole> peut être tout ce que ldap_initialize(3) accepte ({ldap|ldaps|ldapi} et variantes) ; l'<hôte> peut être omis, en utilisant par défaut ce qui est défini dans ldap.conf(5). La partie <contexte de nommage> est obligatoire pour la première URI, mais elle doit être omise pour les suivantes, s'il y en a. La partie contexte de nommage doit être comprise dans le contexte de nommage défini pour le backend, par exemple :
suffix "dc=foo,dc=com"
uri    "ldap://x.foo.com/dc=x,dc=foo,dc=com"
La partie <contexte de nommage> n'a pas besoin d'être unique parmi les cibles ; elle peut également correspondre à l'une des valeurs de la directive "suffix". Plusieurs URI peuvent être définies dans une seule déclaration URI. Les URI supplémentaires doivent être des arguments distincts et ne doivent pas avoir de partie <contexte de nommage>. Cela amène la bibliothèque sous-jacente à contacter le premier serveur de la liste qui répond. Par exemple, si l1.foo.com et l2.foo.com sont des ombres du même serveur, la directive 
suffix "dc=foo,dc=com"
uri    "ldap://l1.foo.com/dc=foo,dc=com" "ldap://l2.foo.com/"
amène l2.foo.com à être contacté chaque fois que l1.foo.com ne répond pas. Dans ce cas, la liste des URI est réorganisée en interne, en déplaçant les URI indisponibles à la fin, de sorte que les tentatives de connexion ultérieures se produisent par rapport à la dernière URI qui a réussi.
acl-authcDN <DN administratif à des fins de contrôle d'accès>
DN utilisé pour interroger le serveur cible pour la vérification des ACL, comme dans le backend LDAP ; il est censé avoir un accès en lecture sur le serveur cible aux attributs utilisés sur le proxy pour la vérification des ACL. Il n'y a aucun risque de divulguer de telles valeurs ; elles sont uniquement utilisées pour vérifier les permissions. L'identité acl-authcDN n'est en aucun cas implicitement utilisée par le proxy lorsque le client se connecte anonymement.
acl-passwd <mot de passe>
Mot de passe utilisé avec l'acl-authcDN ci-dessus.
bind-timeout <microsecondes>
Cette directive définit le délai d'attente, en microsecondes, utilisé lors de l'interrogation de la réponse après une connexion bind asynchrone. L'appel initial à ldap_result(3) est effectué avec un délai d'attente d'échange de 100000 us ; si cela entraîne un dépassement du délai d'attente, les appels ultérieurs utilisent la valeur fournie avec bind-timeout. La valeur par défaut est également utilisée pour les appels ultérieurs si bind-timeout n'est pas spécifié. Si elle est définie avant toute spécification de cible, elle affecte toutes les cibles, sauf si elle est remplacée par une directive par cible.
chase-referrals {OUI|non}
active/désactive le suivi des renvois automatique, qui est délégué à la bibliothèque libldap sous-jacente, avec une re-liaison effectuée éventuellement si la directive rebind-as-user est utilisée. Par défaut, les renvois sont suivis. Si elle est définie avant toute spécification de cible, elle affecte toutes les cibles, sauf si elle est remplacée par une directive par cible.
client-pr {accept-unsolicited|DESACTIVE|<taille>}
Cette fonctionnalité permet d'utiliser le contrôle des résultats paginés RFC 2696 lors de l'exécution d'opérations de recherche avec une cible spécifique, quelle que soit la demande du client. Lorsqu'elle est définie sur une valeur numérique, le contrôle des résultats paginés est toujours utilisé avec taille comme taille de page. Lorsqu'elle est définie sur accept-unsolicited, les réponses non sollicitées du contrôle des résultats paginés sont acceptées et honorées pour la compatibilité avec les DSA distants défectueux. Le client n'est pas exposé à la gestion des résultats paginés entre slapd-meta(5) et les serveurs distants. Par défaut (désactivé), le contrôle des résultats paginés n'est pas utilisé et les réponses ne sont pas acceptées. Si elle est définie avant toute spécification de cible, elle affecte toutes les cibles, sauf si elle est remplacée par une directive par cible.
default-target [<cible>]
La directive "default-target" peut également être utilisée lors de la spécification de cible. Sans arguments, elle marque la cible actuelle comme étant la cible par défaut. Le numéro optionnel marque la cible <cible> comme étant la cible par défaut, à partir de 1. La cible <cible> doit être définie.
filter <motif>
Cette directive permet de spécifier un motif regex(5) pour indiquer quels termes de filtre de recherche sont réellement servis par une cible.

Dans une requête de recherche, si le filtre de recherche correspond au motif, la cible est prise en compte lors de la satisfaction de la requête ; sinon, la cible est ignorée. Il peut y avoir plusieurs occurrences de la directive filter pour chaque cible.

idassert-authzFrom <authz-regexp>
si elle est définie, sélectionne quelles identités locales sont autorisées à exploiter la fonctionnalité d'assertion d'identité. La chaîne <authz-regexp> suit les règles définies pour l'attribut authzFrom. Voir slapd.conf(5), section relative à authz-policy, pour les détails sur la syntaxe de ce champ.

idassert-bind bindmethod=none|simple|sasl [binddn=<DN simple>] [credentials=<mot de passe simple>] [saslmech=<mécanisme SASL>] [secprops=<propriétés>] [realm=<domaine>] [authcId=<identifiant d'authentification>] [authzId=<identifiant d'autorisation>] [authz={native|proxyauthz}] [mode=<mode>] [flags=<indicateurs>] [starttls=non|oui|critique] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<chiffrements>] [tls_ecname=<courbes elliptiques>] [tls_protocol_min=<majeur>[.<mineur>]] [tls_crlcheck=none|peer|all]

Permet de définir les paramètres de la méthode d'authentification qui est utilisée en interne par le proxy pour autoriser les connexions authentifiées par d'autres bases de données. L'identité définie par cette directive, selon les propriétés associées à la méthode d'authentification, est censée avoir un accès d'authentification sur le serveur cible aux attributs utilisés sur le proxy pour l'authentification et l'autorisation, et être autorisée à autoriser les utilisateurs. Cela nécessite d'avoir des privilèges proxyAuthz sur un large ensemble de DN, par exemple authzTo=dn.subtree:"", et que le serveur distant ait authz-policy défini sur to ou both. Voir slapd.conf(5) pour les détails sur ces déclarations et pour les remarques et inconvénients concernant leur utilisation. Les méthodes de liaison prises en charge sont

none|simple|sasl

où none est la valeur par défaut, c'est-à-dire qu'aucune assertion d'identité n'est effectuée.

Le paramètre authz est utilisé pour indiquer à la liaison SASL d'exploiter l'autorisation SASL native, si disponible ; comme les connexions sont mises en cache, cela ne doit être utilisé que lors de l'autorisation avec une identité fixe (par exemple, au moyen des paramètres authzDN ou authzID). Sinon, la valeur par défaut proxyauthz est utilisée, c'est-à-dire que le contrôle proxyAuthz (Proxied Authorization, RFC 4370) est ajouté à toutes les opérations.

Les modes pris en charge sont :

<mode> := {legacy|anonymous|none|self}

Si <mode> n'est pas présent et que authzId est fourni, le proxy autorise toujours cette identité. <Identifiant d'autorisation> peut être

u:<utilisateur>

[dn:]<DN>

Le premier doit être développé par le serveur distant conformément aux règles d'autorisation ; voir slapd.conf(5) pour les détails. Dans le dernier cas, que le préfixe dn: soit présent ou non, la chaîne doit passer la validation et la normalisation des DN.

Le mode par défaut est legacy, ce qui implique que le proxy effectuera soit une liaison simple en tant que authcDN, soit une liaison SASL en tant que authcID et assertira l'identité du client lorsqu'elle n'est pas anonyme. Les liaisons directes sont toujours proxysées. Les autres modes impliquent que le proxy effectuera toujours soit une liaison simple en tant que authcDN, soit une liaison SASL en tant que authcID, sauf si restreint par les règles idassert-authzFrom (voir ci-dessous), auquel cas l'opération échouera ; finalement, elle assertira une autre identité selon <mode>. Les autres modes d'assertion d'identité sont anonymous et self, qui signifient respectivement que l'identité vide ou celle du client sera assertie ; none, ce qui signifie qu'aucun contrôle proxyAuthz ne sera utilisé, donc l'identité authcDN ou authcID sera assertie. Pour tous les modes qui nécessitent l'utilisation du contrôle proxyAuthz, sur le serveur distant l'identité du proxy doit avoir les permissions authzTo appropriées, ou les identités assertées doivent avoir les permissions authzFrom appropriées. Notez cependant que la fonctionnalité d'assertion d'identité est principalement utile lorsque les identités assertées n'existent pas sur le serveur distant. Lorsque bindmethod est SASL, le authcDN doit être spécifié en plus de l'authcID, bien qu'il ne soit pas utilisé dans le processus d'authentification.

Les indicateurs peuvent être

override,[non-]prescriptive,proxy-authz-[non-]critical

Lorsque l'indicateur override est utilisé, l'assertion d'identité a lieu même lorsque la base de données autorise pour l'identité du client, c'est-à-dire qu'après s'être lié avec l'identité fournie, et donc l'avoir authentifiée, le proxy effectue l'assertion d'identité en utilisant l'identité et la méthode d'authentification configurées

od.

Lorsque l'indicateur prescriptive est utilisé (par défaut), les opérations échouent avec inappropriateAuthentication pour les identités dont l'assertion n'est pas autorisée par les motifs idassert-authzFrom. Si l'indicateur non-prescriptive est utilisé, les opérations sont effectuées anonymement pour les identités dont l'assertion n'est pas autorisée par les motifs idassert-authzFrom.

Lorsque l'indicateur proxy-authz-non-critical est utilisé (par défaut), le contrôle proxyAuthz n'est pas marqué comme critique, en violation de la RFC 4370. L'utilisation de proxy-authz-critical est recommandée.

Les paramètres TLS par défaut sont les mêmes que ceux des paramètres TLS principaux de slapd, à l'exception de tls_reqcert qui est par défaut "demand", et tls_reqsan qui est par défaut "allow"..

L'identité associée à cette directive est également utilisée pour les opérations privilégiées lorsque idassert-bind est défini et acl-bind ne l'est pas. Voir acl-bind pour plus de détails.

idle-timeout <temps>
Cette directive provoque la fermeture et la recréation d'une connexion mise en cache après qu'elle soit restée inactive pendant le temps spécifié. La valeur peut être spécifiée comme

[<j>j][<h>h][<m>m][<s>[s]]

où <j>, <h>, <m> et <s> sont respectivement traités comme des jours, heures, minutes et secondes. S'il est défini avant toute spécification de cible, il affecte toutes les cibles, sauf s'il est écrasé par une directive par cible.

keepalive <inactif>:<sondes>:<intervalle>
Le paramètre keepalive définit les valeurs de inactif, sondes et intervalle utilisées pour vérifier si une socket est vivante ; inactif est le nombre de secondes pendant lesquelles une connexion doit rester inactive avant que TCP ne commence à envoyer des sondes keepalive ; sondes est le nombre maximum de sondes keepalive que TCP doit envoyer avant de fermer la connexion ; intervalle est l'intervalle en secondes entre les sondes keepalive individuelles. Seuls certains systèmes prennent en charge la personnalisation de ces valeurs ; le paramètre keepalive est ignoré sinon, et les paramètres globaux du système sont utilisés.
tcp-user-timeout <millisecondes>
S'il est non nul, correspond au TCP_USER_TIMEOUT défini sur les connexions cibles, écrasant le paramètre du système d'exploitation. Seuls certains systèmes prennent en charge la personnalisation de ce paramètre, il est ignoré sinon et les paramètres globaux du système sont utilisés.
map {attribute|objectclass} [<nom local>|*] {<nom étranger>|*}
Ceci mappe les classes d'objets et les attributs comme dans le backend LDAP. Voir slapd-ldap(5).
network-timeout <temps>
Définit la valeur du délai d'attente réseau après lequel poll(2)/select(2) après un connect(2) retourne en cas d'absence d'activité. La valeur est en secondes, et elle peut être spécifiée comme pour idle-timeout. Si elle est définie avant toute spécification de cible, elle affecte toutes les cibles, sauf si elle est écrasée par une directive par cible.
nretries {forever|never|<nretries>}
Cette directive définit le nombre de fois qu'une liaison doit être retentée en cas d'échec temporaire lors de la prise de contact avec une cible. Si elle est définie avant toute spécification de cible, elle s'applique à toutes les cibles (par défaut, 3 fois) ; la valeur globale peut être écrasée par des redéfinitions à l'intérieur de chaque spécification de cible.
rewrite* ...
Les options de réécriture sont décrites dans la section "REWRITING".
subtree-{exclude|include} <règle>
Cette directive permet d'indiquer quels sous-arbres sont effectivement servis par une cible. La syntaxe des règles prises en charge est

<règle>: [dn[.<style>]:]<motif>

<style>: subtree|children|regex

Lorsque <style> est soit subtree soit children, le <motif> est un DN qui doit être dans le contexte de nommage servi par la cible. Lorsque <style> est regex, le <motif> est un motif regex(5). Si le préfixe dn.<style>: est omis, dn.subtree: est implicitement supposé pour des raisons de compatibilité ascendante.

Dans la forme subtree-exclude, si le DN de la requête correspond à au moins une règle, la cible n'est pas prise en compte lors du traitement de la requête ; sinon, la cible est prise en compte en fonction de la valeur du DN de la requête. Lorsque la requête est une recherche, la portée est également prise en compte.

Dans la forme subtree-include, si le DN de la requête correspond à au moins une règle, la cible est prise en compte lors du traitement de la requête ; sinon, la cible est ignorée.

    |  correspondance  | exclure |
    +------------------+---------+-------------------+
    |        OUI       |   OUI   | pas candidat     |
    |        NON       |   OUI   | continuer la vérif |
    +------------------+---------+-------------------+
    |        OUI       |   NON   | candidat         |
    |        NON       |   NON   | pas candidat     |
    +------------------+---------+-------------------+
Il peut y avoir plusieurs occurrences de la directive subtree-exclude ou subtree-include pour chacune des cibles, mais elles sont mutuellement exclusives.
suffixmassage <contexte de nommage virtuel> <contexte de nommage réel>
Toutes les directives commençant par "rewrite" font référence au moteur de réécriture qui a été ajouté à slapd. La directive "suffixmassage" a été introduite dans le backend LDAP pour permettre le massage de suffixes lors du proxy. Elle a été obsolète par les outils de réécriture. Cependant, à la fois pour des raisons de compatibilité ascendante et pour faciliter la configuration lorsqu'un massage de suffixe simple est requis, elle a été conservée. Elle encapsule les instructions de réécriture de base qui effectuent le massage de suffixes. Voir la section "REWRITING" pour une liste détaillée des règles de réécriture qu'elle implique.
t-f-support {NO|yes|discover}
activer si le serveur distant prend en charge les filtres absolus (voir RFC 4526 pour plus de détails). S'il est défini sur discover, le support est détecté en lisant le DSE racine du serveur distant. S'il est défini avant toute spécification de cible, il affecte toutes les cibles, sauf s'il est écrasé par une directive par cible.
timeout [<op>=]<val> [...]
Cette directive permet de définir des délais d'attente par opération. Les opérations peuvent être

<op> ::= bind, add, delete, modrdn, modify, compare, search

La durée totale de l'opération search est contrôlée soit par le paramètre timelimit, soit par des limites de temps appliquées côté serveur (voir timelimit et limits dans slapd.conf(5) pour plus de détails). Ce paramètre timeout contrôle combien de temps la cible peut être sans réponse avant que l'opération ne soit interrompue. Le délai d'attente est dénué de sens pour les opérations restantes, unbind et abandon, qui n'impliquent aucune réponse, tandis qu'il n'est pas encore implémenté dans les opérations extended prises en charge actuellement. Si aucune opération n'est spécifiée, le délai d'attente val affecte toutes les opérations prises en charge. S'il est spécifié avant toute définition de cible, il affecte toutes les cibles à moins d'être écrasé par des directives par cible.

Remarque : si le délai d'attente est dépassé, l'opération est annulée (conformément à la directive cancel) ; le protocole ne fournit aucun moyen de revenir en arrière sur les opérations, le client ne sera donc pas informé du résultat de l'opération, qui pourrait éventuellement réussir ou non. En cas de dépassement du délai d'attente pendant une opération bind, la connexion est détruite, conformément à la RFC4511.

tls {none|[try-]start|[try-]propagate|ldaps}
[starttls=no] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<chiffrements>] [tls_ecname=<noms>] [tls_crlcheck=none|peer|all]
Spécifie les paramètres TLS pour les connexions régulières.

Si le premier paramètre n'est pas "none", cela configure les paramètres TLS à utiliser pour les connexions régulières. L'opération étendue StartTLS sera utilisée lors de l'établissement de la connexion, sauf si le schéma de protocole de la directive URI est ldaps://. Dans ce cas, ce mot-clé ne peut être défini que sur "ldaps" et l'opération StartTLS ne sera pas utilisée.

Avec propagate, le proxy émet l'opération StartTLS uniquement si la connexion d'origine dispose d'une couche TLS configurée. Le préfixe try- demande au proxy de continuer les opérations si l'opération StartTLS a échoué ; son utilisation n'est pas recommandée.

Les paramètres TLS par défaut sont les mêmes que ceux des paramètres TLS principaux de slapd, à l'exception de tls_reqcert qui est par défaut "demand", tls_reqsan qui est par défaut "allow", et starttls qui est éclipsé par le premier mot-clé et donc ignoré.

S'il est défini avant toute spécification de cible, il affecte toutes les cibles, sauf s'il est écrasé par une directive par cible.

SCÉNARIOS

Un moteur de réécriture puissant (et dans un sens dangereux) a été ajouté aux backends LDAP et Meta. Tandis que le premier peut tirer des effets bénéfiques limités de la réécriture, le second peut devenir un outil incroyablement puissant.

Considérons d'abord quelques scénarios.

1) Deux serveurs d'annuaire partagent deux niveaux de contexte de nommage ; par exemple "dc=a,dc=foo,dc=com" et "dc=b,dc=foo,dc=com". Alors, une base de données Meta sans ambiguïté peut être configurée comme suit :

database meta
suffix   "dc=foo,dc=com"
uri      "ldap://a.foo.com/dc=a,dc=foo,dc=com"
uri      "ldap://b.foo.com/dc=b,dc=foo,dc=com"

Les opérations dirigées vers une cible spécifique peuvent être facilement résolues car il n'y a pas d'ambiguïtés. La seule opération qui peut aboutir à plusieurs cibles est une recherche avec la base "dc=foo,dc=com" et

scope au moins "un", ce qui entraîne le lancement de deux recherches vers les cibles.

2a) Deux serveurs de répertoires ne partagent aucune partie du contexte de nommage, mais ils apparaissent comme un seul DIT [Caveat : l'unicité des entrées (lissées) entre les deux serveurs est supposée ; les vérifications d'intégrité risquent d'entraîner une surcharge excessive et n'ont pas été implémentées]. Supposons que nous ayons "dc=bar,dc=org" et "o=Foo,c=US", et que nous souhaitions qu'ils apparaissent comme des branches de "dc=foo,dc=com", par exemple "dc=a,dc=foo,dc=com" et "dc=b,dc=foo,dc=com". Nous devons alors configurer notre backend Meta comme suit :

database      meta
suffix        "dc=foo,dc=com"
uri           "ldap://a.bar.com/dc=a,dc=foo,dc=com"
suffixmassage "dc=a,dc=foo,dc=com" "dc=bar,dc=org"
uri           "ldap://b.foo.com/dc=b,dc=foo,dc=com"
suffixmassage "dc=b,dc=foo,dc=com" "o=Foo,c=US"

Encore une fois, les opérations peuvent être résolues sans ambiguïté, bien que certaines réécritures soient nécessaires. Notez que le contexte de nommage virtuel de chaque cible est une branche du contexte de nommage de la base de données ; il est réécrit dans les deux sens lors des opérations effectuées vers les serveurs cibles. Ce que signifie "dans les deux sens" sera clarifié plus tard.

Lorsqu'une recherche avec la base "dc=foo,dc=com" est tentée, si la portée est "base", elle échoue avec "aucun objet de ce type" ; en fait, la racine commune des deux cibles (avant lissage) n'existe pas. Si la portée est "one", les deux cibles sont contactées avec la base remplacée par la base de chaque cible ; la portée est réduite à "base". En général, une recherche avec la portée "one" est honorée, et la portée est réduite, uniquement lorsque la base entrante est au plus un niveau inférieur au contexte de nommage d'une cible (avant lissage).

Enfin, si la portée est "sub", la base entrante est remplacée par le contexte de nommage non lissé de chaque cible, et la portée n'est pas modifiée.

2b) Considérons le scénario rapporté ci-dessus avec les deux serveurs partageant le même contexte de nommage :

database      meta
suffix        "dc=foo,dc=com"
uri           "ldap://a.bar.com/dc=foo,dc=com"
suffixmassage "dc=foo,dc=com" "dc=bar,dc=org"
uri           "ldap://b.foo.com/dc=foo,dc=com"
suffixmassage "dc=foo,dc=com" "o=Foo,c=US"

Toutes les considérations précédentes tiennent, sauf qu'il n'y a plus moyen de résoudre un DN sans ambiguïté. Dans ce cas, toutes les opérations qui nécessitent une sélection de cible sans ambiguïté échoueront à moins que le DN ne soit déjà mis en cache ou qu'une cible par défaut n'ait été définie. Les configurations pratiques peuvent résulter d'une combinaison de tous les scénarios ci-dessus.

ACLs

Note sur les ACL : actuellement, vous pouvez ajouter toute règle d'ACL que vous désirez aux backends Meta (et LDAP). Cependant, la signification d'une ACL sur un proxy peut nécessiter certaines considérations. Deux philosophies peuvent être envisagées :

a) le serveur distant dicte les permissions ; le proxy renvoie simplement ce qu'il reçoit du serveur distant.

b) le serveur distant dévoile "tout" ; le proxy est responsable de la protection des données contre les accès non autorisés.

Bien sûr, cette dernière option semble déraisonnable, mais elle ne l'est pas. Il est possible d'imaginer des scénarios dans lesquels un hôte distant divulgue des données qui peuvent être considérées comme "publiques" au sein d'un intranet, et un proxy qui le connecte à Internet peut imposer des contraintes supplémentaires. À cette fin, le proxy doit être capable de se conformer à tous les critères de correspondance ACL que le serveur prend en charge. Cela a été réalisé en ce qui concerne tous les critères pris en charge par slapd, à l'exception d'un cas spécial subtil (veuillez soumettre un ITS si vous trouvez d'autres exceptions : http://www.openldap.org/its/). La règle

access to dn="<dn>" attrs=<attr>
       by dnattr=<dnattr> read
       by * none

ne peut pas être satisfaite si l'attribut demandé, <attr>, N'EST PAS <dnattr>, et que l'attribut qui détermine l'appartenance, <dnattr>, n'a pas été demandé (par exemple, dans une recherche)

En fait, cette ACL est résolue par slapd en utilisant la partie de l'entrée qu'il a récupérée du serveur distant sans nécessiter d'intervention supplémentaire du backend. Ainsi, si l'attribut <dnattr> n'a pas été récupéré, la correspondance ne peut pas être évaluée car l'attribut n'est pas présent, et non pas parce qu'aucune valeur ne correspond à l'exigence !

Note sur les ACL et le mappage d'attributs : les ACL sont appliquées aux attributs mappés ; par exemple, si l'attribut connu localement sous le nom de "foo" est mappé à "bar" sur un serveur distant, alors les ACL locales s'appliquent à l'attribut "foo" et ignorent totalement son nom distant. Le serveur distant vérifiera les permissions pour "bar", et le serveur local imposera éventuellement des restrictions supplémentaires à "foo".

REWRITING

Une chaîne est réécrite selon un ensemble de règles, appelé un `contexte de réécriture'. Les règles sont basées sur des expressions régulières POSIX (''étendues'') avec correspondance de sous-chaînes ; la substitution de variables de base et la résolution de cartes de sous-chaînes sont autorisées par des mécanismes spécifiques détaillés ci-dessous. Le comportement de la correspondance/substitution de motifs peut être modifié par un ensemble d'indicateurs.

Le concept sous-jacent est de construire un module de réécriture léger pour le serveur slapd (initialement dédié au backend LDAP).

Passes

Une chaîne entrante est mise en correspondance avec un ensemble de règles. Les règles sont composées d'un motif de correspondance regex, d'un motif de substitution et d'un ensemble d'actions, décrits par un ensemble d'indicateurs. En cas de correspondance, une réécriture de chaîne est effectuée selon le motif de substitution qui permet de faire référence aux sous-chaînes trouvées dans la chaîne entrante. Les actions, le cas échéant, sont finalement effectuées. Le motif de substitution permet la résolution de cartes de sous-chaînes. Une carte est un objet générique qui associe un motif de substitution à une valeur. Les indicateurs sont divisés en "Indicateurs de correspondance de motif" et "Indicateurs d'action" ; les premiers modifient le comportement du motif regex, tandis que les seconds modifient l'action entreprise après la substitution.

Indicateurs de Correspondance de Motif

`C'
respecte la casse dans la correspondance (par défaut, insensible à la casse)
`R'
utilise les expressions régulières POSIX ''de base'' (par défaut, ''étendues'')
`M{n}'
autorise au plus n passes récursives pour une règle spécifique ; ne modifie pas le nombre total maximal de passes, donc il ne peut qu'appliquer une limite plus stricte pour une règle spécifique.

Indicateurs d'Action

`:'
applique la règle une seule fois (par défaut, récursif)
`@'
arrête l'application des règles en cas de correspondance ; la règle actuelle est toujours appliquée récursivement ; combiner avec `:' pour appliquer la règle actuelle une seule fois puis s'arrêter.
`#'
arrête l'opération en cours si la règle correspond, et génère une erreur "non disposé à effectuer".
`G{n}'
saute n règles en arrière et en avant (attention aux boucles !). Notez que `G{1}' est implicite dans chaque règle.
`I'
ignore les erreurs dans la règle ; cela signifie qu'en cas d'erreur, par exemple générée par une carte, l'erreur est traitée comme une correspondance manquée. L'état "non disposé à effectuer" n'est pas remplacé.
`U{n}'
utilise n comme code de retour si la règle correspond ; l'indicateur ne modifie pas le comportement récursif de la règle, donc, pour qu'elle soit effectuée une seule fois, elle doit être utilisée en combinaison avec `:', par exemple `:U{16}' renvoie la valeur `16' après exactement une exécution de la règle, si le motif correspond. Par conséquent, son comportement est équivalent à `@', avec le code de retour défini à n ; ou, en d'autres termes, `@' est équivalent à `U{0}'. Par convention, les codes disponibles librement sont supérieurs ou égaux à 16 ; les autres sont réservés.

L'ordre des indicateurs peut être significatif. Par exemple : `IG{2}' signifie ignorer les erreurs et sauter deux lignes en avant à la fois en cas de correspondance et en cas d'erreur, tandis que `G{2}I' signifie ignorer les erreurs, mais sauter deux lignes en avant uniquement en cas de correspondance.

D'autres indicateurs (principalement des Indicateurs d'Action) seront ajoutés si nécessaire.

Correspondance de Motif :

Voir regex(7) et/ou re_format(7).

Syntaxe du Motif de Substitution :

Tout ce qui commence par `%' nécessite une substitution ;

la seule exception évidente est `%%', qui est laissée telle quelle ;

la substitution de base est `%d', où `d' est un chiffre ; 0 signifie la chaîne entière, tandis que 1-9 correspond à une sous-correspondance ;

un `%' suivi d'un `{' invoque une substitution avancée. Le motif est :

`%' `{' [ <op> ] <nom> `(' <substitution> `)' `}'

où <nom> doit être un nom légal pour la carte, c'est-à-dire

<nom> ::= [a-z][a-z0-9]* (insensible à la casse)
<op> ::= `>' `|' `&' `&&' `*' `**' `$'

et <substitution> doit être un motif de substitution légal, sans limite de niveau d'imbrication.

Les opérateurs sont :

>
invocation de sous-contexte ; <nom> doit être un nom de contexte de réécriture légal et déjà défini
|
invocation de commande externe ; <nom> doit faire référence à un nom de commande légal et déjà défini (NON IMPL.)
&
affectation de variable ; <nom> définit une variable dans la structure de l'opération en cours qui peut être déréférencée plus tard ; l'opérateur & affecte une variable dans la portée du contexte de réécriture ; l'opérateur && affecte une variable qui s'étend à toute la session, par exemple sa valeur peut être déréférencée plus tard par d'autres contextes de réécriture
*
déréférencement de variable ; <nom> doit faire référence à une variable définie et affectée pour l'opération en cours ; l'opérateur * déréférence une variable dont la portée est le contexte de réécriture ; l'opérateur ** déréférence une variable dont la portée est toute la session, c'est-à-dire que la valeur est transmise à travers les contextes de réécriture
$
déréférencement de paramètre ; <nom> doit faire référence à un paramètre existant ; l'idée est de rendre s
Les paramètres d'exécution définis par le système sont disponibles pour le moteur de réécriture, tels que le nom d'hôte du client, le DN de liaison le cas échéant, les paramètres constants initialisés au moment de la configuration, et ainsi de suite ; aucun paramètre n'est actuellement défini par back-ldap ou back-meta, mais les paramètres constants peuvent être définis dans le fichier de configuration en utilisant la directive rewriteParam.

L'échappement de substitution a été délégué au symbole `%' , qui est utilisé à la place de `\' dans les modèles de substitution de chaînes car `\' est déjà échappé par les routines d'analyse de bas niveau de slapd ; par conséquent, l'échappement regex nécessite deux symboles `\' , par exemple `.*\.foo\.bar' doit être écrit comme `.*\\.foo\\.bar'.

Contexte de réécriture :

Un contexte de réécriture est un ensemble de règles appliquées séquentiellement. L'idée de base est qu'une application initialise un moteur de réécriture (pensez à mod_rewrite d'Apache...) avec un ensemble de contextes de réécriture ; lorsqu'une réécriture de chaîne est nécessaire, on invoque le contexte de réécriture approprié avec la chaîne d'entrée et on obtient la chaîne nouvellement réécrite s'il n'y a pas d'erreurs.

Chaque opération de serveur de base est associée à un contexte de réécriture ; elles sont divisées en deux groupes principaux : réécriture client -> serveur et serveur -> client.

client -> serveur :

(par défaut)            si défini et aucun contexte spécifique 
                     n'est disponible
bindDN               bind
searchBase           search
searchFilter         search
searchFilterAttrDN   search
compareDN            compare
compareAttrDN        compare AVA
addDN                add
addAttrDN            add AVA
modifyDN             modify
modifyAttrDN         modify AVA
modrDN               modrdn
newSuperiorDN        modrdn
deleteDN             delete
exopPasswdDN         DN d'opération étendue de modification de mot de passe si proxy

serveur -> client :

searchResult         search (seulement si défini ; pas de défaut ;
                     agit sur les attributs DN et de syntaxe DN 
                     des résultats de recherche)
searchAttrDN         search AVA
matchedDN            toutes les opérations (seulement si applicable)

Syntaxe de configuration de base

rewriteEngine { on | off }
Si `on', la réécriture demandée est effectuée ; si `off', aucune réécriture n'a lieu (un moyen simple d'arrêter la réécriture sans trop modifier le fichier de configuration).
rewriteContext <nom du contexte> [ alias <nom du contexte alias> ]
<Nom du contexte> est le nom qui identifie le contexte, c'est-à-dire le nom utilisé par l'application pour faire référence à l'ensemble des règles qu'il contient. Il est également utilisé pour référencer des sous-contextes dans la réécriture de chaînes. Un contexte peut en aliaser un autre. Dans ce cas, le contexte alias ne contient aucune règle, et toute référence à celui-ci entraînera l'accès au contexte aliasé.
rewriteRule <modèle de correspondance regex> <modèle de substitution> [ <flags> ]
Détermine comment une chaîne peut être réécrite si un modèle est trouvé. Des exemples sont rapportés ci-dessous.

Syntaxe de configuration supplémentaire :

rewriteMap <type de map> <nom de map> [ <attributs de map> ]
Permet de définir une map qui transforme la réécriture de sous-chaînes en quelque chose d'autre. La map est référencée à l'intérieur du modèle de substitution d'une règle.
rewriteParam <nom du param> <valeur du param>
Définit une valeur avec une portée globale, qui peut être déréférencée par la commande `%'{$nomDuParam}'.
rewriteMaxPasses <nombre de passes> [<nombre de passes par règle>]
Définit le nombre maximum de passes de réécriture totales qui peuvent être effectuées en une seule opération de réécriture (pour éviter les boucles). Une valeur par défaut sûre est fixée à 100 ; notez que l'atteinte de cette limite est toujours traitée comme un succès ; l'invocation récursive des règles est simplement interrompue. Le décompte s'applique à l'opération de réécriture dans son ensemble, pas à une règle unique ; une limite facultative par règle peut être définie. Cette limite est remplacée en définissant des limites spécifiques par règle avec le flag `M{n}'.

Exemples de configuration :

# mettre à `off' pour désactiver la réécriture
rewriteEngine on
# les règles que la directive "suffixmassage" implique
rewriteEngine on
# tout flux de données du client vers le serveur faisant référence à des DN
rewriteContext default
rewriteRule "(.*)<virtualnamingcontext>$" "%1<realnamingcontext>" ":"
# règle de filtre vide
rewriteContext searchFilter
# tout flux de données du serveur vers le client
rewriteContext searchResult
rewriteRule "(.*)<realnamingcontext>$" "%1<virtualnamingcontext>" ":"
rewriteContext searchAttrDN alias searchResult
rewriteContext matchedDN alias searchResult
# Tout ce qui est défini ici va dans le contexte `default'.
# Cette règle change le contexte de nommage de tout ce qui est envoyé
# à `dc=home,dc=net' en `dc=OpenLDAP, dc=org'
rewriteRule "(.*)dc=home,[ ]?dc=net"
            "%1dc=OpenLDAP, dc=org"  ":"
# comme un DN joli/normalisé n'inclut pas d'espaces
# après les séparateurs de RDN, par exemple `,', cette règle suffit :
rewriteRule "(.*)dc=home,dc=net"
            "%1dc=OpenLDAP,dc=org"  ":"
# Démarrer un nouveau contexte (termine l'entrée du contexte précédent).
# Cette règle ajoute des blancs entre les parties du DN si absents.
rewriteContext  addBlanks
rewriteRule     "(.*),([^ ].*)" "%1, %2"
# Ceci supprime les blancs
rewriteContext  eatBlanks
rewriteRule     "(.*),[ ](.*)" "%1,%2"
# Ici, le contrôle revient au contexte de réécriture par défaut
# ; les règles sont ajoutées à celles existantes.
# tout ce qui arrive ici est pipé dans la règle `addBlanks'
rewriteContext  default
rewriteRule     ".*" "%{>addBlanks(%0)}" ":"
# Réécrire la base de recherche selon les règles `default'.
rewriteContext  searchBase alias default
# Les résultats de recherche avec un DN OpenLDAP sont réécrits avec
# le contexte de nommage `dc=home,dc=net', avec suppression des espaces.
rewriteContext  searchResult
rewriteRule     "(.*[^ ]?)[ ]?dc=OpenLDAP,[ ]?dc=org"
                "%{>eatBlanks(%1)}dc=home,dc=net"    ":"
# Se connecter avec une adresse e-mail au lieu d'un DN complet : nous avons d'abord besoin
# d'une map ldap qui transforme les attributs en DN (l'argument
# utilisé lors de l'invocation de la map est ajouté à
# l'URI et agit comme la partie filtre)
rewriteMap ldap attr2dn "ldap://host/dc=my,dc=org?dn?sub"
# Ensuite, nous devons détecter un DN composé d'une seule adresse e-mail,
# par exemple `mail=someone@example.com'; notez que la règle
# en cas de correspondance arrête la réécriture ; en cas d'erreur,
# elle est ignorée.  Dans le cas où nous mappons des contextes de nommage
# virtuels à réels, nous devons également réécrire
# les DN ordinaires, car la définition d'un contexte de réécriture bindDn
# supplante la définition par défaut.
rewriteContext bindDN
rewriteRule "^mail=[^,]+@[^,]+$" "%{attr2dn(%0)}" ":@I"
# C'est un exemple assez sophistiqué. Il masse un
# filtre de recherche si celui qui effectue la recherche a
# des privilèges administratifs.  D'abord, nous devons garder
# la trace du DN de liaison de la requête entrante, qui est
# stocké dans une variable appelée `binddn' avec une portée de session,
# et laissé en place pour permettre une liaison régulière :
rewriteContext  bindDN
rewriteRule     ".+" "%{&&binddn(%0)}%0" ":"
# Un filtre de recherche contenant `uid=' est réécrit seulement
# si un DN approprié est lié.
# Pour ce faire, dans la première règle, le DN lié est
# déréférencé, tandis que le filtre est décomposé en un
# préfixe, la valeur de l'AVA `uid=<arg>', et
# un suffixe. Un tag `<>' est ajouté au DN. 
# Si le DN fait référence à une entrée dans le sous-arbre `ou=admin', 
# le filtre est réécrit en faisant un OR de `uid=<arg>' avec
# `cn=<arg>'; sinon, il est laissé tel quel. Ceci pourrait être
# utile, par exemple, pour permettre au module auth_ldap-1.4 d'Apache
# d'authentifier les utilisateurs avec `uid' et
# `cn', mais seulement si la requête provient d'un utilisateur possible
# `cn=Web auth,ou=admin,dc=home,dc=net'.
rewriteContext searchFilter
rewriteRule "(.*\\()uid=([a-z0-9_]+)(\\).*)"
  "%{**binddn}<>%{&prefix(%1)}%{&arg(%2)}%{&suffix(%3)}"
  ":I"
rewriteRule "[^,]+,ou=admin,dc=home,dc=net"
  "%{*prefix}|(uid=%{*arg})(cn=%{*arg})%{*suffix}" ":@I"
rewriteRule ".*<>" "%{*prefix}uid=%{*arg}%{*suffix}" ":"
# Cet exemple montre comment supprimer des valeurs d'attributs indésirables de type DN
# d'un résultat de recherche ; la première règle
# correspond aux valeurs DN en dessous de "ou=People,dc=example,dc=com" ;
# en cas de correspondance, la réécriture se termine avec succès.
# La deuxième règle correspond à tout le reste et provoque
# le rejet de la valeur.
rewriteContext searchResult
rewriteRule ".*,ou=People,dc=example,dc=com" "%0" ":@"
rewriteRule ".*" "" "#"

Résolution du Proxy LDAP (une évolution possible de slapd-ldap(5)) :

Si le DN réécrit est une URI LDAP, l'opération est initiée vers l'hôte[:port] indiqué dans l'URI, s'il ne fait pas référence au serveur local. Par exemple :

  rewriteRule '^cn=root,.*' '%0'                     'G{3}'
  rewriteRule '^cn=[a-l].*' 'ldap://ldap1.my.org/%0' ':@'
  rewriteRule '^cn=[m-z].*' 'ldap://ldap2.my.org/%0' ':@'
  rewriteRule '.*'          'ldap://ldap3.my.org/%0' ':@'

(La règle 1 est simplement là pour illustrer l'action `G{n}' ; elle aurait pu être écrite :

  rewriteRule '^cn=root,.*' 'ldap://ldap3.my.org/%0' ':@'

avec l'avantage d'économiser une passe de réécriture ...)

CONTRÔLE D'ACCÈS

Le backend meta ne respecte pas toutes les sémantiques ACL telles que décrites dans slapd.access(5). En général, la vérification d'accès est déléguée aux serveurs distants. Seuls les accès en lecture (=r) au pseudo-attribut entry et aux autres valeurs d'attributs des entrées retournées par l'opération search sont honorés, ce qui est effectué par le frontend.

SUPERPOSITION DE CACHE PROXY

La superposition de cache proxy permet la mise en cache des requêtes de recherche LDAP (requêtes) dans une base de données locale. Voir slapo-pcache(5) pour plus de détails.

Utilisez idassert-bind à la place.
