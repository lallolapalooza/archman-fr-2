SLAPD.ACCESS(5) Formats de fichiers SLAPD.ACCESS(5)

NOM

slapd.access - configuration d'accès pour slapd, le démon LDAP autonome

SYNOPSIS

/etc/openldap/slapd.conf

DESCRIPTION

Le fichier slapd.conf(5) contient des informations de configuration pour le démon slapd(8). Ce fichier de configuration est également utilisé par les outils SLAPD : slapacl(8), slapadd(8), slapauth(8), slapcat(8), slapdn(8), slapindex(8), slapmodify(8), et slaptest(8).

Le fichier slapd.conf se compose d'une série d'options de configuration globales qui s'appliquent à slapd dans son ensemble (y compris tous les backends), suivies de zéro ou plusieurs définitions de backend de base de données qui contiennent des informations spécifiques à une instance de backend.

Le format général de slapd.conf est le suivant :

    # commentaire - ces options s'appliquent à chaque base de données
    <options de configuration globales>
    # première définition de base de données & options de configuration
    database    <type de backend 1>
    <options de configuration spécifiques au backend 1>
    # définitions de base de données & options de configuration ultérieures
    ...

La configuration globale et chaque section spécifique au backend peuvent contenir des informations d'accès. Les directives de contrôle d'accès spécifiques au backend sont utilisées pour les entrées qui appartiennent au backend, conformément à leur contexte de nommage. Si aucune directive de contrôle d'accès n'est définie pour un backend ou si celles qui sont définies ne sont pas applicables, les directives de la section de configuration globale sont utilisées.

Si aucun contrôle d'accès n'est présent, la politique par défaut permet à quiconque et à tous de lire n'importe quoi, mais restreint les mises à jour à rootdn. (par exemple, « access to * by * read »).

Lorsqu'on traite une liste d'accès, étant donné que la liste d'accès globale est effectivement ajoutée à chaque liste par backend, si la liste résultante n'est pas vide, la liste d'accès se termine par une directive implicite access to * by * none. S'il n'y a pas de directives d'accès applicables à un backend, un accès en lecture par défaut est utilisé.

Attention : rootdn peut toujours lire et écrire TOUT !

Pour les entrées qui ne sont détenues par aucun backend (comme un DSE racine), les directives globales sont utilisées.

Les arguments qui doivent être remplacés par du texte réel sont indiqués entre crochets <>.

LA DIRECTIVE ACCESS

La structure des directives de contrôle d'accès est

access to <what> [ by <who> [ <access> ] [ <control> ] ]+
Accorde l'accès (spécifié par <access>) à un ensemble d'entrées et/ou d'attributs (spécifié par <what>) par un ou plusieurs demandeurs (spécifié par <who>).

Les listes de directives d'accès sont évaluées dans l'ordre où elles apparaissent dans slapd.conf. Lorsqu'une clause <what> correspond à la donnée dont l'accès est évalué, sa liste de clauses <who> est vérifiée. Lorsqu'une clause <who> correspond aux propriétés de l'accesseur, ses clauses <access> et <control> sont évaluées.

La vérification du contrôle d'accès s'arrête à la première correspondance de la clause <what> et <who>, sauf indication contraire de la clause <control>. Chaque liste de clauses <who> est implicitement terminée par une

by * none stop

clause <control>. Ce <control> implicite arrête l'évaluation des directives d'accès, sans accorder plus de privilèges d'accès à personne d'autre. Pour arrêter l'évaluation des directives d'accès uniquement lorsque <who> et <what> correspondent, ajoutez un

by * break

explicite à la fin de la liste de clauses <who>.

Chaque liste de clauses <what> est implicitement terminée par une

access to *
	by * none

clause qui aboutit à ne pas accorder de privilèges d'accès à une donnée non spécifiée autrement.

LE CHAMP <WHAT>

Le champ <what> spécifie l'entité à laquelle la directive de contrôle d'accès s'applique. Il peut avoir les formes

dn[.<dnstyle>]=<dnpattern>
filter=<ldapfilter>
attrs=<attrlist>[ val[/matchingRule][.<attrstyle>]=<attrval>]

avec

<dnstyle>={{exact|base(object)}|regex
	|one(level)|sub(tree)|children}
<attrlist>={<attr>|[{!|@}]<objectClass>}[,<attrlist>]
<attrstyle>={{exact|base(object)}|regex
	|one(level)|sub(tree)|children}

L'instruction dn=<dnpattern> sélectionne les entrées en fonction de leur contexte de nommage. Le <dnpattern> est une représentation textuelle du DN de l'entrée. Le caractère générique * représente toutes les entrées, et il est implicite si aucune forme dn n'est donnée.

Le <dnstyle> est facultatif ; cependant, il est recommandé de le spécifier pour éviter toute ambiguïté. Base (synonyme de baseObject), qui est le défaut, ou exact (un alias de base) indique l'entrée dont le DN est égal au <dnpattern> ; one (synonyme de onelevel) indique toutes les entrées immédiatement sous le <dnpattern>, sub (synonyme de subtree) indique toutes les entrées dans le sous-arbre au <dnpattern>, children indique toutes les entrées sous (subordonnées à) le <dnpattern>.

Si le qualificateur <dnstyle> est regex, alors <dnpattern> est un motif d'expression régulière POSIX (''étendue''), comme détaillé dans regex(7) et/ou re_format(7), correspondant à une représentation textuelle normalisée du DN de l'entrée. La forme regex du motif ne prend (pas encore) en charge UTF-8.

L'instruction filter=<ldapfilter> sélectionne les entrées en fonction d'un filtre LDAP valide tel que décrit dans la RFC 4515. Un filtre de (objectClass=*) est implicite si aucune forme filter n'est donnée.

L'instruction attrs=<attrlist> sélectionne les attributs auxquels la règle de contrôle d'accès s'applique. Il s'agit d'une liste d'attributs séparés par des virgules, plus les noms spéciaux entry, indiquant l'accès à l'entrée elle-même, et children, indiquant l'accès aux enfants de l'entrée. Les noms d'ObjectClass peuvent également être spécifiés dans cette liste, ce qui affectera tous les attributs requis et/ou autorisés par cette objectClass. En fait, les noms dans <attrlist> préfixés par @ sont directement traités comme des noms d'ObjectClass. Un nom préfixé par ! est également traité comme une objectClass, mais dans ce cas, la règle d'accès affecte les attributs qui ne sont ni requis ni autorisés par cette objectClass. Si aucune forme attrs n'est donnée, attrs=@extensibleObject est implicite, c'est-à-dire que tous les attributs sont adressés.

En utilisant la forme attrs=<attr> val[/matchingRule][.<attrstyle>]=<attrval>, on spécifie l'accès à une valeur particulière d'un attribut unique. Dans ce cas, un seul type d'attribut peut être donné. Le <attrstyle> exact (le défaut) utilise la règle de mise en correspondance d'égalité de l'attribut pour comparer la valeur, à moins qu'une règle de mise en correspondance différente (et compatible) ne soit spécifiée. Si le <attrstyle> est regex, la valeur fournie est utilisée comme motif d'expression régulière POSIX (''étendue''). Si l'attribut a une syntaxe de DN, le <attrstyle> peut être base, onelevel, subtree ou children, résultant respectivement en une correspondance base, onelevel, subtree ou children.

Les instructions dn, filter et attrs sont additives ; elles peuvent être utilisées séquentiellement pour sélectionner les entités auxquelles la règle d'accès s'applique en fonction simultanément du contexte de nommage, de la valeur et du type d'attribut. Les sous-correspondances résultant d'une mise en correspondance regex peuvent être déréférencées dans le champ <who> en utilisant la syntaxe ${v<n>}, où <n> est le numéro de la sous-correspondance. La syntaxe par défaut, $<n>, est en fait un alias pour ${d<n>}, qui correspond au déréférencement des sous-correspondances de la portion dnpattern du champ <what>.

LE CHAMP <WHO>

Le champ <who> indique à qui l'accès est accordé ou refusé.

Le joker * fait référence à tout le monde.

Les mots clés précédés de real agissent comme leurs homologues sans préfixe ; la vérification s'effectue respectivement avec le DN d'authentification et le DN d'autorisation.

Le mot clé anonymous signifie que l'accès est accordé aux clients non authentifiés ; il est principalement utilisé pour limiter l'accès aux ressources d'authentification (par exemple, l'attribut userPassword) aux clients non authentifiés à des fins d'authentification.

Le mot clé users signifie que l'accès est accordé aux clients authentifiés.

Le mot clé self signifie que l'accès à une entrée est autorisé à l'entrée elle-même (par exemple, l'entrée accédée et l'entrée requérante doivent être identiques). Il autorise le style level{<n>}, où <n> indique quel ancêtre du DN doit être utilisé dans les correspondances. Une valeur positive indique que le <n>-ième ancêtre du DN de l'utilisateur est à considérer ; une valeur négative indique que le <n>-ième ancêtre de la cible est à considérer. Par exemple, une clause « by self.level{1} ... » correspondra lorsque l'objet « dc=example,dc=com » est accédé par « cn=User,dc=example,dc=com ». Une clause « by self.level{-1} ... » correspondra lorsque le même utilisateur accède à l'objet « ou=Address Book,cn=User,dc=example,dc=com ».

La déclaration dn=<DN> signifie que l'accès est accordé au DN correspondant. Le qualificateur de style optionnel dnstyle permet les mêmes choix que la forme dn du champ <what>. De plus, le style regex peut exploiter la substitution de sous-chaînes des sous-correspondances dans la clause dn.regex de <what> en utilisant la forme $<digit>, avec digit allant de 0 à 9 (où 0 correspond à la chaîne entière), ou la forme ${<digit>+}, pour les sous-correspondances supérieures à 9. La substitution de sous-chaînes à partir de la valeur d'un attribut peut se faire en utilisant la forme ${v<digit>+}. Étant donné que le caractère dollar est utilisé pour indiquer un remplacement de sous-chaîne, le caractère dollar utilisé pour indiquer une correspondance jusqu'à la fin de la chaîne doit être échappé par un second caractère dollar, par exemple,

    access to dn.regex="^(.+,)?uid=([^,]+),dc=[^,]+,dc=com$"
        by dn.regex="^uid=$2,dc=[^,]+,dc=com$$" write

Le qualificateur de style permet un modifier optionnel. À l'heure actuelle, le seul type autorisé est expand, qui provoque la substitution de sous-chaînes des sous-correspondances même si dnstyle n'est pas regex. Notez que le dnstyle regex dans l'exemple ci-dessus peut être utile uniquement si la clause <by> doit être une regex ; sinon, si la valeur de la deuxième partie (à partir de la droite) dc= du DN dans l'exemple ci-dessus était fixe, la forme

    access to dn.regex="^(.+,)?uid=([^,]+),dc=example,dc=com$"
        by dn.exact,expand="uid=$2,dc=example,dc=com" write

pourrait être utilisée ; si elle devait correspondre à la valeur dans la clause <what>, la forme

    access to dn.regex="^(.+,)?uid=([^,]+),dc=([^,]+),dc=com$"
        by dn.exact,expand="uid=$2,dc=$3,dc=com" write

pourrait être utilisée.

Les formes de la clause <what> autres que regex peuvent également fournir des sous-correspondances. Les formes base(object), sub(tree), one(level) et children fournissent $0 comme correspondance de la chaîne entière. Les formes sub(tree), one(level) et children fournissent également $1 comme correspondance de la partie la plus à droite du DN tel que défini dans la clause <what>. Cela peut être utile, par exemple, pour fournir un accès à tous les ancêtres d'un utilisateur en définissant

    access to dn.subtree="dc=com"
        by dn.subtree,expand="$1" read

ce qui signifie que seul l'accès aux entrées qui apparaissent dans le DN de la clause <by> est autorisé.

La forme level{<n>} est une extension et une généralisation de la forme onelevel, qui correspond à tous les DN dont le <n>-ième ancêtre est le motif. Ainsi, level{1} est équivalent à onelevel, et level{0} est équivalent à base.

Il est totalement inutile d'accorder des privilèges d'accès à un DN qui correspond exactement au rootdn de la base de données à laquelle s'appliquent les ACL, car il possède implicitement des privilèges d'écriture pour l'ensemble de l'arborescence de cette base de données. En fait, le contrôle d'accès est contourné pour le rootdn, afin de résoudre le problème intrinsèque de l'œuf et de la poule.

La déclaration dnattr=<attrname> signifie que l'accès est accordé aux requêtes dont le DN est listé dans l'entrée accédée sous l'attribut <attrname>.

La déclaration group=<group> signifie que l'accès est accordé aux requêtes dont le DN est listé dans l'entrée de groupe dont le DN est donné par <group>. Les paramètres optionnels <objectclass> et <attrname> définissent l'objetClass et le type d'attribut membre de l'entrée de groupe. Les valeurs par défaut sont groupOfNames et member, respectivement. Le qualificateur de style optionnel <style> peut être expand, ce qui signifie que <group> sera développé comme une chaîne de remplacement (mais pas comme une expression régulière) conformément à regex(7) et/ou re_format(7), et exact, ce qui signifie qu'une correspondance exacte sera utilisée. Si le style de la partie DN de la clause <what> est regex, les sous-correspondances sont disponibles conformément à regex(7) et/ou re_format(7) ; d'autres styles fournissent des sous-correspondances limitées comme discuté ci-dessus à propos de la forme DN de la clause <by>.

Pour les groupes statiques, le type d'attribut spécifié doit avoir une syntaxe DistinguishedName ou NameAndOptionalUID. Pour les groupes dynamiques, le type d'attribut doit être un sous-type du type d'attribut labeledURI. Seules les URIs LDAP de la forme ldap:///<base>??<scope>?<filter> seront évaluées dans un groupe dynamique, en recherchant uniquement sur le serveur local.

Les déclarations peername=<peername>, sockname=<sockname>, domain=<domain> et sockurl=<sockurl> signifient que l'adresse IP de l'hôte contactant (sous la forme IP=<ip>:<port> pour IPv4, ou IP=[<ipv6>]:<port> pour IPv6) ou le nom du fichier de pipe nommé de l'hôte contactant (sous la forme PATH=<path> si la connexion passe par un pipe nommé) pour peername, le nom du fichier de pipe nommé pour sockname, le nom de l'hôte contactant pour domain, et l'URL contactante pour sockurl sont comparés au pattern pour déterminer l'accès. Les mêmes règles de style pour la correspondance de motif décrites pour le cas group s'appliquent, ainsi que le style regex, qui implique l' expand de sous-correspondance et la correspondance regex des paramètres de connexion correspondants. Le style exact de la clause <peername> (par défaut) implique une correspondance exacte sensible à la casse de l'IP du client, y compris le préfixe IP= et le suffixe :<port>, ou le chemin du client, y compris le préfixe PATH= si la connexion passe par un pipe nommé. Le style spécial ip interprète le motif comme <peername>=<ip>[%<mask>][{<n>}], où <ip> et <mask> sont des représentations numériques pointées de l'IP et du masque, tandis que <n>, délimité par des accolades, est un port optionnel. Il en va de même pour les adresses IPv6 lorsque le style spécial ipv6 est utilisé. Lors de la vérification des privilèges d'accès, la partie IP du peername est extraite, en éliminant le préfixe IP= et la partie :<port>, et elle est comparée à la partie <ip> du motif après masquage avec <mask> : ((peername & <mask>) == <ip>). Par exemple, peername.ip=127.0.0.1 et peername.ipv6=::1 autorisent les connexions uniquement depuis localhost, peername.ip=192.168.1.0%255.255.255.0 autorise les connexions depuis n'importe quelle IP du domaine de classe C 192.168.1, et peername.ip=192.168.1.16%255.255.255.240{9009} autorise les connexions depuis n'importe quelle IP de la plage 192.168.1.[16-31] du même domaine, uniquement si le port 9009 est utilisé. Le style spécial path élimine le préfixe PATH= du peername lors de la connexion via un pipe nommé, et effectue une correspondance exacte sur le motif donné. La clause <domain> autorise également le style subtree, qui réussit lorsqu'un nom entièrement qualifié correspond exactement au motif domain, ou que sa partie droite, après un point, correspond exactement au motif domain. Le style expand est autorisé, impliquant une correspondance exact avec l'expansion de sous-correspondance ; l'utilisation de expand comme modificateur de style est considérée comme plus appropriée. Par exemple, domain.subtree=example.com correspondra à www.example.com, mais ne correspondra pas à www.anotherexample.com. Le domain de l'hôte contactant est déterminé en effectuant une recherche inversée DNS. Comme cette recherche peut facilement être falsifiée, l'utilisation de la déclaration domain est fortement déconseillée. Par défaut, les recherches inversées sont désactivées. Le qualificateur optionnel domainstyle de la clause <domain> autorise une option modifier ; la seule valeur actuellement prise en charge est expand, qui provoque la substitution de sous-chaînes des sous-correspondances même si le domainstyle n'est pas regex, tout comme l'usage analogue dans la clause <dn>.

La déclaration set=<pattern> n'est pas encore documentée.

La déclaration dynacl/<name>[/<options>][.<dynstyle>][=<pattern>] signifie que ac

cess est déléguée à la méthode définie par l'administrateur indiquée par <name>, qui peut être enregistrée à l'exécution au moyen de l'instruction moduleload. Les champs <options>, <dynstyle> et <pattern> sont facultatifs et sont directement transmis à la routine d'analyse enregistrée. Dynacl est expérimental ; il doit être activé au moment de la compilation.

L'instruction dynacl/aci[=<attrname>] signifie que le contrôle d'accès est déterminé par les valeurs de l'attribut attrname de l'entrée elle-même. L'attribut facultatif <attrname> indique quel type d'attribut contient les informations ACI dans l'entrée. Par défaut, l'attribut opérationnel OpenLDAPaci est utilisé. Les ACI sont expérimentaux ; ils doivent être activés au moment de la compilation.

Les instructions ssf=<n>, transport_ssf=<n>, tls_ssf=<n> et sasl_ssf=<n> définissent le facteur de force de sécurité (ssf) minimum requis pour accorder l'accès. La valeur doit être un entier positif.

LE CHAMP <ACCES>

Le champ facultatif <access> ::= [[real]self]{<level>|<priv>} détermine le niveau d'accès ou les privilèges d'accès spécifiques que le champ who aura. Ses composants sont définis comme suit :

<level> ::= none|disclose|auth|compare|search|read|{write|add|delete}|manage
<priv> ::= {=|+|-}{0|d|x|c|s|r|{w|a|z}|m}+

Le modificateur self permet des opérations spéciales, comme avoir un certain niveau d'accès ou privilège uniquement si l'opération concerne le nom de l'utilisateur qui demande l'accès. Il implique que l'utilisateur qui demande l'accès est autorisé. Le modificateur realself fait référence au DN authentifié par opposition au DN autorisé du modificateur self. Un exemple est l'accès selfwrite à l'attribut member d'un groupe, qui permet d'ajouter/supprimer son propre DN de la liste des membres d'un groupe, tout en n'étant pas autorisé à affecter les autres membres.

Le modèle d'accès level repose sur une interprétation incrémentale des privilèges d'accès. Les niveaux possibles sont none, disclose, auth, compare, search, read, write et manage. Chaque niveau d'accès implique tous les niveaux précédents, donc manage accorde tous les accès, y compris l'accès administratif. Cet accès permet certaines modifications qui seraient autrement interdites par le modèle de données LDAP ou le schéma du répertoire, par exemple, changer la classe d'objet structurelle d'une entrée, ou modifier un attribut opérationnel défini comme non modifiable par l'utilisateur. L'accès write est en fait la combinaison de add et delete, qui restreignent respectivement le privilège d'écriture à l'ajout ou à la suppression du <what> spécifié.

Le niveau d'accès none interdit tout accès, y compris la divulgation en cas d'erreur.

Le niveau d'accès disclose permet la divulgation d'informations en cas d'erreur.

Le niveau d'accès auth signifie qu'une personne est autorisée à accéder à un attribut pour effectuer des opérations d'authentification/autorisation (par exemple, bind) sans autre accès. Ceci est utile pour accorder aux clients non authentifiés le niveau d'accès le plus bas possible aux ressources critiques, telles que les mots de passe.

Le modèle d'accès priv repose sur la définition explicite des privilèges d'accès pour chaque clause. Le signe = réinitialise les accès précédemment définis ; par conséquent, les privilèges d'accès finaux ne seront que ceux définis par la clause. Les signes + et - ajoutent/suppriment des privilèges d'accès aux existants. Les privilèges sont m pour manage, w pour write, a pour add, z pour delete, r pour read, s pour search, c pour compare, x pour authentication, et d pour disclose. Il est possible d'ajouter plusieurs des privilèges ci-dessus dans une seule instruction. 0 indique aucun privilège et n'est utilisé qu'en tant que tel (par exemple, +0). Notez que +az est équivalent à +w.

Si aucun accès n'est spécifié, la valeur par défaut est +0.

LE CHAMP <CONTROLE>

Le champ facultatif <control> contrôle le flux de l'application des règles d'accès. Il peut avoir les formes suivantes :

stop
continue
break

où stop, qui est le défaut, signifie que la vérification d'accès s'arrête en cas de correspondance. Les deux autres formes sont utilisées pour continuer le traitement des clauses d'accès. En détail, la forme continue permet que d'autres clauses <who> dans la même clause <access> soient prises en compte, de sorte qu'elles puissent résulter en une modification incrémentale des privilèges, tandis que la forme break permet que d'autres clauses <access> qui correspondent à la même cible soient traitées. Considérez l'exemple (simpliste) :

access to dn.subtree="dc=example,dc=com" attrs=cn
	by * =cs break
access to dn.subtree="ou=People,dc=example,dc=com"
	by * +r

qui accorde les privilèges de recherche et de comparaison à tout le monde dans l'arbre "dc=example,dc=com", la deuxième règle autorisant également la lecture dans le sous-arbre "ou=People", ou l'exemple (encore plus simpliste) :

access to dn.subtree="dc=example,dc=com" attrs=cn
	by * =cs continue
	by users +r

qui accorde à tout le monde les privilèges de recherche et de comparaison, et ajoute des privilèges de lecture aux clients authentifiés.

Une application utile est d'accorder facilement des privilèges d'écriture à un updatedn différent du rootdn. Dans ce cas, puisque l'updatedn a besoin d'un accès en écriture à (presque) toutes les données, on peut utiliser :

access to *
	by dn.exact="cn=The Update DN,dc=example,dc=com" write
	by * break

comme première règle d'accès. Par conséquent, sauf si l'opération est effectuée avec l'identité updatedn, le contrôle est passé directement aux règles suivantes.

EXIGENCES OPERATOIRES

Les opérations nécessitent des privilèges différents sur différentes parties des entrées. Le résumé suivant s'applique au backend de base de données MDB principal. Les exigences pour d'autres backends peuvent (et font souvent) différer.

L'opération add nécessite des privilèges add (=a) sur le pseudo-attribut entry de l'entrée ajoutée, et des privilèges add (=a) sur le pseudo-attribut children du parent de l'entrée. Lors de l'ajout de l'entrée suffixe d'une base de données, l'accès add aux children du DN vide ("") est requis. De plus, si la vérification ACL du contenu d'ajout a été configurée sur la base de données (voir la page de manuel slapd.conf(5) ou slapd-config(5)), add (=a) sera requis sur tous les attributs ajoutés.

L'opération bind, lorsque les identifiants sont stockés dans le répertoire, nécessite des privilèges auth (=x) sur l'attribut où les identifiants sont stockés (généralement userPassword).

L'opération compare nécessite des privilèges compare (=c) sur l'attribut qui est comparé.

L'opération delete nécessite des privilèges delete (=z) sur le pseudo-attribut entry de l'entrée à supprimer, et des privilèges delete (=d) sur le pseudo-attribut children du parent de l'entrée.

L'opération modify nécessite des privilèges write (=w) sur les attributs modifiés. En détail, add (=a) est requis pour ajouter de nouvelles valeurs, delete (=z) est requis pour supprimer les valeurs existantes, et à la fois delete et add (=az), ou write (=w), sont requis pour remplacer les valeurs existantes.

L'opération modrdn nécessite des privilèges write (=w) sur le pseudo-attribut entry de l'entrée dont le DN relatif est modifié, des privilèges delete (=z) sur le pseudo-attribut children du parent de l'ancienne entrée, des privilèges add (=a) sur le pseudo-attribut children du parent de la nouvelle entrée, et des privilèges add (=a) sur les attributs présents dans le nouveau DN relatif. Des privilèges Delete (=z) sont également requis sur les attributs présents dans l'ancien DN relatif si deleteoldrdn est défini à 1.

L'opération search nécessite des privilèges search (=s) sur le pseudo-attribut entry de la base de recherche (NOTE : cela a été introduit avec OpenLDAP 2.4). Ensuite, pour chaque entrée, elle nécessite des privilèges search (=s) sur les attributs définis dans le filtre. Les entrées résultantes sont finalement testées pour les privilèges read (=r) sur le pseudo-attribut entry (pour l'accès en lecture à l'entrée elle-même) et pour l'accès read (=r) sur chaque valeur de chaque attribut demandé. De plus, pour chaque objet referral utilisé pour générer des références de continuation, l'opération nécessite un accès read (=r) sur le pseudo-attribut entry (pour l'accès en lecture à l'objet de renvoi lui-même), ainsi qu'un accès read (=r) à l'attribut contenant les informations de renvoi (généralement l'attribut ref).

Certaines opérations internes et certains controls nécessitent des privilèges d'accès spécifiques.

Le mappage SASL authzID et le contrôle LDAP proxyAuthz nécessitent des privilèges auth (=x) sur tous les attributs présents dans le filtre de recherche des mappages regexp d'URI (le côté droit des directives authz-regexp). Des privilèges Auth (=x) sont également requis sur l'attribut authzTo de l'identité autorisante et/ou sur l'attribut authzFrom de l'identité autorisée. Dans les deux cas, c'est l'identité autorisante qui requiert les privilèges (c'est-à-dire l'identité qui s'est authentifiée et qui essaie maintenant d'effectuer une opération en utilisant les permissions d'une autre entité).

En général, lorsqu'une recherche interne est effectuée à des fins d'authentification ou d'autorisation, les privilèges de recherche (voir les exigences d'accès pour l'opération de recherche illustrées ci-dessus) sont assouplis à auth.

Le contrôle d'accès aux entrées de recherche est vérifié par le frontend, il est donc entièrement respecté par tous les backends ; pour toutes les autres opérations et pour la phase de découverte de l'opération de recherche, les sémantiques ACL complètes ne sont prises en charge que par les backends principaux, c'est-à-dire slapd-mdb(5).

Certains autres backends, comme slapd-sql(5), peuvent les prendre en charge entièrement ; d'autres ne peuvent prendre en charge qu'une partie des sémantiques décrites, voire différer sur certains aspects. Les détails pertinents sont décrits dans les pages man spécifiques au backend.

NAME

slapd.access

Access control list syntax for slapd

SYNOPSIS

Configuration

olcAccess: "<access>"

slapd.conf

access <access>

DESCRIPTION

The access directive is used to specify access controls for LDAP entries and attributes. Access controls are hierarchical and are evaluated in the order in which they appear in the configuration file. The first matching access control rule determines the access rights granted or denied for a given operation.

An access control rule consists of a target specification (<what>), a subject specification (<who>), and an access specification (<access>). Optionally, a control specification (<control>) may also be appended.

THE ACCESS DIRECTIVE

The full syntax for the access directive is:

access to <what> [ by <who> [<access>] [<control>] [<control>] ... ] ...

Where:

<what>
Specifies the target entry or entries, and optionally attributes, to which the rule applies.
<who>
Specifies the subject performing the operation.
<access>
Specifies the type of access granted or denied. This is a set of permission characters.
<control>
Specifies optional control clauses that modify the behavior of the access rule.

THE <WHAT> FIELD

The <what> field specifies the target of the access control rule. It consists of a base DN and an optional filter. The base DN specifies the entry or subtree to which the rule applies. The filter, if present, is used to further restrict the entries that the rule applies to.

The <what> field can also specify a list of attributes to which the rule applies. If no attributes are specified, the rule applies to all attributes of the matching entries.

The following keywords are supported for specifying the <what> field:

dn
Matches entries based on their Distinguished Name (DN).
dn.exact
Matches entries based on an exact DN.
dn.base
Matches entries at the specified base DN.
dn.onelevel
Matches entries one level below the specified base DN.
dn.subtree
Matches entries in the subtree specified by the base DN.
dn.regex
Matches entries based on a regular expression applied to their DN.
filter
Matches entries based on an LDAP search filter.

Attributes can be specified after the DN or filter, separated by a colon. For example:

access to dn.subtree="ou=people,dc=example,dc=com":cn,sn,givenName

This rule applies to the `cn`, `sn`, and `givenName` attributes of entries in the subtree `ou=people,dc=example,dc=com`.

If no attribute specification is provided, the rule applies to all attributes.

access to dn.subtree="ou=people,dc=example,dc=com"

This rule applies to all attributes of entries in the subtree `ou=people,dc=example,dc=com`.

THE <WHO> FIELD

The <who> field specifies the subject for whom the access is being granted or denied. The following keywords are supported:

self
The authenticated user.
anonymous
Unauthenticated users.
users
All authenticated users.
group
Users who are members of the specified group.
dn
Users with the specified DN.
dn.exact
Users with the exact specified DN.
dn.base
Users at the specified base DN.
dn.onelevel
Users one level below the specified base DN.
dn.subtree
Users in the subtree specified by the base DN.
dn.regex
Users whose DN matches the specified regular expression.
filter
Users whose DN matches the specified LDAP search filter.

The <who> field can also be specified as a DN string, which is equivalent to dn.exact.

For group membership checking, the group keyword is followed by the DN of the group entry. The membership is checked based on the `member` or `uniqueMember` attribute of the group entry, or by using the `groupOfNames`, `groupOfUniqueNames`, or `posixGroup` object classes.

access to dn.subtree="dc=example,dc=com"
	by group="cn=admins,dc=example,dc=com" write
	by * read

This rule grants write access to members of the `cn=admins,dc=example,dc=com` group and read access to all other users for entries in the `dc=example,dc=com` subtree.

THE <ACCESS> FIELD

The <access> field specifies the permissions granted or denied to the subject. The following permission characters are supported:

{
Start of an entry-level or attribute-level ACL.
}
End of an entry-level or attribute-level ACL.
+
Grant access.
-
Deny access.
?
Allow access only if the user has read access to the entry.
=
Allow access only if the user has write access to the entry.
read
Grant read access.
write
Grant write access.
search
Grant search access.
compare
Grant compare access.
auth
Grant authentication access.
add
Grant add access.
delete
Grant delete access.
read,write,search,compare,auth,add,delete
Grant all access.

The special character `*` is used as a wildcard to match any subject not explicitly matched by a preceding rule.

If no access specification is provided, the default is to grant no access.

access to entry dn.exact="dc=example,dc=com"
	by * none

This rule denies all access to the entry `dc=example,dc=com` for all users.

THE <CONTROL> FIELD

The <control> field allows for more fine-grained control over access rules. The following control keywords are supported:

expand
Expands DNs in the subject specification. This is useful when using wildcards in DNs.
stop
Stop processing access control rules after this rule is matched.
break
Stop processing access control rules for the current subject and proceed to the next rule.

OPERATION REQUIREMENTS

Access controls are evaluated based on the type of operation being performed. The following operations are supported:

add
Add entry operation.
bind
Bind operation.
delete
Delete entry operation.
extended
Extended operations.
modify
Modify entry operation.
search
Search operation.
read
Read attribute operation.
compare
Compare operation.

The access control rules are evaluated in the order they appear in the configuration file. The first rule that matches the operation and the subject determines the access rights.

CAVEATS

When using regular expressions in access control rules, it is important to be aware of their behavior. Regular expressions are matched against the entire DN or attribute value. If a regular expression does not match the entire string, it will not be considered a match.

For example, the following rule:

access to dn.regex="dc=example,dc=com"
	by ...

will only match the entry with the exact DN `dc=example,dc=com`. It will not match entries in the subtree of `dc=example,dc=com`.

To match entries in a subtree using regular expressions, you need to use anchors and quantifiers to specify the beginning and end of the string. For example:

access to dn.regex="^(.+,)?dc=example,dc=com$"
	by ...

This rule will match `dc=example,dc=com` as well as any entry whose DN ends with `,dc=example,dc=com`.

For performance reasons, it is generally recommended to use the subtree style access control when possible, as it is more efficient than using regular expressions for subtree matching.

access to dn.subtree="dc=example,dc=com"
	by ...

When writing submatch rules, it may be convenient to avoid unnecessary regex <dnstyle> use; for instance, to allow access to the subtree of the user that matches the <what> clause, one could use

access to dn.regex="^(.+,)?uid=([^,]+),dc=example,dc=com$"
	by dn.regex="^uid=$2,dc=example,dc=com$$" write
	by ...

However, since all that is required in the <by> clause is substring expansion, a more efficient solution is

access to dn.regex="^(.+,)?uid=([^,]+),dc=example,dc=com$"
	by dn.exact,expand="uid=$2,dc=example,dc=com" write
	by ...

In fact, while a <dnstyle> of regex implies substring expansion, exact, as well as all the other DN specific <dnstyle> values, does not, so it must be explicitly requested.
