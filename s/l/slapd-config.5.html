SLAPD-CONFIG(5) Manuel des formats de fichiers SLAPD-CONFIG(5)

NOM

slapd-config - backend de configuration pour slapd

SYNTAXE

/etc/openldap/slapd.d

DESCRIPTION

Le backend config gère toutes les informations de configuration du démon slapd(8). Ces informations de configuration sont également utilisées par les outils SLAPD slapacl(8), slapadd(8), slapauth(8), slapcat(8), slapdn(8), slapindex(8), slapmodify(8), et slaptest(8).

Le backend config est rétrocompatible avec l'ancien fichier slapd.conf(5), mais il offre la possibilité de changer la configuration dynamiquement à l'exécution. Si slapd est exécuté avec seulement un fichier slapd.conf, les changements dynamiques seront autorisés mais ils ne persisteront pas lors d'un redémarrage du serveur. Les changements dynamiques ne sont enregistrés que lorsque slapd fonctionne à partir d'un répertoire de configuration slapd.d.

Contrairement aux autres backends, il ne peut y avoir qu'une seule instance du backend config, et la plupart de sa structure est prédéfinie. La racine de la base de données est codée en dur à cn=config et cette entrée racine contient les paramètres globaux de slapd. Plusieurs entrées enfants sous l'entrée racine sont utilisées pour transporter divers autres paramètres :

cn=Module
modules chargés dynamiquement
cn=Schema
définitions de schémas
olcBackend=xxx
paramètres spécifiques au backend
olcDatabase=xxx
paramètres spécifiques à la base de données

Les entrées cn=Module n'apparaîtront que dans les configurations où slapd a été compilé avec la prise en charge des modules chargés dynamiquement. Il peut y avoir plusieurs entrées, une pour chaque chemin de module configuré. Dans chaque entrée, des valeurs seront enregistrées pour chaque module chargé sur un chemin donné. Ces entrées n'ont pas d'enfants.

L'entrée cn=Schema contient tous les éléments de schéma codés en dur. Les enfants de cette entrée contiennent tous les éléments de schéma définis par l'utilisateur. Dans les schémas qui ont été chargés à partir de fichiers d'inclusion, l'entrée enfant sera nommée d'après le fichier d'inclusion à partir duquel le schéma a été chargé. Généralement, le premier enfant de cet arbre sera cn=core,cn=schema,cn=config.

Les entrées olcBackend servent à stocker les paramètres spécifiques à un type de backend unique (et donc globaux pour toutes les instances de base de données de ce type). À l'heure actuelle, seul back-mdb implémente des options de ce type, donc ce paramètre n'est pas nécessaire pour les autres backends.

Les entrées olcDatabase stockent les paramètres spécifiques à une instance de base de données unique. Ces entrées peuvent avoir des entrées enfants olcOverlay correspondant aux superpositions configurées sur la base de données. Les entrées olcDatabase et olcOverlay peuvent également avoir des entrées enfants diverses pour d'autres paramètres si nécessaire. Il existe deux entrées de base de données spéciales qui sont prédéfinies : l'une est une entrée pour la base de données de configuration elle-même, et l'autre est pour la base de données "frontend". Les paramètres de la base de données frontend sont hérités par les autres bases de données, à moins qu'ils ne soient explicitement remplacés dans une base de données spécifique.

Les options de configuration spécifiques disponibles sont discutées ci-dessous dans les Options de configuration globale, les Options générales de backend et les Options générales de base de données. Les options sont définies en attribuant des attributs LDAP avec des valeurs spécifiques. En général, les noms des attributs LDAP sont identiques aux mots-clés correspondants de slapd.conf, avec le préfixe "olc" ajouté.

L'analyseur pour nombre de ces attributs est le même que celui utilisé pour analyser les mots-clés de slapd.conf. Ainsi, les mots-clés de slapd.conf qui autorisent plusieurs éléments à être spécifiés sur une seule ligne, séparés par des espaces, autoriseront plusieurs éléments à être spécifiés dans une seule valeur d'attribut. Cependant, lors de la lecture de l'attribut via LDAP, les éléments seront renvoyés comme des valeurs d'attribut individuelles.

Les options spécifiques au backend sont discutées dans les pages du manuel slapd-<backend>(5). Référez-vous au "Guide de l'administrateur OpenLDAP" pour plus de détails sur la configuration de slapd.

Si vous utilisez la directive olcAttributeOptions, `lang-' ne sera plus défini et vous devrez le spécifier explicitement si vous souhaitez qu'il soit défini.

Une description d'attribut avec une option de marquage est un sous-type de cette description d'attribut sans l'option. Sauf pour cela, les options définies de cette manière n'ont pas de sémantique spéciale. Les préfixes définis de cette manière fonctionnent comme les options `lang-' : Ils définissent un préfixe pour les options de marquage commençant par le préfixe. C'est-à-dire que si vous définissez le préfixe `x-foo-', vous pouvez utiliser l'option `x-foo-bar'. De plus, dans une recherche ou une comparaison, un nom de préfixe ou de plage (avec un '-' final) correspond à toutes les options commençant par ce nom, ainsi qu'à l'option avec le nom de plage sans le '-' final. Directives Access

Access rules define which users are allowed to perform operations on which attributes. The rules are processed in the order in which they appear in the configuration file. The first rule that applies to an operation is selected, and the corresponding access permissions are granted or denied. A default rule of access to * by * read is added if no access rules are specified.

The syntax for access rules is:

access to dn_pattern [by authz_spec [authz_spec] ...]

where dn_pattern is a pattern that specifies the entries or attributes to which the rule applies, and authz_spec is a specification of the authorization context and the access permissions granted in that context.

The dn_pattern can be a full DN, a partial DN, or a pattern that matches a set of DNs. The wildcard character '*' matches any sequence of zero or more characters. The wildcard character '?' matches any single character.

The authz_spec has the syntax:

by { self | dn[.<dnstyle>]:<pattern> | group[/objectClass[/attributeType]]:<pattern> | anonymous | authc | authzid | id=<name> | peername=<name> | valid } [read | write | search | compare | auth | add | delete | read | write | search | compare | auth | add | delete | all]

The by keyword specifies the authorization context. The following contexts are supported:

self: Matches the authenticated user.

dn[.dnstyle]:pattern: Matches users whose DN matches pattern. The dnstyle can be exact, onelevel, children, subtree, or regex. If dnstyle is omitted, exact is assumed.

group[/objectClass[/attributeType]]:pattern: Matches users who are members of the group specified by pattern. The objectClass and attributeType specify the group's object class and member attribute, respectively. The defaults are groupOfNames and member.

anonymous: Matches anonymous users.

authc: Matches authenticated users.

authzid: Matches users with asserted authorization IDs.

id=name: Matches users whose SASL ID is name.

peername=name: Matches users whose peer name is name.

valid: Matches any valid user.

The following access permissions can be granted:

read: Allows reading attributes.

write: Allows writing attributes.

search: Allows searching entries.

compare: Allows comparing attributes.

auth: Allows authentication.

add: Allows adding entries.

delete: Allows deleting entries.

all: Grants all permissions.

The all flag requires both authorizations to succeed.

The rules are mechanisms to specify which identities are allowed to perform proxy authorization. The authzFrom attribute in an entry specifies which other users are allowed to proxy login to this entry. The authzTo attribute in an entry specifies which other users this user can authorize as. Use of authzTo rules can be easily abused if users are allowed to write arbitrary values to this attribute. In general the authzTo attribute must be protected with ACLs such that only privileged users can modify it. The value of authzFrom and authzTo describes an identity or a set of identities; it can take five forms:
ldap:///<base>??[<scope>]?<filter>
dn[.<dnstyle>]:<pattern>
u[.<mech>[<realm>]]:<pattern>
group[/objectClass[/attributeType]]:<pattern>
<pattern>

<dnstyle>:={exact|onelevel|children|subtree|regex}

The first form is a valid LDAP URI where the <host>:<port>, the <attrs> and the <extensions> portions must be absent, so that the search occurs locally on either authzFrom or authzTo.

The second form is a DN, with the optional style modifiers exact, onelevel, children, and subtree for exact, onelevel, children and subtree matches, which cause <pattern> to be normalized according to the DN normalization rules, or the special regex style, which causes the <pattern> to be treated as a POSIX (''extended'') regular expression, as discussed in regex(7) and/or re_format(7). A pattern of * means any non-anonymous DN.

The third form is a SASL id, with the optional fields <mech> and <realm> that allow to specify a SASL mechanism, and eventually a SASL realm, for those mechanisms that support one. The need to allow the specification of a mechanism is still debated, and users are strongly discouraged to rely on this possibility.

The fourth form is a group specification. It consists of the keyword group, optionally followed by the specification of the group objectClass and attributeType. The objectClass defaults to groupOfNames. The attributeType defaults to member. The group with DN <pattern> is searched with base scope, filtered on the specified objectClass. The values of the resulting attributeType are searched for the asserted DN.

The fifth form is provided for backwards compatibility. If no identity type is provided, i.e. only <pattern> is present, an exact DN is assumed; as a consequence, <pattern> is subjected to DN normalization.

Since the interpretation of authzFrom and authzTo can impact security, users are strongly encouraged to explicitly set the type of identity specification that is being used. A subset of these rules can be used as third arg in the olcAuthzRegexp statement (see below); significantly, the URI, provided it results in exactly one entry, and the dn.exact:<dn> forms.

olcAuthzRegexp: <match> <replace>
Used by the authentication framework to convert simple user names, such as provided by SASL subsystem, or extracted from certificates in case of cert-based SASL EXTERNAL, or provided within the RFC 4370 "proxied authorization" control, to an LDAP DN used for authorization purposes. Note that the resulting DN need not refer to an existing entry to be considered valid. When an authorization request is received from the SASL subsystem, the SASL USERNAME, REALM, and MECHANISM are taken, when available, and combined into a name of the form
UID=<username>[[,CN=<realm>],CN=<mechanism>],CN=auth
This name is then compared against the match POSIX (''extended'') regular expression, and if the match is successful, the name is replaced with the replace string. If there are wildcard strings in the match regular expression that are enclosed in parenthesis, e.g.
UID=([^,]*),CN=.*
then the portion of the name that matched the wildcard will be stored in the numbered placeholder variable $1. If there are other wildcard strings in parenthesis, the matching strings will be in $2, $3, etc. up to $9. The placeholders can then be used in the replace string, e.g.
UID=$1,OU=Accounts,DC=example,DC=com
The replaced name can be either a DN, i.e. a string prefixed by "dn:", or an LDAP URI. If the latter, the server will use the URI to search its own database(s) and, if the search returns exactly one entry, the name is replaced by the DN of that entry. The LDAP URI must have no hostport, attrs, or extensions components, but the filter is mandatory, e.g.
ldap:///OU=Accounts,DC=example,DC=com??one?(UID=$1)
The protocol portion of the URI must be strictly ldap. Note that this search is subject to access controls. Specifically, the authentication identity must have "auth" access in the subject.

Multiple olcAuthzRegexp values can be specified to allow for multiple matching and replacement patterns. The matching patterns are checked in the order they appear in the attribute, stopping at the first successful match.

olcConcurrency: <integer>
Specify a desired level of concurrency. Provided to the underlying thread system as a hint. The default is not to provide any hint. This setting is only meaningful on some platforms where there is not a one to one correspondence between user threads and kernel threads.
olcConnMaxPending: <integer>
Specify the maximum number of pending requests for an anonymous session. If requests are submitted faster than the server can process them, they will be queued up to this limit. If the limit is exceeded, the session is closed. The default is 100.
olcConnMaxPendingAuth: <integer>
Specify the maximum number of pending requests for an authenticated session. The default is 1000.
olcDisallows: <features>
Specify a set of features to disallow (default none). bind_anon disables acceptance of anonymous bind requests. Note that this setting does not prohibit anonymous directory access (See "require authc"). bind_simple disables simple (bind) authentication. tls_2_anon disables forcing session to anonymous status (see also tls_authc) upon StartTLS operation receipt. tls_authc disallows the StartTLS operation if authenticated (see also tls_2_anon). proxy_authz_non_critical disables acceptance of the proxied authorization control (RFC4370) with criticality set to FALSE. dontusecopy_non_critical disables acceptance of the dontUseCopy control (a work in progress) with criticality set to FALSE.
olcGentleHUP: { TRUE | FALSE }
A SIGHUP signal will only cause a 'gentle' shutdown-attempt: Slapd will stop listening for new connections, but will not close the connections to the current clients. Future write operations return unwilling-to-perform, though. Slapd terminates when all clients have closed their connections (if they ever do), or - as before - if it receives a SIGTERM signal. This can be useful if you wish to terminate the server and start a new slapd server with another database, without disrupting the currently active clients. The default is FALSE. You may wish to use olcIdleTimeout along with this option.
olcIdleTimeout: <integer>
Specify the number of seconds to wait before forcibly closing an idle client connection. A setting of 0 disables this feature. The default is 0. You may also want to set the olcWriteTimeout option.
olcIndexHash64: { TRUE | FALSE }
Use a 64 bit hash for indexing. The default is to use 32 bit hashes. These hashes are used for equality and substring indexing. The 64 bit version may be needed to avoid index collisions when the number of indexed values exceeds ~64 million. (Note that substring indexing generates multiple index values per actual attribute value.) Indices generated with 32 bit hashes are incompatible with the 64 bit version, and vice versa. Any existing databases must be fully reloaded when changing this setting. This directive is only supported on 64 bit CPUs.
olcIndexIntLen: <integer>
Specify the key length for ordered integer indices. The most significant bytes of the binary integer will be used for index keys. The default value is 4, which provides exact indexing for 31 bit values. A floating point representation is used to index too large values.
olcIndexSubstrIfMaxlen: <integer>
Specify the maximum length for subinitial and subfinal indices. Only this many characters of an attribute value will be processed by the indexing functions; any excess characters are ignored. The default is 4.
olcIndexSubstrIfMinlen: <integer>
Specify the minimum length for subinitial and subfinal indices. Only this many characters of an attribute value will be processed by the indexing functions; any excess characters are ignored. The default is 0.
 ">olcIndexSubstrIfMinlen: <entier>
Spécifiez la longueur minimale des index subinitial et subfinal. Une valeur d'attribut doit avoir au moins ce nombre de caractères pour être traitée par les fonctions d'indexation. La valeur par défaut est 2.
olcIndexSubstrAnyLen: <entier>
Spécifiez la longueur utilisée pour les index subany. Une valeur d'attribut doit avoir au moins ce nombre de caractères pour être traitée. Les valeurs d'attributs plus longues que cette longueur seront traitées par segments de cette longueur. La valeur par défaut est 4. L'index subany sera également utilisé dans les recherches d'index subinitial et subfinal lorsque la chaîne de filtre est plus longue que la valeur olcIndexSubstrIfMaxlen.
olcIndexSubstrAnyStep: <entier>
Spécifiez les pas utilisés dans les recherches d'index subany. Cette valeur définit le décalage pour les segments d'une chaîne de filtre qui sont traités pour une recherche d'index subany. La valeur par défaut est 2. Par exemple, avec les valeurs par défaut, une recherche utilisant le filtre "cn=*abcdefgh*" générerait des recherches d'index pour "abcd", "cdef" et "efgh".

Note : La prise en charge de l'indexation dépend du backend utilisé. De plus, la modification de ces paramètres nécessitera généralement la suppression des index qui dépendent de ces paramètres et leur recréation avec slapindex(8).

olcListenerThreads: <entier>
Spécifiez le nombre de threads à utiliser pour le gestionnaire de connexions. La valeur par défaut est 1, ce qui est généralement suffisant pour jusqu'à 16 cœurs de processeur. La valeur doit être une puissance de 2.
olcLocalSSF: <SSF>
Spécifie le facteur de force de sécurité (SSF) à attribuer aux sessions LDAP locales, telles que celles du listener ldapi://. Pour une description des valeurs SSF, voir la description de l'option minssf de olcSaslSecProps. La valeur par défaut est 71.
olcLogFile: <nom_fichier>
Spécifiez un fichier pour enregistrer les messages de débogage de slapd. Ces messages ne sont pas liés aux messages exposés par le paramètre de configuration olcLogLevel. Ce paramètre n'affecte que le démon slapd et n'a aucun effet sur les outils en ligne de commande. Par défaut, ces messages ne sont envoyés qu'à la sortie d'erreur standard et ne sont enregistrés nulle part ailleurs. La spécification d'un fichier journal copie les messages à la fois vers la sortie d'erreur standard et vers le fichier journal.
olcLogFileFormat: debug|syslog-utc|syslog-localtime|rfc3339-utc
Spécifiez le format du préfixe pour les messages écrits dans le fichier journal. Le format de débogage est le format normal utilisé pour les messages de débogage de slapd, avec une horodatage en hexadécimal, suivi d'un ID de thread. Les autres options consistent à utiliser des préfixes de style syslog(3), avec des horodatages en UTC ou dans le fuseau horaire local. La valeur par défaut est le format de débogage.
olcLogFileOnly: TRUE | FALSE
Spécifiez que les messages de débogage ne doivent être envoyés qu'au fichier journal configuré, et non à la sortie d'erreur standard.
olcLogFileRotate: <max> <Mbytes> <heures>
Spécifiez la rotation automatique du fichier journal configuré comme nombre maximal de vieux fichiers journaux à conserver, une taille maximale en mégaoctets autorisée pour un fichier journal avant rotation, et une durée maximale en heures d'utilisation d'un fichier journal avant rotation. Le nombre maximal doit être compris entre 1 et 99. La définition de Mbytes ou heures à zéro désactive respectivement le contrôle de la taille ou de l'âge. Au moins un des paramètres Mbytes ou heures doit être non nul. Par défaut, aucune rotation automatique n'est effectuée.
olcLogLevel: <entier> [...]
Spécifiez le niveau auquel les instructions de débogage et les statistiques d'opérations doivent être journalisées (syslogged) (actuellement journalisées dans la facilité LOG_LOCAL4 de syslogd(8)). Elles doivent être considérées comme des sous-systèmes plutôt que comme des niveaux de journalisation de plus en plus verbeux. Certains messages de plus haute priorité sont journalisés indépendamment du niveau de journalisation configuré dès qu'une journalisation est configurée. Les niveaux de journalisation sont additifs et les niveaux disponibles sont :
1
(0x1 trace) trace des appels de fonction
2
(0x2 packets) débogage de la gestion des paquets
4
(0x4 args) débogage intensif (arguments de fonction)
8
(0x8 conns) gestion des connexions
16
(0x10 BER) affichage des paquets envoyés et reçus
32
(0x20 filter) traitement des filtres de recherche
64
(0x40 config) traitement du fichier de configuration
128
(0x80 ACL) traitement des listes de contrôle d'accès
256
(0x100 stats) connexions, opérations LDAP, résultats (recommandé)
512
(0x200 stats2) écritures du journal stats2 envoyées
1024
(0x400 shell) affichage de la communication avec les backends shell
2048
(0x800 parse) analyse des entrées
16384
(0x4000 sync) réplication LDAPSync
32768
(0x8000 none) uniquement les messages qui sont journalisés quel que soit le niveau de journalisation défini
Le niveau de journalisation souhaité peut être saisi sous forme d'un entier unique qui combine (OU) les niveaux souhaités, en notation décimale ou hexadécimale, sous forme d'une liste d'entiers (qui sont mis en OU en interne), ou sous forme d'une liste de noms indiqués entre parenthèses, de sorte que 
    olcLogLevel: 129
    olcLogLevel: 0x81
    olcLogLevel: 128 1
    olcLogLevel: 0x80 0x1
    olcLogLevel: acl trace

soient équivalents. Le mot-clé any peut être utilisé comme raccourci pour activer la journalisation à tous les niveaux (équivalent à -1). Le mot-clé none, ou sa représentation entière équivalente, permet de journaliser les messages qui sont journalisés quel que soit le niveau de journalisation configuré. En fait, si aucun olcLogLevel (ou un niveau 0) n'est défini, aucune journalisation n'a lieu, donc au moins le niveau none est requis pour que les messages de haute priorité soient journalisés.

Notez que les niveaux packets, BER et parse ne sont disponibles que sous forme de sortie de débogage sur la sortie d'erreur standard, et ne sont pas envoyés à syslog.

Ce paramètre est par défaut stats. Ce niveau devrait généralement également être inclus lors de l'utilisation d'autres niveaux de journalisation, pour aider à analyser les journaux.

olcMaxFilterDepth: <entier>
Spécifiez la profondeur maximale des filtres imbriqués dans les requêtes de recherche. La valeur par défaut est 1000.
olcPasswordCryptSaltFormat: <format>
Spécifiez le format du sel passé à crypt(3) lors de la génération des mots de passe {CRYPT} (voir olcPasswordHash) lors du traitement des opérations d'extension de modification de mot de passe LDAP (RFC 3062).

Cette chaîne doit être au format sprintf(3) et peut inclure une (et une seule) conversion %s. Cette conversion sera remplacée par une chaîne de caractères aléatoires parmi [A-Za-z0-9./]. Par exemple, "%.2s" fournit un sel de deux caractères et "$1$%.8s" indique à certaines versions de crypt(3) d'utiliser un algorithme MD5 et fournit 8 caractères aléatoires de sel. La valeur par défaut est "%s", qui fournit 31 caractères de sel.

olcPluginLogFile: <nom_fichier>

olcReferral: <url>
Spécifiez la référence à renvoyer lorsque slapd(8) ne trouve pas de base de données locale pour gérer une requête. Si plusieurs valeurs sont spécifiées, chaque URL est fournie.
olcReverseLookup: TRUE | FALSE
Activer/désactiver la recherche inversée non vérifiée du nom du client (par défaut est FALSE si compilé avec --enable-rlookups).
olcRootDSE: <fichier>
Spécifiez le nom d'un fichier LDIF(5) contenant des attributs définis par l'utilisateur pour le DSE racine. Ces attributs sont retournés en plus des attributs normalement produits par slapd.

Le DSE racine est une entrée contenant des informations sur le serveur et ses capacités, dans les attributs opérationnels. Il a le DN vide, et peut être lu avec par exemple : ldapsearch -x -b "" -s base "+"
Voir la section 5.1 de la RFC 4512 pour les détails.

olcSaslAuxprops: <plugin> [...]
Spécifiez les plugins auxprop à utiliser pour les recherches d'authentification. La valeur par défaut est vide, ce qui utilise simplement le support interne de slapd. Généralement, aucun autre plugin auxprop n'est nécessaire.
olcSaslAuxpropsDontUseCopy: <attr> [...]
Spécifiez quels attribut(s) doivent être soumis au contrôle "ne pas utiliser de copie". Ceci est nécessaire pour que certains mécanismes SASL comme OTP fonctionnent dans un environnement répliqué. L'attribut "cmusaslsecretOTP" est la valeur par défaut.
olcSaslAuxpropsDontUseCopyIgnore TRUE | FALSE
Utilisé pour désactiver la réplication de l'attribut (ou des attributs) défini(s) par olcSaslAuxpropsDontUseCopy et utiliser à la place une valeur locale pour l'attribut. Cela permet au mécanisme SASL de continuer à fonctionner si le fournisseur est hors ligne. Cela peut entraîner une incohérence de réplication. Par défaut à FALSE.
olcSaslHost: <fqdn>
Utilisé pour spécifier le nom de domaine pleinement qualifié utilisé pour le traitement SASL.
olcSaslRealm: <realm>
Spécifiez le realm SASL. Par défaut, il est vide.
olcSaslCbinding: none | tls-unique | tls-endpoint
Spécifie le type de liaison de canal, voir aussi LDAP_OPT_X_SASL_CBINDING. La valeur par défaut est none.
olcSaslSecProps: <propriétés>
Utilisé pour spécifier les propriétés de sécurité Cyrus SASL. Le drapeau none (sans aucune autre propriété) entraîne l'effacement des propriétés par défaut, "noanonymous,noplain". Le drapeau noplain désactive les mécanismes susceptibles aux attaques passives simples. Le drapeau noactive désactive les mécanismes susceptibles aux attaques actives. Le drapeau nodict désactive les mécanismes susceptibles aux attaques par dictionnaire passives. Le drapeau noanonymous désactive les mécanismes qui prennent en charge la connexion anonyme. Le drapeau forwardsec requiert une sécurité directe entre les sessions. Le drapeau passcred requiert les mécanismes qui transmettent les informations d'identification du client (et autorisent les mécanismes capables de transmettre des informations d'identification à le faire). La propriété minssf=<facteur> spécifie le *facteur de force de sécurité* minimum acceptable sous forme d'un entier approximatif de la longueur de clé effective utilisée pour le chiffrement. 0 (zéro) implique aucune protection, 1 implique uniquement la protection d'intégrité, 128 autorise RC4, Blowfish et d'autres chiffrements similaires, 256 nécessitera des chiffrements modernes. La valeur par défaut est 0. La propriété maxssf=<facteur> spécifie le *facteur de force de sécurité* maximum acceptable sous forme d'un entier (voir la description de minssf). La valeur par défaut est INT_MAX. La propriété maxbufsize=<taille> spécifie la taille maximale du tampon de réception de la couche de sécurité autorisée. 0 désactive les couches de sécurité. La valeur par défaut est 65536.
olcServerID: <entier> [<URL>]
Spécifie un identifiant entier de 0 à 4095 pour ce serveur. L'identifiant peut également être spécifié comme un identifiant hexadécimal en préfixant la valeur avec "0x". Des identifiants non nuls sont requis lors de l'utilisation de la réplication multi-fournisseurs et chaque fournisseur doit avoir un identifiant non nul unique. Notez que cette exigence s'applique également aux fournisseurs distincts contribuant à un ensemble groupé de bases de données. Si l'URL est fournie, cette directive peut être spécifiée plusieurs fois, fournissant une liste complète des serveurs participants et de leurs identifiants. Le nom d'hôte complet de chaque serveur doit être utilisé dans les URL fournies. Les identifiants sont utilisés dans le champ "replica id" de tous les CSN générés par le serveur spécifié. La valeur par défaut est zéro, ce qui n'est valide que pour la réplication à fournisseur unique. Exemple :
olcServerID: 1 ldap://ldap1.example.com
olcServerID: 2 ldap://ldap2.example.com
olcSockbufMaxIncoming: <entier>
Spécifie la taille maximale de PDU LDAP entrante pour les sessions anonymes. La valeur par défaut est 262143.
olcSockbufMaxIncomingAuth: <entier>
Spécifie la taille maximale de PDU LDAP entrante pour les sessions authentifiées. La valeur par défaut est 4194303.
olcTCPBuffer [listener=<URL>] [{read|write}=]<taille>
Spécifie la taille du tampon TCP. Une valeur globale pour les tampons TCP de lecture et d'écriture liés à n'importe quel écouteur est définie, sauf si l'écouteur est explicitement spécifié, ou si les qualificateurs de lecture ou d'écriture sont utilisés. Voir tcp(7) pour plus de détails. Notez que certains systèmes d'exploitation implémentent un réglage automatique des tampons TCP.
olcThreads: <entier>
Spécifie la taille maximale du pool de threads primaire. La valeur par défaut est 16 ; la valeur minimale est 2.
olcThreadQueues: <entier>
Spécifie le nombre de files d'attente de travail à utiliser pour le pool de threads primaire. La valeur par défaut est 1 et cela est généralement suffisant pour jusqu'à 8 cœurs de processeur. La valeur ne doit pas dépasser le nombre de processeurs dans le système.
olcToolThreads: <entier>
Spécifie le nombre maximal de threads à utiliser en mode outil. Cela ne doit pas être supérieur au nombre de processeurs dans le système. La valeur par défaut est 1.
olcWriteTimeout: <entier>
Spécifie le nombre de secondes à attendre avant de fermer de force une connexion avec une écriture en attente. Cela permet de récupérer de diverses conditions de blocage réseau. Une valeur de 0 désactive cette fonctionnalité. La valeur par défaut est 0.

OPTIONS TLS

Si slapd est compilé avec la prise en charge de la couche TLS (Transport Layer Security), il existe d'autres options que vous pouvez spécifier.

olcTLSCipherSuite: <spécification-suite-chiffrement>
Permet de configurer les chiffrements qui seront acceptés et leur ordre de préférence. <spécification-suite-chiffrement> doit être une spécification de chiffrement pour la bibliothèque TLS utilisée (OpenSSL ou GnuTLS). Exemple :
OpenSSL:
olcTLSCipherSuite: HIGH:MEDIUM:+SSLv2
GnuTLS:
olcTLSCiphersuite: SECURE256:!AES-128-CBC

Pour vérifier quels chiffrements une spécification donnée sélectionne dans OpenSSL, utilisez :

openssl ciphers -v <spécification-suite-chiffrement>

Avec GnuTLS, les spécifications disponibles se trouvent dans la page de manuel de gnutls-cli(1) (voir la description de l'option --priority).

Dans les anciennes versions de GnuTLS, où gnutls-cli ne prend pas en charge l'option --priority, vous pouvez obtenir la liste — plus limitée — des chiffrements en appelant :

gnutls-cli -l
olcTLSCACertificateFile: <nom-fichier>
Spécifie le fichier contenant les certificats de toutes les autorités de certification que slapd reconnaîtra. Le certificat de l'AC qui a signé le certificat du serveur doit être inclus parmi ces certificats. Si l'AC signataire n'était pas une AC de niveau supérieur (racine), les certificats de toute la séquence d'AC, de l'AC signataire à l'AC de niveau supérieur, doivent être présents. Plusieurs certificats sont simplement ajoutés au fichier ; l'ordre n'est pas significatif.
olcTLSCACertificatePath: <chemin>
Spécifie le chemin des répertoires contenant les certificats d'autorités de certification dans des fichiers individuels distincts. Habituellement, une seule de ces options ou olcTLSCACertificateFile est définie. Si les deux sont spécifiées, les deux emplacements seront utilisés. Plusieurs répertoires peuvent être spécifiés, séparés par un point-virgule.
olcTLSCACertificate: <certificat-AC>
Stocke un seul certificat d'AC qui sera approuvé par le serveur, au format DER. Si cette option est définie, les options olcTLSCACertificateFile et olcTLSCACertificatePath sont ignorées. Si plusieurs certificats d'AC sont requis, les options olcTLSCACertificateFile ou olcTLSCACertificatePath doivent être utilisées à la place de cette option.
olcTLSCertificateFile: <nom-fichier>
Spécifie le fichier contenant le certificat du serveur slapd.

Lors de l'utilisation d'OpenSSL, ce fichier peut également contenir un nombre quelconque de certificats intermédiaires après le certificat du serveur.

olcTLSCertificate: <certificat>
Stocke un seul certificat pour le serveur, au format DER. Si cette option est utilisée, l'option olcTLSCertificateFile est ignorée.
olcTLSCertificateKeyFile: <nom-fichier>
Spécifie le fichier contenant la clé privée du serveur slapd qui correspond au certificat du serveur spécifié. Si le fichier de clé privée est protégé par un mot de passe, le mot de passe doit être saisi manuellement au démarrage de slapd. Habituellement, la clé privée n'est pas protégée par un mot de passe, afin de permettre à slapd de démarrer sans intervention manuelle, il est donc d'une importance critique que le fichier soit protégé soigneusement.
olcTLSCertificateKey <clé>
Stocke la clé privée qui correspond au certificat du serveur. Si cette option est utilisée, l'option olcTLSCertificateKeyFile est ignorée.
olcTLSDHParamFile: <nom-fichier>
Cette directive spécifie le fichier contenant les paramètres pour l'échange de clés éphémères Diffie-Hellman. Ceci est requis pour utiliser un certificat DSA sur le serveur, ou un certificat RSA manquant l'utilisation de clé "chiffrement de clé". Notez que la définition de cette option peut également activer les échanges de clés Diffie-Hellman anonymes dans certaines suites de chiffrement non standard. Les échanges de clés anonymes doivent généralement être évités car ils ne fournissent aucune authentification réelle du client ou du serveur et aucune protection contre les attaques de l'homme du milieu. Vous devriez ajouter "!ADH" à vos suites de chiffrement pour vous assurer que ces suites ne sont pas utilisées.
olcTLSECName: <nom>
Spécifie le nom de la ou des courbes à utiliser pour l'échange de clés éphémères Diffie-Hellman sur courbes elliptiques. Cette option est uniquement utilisée pour OpenSSL. Cette option n'est pas utilisée avec GnuTLS ; les courbes peuvent être choisies dans la spécification de la suite de chiffrement GnuTLS.
olcTLSProtocolMin: <majeur>[.<mineur>]
Spécifie la version minimale du protocole SSL/TLS qui sera négociée. Si le serveur ne prend pas en charge au moins cette version, la négociation SSL échouera. Pour exiger TLS 1.x ou supérieur, définissez cette option sur 3.(x+1), par exemple : 
olcTLSProtocolMin: 3.2

exigerait TLS 1.1. Spécifier un minimum supérieur à celui pris en charge par l'implémentation OpenLDAP entraînera l'exigence du niveau le plus élevé qu'elle prend en charge. Cette directive est ignorée avec GnuTLS.

olcTLSRandFile: <nom-fichier>
Spécifie le fichier à partir duquel obtenir des bits aléatoires lorsque /dev/[u]random n'est pas
t disponible. Généralement défini sur le nom du socket EGD/PRNGD. La variable d'environnement RANDFILE peut également être utilisée pour spécifier le nom du fichier. Cette directive est ignorée avec GnuTLS.
olcTLSVerifyClient: <level>
Spécifie quelles vérifications effectuer sur les certificats clients dans une session TLS entrante, le cas échéant. Le <level> peut être spécifié comme l'un des mots-clés suivants :
never
C'est la valeur par défaut. slapd ne demandera pas de certificat au client.
allow
Le certificat client est demandé. Si aucun certificat n'est fourni, la session se déroule normalement. Si un certificat invalide est fourni, il sera ignoré et la session se déroulera normalement.
try
Le certificat client est demandé. Si aucun certificat n'est fourni, la session se déroule normalement. Si un certificat invalide est fourni, la session est immédiatement terminée.
demand | hard | true
Ces mots-clés sont tous équivalents, pour des raisons de compatibilité. Le certificat client est demandé. Si aucun certificat n'est fourni, ou si un certificat invalide est fourni, la session est immédiatement terminée.

Notez qu'un certificat client valide est requis pour utiliser le mécanisme d'authentification SASL EXTERNAL avec une session TLS. En tant que tel, un réglage olcTLSVerifyClient non par défaut doit être choisi pour activer l'authentification SASL EXTERNAL.

olcTLSCRLCheck: <level>
Spécifie si la Liste de Révocation de Certificats (CRL) de l'AC doit être utilisée pour vérifier si les certificats clients n'ont pas été révoqués. Ceci requiert que le paramètre olcTLSCACertificatePath soit défini. Ce paramètre est ignoré avec GnuTLS. <level> peut être spécifié comme l'un des mots-clés suivants :
none
Aucune vérification CRL n'est effectuée.
peer
Vérifie la CRL du certificat du pair.
all
Vérifie la CRL pour toute la chaîne de certificats.
olcTLSCRLFile: <filename>
Spécifie un fichier contenant une Liste de Révocation de Certificats à utiliser pour vérifier que les certificats n'ont pas été révoqués. Ce paramètre n'est valide qu'en utilisant GnuTLS.

OPTIONS DE MODULE DYNAMIQUES

Si slapd est compilé avec --enable-modules, alors les entrées liées aux modules seront disponibles. Ces entrées sont nommées cn=module{x},cn=config et doivent avoir l'objectClass olcModuleList. Une entrée doit être créée par olcModulePath. Normalement, le moteur de configuration génère automatiquement l'index "{x}" dans le RDN, il peut donc être omis lors du chargement initial de ces entrées.

Spécifie le nom d'un module chargeable dynamiquement à charger et les arguments supplémentaires s'ils sont pris en charge par le module. Spécifie une liste de répertoires dans lesquels rechercher les modules chargeables. Typiquement, le chemin est séparé par des deux-points, mais cela dépend du système d'exploitation. La valeur par défaut est /usr/lib/openldap, où l'installation standard d'OpenLDAP placera ses modules.

OPTIONS DE SCHÉMA

Les définitions de schéma sont créées comme des entrées dans le sous-arbre cn=schema,cn=config. Ces entrées doivent avoir l'objectClass olcSchemaConfig. Comme mentionné ci-dessus, l'entrée réelle cn=schema,cn=config est prédéfinie et toute valeur qui lui est spécifiée est ignorée.

Spécifie une règle de contenu DIT en utilisant la syntaxe LDAPv3 définie dans la RFC 4512. L'analyseur slapd étend la définition de la RFC 4512 en autorisant les formes textuelles ainsi que les OID numériques à être utilisées pour l'OID de l'attribut et l'OID de la syntaxe de l'attribut. (Voir la description de olcObjectIdentifier.)

Spécifie une syntaxe LDAP en utilisant la syntaxe LDAPv3 définie dans la RFC 4512. L'analyseur slapd étend la définition de la RFC 4512 en autorisant les formes textuelles ainsi que les OID numériques à être utilisées pour l'OID de la syntaxe. (Voir la description de objectidentifier.) L'analyseur slapd respecte également l'extension X-SUBST (une extension spécifique à OpenLDAP), qui permet d'utiliser l'attribut olcLdapSyntaxes pour définir une syntaxe non implémentée avec une autre syntaxe, la valeur de l'extension substitute-syntax, comme remplacement temporaire. Définit un nom textuel qui équivaut à l'OID donné. Le texte peut être utilisé à la place de l'OID numérique dans les définitions de classes d'objet et d'attributs. Le nom peut également être utilisé avec un suffixe de la forme ":xx" auquel cas la valeur "oid.xx" sera utilisée.

OPTIONS GÉNÉRALES DE BACKEND

Les options dans ces entrées s'appliquent uniquement à la configuration d'un seul type de backend. Tous les backends peuvent prendre en charge cette classe d'options, mais actuellement seul back-mdb le fait. L'entrée doit être nommée olcBackend=<databasetype>,cn=config et doit avoir l'objectClass olcBackendConfig. <databasetype> doit être l'un de asyncmeta, config, dnssrv, ldap, ldif, mdb, meta, monitor, null, passwd, perl, relay, sock, sql, ou wt. À l'heure actuelle, seul back-mdb implémente des options de ce type, donc cette entrée ne doit pas être utilisée pour d'autres backends.

OPTIONS DE BASE DE DONNÉES

Les options de base de données sont définies dans des entrées nommées olcDatabase={x}<databasetype>,cn=config et doivent avoir l'objectClass olcDatabaseConfig. Normalement, le moteur de configuration génère automatiquement l'index "{x}" dans le RDN, il peut donc être omis lors du chargement initial de ces entrées.

La base de données front-end spéciale est toujours numérotée "{-1}" et la base de données de configuration est toujours numérotée "{0}".

OPTIONS GLOBALES DE BASE DE DONNÉES

Les options de cette section peuvent être définies dans la base de données spéciale "frontend" et héritées dans toutes les autres bases de données. Ces options peuvent être modifiées par des réglages ultérieurs dans chaque base de données spécifique. L'entrée front-end doit être nommée olcDatabase=frontend,cn=config et doit avoir l'objectClass olcFrontendConfig.

olcAccess: to <what> [ by <who> <access> <control> ]+
Accorde l'accès (spécifié par <access>) à un ensemble d'entrées et/ou d'attributs (spécifié par <what>) par un ou plusieurs demandeurs (spécifié par <who>). Si aucun contrôle d'accès n'est présent, la politique par défaut permet à quiconque de lire n'importe quoi mais restreint les mises à jour à rootdn. (par exemple, "olcAccess: to * by * read"). Voir slapd.access(5) et le "Guide de l'administrateur OpenLDAP" pour plus de détails.

Les contrôles d'accès définis dans le front-end sont ajoutés à tous les contrôles d'accès définis sur les bases de données spécifiques. Le rootdn d'une base de données peut toujours lire et écrire TOUT dans cette base de données.

Une attention particulière doit être portée aux contrôles d'accès sur la base de données de configuration. Spécifie une regexp pour la recherche de la correspondance d'autorisation. Le motif de la regexp et la chaîne à rechercher dépendent du type de réécriture. Voir slapd.replacements(5) pour plus de détails. Cette option est autorisée uniquement dans l'entrée frontend.
olcConcurrency: <integer>
Spécifie le nombre de threads qui peuvent accéder à la base de données. Cela ne s'applique qu'aux bases de données à accès concurrentiel (par exemple, MDB).
olcConnectivity: <bind>
Spécifie les exigences de connectivité pour les opérations de recherche. Par exemple, olcConnectivity: bind exige qu'une opération de liaison soit effectuée avant que les opérations de répertoire puissent être effectuées. Ceci est seulement autorisé dans l'entrée frontend.
olcDbDir: <path>
Spécifie le chemin du répertoire dans lequel les fichiers de base de données seront stockés. Les valeurs par défaut sont dans le répertoire de données du serveur.
olcExtraAttrs: <attr>
Liste les attributs qui doivent être ajoutés aux requêtes de recherche. Les backends de stockage local renvoient l'entrée entière au frontend. Le frontend se charge de ne renvoyer que les attributs demandés qui sont autorisés par les ACL. Cependant, des fonctionnalités telles que la vérification d'accès peuvent nécessiter des attributs spécifiques qui ne sont pas automatiquement renvoyés par les backends de stockage distants, tels que les backends proxy, etc. <attr> est un attribut nécessaire à des fins internes et doit donc toujours être collecté, même lorsqu'il n'est pas explicitement demandé par les clients. olcPasswordHash: <hash> [<hash>...]
Cette option configure un ou plusieurs hachages à utiliser pour la génération des mots de passe utilisateur stockés dans l'attribut userPassword lors du traitement des opérations étendues de modification de mot de passe LDAP (RFC 3062). Le <hash> doit être l'un des éléments suivants : {SSHA}, {SHA}, {SMD5}, {MD5}, {CRYPT}, et {CLEARTEXT}. La valeur par défaut est {SSHA}.

{SHA} et {SSHA} utilisent l'algorithme SHA-1 (FIPS 160-1), ce dernier avec une graine.

{MD5} et {SMD5} utilisent l'algorithme MD5 (RFC 1321), ce dernier avec une graine.

{CRYPT} utilise crypt(3).

{CLEARTEXT} indique que le nouveau mot de passe doit être ajouté à userPassword en texte clair.

Notez que cette option ne modifie pas la gestion normale par les applications utilisateur de userPassword lors des opérations LDAP Add, Modify, ou autres opérations LDAP. Ce réglage est autorisé uniquement dans l'entrée frontend.

Cette option met la base de données en mode "lecture seule". Toute tentative de modification de la base de données renverra une erreur "récalcitrant à exécuter". Par défaut, olcReadOnly est FALSE. Notez que lorsque cette option est définie sur TRUE dans le frontend, elle ne peut pas être réinitialisée sans redémarrer le serveur, car les écritures supplémentaires dans la base de données de configuration seront rejetées.

Spécifie un ensemble de conditions requises (par défaut aucune). LDAPv3 exige que la session utilise LDAP version 3. authc exige une authentification avant les opérations de répertoire. SASL exige une authentification SASL avant les opérations de répertoire. strong exige une authentification forte avant les opérations de répertoire. Le mot-clé strong permet une authentification "simple" protégée ainsi qu'une authentification SASL. none peut être utilisé pour ne requérir aucune condition (utile pour effacer les conditions définies globalement dans une base de données particulière) ; il doit apparaître en premier dans la liste des conditions.

Spécifie une liste d'opérations restreintes. Les restrictions sur une base de données spécifique remplacent tout réglage du frontend. Les opérations peuvent être parmi add, bind, compare, delete, extended[=<OID>], modify, rename, search, ou les pseudo-opérations spéciales read et write, qui résument respectivement les opérations de lecture et d'écriture. L'utilisation de restrict write équivaut à olcReadOnly: TRUE (voir ci-dessus). Le mot-clé extended permet d'indiquer l'OID de l'opération spécifique à restreindre.
olcSchemaDN: <dn>
Spécifie le nom distinctif de la sous-entrée de schéma qui contrôle les entrées sur ce serveur. La valeur par défaut est "cn=Subschema".
olcSecurity: <factors>
Spécifie un ensemble de facteurs de force de sécurité (séparés par des espaces blancs) à exiger (voir l'option minssf de olcSaslSecprops pour une description des facteurs de force de sécurité). La directive peut être spécifiée globalement et/ou par base de données. ssf=<n> spécifie le facteur de force de sécurité global. transport=<n> spécifie le facteur de force de sécurité du transport. tls=<n> spécifie le facteur de force de sécurité TLS. sasl=<n> spécifie le facteur de force de sécurité SASL. update_ssf=<n> spécifie le facteur de force de sécurité global requis pour les mises à jour du répertoire. update_transport=<n> spécifie le facteur de force de sécurité du transport requis pour les mises à jour du répertoire. update_tls=<n> spécifie le facteur de force de sécurité TLS requis pour les mises à jour du répertoire. update_sasl=<n> spécifie le facteur de force de sécurité SASL requis pour les mises à jour du répertoire. simple_bind=<n> spécifie le facteur de force de sécurité requis pour l'authentification par nom d'utilisateur/mot de passe simple. Notez que le facteur transport mesure la sécurité fournie par le transport sous-jacent, par exemple ldapi:// (et éventuellement IPSEC). Il n'est normalement pas utilisé.
olcSizeLimit: {<integer>|unlimited}
olcSizeLimit: size[.{soft|hard}]=<integer> [...]
Spécifie le nombre maximum d'entrées à renvoyer à partir d'une opération de recherche. La limite de taille par défaut est 500. Utilisez unlimited pour spécifier aucune limite. Le second format permet un réglage fin des limites de taille. Si aucun qualificateur spécial n'est spécifié, les limites douce et dure sont définies. Des arguments supplémentaires peuvent être ajoutés dans la même valeur. Des qualificateurs supplémentaires sont disponibles ; voir olcLimits pour une explication de tous les différents indicateurs.

Spécifie une liste d'attributs multivalués dont les valeurs seront toujours maintenues dans un ordre trié. L'ordre de tri résultant dépend de la syntaxe et des règles de correspondance des attributs et peut ne pas correspondre à l'ordre lexical ou à tout autre ordre reconnaissable. Ce réglage est autorisé uniquement dans l'entrée frontend.
olcTimeLimit: {<integer>|unlimited}
olcTimeLimit: time[.{soft|hard}]=<integer> [...]
Spécifie le nombre maximum de secondes (en temps réel) que slapd passera à répondre à une requête de recherche. La limite de temps par défaut est 3600. Utilisez unlimited pour spécifier aucune limite. Le second format permet un réglage fin des limites de temps. Des arguments supplémentaires peuvent être ajoutés dans la même valeur. OPTIONS GÉNÉRALES DE BASE DE DONNÉES

Les options de cette section s'appliquent uniquement à la base de données spécifique pour laquelle elles sont définies. Elles sont prises en charge par tous les types de backends. Toutes les options globales de base de données peuvent également être utilisées ici.

olcAddContentAcl: TRUE | FALSE
Contrôle si les opérations d'ajout effectuent des vérifications ACL sur le contenu de l'entrée ajoutée. Cette vérification est désactivée par défaut. Voir la page de manuel slapd.access(5) pour plus de détails sur les exigences ACL pour les opérations d'ajout.
olcHidden: TRUE | FALSE
Contrôle si la base de données sera utilisée pour répondre aux requêtes. Une base de données qui est cachée ne sera jamais sélectionnée pour répondre à des requêtes, et tout suffixe configuré sur la base de données sera ignoré dans les vérifications de conflits avec d'autres bases de données. Par défaut, olcHidden est FALSE.
olcLastMod: TRUE | FALSE
Contrôle si slapd maintiendra automatiquement les attributs modifiersName, modifyTimestamp, creatorsName et createTimestamp pour les entrées. Il contrôle également les attributs entryCSN et entryUUID, qui sont nécessaires au fournisseur syncrepl. Par défaut, olcLastMod est TRUE.
olcLastBind: TRUE | FALSE
Contrôle si slapd maintiendra automatiquement l'attribut pwdLastSuccess pour les entrées. Par défaut, olcLastBind est FALSE.
olcLastBindPrecision: <integer>
Si olcLastBind est activé, spécifie la fréquence de mise à jour de pwdLastSuccess. Plus de integer secondes doivent s'être écoulées depuis la dernière liaison réussie. Dans un environnement répliqué avec une activité de liaison fréquente, il peut être utile de définir cette valeur sur une valeur élevée.
olcLimits: <selector> <limit> [<limit> [...]]
Spécifie les limites de temps et de taille basées sur l'initiateur de l'opération ou le DN de base. L'argument <selector> peut être l'un des éléments suivants :
anonymous | users | [<dnspec>=]<pattern> | group[/oc[/at]]=<pattern>
avec
<dnspec> ::= dn[.<type>][.<style>]
<type> ::= self | this
<style> ::= exact | base | onelevel | subtree | children | regex | anonymous
Le type de DN self est la valeur par défaut et signifie l'utilisateur lié, tandis que this signifie le DN de base de l'opération. Le terme anonymous correspond à tous les clients non authentifiés. Le terme users correspond à tous les clients authentifiés ; sinon, un motif DN exact est supposé, sauf indication contraire en qualifiant la chaîne de clé (optionnelle) dn avec exact ou base (qui sont des synonymes), pour exiger une correspondance exacte ; avec onelevel, pour exiger une correspondance de profondeur exactement un niveau ; avec subtree, pour autoriser une correspondance de n'importe quel niveau de profondeur, y compris la correspondance exacte ; avec children, pour autoriser une correspondance de n'importe quel niveau de profondeur, sans inclureg la correspondance exacte ; regex exige explicitement la correspondance (par défaut) basée sur un modèle d'expression régulière POSIX (« extended »). Enfin, anonymous correspond aux opérations non liées ; le champ pattern est ignoré. Le même comportement est obtenu en utilisant la forme anonymous de la clause <selector>. Le terme group, avec les champs optionnels objectClass oc et attributeType at, suivi de pattern, définit les limites pour tout DN répertorié dans les valeurs de l'attribut at (par défaut member) de l'objet class group oc (par défaut groupOfNames) dont le DN correspond exactement au pattern.

Les limites actuellement prises en charge sont size et time.

La syntaxe des limites de temps est time[.{soft|hard}]=<entier>, où entier est le nombre de secondes que slapd passera à répondre à une requête de recherche. Si aucune limite de temps n'est explicitement demandée par le client, la limite soft est utilisée ; si la limite de temps demandée dépasse la limite hard, la valeur de la limite est utilisée à la place. Si la limite hard est définie sur le mot-clé soft, la limite soft est utilisée dans les deux cas ; si elle est définie sur le mot-clé unlimited, aucune limite hard n'est appliquée. Les demandes explicites de limites de temps inférieures ou égales à la limite hard sont respectées. Si aucun spécificateur de limite n'est défini, la valeur est attribuée à la limite soft et la limite hard est définie sur soft, pour préserver le comportement d'origine.

La syntaxe des limites de taille est size[.{soft|hard|unchecked}]=<entier>, où entier est le nombre maximum d'entrées que slapd retournera en répondant à une requête de recherche. Si aucune limite de taille n'est explicitement demandée par le client, la limite soft est utilisée ; si la limite de taille demandée dépasse la limite hard, la valeur de la limite est utilisée à la place. Si la limite hard est définie sur le mot-clé soft, la limite soft est utilisée dans les deux cas ; si elle est définie sur le mot-clé unlimited, aucune limite hard n'est appliquée. Les demandes explicites de limites de taille inférieures ou égales à la limite hard sont respectées. Le spécificateur unchecked définit une limite sur le nombre de candidats qu'une requête de recherche est autorisée à examiner. La raison d'être est que les recherches d'attributs non correctement indexés peuvent entraîner de grands ensembles de candidats, qui doivent être examinés par slapd(8) pour déterminer s'ils correspondent ou non au filtre de recherche. La limite unchecked fournit un moyen de rejeter de telles opérations avant même qu'elles ne soient lancées. Si les candidats sélectionnés dépassent la limite unchecked, la recherche sera abandonnée avec Unwilling to perform. Si elle est définie sur le mot-clé unlimited, aucune limite n'est appliquée (par défaut). Si elle est définie sur disabled, la recherche n'est même pas effectuée ; cela peut être utilisé pour interdire les recherches d'un ensemble spécifique d'utilisateurs. Si aucun spécificateur de limite n'est défini, la valeur est attribuée à la limite soft et la limite hard est définie sur soft, pour préserver le comportement d'origine.

En cas de non-correspondance, les limites globales sont utilisées. Les valeurs par défaut sont les mêmes que pour olcSizeLimit et olcTimeLimit ; aucune limite n'est définie sur unchecked.

Si le contrôle pagedResults est demandé, la limite de taille hard est utilisée par défaut, car la demande d'une taille de page spécifique est considérée comme une demande explicite de limitation du nombre d'entrées à retourner. Cependant, la limite de taille s'applique au nombre total d'entrées renvoyées dans la recherche, et non à une seule page. Des limites de taille supplémentaires peuvent être appliquées ; la syntaxe est size.pr={<entier>|noEstimate|unlimited}, où entier est la taille de page maximale si aucune limite explicite n'est définie ; le mot-clé noEstimate empêche le serveur de renvoyer une estimation du nombre total d'entrées qui pourraient être renvoyées (remarque : l'implémentation actuelle ne renvoie aucune estimation). Le mot-clé unlimited indique qu'aucune limite n'est appliquée à la taille de page du contrôle pagedResults. La syntaxe size.prtotal={<entier>|hard|unlimited|disabled} permet de définir une limite sur le nombre total d'entrées que le contrôle pagedResults renverra. Par défaut, elle est définie sur la limite hard qui utilisera la valeur size.hard. Lorsqu'elle est définie, entier est le nombre maximum d'entrées que la recherche entière avec le contrôle pagedResults peut renvoyer. Utilisez unlimited pour autoriser un nombre illimité d'entrées à être renvoyées, par exemple pour permettre l'utilisation du contrôle pagedResults comme moyen de contourner les limitations de taille des recherches régulières ; le mot-clé disabled désactive le contrôle, c'est-à-dire qu'aucun résultat paginé ne peut être renvoyé. Notez que le nombre total d'entrées renvoyées lorsque le contrôle pagedResults est demandé ne peut pas dépasser la limite de taille hard des recherches régulières, sauf si elle est étendue par le commutateur prtotal.

L'instruction olcLimits est généralement utilisée pour permettre à un nombre illimité d'entrées d'être retourné par les recherches effectuées avec l'identité utilisée par le consommateur à des fins de synchronisation au moyen du protocole de synchronisation de contenu LDAP RFC 4533 (voir olcSyncrepl pour plus de détails).

Lors de l'utilisation de bases de données subordonnées, il est nécessaire que toutes les limites qui doivent être appliquées à la fois au parent et à ses subordonnés soient définies à la fois dans le parent et dans ses subordonnés. Sinon, les paramètres des bases de données subordonnées ne sont pas respectés.

olcMaxDerefDepth: <profondeur>
Spécifie le nombre maximum d'alias à déréférencer lors de la tentative de résolution d'une entrée, utilisé pour éviter les boucles d'alias infinies. La valeur par défaut est de 15.
olcMultiProvider: TRUE | FALSE
Cette option met une base de données consommateur en mode Multi-Provider. Les opérations de mise à jour seront acceptées de la part de n'importe quel utilisateur, pas seulement de l'updatedn. La base de données doit déjà être configurée comme un consommateur syncrepl avant que ce mot-clé puisse être défini. Ce mode nécessite également la configuration d'un olcServerID (voir ci-dessus). Par défaut, ce paramètre est FALSE.
olcMonitoring: TRUE | FALSE
Cette option active la surveillance spécifique à la base de données dans l'entrée liée à la base de données actuelle dans le sous-arbre « cn=Databases,cn=Monitor » de la base de données de surveillance, si la base de données de surveillance est activée. Actuellement, seule la base de données MDB fournit une surveillance spécifique à la base de données. Si la surveillance est prise en charge par le backend, elle est TRUE par défaut, sinon FALSE.
olcPlugin: <type_plugin> <chemin_lib> <fonction_init> [<arguments>]
Configure un plugin SLAPI. Voir la page de manuel slapd.plugin(5) pour plus d'informations.
olcRootDN: <dn>
Spécifiez le nom distinctif qui n'est pas soumis aux restrictions de contrôle d'accès ou de limite administrative pour les opérations sur cette base de données. Ce DN peut ou peut ne pas être associé à une entrée. Un DN racine vide (par défaut) spécifie qu'aucun accès racine ne doit être accordé. Il est recommandé de ne spécifier le rootdn que lorsque nécessaire (par exemple, lors du premier remplissage d'une base de données). Si le rootdn se trouve dans un namingContext (suffixe) de la base de données, un mot de passe de liaison simple peut également être fourni en utilisant la directive olcRootPW. De nombreuses fonctionnalités optionnelles, y compris syncrepl, nécessitent que le rootdn soit défini pour la base de données. Le olcRootDN de la base de données cn=config est par défaut cn=config lui-même.
olcRootPW: <mot_de_passe>
Spécifiez un mot de passe (ou un hachage du mot de passe) pour le rootdn. Le mot de passe ne peut être défini que si le rootdn se trouve dans le namingContext (suffixe) de la base de données. Cette option accepte tous les formats RFC 2307 userPassword connus du serveur (voir la description de olcPasswordHash) ainsi que le texte clair. slappasswd(8) peut être utilisé pour générer un hachage d'un mot de passe. Les mots de passe en texte clair et {CRYPT} ne sont pas recommandés. S'il est vide (par défaut), l'authentification du DN racine se fait par d'autres moyens (par exemple, SASL). L'utilisation de SASL est encouragée.
olcSubordinate: [TRUE | FALSE | advertise]
Spécifiez que la base de données backend actuelle est subordonnée à une autre base de données backend. Une base de données subordonnée ne peut avoir qu'un seul suffixe. Cette option peut être utilisée pour coller plusieurs bases de données en un seul namingContext. Si le suffixe de la base de données actuelle se trouve dans le namingContext d'une base de données supérieure, les recherches sur la base de données supérieure seront également propagées à la subordonnée. Toutes les bases de données associées à un même namingContext doivent avoir des rootdns identiques. Le comportement des autres opérations LDAP n'est pas affecté par ce paramètre. En particulier, il n'est pas possible d'utiliser moddn pour déplacer une entrée d'une subordonnée à une autre subordonnée au sein du namingContext.

Si le drapeau optionnel advertise est fourni, le naming context de cette base de données est annoncé dans le DSE racine. Par défaut, ce contexte de base de données est masqué, de sorte que seul le contexte supérieur est visible.

Si les outils slap slapcat(8), slapadd(8), slapmodify(8), ou slapindex(8) sont utilisés sur la base de données supérieure, toutes les subordonnées collées qui prennent en charge ces outils sont également ouvertes.

Les bases de données qui sont collées ensemble doivent généralement être configurées avec les mêmes index (en supposant qu'elles prennent en charge l'indexation), même pour les attributs qui n'existent que dans certaines de ces bases de données. En général, toutes les bases de données collées doivent être configurées de la manière la plus similaire possible, car l'intention est de donner l'apparence d'un répertoire unique.

Notez que la fonctionnalité subordonnée est implémentée en interne par la surcouche glue et, en tant que telle, son comportement interagira avec les autres surcouches utilisées. Par défaut, la surcouche glue est automatiquement configurée comme la dernière surcouche sur la base de données supérieure. Sa position sur la base de données peut être explicitement configurée en définissant une directive overlay glue à la position souhaitée. Cette configuration explicite est nécessaire, par exemple, lorsque vous utilisez la surcouche syncprov, qui doit suivre glue pour fonctionner sur toutes les bases de données collées. Par exemple :

dn: olcDatabase={1}mdb,cn=config
olcSuffix: dc=example,dc=com
...
dn: olcOverlay={0}glue,olcDatabase={1}mdb,cn=config
...
dn: olcOverlay={1}syncprov,olcDatabase={1}mdb,cn=config
...
Voir la section Overlays ci-dessous pour plus de détails.
olcSuffix: <suffixe_dn>
Spécifiez le suffixe DN des requêtes qui seront transmises à ce backend base de données. Plusieurs lignes suffixe peuvent être fournies et au moins une est requise pour chaque définition de base de données.

Si le suffixe d'une base de données est "à l'intérieur" de celui d'une autre, la base de données avec le suffixe intérieur doit apparaître en premier dans le fichier de configuration. Vous pouvez également souhaiter lier de telles bases de données avec l'attribut olcSubordinate.

olcSyncUseSubentry: TRUE | FALSE
Stocke le contexteCSN de syncrepl dans une sous-entrée au lieu de l'entrée de contexte de la base de données. Le RDN de la sous-entrée sera "cn=ldapsync". La valeur par défaut est FALSE, signifiant que le contextCSN est stocké dans l'entrée de contexte.

olcSyncrepl: rid=<ID de réplica> provider=ldap[s]://<nom d'hôte>[:port] searchbase=<DN de base> [type=refreshOnly|refreshAndPersist] [interval=jj:hh:mm:ss] [retry=[<intervalle de nouvelle tentative> <# de nouvelles tentatives>]+] [filter=<chaîne de filtre>] [scope=sub|one|base|subord] [attrs=<liste d'attributs>] [exattrs=<liste d'attributs>] [attrsonly] [sizelimit=<limite>] [timelimit=<limite>] [schemachecking=on|off] [network-timeout=<secondes>] [timeout=<secondes>] [tcp-user-timeout=<millisecondes>] [bindmethod=simple|sasl] [binddn=<dn>] [saslmech=<mech>] [authcid=<identité>] [authzid=<identité>] [credentials=<mot de passe>] [realm=<domaine>] [secprops=<propriétés>] [keepalive=<inactif>:<sondes>:<intervalle>] [starttls=yes|critical] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<chiffrements>] [tls_ecname=<noms>] [tls_crlcheck=none|peer|all] [tls_protocol_min=<majeur>[.<mineur>]] [suffixmassage=<DN réel>] [logbase=<DN de base>] [logfilter=<chaîne de filtre>] [syncdata=default|accesslog|changelog] [lazycommit]

Spécifie la base de données actuelle en tant que consommateur qui est maintenu à jour avec le contenu du fournisseur en établissant le slapd(8) actuel comme site de réplication consommateur exécutant un moteur de réplication syncrepl. Le contenu du consommateur est synchronisé avec le contenu du fournisseur en utilisant le protocole de synchronisation de contenu LDAP. Reportez-vous au "Guide de l'administrateur OpenLDAP" pour des informations détaillées sur la configuration d'un service d'annuaire slapd répliqué à l'aide du moteur de réplication syncrepl.

rid identifie la directive syncrepl actuelle au sein du site consommateur de réplication. C'est un entier non négatif ne dépassant pas 999 (limité à trois chiffres décimaux).

provider spécifie le site fournisseur de réplication contenant le contenu du fournisseur sous forme d'URI LDAP. Si <port> n'est pas spécifié, le numéro de port LDAP standard (389 ou 636) est utilisé.

Le contenu du consommateur syncrepl est défini à l'aide d'une spécification de recherche comme son jeu de résultats. Le consommateur slapd enverra des requêtes de recherche au fournisseur slapd conformément à la spécification de recherche. La spécification de recherche comprend les paramètres searchbase, scope, filter, attrs, attrsonly, sizelimit et timelimit, comme dans la spécification de recherche normale. L'option exattrs peut également être utilisée pour spécifier les attributs qui doivent être omis des entrées entrantes. Le scope est par défaut sub, le filter est par défaut (objectclass=*), et il n'y a pas de searchbase par défaut. La liste attrs est par défaut "*»,+"" pour renvoyer tous les attributs utilisateur et opérationnels, et attrsonly et exattrs ne sont pas définis par défaut. Les sizelimit et timelimit n'acceptent que "illimité" et des entiers positifs, et les deux sont par défaut "illimité". Les paramètres sizelimit et timelimit définissent une limitation demandée par le consommateur sur le nombre d'entrées qui peuvent être renvoyées par l'opération de synchronisation de contenu LDAP ; ceux-ci doivent être laissés inchangés par défaut, sinon la réplication pourrait ne jamais réussir. Notez, cependant, que toutes les limites côté fournisseur pour l'identité de réplication seront appliquées par le fournisseur indépendamment des limites demandées par l'opération de synchronisation de contenu LDAP, tout comme pour toute autre opération de recherche.

Le protocole de synchronisation de contenu LDAP comporte deux types d'opérations. Dans l'opération refreshOnly, la prochaine opération de recherche de synchronisation est reprogrammée périodiquement à un intervalle de temps (spécifié par le paramètre interval ; 1 jour par défaut) après la fin de chaque opération de synchronisation. Dans l'opération refreshAndPersist, une recherche de synchronisation reste persistante dans le slapd du fournisseur. Les mises à jour ultérieures du fournisseur généreront des searchResultEntry vers le slapd du consommateur en tant que réponses de recherche à la recherche de synchronisation persistante. Si la recherche initiale échoue en raison d'une erreur, la prochaine opération de recherche de synchronisation est reprogrammée périodiquement à un intervalle de temps (spécifié par le paramètre interval ; 1 jour par défaut)

Si une erreur se produit pendant la réplication, le consommateur tentera de se reconnecter conformément au paramètre retry, qui est une liste de paires <intervalle de nouvelle tentative> et <# de nouvelles tentatives>. Par exemple, retry="60 10 300 3" permet au consommateur de réessayer toutes les 60 secondes pendant les 10 premières fois, puis de réessayer toutes les 300 secondes pendant les 3 fois suivantes avant d'arrêter d'essayer. Le '+' dans <# de nouvelles tentatives> signifie un nombre indéfini de nouvelles tentatives jusqu'au succès. Si aucun retry n'est spécifié, par défaut syncrepl réessaie toutes les heures indéfiniment.

La vérification du schéma peut être appliquée sur le site consommateur LDAP Sync en activant le paramètre schemachecking. La valeur par défaut est off. Schema checking on signifie que les entrées répliquées doivent avoir une objectClass structurelle, doivent respecter les exigences d'objectClass en termes d'attributs requis/autorisés, et que les attributs de dénomination et les valeurs distinguées doivent être présents. Par conséquent, la vérification du schéma doit être off lorsque la réplication partielle est utilisée.

Le paramètre network-timeout définit combien de temps le consommateur attendra pour établir une connexion réseau avec le fournisseur. Une fois la connexion établie, le paramètre timeout détermine combien de temps le consommateur attendra que la demande Bind initiale soit terminée. Les valeurs par défaut pour ces paramètres proviennent de ldap.conf(5). Le paramètre tcp-user-timeout, s'il est non nul, correspond à TCP_USER_TIMEOUT défini sur les connexions cibles, remplaçant le paramètre du système d'exploitation. Seuls certains systèmes prennent en charge la personnalisation de ce paramètre ; il est ignoré sinon et les paramètres globaux du système sont utilisés.

Une méthode de connexion bindmethod de simple nécessite les options binddn et credentials et ne doit être utilisée que lorsque des services de sécurité adéquats (par exemple, TLS ou IPSEC) sont en place. RAPPEL : les identifiants de connexion simple doivent être en clair ! Une méthode de connexion bindmethod de sasl nécessite l'option saslmech. Selon le mécanisme, une identité d'authentification et/ou des identifiants peuvent être spécifiés à l'aide de authcid et credentials. Le paramètre authzid peut être utilisé pour spécifier une identité d'autorisation. Des propriétés de sécurité spécifiques (comme avec le mot-clé sasl-secprops ci-dessus) pour une connexion SASL peuvent être définies avec l'option secprops. Un domaine SASL non par défaut peut être défini avec l'option realm. L'identité utilisée pour la synchronisation par le consommateur doit être autorisée à recevoir un nombre illimité d'entrées en réponse à une requête de recherche. Le fournisseur, en plus d'autoriser l'authentification de l'identité syncrepl, doit accorder à cette identité les privilèges d'accès appropriés aux données qui sont répliquées (directive access), et les limites de temps et de taille appropriées. Cela peut être réalisé soit en autorisant des sizelimit et timelimit illimités, soit en définissant une instruction limits appropriée dans la configuration du consommateur (voir sizelimit et limits pour les détails).

Le paramètre keepalive définit les valeurs de idle, probes et interval utilisées pour vérifier si une socket est active ; idle est le nombre de secondes pendant lesquelles une connexion doit rester inactive avant que TCP ne commence à envoyer des sondes keepalive ; probes est le nombre maximum de sondes keepalive que TCP doit envoyer avant de fermer la connexion ; interval est l'intervalle en secondes entre les sondes keepalive individuelles. Seuls certains systèmes prennent en charge la personnalisation de ces valeurs ; le paramètre keepalive est ignoré sinon, et les paramètres globaux du système sont utilisés.

Le paramètre starttls spécifie l'utilisation de l'opération étendue StartTLS pour établir une session TLS avant de se connecter au fournisseur. Si l'argument critical est fourni, la session sera interrompue si la requête StartTLS échoue. Sinon, la session syncrepl continue sans TLS. Le paramètre tls_reqcert est par défaut "demand", le paramètre tls_reqsan est par défaut "allow", et les autres paramètres TLS sont par défaut les mêmes que les paramètres TLS principaux de slapd.

Le paramètre suffixmassage permet au consommateur d'extraire des entrées d'un répertoire distant dont le suffixe DN diffère du répertoire local. La partie des DN des entrées distantes qui correspond au searchbase sera remplacée par le DN de suffixemassage.

Plutôt que de répliquer des entrées entières, le consommateur peut interroger les journaux des modifications de données. Ce mode de fonctionnement est appelé delta syncrepl. En plus des paramètres ci-dessus, les paramètres logbase et logfilter doivent être définis de manière appropriée pour le journal qui sera utilisé. Le paramètre syncdata doit être défini sur "accesslog" si le journal est conforme au format de journal slapo-accesslog(5), ou "changelog" si le journal est conforme au format obsolète changelog. Si le paramètre syncdata est omis ou défini sur "default", les paramètres de journal sont ignorés.

Le paramètre lazycommit indique à la base de données sous-jacente qu'elle peut stocker les modifications sans effectuer de vidage complet après chaque modification. Cela peut améliorer les performances du consommateur, tout en sacrifiant la sécurité ou la durabilité.

olcUpdateDN: <dn>
Cette option n'est applicable que dans une base de données réplique. Elle spécifie le DN autorisé à mettre à jour (sous réserve des contrôles d'accès) la réplique. Elle n'est nécessaire que dans certains scénarios de réplication en mode push. En général, ce DN ne doit pas être le même que le rootdn utilisé au fournisseur.
olcUpdateRef: <url>
Spécifiez la référence à retourner lorsque slapd(8) est invité à modifier une base de données locale répliquée. Si plusieurs valeurs sont spécifiées, chaque URL est fournie.

OPTIONS SPÉCIFIQUES À LA BASE DE DONNÉES

Chaque base de données peut autoriser des options de configuration spécifiques ; elles sont documentées séparément dans les pages de manuel des backends. Voir la page de manuel slapd.backends(5) pour un aperçu des backends disponibles.

SUPERPOSITIONS

Une superposition est un bloc de code qui intercepte les opérations de la base de données afin de les étendre ou de les modifier. Les superpositions sont empilées sur la base de données, de sorte qu'elles s'exécuteront dans l'ordre inverse de celui dans lequel elles ont été configurées et que la base de données elle-même recevra le contrôle en dernier.

Les superpositions doivent être configurées en tant qu'entrées filles d'une base de données spécifique. Le RDN de l'entrée doit être de la forme olcOverlay={x}<type-de-superposition> et l'entrée doit avoir l'objectClass olcOverlayConfig. Normalement, le moteur de configuration génère automatiquement l'index "{x}" dans le RDN, il peut donc être omis lors du chargement initial de ces entrées.

Voir la page de manuel slapd.overlays(5) pour un aperçu des superpositions disponibles.

EXEMPLES

Voici un court exemple de configuration en LDIF approprié pour une utilisation avec slapadd(8) :

dn: cn=config
objectClass: olcGlobal
cn: config
olcPidFile: /var/lib/openldap/run/slapd.pid
olcAttributeOptions: x-hidden lang-
dn: cn=schema,cn=config
objectClass: olcSchemaConfig
cn: schema
include: file:///etc/openldap/schema/core.ldif
dn: olcDatabase=frontend,cn=config
objectClass: olcDatabaseConfig
objectClass: olcFrontendConfig
olcDatabase: frontend
# Sous-types de "name" (par exemple, "cn" et "ou") avec l'option
# ";x-hidden" peuvent être recherchés/comparés,
# mais ne sont pas affichés. Voir slapd.access(5).
olcAccess: to attrs=name;x-hidden by * =cs
# Protéger les mots de passe. Voir slapd.access(5).
olcAccess: to attrs=userPassword  by * auth
# Accès en lecture aux autres attributs et entrées.
olcAccess: to * by * read
# définir un rootpw pour la base de données de configuration afin que nous puissions nous lier.
# refuser l'accès à tous les autres.
dn: olcDatabase=config,cn=config
objectClass: olcDatabaseConfig
olcDatabase: config
olcRootPW: {SSHA}XKYnrjvGT3wZFQrDD5040US592LxsdLy
olcAccess: to * by * none
dn: olcDatabase=mdb,cn=config
objectClass: olcDatabaseConfig
objectClass: olcMdbConfig
olcDatabase: mdb
olcSuffix: "dc=our-domain,dc=com"
# Le répertoire de la base de données DOIT exister avant
# d'exécuter slapd ET ne devrait être accessible
# que par slapd/outils. Mode 0700 recommandé.
olcDbDirectory: /var/lib/openldap/openldap-data
# Indices à maintenir
olcDbIndex:     objectClass  eq
olcDbIndex:     cn,sn,mail   pres,eq,approx,sub
# Nous servons des clients légers qui ne gèrent pas les références,
# donc nous gérons les recherches à distance en leur nom.
dn: olcDatabase=ldap,cn=config
objectClass: olcDatabaseConfig
objectClass: olcLdapConfig
olcDatabase: ldap
olcSuffix: ""
olcDbUri: ldap://ldap.some-server.com/

En supposant que les données ci-dessus ont été enregistrées dans un fichier nommé "config.ldif" et que le répertoire /etc/openldap/slapd.d a été créé, cette commande initialisera la configuration :

slapadd -F /etc/openldap/slapd.d -n 0 -l config.ldif

Alternativement, un fichier slapd.conf existant peut être converti vers le nouveau format en utilisant slapd ou l'un des outils slap :

slaptest -f /etc/openldap/slapd.conf -F /etc/openldap/slapd.d
