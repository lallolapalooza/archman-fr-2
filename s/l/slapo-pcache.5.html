NOM

slapo-pcache - surcouche de cache proxy pour slapd

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

La surcouche pcache de slapd(8) permet la mise en cache des requêtes de recherche LDAP (requêtes) dans une base de données locale. Pour une requête entrante, le cache proxy détermine son modèle correspondant. Si le modèle a été spécifié comme pouvant être mis en cache à l'aide de la directive pcacheTemplate et que la requête est contenue dans une requête mise en cache, elle est traitée à partir du cache proxy. Sinon, la recherche est effectuée comme d'habitude et les résultats de recherche pouvant être mis en cache sont enregistrés dans le cache pour une utilisation ultérieure dans les requêtes futures.

Un modèle est défini par une chaîne de filtre et un index identifiant un ensemble d'attributs. La chaîne de modèle d'une requête peut être obtenue en supprimant les valeurs d'assertion de la représentation RFC 4515 de son filtre de recherche. Une requête appartient à un modèle si sa chaîne de modèle et son ensemble d'attributs projetés correspondent à un modèle pouvant être mis en cache. Des exemples de chaînes de modèle sont (mail=), (|(sn=)(cn=)), (&(sn=)(givenName=)).

Les directives de configuration spécifiques à la surcouche pcache peuvent être préfixées par pcache-, afin d'éviter les conflits avec les directives spécifiques à la base de données sous-jacente ou à d'autres surcouches empilées. Cela peut être particulièrement utile pour les directives qui font référence à la base de données utilisée pour le stockage local. Les directives suivantes spécifiques au cache peuvent être utilisées pour configurer le cache proxy :

overlay pcache
Cette directive ajoute la surcouche de cache proxy à la base de données actuelle. La surcouche de cache proxy peut être utilisée avec n'importe quelle base de données mais est destinée à être utilisée avec les bases de données ldap, meta et sql. Veuillez noter que la base de données sous-jacente doit avoir un rootdn configuré.
pcache <base_de_donnees> <max_entrees> <nb_ensembles_attributs> <limite_entree> <periode_vc>
La directive active la mise en cache proxy dans la base de données actuelle et définit les paramètres généraux du cache. Une base de données <base_de_donnees> sera utilisée en interne pour maintenir les entrées mises en cache. La base de données choisie devra également être configurée, comme indiqué ci-dessous. Le remplacement du cache est déclenché lorsque la taille du cache atteint <max_entrees> entrées et continue jusqu'à ce que la taille du cache descende en dessous de cette taille. <nb_ensembles_attributs> doit être égal au nombre de directives pcacheAttrset suivantes. Les requêtes ne sont mises en cache que si elles correspondent à un modèle pouvant être mis en cache (spécifié par la directive pcacheTemplate) et si le nombre d'entrées retournées est inférieur à <limite_entree>. La vérification de cohérence est effectuée toutes les <periode_vc> (spécifiées en secondes). Dans chaque cycle, les requêtes dont la "durée de vie (TTL)" a expiré sont supprimées. Un exemple de configuration de cache est :
pcache mdb 10000 1 50 100
pcacheAttrset <index> <attributs...>
Utilisé pour associer un ensemble d'attributs <attributs...> à un <index>. Chaque ensemble d'attributs est associé à un entier de 0 à <nb_ensembles_attributs>-1. Ces indices sont utilisés par la directive pcacheTemplate pour définir les modèles pouvant être mis en cache. Un ensemble d'attributs ne peut pas être vide. Un ensemble d'attributs peut contenir les attributs spéciaux "*" (tous les attributs utilisateur), "+" (tous les attributs opérationnels) ou les deux ; dans ce dernier cas, tout autre attribut est redondant et devrait être évité pour des raisons de clarté. Un ensemble d'attributs peut contenir "1.1" comme seul attribut ; dans ce cas, seule la présence des entrées est mise en cache. Les attributs préfixés par "undef:" n'ont pas besoin d'être présents dans le schéma. Le mot-clé "undef" ne peut pas être utilisé avec la base de données slapd-mdb(5) car elle exige que tous les éléments du schéma soient entièrement définis.
pcacheMaxQueries <requêtes>
Spécifie le nombre maximum de requêtes à mettre en cache. La valeur par défaut est 10000.
pcacheValidate { VRAI | FAUX }
Vérifie si les résultats d'une requête mise en cache peuvent réellement être renvoyés depuis le cache par le DSA proxy. Lorsqu'elle est activée, les entrées renvoyées lors de la mise en cache des résultats d'une requête sont vérifiées pour s'assurer de leur cohérence avec le schéma connu du DSA proxy. En cas d'échec, la requête n'est pas mise en cache. Par défaut, la vérification est désactivée.
pcacheOffline { VRAI | FAUX }
Définit le cache en mode hors ligne. En mode hors ligne, le vérificateur de cohérence sera arrêté et aucune expiration ne se produira. Cela permet d'utiliser le contenu du cache indéfiniment pendant que le proxy est coupé de l'accès réseau au DSA distant. La valeur par défaut est FAUX, c'est-à-dire que les vérifications de cohérence et les expirations seront effectuées.
pcachePersist { VRAI | FAUX }
Spécifie si les requêtes mises en cache doivent être enregistrées lors des redémarrages du proxy de mise en cache, afin de permettre un démarrage à chaud du cache. Seules les requêtes non expirées sont rechargées. La valeur par défaut est FAUX.

ATTENTION : bien sûr, la configuration du cache proxy ne doit pas changer entre les redémarrages ; la surcouche pcache n'effectue aucune vérification de cohérence en ce sens. En détail, cette option ne doit être désactivée que si les directives pcacheAttrset et pcacheTemplate existantes ne sont pas modifiées, ni en ordre, ni en contenu. Si de nouveaux ensembles et modèles sont ajoutés, ou si d'autres détails de la configuration de la surcouche pcache ont changé, cette fonctionnalité ne devrait pas être affectée.

pcacheTemplate <chaine_modele> <index_ensemble_attributs> <ttl> [<negttl> [<limitttl> [<ttr>]]]
Spécifie un modèle pouvant être mis en cache et la "durée de vie" <ttl> des requêtes appartenant au modèle. Un <negttl> optionnel peut être utilisé pour spécifier que les résultats négatifs (c'est-à-dire les requêtes qui ont renvoyé zéro entrée) doivent également être mis en cache pendant la durée spécifiée. Les résultats négatifs ne sont pas mis en cache par défaut (<negttl> réglé sur 0). Un <limitttl> optionnel peut être utilisé pour spécifier que les résultats atteignant une limite de taille doivent également être mis en cache pendant la durée spécifiée. Les résultats atteignant une limite de taille ne sont pas mis en cache par défaut (<limitttl> réglé sur 0). Un <ttr> optionnel, "temps de rafraîchissement", peut être utilisé pour spécifier que les entrées mises en cache doivent être automatiquement rafraîchies après un certain temps. Les entrées ne seront rafraîchies que tant qu'elles n'ont pas expiré, donc le <ttl> doit être supérieur au <ttr> pour que cette option soit utile. Les entrées ne sont pas rafraîchies par défaut (<ttr> réglé sur 0).
pcacheBind <modele_filtre> <index_ensemble_attributs> <ttr> <portee> <base>
Spécifie un modèle pour la mise en cache des identifiants de liaison Simple (Bind) basé sur un pcacheTemplate déjà défini. Le <modele_filtre> est similaire à une <chaine_modele> sauf qu'il peut contenir certaines valeurs. Son objectif est de permettre à la surcouche de générer des filtres similaires à ceux que d'autres applications utilisent lorsqu'elles effectuent une recherche juste avant une liaison. Par exemple, si un client comme nss_ldap est configuré pour rechercher un utilisateur avec le filtre "(&(objectClass=posixAccount)(uid=<nom_utilisateur>))", alors le modèle correspondant "(&(objectClass=posixAccount)(uid=))" devrait être utilisé ici. Lorsqu'il est converti en un modèle régulier, par exemple "(&(objectClass=)(uid=))", ce modèle et l'<index_ensemble_attributs> doivent correspondre à une clause pcacheTemplate déjà définie. Le "temps de rafraîchissement" <ttr> détermine l'intervalle de temps après lequel les identifiants mis en cache peuvent être rafraîchis. La première requête de liaison qui survient après cette heure déclenchera la tentative de rafraîchissement. Les rafraîchissements ne sont pas effectués lorsque la surcouche est hors ligne. Il n'y a pas de paramètre "durée de vie" pour les identifiants de liaison ; les identifiants expireront conformément au ttl du pcacheTemplate. Le <portee> et la <base> doivent correspondre à la portée et à la base de recherche utilisées par les clients d'authentification. Les identifiants mis en cache ne sont pas stockés en clair, ils sont hachés en utilisant le hachage de mot de passe par défaut. Par défaut, la mise en cache des liaisons n'est pas activée.

slapo-pcache(5) — OpenLDAP 2.6.10

NAME

slapo-pcache — proxy cache overlay for slapd

SYNOPSIS

This overlay is configured using the directives described below. The overlay directive is used to load the overlay module:

overlay pcache

The configuration options are specific to the pcache overlay:

pcacheLocal IFaces IFaces...
pcacheMaxEntries <max_entries>
pcacheEntrySize <entry_size>
pcacheAttrset ATTRSET [ ATTR ... ]
pcacheTemplate FILTER ATTRSET [ TTL ]
pcacheQueryid ATTR
pcachePosition {head|tail}
pcachePersist {TRUE|FALSE}
pcacheMaxQueries <max_queries>
pcacheValidate {TRUE|FALSE}

DESCRIPTION

The pcache overlay implements a proxy cache for the results of LDAP operations. It is intended to be used in front of slow or remote data sources, such as LDAP servers that are geographically distant or require expensive computations to satisfy requests. The cache is managed by the slapd(8) daemon, and intercepts LDAP requests that are forwarded to a backend data source. If the requested data is found in the cache and is valid, it is returned directly to the client, avoiding the need to contact the backend. If the data is not in the cache, or has expired, the request is forwarded to the backend, and the results are cached for future use.

The pcache overlay requires an underlying backend to store the cached entries. This backend can be any of the supported slapd backends, such as `ldap`, `meta`, or `sql`. The configuration of this backend is independent of the pcache overlay itself.

pcacheLocal IFaces IFaces...
Specifies a list of network interfaces that the cache should listen on. If not specified, the cache will listen on all available interfaces.
pcacheMaxEntries <max_entries>
Specifies the maximum number of entries that the cache can hold. If the cache reaches this limit, the oldest entries will be evicted to make room for new ones.
pcacheEntrySize <entry_size>
Specifies the maximum size of an individual entry in the cache, in bytes. This helps to prevent excessively large entries from consuming too much memory.
pcacheAttrset ATTRSET [ ATTR ... ]
Defines a named set of attributes. ATTRSET is a name for the attribute set, and ATTR is the name of an attribute. This directive can be used multiple times to define multiple attribute sets.
pcacheTemplate FILTER ATTRSET [ TTL ]
Defines a caching template. FILTER is an LDAP search filter that specifies which entries this template applies to. ATTRSET is the name of an attribute set defined using pcacheAttrset. TTL is the time-to-live for cached entries, in seconds. If TTL is not specified, the default TTL is used.
pcacheQueryid ATTR
Specifies the attribute that uniquely identifies a query. This is used to manage cached query results.
pcachePosition {head|tail}
Specifies whether the response callback should be placed at the tail (the default) or at the head (actually, wherever the stacking sequence would make it appear) of the callback list. This affects how the overlay interacts with other overlays, since the proxycache overlay should be executed as early as possible (and thus configured as late as possible), to get a chance to return the cached results; however, if executed early at response, it would cache entries that may be later "massaged" by other databases and thus returned after massaging the first time, and before massaging when cached.
Il y a quelques contraintes:

toutes les valeurs doivent être positives ;

<entry_limit> doit être inférieur ou égal à <max_entries> ;

les ensembles d'attributs <numattrsets> DOIVENT être définis en utilisant la directive pcacheAttrset ;

tous les ensembles d'attributs DEVRAIENT être référencés par (au moins) une directive pcacheTemplate ;

Ce qui suit ajoute un modèle avec la chaîne de filtre (&(sn=)(givenName=)) et les attributs mail, postaladdress, telephonenumber et un TTL de 1 heure.

pcacheAttrset 0 mail postaladdress telephonenumber
pcacheTemplate (&(sn=)(givenName=)) 0 3600

Les directives pour configurer la base de données sous-jacente doivent également être fournies, comme indiqué ici :

directory /var/tmp/cache
maxsize   1073741824

Toute directive valide pour le type de base de données choisi peut être utilisée. L'indexation doit être utilisée de manière appropriée pour les requêtes traitées. De plus, un index d'égalité sur l'attribut pcacheQueryid doit être configuré, pour aider à la suppression des données de requête expirées.

LIMITATIONS

La mise en cache des données est sujette à des incohérences car les mises à jour sur le serveur distant ne seront pas reflétées dans la réponse du cache pendant au moins (et au plus) la durée du TTL de pcacheTemplate. Ces incohérences peuvent être minimisées par une utilisation judicieuse du TTL.

L'overlay de cache proxy nécessite un ensemble complet de données pour fonctionner correctement. Par conséquent, il supprimera le contrôle des résultats paginés s'il est demandé par le client.

Le serveur distant doit exposer l'attribut objectClass car la base de données sous-jacente qui met réellement en cache les entrées peut en avoir besoin pour un traitement local optimal des requêtes.

Le serveur proxy doit contenir toutes les informations de schéma requises pour la mise en cache. Notamment, il a besoin du schéma des attributs utilisés dans les modèles de requête. Si l'attribut objectClass est utilisé dans un modèle de requête, il a besoin de la définition des objectClasses des entrées qu'il est censé mettre en cache. Il incombe à l'administrateur du proxy de maintenir le schéma du proxy aligné sur celui du serveur proxifié.

Une autre incohérence potentielle (et subtile) peut survenir lorsque les données sont récupérées avec différentes identités et que des contrôles d'accès spécifiques par identité sont appliqués par le serveur distant. Si les données ont été récupérées avec une identité qui n'a collecté que des résultats partiels en raison de l'application de règles d'accès sur le serveur distant, d'autres utilisateurs ayant des privilèges d'accès différents sur le serveur distant obtiendront des résultats différents du serveur et du cache. Si ces utilisateurs ont des privilèges d'accès plus élevés sur le serveur distant, ils obtiendront du cache seulement un sous-ensemble des résultats qu'ils obtiendraient directement du serveur distant ; mais s'ils ont des privilèges d'accès plus bas, ils obtiendront du cache un sur-ensemble des résultats qu'ils obtiendraient directement du serveur distant. L'une ou l'autre occurrence peut ou peut ne pas être acceptable, en fonction de la politique de sécurité du cache et du serveur distant. Il est important de noter que dans ce cas, le proxy viole la sécurité du serveur distant en divulguant à une identité des données qui ont été collectées par une autre identité. Pour cette raison, il est suggéré que, lors de l'utilisation de back-ldap, la mise en cache par proxy soit utilisée en conjonction avec la fonctionnalité d'assertion d'identité de slapd-ldap(5) (voir les instructions idassert-bind et idassert-authz), de sorte que l'interrogation du serveur distant se fasse avec une identité vierge qui a des privilèges d'accès search et read relativement élevés, et que le "vrai" contrôle d'accès soit délégué aux ACL du proxy. Attention, comme seule la fraction mise en cache des données réelles est disponible pour le cache, il peut ne pas être possible d'appliquer les mêmes règles d'accès que celles définies sur le serveur distant. Lorsque la sécurité est une préoccupation, l'accès au proxy mis en cache doit être soigneusement adapté.
