SLAPO-NSSOV(5) Manuel des formats de fichiers SLAPO-NSSOV(5)

NOM

slapo-nssov - Requêtes NSS et PAM via un socket de domaine Unix local

SYNTAXE

ETCDIR/slapd.conf

DESCRIPTION

La surcouche nssov de slapd(8) gère les requêtes NSS et PAM via un socket de domaine Unix local. Elle utilise le même protocole IPC que le nss-pam-ldapd d'Arthur de Jong. Un extrait du code source de nss-ldapd est inclus avec le code source de nssov pour permettre à la surcouche de communiquer avec les stubs clients de nss-pam-ldapd.

L'utilisation d'un protocole IPC distinct pour les requêtes NSS et PAM élimine les dépendances/conflits de libldap dont souffrent toutes les solutions actuelles pam_ldap/nss_ldap. Le nss-ldapd original et cette solution nssov sont exempts de ces problèmes de bibliothèques.

Contrairement à nss-pam-ldapd, cette surcouche s'exécutant à l'intérieur de slapd permet la possibilité de mise en cache sophistiquée, sans aucune des faiblesses de nscd et autres solutions de mise en cache connexes. Par exemple, une base de données LDAP distante peut être accédée en utilisant back-ldap avec une mise en cache proxy (voir slapd-ldap(5) et slapo-pcache(5)) pour tirer parti de la mise en commun des connexions de back-ldap ainsi que de la mise en cache persistante de pcache, afin d'offrir des performances élevées et un certain support pour le fonctionnement déconnecté. Alternativement, les considérations de mise en cache peuvent être complètement éliminées en exécutant une base de données régulière avec syncrepl pour maintenir la synchronisation avec une base de données LDAP distante.

Un autre avantage majeur de nssov est qu'il permet à toute la politique de sécurité d'être administrée de manière centralisée via LDAP, au lieu d'avoir des règles fragiles dispersées dans plusieurs fichiers plats. À ce titre, il n'y a aucune configuration côté client pour les bibliothèques stub NSS/PAM. (Les stubs communiquent avec le serveur via un socket de domaine Unix dont le chemin est codé en dur sur NSLCDPATH). En tant que bénéfice secondaire, cela peut enfin éliminer la confusion perpétuelle entre le fichier ldap.conf d'OpenLDAP dans ETCDIR/ldap.conf et les fichiers de nom similaire généralement utilisés par pam_ldap et nss_ldap.

L'authentification des utilisateurs est effectuée par des liaisons simples internes. L'autorisation des utilisateurs s'appuie sur le moteur ACL de slapd, qui offre beaucoup plus de puissance et de flexibilité que les simples vérifications de groupe/nom d'hôte dans l'ancien code pam_ldap.

Pour utiliser ce code, vous aurez besoin de la bibliothèque stub côté client de nss-pam-ldapd. Vous pouvez l'obtenir à l'adresse : http://arthurdejong.org/nss-pam-ldapd Vous n'aurez pas besoin du démon nslcd ; cette surcouche remplace cette partie. Pour désactiver la compilation du démon nslcd dans nss-pam-ldapd, ajoutez l'option --disable-nslcd au script de configuration de nss-pam-ldapd. Vous devriez déjà être familiarisé avec le schéma RFC2307 et RFC2307bis pour utiliser cette surcouche. Voir le README de nss-pam-ldapd pour plus d'informations sur le schéma et les fonctionnalités prises en charge.

Vous devrez également inclure le schéma nis dans votre configuration slapd pour le support RFC2307. Si vous souhaitez utiliser RFC2307bis, vous aurez besoin d'un schéma légèrement différent. Vous aurez également besoin du schéma ldapns pour la gestion des autorisations PAM.

Vous devez sélectionner ldap dans les services appropriés dans /etc/nsswitch.conf pour que ces fonctionnalités NSS prennent effet. De même, vous devez activer pam_ldap pour les services d'authentification, de compte, de session et de mot de passe dans /etc/pam.conf ou /etc/pam.d pour que ces fonctionnalités PAM prennent effet.

overlay nssov
Cette directive ajoute la surcouche nssov au backend actuel.
nssov-ssd <service> <url>
Cette directive configure un descripteur de recherche de service (SSD) pour chaque service NSS qui sera utilisé. Le <service> peut être l'un des suivants :
    aliases
    ethers
    group
    hosts
    netgroup
    networks
    passwd
    protocols
    rpc
    services
    shadow
et l'<url> doit être de la forme
ldap:///[<basedn>][??[<scope>][?<filter>]]
Le <basedn> sera par défaut le premier suffixe de la base de données actuelle. La <scope> par défaut est "subtree". Le <filter> par défaut dépend du service utilisé.
nssov-map <service> <orig> <new>
Si la base de données locale est en fait un proxy vers un serveur LDAP étranger, un mappage de schéma peut être nécessaire. Cette directive permet de réaliser quelques substitutions d'attributs simples. Voir le fichier nss-ldapd/README pour les noms d'attributs originaux utilisés dans ce code.
nssov-pam <option> [...]
Cette directive détermine un certain nombre de comportements PAM. Plusieurs options peuvent être utilisées simultanément, et les niveaux disponibles sont :
userhost
vérifier l'attribut host dans l'entrée utilisateur pour l'autorisation
userservice
vérifier l'attribut authorizedService dans l'entrée utilisateur pour l'autorisation
usergroup
vérifier que l'utilisateur est membre d'un groupe spécifique pour l'autorisation
hostservice
vérifier l'attribut authorizedService dans l'entrée hôte pour l'autorisation
authz2dn
utiliser le mappage authz-regexp pour mapper l'uid au DN LDAP
uid2dn
utiliser le SSD passwd NSS pour mapper l'uid au DN LDAP

La définition des options userhost, userservice et usergroup duplique le comportement d'autorisation original de pam_ldap.

L'approche recommandée est d'utiliser hostservice à la place. Dans ce cas, des entrées ipHost doivent être créées pour tous les hôtes gérés, et elles doivent également avoir la classe authorizedServiceObject pour permettre l'utilisation des attributs authorizedService. De plus, le SSD host NSS doit être configuré afin que les entrées ipHost puissent être trouvées. L'autorisation est vérifiée en effectuant une opération de comparaison LDAP recherchant le nom du service PAM dans l'attribut authorizedService. Les ACL de slapd doivent être définies pour accorder ou refuser le privilège de Compare aux utilisateurs ou groupes appropriés selon les besoins.

Si l'option authz2dn est définie, alors les mappages authz-regexp seront utilisés pour mapper le nom d'utilisateur PAM à un DN LDAP. Le DN d'authentification sera de la forme

cn=<service>+uid=<user>,cn=<hostname>,cn=pam,cn=auth

Si aucun mappage n'est trouvé pour ce DN d'authentification, alors ce mappage sera ignoré.

Si l'option uid2dn est définie, alors le SSD passwd NSS sera utilisé pour mapper le nom d'utilisateur PAM à un DN LDAP. Le SSD passwd doit avoir été préalablement configuré pour que ce mappage réussisse.

Si aucun des mappages authz2dn ni uid2dn ne réussit, le module renverra un code d'échec PAM_USER_UNKNOWN. Si les deux options sont définies, le mappage authz est tenté en premier ; s'il réussit, le mappage uid2dn sera ignoré.

Par défaut, seule l'option uid2dn est définie.

nssov-pam-defhost <hostname>
Spécifie un nom d'hôte par défaut à vérifier si une entrée ipHost pour le nom d'hôte actuel ne peut être trouvée. Ce réglage n'est pertinent que si l'option hostservice a été définie.
nssov-pam-group-dn <DN>
Spécifie le DN d'un groupe LDAP à vérifier pour l'autorisation. L'utilisateur LDAP doit être membre de ce groupe pour que la connexion soit autorisée. Il n'y a pas de valeur par défaut. Ce réglage n'est pertinent que si l'option usergroup a été définie.
nssov-pam-group-ad <attribute>
Spécifie l'attribut à utiliser pour les vérifications d'appartenance à un groupe. Il n'y a pas de valeur par défaut. Ce réglage n'est pertinent que si l'option usergroup a été définie.
nssov-pam-min-uid <entier>
Spécifie un uid minimum autorisé à se connecter. Les utilisateurs dont le uidNumber est inférieur à cette valeur se verront refuser l'accès.

slapo-nssov(5) - OpenLDAP

NAME

slapo-nssov - NSS/NSS_LDAP service integration overlay

SYNOPSIS

/etc/openldap/slapd.conf
olcOverlay={0}nssov

DESCRIPTION

The NSS/NSS_LDAP service integration overlay, slapo-nssov, provides a means to integrate services that rely on the Name Service Switch (NSS) libraries with an LDAP database. It allows services such as login, passwd, group, hosts, and others to retrieve their required information from LDAP. This overlay can be used in conjunction with the MDB backend to store and retrieve the data, or it can be used to proxy requests to another LDAP server.

The slapo-nssov overlay supports the following directives in slapd.conf(5) format:

nssov-log-level <level>
Set the logging level for the nssov overlay. The level is a bitmask that can be used to enable specific debug messages.
nssov-module <module>
Load the specified module. Modules are used to extend the functionality of the nssov overlay. Currently, only the pam module is supported.
nssov-pam-host <host>
Specify a hostname that is allowed to use the PAM services. If this option is specified, only logins from the specified host will be accepted. The default is to allow logins from any host.
nssov-pam-service <service>
Specify a PAM service name that is allowed to use the nssov overlay. If this option is specified, only logins from the specified service will be accepted. The default is to allow logins from any service.
nssov-pam-account-by <attribute>
Specify an attribute to use when checking the account for authorization. The default is uid.
nssov-pam-map-uid-dn <attribute>
Specify an attribute to use when mapping a uid to a dn. The default is uid.
nssov-pam-map-uid-dn-search <filter>
Specify a search filter to use when mapping a uid to a dn. The default is (&(objectClass=posixAccount)(uid=%s)).
nssov-pam-map-user-dn <attribute>
Specify an attribute to use when mapping a user to a dn. The default is cn.
nssov-pam-map-user-dn-search <filter>
Specify a search filter to use when mapping a user to a dn. The default is (&(objectClass=posixAccount)(cn=%s)).
nssov-pam-min-uid <integer>
Specify a minimum uid that is allowed to login. Users with a uidNumber lower than this value will be denied access. The default is zero, which disables this setting.
nssov-pam-max-uid <integer>
Specify a maximum uid that is allowed to login. Users with a uidNumber higher than this value will be denied access. The default is zero, which disables this setting.
nssov-pam-template-ad <attribute>
Specify an attribute to check in a user's entry for a template login name. The template login feature is used by FreeBSD's PAM framework. It can be viewed as a form of proxying, where a user can authenticate with one username/password pair, but is assigned the identity and credentials of the template user. This setting is disabled by default.
nssov-pam-template <name>
Specify a default username to be used if no template attribute is found in the user's entry. The nssov-pam-template-ad directive must be configured for this setting to have any effect.
nssov-pam-session <service>
Specify a PAM service name whose sessions will be recorded. For the configured services, logins will be recorded in the
nssov-pam-password-prohibit-message <message>
Disable password change service and return the specified message to users.
nssov-pam-pwdmgr-dn <dn>
Specify the dn of the password manager.
nssov-pam-pwdmgr-pwd <pwd>
Specify the pwd of the password manager.
loginStatus
operational attribute of the user's entry. The attribute's values are of the form
<generalizedTime> <host> <service> <tty> (<ruser@rhost>)
Upon logout the corresponding value will be deleted. This feature allows a single LDAP Search to be used to check which users are logged in across all the hosts of a network. The rootdn of the database is used to perform the updates of the loginStatus attribute, so a rootdn must already be configured for this feature to work. By default no services are configured.

The PAM functions support LDAP Password Policy as well. If the password policy overlay is in use (see slapo-ppolicy(5)), policy information (e.g. password expiration, password quality, etc.) may be returned to the PAM client as a result of authentication, account management, and password modification requests.

The overlay also supports dynamic configuration in cn=config. An example of the config entry is

    dn: olcOverlay={0}nssov,ocDatabase={1}mdb,cn=config
    objectClass: olcOverlayConfig
    objectClass: olcNssOvConfig
    olcOverlay: {0}nssov
    olcNssSsd: passwd ldap:///ou=users,dc=example,dc=com??one
    olcNssMap: passwd uid accountName
    olcNssPam: hostservice uid2dn
    olcNssPamDefHost: defaulthost
    olcNssPamMinUid: 500
    olcNssPamMaxUid: 32000
    olcNssPamSession: login
    olcNssPamSession: sshd

which enables the passwd service, and uses the accountName attribute to fetch what is usually retrieved from the uid attribute. It also enables some PAM authorization controls, and specifies that the PAM login and sshd services should have their logins recorded.

FILES

ETCDIR/slapd.conf
default slapd configuration file
