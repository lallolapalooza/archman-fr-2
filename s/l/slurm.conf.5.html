NOM

slurm.conf - Fichier de configuration Slurm

DESCRIPTION

slurm.conf est un fichier ASCII qui décrit les informations générales de configuration de Slurm, les nœuds à gérer, les informations sur la manière dont ces nœuds sont regroupés en partitions, et divers paramètres de planification associés à ces partitions. Ce fichier doit être cohérent sur tous les nœuds du cluster.

L'emplacement du fichier peut être modifié au moment de l'exécution en définissant la variable d'environnement SLURM_CONF. Les démons Slurm vous permettent également de remplacer l'emplacement intégré et celui fourni par l'environnement en utilisant l'option « -f » en ligne de commande.

Le contenu du fichier est insensible à la casse, à l'exception des noms des nœuds et des partitions. Tout texte suivant un « # » dans le fichier de configuration est traité comme un commentaire jusqu'à la fin de cette ligne. Les modifications du fichier de configuration prennent effet au redémarrage des démons Slurm, à la réception du signal SIGHUP par un démon, ou à l'exécution de la commande « scontrol reconfigure », sauf indication contraire. Les modifications des paramètres d'écoute TCP nécessiteront un redémarrage du démon.

Si une ligne commence par le mot « Include » suivi d'un espace blanc puis d'un nom de fichier, ce fichier sera inclus en ligne dans le fichier de configuration actuel. Pour les systèmes de grande taille ou complexes, il peut être plus facile de gérer plusieurs fichiers de configuration et de permettre la réutilisation de certains fichiers (voir la section MODIFICATEURS D'INCLUSION pour plus de détails).

Note sur les permissions de fichiers :

Le fichier slurm.conf doit être lisible par tous les utilisateurs de Slurm, car il est utilisé par de nombreuses commandes Slurm. D'autres fichiers définis dans le fichier slurm.conf, tels que les fichiers de journalisation et de comptabilité des travaux, peuvent devoir être créés/détenus par l'utilisateur « SlurmUser » pour être accédés avec succès. Utilisez les commandes « chown » et « chmod » pour définir la propriété et les permissions de manière appropriée. Voir la section PERMISSIONS DE FICHIERS ET DE RÉPERTOIRES pour des informations sur les divers fichiers et répertoires utilisés par Slurm.

PARAMÈTRES

Les paramètres de configuration généraux disponibles incluent :

AccountingStorageBackupHost
Le nom de la machine de secours hébergeant la base de données de stockage de la comptabilité. Utilisé avec le plugin accounting_storage/slurmdbd, il s'agit de l'emplacement où le slurmdbd de sauvegarde serait en cours d'exécution. Utilisé uniquement avec les systèmes utilisant SlurmDBD, ignoré sinon.
AccountingStorageEnforce
Ceci contrôle le niveau de contrôle basé sur les associations à imposer lors de la soumission des travaux. Les options valides sont toute combinaison séparée par des virgules des options suivantes, dont beaucoup incluent implicitement d'autres options :
all
Implique toutes les autres options disponibles, sauf nojobs et nosteps.
associations
Aucun nouveau travail ne peut être exécuté à moins qu'une association correspondante n'existe dans le système.
limits
Les utilisateurs peuvent être limités par association à la taille de travail ou aux limites de temps d'exécution définies. Implique associations.
nojobs
Slurm ne comptabilisera aucun travail ou étape sur le système. Implique nosteps.
nosteps
Slurm ne comptabilisera aucune étape qui a été exécutée.
qos
Les travaux ne seront pas planifiés à moins qu'un qos valide ne soit spécifié. Implique associations.
safe
Un travail ne sera lancé contre une association ou un qos ayant une limite en TRES-minutes définie que si le travail peut s'exécuter jusqu'à son terme. Sans cette option, les travaux seront lancés tant que leur utilisation n'a pas atteint la limite de TRES-minutes. Cela peut conduire à des travaux lancés mais ensuite tués lorsque la limite est atteinte. Avec cette option, un travail ne sera pas tué en raison des limites, même si les limites sont modifiées après le démarrage du travail et que l'association ou le qos viole les limites mises à jour. Implique limits et associations.
wckeys
Les travaux ne seront pas planifiés à moins qu'une clé de caractérisation de charge de travail valide ne soit spécifiée. Implique associations et TrackWCKey (une option de configuration distincte).
AccountingStorageExternalHost
Une liste de slurmdbd externes séparés par des virgules (<hôte/ip>[:port][,...]) à enregistrer. Si aucun port n'est donné, le AccountingStoragePort sera utilisé.

Ceci permet aux clusters enregistrés avec le slurmdbd externe de communiquer entre eux en utilisant les options de commande client « --cluster/-M ».

Le cluster s'ajoutera au slurmdbd externe s'il n'existe pas déjà. Si un cluster non externe existe déjà sur le slurmdbd externe, le slurmctld ignorera l'enregistrement auprès du slurmdbd externe.

AccountingStorageHost
Le nom de la machine hébergeant la base de données de stockage de la comptabilité. Utilisé uniquement avec les systèmes utilisant SlurmDBD, ignoré sinon.

Liste d'options séparées par des virgules.

les étapes batch, extern et interactive.

SSL_CA

SSL_CAPATH
Le nom du chemin du répertoire contenant les fichiers de certificat CA SSL de confiance.
SSL_KEY
Le nom du chemin du fichier de la clé privée du client.
SSL_CIPHER
La liste des chiffrements autorisés pour le chiffrement SSL.
AccountingStoragePass
Le mot de passe utilisé pour accéder à la base de données afin de stocker les données de comptabilité. Utilisé uniquement pour les plugins de type base de données, ignoré sinon. Dans le cas de SlurmDBD (Database Daemon) avec authentification MUNGE, cela peut être configuré pour utiliser un démon MUNGE spécifiquement configuré pour fournir

Dans ce cas, AccountingStoragePass doit spécifier le port nommé à utiliser pour les communications avec le démon MUNGE alternatif (par exemple, "/var/run/munge/global.socket.2"). La valeur par défaut est NULL.
AccountingStoragePort
Le port d'écoute du serveur de base de données de stockage comptable. Uniquement utilisé pour les plugins de stockage de type base de données, ignoré sinon. La valeur par défaut est SLURMDBD_PORT tel qu'établi au moment de la compilation du système. Si aucune valeur n'est explicitement spécifiée, elle sera définie à 6819. Cette valeur doit être égale au paramètre DbdPort dans le fichier slurmdbd.conf.
AccountingStorageTRES
Liste séparée par des virgules des ressources que vous souhaitez suivre sur le cluster. Ce sont les ressources demandées par le travail sbatch/srun lors de sa soumission. Actuellement, cela comprend tous les GRES, BB (burst buffer) ou licences, ainsi que CPU, Memory, Node, Energy, FS/[Disk|Lustre], IC/OFED, Pages et VMem. Par défaut, Billing, CPU, Energy, Memory, Node, FS/Disk, Pages et VMem sont suivis. Ces TRES par défaut ne peuvent pas être désactivés, mais seulement complétés. AccountingStorageTRES=gres/craynetwork,license/iop1 suivra la facturation, le CPU, l'énergie, la mémoire, les nœuds, le FS/disque, les pages et la VMEM, ainsi qu'un GRES appelé craynetwork et une licence appelée iop1. Chaque fois que ces ressources sont utilisées sur le cluster, elles sont enregistrées. Les TRES sont automatiquement configurés dans la base de données au démarrage de slurmctld.

Si plusieurs GRES de types différents sont suivis (par exemple, des GPU de types différents), les requêtes de travaux avec des spécifications de type correspondantes seront enregistrées. Compte tenu d'une configuration de "AccountingStorageTRES=gres/gpu,gres/gpu:tesla,gres/gpu:volta" Alors "gres/gpu:tesla" et "gres/gpu:volta" suivront uniquement les travaux qui demandent explicitement ces deux types de GPU, tandis que "gres/gpu" suivra les GPU alloués de tout type ("tesla", "volta" ou tout autre type de GPU).

Compte tenu d'une configuration de "AccountingStorageTRES=gres/gpu:tesla,gres/gpu:volta" Alors "gres/gpu:tesla" et "gres/gpu:volta" suivront les travaux qui demandent explicitement ces types de GPU. Si un travail demande des GPU, mais ne spécifie pas explicitement le type de GPU, alors son allocation de ressources sera comptabilisée comme "gres/gpu:tesla" ou "gres/gpu:volta", bien que la comptabilité puisse ne pas correspondre au type de GPU réellement alloué au travail et que les GPU alloués au travail puissent être hétérogènes. Dans un environnement contenant divers types de GPU, l'utilisation d'un plugin job_submit peut être souhaitable afin de forcer les travaux à spécifier explicitement un type de GPU.

NOTE: La définition de gres/gpu définira également gres/gpumem et gres/gpuutil. gres/gpumem et gres/gpuutil peuvent être définis individuellement lorsque gres/gpu n'est pas défini.

AccountingStorageType
Le type de mécanisme de stockage comptable. Non défini par défaut, ce qui indique que les enregistrements comptables ne sont pas maintenus.

Les options actuelles sont :

accounting_storage/slurmdbd
Les enregistrements comptables seront écrits dans SlurmDBD, qui gère une base de données MySQL sous-jacente. Voir "man slurmdbd" pour plus d'informations.
AccountingStoreFlags
Liste séparée par des virgules utilisée pour modifier les champs que slurmctld envoie à la base de données comptable.
Les options actuelles sont :
job_comment
Inclure le champ commentaire du travail dans le message de fin de travail envoyé à la base de données Accounting Storage. Notez que AdminComment et SystemComment sont toujours enregistrés dans la base de données.
job_env
Inclure les variables d'environnement d'un travail batch utilisées lors de la soumission du travail dans le message de début de travail envoyé à la base de données Accounting Storage.
job_extra
Inclure le champ extra du travail dans le message de fin de travail envoyé à la base de données Accounting Storage.
job_script
Inclure le script batch du travail dans le message de début de travail envoyé à la base de données Accounting Storage.
no_stdio
Exclure les chemins stdio lors de l'enregistrement des données dans la base de données lors du début d'un travail ou d'une étape. Les champs db StdOut, StdErr et StdIn pour les travaux et les étapes seront vides.
AcctGatherNodeFreq
L'intervalle d'échantillonnage des plugins AcctGather pour la comptabilité des nœuds. Pour les valeurs du plugin AcctGather nulles, ce paramètre est ignoré. Pour toutes les autres valeurs, ce paramètre est le nombre de secondes entre les échantillons de comptabilité des nœuds. Pour le plugin acct_gather_energy/rapl, définissez une valeur inférieure à 300 car les compteurs peuvent déborder au-delà de ce taux. La valeur par défaut est zéro. Cela désactive l'échantillonnage comptable pour les nœuds. Remarque : L'intervalle d'échantillonnage comptable pour les travaux est déterminé par la valeur de JobAcctGatherFrequency.
AcctGatherEnergyType
Identifie le plugin à utiliser pour la comptabilité de la consommation d'énergie. Le plugin jobacct_gather et le démon slurmd appellent ce plugin pour collecter les données de consommation d'énergie pour les travaux et les nœuds. La collecte des données de consommation d'énergie a lieu au niveau du nœud, par conséquent, ce n'est qu'en cas d'allocation de travail exclusive que les mesures de consommation d'énergie refléteront la consommation réelle du travail. En cas de partage de nœuds entre travaux, l'énergie consommée rapportée par travail (via sstat ou sacct) ne reflétera pas la consommation d'énergie réelle des travaux. Par défaut, rien n'est collecté.

Les valeurs configurables à l'heure actuelle sont :

acct_gather_energy/gpu
Les données de consommation d'énergie sont collectées à partir de la bibliothèque de gestion GPU (par exemple, rsmi) pour le type de GPU correspondant. Disponible uniquement pour rsmi pour le moment. Remarque : slurmd conservera le plugin gpu chargé après configuration lorsque ceci est défini.
acct_gather_energy/ipmi
Les données de consommation d'énergie sont collectées à partir du contrôleur de gestion de carte mère (BMC) à l'aide de l'Interface de gestion de plateforme intelligente (IPMI).
acct_gather_energy/pm_counters
Les données de consommation d'énergie sont collectées à partir du contrôleur de gestion de carte mère (BMC) pour les systèmes HPE Cray.
acct_gather_energy/rapl
Les données de consommation d'énergie sont collectées à partir des capteurs matériels à l'aide du mécanisme Running Average Power Limit (RAPL). Notez que l'activation de RAPL peut nécessiter l'exécution de la commande "sudo modprobe msr".
acct_gather_energy/xcc
Les données de consommation d'énergie sont collectées à partir du Lenovo SD650 XClarity Controller (XCC) à l'aide de commandes brutes OEM IPMI.
AcctGatherInterconnectType
Identifie le plugin à utiliser pour la comptabilité du trafic réseau d'interconnexion. Le plugin jobacct_gather et le démon slurmd appellent ce plugin pour collecter les données de trafic réseau pour les travaux et les nœuds. La collecte des données de trafic réseau a lieu au niveau du nœud, par conséquent, ce n'est qu'en cas d'allocation de travail exclusive que les valeurs collectées refléteront le trafic réel du travail. En cas de partage de nœuds entre travaux, le trafic réseau rapporté par travail (via sstat ou sacct) ne reflétera pas le trafic réseau réel des travaux.

Les valeurs configurables à l'heure actuelle sont :

acct_gather_interconnect/ofed
Les données de trafic réseau Infiniband sont collectées à partir des compteurs de surveillance matérielle des périphériques Infiniband via la bibliothèque OFED. Afin de comptabiliser le trafic réseau par travail, ajoutez le TRES "ic/ofed" à AccountingStorageTRES.
acct_gather_interconnect/sysfs
Les statistiques de trafic réseau sont collectées à partir du système de fichiers pseudo sysfs de Linux pour les interfaces spécifiques définies dans acct_gather.conf(5). Afin de comptabiliser le trafic réseau par travail, ajoutez le TRES "ic/sysfs" à AccountingStorageTRES.
AcctGatherFilesystemType
Identifie le plugin à utiliser pour la comptabilité du trafic du système de fichiers. Le plugin jobacct_gather et le démon slurmd appellent ce plugin pour collecter les données de trafic du système de fichiers pour les jobs et les nœuds. La collecte de données de trafic du système de fichiers a lieu au niveau du nœud, donc uniquement dans le cas d'une allocation de job exclusive, les valeurs collectées refléteront le trafic réel du job. En cas de partage de nœuds entre des jobs, le trafic de système de fichiers signalé par job (via sstat ou sacct) ne reflétera pas le trafic réel du système de fichiers par les jobs.

Valeurs configurables actuellement :

acct_gather_filesystem/lustre
Les données de trafic du système de fichiers Lustre sont collectées à partir des compteurs trouvés dans /proc/fs/lustre/. Afin de comptabiliser le trafic Lustre par job, ajoutez le TRES "fs/lustre" à AccountingStorageTRES.
AcctGatherProfileType
Identifie le plugin à utiliser pour le profilage détaillé des jobs. Le plugin jobacct_gather et le démon slurmd appellent ce plugin pour collecter des données détaillées telles que les comptes d'E/S, l'utilisation de la mémoire ou la consommation d'énergie pour les jobs et les nœuds. Il existe des interfaces dans ce plugin pour collecter des données au moment du début et de la fin des étapes, du début et de la fin des tâches, et à la fréquence de collecte des comptes. Les données collectées au niveau du nœud ne sont liées aux jobs qu'en cas d'allocation de job exclusive.

Valeurs configurables actuellement :

acct_gather_profile/hdf5
Cela active le plugin HDF5. Le répertoire où les fichiers de profil sont stockés et quelles valeurs sont collectées sont configurés dans le fichier acct_gather.conf.
acct_gather_profile/influxdb
Cela active le plugin influxdb. L'hôte de l'instance influxdb, le port, la base de données, la politique de rétention et les valeurs collectées sont configurés dans le fichier acct_gather.conf.
AllowSpecResourcesUsage
Si réglé sur "YES", Slurm permet aux jobs individuels de remplacer la valeur CoreSpecCount configurée du nœud. Pour qu'un job tire parti de cette fonctionnalité, une option de ligne de commande --core-spec doit être spécifiée. La valeur par défaut de cette option est "YES" pour les systèmes Cray et "NO" pour les autres types de systèmes.
AuthAltTypes
Liste séparée par des virgules des plugins d'authentification alternatifs que slurmctld autorisera pour la communication. Les valeurs acceptables actuellement incluent auth/jwt.

NOTE : Si AuthAltParameters n'est pas utilisé pour spécifier un chemin d'accès au fichier jwt_hs256.key requis, slurmctld cherchera par défaut dans le fichier StateSaveLocation. Le fichier jwt_hs256.key ne devrait être visible que par l'utilisateur Slurm et root. Il n'est pas conseillé de placer le fichier jwt_hs256.key sur d'autres nœuds que la machine exécutant slurmctld et la machine exécutant slurmdbd. auth/jwt peut être activé par la présence de la variable d'environnement SLURM_JWT. Lorsqu'il est activé, il remplace le AuthType par défaut.

AuthAltParameters
Utilisé pour définir les options des plugins d'authentification alternatifs. Plusieurs options peuvent être séparées par des virgules.
disable_token_creation
Désactive l'utilisation de "scontrol token" par les comptes non-SlurmUser.
max_token_lifespan=<secondes>
Définit la durée de vie maximale (en secondes) de tout jeton généré pour les comptes utilisateurs. La limite s'applique à tous les utilisateurs sauf SlurmUser. Les sites souhaitant avoir des limites par utilisateur devraient générer des jetons à l'aide d'outils compatibles JWT, et/ou d'un proxy d'authentification, au lieu d'utiliser scontrol token.
jwks=
Chemin d'accès absolu au fichier JWKS. La clé doit appartenir à SlurmUser ou root, doit être lisible par SlurmUser, avec des permissions suggérées de 0400. Elle ne doit pas être inscriptible par 'other'. Seules les clés RS256 sont prises en charge, bien que d'autres types de clés puissent être listés dans le fichier. Si défini, aucune clé HS256 ne sera chargée par défaut (et la génération de jetons est désactivée), bien que le paramètre jwt_key puisse être utilisé pour réactiver explicitement l'utilisation de la clé HS256 (et la génération de jetons).
jwt_key=
Chemin d'accès absolu au fichier de clé JWT. La clé doit être HS256. La clé doit appartenir à SlurmUser ou root, doit être lisible par SlurmUser, avec des permissions suggérées de 0400. Elle ne doit pas être accessible par 'other'. Si non défini, le fichier de clé par défaut est jwt_hs256.key dans StateSaveLocation.
userclaimfield=
Utilise un champ de revendication alternatif pour le nom d'utilisateur Slurm (champ sun). Cette option est conçue pour permettre la compatibilité avec les jetons générés en dehors de Slurm. (Ce champ peut également être appelé une concession.) Par défaut : (désactivé)
AuthInfo
Informations supplémentaires à utiliser pour l'authentification des communications entre les démons Slurm (slurmctld et slurmd) et les clients Slurm. L'interprétation de cette option est spécifique au AuthType configuré. Plusieurs options peuvent être spécifiées dans une liste délimitée par des virgules. Si non spécifié, les informations d'authentification par défaut seront utilisées.
cred_expire
Durée de vie par défaut du jeton d'étape de job, en secondes (par exemple, "cred_expire=1200"). Elle doit être suffisamment longue pour charger l'environnement utilisateur, exécuter le prolog, gérer le fait que slurmd soit paginé hors de la mémoire, etc. Elle contrôle également le temps d'attente d'un job replanifié avant de redémarrer. La valeur par défaut est 120 secondes.
socket
Nom du chemin d'un socket du démon MUNGE à utiliser (par exemple, "socket=/var/run/munge/munge.socket.2"). La valeur par défaut est "/var/run/munge/munge.socket.2". Utilisé par auth/munge et cred/munge.
ttl
Durée de vie du jeton, en secondes (par exemple, "ttl=300"). La valeur par défaut dépend du AuthType utilisé. Pour auth/munge, la valeur par défaut dépend de l'installation MUNGE, mais est généralement de 300 secondes. Pour auth/slurm, la valeur par défaut est de 60 secondes. Pour auth/jwt, la valeur par défaut est de 1800 secondes.
use_client_ids
Permet au plugin auth/slurm d'authentifier les utilisateurs sans dépendre des informations utilisateur de LDAP ou du système d'exploitation. Couplé avec nss_slurm, les informations utilisateur peuvent être gérées sur les nœuds de calcul par slurmstepd. Cela permettrait au cluster de fonctionner dans un environnement où seuls les nœuds de connexion ont accès aux informations utilisateur LDAP/OS. Voir https://slurm.schedmd.com/nss_slurm.html pour plus d'informations.
AuthType
La méthode d'authentification pour les communications entre les composants Slurm. Tous les démons et commandes Slurm doivent être arrêtés avant de changer la valeur de AuthType et redémarrés ultérieurement. Les changements à cette valeur interrompront les étapes de job en cours et les empêcheront de se terminer. Valeurs acceptables actuellement :
auth/munge
Indique que MUNGE doit être utilisé (par défaut). (Voir "https://dun.github.io/munge/" pour plus d'informations).
auth/slurm
Utilise le plugin d'authentification interne de Slurm.
BatchStartTimeout
Le temps maximum (en secondes) que le démarrage d'un job batch est autorisé avant d'être considéré comme manquant et de libérer l'allocation. La valeur par défaut est 10 (secondes). Des valeurs plus importantes peuvent être nécessaires si plus de temps est requis pour exécuter le Prolog, charger les variables d'environnement utilisateur, ou si le démon slurmd est paginé hors de la mémoire.
NOTE : Le test de lancement réussi d'un job n'est effectué que lorsque le démon Slurm sur le nœud de calcul enregistre son état auprès du démon slurmctld sur le nœud principal, ce qui arrive assez rarement. Par conséquent, un job ne sera pas nécessairement terminé si son temps de démarrage dépasse BatchStartTimeout. Ce paramètre de configuration est également appliqué aux tâches de lancement pour éviter l'abandon des commandes srun en raison de scripts Prolog de longue durée.
BcastExclude
Liste séparée par des virgules des chemins d'accès absolus des répertoires à exclure lors de la détection automatique et de la diffusion des exécutables
objets partagés coupables via sbcast ou srun --bcast. Le mot-clé "none" peut être utilisé pour indiquer qu'aucun chemin de répertoire ne doit être exclu. La valeur par défaut est "/lib,/usr/lib,/lib64,/usr/lib64". Cette option peut être écrasée par sbcast --exclude et srun --bcast-exclude.
BcastParameters
Contrôle le comportement de sbcast et de srun --bcast. Plusieurs options peuvent être spécifiées dans une liste séparée par des virgules. Les valeurs prises en charge incluent :
DestDir=
Répertoire de destination pour le fichier en cours de diffusion vers les nœuds de calcul alloués. La valeur par défaut est le répertoire de travail actuel, ou --chdir pour srun si défini.
Compression=
Spécifiez la bibliothèque de compression de fichiers par défaut à utiliser. Les valeurs prises en charge sont "lz4" et "none". La valeur par défaut avec l'option sbcast --compress est "lz4" et "none" sinon. Certaines bibliothèques de compression peuvent ne pas être disponibles sur certains systèmes.
send_libs
Si défini, tente de détecter automatiquement et de diffuser les dépendances des objets partagés de l'exécutable vers les nœuds de calcul alloués. Les fichiers sont placés dans un répertoire à côté de l'exécutable. Pour srun uniquement, LD_LIBRARY_PATH est automatiquement mis à jour pour inclure également ce répertoire cache. Cela peut être écrasé par l'option --send-libs de sbcast ou srun. Par défaut, cette option est désactivée.
BurstBufferType
Le plugin utilisé pour gérer les buffers d'éclatement. Non défini par défaut. Les valeurs acceptables actuellement sont :
burst_buffer/datawarp
Utilise l'API Cray DataWarp pour fournir la fonctionnalité de buffer d'éclatement.
burst_buffer/lua
Ce plugin fournit des hooks à une API définie par un script Lua. Ce plugin a été développé pour permettre aux administrateurs système d'effectuer toute tâche (pas seulement la mise en scène de fichiers) à différents points du cycle de vie d'un travail.
CertgenParameters
Options séparées par des virgules identifiant les options du plugin certgen. Les valeurs prises en charge incluent :
certgen_script=
Chemin absolu vers le script exécutable pour générer un certificat TLS auto-signé. La clé privée générée par keygen_script est passée en entrée standard, et seul le fichier PEM du certificat doit être imprimé sur la sortie standard. Doit retourner 0 en cas de succès, et non nul en cas d'erreur.
keygen_script=
Chemin absolu vers le script exécutable pour générer la clé privée utilisée plus tard pour générer un certificat auto-signé. Seul le fichier PEM de la clé privée doit être imprimé sur la sortie standard, qui sera plus tard envoyée en entrée standard à certgen_script. Doit retourner 0 en cas de succès, et non nul en cas d'erreur.
CertgenType
Spécifiez le plugin certgen qui sera utilisé. Les valeurs acceptables actuellement :
certgen/script
Utilise des scripts intégrés/configurés pour générer une paire de clés de certificat.
CertmgrParameters
Utilisé pour définir les paramètres du plugin certmgr.
certificate_renewal_period=
slurmd/sackd demanderont un nouveau certificat signé à slurmctld à cet intervalle spécifié (en minutes).

Par défaut, 1440 minutes (une fois par jour).

generate_csr_script=
Chemin vers le script utilisé pour générer des demandes de signature de certificat. Le nom du nœud est passé comme argument au script. Le script doit imprimer uniquement le fichier PEM de la demande de signature de certificat sur la sortie standard et retourner 0 en cas de succès. Doit retourner une valeur non nulle en cas d'erreur.

Requis avec certmgr/script. Exécuté uniquement par les démons demandant des certificats.

get_node_cert_key_script=
Chemin vers le script utilisé pour obtenir la clé privée du nœud qui a été utilisée pour générer la CSR retournée par generate_csr_script. Le nom du nœud est passé comme argument au script. Le script doit imprimer la clé privée du nœud (fichier PEM) sur la sortie standard. Doit retourner 0 en cas de succès et non nul en cas d'erreur.

Requis avec certmgr/script. Exécuté uniquement par les démons demandant des certificats.

get_node_token_script=
Chemin vers le script utilisé pour obtenir le jeton unique du nœud, qui sera validé par slurmctld en utilisant le script défini par validate_node_script=. Le nom du nœud est passé comme argument au script. Le script doit imprimer le jeton unique du nœud sur la sortie standard et retourner 0 en cas de succès. Doit retourner une valeur non nulle en cas d'erreur.

Requis avec certmgr/script. Exécuté uniquement par les démons demandant des certificats.

sign_csr_script=
Chemin vers le script utilisé pour signer les demandes de signature de certificat entrantes. Ce script ne sera appelé que si validate_node_script= a déjà été appelé sur le jeton de nœud unique associé et a retourné un code de sortie non nul. La demande de signature de certificat (telle que fournie par generate_csr_script=) est passée comme argument à ce script. Le script doit imprimer le nouveau certificat signé sur la sortie standard et retourner 0 en cas de succès. Doit retourner une valeur non nulle en cas d'erreur.

Requis avec certmgr/script. Exécuté uniquement par slurmctld.

single_use_tokens
Les jetons de nœud uniques qui sont définis dynamiquement (par exemple, définis via scontrol) seront consommés après une signature de certificat réussie.
validate_node_script=
Chemin vers le script utilisé pour valider un jeton de nœud unique. Le jeton de nœud unique est passé comme argument à ce script. Si le script trouve le jeton de nœud valide, il retourne 0. Sinon, si le jeton de nœud est invalide, il retourne une valeur non nulle.

Requis avec certmgr/script. Exécuté uniquement par slurmctld.

CompleteWait
Le temps d'attente, en secondes, lorsqu'un travail est dans l'état COMPLETING avant que des travaux supplémentaires ne soient planifiés. Ceci vise à essayer de conserver les travaux sur les nœuds qui ont été récemment utilisés, dans le but d'éviter la fragmentation. S'il est défini sur zéro, les travaux en attente seront démarrés dès que possible. Étant donné que les ressources d'un travail COMPLETING sont libérées pour être utilisées par d'autres travaux dès que l'Epilog se termine sur chaque nœud individuel, cela peut entraîner des allocations de ressources très fragmentées. Pour offrir aux travaux un temps de réponse minimal, une valeur de zéro est recommandée (pas d'attente). Pour minimiser la fragmentation des ressources, une valeur égale à KillWait plus deux est recommandée. Dans ce cas, définir KillWait à une petite valeur peut être bénéfique. La valeur par défaut de CompleteWait est zéro seconde. La valeur ne peut pas dépasser 65533.

NOTE : La définition de reduce_completing_frag affecte le comportement de CompleteWait.

Nombre par défaut de CPU alloués par GPU alloué. Cette valeur est utilisée uniquement si le travail n'a pas spécifié --cpus-per-task et --cpus-per-gpu.
DefMemPerCPU
Taille de mémoire réelle par défaut disponible par CPU alloué utilisable en mégaoctets. Utilisé pour éviter la sur-allocation de mémoire
y et provoquant la pagination. DefMemPerCPU serait généralement utilisé si des processeurs individuels sont alloués aux travaux (SelectType=select/cons_tres). La valeur par défaut est 0 (illimitée). Voir aussi DefMemPerGPU, DefMemPerNode et MaxMemPerCPU. DefMemPerCPU, DefMemPerGPU et DefMemPerNode sont mutuellement exclusifs.

NOTE : Ceci s'applique aux CPU alloués utilisables dans une allocation de travail. Ceci est important lorsque plus d'un thread par cœur est configuré. Si un travail demande --threads-per-core avec moins de threads sur un cœur que ce qui existe sur le cœur (ou --hint=nomultithread qui implique --threads-per-core=1), le travail ne pourra pas utiliser ces threads supplémentaires sur le cœur et ces threads ne seront pas inclus dans le calcul de la mémoire par CPU. Mais si le travail a accès à tous les threads sur le cœur, ces threads seront inclus dans le calcul de la mémoire par CPU même si le travail n'a pas explicitement demandé ces threads.

Dans les exemples suivants, chaque cœur a deux threads.

Dans ce premier exemple, deux tâches peuvent s'exécuter sur des hyperthreads séparés dans le même cœur car --threads-per-core n'est pas utilisé. La troisième tâche utilise les deux threads du deuxième cœur. La mémoire allouée par CPU inclut tous les threads :

$ salloc -n3 --mem-per-cpu=100
salloc: Granted job allocation 17199
$ sacct -j $SLURM_JOB_ID -X -o jobid%7,reqtres%35,alloctres%35
  JobID                             ReqTRES                           AllocTRES
------- ----------------------------------- -----------------------------------
  17199     billing=3,cpu=3,mem=300M,node=1     billing=4,cpu=4,mem=400M,node=1

Dans ce deuxième exemple, en raison de --threads-per-core=1, chaque tâche se voit attribuer un cœur entier mais ne peut utiliser qu'un seul thread par cœur. Les CPU alloués incluent tous les threads sur chaque cœur. Cependant, la mémoire allouée par CPU n'inclut que le thread utilisable sur chaque cœur.

$ salloc -n3 --mem-per-cpu=100 --threads-per-core=1
salloc: Granted job allocation 17200
$ sacct -j $SLURM_JOB_ID -X -o jobid%7,reqtres%35,alloctres%35
  JobID                             ReqTRES                           AllocTRES
------- ----------------------------------- -----------------------------------
  17200     billing=3,cpu=3,mem=300M,node=1     billing=6,cpu=6,mem=300M,node=1

DependencyParameters
Plusieurs options peuvent être séparées par des virgules.
disable_remote_singleton
Par défaut, lorsqu'un travail fédéré a une dépendance singleton, chaque cluster de la fédération doit effacer la dépendance singleton avant que la dépendance singleton du travail ne soit considérée comme satisfaite. L'activation de cette option signifie que seul le cluster d'origine doit effacer la dépendance singleton. Cette option doit être définie dans chaque cluster de la fédération.
kill_invalid_depend
Si un travail a une dépendance invalide et qu'il ne peut jamais s'exécuter, terminez-le et définissez son état sur JOB_CANCELLED. Par défaut, le travail reste en attente avec la raison DependencyNeverSatisfied.
max_depend_depth=Nombre maximum de travaux à tester pour une dépendance de travaux circulaire. Arrêter les tests
après ce nombre de dépendances de travaux testées. La valeur par défaut est de 10 travaux.
DisableRootJobs
Si défini sur "YES", l'utilisateur root sera empêché d'exécuter des travaux. La valeur par défaut est "NO", ce qui signifie que l'utilisateur root pourra exécuter des travaux. DisableRootJobs peut également être défini par partition.
EioTimeout
Le nombre de secondes pendant lesquelles srun attend que slurmstepd ferme la connexion TCP/IP utilisée pour relayer les données entre l'application utilisateur et srun lorsque l'application utilisateur se termine. La valeur par défaut est de 60 secondes. Ne peut pas dépasser 65533.
EnforcePartLimits
Contrôle si les limites de partition sont appliquées lors de la soumission d'un travail au cluster. Les limites de partition considérées par cette option sont MaxMemPerCPU, MaxMemPerNode, MinNodes, MaxNodes, MaxTime, AllocNodes, AllowAccounts, AllowGroups, AllowQOS et le seuil d'utilisation QOS configurés. Elle considère également si le travail demande plus de nœuds qu'il n'en existe dans la partition. Si défini, un travail et un QOS de travail ne peuvent pas être soumis qui dépassent les limites de partition.
ALL
Les travaux qui dépassent le nombre de nœuds dans une partition et/ou l'une de ses limites configurées seront rejetés au moment de la soumission. Si le travail est soumis à plusieurs partitions, le travail doit satisfaire aux limites de toutes les partitions demandées.
ANY
Les travaux seront acceptés s'ils satisfont aux limites d'au moins une des partitions demandées.
NO
Les limites de partition ne seront pas appliquées au moment de la soumission, mais seront toujours appliquées pendant la planification. Cela inclut les travaux qui demandent plus de nœuds qu'il n'en existe dans l'une des partitions, de sorte que les travaux puissent être soumis à des partitions vides. Un travail qui dépasse les limites de toutes les partitions demandées restera en file d'attente jusqu'à ce que les limites de partition soient modifiées. C'est la valeur par défaut.
Epilog
Chemin d'accès à un script à exécuter en tant qu'utilisateur root sur chaque nœud lorsque le travail d'un utilisateur se termine (par exemple, "/usr/local/slurm/epilog"). S'il ne s'agit pas d'un chemin absolu (c'est-à-dire qu'il ne commence pas par un slash), il sera recherché dans le même répertoire que le fichier slurm.conf. Un modèle glob (voir glob(7)) peut également être utilisé pour exécuter plusieurs scripts d'épilogue (par exemple, "/etc/slurm/epilog.d/*"). Lorsque plusieurs scripts d'épilogue sont configurés, ils sont exécutés par ordre alphabétique inverse (z-a -> Z-A -> 9-0). Le(s) script(s) d'épilogue peut (peuvent) être utilisé(s) pour purger des fichiers, désactiver la connexion utilisateur, etc. Par défaut, il n'y a pas d'épilogue. Voir Prolog and Epilog Scripts pour plus d'informations.

NOTE : Il est possible de configurer plusieurs scripts d'épilogue en incluant cette option sur plusieurs lignes.

EpilogMsgTime
Le nombre de microsecondes dont le démon slurmctld a besoin pour traiter un message de complétion d'épilogue des démons slurmd. Ce paramètre peut être utilisé pour éviter qu'une rafale de messages de complétion d'épilogue ne soit envoyée en même temps, ce qui devrait aider à éviter les messages perdus et à améliorer le débit pour les gros travaux. La valeur par défaut est de 2000 microsecondes. Pour un travail de 1000 nœuds, cela répartit les messages de complétion d'épilogue sur deux secondes.

JobAcctGatherType
Le plugin JobAcctGather collecte des informations sur l'utilisation de la mémoire, du processeur, des E/S, de l'interconnexion, de l'énergie et du GPU au niveau des tâches, en fonction des plugins configurés dans Slurm. Ce paramètre contrôlera la manière dont certaines de ces métriques seront collectées. Non défini par défaut.

Valeurs configurables à l'heure actuelle:

jobacct_gather/cgroup (recommandé)
Collecte les statistiques du processeur et de la mémoire en lisant les interfaces du répertoire cgroup de la tâche (par exemple, memory.stat, cpu.stat) en appelant le CgroupPlugin configuré (voir "man cgroup.conf"). Ce mécanisme ignore JobAcctGatherParams=UsePSS ou NoShared car ils ne sont utilisés que lors de la lecture de l'utilisation de la mémoire depuis le système de fichiers proc.
jobacct_gather/linux
Collecte les statistiques du processeur et de la mémoire en lisant le procfs. Le plugin prendra tous les pids de la tâche et pour chacun d'eux lira /proc/<pid>/stats. Si UsePSS est défini, il lira également /proc/<pid>/smaps, et si NoShare est défini, il lira également /proc/<pid>/statm (voir JobAcctGatherParams pour plus d'informations).

Ce plugin entraîne une pénalité de performance sur les travaux comportant un grand nombre de processus lancés car il doit parcourir tous les pids des tâches et agréger les statistiques en une seule métrique pour le ppid, puis ces valeurs doivent être agrégées aux statistiques de la tâche.

NOTE: Il est possible de changer le type de plugin lorsque des travaux sont en cours d'exécution dans le cluster. Les étapes déjà en cours continueront à utiliser l'ancien mécanisme de plugin, tandis que les nouvelles étapes utiliseront le nouveau mécanisme.

Les travaux peuvent être remis en file d'attente explicitement par un administrateur système, après une défaillance de nœud ou suite à une préemption par un travail de priorité supérieure. Si JobRequeue est défini sur 1, les travaux batch peuvent être remis en file d'attente sauf s'ils sont explicitement désactivés par l'utilisateur. Si JobRequeue est défini sur 0, les travaux batch ne seront pas remis en file d'attente sauf s'ils sont explicitement activés par l'utilisateur. Utilisez l'option sbatch --no-requeue ou --requeue pour changer le comportement par défaut pour les travaux individuels. La valeur par défaut est 1.

LogTimeFormat

Les valeurs se terminant par "_ms" diffèrent de celles sans par le fait que les secondes fractionnaires avec une précision en millisecondes sont imprimées. La valeur par défaut est "iso8601_ms". Le nombre maximum de travaux que slurmctld peut avoir en mémoire à la fois. À combiner avec MinJobAge pour s'assurer que le démon slurmctld n'épuise pas sa mémoire ou d'autres ressources. Une fois cette limite atteinte, les demandes de soumission de travaux supplémentaires échoueront. La valeur par défaut est 10000 travaux. Définir MaxSubmitJobs par utilisateur est généralement utile pour éviter qu'un seul utilisateur ne remplisse le système de travaux. L'ID de travail local maximal autorisé est 67 108 863 (0x3FFFFFF). La valeur par défaut est 67 043 328 (0x03ff0000). MaxJobId ne s'applique qu'à l'ID de travail local et non à l'ID de travail fédéré. Les valeurs d'ID de travail générées seront incrémentées de 1 pour chaque travail suivant. Une fois MaxJobId atteint, le travail suivant se verra attribuer FirstJobId. Les travaux fédérés auront toujours un ID de travail de 67 108 865 ou plus. Voir également FirstJobId.

PreemptMode
Mécanisme utilisé pour préempter les jobs ou activer la planification gang. Lorsque le paramètre PreemptType est défini pour activer la préemption, PreemptMode sélectionne le mécanisme par défaut utilisé pour préempter les jobs éligibles pour le cluster.
PreemptMode peut être spécifié par partition pour remplacer la valeur par défaut si PreemptType=preempt/partition_prio. Alternativement, il peut être spécifié par QOS si PreemptType=preempt/qos. Dans les deux cas, une valeur valide de PreemptMode doit être spécifiée pour l'ensemble du cluster lorsque la préemption est activée.
L'option GANG est utilisée pour activer la planification gang indépendamment de l'activation de la préemption (c'est-à-dire indépendamment du paramètre PreemptType). Elle peut être spécifiée en plus d'un paramètre PreemptMode, les deux options étant séparées par une virgule (par exemple, PreemptMode=SUSPEND,GANG).
Voir https://slurm.schedmd.com/preempt.html et https://slurm.schedmd.com/gang_scheduling.html pour plus de détails.

NOTE : Pour des raisons de performance, le planificateur backfill réserve des nœuds entiers pour les tâches, et non des nœuds partiels. Si, lors de la planification backfill, une tâche préempte une ou plusieurs autres tâches, les nœuds entiers de ces tâches préemptées sont réservés pour la tâche préemptrice, même si la tâche préemptrice a demandé moins de ressources. Ces nœuds réservés ne sont pas disponibles pour d'autres tâches pendant ce cycle de backfill, même si les autres tâches pourraient tenir sur les nœuds. Par conséquent, les tâches peuvent préempter plus de ressources lors d'une itération de backfill que ce qu'elles ont demandé.
NOTE : Pour qu'une tâche hétérogène soit prise en compte pour la préemption, tous ses composants doivent être éligibles à la préemption. Lorsqu'une tâche hétérogène doit être préemptée, le premier composant identifié de la tâche avec le PreemptMode le plus élevé (SUSPEND (le plus élevé), REQUEUE, CANCEL (le plus bas)) sera utilisé pour définir le PreemptMode pour tous les composants. Le GraceTime et le signal d'avertissement utilisateur pour chaque composant de la tâche hétérogène restent uniques. Les tâches hétérogènes sont exclues des opérations de planification gang.

OFF
Est la valeur par défaut et désactive la préemption de tâche et la planification gang. Elle n'est compatible qu'avec la désactivation de la préemption au niveau global. Un cas d'utilisation courant pour ce paramètre est de le définir sur une partition pour désactiver la préemption pour cette partition.
CANCEL
La tâche préemptée sera annulée.
GANG
Active la planification gang (time slicing) des tâches dans la même partition, et permet la reprise des tâches suspendues. Pour utiliser la planification gang, l'option GANG doit être spécifiée au niveau du cluster.

NOTE : Si la planification GANG est activée avec PreemptType=preempt/partition_prio, le contrôleur ignorera PreemptExemptTime et les PreemptParameters suivants : reorder_count, strict_order et youngest_first.

NOTE : La planification gang est effectuée indépendamment pour chaque partition, donc si vous souhaitez uniquement un time-slicing par OverSubscribe, sans aucune préemption, il n'est pas recommandé de configurer des partitions avec des nœuds qui se chevauchent. D'autre part, si vous souhaitez utiliser PreemptType=preempt/partition_prio pour permettre aux tâches des partitions de PriorityTier plus élevé de suspendre les tâches des partitions de PriorityTier plus bas, vous aurez besoin de partitions qui se chevauchent, et de PreemptMode=SUSPEND,GANG pour utiliser le planificateur Gang afin de reprendre la ou les tâches suspendues. Vous devez configurer le paramètre OverSubscribe de la partition sur FORCE pour toutes les partitions où le time-slicing doit avoir lieu. Dans tous les cas, le time-slicing n'aura pas lieu entre les tâches de partitions différentes.

NOTE : Les tâches hétérogènes sont exclues des opérations de planification GANG.

NOTE : En cas de partitions qui se chevauchent. Si le nœud est alloué à une tâche qui autorise le partage de ressources (Oversubscribe=FORCE ou Oversubscribe=YES et la tâche a été soumise avec -s/--oversubscribe), il ne peut être alloué qu'à des tâches de la même partition.

REQUEUE
Prépempte les tâches en les remettant dans la file d'attente (si possible) ou en les annulant. Pour que les tâches soient remises dans la file d'attente, elles doivent avoir l'option --requeue de sbatch définie ou le paramètre JobRequeue au niveau du cluster dans slurm.conf doit être défini sur 1.
SUSPEND
Les tâches préemptées seront suspendues, et plus tard le planificateur Gang les reprendra. Par conséquent, le mode de préemption SUSPEND a toujours besoin que l'option GANG soit spécifiée au niveau du cluster. De plus, comme les tâches suspendues continueront d'utiliser de la mémoire sur les nœuds alloués, Slurm doit être capable de suivre les ressources mémoire pour pouvoir suspendre les tâches.
Lors de la suspension des tâches, Slurm envoie le signal SIGTSTP, attend le temps spécifié par PreemptParameters=suspend_grace_time (par défaut 2 secondes), puis envoie le signal SIGSTOP. Le signal SIGCONT est envoyé lors de la reprise des tâches.
Si PreemptType=preempt/qos est configuré et si les tâches préemptées et la tâche préemptrice sont sur la même partition, alors elles partageront les ressources avec le planificateur Gang (time-slicing). Sinon (c'est-à-dire si les tâches préemptées et préemptrice sont sur des partitions différentes), les tâches préemptées resteront suspendues jusqu'à ce que la tâche préemptrice se termine.

NOTE : Comme la planification gang est effectuée indépendamment pour chaque partition, si vous utilisez PreemptType=preempt/partition_prio, les tâches des partitions de PriorityTier plus élevé suspendront les tâches des partitions de PriorityTier plus bas pour s'exécuter sur les ressources libérées. Ce n'est que lorsque la tâche préemptrice se termine que les tâches suspendues seront reprises par le planificateur Gang.
NOTE : Les tâches suspendues ne libéreront pas les GRES. Les tâches de priorité plus élevée ne pourront pas préempter pour accéder aux GRES.

PRIORITY
Autorise la préemption uniquement si la priorité de la tâche préemptrice est plus élevée que la priorité de la tâche préemptée.
WITHIN
Pour PreemptType=preempt/qos, autorise les tâches au sein du même qos à se préempter mutuellement. Bien que cela puisse être défini globalement ici, il est recommandé de ne le définir directement que sur un sous-ensemble pertinent des valeurs qos du système.

C'est une méthode de travail beaucoup plus rapide et si vous utilisez srun pour lancer vos tâches, vous devriez utiliser cet indicateur. ResumeProgram
Slurm prend en charge un mécanisme pour réduire la consommation d'énergie sur les nœuds qui restent inactifs pendant une période prolongée. Ceci est généralement réalisé en réduisant la tension et la fréquence ou en éteignant le nœud. ResumeProgram est le programme qui sera exécuté lorsqu'un nœud en mode d'économie d'énergie se voit attribuer une tâche à effectuer. Pour des raisons de fiabilité, ResumeProgram peut s'exécuter plus d'une fois pour un nœud lorsque le démon slurmctld plante et est redémarré. Si ResumeProgram ne parvient pas à remettre un nœud en service avec un slurmd répondant et un BootTime mis à jour, il doit définir l'état du nœud sur HORS SERVICE, ce qui entraînera la remise en file d'attente de tout travail associé au nœud - cela se produira automatiquement si le nœud ne s'enregistre pas dans le délai ResumeTimeout. SchedulerParameters=requeue_on_resume_failure peut être utilisé pour toujours remettre en file d'attente les travaux batch dans cette situation, même si le travail n'a demandé aucune remise en file d'attente. Si le nœud n'est pas réellement redémarré (par exemple, lorsque le mode multiple-slurmd est configuré), le démarrage de slurmd avec l'option "-b" peut être utile. Le programme s'exécute en tant que SlurmUser. L'argument du programme sera les noms des nœuds à retirer du mode d'économie d'énergie (en utilisant le format d'expression de liste d'hôtes de Slurm). Une correspondance entre les travaux et les nœuds est disponible au format JSON en lisant le fichier temporaire spécifié par la variable d'environnement SLURM_RESUME_FILE. Ce fichier est fermé une fois que slurmctld s'arrête. Si ResumeProgram est en cours d'exécution, l'arrêt de slurmctld est retardé jusqu'à dix secondes pour donner à ResumeProgram le temps de lire ce fichier. Par conséquent, ce fichier doit être lu au début de ResumeProgram. Par défaut, aucun programme n'est exécuté. Les programmes seront tués s'ils s'exécutent plus longtemps que la plus longue durée configurée, globale ou de partition, de ResumeTimeout ou SuspendTimeout.

Le taux auquel les nœuds en mode d'économie d'énergie reviennent à leur fonctionnement normal par ResumeProgram. La valeur est un nombre de nœuds par minute et elle peut être utilisée pour éviter les surtensions de courant si un grand nombre de nœuds en mode d'économie d'énergie se voient attribuer des tâches en même temps (par exemple, un grand travail démarre). Une valeur de zéro ne limite pas. La valeur par défaut est de 300 nœuds par minute.
ResumeTimeout
Temps maximal autorisé (en secondes) entre le moment où une demande de reprise de nœud est émise et le moment où le nœud est réellement disponible pour utilisation. Les nœuds qui ne répondent pas dans ce délai seront marqués comme HORS SERVICE et les travaux programmés sur le nœud seront remis en file d'attente si possible. Les nœuds qui redémarrent après ce délai seront marqués comme HORS SERVICE avec la raison "Nœud redémarré de manière inattendue.". La valeur par défaut est de 60 secondes, et la valeur maximale est soit 65533, soit INFINIE.

ReturnToService
Contrôle quand un nœud DOWN sera remis en service. La valeur par défaut est 0. Les valeurs prises en charge incluent :

Par défaut, le planificateur de backfill n'ajoutera pas de slot dans le plan bf lorsqu'un travail tente d'utiliser une réservation magnétique. Au début de chaque cycle de planification de backfill, une liste des travaux en attente à planifier est triée selon l'ordre de priorité configuré dans PriorityType. Cette option demande au planificateur de modifier l'algorithme de tri pour garantir que tous les composants appartenant au même travail hétérogène seront tentés d'être planifiés consécutivement (donc non fragmentés dans la liste résultante). Plus spécifiquement, tous les composants du même travail hétérogène seront traités comme s'ils avaient tous la même priorité (minimale, moyenne ou maximale selon le paramètre de cette option) lorsqu'ils sont comparés à d'autres travaux (ou à d'autres composants de travaux hétérogènes). L'ordre original sera préservé au sein du même travail hétérogène. Notez que l'opération est calculée pour la couche PriorityTier et pour la Priority résultant des calculs du plugin priority/multifactor. Lorsqu'elle est activée, si un travail hétérogène demande une réservation avancée, alors tous les composants de ce travail seront traités comme s'ils avaient demandé une réservation avancée (et bénéficieront d'un traitement préférentiel en planification).

Notez que cette opération ne met pas à jour les valeurs de Priority des composants du travail hétérogène, seulement leur ordre dans la liste, donc la sortie de la commande sprio ne sera pas affectée.

Les travaux hétérogènes ont des propriétés de planification spéciales : ils ne sont planifiés que par le plugin de planification de backfill, chaque composant est considéré séparément lors de la réservation de ressources (et peut avoir un PriorityTier différent ou des valeurs de Priority différentes), et aucun composant de travail hétérogène ne se voit attribuer de ressources tant que tous ses composants ne peuvent pas être initiés. Cela peut impliquer des scénarios potentiels de blocage de planification car les composants de différents travaux hétérogènes peuvent commencer à réserver des ressources de manière entrelacée (non consécutive), mais aucun des travaux ne peut réserver de ressources pour tous ses composants et démarrer. L'activation de cette option peut aider à atténuer ce problème. Par défaut, cette option est désactivée.

Les spécifications de mémoire dans les requêtes de travail s'appliquent à la taille de la mémoire réelle (également connue sous le nom de taille de l'ensemble résident). Il est possible d'appliquer des limites de mémoire virtuelle pour les travaux et les étapes de travail en limitant leur mémoire virtuelle à un certain pourcentage de leur allocation de mémoire réelle. Le paramètre VSizeFactor spécifie la limite de mémoire virtuelle du travail ou de l'étape de travail en pourcentage de sa limite de mémoire réelle. CONFIGURATION DES NŒUDS

La configuration des nœuds (ou machines) à gérer par Slurm est également spécifiée dans /etc/slurm.conf. Les changements dans la configuration des nœuds (par exemple, l'ajout de nœuds, la modification de leur nombre de processeurs, etc.) nécessitent le redémarrage ou la reconfiguration de tous les démons slurmctld et slurmd. Tous les démons slurmd doivent connaître chaque nœud du système pour transmettre des messages afin de supporter la communication hiérarchique. Seul NodeName doit être fourni dans le fichier de configuration. Toutes les autres informations de configuration du nœud sont facultatives. Il est conseillé d'établir des configurations de nœuds de base, surtout si le cluster est hétérogène. Les nœuds qui s'enregistrent auprès du système avec moins de ressources configurées (par exemple, trop peu de mémoire) seront placés dans l'état "DOWN" pour éviter de leur planifier des travaux. L'établissement de configurations de base accélérera également le processus de planification de Slurm en lui permettant de comparer les exigences des travaux par rapport à ces paramètres de configuration (relativement peu nombreux) et potentiellement d'éviter d'avoir à vérifier les exigences des travaux par rapport à la configuration de chaque nœud individuel. Les ressources vérifiées lors de l'enregistrement du nœud sont : CPU, RealMemory et TmpDisk.

Les valeurs par défaut peuvent être spécifiées avec un enregistrement dans lequel NodeName est "DEFAULT". Les valeurs par défaut s'appliqueront uniquement aux lignes qui suivent dans le fichier de configuration et les valeurs par défaut peuvent être réinitialisées plusieurs fois dans le fichier de configuration avec plusieurs entrées où "NodeName=DEFAULT". Chaque ligne où NodeName est "DEFAULT" remplacera ou ajoutera aux valeurs par défaut précédentes et ne réinitialisera pas les valeurs par défaut. La spécification "NodeName=" doit être placée sur chaque ligne décrivant la configuration des nœuds. Un seul nom de nœud ne peut pas apparaître en tant que valeur NodeName dans plus d'une ligne (les enregistrements de noms de nœuds dupliqués seront ignorés). En fait, il est généralement possible et souhaitable de définir la configuration de tous les nœuds en quelques lignes seulement. Cette convention permet une optimisation significative dans la planification des clusters plus grands. Afin de supporter le concept de travaux nécessitant des nœuds consécutifs sur certaines architectures, les spécifications de nœuds doivent être placées dans ce fichier dans un ordre consécutif. Aucun nom de nœud unique ne peut être listé plus d'une fois dans le fichier de configuration. Utilisez "DownNodes=" pour enregistrer l'état des nœuds qui sont temporairement dans un état DOWN, DRAIN ou FAILING sans modifier les informations de configuration permanentes. Les tâches d'une étape de travail sont allouées aux nœuds dans l'ordre où les nœuds apparaissent dans le fichier de configuration. Il n'existe actuellement aucune capacité au sein de Slurm pour ordonner arbitrairement les tâches d'une étape de travail.

Plusieurs noms de nœuds peuvent être séparés par des virgules (par exemple, "alpha,beta,gamma") et/ou une expression simple de plage de nœuds peut éventuellement être utilisée pour spécifier des plages numériques de nœuds afin d'éviter la création d'un fichier de configuration avec un grand nombre d'entrées. L'expression de plage de nœuds peut contenir une paire de crochets avec une séquence de nombres séparés par des virgules et/ou des plages de nombres séparées par un "-" (par exemple, "linux[0-64,128]", ou "lx[15,18,32-33]"). Notez que les plages numériques peuvent inclure un ou plusieurs zéros non significatifs pour indiquer que la partie numérique a un nombre fixe de chiffres (par exemple, "linux[0000-1023]"). Plusieurs plages numériques peuvent être incluses dans l'expression (par exemple, "rack[0-63]_blade[0-41]"). Si une ou plusieurs expressions numériques sont incluses, l'une d'elles doit se trouver à la fin du nom (par exemple, "unit[0-31]rack" est invalide), mais des noms arbitraires peuvent toujours être utilisés.

La configuration du nœud a spécifié les informations suivantes :

NodeName
Nom utilisé par Slurm pour désigner un nœud. Typiquement, il s'agirait de la chaîne retournée par "/bin/hostname -s". Il peut également s'agir du nom de domaine complet tel que retourné par "/bin/hostname -f" (par exemple, "foo1.bar.com"), ou de tout nom de domaine valide associé à l'hôte via la base de données des hôtes (/etc/hosts) ou DNS, en fonction des paramètres du résolveur. Notez que si la forme courte du nom d'hôte n'est pas utilisée, cela peut empêcher l'utilisation des expressions de liste d'hôtes (la partie numérique entre crochets doit être à la fin de la chaîne). Il peut également s'agir d'une chaîne arbitraire si NodeHostname est spécifié. Si le NodeName est "DEFAULT", les valeurs spécifiées avec cet enregistrement s'appliqueront aux spécifications de nœuds ultérieures, sauf si elles sont explicitement définies à d'autres valeurs dans cet enregistrement de nœud ou remplacées par un autre ensemble de valeurs par défaut. Chaque ligne où NodeName est "DEFAULT" remplacera ou ajoutera aux valeurs par défaut précédentes et ne réinitialisera pas les valeurs par défaut. Pour les architectures dans lesquelles l'ordre des nœuds est significatif, les nœuds seront considérés comme consécutifs dans l'ordre défini. Par exemple, si la configuration pour "NodeName=charlie" suit immédiatement la configuration pour "NodeName=baker", ils seront considérés comme adjacents dans l'ordinateur. NOTE : Si le NodeName est "ALL", le processus qui analyse la configuration se terminera immédiatement car il s'agit d'un mot réservé en interne.
NodeHostname
Typiquement, il s'agirait de la chaîne retournée par "/bin/hostname -s". Il peut également s'agir du nom de domaine complet tel que retourné par "/bin/hostname -f" (par exemple, "foo1.bar.com"), ou de tout nom de domaine valide associé à l'hôte via la base de données des hôtes (/etc/hosts) ou DNS, en fonction des paramètres du résolveur. Notez que si la forme courte du nom d'hôte n'est pas utilisée, cela peut empêcher l'utilisation des expressions de liste d'hôtes (la partie numérique entre crochets doit être à la fin de la chaîne). Une expression de plage de nœuds peut être utilisée pour spécifier un ensemble de nœuds. Si une expression est utilisée, le nombre de nœuds identifiés par NodeHostname sur une ligne du fichier de configuration doit être identique au nombre de nœuds identifiés par NodeName. Par défaut, le NodeHostname sera identique en valeur au NodeName.
NodeAddr
Nom utilisé par un nœud pour établir un chemin de communication. Ce nom sera utilisé comme argument de la fonction getaddrinfo() pour l'identification. Si une expression de plage de nœuds est utilisée pour désigner plusieurs nœuds, elle doit correspondre exactement aux entrées de NodeName (par exemple, "NodeName=lx[0-7] NodeAddr=elx[0-7]"). NodeAddr peut également contenir des adresses IP. Par défaut, le NodeAddr sera identique en valeur au NodeHostname.
BcastAddr
Chemin réseau alternatif à utiliser pour le trafic réseau sbcast vers un nœud donné. Ce nom sera utilisé comme argument de la fonction getaddrinfo(). Si une expression de plage de nœuds est utilisée pour désigner plusieurs nœuds, elle doit correspondre exactement aux entrées de NodeName (par exemple, "NodeName=lx[0-7] BcastAddr=elx[0-7]"). BcastAddr peut également contenir des adresses IP. Par défaut, BcastAddr n'est pas défini et le trafic sbcast sera acheminé vers le NodeAddr d'un nœud donné. Note : ne peut pas être utilisé avec CommunicationParameters=NoInAddrAny.
Boards
Nombre de cartes mères dans les nœuds dotés d'un contrôleur de carte mère. Notez que lorsque Boards est spécifié, SocketsPerBoard, CoresPerSocket et ThreadsPerCore doivent également l'être. La valeur par défaut est 1.
CoreSpecCount
Nombre de cœurs réservés pour l'utilisation système. Selon l'option TaskPluginParam de SlurmdOffSpec, le démon Slurm slurmd peut être confiné à ces ressources (par défaut) ou empêché d'utiliser ces ressources. Si cgroup/v1 est utilisé, il en va de même pour les processus slurmstepd. L'isolation de slurmd des tâches utilisateur peut améliorer les performances de l'application. Une tâche peut utiliser ces cœurs si AllowSpecResourcesUsage=yes et si l'utilisateur demande explicitement moins que le CoreSpecCount configuré. Si cette option et CpuSpecList sont toutes deux désignées pour un nœud, une erreur est générée. Pour plus d'informations sur l'algorithme utilisé par Slurm pour sélectionner les cœurs, reportez-vous à la documentation sur la spécialisation des cœurs ( https://slurm.schedmd.com/core_spec.html ).
CoresPerSocket
Nombre de cœurs dans un seul socket de processeur physique (par exemple, "2"). La valeur de CoresPerSocket décrit les cœurs physiques, et non le nombre logique de processeurs par socket. NOTE : Si vous avez des processeurs multi-cœurs, vous devrez probablement spécifier ce paramètre afin d'optimiser la planification. La valeur par défaut est 1.
CpuBind
Si une demande d'étape de tâche ne spécifie pas d'option pour contrôler la manière dont les tâches sont liées aux CPU alloués (en utilisant --cpu-bind) et si tous les nœuds alloués à la tâche ont la même option CpuBind, l'option CpuBind du nœud contrôlera la manière dont les tâches sont liées aux ressources allouées. Les définitions de partition sont utilisées ensuite si les définitions de nœud ne peuvent pas être utilisées, suivies de TaskPluginParam en dernier recours, avec par défaut aucune liaison. Les valeurs prises en charge pour CpuBind sont none, socket, ldom (NUMA), core et thread.
CPUs
Nombre de processeurs logiques sur le nœud (par exemple, "2"). Il peut être défini sur le nombre total de sockets (pris en charge uniquement par select/linear), de cœurs ou de threads. Cela peut être utile lorsque vous souhaitez planifier uniquement les cœurs sur un nœud hyper-threadé. Si CPUs est omis, sa valeur par défaut sera égale au produit de Boards, Sockets, CoresPerSocket et ThreadsPerCore.
CpuSpecList
Une liste d'identifiants CPU abstraits Slurm séparés par des virgules et réservés pour l'utilisation système. La liste sera étendue pour inclure tous les autres CPU, le cas échéant, sur les mêmes cœurs. Selon l'option TaskPluginParam de SlurmdOffSpec, le démon Slurm slurmd peut être confiné à ces ressources (par défaut) ou empêché d'utiliser ces ressources. Si cgroup/v1 est utilisé, il en va de même pour les processus slurmstepd. L'isolation de slurmd des tâches utilisateur peut améliorer les performances de l'application. Une tâche peut utiliser ces cœurs si AllowSpecResourcesUsage=yes et si l'utilisateur demande explicitement moins que le nombre de CPU dans cette liste. Si cette option et CoreSpecCount sont toutes deux désignées pour un nœud, une erreur est générée. Cette option n'a aucun effet à moins que le confinement des tâches cgroup ne soit également configuré (c'est-à-dire que le TaskPlugin task/cgroup soit activé et que ConstrainCores=yes soit défini dans cgroup.conf).
Features
Une liste de chaînes de caractères arbitraires séparées par des virgules, indiquant une caractéristique associée au nœud. Il n'y a pas de valeur ou de compte associé à une caractéristique pour le moment, un nœud possède une caractéristique ou non. Une caractéristique souhaitée peut contenir un composant numérique indiquant, par exemple, la vitesse du processeur, mais ce composant numérique sera considéré comme faisant partie de la chaîne de caractéristiques. Les caractéristiques sont destinées à être utilisées pour filtrer les nœuds éligibles à l'exécution de tâches via l'argument --constraint. Par défaut, un nœud n'a pas de caractéristiques. Voir également Gres pour avoir plus de contrôle, comme les types et le nombre. L'utilisation de caractéristiques est plus rapide que la planification sur GRES, mais elle est limitée aux opérations booléennes.

NOTE : La fonction de liste d'hôtes feature{myfeature} s'étend à tous les nœuds ayant la caractéristique spécifiée. Elle peut être utilisée à la place ou en plus des expressions de liste d'hôtes régulières dans les commandes ou les fichiers de configuration qui interagissent avec slurmctld. Par exemple : scontrol update node=feature{myfeature} state=resume ou PartitionName=p1 Nodes=feature{myfeature}.

Gres
Une liste de spécifications de ressources génériques pour un nœud, séparées par des virgules. Le format est : "<nom>[:<type>][:no_consume]:<nombre>[K|M|G]". Le premier champ est le nom de la ressource, qui correspond au nom du paramètre de configuration GresType. Le champ de type optionnel peut être utilisé pour identifier un modèle de cette ressource générique. Il est interdit de spécifier à la fois un GRES non typé et un GRES typé avec le même <nom>. Le champ facultatif no_consume vous permet de spécifier qu'une ressource générique n'a pas un nombre fini de cette ressource qui est consommé lorsqu'elle est demandée. Le champ no_consume est un paramètre spécifique au GRES et s'applique au GRES, quel que soit le type spécifié. Il ne doit pas être utilisé avec des GRES qui ont un plugin dédié ; si vous cherchez un moyen de surallouer des GPU à plusieurs processus à la fois, vous pourriez envisager d'utiliser le GRES "shard" à la place. Le dernier champ doit spécifier un nombre de ressources génériques. Un suffixe "K", "M", "G", "T" ou "P" peut être utilisé pour multiplier le nombre par 1024, 1048576, 1073741824, etc. respectivement. (par exemple, "Gres=gpu:tesla:1,gpu:kepler:1,bandwidth:lustre:no_consume:4G"). Par défaut, un nœud n'a pas de ressources génériques et son nombre maximum est celui d'un entier non signé de 64 bits. Voir également Features pour des indicateurs booléens permettant de filtrer les nœuds en utilisant les contraintes de tâche.

MemSpecLimit
Quantité de RealMemory, en mégaoctets, réservée pour l'utilisation du système et non disponible pour les allocations utilisateur. Doit être inférieure à la quantité définie pour RealMemory. Si le plugin task/cgroup est configuré et que ce plugin contraint les allocations mémoire (c'est-à-dire si le plugin TaskPlugin task/cgroup est activé et que ConstrainRAMSpace=yes est défini dans cgroup.conf), alors le slurmd recevra la limite de mémoire spécifiée. Si cgroup/v1 est utilisé, le slurmstepd recevra également la limite de mémoire spécifiée. Si cgroup/v2 est utilisé, la consommation du slurmstepd dépend entièrement de la topologie du job. Si le plugin task/cgroup n'est pas configuré, la mémoire spécifiée sera uniquement indisponible pour les allocations utilisateur.
Parameters
Permet des ajouts spécifiques aux nœuds aux SlurmdParameters globaux. Les options sont ajoutées et ne peuvent pas outrepasser les options globales.
Port
Le numéro de port sur lequel le démon du nœud de calcul Slurm, slurmd, écoute pour travailler sur ce nœud particulier. L'utilisation de cette option n'est généralement pas recommandée, sauf à des fins de développement ou de test. Si plusieurs démons slurmd s'exécutent sur un nœud, cela peut spécifier une plage de ports.

RealMemory
Taille de la mémoire réelle sur le nœud en mégaoctets (par exemple, "2048"). La valeur par défaut est 1. Diminuer RealMemory dans le but de réserver une partie pour le système d'exploitation et non disponible pour les allocations de jobs ne fonctionnera pas comme prévu si Memory n'est pas défini comme une ressource consommable dans SelectTypeParameters. Par conséquent, l'une des options *_Memory doit être activée pour que cet objectif soit atteint. Voir aussi MemSpecLimit.
Reason
Identifie la raison pour laquelle un nœud est dans l'état "DOWN", "DRAINED", "DRAINING", "FAIL" ou "FAILING". Utilisez des guillemets pour inclure une raison comportant plus d'un mot.
RestrictedCoresPerGPU
Nombre de cœurs par GPU restreints uniquement à l'utilisation des GPU. Si un job ne demande pas de GPU, il n'aura pas accès à ces cœurs. Les GPU du nœud doivent être autodétectés ou avoir des cœurs valides configurés dans gres.conf(5).

Sockets
Nombre de sockets/puces de processeur physiques sur le nœud (par exemple, "2"). Si Sockets est omis, il sera déduit de CPUs, CoresPerSocket et ThreadsPerCore. NOTE : Si vous avez des processeurs multi-cœurs, vous devrez probablement spécifier ces paramètres. Sockets et SocketsPerBoard sont mutuellement exclusifs. Si Sockets est spécifié en même temps que Boards, Sockets est interprété comme SocketsPerBoard plutôt que comme le nombre total de sockets. La valeur par défaut est 1.
SocketsPerBoard
Nombre de sockets/puces de processeur physiques sur une carte mère. Sockets et SocketsPerBoard sont mutuellement exclusifs. La valeur par défaut est 1.
State
État du nœud par rapport au lancement des jobs utilisateur. Les valeurs acceptables sont CLOUD, DOWN, DRAIN, FAIL, FAILING, FUTURE et UNKNOWN. Les états de nœud BUSY et IDLE ne doivent pas être spécifiés dans la configuration du nœud, mais définissez plutôt l'état du nœud sur UNKNOWN. La définition de l'état du nœud sur UNKNOWN entraînera la définition de l'état du nœud sur BUSY, IDLE ou un autre état approprié basé sur les informations d'état du système récupérées. La valeur par défaut est UNKNOWN. Voir également le paramètre DownNodes ci-dessous.
CLOUD
Indique que le nœud existe dans le cloud. Son état initial sera traité comme éteint. Le nœud sera disponible pour utilisation après que son état ait été récupéré du fichier de sauvegarde d'état de Slurm ou que le démon slurmd démarre sur le nœud de calcul.
DOWN
Indique que le nœud est en panne et n'est pas disponible pour l'allocation de travail.
DRAIN
Indique que le nœud n'est pas disponible pour l'allocation de travail.
FAIL
Indique que le nœud est censé tomber en panne prochainement, qu'il n'a aucun job lui étant alloué et qu'aucun nouveau job ne lui sera alloué.
FAILING
Indique que le nœud est censé tomber en panne prochainement, qu'il a un ou plusieurs jobs lui étant alloués, mais qu'aucun nouveau job ne lui sera alloué.
FUTURE
Indique que le nœud est défini pour une utilisation future et qu'il n'est pas nécessaire qu'il existe lorsque les démons Slurm sont démarrés. Ces nœuds peuvent être mis à disposition simplement en mettant à jour l'état du nœud à l'aide de la commande scontrol plutôt qu'en redémarrant le démon slurmctld. Une fois ces nœuds mis à disposition, modifiez leur état dans le fichier slurm.conf. Jusqu'à ce que ces nœuds soient mis à disposition, ils ne seront visibles par aucune commande Slurm et aucune tentative ne sera faite pour les contacter. Les nœuds FUTURE conservent leur état non-FUTURE lors du redémarrage. Utilisez scontrol pour remettre un nœud à l'état FUTURE.
FUTURE Nœuds Dynamiques
Un slurmd démarré avec -F[<feature>] sera associé à un nœud FUTURE qui correspond à la même configuration (sockets, cœurs, threads) que celle rapportée par slurmd -C. L'adresse réseau et le nom d'hôte du nœud (NodeAddr et NodeHostname) seront automatiquement récupérés du slurmd et seront effacés lorsqu'ils seront remis à l'état FUTURE.
UNKNOWN
Indique que l'état du nœud n'est pas défini mais sera établi (défini sur BUSY ou IDLE) lorsque le démon slurmd sur ce nœud s'enregistrera. UNKNOWN est l'état par défaut.
ThreadsPerCore
Nombre de threads logiques dans un seul cœur physique (par exemple, "2"). Notez que Slurm peut allouer des ressources aux jobs jusqu'à la résolution d'un cœur. Si votre système est configuré avec plus d'un thread par cœur, l'exécution d'un job différent sur chaque thread n'est pas prise en charge, sauf si vous configurez SelectTypeParameters=CR_CPU plus CPUs ; ne configurez pas Sockets, CoresPerSocket ou ThreadsPerCore. Un job peut exécuter une tâche par thread à partir d'une étape de job ou exécuter une étape de job distincte sur chacun des threads. Notez également que si vous utilisez plus d'un thread par cœur et que vous exécutez le plugin select/cons_tres, vous voudrez définir la variable SelectTypeParameters sur autre chose que CR_CPU pour éviter des résultats inattendus. La valeur par défaut est 1.
TmpDisk
Taille totale du stockage disque temporaire dans TmpFS en mégaoctets (par exemple, "16384"). TmpFS (pour "Temporary File System") identifie l'emplacement que les jobs doivent utiliser pour le stockage temporaire. Notez que cela n'indique pas la quantité d'espace libre disponible pour l'utilisateur sur le nœud, seulement la taille totale du système de fichiers. L'administrateur système doit s'assurer que ce système de fichiers est purgé si nécessaire afin que les jobs utilisateur aient accès à la majeure partie de cet espace. Les programmes Prolog et/ou Epilog (spécifiés dans le fichier de configuration) pourraient être utilisés pour s'assurer que le système de fichiers reste propre. La valeur par défaut est 0.
Topology
Liste séparée par des virgules de paires au format <nom_topologie>:<unité_topologie>. Où <unité_topologie> est le nom du bloc ou le nom d'un commutateur feuille. Les noms de commutateurs intermédiaires -- séparés par ':' -- peuvent être fournis et seront créés si nécessaire (par exemple, Topology=topo-tree:sw_root:s1:s2). Ce réglage
surécrit la configuration d'affiliation de topologie de nœud spécifiée dans topology.conf(5) et topology.yaml(5).
Poids
La priorité du nœud à des fins de planification. Toutes choses égales par ailleurs, les travaux seront alloués aux nœuds ayant le poids le plus bas qui satisfont leurs exigences. Par exemple, une collection hétérogène de nœuds pourrait être placée dans une seule partition pour une plus grande utilisation du système, réactivité et capacité. Il serait préférable d'allouer des nœuds à mémoire plus petite plutôt que des nœuds à mémoire plus grande si l'un ou l'autre satisfera les exigences d'un travail. Les unités de poids sont arbitraires, mais des poids plus importants doivent être attribués aux nœuds ayant plus de processeurs, de mémoire, d'espace disque, une vitesse de processeur plus élevée, etc. Notez que si une demande d'allocation de travail ne peut pas être satisfaite en utilisant les nœuds avec le poids le plus bas, l'ensemble des nœuds avec le poids le plus bas suivant est ajouté à l'ensemble des nœuds en cours de considération pour l'utilisation (répéter au besoin pour des valeurs de poids plus élevées). Si vous voulez absolument minimiser le nombre de nœuds à poids plus élevé alloués à un travail (au détriment d'une surcharge de planification plus élevée), donnez à chaque nœud une valeur de Poids distincte et ils seront ajoutés au pool de nœuds en cours de considération pour la planification individuellement.

La valeur par défaut est 1.

NOTE : Les poids des nœuds sont d'abord considérés parmi les nœuds actuellement disponibles. Par exemple, les nœuds POWERED_DOWN et POWERING_UP avec des poids plus faibles ne seront pas évalués avant un nœud IDLE sous tension.

Nom unique pour un ensemble de nœuds. Ne doit pas chevaucher les définitions de NodeName.

CONFIGURATION DES PARTITIONS

La configuration des partitions vous permet d'établir différentes limites de travaux ou contrôles d'accès pour divers groupes (ou partitions) de nœuds. Les nœuds peuvent appartenir à plus d'une partition, permettant aux partitions de servir de files d'attente polyvalentes. Par exemple, on peut mettre le même ensemble de nœuds dans deux partitions différentes, chacune avec des contraintes différentes (limite de temps, tailles de travaux, groupes autorisés à utiliser la partition, etc.). Les travaux se voient allouer des ressources au sein d'une seule partition. Des valeurs par défaut peuvent être spécifiées avec un enregistrement dans lequel PartitionName est "DEFAULT". Les valeurs d'entrée par défaut ne s'appliqueront qu'aux lignes qui les suivent dans le fichier de configuration et les valeurs par défaut peuvent être réinitialisées plusieurs fois dans le fichier de configuration avec plusieurs entrées où "PartitionName=DEFAULT". La spécification "PartitionName=" doit être placée sur chaque ligne décrivant la configuration des partitions. Chaque ligne où PartitionName est "DEFAULT" remplacera ou ajoutera aux valeurs par défaut précédentes et ne réinitialisera pas les valeurs par défaut. Un seul nom de partition ne peut pas apparaître en tant que valeur de PartitionName sur plus d'une ligne (les enregistrements de noms de partitions dupliqués seront ignorés). Si une partition qui est en cours d'utilisation est supprimée de la configuration et que slurm est redémarré ou reconfiguré (scontrol reconfigure), les travaux utilisant la partition sont annulés. NOTE : Placez tous les paramètres de chaque partition sur une seule ligne. Chaque ligne de configuration de partition doit représenter une partition différente. Le fichier de configuration des partitions contient les informations suivantes :

AllocNodes
Liste séparée par des virgules des nœuds à partir desquels les utilisateurs peuvent soumettre des travaux dans la partition. Les noms de nœuds peuvent être spécifiés en utilisant la syntaxe d'expression de plage de nœuds décrite ci-dessus. La valeur par défaut est "ALL".
AllowAccounts
Liste séparée par des virgules des comptes qui peuvent exécuter des travaux dans la partition. La valeur par défaut est "ALL". Cette liste est hiérarchique, ce qui signifie que les sous-comptes sont inclus automatiquement. NOTE : Si AllowAccounts est utilisé, DenyAccounts ne sera pas appliqué. Se référer également à DenyAccounts.
AllowGroups
Liste séparée par des virgules des noms de groupes qui peuvent exécuter des travaux dans cette partition. Un utilisateur sera autorisé à soumettre un travail à cette partition si AllowGroups a au moins un groupe associé à l'utilisateur. Les travaux exécutés en tant qu'utilisateur root ou en tant qu'utilisateur SlurmUser pourront utiliser n'importe quelle partition, indépendamment de la valeur de AllowGroups. De plus, un administrateur ou un opérateur Slurm pourra visualiser n'importe quelle partition, indépendamment de la valeur de AllowGroups. Si l'utilisateur root tente d'exécuter un travail en tant qu'autre utilisateur (par exemple, en utilisant l'option --uid de srun), le travail sera soumis à AllowGroups comme s'il avait été soumis par cet utilisateur. Par défaut, AllowGroups est non défini, ce qui signifie que tous les groupes sont autorisés à utiliser cette partition. La valeur spéciale 'ALL' est équivalente à cela. Les utilisateurs qui ne sont pas membres du groupe spécifié ne verront pas les informations sur cette partition par défaut. Cependant, cela ne doit pas être considéré comme un mécanisme de sécurité, car les informations sur les travaux seront renvoyées si un utilisateur demande des détails sur la partition ou un travail spécifique. Voir le paramètre PrivateData pour restreindre l'accès aux informations sur les travaux. NOTE : Pour des raisons de performance, Slurm maintient une liste des identifiants d'utilisateurs autorisés à utiliser chaque partition, et celle-ci est vérifiée au moment de la soumission du travail. Cette liste d'identifiants d'utilisateurs est mise à jour lorsque le démon slurmctld est redémarré, reconfiguré (par exemple, "scontrol reconfig") ou que la valeur AllowGroups de la partition est réinitialisée, même si sa valeur n'est pas modifiée (par exemple, "scontrol update PartitionName=name AllowGroups=group"). Pour que l'accès d'un utilisateur à une partition change, sa composition de groupe doit changer et la liste interne d'identifiants d'utilisateurs de Slurm doit changer en utilisant l'une des méthodes décrites ci-dessus.
AllowQos
Liste séparée par des virgules des Qos qui peuvent exécuter des travaux dans la partition. Les travaux exécutés en tant qu'utilisateur root peuvent utiliser n'importe quelle partition sans tenir compte de la valeur de AllowQos. La valeur par défaut est "ALL". NOTE : Si AllowQos est utilisé, DenyQos ne sera pas appliqué. Se référer également à DenyQos.
Alternate
Nom de partition de la partition alternative à utiliser si l'état de cette partition est "DRAIN" ou "INACTIVE."
LiaisonCPU
Si une requête de tâche ne spécifie pas d'option pour contrôler comment les tâches sont liées aux CPU alloués (en utilisant --cpu-bind) et que tous les nœuds alloués au travail n'ont pas la même option LiaisonCPU pour le nœud, alors l'option LiaisonCPU de la partition contrôlera comment les tâches sont liées aux ressources allouées. Le TaskPluginParam sera utilisé comme dernier recours, avec comme valeur par défaut aucune liaison. Les valeurs prises en charge pour LiaisonCPU sont none, socket, ldom (NUMA), core et thread.
Défaut
Si ce mot-clé est défini, les travaux soumis sans spécification de partition utiliseront cette partition. Les valeurs possibles sont "YES" et "NO". La valeur par défaut est "NO".
TempsDéfaut
Limite de temps d'exécution utilisée pour les travaux qui ne spécifient pas de valeur. Si elle n'est pas définie, MaxTime sera utilisée. Le format est le même que pour MaxTime.
DefCpuPerGPU
Nombre par défaut de CPUs alloués par GPU alloué. Cette valeur est utilisée uniquement si la tâche n'a pas spécifié --cpus-per-task et --cpus-per-gpu.
DefMemPerCPU
Taille par défaut de la mémoire vive disponible par CPU alloué en mégaoctets. Utilisé pour éviter la surengagement de la mémoire et la pagination. DefMemPerCPU serait généralement utilisé si des processeurs individuels sont alloués aux tâches (SelectType=select/cons_tres). Si non défini, la valeur DefMemPerCPU pour l'ensemble du cluster sera utilisée. Voir également DefMemPerGPU, DefMemPerNode et MaxMemPerCPU. DefMemPerCPU, DefMemPerGPU et DefMemPerNode sont mutuellement exclusifs.
DefMemPerGPU
Taille par défaut de la mémoire vive disponible par GPU alloué en mégaoctets. Veuillez noter qu'un effort est fait pour prédire quels GPU du système seront utilisés, mais cela pourrait changer entre la soumission et le démarrage de la tâche, ce qui pourrait entraîner un fonctionnement inattendu de MaxMemPerNode pour les tâches hétérogènes. Voir également DefMemPerCPU, DefMemPerNode et MaxMemPerCPU. DefMemPerCPU, DefMemPerGPU et DefMemPerNode sont mutuellement exclusifs.
DefMemPerNode
Taille par défaut de la mémoire vive disponible par nœud alloué en mégaoctets. Utilisé pour éviter la surengagement de la mémoire et la pagination. DefMemPerNode serait généralement utilisé si des nœuds entiers sont alloués aux tâches (SelectType=select/linear) et que les ressources sont surengagées (OverSubscribe=yes ou OverSubscribe=force). Si non défini, la valeur DefMemPerNode pour l'ensemble du cluster sera utilisée. Voir également DefMemPerCPU, DefMemPerGPU et MaxMemPerCPU. DefMemPerCPU, DefMemPerGPU et DefMemPerNode sont mutuellement exclusifs.
DenyAccounts
Liste des comptes séparés par des virgules qui ne peuvent pas exécuter de tâches dans la partition. Par défaut, aucun compte n'est interdit d'accès. Cette liste est hiérarchique, ce qui signifie que les sous-comptes sont inclus automatiquement. NOTE : Si AllowAccounts est utilisé, DenyAccounts ne sera pas appliqué. Voir également AllowAccounts.
DenyQos
Liste des Qos séparés par des virgules qui ne peuvent pas exécuter de tâches dans la partition. Par défaut, aucun QOS n'est interdit d'accès. NOTE : Si AllowQos est utilisé, DenyQos ne sera pas appliqué. Voir également AllowQos.
DisableRootJobs
Si défini sur "YES", l'utilisateur root sera empêché d'exécuter toute tâche sur cette partition. La valeur par défaut sera la valeur de DisableRootJobs définie en dehors d'une spécification de partition (qui est "NO", permettant à l'utilisateur root d'exécuter des tâches).
ExclusiveTopo
Si défini sur "YES,", une seule tâche pourra être exécutée sur un segment de topologie unique. Cette capacité est également disponible sur une base par tâche en utilisant l'option --exclusive=topo.
ExclusiveUser
Si défini sur "YES", les nœuds seront alloués exclusivement aux utilisateurs. Plusieurs tâches peuvent être exécutées pour le même utilisateur, mais un seul utilisateur peut être actif à la fois. Cette capacité est également disponible sur une base par tâche en utilisant l'option --exclusive=user.
GraceTime
Spécifie, en secondes, le délai de grâce de préemption qui sera accordé à une tâche qui a été sélectionnée pour préemption. Ce paramètre ne prend effet que lorsque PreemptType=partition_prio. La valeur par défaut est zéro, aucun délai de grâce de préemption n'est autorisé sur cette partition. Une fois qu'une tâche a été sélectionnée pour préemption, son heure de fin est définie sur l'heure actuelle plus GraceTime. Les tâches de la tâche reçoivent immédiatement les signaux SIGCONT et SIGTERM afin de les informer de leur terminaison imminente. Ceci est suivi par la séquence de signaux SIGCONT, SIGTERM et SIGKILL à l'expiration de sa nouvelle heure de fin. Cette seconde série de signaux est envoyée aux tâches et au script de batch contenant, le cas échéant. Voir également le paramètre de configuration global KillWait.
NOTE : Ce paramètre ne s'applique pas à PreemptMode=SUSPEND. Pour définir le délai de grâce de préemption lors de l'utilisation de PreemptMode=SUSPEND, voir PreemptParameters=suspend_grace_time.
Hidden
Spécifie si la partition et ses tâches doivent être masquées par défaut. Les partitions masquées ne seront pas signalées par défaut par les API ou commandes Slurm. Les valeurs possibles sont "YES" et "NO". La valeur par défaut est "NO". Notez que les partitions auxquelles un utilisateur n'a pas accès en vertu du paramètre AllowGroups seront également masquées par défaut.
LLN
Planifie les ressources pour les tâches sur les nœuds les moins chargés (basé sur le nombre de CPUs inactifs). Ceci n'est généralement recommandé que pour un environnement avec des tâches série car les ressources inactives auront tendance à être fortement fragmentées, ce qui entraînera la distribution des tâches parallèles sur de nombreux nœuds. Notez que le Weight du nœud a la priorité sur le nombre de ressources inactives sur chaque nœud. Voir également le paramètre de configuration SelectTypeParameters CR_LLN pour utiliser les nœuds les moins chargés dans chaque partition.
MaxCPUsPerNode
Nombre maximum de CPUs sur un nœud disponible pour toutes les tâches de cette partition. Ceci peut être particulièrement utile pour planifier des GPU. Par exemple, un nœud peut être associé à deux partitions Slurm (par exemple, "cpu" et "gpu") et la partition/file d'attente "cpu" pourrait être limitée à seulement un sous-ensemble des CPUs du nœud, garantissant qu'un ou plusieurs CPUs seraient disponibles pour les tâches dans la partition/file d'attente "gpu". Voir également MaxCPUsPerSocket.
MaxCPUsPerSocket
Nombre maximum de CPUs sur un nœud disponible pour toutes les tâches de cette partition. Ceci peut être particulièrement utile pour planifier des GPU. Voir également MaxCPUsPerNode.
MaxMemPerCPU
Taille maximale de la mémoire vive disponible par CPU alloué en mégaoctets. Utilisé pour éviter la surengagement de la mémoire et la pagination. MaxMemPerCPU serait généralement utilisé si des processeurs individuels sont alloués aux tâches (SelectType=select/cons_tres). Si non défini, la valeur MaxMemPerCPU pour l'ensemble du cluster sera utilisée. Voir également DefMemPerCPU et MaxMemPerNode. MaxMemPerCPU et MaxMemPerNode sont mutuellement exclusifs.
MaxMemPerNode
Taille maximale de la mémoire vive disponible par nœud alloué dans une allocation de tâche en mégaoctets. Utilisé pour éviter la surengagement de la mémoire et la pagination. MaxMemPerNode serait généralement utilisé si des nœuds entiers sont alloués aux tâches (SelectType=select/linear) et que les ressources sont surengagées (OverSubscribe=yes ou OverSubscribe=force). Si non défini, la valeur MaxMemPerNode pour l'ensemble du cluster sera utilisée. Voir également DefMemPerNode et MaxMemPerCPU. MaxMemPerCPU et MaxMemPerNode sont mutuellement exclusifs.
MaxNodes
Nombre maximum de nœuds qui peuvent être alloués à une seule tâche. La valeur par défaut est "UNLIMITED", qui est représentée en interne par -1.
MaxTime
Limite de temps d'exécution maximale pour les tâches. Le format est minutes, minutes:secondes, heures:minutes:secondes, jours-heures, jours-heures:minutes, jours-heures:minutes:secondes ou "UNLIMITED". La résolution temporelle est d'une minute et les valeurs de seconde sont arrondies à la minute suivante. Le TimeLimit de la tâche peut être mis à jour par root, SlurmUser ou un opérateur pour une valeur supérieure à MaxTime configuré après la soumission de la tâche.
MinNodes
Nombre minimum de nœuds qui peuvent être alloués à une seule tâche. La valeur par défaut est 0.
Nodes
Liste des nœuds ou des ensembles de nœuds associés à cette partition, séparés par des virgules. Les noms de nœuds peuvent être spécifiés en utilisant la syntaxe d'expression de plage de nœuds décrite ci-dessus. Une liste vide de nœuds (c'est-à-dire Nodes="") peut être utilisée si l'on souhaite qu'une partition existe, mais sans ressources (éventuellement temporairement). Une valeur de "ALL" est mappée à tous les nœuds configurés dans le cluster.
OverSubscribe
Contrôle la capacité de la partition à exécuter plus d'une tâche à la fois sur chaque ressource (nœud, socket ou cor
e selon la valeur de SelectTypeParameters). Si des ressources doivent être sur-attribuées, il est très important d'éviter la sur-attriibution de mémoire. SelectTypeParameters doit être configuré pour traiter la mémoire comme une ressource consommable et l'option --mem doit être utilisée pour les allocations de travaux. Le partage de ressources est généralement utile uniquement lors de l'utilisation de la planification de groupe (PreemptMode=suspend,gang). Les valeurs possibles pour OverSubscribe sont "EXCLUSIVE", "FORCE", "YES", et "NO". Notez qu'une valeur de "YES" ou "FORCE" peut avoir un impact négatif sur les performances des systèmes comportant des milliers de travaux en cours d'exécution. La valeur par défaut est "NO". Pour plus d'informations, voir les pages Web suivantes :
https://slurm.schedmd.com/cons_tres.html
https://slurm.schedmd.com/cons_tres_share.html
https://slurm.schedmd.com/gang_scheduling.html
https://slurm.schedmd.com/preempt.html
EXCLUSIVE
Alloue des nœuds entiers aux travaux même avec SelectType=select/cons_tres configuré. Les travaux exécutés dans des partitions avec OverSubscribe=EXCLUSIVE auront un accès exclusif à tous les nœuds alloués. Ces travaux se voient allouer tous les CPU et GRES des nœuds, mais ils ne se voient allouer que la quantité de mémoire qu'ils demandent. Ceci est conçu pour prendre en charge la planification de groupe, car les travaux suspendus résident toujours en mémoire. Pour demander toute la mémoire d'un nœud, utilisez --mem=0 au moment de la soumission.
FORCE
Rend toutes les ressources (sauf les GRES) de la partition disponibles pour la sur-attriibution sans aucun moyen pour les utilisateurs de la désactiver. Peut être suivi d'un deux-points et du nombre maximal de travaux en cours d'exécution ou suspendus. Par exemple, OverSubscribe=FORCE:4 permet à chaque nœud, socket ou cœur de sur-attribuer chaque ressource quatre fois. Recommandé uniquement pour les systèmes utilisant PreemptMode=suspend,gang.

NOTE : OverSubscribe=FORCE:1 est un cas spécial qui n'est pas exactement équivalent à OverSubscribe=NO. OverSubscribe=FORCE:1 désactive la sur-attriibution normale des ressources dans la même partition, mais permettra toujours la sur-attriibution due à la préemption ou sur des partitions qui se chevauchent avec le même PriorityTier. La configuration de OverSubscribe=NO empêchera la sur-attriibution dans tous les cas.

NOTE : Si vous utilisez PreemptType=preempt/qos, vous pouvez spécifier une valeur pour FORCE supérieure à 1. Par exemple, OverSubscribe=FORCE:2 permettra normalement deux travaux par ressource, mais un troisième travail ne pourra être démarré que s'il l'est par préemption basée sur QOS.

NOTE : Si OverSubscribe est configuré sur FORCE ou YES dans votre slurm.conf et que le système n'est pas configuré pour utiliser la préemption (PreemptMode=OFF), la comptabilité peut facilement dépasser l'utilisation réelle. Il est courant sur de tels systèmes de recevoir des messages d'erreur dans le journal slurmdbd indiquant : "Nous avons plus de temps alloué que ce qui est possible."

YES
Rend toutes les ressources (sauf les GRES) de la partition disponibles pour le partage sur demande du travail. Les ressources ne seront sur-attribuées que lorsqu'elles seront explicitement demandées par l'utilisateur en utilisant l'option "--oversubscribe" lors de la soumission du travail. Peut être suivi d'un deux-points et du nombre maximal de travaux en cours d'exécution ou suspendus. Par exemple, "OverSubscribe=YES:4" permet à chaque nœud, socket ou cœur d'exécuter jusqu'à quatre travaux à la fois. Recommandé uniquement pour les systèmes fonctionnant avec la planification de groupe (PreemptMode=suspend,gang).
NO
Les ressources sélectionnées sont allouées à un seul travail. Aucune ressource ne sera allouée à plus d'un travail.

NOTE : Même si vous utilisez PreemptMode=suspend,gang, la configuration de OverSubscribe=NO désactivera la préemption sur cette partition. Utilisez OverSubscribe=FORCE:1 si vous souhaitez désactiver la sur-attriibution normale tout en autorisant la suspension due à la préemption.

OverTimeLimit
Nombre de minutes pendant lesquelles un travail peut dépasser sa limite de temps avant d'être annulé. Normalement, la limite de temps d'un travail est traitée comme une limite *stricte* et le travail sera arrêté lorsqu'il atteindra cette limite. La configuration de OverTimeLimit entraînera le traitement de la limite de temps du travail comme une limite *douce*. L'ajout de la valeur OverTimeLimit à la limite de temps *douce* fournit une limite de temps *stricte*, à laquelle le travail est annulé. Ceci est particulièrement utile pour la planification de remplissage (backfill scheduling), qui se base sur la limite de temps douce de chaque travail. Si non défini, la valeur OverTimeLimit pour l'ensemble du cluster sera utilisée. Ne peut pas dépasser 65533 minutes. Une valeur de "UNLIMITED" est également prise en charge.
PartitionName
Nom par lequel la partition peut être référencée (par exemple, "Interactive"). Ce nom peut être spécifié par les utilisateurs lors de la soumission des travaux. Si PartitionName est "DEFAULT", les valeurs spécifiées avec cet enregistrement s'appliqueront aux spécifications de partitions ultérieures, sauf si elles sont explicitement définies sur d'autres valeurs dans cet enregistrement de partition ou remplacées par un ensemble différent de valeurs par défaut. Chaque ligne où PartitionName est "DEFAULT" remplacera ou ajoutera aux valeurs par défaut précédentes et ne réinitialisera pas les valeurs par défaut.
PowerDownOnIdle
Si défini sur "YES" et que l'économie d'énergie est activée pour la partition, les nœuds alloués à partir de cette partition seront invités à s'éteindre après s'être vu attribuer au moins un travail. Ces nœuds ne s'éteindront pas tant qu'ils ne seront pas passés de COMPLETING à IDLE. S'il est défini sur "NO", l'économie d'énergie fonctionnera comme configuré pour la partition. La valeur par défaut est "NO". Voir https://slurm.schedmd.com/power_save.html et https://slurm.schedmd.com/elastic_computing.html pour plus de détails.

NOTE : Les actions suivantes entraîneront une transition de COMPLETING à IDLE :
Achèvement de tous les travaux en cours sans allocation de travaux supplémentaires.
ExclusiveUser=YES et après l'achèvement de tous les travaux en cours mais avant l'allocation du travail d'un autre utilisateur.
OverSubscribe=EXCLUSIVE et après l'achèvement du travail en cours mais avant l'allocation d'un nouveau travail.

NOTE : Les nœuds sont toujours sujets à l'extinction s'ils sont inactifs pendant SuspendTime lorsque PowerDownOnIdle est défini sur NO.</p>

Voir également SuspendTime.

PreemptMode
Mécanisme utilisé pour préempter des travaux ou activer la planification de groupe pour cette partition lorsque PreemptType=preempt/partition_prio est configuré. Cette configuration PreemptMode spécifique à la partition remplacera le PreemptMode global du cluster pour cette partition. Il peut être défini sur OFF pour désactiver la préemption et la planification de groupe pour cette partition. Voir également PriorityTier et la description ci-dessus du paramètre PreemptMode global du cluster pour plus de détails.
L'option GANG est utilisée pour activer la planification de groupe indépendamment de l'activation de la préemption (c'est-à-dire indépendamment du paramètre PreemptType). Elle peut être spécifiée en plus d'un paramètre PreemptMode avec les deux options séparées par une virgule (par exemple, PreemptMode=SUSPEND,GANG).
Voir https://slurm.schedmd.com/preempt.html et https://slurm.schedmd.com/gang_scheduling.html pour plus de détails.

NOTE : Pour des raisons de performance, le planificateur de remplissage réserve des nœuds entiers pour les travaux, pas des nœuds partiels. Si, lors de la planification de remplissage, un travail préempte un ou plusieurs autres travaux, les nœuds entiers de ces travaux préemptés sont réservés pour le travail préempteur, même si le travail préempteur demandait moins de ressources que cela. Ces nœuds réservés ne sont pas disponibles pour d'autres travaux pendant ce cycle de remplissage, même si les autres travaux pourraient tenir sur les nœuds. Par conséquent, les travaux peuvent préempter plus de ressources pendant une seule itération de remplissage qu'ils n'en ont demandé.
NOTE : Pour que les travaux hétérogènes soient pris en compte pour la préemption, tous les composants doivent être éligibles à la préemption. Lorsqu'un travail hétérogène doit être préempté, le premier composant identifié du travail avec le PreemptMode d'ordre le plus élevé (SUSPEND (le plus élevé), REQUEUE, CANCEL (le plus bas)) sera utilisé pour définir le PreemptMode pour tous les composants. Le GraceTime et le signal d'avertissement de l'utilisateur pour chaque composant du travail hétérogène restent uniques. Les travaux hétérogènes sont exclus des opérations de planification de groupe (GANG).

OFF
Désactive la préemption de travaux et la planification de groupe.
CANCEL
Le travail préempté sera annulé.
GANG
Active la planification de groupe (time slicing) des travaux dans la même partition, et permet la reprise des travaux suspendus.

NOTE : La planification de groupe est effectuée indépendamment pour chaque partition. Ainsi, si vous souhaitez uniquement un découpage temporel par OverSubscribe, sans aucune préemption, il n'est pas recommandé de configurer des partitions avec des nœuds qui se chevauchent. D'autre part, si vous souhaitez utiliser PreemptType=preempt/partition_prio pour autoriser les travaux de haut

her PriorityTier partitions pour suspendre les tâches des partitions de PrioritéInférieure vous aurez besoin de partitions qui se chevauchent, et de PreemptMode=SUSPEND,GANG pour utiliser le planificateur Gang afin de reprendre la ou les tâches suspendues. Dans tous les cas, le partage de temps ne se produira pas entre les tâches sur des partitions différentes.
NOTE: Les tâches hétérogènes sont exclues des opérations de planification GANG.

REQUEUE
Prépense les tâches en les remettant dans la file d'attente (si possible) ou en les annulant. Pour que les tâches soient remises dans la file d'attente, elles doivent avoir l'option --requeue sbatch définie ou le paramètre JobRequeue à l'échelle du cluster dans slurm.conf doit être défini sur 1.
SUSPEND
Les tâches préemptées seront suspendues, et plus tard le planificateur Gang les reprendra. Par conséquent, le mode de préemption SUSPEND a toujours besoin de l'option GANG pour être spécifié au niveau du cluster. De plus, comme les tâches suspendues utiliseront toujours de la mémoire sur les nœuds alloués, Slurm doit être capable de suivre les ressources mémoire pour pouvoir suspendre les tâches.

Si les tâches préemptées et le préempteur sont sur des partitions différentes, les tâches préemptées resteront suspendues jusqu'à ce que le préempteur se termine.

NOTE: Comme la planification gang est effectuée indépendamment pour chaque partition, si vous utilisez PreemptType=preempt/partition_prio, les tâches des partitions de PriorityTier plus élevées suspendront les tâches des partitions de PriorityTier plus basses pour s'exécuter sur les ressources libérées. Ce n'est qu'à la fin de la tâche préempteuse que les tâches suspendues seront reprises par le planificateur Gang.

NOTE: Les tâches suspendues ne libéreront pas les GRES. Les tâches à priorité plus élevée ne pourront pas préempter pour accéder aux GRES.

PriorityJobFactor
Facteur de partition utilisé par le plugin priority/multifactor pour calculer la priorité des tâches. Par défaut, il est de 1. Une valeur de 0 empêche cette partition d'ajouter à la priorité de la tâche. La valeur ne peut pas dépasser 65533. Voir aussi PriorityTier.
PriorityTier
Les tâches soumises à une partition avec une valeur PriorityTier plus élevée seront évaluées par le planificateur avant les tâches en attente dans une partition avec une valeur PriorityTier plus basse. Elles seront également prises en compte pour la préemption des tâches en cours d'exécution dans des partitions avec des valeurs PriorityTier plus basses si PreemptType=preempt/partition_prio. La valeur ne peut pas dépasser 65533. Voir aussi PriorityJobFactor.
QOS
Utilisé pour étendre les limites disponibles pour un QOS sur une partition. Les tâches ne seront pas associées à ce QOS en dehors de leur association à la partition. Elles seront toujours associées à leur QOS demandé. Par défaut, aucun QOS n'est utilisé. Des détails supplémentaires se trouvent dans la documentation QOS à l'adresse https://slurm.schedmd.com/qos.html, y compris des conditions spéciales lorsqu'un QOS relatif est utilisé pour ce paramètre. NOTE: Si une limite est définie à la fois dans le QOS de la partition et dans le QOS de la tâche, la limite du QOS de la partition sera respectée, sauf si le QOS de la tâche a le drapeau OverPartQOS défini, auquel cas la limite du QOS de la tâche aura la priorité.
ReqResv
Spécifie que les utilisateurs de cette partition doivent désigner une réservation lors de la soumission d'une tâche. Cette option peut être utile pour restreindre l'utilisation d'une partition qui pourrait avoir une priorité plus élevée ou des ressources supplémentaires à n'autoriser qu'à l'intérieur d'une réservation. Les valeurs possibles sont "YES" et "NO". La valeur par défaut est "NO".
ResumeTimeout
Temps maximum autorisé (en secondes) entre l'émission d'une demande de reprise de nœud et la disponibilité réelle du nœud pour utilisation. Les nœuds qui ne répondent pas dans ce délai seront marqués comme DOWN et les tâches planifiées sur le nœud seront remises dans la file d'attente si possible. Les nœuds qui redémarrent après ce délai seront marqués comme DOWN avec la raison "Node unexpectedly rebooted.". Pour les nœuds qui se trouvent dans plusieurs partitions avec cette option définie, la durée la plus longue s'appliquera. Si elle n'est pas définie sur une partition, le nœud utilisera la valeur ResumeTimeout définie pour l'ensemble du cluster. La valeur maximale est soit 65533, soit INFINITE.
RootOnly
Spécifie si seul l'identifiant utilisateur zéro (c'est-à-dire l'utilisateur root) peut allouer des ressources dans cette partition. L'utilisateur root peut allouer des ressources pour tout autre utilisateur, mais la demande doit être initiée par l'utilisateur root. Cette option peut être utile pour une partition gérée par une entité externe (par exemple, un gestionnaire de tâches de niveau supérieur) et empêche les utilisateurs d'utiliser directement ces ressources. Les valeurs possibles sont "YES" et "NO". La valeur par défaut est "NO".
SelectTypeParameters
Type d'allocation de ressources spécifique à la partition. Cette option remplace la valeur globale SelectTypeParameters. Les valeurs prises en charge sont CR_Core, CR_Core_Memory, CR_Socket et CR_Socket_Memory. L'utilisation nécessite que la valeur SelectTypeParameters à l'échelle du système soit définie sur l'une des quatre valeurs prises en charge listées précédemment ; sinon, la valeur spécifique à la partition sera ignorée.

Le paramètre de configuration Shared a été remplacé par le paramètre OverSubscribe décrit ci-dessus.
State
État de la partition ou disponibilité pour utilisation. Les valeurs possibles sont "UP", "DOWN", "DRAIN" et "INACTIVE". La valeur par défaut est "UP". Voir aussi le mot-clé associé "Alternate".
UP
Indique que de nouvelles tâches peuvent être mises en file d'attente sur la partition, et que les tâches peuvent allouer des nœuds et s'exécuter à partir de la partition.
DOWN
Indique que de nouvelles tâches peuvent être mises en file d'attente sur la partition, mais que les tâches mises en file d'attente ne peuvent pas allouer de nœuds et s'exécuter à partir de la partition. Les tâches déjà en cours d'exécution sur la partition continuent de s'exécuter. Les tâches doivent être explicitement annulées pour forcer leur terminaison.
DRAIN
Indique qu'aucune nouvelle tâche ne peut être mise en file d'attente sur la partition (les demandes de soumission de tâches seront refusées avec un message d'erreur), mais que les tâches déjà mises en file d'attente sur la partition peuvent allouer des nœuds et s'exécuter. Voir aussi la spécification de partition "Alternate".
INACTIVE
Indique qu'aucune nouvelle tâche ne peut être mise en file d'attente sur la partition, et que les tâches déjà mises en file d'attente ne peuvent pas allouer de nœuds et s'exécuter. Voir aussi la spécification de partition "Alternate".
SuspendTime
Les nœuds qui restent inactifs ou hors service pendant ce nombre de secondes seront mis en mode d'économie d'énergie par SuspendProgram. Pour les nœuds qui se trouvent dans plusieurs partitions avec cette option définie, la durée la plus longue s'appliquera. Si elle n'est pas définie sur une partition, le nœud utilisera la valeur SuspendTime définie pour l'ensemble du cluster. Définir SuspendTime sur INFINITE désactivera la suspension des nœuds dans cette partition. Définir SuspendTime sur autre chose qu'INFINITE (ou -1) activera le mode d'économie d'énergie.
SuspendTimeout
Temps maximum autorisé (en secondes) entre l'émission d'une demande de suspension de nœud et l'arrêt du nœud. À ce moment-là, le nœud doit être prêt pour qu'une demande de reprise soit émise si nécessaire pour un nouveau travail. Pour les nœuds qui se trouvent dans plusieurs partitions avec cette option définie, la durée la plus longue s'appliquera. Si elle n'est pas définie sur une partition, le nœud utilisera la valeur SuspendTimeout définie pour l'ensemble du cluster.
Topology
Nom de la topologie, définie dans topology.yaml, utilisée par les tâches de cette partition.
TRESBillingWeights
TRESBillingWeights est utilisé pour définir les poids de facturation de chaque type TRES suivi (voir AccountingStorageTRES) qui sera utilisé pour calculer l'utilisation d'une tâche. L'utilisation calculée est utilisée lors du calcul du partage équitable et lors de l'application de la limite de facturation TRES sur les tâches.

Les poids de facturation sont spécifiés sous forme de liste séparée par des virgules de paires <Type TRES>=<Poids de facturation TRES>.

Tout type TRES est disponible pour la facturation. Notez que l'unité de base pour la mémoire et les buffers d'éclatement est en mégaoctets.

Par défaut, la facturation des TRES est calculée comme la somme de tous les types TRES multipliée par leur poids de facturation correspondant.

Le montant pondéré d'une ressource peut être ajusté en ajoutant un suffixe K, M, G, T ou P après le poids de facturation. Par exemple, un poids de mémoire de "mem=.25" sur une tâche allouée de 8 Go sera facturé 2048 (8192 Mo * 0,25) unités. Un poids de mémoire de "mem=.25G" sur la même tâche sera facturé 2 (8

{ "192MB * (.25/1024)) units.

\n

Negative values are allowed.

\n

When a job is allocated 1 CPU and 8 GB of memory on a\n partition configured with\n TRESBillingWeights="CPU=1.0,Mem=0.25G,GRES/gpu=2.0,license/licA=1.5",\n the billable TRES will be: (1*1.0) + (8*0.25) + (0*2.0) + (0*1.5) =\n 3.0.

\n

If PriorityFlags=MAX_TRES is configured, the billable TRES is\n calculated as the MAX of individual TRESs on a node (e.g. cpus, mem,\n gres) plus the sum of all global TRESs (e.g. licenses). Using the same\n example above the billable TRES will be MAX(1*1.0, 8*0.25, 0*2.0) +\n (0*1.5) = 2.0.

\n

If TRESBillingWeights is not defined then the job is billed\n against the total number of allocated CPUs.

\n

NOTE: TRESBillingWeights doesn't affect job priority\n directly as it is currently not used for the size of the job. If you\n want TRESs to play a role in the job's priority then refer to the\n PriorityWeightTRES option.

PROLOG AND EPILOG SCRIPTS

\n

There are a variety of prolog and epilog program options that\n execute with various permissions and at various times. The four options most\n likely to be used are: Prolog and Epilog (executed once on\n each compute node for each job) plus PrologSlurmctld and\n EpilogSlurmctld (executed once on the SlurmctldHost for each\n job).

\n

NOTE: Standard output and error messages are normally not\n preserved. Explicitly write output and error messages to an appropriate\n location if you wish to preserve that information.

\n

NOTE: By default the Prolog script is ONLY run on any\n individual node when it first sees a job step from a new allocation. It does\n not run the Prolog immediately when an allocation is granted. If no job\n steps from an allocation are run on a node, it will never run the Prolog for\n that allocation. This Prolog behavior can be changed by the\n PrologFlags parameter. The Epilog, on the other hand, always runs on\n every node of an allocation when the allocation is released.

\n

If the Epilog fails (returns a non-zero exit code), this will\n result in the node being set to a DRAIN state. If the EpilogSlurmctld fails\n (returns a non-zero exit code), this will only be logged. If the Prolog\n fails (returns a non-zero exit code), this will result in the node being set\n to a DRAIN state and the job being requeued. The job will be placed in a\n held state unless nohold_on_prolog_fail is configured in\n SchedulerParameters. If the PrologSlurmctld fails (returns a non-zero\n exit code), this will result in the job being requeued to be executed on\n another node if possible. Only batch jobs can be requeued. Interactive jobs\n (salloc and srun) will be cancelled if the PrologSlurmctld fails. If\n slurmctld is stopped while either PrologSlurmctld or EpilogSlurmctld is\n running, the script will be killed with SIGKILL. The script will restart\n when slurmctld restarts.

\n

Information about the job is passed to the script using\n environment variables. For a full list of environment variables please see\n the Prolog and Epilog Guide\n https://slurm.schedmd.com/prolog_epilog.html.

NETWORK TOPOLOGY

\n

Slurm is able to optimize job allocations to minimize network\n contention. Special Slurm logic is used to optimize allocations on systems\n with a three-dimensional interconnect. and information about configuring\n those systems are available on web pages available here:\n https://slurm.schedmd.com/. For a hierarchical network, Slurm needs\n to have detailed information about how nodes are configured on the network\n switches.

\n

The TopologyPlugin parameter controls which plugin is used\n to collect network topology information. The only values presently supported\n are "topology/flat" (best-fit logic over one-dimensional\n topology), "topology/tree", and "topology/block" (both\n determine the network topology based upon information contained in a\n topology.conf or topology.yaml file, see "man topology.conf" and\n "man topology.yaml" for more information). Future plugins may\n gather topology information directly from the network. The topology\n information is optional. If not provided, Slurm will perform a best-fit\n algorithm assuming the nodes are in a one-dimensional array as configured\n and the communications cost is related to the node distance in this\n array.

RELOCATING CONTROLLERS

\n

If the cluster's computers used for the primary or backup\n controller will be out of service for an extended period of time, it may be\n desirable to relocate them. In order to do so, follow this procedure:

\n

1. Stop the Slurm daemons on the old controller and nodes.\n
\n 2. Modify the slurm.conf file appropriately.\n
\n 3. Copy the files from the StateSaveLocation to the new controller or ensure\n that they are accessible to the new controller via a shared drive.\n
\n 4. Distribute the updated slurm.conf file to all nodes.\n
\n 5. Restart the Slurm daemons on the new controller and nodes.

\n

There should be no loss of any pending jobs. Any running jobs will\n get the updated host info and finish normally. Ensure that any nodes added\n to the cluster have the current slurm.conf file installed.

\n

CAUTION: If two nodes are simultaneously configured as the\n primary controller (two nodes on which SlurmctldHost specify the\n local host and the slurmctld daemon is executing on each), system\n behavior will be destructive. If a compute node has an incorrect\n SlurmctldHost parameter, that node may be rendered unusable, but no\n other harm will result.

\n
\n

JOURNALISATION

Notez que bien que les démons Slurm créent des fichiers journaux et d'autres fichiers selon les besoins, ils traitent l'absence de répertoires parents comme une erreur fatale. Cela empêche les démons de s'exécuter si les systèmes de fichiers critiques ne sont pas montés et minimise le risque de démarrage à froid (démarrage sans préservation des jobs).

Les fichiers journaux et les fichiers de comptabilisation des jobs peuvent devoir être créés/détenus par l'UID "SlurmUser" pour être accessibles avec succès. Utilisez les commandes "chown" et "chmod" pour définir la propriété et les permissions de manière appropriée. Voir la section PERMISSIONS DE FICHIERS ET DE RÉPERTOIRES pour des informations sur les différents fichiers et répertoires utilisés par Slurm.

Il est recommandé d'utiliser l'utilitaire logrotate pour s'assurer que divers fichiers journaux ne deviennent pas trop volumineux. Ceci s'applique également aux fichiers texte utilisés pour la comptabilisation, le suivi des processus et le journal slurmdbd s'ils sont utilisés.

Voici un exemple de configuration logrotate. Apportez les modifications de site appropriées et enregistrez-les sous /etc/logrotate.d/slurm sur tous les nœuds. Voir la page de manuel logrotate pour plus de détails.

##
# Configuration logrotate de Slurm
##
/var/log/slurm/*.log {
	compress
	missingok
	nocopytruncate
	nodelaycompress
	nomail
	notifempty
	noolddir
	rotate 5
	sharedscripts
	size=5M
	create 640 slurm root
	postrotate
		pkill -x --signal SIGUSR2 slurmctld
		pkill -x --signal SIGUSR2 slurmd
		pkill -x --signal SIGUSR2 slurmdbd
		exit 0
	endscript
}
