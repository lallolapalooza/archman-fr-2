SLAPO-ACCESSLOG(5) Manuel des formats de fichiers SLAPO-ACCESSLOG(5)

NOM

slapo-accesslog - Superposition d'enregistrement des accès pour slapd

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

La superposition d'enregistrement des accès (Access Logging overlay) peut être utilisée pour enregistrer tous les accès à une base de données donnée dans une autre base de données. Cela permet de revoir toute l'activité sur une base de données donnée à l'aide de requêtes LDAP arbitraires, au lieu de se contenter d'enregistrer dans des fichiers texte plats locaux. Des options de configuration sont disponibles pour sélectionner un sous-ensemble de types d'opérations à enregistrer et pour purger automatiquement les anciens enregistrements de la base de données de journalisation. Les enregistrements sont stockés avec le schéma d'audit (voir ci-dessous) pour garantir leur lisibilité qu'ils soient consultés en LDIF ou sous forme brute.

CONFIGURATION

Ces options slapd.conf s'appliquent à la superposition d'enregistrement des accès. Elles doivent apparaître après la directive overlay.

logdb <suffixe>
Spécifie le suffixe d'une base de données à utiliser pour stocker les enregistrements de journalisation. La base de données spécifiée doit être définie ailleurs dans la configuration et doit supporter un retour ordonné des résultats comme slapd-mdb(5). Les contrôles d'accès sur la base de données de journalisation devraient empêcher l'accès général. L'entrée de suffixe de la base de données de journalisation sera créée automatiquement par cette superposition. Les entrées de journal seront générées comme enfants immédiats de l'entrée de suffixe.
logops <opérations>
Spécifie quels types d'opérations enregistrer. Les types d'opérations valides sont abandon, add, bind, compare, delete, extended, modify, modrdn, search, et unbind. Des alias pour des ensembles courants d'opérations sont également disponibles :
writes
add, delete, modify, modrdn
reads
compare, search
session
abandon, bind, unbind
all
toutes les opérations
logbase <opérations> <DN de base>
Spécifie un ensemble d'opérations qui ne seront enregistrées que si elles se produisent sous un sous-arbre spécifique de la base de données. Les types d'opérations sont les mêmes que ci-dessus pour le paramètre logops, et délimités par un caractère '|'.
logold <filtre>
Spécifie un filtre pour faire correspondre les entrées supprimées et modifiées. Si l'entrée correspond au filtre, le contenu ancien de l'entrée sera enregistré avec la requête actuelle.
logoldattr <attribut> ...
Spécifie une liste d'attributs dont le contenu ancien est toujours enregistré dans les requêtes Modify et ModRDN qui correspondent à l'un des filtres configurés dans logold. Habituellement, seul le contenu des attributs qui ont été effectivement modifiés sera enregistré ; par défaut, aucun attribut ancien n'est enregistré pour les requêtes ModRDN.
logpurge <âge> <intervalle>
Spécifie l'âge maximum des entrées de journal à conserver dans la base de données, et la fréquence de balayage de la base de données pour les anciennes entrées. L'âge et l'intervalle sont spécifiés comme une période de temps en jours, heures, minutes et secondes. Le format de temps est [jjj+]hh:mm[:ss], c'est-à-dire que les composantes jours et secondes sont optionnelles mais les heures et minutes sont obligatoires. Sauf pour les jours, qui peuvent aller jusqu'à 5 chiffres, chaque champ numérique doit être exactement de deux chiffres. Par exemple :
logpurge 2+00:00 1+00:00
spécifierait que la base de données de journalisation doit être balayée tous les jours pour les anciennes entrées, et que les entrées plus anciennes que deux jours doivent être supprimées. Lors de l'utilisation d'une base de données de journalisation qui prend en charge l'indexation ordonnée sur les attributs generalizedTime, la spécification d'un index eq sur l'attribut reqStart améliorera considérablement les performances de l'opération de purge.
logsuccess VRAI | FAUX
Si défini sur VRAI, seuls les enregistrements de journalisation seront générés pour les requêtes réussies, c'est-à-dire les requêtes qui produisent un code de résultat de 0 (LDAP_SUCCESS). Si FAUX, les enregistrements de journalisation sont générés pour toutes les requêtes, qu'elles réussissent ou non. La valeur par défaut est FAUX.

EXEMPLES

database mdb
suffix dc=example,dc=com
...
overlay accesslog
logdb cn=log
logops writes reads
logbase search|compare ou=testing,dc=example,dc=com
logold (objectclass=person)
database mdb
suffix cn=log
...
index reqStart eq
access to *
  by dn.base="cn=admin,dc=example,dc=com" read

SCHEMA

La superposition accesslog utilise le schéma "audit" décrit ici. Ce schéma est spécifiquement conçu pour l'audit par accesslog et n'est pas destiné à être utilisé autrement. Il est à noter également que le schéma décrit ici est en cours de développement, et par conséquent sujet à changement sans préavis. Le schéma est chargé automatiquement par la superposition.

Le schéma comprend un certain nombre de classes d'objets et de types d'attributs associés, décrits ci-dessous.

L'entrée racine de la base de données sous-jacente d'enregistrement des accès utilise la classe auditContainer qui est la suivante :

( 1.3.6.1.4.1.4203.666.11.5.2.0
NAME 'auditContainer'
DESC 'AuditLog container'
SUP top STRUCTURAL
MAY ( cn $ reqStart $ reqEnd ) )

Il existe une classe de base auditObject dont dérivent deux classes supplémentaires, auditReadObject et auditWriteObject. Les classes d'objets pour chaque type d'opération LDAP sont dérivées supplémentairement de ces classes. Cette hiérarchie de classes d'objets est conçue pour permettre des recherches flexibles mais efficaces dans le journal en fonction de la classe d'un type d'opération spécifique, ou de classifications plus générales. La définition de la classe auditObject est la suivante :

( 1.3.6.1.4.1.4203.666.11.5.2.1
NAME 'auditObject'
DESC 'OpenLDAP request auditing'
SUP top STRUCTURAL
MUST ( reqStart $ reqType $ reqSession )
MAY ( reqDN $ reqAuthzID $ reqControls $ reqRespControls $
reqEnd $ reqResult $ reqMessage $ reqReferral $ reqEntryUUID ) )

Notez que tous les OID utilisés dans le schéma de journalisation résident actuellement sous la branche expérimentale d'OpenLDAP. Il est prévu qu'ils migrent vers une branche standard à l'avenir.

Un aperçu des attributs suit : reqStart et reqEnd fournissent respectivement l'heure de début et de fin de l'opération. Ils utilisent la syntaxe generalizedTime. L'attribut reqStart est également utilisé comme RDN pour chaque entrée de journal.

L'attribut reqType est une simple chaîne contenant le type d'opération enregistrée, par exemple add, delete, search, etc. Pour les opérations étendues, le type inclut également l'OID de l'opération étendue, par exemple extended(1.1.1.1)

L'attribut reqSession est un identifiant spécifique à l'implémentation qui est commun à toutes les opérations associées à la même session LDAP. Actuellement, il s'agit de l'identifiant de connexion interne de slapd, stocké en décimal.

L'attribut reqDN est le distinguishedName de la cible de l'opération. Par exemple, pour une requête Bind, il s'agit du DN de Bind. Pour une requête Add, il s'agit du DN de l'entrée en cours d'ajout. Pour une requête Search, il s'agit du DN de base de la recherche.

L'attribut reqAuthzID est le distinguishedName de l'utilisateur qui a effectué l'opération. Il s'agira généralement du même nom que celui établi au début d'une session par une requête Bind (le cas échéant), mais il peut être modifié dans diverses circonstances.

Les attributs reqControls et reqRespControls transportent les éventuels contrôles envoyés par le client dans la requête et renvoyés par le serveur dans la réponse, respectivement. Les valeurs des attributs sont de simples chaînes d'octets non interprétées.

L'attribut reqResult est le code de résultat LDAP numérique de l'opération, indiquant soit le succès, soit un code d'erreur LDAP particulier. Un code d'erreur peut être accompagné d'un message d'erreur textuel qui sera enregistré dans l'attribut reqMessage.

L'attribut l'attribut reqReferral contient tous les renvois renvoyés avec le résultat de la requête.

L'attribut reqEntryUUID enregistre l'attribut entryUUID de l'entrée sur laquelle l'opération a été effectuée. Pour une requête d'ajout, il s'agit de l'entryUUID de la nouvelle entrée créée.

Des classes spécifiques à l'opération sont définies avec des attributs supplémentaires pour transporter tous les paramètres pertinents associés à l'opération :

( 1.3.6.1.4.1.4203.666.11.5.2.4
NAME 'auditAbandon'
DESC 'Abandon operation'
SUP auditObject STRUCTURAL
MUST reqId )

Pour l'opération Abandon, l'attribut reqId contient l'identifiant du message de la requête qui a été abandonnée.

( 1.3.6.1.4.1.4203.666.11.5.2.5
NAME 'auditAdd'
DESC 'Add operation'
SUP auditWriteObject STRUCTURAL
MUST reqMod )

La classe Add hérite de la classe auditWriteObject. Les classes Add et Modify sont très similaires. L'attribut reqMod contient tous les attributs de l'entrée originale en cours d'ajout. (Ou dans le cas d'une opération de modification, toutes les modifications effectuées.) Les valeurs sont formatées comme suit :

attribute:<+|-|=|#> [ value]
Où '+' indique un ajout de valeur, '-' une suppression, '=' un remplacement et '#' un incrément. Dans une opération d'ajout, toutes les valeurs de reqMod auront le descripteur '+'.
( 1.3.6.1.4.1.4203.666.11.5.2.6
NAME 'auditBind'
DESC 'Bind operation'
SUP auditObject STRUCTURAL
MUST ( reqVersion $ reqMethod ) )

La classe Bind inclut l'attribut reqVersion qui contient la version du protocole LDAP spécifiée dans la liaison, ainsi que l'attribut reqMethod qui contient la méthode de liaison utilisée. Il s'agira de la chaîne SIMPLE pour les liaisons LDAP simples ou SASL(<mech>) pour les liaisons SASL. Notez que, sauf si elle est configurée comme une superposition globale, seules les liaisons simples utilisant des DN résidant dans la base de données actuelle seront enregistrées.

( 1.3.6.1.4.1.4203.666.11.5.2.7
NAME 'auditCompare'
DESC 'Compare operation'
SUP auditObject STRUCTURAL
MUST reqAssertion )

Pour l'opération Compare, l'attribut reqAssertion contient l'assertion de valeur d'attribut utilisée dans la requête de comparaison.

( 1.3.6.1.4.1.4203.666.11.5.2.8
NAME 'auditDelete'
DESC 'Delete operation'
SUP auditWriteObject STRUCTURAL
MAY reqOld )

L'opération Delete ne nécessite aucun paramètre supplémentaire. Cependant, l'attribut reqOld peut être utilisé facultativement pour enregistrer le contenu de l'entrée avant sa suppression. Les valeurs sont formatées comme suit :

attribute: value
L'attribut reqOld n'est rempli que si l'entrée supprimée correspond au filtre logold configuré.
( 1.3.6.1.4.1.4203.666.11.5.2.9
NAME 'auditModify'
DESC 'Modify operation'
SUP auditWriteObject STRUCTURAL
MAY ( reqOld $ reqMod ) )

L'opération Modify contient une description des modifications dans l'attribut reqMod, qui a déjà été décrit ci-dessus dans l'opération Add. Elle peut éventuellement contenir le contenu précédent des attributs modifiés dans l'attribut reqOld, en utilisant le même format que celui décrit ci-dessus pour l'opération Delete. L'attribut reqOld n'est rempli que si l'entrée modifiée correspond au filtre logold configuré.

( 1.3.6.1.4.1.4203.666.11.5.2.10
NAME 'auditModRDN'
DESC 'ModRDN operation'
SUP auditWriteObject STRUCTURAL
MUST ( reqNewRDN $ reqDeleteOldRDN )
MAY ( reqNewSuperior $ reqMod $ reqOld ) )

La classe ModRDN utilise l'attribut reqNewRDN pour transporter le nouveau RDN de la requête. L'attribut reqDeleteOldRDN est une valeur booléenne indiquant TRUE si l'ancien RDN a été supprimé de l'entrée, ou FALSE s'il a été préservé. L'attribut reqNewSuperior transporte le DN de la nouvelle entrée parente si la requête a spécifié le nouveau parent. L'attribut reqOld n'est rempli que si l'entrée modifiée correspond au filtre logold configuré et contient des attributs dans la liste logoldattr.

( 1.3.6.1.4.1.4203.666.11.5.2.11
NAME 'auditSearch'
DESC 'Search operation'
SUP auditReadObject STRUCTURAL
MUST ( reqScope $ reqDerefAliases $ reqAttrsOnly )
MAY ( reqFilter $ reqAttr $ reqEntries $ reqSizeLimit $
reqTimeLimit ) )

Pour la classe Search, l'attribut reqScope contient la portée de la requête de recherche originale, en utilisant les valeurs spécifiées pour le format de l'URL LDAP. C'est-à-dire base, one, sub, ou subord. L'attribut reqDerefAliases est l'une des valeurs never, finding, searching, ou always, indiquant comment les alias seront traités pendant la recherche. L'attribut reqAttrsOnly est une valeur booléenne indiquant TRUE si seuls les noms d'attributs ont été demandés, ou FALSE si les attributs et leurs valeurs ont été demandés. L'attribut reqFilter contient le filtre utilisé dans la requête de recherche. L'attribut reqAttr liste les attributs demandés si des attributs spécifiques ont été demandés. L'attribut reqEntries est le nombre entier d'entrées renvoyées par cette requête de recherche. Les attributs reqSizeLimit et reqTimeLimit indiquent les limites demandées sur l'opération de recherche.

( 1.3.6.1.4.1.4203.666.11.5.2.12
NAME 'auditExtended'
DESC 'Extended operation'
SUP auditObject STRUCTURAL
MAY reqData )

La classe Extended représente une opération étendue LDAP. Comme mentionné ci-dessus, l'OID réel de l'opération est inclus dans l'attribut reqType de la classe parente. Si des données facultatives ont été fournies avec la requête, elles seront contenues dans l'attribut reqData sous forme d'une chaîne d'octets non interprétée.

NOTES

Le journal d'accès implémenté par cette superposition peut être utilisé pour diverses autres tâches, par exemple comme journal de modification pour un mécanisme de réplication, ainsi qu'à des fins de journalisation de sécurité/audit.

FICHIERS

/etc/openldap/slapd.conf
fichier de configuration par défaut de slapd
