NOM

slapd-mdb - Backend de base de données MDB pour slapd

SYNOPIS

/etc/openldap/slapd.conf

DESCRIPTION

Le backend mdb pour slapd(8) utilise la bibliothèque Lightning Memory-Mapped DB (LMDB) d'OpenLDAP pour stocker les données. Il repose entièrement sur le système d'exploitation sous-jacent pour la gestion de la mémoire et ne fait pas de mise en cache propre. C'est le backend de base de données principal recommandé.

Le backend mdb utilise une structure de base de données hiérarchique qui prend en charge les renommages de sous-arbres.

CONFIGURATION

Ces options de slapd.conf s'appliquent au backend mdb. C'est-à-dire qu'elles doivent suivre une ligne "backend mdb" et précéder toute ligne "backend" ou "database" subséquente.

idlexp <exp>
Spécifie une puissance de 2 pour la taille maximale d'une cellule d'index. La valeur par défaut est 16, ce qui donne une taille maximale de cellule de 2^16, soit 65536. Une fois définie, cette option s'applique à chaque instance de base de données mdb. La valeur spécifiée doit être comprise entre 16 et 30.

Ces options de slapd.conf s'appliquent à la base de données du backend mdb. C'est-à-dire qu'elles doivent suivre une ligne "database mdb" et précéder toute ligne "backend" ou "database" subséquente. Les autres options de base de données sont décrites dans la page de manuel slapd.conf(5).

checkpoint <kbyte> <min>
Spécifie la fréquence de vidage des tampons du disque de la base de données. Ce réglage n'est nécessaire que si l'option dbnosync est utilisée. Le checkpoint aura lieu si soit <kbyte> octets ont été écrits, soit <min> minutes se sont écoulées depuis le dernier checkpoint. Les deux arguments sont par défaut à zéro, auquel cas ils sont ignorés. Lorsque l'argument <min> n'est pas nul, une tâche interne s'exécutera toutes les <min> minutes pour effectuer le checkpoint. Remarque : le réglage <kbyte> n'est actuellement pas implémenté.
dbnosync
Spécifie que le contenu de la base de données sur disque ne doit pas être immédiatement synchronisé avec les modifications en mémoire. L'activation de cette option peut améliorer les performances au détriment de la sécurité des données. En particulier, si le système d'exploitation plante avant que les modifications ne soient vidées, un certain nombre de transactions peuvent être perdues. Par défaut, un vidage/une synchronisation complète des données est effectuée lors de la validation de chaque transaction.
directory <répertoire>
Spécifie le répertoire où se trouvent les fichiers LMDB contenant cette base de données et les index associés. Un répertoire séparé doit être spécifié pour chaque base de données. La valeur par défaut est /var/lib/openldap/openldap-data.
envflags {nosync,nometasync,writemap,mapasync,nordahead}
Spécifie des drapeaux pour un contrôle plus granulaire du fonctionnement de la bibliothèque LMDB.
nosync
Ceci est exactement le même que la directive dbnosync.
nometasync
Vide les données lors d'une validation, mais saute la synchronisation de la page de métadonnées. Ce mode est légèrement plus rapide qu'une synchronisation complète, mais peut potentiellement faire perdre la dernière transaction validée en cas de crash du système d'exploitation. Si nometasync et nosync sont tous deux définis, le drapeau nosync a la priorité.
writemap
Utilise une mémoire mappée inscriptible au lieu d'une mémoire en lecture seule. Cela accélère les opérations d'écriture mais rend la base de données vulnérable à la corruption si des bugs dans slapd provoquent des écritures errantes dans la région mmap.
mapasync
Lors de l'utilisation d'une mémoire mappée inscriptible et lors des vidages à chaque validation, utilise un vidage asynchrone au lieu d'un vidage synchrone (par défaut). Cette option n'a aucun effet si writemap n'a pas été défini. Elle n'a pas non plus d'effet si nosync est défini.
nordahead
Désactive la pré-lecture de fichier. Habituellement, le système d'exploitation effectue une pré-lecture sur chaque demande de lecture. Cela améliore généralement les performances de lecture, mais peut nuire aux performances de lecture aléatoire si la mémoire du système est pleine et que la base de données est plus grande que la RAM. Cette option n'est pas implémentée sous Windows.
index {<liste_attributs>|default} [pres,eq,approx,sub,<spécial>]
Spécifie les index à maintenir pour l'attribut donné (ou la liste d'attributs). Certains attributs ne supportent qu'un sous-ensemble d'index. Si seul un <attribut> est donné, les index spécifiés pour default sont maintenus. Notez que la définition d'une valeur par défaut n'implique pas que tous les attributs seront indexés. De plus, pour des performances optimales, un index eq devrait toujours être configuré pour l'attribut objectClass.

Un certain nombre de paramètres d'index spéciaux peuvent être spécifiés. Le type d'index sub peut être décomposé en index subinitial, subany et subfinal. Le type spécial nolang peut être spécifié pour interdire l'utilisation de cet index par les sous-types linguistiques. Le type spécial nosubtypes peut être spécifié pour interdire l'utilisation de cet index par les sous-types nommés. Remarque : la modification des paramètres index dans slapd.conf(5) nécessite de reconstruire les index, voir slapindex(8) ; la modification dynamique des paramètres index en modifiant cn=config par LDAP entraîne automatiquement la reconstruction des index en ligne dans une tâche d'arrière-plan.

maxentrysize <octets>
Spécifie la taille maximale d'une entrée en octets. Les tentatives de stockage d'une entrée dont la taille dépasse cette limite seront rejetées avec l'erreur LDAP_ADMINLIMIT_EXCEEDED. La valeur par défaut est 0, ce qui signifie illimité.
maxreaders <entier>
Spécifie le nombre maximum de threads pouvant avoir un accès concurrent en lecture à la base de données. Les outils tels que slapcat comptent comme un seul thread, en plus des threads des processus slapd actifs. La valeur par défaut est 126.
maxsize <octets>
Spécifie la taille maximale de la base de données en octets. Une mémoire mappée de cette taille est allouée au démarrage et la base de données ne sera pas autorisée à dépasser cette taille. La valeur par défaut est 10485760 octets. Ce réglage peut être augmenté si la limite configurée doit être augmentée.

Remarque : Il est important de définir une valeur aussi grande que possible (par rapport à la croissance anticipée des données réelles au fil du temps), car l'augmentation de la taille ultérieurement peut ne pas être réalisable lorsque le système est fortement sollicité.

mode <entier>
Spécifie le mode de protection de fichier que les fichiers de base de données nouvellement créés devraient avoir. La valeur par défaut est 0600.
multival {<liste_attributs>|default} <entier hi>,<entier lo>
Spécifie le nombre de valeurs pour lesquelles un attribut multi-valeur est stocké dans une table séparée. Normalement, les entrées sont stockées sous forme d'un seul bloc dans la base de données. Lorsque une entrée devient très volumineuse ou contient des attributs avec un très grand nombre de valeurs, les modifications sur cette entrée peuvent devenir très lentes. La séparation des attributs volumineux dans une table distincte peut améliorer les performances des opérations de modification. Le seuil est spécifié comme une paire d'entiers. Si le nombre de valeurs dépasse le seuil hi, les valeurs seront séparées. Si une modification supprime suffisamment de valeurs pour ramener un attribut en dessous du seuil lo, les valeurs seront retirées de la table séparée et fusionnées dans le bloc d'entrée principal. rtxnsize <entrées>
Spécifie le nombre maximum d'entrées à traiter dans une seule transaction de lecture lors de l'exécution d'une recherche volumineuse. Les transactions de lecture de longue durée empêchent la réutilisation des anciennes pages de base de données dans les transactions d'écriture, et donc peuvent provoquer une croissance significative du fichier de base de données en cas de trafic d'écriture intense. Ce réglage provoque la libération et la réacquisition de la transaction de lecture dans les recherches volumineuses après que le nombre d'entrées donné a été lu, afin de donner aux écrivains l'opportunité de récupérer les anciennes pages de base de données. La valeur par défaut est 10000.
searchstack <profondeur>
Spécifie la profondeur de la pile utilisée pour l'évaluation des filtres de recherche. Les filtres de recherche sont évalués sur une pile pour prendre en charge les clauses AND / OR imbriquées. Une pile individuelle est assignée à chaque thread serveur. La profondeur de la pile détermine la complexité d'un filtre qui peut être évalué sans nécessiter d'allocation de mémoire supplémentaire. Les filtres imbriqués plus profondément que la profondeur de la pile de recherche provoqueront l'allocation d'une pile séparée pour cette opération de recherche particulière. Ces allocations peuvent avoir un impact négatif majeur sur les performances du serveur, mais spécifier une pile trop importante consommera également beaucoup de mémoire. Chaque pile de recherche utilise 512 Ko par niveau. La profondeur de pile par défaut est de 16, donc 8 Mo par thread est utilisé.

CONTRÔLE D'ACCÈS

Le backend mdb respecte les sémantiques de contrôle d'accès comme indiqué dans slapd.access(5).
