NOM

slapd-ldap - Backend LDAP pour slapd

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

Le backend LDAP de slapd(8) n'est pas une véritable base de données ; il agit plutôt comme un proxy pour transférer les requêtes entrantes vers un autre serveur LDAP. Lors du traitement des requêtes, il suivra également les renvois, de sorte que les renvois soient entièrement traités au lieu d'être renvoyés au client slapd.

Les sessions qui se lient explicitement à la base de données back-ldap créent toujours leur propre connexion privée avec le serveur LDAP distant. Les sessions anonymes partageront une seule connexion anonyme avec le serveur distant. Pour les sessions liées via d'autres mécanismes, toutes les sessions avec le même DN partageront la même connexion. Cette stratégie de mise en commun des connexions peut améliorer l'efficacité du proxy en réduisant la surcharge liée à l'établissement/la rupture répétées de multiples connexions.

L'instance proxy de slapd(8) doit contenir des informations de schéma pour les attributs et les objectClasses utilisés dans les filtres, les DN de requête et les données relatives aux requêtes en général. Elle devrait également contenir des informations de schéma pour les données renvoyées par le serveur proxifié. Il incombe à l'administrateur du proxy de maintenir le schéma du proxy aligné sur celui du serveur proxifié.

Note : En cas de bouclage vers la même instance de slapd(8), chaque connexion nécessite un nouveau thread ; par conséquent, le paramètre threads de slapd(8) pourrait nécessiter un certain ajustement. Dans ces cas, on peut envisager d'utiliser slapd-relay(5) à la place, qui effectue l'opération relayée en interne et réutilise ainsi la même connexion.

CONFIGURATION

Ces options slapd.conf s'appliquent à la base de données backend LDAP. C'est-à-dire qu'elles doivent suivre une ligne "database ldap" et précéder toute ligne "backend" ou "database" ultérieure. Les autres options de base de données sont décrites dans la page de manuel slapd.conf(5).

Note : Dans les premières versions de back-ldap, il était recommandé de toujours définir

lastmod  off

pour les bases de données ldap et meta. Ceci était nécessaire car les attributs opérationnels liés à la création et à la modification des entrées ne devaient pas être proxifiés, car ils pouvaient être écrits par erreur sur le ou les serveurs cibles, générant une erreur. L'implémentation actuelle définit automatiquement lastmod sur off, son utilisation est donc redondante et doit être omise.

uri <ldapurl>
Serveur LDAP à utiliser. Plusieurs URI peuvent être définis dans un seul argument ldapurl, ce qui amène la bibliothèque sous-jacente à appeler automatiquement le premier serveur de la liste qui répond, par exemple

uri "ldap://hote/ ldap://hote-secours/"

La liste des URI est séparée par des espaces ou des virgules. Chaque fois que le serveur qui répond n'est pas le premier de la liste, la liste est réorganisée et le serveur réactif est déplacé en tête, de sorte qu'il soit contacté en premier la prochaine fois qu'une connexion doit être créée.

acl-bind bindmethod=simple|sasl [binddn=<DN simple>] [credentials=<mot de passe simple>] [saslmech=<mécanisme SASL>] [secprops=<propriétés>] [realm=<domaine>] [authcId=<ID d'authentification>] [authzId=<ID d'autorisation>] [starttls=no|yes|critical] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<chiffrements>] [tls_ecname=<noms>] [tls_protocol_min=<majeur>[.<mineur>]] [tls_crlcheck=none|peer|all]

Permet de définir les paramètres de la méthode d'authentification utilisée en interne par le proxy pour collecter des informations relatives au contrôle d'accès, et chaque fois qu'une opération se produit avec l'identité du rootdn de la base de données proxy LDAP. L'identité définie par cette directive, conformément aux propriétés associées à la méthode d'authentification, est supposée avoir un accès en lecture sur le serveur cible aux attributs utilisés sur le proxy pour la vérification des ACL.

Il n'y a aucun risque de divulgation de ces valeurs ; elles sont uniquement utilisées pour vérifier les permissions. Par défaut, la liaison simple est utilisée, avec binddn et credentials vides, ce qui signifie que les opérations associées seront effectuées de manière anonyme. Si non défini, et si idassert-bind est défini, cette dernière identité est utilisée à la place. Voir idassert-bind pour plus de détails.

La connexion entre la base de données proxy et le serveur distant associée à cette identité est mise en cache indépendamment de la durée de vie de la connexion client-proxy qui l'a initialement établie.

Cette identité n'est pas utilisée implicitement par le proxy lorsque le client se connecte anonymement. La fonctionnalité idassert-bind, quant à elle, peut dans certains cas être configurée pour implémenter ce comportement, ce qui est intrinsèquement non sécurisé et doit être utilisé avec une extrême prudence.

Les paramètres TLS par défaut sont les mêmes que les paramètres TLS principaux de slapd, à l'exception de tls_reqcert qui est par défaut "demand", et tls_reqsan qui est par défaut "allow".

cancel {ABANDON|ignore|exop[-discover]}
Définit comment gérer l'annulation d'une opération. Par défaut, abandon est appelée, de sorte que l'opération est abandonnée immédiatement. Si défini sur ignore, aucune action n'est effectuée et toute réponse ultérieure est ignorée ; cela peut entraîner la mise en file d'attente de messages de réponse supplémentaires pour cette connexion, il est donc recommandé que les connexions de longue durée soient expirées soit par idle-timeout soit par conn-ttl, afin que les ressources soient éventuellement libérées. Si défini sur exop, une opération cancel (RFC 3909) est émise, entraînant l'annulation de l'opération en cours ; l'opération cancel attend la réponse du serveur distant, son utilisation peut donc ne pas être recommandée. Si défini sur exop-discover, la prise en charge de l'opération étendue cancel est détectée en lisant le DSE racine du serveur distant.
chase-referrals {YES|no}
active/désactive le suivi automatique des renvois, qui est délégué à la bibliothèque libldap sous-jacente, avec une re-liaison effectuée éventuellement si la directive rebind-as-user est utilisée. Par défaut, les renvois sont suivis.
conn-pool-max <int>
Cette directive définit la taille maximale du pool de connexions privilégiées.
conn-ttl <temps>
Cette directive entraîne la fermeture d'une connexion mise en cache après une durée de vie donnée, qu'elle soit inactive ou non. Si une connexion client survit à la connexion distante, le client recevra LDAP_UNAVAILABLE lorsqu'il exécutera la prochaine opération.
idassert-authzFrom <authz-regexp>
si défini, sélectionne quelles identités locales sont autorisées à exploiter la fonctionnalité d'assertion d'identité. La chaîne <authz-regexp> suit la plupart des règles définies pour l'attribut authzFrom. Voir slapd.conf(5), section relative à authz-policy, pour les détails sur la syntaxe de ce champ. Ce paramètre diffère du comportement documenté concernant la signification de *, qui dans ce cas autorise l'anonymat plutôt que de le refuser.

idassert-bind bindmethod=none|simple|sasl [binddn=<DN simple>] [credentials=<mot de passe simple>] [saslmech=<mécanisme SASL>] [secprops=<propriétés>] [realm=<domaine>] [authcId=<ID d'authentification>] [authzId=<ID d'autorisation>] [authz={native|proxyauthz}] [mode

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

=<mode>] [flags=<flags>] [starttls=non|oui|critique] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=jamais|autoriser|essayer|exiger] [tls_reqsan=jamais|autoriser|essayer|exiger] [tls_cipher_suite=<chiffrements>] [tls_ecname=<noms>] [tls_protocol_min=<version>] [tls_crlcheck=aucun|pair|tous]

Permet de définir les paramètres de la méthode d'authentification qui est utilisée en interne par le proxy pour autoriser les connexions authentifiées par d'autres bases de données. Les liaisons directes sont toujours transmises sans aucune gestion d'assertion d'identité.

L'identité définie par cette directive, selon les propriétés associées à la méthode d'authentification, est censée avoir un accès d'authentification sur le serveur cible aux attributs utilisés sur le proxy pour l'authentification et l'autorisation, et être autorisée à autoriser les utilisateurs. Cela nécessite d'avoir les privilèges proxyAuthz sur un large ensemble de DN, par ex. authzTo=dn.subtree:"", et que le serveur distant ait authz-policy défini sur to ou both. Voir slapd.conf(5) pour les détails sur ces instructions ainsi que pour les remarques et les inconvénients concernant leur utilisation. Les méthodes de liaison prises en charge sont

none|simple|sasl

où none est la valeur par défaut, c'est-à-dire qu'aucune assertion d'identité n'est effectuée.

Le paramètre authz est utilisé pour indiquer à la liaison SASL d'exploiter l'autorisation SASL native, si disponible ; étant donné que les connexions sont mises en cache, cela ne doit être utilisé que lors de l'autorisation avec une identité fixe (par exemple, au moyen des paramètres authzDN ou authzID). Sinon, le proxyauthz par défaut est utilisé, c'est-à-dire que le contrôle proxyAuthz (Proxied Authorization, RFC 4370) est ajouté à toutes les opérations.

Les modes pris en charge sont :

<mode> := {legacy|anonymous|none|self}

Si <mode> est absent et que authzId est fourni, le proxy autorise toujours cette identité. <authorization ID> peut être

u:<utilisateur>

[dn:]<DN>

Le premier est censé être développé par le serveur distant conformément aux règles d'autorisation ; voir slapd.conf(5) pour plus de détails. Dans le second cas, que le préfixe dn: soit présent ou non, la chaîne doit passer la validation et la normalisation du DN.

Le mode par défaut est legacy, ce qui implique que le proxy effectuera une liaison simple en tant que authcDN ou une liaison SASL en tant que authcID et affirmera l'identité du client lorsqu'elle n'est pas anonyme. Les autres modes impliquent que le proxy effectuera toujours une liaison simple en tant que authcDN ou une liaison SASL en tant que authcID, sauf si restreint par les règles idassert-authzFrom (voir ci-dessous), auquel cas l'opération échouera ; finalement, il affirmera une autre identité conformément à <mode>. D'autres modes d'assertion d'identité sont anonymous et self, qui signifient respectivement que l'identité vide ou celle du client sera affirmée ; none, ce qui signifie qu'aucun contrôle proxyAuthz ne sera utilisé, donc l'identité authcDN ou authcID sera affirmée. Pour tous les modes qui nécessitent l'utilisation du contrôle proxyAuthz, sur le serveur distant, l'identité du proxy doit avoir les permissions authzTo appropriées, ou les identités affirmées doivent avoir les permissions authzFrom appropriées. Notez cependant que la fonctionnalité d'assertion d'identité est principalement utile lorsque les identités affirmées n'existent pas sur le serveur distant.

Les indicateurs peuvent être

override,[non-]prescriptive,proxy-authz-[non-]critical,dn-{authzid|whoami}

Lorsque l'indicateur override est utilisé, l'assertion d'identité a lieu même lorsque la base de données autorise l'identité du client, c'est-à-dire qu'après avoir établi une liaison avec l'identité fournie, et donc l'avoir authentifiée, le proxy effectue l'assertion d'identité en utilisant l'identité et la méthode d'authentification configurées.

Lorsque l'indicateur prescriptive est utilisé (par défaut), les opérations échouent avec inappropriateAuthentication pour les identités dont l'assertion n'est pas autorisée par les motifs idassert-authzFrom. Si l'indicateur non-prescriptive est utilisé, les opérations sont effectuées anonymement pour les identités dont l'assertion n'est pas autorisée par les motifs idassert-authzFrom.

Lorsque l'indicateur proxy-authz-non-critical est utilisé (par défaut), le contrôle proxyAuthz n'est pas marqué comme critique, en violation de la RFC 4370. L'utilisation de proxy-authz-critical est recommandée.

Lorsque l'indicateur dn-authzid est utilisé, les contrôles d'identité d'autorisation LDAP RFC 3829 sont utilisés pour récupérer l'identité associée à l'identité SASL ; lorsque l'indicateur dn-whoami est utilisé, l'opération LDAP Who am I? RFC 4532 est effectuée après la liaison dans le même but.

Les paramètres TLS sont par défaut les mêmes que les paramètres TLS principaux de slapd, à l'exception de tls_reqcert qui est par défaut "demand", et tls_reqsan qui est par défaut "allow".

L'identité associée à cette directive est également utilisée pour les opérations privilégiées chaque fois que idassert-bind est défini et que acl-bind ne l'est pas. Voir acl-bind pour plus de détails.

idassert-passthru <authz-regexp>
Si défini, sélectionne quelles identités locales contournent la fonctionnalité d'assertion d'identité. Ces identités doivent être connues de l'hôte distant. La chaîne <authz-regexp> suit les règles définies pour l'attribut authzFrom. Voir slapd.conf(5), section relative à authz-policy, pour les détails de la syntaxe de ce champ.
idle-timeout <temps>
Cette directive provoque la fermeture d'une connexion mise en cache après avoir été inactive pendant le temps spécifié. Si une connexion client survit à la connexion distante, le client recevra LDAP_UNAVAILABLE lorsqu'il exécutera la prochaine opération.
keepalive <idle>:<probes>:<interval>
Le paramètre keepalive définit les valeurs de idle, probes et interval utilisées pour vérifier si un socket est actif ; idle est le nombre de secondes pendant lesquelles une connexion doit rester inactive avant que TCP ne commence à envoyer des sondes keepalive ; probes est le nombre maximum de sondes keepalive que TCP doit envoyer avant de fermer la connexion ; interval est l'intervalle en secondes entre les sondes keepalive individuelles. Seuls certains systèmes prennent en charge la personnalisation de ces valeurs ; le paramètre keepalive est ignoré sinon, et les paramètres globaux du système sont utilisés.
tcp-user-timeout <millisecondes>
Si non nul, correspond à TCP_USER_TIMEOUT défini sur les connexions cibles, remplaçant le paramètre du système d'exploitation. Seuls certains systèmes prennent en charge la personnalisation de ce paramètre, il est ignoré sinon et les paramètres globaux du système sont utilisés.
network-timeout <temps>
Définit la valeur du délai d'attente réseau après lequel poll(2)/select(2) après un connect(2) retourne en cas d'absence d'activité. La valeur est en secondes, et elle peut être spécifiée comme pour idle-timeout.
norefs {NO|yes}
Si yes, ne renvoie pas les réponses de référence de recherche. Par défaut, elles sont renvoyées à moins que la requête ne soit LDAPv2.
omit-unknown-schema {NO|yes}
Si yes, ne renvoie pas les objectClasses ou attributs qui ne sont pas connus du serveur local. Par défaut, tous les éléments du schéma sont renvoyés.
noundeffilter {NO|yes}
Si yes, renvoie succès au lieu de rechercher si un filtre est non défini ou contient des parties non définies. Par défaut, la recherche est propagée après le remplacement des parties non définies par (!(objectClass=*)), ce qui correspond à l'ensemble de résultats vide.
onerr {CONTINUE|stop}
Cette directive permet de sélectionner le comportement en cas d'erreur renvoyée par le serveur distant lors d'une recherche. La valeur par défaut, continue, consiste à renvoyer succès. Si la valeur est définie sur stop, l'erreur est renvoyée au client.
protocol-version {0,2,3}
Cette directive indique quelle version de protocole doit être utilisée pour contacter le serveur distant. Si elle est définie sur 0 (par défaut), le proxy utilise la même version de protocole que celle utilisée par le client, sinon le protocole demandé est utilisé. Le proxy renvoie unwillingToPerform si une opération incompatible avec le protocole demandé est tentée.
proxy-whoami {NO|yes}
Active la transmission de l'opération étendue WhoAmI. Si cette option est fournie, back-ldap remplacera la routine WhoAmI d'origine de slapd par la sienne. Sur les sessions slapd qui ont été authentifiées par back-ldap, la requête WhoAmI sera transmise au serveur LDAP distant. Les autres sessions seront gérées par le slapd local, comme auparavant. Cette option est principalement utile en conjonction avec Proxy Authorization.
quarantine <interval>,<num>[;<interval>,<num>[...]]
Active la mise en quarantaine des URI qui ont renvoyé LDAP_UNAVAILABLE, de sorte qu'une tentative de reconnexion ne se produise qu'à des intervalles donnés au lieu de toute tentative lorsqu'un client demande une opération. Le modèle est le suivant : retenter uniquement après que interval secondes au moins se soient écoulées depuis la dernière tentative, pendant exactement num fois ; puis utiliser le modèle suivant. Si num pour le dernier modèle est "+", il retente indéfiniment ; sinon, plus aucune tentative n'est effectuée. Le processus peut être redémarré en réinitialisant l'attribut olcDbQuarantine de l'entrée de base de données dans le backend de configuration.
rebind-as-user {NO|yes}
Si cette option est fournie, les informations d'identification de liaison du client sont mémorisées pour les rebinds, lors de la tentative de rétablissement d'une connexion interrompue, ou lors du suivi d'une référence, si chase-referrals est défini sur yes. Notez cependant que la connexion n'est pas rétablie automatiquement après avoir été interrompue en raison de idle-timeout ou conn-ttl.
session-tracking-request {NO|oui}
Ajoute le suivi de session pour toutes les requêtes. L'adresse IP et le nom d'hôte du client, ainsi que l'identité associée à chaque requête, si connue, sont envoyés au serveur distant à des fins d'information. Cette directive est incompatible avec la définition de protocol-version à 2.
single-conn {NO|oui}
Supprime la connexion mise en cache actuelle lorsque le client se reconnecte.
t-f-support {NO|oui|discover}
active si le serveur distant prend en charge les filtres absolus (voir RFC 4526 pour plus de détails). Si défini sur discover, la prise en charge est détectée en lisant le DSE racine du serveur distant.
timeout [<op>=]<val> [...]
Cette directive permet de définir des délais d'attente par opération. Les opérations peuvent être

<op> ::= bind, add, delete, modrdn, modify, compare, search

La durée totale de l'opération search est contrôlée soit par le paramètre timelimit, soit par les limites de temps imposées côté serveur (voir timelimit et limits dans slapd.conf(5) pour plus de détails). Ce paramètre timeout contrôle combien de temps la cible peut être sans réponse avant que l'opération ne soit annulée. Le délai d'attente est dénué de sens pour les opérations restantes, unbind et abandon, qui n'impliquent aucune réponse, tandis qu'il n'est pas encore implémenté dans les opérations extended actuellement prises en charge. Si aucune opération n'est spécifiée, le délai d'attente val affecte toutes les opérations prises en charge.

Note : si la limite de temps est dépassée, l'opération est annulée (conformément à la directive cancel) ; le protocole ne fournit aucun moyen de rétablir les opérations, de sorte que le client ne sera pas informé du résultat de l'opération, qui peut éventuellement réussir ou non. En cas de dépassement du délai d'attente lors d'une opération de bind, la connexion est détruite, conformément à la RFC4511.

Note : dans certains cas, ce backend peut émettre des binds avant d'autres opérations (par exemple, pour se lier anonymement ou avec une identité prescrite conformément à la directive idassert-bind). Dans ce cas, le délai d'attente de l'opération qui a entraîné le bind est utilisé.

tls {none|[try-]start|[try-]propagate|ldaps} [starttls=no] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<chiffrements>] [tls_ecname=<noms>] [tls_crlcheck=none|peer|all]

Spécifie les paramètres TLS pour les connexions régulières.

Si le premier paramètre n'est pas "none", cela configure les paramètres TLS à utiliser pour les connexions régulières. L'opération étendue StartTLS sera utilisée lors de l'établissement de la connexion, sauf si le schéma de protocole de la directive URI est ldaps://. Dans ce cas, ce mot-clé ne peut être défini que sur "ldaps" et l'opération StartTLS ne sera pas utilisée.

Avec propagate, le proxy émet l'opération StartTLS uniquement si la connexion d'origine a une couche TLS configurée. Le préfixe try- demande au proxy de continuer les opérations si l'opération StartTLS a échoué ; son utilisation n'est pas recommandée.

Les paramètres TLS sont par défaut les mêmes que les paramètres TLS principaux de slapd, à l'exception de tls_reqcert qui est par défaut "demand", tls_reqsan qui est par défaut "allow", et starttls qui est éclipsé par le premier mot-clé et donc ignoré.

use-temporary-conn {NO|oui}
lorsque défini sur yes, crée une connexion temporaire lors de la concurrence avec d'autres threads pour une connexion partagée ; sinon, attend que la connexion partagée soit disponible.

CONTRÔLE D'ACCÈS

Le backend ldap ne respecte pas toutes les sémantiques des ACL telles que décrites dans slapd.access(5). En général, la vérification d'accès est déléguée aux serveurs distants. Seul l'accès en lecture (=r) au pseudo-attribut entry et aux autres valeurs d'attribut des entrées retournées par l'opération search est respecté, ce qui est effectué par le frontend.

SUPERPOSITIONS

Le backend LDAP fournit des fonctionnalités de proxy de base pour de nombreuses superpositions. La superposition chain, décrite dans slapo-chain(5), et la superposition translucent, décrite dans slapo-translucent(5), méritent une mention spéciale.

Inversement, de nombreuses superpositions sont mieux utilisées en conjonction avec le backend LDAP. La superposition proxycache permet la mise en cache des requêtes de recherche LDAP (requêtes) dans une base de données locale. Voir slapo-pcache(5) pour plus de détails. La superposition rwm fournit des capacités de réécriture de DN et de mappage d'attributs/objectClass à la base de données sous-jacente. Voir slapo-rwm(5) pour plus de détails.
