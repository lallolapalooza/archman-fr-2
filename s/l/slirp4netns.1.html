SLIRP4NETNS(1) Commandes utilisateur SLIRP4NETNS(1)

NOM

slirp4netns - Réseau en mode utilisateur pour les espaces réseau non privilégiés

SYNTAXE

slirp4netns [OPTION]... PID|CHEMIN|FD [NOM_TAP]

DESCRIPTION

slirp4netns fournit le réseau en mode utilisateur (« slirp ») pour les espaces réseau.

Contrairement à veth(4), slirp4netns ne nécessite pas les privilèges root sur l'hôte.

Configuration par défaut :

  • MTU : 1500
  • CIDR : 10.0.2.0/24
  • Passerelle/Hôte : 10.0.2.2 (adresse réseau + 2)
  • DNS : 10.0.2.3 (adresse réseau + 3)
  • Démarrage DHCP : 10.0.2.15 (adresse réseau + 15)
  • Fin DHCP : 10.0.2.30 (adresse réseau + 30)
  • CIDR IPv6 : fd00::/64
  • Passerelle/Hôte IPv6 : fd00::2
  • DNS IPv6 : fd00::3

OPTIONS

-c, --configure active l'interface TAP. L'IP sera définie par défaut à 10.0.2.100 (adresse réseau + 100). L'IPv6 sera défini sur une adresse aléatoire. Depuis la v0.4.0, l'interface de bouclage (lo) est également activée.

-e, --exit-fd=FD spécifie le descripteur de fichier (FD) pour terminer slirp4netns. Lorsque le FD est spécifié, slirp4netns se termine lorsqu'un événement poll(2) se produit sur le FD.

-r, --ready-fd=FD spécifie le FD vers lequel écrire lorsque les étapes d'initialisation sont terminées. Lorsque le FD est spécifié, slirp4netns écrit « 1 » dans le FD et ferme le FD. Avant la v0.4.0, le FD était écrit après la configuration réseau (-c) mais avant la configuration du socket API (-a).

-m, --mtu=MTU (depuis v0.2.0) spécifie le MTU (max=65521).

-6, --enable-ipv6 (depuis v0.2.0, EXPÉRIMENTAL) active l'IPv6

-a, --api-socket (depuis v0.3.0) chemin du socket API

--cidr (depuis v0.3.0) spécifie le CIDR, par exemple 10.0.2.0/24

--disable-host-loopback (depuis v0.3.0) interdit la connexion à 127.0.0.1:* dans l'espace réseau de l'hôte

--netns-type=TYPE (depuis v0.4.0) spécifie le type d'espace réseau ([path|pid|tapfd], par défaut=pid)

Si le type d'espace est tapfd, le premier argument positionnel est attendu comme étant un descripteur de fichier hérité qui correspond à une connexion /dev/net/tun. Cela entre en conflit avec --configure et un NOM_TAP est ignoré.

--userns-path=PATH (depuis v0.4.0) spécifie le chemin de l'espace utilisateur

--enable-sandbox (depuis v0.4.0) entre dans l'espace utilisateur et crée un nouvel espace de montage où seuls /etc et /run sont montés depuis l'hôte.

Nécessite que /etc/resolv.conf ne soit pas un lien symbolique vers un fichier en dehors de /etc et /run.

Lors de l'exécution en tant que root, le processus n'entre pas dans l'espace utilisateur mais toutes les capacités sauf CAP_NET_BIND_SERVICE sont supprimées.

--enable-seccomp (depuis v0.4.0, EXPÉRIMENTAL) active seccomp(2) pour limiter les appels système. Typiquement utilisé en conjonction avec --enable-sandbox.

--outbound-addr=IPv4 (depuis v1.1.0, EXPÉRIMENTAL) spécifie l'adresse ipv4 sortante sur laquelle slirp doit se lier

--outbound-addr=INTERFACE (depuis v1.1.0, EXPÉRIMENTAL) spécifie l'interface sortante sur laquelle slirp doit se lier (trafic ipv4 uniquement)

--outbound-addr=IPv6 (depuis v1.1.0, EXPÉRIMENTAL) spécifie l'adresse ipv6 sortante sur laquelle slirp doit se lier

--outbound-addr6=INTERFACE (depuis v1.1.0, EXPÉRIMENTAL) spécifie l'interface sortante sur laquelle slirp doit se lier (trafic ipv6 uniquement)

--disable-dns (depuis v1.1.0) désactive le DNS intégré (10.0.2.3 par défaut)

--macaddress (depuis v1.1.9) spécifie l'adresse MAC de l'interface TAP (valide uniquement avec -c)

--target-type=TYPE (depuis v1.2.0) spécifie le type de cible ([netns|bess], par défaut=netns).

Le mode bess (depuis v1.2.0, EXPÉRIMENTAL) est censé être utilisé avec User Mode Linux. Le mode bess entre en conflit avec --configure, --netns-type et --userns-path.

-h, --help (depuis v0.2.0) affiche l'aide et quitte

-v, --version (depuis v0.2.0) affiche la version et quitte

EXEMPLE

Terminal 1 : Créer des espaces utilisateur/réseau/montage

(host)$ unshare --user --map-root-user --net --mount
(namespace)$ echo $$ > /tmp/pid

Dans cette documentation, nous utilisons (host)$ comme invite du shell hôte, et (namespace)$ comme invite du shell s'exécutant dans les espaces.

Si unshare échoue, essayez les commandes suivantes (savoir si elles sont nécessaires sur Debian, Arch et les anciennes versions de CentOS 7.X) :

(host)$ sudo sh -c 'echo "user.max_user_namespaces=28633" >> /etc/sysctl.d/userns.conf'
(host)$ if [ -f /proc/sys/kernel/unprivileged_userns_clone ]; then sudo sh -c 'echo "kernel.unprivileged_userns_clone=1" >> /etc/sysctl.d/userns.conf'; fi
(host)$ sudo sysctl --system

Terminal 2 : Démarrer slirp4netns

(host)$ slirp4netns --configure --mtu=65520 $(cat /tmp/pid) tap0
starting slirp, MTU=65520

Terminal 1 : Assurez-vous que tap0 est configuré et connecté à Internet

(namespace)$ ip a
1: lo: <LOOPBACK> mtu 65536 qdisc noop state DOWN group default qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
3: tap0: <BROADCAST,UP,LOWER_UP> mtu 65520 qdisc fq_codel state UNKNOWN group default qlen 1000
    link/ether c2:28:0c:0e:29:06 brd ff:ff:ff:ff:ff:ff
    inet 10.0.2.100/24 brd 10.0.2.255 scope global tap0
       valid_lft forever preferred_lft forever
    inet6 fe80::c028:cff:fe0e:2906/64 scope link 
       valid_lft forever preferred_lft forever
(namespace)$ echo "nameserver 10.0.2.3" > /tmp/resolv.conf
(namespace)$ mount --bind /tmp/resolv.conf /etc/resolv.conf
(namespace)$ curl https://example.com

Le montage par liaison (bind mount) de /etc/resolv.conf n'est nécessaire que lorsque /etc/resolv.conf sur l'hôte fait référence à des adresses de bouclage (127.0.0.X, typiquement dnsmasq(8) ou systemd-resolved.service(8)) qui ne sont pas accessibles depuis l'espace réseau.

Si votre /etc/resolv.conf sur l'hôte est géré par networkmanager(8) ou systemd-resolved.service(8), vous pourriez devoir monter un nouveau système de fichiers sur /etc à la place, afin d'empêcher le nouveau /etc/resolv.conf d'être démonté de manière inattendue lorsque /etc/resolv.conf sur l'hôte est régénéré.

(namespace)$ mkdir /tmp/a /tmp/b
(namespace)$ mount --rbind /etc /tmp/a
(namespace)$ mount --rbind /tmp/b /etc
(namespace)$ mkdir /etc/.ro
(namespace)$ mount --move /tmp/a /etc/.ro
(namespace)$ cd /etc
(namespace)$ for f in .ro/*; do ln -s $f $(basename $f); done
(namespace)$ rm resolv.conf
(namespace)$ echo "nameserver 10.0.2.3" > resolv.conf
(namespace)$ curl https://example.com

Ces étapes peuvent être simplifiées avec rootlesskit --copy-up=/etc si rootlesskit est installé :

(host)$ rootlesskit --net=slirp4netns --copy-up=/etc bash
(namespace)$ cat /etc/resolv.conf
nameserver 10.0.2.3

ROUTAGE PAQUETS PING

Pour router les paquets ping, vous pourriez avoir besoin de configurer correctement net.ipv4.ping_group_range en tant que root.

par exemple.

(host)$ sudo sh -c 'echo "net.ipv4.ping_group_range=0   2147483647" > /etc/sysctl.d/ping_group_range.conf'
(host)$ sudo sysctl --system

FILTRAGE CONNEXIONS

Par défaut, les ports en écoute sur INADDR_LOOPBACK (127.0.0.1) sur l'hôte sont accessibles depuis l'espace enfant via la passerelle (par défaut : 10.0.2.2). --disable-host-loopback peut être utilisé pour interdire la connexion à INADDR_LOOPBACK sur l'hôte.

Cependant, une adresse de bouclage de l'hôte peut toujours être accessible via le DNS intégré (par défaut : 10.0.2.3) si /etc/resolv.conf sur l'hôte fait référence à une adresse de bouclage. Vous pourriez vouloir configurer iptables pour limiter l'accès au DNS intégré dans un tel cas.

(host)$ nsenter -t $(cat /tmp/pid) -U --p
reserve-credentials -n (espace de noms)$ iptables -A OUTPUT -d 10.0.2.3 -p udp --dport 53 -j ACCEPT (espace de noms)$ iptables -A OUTPUT -d 10.0.2.3 -j DROP

SOCKET

slirp4netns peut fournir un serveur d'API de type QMP sur un fichier de socket UNIX :

(hôte)$ slirp4netns --api-socket /tmp/slirp4netns.sock ...

add_hostfwd : Exposer un port (IPv4 uniquement)

(espace de noms)$ json='{"execute": "add_hostfwd", "arguments": {"proto": "tcp", "host_addr": "0.0.0.0", "host_port": 8080, "guest_addr": "10.0.2.100", "guest_port": 80}}'
(espace de noms)$ echo -n $json | nc -U /tmp/slirp4netns.sock
{"return": {"id": 42}}

Si host_addr n'est pas spécifié, il vaut par défaut "0.0.0.0".

Si guest_addr n'est pas spécifié, il sera défini sur l'adresse par défaut qui correspond à --configure.

list_hostfwd : Lister les ports exposés

(espace de noms)$ json='{"execute": "list_hostfwd"}'
(espace de noms)$ echo -n $json | nc -U /tmp/slirp4netns.sock
{"return": {"entries": [{"id": 42, "proto": "tcp", "host_addr": "0.0.0.0", "host_port": 8080, "guest_addr": "10.0.2.100", "guest_port": 80}]}}

remove_hostfwd : Supprimer un port exposé

(espace de noms)$ json='{"execute": "remove_hostfwd", "arguments": {"id": 42}}'
(espace de noms)$ echo -n $json | nc -U /tmp/slirp4netns.sock
{"return": {}}

Remarques :

  • Le client doit shutdown(2) le socket avec SHUT_WR après l'envoi de chaque requête. C'est-à-dire, pas de prise en charge de la connexion persistante ni du timeout.
  • slirp4netns "arrête le monde" pendant le traitement des requêtes API.
  • Une requête doit faire moins de 4096 octets.
  • Les réponses JSON peuvent contenir error au lieu de return.

CHEMINS DES ESPACES DE NOMMAGE DÉFINIS

Un utilisateur peut définir un chemin d'espace de nommage réseau au lieu de l'ID de processus par défaut :

(hôte)$ slirp4netns --netns-type=path ... /chemin/vers/netns tap0

Actuellement, l'argument netns-type=TYPE prend en charge les arguments path ou pid, le défaut étant pid.

De plus, un argument --userns-path=PATH peut être inclus pour remplacer les valeurs par défaut du chemin de l'espace de nommage utilisateur.

(hôte)$ slirp4netns --netns-type=path --userns-path=/chemin/vers/userns /chemin/vers/netns tap0

ADRESSES SORTANTES

Un utilisateur peut définir une adresse de sortie IPv4 et IPv6 préférée dans les scénarios multi-IP.

(hôte)$ slirp4netns --outbound-addr=10.2.2.10 --outbound-addr6=fe80::10 ...

Optionnellement, vous pouvez utiliser des noms d'interface au lieu d'adresses IP.

(hôte)$ slirp4netns --outbound-addr=eth0 --outbound-addr6=eth0 ...

COMMUNICATION INTER-ESPACES DE NOMMAGE

La manière la plus simple de permettre la communication inter-espaces de nommage est de imbriquer des espaces de nommage réseau dans l'espace de nommage réseau de slirp4netns.

(hôte)$ nsenter -t $(cat /tmp/pid) -U --preserve-credentials -n -m
(espace de noms)$ mount -t tmpfs none /run
(espace de noms)$ ip netns add foo
(espace de noms)$ ip netns add bar
(espace de noms)$ ip link add veth-foo type veth peer name veth-bar
(espace de noms)$ ip link set veth-foo netns foo
(espace de noms)$ ip link set veth-bar netns bar
(espace de noms)$ ip netns exec foo ip link set veth-foo name eth0
(espace de noms)$ ip netns exec bar ip link set veth-bar name eth0
(espace de noms)$ ip netns exec foo ip link set lo up
(espace de noms)$ ip netns exec bar ip link set lo up
(espace de noms)$ ip netns exec foo ip link set eth0 up
(espace de noms)$ ip netns exec bar ip link set eth0 up
(espace de noms)$ ip netns exec foo ip addr add 192.168.42.100/24 dev eth0
(espace de noms)$ ip netns exec bar ip addr add 192.168.42.101/24 dev eth0
(espace de noms)$ ip netns exec bar ping 192.168.42.100

Cependant, cette méthode ne fonctionne pas lorsque vous souhaitez permettre la communication entre plusieurs instances de slirp4netns. Pour permettre la communication entre plusieurs instances de slirp4netns, vous devez combiner une autre pile réseau telle que vde_plug(1) avec slirp4netns.

(hôte)$ vde_plug --daemon switch:///tmp/switch null://
(hôte)$ nsenter -t $(cat /tmp/pid-instance0) -U --preserve-credentials -n
(espace de noms-instance0)$ vde_plug --daemon vde:///tmp/switch tap://vde
(espace de noms-instance0)$ ip link set vde up
(espace de noms-instance0)$ ip addr add 192.168.42.100/24 dev vde
(espace de noms-instance0)$ exit
(hôte)$ nsenter -t $(cat /tmp/pid-instance1) -U --preserve-credentials -n
(espace de noms-instance1)$ vde_plug --daemon vde:///tmp/switch tap://vde
(espace de noms-instance1)$ ip link set vde up
(espace de noms-instance1)$ ip addr add 192.168.42.101/24 dev vde
(espace de noms-instance1)$ ping 192.168.42.100

COMMUNICATION INTER-HÔTES

VXLAN est connu pour fonctionner. Voir le projet Usernetes pour un exemple de cluster Kubernetes rootless multi-nœuds avec VXLAN : https://github.com/rootless-containers/usernetes

MODE BESS (POUR USER MODE LINUX)

slirp4netns (depuis v1.2.0) peut également être utilisé comme un serveur compatible BESS pour fournir une connectivité réseau à User Mode Linux.

Terminal 1 : Lancer slirp4netns

(hôte)$ slirp4netns --target-type=bess /tmp/bess.sock

Terminal 2 : Lancer User Mode Linux

(hôte)$ linux.uml vec0:transport=bess,dst=/tmp/bess.sock,depth=128,gro=1 root=/dev/root rootfstype=hostfs init=/bin/bash mem=2G
(UML)$ ip addr add 10.0.2.100/24 dev vec0
(UML)$ ip link set vec0 up
(UML)$ ip route add default via 10.0.2.2

Actuellement, une seule instance de User Mode Linux peut être connectée au serveur BESS de slirp4netns.

Voir également la documentation de User Mode Linux : https://www.kernel.org/doc/html/latest/virt/uml/user_mode_linux_howto_v2.html#bess-socket-transport

BOGUES

Le noyau 4.20 a augmenté la valeur par défaut de /proc/sys/net/ipv4/tcp_rmem de 87380 à 131072. Ceci est connu pour ralentir le transfert de port de slirp4netns : https://github.com/rootless-containers/slirp4netns/issues/128.

Comme solution de contournement, vous pouvez ajuster la valeur de /proc/sys/net/ipv4/tcp_rmem à l'intérieur de l'espace de nommage. Aucun privilège root réel n'est nécessaire pour modifier le fichier depuis le noyau 4.15.

(hôte)$ nsenter -t $(cat /tmp/pid) -U --preserve-credentials -n -m
(espace de noms)$ c=$(cat /proc/sys/net/ipv4/tcp_rmem); echo $c | sed -e s/131072/87380/g > /proc/sys/net/ipv4/tcp_rmem
