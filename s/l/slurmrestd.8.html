slurmrestd(8) Démon REST de Slurm slurmrestd(8)

NOM

slurmrestd - Interface vers Slurm via l'API REST.

SYNTAXE

slurmrestd [OPTIONS...] <[hôte]:port|unix:/chemin/vers/socket>...

DESCRIPTION

slurmrestd est une interface d'API REST pour Slurm. Il peut être utilisé dans deux modes :

Mode Inetd : slurmrestd lira et écrira sur STDIO. Si STDIN est un descripteur de fichier socket, alors slurmrestd le détectera et utilisera la fonctionnalité pertinente. Ce mode est conçu pour fonctionner avec des entrées pipées, inetd, xinetd ou l'activation de socket systemd.

Mode Écoute : slurmrestd ouvrira un socket d'écoute sur chaque paire hôte:port demandée ou sur un socket UNIX.

OPTIONS

[https://][hôte]:port
Nom d'hôte et port sur lesquels écouter. hôte peut être une IP IPv4/IPv6 ou un nom d'hôte résolvable. Les noms d'hôte ne sont recherchés qu'au démarrage et ne changent pas pendant la durée de vie du processus. hôte est optionnel ; s'il n'est pas fourni, slurmrestd écoutera sur toutes les interfaces réseau. https:// est optionnel ; s'il n'est pas fourni, slurmrestd utilisera automatiquement le plugin TLS pour chiffrer le trafic lorsque possible. Si https:// est spécifié ; slurmrestd exigera que le plugin TLS configuré chiffre le trafic.
unix:///chemin/vers/socket
Écouter sur un socket UNIX local. Doit avoir la permission de créer un socket dans le système de fichiers.
-a <plugin>[,plugin]...
Liste de plugins d'authentification délimitée par des virgules à charger. Par défaut, tous les plugins d'authentification disponibles seront chargés.
liste
Afficher une liste des plugins possibles à charger.
rest_auth/local
Permet l'authentification via des sockets UNIX lorsque auth/munge est actif.
NOTE : slurmrestd et les processus clients doivent s'exécuter sous le même UID ou les requêtes client seront rejetées.
rest_auth/jwt
Permet l'authentification via des sockets TCP et UNIX lorsque AuthAltTypes=auth/jwt est actif. L'utilisateur doit spécifier les cookies HTTP suivants avec chaque requête :
X-SLURM-USER-NAME:<nom d'utilisateur>
X-SLURM-USER-TOKEN:<JSON Web Token>
NOTE : Les tokens sont généralement générés en appelant "scontrol token".
-d <plugin>[,plugin]...
Liste de plugins data_parser délimitée par des virgules, qui détermineront le format de sortie. Peut inclure des drapeaux optionnels dénotés par le symbole '+'. Par défaut, tous les plugins data_parser disponibles seront chargés sans aucun drapeau optionnel. Voir aussi -s pour les plugins OpenAPI contrôlant le contenu disponible. Chaque connexion peut également conserver de la mémoire pendant toute la durée de vie de la connexion. Avoir trop de connexions en traitement simultanément pourrait utiliser considérablement plus de mémoire. Fonctionnement verbeux. Plusieurs v peuvent être spécifiés, chaque 'v' au-delà du premier augmentant la verbosité, jusqu'à 6 fois (c'est-à-dire -vvvvvv). Afficher les informations de version et quitter.

TLS

slurmrestd prend en charge le chiffrement TLS via l'interface de plugin TLS. Pour une description détaillée de la prise en charge TLS dans Slurm, voir https://slurm.schedmd.com/tls.html.

slurmrestd prend en charge le chiffrement TLS pour les connexions HTTPS entrantes indépendamment de la façon dont TLSType dans slurm.conf(5) est configuré. La configuration de TLSParameters dans slurm.conf(5) est toujours appliquée. Cela permet à la couche RPC de Slurm de rester non chiffrée via TLS tout en permettant à slurmrestd de traiter les requêtes HTTPS via TLS.

slurmrestd inclut la détection automatique des connexions TLS entrantes. Si le plugin TLS est entièrement configuré et se charge avec succès au démarrage, toutes les nouvelles connexions entrantes seront identifiées pour les négociations SSLv3 (selon RFC#6101) et TLSv1.x (selon RFC#8446). Après une correspondance d'empreinte, chaque connexion entrante sera alors chiffrée via le plugin TLS configuré pour la durée de la connexion. La prise en charge de TLS est gérée indépendamment du fait que la connexion soit un [unix(2)] socket(2) ou un pipe(2) (en mode INETD). Les connexions d'écoute créées avec https:// devront être chiffrées via le plugin TLS. Toute connexion entrante à ces écoutes sans chiffrement TLS sera fermée immédiatement sans envoyer de réponse d'erreur au client.

La prise en charge de TLS dans slurmrestd dépend des exigences du plugin TLS. slurmrestd tentera de charger automatiquement le premier plugin TLS disponible (sauf tls/none) au démarrage. Les exigences pour chaque plugin sont listées ci-dessous :

tls/s2n
Les fichiers suivants doivent être présents et lisibles par l'utilisateur appelant (avant que -u <id utilisateur> ne soit appliqué) au démarrage :
restd_cert_file.pem
Certificat public x509 du serveur TLS. Doit être signé par une CA de confiance pour les clients. Le CN (nom commun) du certificat doit correspondre au nom d'hôte. slurmrestd ignore l'hôte dans les requêtes HTTP des clients, mais la plupart des clients TLS exigeront qu'il corresponde.

Remarque : Le fichier du certificat doit être placé dans le répertoire de variables sysconfdir d'installation de autoconf(1), qui peut être remplacé en définissant TLSParameters=restd_cert_file=/chemin/vers/restd_cert_file.pem dans slurm.conf(5).

restd_cert_key_file.pem
Clé privée pour restd_cert_file.pem. Ce fichier ne doit être lisible que par l'utilisateur slurmrestd.

Remarque : Le fichier du certificat doit être placé dans le répertoire de variables sysconfdir d'installation de autoconf(1), qui peut être remplacé en définissant TLSParameters=restd_cert_key_file=/chemin/vers/restd_cert_key.pem dans slurm.conf(5).

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes peuvent être utilisées pour remplacer les paramètres compilés dans slurmrestd.

ABORT_ON_FATAL
Lorsqu'une erreur fatale est détectée, utilise abort() au lieu de exit() pour terminer le processus. Cela permet de capturer des traces sans recompiler Slurm.
SLURM_CONF
L'emplacement du fichier de configuration Slurm.
SLURM_DEBUG_FLAGS
Spécifie les indicateurs de débogage à utiliser par slurmrestd. Voir DebugFlags dans la page de manuel slurm.conf(5) pour une liste complète des indicateurs. La variable d'environnement a la priorité sur le paramètre dans slurm.conf.
SLURM_DEBUG
Définit explicitement le niveau de débogage. Les valeurs valides sont 0-9, ou les mêmes chaînes de caractères que les options de débogage telles que SlurmctldDebug dans slurm.conf(5). Augmenté si -v est passé en argument lors de l'invocation. Ignoré si SLURMRESTD_DEBUG ou SLURMRESTD_DEBUG_STDERR ou SLURMRESTD_DEBUG_SYSLOG sont définis dans l'environnement. Voir SLURMRESTD_DEBUG pour la description des cibles de journalisation.
SLURMRESTD_JSON ou SLURM_JSON
Contrôle la sérialisation JSON :
compact
Sortie JSON aussi compacte que possible.
pretty
Sortie JSON au format lisible pour la rendre plus compréhensible.
SLURM_JWT
Cette variable doit être définie pour utiliser l'authentification par jeton JWT.
SLURMRESTD_AUTH_TYPES
Définit les types d'authentification autorisés. Voir -a
SLURMRESTD_DEBUG
Définit explicitement le niveau de débogage. Les valeurs valides sont 0-9, ou les mêmes valeurs de chaîne que les options de débogage telles que SlurmctldDebug dans slurm.conf(5). Si un TTY de contrôle est détecté, le mode interactif s'activera automatiquement pour fournir des informations de journalisation supplémentaires à stderr. Si un TTY de contrôle n'est pas détecté, les journaux sont envoyés à syslog. Augmenté si -v est passé en argument lors de l'invocation. Ignoré si SLURMRESTD_DEBUG_STDERR ou SLURMRESTD_DEBUG_SYSLOG sont définis dans l'environnement.
SLURMRESTD_DEBUG_STDERR
Définit explicitement le niveau de débogage pour la journalisation vers STDERR. Les valeurs valides sont 0-9, ou les mêmes valeurs de chaîne que les options de débogage telles que SlurmctldDebug dans slurm.conf(5). Augmenté si -v est passé en argument lors de l'invocation.
SLURMRESTD_DEBUG_SYSLOG
Définit explicitement le niveau de débogage pour la journalisation vers syslog. Les valeurs valides sont 0-9, ou les mêmes valeurs de chaîne que les options de débogage telles que SlurmctldDebug dans slurm.conf(5). Augmenté si -v est passé en argument lors de l'invocation.
SLURMRESTD_DATA_PARSER_PLUGINS
Liste séparée par des virgules des plugins data_parser à charger. Voir -d
SLURMRESTD_LISTEN
Liste séparée par des virgules des paires hôte:port ou des sockets Unix sur lesquels écouter.
SLURMRESTD_MAX_CONNECTIONS
Définit le nombre maximum de connexions à traiter à un moment donné. Voir --max-connections
SLURMRESTD_OPENAPI_PLUGINS
Liste séparée par des virgules des plugins OpenAPI à charger. Voir -s
SLURMRESTD_RESPONSE_STATUS_CODES
Liste séparée par des virgules des réponses de méthodes OpenAPI à générer dans la spécification OpenAPI. Par défaut : 200,default
SLURMRESTD_SECURITY
Contrôle les fonctionnalités de sécurité de slurmrestd en utilisant les valeurs suivantes séparées par des virgules :
become_user
Permet à slurmrestd d'être exécuté en tant que root pour devenir l'utilisateur demandeur pour toutes les requêtes. Lorsqu'il est combiné avec rest_auth/local, lorsqu'un utilisateur se connecte via un socket UNIX nommé, slurmrestd effectuera setuid()/setgid() vers cet utilisateur/groupe, puis terminera toutes les requêtes en tant qu'utilisateur donné. Ce mode est uniquement destiné au mode inet, car le changement d'utilisateur est permanent pour la durée du processus. Ce mode est incompatible avec rest_auth/jwt et il est suggéré de démarrer slurmrestd avec les arguments « -a rest_auth/local ».
disable_unshare_files
Désactive le partage des descripteurs de fichiers avec le processus parent.
disable_unshare_sysv
Désactive le partage de l'espace de noms SYSV.
disable_user_check
Désactive la vérification que slurmrestd ne s'exécute pas en tant que root ou SlurmUser, ou avec le groupe principal de root ou SlurmUser. La désactivation de cette vérification permettra à slurmrestd de s'exécuter en tant que root ou SlurmUser, ce qui permettra à quiconque peut communiquer avec ce démon d'exécuter n'importe quoi en tant qu'utilisateur root sur le cluster.
SLURMRESTD_YAML ou SLURM_YAML
Contrôle la sérialisation YAML :
compact
Produit une sortie YAML aussi compacte que possible.
no_tag
Produit une sortie YAML sans les balises de type de données !!.
pretty
Produit une sortie YAML au format joli pour la rendre plus lisible.

SIGNALEMENTS

SIGINT
slurmrestd s'arrêtera proprement.
SIGPIPE
Ce signal est explicitement ignoré.
SIGPROF
Journalise l'état du gestionnaire de connexions lorsque le niveau de débogage est au moins sur info.

NOTES

Les plugins SPANK et clifilter ne sont pas pris en charge dans slurmrestd en raison de leur manque de sécurité au niveau des threads. Les plugins SPANK actifs et les JobSubmitPlugins dans slurmctld sont indépendants de slurmrestd et peuvent être utilisés pour appliquer la politique du site sur les soumissions de jobs.

EXEMPLES

Générer un schéma OpenAPI sans configuration

$ slurmrestd -f /dev/null  --generate-openapi-spec -s slurmdbd,slurmctld -d v0.0.42 > openapi.json

Démarrer slurmrestd avec un socket UNIX en mode écoute :

$ export SLURMRESTD=/var/spool/slurm/restd/rest
$ slurmrestd -s slurmctld,slurmdbd -d v0.0.42 unix:$SLURMRESTD
