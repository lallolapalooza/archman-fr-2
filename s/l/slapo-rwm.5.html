NOM

slapo-rwm - overlay de réécriture/re-mappage pour slapd

SYNOPSIS

/etc/openldap/slapd.conf

DESCRIPTION

L'overlay rwm pour slapd(8) effectue des réécritures de base de DN/données et des mappages d'objectClass/attributeType. Son utilisation est principalement destinée à fournir des vues virtuelles de données existantes, soit à distance, en conjonction avec le backend proxy décrit dans slapd-ldap(5), soit localement, en conjonction avec le backend relay décrit dans slapd-relay(5).

Cet overlay est expérimental.

MAPPAGE

Une caractéristique importante de l'overlay rwm est la capacité de mapper les objectClasses et les attributeTypes de l'ensemble local (ou d'un sous-ensemble) vers un ensemble étranger, et vice versa. Ceci est réalisé au moyen de la directive rwm-map.

rwm-map {attribut | objectclass} [<nom local> | *] {<nom étranger> | *}
Mappe les attributeTypes et objectClasses du serveur étranger vers des valeurs différentes sur le slapd local. La raison est que certains attributs pourraient ne pas faire partie du schéma du slapd local, certains noms d'attributs pourraient être différents mais servir le même objectif, etc. Si le nom local ou étranger est `*', le nom est préservé. Si le nom local est omis, le nom étranger est supprimé. Les noms non mappés sont préservés si les noms local et étranger sont `*', et supprimés si le nom local est omis et le nom étranger est `*'.

Les objectClasses et attributeTypes locaux doivent être définis dans le schéma local ; les étrangers ne le doivent pas nécessairement, mais il est conseillé aux utilisateurs de définir explicitement les attributeTypes distants et les objectClasses qu'ils ont l'intention de mapper. Tout bien considéré, lors du remappage d'un serveur distant via back-ldap (slapd-ldap(5)) ou back-meta (slapd-meta(5)), leur définition peut être facilement obtenue en interrogeant le subschemaSubentry du serveur distant ; le problème ne devrait pas se poser lors du remappage d'une base de données locale. Notez cependant que la décision de réécrire ou non les attributeTypes avec une syntaxe distinguishedName, nécessite la connaissance de la syntaxe de l'attributeType. Voir la section RÉÉCRITURE pour plus de détails.

Notez que lors du mappage d'attributs à valeur DN du local vers le distant, le DN est d'abord réécrit, puis l'attributType est mappé ; lors du mappage du distant vers le local, l'attributType est d'abord mappé, puis le DN est réécrit. En tant que tel, il est important que l'attributType local soit correctement défini comme utilisant la syntaxe distinguishedName. Notez également que certaines syntaxes liées au DN (c'est-à-dire les types composites avec une partie à valeur DN), comme nameAndOptionalUID, dont les valeurs ne sont actuellement pas réécrites.

Si le type étranger d'un mappage d'attribut n'est pas défini sur le serveur local, il peut être souhaitable que les valeurs des attributs soient normalisées après le processus de mappage. Ne pas normaliser les valeurs peut entraîner des résultats incorrects lorsque l'overlay rwm est utilisé conjointement avec, par exemple, l'overlay pcache. Cette normalisation peut être activée au moyen de la directive rwm-normalize-mapped-attrs.

rwm-normalize-mapped-attrs {oui|non}
Réglez ceci sur "oui", si l'overlay rwm doit essayer de normaliser les valeurs des attributs qui sont mappés à partir d'un type d'attribut inconnu du serveur local. La valeur par défaut de ce paramètre est "non".
rwm-drop-unrequested-attrs {oui|non}
Réglez ceci sur "oui", si l'overlay rwm doit supprimer les attributs qui ne sont pas explicitement demandés par une opération de recherche. Lorsque ceci est défini sur "non", l'overlay rwm laissera tous les attributs en place, afin que les modules ultérieurs puissent les manipuler davantage. Dans tous les cas, les attributs non sollicités seront omis des résultats de recherche par le frontend, lorsque le paquet de réponse de l'entrée de recherche sera encodé. La valeur par défaut de ce paramètre est "oui".

MASSAGE DE SUFFIXE

Une fonctionnalité de base de l'overlay rwm est la capacité d'effectuer un massage de suffixe entre un contexte de nommage virtuel et réel au moyen de la directive rwm-suffixmassage. Ceci, en conjonction avec les backends proxy, slapd-ldap(5) et slapd-meta(5), ou avec le backend relay, slapd-relay(5), permet de créer des vues virtuelles de bases de données. Une caractéristique distinctive de cet overlay est que, lorsqu'il est instancié avant toute base de données, il peut modifier le DN des requêtes avant la sélection de la base de données. Pour cette raison, les règles qui réécrivent le DN vide ("") ou le DN subschemaSubentry (généralement "cn=subschema"), empêcheraient les clients de lire le DSE racine ou le schéma du DSA.

rwm-suffixmassage [<contexte de nommage virtuel>] <contexte de nommage réel>
Raccourci pour implémenter la réécriture des contextes de nommage ; la partie finale du DN est réécrite du contexte de nommage virtuel vers le réel dans les contextes de réécriture bindDN, searchDN, searchFilterAttrDN, compareDN, compareAttrDN, addDN, addAttrDN, modifyDN, modifyAttrDN, modrDN, newSuperiorDN, deleteDN, exopPasswdDN, et du contexte réel vers le virtuel dans les contextes de réécriture searchEntryDN, searchAttrDN et matchedDN. Par défaut, aucune réécriture n'a lieu pour le searchFilter et pour les contextes de réécriture referralAttrDN et referralDN. Si aucun <contexte de nommage virtuel> n'est donné, le premier suffix de la base de données est utilisé ; cela nécessite que la directive rwm-suffixmassage soit définie après la directive suffix de la base de données. La directive rwm-suffixmassage active automatiquement le rwm-rewriteEngine à ON.

Voir la section RÉÉCRITURE pour plus de détails.

RÉÉCRITURE

Une chaîne est réécrite selon un ensemble de règles, appelées un `contexte de réécriture'. Les règles sont basées sur des expressions régulières POSIX (''étendues'') avec mise en correspondance de sous-chaînes ; la substitution de variables de base et la résolution de correspondance de sous-chaînes sont autorisées par des mécanismes spécifiques détaillés ci-après. Le comportement de la mise en correspondance/substitution de motifs peut être modifié par un ensemble de drapeaux.

<contexte de réécriture> ::= <règle de réécriture> [...]
<règle de réécriture> ::= <motif> <motif de substitution> [<drapeaux>]

Le concept sous-jacent est de construire un module de réécriture léger pour le serveur slapd (initialement dédié au backend LDAP) :

Passages

Une chaîne entrante est mise en correspondance avec un ensemble de règles de réécriture. Les règles sont composées d'un motif de correspondance regex, d'un motif de substitution et d'un ensemble d'actions, décrites par un ensemble de drapeaux optionnels. En cas de correspondance, la réécriture de la chaîne est effectuée selon le motif de substitution qui permet de faire référence aux sous-chaînes mises en correspondance dans la chaîne entrante. Les actions, le cas échéant, sont finalement effectuées. Chaque règle est exécutée récursivement, sauf indication contraire de drapeaux d'action spécifiques ; voir "Drapeaux d'action" pour les détails. Une limite par défaut sur le niveau de récursion est définie, et peut être modifiée par la directive rwm-rewriteMaxPasses, comme détaillé dans la section "Syntaxe de configuration supplémentaire". Le motif de substitution permet la résolution de carte des sous-chaînes. Une carte est un objet générique qui mappe un motif de substitution à une valeur. Les drapeaux sont divisés en "Drapeaux de mise en correspondance de motifs" et "Drapeaux d'action" ; les premiers modifient le comportement du motif de correspondance regex, tandis que les seconds modifient les actions entreprises après la substitution.

Passages

Une chaîne entrante est mise en correspondance avec un ensemble de règles de réécriture. Les règles sont composées d'un motif de correspondance regex, d'un motif de substitution et d'un ensemble d'actions, décrites par un ensemble de drapeaux optionnels. En cas de correspondance, la réécriture de la chaîne est effectuée selon le motif de substitution qui permet de faire référence aux sous-chaînes mises en correspondance dans la chaîne entrante. Chaque règle est exécutée récursivement, sauf indication contraire de drapeaux d'action spécifiques ; voir "Drapeaux d'action" pour les détails. Les drapeaux sont divisés en "Drapeaux de mise en correspondance de motifs" et "Drapeaux d'action" ; les premiers modifient le comportement du motif de correspondance regex, tandis que les seconds modifient les actions entreprises après la substitution.

Drapeaux d'action

`:'
appliquer la règle une seule fois (par défaut, récursif)
`@'
arrêter l'application des règles en cas de correspondance ; la règle actuelle est toujours appliquée récursivement ; combinez avec `:' pour appliquer la règle actuelle une seule fois, puis arrêter.
`#'
arrêter l'opération en cours si la règle correspond, et générer une erreur « unwilling to perform ».
`G{n}'
sauter n règles en arrière et en avant (attention aux boucles !). Notez que `G{1}' est implicite dans chaque règle.
`I'
ignore les erreurs dans la règle ; cela signifie qu'en cas d'erreur, par exemple générée par une carte, l'erreur est traitée comme une non-correspondance. Le message « unwilling to perform » n'est pas remplacé.
`U{n}'
utilise n comme code de retour si la règle correspond ; le drapeau ne modifie pas le comportement récursif de la règle, donc, pour qu'elle ne soit exécutée qu'une seule fois, elle doit être utilisée en combinaison avec `:', par exemple, `:U{32}' retourne la valeur `32' (indiquant noSuchObject) après une seule exécution de la règle, si le modèle correspond. Par conséquent, son comportement est équivalent à `@', avec le code de retour défini sur n ; ou, en d'autres termes, `@' est équivalent à `U{0}'. Des erreurs positives sont autorisées, indiquant les codes d'erreur LDAP liés, tels que spécifiés dans RFC4511.

L'ordre des drapeaux peut être significatif. Par exemple : `IG{2}' signifie ignorer les erreurs et sauter deux lignes en avant en cas de correspondance et en cas d'erreur, tandis que `G{2}I' signifie ignorer les erreurs, mais sauter deux lignes en avant seulement en cas de correspondance.

Plus de drapeaux (principalement des drapeaux d'action) seront ajoutés au besoin.

Correspondance des modèles

Voir regex(7) et/ou re_format(7).

Syntaxe des modèles de substitution

Tout ce qui commence par `$' nécessite une substitution ;

la seule exception évidente est `$$', qui est transformé en un seul `$' ;

la substitution de base est `$<d>', où `<d>' est un chiffre ; 0 signifie toute la chaîne, tandis que 1-9 est une sous-correspondance, comme expliqué dans regex(7) et/ou re_format(7).

un `$' suivi d'un `{' appelle une substitution avancée. Le modèle est :

`$' `{' [ <opérateur> ] <nom> `(' <substitution> `)' `}'

où <nom> doit être un nom valide pour la carte, c'est-à-dire

<nom> ::= [a-z][a-z0-9]* (insensible à la casse)
<opérateur> ::= `>' `|' `&' `&&' `*' `**' `$'

et <substitution> doit être un modèle de substitution valide, sans limite de niveau d'imbrication.

Les opérateurs sont :

>
invocation de sous-contexte ; <nom> doit être un nom de contexte de réécriture légal et déjà défini.
|
invocation de commande externe ; <nom> doit faire référence à un nom de commande légal et déjà défini (PAS ENCORE IMPLÉMENTÉ).
&
affectation de variable ; <nom> définit une variable dans la structure de l'opération en cours qui peut être déréférencée plus tard ; l'opérateur & affecte une variable dans la portée du contexte de réécriture ; l'opérateur && affecte une variable qui s'étend sur toute la session, par exemple sa valeur peut être déréférencée plus tard par d'autres contextes de réécriture.
*
déréférencement de variable ; <nom> doit faire référence à une variable définie et affectée pour l'opération en cours ; l'opérateur * déréférence une variable qui s'étend sur le contexte de réécriture ; l'opérateur ** déréférence une variable qui s'étend sur toute la session, par exemple la valeur est transmise à travers les contextes de réécriture.
$
déréférencement de paramètre ; <nom> doit faire référence à un paramètre existant ; l'idée est de rendre certains paramètres d'exécution définis par le système disponibles pour le moteur de réécriture, tels que le nom de l'hôte client, le DN de connexion le cas échéant, des paramètres constants initialisés au moment de la configuration, etc. ; aucun paramètre n'est actuellement défini par back-ldap ou back-meta, mais des paramètres constants peuvent être définis dans le fichier de configuration en utilisant la directive rewriteParam.

L'échappement de substitution a été délégué au symbole `$', qui est utilisé à la place de `\' dans les modèles de substitution de chaînes car `\' est déjà échappé par les routines d'analyse de bas niveau de slapd ; par conséquent, l'échappement regex nécessite deux symboles `\', par exemple `.*\.foo\.bar' doit être écrit comme `.*\\.foo\\.bar'.

Contexte de réécriture

Un contexte de réécriture est un ensemble de règles qui sont appliquées séquentiellement. L'idée de base est qu'une application initialise un moteur de réécriture (pensez à mod_rewrite d'Apache...) avec un ensemble de contextes de réécriture ; lorsqu'une réécriture de chaîne est requise, on invoque le contexte de réécriture approprié avec la chaîne d'entrée et on obtient la chaîne nouvellement réécrite si aucune erreur ne survient.

Chaque opération de serveur de base est associée à un contexte de réécriture ; ils sont divisés en deux groupes principaux : réécriture client -> serveur et serveur -> client.

Client -> serveur :

(défaut)            si défini et aucun contexte spécifique
                     n'est disponible
bindDN               bind
searchDN             search
searchFilter         search
searchFilterAttrDN   search
compareDN            compare
compareAttrDN        compare AVA
addDN                add
addAttrDN            add AVA (partie DN de « ref » exclue)
modifyDN             modify
modifyAttrDN         modify AVA (partie DN de « ref » exclue)
referralAttrDN       partie DN d'add/modify des referrals
                     (par défaut aucun)
renameDN             modrdn (le DN ancien)
newSuperiorDN        modrdn (le DN parent nouveau, le cas échéant)
newRDN               modrdn (le DN relatif nouveau)
deleteDN             delete
exopPasswdDN         opération étendue de modification de mot de passe DN

Serveur -> client :

searchEntryDN        search (uniquement si défini ; aucun défaut ;
                     agit sur le DN des entrées de recherche)
searchAttrDN         search AVA (uniquement si défini ; par défaut
                     à searchEntryDN ; agit sur les attributs syntaxe DN des résultats de recherche)
matchedDN            toutes les ops (uniquement si applicable ; par défaut
                     à searchEntryDN)
referralDN           toutes les ops (uniquement si applicable ; par défaut
                     à aucun)

Syntaxe de configuration de base

Toutes les directives de réécriture/re-mappage commencent par le préfixe rwm-

rwm-rewriteEngine { on | off }
Si `on', la réécriture demandée est effectuée ; si `off', aucune réécriture n'a lieu (un moyen simple d'arrêter la réécriture sans trop modifier le fichier de configuration).
rwm-rewriteContext <nom du contexte> [ alias <nom du contexte alias> ]
<Nom du contexte> est le nom qui identifie le contexte, c'est-à-dire le nom utilisé par l'application pour faire référence à l'ensemble des règles qu'il contient. Il est également utilisé pour référencer des sous-contextes dans la réécriture de chaînes. Un contexte peut en aliaser un autre. Dans ce cas, le contexte alias ne contient aucune règle, et toute référence à celui-ci entraînera l'accès au contexte aliasé.
rwm-rewriteRule <modèle de correspondance regex> <modèle de substitution> [ <drapeaux> ]
Détermine comment une chaîne peut être réécrite si un modèle est trouvé. Des exemples sont rapportés ci-dessous.

Syntaxe de configuration supplémentaire

rwm-rewriteMap <type de carte> <nom de carte> [ <attributs de carte> ]
Permet de définir une carte qui transforme la réécriture de sous-chaînes en autre chose. La carte est référencée à l'intérieur du modèle de substitution d'une règle.
rwm-rewriteParam <nom du paramètre> <valeur du paramètre>
Définit une valeur avec une portée globale, qui peut être déréférencée par la commande `${$nomParametre}'.
rwm-rewriteMaxPasses <nombre de passes> [<nombre de passes par règle>]
Définit le nombre maximum de passes de réécriture totales qui peuvent être effectuées dans une seule opération de réécriture (pour éviter les boucles). Une valeur par défaut sûre est définie à 100 ; notez que l'atteinte de cette limite est toujours traitée comme un succès ; l'invocation récursive des règles est simplement interrompue. La limite s'applique à l'ensemble de l'opération de réécriture, et non à une seule règle ; une limite facultative par règle peut être définie. Cette limite est remplacée en définissant des limites spécifiques par règle avec le drapeau `M{n}'.

CARTES

Actuellement, peu de cartes sont intégrées, mais des types de cartes supplémentaires peuvent être enregistrés à l'exécution.

Les cartes prises en charge sont :

LDAP <URI> [bindwhen=<quand>] [version=<version>] [binddn=<DN>] [credentials=<identifiants>]
La carte LDAP développe une valeur en effectuant une recherche LDAP simple. Sa configuration est basée sur une URI obligatoire, dont la partie attrs doit contenir exactement un attribut (utiliser entryDN pour récupérer le DN d'une entrée). Si un attribut multivalué est utilisé, seule la première valeur est prise en compte.

Le paramètre bindwhen détermine quand la connexion est établie. Il peut prendre les valeurs now, later et everytime, indiquant respectivement que la connexion doit être créée au démarrage, lorsque nécessaire, ou à chaque utilisation. Dans les deux premiers cas, la connexion est mise en cache, tandis que dans le dernier, une nouvelle connexion fraîche est utilisée à chaque fois. C'est le comportement par défaut.

Les paramètres binddn et credentials représentent le DN et le mot de passe utilisés pour effectuer un bind simple authentifié avant d'effectuer l'opération de recherche ; s'ils ne sont pas fournis, une connexion anonyme est utilisée.

Le paramètre version peut être 2 ou 3 pour indiquer la version du protocole qui doit être utilisée. La valeur par défaut est 3.

MAPPING

The map directive is used to map attribute types and object classes between servers. It is used to translate between different schemas when using proxying or replication. For example, to map the object class `groupOfNames' to `groupOfUniqueNames' and the attribute type `member' to `uniqueMember', you could use the following directives:

map objectclass groupOfNames groupOfUniqueNames
map attribute member uniqueMember

The map directive can also be used to selectively export or import attributes. For example, to export only the `cn', `sn', `manager', and `description' attributes from a server, you could use:

map attribute cn *
map attribute sn *
map attribute manager *
map attribute description *
map attribute *

This example maps `cn', `sn', `manager', and `description' to themselves, and all other attributes are effectively removed from the object before it is sent to the client. This is a basic example to illustrate the concept.

SUFFIX MASSAGING

The suffixMassage directive is used to rewrite the DNs in entries returned by a backend database. This is useful when a backend database is configured with a different suffix than the one used by the client. For example, if a backend database is configured with the suffix `dc=internal,dc=example,dc=com' but the client uses the suffix `dc=example,dc=com', the suffixMassage directive can be used to rewrite the DNs in the entries returned by the backend database to match the client's suffix.

The suffixMassage directive takes two arguments: the old suffix and the new suffix. For example:

suffixMassage dc=internal,dc=example,dc=com dc=example,dc=com

This directive would rewrite any DN that contains the suffix `dc=internal,dc=example,dc=com' to use the suffix `dc=example,dc=com' instead.

REWRITING

The rwm module provides a general-purpose rewrite and remap engine. It can be used to modify requests and responses on the fly. The rewrite engine operates on contexts, which define the type of operation being performed (e.g., search, bind, modify). Within each context, rules are applied to transform the data.

Passes

The rewrite engine supports multiple passes over the data. Each pass can perform a different set of transformations. This allows for complex rewriting scenarios.

Pattern Matching Flags

The following flags can be used to modify the behavior of pattern matching:

I
Ignore case.
M
Multi-line mode: `^' and `$' match the beginning and end of each line, respectively.
S
Single-line mode: `.' matches any character, including newline.

Action Flags

The following flags can be used to modify the behavior of rewrite actions:

@
Perform rewriting via the specified map.
:
Perform rewriting using the specified rule.
I
Ignore errors during rewriting. If an error occurs, the original data is used.
i
Ignore errors during rewriting. If an error occurs, the rewrite action is aborted and the original data is used.

Pattern Matching

The rewrite engine uses regular expressions for pattern matching. The syntax is compatible with POSIX regular expressions.

Substitution Pattern Syntax

The substitution pattern supports the following special sequences:

$0
The entire matched string.
$1, $2, ...
The captured sub-expressions from the pattern.
${map(arg)}
Call a rewrite map named `map' with argument `arg'.
${&map(arg)}
Call a rewrite map named `map' with argument `arg', and perform rewriting based on the map's result.
${>map(arg)}
Call a rewrite map named `map' with argument `arg', and use its result as part of the substitution string.

Rewrite Context

A rewrite context defines a set of rules that are applied to a specific type of operation. The following contexts are supported:

default
The default context, used for general rewriting.
searchFilter
Context for rewriting search filters.
searchEntryDN
Context for rewriting DNs in search results.
searchAttrDN
Context for rewriting DNs in attribute values of search results.
bindDN
Context for rewriting bind DNs.
matchedDN
Context for rewriting the matched DN.
referralDN
Context for rewriting referral DNs.
referralAttrDN
Context for rewriting DNs in attribute values of referrals.

Basic Configuration Syntax

The following directives are used to configure the rewrite engine:

rwm-rewriteEngine [on|off]
Enable or disable the rewrite engine.
rwm-rewriteContext context-name [alias other-context]
Define a rewrite context or make a context an alias of another.
rwm-rewriteRule pattern substitution [flags]
Define a rewrite rule within the current context.

Additional Configuration Syntax

The following directives are used to define rewrite maps:

rwm-rewriteMap map-name map-type [arguments]
Define a rewrite map.

Supported map types include:

ldap
A map that uses LDAP search to resolve values. The URI must begin with ldap:/// and must not specify a host. The attrs portion must contain exactly one attribute. If a multi-valued attribute is used, only the first value is considered.
escape
A map that performs character escaping and unescaping for DNs and filters. It supports the following operations:
escape2dn
Escapes a string for safe inclusion in a DN.
escape2filter
Escapes a string for safe inclusion in a filter.
unescapedn
Unescapes a string that was previously escaped for a DN.
unescapefilter
Unescapes a string that was previously escaped for a filter.
It is recommended that each escape map ends with an escape operation to safely handle arbitrary strings.

REWRITE CONFIGURATION EXAMPLES

# set to `off' to disable rewriting
rwm-rewriteEngine on
# the rules the "suffixmassage" directive implies
rwm-rewriteEngine on
# all dataflow from client to server referring to DNs
rwm-rewriteContext default
rwm-rewriteRule "(.+,)?<virtualnamingcontext>$" "$1<realnamingcontext>" ":"
# empty filter rule
rwm-rewriteContext searchFilter
# all dataflow from server to client
rwm-rewriteContext searchEntryDN
rwm-rewriteRule "(.+,)?<realnamingcontext>$" "$1<virtualnamingcontext>" ":"
rwm-rewriteContext searchAttrDN alias searchEntryDN
rwm-rewriteContext matchedDN alias searchEntryDN
# misc empty rules
rwm-rewriteContext referralAttrDN
rwm-rewriteContext referralDN
# Everything defined here goes into the `default' context.
# This rule changes the naming context of anything sent
# to `dc=home,dc=net' to `dc=OpenLDAP, dc=org'
rwm-rewriteRule "(.+,)?dc=home,[ ]?dc=net$"
            "$1dc=OpenLDAP, dc=org"  ":"
# since a pretty/normalized DN does not include spaces
# after rdn separators, e.g. `,', this rule suffices:
rwm-rewriteRule "(.+,)?dc=home,dc=net$"
            "$1dc=OpenLDAP,dc=org"  ":"
# Start a new context (ends input of the previous one).
# This rule adds blanks between DN parts if not present.
rwm-rewriteContext  addBlanks
rwm-rewriteRule     "(.*),([^ ].*)" "$1, $2"
# This one eats blanks
rwm-rewriteContext  eatBlanks
rwm-rewriteRule     "(.*), (.*)" "$1,$2"
# Here control goes back to the default rewrite
# context; rules are appended to the existing ones.
# anything that gets here is piped into rule `addBlanks'
rwm-rewriteContext  default
rwm-rewriteRule     ".*" "${>addBlanks($0)}" ":"
# Rewrite the search base according to `default' rules.
rwm-rewriteContext  searchDN alias default
# Search results with OpenLDAP DN are rewritten back with
# `dc=home,dc=net' naming context, with spaces eaten.
rwm-rewriteContext  searchEntryDN
rwm-rewriteRule     "(.*[^ ],)?[ ]?dc=OpenLDAP,[ ]?dc=org$"
                "${>eatBlanks($1)}dc=home,dc=net"    ":"
# Transform a DN value such that it can be used in a filter
rwm-rewriteMap escape dn2filter unescapedn escape2filter
# Bind with email instead of full DN: we first need
# an ldap map that turns attributes into a DN (the
# argument used when invoking the map is appended to 
# the URI and acts as the filter portion)
rwm-rewriteMap ldap attr2dn "ldap://host/dc=my,dc=org?dn?sub"
# Then we need to detect DN made up of a single email,
# e.g. `mail=someone@example.com'; note that the rule
# in case of match stops rewriting; in case of error,
# it is ignored.  In case we are mapping virtual
# to real naming contexts, we also need to rewrite
# regular DNs, because the definition of a bindDN
# rewrite context overrides the default definition.
#
# While actual email addresses tend not to contain filter
# special characters, the provided Bind DN has no such
# restrictions.
rwm-rewriteContext bindDN
rwm-rewriteRule "^(mail=)([^,]+@[^,]+)$"
                "${attr2dn($1${dn2filter($2)})}" ":@I"
# This is a rather sophisticated example. It massages a
# search filter in case who performs the search has
# administrative privileges.  First we need to keep
# track of the bind DN of the incoming request, which is
# stored in a variable called `binddn' with session scope,
# and left in place to allow regular binding:
rwm-rewriteContext  bindDN
rwm-rewriteRule     ".+" "${&&binddn($0)}$0" ":"
# A search filter containing `uid=' is rewritten only
# if an appropriate DN is bound.
# To do this, in the first rule the bound DN is
# dereferenced, while the filter is decomposed in a
# prefix, in the value of the `uid=<arg>' AVA, and 
# in a suffix. A tag `<>' is appended to the DN. 
# If the DN refers to an entry in the `ou=admin' subtree, 
# the filter is rewritten OR-ing the `uid=<arg>' with
# `cn=<arg>'; otherwise it is left as is. This could be
# useful, for instance, to allow apache's auth_ldap-1.4
# module to authenticate users with both `uid' and
# `cn', but only if the request comes from a possible
# `cn=Web auth,ou=admin,dc=home,dc=net' user.
rwm-rewriteContext searchFilter
rwm-rewriteRule "(.*\\()uid=([a-z0-9_]+)(\\).*)"
  "${**binddn}<>${&prefix($1)}${&arg($2)}${&suffix($3)}"
  ":I"
rwm-rewriteRule "^[^,]+,ou=admin,dc=home,dc=net$"
  "${*prefix}|(uid=${*arg})(cn=${*arg})${*suffix}" ":@I"
rwm-rewriteRule ".*<>$" "${*prefix}uid=${*arg}${*suffix}" ":"
# This example shows how to strip unwanted DN-valued
# attribute values from a search result; the first rule
# matches DN values below "ou=People,dc=example,dc=com";
# in case of match the rewriting exits successfully.
# The second rule matches everything else and causes
# the value to be rejected.
rwm-rewriteContext searchEntryDN
rwm-rewriteRule ".+,ou=People,dc=example,dc=com$" "$0" ":@"
rwm-rewriteRule ".*" "" "#"
