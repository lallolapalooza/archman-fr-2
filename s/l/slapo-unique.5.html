NOM

slapo-unique - Superposition d'unicité d'attribut pour slapd

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

La superposition d'unicité d'attribut peut être utilisée avec une base de données backend telle que slapd-mdb(5) pour imposer l'unicité de certains ou de tous les attributs dans une portée donnée. Cette sous-arborescence concerne par défaut tous les objets de la sous-arborescence de la base de données pour laquelle la superposition d'unicité est configurée.

L'unicité est imposée en recherchant dans la sous-arborescence pour s'assurer que les valeurs de tous les attributs présentés avec une opération add, modify ou modrdn sont uniques dans la portée. Par exemple, si l'unicité était imposée pour l'attribut uid, la sous-arborescence serait recherchée pour tout autre enregistrement ayant également un attribut uid contenant la même valeur. Si des correspondances sont trouvées, la demande est rejetée.

La recherche est effectuée en utilisant le rootdn de la base de données, pour éviter les problèmes liés aux ACL qui empêcheraient la superposition de voir toutes les données pertinentes. Par conséquent, la base de données doit avoir un rootdn configuré.

CONFIGURATION

Ces options slapd.conf s'appliquent à la superposition d'unicité d'attribut. Elles doivent apparaître après la directive overlay.

unique_uri <[strict ][ignore ][serialize ]URI[[ URI...]...]>
Configure la base, les attributs, la portée et le filtre pour la vérification d'unicité. Plusieurs URI peuvent être spécifiées au sein d'un domaine, permettant des sélections complexes d'objets. Plusieurs instructions unique_uri ou valeurs d'attribut olcUniqueURI créeront des domaines indépendants, chacun avec ses propres listes d'URI et ses paramètres d'ignorance/stricte indépendants.

Les mots-clés strict, ignore et serialize doivent être entourés de guillemets (") avec l'URI lors de l'utilisation de configurations obsolètes de slapd.conf.

La syntaxe URI LDAP est un sous-ensemble de RFC-4516 et prend la forme :

ldap:///[dn de base]?[attributs...]?[portée]?[filtre]

Le dn de base est celui de la base de données backend par défaut. Les dn de base spécifiés doivent se trouver dans la sous-arborescence de la base de données backend.

Si aucun attribut n'est spécifié, l'URI s'applique à tous les attributs non opérationnels.

Le composant portée est effectivement obligatoire, car les URI LDAP utilisent par défaut la portée base, ce qui n'est pas valide pour l'unicité, car les groupes d'un seul objet sont toujours uniques. Les portées sub (pour sous-arborescence) et one (pour un seul niveau) sont valides.

Le composant filtre fait que le domaine n'applique des contraintes d'unicité qu'aux objets correspondants. Par exemple : ldap:///?cn?sub?(sn=e*) imposerait des attributs cn uniques pour tous les objets de la sous-arborescence de la base de données backend dont le sn commence par un 'e'.

Il est possible de déclarer l'unicité sur tous les attributs non opérationnels sauf ceux listés en préfixant le mot-clé ignore. Si non configuré, tous les attributs non opérationnels (par exemple, système) doivent être uniques. Notez que la liste des attributs d'une URI ignore devrait généralement contenir les attributs objectClass, dc, ou et o, car ceux-ci ne seront généralement pas uniques, ni des attributs opérationnels.

Il est possible de définir une vérification stricte pour le domaine d'unicité en préfixant le mot-clé strict. Par défaut, l'unicité n'est pas appliquée aux valeurs nulles. L'activation du mode strict étend le concept d'unicité pour inclure les valeurs nulles, de sorte qu'un seul attribut au sein d'une sous-arborescence sera autorisé à avoir une valeur nulle. La stricte s'applique à toutes les URI au sein d'un domaine d'unicité, mais certains domaines peuvent être stricts tandis que d'autres ne le sont pas.

Il est possible d'imposer une sérialisation stricte des modifications en préfixant le mot-clé serialize. Par défaut, aucune sérialisation n'est effectuée, de sorte que plusieurs modifications se produisant presque simultanément peuvent afficher des résultats d'unicité incomplets. L'utilisation de serialize forcera les opérations d'écriture individuelles à s'achever complètement avant d'en autoriser d'autres, afin de garantir que les vérifications d'unicité de chaque opération soient cohérentes.

Il n'est pas possible de définir simultanément des URI et d'anciennes paramètres de configuration slapo-unique. En général, les anciennes options de configuration contrôlent des parties d'un seul domaine de sous-arborescence sans filtre.

unique_base <basedn>
Ce paramètre de configuration obsolète doit être converti en composant dn de base du paramètre de style unique_uri ci-dessus.
unique_ignore <attribut...>
Ce paramètre de configuration obsolète doit être converti en paramètre unique_uri avec le mot-clé ignore tel que décrit ci-dessus.
unique_attributes <attribut...>
Ce paramètre de configuration obsolète doit être converti en paramètre unique_uri, tel que décrit ci-dessus.
unique_strict <attribut...>
Ce paramètre de configuration obsolète doit être converti en mot-clé strict précédant un paramètre unique_uri, tel que décrit ci-dessus.

ATTENTION

unique_uri ne peut pas être utilisé avec l'ancien style de configuration, et vice versa. unique_uri peut implémenter tout ce que l'ancien système peut faire, cependant.

Les attributs typiques pour les URI ignore ldap:///... ne sont intentionnellement pas codés en dur dans la superposition pour permettre une flexibilité maximale afin de répondre aux exigences spécifiques du site.

La réplication et les opérations avec le contrôle relax sont autorisées à contourner cette application. Il est donc important que tous les serveurs acceptant les écritures aient cette superposition configurée afin de maintenir l'unicité dans un DIT répliqué.

FICHIERS

/etc/openldap/slapd.conf
fichier de configuration slapd par défaut

VOIR AUSSI

slapd.conf(5), slapd-config(5).
