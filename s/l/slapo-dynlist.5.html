SLAPO-DYNLIST(5) Manuel des formats de fichiers SLAPO-DYNLIST(5)

NOM

slapo-dynlist - Superposition de listes dynamiques pour slapd

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

La superposition dynlist de slapd(8) permet l'expansion de listes et de groupes dynamiques. Chaque fois qu'une entrée ayant un objectClass spécifique (défini dans la configuration de la superposition) est retournée, les occurrences de type URI LDAP d'un attribut spécifique (également défini dans la configuration de la superposition) sont développées en entrées correspondantes.

Pour une liste dynamique, les valeurs des attributs listés dans l'URI sont ajoutées à partir des entrées correspondantes à l'entrée d'origine. Aucune récursion n'est autorisée, afin d'éviter des boucles infinies potentielles. L'entrée résultante doit être conforme au modèle de données LDAP, de sorte que des contraintes sont appliquées. Par exemple, si un attribut SINGLE-VALUE est listé, seule la première valeur trouvée lors de l'expansion de la liste apparaît dans l'entrée finale.

Pour un groupe dynamique, les DN des entrées correspondantes sont ajoutés à un attribut membre dans l'entrée d'origine.

Toute activité dynamique est désactivée lorsque la commande manageDSAit (RFC 3296) est utilisée. Dans ce cas, le contenu de l'entrée d'origine est retourné ; à savoir, les URL sont retournées au lieu d'être développées.

CONFIGURATION

Les directives de configuration spécifiques à la superposition dynlist doivent être préfixées par dynlist-, afin d'éviter d'éventuels conflits avec des directives spécifiques à la base de données sous-jacente ou à d'autres superpositions empilées.

overlay dynlist
Cette directive ajoute la superposition dynlist à la base de données actuelle, ou au frontal, si elle est utilisée avant toute instantiation de base de données ; voir slapd.conf(5) pour plus de détails.

Cette option de configuration slapd.conf est définie pour la superposition dynlist. Elle peut apparaître plusieurs fois et doit figurer après la directive overlay.

dynlist-attrset <group-oc> [<URI>] <URL-ad> [options]

La valeur group-oc est le nom de l'objectClass qui déclenche l'expansion dynamique des données.

L'option URI restreint l'expansion uniquement aux entrées correspondant au DN, à la portée et au filtre de l'URI.

La valeur URL-ad est le nom de la description d'attribut qui contient l'URI développée par la superposition ; s'il n'y en a pas, aucune expansion ne se produit. Si l'intersection des attributs demandés par l'opération de recherche (ou l'attribut asserté pour les comparaisons) et les attributs listés dans l'URI est vide, aucune expansion ne se produit pour cette URI spécifique. Elle doit être un sous-type de labeledURI.

Les options restantes dépendent de la configuration d'une liste dynamique ou d'un groupe dynamique.

Pour une liste dynamique, les options autorisées sont de la forme

[<mapped-ad>:<list-ad> ...]

Le mapped-ad peut être utilisé pour remapper les attributs obtenus par expansion. Le list-ad doit être l'un des attributs retournés dans l'expansion des URI dans l'attribut URL-ad de l'entrée dynamique. Plusieurs déclarations de mapping peuvent être utilisées. Notez que pour que les listes dynamiques soient utilisables dans un filtre de recherche, les attributs dynamiques à filtrer doivent être explicitement mappés. Ils peuvent être mappés à eux-mêmes si aucune transformation n'est requise.

Pour un groupe dynamique, les options autorisées sont

<member-ad>[+<memberOf-ad>[@<static-oc>[*]]]

Le member-ad est requis ; cet attribut listera le DN des entrées résultant de la recherche interne. Dans ce cas, la portion attrs des URI dans l'attribut URL-ad doit être absente, et les DN de toutes les entrées résultant de l'expansion des URI sont listés comme valeurs de cet attribut. Les comparaisons qui affirment la valeur de l'attribut member-ad des entrées avec l'objectClass group-oc s'appliquent comme si le DN des entrées résultant de l'expansion de l'URI était présent dans l'entrée group-oc comme valeurs de l'attribut member-ad. Si l'attribut optionnel memberOf-ad est également spécifié, il sera alors peuplé avec les DN des groupes dynamiques dont une entrée est membre. Si l'objectClass optionnel static-oc est également spécifié, alors l'attribut memberOf sera également peuplé avec les DN des groupes statiques dont une entrée est membre. Notez que l'utilisation du même objectClass static-oc dans plus d'une configuration de groupe dynamique n'est pas prise en charge. Si le caractère optionnel * est également spécifié, alors les valeurs membre et memberOf seront peuplées récursivement, pour les groupes imbriqués. Notez qu'actuellement, l'imbrication n'est prise en charge que pour les opérations de recherche, pas pour les comparaisons.

dynlist-simple TRUE | FALSE
Cette option réduit la fonctionnalité au comportement de la superposition dynlist d'OpenLDAP 2.4. Elle désactive le traitement memberOf, le support des groupes imbriqués et l'évaluation des filtres des valeurs générées dynamiquement. La valeur par défaut est FALSE.

La superposition dynlist peut être utilisée avec n'importe quel backend, mais elle est principalement destinée à être utilisée avec des backends de stockage locaux. Si l'expansion des URI est très coûteuse en ressources et se produit fréquemment avec des motifs bien définis, il convient d'envisager d'ajouter un proxycache plus loin dans la pile de superpositions.

AUTORISATION

Par défaut, les expansions sont effectuées en utilisant l'identité de l'utilisateur LDAP actuel. Cette identité peut être remplacée en définissant l'attribut dgIdentity dans l'entrée du groupe avec le DN d'un autre utilisateur LDAP. Dans ce cas, le dgIdentity sera utilisé lors de l'expansion des URI dans l'objet. Définir dgIdentity à une chaîne de longueur nulle provoquera l'exécution des expansions de manière anonyme. Notez que l'attribut dgIdentity est défini dans le schéma dyngroup, et ce schéma doit être chargé avant que la fonctionnalité d'autorisation dgIdentity puisse être utilisée. Si l'attribut dgAuthz est également présent dans l'entrée du groupe, ses valeurs sont utilisées pour déterminer quelles identités sont autorisées à utiliser le dgIdentity pour développer le groupe. Les valeurs de l'attribut dgAuthz doivent être conformes à la syntaxe (expérimentale) OpenLDAP authz. Lors de l'utilisation de membre dynamique dans les filtres de recherche, un accès de recherche au pseudo-attribut entryDN est requis.

EXEMPLE

Cet exemple collecte toutes les adresses e-mail d'une base de données en une seule entrée ; tout d'abord, assurez-vous que slapd.conf contient les directives :

    include /chemin/vers/dyngroup.schema
    # ...
    database <database>
    # ...
    overlay dynlist
    dynlist-attrset groupOfURLs memberURL

et que slapd charge dynlist.la, s'il est compilé en tant que module de runtime ; puis ajoutez à la base de données une entrée comme

    dn: cn=Liste Dynamique,ou=Groupes,dc=exemple,dc=com
    objectClass: groupOfURLs
    cn: Liste Dynamique
    memberURL: ldap:///ou=Personnes,dc=exemple,dc=com?mail?sub?(objectClass=person)

Si aucun <attrs> n'est fourni dans l'URI, tous les attributs (non opérationnels) sont collectés.

Les valeurs de la liste ci-dessus ne peuvent pas être évaluées dans un filtre de recherche. Pour permettre l'évaluation des filtres sur la liste dynamique, la configuration doit être modifiée pour mapper explicitement les attributs dynamiques à filtrer. Dans ce cas, mail est simplement mappé à lui-même.

    include /chemin/vers/dyngroup.schema
    # ...
    database <database>
    # ...
    overlay dynlist
    dynlist-attrset groupOfURLs memberURL mail:mail

Cet exemple implémente la fonctionnalité de groupe dynamique sur l'attribut member :

    include /chemin/vers/dyngroup.schema
    # ...
    database <database>
    # ...
    overlay dynlist
    dynlist-attrset groupOfURLs memberURL member

Un groupe dynamique avec autorisation dgIdentity pourrait être créé avec une entrée comme

    dn: cn=Groupe Dynamique,ou=Groupes,dc=exemple,dc=com
    objectClass: groupOfURLs
    objectClass: dgIdentityAux
    cn: Groupe Dynamique
    memberURL: ldap:///ou=Personnes,dc=exemple,dc=com??sub?(objectClass=person)
    dgIdentity: cn=Proxy Groupe,ou=Services,dc=exemple,dc=com

Cet exemple étend la fonctionnalité de groupe dynamique pour ajouter un membre dynamique

dgMem

slapo-dynlist(5) - OpenLDAP

NAME

slapo-dynlist - dynamic list overlay for OpenLDAP

SYNOPSIS

    cn=config
      olcOverlay={1}dynlist
        olcDlAttrSet: <set tag> <group membership attr> <group members attr> ...
        olcDynamicList: <group membership attr> <group members attr> ...

DESCRIPTION

The dynlist overlay provides dynamic membership management for groups. It allows defining groups whose membership is determined by a filter rather than explicit enumeration. This means that members are automatically added or removed from the group based on their attributes matching the group definition.

The overlay works by intercepting modify operations and re-evaluating group memberships when necessary. It can be used to implement features like dynamic distribution lists or role-based access control.

CONFIGURATION

The dynlist overlay is configured using the cn=config backend. The following configuration options are available:

olcOverlay={1}dynlist
This directive enables the dynlist overlay. The number in braces should be unique to the overlay instance.
olcDlAttrSet
This directive defines a set of attributes for group membership. It takes a tag (which can be used to reference this set later) followed by pairs of attributes. The first attribute in a pair represents the group membership attribute (e.g., member, uniqueMember), and the second attribute represents the attribute storing the members' DNs (e.g., member, memberUid).
olcDynamicList
This directive defines how dynamic group memberships are evaluated. It specifies the group membership attribute and the attribute that stores the members' DNs. This directive can be specified multiple times to support different group types.

AUTHORIZATION

The dynlist overlay performs authorization checks based on the group memberships it manages. This means that access control rules can be defined in terms of dynamic group membership, simplifying management.

EXAMPLE

Here is an example of how to configure the dynlist overlay to manage dynamic groups:

    dn: olcOverlay={1}dynlist,olcDatabase={1}mdb,cn=config
    objectClass: olcOverlayConfig
    objectClass: olcDynListConfig
    olcOverlay: {1}dynlist
    olcDlAttrSet: groupOfNames member member
    olcDlAttrSet: groupOfURLs memberURL memberURL
    olcDynamicList: memberOf member

In this example:

  • The first olcDlAttrSet directive defines a set named groupOfNames, where the group membership is indicated by the member attribute, and the group members' DNs are also stored in the member attribute.
  • The second olcDlAttrSet directive defines a set named groupOfURLs, used for groups where membership is defined by URLs. The memberURL attribute indicates the group membership, and the members' DNs are also stored in memberURL.
  • The olcDynamicList directive specifies that the memberOf attribute should be used to dynamically determine group membership. Any user whose memberOf attribute contains a DN that matches a group entry will be considered a member of that group.

This configuration effectively allows users to have a list of groups they belong to dynamically populated based on their attributes, without explicitly listing each group membership in their user entry.

The example below shows how to add the dgMemberOf attribute to all members of a dynamic group:

    include /path/to/dyngroup.schema
    # ...
    database <database>
    # ...
    overlay dynlist
    dynlist-attrset groupOfURLs memberURL member+dgMemberOf

This example extends the dynamic memberOf feature to add the memberOf attribute to all the members of both static and dynamic groups:

    include /path/to/dyngroup.schema
    # ...
    database <database>
    # ...
    overlay dynlist
    dynlist-attrset groupOfURLs memberURL member+memberOf@groupOfNames

This dynamic memberOf feature can fully replace the functionality of the slapo-memberof(5) overlay.

FILES

/etc/openldap/slapd.conf
default slapd configuration file

BACKWARD COMPATIBILITY

The dynlist overlay has been reworked with the 2.5 release to use a consistent namespace as with other overlays. As a side-effect the following cn=config parameters are deprecated and will be removed in a future release: olcDlAttrSet is replaced with olcDynListAttrSet olcDynamicList is replaced with olcDynListConfig

SEE ALSO

slapd.conf(5), slapd-config(5), slapd(8). The slapo-dynlist(5) overlay supports dynamic configuration via back-config.

BUGS

Filtering on dynamic groups may return incomplete results if the search operation uses the pagedResults control.
