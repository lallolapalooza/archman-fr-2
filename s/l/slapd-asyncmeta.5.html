NOM

slapd-asyncmeta - backend métadirectory asynchrone pour slapd

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

Le backend asyncmeta pour slapd(8) effectue un proxy LDAP de base par rapport à un ensemble de serveurs LDAP distants, appelés "cibles". Les informations contenues dans ces serveurs peuvent être présentées comme appartenant à un seul Arbre d'Information d'Annuaire (DIT).

Une bonne connaissance des fonctionnalités du backend slapd-meta(5) est recommandée. Ce backend a été conçu comme une version asynchrone du backend meta. Contrairement à meta, les threads gérant les opérations n'attendent plus la réponse du serveur distant, réduisant ainsi le nombre de threads nécessaires pour gérer la même charge. Bien qu'asyncmeta maintienne les fonctionnalités de meta et ait une base de code largement similaire, certains changements dans le fonctionnement et quelques nouvelles directives de configuration ont été ajoutés. Certaines options de configuration, telles que conn-pool-max, conn-ttl, single-conn et use-temporary-conn ont été supprimées, car elles ne sont plus pertinentes.

Gestion des nouvelles connexions :

Contrairement à meta, qui met en cache les connexions liées, asyncmeta fonctionne avec un nombre maximum de connexions configuré par cible. Pour chaque requête redirigée vers une cible, une connexion différente est sélectionnée. Chaque connexion a une file d'attente, à laquelle la requête est ajoutée avant d'être envoyée au serveur distant, et elle est retirée après réception de la dernière réponse pour cette requête.
Pour chaque nouvelle requête, une nouvelle connexion est choisie en utilisant une planification round-robin.

Superpositions (Overlays) :

En raison de spécificités d'implémentation, il n'y a aucune garantie que l'une des superpositions OpenLDAP existantes fonctionnera avec le backend asyncmeta.

EXEMPLES

Reportez-vous à slapd-meta(5) pour des exemples de configuration.

CONFIGURATION

Ces options de slapd.conf s'appliquent à la base de données du backend ASYNCMETA. C'est-à-dire qu'elles doivent suivre une ligne "database asyncmeta" et précéder toute ligne "backend" ou "database" ultérieure. Les autres options de base de données sont décrites dans la page du manuel slapd.conf(5).

DIRECTIVES DE CONFIGURATION SPÉCIALES

La configuration de la cible commence par la directive "uri". Toutes les directives de configuration qui ne sont pas spécifiques aux cibles doivent être définies en premier pour plus de clarté, y compris celles qui sont communes à tous les backends. Elles sont:

cible-par-défaut aucune
Cette directive force le backend à rejeter toutes les opérations qui doivent aboutir à une seule cible si aucune ou plusieurs cibles sont sélectionnées. Elles comprennent : ajouter, supprimer, modifier, modrdn ; compare n'est pas inclus, ainsi que bind car, puisqu'ils n'altèrent pas les entrées, en cas de correspondances multiples une tentative est faite pour effectuer l'opération sur n'importe quelle cible candidate, avec la contrainte qu'au maximum une doit réussir. Cette directive peut également être utilisée lors du traitement des cibles pour marquer une cible spécifique comme par défaut.
cache-dn-ttl {DÉSACTIVÉ|jamais|<ttl>}
Cette directive définit la durée de vie du cache DN. Ce cache stocke la cible qui contient un DN donné pour accélérer la sélection de la cible en cas de plusieurs cibles résultant d'une recherche non mise en cache ; jamais signifie que le cache expire jamais ; désactivé signifie aucun cache DN ; sinon, une valeur ttl valide ( > 0 ) est requise, dans le format illustré pour la directive idle-timeout.
onerr {CONTINUER|rapporter|arrêter}
Cette directive permet de sélectionner le comportement en cas d'erreur retournée par une cible lors d'une recherche. La valeur par défaut, continuer, consiste à poursuivre l'opération, en essayant de retourner autant de données que possible. Si la valeur est définie sur arrêter, la recherche est terminée dès qu'une erreur est retournée par une cible, et l'erreur est immédiatement propagée au client. Si la valeur est définie sur rapporter, la recherche est continuée jusqu'à la fin mais, si au moins une cible a retourné un code d'erreur, le premier code d'erreur non-succès est retourné.
max-timeout-ops <nombre>
Spécifie le nombre de requêtes consécutives expirées, après lesquelles la connexion sera considérée défectueuse et fermée.
max-pending-ops <nombre>
Le nombre maximum de requêtes en attente stockées dans la file d'attente d'une connexion. La valeur par défaut est 128. Lorsque ce nombre est dépassé, LDAP_BUSY sera retourné au client.
max-target-conns <nombre>
Le nombre maximum de connexions par cible. Contrairement à slapd-meta(5), aucune nouvelle connexion ne sera créée une fois ce nombre atteint. La valeur par défaut est 255.
norefs <NON|oui>
Si oui, ne pas retourner les réponses de référence de recherche. Par défaut, elles sont retournées à moins que la requête ne soit LDAPv2. Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si outrepassé par une directive par cible.
noundeffilter <NON|oui>
Si oui, retourner succès au lieu de rechercher si un filtre est indéfini ou contient des portions indéfinies. Par défaut, la recherche est propagée après le remplacement des portions indéfinies par (!(objectClass=*)), ce qui correspond à l'ensemble de résultats vide. Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si outrepassé par une directive par cible.
version-protocole {0,2,3}
Cette directive indique quelle version du protocole doit être utilisée pour contacter le serveur distant. Si défini sur 0 (par défaut), le proxy utilise la même version de protocole que celle utilisée par le client, sinon le protocole demandé est utilisé. Le proxy retourne unwillingToPerform si une opération incompatible avec le protocole demandé est tentée. Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si outrepassé par une directive par cible.
pseudo-root-bind-defer {OUI|non}
Cette directive, lorsqu'elle est définie sur oui, entraîne le report de l'authentification aux serveurs distants avec l'identité pseudo-racine (l'identité définie dans chaque directive idassert-bind) jusqu'à ce qu'elle soit effectivement nécessaire par les opérations ultérieures. Sinon, toutes les liaisons en tant que rootdn sont propagées aux cibles.
quarantaine <intervalle>,<num>[;<intervalle>,<num>[...]]
Active la mise en quarantaine des URIs qui ont retourné LDAP_UNAVAILABLE, de sorte qu'une tentative de reconnexion ne se produit qu'à des intervalles donnés au lieu de chaque fois qu'un client demande une opération. Le modèle est : réessayer uniquement après qu'au moins intervalle secondes se soient écoulées depuis la dernière tentative, pour exactement num fois ; ensuite, utiliser le modèle suivant. Si num pour le dernier modèle est "+", il réessaie indéfiniment ; sinon, plus aucune tentative n'est effectuée. Cette directive doit apparaître avant toute spécification de cible ; elle affecte toutes les cibles avec le même modèle.
rebind-en-tant-qu-utilisateur {NON|oui}
Si cette option est donnée, les informations d'identification de liaison du client sont conservées pour les rebinds, lors de la tentative de rétablissement d'une connexion rompue, ou lors du suivi d'une référence, si chase-referrals est défini sur oui.
suivi-session-request {NON|oui}
Ajoute un contrôle de suivi de session pour toutes les requêtes. L'adresse IP et le nom d'hôte du client, ainsi que l'identité associée à chaque requête, si connue, sont envoyés au serveur distant à des fins d'information. Cette directive est incompatible avec le réglage de version-protocole sur 2. Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si outrepassé par une directive par cible.

SPÉCIFICATION DE LA CIBLE

La spécification de la cible commence par une directive « uri » :

uri <protocole>://[<hôte>]/<contexte de nommage> [...]
Identique à meta. Voir slapd-meta(5) pour plus de détails.
acl-authcDN <DN administratif à des fins de contrôle d'accès>
DN utilisé pour interroger le serveur cible afin de vérifier les ACL, comme dans le backend LDAP ; il est censé avoir un accès en lecture sur le serveur cible aux attributs utilisés sur le proxy pour la vérification des ACL. Il n'y a aucun risque de divulguer de telles valeurs ; elles sont uniquement utilisées pour vérifier les permissions. L'identité acl-authcDN n'est en aucun cas utilisée implicitement par le proxy lorsque le client se connecte anonymement.
acl-passwd <mot de passe>
Mot de passe utilisé avec l'acl-authcDN ci-dessus.
bind-timeout <microsecondes>
Cette directive définit le délai d'attente, en microsecondes, utilisé lors de la mise en attente d'une réponse après une connexion bind asynchrone. Voir slapd-meta(5) pour plus de détails.
chase-referrals {OUI|non}
activer/désactiver la poursuite automatique des références, qui est déléguée à la bibliothèque libldap sous-jacente, avec une nouvelle liaison effectuée si la directive rebind-as-user est utilisée. Par défaut, les références sont suivies. Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si cela est remplacé par une directive par cible.
client-pr {accepter-non sollicité|DÉSACTIVER|<taille>}
Cette fonctionnalité permet d'utiliser le contrôle des résultats paginés RFC 2696 lors de l'exécution d'opérations de recherche avec une cible spécifique, quelle que soit la requête du client. Voir slapd-meta(5) pour plus de détails.
default-target [<cible>]
La directive « default-target » peut également être utilisée lors de la spécification de la cible. Sans arguments, elle marque la cible actuelle comme étant la cible par défaut. Le numéro optionnel marque la cible <cible> comme étant la cible par défaut, en commençant par 1. La cible <cible> doit être définie.
filter <modèle>
Cette directive permet de spécifier un modèle regex(5) pour indiquer quels termes du filtre de recherche sont réellement servis par une cible.

Dans une requête de recherche, si le filtre de recherche correspond au modèle, la cible est prise en compte lors de la satisfaction de la requête ; sinon, la cible est ignorée. Il peut y avoir plusieurs occurrences de la directive filter pour chaque cible.

idassert-authzFrom <authz-regexp>
Si défini, sélectionne quelles identités *locales* sont autorisées à exploiter la fonctionnalité d'assertion d'identité. La chaîne <authz-regexp> suit les règles définies pour l'attribut authzFrom. Voir slapd.conf(5), section relative à authz-policy, pour les détails sur la syntaxe de ce champ.

idassert-bind bindmethod=none|simple|sasl [binddn=<DN simple>] [credentials=<mot de passe simple>] [saslmech=<mécanisme SASL>] [secprops=<propriétés>] [realm=<domaine>] [authcId=<ID d'authentification>] [authzId=<ID d'autorisation>] [authz={native|proxyauthz}] [mode=<mode>] [flags=<indicateurs>] [starttls=no|yes|critical] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<chiffrements>] [tls_ecname=<noms>] [tls_protocol_min=<majeur>[.<mineur>]] [tls_crlcheck=none|peer|all] Permet de définir les paramètres de la méthode d'authentification utilisée en interne par le proxy pour autoriser les connexions authentifiées par d'autres bases de données. Voir slapd-meta(5) pour plus de détails.

idle-timeout <temps>
Cette directive provoque la fermeture d'une connexion persistante après qu'elle soit restée inactive pendant la durée spécifiée. La connexion sera recréée lors de la prochaine utilisation. Une connexion est considérée comme inactive si le backend n'a tenté de l'utiliser pour envoyer une requête au serveur backend. S'il reste encore des requêtes en attente dans sa file d'attente, la connexion sera fermée une fois que la dernière requête aura reçu un résultat ou aura expiré.

[<j>j][<h>h][<m>m][<s>[s]]

où <j>, <h>, <m> et <s> sont traités respectivement comme des jours, heures, minutes et secondes. Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si cela est remplacé par une directive par cible.

keepalive <inactif>:<sondes>:<intervalle>
Le paramètre keepalive définit les valeurs de inactif, sondes et intervalle utilisées pour vérifier si une socket est active ; inactif est le nombre de secondes pendant lesquelles une connexion doit rester inactive avant que TCP ne commence à envoyer des sondes keepalive ; sondes est le nombre maximum de sondes keepalive que TCP doit envoyer avant de fermer la connexion ; intervalle est l'intervalle en secondes entre les sondes keepalive individuelles. Seuls certains systèmes prennent en charge la personnalisation de ces valeurs ; le paramètre keepalive est ignoré sinon, et les paramètres globaux du système sont utilisés.
tcp-user-timeout <millisecondes>
S'il est différent de zéro, correspond à la valeur TCP_USER_TIMEOUT définie sur les connexions cibles, remplaçant le paramètre du système d'exploitation. Seuls certains systèmes prennent en charge la personnalisation de ce paramètre ; il est ignoré sinon et les paramètres globaux du système sont utilisés.
map {attribut|objectclass} [<nom local>|*] {<nom étranger>|*}
Ceci mappe les classes d'objets et les attributs comme dans le backend LDAP. Voir slapd-ldap(5).
network-timeout <temps>
Définit la valeur du délai d'attente réseau après laquelle poll(2)/select(2) après un connect(2) retourne en cas d'inactivité lors de l'envoi d'une opération à la cible distante. La valeur est en millisecondes, et elle peut être spécifiée comme pour idle-timeout. Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si cela est remplacé par une directive par cible.
nretries {jamais|jamais|<nretries>}
Cette directive définit le nombre de fois où la réexpédition d'une opération doit être tentée en cas d'échec temporaire de contact avec une cible. Le nombre de tentatives est par opération, donc si une liaison à la cible est nécessaire d'abord, le nombre restant est décrémenté. Si défini avant toute spécification de cible, il s'applique à toutes les cibles (par défaut, 3 fois) ; la valeur globale peut être remplacée par des redéfinitions à l'intérieur de chaque spécification de cible.
subtree-{exclude|include} <règle>
Cette directive permet d'indiquer quelles sous-arborescences sont effectivement desservies par une cible. Voir slapd-meta(5) pour plus de détails.
suffixmassage <suffix local> <suffix distant>
slapd-asyncmeta ne prend pas en charge le moteur de réécriture utilisé par les backends LDAP et META. suffixmassage peut être utilisé pour effectuer une réécriture de suffixe DN, de la même manière que la directive obsolète suffixmassage précédemment utilisée par le backend LDAP.
t-f-support {NON|oui|découvrir}
activer si le serveur distant prend en charge les filtres absolus (voir RFC 4526 pour plus de détails). Si réglé sur découvrir, la prise en charge est détectée en lisant le DSE racine du serveur distant. Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si cela est remplacé par une directive par cible.
timeout [<op>=]<val> [...]
Cette directive permet de définir des délais d'attente par opération. Les opérations peuvent être

<op> ::= bind, add, delete, modrdn, modify, compare, search

Par défaut, le délai d'attente pour toutes les opérations est de 2 secondes.

Voir slapd-meta(5) pour plus de détails.

tls {none|[try-]start|[try-]propagate|ldaps}
B [starttls=no] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<chiffrements>] [tls_ecname=<noms>] [tls_crlcheck=none|peer|all]
Spécifie les paramètres TLS pour les connexions régulières.

Si le premier paramètre n'est pas « none », cela configure les paramètres TLS à utiliser pour les connexions régulières. L'opération étendue StartTLS sera utilisée lors de l'établissement de la connexion, sauf si le schéma de protocole de la directive URI est ldaps://. Dans ce cas, ce mot-clé ne peut être défini que sur « ldaps » et l'opération StartTLS ne sera pas utilisée.

Avec propagate, le proxy émet l'opération StartTLS uniquement si la connexion d'origine dispose d'une couche TLS configurée. Le préfixe try- demande au proxy de continuer les opérations si l'opération StartTLS a échoué ; son utilisation n'est pas recommandée.

Les paramètres TLS sont par défaut les mêmes que les paramètres TLS principaux de slapd, sauf pour tls_reqcert qui est par défaut « demand », tls_reqsan qui est par défaut « allow », et starttls qui est éclipsé par le premier mot-clé et donc ignoré.

Si défini avant toute spécification de cible, cela affecte toutes les cibles, sauf si cela est remplacé par une directive par cible.

SCÉNARIOS

Voir slapd-meta(5) pour les scénarios de configuration.

ACLs

Le comportement des ACL est identique à celui de meta. Voir slapd-meta(5).

CONTRÔLE D'ACCÈS

Le backend asyncmeta ne respecte pas toutes les sémantiques des ACL telles que décrites dans slapd.access(5). En général, la vérification d'accès est déléguée au(x) serveur(s) distant(s). Seul l'accès en lecture (=r) au pseudo-attribut entry et aux autres valeurs d'attribut des entrées renvoyées par l'opération search est respecté, ce qui est effectué par le frontend.
