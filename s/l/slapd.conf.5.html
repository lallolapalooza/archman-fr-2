SLAPD.CONF(5) Manuel des formats de fichiers SLAPD.CONF(5)

NOM

slapd.conf - fichier de configuration pour slapd, le démon LDAP autonome

SYNTAXE

/etc/openldap/slapd.conf

DESCRIPTION

Le fichier /etc/openldap/slapd.conf contient des informations de configuration pour le démon slapd(8). Ce fichier de configuration est également utilisé par les outils SLAPD slapacl(8), slapadd(8), slapauth(8), slapcat(8), slapdn(8), slapindex(8), slapmodify(8) et slaptest(8).

Le fichier slapd.conf se compose d'une série d'options de configuration globales qui s'appliquent à slapd dans son ensemble (y compris tous les backends), suivies de zéro ou plusieurs définitions de backends de base de données qui contiennent des informations spécifiques à une instance de backend. Les options de configuration ne sont pas sensibles à la casse ; leurs valeurs, au cas par cas, peuvent l'être.

Le format général de slapd.conf est le suivant :

    # commentaire - ces options s'appliquent à chaque base de données
    <options de configuration globales>
    # première définition de base de données & options de configuration
    database <type de backend 1>
    <options de configuration spécifiques au backend 1>
    # définitions de bases de données et options de configuration suivantes
    ...

Autant de sections spécifiques au backend que désiré peuvent être incluses. Les options globales peuvent être remplacées dans un backend (pour les options qui apparaissent plus d'une fois, la dernière apparition dans le fichier slapd.conf est utilisée).

Si une ligne commence par un espace blanc, elle est considérée comme une continuation de la ligne précédente. Aucune ligne physique ne doit dépasser 2000 octets.

Les lignes vides et les lignes de commentaires commençant par un caractère `#' sont ignorées. Remarque : les lignes de continuation sont déballées avant que le traitement des commentaires ne soit appliqué.

Les arguments des lignes de configuration sont séparés par des espaces blancs. Si un argument contient des espaces blancs, il doit être entouré de guillemets doubles. Si un argument contient un guillemet double (`"') ou un caractère backslash (`\'), le caractère doit être précédé d'un backslash.

Les options de configuration spécifiques sont discutées ci-dessous dans les Options de configuration globales, les Options générales de backend et les Options générales de base de données. Les options spécifiques au backend sont discutées dans les pages de manuel slapd-<backend>(5). Reportez-vous au "Guide de l'administrateur OpenLDAP" pour plus de détails sur le fichier de configuration slapd.

OPTIONS DE CONFIGURATION GLOBALES

Les options décrites dans cette section s'appliquent à tous les backends, sauf indication contraire dans une définition de backend. Les arguments qui doivent être remplacés par du texte réel sont indiqués entre crochets <>.

access à <quoi> [ par <qui> <accès> <contrôle> ]+
Accorde l'accès (spécifié par <accès>) à un ensemble d'entrées et/ou d'attributs (spécifié par <quoi>) par un ou plusieurs demandeurs (spécifié par <qui>). Si aucun contrôle d'accès n'est présent, la politique par défaut autorise toute personne à lire n'importe quoi, mais restreint les mises à jour au rootdn. (par exemple, "access to * by * read"). Le rootdn peut toujours lire et écrire TOUT ! Voir slapd.access(5) et le "Guide de l'administrateur d'OpenLDAP" pour les détails.
allow <fonctionnalités>
Spécifie un ensemble de fonctionnalités (séparées par des espaces) à autoriser (par défaut aucune). bind_v2 autorise l'acceptation des requêtes bind LDAPv2. Notez que slapd(8) n'implémente pas vraiment LDAPv2 (RFC 1777), maintenant Historique (RFC 3494). bind_anon_cred autorise le bind anonyme lorsque les identifiants ne sont pas vides (par exemple, lorsque le DN est vide). bind_anon_dn autorise le bind non authentifié (anonyme) lorsque le DN n'est pas vide. update_anon autorise le traitement des opérations de mise à jour non authentifiées (anonymes) (sous réserve des contrôles d'accès et autres limites administratives). proxy_authz_anon autorise le traitement du contrôle d'autorisation proxy non authentifié (anonyme) (sous réserve des contrôles d'accès, de l'autorisation et autres limites administratives).
argsfile <nom_de_fichier>
Le nom (absolu) d'un fichier qui contiendra la ligne de commande du serveur slapd (nom du programme et options).
attributeoptions [nom-option]...
Définit les options d'attributs de marquage ou les préfixes/plages de tags. Les options ne doivent pas se terminer par `-', les préfixes doivent se terminer par `-'. Le préfixe `lang-' est prédéfini. Si vous utilisez la directive attributeoptions, `lang-' ne sera plus défini et vous devrez l'indiquer explicitement si vous souhaitez le définir.

Une description d'attribut avec une option de marquage est un sous-type de cette description d'attribut sans l'option. À part cela, les options définies de cette manière n'ont pas de sémantique spéciale. Les préfixes définis de cette manière fonctionnent comme les options `lang-' : Ils définissent un préfixe pour les options de marquage commençant par ce préfixe. C'est-à-dire, si vous définissez le préfixe `x-foo-', vous pouvez utiliser l'option `x-foo-bar'. De plus, dans une recherche ou une comparaison, un nom de préfixe ou de plage (avec un `- ' final) correspond à toutes les options commençant par ce nom, ainsi qu'à l'option avec le nom de plage sans le `- ' final. C'est-à-dire, `x-foo-bar-' correspond à `x-foo-bar' et `x-foo-bar-baz'.

RFC 4520 réserve les options commençant par `x-' pour des expériences privées. D'autres options doivent être enregistrées auprès de l'IANA, voir la section 3.5 du RFC 4520. OpenLDAP dispose également de l'option `binary' intégrée, mais il s'agit d'une option de transfert, pas d'une option de marquage.

L'analyseur slapd étend la définition RFC 4512 en autorisant les formes de chaîne ainsi que les OID numériques à être utilisées pour l'OID de l'attribut et l'OID de la syntaxe de l'attribut. (Voir la description de objectidentifier.)
authid-rewrite<cmd> <args>
Utilisé par le framework d'authentification pour convertir des noms d'utilisateur simples en un DN LDAP utilisé à des fins d'autorisation. Son but est analogue à celui de authz-regexp (voir ci-dessous). Le préfixe authid- est suivi d'un ensemble de règles analogues à celles décrites dans slapo-rwm(5) pour la réécriture des données (remplacer le préfixe rwm- par authid-). Les règles de authid-rewrite<cmd> et authz-regexp ne doivent pas être mélangées.
authz-policy <politique>
Utilisé pour spécifier quelles règles utiliser pour l'autorisation proxy. L'autorisation proxy permet à un client de s'authentifier auprès du serveur en utilisant les identifiants d'un utilisateur, mais de spécifier une autre identité à utiliser pour l'autorisation et le contrôle d'accès. Elle permet essentiellement à l'utilisateur A de se connecter en tant qu'utilisateur B, en utilisant le mot de passe de l'utilisateur A. Le drapeau none désactive l'autorisation proxy. C'est le réglage par défaut. Le drapeau from utilisera les règles de l'attribut authzFrom du DN d'autorisation. Le drapeau to utilisera les règles de l'attribut authzTo du DN d'authentification. Le drapeau any, un alias pour la valeur dépréciée de both, autorisera n'importe laquelle des options ci-dessus, selon ce qui réussit en premier (vérifié dans la séquence to, from. Le drapeau all exige que les deux autorisations réussissent.
Les règles sont des mécanismes pour spécifier quelles identités sont autorisées à effectuer une autorisation proxy. L'attribut authzFrom dans une entrée spécifie quels autres utilisateurs sont autorisés à se connecter en tant que proxy vers cette entrée. L'attribut authzTo dans une entrée spécifie quels autres utilisateurs cet utilisateur peut autoriser en tant que. L'utilisation des règles authzTo peut être facilement abusée si les utilisateurs sont autorisés à écrire des valeurs arbitraires dans cet attribut. En général, l'attribut authzTo doit être protégé par des ACLs de telle sorte que seuls les utilisateurs privilégiés puissent le modifier. identités; elle peut prendre cinq formes :
ldap:///<base>??[<scope>]?<filter>
dn[.<dnstyle>]:<pattern>
u[.<mech>[/<realm>]]:<pattern>
group[/objectClass[/attributeType]]:<pattern>

<dnstyle>:={exact|onelevel|children|subtree|regex}

La première forme est une URI LDAP valide où les portions <host>:<port>, <attrs> et <extensions> doivent être absentes, de sorte que la recherche s'effectue localement sur authzFrom ou authzTo.

La deuxième forme est un DN. Les modificateurs optionnels dnstyle exact, onelevel, children et subtree fournissent des correspondances exactes, au niveau un, pour les enfants et en sous-arbre, ce qui entraîne la normalisation de <pattern> selon les règles de normalisation DN. Le modificateur spécial dnstyle regex fait que <pattern> est traité comme une expression régulière POSIX (''étendue''), comme discuté dans regex(7) et/ou re_format(7). Un motif de * signifie n'importe quel DN non anonyme.

La troisième forme est un id SASL. Les champs optionnels <mech> et <realm> permettent de spécifier un mécanisme SASL, et éventuellement un domaine SASL, pour les mécanismes qui le supportent. La nécessité d'autoriser la spécification d'un mécanisme est toujours débattue, et il est fortement déconseillé aux utilisateurs de se fier à cette possibilité.

La quatrième forme est une spécification de groupe. Elle consiste en le mot-clé group, suivi optionnellement de la spécification de l'objectClass et du attributeType du groupe. L'objectClass est par défaut groupOfNames. L'attributeType est par défaut member. Le groupe dont le DN est <pattern> est recherché avec une portée de base, filtré sur l'objectClass spécifié. Les valeurs de l'attributeType résultant sont recherchées pour le DN asserté.

La cinquième forme est fournie pour des raisons de compatibilité ascendante. Si aucun type d'identité n'est fourni, c'est-à-dire si seul <pattern> est présent, un DN exact est supposé ; par conséquent, <pattern> est soumis à la normalisation DN.

L'interprétation de authzFrom et authzTo pouvant avoir un impact sur la sécurité, il est fortement recommandé aux utilisateurs de définir explicitement le type de spécification d'identité utilisé. Un sous-ensemble de ces règles peut être utilisé comme troisième argument dans l'instruction authz-regexp (voir ci-dessous) ; notamment, les formes URI, à condition qu'elles aboutissent à une seule entrée, et dn.exact:<dn>.

authz-regexp <match> <replace>
Utilisé par le framework d'authentification pour convertir des noms d'utilisateur simples, tels que ceux fournis par le sous-système SASL, ou extraits de certificats en cas de SASL EXTERNAL basé sur certificat, ou fournis dans le contrôle RFC 4370 "proxied authorization", en un DN LDAP utilisé à des fins d'autorisation. Notez que le DN résultant n'a pas besoin de faire référence à une entrée existante pour être considéré comme valide. Lorsqu'une demande d'autorisation est reçue du sous-système SASL, l'USERNAME, le REALM et le MECHANISM SASL sont pris, lorsqu'ils sont disponibles, et combinés en un nom de la forme
UID=<username>[[,CN=<realm>],CN=<mechanism>],CN=auth
Ce nom est ensuite comparé à l'expression régulière POSIX (''étendue'') match, et si la correspondance est réussie, le nom est remplacé par la chaîne replace. S'il y a des chaînes génériques dans l'expression régulière match qui sont entourées de parenthèses, par exemple
UID=([^,]*),CN=.*
alors la partie du nom qui correspondait à la chaîne générique sera stockée dans la variable réservée numérotée $1. S'il y a d'autres chaînes génériques entre parenthèses, les chaînes correspondantes seront dans $2, $3, etc. jusqu'à $9. Les variables réservées peuvent alors être utilisées dans la chaîne replace, par exemple
UID=$1,OU=Accounts,DC=example,DC=com
Le nom remplacé peut être soit un DN, c'est-à-dire une chaîne préfixée par "dn:", soit une URI LDAP. Dans ce dernier cas, le serveur utilisera l'URI pour rechercher dans sa propre base de données et, si la recherche renvoie exactement une entrée, le nom sera remplacé par le DN de cette entrée. L'URI LDAP ne doit pas avoir de composant hostport, attrs, ou extensions, mais le filtre est obligatoire, par exemple
ldap:///OU=Accounts,DC=example,DC=com??one?(UID=$1)
La partie protocole de l'URI doit être strictement ldap. Notez que cette recherche est soumise aux contrôles d'accès. Plus précisément, l'identité d'authentification doit avoir un accès "auth" dans le sujet.

Plusieurs options authz-regexp peuvent être fournies dans le fichier de configuration pour permettre plusieurs modèles de correspondance et de remplacement. Les modèles de correspondance sont vérifiés dans l'ordre où ils apparaissent dans le fichier, en s'arrêtant à la première correspondance réussie.

concurrency <entier>
Spécifie un niveau de concurrence souhaité. Fourni au système de threads sous-jacent comme indice. La valeur par défaut est de ne fournir aucun indice. Ce réglage n'est significatif que sur certaines plateformes où il n'y a pas une correspondance un à un entre les threads utilisateur et les threads du noyau.
conn_max_pending <entier>
Spécifie le nombre maximum de requêtes en attente pour une session anonyme. Si les requêtes sont soumises plus rapidement que le serveur ne peut les traiter, elles seront mises en file d'attente jusqu'à cette limite. Si la limite est dépassée, la session est fermée. La valeur par défaut est 100.
conn_max_pending_auth <entier>
Spécifie le nombre maximum de requêtes en attente pour une session authentifiée. La valeur par défaut est 1000.
defaultsearchbase <dn>
Spécifie une base de recherche par défaut à utiliser lorsqu'un client soumet une requête de recherche non-base avec un DN de base vide. Les requêtes de recherche à portée de base avec un DN de base vide ne sont pas affectées.
disallow <features>
Spécifie un ensemble de fonctionnalités (séparées par des espaces blancs) à interdire (par défaut aucune). bind_anon désactive l'acceptation des requêtes de connexion anonymes. Notez que ce réglage n'interdit pas l'accès annonyme au répertoire (voir "require authc"). bind_simple désactive l'authentification simple (bind). tls_2_anon désactive la mise en force de la session à l'état anonyme (voir aussi tls_authc) lors de la réception d'une opération StartTLS. tls_authc interdit l'opération StartTLS si authentifié (voir aussi tls_2_anon). proxy_authz_non_critical désactive l'acceptation du contrôle d'autorisation proxysé (RFC4370) avec la criticité définie sur FALSE. dontusecopy_non_critical désactive l'acceptation du contrôle dontUseCopy (en cours de développement) avec la criticité définie sur FALSE.

ditcontentrule ( <oid> [NAME <name>] [DESC <description>] [OBSOLETE] [AUX <oids>] [MUST <oids>] [MAY <oids>] [NOT <oids>] )

Spécifie une règle de contenu DIT en utilisant la syntaxe LDAPv3 définie dans RFC 4512. L'analyseur slapd étend la définition RFC 4512 en permettant l'utilisation de formes de chaînes ainsi que des OID numériques pour l'OID de l'attribut et l'OID de la syntaxe de l'attribut. (Voir la description de objectidentifier.)
gentlehup { on | off }
Un signal SIGHUP provoquera uniquement une tentative d'arrêt 'douce' : Slapd cessera d'écouter les nouvelles connexions, mais ne fermera pas les connexions avec les clients actuels. Les futures opérations d'écriture renverront cependant unwilling-to-perform. Slapd se terminera lorsque tous les clients auront fermé leurs connexions (s'ils le font un jour), ou - comme auparavant - s'il reçoit un signal SIGTERM. Ceci peut être utile si vous souhaitez arrêter le serveur et en démarrer un nouveau slapd avec une autre base de données, sans perturber les clients activement connectés. La valeur par défaut est off. Vous pourriez vouloir utiliser idletimeout avec cette option.
idletimeout <entier>
Spécifie le nombre de secondes à attendre avant de fermer de force une connexion client inactive. Une valeur de 0 désactive cette fonctionnalité. La valeur par défaut est 0. Vous pourriez également vouloir régler l'option writetimeout.
include <filename>
Lire des informations de configuration supplémentaires à partir du fichier donné avant de continuer avec la ligne suivante du fichier actuel.
index_hash64 { on | off }
Utiliser un hash de 64 bits pour l'indexation. Par défaut, on utilise des hashes de 32 bits. Ces hashes sont utilisés pour l'indexation d'égalité et de sous-chaîne. La version 64 bits peut être nécessaire pour éviter les collisions d'index lorsque le nombre de valeurs indexées dépasse ~64 millions. (Notez que l'indexation de sous-chaîne génère plusieurs valeurs d'index par valeur d'attribut réelle.) Les index générés avec des hashes de 32 bits sont incompatibles avec la version 64 bits, et vice versa. Les bases de données existantes doivent être complètement rechargées lors du changement de ce paramètre. Cette directive n'est prise en charge que sur les CPU 64 bits.
index_intlen <entier>
Spécifie la longueur de la clé pour les index d'entiers ordonnés. Les octets les plus significatifs de l'entier binaire seront utilisés pour les clés d'index. La valeur par défaut est 4, ce qui fournit une indexation exacte pour les valeurs de 31 bits. Une représentation en virgule flottante est utilisée pour indexer les valeurs trop grandes.
index_substr_if_maxlen <i
index_substr_if_maxlen <entier>
Spécifiez la longueur maximale pour les indices subinitial et subfinal. Seul ce nombre de caractères d'une valeur d'attribut sera traité par les fonctions d'indexation ; tout caractère excédentaire est ignoré. La valeur par défaut est 4.
index_substr_if_minlen <entier>
Spécifiez la longueur minimale pour les indices subinitial et subfinal. Une valeur d'attribut doit comporter au moins ce nombre de caractères pour être traitée par les fonctions d'indexation. La valeur par défaut est 2.
index_substr_any_len <entier>
Spécifiez la longueur utilisée pour les indices subany. Une valeur d'attribut doit comporter au moins ce nombre de caractères pour être traitée. Les valeurs d'attribut plus longues que cette longueur seront traitées par segments de cette longueur. La valeur par défaut est 4. L'indice subany sera également utilisé lors des recherches d'indices subinitial et subfinal lorsque la chaîne de filtre est plus longue que la valeur index_substr_if_maxlen.
index_substr_any_step <entier>
Spécifiez les pas utilisés dans les recherches d'indices subany. Cette valeur définit le décalage pour les segments d'une chaîne de filtre qui sont traités pour une recherche d'indice subany. La valeur par défaut est 2. Par exemple, avec les valeurs par défaut, une recherche utilisant le filtre "cn=*abcdefgh*" générerait des recherches d'indices pour "abcd", "cdef" et "efgh".

Note : La prise en charge de l'indexation dépend du backend spécifique utilisé. De plus, la modification de ces paramètres nécessitera généralement la suppression de tous les indices qui dépendent de ces paramètres et leur recréation avec slapindex(8).

ldapsyntax ( <oid> [DESC <description>] [X-SUBST <syntaxe-de-substitution>] )

Spécifiez une syntaxe LDAP en utilisant la syntaxe LDAPv3 définie dans la RFC 4512. L'analyseur slapd étend la définition de la RFC 4512 en autorisant des formes textuelles ainsi que des OID numériques pour l'OID de syntaxe. (Voir la description de objectidentifier.) L'analyseur slapd respecte également l'extension X-SUBST (une extension spécifique à OpenLDAP), qui permet d'utiliser l'instruction ldapsyntax pour définir une syntaxe non implémentée avec une autre syntaxe, la valeur d'extension syntaxe-de-substitution, comme son remplacement temporaire. La syntaxe-de-substitution doit être définie. Cela permet de définir des types d'attributs qui utilisent des syntaxes non implémentées en utilisant l'OID de syntaxe correct. Sauf si X-SUBST est utilisé, cette instruction de configuration entraînerait une erreur, car aucun gestionnaire ne serait associé à la structure de syntaxe résultante.
listener-threads <entier>
Spécifiez le nombre de threads à utiliser pour le gestionnaire de connexions. La valeur par défaut est 1 et elle est généralement suffisante pour jusqu'à 16 cœurs de processeur. La valeur doit être une puissance de 2.
localSSF <SSF>
Spécifie le facteur de force de sécurité (SSF) à attribuer aux sessions LDAP locales, telles que celles du gestionnaire ldapi://. Pour une description des valeurs SSF, voir la description de l'option minssf de sasl-secprops. La valeur par défaut est 71.
logfile <nom-de-fichier>
Spécifiez un fichier pour enregistrer les messages de débogage de slapd. Ces messages sont sans rapport avec les messages exposés par le paramètre de configuration loglevel. Ce réglage n'affecte que le démon slapd et n'a aucun effet sur les outils en ligne de commande. Par défaut, ces messages ne sont envoyés qu'à stderr et ne sont enregistrés nulle part ailleurs. La spécification d'un fichier journal copie les messages vers stderr et le fichier journal.
logfile-format debug|syslog-utc|syslog-localtime|rfc3339-utc
Spécifiez le format du préfixe pour les messages écrits dans le fichier journal. Le format debug est le format normal utilisé pour les messages de débogage de slapd, avec un horodatage en hexadécimal, suivi d'un identifiant de thread. Les autres options consistent à utiliser des préfixes de style syslog(3), avec des horodatages en UTC ou dans le fuseau horaire local. La valeur par défaut est le format debug.
logfile-only on | off
Spécifiez que les messages de débogage doivent uniquement être envoyés au fichier journal configuré, et non à stderr.
logfile-rotate <max> <Mbytes> <heures>
Spécifiez la rotation automatique du fichier journal configuré comme nombre maximum d'anciens fichiers journaux à conserver, une taille maximale en mégaoctets autorisée pour un fichier journal avant rotation, et un âge maximum en heures pour un fichier journal avant rotation. Le nombre maximum doit être compris entre 1 et 99. La définition de Mbytes ou heures à zéro désactive respectivement la vérification de taille ou d'âge. Au moins un des deux, Mbytes ou heures, doit être non nul. Par défaut, aucune rotation automatique n'est effectuée.
loglevel <entier> [...]
Spécifiez le niveau auquel les instructions de débogage et les statistiques d'opérations doivent être enregistrées par syslog (actuellement enregistrées dans la facility LOG_LOCAL4 de syslogd(8)). Elles doivent être considérées comme des sous-systèmes plutôt que comme des niveaux de journalisation de plus en plus verbeux. Certains messages de priorité plus élevée sont enregistrés indépendamment du loglevel configuré dès qu'une journalisation est configurée. Les niveaux de journalisation sont additifs, et les niveaux disponibles sont :
1
(0x1 trace) suivi des appels de fonction
2
(0x2 packets) débogage de la gestion des paquets
4
(0x4 args) débogage intensif (arguments de fonction)
8
(0x8 conns) gestion des connexions
16
(0x10 BER) affichage des paquets envoyés et reçus
32
(0x20 filter) traitement des filtres de recherche
64
(0x40 config) traitement du fichier de configuration
128
(0x80 ACL) traitement des listes de contrôle d'accès
256
(0x100 stats) connexions, opérations LDAP, résultats (recommandé)
512
(0x200 stats2) entrées de journal stats2 envoyées
1024
(0x400 shell) affichage de la communication avec les backends shell
2048
(0x800 parse) analyse des entrées
16384
(0x4000 sync) réplication LDAPSync
32768
(0x8000 none) uniquement les messages qui sont enregistrés quel que soit le niveau de journalisation défini
Le niveau de journalisation souhaité peut être saisi sous forme d'un seul entier combinant (par OU logique) les niveaux désirés, en notation décimale ou hexadécimale, sous forme d'une liste d'entiers (qui sont mis en OU logiquement), ou sous forme d'une liste des noms indiqués entre parenthèses, de telle sorte que 
    loglevel 129
    loglevel 0x81
    loglevel 128 1
    loglevel 0x80 0x1
    loglevel acl trace

soient équivalents. Le mot-clé any peut être utilisé comme raccourci pour activer la journalisation à tous les niveaux (équivalent à -1). Le mot-clé none, ou sa représentation entière équivalente, permet d'enregistrer les messages qui sont enregistrés indépendamment du niveau de journalisation configuré. En fait, si loglevel est défini sur 0, aucune journalisation n'a lieu, donc au moins le niveau none est requis pour que les messages de haute priorité soient enregistrés.

Notez que les niveaux packets, BER et parse ne sont disponibles que sous forme de sortie de débogage sur stderr, et ne sont pas envoyés à syslog.

Si slapd est compilé avec le support de la couche de sécurité du transport (Transport Layer Security), il existe d'autres options que vous pouvez spécifier.

TLSCipherSuite <spécification-suite-de-chiffrement>
Permet de configurer les chiffrements qui seront acceptés et l'ordre de préférence. <spécification-suite-de-chiffrement> doit être une spécification de chiffrement pour la bibliothèque TLS utilisée (OpenSSL ou GnuTLS). Exemple :
OpenSSL :

GnuTLS :

gnutls-cli -l

Contrôle si slapd maintiendra automatiquement l'attribut pwdLastSuccess pour les entrées. Par défaut, lastbind est désactivé.

Si lastbind est activé, spécifie la fréquence de mise à jour de pwdLastSuccess. Plus de integer secondes doivent s'être écoulées depuis le dernier bind réussi. Dans un environnement répliqué avec une activité de bind fréquente, il peut être utile de définir une valeur élevée.
limits <selector> <limit> [<limit> [...]]
Spécifie les limites de temps et de taille basées sur l'initiateur de l'opération ou le DN de base. L'argument <selector> peut être l'un des éléments suivants
anonymous | users | [<dnspec>=]<pattern> | group[/oc[/at]]=<pattern>
avec
<dnspec> ::= dn[.<type>][.<style>]
<type> ::= self | this
<style> ::= exact | base | onelevel | subtree | children | regex | anonymous
Le type de DN self est le défaut et signifie l'utilisateur authentifié, tandis que this signifie le DN de base de l'opération. Le terme anonymous correspond à tous les clients non authentifiés. Le terme users correspond à tous les clients authentifiés ; sinon, un motif de DN exact est supposé, sauf indication contraire en qualifiant la chaîne de clé (optionnelle) dn avec exact ou base (qui sont synonymes), pour exiger une correspondance exacte ; avec onelevel, pour exiger une correspondance de profondeur exactement un niveau ; avec subtree, pour autoriser une correspondance de profondeur de n'importe quel niveau, y compris la correspondance exacte ; avec children, pour autoriser une correspondance de profondeur de n'importe quel niveau, sans inclure la correspondance exacte ; regex exige explicitement le motif (par défaut) basé sur une expression régulière POSIX (''étendu''). Enfin, anonymous correspond aux opérations non liées ; le champ pattern est ignoré. Le même comportement est obtenu en utilisant la forme anonymous de la clause <selector>. Le terme group, avec les champs optionnels objectClass oc et attributeType at, suivi de pattern, définit les limites pour tout DN listé dans les valeurs de l'attribut at (par défaut member) de l'objectClass de groupe oc (par défaut groupOfNames) dont le DN correspond exactement à pattern.

Les limites actuellement prises en charge sont size et time.

La syntaxe des limites de temps est time[.{soft|hard}]=<integer>, où integer est le nombre de secondes que slapd passera à répondre à une requête de recherche. Si aucune limite de temps n'est explicitement demandée par le client, la limite soft est utilisée ; si la limite de temps demandée dépasse la limite hard, la valeur de la limite est utilisée à la place. Si la limite hard est définie sur le mot-clé soft, la limite soft est utilisée dans les deux cas ; si elle est définie sur le mot-clé unlimited, aucune limite hard n'est appliquée. Les requêtes explicites de limites de temps inférieures ou égales à la limite hard sont honorées. Si aucun spécificateur de limite n'est défini, la valeur est attribuée à la limite soft et la limite hard est définie sur soft, pour préserver le comportement d'origine.

La syntaxe des limites de taille est size[.{soft|hard|unchecked}]=<integer>, où integer est le nombre maximum d'entrées que slapd retournera en répondant à une requête de recherche. Si aucune limite de taille n'est explicitement demandée par le client, la limite soft est utilisée ; si la limite de taille demandée dépasse la limite hard, la valeur de la limite est utilisée à la place. Si la limite hard est définie sur le mot-clé soft, la limite soft est utilisée dans les deux cas ; si elle est définie sur le mot-clé unlimited, aucune limite hard n'est appliquée. Les requêtes explicites de limites de taille inférieures ou égales à la limite hard sont honorées. Le spécificateur unchecked définit une limite sur le nombre de candidats qu'une requête de recherche est autorisée à examiner. La raison d'être est que les recherches d'attributs mal indexés peuvent entraîner de grands ensembles de candidats, qui doivent être examinés par slapd(8) pour déterminer s'ils correspondent au filtre de recherche ou non. La limite unchecked fournit un moyen de supprimer de telles opérations avant même qu'elles ne commencent. Si les candidats sélectionnés dépassent la limite unchecked, la recherche sera abandonnée avec Unwilling to perform. Si elle est définie sur le mot-clé unlimited, aucune limite n'est appliquée (par défaut). Si elle est définie sur disabled, la recherche n'est même pas effectuée ; cela peut être utilisé pour interdire les recherches d'un ensemble spécifique d'utilisateurs. Si aucun spécificateur de limite n'est défini, la valeur est attribuée à la limite soft et la limite hard est définie sur soft, pour préserver le comportement d'origine.

En cas de non-correspondance, les limites globales sont utilisées. Les valeurs par défaut sont les mêmes que pour sizelimit et timelimit ; aucune limite n'est définie sur unchecked.

Si le contrôle pagedResults est demandé, la limite de taille hard est utilisée par défaut, car la demande d'une taille de page spécifique est considérée comme une demande explicite de limitation du nombre d'entrées à retourner. Cependant, la limite de taille s'applique au nombre total d'entrées retournées dans la recherche, et non à une seule page. Des limites de taille supplémentaires peuvent être appliquées ; la syntaxe est size.pr={<integer>|noEstimate|unlimited}, où integer est la taille de page maximale si aucune limite explicite n'est définie ; le mot-clé noEstimate empêche le serveur de retourner une estimation du nombre total d'entrées qui pourraient être retournées (note : l'implémentation actuelle ne retourne aucune estimation). Le mot-clé unlimited indique qu'aucune limite n'est appliquée à la taille de page du contrôle pagedResults. La syntaxe size.prtotal={<integer>|hard|unlimited|disabled} permet de définir une limite sur le nombre total d'entrées que le contrôle pagedResults retournera. Par défaut, elle est définie sur la limite hard qui utilisera la valeur size.hard. Lorsqu'elle est définie, integer est le nombre maximum d'entrées que la recherche entière avec le contrôle pagedResults peut retourner. Utilisez unlimited pour autoriser un nombre illimité d'entrées à retourner, par exemple pour permettre l'utilisation du contrôle pagedResults comme moyen de contourner les limitations de taille sur les recherches normales ; le mot-clé disabled désactive le contrôle, c'est-à-dire qu'aucun résultat paginé ne peut être retourné. Notez que le nombre total d'entrées retournées lorsque le contrôle pagedResults est demandé ne peut pas dépasser la limite de taille hard des recherches normales, sauf si elle est étendue par le commutateur prtotal.

L'instruction limits est généralement utilisée pour autoriser un nombre illimité d'entrées à être retournées par les recherches effectuées avec l'identité utilisée par le consommateur à des fins de synchronisation au moyen du protocole de synchronisation LDAP RFC 4533 (voir syncrepl pour plus de détails).

Lors de l'utilisation de bases de données subordonnées, il est nécessaire que toutes les limites qui doivent être appliquées à l'ensemble du parent et de ses subordonnés soient définies à la fois dans le parent et dans ses subordonnés. Sinon, les paramètres des bases de données subordonnées ne sont pas respectés.

Cette option met la base de données en mode « lecture seule ». Toute tentative de modification de la base de données retournera une erreur « unwilling to perform ». Par défaut, readonly est désactivé.
restrict <oplist>
Spécifiez une liste d'opérations séparées par des espaces qui sont restreintes. Les opérations peuvent être add, bind, compare, delete, extended[=<OID>], modify, rename, search, ou les pseudo-opérations spéciales read et write, qui résument respectivement les opérations de lecture et d'écriture. Si le rootdn se trouve dans un namingContext (suffixe) de la base de données, un mot de passe bind simple peut également être fourni à l'aide de la directive rootpw. L'utilisation de SASL est encouragée.

Spécifiez le suffixe DN des requêtes qui seront transmises à cette base de données backend. Plusieurs lignes de suffixe peuvent être fournies et au moins une est requise pour chaque définition de base de données.

Spécifiez que la base de données backend actuelle est subordonnée à une autre base de données backend. Une base de données subordonnée ne peut avoir qu'un seul suffixe. Cette option peut être utilisée pour lier plusieurs bases de données en un seul namingContext. Si le suffixe de la base de données actuelle se trouve dans le namingContext d'une base de données supérieure, les recherches effectuées sur la base de données supérieure seront également propagées à la subordonnée. Toutes les bases de données associées à un seul namingContext doivent avoir des rootdns identiques. Le comportement des autres opérations LDAP n'est pas affecté par ce paramètre. En particulier, il n'est pas possible d'utiliser moddn pour déplacer une entrée d'une subordonnée à une autre subordonnée au sein du namingContext.

En général, toutes les bases de données liées doivent être configurées aussi similairement que possible, car l'intention est de donner l'apparence d'un répertoire unique.

Cette configuration explicite est nécessaire, par exemple, lors de l'utilisation de la superposition syncprov, qui doit suivre glue pour fonctionner sur toutes les bases de données liées. Notez, cependant, que toutes les limites côté fournisseur pour l'identité de réplication seront appliquées par le fournisseur, quelles que soient les limites demandées par l'opération LDAP Content Synchronization, tout comme pour toute autre opération de recherche.

Le protocole LDAP Content Synchronization a deux types d'opérations. Dans l'opération refreshOnly, la prochaine opération de recherche de synchronisation est reprogrammée périodiquement à un intervalle de temps (spécifié par le paramètre interval ; 1 jour par défaut) après la fin de chaque opération de synchronisation. Dans l'opération refreshAndPersist, une recherche de synchronisation reste persistante dans le slapd fournisseur. Les mises à jour ultérieures du fournisseur généreront searchResultEntry pour le slapd consommateur en tant que réponses de recherche à la recherche de synchronisation persistante. Si la recherche initiale échoue en raison d'une erreur, la prochaine opération de recherche de synchronisation est reprogrammée périodiquement à un intervalle de temps (spécifié par le paramètre interval ; 1 jour par défaut)

En cas d'erreur lors de la réplication, le consommateur tentera de se reconnecter conformément au paramètre retry qui est une liste de paires <intervalle de nouvelle tentative> et <# de nouvelles tentatives>. Par exemple, retry="60 10 300 3" permet au consommateur de réessayer toutes les 60 secondes pour les 10 premières fois, puis de réessayer toutes les 300 secondes pour les 3 fois suivantes avant d'arrêter de réessayer. NAME

slapd.conf - OpenLDAP démon de configuration, syntaxe de fichier

SYNOPSIS

/etc/openldap/slapd.conf

DESCRIPTION

Le fichier de configuration de slapd, le démon de répertoire LDAP, est décrit ici. Ce fichier utilise un format textuel, où chaque ligne contient une directive et ses arguments. Les lignes commençant par # sont considérées comme des commentaires. Les directives peuvent apparaître plusieurs fois, sauf indication contraire.

Les chaînes de caractères peuvent être délimitées par des guillemets simples (') ou doubles ("). Les espaces blancs et les caractères de nouvelle ligne dans les chaînes délimitées par des guillemets sont préservés. Les guillemets et les barres obliques inverses dans les chaînes délimitées doivent être échappés avec une barre oblique inverse.

Les directives peuvent être regroupées logiquement, en utilisant des blocs database, frontend, ou access to. Ces blocs définissent la portée des directives qu'ils contiennent.

Ces options s'appliquent globalement au démon slapd.

Charge les directives à partir du fichier spécifié. Utile pour inclure des fichiers de schéma ou d'autres fichiers de configuration partiels.

Spécifie l'intervalle de nouvelle tentative en secondes et le nombre de tentatives. Si seule la valeur en secondes est fournie, elle est utilisée indéfiniment. L'absence de retry fait que syncrepl tente toutes les heures indéfiniment. La valeur 0 signifie un nombre indéfini de tentatives jusqu'au succès.
schemachecking {on|off}
Active ou désactive la vérification du schéma côté consommateur. Par défaut, elle est désactivée. L'activation de la vérification du schéma garantit que les entrées répliquées respectent les contraintes du schéma (objectClass, attributs requis/autorisés).
network-timeout secondes
Définit le temps d'attente pour établir une connexion réseau vers le fournisseur.
timeout secondes
Définit le temps d'attente pour la requête Bind initiale une fois la connexion établie.
tcp-user-timeout secondes
Définit l'option TCP_USER_TIMEOUT pour les connexions cibles, remplaçant le paramètre du système d'exploitation.
bindmethod {simple|sasl}
Méthode de liaison à utiliser pour se connecter au fournisseur. simple nécessite binddn et credentials. sasl nécessite saslmech et potentiellement authcid, credentials, authzid, secprops, realm.
keepalive idle [probes [interval]]
Configure les paramètres TCP keepalive pour maintenir les connexions actives.
starttls [critical]
Utilise l'opération étendue StartTLS pour établir une session TLS avant la liaison. L'argument critical rend la session non critique en cas d'échec de StartTLS.
suffixmassage vieil dn=nouveau dn
Permet de remplacer une partie du DN des entrées distantes par un DN local. Utile lorsque les suffixes des DN diffèrent entre le fournisseur et le consommateur.
syncdata {accesslog|changelog|default}
Spécifie le format du journal utilisé pour la réplication delta. accesslog pour le format d'accès, changelog pour l'ancien format de modification.
lazycommit {on|off}
Active/désactive le mode de validation paresseuse pour la base de données sous-jacente, ce qui peut améliorer les performances au détriment de la durabilité.

OPTIONS SPÉCIFIQUES À LA BASE DE DONNÉES

Chaque type de base de données peut autoriser des options de configuration spécifiques, qui sont documentées séparément dans les pages de manuel des backends. Voir la page de manuel slapd.backends(5) pour un aperçu des backends disponibles.

EXEMPLES

Voici un bref exemple de fichier de configuration :

include   /etc/openldap/schema/core.schema
pidfile   /var/lib/openldap/run/slapd.pid
# Sous-types de "name" (par ex., "cn" et "ou") avec
# l'option ";x-hidden" peuvent être recherchés/comparés,
# mais ne sont pas affichés. Voir slapd.access(5).
attributeoptions x-hidden lang-
access to attrs=name;x-hidden by * =cs
# Protéger les mots de passe. Voir slapd.access(5).
access    to attrs=userPassword  by * auth
# Accès en lecture aux autres attributs et entrées.
access    to *  by * read
database  mdb
suffix    "dc=our-domain,dc=com"
# Le répertoire de la base de données DOIT exister avant
# d'exécuter slapd ET ne devrait être accessible
# que par slapd/outils. Mode 0700 recommandé.
directory /var/lib/openldap/openldap-data
# Index à maintenir
index     objectClass  eq
index     cn,sn,mail   pres,eq,approx,sub
# Nous servons de petits clients qui ne gèrent pas les références,
# nous gérons donc les recherches distantes en leur nom.
database  ldap
suffix    ""
uri       ldap://ldap.some-server.com/
lastmod   off
