NOM

slapd-relay - backend relais pour slapd

SYNOPSIS

/etc/openldap/slapd.conf

DESCRIPTION

L'objectif principal de ce backend slapd(8) est de mapper un contexte de nommage défini dans une base de données exécutée dans la même instance slapd(8) dans un contexte de nommage virtuel, avec manipulation des attributs de type et des classes d'objets, si nécessaire. Il nécessite l'overlay slapo-rwm(5).

Ce backend et l'overlay mentionné ci-dessus sont expérimentaux.

CONFIGURATION

Les directives slapd.conf suivantes s'appliquent à la base de données backend relay. C'est-à-dire qu'elles doivent suivre une ligne "database relay" et précéder toute ligne "backend" ou "database" ultérieure. Les autres options de base de données sont décrites dans le manuel slapd.conf(5) ; seule la directive suffix est autorisée par le backend relay.

relay <contexte de nommage réel>
Le contexte de nommage de la base de données qui est présenté sous un contexte de nommage virtuel. La présence de cette directive implique qu'une base de données spécifique, c'est-à-dire celle qui sert le contexte de nommage réel, sera présentée sous un contexte de nommage virtuel.

MASSAGE

La base de données relay ne réécrit pas automatiquement le contexte de nommage des requêtes et des réponses. À cette fin, l'overlay slapo-rwm(5) doit être explicitement instancié et configuré comme il convient. Généralement, la directive rwm-suffixmassage suffit si seule la réécriture du contexte de nommage est requise.

RÈGLES D'ACCÈS

Un problème important est que les règles d'accès sont basées sur l'identité qui a émis l'opération. Après le massage du contexte virtuel vers le contexte réel, le frontend voit l'opération comme effectuée par l'identité dans le contexte réel. De plus, puisque back-relay court-circuite les opérations du frontend de la base de données réelle en les faisant passer par l'API interne du backend, les règles d'accès d'origine de la base de données ne s'appliquent pas, sauf dans des cas sélectionnés, c'est-à-dire lorsque le backend applique lui-même le contrôle d'accès. Par conséquent, les instances de la base de données relay doivent fournir leurs propres règles d'accès qui sont cohérentes avec celles de la base de données d'origine, en ajoutant éventuellement des restrictions spécifiques supplémentaires. Ainsi, les règles d'accès dans la base de données relay doivent faire référence aux identités dans le contexte de nommage réel. Des exemples sont rapportés dans la section EXEMPLES.

SCÉNARIOS

Si aucune directive relay n'est donnée, la base de données relay ne fait référence à aucune base de données spécifique, mais la base de données la plus appropriée est recherchée après réécriture du DN de la requête pour l'opération en cours.

Cela permet d'écrire des règles de réécriture soigneusement élaborées qui font que certaines requêtes sont dirigées vers une base de données, et d'autres vers une autre ; par exemple, l'authentification peut être mappée sur une base de données, et les recherches sur une autre, ou différentes bases de données cibles peuvent être sélectionnées en fonction du DN de la requête, etc.

Une autre possibilité est de mapper la même opération à différentes bases de données en fonction des détails du contexte de nommage virtuel, par exemple, les groupes sur une base de données et les personnes sur une autre.

EXEMPLES

Pour implémenter un mappage de contexte de nommage virtuel simple qui fait référence à une seule base de données, utilisez :

  database                relay
  suffix                  "dc=virtuel,dc=nommage,dc=contexte"
  relay                   "dc=reel,dc=nommage,dc=contexte"
  overlay                 rwm
  rwm-suffixmassage       "dc=reel,dc=nommage,dc=contexte"

Pour implémenter un mappage de contexte de nommage virtuel simple qui recherche le contexte de nommage réel pour chaque opération, utilisez :

  database                relay
  suffix                  "dc=virtuel,dc=nommage,dc=contexte"
  overlay                 rwm
  rwm-suffixmassage       "dc=reel,dc=nommage,dc=contexte"

Ceci est utile, par exemple, pour relayer différentes bases de données qui partagent la partie terminale du contexte de nommage (celle qui est réécrite).

Pour implémenter l'ancien suffixalias, par exemple, en mappant le contexte virtuel au contexte réel, mais pas les résultats du réel vers le virtuel, utilisez :

  database                relay
  suffix                  "dc=virtuel,dc=nommage,dc=contexte"
  relay                   "dc=reel,dc=nommage,dc=contexte"
  overlay                 rwm
  rwm-rewriteEngine       on
  rwm-rewriteContext      default
  rwm-rewriteRule         "dc=virtuel,dc=nommage,dc=contexte"
                          "dc=reel,dc=nommage,dc=contexte" ":@"
  rwm-rewriteContext      searchFilter
  rwm-rewriteContext      searchEntryDN
  rwm-rewriteContext      searchAttrDN
  rwm-rewriteContext      matchedDN

Notez que l'overlay slapo-rwm(5) est instancié, mais les règles de réécriture sont écrites explicitement, plutôt qu'automatiquement comme avec l'instruction rwm-suffixmassage, pour mapper tout le flux de données du virtuel vers le réel, mais aucun du réel vers le virtuel.

Règles d'accès :

  database                mdb
  suffix                  "dc=exemple,dc=com"
  # sauter...
  access to dn.subtree="dc=exemple,dc=com"
          by dn.exact="cn=Superviseur,dc=exemple,dc=com" write
          by * read
  database                relay
  suffix                  "o=Exemple,c=US"
  relay                   "dc=exemple,dc=com"
  overlay                 rwm
  rwm-suffixmassage       "dc=exemple,dc=com"
  # sauter ...
  access to dn.subtree="o=Exemple,c=US"
          by dn.exact="cn=Superviseur,dc=exemple,dc=com" write
          by dn.exact="cn=SuperviseurRelais,dc=exemple,dc=com" write
          by * read

Notez que, dans les deux bases de données, les identités (la clause <qui>) sont dans le contexte de nommage réel, c'est-à-dire `dc=example,dc=com', tandis que les cibles (la clause <quoi>) sont dans le contexte réel et dans le contexte virtuel, respectivement.

CONTRÔLE D'ACCÈS

Le backend relay n'honore aucune des sémantiques de contrôle d'accès décrites dans slapd.access(5) ; tout le contrôle d'accès est délégué à la (aux) base(s) de données relayée(s). Seul l'accès en lecture (=r) à l'attribut pseudo-entry et aux valeurs des autres attributs des entrées renvoyées par l'opération search est honoré, ce qui est effectué par le frontend.

FICHIERS

/etc/openldap/slapd.conf
fichier de configuration slapd par défaut

VOIR AUSSI

slapd.conf(5), slapd-config(5), slapo-rwm(5), slapd(8).
