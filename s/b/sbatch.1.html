sbatch(1) Commandes Slurm sbatch(1)

NOM

sbatch - Soumettre un script de batch à Slurm.

SYNTAXE

sbatch [OPTIONS(0)...] [ : [OPTIONS(N)...]] script(0) [args(0)...]

L'option(s) définissent plusieurs travaux dans un travail hétérogène co-planifié. Pour plus de détails sur les travaux hétérogènes, consultez le document
https://slurm.schedmd.com/heterogeneous_jobs.html

DESCRIPTION

sbatch soumet un script de batch à Slurm. Le script de batch peut être fourni à sbatch via un nom de fichier sur la ligne de commande, ou si aucun nom de fichier n'est spécifié, sbatch lira un script depuis l'entrée standard.

Le script de batch peut contenir une ou plusieurs lignes commençant par "#SBATCH" suivies de l'une des options CLI documentées sur cette page. Les directives #SBATCH sont lues directement par Slurm, de sorte que la syntaxe spécifique au shell, y compris les noms de variables, sera lue comme du texte littéral. Une fois la première ligne non commentée et sans espace blanc atteinte dans le script, plus aucune directive #SBATCH ne sera traitée. Voir l'exemple ci-dessous.

sbatch se termine immédiatement après le transfert réussi du script au contrôleur Slurm et l'attribution d'un ID de travail Slurm. Le script de batch ne se voit pas nécessairement attribuer de ressources immédiatement, il peut rester dans la file d'attente des travaux en attente pendant un certain temps avant que ses ressources requises ne deviennent disponibles.

Par défaut, la sortie standard et l'erreur standard sont dirigées vers un fichier du nom "slurm-%j.out", où "%j" est remplacé par le numéro d'allocation du travail. Le fichier sera généré sur le premier nœud de l'allocation du travail. À l'exception du script de batch lui-même, Slurm ne déplace aucun fichier utilisateur.

Lorsque l'allocation du travail est finalement accordée pour le script de batch, Slurm exécute une seule copie du script de batch sur le premier nœud de l'ensemble des nœuds alloués.

Le document suivant décrit l'influence de diverses options sur l'allocation des CPU aux travaux et aux tâches.
https://slurm.schedmd.com/cpu_management.html

VALEUR DE RETOUR

sbatch retournera 0 en cas de succès ou un code d'erreur en cas d'échec.

RESOLUTION DU CHEMIN DU SCRIPT

Le script de batch est résolu dans l'ordre suivant :

1. Si le script commence par ".", le chemin est construit comme suit : répertoire de travail actuel / script
2. Si le script commence par "/", le chemin est considéré comme absolu.
3. Si le script se trouve dans le répertoire de travail actuel.
4. Si le script peut être résolu via le PATH. Voir path_resolution(7).

Le répertoire de travail actuel est le répertoire de travail du processus appelant, sauf si l'argument --chdir est passé, ce qui remplacera le répertoire de travail actuel.

OPTIONS

-A, --account=<compte>
Imputer les ressources utilisées par ce travail au compte spécifié. Le compte est une chaîne de caractères arbitraire. Le nom du compte peut être modifié après la soumission du travail à l'aide de la commande scontrol.
--acctg-freq=<datatype>=<intervalle>[,<datatype>=<intervalle>...]
Définir les intervalles d'échantillonnage de la comptabilité et du profilage du travail en secondes. Ceci peut être utilisé pour remplacer le paramètre JobAcctGatherFrequency dans le fichier slurm.conf. <datatype>=<intervalle> spécifie l'intervalle d'échantillonnage des tâches pour le plugin jobacct_gather ou un intervalle d'échantillonnage pour un type de profilage par le plugin acct_gather_profile. Plusieurs paires <datatype>=<intervalle> séparées par des virgules peuvent être spécifiées. Les valeurs de datatype prises en charge sont :
tache
Intervalle d'échantillonnage pour les plugins jobacct_gather et pour le profilage des tâches par le plugin acct_gather_profile.
NOTE : Cette fréquence est utilisée pour surveiller l'utilisation de la mémoire. Si des limites de mémoire sont appliquées, la fréquence la plus élevée qu'un utilisateur puisse demander est celle configurée dans le fichier slurm.conf. Elle ne peut pas être désactivée.
energie
Intervalle d'échantillonnage pour le profilage de l'énergie à l'aide du plugin acct_gather_energy.
reseau
Intervalle d'échantillonnage pour le profilage infiniband à l'aide du plugin acct_gather_interconnect.
système_de_fichiers
Intervalle d'échantillonnage pour le profilage du système de fichiers à l'aide du plugin acct_gather_filesystem.

La valeur par défaut pour l'intervalle d'échantillonnage des tâches est de 30 secondes. La valeur par défaut pour tous les autres intervalles est de 0. Un intervalle de 0 désactive l'échantillonnage du type spécifié. Si l'intervalle d'échantillonnage des tâches est de 0, les informations de comptabilité ne sont collectées qu'à la fin du travail (réduisant l'interférence de Slurm avec le travail).
Des valeurs plus petites (non nulles) ont un impact plus important sur les performances du travail, mais une valeur de 30 secondes n'est pas susceptible d'être remarquée pour les applications comportant moins de 10 000 tâches.

-a, --array=<index>
Soumettre un tableau de travaux, plusieurs travaux à exécuter avec des paramètres identiques. La spécification des index identifie quelles valeurs d'index de tableau doivent être utilisées. Plusieurs valeurs peuvent être spécifiées en utilisant une liste séparée par des virgules et/ou une plage de valeurs avec un séparateur "-". Par exemple, "--array=0-15" ou "--array=0,6,16-32". Une fonction de pas peut également être spécifiée avec un suffixe contenant un deux-points et un nombre. Par exemple, "--array=0-15:4" équivaut à "--array=0,4,8,12". Un nombre maximum de tâches simultanément actives provenant du tableau de travaux peut être spécifié à l'aide d'un séparateur "%". Par exemple, "--array=0-15%4" limitera le nombre de tâches simultanément actives de ce tableau de travaux à 4. La valeur minimale de l'index est 0. La valeur maximale est inférieure de un à la valeur du paramètre de configuration MaxArraySize. NOTE : Actuellement, les tableaux de travaux fédérés ne s'exécutent que sur le cluster local.
--batch=<liste>
Les nœuds peuvent avoir des caractéristiques (features) qui leur sont attribuées par l'administrateur Slurm. Les utilisateurs peuvent spécifier quelles de ces caractéristiques sont requises par leur script de batch en utilisant cette option. Par exemple, l'allocation d'un travail peut inclure des nœuds Intel Haswell et KNL avec les caractéristiques "haswell" et "knl" respectivement. Dans une telle configuration, le script de batch bénéficierait normalement de l'exécution sur un nœud Haswell plus rapide. Ceci serait spécifié en utilisant l'option "--batch=haswell". La spécification peut inclure des opérateurs ET et OU en utilisant les séparateurs ampersand et barre verticale. Par exemple : "--batch=haswell|broadwell" ou "--batch=haswell|big_memory". L'argument --batch doit être un sous-ensemble de l'argument --constraint=<liste> du travail (c'est-à-dire que le travail ne peut pas demander uniquement des nœuds KNL, mais exiger que le script s'exécute sur un nœud Haswell). Si la demande ne peut pas être satisfaite par les ressources allouées au travail, le script de batch s'exécutera sur le premier nœud de l'allocation du travail.
--bb=<spec>
Spécification du burst buffer. La forme de la spécification dépend du système. Voir également --bbf. Lorsque l'option --bb est utilisée, Slurm analyse cette option et crée un fichier script temporaire de burst buffer qui est utilisé en interne par les plugins de burst buffer. Voir le guide du burst buffer de Slurm pour plus d'informations et des exemples.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

s:
https://slurm.schedmd.com/burst_buffer.html
--bbf=<nom_fichier>
Chemin du fichier contenant la spécification du burst buffer. La forme de la spécification dépend du système. Ces directives de burst buffer seront insérées dans le script batch soumis. Voir le guide burst buffer de Slurm pour plus d'informations et d'exemples :
https://slurm.schedmd.com/burst_buffer.html
-b, --begin=<heure>
Soumet le script batch au contrôleur Slurm immédiatement, comme d'habitude, mais indique au contrôleur de différer l'allocation du travail jusqu'à l'heure spécifiée.

L'heure peut être de la forme HH:MM:SS pour exécuter un travail à une heure spécifique de la journée (les secondes sont facultatives). (Si cette heure est déjà passée, le jour suivant est supposé.) Vous pouvez également spécifier midnight, noon, elevenses (11h), fika (15h) ou teatime (16h) et vous pouvez avoir une heure de la journée suffixée par AM ou PM pour une exécution le matin ou le soir. Vous pouvez également indiquer le jour où le travail sera exécuté, en spécifiant une date sous la forme MMJJAA ou MM/JJ/AA AAAA-MM-JJ. Combinez la date et l'heure en utilisant le format suivant AAAA-MM-JJ[THH:MM[:SS]]. Vous pouvez également donner des heures comme now + count time-units, où les time-units peuvent être seconds (par défaut), minutes, hours, days, ou weeks et vous pouvez dire à Slurm d'exécuter le travail aujourd'hui avec le mot-clé today et d'exécuter le travail demain avec le mot-clé tomorrow. La valeur peut être modifiée après la soumission du travail en utilisant la commande scontrol. Par exemple :

   --begin=16:00
   --begin=now+1hour
   --begin=now+60           (secondes par défaut)
   --begin=2010-01-20T12:34:00

Notes sur les spécifications de date/heure :
- Bien que le champ 'secondes' de la spécification horaire HH:MM:SS soit autorisé par le code, notez que la fréquence de sondage du planificateur Slurm n'est pas assez précise pour garantir la mise en service du travail à la seconde près. Le travail sera éligible pour commencer lors du prochain sondage suivant l'heure spécifiée. L'intervalle de sondage exact dépend du planificateur Slurm (par exemple, 60 secondes avec la configuration par défaut sched/builtin).
- Si aucune heure (HH:MM:SS) n'est spécifiée, la valeur par défaut est (00:00:00).
- Si une date est spécifiée sans année (par exemple, MM/JJ), l'année en cours est supposée, sauf si la combinaison de MM/JJ et HH:MM:SS est déjà passée pour cette année, auquel cas l'année suivante est utilisée.

-D, --chdir=<répertoire>
Définit le répertoire de travail du script batch à répertoire avant son exécution. Le chemin peut être spécifié comme un chemin absolu ou un chemin relatif au répertoire où la commande est exécutée.
--cluster-constraint=[!]<liste>
Spécifie les caractéristiques qu'un cluster fédéré doit posséder pour qu'un travail frère lui soit soumis. Slurm tentera de soumettre un travail frère à un cluster s'il possède au moins une des caractéristiques spécifiées. Si l'option "!" est incluse, Slurm tentera de soumettre un travail frère à un cluster qui ne possède aucune des caractéristiques spécifiées.
-M, --clusters=<chaîne>
Clusters auxquels adresser les commandes. Plusieurs noms de clusters peuvent être séparés par des virgules. Le travail sera soumis au cluster offrant le temps d'initiation du travail prévu le plus tôt. La valeur par défaut est le cluster actuel. Une valeur de 'all' interrogera tous les clusters pour une exécution. Notez l'option --export pour contrôler les variables d'environnement exportées entre les clusters. Notez que le slurmdbd doit être actif pour que cette option fonctionne correctement, sauf si vous exécutez dans une fédération avec FederationParameters=fed_display configuré.
--comment=<chaîne>
Un commentaire arbitraire entre guillemets s'il contient des espaces ou des caractères spéciaux.
--consolidate-segments
Garantit que tous les segments de l'allocation seront consolidés en un bloc agrégé de niveau supérieur.

Cette option s'applique aux allocations de travaux. NOTE : Cette option ne fonctionnera qu'avec le plugin topology/block.

-C, --constraint=<liste>
Les nœuds peuvent avoir des caractéristiques qui leur sont attribuées par l'administrateur Slurm. Les utilisateurs peuvent spécifier quelles sont ces caractéristiques requises par leur travail en utilisant l'option de contrainte. Si vous recherchez des contraintes 'douces', veuillez consulter --prefer pour plus d'informations. Seuls les nœuds ayant des caractéristiques correspondant aux contraintes du travail seront utilisés pour satisfaire la demande. Plusieurs contraintes peuvent être spécifiées avec ET, OU, OU correspondant, décomptes de ressources, etc. (certains opérateurs ne sont pas pris en charge sur tous les types de systèmes).

NOTE : Les caractéristiques modifiables sont des caractéristiques définies par un plugin NodeFeatures.

Les options --constraint prises en charge incluent :

Nom Unique
Seuls les nœuds possédant la caractéristique spécifiée seront utilisés. Par exemple, --constraint="intel"
Nombre de Nœuds
Une demande peut spécifier le nombre de nœuds nécessaires avec une certaine caractéristique en ajoutant un astérisque et un nombre après le nom de la caractéristique. Par exemple, --nodes=16 --constraint="graphics*4" indique que le travail nécessite 16 nœuds et qu'au moins quatre de ces nœuds doivent avoir la caractéristique "graphics". Si vous demandez plus d'une caractéristique et utilisez des décomptes de nœuds, la demande doit être entourée de crochets.

NOTE : Cette option n'est pas prise en charge par le plugin helpers NodeFeatures. Les travaux hétérogènes peuvent être utilisés à la place.

ET
Seuls les nœuds possédant toutes les caractéristiques spécifiées seront utilisés. L'esperluette est utilisée pour un opérateur ET. Par exemple, --constraint="intel&gpu"
OU
Seuls les nœuds possédant au moins une des caractéristiques spécifiées seront utilisés. La barre verticale est utilisée pour un opérateur OU. Si des caractéristiques modifiables ne sont pas demandées, les nœuds de l'allocation peuvent avoir des caractéristiques différentes. Par exemple, salloc -N2 --constraint="intel|amd" peut entraîner une allocation de travail où un nœud a la caractéristique intel et l'autre nœud a la caractéristique amd. Cependant, si l'expression contient une caractéristique modifiable, alors tous les opérateurs OU sont automatiquement traités comme des OU correspondants afin que tous les nœuds de l'allocation de travail aient le même ensemble de caractéristiques. Par exemple, salloc -N2 --constraint="foo|bar&baz" Le travail est alloué sur deux nœuds où les deux nœuds ont foo, ou bar et baz (un ou les deux nœuds peuvent avoir foo, bar et baz). Le plugin helpers NodeFeatures trouvera le premier ensemble de caractéristiques de nœuds qui correspond à tous les nœuds de l'allocation de travail ; ces caractéristiques sont définies comme caractéristiques actives sur le nœud et transmises à RebootProgram (voir slurm.conf(5)) et au script helper (voir helpers.conf(5)). Dans ce cas, le plugin helpers utilise le premier des "foo" ou "bar,baz" qui correspond aux deux nœuds de l'allocation de travail.
OU Correspondant
Si une seule option parmi un ensemble d'options possibles doit être utilisée pour tous les nœuds alloués, utilisez alors l'opérateur OU et entourez les options de crochets. Par exemple, --constraint="[rack1|rack2|rack3|rack4]" pourrait être utilisé pour spécifier que tous les nœuds doivent être alloués sur un seul rack du cluster, mais n'importe lequel de ces quatre racks peut être utilisé.
Décomptes Multiples
Des décomptes spécifiques de plusieurs ressources peuvent être spécifiés en utilisant l'opérateur ET et en entourant les options de crochets. Par exemple, --constraint="[rack1*2&rack2*4]" pourrait être utilisé pour spécifier que deux nœuds doivent être alloués parmi les nœuds ayant la caractéristique "rack1" et quatre nœuds doivent être alloués parmi les nœuds ayant la caractéristique "rack2".

NOTE : Cette option n'est pas prise en charge par le plugin helpers NodeFeatures.

NOTE : Les décomptes multiples peuvent entraîner l'allocation de travaux avec une disposition réseau non optimale.

Crochets
Les crochets peuvent être utilisés pour indiquer que vous recherchez un ensemble de nœuds avec différentes exigences contenues dans les crochets. Par exemple, --constraint="[(rack1|rack2)*1&(rack3)*2]" vous obtiendra un nœud avec la caractéristique "rack1" ou "rack2" et deux nœuds avec la caractéristique "rack3". Si vous demandez plus d'une caractéristique et utilisez des décomptes de nœuds, la demande doit être entourée de crochets.

NOTE : Les crochets sont réservés uniquement à la syntaxe Décomptes Multiples et OU Correspondant. Les opérateurs ET nécessitent un décompte pour chaque caractéristique à l'intérieur des crochets (c'est-à-dire "[quad*2&hemi*1]"). Slurm n'autorisera qu'un seul ensemble de contraintes entre crochets par travail.

PAS

E : Les crochets ne sont pas pris en charge par les extensions NodeFeatures des assistants. Une correspondance OU peut être demandée sans crochets en utilisant le caractère de barre verticale avec au moins une fonctionnalité modifiable.

Parenthèses
Les parenthèses peuvent être utilisées pour regrouper des fonctionnalités de nœuds similaires. Par exemple, --constraint="[(knl&snc4&flat)*4&haswell*1]" pourrait être utilisé pour spécifier que quatre nœuds avec les fonctionnalités "knl", "snc4" et "flat" plus un nœud avec la fonctionnalité "haswell" sont requis. Les parenthèses peuvent également être utilisées pour regrouper des opérations. Sans parenthèses, les fonctionnalités des nœuds sont analysées strictement de gauche à droite. Par exemple, --constraint="foo&bar|baz" demande des nœuds avec foo et bar, ou baz. --constraint="foo|bar&baz" demande des nœuds avec foo et baz, ou bar et baz (notez comment baz a été mis en AND avec tout). --constraint="foo&(bar|baz)" demande des nœuds avec foo et au moins l'un de bar ou baz. NOTE : OU à l'intérieur des parenthèses ne doit pas être utilisé avec une extension NodeFeatures KNL, mais est pris en charge par l'extension NodeFeatures des assistants.
--container=<chemin_vers_conteneur>
Chemin absolu vers le bundle de conteneur OCI.
--container-id=<id_conteneur>
Nom unique pour le conteneur OCI.
--contiguous
S'il est défini, les nœuds alloués doivent former un ensemble contigu.

NOTE : Cette option ne fonctionnera qu'avec le plugin topology/flat. Les autres plugins de topologie modifient l'ordre des nœuds et empêchent cette option de prendre effet.

-S, --core-spec=<nombre>
Nombre de cœurs spécialisés par nœud réservés par le travail pour les opérations système et non utilisés par l'application. Si AllowSpecResourcesUsage est activé, un travail peut remplacer le CoreSpecCount de tous ses nœuds alloués avec cette option. Les cœurs spécialisés remplacés resteront réservés aux processus système. Le travail recevra une allocation --exclusive implicite pour le reste des cœurs sur les nœuds, ce qui permettra aux processus du travail d'utiliser (et d'être facturés pour) tous les cœurs des nœuds, à l'exception des cœurs spécialisés remplacés. Cette option ne peut pas être utilisée avec l'option --thread-spec.

NOTE : La définition explicite de la valeur des cœurs spécialisés d'un travail active implicitement l'option --exclusive.

--cores-per-socket=<cœurs>
Restreindre la sélection des nœuds aux nœuds ayant au moins le nombre spécifié de cœurs par socket. Voir des informations supplémentaires sous l'option -B ci-dessus lorsque le plugin task/affinity est activé.
NOTE : Cette option peut implicitement définir le nombre de tâches (si -n n'a pas été spécifié) comme une tâche par thread demandé.
--cpu-freq=<p1>[-p2][:p3]

Demander que les étapes de travail initiées par les commandes srun dans ce script sbatch soient exécutées à une fréquence demandée si possible, sur les CPU sélectionnés pour l'étape sur le(s) nœud(s) de calcul.

p1 peut être [#### | low | medium | high | highm1] ce qui définira la vitesse de mise à l'échelle de fréquence (scaling_speed) à la valeur correspondante, et définira le gouverneur de fréquence (scaling_governor) sur UserSpace. Voir ci-dessous pour la définition des valeurs.

p1 peut être [Conservative | OnDemand | Performance | PowerSave] ce qui définira le gouverneur sur la valeur correspondante. Le gouverneur doit être dans la liste définie par l'option slurm.conf CpuFreqGovernors.

Lorsque p2 est présent, p1 sera la fréquence minimale de mise à l'échelle et p2 sera la fréquence maximale de mise à l'échelle. Dans ce cas, le gouverneur p3 ou CpuFreqDef ne peut pas être UserSpace puisqu'il ne prend pas en charge une plage.

p2 peut être [#### | medium | high | highm1]. p2 doit être supérieur à p1 et est incompatible avec le gouverneur UserSpace.

p3 peut être [Conservative | OnDemand | Performance | PowerSave | SchedUtil | UserSpace] ce qui définira le gouverneur sur la valeur correspondante.

Si p3 est UserSpace, la vitesse de mise à l'échelle de fréquence (scaling_speed), la fréquence maximale de mise à l'échelle (scaling_max_freq) et la fréquence minimale de mise à l'échelle (scaling_min_freq) seront définies statiquement à la valeur définie par p1.

Toute fréquence demandée inférieure à la fréquence minimale disponible sera arrondie à la fréquence minimale disponible. De même, toute fréquence demandée supérieure à la fréquence maximale disponible sera arrondie à la fréquence maximale disponible.

Le paramètre CpuFreqDef dans slurm.conf sera utilisé pour définir le gouverneur en l'absence de p3. S'il n'y a pas de CpuFreqDef, le gouverneur par défaut utilisera le gouverneur système actuel défini pour chaque cpu. La spécification d'une plage sans CpuFreqDef ou d'un gouverneur spécifique n'est donc pas autorisée.

Les valeurs acceptables à l'heure actuelle incluent :

####
fréquence en kilohertz
Low
la fréquence la plus basse disponible
High
la fréquence la plus élevée disponible
HighM1
(high moins un) sélectionnera la fréquence disponible la plus élevée suivante
Medium
tente de définir une fréquence au milieu de la plage disponible
Conservative
tente d'utiliser le gouverneur CPU Conservative
OnDemand
tente d'utiliser le gouverneur CPU OnDemand (la valeur par défaut)
Performance
tente d'utiliser le gouverneur CPU Performance
PowerSave
tente d'utiliser le gouverneur CPU PowerSave
UserSpace
tente d'utiliser le gouverneur CPU UserSpace

La variable d'environnement informative suivante est définie dans l'étape de travail lorsque l'option --cpu-freq est demandée.

        SLURM_CPU_FREQ_REQ

Cette variable d'environnement peut également être utilisée pour fournir la valeur de la demande de fréquence CPU si elle est définie lorsque la commande 'srun' est émise. L'option --cpu-freq sur la ligne de commande remplacera la valeur de la variable d'environnement. Le format sur la variable d'environnement est le même que sur la ligne de commande. Voir la section VARIABLES D'ENVIRONNEMENT pour une description de la variable SLURM_CPU_FREQ_REQ.

NOTE : Ce paramètre est traité comme une demande, pas une exigence. Si le nœud de l'étape de travail ne prend pas en charge la définition de la fréquence CPU, ou si la valeur demandée est en dehors des limites des fréquences légales, une erreur est enregistrée, mais l'étape de travail est autorisée à continuer.

NOTE : La définition de la fréquence pour les CPU de l'étape de travail uniquement implique que les tâches sont confinées à ces CPU. Si le confinement des tâches (c'est-à-dire si le plugin TaskPlugin task/affinity est activé, ou si le plugin TaskPlugin task/cgroup est activé avec "ConstrainCores=yes" défini dans cgroup.conf) n'est pas configuré, ce paramètre est ignoré.

NOTE : Lorsque l'étape se termine, la fréquence et le gouverneur de chaque CPU sélectionné sont réinitialisés à leurs valeurs précédentes.

NOTE : Lors de la soumission de travaux avec l'option --cpu-freq avec linuxproc comme ProctrackType, cela peut entraîner une exécution trop rapide des travaux avant que la comptabilité ne puisse interroger les informations du travail. Par conséquent, toutes les informations de comptabilité ne seront pas présentes.

--cpus-per-gpu=<ncpu>
Demander que ncpu processeurs soient alloués par GPU alloué. Les étapes héritant de cette valeur impliqueront --exact. Non compatible avec l'option --cpus-per-task.
-c, --cpus-per-task=<ncpu>
Indiquer au contrôleur Slurm que les étapes de travail suivantes nécessiteront ncpu processeurs par tâche. Sans cette option, le contrôleur tentera simplement d'allouer un processeur par tâche.

Par exemple, considérons une application qui a 4 tâches, chacune nécessitant 3 processeurs. Si notre cluster est composé de nœuds quad-processeurs et que nous demandons simplement 12 processeurs, le contrôleur pourrait nous donner seulement 3 nœuds. Cependant, en utilisant l'option --cpus-per-task=3, le contrôleur sait que chaque tâche nécessite 3 processeurs sur le même nœud, et le contrôleur accordera une allocation de 4 nœuds, un pour chacune des 4 tâches.

--deadline=<OPT>
Supprimer le travail s'il n'est pas possible d'y mettre fin avant cette échéance (début > (échéance - temps[-min])). Par défaut, il n'y a pas d'échéance. Notez que si ni DefaultTime ni MaxTime ne sont configurés sur la partition dans laquelle se trouve le travail, le travail devra spécifier une forme de limite de temps. Les formats de temps valides sont :
HH:MM[:SS] [AM|PM]
MMDD[YY] ou MM/DD[/YY] ou MM.DD[.YY]

AAAA-MM-JJ[THH:MM[:SS]]

--delay-boot=<minutes>
Ne pas redémarrer les nœuds pour satisfaire la spécification de fonctionnalité de ce travail si le travail est éligible pour s'exécuter depuis moins de cette période. Si le travail a attendu moins que la période spécifiée, il utilisera uniquement les nœuds qui ont déjà les fonctionnalités spécifiées. L'argument est en unités de minutes. Une valeur par défaut peut être définie par un administrateur système en utilisant l'option delay_boot du paramètre de configuration SchedulerParameters dans le fichier slurm.conf, sinon la valeur par défaut est zéro (pas de délai).
-d, --dependency=<liste_dépendances>
Reporter le début de ce travail jusqu'à ce que les dépendances spécifiées soient satisfaites. Une fois une dépendance satisfaite, elle est supprimée du travail. <liste_dépendances> est de la forme <type:job_id[:job_id][,type:job_id[:job_id]]> ou <type:job_id[:job_id][?type:job_id[:job_id]]>. Toutes les dépendances doivent être satisfaites si le séparateur "," est utilisé. N'importe quelle dépendance peut être satisfaite si le séparateur "?" est utilisé. Un seul séparateur peut être utilisé. Par exemple : 
-d afterok:20:21,afterany:23
signifie que le travail ne peut s'exécuter qu'après un code de retour 0 des travaux 20 et 21 ET l'achèvement du travail 23. Cependant : 
-d afterok:20:21?afterany:23
signifie que l'une des conditions (afterok:20 OU afterok:21 OU afterany:23) suffira à libérer le travail. Plusieurs travaux peuvent partager la même dépendance et ces travaux peuvent même appartenir à des utilisateurs différents. La valeur peut être modifiée après la soumission du travail en utilisant la commande scontrol. Les dépendances sur des travaux distants sont autorisées dans une fédération. Une fois qu'une dépendance de travail échoue en raison de l'état de terminaison d'un travail précédent, le travail dépendant ne sera jamais exécuté, même si le travail précédent est remis en file d'attente et a un état de terminaison différent lors d'une exécution ultérieure.
after:job_id[[+time][:jobid[+time]...]]
Après le démarrage ou l'annulation des travaux spécifiés et 'time' en minutes après le démarrage ou l'annulation, ce travail peut commencer son exécution. Si aucun 'time' n'est donné, il n'y a pas de délai après le démarrage ou l'annulation.
afterany:job_id[:jobid...]
Ce travail peut commencer son exécution après la terminaison des travaux spécifiés. C'est le type de dépendance par défaut.
afterburstbuffer:job_id[:jobid...]
Ce travail peut commencer son exécution après la terminaison des travaux spécifiés et que toutes les opérations de sortie de buffer éclaté associées soient terminées.
aftercorr:job_id[:jobid...]
Une tâche de ce tableau de tâches peut commencer son exécution après que la tâche correspondante ID dans le travail spécifié ait terminé avec succès (exécuté jusqu'à la fin avec un code de sortie zéro). Si le travail spécifié n'est pas un tableau, cela est traité de la même manière qu'afterok.
afternotok:job_id[:jobid...]
Ce travail peut commencer son exécution après la terminaison des travaux spécifiés dans un état d'échec (code de sortie non nul, échec de nœud, dépassement de délai, etc.). Ce travail doit être soumis pendant que le travail spécifié est toujours actif ou dans les MinJobAge secondes après la fin du travail spécifié. Si l'ID du travail dépendant n'est pas trouvé et se trouve sur le même cluster que la soumission du travail, le travail est rejeté. Si l'ID du travail dépendant n'est pas trouvé et se trouve sur un cluster différent de celui de la soumission du travail, la dépendance est marquée comme échouée.
afterok:job_id[:jobid...]
Ce travail peut commencer son exécution après que les travaux spécifiés se soient exécutés avec succès (exécutés jusqu'à la fin avec un code de sortie zéro). Ce travail doit être soumis pendant que le travail spécifié est toujours actif ou dans les MinJobAge secondes après la fin du travail spécifié. Si l'ID du travail dépendant n'est pas trouvé et se trouve sur le même cluster que la soumission du travail, le travail est rejeté. Si l'ID du travail dépendant n'est pas trouvé et se trouve sur un cluster différent de celui de la soumission du travail, la dépendance est marquée comme échouée.
singleton
Ce travail peut commencer son exécution après que tous les travaux précédemment lancés partageant le même nom de travail et le même utilisateur se soient terminés. Autrement dit, un seul travail portant ce nom et appartenant à cet utilisateur peut être en cours d'exécution ou suspendu à tout moment. Dans une fédération, une dépendance singleton doit être satisfaite sur tous les clusters, sauf si DependencyParameters=disable_remote_singleton est utilisé dans slurm.conf.
-m, --distribution={*|block|cyclic|arbitrary|plane=<taille>}[:{*|block|cyclic|fcyclic}[:{*|block|cyclic|fcyclic}]][,{Pack|NoPack}]

Spécifiez des méthodes de distribution alternatives pour les processus distants. Pour l'allocation de travaux, cela définit des variables d'environnement qui seront utilisées par les requêtes srun ultérieures et affecte également quels cœurs seront sélectionnés pour l'allocation de travaux.

Cette option contrôle la distribution des tâches aux nœuds sur lesquels les ressources ont été allouées, et la distribution de ces ressources aux tâches pour le liaison (affinité des tâches). La première méthode de distribution (avant le premier ":") contrôle la distribution des tâches aux nœuds. La deuxième méthode de distribution (après le premier ":") contrôle la distribution des CPUs alloués sur les sockets pour la liaison aux tâches. La troisième méthode de distribution (après le second ":") contrôle la distribution des CPUs alloués sur les cœurs pour la liaison aux tâches. Les deuxième et troisième distributions s'appliquent uniquement si l'affinité des tâches est activée. La troisième distribution n'est prise en charge que si le plugin task/cgroup est configuré. La valeur par défaut de chaque type de distribution est spécifiée par *.

Notez qu'avec select/cons_tres, le nombre de CPUs alloués à chaque socket et nœud peut être différent. Référez-vous à https://slurm.schedmd.com/mc_support.html pour plus d'informations sur l'allocation des ressources, la distribution des tâches aux nœuds et la liaison des tâches aux CPUs.

Première méthode de distribution (distribution des tâches sur les nœuds) :
*
Utiliser la méthode par défaut pour distribuer les tâches aux nœuds (block).
block
La méthode de distribution par bloc distribuera les tâches à un nœud de telle sorte que les tâches consécutives partagent un nœud. Par exemple, considérez une allocation de trois nœuds avec deux cœurs chacun. Une demande de distribution par bloc de quatre tâches distribuera ces tâches aux nœuds avec les tâches un et deux sur le premier nœud, la tâche trois sur le deuxième nœud et la tâche quatre sur le troisième nœud. La distribution par bloc est le comportement par défaut si le nombre de tâches dépasse le nombre de nœuds alloués.
cyclic
La méthode de distribution cyclique distribuera les tâches à un nœud de telle sorte que les tâches consécutives soient distribuées sur des nœuds consécutifs (de manière cyclique). Par exemple, considérez une allocation de trois nœuds avec deux cœurs chacun. Une demande de distribution cyclique de quatre tâches distribuera ces tâches aux nœuds avec les tâches un et quatre sur le premier nœud, la tâche deux sur le deuxième nœud et la tâche trois sur le troisième nœud. Notez que lorsque SelectType est select/cons_tres, le même nombre de CPUs peut ne pas être alloué sur chaque nœud. La distribution des tâches sera cyclique parmi tous les nœuds avec des CPUs encore à attribuer aux tâches. La distribution cyclique est le comportement par défaut si le nombre de tâches n'est pas supérieur au nombre de nœuds alloués.
plane
Les tâches sont distribuées par blocs de taille <taille>. La taille doit être fournie ou SLURM_DIST_PLANESIZE doit être définie. Le nombre de tâches distribuées à chaque nœud est le même qu'en distribution cyclique, mais les taskids attribués à chaque nœud dépendent de la taille du plan. Des spécifications de distribution supplémentaires ne peuvent pas être combinées avec cette option. Pour plus de détails (y compris des exemples et des schémas), veuillez consulter https://slurm.schedmd.com/mc_support.html et https://slurm.schedmd.com/dist_plane.html
arbitrary
La méthode de distribution arbitraire allouera les processus dans l'ordre tel qu'énuméré dans le fichier désigné par la variable d'environnement SLURM_HOSTFILE. Si cette variable est répertoriée, elle remplacera toute autre méthode spécifiée. Si elle n'est pas définie, la méthode sera par défaut block. À l'intérieur du fichier hôte, il doit contenir au minimum le nombre d'hôtes demandés et être un par ligne ou séparé par des virgules. Si vous spécifiez une tâche
Le nombre de tâches est fixé par -n, --ntasks=<nombre>. Vos tâches seront réparties sur les nœuds dans l'ordre du fichier.
NOTE: L'option de distribution arbitraire sur une allocation de travail ne contrôle que les nœuds à allouer au travail et non l'allocation des CPU sur ces nœuds. Cette option est principalement destinée à contrôler la disposition des tâches d'une étape de travail dans une allocation de travail existante pour la commande srun.
NOTE: Si le nombre de tâches est donné et qu'une liste de nœuds demandés est également donnée, le nombre de nœuds utilisés à partir de cette liste sera réduit pour correspondre à celui du nombre de tâches si le nombre de nœuds dans la liste est supérieur au nombre de tâches.

Deuxième méthode de distribution (distribution des CPU sur les sockets pour le binding) :

*
Utilise la méthode par défaut pour distribuer les CPU sur les sockets (cyclique).
block
La méthode de distribution par blocs distribuera les CPU alloués consécutivement à partir du même socket pour le binding aux tâches, avant d'utiliser le socket consécutif suivant.
cyclic
La méthode de distribution cyclique distribuera les CPU alloués pour le binding à une tâche donnée consécutivement à partir du même socket, et à partir du socket consécutif suivant pour la tâche suivante, de manière circulaire sur les sockets. Les tâches nécessitant plus d'un CPU se verront allouer tous ces CPU sur un seul socket si possible.
NOTE: Dans les nœuds où l'hyper-threading est activé, une tâche ne demandant pas des cœurs complets peut être distribuée sur plusieurs sockets. Cela peut être évité en spécifiant --ntasks-per-core=1, ce qui force les tâches à allouer des cœurs complets.
fcyclic
La méthode de distribution fcyclic distribuera les CPU alloués pour le binding aux tâches à partir de sockets consécutifs de manière circulaire sur les sockets. Les tâches nécessitant plus d'un CPU se verront allouer chaque CPU de manière cyclique sur les sockets.

Troisième méthode de distribution (distribution des CPU sur les cœurs pour le binding) :

*
Utilise la méthode par défaut pour distribuer les CPU sur les cœurs (héritée de la deuxième méthode de distribution).
block
La méthode de distribution par blocs distribuera les CPU alloués consécutivement à partir du même cœur pour le binding aux tâches, avant d'utiliser le cœur consécutif suivant.
cyclic
La méthode de distribution cyclique distribuera les CPU alloués pour le binding à une tâche donnée consécutivement à partir du même cœur, et à partir du cœur consécutif suivant pour la tâche suivante, de manière circulaire sur les cœurs.
fcyclic
La méthode de distribution fcyclic distribuera les CPU alloués pour le binding aux tâches à partir de cœurs consécutifs de manière circulaire sur les cœurs.

Contrôle optionnel de la distribution des tâches sur les nœuds :

Pack
Plutôt que de distribuer uniformément les tâches d'une étape de travail sur ses nœuds alloués, les regroupe autant que possible sur les nœuds. Ceci ne s'applique que lorsque la méthode de distribution de tâches "block" est utilisée.
NoPack
Plutôt que de regrouper les tâches d'une étape de travail autant que possible sur les nœuds, les distribue uniformément. Cette option utilisateur remplacera le paramètre de configuration CR_Pack_Nodes de SelectTypeParameters.
-e, --error=<modèle_nom_fichier>
Demande à Slurm de connecter la sortie d'erreur standard du script de batch directement au nom de fichier spécifié dans le "modèle de nom de fichier". Par défaut, la sortie standard et la sortie d'erreur standard sont dirigées vers le même fichier. Pour les tableaux de jobs, le nom de fichier par défaut est "slurm-%A_%a.out", "%A" est remplacé par l'ID du job et "%a" par l'index du tableau. Pour les autres jobs, le nom de fichier par défaut est "slurm-%j.out", où "%j" est remplacé par l'ID du job. Voir la section modèle de nom de fichier ci-dessous pour les options de spécification de nom de fichier.
-x, --exclude=<liste_noms_nœuds>
Exclut explicitement certains nœuds des ressources allouées au job.
--exclusive[={user|mcs|topo}]
L'allocation du job ne peut pas partager de nœuds (ou de segment de topologie avec l'option "=topo") avec d'autres jobs en cours d'exécution (ou juste d'autres utilisateurs avec l'option "=user" ou avec l'option "=mcs"). Si user/mcs/topo ne sont pas spécifiés (c'est-à-dire que l'allocation du job ne peut pas partager de nœuds avec d'autres jobs en cours d'exécution), le job se voit allouer tous les CPU et GRES sur tous les nœuds de l'allocation, mais seulement la quantité de mémoire demandée. Ceci est conçu pour supporter le "gang scheduling", car les jobs suspendus résident toujours en mémoire. Pour demander toute la mémoire d'un nœud, utilisez --mem=0. Le comportement par défaut de partage/exclusivité dépend de la configuration du système et l'option OverSubscribe de la partition a la priorité sur l'option du job. NOTE: Comme les GRES partagés (MPS) ne peuvent pas être alloués en même temps que des GRES partagés (GPU), cette option n'alloue que tous les GRES partagés et aucun GRES partagés sous-jacents.

NOTE: Cette option est mutuellement exclusive avec --oversubscribe.

--export={[ALL,]<variables_environnement>|ALL|NIL|NONE}
Identifie quelles variables d'environnement de l'environnement de soumission sont propagées à l'application lancée. Notez que les variables SLURM_* sont toujours propagées.
--export=ALL
Mode par défaut si --export n'est pas spécifié. Tout l'environnement de l'utilisateur sera chargé (soit depuis l'environnement de l'appelant, soit depuis un environnement propre si --get-user-env est spécifié).
--export=NIL
Seules les variables SLURM_* et SPANK optionnelles de l'environnement utilisateur seront définies. L'utilisateur doit utiliser le chemin absolu vers le binaire à exécuter qui définira l'environnement. L'utilisateur ne peut pas spécifier de variables d'environnement explicites avec "NIL".

Contrairement à NONE, NIL ne créera pas automatiquement l'environnement de l'utilisateur en utilisant le mécanisme --get-user-env.

--export=NONE
Seules les variables SLURM_* et SPANK optionnelles de l'environnement utilisateur seront définies. L'utilisateur doit utiliser le chemin absolu vers le binaire à exécuter qui définira l'environnement. L'utilisateur ne peut pas spécifier de variables d'environnement explicites avec "NONE". Cependant, Slurm tentera alors implicitement de charger l'environnement de l'utilisateur sur le nœud où le script est exécuté, comme si --get-user-env avait été spécifié.

Cette option est particulièrement importante pour les jobs qui sont soumis sur un cluster et exécutés sur un cluster différent (par exemple, avec des chemins différents). Pour éviter que les étapes n'héritent des paramètres d'exportation d'environnement (par exemple, "NONE") de la commande sbatch, la variable d'environnement SLURM_EXPORT_ENV doit être définie sur "ALL" dans le script du job.

--export=[ALL,]<variables_environnement>
Exporte toutes les variables d'environnement SLURM_* et SPANK optionnelles ainsi que les variables explicitement définies. Plusieurs noms de variables d'environnement doivent être séparés par des virgules. Les noms de variables d'environnement peuvent être spécifiés pour propager la valeur actuelle (par exemple, "--export=EDITOR") ou des valeurs spécifiques peuvent être exportées (par exemple, "--export=EDITOR=/bin/emacs"). Si "ALL" est spécifié, alors toutes les variables d'environnement de l'utilisateur seront chargées et auront la priorité sur toutes les variables d'environnement explicitement données.
Exemple : --export=EDITOR,ARG1=test
Dans cet exemple, l'environnement propagé ne contiendra que la variable EDITOR de l'environnement de l'utilisateur, les variables d'environnement SLURM_*, et ARG1=test.
Exemple : --export=ALL,EDITOR=/bin/emacs
Il y a deux résultats possibles pour cet exemple. Si l'appelant a la variable d'environnement EDITOR définie, alors l'environnement du job héritera de la variable de l'environnement de l'appelant. Si l'appelant n'a pas de variable d'environnement définie pour EDITOR, alors l'environnement du job utilisera la valeur fournie par --export.

NOTE: NONE et [ALL,]<variables_environnement> fonctionnent implicitement comme si --get-user-env était défini. Veuillez vous référer aux implications dans sa section respective.

--export-file={<nom_fichier>|<fd>}
Si un nombre compris entre 3 et OPEN_MAX est spécifié comme argument de cette option, un descripteur de fichier lisible sera supposé (STDIN et STDOUT sont
non pris en charge comme arguments valides). Sinon, un nom de fichier est supposé. Exportez les variables d'environnement définies dans <nom de fichier> ou lues depuis <fd> dans l'environnement d'exécution du job. Le contenu est une ou plusieurs définitions de variables d'environnement de la forme NOM=valeur, chacune séparée par un caractère nul. Cela permet l'utilisation de caractères spéciaux dans les définitions d'environnement.
--extra=<chaîne>
Une chaîne arbitraire entourée d'apostrophes ou de guillemets doubles si des espaces ou certains caractères spéciaux sont utilisés.

Si SchedulerParameters=extra_constraints est activé, cette chaîne est utilisée pour le filtrage des nœuds basé sur le champ Extra de chaque nœud.

Restreindre la sélection de nœuds aux nœuds ayant au moins le nombre spécifié de sockets, de cœurs par socket et/ou de threads par cœur.
NOTE : Ces options ne spécifient pas la taille de l'allocation de ressources. Chaque valeur spécifiée est considérée comme un minimum. Un astérisque (*) peut être utilisé comme espace réservé indiquant que toutes les ressources disponibles de ce type doivent être utilisées. Les valeurs peuvent également être spécifiées sous forme de min-max. Les niveaux individuels peuvent également être spécifiés dans des options séparées si désiré : 
    --sockets-per-node=<sockets>
    --cores-per-socket=<cores>
    --threads-per-core=<threads>
Si le plugin task/affinity est activé, la spécification d'une allocation de cette manière entraîne également que les tâches lancées par la suite seront liées aux threads si l'option -B spécifie un nombre de threads, sinon à une option de cores si un nombre de cœurs est spécifié, sinon à une option de sockets. --get-user-env
Cette option indique à sbatch de récupérer les variables d'environnement de connexion pour l'utilisateur spécifié dans l'option --uid. Les variables d'environnement sont récupérées en exécutant quelque chose comme "su - <nom d'utilisateur> -c /usr/bin/env" et en analysant la sortie. Soyez conscient que toutes les variables d'environnement déjà définies dans l'environnement de sbatch auront la priorité sur toutes les variables d'environnement de l'environnement de connexion de l'utilisateur. Effacez toutes les variables d'environnement avant d'appeler sbatch que vous ne souhaitez pas propager au programme lancé. Si la récupération de l'environnement utilisateur échoue ou expire, le job sera avorté, remis en file d'attente et bloqué.

NOTE : L'utilisation explicite ou implicite de --get-user-env repose sur la capacité de créer des espaces de noms PID et de montage. Il est fortement conseillé de s'assurer que la création d'espaces de noms PID et de montage est disponible et non limitée (vérifiez que /proc/sys/user/max_[pid|mnt]_namespaces n'est pas 0). Bien qu'ils ne soient pas strictement obligatoires pour le fonctionnement de --get-user-env, ils garantissent qu'aucun processus orphelin ne reste après la récupération de l'environnement.

--gid=<groupe>
Si sbatch est exécuté en tant que root, et que l'option --gid est utilisée, soumettez le job avec les permissions d'accès de groupe de groupe. groupe peut être le nom du groupe ou l'identifiant numérique du groupe.
--gpu-bind=[verbose,]<type>
Équivalent à --tres-bind=gres/gpu:[verbose,]<type>. Voir --tres-bind pour toutes les options et la documentation.

Demande que les GPU alloués au job soient configurés avec des fréquences spécifiques. Cette option peut être utilisée pour configurer indépendamment les fréquences du GPU et de sa mémoire. low
la fréquence disponible la plus basse.
medium
tente de définir une fréquence au milieu de la plage disponible.
high
la fréquence disponible la plus élevée.
highm1
(high moins un) sélectionnera la fréquence disponible juste inférieure à la plus élevée.

Mais si le job a accès à tous les threads sur le cœur, ces threads seront inclus dans le calcul de la mémoire par CPU même si le job n'a pas explicitement demandé ces threads.

Dans les exemples suivants, chaque cœur a deux threads.

Dans ce premier exemple, deux tâches peuvent s'exécuter sur des hyperthreads séparés dans le même cœur car --threads-per-core n'est pas utilisé. La troisième tâche utilise les deux threads du deuxième cœur. La mémoire allouée par CPU inclut tous les threads :

$ sacct -j $SLURM_JOB_ID -X -o jobid%7,reqtres%35,alloctres%35

------- ----------------------------------- -----------------------------------
  17199     billing=3,cpu=3,mem=300M,node=1     billing=4,cpu=4,mem=400M,node=1

Dans ce deuxième exemple, en raison de --threads-per-core=1, chaque tâche se voit attribuer un cœur entier mais ne peut utiliser qu'un seul thread par cœur. Les CPU alloués incluent tous les threads sur chaque cœur. Cependant, la mémoire allouée par CPU n'inclut que le thread utilisable sur chaque cœur.

salloc: Granted job allocation 17200
$ sacct -j $SLURM_JOB_ID -X -o jobid%7,reqtres%35,alloctres%35
  JobID                             ReqTRES                           AllocTRES
------- ----------------------------------- -----------------------------------

Sur les systèmes configurés avec SwitchType=switch/nvidia_imex, les options suivantes sont prises en charge :

unique-channel-per-segment
Au lieu d'un seul canal pour l'ensemble de la tâche, allouez un canal par segment dans la tâche. Ceci ne prend effet que lorsque topology/block est configuré.
--nice[=ajustement]
Exécutez la tâche avec une priorité de planification ajustée dans Slurm. Sans valeur d'ajustement, la priorité de planification est diminuée de 100. Une valeur de nice négative augmente la priorité, sinon elle la diminue. La plage d'ajustement est de +/- 2147483645. Seuls les utilisateurs privilégiés peuvent spécifier un ajustement négatif.
-k, --no-kill[=off]
Ne pas terminer automatiquement une tâche si l'un des nœuds qui lui ont été alloués échoue. L'utilisateur assumera les responsabilités de la tolérance aux pannes en cas de défaillance d'un nœud. L'allocation de tâche ne sera pas révoquée, de sorte que l'utilisateur pourra lancer de nouvelles étapes de tâche sur les nœuds restants de son allocation. Cette option ne définit pas la variable d'environnement SLURM_NO_KILL. Par conséquent, lorsqu'un nœud échoue, les étapes s'exécutant sur ce nœud seront tuées, sauf si la variable d'environnement SLURM_NO_KILL a été explicitement définie ou si les appels srun dans l'allocation de tâche ont explicitement demandé --no-kill.

Spécifiez un argument optionnel "off" pour désactiver l'effet de la variable d'environnement SBATCH_NO_KILL.

Par défaut, Slurm termine l'allocation de tâche entière si un nœud échoue dans sa plage de nœuds alloués.

--no-requeue
Spécifie que la tâche batch ne doit jamais être remise en file d'attente en aucune circonstance (voir la note ci-dessous). Définir cette option empêchera les administrateurs système de pouvoir redémarrer la tâche (par exemple, après un temps d'arrêt programmé), de récupérer d'une défaillance de nœud, ou d'être remise en file d'attente suite à une préemption par une tâche de priorité supérieure. Lorsqu'une tâche est remise en file d'attente, le script batch est lancé depuis le début. Voir également l'option --requeue. Le paramètre de configuration JobRequeue contrôle le comportement par défaut sur le cluster.

NOTE : ForceRequeueOnFail, s'il est défini comme option du paramètre PrologFlags dans slurm.conf, peut remplacer ce paramètre.

-F, --nodefile=<fichier_nœuds>
Tout comme --nodelist, mais la liste est contenue dans un fichier nommé fichier_nœuds. Le nom du nœud
les de la liste peuvent également s'étendre sur plusieurs lignes dans le fichier. Les noms de nœuds dupliqués dans le fichier seront ignorés. L'ordre des noms de nœuds dans la liste n'a pas d'importance ; les noms de nœuds seront triés par Slurm.
-w, --nodelist=<liste_noms_nœuds>
Demande une liste spécifique d'hôtes. Le travail contiendra *tous* ces hôtes et potentiellement des hôtes supplémentaires si nécessaire pour satisfaire les exigences en ressources. La liste peut être spécifiée comme une liste d'hôtes séparés par des virgules, une plage d'hôtes (par exemple, hôte[1-5,7,...]) ou un nom de fichier. La liste d'hôtes sera présumée être un nom de fichier si elle contient un caractère "/". Si vous spécifiez un nombre minimum de nœuds ou de processeurs supérieur à ce qui peut être satisfait par la liste d'hôtes fournie, des ressources supplémentaires seront allouées sur d'autres nœuds si nécessaire. Les noms de nœuds dupliqués dans la liste seront ignorés. L'ordre des noms de nœuds dans la liste n'a pas d'importance ; les noms de nœuds seront triés par Slurm.
-N, --nodes=<minnœuds>[-maxnœuds]|<chaîne_taille>
Demande qu'un minimum de minnœuds nœuds soient alloués à ce travail. Un nombre maximum de nœuds peut également être spécifié avec maxnœuds. Si un seul nombre est spécifié, il est utilisé comme nombre minimum et maximum de nœuds. Le nombre de nœuds peut également être spécifié sous forme de chaîne de taille. La spécification de la chaîne de taille identifie les valeurs de nœuds qui doivent être utilisées. Plusieurs valeurs peuvent être spécifiées en utilisant une liste séparée par des virgules ou avec une fonction de pas par un suffixe contenant deux points et des valeurs numériques avec un séparateur "-". Par exemple, "--nodes=1-15:4" est équivalent à "--nodes=1,5,9,13". Les limites de nœuds de la partition remplacent celles du travail. Si les limites de nœuds d'un travail sont en dehors de la plage autorisée pour sa partition associée, le travail restera dans un état PENDING. Cela permet une exécution possible plus tard, lorsque la limite de la partition sera modifiée. Si la limite de nœuds d'un travail dépasse le nombre de nœuds configurés dans la partition, le travail sera rejeté. Notez que la variable d'environnement SLURM_JOB_NUM_NODES sera définie sur le nombre de nœuds réellement alloués au travail. Voir la section VARIABLES D'ENVIRONNEMENT pour plus d'informations. Si -N n'est pas spécifié, le comportement par défaut est d'allouer suffisamment de nœuds pour satisfaire les ressources demandées telles qu'exprimées par les options de spécification par travail, par exemple -n, -c et --gpus. Le travail se verra allouer autant de nœuds que possible dans la plage spécifiée et sans retarder le démarrage du travail. La spécification du nombre de nœuds peut inclure une valeur numérique suivie d'un suffixe "k" (multiplie la valeur numérique par 1 024) ou "m" (multiplie la valeur numérique par 1 048 576).

NOTE: Cette option ne peut pas être utilisée avec une distribution arbitraire.

-n, --ntasks=<nombre>
sbatch ne lance pas de tâches, il demande une allocation de ressources et soumet un script de traitement par lots. Cette option informe le contrôleur Slurm que les étapes du travail exécutées dans l'allocation lanceront un maximum de nombre tâches et qu'il fournira suffisamment de ressources. La valeur par défaut est une tâche par nœud, mais notez que l'option --cpus-per-task modifiera cette valeur par défaut.
--ntasks-per-core=<ntasks>
Demande que le nombre maximal de ntasks soit lancé sur chaque cœur. Destiné à être utilisé avec l'option --ntasks. Lié à --ntasks-per-node, mais au niveau du cœur au lieu du niveau du nœud. Cette option sera héritée par srun. Slurm peut allouer plus de cœurs que ce qui était demandé afin de respecter cette option.
NOTE: Cette option n'est pas prise en charge lors de l'utilisation de SelectType=select/linear. Cette valeur ne peut pas être supérieure à --threads-per-core.
--ntasks-per-gpu=<ntasks>
Demande que ntasks tâches soient lancées pour chaque GPU. Cette option peut fonctionner de deux manières : 1) soit spécifier --ntasks en plus, auquel cas une spécification de GPU sans type sera automatiquement déterminée pour satisfaire --ntasks-per-gpu, soit 2) spécifier les GPU souhaités (par exemple via --gpus ou --gres) sans spécifier --ntasks, et le nombre total de tâches sera automatiquement déterminé. Le nombre de CPU nécessaires sera automatiquement augmenté si nécessaire pour permettre tout compte de tâches calculé. Cette option définira implicitement --tres-bind=gres/gpu:single:<ntasks>, mais cela peut être remplacé par une spécification explicite de --tres-bind=gres/gpu. Cette option n'est pas compatible avec une plage de nœuds (c'est-à-dire -N<minnœuds-maxnœuds>). Cette option n'est pas compatible avec --gpus-per-task, --gpus-per-socket, ou --ntasks-per-node. Cette option n'est pas prise en charge à moins que SelectType=cons_tres ne soit configuré (directement ou indirectement sur les systèmes Cray).
--ntasks-per-node=<ntasks>
Demande que ntasks soient lancées sur chaque nœud. Si elle est utilisée avec l'option --ntasks, l'option --ntasks aura la priorité et --ntasks-per-node sera traitée comme un nombre maximum de tâches par nœud. Destinée à être utilisée avec l'option --nodes. Ceci est lié à --cpus-per-task=ncpus, mais ne nécessite pas de connaître le nombre réel de cœurs sur chaque nœud. Dans certains cas, il est plus pratique de demander qu'un nombre spécifique de tâches ne soit pas dépassé sur chaque nœud. Les exemples incluent la soumission d'une application hybride MPI/OpenMP où une seule "tâche/rang" MPI doit être attribuée à chaque nœud tout en permettant à la partie OpenMP d'utiliser tout le parallélisme présent dans le nœud, ou la soumission d'un seul travail de configuration/nettoyage/surveillance à chaque nœud d'une allocation préexistante en tant qu'étape d'un script de travail plus important.
--ntasks-per-socket=<ntasks>
Demande que le nombre maximal de ntasks soit lancé sur chaque socket. Destiné à être utilisé avec l'option --ntasks. Lié à --ntasks-per-node, mais au niveau du socket au lieu du niveau du nœud. NOTE: Cette option n'est pas prise en charge lors de l'utilisation de SelectType=select/linear.
--oom-kill-step[={0|1}]
Indique s'il faut tuer toute l'étape si un événement OOM (Out Of Memory) est détecté dans une tâche d'une étape. Cela remplace le paramètre "OOMKillStep" de TaskPluginParam dans slurm.conf. Lorsqu'il n'est pas défini, il utilise le paramètre de slurm.conf. Lorsqu'il est défini, une valeur de "0" désactivera la mise à mort de toute l'étape, tandis qu'une valeur de "1" l'activera. Ceci s'applique à toute l'allocation, à l'exception de l'étape externe. La valeur par défaut est "1" (activé) lorsque l'option est trouvée sans valeur.
--open-mode={append|truncate}
Ouvre les fichiers de sortie et d'erreur en mode ajout ou troncature, comme spécifié. La valeur par défaut est spécifiée par le paramètre de configuration système JobFileAppend.
-o, --output=<modèle_nom_fichier>
Indique à Slurm de connecter la sortie standard du script de traitement par lots directement au nom de fichier spécifié dans le "modèle de nom de fichier". Par défaut, la sortie standard et l'erreur standard sont dirigées vers le même fichier. Pour les tableaux de travaux, le nom de fichier par défaut est "slurm-%A_%a.out", "%A" est remplacé par l'ID du travail et "%a" par l'index du tableau. Pour les autres travaux, le nom de fichier par défaut est "slurm-%j.out", où "%j" est remplacé par l'ID du travail. Voir la section modèle de nom de fichier ci-dessous pour les options de spécification des noms de fichier.
-O, --overcommit
Surcharge des ressources.

Lorsqu'elle est appliquée à une allocation de travail (à l'exclusion des travaux demandant un accès exclusif aux nœuds), les ressources sont allouées comme si une seule tâche par nœud était demandée. Cela signifie que le nombre de cœurs par tâche demandé (-c, --cpus-per-task) est alloué par nœud au lieu d'être multiplié par le nombre de tâches. Les options utilisées pour spécifier le nombre de tâches par nœud, socket, cœur, etc. sont ignorées.

Lorsqu'elle est appliquée aux allocations d'étapes de travail (la commande srun lorsqu'elle est exécutée dans une allocation de travail existante), cette option peut être utilisée pour lancer plus d'une tâche par CPU. Normalement, srun n'alloue pas plus d'un processus par CPU. En spécifiant --overcommit, vous autorisez explicitement plus d'un processus par CPU. Cependant, pas plus de MAX_TASKS_PER_NODE tâches ne sont autorisées à s'exécuter par nœud. NOTE: MAX_TASKS_PER_NODE est défini dans le fichier slurm.h et n'est pas une variable, il est défini au moment de la construction de Slurm.

-s, --oversubscribe
L'allocation de travail peut sur-abonner des ressources avec d'autres travaux en cours d'exécution. Les ressources à sur-abonner peuvent être des nœuds, des sockets, des cœurs et/ou des hyperfils en fonction de la configuration. Le comportement de sur-abonnement par défaut dépend de la configuration du système et l'option OverSubscribe de la partition a la priorité sur l'option du travail. Cette option peut entraîner l'octroi plus rapide de l'allocation que si l'option --oversubscribe n'était pas définie et permettre une utilisation plus élevée du système, mais les performances de l'application risquent de souffrir en raison de la concurrence pour les ressources. Voir également l'option --exclusive.

NOTE: Cette option est mutuellement exclusive avec --exclusive.

--parsable
Affiche uniquement l'identifiant du travail et le nom du cluster s'il est présent. Les valeurs sont séparées par un point-virgule. Les erreurs seront toujours affichées.
-p, --partition=<noms_partitions>
Demande une partition spécifique pour l'allocation des ressources. Si non spécifié, le comportement par défaut est de permettre au contrôleur Slurm de sélectionner la partition par défaut telle que désignée par l'administrateur système. Si le travail peut utiliser plus d'une partition, spécifiez leurs noms dans une liste séparée par des virgules et celle offrant l'initiation la plus précoce sera utilisée, sans tenir compte de l'ordre des noms de partitions (bien que les partitions de priorité supérieure soient considérées en premier). Lorsque le travail est lancé, le nom de la partition utilisée sera placé en premier dans la chaîne de partitions de l'enregistrement du travail.
--prefer=<liste>
Les nœuds peuvent avoir des fonctionnalités qui leur sont attribuées par l'administrateur Slurm. Les utilisateurs peuvent spécifier quelles sont ces fonctionnalités souhaitées mais non requises par leur travail en utilisant l'option prefer. Cette option agit indépendamment de --constraint et remplacera tout ce qui est défini là si possible. Lors de la planification, les fonctionnalités dans --prefer sont essayées en premier. Si un ensemble de nœuds n'est pas disponible avec ces fonctionnalités, alors --constraint est tenté. Voir --constraint pour plus d'informations, cette option se comporte de la même manière.
--priority=<valeur>
Demande une priorité de travail spécifique. Peut être soumise à des contraintes spécifiques à la configuration. valeur doit être une valeur numérique ou "TOP" (pour la valeur la plus élevée possible). Seuls les opérateurs et administrateurs Slurm peuvent définir la priorité d'un travail.

--reboot
Force le redémarrage des nœuds alloués avant de démarrer le travail. Ceci n'est pris en charge qu'avec certaines configurations système et sera sinon ignoré silencieusement. Seul root, SlurmUser ou les administrateurs peuvent redémarrer des nœuds.
--requeue[=expedited]
Spécifie que le travail par lots doit être éligible pour être remis en file d'attente. Le travail peut être remis en file d'attente explicitement par un administrateur système, après une défaillance de nœud, ou suite à une préemption par un travail de priorité supérieure. Lorsqu'un travail est remis en file d'attente, le script de lots est lancé depuis le début avec le même ID de travail. Voir également l'option --no-requeue. Le paramètre de configuration JobRequeue contrôle le comportement par défaut sur le cluster.

Le paramètre optionnel expedited demandera que le travail soit immédiatement éligible pour redémarrer, et qu'il soit planifié avec la priorité la plus élevée possible. Cela ne se produira que si les remises en file d'attente accélérées sont autorisées globalement avec SlurmctldParameters=enable_expedited_requeue dans slurm.conf.

--reservation=<noms_reservation>
Alloue des ressources pour le travail à partir de la réservation nommée. Si le travail peut utiliser plus d'une réservation, spécifiez leurs noms dans une liste séparée par des virgules et celle offrant l'initiation la plus précoce. Chaque réservation sera considérée dans l'ordre où elle a été demandée. Toutes les réservations seront listées dans scontrol/squeue pendant la durée du travail. En comptabilité, la première réservation sera visible et après le démarrage du travail, la réservation utilisée la remplacera.
--resources=<noms_ressources>
Spécification des ressources hiérarchiques qui doivent être allouées à ce travail. Les noms de ressources peuvent être suivis d'un deux-points et d'un compte (le compte par défaut est un). Plusieurs ressources en Mode 1 et Mode 2 peuvent être demandées dans une liste séparée par des virgules, mais une seule de Mode 3 peut être demandée. Par exemple, "--resources=flat:2,natural:1".

Voir https://slurm.schedmd.com/hres.html pour plus d'informations sur l'utilisation des ressources hiérarchiques avec Slurm.

--resv-ports[=compte]
Réserve des ports de communication pour ce travail. Les utilisateurs peuvent spécifier le nombre de ports qu'ils souhaitent réserver. Le paramètre MpiParams=ports=12000-12999 doit être spécifié dans slurm.conf. Si le nombre de ports réservés est zéro, alors aucun port n'est réservé. Utilisé uniquement pour le PMI natif de Cray. Cette option ne peut être utilisée que si la gestion des étapes slurmstepd est activée. Cette option s'applique aux allocations de travaux. Voir --stepmgr.
--segment=<taille_segment>
Lorsqu'une topologie de bloc est utilisée, cela définit la taille des segments qui seront
utilisé pour créer l'allocation de tâches. Aucune exigence ne serait placée sur tous les segments pour une tâche devant être placée dans le même bloc de niveau supérieur.

NOTE : Le nombre de nœuds demandé doit toujours être divisible par la taille de segment demandée.

NOTE : Lors de l'utilisation conjointe avec --nodelist=<node_list> : Le nombre de nœuds demandé doit être inférieur ou égal au nombre total de nœuds uniques spécifiés dans l'argument --nodelist. Demander plus de nœuds que les nœuds uniques disponibles dans le --nodelist fourni entraînera le rejet de la tâche par slurmctld.

--signal=[{R|B}:]<sig_num>[@sig_time]
Lorsque la tâche est à moins de sig_time secondes de sa fin, envoyez-lui le signal sig_num. En raison de la résolution du traitement des événements par Slurm, le signal peut être envoyé jusqu'à 60 secondes plus tôt que spécifié. sig_num peut être un numéro ou un nom de signal (par exemple, "10" ou "USR1"). sig_time doit être une valeur entière comprise entre 0 et 65535. Par défaut, aucun signal n'est envoyé avant la fin de la tâche. Si un sig_num est spécifié sans sig_time, le temps par défaut sera de 60 secondes. Utilisez l'option "B:" pour signaler uniquement le shell de traitement par lots, aucun des autres processus ne sera signalé. Par défaut, toutes les étapes de la tâche seront signalées, mais pas le shell de traitement par lots lui-même. Utilisez l'option "R:" pour permettre à cette tâche de chevaucher une réservation avec MaxStartDelay défini. Si l'option "R:" est utilisée, la préemption doit être activée sur le système, et si la tâche est préemptée, elle sera mise en file d'attente si autorisée, sinon la tâche sera annulée. Pour que le signal soit envoyé au moment de la préemption, voir send_user_signal PreemptParameter.
--sockets-per-node=<sockets>
Restreindre la sélection des nœuds aux nœuds ayant au moins le nombre spécifié de sockets. Voir les informations supplémentaires sous l'option -B ci-dessus lorsque le plugin task/affinity est activé.
NOTE : Cette option peut implicitement définir le nombre de tâches (si -n n'a pas été spécifié) comme une tâche par thread demandé.
--spread-job
Répartir l'allocation de la tâche sur autant de nœuds que possible et tenter de distribuer uniformément les tâches sur les nœuds alloués. Cette option désactive le plugin topology/tree.
--spread-segments
Empêcher les nœuds au sein du même bloc de base d'être alloués à des segments séparés au sein du même bloc.

Cette option s'applique aux allocations de tâches. NOTE : Cette option ne fonctionnera qu'avec le plugin topology/block.

--stepmgr
Activer la gestion des étapes slurmstepd par tâche si elle n'est pas activée globalement. Cela permet aux étapes de tâche d'être gérées par un seul slurmstepd externe associé à la tâche pour gérer les étapes. Ceci est bénéfique pour les tâches qui soumettent de nombreuses étapes dans leurs allocations. PrologFlags=contain doit être défini.
--switches=<count>[@max-time]
Lorsqu'une topologie arborescente est utilisée, ceci définit le nombre maximum de commutateurs feuilles souhaités pour l'allocation de la tâche et éventuellement le temps maximum d'attente pour ce nombre de commutateurs. Si Slurm trouve une allocation contenant plus de commutateurs que le nombre spécifié, la tâche reste en attente jusqu'à ce qu'elle trouve une allocation avec le nombre de commutateurs souhaité ou que la limite de temps expire. S'il n'y a pas de limite de nombre de commutateurs, il n'y a aucun délai dans le démarrage de la tâche. Les formats de temps acceptables incluent "minutes", "minutes:secondes", "heures:minutes:secondes", "jours-heures", "jours-heures:minutes" et "jours-heures:minutes:secondes". Le délai maximum de la tâche peut être limité par l'administrateur système en utilisant le paramètre de configuration SchedulerParameters avec le paramètre max_switch_wait. Sur un réseau dragonfly, le seul nombre de commutateurs pris en charge est 1, car les performances de communication seront les plus élevées lorsqu'une tâche alloue des ressources sur un seul commutateur feuille ou sur plus de 2 commutateurs feuilles. Le temps maximum par défaut est le SchedulerParameters max_switch_wait.
--test-only
Valider le script de traitement par lots et retourner une estimation du moment où une tâche serait planifiée pour s'exécuter compte tenu de la file d'attente des tâches actuelle et de tous les autres arguments spécifiant les exigences de la tâche. Aucune tâche n'est réellement soumise.
--thread-spec=<num>
Nombre de threads spécialisés par nœud réservés par la tâche pour les opérations système et non utilisés par l'application. L'application n'utilisera pas ces threads, mais sera facturée pour leur allocation. Cette option ne peut pas être utilisée avec l'option --core-spec.

NOTE : La définition explicite de la valeur des threads spécialisés d'une tâche définit implicitement son option --exclusive, réservant des nœuds entiers pour la tâche.

--threads-per-core=<threads>
Restreindre la sélection des nœuds aux nœuds ayant au moins le nombre spécifié de threads par cœur. Dans la disposition des tâches, utiliser le nombre maximum spécifié de threads par cœur. NOTE : "Threads" fait référence au nombre d'unités de traitement sur chaque cœur plutôt qu'au nombre de tâches d'application à lancer par cœur. Voir les informations supplémentaires sous l'option -B ci-dessus lorsque le plugin task/affinity est activé.
NOTE : Cette option peut implicitement définir le nombre de tâches (si -n n'a pas été spécifié) comme une tâche par thread demandé.
-t, --time=<time>
Définir une limite sur le temps d'exécution total de l'allocation de la tâche. Si la limite de temps demandée dépasse la limite de temps de la partition, la tâche restera dans un état PENDING (éventuellement indéfiniment). La limite de temps par défaut est la limite de temps par défaut de la partition. Lorsque la limite de temps est atteinte, chaque tâche de chaque étape de la tâche reçoit SIGTERM suivi de SIGKILL. L'intervalle entre les signaux est spécifié par le paramètre de configuration Slurm KillWait. Le paramètre de configuration OverTimeLimit peut permettre à la tâche de s'exécuter plus longtemps que prévu. La résolution temporelle est d'une minute et les valeurs de secondes sont arrondies à la minute supérieure.

Une limite de temps de zéro demande qu'aucune limite de temps ne soit imposée. Les formats de temps acceptables incluent "minutes", "minutes:secondes", "heures:minutes:secondes", "jours-heures", "jours-heures:minutes" et "jours-heures:minutes:secondes".

--time-min=<time>
Définir une limite de temps minimale sur l'allocation de la tâche. Si spécifié, la tâche peut voir sa limite --time réduite à une valeur non inférieure à --time-min si cela permet à la tâche de commencer son exécution plus tôt que ce qui serait autrement possible. La limite de temps de la tâche ne sera pas modifiée après que la tâche ait obtenu des ressources. Ceci est effectué par un algorithme de planification de remplissage pour allouer des ressources autrement réservées à des tâches de priorité plus élevée. Les formats de temps acceptables incluent "minutes", "minutes:secondes", "heures:minutes:secondes", "jours-heures", "jours-heures:minutes" et "jours-heures:minutes:secondes".
--tmp=<size>[units]
Spécifier une quantité minimale d'espace disque temporaire par nœud. Les unités par défaut sont les mégaoctets. Différentes unités peuvent être spécifiées en utilisant le suffixe [K|M|G|T].
--tres-bind=<tres>:[verbose,]<type>[+<tres>:
[verbose,]<type>...] Spécifier une liste de ressources (tres) avec leurs options de liaison de tâche. Actuellement, les gres sont les seules ressources prises en charge pour cette option. Spécifier les gres comme "gres/<nom_gres>" (par exemple, gres/gpu)

Exemple : --tres-bind=gres/gpu:verbose,map:0,1,2,3+gres/nic:closest

Par défaut, la plupart des gres ne sont pas liés aux tâches individuelles

Options de liaison type prises en charge pour gres :

closest
Lier chaque tâche aux gres qui sont les plus proches. Dans un environnement NUMA, chaque tâche peut être liée à plusieurs gres (c'est-à-dire tous les gres de cet environnement NUMA).
map:<list>
Lier en définissant des masques gres sur les tâches (ou rangs) comme spécifié où <list> est <id_gres_pour_tache_0>,<id_gres_pour_tache_1>,... Les identifiants gres sont interprétés comme des valeurs décimales. Si le nombre de tâches (ou de rangs) dépasse le nombre d'éléments dans cette liste, les éléments de la liste seront réutilisés si nécessaire en commençant par le début de la liste. Pour simplifier la prise en charge des grands nombres de tâches, les listes peuvent suivre un masque avec un astérisque et un nombre de répétitions. Par exemple "map:0*4,1*4". Si le plugin task/cgroup est utilisé et que ConstrainDevices est défini dans cgroup.conf, alors les identifiants gres sont des index basés sur zéro par rapport aux gres alloués à la tâche (par exemple, le premier gres est 0, même si l'identifiant global est 3). Sinon, les identifiants gres sont des identifiants globaux, et tous les gres sur chaque nœud de la tâche doivent être alloués pour des résultats de liaison prévisibles.
mask:<list>
Lier en définissant
gres masks sur les tâches (ou les rangs) comme spécifié où <liste> est <gres_mask_pour_tache_0>,<gres_mask_pour_tache_1>,... Le mappage est spécifié pour un nœud et un mappage identique est appliqué aux tâches sur chaque nœud (c'est-à-dire que la tâche avec le plus petit ID sur chaque nœud est mappée au premier masque spécifié dans la liste, etc.). Les masques gres sont toujours interprétés comme des valeurs hexadécimales mais peuvent être précédés d'un '0x' optionnel. Pour simplifier la prise en charge de grands nombres de tâches, les listes peuvent suivre une carte avec un astérisque et un nombre de répétitions. Par exemple "mask:0x0f*4,0xf0*4". Si le plugin task/cgroup est utilisé et que ConstrainDevices est défini dans cgroup.conf, alors les identifiants gres sont des indices basés sur zéro par rapport aux gres alloués au travail (par exemple, le premier gres est 0, même si l'ID global est 3). Sinon, les identifiants gres sont des identifiants globaux, et tous les gres de chaque nœud du travail doivent être alloués pour des résultats de liaison prévisibles.
none
Ne pas lier les tâches à ce gres (désactive la liaison implicite de --tres-per-task et --gpus-per-task).
per_task:<gres_per_task>
Chaque tâche sera liée au nombre de gres spécifié dans <gres_per_task>. Les tâches se voient préférablement attribuer des gres avec affinité pour les cœurs de leur allocation, comme dans closest, bien qu'elles prennent n'importe quel gres s'il n'est pas disponible. S'il n'y a pas d'affinité, la première tâche se verra attribuer les x premiers gres du nœud, etc. Les gres partagés préféreront lier un appareil de partage par tâche si possible.
single:<tasks_per_gres>
Comme closest, sauf que chaque tâche ne peut être liée qu'à un seul gres, même lorsqu'elle peut être liée à plusieurs gres qui sont également proches. Le gres auquel se lier est déterminé par <tasks_per_gres>, où les <tasks_per_gres> premières tâches sont liées au premier gres disponible, les <tasks_per_gres> tâches suivantes sont liées au deuxième gres disponible, etc. Il s'agit essentiellement d'une distribution par blocs de tâches sur les gres disponibles, où les gres disponibles sont déterminés par l'affinité du socket de la tâche et l'affinité du socket du gres, comme spécifié dans le paramètre Cores de gres.conf.

NOTE: La liaison de gres partagés est actuellement limitée à per_task ou none

--tres-per-task=<liste>
Spécifie une liste séparée par des virgules de ressources traçables requises pour le travail sur chaque tâche à lancer dans l'allocation de ressources du travail. Le format de chaque entrée dans la liste est "type_res[/nom_res]=nombre". Le type_res est le type de ressource traçable demandée (par exemple, cpu, gres, license, etc.). Le nom_res est le nom de la ressource traçable, comme on peut le voir avec sacctmgr show tres. Ceci est requis lorsqu'il existe pour des types de tres tels que gres, license, etc. (par exemple, gpu, gpu:a100). Pour demander une license avec cette option, la ou les licenses doivent être définies dans le paramètre AccountingStorageTRES de slurm.conf. Le nombre est le nombre de ces ressources.
Le nombre peut avoir un suffixe de
"k" ou "K" (multiple de 1024),
"m" ou "M" (multiple de 1024 x 1024),
"g" ou "G" (multiple de 1024 x 1024 x 1024),
"t" ou "T" (multiple de 1024 x 1024 x 1024 x 1024),
"p" ou "P" (multiple de 1024 x 1024 x 1024 x 1024 x 1024).
Exemples: 
--tres-per-task=cpu=4
--tres-per-task=cpu=8,license/ansys=1
--tres-per-task=gres/gpu=1
--tres-per-task=gres/gpu:a100=2
Les ressources spécifiées seront allouées au travail sur chaque nœud. Les ressources traçables disponibles sont configurables par l'administrateur système.
NOTE: Cette option avec gres/gpu ou gres/shard définira implicitement --tres-bind=gres/[gpu|shard]:per_task:<tres_per_task>, ou si plusieurs types de gpu sont spécifiés --tres-bind=gres/gpu:per_task:<somme_gpus_par_type_de_tache>. Ceci peut être remplacé par une spécification --tres-bind explicite.
NOTE: Les TRES invalides pour --tres-per-task incluent bb,billing,energy,fs,mem,node,pages,vmem.
--uid=<utilisateur>
Tenter de soumettre et/ou d'exécuter un travail en tant qu'utilisateur au lieu de l'utilisateur appelant. L'utilisateur root peut utiliser cette option pour exécuter des travaux en tant qu'utilisateur normal dans une partition RootOnly, par exemple. PERFORMANCE

L'exécution de sbatch envoie un appel de procédure distante à slurmctld. Si suffisamment d'appels de sbatch ou d'autres commandes client Slurm qui envoient des appels de procédure distante au démon slurmctld arrivent simultanément, cela peut entraîner une dégradation des performances du démon slurmctld, entraînant éventuellement un déni de service.

N'exécutez pas sbatch ou d'autres commandes client Slurm qui envoient des appels de procédure distante à slurmctld à partir de boucles dans des scripts shell ou d'autres programmes. Assurez-vous que les programmes limitent les appels à sbatch au minimum nécessaire pour les informations que vous essayez de collecter.

L'ID du processus de la tâche en cours de lancement.
SLURM_TASKS_PER_NODE
Nombre de tâches à initier sur chaque nœud. Les valeurs sont séparées par des virgules et dans le même ordre que SLURM_JOB_NODELIST. Si deux nœuds consécutifs ou plus doivent avoir le même nombre de tâches, ce nombre est suivi de "(x#)" où "#" est le nombre de répétitions. Par exemple, "SLURM_TASKS_PER_NODE=2(x3),1" indique que les trois premiers nœuds exécuteront chacun deux tâches et que le quatrième nœud exécutera une tâche.
SLURM_THREADS_PER_CORE
Ceci est uniquement défini si --threads-per-core ou SBATCH_THREADS_PER_CORE ont été spécifiés. La valeur sera définie à la valeur spécifiée par --threads-per-core ou SBATCH_THREADS_PER_CORE. Ceci est utilisé par les appels srun ultérieurs au sein de l'allocation de tâches.
SLURM_TOPOLOGY_ADDR
Ceci est défini uniquement si le système a le plugin topology/tree configuré. La valeur sera définie aux noms des commutateurs réseau qui peuvent être impliqués dans les communications de la tâche, depuis le commutateur de niveau supérieur du système jusqu'au commutateur feuille et se terminant par le nom du nœud. Un point est utilisé pour séparer chaque nom de composant matériel.
SLURM_TOPOLOGY_ADDR_PATTERN
Ceci est défini uniquement si le système a le plugin topology/tree configuré. La valeur sera définie aux types de composants listés dans SLURM_TOPOLOGY_ADDR. Chaque composant sera identifié comme "switch" ou "node". Un point est utilisé pour séparer chaque type de composant matériel.
SLURM_TRES_PER_TASK
Défini à la valeur de --tres-per-task. Si --cpus-per-task ou --gpus-per-task est spécifié, il est également défini dans SLURM_TRES_PER_TASK comme s'il avait été spécifié dans --tres-per-task.
SLURMD_NODENAME
Nom du nœud exécutant le script de tâche.

EXEMPLES

Spécifiez un script de lot par nom de fichier sur la ligne de commande. Le script de lot spécifie une limite de temps de 1 minute pour la tâche.
$ cat myscript
#!/bin/sh
#SBATCH --time=1
srun hostname |sort
$ sbatch -N4 myscript
salloc: Granted job allocation 65537
$ cat slurm-65537.out
host1
host2
host3
host4
Passez un script de lot à sbatch sur l'entrée standard :
$ sbatch -N4 <<EOF
> #!/bin/sh
> srun hostname |sort
> EOF
sbatch: Submitted batch job 65541
$ cat slurm-65541.out
host1
host2
host3
host4
Pour créer une tâche hétérogène avec 3 composants, chacun allouant un ensemble unique de nœuds :
$ sbatch -w node[2-3] : -w node4 : -w node[5-7] work.bash
Submitted batch job 34987
