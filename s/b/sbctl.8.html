NOM

sbctl - Gestionnaire de démarrage sécurisé

SYNOPSIS

sbctl <commande>

DESCRIPTION

sbctl est un outil qui permet de créer des clés pour le démarrage sécurisé, de les enregistrer de manière sécurisée et de garder une trace des fichiers à signer.

COMMANDES DE SIGNATURE EFI

status

Affiche l'état actuel du démarrage sécurisé du système. Il vérifie si vous démarrez actuellement en UEFI avec le démarrage sécurisé activé, et si le mode d'installation a été activé.

create-keys

Crée un ensemble de clés de signature utilisées pour signer les binaires EFI. Actuellement, il créera les clés suivantes :
•Clé de Plateforme
•Clé d'Échange de Clés
•Clé de Base de Données de Signatures

-e, --export

Le répertoire où persister les clés exportées.

-d, --database-path

Chemin pour enregistrer le fichier GUID lors de la génération des clés.

enroll-keys

Enregistre la clé créée dans les variables EFI. 
Notez que certains appareils ont un micrologiciel matériel qui est signé et
validé lorsque le démarrage sécurisé est activé. Ne pas valider ce micrologiciel
pourrait rendre les appareils inutilisables. Il est recommandé
d'enregistrer vos propres clés avec des certificats Microsoft.

-m, --microsoft

Enregistre les certificats du fournisseur UEFI de Microsoft dans la base de données de signatures.

Voir Option ROM*.

Enregistre les sommes de contrôle du journal d'événements du TPM dans la base de données de signatures.

Enregistre des clés KEK et db personnalisées depuis "/var/lib/sbctl/keys/custom/KEK/", "/var/lib/sbctl/keys/custom/db/", respectivement.

Enregistre les signatures de dbDefault, KEKDefault ou PKDefault. Ceci est utile si sbctl ne fournit pas vos certificats OEM, ou n'inclut pas tous les certificats.

PAQUETS

Note : Ceci est en cours de dépréciation. Veuillez passer à dracut/mkinitcpio/ukify.

Normalement, seul le noyau est signé avec vos clés de démarrage sécurisé. Cela signifie que la ligne de commande du noyau et l'initramfs peuvent être modifiées sans possibilité de vérification.

Les paquets sont des exécutables EFI qui regroupent les trois (initramfs, noyau et ligne de commande) en un seul fichier facile à signer. Éviter tout fichier non signé au démarrage rend l'ensemble du processus plus résistant aux falsifications.

Lorsqu'un paquet est généré, sa configuration est stockée dans la base de données des paquets (voir FICHIERS). Les exécutions ultérieures de sbctl generate-bundles reconstruiront ces paquets, vous n'avez donc pas besoin de réspécifier tous les paramètres après chaque mise à jour du système.

Astuce : systemd-boot affichera automatiquement les entrées pour tous les paquets trouvés dans esp/EFI/Linux/*.efi.

TYPES DE CLÉS SUPPORTÉS

sbctl prend actuellement en charge le stockage des clés sous forme de fichiers simples non chiffrés, ou sous forme de clés protégées par TPM.

Les fichiers simples non chiffrés (file) ne doivent être utilisés que lorsque la partition racine est chiffrée. C'est le type de clé par défaut pour des raisons historiques. Les clés de fichier sont codées en dur sur RSA 4096.

Les clés protégées par TPM (tpm) sont protégées à l'intérieur du TPM et disponibles s'il existe un TPM accessible sur le système. Les politiques TPM ne sont pas prises en charge, ce qui signifie que nous ne pouvons pas sceller les clés en fonction de l'état du système. Notez que les clés TPM sont codées en dur sur RSA 2048, ce qui est généralement la force de bits la plus élevée prise en charge par les TPM.

Lors de la création d'une hiérarchie de clés pour le démarrage sécurisé, l'utilisateur peut décider du type de clé pour chaque clé de la hiérarchie. Comme les TPM peuvent être lents pour signer, il est généralement conseillé de garder PK et KEK dans le TPM, tandis que la clé db peut être une clé standard de type file.

Notez que la protection par mot de passe n'est actuellement pas prise en charge.

LANDLOCK

sbctl prend en charge Landlock et tentera de restreindre l'accès aux chemins de fichiers là où c'est nécessaire pendant l'exécution. Toute tentative d'établir un accès réseau est également restreinte.

Cette fonctionnalité peut être désactivée en définissant landlock: false dans le fichier de configuration, ou en passant --disable-landlock à sbctl.

OPTION ROM

Voir https://github.com/Foxboron/sbctl/wiki/FAQ#option-rom

UTILISATION

Note : Pour utiliser des clés de démarrage sécurisé personnalisées, il est important de redémarrer dans la configuration du firmware (systemctl reboot --firmware-setup) et de naviguer dans le menu Démarrage Sécurisé pour entrer en Mode de Configuration. Ceci est normalement accompli en supprimant/effaçant les clés de démarrage sécurisé (ou au minimum la clé de plateforme) tout en laissant le mode de démarrage sécurisé activé. Certains firmwares ont un Mode Personnalisé qui désactive uniquement la vérification de signature et ne devrait donc pas être activé sauf s'il n'y a pas d'autre moyen d'accéder à la gestion des clés. Si cette étape n'est pas terminée, l'enrôlement de clés personnalisées sera rejeté par le firmware.

Ensuite, il faut créer les clés pour le démarrage sécurisé. create-keys crée la hiérarchie de clés nécessaire au démarrage sécurisé dans "/var/lib/sbctl/keys".

# sbctl create-keys
Créé UUID de propriétaire a9fbbdb7-a05f-48d5-b63a-08c5df45ee70
Création des clés de démarrage sécurisé...✔
Clés de démarrage sécurisé créées !

Ensuite, il faut enrôler les clés dans le firmware efi. sbctl prend en charge l'exécution de cette opération sur un système en direct au lieu d'avoir à démarrer ou exécuter un outil de gestion de clés depuis le shell UEFI.

Note : Cela peut échouer en raison de problèmes de firmware et d'options uniques dans le menu BIOS de la machine. De plus, certains appareils ont un firmware matériel signé et validé lorsque le démarrage sécurisé est activé. Ne pas valider ce firmware pourrait rendre les appareils inutilisables. Il est recommandé d'enrôler vos propres clés avec des certificats Microsoft en utilisant l'option -m. Voir Option ROM* ci-dessus.

# sbctl enroll-keys
Enrôlement des clés dans les variables EFI...✔
Clés enrôlées dans les variables EFI !

Après avoir réussi à enrôler les clés, nous devons signer notre chaîne de démarrage actuelle. Traditionnellement, sur les systèmes UEFI, on peut avoir une partition système EFI (ESP) sur /efi, /boot ou /boot/efi. On peut généralement trouver la bonne en regardant les points de montage ou en trouvant le répertoire EFI sur l'ESP.

Le fichier le plus important à signer est le noyau. Cet emplacement diffère selon les distributions mais peut généralement être trouvé sur l'ESP ou /boot. Nous utilisons --save pour stocker le chemin du fichier, de sorte que nous n'ayons pas besoin de le signer manuellement plus tard.

Notez que sbctl ne peut suivre que les chemins de fichiers. Sur les noyaux versionnés, cela peut s'avérer délicat.

# sbctl sign --save /efi/vmlinuz-linux
✔ Signé /efi/vmlinuz-linux

Ensuite, il faut signer le chargeur de démarrage. Celui-ci se trouve généralement au chemin standard ci-dessous, mais peut différer selon les installations.

# sbctl sign --save /efi/EFI/BOOT/BOOTX64.EFI
✔ Signé /efi/EFI/BOOT/BOOTX64.EFI

sbctl est capable de trouver et de vérifier l'ESP, ainsi que tous les fichiers enregistrés pour vérifier que nous avons signé les fichiers nécessaires.

# sbctl verify
Vérification de la base de données de fichiers et des images EFI dans /efi...
✔ /efi/EFI/BOOT/BOOTX64.EFI est signé
✔ /efi/vmlinuz-linux est signé

Une fois que nous avons confirmé que tout fonctionne, nous pouvons redémarrer. Une fois que nous nous sommes reconnectés, nous pouvons vérifier l'état du système. Il ne devrait plus être nécessaire de réactiver le démarrage sécurisé ou d'entrer en mode utilisateur dans le firmware.

$ sbctl status
Installé :  ✓ sbctl est installé
GUID propriétaire : a7b893cc-949d-408c-b5cc-6e7d0370fdb6
Mode de configuration : ✓ Désactivé
Démarrage sécurisé :    ✓ Activé

Lorsque nous effectuons une mise à jour du système, nous pouvons exécuter sign-all pour resigner tous les fichiers enregistrés précédemment.

# sbctl sign-all
Le fichier a déjà été signé /boot/vmlinuz-linux
✓ Signé /efi/EFI/BOOT/BOOTX64.EFI

NAME

sbctl — Secure Boot Key management utility

SYNOPSIS

sbctl [-d | --debug] [-v | --verbose] [-h | --help] [-V | --version]

sbctl [COMMAND] [--help]

DESCRIPTION

The sbctl utility manages your Secure Boot keys and allows you to manage your EFI binaries. It is intended to make it easier for users to enable Secure Boot without having to create and manage keys manually.

sbctl provides a unified interface for managing Secure Boot keys, enrolling them into your firmware, and signing EFI binaries.

sbctl is designed to be simple and easy to use. It uses a database to store information about your keys and EFI binaries. This allows you to manage your Secure Boot configuration from a single location.

EFI SIGNING COMMANDS

These commands are used for signing EFI binaries:

sign
Sign EFI binaries with the enrolled keys.
enroll
Enroll keys into the firmware.
revoke
Revoke keys from the firmware.

EFI BINARY COMMANDS

These commands are used for managing EFI binaries:

list
List EFI binaries that are currently signed.
add
Add EFI binaries to be signed.
remove
Remove EFI binaries from being signed.

OPTIONS

-d, --debug
Enable debug logging.
-v, --verbose
Enable verbose output.
-h, --help
Display help message.
-V, --version
Display version information.

BUNDLES

Unified kernel images (UKI) are UEFI executables that bundle the initramfs, kernel, and cmdline into a single executable that can be signed for secure boot. This allows you to authenticate larger parts of the bootchain instead of only signing the kernel.

# sbctl bundle -i /boot/intel-ucode.img
               -l /usr/share/systemd/bootctl/splash-arch.bmp
               -k /boot/vmlinuz-linux
               -f /boot/initramfs-linux-lts.img
               -c /etc/kernel/cmdline
               /efi/EFI/Linux/linux-linux.efi

Note that dracut(8) and mkinitcpio(8) support unified kernel features, and they should be preferred over the sbctl implementation. It is mostly provided in the cases where this feature is not supported by the initramfs generator of the distribution.

SUPPORTED KEY TYPES

sbctl supports the following key types:

PK (Platform Key)
The root of trust for Secure Boot.
KEK (Key Exchange Key)
Used to exchange keys with the firmware.
db (Signature Database)
Contains the hashes of allowed executables.
dbx (Revoked Signatures Database)
Contains the hashes of disallowed executables.

LANDLOCK

sbctl integrates with the Linux Landlock Security Module to provide enhanced security for its operations. This ensures that sbctl only has access to the resources it needs to perform its tasks.

OPTION ROM

sbctl can also manage Option ROMs, which are firmware images that are loaded by the system during boot. This can be used to sign firmware images for devices such as network cards or graphics cards.

USAGE

Here is a typical workflow for using sbctl:

  1. Generate keys: 
    # sbctl create-keys
  2. Enroll keys into firmware: 
    # sbctl enroll-keys
  3. Sign your EFI binaries: 
    # sbctl sign -s /path/to/your/efi/binary
  4. (Optional) Create unified kernel images: 
    # sbctl bundle -k /boot/vmlinuz-linux -f /boot/initramfs-linux.img /efi/EFI/Linux/linux.efi

Refer to the specific command's help message for more details on usage.

NOTES

All commands that take path arguments convert them into absolute paths when saving them to the database.

EXIT STATUS

On success, 0 is returned, a non-zero failure code otherwise.

ENVIRONMENT VARIABLES

SYSTEMD_ESP_PATH, ESP_PATH

Defines the EFI system partition (ESP) location. This overrides the behaviour from sbctl where we query for the correct partition with lsblk. No checks are performed on this path and can be usefull for testing purposes.

SBCTL_UNICODE

If this value is "0" sbctl will replace the unicode symbols to equivalent ascii ones. The default value is assumed to be 1.

/var/lib/sbctl/bundles.db
