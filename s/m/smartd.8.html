SMARTD(8) Outils de surveillance SMART SMARTD(8)

NOM

smartd - Daemon de surveillance des disques SMART

SYNOPIS

smartd [options]

DESCRIPTION

[Cette page de manuel est générée pour la version Linux de smartmontools. Elle ne contient pas d'informations spécifiques à d'autres plateformes.]

smartd est un démon qui surveille le système de surveillance, d'analyse et de reporting technologique (SMART) intégré dans la plupart des disques durs et des disques SSD ATA/SATA et SCSI/SAS. Le but de SMART est de surveiller la fiabilité du disque dur et de prédire les pannes de disque, et d'effectuer différents types d'auto-tests de disque. Cette version de smartd est compatible avec les normes ACS-3, ACS-2, ATA8-ACS, ATA/ATAPI-7 et antérieures (voir REFERENCES ci-dessous).

smartd tentera d'activer la surveillance SMART sur les périphériques ATA (équivalent à smartctl -s on) et interroge ces périphériques ainsi que les périphériques SCSI toutes les 30 minutes (configurable), enregistrant les erreurs SMART et les changements d'attributs SMART via l'interface SYSLOG. L'emplacement par défaut pour ces notifications et avertissements SYSLOG dépend du système (typiquement /var/log/messages ou /var/log/syslog). Pour modifier cet emplacement par défaut, veuillez consulter l'option de ligne de commande '-l' décrite ci-dessous.

En plus de l'enregistrement dans un fichier, smartd peut également être configuré pour envoyer des avertissements par e-mail si des problèmes sont détectés. Selon le type de problème, vous voudrez peut-être exécuter des auto-tests sur le disque, sauvegarder le disque, remplacer le disque, ou utiliser un utilitaire du fabricant pour forcer la réallocation des secteurs de disque défectueux ou illisibles. Si des problèmes de disque sont détectés, veuillez consulter la page de manuel smartctl et la page web/FAQ de smartmontools pour des conseils supplémentaires.

Si vous envoyez un signal USR1 à smartd, il vérifiera immédiatement l'état des disques, puis reprendra l'interrogation des disques toutes les 30 minutes. Voir l'option '-i' ci-dessous pour plus de détails.

smartd peut être configuré au démarrage en utilisant le fichier de configuration /etc/smartd.conf (Windows : EXEDIR/smartd.conf). Si le fichier de configuration est modifié ultérieurement, smartd peut être informé de relire le fichier de configuration en lui envoyant un signal HUP, par exemple avec la commande :
killall -HUP smartd.

Au démarrage, si smartd trouve une erreur de syntaxe dans le fichier de configuration, il affichera un message d'erreur puis quittera. Cependant, si smartd est déjà en cours d'exécution, puis est informé par un signal HUP de relire le fichier de configuration, et trouve une erreur de syntaxe dans ce fichier, il affichera un message d'erreur puis continuera, ignorant le contenu du fichier de configuration (défectueux), comme si le signal HUP n'avait jamais été reçu.

Lorsque smartd s'exécute en mode de débogage, le signal INT (normalement généré depuis un shell avec CTRL-C) est traité de la même manière qu'un signal HUP : il fait recharger le fichier de configuration par smartd. Pour quitter smartd, utilisez CTRL-\.

[Linux uniquement] Si smartd est démarré comme service systemd(1) et que 'Type=Notify' est spécifié dans le fichier de service, le gestionnaire de service est notifié après un démarrage réussi. D'autres changements d'état sont rapportés via les messages STATUS de notification systemd. La notification de rechargements réussis (après le signal HUP) n'est pas prise en charge. Pour détecter ce type de démarrage de processus, smartd vérifie si la variable d'environnement 'NOTIFY_SOCKET' est définie. Notez qu'il est requis de définir l'option '-n' ('--nofork') dans la ligne de commande 'ExecStart=/usr/bin/smartd' si 'Type=Notify' est utilisé.

Au démarrage, en l'absence du fichier de configuration /etc/smartd.conf, le démon smartd recherche d'abord tous les périphériques qui prennent en charge SMART. La recherche est effectuée comme suit :

LINUX :
Examine toutes les entrées "/dev/hd[a-t]" pour les périphériques IDE/ATA, et "/dev/sd[a-z]", "/dev/sd[a-z][a-z]" pour les périphériques ATA/SATA ou SCSI/SAS. Les disques derrière les contrôleurs RAID ne sont pas inclus.

Si la directive '-d nvme' ou aucune directive '-d' n'est spécifiée, examine toutes les entrées "/dev/nvme[0-99]" pour les périphériques NVMe.

smartd surveille ensuite toutes les erreurs SMART possibles (correspondant à la directive '-a' dans le fichier de configuration ; voir la page de manuel smartd.conf(5)).

OPTIONS

-A PREFIX, --attributelog=PREFIX
Écrit les informations d'attributs du disque dans les fichiers
'PREFIX''MODEL-SERIAL[-NSID].PRT.csv'.
PREFIX spécifie le répertoire de destination s'il inclut une barre oblique finale. Sinon, son dernier composant de chemin spécifie le préfixe du nom de fichier. Le chemin doit être absolu, sauf si le mode de débogage est activé. MODEL et SERIAL sont construits à partir des informations d'identification du disque, les caractères invalides sont remplacés par un soulignement. NSID est l'identifiant de l'espace de noms NVMe si un espace de noms individuel est adressé. PRT est l'un de 'ata', 'scsi' ou 'nvme'.

À chaque cycle de vérification, les attributs sont enregistrés sous forme de ligne de tuples séparés par des tabulations qui consistent en des noms ou des valeurs séparés par des points-virgules. Chaque ligne est précédée d'une chaîne de date au format "aaaa-mm-jj HH:MM:SS" (en heure locale). La partie restante est spécifique au protocole :
[ATA] Écrit les attributs SMART ATA sous forme "id;valeur-normalisée;valeur-brute;".
[SCSI] Écrit les compteurs d'erreurs SCSI et la température sous forme "nom;valeur;".
[NVME : NOUVELLE FONCTIONNALITÉ EXPÉRIMENTALE SMARTD 7.5] Écrit les informations SMART/Santé NVMe sous forme "nom;valeur;".

-B [+]FICHIER, --drivedb=[+]FICHIER
[ATA uniquement] Lit la base de données des disques à partir de FICHIER. La nouvelle base de données remplace la base de données intégrée par défaut. Si '+' est spécifié, alors les nouvelles entrées précèdent les entrées intégrées. Veuillez consulter la page de manuel de smartctl(8) pour plus de détails.
-c FICHIER, --configfile=FICHIER
Lit les directives de configuration de smartd à partir de FICHIER, au lieu de l'emplacement par défaut /etc/smartd.conf (Windows : EXEDIR/smartd.conf). Si FICHIER n'existe pas, alors smartd affichera un message d'erreur et quittera avec un statut non nul. Ainsi, '-c /etc/smartd.conf' peut être utilisé pour vérifier l'existence du fichier de configuration par défaut.

En utilisant '-' pour FICHIER, la configuration est lue depuis l'entrée standard. Ceci est utile pour des commandes comme :
echo /dev/sdb -m utilisateur@maison -M test | smartd -c - -q onecheck
pour effectuer des vérifications rapides et simples sans fichier de configuration.

-C, --capabilities[=mail]
[Linux uniquement] Utilise libcap-ng pour supprimer les capabilities(7) non nécessaires du processus Linux. Les capabilities suivantes sont conservées dans les ensembles effectif et permissif : CAP_SYS_ADMIN, CAP_SYS_RAWIO, CAP_MKNOD. Si l'option '-u, --warn_as_user' (voir ci-dessous) est utilisée avec un utilisateur ou un groupe non privilégié, les capabilities suivantes sont également conservées : CAP_SETGID, CAP_SETUID. L'ensemble de limites de capabilities est effacé. Il dépend du MTA local si l'envoi d'e-mails peut être effectué depuis un processus root avec toutes les capabilities supprimées. Cela fonctionne avec le MTA postfix.

Si '--capabilities=mail' est spécifié, les capabilities suivantes sont ajoutées à l'ensemble de limites : CAP_SETGID, CAP_SETUID, CAP_CHOWN, CAP_FOWNER, CAP_DAC_OVERRIDE. Cela permet d'envoyer des e-mails avec le MTA exim.

-d, --debug
Exécute smartd en mode "debug". Dans ce mode, il affiche les informations de statut sur STDOUT au lieu de les enregistrer dans SYSLOG et ne fait pas de fork(2) en arrière-plan et ne se détache pas du terminal de contrôle. Dans ce mode, smartd affiche également des informations plus détaillées sur ce qu'il fait que lorsqu'il opère en mode "daemon". Dans ce mode, le signal INT (normalement généré depuis un terminal avec CTRL-C) fait recharger son fichier de configuration par smartd. Veuillez utiliser CTRL-\ pour quitter.
-D, --showdirectives
Affiche une liste (sur STDOUT) de toutes les directives possibles qui peuvent apparaître dans le fichier de configuration /etc/smartd.conf, puis quitte. Ces directives sont décrites dans la page de manuel smartd.conf(5). Elles peuvent apparaître dans le fichier de configuration après le nom du périphérique.

OPTIONS

-h, --help, --usage
Affiche le message d'utilisation sur STDOUT et quitte.
-i N, --interval=N
Définit l'intervalle entre les vérifications du disque à N secondes, où N est un entier décimal. La valeur minimale autorisée est dix et la valeur maximale est le plus grand entier positif qui peut être représenté sur votre système (souvent 2^31-1). La valeur par défaut est 1800 secondes. L'intervalle pourrait être remplacé par la directive '-c i=N', voir la page de manuel smartd.conf(5).

Notez que le superutilisateur peut faire vérifier l'état des disques par smartd à tout moment en lui envoyant le signal SIGUSR1, par exemple avec la commande :
kill -SIGUSR1 <pid>
où <pid> est le numéro d'identification du processus de smartd. On peut aussi utiliser :
killall -USR1 smartd
dans le même but.

-l FACILITY, --logfacility=FACILITY
Utilise lefacility syslog FACILITY pour enregistrer les messages de smartd. Ici FACILITY est l'un des local0, local1, ..., local7, ou daemon [par défaut]. Si cette option de ligne de commande n'est pas utilisée, alors par défaut les messages de smartd sont enregistrés dans le facility daemon.

Si vous souhaitez que les messages de smartd soient enregistrés ailleurs que dans l'emplacement par défaut, incluez (par exemple) '-l local3' dans sa liste d'arguments de démarrage. Dites au démon syslog d'enregistrer tous les messages du facility local3 dans (par exemple) '/var/log/smartd.log'.

Pour plus d'informations, veuillez vous référer aux pages de manuel du démon syslog local, typiquement syslogd(8), syslog-ng(8) ou rsyslogd(8).

-n, --no-fork
Ne pas se séparer en arrière-plan ; ceci est utile lorsqu'il est exécuté depuis des méthodes d'initialisation modernes comme initng, minit, supervise ou systemd.
-p NAME, --pidfile=NAME
Écrit le fichier pid NAME contenant le numéro d'identification du processus (PID) de smartd. Pour éviter les attaques par lien symbolique, assurez-vous que le répertoire dans lequel le fichier pid est écrit n'est accessible en écriture qu'à root. Sans cette option, ou si l'option --debug est donnée, aucun fichier PID n'est écrit au démarrage. Si smartd est tué par un signal masquable, le fichier pid est supprimé.
-q WHEN, --quit=WHEN
Spécifie quand, le cas échéant, smartd doit se terminer. Les arguments valides pour cette option sont :

nodev - Quitte s'il n'y a pas de périphériques à surveiller, ou si des erreurs sont trouvées au démarrage dans le fichier de configuration. C'est la valeur par défaut.

errors - Quitte s'il n'y a pas de périphériques à surveiller, ou si des erreurs sont trouvées dans le fichier de configuration /etc/smartd.conf au démarrage ou lors de son rechargement.

nodevstartup - Quitte s'il n'y a pas de périphériques à surveiller au démarrage. Mais continue de fonctionner si aucun périphérique n'est trouvé lors du rechargement du fichier de configuration.

never - Ne quitte qu'en cas d'erreur fatale (pas de mémoire système restante, arguments de ligne de commande invalides). Dans ce mode, même s'il n'y a pas de périphériques à surveiller, ou si le fichier de configuration /etc/smartd.conf contient des erreurs, smartd continuera à s'exécuter, attendant de charger un fichier de configuration listant des périphériques valides.

nodev0 - Identique à 'nodev', sauf que le code de sortie est 0 s'il n'y a pas de périphériques à surveiller.

nodev0startup - Identique à 'nodevstartup', sauf que le code de sortie est 0 s'il n'y a pas de périphériques à surveiller.

errors,nodev0 - Identique à 'errors', sauf que le code de sortie est 0 s'il n'y a pas de périphériques à surveiller.

onecheck - Démarre smartd en mode debug, enregistre ensuite les périphériques, vérifie une seule fois l'état SMART du périphérique, puis quitte avec un code de sortie zéro si toutes ces étapes se sont déroulées correctement.

Cette dernière option est destinée aux 'distributeurs' qui souhaitent créer des scripts automatisés pour déterminer s'il faut ou non démarrer automatiquement smartd après l'installation de smartmontools. Après avoir démarré smartd avec cette option de ligne de commande, les scripts d'installation de la distribution doivent attendre un temps raisonnable (disons dix secondes). Si smartd n'a pas quitté avec un code de sortie zéro à ce moment-là, le script doit envoyer un signal SIGTERM ou SIGKILL à smartd et supposer que smartd ne fonctionnera pas correctement sur l'hôte. Inversement, si smartd quitte avec un code de sortie zéro, alors il est sûr d'exécuter smartd en mode démon normal. Si smartd ne peut pas surveiller de périphériques ou rencontre d'autres problèmes, il retournera un code de sortie non nul.

showtests - Démarre smartd en mode debug, enregistre ensuite les périphériques, écrit ensuite une liste des futurs tests automatiques programmés sur la sortie standard, puis quitte avec un code de sortie zéro si toutes ces étapes se sont déroulées correctement. L'état SMART du périphérique n'est pas vérifié.

Cette option est destinée à tester si les directives '-s REGEX' dans smartd.conf auront l'effet désiré. La sortie liste les prochaines planifications de test, limitées à 5 tests par type et par périphérique. Ceci est suivi d'un résumé de tous les tests de chaque périphérique dans les 90 prochains jours.

-r TYPE, --report=TYPE
Destiné principalement à aider les développeurs de smartmontools à comprendre le comportement de smartmontools sur du matériel non conforme ou mal conforme. Cette option rapporte des détails sur les transactions de smartd avec le périphérique. L'option peut être utilisée plusieurs fois. Utilisée une seule fois, elle montre un enregistrement des transactions ioctl() avec le périphérique. Utilisée plus d'une fois, le détail de ces transactions ioctl() est rapporté plus en détail. Les arguments valides pour cette option sont :

ioctl - rapporte toutes les transactions ioctl().

ataioctl - rapporte uniquement les transactions ioctl() avec les périphériques ATA.

scsiioctl - rapporte uniquement les transactions ioctl() avec les périphériques SCSI.

nvmeioctl - rapporte uniquement les transactions ioctl() avec les périphériques NVMe.

Tout argument peut inclure un entier positif pour spécifier le niveau de détail qui doit être rapporté. L'argument doit être suivi d'une virgule puis de l'entier sans espaces. Par exemple, ataioctl,2 Le niveau par défaut est 1, donc '-r ataioctl,1' et '-r ataioctl' sont équivalents.

-s PREFIX, --savestates=PREFIX
Lit/écrit les informations d'état de smartd depuis/vers les fichiers
'PREFIX''MODEL-SERIAL[-NSID].PRT.state'.
Pour PREFIX, MODEL, SERIAL, NSID et PRT, voir l'option '-A' ci-dessus.

Les fichiers d'informations d'état conservent diverses informations entre les redémarrages de smartd, par exemple : les attributs SMART, les températures minimale et maximale du disque (directive '-W'), les informations sur le dernier e-mail d'avertissement envoyé (directive '-m'), l'heure de la prochaine vérification de l'expression régulière de test automatique ('-s' directive), et les informations sur les dernières entrées de journal d'erreurs signalées (directives '-l [x]error').

Les fichiers d'informations d'état sont lus au démarrage de smartd. Les fichiers sont toujours (ré)écrits après la lecture du fichier de configuration, avant la relecture du fichier de configuration (SIGHUP), avant l'arrêt de smartd, et après une vérification forcée par SIGUSR1. Après un cycle de vérification normal, un fichier n'est réécrit que si un changement important (qui entraîne généralement une sortie SYSLOG) s'est produit.

-w PATH, --warnexec=PATH
Exécute l'exécutable PATH au lieu du script par défaut lorsque smartd doit envoyer des messages d'avertissement. PATH doit pointer vers un fichier binaire exécutable ou un script. Le script par défaut est /usr/share/smartmontools/smartd_warning.sh.
-u USER[:GROUP], --warn-as-user=USER[:GROUP]
Exécute le script d'avertissement en tant qu'utilisateur non privilégié au lieu de root. L'utilisateur et le groupe optionnel peuvent être spécifiés comme des ID numériques ou des noms. Si aucun groupe n'est spécifié, le groupe par défaut de l'utilisateur est utilisé à la place.

Si un avertissement se produit, un processus enfant est créé avec fork(2). Ce processus ferme tous les descripteurs de fichier hérités, connecte stdio à /dev/null, change les ID utilisateur et groupe, supprime tous les ID de groupe supplémentaires et appelle ensuite la fonction popen(3) de la bibliothèque standard.

Si '0:0' est spécifié, l'utilisateur et le groupe ne sont pas modifiés, mais les autres actions s'appliquent toujours.

Si '-' est spécifié, popen(3) est appelé directement. C'est la valeur par défaut.

-V, --version, --license, --copyright
Affiche la version, le copyright, la licence, la page d'accueil et les informations de révision SVN de votre copie de smartd sur STDOUT, puis quitte.

EXEMPLES

smartd
Exécute le démon en mode séparé. C'est la manière normale d'exécuter smartd. Les entrées sont enregistrées dans SYSLOG.

smartd -d -i 30
Exécute en mode premier plan (debug), vérifiant l'état du disque toutes les 30 secondes.

smartd -q onecheck
Enregistre les périphériques et vérifie l'état des périphériques une seule fois. Le code de sortie (la variable shell $?) sera zéro si tout s'est bien passé, et non nul si aucun périphérique n'a été détecté ou si un autre problème a été rencontré.

CONFIGURATION

La syntaxe du fichier smartd.conf(5) est discutée séparément.

NOTES

smartd fera des entrées de journal au niveau de log LOG_INFO si les valeurs normalisées des attributs SMART ont changé, comme rapporté en utilisant les directives '-t', '-p', ou '-u'. Par exemple :
'Device: /dev/sda, SMART Attribute: 194 Temperature_Celsius changed from 94 to 93'
Notez que dans ce message, la valeur donnée est la valeur 'Normalisée' et non la valeur 'Brute' de l'Attribut (la température du disque dans ce cas est d'environ 22 Celsius). Les directives '-R' et '-r' modifient ce comportement, de sorte que l'information soit également imprimée avec les valeurs Brutes, par exemple :
'Device: /dev/sda, SMART Attribute: 194 Temperature_Celsius changed from 94 [Raw 22] to 93 [Raw 23]'
Ici, th

smartd(8) — Linux manual pages

NOTES

Les valeurs Raw sont les températures réelles du disque en Celsius. La manière dont les valeurs Raw sont imprimées, et les noms sous lesquels les Attributs sont rapportés, est régie par les diverses directives '-v Num,Description' décrites précédemment.

Veuillez consulter la page de manuel smartctl pour plus d'explications sur les différences entre les valeurs d'Attribut Normalisées et Brutes.

smartd créera des entrées de journal au niveau de journalisation LOG_CRIT si un attribut SMART a échoué, par exemple :
'Device: /dev/sdc, Failed SMART Attribute: 5 Reallocated_Sector_Ct'
Ce niveau de journalisation est utilisé pour les rapports activés par les directives '-H', '-f', '-l selftest', et '-l error'. Les entrées rapportant l'échec des attributs SMART de préfail ne doivent pas être ignorées : elles signifient que le disque est en train de tomber en panne. Utilisez l'utilitaire smartctl pour enquêter.

LOG TIMESTAMP TIMEZONE

Lorsque smartd crée des entrées de journal, celles-ci sont horodatées. Les horodatages sont dans le fuseau horaire local de l'ordinateur, qui est généralement défini soit par la variable d'environnement 'TZ', soit par un fichier de fuseau horaire tel que /etc/localtime. Vous pourriez souhaiter changer le fuseau horaire pendant que smartd est en cours d'exécution (par exemple, si vous transportez un ordinateur portable dans un nouveau fuseau horaire et que vous ne le redémarrez pas). En raison d'un bug dans la fonction tzset(3) de nombreuses bibliothèques C standard Unix, les horodatages de fuseau horaire de smartd pourraient ne pas changer. Pour certains systèmes, smartd contournera ce problème *si* le fuseau horaire est défini à l'aide de /etc/localtime. Le contournement *échoue* si le fuseau horaire est défini à l'aide de la variable 'TZ' (ou d'un fichier auquel elle pointe).

EXIT STATUS

Le statut de sortie (valeur de retour) de smartd peut avoir les valeurs suivantes :

0 :
Démarrage du démon réussi, ou smartd a été arrêté par un SIGTERM (ou en mode débogage, un SIGQUIT).
1 :
La ligne de commande n'a pas pu être analysée.
2 :
Il y a eu une erreur de syntaxe dans le fichier de configuration.
3 :
L'exécution du démon a échoué.
4 :
Impossible de créer le fichier PID.
5 :
Le fichier de configuration n'existe pas (uniquement renvoyé en conjonction avec l'option '-c').
6 :
Le fichier de configuration existe, mais ne peut pas être lu.
8 :
smartd a manqué de mémoire lors du démarrage.
10 :
Une incohérence a été trouvée dans les structures de données internes de smartd. Cela ne devrait jamais arriver. Cela doit être dû à un bug de code ou de compilateur. *Veuillez* signaler de tels échecs aux développeurs de smartmontools, voir REPORTING BUGS ci-dessous.
16 :
Un périphérique explicitement listé dans /etc/smartd.conf ne peut pas être surveillé.
17 :
smartd n'a trouvé aucun périphérique à surveiller. Cela pourrait être modifié à 0 (succès) avec l'une des options '-q \*nodev0*', voir ci-dessus.
254 :
En mode démon, smartd a reçu un SIGINT ou SIGQUIT. (Notez qu'en mode débogage, SIGINT a le même effet que SIGHUP, et fait que smartd recharge son fichier de configuration. SIGQUIT a le même effet que SIGTERM et provoque la sortie de smartd avec un statut de sortie nul.
132 et plus
smartd a été arrêté par un signal qui n'est pas explicitement listé ci-dessus. Le statut de sortie est alors 128 plus le numéro du signal. Par exemple, si smartd est arrêté par SIGKILL (signal 9), le statut de sortie est 137.

Le fonctionnement de SMART a été initialement défini par les spécifications SFF-8035i révision 2 et SFF-8055i révision 1.4. Ce sont des publications du Small Form Factors (SFF) Committee.

Des liens vers ces documents et d'autres peuvent être trouvés sur la page Liens du Wiki smartmontools à l'adresse https://www.smartmontools.org/wiki/Links.
