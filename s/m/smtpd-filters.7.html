NOM

smtpd-filters — API de filtrage pour le démon smtpd

DESCRIPTION

Le démon smtpd(8) fournit une implémentation du protocole SMTP (Simple Mail Transfer Protocol), qui permet aux machines ordinaires de devenir des échangeurs de courrier (MX). Certaines fonctionnalités couramment utilisées par les MX, telles que les rapports de livraison ou le filtrage de spam, sortent du cadre du SMTP et sont trop complexes pour tenir dans smtpd(8).

Étant donné qu'un MX peut avoir besoin de fournir ces fonctionnalités, smtpd(8) offre une API pour étendre son comportement via smtpd-filters.

À l'exécution, smtpd(8) peut signaler des événements à smtpd-filters, en demandant quelle réponse il doit donner à ces événements. Cela permet à la logique de décision de s'appuyer sur des programmes tiers.

CONCEPTION

smtpd-filters sont des programmes qui s'exécutent en tant que processus autonomes uniques ; ils ne partagent pas l'espace mémoire de smtpd(8). Ils sont exécutés par smtpd(8) au démarrage et sont censés s'exécuter dans une boucle infinie, lisant les événements et les requêtes de filtrage depuis stdin(4), écrivant les réponses sur stdout(4) et journalisant sur stderr(4). Il ne leur est pas permis de se terminer.

Étant donné que smtpd-filters sont des programmes autonomes qui communiquent avec smtpd(8) via des descripteurs de fichiers (fd), ils peuvent s'exécuter sous des utilisateurs différents de smtpd(8) et peuvent être écrits dans n'importe quel langage. Les smtpd-filters ne doivent pas utiliser d'E/S bloquantes ; ils doivent pouvoir répondre de manière asynchrone à smtpd(8).

SIGNALER ET FILTRER

L'API repose sur deux flux : le flux de signalement (report) et le flux de filtrage (filter).

Le flux de signalement est un flux unidirectionnel qui permet à smtpd(8) d'informer en temps réel les smtpd-filters des événements. Les événements de signalement n'attendent pas de réponse de la part des smtpd-filters ; ils sont juste destinés à fournir des informations. Un filtre devrait pouvoir répliquer l'état de smtpd(8) pour une session en collectant les informations provenant des événements de signalement. Aucune décision n'est jamais prise par le flux de signalement.

Le flux de filtrage est un flux bidirectionnel qui permet à smtpd(8) de demander aux smtpd-filters ce qu'il doit faire d'une session à une phase donnée. Les requêtes de filtrage attendent une réponse des smtpd-filters ; smtpd(8) ne laissera pas la session avancer avant. Une décision doit toujours être prise par le flux de filtrage.

Il est parfois possible de s'appuyer sur les requêtes de filtrage pour collecter des informations, mais comme une réponse est attendue par smtpd(8), c'est plus coûteux que d'utiliser les événements de signalement. Le modèle correct pour écrire des filtres est d'utiliser les événements de signalement pour créer un état local pour une session, puis d'utiliser les requêtes de filtrage pour prendre des décisions basées sur cet état. Le seul cas où l'utilisation de requêtes de filtrage au lieu d'événements de signalement est correct est lorsqu'une décision est requise pour la requête de filtrage et qu'il n'y a pas besoin de plus d'informations que celles de l'événement lui-même.

PROTOCOLE

Le protocole consiste en des lignes lisibles par l'homme échangées entre smtpd-filters et smtpd(8), via des descripteurs de fichiers.

Le protocole commence par une négociation. Tout d'abord, smtpd(8) fournit aux smtpd-filters des informations de configuration générales sous forme de lignes clé-valeur :

config|smtpd-version|7.8.0
config|protocol|0.7
config|smtp-session-timeout|300
config|subsystem|smtp-in
config|ready

Ensuite, les smtpd-filters enregistrent le flux, le sous-système et l'événement qu'ils souhaitent gérer :

register|report|smtp-in|link-connect
register|ready

Enfin, smtpd(8) émet des événements de signalement et des requêtes de filtrage, s'attendant à ce que les smtpd-filters répondent ou non en fonction du flux :

report|0.7|1576146008.006099|smtp-in|link-connect|7641df9771b4ed00|mail.openbsd.org|pass|199.185.178.25:33174|45.77.67.80:25
report|0.7|1576147242.200225|smtp-in|link-connect|7641dfb3798eb5bf|mail.openbsd.org|pass|199.185.178.25:31205|45.77.67.80:25
report|0.7|1576148447.982572|smtp-in|link-connect|7641dfc063102cbd|mail.openbsd.org|pass|199.185.178.25:24786|45.77.67.80:25

Le caractère “|” ne peut apparaître que dans le dernier champ d'une charge utile, auquel cas il doit être considéré comme un caractère ordinaire et non comme un séparateur. Aucun autre champ ne peut contenir de “|”.

La liste des sous-systèmes et des événements, ainsi que le format des requêtes et des réponses, sont documentés dans les sections ci-dessous.

CONFIGURATION

Lors de la négociation initiale, smtpd(8) émet une série de clés et de valeurs de configuration. La liste est destinée à être ignorée par les smtpd-filters qui n'en ont pas besoin et consommée gracieusement par les filtres qui en ont.

Il existe actuellement trois clés :

config|smtpd-version|7.8.0
config|protocol|0.7
config|smtp-session-timeout|300
config|subsystem|smtp-in

Lorsque smtpd(8) a envoyé toutes les clés de configuration, il émet la ligne suivante :

config|ready

ÉVÉNEMENTS DE SIGNALEMENT

Il n'y a actuellement qu'un seul sous-système pris en charge dans l'API : smtp-in.

Chaque événement de signalement est généré par smtpd(8) sous forme d'une ligne unique similaire à celle ci-dessous :

report|0.7|1576146008.006099|smtp-in|link-connect|7641df9771b4ed00|mail.openbsd.org|pass|199.185.178.25:33174|45.77.67.80:25

Le format se compose d'un préfixe de protocole contenant le flux, la version du protocole, l'horodatage, le sous-système, l'événement et l'identifiant unique de session, séparés par des “|” :

report|0.7|1576146008.006099|smtp-in|link-connect|7641df9771b4ed00

Il est suivi d'un suffixe contenant les paramètres spécifiques à l'événement, également séparés par des “|” :

mail.openbsd.org|pass|199.185.178.25:33174|45.77.67.80:25

La liste des événements et des paramètres spécifiques à l'événement pour smtp-in est la suivante :

link-connect: rdns fcrdns src dest
Cet événement est généré lors de la connexion.

rdns contient le nom d'hôte DNS inverse pour l'extrémité distante ou une chaîne vide si aucun.

fcrdns contient la chaîne “pass” ou “fail” selon que l'extrémité distante valide FCrDNS.

src contient soit l'adresse IP et le port de l'adresse source, au format “address:port”, soit le chemin vers une socket UNIX au format “unix:/chemin”.

dest contient soit l'adresse IP et le port de l'adresse de destination, au format “address:port”, soit le chemin vers une socket UNIX au format “unix:/chemin”.

link-greeting: hostname
Cet événement est généré lors de l'affichage de la bannière du serveur.

hostname contient le nom d'hôte affiché dans la bannière.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

link-identify: method identity
Cet événement est généré lors de la commande « HELO » ou « EHLO » provenant du client.

method contient la chaîne « HELO » ou « EHLO » indiquant la méthode utilisée par le client.

identity contient l'identité fournie par le client.

link-tls: tls-string
Cet événement est généré lors de la négociation réussie du TLS.

tls-string contient une liste de propriétés TLS séparées par des deux-points, incluant la version TLS, la suite de chiffrement utilisée par la session et la force du chiffrement en bits.

link-disconnect
Cet événement est généré lors de la déconnexion du client.
link-auth: result username
Cet événement est généré lors d'une tentative d'authentification par le client.

result contient la chaîne « pass », « fail » ou « error » en fonction du résultat de la tentative d'authentification.

username contient le nom d'utilisateur utilisé pour la tentative d'authentification.

tx-reset: [message-id]
Cet événement est généré lorsqu'une transaction est réinitialisée.

Si la réinitialisation a eu lieu pendant une transaction, message-id contient l'identifiant de la transaction en cours de réinitialisation.

tx-begin: message-id
Cet événement est généré lorsqu'une transaction est initiée.

message-id contient l'identifiant de la transaction.

tx-mail: message-id result address
Cet événement est généré lorsque le client émet « MAIL FROM ».

message-id contient l'identifiant de la transaction.

result contient « ok » si l'expéditeur a été accepté, « permfail » s'il a été rejeté ou « tempfail » s'il a été rejeté pour une erreur transitoire.

address contient l'adresse e-mail de l'expéditeur. L'adresse est normalisée et nettoyée, les caractères « < » et « > » sont supprimés, ainsi que tous les paramètres de « MAIL FROM ».

tx-rcpt: message-id result address
Cet événement est généré lorsque le client émet « RCPT TO ».

message-id contient l'identifiant de la transaction.

result contient « ok » si le destinataire a été accepté, « permfail » s'il a été rejeté ou « tempfail » s'il a été rejeté pour une erreur transitoire.

address contient l'adresse e-mail du destinataire. L'adresse est normalisée et nettoyée, les caractères « < » et « > » sont supprimés, ainsi que tous les paramètres de « RCPT TO ».

tx-envelope: message-id envelope-id
Cet événement est généré lorsqu'une enveloppe est acceptée.

envelope-id contient l'identifiant unique de l'enveloppe.

tx-data: message-id result
Cet événement est généré lorsque le client a émis « DATA ».

message-id contient l'identifiant unique de la transaction.

result contient « ok » si le serveur a accepté le message pour traitement, « permfail » s'il n'a pas été accepté et « tempfail » si une erreur transitoire a empêché le traitement du message.

tx-commit: message-id message-size
Cet événement est généré lorsqu'une transaction a été acceptée par le serveur.

message-id contient l'identifiant unique de la transaction SMTP.

message-size contient la taille du message soumis lors de la phase « DATA » de la transaction SMTP.

tx-rollback: message-id
Cet événement est généré lorsqu'une transaction a été rejetée par le serveur.

message-id contient l'identifiant unique de la transaction SMTP.

protocol-client: command
Cet événement est généré pour chaque commande soumise par le client. Il contient la commande brute telle qu'elle a été reçue par le serveur.

command contient la commande émise par le client au serveur.

protocol-server: response
Cet événement est généré pour chaque réponse émise par le serveur. Il contient la réponse brute telle qu'elle a été émise par le serveur.

response contient la réponse émise par le serveur au client.

filter-report: filter-kind name message
Cet événement est généré lorsqu'un filtre émet un rapport.

filter-kind peut être « builtin » ou « proc », selon que le filtre est un filtre intégré à smtpd(8) ou un filtre proc implémentant l'API.

name est le nom du filtre qui a généré le rapport.

message est un message spécifique au filtre.

filter-response: phase response [param]
Cet événement est généré lorsqu'un filtre répond à une demande de filtrage.

phase contient le nom de la phase de la demande. Les phases sont documentées dans la section suivante.

response contient la réponse du filtre à la demande, c'est soit l'un des éléments suivants : « proceed », « report », « reject », « disconnect », « junk » ou « rewrite ».

Si spécifié, param est le paramètre de la réponse.

timeout
Cet événement est généré lorsqu'un délai d'attente se produit pour une session.

DEMANDES DE FILTRE

Actuellement, un seul sous-système est pris en charge dans l'API : smtp-in.

Les demandes de filtre permettent à smtpd(8) d'interroger smtpd-filters sur la manière de traiter une session à une phase donnée. De plus, elles permettent à smtpd-filters de modifier le contenu d'un message en ajoutant, modifiant ou supprimant des lignes d'entrée, de manière similaire à ce que feraient des programmes comme sed(1) ou grep(1).

Chaque demande de filtre est générée par smtpd(8) sous forme d'une seule ligne similaire à celle ci-dessous. Les champs sont séparés par le caractère « | ».

filter|0.7|1576146008.006099|smtp-in|connect|7641df9771b4ed00|1ef1c203cc576e5d|mail.openbsd.org|199.185.178.25

Le format comprend un préfixe de protocole contenant le flux, la version du protocole, l'horodatage, le sous-système, la phase de filtrage, l'identifiant unique de la session et un jeton opaque que le filtre doit fournir dans sa réponse :

filter|0.7|1576146008.006099|smtp-in|connect|7641df9771b4ed00|1ef1c203cc576e5d

Il est suivi d'un suffixe contenant les paramètres spécifiques à la phase de la demande de filtre, également séparés par « | » :

mail.openbsd.org|199.185.178.25

Contrairement aux événements de rapport, smtpd(8) attend des réponses aux demandes de filtre et ne permettra pas à une session de progresser tant que le filtre n'aura pas indiqué à smtpd(8) comment la traiter.

Pour toutes les phases sauf « data-line », les réponses doivent suivre la même structure : un message de type « filter-result », suivi de l'identifiant unique de la session, du jeton opaque, d'une décision et de paramètres optionnels spécifiques à la décision :

filter-result|7641df9771b4ed00|1ef1c203cc576e5d|proceed
filter-result|7641df9771b4ed00|1ef1c203cc576e5d|reject|550 nope

Les décisions possibles pour un message « filter-result » sont documentées ci-dessous.

filter|0.7|1576146008.006103|smtp-in|data-line|7641df9771b4ed00|1ef1c203cc576e5d|line 2
filter|0.7|1576146008.006105|smtp-in|data-line|7641df9771b4ed00|1ef1c203cc576e5d|.

DESCRIPTION

The smtpd-filters utility is used to process the output from smtpd-filters.

Note that filters may be chained, and the lines that are input into a subsequent filter are the lines that are output from a previous filter.

The response to “data-line” requests use their own construct. A “filter-dataline” prefix, followed by the unique session identifier, the opaque token and the output line as follows:

filter-dataline|7641df9771b4ed00|1ef1c203cc576e5d|line 1
filter-dataline|7641df9771b4ed00|1ef1c203cc576e5d|line 2
filter-dataline|7641df9771b4ed00|1ef1c203cc576e5d|.

The list of events and event-specific parameters for smtp-in are as follows:

connect: rdns src
This request is emitted after connection, before the banner is displayed.

src contains either the IP address of the source (a.b.c.d for IPv4 or [x:x:x:x:x:x:x:x] IPv6) or “local” (for UNIX sockets).

helo: identity
This request is emitted after the client has emitted “HELO”.
ehlo: identity
This request is emitted after the client has emitted “EHLO”.
starttls: tls-string
This request is emitted after the client has requested “STARTTLS”.
auth: auth
This request is emitted after the client has requested “AUTH”.
mail-from: address
This request is emitted after the client has requested “MAIL FROM”.
rcpt-to: address
This request is emitted after the client has requested “RCPT TO”.
data
This request is emitted after the client has requested “DATA”.
data-line: line
This request is emitted for each line of input in the “DATA” phase. The lines are raw dot-escaped SMTP DATA input, terminated with a single dot.
commit
This request is emitted after the final single dot is received.

For every filtering phase, excepted “data-line”, the following decisions may be taken by a filter:

proceed
No action is taken, session or transaction may be passed to the next filter.
junk
The session or transaction is marked as spam. smtpd(8) will prepend an “X-Spam” header to the message.
reject error
The command is rejected with the message error. The message must be a valid SMTP message including status code, 5xx or 4xx.

Messages starting with a 5xx status result in a permanent failure, those starting with a 4xx status result in a temporary failure.

Messages starting with a 421 status will result in a client disconnect.

disconnect error
The client is disconnected with the message error. The message must be a valid SMTP message including status code, 5xx or 4xx.

Messages starting with a 5xx status result in a permanent failure, those starting with a 4xx status result in a temporary failure.

rewrite parameter
The command parameter is rewritten.

This decision allows a filter to perform a rewrite of client-submitted commands before they are processed by the SMTP engine. parameter is expected to be a valid SMTP parameter for the command.

report parameter
Generates a report with parameter for this filter.
