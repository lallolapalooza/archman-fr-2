SMOKEPING_EXTEND(7) SmokePing SMOKEPING_EXTEND(7)

NOM

smokeping_extend - Notes sur l'extension de Smokeping

APERÇU

Ce document est destiné à guider les auteurs potentiels dans la rédaction de nouvelles sondes Smokeping. Il décrit principalement l'interface entre Smokeping et ses modules de sonde. Si cela vous semble trop compliqué à comprendre, regardez les modules existants pour des exemples.

Les commentaires et les propositions de modifications ou d'ajouts sont les bienvenus. Veuillez les envoyer à la liste de diffusion smokeping-users. Les patchs contre la source POD de ce document sont les plus appréciés.

CHOIX D'UNE CLASSE DE BASE

La première chose à décider est quelle classe de base utiliser pour votre sonde. Pour la plupart des utilisations (sinon toutes), c'est un choix entre "Smokeping::probes::base" et "Smokeping::probes::basefork". La première est destinée aux sondes qui peuvent mesurer leurs cibles en une seule fois, tandis que la seconde est pour les sonder une par une, potentiellement dans plusieurs sous-processus concurrents.

Pour le moment, les seules sondes qui utilisent "Smokeping::probes::base" sont les dérivés de FPing. Toutes les autres utilisent "Smokeping::probes::basefork", et il y a de fortes chances que vous devriez en faire autant. Ce document se concentrera donc sur ce dernier cas.

FICHIER SQUELETTE

Le module "Smokeping::probes::skel" est une sonde non fonctionnelle conçue pour servir de bonne base à un nouveau module de sonde. Copiez le fichier, "lib/probes/skel.pm", sous un nouveau nom et remplissez simplement les blancs :) Notez que les noms des vrais modules de sonde doivent commencer par une majuscule.

DOCUMENTATION DE SONDE

La documentation de la sonde est générée à partir du code source avec les arguments smokeping "--man" ou "--makepod". La documentation POD intégrée doit pointer vers la documentation réelle, afin que les utilisateurs curieux de la commande "perldoc" voient ce qui se passe. Toutes les sondes actuelles font cela.

Vous devez fournir la méthode "pod_hash" qui retourne une référence à une table de hachage avec des clés correspondant aux noms de section que vous souhaitez dans la page de manuel. Les noms de section pris en charge sont "name", "overview", "description", "authors", "notes", "bugs", et "see_also". Si vous n'avez pas besoin d'une section particulière, laissez-la simplement de côté.

Les sections spéciales "synopsis" et "variables" sont générées automatiquement à partir de la description de vos variables. Voir ci-dessous.

Notez que si vous utilisez des 'here documents' ('<<') qui contiennent du balisage POD, vous devez échapper le balisage pour qu'il n'apparaisse pas dans la documentation POD intégrée. La plupart des sondes le font comme ceci :

my $e = "=";
my $doc = <<DOC;
${e}head1 TITRE DE SECTION
DOC

DESCRIPTION DE SONDE

La sonde doit offrir la méthode "ProbeDesc" qui retourne une courte description de ce qu'elle fait. Ceci sera utilisé dans les graphiques produits par le frontend web.

VARIABLES

Toutes les sondes Smokeping doivent définir leurs variables en implémentant une méthode "probevars" pour les variables spécifiques à la sonde et une méthode "targetvars" pour les variables spécifiques à la cible. Si vous ne connaissez pas encore la différence entre celles-ci, consultez smokeping_examples.

(Les sondes qui dérivent de "Smokeping::probes::base" ne prennent pas en charge les variables spécifiques à la cible, elles n'utilisent donc que la méthode "probevars".)

Les classes de base offrent également ces méthodes pour fournir les variables communes à toutes les sondes (par exemple, la variable spécifique à la sonde "step" et la variable spécifique à la cible "pings". Si vous ne souhaitez pas ajouter quoi que ce soit aux variables de la classe de base (peut-être parce que toutes vos variables sont de nature spécifique à la cible, donc vous n'avez pas besoin de nouvelles variables spécifiques à la sonde du tout), vous pouvez laisser la méthode correspondante de côté et elle sera héritée de la classe de base.

Lorsque vous fournissez votre propre méthode "probevars" ou "targetvars", vous devez combiner vos variables avec celles provenant de la superclasse. Il existe une méthode pratique appelée "_makevars" qui fait cela, et l'idiome courant est

sub probevars {
       my $class = shift;
       return $class->_makevars($class->SUPER::probevars, {
               # vos variables vont ici
       }
}

Les variables sont déclarées dans une syntaxe qui provient du module utilisé pour analyser le fichier de configuration, "Config::Grammar". Chaque variable doit être une table de hachage qui utilise les « clés de variable spéciales » documentées dans Config::Grammar. Voir "Smokeping::probes::skel" et les autres sondes pour des exemples.

Pour référence, voici les clés que la table de hachage doit avoir. Une grande partie de ceci est directement tirée du manuel "Config::Grammar".

Clés que vous devez fournir
_doc
Description de la variable.
_example
Une valeur d'exemple. Ceci sera utilisé dans la section SYNOPSIS du manuel de la sonde.
Clés optionnelles
_default
Une valeur par défaut qui sera assignée à la variable si aucune n'est spécifiée ou héritée.
_re
Expression régulière sur laquelle la valeur sera vérifiée.
_re_error
Chaîne contenant l'erreur retournée au cas où l'expression régulière ne correspond pas (si non spécifié, un message générique d'erreur de syntaxe sera retourné).
_sub
Un pointeur de fonction. Il est appelé pour chaque valeur, avec la valeur passée comme premier argument. Si la fonction retourne une valeur définie, on suppose que le test n'a pas réussi et une erreur est générée avec la chaîne retournée comme contenu.

Les méthodes "probevars" et "targetvars" doivent retourner des références à des tables de hachage contenant les noms de variables comme clés et les tables de hachage décrites ci-dessus comme valeurs. De plus, la clé de section spéciale "Config::Grammar" "_mandatory" est prise en charge et doit contenir une référence à une liste de variables obligatoires. La méthode "_makevars" est consciente de cette clé spéciale et fusionne les listes obligatoires dans ses arguments. Notez qu'aucune autre clé de section spéciale de "Config::Grammar" n'est prise en charge.

INITIALISATION

Si vous devez faire quelque chose lors de l'initialisation de la sonde, comme vérifier que le programme externe que vous allez utiliser se comporte comme prévu, vous devriez le faire dans la méthode "new". Vous devriez probablement aussi veiller à ne pas exécuter les tests inutilement en mode CGI. La façon habituelle de faire cela est de tester $ENV{SERVER_SOFTWARE}. Voir le module "Smokeping::probes::skel" pour un exemple.

smokeping_extend(7) — Smokeping 2.9.0

NAME

smokeping_extend — writing new probes for Smokeping

OVERVIEW

This document describes how to write new probes for Smokeping.

Probes are the modules that do the actual measuring. Currently there are probes for CGI/bin/smokeping, fping, geturl, ICMP, IPMI, metrics, mlookup, MPLS-LSR, mysql, nntp, nping, omr, port, postgres, rbl, serve, smnp, sshuser, tcp_content, tcp_connect, tcp_ping, tcp_ssl, udp_connect, udp_port, udp_probe, and webcheck.

CHOOSING A BASE CLASS

Most probes can be implemented as a subclass of "Smokeping::probes::basefork". This class handles forking off a child process to do the actual probing and reaping the child. It also handles basic error checking and timeouts.

If your probe does not need to fork, you can subclass "Smokeping::probes::base" directly. This is rarely needed.

SKELETON FILE

A minimal probe looks like this:

package Smokeping::probes::MyProbe;

use strict;
use base qw(Smokeping::probes::basefork);

sub probevars {
        my $class = shift;
        return {
                # your probe variables go here
        };
}

sub run {
        my ($self, $target) = @_;
        # your probe logic goes here
}

1;

PROBE DOCUMENTATION

The probe documentation should be written in POD format within the probe file itself. Start with a NAME section, followed by DESCRIPTION, and then the specific sections for your probe.

For example:

=head1 NAME

MyProbe - A simple example probe

=head1 DESCRIPTION

This probe does something simple.

PROBE DESCRIPTION

The probe description is displayed in the web interface. It should be a short, human-readable description of what the probe does.

It can be set in the probe's documentation using the "=head1 DESCRIPTION" tag.

VARIABLES

Probes can define variables that can be configured either globally or per target. These variables are defined in the "probevars" subroutine.

The "probevars" subroutine should return a hash reference. The keys of the hash are the variable names. The values are themselves hash references containing information about the variable.

The basic structure of a probe variable definition is:

    'varname' => {
            'title'         => 'Variable Title',
            'short'         => 'Short description',
            'type'          => 'string|integer|float|boolean|hidden',
            'required'      => 1 | 0,
            'default'       => 'default value',
            '_default'      => 'default value', # for probe-specific defaults
            'pattern'       => 'regex pattern',
            'edit'          => 'yes' | 'no',
            'order'         => number,
            'menu'          => 'select' | 'radio' | 'text',
            'check'         => \&subroutine,
            'enum'          => [ 'value1', 'value2', ... ],
            'description'   => 'Detailed description',
    }

For a more detailed explanation of these options, see "Smokeping::lib::General::varspec".

The probe-specific default value for a variable can be set using the "_default" key. This value will be used if no value is specified in the main configuration file or per target.

Example:

sub probevars {
        my $class = shift;
        my $vars = $class->SUPER::probevars; # get defaults from base class
        $vars->{count}{title}     = 'Number of pings';
        $vars->{count}{short}     = 'Number of pings to send';
        $vars->{count}{type}      = 'integer';
        $vars->{count}{required}  = 0;
        $vars->{count}{default}   = 5;
        $vars->{count}{pattern}   = '/^\d+$/';
        $vars->{count}{order}     = 10;
        $vars->{count}{edit}      = 'yes';
        $vars->{count}{menu}      = 'text';
        $vars->{count}{description} = 'Number of pings to send to the target.';

        $vars->{timeout}{_default} = 5; # probe-specific default

        return $class->_makevars($vars, {
                # target-specific variables can go here
                'timeout'   => {
                        'title'     => 'Timeout',
                        'short'     => 'Probe timeout',
                        'type'      => 'integer',
                        'required'  => 0,
                        'default'   => undef, # will be set by probe-specific default
                        'pattern'   => '/^\d+$/',
                        'edit'      => 'yes',
                        'menu'      => 'text',
                        'description' => 'Timeout in seconds for the probe.',
                },
        });
}

INITIALIZATION

The "Smokeping::probes::basefork" class initializes the probe by calling the "probevars" subroutine of your probe class. It then merges the probe-specific variables with the target-specific variables and makes them available via the "$self->{properties}" hash.

The target-specific variables are available via the "$target->{vars}" hash.

PINGING

The actual probing logic should be implemented in the "run" subroutine. This subroutine is called by the base class after it has forked a child process.

The "run" subroutine takes one argument: the target object. You can access the target's address via "$target->{host}".

The probe-specific variables are available via the "$self->{properties}" hash, and the target-specific ones via the "$target->{vars}" hash. You get the number of pings needed for the target via the "pings" method: "my $count = $self->pings($target)".

You should return a sorted array of the latency times measured. If a ping fails, don't put anything in the array.

That's it, you're done!

EXAMPLE CONFIGURATIONS

If you would like to provide a documented example configuration for your probe (in addition to the automatically generated SYNOPSIS section in the probe manual), you can do so by adding it to the Smokeping::Examples module. Look for the 'examples' subroutine and add your example there.

Future versions of Smokeping might provide a way to embed examples in the probe modules too. The author's motivation for implementing this would be greatly increased by even a single demand for it, so please speak up if you think you'd use it.

TIMEOUT HANDLING

If you deal with timeouts (for example because your program offers a parameter for specifying the timeout for the pings), you should know a few things.

First, there's timeout logic in "Smokeping::probes::basefork" that kills the probe when the timeout is reached. By default the timeout is (# of pings * 5 seconds) + 1 second. If you expect that your pings can take longer, you should modify the default value of the probe-specific variable "timeout". This would be done like this:

sub probevars {
       my $class = shift;
       my $h = $class->SUPER::probevars;
       $h->{timeout}{_default} = 10; # override the superclass default
       return $class->_makevars($h, {
               # your variables go here
       }
}

If you want to provide a target-specific "timeout" setting, you should delete the probe-specific variable and be sure to provide a default for your target-specific one. See eg. "Smokeping::probes::AnotherDNS" for an example of how this is done.

Providing a target-specific "timeout" will make the timeout in "Smokeping::probes::basefork" be (# of pings * the maximum timeout of all targets) + 1 second. The 1 second is added so that the own timeout logic of the probe has time to kick in even in the worst case (ie. all pings are lost) before "Smokeping::probes::basefork" starts killing the processes.

NOM

smokeping_extend — écrire de nouvelles sondes pour Smokeping

APERÇU

Ce document décrit comment écrire de nouvelles sondes pour Smokeping.

Les sondes sont les modules qui effectuent les mesures réelles. Actuellement, il existe des sondes pour CGI/bin/smokeping, fping, geturl, ICMP, IPMI, métriques, mlookup, MPLS-LSR, mysql, nntp, nping, omr, port, postgres, rbl, serve, smnp, sshuser, tcp_content, tcp_connect, tcp_ping, tcp_ssl, udp_connect, udp_port, udp_probe, et webcheck.

CHOIX D'UNE CLASSE DE BASE

La plupart des sondes peuvent être implémentées en tant que sous-classe de "Smokeping::probes::basefork". Cette classe gère la création d'un processus enfant pour effectuer la sonde réelle et la récupération de ce processus. Elle gère également la vérification de base des erreurs et les délais d'attente.

Si votre sonde n'a pas besoin de créer un processus, vous pouvez hériter directement de "Smokeping::probes::base". Ceci est rarement nécessaire.

FICHIER SQUELETTE

Une sonde minimale ressemble à ceci :

package Smokeping::probes::MaSonde;

use strict;
use base qw(Smokeping::probes::basefork);

sub probevars {
        my $class = shift;
        return {
                # vos variables de sonde vont ici
        };
}

sub run {
        my ($self, $target) = @_;
        # votre logique de sonde va ici
}

1;

DOCUMENTATION DE SONDE

La documentation de la sonde doit être écrite au format POD dans le fichier de sonde lui-même. Commencez par une section NOM, suivie de DESCRIPTION, puis des sections spécifiques à votre sonde.

Par exemple :

=head1 NOM

MaSonde - Une sonde d'exemple simple

=head1 DESCRIPTION

Cette sonde fait quelque chose de simple.

DESCRIPTION DE SONDE

La description de la sonde est affichée dans l'interface web. Elle doit être une description courte et lisible par l'homme de ce que fait la sonde.

Elle peut être définie dans la documentation de la sonde en utilisant la balise "=head1 DESCRIPTION".

VARIABLES

Les sondes peuvent définir des variables qui peuvent être configurées globalement ou par cible. Ces variables sont définies dans la sous-routine "probevars".

La sous-routine "probevars" doit retourner une référence de hachage. Les clés du hachage sont les noms des variables. Les valeurs sont elles-mêmes des références de hachage contenant des informations sur la variable.

La structure de base d'une définition de variable de sonde est :

    'nom_variable' => {
            'title'         => 'Titre de la Variable',
            'short'         => 'Description courte',
            'type'          => 'string|integer|float|boolean|hidden',
            'required'      => 1 | 0,
            'default'       => 'valeur par défaut',
            '_default'      => 'valeur par défaut', # pour les valeurs par défaut spécifiques à la sonde
            'pattern'       => 'modèle regex',
            'edit'          => 'yes' | 'no',
            'order'         => nombre,
            'menu'          => 'select' | 'radio' | 'text',
            'check'         => \&sous-routine,
            'enum'          => [ 'valeur1', 'valeur2', ... ],
            'description'   => 'Description détaillée',
    }

Pour une explication plus détaillée de ces options, voir "Smokeping::lib::General::varspec".

La valeur par défaut spécifique à la sonde pour une variable peut être définie en utilisant la clé "_default". Cette valeur sera utilisée si aucune valeur n'est spécifiée dans le fichier de configuration principal ou par cible.

Exemple :

sub probevars {
        my $class = shift;
        my $vars = $class->SUPER::probevars; # obtenir les valeurs par défaut de la classe de base
        $vars->{nombre}{title}     = 'Nombre de pings';
        $vars->{nombre}{short}     = 'Nombre de pings à envoyer';
        $vars->{nombre}{type}      = 'integer';
        $vars->{nombre}{required}  = 0;
        $vars->{nombre}{default}   = 5;
        $vars->{nombre}{pattern}   = '/^\d+$/';
        $vars->{nombre}{order}     = 10;
        $vars->{nombre}{edit}      = 'yes';
        $vars->{nombre}{menu}      = 'text';
        $vars->{nombre}{description} = 'Nombre de pings à envoyer à la cible.';

        $vars->{timeout}{_default} = 5; # valeur par défaut spécifique à la sonde

        return $class->_makevars($vars, {
                # les variables spécifiques à la cible peuvent aller ici
                'timeout'   => {
                        'title'     => 'Délai d\'attente',
                        'short'     => 'Délai d\'attente de la sonde',
                        'type'      => 'integer',
                        'required'  => 0,
                        'default'   => undef, # sera défini par la valeur par défaut spécifique à la sonde
                        'pattern'   => '/^\d+$/',
                        'edit'      => 'yes',
                        'menu'      => 'text',
                        'description' => 'Délai d\'attente en secondes pour la sonde.',
                },
        });
}

INITIALISATION

La classe "Smokeping::probes::basefork" initialise la sonde en appelant la sous-routine "probevars" de votre classe de sonde. Elle fusionne ensuite les variables spécifiques à la sonde avec les variables spécifiques à la cible et les rend disponibles via le hachage "$self->{properties}".

Les variables spécifiques à la cible sont disponibles via le hachage "$target->{vars}".

PING

La logique de sondage réelle doit être implémentée dans la sous-routine "run". Cette sous-routine est appelée par la classe de base après qu'elle ait créé un processus enfant.

La sous-routine "run" prend un argument : l'objet cible. Vous pouvez accéder à l'adresse de la cible via "$target->{host}".

Les variables spécifiques à la sonde sont disponibles via le hachage "$self->{properties}", et celles spécifiques à la cible via le hachage "$target->{vars}". Vous obtenez le nombre de pings nécessaires pour la cible via la méthode "pings" : "my $count = $self->pings($target)".

Vous devez retourner un tableau trié des temps de latence mesurés. Si un ping échoue, ne rien mettre dans le tableau.

Voilà, vous avez terminé !

EXEMPLES DE CONFIGURATIONS

Si vous souhaitez fournir un exemple de configuration documenté pour votre sonde (en plus de la section SYNOPSIS générée automatiquement dans le manuel de la sonde), vous pouvez le faire en l'ajoutant au module Smokeping::Examples. Recherchez la sous-routine 'examples' et ajoutez votre exemple là-bas.

Les futures versions de Smokeping pourraient offrir un moyen d'intégrer des exemples dans les modules de sondes également. La motivation de l'auteur pour implémenter cela serait grandement accrue par une seule demande en ce sens, alors n'hésitez pas à vous manifester si vous pensez que cela vous serait utile.

GESTION DES DÉLAIS D'ATTENTE

Si vous traitez des délais d'attente (par exemple parce que votre programme offre un paramètre pour spécifier le délai d'attente pour les pings), vous devriez savoir quelques choses.

Premièrement, il existe une logique de délai d'attente dans "Smokeping::probes::basefork" qui tue la sonde lorsque le délai d'attente est atteint. Par défaut, le délai d'attente est de (# de pings * 5 secondes) + 1 seconde. Si vous vous attendez à ce que vos pings prennent plus de temps, vous devriez modifier la valeur par défaut de la variable spécifique à la sonde "timeout". Cela se ferait comme ceci :

sub probevars {
       my $class = shift;
       my $h = $class->SUPER::probevars;
       $h->{timeout}{_default} = 10; # outrepasser la valeur par défaut de la superclasse
       return $class->_makevars($h, {
               # vos variables vont ici
       }
}

Si vous souhaitez fournir un réglage de "timeout" spécifique à la cible, vous devriez supprimer la variable spécifique à la sonde et vous assurer de fournir une valeur par défaut pour votre variable spécifique à la cible. Voir par exemple "Smokeping::probes::AnotherDNS" pour un exemple de la façon dont cela est fait.

Fournir un "timeout" spécifique à la cible rendra le délai d'attente dans "Smokeping::probes::basefork" égal à (# de pings * le délai d'attente maximum de toutes les cibles) + 1 seconde. La seconde est ajoutée afin que la propre logique de délai d'attente de la sonde ait le temps de s'activer même dans le pire des cas (c'est-à-dire que tous les pings sont perdus) avant que "Smokeping::probes::basefork" ne commence à tuer les processus.
