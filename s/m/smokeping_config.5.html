NOM

smokeping_config - Référence du fichier de configuration SmokePing

APERÇU

SmokePing prend sa configuration à partir d'un seul fichier de configuration central. Son emplacement doit être codé en dur dans le script smokeping et smokeping.cgi.

Le contenu de ce manuel est généré directement à partir de l'analyseur de fichier de configuration.

L'analyseur pour le fichier de configuration est écrit à l'aide du module Config::Grammar de David Schweikert. Lisez tout à ce sujet dans Config::Grammar.

Le fichier de configuration a une structure arborescente avec des titres de section à différents niveaux. Il contient également des assignations de variables et des tableaux.

Attention : ce manuel est assez long. Voir smokeping_examples pour des exemples de configuration simples.

RÉFÉRENCE

SYNTAXE GÉNÉRALE

Le texte ci-dessous décrit la syntaxe générale du fichier de configuration SmokePing. Il a été copié de la documentation de Config::Grammar.

« # » désigne un commentaire jusqu'à la fin de la ligne, les lignes vides sont autorisées et les espaces au début et à la fin des lignes sont supprimés.

« \ » à la fin de la ligne marque une continuation de ligne à la ligne suivante. Un seul espace sera inséré entre les lignes concaténées.

« @include filename » est utilisé pour inclure un autre fichier.

« @define a some value » remplacera toutes les occurrences de « a » dans le texte suivant par « some value ». »

Les champs dans les tableaux contenant des espaces blancs peuvent être entourés de « ' » ou de « """ ». Les espaces blancs peuvent également être échappés avec « \ ». Les guillemets à l'intérieur de guillemets sont autorisés mais doivent également être échappés avec une barre oblique inverse.

SYNTAXE SPÉCIFIQUE

Le texte ci-dessous décrit la syntaxe spécifique du fichier de configuration SmokePing.

*** Général *** (section obligatoire)

Valeurs de configuration générales valides pour l'ensemble de la configuration SmokePing.

Les variables suivantes peuvent être définies dans cette section :

propriétaire (paramètre obligatoire)
Nom de la personne responsable de cette installation smokeping.
imgcache (paramètre obligatoire)
Un répertoire visible sur votre serveur Web où SmokePing peut mettre en cache les graphiques.
imgurl (paramètre obligatoire)
Soit une URL absolue vers le répertoire imgcache, soit une URL relative au répertoire où vous conservez le cgi SmokePing.
datadir (paramètre obligatoire)
Le répertoire où SmokePing peut conserver ses fichiers rrd.
dyndir
Le répertoire de base où SmokePing conserve les fichiers liés à la fonction DYNAMIQUE. Ce répertoire doit être accessible en écriture par le serveur WWW. Il est également utilisé pour le stockage temporaire des résultats d'interrogation des esclaves par le maître en mode maître/esclave.

Si cette variable n'est pas spécifiée, la valeur de "datadir" sera utilisée à la place.

pagedir
Répertoire pour stocker les représentations statiques des pages.
piddir (paramètre obligatoire)
Le répertoire où SmokePing conserve son pid lorsqu'il est démarré en tant que démon.
sendmail
Chemin vers votre binaire sendmail. Il sera utilisé pour envoyer des courriels dans le cadre de la prise en charge des adresses DYNAMIQUES.
offset
Si vous exécutez plusieurs instances de smokeping, vous voudrez peut-être éviter qu'elles ne frappent votre réseau en même temps. En utilisant le paramètre offset, vous pouvez modifier le moment où les sondes sont exécutées. L'offset est spécifié en % de l'intervalle total, ou alternativement comme 'random'. Je recommande d'utiliser 'random'. Notez que cela n'influence PAS les rrd eux-mêmes, c'est juste une question du moment où l'acquisition des données est initiée. L'offset par défaut est 'random'.
smokemail (paramètre obligatoire)
Chemin vers le modèle d'e-mail pour les hôtes DYNAMIQUES. Ce modèle d'e-mail doit contenir des mots-clés de la forme <##mot-clé##>. Il existe un modèle d'exemple inclus avec SmokePing.
cgiurl (paramètre obligatoire)
Chemin URL complet du SmokePing.cgi
mailhost
Au lieu d'utiliser sendmail, vous pouvez spécifier le nom d'un serveur smtp et utiliser le module Net::SMTP de perl pour envoyer des courriels (pour les alertes et le script client DYNAMIQUE). Plusieurs mailhosts séparés par des virgules peuvent être spécifiés. SmokePing essaiera l'un après l'autre si l'un ne répond pas pendant 5 secondes.
mailuser
nom d'utilisateur sur mailhost, SmokePing utilisera cet utilisateur pour envoyer des courriels (Net::SMTP).
mailpass
mot de passe de l'utilisateur sur mailhost, SmokePing utilisera ce mot de passe pour envoyer des courriels (Net::SMTP).
snpphost
Si vous avez un serveur SNPP (Simple Network Pager Protocol) à disposition, vous pouvez également y envoyer des alertes. Utilisez la syntaxe snpp:someaddress pour utiliser une adresse snpp là où vous pouvez utiliser une adresse e-mail autrement.
contact (paramètre obligatoire)
Adresse e-mail de la personne responsable de cette installation smokeping.
display_name
Comment le serveur maître doit-il être appelé lorsqu'il fonctionne en mode maître/esclave ? Ceci est utilisé dans le graphique d'aperçu, par exemple.
syslogfacility
La facilité syslog à utiliser, par exemple local0...local7. Remarque : la journalisation syslog n'est utilisée que si vous la spécifiez.
syslogpriority
La priorité syslog à utiliser, par exemple debug, notice ou info. Par défaut, c'est info.
concurrentprobes
Si vous utilisez plusieurs sondes ou plusieurs instances de la même sonde et que vous souhaitez qu'elles s'exécutent simultanément dans des processus distincts, définissez cette option sur 'yes'. Cela vous donne la possibilité de spécifier des paramètres step et offset spécifiques à la sonde (voir la section 'Probes') pour chaque sonde et permet aux sondes de ne pas se bloquer mutuellement en cas de pannes de service. La valeur par défaut est 'yes', mais si pour une raison quelconque vous souhaitez l'ancien comportement, vous pouvez définir cette option sur 'no'.
changeprocessnames
Lorsque vous utilisez 'concurrentprobes' (voir ci-dessus), cela contrôle si les sous-processus de sonde doivent modifier leur chaîne argv pour indiquer leur sonde dans le nom du processus. S'il est défini sur 'yes' (par défaut), le nom de la sonde sera ajouté au nom du processus sous la forme '[probe]', par exemple '/usr/bin/smokeping [FPing]'. Si vous n'aimez pas ce comportement, définissez cette variable sur 'no'. Si 'concurrentprobes' n'est pas défini sur 'yes', cette variable n'a aucun effet.

Valeur par défaut : changeprocessnames = yes

tmail
Chemin vers votre fichier de modèle d'e-mail HTML tSmoke. Voir la documentation tSmoke pour plus de détails.
changecgiprogramname
Habituellement, le CGI Smokeping essaie d'enregistrer toute erreur possible avec un nom de programme étendu qui inclut l'adresse IP du client distant pour faciliter le débogage. Si cette variable est définie sur 'no', le nom du programme ne sera pas modifié. La seule raison pour laquelle vous voudriez cela est si vous avez une version très ancienne du module CGI::Carp. Voir le document d'installation pour plus de détails.

Valeur par défaut : changecgiprogramname = yes

linkstyle
Comment le CGI se

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Les liens auto-référents sont créés. Les valeurs possibles sont
absolu
Nom d'hôte complet et chemin dérivés de la variable 'cgiurl'

<a href="http://hostname/path/smokeping.cgi?foo=bar">

relatif
Seule la partie paramètre est spécifiée

<a href="?foo=bar">

original
La manière dont les liens étaient générés avant la version 2.0.4 de Smokeping : pas de nom d'hôte, seulement le chemin

<a href="/path/smokeping.cgi?foo=bar">

La valeur par défaut est "relative", ce qui, espérons-le, fonctionne pour tout le monde.

Valeur par défaut : linkstyle = relative

precreateperms
Si cette variable est définie, le démon Smokeping créera sa hiérarchie de répertoires sous 'dyndir' (l'arborescence accessible en écriture par le CGI) au démarrage avec les bits de permission de répertoire spécifiés. La valeur est interprétée comme une valeur octale, par exemple 775 pour rwxrwxr-x, etc.

Si elle n'est pas définie, les répertoires seront créés dynamiquement avec umask 022.

Exemple : precreateperms = 2755

*** Base de données *** (section obligatoire)

Décrit les propriétés de la base de données en cercle pour stocker les données de SmokePing. Notez qu'il n'est pas possible de modifier les RRD existants en changeant les entrées dans le fichier cfg.

Les variables suivantes peuvent être définies dans cette section :

step (paramètre obligatoire)
Durée de l'intervalle d'opération de base de SmokePing en secondes. SmokePing pingera vos hôtes cibles toutes les step secondes. Si 'concurrentprobes' est défini sur 'yes' (voir ci-dessus), cette variable peut être remplacée par chaque sonde. Notez que l'intervalle dans les fichiers RRD est fixe lorsqu'ils sont générés à l'origine, et si vous modifiez le paramètre step par la suite, vous devrez supprimer les anciens fichiers RRD ou les convertir d'une manière ou d'une autre.
pings (paramètre obligatoire)
Combien de pings doivent être envoyés à chaque cible. Suggéré : 20 pings. Valeur minimale : 3 pings. Ceci peut être remplacé par chaque sonde. Certaines sondes (celles dérivées de basefork.pm, c'est-à-dire la plupart sauf les variantes FPing) permettront même de remplacer ceci spécifiquement pour la cible. Notez que le nombre de pings dans les fichiers RRD est fixe lorsqu'ils sont générés à l'origine, et si vous modifiez ce paramètre par la suite, vous devrez supprimer les anciens fichiers RRD ou les convertir d'une manière ou d'une autre.

Cette section contient également un tableau décrivant la configuration de la base de données SmokePing. Ci-dessous se trouvent des valeurs par défaut raisonnables. Ne les modifiez que si vous connaissez rrdtool et son fonctionnement. Chaque ligne du tableau décrit une RRA.

Méthode de consolidation.
colonne 1

colonne 2

colonne 3
Combien de rows cette RRA doit avoir.

*** Présentation *** (section obligatoire)

Définit comment les données SmokePing doivent être présentées.

Les variables suivantes peuvent être définies dans cette section :

template (paramètre obligatoire)
Le modèle de page web doit contenir des mots-clés de la forme <##mot-clé##>. Il y a un modèle d'exemple inclus avec SmokePing ; utilisez-le comme base pour vos expériences. Le modèle par défaut contient un pointeur vers le compteur SmokePing et la page d'accueil. Je serais heureux si vous ne supprimiez pas cela, car cela me donne une indication de l'utilisation de l'outil.
charset
Par défaut, SmokePing suppose le jeu de caractères 'utf-8'. Si vous utilisez quelque chose d'autre, c'est ici qu'il faut le spécifier.
htmltitle
Par défaut, SmokePing rendra le titre du graphique dans l'image ; lorsqu'il est défini sur 'yes', le titre est inséré dans la page html.
graphborders
Par défaut, SmokePing affichera une bordure grise sur un fond gris clair ; s'il est défini sur 'no', les bordures seront masquées et le fond et la toile seront transparents.
literalsearch
Par défaut, SmokePing traitera les requêtes du menu de filtrage comme des expressions régulières ; s'il est défini sur 'yes', les recherches seront traitées comme des chaînes littérales à la place.
colortext
colorbackground
Par défaut, SmokePing affichera un fond gris clair, ce qui peut être remplacé ici par votre propre valeur RGB.
colorborder
Par défaut, SmokePing affichera une bordure grise, ce qui peut être remplacé ici par votre propre valeur RGB.

+overview (section obligatoire)

Les variables suivantes peuvent être définies dans cette section :

Quelle quantité de temps doit être représentée dans le graphique d'aperçu. Le temps doit être spécifié comme un nombre suivi d'une lettre qui spécifie l'unité de temps. Les unités connues sont : secondes, minutes, heures, djours, wsemaines, yannées.

Tout temps de réponse supérieur à cette valeur sera tronqué dans le graphique d'aperçu. L'unité est la seconde (par exemple, 0.800).
median_color
Par défaut, la ligne médiane est dessinée en rouge. Remplacez-la ici par une couleur hexadécimale au format rrggbb. Notez que si vous travaillez avec des esclaves, les médianes des esclaves seront dessinées dans la couleur de l'esclave dans le graphique d'aperçu.

Si un graphique dépasse ce facteur de la médiane 'max', il sort de l'algorithme de mise à l'échelle unifiée. Un facteur de deux signifierait que tout graphique dont le maximum est inférieur de moitié ou supérieur au double de la médiane 'max' sera exclu de la mise à l'échelle unifiée.

*** Sondes *** (section obligatoire)

La section Sondes configure les modules de sonde. Les modules de sonde intègrent une commande ping externe dans SmokePing. Consultez la documentation de chaque module pour plus d'informations à son sujet.

Les sections suivantes sont valides au niveau 1 :

+/[-_0-9a-zA-Z]+/
Chaque module peut prendre des informations de configuration spécifiques de cette zone. Le mélange de lettres ci-dessus est une expression régulière définissant des noms de modules légaux.

Voir la documentation de chaque module pour les détails sur ses variables.

La grammaire de cette section est modifiée dynamiquement en fonction de son nom.

Les sections suivantes sont valides au niveau 2 :

++/[-_0-9a-zA-Z]+/
Vous pouvez définir plusieurs instances de la même sonde avec des sous-sections. Ces instances peuvent avoir des valeurs différentes pour leurs variables, vous pouvez donc par exemple avoir une instance de la sonde FPing avec une taille de paquet de 1000 et un pas de 300, et une autre instance avec une taille de paquet de 64 et un pas de 30. Le nom de la sous-section détermine comment la sonde sera appelée, vous pouvez donc écrire des noms descriptifs pour les sondes.

S'il y a des sous-sections définies, la section principale de cette sonde fournira simplement des valeurs de paramètres par défaut pour les instances de sonde, c'est-à-dire qu'elle ne deviendra pas une instance de sonde elle-même.

L'exemple ci-dessus serait écrit comme suit :

*** Probes ***
+ FPing
# cette valeur est commune aux deux sous-sondes
binary = /usr/bin/fping
++ FPingLarge
packetsize = 1000
step = 300
++ FPingSmall
packetsize = 64
step = 30

*** Alertes ***

La section Alertes vous permet de configurer des détecteurs de pertes et de RTT. Après chaque cycle de sondage, SmokePing examinera ses données et déterminera quels détecteurs correspondent. Les détecteurs sont activés par cible et sont hérités par les enfants des cibles.

Les détecteurs ne sont pas de simples seuils qui se déclenchent à la première apparition d'un problème. Ils sont configurables pour détecter des motifs de perte ou de RTT spéciaux. Ils permettent d'examiner un certain nombre de lectures passées pour prendre une décision plus éclairée sur le type d'alerte à envoyer, ou si une alerte doit être envoyée.

Les motifs sont des nombres précédés d'un opérateur indiquant le type de comparaison requis pour une correspondance.

Le motif RTT suivant détecte si le RTT d'une cible passe de constamment inférieur à 10 ms à constamment supérieur ou égal à 100 ms :

old ------------------------------> new
<10,<10,<10,<10,<10,>10,>100,>100,>100

Les motifs de perte fonctionnent de manière similaire, sauf que la perte est définie comme le pourcentage du nombre total de paquets reçus par rapport au nombre total de paquets envoyés.

old ------------------------------> new
==0%,==0%,==0%,==0%,>20%,>20%,>=20%

Outre les nombres normaux, les motifs peuvent également contenir les valeurs * qui est vraie pour toutes les valeurs quel que soit l'opérateur. Et U qui est vraie pour les données inconnues avec les opérateurs == et =!.

Les détecteurs agissent normalement sur les changements d'état. Cela a l'inconvénient de ne pas trouver les conditions qui étaient déjà présentes au lancement de smokeping. Pour cela, il est possible d'écrire des détecteurs qui commencent par la valeur spéciale ==S, elle est insérée chaque fois que smokeping démarre.

Vous pouvez écrire

==S,>20%,>20%

pour détecter les lignes qui ont perdu plus de 20 % des paquets pendant deux périodes après le démarrage.

Si vous voulez vous assurer qu'une valeur se situe dans une certaine plage, vous pouvez utiliser deux conditions dans un seul élément

>45%<=55%

Il peut parfois arriver que des conditions se produisent à intervalles irréguliers. Mais vous ne voulez quand même déclencher une alerte que si elles se produisent plusieurs fois dans une période donnée. L'opérateur *X* ignorera jusqu'à X valeurs et laissera le motif correspondre :

>10%,*10*,>10%

se déclenchera si plus de 10 % des paquets ont été perdus au moins deux fois au cours des 10 derniers échantillons.

Un exemple complet

*** Alerts ***
to = admin@company.xy,peter@home.xy
from = smokealert@company.xy
+lossdetect
type = loss
# en pour cent
pattern = ==0%,==0%,==0%,==0%,>20%,>20%,>20%
comment = soudainement il y a perte de paquets
+miniloss
type = loss
# en pour cent
pattern = >0%,*12*,>0%,*12*,>0%
comment = perte détectée 3 fois au cours des deux dernières heures
+rttdetect
type = rtt
# en millisecondes
pattern = <10,<10,<10,<10,<10,<100,>100,>100,>100
comment = le routage est encore désorganisé ?
+rttbadstart
type = rtt
# en millisecondes
pattern = ==S,==U
comment = hors ligne au démarrage

to (paramètre obligatoire)
Soit une adresse e-mail à laquelle envoyer les alertes, soit le nom d'un programme à exécuter lorsqu'une alerte correspond. Pour appeler un programme, le premier caractère de la valeur to doit être un symbole pipe "|". Le programme sera alors appelé chaque fois qu'une alerte correspondra, en utilisant les 5 arguments suivants (sauf si edgetrigger est 'yes' ; voir ci-dessous) : nom-de-l'alerte, cible, motif-perte, motif-rtt, nom-hote. Vous pouvez également fournir une liste d'adresses et de programmes séparés par des virgules.
from (paramètre obligatoire)
De la part de qui les alertes doivent-elles apparaître ?
edgetrigger
Les notifications d'alerte et/ou les programmes exécutés sont normalement déclenchés à chaque fois que l'alerte correspond. Si cette variable est définie sur 'yes', ils ne seront déclenchés que lorsque l'état de l'alerte change, c'est-à-dire lorsqu'elle est levée et lorsqu'elle est effacée. Les correspondances ultérieures de la même alerte ne déclencheront donc pas de notification.

Lorsque cette variable est définie sur 'yes', un programme de notification (voir la documentation de la variable to ci-dessus) recevra un sixième argument, raise, qui aura la valeur 1 si l'alerte vient d'être levée et 0 si elle a été effacée.

Valeur par défaut : edgetrigger = no

mailtemplate
Lors de l'envoi d'e-mails pour les alertes, smokeping utilise normalement un message généré en interne. Avec mailtemplate, vous pouvez spécifier le nom d'un fichier pour un modèle personnalisé. Le fichier doit contenir une ligne 'Subject: ...'. Le reste du fichier doit contenir du texte. Toutes les chaînes de type <##mot-clé##> seront remplacées dans le modèle avant son envoi. les mots-clés suivants sont pris en charge : 
<##ALERT##>    - nom de la cible
<##WHAT##>     - statut (est actif, a été levé, a été effacé)
<##LINE##>     - chemin dans l'arborescence de configuration
<##URL##>      - page web du graphique
<##STAMP##>    - date et heure
<##PAT##>      - motif qui a correspondu à l'alerte
<##LOSS##>     - historique des pertes
<##RTT##>      - historique du RTT
<##COMMENT##>  - commentaire

La valeur d'offset pour l'alarme. La valeur d'offset est une valeur arbitraire qui est ajoutée à la mesure avant que les comparaisons ne soient effectuées. L'opérateur > compare donc la mesure + offset. La valeur par défaut est 0.

*** Esclaves ***

Dans la configuration /etc/smokeping/config de l'esclave, vous devez spécifier la source des données de télémétrie. Pour ce faire, vous devez ajouter une section slaves et y spécifier le nom du maître et l'adresse réseau sur laquelle il écoute.

*** slaves ***
+	master.example.com/2801:1:2:3::30

Cela suppose que l'esclave peut atteindre le maître sur l'adresse IPv6 2801:1:2:3::30. SmokePing écoute par défaut sur le port 2801. Si le maître écoute sur un port différent, vous pouvez le spécifier après le nom de l'hôte.

+	master.example.com:2802

Vous pouvez également spécifier une adresse IPv4 pour le maître.

+	master.example.com/192.168.1.1:2802

Il est possible de spécifier une liste de maîtres. Dans ce cas, l'esclave tentera de se connecter à chaque maître dans l'ordre jusqu'à ce qu'il réussisse.

*** slaves ***
+	master1.example.com
+	master2.example.com

Le nom de l'hôte (ou l'adresse IP) utilisé dans la section slaves sera utilisé comme nom de l'esclave lors de l'affichage des données dans l'interface web.

Sur le maître, vous devez spécifier quel esclave vous autorisez à envoyer des données. Ceci est fait dans la section General avec la variable master.

*** General ***
owner	=	Homer J. Simpson
contact	=	homer@thesimpsons.com
# specify masters here
master	=	slave1.example.com

Ou si vous autorisez plusieurs esclaves.

master	=	slave1.example.com, slave2.example.com

En plus des données de télémétrie, les esclaves peuvent également envoyer des données de diagnostic. Pour ce faire, la section [matchers] sur l'esclave doit être configurée pour faire correspondre les valeurs envoyées par le maître.

*** [matchers] ***
# This is a simple example. Consult the Smokeping documentation for details.
+	name = rtt
	type = rtt
	average = average
+	name = loss
	type = loss
	average = average

Le maître doit alors spécifier une section [slave-targets] qui lui indique comment traiter les données envoyées par l'esclave.

*** [slave-targets] ***
+	slave1.example.com

Les sections de diagnostic sont maintenant disponibles sous l'esclave approprié dans l'interface web.

Le nom de l'hôte (ou l'adresse IP) doit correspondre exactement à celui spécifié dans la section slaves de l'esclave.
