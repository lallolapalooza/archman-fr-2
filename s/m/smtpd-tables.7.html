NOM

smtpd-tables — API de table pour le démon smtpd

DESCRIPTION

Le démon smtpd(8) fournit une implémentation du protocole Simple Mail Transfer Protocol (SMTPD), qui permet aux machines ordinaires de devenir des échangeurs de courrier (MX). Certaines fonctionnalités couramment utilisées par les MX, telles que l'interrogation de bases de données pour les identifiants d'utilisateur, sont en dehors du champ d'application de SMTP et trop complexes pour être intégrées dans smtpd(8).

Étant donné qu'un MX peut avoir besoin de fournir ces fonctionnalités, smtpd(8) fournit une API pour implémenter des backends table(5) avec un simple protocole basé sur du texte.

CONCEPTION

smtpd-tables sont des programmes qui s'exécutent en tant que processus autonomes uniques, ils ne partagent pas l'espace d'adressage de smtpd(8). Ils sont exécutés par smtpd(8) au démarrage et sont censés s'exécuter dans une boucle infinie, lisant les événements et les requêtes depuis l'entrée standard et écrivant les réponses sur la sortie standard. Ils ne sont pas autorisés à se terminer.

Étant donné que smtpd-tables sont des programmes autonomes qui communiquent avec smtpd(8), ils peuvent s'exécuter sous des utilisateurs différents de smtpd(8) et peuvent être écrits dans n'importe quel langage. smtpd-tables ne doivent pas utiliser d'E/S bloquantes, ils doivent pouvoir répondre de manière asynchrone à smtpd(8).

PROTOCOLE

Le protocole consiste en des lignes lisibles par l'homme échangées entre smtpd-tables et smtpd(8).

Le protocole commence par une poignée de main. D'abord, smtpd(8) fournit à smtpd-tables des informations de configuration générales sous forme de lignes clé-valeur, terminées par ‘config|ready’. Par exemple :

config|smtpd-version|7.8.0
config|protocol|0.1
config|tablename|devs
config|ready

Ensuite, smtpd-tables enregistre les services pris en charge, se terminant par ‘register|ready’. Par exemple :

register|alias
register|credentials
register|ready

Enfin, smtpd(8) peut commencer à interroger la table. Par exemple :

table|0.1|1713795082.354255|devs|lookup|alias|b72508d|op

Le caractère “|” est utilisé pour séparer les champs et ne peut apparaître textuellement que dans le dernier champ de la charge utile, auquel cas il doit être considéré comme un caractère ordinaire et non comme un séparateur. Aucun autre champ ne peut contenir de “|”.

Chaque requête a un ensemble commun de champs, suivis de quelques autres champs qui sont spécifiques à l'opération. Le format commun se compose d'un préfixe de protocole ‘table’, de la version du protocole, de l'horodatage et du nom de la table. Par exemple :

table|0.1|1713795091.202157|devs

Le protocole est intrinsèquement asynchrone, ainsi plusieurs requêtes peuvent être envoyées sans attendre la réponse de la table. Toutes les réponses ont un préfixe commun, suivi de la réponse spécifique à l'opération. Le format commun consiste en un préfixe avec le nom de l'opération suivi de ‘-result’, et l'identifiant unique de la requête. Par exemple :

lookup-result|b72508d

La liste des opérations, des paramètres spécifiques à l'opération et des réponses est la suivante :

update id
Demande à la table de recharger sa configuration. Le résultat est soit ‘ok’ en cas de succès, soit ‘error’ et un message en cas d'échec.
check service id query
Vérifie si query est présent dans la table. Le résultat est ‘found’ s'il est trouvé, ‘not-found’ s'il ne l'est pas, ou ‘error’ et un message en cas d'erreur.
lookup service id query
Recherche une valeur dans la table pour la query donnée. Le résultat est ‘found’ et la valeur s'ils sont trouvés, ‘not-found’ s'ils ne sont pas trouvés, ou ‘error’ et un message en cas d'erreur.
fetch service id
Récupère le prochain élément de la table, en revenant éventuellement au début. Il n'est pris en charge que pour les services source et relayhost. Le résultat est ‘found’ et la valeur si trouvée, ‘not-found’ si la table est vide, ou ‘error’ et un message en cas d'erreur.

Chaque service a un format spécifique pour le résultat. La syntaxe exacte des valeurs et éventuellement des clés est décrite dans table(5). Les services et leur format de résultat sont les suivants :

alias
Un ou plusieurs alias séparés par une virgule.
auth
Utilisable uniquement pour check. La clé de recherche est le nom d'utilisateur et le mot de passe en clair séparés par ‘:’.
domain
Un nom de domaine.
credentials
Le nom d'utilisateur, suivi de ‘:’ et du mot de passe chiffré conformément à la sous-commande encrypt de smtpctl(8).
netaddr
Adresse IPv4 et IPv6 ou masque de réseau.
userinfo
L'identifiant utilisateur, suivi de ‘:’ puis de l'identifiant de groupe, puis de ‘:’ et enfin du répertoire personnel.
source
Adresse IPv4 et IPv6.
mailaddr
Un nom d'utilisateur, un domaine ou une adresse e-mail complète.
addrname
Utilisé pour mapper les adresses IP aux noms d'hôtes.

EXEMPLES

En supposant que la table s'appelle “devs”, voici un exemple de transaction update échouée :

table|0.1|1713795097.394049|devs|update|478ff0d2
update-result|478ff0d2|error|échec de la connexion à la base de données

Une requête check pour le service netaddr pour l'adresse IPv4 192.168.0.7 qui n'est pas dans la table :

table|0.1|1713795103.314423|devs|check|netaddr|e5862859|192.168.0.7
check-result|e5862859|not-found

Une requête lookup réussie pour le service userinfo pour l'utilisateur ‘op’ :

table|0.1|1713795110.354921|devs|lookup|userinfo|f993c74|op
lookup-result|f993c74|found|1000:1000:/home/op

Une série de requêtes fetch pour le service source qui revient au début :

table|0.1|1713795116.227321|devs|fetch|source|189bd3ee
lookup-result|189bd3ee|found|192.168.1.7
table|0.1|1713795120.162438|devs|fetch|source|9e4c56d4
lookup-result|9e4c56d4|found|10.0.0.8
table|0.1|1713795122.930928|devs|fetch|source|f2c8b906
lookup-result|f2c8b906|found|192.168.1.7

NAME

smtpd-tables — OpenSMTPD configuration tables

SYNOPSIS

smtpd-tables

DESCRIPTION

The OpenSMTPD mailer uses configuration tables to control various aspects of its behavior, such as routing, aliases, and sender rewriting. These tables are typically defined in the main OpenSMTPD configuration file, smtpd.conf(5).

The following types of tables are supported:

  • hosted: Specifies domains for which the server receives mail.

  • relay: Specifies domains or addresses to which mail should be relayed.

  • alias: Maps local recipients to other local or remote recipients.

  • rewrite: Rewrites sender addresses.

  • credentials: Stores authentication credentials for outgoing connections.

  • finger: Specifies information to be returned for a given username.

  • postmaster: Defines the address of the postmaster.

Tables can be specified in several formats, including:

  • file: A plain text file, with one entry per line. The format of the file depends on the type of table.

  • hash: A Berkeley DB hash file. This is a more efficient format for large tables.

  • ldap: An LDAP directory. This allows for centralized management of tables.

DESIGN

The design of the OpenSMTPD configuration tables is centered around flexibility and performance. By allowing different backends (file, hash, ldap), administrators can choose the most appropriate method for managing their mail routing and other configuration data. The use of hash files provides significant performance improvements for large datasets, while LDAP integration enables centralized management in larger environments.

PROTOCOL

The configuration tables themselves do not define a protocol in the traditional sense. They are data structures used by the smtpd daemon to make decisions about mail delivery. The format of the data within each table is specific to the table type and its backend implementation. For example, an alias table in file format typically maps a local username to one or more other usernames or addresses, separated by commas or newlines.

EXAMPLES

A basic smtpd.conf(5) entry for a hosted domain:

table hosted file:/etc/mail/hosted

A corresponding /etc/mail/hosted file:

example.com
        example.org

An example of an alias table:

table alias file:/etc/mail/aliases

A corresponding /etc/mail/aliases file:

root: john, jane@example.net
        info: support@example.com
