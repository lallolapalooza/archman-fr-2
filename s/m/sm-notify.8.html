SM-NOTIFY(8) Manuel de l'administrateur système SM-NOTIFY(8)

NOM

sm-notify - envoie des notifications de redémarrage aux pairs NFS

SYNTAXE

/usr/sbin/sm-notify [-dfn] [-m minutes] [-v nom] [-p port-notification] [-P chemin]

DESCRIPTION

Les verrous de fichiers ne font pas partie de l'état persistant du système de fichiers. L'état des verrous est donc perdu lors d'un redémarrage de l'hôte.

Les systèmes de fichiers réseau doivent également détecter lorsqu'un état de verrouillage est perdu parce qu'un hôte distant a redémarré. Après le redémarrage d'un client NFS, un serveur NFS doit libérer tous les verrous de fichiers détenus par les applications qui s'exécutaient sur ce client. Après le redémarrage d'un serveur, un client doit rappeler au serveur les verrous de fichiers détenus par les applications s'exécutant sur ce client.

Pour NFS version 2 et version 3, le protocole Network Status Monitor (ou NSM en bref) est utilisé pour notifier les pairs NFS des redémarrages. Sous Linux, deux composants distincts en espace utilisateur constituent le service NSM :

sm-notify
Un programme auxiliaire qui notifie les pairs NFS après le redémarrage du système local.
rpc.statd
Un démon qui écoute les notifications de redémarrage provenant d'autres hôtes et gère la liste des hôtes à notifier lorsque le système local redémarre.

Le gestionnaire de verrous NFS local alerte son rpc.statd local de chaque pair distant qui doit être surveillé. Lorsque le système local redémarre, la commande sm-notify notifie le service NSM sur les pairs surveillés du redémarrage. Lorsqu'un pair distant redémarre, ce pair notifie le rpc.statd local, qui transmet à son tour la notification de redémarrage au gestionnaire de verrous NFS local.

FONCTIONNEMENT DU NSM EN DÉTAIL

La première interaction de verrouillage de fichier entre un client NFS et un serveur entraîne le contact des gestionnaires de verrous NFS des deux pairs avec leur service NSM local pour stocker des informations sur le pair opposé. Sous Linux, le gestionnaire de verrous local contacte rpc.statd.

rpc.statd enregistre des informations sur chaque pair NFS surveillé dans un stockage persistant. Ces informations décrivent comment contacter un pair distant en cas de redémarrage du système local, comment reconnaître quel pair surveillé signale un redémarrage et comment notifier le gestionnaire de verrous local lorsqu'un pair surveillé indique qu'il a redémarré.

Un client NFS envoie un nom d'hôte, connu sous le nom de caller_name du client, dans chaque requête de verrouillage de fichier. Un serveur NFS peut utiliser ce nom d'hôte pour envoyer des appels GRANT asynchrones à un client, ou pour notifier au client qu'il a redémarré.

Le serveur NFS Linux peut fournir le caller_name du client ou l'adresse réseau du client à rpc.statd. Aux fins du protocole NSM, ce nom ou cette adresse est connu sous le nom de mon_name du pair surveillé. De plus, le gestionnaire de verrous local indique à rpc.statd quel nom d'hôte il pense être le sien. Aux fins du protocole NSM, ce nom d'hôte est connu sous le nom de my_name.

Il n'y a pas d'interaction équivalente entre un serveur NFS et un client pour informer le client du caller_name du serveur. Par conséquent, les clients NFS ne savent pas réellement quel mon_name un serveur NFS pourrait utiliser dans une requête SM_NOTIFY. Le client NFS Linux enregistre le nom d'hôte du serveur utilisé dans la commande mount pour identifier les serveurs NFS en redémarrage.

Notification de redémarrage

Lorsque le système local redémarre, la commande sm-notify lit la liste des pairs surveillés dans le stockage persistant et envoie une requête SM_NOTIFY au service NSM de chaque pair distant listé. Elle utilise la chaîne mon_name comme destination. Pour identifier quel hôte a redémarré, la commande sm-notify envoie normalement la chaîne my_name enregistrée lorsque ce pair a été surveillé. Le rpc.statd distant fait correspondre les requêtes SM_NOTIFY entrantes à l'aide de cette chaîne, ou de l'adresse réseau de l'appelant, à un ou plusieurs pairs de sa propre liste de surveillance.

Si rpc.statd ne trouve pas de pair dans sa liste de surveillance qui corresponde à une requête SM_NOTIFY entrante, la notification n'est pas transmise au gestionnaire de verrous local. De plus, chaque pair a son propre numéro d'état NSM, un entier de 32 bits qui est incrémenté après chaque redémarrage par la commande sm-notify. rpc.statd utilise ce numéro pour distinguer les redémarrages réels des notifications rejouées.

Une partie de la récupération des verrous NFS consiste à redécouvrir quels pairs doivent à nouveau être surveillés. La commande sm-notify efface la liste de surveillance dans le stockage persistant après chaque redémarrage.

OPTIONS

-d
Maintient sm-notify attaché à son terminal de contrôle et en cours d'exécution au premier plan afin que la progression de la notification puisse être surveillée directement.
-f
Envoie les notifications même si sm-notify a déjà été exécuté depuis le dernier redémarrage du système.
-m temps-retentative
Spécifie la durée, en minutes, pendant laquelle les tentatives de notification vers les hôtes inaccessibles seront poursuivies. Si cette option n'est pas spécifiée, sm-notify tente d'envoyer des notifications pendant 15 minutes. La spécification d'une valeur de 0 fait que sm-notify continue d'envoyer des notifications aux pairs inaccessibles jusqu'à ce qu'il soit arrêté manuellement.
Les notifications sont retentées si l'envoi échoue, si le pair distant ne répond pas, si le service NSM du pair distant n'est pas enregistré, ou s'il y a un échec DNS qui empêche la résolution du mon_name du pair distant en une adresse.
Les hôtes ne sont pas retirés de la liste de notification tant qu'une réponse valide n'a pas été reçue. Cependant, la procédure SM_NOTIFY a un résultat vide. Il n'y a aucun moyen pour sm-notify de savoir si le pair distant a reconnu l'expéditeur et a commencé la récupération appropriée des verrous.
-n
Empêche sm-notify de mettre à jour le numéro d'état NSM du système local.
-p port
Spécifie le numéro de port source que sm-notify doit utiliser lors de l'envoi des notifications de redémarrage. Si cette option n'est pas spécifiée, un port éphémère choisi aléatoirement est utilisé.
Cette option peut être utilisée pour traverser un pare-feu entre le client et le serveur.
-P, --chemin-repertoire-etat chemin
Spécifie le chemin du répertoire parent où résident les informations d'état NSM. Si cette option n'est pas spécifiée, sm-notify utilise par défaut /var/lib/nfs.
Après son démarrage, sm-notify tente de définir son UID et son GID effectifs sur le propriétaire et le groupe du sous-répertoire sm de ce répertoire. Après avoir modifié les identifiants effectifs, sm-notify n'a besoin d'accéder qu'aux fichiers dans sm et sm.bak dans le chemin-repertoire-etat.
-v addr-ip | nom-hote
Spécifie l'adresse réseau à partir de laquelle envoyer les notifications de redémarrage, et l'argument mon_name à utiliser lors de l'envoi des requêtes SM_NOTIFY. Si cette option n'est pas spécifiée, sm-notify utilise une adresse wildcard comme adresse de liaison de transport, et utilise le my_name enregistré lors de la surveillance du pair comme argument mon_name lors de l'envoi des requêtes SM_NOTIFY.
La forme addr-ip peut être exprimée soit comme une adresse de présentation IPv4, soit comme une adresse de présentation IPv6. Si la forme addr-ip est utilisée, la commande sm-notify convertit cette adresse en nom d'hôte pour l'utiliser comme argument mon_name lors de l'envoi des requêtes SM_NOTIFY.
Cette option peut être utile dans les configurations multi-hébergées où le pair distant nécessite une notification à partir d'une adresse réseau spécifique.

FICHIER DE CONFIGURATION

Beaucoup des options qui peuvent être définies sur la ligne de commande peuvent également être contrôlées par des valeurs définies dans la section [sm-notify] ou, dans un cas, la section [statd] du fichier de configuration /etc/nfs.conf.

sm-notify(8) — Arch Linux

NAME

sm-notify - Notify NFS peers about state changes

SYNOPSIS

sm-notify [-v] [-m retries] [-p port] [-h]

DESCRIPTION

The sm-notify command is part of the Network Status Monitor (NSM) protocol implementation in the Linux NFS client. It is used by rpc.statd to notify NFS peers about server reboots. When a server reboots, its NFS client state is lost. sm-notify is called by rpc.statd after a server reboot to inform all clients that were connected to the server that the server is back online and the locks held by those clients are now re-established.

This command should not be executed directly. It is called by rpc.statd when needed.

NSM OPERATION IN DETAIL

When an NFS server restarts (e.g., after a reboot), it needs to recover its state, including any file locks that were held by clients. The NSM protocol is designed to handle this. Here's how sm-notify fits in:

  • 1.

    After a server reboot, rpc.statd is started on the server. It loads its state information from files in /var/lib/nfs/.

  • 2.

    rpc.statd then contacts all the NFS clients that were previously connected to the server. It uses the sm-notify command (or its internal equivalent) to send notification requests to each client.

  • 3.

    Upon receiving the notification, the client's rpc.statd knows that the server has rebooted. It then re-establishes any locks that were held by clients on that server.

The process of re-establishing locks is crucial for maintaining data integrity and preventing applications from hanging indefinitely.

OPTIONS

-v
Enable verbose output. This option is useful for debugging.
-m retries
Set the number of retries for sending notifications. The default is 3 retries.
-p port
Specify the outgoing port to use for notifications. The default is to let the system choose an available port.
-h
Display a help message and exit.

CONFIGURATION FILE

Configuration parameters for sm-notify can also be set in the /etc/nfs.conf file, within the [sm-notify] and [statd] sections.

Values recognized in the [sm-notify] section include: retry-time, outgoing-port, and outgoing-addr. These have the same effect as the command line options m, p, and v respectively.

An additional value recognized in the [sm-notify] section is lift-grace. By default, sm-notify will lift lockd's grace period early if it has no hosts to notify. Some high availability configurations will run one sm-notify per floating IP address. In these configurations, lifting the grace period early may prevent clients from reclaiming locks. Setting lift-grace to n will prevent sm-notify from ending the grace period early. lift-grace has no corresponding command line option.

The value recognized in the [statd] section is state-directory-path.

SECURITY

The sm-notify command must be started as root to acquire privileges needed to access the state information database. It drops root privileges as soon as it starts up to reduce the risk of a privilege escalation attack.

During normal operation, the effective user ID it chooses is the owner of the state directory. This allows it to continue to access files in that directory after it has dropped its root privileges. To control which user ID rpc.statd chooses, simply use chown(1) to set the owner of the state directory.

ADDITIONAL NOTES

Lock recovery after a reboot is critical to maintaining data integrity and preventing unnecessary application hangs.

To help rpc.statd match SM_NOTIFY requests to NLM requests, a number of best practices should be observed, including:

The UTS nodename of your systems should match the DNS names that NFS peers use to contact them
The UTS nodenames of your systems should always be fully qualified domain names
The forward and reverse DNS mapping of the UTS nodenames should be consistent
The hostname the client uses to mount the server should match the server's mon_name in SM_NOTIFY requests it sends

Unmounting an NFS file system does not necessarily stop either the NFS client or server from monitoring each other. Both may continue monitoring each other for a time in case subsequent NFS traffic between the two results in fresh mounts and additional file locking.

On Linux, if the lockd kernel module is unloaded during normal operation, all remote NFS peers are unmonitored. This can happen on an NFS client, for example, if an automounter removes all NFS mount points due to inactivity.

IPv6 and TI-RPC support

TI-RPC is a pre-requisite for supporting NFS on IPv6. If TI-RPC support is built into the sm-notify command ,it will choose an appropriate IPv4 or IPv6 transport based on the network address returned by DNS for each remote peer. It should be fully compatible with remote systems that do not support TI-RPC or IPv6.

Currently, the sm-notify command supports sending notification only via datagram transport protocols.
