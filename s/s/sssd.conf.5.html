SSSD.CONF(5) Formats et Conventions de Fichiers SSSD.CONF(5)

NOM

sssd.conf - le fichier de configuration pour SSSD

FORMAT DU FICHIER

Le fichier a une syntaxe de style ini et se compose de sections et de paramètres. Une section commence par le nom de la section entre crochets et se poursuit jusqu'à ce que la section suivante commence. Un exemple de section avec des paramètres à valeur unique et à valeurs multiples :

[section]
clé = valeur
clé2 = valeur2,valeur3

Les types de données utilisés sont chaîne (pas de guillemets requis), entier et booléen (avec les valeurs « TRUE/FALSE »).

Une ligne de commentaire commence par un signe dièse (« # ») ou un point-virgule (« ; »). Les commentaires en ligne ne sont pas pris en charge.

Toutes les sections peuvent avoir un paramètre optionnel description. Sa fonction est uniquement d'étiqueter la section.

sssd.conf doit être un fichier régulier, accessible uniquement par l'utilisateur utilisé pour exécuter le service SSSD ou par root.

EXTRAITS DE CONFIGURATION DU RÉPERTOIRE INCLUDE

Le fichier de configuration sssd.conf inclura des extraits de configuration en utilisant le répertoire d'inclusion conf.d.

Tout fichier placé dans conf.d se terminant par « .conf » et ne commençant pas par un point (« . ») sera utilisé avec sssd.conf pour configurer SSSD.

Les extraits de configuration de conf.d ont une priorité plus élevée que sssd.conf et remplaceront sssd.conf en cas de conflits. Si plusieurs extraits sont présents dans conf.d, ils sont inclus dans l'ordre alphabétique (basé sur la locale). Les fichiers inclus plus tard ont une priorité plus élevée. Les préfixes numériques (01_snippet.conf, 02_snippet.conf, etc.) peuvent aider à visualiser la priorité (un nombre plus élevé signifie une priorité plus élevée).

Les fichiers d'extrait nécessitent le même propriétaire et les mêmes permissions que sssd.conf.

OPTIONS GÉNÉRALES

Les options suivantes sont utilisables dans plus d'une section de configuration.

Options utilisables dans toutes les sections

debug_level (entier)

SSSD prend en charge deux représentations pour spécifier le niveau de débogage. La plus simple consiste à spécifier une valeur décimale de 0 à 9, ce qui représente l'activation de ce niveau et de tous les messages de débogage des niveaux inférieurs. L'option la plus complète consiste à spécifier un masque de bits hexadécimal pour activer ou désactiver des niveaux spécifiques (par exemple, si vous souhaitez supprimer un niveau).

Veuillez noter que chaque service SSSD enregistre dans son propre fichier journal. Veuillez également noter que l'activation de « debug_level » dans la section « [sssd] » n'active le débogage que pour le processus sssd lui-même, et non pour les processus répondeurs ou fournisseurs. Le paramètre « debug_level » doit être ajouté à toutes les sections à partir desquelles vous souhaitez produire des journaux de débogage.

En plus de modifier le niveau de journalisation dans le fichier de configuration en utilisant le paramètre « debug_level », qui est persistant mais nécessite un redémarrage de SSSD, il est également possible de modifier le niveau de débogage à la volée en utilisant l'outil sss_debuglevel(8).

Niveaux de débogage actuellement pris en charge :

0, 0x0010 : Échecs fatals. Tout ce qui empêcherait SSSD de démarrer ou le ferait cesser de fonctionner.

1, 0x0020 : Échecs critiques. Une erreur qui ne tue pas SSSD, mais qui indique qu'au moins une fonctionnalité majeure ne fonctionnera pas correctement.

2, 0x0040 : Échecs graves. Une erreur annonçant qu'une requête ou une opération particulière a échoué.

3, 0x0080 : Échecs mineurs. Ce sont les erreurs qui remonteraient pour causer l'échec de l'opération 2.

4, 0x0100 : Paramètres de configuration.

5, 0x0200 : Données de fonction.

6, 0x0400 : Messages de trace pour les fonctions d'opération.

7, 0x1000 : Messages de trace pour les fonctions de contrôle internes.

8, 0x2000 : Contenu des variables internes des fonctions qui peuvent être intéressantes.

9, 0x4000 : Informations de traçage de niveau extrêmement bas.

9, 0x20000 : Données de performance et statistiques, veuillez noter qu'en raison de la manière dont les requêtes sont traitées en interne, le temps d'exécution enregistré d'une requête peut être plus long qu'il ne l'a réellement été.

10, 0x10000 : Informations de traçage libldb de niveau encore plus bas. Presque jamais vraiment nécessaire.

Pour enregistrer les niveaux de débogage de masque de bits requis, ajoutez simplement leurs numéros comme indiqué dans les exemples suivants :

Exemple : Pour enregistrer les échecs fatals, les échecs critiques, les échecs graves et les données de fonction, utilisez 0x0270.

Exemple : Pour enregistrer les échecs fatals, les paramètres de configuration, les données de fonction, les messages de trace pour les fonctions de contrôle internes, utilisez 0x1310.

Note : Le format de masque de bits des niveaux de débogage a été introduit dans la version 1.7.0.

Par défaut : 0x0070 (c'est-à-dire les échecs fatals, critiques et graves ; correspond à la définition 2 en notation décimale)

debug (entier)

SSSD 1.14 et versions ultérieures incluent également l'alias debug pour debug_level à titre de commodité. Si les deux sont spécifiés, la valeur de debug_level sera utilisée.

debug_timestamps (booléen)

Ajoute un horodatage aux messages de débogage. Si journald est activé pour la journalisation du débogage SSSD, cette option est ignorée.

Par défaut : vrai

debug_microseconds (booléen)

Ajoute des microsecondes à l'horodatage dans les messages de débogage. Si journald est activé pour la journalisation du débogage SSSD, cette option est ignorée.

Par défaut : faux

debug_backtrace_enabled (booléen)

Active la trace de débogage.

Si SSSD est exécuté avec un debug_level inférieur à 9, tout est enregistré dans un tampon annulaire en mémoire et vidé dans un fichier journal en cas d'erreur jusqu'à et y compris `min(0x0040, debug_level)` (c'est-à-dire si debug_level est explicitement défini sur 0 ou 1, alors seuls ces niveaux d'erreur déclencheront la trace, sinon jusqu'à 2).

La fonctionnalité n'est prise en charge que pour `logger == files` (c'est-à-dire que le paramètre n'a pas d'effet pour les autres types de journalisation).

Par défaut : vrai

Options utilisables dans les sections SERVICE et DOMAINE

timeout (entier)

Délai en secondes entre les battements de cœur pour ce service. Ceci est utilisé pour s'assurer que le processus est en vie et capable de répondre aux requêtes. Notez qu'après trois battements de cœur manqués, le processus se terminera lui-même.

Par défaut : 10

SECTIONS SPÉCIALES

La section [sssd]

Des éléments individuels de la fonctionnalité SSSD sont fournis par des services SSSD spéciaux qui sont démarrés et arrêtés avec SSSD. Les services sont gérés par un service spécial fréquemment appelé « moniteur ». La section « [sssd] » est utilisée pour configurer le moniteur ainsi que certaines autres options importantes comme les domaines d'identité.

Paramètres de section

services

Liste des services séparés par des virgules qui sont démarrés lorsque sssd lui-même démarre. La liste des services est facultative sur les plateformes où systemd est pris en charge, car ils seront activés par socket ou D-Bus lorsque nécessaire.

Services pris en charge : nss, pam, ifp, sudo, autofs, ssh, pac

Par défaut, tous les services sont désactivés et l'administrateur doit activer ceux qui sont autorisés à être utilisés en exécutant : "systemctl enable sssd-@service@.socket".

domains

Un domaine est une base de données contenant des informations utilisateur. SSSD peut utiliser plusieurs domaines en même temps, mais au moins un doit être configuré ou SSSD ne démarrera pas. Ce paramètre décrit la liste des domaines dans l'ordre dans lequel vous souhaitez qu'ils soient interrogés. Il est recommandé qu'un nom de domaine contienne uniquement des caractères ASCII alphanumériques, des tirets, des points et des soulignements. Le caractère « / » est interdit.

re_expression (chaîne)

Expression régulière par défaut qui décrit comment analyser la chaîne contenant le nom d'utilisateur et

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

le domaine en ces composants.

Chaque domaine peut avoir une expression régulière individuelle configurée. Pour certains fournisseurs d'ID, il existe également des expressions régulières par défaut. Voir la section DOMAINES pour plus d'informations sur ces expressions régulières.

full_name_format (chaîne)

Un format compatible printf(3) qui décrit comment composer un nom complet à partir des composants nom d'utilisateur et nom de domaine.

Les expansions suivantes sont prises en charge :

%1$s

nom d'utilisateur

%2$s

nom de domaine tel que spécifié dans le fichier de configuration SSSD.

%3$s

nom plat du domaine. Principalement utilisable pour les domaines Active Directory, qu'ils soient directement configurés ou découverts via des trusts IPA.

Chaque domaine peut avoir une chaîne de format individuelle configurée. Voir la section DOMAINES pour plus d'informations sur cette option.

monitor_resolv_conf (booléen)

Contrôle si SSSD doit surveiller l'état de resolv.conf pour identifier quand il doit mettre à jour son résolveur DNS interne.

Par défaut : true

try_inotify (booléen)

Par défaut, SSSD tentera d'utiliser inotify pour surveiller les modifications des fichiers de configuration et se rabattra sur un sondage toutes les cinq secondes si inotify ne peut pas être utilisé.

Il existe quelques situations limitées où il est préférable de ne même pas essayer d'utiliser inotify. Dans ces rares cas, cette option doit être définie sur 'false'

Par défaut : true sur les plateformes où inotify est pris en charge. False sur d'autres plateformes.

Remarque : cette option n'aura aucun effet sur les plateformes où inotify n'est pas disponible. Sur ces plateformes, le sondage sera toujours utilisé.

krb5_rcache_dir (chaîne)

Répertoire sur le système de fichiers où SSSD doit stocker les fichiers de cache de relecture Kerberos.

Cette option accepte une valeur spéciale __LIBKRB5_DEFAULTS__ qui indiquera à SSSD de laisser libkrb5 décider de l'emplacement approprié pour le cache de relecture.

Par défaut : spécifique à la distribution et spécifié lors de la compilation. (__LIBKRB5_DEFAULTS__ si non configuré)

default_domain_suffix (chaîne)

Veuillez noter que cette option est dépréciée et que domain_resolution_order devrait être utilisée.

Cette chaîne sera utilisée comme nom de domaine par défaut pour tous les noms sans composant de nom de domaine. Le cas d'utilisation principal est les environnements où le domaine principal est destiné à gérer les politiques d'hôtes et où tous les utilisateurs se trouvent dans un domaine approuvé. L'option permet à ces utilisateurs de se connecter simplement avec leur nom d'utilisateur sans spécifier de nom de domaine.

Veuillez noter que si cette option est définie, tous les utilisateurs du domaine principal devront utiliser leur nom complet, par exemple, utilisateur@nom.domaine, pour se connecter. La définition de cette option modifie la valeur par défaut de use_fully_qualified_names à True. Il n'est pas autorisé d'utiliser cette option conjointement avec use_fully_qualified_names défini à False.

Par défaut : non défini

override_space (chaîne)

Ce paramètre remplacera les espaces (barre d'espace) par le caractère donné pour les noms d'utilisateur et de groupe. Par exemple, (_). Le nom d'utilisateur "john doe" deviendra "john_doe". Cette fonctionnalité a été ajoutée pour améliorer la compatibilité avec les scripts shell qui ont du mal à gérer les espaces, en raison du séparateur de champs par défaut dans le shell.

Veuillez noter qu'il s'agit d'une erreur de configuration d'utiliser un caractère de remplacement qui pourrait être utilisé dans les noms d'utilisateur ou de groupe. Si un nom contient le caractère de remplacement, SSSD essaie de retourner le nom non modifié, mais en général, le résultat d'une recherche est indéfini.

Par défaut : non défini (les espaces ne seront pas remplacés)

certificate_verification (chaîne)

Avec ce paramètre, la vérification du certificat peut être ajustée avec une liste d'options séparées par des virgules. Les options prises en charge sont :

no_ocsp

Désactive les vérifications du protocole OCSP (Online Certificate Status Protocol). Cela pourrait être nécessaire si les serveurs OCSP définis dans le certificat ne sont pas accessibles depuis le client.

soft_ocsp

Si une connexion ne peut pas être établie avec un répondeur OCSP, la vérification OCSP est ignorée. Cette option doit être utilisée pour autoriser l'authentification lorsque le système est hors ligne et que le répondeur OCSP ne peut pas être atteint.

ocsp_dgst

Fonction de hachage utilisée pour créer l'ID du certificat pour la requête OCSP. Les valeurs autorisées sont :
•sha1
•sha256
•sha384
•sha512

Par défaut : sha1 (pour permettre la compatibilité avec les répondeurs conformes à RFC5019)

no_verification

Désactive complètement la vérification. Cette option ne doit être utilisée qu'à des fins de test.

partial_chain

Permet à la vérification de réussir même si une chaîne *complète* ne peut pas être construite jusqu'à un point d'ancrage d'approbation auto-signé, à condition qu'il soit possible de construire une chaîne vers un certificat approuvé qui pourrait ne pas être auto-signé.

ocsp_default_responder=URL

Définit le répondeur OCSP par défaut qui doit être utilisé au lieu de celui mentionné dans le certificat. URL doit être remplacé par l'URL du répondeur OCSP par défaut, par exemple http://example.com:80/ocsp.

ocsp_default_responder_signing_cert=NAME

Cette option est actuellement ignorée. Tous les certificats nécessaires doivent être disponibles dans le fichier PEM fourni par pam_cert_db_path.

crl_file=/CHEMIN/VERS/FICHIER/CRL

Utilise la liste de révocation de certificats (CRL) du fichier donné lors de la vérification du certificat. La CRL doit être fournie au format PEM, voir crl(1ssl) pour plus de détails.

soft_crl

Si une CRL a expiré, ignore la date d'expiration de la CRL et vérifie les certificats associés avec la CRL expirée. Cette option doit être utilisée pour permettre l'authentification lorsque le système est hors ligne et que la CRL ne peut pas être renouvelée.

Les options inconnues sont signalées mais ignorées.

Par défaut : non défini, c'est-à-dire qu'aucune restriction sur la vérification du certificat n'est appliquée

disable_netlink (booléen)

SSSD s'accroche à l'interface netlink pour surveiller les modifications des routes, adresses et liens et déclencher certaines actions.

Les changements d'état SSSD causés par les événements netlink peuvent être indésirables et peuvent être désactivés en définissant cette option sur 'true'

Par défaut : false (les modifications netlink sont détectées)

domain_resolution_order

Liste de domaines et sous-domaines séparés par des virgules représentant l'ordre de recherche qui sera suivi. La liste n'a pas à inclure tous les domaines possibles car les domaines manquants seront recherchés en fonction de l'ordre dans lequel ils sont présentés dans l'option de configuration “domains”. Les sous-domaines qui ne sont pas listés dans “lookup_order” seront recherchés dans un ordre aléatoire pour chaque domaine parent.

Veuillez noter que lorsque cette option est définie, le format de sortie de toutes les commandes est toujours entièrement qualifié, même lors de l'utilisation de noms courts en entrée. Si l'administrateur souhaite que la sortie ne soit pas entièrement qualifiée, l'option full_name_format peut être utilisée comme montré ci-dessous : “full_name_format=%1$s” Cependant, gardez à l'esprit que lors de la connexion, les applications de connexion canonicalisent souvent le nom d'utilisateur en appelant getpwnam(3) qui, si un nom court est retourné pour une entrée qualifiée (tout en essayant d'atteindre un utilisateur qui existe dans plusieurs domaines) pourrait réacheminer la tentative de connexion vers le domaine qui utilise des noms courts, rendant cette solution de contournement totalement déconseillée dans les cas où les noms d'utilisateur peuvent se chevaucher entre les domaines.

Par défaut : Non défini

implicit_pac_responder (booléen)

Le répondeur PAC est activé automatiquement pour le fournisseur IPA et AD afin d'évaluer et de vérifier le PAC. S'il doit être désactivé, définissez cette option sur 'false'.

Par défaut : true

core_dumpable (booléen)

Cette option peut être utilisée pour le renforcement général du système : la définir sur 'false' interdit les dumps de cœur pour tous les processus SSSD afin d'éviter de divulguer des mots de passe en texte clair. Voir la page man prctl:PR_SET_DUMPABLE sous Linux ou procctl:PROC_TRACE_CTL sous FreeBSD pour plus de détails.

Notez que ce paramètre n'a aucun effet sur 'ldap_child', 'krb5_child' et 'sssd_pam', car ces binaires privilégiés peuvent avoir une copie des données de keytab de l'hôte en mémoire et leur comportement à cet égard est régi par le paramètre système /proc/sys/fs/suid_dumpable.

Par défaut : true

passkey_verification (chaîne)

Avec ce paramètre, la vérification du passkey peut être ajustée avec une liste d'options séparées par des virgules. Les options prises en charge sont :

user_verification (booléen)

Active ou désactive la vérification utilisateur (c'est-à-dire PIN, empreinte digitale) lors de l'authentification. Si elle est activée, le PIN sera toujours demandé.

Par défaut, les paramètres de la clé décident quoi faire. Dans le cas d'une pré-authentification IPA ou Kerberos, cette valeur sera écrasée par le serveur.

SECTIONS SERVICES

Les paramètres qui peuvent être utilisés pour configurer différents services sont décrits dans cette section. Ils doivent résider dans la section [$NOM], par exemple, pour le service NSS, la section serait “[nss]”

Options générales de configuration des services

Ces options peuvent être utilisées pour configurer n'importe quel service.

fd_limit

Cette option spécifie le nombre maximum de descripteurs de fichiers qui peuvent être ouverts simultanément par ce processus SSSD. Sur les systèmes où SSSD se voit accorder la capacité CAP_SYS_RESOURCE, il s'agira d'un réglage absolu. Sur les systèmes sans cette capacité, la valeur résultante sera la plus basse entre celle-ci et la limite "hard" de limits.conf.

Par défaut : 8192 (ou limite "hard" de limits.conf)

client_idle_timeout

Cette option spécifie le nombre de secondes pendant lesquelles un client d'un processus SSSD peut conserver un descripteur de fichier sans communiquer dessus. Cette valeur est limitée afin d'éviter l'épuisement des ressources sur le système. La valeur du délai d'attente ne peut pas être inférieure à 10 secondes. Si une valeur inférieure est configurée, elle sera ajustée à 10 secondes.

Par défaut : 60, KCM : 300

offline_timeout (entier)

Lorsque SSSD passe en mode hors ligne, le temps avant qu'il ne tente de revenir en ligne augmente en fonction du temps passé déconnecté. Par défaut, SSSD utilise un comportement incrémental pour calculer le délai entre les tentatives. Ainsi, le temps d'attente pour une tentative donnée sera plus long que le temps d'attente pour t

les précédents. Après chaque tentative infructueuse de se connecter en ligne, le nouvel intervalle est recalculé comme suit :

nouveau_délai = Minimum(ancien_délai * 2, offline_timeout_max) + aléatoire[0...offline_timeout_random_offset]

La valeur par défaut de offline_timeout est 60. La valeur par défaut de offline_timeout_max est 3600. La valeur par défaut de offline_timeout_random_offset est 30. Le résultat final est le nombre de secondes avant la prochaine tentative.

Notez que la durée maximale de chaque intervalle est définie par offline_timeout_max (en plus de la partie aléatoire).

Par défaut : 60

offline_timeout_max (entier)

Contrôle jusqu'à quel point le temps entre les tentatives de se connecter en ligne peut être incrémenté suite à des tentatives infructueuses de se connecter en ligne.

Une valeur de 0 désactive le comportement d'incrémentation.

La valeur de ce paramètre doit être définie en corrélation avec la valeur du paramètre offline_timeout.

Avec offline_timeout défini à 60 (valeur par défaut), il est inutile de régler offline_timeout_max à moins de 120 car il sera saturé instantanément. La règle générale ici devrait être de régler offline_timeout_max à au moins 4 fois offline_timeout.

Bien qu'une valeur comprise entre 0 et offline_timeout puisse être spécifiée, elle a pour effet de remplacer la valeur de offline_timeout, donc elle est d'une utilité limitée.

Par défaut : 3600

offline_timeout_random_offset (entier)

Lorsque SSSD est en mode hors ligne, il continue de sonder les serveurs backend à des intervalles de temps spécifiés :

nouveau_délai = Minimum(ancien_délai * 2, offline_timeout_max) + aléatoire[0...offline_timeout_random_offset]

Ce paramètre contrôle la valeur du décalage aléatoire utilisé pour l'équation ci-dessus. La valeur finale du décalage aléatoire sera un nombre aléatoire dans la plage :

[0 - offline_timeout_random_offset]

Une valeur de 0 désactive l'ajout du décalage aléatoire.

Par défaut : 30

responder_idle_timeout

Cette option spécifie le nombre de secondes pendant lesquelles un processus répondeur SSSD peut rester actif sans être utilisé. Cette valeur est limitée afin d'éviter l'épuisement des ressources sur le système. La valeur minimale acceptable pour cette option est de 60 secondes. Régler cette option à 0 (zéro) signifie qu'aucun délai d'expiration ne sera défini pour le répondeur. Cette option n'a d'effet que lorsque SSSD est compilé avec le support de systemd et lorsque les services sont activés par socket ou D-Bus.

Par défaut : 300

cache_first

Cette option spécifie si le répondeur doit interroger tous les caches avant d'interroger les fournisseurs de données.

Par défaut : true

Options de configuration NSS

Ces options peuvent être utilisées pour configurer le service Name Service Switch (NSS).

enum_cache_timeout (entier)

Combien de secondes le cache des énumérations nss_sss (requêtes d'informations sur tous les utilisateurs) doit être conservé.

Par défaut : 120

entry_cache_nowait_percentage (entier)

Le cache d'entrées peut être configuré pour mettre à jour automatiquement les entrées en arrière-plan si elles sont demandées au-delà d'un certain pourcentage de la valeur de entry_cache_timeout pour le domaine.

Par exemple, si le entry_cache_timeout du domaine est réglé à 30 s et que entry_cache_nowait_percentage est réglé à 50 (pour cent), les entrées qui arrivent après 15 secondes par rapport à la dernière mise à jour du cache seront renvoyées immédiatement, mais SSSD ira mettre à jour le cache de son côté, de sorte que les futures requêtes n'auront pas à attendre une mise à jour du cache.

Les valeurs valides pour cette option sont 0-99 et représentent un pourcentage de entry_cache_timeout pour chaque domaine. Pour des raisons de performance, ce pourcentage ne réduira jamais le délai d'attente à moins de 10 secondes. (0 désactive cette fonctionnalité)

Par défaut : 50

entry_negative_timeout (entier)

Spécifie pendant combien de secondes nss_sss doit mettre en cache les succès du cache négatif (c'est-à-dire les requêtes pour des entrées de base de données invalides, comme celles inexistantes) avant de redemander au backend.

Par défaut : 15

filter_users, filter_groups (chaîne de caractères)

Exclure certains utilisateurs ou groupes de la récupération à partir de la base de données NSS de sss. Ceci est particulièrement utile pour les comptes système. Cette option peut également être définie par domaine ou inclure des noms complets pour filtrer uniquement les utilisateurs du domaine particulier ou par nom principal d'utilisateur (UPN).

NOTE : L'option filter_groups n'affecte pas l'héritage des membres de groupes imbriqués, car le filtrage se produit après leur propagation pour être renvoyés via NSS. Par exemple, un groupe ayant un membre groupe filtré ne listera toujours pas les utilisateurs de ce dernier.

Par défaut : root

filter_users_in_groups (booléen)

Si vous souhaitez que les utilisateurs filtrés restent membres de groupe, définissez cette option sur false.

Par défaut : true

override_homedir (chaîne de caractères)

Remplacer le répertoire personnel de l'utilisateur. Vous pouvez fournir une valeur absolue ou un modèle. Dans le modèle, les séquences suivantes sont substituées :

%u

nom de connexion

%U

numéro UID

%d

nom du domaine

%f

nom d'utilisateur complet (utilisateur@domaine)

%l

La première lettre du nom de connexion.

%P

UPN - Nom Principal d'Utilisateur (nom@REALM)

%o

La valeur du répertoire personnel définie dans le répertoire du fournisseur d'identité.

Cette substitution est conçue pour être utilisée dans un scénario de confiance IPA-AD. Si cette substitution est utilisée pour l'option subdomain_homedir, elle propage la valeur du répertoire personnel du domaine AD aux clients IPA. Dans ce scénario, l'option doit être définie dans la configuration SSSD sur le serveur IPA où SSSD s'exécute en mode serveur.

%h

La valeur de l'option de configuration homedir_substring.

%H

La valeur de l'option de configuration homedir_substring.

%%

un caractère '%' littéral

Cette option peut également être définie par domaine.

exemple :

override_homedir = /home/%u

Par défaut : non défini (SSSD utilisera la valeur récupérée de LDAP)

Restreint le shell de l'utilisateur à l'une des valeurs listées. L'ordre d'évaluation est le suivant :

1. Si le shell est présent dans « /etc/shells », il est utilisé.

2. Si le shell est dans la liste allowed_shells mais pas dans « /etc/shells », utilisez la valeur du paramètre shell_fallback.

3. Si le shell n'est ni dans la liste allowed_shells ni dans « /etc/shells », un shell de connexion impossible (nologin) est utilisé.

Le caractère générique (*) peut être utilisé pour autoriser n'importe quel shell.

Le (*) est utile si vous souhaitez utiliser shell_fallback au cas où le shell de l'utilisateur ne serait pas dans « /etc/shells » et que la maintenance d'une liste de tous les shells autorisés dans allowed_shells serait trop coûteuse.

Une chaîne vide pour le shell est passée telle quelle à libc.

« /etc/shells » n'est lu qu'au démarrage de SSSD, ce qui signifie qu'un redémarrage de SSSD est requis en cas d'installation d'un nouveau shell.

Remplace toute instance de ces shells par le shell_fallback

Options de configuration PAM

Ces options peuvent être utilisées pour configurer le service de module d'authentification enfichable (PAM).

offline_credentials_expiration (entier)

Si le fournisseur d'authentification est hors ligne, combien de temps nous devons autoriser les connexions mises en cache (en jours depuis la dernière connexion en ligne réussie).

Défaut : 0 (Pas de limite)

offline_failed_login_attempts (entier)

Si le fournisseur d'authentification est hors ligne, combien de tentatives de connexion échouées sont autorisées.

Défaut : 0 (Pas de limite)

offline_failed_login_delay (entier)

Le temps en minutes qui doit s'écouler après que le nombre de tentatives de connexion échouées hors ligne ait été atteint avant qu'une nouvelle tentative de connexion ne soit possible.

Si défini sur 0, l'utilisateur ne peut pas s'authentifier hors ligne si le nombre de tentatives de connexion échouées hors ligne a été atteint. Seule une authentification en ligne réussie peut réactiver l'authentification hors ligne.

Défaut : 5

pam_verbosity (entier)

Contrôle quels types de messages sont affichés à l'utilisateur pendant l'authentification. Plus le chiffre est élevé, plus les messages sont affichés.

Actuellement, sssd prend en charge les valeurs suivantes :

0 : aucun message à afficher

1 : afficher uniquement les messages importants

2 : afficher les messages d'information

3 : afficher tous les messages et les informations de débogage

Défaut : 1

pam_response_filter (chaîne)

Une liste de chaînes séparées par des virgules qui permet de supprimer (filtrer) les données envoyées par le répondeur PAM au module PAM pam_sss. Il existe différents types de réponses envoyées à pam_sss, par exemple les messages affichés à l'utilisateur ou les variables d'environnement qui doivent être définies par pam_sss.

Alors que les messages peuvent déjà être contrôlés à l'aide de l'option pam_verbosity, cette option permet de filtrer d'autres types de réponses.

Actuellement, les filtres suivants sont pris en charge :

ENV

Ne pas envoyer de variables d'environnement à aucun service.

ENV:nom_variable

Ne pas envoyer la variable d'environnement nom_variable à aucun service.

ENV:nom_variable:service

Ne pas envoyer la variable d'environnement nom_variable au service.

La liste des chaînes peut soit être la liste des filtres qui définiront cette liste de filtres et écraseront les valeurs par défaut. Soit chaque élément de la liste peut être préfixé par un caractère '+' ou '-', ce qui ajoutera le filtre à la liste par défaut existante ou le supprimera des valeurs par défaut, respectivement. Veuillez noter que soit tous les éléments de la liste doivent avoir un préfixe '+' ou '-' soit aucun. Il est considéré comme une erreur de mélanger les deux styles.

Défaut : ENV:KRB5CCNAME:sudo, ENV:KRB5CCNAME:sudo-i

Exemple : -ENV:KRB5CCNAME:sudo-i supprimera le filtre de la liste par défaut

pam_id_timeout (entier)

Pour toute requête PAM lorsque SSSD est en ligne, SSSD tentera de mettre immédiatement à jour les informations d'identité mises en cache pour l'utilisateur afin de garantir que l'authentification s'effectue avec les informations les plus récentes.

Une conversation PAM complète peut effectuer plusieurs requêtes PAM, telles que la gestion de compte et l'ouverture de session. Cette option contrôle (par application cliente) combien de temps (en secondes) nous pouvons mettre en cache les informations d'identité pour éviter des allers-retours excessifs vers le fournisseur d'identité.

Défaut : 5

pam_pwd_expiration_warning (entier)

Afficher un avertissement N jours avant l'expiration du mot de passe.

Veuillez noter que le serveur backend doit fournir des informations sur la date d'expiration du mot de passe. Si ces informations sont manquantes, sssd ne peut pas afficher d'avertissement.

Si zéro est défini, ce filtre n'est pas appliqué, c'est-à-dire que si l'avertissement d'expiration a été reçu du serveur backend, il sera automatiquement affiché.

Ce paramètre peut être remplacé en définissant pwd_expiration_warning pour un domaine particulier.

Spécifie le temps en secondes pendant lequel la liste des sous-domaines sera considérée comme valide.

Défaut : 60

Deux valeurs spéciales pour l'option pam_public_domains sont définies :

p11_uri (chaîne)

URI PKCS#11 (voir RFC-7512 pour plus de détails) qui peut être utilisée pour restreindre la sélection des périphériques utilisés pour l'authentification par carte à puce. Par défaut, p11_child de SSSD recherche un emplacement (lecteur) PKCS#11 où le drapeau 'removable' est défini et lit les certificats du jeton inséré depuis le premier emplacement trouvé. Si plusieurs lecteurs sont connectés, p11_uri peut être utilisé pour indiquer à p11_child d'utiliser un lecteur spécifique.

Exemple :

p11_uri = pkcs11:slot-description=My%20Smartcard%20Reader

ou

p11_uri = pkcs11:library-description=OpenSC%20smartcard%20framework;slot-id=2

Pour trouver des URI appropriés, veuillez vérifier la sortie de débogage de p11_child. Alternativement, l'utilitaire GnuTLS 'p11tool' avec par exemple '--list-all' affichera également les URI PKCS#11.

toujours

pas_de_session

Effectuer une recherche en ligne uniquement s'il n'y a pas de session active de l'utilisateur, c'est-à-dire si l'utilisateur n'est actuellement pas connecté

jamais

Ne jamais forcer une recherche en ligne, utiliser les données du cache tant qu'elles ne sont pas expirées

pam_gssapi_check_upn

Remarque : Cette option peut également être définie par domaine, ce qui remplace la valeur dans la section [pam]. Elle peut également être définie pour un domaine de confiance, ce qui remplace la valeur dans la section du domaine.

pam_gssapi_indicators_map

Liste des indicateurs d'authentification séparés par des virgules requis pour être présents dans un ticket Kerberos afin d'accéder à un service PAM autorisé à tenter une authentification GSSAPI en utilisant le module pam_sss_gss.so.

Chaque élément de la liste peut être soit un nom d'indicateur d'authentification, soit une paire “service:indicateur”. Les indicateurs non préfixés par le nom du service PAM seront requis pour accéder à tout service PAM configuré pour être utilisé avec pam_gssapi_services. Une liste résultante d'indicateurs par service PAM est ensuite comparée aux indicateurs dans le ticket Kerberos lors de l'authentification par pam_sss_gss.so. Tout indicateur du ticket qui correspond à la liste résultante d'indicateurs pour le service PAM accordera l'accès. Si aucun des indicateurs de la liste ne correspond, l'accès sera refusé. Si la liste résultante d'indicateurs pour le service PAM est vide, la vérification n'empêchera pas l'accès.

Pour désactiver la vérification des indicateurs d'authentification GSSAPI, définissez cette option sur “-” (tiret). Pour désactiver la vérification pour un service PAM spécifique, ajoutez “service:-”.

Remarque : Cette option peut également être définie par domaine, ce qui remplace la valeur dans la section [pam]. Elle peut également être définie pour un domaine de confiance, ce qui remplace la valeur dans la section du domaine.

Les indicateurs d'authentification suivants sont pris en charge par les déploiements Kerberos IPA :

•pkinit -- pré-authentification utilisant des certificats X.509 -- qu'ils soient stockés dans des fichiers ou sur des cartes à puce.
•hardened -- pré-authentification SPAKE ou toute pré-authentification encapsulée dans un canal FAST.
•radius -- pré-authentification avec l'aide d'un serveur RADIUS.
•otp -- pré-authentification utilisant l'authentification intégrée à deux facteurs (2FA ou mot de passe à usage unique, OTP) dans IPA.
•idp -- pré-authentification utilisant un fournisseur d'identité externe.

Exemple : pour exiger l'accès aux services SUDO uniquement pour les utilisateurs qui ont obtenu leurs tickets Kerberos avec une pré-authentification par certificat X.509 (PKINIT), définissez

pam_gssapi_indicators_map = sudo:pkinit, sudo-i:pkinit

Par défaut : non défini (l'utilisation des indicateurs d'authentification n'est pas requise)

Options de configuration SSH

Ces options peuvent être utilisées pour configurer le service SSH.

ssh_use_certificate_keys (booléen)

Si défini sur vrai, sss_ssh_authorizedkeys renverra également les clés ssh dérivées de la clé publique des certificats X.509 stockés dans l'entrée utilisateur. Voir sss_ssh_authorizedkeys(1) pour plus de détails.

Par défaut : vrai

ssh_use_certificate_matching_rules (chaîne)

Par défaut, le répondeur ssh utilisera toutes les règles de correspondance de certificat disponibles pour filtrer les certificats afin que les clés ssh ne soient dérivées que des certificats correspondants. Avec cette option, les règles utilisées peuvent être restreintes avec une liste de noms de règles de mappage et de correspondance séparés par des virgules. Toutes les autres règles seront ignorées.

Il existe deux mots-clés spéciaux 'all_rules' et 'no_rules' qui activeront toutes les règles ou aucune règle, respectivement. Ce dernier signifie qu'aucun certificat ne sera filtré et que les clés ssh seront générées à partir de tous les certificats valides.

Si aucune règle n'est configurée, 'all_rules' activera une règle par défaut qui active tous les certificats appropriés à l'authentification client. C'est le même comportement que pour le répondeur PAM si l'authentification par certificat est activée.

Un nom de règle inexistant est considéré comme une erreur. Si, par conséquent, aucune règle n'est sélectionnée, tous les certificats seront ignorés.

Par défaut : non défini, équivalent à 'all_rules', toutes les règles trouvées ou la règle par défaut sont utilisées

ca_db (chaîne)

Chemin vers un stockage de certificats d'autorité de certification (AC) de confiance. L'option est utilisée pour valider les certificats utilisateur avant d'en dériver les clés ssh publiques.

Par défaut :

•/etc/sssd/pki/sssd_auth_ca_db.pem (chemin vers un fichier avec des certificats d'AC de confiance au format PEM)

allowed_uids (chaîne)

Spécifie la liste des identifiants d'utilisateur (UID) ou des noms d'utilisateur, séparés par des virgules, qui sont autorisés à accéder au répondeur PAC. Les noms d'utilisateur sont résolus en UID au démarrage.

pac_lifetime (entier)

Durée de vie de l'entrée PAC en secondes. Tant que le PAC est valide, les données du PAC peuvent être utilisées pour déterminer les appartenances aux groupes d'un utilisateur.

pac_check (chaîne)

Applique des vérifications supplémentaires au PAC du ticket Kerberos disponible dans les domaines Active Directory et FreeIPA, si configuré. Veuillez noter que la validation du ticket Kerberos doit être activée pour pouvoir vérifier le PAC, c'est-à-dire que l'option krb5_validate doit être définie sur 'True', ce qui est le comportement par défaut pour les fournisseurs IPA et AD. Si krb5_validate est défini sur 'False', les vérifications du PAC seront ignorées.

Les options suivantes peuvent être utilisées seules ou dans une liste séparée par des virgules :

no_check

Le PAC ne doit pas être présent et même s'il est présent, aucune vérification supplémentaire ne sera effectuée.

pac_present

Le PAC doit être présent dans le ticket de service que SSSD demandera avec l'aide du TGT de l'utilisateur. Si le PAC n'est pas disponible, l'authentification échouera.

check_upn

Si le PAC est présent, vérifie si les informations du nom d'utilisateur principal (UPN) sont cohérentes.

check_upn_allow_missing

Cette option doit être utilisée conjointement avec 'check_upn' et gère le cas où un UPN est défini côté serveur mais n'est pas lu par SSSD. L'exemple typique est un domaine FreeIPA où 'ldap_user_principal' est défini sur un nom d'attribut inexistant. Ceci était généralement fait pour contourner des problèmes dans la gestion des principaux d'entreprise. Mais cela est corrigé depuis un certain temps et FreeIPA peut gérer les principaux d'entreprise sans problème, et il n'est plus nécessaire de définir 'ldap_user_principal'.

Actuellement, cette option est définie par défaut pour éviter les régressions dans de tels environnements. Un message de journalisation sera ajouté au journal système et au journal de débogage de SSSD si un UPN est trouvé dans le PAC mais pas dans le cache de SSSD. Pour éviter ce message de journalisation, il serait préférable d'évaluer si l'option 'ldap_user_principal' peut être supprimée. Si ce n'est pas possible, la suppression de 'check_upn' sautera le test et évitera le message de journalisation.

upn_dns_info_present

Le PAC doit contenir le tampon UPN-DNS-INFO, implique 'check_upn'.

check_upn_dns_info_ex

Si le PAC est présent et que l'extension du tampon UPN-DNS-INFO est disponible, vérifie si les informations de l'extension sont cohérentes.

upn_dns_info_ex_present

Le PAC doit contenir l'extension du tampon UPN-DNS-INFO, implique 'check_upn_dns_info_ex', 'upn_dns_info_present' et 'check_upn'.

Par défaut : no_check (fournisseurs AD et IPA 'check_upn, check_upn_allow_missing, check_upn_dns_info_ex')

Configuration des options d'enregistrement de session

L'enregistrement de session fonctionne en conjonction avec tlog-rec-session(8), une partie du package tlog, pour enregistrer ce que les utilisateurs voient et tapent lorsqu'ils se connectent sur un terminal texte. Voir aussi sssd-session-recording(5).

Ces options peuvent être utilisées pour configurer l'enregistrement de session.

scope (chaîne)

Une des chaînes suivantes spécifiant la portée de l'enregistrement de session :

"none"

Aucun utilisateur n'est enregistré.

"some"

Les utilisateurs/groupes spécifiés par les options users et groups sont enregistrés.

"all"

Tous les utilisateurs sont enregistrés.

Par défaut : "none"

users (chaîne)

Une liste d'utilisateurs séparés par des virgules qui devraient avoir l'enregistrement de session activé. Correspond aux noms d'utilisateurs tels que retournés par NSS. C'est-à-dire, après le remplacement possible des espaces, les changements de casse, etc.

Par défaut : Vide. Ne correspond à aucun utilisateur.

groups (chaîne)

Une liste de groupes séparés par des virgules, dont les membres devraient avoir l'enregistrement de session activé. Correspond aux noms de groupes tels que retournés par NSS. C'est-à-dire, après le remplacement possible des espaces, les changements de casse, etc.

NOTE : l'utilisation de cette option (l'avoir définie sur n'importe quelle valeur) a un coût de performance considérable, car chaque demande non mise en cache pour un utilisateur nécessite de récupérer et de faire correspondre les groupes dont l'utilisateur est membre.

Par défaut : Vide. Ne correspond à aucun groupe.

exclude_users (chaîne)

Une liste d'utilisateurs séparés par des virgules à exclure de l'enregistrement, applicable uniquement avec 'scope=all'.

Par défaut : Vide. Aucun utilisateur exclu.

exclude_groups (chaîne)

Une liste de groupes séparés par des virgules, dont les membres devraient être exclus de l'enregistrement. Applicable uniquement avec 'scope=all'.

NOTE : l'utilisation de cette option (l'avoir définie sur n'importe quelle valeur) a un coût de performance considérable, car chaque demande non mise en cache pour un utilisateur nécessite de récupérer et de faire correspondre les groupes dont l'utilisateur est membre.

Par défaut : Vide. Aucun groupe exclu.

SECTIONS DE DOMAINE

Ces options de configuration peuvent être présentes dans une section de configuration de domaine, c'est-à-dire dans une section appelée « [domain/NOM] »

enabled

Active ou désactive explicitement le domaine. Si « true », le domaine est toujours « activé ». Si « false », le domaine est toujours « désactivé ». Si cette option n'est pas définie, le domaine est activé uniquement s'il est répertorié dans l'option domains de la section « [sssd] ».

domain_type (chaîne)

Spécifie si le domaine est destiné à être utilisé par des clients compatibles POSIX tels que le Name Service Switch ou par des applications qui n'ont pas besoin de données POSIX présentes ou générées. Seuls les objets des domaines POSIX sont disponibles pour les interfaces et utilitaires du système d'exploitation.

Les valeurs autorisées pour cette option sont « posix » et « application ».

Les domaines POSIX sont accessibles par tous les services. Les domaines d'application ne sont accessibles que depuis le répondeur InfoPipe (voir sssd-ifp(5)) et le répondeur PAM.

NOTE : Les domaines d'application sont actuellement bien testés uniquement avec « id_provider=ldap ».

Pour une manière simple de configurer des domaines non-POSIX, veuillez consulter la section « Domaines d'application ».

Par défaut : posix

min_id,max_id (entier)

Limites d'UID et de GID pour le domaine. Si un domaine contient une entrée qui se trouve en dehors de ces limites, elle est ignorée.

Pour les utilisateurs, cela affecte la limite du GID primaire. L'utilisateur ne sera pas retourné à NSS si l'UID ou le GID primaire est en dehors de la plage. Pour les appartenances à des groupes non primaires, ceux qui sont dans la plage seront signalés comme prévu.

Ces limites d'ID affectent même l'enregistrement des entrées dans le cache, pas seulement leur retour par nom ou par ID.

Par défaut : 1 pour min_id, 0 (aucune limite) pour max_id

enumerate (bool)

Détermine si un domaine peut être énuméré, c'est-à-dire si le domaine peut lister tous les utilisateurs et groupes qu'il contient. Notez qu'il n'est pas nécessaire d'activer l'énumération pour que les groupes secondaires soient affichés. Ce paramètre peut prendre l'une des valeurs suivantes :

TRUE = Les utilisateurs et groupes sont énumérés

FALSE = Aucune énumération pour ce domaine

Par défaut : FALSE

L'énumération d'un domaine nécessite que SSSD télécharge et stocke TOUTES les entrées d'utilisateur et de groupe du serveur distant.

La fonctionnalité n'est prise en charge que pour les domaines avec id_provider = ldap ou id_provider = proxy.

Note : l'activation de l'énumération a un impact sévère sur les performances de SSSD pendant que l'énumération est en cours. Cela peut prendre jusqu'à plusieurs minutes après le démarrage de SSSD pour que les énumérations se terminent complètement. Pendant ce temps, les requêtes individuelles d'informations iront directement à LDAP, bien que cela puisse être lent, en raison du traitement intensif de l'énumération. L'enregistrement d'un grand nombre d'entrées dans le cache après la fin de l'énumération peut également être coûteux en termes de CPU, car les appartenances doivent être recalculées. Cela peut entraîner le processus « sssd_be » à devenir non réactif, voire à être redémarré par le chien de garde interne.

Pendant que la première énumération est en cours, les requêtes pour les listes complètes d'utilisateurs ou de groupes peuvent ne retourner aucun résultat jusqu'à ce qu'elle soit terminée.

De plus, l'activation de l'énumération peut augmenter le temps nécessaire pour détecter une déconnexion réseau, car des délais d'attente plus longs sont nécessaires pour garantir que les requêtes d'énumération se terminent avec succès. Pour plus d'informations, référez-vous aux pages man du fournisseur d'identité spécifique utilisé.

Pour les raisons susmentionnées, l'activation de l'énumération n'est pas recommandée, en particulier dans les environnements de grande taille.

Note : le fournisseur proxy est testé avec des modules open source comme 'libnss_files' et 'libnss_ldap'. Les modules tiers doivent suivre le comportement documenté des modules nss pour être utilisés dans cette configuration.

refresh_expired_interval (integer)

Spécifie combien de secondes SSSD doit attendre avant de déclencher une tâche d'actualisation en arrière-plan qui actualisera tous les enregistrements expirés ou presque expirés.

L'actualisation en arrière-plan traitera les utilisateurs, les groupes et les netgroup dans le cache. Pour les utilisateurs qui ont effectué l'opération initgroups (obtenir l'appartenance au groupe pour l'utilisateur, généralement exécutée à la connexion) dans le passé, l'entrée utilisateur et l'appartenance au groupe sont mises à jour.

Cette option est automatiquement héritée pour tous les domaines approuvés.

Vous pouvez envisager de définir cette valeur sur 3/4 de entry_cache_timeout.

Une entrée de cache sera actualisée par une tâche en arrière-plan lorsque les 2/3 du temps d'expiration du cache seront écoulés. S'il existe des entrées mises en cache, la tâche en arrière-plan se référera aux valeurs d'expiration d'origine au lieu de la valeur de configuration actuelle. Cela peut conduire à une situation où l'actualisation en arrière-plan ne semble pas fonctionner. Ceci est fait intentionnellement pour améliorer le fonctionnement en mode hors ligne et la réutilisation des entrées de cache valides existantes. Pour rendre ce changement instantané, l'utilisateur peut vouloir invalider manuellement le cache existant.

Par défaut : 0 (désactivé)

cache_credentials (bool)

Détermine si les identifiants utilisateur sont également mis en cache dans le cache LDB local. Les identifiants mis en cache font référence aux mots de passe, qui incluent le premier facteur (à long terme) de l'authentification à deux facteurs, et non à d'autres mécanismes d'authentification. Les authentifications par clé d'accès et carte à puce sont censées fonctionner hors ligne tant qu'une authentification en ligne réussie est enregistrée dans le cache sans configuration supplémentaire.

Notez que bien que les identifiants soient stockés sous forme de hachage SHA512 salé, cela pose toujours un risque de sécurité potentiel au cas où un attaquant parviendrait à accéder à un fichier de cache (nécessite normalement un accès privilégié) et à casser un mot de passe par une attaque par force brute.

Par défaut : FAUX

cache_credentials_minimal_first_factor_length (int)

Si l'authentification à 2 facteurs (2FA) est utilisée et que les identifiants doivent être enregistrés, cette valeur détermine la longueur minimale que doit avoir le premier facteur d'authentification (mot de passe à long terme) pour être enregistré sous forme de hachage SHA512 dans le cache.

Cela devrait éviter que les courts codes PIN d'un schéma 2FA basé sur des codes PIN soient enregistrés dans le cache, ce qui les rendrait faciles à cibler pour des attaques par force brute.

Par défaut : 8

“ldap” pour charger les cartes stockées dans LDAP. Voir sssd-ldap(5) pour plus d'informations sur la configuration LDAP.

“ipa” pour charger les cartes stockées dans un serveur IPA. Voir sssd-ipa(5) pour plus d'informations sur la configuration d'IPA.

“ad” pour charger les cartes stockées dans un serveur AD. Voir sssd-ad(5) pour plus d'informations sur la configuration du fournisseur AD.

“none” désactive explicitement autofs.

Par défaut : La valeur de “id_provider” est utilisée s'il est défini et peut gérer les requêtes autofs.

hostid_provider (string)

Le fournisseur utilisé pour récupérer les informations d'identité de l'hôte. Les fournisseurs hostid pris en charge sont :

“ipa” pour charger l'identité de l'hôte stockée dans un serveur IPA. Voir sssd-ipa(5) pour plus d'informations sur la configuration d'IPA.

“none” désactive explicitement hostid.

Par défaut : La valeur de “id_provider” est utilisée s'il est défini et peut gérer les requêtes hostid.

resolver_provider (string)

Le fournisseur qui doit gérer les recherches d'hôtes et de réseaux. Les fournisseurs de résolution pris en charge sont :

“proxy” pour transférer les recherches vers une autre bibliothèque NSS. Voir « proxy_resolver_lib_name »

“ldap” pour récupérer les hôtes et les réseaux stockés dans LDAP. Voir sssd-ldap(5) pour plus d'informations sur la configuration LDAP.

“ad” pour récupérer les hôtes et les réseaux stockés dans AD. Voir sssd-ad(5) pour plus d'informations sur la configuration du fournisseur AD.

“none” interdit explicitement la récupération des hôtes et des réseaux.

Par défaut : La valeur de “id_provider” est utilisée s'il est défini et peut gérer les requêtes de résolution.

re_expression (string)

Expression régulière pour ce domaine qui décrit comment analyser la chaîne contenant le nom d'utilisateur et le domaine en ces composants. Le « domaine » peut correspondre soit au nom du domaine de configuration SSSD, soit, dans le cas des sous-domaines de confiance IPA et des domaines Active Directory, au nom plat (NetBIOS) du domaine.

Par défaut : “^((?P<name>.+)@(?P<domain>[^@]*)|(?P<name>[^@]+))$” qui autorise deux styles différents pour les noms d'utilisateur :

•nomutilisateur
•nomutilisateur@nom.domaine

Par défaut pour le fournisseur AD et IPA : “^(((?P<domain>[^\\]+)\\(?P<name>.+))|((?P<name>.+)@(?P<domain>[^@]+))|((?P<name>[^@\\]+)))$” qui autorise trois styles différents pour les noms d'utilisateur :

•nomutilisateur
•nomutilisateur@nom.domaine
•domaine\nomutilisateur

Alors que les deux premiers correspondent au défaut général, le troisième est introduit pour permettre une intégration facile des utilisateurs des domaines Windows.

Le re_expression par défaut utilise le caractère « @ » comme séparateur entre le nom et le domaine. En conséquence de ce paramètre, le défaut n'accepte pas le caractère « @ » dans les noms courts (car il est autorisé dans les noms de groupes Windows). Si un utilisateur souhaite utiliser des noms courts avec « @ », il doit créer son propre re_expression.

full_name_format (string)

Un format compatible avec printf(3) qui décrit comment composer un nom pleinement qualifié à partir des composants nom d'utilisateur et nom de domaine.

Les expansions suivantes sont prises en charge :

%1$s

nom d'utilisateur

%2$s

nom de domaine tel que spécifié dans le fichier de configuration SSSD.

%3$s

nom plat du domaine. Principalement utilisable pour les domaines Active Directory, qu'ils soient configurés directement ou découverts via des trusts IPA.

Par défaut : “%1$s@%2$s”.

lookup_family_order (string)

Permet de sélectionner la famille d'adresses préférée à utiliser lors des recherches DNS.

Valeurs prises en charge :

ipv4_first : Tente de rechercher une adresse IPv4, si cela échoue, tente IPv6

ipv4_only : Ne tente de résoudre les noms d'hôte qu'en adresses IPv4.

ipv6_first : Tente de rechercher une adresse IPv6, si cela échoue, tente IPv4

ipv6_only : Ne tente de résoudre les noms d'hôte qu'en adresses IPv6.

Par défaut : ipv4_first

Spécifie le temps en secondes depuis la dernière authentification en ligne réussie pendant lequel l'utilisateur sera authentifié à l'aide d'identifiants mis en cache pendant que SSSD est en mode en ligne. Si les identifiants sont incorrects, SSSD revient à l'authentification en ligne.

local_auth_policy (string)

Politique des méthodes d'authentification locales. Certains backends (c'est-à-dire LDAP, fournisseur proxy) ne prennent en charge qu'une authentification basée sur mot de passe, tandis que d'autres peuvent gérer l'authentification par carte à puce basée sur PKINIT (AD, IPA), l'authentification à deux facteurs (IPA) ou d'autres méthodes contre une instance centrale. Par défaut, dans de tels cas, l'authentification n'est effectuée qu'avec les méthodes prises en charge par le backend. Avec cette option, des méthodes supplémentaires peuvent être activées, qui sont évaluées et vérifiées localement.

Il existe trois valeurs possibles pour cette option : match, only, enable. « match » est utilisé pour faire correspondre les états hors ligne et en ligne pour les méthodes Kerberos. « only » ignore les méthodes en ligne et ne propose que les méthodes locales. enable permet de définir explicitement les méthodes d'authentification locale. Par exemple, « enable:passkey », n'active que le passkey pour l'authentification locale. Plusieurs valeurs enable doivent être séparées par des virgules, telles que « enable:passkey, enable:smartcard »

Le tableau suivant montre quelles méthodes d'authentification, si elles sont correctement configurées, sont actuellement activées ou désactivées pour chaque backend, avec la politique d'authentification locale par défaut : « match »

local_auth_policy = match (par défaut)
  Passkey Carte à puce
IPA activé activé
AD désactivé activé
LDAP désactivé désactivé

Veuillez noter que si l'authentification locale par carte à puce est activée et qu'une carte à puce est présente, l'authentification par carte à puce sera préférée aux méthodes d'authentification prises en charge par le backend. C'est-à-dire qu'il y aura une invite de code PIN au lieu, par exemple, d'une invite de mot de passe.

L'exemple de configuration suivant permet aux utilisateurs locaux de s'authentifier localement en utilisant toute méthode activée (c'est-à-dire carte à puce, passkey).

[domain/shadowutils]
id_provider = proxy
proxy_lib_name = files
auth_provider = none
local_auth_policy = only

Par défaut : match

auto_private_groups (string)

Cette option accepte l'une des trois valeurs disponibles :

true

Crée le groupe privé de l'utilisateur de manière inconditionnelle à partir du numéro UID de l'utilisateur. Le numéro GID est ignoré dans ce cas.

REMARQUE : comme le numéro GID et le groupe privé de l'utilisateur sont déduits du numéro UID, il n'est pas possible d'avoir plusieurs entrées avec le même numéro UID ou GID avec cette option. En d'autres termes, l'activation de cette option impose l'unicité dans l'espace d'identification.

false

Utilise toujours le numéro GID principal de l'utilisateur. Le numéro GID doit faire référence à un objet groupe dans la base de données LDAP.

hybrid

Un groupe principal est auto-généré pour les entrées utilisateur dont les numéros UID et GID ont la même valeur et où le numéro GID ne correspond pas à un objet groupe réel dans LDAP. Si les valeurs sont identiques, mais que le GID principal de l'entrée utilisateur est également utilisé par un objet groupe, le GID principal de l'utilisateur fait référence à cet objet groupe.

Si l'UID et le GID d'un utilisateur sont différents, alors le GID doit correspondre à une entrée de groupe, sinon le GID n'est tout simplement pas résoluble.

Cette fonctionnalité est utile pour les environnements qui souhaitent cesser de maintenir des objets groupe distincts pour les groupes privés des utilisateurs, mais qui souhaitent également conserver les groupes privés existants des utilisateurs.

Pour les fournisseurs d'identité basés sur LDAP (LDAP, IPA et AD), la valeur par défaut pour le domaine configuré est généralement False car les sources ont le concept de groupe principal. Le fournisseur d'identité IdP utilise True car les IdP n'ont généralement pas de groupes principaux.

Pour les sous-domaines, la valeur par défaut est False pour les sous-domaines qui utilisent des identifiants POSIX assignés et True pour les sous-domaines qui utilisent le mappage d'identifiants automatique.

La valeur de auto_private_groups peut être définie par sous-domaine dans une sous-section, par exemple :

[domain/forest.domain/sub.domain]
auto_private_groups = false

ou globalement pour tous les sous-domaines dans la section de domaine principale à l'aide de l'option subdomain_inherit :

[domain/forest.domain]
subdomain_inherit = auto_private_groups
auto_private_groups = false

proxy_lib_name (string)

Le nom de la bibliothèque NSS à utiliser dans les domaines proxy. Les fonctions NSS recherchées dans la bibliothèque sont sous la forme _nss_$(libName)_$(function), par exemple _nss_files_getpwent.

Le nom de la bibliothèque NSS à utiliser pour la recherche d'hôtes et de réseaux dans les domaines proxy. Les fonctions NSS recherchées dans la bibliothèque sont sous la forme _nss_$(libName)_$(function), par exemple _nss_dns_gethostbyname2_r.

proxy_fast_alias (boolean)

Lorsqu'un utilisateur ou un groupe est recherché par nom dans le fournisseur proxy, une deuxième recherche par ID est effectuée pour « canonicaliser » le nom au cas où le nom demandé serait un alias. Cette option spécifie le nombre d'enfants proxy pré-forkés. Elle est utile pour les environnements SSSD à forte charge où sssd pourrait manquer d'emplacements d'enfants disponibles, ce qui entraînerait certains problèmes en raison de la mise en file d'attente des requêtes.

Domaines d'application

SSSD, avec son interface D-Bus (voir sssd-ifp(5)) est attrayant pour les applications en tant que passerelle vers un annuaire LDAP où les utilisateurs et les groupes sont stockés. Cependant, contrairement au déploiement SSSD traditionnel où tous les utilisateurs et groupes ont des attributs POSIX ou ces attributs peuvent être déduits des identifiants SID Windows, dans de nombreux cas, les utilisateurs et les groupes dans le scénario de support d'application n'ont pas d'attributs POSIX. Au lieu de définir une section « [domain/NAME] », l'administrateur peut configurer une section « [application/NAME] » qui représente en interne un domaine de type « application » héritant éventuellement des paramètres d'un domaine SSSD traditionnel.

Veuillez noter que le domaine d'application doit toujours être explicitement activé dans le paramètre « domains » afin que l'ordre de recherche entre le domaine d'application et son domaine frère POSIX soit correctement défini.

Paramètres du domaine d'application

inherit_from (string)

Le domaine SSSD de type POSIX dont le domaine d'application hérite de tous les paramètres. Le domaine d'application peut en outre ajouter ses propres paramètres aux paramètres de l'application qui augmentent ou remplacent les paramètres du domaine « frère ».

Par défaut : non défini

L'exemple suivant illustre l'utilisation d'un domaine d'application. Dans cette configuration, le domaine POSIX est connecté à un serveur LDAP et est utilisé par le système d'exploitation via le répondeur NSS. De plus, le domaine d'application demande également l'attribut telephoneNumber, le stocke sous le nom d'attribut phone dans le cache et rend l'attribut phone accessible via l'interface D-Bus.

[sssd]
domains = appdom, posixdom
[ifp]
user_attributes = +phone
[domain/posixdom]
id_provider = ldap
ldap_uri = ldap://ldap.example.com
ldap_search_base = dc=example,dc=com
[application/appdom]
inherit_from = posixdom
ldap_user_extra_attrs = phone:telephoneNumber

SECTION DE MAPPAGE DES CERTIFICATS

Pour permettre l'authentification avec des cartes à puce et des certificats, SSSD doit être capable de mapper les certificats aux utilisateurs. Cela peut être fait en ajoutant le certificat complet à l'objet LDAP de l'utilisateur ou à un remplacement local. Bien que l'utilisation du certificat complet soit requise pour utiliser la fonctionnalité d'authentification par carte à puce de SSH (voir sss_ssh_authorizedkeys(8) pour les détails), cela peut être fastidieux ou même impossible dans le cas général où les services locaux utilisent PAM pour l'authentification.

Pour rendre le mappage plus flexible, des règles de mappage et de correspondance ont été ajoutées à SSSD (voir sss-certmap(5) pour les détails).

Une règle de mappage et de correspondance peut être ajoutée à la configuration de SSSD dans sa propre section avec un nom tel que “[certmap/NOM_DU_DOMAINE/NOM_DE_LA_REGLE]”. Dans cette section, les options suivantes sont autorisées :

matchrule (string)

Seuls les certificats de la carte à puce qui correspondent à cette règle seront traités, tous les autres seront ignorés.

Par défaut : KRB5:<EKU>clientAuth, c'est-à-dire seuls les certificats ayant l'usage de clé étendu « clientAuth ».

maprule (string)

Définit comment l'utilisateur est trouvé pour un certificat donné.

Par défaut :

•LDAP:(userCertificate;binary={cert!bin}) pour les fournisseurs basés sur LDAP tels que « ldap », « AD » ou « ipa ».
•Si maprule n'est pas défini et que le fournisseur est « proxy », le nom RULE_NAME est supposé être le nom de l'utilisateur correspondant.

domains (string)

Liste des noms de domaines séparés par des virgules à laquelle la règle doit s'appliquer. Par défaut, une règle n'est valide que dans le domaine configuré dans sssd.conf. Si le fournisseur prend en charge les sous-domaines, cette option peut être utilisée pour ajouter la règle aux sous-domaines également.

Par défaut : le domaine configuré dans sssd.conf

priority (integer)

Valeur entière non signée définissant la priorité de la règle. Plus le nombre est élevé, plus la priorité est basse. « 0 » représente la priorité la plus élevée, tandis que « 4294967295 » est la plus basse.

Par défaut : la priorité la plus basse

SECTION DE CONFIGURATION DES INVITES

Si un fichier spécial (/var/lib/sss/pubconf/pam_preauth_available) existe, le module PAM pam_sss de SSSD demandera à SSSD de déterminer quelles méthodes d'authentification sont disponibles pour l'utilisateur qui tente de se connecter. En fonction des résultats, pam_sss invitera l'utilisateur à fournir les identifiants appropriés.

Avec le nombre croissant de méthodes d'authentification et la possibilité qu'il y en ait plusieurs pour un seul utilisateur, l'heuristique utilisée par pam_sss pour sélectionner l'invite peut ne pas convenir à tous les cas d'utilisation. Les options suivantes devraient offrir une meilleure flexibilité ici.

Chaque méthode d'authentification prise en charge a sa propre sous-section de configuration sous « [prompting/...] ». Actuellement, il y a :

[prompting/password]

pour configurer l'invite de mot de passe, les options autorisées sont :

password_prompt

pour changer la chaîne de l'invite de mot de passe

[prompting/2fa]

pour configurer l'invite d'authentification à deux facteurs, les options autorisées sont :

first_prompt

pour changer la chaîne de l'invite pour le premier facteur

second_prompt

pour changer la chaîne de l'invite pour le second facteur

single_prompt

valeur booléenne, si True, il n'y aura qu'une seule invite utilisant la valeur de first_prompt où il est attendu que les deux facteurs soient entrés comme une seule chaîne. Veuillez noter que les deux facteurs doivent être saisis ici, même si le second facteur est facultatif.

Si le second facteur est facultatif et qu'il doit être possible de se connecter soit uniquement avec le mot de passe, soit avec les deux facteurs, l'invite en deux étapes doit être utilisée.

Certains clients, tels que SSH avec 'PasswordAuthentication yes', génèrent leurs propres invites et n'utilisent pas les invites fournies par SSSD ou d'autres modules PAM. De plus, pour SSH avec PasswordAuthentication, si l'authentification à deux facteurs est disponible, SSSD s'attend à ce que les identifiants entrés par l'utilisateur à l'invite de mot de passe SSH soient toujours les deux facteurs sous forme d'une seule chaîne, même si l'authentification à deux facteurs est facultative.

[prompting/passkey]

pour configurer l'invite d'authentification par clé d'accès, les options autorisées sont :

interactive

valeur booléenne, si True, afficher un message et attendre avant de tester la présence d'un périphérique de clé d'accès. Recommandé si votre appareil n'a pas de déclencheur tactile.

interactive_prompt

pour changer le message de l'invite interactive.

touch

valeur booléenne, si True, afficher un message pour rappeler à l'utilisateur de toucher l'appareil.

touch_prompt

pour changer le message de l'invite de contact.

Il est possible d'ajouter une sous-section pour des services PAM spécifiques, par exemple « [prompting/password/sshd] » pour modifier individuellement l'invite pour ce service.
