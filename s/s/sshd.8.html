SSHD(8) Manuel du gestionnaire système SSHD(8)

NOM

sshd — démon OpenSSH

SYNTAXE

sshd [-46DdeGiqTtV] [-C spécification_connexion] [-c fichier_certificat_hote] [-E fichier_journal] [-f fichier_config] [-g temps_grace_connexion] [-h fichier_cle_hote] [-o option] [-p port] [-u len]

DESCRIPTION

sshd (Démon OpenSSH) est le programme démon pour ssh(1). Il fournit des communications cryptées sécurisées entre deux hôtes non fiables sur un réseau non sécurisé.

sshd écoute les connexions des clients. Il est normalement démarré au démarrage depuis /etc/rc. Il crée un nouveau démon pour chaque connexion entrante. Les démons créés gèrent l'échange de clés, le cryptage, l'authentification, l'exécution de commandes et l'échange de données.

sshd peut être configuré à l'aide d'options en ligne de commande ou d'un fichier de configuration (par défaut sshd_config(5)) ; les options en ligne de commande remplacent les valeurs spécifiées dans le fichier de configuration. sshd relit son fichier de configuration lorsqu'il reçoit un signal de suspension, SIGHUP, en s'exécutant lui-même avec le nom et les options avec lesquels il a été démarré, par exemple /usr/sbin/sshd.

Les options sont les suivantes :

-4
Force sshd à n'utiliser que les adresses IPv4.
-6
Force sshd à n'utiliser que les adresses IPv6.
-C spécification_connexion
Spécifie les paramètres de connexion à utiliser pour le mode de test étendu -T. Si fourni, les directives Match dans le fichier de configuration qui s'appliqueraient sont appliquées avant que la configuration ne soit écrite sur la sortie standard. Les paramètres de connexion sont fournis sous forme de paires mot-clé=valeur et peuvent être fournis dans n'importe quel ordre, soit avec plusieurs options -C, soit sous forme de liste séparée par des virgules. Les mots-clés sont « addr », « user », « host », « laddr », « lport », et « rdomain » et correspondent respectivement à l'adresse source, l'utilisateur, le nom d'hôte source résolu, l'adresse locale, le numéro de port local et le domaine de routage. De plus, l'indicateur « invalid-user » (qui ne prend pas d'argument de valeur) peut être spécifié pour simuler une connexion à partir d'un nom d'utilisateur non reconnu.
-c fichier_certificat_hote
Spécifie un chemin vers un fichier de certificat pour identifier sshd pendant l'échange de clés. Le fichier de certificat doit correspondre à un fichier de clé d'hôte spécifié à l'aide de l'option -h ou de la directive de configuration HostKey.
-D
Lorsque cette option est spécifiée, sshd ne se détache pas et ne devient pas un démon. Cela permet une surveillance facile de sshd.
-d
Mode débogage. Le serveur envoie une sortie de débogage détaillée à la sortie d'erreur standard et ne se met pas en arrière-plan. Le serveur ne fork(2) pas non plus et ne traite qu'une seule connexion. Cette option est uniquement destinée au débogage du serveur. Plusieurs options -d augmentent le niveau de débogage. Le maximum est de 3.
-E fichier_journal
Ajoute les journaux de débogage au fichier fichier_journal au lieu du journal système.
-e
Écrit les journaux de débogage sur la sortie d'erreur standard au lieu du journal système.
-f fichier_config
Spécifie le nom du fichier de configuration. Le défaut est /etc/ssh/sshd_config. sshd refuse de démarrer s'il n'y a pas de fichier de configuration.
-G
Analyse et affiche le fichier de configuration. Vérifie la validité du fichier de configuration, affiche la configuration effective sur la sortie standard, puis quitte. Optionnellement, les règles Match peuvent être appliquées en spécifiant les paramètres de connexion à l'aide d'une ou plusieurs options -C.
-g temps_grace_connexion
Donne le temps de grâce pour que les clients s'authentifient (120 secondes par défaut). Si le client ne parvient pas à authentifier l'utilisateur dans ce nombre de secondes, le serveur déconnecte et quitte. Une valeur de zéro indique aucune limite.
-h fichier_cle_hote
Spécifie un fichier à partir duquel une clé d'hôte est lue. Cette option doit être donnée si sshd n'est pas exécuté en tant que root (car les fichiers de clés d'hôte normaux ne sont normalement lisibles que par root). Le défaut est /etc/ssh/ssh_host_ecdsa_key, /etc/ssh/ssh_host_ed25519_key et /etc/ssh/ssh_host_rsa_key. Il est possible d'avoir plusieurs fichiers de clés d'hôte pour différents algorithmes de clés d'hôte.
-i
Spécifie que sshd est exécuté à partir de inetd(8).
-o option
Peut être utilisé pour fournir des options dans le format utilisé dans le fichier de configuration. Ceci est utile pour spécifier des options pour lesquelles il n'y a pas d'option de ligne de commande distincte. Pour plus de détails sur les options et leurs valeurs, voir sshd_config(5).
-p port
Spécifie le port sur lequel le serveur écoute les connexions (port par défaut 22). Plusieurs options de port sont permises. Les ports spécifiés dans le fichier de configuration avec l'option Port sont ignorés lorsqu'un port en ligne de commande est spécifié. Les ports spécifiés à l'aide de l'option ListenAddress remplacent les ports en ligne de commande.
-q
Mode silencieux. Rien n'est envoyé au journal système. Normalement, le début, l'authentification et la fin de chaque connexion sont enregistrés.
-T
Mode de test étendu. Vérifie la validité du fichier de configuration, affiche la configuration effective sur la sortie standard, puis quitte. Optionnellement, les règles Match peuvent être appliquées en spécifiant les paramètres de connexion à l'aide d'une ou plusieurs options -C. Ceci est similaire à l'option -G, mais inclut les tests supplémentaires effectués par l'option -t.
-t
Mode test. Vérifie uniquement la validité du fichier de configuration et la cohérence des clés. Ceci est utile pour mettre à jour sshd de manière fiable car les options de configuration peuvent changer.
-u len
Cette option est utilisée pour spécifier la taille du champ dans la structure utmp qui contient le nom d'hôte distant. Si le nom d'hôte résolu est plus long que len, le format en points

La spécification de -u0 indique que seules les adresses décimales pointées doivent être insérées dans le fichier utmp. La valeur -u0 peut également être utilisée pour empêcher sshd d'effectuer des requêtes DNS à moins que le mécanisme d'authentification ou la configuration ne l'exigent. Les mécanismes d'authentification qui peuvent nécessiter DNS incluent HostbasedAuthentication et l'utilisation d'une option from="pattern-list" dans un fichier de clés. Affiche le numéro de version et quitte.

AUTHENTIFICATION

Le démon SSH OpenSSH prend en charge le protocole SSH 2 uniquement. Chaque hôte possède une clé spécifique à l'hôte, utilisée pour l'identifier. Chaque fois qu'un client se connecte, le démon répond avec sa clé d'hôte publique. Le client compare la clé d'hôte à sa propre base de données pour vérifier qu'elle n'a pas changé. La confidentialité persistante est assurée par un accord de clé Diffie-Hellman. Cet accord de clé aboutit à une clé de session partagée. Le reste de la session est chiffré à l'aide d'un algorithme de chiffrement symétrique. Le client sélectionne l'algorithme de chiffrement à utiliser parmi ceux proposés par le serveur. De plus, l'intégrité de la session est assurée par un code d'authentification de message cryptographique (MAC).

Enfin, le serveur et le client entrent dans un dialogue d'authentification. Le client tente de s'authentifier à l'aide de l'authentification basée sur l'hôte, de l'authentification par clé publique, de l'authentification par défi-réponse ou de l'authentification par mot de passe.

Indépendamment du type d'authentification, le compte est vérifié pour s'assurer qu'il est accessible. Un compte n'est pas accessible s'il est verrouillé, répertorié dans DenyUsers ou si son groupe est répertorié dans DenyGroups. La définition d'un compte verrouillé dépend du système. Certaines plateformes ont leur propre base de données de comptes (par exemple, AIX) et d'autres modifient le champ passwd ( ‘*LK*’ sur Solaris et UnixWare, ‘*’ sur HP-UX, contenant ‘Nologin’ sur Tru64, un ‘*LOCKED*’ préfixé sur FreeBSD et un ‘!’ préfixé sur la plupart des distributions Linux). S'il est nécessaire de désactiver l'authentification par mot de passe pour le compte tout en autorisant toujours la clé publique, le champ passwd doit être défini sur autre chose que ces valeurs (par exemple, ‘NP’ ou ‘*NP*’ ).

Si le client s'authentifie avec succès, un dialogue de préparation de la session est initié. À ce stade, le client peut demander des choses comme l'allocation d'un pseudo-tty, le transfert des connexions X11, le transfert des connexions TCP ou le transfert de la connexion de l'agent d'authentification via le canal sécurisé.

Après cela, le client demande soit un shell interactif, soit l'exécution d'une commande non interactive, que sshd exécutera via le shell de l'utilisateur en utilisant son option -c. Les deux parties entrent alors en mode session. Dans ce mode, l'une ou l'autre partie peut envoyer des données à tout moment, et ces données sont transférées vers/depuis le shell ou la commande côté serveur, et le terminal utilisateur côté client.

Lorsque le programme utilisateur se termine et que toutes les connexions X11 et autres connexions transférées ont été fermées, le serveur envoie le statut de sortie de la commande au client, et les deux parties se terminent.

PROCESSUS DE CONNEXION

Lorsqu'un utilisateur se connecte avec succès, sshd effectue les actions suivantes :

  1. Si la connexion se fait sur un tty et qu'aucune commande n'a été spécifiée, affiche la dernière heure de connexion et le fichier /etc/motd (sauf si cela est empêché dans le fichier de configuration ou par le fichier ~/.hushlogin ; voir la section FICHIERS).
  2. Si la connexion se fait sur un tty, enregistre l'heure de connexion.
  3. Vérifie le fichier /etc/nologin ; s'il existe, affiche son contenu et quitte (sauf pour l'utilisateur root).
  4. Passe en mode d'exécution avec les privilèges utilisateur normaux.
  5. Configure l'environnement de base.
  6. Lit le fichier ~/.ssh/environment, s'il existe, et si les utilisateurs sont autorisés à modifier leur environnement. Voir l'option PermitUserEnvironment dans sshd_config(5).
  7. Change pour le répertoire personnel de l'utilisateur.
  8. Si le fichier ~/.ssh/rc existe et que l'option PermitUserRC de sshd_config(5) est définie, l'exécute ; sinon, si le fichier /etc/ssh/sshrc existe, l'exécute ; sinon, exécute xauth(1). Les fichiers « rc » reçoivent le protocole d'authentification X11 et le cookie sur l'entrée standard. Voir SSHRC, ci-dessous.
  9. Exécute le shell ou la commande de l'utilisateur. Toutes les commandes sont exécutées sous le shell de connexion de l'utilisateur tel que spécifié dans la base de données des mots de passe du système.

SSHRC

Si le fichier ~/.ssh/rc existe, sh(1) l'exécute après avoir lu les fichiers d'environnement mais avant de démarrer le shell ou la commande de l'utilisateur. Il ne doit produire aucune sortie sur stdout ; stderr doit être utilisé à la place. Si le transfert X11 est utilisé, il recevra la paire « proto cookie » sur son entrée standard (et DISPLAY dans son environnement). Le script doit appeler xauth(1) car sshd n'exécutera pas xauth automatiquement pour ajouter les cookies X11.

Le but principal de ce fichier est d'exécuter les routines d'initialisation qui peuvent être nécessaires avant que le répertoire personnel de l'utilisateur ne devienne accessible ; AFS est un exemple particulier d'un tel environnement.

Ce fichier contiendra probablement un code d'initialisation suivi de quelque chose de similaire à :

if read proto cookie && [ -n "$DISPLAY" ]; then
	if [ `echo $DISPLAY | cut -c1-10` = 'localhost:' ]; then
		# X11UseLocalhost=yes
		echo add unix:`echo $DISPLAY |
		    cut -c11-` $proto $cookie
	else
		# X11UseLocalhost=no
		echo add $DISPLAY $proto $cookie
	fi | xauth -q -
fi

Si ce fichier n'existe pas, /etc/ssh/sshrc est exécuté, et s'il n'existe pas non plus, xauth est utilisé pour ajouter le cookie.

FORMAT DU FICHIER AUTHORIZED_KEYS

AuthorizedKeysFile spécifie les fichiers contenant les clés publiques pour l'authentification par clé publique ; si cette option n'est pas spécifiée, les valeurs par défaut sont ~/.ssh/authorized_keys et ~/.ssh/authorized_keys2. Chaque ligne du fichier contient une clé (les lignes vides et les lignes commençant par un ‘#’ sont ignorées comme commentaires). Les clés publiques se composent des champs séparés par des espaces suivants : options, type de clé, clé encodée en base64, commentaire. Le champ options est facultatif. Les types de clés pris en charge sont :

  • sk-ecdsa-sha2-nistp256@openssh.com
  • ecdsa-sha2-nistp256
  • ecdsa-sha2-nistp384
  • ecdsa-sha2-nistp521
  • sk-ssh-ed25519@openssh.com
  • ssh-ed25519
  • ssh-rsa

Le champ commentaire n'est pas utilisé (mais peut être pratique pour l'utilisateur afin d'identifier la clé).

Notez que les lignes de ce fichier peuvent avoir plusieurs centaines d'octets de long (en raison de la taille de l'encodage de la clé publique) jusqu'à une limite de 8 kilo-octets, ce qui permet des clés RSA allant jusqu'à 16 kilobits. Vous ne voudrez pas les taper ; copiez plutôt le fichier id_ecdsa.pub, id_ecdsa_sk.pub, id_ed25519.pub, id_ed25519_sk.pub, ou le fichier id_rsa.pub et modifiez-le.

sshd applique une taille de module minimale de 1024 bits pour les clés RSA.

Les options (si présentes) se composent de spécifications d'options séparées par des virgules. Aucun espace n'est autorisé, sauf entre guillemets doubles. Les spécifications d'options suivantes sont prises en charge (notez que les mots-clés des options ne sont pas sensibles à la casse) :

agent-forwarding
Active le transfert de l'agent d'authentification précédemment désactivé par l'option restrict.
cert-authority
Spécifie que la clé répertoriée est une autorité de certification (CA) qui est approuvée pour valider les certificats signés pour l'authentification utilisateur.

Les certificats peuvent encoder des restrictions d'accès similaires à ces options de clé. Si des restrictions de certificat et des options de clé sont présentes, l'union la plus restrictive des deux est appliquée.

command="commande"
Spécifie que la commande est exécutée chaque fois que cette clé est utilisée pour l'authentification. La commande fournie par l'utilisateur (le cas échéant) est ignorée. La commande est exécutée sur un pty si le client demande un pty ; sinon, elle est exécutée sans tty. Si un canal 8 bits propre est requis, il ne faut pas demander un pty ou spécifier no-pty. Un guillemet peut être inclus dans la commande en le citant avec une barre oblique inverse.

Cette option peut être utile pour restreindre certaines clés publiques à n'effectuer qu'une opération spécifique. Un exemple pourrait être une clé qui autorise les sauvegardes à distance mais rien d'autre. Notez que le client peut spécifier le transfert TCP et/ou X11 à moins qu'ils ne soient explicitement interdits, par exemple en utilisant l'option de clé restrict.

La commande fournie initialement par le client est disponible dans la variable d'environnement SSH_ORIGINAL_COMMAND. Notez que cette option s'applique à l'exécution du shell, de la commande ou du sous-système. Notez également que cette commande peut être remplacée par une directive ForceCommand de sshd_config(5).

Si une commande est spécifiée et qu'une commande forcée est intégrée dans un certificat utilisé pour l'authentification, alors le certificat sera accepté uniquement si les deux commandes sont identiques.

environment="NAME=value"
Spécifie que la chaîne doit être ajoutée à l'environnement lors de la connexion avec cette clé. Les variables d'environnement ainsi définies remplacent les autres valeurs par défaut de l'environnement. Plusieurs options de ce type sont autorisées. Le traitement de l'environnement est désactivé par défaut et est contrôlé par l'option PermitUserEnvironment.
expiry-time="timespec"
Spécifie une date après laquelle la clé ne sera plus acceptée. L'heure peut être spécifiée sous forme de date YYYYMMDD[Z] ou d'heure YYYYMMDDHHMM[SS][Z]. Les dates et heures seront interprétées dans le fuseau horaire du système, sauf si elles sont suffixées par un caractère Z, auquel cas elles seront interprétées dans le fuseau horaire UTC.
from="pattern-list"
Spécifie qu'en plus de l'authentification par clé publique, le nom canonique de l'hôte distant ou son adresse IP doit figurer dans la liste de motifs séparés par des virgules. Voir PATTERNS dans ssh_config(5) pour plus d'informations sur les motifs.

En plus de la correspondance de caractères génériques qui peut être appliquée aux noms d'hôtes ou aux adresses, une section from peut correspondre à des adresses IP en utilisant la notation CIDR adresse/masque.

Le but de cette option est d'augmenter éventuellement la sécurité : l'authentification par clé publique en soi ne fait pas confiance au réseau, aux serveurs de noms ou à quoi que ce soit (sauf la clé) ; cependant, si quelqu'un vole la clé, celle-ci permet à un intrus de se connecter de n'importe où dans le monde. Cette option supplémentaire rend l'utilisation d'une clé volée plus difficile (les serveurs de noms et/ou les routeurs devraient être compromis en plus de la clé).

no-agent-forwarding
Interdit le transfert de l'agent d'authentification lorsque cette clé est utilisée pour l'authentification.
no-port-forwarding
Interdit le transfert de port TCP lorsque cette clé est utilisée pour l'authentification. Toute demande de transfert de port par le client retournera une erreur. Cela pourrait être utilisé, par exemple, en conjonction avec l'option command.
no-pty
Empêche l'allocation d'un tty (une demande d'allocation de pty échouera).
no-user-rc
Désactive l'exécution de ~/.ssh/rc.
no-X11-forwarding
Interdit le transfert X11 lorsque cette clé est utilisée pour l'authentification. Toute demande de transfert X11 par le client retournera une erreur.
permitlisten="[host:]port"
Limite le transfert de port distant avec l'option ssh(1) -R afin qu'il ne puisse écouter que sur l'hôte (facultatif) et le port spécifiés. Les adresses IPv6 peuvent être spécifiées en plaçant l'adresse entre crochets. Plusieurs options permitlisten peuvent être appliquées, séparées par des virgules. Les noms d'hôtes peuvent inclure des caractères génériques comme décrit dans la section PATTERNS de ssh_config(5). Une spécification de port de * correspond à n'importe quel port. Notez que le réglage de GatewayPorts peut restreindre davantage les adresses d'écoute. Notez que ssh(1) enverra le nom d'hôte “localhost” si aucun hôte d'écoute n'a été spécifié lors de la demande de transfert, et que ce nom est traité différemment des adresses localhost explicites “127.0.0.1” et “::1”.
permitopen="host:port"
Limite le transfert de port local avec l'option ssh(1) -L afin qu'il ne puisse se connecter qu'à l'hôte et au port spécifiés. Les adresses IPv6 peuvent être spécifiées en plaçant l'adresse entre crochets. Plusieurs options permitopen peuvent être appliquées, séparées par des virgules. Aucune correspondance de motif ou recherche de nom n'est effectuée sur les noms d'hôtes spécifiés, ce doivent être des noms d'hôtes et/ou adresses littéraux. Une spécification de port de * correspond à n'importe quel port.
port-forwarding
Active le transfert de port précédemment désactivé par l'option restrict.
principals="principals"
Sur une ligne cert-authority, spécifie les principaux autorisés pour l'authentification par certificat sous forme de liste séparée par des virgules. Au moins un nom de la liste doit figurer dans la liste des principaux du certificat pour que celui-ci soit accepté. Cette option est ignorée pour les clés qui ne sont pas marquées comme signataires de certificats approuvés à l'aide de l'option cert-authority.
pty
Autorise l'allocation de tty précédemment désactivée par l'option restrict.
no-touch-required
Ne pas exiger la démonstration de présence utilisateur pour les signatures effectuées avec cette clé. Cette option n'a de sens que pour les algorithmes d'authentification FIDO ecdsa-sk et ed25519-sk.
verify-required
Exiger que les signatures faites avec cette clé attestent qu'elles ont vérifié l'utilisateur, par exemple via un PIN. Cette option n'a de sens que pour les algorithmes d'authentification FIDO ecdsa-sk et ed25519-sk.
restrict
Active toutes les restrictions, c'est-à-dire désactive le transfert de port, d'agent et X11, ainsi que la désactivation de l'allocation PTY et de l'exécution de ~/.ssh/rc. Si de futures capacités de restriction sont ajoutées aux fichiers authorized_keys, elles seront incluses dans cet ensemble.
tunnel="n"
Force un périphérique tun(4) sur le serveur. Sans cette option, le prochain périphérique disponible sera utilisé si le client demande un tunnel.
user-rc
Active l'exécution de ~/.ssh/rc précédemment désactivée par l'option restrict.
X11-forwarding
Autorise le transfert X11 précédemment désactivé par l'option restrict.

Un exemple de fichier authorized_keys :

# Les commentaires sont autorisés en début de ligne. Les lignes vides sont autorisées.
# Clé simple, sans restrictions
ssh-rsa ...
# Commande forcée, désactiver PTY et tout transfert
restrict,command="dump /home" ssh-rsa ...
# Restriction des destinations de transfert ssh -L
permitopen="192.0.2.1:80",permitopen="192.0.2.2:25" ssh-rsa ...
# Restriction des écoutes de transfert ssh -R
permitlisten="localhost:8080",permitlisten="[::1]:22000" ssh-rsa ...
# Configuration pour le transfert tunnel
tunnel="0",command="sh /etc/netstart tun0" ssh-rsa ...
# Substitution de la restriction pour autoriser l'allocation PTY
restrict,pty,command="nethack" ssh-rsa ...
# Autoriser la clé FIDO sans exiger de toucher
no-touch-required sk-ecdsa-sha2-nistp256@openssh.com ...
# Exiger la vérification utilisateur (par ex. PIN ou biométrie) pour la clé FIDO
verify-required sk-ecdsa-sha2-nistp256@openssh.com ...
# Faire confiance à la clé CA, autoriser FIDO sans toucher si demandé dans le certificat
cert-authority,no-touch-required,principals="user_a" ssh-rsa ...

FORMAT DU FICHIER SSH_KNOWN_HOSTS

Les fichiers /etc/ssh/ssh_known_hosts et ~/.ssh/known_hosts contiennent les clés publiques des hôtes pour tous les hôtes connus. Le fichier global doit être préparé par l'administrateur (facultatif), et le fichier par utilisateur est maintenu automatiquement : chaque fois que l'utilisateur se connecte à un hôte inconnu, sa clé est ajoutée au fichier par utilisateur.

Chaque ligne de ces fichiers contient les champs suivants : marqueur (facultatif), noms d'hôtes, type de clé, clé encodée en base64, commentaire. Les champs sont séparés par des espaces.

Le marqueur est facultatif, mais s'il est présent, il doit être l'un des suivants : “@cert-authority”, pour indiquer que la ligne contient une clé d'autorité de certification (CA), ou “@revoked”, pour indiquer que la clé contenue sur la ligne est révoquée et ne doit jamais être acceptée. Un seul marqueur doit être utilisé sur une ligne de clé.

Les noms d'hôtes sont une liste de motifs séparés par des virgules (‘*’ et ‘?’ agissent comme des caractères génériques) ; chaque motif est ensuite comparé au nom de l'hôte. Lorsque sshd authentifie un client, par exemple lors de l'utilisation de HostbasedAuthentication, ce sera le nom d'hôte canonique du client. Lorsque ssh(1) authentifie un serveur, ce sera le nom d'hôte fourni par l'utilisateur, la valeur de ssh(1) HostkeyAlias s'il a été spécifié, ou le nom d'hôte canonique du serveur si l'option ssh(1) CanonicalizeHostname a été utilisée.

Un motif peut également être précédé de ‘!’ pour indiquer une négation : si le nom d'hôte correspond à un motif nié, il n'est pas accepté (par cette ligne) même s'il correspondait à un autre motif sur la ligne. Un nom d'hôte ou une adresse peut optionnellement être entouré de crochets ‘[’ et ‘]’, puis suivi de ‘:’ et d'un numéro de port non standard.

Alternativement, les noms d'hôtes peuvent être stockés sous une forme hachée qui masque les noms et adresses d'hôtes si le contenu du fichier est divulgué. Les noms d'hôtes hachés commencent par un ‘#’.

OPTIONS DE CONFIGURATION

Le fichier ~/.ssh/known_hosts contient une liste des clés publiques des hôtes auxquels l'utilisateur s'est connecté. Ce fichier est utilisé pour vérifier l'identité des hôtes distants afin d'éviter les attaques de type « man-in-the-middle ».

Chaque ligne du fichier known_hosts représente une clé d'hôte pour un ou plusieurs noms d'hôtes. Le format général est le suivant :

nom(s)-hôte clétype cléencodée-en-base64 [commentaire]

Le champ nom(s)-hôte est une liste de noms d'hôtes séparés par des virgules. Les noms d'hôtes peuvent inclure des noms d'hôtes canoniques, des adresses IP ou des noms de domaine joker (par exemple, *.example.com). Si un nom d'hôte contient un caractère spécial comme « ! », « " », « # », « $ », « ` », « / », « \ », « | » ou « ~ », il doit être échappé avec une barre oblique inverse (« \ »).

Seul un nom d'hôte haché peut apparaître sur une seule ligne, et aucun des opérateurs de négation ou de joker mentionnés ci-dessus ne peut être appliqué.

Les champs clétype et cléencodée-en-base64 sont directement tirés de la clé de l'hôte ; ils peuvent être obtenus, par exemple, à partir de /etc/ssh/ssh_host_rsa_key.pub. Le champ facultatif commentaire se poursuit jusqu'à la fin de la ligne et n'est pas utilisé.

Les lignes commençant par « # » et les lignes vides sont ignorées comme commentaires.

Lors de l'authentification de l'hôte, l'authentification est acceptée si une ligne correspondante contient la clé appropriée ; soit une clé qui correspond exactement, soit, si le serveur a présenté un certificat pour l'authentification, la clé de l'autorité de certification qui a signé le certificat. Pour qu'une clé soit considérée comme une autorité de certification de confiance, elle doit utiliser le marqueur « @cert-authority » décrit ci-dessus.

Le fichier known_hosts fournit également un moyen de marquer les clés comme révoquées, par exemple lorsqu'il est connu que la clé privée associée a été volée. Les clés révoquées sont spécifiées en incluant le marqueur « @revoked » au début de la ligne de la clé, et ne sont jamais acceptées pour l'authentification ou comme autorités de certification, mais généreront plutôt un avertissement de ssh(1) lorsqu'elles seront rencontrées.

Il est permis (mais déconseillé) d'avoir plusieurs lignes ou différentes clés d'hôtes pour les mêmes noms. Cela se produira inévitablement lorsque des formes courtes de noms d'hôtes provenant de différents domaines seront mises dans le fichier. Il est possible que les fichiers contiennent des informations conflictuelles ; l'authentification est acceptée si des informations valides peuvent être trouvées dans l'un ou l'autre fichier.

Notez que les lignes de ces fichiers font généralement des centaines de caractères de long, et vous ne voudrez certainement pas les taper à la main. Préférez générer les clés à l'aide d'un script, de ssh-keyscan(1) ou en prenant, par exemple, /etc/ssh/ssh_host_rsa_key.pub et en ajoutant les noms d'hôtes au début. ssh-keygen(1) propose également une édition automatisée de base pour ~/.ssh/known_hosts, y compris la suppression des hôtes correspondant à un nom d'hôte et la conversion de tous les noms d'hôtes en leurs représentations hachées.

Voici un exemple de fichier ssh_known_hosts :

# Commentaires autorisés en début de ligne
cvs.example.net,192.0.2.10 ssh-rsa AAAA1234.....=
# Un nom d'hôte haché
|1|JfKTdBh7rNbXkVAQCRp4OQoPfmI=|USECr3SWf1JUPsms5AqfD5QfxkM= ssh-rsa
AAAA1234.....=
# Une clé révoquée
@revoked * ssh-rsa AAAAB5W...
# Une clé d'AC, acceptée pour n'importe quel hôte dans *.mydomain.com ou *.mydomain.org
@cert-authority *.mydomain.org,*.mydomain.com ssh-rsa AAAAB5W...

FICHIERS

~/.hushlogin
Ce fichier est utilisé pour supprimer l'affichage de la dernière heure de connexion et de /etc/motd, si PrintLastLog et PrintMotd, respectivement, sont activés. Il ne supprime pas l'affichage de la bannière spécifiée par Banner.
~/.rhosts
Ce fichier est utilisé pour l'authentification basée sur l'hôte (voir ssh(1) pour plus d'informations). Sur certaines machines, ce fichier peut devoir être lisible par tous si le répertoire personnel de l'utilisateur se trouve sur une partition NFS, car sshd le lit en tant que root. De plus, ce fichier doit appartenir à l'utilisateur et ne doit pas avoir de permissions d'écriture pour d'autres. Les permissions recommandées pour la plupart des machines sont lecture/écriture pour l'utilisateur et inaccessibles par les autres.
~/.shosts
Ce fichier est utilisé de la même manière que .rhosts, mais permet l'authentification basée sur l'hôte sans autoriser la connexion avec rlogin/rsh.
~/.ssh/
Ce répertoire est l'emplacement par défaut pour toutes les informations de configuration et d'authentification spécifiques à l'utilisateur. Il n'y a pas d'exigence générale pour garder secret l'intégralité du contenu de ce répertoire, mais les permissions recommandées sont lecture/écriture/exécution pour l'utilisateur, et inaccessibles par les autres.
~/.ssh/authorized_keys
Liste les clés publiques (ECDSA, Ed25519, RSA) qui peuvent être utilisées pour se connecter en tant que cet utilisateur. Le format de ce fichier est décrit ci-dessus. Le contenu du fichier n'est pas très sensible, mais les permissions recommandées sont lecture/écriture pour l'utilisateur, et inaccessibles par les autres.

Si ce fichier, le répertoire ~/.ssh, ou le répertoire personnel de l'utilisateur sont accessibles en écriture par d'autres utilisateurs, alors le fichier pourrait être modifié ou remplacé par des utilisateurs non autorisés. Dans ce cas, sshd ne permettra pas son utilisation à moins que l'option StrictModes n'ait été définie sur « no ».

~/.ssh/environment
Ce fichier est lu dans l'environnement lors de la connexion (s'il existe). Il ne peut contenir que des lignes vides, des lignes de commentaires (qui commencent par « # ») et des lignes d'affectation de la forme nom=valeur. Le fichier doit être accessible en écriture uniquement par l'utilisateur ; il n'a pas besoin d'être lisible par les autres. Le traitement de l'environnement est désactivé par défaut et est contrôlé par l'option PermitUserEnvironment.
~/.ssh/known_hosts
Contient une liste des clés d'hôtes de tous les hôtes auxquels l'utilisateur s'est connecté et qui ne figurent pas déjà dans la liste système des clés d'hôtes connues. Le format de ce fichier est décrit ci-dessus. Ce fichier ne doit être accessible en écriture que par root/le propriétaire et peut être, mais n'a pas besoin d'être, lisible par tous.
~/.ssh/rc
Contient les routines d'initialisation à exécuter avant que le répertoire personnel de l'utilisateur ne devienne accessible. Ce fichier doit être accessible en écriture uniquement par l'utilisateur, et n'a pas besoin d'être lisible par les autres.
/etc/hosts.equiv
Ce fichier est destiné à l'authentification basée sur l'hôte (voir ssh(1)). Il ne doit être accessible en écriture que par root.
/etc/ssh/moduli
Contient les groupes Diffie-Hellman utilisés pour la méthode d'échange de clés « Diffie-Hellman Group Exchange ». Le format du fichier est décrit dans moduli(5). Si aucun groupe utilisable n'est trouvé dans ce fichier, des groupes internes fixes seront utilisés.
/etc/motd
Voir motd(5).
/etc/nologin
Si ce fichier existe, sshd refuse de laisser qui que ce soit d'autre que root se connecter. Le contenu du fichier est affiché à toute personne essayant de se connecter, et les connexions non root sont refusées. Le fichier doit être lisible par tous.
/etc/ssh/shosts.equiv
Ce fichier est utilisé exactement de la même manière que hosts.equiv, mais permet l'authentification basée sur l'hôte sans autoriser la connexion avec rlogin/rsh.
/etc/ssh/ssh_host_ecdsa_key
 
/etc/ssh/ssh_host_ed25519_key
 
/etc/ssh/ssh_host_rsa_key
Ces fichiers contiennent les parties privées des clés d'hôtes. Ces fichiers ne doivent appartenir qu'à root, n'être lisibles que par root, et inaccessibles aux autres. Notez que sshd ne démarre pas si ces fichiers sont accessibles par groupe/monde.
/etc/ssh/ssh_host_ecdsa_key.pub
 
/etc/ssh/ssh_host_ed25519_key.pub
 
/etc/ssh/ssh_host_rsa_key.pub
Ces fichiers contiennent les parties publiques des clés d'hôtes. Ces fichiers doivent être lisibles par tous, mais accessibles en écriture uniquement par root. Leur contenu doit correspondre aux parties privées respectives. Ces fichiers ne sont pas réellement utilisés pour quoi que ce soit ; ils sont fournis pour la commodité de l'utilisateur afin que leur contenu puisse être copié dans les fichiers known hosts. Ces fichiers sont créés à l'aide de ssh-keygen(1).
/etc/ssh/ssh_known_hosts
Liste système des clés d'hôtes connues. Ce fichier doit être préparé par l'administrateur système pour contenir les clés publiques des hôtes de toutes les machines de l'organisation. Le format de ce fichier est décrit ci-dessus. Ce fichier ne doit être accessible en écriture que par root/le propriétaire et doit être lisible par tous.
/etc/ssh/sshd_config
Contient les données de configuration pour sshd. Le format du fichier et les options de configuration sont décrits dans sshd_config(5).
/etc/ssh/sshrc
Similaire à ~/.ssh/rc, il peut être utilisé pour spécifier globalement des initialisations au moment de la connexion spécifiques à la machine. Ce fichier doit être accessible en écriture uniquement par root, et doit être lisible par tous.
/usr/share/empty.sshd
Répertoire chroot(2) utilisé par sshd lors de la séparation des privilèges dans la phase de pré-authentification. Le répertoire ne doit contenir aucun fichier et doit appartenir à root et ne pas être accessible en écriture par groupe ou par monde.
/run/sshd.pid
Contient l'identifiant de processus de sshd en attente de connexions (s'il y a plusieurs démons en cours d'exécution simultanément pour différents ports, celui-ci contient l'identifiant de processus de celui qui a été démarré en dernier). Le contenu de ce fichier n'est pas sensible ; il peut être lisible par tous.
