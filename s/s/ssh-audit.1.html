SSH-AUDIT(1) Manuel des commandes générales SSH-AUDIT(1)

NOM

ssh-audit - Auditeur de configuration de serveur et client SSH

SYNOPSIS

ssh-audit [options] <hôte_cible>

DESCRIPTION

ssh-audit analyse la configuration des serveurs et clients SSH, puis avertit l'utilisateur des primitives cryptographiques faibles, obsolètes et/ou non testées. Il est très utile pour renforcer les tunnels SSH, qui par défaut ont tendance à être optimisés pour la compatibilité, pas pour la sécurité.

Voir https://www.ssh-audit.com/ pour les guides officiels de renforcement pour les plates-formes courantes.

OPTIONS

-h, --help

Imprime un bref résumé des options.
-1, --ssh1

Effectue un audit en utilisant uniquement le protocole SSH version 1.
-2, --ssh2

Effectue un audit en utilisant uniquement le protocole SSH version 2.
-4, --ipv4

Priorise l'utilisation d'IPv4.
-6, --ipv6

Priorise l'utilisation d'IPv6.
-b, --batch

Active la sortie interprétable par grep.
-c, --client-audit

Démarre un serveur sur le port 2222 pour auditer la configuration du logiciel client. Utilisez -p/--port=<port> pour changer de port et -t/--timeout=<secs> pour changer le délai d'attente d'écoute.
--conn-rate-test=N[:max_rate]

Effectue un test de débit de connexion (utile pour collecter des métriques relatives à la susceptibilité à la vulnérabilité DHEat [CVE-2002-20001]). Une connexion réussie est comptée lorsque le serveur renvoie une bannière SSH valide. Les tests sont effectués avec N sockets simultanés avec un débit maximal optionnel de connexions par seconde.
-d, --debug

Active la sortie de débogage.
--dheat=N[:kex[:e_len]]

Exécute l'attaque par déni de service DHEat (CVE-2002-20001) contre le serveur cible (ce qui consommera toutes les ressources CPU disponibles). Le nombre de sockets simultanés, N, nécessaire pour obtenir cet effet dépendra fortement des ressources CPU disponibles sur la cible, ainsi que de la latence entre les machines source et cible. L'échange de clés est choisi automatiquement en fonction de ce qui causera un effet maximal, sauf s'il est explicitement choisi dans le second champ. Enfin, une option (expérimentale) permet de spécifier la longueur en octets de la fausse valeur e envoyée au serveur dans le troisième champ. Normalement, la longueur de e est à peu près la longueur du module de l'échange Diffie-Hellman (donc, une valeur de e de 8192 bits / 1024 octets est envoyée dans chaque connexion lors du ciblage de l'algorithme diffie-hellman-group18-sha512). Au lieu de cela, il a été observé que de nombreuses implémentations SSH acceptent de petites valeurs, comme 4 octets ; cela résulte en une attaque beaucoup plus efficace en termes de réseau.
-g, --gex-test=<x[,y,...] | min1:pref1:max1[,min2:pref2:max2,...] | x-y[:step]>

Exécute un test de taille de module Diffie-Hellman Group Exchange contre un serveur.

Diffie-Hellman exige que le client et le serveur se mettent d'accord sur une valeur génératrice et une valeur de module. Dans l'implémentation "Group Exchange" de Diffie-Hellman, le client spécifie la taille du module en bits en fournissant au serveur des valeurs minimum, préférée et maximum. Le serveur trouve ensuite un groupe qui correspond le mieux à la demande du client, renvoyant le générateur et le module correspondants. Pour une explication complète de ce processus, voir la RFC 4419 et ses successeurs.

Ce test agit comme un client en fournissant à un serveur SSH la taille d'un module, puis obtient la taille du module renvoyé par le serveur.

Trois types de syntaxe sont pris en charge :


1. <x[,y,...]>


Une liste de tailles de modules délimitées par des virgules.
Un test est effectué pour chaque valeur de la liste où elle agit comme taille de module minimum, préférée et maximum.


2. <min:pref:max[,min:pref:max,...]>


Un ensemble de trois valeurs délimitées par des deux-points, représentant la taille de module minimum, préférée et maximum.
Un test est effectué pour chaque ensemble.
Plusieurs ensembles peuvent être spécifiés sous forme de liste séparée par des virgules.


3. <x-y[:step]>


Une plage de tailles de modules avec une valeur de pas optionnelle. Le pas vaut 1 par défaut s'il est omis.
Si la valeur de gauche est supérieure à la valeur de droite, la séquence fonctionne de droite à gauche.
Un test est effectué pour chaque valeur de la plage où elle agit comme taille de module minimum, préférée et maximum.

Les doublons sont exclus de la valeur de retour.

-j, --json

Affiche les résultats au format JSON. Spécifiez deux fois (-jj) pour activer l'impression indentée (utile pour le débogage).
-l, --level=<info|warn|fail>

Spécifie le niveau de sortie minimum. Par défaut : info.
-L, --list-policies

Liste toutes les politiques officielles intégrées pour les systèmes courants. Leurs noms complets peuvent ensuite être passés à -P/--policy. Ajoutez -v à -L pour afficher les journaux de modification des politiques.
--lookup=<alg1,alg2,...>

Recherche les informations de sécurité d'un ou plusieurs algorithmes dans la base de données interne. Ne se connecte pas à un serveur.
-m, --manual

Imprime la page de manuel (uniquement pour les versions Docker, PyPI, Snap et Windows).
-M, --make-policy=<custom_policy.txt>

Crée une politique basée sur le serveur cible. Utile lorsque d'autres serveurs doivent être comparés à la configuration personnalisée du serveur cible (par exemple, dans un environnement de cluster). Notez que la politique résultante peut être modifiée manuellement.
-n, --no-colors

Désactive la sortie en couleur. Automatiquement activé lorsque la variable d'environnement NO_COLOR est définie.
-p, --port=<port>

Le port TCP auquel se connecter lors de l'audit d'un serveur, ou le port à écouter lors de l'audit d'un client.
-P, --policy=<"nom de politique intégré" | chemin/vers/politique_personnalisée.txt>

Exécute un audit de politique contre une cible en utilisant la politique spécifiée (voir la section AUDIT DE POLITIQUE pour une description détaillée de ce mode de fonctionnement). Combinez avec -c/--client-audit pour auditer une configuration client au lieu d'un serveur. Utilisez -L/--list-policies pour lister toutes les politiques officielles intégrées pour les systèmes courants.
--skip-rate-test

Ignore le test de débit de connexion lors des audits standard. Par défaut, quelques douzaines de connexions TCP sont créées avec l'hôte cible pour voir si la limitation de connexion est implémentée (cela peut inférer en toute sécurité si la cible est vulnérable à l'attaque DHEat ; voir CVE-2002-20001).
-t, --timeout=<secs>

Le délai d'attente, en secondes, pour la création de connexions et la lecture de données depuis le socket. Par défaut : 5.
-T, --targets=<hosts.txt>

Un fichier contenant une liste d'hôtes cibles. Chaque ligne doit contenir un hôte, au format HÔTE[:PORT]. Utilisez -p/--port pour définir le port par défaut pour tous les hôtes. Utilisez --threads pour contrôler les analyses simultanées.
--threads=<threads>

Le nombre de threads à utiliser lors de l'analyse de plusieurs cibles (avec -T/--targets). Par défaut : 32.
-v, --verbose

Augmente la verbosité de la sortie.

AUDIT DE POLITIQUE

L'audit de politique est utilisé pour tester si une cible SSH correspond à une configuration de sécurité recommandée. Pour plus d'informations, voir https://www.ssh-audit.com/policies.html.

Le programme prend en charge plusieurs modes de fonctionnement :

Audit standard

Ce mode est utilisé par défaut. Il effectue des tests sur les chiffrements, les modes, les clés d'hôte, les algorithmes MAC, les versions du protocole SSH et les versions du logiciel serveur (si disponibles) pour un hôte SSH donné. Il utilise les politiques officielles pour déterminer si les éléments testés sont considérés comme sûrs, obsolètes ou à éviter.

Audit de client

Utilisez l'option -c pour activer l'audit de client. Cela lance un serveur SSH sur le port 2222 (par défaut) qui écoute les connexions entrantes des clients SSH. Pour tester un client, exécutez simplement l'outil sur la machine du client et laissez-le se connecter à l'instance du serveur ssh-audit.

Test de politique

Utilisez l'option -P pour tester une configuration SSH contre une politique spécifique. Ceci est utile lorsque vous souhaitez vous assurer qu'un serveur SSH spécifique respecte une politique particulière. Vous pouvez choisir parmi les politiques intégrées (voir -L pour la liste) ou fournir un chemin vers un fichier de politique personnalisé.

Création de politique

Utilisez l'option -M pour créer un fichier de politique basé sur la configuration d'un serveur SSH cible. Ceci est utile pour créer des configurations personnalisées ou pour comparer la configuration d'un serveur avec celle d'autres serveurs dans un environnement similaire.

EXEMPLES

Tester la configuration d'un serveur SSH sur l'hôte example.com :


$ ssh-audit example.com

Tester la configuration d'un serveur SSH sur l'hôte example.com sur le port 2200 :


$ ssh-audit -p 2200 example.com

Tester la configuration d'un client SSH (en exécutant ssh-audit sur la machine du client) :


$ ssh-audit -c

Tester la configuration d'un serveur SSH contre la politique "openssh-8-0" :


$ ssh-audit -P "openssh-8-0" example.com

Tester plusieurs hôtes à partir d'un fichier et générer une sortie JSON :


$ ssh-audit -T targets.txt -j

ssh-audit(1) — Arch manual pages

NAME

ssh-audit - audit SSH server configuration

SYNOPSIS

ssh-audit [-b|--batch] [-c|--client] [-C|--color] [-d|--debug] [-h|--help] [-L|--list-policies] [-M FILE|--make-policy=FILE] [-P POLICY|--policy=POLICY] [-p PORT|--port=PORT] [-q|--quiet] [-T FILE|--targets=FILE] [-v|--verbose] [--conn-rate-test=RATES] [--dheat=ATTACK] [--gex-test=SIZES] [TARGET...]

DESCRIPTION

ssh-audit is a Python script that audits an SSH server's configuration. It checks for weak, default, or insecure SSH server configuration options. It can also audit SSH client configurations.

OPTIONS

-b, --batch

Enable batch mode (disable colors, use standard output).
-c, --client

Audit a client configuration. This assumes that the client is running an SSH server (e.g., sshd). Note that this option disables key exchange algorithms checks, as these are determined by the server.
-C, --color

Force colorized output. If --color is not specified, color output is disabled when the output is not a TTY.
-d, --debug

Enable debug output.
-h, --help

Show help message and exit.
-L, --list-policies

List all built-in policies and exit.
-M FILE, --make-policy=FILE

Create a custom policy file based on the configuration of the target server(s) or client. The generated policy file can be manually edited and used later with the -P option. See section POLICY AUDIT for more information.
-P POLICY, --policy=POLICY

Perform a policy audit. POLICY can either be the name of a built-in policy or the path to a custom policy file. See section POLICY AUDIT for more information.
-p PORT, --port=PORT

Specify the port number to connect to. Defaults to 22.
-q, --quiet

Suppress normal output. Only print errors and warnings.
-T FILE, --targets=FILE

Provide a file containing a list of targets to audit. Each line in the file should contain a target in the format of HOST[:PORT].
-v, --verbose

Enable verbose output.
--conn-rate-test=RATES

Test the connection rate of the target. RATES can be specified as `THREAD_COUNT` or `THREAD_COUNT:MAX_CONNECTIONS_PER_SECOND`. See section EXAMPLES for more information.
--dheat=ATTACK

Run the DHEat DoS attack against the target. ATTACK can be specified as `MAX_SOCKETS` or `MAX_SOCKETS:ALGORITHM[:KEY_LENGTH]`. See section EXAMPLES for more information.
--gex-test=SIZES

Test the Diffie-Hellman Group Exchange (DHGE) modulus size. SIZES can be specified as a comma-separated list of bit lengths, a range with a step (e.g., 0-5120:1024), or min:preferred:max. See section EXAMPLES for more information.

STANDARD AUDIT

By default, ssh-audit performs a standard audit. That is, it enumerates all host key types, key exchanges, ciphers, MACs, and other information, then color-codes them in output to the user. Cryptographic primitives with potential issues are displayed in yellow; primitives with serious flaws are displayed in red.

POLICY AUDIT

When the -P/--policy option is used, ssh-audit performs a policy audit. The target's host key types, key exchanges, ciphers, MACs, and other information is compared to a set of expected values defined in the specified policy file. If everything matches, only a short message stating a passing result is reported. Otherwise, the field(s) that did not match are reported.

Policy auditing is helpful for ensuring a group of related servers are properly hardened to an exact specification.

The set of official built-in policies can be viewed with -L/--list-policies. Multiple servers can be audited with -T/--targets=<servers.txt>. Custom policies can be made from an ideal target server with -M/--make-policy=<custom_policy.txt>.

EXAMPLES

Basic server auditing:

ssh-audit localhost
ssh-audit 127.0.0.1
ssh-audit 127.0.0.1:222
ssh-audit ::1
ssh-audit [::1]:222

To run a standard audit against many servers (place targets into servers.txt, one on each line in the format of HOST[:PORT]):

ssh-audit -T servers.txt

To audit a client configuration (listens on port 2222 by default; connect using "ssh -p 2222 anything@localhost"):

ssh-audit -c

To audit a client configuration, with a listener on port 4567:

ssh-audit -c -p 4567

To list all official built-in policies (hint: use their full names with -P/--policy):

ssh-audit -L

To run a built-in policy audit against a server (hint: use -L to see list of built-in policies):

ssh-audit -P "Hardened Ubuntu Server 20.04 LTS (version 1)" targetserver

To run a custom policy audit against a server (hint: use -M/--make-policy to create a custom policy file):

ssh-audit -P path/to/server_policy.txt targetserver

To run a policy audit against a client:

ssh-audit -c -P ["policy name" | path/to/client_policy.txt]

To run a policy audit against many servers:

ssh-audit -T servers.txt -P ["policy name" | path/to/server_policy.txt]

To create a policy based on a target server (which can be manually edited; see official built-in policies for syntax examples):

ssh-audit -M new_policy.txt targetserver

To run a Diffie-Hellman Group Exchange modulus size test using the values 2000 bits, 3000 bits, 4000 bits and 5000 bits:

ssh-audit targetserver --gex-test=2000,3000,4000,5000

To run a Diffie-Hellman Group Exchange modulus size test where 2048 bits is the minimum, 3072 bits is the preferred and 5000 bits is the maximum:

ssh-audit targetserver --gex-test=2048:3072:5000

To run a Diffie-Hellman Group Exchange modulus size test from 0 bits to 5120 bits in increments of 1024 bits:

ssh-audit targetserver --gex-test=0-5120:1024

To run the DHEat DoS attack (monitor the target server's CPU usage to determine the optimal number of concurrent sockets):

ssh-audit targetserver --dheat=10

To run the DHEat attack and manually target the diffie-hellman-group-exchange-sha256 algorithm:

ssh-audit targetserver --dheat=10:diffie-hellman-group-exchange-sha256

To run the DHEat attack and manually target the diffie-hellman-group-exchange-sha256 algorithm with a very small length of e (resulting in the same effect but without having to send large packets):

ssh-audit targetserver --dheat=10:diffie-hellman-group-exchange-sha256:4

To test the number of successful connections per second that can be created with the target using 8 parallel threads (useful for detecting whether connection throttling is implemented by the target):

ssh-audit targetserver --conn-rate-test=8

To use 8 parallel threads to create up to 100 connections per second with the target (useful for understanding how much CPU load is caused on the target simply from handling new connections vs excess modular exponentiation when performing the DHEat attack):

ssh-audit targetserver --conn-rate-test=8:100

RETURN VALUES

When a successful connection is made and all algorithms are rated as "good", ssh-audit returns 0. Other possible return values are:

1 = connection error
2 = at least one algorithm warning was found
3 = at least one algorithm failure was found
<any other non-zero value> = unknown error
