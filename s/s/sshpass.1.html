SSHPASS(1) Manuel utilisateur Sshpass SSHPASS(1)

NOM

sshpass - fournisseur de mot de passe ssh non interactif

SYNTAXE

sshpass [-fnom_fichier|-dnum|-pmot_de_passe|-e[var_env]] [options] commande arguments

DESCRIPTION

Cette page de manuel documente la commande sshpass.

sshpass est un utilitaire conçu pour exécuter ssh en utilisant le mode d'authentification par mot de passe dit « clavier interactif », mais en mode non interactif.

ssh utilise un accès TTY direct pour s'assurer que le mot de passe est bien fourni par un utilisateur au clavier interactif. Sshpass exécute ssh dans un tty dédié, le trompant ainsi en lui faisant croire qu'il reçoit le mot de passe d'un utilisateur interactif.

La commande à exécuter est spécifiée après les propres options de sshpass. Généralement, il s'agira de « ssh » avec des arguments, mais cela peut tout aussi bien être n'importe quelle autre commande. L'invite du mot de passe utilisée par ssh est cependant actuellement codée en dur dans sshpass.

Options

Si aucune option n'est donnée, sshpass lit le mot de passe depuis l'entrée standard. L'utilisateur peut donner au plus une source alternative pour le mot de passe :

-pmot_de_passe
Le mot de passe est fourni sur la ligne de commande. Veuillez noter la section intitulée « CONSIDÉRATIONS DE SÉCURITÉ ».
-fnom_fichier
Le mot de passe est la première ligne du fichier nom_fichier.
-dnuméro
numéro est un descripteur de fichier hérité par sshpass du processus appelant. Le mot de passe est lu depuis le descripteur de fichier ouvert.
-e[var_env]
Le mot de passe est tiré d'une variable d'environnement. Si var_env est fournie, c'est cette variable d'environnement qui est utilisée. Sinon, le mot de passe est tiré de la variable SSHPASS.
-P
Définit l'invite du mot de passe. Sshpass recherche cette invite dans la sortie du programme vers le TTY comme indication quand envoyer le mot de passe. Par défaut, sshpass recherche la chaîne « assword: » (qui correspond à la fois à « Password: » et « password: »). Si l'invite de votre client ne correspond à aucune de celles-ci, vous pouvez outrepasser le défaut avec cette option.
-v
Soyez verbeux. sshpass affichera sur stderr des informations qui devraient aider à déboguer les cas où la connexion se bloque, apparemment sans raison.

CONSIDÉRATIONS DE SÉCURITÉ

Avant tout, les utilisateurs de sshpass doivent réaliser que l'insistance de ssh à ne recevoir le mot de passe qu'interactivement n'est pas sans raison. Il est quasiment impossible de stocker le mot de passe en toute sécurité, et les utilisateurs de sshpass devraient se demander si l'authentification par clé publique de ssh ne fournit pas la même expérience utilisateur, tout en impliquant moins de tracas et en étant plus sécurisée.

L'option -p devrait être considérée comme la moins sécurisée de toutes les options de sshpass. Tous les utilisateurs du système peuvent voir le mot de passe dans la ligne de commande avec une simple commande « ps ». Sshpass fait une tentative minimale pour masquer le mot de passe, mais de telles tentatives sont condamnées à créer des conditions de concurrence sans résoudre réellement le problème. Les utilisateurs de sshpass sont encouragés à utiliser l'une des autres techniques de passage de mot de passe, qui sont toutes plus sécurisées.

En particulier, les personnes écrivant des programmes destinés à communiquer le mot de passe par programme sont encouragées à utiliser un pipe anonyme et à passer l'extrémité de lecture du pipe à sshpass en utilisant l'option -d.

VALEURS DE RETOUR

Comme pour tout autre programme, sshpass retourne 0 en cas de succès. En cas d'échec, les codes de retour suivants sont utilisés :

1
Argument de ligne de commande invalide
2
Arguments contradictoires donnés
3
Erreur d'exécution générale
4
Réponse non reconnue de ssh (erreur d'analyse)
5
Mot de passe invalide/incorrect
6
La clé publique de l'hôte est inconnue. sshpass se termine sans confirmer la nouvelle clé.
7
La clé publique IP a changé. sshpass se termine sans confirmer la nouvelle clé.

En outre, ssh peut se plaindre d'une attaque de type "man-in-the-middle". Cette plainte ne va pas au tty. En d'autres termes, même avec sshpass, le message d'erreur de ssh est imprimé sur la sortie d'erreur standard. Dans un tel cas, le code de retour de ssh est rapporté. Il s'agit généralement d'un « 255 » peu imaginatif (et non informatif) pour tous les cas d'erreur.

EXEMPLES

Exécutez rsync sur SSH en utilisant l'authentification par mot de passe, en passant le mot de passe sur la ligne de commande :

rsync --rsh='sshpass -p 12345 ssh -l test' host.example.com:path .

Pour faire la même chose à partir d'un script shell bourne d'une manière marginalement moins exposée :

SSHPASS=12345 rsync --rsh='sshpass -e ssh -l test' host.example.com:path .

BOGUES

Sshpass utilise l'interface pty(7) pour contrôler le TTY pour ssh. Cette interface, du moins sous Linux, a un défaut où si aucun descripteur de fichier esclave n'est ouvert, le pty maître retourne EIO. C'est le comportement normal, sauf qu'un pty esclave peut être créé à tout moment par un programme ouvrant /dev/tty. Cela rend impossible d'attendre de manière fiable les événements sans consommer 100% du CPU.

Au cours des différentes versions, différentes approches ont été tentées pour résoudre ce problème. N'importe quelle version donnée de sshpass est publiée avec la conviction qu'elle fonctionne, mais l'expérience a montré que ces choses peuvent, occasionnellement, casser. Cela s'est produit avec OpenSSH version 5.6. À l'heure actuelle, on pense que sshpass fonctionne à nouveau correctement.

Il semble que HPUX ait des idées non conformes à Posix sur la manière dont le TTY de contrôle est détaché. sshpass pourrait ne pas fonctionner correctement sur cette plateforme.
