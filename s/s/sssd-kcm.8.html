NOM

sssd-kcm - Gestionnaire de Cache Kerberos SSSD

DESCRIPTION

Cette page de manuel décrit la configuration du Gestionnaire de Cache Kerberos SSSD (KCM). KCM est un processus qui stocke, suit et gère les caches d'identifiants Kerberos. Il provient du projet Heimdal Kerberos, bien que la bibliothèque Kerberos MIT fournisse également un support côté client (plus de détails ci-dessous) pour le cache d'identifiants KCM.

Dans une configuration où les caches Kerberos sont gérés par KCM, la bibliothèque Kerberos (généralement utilisée via une application, comme par exemple, kinit(1), est un « client KCM » et le démon KCM est désigné comme un « serveur KCM ». Le client et le serveur communiquent via un socket UNIX.

Le serveur KCM garde une trace du propriétaire de chaque cache d'identifiants et effectue des contrôles d'accès basés sur l'UID et le GID du client KCM. L'utilisateur root a accès à tous les caches d'identifiants.

Le cache d'identifiants KCM présente plusieurs propriétés intéressantes :

• Comme le processus s'exécute en espace utilisateur, il est sujet à l'espacement des noms d'UID, contrairement au keyring du noyau.
• Contrairement au cache basé sur le keyring du noyau, qui est partagé entre tous les conteneurs, le serveur KCM est un processus distinct dont le point d'entrée est un socket UNIX.
• L'implémentation SSSD stocke les caches (ccaches) dans une base de données, généralement située dans /var/lib/sss/secrets, permettant aux caches de survivre aux redémarrages du serveur KCM ou aux redémarrages de la machine.

Cela permet au système d'utiliser un cache d'identifiants conscient des collections, tout en partageant le cache d'identifiants entre certains ou aucun conteneur en montant le socket en bind-mount.

Le délai d'inactivité par défaut du client KCM est de 5 minutes, ce qui laisse plus de temps pour l'interaction de l'utilisateur avec des outils en ligne de commande tels que kinit.

UTILISATION DU CACHE D'IDENTIFIANTS KCM

Pour utiliser le cache d'identifiants KCM, il doit être sélectionné comme type de cache d'identifiants par défaut dans krb5.conf(5). Le nom du cache d'identifiants doit être uniquement « KCM: » sans aucune expansion de modèle. Par exemple :

[libdefaults]
    default_ccache_name = KCM:

Ensuite, assurez-vous que les bibliothèques clientes Kerberos et le serveur KCM s'accordent sur le chemin du socket UNIX. Par défaut, les deux utilisent le même chemin /var/run/.heim_org.h5l.kcm-socket. Pour configurer la bibliothèque Kerberos, modifiez son option « kcm_socket », qui est décrite dans la page de manuel krb5.conf(5).

Enfin, assurez-vous que le serveur KCM SSSD est joignable. Le service KCM est généralement activé par socket par systemd(1). Contrairement aux autres services SSSD, il ne peut pas être démarré en ajoutant la chaîne « kcm » à la directive « service ».

systemctl start sssd-kcm.socket
systemctl enable sssd-kcm.socket

Notez que votre distribution peut déjà configurer les unités pour vous.

LE STOCKAGE DU CACHE D'IDENTIFIANTS

Les caches d'identifiants sont stockés dans une base de données, tout comme SSSD met en cache les entrées utilisateur ou groupe. La base de données est généralement située dans « /var/lib/sss/secrets ».

OBTENIR DES LOGS DE BOGAGE

Le service sssd-kcm est généralement activé par socket par systemd(1). Pour générer des logs de bogage, ajoutez l'élément suivant soit directement dans le fichier /etc/sssd/sssd.conf, soit sous forme d'extrait de configuration dans le répertoire /etc/sssd/conf.d/ :

[kcm]
debug_level = 10

Redémarrez ensuite le service sssd-kcm :

systemctl restart sssd-kcm.service

Enfin, exécutez le cas d'utilisation qui ne fonctionne pas pour vous. Les logs KCM seront générés dans /var/log/sssd/sssd_kcm.log. Il est recommandé de désactiver les logs de bogage lorsque vous n'avez plus besoin du bogage activé, car le service sssd-kcm peut générer une quantité assez importante d'informations de bogage.

Veuillez noter que les extraits de configuration ne sont actuellement traités que si le fichier de configuration principal à /etc/sssd/sssd.conf existe.

RENOUVELLEMENTS

Le service sssd-kcm peut être configuré pour tenter le renouvellement des TGT renouvelables stockés dans le cache KCM. Les renouvellements ne sont tentés que lorsque la moitié de la durée de vie du ticket est atteinte. Les renouvellements KCM sont configurés lorsque les options suivantes sont définies dans la section [kcm] :

tgt_renewal = true
krb5_renew_interval = 60m

SSSD peut également hériter des options krb5 pour les renouvellements d'un domaine existant.

tgt_renewal = true
tgt_renewal_inherit = nom-domaine

Les options krb5 suivantes peuvent être configurées dans la section [kcm] pour contrôler le comportement de renouvellement ; ces options sont décrites en détail ci-dessous :

krb5_renew_interval
krb5_renewable_lifetime
krb5_lifetime
krb5_validate
krb5_canonicalize
krb5_auth_timeout

OPTIONS DE CONFIGURATION

Le service KCM est configuré dans la section « kcm » du fichier sssd.conf. Veuillez noter que, comme le service KCM est généralement activé par socket, il suffit de redémarrer le service « sssd-kcm » après avoir modifié les options dans la section « kcm » de sssd.conf :

systemctl restart sssd-kcm.service

Le service KCM est configuré dans la section « kcm ». Pour une référence syntaxique détaillée, consultez la section « FORMAT DU FICHIER » de la page de manuel sssd.conf(5).

Les options génériques du service SSSD telles que « debug_level » ou « fd_limit » sont acceptées par le service kcm. Veuillez consulter la page de manuel sssd.conf(5) pour une liste complète. De plus, il existe également des options spécifiques à KCM.

socket_path (chaîne)

Le socket sur lequel le service KCM écoutera.

Par défaut : /var/run/.heim_org.h5l.kcm-socket

Note : sur les plateformes où systemd est pris en charge, le chemin du socket est remplacé par celui défini dans le fichier d'unité sssd-kcm.socket.

max_ccaches (entier)

Combien de caches d'identifiants la base de données KCM autorise pour tous les utilisateurs.

Par défaut : 0 (illimité, seule la quotité par UID est appliquée)

max_uid_ccaches (entier)

Combien de caches d'identifiants la base de données KCM autorise par UID. Ceci est équivalent à « avec combien de principaux vous pouvez kinit ».

Par défaut : 64

max_ccache_size (entier)

Quelle taille peut avoir un cache d'identifiants par cache. Chaque ticket de service compte dans cette quotité.

Par défaut : 65536

tgt_renewal (booléen)

Active la fonctionnalité de renouvellement des TGT.

Par défaut : False (Renouvellements automatiques désactivés)

tgt_renewal_inherit (chaîne)

Domaine à partir duquel hériter des options krb5_* pour le renouvellement des TGT.

Par défaut : NULL

krb5_auth_timeout (entier)

Délai en secondes après lequel une requête d'authentification en ligne ou une requête de changement de mot de passe est abandonnée. Si possible, la requête d'authentification est poursuivie hors ligne.

Par défaut : 6

krb5_validate (booléen)

Vérifie à l'aide de krb5_keytab que le TGT obtenu n'a pas été usurpé. La keytab est vérifiée séquentiellement pour les entrées, et la première entrée avec un royaume correspondant est utilisée pour la validation. Si aucune entrée ne correspond au royaume, la dernière entrée de la keytab est utilisée. Ce processus peut être utilisé pour valider les environnements utilisant une confiance inter-royaumes en plaçant l'entrée keytab appropriée comme dernière entrée ou seule entrée dans le fichier keytab.

Par défaut : false (Fournisseur IPA et AD : true)

krb5_renewable_lifetime (string)

Demande un ticket renouvelable avec une durée de vie totale, donnée sous forme d'un entier immédiatement suivi d'une unité de temps :

s pour secondes

m pour minutes

h pour heures

d pour jours.

Si aucune unité n'est donnée, s est supposé.

NOTE : Il n'est pas possible de mélanger les unités. Pour définir la durée de vie renouvelable à une heure et demie, utilisez '90m' au lieu de '1h30m'.

Par défaut : non défini, c'est-à-dire que le TGT n'est pas renouvelable

krb5_lifetime (string)

Demande un ticket avec une durée de vie, donnée sous forme d'un entier immédiatement suivi d'une unité de temps :

s pour secondes

m pour minutes

h pour heures

d pour jours.

Si aucune unité n'est donnée, s est supposé.

NOTE : Il n'est pas possible de mélanger les unités. Pour définir la durée de vie à une heure et demie, veuillez utiliser '90m' au lieu de '1h30m'.

Par défaut : non défini, c'est-à-dire la durée de vie par défaut du ticket configurée sur le KDC.

krb5_renew_interval (string)

Le temps en secondes entre deux vérifications si le TGT doit être renouvelé. Les TGT sont renouvelés si environ la moitié de leur durée de vie est dépassée, donnée sous forme d'un entier immédiatement suivi d'une unité de temps :

s pour secondes

m pour minutes

h pour heures

d pour jours.

Si aucune unité n'est donnée, s est supposé.

NOTE : Il n'est pas possible de mélanger les unités. Pour définir la durée de vie renouvelable à une heure et demie, utilisez '90m' au lieu de '1h30m'.

Si cette option n'est pas définie ou est égale à 0, le renouvellement automatique est désactivé.

Par défaut : non défini

krb5_canonicalize (boolean)

Spécifie si le principal de l'hôte et de l'utilisateur doit être canonisé. Cette fonctionnalité est disponible avec MIT Kerberos 1.7 et versions ultérieures.

Par défaut : false
