NOM

sshguard-setup - configuration de SSHGuard sur votre système

DESCRIPTION

Pour configurer SSHGuard, écrivez sshguard.conf et configurez le backend si nécessaire. Les options de configuration sont documentées dans le fichier de configuration d'exemple. Un bon point de départ est de le copier et d'apporter les modifications nécessaires :

1.
Définissez BACKEND. Vous devrez peut-être également le configurer pour qu'il fonctionne avec SSHGuard (voir BACKENDS).
2.
Définissez FILES, LOGREADER, ou les deux. Alternativement, donnez à sshguard une liste de fichiers à surveiller en tant qu'arguments positionnels sur la ligne de commande.

Utilisez FILES pour spécifier une liste de fichiers journaux séparés par des espaces à surveiller. Utilisez LOGREADER pour spécifier une commande shell à exécuter pour obtenir les journaux. Les deux paramètres sont ignorés si des fichiers sont fournis sur la ligne de commande.

Des commandes LOGREADER d'exemple pour journalctl(1) et macOS 10.12+ sont disponibles dans le fichier de configuration d'exemple.

AUTRES JOURNAUX

syslog-ng

Pour syslog-ng 2.x, ajoutez les lignes suivantes à syslog-ng.conf :

# passe uniquement les entrées avec les facilités auth+authpriv provenant de programmes autres que sshguard
filter sshlogs { facility(auth, authpriv) and not match("sshguard"); };
# passe à ce processus avec ce modèle (évite les préfixes <ID>)
destination sshguardproc {
program("/usr/local/sbin/sshguard"
template("$DATE $FULLHOST $MESSAGE\n"));
};
log { source(src); filter(sshlogs); destination(sshguardproc); };

Pour syslog-ng 3.x, ajoutez les lignes suivantes à syslog-ng.conf :

# active le mode 3.x
@version:3.0
# passe uniquement les entrées avec les facilités auth+authpriv provenant de programmes autres que sshguard
filter f_sshguard { facility(auth, authpriv) and not program("sshguard"); };
# passe les entrées construites avec ce format
destination sshguard {
program("/usr/sbin/sshguard"
template("$DATE $FULLHOST $MSGHDR$MESSAGE\n")
);
};
log { source(src); filter(f_sshguard); destination(sshguard); };

Après avoir redémarré syslog-ng, SSHGuard devrait démarrer dès qu'une entrée de journal avec la facilité auth ou authpriv arrive. Si vous surveillez des services autres que sshd, ajoutez les facilités de journal appropriées à syslog-ng.conf.

metalog

Ajoutez les lignes suivantes à metalog.conf :

Choses à protéger contre les attaques par force brute :
    # pour ssh
    facility = "*"
    program = "sshd"
    # autres services ...
    # journaliser dans le répertoire /var/log/sshguard
    logdir = "/var/log/sshguard"

Après avoir redémarré metalog, les entrées de journal apparaîtront dans /var/log/sshguard. Utilisez la collecte de journaux pour surveiller le journal *actuel*.

BACKENDS

SSHGuard peut bloquer les attaquants à l'aide de l'un des plusieurs backends de pare-feu sélectionnés lors de la compilation.

ATTENTION :

Lisez la documentation de votre pare-feu. Assurez-vous de bien comprendre chaque règle ou commande dans les exemples ci-dessous avant de les utiliser. Ils pourraient nécessiter des ajustements pour convenir à votre configuration particulière.

pf

SSHGuard ajoute les attaquants à la table <sshguard>. Créez la table et bloquez les attaquants en ajoutant les lignes suivantes à la fin de pf.conf :

table <sshguard> persist
block in proto tcp from <sshguard>

Après avoir rechargé la configuration pf, vous pouvez inspecter le contenu de la table en utilisant :

# pfctl -t sshguard -T show

ipfw

SSHGuard crée et ajoute les attaquants à la table 22. La table peut être utilisée pour bloquer les attaquants dans votre jeu de règles. Par exemple :

# ipfw add 5000 reset ip from table\(22\) to me

Vous pouvez inspecter le contenu de la table en utilisant :

# ipfw table 22 list

firewalld

Les attaquants bloqués sont ajoutés à deux ipsets nommés sshguard4 et sshguard6. Les entrées dans les ipsets sont bloquées par défaut dans la zone de pare-feu par défaut. D'autres zones de pare-feu peuvent être configurées en utilisant :

# firewall-cmd --zone=zone-name --permanent \
    --add-rich-rule="rule source ipset=sshguard4 drop"
# firewall-cmd --zone=zone-name --permanent \
    --add-rich-rule="rule source ipset=sshguard6 drop"

Vous pouvez inspecter les entrées dans les deux ipsets en utilisant :

# firewall-cmd --permanent --info-ipset=sshguard4
# firewall-cmd --permanent --info-ipset=sshguard6

ipset

Les attaquants bloqués sont ajoutés à deux ipsets nommés sshguard4 et sshguard6. Rien n'est bloqué par défaut, mais ils peuvent être utilisés comme source pour iptables et d'autres outils. Par exemple :

# iptables  -I INPUT -m set --match-set sshguard4 src -j DROP
# ip6tables -I INPUT -m set --match-set sshguard6 src -j DROP

netfilter/iptables

Créez une chaîne pour SSHGuard :

# iptables -N sshguard      # pour IPv4
# ip6tables -N sshguard     # pour IPv6

Mettez à jour la chaîne INPUT pour passer également le trafic à la chaîne sshguard à la toute fin de son traitement. Spécifiez dans --dport tous les ports des services que votre sshguard protège. Si vous voulez empêcher les attaquants de faire du trafic vers l'hôte, supprimez complètement l'option :

# bloquer tout trafic provenant des abuseurs
iptables -A INPUT -j sshguard
ip6tables -A INPUT -j sshguard

Ou :

# bloquer les abuseurs uniquement pour les services SSH, FTP, POP, IMAP (utiliser le module "multiport")
iptables -A INPUT -m multiport -p tcp --destination-ports 21,22,110,143 -j sshguard
ip6tables -A INPUT -m multiport -p tcp --destination-ports 21,22,110,143 -j sshguard

Vérifiez que vous n'avez PAS une règle d'autorisation par défaut qui laisse passer tout le trafic ssh plus haut dans la chaîne. Vérifiez que vous n'avez PAS une règle de refus par défaut qui bloque tout le trafic ssh dans votre pare-feu. Dans l'un ou l'autre cas, vous avez déjà les compétences pour ajuster la configuration de votre pare-feu.

Voici un exemple de jeu de règles qui a du sens :

iptables -N sshguard
# bloquer tout ce que SSHGuard juge mauvais ...
iptables -A INPUT -j sshguard
# activer ssh, dns, http, https
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
iptables -A INPUT -p udp --dport 53 -j ACCEPT
iptables -A INPUT -p tcp --dport 80 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT
# et tout le reste est bloqué (refus par défaut)
iptables -P INPUT DROP

Au redémarrage, la plupart des systèmes réinitialisent la configuration du pare-feu par défaut. Pour conserver votre configuration, vous utilisez généralement les utilitaires iptables-save et iptables-restore. Cependant, chaque variante de Linux a sa propre "bonne façon" de faire.

nftables

SSHGuard crée des tables avec une priorité élevée et ajoute automatiquement les attaquants à un ensemble.

Vous pouvez inspecter le contenu des ensembles en utilisant :

# nft list set ip sshguard attackers
# nft list set ip6 sshguard attackers

De plus, vous pouvez afficher les tables de sshguard avec :

# nft list table ip sshguard
# nft list table ip6 sshguard

DIAGNOSTIC

Problèmes de connexion SSH

Si vous êtes bloqué en dehors de votre système, il est fort probable que vous ayez configuré sshguard pour qu'il bloque les attaquants sur le port 22.

Dans la plupart des cas, vous devrez déconnecter une adresse IP bloquée dans une table de pare-feu (par exemple, iptables, pf, firewalld).

Si vous êtes un utilisateur légitime, vous pouvez généralement redémarrer l'ordinateur pour effacer tous les blocs. Sinon, demandez à votre administrateur système de vous débloquer.

NAME

sshguard-setup — Configuration and troubleshooting for SSHGuard

DESCRIPTION

SSHGuard provides an abstraction layer for logging and firewalling. This man page explains how to verify that SSHGuard is configured correctly, is running, and is recognizing attacks.

Is SSHGuard configured correctly?

Check that the correct FILES (or LOGREADER) and BACKEND are set in sshguard.conf.

Is SSHGuard running?

SSHGuard spawns a pipeline of cooperating processes. You can verify that SSHGuard is started correctly by viewing your process list using ps or top. Shown here are the processes associated with an example configuration:

/bin/sh /opt/sshguard/sbin/sshguard
tail -F -n 0 /tmp/log.txt
/opt/sshguard/libexec/sshg-parser
/opt/sshguard/libexec/sshg-blocker -a 30 -p 120 -s 1800 -N 128 -n 32
/bin/sh /usr/local/libexec/sshg-fw-null

In order:

  • SSHGuard, installed in /opt/sshguard, is being interpreted by /bin/sh.
  • SSHGuard launched tail -F -n 0, which is monitoring /tmp/log.txt.
  • The default parser sshg-parser is running.
  • The blocker is running with options -a 30 -p 120 -s 1800 -N 128 -n 32.
  • The firewall sshg-fw-null is running. The null backend doesn't actually block any attacks.

Is SSHGuard recognizing attacks?

SSHGuard recognizes attacks by parsing log messages. The format of log messages can occasionally change. If you are using the default, built-in attack parser, you can check if SSHGuard recognizes your attacks by running:

$ cat /var/log/auth.log | %PREFIX%/libexec/sshg-parser -a

Log messages that are recognized as attacks are prefixed with a '*' at the beginning of each line. If a log message that should be recognized as an attack is not, consider reporting it.

OTHER LOGS

If you want SSHGuard to monitor logs other than the system log, you can edit the sshguard.conf file and uncomment the FILES directive, and set it to the log files you wish to monitor.

FILES=/var/log/auth.log /var/log/maillog

Alternatively, you can specify the log files on the command line:

# sshguard /var/log/auth.log /var/log/maillog

BACKENDS

SSHGuard supports multiple backends for blocking attackers. The default backend is iptables. Other supported backends include nftables, firewalld, and a null backend (which does not block anything). You can specify the backend in the sshguard.conf file using the BACKEND directive.

BACKEND=nftables

You can also specify the backend on the command line:

# sshguard -b nftables

EXAMPLES

Ignore FILES and monitor these files instead:

# sshguard /var/log/auth.log /var/log/maillog

Use the firewalld backend:

# sshguard -b firewalld
