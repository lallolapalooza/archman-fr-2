SSH(1) Manuel des commandes générales SSH(1)

NOM

ssh — Client de connexion à distance OpenSSH

SYNTAXE

ssh [-46AaCfGgKkMNnqsTtVvXxYy] [-B interface_liaison] [-b adresse_liaison] [-c spec_chiffrement] [-D [adresse_liaison:]port] [-E fichier_journal] [-e caractere_echappement] [-F fichier_config] [-I pkcs11] [-i fichier_identite] [-J destination] [-L adresse] [-l nom_connexion] [-m spec_mac] [-O commande_ctl] [-o option] [-P balise] [-p port] [-R adresse] [-S chemin_ctl] [-W hote:port] [-w tun_local[:tun_distant]] destination [commande [argument ...]]

ssh [-Q option_requete]

DESCRIPTION

ssh (client SSH) est un programme permettant de se connecter à une machine distante et d'exécuter des commandes sur cette machine. Il est conçu pour fournir des communications chiffrées sécurisées entre deux hôtes non fiables sur un réseau non sécurisé. Les connexions X11, les ports TCP arbitraires et les sockets de domaine UNIX peuvent également être redirigés sur le canal sécurisé.

ssh se connecte et ouvre une session sur la destination spécifiée, qui peut être soit [utilisateur@]hôte, soit une URI de la forme ssh://[utilisateur@]hôte[:port]. L'utilisateur doit prouver son identité à la machine distante en utilisant l'une des méthodes ci-dessous (voir ci-dessous).

Si une commande est spécifiée, elle sera exécutée sur l'hôte distant au lieu d'un shell de connexion. Une ligne de commande complète peut être spécifiée comme commande, ou elle peut avoir des arguments supplémentaires. S'ils sont fournis, les arguments seront ajoutés à la commande, séparés par des espaces, avant d'être envoyés au serveur pour exécution.

Les options sont les suivantes :

-4
Force ssh à utiliser uniquement les adresses IPv4.
-6
Force ssh à utiliser uniquement les adresses IPv6.
-A
Active la redirection des connexions d'un agent d'authentification tel que ssh-agent(1). Ceci peut aussi être spécifié sur une base par hôte dans un fichier de configuration.

La redirection d'agent doit être activée avec prudence. Les utilisateurs ayant la capacité de contourner les permissions de fichiers sur l'hôte distant (pour le socket de domaine UNIX de l'agent) peuvent accéder à l'agent local via la connexion redirigée. Un attaquant ne peut cependant pas obtenir de clés de l'agent, mais il peut effectuer des opérations sur les clés qui lui permettent de s'authentifier en utilisant les identités chargées dans l'agent. Une alternative plus sûre peut être d'utiliser un hôte de saut (voir -J).

-a
Désactive la redirection de la connexion de l'agent d'authentification.
-B interface_liaison
Se lie à l'adresse de interface_liaison avant de tenter de se connecter à l'hôte de destination. Ceci n'est utile que sur les systèmes ayant plus d'une adresse.
-b adresse_liaison
Utilise adresse_liaison sur la machine locale comme adresse source de la connexion. N'est utile que sur les systèmes ayant plus d'une adresse.
-C
Demande la compression de toutes les données (y compris stdin, stdout, stderr, et les données pour les connexions X11, TCP et de domaine UNIX redirigées). L'algorithme de compression est le même que celui utilisé par gzip(1). La compression est souhaitable sur les lignes modem et autres connexions lentes, mais ne fera que ralentir les choses sur les réseaux rapides. La valeur par défaut peut être définie hôte par hôte dans les fichiers de configuration ; voir l'option Compression dans ssh_config(5).
-c spec_chiffrement
Sélectionne la spécification de chiffrement pour le chiffrement de la session. spec_chiffrement est une liste de chiffrements séparés par des virgules, listés par ordre de préférence. Voir la directive Ciphers dans ssh_config(5) pour plus d'informations.
-D [adresse_liaison:]port
Spécifie une redirection de port locale “dynamique” au niveau application. Cela fonctionne en allouant un socket pour écouter sur le port côté local, éventuellement lié à adresse_liaison spécifiée. Chaque fois qu'une connexion est établie à ce port, la connexion est redirigée via le canal sécurisé, et le protocole applicatif est ensuite utilisé pour déterminer où se connecter depuis la machine distante. Actuellement, les protocoles SOCKS4 et SOCKS5 sont pris en charge, et ssh agit comme un serveur SOCKS. Seul le superutilisateur peut rediriger les ports privilégiés. Les redirections de port dynamiques peuvent également être spécifiées dans le fichier de configuration.

Les adresses IPv6 peuvent être spécifiées en plaçant l'adresse entre crochets. Seul le superutilisateur peut rediriger les ports privilégiés. Par défaut, le port local est lié conformément au paramètre GatewayPorts. Cependant, une adresse_liaison explicite peut être utilisée pour lier la connexion à une adresse spécifique. L'adresse_liaison “localhost” indique que le port d'écoute doit être lié à une utilisation locale uniquement, tandis qu'une adresse vide ou ‘*’ indique que le port doit être disponible depuis toutes les interfaces.

-E fichier_journal
Ajoute les journaux de débogage à fichier_journal au lieu de l'erreur standard.
-e caractere_echappement
Définit le caractère d'échappement pour les sessions avec un pty (par défaut : ‘~’). Le caractère d'échappement n'est reconnu qu'en début de ligne. Le caractère d'échappement suivi d'un point (‘.’) ferme la connexion ; suivi du contrôle-Z suspend la connexion ; et suivi de lui-même envoie le caractère d'échappement une fois. Définir le caractère sur “aucun” désactive tout échappement et rend la session entièrement transparente.
-F fichier_config
Spécifie un fichier de configuration utilisateur alternatif

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

fichier de configuration. Si un fichier de configuration est fourni sur la ligne de commande, le fichier de configuration système (/etc/ssh/ssh_config) sera ignoré. La valeur par défaut pour le fichier de configuration par utilisateur est ~/.ssh/config. Si elle est définie sur « none », aucun fichier de configuration ne sera lu.
-f
Demande à ssh de passer en arrière-plan juste avant l'exécution de la commande. Ceci est utile si ssh doit demander des mots de passe ou des phrases secrètes, mais que l'utilisateur souhaite que cela se fasse en arrière-plan. Ceci implique -n. La manière recommandée de lancer des programmes X11 sur un site distant est d'utiliser quelque chose comme ssh -f hôte xterm.

Si l'option de configuration ExitOnForwardFailure est définie sur « yes », alors un client lancé avec -f attendra que toutes les redirections de ports distants soient établies avec succès avant de se placer en arrière-plan. Reportez-vous à la description de ForkAfterAuthentication dans ssh_config(5) pour plus de détails.

-G
Demande à ssh d'afficher sa configuration après avoir évalué les blocs Host et Match et de quitter.
-g
Permet aux hôtes distants de se connecter aux ports locaux redirigés. Si utilisé sur une connexion multiplexée, cette option doit être spécifiée sur le processus maître.
-I pkcs11
Spécifie la bibliothèque partagée PKCS#11 que ssh doit utiliser pour communiquer avec un token PKCS#11 fournissant les clés pour l'authentification de l'utilisateur.
-i fichier_identité
Sélectionne un fichier à partir duquel l'identité (clé privée) pour l'authentification par clé publique est lue. Vous pouvez également spécifier un fichier de clé publique pour utiliser la clé privée correspondante chargée dans ssh-agent(1) lorsque le fichier de clé privée n'est pas présent localement. La valeur par défaut est ~/.ssh/id_rsa, ~/.ssh/id_ecdsa, ~/.ssh/id_ecdsa_sk, ~/.ssh/id_ed25519 et ~/.ssh/id_ed25519_sk. Les fichiers d'identité peuvent également être spécifiés par hôte dans le fichier de configuration. Il est possible d'avoir plusieurs options -i (et plusieurs identités spécifiées dans les fichiers de configuration). Si aucun certificat n'a été explicitement spécifié par la directive CertificateFile, ssh essaiera également de charger les informations de certificat à partir du nom de fichier obtenu en ajoutant -cert.pub aux noms de fichiers d'identité.
-J destination
Se connecte à l'hôte cible en établissant d'abord une connexion ssh à l'hôte de saut décrit par destination, puis en établissant une redirection TCP vers la destination finale à partir de là. Plusieurs sauts peuvent être spécifiés séparés par des virgules. Les adresses IPv6 peuvent être spécifiées en encadrant l'adresse avec des crochets. Ceci est un raccourci pour spécifier une directive de configuration ProxyJump. Notez que les directives de configuration fournies sur la ligne de commande s'appliquent généralement à l'hôte de destination et non aux hôtes de saut spécifiés. Utilisez ~/.ssh/config pour spécifier la configuration des hôtes de saut.
-K
Active l'authentification basée sur GSSAPI et la redirection (délégation) des informations d'identification GSSAPI vers le serveur.
-k
Désactive la redirection (délégation) des informations d'identification GSSAPI vers le serveur.
-L [adresse_liaison:]port:hôte:port_hôte
 
-L [adresse_liaison:]port:socket_distant
 
-L socket_local:hôte:port_hôte
 
-L socket_local:socket_distant
Spécifie que les connexions au port TCP ou au socket Unix donné sur l'hôte local (client) doivent être redirigées vers l'hôte et le port, ou le socket Unix, donné du côté distant. Cela fonctionne en allouant un socket pour écouter soit un port TCP du côté local, éventuellement lié à l'adresse_liaison spécifiée, soit un socket Unix. Chaque fois qu'une connexion est établie vers le port ou le socket local, la connexion est redirigée via le canal sécurisé, et une connexion est établie vers l'hôte port port_hôte, ou le socket Unix socket_distant, depuis la machine distante.

Les redirections de ports peuvent également être spécifiées dans le fichier de configuration. Seul le superutilisateur peut rediriger des ports privilégiés. Les adresses IPv6 peuvent être spécifiées en encadrant l'adresse avec des crochets.

Par défaut, le port local est lié conformément au paramètre GatewayPorts. Cependant, une adresse_liaison explicite peut être utilisée pour lier la connexion à une adresse spécifique. L'adresse_liaison « localhost » indique que le port d'écoute doit être lié uniquement à un usage local, tandis qu'une adresse vide ou « * » indique que le port doit être disponible depuis toutes les interfaces.

-l nom_connexion
Spécifie l'utilisateur sous lequel se connecter sur la machine distante. Ceci peut également être spécifié par hôte dans le fichier de configuration.
-M
Place le client ssh en mode « maître » pour le partage de connexion. Plusieurs options -M placent ssh en mode « maître » mais avec une confirmation requise via ssh-askpass(1) avant chaque opération qui modifie l'état de multiplexage (par exemple, ouverture d'une nouvelle session). Reportez-vous à la description de ControlMaster dans ssh_config(5) pour plus de détails.
-m spec_mac
Une liste d'algorithmes MAC (code d'authentification de message) séparés par des virgules, spécifiés par ordre de préférence. Voir la directive MACs dans ssh_config(5) pour plus d'informations.
-N
N'exécute aucune commande distante. Ceci est utile uniquement pour rediriger des ports. Reportez-vous à la description de SessionType dans ssh_config(5) pour plus de détails.
-n
Redirige l'entrée standard depuis /dev/null (en fait, empêche la lecture depuis l'entrée standard). Ceci doit être utilisé lorsque ssh est exécuté en arrière-plan. Une astuce courante consiste à l'utiliser pour exécuter des programmes X11 sur une machine distante. Par exemple, ssh -n shadows.cs.hut.fi emacs & lancera un emacs sur shadows.cs.hut.fi, et la connexion X11 sera automatiquement redirigée via un canal crypté. Le programme ssh sera mis en arrière-plan. (Cela ne fonctionne pas si ssh a besoin de demander un mot de passe ou une phrase secrète ; voir également l'option -f.) Reportez-vous à la description de StdinNull dans ssh_config(5) pour plus de détails.
-O cmd_ctl
Contrôle un processus maître de multiplexage de connexion actif. Lorsque l'option -O est spécifiée, l'argument cmd_ctl est interprété et passé au processus maître. Les commandes valides sont : « check » (vérifier que le processus maître est en cours d'exécution), « forward » (demander des redirections sans exécution de commande), « cancel » (annuler les redirections), « proxy » (se connecter à un maître de multiplexage en cours d'exécution en mode proxy), « exit » (demander au maître de quitter) et « stop » (demander au maître d'arrêter d'accepter d'autres requêtes de multiplexage).
-o option
Peut être utilisé pour donner des options dans le format utilisé dans le fichier de configuration. Ceci est utile pour spécifier des options pour lesquelles il n'y a pas de drapeau de ligne de commande distinct. Pour plus de détails sur les options listées ci-dessous, et leurs valeurs possibles, voir ssh_config(5).

-P tag
Spécifie un nom de balise qui peut être utilisé pour sélectionner la configuration dans ssh_config(5). Reportez-vous aux mots-clés Tag et Match dans ssh_config(5) pour plus d'informations.
-p port
Port de connexion sur l'hôte distant. Ceci peut être spécifié sur une base par hôte dans le fichier de configuration.
-Q query_option
Interroge les algorithmes pris en charge par l'une des fonctionnalités suivantes : cipher (chiffrements symétriques pris en charge), cipher-auth (chiffrements symétriques prenant en charge le chiffrement authentifié), help (termes de requête pris en charge pour une utilisation avec le drapeau -Q), mac (codes d'intégrité de message pris en charge), kex (algorithmes d'échange de clés), key (types de clés), key-ca-sign (algorithmes de signature CA valides pour les certificats), key-cert (types de clés de certificat), key-plain (types de clés non certificats), key-sig (tous les types de clés et algorithmes de signature), protocol-version (versions de protocole SSH prises en charge), et sig (algorithmes de signature pris en charge). Alternativement, tout mot-clé de ssh_config(5) ou sshd_config(5) qui prend une liste d'algorithmes peut être utilisé comme alias pour le query_option correspondant.
-q
Mode silencieux. Supprime la plupart des messages d'avertissement et de diagnostic.
-R [bind_address:]port:host:hostport
 
-R [bind_address:]port:local_socket
 
-R remote_socket:host:hostport
 
-R remote_socket:local_socket
 
-R [bind_address:]port
Spécifie que les connexions au port TCP ou au socket Unix donné sur l'hôte distant (serveur) doivent être transférées vers le côté local.

Cela fonctionne en allouant un socket pour écouter soit un port TCP, soit un socket Unix côté distant. Chaque fois qu'une connexion est établie à ce port ou socket Unix, la connexion est transférée via le canal sécurisé, et une connexion est établie depuis la machine locale vers une destination explicite spécifiée par host port hostport, ou local_socket, ou, si aucune destination explicite n'a été spécifiée, ssh agira comme un proxy SOCKS 4/5 et transférera les connexions vers les destinations demandées par le client SOCKS distant.

Les transferts de port peuvent également être spécifiés dans le fichier de configuration. Les ports privilégiés ne peuvent être transférés que lorsque l'on se connecte en tant que root sur la machine distante. Les adresses IPv6 peuvent être spécifiées en plaçant l'adresse entre crochets.

Par défaut, les sockets d'écoute TCP sur le serveur seront liés uniquement à l'interface de boucle locale. Ceci peut être outrepassé en spécifiant une bind_address. Une bind_address vide, ou l'adresse ‘*’, indique que le socket distant doit écouter sur toutes les interfaces. La spécification d'une bind_address distante ne réussira que si l'option GatewayPorts du serveur est activée (voir sshd_config(5)).

Si l'argument port est ‘0’, le port d'écoute sera dynamiquement alloué sur le serveur et rapporté au client au moment de l'exécution. Lorsqu'il est utilisé avec -O forward, le port alloué sera imprimé sur la sortie standard.

Peut être utilisé pour demander l'invocation d'un sous-système sur le système distant. Les sous-systèmes facilitent l'utilisation de SSH comme transport sécurisé pour d'autres applications (par exemple sftp(1)). Le sous-système est spécifié comme la commande distante. Se référer à la description de SessionType dans ssh_config(5) pour plus de détails.
-T

-t
Force l'allocation d'un pseudo-terminal. Ceci peut être utilisé pour exécuter des programmes arbitraires basés sur un écran sur une machine distante, ce qui peut être très utile, par exemple lors de la mise en œuvre de services de menu. Plusieurs options -t forcent l'allocation d'un tty, même si ssh n'a pas de tty local.
-V
Affiche le numéro de version et quitte.
-v
Mode verbeux. Fait en sorte que ssh affiche des messages de débogage sur sa progression. Ceci est utile pour le débogage des problèmes de connexion, d'authentification et de configuration. Plusieurs options -v augmentent la verbosité. Le maximum est de 3.
-W hôte:port
Demande que l'entrée et la sortie standard sur le client soient redirigées vers hôte sur le port port via le canal sécurisé. Implique -N, -T, ExitOnForwardFailure et ClearAllForwardings, bien que celles-ci puissent être remplacées dans le fichier de configuration ou en utilisant les options de ligne de commande -o.
-w tun_local[:tun_distant]
Demande la redirection du périphérique tunnel avec les périphériques tun(4) spécifiés entre le client (tun_local) et le serveur (tun_distant).

Les périphériques peuvent être spécifiés par leur identifiant numérique ou par le mot-clé “any”, qui utilise le prochain périphérique tunnel disponible. Si tun_distant n'est pas spécifié, il vaut par défaut “any”. Voir aussi les directives Tunnel et TunnelDevice dans ssh_config(5).

Si la directive Tunnel est non définie, elle sera définie sur le mode tunnel par défaut, qui est “point-à-point”. Si un mode de redirection Tunnel différent est souhaité, il doit être spécifié avant -w.

-X
Active la redirection X11. Ceci peut également être spécifié sur une base par hôte dans un fichier de configuration.

La redirection X11 doit être activée avec prudence. Les utilisateurs ayant la capacité de contourner les permissions de fichiers sur l'hôte distant (pour la base de données d'autorisation X de l'utilisateur) peuvent accéder à l'affichage X local via la connexion redirigée. Un attaquant peut alors être capable d'effectuer des activités telles que la surveillance des frappes au clavier.

Pour cette raison, la redirection X11 est soumise par défaut aux restrictions de l'extension X11 SECURITY. Se référer à l'option ssh -Y et à la directive ForwardX11Trusted dans ssh_config(5) pour plus d'informations.

-x
Désactive la redirection X11.
-Y
Active la redirection X11 de confiance. Les redirections X11 de confiance ne sont pas soumises aux contrôles de l'extension X11 SECURITY.
-y
Envoie des informations de journalisation en utilisant le module système syslog(3). Par défaut, ces informations sont envoyées à stderr.

ssh peut obtenir des données de configuration supplémentaires à partir d'un fichier de configuration par utilisateur et d'un fichier de configuration à l'échelle du système. Le format du fichier et les options de configuration sont décrits dans ssh_config(5).

AUTHENTICATION

Le client SSH OpenSSH prend en charge le protocole SSH 2.

Les méthodes disponibles pour l'authentification sont : l'authentification basée sur GSSAPI, l'authentification basée sur l'hôte, l'authentification par clé publique, l'authentification interactive au clavier et l'authentification par mot de passe. Les méthodes d'authentification sont essayées dans l'ordre spécifié ci-dessus, bien que PreferredAuthentications puisse être utilisé pour changer l'ordre par défaut.

L'authentification basée sur l'hôte fonctionne comme suit : Si la machine à partir de laquelle l'utilisateur se connecte est listée dans /etc/hosts.equiv ou /etc/ssh/shosts.equiv sur la machine distante, l'utilisateur n'est pas root et les noms d'utilisateur sont les mêmes des deux côtés, ou si les fichiers ~/.rhosts ou ~/.shosts existent dans le répertoire personnel de l'utilisateur sur la machine distante et contiennent une ligne incluant le nom de la machine cliente et le nom de l'utilisateur sur cette machine, l'utilisateur est considéré pour la connexion. De plus, le serveur doit être capable de vérifier la clé d'hôte du client (voir la description de /etc/ssh/ssh_known_hosts et ~/.ssh/known_hosts, ci-dessous) pour que la connexion soit autorisée. Cette méthode d'authentification comble les failles de sécurité dues à l'usurpation d'IP, à l'usurpation DNS et à l'usurpation de routage. [Note à l'administrateur : /etc/hosts.equiv, ~/.rhosts, et le protocole rlogin/rsh en général, sont intrinsèquement non sécurisés et devraient être désactivés si la sécurité est souhaitée.]

L'authentification par clé publique fonctionne comme suit : Le schéma est basé sur la cryptographie à clé publique, utilisant des systèmes cryptographiques où le chiffrement et le déchiffrement sont effectués à l'aide de clés distinctes, et il est infaisable de dériver la clé de déchiffrement à partir de la clé de chiffrement. L'idée est que chaque utilisateur crée une paire de clés publique/privée à des fins d'authentification. Le serveur connaît la clé publique, et seul l'utilisateur connaît la clé privée. ssh implémente automatiquement le protocole d'authentification par clé publique, en utilisant l'un des algorithmes ECDSA, Ed25519 ou RSA.

Le fichier ~/.ssh/authorized_keys liste les clés publiques qui sont autorisées pour la connexion. Lorsque l'utilisateur se connecte, le programme ssh indique au serveur quelle paire de clés il souhaite utiliser pour l'authentification. Le client prouve qu'il a accès à la clé privée et le serveur vérifie que la clé publique correspondante est autorisée à accepter le compte.

Le serveur peut informer le client des erreurs qui ont empêché l'authentification par clé publique de réussir après que l'authentification a été complétée par une autre méthode. Celles-ci peuvent être consultées en augmentant le LogLevel à DEBUG ou plus (par exemple, en utilisant le drapeau -v).

L'utilisateur crée sa paire de clés en exécutant ssh-keygen(1). Ceci stocke la clé privée dans ~/.ssh/id_ecdsa (ECDSA), ~/.ssh/id_ecdsa_sk (ECDSA hébergé par authentificateur), ~/.ssh/id_ed25519 (Ed25519), ~/.ssh/id_ed25519_sk (Ed25519 hébergé par authentificateur), ou ~/.ssh/id_rsa (RSA) et stocke la clé publique dans ~/.ssh/id_ecdsa.pub (ECDSA), ~/.ssh/id_ecdsa_sk.pub (ECDSA hébergé par authentificateur), ~/.ssh/id_ed25519.pub (Ed25519), ~/.ssh/id_ed25519_sk.pub (Ed25519 hébergé par authentificateur), ou ~/.ssh/id_rsa.pub (RSA) dans le répertoire personnel de l'utilisateur. L'utilisateur devrait alors copier la clé publique dans ~/.ssh/authorized_keys dans son répertoire personnel sur la machine distante. Le fichier authorized_keys correspond au fichier conventionnel ~/.rhosts, et contient une clé par ligne, bien que les lignes puissent être très longues. Après cela, l'utilisateur peut se connecter sans fournir de mot de passe.

Une variation de l'authentification par clé publique est disponible sous forme d'authentification par certificat : au lieu d'un ensemble de clés publiques/privées, des certificats signés sont utilisés. Cela a l'avantage qu'une seule autorité de certification de confiance peut être utilisée à la place de nombreuses clés publiques/privées. Voir la section CERTIFICATES de ssh-keygen(1) pour plus d'informations.

La manière la plus pratique d'utiliser l'authentification par clé publique ou par certificat peut être avec un agent d'authentification. Voir ssh-agent(1) et (facultativement) la directive AddKeysToAgent dans ssh_config(5) pour plus d'informations.

L'authentification interactive au clavier fonctionne comme suit : Le serveur envoie un texte de « défi » arbitraire et demande une réponse, éventuellement plusieurs fois. Des exemples d'authentification interactive au clavier incluent l'authentification BSD (voir login.conf(5)) et PAM (certains systèmes non OpenBSD).

Enfin, si d'autres méthodes d'authentification échouent, ssh demande à l'utilisateur un mot de passe. Le mot de passe est envoyé à l'hôte distant pour vérification ; cependant, comme toutes les communications sont chiffrées, le mot de passe ne peut pas être vu par quelqu'un écoutant sur le réseau.

ssh maintient et vérifie automatiquement une base de données contenant l'identification de tous les hôtes avec lesquels il a été utilisé. Les clés d'hôte sont stockées dans ~/.ssh/known_hosts dans le répertoire personnel de l'utilisateur. De plus, le fichier /etc/ssh/ssh_known_hosts est automatiquement vérifié pour les hôtes connus.

les hôtes. Tous les nouveaux hôtes sont automatiquement ajoutés au fichier de l'utilisateur. Si l'identification d'un hôte change, ssh en avertit et désactive l'authentification par mot de passe pour empêcher l'usurpation de serveur ou les attaques de type « man-in-the-middle », qui pourraient sinon être utilisées pour contourner le chiffrement. L'option StrictHostKeyChecking peut être utilisée pour contrôler les connexions aux machines dont la clé d'hôte est inconnue ou a changé.

Lorsque l'identité de l'utilisateur a été acceptée par le serveur, le serveur exécute la commande donnée dans une session non interactive ou, si aucune commande n'a été spécifiée, se connecte à la machine et donne à l'utilisateur un shell normal en tant que session interactive. Toute communication avec la commande ou le shell distant sera automatiquement chiffrée.

Si une session interactive est demandée, ssh par défaut ne demandera un pseudo-terminal (pty) pour les sessions interactives que lorsque le client en possède un. Les options -T et -t peuvent être utilisées pour outrepasser ce comportement.

Si un pseudo-terminal a été alloué, l'utilisateur peut utiliser les caractères d'échappement mentionnés ci-dessous.

Si aucun pseudo-terminal n'a été alloué, la session est transparente et peut être utilisée pour transférer de manière fiable des données binaires. Sur la plupart des systèmes, régler le caractère d'échappement sur « none » rendra également la session transparente même si un tty est utilisé.

La session se termine lorsque la commande ou le shell sur la machine distante se termine et que toutes les connexions X11 et TCP ont été fermées.

CARACTÈRES D'ÉCHAPPEMENT

Lorsqu'un pseudo-terminal a été demandé, ssh prend en charge un certain nombre de fonctions via l'utilisation d'un caractère d'échappement.

Un seul caractère tilde peut être envoyé comme ~~ ou en faisant suivre le tilde d'un caractère autre que ceux décrits ci-dessous. Le caractère d'échappement doit toujours suivre un saut de ligne pour être interprété comme spécial. Le caractère d'échappement peut être modifié dans les fichiers de configuration à l'aide de la directive de configuration EscapeChar ou sur la ligne de commande par l'option -e.

Les échappements pris en charge (en supposant le tilde par défaut « ~ ») sont :

~.
Déconnecter.
~^Z
Mettre ssh en arrière-plan.
~#
Lister les connexions transférées.
~&
Mettre ssh en arrière-plan lors de la déconnexion en attendant que les connexions transférées / sessions X11 se terminent.
~?
Afficher une liste des caractères d'échappement.
~B
Envoyer un signal BREAK au système distant (utile uniquement si le pair le prend en charge).
~C
Ouvrir la ligne de commande. Actuellement, cela permet d'ajouter des transferts de ports à l'aide des options -L, -R et -D (voir ci-dessus). Cela permet également d'annuler les transferts de ports existants avec -KL[adresse_liaison:]port pour les transferts locaux, -KR[adresse_liaison:]port pour les transferts distants et -KD[adresse_liaison:]port pour les transferts de ports dynamiques. !commande permet à l'utilisateur d'exécuter une commande locale si l'option PermitLocalCommand est activée dans ssh_config(5). Une aide de base est disponible en utilisant l'option -h.
~R
Demander le renégociation de la clé de chiffrement de la connexion (utile uniquement si le pair le prend en charge).
~V
Diminuer la verbosité (LogLevel) lorsque des erreurs sont écrites dans stderr.
~v
Augmenter la verbosité (LogLevel) lorsque des erreurs sont écrites dans stderr.

TRANSFERT TCP

Le transfert de connexions TCP arbitraires sur un canal sécurisé peut être spécifié soit sur la ligne de commande, soit dans un fichier de configuration. Une application possible du transfert TCP est une connexion sécurisée à un serveur de messagerie ; une autre est de passer à travers les pare-feux.

Dans l'exemple ci-dessous, nous examinons le chiffrement de la communication pour un client IRC, même si le serveur IRC auquel il se connecte ne prend pas directement en charge la communication chiffrée. Cela fonctionne comme suit : l'utilisateur se connecte à l'hôte distant en utilisant ssh, en spécifiant les ports à utiliser pour transférer la connexion. Après cela, il est possible de démarrer le programme localement, et ssh chiffrera et transférera la connexion au serveur distant.

L'exemple suivant tunnelise une session IRC du client vers un serveur IRC à « server.example.com », rejoignant le canal « #users », avec le pseudo « pinky », en utilisant le port IRC standard, 6667 :

$ ssh -f -L 6667:localhost:6667 server.example.com sleep 10
$ irc -c '#users' pinky IRC/127.0.0.1

L'option -f met ssh en arrière-plan et la commande distante « sleep 10 » est spécifiée pour laisser un temps (10 secondes, dans l'exemple) pour démarrer le programme qui va utiliser le tunnel. Si aucune connexion n'est établie dans le délai spécifié, ssh se terminera.

TRANSFERT X11

Si la variable ForwardX11 est définie sur « yes » (ou voir la description des options -X, -x et -Y ci-dessus) et que l'utilisateur utilise X11 (la variable d'environnement DISPLAY est définie), la connexion au serveur d'affichage X11 est automatiquement transférée côté distant de telle sorte que tout programme X11 démarré depuis le shell (ou la commande) passera par le canal chiffré, et la connexion au serveur X réel sera effectuée depuis la machine locale. L'utilisateur ne devrait pas définir manuellement DISPLAY. Le transfert des connexions X11 peut être configuré sur la ligne de commande ou dans les fichiers de configuration.

La valeur DISPLAY définie par ssh pointera vers la machine serveur, mais avec un numéro d'affichage supérieur à zéro. C'est normal, et cela se produit parce que ssh crée un serveur X « proxy » sur la machine serveur pour transférer les connexions sur le canal chiffré.

ssh mettra également en place des données d'authentification Xauthority sur la machine serveur. À cette fin, il générera un cookie d'authentification aléatoire, le stockera dans Xauthority sur le serveur, et vérifiera que toute connexion transférée porte ce cookie et le remplacera par le cookie réel à l'ouverture de la connexion. Le cookie d'authentification réel n'est jamais envoyé à la machine serveur (et aucun cookie n'est envoyé en clair).

Si la variable ForwardAgent est définie sur « yes » (ou voir la description des options -A et -a ci-dessus) et que l'utilisateur utilise un agent d'authentification, la connexion à l'agent est automatiquement transférée côté distant.

VÉRIFICATION DES CLÉS D'HÔTE

Lors de la connexion à un serveur pour la première fois, une empreinte (fingerprint) de la clé publique du serveur est présentée à l'utilisateur (sauf si l'option StrictHostKeyChecking a été désactivée). Les empreintes peuvent être déterminées à l'aide de ssh-keygen(1) :

$ ssh-keygen -l -f /etc/ssh/ssh_host_rsa_key

Si l'empreinte est déjà connue, elle peut être comparée et la clé peut être acceptée ou rejetée. Si seules des empreintes obsolètes (MD5) sont disponibles pour le serveur, l'option -E de ssh-keygen(1) peut être utilisée pour abaisser l'algorithme d'empreinte afin de correspondre.

En raison de la difficulté de comparer les clés d'hôte en se basant uniquement sur les chaînes d'empreintes, il existe également une prise en charge pour comparer visuellement les clés d'hôte, en utilisant des « random art ». En définissant l'option VisualHostKey sur « yes », un petit graphique ASCII est affiché à chaque connexion à un serveur, que la session elle-même soit interactive ou non. En mémorisant le motif qu'un serveur connu produit, un utilisateur peut facilement découvrir que la clé d'hôte a changé lorsqu'un motif complètement différent est affiché. Comme ces motifs ne sont cependant pas sans ambiguïté, un motif qui ressemble au motif mémorisé ne donne qu'une bonne probabilité que la clé d'hôte soit la même, pas une preuve garantie.

Pour obtenir une liste des empreintes ainsi que leur « random art » pour tous les hôtes connus, la ligne de commande suivante peut être utilisée :

$ ssh-keygen -lv -f ~/.ssh/known_hosts

Si l'empreinte est inconnue, une méthode de vérification alternative est disponible : les empreintes SSH vérifiées par DNS. Un enregistrement de ressource (RR) supplémentaire, SSHFP, est ajouté à un fichier de zone et le client de connexion est capable de faire correspondre l'empreinte avec celle de la clé présentée.

Dans cet exemple, nous connectons un client à un serveur, « host.example.com ». Les enregistrements de ressources SSHFP doivent d'abord être ajoutés au fichier de zone pour host.example.com :

$ ssh-keygen -r host.example.com.

Les lignes de sortie devront être ajoutées au fichier de zone. Pour vérifier que la zone répond aux requêtes d'empreinte :

$ dig -t SSHFP host.example.com

Enfin, le client se connecte :

$ ssh -o "VerifyHostKeyDNS ask" host.example.com
[...]
Matching host key fingerprint found in DNS.
Are you sure you want to continue connecting (yes/no)?

"Pp">Voir l'option VerifyHostKeyDNS dans ssh_config(5) pour plus d'informations.

RÉSEAUX PRIVÉS VIRTUELS BASÉS SUR SSH

ssh contient un support pour le tunnel VPN (Virtual Private Network) utilisant le pseudo-périphérique réseau tun(4), permettant de joindre deux réseaux de manière sécurisée. L'option de configuration PermitTunnel de sshd_config(5) contrôle si le serveur supporte cela, et à quel niveau (trafic de couche 2 ou 3).

L'exemple suivant connecterait le réseau client 10.0.50.0/24 au réseau distant 10.0.99.0/24 en utilisant une connexion point à point de 10.1.1.1 à 10.1.1.2, à condition que le serveur SSH fonctionnant sur la passerelle vers le réseau distant, à 192.168.1.15, l'autorise.

Côté client :

# ssh -f -w 0:1 192.168.1.15 true
# ifconfig tun0 10.1.1.1 10.1.1.2 netmask 255.255.255.252
# route add 10.0.99.0/24 10.1.1.2

Côté serveur :

# ifconfig tun1 10.1.1.2 10.1.1.1 netmask 255.255.255.252
# route add 10.0.50.0/24 10.1.1.1

L'accès client peut être plus finement contrôlé via le fichier /root/.ssh/authorized_keys (voir ci-dessous) et l'option serveur PermitRootLogin. L'entrée suivante autoriserait les connexions sur le périphérique tun(4) 1 pour l'utilisateur « jane » et sur le périphérique tun 2 pour l'utilisateur « john », si PermitRootLogin est défini sur « forced-commands-only » :

tunnel="1",command="sh /etc/netstart tun1" ssh-rsa ... jane
tunnel="2",command="sh /etc/netstart tun2" ssh-rsa ... john

Étant donné qu'une configuration basée sur SSH entraîne une charge considérable, elle peut être plus adaptée aux configurations temporaires, comme pour les VPN sans fil. Les VPN plus permanents sont mieux assurés par des outils tels que ipsecctl(8) et isakmpd(8).

ENVIRONNEMENT

ssh définit normalement les variables d'environnement suivantes :

DISPLAY
La variable DISPLAY indique l'emplacement du serveur X11. Elle est automatiquement définie par ssh pour pointer vers une valeur de la forme « hostname:n », où « hostname » indique la machine où le shell s'exécute, et « n » est un entier ≥ 1. ssh utilise cette valeur spéciale pour transférer les connexions X11 sur le canal sécurisé. L'utilisateur ne devrait normalement pas définir DISPLAY explicitement, car cela rendrait la connexion X11 non sécurisée (et obligerait l'utilisateur à copier manuellement tous les cookies d'autorisation requis).
HOME
Définit le chemin du répertoire personnel de l'utilisateur.
LOGNAME
Synonyme de USER ; défini pour la compatibilité avec les systèmes qui utilisent cette variable.
MAIL
Définit le chemin de la boîte aux lettres de l'utilisateur.
PATH
Définit le PATH par défaut, tel que spécifié lors de la compilation de ssh.
SSH_ASKPASS
Si ssh a besoin d'une phrase secrète, il lira la phrase secrète depuis le terminal courant s'il a été lancé depuis un terminal. Si ssh n'a pas de terminal associé mais que DISPLAY et SSH_ASKPASS sont définis, il exécutera le programme spécifié par SSH_ASKPASS et ouvrira une fenêtre X11 pour lire la phrase secrète. Ceci est particulièrement utile lors de l'appel de ssh depuis un .xsession ou un script similaire. (Notez que sur certaines machines, il peut être nécessaire de rediriger l'entrée depuis /dev/null pour que cela fonctionne.)
SSH_ASKPASS_REQUIRE
Permet un contrôle supplémentaire sur l'utilisation d'un programme askpass. Si cette variable est définie sur « never », alors ssh ne tentera jamais de l'utiliser. Si elle est définie sur « prefer », alors ssh préférera utiliser le programme askpass au lieu du TTY lors de la demande de mots de passe. Enfin, si la variable est définie sur « force », alors le programme askpass sera utilisé pour toute saisie de phrase secrète, que DISPLAY soit défini ou non.
SSH_AUTH_SOCK
Identifie le chemin d'un socket de domaine UNIX utilisé pour communiquer avec l'agent.
SSH_CONNECTION
Identifie les extrémités client et serveur de la connexion. La variable contient quatre valeurs séparées par des espaces : l'adresse IP du client, le numéro de port du client, l'adresse IP du serveur et le numéro de port du serveur.
SSH_ORIGINAL_COMMAND
Cette variable contient la ligne de commande d'origine si une commande forcée est exécutée. Elle peut être utilisée pour extraire les arguments d'origine.
SSH_TTY
Ceci est défini sur le nom du tty (chemin vers le périphérique) associé au shell ou à la commande courante. Si la session courante n'a pas de tty, cette variable n'est pas définie.
SSH_TUNNEL
Optionnellement définie par sshd(8) pour contenir les noms d'interface attribués si le transfert de tunnel a été demandé par le client.
SSH_USER_AUTH
Optionnellement définie par sshd(8), cette variable peut contenir un chemin vers un fichier listant les méthodes d'authentification utilisées avec succès lors de l'établissement de la session, y compris les clés publiques qui ont été utilisées.
TZ
Cette variable est définie pour indiquer le fuseau horaire actuel s'il a été défini au démarrage du démon (c'est-à-dire que le démon transmet la valeur aux nouvelles connexions).
USER
Définit le nom de l'utilisateur qui se connecte.

De plus, ssh lit ~/.ssh/environment, et ajoute des lignes du format « VARNAME=valeur » à l'environnement si le fichier existe et que les utilisateurs sont autorisés à modifier leur environnement. Pour plus d'informations, voir l'option PermitUserEnvironment dans sshd_config(5).

FICHIERS

~/.rhosts
Ce fichier est utilisé pour l'authentification basée sur l'hôte (voir ci-dessus). Sur certaines machines, ce fichier peut devoir être lisible par tous si le répertoire personnel de l'utilisateur est sur une partition NFS, car sshd(8) le lit en tant que root. De plus, ce fichier doit appartenir à l'utilisateur et ne doit avoir aucune permission d'écriture pour quiconque d'autre. La permission recommandée pour la plupart des machines est lecture/écriture pour l'utilisateur, et non accessible par les autres.
~/.shosts
Ce fichier est utilisé exactement de la même manière que .rhosts, mais permet l'authentification basée sur l'hôte sans autoriser la connexion avec rlogin/rsh.
~/.ssh/
Ce répertoire est l'emplacement par défaut pour toutes les configurations et informations d'authentification spécifiques à l'utilisateur. Il n'y a pas d'exigence générale de garder secret tout le contenu de ce répertoire, mais les permissions recommandées sont lecture/écriture/exécution pour l'utilisateur, et non accessibles par les autres.
~/.ssh/authorized_keys
Liste les clés publiques (ECDSA, Ed25519, RSA) qui peuvent être utilisées pour se connecter en tant que cet utilisateur. Le format de ce fichier est décrit dans la page de manuel de sshd(8). Ce fichier n'est pas hautement sensible, mais les permissions recommandées sont lecture/écriture pour l'utilisateur, et non accessibles par les autres.
~/.ssh/config
C'est le fichier de configuration par utilisateur. Le format du fichier et les options de configuration sont décrits dans ssh_config(5). En raison du potentiel d'abus, ce fichier doit avoir des permissions strictes : lecture/écriture pour l'utilisateur, et non accessible en écriture par les autres.
~/.ssh/environment
