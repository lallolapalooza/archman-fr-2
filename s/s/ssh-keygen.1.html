NOM

ssh-keygen — Utilitaire de clé d'authentification OpenSSH

SYNTAXE

ssh-keygen -c [-a rounds] [-C comment] [-f keyfile] [-P passphrase]

ssh-keygen -l [-v] [-E fingerprint_hash] [-f input_keyfile]

DESCRIPTION

ssh-keygen est un outil OpenSSH qui génère, gère et convertit les clés d'authentification pour la connexion à un serveur SSH.

Il peut être utilisé pour créer de nouvelles paires de clés publiques/privées, modifier le commentaire associé à une clé, changer la phrase secrète d'une clé, supprimer une clé, afficher les empreintes de clés et les clés publiques, et ajouter ou supprimer des hôtes de la liste known_hosts.

Les options disponibles sont les suivantes :

-A
Crée les fichiers de clés par défaut (id_rsa, id_ecdsa, id_ed25519) s'ils n'existent pas.
-a rounds
Augmente le nombre de tours utilisés par kdf(1) lors du chiffrement de la clé privée. Une valeur plus élevée rend le déchiffrement plus lent, mais rend la clé plus résistante aux attaques par force brute.
-b bits
Spécifie le nombre de bits dans la clé. La valeur par défaut est 3072 pour RSA, 256 pour ECDSA, et 256 pour Ed25519.
-C comment
Ajoute un commentaire à la clé publique. Ce commentaire est généralement utilisé pour identifier la clé.
-c
Change le commentaire d'une clé existante.
-D pkcs11
Extrait la clé publique d'un jeton PKCS#11. L'argument pkcs11 est le chemin vers la bibliothèque partagée du fournisseur PKCS#11.
-e
Affiche la clé publique au format spécifié par -m. Par défaut, le format est PEM.
-E fingerprint_hash
Spécifie l'algorithme de hachage à utiliser pour calculer l'empreinte digitale de la clé. Les valeurs possibles sont md5 et sha256.
-f output_keyfile
Spécifie le nom du fichier de sortie pour la clé publique et/ou privée. Le fichier de clé privée sera nommé output_keyfile et le fichier de clé publique sera nommé output_keyfile.pub. Si l'option n'est pas spécifiée, les valeurs par défaut sont utilisées.
-F hostname
Recherche une entrée pour l'hôte spécifié dans le fichier known_hosts.
-H
Crée des empreintes digitales hachées pour toutes les entrées du fichier known_hosts. Cela empêche les attaques de type "man-in-the-middle" en rendant plus difficile la falsification du fichier known_hosts.
-i
Affiche la clé publique au format spécifié par -m. Par défaut, le format est OpenSSH.
-I certificate_identity
Spécifie l'identité de la clé du signataire à utiliser lors de la signature d'un certificat.
-k
Génère une nouvelle liste de révocation de clés (KRL) à partir des certificats et/ou des clés spécifiés.
-K
Enregistre les certificats PKCS#11 sur le système.
-l
Affiche l'empreinte digitale de la clé publique.
-L
Affiche toutes les informations sur un certificat.
-m format
Spécifie le format de la clé à afficher ou convertir. Les formats possibles sont RFC4716, PEM, et OpenSSH
-M generate | screen
Traite les données de sortie d'une commande ssh-keygen à l'aide de l'algorithme de compression Muldis. La sous-commande generate génère une sortie compressée, tandis que screen décompresse la sortie.
-N new_passphrase
Spécifie la nouvelle phrase secrète pour une clé.
-O option
Spécifie des options supplémentaires pour la commande ssh-keygen. Les options disponibles dépendent de la sous-commande utilisée.
-p
Change la phrase secrète d'une clé privée existante.
-P old_passphrase
Spécifie l'ancienne phrase secrète d'une clé privée existante lors de son changement.
-Q
Interroge un fichier KRL pour vérifier si une clé est révoquée.
-q
Mode silencieux. Ne demande pas la phrase secrète lors de la création d'une nouvelle clé.
-R hostname
Supprime toutes les entrées pour l'hôte spécifié du fichier known_hosts.
-r
Affiche la clé publique au format sshfp.
-s ca_key
Spécifie la clé du certificat d'autorité (CA) à utiliser lors de la signature d'un certificat.
-t ecdsa | ecdsa-sk | ed25519 | ed25519-sk | rsa
Spécifie le type de clé à créer. Les types pris en charge sont rsa, ecdsa, ecdsa-sk, ed25519 et ed25519-sk. Les clés de type -sk sont des clés FIDO authenticator.
-u
Ajoute une KRL aux certificats et/ou clés spécifiés.
-v
Mode verbeux. Affiche plus d'informations sur le processus.
-V validity_interval
Spécifie l'intervalle de validité d'un certificat signé.
-w provider
Spécifie le fournisseur PKCS#11 à utiliser.
-Y find-principals | match-principals | check-novalidate | sign | verify
Effectue une opération liée aux certificats signés par clé.
-Z cipher
Spécifie l'algorithme de chiffrement à utiliser pour chiffrer la clé privée.

EXEMPLES

Générer une paire de clés RSA 4096 bits avec un commentaire :

ssh-keygen -t rsa -b 4096 -C "votre_email@example.com"

Générer une paire de clés Ed25519 :

ssh-keygen -t ed25519

Changer la phrase secrète d'une clé privée existante :

ssh-keygen -p -f ~/.ssh/id_ed25519

Afficher l'empreinte digitale d'une clé publique :

ssh-keygen -lf ~/.ssh/id_ed25519.pub

Convertir une clé privée OpenSSH au format PEM :

ssh-keygen -p -m PEM -f ~/.ssh/id_rsa

Ajouter une clé publique à un serveur distant sans phrase secrète (utilisé dans les scripts) :

ssh-copy-id -f -i ~/.ssh/id_ed25519.pub utilisateur@serveur_distant

Supprimer une clé d'un serveur distant :

ssh-keygen -R serveur_distant

DESCRIPTION

ssh-keygen génère, gère et convertit des clés d'authentification pour ssh(1). ssh-keygen peut créer des clés pour utilisation par le protocole SSH version 2.

Le type de clé à générer est spécifié avec l'option -t. S'il est appelé sans aucun argument, ssh-keygen générera une clé Ed25519.

ssh-keygen est également utilisé pour générer des groupes à utiliser dans l'échange de groupes Diffie-Hellman (DH-GEX). Voir la section GÉNÉRATION DE MODULI pour les détails.

Enfin, ssh-keygen peut être utilisé pour générer et mettre à jour des listes de révocation de clés (KRL), et pour tester si des clés données ont été révoquées par une KRL. Voir la section LISTES DE RÉVOCATION DE CLÉS pour les détails.

Normalement, chaque utilisateur souhaitant utiliser SSH avec l'authentification par clé publique exécute cette commande une fois pour créer la clé d'authentification dans ~/.ssh/id_ecdsa, ~/.ssh/id_ecdsa_sk, ~/.ssh/id_ed25519, ~/.ssh/id_ed25519_sk ou ~/.ssh/id_rsa. De plus, l'administrateur système peut l'utiliser pour générer des clés d'hôte, comme vu dans /etc/rc.

Normalement, ce programme génère la clé et demande un fichier dans lequel stocker la clé privée. La clé publique est stockée dans un fichier du même nom auquel est ajoutée l'extension ".pub". Le programme demande également une phrase secrète. La phrase secrète peut être vide pour indiquer aucune phrase secrète (les clés d'hôte doivent avoir une phrase secrète vide), ou elle peut être une chaîne de longueur arbitraire. Une phrase secrète est similaire à un mot de passe, sauf qu'elle peut être une phrase avec une série de mots, de ponctuations, de nombres, d'espaces ou toute chaîne de caractères que vous souhaitez. De bonnes phrases secrètes font 10 à 30 caractères de long, ne sont pas des phrases simples ou facilement devinables (la prose anglaise n'a que 1 à 2 bits d'entropie par caractère et fournit de très mauvaises phrases secrètes), et contiennent un mélange de lettres majuscules et minuscules, de chiffres et de caractères non alphanumériques. La phrase secrète peut être modifiée ultérieurement en utilisant l'option -p.

Il n'y a aucun moyen de récupérer une phrase secrète perdue. Si la phrase secrète est perdue ou oubliée, une nouvelle clé doit être générée et la clé publique correspondante copiée sur d'autres machines.

ssh-keygen écrira par défaut les clés dans un format spécifique à OpenSSH. Ce format est préférable car il offre une meilleure protection pour les clés au repos ainsi que la possibilité de stocker des commentaires de clé dans le fichier de clé privée lui-même. Le commentaire de clé peut être utile pour identifier la clé. Le commentaire est initialisé à "user@host" lors de la création de la clé, mais peut être modifié en utilisant l'option -c.

Il est toujours possible pour ssh-keygen d'écrire les clés privées au format PEM précédemment utilisé en utilisant le drapeau -m. Cela peut être utilisé lors de la génération de nouvelles clés, et les clés existantes au nouveau format peuvent être converties en utilisant cette option conjointement avec le drapeau -p (changer la phrase secrète).

Après la génération d'une clé, ssh-keygen demandera où les clés doivent être placées pour être activées.

Les options sont les suivantes :

-A
Génère des clés d'hôte de tous les types de clés par défaut (rsa, ecdsa, et ed25519) si elles n'existent pas déjà. Les clés d'hôte sont générées avec le chemin de fichier de clé par défaut, une phrase secrète vide, le nombre de bits par défaut pour le type de clé et le commentaire par défaut. Si -f a également été spécifié, son argument est utilisé comme préfixe du chemin par défaut pour les fichiers de clé d'hôte résultants. Ceci est utilisé par /etc/rc pour générer de nouvelles clés d'hôte.
-a tours
Lors de la sauvegarde d'une clé privée, cette option spécifie le nombre de tours KDF (key derivation function, actuellement bcrypt_pbkdf(3)) utilisés. Des nombres plus élevés entraînent une vérification de phrase secrète plus lente et une résistance accrue aux attaques par force brute (en cas de vol des clés). Le défaut est de 16 tours.
-B
Affiche le résumé "bubblebabble" du fichier de clé privée ou publique spécifié.
-b bits
Spécifie le nombre de bits dans la clé à créer. Pour les clés RSA, la taille minimale est de 1024 bits et la valeur par défaut est de 3072 bits. En général, 3072 bits est considéré comme suffisant. Pour les clés ECDSA, le drapeau -b détermine la longueur de la clé en sélectionnant parmi trois tailles de courbes elliptiques : 256, 384 ou 521 bits. Tenter d'utiliser des longueurs de bits autres que ces trois valeurs pour les clés ECDSA échouera. Les clés ECDSA-SK, Ed25519 et Ed25519-SK ont une longueur fixe et le drapeau -b sera ignoré.
-C commentaire
Fournit un nouveau commentaire.
-c
Demande la modification du commentaire dans les fichiers de clé privée et publique. Le programme demandera le fichier contenant les clés privées, la phrase secrète si la clé en a une, et le nouveau commentaire.
-D pkcs11
Télécharge les clés publiques fournies par la bibliothèque partagée PKCS#11 pkcs11. Lorsqu'il est utilisé en combinaison avec -s, cette option indique qu'une clé CA réside dans un jeton PKCS#11 (voir la section CERTIFICATS pour les détails).
-E empreinte_hachage
Spécifie l'algorithme de hachage utilisé lors de l'affichage des empreintes de clés. Les options valides sont : "md5" et "sha256". La valeur par défaut est "sha256".
-e
Cette option lira un fichier de clé OpenSSH privée ou publique et affichera sur stdout une clé publique dans l'un des formats spécifiés par l'option -m. Le format d'exportation par défaut est "RFC4716". Cette option permet d'exporter les clés OpenSSH pour une utilisation par d'autres programmes, y compris plusieurs implémentations SSH commerciales.
-F nom_hote | [nom_hote]:port
Recherche le nom_hote spécifié (avec un numéro de port optionnel) dans un fichier known_hosts, en listant toutes les occurrences trouvées. Cette option est utile pour trouver des noms d'hôtes ou des adresses hachés et peut également être utilisée en conjonction avec l'option -H pour afficher les clés trouvées dans un format haché.
-f nom_fichier
Spécifie le nom du fichier de clé.
-g
Utilise le format DNS générique lors de l'affichage des enregistrements de ressource d'empreinte à l'aide de la commande -r.
-H
Hache un fichier known_hosts. Ceci remplace tous les noms d'hôtes et adresses par des représentations hachées dans le fichier spécifié ; le contenu original est déplacé vers un fichier avec une extension .old. Ces hachages peuvent être utilisés normalement par ssh et sshd, mais ils ne révèlent pas d'informations identificatrices en cas de divulgation du contenu du fichier. Cette option ne modifiera pas les noms d'hôtes hachés existants et est donc sans danger à utiliser sur des fichiers qui mélangent des noms hachés et non hachés.
-h
Lors de la signature d'une clé, crée un certificat d'hôte au lieu d'un certificat utilisateur. Voir la section CERTIFICATS pour les détails.
-I identité_certificat
Spécifie l'identité de la clé lors de la signature d'une clé publique. Voir la section CERTIFICATS pour les détails.
-i
Cette option lira une clé privée (ou publique) non chiffrée dans le format spécifié par l'option -m et affichera une clé privée (ou publique) compatible OpenSSH sur stdout. Cette option permet d'importer des clés d'autres logiciels, y compris plusieurs implémentations SSH commerciales. Le format d'importation par défaut est "RFC4716".
-K
Télécharge les clés résidentes d'un authentificateur FIDO. Des fichiers de clé publique et privée seront écrits dans le répertoire courant pour chaque clé téléchargée. Si plusieurs authentificateurs FIDO sont connectés, les clés seront téléchargées depuis le premier authentificateur touché. Voir la section AUTHENTIFICATEUR FIDO pour plus d'informations.
-k
Génère un fichier KRL. Dans ce mode, ssh-keygen générera un fichier KRL à l'emplacement spécifié via le drapeau -f qui révoque chaque clé ou certificat présenté en ligne de commande. Les clés/certificats à révoquer peuvent être spécifiés par fichier de clé publique ou en utilisant le format décrit dans la section LISTES DE RÉVOCATION DE CLÉS.
-L
Affiche le contenu d'un ou plusieurs certificats.
-l
Affiche l'empreinte d'un fichier de clé publique spécifié. ssh-keygen essaiera de trouver le fichier de clé publique correspondant et affichera son empreinte. Si combiné avec -v, une représentation visuelle en art ASCII de la clé est fournie avec l'empreinte.
-M generate
Génère des paramètres candidats pour l'échange de groupe Diffie-Hellman (DH-GEX) pour une utilisation éventuelle par les méthodes d'échange de clé 'diffie-hellman-group-exchange-*'. Les nombres générés par cette opération doivent être filtrés davantage avant utilisation. Voir la section GÉNÉRATION DE MODULI pour plus d'informations.
...
-M screen
Écran des paramètres candidats pour l'échange de groupe Diffie-Hellman. Cela acceptera une liste de nombres candidats et testera qu'il s'agit de nombres premiers sûrs (Sophie Germain) avec des générateurs de groupe acceptables. Les résultats de cette opération peuvent être ajoutés au fichier /etc/ssh/moduli. Voir la section GÉNÉRATION DE MODULI pour plus d'informations.
-m key_format
Spécifie un format de clé pour la génération de clés, les options de conversion d'importation (-i) et d'exportation (-e), et l'opération de changement de phrase de passe (-p). Cette dernière peut être utilisée pour convertir entre les formats de clé privée OpenSSH et les formats de clé privée PEM. Les formats de clé pris en charge sont : “RFC4716” (clé publique ou privée RFC 4716/SSH2), “PKCS8” (clé publique ou privée PKCS8) ou “PEM” (clé publique PEM). Par défaut, OpenSSH écrira les clés privées nouvellement générées dans son propre format, mais lors de la conversion de clés publiques pour l'exportation, le format par défaut est “RFC4716”. Définir un format de “PEM” lors de la génération ou de la mise à jour d'un type de clé privée pris en charge entraînera le stockage de la clé dans le format hérité de clé privée PEM.
-N new_passphrase
Fournit la nouvelle phrase de passe.
-n principals
Spécifie un ou plusieurs principaux (noms d'utilisateur ou d'hôtes) à inclure dans un certificat lors de la signature d'une clé. Plusieurs principaux peuvent être spécifiés, séparés par des virgules. Voir la section CERTIFICATS pour les détails.
-O option
Spécifie une option clé/valeur. Celles-ci sont spécifiques à l'opération pour laquelle ssh-keygen a été invité à effectuer.

Lors de la signature de certificats, l'une des options listées dans la section CERTIFICATS peut être spécifiée ici.

Lors de la génération ou du filtrage de moduli, l'une des options listées dans la section GÉNÉRATION DE MODULI peut être spécifiée.

Lors de la génération de clés sauvegardées par des authentificateurs FIDO, les options listées dans la section AUTHENTIFICATEUR FIDO peuvent être spécifiées.

Lors de l'exécution d'options liées à la signature à l'aide du drapeau -Y, les options suivantes sont acceptées :

hashalg=algorithm
Sélectionne l'algorithme de hachage à utiliser pour hacher le message à signer. Les algorithmes valides sont “sha256” et “sha512.” La valeur par défaut est “sha512.”
print-pubkey
Affiche la clé publique complète sur la sortie standard après vérification de la signature.
verify-time=timestamp
Spécifie une heure à utiliser lors de la validation des signatures au lieu de l'heure actuelle. L'heure peut être spécifiée sous forme de date ou d'heure aux formats AAAAMMJJ[Z] ou AAAAMMJJHHMM[SS][Z]. Les dates et heures seront interprétées dans le fuseau horaire système actuel, sauf si elles sont suffixées par un caractère Z, ce qui entraîne leur interprétation dans le fuseau horaire UTC.

Lors de la génération d'enregistrements DNS SSHFP à partir de clés publiques à l'aide du drapeau -r, les options suivantes sont acceptées :

hashalg=algorithm
Sélectionne un algorithme de hachage à utiliser lors de l'impression des enregistrements SSHFP à l'aide du drapeau -D. Les algorithmes valides sont “sha1” et “sha256”. Par défaut, les deux sont imprimés.

L'option -O peut être spécifiée plusieurs fois.

-P passphrase
Fournit l'ancienne phrase de passe.
-p
Demande le changement de la phrase de passe d'un fichier de clé privée au lieu de créer une nouvelle clé privée. Le programme demandera le fichier contenant la clé privée, l'ancienne phrase de passe et deux fois la nouvelle phrase de passe.
-Q
Teste si les clés ont été révoquées dans une KRL. Si l'option -l est également spécifiée, le contenu de la KRL sera affiché.
-q
Fait taire ssh-keygen.
-R hostname | [hostname]:port
Supprime toutes les clés appartenant à l'hostname spécifié (avec un numéro de port optionnel) d'un fichier known_hosts. Cette option est utile pour supprimer les hôtes hachés (voir l'option -H ci-dessus).
-r hostname
Affiche l'enregistrement de ressource d'empreinte SSHFP nommé hostname pour le fichier de clé publique spécifié.
-s ca_key
Certifie (signe) une clé publique en utilisant la clé CA spécifiée. Voir la section CERTIFICATS pour les détails.

Lors de la génération d'une KRL, -s spécifie un chemin vers un fichier de clé publique CA utilisé pour révoquer les certificats directement par ID de clé ou numéro de série. Voir la section LISTES DE RÉVOCATION DE CLÉS pour les détails.

-t ecdsa | ecdsa-sk | ed25519 | ed25519-sk | rsa
Spécifie le type de clé à créer. Les valeurs possibles sont “ecdsa”, “ecdsa-sk”, “ed25519 (par défaut), ” “ed25519-sk”, ou “rsa”.

Ce drapeau peut également être utilisé pour spécifier le type de signature souhaité lors de la signature de certificats à l'aide d'une clé CA RSA. Les variantes de signature RSA disponibles sont “ssh-rsa” (signatures SHA1, déconseillé), “rsa-sha2-256”, et “rsa-sha2-512” (par défaut pour les clés RSA).

-U
Lorsqu'il est utilisé en combinaison avec -s ou -Y sign, cette option indique qu'une clé CA réside dans un ssh-agent(1). Voir la section CERTIFICATS pour plus d'informations.
-u
Met à jour une KRL. Lorsqu'il est spécifié avec -k, les clés listées via la ligne de commande sont ajoutées à la KRL existante plutôt qu'à la création d'une nouvelle KRL.
-V validity_interval
Spécifie un intervalle de validité lors de la signature d'un certificat. Un intervalle de validité peut consister en un seul moment, indiquant que le certificat est valide à partir de maintenant et expire à ce moment-là, ou peut consister en deux moments séparés par un deux-points pour indiquer un intervalle de temps explicite.

L'heure de début peut être spécifiée comme suit :

  • La chaîne “always” pour indiquer que le certificat n'a pas d'heure de début spécifiée.
  • Une date ou une heure dans le fuseau horaire système au format AAAAMMJJ ou AAAAMMJJHHMM[SS].
  • Une date ou une heure dans le fuseau horaire UTC au format AAAA MMJJZ ou AAAAMMJJHHMM[SS]Z.
  • Un temps relatif avant l'heure système actuelle consistant en un signe moins suivi d'un intervalle dans le format décrit dans la section FORMATS HORAIRES de sshd_config(5).
  • Des secondes brutes depuis l'époque (1er janvier 1970 00:00:00 UTC) sous forme de nombre hexadécimal commençant par “0x”.

L'heure de fin peut être spécifiée de manière similaire à l'heure de début :

  • La chaîne “forever” pour indiquer que le certificat n'a pas d'heure de fin spécifiée.
  • Une date ou une heure dans le fuseau horaire système au format AAAA MMJJ ou AAAAMMJJHHMM[SS].
  • Une date ou une heure dans le fuseau horaire UTC au format AAAAMMJJZ ou AAAAMMJJHHMM[SS]Z.
  • Un temps relatif après l'heure système actuelle consistant en un signe plus suivi d'un intervalle dans le format décrit dans la section FORMATS HORAIRES de sshd_config(5).
  • Des secondes brutes depuis l'époque (1er janvier 1970 00:00:00 UTC) sous forme de nombre hexadécimal commençant par “0x”.

Par exemple :

+52w1d
Valide à partir de maintenant jusqu'à 52 semaines et un jour à partir de maintenant.
-4w:+4w
Valide à partir d'il y a quatre semaines jusqu'à dans quatre semaines.
20100101123000:20110101123000
Valide de 12h30 le 1er janvier 2010 à 12h30 le 1er janvier 2011.
20100101123000Z:20110101123000Z
Similaire, mais interprété dans le fuseau horaire UTC plutôt que dans le fuseau horaire système.
-1d:20110101
Valide à partir de hier jusqu'à minuit le 1er janvier 2011.
0x1:0x2000000000
Valide d'environ début 1970 à mai 2033.
-1m:forever
Valide depuis une minute et n'expirant jamais.
-v
Mode verbeux. Fait imprimer des messages de débogage sur sa progression par ssh-keygen. Ceci est utile pour le débogage de la génération de moduli. Plusieurs options -v augmentent la verbosité. Le maximum est 3.
ref="#w">-w fournisseur
Spécifie un chemin vers une bibliothèque qui sera utilisée lors de la création de clés hébergées par l'authentificateur FIDO, remplaçant l'utilisation par défaut du support interne USB HID.
-Y find-principals
Trouve le ou les principaux associés à la clé publique d'une signature, fournie à l'aide de l'option -s dans un fichier de signataires autorisés fourni à l'aide de l'option -f. Le format du fichier de signataires autorisés est documenté dans la section SIGNATAIRES AUTORISÉS ci-dessous. Si un ou plusieurs principaux correspondants sont trouvés, ils sont renvoyés sur la sortie standard.
-Y match-principals
Trouve les principaux correspondant au nom du principal fourni à l'aide de l'option -I dans le fichier de signataires autorisés spécifié à l'aide de l'option -f. Si un ou plusieurs principaux correspondants sont trouvés, ils sont renvoyés sur la sortie standard.
-Y check-novalidate
Vérifie qu'une signature générée à l'aide de ssh-keygen -Y sign a une structure valide. Cela ne valide pas si une signature provient d'un signataire autorisé. Lors du test d'une signature, ssh-keygen accepte un message sur l'entrée standard et un espace de noms de signature à l'aide de -n. Un fichier contenant la signature correspondante doit également être fourni à l'aide de l'option -s. Le test réussi de la signature est signalé par le renvoi d'un statut de sortie nul par ssh-keygen.
-Y sign
Signe cryptographiquement un fichier ou des données à l'aide d'une clé SSH. Lors de la signature, ssh-keygen accepte zéro ou plusieurs fichiers à signer en ligne de commande - si aucun fichier n'est spécifié, ssh-keygen signera les données présentées sur l'entrée standard. Les signatures sont écrites dans le chemin du fichier d'entrée avec “.sig” ajouté, ou sur la sortie standard si le message à signer a été lu depuis l'entrée standard.

La clé utilisée pour la signature est spécifiée à l'aide de l'option -f et peut faire référence soit à une clé privée, soit à une clé publique dont la partie privée est disponible via ssh-agent(1). Un espace de noms de signature supplémentaire, utilisé pour éviter la confusion des signatures entre différents domaines d'utilisation (par exemple, signature de fichiers vs signature d'e-mails), doit être fourni via l'option -n. Les espaces de noms sont des chaînes de caractères arbitraires et peuvent inclure : “file” pour la signature de fichiers, “email” pour la signature d'e-mails. Pour des utilisations personnalisées, il est recommandé d'utiliser des noms suivant un modèle NAMESPACE@YOUR.DOMAIN pour générer des espaces de noms sans ambiguïté.

-Y verify
Demande de vérifier une signature générée à l'aide de ssh-keygen -Y sign comme décrit ci-dessus. Lors de la vérification d'une signature, ssh-keygen accepte un message sur l'entrée standard et un espace de noms de signature à l'aide de -n. Un fichier contenant la signature correspondante doit également être fourni à l'aide de l'option -s, ainsi que l'identité du signataire à l'aide de -I et une liste de signataires autorisés via l'option -f. Le format du fichier de signataires autorisés est documenté dans la section SIGNATAIRES AUTORISÉS ci-dessous. Un fichier contenant les clés révoquées peut être passé à l'aide de l'option -r. Le fichier de révocation peut être un KRL ou une liste de clés publiques une par ligne. La vérification réussie par un signataire autorisé est signalée par le renvoi d'un statut de sortie nul par ssh-keygen.
-y
Cette option lit un fichier privé au format OpenSSH et affiche une clé publique OpenSSH sur stdout.
-Z chiffrement
Spécifie le chiffrement à utiliser pour le cryptage lors de l'écriture d'un fichier de clé privée au format OpenSSH. La liste des chiffrements disponibles peut être obtenue en utilisant "ssh -Q cipher". La valeur par défaut est “aes256-ctr”.
-z numéro_de_série
Spécifie un numéro de série à intégrer dans le certificat pour distinguer ce certificat des autres émis par la même AC. Si le numéro_de_série est préfixé par un caractère ‘+’, alors le numéro de série sera incrémenté pour chaque certificat signé sur une seule ligne de commande. Le numéro de série par défaut est zéro.

Lors de la génération d'un KRL, l'option -z est utilisée pour spécifier un numéro de version KRL.

GÉNÉRATION DES MODULI

ssh-keygen peut être utilisé pour générer des groupes pour le protocole d'échange de groupe Diffie-Hellman (DH-GEX). La génération de ces groupes est un processus en deux étapes : d'abord, des nombres premiers candidats sont générés à l'aide d'un processus rapide, mais gourmand en mémoire. Ces nombres premiers candidats sont ensuite testés pour leur aptitude (un processus gourmand en CPU).

La génération des nombres premiers est effectuée à l'aide de l'option -M generate. La longueur souhaitée des nombres premiers peut être spécifiée par l'option -O bits. Par exemple:

# ssh-keygen -M generate -O bits=2048 moduli-2048.candidates

Par défaut, la recherche de nombres premiers commence à un point aléatoire dans la plage de longueurs souhaitée. Cela peut être remplacé en utilisant l'option -O start, qui spécifie un point de départ différent (en hexadécimal).

Une fois qu'un ensemble de candidats a été généré, ils doivent être filtrés pour vérifier leur aptitude. Cela peut être effectué à l'aide de l'option -M screen. Dans ce mode, ssh-keygen lira les candidats depuis l'entrée standard (ou un fichier spécifié à l'aide de l'option -f). Par exemple:

# ssh-keygen -M screen -f moduli-2048.candidates moduli-2048

Par défaut, chaque candidat sera soumis à 100 tests de primalité. Cela peut être remplacé en utilisant l'option -O prime-tests. La valeur du générateur DH sera choisie automatiquement pour le nombre premier considéré. Si un générateur spécifique est souhaité, il peut être demandé en utilisant l'option -O generator. Les valeurs de générateur valides sont 2, 3 et 5.

Les groupes DH filtrés peuvent être installés dans /etc/ssh/moduli. Il est important que ce fichier contienne des moduli de différentes longueurs de bits.

Un certain nombre d'options sont disponibles pour la génération et le filtrage des moduli via le drapeau -O :

lines=nombre
Sortir après avoir filtré le nombre spécifié de lignes lors du filtrage des candidats DH.
start-line=numéro_de_ligne
Commencer le filtrage au numéro de ligne spécifié lors du filtrage des candidats DH.
checkpoint=nom_de_fichier
Écrire la dernière ligne traitée dans le fichier spécifié lors du filtrage des candidats DH. Cela sera utilisé pour sauter les lignes du fichier d'entrée qui ont déjà été traitées si le travail est redémarré.
start=valeur_hex
Spécifier le point de départ (en hexadécimal) lors de la génération de moduli candidats pour DH-GEX.
generator=valeur
Spécifier le générateur souhaité (en décimal) lors du test des moduli candidats pour DH-GEX.

CERTIFICATS

ssh-keygen prend en charge la signature de clés pour produire des certificats qui peuvent être utilisés pour l'authentification d'utilisateur ou d'hôte. Les certificats consistent en une clé publique, des informations d'identité, zéro ou plusieurs noms de principaux (utilisateur ou hôte) et un ensemble d'options qui sont signés par une clé d'Autorité de Certification (AC). Les clients ou serveurs peuvent alors faire confiance uniquement à la clé d'AC et vérifier sa signature sur un certificat plutôt que de faire confiance à de nombreuses clés utilisateur/hôte. Notez que les certificats OpenSSH sont d'un format différent, et beaucoup plus simple, que les certificats X.509 utilisés dans ssl(8).

ssh-keygen prend en charge deux types de certificats : utilisateur et hôte. Les certificats utilisateur authentifient les utilisateurs auprès des serveurs, tandis que les certificats d'hôte authentifient les hôtes de serveur auprès des utilisateurs. Pour générer un certificat utilisateur :

$ ssh-keygen -s /chemin/vers/cle_ac -I id_cle /chemin/vers/cle_utilisateur.pub

Le certificat résultant sera placé dans /chemin/vers/cle_utilisateur-cert.pub. Un certificat d'hôte nécessite l'option -h :

$ ssh-keygen -s /chemin/vers/cle_ac -I id_cle -h /chemin/vers/cle_hote.pub

Le certificat d'hôte sera affiché sur /chemin/vers/cle_hote-cert.pub.

Il est possible de signer à l'aide d'une clé d'AC stockée dans un token PKCS#11 en fournissant la bibliothèque du token à l'aide de -D et en identifiant la clé d'AC en fournissant sa moitié publique comme argument à -s :

$ ssh-keygen -s cle_ac.pub -D libpkcs11.so -I id_cle cle_utilisateur.pub

De même, il est possible que la clé d'AC soit hébergée dans un ssh-agent(1). Ceci est indiqué par le drapeau -U et, à nouveau, la clé d'AC doit être identifiée par sa moitié publique.

$ ssh-keygen -Us cle_ac.pub -I id_cle cle_utilisateur.pub

Dans tous les cas, id_cle est un "identifiant de clé" qui est enregistré par le serveur

AUTORITÉ DE CERTIFICATION

Les clés publiques utilisées pour signer des clés et des certificats sont appelées clés de confiance. Les clés de confiance sont utilisées pour signer des clés privées ou des certificats afin d'établir une relation de confiance avec le propriétaire de la clé privée ou du certificat. Un certificat est une clé publique signée par une autorité de certification (CA) qui contient également des informations sur le propriétaire de la clé, telles que son nom, son organisation et son adresse électronique.

Les certificats peuvent être limités pour être valides pour un ensemble de noms de principaux (utilisateurs/hôtes). Par défaut, les certificats générés sont valides pour tous les utilisateurs ou hôtes. Pour générer un certificat pour un ensemble spécifié de principaux :

$ ssh-keygen -s ca_key -I key_id -n user1,user2 user_key.pub
$ ssh-keygen -s ca_key -I key_id -h -n host.domain host_key.pub

Des limitations supplémentaires sur la validité et l'utilisation des certificats d'utilisateur peuvent être spécifiées via des options de certificat. Une option de certificat peut désactiver des fonctionnalités de la session SSH, peut n'être valide que lorsqu'elle est présentée depuis des adresses sources particulières, ou peut forcer l'utilisation d'une commande spécifique.

Les options valides pour les certificats d'utilisateur sont :

clear
Efface toutes les permissions activées. Ceci est utile pour effacer l'ensemble par défaut des permissions afin que les permissions puissent être ajoutées individuellement.
critical:name[=contents]
 
extension:name[=contents]
Inclut une option critique ou une extension de certificat arbitraire. Le name spécifié doit inclure un suffixe de domaine, par exemple « name@example.com ». Si contents est spécifié, il est inclus comme contenu de l'extension/option encodé sous forme de chaîne, sinon l'extension/option est créée sans contenu (indiquant généralement un drapeau). Les extensions peuvent être ignorées par un client ou un serveur qui ne les reconnaît pas, tandis que les options critiques inconnues entraîneront le refus du certificat.
force-command=command
Force l'exécution de la command au lieu de tout shell ou commande spécifiée par l'utilisateur lorsque le certificat est utilisé pour l'authentification.
no-agent-forwarding
Désactive le transfert ssh-agent(1) (autorisé par défaut).
no-port-forwarding
Désactive le transfert de port (autorisé par défaut).
no-pty
Désactive l'allocation de PTY (autorisé par défaut).
no-user-rc
Désactive l'exécution de ~/.ssh/rc par sshd(8) (autorisé par défaut).
no-x11-forwarding
Désactive le transfert X11 (autorisé par défaut).
permit-agent-forwarding
Autorise le transfert ssh-agent(1).
permit-port-forwarding
Autorise le transfert de port.
permit-pty
Autorise l'allocation de PTY.
permit-user-rc
Autorise l'exécution de ~/.ssh/rc par sshd(8).
permit-X11-forwarding
Autorise le transfert X11.
no-touch-required
Ne pas exiger que les signatures faites avec cette clé incluent une démonstration de présence de l'utilisateur (par exemple, en demandant à l'utilisateur de toucher l'authentificateur). Cette option n'a de sens que pour les algorithmes d'authentification FIDO ecdsa-sk et ed25519-sk.
source-address=address_list
Restreint les adresses sources à partir desquelles le certificat est considéré comme valide. La address_list est une liste séparée par des virgules d'une ou plusieurs paires adresse/masque de réseau au format CIDR.
verify-required
Exiger que les signatures faites avec cette clé indiquent que l'utilisateur a été vérifié au préalable, par exemple par un code PIN ou des données biométriques sur le jeton. Cette option n'a de sens que pour les algorithmes d'authentification FIDO ecdsa-sk et ed25519-sk.

Actuellement, aucune option standard n'est valide pour les clés d'hôte.

Enfin, les certificats peuvent être définis avec une durée de validité. L'option -V permet de spécifier les heures de début et de fin de validité du certificat. Un certificat présenté en dehors de cet intervalle ne sera pas considéré comme valide. Par défaut, les certificats sont valides à partir de l'Epoch UNIX jusqu'à un avenir lointain.

Pour que les certificats soient utilisés pour l'authentification d'utilisateur ou d'hôte, la clé publique de la CA doit être approuvée par sshd(8) ou ssh(1). Référez-vous à ces pages de manuel pour plus de détails.

AUTHENTIFICATEUR FIDO

ssh-keygen est capable de générer des clés soutenues par des authentificateurs FIDO, qui peuvent ensuite être utilisées de manière similaire à tout autre type de clé pris en charge par OpenSSH, tant que l'authentificateur matériel est connecté lors de l'utilisation des clés. Les authentificateurs FIDO exigent généralement que l'utilisateur autorise explicitement les opérations en les touchant ou en les tapotant. Les clés FIDO sont composées de deux parties : un descripteur de clé stocké dans le fichier de clé privée sur le disque, et une clé privée par appareil unique à chaque authentificateur FIDO et qui ne peut pas être exportée du matériel de l'authentificateur. Celles-ci sont combinées par le matériel au moment de l'authentification pour dériver la clé réelle utilisée pour signer les défis d'authentification. Les types de clés pris en charge sont ecdsa-sk et ed25519-sk.

Les options valides pour les clés FIDO sont :

application
Remplace la chaîne d'application/origine FIDO par défaut de « ssh: ». Ceci peut être utile lors de la génération de clés résidentielles spécifiques à un hôte ou à un domaine. La chaîne d'application spécifiée doit commencer par « ssh: ».
challenge=path
Spécifie un chemin vers une chaîne de défi qui sera passée à l'authentificateur FIDO lors de la génération de la clé. La chaîne de défi peut être utilisée dans le cadre d'un protocole hors bande pour l'enregistrement des clés (un défi aléatoire est utilisé par défaut).
device
Spécifie explicitement un périphérique fido(4) à utiliser, au lieu de laisser le middleware de l'authentificateur en sélectionner un.
no-touch-required
Indique que la clé privée générée ne doit pas nécessiter d'événements tactiles (présence utilisateur) lors de la signature. Notez que sshd(8) refusera de telles signatures par défaut, sauf si elles sont remplacées via une option authorized_keys.
resident
Indique que le descripteur de clé doit être stocké sur l'authentificateur FIDO lui-même. Cela facilite l'utilisation de l'authentificateur sur plusieurs ordinateurs. Les clés résidentielles peuvent être prises en charge sur les authentificateurs FIDO2 et nécessitent généralement qu'un code PIN soit défini sur l'authentificateur avant la génération. Les clés résidentielles peuvent être chargées depuis l'authentificateur à l'aide de ssh-add(1). Le stockage des deux parties d'une clé sur un authentificateur FIDO augmente la probabilité qu'un attaquant puisse utiliser un périphérique d'authentification volé.
user
Un nom d'utilisateur à associer à une clé résidentielle, remplaçant le nom d'utilisateur vide par défaut. Spécifier un nom d'utilisateur peut être utile lors de la génération de plusieurs clés résidentielles pour le même nom d'application.
verify-required
Indique que cette clé privée doit exiger une vérification de l'utilisateur pour chaque signature. Tous les authentificateurs FIDO ne prennent pas en charge cette option. Actuellement, l'authentification par code PIN est la seule méthode de vérification prise en charge, mais d'autres méthodes pourraient l'être à l'avenir.
write-attestation=path
Peut être utilisé au moment de la génération de la clé pour enregistrer les données d'attestation renvoyées par les authentificateurs FIDO lors de la génération de la clé. Ces informations sont potentiellement sensibles. Par défaut, ces informations sont ignorées.

LISTES DE RÉVOCATION DE CLÉS

La liste de révocation de clés (KRL) est utilisée pour spécifier les certificats ou les clés publiques qui ont été révoqués par une autorité de certification (CA).

Lorsque l'option -k est spécifiée, ssh-keygen lit les directives suivantes, suivies d'un deux-points et d'informations spécifiques à la directive.

serial: numéro_de_série[-numéro_de_série]
Révogue un certificat avec le numéro de série spécifié. Les numéros de série sont des valeurs de 64 bits, sans compter le zéro, et peuvent être exprimés en décimal, hexadécimal ou octal. Si deux numéros de série sont spécifiés séparés par un trait d'union, alors la plage de numéros de série incluant et entre chacun est révoquée. La clé CA doit avoir été spécifiée sur la ligne de commande ssh-keygen en utilisant l'option -s.
id: id_clé
Révogue un certificat avec la chaîne d'identifiant de clé spécifiée. La clé CA doit avoir été spécifiée sur la ligne de commande ssh-keygen en utilisant l'option -s.
key: clé_publique
Révogue la clé spécifiée. Si un certificat est listé, alors il est révoqué en tant que clé publique simple.
sha1: clé_publique
Révogue la clé spécifiée en incluant son hachage SHA1 dans la KRL.
sha256: clé_publique
Révogue la clé spécifiée en incluant son hachage SHA256 dans la KRL. Les KRL qui révoquent les clés par hachage SHA256 ne sont pas prises en charge par les versions d'OpenSSH antérieures à 7.9.
hash: empreinte_digitale
Révogue une clé en utilisant un hachage d'empreinte, tel qu'obtenu à partir d'un message de journal d'authentification sshd(8) ou du drapeau -l de ssh-keygen. Seules les empreintes SHA256 sont prises en charge ici et les KRL résultantes ne sont pas prises en charge par les versions d'OpenSSH antérieures à 7.9.

Les KRL peuvent être mises à jour en utilisant le drapeau -u en plus de -k. Lorsque cette option est spécifiée, les clés listées via la ligne de commande sont fusionnées dans la KRL, s'ajoutant à celles déjà présentes.

Il est également possible, étant donné une KRL, de tester si elle révoque une clé (ou des clés) particulière. Le drapeau -Q interrogera une KRL existante, testant chaque clé spécifiée sur la ligne de commande. Si une clé listée sur la ligne de commande a été révoquée (ou si une erreur a été rencontrée), alors ssh-keygen se terminera avec un statut de sortie non nul. Un statut de sortie nul ne sera retourné que si aucune clé n'a été révoquée.

SIGNATAIRES AUTORISÉS

Lors de la vérification des signatures, ssh-keygen utilise une simple liste d'identités et de clés pour déterminer si une signature provient d'une source autorisée. Ce fichier de « signataires autorisés » utilise un format inspiré du FORMAT DE FICHIER AUTHORIZED_KEYS décrit dans sshd(8). Chaque ligne du fichier contient les champs suivants séparés par des espaces : principaux, options, type de clé, clé encodée en base64. Les lignes vides et les lignes commençant par un ‘#’ sont ignorées en tant que commentaires.

Le champ principaux est une liste de motifs (voir MOTIFS dans ssh_config(5)) composée d'un ou plusieurs motifs d'identité USER@DOMAIN séparés par des virgules qui sont acceptés pour la signature. Lors de la vérification, l'identité présentée via l'option -I doit correspondre à un motif de principaux pour que la clé correspondante soit considérée comme acceptable pour la vérification.

Les options (si présentes) consistent en des spécifications d'options séparées par des virgules. Aucune espace n'est permise, sauf dans les guillemets doubles. Les spécifications d'options suivantes sont prises en charge (notez que les mots-clés d'option ne sont pas sensibles à la casse) :

cert-authority
Indique que cette clé est acceptée comme autorité de certification (CA) et que les certificats signés par cette CA peuvent être acceptés pour la vérification.
namespaces=liste-espaces-de-noms
Spécifie une liste de motifs d'espaces de noms qui sont acceptés pour cette clé. Si cette option est présente, l'espace de noms de signature intégré dans l'objet de signature et présenté sur la ligne de commande de vérification doit correspondre à la liste spécifiée avant que la clé ne soit considérée comme acceptable.
valid-after=horodatage
Indique que la clé est valide pour une utilisation à partir du timestamp spécifié, qui peut être une date ou une heure aux formats YYYYMMDD[Z] ou YYYYMMDDHHMM[SS][Z]. Les dates et heures seront interprétées dans le fuseau horaire actuel du système, sauf si elles sont suffixées d'un caractère Z, qui provoque leur interprétation dans le fuseau horaire UTC.
valid-before=horodatage
Indique que la clé est valide pour une utilisation jusqu'au timestamp spécifié.

Lors de la vérification des signatures faites par des certificats, le nom de principal attendu doit correspondre à la fois au motif de principaux dans le fichier des signataires autorisés et aux principaux intégrés dans le certificat lui-même.

Exemple de fichier de signataires autorisés :

# Commentaires autorisés en début de ligne
user1@example.com,user2@example.com ssh-rsa AAAAX1...
# Une autorité de certification, approuvée pour tous les principaux d'un domaine.
*@example.com cert-authority ssh-ed25519 AAAB4...
# Une clé qui est acceptée uniquement pour la signature de fichiers.
user2@example.com namespaces="file" ssh-ed25519 AAA41...

Il est possible de spécifier une phrase secrète lors de la génération de la clé ; cette phrase secrète sera utilisée pour chiffrer la partie privée de ce fichier à l'aide de AES 128 bits. Ce fichier n'est pas automatiquement accédé par ssh-keygen mais il est proposé comme fichier par défaut pour la clé privée. ssh(1) lira ce fichier lorsqu'une tentative de connexion est effectuée.
