NOM

sss-certmap - Règles de correspondance et de mappage de certificats SSSD

DESCRIPTION

La page de manuel décrit les règles qui peuvent être utilisées par SSSD et d'autres composants pour faire correspondre les certificats X.509 et les mapper à des comptes.

Chaque règle comporte quatre composants, une « priorité », une « règle de correspondance », une « règle de mappage » et une « liste de domaines ». Tous les composants sont facultatifs. Une « priorité » manquante ajoutera la règle avec la priorité la plus basse. La « règle de correspondance » par défaut correspondra aux certificats avec l'usage de clé digitalSignature et l'usage de clé étendue clientAuth. Si la « règle de mappage » est vide, les certificats seront recherchés dans l'attribut userCertificate sous forme binaire encodée DER. Si aucun domaine n'est spécifié, seul le domaine local sera recherché.

Pour permettre des extensions ou un style de règle complètement différent, les « règles de mappage » et de « correspondance » peuvent contenir un préfixe séparé par un « : » du corps principal de la règle. Le préfixe ne peut contenir que des lettres ASCII majuscules et des chiffres. Si le préfixe est omis, le type par défaut sera utilisé, qui est 'KRB5' pour les règles de correspondance et 'LDAP' pour les règles de mappage.

L'utilitaire 'sssctl' fournit la commande 'cert-eval-rule' pour vérifier si un certificat donné correspond à une règle de correspondance et à quoi ressemblerait la sortie d'une règle de mappage.

COMPOSANTS DES RÈGLES

PRIORITÉ

Les règles sont traitées par priorité, le nombre '0' (zéro) indiquant la priorité la plus élevée. Plus le nombre est élevé, plus la priorité est basse. Une valeur manquante indique la priorité la plus basse. Le traitement des règles s'arrête lorsqu'une règle correspondante est trouvée et aucune autre règle n'est vérifiée.

En interne, la priorité est traitée comme un entier non signé de 32 bits. L'utilisation d'une valeur de priorité supérieure à 4294967295 provoquera une erreur.

Si plusieurs règles ont la même priorité et que seule l'une des règles de correspondance associées s'applique, cette règle sera choisie. S'il existe plusieurs règles avec la même priorité qui correspondent, une est choisie mais laquelle est indéfinie. Pour éviter ce comportement indéfini, utilisez soit des priorités différentes, soit rendez les règles de correspondance plus spécifiques, par exemple en utilisant des motifs <ISSUER> distincts.

RÈGLE DE CORRESPONDANCE

La règle de correspondance est utilisée pour sélectionner un certificat auquel la règle de mappage doit être appliquée. Elle utilise un système similaire à celui utilisé par l'option “pkinit_cert_match” de MIT Kerberos. Elle se compose d'un mot-clé entouré de '<' et '>' qui identifie une certaine partie du certificat et d'un motif qui doit être trouvé pour que la règle corresponde. Plusieurs paires mot-clé motif peuvent être jointes avec '&&' (et) ou '||' (ou).

Compte tenu de la similitude avec MIT Kerberos, le préfixe de type pour cette règle est 'KRB5'. Mais 'KRB5' sera également le défaut pour les règles de “correspondance”, de sorte que "<SUBJECT>.*,DC=MY,DC=DOMAIN" et "KRB5:<SUBJECT>.*,DC=MY,DC=DOMAIN" sont équivalents.

Les options disponibles sont :

<SUBJECT>expression-régulière

Avec ceci, une partie ou la totalité du nom du sujet du certificat peut être mise en correspondance. Pour la correspondance, la syntaxe POSIX Extended Regular Expression est utilisée, voir regex(7) pour les détails.

Pour la correspondance, le nom du sujet stocké dans le certificat en ASN.1 encodé DER est converti en une chaîne selon la RFC 4514. Cela signifie que le composant de nom le plus spécifique vient en premier. Veuillez noter que tous les noms d'attributs possibles ne sont pas couverts par la RFC 4514. Les noms inclus sont 'CN', 'L', 'ST', 'O', 'OU', 'C', 'STREET', 'DC' et 'UID'. D'autres noms d'attributs peuvent apparaître différemment selon les plateformes et les outils. Pour éviter toute confusion, il est préférable de ne pas utiliser ces noms d'attributs ou de les couvrir par une expression régulière appropriée.

Exemple : <SUBJECT>.*,DC=MY,DC=DOMAIN

Veuillez noter que les caractères "^.[$()|*+?{\" ont une signification spéciale dans les expressions régulières et doivent être échappés à l'aide du caractère '\' afin qu'ils soient mis en correspondance en tant que caractères ordinaires.

Exemple : <SUBJECT>^CN=.* \(Admin\),DC=MY,DC=DOMAIN$

<ISSUER>expression-régulière

Avec ceci, une partie ou la totalité du nom de l'émetteur du certificat peut être mise en correspondance. Tous les commentaires pour <SUBJECT> s'appliquent également ici.

Exemple : <ISSUER>^CN=Mon-CA,DC=MY,DC=DOMAIN$

<KU>usage-clé

Cette option peut être utilisée pour spécifier les valeurs d'usage de clé que le certificat doit avoir. Les valeurs suivantes peuvent être utilisées dans une liste séparée par des virgules :
•digitalSignature
•nonRepudiation
•keyEncipherment
•dataEncipherment
•keyAgreement
•keyCertSign
•cRLSign
•encipherOnly
•decipherOnly

Une valeur numérique dans la plage d'un entier non signé de 32 bits peut également être utilisée pour couvrir des cas d'utilisation spéciaux.

Exemple : <KU>digitalSignature,keyEncipherment

<EKU>usage-clé-étendu

Cette option peut être utilisée pour spécifier quel usage de clé étendue le certificat doit avoir. La liste suivante peut être utilisée dans une liste séparée par des virgules :
•serverAuth
•clientAuth
•codeSigning
•emailProtection
•timeStamping
•OCSPSigning
•KPClientAuth
•pkinit
•msScLogin

Les usages de clés étendus qui ne sont pas listés ci-dessus peuvent être spécifiés avec leur OID en notation décimale pointée.

Exemple : <EKU>clientAuth,1.3.6.1.5.2.3.4

<SAN>expression-régulière

Pour être compatible avec l'utilisation de MIT Kerberos, cette option correspondra aux principaux Kerberos dans le SAN PKINIT ou AD NT Principal comme le fait <SAN:Principal>.

Exemple : <SAN>.*@MY\.REALM

<SAN:Principal>expression-régulière

Correspond aux principaux Kerberos dans le SAN PKINIT ou AD NT Principal.

Exemple : <SAN:Principal>.*@MY\.REALM

<SAN:ntPrincipalName>expression-régulière

Correspond aux principaux Kerberos du SAN AD NT Principal.

Exemple : <SAN:ntPrincipalName>.*@MY.AD.REALM

<SAN:pkinit>expression-régulière

Correspond aux principaux Kerberos du SAN PKINIT.

Exemple : <SAN:ntPrincipalName>.*@MY\.PKINIT\.REALM

<SAN:dotted-decimal-oid>expression-régulière

Prend la valeur du composant SAN otherName donné par l'OID en notation décimale pointée, l'interprète comme une chaîne et tente de la mettre en correspondance avec l'expression régulière.

Exemple : <SAN:1.2.3.4>test

<SAN:otherName>chaîne-base64

Effectue une correspondance binaire avec le blob encodé en base64 contre tous les composants SAN otherName. Avec cette option, il est possible de faire correspondre des composants otherName personnalisés avec des encodages spéciaux qui ne pouvaient pas être traités comme des chaînes.

Exemple : <SAN:otherName>MTIz

<SAN:rfc822Name>expression-régulière

Correspond à la valeur du SAN rfc822Name.

Exemple : <SAN:rfc822Name>.*@email\.domain

<SAN:dNSName>expression-régulière

Correspond à la valeur du SAN dNSName.

Exemple : <SAN:dNSName>.*\.my\.dns\.domain

<SAN:x400Address>chaîne-base64

Correspond binaire à la valeur du SAN x400Address.

Exemple : <SAN:x400Address>MTIz

<SAN:directoryName>expression-régulière

Correspond à la valeur du SAN directoryName. Les mêmes commentaires que ceux donnés pour <ISSUER> et <SUBJECT> s'appliquent ici aussi.

Exemple : <SAN:directoryName>.*,DC=com

<SAN:ediPartyName>chaîne-base64

dent">Correspondance binaire de la valeur de SAN ediPartyName.

Exemple : <SAN:ediPartyName>MTIz

<SAN:uniformResourceIdentifier>expression-régulière

Correspondance de la valeur de SAN uniformResourceIdentifier.

Exemple : <SAN:uniformResourceIdentifier>URN:.*

<SAN:iPAddress>expression-régulière

Correspondance de la valeur de SAN iPAddress.

Exemple : <SAN:iPAddress>192\.168\..*

<SAN:registeredID>expression-régulière

Correspondance de la valeur de SAN registeredID sous forme de chaîne décimale pointée.

Exemple : <SAN:registeredID>1\.2\.3\..*

RÈGLE DE MAPPING

La règle de mapping est utilisée pour associer un certificat à un ou plusieurs comptes. Une carte à puce avec le certificat et la clé privée correspondante peut alors être utilisée pour s'authentifier en tant que l'un de ces comptes.

Actuellement, SSSD prend principalement en charge LDAP pour rechercher des informations utilisateur (l'exception est le fournisseur proxy qui n'est pas pertinent ici). Pour cette raison, la règle de mapping est basée sur la syntaxe des filtres de recherche LDAP avec des modèles pour ajouter le contenu du certificat au filtre. On s'attend à ce que le filtre ne contienne que les données spécifiques nécessaires au mapping et que l'appelant l'intègre dans un autre filtre pour effectuer la recherche réelle. Pour cette raison, la chaîne de filtre doit commencer par '(' et se terminer par ')'.

En général, il est recommandé d'utiliser des attributs du certificat et de les ajouter à des attributs spéciaux de l'objet utilisateur LDAP. Par exemple, l'attribut 'altSecurityIdentities' dans AD ou l'attribut 'ipaCertMapData' pour IPA peuvent être utilisés.

Il est préférable de lire les données spécifiques à l'utilisateur du certificat, comme par exemple une adresse e-mail, et de les rechercher sur le serveur LDAP. La raison en est que les données spécifiques à l'utilisateur dans LDAP peuvent changer pour diverses raisons, ce qui casserait le mapping. D'un autre côté, il serait difficile de casser le mapping intentionnellement pour un utilisateur spécifique.

Le type de "règle de mapping" par défaut est 'LDAP', qui peut être ajouté comme préfixe à une règle telle que 'LDAP:(userCertificate;binary={cert!bin})'. Il existe une extension appelée 'LDAPU1' qui offre plus de modèles pour plus de flexibilité. Pour permettre aux anciennes versions de cette bibliothèque d'ignorer l'extension, le préfixe 'LDAPU1' doit être utilisé lors de l'utilisation des nouveaux modèles dans une "règle de mapping", sinon l'ancienne version de cette bibliothèque échouera avec une erreur d'analyse. Les nouveaux modèles sont décrits dans la section intitulée "extension LDAPU1".

Les modèles pour ajouter des données de certificat au filtre de recherche sont basés sur des chaînes de formatage de style Python. Ils consistent en un mot-clé entre accolades avec un spécificateur de sous-composant optionnel séparé par un '.' ou une option de conversion/formatage optionnelle séparée par un '!'. Les valeurs autorisées sont :

{issuer_dn[!((ad|ad_x500)|ad_ldap|nss_x500|(nss|nss_ldap))]}

Ce modèle ajoutera le DN d'émetteur complet converti en une chaîne conformément à la RFC 4514. Si l'ordre X.500 (le RDN le plus spécifique vient en dernier) est utilisé, une option avec le préfixe '_x500' doit être utilisée.

Les options de conversion commençant par 'ad_' utiliseront les noms d'attributs tels qu'utilisés par AD, par exemple 'S' au lieu de 'ST'.

Les options de conversion commençant par 'nss_' utiliseront les noms d'attributs tels qu'utilisés par NSS.

L'option de conversion par défaut est 'nss', c'est-à-dire les noms d'attributs conformément à l'ordre NSS et LDAP/RFC 4514.

Exemple : (ipacertmapdata=X509:<I>{issuer_dn!ad}<S>{subject_dn!ad})

{subject_dn[!((ad|ad_x500)|ad_ldap|nss_x500|(nss|nss_ldap))]}

Ce modèle ajoutera le DN de sujet complet converti en une chaîne conformément à la RFC 4514. Si l'ordre X.500 (le RDN le plus spécifique vient en dernier) est utilisé, une option avec le préfixe '_x500' doit être utilisée.

Les options de conversion commençant par 'ad_' utiliseront les noms d'attributs tels qu'utilisés par AD, par exemple 'S' au lieu de 'ST'.

Les options de conversion commençant par 'nss_' utiliseront les noms d'attributs tels qu'utilisés par NSS.

L'option de conversion par défaut est 'nss', c'est-à-dire les noms d'attributs conformément à l'ordre NSS et LDAP/RFC 4514.

Exemple : (ipacertmapdata=X509:<I>{issuer_dn!nss_x500}<S>{subject_dn!nss_x500})

{cert[!(bin|base64)]}

Ce modèle ajoutera le certificat codé DER complet sous forme de chaîne au filtre de recherche. Selon l'option de conversion, le certificat binaire est converti en une séquence hexadécimale échappée '\xx' ou en base64. La séquence hexadécimale échappée est la valeur par défaut et peut, par exemple, être utilisée avec l'attribut LDAP 'userCertificate;binary'.

Exemple : (userCertificate;binary={cert!bin})

{subject_principal[.short_name]}

Ce modèle ajoutera le principal Kerberos, qui est extrait soit du SAN utilisé par pkinit, soit de celui utilisé par AD. Le composant 'short_name' représente la première partie du principal avant le signe '@'.

Exemple : (|(userPrincipal={subject_principal})(samAccountName={subject_principal.short_name}))

{subject_pkinit_principal[.short_name]}

Ce modèle ajoutera le principal Kerberos, qui est fourni par le SAN utilisé par pkinit. Le composant 'short_name' représente la première partie du principal avant le signe '@'.

Exemple : (|(userPrincipal={subject_pkinit_principal})(uid={subject_pkinit_principal.short_name}))

{subject_nt_principal[.short_name]}

Ce modèle ajoutera le principal Kerberos, qui est fourni par le SAN utilisé par AD. Le composant 'short_name' représente la première partie du principal avant le signe '@'.

Exemple : (|(userPrincipalName={subject_nt_principal})(samAccountName={subject_nt_principal.short_name}))

{subject_rfc822_name[.short_name]}

Ce modèle ajoutera la chaîne stockée dans le composant rfc822Name du SAN, typiquement une adresse e-mail. Le composant 'short_name' représente la première partie de l'adresse avant le signe '@'.

Exemple : (|(mail={subject_rfc822_name})(uid={subject_rfc822_name.short_name}))

{subject_dns_name[.short_name]}

Ce modèle ajoutera la chaîne stockée dans le composant dNSName du SAN, typiquement un nom d'hôte entièrement qualifié. Le composant 'short_name' représente la première partie du nom avant le premier signe '.'.

Exemple : (|(fqdn={subject_dns_name})(host={subject_dns_name.short_name}))

{subject_uri}

Ce modèle ajoutera la chaîne stockée dans le composant uniformResourceIdentifier du SAN.

Exemple : (uri={subject_uri})

{subject_ip_address}

Ce modèle ajoutera la chaîne stockée dans le composant iPAddress du SAN.

Exemple : (ip={subject_ip_address})

{subject_x400_address}

Ce modèle ajoutera la valeur stockée dans le composant x400Address du SAN sous forme de séquence hexadécimale échappée.

Exemple : (attr:binary={subject_x400_address})

{subject_directory_name[!((ad|ad_x500)|ad_ldap|nss_x500|(nss|nss_ldap))]}

Ce modèle ajoutera le DN de la valeur stockée dans le composant directoryName du SAN.

Exemple : (orig_dn={subject_directory_name})

{subject_ediparty_name}

Ce modèle ajoutera la valeur stockée dans le composant ediPartyName du SAN sous forme de séquence hexadécimale échappée.

Exemple : (attr:binary={subject_ediparty_name})

{subject_registered_id}

Ce modèle ajoutera l'OID stockée dans le composant registeredID du SAN sous forme de chaîne décimale pointée.

Exemple : (oid={subject_registered_id})

Extension LDAPU1

Les modèles suivants sont disponibles lors de l'utilisation de l'extension 'LDAPU1' :

{serial_number[!(dec|hex[_ucr])]}

Ce modèle ajoutera le numéro de série du certificat. Par défaut, il sera imprimé sous forme de nombre hexadécimal avec des lettres minuscules.

Avec l'option de formatage '!dec', le nombre sera imprimé sous forme de chaîne décimale. La sortie hexadécimale peut être imprimée avec des lettres majuscules ('!hex_u'), avec un deux-points séparant les octets hexadécimaux ('!hex_c') ou avec les octets hexadécimaux dans l'ordre inverse ('!hex_r'). Les lettres de postfixe peuvent être combinées, de sorte que, par exemple, '!hex_uc' produira une chaîne hexadécimale séparée par des deux-points avec des lettres majuscules.

Exemple : LDAPU1:(serial={serial_number})

{subject_key_id[!hex[_ucr]]}

Ce modèle ajoutera l'identifiant de clé du sujet du certificat. Par défaut, il sera imprimé sous forme de nombre hexadécimal avec des lettres minuscules.

La sortie hexadécimale peut être imprimée avec des lettres majuscules ('!hex_u'), avec un deux-points séparant les octets hexadécimaux ('!hex_c') ou avec les octets hexadécimaux dans l'ordre inverse ('!hex_r'). Les lettres de postfixe peuvent être combinées, de sorte que, par exemple, '!hex_uc' produira une chaîne hexadécimale séparée par des deux-points avec des lettres majuscules.

Exemple : LDAPU1:(ski={subject_key_id})

{cert[!DIGEST[_ucr]]}

Ce modèle ajoutera le digest/hash hexadécimal du certificat, où DIGEST doit être remplacé par le nom d'une fonction de digest/hash prise en charge par OpenSSL, par exemple 'sha512'.

La sortie hexadécimale peut être imprimée avec des lettres majuscules ('!sha512_u'), avec un deux-points séparant les octets hexadécimaux ('!sha512_c') ou avec les octets hexadécimaux dans l'ordre inverse ('!sha512_r'). Les lettres de postfixe peuvent être combinées, de sorte que, par exemple, '!sha512_uc' produira une chaîne hexadécimale séparée par des deux-points avec des lettres majuscules.

Exemple : LDAPU1:(dgst={cert!sha256})

{subject_dn_component[(.attr_name|[number]]}

Ce modèle ajoutera la valeur d'un attribut d'un composant du DN de sujet, par défaut la valeur du composant le plus spécifique.

Un composant différent peut être sélectionné par nom d'attribut, par exemple {subject_dn_component.uid}, ou par position, par exemple {subject_dn_component.[2]}, où les nombres positifs commencent à compter à partir du composant le plus spécifique et les nombres négatifs commencent à compter à partir du composant le moins spécifique. Le nom de l'attribut et la position peuvent être combinés, par exemple {subject_dn_component.uid[2]}, ce qui signifie que le nom du deuxième composant doit être 'uid'.

Exemple : LDAPU1:(uid={subject_dn_component.uid})

{issuer_dn_component[(.attr_name|[number]]}

Ce modèle ajoutera la valeur d'un attribut d'un composant du DN d'émetteur, par défaut la valeur du composant le plus spécifique.

NAME

sss-certmap – certificate mapping rules

DESCRIPTION

The certificate mapping is a new feature that allows SSSD to map client certificates to local users. It is intended primarily for TLS-enabled protocols like LDAP, IMAP, etc.

The mapping rules are stored in the file /etc/sssd/sssd.conf in the [certmap] section.

A rule has the following format:

RULE_NAME: RULE_DEFINITION

Each rule has a name, which is used for logging purposes only. The rule definition consists of a list of key-value pairs, separated by whitespace. The keys and values are case-sensitive.

The available keys are:

`<ldap_field>`
The certificate field or attribute to use for mapping. This can be a standard X.509 field name, like subject, issuer, or serial_number, or an LDAP attribute name, if the certificate is stored in an LDAP server. It can also be a special field like subject_alt which represents the subject alternative name.
`<rule_filter>`
A filter to apply to the certificate field. The filter supports the same syntax as the filter used in the ldap_search_filter option in the [ldap] section. For example, uid=%s.
`<map_rule>`
A rule that defines how to map the certificate to a user. The available map rules are:
`LDAP_DN`
Map the certificate to a user's LDAP distinguished name (DN). The DN is constructed from the certificate fields. The placeholder %s is replaced with the corresponding certificate field value.
`LDAPU`
Map the certificate to a user's LDAP userPrincipalName (UPN). The UPN is constructed from the certificate fields.
`LDAP_URI`
Map the certificate to a user's LDAP URI. The URI is constructed from the certificate fields.
`SID`
Map the certificate to a user's Security Identifier (SID). The SID is retrieved from the certificate extension introduced by Microsoft.

The following special fields are available:

`issuer_dn_component.<name>`
The issuer DN component <name>. For example, issuer_dn_component.dc for the domain component, or issuer_dn_component.cn for the common name.
`subject_dn_component.<name>`
The subject DN component <name>. For example, subject_dn_component.uid for the user ID.
`subject_alt`
The subject alternative name. This can be a DNS name, an email address, or a UPN.
`sid`
The Microsoft Certificate Basic Constraints extension, which contains the user's SID.

The map rule can optionally be followed by selectors that further refine the mapping. The available selectors are:

`.<name>`
Select a specific component of the DN. For example, subject_dn_component.uid.cn selects the common name (CN) from the user ID (UID) component of the subject DN.
`.[-N]`
Select the Nth component from the end of the DN. For example, subject_dn_component.dc.[-1] selects the last domain component.
`.[-N].<name>`
Select a specific component of the Nth component from the end of the DN.
`.rid`
Select the RID (Relative Identifier) from the SID.

The placeholder %s is used to insert the value of the certificate field into the rule definition.

Rules are processed in the order they appear in the configuration file. The first rule that matches the certificate is used.

EXAMPLES

Map the user ID from the subject DN to the LDAP DN:

uid=foo,cn=users,cn=accounts,dc=example,dc=com: \ subject_dn_component.uid=%s,LDAP_DN

Map the UPN from the subject alternative name to the LDAP UPN:

upn_map: subject_alt=%s@example.com,LDAPU

Map the SID from the certificate extension to the local user ID:

sid_map: sid=%s,SID

Map the RID from the SID extension to the local user ID:

rid_map: sid=%s.rid,SID

Map the issuer DN component 'dc' to the domain name:

domain_map: issuer_dn_component.dc=%s,LDAP_DN

Map the last domain component of the issuer DN to the domain name:

last_dc_map: issuer_dn_component.dc.[-1]=%s,LDAP_DN

Map the SID from the Microsoft certificate extension (OID 1.3.6.1.4.1.311.25.2) to the user's SID:

ms_sid_map: sid=1.3.6.1.4.1.311.25.2=%s,SID

Map the last component of the issuer DN to the domain name:

issuer_last_comp: ({issuer_dn_component.dc.[-1]})

This template will add the SID if the corresponding extension introduced by Microsoft with the OID 1.3.6.1.4.1.311.25.2 is available. With the '.rid' selector only the last component, i.e. the RID, will be added.

Example: LDAPU1:(objectsid={sid})

DOMAIN LIST

If the domain list is not empty users mapped to a given certificate are not only searched in the local domain but in the listed domains as well as long as they are know by SSSD. Domains not know to SSSD will be ignored.
