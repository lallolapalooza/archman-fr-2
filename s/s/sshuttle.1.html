SSHUTTLE(1) sshuttle SSHUTTLE(1)

NOM

sshuttle - Documentation de sshuttle

SYNTAXE

sshuttle [options] -r [nomutilisateur@]serveurssh[:port] <sous-réseaux ...>

DESCRIPTION

sshuttle permet de créer une connexion VPN de votre machine vers n'importe quel serveur distant auquel vous pouvez vous connecter via ssh, tant que ce serveur dispose d'une installation Python suffisamment récente.

Pour fonctionner, vous devez avoir un accès root sur la machine locale, mais vous pouvez avoir un compte normal sur le serveur.

Il est valide d'exécuter sshuttle plusieurs fois simultanément sur une seule machine cliente, en se connectant à des serveurs différents à chaque fois, vous pouvez ainsi être sur plus d'un VPN à la fois.

S'il est exécuté sur un routeur, sshuttle peut rediriger le trafic pour votre sous-réseau entier vers le VPN.

OPTIONS

<sous-réseaux>
Une liste de sous-réseaux à acheminer via le VPN, sous la forme a.b.c.d[/largeur][port[-port]]. Les exemples valides sont 1.2.3.4 (une seule adresse IP) et 1.2.3.4/32 (équivalent à 1.2.3.4), 1.2.3.0/24 (un sous-réseau de 24 bits, c'est-à-dire avec un masque de réseau 255.255.255.0). Spécifiez les sous-réseaux 0/0 pour correspondre à toutes les adresses IPv4 et ::/0 pour correspondre à toutes les adresses IPv6. N'importe lequel des exemples précédents est également valide si vous ajoutez un port ou une plage de ports, donc 1.2.3.4:8000 acheminera uniquement le trafic qui a comme port de destination 8000 de 1.2.3.4 et 1.2.3.0/24:8000-9000 acheminera le trafic destiné à n'importe quel port entre 8000 et 9000 (inclus) pour toutes les IPs du sous-réseau 1.2.3.0/24. Un nom d'hôte peut être fourni à la place d'une adresse IP. Si le nom d'hôte résout en plusieurs IPs, toutes les IPs sont incluses. Si une largeur est fournie avec un nom d'hôte, la largeur est appliquée à toutes les IPs des noms d'hôtes (si elles sont toutes IPv4 ou IPv6). Les largeurs ne peuvent pas être fournies aux noms d'hôtes qui résolvent en IPv4 et IPv6. Les exemples valides sont example.com, example.com:8000, example.com/24, example.com/24:8000 et example.com:8000-9000.
--methode <auto|nat|nft|tproxy|pf|ipfw>
Quelle méthode de pare-feu sshuttle doit-il utiliser ? Pour auto, sshuttle tente de deviner la méthode appropriée en fonction de ce qu'il trouve dans PATH. La valeur par défaut est auto.
-l <[ip:]port>, --ecouter=<[ip:]port>
Utiliser cette adresse IP et ce numéro de port comme port du proxy transparent. Par défaut, sshuttle trouve automatiquement un port disponible et écoute sur l'IP 127.0.0.1 (localhost), vous n'avez donc pas besoin de le remplacer, et les connexions sont uniquement acheminées depuis la machine locale, pas depuis des machines externes. Si vous souhaitez accepter des connexions provenant d'autres machines de votre réseau (c'est-à-dire exécuter sshuttle sur un routeur), essayez d'activer la redirection IP dans votre noyau, puis utilisez --ecouter 0.0.0.0:0. Vous pouvez utiliser n'importe quel nom résolvant vers une adresse IP de la machine exécutant sshuttle, par exemple --ecouter localhost.

Pour les méthodes nft, tproxy et pf, il peut s'agir d'une adresse IPv6. Utilisez cette option avec des valeurs séparées par des virgules si nécessaire, pour fournir des adresses IPv4 et IPv6, par exemple --ecouter 127.0.0.1:0,[::1]:0.

-H, --auto-hotes
Analyser les noms d'hôtes distants et mettre à jour le fichier local /etc/hosts avec les entrées correspondantes tant que le VPN est ouvert. C'est mieux que de modifier les paramètres DNS de votre système (/etc/resolv.conf), pour plusieurs raisons. Premièrement, les noms d'hôtes sont ajoutés sans noms de domaine, vous pouvez donc ssh nomd'hote sans vous soucier si votre domaine local correspond au domaine distant. Deuxièmement, si vous utilisez sshuttle sur plus d'un VPN à la fois, il est de toute façon impossible d'utiliser plus d'un serveur DNS à la fois, mais sshuttle fusionne correctement les entrées /etc/hosts entre toutes les copies en cours d'exécution. Troisièmement, si vous n'acheminez que quelques sous-réseaux via le VPN, vous préférerez probablement continuer à utiliser votre serveur DNS local pour tout le reste.

sshuttle essaie de stocker un cache des noms d'hôtes dans ~ / .sshuttle.hosts sur l'hôte distant. De même, il essaie de lire le fichier lorsque vous vous reconnectez plus tard à l'hôte avec --auto-hotes activé pour peupler rapidement la liste des hôtes. Lors du dépannage de cette fonctionnalité, essayez de supprimer ce fichier sur l'hôte distant lorsque sshuttle n'est pas en cours d'exécution.

-N, --auto-reseaux
En plus des sous-réseaux fournis en ligne de commande, demandez au serveur quels sous-réseaux il pense que nous devrions acheminer, et acheminez-les automatiquement. Les suggestions sont prises automatiquement dans la table de routage du serveur.

Cette fonctionnalité ne détecte pas les routes IPv6. Spécifiez manuellement les sous-réseaux IPv6. Par exemple, spécifiez le sous-réseau ::/0 sur la ligne de commande pour acheminer tout le trafic IPv6.

--dns
Intercepter les requêtes DNS locales et les transmettre au serveur DNS distant. Toutes les requêtes vers n'importe lequel des serveurs DNS du système local (/etc/resolv.conf et, s'il existe, /run/systemd/resolve/resolv.conf) seront interceptées et résolues du côté distant du tunnel, en utilisant le DNS spécifié via l'option --vers-ns, si spécifié. Seul le trafic DNS simple envoyé à ces serveurs sur le port 53 est capturé.
--hotes-ns=<serveur1[,serveur2[,serveur3[...]]]>
Intercepter les requêtes DNS locales vers le(s) serveur(s) spécifié(s) et les transmettre au serveur DNS distant. Contrairement à l'option --dns, ce drapeau permet de spécifier le(s) serveur(s) DNS dont les requêtes doivent être interceptées, au lieu d'intercepter tout le trafic DNS sur la machine locale. Cela peut être utile lorsque seules certaines requêtes DNS doivent être résolues du côté distant du tunnel, par exemple en combinaison avec dnsmasq.
--vers-ns=<serveur>
Le DNS auquel transmettre les requêtes lorsque la résolution DNS distante est activée. Si non spécifié, sshuttle résoudra simplement en utilisant le résolveur configuré par le système du côté distant (via /etc/resolv.conf du côté distant).
--python
Spécifier le nom/chemin de l'interpréteur Python distant. La valeur par défaut est d'utiliser python3 (ou python, si python3 échoue) dans le PATH du système distant.
-r <[nomutilisateur@]serveurssh[:port]>, --distant=<[nomutilisateur@]serveurssh[:port]>
Le nom d'hôte distant et le nom d'utilisateur et le numéro de port ssh optionnels à utiliser pour la connexion au serveur distant. Par exemple, example.com, testuser@example.com, testuser@example.com:2222, ou example.com:2244. Ce nom d'hôte est passé à ssh, il reconnaîtra donc tous les alias et paramètres que vous auriez pu configurer dans ~/.ssh/config.
-x <sous-reseau>, --exclure=<sous-reseau>
Exclure explicitement ce sous-réseau de l'acheminement. Le format de cette option est le même que celui de l'option <sous-réseaux>. Pour exclure plus d'un sous-réseau, spécifiez l'option -x plusieurs fois. Vous pouvez dire quelque chose comme 0/0 -x 1.2.3.0/24 pour acheminer tout sauf le sous-réseau local via le VPN, par exemple.
-X <fichier>, --exclure-depuis=<fichier>
Exclure les sous-réseaux spécifiés dans un fichier, un sous-réseau par ligne. Utile lorsque vous avez beaucoup de sous-réseaux à exclure.
-v, --verbeux
Afficher plus d'informations sur la session. Cette option peut être utilisée plusieurs fois pour augmenter la verbosité. Par défaut, sshuttle n'affiche que les messages d'erreur.
-e, --cmd-ssh
La commande à utiliser pour se connecter au serveur distant. La valeur par défaut est simplement ssh. Utilisez ceci si votre client ssh se trouve dans un emplacement non standard ou si vous souhaitez fournir des options supplémentaires à la commande ssh, par exemple

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

ple, -e 'ssh -v'.
--remote-shell
Pour les cibles Windows, spécifiez un programme de shell distant configuré comme alternative au shell posix de facto. Il s'agira soit de cmd, soit de powershell, sauf si quelque chose comme git-bash est utilisé.
--no-cmd-delimiter
N'ajoute pas de délimiteur de double trait d'union (--) avant d'invoquer Python sur l'hôte distant. Cette option est utile lorsque la commande ssh utilisée pour la connexion est une commande personnalisée qui n'interprète pas correctement ce délimiteur.
--seed-hosts
Une liste de noms d'hôtes séparés par des virgules à utiliser pour initialiser l'algorithme d'analyse --auto-hosts. --auto-hosts fait des choses comme interroger la sortie de netstat pour des listes de noms d'hôtes locaux, mais peut accélérer les choses si vous utilisez cette option pour lui donner quelques noms pour commencer.

Si cette option est utilisée sans --auto-hosts, les noms d'hôtes listés seront analysés et ajoutés, mais aucun autre nom d'hôte ne sera ajouté.

--no-latency-control
Sacrifie la latence pour améliorer les benchmarks de bande passante. ssh utilise des tampons de socket très volumineux, ce qui peut surcharger la connexion si vous commencez à effectuer de grands transferts de fichiers, rendant ainsi toutes vos autres sessions au sein du même tunnel lentes. Normalement, sshuttle essaie d'éviter ce problème en utilisant une "vérification de saturation" qui permet de ne bufferiser qu'une certaine quantité de données en attente à la fois. Mais sur les liaisons à haute bande passante, cela peut laisser une grande partie de votre bande passante sous-utilisée. Cela donne également à sshuttle une apparence lente dans les benchmarks de bande passante (les benchmarks ne testent rarement la latence du ping, qui est ce que sshuttle essaie de contrôler). Cette option désactive la fonctionnalité de contrôle de latence, maximisant l'utilisation de la bande passante. À utiliser à vos risques et périls.
--latency-buffer-size
Définit la taille du tampon utilisé dans le contrôle de latence. La valeur par défaut est 32768. La modification de cette option permet de faire un compromis entre latence et bande passante sans désactiver complètement le contrôle de latence (avec --no-latency-control).
-D, --daemon
Se dédouble automatiquement en arrière-plan après la connexion au serveur distant. Implique --syslog.
-s <fichier>, --subnets=<fichier>
Inclut les sous-réseaux spécifiés dans un fichier au lieu de la ligne de commande. Un sous-réseau par ligne.
--syslog
après la connexion, envoie tous les messages de journalisation au service syslog(3) au lieu de stderr. Ceci est implicite si vous utilisez --daemon.
--pidfile=<pidfilename>
lorsque vous utilisez --daemon, enregistre le pid de sshuttle dans pidfilename. La valeur par défaut est sshuttle.pid dans le répertoire courant.
--disable-ipv6
Désactive le support IPv6 pour les méthodes qui le prennent en charge (nat, nft, tproxy et pf).
--firewall
(usage interne uniquement) exécute le gestionnaire de pare-feu. C'est la seule partie de sshuttle qui doit s'exécuter en tant que root. Si vous démarrez sshuttle en tant qu'utilisateur non-root, il exécutera automatiquement sudo ou su pour démarrer le gestionnaire de pare-feu, mais le cœur de sshuttle continuera de s'exécuter en tant qu'utilisateur normal.
--hostwatch
(usage interne uniquement) exécute le démon hostwatch. Ce processus s'exécute côté serveur et collecte les noms d'hôtes pour l'option --auto-hosts. Utiliser cette option seule facilite grandement le débogage et le test de la fonctionnalité --auto-hosts.
--sudoers-no-modify
sshuttle imprime une configuration sur stdout qui permet à un utilisateur d'exécuter sshuttle sans mot de passe. Cette option est NON SÉCURISÉE car, avec un peu d'astuce, elle permet également à l'utilisateur d'exécuter n'importe quelle commande en tant que root sans mot de passe. La sortie comprend également une méthode suggérée pour installer la configuration.

Utilisez --sudoers-user pour modifier l'utilisateur auquel elle s'applique.

--sudoers-user
Définit le nom d'utilisateur ou le groupe avec %nom_du_groupe pour un fonctionnement sans mot de passe. La valeur par défaut est l'utilisateur actuel. Définissez sur ALL pour tous les utilisateurs (NON RECOMMANDÉ : Voir la note sur la sécurité dans la documentation de --sudoers-no-modify ci-dessus). Ne fonctionne qu'avec l'option --sudoers-no-modify.
-t <marqueur>, --tmark=<marqueur>
Une option utilisée par la méthode tproxy : utilise la marque de trafic spécifiée. La marque doit être une valeur hexadécimale. La valeur par défaut est 0x01.
--version
Affiche la version du programme.

FICHIER DE CONFIGURATION

Toutes les options décrites ci-dessus peuvent être spécifiées en option dans un fichier de configuration.

Pour exécuter sshuttle avec des options définies dans, par exemple, /etc/sshuttle.conf, passez simplement le chemin du fichier précédé du caractère @, par exemple @/etc/sshuttle.conf.

Lors de l'exécution de sshuttle avec des options définies dans un fichier de configuration, des options supplémentaires peuvent toujours être passées via la ligne de commande en plus de ce qui est défini dans le fichier. Si une option donnée est définie à la fois dans le fichier et dans la ligne de commande, la valeur de la ligne de commande aura la priorité.

Les arguments lus à partir d'un fichier doivent être un par ligne, comme montré ci-dessous :

valeur
--option1
valeur1
--option2
valeur2

Le fichier de configuration prend en charge les commentaires pour des annotations lisibles par l'homme. Par exemple :

# API interne de l'entreprise
8.8.8.8/32
# IoT domestique
192.168.63.0/24

VARIABLE D'ENVIRONNEMENT

Vous pouvez spécifier des options de ligne de commande avec la variable d'environnement SSHUTTLE_ARGS. Si une option donnée est définie à la fois dans la variable d'environnement et dans la ligne de commande, la valeur de la ligne de commande aura la priorité.

Par exemple :

SSHUTTLE_ARGS="-e 'ssh -v' --dns" sshuttle -r exemple.com 0/0

NOM


sshuttle - tunnel transparent proxy over ssh






SYNTAXE


sshuttle [-v] [-a] [-D] [-N] [-H] [-h] [-l local_ip] [-r remote_host] [--dns] [--pidfile pidfile] [--daemon] [--no-ipv6] [--no-check-certificate] [--ssh-cmd ssh] [--] --dest ...


sshuttle [-v] [-a] [-D] [-N] [-H] [-h] [-l local_ip] [-r remote_host] [--dns] [--pidfile pidfile] [--daemon] [--no-ipv6] [--no-check-certificate] [--ssh-cmd ssh] [--] --dest ...


sshuttle [-v] [-a] [-D] [-N] [-H] [-h] [-l local_ip] [-r remote_host] [--dns] [--pidfile pidfile] [--daemon] [--no-ipv6] [--no-check-certificate] [--ssh-cmd ssh] [--] --tofs ...






DESCRIPTION


sshuttle is a complete userland transparent proxy server. It
    allows you to specify a list of destinations, and it will create a VPN connection
    to the given remote server, forwarding sessions to those destinations through
    the tunnel. By default, it captures all outgoing TCP connections and forwards
    them. It is written in Python and uses the facilities of your kernel's transparent
    proxy (redirect marks on Linux, for example) to do this transparently. It
    does not require any special installation on the remote server, it just
    needs python. The program uploads its own source code to the server and runs
    it there.






OPTIONS


Supported options include:




-v, --verbose


Increase verbosity. Can be specified multiple times.


-a, --auto-screenshots


Automatically create screenshots when there is traffic. Only works on Linux.


-D, --daemon


Run as a background daemon. Also set by --daemon.


-N, --no-port-forwarding


Disable TCP port forwarding. Only relevant if you are running sshuttle on a
    remote server to make connections between local servers.


-H, --daemon-sethop


Set the hop count on outgoing IP packets to 1. This is useful for bypassing
    some restrictive firewalls, but it can break routing on some networks.


-h, --help


Show help message and exit.


-l local_ip


Listen for connections on the specified local IP address. Default is
    0.0.0.0.


-r remote_host


The remote hostname or IP address to connect to. This can be specified as
    ‘user@host:port’. If the port is not specified, 22 is used. If the user is
    not specified, the current user is used. This can also be specified as a
    list of hosts, in which case sshuttle will choose the fastest one.


--dns


Forward DNS requests to the remote server. This requires that the remote
    server is running a DNS server that can resolve the hostnames. This option
    is automatically enabled if you specify a list of destinations that includes
    a domain name.


--pidfile pidfile


Write the process ID to the specified file. This is useful when running
    sshuttle as a daemon.


--ssh-cmd ssh


The command to use for the SSH connection. This can be used to specify
    options for SSH, such as keys or ports.


--


All subsequent arguments are treated as destinations. This is useful if
    you need to specify a destination that starts with a dash.


--dest


A destination to forward. This can be a hostname, IP address, or CIDR
    notation (e.g., 192.168.0.0/16). If no destinations are specified, all
    outgoing TCP connections are forwarded.


--tofs


A destination to forward for file system operations. This is used by
    sshuttle-mount.








FICHIER DE CONFIGURATION


sshuttle can read configuration from a file specified using the
    @ syntax. The format of the configuration file is a list of destinations,
    one per line. Options can also be specified in the configuration file, one
    per line, starting with a dash.

VARIABLE D'ENVIRONNEMENT


sshuttle respects the following environment variables:

Equivalent to the -l option.

SSHUTTLE_OPTIONS


A string of options to pass to sshuttle. This is useful for setting default

EXEMPLES


Forward all outgoing TCP connections to the server 'example.com':






$ sshuttle -r example.com 0/0

    and enable DNS forwarding:






$ sshuttle --dns -r example.com 0/0






Forward connections to the 192.168.0.0/16 network via the server
    'example.com':






$ sshuttle -r example.com 192.168.0.0/16

    'example.com':






$ sshuttle --daemon -r example.com 0/0






Use a configuration file:






$ sshuttle @/etc/sshuttle.conf






Increase verbosity:






$ sshuttle -vvv










DISCUSSION


When it starts, sshuttle creates an ssh session to the
    server specified by the -r option.


After connecting to the remote server, sshuttle uploads its
    (python) source code to the remote end and executes it there. Thus, you
    don't need to install sshuttle on the remote server, and there are
    never sshuttle version conflicts between client and server.


Unlike most VPNs, sshuttle forwards sessions, not packets.
    That is, it uses kernel transparent proxying (iptables
    REDIRECT rules on Linux) to capture outgoing TCP sessions, then
    creates entirely separate TCP sessions out to the original destination at
    the other end of the tunnel.


Packet-level forwarding (eg. using the tun/tap devices on Linux)
    seems elegant at first, but it results in several problems, notably the 'tcp
    over tcp' problem. The tcp protocol depends fundamentally on packets being
    dropped in order to implement its congestion control algorithm; if you pass
    tcp packets through a tcp-based tunnel (such as ssh), the inner tcp packets
    will never be dropped, and so the inner tcp stream's congestion control will
    be completely broken, and performance will be terrible. Thus, packet-based
    VPNs (such as IPsec and openvpn) cannot use tcp-based encrypted streams like
    ssh or ssl, and have to implement their own encryption from scratch, which
    is very complex and error prone.


sshuttle's simplicity comes from the fact that it can
    safely use the existing ssh encrypted tunnel without incurring a performance
    penalty. It does this by letting the client-side kernel manage the incoming
    tcp stream, and the server-side kernel manage the outgoing tcp stream; there
    is no need for congestion control to be shared between the two separate
    streams, so a tcp-based tunnel is fine.
