NOM

sssd-ldap - Fournisseur LDAP de SSSD

DESCRIPTION

Cette page de manuel décrit la configuration des domaines LDAP pour sssd(8). Référez-vous à la section « FORMAT DE FICHIER » de la page de manuel sssd.conf(5) pour des détails de syntaxe.

Vous pouvez configurer SSSD pour utiliser plus d'un domaine LDAP.

Le backend LDAP prend en charge les fournisseurs d'identifiants, d'authentification, d'accès et de changement de mot de passe (chpass). Si vous souhaitez vous authentifier auprès d'un serveur LDAP, TLS/SSL ou LDAPS est requis. sssd ne prend pas en charge l'authentification sur un canal non chiffré. Même si le serveur LDAP n'est utilisé que comme fournisseur d'identité, un canal chiffré est fortement recommandé. Veuillez vous référer à l'option de configuration « ldap_access_filter » pour plus d'informations sur l'utilisation de LDAP comme fournisseur d'accès.

OPTIONS DE CONFIGURATION

Toutes les options de configuration courantes qui s'appliquent aux domaines SSSD s'appliquent également aux domaines LDAP. Référez-vous à la section « SECTIONS DE DOMAINE » de la page de manuel sssd.conf(5) pour des détails complets. Notez que les attributs de mappage LDAP de SSSD sont décrits dans la page de manuel sssd-ldap-attributes(5).

ldap_uri, ldap_backup_uri (chaîne)

Spécifie la liste des URI des serveurs LDAP, séparés par des virgules, auxquels SSSD doit se connecter, dans l'ordre de préférence. Référez-vous à la section « BASCULEMENT » pour plus d'informations sur le basculement et la redondance des serveurs. Si aucune des options n'est spécifiée, la découverte de service est activée. Pour plus d'informations, référez-vous à la section « DÉCOUVERTE DE SERVICE ».

Le format de l'URI doit correspondre au format défini dans la RFC 2732 :

ldap[s]://<hôte>[:port]

Pour les adresses IPv6 explicites, <hôte> doit être entouré de crochets [].

exemple : ldap://[fc00::126:25]:389

ldap_chpass_uri, ldap_chpass_backup_uri (chaîne)

Spécifie la liste des URI des serveurs LDAP, séparés par des virgules, auxquels SSSD doit se connecter, dans l'ordre de préférence, pour changer le mot de passe d'un utilisateur. Référez-vous à la section « BASCULEMENT » pour plus d'informations sur le basculement et la redondance des serveurs.

Pour activer la découverte de service, ldap_chpass_dns_service_name doit être défini.

Par défaut : vide, c'est-à-dire que ldap_uri est utilisé.

ldap_search_base (chaîne)

Le DN de base par défaut à utiliser pour les opérations utilisateur LDAP.

À partir de SSSD 1.7.0, SSSD prend en charge plusieurs bases de recherche en utilisant la syntaxe :

search_base[?scope?[filter][?search_base?scope?[filter]]*]

La portée peut être l'une des valeurs suivantes : « base », « onelevel » ou « subtree ».

Le filtre doit être un filtre de recherche LDAP valide tel que spécifié par http://www.ietf.org/rfc/rfc2254.txt

Exemples :

ldap_search_base = dc=example,dc=com (ce qui équivaut à) ldap_search_base = dc=example,dc=com?subtree?

ldap_search_base = cn=host_specific,dc=example,dc=com?subtree?(host=thishost)?dc=example.com?subtree?

Note : Il n'est pas pris en charge d'avoir plusieurs bases de recherche qui référencent des objets portant des noms identiques (par exemple, des groupes portant le même nom dans deux bases de recherche différentes). Cela entraînera un comportement imprévisible sur les machines clientes.

Par défaut : S'il n'est pas défini, la valeur de l'attribut defaultNamingContext ou namingContexts du RootDSE du serveur LDAP est utilisée. Si defaultNamingContext n'existe pas ou a une valeur vide, namingContexts est utilisé. L'attribut namingContexts doit avoir une seule valeur avec le DN de la base de recherche du serveur LDAP pour que cela fonctionne. Les valeurs multiples ne sont pas prises en charge.

ldap_read_rootdse (chaîne)

SSSD lit le RootDSE pour obtenir des informations sur LDAP et ses capacités. Par défaut, cela se fait anonymement. Cependant, cela peut ne pas être autorisé par le serveur LDAP. Dans de tels cas, nous pouvons utiliser cette option pour influencer le comportement de SSSD.

Les valeurs autorisées sont :

•anonymous
•authenticated
•never

Par défaut, en utilisant l'option « anonymous », SSSD tente de lire le RootDSE anonymement. Si cela échoue, SSSD retente l'opération avec authentification.

Par défaut : anonymous

ldap_schema (chaîne)

Spécifie le type de schéma utilisé sur le serveur LDAP cible. En fonction du schéma sélectionné, les noms d'attributs par défaut récupérés des serveurs peuvent varier. La manière dont certains attributs sont gérés peut également différer.

Quatre types de schémas sont actuellement pris en charge :

•rfc2307
•rfc2307bis
•IPA
•AD

La principale différence entre ces types de schémas réside dans la manière dont les appartenances aux groupes sont enregistrées sur le serveur. Avec rfc2307, les membres de groupe sont listés par nom dans l'attribut memberUid. Avec rfc2307bis et IPA, les membres de groupe sont listés par DN et stockés dans l'attribut member. Le type de schéma AD définit les attributs pour correspondre aux valeurs d'Active Directory 2008r2.

Par défaut : rfc2307

ldap_pwmodify_mode (chaîne)

Spécifie l'opération utilisée pour modifier le mot de passe de l'utilisateur.

Deux modes sont actuellement pris en charge :

•exop - Opération étendue de modification de mot de passe (RFC 3062)
•ldap_modify - Modification directe de userPassword (non recommandé).
•exop_force - Tente l'opération étendue de modification de mot de passe (RFC 3062) même s'il ne reste plus de connexions de grâce. Selon le type et la configuration du serveur LDAP, la modification du mot de passe peut échouer car une liaison authentifiée n'est pas possible.

Note : Tout d'abord, une nouvelle connexion est établie pour vérifier le mot de passe actuel en se liant en tant qu'utilisateur ayant demandé la modification du mot de passe. Si elle réussit, cette connexion est utilisée pour changer le mot de passe, par conséquent l'utilisateur doit avoir un accès en écriture à l'attribut userPassword.

Par défaut : exop

Le type de jeton d'authentification du DN de liaison par défaut.

password

Certains serveurs d'annuaire, par exemple Active Directory, peuvent fournir la partie domaine (realm) de l'UPN en minuscules, ce qui peut entraîner l'échec de l'authentification. Définissez cette option sur une valeur non nulle si vous souhaitez utiliser un domaine en majuscules.

Spécifie combien de secondes SSSD doit attendre avant de rafraîchir son cache des enregistrements énumérés.

Par défaut : 300

ldap_purge_cache_timeout (entier)

Détermine la fréquence à laquelle vérifier le cache des entrées inactives (telles que les groupes sans membres et les utilisateurs qui ne se sont jamais connectés) et les supprimer pour économiser de l'espace.

ldap_search_timeout (entier)

Spécifie le délai d'attente (en secondes) pendant lequel les recherches LDAP sont autorisées à s'exécuter avant d'être annulées et que les résultats mis en cache soient retournés (et que le mode hors ligne soit entré).

Remarque : cette option est susceptible d'être modifiée dans les futures versions de SSSD. Elle sera probablement remplacée à un moment donné par une série de délais d'attente pour des types de recherche spécifiques.

Cette option peut également être définie par sous-domaine ou héritée via subdomain_inherit.

Par défaut : 6

ldap_enumeration_search_timeout (entier)

Spécifie le délai d'attente (en secondes) pendant lequel les recherches LDAP pour les énumérations d'utilisateurs et de groupes sont autorisées à s'exécuter avant d'être annulées et que les résultats mis en cache soient retournés (et que le mode hors ligne soit entré).

Par défaut : 60

ldap_network_timeout (entier)

Spécifie le délai d'attente (en secondes) après lequel le poll(2) / select(2) suivant un connect(2) retourne en cas d'absence d'activité.

Cette option peut également être définie par sous-domaine ou héritée via subdomain_inherit.

Par défaut : 6

ldap_opt_timeout (entier)

Spécifie un délai d'attente (en secondes) après lequel les appels aux API LDAP synchrones seront annulés si aucune réponse n'est reçue. Contrôle également le délai d'attente lors de la communication avec le KDC en cas de liaison SASL, le délai d'attente d'une opération de liaison LDAP, d'une opération étendue de changement de mot de passe et de l'opération StartTLS.

Cette option peut également être définie par sous-domaine ou héritée via subdomain_inherit.

Par défaut : 8

ldap_connection_expire_timeout (entier)

Spécifie un délai d'attente (en secondes) pendant lequel une connexion à un serveur LDAP sera maintenue. Après ce délai, la connexion sera rétablie. Si elle est utilisée en parallèle avec SASL/GSSAPI, la plus petite des deux valeurs (cette valeur vs la durée de vie du TGT) sera utilisée.

Si la connexion est inactive (pas d'opération en cours) dans les ldap_opt_timeout secondes avant l'expiration, elle sera fermée plus tôt pour garantir qu'une nouvelle requête ne nécessite pas que la connexion reste ouverte au-delà de son expiration. Cela implique que les connexions seront toujours fermées immédiatement et ne seront jamais réutilisées si ldap_connection_expire_timeout <= ldap_opt_timout.

Ce délai d'attente peut être prolongé d'une valeur aléatoire spécifiée par ldap_connection_expire_offset.

Cette option peut également être définie par sous-domaine ou héritée via subdomain_inherit.

Par défaut : 900 (15 minutes)

ldap_connection_expire_offset (entier)

Un décalage aléatoire entre 0 et la valeur configurée est ajouté à ldap_connection_expire_timeout.

Cette option peut également être définie par sous-domaine ou héritée via subdomain_inherit.

Par défaut : 0

ldap_connection_idle_timeout (entier)

Spécifie un délai d'attente (en secondes) pendant lequel une connexion inactive à un serveur LDAP sera maintenue. Si la connexion est inactive pendant plus de ce temps, elle sera fermée.

Vous pouvez désactiver ce délai d'attente en définissant la valeur sur 0.

Cette option peut également être définie par sous-domaine ou héritée via subdomain_inherit.

Par défaut : 900 (15 minutes)

ldap_page_size (entier)

Spécifie le nombre d'enregistrements à récupérer de LDAP en une seule requête. Certains serveurs LDAP imposent une limite maximale par requête.

Par défaut : 1000

ldap_disable_paging (booléen)

Désactive le contrôle de pagination LDAP. Cette option doit être utilisée si le serveur LDAP signale qu'il prend en charge le contrôle de pagination LDAP dans son RootDSE, mais qu'il n'est pas activé ou ne se comporte pas correctement.

Exemple : les serveurs OpenLDAP avec le module de contrôle de pagination installé sur le serveur mais non activé le signaleront dans le RootDSE mais seront incapables de l'utiliser.

Exemple : 389 DS a un bug où il ne peut prendre en charge qu'un seul contrôle de pagination à la fois sur une seule connexion. Sur les clients très sollicités, cela peut entraîner le refus de certaines requêtes.

Par défaut : False

ldap_disable_range_retrieval (booléen)

Désactive la récupération de plage Active Directory.

Active Directory limite le nombre de membres pouvant être récupérés en une seule recherche à l'aide de la politique MaxValRange, qui est par défaut de 1500 membres. Si un groupe contient plus de 1500 membres, la réponse inclut une extension de plage spécifique à AD. Lorsque cette option est activée, elle empêche SSSD d'analyser l'extension de plage. Par conséquent, les grands groupes apparaîtront comme s'ils n'avaient aucun membre. Cette option n'autorise pas SSSD à lire les plages suivantes. Pour récupérer tous les membres d'un groupe, vous devez augmenter le paramètre MaxValRange dans Active Directory.

Par défaut : False

ldap_sasl_minssf (entier)

Lors de la communication avec un serveur LDAP à l'aide de SASL, spécifiez le niveau de sécurité minimum nécessaire pour établir la connexion. Les valeurs de cette option sont définies par OpenLDAP.

Par défaut : Utiliser la valeur par défaut du système (généralement spécifiée par ldap.conf)

ldap_sasl_maxssf (entier)

Lors de la communication avec un serveur LDAP à l'aide de SASL, spécifiez le niveau de sécurité maximal nécessaire pour établir la connexion. Les valeurs de cette option sont définies par OpenLDAP.

Par défaut : Utiliser la valeur par défaut du système (généralement spécifiée par ldap.conf)

ldap_deref_threshold (entier)

Spécifiez le nombre de membres du groupe qui doivent être manquants dans le cache interne pour déclencher une recherche de déréférencement. Si moins de membres sont manquants, ils sont recherchés individuellement.

Vous pouvez désactiver complètement les recherches de déréférencement en définissant la valeur sur 0. Veuillez noter qu'il existe des chemins de code dans SSSD, tels que le fournisseur IPA HBAC, qui sont uniquement implémentés à l'aide de l'appel de déréférencement, donc même avec le déréférencement explicitement désactivé, ces parties utiliseront toujours le déréférencement si le serveur le prend en charge et annonce le contrôle de déréférencement dans l'objet rootDSE.

Une recherche de déréférencement est un moyen de récupérer tous les membres d'un groupe en un seul appel LDAP. Différents serveurs LDAP peuvent implémenter différentes méthodes de déréférencement. Les serveurs actuellement pris en charge sont 389/RHDS, OpenLDAP et Active Directory.

Remarque : Si l'une des bases de recherche spécifie un filtre de recherche, l'amélioration des performances de recherche de déréférencement sera désactivée quelle que soit cette option.

Par défaut : 10

ldap_ignore_unreadable_references (bool)

Ignorer les entrées LDAP illisibles référencées
dans les groupes attribut `member`. Si ce paramètre est défini sur `false`, une erreur sera retournée et l'opération échouera au lieu de simplement ignorer l'entrée illisible.

Ce paramètre peut être utile lors de l'utilisation du fournisseur AD et que le compte d'ordinateur que sssd utilise pour se connecter à AD n'a pas accès à une entrée particulière ou à un sous-arbre LDAP pour des raisons de sécurité.

Par défaut : `false`

ldap_tls_reqcert (string)

Spécifie les vérifications à effectuer sur les certificats du serveur dans une session TLS, le cas échéant. Il peut être spécifié comme l'une des valeurs suivantes :

never = Le client ne demandera ni ne vérifiera aucun certificat serveur.

allow = Le certificat du serveur est demandé. Si aucun certificat n'est fourni, la session se poursuit normalement. Si un certificat invalide est fourni, il sera ignoré et la session se poursuivra normalement.

try = Le certificat du serveur est demandé. Si aucun certificat n'est fourni, la session se poursuit normalement. Si un certificat invalide est fourni, la session est immédiatement terminée.

demand = Le certificat du serveur est demandé. Si aucun certificat n'est fourni, ou si un certificat invalide est fourni, la session est immédiatement terminée.

hard = Identique à « demand »

Par défaut : `hard`

Spécifie le fichier contenant les certificats de toutes les autorités de certification que sssd reconnaîtra.

Par défaut : utilise les valeurs par défaut d'OpenLDAP, généralement dans /etc/openldap/ldap.conf

Généralement, les noms de fichiers doivent être le hachage du certificat suivi de '.0'. Si disponible, openssl rehash ou c_rehash peut être utilisé pour créer les noms corrects.

Par défaut : utilise les valeurs par défaut d'OpenLDAP, généralement dans /etc/openldap/ldap.conf

Spécifie les suites de chiffrement acceptables. Généralement, il s'agit d'une liste séparée par des deux-points. Voir ldap.conf(5) pour le format.

Par défaut : utilise les valeurs par défaut d'OpenLDAP, généralement dans /etc/openldap/ldap.conf

ldap_id_use_start_tls (boolean)

Spécifie que la connexion du fournisseur d'identité (`id_provider`) doit également utiliser TLS pour protéger le canal. La valeur true est fortement recommandée pour des raisons de sécurité.

Par défaut : `true`

ldap_id_mapping (boolean)

Spécifie que SSSD doit tenter de mapper les identifiants utilisateur et groupe à partir des attributs `ldap_user_objectsid` et `ldap_group_objectsid` au lieu de s'appuyer sur `ldap_user_uid_number` et `ldap_group_gid_number`.

Actuellement, cette fonctionnalité ne prend en charge que le mappage des objectSID d'Active Directory.

Par défaut : `false`

ldap_min_id, ldap_max_id (integer)

Contrairement au mappage d'ID basé sur SID qui est utilisé si `ldap_id_mapping` est défini sur `true`, la plage d'ID autorisée pour `ldap_user_uid_number` et `ldap_group_gid_number` est illimitée. Dans une configuration avec des domaines enfants/trusted, cela pourrait entraîner des collisions d'ID. Pour éviter les collisions, `ldap_min_id` et `ldap_max_id` peuvent être définis pour restreindre la plage autorisée pour les ID lus directement depuis le serveur. Les domaines enfants peuvent alors choisir d'autres plages pour mapper les ID.

Par défaut : non défini (les deux options sont définies sur 0)

ldap_sasl_mech (string)

Spécifie le mécanisme SASL à utiliser. Actuellement, seuls GSSAPI et GSS-SPNEGO sont testés et pris en charge.

Si le backend prend en charge les domaines enfants, la valeur de `ldap_sasl_mech` est automatiquement héritée par les domaines enfants. Si une valeur différente est nécessaire pour un domaine enfant, elle peut être remplacée en définissant explicitement `ldap_sasl_mech` pour ce domaine enfant. Veuillez consulter la section DOMAINES TRUSTED dans sssd.conf(5) pour plus de détails.

Par défaut : non défini

ldap_sasl_authid (string)

Spécifie l'ID d'autorisation SASL à utiliser. Lorsque GSSAPI/GSS-SPNEGO sont utilisés, cela représente le principal Kerberos utilisé pour l'authentification auprès du répertoire. Cette option peut contenir le principal complet (par exemple, `host/myhost@EXAMPLE.COM`) ou simplement le nom du principal (par exemple, `host/myhost`). Par défaut, la valeur n'est pas définie et les principaux suivants sont utilisés : 
hostname@REALM
netbiosname$@REALM
host/hostname@REALM
*$@REALM
host/*@REALM
host/*

Si aucun d'entre eux n'est trouvé, le premier principal du keytab est retourné.

Par défaut : `host/hostname@REALM`

ldap_sasl_realm (string)

ldap_sasl_canonicalize (boolean)

Si défini sur `true`, la bibliothèque LDAP effectuera une recherche inversée pour canoniser le nom d'hôte lors d'une liaison SASL.

Spécifie le keytab à utiliser lors de l'utilisation de SASL/GSSAPI/GSS-SPNEGO.

ldap_krb5_init_creds (boolean)

Spécifie que le fournisseur d'identité (`id_provider`) doit initialiser les informations d'identification Kerberos (TGT). Cette action n'est effectuée que si SASL est utilisé et que le mécanisme sélectionné est GSSAPI ou GSS-SPNEGO.

ldap_krb5_ticket_lifetime (integer)

Spécifie la durée de vie en secondes du TGT si GSSAPI ou GSS-SPNEGO est utilisé.

Cette option peut également être définie par domaine enfant ou héritée via subdomain_inherit.

Par défaut : 86400 (24 heures)

krb5_server, krb5_backup_server (string)

Spécifie la liste séparée par des virgules des adresses IP ou des noms d'hôtes des serveurs Kerberos auxquels SSSD doit se connecter, dans l'ordre de préférence. Pour plus d'informations sur le basculement et la redondance des serveurs, voir la section « BASCULEMENT ». Un numéro de port optionnel (précédé d'un deux-points) peut être ajouté aux adresses ou aux noms d'hôtes. Lors de l'utilisation de la découverte de service pour les serveurs KDC ou kpasswd, SSSD recherche d'abord les entrées DNS qui spécifient _udp comme protocole et revient à _tcp si aucune n'est trouvée.

Cette option s'appelait « krb5_kdcip » dans les versions antérieures de SSSD. Bien que le nom hérité soit reconnu pour le moment, il est conseillé aux utilisateurs de migrer leurs fichiers de configuration pour utiliser « krb5_server » à la place.

Spécifie le DOMAINE Kerberos (pour l'authentification SASL/GSSAPI/GSS-SPNEGO).

Par défaut : Valeurs par défaut du système, voir /etc/krb5.conf

krb5_canonicalize (boolean)

Spécifie si le principal hôte doit être canonisé lors de la connexion au serveur LDAP. Cette fonctionnalité est disponible avec MIT Kerberos >= 1.7.

Par défaut : `false`

krb5_use_kdcinfo (boolean)

Spécifie si SSSD doit indiquer aux bibliothèques Kerberos quel domaine et quels KDC utiliser. Cette option est activée par défaut. Si vous la désactivez, vous devez configurer la bibliothèque Kerberos à l'aide du fichier de configuration krb5.conf(5).

Voir la page de manuel sssd_krb5_locator_plugin(8) pour plus d'informations sur le plugin localisateur.

Par défaut : `true`

ldap_pwd_policy (string)

Sélectionne la politique pour évaluer l'expiration du mot de passe côté client. Les valeurs suivantes sont autorisées :

none - Aucune évaluation côté client. Cette option ne peut pas désactiver les politiques de mot de passe côté serveur.

shadow - Utilise les attributs de style shadow(5) pour évaluer si le mot de passe a expiré. Veuillez également consulter l'option « ldap_chpass_update_last_change ».

mit_kerberos - Utilise les attributs utilisés par MIT Kerberos pour déterminer si le mot de passe a expiré. Utilisez `chpass_provider=krb5` pour mettre à jour ces attributs lors du changement de mot de passe.

Par défaut : `none`

Remarque : si une politique de mot de passe est configurée côté serveur, elle a toujours la priorité sur la politique définie avec cette option.

ldap_referrals (boolean)

Spécifie si le suivi automatique des renvois doit être activé.

Veuillez noter que sssd ne prend en charge le renvoi des renvois que s'il est compilé avec OpenLDAP version 2.4.13 ou supérieure.

Le suivi des renvois peut entraîner une pénalité de performance dans les environnements qui les utilisent intensivement, un exemple notable étant Microsoft Active Directory. Si votre configuration n'exige pas réellement l'utilisation de renvois, la définition de cette option sur `false` pourrait apporter une amélioration notable des performances. Il est donc recommandé de définir cette option sur `false` si le fournisseur LDAP de SSSD est utilisé avec Microsoft Active Directory comme backend. Même si SSSD était capable de suivre le renvoi vers un autre contrôleur de domaine AD, aucune donnée supplémentaire ne serait disponible.

Par défaut : `true`

ldap_dns_service_name (string)

Spécifie le nom du service à utiliser lorsque la découverte de service est activée.

Par défaut : `ldap`

ldap_chpass_dns_service_name (string)

Spécifie le nom du service à utiliser pour trouver un serveur LDAP qui autorise les modifications de mot de passe lorsque la découverte de service est activée.

Par défaut : non défini, c'est-à-dire que la découverte de service est désactivée

ldap_chpass_update_last_change (bool)

Spécifie s'il faut mettre à jour l'attribut `ldap_user_shadow_last_change` avec le nombre de jours depuis l'Epoch après une opération de changement de mot de passe.

Il est recommandé de définir explicitement cette option si « ldap_pwd_policy = shadow » est utilisé, afin que SSSD sache si le serveur LDAP mettra à jour automatiquement l'attribut `shadowLastChange` LDAP après un changement de mot de passe, ou si SSSD doit le mettre à jour.

Par défaut : `False`

ldap_access_filter (string)

Si vous utilisez `access_provider = ldap` et `ldap_access_order = filter` (par défaut), cette option est obligatoire. Elle spécifie un critère de filtre de recherche LDAP qui doit être rempli pour que l'utilisateur accède à cet hôte. Si `access_provider = ldap`, `ldap_access_order = filter` et que cette option n'est pas définie, tous les utilisateurs se verront refuser l'accès. Utilisez
access_provider = permit pour changer ce comportement par défaut. Veuillez noter que ce filtre est appliqué sur l'entrée utilisateur LDAP uniquement et que le filtrage basé sur des groupes imbriqués peut ne pas fonctionner (par exemple, l'attribut memberOf sur les entrées AD ne pointe que vers les parents directs). Si un filtrage basé sur des groupes imbriqués est requis, veuillez consulter sssd-simple(5).

Exemple :

access_provider = ldap
ldap_access_filter = (employeeType=admin)

Cet exemple signifie que l'accès à cet hôte est limité aux utilisateurs dont l'attribut employeeType est défini sur "admin".

La mise en cache hors ligne pour cette fonctionnalité est limitée à la détermination si la dernière connexion en ligne de l'utilisateur a accordé l'autorisation d'accès. S'ils ont obtenu l'accès lors de leur dernière connexion, ils continueront à avoir l'accès hors ligne et vice versa.

Par défaut : Vide

ldap_account_expire_policy (string)

Avec cette option, une évaluation côté client des attributs de contrôle d'accès peut être activée.

Veuillez noter qu'il est toujours recommandé d'utiliser le contrôle d'accès côté serveur, c'est-à-dire que le serveur LDAP devrait refuser la demande de liaison avec un code d'erreur approprié, même si le mot de passe est correct.

Les valeurs suivantes sont autorisées :

shadow : utilise la valeur de ldap_user_shadow_expire pour déterminer si le compte a expiré.

ad : utilise la valeur du champ 32 bits ldap_user_ad_user_account_control et autorise l'accès si le deuxième bit n'est pas défini. Si l'attribut est manquant, l'accès est accordé. L'heure d'expiration du compte est également vérifiée.

rhds, ipa, 389ds : utilise la valeur de ldap_ns_account_lock pour vérifier si l'accès est autorisé ou non.

nds : les valeurs de ldap_user_nds_login_allowed_time_map, ldap_user_nds_login_disabled et ldap_user_nds_login_expiration_time sont utilisées pour vérifier si l'accès est autorisé. Si les deux attributs sont manquants, l'accès est accordé.

Veuillez noter que l'option de configuration ldap_access_order *doit* inclure "expire" pour que l'option ldap_account_expire_policy fonctionne.

Par défaut : Vide

ldap_access_order (string)

Liste séparée par des virgules des options de contrôle d'accès. Les valeurs autorisées sont :

filter : utilise ldap_access_filter

lockout : utilise le verrouillage de compte. Si défini, cette option refuse l'accès au cas où l'attribut LDAP 'pwdAccountLockedTime' est présent et a la valeur '000001010000Z'. Veuillez consulter l'option ldap_pwdlockout_dn. Veuillez noter que 'access_provider = ldap' doit être défini pour que cette fonctionnalité fonctionne.

Veuillez noter que cette option est remplacée par l'option "ppolicy" et pourrait être supprimée dans une future version.

ppolicy : utilise le verrouillage de compte. Si défini, cette option refuse l'accès si l'attribut LDAP 'pwdAccountLockedTime' est présent et a la valeur '000001010000Z' ou représente une date passée. La valeur de l'attribut 'pwdAccountLockedTime' doit se terminer par 'Z', qui désigne le fuseau horaire UTC. Les autres fuseaux horaires ne sont pas actuellement pris en charge et entraîneront un "accès refusé" lorsque les utilisateurs tenteront de se connecter. Veuillez consulter l'option ldap_pwdlockout_dn. Veuillez noter que 'access_provider = ldap' doit être défini pour que cette fonctionnalité fonctionne.

expire : utilise ldap_account_expire_policy

pwd_expire_policy_reject, pwd_expire_policy_warn, pwd_expire_policy_renew : Ces options sont utiles si les utilisateurs souhaitent être avertis que leur mot de passe est sur le point d'expirer et que l'authentification est basée sur une méthode autre que les mots de passe, par exemple les clés SSH.

La différence entre ces options réside dans l'action effectuée si le mot de passe de l'utilisateur a expiré :

•pwd_expire_policy_reject - l'utilisateur ne peut pas se connecter,
•pwd_expire_policy_warn - l'utilisateur peut toujours se connecter,
•pwd_expire_policy_renew - l'utilisateur est invité à changer son mot de passe immédiatement.

Veuillez noter que 'access_provider = ldap' doit être défini pour que cette fonctionnalité fonctionne. De plus, 'ldap_pwd_policy' doit être défini sur shadow ou mit_kerberos, ces options ne fonctionnent pas avec les politiques de mot de passe côté serveur.

authorized_service : utilise l'attribut authorizedService pour déterminer l'accès

host : utilise l'attribut host pour déterminer l'accès

rhost : utilise l'attribut rhost pour déterminer si l'hôte distant peut accéder

Veuillez noter que le champ rhost dans pam est défini par l'application, il est préférable de vérifier ce que l'application envoie à pam avant d'activer cette option de contrôle d'accès.

Par défaut : filter

Veuillez noter que c'est une erreur de configuration si une valeur est utilisée plus d'une fois.

ldap_pwdlockout_dn (string)

Cette option spécifie le DN de l'entrée de politique de mot de passe sur le serveur LDAP. Veuillez noter que l'absence de cette option dans sssd.conf en cas de vérification du verrouillage de compte activée entraînera un refus d'accès car les attributs ppolicy sur le serveur LDAP ne peuvent pas être vérifiés correctement.

Exemple : cn=ppolicy,ou=policies,dc=example,dc=com

Par défaut : cn=ppolicy,ou=policies,$ldap_search_base

ldap_deref (string)

Spécifie comment la désindirection des alias est effectuée lors d'une recherche. Les options suivantes sont autorisées :

never : Les alias ne sont jamais désindirigés.

searching : Les alias sont désindirigés dans les subordonnés de l'objet de base, mais pas dans la localisation de l'objet de base de la recherche.

finding : Les alias ne sont désindirigés que lors de la localisation de l'objet de base de la recherche.

always : Les alias sont désindirigés à la fois lors de la recherche et de la localisation de l'objet de base de la recherche.

Par défaut : Vide (ceci est traité comme never par les bibliothèques clientes LDAP)

ldap_rfc2307_fallback_to_local_users (boolean)

Permet de conserver les utilisateurs locaux en tant que membres d'un groupe LDAP pour les serveurs qui utilisent le schéma RFC2307.

Dans certains environnements où le schéma RFC2307 est utilisé, les utilisateurs locaux sont ajoutés comme membres de groupes LDAP en ajoutant leurs noms à l'attribut memberUid. L'auto-cohérence du domaine est compromise lorsque cela est fait, de sorte que SSSD supprimait normalement les utilisateurs "manquants" des appartenances de groupe mises en cache dès que nsswitch tente de récupérer des informations sur l'utilisateur via des appels getpw*() ou initgroups().

Cette option revient à vérifier si les utilisateurs locaux sont référencés et les met en cache afin que les appels initgroups() ultérieurs complètent les utilisateurs locaux avec les groupes LDAP supplémentaires.

Par défaut : false

wildcard_limit (integer)

Spécifie une limite supérieure sur le nombre d'entrées téléchargées lors d'une recherche de wildcard.

Pour le moment, seul le répondeur InfoPipe prend en charge les recherches de wildcard.

Par défaut : 1000 (souvent la taille d'une page)

ldap_library_debug_level (integer)

Active le débogage de libldap avec le niveau donné. Les messages de débogage de libldap seront écrits indépendamment du niveau de débogage général.

OpenLDAP utilise un masque de bits pour activer le débogage pour des composants spécifiques, -1 activera une sortie de débogage complète.

Par défaut : 0 (débogage libldap désactivé)

ldap_use_ppolicy (boolean)

Active la demande et la prise en compte des contrôles de politique de mot de passe côté serveur. La désactivation permet d'interagir avec des services qui renvoient des extensions ppolicy invalides.

Par défaut : true

ldap_ppolicy_pwd_change_threshold (integer)

Force un changement de mot de passe lorsque les contrôles de politique de mot de passe côté serveur sont activés et que les connexions de grâce restantes renvoyées par le serveur après l'authentification atteignent ou descendent en dessous du seuil. Notez que la valeur minimale utile est 2, car le changement de mot de passe consomme 2 connexions de grâce supplémentaires, une pour vérifier le mot de passe actuel et une seconde pour effectuer le changement de mot de passe.

Par défaut : 0

OPTIONS SUDO

Les instructions détaillées pour la configuration de sudo_provider se trouvent dans la page de manuel sssd-sudo(5).

ldap_sudo_full_refresh_interval (integer)

Nombre de secondes SSSD attendra entre l'exécution d'un rafraîchissement complet des règles sudo (qui télécharge toutes les règles stockées sur le serveur).

La valeur doit être supérieure à ldap_sudo_smart_refresh_interval.

Vous pouvez désactiver le rafraîchissement complet en définissant cette option sur 0. Cependant, le rafraîchissement intelligent ou complet doit être activé.

Par défaut : 21600 (6 heures)

ldap_sudo_smart_refresh_interval (integer)

Nombre de secondes SSSD doit attendre avant d'exécuter un rafraîchissement intelligent des règles sudo (qui télécharge toutes les règles dont l'USN est supérieur à la valeur USN du serveur la plus élevée actuellement connue par SSSD).

Si les attributs USN ne sont pas pris en charge par le serveur, l'attribut modifyTimestamp est utilisé à la place.

Note : la valeur USN la plus élevée peut être mise à jour par trois tâches : 1) Par le rafraîchissement sudo complet et intelligent (si des règles mises à jour sont trouvées), 2) Par l'énumération des utilisateurs et des groupes (si activée et si des utilisateurs ou groupes mis à jour sont trouvés) et 3) En se reconnectant au serveur (par défaut toutes les 15 minutes, voir ldap_connection_expire_timeout).

Vous pouvez désactiver le rafraîchissement intelligent en définissant cette option sur 0. Cependant, le rafraîchissement intelligent ou complet doit être activé.

Par défaut : 900 (15 minutes)

ldap_sudo_random_offset (integer)

Un décalage aléatoire entre 0 et la valeur configurée est ajouté aux périodes de rafraîchissement intelligent et complet chaque fois que la tâche périodique est planifiée. La valeur est en secondes.

Notez que ce décalage aléatoire est également appliqué au premier démarrage de SSSD, ce qui retarde le premier rafraîchissement des règles sudo. Cela prolonge le temps pendant lequel les règles sudo ne sont pas disponibles pour utilisation.

Vous pouvez désactiver ce décalage en définissant la valeur sur 0.

Par défaut : 0 (désactivé)

ldap_sudo_use_host_filter (boolean)

Si vrai, SSSD téléchargera uniquement les règles applicables à cette machine (en utilisant les adresses IPV4 ou IPV6 et les noms d'hôte).

Par défaut : true

ldap_sudo_hostnames (string)

Liste de noms d'hôte ou de noms de domaine complets séparés par des espaces qui devraient être utilisés pour filtrer les règles.

Si cette option est vide, SSSD essaiera de découvrir automatiquement le nom d'hôte et le nom de domaine complet.

Si ldap_sudo_use_host_filter est false, cette option n'a aucun effet.

Par défaut : non spécifié

ldap_sudo_ip (string)

Liste d'adresses IPv4 ou IPv6 d'hôtes/réseaux séparées par des espaces qui devraient être utilisées
pour filtrer les règles.

Si cette option est vide, SSSD tentera de découvrir les adresses automatiquement.

Si ldap_sudo_use_host_filter est false, alors cette option n'a aucun effet.

Par défaut : non spécifié

ldap_sudo_include_netgroups (booléen)

Si vrai, SSSD téléchargera toutes les règles qui contiennent un netgroup dans l'attribut sudoHost.

Si ldap_sudo_use_host_filter est false, alors cette option n'a aucun effet.

Par défaut : vrai

ldap_sudo_include_regexp (booléen)

Si vrai, SSSD téléchargera toutes les règles qui contiennent un joker dans l'attribut sudoHost.

Si ldap_sudo_use_host_filter est false, alors cette option n'a aucun effet.


Note
L'utilisation de jokers est une opération très coûteuse à évaluer côté serveur LDAP !
Par défaut : faux

La portée peut être l'une des valeurs suivantes : "base", "onelevel" ou "subtree". La portée fonctionne comme spécifié dans la section 4.5.1.2 de http://tools.ietf.org/html/rfc4511

Le filtre doit être un filtre de recherche LDAP valide tel que spécifié par http://www.ietf.org/rfc/rfc2254.txt

Pour des exemples de cette syntaxe, veuillez vous référer à la section des exemples de “ldap_search_base”.

Par défaut : la valeur de ldap_search_base

Veuillez noter que la spécification de la portée ou du filtre n'est pas prise en charge pour les recherches contre un serveur Active Directory qui pourrait renvoyer un grand nombre de résultats et déclencher l'extension de récupération de plage dans la réponse.

BASCULE

La fonctionnalité de bascule permet aux backends de passer automatiquement à un autre serveur si le serveur actuel échoue.

Syntaxe de bascule

La liste des serveurs est donnée sous forme de liste séparée par des virgules ; tout nombre d'espaces est autorisé autour de la virgule. Les serveurs sont listés par ordre de préférence. La liste peut contenir n'importe quel nombre de serveurs.

Pour chaque option de configuration activée pour la bascule, il existe deux variantes : primaire et secours. L'idée est que les serveurs de la liste primaire sont préférés et que les serveurs de secours ne sont recherchés que si aucun serveur primaire ne peut être atteint. Si un serveur de secours est sélectionné, un délai d'expiration de 31 secondes est défini. Après ce délai, SSSD tentera périodiquement de se reconnecter à l'un des serveurs primaires. S'il réussit, il remplacera le serveur actif actuel (de secours).

Le mécanisme de bascule

Le mécanisme de bascule distingue une machine d'un service. Le backend tente d'abord de résoudre le nom d'hôte d'une machine donnée ; si cette tentative de résolution échoue, la machine est considérée comme hors ligne. Aucune autre tentative n'est faite pour se connecter à cette machine pour un autre service. Si la tentative de résolution réussit, le backend tente de se connecter à un service sur cette machine. Si la tentative de connexion au service échoue, alors seul ce service particulier est considéré comme hors ligne et le backend bascule automatiquement vers le service suivant. La machine est toujours considérée comme en ligne et peut toujours être essayée pour un autre service.

D'autres tentatives de connexion seront effectuées vers les machines ou services marqués comme hors ligne après un délai spécifié ; ceci est actuellement codé en dur à 30 secondes.

S'il n'y a plus de machines à essayer, le backend dans son ensemble passe en mode hors ligne, puis tente de se reconnecter toutes les 30 secondes.

Délais d'attente et réglage de la bascule

Réglage

La résolution d'un serveur auquel se connecter peut être aussi simple que d'exécuter une seule requête DNS, ou impliquer plusieurs étapes, telles que la recherche du bon site ou l'essai de plusieurs noms d'hôte au cas où certains des serveurs configurés ne seraient pas joignables. Les scénarios les plus complexes peuvent prendre du temps et SSSD doit trouver un équilibre entre accorder suffisamment de temps pour terminer le processus de résolution et, d'autre part, ne pas essayer trop longtemps avant de revenir au mode hors ligne. Si les journaux de débogage de SSSD indiquent que la résolution du serveur expire avant qu'un serveur actif ne soit contacté, vous pouvez envisager de modifier les délais d'attente.

Cette section liste les éléments réglables disponibles. Veuillez vous référer à leur description dans la page de manuel sssd.conf(5).

dns_resolver_server_timeout

Temps en millisecondes pour définir combien de temps SSSD communiquerait avec un seul serveur DNS avant d'essayer le suivant.

Par défaut : 1000

dns_resolver_op_timeout

Temps en secondes pour indiquer combien de temps SSSD essaierait de résoudre une seule requête DNS (par exemple, la résolution d'un nom d'hôte ou d'un enregistrement SRV) avant d'essayer le nom d'hôte ou le domaine de découverte suivant.

Par défaut : 3

dns_resolver_timeout

Combien de temps SSSD essaierait de résoudre un service de basculement. La résolution de ce service peut inclure en interne plusieurs étapes, telles que la résolution des requêtes DNS SRV ou la localisation du site.

Par défaut : 6

Pour les fournisseurs basés sur LDAP, l'opération de résolution est effectuée dans le cadre d'une opération de connexion LDAP. Par conséquent, le délai d'attente « ldap_opt_timeout » doit également être défini sur une valeur supérieure à « dns_resolver_timeout », qui à son tour doit être définie sur une valeur supérieure à « dns_resolver_op_timeout », qui doit être supérieure à « dns_resolver_server_timeout ».

DÉCOUVERTE DE SERVICE

La fonctionnalité de découverte de service permet aux backends de trouver automatiquement les serveurs appropriés auxquels se connecter à l'aide d'une requête DNS spéciale. Cette fonctionnalité n'est pas prise en charge pour les serveurs de sauvegarde.

Configuration

Si aucun serveur n'est spécifié, le backend utilise automatiquement la découverte de service pour essayer de trouver un serveur. Facultativement, l'utilisateur peut choisir d'utiliser à la fois des adresses de serveur fixes et la découverte de service en insérant un mot-clé spécial, « _srv_ », dans la liste des serveurs. L'ordre de préférence est maintenu. Cette fonctionnalité est utile si, par exemple, l'utilisateur préfère utiliser la découverte de service chaque fois que possible, et revenir à un serveur spécifique lorsqu'aucun serveur ne peut être découvert via DNS.

Le nom de domaine

Veuillez vous référer au paramètre « dns_discovery_domain » dans la page de manuel sssd.conf(5) pour plus de détails.

Le protocole

Les requêtes spécifient généralement _tcp comme protocole. Les exceptions sont documentées dans la description de l'option respective.

Voir aussi

Pour plus d'informations sur le mécanisme de découverte de service, reportez-vous à la RFC 2782.

MISE EN CORRESPONDANCE DES IDENTIFIANTS

La fonctionnalité de mise en correspondance des identifiants permet à SSSD d'agir en tant que client d'Active Directory sans obliger les administrateurs à étendre les attributs des utilisateurs pour prendre en charge les attributs POSIX pour les identifiants d'utilisateur et de groupe.

NOTE : Lorsque la mise en correspondance des identifiants est activée, les attributs uidNumber et gidNumber sont ignorés. Ceci afin d'éviter les conflits potentiels entre les valeurs attribuées automatiquement et celles attribuées manuellement. Si vous avez besoin d'utiliser des valeurs attribuées manuellement, TOUTES les valeurs doivent être attribuées manuellement.

Veuillez noter que la modification des options de configuration relatives à la mise en correspondance des identifiants entraînera la modification des identifiants d'utilisateur et de groupe. Actuellement, SSSD ne prend pas en charge la modification des identifiants, la base de données SSSD doit donc être supprimée. Comme les mots de passe mis en cache sont également stockés dans la base de données, la suppression de la base de données ne doit être effectuée que lorsque les serveurs d'authentification sont joignables, sinon les utilisateurs pourraient être bloqués. Pour mettre en cache le mot de passe, une authentification doit être effectuée. Il ne suffit pas d'utiliser sss_cache(8) pour supprimer la base de données, le processus consiste plutôt à :

•S'assurer que les serveurs distants sont joignables
•Arrêter le service SSSD
•Supprimer la base de données
•Démarrer le service SSSD

De plus, comme la modification des identifiants pourrait nécessiter l'ajustement d'autres propriétés système telles que la propriété des fichiers et des répertoires, il est conseillé de planifier à l'avance et de tester minutieusement la configuration de la mise en correspondance des identifiants.

Algorithme de mise en correspondance

Active Directory fournit un objetSID pour chaque objet utilisateur et groupe dans le répertoire. Cet objetSID peut être décomposé en composantes qui représentent l'identité du domaine Active Directory et l'identifiant relatif (RID) de l'objet utilisateur ou groupe.

L'algorithme de mise en correspondance des identifiants SSSD prend une plage d'UID disponibles et la divise en sections de composantes de taille égale - appelées « tranches ». Chaque tranche représente l'espace disponible pour un domaine Active Directory.

Lorsqu'une entrée d'utilisateur ou de groupe pour un domaine particulier est rencontrée pour la première fois, SSSD alloue une des tranches disponibles pour ce domaine. Afin de rendre cette affectation de tranche répétable sur différentes machines clientes, nous sélectionnons la tranche en fonction de l'algorithme suivant :

La chaîne SID est traitée par l'algorithme murmurhash3 pour la convertir en une valeur hachée de 32 bits. Nous prenons ensuite le modulo de cette valeur avec le nombre total de tranches disponibles pour sélectionner la tranche.

NOTE : Il est possible de rencontrer des collisions dans le hachage et le modulo résultant. Dans ces situations, nous sélectionnerons la tranche disponible suivante, mais il ne sera peut-être pas possible de reproduire exactement le même ensemble de tranches sur d'autres machines (puisque l'ordre dans lequel elles sont rencontrées déterminera leurs tranches). Dans cette situation, il est recommandé soit de passer à l'utilisation d'attributs POSIX explicites dans Active Directory (désactivation de la mise en correspondance des identifiants), soit de configurer un domaine par défaut pour garantir qu'au moins un domaine soit toujours cohérent. Voir « Configuration » pour plus de détails.

Configuration

Configuration minimale (dans la section « [domain/NOMDEDOMAINE] »):

ldap_id_mapping = True
ldap_schema = ad

La configuration par défaut entraîne la configuration de 10 000 tranches, chacune capable de contenir jusqu'à 200 000 identifiants, commençant à 200 000 et allant jusqu'à 2 000 200 000. Cela devrait suffire pour la plupart des déploiements.

Configuration avancée

ldap_idmap_range_min (entier)

Spécifie la borne inférieure (inclusive) de la plage d'identifiants POSIX à utiliser pour la mise en correspondance des SID d'utilisateurs et de groupes Active Directory. C'est le premier identifiant POSIX qui peut être utilisé pour la mise en correspondance.

NOTE : Cette option est différente de « min_id » en ce sens que « min_id » filtre la sortie des requêtes vers ce domaine, tandis que cette option contrôle la plage d'attribution des identifiants. C'est une distinction subtile, mais un bon conseil général serait que « min_id » soit inférieur ou égal à « ldap_idmap_range_min ».

Par défaut : 200000

ldap_idmap_range_max (entier)

Spécifie la borne supérieure (exclusive) de la plage d'identifiants POSIX à utiliser pour la mise en correspondance des SID d'utilisateurs et de groupes Active Directory. C'est le premier identifiant POSIX qui ne peut plus être utilisé pour la mise en correspondance, c'est-à-dire un identifiant supérieur au dernier qui peut être utilisé pour la mise en correspondance.

NOTE : Cette option est différente de « max_id » en ce sens que « max_id » filtre la sortie des requêtes vers ce domaine, tandis que cette option contrôle la plage d'attribution des identifiants. C'est une distinction subtile, mais un bon conseil général serait que « max_id » soit supérieur ou égal à « ldap_idmap_range_max ».

Par défaut : 2000200000

ldap_idmap_range_size (entier)

Spécifie le nombre d'identifiants disponibles pour chaque tranche. Si la taille de la plage ne divise pas uniformément les valeurs minimale et maximale, elle créera autant de tranches complètes que possible.

NOTE : La valeur de cette option doit être au moins égale au RID d'utilisateur le plus élevé prévu pour être utilisé sur le serveur Active Directory. Les recherches d'utilisateurs et les connexions échoueront pour tout utilisateur dont le RID est supérieur à cette valeur.

Par exemple, si votre utilisateur Active Directory ajouté le plus récemment a objectSid=S-1-5-21-2153326666-2176343378-3404031434-1107, « ldap_idmap_range_size » doit être d'au moins 1108 car la taille de la plage est égale au RID maximal moins le RID minimal plus un (par exemple, 1108 = 1107 - 0 + 1).

Il est important de planifier l'expansion future, car la modification de cette valeur entraînera la modification de toutes les mises en correspondance d'identifiants sur le système, ce qui conduira les utilisateurs à avoir des identifiants locaux différents de ceux qu'ils avaient précédemment.

Par défaut : 200000

ldap_idmap_default_domain_sid (chaîne)

Spécifie le SID de domaine du domaine par défaut. Cela garantira que ce domaine sera toujours affecté à la tranche zéro dans la carte d'identifiants, contournant ainsi l'algorithme murmurhash décrit ci-dessus.

Par défaut : non défini

ldap_idmap_default_domain (chaîne)

Spécifie le nom du domaine par défaut.

Par défaut : non défini

ldap_idmap_autorid_compat (booléen)

Modifie le comportement de l'algorithme de mise en correspondance des identifiants pour qu'il se comporte de manière plus similaire à l'algorithme « idmap_autorid » de winbind.

Lorsque cette option est configurée, les domaines seront alloués à partir de la tranche zéro et augmenteront monotonically avec chaque domaine supplémentaire.

NOTE : Cet algorithme n'est pas déterministe (il dépend de l'ordre dans lequel les utilisateurs et les groupes sont demandés). Si ce mode est requis pour la compatibilité avec les machines exécutant winbind, il est recommandé d'utiliser également l'option « ldap_idmap_default_domain_sid » pour garantir qu'au moins un domaine est toujours affecté de manière cohérente à la tranche zéro.

Par défaut : Faux

ldap_idmap_helper_table_size (entier)

Nombre maximal de tranches secondaires qui sont essayées lors de l'exécution de la mise en correspondance from UNIX id to SID.

Note : Des tranches secondaires supplémentaires peuvent être générées lorsque le SID est en cours de mappage vers un ID UNIX et que la partie RID du SID est hors de portée pour les tranches secondaires générées jusqu'à présent. Si la valeur de ldap_idmap_helper_table_size est égale à 0, aucune tranche secondaire supplémentaire n'est générée.

Par défaut : 10

SIDs bien connus

SSSD prend en charge la recherche des noms de SIDs bien connus, c'est-à-dire les SIDs ayant une signification spéciale codée en dur. Étant donné que les utilisateurs et groupes génériques associés à ces SIDs bien connus n'ont pas d'équivalent dans un environnement Linux/UNIX, aucun ID POSIX n'est disponible pour ces objets.

L'espace de noms des SIDs est organisé en autorités qui peuvent être considérées comme différents domaines. Les autorités pour les SIDs bien connus sont :

•Autorité nulle
•Autorité du monde
•Autorité locale
•Autorité créatrice
•Autorité d'étiquette obligatoire
•Autorité d'authentification
•Autorité NT
•Intégré

La version en majuscules de ces noms est utilisée comme noms de domaine lors du retour du nom complet d'un SID bien connu.

Étant donné que certains utilitaires permettent de modifier les informations de contrôle d'accès basées sur les SIDs à l'aide d'un nom au lieu d'utiliser directement le SID, SSSD prend également en charge la recherche du SID par son nom. Pour éviter les collisions, seuls les noms complets peuvent être utilisés pour rechercher les SIDs bien connus. Par conséquent, les noms de domaine « AUTORITÉ NULLE », « AUTORITÉ DU MONDE », « AUTORITÉ LOCALE », « AUTORITÉ CRÉATRICE », « AUTORITÉ D'ÉTIQUETTE OBLIGATOIRE », « AUTORITÉ D'AUTHENTIFICATION », « AUTORITÉ NT » et « BUILTIN » ne doivent pas être utilisés comme noms de domaine dans sssd.conf.

EXEMPLE

L'exemple suivant suppose que SSSD est correctement configuré et que LDAP est défini sur l'un des domaines dans la section [domains].

[domain/LDAP]
id_provider = ldap
auth_provider = ldap
ldap_uri = ldap://ldap.mydomain.org
ldap_search_base = dc=mydomain,dc=org
ldap_tls_reqcert = demand
cache_credentials = true

EXEMPLE DE FILTRE D'ACCÈS LDAP

L'exemple suivant suppose que SSSD est correctement configuré et qu'il utilise ldap_access_order=lockout.

[domain/LDAP]
id_provider = ldap
auth_provider = ldap
access_provider = ldap
ldap_access_order = lockout
ldap_pwdlockout_dn = cn=ppolicy,ou=policies,dc=mydomain,dc=org
ldap_uri = ldap://ldap.mydomain.org
ldap_search_base = dc=mydomain,dc=org
ldap_tls_reqcert = demand
cache_credentials = true
