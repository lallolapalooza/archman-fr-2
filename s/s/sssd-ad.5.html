NOM

sssd-ad - Fournisseur Active Directory de SSSD

DESCRIPTION

Cette page de manuel décrit la configuration du fournisseur AD pour sssd(8). Pour une référence syntaxique détaillée, consultez la section “FORMAT DE FICHIER” de la page de manuel de sssd.conf(5).

Le fournisseur AD est un backend utilisé pour se connecter à un serveur Active Directory. Ce fournisseur nécessite que la machine soit jointe au domaine AD et qu'une keytab soit disponible. La communication backend se fait via un canal crypté GSSAPI ; les options SSL/TLS ne doivent pas être utilisées avec le fournisseur AD et seront supplantées par l'utilisation de Kerberos.

Le fournisseur AD prend en charge la connexion à Active Directory 2008 R2 ou version ultérieure. Les versions antérieures peuvent fonctionner, mais ne sont pas prises en charge.

Le fournisseur AD peut être utilisé pour obtenir des informations sur les utilisateurs et authentifier les utilisateurs des domaines approuvés. Actuellement, seuls les domaines approuvés dans la même forêt sont reconnus. De plus, les serveurs des domaines approuvés sont toujours auto-découverts.

Le fournisseur AD permet à SSSD d'utiliser le fournisseur d'identité sssd-ldap(5) et le fournisseur d'authentification sssd-krb5(5) avec des optimisations pour les environnements Active Directory. Le fournisseur AD accepte les mêmes options que celles utilisées par les fournisseurs sssd-ldap et sssd-krb5, à quelques exceptions près. Cependant, il n'est ni nécessaire ni recommandé de définir ces options.

Le fournisseur AD copie principalement les options par défaut des fournisseurs ldap et krb5 traditionnels, à quelques exceptions près ; les différences sont listées dans la section “OPTIONS PAR DÉFAUT MODIFIÉES”.

Le fournisseur AD peut également être utilisé comme fournisseur d'accès, de changement de mot de passe (chpass), sudo et autofs. Aucune configuration du fournisseur d'accès n'est requise côté client.

Si “auth_provider=ad” ou “access_provider=ad” est configuré dans sssd.conf, alors id_provider doit également être défini sur “ad”.

Par défaut, le fournisseur AD associe les valeurs UID et GID du paramètre objectSID dans Active Directory. Pour plus de détails à ce sujet, voir la section “ASSOCIATION DES IDENTIFIANTS” ci-dessous. Si vous souhaitez désactiver l'association des identifiants et vous fier aux attributs POSIX définis dans Active Directory, vous devez définir

ldap_id_mapping = False

Si les attributs POSIX doivent être utilisés, il est recommandé pour des raisons de performance que les attributs soient également répliqués dans le catalogue global. Si les attributs POSIX sont répliqués, SSSD tentera de localiser le domaine d'un identifiant numérique demandé à l'aide du catalogue global et ne recherchera que dans ce domaine. En revanche, si les attributs POSIX ne sont pas répliqués dans le catalogue global, SSSD doit rechercher séquentiellement tous les domaines de la forêt. Veuillez noter que l'option “cache_first” peut également être utile pour accélérer les recherches sans domaine. Notez que si seul un sous-ensemble d'attributs POSIX est présent dans le catalogue global, les attributs non répliqués ne sont actuellement pas lus sur le port LDAP.

Les utilisateurs, groupes et autres entités servis par SSSD sont toujours traités comme insensibles à la casse dans le fournisseur AD pour assurer la compatibilité avec l'implémentation LDAP d'Active Directory.

SSSD ne résout que les groupes de sécurité Active Directory. Pour plus d'informations sur les types de groupes AD, voir : Groupes de sécurité Active Directory[1]

SSSD filtre les groupes locaux au domaine (Domain Local groups) des domaines distants dans la forêt AD. Par défaut, ils sont filtrés, par exemple lors du suivi d'une hiérarchie de groupes imbriqués dans des domaines distants, car ils ne sont pas valides dans le domaine local. Ceci est fait pour être en accord avec l'affectation des appartenances aux groupes d'Active Directory, telle qu'elle peut être vue dans le PAC du ticket Kerberos d'un utilisateur émis par Active Directory.

OPTIONS DE CONFIGURATION

Consultez la section “SECTIONS DE DOMAINE” de la page de manuel de sssd.conf(5) pour les détails sur la configuration d'un domaine SSSD.

ad_domain (chaîne)

Spécifie le nom du domaine Active Directory. Ceci est facultatif. Si non fourni, le nom du domaine de configuration est utilisé.

Pour un fonctionnement correct, cette option doit être spécifiée en minuscules et sous la forme longue du nom de domaine Active Directory.

Le nom court du domaine (également connu sous le nom NetBIOS ou nom plat) est détecté automatiquement par SSSD.

ad_enabled_domains (chaîne)

Une liste de domaines Active Directory activés, séparés par des virgules. Si fournie, SSSD ignorera tous les domaines non listés dans cette option. Si elle est laissée vide, tous les domaines découverts de la forêt AD seront disponibles.

Lors de la découverte des domaines, SSSD filtrera certains domaines pour lesquels des indicateurs ou des attributs indiquent qu'ils n'appartiennent pas à la forêt locale ou qu'ils ne sont pas approuvés. Si ad_enabled_domains est défini, SSSD essaiera d'activer tous les domaines listés.

Pour un fonctionnement correct, cette option doit être spécifiée entièrement en minuscules et comme nom de domaine complet d'Active Directory. Par exemple :

ad_enabled_domains = sales.example.com, eng.example.com

Le nom court du domaine (également connu sous le nom NetBIOS ou nom plat) sera détecté automatiquement par SSSD.

Défaut : Non défini

ad_server, ad_backup_server (chaîne)

La liste des noms d'hôtes des serveurs AD auxquels SSSD doit se connecter, séparés par des virgules, par ordre de préférence. Pour plus d'informations sur la bascule et la redondance des serveurs, consultez la section “BASCULE” (FAILOVER).

Ceci est facultatif si la découverte automatique est activée. Pour plus d'informations sur la découverte de services, consultez la section “DÉCOUVERTE DE SERVICES”.

Remarque : Les domaines approuvés découvriront toujours les serveurs même si le serveur principal est explicitement défini dans l'option ad_server.

ad_hostname (chaîne)

Facultatif. Sur les machines où le nom d'hôte (hostname(5)) ne reflète pas le nom qualifié complet, sssd essaiera d'étendre le nom court. S'il n'est pas possible de le faire ou si le nom court doit réellement être utilisé à la place, définissez ce paramètre explicitement.

Ce champ est utilisé pour déterminer le principal de l'hôte utilisé dans la keytab et pour effectuer des mises à jour DNS dynamiques. Il doit correspondre au nom d'hôte pour lequel la keytab a été émise.

ad_enable_dns_sites (booléen)

Active les sites DNS - découverte de services basée sur la localisation.

Si vrai et si la découverte de services (voir le paragraphe Service Discovery au bas de la page de manuel) est activée, SSSD tentera d'abord de découvrir le serveur Active Directory auquel se connecter en utilisant la découverte de site Active Directory, puis se rabattra sur les enregistrements SRV DNS si aucun site AD n'est trouvé. La configuration DNS SRV, y compris le domaine de découverte, est également utilisée lors de la découverte de site.

Défaut : vrai

ad_access_filter (chaîne)

Spécifie un filtre de contrôle d'accès LDAP auquel un utilisateur doit correspondre pour obtenir l'accès. L'option “access_provider” doit être explicitement définie sur “ad” pour que cette option prenne effet. Si vous souhaitez utiliser “ad_access_filter” comme seul schéma de contrôle d'accès, vous devez désactiver le contrôle d'accès basé sur les GPO (voir l'option “ad_gpo_access_control” pour plus de détails).

L'option prend également en charge la spécification de filtres différents par domaine ou forêt. Ce filtre étendu consisterait en : “MOT-CLÉ:NOM:FILTRE”. Le mot-clé peut être soit “DOM”, soit “FORÊT”, soit absent.

Si le mot-clé est égal à “DOM” ou est absent, alors “NOM” spécifie le domaine ou le sous-domaine auquel le filtre s'applique. Si le mot-clé est égal à “FORÊT”, alors le filtre s'applique à tous les domaines de la forêt spécifiée par “NOM”.

Plusieurs filtres peuvent être séparés par le caractère “?”, de la même manière que fonctionnent les bases de recherche.

L'appartenance à des groupes imbriqués doit être recherchée à l'aide d'un OID spécial “:1.2.840.113556.1.4.1941:” en plus de la syntaxe complète DOM:domain.example.org: pour garantir que l'analyseur n'essaie pas d'interpréter les caractères deux-points associés à l'OID. Si vous n'utilisez pas cet OID, l'appartenance à des groupes imbriqués ne sera pas résolue. Voir l'exemple d'utilisation ci-dessous et se référer ici pour plus d'informations sur l'OID : [MS-ADTS] section extensions LDAP[2]

La correspondance la plus spécifique est toujours utilisée. Par exemple, si l'option spécifie un filtre pour un domaine dont l'utilisateur est membre et un filtre global, le filtre spécifique au domaine sera appliqué. En cas de plusieurs correspontches avec la même spécification, le premier est utilisé.

Exemples:

# appliquer le filtre sur le domaine appelé dom1 uniquement :
dom1:(memberOf=cn=admins,ou=groups,dc=dom1,dc=com)
# appliquer le filtre sur le domaine appelé dom2 uniquement :
DOM:dom2:(memberOf=cn=admins,ou=groups,dc=dom2,dc=com)
# appliquer le filtre sur la forêt appelée EXAMPLE.COM uniquement :
FOREST:EXAMPLE.COM:(memberOf=cn=admins,ou=groups,dc=example,dc=com)
# appliquer le filtre pour un membre d'un groupe imbriqué dans dom1 :
DOM:dom1:(memberOf:1.2.840.113556.1.4.1941:=cn=nestedgroup,ou=groups,dc=example,dc=com)

Par défaut : Non défini

ad_site (chaîne)

Spécifiez le site AD auquel le client doit essayer de se connecter. Si cette option n'est pas fournie, le site AD sera découvert automatiquement.

Par défaut : Non défini

ad_enable_gc (booléen)

Par défaut, SSSD se connecte d'abord au catalogue global pour récupérer les utilisateurs des domaines approuvés et utilise le port LDAP pour récupérer les appartenances aux groupes ou comme solution de repli. La désactivation de cette option amène SSSD à se connecter uniquement au port LDAP du serveur AD actuel.

Veuillez noter que la désactivation du support du catalogue global ne désactive pas la récupération des utilisateurs des domaines approuvés. SSSD se connecterait au port LDAP des domaines approuvés à la place. Cependant, le catalogue global doit être utilisé pour résoudre les appartenances aux groupes inter-domaines.

Par défaut : vrai

ad_gpo_access_control (chaîne)

Cette option spécifie le mode de fonctionnement de la fonctionnalité de contrôle d'accès basé sur les GPO : s'il fonctionne en mode désactivé, en mode d'application stricte ou en mode permissif. Veuillez noter que l'option “access_provider” doit être explicitement définie sur “ad” pour que cette option ait un effet.

La fonctionnalité de contrôle d'accès basé sur les GPO utilise les paramètres de stratégie GPO pour déterminer si un utilisateur particulier est autorisé à se connecter à l'hôte. Pour plus d'informations sur les paramètres de stratégie pris en charge, veuillez vous référer aux options “ad_gpo_map”.

Veuillez noter que la version actuelle de SSSD ne prend pas en charge les groupes intégrés d'Active Directory. Les groupes intégrés (tels que les administrateurs avec le SID S-1-5-32-544) dans les règles de contrôle d'accès GPO seront ignorés par SSSD. Voir le suivi des problèmes en amont https://github.com/SSSD/sssd/issues/5063 .

Avant d'effectuer le contrôle d'accès, SSSD applique le filtrage de sécurité des stratégies de groupe aux GPO. Pour chaque connexion d'utilisateur, l'applicabilité des GPO liés à l'hôte est vérifiée. Pour qu'un GPO s'applique à un utilisateur, l'utilisateur ou au moins l'un des groupes auxquels il appartient doit avoir les permissions suivantes sur le GPO :

•Lecture : L'utilisateur ou l'un de ses groupes doit avoir un accès en lecture aux propriétés du GPO (RIGHT_DS_READ_PROPERTY)
•Appliquer la stratégie de groupe : L'utilisateur ou au moins l'un de ses groupes doit être autorisé à appliquer le GPO (RIGHT_DS_CONTROL_ACCESS).

Par défaut, le groupe Utilisateurs authentifiés est présent sur un GPO et ce groupe possède les droits d'accès en Lecture et Application de la stratégie de groupe. Comme l'authentification d'un utilisateur doit avoir été effectuée avec succès avant le démarrage du filtrage de sécurité GPO et du contrôle d'accès, les permissions du groupe Utilisateurs authentifiés sur le GPO s'appliquent toujours à l'utilisateur.

NOTE : Si le mode de fonctionnement est défini sur application stricte, il est possible que les utilisateurs qui avaient auparavant un accès autorisé se voient refuser l'accès (conformément aux paramètres de stratégie GPO). Afin de faciliter une transition en douceur pour les administrateurs, un mode permissif est disponible qui n'appliquera pas les règles de contrôle d'accès, mais les évaluera et émettra un message syslog si l'accès aurait été refusé. En examinant les journaux, les administrateurs peuvent alors apporter les modifications nécessaires avant de définir le mode sur application stricte. Pour le débogage du contrôle d'accès basé sur les GPO, le niveau de débogage “trace functions” est requis (voir la page de manuel sssctl(8)).

Trois valeurs sont prises en charge pour cette option :

•disabled : Les règles de contrôle d'accès basées sur les GPO ne sont ni évaluées ni appliquées.
•enforcing : Les règles de contrôle d'accès basées sur les GPO sont évaluées et appliquées.
•permissive : Les règles de contrôle d'accès basées sur les GPO sont évaluées, mais pas appliquées. Au lieu de cela, un message syslog sera émis indiquant que l'utilisateur se serait vu refuser l'accès si cette option avait été définie sur “enforcing”.

Par défaut : enforcing

ad_gpo_implicit_deny (booléen)

Normalement, lorsqu'aucun GPO applicable n'est trouvé, les utilisateurs sont autorisés à accéder. Lorsque cette option est définie sur True, les utilisateurs ne seront autorisés à accéder que s'ils sont explicitement autorisés par une règle GPO. Sinon, les utilisateurs se verront refuser l'accès. Cela peut être utilisé pour renforcer la sécurité, mais faites attention lors de l'utilisation de cette option, car elle peut refuser l'accès même aux utilisateurs du groupe intégré Administrateurs si aucun GPO ne s'applique à eux.

Par défaut : Faux

ad_gpo_implicit_deny = False (par défaut)
règles d'autorisation règles de refus résultats

ad_gpo_ignore_unreadable (booléen)

Normalement, lorsque certains conteneurs de stratégie de groupe (objet AD) des objets de stratégie de groupe applicables ne sont pas lisibles par SSSD, les utilisateurs se voient refuser l'accès. Cette option permet d'ignorer les conteneurs de stratégie de groupe et les stratégies associées si leurs attributs dans les conteneurs de stratégie de groupe ne sont pas lisibles par SSSD.

Par défaut : Faux

ad_gpo_cache_timeout (entier)

Durée entre les recherches de fichiers de stratégie GPO sur le serveur AD. Cela réduira la latence et la charge sur le serveur AD s'il y a de nombreuses demandes de contrôle d'accès effectuées sur une courte période.

Par défaut : 5 (secondes)

ad_gpo_map_interactive (chaîne)

Une liste de noms de services PAM séparés par des virgules pour lesquels le contrôle d'accès basé sur les GPO est évalué en fonction des paramètres de stratégie InteractiveLogonRight et DenyInteractiveLogonRight. Seuls les GPO pour lesquels l'utilisateur a les permissions de lecture et d'application de la stratégie de groupe (voir l'option “ad_gpo_access_control”) sont évalués. Si un GPO évalué contient le paramètre de refus de connexion interactive pour l'utilisateur ou l'un de ses groupes, l'utilisateur se voit refuser l'accès local. Si aucun des GPO évalués n'a de droit de connexion interactive défini, l'utilisateur se voit accorder l'accès local. Si au moins un GPO évalué contient des paramètres de droit de connexion interactive, l'utilisateur se voit accorder l'accès local uniquement s'il ou au moins l'un de ses groupes fait partie des paramètres de stratégie.

Remarque : En utilisant l'éditeur de gestion des stratégies de groupe, cette valeur est appelée "Autoriser la connexion localement" et "Refuser la connexion localement".

Il est possible d'ajouter un autre nom de service PAM à l'ensemble par défaut en utilisant “+nom_service” ou de supprimer explicitement un nom de service PAM de l'ensemble par défaut en utilisant “-nom_service”. Par exemple, afin de remplacer un nom de service PAM par défaut pour ce droit de connexion (par exemple “login”) par un nom de service PAM personnalisé (par exemple “my_pam_service”), vous utiliseriez la configuration suivante :

ad_gpo_map_interactive = +my_pam_service, -login

Par défaut : l'ensemble par défaut des noms de services PAM inclut :

•login
•su
•su-l
•gdm-fingerprint
•gdm-password
•gdm-smartcard
•kdm
•lightdm
•lxdm
•sddm
•unity
•xdm

ad_gpo_map_remote_interactive (chaîne)

Une liste de noms de services PAM séparés par des virgules pour lesquels le contrôle d'accès basé sur les GPO est évalué en fonction des paramètres de stratégie RemoteInteractiveLogonRight et DenyRemoteInteractiveLogonRight. Seuls les GPO pour lesquels l'utilisateur a les permissions de lecture et d'application de la stratégie de groupe (voir l'option “ad_gpo_access_control”) sont évalués. Si un GPO évalué contient le paramètre de refus de connexion à distance pour l'utilisateur ou l'un de ses groupes, l'utilisateur se voit refuser l'accès interactif à distance. Si aucun des GPO évalués n'a de droit de connexion interactive à distance défini, l'utilisateur se voit accorder l'accès à distance. Si au moins un GPO évalué contient des paramètres de droit de connexion interactive à distance, l'utilisateur se voit accorder l'accès à distance uniquement s'il ou au moins l'un de ses groupes fait partie des paramètres de stratégie.

Remarque : En utilisant l'éditeur de gestion des stratégies de groupe, cette valeur est appelée "Autoriser la connexion via les services Bureau à distance" et "Refuser la connexion via les services Bureau à distance".

Il est possible d'ajouter un autre nom de service PAM à l'ensemble par défaut en utilisant “+nom_service” ou pour supprimer explicitement un nom de service PAM de l'ensemble par défaut en utilisant “-nom_service”. Par exemple, afin de remplacer un nom de service PAM par défaut pour ce droit de connexion (par exemple, “sshd”) par un nom de service PAM personnalisé (par exemple, “mon_service_pam”), vous utiliseriez la configuration suivante :

ad_gpo_map_remote_interactive = +mon_service_pam, -sshd

Par défaut : l'ensemble par défaut de noms de services PAM inclut :

•sshd
•cockpit

ad_gpo_map_network (string)

Une liste de noms de services PAM séparés par des virgules pour lesquels le contrôle d'accès basé sur GPO est évalué en fonction des paramètres de stratégie NetworkLogonRight et DenyNetworkLogonRight. Seuls les GPO pour lesquels l'utilisateur dispose de l'autorisation de lecture et d'application de la stratégie de groupe (voir l'option “ad_gpo_access_control”) sont évalués. Si un GPO évalué contient le paramètre de refus de connexion réseau pour l'utilisateur ou l'un de ses groupes, l'utilisateur se voit refuser l'accès à la connexion réseau. Si aucun des GPO évalués n'a de droit de connexion réseau défini, l'utilisateur reçoit l'accès à la connexion. Si au moins un GPO évalué contient des paramètres de droit de connexion réseau, l'utilisateur reçoit l'accès à la connexion uniquement s'il, ou au moins l'un de ses groupes, fait partie des paramètres de stratégie.

Note : En utilisant l'Éditeur de gestion des stratégies de groupe, cette valeur est appelée « Accéder à cet ordinateur depuis le réseau » et « Refuser l'accès à cet ordinateur depuis le réseau ».

Il est possible d'ajouter un autre nom de service PAM à l'ensemble par défaut en utilisant “+nom_service” ou de supprimer explicitement un nom de service PAM de l'ensemble par défaut en utilisant “-nom_service”. Par exemple, afin de remplacer un nom de service PAM par défaut pour ce droit de connexion (par exemple, “ftp”) par un nom de service PAM personnalisé (par exemple, “mon_service_pam”), vous utiliseriez la configuration suivante :

ad_gpo_map_network = +mon_service_pam, -ftp

Par défaut : l'ensemble par défaut de noms de services PAM inclut :

•ftp
•samba

ad_gpo_map_batch (string)

Une liste de noms de services PAM séparés par des virgules pour lesquels le contrôle d'accès basé sur GPO est évalué en fonction des paramètres de stratégie BatchLogonRight et DenyBatchLogonRight. Seuls les GPO pour lesquels l'utilisateur dispose de l'autorisation de lecture et d'application de la stratégie de groupe (voir l'option “ad_gpo_access_control”) sont évalués. Si un GPO évalué contient le paramètre de refus de connexion par lots pour l'utilisateur ou l'un de ses groupes, l'utilisateur se voit refuser l'accès à la connexion par lots. Si aucun des GPO évalués n'a de droit de connexion par lots défini, l'utilisateur reçoit l'accès à la connexion. Si au moins un GPO évalué contient des paramètres de droit de connexion par lots, l'utilisateur reçoit l'accès à la connexion uniquement s'il, ou au moins l'un de ses groupes, fait partie des paramètres de stratégie.

Note : En utilisant l'Éditeur de gestion des stratégies de groupe, cette valeur est appelée « Autoriser la connexion en tant que tâche » et « Refuser la connexion en tant que tâche ».

Il est possible d'ajouter un autre nom de service PAM à l'ensemble par défaut en utilisant “+nom_service” ou de supprimer explicitement un nom de service PAM de l'ensemble par défaut en utilisant “-nom_service”. Par exemple, afin de remplacer un nom de service PAM par défaut pour ce droit de connexion (par exemple, “crond”) par un nom de service PAM personnalisé (par exemple, “mon_service_pam”), vous utiliseriez la configuration suivante :

ad_gpo_map_batch = +mon_service_pam, -crond

Note : Le nom du service Cron peut varier en fonction de la distribution Linux utilisée.

Par défaut : l'ensemble par défaut de noms de services PAM inclut :

•crond

ad_gpo_map_service (string)

Une liste de noms de services PAM séparés par des virgules pour lesquels le contrôle d'accès basé sur GPO est évalué en fonction des paramètres de stratégie ServiceLogonRight et DenyServiceLogonRight. Seuls les GPO pour lesquels l'utilisateur dispose de l'autorisation de lecture et d'application de la stratégie de groupe (voir l'option “ad_gpo_access_control”) sont évalués. Si un GPO évalué contient le paramètre de refus de connexion de service pour l'utilisateur ou l'un de ses groupes, l'utilisateur se voit refuser l'accès à la connexion de service. Si aucun des GPO évalués n'a de droit de connexion de service défini, l'utilisateur reçoit l'accès à la connexion. Si au moins un GPO évalué contient des paramètres de droit de connexion de service, l'utilisateur reçoit l'accès à la connexion uniquement s'il, ou au moins l'un de ses groupes, fait partie des paramètres de stratégie.

Note : En utilisant l'Éditeur de gestion des stratégies de groupe, cette valeur est appelée « Autoriser la connexion en tant que service » et « Refuser la connexion en tant que service ».

Il est possible d'ajouter un nom de service PAM à l'ensemble par défaut en utilisant “+nom_service”. Comme l'ensemble par défaut est vide, il n'est pas possible de supprimer un nom de service PAM de l'ensemble par défaut. Par exemple, afin d'ajouter un nom de service PAM personnalisé (par exemple, “mon_service_pam”), vous utiliseriez la configuration suivante :

ad_gpo_map_service = +mon_service_pam

Par défaut : non défini

ad_gpo_map_permit (string)

Une liste de noms de services PAM séparés par des virgules pour lesquels l'accès basé sur GPO est toujours accordé, quelles que soient les autorisations de connexion GPO.

Il est possible d'ajouter un autre nom de service PAM à l'ensemble par défaut en utilisant “+nom_service” ou de supprimer explicitement un nom de service PAM de l'ensemble par défaut en utilisant “-nom_service”. Par exemple, afin de remplacer un nom de service PAM par défaut pour un accès inconditionnellement autorisé (par exemple, “sudo”) par un nom de service PAM personnalisé (par exemple, “mon_service_pam”), vous utiliseriez la configuration suivante :

ad_gpo_map_permit = +mon_service_pam, -sudo

Par défaut : l'ensemble par défaut de noms de services PAM inclut :

•polkit-1
•sudo
•sudo-i
•systemd-user

Une liste de noms de services PAM séparés par des virgules pour lesquels l'accès basé sur GPO est toujours refusé, quelles que soient les autorisations de connexion GPO.

Par exemple, afin d'ajouter un nom de service PAM personnalisé (par exemple, “mon_service_pam”), vous utiliseriez la configuration suivante :

ad_gpo_map_deny = +mon_service_pam

Par défaut : non défini

ad_gpo_default_right (string)

Cette option définit comment le contrôle d'accès est évalué pour les noms de services PAM qui ne sont pas explicitement listés dans l'une des options ad_gpo_map_*. Cette option peut être configurée de deux manières. Premièrement, cette option peut être configurée pour utiliser un droit de connexion par défaut. Par exemple, si cette option est définie sur 'interactive', cela signifie que les noms de services PAM non mappés seront traités en fonction des paramètres de stratégie InteractiveLogonRight et DenyInteractiveLogonRight. Alternativement, cette option peut être configurée soit pour autoriser systématiquement, soit pour refuser systématiquement l'accès aux noms de services PAM non mappés.

Les valeurs prises en charge pour cette option incluent :

•interactive
•remote_interactive
•network
•batch
•service
•permit
•deny

Par défaut : deny

ad_maximum_machine_account_password_age (integer)

SSSD vérifiera une fois par jour si le mot de passe du compte de machine est plus ancien que l'âge donné en jours et essaiera de le renouveler. Une valeur de 0 désactivera la tentative de renouvellement.

Par défaut : 30 jours

ad_machine_account_password_renewal_opts (string)

Cette option ne doit être utilisée que pour tester la tâche de renouvellement du compte de machine. L'option attend 3 entiers et une chaîne séparés par deux-points (':'). Le premier entier définit l'intervalle en secondes de la fréquence d'exécution de la tâche. Le second spécifie le délai initial en secondes avant que la tâche ne s'exécute pour la première fois après le démarrage. La troisième valeur optionnelle spécifie un décalage aléatoire maximal par rapport aux deux valeurs précédentes pour éviter les mises à jour de nombreux hôtes en même temps (« problème de la horde d'attaquants »). Si cette valeur est manquante ou vide dans la chaîne de valeur, '0' sera utilisé.

La quatrième chaîne de valeur optionnelle identifie le programme auxiliaire qui doit être utilisé pour le renouvellement. Actuellement, adcli et realm sont pris en charge. Si cette valeur est manquante ou vide dans la chaîne de valeur, realm sera utilisé. Étant donné que l'auxiliaire est lancé en tant qu'utilisateur sous lequel SSSD s'exécute, il est possible que le renouvellement échoue si cet utilisateur n'a pas les permissions nécessaires pour modifier le fichier keytab où sont stockés les identifiants du compte de machine. Ce sera généralement le cas pour adcli.

realm ne met pas à jour le keytab directement, mais appelle le processus realmd, qui s'exécute en tant qu'utilisateur root, pour cette tâche. realmd peut autoriser l'accès aux utilisateurs non privilégiés à l'aide de PolicyKit et, par défaut, SSSD fournit des règles appropriées pour l'utilisateur sous lequel SSSD s'exécute.

Par défaut : 86400:750:300:realm (24h, 12m30s et 5m)

TRANSFERT

La fonctionnalité de transfert permet aux backends de passer automatiquement à un serveur différent si le serveur actuel échoue.

Syntaxe de transfert

La liste des serveurs est donnée sous forme de liste séparée par des virgules ; n'importe quel nombre d'espaces est autorisé autour de la virgule. Les serveurs sont listés par ordre de préférence. La liste peut contenir n'importe quel nombre de serveurs.

Pour chaque option de configuration activée pour le transfert, deux variantes existent : primaire et secours. L'idée est que les serveurs de la liste primaire sont préférés et que les serveurs de secours ne sont recherchés que si aucun serveur primaire ne peut être atteint. Si un serveur de secours est sélectionné, un délai de 31 secondes est défini. Après ce délai, SSSD tentera périodiquement de se reconnecter à l'un des serveurs principaux. S'il réussit, il remplacera le serveur actif actuel (de secours).

Le mécanisme de transfert

Le mécanisme de transfert distingue une machine d'un service. Le backend essaie d'abord de résoudre le nom d'hôte d'une machine donnée ; si cette tentative de résolution échoue, la machine est considérée comme hors ligne. Aucune autre tentative n'est faite pour se connecter à cette machine pour quelque autre

service. Si la tentative de résolution réussit, le backend essaie de se connecter à un service sur cette machine. Si la tentative de connexion au service échoue, seul ce service particulier est considéré comme hors ligne et le backend bascule automatiquement sur le service suivant. La machine est toujours considérée comme en ligne et peut encore être essayée pour un autre service.

D'autres tentatives de connexion sont effectuées vers des machines ou des services marqués comme hors ligne après une période de temps spécifiée ; ceci est actuellement codé en dur à 30 secondes.

S'il n'y a plus de machines à essayer, le backend dans son ensemble bascule en mode hors ligne, puis tente de se reconnecter toutes les 30 secondes.

Temps d'attente de basculement et optimisation

La résolution d'un serveur auquel se connecter peut être aussi simple que d'effectuer une seule requête DNS ou peut impliquer plusieurs étapes, comme trouver le bon site ou essayer plusieurs noms d'hôtes au cas où certains des serveurs configurés ne seraient pas joignables. Les scénarios plus complexes peuvent prendre du temps et SSSD doit trouver un équilibre entre accorder suffisamment de temps pour terminer le processus de résolution et, d'autre part, ne pas essayer trop longtemps avant de revenir au mode hors ligne. Si les journaux de débogage de SSSD montrent que la résolution du serveur expire avant qu'un serveur actif ne soit contacté, vous pouvez envisager de modifier les temps d'attente.

Cette section répertorie les éléments configurables disponibles. Veuillez vous référer à leur description dans la page de manuel sssd.conf(5).

dns_resolver_server_timeout

Temps en millisecondes qui définit combien de temps SSSD parlera à un serveur DNS unique avant d'essayer le suivant.

Par défaut : 1000

dns_resolver_op_timeout

Temps en secondes pour indiquer combien de temps SSSD essaiera de résoudre une seule requête DNS (par exemple, la résolution d'un nom d'hôte ou d'un enregistrement SRV) avant d'essayer le nom d'hôte suivant ou le domaine de découverte.

Par défaut : 3

dns_resolver_timeout

Combien de temps SSSD essaiera de résoudre un service de basculement. La résolution de ce service peut inclure plusieurs étapes internes, telles que la résolution de requêtes DNS SRV ou la localisation du site.

Par défaut : 6

Pour les fournisseurs basés sur LDAP, l'opération de résolution est effectuée dans le cadre d'une opération de connexion LDAP. Par conséquent, le délai d'attente « ldap_opt_timeout » doit également être défini sur une valeur supérieure à « dns_resolver_timeout », qui à son tour doit être défini sur une valeur supérieure à « dns_resolver_op_timeout », qui devrait être supérieure à « dns_resolver_server_timeout ».

DÉCOUVERTE DE SERVICE

La fonctionnalité de découverte de service permet aux backends de trouver automatiquement les serveurs appropriés à connecter à l'aide d'une requête DNS spéciale. Cette fonctionnalité n'est pas prise en charge pour les serveurs de secours.

Configuration

Si aucun serveur n'est spécifié, le backend utilise automatiquement la découverte de service pour essayer de trouver un serveur. Facultativement, l'utilisateur peut choisir d'utiliser à la fois des adresses de serveur fixes et la découverte de service en insérant un mot-clé spécial, « _srv_ », dans la liste des serveurs. L'ordre de préférence est maintenu. Cette fonctionnalité est utile si, par exemple, l'utilisateur préfère utiliser la découverte de service chaque fois que possible, et revenir à un serveur spécifique lorsqu'aucun serveur ne peut être découvert à l'aide de DNS.

Le nom de domaine

Veuillez vous référer au paramètre « dns_discovery_domain » dans la page de manuel sssd.conf(5) pour plus de détails.

Le protocole

Les requêtes spécifient généralement _tcp comme protocole. Les exceptions sont documentées dans la description de l'option respective.

Voir aussi

Pour plus d'informations sur le mécanisme de découverte de service, veuillez vous référer à la RFC 2782.

MAPPAGE DES ID

La fonctionnalité de mappage des ID permet à SSSD d'agir en tant que client d'Active Directory sans obliger les administrateurs à étendre les attributs utilisateur pour prendre en charge les attributs POSIX pour les identifiants d'utilisateur et de groupe.

NOTE : Lorsque le mappage des ID est activé, les attributs uidNumber et gidNumber sont ignorés. Ceci afin d'éviter la possibilité de conflits entre les valeurs attribuées automatiquement et celles attribuées manuellement. Si vous avez besoin d'utiliser des valeurs attribuées manuellement, TOUTES les valeurs doivent être attribuées manuellement.

Veuillez noter que la modification des options de configuration liées au mappage des ID entraînera la modification des identifiants d'utilisateur et de groupe. Pour le moment, SSSD ne prend pas en charge la modification des ID, la base de données SSSD doit donc être supprimée. Comme les mots de passe mis en cache sont également stockés dans la base de données, la suppression de la base de données ne doit être effectuée que lorsque les serveurs d'authentification sont joignables, sinon les utilisateurs pourraient être bloqués. Afin de mettre en cache le mot de passe, une authentification doit être effectuée. Il ne suffit pas d'utiliser sss_cache(8) pour supprimer la base de données, le processus consiste plutôt à :

•S'assurer que les serveurs distants sont joignables
•Arrêter le service SSSD
•Supprimer la base de données
•Démarrer le service SSSD

De plus, comme le changement d'ID pourrait nécessiter l'ajustement d'autres propriétés du système telles que la propriété des fichiers et des répertoires, il est conseillé de planifier à l'avance et de tester minutieusement la configuration du mappage des ID.

Algorithme de mappage

Active Directory fournit un objectSID pour chaque objet utilisateur et groupe dans le répertoire. Cet objectSID peut être décomposé en composants qui représentent l'identité du domaine Active Directory et l'identifiant relatif (RID) de l'objet utilisateur ou groupe.

L'algorithme de mappage des ID de SSSD prend une plage d'UID disponibles et la divise en sections de composants de taille égale - appelées « tranches ». Chaque tranche représente l'espace disponible pour un domaine Active Directory.

Lorsqu'une entrée utilisateur ou groupe pour un domaine particulier est rencontrée pour la première fois, SSSD alloue l'une des tranches disponibles pour ce domaine. Afin de rendre cette attribution de tranche reproductible sur différentes machines clientes, nous sélectionnons la tranche en fonction de l'algorithme suivant :

La chaîne SID est passée à travers l'algorithme murmurhash3 pour la convertir en une valeur hachée de 32 bits. Nous prenons ensuite le reste de cette valeur par le nombre total de tranches disponibles pour choisir la tranche.

NOTE : Il est possible de rencontrer des collisions dans le hachage et le modulo subséquent. Dans ces situations, nous sélectionnerons la tranche suivante disponible, mais il peut ne pas être possible de reproduire exactement le même ensemble de tranches sur d'autres machines (puisque l'ordre dans lequel elles sont rencontrées déterminera leurs tranches). Dans cette situation, il est recommandé soit de passer à l'utilisation d'attributs POSIX explicites dans Active Directory (désactivant le mappage des ID), soit de configurer un domaine par défaut pour garantir qu'au moins un est toujours cohérent. Voir « Configuration » pour plus de détails.

Configuration

Configuration minimale (dans la section « [domain/NOMDEDOMAINE] ») :

ldap_id_mapping = True
ldap_schema = ad

La configuration par défaut consiste à configurer 10 000 tranches, chacune capable de contenir jusqu'à 200 000 ID, à partir de 200 000 et jusqu'à 2 000 200 000. Cela devrait suffire pour la plupart des déploiements.

Configuration avancée

ldap_idmap_range_min (entier)

Spécifie la borne inférieure (inclusive) de la plage d'ID POSIX à utiliser pour mapper les SID d'utilisateurs et de groupes Active Directory. C'est le premier ID POSIX qui peut être utilisé pour le mappage.

NOTE : Cette option est différente de « min_id » en ce que « min_id » sert à filtrer la sortie des requêtes vers ce domaine, tandis que cette option contrôle la plage d'attribution des ID. C'est une distinction subtile, mais le bon conseil général serait d'avoir « min_id » inférieur ou égal à « ldap_idmap_range_min »

Par défaut : 200000

ldap_idmap_range_max (entier)

Spécifie la borne supérieure (exclusive) de la plage d'ID POSIX à utiliser pour mapper les SID d'utilisateurs et de groupes Active Directory. C'est le premier ID POSIX qui ne peut plus être utilisé pour le mappage, c'est-à-dire un ID supérieur au dernier qui peut être utilisé pour le mappage.

NOTE : Cette option est différente de « max_id » en ce que « max_id » sert à filtrer la sortie des requêtes vers ce domaine, tandis que cette option contrôle la plage d'attribution des ID. C'est une distinction subtile, mais le bon conseil général serait d'avoir « max_id » supérieur ou égal à « ldap_idmap_range_max »

Par défaut : 2000200000

ldap_idmap_range_size (entier)

Spécifie le nombre d'ID disponibles pour chaque tranche. Si la taille de la plage ne divise pas uniformément les valeurs minimale et maximale, elle créera autant de tranches complètes que possible.

NOTE : La valeur de cette option doit être au moins égale au RID utilisateur le plus élevé prévu pour être utilisé sur le serveur Active Directory. Les recherches d'utilisateurs et les connexions échoueront pour tout utilisateur dont le RID est supérieur à cette valeur.

Par exemple, si votre utilisateur Active Directory ajouté le plus récemment a l'objectSid=S-1-5-21-2153326666-2176343378-3404031434-1107, « ldap_idmap_range_size » doit être au moins 1108 car la taille de la plage est égale au RID maximal moins le RID minimal plus un (par exemple, 1108 = 1107 - 0 + 1).

Il est important de planifier à l'avance pour une expansion future, car la modification de cette valeur entraînera la modification de tous les mappages d'ID sur le système, ce qui donnera aux utilisateurs des ID locaux différents de ceux qu'ils avaient auparavant.

Par défaut : 200000

ldap_idmap_default_domain_sid (chaîne)

Spécifiez le SID du domaine par défaut. Cela garantira que ce domaine sera toujours attribué à la tranche zéro dans la carte d'ID, contournant l'algorithme murmurhash décrit ci-dessus.

Par défaut : non défini

ldap_idmap_default_domain (chaîne)

Spécifiez le nom du domaine par défaut.

Par défaut : non défini

ldap_idmap_autorid_compat (booléen)

sssd-ad.5.fr

NOM

sssd-ad - Le fournisseur SSSD pour Active Directory

DESCRIPTION

Le fournisseur SSSD pour Active Directory (AD) est un fournisseur qui permet à SSSD de récupérer les informations d'identité, d'authentification et d'autorisation depuis un domaine Active Directory.

Il peut être utilisé en remplacement des fournisseurs LDAP et Winbind pour la plupart des cas d'utilisation avec AD.

Le fournisseur AD peut être configuré dans le fichier de configuration SSSD, sssd.conf(5).

OPTIONS DE CONFIGURATION

Les options spécifiques au fournisseur AD sont décrites ci-dessous. Elles sont configurées dans la section [domain/EXAMPLE] où EXAMPLE est le nom du domaine AD.

La plupart de ces options sont des alias pour des options similaires du fournisseur LDAP, veuillez vous référer à sssd-ldap(5) pour plus de détails.

Options spécifiques à l'AD

ad_server
Liste de serveurs DNS AD à utiliser pour ce domaine.
ad_hostname
Nom d'hôte du client utilisé lors de la communication avec le serveur AD.
ad_domain
Nom du domaine AD.
ldap_connection_type
Type de connexion à utiliser avec le serveur AD. Les valeurs possibles sont ldap:// ou ldaps://.
ldap_chase_referrals
Si les recherches doivent suivre les renvois.
ldap_id_use_ur
Si les RID doivent être utilisées pour mapper les utilisateurs et groupes.
ldap_idmap_autorid_compat
Si le comportement de l'algorithme de mappage d'ID doit être plus similaire à l'algorithme « idmap_autorid » de winbind.

OPTIONS PAR DÉFAUT MODIFIÉES

Mappage d'ID

Change le comportement de l'algorithme de mappage d'ID afin qu'il se comporte de manière plus similaire à l'algorithme « idmap_autorid » de winbind.

Lorsque cette option est configurée, les domaines seront alloués en commençant par la tranche zéro et en augmentant mononotoniquement avec chaque domaine supplémentaire.

NOTE : Cet algorithme est non déterministe (il dépend de l'ordre des utilisateurs et groupes demandés). Si ce mode est requis pour la compatibilité avec les machines exécutant winbind, il est recommandé d'utiliser également l'option « ldap_idmap_default_domain_sid » pour garantir qu'au moins un domaine soit constamment alloué à la tranche zéro.

Par défaut : Faux

ldap_idmap_helper_table_size (entier)

Nombre maximal de tranches secondaires qui est essayé lors du mappage d'ID UNIX vers SID.

Note : Des tranches secondaires supplémentaires peuvent être générées lorsque le SID est mappé vers un ID UNIX et que la partie RID du SID est hors de portée pour les tranches secondaires générées jusqu'à présent. Si la valeur de ldap_idmap_helper_table_size est égale à 0, aucune tranche secondaire supplémentaire n'est générée.

Par défaut : 10

SIDS BIEN CONNUS

SSSD prend en charge la recherche des noms des SIDs bien connus, c'est-à-dire les SIDs ayant une signification spéciale codée en dur. Étant donné que les utilisateurs et groupes génériques liés à ces SIDs bien connus n'ont pas d'équivalent dans un environnement Linux/UNIX, aucun ID POSIX n'est disponible pour ces objets.

L'espace de noms SID est organisé en autorités qui peuvent être considérées comme différents domaines. Les autorités pour les SIDs bien connus sont

•Null Authority
•World Authority
•Local Authority
•Creator Authority
•Mandatory Label Authority
•Authentication Authority
•NT Authority
•Built-in

La version capitalisée de ces noms est utilisée comme noms de domaine lors du retour du nom complet d'un SID bien connu.

Étant donné que certains utilitaires permettent de modifier les informations de contrôle d'accès basées sur les SIDs à l'aide d'un nom au lieu d'utiliser directement le SID, SSSD prend également en charge la recherche du SID par son nom. Pour éviter les collisions, seuls les noms complets peuvent être utilisés pour rechercher les SIDs bien connus. En conséquence, les noms de domaine « NULL AUTHORITY », « WORLD AUTHORITY », « LOCAL AUTHORITY », « CREATOR AUTHORITY », « MANDATORY LABEL AUTHORITY », « AUTHENTICATION AUTHORITY », « NT AUTHORITY » et « BUILTIN » ne doivent pas être utilisés comme noms de domaine dans sssd.conf.

EXEMPLE

L'exemple suivant suppose que SSSD est correctement configuré et que example.com est l'un des domaines dans la section [sssd]. Cet exemple ne montre que les options spécifiques au fournisseur AD.

[domain/EXAMPLE]
id_provider = ad
auth_provider = ad
access_provider = ad
chpass_provider = ad
ad_server = dc1.example.com
ad_hostname = client.example.com
ad_domain = example.com

NOTES

Le fournisseur de contrôle d'accès AD vérifie si le compte est expiré. Il a le même effet que la configuration suivante du fournisseur LDAP :

access_provider = ldap
ldap_access_order = expire
ldap_account_expire_policy = ad

Cependant, à moins que le fournisseur d'accès « ad » ne soit explicitement configuré, le fournisseur d'accès par défaut est « permit » . Veuillez noter que si vous configurez un fournisseur d'accès autre que « ad », vous devez définir manuellement tous les paramètres de connexion (tels que les URI LDAP et les détails de chiffrement).

Lorsque le fournisseur autofs est défini sur « ad », le mappage d'attributs du schéma RFC2307 (nisMap, nisObject, ...) est utilisé, car ces attributs sont inclus dans le schéma Active Directory par défaut.
