SSH-COPY-ID(1) Manuel des commandes générales SSH-COPY-ID(1)

NOM

ssh-copy-id — utilise les clés disponibles localement pour autoriser les connexions sur une machine distante

SYNOPIS

ssh-copy-id [-f] [-n] [-s] [-x] [-i [fichier_identité]] [-t chemin_cible] [-F config_ssh] [[-o option_ssh] ...] [-p port] [utilisateur@]nom_hôte

ssh-copy-id -h | -?

DESCRIPTION

ssh-copy-id est un script qui utilise ssh(1) pour se connecter à une machine distante (probablement en utilisant un mot de passe de connexion, donc l'authentification par mot de passe doit être activée, sauf si vous avez fait quelque chose d'ingénieux avec plusieurs identités). Il assemble une liste d'une ou plusieurs empreintes digitales (comme décrit ci-dessous) et essaie de se connecter avec chaque clé, pour voir si l'une d'elles est déjà installée (bien sûr, si vous n'utilisez pas ssh-agent(1) cela peut entraîner des demandes répétées de phrases secrètes). Il assemble ensuite une liste de celles qui ont échoué à la connexion et, en utilisant ssh(1), active les connexions avec ces clés sur le serveur distant. Par défaut, il ajoute les clés en les ajoutant à ~/.ssh/authorized_keys de l'utilisateur distant (créant le fichier, et le répertoire, si nécessaire). Il est également capable de détecter si le système distant est un NetScreen, et d'utiliser sa commande ‘set ssh pka-dsa key ...’ à la place.

Les options sont les suivantes :

-i [fichier_identité]
Utilise uniquement la ou les clés contenues dans fichier_identité (plutôt que de rechercher des identités via ssh-add(1) ou dans le fichier_ID_par_défaut). Si le nom de fichier ne se termine pas par .pub, il est ajouté. Si le nom de fichier est omis, le fichier_ID_par_défaut est utilisé.

Notez que cela peut être utilisé pour s'assurer que les clés copiées ont le commentaire que vous préférez et/ou des options supplémentaires appliquées, en s'assurant que le fichier de clé a ces dernières définies comme préférées avant que la copie ne soit tentée.

-f
Mode forcé : ne vérifie pas si les clés sont présentes sur le serveur distant. Cela signifie qu'il n'a pas besoin de la clé privée. Bien sûr, cela peut entraîner l'installation de plusieurs copies de la clé sur le système distant.
-n
faire un essai à blanc. Au lieu d'installer les clés sur le système distant, il imprime simplement la ou les clés qui auraient été installées.
-s
Mode SFTP : généralement, les clés publiques sont installées en exécutant des commandes côté distant. Avec cette option, le fichier ~/.ssh/authorized_keys de l'utilisateur sera téléchargé, modifié localement et téléversé avec sftp. Cette option est utile si le serveur a des restrictions sur les commandes qui peuvent être utilisées côté distant.
-t chemin_cible
le chemin sur le système cible où les clés doivent être ajoutées (par défaut ".ssh/authorized_keys")
-p port
Spécifie le port auquel se connecter sur l'hôte distant.
-F config_ssh, -o option_ssh
Ces options sont simplement transmises telles quelles (avec leur argument) à ssh/sftp, permettant de définir un fichier de configuration alternatif, ou d'autres options, respectivement.

Plutôt que de les spécifier en tant qu'options de ligne de commande, il est souvent préférable d'utiliser des paramètres (par hôte) dans le fichier de configuration de ssh(1) : ssh_config(5).

-x
Cette option sert au débogage du script ssh-copy-id lui-même. Elle active l'indicateur -x du shell, afin que vous puissiez voir les commandes exécutées.
-h, -?
Affiche le résumé d'utilisation

Le comportement par défaut sans -i est de vérifier si ‘ssh-add -L’ fournit une sortie, et si c'est le cas, ces clés sont utilisées. Notez que cela entraîne que le commentaire sur la clé est le nom de fichier qui a été donné à ssh-add(1) lors du chargement de la clé dans votre ssh-agent(1) plutôt que le commentaire contenu dans ce fichier, ce qui est un peu dommage. Sinon, si ssh-add(1) ne fournit aucune clé, le contenu du fichier_ID_par_défaut sera utilisé.

Le fichier_ID_par_défaut est le fichier le plus récent qui correspond à : ~/.ssh/id*.pub, (excluant ceux qui correspondent à ~/.ssh/*-cert.pub). Donc, si vous créez une clé qui n'est pas celle que vous souhaitez que ssh-copy-id utilise, utilisez simplement touch(1) sur le fichier .pub de votre clé préférée pour la rétablir comme la plus récente.

EXEMPLES

Si vous avez déjà installé des clés d'un système sur de nombreux hôtes distants, et que vous créez ensuite une nouvelle clé, sur une nouvelle machine cliente par exemple, il peut être difficile de suivre les systèmes sur lesquels vous avez installé la nouvelle clé. Une façon de gérer cela est de charger la nouvelle clé et les anciennes clés dans votre ssh-agent(1). Chargez d'abord la nouvelle clé, sans l'option -c, puis chargez une ou plusieurs anciennes clés dans l'agent, éventuellement en vous connectant à la machine cliente qui possède cette ancienne clé, en utilisant l'option -A pour permettre le transfert d'agent :

utilisateur@nouveau_client$ ssh-add
utilisateur@nouveau_client$ ssh -A ancien.client
utilisateur@ancien$ ssh-add -c
... invite pour la phrase secrète ...
utilisateur@ancien$ logoff
utilisateur@nouveau_client$ ssh serveur

Maintenant, si la nouvelle clé est installée sur le serveur, vous serez autorisé à entrer sans être invité, tandis que si seules les anciennes clés sont activées, vous serez invité à confirmer, ce qui est votre signal pour vous déconnecter et exécuter

utilisateur@nouveau_client$ ssh-copy-id -i serveur

La raison pour laquelle vous pourriez vouloir spécifier l'option -i dans ce cas est de vous assurer que le commentaire sur la clé installée est celui du fichier .pub, plutôt que simplement le nom de fichier qui a été chargé dans votre agent. Cela garantit également que seule l'identifiant que vous avez l'intention d'installer est installé, plutôt que toutes les clés que vous avez dans votre ssh-agent(1). Bien sûr, vous pouvez spécifier un autre identifiant, ou utiliser le contenu de ssh-agent(1) comme vous le préférez.

Après avoir mentionné l'option -c de ssh-add(1), vous pourriez envisager de l'utiliser chaque fois que vous utilisez le transfert d'agent pour éviter que votre clé ne soit détournée, mais il est beaucoup mieux d'utiliser à la place l'option ProxyCommand et l'option -W de ssh(1), pour passer par des serveurs distants tout en effectuant toujours une authentification de bout en bout directe.
