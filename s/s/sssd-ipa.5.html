NOM

sssd-ipa - Fournisseur IPA de SSSD

DESCRIPTION

Cette page de manuel décrit la configuration du fournisseur IPA pour sssd(8). Pour une référence de syntaxe détaillée, consultez la section « FORMAT DU FICHIER » de la page de manuel sssd.conf(5).

Le fournisseur IPA est un back end utilisé pour se connecter à un serveur IPA. (Consultez le site web freeipa.org pour des informations sur les serveurs IPA.) Ce fournisseur exige que la machine soit jointe au domaine IPA ; la configuration est presque entièrement auto-découverte et obtenue directement du serveur.

Le fournisseur IPA permet à SSSD d'utiliser le fournisseur d'identité sssd-ldap(5) et le fournisseur d'authentification sssd-krb5(5) avec des optimisations pour les environnements IPA. Le fournisseur IPA accepte les mêmes options que celles utilisées par les fournisseurs sssd-ldap et sssd-krb5, à quelques exceptions près. Cependant, il n'est ni nécessaire ni recommandé de définir ces options.

Le fournisseur IPA copie principalement les options par défaut traditionnelles des fournisseurs ldap et krb5, à quelques exceptions près ; les différences sont listées dans la section « OPTIONS PAR DÉFAUT MODIFIÉES ».

En tant que fournisseur d'accès, le fournisseur IPA a une configuration minimale (voir « ipa_access_order »), car il utilise principalement les règles HBAC (contrôle d'accès basé sur l'hôte). Veuillez vous référer à freeipa.org pour plus d'informations sur HBAC.

Si « auth_provider=ipa » ou « access_provider=ipa » est configuré dans sssd.conf, alors id_provider doit également être défini sur « ipa ».

Le fournisseur IPA utilisera le répondeur PAC si les tickets Kerberos des utilisateurs des domaines de confiance contiennent un PAC. Pour faciliter la configuration, le répondeur PAC démarre automatiquement si le fournisseur d'identité IPA est configuré.

OPTIONS DE CONFIGURATION

Consultez la section « SECTIONS DE DOMAINE » de la page de manuel sssd.conf(5) pour plus de détails sur la configuration d'un domaine SSSD.

ipa_domain (string)

Spécifie le nom du domaine IPA. Ceci est facultatif. S'il n'est pas fourni, le nom du domaine de configuration est utilisé.

ipa_server, ipa_backup_server (string)

La liste des adresses IP ou des noms d'hôte des serveurs IPA auxquels SSSD doit se connecter, séparés par des virgules, dans l'ordre de préférence. Pour plus d'informations sur la gestion des défaillances et la redondance des serveurs, voir la section « GESTION DES DÉFAILLANCES ». Ceci est facultatif si la découverte automatique est activée. Pour plus d'informations sur la découverte de services, reportez-vous à la section « DÉCOUVERTE DE SERVICES ».

ipa_hostname (string)

Facultatif. Peut être défini sur les machines où le nom d'hôte (hostname(5)) ne reflète pas le nom de domaine qualifié complet utilisé dans le domaine IPA pour identifier cet hôte. Le nom d'hôte doit être qualifié complet.

dyndns_update (boolean)

Facultatif. Cette option indique à SSSD de mettre à jour automatiquement le serveur DNS intégré à FreeIPA avec l'adresse IP de ce client. La mise à jour est sécurisée à l'aide de GSS-TSIG. L'adresse IP de la connexion IPA LDAP est utilisée pour les mises à jour, si elle n'est pas spécifiée autrement à l'aide de l'option « dyndns_iface ».

NOTE : Sur les systèmes plus anciens (comme RHEL 5), pour que ce comportement fonctionne de manière fiable, le domaine Kerberos par défaut doit être correctement défini dans /etc/krb5.conf.

NOTE : Bien qu'il soit toujours possible d'utiliser l'ancienne option ipa_dyndns_update, les utilisateurs devraient migrer vers l'utilisation de dyndns_update dans leur fichier de configuration.

Par défaut : false

dyndns_ttl (integer)

Le TTL (Time To Live) à appliquer à l'enregistrement DNS du client lors de sa mise à jour. Si dyndns_update est false, cela n'a aucun effet. Ceci remplacera le TTL côté serveur s'il est défini par un administrateur.

NOTE : Bien qu'il soit toujours possible d'utiliser l'ancienne option ipa_dyndns_ttl, les utilisateurs devraient migrer vers l'utilisation de dyndns_ttl dans leur fichier de configuration.

Par défaut : 1200 (secondes)

dyndns_iface (string)

Facultatif. Applicable uniquement lorsque dyndns_update est vrai. Choisissez l'interface ou une liste d'interfaces dont les adresses IP doivent être utilisées pour les mises à jour DNS dynamiques. Le nom de l'interface peut être un modèle générique (wildcard). Voir man 7 glob pour les détails sur les modèles.

NOTE : Bien qu'il soit toujours possible d'utiliser l'ancienne option ipa_dyndns_iface, les utilisateurs devraient migrer vers l'utilisation de dyndns_iface dans leur fichier de configuration.

Par défaut : Utiliser les adresses IP de l'interface utilisée pour la connexion IPA LDAP

Exemple : dyndns_iface = em1, vnet1, vnet2

dyndns_auth (string)

Indique si l'utilitaire nsupdate doit utiliser l'authentification GSS-TSIG pour des mises à jour sécurisées avec le serveur DNS. Des mises à jour non sécurisées peuvent être envoyées en définissant cette option sur 'none'.

Par défaut : GSS-TSIG

dyndns_auth_ptr (string)

Indique si l'utilitaire nsupdate doit utiliser l'authentification GSS-TSIG pour des mises à jour PTR sécurisées avec le serveur DNS. Des mises à jour non sécurisées peuvent être envoyées en définissant cette option sur 'none'.

Par défaut : Identique à dyndns_auth

ipa_enable_dns_sites (boolean)

Active les sites DNS - découverte de services basée sur la localisation.

Si vrai et si la découverte de services (voir le paragraphe Service Discovery au bas de la page man) est activée, alors SSSD tentera d'abord la découverte basée sur la localisation en utilisant une requête contenant "_location.hostname.example.com", puis se rabattra sur la découverte SRV traditionnelle. Si la découverte basée sur la localisation réussit, les serveurs IPA localisés avec la découverte basée sur la localisation sont traités comme des serveurs primaires et les serveurs IPA localisés à l'aide de la découverte SRV traditionnelle sont utilisés comme serveurs de secours.

Par défaut : false

dyndns_refresh_interval (integer)

Fréquence à laquelle le back end doit effectuer une mise à jour DNS périodique en plus de la mise à jour automatique effectuée lorsque le back end est en ligne. Cette option est facultative et applicable uniquement lorsque dyndns_update est vrai.

Par défaut : 0 (désactivé)

dyndns_update_ptr (bool)

Indique si l'enregistrement PTR doit également être mis à jour explicitement lors de la mise à jour des enregistrements DNS du client. Applicable uniquement lorsque dyndns_update est vrai.

Cette option doit être False dans la plupart des déploiements IPA car le serveur IPA génère automatiquement les enregistrements PTR lorsque les enregistrements directs sont modifiés.

Notez que le paramètre dyndns_update_per_family ne s'applique pas aux mises à jour des enregistrements PTR. Ces mises à jour sont toujours envoyées séparément.

Par défaut : False (désactivé)

dyndns_force_tcp (bool)

Indique si l'utilitaire nsupdate doit utiliser TCP par défaut pour communiquer avec le serveur DNS.

Par défaut : False (laisser nsupdate choisir le protocole)

dyndns_server (string)

Le serveur DNS à utiliser lors de l'exécution d'une mise à jour DNS. Dans la plupart des configurations, il est recommandé de laisser cette option non définie.

Définir cette option a du sens pour les environnements où le serveur DNS est différent du serveur d'identité ou lorsque nous utilisons le DNS crypté.

Le paramètre peut être une simple chaîne contenant le nom DNS ou l'adresse IP. Il peut également s'agir d'une URI. L'URI peut ressembler à dns://servername/ ou dns+tls://1.2.3.4:853#servername/.

Le second exemple active le protocole DNS-over-TLS pour les mises à jour DNS. L'utilitaire nsupdate doit prendre en charge DoT - vérifiez man nsupdate avant de l'activer dans SSSD.

Veuillez noter que cette option ne sera utilisée que dans une tentative de secours lorsque la tentative précédente utilisant les paramètres auto-détectés a échoué ou lorsque DNS-over-TLS est activé.

Par défaut : Aucun (laisser nsupdate choisir le serveur)

dyndns_update_per_family (boolean)

La mise à jour DNS est par défaut effectuée en deux étapes : mise à jour IPv4 puis mise à jour IPv6. Dans certains cas, il peut être souhaitable d'effectuer les mises à jour IPv4 et IPv6 en une seule étape.

Par défaut : true

dyndns_dot_cacert (string)

Cette option spécifie le fichier des certificats d'autorité de certification (au format PEM) afin de vérifier le certificat du serveur distant lors de l'utilisation de DoT.

Par défaut : Aucun (utilise le magasin de certificats global)

dyndns_dot_cert (string)

Cette option définit le ou les fichiers de certificat pour l'authentification du transport DoT vers le serveur distant. Le fichier de chaîne de certificats est attendu au format PEM.

Par défaut : Aucun (aucune authentification client)

FOURNISSEUR SOUSDOMAINES

Le fournisseur de sous-domaines IPA se comporte légèrement différemment s'il est configuré explicitement ou implicitement.

Si l'option 'subdomains_provider = ipa' est trouvée dans la section de domaine de sssd.conf, le fournisseur de sous-domaines IPA est configuré explicitement, et toutes les requêtes de sous-domaines sont envoyées au serveur IPA si nécessaire.

Si l'option 'subdomains_provider' n'est pas définie dans la section de domaine de sssd.conf mais qu'il existe l'option 'id_provider = ipa', le fournisseur de sous-domaines IPA est configuré implicitement. Dans ce cas, si une requête de sous-domaine échoue et indique que le serveur ne prend pas en charge les sous-domaines, c'est-à-dire qu'il n'est pas configuré pour les trusts, le fournisseur de sous-domaines IPA est désactivé. Après une heure ou après que le fournisseur IPA soit en ligne, le fournisseur de sous-domaines est réactivé.

CONFIGURATION DES DOMAINES DE CONFIANCE

Certaines options de configuration peuvent également être définies pour un domaine de confiance. Une configuration de domaine de confiance peut être définie à l'aide de la sous-section domaine de confiance comme montré dans l'exemple ci-dessous. Alternativement, l'option “subdomain_inherit” peut être utilisée dans le domaine parent.

[domain/ipa.domain.com/ad.domain.com]
ad_server = dc.ad.domain.com

Pour plus de détails, consultez la page de manuel sssd.conf(5).

Différentes options de configuration sont ajustables pour un domaine de confiance selon que vous configuriez SSSD sur un serveur IPA ou un client IPA.

OPTIONS AJUSTABLES SUR LES MAÎTRES IPA

Les options suivantes peuvent être définies dans une section de sous-domaine sur un maître IPA :

•ad_server
•ad_backup_server
•ad_site
•ipa_server
•ipa_backup_server
•ldap_search_base
•ldap_user_search_base
•ldap_group_search_base
•use_fully_qualified_names

Les options préfixées par 'ad_' ou 'ipa_' s'appliquent uniquement à leur type de sous-domaine respectif.

OPTIONS AJUSTABLES SUR LES CLIENTS IPA

Les options suivantes peuvent être définies dans une section de sous-domaine AD sur un client IPA :

•ad_server
•ad_site

Notez que si les deux options sont définies, seule “ad_server” est évaluée.

Étant donné que toute requête pour une identité utilisateur ou groupe d'un domaine de confiance déclenchée par un client IPA est résolue par le serveur IPA, les options “ad_server” et “ad_site” affectent uniquement le contrôleur de domaine AD auquel l'authentification sera effectuée. En particulier, les adresses résolues à partir de ces listes seront écrites dans les fichiers “kdcinfo” lus par le plugin localisateur Kerberos. Veuillez vous référer à la page de manuel sssd_krb5_locator_plugin(8) pour plus de détails sur le plugin localisateur Kerberos.

COMMUTATION DE SECOURS

La fonctionnalité de commutation de secours permet aux backends de passer automatiquement à un serveur différent si le serveur actuel échoue.

Syntaxe de commutation de secours

La liste des serveurs est donnée sous forme de liste séparée par des virgules ; tout nombre d'espaces est autorisé autour de la virgule. Les serveurs sont listés par ordre de préférence. La liste peut contenir n'importe quel nombre de serveurs.

Pour chaque option de configuration activée pour la commutation de secours, deux variantes existent : primaire et secondaire. L'idée est que les serveurs de la liste primaire sont préférés et que les serveurs secondaires ne sont recherchés que si aucun serveur primaire ne peut être atteint. Si un serveur secondaire est sélectionné, un délai de 31 secondes est défini. Après ce délai, SSSD tentera périodiquement de se reconnecter à l'un des serveurs primaires. En cas de succès, il remplacera le serveur actif (secondaire) actuel.

Le mécanisme de commutation de secours

Le mécanisme de commutation de secours distingue une machine d'un service. Le backend essaie d'abord de résoudre le nom d'hôte d'une machine donnée ; si cette tentative de résolution échoue, la machine est considérée comme hors ligne. Aucune autre tentative n'est faite pour se connecter à cette machine pour tout autre service. Si la tentative de résolution réussit, le backend essaie de se connecter à un service sur cette machine. Si la tentative de connexion au service échoue, alors seul ce service particulier est considéré comme hors ligne et le backend bascule automatiquement vers le service suivant. La machine est toujours considérée comme en ligne et peut encore être essayée pour un autre service.

D'autres tentatives de connexion sont effectuées vers les machines ou les services marqués comme hors ligne après une période de temps spécifiée ; celle-ci est actuellement codée en dur à 30 secondes.

S'il n'y a plus de machines à essayer, le backend dans son ensemble passe en mode hors ligne, puis tente de se reconnecter toutes les 30 secondes.

Délais d'attente et réglage de la commutation de secours

La résolution d'un serveur auquel se connecter peut être aussi simple qu'une seule requête DNS ou impliquer plusieurs étapes, comme trouver le bon site ou essayer plusieurs noms d'hôtes si certains des serveurs configurés ne sont pas joignables. Les scénarios plus complexes peuvent prendre du temps et SSSD doit trouver un équilibre entre laisser suffisamment de temps pour terminer le processus de résolution, et d'autre part, ne pas essayer trop longtemps avant de revenir au mode hors ligne. Si les logs de débogage SSSD montrent que la résolution du serveur expire avant qu'un serveur actif ne soit contacté, vous pouvez envisager de modifier les délais d'attente.

Cette section liste les paramètres ajustables disponibles. Veuillez vous référer à leur description dans la page de manuel sssd.conf(5).

dns_resolver_server_timeout

Temps en millisecondes qui définit combien de temps SSSD parlera à un serveur DNS unique avant d'essayer le suivant.

Par défaut : 1000

dns_resolver_op_timeout

Temps en secondes pour indiquer combien de temps SSSD essaiera de résoudre une requête DNS unique (par exemple, la résolution d'un nom d'hôte ou d'un enregistrement SRV) avant d'essayer le nom d'hôte ou le domaine de découverte suivant.

Par défaut : 3

dns_resolver_timeout

Combien de temps SSSD essaiera de résoudre un service de secours. Cette résolution de service peut impliquer plusieurs étapes, comme la résolution des requêtes DNS SRV ou la localisation du site.

Par défaut : 6

Pour les fournisseurs basés sur LDAP, l'opération de résolution est effectuée dans le cadre d'une opération de connexion LDAP. Par conséquent, le délai d'attente “ldap_opt_timeout” doit également être défini sur une valeur supérieure à “dns_resolver_timeout”, qui à son tour doit être défini sur une valeur supérieure à “dns_resolver_op_timeout”, qui doit être supérieure à “dns_resolver_server_timeout”.

DÉCOUVERTE DE SERVICE

La fonctionnalité de découverte de service permet aux backends de trouver automatiquement les serveurs appropriés auxquels se connecter à l'aide d'une requête DNS spéciale. Cette fonctionnalité n'est pas prise en charge pour les serveurs de secours.

Configuration

Si aucun serveur n'est spécifié, le backend utilise automatiquement la découverte de service pour essayer de trouver un serveur. Optionnellement, l'utilisateur peut choisir d'utiliser à la fois des adresses de serveur fixes et la découverte de service en insérant un mot-clé spécial, “_srv_”, dans la liste des serveurs. L'ordre de préférence est maintenu. Cette fonctionnalité est utile si, par exemple, l'utilisateur préfère utiliser la découverte de service chaque fois que possible, et se rabattre sur un serveur spécifique lorsqu'aucun serveur ne peut être découvert via DNS.

Le nom de domaine

Veuillez vous référer au paramètre “dns_discovery_domain” dans la page de manuel sssd.conf(5) pour plus de détails.

Le protocole

Les requêtes spécifient généralement _tcp comme protocole. Les exceptions sont documentées dans la description de l'option respective.

Voir aussi

Pour plus d'informations sur le mécanisme de découverte de service, référez-vous à la RFC 2782.

L'exemple suivant suppose que SSSD est correctement configuré et que example.com est l'un des domaines dans la section [sssd]. Cet exemple ne montre que les options spécifiques au fournisseur ipa.
