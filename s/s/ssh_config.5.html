SSH_CONFIG(5) Manuel des formats de fichiers SSH_CONFIG(5)

NOM

ssh_config — Fichier de configuration du client OpenSSH

DESCRIPTION

ssh(1) obtient des données de configuration des sources suivantes, dans l'ordre indiqué :

  1. options en ligne de commande
  2. fichier de configuration de l'utilisateur (~/.ssh/config)
  3. fichier de configuration à l'échelle du système (/etc/ssh/ssh_config)

Sauf indication contraire, pour chaque paramètre, la première valeur obtenue sera utilisée. Les fichiers de configuration contiennent des sections séparées par des spécifications Host, et cette section n'est appliquée qu'aux hôtes qui correspondent à l'un des modèles donnés dans la spécification. Le nom d'hôte correspondant est généralement celui donné en ligne de commande (voir l'option CanonicalizeHostname pour les exceptions).

Étant donné que la première valeur obtenue pour chaque paramètre est utilisée, les déclarations plus spécifiques à l'hôte doivent être données près du début du fichier, et les valeurs par défaut générales à la fin.

Le fichier contient des paires mot-clé-argument, une par ligne. Les lignes commençant par ‘#’ et les lignes vides sont interprétées comme des commentaires. Les arguments peuvent être facultativement entourés de guillemets doubles (") afin de représenter des arguments contenant des espaces. Les options de configuration peuvent être séparées par des espaces blancs ou des espaces blancs facultatifs et exactement un ‘=’ ; le second format est utile pour éviter le besoin de mettre des espaces blancs entre guillemets lors de la spécification des options de configuration à l'aide de l'option -o de ssh, scp et sftp.

Les mots-clés possibles et leurs significations sont les suivants (notez que les mots-clés ne sont pas sensibles à la casse et les arguments le sont) :

Host
Restreint les déclarations suivantes (jusqu'au prochain mot-clé Host ou Match) pour qu'elles ne s'appliquent qu'aux hôtes qui correspondent à l'un des modèles donnés après le mot-clé. Si plusieurs modèles sont fournis, ils doivent être séparés par des espaces. Un seul ‘*’ comme modèle peut être utilisé pour fournir des valeurs par défaut globales à tous les hôtes. L'hôte est généralement l'argument hostname donné en ligne de commande (voir le mot-clé CanonicalizeHostname pour les exceptions).

Une entrée de modèle peut être niée en la faisant précéder d'un point d'exclamation (‘!’). Si une entrée niée correspond, l'entrée Host est ignorée, indépendamment du fait que d'autres modèles sur la ligne correspondent. Les correspondances niées sont donc utiles pour fournir des exceptions aux correspondances génériques.

Voir PATTERNS pour plus d'informations sur les modèles.

Match
Restreint les déclarations suivantes (jusqu'au prochain mot-clé Host ou Match) pour qu'elles ne soient utilisées que lorsque les conditions suivant le mot-clé Match sont satisfaites. Les conditions de correspondance sont spécifiées à l'aide d'un ou plusieurs critères ou du jeton unique all qui correspond toujours. Les critères disponibles sont : canonical, final, exec, localnetwork, host, originalhost, tagged, command, user, localuser, et version. Le critère all doit apparaître seul ou immédiatement après canonical ou final. D'autres critères peuvent être combinés arbitrairement. Tous les critères, sauf all, canonical et final, requièrent un argument. Les critères peuvent être niés en ajoutant un point d'exclamation (‘!’).

Le mot-clé canonical ne correspond que lorsque le fichier de configuration est en cours de ré-analyse après la canonicalisation du nom d'hôte (voir l'option CanonicalizeHostname). Ceci peut être utile pour spécifier des conditions qui fonctionnent uniquement avec des noms d'hôtes canonicalisés.

Le mot-clé final demande que la configuration soit ré-analysée (indépendamment de l'activation de CanonicalizeHostname) et ne correspond que lors de cette dernière passe. Si CanonicalizeHostname est activé, alors canonical et final correspondent lors de la même passe.

Le mot-clé exec exécute la commande spécifiée sous le shell de l'utilisateur. Si la commande retourne un statut de sortie zéro, la condition est considérée comme vraie. Les commandes contenant des espaces doivent être mises entre guillemets. Les arguments de exec acceptent les jetons décrits dans la section TOKENS.

Le mot-clé localnetwork correspond aux adresses des interfaces réseau locales actives par rapport à la liste fournie de réseaux au format CIDR. Ceci peut être pratique pour faire varier la configuration effective sur des appareils qui se déplacent entre les réseaux. Notez que l'adresse réseau n'est pas un critère digne de confiance dans de nombreuses situations (par exemple, lorsque le réseau est configuré automatiquement via DHCP) et donc des précautions doivent être prises si vous l'utilisez pour contrôler une configuration sensible à la sécurité.

Les critères des autres mots-clés doivent être des entrées uniques ou des listes séparées par des virgules et peuvent utiliser les opérateurs génériques et de négation décrits dans la section PATTERNS.

Les critères du mot-clé host sont comparés au nom d'hôte cible, après toute substitution par les options Hostname ou CanonicalizeHostname. Le mot-clé originalhost correspond au nom d'hôte tel qu'il a été spécifié en ligne de commande.

Le mot-clé tagged correspond à un nom de balise spécifié par une directive Tag antérieure ou sur la ligne de commande de ssh(1) via le drapeau -P. Le mot-clé command correspond à la commande distante demandée, ou au nom du sous-système appelé (par exemple, "sftp" pour une session SFTP). La chaîne vide correspond au cas où aucune commande ou balise n'a été spécifiée, c'est-à-dire ‘Match tag ""’. Le mot-clé version correspond à la chaîne de version de ssh(1), par exemple “OpenSSH_10.0”.

Le mot-clé user correspond au nom d'utilisateur cible sur l'hôte distant. Le mot-clé localuser correspond au nom de l'utilisateur local exécutant ssh(1) (ce mot-clé peut être utile dans les fichiers ssh_config système).

Enfin, le mot-clé sessiontype correspond au type de session demandé, qui peut être l'un des suivants : shell pour les sessions interactives, exec pour les sessions d'exécution de commande, subsystem pour les invocations de sous-systèmes telles que sftp(1), ou none pour les sessions de transport uniquement, comme lorsque ssh(1) est lancé avec le drapeau -N.

AddressFamily
Spécifie la famille d'adresses à utiliser lors de la connexion. Les arguments valides sont any (par défaut), inet (utiliser uniquement IPv4) ou inet6 (utiliser uniquement IPv6).
BatchMode
Si défini sur yes, l'interaction avec l'utilisateur, telle que les invites de mot de passe et les demandes de confirmation de clé hôte, sera désactivée. Cette option est utile dans les scripts et autres travaux par lots où aucun utilisateur n'est présent pour interagir avec ssh(1). L'argument doit être yes ou no (par défaut).
BindAddress
Utilise l'adresse spécifiée sur la machine locale comme adresse source de la connexion. Utile uniquement sur les systèmes disposant de plusieurs adresses.
BindInterface
Utilise l'adresse de l'interface spécifiée sur la machine locale comme adresse source de la connexion.
CanonicalDomains
Lorsque CanonicalizeHostname est activé, cette option spécifie la liste des suffixes de domaine dans lesquels rechercher l'hôte de destination spécifié.
CanonicalizeFallbackLocal
Spécifie s'il faut échouer avec une erreur lorsque la canonicalisation du nom d'hôte échoue. Par défaut, yes, il tentera de résoudre le nom d'hôte non qualifié en utilisant les règles de recherche du résolveur système. Une valeur de no provoquera l'échec immédiat de ssh(1) si CanonicalizeHostname est activé et que le nom d'hôte cible ne peut pas être trouvé dans l'un des domaines spécifiés par CanonicalDomains.
CanonicalizeHostname
Contrôle si la canonicalisation explicite du nom d'hôte est effectuée. Par défaut, no, aucune réécriture de nom n'est effectuée et le résolveur système gère toutes les recherches de noms d'hôte. Si défini sur yes, alors, pour les connexions qui n'utilisent pas de ProxyCommand ou de ProxyJump, ssh(1) tentera de canonicaliser le nom d'hôte spécifié sur la ligne de commande en utilisant les suffixes CanonicalDomains et les règles CanonicalizePermittedCNAMEs. Si CanonicalizeHostname est défini sur always, la canonicalisation est également appliquée aux connexions proxysées.

Si cette option est activée, les fichiers de configuration sont traités à nouveau en utilisant le nouveau nom cible pour récupérer toute nouvelle configuration dans les strophes Host et Match correspondantes. Une valeur de none désactive l'utilisation d'un hôte ProxyJump.

CanonicalizeMaxDots
Spécifie le nombre maximum de points dans un nom d'hôte avant que la canonicalisation ne soit désactivée. Par défaut, 1, autorise un seul point (c'est-à-dire hostname.subdomain).
CanonicalizePermittedCNAMEs
Spécifie les règles pour déterminer si les CNAME doivent être suivis lors de la canonicalisation des noms d'hôte. Les règles consistent en un ou plusieurs arguments de liste_domaines_source:liste_domaines_cible, où liste_domaines_source est une liste de motifs de domaines qui peuvent suivre les CNAME lors de la canonicalisation, et liste_domaines_cible est une liste de motifs de domaines vers lesquels ils peuvent résoudre.

Par exemple, "*.a.example.com:*.b.example.com,*.c.example.com" permettra aux noms d'hôtes correspondant à "*.a.example.com" d'être canonicalisés en noms dans les domaines "*.b.example.com" ou "*.c.example.com".

Un seul argument "none" empêche la prise en compte des CNAME pour la canonicalisation. C'est le comportement par défaut.

CASignatureAlgorithms
Spécifie quels algorithmes sont autorisés pour la signature de certificats par les autorités de certification (AC). Par défaut : 
ssh-ed25519,ecdsa-sha2-nistp256,
ecdsa-sha2-nistp384,ecdsa-sha2-nistp521,
sk-ssh-ed25519@openssh.com,
sk-ecdsa-sha2-nistp256@openssh.com,
rsa-sha2-512,rsa-sha2-256

Si la liste spécifiée commence par un caractère ‘+’, les algorithmes spécifiés seront ajoutés à l'ensemble par défaut au lieu de les remplacer. Si la liste spécifiée commence par un caractère ‘-’, les algorithmes spécifiés (y compris les caractères génériques) seront supprimés de l'ensemble par défaut au lieu de les remplacer.

ssh(1) n'acceptera pas les certificats hôtes signés à l'aide d'algorithmes autres que ceux spécifiés.

CertificateFile
Spécifie un fichier à partir duquel le certificat de l'utilisateur est lu. Une clé privée correspondante doit être fournie séparément afin d'utiliser ce certificat, soit à partir d'une directive IdentityFile, soit via le drapeau -i de ssh(1), soit via ssh-agent(1), soit via un PKCS11Provider ou un SecurityKeyProvider.

Les arguments de CertificateFile peuvent utiliser la syntaxe tilde pour faire référence au répertoire personnel de l'utilisateur, les jetons décrits dans la section JETONS et les variables d'environnement comme décrit dans la section VARIABLES D'ENVIRONNEMENT.

Il est possible de spécifier plusieurs fichiers de certificats dans les fichiers de configuration ; ces certificats seront essayés en séquence. Les directives multiples CertificateFile s'ajouteront à la liste des certificats utilisés pour l'authentification.

ChannelTimeout
Spécifie si et à quelle vitesse ssh(1) doit fermer les canaux inactifs. Les délais d'attente sont spécifiés comme une ou plusieurs paires « type=intervalle » séparées par des espaces, où le « type » doit être le mot-clé spécial « global » ou un nom de type de canal de la liste ci-dessous, pouvant contenir des caractères génériques.

La valeur de délai d'attente « intervalle » est spécifiée en secondes ou peut utiliser l'une des unités documentées dans la section FORMATS DE TEMPS. Par exemple, « session=5m » entraînerait la terminaison des sessions interactives après cinq minutes d'inactivité. Spécifier une valeur zéro désactive le délai d'attente d'inactivité.

Le délai d'attente spécial « global » s'applique à tous les canaux actifs, collectivement. Le trafic sur n'importe quel canal actif réinitialisera le délai d'attente, mais lorsque le délai d'attente expirera, tous les canaux ouverts seront fermés. Notez que ce délai d'attente global n'est pas associé aux caractères génériques et doit être spécifié explicitement.

Les noms de types de canaux disponibles incluent :

agent-connection
Connexions ouvertes à ssh-agent(1).
direct-tcpip, direct-streamlocal@openssh.com
Connexions TCP ou de socket Unix (respectivement) ouvertes qui ont été établies à partir d'un transfert local ssh(1), c'est-à-dire LocalForward ou DynamicForward.
forwarded-tcpip, forwarded-streamlocal@openssh.com
Connexions TCP ou de socket Unix (respectivement) ouvertes qui ont été établies vers un sshd(8) écoutant au nom d'un transfert distant ssh(1), c'est-à-dire RemoteForward.
session
La session principale interactive, y compris la session shell, l'exécution de commandes, scp(1), sftp(1), etc.
tun-connection
Connexions TunnelForward ouvertes.
x11-connection
Sessions de transfert X11 ouvertes.

Notez que dans tous les cas ci-dessus, la terminaison

n d’une session inactive ne garantit pas la suppression de toutes les ressources associées à la session, par exemple les processus shell ou les clients X11 liés à la session peuvent continuer à s’exécuter.

De plus, la terminaison d’un canal ou d’une session inactive ne ferme pas nécessairement la connexion SSH, ni nécessairement n’empêche un client de demander un autre canal du même type. En particulier, l’expiration d’une session de transfert inactive n’empêche pas qu’un autre transfert identique soit créé subséquemment.

La valeur par défaut est de ne pas expirer les canaux de quelque type que ce soit en raison de l’inactivité.

CheckHostIP
Si définie sur yes, ssh(1) vérifiera supplémentairement l’adresse IP de l’hôte dans le fichier known_hosts. Cela permet de détecter si une clé d’hôte a changé en raison d’un usurpation de DNS et ajoutera les adresses des hôtes de destination dans ~/.ssh/known_hosts, indépendamment du paramètre StrictHostKeyChecking. Si l’option est définie sur no (la valeur par défaut), la vérification ne sera pas effectuée.
Ciphers
Spécifie les chiffrements autorisés et leur ordre de priorité. Plusieurs chiffrements doivent être séparés par des virgules. Si la liste spécifiée commence par un caractère ‘+’, alors les chiffrements spécifiés seront ajoutés à l’ensemble par défaut au lieu de les remplacer. Si la liste spécifiée commence par un caractère ‘-’, alors les chiffrements spécifiés (y compris les caractères génériques) seront retirés de l’ensemble par défaut au lieu de les remplacer. Si la liste spécifiée commence par un caractère ‘^’, alors les chiffrements spécifiés seront placés en tête de l’ensemble par défaut.

Les chiffrements pris en charge sont :

3des-cbc
aes128-cbc
aes192-cbc
aes256-cbc
aes128-ctr
aes192-ctr
aes256-ctr
aes128-gcm@openssh.com
aes256-gcm@openssh.com
chacha20-poly1305@openssh.com

La valeur par défaut est :

chacha20-poly1305@openssh.com,
aes128-gcm@openssh.com,aes256-gcm@openssh.com,
aes128-ctr,aes192-ctr,aes256-ctr

La liste des chiffrements disponibles peut également être obtenue en utilisant "ssh -Q cipher".

ClearAllForwardings
Spécifie que tous les transferts de ports locaux, distants et dynamiques spécifiés dans les fichiers de configuration ou sur la ligne de commande doivent être effacés. Cette option est principalement utile lorsqu’elle est utilisée depuis la ligne de commande ssh(1) pour effacer les transferts de ports définis dans les fichiers de configuration, et est automatiquement définie par scp(1) et sftp(1). L’argument doit être yes ou no (la valeur par défaut).
Compression
Spécifie si la compression doit être utilisée. L’argument doit être yes ou no (la valeur par défaut).
ConnectionAttempts
Spécifie le nombre d’essais (un par seconde) à effectuer avant de quitter. L’argument doit être un entier. Cela peut être utile dans les scripts si la connexion échoue parfois. La valeur par défaut est 1.
ConnectTimeout
Spécifie le délai d’attente (en secondes) utilisé lors de la connexion au serveur SSH, au lieu d’utiliser le délai d’attente TCP système par défaut. Ce délai d’attente s’applique à la fois à l;établissement de la connexion et à l’exécution de la poignée de main du protocole SSH et de l’échange de clés.
ControlMaster
Active le partage de plusieurs sessions sur une seule connexion réseau. Lorsqu’il est défini sur yes, ssh(1) écoutera les connexions sur une socket de contrôle spécifiée à l’aide de l’argument ControlPath. Des sessions supplémentaires peuvent se connecter à cette socket en utilisant le même ControlPath avec ControlMaster défini sur no (la valeur par défaut). Ces sessions tenteront de réutiliser la connexion réseau de l’instance principale au lieu d’en initier de nouvelles, mais se rabattront sur une connexion normale si la socket de contrôle n’existe pas, ou n’est pas en mode écoute.

Le définir sur ask provoquera l’écoute par ssh(1) des connexions de contrôle, mais exigera une confirmation via ssh-askpass(1). Si ControlPath ne peut pas être ouvert, ssh(1) continuera sans se connecter à une instance principale.

Le transfert X11 et ssh-agent(1) est pris en charge sur ces connexions multiplexées, cependant l’affichage et l’agent transférés seront ceux appartenant à la connexion principale, c’est-à-dire qu’il n’est pas possible de transférer plusieurs affichages ou agents.

Deux options supplémentaires permettent le multiplexage opportuniste : essayer d’utiliser une connexion principale mais se rabattre sur la création d’une nouvelle si aucune n’existe déjà. Ces options sont : auto et autoask. La dernière option exige une confirmation comme l’option ask.

ControlPath
Spécifie le chemin d’accès à la socket de contrôle utilisée pour le partage de connexion comme décrit dans la section ControlMaster ci-dessus ou la chaîne none pour désactiver le partage de connexion. Les arguments de ControlPath peuvent utiliser la syntaxe tilde pour faire référence au répertoire personnel d’un utilisateur, les jetons décrits dans la section TOKENS et les variables d’environnement comme décrit dans la section VARIABLES D’ENVIRONNEMENT. Il est recommandé que tout ControlPath utilisé pour le partage de connexion opportuniste inclue au moins %h, %p et %r (ou alternativement %C) et soit placé dans un répertoire qui ne soit pas accessible en écriture par d’autres utilisateurs. Cela garantit que les connexions partagées sont unique ment identifiées.
ControlPersist
Lorsqu’il est utilisé en conjonction avec ControlMaster, spécifie que la connexion principale doit rester ouverte en arrière-plan (en attendant les futures connexions client) après la fermeture de la connexion client initiale. S’il est défini sur no (la valeur par défaut), alors la connexion principale ne sera pas mise en arrière-plan et se fermera dès que la connexion client initiale sera fermée. S’il est défini sur yes ou 0, alors la connexion principale restera ouverte en arrière-plan indéfiniment (jusqu’à ce qu’elle soit arrêtée ou fermée via un mécanisme tel que "ssh -O exit"). S’il est défini sur un temps en secondes, ou un temps dans l’un des formats documentés dans sshd_config(5), alors la connexion principale en arrière-plan se terminera automatiquement après qu’elle soit restée inactive (sans connexion client) pendant le temps spécifié.
DynamicForward
Spécifie qu’un port TCP sur la machine locale doit être transféré via le canal sécurisé, et que le protocole de l’application est ensuite utilisé pour déterminer où se connecter depuis la machine distante.

L’argument doit être [bind_address:]port. Les adresses IPv6 peuvent être spécifiées en entourant les adresses de crochets. Par défaut, le port local est lié conformément au paramètre GatewayPorts. Cependant, une bind_address explicite peut être utilisée pour lier la connexion à une adresse spécifique. La bind_address de localhost indique que le port d’écoute doit être lié pour un usage local uniquement, tandis qu’une adresse vide ou ‘*’ indique que le port doit être disponible depuis toutes les interfaces.

Actuellement, les protocoles SOCKS4 et SOCKS5 sont pris en charge, et ssh(1) agira comme un serveur SOCKS. Plusieurs transferts peuvent être spécifiés, et des transferts supplémentaires peuvent être donnés sur la ligne de commande. Seul le superutilisateur peut transférer des ports privilégiés.

EnableEscapeCommandline
Active l’option de ligne de commande dans le menu EscapeChar pour les sessions interactives (par défaut ‘~C’). Par défaut, la ligne de commande est désactivée.
EnableSSHKeysign
Le définir sur yes dans le fichier de configuration client global /etc/ssh/ssh_config permet l’utilisation du programme auxiliaire ssh-keysign(8) lors de HostbasedAuthentication. L’argument doit être yes ou no (la valeur par défaut). Cette option doit être placée dans la section non spécifique à l’hôte. Voir ssh-keysign(8) pour plus d’informations.
EscapeChar
Définit le caractère d’évasion (par défaut: ‘~’). Le caractère d’évasion peut également être défini sur la ligne de commande. L’argument doit être un caractère unique, ‘^’ suivi d’une lettre, ou none pour désactiver entièrement le caractère d’évasion (rendant la connexion transparente pour les données binaires).
ExitOnForwardFailure
Spécifie si ssh(1) doit terminer la connexion s’il ne parvient pas à mettre en place tous les transferts de ports dynamiques, tunnel, locaux et distants demandés, (par exemple, si l’une des parties ne parvient pas à lier et écouter sur un port spécifié). Notez que ExitOnForwardFailure ne s’applique pas aux connexions établies via des transferts de ports et ne le fera pas,pour exemple, cause ssh(1) à quitter si les connexions TCP à la destination finale du transfert échouent. L'argument doit être yes ou no (par défaut).
FingerprintHash
Spécifie l'algorithme de hachage utilisé lors de l'affichage des empreintes de clés. Les options valides sont : md5 et sha256 (par défaut).
ForkAfterAuthentication
Demande à ssh de passer en arrière-plan juste avant l'exécution de la commande. Ceci est utile si ssh doit demander des mots de passe ou des phrases secrètes, mais que l'utilisateur veut qu'il soit en arrière-plan. Ceci implique que l'option de configuration StdinNull est réglée sur « yes ». La méthode recommandée pour lancer des programmes X11 sur un site distant est d'utiliser quelque chose comme ssh -f host xterm, ce qui est identique à ssh host xterm si l'option de configuration ForkAfterAuthentication est réglée sur « yes ».

Si l'option de configuration ExitOnForwardFailure est réglée sur « yes », alors un client lancé avec l'option de configuration ForkAfterAuthentication réglée sur « yes » attendra que tous les transferts de ports distants soient établis avec succès avant de se placer en arrière-plan. L'argument de cette option doit être yes (identique à l'option -f) ou no (par défaut).

ForwardAgent
Spécifie si la connexion à l'agent d'authentification (le cas échéant) sera transférée à la machine distante. L'argument peut être yes, no (par défaut), un chemin explicite vers un socket d'agent ou le nom d'une variable d'environnement (commençant par « $ ») dans laquelle trouver le chemin.

Le transfert d'agent doit être activé avec prudence. Les utilisateurs ayant la capacité de contourner les permissions de fichiers sur l'hôte distant (pour le socket de domaine Unix de l'agent) peuvent accéder à l'agent local via la connexion transférée. Un attaquant ne peut pas obtenir de matériel de clé de l'agent, cependant, il peut effectuer des opérations sur les clés qui lui permettent de s'authentifier en utilisant les identités chargées dans l'agent.

ForwardX11
Spécifie si les connexions X11 seront automatiquement redirigées sur le canal sécurisé et si DISPLAY sera défini. L'argument doit être yes ou no (par défaut).
ForwardX11Timeout
Spécifie un délai d'expiration pour le transfert X11 non fiable en utilisant le format décrit dans la section FORMATS DE TEMPS de sshd_config(5). Les connexions X11 reçues par ssh(1) après cette heure seront refusées. Définir ForwardX11Timeout à zéro désactivera le délai d'expiration et autorisera le transfert X11 pendant toute la durée de la connexion. Par défaut, le transfert X11 non fiable est désactivé après vingt minutes.
ForwardX11Trusted
Si cette option est réglée sur yes, les clients X11 distants auront un accès complet à l'affichage X11 d'origine.

Si cette option est réglée sur no (par défaut), les clients X11 distants seront considérés comme non fiables et empêchés de voler ou de falsifier des données appartenant à des clients X11 fiables. De plus, le jeton xauth(1) utilisé pour la session expirera après 20 minutes. Les clients distants seront refusés après ce délai.

Consultez la spécification de l'extension X11 SECURITY pour connaître les détails complets des restrictions imposées aux clients non fiables.

GatewayPorts
Spécifie si les hôtes distants sont autorisés à se connecter aux ports transférés locaux. Par défaut, ssh(1) lie les transferts de ports locaux à l'adresse de boucle locale. Cela empêche d'autres hôtes distants de se connecter aux ports transférés. GatewayPorts peut être utilisé pour spécifier que ssh doit lier les transferts de ports locaux à l'adresse générique, permettant ainsi aux hôtes distants de se connecter aux ports transférés. L'argument doit être yes ou no (par défaut).
GlobalKnownHostsFile
Spécifie un ou plusieurs fichiers à utiliser pour la base de données globale des clés d'hôte, séparés par des espaces. Par défaut, /etc/ssh/ssh_known_hosts, /etc/ssh/ssh_known_hosts2.
GSSAPIAuthentication
Spécifie si l'authentification utilisateur basée sur GSSAPI est autorisée. Par défaut, no.
GSSAPIDelegateCredentials
Transfère (délègue) les identifiants au serveur. Par défaut, no.
HashKnownHosts
Indique que ssh(1) doit hacher les noms d'hôtes et les adresses lorsqu'ils sont ajoutés à ~/.ssh/known_hosts. Ces noms hachés peuvent être utilisés normalement par ssh(1) et sshd(8), mais ils ne révèlent pas d'informations identifiables visuellement si le contenu du fichier est divulgué. Par défaut, no. Notez que les noms et adresses existants dans les fichiers known_hosts ne seront pas convertis automatiquement, mais peuvent être hachés manuellement à l'aide de ssh-keygen(1).

HostKeyAlias
Spécifie un alias qui doit être utilisé à la place du nom d'hôte réel lors de la recherche ou de la sauvegarde de la clé d'hôte dans les fichiers de la base de données des clés d'hôte et lors de la validation des certificats d'hôte. Cette option est utile pour le tunneling des connexions SSH ou pour plusieurs serveurs fonctionnant sur un seul hôte.
Hostname
Spécifie le nom d'hôte réel sur lequel se connecter. Ceci peut être utilisé pour spécifier des surnoms ou des abréviations pour les hôtes. Les arguments pour Hostname accept les jetons décrits dans la section TOKENS. Les adresses IP numériques sont également autorisées (aussi bien en ligne de commande que dans les spécifications Hostname). La valeur par défaut est le nom donné en ligne de commande.
IdentitiesOnly
Spécifie que ssh(1) doit uniquement utiliser les fichiers d'identité et de certificat d'authentification configurés (soit les fichiers par défaut, soit ceux explicitement configurés dans les fichiers ssh_config ou passés en ligne de commande ssh(1)), même si ssh-agent(1) ou un PKCS11Provider ou SecurityKeyProvider offre plus d'identités. L'argument de ce mot-clé doit être yes ou no (la valeur par défaut). Cette option est destinée aux situations où ssh-agent propose de nombreuses identités différentes.
IdentityAgent
Spécifie le socket de domaine UNIX utilisé pour communiquer avec l'agent d'authentification.

Cette option remplace la variable d'environnement SSH_AUTH_SOCK et peut être utilisée pour sélectionner un agent spécifique. Définir le nom du socket sur none désactive l'utilisation d'un agent d'authentification. Si la chaîne de caractères "SSH_AUTH_SOCK" est spécifiée, l'emplacement du socket sera lu à partir de la variable d'environnement SSH_AUTH_SOCK. Sinon, si la valeur spécifiée commence par un caractère ‘$’, elle sera traitée comme une variable d'environnement contenant l'emplacement du socket.

Les arguments de IdentityAgent peuvent utiliser la syntaxe tilde pour faire référence au répertoire personnel de l'utilisateur, aux jetons décrits dans la section TOKENS et aux variables d'environnement telles que décrites dans la section ENVIRONMENT VARIABLES.

IdentityFile
Spécifie un fichier à partir duquel l'identité d'authentification ECDSA, ECDSA hébergée par un authentificateur, Ed25519, Ed25519 hébergée par un authentificateur ou RSA de l'utilisateur est lue. Vous pouvez également spécifier un fichier de clé publique pour utiliser la clé privée correspondante qui est chargée dans ssh-agent(1) lorsque le fichier de clé privée n'est pas présent localement. La valeur par défaut est ~/.ssh/id_rsa, ~/.ssh/id_ecdsa, ~/.ssh/id_ecdsa_sk, ~/.ssh/id_ed25519 et ~/.ssh/id_ed25519_sk. De plus, toutes les identités représentées par l'agent d'authentification seront utilisées pour l'authentification, sauf si IdentitiesOnly est activé. Si aucun certificat n'a été explicitement spécifié par CertificateFile, ssh(1) tentera de charger les informations du certificat à partir du nom de fichier obtenu en ajoutant -cert.pub au chemin d'un IdentityFile spécifié.

Les arguments de IdentityFile peuvent utiliser la syntaxe tilde pour faire référence au répertoire personnel de l'utilisateur ou aux jetons décrits dans la section TOKENS. Alternativement, un argument de none peut être utilisé pour indiquer qu'aucun fichier d'identité ne doit être chargé.

Il est possible d'avoir plusieurs fichiers d'identité spécifiés dans les fichiers de configuration ; toutes ces identités seront essayées en séquence. Les directives IdentityFile multiples s'ajouteront à la liste des identités essayées (ce comportement diffère de celui des autres directives de configuration).

IdentityFile peut être utilisé en conjonction avec IdentitiesOnly pour sélectionner les identités d'un agent qui sont proposées lors de l'authentification. IdentityFile peut également être utilisé en conjonction avec CertificateFile afin de fournir tout certificat nécessaire à l'authentification avec l'identité.

IgnoreUnknown
Spécifie une liste de motifs d'options inconnues à ignorer si elles sont rencontrées lors de l'analyse de la configuration. Cela peut être utilisé pour supprimer les erreurs si ssh_config contient des options non reconnues par ssh(1). Il est recommandé que IgnoreUnknown soit listé tôt dans le fichier de configuration car il ne sera pas appliqué aux options inconnues qui apparaissent avant lui.
Include
Inclut les fichiers de configuration spécifiés. Plusieurs chemins peuvent être spécifiés et chaque chemin peut contenir des caractères génériques glob(7), des jetons tels que décrits dans la section TOKENS, des variables d'environnement telles que décrites dans la section ENVIRONMENT VARIABLES et, pour les configurations utilisateur, des références de type shell ‘~’ aux répertoires personnels des utilisateurs. Les caractères génériques seront développés et traités par ordre lexical. Les fichiers sans chemins absolus sont supposés être dans ~/.ssh s'ils sont inclus dans un fichier de configuration utilisateur ou dans /etc/ssh s'ils sont inclus à partir du fichier de configuration système. Les directives Include peuvent apparaître à l'intérieur d'un bloc Match ou Host pour effectuer une inclusion conditionnelle.
IPQoS
Spécifie la valeur Differentiated Services Field Codepoint (DSCP) pour les connexions. Les valeurs acceptées sont af11, af12, af13, af21, af22, af23, af31, af32, af33, af41, af42, af43, cs0, cs1, cs2, cs3, cs4, cs5, cs6, cs7, ef, le, une valeur numérique, ou none pour utiliser la valeur par défaut du système d'exploitation. Cette option peut prendre un ou deux arguments, séparés par des espaces. Si un argument est spécifié, il est utilisé comme classe de paquet inconditionnellement. Si deux valeurs sont spécifiées, la première est automatiquement sélectionnée pour les sessions interactives et la seconde pour les sessions non interactives. La valeur par défaut est ef (Expedited Forwarding) pour les sessions interactives et none (la valeur par défaut du système d'exploitation) pour les sessions non interactives.
KbdInteractiveAuthentication
Spécifie si l'authentification clavier-interactive doit être utilisée. L'argument de ce mot-clé doit être yes (la valeur par défaut) ou no. ChallengeResponseAuthentication est un alias déprécié pour celui-ci.
KbdInteractiveDevices
Spécifie la liste des méthodes à utiliser dans l'authentification clavier-interactive. Les noms de méthodes multiples doivent être séparés par des virgules. La valeur par défaut est d'utiliser la liste spécifiée par le serveur. Les méthodes disponibles varient en fonction de ce que le serveur prend en charge. Pour un serveur OpenSSH, il peut s'agir de zéro ou plusieurs des méthodes suivantes : bsdauth et pam.

Spécifie les algorithmes KEX (Key Exchange) autorisés qui seront utilisés et leur ordre de préférence. L'algorithme sélectionné sera le premier algorithme de cette liste que le serveur supporte également. Les algorithmes multiples doivent être séparés par des virgules.

Si la liste spécifiée commence par un caractère ‘-’, les algorithmes spécifiés (y compris les caractères génériques) seront supprimés de l'ensemble par défaut au lieu de le remplacer. Si la liste spécifiée commence par un caractère ‘^’, les algorithmes spécifiés seront placés en tête de l'ensemble par défaut.

La valeur par défaut est :

diffie-hellman-group18-sha512,
diffie-hellman-group14-sha256

La liste des algorithmes d'échange de clés pris en charge peut également être obtenue en utilisant "ssh -Q kex".

KnownHostsCommand
Spécifie une commande à utiliser pour obtenir une liste de clés d'hôte, en plus de celles listées dans UserKnownHostsFile et GlobalKnownHostsFile. Cette commande est exécutée après la lecture des fichiers. Elle peut écrire des lignes de clé d'hôte sur la sortie standard dans un format identique aux fichiers habituels (décrit dans la section VERIFYING HOST KEYS de ssh(1)). Les arguments de KnownHostsCommand acceptent les jetons décrits dans la section TOKENS. La commande peut être invoquée plusieurs fois par connexion : une fois lors de la préparation de la liste de préférence des algorithmes de clé d'hôte à utiliser, une fois à nouveau pour obtenir la clé d'hôte pour le nom d'hôte demandé et, si CheckHostIP est activé, une fois de plus pour obtenir la clé d'hôte correspondant à l'adresse du serveur. Si la commande se termine anormalement ou renvoie un code de sortie non nul, la connexion est terminée.
LocalCommand
Spécifie une commande à exécuter sur la machine locale après s'être connecté avec succès à
le serveur. La chaîne de commande s'étend jusqu'à la fin de la ligne et est exécutée avec le shell de l'utilisateur. Les arguments de LocalCommand acceptent les jetons décrits dans la section JETONS.

La commande est exécutée de manière synchrone et n'a pas accès à la session de ssh(1) qui l'a lancée. Elle ne doit pas être utilisée pour des commandes interactives.

Cette directive est ignorée à moins que PermitLocalCommand n'ait été activé.

LocalForward
Spécifie qu'un port TCP ou une socket de domaine Unix sur la machine locale doit être redirigé via le canal sécurisé vers l'hôte et le port spécifiés (ou la socket de domaine Unix) depuis la machine distante. Pour un port TCP, le premier argument doit être [adresse_liaison:]port ou un chemin de socket de domaine Unix. Le second argument est la destination et peut être hôte:port_hôte ou une socket de domaine Unix si l'hôte distant le prend en charge.

Les adresses IPv6 peuvent être spécifiées en plaçant les adresses entre crochets.

Si l'un des arguments contient un '/' dans sa chaîne, cet argument sera interprété comme une socket de domaine Unix (sur l'hôte correspondant) plutôt qu'un port TCP.

Plusieurs redirections peuvent être spécifiées, et des redirections supplémentaires peuvent être fournies sur la ligne de commande. Seul le superutilisateur peut rediriger des ports privilégiés. Par défaut, le port local est lié conformément au paramètre GatewayPorts. Cependant, une adresse_liaison explicite peut être utilisée pour lier la connexion à une adresse spécifique. L'adresse_liaison de localhost indique que le port d'écoute doit être lié à un usage local uniquement, tandis qu'une adresse vide ou ‘*’ indique que le port doit être disponible depuis toutes les interfaces. Les chemins de socket de domaine Unix peuvent utiliser les jetons décrits dans la section JETONS et les variables d'environnement décrites dans la section VARIABLES D'ENVIRONNEMENT.

LogLevel
Définit le niveau de verbosité utilisé lors de l'enregistrement des messages de ssh(1). Les valeurs possibles sont : QUIET, FATAL, ERROR, INFO, VERBOSE, DEBUG, DEBUG1, DEBUG2 et DEBUG3. La valeur par défaut est INFO. DEBUG et DEBUG1 sont équivalents. DEBUG2 et DEBUG3 spécifient chacun des niveaux de sortie plus détaillés.
LogVerbose
Spécifie un ou plusieurs remplacements pour LogLevel. Un remplacement consiste en une ou plusieurs listes de motifs qui correspondent au fichier source, à la fonction et au numéro de ligne pour forcer une journalisation détaillée. Par exemple, un motif de remplacement de : 
kex.c:*:1000,*:kex_exchange_identification():*,packet.c:*

activerait une journalisation détaillée pour la ligne 1000 de kex.c, tout dans la fonction kex_exchange_identification(), et tout le code du fichier packet.c. Cette option est destinée au débogage et aucun remplacement n'est activé par défaut.

MACs
Spécifie les algorithmes MAC (code d'authentification de message) par ordre de préférence. L'algorithme MAC est utilisé pour la protection de l'intégrité des données. Les algorithmes multiples doivent être séparés par des virgules. Si la liste spécifiée commence par un caractère ‘+’, alors les algorithmes spécifiés seront ajoutés à l'ensemble par défaut au lieu de les remplacer. Si la liste spécifiée commence par un caractère ‘-’, alors les algorithmes spécifiés (y compris les généralités) seront supprimés de l'ensemble par défaut au lieu de les remplacer. Si la liste spécifiée commence par un caractère ‘^’, alors les algorithmes spécifiés seront placés en tête de l'ensemble par défaut.

Les algorithmes qui contiennent "-etm" calculent le MAC après le chiffrement (encrypt-then-mac). Ceux-ci sont considérés comme plus sûrs et leur utilisation est recommandée.

La valeur par défaut est :

umac-64-etm@openssh.com,umac-128-etm@openssh.com,
hmac-sha2-256-etm@openssh.com,hmac-sha2-512-etm@openssh.com,
hmac-sha1-etm@openssh.com,
umac-64@openssh.com,umac-128@openssh.com,
hmac-sha2-256,hmac-sha2-512,hmac-sha1

La liste des algorithmes MAC disponibles peut également être obtenue en utilisant "ssh -Q mac".

NoHostAuthenticationForLocalhost
Désactive l'authentification de l'hôte pour localhost (adresses de bouclage). L'argument de ce mot-clé doit être yes ou no (la valeur par défaut).
NumberOfPasswordPrompts
Spécifie le nombre d'invites de mot de passe avant d'abandonner. L'argument de ce mot-clé doit être un entier. La valeur par défaut est 3.
ObscureKeystrokeTiming
Spécifie si ssh(1) doit essayer d'obscurcir les temporisations inter-frappes de clavier des observateurs passifs du trafic réseau. Si activé, alors pour les sessions interactives, ssh(1) enverra les frappes au clavier à des intervalles fixes de quelques dizaines de millisecondes et enverra des paquets de frappes factices pendant un certain temps après la fin de la frappe. L'argument de ce mot-clé doit être yes, no ou un spécificateur d'intervalle de la forme interval:millisecondes (par exemple, interval:80 pour 80 millisecondes). La valeur par défaut est d'obscurcir les frappes en utilisant un intervalle de paquet de 20 ms. Notez que des intervalles plus petits entraîneront des taux de paquets de frappes factices plus élevés.
PasswordAuthentication
Spécifie si l'authentification par mot de passe doit être utilisée. L'argument de ce mot-clé doit être yes (la valeur par défaut) ou no.
PermitLocalCommand
Autorise l'exécution de commandes locales via l'option LocalCommand ou en utilisant la séquence d'échappement !commande dans ssh(1). L'argument doit être yes ou no (la valeur par défaut).
PermitRemoteOpen
Spécifie les destinations vers lesquelles la redirection de port TCP à distance est autorisée lorsque RemoteForward est utilisé comme proxy SOCKS. La spécification de redirection doit être l'une des formes suivantes :
  • PermitRemoteOpen hôte:port
  • PermitRemoteOpen addr_IPv4:port
  • PermitRemoteOpen [addr_IPv6]:port

Plusieurs redirections peuvent être spécifiées en les séparant par des espaces. Un argument de any peut être utilisé pour supprimer toutes les restrictions et autoriser toute demande de redirection. Un argument de none peut être utilisé pour interdire toutes les demandes de redirection. Le caractère générique ‘*’ peut être utilisé pour l'hôte ou le port afin d'autoriser respectivement tous les hôtes ou tous les ports. Sinon, aucun filtrage de motifs ou aucune résolution d'adresses ne sont effectués sur les noms fournis.

PKCS11Provider
Spécifie quel fournisseur PKCS#11 utiliser ou none pour indiquer qu'aucun fournisseur ne doit être utilisé (la valeur par défaut). L'argument de ce mot-clé est un chemin vers la bibliothèque partagée PKCS#11 que ssh(1) doit utiliser pour communiquer avec un jeton PKCS#11 fournissant des clés pour l'authentification utilisateur.
Port
Spécifie le numéro de port pour se connecter sur l'hôte distant. La valeur par défaut est 22.
PreferredAuthentications
Spécifie l'ordre dans lequel le client doit essayer les méthodes d'authentification. Cela permet à un client de préférer une méthode (par exemple, keyboard-interactive) à une autre méthode (par exemple, password). La valeur par défaut est : 
gssapi-with-mic,hostbased,publickey,
keyboard-interactive,password
ProxyCommand
Spécifie la commande à utiliser pour se connecter au serveur. La chaîne de commande s'étend jusqu'à la fin de la ligne et est exécutée en utilisant la directive ‘exec’ du shell de l'utilisateur afin d'éviter un processus shell persistant.

Les arguments de ProxyCommand acceptent les jetons décrits dans la section JETONS. La commande peut être pratiquement n'importe quoi et doit lire depuis son entrée standard et écrire vers sa sortie standard. Elle doit éventuellement se connecter à un serveur sshd(8) en cours d'exécution sur une machine quelconque, ou exécuter sshd -i quelque part. La gestion des clés d'hôte se fera en utilisant le Hostname de l'hôte auquel on se connecte (par défaut, le nom tapé par l'utilisateur). Définir la commande à none désactive complètement cette option. Notez que CheckHostIP n'est pas disponible pour les connexions avec une commande proxy.

Cette directive est utile en conjonction avec nc(1) et sa prise en charge de proxy. Par exemple, la directive suivante se connecterait via un proxy HTTP à 192.0.2.0 :

ProxyCommand /usr/bin/nc -X connect -x 192.0.2.0:8080 %h %p
ProxyJump

Définir l'hôte sur none désactive complètement cette option.

Notez que cette option entrera en concurrence avec l'option ProxyCommand - celle qui est spécifiée en premier empêchera les instances ultérieures de l'autre de prendre effet.

Notez également que la configuration pour l'hôte de destination (fournie via la ligne de commande ou le fichier de configuration) n'est généralement pas appliquée aux hôtes de saut. ~/.ssh/config doit être utilisé si une configuration spécifique est requise pour les hôtes de saut.

rsa-sha2-512,rsa-sha2-256

La liste des algorithmes de signature disponibles peut également être obtenue en utilisant "ssh -Q PubkeyAcceptedAlgorithms".

PubkeyAuthentication
Spécifie s'il faut essayer l'authentification par clé publique. L'argument de ce mot-clé doit être yes (la valeur par défaut), no, unbound ou host-bound. Les deux dernières options activent l'authentification par clé publique tout en désactivant ou en activant respectivement l'extension de protocole d'authentification liée à l'hôte d'OpenSSH requise pour le transfert sécurisé ssh-agent(1) restreint.
RefuseConnection
Permet de refuser une connexion via le fichier de configuration. Si cette option est spécifiée, alors ssh(1) se terminera immédiatement avant de tenter de se connecter à l'hôte distant, affichera un message d'erreur contenant l'argument de ce mot-clé et retournera un statut de sortie non nul. Cette option peut être utile pour exprimer des rappels ou des avertissements à l'utilisateur via ssh_config.
RekeyLimit
Spécifie la quantité maximale de données qui peuvent être transmises ou reçues avant que la clé de session ne soit renégociée, suivie éventuellement d'une durée maximale qui peut s'écouler avant que la clé de session ne soit renégociée. Le premier argument est spécifié en octets et peut avoir un suffixe de ‘K’, ‘M’, ou ‘G’ pour indiquer les Kilooctets, les Mégaoctets ou les Gigaoctets, respectivement. La valeur par défaut est comprise entre ‘1G’ et ‘4G’, en fonction du chiffrement. Le second argument optionnel est spécifié en secondes et peut utiliser l'une des unités documentées dans la section FORMAT DE TEMPS de sshd_config(5). La valeur par défaut de RekeyLimit est default none, ce qui signifie que le rekeying est effectué après l'envoi ou la réception de la quantité de données par défaut du chiffrement et qu'aucun rekeying basé sur le temps n'est effectué.
RemoteCommand
Spécifie une commande à exécuter sur la machine distante après une connexion réussie au serveur. La chaîne de commande s'étend jusqu'à la fin de la ligne et est exécutée avec le shell de l'utilisateur. Les arguments de RemoteCommand acceptent les jetons décrits dans la section JETONS.
RemoteForward
Spécifie qu'un port TCP ou un socket de domaine Unix sur la machine distante doit être transféré via le canal sécurisé. Le port distant peut être transféré vers un hôte et un port spécifiés ou un socket de domaine Unix depuis la machine locale, ou peut agir comme un proxy SOCKS 4/5 qui permet à un client distant de se connecter à des destinations arbitraires depuis la machine locale. Le premier argument est la spécification d'écoute et peut être [adresse_liaison:]port ou, si l'hôte distant le prend en charge, un chemin de socket de domaine Unix. Si le transfert vers une destination spécifique, alors le second argument doit être hôte:port_hôte ou un socket de domaine Unix, sinon si aucun argument de destination n'est spécifié, le transfert distant sera établi comme un proxy SOCKS. En agissant comme un proxy SOCKS, la destination de la connexion peut être restreinte par PermitRemoteOpen.

Les adresses IPv6 peuvent être spécifiées en plaçant les adresses entre crochets.

Si l'un des arguments contient un '/' , cet argument sera interprété comme un socket de domaine Unix (sur l'hôte correspondant) plutôt qu'un port TCP.

Plusieurs transferts peuvent être spécifiés, et des transferts supplémentaires peuvent être donnés sur la ligne de commande. Les ports privilégiés ne peuvent être transférés que lors de la connexion en tant que root sur la machine distante. Les chemins de socket de domaine Unix peuvent utiliser les jetons décrits dans la section JETONS et les variables d'environnement telles que décrites dans la section VARIABLES D'ENVIRONNEMENT.

Si l'argument port est 0, le port d'écoute sera alloué dynamiquement sur le serveur et rapporté au client au moment de l'exécution.

Si l'adresse_liaison n'est pas spécifiée, la valeur par défaut est de ne se lier qu'aux adresses de bouclage. Si l'adresse_liaison est ‘*’ ou une chaîne vide, alors le transfert est demandé pour écouter sur toutes les interfaces. La spécification d'une adresse_liaison distante ne réussira que si l'option GatewayPorts du serveur est activée (voir sshd_config(5)).

RequestTTY
Spécifie s'il faut demander un pseudo-tty pour la session. L'argument peut être l'un des suivants : no (ne jamais demander de TTY), yes (toujours demander un TTY lorsque l'entrée standard est un TTY), force (toujours demander un TTY) ou auto (demander un TTY lors de l'ouverture d'une session de connexion). Cette option reflète les drapeaux -t et -T pour ssh(1).
RequiredRSASize
Spécifie la taille minimale de la clé RSA (en bits) que ssh(1) acceptera. Les clés d'authentification utilisateur plus petites que cette limite seront ignorées. Les serveurs qui présentent des clés d'hôte plus petites que cette limite entraîneront la terminaison de la connexion. La valeur par défaut est 1024 bits. Notez que cette limite ne peut être augmentée par rapport à la valeur par défaut.
RevokedHostKeys
Spécifie les clés d'hôte publiques révoquées. Les clés listées dans ce fichier seront refusées pour l'authentification de l'hôte. Notez que si ce fichier n'existe pas ou n'est pas lisible, alors l'authentification de l'hôte sera refusée pour tous les hôtes. Les clés peuvent être spécifiées sous forme de fichier texte, listant une clé publique par ligne, ou sous forme de liste de révocation de clés OpenSSH (KRL) comme générée par ssh-keygen(1). Pour plus d'informations sur les KRL, consultez la section LISTES DE RÉVOCATION DE CLÉS dans ssh-keygen(1). Les arguments de RevokedHostKeys peuvent utiliser la syntaxe tilde pour faire référence au répertoire personnel d'un utilisateur, les jetons décrits dans la section JETONS et les variables d'environnement telles que décrites dans la section VARIABLES D'ENVIRONNEMENT.
SecurityKeyProvider
Spécifie un chemin vers une bibliothèque qui sera utilisée lors du chargement de toutes les clés hébergées par un authentificateur FIDO, remplaçant la valeur par défaut qui consiste à utiliser le support USB HID intégré.

Si la valeur spécifiée commence par un caractère ‘$’, elle sera traitée comme une variable d'environnement contenant le chemin vers la bibliothèque.

SendEnv
Spécifie quelles variables de l'environ(7) locale doivent être envoyées au serveur. Le serveur doit également le prendre en charge et le serveur doit être configuré pour accepter ces variables d'environnement. Notez que la variable d'environnement TERM est toujours envoyée chaque fois qu'un pseudo-termin
al est demandé car il est requis par le protocole. Voir AcceptEnv dans sshd_config(5) pour savoir comment configurer le serveur. Les variables sont spécifiées par leur nom, qui peut contenir des caractères génériques. Plusieurs variables d'environnement peuvent être séparées par des espaces ou réparties sur plusieurs directives SendEnv.

Voir PATTERNS pour plus d'informations sur les motifs.

Il est possible de supprimer les noms de variables SendEnv précédemment définis en préfixant les motifs par -. Par défaut, aucune variable d'environnement n'est envoyée.

ServerAliveCountMax
Définit le nombre de messages "server alive" (voir ci-dessous) qui peuvent être envoyés sans que ssh(1) ne reçoive de réponse du serveur. Si ce seuil est atteint pendant l'envoi des messages "server alive", ssh se déconnectera du serveur, terminant la session. Il est important de noter que l'utilisation des messages "server alive" est très différente de TCPKeepAlive (ci-dessous). Les messages "server alive" sont envoyés via le canal chiffré et ne peuvent donc pas être usurpés. L'option de keepalive TCP activée par TCPKeepAlive peut être usurpée. Le mécanisme "server alive" est précieux lorsque le client ou le serveur dépendent de la connaissance du caractère non réactif d'une connexion.

La valeur par défaut est 3. Si, par exemple, ServerAliveInterval (voir ci-dessous) est défini sur 15 et ServerAliveCountMax est laissé à sa valeur par défaut, si le serveur devient non réactif, ssh se déconnectera après environ 45 secondes.

ServerAliveInterval
Définit un intervalle de temps en secondes après lequel, si aucune donnée n'a été reçue du serveur, ssh(1) enverra un message via le canal chiffré pour demander une réponse du serveur. La valeur par défaut est 0, indiquant que ces messages ne seront pas envoyés au serveur.
SessionType
Peut être utilisé pour demander l'invocation d'un sous-système sur le système distant, ou pour empêcher complètement l'exécution d'une commande distante. Ce dernier est utile pour simplement transférer des ports. L'argument de ce mot-clé doit être none (identique à l'option -N), subsystem (identique à l'option -s) ou default (exécution de shell ou de commande).
SetEnv
Spécifie directement une ou plusieurs variables d'environnement et leur contenu à envoyer au serveur sous la forme "NOM=VALEUR". Similaire à SendEnv, à l'exception de la variable TERM, le serveur doit être prêt à accepter la variable d'environnement.

La "VALEUR" peut utiliser les jetons décrits dans la section TOKENS et les variables d'environnement comme décrit dans la section ENVIRONMENT VARIABLES.

StdinNull
Redirige stdin depuis /dev/null (en fait, empêche la lecture depuis stdin). L'une ou l'autre de ces options ou l'option équivalente -n doit être utilisée lorsque ssh est exécuté en arrière-plan. L'argument de ce mot-clé doit être yes (identique à l'option -n) ou no (la valeur par défaut).
StreamLocalBindMask
Définit le masque de mode de création de fichier octal (umask) utilisé lors de la création d'un fichier socket de domaine Unix pour le transfert de ports local ou distant. Cette option est uniquement utilisée pour le transfert de ports vers un fichier socket de domaine Unix.

La valeur par défaut est 0177, ce qui crée un fichier socket de domaine Unix lisible et accessible en écriture uniquement par le propriétaire. Notez que tous les systèmes d'exploitation ne respectent pas le mode de fichier sur les fichiers socket de domaine Unix.

StreamLocalBindUnlink
Spécifie s'il faut supprimer un fichier socket de domaine Unix existant pour le transfert de ports local ou distant avant d'en créer un nouveau. Si le fichier socket existe déjà et que StreamLocalBindUnlink n'est pas activé, ssh ne pourra pas transférer le port vers le fichier socket de domaine Unix. Cette option est uniquement utilisée pour le transfert de ports vers un fichier socket de domaine Unix.

L'argument doit être yes ou no (la valeur par défaut).

StrictHostKeyChecking
Si ce drapeau est défini sur yes, ssh(1) n'ajoutera jamais automatiquement les clés d'hôte au fichier ~/.ssh/known_hosts, et refusera de se connecter aux hôtes dont la clé d'hôte a changé. Cela offre une protection maximale contre les attaques de type "man-in-the-middle" (MITM), bien que cela puisse être gênant lorsque le fichier /etc/ssh/ssh_known_hosts est mal maintenu ou lorsque des connexions à de nouveaux hôtes sont fréquemment établies. Cette option oblige l'utilisateur à ajouter manuellement tous les nouveaux hôtes.

Si ce drapeau est défini sur accept-new, ssh ajoutera automatiquement les nouvelles clés d'hôte au fichier known_hosts de l'utilisateur, mais ne permettra pas les connexions aux hôtes dont les clés d'hôte ont changé. Si ce drapeau est défini sur no ou off, ssh ajoutera automatiquement les nouvelles clés d'hôte aux fichiers des hôtes connus de l'utilisateur et permettra aux connexions aux hôtes dont les clés d'hôte ont changé de continuer, sous certaines restrictions. Si ce drapeau est défini sur ask (la valeur par défaut), les nouvelles clés d'hôte seront ajoutées aux fichiers des hôtes connus de l'utilisateur uniquement après que l'utilisateur ait confirmé que c'est bien ce qu'il souhaite faire, et ssh refusera de se connecter aux hôtes dont la clé d'hôte a changé. Les clés d'hôte des hôtes connus seront vérifiées automatiquement dans tous les cas.

SyslogFacility
Donne le code de facilité utilisé lors de la journalisation des messages de ssh(1). Les valeurs possibles sont : DAEMON, USER, AUTH, LOCAL0, LOCAL1, LOCAL2, LOCAL3, LOCAL4, LOCAL5, LOCAL6, LOCAL7. La valeur par défaut est USER.
TCPKeepAlive
Spécifie si le système doit envoyer des messages TCP keepalive à l'autre partie. S'ils sont envoyés, la mort de la connexion ou le crash de l'une des machines sera correctement remarqué. Cependant, cela signifie que les connexions mourront si la route est temporairement indisponible, et certaines personnes trouvent cela ennuyeux.

La valeur par défaut est yes (pour envoyer des messages TCP keepalive), et le client remarquera si le réseau tombe en panne ou si l'hôte distant meurt. C'est important dans les scripts, et de nombreux utilisateurs le souhaitent également.

Pour désactiver les messages TCP keepalive, la valeur doit être définie sur no. Voir également ServerAliveInterval pour les keepalives au niveau du protocole.

Tag
Spécifie un nom de balise de configuration qui peut être utilisé ultérieurement par une directive Match pour sélectionner un bloc de configuration.
Tunnel
Demande le transfert du périphérique tun(4) entre le client et le serveur. L'argument doit être yes, point-to-point (couche 3), ethernet (couche 2), ou no (la valeur par défaut). Spécifier yes demande le mode tunnel par défaut, qui est point-to-point.
TunnelDevice
Spécifie les périphériques tun(4) à ouvrir sur le client (local_tun) et le serveur (remote_tun).

L'argument doit être local_tun[:remote_tun]. Les périphériques peuvent être spécifiés par leur identifiant numérique ou par le mot-clé any, qui utilise le prochain périphérique tunnel disponible. Si remote_tun n'est pas spécifié, il est par défaut réglé sur any. La valeur par défaut est any:any.

UpdateHostKeys
Spécifie si ssh(1) doit accepter les notifications de clés d'hôte supplémentaires envoyées par le serveur après la fin de l'authentification et les ajouter à UserKnownHostsFile. L'argument doit être yes, no ou ask. Cette option permet d'apprendre des clés d'hôte alternatives pour un serveur et prend en charge la rotation gracieuse des clés en permettant à un serveur d'envoyer des clés publiques de remplacement avant que les anciennes ne soient supprimées.

Des clés d'hôte supplémentaires ne sont acceptées que si la clé utilisée pour authentifier l'hôte était déjà approuvée ou explicitement acceptée par l'utilisateur, si l'hôte a été authentifié via UserKnownHostsFile (c'est-à-dire pas GlobalKnownHostsFile) et si l'hôte a été authentifié en utilisant une clé simple et non un certificat.

UpdateHostKeys est activé par défaut si l'utilisateur n'a pas outrepassé le réglage par défaut de UserKnownHostsFile et n'a pas activé VerifyHostKeyDNS, sinon UpdateHostKeys sera réglé sur no.

Si UpdateHostKeys est réglé sur ask, alors l'utilisateur est invité à confirmer les modifications apportées au fichier known_hosts. La confirmation est actuellement incompatible avec ControlPersist, et sera désactivée si celle-ci est activée.

Actuellement, seule sshd(8) d'OpenSSH 6.8 et versions ultérieures prend en charge l'extension de protocole "hostkeys@openssh.com" utilisée pour informer le client de toutes les clés d'hôte du serveur.

User
Spécifie l'utilisateur avec lequel se connecter. Ceci peut être utile lorsqu'un nom d'utilisateur différent est utilisé sur différentes machines. Cela évite d'avoir à se souvenir de donner le nom d'utilisateur sur la ligne de commande. Les arguments de User peuvent utiliser les jetons décrits dans la section TOKENS (à l'exception de %r et %C) et les variables d'environnement telles que décrites dans la section VARIABLES D'ENVIRONNEMENT.
UserKnownHostsFile
Spécifie un ou plusieurs fichiers à utiliser pour la base de données des clés d'hôte utilisateur, séparés par des espaces. Chaque nom de fichier peut utiliser la notation tilde pour faire référence au répertoire personnel de l'utilisateur, aux jetons décrits dans la section TOKENS et aux variables d'environnement telles que décrites dans la section VARIABLES D'ENVIRONNEMENT. Une valeur de none amène ssh(1) à ignorer tous les fichiers d'hôtes connus spécifiques à l'utilisateur. La valeur par défaut est ~/.ssh/known_hosts, ~/.ssh/known_hosts2.
VerifyHostKeyDNS
Spécifie si la clé distante doit être vérifiée à l'aide d'enregistrements ressources DNS et SSHFP. Si cette option est définie sur yes, le client fera implicitement confiance aux clés qui correspondent à une empreinte sécurisée provenant du DNS. Les empreintes non sécurisées seront traitées comme si cette option était définie sur ask. Si cette option est définie sur ask, des informations sur la correspondance de l'empreinte seront affichées, mais l'utilisateur devra toujours confirmer les nouvelles clés d'hôte conformément à l'option StrictHostKeyChecking. La valeur par défaut est no.

Voir aussi VERIFICATION DES CLÉS D'HÔTE dans ssh(1).

VersionAddendum
Spécifie éventuellement un texte supplémentaire à ajouter à la bannière du protocole SSH envoyée par le client lors de la connexion. La valeur par défaut est none.
VisualHostKey
Si cette option est définie sur yes, une représentation en art ASCII de l'empreinte de la clé d'hôte distante est imprimée en plus de la chaîne d'empreinte lors de la connexion et pour les clés d'hôte inconnues. Si cette option est définie sur no (la valeur par défaut), aucune chaîne d'empreinte n'est imprimée lors de la connexion et seule la chaîne d'empreinte sera imprimée pour les clés d'hôte inconnues.
WarnWeakCrypto
Contrôle si l'utilisateur est averti lorsque les algorithmes cryptographiques négociés pour la connexion sont faibles ou déconseillés. Les avertissements peuvent être désactivés en désactivant un avertissement spécifique ou en désactivant tous les avertissements. Les avertissements concernant les connexions qui n'utilisent pas un échange de clés post-quantique peuvent être désactivés à l'aide du drapeau no-pq-kex. no désactivera tous les avertissements. La valeur par défaut, équivalente à yes, est d'activer tous les avertissements.
XAuthLocation
Spécifie le chemin d'accès complet du programme xauth(1). La valeur par défaut est /usr/bin/xauth.

MODÈLES

Un modèle se compose de zéro ou plusieurs caractères non blancs, de ‘*’ (un caractère joker qui correspond à zéro ou plusieurs caractères) ou de ‘?’ (un caractère joker qui correspond à exactement un caractère). Par exemple, pour spécifier un ensemble de déclarations pour n'importe quel hôte du domaine ".co.uk", le modèle suivant pourrait être utilisé :

Host *.co.uk

Le modèle suivant correspondra à n'importe quel hôte dans la plage réseau 192.168.0.[0-9] :

Host 192.168.0.?

Une liste de modèles est une liste de modèles séparés par des virgules. Les modèles dans les listes de modèles peuvent être niés en les faisant précéder d'un point d'exclamation (‘!’). Par exemple, pour autoriser l'utilisation d'une clé depuis n'importe où dans une organisation, sauf depuis le pool "dialup", l'entrée suivante (dans authorized_keys) pourrait être utilisée :

from="!*.dialup.example.com,*.example.com"

Notez qu'une correspondance niée ne produira jamais un résultat positif en soi. Par exemple, tenter de faire correspondre "host3" avec la liste de modèles suivante échouera :

from="!host1,!host2"

La solution ici consiste à inclure un terme qui produira une correspondance positive, tel qu'un caractère joker :

from="!host1,!host2,*"

JETONS

Les arguments de certains mots-clés peuvent utiliser des jetons, qui sont développés à l'exécution :

%%
Un ‘%’ littéral.
%C
Hash de %l%h%p%r%j.
%d
Répertoire personnel de l'utilisateur local.
%f
L'empreinte de la clé d'hôte du serveur.
%H
Le nom d'hôte ou l'adresse known_hosts qui est recherché.
%h
Le nom d'hôte distant.
%I
Une chaîne décrivant la raison d'une exécution de KnownHostsCommand : soit ADDRESS lors de la recherche d'un hôte par adresse (uniquement lorsque CheckHostIP est activé), HOSTNAME lors de la recherche par nom d'hôte, ou ORDER lors de la préparation de la liste de préférence des algorithmes de clés d'hôte à utiliser pour l'hôte de destination.
%i
L'identifiant de l'utilisateur local.
%j
Le contenu de l'option ProxyJump, ou la chaîne vide si cette option n'est pas définie.
%K
La clé d'hôte encodée en base64.
%k
L'alias de la clé d'hôte s'il est spécifié, sinon le nom d'hôte distant d'origine donné sur la ligne de commande.
%L
Le nom d'hôte local.
%l
Le nom d'hôte local, y compris le nom de domaine.
%n
Le nom d'hôte distant d'origine, tel que donné sur la ligne de commande.
%p
Le port distant.
%r
Le nom d'utilisateur distant.
%T
L'interface réseau tun(4) ou tap(4) locale assignée si le transfert de tunnel a été demandé, ou "NONE" sinon.
%t
Le type de la clé d'hôte du serveur, par exemple ssh-ed25519.
%u
Le nom d'utilisateur local.

CertificateFile, ControlPath, IdentityAgent, IdentityFile, Include, KnownHostsCommand, LocalForward, Match exec, RemoteCommand, RemoteForward, RevokedHostKeys, UserKnownHostsFile et VersionAddendum acceptent les jetons %%, %C, %d, %h, %i, %j, %k, %L, %l, %n, %p, %r, et %u.

KnownHostsCommand accepte en outre les jetons %f, %H, %I, %K et %t.

Hostname accepte les jetons %% et %h.

LocalCommand accepte tous les jetons.

ProxyCommand et ProxyJump acceptent les jetons %%, %h, %n, %p, et %r.

Notez que certaines de ces directives construisent des commandes à exécuter via le shell. Comme ssh(1) n'effectue aucun filtrage ou échappement des caractères ayant une signification spéciale dans les commandes shell (par exemple, les guillemets), il incombe à l'utilisateur de s'assurer que les arguments passés à ssh(1) ne contiennent pas de tels caractères et que les jetons sont correctement cités lorsqu'ils sont utilisés.

VARIABLES D'ENVIRONNEMENT

Les arguments de certains mots-clés peuvent être développés à l'exécution à partir des variables d'environnement du client en les plaçant entre ${}, par exemple ${HOME}/.ssh ferait référence au répertoire .ssh de l'utilisateur. Si une variable d'environnement spécifiée n'existe pas, une erreur sera renvoyée et le paramètre pour ce mot-clé sera ignoré.

Les mots-clés CertificateFile, ControlPath, IdentityAgent, IdentityFile, Include, KnownHostsCommand, et UserKnownHostsFile prennent en charge les variables d'environnement. Les mots-clés LocalForward et RemoteForward ne prennent en charge les variables d'environnement que pour les chemins de sockets de domaine Unix.
