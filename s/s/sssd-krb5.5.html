NOM

sssd-krb5 - Fournisseur Kerberos SSSD

DESCRIPTION

Cette page de manuel décrit la configuration du backend d'authentification Kerberos 5 pour sssd(8). Pour une référence syntaxique détaillée, veuillez consulter la section « FORMAT DE FICHIER » de la page de manuel de sssd.conf(5).

Le backend d'authentification Kerberos 5 contient des fournisseurs d'authentification (auth) et de changement de mot de passe (chpass). Il doit être associé à un fournisseur d'identité pour fonctionner correctement (par exemple, id_provider = ldap). Certaines informations requises par le backend d'authentification Kerberos 5 doivent être fournies par le fournisseur d'identité, telles que le nom principal Kerberos (UPN) de l'utilisateur. La configuration du fournisseur d'identité doit contenir une entrée pour spécifier l'UPN. Veuillez vous référer à la page de manuel du fournisseur d'identité applicable pour les détails sur la façon de configurer cela.

Ce backend fournit également un contrôle d'accès basé sur le fichier .k5login dans le répertoire personnel de l'utilisateur. Voir k5login(5) pour plus de détails. Veuillez noter qu'un fichier .k5login vide refusera tout accès à cet utilisateur. Pour activer cette fonctionnalité, utilisez 'access_provider = krb5' dans votre configuration SSSD.

Dans le cas où l'UPN n'est pas disponible dans le backend d'identité, sssd construira un UPN en utilisant le format nom_utilisateur@domaine_krb5.

OPTIONS DE CONFIGURATION

Si le module d'authentification krb5 est utilisé dans un domaine SSSD, les options suivantes doivent être utilisées. Voir la page de manuel sssd.conf(5), section « SECTIONS DE DOMAINE », pour les détails sur la configuration d'un domaine SSSD.

krb5_server, krb5_backup_server (chaîne)

Spécifie la liste des adresses IP ou des noms d'hôtes des serveurs Kerberos auxquels SSSD doit se connecter, séparés par des virgules, dans l'ordre de préférence. Pour plus d'informations sur la redondance et le basculement, voir la section « REDONDANCE ». Un numéro de port optionnel (précédé de deux-points) peut être ajouté aux adresses ou aux noms d'hôtes. S'il est vide, la découverte de services est activée ; pour plus d'informations, reportez-vous à la section « DÉCOUVERTE DE SERVICES ».

Lors de l'utilisation de la découverte de services pour les serveurs KDC ou kpasswd, SSSD recherche d'abord les entrées DNS spécifiant _udp comme protocole et se rabat sur _tcp si aucune n'est trouvée.

Cette option s'appelait « krb5_kdcip » dans les versions antérieures de SSSD. Bien que le nom hérité soit reconnu pour le moment, il est conseillé aux utilisateurs de migrer leurs fichiers de configuration pour utiliser « krb5_server » à la place.

krb5_realm (chaîne)

Le nom du domaine Kerberos. Cette option est obligatoire et doit être spécifiée.

krb5_kpasswd, krb5_backup_kpasswd (chaîne)

Si le service de changement de mot de passe ne fonctionne pas sur le KDC, des serveurs alternatifs peuvent être définis ici. Un numéro de port optionnel (précédé de deux-points) peut être ajouté aux adresses ou aux noms d'hôtes.

Pour plus d'informations sur la redondance et le basculement, voir la section « REDONDANCE ». REMARQUE : Même s'il n'y a plus de serveurs kpasswd à essayer, le backend ne passe pas en mode hors ligne si l'authentification auprès du KDC est toujours possible.

Par défaut : Utilise le KDC

krb5_ccachedir (chaîne)

Répertoire pour stocker les caches de crédentials. Toutes les séquences de substitution de krb5_ccname_template peuvent également être utilisées ici, sauf %d et %P. Le répertoire est créé en privé et appartient à l'utilisateur, avec des permissions définies à 0700.

Par défaut : /tmp

krb5_ccname_template (chaîne)

Emplacement du cache de credentials de l'utilisateur. Trois types de caches de credentials sont actuellement pris en charge : « FILE », « DIR » et « KEYRING:persistent ». Le cache peut être spécifié soit comme TYPE:RÉSIDUEL, soit comme un chemin absolu, qui implique le type « FILE ». Dans le modèle, les séquences suivantes sont substituées :

%u

nom de connexion

%U

UID de connexion

%p

nom principal

%r

nom du domaine

%h

répertoire personnel

%d

valeur de krb5_ccachedir

%P

l'ID du processus du client SSSD

%%

un '%' littéral

Si le modèle se termine par 'XXXXXX', mkstemp(3) est utilisé pour créer un nom de fichier unique de manière sécurisée.

Lors de l'utilisation des types KEYRING, le seul mécanisme pris en charge est « KEYRING:persistent:%U », qui utilise le keyring du noyau Linux pour stocker les credentials par UID. C'est également le choix recommandé, car c'est la méthode la plus sûre et la plus prévisible.

La valeur par défaut pour le nom du cache de credentials provient du profil stocké dans la section [libdefaults] du fichier de configuration krb5.conf du système. Le nom de l'option est default_ccache_name. Voir le paragraphe EXPANSION DES PARAMÈTRES de krb5.conf(5) pour des informations supplémentaires sur le format d'expansion défini par krb5.conf.

REMARQUE : Veuillez noter que le modèle d'expansion du cache libkrb5 de krb5.conf(5) utilise des séquences d'expansion différentes de celles de SSSD.

Par défaut : (depuis libkrb5)

krb5_keytab (chaîne)

L'emplacement du fichier keytab à utiliser lors de la validation des credentials obtenus auprès des KDCs.

Par défaut : Fichier keytab système, normalement /etc/krb5.keytab

krb5_store_password_if_offline (booléen)

Stocke le mot de passe de l'utilisateur si le fournisseur est hors ligne et l'utilise pour demander un TGT lorsque le fournisseur revient en ligne.

REMARQUE : cette fonctionnalité n'est disponible que sous Linux. Les mots de passe stockés de cette manière sont conservés en texte clair dans le keyring du noyau et sont potentiellement accessibles par l'utilisateur root (avec difficulté).

Par défaut : faux

krb5_use_fast (chaîne)

Active le tunneling sécurisé d'authentification flexible (FAST) pour la pré-authentification Kerberos. Les options suivantes sont prises en charge :

jamais utiliser FAST. Ceci est équivalent à ne pas définir cette option du tout.

essayer d'utiliser FAST. Si le serveur ne prend pas en charge FAST, continuez l'authentification sans lui.

exiger d'utiliser FAST. L'authentification échoue si le serveur n'exige pas FAST.

Par défaut : non défini, c'est-à-dire que FAST n'est pas utilisé.

REMARQUE : un fichier keytab ou la prise en charge de PKINIT anonyme est requise pour utiliser FAST.

REMARQUE : SSSD ne prend en charge FAST qu'avec la version 1.8 et ultérieures de MIT Kerberos. Si SSSD est utilisé avec une version antérieure de MIT Kerberos, l'utilisation de cette option constitue une erreur de configuration.

krb5_fast_principal (chaîne)

Spécifie le principal du serveur à utiliser pour FAST.

krb5_fast_use_anonymous_pkinit (booléen)

Si défini sur vrai, essaie d'utiliser PKINIT anonyme au lieu d'un fichier keytab pour obtenir le credential requis pour FAST. L'option krb5_fast_principal est ignorée dans ce cas.

Par défaut : faux

krb5_use_kdcinfo (booléen)

Spécifie si SSSD doit indiquer aux bibliothèques Kerberos quel domaine et quels KDCs utiliser. Cette option est activée par défaut. Si vous la désactivez, vous devez configurer la bibliothèque Kerberos à l'aide du fichier de configuration krb5.conf(5).

Voir la page de manuel sssd_krb5_locator_plugin(8) pour plus d'informations sur le plugin de localisation.

Par défaut : vrai

krb5_kdcinfo_lookahead (chaîne)

Lorsque krb5_use_kdcinfo est défini sur vrai, vous pouvez limiter le nombre de serveurs transmis à sssd_krb5_locator_plugin(8). Cela peut être utile lorsqu'un trop grand nombre de serveurs sont découverts à l'aide des enregistrements SRV.

L'option krb5_kdcinfo_lookahead contient deux nombres séparés par deux-points. Le premier nombre représente le nombre de serveurs primaires utilisés et le second nombre spécifie le nombre de serveurs de sauvegarde.

Par exemple, 10:0 signifie que jusqu'à 10 serveurs primaires seront transmis à sssd_krb5_locator_plugin(8) mais aucun serveur de sauvegarde.

Par défaut : 3:1

krb5_use_enterprise_principal (booléen)

Spécifie si le principal utilisateur doit être traité comme une entreprise

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

principal. Voir la section 5 de la RFC 6806 pour plus de détails sur les principaux d'entreprise.

Par défaut : false (fournisseur AD : true)

Le fournisseur IPA réglera l'option sur 'true' s'il détecte que le serveur est capable de gérer les principaux d'entreprise et que l'option n'est pas définie explicitement dans le fichier de configuration.

krb5_use_subdomain_realm (booléen)

Spécifie l'utilisation des royaumes de sous-domaines pour l'authentification des utilisateurs provenant de domaines approuvés. Cette option peut être définie sur 'true' si des principaux d'entreprise sont utilisés avec des upnSuffixes qui ne sont pas connus sur les KDC du domaine parent. Si l'option est définie sur 'true', SSSD tentera d'envoyer la requête directement à un KDC du domaine approuvé dont provient l'utilisateur.

Par défaut : false

krb5_map_user (chaîne de caractères)

La liste des mappages est donnée sous forme de liste séparée par des virgules de paires « nom_utilisateur:principal » où « nom_utilisateur » est un nom d'utilisateur UNIX et « principal » est la partie utilisateur d'un principal kerberos. Ce mappage est utilisé lorsque l'utilisateur s'authentifie en utilisant « auth_provider = krb5 ».

exemple :

krb5_realm = REALM
krb5_map_user = joe:juser,dick:richard

« joe » et « dick » sont des noms d'utilisateur UNIX et « juser » et « richard » sont les principaux des principaux kerberos. Pour l'utilisateur « joe » resp. « dick », SSSD tentera de faire un kinit en tant que « juser@REALM » resp. « richard@REALM ».

Par défaut : non défini

krb5_auth_timeout (entier)

Délai en secondes après lequel une requête d'authentification en ligne ou une requête de changement de mot de passe est abandonnée. Si possible, la requête d'authentification se poursuit hors ligne.

Par défaut : 6

krb5_validate (booléen)

Vérifie à l'aide de krb5_keytab que le TGT obtenu n'a pas été usurpé. Le keytab est vérifié séquentiellement pour les entrées, et la première entrée avec un royaume correspondant est utilisée pour la validation. Si aucune entrée ne correspond au royaume, la dernière entrée du keytab est utilisée. Ce processus peut être utilisé pour valider des environnements utilisant une confiance inter-royaumes en plaçant l'entrée keytab appropriée comme dernière entrée ou comme seule entrée dans le fichier keytab.

Par défaut : false (fournisseur IPA et AD : true)

Veuillez noter que la validation du ticket est la première étape lors de la vérification du PAC (voir 'pac_check' dans la page de manuel sssd.conf(5) pour les détails). Si la validation du ticket est désactivée, les vérifications du PAC seront également ignorées.

krb5_renewable_lifetime (chaîne de caractères)

Demande un ticket renouvelable avec une durée de vie totale, donnée sous forme d'un entier immédiatement suivi d'une unité de temps :

s pour secondes

m pour minutes

h pour heures

d pour jours.

Si aucune unité n'est donnée, s est supposé.

NOTE : Il n'est pas possible de mélanger les unités. Pour définir la durée de vie renouvelable à une heure et demie, utilisez '90m' au lieu de '1h30m'.

Par défaut : non défini, c'est-à-dire que le TGT n'est pas renouvelable

krb5_lifetime (chaîne de caractères)

Demande un ticket avec une durée de vie, donnée sous forme d'un entier immédiatement suivi d'une unité de temps :

s pour secondes

m pour minutes

h pour heures

d pour jours.

Si aucune unité n'est donnée, s est supposé.

NOTE : Il n'est pas possible de mélanger les unités. Pour définir la durée de vie à une heure et demie, utilisez '90m' au lieu de '1h30m'.

Par défaut : non défini, c'est-à-dire la durée de vie par défaut du ticket configurée sur le KDC.

krb5_renew_interval (chaîne de caractères)

Le temps en secondes entre deux vérifications si le TGT doit être renouvelé. Les TGT sont renouvelés si environ la moitié de leur durée de vie est dépassée, donnée sous forme d'un entier immédiatement suivi d'une unité de temps :

s pour secondes

m pour minutes

h pour heures

d pour jours.

Si aucune unité n'est donnée, s est supposé.

NOTE : Il n'est pas possible de mélanger les unités. Pour définir la durée de vie renouvelable à une heure et demie, utilisez '90m' au lieu de '1h30m'.

Si cette option n'est pas définie ou est égale à 0, le renouvellement automatique est désactivé.

Par défaut : non défini

krb5_canonicalize (booléen)

Spécifie si le principal de l'hôte et de l'utilisateur doit être canonisé. Cette fonctionnalité est disponible avec les versions MIT Kerberos 1.7 et ultérieures.

Par défaut : false

FAILOVER

La fonctionnalité de basculement (failover) permet aux backends de basculer automatiquement vers un autre serveur si le serveur actuel échoue.

Syntaxe de basculement

La liste des serveurs est donnée sous forme de liste séparée par des virgules ; un nombre quelconque d'espaces est autorisé autour de la virgule. Les serveurs sont listés dans l'ordre de préférence. La liste peut contenir n'importe quel nombre de serveurs.

Pour chaque option de configuration activée pour le basculement, deux variantes existent : primaire et sauvegarde. L'idée est que les serveurs de la liste primaire sont préférés et que les serveurs de sauvegarde ne sont recherchés que si aucun serveur primaire ne peut être atteint. Si un serveur de sauvegarde est sélectionné, un délai de 31 secondes est défini. Après ce délai, SSSD tentera périodiquement de se reconnecter à l'un des serveurs primaires. En cas de succès, il remplacera le serveur actif actuel (de sauvegarde).

Le mécanisme de basculement

Le mécanisme de basculement distingue une machine d'un service. Le backend tente d'abord de résoudre le nom d'hôte d'une machine donnée ; si cette tentative de résolution échoue, la machine est considérée comme hors ligne. Aucune autre tentative n'est faite pour se connecter à cette machine pour aucun autre service. Si la tentative de résolution réussit, le backend tente de se connecter à un service sur cette machine. Si la tentative de connexion au service échoue, seul ce service particulier est considéré comme hors ligne et le backend bascule automatiquement vers le service suivant. La machine est toujours considérée comme en ligne et peut encore être essayée pour un autre service.

D'autres tentatives de connexion seront effectuées vers les machines ou services marqués comme hors ligne après un délai spécifié ; celui-ci est actuellement codé en dur à 30 secondes.

S'il n'y a plus de machines à essayer, le backend dans son ensemble passe en mode hors ligne, puis tente de se reconnecter toutes les 30 secondes.

Délais de basculement et réglage

La résolution d'un serveur auquel se connecter peut être aussi simple qu'une seule requête DNS ou impliquer plusieurs étapes, comme la recherche du site correct ou l'essai de plusieurs noms d'hôtes au cas où certains des serveurs configurés ne seraient pas joignables. Les scénarios les plus complexes peuvent prendre du temps et SSSD doit trouver un équilibre entre donner suffisamment de temps pour terminer le processus de résolution et, d'autre part, ne pas essayer trop longtemps avant de revenir au mode hors ligne. Si les journaux de débogage SSSD indiquent que la résolution du serveur expire avant qu'un serveur actif ne soit contacté, vous pouvez envisager de modifier les délais.

Cette section liste les paramètres ajustables disponibles. Veuillez vous référer à leur description dans la page de manuel sssd.conf(5).

dns_resolver_server_timeout

Temps en millisecondes qui définit combien de temps SSSD parlera à un serveur DNS unique avant d'essayer le suivant.

Par défaut : 1000

dns_resolver_op_timeout

Temps en secondes pour indiquer combien de temps SSSD essaiera de résoudre une requête DNS unique (par exemple, la résolution d'un nom d'hôte ou d'un enregistrement SRV) avant d'essayer le nom d'hôte suivant ou le domaine de découverte.

Par défaut : 3

dns_resolver_timeout

Combien de temps SSSD essaiera de résoudre un service de basculement. Cette résolution de service peut inclure en interne plusieurs étapes, telles que la résolution de requêtes SRV DNS ou la localisation du site.

Par défaut : 6

Pour les fournisseurs basés sur LDAP, l'opération de résolution est effectuée dans le cadre d'une opération de connexion LDAP. Par conséquent, le délai d'attente « ldap_opt_timeout » doit également être défini sur une valeur supérieure à « dns_resolver_timeout », qui à son tour doit être défini sur une valeur supérieure à « dns_resolver_op_timeout », qui doit être supérieure à « dns_resolver_server_timeout ».

DÉCOUVERTE DE SERVICE

La fonctionnalité de découverte de service permet aux backends de trouver automatiquement les serveurs appropriés à contacter à l'aide d'une requête DNS spéciale. Cette fonctionnalité n'est pas prise en charge pour les serveurs de sauvegarde.

Configuration

Si aucun serveur n'est spécifié, le backend utilise automatiquement la découverte de service pour essayer de trouver un serveur. Facultativement, l'utilisateur peut choisir d'utiliser à la fois des adresses de serveur fixes et la découverte de service en insérant un mot-clé spécial, « _srv_ », dans la liste des serveurs. L'ordre de préférence est maintenu. Cette fonctionnalité est utile si, par exemple, l'utilisateur préfère utiliser la découverte de service chaque fois que possible, et se rabattre sur un serveur spécifique lorsqu'aucun serveur ne peut être découvert via DNS.

Le nom de domaine

Veuillez vous référer au paramètre « dns_discovery_domain » dans la page de manuel sssd.conf(5) pour plus de détails.

Le protocole

Les requêtes spécifient généralement _tcp comme protocole. Les exceptions sont documentées dans la description de l'option respective.

Voir aussi

Pour plus d'informations sur le mécanisme de découverte de service, veuillez vous référer à la RFC 2782.

EXEMPLE

L'exemple suivant suppose que SSSD est correctement configuré et que FOO est l'un des domaines de la section [sssd]. Cet exemple ne montre que la configuration de l'authentification Kerberos ; il n'inclut aucun fournisseur d'identité.

[domain/FOO]
auth_provider = krb5
krb5_server = 192.168.1.1
krb5_realm = EXAMPLE.COM
