NOM

snmpd.examples - exemples de configuration pour l'agent Net-SNMP

DESCRIPTION

La page de manuel snmpd.conf(5) définit la syntaxe et le comportement des diverses directives de configuration qui peuvent être utilisées pour contrôler le fonctionnement de l'agent Net-SNMP, et les informations de gestion qu'il fournit.

Cette page de manuel complémentaire illustre ces directives, montrant des exemples pratiques de leur utilisation.

COMPORTEMENT DE L'AGENT

Adresses d'écoute

Le comportement par défaut de l'agent (écoute sur le port SNMP UDP standard sur toutes les interfaces) est équivalent à la directive :

agentaddress udp:161
ou simplement
agentaddress 161
L'agent peut être configuré pour n'accepter que les requêtes envoyées à l'interface de bouclage locale (en écoutant également sur le port SNMP UDP), en utilisant :
agentaddress localhost:161 # (udp implicite)
ou
agentaddress 127.0.0.1 # (udp et port standard implicites)
Il peut être configuré pour accepter les requêtes UDP et TCP (sur IPv4 et IPv6), en utilisant :
agentaddress udp:161,tcp:161,udp6:161,tcp6:161
D'autres combinaisons sont également valides.

Privilèges d'exécution

L'agent peut être configuré pour renoncer à tout accès privilégié une fois qu'il a ouvert les ports d'écoute initiaux. En présence d'un groupe "snmp" approprié (défini dans /etc/group), cela pourrait être fait en utilisant les directives :

agentuser  nobody
agentgroup snmp
Un effet similaire pourrait être obtenu en utilisant des valeurs UID et/ou GID numériques : 
agentuser  #10
agentgroup #10

Configuration SNMPv3

Plutôt que d'être généré de manière pseudo-aléatoire, l'ID du moteur pour l'agent pourrait être calculé en fonction de l'adresse MAC de la deuxième interface réseau (eth1), en utilisant les directives :

engineIDType 3 engineIDNic eth1
ou il pourrait être calculé à partir de l'adresse IP (la première), en utilisant :
engineIDType 1
ou il pourrait être spécifié explicitement, en utilisant :
engineID "XXX - QUEL FORMAT"

CONTRÔLE D'ACCÈS

Utilisateurs SNMPv3

Les directives suivantes créeront trois utilisateurs, tous utilisant exactement les mêmes paramètres d'authentification et de chiffrement :

createUser me     MD5 "single pass phrase"
createUser myself MD5 "single pass phrase" DES
createUser andI   MD5 "single pass phrase" DES "single pass phrase"
Notez qu'il s'agit de trois utilisateurs distincts, qui pourraient se voir accorder différents niveaux d'accès. Modifier la phrase secrète pour l'un d'eux n'affecterait pas les deux autres.

Des phrases secrètes distinctes peuvent être spécifiées pour l'authentification et le chiffrement :

createUser onering SHA "to rule them all" AES "to bind them"
N'oubliez pas que ces directives createUser doivent être définies dans le fichier /var/net-snmp/snmpd.conf, plutôt qu'à l'emplacement habituel.

Contrôle d'accès traditionnel

Les utilisateurs SNMPv3 définis ci-dessus peuvent se voir accorder l'accès à l'arborescence MIB complète en utilisant les directives :

rouser me
rwuser onering
Ou un accès sélectif à des sous-arborescences individuelles en utilisant : 
rouser myself   .1.3.6.1.2
rwuser andI     system

Notez qu'une combinaison répétant le même utilisateur, telle que :

rouser onering
rwuser onering
ne doit pas être utilisée. Cela configurerait l'utilisateur onering avec un accès en lecture seule (et ignorerait complètement l'entrée rwuser). Il en va de même pour les directives basées sur la communauté.

Les directives :

rocommunity public
rwcommunity private
définiraient les chaînes de communauté en lecture et en écriture couramment attendues pour les requêtes SNMPv1 et SNMPv2c. Ce comportement n'est pas configuré par défaut et devrait être mis en place explicitement.
Note :
Il serait également très judicieux de remplacer private par quelque chose d'un peu moins prévisible !

Une configuration légèrement moins vulnérable pourrait restreindre les informations qui peuvent être récupérées :

rocommunity public default system
ou les systèmes de gestion qui pourraient manipuler les paramètres :
rwcommunity private 10.10.10.0/24
ou une combinaison des deux.

Configuration VACM

Cette dernière paire de paramètres est équivalente aux définitions VACM complètes :

#         sec.name  source        community
com2sec   public    default       public
com2sec   mynet     10.10.10.0/24 private
com2sec6  mynet     fec0::/64     private
#                  sec.model  sec.name
group  worldGroup  v1         public
group  worldGroup  v2c        public
group  myGroup     v1         mynet
group  myGroup     v2c        mynet
#              incl/excl   subtree     [mask]
view   all     included    .1
view   sysView included    system
#              context model level   prefix  read    write  notify (unused)
access  worldGroup  ""  any  noauth  exact   system  none   none
access  myGroup     ""  any  noauth  exact   all     all    none

Il y a plusieurs points à noter dans cet exemple :

Les directives group doivent être répétées pour les requêtes SNMPv1 et SNMPv2c.

Le nom de sécurité com2sec est distinct de la communauté qui lui est associée. Ils peuvent être identiques ("public") ou différents ("mynet"/"private") - mais ce qui apparaît dans la directive group est le nom de sécurité, quel que soit la communauté d'origine.

Les deux directives view définissent de simples sous-arborescences OID, donc aucune d'entre elles ne nécessite de masque explicite. Il en va de même pour la "vue combinée de sous-arborescences2 définie ci-dessous. En fait, un champ masque n'est nécessaire que lors de la définition de tranches de lignes dans une table (ou de vues similaires), et peut presque toujours être omis.

En général, il est conseillé de ne pas mélanger les paramètres de configuration d'accès traditionnels et basés sur VACM, car ceux-ci peuvent parfois interférer les uns avec les autres de manière inattendue. Choisissez un style particulier de configuration d'accès et tenez-vous-y.

Configuration de vue typée

Une configuration similaire pourrait également être configurée comme suit :

view   sys2View included    system
view   sys2View included    .1.3.6.1.2.1.25.1
authcommunity read       public  default      -v sys2View
authcommunity read,write private 10.10.10.0/8

Ce mécanisme permet d'utiliser des vues multi-sous-arborescences (ou d'autres vues non simples) avec le style de configuration rocommunity en une seule ligne.

Il prendrait également en charge la configuration d'un accès "en écriture seule", si cela était nécessaire.

INFORMATIONS SYSTÈME

Groupe Système

Le contenu complet du groupe 'system' (à l'exception de sysUpTime) peut être configuré explicitement en utilisant :

# Remplace 'uname -a' et l'OID système codé en dur - valeurs intrinsèquement en lecture seule
sysDescr     Universal Turing Machine mk I
sysObjectID  .1.3.6.1.4.1.8072.3.2.1066
# Remplace les valeurs par défaut de 'configure' - rend ces objets en lecture seule
sysContact   Alan.Turing@pre-cs.man.ac.uk
sysName      tortoise.turing.com
sysLocation  An idea in the mind of AT
# Comportement standard de l'hôte final
sysServices  72

Surveillance des processus

La liste des services en cours d'exécution sur un système peut être surveillée (et des dispositions peuvent être prises pour corriger tout problème) à l'aide de :

# Au moins un processus de serveur web doit être en cours d'exécution à tout moment
proc    httpd
procfix httpd  /etc/rc.d/init.d/httpd restart
# Il ne devrait jamais y avoir plus de 10 processus de messagerie en cours d'exécution
#    (plus implique une probable tempête de courrier, donc arrêter le système de messagerie)
proc    sendmail   10
procfix sendmail  /etc/rc.d/init.d/sendmail stop
# Il devrait y avoir un seul agent de gestion de réseau en cours d'exécution
#   ("Il ne peut y en avoir qu'un")
proc    snmpd    1  1
Voir également la section « DisMan Event MIB » plus loin.

Surveillance de l'utilisation du disque

L'état du stockage sur disque peut être surveillé à l'aide de :

includeAllDisks 10%
disk /var 20%
disk /usr  3%
#  Conserver 100 Mo libres pour les vidages de panne
disk /mnt/crash  100000

Surveillance de la charge système

Une vérification simple d'un système surchargé pourrait être :

load 10
Une vérification plus raffinée (pour autoriser de brèves périodes d'utilisation intensive, mais reconnaître une charge moyenne-élevée soutenue) pourrait être :
load 30 10 5

SURVEILLANCE ACTIVE

Gestion des notifications

La configuration de l'agent pour signaler les tentatives d'accès invalides pourrait être faite par :

authtrapenable 1
trapcommunity  public
trap2sink      localhost
Alternativement, les deuxième et troisième directives pourraient être combinées (et un accusé de réception demandé) en utilisant :
informsink localhost public
Une configuration avec des destinations de réception répétées, telle que : 
trapsink       localhost
trap2sink      localhost
informsink     localhost
ne doit PAS être utilisée, car cela entraînerait l'envoi de plusieurs copies de chaque piège au même récepteur de piège.

À FAIRE - discuter des pièges SNMPv3

trapsess options snmpv3 localhost:162

À FAIRE - mentionner la configuration d'accès trapd

DisMan Event MIB

La configuration la plus simple pour l'auto-surveillance active de l'agent, par l'agent, pour l'agent, est probablement :

# Configurer les identifiants pour récupérer les valeurs surveillées
createUser    _internal MD5 "le premier signe de folie"
iquerySecName _internal
rouser        _internal
# Activer les entrées de surveillance standard
defaultMonitors         yes
linkUpDownNotifications yes
# En cas de problème, le signaler à quelqu'un !
trap2sink localhost

Le premier bloc configure un utilisateur approprié pour récupérer les informations à surveiller, tandis que la paire de directives suivante active diverses entrées de surveillance intégrées.

Notez que les directives DisMan ne suffisent pas en elles-mêmes à signaler activement les problèmes - une destination appropriée doit également être configurée pour envoyer réellement les notifications résultantes.

Un exemple de surveillance plus détaillé est donné par :

monitor -u me -o hrSWRunName "haute mémoire de processus" hrSWRunPerfMem > 10000

Cela définit une entrée de surveillance booléenne explicite, recherchant tout processus utilisant plus de 10 Mo de mémoire active. De tels processus seront signalés en utilisant le piège (standard) DisMan mteTriggerFired, mais en ajoutant une variable supplémentaire (avec joker) hrSWRunName.

Cette entrée spécifie également un utilisateur explicite (me, tel que défini précédemment) pour récupérer les valeurs surveillées et construire le piège.

Les objets qui pourraient potentiellement fluctuer autour du niveau spécifié sont mieux surveillés à l'aide d'une entrée de surveillance de seuil :

monitor -D -r 10 "trafic réseau" ifInOctets 1000000 5000000

Cela enverra un piège mteTriggerRising chaque fois que le trafic entrant dépassera (environ) 500 Ko/s sur n'importe quelle interface réseau, et un piège mteTriggerFalling correspondant lorsqu'il redescendra en dessous de 100 Ko/s.

Notez que cela surveille les deltas entre les échantillons successifs (-D) plutôt que les valeurs d'échantillons réelles elles-mêmes. Le même effet pourrait être obtenu en utilisant :

monitor -r 10 "trafic réseau" ifInOctets - - 1000000 5000000

La directive linkUpDownNotifications ci-dessus est globalement équivalente à :

notificationEvent  linkUpTrap    linkUp   ifIndex ifAdminStatus ifOperStatus
notificationEvent  linkDownTrap  linkDown ifIndex ifAdminStatus ifOperStatus
monitor  -r 60 -e linkUpTrap   "Générer linkUp"   ifOperStatus != 2
monitor  -r 60 -e linkDownTrap "Générer linkDown" ifOperStatus == 2

Cela définit les pièges à envoyer (en utilisant notificationEvent) et fait explicitement référence à la notification pertinente dans l'entrée de surveillance correspondante (plutôt que d'utiliser les pièges DisMan par défaut).

La directive defaultMonitors ci-dessus est équivalente à une série d'entrées de surveillance (booléennes) :

monitor	-o prNames      -o prErrMessage  "procTable" prErrorFlag   != 0
monitor	-o memErrorName -o memSwapErrorMsg "memory"  memSwapError  != 0
monitor	-o extNames     -o extOutput     "extTable"  extResult     != 0
monitor	-o dskPath      -o dskErrorMsg   "dskTable"  dskErrorFlag  != 0
monitor	-o laNames      -o laErrMessage  "laTable"   laErrorFlag   != 0
monitor	-o fileName     -o fileErrorMsg  "fileTable" fileErrorFlag != 0
et enverra un piège chaque fois que l'une de ces entrées indiquera un problème.

Une approche alternative serait d'invoquer automatiquement l'action "fix" correspondante :

setEvent   prFixIt  prErrFix = 1
monitor -e prFixIt "procTable" prErrorFlag   != 0
(et de manière similaire pour toute autre entrée defaultMonitor).

DisMan Schedule MIB

L'agent pourrait être configuré pour recharger sa configuration une fois par heure, en utilisant :

repeat 3600 versionUpdateConfig.0 = 1

Alternativement, cela pourrait être configuré pour être exécuté à des heures spécifiques de la journée (peut-être après la rotation des journaux) :

cron 10 0 * * * versionUpdateConfig.0 = 1

Le style de planification unique est plutôt moins courant, mais le virus SNMP secret pourrait être activé lors de la prochaine occurrence du vendredi 13 en utilisant :

at 13 13 13 * 5 snmpVirus.0 = 1

Support Perl embarqué

Si le support Perl embarqué est activé dans l'agent, l'initialisation par défaut est équivalente aux directives :

disablePerl  false
perlInitFile /usr/share/snmp/snmp_perl.pl
Le mécanisme principal pour définir des scripts Perl embarqués est la directive perl. Un gestionnaire de MIB très simple (bien qu'un peu inutile) pourrait être enregistré en utilisant : 
perl use Data::Dumper;
perl sub myroutine  { print "appelé : ",Dumper(@_),"\n"; }
perl $agent->register('mylink', '.1.3.6.1.8765', \&myroutine);

Cela repose sur l'objet $agent, défini dans le fichier exemple snmp_perl.pl.

Un gestionnaire de MIB plus réaliste pourrait être :

XXX - QUOI ???
Alternativement, ce code pourrait être stocké dans un fichier externe et chargé en utilisant :
perl 'do /usr/share/snmp/perl_example.pl';

Support proxy

Une configuration pour agir comme un simple proxy pour deux autres agents SNMP (exécutés sur des systèmes distants) pourrait être :

com2sec -Cn rem1context  rem1user default  remotehost1
com2sec -Cn rem2context  rem2user default  remotehost2
proxy -Cn rem1context  -v 1 -c public  remotehost1  .1.3
proxy -Cn rem2context  -v 1 -c public  remotehost2  .1.3
(plus les entrées de contrôle d'accès appropriées).

Les mêmes directives proxy fonctionneraient également avec les requêtes SNMPv3 (entrantes), qui peuvent spécifier un contexte directement. Il serait probablement plus judicieux d'utiliser les contextes de remotehost1 et remotehost2 - les noms choisis ci-dessus visaient à indiquer comment ces directives fonctionnent ensemble.

Notez que les paramètres administratifs pour la requête proxifiée sont spécifiés explicitement et sont indépendants des paramètres de la requête entrante.

Une utilisation alternative de la directive proxy est de passer une partie de l'arborescence OID à un autre agent (soit sur un hôte distant, soit écoutant sur un port différent sur le même système), tout en gérant le reste en interne :

proxy -v 1 -c public localhost:6161 .1.3.6.1.4.1.99
Ce mécanisme peut être utilisé pour relier deux agents SNMP distincts.

Une approche moins courante consiste à mapper un sous-arbre dans une zone différente de l'arborescence MIB globale (soit localement, soit sur un système distant) :

# utilise SNMPv3 pour accéder à l'arborescence MIB .1.3.6.1.2.1.1 sur 'remotehost'
# et le mappe à l'arborescence locale .1.3.6.1.3.10
proxy -v 3 -l noAuthNoPriv -u user remotehost .1.3.6.1.3.10 .1.3.6.1.2.1.1

Agents AgentX

L'agent Net-SNMP pourrait être configuré pour fonctionner comme un agent maître AgentX (écoutant sur un socket nommé non standard et fonctionnant avec les privilèges d'accès définis précédemment), en utilisant :

master agentx
agentXSocket /tmp/agentx/master
agentXPerms  0660 0550 nobody snmp
Un sous-agent souhaitant se connecter à cet agent maître aurait besoin de la même directive agentXSocket, ou du code équivalent : 
netsnmp_ds_set_string(NETSNMP_DS_APPLICATION_ID, NETSNMP_DS_AGENT_X_SOCKET, 
                      "/tmp/agentx/master");

Une configuration AgentX en réseau en bouclage pourrait être mise en place en utilisant :

agentXSocket   tcp:localhost:705
agentXTimeout  5
agentXRetries  2
du côté maître, et : 
agentXSocket   tcp:localhost:705
agentXTimeout  10
agentXRetries  1
agentXPingInterval 600
du côté client.

Notez que les paramètres de timeout et de nouvelles tentatives peuvent être asymétriques pour les deux directions, et le sous-agent peut interroger l'agent maître à intervalles réguliers (600s = toutes les 10 minutes) pour s'assurer que la connexion est toujours opérationnelle.
