NOM

sniproxy.conf - fichier de configuration de sniproxy

SYNOPSIS

/etc/sniproxy.conf

DESCRIPTION

/etc/sniproxy.conf est le fichier de configuration de sniproxy. Les instructions sont séparées par un retour à la ligne ou un point-virgule. Les lignes commençant par # sont des commentaires. La configuration est divisée en sections délimitées par des accolades. Les caractères peuvent être échappés à l'aide de \. Les directives de configuration peuvent être raccourcies tant qu'elles sont sans ambiguïté, par exemple user daemon au lieu de username daemon.

NOMUTILISATEUR

username daemon

Spécifie l'utilisateur sous lequel sniproxy s'exécutera. Lorsque sniproxy est lancé en tant que superutilisateur, il abandonnera ses privilèges à cet utilisateur.

FICHIERPID

pidfile /var/run/sniproxy.pid

Spécifie le chemin d'accès au fichier pid, le répertoire doit être accessible en écriture par l'utilisateur sous lequel sniproxy s'exécute.

JOURNALERREURS

error_log {
    syslog daemon
    priority notice
}

Spécifie comment les messages d'erreur doivent être traités. Les messages peuvent être journalisés dans syslog en utilisant la directive syslog qui spécifie que les journaux doivent être envoyés à une installation syslog donnée. Alternativement, la directive filename peut être spécifiée pour journaliser dans un fichier, ces deux options sont mutuellement exclusives. La directive priority indique le niveau de gravité des messages à journaliser. Les priorités acceptées sont les priorités syslog standard, par ordre de verbosité croissant : emergency, alert, critical, error, warning, notice, info, et debug.

JOURNALACCES

access_log {
    filename /var/log/sniproxy/access.log
}

Spécifie comment les connexions doivent être journalisées, peut être remplacé dans un écouteur spécifique. Les connexions sont journalisées après la fermeture des sockets du client et du serveur. Les directives syslog et priority peuvent être utilisées ici comme dans error_log.

RESOLVER

resolver {
    nameserver 127.0.0.1
    mode ipv6_first
}

Spécifie comment les requêtes DNS doivent être résolues, ceci n'est requis que si vous utilisez des noms d'hôte comme adresses dans la configuration ou si vous utilisez des backends génériques. Si non spécifié, des requêtes uniquement IPv4 seront effectuées en utilisant les serveurs de noms par défaut du système.

Quatre modes sont supportés :

ipv4_only : requêter tous les enregistrements A, utiliser le premier enregistrement A renvoyé (en suivant les enregistrements CNAME).

ipv6_only : requêter tous les enregistrements AAAA, utiliser le premier enregistrement AAAA renvoyé (en suivant les enregistrements CNAME).

ipv4_first : requêter les enregistrements A et AAAA, attendre que les deux requêtes soient terminées, utiliser le premier enregistrement A s'il y en a, sinon utiliser le premier enregistrement AAAA.

ipv6_first : requêter les enregistrements A et AAAA, attendre que les deux requêtes soient terminées, utiliser le premier enregistrement AAAA s'il y en a, sinon utiliser le premier enregistrement A.

Il est fortement recommandé d'utiliser un serveur de noms local, car un seul socket est réutilisé pour toutes les requêtes DNS et donc le numéro de port UDP est prévisible, ne protégeant la requête que contre les réponses falsifiées par l'ID de requête de 16 bits. De plus, comme aucun cache DNS interne n'est effectué, un résolveur local peut améliorer les performances.

ÉCOUTEUR

listener 192.0.2.10:80 {
    protocol http
    reuseport yes
    table http_hosts
    fallback 192.0.2.100:80
    bad_requests log
    source 192.0.2.10
    access_log {
        filename /var/log/sniproxy/http_access.log
    }
}
listener [::]:80 {
    protocol http
    ipv6_v6only yes
    table http_hosts
    fallback unix:/var/run/http_fallback_unix.sock
}

Définit une adresse d'écoute pour accepter de nouvelles connexions de clients. Les adresses peuvent être spécifiées comme une adresse littérale IPv4 suivie d'un numéro de port TCP, une adresse littérale IPv6 suivie d'un numéro de port TCP, un numéro de port TCP seul ou un chemin de socket Unix préfixé par 'unix:'.

Protocol définit comment la requête du client doit être analysée pour obtenir le nom d'hôte demandé, deux protocoles sont supportés : http et tls.

La directive reuseport contrôle si le port est ouvert en mode SO_REUSEPORT, ce qui permet d'exécuter plusieurs instances de sniproxy sur la même paire ip:port. Cela nous permet de répartir uniformément les connexions entrantes entre ces instances sans utiliser de proxy d'équilibrage de charge externe. Nécessite le noyau Linux 3.9+. Définir reuseport sur « yes » active cette fonctionnalité.

La directive ipv6_v6only contrôle si l'écoute sur l'adresseAny IPv6 « :: » acceptera les connexions à une adresse IPv4 ainsi qu'à une adresse IPv6. Ceci est utile si l'utilisateur souhaite des configurations différentes pour IPv4 et IPv6 ou souhaite gérer le trafic IPv4 avec un autre serveur/proxy. Ceci est applicable uniquement aux écouteurs IPv6 et est ignoré sur les autres écouteurs.

Table spécifie le nom de la table utilisée pour rechercher le serveur auquel transférer la connexion, en fonction du nom d'hôte extrait de la requête client initiale. Si aucune directive table n'est spécifiée, la table par défaut, sans nom, sera utilisée.

La directive fallback spécifie un serveur à utiliser si la requête client ne peut pas être analysée, si un serveur ne peut pas être trouvé dans la table pour le nom d'hôte spécifié, ou si le nom d'hôte ne peut pas être résolu. Il doit s'agir d'une adresse IP et d'un port, ou d'un chemin de socket Unix.

La directive bad_requests permet de journaliser le contenu de la requête client si elle n'est pas analysable, ce qui est utile pour le débogage.

La directive source permet de spécifier une adresse spécifique à lier avant de se connecter au serveur backend. Dans la plupart des cas, il est préférable d'omettre cette option et de laisser le système d'exploitation sélectionner automatiquement l'adresse sortante. N'incluez pas de numéro de port dans cette adresse, car cela limitera le proxy à une seule connexion simultanée à chaque serveur à la fois.

La configuration du journal d'accès peut être remplacée sur chaque écouteur.

TABLE

table http_hosts {
    ^example\.com$ 192.0.2.101
    ^example\.net$ 192.0.2.102
    ^example\.org$ 192.0.2.103 proxy_protocol
}

Les tables définissent comment mapper chaque nom d'hôte à un serveur backend. Le nom d'hôte de chaque requête est mis en correspondance avec les entrées de la table dans l'ordre, jusqu'à ce qu'une correspondance soit trouvée et que ce serveur soit utilisé. L'adresse du serveur peut être une IP, une IP et un port, un chemin de socket Unix, un nom d'hôte ou '*'. Si aucun port n'est spécifié, le port de l'écouteur sur lequel la connexion a été reçue sera utilisé.

L'option facultative proxy_protocol ajoutera un en-tête PROXY v1 du protocole HAProxy à la connexion proxénisée, permettant aux serveurs web compatibles d'obtenir l'adresse IP et le port source et destination de la connexion TCP entrante d'origine.
