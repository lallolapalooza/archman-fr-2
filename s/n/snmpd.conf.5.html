NOM

snmpd.conf - fichier de configuration de l'agent SNMP Net-SNMP

DESCRIPTION

L'agent Net-SNMP utilise un ou plusieurs fichiers de configuration pour contrôler son fonctionnement et les informations de gestion fournies. Ces fichiers (snmpd.conf et snmpd.local.conf) peuvent être situés dans plusieurs emplacements, comme décrit dans la page de manuel snmp_config(5).

L'application (perl) snmpconf peut être utilisée pour générer des fichiers de configuration pour les besoins les plus courants de l'agent. Consultez la page de manuel snmpconf(1) pour plus d'informations, ou essayez d'exécuter la commande :

snmpconf -g basic_setup

Il existe un grand nombre de directives qui peuvent être spécifiées, mais celles-ci se répartissent principalement en quatre catégories distinctes :

  • celles qui contrôlent qui peut accéder à l'agent
  • celles qui configurent les informations fournies par l'agent
  • celles qui contrôlent la surveillance active du système local
  • celles qui concernent l'extension des fonctionnalités de l'agent.

Certaines directives ne rentrent pas naturellement dans l'une de ces quatre catégories, mais cela couvre la majorité du contenu d'un fichier snmpd.conf typique. Une liste complète des directives reconnues peut être obtenue en exécutant la commande :

snmpd -H

COMPORTEMENT DE L'AGENT

Bien que la plupart des directives de configuration concernent les informations MIB fournies par l'agent, il existe une poignée de directives qui contrôlent le comportement de snmpd considéré simplement comme un démon fournissant un service réseau.

agentaddress [<spécificateur-transport>:]<adresse-transport>[,...]
définit une liste d'adresses d'écoute, sur lesquelles recevoir les requêtes SNMP entrantes. Voir la section ADRESSES D'ÉCOUTE dans la page de manuel snmpd(8) pour plus d'informations sur le format des adresses d'écoute.
Le comportement par défaut est d'écouter sur le port UDP 161 sur toutes les interfaces IPv4.
agentgroup {GROUPE|#GID}
change vers le groupe spécifié après avoir ouvert le(s) port(s) d'écoute. Ceci peut faire référence à un groupe par son nom (GROUPE) ou à un ID de groupe numérique commençant par '#' (#GID).
agentuser {UTILISATEUR|#UID}
change vers l'utilisateur spécifié après avoir ouvert le(s) port(s) d'écoute. Ceci peut faire référence à un utilisateur par son nom (UTILISATEUR) ou à un ID d'utilisateur numérique commençant par '#' (#UID).
leave_pidfile yes
instruit l'agent de ne pas supprimer son fichier pid lors de l'arrêt. Équivalent à spécifier "-U" sur la ligne de commande.
maxGetbulkRepeats NB
Définit le nombre maximum de réponses autorisées pour une seule variable dans une requête getbulk. Défini à 0 pour activer le défaut et à -1 pour activer un nombre illimité. Comme la mémoire est allouée à l'avance, définir cela à illimité n'est pas considéré comme sûr si votre population d'utilisateurs ne peut pas être considérée comme fiable. Un nombre de répétitions supérieur à celui-ci sera tronqué à cette valeur.
Ceci est défini par défaut à -1.
maxGetbulkResponses NB
Définit le nombre maximum de réponses autorisées pour une requête getbulk. Ceci est défini par défaut à 100. Défini à 0 pour activer le défaut et à -1 pour activer un nombre illimité. Comme la mémoire est allouée à l'avance, définir cela à illimité n'est pas considéré comme sûr si votre population d'utilisateurs ne peut pas être considérée comme fiable.
En général, le nombre total de réponses ne sera pas autorisé à dépasser le nombre maxGetbulkResponses, et le total renvoyé sera un multiple entier du nombre de variables demandées multiplié par le nombre calculé de répétitions autorisées pour rester en dessous de ce nombre.
Notez également que le traitement de maxGetbulkRepeats est géré en premier.
ifmib_max_num_ifaces NB
Définit le nombre maximum d'interfaces incluses dans la collecte de données IF-MIB. Pour les serveurs avec un grand nombre d'interfaces (ppp, dummy, bridge, etc.), le traitement IF-MIB consommera une grande partie du CPU pour les appels ioctl (sous Linux). Définir un maximum raisonnable pour le CPU utilisé réduira la charge CPU pour le traitement IF-MIB. Par exemple, configurer "ifmib_max_num_ifaces 500" inclura seulement les 500 premières interfaces basées sur ifindex et ignorera toutes les autres pour le traitement IF-MIB.
Le défaut (sans configuration) est d'inclure toutes les interfaces.
include_ifmib_iface_prefix PREFIX1 PREFIX2 ...
Définit les préfixes de nom d'interface à inclure dans la collecte de données IF-MIB. Pour les serveurs avec un grand nombre d'interfaces (ppp, dummy, bridge, etc.), le traitement IF-MIB consommera une grande partie du CPU pour les appels ioctl (sous Linux). Un ensemble de préfixes de nom d'interface séparés par des espaces réduira la charge CPU pour le traitement IF-MIB. Par exemple, configurer "include_ifmib_iface_prefix eth dummy lo" inclura seulement les interfaces avec ces préfixes et ignorera toutes les autres pour le traitement IF-MIB. Si le support des expressions régulières est compilé, chacun des préfixes est une expression régulière (qui ne peut pas contenir d'espace ou de tabulation).
Le défaut (sans configuration) est d'inclure toutes les interfaces.

Configuration SNMPv3 - Vraie sécurité

SNMPv3 ajoute des modèles de sécurité flexibles à la structure des paquets SNMP afin que plusieurs solutions de sécurité puissent être utilisées. SNMPv3 a été initialement défini avec un "User-based Security Model" (USM) [RFC3414] qui nécessitait de maintenir une base de données d'utilisateurs spécifique à SNMP. Cela s'est avéré plus tard difficile à maintenir et présentait quelques problèmes de sécurité mineurs. L'IETF a depuis ajouté des modèles de sécurité supplémentaires pour tunneliser SNMP sur SSH [RFC5592] et DTLS/TLS [RFC-à-venir]. Net-SNMP contient un support robuste pour SNMPv3/USM, SNMPv3/TLS et SNMPv3/DTLS. Il contient également un support partiel pour SNMPv3/SSH mais il n'a pas été aussi largement testé. Il contient également du code pour le support d'un SNMPv3 expérimental basé sur Kerberos qui n'a jamais été standardisé.

On espère que davantage de logiciels et d'appareils SNMP supporteront bientôt SNMP sur (D)TLS ou SSH, mais il est probable que les appareils prenant initialement en charge SNMP ne contiendront que le support des utilisateurs USM. Si votre gestionnaire réseau prend en charge SNMP sur (D)TLS ou SNMP sur SSH, nous vous suggérons d'utiliser l'un de ces mécanismes au lieu d'utiliser USM, mais comme toujours avec Net-SNMP, nous vous donnons les options pour que vous puissiez faire le choix qui vous convient le mieux.

Cela devrait suffire à la plupart des utilisateurs, sauf si vous intégrez notre agent dans un appareil où ces nombres ne varient pas lors du premier démarrage des boîtiers.

SNMPv3 sur TLS

SNMPv3 peut être encapsulé sur TLS et DTLS. TLS s'exécute sur TCP et DTLS est l'équivalent UDP. Wes Hardaker (le fondateur de Net-SNMP) a réalisé une étude et l'a présentée lors d'une réunion de l'IETF, démontrant que les protocoles basés sur TCP sont suffisants pour les réseaux stables, mais deviennent rapidement problématiques dans les réseaux instables avec même un niveau modéré de perte de paquets (~ 20-30%). Si vous envisagez d'utiliser TLS ou DTLS, vous devriez choisir celui qui convient à votre environnement réseau. Vous devriez potentiellement les activer tous les deux afin que votre système de gestion puisse accéder indifféremment au port UDP ou TCP selon les besoins.

De nombreux jetons de configuration décrits ci-dessous sont préfixés par une balise '[snmp]'. Si vous placez ces jetons dans votre fichier snmpd.conf, cette balise est requise. Voir la page de manuel snmp_config(5) pour la signification de ce changement de contexte.

[snmp] localCert <spécificateur>
Ce jeton définit la clé publique X.509 par défaut à utiliser comme identité du serveur. Il doit s'agir soit d'une empreinte numérique, soit d'un nom de fichier. Pour créer une clé publique à utiliser, veuillez exécuter l'utilitaire "net-snmp-cert" qui vous aidera à créer le certificat requis.
La valeur par défaut pour cela est le certificat dans le fichier de certificat nommé "snmpd".
[snmp] tlsAlgorithms <algorithmes>
Cette chaîne sélectionnera les algorithmes à utiliser lors de la négociation de la sécurité pendant l'établissement d'une session (D)TLS. Voir la page de manuel openssl ciphers(1) pour les détails sur le format. Les chaînes d'exemples incluent :
DEFAULT
ALL
HIGH
HIGH:!AES128-SHA
La valeur par défaut est ce avec quoi openssl lui-même a été configuré.
[snmp] x509CRLFile
Si vous utilisez une Autorité de Certification (AC) qui publie une Liste de Révocation de Certificats (CRL), alors ce jeton peut être utilisé pour spécifier l'emplacement dans le système de fichiers d'une copie du fichier CRL. Notez que Net-SNMP ne récupère pas une CRL via http et cela doit être un fichier, pas une URL. De plus, OpenSSL ne recharge pas un fichier CRL lorsqu'il a été modifié, donc les modifications ou mises à jour du fichier ne seront remarquées qu'au redémarrage de l'agent snmpd.
certSecName PRIORITY FINGERPRINT OPTIONS
OPTIONS peut être l'un des <--sn SECNAME | --rfc822 | --dns | --ip | --cn | --any>.
Le jeton certSecName spécifiera comment mapper un champ de certificat du certificat X.509 du client à un nom d'utilisateur SNMPv3. Utilisez le drapeau --sn SECNAME pour spécifier directement un nom de sécurité pour un certificat donné. Les autres drapeaux extraient un composant particulier du certificat à utiliser comme nom de sécurité snmpv3. Ces champs sont : un SubjectAltName contenant une valeur rfc822 (par exemple, hardaker@net-snmp.org), un SubjectAltName contenant une valeur de nom dns (par exemple, foo.net-snmp.org), une adresse IP (par exemple, 192.0.2.1) ou un nom commun "Wes Hardaker". Le drapeau --any spécifie que n'importe lequel des champs subjecAltName peut être utilisé. Assurez-vous qu'une fois qu'un nom de sécurité a été sélectionné, il lui est accordé une autorisation via les contrôles VACM décrits plus loin dans cette page de manuel.
Consultez la page web http://www.net-snmp.org/wiki/index.php/Using_DTLS pour des instructions plus détaillées sur la configuration de (D)TLS.
trustCert <spécificateur>
Pour que X509 vérifie correctement un certificat, il doit être vérifiable jusqu'à une ancre de confiance. Cette ancre de confiance est généralement un certificat d'AC, mais cela peut aussi être un certificat auto-signé. Le jeton "trustCert" doit être utilisé pour charger des ancres de confiance spécifiques dans le moteur de vérification.

SNMP sur (D)TLS nécessite l'utilisation du Modèle de Sécurité de Transport (TSM), donc lisez également la section sur l'utilisation du Modèle de Sécurité de Transport. Assurez-vous lorsque vous configurez le VACM pour accepter les connexions de (D)TLS que vous utilisez le modèle de sécurité "tsm". PAR EXEMPLE :

rwuser -s tsm hardaker@net-snmp.org

Support SNMPv3 sur SSH

Pour utiliser SSH, vous devrez configurer sshd pour invoquer le programme sshtosnmp ainsi que configurer les paramètres de contrôle d'accès pour autoriser l'accès via le modèle de sécurité tsm en utilisant le nom d'utilisateur fourni à snmpd par le transport ssh.

SNMPv3 avec le Modèle de Sécurité de Transport (TSM)

Le Modèle de Sécurité de Transport [RFC5591] définit un système de sécurité SNMPv3 pour une utilisation avec des protocoles de sécurité "encapsulés" comme TLS, DTLS et SSH. C'est un modèle de sécurité très simple qui permet simplement aux paquets correctement protégés de passer dans l'application snmp. Le transport est requis pour passer un securityName à utiliser au TSM et le TSM peut éventuellement le préfixer avec une chaîne de transport (voir ci-dessous).

tsmUseTransportPrefix (1|yes|true|0|no|false)
S'il est défini sur true, le module TSM prendra chaque securityName qui lui est passé par les transports sous-jacents et le préfixera avec une chaîne qui identifie spécifiquement le transport dont il provient. Ceci est utile pour éviter les conflits de securityName avec des transports qui génèrent des securityNames identiques. Par exemple, si le transport de sécurité ssh a livré le securityName "hardaker" pour une connexion SSH et que le transport de sécurité TLS a également livré le securityName "hardaker" pour une connexion TLS, il serait impossible de séparer ces deux utilisateurs pour leur accorder des droits d'accès distincts. Avec tsmUseTransportPrefix défini sur true, cependant, les securityNames seraient correctement préfixés par l'un des éléments suivants : "tls:", "dtls:" ou "ssh:" .

SNMPv3 avec le Modèle de Sécurité Basé sur l'Utilisateur (USM)

SNMPv3 a été initialement défini en utilisant le Modèle de Sécurité Basé sur l'Utilisateur (USM), qui contient une liste privée d'utilisateurs et de clés spécifiques au protocole SNMPv3. Cependant, la communauté opérationnelle a déclaré que la manipulation d'une autre base de données était une corvée et préférerait utiliser l'infrastructure existante. À cette fin, l'IETF a créé le groupe de travail ISMS pour résoudre ce problème, et le groupe de travail ISMS a décidé d'encapsuler SNMP sur SSH et DTLS pour utiliser les infrastructures d'utilisateurs et d'authentification existantes.

Utilisateurs SNMPv3 USM

Pour utiliser les utilisateurs spécifiques à SNMPv3 basés sur l'USM, vous devrez les créer. Il est recommandé d'**utiliser la commande net-snmp-config** pour ce faire, mais vous pouvez également le faire en spécifiant directement des directives createUser vous-même :

createUser [-e ENGINEID] nomutilisateur (MD5|SHA|SHA-512|SHA-384|SHA-256|SHA-224) motdepasseauth [DES|AES] [motdepasseprive]
MD5|SHA|SHA-512|SHA-384|SHA-256|SHA-224 sont les types d'authentification à utiliser. DES et AES sont les protocoles de confidentialité à utiliser. Si le mot de passe de confidentialité n'est pas spécifié, il est supposé être le même que le mot de passe d'authentification. Notez que les utilisateurs créés seront inutiles s'ils ne sont pas également ajoutés aux tables de contrôle d'accès VACM décrites ci-dessus.
L'authentification SHA|SHA-512|SHA-384|SHA-256|SHA-224 et la confidentialité DES/AES nécessitent que OpenSSL soit installé et que l'agent soit compilé avec le support OpenSSL. L'authentification MD5 peut être utilisée sans OpenSSL.
Attention : la longueur minimale du mot de passe est de 8 caractères.
Les utilisateurs SNMPv3 peuvent être créés à la volée en utilisant la commande snmpusm(1).
Au lieu de chercher comment utiliser cette directive et où la placer (voir ci-dessous), exécutez simplement "net-snmp-config --create-snmpv3-user" à la place, ce qui ajoutera l'une de ces lignes au bon endroit.
Cette directive doit être placée dans le fichier /var/net-snmp/snmpd.conf au lieu des autres emplacements normaux. La raison est que l'information est lue du fichier, puis la ligne est supprimée (éliminant ainsi le stockage du mot de passe maître pour cet utilisateur) et remplacée par la clé qui en est dérivée. Cette clé est une clé localisée, de sorte que si elle est volée, elle ne peut pas être utilisée pour accéder à d'autres agents. Si le mot de passe est volé, cependant, il le peut.
Si vous avez besoin de localiser l'utilisateur à un EngineID particulier (ce qui est principalement utile dans le fichier snmptrapd.conf similaire), vous pouvez utiliser l'argument -e pour spécifier un EngineID sous forme hexadécimale (PAR EXEMPLE, "0x01020304").
Si vous souhaitez générer directement vos clés maîtres ou localisées, remplacez le mot de passe donné par une chaîne hexadécimale (précédée de "0x") et précédez la chaîne hexadécimale d'un jeton -m ou -l (respectivement). EXEMPLES :
[ces clés ne sont *pas* sécurisées mais sont faciles à analyser visuellement pour le
comptage. Veuillez générer des clés aléatoires au lieu d'utiliser
ces exemples]
createUser monutilisateur SHA -l 0x0001020304050607080900010203040506070809 AES -l 0x00010203040506070809000102030405
createUser monutilisateur SHA -m 0x0001020304050607080900010203040506070809 AES -m 0x0001020304050607080900010203040506070809
En raison de la façon dont la localisation se produit, les clés de confidentialité localisées sont censées avoir la longueur requise par l'algorithme (128 bits pour tous les algorithmes pris en charge). Les clés de chiffrement maîtres, cependant, doivent avoir la longueur requise par l'algorithme d'authentification et non la longueur requise par l'algorithme de chiffrement (MD5 : 16 octets, SHA : 20 octets).

CONTRÔLE D'ACCÈS

snmpd prend en charge le Modèle de Contrôle d'Accès Basé sur les Vues (VACM) tel que défini dans le RFC 2575, pour contrôler qui peut récupérer ou mettre à jour des informations. À cette fin, il reconnaît diverses directives relatives au contrôle d'accès.

Contrôle d'Accès Traditionnel

La plupart des exigences de contrôle d'accès simples peuvent être spécifiées à l'aide des directives rouser

rouser/rwuser (pour SNMPv3) ou rocommunity/rwcommunity (pour SNMPv1 ou SNMPv2c).

rouser [-s SECMODEL] USER [noauth|auth|priv [OID | -V VIEW [CONTEXT]]]
rwuser [-s SECMODEL] USER [noauth|auth|priv [OID | -V VIEW [CONTEXT]]]
spécifie un utilisateur SNMPv3 qui sera autorisé en lecture seule (GET et GETNEXT) ou en lecture-écriture (GET, GETNEXT et SET) respectivement. Par défaut, cela fournira un accès à l'arbre OID complet pour les requêtes SNMPv3 authentifiées (y compris cryptées), en utilisant le contexte par défaut. Un niveau de sécurité minimum alternatif peut être spécifié en utilisant noauth (pour autoriser les requêtes non authentifiées), ou priv (pour imposer l'utilisation du cryptage). Le champ OID restreint l'accès pour cet utilisateur au sous-arbre enraciné à l'OID donné, ou à la vue nommée. Un contexte optionnel peut également être spécifié, ou "context*" pour désigner un préfixe de contexte. Si aucun champ de contexte n'est spécifié (ou si le jeton "*" est utilisé), la directive correspondra à tous les contextes possibles.
Si SECMODEL est spécifié, ce sera le modèle de sécurité requis pour cet utilisateur (notez que des noms d'utilisateur identiques peuvent provenir de différents modèles de sécurité et seront correctement séparés via les paramètres de contrôle d'accès). Le modèle de sécurité par défaut est "usm" et les autres modèles de sécurité courants sont probablement "tsm" lors de l'utilisation de (D)TLS ou SSH et "ksm" si le support Kerberos a été compilé .
rocommunity COMMUNITY [SOURCE [OID | -V VIEW [CONTEXT]]]
rwcommunity COMMUNITY [SOURCE [OID | -V VIEW [CONTEXT]]]
spécifie une communauté SNMPv1 ou SNMPv2c qui sera autorisée en lecture seule (GET et GETNEXT) ou en lecture-écriture (GET, GETNEXT et SET) respectivement. Par défaut, cela fournira un accès à l'arbre OID complet pour de telles requêtes, quelle que soit leur provenance. Le jeton SOURCE peut être utilisé pour restreindre l'accès aux requêtes provenant du ou des systèmes spécifiés - voir com2sec pour plus de détails. Le champ OID restreint l'accès pour cette communauté au sous-arbre enraciné à l'OID donné, ou à la vue nommée. Les contextes sont généralement moins pertinents pour les versions SNMP basées sur la communauté, mais le même comportement s'applique ici.
rocommunity6 COMMUNITY [SOURCE [OID | -V VIEW [CONTEXT]]]
rwcommunity6 COMMUNITY [SOURCE [OID | -V VIEW [CONTEXT]]]
sont des directives relatives aux requêtes reçues en utilisant IPv6 (si l'agent prend en charge de tels domaines de transport). L'interprétation des jetons SOURCE, OID, VIEW et CONTEXT est exactement la même que pour les versions IPv4 .

Dans chaque cas, une seule directive doit être spécifiée pour un utilisateur SNMPv3 donné, ou une chaîne de communauté. Il n'est pas approprié de spécifier à la fois les directives rouser et rwuser faisant référence au même utilisateur SNMPv3 (ou des paramètres de communauté équivalents). La directive rwuser fournit tout l'accès de rouser (tout en permettant le support SET). Il en va de même pour les directives basées sur la communauté.

Des exigences d'accès plus complexes (telles que l'accès à deux sous-arbres OID distincts ou plus, ou des vues différentes pour les requêtes GET et SET) doivent utiliser l'un des autres mécanismes de contrôle d'accès. Notez que si plusieurs communautés ou utilisateurs SNMPv3 distincts doivent se voir accorder le même niveau d'accès, il serait également plus efficace d'utiliser les directives de configuration principales de VACM.

Configuration de VACM

Toute la flexibilité de VACM est disponible en utilisant quatre directives de configuration - com2sec, group, view et access. Celles-ci fournissent une configuration directe des tables VACM sous-jacentes.

com2sec [-Cn CONTEXT] SECNAME SOURCE COMMUNITY
com2sec6 [-Cn CONTEXT] SECNAME SOURCE COMMUNITY
mappe une chaîne de communauté SNMPv1 ou SNMPv2c vers un nom de sécurité - soit à partir d'une plage spécifique d'adresses source, soit globalement ("default"). Une source restreinte peut être soit un nom d'hôte (ou une adresse) spécifique, soit un sous-réseau - représenté sous forme d'IP/MASK (par exemple 10.10.10.0/255.255.255.0), ou IP/BITS (par exemple 10.10.10.0/24), ou les équivalents IPv6. Une restriction précédée d'un point d'exclamation (!) refuse l'accès depuis cette adresse ou ce sous-réseau, par exemple, !10.10.10.0/24 refuse les requêtes provenant de ces sources dans ce sous-réseau. Les restrictions de refus doivent précéder les autorisations. Par exemple, l'exemple suivant autorise l'accès depuis tout le réseau 10.0.0.0/8 à l'exception de 10.10.10.0/24 :
com2sec sec1 !10.10.10.0/24 public
com2sec sec1 10.0.0.0/8 public
L'accès depuis l'extérieur du réseau 10.0.0.0/8 serait toujours refusé.
La même chaîne de communauté peut être spécifiée dans plusieurs directives distinctes (vraisemblablement avec des jetons source différents), et la première combinaison source/communauté qui correspond à la requête entrante sera sélectionnée. Diverses combinaisons source/communauté peuvent également être mappées au même nom de sécurité.
Si un CONTEXT est spécifié (en utilisant -Cn), la chaîne de communauté sera mappée à un nom de sécurité dans le contexte SNMPv3 nommé. Sinon, le contexte par défaut ("") sera utilisé.
com2secunix [-Cn CONTEXT] SECNAME SOCKPATH COMMUNITY
est la version pour les sockets de domaine Unix de com2sec.
group GROUP {v1|v2c|usm|tsm|ksm} SECNAME
mappe un nom de sécurité (dans le modèle de sécurité spécifié) dans un groupe nommé. Plusieurs directives group peuvent spécifier le même nom de groupe, permettant à un seul paramètre d'accès de s'appliquer à plusieurs utilisateurs et/ou chaînes de communauté.
Notez que les groupes doivent être configurés séparément pour les deux modèles basés sur la communauté - une seule directive com2sec (ou équivalente) sera généralement accompagnée de deux directives group.
view VNAME TYPE OID [MASK]
définit une "vue" nommée - un sous-ensemble de l'arbre OID global. Il s'agit le plus souvent d'un seul sous-arbre, mais plusieurs directives view peuvent être fournies avec le même nom de vue (VNAME), pour construire une collection plus complexe d'OIDs. TYPE est soit included soit excluded, ce qui peut encore définir une vue plus complexe (par exemple en excluant certains objets sensibles d'un sous-arbre autrement accessible).
MASK est une liste d'octets hexadécimaux (optionnellement séparés par '.' ou ':') avec les bits définis indiquant quels sous-identifiants dans l'OID de la vue doivent correspondre. S'il n'est pas spécifié, cela correspond par défaut à l'OID exact (tous les bits définis), définissant ainsi un simple sous-arbre OID. Donc :
view iso1 included .iso 0xf0
view iso2 included .iso
view iso3 included .iso.org.dod.mgmt 0xf0
définiraient tous la même vue, couvrant l'intégralité du sous-arbre 'iso(1)' (le troisième exemple ignorant les sous-identifiants non couverts par le masque).
Plus utilement, le masque peut être utilisé pour définir une vue couvrant une ligne (ou des lignes) particulière(s) dans une table, en faisant correspondre l'index de table approprié , mais en ignorant le sous-identifiant de colonne :
view ifRow4 included .1.3.6.1.2.1.2.2.1.0.4 0xff:a0
Notez qu'un masque de plus de 8 bits doit utiliser ':' pour séparer les octets individuels.
access GROUP CONTEXT {any|v1|v2c|usm|tsm|ksm} LEVEL PREFX READ WRITE NOTIFY
mappe un groupe d'utilisateurs/communautés (avec un modèle de sécurité et un niveau de sécurité minimum particuliers, et dans un contexte spécifique) à l'une des trois vues, en fonction de la requête en cours de traitement.
LEVEL est l'un de noauth, auth, ou priv. PREFX spécifie comment CONTEXT doit être mis en correspondance avec le contexte de la requête entrante, soit exact, soit prefix. READ, WRITE et NOTIFY spécifie la vue à utiliser pour les requêtes GET*, SET et TRAP/INFORM (bien que la vue NOTIFY ne soit actuellement pas utilisée). Pour l'accès v1 ou v2c, LEVEL devra être noauth.

Configuration de vue typée

Le dernier groupe de directives étend l'approche VACM vers un mécanisme plus flexible, qui peut être appliqué à d'autres exigences de contrôle d'accès. Plutôt que les trois vues fixes du mécanisme VACM standard, cela peut être utilisé pour configurer divers types de vues différents. En ce qui concerne l'agent SNMP principal, les deux types de vues principaux sont read et write, correspondant aux vues READ et WRITE de la directive access principale. Voir la page de manuel 'snmptrapd.conf(5)' pour une discussion sur les autres types de vues.

authcommunity TYPES COMMUNITY [SOURCE [OID | -V VIEW [CONTEXT]]]
est une alternative aux directives rocommunity/rwcommunity. TYPES sera généralement read ou read,write respectivement. La spécification de la vue peut être soit un sous-arbre OID (comme précédemment), soit une vue nommée (définie en utilisant la directive view) pour plus de flexibilité. Si elle est omise, l'accès sera autorisé à l'arbre OID complet. Si CONTEXT est spécifié, l'accès est configuré dans ce contexte SNMPv3. Sinon, le contexte par défaut ("") est utilisé.
authuser TYPES [-s MODEL] USER [LEVEL [OID | -V VIEW [CONTEXT]]]
est une alternative aux directives rouser/rwuser. Les champs TYPES, OID, VIEW et CONTEXT ont la même signification que pour authcommunity.
authgroup TYPES [-s MODEL] GROUP [LEVEL [OID | -V VIEW [CONTEXT]]]
est un complément à la directive authuser, spécifiant l'accès pour un groupe particulier (défini en utilisant la directive group comme d'habitude). Les deux directives authuser et authgroup autorisent par défaut les requêtes authentifiées - LEVEL peut également être spécifié comme noauth ou priv pour autoriser les requêtes non authentifiées, ou exiger le cryptage respectivement. Les deux directives authuser et authgroup configurant par défaut l'accès aux requêtes SNMPv3/USM - utilisez l'option '-s' pourspécifier un modèle de sécurité alternatif (utilisant les mêmes valeurs que pour l'accès ci-dessus).
authaccess TYPES [-s MODÈLE] GROUPE VUE [NIVEAU [CONTRÉE]]
configure également l'accès pour un groupe particulier, en spécifiant le nom et le type de vue à appliquer. Les champs MODÈLE et NIVEAU sont interprétés de la même manière que pour authgroup. Si CONTRÉE est spécifié, l'accès est configuré dans ce contexte SNMPv3 (ou les contextes avec ce préfixe si le champ CONTRÉE se termine par '*'). Sinon, le contexte par défaut ("") est utilisé.
setaccess GROUPE CONTRÉE MODÈLE NIVEAU PRÉFIXE VUE TYPES
est un équivalent direct de la directive access d'origine, listant généralement les types de vue comme lecture ou lecture,écriture selon le cas. (ou voir 'snmptrapd.conf(5)' pour d'autres possibilités). Tous les autres champs ont la même interprétation qu'avec access.

INFORMATIONS SYSTÈME

La plupart des informations rapportées par l'agent Net-SNMP sont récupérées du système sous-jacent, ou configurées dynamiquement via des requêtes SNMP SET (et conservées d'une exécution de l'agent à la suivante). Cependant, certains objets MIB peuvent être configurés ou contrôlés via le fichier snmpd.conf(5).

Groupe Système

La plupart des objets scalaires du groupe 'system' peuvent être configurés de cette manière :

sysLocation CHAÎNE
sysContact CHAÎNE
sysName CHAÎNE
définit respectivement l'emplacement du système, le contact système ou le nom du système (sysLocation.0, sysContact.0 et sysName.0) pour l'agent. Normalement, ces objets sont inscriptibles via des requêtes SNMP SET suffisamment autorisées. Cependant, spécifier l'une de ces directives rend l'objet correspondant en lecture seule, et les tentatives de le modifier entraîneront une réponse d'erreur notWritable.
sysServices NOMBRE
définit la valeur de l'objet sysServices.0. Pour un système hôte, une bonne valeur est 72 (couches application + de bout en bout). Si cette directive n'est pas spécifiée, aucune valeur ne sera rapportée pour l'objet sysServices.0.
sysDescr CHAÎNE
sysObjectID OID
définit la description du système ou l'identifiant d'objet pour l'agent. Bien que ces objets MIB ne soient pas inscriptibles via SNMP, ces directives peuvent être utilisées par un administrateur réseau pour configurer des valeurs appropriées pour eux.

Groupe Interfaces

interface NOM TYPE VITESSE
peut être utilisé pour fournir des paramètres de type et de vitesse appropriés pour les interfaces pour lesquelles l'agent ne parvient pas à déterminer correctement ces informations. TYPE est une valeur de type telle que donnée dans le MIB IANAifType, et peut être spécifiée numériquement ou par nom (en supposant que ce MIB est chargé).
interface_fadeout DÉLAI
spécifie pendant combien de temps l'agent conserve les entrées dans ifTable après que les interfaces appropriées ont été supprimées du système (typiquement diverses interfaces ppp, tap ou tun). La valeur du délai est en secondes. La valeur par défaut est de 300 (=5 minutes).
interface_replace_old oui
peut être utilisé pour supprimer les entrées existantes dans ifTable lorsqu'une interface portant le même nom apparaît sur le système. Par exemple, lorsque l'interface ppp0 est supprimée, elle est toujours répertoriée dans le tableau pendant la durée de interface_fadeout. Cette option garantit que l'ancienne interface ppp0 est supprimée même avant l'expiration du délai interface_fadeout lorsqu'une nouvelle ppp0 (avec un ifIndex différent) apparaît.

Groupe Ressources Hôte

Cela nécessite que l'agent ait été compilé avec le support du module host (qui est maintenant inclus dans la configuration de compilation par défaut sur les principales plateformes prises en charge).

ignoreDisk CHAÎNE
contrôle quels périphériques disque sont analysés dans le cadre du remplissage de la table hrDiskStorageTable (et hrDeviceTable). Le code d'implémentation HostRes inclut une liste de modèles de périphériques disque appropriés pour le système d'exploitation actuel, dont certains peuvent provoquer le blocage de l'agent lors de la tentative d'ouverture des périphériques disque correspondants. Cela pourrait entraîner un délai d'attente lors de la parcours de ces tables, entraînant potentiellement un comportement incohérent. Cette directive peut être utilisée pour spécifier des périphériques particuliers (individuellement ou avec des caractères génériques) qui ne doivent pas être vérifiés.
Note :
Veuillez consulter la source (host/hr_disk.c) et vérifier les appels Add_HR_Disk_entry pertinents pour un système d'exploitation particulier afin de déterminer la liste des périphériques qui seront analysés.
Le modèle peut inclure une ou plusieurs expressions de caractères génériques. Voir snmpd.examples(5) pour une illustration de la syntaxe des caractères génériques.
ignoremount [-r] CHAÎNE
contrôle quels montages doivent être omis de la table hrStorageTable. Si l'agent Net-SNMP se bloque lors de l'accès à un système de fichiers, ou si le système de fichiers est toujours majoritairement plein (et conduit donc à des alertes inutiles), vous pouvez l'omettre en listant le chemin complet dans cette directive.

Si l'option "-r" est fournie, le modèle peut inclure une ou plusieurs expressions régulières.
skipNFSInHostResources vrai
contrôle si les systèmes de fichiers NFS et similaires à NFS doivent être omis de la table hrStorageTable (vrai ou 1) ou non (faux ou 0, ce qui est la valeur par défaut). Si l'agent Net-SNMP se bloque sur des systèmes de fichiers montés via NFS, vous pouvez essayer de définir cette valeur sur '1'.

Alternativement, un contrôle plus granulaire sur les montages à omettre de la table hrStorageTable peut être obtenu via la directive ignoremount.
storageUseNFS [1|2]
contrôle comment les systèmes de fichiers NFS et similaires à NFS doivent être rapportés dans la table hrStorageTable. comme 'Disques réseau' (1) ou 'Disques fixes' (2). Historiquement, l'agent Net-SNMP a rapporté de tels systèmes de fichiers comme 'Disques fixes', et c'est toujours le comportement par défaut. Définir cette directive sur '1' rapporte ces systèmes de fichiers comme ´Disques réseau', comme requis par le MIB Host Resources.
realStorageUnits
contrôle comment l'agent rapporte hrStorageAllocationUnits, hrStorageSize et hrStorageUsed dans hrStorageTable. Pour les grands lecteurs de stockage avec de petites unités d'allocation, l'agent recalcule ces valeurs afin qu'elles tiennent toutes dans Integer32 et que hrStorageAllocationUnits x hrStorageSize donne la taille réelle du stockage.
Exemple :
Un système de fichiers Linux xfs de 16 To avec des blocs de 4096 octets sera rapporté comme hrStorageAllocationUnits = 8192 et hrStorageSize = 2147483647, donc 8192 x 2147483647 donne la taille réelle du système de fichiers (=16 To).
Définir cette directive sur '1' désactive ce calcul et l'agent rapporte les hrStorageAllocationUnits réels, mais il pourrait rapporter un hrStorageSize incorrect pour les grands lecteurs car la valeur ne tiendra pas dans Integer32. Dans ce cas, hrStorageAllocationUnits x hrStorageSize ne donnera pas la taille réelle du stockage.

Surveillance des processus

Le groupe hrSWRun du MIB Host Resources fournit des informations sur les processus individuels en cours d'exécution sur le système local. La table prTable du MIB UCD-SNMP-MIB complète cela en rapportant sur des services sélectionnés (qui peuvent impliquer plusieurs processus). Cela nécessite que l'agent ait été compilé avec le support du module ucd-snmp/proc (qui est inclus dans la configuration de compilation par défaut).

proc NOM [MAX [MIN]]
surveille le nombre de processus appelés NOM (tel que rapporté par " -acx") en cours d'exécution sur le système local.
Si le nombre de processus nommés est inférieur à MIN ou supérieur à MAX, alors l'instance prErrorFlag correspondante sera définie sur 1, et un message de description approprié sera rapporté via l'instance prErrMessage.
Note :
Cette situation ne déclenchera pas automatiquement un piège pour signaler le problème - voir la section MIB d'événement DisMan plus loin.
Si ni MAX ni MIN ne sont spécifiés, ils seront par défaut à infini et 1 respectivement ("au moins un"). Si seul MAX est spécifié, MIN sera par défaut à 0 ("pas plus de MAX"). Si MAX est 0 (et MIN ne l'est pas), cela indique l'infini ("au moins MIN"). Si MAX et MIN sont tous deux à 0, cela indique un processus qui ne devrait pas être en cours d'exécution.
procfix NOM PROG ARGS
enregistre une commande qui peut être exécutée pour corriger les erreurs avec le processus donné NOM. Celle-ci sera invoquée lorsque l'instance prErrFix correspondante sera définie sur 1.
Note :
Cette commande ne sera pas invoquée automatiquement.
La directive procfix doit être spécifiée après la directive proc correspondante, et ne peut pas être utilisée seule.

Si aucune directive proc n'est définie, alors le parcours de la table prTable échouera (noSuchObject).

Surveillance de l'utilisation du disque

Cela nécessite que l'agent ait été compilé avec le support du module ucd-snmp/dis

k module (qui est inclus dans la configuration de compilation par défaut).

disk PATH [ MINSPACE | MINPERCENT% ]
surveille le disque monté à PATH pour l'espace disque disponible. Les disques montés après le démarrage de l'agent ne seront pas surveillés, sauf si l'option includeAllDisks est spécifiée.
Le seuil minimum peut être spécifié soit en ko (MINSPACE), soit en pourcentage du disque total (MINPERCENT% avec un caractère '%'), la valeur par défaut étant 100ko si aucun des deux n'est spécifié. Si l'espace disque libre tombe en dessous de ce seuil, l'instance dskErrorFlag correspondante sera définie à 1, et un message de description approprié sera rapporté via l'instance dskErrorMsg.
Note :
Cette situation ne déclenchera pas automatiquement un piège pour signaler le problème - voir la section DisMan Event MIB plus loin.
includeAllDisks MINPERCENT%
configure la surveillance de tous les disques trouvés sur le système, en utilisant le seuil spécifié (en pourcentage). La table dskTable est mise à jour dynamiquement, les disques démontés disparaissent de la table et les nouveaux disques montés sont ajoutés à la table. Le seuil pour les disques individuels peut être ajusté à l'aide des directives disk appropriées (qui peuvent être placées avant ou après la directive includeAllDisks).
Note :
Que les directives disk apparaissent avant ou après includeAllDisks peut affecter l'indexation de la table dskTable.
Une seule directive includeAllDisks doit être spécifiée - toute copie ultérieure sera ignorée.
La liste des disques montés sera déterminée à partir de HOST-RESOURCES-MIB::hrFSTable.

Si aucune directive disk ou includeAllDisks n'est définie, la traversée de la table dskTable échouera (noSuchObject).

Surveillance des E/S disque

Cela nécessite que l'agent ait été compilé avec le support du module ucd-snmp/diskio (qui n'est pas inclus dans la configuration de compilation par défaut).

Par défaut, tous les périphériques blocs connus du système d'exploitation sont inclus dans la table diskIOTable. Sur les plateformes autres que Linux, ce module n'a pas de directives de configuration.

Sur les systèmes Linux, il est possible d'exclure plusieurs classes de périphériques blocs de la table diskIOTable afin d'éviter d'encombrer la table avec des statistiques nulles inutiles pour les pseudo-périphériques qui ne sont souvent pas utilisés mais qui sont configurés par défaut pour exister dans la plupart des distributions Linux récentes.

diskio_exclude_fd yes
Exclut tous les périphériques blocs de lecteurs de disquettes Linux, dont les noms commencent par "fd", par exemple "fd0"
diskio_exclude_loop yes
Exclut tous les périphériques blocs de boucle Linux, dont les noms commencent par "loop", par exemple "loop0"
diskio_exclude_ram yes
Exclut tous les périphériques blocs de disque RAM Linux, dont les noms commencent par "ram", par exemple "ram0"

Sur les systèmes Linux, il est également possible de ne signaler que les périphériques explicitement acceptés. Le traitement des données de la table diskIOTable peut prendre un temps considérable sur les systèmes comportant des dizaines de milliers de périphériques blocs, et accepter uniquement ceux qui sont importants évite une consommation CPU importante.

diskio <device>
Active la liste d'acceptation des périphériques et ajoute le périphérique à la liste d'acceptation. Seuls les périphériques explicitement acceptés seront signalés. Cette option peut être utilisée plusieurs fois.

Surveillance de la charge système

Cela nécessite que l'agent ait été compilé avec le support du module ucd-snmp/loadave ou du module ucd-snmp/memory (qui sont tous deux inclus dans la configuration de compilation par défaut).

load MAX1 [MAX5 [MAX15]]
surveille la charge moyenne du système local, en spécifiant des seuils pour les moyennes sur 1 minute, 5 minutes et 15 minutes. Si l'une de ces charges dépasse la valeur maximale associée, l'instance laErrorFlag correspondante sera définie à 1, et un message de description approprié sera rapporté via l'instance laErrMessage.
Note :
Cette situation ne déclenchera pas automatiquement un piège pour signaler le problème - voir la section DisMan Event MIB plus loin.
Si le seuil MAX15 est omis, il prendra par défaut la valeur MAX5. Si MAX5 et MAX15 sont tous deux omis, ils prendront par défaut la valeur MAX1. Si cette directive n'est pas spécifiée, les trois seuils prendront par défaut la valeur DEFMAXLOADAVE.
Si une valeur de seuil de 0 est donnée, l'agent ne signalera pas d'erreurs via les instances laErrorFlag ou laErrMessage concernées, quelle que soit la charge actuelle.

Contrairement aux directives proc et disk, la traversée de la table laTable réussira (en supposant que le module ucd-snmp/loadave ait été configuré dans l'agent), même si la directive load n'est pas présente.

swap MIN
surveille la quantité d'espace d'échange disponible sur le système local. Si celle-ci tombe en dessous du seuil spécifié (MIN ko), l'objet memErrorSwap sera défini à 1, et un message de description approprié sera rapporté via memSwapErrorMsg.
Note :
Cette situation ne déclenchera pas automatiquement un piège pour signaler le problème - voir la section DisMan Event MIB plus loin.
Si cette directive n'est pas spécifiée, le seuil par défaut est de 16 Mo.

Surveillance des fichiers journaux

Cela nécessite que l'agent ait été compilé avec le support du module ucd-snmp/file ou ucd-snmp/logmatch (qui sont tous deux inclus dans la configuration de compilation par défaut).

file FILE [MAXSIZE]
surveille la taille du fichier spécifié (en ko). Si MAXSIZE est spécifié, et que la taille du fichier dépasse ce seuil, l'instance fileErrorFlag correspondante sera définie à 1, et un message de description approprié sera rapporté via l'instance fileErrorMsg.
Note :
Cette situation ne déclenchera pas automatiquement un piège pour signaler le problème - voir la section DisMan Event MIB plus loin.
Note : Un maximum de 20 fichiers peuvent être surveillés.
Note : Si aucune directive file n'est définie, la traversée de la table fileTable échouera (noSuchObject).
logmatch NAME FILE CYCLETIME REGEX
surveille le fichier spécifié pour les occurrences du modèle REGEX spécifié. La position du fichier est stockée en interne, de sorte que le fichier entier n'est lu qu'initialement, chaque passage ultérieur ne lira que les nouvelles lignes ajoutées au fichier depuis la dernière lecture.
NAME
nom de l'instance logmatch (apparaîtra sous logMatchName dans logMatch/logMatchTable/logMatchEntry/logMatchName dans l'arborescence MIB de ucd-snmp)
FILE
chemin absolu du fichier journal à surveiller. Notez que ce chemin peut contenir des directives de date/heure (comme dans la commande UNIX 'date'). Voir la page de manuel de 'strftime' pour les différentes directives acceptées.
CYCLETIME
intervalle de temps pour chaque lecture de fichier journal et mise à jour des variables internes en secondes. Note : une opération SNMPGET* déclenchera également une lecture immédiate du fichier journal et une mise à jour des variables.
REGEX
l'expression régulière à utiliser. Note : N'entourez PAS l'expression régulière de guillemets, même s'il y a des espaces dans l'expression, car les guillemets feront également partie du modèle à faire correspondre !
Exemple :
logmatch apache-GETs /usr/local/apache/logs/access.log-%Y-%m-%d 60 GET.*HTTP.*
Cette instance logmatch est nommée 'apache-GETs', utilise 'GET.*HTTP.*' comme expression régulière et elle surveillera le fichier nommé (en supposant qu'aujourd'hui soit le 6 mai 2009) : '/usr/local/apache/logs/access.log-2009-05-06', demain elle cherchera 'access.log-2009-05-07'. Le fichier journal est lu toutes les 60 secondes.
Note : Un maximum de 250 directives logmatch peuvent être spécifiées.
Note : Si aucune directive logmatch n'est définie, la traversée de la table logMatchTable échouera (noSuchObject).

Surveillance ACTIVE

Le comportement habituel d'un agent SNMP est d'attendre les requêtes SNMP entrantes et d'y répondre - si aucune requête n'est reçue, un agent n'initie généralement aucune action. Cette section décrit diverses directives qui peuvent configurer snmpd pour jouer un rôle plus actif.

Gestion des Notifications

trapcommunity STRING
définit la chaîne de communauté par défaut à utiliser lors de l'envoi de pièges. Notez que cette directive doit être utilisée avant toute directive de destination de piège basée sur la communauté qui en a besoin.
trapsink [-profile p] [-name n] [-tag t] [-s src] HOST [COMMUNITY [PORT]]
trap2sink [-profile p] [-name n] [-tag t] [-s src] HOST [COMMUNITY [PORT]]
informsink [-profil p] [-nom n] [-tag t] [-s src] HOTE [COMMUNAUTE [PORT]]
définit l'adresse d'un récepteur de notifications auquel doivent être envoyés respectivement les TRAPs SNMPv1, les TRAP2s SNMPv2c ou les notifications INFORM SNMPv2. Voir la section ADRESSES D'ÉCOUTE de la page de manuel snmpd(8) pour plus d'informations sur le format des adresses d'écoute. Si COMMUNITY n'est pas spécifié, la dernière chaîne trapcommunity sera utilisée.
Si l'adresse de transport n'inclut pas de spécification de port explicite, alors PORT sera utilisé. Si ce n'est pas spécifié, le port de trap SNMP bien connu (162) sera utilisé.
Note :
Ce mécanisme est déprécié, et le port d'écoute doit être spécifié via la spécification de transport HOTE à la place.
Les paramètres optionnels nom et tag spécifient le nom ou le tag qui sera utilisé pour les entrées de table SNMP-NOTIFICATION-MIB. Le profil spécifie quelle entrée de profil de filtre de notification sera utilisée pour filtrer les notifications sortantes. (Voir notificationFilter)
Le paramètre optionnel src spécifie l'adresse source qui sera utilisée lors de l'envoi du paquet de trap à ce récepteur. Il est spécifié comme une <adresse-transport>, en utilisant le même <spécificateur-transport> que l'HOTE de destination. Voir la section ADRESSES D'ÉCOUTE de la page de manuel snmpd(8) pour plus d'informations sur le format.
Si plusieurs directives de récepteur sont spécifiées, plusieurs copies de chaque notification (dans les formats appropriés) seront générées.
Note :
Il n'est pas normalement approprié de spécifier deux (ou trois) directives de récepteur avec la même destination.
trapsess [-profil p] [-nom n] [-tag t] [-s src] [ARGUMENTS_SNMPCMD] HOTE
fournit un mécanisme plus générique pour définir les destinations de notification. ARGUMENTS_SNMPCMD doit contenir les options de ligne de commande requises pour une commande snmptrap (ou snmpinform) équivalente pour envoyer la notification souhaitée. L'option -Ci peut être utilisée (avec -v2c ou -v3) pour générer une notification INFORM plutôt qu'un TRAP non acquitté.
Les paramètres optionnels nom et tag spécifient le nom ou le tag qui sera utilisé pour les entrées de table SNMP-NOTIFICATION-MIB. Le profil spécifie quelle entrée de profil de filtre de notification sera utilisée pour filtrer les notifications sortantes. (Voir notificationFilter)
C'est la directive appropriée pour définir les récepteurs de traps SNMPv3. Voir http://www.net-snmp.org/tutorial/tutorial-5/commands/snmptrap-v3.html pour plus d'informations sur le comportement des notifications SNMPv3.
notificationFilter NOM OID MASQUE TYPE
spécifie un profil de filtre de notification SNMP-NOTIFICATION-MIB, qui peut être utilisé pour filtrer les traps. TYPE doit être inclus ou exclu. Quelques exemples :
notificationFilter all_ok .1.3 0x00 inclus
notificationFilter no_coldstart .1.3 0x00 inclus
notificationFilter no_coldstart .1.3.6.1.6.3.1.1.5.1 0x00 exclu
trapsink -profil no_coldstart 192.168.1.3:3162 secret3
authtrapenable {1|2}
détermine s'il faut générer des traps d'échec d'authentification (enabled(1)) ou non (disabled(2) - le défaut). Normalement l'objet MIB correspondant (snmpEnableAuthenTraps.0) est en lecture/écriture, mais spécifier cette directive le rend en lecture seule, et les tentatives de définir la valeur via des requêtes SET entraîneront une réponse d'erreur notWritable.

v1trapaddress HOTE
définit l'adresse de l'agent, qui est insérée dans les TRAPs SNMPv1. Une adresse IPv4 locale arbitraire est choisie si cette option est omise. Cette option est principalement utile lorsque l'agent n'est visible du monde extérieur que par une adresse spécifique (par exemple, en raison d'une traduction d'adresses réseau ou d'un pare-feu).

DisMan Event MIB

Les directives précédentes peuvent être utilisées pour configurer où les traps doivent être envoyés, mais ne concernent pas quand envoyer ces traps (ou quels traps doivent être générés). C'est le domaine de l'Event MIB - développée par le groupe de travail Distributed Management (DisMan) de l'IETF.

Cela nécessite que l'agent ait été compilé avec le support du module disman/event (qui est maintenant inclus dans la configuration de compilation par défaut pour la dernière distribution).

Note :
Le comportement de la dernière implémentation diffère à quelques détails près du code précédent - rien de trop significatif, mais les scripts existants pourraient nécessiter quelques ajustements mineurs.
iquerySecName NOM
agentSecName NOM
spécifie le nom d'utilisateur SNMPv3 par défaut, à utiliser lors des requêtes internes pour récupérer toute information nécessaire (soit pour évaluer l'expression surveillée, soit pour construire une charge utile de notification). Ces requêtes internes utilisent toujours SNMPv3, même si les requêtes normales de l'agent sont effectuées en utilisant SNMPv1 ou SNMPv2c.
Notez que cet utilisateur doit également être créé explicitement (createUser) et disposer des droits d'accès appropriés (par exemple, rouser). Cette directive concerne uniquement la définition de quel utilisateur doit être utilisé - pas sa configuration réelle.
monitor [OPTIONS] NOM EXPRESSION
définit un objet MIB à surveiller. Si la condition EXPRESSION est remplie (voir ci-dessous), cela déclenchera l'événement correspondant, et enverra une notification ou appliquera une affectation SET (ou les deux). Notez que l'événement ne sera déclenché qu'une seule fois, lorsque l'expression correspond pour la première fois. Cette entrée de surveillance ne se déclenchera plus jusqu'à ce que la condition surveillée devienne d'abord fausse, puis corresponde à nouveau. NOM est un nom administratif pour cette expression, et est utilisé pour indexer la mteTriggerTable (et les tables associées). Chaque ligne de surveillance doit avoir un NOM unique. Les lignes de surveillance avec un nom dupliqué sont rejetées et provoquent un avertissement de doublon d'index dans le journal de snmpd. Notez également que de telles surveillances utilisent une requête SNMPv3 interne pour récupérer les valeurs surveillées (même si les requêtes d'agent normales utilisent typiquement SNMPv1 ou SNMPv2c). Voir le jeton iquerySecName décrit ci-dessus.
EXPRESSION
Il existe trois types d'expressions de surveillance prises en charge par l'Event MIB - tests d'existence, booléens et seuils.
OID | ! OID | != OID
définit un test de surveillance d'existence(0). Un OID nu spécifie un test de présence(0), qui se déclenchera lorsqu'une instance de l'OID surveillé est créée. Une expression de la forme ! OID spécifie un test d'absence(1), qui se déclenchera lorsque l'OID surveillé est supprimé. Une expression de la forme != OID spécifie un test de changement(2), qui se déclenchera chaque fois que la ou les valeurs surveillées changent. Notez qu'il doit y avoir un espace avant le jeton OID.
OID OP VALEUR
définit un test de surveillance booléen(1). OP doit être l'un des opérateurs de comparaison définis (!=, ==, <, <=, >, >=) et VALEUR doit être une valeur entière par rapport à laquelle comparer. Notez qu'il doit y avoir des espaces autour du jeton OP. Une comparaison telle que OID !=0 ne sera pas gérée correctement.
OID MIN MAX [DMIN DMAX]
définit un test de surveillance de seuil(2). MIN et MAX sont des valeurs entières, spécifiant les seuils inférieur et supérieur. Si la valeur de l'OID surveillé tombe en dessous du seuil inférieur (MIN) ou dépasse le seuil supérieur (MAX), alors l'entrée de surveillance déclenchera l'événement correspondant.
Notez que l'événement de seuil ascendant ne sera réactivé que lorsque la valeur surveillée tombera en dessous du seuil inférieur (MIN). De même, l'événement de seuil descendant sera réactivé par le seuil supérieur (MAX).
Les paramètres optionnels DMIN et DMAX configurent une paire de tests de seuils similaires, mais travaillant avec les différences delta entre les valeurs d'échantillons successifs.
OPTIONS
Il existe diverses options pour contrôler le comportement de l'expression surveillée. Celles-ci comprennent :
-D
indique que l'expression doit être évaluée en utilisant les différences delta entre les valeurs d'échantillons (plutôt que les valeurs elles-mêmes).
-d OID
-di OID
spécifie un marqueur de discontinuité pour valider les différences delta. Une instance d'objet -di sera utilisée exactement telle quelle. Un objet -d aura les sous-identifiants d'instance de l'objet d'expression (masqué) correspondant ajoutés. Si le drapeau -I est spécifié, alors il n'y a pas de différence entre ces deux options.
Cette option implique également -D.
-e EVENEMENT
spécifie l'événement à invoquer lorsque cette entrée de surveillance est déclenchée. Si cette option n'est pas fournie, l'entrée de surveillance générera une des notifications standard définies dans la DISMAN-EVENT-MIB.
-I
indique que l'expression surveillée doit être appliquée à l'OID spécifié comme une seule instance. Par défaut, l'OID sera traité comme un objet masqué, et la surveillance sera étendue pour couvrir toutes les instances correspondantes.
-i OID< /a>
-o OID
définit des varbinds supplémentaires à ajouter à la charge utile de la notification lorsque ce moniteur se déclenche. Pour une expression avec un caractère générique, le suffixe de l'instance correspondante sera ajouté à tous les OID spécifiés à l'aide de -o, tandis que les OID spécifiés à l'aide de -i seront traités comme des instances exactes. Si l'indicateur -I est spécifié, il n'y a alors aucune différence entre ces deux options.
Voir strictDisman pour les détails de l'ordre des charges utiles de notification.
-r FRÉQUENCE
surveille l'expression donnée toutes les FRÉQUENCE, où FRÉQUENCE est en secondes ou éventuellement suivie de l'un des suffixes suivants : s (pour secondes), m (pour minutes), h (pour heures), d (pour jours) ou w (pour semaines). Par défaut, l'expression sera évaluée toutes les 600s (10 minutes).
-S
indique que l'expression de surveillance ne doit pas être évaluée lors du démarrage initial de l'agent. La première évaluation sera effectuée une fois que le premier intervalle de répétition aura expiré.
-s
indique que l'expression de surveillance doit être évaluée lors du démarrage initial de l'agent. C'est le comportement par défaut.
Note :
Les notifications déclenchées par cette évaluation initiale seront envoyées avant le piège coldStart.
-u SECNAME
spécifie un nom de sécurité à utiliser pour l'analyse de l'hôte local, au lieu de iquerySecName par défaut. Encore une fois, cet utilisateur doit être explicitement créé et disposer des droits d'accès appropriés.
notificationEvent ENAME NOTIFICATION [-m] [-i OID | -o OID ]*
définit un événement de notification nommé ENAME. Celui-ci peut être déclenché à partir d'une entrée monitor donnée en spécifiant l'option -e ENAME (voir ci-dessus). NOTIFICATION doit être l'OID de la définition NOTIFICATION-TYPE pour la notification à générer.
Si l'option -m est donnée, la charge utile de la notification inclura les varbinds standard tels que spécifiés dans la clause OBJECTS de la définition MIB de la notification. Cette option doit venir après l'OID de NOTIFICATION (et le fichier MIB pertinent doit être disponible et chargé par l'agent). Sinon, ces varbinds doivent être listés explicitement (soit ici, soit dans la directive monitor correspondante).
Les options -i OID et -o OID spécifient des varbinds supplémentaires à ajouter à la charge utile de la notification, après la liste standard. Si l'entrée de moniteur qui a déclenché cet événement impliquait une expression avec un caractère générique, le suffixe de l'instance correspondante sera ajouté à tous les OID spécifiés à l'aide de -o, tandis que les OID spécifiés à l'aide de -i seront traités comme des instances exactes. Si l'indicateur -I a été spécifié pour la directive monitor, il n'y a alors aucune différence entre ces deux options.
setEvent ENAME [-I] OID = VALEUR
définit un événement de réglage nommé ENAME, en attribuant la VALEUR (entière) à l'OID spécifié. Ceci peut être déclenché à partir d'une entrée monitor donnée en spécifiant l'option -e ENAME (voir ci-dessus).
Si l'entrée de moniteur qui a déclenché cet événement impliquait une expression avec un caractère générique, le suffixe de l'instance correspondante sera normalement ajouté à l'OID. Si l'indicateur -I a été spécifié pour la directive monitor ou setEvent, l'OID spécifié sera considéré comme une instance unique exacte.
strictDisman yes
La définition des notifications SNMP stipule que les varbinds définis dans la clause OBJECTS doivent venir en premier (dans l'ordre spécifié), suivis des varbinds "supplémentaires" que le générateur de notification juge utiles. L'approche la plus naturelle serait d'associer ces varbinds obligatoires à l'entrée notificationEvent, et d'ajouter à la fin de cette liste tous les varbinds associés à l'entrée de moniteur qui a déclenché la notification. C'est le comportement par défaut de l'implémentation Net-SNMP de l'Event MIB.
Malheureusement, les spécifications de la DisMan Event MIB stipulent en fait que les varbinds liés au déclenchement doivent venir en premier, suivis de ceux liés à l'événement. Cette directive peut être utilisée pour rétablir ce comportement strictement correct (mais inapproprié).
Note :
L'ordre strict DisMan peut entraîner la génération de listes de charges utiles de notification invalides si le drapeau notificationEvent -n est utilisé conjointement avec les options de varbind monitor -o (ou -i).
Si aucune entrée monitor ne spécifie de varbinds de charge utile, alors le réglage de cette directive est sans importance.
linkUpDownNotifications yes
configurera les tables Event MIB pour surveiller ifTable afin de détecter la mise en marche ou l'arrêt des interfaces réseau, et déclencher une notification linkUp ou linkDown en conséquence.
Ceci est exactement équivalent à la configuration :
notificationEvent  linkUpTrap    linkUp   ifIndex ifAdminStatus ifOperStatus
notificationEvent  linkDownTrap  linkDown ifIndex ifAdminStatus ifOperStatus
monitor  -r 60 -e linkUpTrap   "Générer linkUp" ifOperStatus != 2
monitor  -r 60 -e linkDownTrap "Générer linkDown" ifOperStatus == 2
defaultMonitors yes
configurera les tables Event MIB pour surveiller les diverses tables UCD-SNMP-MIB pour détecter les problèmes (comme indiqué par les objets de colonne xxErrFlag appropriés).
Ceci est exactement équivalent à la configuration :
monitor	-o prNames -o prErrMessage "table de processus" prErrorFlag != 0
monitor	-o memErrorName -o memSwapErrorMsg "mémoire" memSwapError != 0
monitor	-o extNames -o extOutput "table ext" extResult != 0
monitor	-o dskPath -o dskErrorMsg "table dsk" dskErrorFlag != 0
monitor	-o laNames -o laErrMessage  "table la" laErrorFlag != 0
monitor	-o fileName -o fileErrorMsg  "table file" fileErrorFlag != 0

Dans ces deux derniers cas, le fichier snmpd.conf doit également contenir une directive iquerySecName, ainsi qu'une entrée createUser correspondante et une configuration de contrôle d'accès appropriée.

DisMan Schedule MIB

Le groupe de travail DisMan a également produit un mécanisme pour planifier des actions particulières (une affectation SET spécifiée) à des moments donnés. Ceci nécessite que l'agent ait été compilé avec le support du module disman/schedule (qui est inclus dans la configuration de build par défaut pour la distribution la plus récente).

Il existe trois façons de spécifier l'action planifiée :

repeat FRÉQUENCE OID = VALEUR
configure une affectation SET de la VALEUR (entière) à l'instance MIB OID, à exécuter toutes les FRÉQUENCE secondes, où FRÉQUENCE est en secondes ou éventuellement suivie de l'un des suffixes suivants : s (pour secondes), m (pour minutes), h (pour heures), d (pour jours) ou w (pour semaines).
cron MINUTE HEURE JOUR MOIS JOUR_SEMAINE OID = VALEUR
configure une affectation SET de la VALEUR (entière) à l'instance MIB OID, à exécuter aux heures spécifiées par les champs MINUTE à JOUR_SEMAINE. Ceux-ci suivent le même modèle que les champs équivalents de crontab(5).
Note :
Ces champs doivent être spécifiés sous forme de liste de valeurs numériques (séparées par des virgules). Les valeurs nommées pour les champs MOIS et JOUR_SEMAINE ne sont pas prises en charge, pas plus que les plages de valeurs. Un caractère générique peut être spécifié sous la forme '*'.
Le champ JOUR peut également accepter des valeurs négatives, pour indiquer les jours en comptant à rebours depuis la fin du mois.
at MINUTE HEURE JOUR MOIS JOUR_SEMAINE OID = VALEUR
configure une affectation SET unique, à exécuter lors de la première heure correspondante telle que spécifiée par les champs MINUTE à JOUR_SEMAINE. L'interprétation de ces champs est exactement la même que pour la directive cron.

Distribution des données via les Notifications

Note : cette fonctionnalité n'est disponible que si le module MIB deliver/deliverByNotify a été compilé dans l'agent

Dans certaines situations, il peut être avantageux de distribuer des données SNMP via des Notifications SNMP (TRAPs et INFORMs) plutôt que par le processus typique où le gestionnaire émet des requêtes pour les données (via GET et GETNEXT). Les raisons de le faire sont nombreuses, mais souvent des cas limites. La raison la plus courante de vouloir ce comportement pourrait être de surveiller des périphériques qui résident derrière des NAT ou des pare-feu qui empêchent le trafic SNMP entrant.

Il convient de noter que bien que la plupart des logiciels de gestion soient capables d'enregistrer les notifications, très peu (voire aucun) logiciel de gestion ne mettront à jour leur "base de connaissances" en fonction du contenu des notifications SNMP. C'est-à-dire qu'ils ne mettront pas à jour (par exemple) l'historique des compteurs de trafic de l'interface utilisé pour produire des graphiques. La plupart des progiciels de gestion de réseau plus importants disposent d'une base de données distincte pour stocker les données reçues via les requêtes SNMP (GET et GETNEXT) par rapport à celles reçues des notifications. Une recherche sur les capacités de votre logiciel de station de gestion est nécessaire avant de supposer que cette fonctionnalité résoudra vos besoins de distribution de données.

Les notifications générées via ce mécanisme seront envoyées à l'ensemble standard des cibles de notification configurées. Voir la section "Gestion des notifications" de ce document pour plus d'informations.

Pour diviser les notifications en tailles de paquets gérables, utilisez le drapeau -s pour spécifier le nombre approximatif d'octets maximum que doit contenir un message de notification. S'il faut plus de MAXSIZE octets, plusieurs notifications seront envoyées pour délivrer les données. Notez que les calculs pour garantir la taille maximale sont des approximations et il n'est donc pas absolument garanti qu'elles soient inférieures à cette taille, laissez donc une marge de précaution si vous devez absolument éviter la fragmentation. Une valeur de -1 force tout dans un seul message, quelle que soit sa taille. EXTENSION DES FONCTIONNALITÉS DE L'AGENT

L'une des premières caractéristiques distinctives de la suite UCD d'origine était la capacité d'étendre les fonctionnalités de l'agent - pas seulement en recompilant avec du code pour de nouveaux modules MIB, mais aussi en configurant l'agent en cours d'exécution pour signaler des informations supplémentaires. Il existe un certain nombre de techniques pour cela, notamment :

  • lancement de commandes externes (exec, extend, pass)
  • chargement dynamique de nouveau code (Perl embarqué, dlmod)
  • communication avec d'autres agents (proxy, SMUX, AgentX)

Commandes d'extension arbitraires

Le premier mécanisme d'extension était la capacité d'exécuter des commandes ou des scripts shell arbitraires. Ces commandes n'ont pas besoin d'être conscientes des opérations SNMP, ni de se conformer à un comportement particulier - les structures MIB sont conçues pour accueillir toute forme de sortie de commande. L'utilisation de ce mécanisme nécessite que l'agent ait été construit avec la prise en charge des modules ucd-snmp/extensible et/ou agent/extend (qui sont tous deux inclus dans la configuration de compilation par défaut).

exec [MIBOID] NOM PROG ARGS
sh [MIBOID] NOM PROG ARGS
invoque le PROG nommé avec les arguments ARGS. Par défaut, le code de sortie et la première ligne de sortie de la commande seront signalés via la table extTable, en rejetant toute sortie supplémentaire.
Note :
Les entrées de cette table apparaissent dans l'ordre où elles sont lues à partir du fichier de configuration. Cela signifie que l'ajout de nouvelles directives exec (ou sh) et le redémarrage de l'agent peuvent affecter l'indexation des autres entrées.
L'argument PROG pour les directives exec doit être le chemin complet vers un binaire réel, car il est exécuté via l'appel système exec(). Pour invoquer un script shell, utilisez plutôt la directive sh.
Si MIBOID est spécifié, les résultats seront enracinés à ce point dans l'arbre OID, renvoyant l'instruction de sortie comme MIBOID.100.0 et la sortie complète de la commande dans une pseudo-table basée sur MIBNUM.101 - avec une 'ligne' pour chaque ligne de sortie.
Note :
La disposition de cette forme « relocalisable » de sortie exec (ou sh) ne forme pas strictement une structure MIB valide. Ce mécanisme est en cours de dépréciation - veuillez plutôt consulter la directive extend (décrite ci-dessous).
L'agent ne met pas en cache le code de sortie ni la sortie du programme exécuté.
execfix NOM PROG ARGS
enregistre une commande qui peut être invoquée à la demande - généralement pour répondre ou corriger des erreurs avec l'entrée exec ou sh correspondante. Lorsque l'instance extErrFix pour une entrée NAMED donnée est définie sur la valeur entière de 1, cette commande sera appelée.
Note :
Cette directive ne peut être utilisée qu'en combinaison avec une directive exec ou sh correspondante, qui doit être définie en premier. Tenter de définir une directive execfix non accompagnée échouera.

Les extensions exec et sh ne peuvent être configurées que via le fichier snmpd.conf. Elles ne peuvent pas être configurées via des requêtes SNMP SET.

extend [-cacheTime TIME] [-execType TYPE] [MIBOID] NOM PROG ARGS
fonctionne de manière similaire à la directive exec, mais avec un certain nombre d'améliorations. Les tables MIB (nsExtendConfigTable, etc.) sont indexées par le jeton NOM, elles ne sont donc pas affectées par l'ordre dans lequel les entrées sont lues à partir des fichiers de configuration. Il y a deux tables de résultats - l'une (nsExtendOutput1Table) contenant le code de sortie, la première ligne et la sortie complète (en tant que chaîne unique) pour chaque entrée extend, et l'autre (nsExtendOutput2Table) contenant la sortie complète sous forme d'une série de lignes distinctes.
Si -cacheTime est spécifié, son argument est utilisé comme délai de mise en cache (en secondes entières) pour cette entrée extend. Ce mécanisme fournit un moyen non volatil de spécifier le délai de mise en cache.
Si -execType est spécifié et a la valeur sh, cette entrée extend sera exécutée dans un shell. Sinon, elle sera exécutée dans le mode exec par défaut. Ce mécanisme fournit un moyen non volatil de spécifier le type d'exécution.
Si MIBOID est spécifié, les tables de configuration et de résultats seront enracinées à ce point dans l'arbre OID, mais seront par ailleurs structurées exactement de la même manière. Cela signifie que plusieurs directives extend distinctes peuvent spécifier la même racine MIBOID, sans conflit.
Le code de sortie et la sortie sont mis en cache pour chaque entrée individuellement, et peuvent être effacés (et le comportement de mise en cache configuré) à l'aide de la table nsCacheTable.
extendfix NOM PROG ARGS
enregistre une commande qui peut être invoquée à la demande, en définissant l'instance nsExtendRunType appropriée sur la valeur run-command(3). Contrairement à l'équivalent execfix, cette directive n'a pas besoin d'être associée à une entrée extend correspondante, et peut apparaître seule.

Les directives extend et extendfix peuvent être configurées dynamiquement, à l'aide de requêtes SNMP SET sur la MIB NET-SNMP-EXTEND-MIB.

Commandes d'extension spécifiques aux MIB

Le premier groupe de directives d'extension invoque des commandes arbitraires et s'appuie sur la structure MIB (et les applications de gestion) pour être suffisamment flexible pour accueillir et interpréter la sortie. C'est un moyen pratique de rendre les informations disponibles rapidement et simplement, mais cela est inutile lors de l'implémentation d'objets MIB spécifiques, où l'extension doit se conformer à la structure de la MIB (plutôt que l'inverse). Les mécanismes d'extension restants concernent tous ces situations spécifiques aux MIB - en commençant par les scripts de « passage ». L'utilisation de ce mécanisme nécessite que l'agent ait été construit avec la prise en charge des modules ucd-snmp/pass et ucd-snmp/pass_persist (qui sont tous deux inclus dans la configuration de compilation par défaut).

pass [-p priority] MIBOID PROG
passera le contrôle du sous-arbre enraciné à MIBOID au programme PROG spécifié. Les requêtes GET et GETNEXT pour les OID dans cet arbre déclencheront cette commande, appelée comme suit :
PROG -g OID
PROG -n OID
respectivement, où OID est l'OID demandé. La commande PROG doit renvoyer la réponse varbind sous forme de trois lignes distinctes imprimées sur stdout - la première ligne doit être l'OID de la valeur renvoyée, la seconde doit être son TYPE (une des chaînes de caractères integer, gauge, counter, timeticks, ipaddress, objectid, octet, ou string ), et la troisième doit être la valeur elle-même. (Note : les octets sont envoyés sous forme de chaînes hexadécimales séparées par des espaces, par exemple « 00 3f dd 00 c6 be »).
Si la commande ne peut pas renvoyer une varbind appropriée - par exemple, si l'OID spécifié ne correspondait pas à une instance valide pour une requête GET, ou s'il n'y avait pas d'instances suivantes pour un GETNEXT - elle devrait se terminer sans produire aucune sortie. Cela entraînera une erreur SNMP noSuchName, ou une exception noSuchInstance.
Note :
Le type SMIv2 counter64 et l'exception SNMPv2 noSuchObject ne sont pas pris en charge.
Une requête SET entraînera l'appel de la commande comme suit :
PROG -s OID TYPE VALUE
où TYPE est l'un des jetons listés ci-dessus, indiquant le type de la valeur passée comme troisième paramètre.
Si l'assignation réussit, la commande PROG doit se terminer sans produire aucune sortie. Les erreurs doivent être indiquées en écrivant

pass MIBOID PROG

passera le contrôle du sous-arbre enraciné à MIBOID à la commande PROG spécifiée. La commande PROG sera lancée une fois pour chaque requête SNMP reçue pour une OID dans le sous-arbre spécifié. Le programme PROG recevra deux lignes sur son entrée standard : la commande (get ou getnext) et l'OID demandée. Il doit répondre en imprimant trois lignes sur sa sortie standard : l'OID du varbind résultant, son TYPE et sa VALEUR. Si la commande ne peut pas retourner de varbind approprié, elle doit imprimer "NONE\n" sur sa sortie standard. Pour les requêtes SET, PROG recevra trois lignes sur stdin : la commande (set), l'OID demandée, puis le type et la valeur (tous deux sur la même ligne). Si l'affectation réussit, la commande doit imprimer "DONE\n" sur stdout. Les erreurs doivent être indiquées en écrivant une des chaînes not-writable, ou wrong-type sur stdout, et l'agent générera la réponse d'erreur appropriée.
Note :
Les autres erreurs SNMPv2 ne sont pas prises en charge.
Dans tous les cas, la commande doit se terminer une fois qu'elle a fini de traiter. Chaque requête (et chaque varbind dans une seule requête) déclenchera une invocation distincte de la commande.
La priorité d'enregistrement par défaut est 127. Elle peut être modifiée en fournissant l'indicateur facultatif -p, les enregistrements de priorité inférieure étant utilisés de préférence aux valeurs de priorité plus élevée.
pass_persist [-p priority] MIBOID PROG
transmettra également le contrôle du sous-arbre enraciné à MIBOID au programme PROG spécifié. Cependant, cette commande continuera à s'exécuter après que la requête initiale ait été traitée, permettant ainsi aux requêtes ultérieures d'être traitées sans les surcoûts de démarrage.
Lors de l'initialisation, PROG recevra la chaîne "PING\n" sur stdin, et devra répondre en imprimant "PONG\n" sur stdout.
Pour les requêtes GET et GETNEXT, PROG recevra deux lignes sur stdin, la commande (get ou getnext) et l'OID demandée. Il devra répondre en imprimant trois lignes sur stdout - l'OID du varbind résultant, le TYPE et la VALEUR elle-même - exactement comme pour la directive pass ci-dessus. Si la commande ne peut pas retourner de varbind approprié, elle devra imprimer "NONE\n" sur stdout (mais continuer à s'exécuter).
Pour les requêtes SET, PROG recevra trois lignes sur stdin, la commande (set) et l'OID demandée, suivies du type et de la valeur (tous deux sur la même ligne). Si l'affectation réussit, la commande doit imprimer "DONE\n" sur stdout. Les erreurs doivent être indiquées en écrivant une des chaînes not-writable, wrong-type, wrong-length, wrong-value ou inconsistent-value sur stdout, et l'agent générera la réponse d'erreur appropriée. Dans tous les cas, la commande doit continuer à s'exécuter.
La priorité d'enregistrement peut être modifiée à l'aide de l'indicateur facultatif -p, tout comme pour la directive pass.

Les extensions pass et pass_persist ne peuvent être configurées que via le fichier snmpd.conf. Elles ne peuvent pas être configurées via des requêtes SNMP SET.

Prise en charge de Perl embarqué

Les programmes utilisant les mécanismes d'extension précédents peuvent être écrits dans n'importe quel langage de programmation pratique, y compris Perl, qui est un choix courant pour les extensions de type pass-through en particulier. Cependant, l'agent Net-SNMP inclut également la prise en charge de la technologie Perl embarqué (similaire à mod_perl pour le serveur Web Apache). Cela permet à l'agent d'interpréter directement les scripts Perl, évitant ainsi la surcharge liée au lancement de processus et à l'initialisation du système Perl lors de la réception d'une requête.

L'utilisation de ce mécanisme nécessite que l'agent ait été compilé avec la prise en charge du mécanisme Perl embarqué, qui ne fait pas partie de l'environnement de compilation par défaut. Il doit être explicitement inclus en spécifiant l'option '--enable-embedded-perl' au script configure lors de la première compilation du paquet.

Si activé, les directives suivantes seront reconnues :

disablePerl true
désactivera complètement la prise en charge de Perl embarqué (par exemple, en cas de problèmes avec l'installation de Perl).
perlInitFile FILE
charge le fichier d'initialisation spécifié (s'il est présent) juste avant que la première directive perl ne soit analysée. S'il n'est pas explicitement spécifié, l'agent recherchera le fichier d'initialisation par défaut /usr/share/snmp/snmp_perl.pl.
Le fichier d'initialisation par défaut crée une instance d'un objet NetSNMP::agent - une variable $agent qui peut être utilisée pour enregistrer des routines de gestionnaire basées sur Perl.
perl EXPRESSION
évalue l'expression donnée. Cela enregistrerait généralement une routine de gestionnaire à appeler lorsqu'une section de l'arbre OID est demandée :
perl use Data::Dumper;
perl sub myroutine  { print "got called: ",Dumper(@_),"\n"; }
perl $agent->register('mylink', '.1.3.6.1.8765', \&myroutine);
Cette expression pourrait également importer un fichier externe :
perl 'do /path/to/file.pl';
ou effectuer tout autre traitement basé sur Perl qui pourrait être nécessaire.

Modules chargeables dynamiquement

La plupart des MIB pris en charge par l'agent Net-SNMP sont implémentés sous forme de modules de code C, qui ont été compilés et liés aux bibliothèques de l'agent lors de la première compilation de la suite. De tels modules d'implémentation peuvent également être compilés indépendamment et chargés dans l'agent en cours d'exécution une fois qu'il a démarré. L'utilisation de ce mécanisme nécessite que l'agent ait été compilé avec la prise en charge du module ucd-snmp/dlmod (qui est inclus dans la configuration de compilation par défaut).

dlmod NOM CHEMIN
chargera le module d'objet partagé à partir du fichier CHEMIN (un nom de fichier absolu) et appellera la routine d'initialisation init_NOM.
Note :
Si le CHEMIN spécifié n'est pas un nom de fichier entièrement qualifié, il sera interprété par rapport à /usr/lib/snmp/dlmod, et .so sera ajouté au nom de fichier.

Cette fonctionnalité peut également être configurée à l'aide de requêtes SNMP SET sur la MIB UCD-DLMOD.

Prise en charge du proxy

Un autre mécanisme pour étendre les fonctionnalités de l'agent consiste à transmettre des requêtes sélectionnées (ou des varbinds sélectionnés) à un autre agent SNMP, qui peut être en cours d'exécution sur le même hôte (probablement en écoute sur un port différent), ou sur un système distant. Cela peut être considéré soit comme l'agent principal déléguant des requêtes à l'agent distant, soit comme agissant en tant que proxy pour celui-ci. L'utilisation de ce mécanisme nécessite que l'agent ait été compilé avec la prise en charge du module ucd-snmp/proxy (qui est inclus dans la configuration de compilation par défaut).

proxy [-Cn NOM_CONTEXTE] [ARGUMENTS_SNMPCMD] HOTE OID [OID_DISTANTE]
transmettra toutes les requêtes entrantes sous OID à l'agent en écoute sur le port spécifié par l'adresse de transport HOTE. Voir la section ADRESSES D'ÉCOUTE dans la page de manuel snmpd(8) pour plus d'informations sur le format des adresses d'écoute.
Note :
Pour proxyser l'arborescence MIB entière, utilisez l'OID .1.3 (pas le niveau supérieur .1)

Les ARGUMENTS_SNMPCMD doivent fournir suffisamment d'informations de version et administratives pour générer une requête SNMP valide (voir snmpcmd(1)).

Note :
La requête proxysée n'utilisera pas les paramètres administratifs de la requête d'origine.

Si un NOM_CONTEXTE est spécifié, cela enregistrera la délégation de proxy dans le contexte nommé de l'agent local. La définition de plusieurs directives proxy pour la même OID mais des contextes différents peut être utilisée pour interroger plusieurs agents distants via un seul proxy, en spécifiant le contexte SNMPv3 approprié dans la requête entrante (ou en utilisant des chaînes de communauté configurées de manière appropriée - voir la directive com2sec).

La spécification du paramètre OID_DISTANTE mappera l'arborescence MIB locale enracinée à OID à un sous-arbre équivalent enraciné à OID_DISTANTE sur l'agent distant.

Sous-agents SMUX

L'agent Net-SNMP prend en charge le protocole SMUX (RFC 1227) pour communiquer avec les sous-agents basés sur SMUX (tels que gated, zebra ou quagga). L'utilisation de ce mécanisme nécessite que l'agent ait été compilé avec la prise en charge du module smux, qui ne fait pas partie de l'environnement de compilation par défaut, et doit être explicitement inclus en spécifiant l'option '--with-mib-modules=smux' au script configure lors de la première compilation du paquet.

Note :
Ce protocole d'extension a été officiellement déprécié au profit d'AgentX (voir ci-dessous).
smuxpeer OID MOTDEPASSE
enregistrera un sous-arbre pour le traitement basé sur SMUX, à authentifier à l'aide du mot de passe MOTDEPASSE. Si un sous-agent (ou "pair") se connecte à l'agent et enregistre ce sous-arbre, les requêtes pour les OIDs à l'intérieur seront transmises à ce sous-agent SMUX pour traitement.
Une entrée appropriée pour un démon de routage OSPF (tel que gated, zebra ou quagga) pourrait être quelque chose comme
smuxpeer .1.3.6.1.2.1.14 motdepasse_ospf
smuxsocket <adresse-IPv4>
définit l'adresse IPv4 pour que les pairs SMUX communiquent avec l'agent Net-SNMP. La valeur par défaut est d'écouter sur toutes les interfaces IPv4 ("0.0.0.0"), sauf si le paquet a été configuré avec "--enable-local-smux" lors de la compilation, ce qui fait qu'il écoute uniquement sur 127.0.0.1 par défaut. SMUX utilise le port TCP bien connu 199.

Notez que l'agent Net-SNMP fonctionnera uniquement comme un agent maître SMUX. Il ne prend pas en charge le rôle d'agent subalterne SMUX.

Sous-agents AgentX

L'agent Net-SNMP prend en charge le protocole AgentX (RFC 2741) dans les rôles de maître et de sous-agent. L'utilisation de ce mécanisme nécessite que l'agent ait été compilé avec la prise en charge du module agentx (qui est inclus dans la configuration de compilation par défaut), et que cette prise en charge soit explicitement activée (par exemple, via le fichier snmpd.conf).

Deux directives sont spécifiquement pertinentes pour fonctionner en tant qu'agent maître AgentX :

>
master agentx
activera la fonctionnalité AgentX et amènera l'agent à commencer à écouter les enregistrements AgentX entrants. Ceci peut également être activé en spécifiant l'option de ligne de commande '-x' (pour spécifier un socket d'écoute alternatif).
agentXPerms SOCKPERMS [DIRPERMS [USER|UID [GROUP|GID]]]
Définit les permissions et la propriété du socket Unix Domain AgentX, et les répertoires parents de ce socket. SOCKPERMS et DIRPERMS doivent être des chiffres octaux (voir chmod(1) ). Par défaut, ce socket ne sera accessible qu'aux sous-agents qui ont le même userid que l'agent.

Il existe une directive spécifiquement pertinente pour l'exécution en tant que sous-agent AgentX :

agentXPingInterval NUM
obligera le sous-agent à essayer de se reconnecter toutes les NUM secondes au maître s'il est déconnecté (ou démarre déconnecté).

Les directives restantes sont pertinentes pour les agents maîtres et sous-agents AgentX :

agentXSocket [<transport-specifier>:]<transport-address>[,...]
définit l'adresse à laquelle l'agent maître écoute, ou à laquelle le sous-agent doit se connecter. La valeur par défaut est le socket Unix Domain "/var/agentx/master". Une autre alternative courante est tcp:localhost:705. Voir la section ADRESSES D'ÉCOUTE dans la page de manuel de snmpd(8) pour plus d'informations sur le format des adresses.
Note :
Spécifier un socket AgentX ne pas active pas automatiquement la fonctionnalité AgentX (contrairement à l'option de ligne de commande '-x').
agentXTimeout NUM
définit la période de temporisation (NUM secondes) pour une requête AgentX. La valeur par défaut est 1 seconde. NUM peut également être spécifié avec un suffixe : s (pour secondes), m (pour minutes), h (pour heures), d (pour jours) ou w (pour semaines).
agentXRetries NUM
définit le nombre de tentatives pour une requête AgentX. La valeur par défaut est 5 tentatives.

net-snmp est livré avec des API C et Perl pour développer votre propre sous-agent AgentX.

AUTRE CONFIGURATION

override [-rw] OID TYPE VALUE
Cette directive vous permet de remplacer un OID particulier par une valeur différente (et éventuellement un type de valeur différent). L'indicateur -rw permettra également aux commandes SET SNMP de modifier sa valeur. (notez que si vous remplacez une fonctionnalité d'origine, cette fonctionnalité sera entièrement perdue. Ainsi les SETs ne feront rien de plus que modifier la valeur interne remplacée et n'effectueront aucune des fonctionnalités d'origine prévues par l'objet MIB. C'est une émulation uniquement.) Un exemple :
override sysDescr.0 octet_str "mon propre sysDescr"
Cette ligne définira la valeur de sysDescr.0 sur "mon propre sysDescr" et la rendra également modifiable avec des SETs SNMP (ce qui est en fait illégal selon les spécifications MIB).
Notez qu'il faut être prudent lors de l'utilisation de ceci. Par exemple, si vous essayez de remplacer une propriété de la 3ème interface dans la ifTable par une nouvelle valeur et que plus tard la numérotation au sein de la ifTable change son ordre d'index, vous rencontrerez des problèmes et votre valeur modifiée n'apparaîtra pas au bon endroit dans la table.
Les TYPEs valides sont : integer, uinteger, octet_str, object_id, counter, null (pour les jauges, utilisez "uinteger" ; pour les chaînes de bits, utilisez "octet_str"). Notez que la définition d'un objet à "null" le supprime effectivement de l'accessibilité. Aucune VALEUR n'est nécessaire si le type d'objet est null.
D'autres types devraient être disponibles à l'avenir.

Si vous essayez de comprendre des aspects des divers modules mib (éventuellement certains que vous avez ajoutés vous-même), ce qui suit peut vous aider à obtenir des informations de débogage utiles. Tout d'abord, veuillez lire la page de manuel snmpd sur l'option -D. Ensuite, le jeton de configuration snmpd.conf suivant, combiné à l'option -D, peut produire une sortie utile :

injectHandler HANDLER nom_module [avantCeci]
Cela insérera de nouveaux gestionnaires dans la section de l'arbre mib référencée par "nom_module". Si "avantCeci" est spécifié, alors le module sera injecté avant le module nommé. Ceci est utile pour positionner un gestionnaire exactement au bon endroit dans la chaîne.
Les types de gestionnaires disponibles pour l'insertion sont :
stash_cache
Met en cache les informations renvoyées par le niveau inférieur. Cela améliore considérablement les performances de l'agent, au prix de la mise en cache des données de sorte qu'elles ne soient plus "en direct" pendant 30 secondes (à l'avenir, cela sera configurable). Notez que cela signifie que snmpd utilisera également plus de mémoire pendant que les informations sont mises en cache. Actuellement, cela ne fonctionne que pour les gestionnaires enregistrés à l'aide du support table_iterator, qui ne concerne que quelques tables mib. Pour l'utiliser, vous devez vous assurer de l'installer avant le point table_iterator dans la chaîne, donc pour ce faire :


injectHandler stash_cache NOM table_iterator

Si vous souhaitez tester une table, essayez de parcourir la nsModuleTable avec et sans cette injection.

debug
Affiche de nombreuses informations de débogage lorsque l'option -Dhelper:debug est passée à l'application snmpd.
read_only
Force la désactivation du support d'écriture pour le module donné.
serialize
Si un module ne parvient pas à gérer plusieurs requêtes correctement (en utilisant la nouvelle API de module 5.0), cela forcera le module à ne recevoir qu'une requête à la fois.
bulk_to_next
Si un module s'enregistre pour gérer le support getbulk, mais pour une raison quelconque ne l'implémente pas correctement, ce module convertira toutes les requêtes getbulk en requêtes getnext avant que le module final ne les reçoive.
dontLogTCPWrappersConnects
Si snmpd a été compilé avec le support TCP Wrapper, il enregistre chaque connexion établie à l'agent. Ce paramètre désactive les messages de journalisation pour les connexions acceptées. Les connexions refusées seront toujours enregistrées.
Trouver les noms de modules
Pour savoir dans quels modules vous pouvez injecter des éléments, exécutez snmpwalk sur la nsModuleTable, ce qui donnera une liste de tous les modules nommés enregistrés dans l'agent.
