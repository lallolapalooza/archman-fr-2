SNMPTRAPD.CONF(5) Net-SNMP SNMPTRAPD.CONF(5)

NOM

snmptrapd.conf - fichier de configuration pour le récepteur de notifications Net-SNMP

DESCRIPTION

Le récepteur de notifications (démon de trappe) Net-SNMP utilise un ou plusieurs fichiers de configuration pour contrôler son fonctionnement et la manière dont les trappes entrantes (et les requêtes INFORM) doivent être traitées. Ce fichier (snmptrapd.conf) peut être situé à plusieurs endroits, comme décrit dans la page de manuel de snmp_config(5).

IMPORTANT

Précédemment, snmptrapd acceptait toutes les notifications entrantes et les enregistrait automatiquement (même sans configuration explicite). À partir de la version 5.3, des vérifications de contrôle d'accès seront appliquées aux notifications entrantes. Si snmptrapd est exécuté sans fichier de configuration approprié (ou sans paramètres de contrôle d'accès équivalents), alors ces trappes NE SERONT PAS traitées. Voir la section CONTRÔLE D'ACCÈS pour plus de détails.

Comme pour la configuration de l'agent, les directives snmptrapd.conf peuvent être divisées en quatre groupes distincts.

COMPORTEMENT DU TRAPD

snmpTrapdAddr [<spécificateur_de_transport>:]<adresse_de_transport>[,...]
définit une liste d'adresses d'écoute sur lesquelles recevoir les notifications SNMP entrantes. Voir la section ADRESSES D'ÉCOUTE dans la page de manuel de snmpd(8) pour plus d'informations sur le format des adresses d'écoute.
Le comportement par défaut est d'écouter sur le port UDP 162 sur toutes les interfaces IPv4.
doNotRetainNotificationLogs yes
désactive la prise en charge de la MIB NOTIFICATION-LOG-MIB. Normalement, le programme snmptrapd conserve un enregistrement des trappes reçues, qui peut être récupéré en interrogeant les tables nlmLogTable et nlmLogvariableTable. Cette directive peut être utilisée pour supprimer ce comportement.
Voir la page de manuel de snmptrapd(8) et la MIB NOTIFICATION-LOG-MIB pour plus de détails.
doNotLogTraps yes
désactive complètement l'enregistrement des notifications. Ceci est utile si l'application snmptrapd doit uniquement exécuter des hooks traphandle et ne doit pas enregistrer les trappes à aucun endroit.
doNotFork yes
ne pas forker à partir du shell appelant.
pidFile CHEMIN
définit un fichier dans lequel stocker l'identifiant du processus du récepteur de notifications. Par défaut, cet identifiant n'est pas sauvegardé.

CONTRÔLE D'ACCÈS

À partir de la version 5.3, il est nécessaire de spécifier explicitement qui est autorisé à envoyer des trappes et des informations au récepteur de notifications (et quels types de traitement ces derniers sont autorisés à déclencher). Ceci utilise une extension du modèle VACM, utilisé dans l'agent SNMP principal.

Il existe actuellement trois types de traitement qui peuvent être spécifiés :

log
enregistrer les détails de la notification - soit dans un fichier spécifié, sur la sortie standard (ou stderr), soit via syslog (ou similaire).
execute
transmettre les détails de la trappe à un programme de traitement spécifié, y compris perl embarqué.
net
transférer la trappe à un autre récepteur de notifications.

Dans les directives suivantes, TYPES sera une liste (séparée par des virgules) d'un ou plusieurs de ces jetons. Le plus souvent, il s'agira généralement de log,execute,net pour couvrir tout style de traitement pour une catégorie de notification particulière. Mais il est tout à fait possible (voire souhaitable) de limiter certaines sources de notifications à un traitement sélectionné uniquement.

authCommunity TYPES COMMUNAUTE [SOURCE [OID | -v VUE ]]
autorise les trappes (et les requêtes INFORM SNMPv2c) avec la communauté spécifiée à déclencher les types de traitement listés. Par défaut, cela autorise le traitement de toute notification utilisant cette communauté. Le champ SOURCE peut être utilisé pour spécifier que la configuration ne doit s'appliquer qu'aux notifications reçues de sources particulières - voir snmpd.conf(5) pour plus de détails.
authUser TYPES [-s MODELE] UTILISATEUR [NIVEAU [OID | -v VUE ]]
autorise les notifications SNMPv3 avec l'utilisateur spécifié à déclencher les types de traitement listés. Par défaut, cela accepte les requêtes authentifiées. (authNoPriv ou authPriv). Le champ NIVEAU peut être utilisé pour autoriser les notifications non authentifiées (noauth), ou pour exiger le chiffrement (priv), tout comme pour l'agent SNMP.
Avec ces deux directives, le champ OID (ou -v VUE) peut être utilisé pour restreindre cette configuration au traitement de notifications particulières.
Note :
Contrairement au traitement VACM décrit dans la RFC 3415, cette vue est uniquement comparée à la valeur snmpTrapOID de la notification entrante. Elle n'est pas appliquée aux varbinds de la charge utile contenue dans cette notification.
authGroup TYPES [-s MODELE] GROUPE [NIVEAU [OID | -v VUE ]]
authAccess TYPES [-s MODELE] GROUPE VUE [NIVEAU [CONTEXTE]]
setAccess GROUPE CONTEXTE MODELE NIVEAU PREFIX VUE TYPES
autorise les notifications du GROUPE spécifié (configuré à l'aide de la directive group) à déclencher les types de traitement listés. Voir snmpd.conf(5) pour plus de détails.
createUser [-e ENGINEID] nomutilisateur (MD5|SHA|SHA-512|SHA-384|SHA-256|SHA-224) motdepasseauth [DES|AES]
Voir la page de manuel de snmpd.conf(5) pour une description de la création d'utilisateurs SNMPv3. C'est à peu près la même chose, mais le nom du fichier passe de snmpd.conf à snmptrapd.conf.
disableAuthorization yes
désactivera les vérifications de contrôle d'accès ci-dessus et reviendra au comportement précédent d'acceptation de toutes les notifications entrantes.

ENREGISTREMENT

format1 FORMAT
format2 FORMAT
spécifie le format utilisé pour afficher respectivement les trappes SNMPv1 et les notifications SNMPv2. Notez que SNMPv2c et SNMPv3 utilisent tous deux le même format de PDU SNMPv2.
format DESTINATION FORMAT
spécifie le format utilisé pour différentes destinations. DESTINATION est l'un des suivants : print, print1, print2, syslog, syslog1, syslog2, execute, execute1, execute2. print1 est utilisé pour imprimer les trappes SNMPv1, print2 est pour SNMPv2. print est utilisé pour les deux versions. syslog est utilisé de manière similaire lors de l'envoi de trappes à syslog, et execute est utilisé lors de l'envoi de trappes à un programme tel que traptoemail(1).
Les formats par défaut sont
format print1 %.4y-%.2m-%.2l %.2h:%.2j:%.2k %B [%b] (via %A [%a]): %N\n\t%W Trap (%q) Uptime: %#T\n%v\n
format print2 %.4y-%.2m-%.2l %.2h:%.2j:%.2k %B [%b]:\n%v\n
format syslog1 %a: %W Trap (%q) Uptime: %#T%#v\n
format syslog2 %B [%b]: Trap %#v\n
format execute %B\n%b\n%V\n%v\n
Voir snmptrapd(8) pour les caractères de mise en page disponibles.
ignoreAuthFailure yes
demande au récepteur d'ignorer les trappes authenticationFailure.
Note :
Ceci affecte actuellement uniquement l'enregistrement de telles notifica

snmptrapd.conf(5)

NAME

snmptrapd.conf — configuration file for snmptrapd(8)

DESCRIPTION

The snmptrapd.conf file is used to configure the snmptrapd(8) daemon, the standard Net-SNMP trap receiver.

This file is read once when the snmptrapd daemon is started. Directives can be specified, one per line. Lines starting with a '#' character are ignored.

Arguments that contain spaces should be quoted.

IMPORTANT

This man page only lists the directives relevant to configuration of the trap daemon itself. Many other directives are processed by snmptrapd(8) but are primarily associated with the SNMP agent configuration (e.g. com2sec, group, view, etc.). Please refer to the snmpd.conf(5) manual page for details of these.

TRAPD BEHAVIOUR

doNotFragment yes|no
If set to yes, snmptrapd will attempt to avoid sending traps that are too large to be transmitted over the network. This is done by setting the IP Do Not Fragment bit. This may not be supported by all network interfaces or operating systems.
disableDispatcher yes|no
If set to yes, snmptrapd will not use the default dispatcher thread. This is required if you are using external applications to handle traps (see traphandle below).
maxMessageSize size
Sets the maximum message size that the snmptrapd daemon will generate. The default value is 8000 bytes. Note that this only affects the size of messages generated by the daemon (e.g. when forwarding traps), not the size of traps received.
trap2sink HOST
Sends received SNMPv2 traps to the specified HOST. This is equivalent to setting up a forward directive for all trap types. Note that this directive is deprecated and the forward directive should be used instead.
trapsink HOST
Sends received SNMPv1 traps to the specified HOST. This is equivalent to setting up a forward directive for all trap types. Note that this directive is deprecated and the forward directive should be used instead.

ACCESS CONTROL

The following directives control access to the trap receiver.

trapcommunity [default] NAME
Defines a community name that will be accepted for incoming SNMPv1 traps. If default is specified, then this community name will be accepted for all incoming traps that do not have a community name explicitly defined by a subsequent trapcommunity directive.
disableSNMPv1 yes|no
If set to yes, snmptrapd will ignore all incoming SNMPv1 traps.
disableSNMPv2c yes|no
If set to yes, snmptrapd will ignore all incoming SNMPv2c traps.
disableSNMPv3 yes|no
If set to yes, snmptrapd will ignore all incoming SNMPv3 traps.

LOGGING

The following directives control how incoming notifications are logged.

logOption string
specifies where notifications should be logged - to standard output, standard error, a specified file or via syslog. See the section LOGGING OPTIONS in the snmpcmd(1) manual page for details.
outputOption string
specifies various characteristics of how OIDs and other values should be displayed. See the section OUTPUT OPTIONS in the snmpcmd(1) manual page for details.

Note that authenticationFailure traps will still be passed to trap handler scripts, and forwarded to other notification receivers. This behaviour should not be relied on, as it is likely to change in future versions.

MySQL Logging

There are two configuration variables that work together to control when queued traps are logged to the MySQL database. A non-zero value must be specified for sqlSaveInterval to enable MySQL logging.

sqlMaxQueue max
specifies the maximum number of traps to queue before a forced flush to the MySQL database.

sqlSaveInterval seconds
specified the number of seconds between periodic queue flushes. A value of 0 for will disable MySQL logging.

NOTIFICATION PROCESSING

As well as logging incoming notifications, they can also be forwarded on to another notification receiver, or passed to an external program for specialised processing.

traphandle OID|default PROGRAM [ARGS ...]
invokes the specified program (with the given arguments) whenever a notification is received that matches the OID token. For SNMPv2c and SNMPv3 notifications, this token will be compared against the snmpTrapOID value taken from the notification. For SNMPv1 traps, the generic and specific trap values and the enterprise OID will be converted into the equivalent OID (following RFC 2576).
Typically, the OID token will be the name (or numeric OID) of a NOTIFICATION-TYPE object, and the specified program will be invoked for notifications that match this OID exactly. However this token also supports a simple form of wildcard suffixing. By appending the character ´*' to the OID token, the corresponding program will be invoked for any notification based within subtree rooted at the specified OID. For example, an OID token of .1.3.6.1.4.1* would match any enterprise specific notification (including the specified OID itself). An OID token of .1.3.6.1.4.1.* would would work in much the same way, but would not match this exact OID - just notifications that lay strictly below this root. Note that this syntax does not support full regular expressions or wildcards - an OID token of the form oid.*.subids is not valid.
If the OID field is the token default then the program will be invoked for any notification not matching another (OID specific) traphandle entry.

Details of the notification are fed to the program via its standard input. Note that this will always use the SNMPv2-style notification format, with SNMPv1 traps being converted as per RFC 2576, before being passed to the program. The input format is, if you use the default set by the "format execute %B\n%b\n%V\n%v\n", one entry per line:

HOSTNAME
The name of the host that sent the notification, as determined by gethostbyaddr(3).
ADDRESS
The transport address, like
"[UDP: [172.16.10.12]:23456->[10.150.0.8]]"
VARBINDS
A list of variable bindings describing the contents of the notification, one per line. The first token on each line (up until a space) is the OID of the varind, and the remainder of the line is its value. The format of both of these are controlled by the outputOption directive (or similar configuration).
The first OID should always be SNMPv2-MIB::sysUpTime.0, and the second should be SNMPv2-MIB::snmpTrapOID.0. The remaining lines will contain the payload varbind list. For SNMPv1 traps, the final OID will be SNMPv2-MIB::snmpTrapEnterprise.0.
Example:
A traptoemail script has been included in the Net-SNMP package that can be used within a traphandle directive:

traphandle default /usr/bin/perl /usr/bin/traptoemail -s mysmtp.somewhere.com -f admin@somewhere.com me@somewhere.com

forward OID|default DESTINATION
forwards notifications that match the specified OID to another receiver listening on DESTINATION. The interpretation of OID (and default) is the same as for the traphandle directive).
See the section LISTENING ADDRESSES in the snmpd(8) manual page for more information about the format of listening addresses.

addForwarderInfo 1|yes|true|0|no|false

Each time a trap is forwarded, add an OID with the IP address of the system from which the trap has been received. The following OID is added: .1.3.6.1.6.3.18.1.3.x (SNMP-COMMUNITY-MIB::snmpTrapAddress.x) where x is the lowest index >= 0 that does not yet occur in the trap payload. The end recipient (i.e. the monitoring system) can determine the IPv4 address of the original sender by looking for the varbind with OID snmpTrapAddress.0. If that OID is not populated it means that the trap has been sent directly or in other words that it has not been forwarded.

NOTES

o
The daemon blocks while executing the traphandle commands. (This should be fixed in the future with an appropriate signal catch and wait() combination).
o
All directives listed with a value of "yes" actually accept a range of boolean values. These will accept any of 1, yes or true to enable the corresponding behaviour, or any of 0, no or false to disable it. The default in each case is for the feature to be turned off, so these directives are typically only used to enable the appropriate behaviour.

FILES

/etc/snmp/snmptrapd.conf
