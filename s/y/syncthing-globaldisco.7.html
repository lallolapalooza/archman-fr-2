NOM

syncthing-globaldisco - Protocole de découverte globale v3

ANNONCES

Un appareil doit s'annoncer au démarrage. Il le fait via une requête HTTPS POST à l'URL du serveur d'annonce. La découverte standard nécessite actuellement que le chemin soit “/v2/”, bien que cela puisse être déterminé par le serveur de découverte. La requête POST contient une charge utile JSON listant les adresses de connexion (le cas échéant) :

{
        addresses: ["tcp://192.0.2.45:22000", "tcp://:22000", "relay://192.0.2.99:22028"],
}

Il est acceptable que le champ “addresses” soit une liste vide ([]), null, ou absent. Une annonce avec le champ manquant ou vide n'est cependant pas très utile...

Toute adresse IP vide ou non spécifiée (c'est-à-dire les adresses comme tcp://:22000, tcp://0.0.0.0:22000, tcp://[::]:22000) est interprétée comme faisant référence à l'adresse IP source de l'annonce.

L'identifiant de l'appareil qui fait l'annonce ne fait pas partie de l'annonce. Au lieu de cela, le serveur exige que le client effectue une authentification par certificat. L'identifiant de l'appareil est déduit du certificat présenté.

La réponse du serveur est vide, avec le code 204 (No Content) en cas de succès. Si aucun certificat n'a été présenté, le statut 403 (Forbidden) est retourné. Si les données postées ne sont pas conformes au format attendu, 400 (Bad Request) est retourné.

Dans les réponses réussies, le serveur peut retourner un en-tête Reannounce-After contenant le nombre de secondes après lequel le client doit effectuer une nouvelle annonce.

Dans les réponses d'erreur, le serveur peut retourner un en-tête Retry-After contenant le nombre de secondes après lequel le client doit réessayer.

Effectuer des annonces beaucoup plus souvent que ce qui est indiqué par les en-têtes Reannounce-After ou Retry-After peut entraîner un ralentissement du client. Dans de tels cas, le serveur peut répondre avec le code d'état 429 (Too Many Requests).

REQUETES

Les requêtes sont effectuées via des requêtes HTTPS GET à l'URL du serveur d'annonce. L'identifiant de l'appareil demandé est passé en tant que paramètre de requête “device”, sous sa forme canonique, c'est-à-dire https://discovery.syncthing.net/?device=ABC12345-....

Les réponses réussies auront le code d'état 200 (OK) et contiendront une charge utile JSON du même format que l'annonce ci-dessus. La réponse ne contiendra pas d'adresses vides ou non spécifiées.

Si le paramètre de requête “device” est manquant ou mal formé, le code d'état 400 (Bad Request) est retourné.

Si l'identifiant de l'appareil est d'un format valide mais n'est pas trouvé dans le registre, 404 (Not Found) est retourné.

Si le client a dépassé une limite de débit, le serveur peut répondre avec 429 (Too Many Requests).

AUTHENTIFICATION

La découverte globale est utilisée via HTTPS et est protégée contre les attaquants de la même manière que le trafic HTTPS. Cependant, il existe quelques considérations spécifiques à Syncthing en plus de cela. Comme mentionné ci-dessus, pour les annonces, le client doit fournir un certificat pour prouver la propriété de l'identifiant de l'appareil annoncé.

De plus, Syncthing dispose d'un mécanisme pour vérifier l'identité du serveur de découverte. Bien que cela se ferait normalement en utilisant un certificat signé par une AC, Syncthing s'exécute souvent dans des environnements avec des bundles de certificats racine obsolètes ou inexistants. Au lieu de cela, Syncthing peut vérifier l'empreinte digitale du certificat du serveur de découverte à l'aide du mécanisme d'identifiant d'appareil. Il s'agit d'une épinglage de certificat et elle est communiquée dans la configuration de Syncthing sous la forme d'un paramètre synthétique “id” sur l'URL du serveur de découverte : https://discovery.syncthing.net/?id=.... Le paramètre “id” n'est pas, en fait, envoyé au serveur de découverte - il est utilisé par Syncthing lui-même pour savoir quel certificat attendre côté serveur.

Le réseau de découverte public utilise ce mécanisme d'authentification au lieu des certificats signés par une AC.

Le serveur de découverte affiche son identifiant de certificat de cette manière au démarrage.
