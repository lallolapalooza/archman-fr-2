NOM

systemd.slice - Configuration d'une unité slice

SYNTAXE

slice.slice

DESCRIPTION

Un fichier de configuration d'unité dont le nom se termine par ".slice" encode des informations sur une unité slice. Une unité slice est un concept pour la gestion hiérarchique des ressources d'un groupe de processus. Cette gestion est effectuée en créant un nœud dans l'arbre des groupes de contrôle Linux (cgroup). Les unités qui gèrent des processus (principalement les unités scope et service) peuvent être assignées à une slice spécifique. Pour chaque slice, certaines limites de ressources peuvent être définies et s'appliquer à tous les processus de toutes les unités contenues dans cette slice. Les slices sont organisées hiérarchiquement dans un arbre. Le nom de la slice encode la position dans l'arbre. Le nom consiste en une série de noms séparés par des tirets, décrivant le chemin de la slice depuis la slice racine. La slice racine est nommée -.slice. Exemple : foo-bar.slice est une slice située dans foo.slice, qui est elle-même située dans la slice racine -.slice.

Notez que les unités slice ne peuvent pas être des templates, et il n'est pas possible d'ajouter plusieurs noms à une unité slice en créant des liens symboliques supplémentaires vers son fichier d'unité.

Par défaut, les unités de service et de scope sont placées dans system.slice, les machines virtuelles et les conteneurs enregistrés auprès de systemd-machined(8) se trouvent dans machine.slice, et les sessions utilisateur gérées par systemd-logind(8) dans user.slice. Voir systemd.special(7) pour plus d'informations.

Voir systemd.unit(5) pour les options communes à tous les fichiers de configuration d'unité. Les éléments de configuration communs sont configurés dans les sections génériques [Unit] et [Install]. Les options de configuration spécifiques à la slice sont configurées dans la section [Slice]. Actuellement, seuls les paramètres génériques de contrôle des ressources décrits dans systemd.resource-control(5) sont autorisés.

Voir les Nouvelles Interfaces de Groupe de Contrôle[1] pour une introduction à l'utilisation des unités slice depuis des programmes.

DEPENDANCES AUTOMATIQUES

Dépendances implicites

Les dépendances suivantes sont ajoutées implicitement :

•Les unités slice acquièrent automatiquement des dépendances de type After= et Requires= sur leur unité slice parente immédiate.

Dépendances par défaut

Les dépendances suivantes sont ajoutées sauf si DefaultDependencies=no est défini :

•Les unités slice auront automatiquement des dépendances de type Conflicts= et Before= sur shutdown.target. Celles-ci assurent que les unités slice sont supprimées avant l'arrêt du système. Seules les unités slice impliquées dans l'arrêt tardif du système devraient désactiver l'option DefaultDependencies=.

OPTIONS

Les fichiers d'unité slice peuvent inclure les sections [Unit] et [Install], qui sont décrites dans systemd.unit(5).

Les fichiers slice peuvent inclure une section [Slice]. De nombreuses options utilisables dans cette section sont partagées avec d'autres types d'unités. Ces options sont documentées dans systemd.resource-control(5).

Les options spécifiques à la section [Slice] des unités slice sont les suivantes :

ConcurrencyHardMax=, ConcurrencySoftMax=

Configure une limite dure et une limite souple sur le nombre maximum d'unités assignées à cette slice (ou à toute slice descendante) qui peuvent être actives en même temps. Si la limite dure est atteinte, aucune autre unité associée à la slice ne pourra être activée, et leur activation échouera avec une erreur. Si la limite souple est atteinte, toute activation ultérieure demandée d'unités sera mise en file d'attente, mais aucune erreur immédiate ne sera générée. La tâche d'activation mise en file d'attente restera en attente jusqu'à ce que le nombre d'unités actives simultanées dans la slice soit à nouveau inférieur à la limite.

Si la valeur spéciale "infinity" est spécifiée, aucune limite de concurrence n'est appliquée. C'est le comportement par défaut.

Notez que si plusieurs tâches de démarrage sont mises en file d'attente pour des unités, et que toutes leurs dépendances sont satisfaites, elles seront traitées dans un ordre qui dépend du type d'unité, du poids du CPU (pour les types d'unités qui connaissent ce concept, comme les services), du niveau de priorité (nice, similaire), et enfin par ordre alphabétique du nom de l'unité. Ceci peut être utilisé pour influencer l'ordre de traitement lors de l'utilisation de ConcurrencySoftMax= pour réguler la concurrence au sein d'une unité slice.

Notez que ces options ont un effet hiérarchique : une limite définie pour une unité slice s'appliquera aux unités directement dans la slice, mais aussi à toutes les unités plus loin dans l'arbre des slices. Notez également que chaque sous-slice compte aussi comme une unité, et donc lors du choix d'une limite pour une hiérarchie de slices, la limite doit prévoir de la place pour les unités de charge utile (c'est-à-dire les services, montages, ...) et les unités structurelles (c'est-à-dire les unités slice), si elles sont définies.
