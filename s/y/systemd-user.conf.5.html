NOM

systemd-system.conf, system.conf.d, systemd-user.conf, user.conf.d - Fichiers de configuration du gestionnaire de services système et de session

SYNTAXE

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/system.conf.d/*.conf, /run/systemd/system.conf.d/*.conf, /usr/lib/systemd/system.conf.d/*.conf

~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf, /etc/systemd/user.conf.d/*.conf, /run/systemd/user.conf.d/*.conf, /usr/lib/systemd/user.conf.d/*.conf

DESCRIPTION

Lorsqu'il est exécuté en tant qu'instance système, systemd interprète le fichier de configuration system.conf et les fichiers des répertoires system.conf.d ; lorsqu'il est exécuté en tant qu'instance utilisateur, il interprète le fichier de configuration user.conf (par ordre de priorité, dans le répertoire personnel de l'utilisateur et sous /etc/systemd/, /run/systemd/, et /usr/lib/systemd/) et les fichiers des répertoires user.conf.d. Ces fichiers de configuration contiennent quelques réglages contrôlant les opérations de base du gestionnaire.

Voir systemd.syntax(7) pour une description générale de la syntaxe.

RÉPERTOIRES DE CONFIGURATION ET PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation, ainsi la configuration n'est nécessaire que lorsqu'il est nécessaire de déroger à ces valeurs par défaut. Le fichier de configuration principal est chargé depuis l'un des répertoires listés par ordre de priorité, seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du fournisseur du fichier contient des entrées commentées montrant les valeurs par défaut comme guide pour l'administrateur. Des substitutions locales peuvent également être créées en créant des fichiers drop-in, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est livré sous /etc/), cependant l'utilisation de fichiers drop-in pour la configuration locale est recommandée plutôt que des modifications du fichier de configuration principal.

En plus du fichier de configuration principal, des fragments de configuration drop-in sont lus depuis /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, et /etc/systemd/*.conf.d/. Ces fichiers drop-in ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier dans l'ordre lexicographique, indépendamment de dans lequel des sous-répertoires ils résident. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée dans le fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées au fur et à mesure qu'elles apparaissent dans les fichiers triés.

Lorsque les paquets ont besoin de personnaliser la configuration, ils peuvent installer des fichiers drop-in sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour outrepasser les fichiers de configuration installés par les paquets du fournisseur. Les fichiers drop-in doivent être utilisés pour remplacer les fichiers drop-in des paquets, car le fichier de configuration principal a une priorité inférieure. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un numéro à deux chiffres et un tiret, pour simplifier l'ordre. Cela définit également un concept de priorités drop-in pour permettre aux fournisseurs de systèmes d'exploitation de livrer des fichiers drop-in dans une plage spécifique inférieure à la plage utilisée par les utilisateurs. Cela devrait réduire le risque que les fichiers drop-in des paquets outrepassent accidentellement les fichiers drop-in définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les fichiers drop-in dans /usr/ et la plage 60-90 pour les fichiers drop-in dans /etc/ et /run/, afin de s'assurer que les fichiers drop-in locaux et transitoires ont la priorité sur les fichiers drop-in livrés par le fournisseur du système d'exploitation.

Pour désactiver un fichier de configuration fourni par le fournisseur, la méthode recommandée est de placer un lien symbolique vers /dev/null dans le répertoire de configuration sous /etc/, avec le même nom de fichier que le fichier de configuration du fournisseur.

OPTIONS

Toutes les options sont configurées dans la section [Manager] :

LogColor=, LogLevel=, LogLocation=, LogTarget=, LogTime=, DumpCore=yes, CrashChangeVT=no, CrashShell=no, CrashAction=freeze, ShowStatus=yes, DefaultStandardOutput=journal, DefaultStandardError=inherit

Configure divers paramètres de fonctionnement de base du gestionnaire. Ces options peuvent être remplacées par les arguments respectifs du processus et de la ligne de commande du noyau. Voir systemd(1) pour plus de détails.

Ajouté dans la version 198.

CtrlAltDelBurstAction=

Définit l'action qui sera effectuée si l'utilisateur appuie sur Ctrl-Alt-Suppression plus de 7 fois en 2 secondes. Peut être défini sur "reboot-force", "poweroff-force", "reboot-immediate", "poweroff-immediate" ou désactivé avec "none". Par défaut "reboot-force".

Ajouté dans la version 232.

StatusUnitFormat=

Prend name, description ou combined comme valeur. Si name, le gestionnaire système utilisera les noms d'unités dans les messages d'état (par exemple "systemd-journald.service"), au lieu des descriptions plus longues et plus informatives définies avec Description= (par exemple "Journal Logging Service"). Si combined, le gestionnaire système utilisera à la fois les noms d'unités et les descriptions dans les messages d'état (par exemple "systemd-journald.service - Journal Logging Service").

Voir systemd.unit(5) pour les détails sur les noms d'unités et Description=.

Ajouté dans la version 243.

DefaultTimerAccuracySec=

Définit la précision par défaut des unités de timer. Cela contrôle la valeur par défaut globale du réglage AccuracySec= des unités de timer, voir systemd.timer(5) pour plus de détails. AccuracySec= défini dans les unités individuelles outrepassent la valeur par défaut globale pour l'unité spécifique. Par défaut 1 minute. Notez que la précision des unités de timer est également affectée par le temps d'attente du timer configuré pour PID 1, voir TimerSlackNSec= ci-dessus.

Ajouté dans la version 212.

GESTION DES RESSOURCES

TimerSlackNSec=

Définit le temps d'attente du timer en nanosecondes pour PID 1, qui est hérité par tous les processus exécutés, sauf si remplacé individuellement, par exemple avec le réglage TimerSlackNSec= dans les unités de service (pour plus de détails voir systemd.exec(5)). Le temps d'attente du timer contrôle la précision des réveils déclenchés par les timers système. Voir prctl(2) pour plus d'informations. Notez que contrairement à la plupart des autres définitions d'intervalles de temps, ce paramètre prend une valeur entière en nanosecondes si aucune unité n'est spécifiée. Les unités de temps habituelles sont également comprises.

Ajouté dans la version 198.

CPUAffinity=

Configure l'affinité CPU pour le gestionnaire de services ainsi que l'affinité CPU par défaut pour tous les processus créés. Prend une liste d'indices CPU ou de plages séparées par des espaces ou des virgules. Les plages CPU sont spécifiées par les indices CPU inférieur et supérieur séparés par un tiret. Cette option peut être spécifiée plusieurs fois, auquel cas les masques d'affinité CPU spécifiés sont fusionnés. Si la chaîne vide est assignée, le masque est réinitialisé, toutes les affectations précédentes n'auront aucun effet. Les services individuels peuvent outrepasser l'affinité CPU pour leurs processus avec le réglage CPUAffinity= dans les fichiers d'unités, voir systemd.exec(5).

Ajouté dans la version 198.

NUMAPolicy=

Configure la politique mémoire NUMA pour le gestionnaire de services et la politique mémoire NUMA par défaut pour tous les processus créés. Les services individuels peuvent outrepasser la politique par défaut avec le réglage NUMAPolicy= dans les fichiers d'unités, voir systemd.exec(5).

Ajouté dans la version 243.

NUMAMask=

Configure le masque de nœuds NUMA qui sera associé à la politique NUMA sélectionnée. Notez que les politiques NUMA default et local ne nécessitent pas de masque de nœud NUMA explicite et la valeur de l'option peut être vide. Similairement à NUMAPolicy=, la valeur peut être outrepassée par des services individuels dans les fichiers d'unités, voir systemd.exec(5).

Ajouté dans la version 243.

DefaultMemoryAccounting=, DefaultTasksAccounting=, DefaultIOAccounting=, DefaultIPAccounting=

Configure les paramètres de comptage des ressources par défaut, tels que configurés par unité par
MemoryAccounting=, TasksAccounting=, IOAccounting=, et IPAccounting=. Voir systemd.resource-control(5) pour des détails sur les paramètres par unité.

DefaultMemoryAccounting= vaut par défaut yes. DefaultTasksAccounting= vaut par défaut yes. Les autres paramètres valent par défaut no.

Ajouté en version 211.

DefaultTasksMax=

Configure la valeur par défaut pour le paramètre par unité TasksMax=. Voir systemd.resource-control(5) pour des détails. Ce paramètre s'applique à tous les types d'unités qui prennent en charge les paramètres de contrôle des ressources, à l'exception des unités slice. Vaut par défaut 15 % du minimum de kernel.pid_max=, kernel.threads-max= et pids.max du cgroup racine. Le noyau a une valeur par défaut pour kernel.pid_max= et un algorithme de comptage en cas de plus de 32 cœurs. Par exemple, avec kernel.pid_max= par défaut, DefaultTasksMax= vaut par défaut 4915, mais peut être supérieur sur d'autres systèmes ou inférieur dans les conteneurs OS.

Ajouté en version 228.

DefaultLimitCPU=, DefaultLimitFSIZE=, DefaultLimitDATA=, DefaultLimitSTACK=, DefaultLimitCORE=, DefaultLimitRSS=, DefaultLimitNOFILE=, DefaultLimitAS=, DefaultLimitNPROC=, DefaultLimitMEMLOCK=, DefaultLimitLOCKS=, DefaultLimitSIGPENDING=, DefaultLimitMSGQUEUE=, DefaultLimitNICE=, DefaultLimitRTPRIO=, DefaultLimitRTTIME=

Ces paramètres contrôlent diverses limites de ressources par défaut pour les processus exécutés par les unités. Voir setrlimit(2) pour des détails. Ces paramètres peuvent être remplacés dans les unités individuelles en utilisant les directives LimitXXX= correspondantes et ils acceptent la même syntaxe de paramètre, voir systemd.exec(5) pour des détails. Notez que ces limites de ressources ne sont que des valeurs par défaut pour les unités, elles ne sont pas appliquées au processus de gestion de service (c'est-à-dire PID 1) lui-même.

La plupart de ces paramètres ne sont pas définis, ce qui signifie que les limites de ressources sont héritées du noyau ou, si invoqués dans un conteneur, du gestionnaire de conteneurs. Cependant, les éléments suivants ont des valeurs par défaut :

•DefaultLimitNOFILE= vaut par défaut 1024:524288.
•DefaultLimitMEMLOCK= vaut par défaut 8M.
•DefaultLimitCORE= n'a pas de valeur par défaut mais il est utile de mentionner que RLIMIT_CORE est défini sur « infinity » par PID 1, ce qui est hérité par ses enfants.

Notez que le gestionnaire de service, en interne au niveau du PID 1, augmente RLIMIT_NOFILE et RLIMIT_MEMLOCK à des valeurs plus élevées, cependant la limite est rétablie aux valeurs par défaut mentionnées pour tous les processus enfants issus.

Ajouté en version 198.

DefaultOOMPolicy=

Configure la politique par défaut pour réagir aux processus tués par le tueur OOM (Out-Of-Memory) de Linux ou systemd-oomd. Ceci peut être utilisé pour choisir une valeur par défaut globale pour le paramètre par unité OOMPolicy=. Voir systemd.service(5) pour des détails. Notez que cette valeur par défaut n'est pas utilisée pour les services dont Delegate= est activé.

Ajouté en version 243.

DefaultOOMScoreAdjust=

Configure les ajustements du score OOM par défaut des processus exécutés par le gestionnaire de service. La valeur par défaut est non définie (ce qui signifie que les processus issus héritent de la valeur d'ajustement du score OOM du gestionnaire de service), sauf si le gestionnaire de service est exécuté pour un utilisateur non privilégié, auquel cas la valeur par défaut est la valeur d'ajustement OOM du gestionnaire de service plus 100 (ce qui rend les processus de service légèrement plus susceptibles d'être tués sous pression mémoire que le gestionnaire lui-même). Ceci peut être utilisé pour choisir une valeur par défaut globale pour le paramètre par unité OOMScoreAdjust=. Voir systemd.exec(5) pour des détails. Notez que ce paramètre n'a aucun effet sur la valeur d'ajustement du score OOM du processus de gestion de service lui-même, il conserve la valeur d'origine définie lors de son invocation.

Ajouté en version 250.

DefaultMemoryPressureWatch=, DefaultMemoryPressureThresholdSec=

Configure les paramètres par défaut pour les paramètres par unité MemoryPressureWatch= et MemoryPressureThresholdSec=. Voir systemd.resource-control(5) pour des détails. Vaut par défaut « auto » et « 200ms », respectivement. Ceci définit également le seuil de surveillance de la pression mémoire pour le gestionnaire de service lui-même.

Ajouté en version 254.

SURVEILLANCE MATÉRIELLE

RuntimeWatchdogSec=, RebootWatchdogSec=, KExecWatchdogSec=

Configure la surveillance matérielle en temps d'exécution et au redémarrage. Prend une valeur de délai d'attente en secondes (ou dans d'autres unités de temps si suffixé avec « ms », « min », « h », « d », « w »), ou les chaînes spéciales « off » ou « default ». Si défini sur « off » (alternativement : « 0 »), la logique de surveillance est désactivée : aucun périphérique de surveillance n'est ouvert, configuré ou contacté. Si défini sur la chaîne spéciale « default », la surveillance est ouverte et contactée à intervalles réguliers, mais le délai d'attente n'est pas modifié par rapport à la valeur par défaut. Si défini sur toute autre valeur temporelle, le délai d'attente de la surveillance est configuré à la valeur spécifiée (ou une valeur proche, en fonction des capacités matérielles).

Si RuntimeWatchdogSec= est défini sur une valeur non nulle, le matériel de surveillance (/dev/watchdog0 ou le chemin spécifié avec WatchdogDevice= ou l'option du noyau systemd.watchdog_device=) sera programmé pour redémarrer automatiquement le système s'il n'est pas contacté dans le délai spécifié. Le gestionnaire système s'assurera de le contacter au moins une fois dans la moitié du délai spécifié. Cette fonctionnalité nécessite un périphérique de surveillance matérielle, comme c'est couramment le cas dans les systèmes embarqués et les serveurs. Tous les matériels de surveillance ne permettent pas la configuration de toutes les valeurs de délai de redémarrage possibles, auquel cas le délai le plus proche disponible est choisi.

RebootWatchdogSec= peut être utilisé pour configurer la surveillance matérielle lorsque le système est invité à redémarrer. Il fonctionne comme une mesure de sécurité pour garantir que le redémarrage a lieu même si une tentative de redémarrage propre expire. Notez que le délai RebootWatchdogSec= s'applique uniquement à la deuxième phase du redémarrage, c'est-à-dire après que tous les services réguliers sont déjà terminés, et après que le système et le processus de gestion de service (PID 1) ont été remplacés par le binaire systemd-shutdown, voir bootup(7) pour des détails. Pendant la première phase de l'opération de mise hors tension, le système et le gestionnaire de service restent actifs et donc RuntimeWatchdogSec= est toujours honoré. Afin de définir un délai sur cette première phase de mise hors tension du système, configurez JobTimeoutSec= et JobTimeoutAction= dans la section [Unit] de l'unité shutdown.target. Par défaut, RuntimeWatchdogSec= vaut 0 (off), et RebootWatchdogSec= vaut 10min.

KExecWatchdogSec= peut être utilisé pour activer la surveillance en plus lors de l'exécution de kexec plutôt que lors d'un redémarrage. Notez que si le noyau ne réinitialise pas la surveillance lors de kexec (selon le matériel et/ou le pilote spécifique), dans ce cas, la surveillance pourrait ne pas être désactivée après la réussite de kexec et donc le système pourrait redémarrer, sauf si RuntimeWatchdogSec= est également activé en même temps. Pour cette raison, il est recommandé d'activer KExecWatchdogSec= uniquement si RuntimeWatchdogSec= est également activé.

Ces paramètres n'ont aucun effet si un matériel de surveillance n'est pas disponible.

Ajouté en version 198.

RuntimeWatchdogPreSec=

Configure la valeur de pré-délai de la surveillance matérielle. Prend une valeur de délai d'attente en secondes (ou dans d'autres unités de temps similaires à RuntimeWatchdogSec=). Un pré-délai de surveillance est une notification générée par la surveillance avant que le réinitialisation par la surveillance ne puisse se produire dans le cas où la surveillance n'a pas été servie. Cette notification est gérée par le noyau et peut être configurée pour effectuer une action (c'est-à-dire générer une panique du noyau) en utilisant RuntimeWatchdogPreGovernor=. Tout le matériel de surveillance ou les pilotes ne prennent pas en charge la génération d'un pré-délai et, en fonction de l'état du système, le noyau peut être incapable d'effectuer l'action configurée avant le redémarrage par la surveillance. La surveillance sera configurée pour générer l'événement de pré-délai à la durée spécifiée par RuntimeWatchdogPreSec= avant le délai d'attente de la surveillance en temps réel (défini par RuntimeWatchdogSec=). Par exemple, si nous avons RuntimeWatchdogSec=30 et RuntimeWatchdogPreSec=10, alors l'événement de pré-délai se produira si la surveillance n'a pas été contactée pendant 20 secondes (10 secondes avant que la surveillance ne se déclenche). Par défaut, RuntimeWatchdogPreSec= vaut 0 (désactivé). La valeur définie pour RuntimeWatchdogPreSec= doit être inférieure à la valeur de délai d'attente pour RuntimeWatchdogSec=. Ce paramètre n'a aucun effet si un matériel de surveillance n'est pas disponible ou si le matériel de surveillance ne prend pas en charge de pré-délai et sera ignoré par le noyau si le paramètre est supérieur au délai de surveillance réel.

Ajouté en version 251.

RuntimeWatchdogPreGovernor=

Configure l'action effectuée par le périphérique de surveillance matérielle lors de l'expiration du pré-délai. L'action par défaut pour l'événement de pré-délai dépend de la configuration du noyau, mais il s'agit généralement d'enregistrer un message du noyau. Pour une liste des actions valides disponibles pour un périphérique de surveillance donné, vérifiez le contenu du fichier /sys/class/watchdog/watchdogX/pretimeout_available_governors. En général, les types de gouverneurs disponibles sont noop et panic. La disponibilité, les noms et les fonctionnalités peuvent varier en fonction du pilote spécifique utilisé. Si le fichier sysfs pretimeout_available_governors est vide, le gouverneur peut être intégré sous forme de module noyau et peut nécessiter d'être chargé manuellement (par exemple, pretimeout_noop.ko), ou le périphérique de surveillance peut ne pas prendre en charge les pré-délais.

Ajouté en version 251.

WatchdogDevice=

Configure le périphérique de surveillance matérielle que les minuteurs de surveillance en temps réel et d'arrêt ouvriront et utiliseront. Vaut par défaut /dev/watchdog0. Ce paramètre n'a aucun effet si un matériel de surveillance n'est pas disponible.

Ajouté en version 236.

SÉCURITÉ

CapabilityBoundingSet=

Contrôle quelles capacités inclure dans l'ensemble des capacités bornées pour PID 1 et ses enfants. Voir capabilities(7) pour des détails. Prend une liste de noms de capacités séparés par des espaces, tels que lus par cap_from_name(3). Les capacités listées seront incluses dans l'ensemble des bornes, toutes les autres seront supprimées. Si la liste des capacités est précédée de
h ~, toutes les capacités sauf celles listées seront incluses, l'effet de l'affectation est inversé. Notez que cette option affecte également les capacités respectives dans les ensembles de capacités effectives, permises et héritables. L'ensemble des limites de capacités peut également être configuré individuellement pour les unités en utilisant la directive CapabilityBoundingSet= pour les unités, mais notez que les capacités supprimées pour le PID 1 ne peuvent pas être récupérées dans les unités individuelles, elles sont perdues définitivement.

Ajouté dans la version 198.

NoNewPrivileges=

Prend un argument booléen. Si vrai, garantit que le PID 1 et tous ses enfants ne pourront jamais obtenir de nouveaux privilèges via execve(2) (par exemple, via les bits setuid ou setgid, ou les capacités du système de fichiers). Par défaut à faux. Les distributions à usage général s'appuient couramment sur des exécutables avec des bits setuid ou setgid et ne fonctionneront donc pas correctement avec cette option activée. Les unités individuelles ne peuvent pas désactiver cette option. Voir également le No New Privileges Flag[2].

Ajouté dans la version 239.

ProtectSystem=

Prend un argument booléen ou la chaîne "auto". Si défini sur vrai, remonte /usr/ en lecture seule. Si défini sur "auto" (par défaut) et en cours d'exécution dans un initrd équivalent à vrai, sinon faux. Cela implémente un sous-ensemble restreint du paramètre du même nom par unité, voir systemd.exec(5) pour les détails : actuellement, les valeurs "full" ou "strict" ne sont pas supportées.

Ajouté dans la version 256.

SystemCallArchitectures=

Prend une liste d'identifiants d'architecture séparés par des espaces. Sélectionne à partir de quelles architectures les appels système peuvent être invoqués sur ce système. Cela peut être utilisé comme un moyen efficace de désactiver l'invocation de binaires non natifs à l'échelle du système, par exemple pour interdire l'exécution de binaires x86 32 bits sur des systèmes x86-64 64 bits. Cette option fonctionne à l'échelle du système et agit de manière similaire au réglage SystemCallArchitectures= des fichiers d'unités, voir systemd.exec(5) pour les détails. Ce réglage est vide par défaut, auquel cas aucun filtrage des appels système basé sur l'architecture n'est appliqué. Les identifiants d'architecture connus sont "x86", "x86-64", "x32", "arm" et l'identifiant spécial "native". Ce dernier correspond implicitement à l'architecture native du système (ou plus précisément, à l'architecture pour laquelle le gestionnaire système a été compilé). Définissez ce réglage sur "native" pour interdire l'exécution de tout binaire non natif. Lorsqu'un binaire exécute un appel système d'une architecture qui n'est pas listée dans ce réglage, il sera immédiatement terminé avec le signal SIGSYS.

Ajouté dans la version 209.

DefaultSmackProcessLabel=

Prend une étiquette de sécurité SMACK64 comme argument. Le processus exécuté par une unité sera démarré sous cette étiquette si SmackProcessLabel= n'est pas défini dans l'unité. Voir systemd.exec(5) pour les détails.

Si la valeur est "/", seules les étiquettes spécifiées avec SmackProcessLabel= sont attribuées et la valeur par défaut de compilation est ignorée.

Ajouté dans la version 252.

DefaultRestrictSUIDSGID=

Prend un argument booléen. Ceci est utilisé comme valeur par défaut pour les unités qui n'ont pas de définition explicite pour RestrictSUIDSGID=. Voir systemd.exec(5) pour les détails.

TEMPORISATIONS ET LIMITES DE TAUX

DefaultTimeoutStartSec=, DefaultTimeoutStopSec=, DefaultTimeoutAbortSec=, DefaultRestartSec=

Configure les temporisations par défaut pour le démarrage, l'arrêt et l'abandon des unités, ainsi que le temps par défaut pour attendre entre les redémarrages automatiques des unités, tels que configurés par unité dans TimeoutStartSec=, TimeoutStopSec=, TimeoutAbortSec= et RestartSec= (pour les services, voir systemd.service(5) pour les détails sur les paramètres par unité). Pour les unités autres que les services, DefaultTimeoutStartSec= définit la valeur par défaut de TimeoutSec=.

DefaultTimeoutStartSec= et DefaultTimeoutStopSec= valent 90 s par défaut dans le gestionnaire système et 90 s dans le gestionnaire utilisateur. DefaultTimeoutAbortSec= n'est pas défini par défaut afin que toutes les unités reviennent à TimeoutStopSec=. DefaultRestartSec= vaut 100 ms par défaut.

Ajouté dans la version 209.

DefaultDeviceTimeoutSec=

Configure la temporisation par défaut pour l'attente des périphériques. Elle peut être modifiée par périphérique via l'option x-systemd.device-timeout= dans /etc/fstab et /etc/crypttab (voir systemd.mount(5), crypttab(5)). Vaut 90 s par défaut dans le gestionnaire système et 90 s dans le gestionnaire utilisateur.

Ajouté dans la version 252.

DefaultStartLimitIntervalSec=, DefaultStartLimitBurst=

Configure la limitation du taux de démarrage des unités par défaut, telle que configurée par service par StartLimitIntervalSec= et StartLimitBurst=. Voir systemd.service(5) pour les détails sur les paramètres par service. DefaultStartLimitIntervalSec= vaut 10s par défaut. DefaultStartLimitBurst= vaut 5 par défaut.

Ajouté dans la version 209.

ReloadLimitIntervalSec=, ReloadLimitBurst=

Limitation du taux pour les requêtes daemon-reload et (depuis v256) daemon-reexec. Le réglage s'applique aux deux opérations, mais les limites de taux sont suivies séparément. Par défaut non défini, et tout nombre d'opérations peut être demandé à tout moment. ReloadLimitIntervalSec= prend une valeur en secondes pour configurer la fenêtre de limitation de taux, et ReloadLimitBurst= prend un entier positif pour configurer le nombre maximum d'opérations autorisées dans la fenêtre de temps configurée.

Ajouté dans la version 253.

ENVIRONNEMENT

DefaultEnvironment=

Configure les variables d'environnement passées à tous les processus exécutés. Prend une liste de variables séparées par des espaces. Voir environ(7) pour les détails sur les variables d'environnement. Ce bloc d'environnement est interne, et les changements ne sont pas reflétés dans le /proc/PID/environ du gestionnaire.

Une expansion simple de spécificateurs "%" est prise en charge, voir ci-dessous pour une liste des spécificateurs pris en charge.

Exemple :

DefaultEnvironment="VAR1=mot1 mot2" VAR2=mot3 "VAR3=mot 5 6"

Définit trois variables : "VAR1", "VAR2", "VAR3".

Ajouté dans la version 205.

ManagerEnvironment=

Définit les variables d'environnement pour le processus gestionnaire lui-même. Prend une liste de variables séparées par des espaces dans le même format que DefaultEnvironment=, voir ci-dessus. Ces variables sont fusionnées dans le bloc d'environnement existant du processus gestionnaire. En particulier, dans le cas du gestionnaire système, ce bloc inclut les variables définies par le noyau en fonction de la ligne de commande du noyau, et dans le cas du gestionnaire utilisateur, les variables transmises par le gestionnaire système. Après que ces variables ont été fusionnées, elles persistent jusqu'à être remplacées, même si le gestionnaire est rechargé ou réexécuté. Dans le cas du gestionnaire utilisateur, ces variables sont également héritées par les processus lancés par le gestionnaire. Comme avec DefaultEnvironment=, ce bloc d'environnement est interne, et les changements ne sont pas reflétés dans le /proc/PID/environ du gestionnaire.

Définir des variables d'environnement pour le processus gestionnaire peut être utile pour modifier son comportement. Voir Known Environment Variables[3] pour une description de certaines variables comprises par systemd.

Une expansion simple de spécificateurs "%" est prise en charge, voir ci-dessous pour une liste des spécificateurs pris en charge.

Ajouté dans la version 248.

DESCRIPTION

systemd uses configuration files to configure its various components and services. These files are typically located in directories under /etc/systemd/, /run/systemd/, and /usr/lib/systemd/. The precedence order for these directories is described in systemd.directives(7).

This page describes the various configuration files and their options. For a detailed explanation of the file format and the precedence rules, see systemd.directives(7).

CONFIGURATION DIRECTORIES AND PRECEDENCE

Configuration files are read from the following directories in order of precedence, with files in later directories overriding files in earlier directories:

  1. /etc/systemd/ (and its subdirectories)
  2. /run/systemd/ (and its subdirectories)
  3. /usr/lib/systemd/ (and its subdirectories)

For specific configuration files like journald.conf, configuration snippets may be placed in /etc/systemd/journald.conf.d/, /run/systemd/journald.conf.d/, and /usr/lib/systemd/journald.conf.d/. These snippets are read in the order listed above, and their settings override the main configuration file. See systemd.directives(7) for more details.
