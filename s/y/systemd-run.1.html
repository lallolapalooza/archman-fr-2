SYSTEMD-RUN(1) systemd-run SYSTEMD-RUN(1)

NOM

systemd-run - Exécute des programmes dans des unités de portée, de service, ou d'unités de service déclenchées par un chemin, un socket ou un minuteur transitoires

SYNTAXE

systemd-run [OPTIONS...] COMMANDE [ARGUMENTS...]

systemd-run [OPTIONS...] [OPTIONS_CHEMIN...] {COMMANDE [ARGUMENTS...]}

systemd-run [OPTIONS...] [OPTIONS_SOCKET...] {COMMANDE [ARGUMENTS...]}

systemd-run [OPTIONS...] [OPTIONS_MINUTEUR...] {COMMANDE [ARGUMENTS...]}

DESCRIPTION

systemd-run peut être utilisé pour créer et démarrer une unité .service ou .scope transitoire et y exécuter la COMMANDE spécifiée. Il peut également être utilisé pour créer et démarrer une unité .path, .socket ou .timer transitoire, qui active une unité .service lorsqu'elle s'active.

Si une commande est exécutée en tant qu'unité de service transitoire, elle sera démarrée et gérée par le gestionnaire de services comme toute autre unité de service. Elle apparaîtra donc dans la sortie de systemctl list-units comme toute autre unité. Elle s'exécutera dans un environnement d'exécution propre et détaché, avec le gestionnaire de services comme processus parent. Dans ce mode, systemd-run démarrera le service asynchroniquement en arrière-plan et retournera après que la commande ait commencé son exécution (sauf si --no-block, --wait, --pipe, ou --pty sont spécifiés, voir ci-dessous).

Si une commande est exécutée en tant qu'unité de portée transitoire, elle sera exécutée par systemd-run lui-même en tant que processus parent et héritera donc de l'environnement d'exécution de l'appelant. Cependant, les processus de la commande sont gérés par le gestionnaire de services, de manière similaire aux services normaux, et apparaîtront dans la sortie de systemctl list-units. L'exécution dans ce cas est synchrone et ne retournera que lorsque la commande se terminera. Ce mode est activé via le commutateur --scope (voir ci-dessous).

Si une commande est exécutée avec des options de chemin, de socket ou de minuteur comme --on-calendar= (voir ci-dessous), une unité de chemin, de socket ou de minuteur transitoire est créée en parallèle de l'unité de service pour la commande spécifiée. Seule l'unité de chemin, de socket ou de minuteur transitoire est démarrée immédiatement ; l'unité de service transitoire sera déclenchée par l'unité de chemin, de socket ou de minuteur. Si l'option --unit= est spécifiée, la COMMANDE peut être omise. Dans ce cas, systemd-run crée uniquement une unité .path, .socket ou .timer qui déclenche l'unité spécifiée.

Par défaut, les services créés avec systemd-run utilisent le type simple, voir la description de Type= dans systemd.service(5) pour plus de détails. Notez que lorsque ce type est utilisé, le gestionnaire de services (et donc la commande systemd-run) considère que le démarrage du service a réussi dès que le fork() pour le processus principal du service a réussi, c'est-à-dire avant l'appel de execve(), et donc même si la commande spécifiée ne peut pas être démarrée. Envisagez d'utiliser le type de service exec (c'est-à-dire --property=Type=exec) pour vous assurer que systemd-run ne retourne avec succès que si la ligne de commande spécifiée a été démarrée avec succès.

Après que systemd-run ait transmis la commande au gestionnaire de services, celui-ci effectue l'expansion des variables. Cela signifie que les caractères dollar ("$") qui ne doivent pas être développés doivent être échappés sous la forme "$$". L'expansion peut également être désactivée à l'aide de --expand-environment=no.

OPTIONS

Les options suivantes sont comprises :

--scope

Crée une unité .scope transitoire au lieu de l'unité .service transitoire par défaut (voir ci-dessus).

Ajouté en version 206.

--unit=, -u

Utilise ce nom d'unité au lieu d'un nom généré automatiquement.

Ajouté en version 206.

--property=, -p

Définit une propriété sur l'unité de portée ou de service créée. Cette option prend une affectation dans le même format que la commande set-property de systemctl(1).

Ajouté en version 211.

--description=

Fournit une description pour l'unité de service, de portée, de chemin, de socket ou de minuteur. Si elle n'est pas spécifiée, la commande elle-même sera utilisée comme description. Voir Description= dans systemd.unit(5).

Ajouté en version 206.

--slice=

Fait de la nouvelle unité .service ou .scope une partie de la tranche spécifiée, au lieu de system.slice (lors de l'exécution en mode --system) ou de la tranche racine (lors de l'exécution en mode --user).

Ajouté en version 206.

--slice-inherit

Fait de la nouvelle unité .service ou .scope une partie de la tranche dans laquelle systemd-run lui-même a été invoqué. Cette option peut être combinée avec --slice=, auquel cas la tranche spécifiée via --slice= sera placée sous la tranche dans laquelle la commande systemd-run est invoquée.

Exemple : considérez systemd-run invoqué dans la tranche foo.slice, et l'argument --slice= est bar. L'unité sera alors placée sous foo-bar.slice.

Ajouté en version 246.

--expand-environment=BOOL

Développe les variables d'environnement dans les arguments de la commande. Si activé (par défaut), les variables d'environnement spécifiées comme "${VARIABLE}" seront développées de la même manière que dans les commandes spécifiées via ExecStart= dans les unités. Avec --scope, ce développement est effectué par systemd-run lui-même, et dans d'autres cas par le gestionnaire de services qui lance la commande. Notez que c'est similaire, mais pas identique, à l'expansion des variables dans bash(1) et d'autres shells.

Voir systemd.service(5) pour une description de l'expansion des variables. Désactiver l'expansion des variables est utile si la commande spécifiée inclut ou peut inclure un signe "$".

Ajouté en version 254.

-r, --remain-after-exit

Après la terminaison du processus de service, conservez l'unité de service jusqu'à ce qu'elle soit explicitement arrêtée. Ceci est utile pour collecter des informations d'exécution sur le service après qu'il ait fini de s'exécuter. Voir également RemainAfterExit= dans systemd.service(5).

Ajouté en version 207.

--send-sighup

Lors de la terminaison de l'unité de portée ou de service, envoie un SIGHUP immédiatement après SIGTERM. Ceci est utile pour indiquer aux shells et aux processus de type shell que la connexion a été rompue. Voir également SendSIGHUP= dans systemd.kill(5).

Ajouté en version 207.

--service-type=

Définit le type de service. Voir également Type= dans systemd.service(5). Cette option n'a aucun effet en conjonction avec --scope. Par défaut, c'est simple.

Ajouté en version 211.

--uid=, --gid=

Exécute le processus de service sous l'utilisateur et le groupe UNIX spécifiés. Voir également User= et Group= dans systemd.exec(5).

Ajouté en version 211.

--nice=

Exécute le processus de service avec le niveau de priorité spécifié. Voir également Nice= dans systemd.exec(5).

Ajouté en version 211.

--working-directory=

Exécute le processus de service avec le répertoire de travail spécifié. Voir également WorkingDirectory= dans systemd.exec(5).

Ajouté en version 240.

--same-dir, -d

Similaire à --working-directory=, mais utilise le répertoire de travail actuel de l'appelant pour l'exécution du service.

Ajouté en version 240.

-E NOM[=VALEUR], --setenv=NOM[=VALEUR]

Exécute le processus de service avec la variable d'environnement spécifiée définie. Ce paramètre peut être utilisé plusieurs fois pour définir plusieurs variables. Lorsque "=" et VALEUR sont omis, la valeur de la variable portant le même nom dans l'environnement du programme sera utilisée.

Voir également Environment= dans systemd.exec(5).

Ajouté en version 211.

--pty, -t

>Lorsque vous appelez la commande, le service transitoire connecte son entrée standard, sa sortie standard et son flux d'erreurs à l'émulateur de terminal sur lequel systemd-run est appelé, via un périphérique pseudo-TTY. Cela permet d'exécuter des programmes qui attendent des entrées/sorties utilisateur interactives en tant que services, tels que des shells de commande interactifs.

Cette option entraînera l'attente synchrone par systemd-run jusqu'à ce que le service transitoire soit terminé, de manière similaire à la spécification de --wait. Si elle est spécifiée avec --wait, systemd-run ne se terminera pas lors de la déconnexion manuelle du périphérique pseudo-TTY.

Notez que la commande shell de machinectl(1) est généralement une meilleure alternative pour demander une nouvelle session de connexion interactive sur l'hôte local ou dans un conteneur local.

Voir ci-dessous pour les détails sur la manière dont ce commutateur se combine avec --pipe.

Ajouté dans la version 219.

--pty-late, -T

Similaire à --pty, mais la communication PTY ne commence qu'une fois le démarrage de l'unité terminé. Cela signifie effectivement que l'entrée PTY pendant ExecStartPre= d'un service n'est pas disponible lors de l'utilisation de --pty-late, alors qu'elle est disponible en utilisant --pty, pour la plupart des types de services. Cependant, si cette option est utilisée, l'accès au TTY appelant est disponible pour les requêtes de mot de passe (voir --no-ask-password ci-dessous) pendant le démarrage de l'unité.

Ajouté dans la version 258.

--pipe, -P

Si spécifié, l'entrée standard, la sortie standard et le flux d'erreurs du service transitoire sont hérités de la commande systemd-run elle-même. Cela permet d'utiliser systemd-run dans des pipelines shell.

Notez que ce mode ne convient pas aux shells de commande interactifs et similaires, car le processus de service ne deviendra pas un contrôleur TTY lorsqu'il sera appelé sur un terminal. Utilisez --pty à la place dans ce cas.

Lorsque --pipe et --pty sont utilisés en combinaison, l'option la plus appropriée est déterminée et utilisée automatiquement. Spécifiquement, lorsqu'elle est appelée avec l'entrée standard, la sortie standard et le flux d'erreurs connectés à un TTY, --pty est utilisée, et sinon, --pipe.

Cette option entraînera l'attente synchrone par systemd-run jusqu'à ce que le service transitoire soit terminé, de manière similaire à la spécification de --wait.

Lorsque cette option est utilisée, les descripteurs de fichiers d'origine reçus par systemd-run sont transmis tels quels aux processus de service. Si le service s'exécute avec des privilèges différents de ceux de systemd-run, cela signifie que le service pourrait ne pas être en mesure de rouvrir les descripteurs de fichiers transmis, en raison des restrictions d'accès normales aux descripteurs de fichiers. Si le processus appelé est un script shell qui utilise la construction echo "hello" >/dev/stderr pour écrire des messages sur stderr, cela pourrait causer des problèmes, car cela ne fonctionne que si stderr peut être rouvert. Pour atténuer cela, utilisez la construction echo "hello" >&2 à la place, qui est la plupart du temps équivalente et évite ce piège.

Ajouté dans la version 235.

--shell, -S

Un raccourci pour "--pty --same-dir --wait --collect --service-type=exec $SHELL", c'est-à-dire qu'il demande un shell interactif dans le répertoire de travail actuel, exécuté dans le contexte d'un service, accessible avec un seul commutateur.

Ajouté dans la version 240.

--quiet, -q

Supprime les informations supplémentaires pendant l'exécution. Ceci est particulièrement utile en combinaison avec --pty où cela supprimera le message initial expliquant comment terminer la connexion TTY.

Ajouté dans la version 219.

-v, --verbose

Affiche la sortie du journal de l'unité pendant l'exécution.

Ajouté dans la version 258.

--on-active=, --on-boot=, --on-startup=, --on-unit-active=, --on-unit-inactive=

Définit un minuteur monotone relatif à différents points de départ pour le démarrage de la commande spécifiée. Voir OnActiveSec=, OnBootSec=, OnStartupSec=, OnUnitActiveSec= et OnUnitInactiveSec= dans systemd.timer(5) pour les détails. Ces options sont des raccourcis pour --timer-property= avec les propriétés pertinentes. Ces options ne peuvent pas être combinées avec --scope ou --pty.

Ajouté dans la version 218.

--on-calendar=

Définit un minuteur calendaire pour le démarrage de la commande spécifiée. Voir OnCalendar= dans systemd.timer(5). Cette option est un raccourci pour --timer-property=OnCalendar=. Cette option ne peut pas être combinée avec --scope ou --pty.

Ajouté dans la version 218.

--on-clock-change, --on-timezone-change

Définit un déclencheur basé sur les sauts de l'horloge système ou les changements de fuseau horaire pour le démarrage de la commande spécifiée. Voir OnClockChange= et OnTimezoneChange= dans systemd.timer(5). Ces options sont des raccourcis pour --timer-property=OnClockChange=yes et --timer-property=OnTimezoneChange=yes. Ces options ne peuvent pas être combinées avec --scope ou --pty.

Ajouté dans la version 242.

--path-property=, --socket-property=, --timer-property=

Définit une propriété sur l'unité de chemin, de socket ou de minuteur qui est créée. Cette option est similaire à --property=, mais s'applique à l'unité transitoire de chemin, de socket ou de minuteur plutôt qu'à l'unité de service transitoire créée. Cette option prend une affectation dans le même format que la commande set-property de systemctl(1). Ces options ne peuvent pas être combinées avec --scope ou --pty.

Ajouté dans la version 218.

--no-block

N'attendez pas de manière synchrone que l'opération de démarrage de l'unité se termine. Si cette option n'est pas spécifiée, la demande de démarrage de l'unité transitoire sera vérifiée, mise en file d'attente et systemd-run attendra la fin du démarrage de l'unité. En passant cet argument, elle est seulement vérifiée et mise en file d'attente. Cette option ne peut pas être combinée avec --wait.

Ajouté dans la version 220.

--wait

Attendez de manière synchrone la terminaison du service transitoire. Si cette option est spécifiée, la demande de démarrage de l'unité transitoire est vérifiée, mise en file d'attente et attendue. Ensuite, l'unité appelée est surveillée et on attend qu'elle soit désactivée à nouveau (très probablement parce que la commande spécifiée s'est terminée). À la sortie, des informations concises sur le temps d'exécution de l'unité sont affichées, y compris le temps d'exécution total (ainsi que les données de comptabilité CPU, mémoire, IO et IP, si les paramètres de comptabilité cgroup correspondants sont activés) et le code de sortie et le statut du processus principal. Cette sortie peut être supprimée avec --quiet. Cette option ne peut pas être combinée avec --no-block, --scope ou les différentes options de chemin, socket ou minuteur.

Ajouté dans la version 232.

-G, --collect

Décharge l'unité transitoire après qu'elle a terminé, même si elle a échoué. Normalement, sans cette option, toutes les unités qui ont été exécutées et ont échoué sont conservées en mémoire jusqu'à ce que l'utilisateur réinitialise explicitement leur état d'échec avec systemctl reset-failed ou une commande équivalente. D'autre part, les unités qui ont été exécutées avec succès sont déchargées immédiatement. Si cette option est activée, le "nettoyage" des unités est plus agressif, et décharge les unités indépendamment de leur succès ou de leur échec à la sortie. Cette option est un raccourci pour --property=CollectMode=inactive-or-failed, voir l'explication de CollectMode= dans systemd.unit(5) pour plus d'informations.

Ajouté dans la version 236.

--job-mode=MODE

Lors de la mise en file d'attente d'un nouveau travail, cette option contrôle la manière de traiter les travaux déjà mis en file d'attente.

L'option accepte les mêmes valeurs de mode que l'option --job-mode= de systemctl(1). Le mode de travail par défaut est "fail".

L'exécution de --job-mode=help affiche une liste des modes de travail disponibles.

Ajouté dans la version 258.

--ignore-failure

Par défaut, si la commande spécifiée échoue, l'unité appelée sera marquée comme échouée (bien que potentiellement toujours déchargée, voir --collect=, ci-dessus), et cela sera signalé dans les journaux. Si ce commutateur est spécifié, cela est supprimé et tout statut de sortie/code non réussi de la commande est traité comme un succès.

Ajouté dans la version 256.

--background=COLOR

Change la couleur de fond du terminal à la couleur ANSI spécifiée tant que la session dure. La couleur spécifiée doit être une couleur de fond SGR ANSI X3.64, c'est-à-dire des chaînes telles que "40", "41", ..., "47", "48;2;...", "48;5;...". Voir ANSI Escape Code (Wikipedia)[1] pour plus de détails.

Ajouté dans la version 256.

--user

Communique avec le gestionnaire de services de l'utilisateur appelant, plutôt qu'avec le gestionnaire de services du système.

--system

Communique avec le gestionnaire de services du système. C'est l'option par défaut implicite.

-H, --host=

Exécute l'opération à distance. Spécifiez un nom d'hôte, ou un nom d'utilisateur et un nom d'hôte séparés par "@", pour vous connecter. Le nom d'hôte peut éventuellement être suivi d'un port sur lequel ssh écoute, séparé par ":", puis d'un nom de conteneur, séparé par "/", ce qui se connecte directement à un conteneur spécifique sur l'hôte spécifié. Cela utilisera SSH pour communiquer avec l'instance du gestionnaire de machine distante. Les noms de conteneurs peuvent être énumérés avec machinectl -H HOST. Placez les adresses IPv6 entre crochets.

-M, --machine=

Exécute l'opération sur un conteneur local. Spécifiez un nom de conteneur auquel se connecter, éventuellement préfixé par un nom d'utilisateur pour se connecter et un caractère "@" séparateur. Si la chaîne spéciale ".host" est utilisée à la place du nom du conteneur, une connexion au système local est établie (ce qui est utile pour se connecter au bus utilisateur d'un utilisateur spécifique : "--user --machine=lennart@.host"). Si la syntaxe "@" n'est pas utilisée, la connexion est effectuée en tant qu'utilisateur root. Si la syntaxe "@" est utilisée, soit la partie gauche, soit la partie droite peut être omise (mais pas les deux), auquel cas le nom d'utilisateur local et ".host" sont implicites.

-C, --capsule=

Exécute l'opération sur une capsule. Spécifiez un nom de capsule auquel se connecter. Voir capsule@.service(5) pour les détails sur les capsules.

Ajouté dans la version 256.

--no-ask-password

Ne pas interroger l'utilisateur pour l'authentification pour les opérations privilégiées.

-h, --help

Affiche un court message d'aide et quitte.

--version

NAME

systemd-run - run a systemd service or timer on the side

SYNOPSIS

systemd-run [OPTION...] {--shell | --user | --scope | --service | --timer} {--quiet | --no-pager} {-p PROPERTY} ... {COMMAND [ARG ]...}

systemd-run [OPTION...] {--shell | --user | --scope | --service | --timer} {--quiet | --no-pager} {-p PROPERTY} ... UNIT

systemd-run {--help | --version}

DESCRIPTION

Runs a command on the side as a systemd service or timer unit. This is useful for debugging, testing, or simply running a command that should benefit from the systemd infrastructure.

If no unit type is specified using --scope, --service, or --timer, a service unit is created by default.

By default, the service unit is created in the system instance. Use --user to create it in the user instance.

If --wait is passed, systemd-run will wait until the created service unit terminates and then print its exit code. This is useful for running commands in a service and wait for them to finish.

If --scope is used, a scope unit is created instead of a service unit. Scope units are primarily used to group other units and manage resources. They do not execute a command directly but rather govern the execution of processes within them.

If --shell is used, systemd-run will execute the command in a login shell, which might alter the environment and search path. This is useful for running interactive commands or scripts that rely on shell features.

If --timer is used, a timer unit is created that will activate a service unit after a specified delay or at a specified time. The --on-active= or --on-boot= options must be used to configure the timer.

If --user is used, the created unit will be associated with the calling user's systemd instance. This requires the user to be logged in and have lingering enabled if the service needs to run after logout.

All command line arguments after the first non-option argument become part of the command line of the launched process, unless they are part of a unit definition (e.g., -p PROPERTY).

OPTIONS

The following options are understood:

--quiet
Suppress output messages. Only print the unit name on success.
--scope
Create a scope unit instead of a service unit. This is useful for grouping processes without starting a separate service.
--service
Create a service unit. This is the default behavior if no other unit type is specified.
--shell
Execute the command in a login shell. This may affect the environment and search path.
--timer
Create a timer unit. Requires options like --on-active= or --on-boot= to define the timer's schedule.
--user
Create the unit in the user's systemd instance instead of the system instance.
Wait for the created service unit to terminate and print its exit code.
--show-control-group
Print the control group (cgroup) path of the created unit.
--show-slice
Print the slice the created unit belongs to.
--show-version
Print the version of systemd being used.
--json=MODE
Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).
--no-pager
Do not pipe output into a pager. This currently only applies to --help. (The pager is not started during normal operation.
Added in version 258.

All command line arguments after the first non-option argument become part of the command line of the launched process.

EXIT STATUS

On success, 0 is returned. If systemd-run failed to start the service, a non-zero return value will be returned. If systemd-run waits for the service to terminate, the return value will be propagated from the service. 0 will be returned on success, including all the cases where systemd considers a service to have exited cleanly, see the discussion of SuccessExitStatus= in systemd.service(5).

EXAMPLES

Example 1. Logging environment variables provided by systemd to services

# systemd-run env
Running as unit: run-19945.service
# journalctl -u run-19945.service
Sep 08 07:37:21 bupkis systemd[1]: Starting /usr/bin/env...
Sep 08 07:37:21 bupkis systemd[1]: Started /usr/bin/env.
Sep 08 07:37:21 bupkis env[19948]: PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin
Sep 08 07:37:21 bupkis env[19948]: LANG=en_US.UTF-8
Sep 08 07:37:21 bupkis env[19948]: BOOT_IMAGE=/vmlinuz-3.11.0-0.rc5.git6.2.fc20.x86_64

Example 2. Limiting resources available to a command

# systemd-run -p IOWeight=10 updatedb

This command invokes the updatedb(8) tool, but lowers the block I/O weight for it to 10. See systemd.resource-control(5) for more information on the IOWeight= property.

Example 3. Running commands at a specified time

The following command will touch a file after 30 seconds.

# date; systemd-run --on-active=30 --timer-property=AccuracySec=100ms /bin/touch /tmp/foo
Mon Dec  8 20:44:24 KST 2014
Running as unit: run-71.timer
Will run service as unit: run-71.service
# journalctl -b -u run-71.timer
-- Journal begins at Fri 2014-12-05 19:09:21 KST, ends at Mon 2014-12-08 20:44:54 KST. --
Dec 08 20:44:38 container systemd[1]: Starting /bin/touch /tmp/foo.
Dec 08 20:44:38 container systemd[1]: Started /bin/touch /tmp/foo.
# journalctl -b -u run-71.service
-- Journal begins at Fri 2014-12-05 19:09:21 KST, ends at Mon 2014-12-08 20:44:54 KST. --
Dec 08 20:44:48 container systemd[1]: Starting /bin/touch /tmp/foo...
Dec 08 20:44:48 container systemd[1]: Started /bin/touch /tmp/foo.

Example 4. Allowing access to the tty

The following command invokes bash(1) as a service passing its standard input, output and error to the calling TTY.

# systemd-run -t --send-sighup bash

Example 5. Start screen as a user service

$ systemd-run --scope --user screen
Running scope as unit run-r14b0047ab6df45bfb45e7786cc839e76.scope.
$ screen -ls
There is a screen on:
        492..laptop     (Detached)
1 Socket in /var/run/screen/S-fatima.

This starts the screen process as a child of the systemd --user process that was started by user@.service, in a scope unit. A systemd.scope(5) unit is used instead of a systemd.service(5) unit, because screen will exit when detaching from the terminal, and a service unit would be terminated. Running screen as a user unit has the advantage that it is not part of the session scope. If KillUserProcesses=yes is configured in logind.conf(5), the default, the session scope will be terminated when the user logs out of that session.

The user@.service is started automatically when the user first logs in, and stays around as long as at least one login session is open. After the user logs out of the last session, user@.service and all services underneath it are terminated. This behavior is the default, when "lingering" is not enabled for that user. Enabling lingering means that user@.service is started automatically during boot, even if the user is not logged in, and that the service is not terminated when the user logs out.

Enabling lingering allows the user to run processes without being logged in, for example to allow screen to persist after the user logs out, even if the session scope is terminated. In the default configuration, users can enable lingering for themselves:

$ loginctl enable-linger

Example 6. Variable expansion by the manager

$ systemd-run -t echo "<${INVOCATION_ID}>" '<${INVOCATION_ID}>'
      <> <5d0149bfa2c34b79bccb13074001eb20>

The first argument is expanded by the shell (double quotes), but the second one is not expanded by the shell (single quotes). echo(1) is called with ["/usr/bin/echo", "<>", "<${INVOCATION_ID}>"] as the argument array, and then systemd(1) generates ${INVOCATION_ID} and substitutes it in the command-line. This substitution could not be done on the client side, because the target ID that will be set for the service is not known before the call is made.

Example 7. Variable expansion and output redirection using a shell

Variable expansion by systemd(1) can be disabled with --expand-environment=no.

Disabling variable expansion can be useful if the command to execute contains dollar characters and escaping them would be inconvenient. For example, when a shell is used:

$ systemd-run --expand-environment=no -t bash \
      -c 'echo $SHELL $$ >/dev/stdout'
/bin/bash 12345

The last argument is passed verbatim to the bash(1) shell which is started by the service unit. The shell expands "$SHELL" to the path of the shell, and "$$" to its process number, and then those strings are passed to the echo built-in and printed to standard output (which, in this case, is connected to the calling terminal).

Example 8. Return value

$ systemd-run --user --wait true
$ systemd-run --user --wait -p SuccessExitStatus=11 bash -c 'exit 11'
$ systemd-run --user --wait -p SuccessExitStatus=SIGUSR1 --expand-environment=no \
      bash -c 'kill -SIGUSR1 $$'

Those three invocations will succeed, i.e. terminate with an exit code of 0.
