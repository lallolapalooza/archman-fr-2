NOM

systemd.journal-fields - Champs spéciaux du journal

DESCRIPTION

Les entrées du journal (écrites par systemd-journald.service(8)) ressemblent à un bloc d'environnement de processus UNIX en syntaxe, mais avec des valeurs de champ pouvant inclure des données binaires, et avec des noms de champ non uniques autorisés. Principalement, les valeurs des champs sont des chaînes de texte UTF-8 formatées — l'encodage binaire n'est utilisé que lorsque le formatage en chaînes de texte UTF-8 a peu de sens. De nouveaux champs peuvent être définis librement par les applications, mais quelques champs ont des significations spéciales, listées ci-dessous. Typiquement, les champs ne peuvent apparaître qu'une fois par entrée de journal, cependant il existe des exceptions spéciales : certains champs peuvent apparaître plus d'une fois par entrée, auquel cas cela est explicitement mentionné ci-dessous. Bien que le sous-système de journalisation n'impose aucune restriction sur les champs pour lesquels il accepte des valeurs non uniques, il est fortement recommandé d'éviter de s'appuyer sur cela pour les champs listés ci-dessous (sauf indication contraire) afin d'éviter des incompatibilités inutiles avec d'autres applications.

CHAMPS JOURNAL UTILISATEUR

Les champs utilisateur sont des champs directement transmis par les clients et stockés dans le journal.

MESSAGE=

La chaîne de message lisible par l'homme pour cette entrée. Il est censé s'agir du texte principal affiché à l'utilisateur. Il n'est généralement pas traduit (mais peut l'être dans certains cas) et n'est pas censé être analysé pour des métadonnées. Afin d'encoder plusieurs lignes dans une seule entrée de journal, séparez-les par des caractères de nouvelle ligne (code ASCII 10), mais encodez-les sous un seul champ MESSAGE=. N'ajoutez pas plusieurs valeurs de ce type de champ à la même entrée (voir aussi ci-dessus), car les applications consommatrices ne s'y attendent généralement pas et sont peu susceptibles d'afficher toutes les valeurs dans ce cas.

MESSAGE_ID=

Un identifiant de message de 128 bits pour reconnaître certains types de messages, si cela est souhaitable. Ceci doit contenir un ID de 128 bits formaté sous forme de chaîne hexadécimale en minuscules, sans aucun tiret de séparation ou similaire. Il est recommandé que ce soit un ID compatible UUID, mais cela n'est pas appliqué et formaté différemment. Les développeurs peuvent générer un nouvel ID à cet effet avec systemd-id128 new.

PRIORITY=

Une valeur de priorité comprise entre 0 (« emerg ») et 7 (« debug ») formatée sous forme de chaîne décimale. Ce champ est compatible avec le concept de priorité de syslog.

CODE_FILE=, CODE_LINE=, CODE_FUNC=

L'emplacement du code générant ce message, si connu. Contient le nom du fichier source, le numéro de ligne et le nom de la fonction.

ERRNO=

Le numéro d'erreur Unix de bas niveau provoquant cette entrée, le cas échéant. Contient la valeur numérique de errno(3) formatée sous forme de chaîne décimale.

Ajouté dans la version 188.

INVOCATION_ID=, USER_INVOCATION_ID=

Un ID aléatoire unique de 128 bits identifiant chaque cycle d'exécution de l'unité. Ceci est différent de _SYSTEMD_INVOCATION_ID car il est uniquement utilisé pour les messages provenant du code systemd (par exemple, les journaux du gestionnaire système/utilisateur ou des processus dérivés effectuant la configuration liée à systemd).

Ajouté dans la version 245.

SYSLOG_FACILITY=, SYSLOG_IDENTIFIER=, SYSLOG_PID=, SYSLOG_TIMESTAMP=

Champs de compatibilité syslog contenant la facilité (formatée en chaîne décimale), la chaîne d'identifiant (c'est-à-dire « tag »), le PID du client et l'horodatage tels que spécifiés dans le datagramme d'origine. (Notez que le tag est généralement dérivé de la variable program_invocation_short_name de glibc, voir program_invocation_short_name(3).)

Notez que le service de journal ne valide pas les valeurs des champs de journal structurés dont le nom n'est pas précédé d'un trait de soulignement, et cela inclut tous les champs liés à syslog comme ceux-ci. Par conséquent, les applications qui fournissent une facilité, un PID ou un niveau de journalisation sont censées le faire correctement formaté, c'est-à-dire sous forme d'entiers formatés en décimales.

SYSLOG_RAW=

Le contenu d'origine de la ligne syslog telle que reçue dans le datagramme syslog. Ce champ n'est inclus que si le champ MESSAGE= a été modifié par rapport à la charge utile d'origine ou si l'horodatage n'a pas pu être localisé correctement et n'est pas inclus dans SYSLOG_TIMESTAMP=. La troncature du message se produit lorsque le message contient des espaces blancs de début ou de fin (les espaces blancs de fin et de début sont supprimés), ou s'il contient un octet NUL intégré (l'octet NUL et tout ce qui suit est omis). Ainsi, la ligne syslog d'origine est soit stockée sous SYSLOG_RAW=, soit elle peut être recréée sur la base de la priorité et de la facilité stockées, de l'horodatage, de l'identifiant et de la charge utile du message dans MESSAGE=.

Ajouté dans la version 240.

DOCUMENTATION=

Une URL de documentation avec des informations supplémentaires sur le sujet du message de journalisation. Les outils tels que journalctl incluront un lien hypertexte vers une URL spécifiée de cette manière dans leur sortie. Doit être une URL « http:// », « https:// », « file:/ », « man: » ou « info: ».

Ajouté dans la version 246.

TID=

L'ID du thread (TID) numérique d'où provient le message de journalisation.

Ajouté dans la version 247.

UNIT=, USER_UNIT=

Le nom d'une unité. Utilisé par les gestionnaires système et utilisateur lors de la journalisation concernant des unités spécifiques.

Lorsque --unit=nom ou --user-unit=nom sont utilisés avec journalctl(1), un modèle de correspondance incluant « UNIT=nom.service » ou « USER_UNIT=nom.service » sera généré.

Ajouté dans la version 251.

CHAMPS JOURNAL CONFIANTS

Les champs précédés d'un trait de soulignement sont des champs de confiance, c'est-à-dire des champs ajoutés implicitement par le journal et qui ne peuvent pas être modifiés par le code client.

_PID=, _UID=, _GID=

Le numéro de processus, le numéro d'utilisateur et le numéro de groupe du processus dont provient l'entrée du journal, formatés en décimal. Notez que les entrées obtenues via « stdout » ou « stderr » de processus dérivés contiendront les informations d'identification valides pour un processus parent (celui qui a initié la connexion à systemd-journald).

_COMM=, _EXE=, _CMDLINE=

Le nom, le chemin d'exécution et la ligne de commande du processus dont provient l'entrée du journal.

_CAP_EFFECTIVE=

Les capacités(7) effectives du processus dont provient l'entrée du journal.

Ajouté dans la version 206.

_AUDIT_SESSION=, _AUDIT_LOGINUID=

La session et l'UID de connexion du processus dont provient l'entrée du journal, tels que maintenus par le sous-système d'audit du noyau.

_SYSTEMD_CGROUP=, _SYSTEMD_SLICE=, _SYSTEMD_UNIT=, _SYSTEMD_USER_UNIT=, _SYSTEMD_USER_SLICE=, _SYSTEMD_SESSION=, _SYSTEMD_OWNER_UID=

Le chemin du groupe de contrôle dans la hiérarchie systemd, le nom de l'unité slice systemd, le nom de l'unité systemd, le nom de l'unité dans le gestionnaire utilisateur systemd (le cas échéant), l'identifiant de session systemd (le cas échéant), et l'UID propriétaire de l'unité utilisateur systemd ou de la session systemd (le cas échéant) du processus dont provient l'entrée du journal.

_SELINUX_CONTEXT=

Le contexte de sécurité SELinux (étiquette) du processus dont provient l'entrée du journal.

_SOURCE_REALTIME_TIMESTAMP=

L'horodatage de confiance le plus ancien du message, s'il est connu et différent de l'heure de réception du journal. L'horodatage est l'heure CLOCK_REALTIME en microsecondes, formatée en décimal.

_SOURCE_BOOTTIME_TIMESTAMP=

L'horodatage de confiance le plus ancien du message dans l'heure CLOCK_BOOTTIME, dans le même format que _SOURCE_REALTIME_TIMESTAMP=.

Ajouté dans la version 257.

_BOOT_ID=

L'identifiant de démarrage du noyau pour le démarrage pendant lequel le message a été généré, formaté en chaîne hexadécimale de 128 bits.

_MACHINE_ID=

L'identifiant de la machine de l'hôte d'origine, comme décrit dans

NAME

systemd.journal-fields — metadata fields in the journal

SYNOPSIS

_TRANSPORT=, _STREAM_ID=, _LINE_BREAK=, _HOSTNAME=, _MACHINE_ID=, _SYSTEMD_UNIT=, _SYSTEMD_USER_UNIT=, _SYSTEMD_SESSION=, _SYSTEMD_OWNER_UID=, _SYSTEMD_INVOCATION_ID=, _COMM=, _EXE=, _CMDLINE=, _UID=, _GID=, _CAP_EFFECTIVE=, _AUDIT_SESSION=, _AUDIT_LOGINUID=, _SYSTEMD_CGROUP=, _SOURCE_REALTIME_TIMESTAMP=, _BOOT_ID=, _JOB_ID=, _JOB_CMD=, _JOB_UID=, _LINE_SOURCE=, _PID=, _PPID=, _THREAD_ID=, _NAMESPACE=, _RUNTIME_SCOPE=, _KERNEL_DEVICE=, _KERNEL_SUBSYSTEM=, _UDEV_SYSNAME=, _UDEV_DEVNODE=, _UDEV_DEVLINK=, COREDUMP_UNIT=, COREDUMP_USER_UNIT=, OBJECT_PID=, OBJECT_UID=, OBJECT_GID=, OBJECT_COMM=, OBJECT_EXE=, OBJECT_CMDLINE=, OBJECT_AUDIT_SESSION=, OBJECT_AUDIT_LOGINUID=, OBJECT_SYSTEMD_CGROUP=, OBJECT_SYSTEMD_SESSION=, OBJECT_SYSTEMD_OWNER_UID=, OBJECT_SYSTEMD_UNIT=, OBJECT_SYSTEMD_USER_UNIT=, OBJECT_SYSTEMD_INVOCATION_ID=, __CURSOR=, __REALTIME_TIMESTAMP=, __MONOTONIC_TIMESTAMP=, __SEQNUM=, __SEQNUM_ID=

DESCRIPTION

When messages are logged into the systemd journal, they are associated with a set of metadata fields. These fields are key-value pairs that describe the origin, context, and nature of the message. This document lists and describes the most common fields.

Many of these fields are automatically populated by systemd-journald based on the context in which the message was logged. Others may be explicitly set by the logging application or by helper utilities.

Note that the set of available fields may change between versions, and new fields might be added.

STANDARD FIELDS

These fields are common across most log entries.

_TRANSPORT=

How the entry was received by the journal service. Valid transports are:

audit

for those read from the kernel audit subsystem

Added in version 227.

driver

for internally generated messages

Added in version 205.

syslog

for those received via the local syslog socket with the syslog protocol

Added in version 205.

journal

for those received via the native journal protocol

Added in version 205.

stdout

for those read from a service's standard output or error output

Added in version 205.

kernel

for those read from the kernel

Added in version 205.

_HOSTNAME=

The hostname of the originating host.

_MACHINE_ID=

The unique machine ID of the host, as stored in /etc/machine-id (see machine-id(5)).

_COMM=

The command name of the process that logged the message. This is usually limited to 15 characters.

_EXE=

The absolute path to the executable of the process that logged the message.

_CMDLINE=

The full command line of the process that logged the message.

_UID=

The real user ID of the process that logged the message.

_GID=

The real group ID of the process that logged the message.

_CAP_EFFECTIVE=

The effective capabilities of the process that logged the message, formatted as a space-separated list of capability names.

_AUDIT_SESSION=

The audit session ID of the process that logged the message.

_AUDIT_LOGINUID=

The login UID of the process that logged the message.

_SYSTEMD_UNIT=

The systemd unit name (e.g., sshd.service) of the service that logged the message. This field is only available for messages logged from within a systemd service or scope.

_SYSTEMD_USER_UNIT=

The systemd user unit name of the service that logged the message. This field is only available for messages logged from within a user systemd service or scope.

_SYSTEMD_SESSION=

The systemd session ID of the process that logged the message.

_SYSTEMD_OWNER_UID=

The UID of the user who owns the systemd session to which the logged process belongs.

_SYSTEMD_INVOCATION_ID=

The invocation ID for the runtime cycle of the unit the message was generated in, as available to processes of the unit in $INVOCATION_ID (see systemd.exec(5)).

Added in version 233.

_SOURCE_REALTIME_TIMESTAMP=

The timestamp of the log message as generated by the source process, using the system's CLOCK_REALTIME clock. This is typically the most accurate timestamp available for the event itself. This field is a decimal number representing microseconds since the epoch.

_BOOT_ID=

The boot ID of the system when the message was logged. This is a 128-bit identifier that changes with every boot.

_JOB_ID=, _JOB_CMD=, _JOB_UID=

These fields are set when logging occurs within the context of a systemd job (e.g., during boot or shutdown, or when mounting/unmounting filesystems). _JOB_ID is the numeric job ID, _JOB_CMD is the command that was executed, and _JOB_UID is the UID of the user who initiated the job.

Added in version 220.

_LINE_SOURCE=

Source information for log lines coming from the kernel or userspace. For kernel messages, this contains the kernel message ID. For userspace messages originating from stdout or stderr, this field contains the executable name, source file name, source line number, and source function name. The format is typically FILENAME:LINENUMBER:FUNCTION.

Added in version 235.

_PID=

The process ID (PID) of the process that logged the message.

_PPID=

The parent process ID (PPID) of the process that logged the message.

_THREAD_ID=

The thread ID (TID) of the thread that logged the message.

Added in version 248.

_RUNTIME_SCOPE=

A string field that specifies the runtime scope in which the message was logged. If "initrd", the log message was processed while the system was running inside the initrd. If "system", the log message was generated after the system switched execution to the host root filesystem.

Added in version 252.

UNIT SPECIFIC FIELDS

These fields are specific to messages generated by systemd units.

_STREAM_ID=

Only applies to "_TRANSPORT=stdout" records: specifies a randomized 128-bit ID assigned to the stream connection when it was first created. This ID is useful to reconstruct individual log streams from the log records: all log records carrying the same stream ID originate from the same stream.

Added in version 235.

_LINE_BREAK=

Only applies to "_TRANSPORT=stdout" records: indicates that the log message in the standard output/error stream was not terminated with a normal newline character ("\n", i.e. ASCII 10). Specifically, when set this field is one of nul (in case the line was terminated by a NUL byte), line-max (in case the maximum log line length was reached, as configured with LineMax= in journald.conf(5)), eof (if this was the last log record of a stream and the stream ended without a final newline character), or pid-change (if the process which generated the log output changed in the middle of a line). Note that this record is not generated when a normal newline character was used for marking the log line end.

Added in version 235.

_NAMESPACE=

If this file was written by a systemd-journald instance managing a journal namespace that is not the default, this field contains the namespace identifier. See systemd-journald.service(8) for details about journal namespaces.

Added in version 245.

KERNEL JOURNAL FIELDS

Kernel fields are fields that are used by messages originating in the kernel and stored in the journal.

_KERNEL_DEVICE=

The kernel device name. If the entry is associated to a block device, contains the major and minor numbers of the device node, separated by ":" and prefixed by "b". Similarly for character devices, but prefixed by "c". For network devices, this is the interface index prefixed by "n". For all other devices, this is the subsystem name prefixed by "+", followed by ":", followed by the kernel device name.

Added in version 189.

_KERNEL_SUBSYSTEM=

The kernel subsystem name.

Added in version 189.

_UDEV_SYSNAME=

The kernel device name as it shows up in the device tree below /sys/.

Added in version 189.

_UDEV_DEVNODE=

The device node path of this device in /dev/.

Added in version 189.

_UDEV_DEVLINK=

Additional symlink names pointing to the device node in /dev/. This field is frequently set more than once per entry.

Added in version 189.

FIELDS TO LOG ON BEHALF OF A DIFFERENT PROGRAM

Fields in this section are used by programs to specify that they are logging on behalf of another program or unit.

Fields used by the systemd-coredump coredump kernel helper:

COREDUMP_UNIT=, COREDUMP_USER_UNIT=

Used to annotate messages containing coredumps from system and session units. See coredumpctl(1).

Added in version 198.

Privileged programs (currently UID 0) may attach OBJECT_PID= to a message. This will instruct systemd-journald to attach additional fields on behalf of the caller:

OBJECT_PID=PID

PID of the program that this message pertains to.

Added in version 205.

OBJECT_UID=, OBJECT_GID=, OBJECT_COMM=, OBJECT_EXE=, OBJECT_CMDLINE=, OBJECT_AUDIT_SESSION=, OBJECT_AUDIT_LOGINUID=, OBJECT_SYSTEMD_CGROUP=, OBJECT_SYSTEMD_SESSION=, OBJECT_SYSTEMD_OWNER_UID=, OBJECT_SYSTEMD_UNIT=, OBJECT_SYSTEMD_USER_UNIT=

These are additional fields added automatically by systemd-journald. Their meaning is the same as _UID=, _GID=, _COMM=, _EXE=, _CMDLINE=, _AUDIT_SESSION=, _AUDIT_LOGINUID=, _SYSTEMD_CGROUP=, _SYSTEMD_SESSION=, _SYSTEMD_UNIT=, _SYSTEMD_USER_UNIT=, and _SYSTEMD_OWNER_UID= as described above, except that the process identified by PID is described, instead of the process which logged the message.

Added in version 205.

OBJECT_SYSTEMD_INVOCATION_ID=

An additional field added automatically by systemd-journald. The meaning is mostly the same as _SYSTEMD_INVOCATION_ID=, with the difference described above.

Added in version 235.

ADDRESS FIELDS

During serialization into external formats, such as the Journal Export Format[1] or the Journal JSON Format[2], the addresses of journal entries are serialized into fields prefixed with double underscores. Note that these are not proper fields when stored in the journal but for addressing metadata of entries. They cannot be written as part of structured log entries via calls such as sd_journal_send(3). They may also not be used as matches for sd_journal_add_match(3).

__CURSOR=

The cursor for the entry. A cursor is an opaque text string that uniquely describes the position of an entry in the journal and is portable across machines, platforms and journal files.

__REALTIME_TIMESTAMP=

The wallclock time (CLOCK_REALTIME) at the point in time the entry was received by the journal, in microseconds since the epoch UTC, formatted as a decimal. This has different properties from "_SOURCE_REALTIME_TIMESTAMP=", as it is usually a bit later but more likely to be monotonic.

__MONOTONIC_TIMESTAMP=

The monotonic time (CLOCK_MONOTONIC) at the point in time the entry was received by the journal in microseconds, formatted as a decimal. To be useful as an address for the entry, this should be combined with the boot ID in "_BOOT_ID=".

__SEQNUM=, __SEQNUM_ID=

The sequence number (and associated sequence number ID) of this journal entry in the journal file it originates from. See sd_journal_get_seqnum(3) for details.

Added in version 254.

systemd.journal-fields

Champs de journal de systemd

DESCRIPTION

Le journal système de systemd enregistre des champs de journal spécifiques et peut être étendu avec des champs définis par l'utilisateur. Les champs de journal sont des paires clé-valeur qui identifient des informations spécifiques sur un événement de journal. Il existe des champs prédéfinis par systemd et des champs personnalisés que les applications peuvent définir.

CHAMP JOURNAL UTILISATEUR

Les champs du journal utilisateur sont ceux qui sont définis par les applications utilisateur. Par exemple, une application web peut enregistrer le nom d'utilisateur connecté comme _USER_ID.

  • _COMM : Le nom de la commande (tronqué à 15 caractères).
  • _EXE : Le chemin d'accès complet du binaire exécutable.
  • _CMDLINE : La ligne de commande complète passée au processus.
  • _UID : L'ID d'utilisateur effectif du processus.
  • _GID : L'ID de groupe effectif du processus.
  • _PID : L'ID du processus.
  • _PPID : L'ID du processus parent.
  • _CgroupID : L'identifiant du cgroup du processus.
  • _SYSTEMD_UNIT : L'unité systemd qui a lancé le processus.
  • _TRANSPORT : Le mécanisme de transport utilisé pour la journalisation (par exemple, `stdout`, `syslog`).
  • _HOSTNAME : Le nom d'hôte du système.
  • _MACHINE_ID : L'ID machine du système.
  • _BOOT_ID : L'ID du démarrage actuel.
  • _T kurang : La date et l'heure de l'événement.
  • _SOURCE_REALTIME_TIMESTAMP : Le timestamp de l'événement tel qu'il a été vu par la source.
  • _SELINUX_CONTEXT : Le contexte SELinux du processus.
  • _AUDIT_SESSION : L'ID de la session audit.
  • _AUDIT_LOGINUID : L'ID de connexion audit.

CHAMP JOURNAL CONFIANT

Les champs de journal fiables sont ceux qui sont vérifiés cryptographiquement pour leur intégrité et leur authenticité. Ces champs sont généralement générés par le noyau ou des services de confiance.

  • _KERNEL_MESSAGE : Les messages du noyau.
  • _SECURE : Indicateur pour les messages sécurisés.

CHAMP JOURNAL NOYAU

Les champs spécifiques au noyau sont enregistrés lorsque le noyau génère des messages.

  • _KERNEL_MESSAGE : Le message du noyau.
  • _LINUX_SCHED_POLICY : La politique de planification du noyau.
  • _LINUX_SCHED_PRIORITY : La priorité de planification du noyau.
  • _LINUX_SYSCALL : Le numéro de l'appel système.
  • _LINUX_SCHED_AFFINITY : L'affinité du processeur du processus.

CHAMPS À ENREGISTRER POUR LE COMPTE D'UN PROGRAMME DIFFÉRENT

Il est possible d'enregistrer des messages au nom d'un autre programme. Ceci est souvent utilisé par les démons qui lancent d'autres processus.

  • _COMM= : Le nom de la commande du programme d'origine.
  • _EXE= : Le chemin d'accès complet du binaire exécutable du programme d'origine.
  • _CMDLINE= : La ligne de commande complète du programme d'origine.
  • _UID= : L'ID d'utilisateur effectif du programme d'origine.
  • _GID= : L'ID de groupe effectif du programme d'origine.
  • _PID= : L'ID du processus du programme d'origine.
  • _PPID= : L'ID du processus parent du programme d'origine.
  • _CgroupID= : L'identifiant du cgroup du programme d'origine.
  • _SYSTEMD_UNIT= : L'unité systemd qui a lancé le programme d'origine.

CHAMPS D'ADRESSE

Les champs d'adresse sont utilisés pour enregistrer des informations d'adresse réseau.

  • _IP4_ADDRESS : Adresse IPv4.
  • _IP4_PORT : Port IPv4.
  • _IP6_ADDRESS : Adresse IPv6.
  • _IP6_PORT : Port IPv6.
  • _INTERFACE : Nom de l'interface réseau.
  • _REMOTE_HOST : Nom d'hôte distant.
  • _REMOTE_USER : Nom d'utilisateur distant.
