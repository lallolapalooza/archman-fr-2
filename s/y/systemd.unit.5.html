DESCRIPTION

Un fichier d'unité est un fichier texte brut de style ini qui encode des informations sur un service, une socket, un périphérique, un point de montage, un point de montage automatique, un fichier ou une partition swap, une cible de démarrage, un chemin de système de fichiers surveillé, un minuteur contrôlé et supervisé par systemd(1), une tranche de gestion des ressources ou un groupe de processus créés extérieurement. Voir systemd.syntax(7) pour une description générale de la syntaxe.

Cette page de manuel liste les options de configuration courantes de tous les types d'unités. Ces options doivent être configurées dans les sections [Unit] ou [Install] des fichiers d'unité.

En plus des sections génériques [Unit] et [Install] décrites ici, chaque unité peut avoir une section spécifique au type, par exemple [Service] pour une unité de service. Voir les pages de manuel respectives pour plus d'informations : systemd.service(5), systemd.socket(5), systemd.device(5), systemd.mount(5), systemd.automount(5), systemd.swap(5), systemd.target(5), systemd.path(5), systemd.timer(5), systemd.slice(5), systemd.scope(5).

Les fichiers d'unité sont chargés à partir d'un ensemble de chemins déterminés lors de la compilation, décrits dans la section suivante.

Les noms d'unités valides se composent d'un « préfixe de nom d'unité » et d'un suffixe spécifiant le type d'unité qui commence par un point. Le « préfixe de nom d'unité » doit être composé d'un ou plusieurs caractères valides (lettres ASCII, chiffres, « : », « - », « _ », « . » et « \ »). La longueur totale du nom d'unité, y compris le suffixe, ne doit pas dépasser 255 caractères. Le suffixe de type d'unité doit être l'un des « .service », « .socket », « .device », « .mount », « .automount », « .swap », « .target », « .path », « .timer », « .slice » ou « .scope ».

Les noms d'unités peuvent être paramétrés par un seul argument appelé le « nom d'instance ». L'unité est alors construite à partir d'un « fichier modèle » qui sert de définition à plusieurs services ou autres unités. Une unité modèle doit avoir un seul « @ » à la fin du préfixe du nom d'unité (juste avant le suffixe de type). Le nom de l'unité complète est formé en insérant le nom d'instance entre « @ » et le suffixe de type d'unité. Dans le fichier d'unité lui-même, le paramètre d'instance peut être référencé en utilisant « %i » et d'autres spécificateurs, voir ci-dessous.

Les fichiers d'unité peuvent contenir des options supplémentaires en plus de celles listées ici. Si systemd rencontre une option inconnue, il écrira un message d'avertissement dans les logs mais continuera à charger l'unité. Si une option ou un nom de section est préfixé par X-, il est complètement ignoré par systemd. Les options au sein d'une section ignorée n'ont pas besoin du préfixe. Les applications peuvent l'utiliser pour inclure des informations supplémentaires dans les fichiers d'unité. Pour accéder à ces options, les applications doivent analyser les fichiers d'unité elles-mêmes.

Les unités peuvent être aliasées (avoir un nom alternatif), en créant un lien symbolique du nouveau nom vers le nom existant dans l'un des chemins de recherche d'unités. Par exemple, systemd-networkd.service a l'alias dbus-org.freedesktop.network1.service, créé lors de l'installation sous forme de lien symbolique, donc lorsque systemd est invité via D-Bus à charger dbus-org.freedesktop.network1.service, il chargera systemd-networkd.service. Comme autre exemple, default.target — la cible système par défaut démarrée au démarrage — est couramment aliasée en multi-user.target ou graphical.target pour sélectionner ce qui est démarré par défaut. Les noms d'alias peuvent être utilisés dans des commandes comme disable, start, stop, status, et similaires, ainsi que dans toutes les directives de dépendance d'unité, y compris Wants=, Requires=, Before=, After=. Les alias ne peuvent pas être utilisés avec la commande preset.

Les alias respectent les restrictions suivantes : une unité d'un certain type (« .service », « .socket », ... ) ne peut être aliasée que par un nom ayant le même suffixe de type. Une unité simple (pas un modèle ni une instance) ne peut être aliasée que par un nom simple. Une instance de modèle ne peut être aliasée que par une autre instance de modèle, et la partie instance doit être identique. Un modèle peut être aliasé par un autre modèle (auquel cas l'alias s'applique à toutes les instances du modèle). À titre de cas particulier, une instance de modèle (par ex. « alias@inst.service ») peut être un lien symbolique vers un modèle différent (par ex. « template@inst.service »). Dans ce cas, seule cette instance spécifique est aliasée, tandis que d'autres instances du modèle (par ex. « alias@foo.service », « alias@bar.service ») ne sont pas aliasées. Ces règles préservent l'exigence que l'instance (le cas échéant) est toujours définie de manière unique pour une unité donnée et tous ses alias. La cible du lien symbolique d'alias doit pointer vers un emplacement de fichier d'unité valide, c'est-à-dire que le nom du fichier cible doit correspondre au nom du fichier source comme décrit, et le chemin de destination doit se trouver dans l'un des chemins de recherche d'unités, voir la section CHEMIN DE RECHERCHE DES FICHIERS D'UNITÉ ci-dessous pour plus de détails. Notez que le fichier cible peut ne pas exister, c'est-à-dire que le lien symbolique peut être orphelin.

Les fichiers d'unité peuvent spécifier des alias via la directive Alias= dans la section [Install]. Lorsque l'unité est activée, des liens symboliques seront créés pour ces noms, et supprimés lorsque l'unité est désactivée. Par exemple, reboot.target spécifie Alias=ctrl-alt-del.target, donc lorsqu'elle est activée, le lien symbolique /etc/systemd/system/ctrl-alt-del.target pointant vers le fichier reboot.target sera créé, et lorsque Ctrl+Alt+Del est invoqué, systemd recherchera ctrl-alt-del.target, suivra le lien symbolique vers reboot.target, et exécutera reboot.service dans le cadre de cette cible. systemd ne consulte pas du tout la section [Install] pendant le fonctionnement normal, donc toutes les directives de cette section n'ont d'effet que par le biais des liens symboliques créés lors de l'activation.

Parallèlement au fichier d'unité foo.service, le répertoire foo.service.wants/ peut exister. Tous les fichiers d'unité liés par un lien symbolique de ce répertoire sont implicitement ajoutés comme dépendances de type Wants= à l'unité. Une fonctionnalité similaire existe pour les dépendances de type Requires=, le suffixe du répertoire est .requires/ dans ce cas. SÉMANTIQUE DE WANTS= ET REQUIRES=

Voir ci-dessous la sémantique de Wants= et Requires=. La manière préférée de créer des liens symboliques dans les répertoires .wants/ ou .requires/ est de spécifier la dépendance dans la section [Install] de l'unité cible, et de créer le lien symbolique dans le système de fichiers avec les commandes enable ou preset de systemctl(1). La cible peut être une unité normale (soit une unité simple, soit une instance spécifique d'une unité modèle). Dans le cas où l'unité source est un modèle, la cible peut également être un modèle, auquel cas l'instance sera « propagée » à l'unité cible pour former une instance d'unité valide. La cible des liens symboliques dans .wants/ ou .requires/ doit donc pointer vers un emplacement de fichier d'unité valide, c'est-à-dire que le nom de la cible du lien symbolique doit satisfaire les exigences décrites, et le chemin de destination doit se trouver dans l'un des chemins de recherche d'unités, voir la section PATH DE CHARGEMENT DES FICHIERS D'UNITÉ ci-dessous pour plus de détails. Notez que le fichier cible peut ne pas exister, c'est-à-dire que le lien symbolique peut être orphelin.

Parallèlement à un fichier d'unité foo.service, un répertoire « drop-in » foo.service.d/ peut exister. Tous les fichiers avec le suffixe « .conf » de ce répertoire seront fusionnés dans l'ordre alphabétique et analysés après que le fichier d'unité principal lui-même ait été analysé. Ceci est utile pour modifier ou ajouter des paramètres de configuration pour une unité, sans avoir à modifier les fichiers d'unité. Chaque fichier drop-in doit contenir des en-têtes de section appropriés. Pour les unités instanciées, cette logique recherchera d'abord le sous-répertoire « .d/ » de l'instance (par exemple, « foo@bar.service.d/ ») et lira ses fichiers « .conf », suivi du sous-répertoire « .d/ » du modèle (par exemple, « foo@.service.d/ ») et des fichiers « .conf » qui s'y trouvent. De plus, pour les noms d'unités contenant des tirets (« - »), l'ensemble des répertoires générés en tronquant répétitivement le nom de l'unité après tous les tirets est également recherché. Spécifiquement, pour un nom d'unité foo-bar-baz.service, non seulement le répertoire drop-in régulier foo-bar-baz.service.d/ est recherché, mais aussi foo-bar-.service.d/ et foo-.service.d/. Ceci est utile pour définir des drop-ins communs pour un ensemble d'unités liées, dont les noms commencent par un préfixe commun. Ce schéma est particulièrement utile pour les unités de montage, de montage automatique et de tranche, dont la structure de nommage systématique est construite autour des tirets comme séparateurs de composants. Notez que des fichiers drop-in de nom identique plus loin dans la hiérarchie des préfixes remplacent ceux plus haut, c'est-à-dire que foo-bar-.service.d/10-override.conf remplace foo-.service.d/10-override.conf.

Dans les cas d'alias d'unités (décrits ci-dessus), les drop-ins pour le nom alias et tous les alias sont chargés. Dans l'exemple de default.target qui alias graphical.target, default.target.d/, default.target.wants/, default.target.requires/, graphical.target.d/, graphical.target.wants/, graphical.target.requires/ seraient tous lus. Pour les modèles, les drop-ins pour le modèle, tout alias de modèle, l'instance de modèle, et tous les instances d'alias sont lus. Lorsqu'une instance de modèle spécifique est uniquement alias, les drop-ins pour le modèle cible, l'instance de modèle cible, et l'instance de modèle alias sont lus.

En plus de /etc/systemd/system, les répertoires drop-in « .d/ » pour les services système peuvent être placés dans /usr/lib/systemd/system ou /run/systemd/system. Les fichiers drop-in dans /etc/ ont la priorité sur ceux dans /run/ qui ont eux-mêmes la priorité sur ceux dans /usr/lib/. Les fichiers drop-in sous l'un de ces répertoires ont la priorité sur les fichiers d'unité où qu'ils se trouvent. Plusieurs fichiers drop-in avec des noms différents sont appliqués dans l'ordre lexicographique, quel que soit le répertoire dans lequel ils résident.

Les unités prennent également en charge un drop-in de niveau supérieur avec type.d/, où type peut être par exemple « service » ou « socket », ce qui permet de modifier ou d'ajouter des paramètres à tous les fichiers d'unité correspondants sur le système. Le formatage et la priorité d'application des configurations drop-in suivent ce qui est défini ci-dessus. Les fichiers dans type.d/ ont une priorité inférieure à celle des fichiers dans les répertoires de remplacement spécifiques au nom. Les règles habituelles s'appliquent : plusieurs fichiers drop-in avec des noms différents sont appliqués dans l'ordre lexicographique, quel que soit le répertoire dans lequel ils résident, donc un fichier dans type.d/ s'applique à une unité uniquement s'il n'y a pas de drop-ins ou de masques de ce nom dans des répertoires de priorité supérieure. Voir Exemples.

Notez que si systemd offre un système de dépendances flexible entre les unités, il est recommandé d'utiliser cette fonctionnalité avec parcimonie et de s'appuyer plutôt sur des techniques telles que l'activation basée sur le bus ou sur socket, qui rendent les dépendances implicites, résultant en un système plus simple et plus flexible.

Comme mentionné ci-dessus, une unité peut être instanciée à partir d'un fichier modèle. Cela permet la création de plusieurs unités à partir d'un seul fichier de configuration. Si systemd recherche un fichier de configuration d'unité, il recherchera d'abord le nom d'unité littéral dans le système de fichiers. Si cela ne donne aucun résultat et que le nom d'unité contient un caractère « @ », systemd recherchera un modèle d'unité qui partage le même nom mais avec la chaîne d'instance (c'est-à-dire la partie entre le caractère « @ » et le suffixe) supprimée. Exemple : si un service getty@tty3.service est demandé et qu'aucun fichier de ce nom n'est trouvé, systemd recherchera getty@.service et instanciera un service à partir de ce fichier de configuration s'il est trouvé.

Pour faire référence à la chaîne d'instance à partir du fichier de configuration, vous pouvez utiliser le spécificateur spécial « %i » dans bon nombre des options de configuration. Voir ci-dessous pour les détails.

Si un fichier d'unité est vide (c'est-à-dire a une taille de fichier de 0) ou est lié symboliquement à /dev/null, sa configuration ne sera pas chargée et il apparaîtra avec un état de chargement « masqué », et ne pourra pas être activé. Utilisez ceci comme un moyen efficace de désactiver complètement une unité, rendant impossible son démarrage, même manuellement.

Le format des fichiers d'unité est couvert par la Promesse de portabilité et de stabilité de l'interface[1].

ÉCHAPPEMENT DE CHAINES POUR INCLUSION DANS LES NOMS D'UNITES

Il est parfois utile de convertir des chaînes arbitraires en noms d'unités. Pour faciliter cela, une méthode d'échappement de chaînes est utilisée, afin de mapper des chaînes contenant des valeurs d'octets arbitraires (sauf NUL) dans des noms d'unités valides et leur jeu de caractères restreint. Un cas spécial courant concerne les noms d'unités qui reflètent les chemins d'objets dans la hiérarchie du système de fichiers. Exemple : une unité de périphérique dev-sda.device fait référence à un périphérique avec le nœud de périphérique /dev/sda dans le système de fichiers.

L'algorithme d'échappement fonctionne comme suit : étant donné une chaîne, tout caractère « / » est remplacé par « - », et tous les autres caractères qui ne sont pas alphanumériques ASCII, « : », « _ » ou « . » sont remplacés par des échappements de style C « \x2d ». De plus, « . » est remplacé par un tel échappement de style C lorsqu'il apparaît comme premier caractère dans la chaîne échappée.

Lorsque l'entrée est qualifiée de chemin absolu du système de fichiers, cet algorithme est légèrement étendu : le chemin vers le répertoire racine « / » est encodé comme un simple tiret « - ». De plus, tous les caractères « / » de début, de fin ou dupliqués sont supprimés de la chaîne avant transformation. Exemple : /foo//bar/baz/ devient « foo-bar-baz ».

Cet échappement est entièrement réversible, tant qu'il est connu si la chaîne échappée était un chemin (les résultats de déséchappement sont différents pour les chemins et les chaînes non-chemins). La commande systemd-escape(1) peut être utilisée pour appliquer et inverser l'échappement sur des chaînes arbitraires. Utilisez systemd-escape --path pour échapper les chaînes de chemins, et systemd-escape sans --path sinon.

DÉPENDANCES AUTOMATIQUES

Dépendances Implicites

Un certain nombre de dépendances d'unités sont établies implicitement, selon le type d'unité et la configuration de l'unité. Ces dépendances implicites peuvent rendre le fichier de configuration d'unité plus propre. Pour les dépendances implicites de chaque type d'unité, veuillez vous référer à la section « Dépendances Implicites » des pages man respectives.

Par exemple, les unités de service avec Type=dbus acquièrent automatiquement des dépendances de type Requires= et After= sur dbus.socket. Voir systemd.service(5) pour les détails.

Dépendances Par Défaut

Les dépendances par défaut sont similaires aux dépendances implicites, mais elles peuvent être activées ou désactivées en définissant DefaultDependencies= à yes (par défaut) et no, tandis que les dépendances implicites sont toujours effectives. Voir la section « Dépendances Par Défaut » des pages man respectives pour l'effet de l'activation de DefaultDependencies= dans chaque type d'unité.

Par exemple, les unités cibles complèteront toutes les dépendances configurées de type Wants= ou Requires= avec des dépendances de type After=. Voir systemd.target(5) pour les détails. Notez que ce comportement peut être désactivé en définissant DefaultDependencies=no dans les unités spécifiées, ou il peut être sélectivement remplacé via une dépendance Before= explicite.

Moreover, additional units might be loaded into systemd from directories not on the unit load path by creating a symlink pointing to a unit file in the directories. You can use systemctl link for this; see systemctl(1). The file system where the linked unit files are located must be accessible when systemd is started (e.g. anything underneath /home/ or /var/ is not allowed, unless those directories are located on the root file system).

It is important to distinguish "linked unit files" from "unit file aliases": any symlink where the symlink target is within the unit load path becomes an alias: the source name and the target file name must satisfy specific constraints listed above in the discussion of aliases, but the symlink target does not have to exist, and in fact the symlink target path is not used, except to check whether the target is within the unit load path. In contrast, a symlink which goes outside of the unit load path signifies a linked unit file. The symlink is followed when loading the file, but the destination name is otherwise unused (and may even not be a valid unit file name). For example, symlinks /etc/systemd/system/alias1.service → service1.service, /etc/systemd/system/alias2.service → /usr/lib/systemd/service1.service, /etc/systemd/system/alias3.service → /etc/systemd/system/service1.service are all valid aliases and service1.service will have four names, even if the unit file is located at /run/systemd/system/service1.service. In contrast, a symlink /etc/systemd/system/link1.service → ../link1_service_file means that link1.service is a "linked unit" and the contents of /etc/systemd/link1_service_file provide its configuration.

UNIT GARBAGE COLLECTION

The system and service manager loads a unit's configuration automatically when a unit is referenced for the first time. It will automatically unload the unit configuration and state again when the unit is not needed anymore ("garbage collection"). A unit may be referenced through a number of different mechanisms:

1.Another loaded unit references it with a dependency such as After=, Wants=, ...
2.The unit is currently starting, running, reloading or stopping.
3.The unit is currently in the failed state. (But see below.)
4.A job for the unit is pending.
5.The unit is pinned by an active IPC client program.
6.The unit is a special "perpetual" unit that is always active and loaded. Examples for perpetual units are the root mount unit -.mount or the scope unit init.scope that the service manager itself lives in.
7.The unit has running processes associated with it.

The garbage collection logic may be altered with the CollectMode= option, which allows configuration whether automatic unloading of units that are in failed state is permissible, see below.

Note that when a unit's configuration and state is unloaded, all execution results, such as exit codes, exit signals, resource consumption and other statistics are lost, except for what is stored in the log subsystem.

Use systemctl daemon-reload or an equivalent command to reload unit configuration while the unit is already loaded. In this case, all configuration settings are flushed out and replaced with the new configuration (which however might not be in effect immediately), however all runtime state is saved/restored.

[UNIT] SECTION OPTIONS

The unit file may include a [Unit] section, which carries generic information about the unit that is not dependent on the type of unit:

Description=

A brief, meaningful, human-readable text identifying the unit. This may be used by systemd (and suitable UIs) as a user-visible label for the unit, so this string should identify the unit rather than just describe it, despite the name. This string also should not just repeat the unit name. "Apache HTTP Server" or "Postfix Mail Server" are good examples. Bad examples are "high-performance lightweight HTTP server" (too generic) or "Apache" (meaningless for people who do not know the Apache HTTP server project, duplicates the unit name). systemd may use this string as a noun in status messages ("Starting Description...", "Started Description.", "Reached target Description.", "Failed to start Description."), so it should be capitalized, and should not be a full sentence, or a phrase with a verb conjugated in the present continuous, or end in a full stop. Bad examples include "exiting the container", "updating the database once per day.", or "OpenSSH server second instance daemon".

Added in version 201.

Documentation=

A space-separated list of URIs referencing documentation for this unit or its configuration. Accepted are only URIs of the types "http://", "https://", "file:", "info:", "man:". For more information about the syntax of these URIs, see uri(7). The URIs should be listed in order of relevance, starting with the most relevant. It is a good idea to first reference documentation that explains what the unit's purpose is, followed by how it is configured, followed by any other related documentation. This option may be specified more than once, in which case the specified list of URIs is merged. If the empty string is assigned to this option, the list is reset and all prior assignments will have no effect.

Wants=

Configures (weak) requirement dependencies on other units. This option may be specified more than once or multiple space-separated units may be specified in one option in which case dependencies for all listed names will be created. Dependencies of this type may also be configured outside of the unit configuration file by adding a symlink to a .wants/ directory accompanying the unit file. For details, see above.

Units listed in this option will be started if the configuring unit is. However, if the listed units fail to start or cannot be added to the transaction, this has no impact on the validity of the transaction as a whole, and this unit will still be started. This is the recommended way to hook the start-up of one unit to the start-up of another unit.

Note that requirement dependencies do not influence the order in which services are started or stopped. This has to be configured independently with the After= or Before= options. If unit foo.service pulls in unit bar.service as configured with Wan

ts= et aucune ordonnance n'est configurée avec Après= ou Avant=, alors les deux unités seront démarrées simultanément et sans délai entre elles si foo.service est activé.

Ajouté dans la version 201.

Requires=

Similaire à Wants=, mais déclare une dépendance plus forte. Les dépendances de ce type peuvent également être configurées en ajoutant un lien symbolique au répertoire .requires/ qui accompagne le fichier d'unité.

Si cette unité est activée, les unités listées seront également activées. Si l'une des autres unités échoue à s'activer, et qu'une dépendance d'ordonnancement Après= sur l'unité défaillante est définie, cette unité ne sera pas démarrée. De plus, avec ou sans spécification de Après=, cette unité sera arrêtée (ou redémarrée) si l'une des autres unités est explicitement arrêtée (ou redémarrée).

Souvent, il est préférable d'utiliser Wants= plutôt que Requires= afin d'obtenir un système plus robuste face aux services défaillants.

Notez que ce type de dépendance n'implique pas que l'autre unité doit toujours être dans un état actif lorsque cette unité est en cours d'exécution. En particulier : les vérifications de condition d'échec (telles que ConditionPathExists=, ConditionPathIsSymbolicLink=, ... — voir ci-dessous) ne provoquent pas l'échec du travail de démarrage d'une unité ayant une dépendance Requires= sur elle. De plus, certains types d'unités peuvent se désactiver d'eux-mêmes (par exemple, un processus de service peut décider de se terminer proprement, ou un périphérique peut être débranché par l'utilisateur), ce qui n'est pas propagé aux unités ayant une dépendance Requires=. Utilisez le type de dépendance BindsTo= conjointement avec Après= pour garantir qu'une unité ne puisse jamais être dans un état actif sans qu'une autre unité spécifique ne le soit également (voir ci-dessous).

Ajouté dans la version 201.

Requisite=

Similaire à Requires=. Cependant, si les unités listées ici ne sont pas déjà démarrées, elles ne seront pas démarrées et le démarrage de cette unité échouera immédiatement. Requisite= n'implique pas de dépendance d'ordonnancement, même si les deux unités sont démarrées dans la même transaction. Par conséquent, ce paramètre doit généralement être combiné avec Après=, pour garantir que cette unité ne démarre pas avant l'autre unité.

Lorsque Requisite=b.service est utilisé sur a.service, cette dépendance apparaîtra comme RequisiteOf=a.service dans la liste des propriétés de b.service. La dépendance RequisiteOf= ne peut pas être spécifiée directement.

Ajouté dans la version 201.

BindsTo=

Configure des dépendances de nécessité, très similaires en style à Requires=. Cependant, ce type de dépendance est plus fort : en plus de l'effet de Requires=, il déclare que si l'unité à laquelle elle est liée est arrêtée, cette unité sera également arrêtée. Cela signifie qu'une unité liée à une autre unité qui entre soudainement dans un état inactif sera également arrêtée. Les unités peuvent soudainement, de manière inattendue, entrer dans un état inactif pour différentes raisons : le processus principal d'une unité de service peut se terminer de son propre chef, le périphérique sous-jacent d'une unité de périphérique peut être débranché ou le point de montage d'une unité de montage peut être démonté sans l'intervention du système et du gestionnaire de services.

Lorsqu'il est utilisé conjointement avec Après= sur la même unité, le comportement de BindsTo= est encore plus fort. Dans ce cas, l'unité à laquelle elle est liée doit strictement être dans un état actif pour que cette unité le soit également. Cela signifie non seulement qu'une unité liée à une autre unité qui entre soudainement dans un état inactif, mais aussi une unité liée à une autre unité qui est ignorée en raison d'une condition non remplie (telle que ConditionPathExists=, ConditionPathIsSymbolicLink=, ... — voir ci-dessous) sera arrêtée, si elle est en cours d'exécution. Par conséquent, dans de nombreux cas, il est préférable de combiner BindsTo= avec Après=.

Lorsque BindsTo=b.service est utilisé sur a.service, cette dépendance apparaîtra comme BoundBy=a.service dans la liste des propriétés de b.service. La dépendance BoundBy= ne peut pas être spécifiée directement.

Ajouté dans la version 201.

PartOf=

Configure des dépendances similaires à Requires=, mais limitées à l'arrêt et au redémarrage des unités. Lorsque systemd arrête ou redémarre les unités listées ici, l'action est propagée à cette unité. Notez qu'il s'agit d'une dépendance unidirectionnelle  — les changements sur cette unité n'affectent pas les unités listées.

Lorsque PartOf=b.service est utilisé sur a.service, cette dépendance apparaîtra comme ConsistsOf=a.service dans la liste des propriétés de b.service. La dépendance ConsistsOf= ne peut pas être spécifiée directement.

Ajouté dans la version 201.

Upholds=

Configure des dépendances similaires à Wants=, mais tant que cette unité est active, toutes les unités listées dans Upholds= sont démarrées lorsqu'elles sont trouvées inactives ou en échec, et aucun travail n'est mis en file d'attente pour elles. Alors qu'une dépendance Wants= sur une autre unité a un effet unique lorsque cette unité démarre, une dépendance Upholds= sur elle a un effet continu, redémarrant constamment l'unité si nécessaire. Ceci est une alternative au paramètre Restart= des unités de service, pour s'assurer qu'elles restent en cours d'exécution quoi qu'il arrive. Le redémarrage se fait sans délai, et la limite de débit habituelle par unité s'applique.

Lorsque Upholds=b.service est utilisé sur a.service, cette dépendance apparaîtra comme UpheldBy=a.service dans la liste des propriétés de b.service.

Ajouté dans la version 249.

Conflicts=

Une liste d'unités séparées par des espaces. Configure des dépendances de nécessité négatives. Si une unité a une exigence Conflicts= sur un ensemble d'autres unités, son démarrage arrêtera toutes ces unités et le démarrage de l'une d'entre elles l'arrêtera.

Notez que ce paramètre n'implique pas de dépendance d'ordonnancement, de manière similaire aux dépendances Wants= et Requires= décrites ci-dessus. Cela signifie que pour garantir que l'unité conflituelle est arrêtée avant que l'autre unité ne démarre, une dépendance Après= ou Avant= doit être déclarée. Peu importe laquelle des deux dépendances d'ordonnancement est utilisée, car les travaux d'arrêt sont toujours ordonnancés avant les travaux de démarrage, voir la discussion dans Avant=/Après= ci-dessous.

Si l'unité A qui entre en conflit avec l'unité B est planifiée pour démarrer en même temps que B, la transaction échouera (si les deux sont des parties requises de la transaction) ou sera modifiée pour être corrigée (si un ou les deux travaux ne sont pas une partie requise de la transaction). Dans ce dernier cas, le travail qui n'est pas requis sera supprimé, ou si les deux ne sont pas requis, l'unité qui entre en conflit sera démarrée et l'unité en conflit sera arrêtée.

Ajouté dans la version 201.

Avant=, Après=

Ces deux paramètres attendent une liste d'unités séparées par des espaces. Ils peuvent être spécifiés plusieurs fois, auquel cas des dépendances pour tous les noms listés sont créées.

Ces deux paramètres configurent des dépendances d'ordonnancement entre les unités. Si l'unité foo.service contient le paramètre Avant=bar.service et que les deux unités sont démarrées, le démarrage de bar.service est retardé jusqu'à ce que foo.service ait terminé son démarrage. Après= est l'inverse de Avant=, c'est-à-dire que tandis que Avant= garantit que l'unité configurée est démarrée avant que l'unité listée ne commence à démarrer, Après= garantit le contraire, que l'unité listée est complètement démarrée avant que l'unité configurée ne démarre.

Lorsque deux unités ayant une dépendance d'ordonnancement entre elles sont arrêtées, l'inverse de l'ordre de démarrage est appliqué. C'est-à-dire que si une unité est configurée avec Après= sur une autre unité, la première est arrêtée avant la seconde si les deux sont arrêtées. Étant donné deux unités ayant une dépendance d'ordonnancement entre elles, si une unité est arrêtée et l'autre est démarrée, l'arrêt est ordonnancé avant le démarrage. Peu importe si la dépendance d'ordonnancement est Après= ou Avant=, dans ce cas. Il n'importe pas non plus laquelle des deux est arrêtée, tant que l'une est arrêtée et l'autre est démarrée ; l'arrêt est ordonnancé avant le démarrage dans tous les cas. Si deux unités n'ont aucune dépendance d'ordonnancement entre elles, elles sont arrêtées ou démarrées simultanément, et aucun ordonnancement n'a lieu. Il dépend du type d'unité quand précisément une unité a terminé son démarrage. Plus important encore, pour les unités de service, le démarrage est considéré comme terminé aux fins de Avant=/Après= lorsque toutes ses commandes de démarrage configurées ont été invoquées et qu'elles ont échoué ou rapporté un succès de démarrage. Notez que cela inclut ExecStartPost= (ou ExecStopPost= pour le cas d'arrêt).

Notez que ces paramètres sont indépendants et orthogonaux aux dépendances de nécessité configurées par Requires=, Wants=, Requisite=, ou BindsTo=. C'est un modèle courant d'inclure un nom d'unité à la fois dans les options Après= et Wants=, auquel cas l'unité listée sera démarrée avant l'unité configurée avec ces options.

Notez que les dépendances Avant= sur les unités de périphérique n'ont aucun effet et ne sont pas prises en charge. Les périphériques deviennent généralement disponibles suite à un événement de branchement à chaud externe, et systemd crée l'unité de périphérique correspondante sans délai.

FailureAction=, SuccessAction=

Configure l'action à entreprendre lorsque l'unité s'arrête et entre dans un état de défaillance ou inactif. Prend l'une des valeurs none, reboot, reboot-force, reboot-immediate, poweroff, poweroff-force, poweroff-immediate, exit, exit-force, soft-reboot, soft-reboot-force, kexec, kexec-force, halt, halt-force et halt-immediate. En mode système, toutes les options sont autorisées. En mode utilisateur, seules none, exit et exit-force sont autorisées. Les deux options valent par défaut none.

De même, poweroff, poweroff-force, poweroff-immediate, kexec, kexec-force, halt, halt-force et halt-immediate ont respectivement pour effet d'éteindre le système, d'exécuter kexec et d'arrêter le système avec des sémantiques similaires. exit provoque la sortie du gestionnaire en suivant la procédure d'arrêt normale, et exit-force le fait terminer sans arrêter les services. Lorsque exit ou exit-force est utilisé par défaut, le code de sortie du processus principal de l'unité (si applicable) est renvoyé par le gestionnaire de service. Cependant, cela peut être remplacé par FailureActionExitStatus=/SuccessActionExitStatus=, voir ci-dessous. soft-reboot déclenchera une opération de redémarrage de l'espace utilisateur. soft-reboot-force le fait aussi, mais ne passe pas par la transaction d'arrêt au préalable.

Configure la limitation du taux de démarrage des unités. Les unités qui sont démarrées plus de limite fois dans un intervalle de temps intervalle ne sont plus autorisées à démarrer. À partir de ce moment, la logique de redémarrage est à nouveau activée. systemctl reset-failed provoquera la suppression du compteur de débit de redémarrage d'un service, ce qui est utile si l'administrateur souhaite démarrer manuellement une unité et que la limite de démarrage interfère avec cela. La limitation de débit est appliquée après l'exécution de toutes les vérifications de condition d'unité, et par conséquent, les activations d'unité avec des conditions échouées ne comptent pas dans la limite de débit.

Lorsqu'une unité est déchargée en raison de la logique de collecte des déchets (voir ci-dessus), ses compteurs de limite de débit sont également vidés. Cela signifie que la configuration d'une limite de débit de démarrage pour une unité qui n'est pas référencée en continu n'a aucun effet.

Ce paramètre ne s'applique pas aux unités de type slice, target, device et scope, car ce sont des types d'unités dont l'activation peut soit ne jamais échouer, soit réussir une seule fois.

Conditions et Asserts

Les fichiers d'unité peuvent également inclure un certain nombre de paramètres Condition...= et Assert...=. Avant que l'unité ne soit démarrée, systemd vérifiera que les conditions et les asserts spécifiés sont vrais. Sinon, le démarrage de l'unité sera (presque silencieusement) ignoré (dans le cas des conditions), ou annulé avec un message d'erreur (dans le cas des asserts). L'échec des conditions ou des asserts ne déplacera pas l'unité dans l'état "échoué". Les conditions et les asserts sont vérifiés au moment où le travail de démarrage mis en file d'attente doit être exécuté. Les dépendances d'ordonnancement sont toujours respectées, de sorte que d'autres unités sont toujours tirées et ordonnancées comme si cette unité avait été activée avec succès, et que les conditions et les asserts sont exécutés au moment précis où l'unité démarrerait normalement et peuvent ainsi valider l'état du système après que les unités ordonnancées avant aient terminé leur initialisation. Utilisez les expressions conditionnelles pour ignorer les unités qui ne s'appliquent pas au système local, par exemple parce que le noyau ou l'environnement d'exécution ne nécessitent pas leur fonctionnalité.

Si plusieurs conditions sont spécifiées, l'unité sera exécutée si toutes s'appliquent (c'est-à-dire qu'un ET logique est appliqué). Les vérifications de conditions peuvent utiliser un symbole pipe (|) après le signe égal (Condition...=|...) , ce qui fait de la condition une condition de déclenchement. S'il existe au moins une condition de déclenchement définie pour une unité, alors l'unité sera démarrée si au moins une des conditions de déclenchement de l'unité s'applique et si toutes les conditions régulières (c'est-à-dire non déclenchantes) s'appliquent. Si vous préfixez un argument avec le symbole pipe et un point d'exclamation, le symbole pipe doit être passé en premier, le point d'exclamation ensuite. Si l'une de ces options se voit attribuer une chaîne vide, la liste des conditions est complètement réinitialisée, tous les paramètres de conditions précédents (quel qu'ils soient) n'auront aucun effet.

Les options AssertArchitecture=, AssertVirtualization=, etc. sont similaires aux conditions mais font échouer le travail de démarrage (au lieu d'être ignoré). La vérification échouée est enregistrée. Les unités dont les conditions ne sont pas remplies sont considérées comme étant dans un état propre et seront collectées comme déchets si elles ne sont pas référencées. Cela signifie que lorsqu'elles sont interrogées, l'échec de la condition peut ou non apparaître dans l'état de l'unité.

Notez qu'aucune expression d'assertion ni de condition ne modifie l'état de l'unité. Notez également que toutes deux sont vérifiées au moment où le travail doit être exécuté, c'est-à-dire bien après que les travaux dépendants et le travail lui-même aient été mis en file d'attente. Par conséquent, ni les expressions de condition ni d'assertion ne conviennent pour conditionner les dépendances d'unité.

Le verbe condition de systemd-analyze(1) peut être utilisé pour tester les expressions de condition et d'assert.

À l'exception de ConditionPathIsSymbolicLink=, toutes les vérifications de chemin suivent les liens symboliques.

ConditionNeedsUpdate=

Prend un argument parmi /var/ ou /etc/, éventuellement préfixé par un "!" (pour inverser la condition). Si l'option systemd.condition_needs_update= est spécifiée sur la ligne de commande du noyau (prenant une valeur booléenne), elle remplacera le résultat de cette vérification de condition, prenant la priorité sur toutes les vérifications d'heure de modification de fichier. Notez que pour rendre ce système efficace, l'horodatage de /usr/ doit être explicitement mis à jour après la modification de son contenu. Le noyau mettra automatiquement à jour l'horodatage de modification d'un répertoire uniquement lorsque les enfants immédiats d'un répertoire sont modifiés ; une modification de fichiers imbriqués ne mettra pas automatiquement à jour le mtime de /usr/.

Notez également que si la méthode de mise à jour inclut un appel pour exécuter elle-même les étapes post-mise à jour appropriées, elle ne devrait pas toucher l'horodatage de /usr/. Dans un schéma d'empaquetage de distribution typique, les paquets effectueront toutes les étapes de mise à jour nécessaires dans le cadre de l'installation ou de la mise à niveau, pour rendre le contenu du paquet immédiatement utilisable. Prend un argument booléen. Cette condition peut être utilisée pour conditionner les unités en fonction du fait que le système démarre pour la première fois. Les valeurs valides sont : "fpu", "vme", "de", "pse", "tsc", "msr", "pae", "mce", "cx8", "apic", "sep", "mtrr", "pge", "mca", "cmov", "pat", "pse36", "clflush", "mmx", "fxsr", "sse", "sse2", "ht", "pni", "pclmul", "monitor", "ssse3", "fma3", "cx16", "sse4_1", "sse4_2", "movbe", "popcnt", "aes", "xsave", "osxsave", "avx", "f16c", "rdrand", "bmi1", "avx2", "bmi2", "rdseed", "adx", "sha_ni", "syscall", "rdtscp", "lm", "lahf_lm", "abm", "constant_tsc".

ConditionOSRelease=

Vérifie qu'une paire "clé=valeur" spécifique est définie dans le fichier os-release(5) de l'hôte.

Outre la correspondance exacte de chaînes (avec "=" et "!="), les comparaisons relatives sont prises en charge pour les paramètres versionnés (par exemple, "VERSION_ID" ; avec "<", "<=", "==", "<>", ">=", ">"), et les comparaisons par caractères génériques de style shell ("*", "?", "[]") sont prises en charge avec "$=" (correspondance) et "!$=" (non-correspondance).

Si la clé donnée n'est pas trouvée dans le fichier, la correspondance est effectuée avec une valeur vide.

Ajouté dans la version 249.

ConditionMemoryPressure=, ConditionCPUPressure=, ConditionIOPressure=

Vérifie que la pression globale du système (mémoire, CPU ou IO) est inférieure ou égale à un seuil. Ce paramètre prend un seuil comme argument. Il peut être spécifié comme une simple valeur en pourcentage, suffixée par "%", auquel cas la pression sera mesurée comme une moyenne sur les cinq dernières minutes avant la tentative de démarrage de l'unité. Alternativement, la durée moyenne peut également être spécifiée en utilisant "/" comme séparateur, par exemple : "10%/1min". Les durées prises en charge correspondent à ce que le noyau fournit, et sont limitées à "10sec", "1min" et "5min". Le PSI "full" (complet) sera vérifié en premier, et s'il n'est pas trouvé, le PSI "some" (quelques) sera vérifié. Pour plus de détails, voir la documentation sur PSI (Pressure Stall Information)[5].

Optionnellement, le seuil peut être préfixé par l'unité de slice sous laquelle la pression sera vérifiée, suivi d'un ":". Si l'unité de slice n'est pas spécifiée, la pression globale du système sera mesurée, au lieu de celle d'un cgroup particulier.

Ajouté dans la version 250.

ConditionKernelModuleLoaded=

Teste si le module noyau spécifié a été chargé et est déjà entièrement initialisé.

OPTIONS DE LA SECTION [INSTALL]

Les fichiers d'unité peuvent inclure une section [Install], qui contient des informations d'installation pour l'unité. Cette section n'est pas interprétée par systemd(1) pendant l'exécution ; elle est utilisée par les commandes enable et disable de l'outil systemctl(1) lors de l'installation d'une unité.

Alias=

Une liste séparée par des espaces de noms supplémentaires sous lesquels cette unité doit être installée. Les noms listés ici doivent avoir la même extension (c'est-à-dire le même type) que le nom du fichier de l'unité. Cette option peut être spécifiée plusieurs fois, auquel cas tous les noms listés sont utilisés. Au moment de l'installation, systemctl enable créera des liens symboliques de ces noms vers le nom du fichier de l'unité. Notez que tous les types d'unités ne prennent pas en charge de tels noms d'alias, et ce paramètre n'est pas pris en charge pour eux. En particulier, les unités de montage, de tranche, de swap et de montage automatique ne prennent pas en charge l'aliasing.

Ajouté dans la version 201.

WantedBy=, RequiredBy=, UpheldBy=

Cette option peut être utilisée plusieurs fois, ou une liste d'unités séparées par des espaces peut être fournie. Un lien symbolique est créé dans le répertoire .wants/, .requires/, ou .upholds/ de chacune des unités listées lorsque cette unité est installée par systemctl enable. Cela a pour effet d'ajouter une dépendance de type Wants=, Requires=, ou Upholds= de l'unité listée vers l'unité actuelle. Voir la description des types de dépendances mentionnés dans la section [Unit] pour plus de détails.

Dans le cas d'unités modèles listant des unités non modèles, l'unité listée doit avoir DefaultInstance= défini, ou systemctl enable doit être appelé avec un nom d'instance. L'instance (par défaut ou spécifiée) sera ajoutée à la liste .wants/, .requires/, ou .upholds/ de l'unité listée. Par exemple, WantedBy=getty.target dans un service getty@.service entraînera la création par systemctl enable getty@tty2.service d'un lien getty.target.wants/getty@tty2.service vers getty@.service. Ceci s'applique également à la liste d'instances spécifiques d'unités à modèle : cette instance spécifique gagnera la dépendance. Une unité modèle peut également lister une unité modèle, auquel cas une dépendance générique sera ajoutée où chaque instance de l'unité listée aura une dépendance sur une instance de l'unité modèle listée avec la même valeur d'instance. Par exemple, WantedBy=container@.target dans un service monitor@.service entraînera la création par systemctl enable monitor@.service d'un lien container@.target.wants/monitor@.service vers monitor@.service, ce qui s'applique à toutes les instances de container@.target.

Ajouté dans la version 201.

Also=

Unités supplémentaires à installer/désinstaller lorsque cette unité est installée/désinstallée. Si l'utilisateur demande l'installation/désinstallation d'une unité avec cette option configurée, systemctl enable et systemctl disable installeront/désinstalleront automatiquement les unités listées dans cette option également.

Cette option peut être utilisée plusieurs fois, ou une liste d'unités séparées par des espaces peut être fournie.

Ajouté dans la version 201.

DefaultInstance=

Dans les fichiers d'unité modèles, cela spécifie pour quelle instance l'unité doit être activée si le modèle est activé sans aucune instance explicitement définie. Cette option n'a aucun effet dans les fichiers d'unités non modèles. La chaîne spécifiée doit être utilisable comme identifiant d'instance.

EXEMPLES

Exemple 1. Autoriser l'activation des unités

L'extrait suivant (surligné) permet d'activer une unité (par exemple foo.service) via systemctl enable :

[Unit]
Description=Foo
[Service]
ExecStart=/usr/sbin/foo-daemon
[Install]
WantedBy=multi-user.target

Après avoir exécuté systemctl enable, un lien symbolique /etc/systemd/system/multi-user.target.wants/foo.service pointant vers l'unité réelle sera créé. Il indique à systemd de prendre en compte l'unité lors du démarrage de multi-user.target. La commande inverse systemctl disable supprimera ce lien symbolique.

Exemple 2. Remplacer les paramètres du fournisseur

Il existe deux méthodes pour remplacer les paramètres du fournisseur dans les fichiers d'unité : copier le fichier d'unité de /usr/lib/systemd/system vers /etc/systemd/system et modifier les paramètres choisis. Alternativement, on peut créer un répertoire nommé unité.d/ dans /etc/systemd/system et y placer un fichier de remplacement nom.conf qui ne modifie que les paramètres spécifiques qui nous intéressent. Notez que plusieurs fichiers de remplacement de ce type sont lus s'ils sont présents, traités dans l'ordre lexicographique de leur nom de fichier.

L'avantage de la première méthode est qu'elle permet de remplacer facilement l'unité complète, l'unité fournisseur n'est plus analysée du tout. Son inconvénient est que les améliorations apportées au fichier d'unité par le fournisseur ne sont pas automatiquement intégrées lors des mises à jour.

L'avantage de la seconde méthode est que l'on ne remplace que les paramètres spécifiquement souhaités, tandis que les mises à jour de l'unité par le fournisseur s'appliquent automatiquement. L'inconvénient est que certaines mises à jour futures par le fournisseur pourraient être incompatibles avec les modifications locales.

Cela s'applique également aux instances utilisateur de systemd, mais avec des emplacements différents pour les fichiers d'unité. Voir la section sur les chemins de chargement des unités pour plus de détails.

Supposons qu'il existe une unité fournie par le vendeur /usr/lib/systemd/system/httpd.service avec le contenu suivant :

[Unit]
Description=Some HTTP Server
After=remote-fs.target sqldb.service
Requires=sqldb.service
AssertPathExists=/srv/webserver
[Service]
Type=notify
ExecStart=/usr/sbin/some-fancy-httpd-server
Nice=5
[Install]
WantedBy=multi-user.target

Maintenant, nous voulons modifier certains paramètres en tant qu'administrateur : premièrement, dans la configuration locale, /srv/webserver peut ne pas exister, car le serveur HTTP est configuré pour utiliser /srv/www à la place. Deuxièmement, la configuration locale fait que le serveur HTTP dépend également d'un service de cache mémoire, memcached.service, qui devrait être inclus (Requires=) et également ordonné correctement (After=). Troisièmement, afin de renforcer un peu plus le service, l'administrateur souhaite définir le paramètre PrivateTmp= (voir systemd.exec(5) pour les détails). Et enfin, l'administrateur souhaite réinitialiser la priorité (niceness) du service à sa valeur par défaut de 0.

La première possibilité est de copier le fichier d'unité vers /etc/systemd/system/httpd.service et de modifier les paramètres choisis :

[Unit]
Description=Some HTTP Server
After=remote-fs.target sqldb.service memcached.service
Requires=sqldb.service memcached.service
AssertPathExists=/srv/www
[Service]
Type=notify
ExecStart=/usr/sbin/some-fancy-httpd-server
Nice=0
PrivateTmp=yes
[Install]
WantedBy=multi-user.target

Alternativement, l'administrateur pourrait créer un fichier de remplacement /etc/systemd/system/httpd.service.d/local.conf avec le contenu suivant :

[Unit]
After=memcached.service
Requires=memcached.service
# Réinitialiser toutes les assertions puis réajouter la condition souhaitée
AssertPathExists=
AssertPathExists=/srv/www
[Service]
Nice=0
PrivateTmp=yes

Notez que pour les fichiers de remplacement, si l'on souhaite supprimer des entrées d'un paramètre qui est analysé comme une liste (et qui n'est pas une dépendance), comme AssertPathExists= (ou par exemple ExecStart= dans les unités de service), il faut d'abord effacer la liste avant de réajouter toutes les entrées sauf celle à supprimer. Les dépendances (After=, etc.) ne peuvent pas être réinitialisées à une liste vide, donc les dépendances ne peuvent être ajoutées que dans les fichiers de remplacement. Si vous souhaitez supprimer des dépendances, vous devez remplacer l'unité entière.

Exemple 3. Fichiers de remplacement de niveau supérieur avec des unités modèles

Des fichiers de remplacement de niveau supérieur par type peuvent être utilisés pour modifier certains aspects de toutes les unités d'un type particulier. Par exemple, en créant le répertoire /etc/systemd/system/service.d/ avec un fichier de remplacement, le contenu du fichier de remplacement peut être appliqué à toutes les unités de service. Nous pouvons aller plus loin en faisant instancier le fichier de remplacement de niveau supérieur par une unité auxiliaire secondaire. Considérons par exemple l'ensemble suivant d'unités et de fichiers de remplacement où nous installons une dépendance OnFailure= pour toutes les unités de service.

/etc/systemd/system/failure-handler@.service :

[Unit]
Description=My Failure Handler For %i
[Service]
Type=oneshot
# Effectuer une action spéciale lorsque %i se termine de manière inattendue.
ExecStart=/usr/sbin/myfailurehandler %i

Nous pouvons ensuite ajouter une instance de failure-handler@.service comme

an OnFailure= pour toutes les unités de service.

/etc/systemd/system/service.d/10-all.conf :

[Unit]
OnFailure=failure-handler@%N.service

Maintenant, après avoir exécuté systemctl daemon-reload, tous les services auront acquis une dépendance OnFailure= sur failure-handler@%N.service. Les unités d'instance de modèle auront également acquis la dépendance, ce qui entraînera la création d'une chaîne de dépendances récursive. systemd essaiera de détecter ces chaînes de dépendances récursives où une unité de modèle dépend directement et récursivement d'elle-même et supprimera automatiquement de telles dépendances si elle les trouve. Si systemd ne détecte pas la chaîne de dépendances récursive, nous pouvons casser la chaîne nous-mêmes en désactivant le drop-in pour les unités d'instance du modèle via un lien symbolique vers /dev/null :

mkdir /etc/systemd/system/failure-handler@.service.d/
ln -s /dev/null /etc/systemd/system/failure-handler@.service.d/10-all.conf
systemctl daemon-reload

Cela garantit que si une instance de failure-handler@.service échoue, elle ne déclenchera pas une instance nommée failure-handler@failure-handler.service.
