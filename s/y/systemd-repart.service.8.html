SYSTEMD-REPART(8) systemd-repart SYSTEMD-REPART(8)

NOM

systemd-repart, systemd-repart.service - Agrandir et ajouter des partitions automatiquement, et générer des images disque (DDI)

SYNTAXE

systemd-repart [OPTIONS...] [[PÉRIPHÉRIQUE_BLOC]...]

systemd-repart.service

DESCRIPTION

systemd-repart crée des tables de partitions, et ajoute ou agrandit des partitions, en se basant sur les fichiers de configuration décrits dans repart.d(5).

systemd-repart est utilisé lors de la *construction* d'images de systèmes d'exploitation, ainsi que lors du *déploiement* d'images pour les ajuster automatiquement, au démarrage, au système sur lequel elles s'exécutent. De cette façon, l'image peut être de taille minimale et peut être augmentée automatiquement au démarrage, prenant possession de l'espace disque disponible.

S'il est invoqué sans arguments, systemd-repart opère sur le périphérique bloc qui sous-tend la partition de système de fichiers racine du système d'exploitation en cours d'exécution, ajoutant et agrandissant ainsi les partitions du système d'exploitation démarré lui-même. Lorsqu'il est appelé dans l'initrd, il opère sur le périphérique bloc qui sous-tend /sysroot/, c'est-à-dire sur le périphérique bloc dans lequel le système va bientôt transitionner. Si --image= est utilisé, il opérera sur le périphérique ou le fichier image spécifié. Le service systemd-repart.service est généralement exécuté au démarrage dans l'initrd, afin d'augmenter la table de partitions du système d'exploitation avant le montage de ses partitions.

Les opérations de systemd-repart sont principalement incrémentielles : il agrandit les partitions existantes ou en ajoute de nouvelles, mais ne réduit, ne supprime ou ne déplace pas les partitions existantes. Le service est destiné à être exécuté à chaque démarrage, mais lorsqu'il détecte que la table de partitions correspond déjà à la configuration installée dans repart.d/*.conf, il n'exécute aucune opération.

Les cas d'utilisation suivants font partie de ceux couverts :

• La partition racine peut être agrandie pour couvrir tout l'espace disque disponible.
• Une partition /home/, swap, ou /srv/ peut être ajoutée.
• Une deuxième (ou troisième, ...) partition racine peut être ajoutée, pour couvrir des configurations de type A/B où une deuxième version du système de fichiers racine est utilisée alternativement pour mettre en œuvre des schémas de mise à jour. L'image déployée ne contiendrait qu'une seule partition ("A"), mais lors du premier démarrage, une deuxième partition ("B") à cet effet serait automatiquement créée.

L'algorithme exécuté par systemd-repart est approximativement le suivant :

1.Les fichiers de configuration repart.d/*.conf sont chargés et analysés, et ordonnés par nom de fichier (sans le préfixe du répertoire). Pour chaque fichier de configuration, les fichiers de remplacement sont chargés depuis les répertoires portant le même nom que le fichier de configuration avec le suffixe ".d" ajouté.
2.La table de partitions sur le périphérique bloc est chargée et analysée, si présente.
3.Les partitions existantes dans la table de partitions sont associées aux fichiers repart.d/*.conf par l'UUID du type de partition GPT. La première partition existante d'un type spécifique est associée au premier fichier de configuration déclarant le même type. La deuxième partition existante d'un type spécifique est alors associée au deuxième fichier de configuration déclarant le même type, et ainsi de suite. Une fois cette association itérative terminée, toute partition existante sans fichier de configuration correspondant est considérée comme "étrangère" et laissée telle quelle. Et tout fichier de configuration pour lequel aucune partition n'a été associée est traité comme une demande de création de partition.
4.Les partitions à créer sont maintenant allouées sur le disque, en tenant compte des contraintes de taille et des poids déclarés dans les fichiers de configuration. L'espace libre est utilisé dans les limites fixées par les demandes de taille et de remplissage. De plus, les partitions existantes qui doivent être agrandies sont effectivement agrandies. Les nouvelles partitions sont toujours ajoutées à la fin de la table de partitions, prenant le premier emplacement de la table de partitions dont l'indice est supérieur aux indices de toutes les partitions existantes. Les partitions ne sont jamais réorganisées et donc les numéros de partitions restent stables. Lorsque les partitions sont créées, elles sont placées dans la plus petite zone d'espace libre suffisamment grande pour satisfaire les limites de taille et de remplissage. Cela signifie que les partitions peuvent avoir un ordre différent sur le disque que dans la table de partitions. Notez que cette allocation se fait uniquement en mémoire, la table de partitions sur le disque n'est pas encore mise à jour.
5.Toutes les partitions existantes pour lesquelles des fichiers de configuration existent et qui n'ont actuellement aucun label de partition GPT installé se verront attribuer un label, soit explicitement configuré dans la configuration, soit - si celui-ci est manquant - dérivé automatiquement du type de partition. Il en va de même pour toutes les partitions nouvellement créées. Ces attributions se font uniquement en mémoire, le disque n'est pas encore mis à jour.
6.De même, toutes les partitions existantes pour lesquelles des fichiers de configuration existent et qui ont actuellement un UUID identifiant composé uniquement de zéros se verront attribuer un nouvel UUID. Cet UUID est haché cryptographiquement à partir d'une valeur de graine commune ainsi que de l'UUID du type de partition (et d'un compteur au cas où plusieurs partitions du même type seraient définies), voir ci-dessous. Il en va de même pour toutes les partitions qui sont créées. Ces attributions se font uniquement en mémoire, le disque n'est pas encore mis à jour.
7.De même, si l'UUID du volume du disque est composé uniquement de zéros, il est également initialisé, également haché cryptographiquement à partir de la même valeur de graine commune. Ceci est également fait uniquement en mémoire.
8.L'espace disque assigné aux nouvelles partitions (c'est-à-dire ce qui était auparavant de l'espace libre) est maintenant effacé. Plus précisément, toutes les signatures de système de fichiers sont supprimées, et si le périphérique le supporte, la commande d'E/S BLKDISCARD est émise pour informer le matériel que l'espace est maintenant vide. De plus, tout "remplissage" entre les partitions et à la fin du périphérique est également effacé de la même manière.
9.La nouvelle table de partitions est finalement écrite sur le disque. Le noyau est invité à relire la table de partitions.

Par exception à l'opération incrémentielle normale, lorsqu'il est appelé dans un mode spécial de "réinitialisation d'usine", systemd-repart peut être utilisé pour effacer les partitions existantes afin de réinitialiser une installation aux paramètres d'usine par défaut. Ce mode de fonctionnement est utilisé lorsque soit le commutateur --factory-reset=yes est passé sur la ligne de commande de l'outil, soit l'option systemd.factory_reset=yes est spécifiée sur la ligne de commande du noyau, soit la variable EFI FactoryResetRequest (UUID du fournisseur 8cf2644b-4b0b-428f-9387-6d876050dc67) est définie sur "yes". Cela modifie légèrement l'algorithme ci-dessus : entre la 3ème et la 4ème étape, toute partition marquée explicitement via le booléen FactoryReset= est supprimée, et l'algorithme redémarre, recréant ainsi immédiatement ces partitions à nouveau vides.

Notez que systemd-repart ne modifie par défaut que les tables de partitions, il ne crée ni ne redimensionne de systèmes de fichiers à l'intérieur de ces partitions, sauf si l'option de configuration Format= est spécifiée. Notez également qu'il existe des mécanismes séparés à cette fin, par exemple systemd-growfs(8) et systemd-makefs.

Les UUID identifiant les nouvelles partitions créées (ou attribuées aux partitions existantes qui n'ont pas encore d'UUID), ainsi que le disque dans son ensemble sont hachés cryptographiquement à partir d'une valeur de graine commune. Cette valeur de graine est généralement l'id machine(5) du système, de sorte que l'ID machine détermine de manière reproductible les UUID attribués à toutes les partitions. Si l'ID machine ne peut être lu (ou si l'utilisateur passe --seed=random, voir ci-dessous), la graine est générée aléatoirement à la place, de sorte que les UUID des partitions soient également effectivement aléatoires. La valeur de la graine peut également être définie explicitement, formatée en UUID via l'option --seed=. En hachant ces UUID à partir d'une graine commune, les images préparées avec cet outil deviennent reproductibles et le résultat de l'algorithme ci-dessus déterministe.

L'argument positionnel doit spécifier le périphérique bloc ou un fichier régulier sur lequel opérer. Si --empty=create est spécifié, le chemin spécifié est créé en tant que fichier régulier, ce qui est utile pour générer des images disque à partir de zéro.

OPTIONS

Les options suivantes sont comprises :

--dry-run=

Prend une valeur booléenne. Si ce commutateur n'est pas spécifié, --dry-run=yes est la valeur par défaut implicite. Contrôle si systemd-repart exécute les opérations de re-partitionnement demandées ou s'il doit seulement montrer ce qu'il ferait. Sauf si --dry-run=no est spécifié, systemd-repart ne touchera pas la table de partitions du périphérique.

Ajouté dans la version 245.

--empty=

Prend l'une des valeurs suivantes : "refuse", "allow", "require", "force" ou "create". Contrôle comment opér

sur des périphériques de bloc entièrement vides, c'est-à-dire ne portant pas encore de table de partitions / étiquette de disque. Si ce commutateur n'est pas spécifié, la valeur par défaut implicite est « refuser ».

Si « refuser », systemd-repart exige que le périphérique de bloc sur lequel il doit opérer porte déjà une table de partitions et refuse l'opération si aucune n'est trouvée. Si « autoriser », la commande étendra une table de partitions existante ou en créera une nouvelle si aucune n'existe. Si « exiger », la commande créera une nouvelle table de partitions si aucune n'existe jusqu'à présent, et refusera l'opération si une existe déjà. Si « forcer », elle créera une table de partitions vierge inconditionnellement, effaçant ainsi complètement le disque. Si « forcer », aucune partition existante ne sera prise en compte ou ne survivra à l'opération. Par conséquent : utilisez avec prudence, c'est un excellent moyen de perdre toutes vos données. Si « créer », un nouveau fichier de boucle est créé sous le chemin passé via le paramètre du nœud de périphérique, de la taille indiquée avec --size=, voir ci-dessous.

Ajouté dans la version 245.

--discard=

Prend une valeur booléenne. Si ce commutateur n'est pas spécifié, --discard=yes est la valeur par défaut implicite. Contrôle si la commande BLKDISCARD doit être émise sur l'espace occupé par les partitions ajoutées ou sur l'espace entre elles. Généralement, il est bon d'émettre cette requête car elle indique au matériel sous-jacent que les blocs couverts doivent être considérés comme vides, améliorant ainsi les performances. Si l'on opère sur un fichier ordinaire au lieu d'un nœud de périphérique de bloc, un fichier épars est généré.

Ajouté dans la version 245.

--size=

Prend une taille en octets, en utilisant les suffixes habituels K, M, G, T, ou la valeur spéciale « auto ». Si utilisé, le chemin du nœud de périphérique spécifié doit faire référence à un fichier ordinaire, qui est ensuite agrandi à la taille spécifiée s'il est plus petit, avant que toute modification ne soit apportée à la table de partitions. Si spécifié comme « auto », la taille minimale de l'image disque est déterminée automatiquement (c'est-à-dire que les tailles minimales de toutes les partitions sont additionnées, en tenant compte de l'espace pour les métadonnées supplémentaires). Ce commutateur n'est pas pris en charge si le nœud spécifié est un périphérique de bloc. Ce commutateur n'a aucun effet si le fichier est déjà aussi grand que la taille spécifiée ou plus grand. La taille spécifiée est implicitement arrondie aux multiples de 4096. Lorsqu'il est utilisé avec --empty=create, il spécifie la taille initiale du fichier de boucle à créer.

L'option --size=auto prend en compte les tailles des partitions préexistantes. Cependant, elle ne tient pas compte des tables de partitions qui ne sont pas étroitement empaquetées : les partitions configurées pourraient toujours ne pas tenir dans le périphérique de support s'il existe un espace vide entre les partitions préexistantes (ou avant la première partition) qui ne peut pas être entièrement rempli par les partitions à agrandir ou à créer.

Notez également que la détermination automatique de la taille ne tient pas compte des fichiers ou répertoires spécifiés avec CopyFiles= : l'opération pourrait échouer si les fichiers ou répertoires spécifiés nécessitent plus d'espace disque que la limite minimale de taille par partition configurée.

Ajouté dans la version 246.

--factory-reset=

Prend une valeur booléenne. Si ce commutateur n'est pas spécifié, --factory-reset=no est la valeur par défaut implicite. Contrôle si l'opération s'effectue en mode « réinitialisation d'usine », voir ci-dessus. Si défini sur vrai, toutes les partitions existantes marquées avec FactoryReset= défini sur oui seront supprimées tôt dans l'exécution de l'algorithme de re-partitionnement. À utiliser avec prudence, c'est un excellent moyen de perdre toutes vos données. Notez que les fichiers de partition doivent explicitement activer FactoryReset=, car l'option est désactivée par défaut. Si aucune partition n'est marquée pour la réinitialisation d'usine, ce commutateur n'a aucun effet. Notez qu'il existe deux autres méthodes pour demander une opération de réinitialisation d'usine : via la ligne de commande du noyau et via une variable EFI, voir ci-dessus.

Ajouté dans la version 245.

--can-factory-reset

Si ce commutateur est spécifié, le disque n'est pas re-partitionné. Au lieu de cela, on détermine si des partitions existantes sont marquées avec FactoryReset=. Si c'est le cas, l'outil se terminera avec le statut de sortie zéro, sinon non-zéro. Ce commutateur peut être utilisé pour déterminer rapidement si le système en cours d'exécution prend en charge un mécanisme de réinitialisation d'usine basé sur systemd-repart.

Ajouté dans la version 245.

--root=

Prend un chemin vers un répertoire à utiliser comme système de fichiers racine lors de la recherche des fichiers repart.d/*.conf, pour le fichier d'ID machine à utiliser comme amorce et pour les fichiers et répertoires sources CopyFiles= et CopyBlocks=. Par défaut, lorsqu'il est appelé sur le système régulier, il est défini sur le système de fichiers racine de l'hôte /. S'il est appelé depuis l'initrd, il est défini sur /sysroot/, de sorte que l'outil opère sur la configuration et l'ID machine stockés dans le système de fichiers racine, puis fait la transition vers lui-même.

Voir --copy-source= pour une option plus restreinte qui affecte uniquement CopyFiles=.

Ajouté dans la version 245.

--image=

Prend un chemin vers un fichier image disque ou un périphérique à monter et à utiliser de manière similaire à --root=, voir ci-dessus.

Ajouté dans la version 249.

--image-policy=politique

Prend une chaîne de politique d'image comme argument, conformément à systemd.image-policy(7). La politique est appliquée lors de l'opération sur l'image disque spécifiée via --image=, voir ci-dessus. Si elle n'est pas spécifiée, la politique par défaut est « * », c'est-à-dire que tous les systèmes de fichiers reconnus dans l'image sont utilisés.

--seed=

Prend un UUID comme argument ou la valeur spéciale random. Si un UUID est spécifié, les UUIDs à attribuer aux partitions et à la table de partitions elle-même sont dérivés par hachage cryptographique à partir de celui-ci. Si non spécifié, on tente de lire l'ID machine de l'hôte (ou plus précisément, du répertoire racine configuré via --root=) et de l'utiliser comme amorce à la place, en se rabattant sur une amorce aléatoire sinon. Utilisez --seed=random pour forcer une amorce aléatoire. La spécification explicite de l'amorce peut être utilisée pour générer des tables de partitions strictement reproductibles.

Ajouté dans la version 245.

--pretty=

Prend un argument booléen. Si ce commutateur n'est pas spécifié, il est activé par défaut lorsqu'il est appelé depuis un terminal interactif et désactivé sinon. Contrôle si une table et un graphique conviviaux illustrant les changements appliqués doivent être affichés.

Ajouté dans la version 245.

--definitions=

Prend un chemin de système de fichiers. Si spécifié, les fichiers *.conf sont lus à partir du répertoire spécifié au lieu de rechercher dans /usr/lib/repart.d/*.conf, /etc/repart.d/*.conf, /run/repart.d/*.conf.

Ce paramètre peut être spécifié plusieurs fois.

Ajouté dans la version 245.

--key-file=

Prend un chemin de système de fichiers. Configure la clé de chiffrement à utiliser lors de la configuration de volumes LUKS2 configurés avec le réglage Encrypt=key-file dans les fichiers de partition. Doit faire référence à un fichier ordinaire contenant la clé, ou à un socket de flux AF_UNIX dans le système de fichiers. Dans ce dernier cas, une connexion est établie avec celui-ci et la clé y est lue. Si ce commutateur n'est pas spécifié, la clé vide (c'est-à-dire une clé de longueur nulle) est utilisée. Ce comportement est utile pour configurer des partitions chiffrées lors du premier démarrage, qui ne reçoivent leur mot de passe fourni par l'utilisateur que lors d'une étape de configuration ultérieure.

Ajouté dans la version 247.

--private-key=

Prend un chemin de système de fichiers ou une désignation spécifique au moteur ou au fournisseur. Configure la clé de signature à utiliser lors de la création de partitions de signature de vérification avec le réglage Verity=signature dans les fichiers de partition.

Ajouté dans la version 252.

--private-key-source=

Prend l'une des valeurs « file », « engine » ou « provider ». Dans les deux derniers cas, elle est suivie du nom d'un fournisseur ou d'un moteur, séparé par un deux-points, qui sera passé à la logique « engine » ou « provider » d'OpenSSL. Configure comment charger la clé privée à utiliser lors de la création de partitions de signature de vérification avec le réglage Verity=signature dans les fichiers de partition.

Ajouté dans la version 256.

--certificate=

Prend un chemin de système de fichiers ou une désignation spécifique au fournisseur. Configure le certificat X.509 encodé PEM à utiliser lors de la création de partitions de signature de vérification avec le réglage Verity=signature dans les fichiers de partition.

Ajouté dans la version 252.

--certificate-source=

Prend l'une des valeurs « file » ou « provider ». Dans le dernier cas, elle est suivie du nom d'un fournisseur, séparé par un deux-points, qui sera passé à la logique « provider » d'OpenSSL. Configure comment charger le certificat X.509 à utiliser lors de la création de partitions de signature de vérification avec le réglage Verity=signature dans les fichiers de partition.

Ajouté dans la version 257.

--join-signature=

Spécifie un tuple séparé par des deux-points avec un hachage de vérification de niveau supérieur encodé en hexadécimal d'une partition Verity=hash comme premier élément, et une signature PKCS7 du roothash comme chemin vers un fichier de signature encodé en DER, ou comme chaîne d'encodage base64 ASCII d'une signature encodée en DER préfixée par « base64: ». À utiliser sur une image préexistante qui a été créée avec un paramètre tel que --defer-partitions=root-verity-sig, afin de permettre la signature hors ligne de la partition de signature de vérification.

Ceci est une alternative à la signature en ligne utilisant des paramètres tels que --private-key=, pour les systèmes de construction où la clé privée pour la signature de production n'est pas disponible dans le même contexte que celui où le contenu est créé.

Ajouté dans la version 258.

--tpm2-device=, --tpm2-pcrs=

Configure le périphérique TPM2 et la liste des PCR à utiliser pour les volumes LUKS2 configurés avec l'option Encrypt=tpm2. Ces options prennent les mêmes paramètres que les options de même nom de systemd-cryptenroll(1) et ont le même effet sur les partitions où l'enrôlement TPM2 est demandé.

Ajouté dans la version 248.

--tpm2-device-key=CHEMIN, --tpm2-seal-key-handle=HANDLE

Configure une clé SRK TPM2 pour lier le chiffrement. Voir systemd-cryptenroll(1) pour les détails sur cette option.

Ajouté dans la version 255.

--tpm2-public-key=CHEMIN, --tpm2-public-key-pcrs=PCR[+PCR...]

Configure une politique de PCR signée TPM2 pour lier le chiffrement. Voir systemd-cryptenroll(1) pour les détails sur ces deux options.

Ajouté dans la version 252.

--tpm2-pcrlock=CHEMIN

Configure une politique pcrlock TPM2 pour lier le chiffrement. Voir SplitName=. Si activé, pour chaque partition avec SplitName= défini, un fichier de sortie distinct contenant uniquement le contenu de cette partition est généré. Le nom du fichier de sortie se compose du nom de fichier du loopback suffixé par le nom configuré avec SplitName=. Si le nom du fichier loopback se termine par ".raw", le suffixe est inséré avant l'extension ".raw" à la place.

Notez que --split est indépendant de --dry-run. Même si --dry-run est activé, les artefacts de division seront toujours générés à partir d'une image existante si --split est activé.

Ajouté dans la version 252.

--include-partitions=PARTITIONS, --exclude-partitions=PARTITIONS

Ces options spécifient les types de partitions sur lesquels systemd-repart doit opérer. Si --include-partitions= est utilisé, toutes les partitions qui ne sont pas spécifiées sont exclues. Si --exclude-partitions= est utilisé, toutes les partitions spécifiées sont exclues. Les deux options acceptent une liste d'UUID ou d'identifiants de type de partition GPT séparés par des virgules (voir Type= dans repart.d(5)).

Ajouté dans la version 253.

--defer-partitions=PARTITIONS

Cette option spécifie pour quels types de partitions systemd-repart doit reporter. Toutes les partitions qui sont reportées en utilisant cette option sont toujours prises en compte lors du calcul des tailles et des décalages des autres partitions, mais ne sont pas réellement écrites sur l'image disque. L'effet net de cette option est que si vous exécutez à nouveau systemd-repart sans cette option, les partitions manquantes seront ajoutées comme si elles n'avaient pas été reportées la première fois que systemd-repart a été exécuté.

Ajouté dans la version 253.

--sector-size=BYTES

Cette option permet de configurer la taille de secteur de l'image produite par systemd-repart. Elle accepte une valeur qui est une puissance de "2" comprise entre "512" et "4096". Cette option est utile lors de la création d'images pour des disques qui utilisent une taille de secteur différente de celle du disque sur lequel l'image est produite.

Ajouté dans la version 253.

--architecture=ARCH

Cette option permet de remplacer l'architecture utilisée pour les types de partitions spécifiques à l'architecture. Par exemple, si défini sur "arm64", un type de partition "root-x86-64" référencé dans les fichiers drop-in de repart.d/ sera patché dynamiquement pour faire référence à "root-arm64" à la place. Accepte l'une des valeurs suivantes : "alpha", "arc", "arm", "arm64", "ia64", "loongarch64", "mips-le", "mips64-le", "parisc", "ppc", "ppc64", "ppc64-le", "riscv32", "riscv64", "s390", "s390x", "tilegx", "x86" ou "x86-64".

Ajouté dans la version 254.

--offline=BOOL

Indique à systemd-repart de construire l'image hors ligne. Accepte une valeur booléenne ou "auto". Par défaut, "auto". Si activé, l'image est construite sans utiliser de périphériques loop. Ceci est utile pour construire des images sans privilèges ou lorsque les périphériques loop ne sont pas disponibles. Si désactivé, l'image est toujours construite en utilisant des périphériques loop. Si "auto", systemd-repart construira l'image en ligne si possible et se rabattra sur la construction hors ligne si les périphériques loop ne sont pas disponibles ou ne peuvent pas être accessibles en raison d'autorisations manquantes.

Ajouté dans la version 254.

--copy-from=PATH

Indique à systemd-repart de synthétiser les définitions de partitions à partir de la table des partitions dans l'image ou le périphérique donné. Cette option peut être spécifiée plusieurs fois pour synthétiser des définitions à partir de chacune des images ou des périphériques donnés. Les définitions générées copieront les partitions dans la table des partitions de destination. Les partitions copiées auront la même taille, les mêmes métadonnées et le même contenu, mais pourraient avoir un numéro de partition différent et pourraient être situées à un décalage différent dans la table des partitions de destination. Ces définitions peuvent être combinées avec les définitions de partitions lues à partir de fichiers de définition de partitions réguliers. Les définitions synthétisées ont la priorité sur les définitions lues à partir des fichiers de définition de partitions.

Ajouté dans la version 255.

--copy-source=PATH, -s PATH

Spécifie un répertoire source par rapport auquel tous les chemins sources CopyFiles= doivent être considérés. Ceci est similaire à --root=, mais s'applique exclusivement au paramètre CopyFiles=. Si --root= et --copy-source= sont utilisés en combinaison, le premier s'applique comme d'habitude, sauf pour CopyFiles= où le second a la priorité.

Ajouté dans la version 255.

--make-ddi=TYPE

Accepte "sysext", "confext" ou "portable". Génère une image disque découvrable (DDI) pour une extension système (sysext, voir systemd-sysext(8) pour plus de détails), une extension de configuration (confext) ou des Services Portables[1]. L'image générée consistera en un système de fichiers "erofs" signé Verity comme partition racine. Dans ce mode de fonctionnement, les définitions de partitions dans /usr/lib/repart.d/*.conf et les répertoires associés ne sont pas lus, et --definitions= n'est pas supporté, car les définitions appropriées pour la classe DDI sélectionnée seront choisies automatiquement.

Doit être utilisé en conjonction avec --copy-source= pour spécifier la hiérarchie de fichiers à remplir dans la DDI. Le répertoire spécifié doit contenir un sous-répertoire etc/ si "confext" est sélectionné. Si "sysext" est sélectionné, il doit contenir un répertoire usr/ ou opt/, ou les deux. Si "portable" est utilisé, une hiérarchie complète de système d'exploitation peut être fournie.

Cette option implique --empty=create, --size=auto et --seed=random (les deux derniers peuvent être surchargés).

La clé privée et le certificat pour signer la DDI doivent être spécifiés via les commutateurs --private-key= et --certificate=.

Ajouté dans la version 255.

-S, -C, -P

Raccourcis pour --make-ddi=sysext, --make-ddi=confext, --make-ddi=portable, respectivement.

Ajouté dans la version 255.

--append-fstab=

Accepte "no", "auto" ou "replace". Contrôle comment le fichier fstab(5) généré par --generate-fstab= se comportera en cas de fichier préexistant.

Si "no", systemd-repart se plaindra et abandonnera en cas de fichier. C'est le comportement par défaut. Si "replace", le fichier sera silencieusement remplacé par le nouveau fichier généré.

Si "auto", systemd-repart recherchera dans le fichier préexistant la section qui appartient au contenu généré automatiquement et la remplacera par le contenu généré plus récent, et conservera la section fournie par l'utilisateur s'il y en a une. La section générée est identifiée en recherchant le contenu automatique entouré par "# Start section ↓ of automatically generated fstab by systemd-repart" et "# End section ↑ of automatically generated fstab by systemd-repart". Le contenu qui se trouve avant et après ces commentaires est considéré comme fourni par l'utilisateur et est conservé dans le nouveau fichier.

Ajouté dans la version 258.

--generate-fstab=PATH

Spécifie un chemin où écrire les entrées fstab(5) pour les points de montage configurés avec MountPoint= dans le répertoire racine spécifié avec --copy-source= ou --root=, ou dans le répertoire racine de l'hôte si aucun des deux n'est spécifié. Désactivé par défaut.

Ajouté dans la version 256.

--generate-crypttab=PATH

Spécifie un chemin où écrire les entrées crypttab pour les volumes chiffrés configurés avec EncryptedVolume= dans le répertoire racine spécifié avec --copy-source= ou --root=, ou dans le répertoire racine de l'hôte si aucun des deux n'est spécifié. Désactivé par défaut.

Ajouté dans la version 256.

--list-devices

Affiche une liste des périphériques blocs candidats sur lesquels cette commande peut opérer. Plus précisément, elle énumère les périphériques blocs actuellement présents qui supportent les tables de partitions, et affiche leurs chemins de nœuds de périphérique ainsi que leurs liens symboliques.

Ajouté dans la version 257.

-h, --help

Affiche un bref texte d'aide et quitte.

--version

Affiche une courte chaîne de version et quitte.

--no-pager

Ne pas rediriger la sortie vers un paginator.

--no-legend

Ne pas imprimer la légende, c'est-à-dire les en-têtes de colonne et le pied de page avec des indices.

--json=MODE

Affiche la sortie formatée en JSON. Attend l'une des valeurs suivantes : "short" (pour la sortie la plus courte possible sans espaces superflus ni sauts de ligne), "pretty" (pour une version formatée de la même sortie, avec indentation et sauts de ligne) ou "off" (pour désactiver la sortie JSON, par défaut).

STATUT DE SORTIE

En cas de succès, 0 est retourné, et un code d'erreur non nul sinon.

EXEMPLE

Exemple 1. Générer une image d'extension de configuration

Ce qui suit crée une DDI d'extension de configuration (confext) pour une mise à jour /etc/motd :

mkdir -p tree/etc/extension-release.d
echo "Hello World" >tree/etc/motd
cat >tree/etc/extension-release.d/extension-release.my-motd <<EOF
ID=fedora
VERSION_ID=38
IMAGE_ID=my-motd
IMAGE_VERSION=7
EOF
systemd-repart -C \
  --private-key=verity-private-key.pem \
  --certificate=verity-certificate.pem \
  -s tree/ \
  /var/lib/confexts/my-motd.confext.raw
systemd-confext refresh

La DDI générée de cette manière peut être appliquée au système avec systemd-confext(1).

Exemple 2. Générer une image d'extension système et la signer via PKCS11

Ce qui suit crée une DDI d'extension système (sysext) pour une mise à jour /usr/foo et la signe avec un jeton matériel via PKCS11 :

mkdir -p tree/usr/lib/extension-release.d
echo "Hello World" >tree/usr/foo
cat >tree/usr/lib/extension-release.d/extension-release.my-foo <<
EOF ID=fedora VERSION_ID=38 IMAGE_ID=my-foo IMAGE_VERSION=7 EOF systemd-repart --make-ddi=sysext \ --private-key-source=engine:pkcs11 \ --private-key="pkcs11:model=PKCS%2315%20emulated;manufacturer=piv_II;serial=0123456789abcdef;token=Some%20Cert" \ --certificate=verity-certificate.pem \ -s tree/ \ /var/lib/extensions/my-foo.sysext.raw systemd-sysext refresh

Le DDI généré de cette manière peut être appliqué au système avec systemd-sysext(8).

Exemple 3. Générer une signature dm-verity hors ligne et l'ajouter à une image pré-construite

Ce qui suit crée une image avec des métadonnées dm-verity, la signe séparément pour simuler un système de signature hors ligne, puis ajoute la signature à l'image :

mkdir -p repart.d/ /tmp/tree/usr/lib/
cat >/tmp/tree/usr/lib/os-release <<EOF
ID=debian
VERSION_ID=13
EOF
cat >repart.d/10-root.conf <<EOF
[Partition]
Type=root
Format=erofs
SizeMinBytes=100M
SizeMaxBytes=100M
Verity=data
VerityMatchKey=root
EOF
cat >repart.d/11-root-verity.conf <<EOF
[Partition]
Type=root-verity
Label=%o_%w_verity
Verity=hash
VerityMatchKey=root
SizeMinBytes=400M
SizeMaxBytes=400M
EOF
cat >repart.d/12-root-verity-sig.conf <<EOF
[Partition]
Type=root-verity-sig
Label=%o_%w_verity_sig
Verity=signature
VerityMatchKey=root
EOF
systemd-repart --definitions repart.d \
  --defer-partitions=root-verity-sig \
  --copy-source=/tmp/tree/ \
  --empty=create --size=600M \
  --json=short \
  /tmp/img.raw | | jq --raw-output0 .[-1].roothash > /tmp/img.roothash
openssl smime -sign -in /tmp/img.roothash \
  -inkey verity-private-key.pem \
  -signer verity-certificate.pem \
  -noattr -binary -outform der \
  -out /tmp/img.roothash.p7s
systemd-repart --definitions repart.d \
  --dry-run=no --root=/tmp/tree/ \
  --join-signature="$(cat /tmp/img.roothash):/tmp/img.roothash.p7s" \
  --certificate=verity-certificate.pem \
  /tmp/img.raw
