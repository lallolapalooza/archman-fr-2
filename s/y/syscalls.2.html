syscalls(2) Manuel des appels système syscalls(2)

NOM

syscalls - Appels système Linux

SYNOPIS

Appels système Linux.

DESCRIPTION

L'appel système est l'interface fondamentale entre une application et le noyau Linux.

Appels système et fonctions enveloppes de bibliothèque

Les appels système ne sont généralement pas invoqués directement, mais plutôt via des fonctions enveloppes dans glibc (ou peut-être une autre bibliothèque). Pour les détails sur l'invocation directe d'un appel système, voir intro(2). Souvent, mais pas toujours, le nom de la fonction enveloppe est le même que le nom de l'appel système qu'elle invoque. Par exemple, glibc contient une fonction chdir() qui invoque l'appel système sous-jacent "chdir".

Souvent, la fonction enveloppe glibc est assez mince, faisant peu de travail autre que de copier les arguments dans les bons registres avant d'invoquer l'appel système, puis de définir errno de manière appropriée après que l'appel système a renvoyé. (Ce sont les mêmes étapes qui sont effectuées par syscall(2), qui peut être utilisé pour invoquer les appels système pour lesquels aucune fonction enveloppe n'est fournie.) Note : les appels système indiquent un échec en renvoyant un numéro d'erreur négatif à l'appelant sur les architectures sans registre/indicateur d'erreur séparé, comme noté dans syscall(2) ; lorsque cela se produit, la fonction enveloppe inverse le numéro d'erreur renvoyé (pour le rendre positif), le copie dans errno et renvoie -1 à l'appelant de l'enveloppe.

Parfois, cependant, la fonction enveloppe effectue un travail supplémentaire avant d'invoquer l'appel système. Par exemple, de nos jours, il existe (pour les raisons décrites ci-dessous) deux appels système apparentés, truncate(2) et truncate64(2), et la fonction enveloppe glibc truncate() vérifie quels de ces appels système sont fournis par le noyau et détermine lequel doit être utilisé.

Liste des appels système

Ci-dessous se trouve une liste des appels système Linux. Dans la liste, la colonne Noyau indique la version du noyau pour les appels système qui étaient nouveaux dans Linux 2.2, ou qui sont apparus depuis cette version du noyau. Notez les points suivants :

•
Lorsqu'aucune version du noyau n'est indiquée, l'appel système est apparu dans Linux 1.0 ou avant.
•
Lorsqu'un appel système est marqué "1.2" cela signifie que l'appel système est probablement apparu dans une version du noyau Linux 1.1.x, et est apparu pour la première fois dans un noyau stable avec 1.2. (Le développement du noyau Linux 1.2 a été initié à partir d'une branche de Linux 1.0.6 via la série de noyaux instables Linux 1.1.x.)
•
Lorsqu'un appel système est marqué "2.0" cela signifie que l'appel système est probablement apparu dans une version du noyau Linux 1.3.x, et est apparu pour la première fois dans un noyau stable avec Linux 2.0. (Le développement du noyau Linux 2.0 a été initié à partir d'une branche de Linux 1.2.x, quelque part autour de Linux 1.2.10, via la série de noyaux instables Linux 1.3.x.)
•
Lorsqu'un appel système est marqué "2.2" cela signifie que l'appel système est probablement apparu dans une version du noyau Linux 2.1.x, et est apparu pour la première fois dans un noyau stable avec Linux 2.2.0. (Le développement du noyau Linux 2.2 a été initié à partir d'une branche de Linux 2.0.21 via la série de noyaux instables Linux 2.1.x.)
•
Lorsqu'un appel système est marqué "2.4" cela signifie que l'appel système est probablement apparu dans une version du noyau Linux 2.3.x, et est apparu pour la première fois dans un noyau stable avec Linux 2.4.0. (Le développement du noyau Linux 2.4 a été initié à partir d'une branche de Linux 2.2.8 via la série de noyaux instables Linux 2.3.x.)
•
Lorsqu'un appel système est marqué "2.6" cela signifie que l'appel système est probablement apparu dans une version du noyau Linux 2.5.x, et est apparu pour la première fois dans un noyau stable avec Linux 2.6.0. (Le développement de Linux 2.6 a été initié à partir d'une branche de Linux 2.4.15 via la série de noyaux instables Linux 2.5.x.)
•
À partir de Linux 2.6.0, le modèle de développement a changé, et de nouveaux appels système peuvent apparaître dans chaque version de Linux 2.6.x. Dans ce cas, la version exacte où l'appel système est apparu est indiquée. Cette convention se poursuit avec la série de noyaux Linux 3.x, qui a suivi Linux 2.6.39 ; et la série de noyaux Linux 4.x, qui a suivi Linux 3.19 ; et la série de noyaux Linux 5.x, qui a suivi Linux 4.20 ; et la série de noyaux Linux 6.x, qui a suivi Linux 5.19.
•
Dans certains cas, un appel système a été ajouté à une série de noyaux stable après qu'elle se soit détachée de la série de noyaux stable précédente, puis rétroporté dans le noyau stable antérieur. Par exemple, certains appels système qui sont apparus dans Linux 2.6.x ont également été rétroportés dans une version Linux 2.4.x après Linux 2.4.15. Lorsque c'est le cas, la version où l'appel système est apparu dans les deux séries de noyaux majeures est répertoriée.

On many platforms, including x86-32, socket calls are all multiplexed (via glibc wrapper functions) through socketcall(2) and similarly System V IPC calls are multiplexed through ipc(2).

Although slots are reserved for them in the system call table, the following system calls are not implemented in the standard kernel: afs_syscall(2), break(2), ftime(2), getpmsg(2), gtty(2), idle(2), lock(2), madvise1(2), mpx(2), phys(2), prof(2), profil(2), putpmsg(2), security(2), stty(2), tuxcall(2), ulimit(2), and vserver(2) (see also unimplemented(2)). The getpmsg(2) and putpmsg(2) calls are for kernels patched to support STREAMS, and may never be in the standard kernel.

There was briefly set_zone_reclaim(2), added in Linux 2.6.13, and removed in Linux 2.6.16; this system call was never available to user space.

syscalls(2) — Linux manual pages

NAME

syscalls — Linux system call numbers and descriptions

SYNOPSIS

The Linux kernel exposes its system calls to user space via a well-defined interface. Each system call is identified by a unique number. This document lists the system calls known to the kernel, along with their associated numbers and descriptions.

#include <sys/syscall.h>

long syscall(long number, ...);

DESCRIPTION

System calls are the fundamental interface between user-space programs and the Linux kernel. When a program needs to perform an operation that requires kernel privileges (e.g., creating a process, opening a file, or communicating with hardware), it makes a system call.

Each system call has a unique number that identifies it to the kernel. These numbers can vary between different kernel versions and architectures. The glibc wrapper functions, such as open(), read(), fork(), etc., are typically used by applications instead of directly invoking the syscall() function. These wrappers handle the details of determining the correct system call number and passing arguments to the kernel, ensuring ABI compatibility.

The table below provides a list of system calls, their corresponding numbers on the current architecture, and a brief description. Note that the system call numbers are architecture-dependent.

The set of system calls has evolved over time. Some older system calls have been superseded by newer, more capable versions. This has led to multiple versions of certain system calls existing simultaneously, often differing in the size of their arguments or data structures. The glibc wrappers usually provide a unified interface, hiding these low-level differences from the application developer.

Examples of system calls that exist in multiple versions include:

•
stat(2), lstat(2), and fstat(2): There are typically three versions: an old version (e.g., sys_oldstat), a standard version (e.g., sys_newstat), and a 64-bit version (e.g., sys_stat64) for handling large file sizes and offsets.
•
uname(2): Multiple versions exist, such as sys_olduname, sys_uname, and sys_newuname, corresponding to different kernel interfaces.
•
vm86(2): Introduced in Linux 2.0, with sys_vm86old and sys_vm86 versions.
•
getrlimit(2): Introduced in Linux 2.4, with sys_old_getrlimit and sys_getrlimit.
•
User and Group IDs: Linux 2.4 increased the size of UIDs and GIDs from 16 to 32 bits. This led to the introduction of new system calls like chown32(2), getuid32(2), etc., which replaced older calls.
•
Large File Support: Linux 2.4 introduced support for large files (files larger than 2GB) on 32-bit architectures. New system calls like fcntl64(2), getdents64(2), stat64(2), etc., were added to handle file offsets and sizes that exceed 32 bits. On modern 64-bit architectures, these *64 variants are often the only ones available.
•
rt_sig* calls: Added in Linux 2.2 to support real-time signals, superseding older signal-related system calls.
•
select(2) and mmap(2): Due to argument passing conventions on some architectures (like i386), older versions (old_select, old_mmap) existed that used a pointer to an argument block. Newer versions (__NR__newselect, __NR_mmap2) directly support multiple arguments.

NOTES

The system call interface is primarily managed by the kernel developers. Applications should generally use the C library wrapper functions, which abstract away the details of system call numbers and argument passing. This ensures better portability and simplifies development.

For a complete and up-to-date list of system calls and their numbers for a specific architecture, one can consult the kernel source code (typically in files like arch/*/entry/syscalls/syscall_*.tbl) or use tools like strace(1).
