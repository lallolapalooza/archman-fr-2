NOM

systemd.network - Configuration réseau

SYNTAXE

network.network

DESCRIPTION

Un fichier texte simple de style ini qui encode la configuration réseau pour les interfaces réseau correspondantes, utilisé par systemd-networkd(8). Voir systemd.syntax(7) pour une description générale de la syntaxe.

Le fichier réseau principal doit avoir l'extension .network ; les autres extensions sont ignorées. Les réseaux sont appliqués aux liens dès que les liens apparaissent.

Notez que tous les paramètres et configurations ne peuvent pas être effectués avec des fichiers .network, et qu'il peut être nécessaire d'utiliser des fichiers systemd.link(5)) ou systemd.netdev(5)) en conjonction avec les fichiers .network lors de l'utilisation de périphériques réseau physiques et virtuels respectivement.

Les fichiers .network sont lus depuis les répertoires réseau système /usr/lib/systemd/network et /usr/local/lib/systemd/network [1], le répertoire volatil d'exécution réseau /run/systemd/network et le répertoire de configuration réseau local /etc/systemd/network. Tous les fichiers de configuration sont collectivement triés et traités par ordre alphabétique, quel que soit le répertoire dans lequel ils se trouvent. Cependant, les fichiers ayant des noms identiques se remplacent mutuellement. Il est recommandé que chaque nom de fichier soit préfixé par un nombre inférieur à "70" (par exemple, 10-eth0.network). Sinon, les fichiers .network par défaut ou ceux générés par systemd-network-generator.service(8) peuvent prendre le pas sur les fichiers configurés par l'utilisateur. Les fichiers dans /etc/ ont la plus haute priorité, les fichiers dans /run/ prennent le pas sur les fichiers du même nom sous /usr/. Ceci peut être utilisé pour remplacer un fichier de configuration fourni par le système par un fichier local si nécessaire. Comme cas spécial, un fichier vide (taille 0) ou un lien symbolique du même nom pointant vers /dev/null désactive complètement le fichier de configuration (il est "masqué").

En plus du fichier réseau foo.network, un répertoire "drop-in" foo.network.d/ peut exister. Tous les fichiers avec le suffixe ".conf" provenant de ce répertoire seront fusionnés dans l'ordre alphabétique et analysés après que le fichier principal lui-même ait été analysé. Ceci est utile pour modifier ou ajouter des paramètres de configuration, sans avoir à modifier le fichier de configuration principal. Chaque fichier drop-in doit avoir des en-têtes de section appropriés.

En plus de /etc/systemd/network, des répertoires ".d" de drop-in peuvent être placés dans les répertoires /usr/lib/systemd/network ou /run/systemd/network. Les fichiers drop-in dans /etc/ prennent le pas sur ceux dans /run/ qui à leur tour prennent le pas sur ceux dans /usr/lib/. Les fichiers drop-in sous n'importe lequel de ces répertoires prennent le pas sur le fichier réseau principal, où qu'il se trouve.

OPTIONS DE SECTION [MATCH]

Le fichier réseau contient une section [Match], qui détermine si un fichier réseau donné peut être appliqué à une interface donnée ; et une section [Network] spécifiant comment l'interface doit être configurée. Le premier (par ordre alphabétique) des fichiers réseau qui correspond à une interface donnée est appliqué, tous les fichiers suivants sont ignorés, même s'ils correspondent aussi.

Notez que toutes les interfaces réseau qui ont la propriété udev ID_NET_MANAGED_BY= définie ne seront jamais mises en correspondance par aucun fichier .network – à moins que la valeur de la propriété ne soit la chaîne "io.systemd.Network" –, même si la section [Match] correspondrait autrement. Ceci peut être utilisé pour exclure des interfaces réseau spécifiques de la gestion de systemd-networkd(8), tout en conservant la section [Match] générique. La propriété ID_NET_MANAGED_BY= déclare ainsi la *propriété* prévue du périphérique, et permet de s'assurer que les implémentations concurrentes de gestion réseau ne se font pas concurrence pour la gestion de périphériques spécifiques.

Un fichier réseau est dit correspondre à une interface réseau si toutes les correspondances spécifiées par la section [Match] sont satisfaites. Lorsqu'un fichier réseau ne contient pas de paramètres valides dans la section [Match], le fichier correspond à toutes les interfaces et systemd-networkd émet un avertissement à ce sujet. Astuce : pour éviter l'avertissement et indiquer clairement que toutes les interfaces doivent correspondre, ajoutez ceci :

Name=*

MACAddress=

Une liste d'adresses matérielles séparées par des espaces. Les formats acceptables sont :

hexadécimal séparé par des deux-points

Chaque champ doit être un octet. Par exemple, "12:34:56:78:90:ab" ou "AA:BB:CC:DD:EE:FF".

Ajouté dans la version 250.

hexadécimal séparé par des traits d'union

Chaque champ doit être un octet. Par exemple, "12-34-56-78-90-ab" ou "AA-BB-CC-DD-EE-FF".

hexadécimal séparé par des points

Chaque champ doit être deux octets. Par exemple, "1234.5678.90ab" ou "AABB.CCDD.EEFF".

format d'adresse IPv4

Par exemple, "127.0.0.1" ou "192.168.0.1".

Ajouté dans la version 250.

format d'adresse IPv6

Par exemple, "2001:0db8:85a3::8a2e:0370:7334" ou "::1".

[LIEN] OPTIONS DE SECTION

La section [Link] accepte les clés suivantes :

MACAddress=

L'adresse matérielle à définir pour l'appareil.

Ajouté dans la version 218.

MTUBytes=

L'unité de transmission maximale en octets à définir pour l'appareil. Les suffixes habituels K, M, G, sont pris en charge et sont compris dans la base 1024.

Notez que si IPv6 est activé sur l'interface, et que le MTU est choisi en dessous de 1280 (le MTU minimum pour IPv6), il sera automatiquement augmenté à cette valeur.

Ajouté dans la version 218.

ARP=

Prend une valeur booléenne. Si elle est définie sur vrai, le protocole ARP (Address Resolution Protocol) de bas niveau pour IPv4 et le protocole NDP (Neighbor Discovery Protocol) pour IPv6 sont activés pour cette interface. Par exemple, la désactivation de l'ARP est utile lors de la création de plusieurs interfaces virtuelles MACVLAN ou VLAN au-dessus d'une seule interface physique de niveau inférieur, qui servira alors uniquement de périphérique de liaison/"pont" agrégeant le trafic vers le même lien physique et ne participant pas autrement au réseau. Par défaut, non défini, et activé lorsque l'adressage local de lien IPv4 est activé dans LinkLocalAddressing= ou qu'une adresse IPv4 avec DuplicateAddressDetection= activé est demandée. Sinon, la valeur par défaut du noyau sera utilisée.

Ajouté dans la version 232.

Multicast=

Prend une valeur booléenne. Si elle est définie sur vrai, l'indicateur multicast sur l'appareil est activé. Par défaut, non défini et l'indicateur reste inchangé. Lorsqu'il est désactivé, IPv6AcceptRA= et IPv6SendRA= ne peuvent pas être activés.

Ajouté dans la version 239.

AllMulticast=

Prend une valeur booléenne. Si elle est définie sur vrai, le pilote récupère tous les paquets multicast du réseau. Cela se produit lorsque le routage multicast est activé. Par défaut, non défini.

Ajouté dans la version 239.

Promiscuous=

Prend une valeur booléenne. Si elle est définie sur vrai, le mode promiscuous de l'interface est activé. Par défaut, non défini.

Si cela est défini sur faux pour le lien sous-jacent d'un MACVLAN/MACVTAP en mode "passthrough", l'interface virtuelle sera créée avec l'indicateur "nopromisc" défini.

Ajouté dans la version 248.

Unmanaged=

Prend une valeur booléenne. Lorsqu'elle est définie sur "yes", aucune tentative n'est faite pour activer ou configurer les liens correspondants, ce qui équivaut à l'absence de fichiers réseau correspondants. Par défaut, "no".

Ceci est utile pour empêcher les fichiers réseau correspondants ultérieurs d'interférer avec certaines interfaces entièrement contrôlées par d'autres applications.

Ajouté dans la version 233.

Group=

Les groupes de liens sont similaires aux ports de commutation dans les commutateurs gérés. Lorsque des interfaces réseau sont ajoutées à un groupe numéroté, des opérations sur toutes les interfaces de ce groupe peuvent être effectuées simultanément. Prend un entier non signé dans la plage 0...2147483647. Par défaut, non défini.

[OPTIONS DE LIEN]

Le fichier de configuration du <code>.link</code> est utilisé pour configurer les paramètres de bas niveau des interfaces réseau, tels que l'adresse MAC, le nom de l'appareil, et les paramètres spécifiques à SR-IOV.

Les options suivantes sont acceptées dans la section [Link] :

Name=

Spécifie le nom de l'interface réseau. Le nom peut être une chaîne quelconque, mais il est recommandé d'utiliser des noms tels que eth0, wlan0, etc. Des caractères génériques peuvent être utilisés pour correspondre à plusieurs interfaces. Par exemple, "eth*" correspondra à toutes les interfaces commençant par "eth". Si cette option n'est pas définie, le nom de l'interface est dérivé du nom de fichier du fichier de configuration, par exemple, "enp2s0.link" deviendra "enp2s0". La prise en charge de "eth*" a été ajoutée dans la version 250.

MACAddress=

Spécifie l'adresse MAC de l'interface réseau. L'adresse MAC doit être dans le format standard des six paires d'hexadécimaux séparées par des deux-points, par exemple : 12:34:56:78:9a:bc.

WakeOnLan=

Définit la politique de réveil sur réseau local (Wake-on-LAN). Accepte les valeurs "phy", "unicast", "magic", "disabled". "disabled" désactive complètement WoL. "magic" n'active WoL que pour les paquets magiques. "unicast" active WoL pour les paquets unicast en plus des paquets magiques. "phy" active WoL pour le signal de la couche physique, ce qui inclut les paquets magiques et unicast, ainsi que toute autre activité de WoL prise en charge par le matériel. La valeur par défaut est "disabled". Les versions antérieures à 223 ne prennent en charge que "magic" et "disabled".

WakeOnLanMagic=

Définit le comportement de Wake-on-LAN pour les paquets magiques. Accepte une valeur booléenne. S'il est défini sur true, WoL est activé pour les paquets magiques. Par défaut, false. Cette option est obsolète depuis la version 223 et remplacée par WakeOnLan=.

WakeOnLanMagicSet=

Définit le comportement de Wake-on-LAN pour les paquets magiques. Accepte une valeur booléenne. S'il est défini sur true, WoL est activé pour les paquets magiques. Par défaut, false. Cette option est obsolète depuis la version 223 et remplacée par WakeOnLan=.

WakeOnLanPhy=

Définit le comportement de Wake-on-LAN pour le signal de la couche physique. Accepte une valeur booléenne. S'il est défini sur true, WoL est activé pour le signal de la couche physique. Par défaut, false. Cette option est obsolète depuis la version 223 et remplacée par WakeOnLan=.

WakeOnLanPhySet=

Définit le comportement de Wake-on-LAN pour le signal de la couche physique. Accepte une valeur booléenne. S'il est défini sur true, WoL est activé pour le signal de la couche physique. Par défaut, false. Cette option est obsolète depuis la version 223 et remplacée par WakeOnLan=.

WakeOnLanUnicast=

Définit le comportement de Wake-on-LAN pour les paquets unicast. Accepte une valeur booléenne. S'il est défini sur true, WoL est activé pour les paquets unicast. Par défaut, false. Cette option est obsolète depuis la version 223 et remplacée par WakeOnLan=.

WakeOnLanUnicastSet=

Définit le comportement de Wake-on-LAN pour les paquets unicast. Accepte une valeur booléenne. S'il est défini sur true, WoL est activé pour les paquets unicast. Par défaut, false. Cette option est obsolète depuis la version 223 et remplacée par WakeOnLan=.

MTUBytes=

Définit la taille de l'unité de transmission maximale (MTU) en octets. La valeur doit être un entier dans la plage de 68 à 65535. Si cette option n'est pas spécifiée, la valeur par défaut du noyau est utilisée.

Netfilter=

Définit le comportement de Netfilter pour cette interface. Accepte une valeur booléenne. Si true, Netfilter est activé pour cette interface. Par défaut, false.

IPVLAN=

Configure une interface IP-in-IPVLAN. Accepte un entier dans la plage 0...4094. Si cette option est définie, une interface IPVLAN est créée avec l'ID VLAN spécifié.

LinkLocalAddressing=

Active l'autoconfiguration d'adresses locales de lien. Accepte une valeur booléenne, ipv4, et ipv6. Une adresse locale de lien IPv6 est configurée lorsque yes ou ipv6. Une adresse locale de lien IPv4 est configurée lorsque yes ou ipv4 et lorsque l'autoconfiguration DHCPv4 a échoué pendant un certain temps. (L'autoconfiguration d'adresses locales de lien IPv4 se produit généralement en parallèle avec des tentatives répétées pour acquérir un bail DHCPv4).

Par défaut no lorsque KeepMaster= ou Bridge= est défini ou lorsque MACVLAN=/MACVTAP= spécifié a Mode=passthru, ou ipv6 sinon.

Lorsque l'adressage local de lien IPv4 est activé, ARP= est activé sauf s'il est explicitement configuré.

Ajouté en version 219.

IPv6LinkLocalAddressGenerationMode=

Spécifie comment l'adresse locale de lien IPv6 est générée. Accepte l'une des valeurs suivantes : "eui64", "none", "stable-privacy" et "random". Si cette option n'est pas définie, "stable-privacy" est utilisé si IPv6StableSecretAddress= est spécifié, et si ce n'est pas le cas, "eui64" est utilisé. Notez que si LinkLocalAddressing= est "no" ou "ipv4", alors IPv6LinkLocalAddressGenerationMode= sera ignoré. De plus, même si LinkLocalAddressing= est "yes" ou "ipv6", la définition de IPv6LinkLocalAddressGenerationMode=none désactive la configuration d'une adresse locale de lien IPv6.

Ajouté en version 246.

IPv6StableSecretAddress=

Accepte une adresse IPv6. L'adresse spécifiée sera utilisée comme secret stable pour générer l'adresse locale de lien IPv6. Si ce paramètre est spécifié et que IPv6LinkLocalAddressGenerationMode= n'est pas défini, alors IPv6LinkLocalAddressGenerationMode=stable-privacy est implicite. Si ce paramètre n'est pas spécifié et que "stable-privacy" est défini sur IPv6LinkLocalAddressGenerationMode=, alors une adresse secrète stable sera générée à partir de l'ID de la machine locale et du nom de l'interface.

Ajouté en version 249.

IPv4LLStartAddress=

[SR-IOV] OPTIONS DE SECTION

Si une chaîne vide est assignée, alors toutes les attributions précédentes sont effacées. Ce paramètre est lu par systemd-resolved.service(8).

Domains=

Une liste de domaines séparés par des espaces qui devraient être résolus en utilisant les serveurs DNS sur cette liaison. Chaque élément de la liste doit être un nom de domaine, éventuellement préfixé par un tilde ("~"). Les domaines avec le préfixe sont appelés "domaines de routage uniquement". Les domaines sans préfixe sont appelés "domaines de recherche" et sont d'abord utilisés comme suffixes de recherche pour étendre les noms d'hôtes à étiquette unique (noms d'hôtes ne contenant aucun point) en noms de domaine complets (FQDN). Si un nom d'hôte à étiquette unique est résolu sur cette interface, chacun des domaines de recherche spécifiés lui est ajouté tour à tour, le convertissant en un nom de domaine complet, jusqu'à ce que l'un d'eux puisse être résolu avec succès.

Les domaines "de recherche" et "de routage uniquement" sont utilisés pour le routage des requêtes DNS : les recherches de noms d'hôtes se terminant par ces domaines (donc aussi les noms à étiquette unique, si des "domaines de recherche" sont listés) sont acheminées vers les serveurs DNS configurés pour cette interface. La logique de routage des domaines est particulièrement utile sur les hôtes multi-homed avec des serveurs DNS servant des zones DNS privées particulières sur chaque interface.

Le domaine "de routage uniquement" "~." (le tilde indiquant la définition d'un domaine de routage, le point faisant référence au domaine racine DNS qui est le suffixe implicite de tous les noms DNS valides) a un effet spécial. Il fait en sorte que tout le trafic DNS qui ne correspond à aucune autre entrée de routage de domaine configurée soit acheminé vers les serveurs DNS spécifiés pour cette interface. Ce paramètre est utile pour préférer un certain ensemble de serveurs DNS si une liaison sur laquelle ils sont connectés est disponible.

Ce paramètre est lu par systemd-resolved.service(8). Les "domaines de recherche" correspondent aux entrées domain et search dans resolv.conf(5). Le routage des noms de domaine n'a pas d'équivalent dans l'API glibc traditionnelle, qui n'a pas de concept de serveurs de noms de domaine limités à une liaison spécifique.

Si faux, les serveurs DNS configurés de cette liaison ne sont jamais utilisés pour de tels domaines, et sont exclusivement utilisés pour résoudre les noms qui correspondent à unau moins un des domaines configurés sur ce lien. IPv6AcceptRA=

Prend une valeur booléenne. Contrôle la prise en charge de la réception des annonces de routeur IPv6 (RA) pour l'interface. Si vrai, les RA sont acceptés ; si faux, les RA sont ignorés. Lorsque les RA sont acceptés, ils peuvent déclencher le démarrage du client DHCPv6 si les indicateurs pertinents sont définis dans les données RA, ou si aucun routeur n'est trouvé sur le lien.

Cela ne peut pas être activé sur les périphériques agrégés dans un périphérique de liaison, ni lorsque l'adressage de lien local IPv6 (voir LinkLocalAddressing=) ou le multicast (voir Multicast=) est désactivé. Par conséquent, dans ce cas, Multicast= doit être explicitement activé pour rendre cette fonctionnalité utilisable. Lorsque IPv6SendRA=, IPv6Forwarding= ou IPMasquerade= est activé, cette fonctionnalité est désactivée par défaut, mais peut être outrepassée en activant explicitement ce réglage. Notez que IPv6Forwarding= peut être activé indirectement lorsque le réglage global portant le même nom est activé, ou lorsque IPMasquerade= est activé sur d'autres interfaces. Voir également IPv6Forwarding= et IPMasquerade= pour plus de détails. Activé par défaut sinon.

D'autres réglages pour la prise en charge des RA IPv6 peuvent être configurés dans la section [IPv6AcceptRA], voir ci-dessous.

Voir également IP Sysctl[9] dans la documentation du noyau concernant "accept_ra", mais notez que le réglage 1 de systemd (c'est-à-dire vrai) correspond au réglage 2 du noyau.

Notez que l'implémentation du protocole RA IPv6 du noyau est toujours désactivée, quel que soit ce réglage. Si cette option est activée, une implémentation en espace utilisateur du protocole RA IPv6 est utilisée, et l'implémentation propre au noyau reste désactivée, car systemd-networkd doit connaître tous les détails fournis dans les annonces, et ceux-ci ne sont pas disponibles auprès du noyau si l'implémentation propre au noyau est utilisée.

IPv4ReversePathFilter=

Configure le filtrage de chemin inverse IPv4. S'il est activé, lorsqu'un paquet IPv4 est reçu, la machine vérifiera d'abord si la *source* du paquet serait routée via l'interface par laquelle il est arrivé. S'il n'y a pas de route vers la source sur cette interface, la machine rejettera le paquet. Prend l'une des valeurs "no", "strict" ou "loose". Lorsque "no", aucune validation de source ne sera effectuée. Lorsque "strict", chaque paquet entrant est testé par rapport à la FIB et si l'interface entrante n'est pas le meilleur chemin inverse, le contrôle du paquet échouera. Par défaut, les paquets échoués sont rejetés. Lorsque "loose", l'adresse source de chaque paquet entrant est testée par rapport à la FIB. Le paquet n'est rejeté que si l'adresse source n'est atteignable via aucune interface sur ce routeur. Voir RFC 3704[11]. Lorsqu'il n'est pas défini, la valeur par défaut du noyau sera utilisée.

MulticastIGMPVersion=

Configure la version IGMP multicast IPv4 à utiliser, et contrôle la valeur de /proc/sys/net/ipv4/conf/INTERFACE/force_igmp_version. Prend l'une des valeurs "no", "v1", "v2" ou "v3". Lorsque "no", aucune application forcée d'une version IGMP n'est appliquée. Les retours en arrière IGMPv1/v2 sont autorisés, et systemd-networkd reviendra en mode IGMPv3 après l'expiration de tous les minuteurs de Querier Present IGMPv1/v2. Lorsque "v1", l'utilisation de la version IGMP 1 est forcée. Un rapport IGMPv1 sera retourné même si des requêtes IGMPv2/v3 sont reçues. Lorsque "v2", l'utilisation de la version IGMP 2 est forcée. Un rapport IGMPv2 sera retourné si une requête IGMPv2/v3 est reçue. systemd-networkd reviendra à IGMPv1 si une requête IGMPv1 est reçue. Lorsque "v3", l'utilisation de la version IGMP 3 est forcée, et la réponse est la même qu'avec "no". Par défaut, non défini - le sysctl n'est pas défini.

Prend une valeur booléenne. Permet à systemd-networkd de configurer un lien spécifique même s'il n'a pas de porteur (carrier). Par défaut, false. Si activé, et que le réglage IgnoreCarrierLoss= n'est pas explicitement défini, alors il est également activé.

Avec cette option activée, pour que l'interface entre dans l'état "configurée", ce qui est nécessaire pour que systemd-networkd-wait-online fonctionne correctement pour l'interface, tous les mécanismes de configuration d'adresse dynamique comme DHCP= et IPv6AcceptRA= (qui est activé par défaut dans la plupart des cas) doivent être désactivés. Sinon, sans porteur, l'interface restera bloquée dans l'état "configuration", et systemd-networkd-wait-online pour l'interface expirera. Ajouté dans la version 235.

IgnoreCarrierLoss=

Prend une valeur booléenne ou une durée (timespan). Lorsque vrai, systemd-networkd conserve la configuration statique et dynamique de l'interface même si son porteur est perdu. Lorsque faux, systemd-networkd abandonne la configuration statique et dynamique de l'interface. Lorsqu'une durée est spécifiée, systemd-networkd attend la durée spécifiée, et ignore la perte du porteur si le lien redevient porteur dans le délai imparti. Régler à 0 seconde équivaut à "non", et "infini" équivaut à "oui".

Spécifier une durée finie peut être utile dans les cas suivants, par exemple :

• Une interface sans fil se connectant à un réseau qui possède plusieurs points d'accès avec le même SSID.
• L'asservissement d'une interface sans fil à une interface bond, qui peut se déconnecter du point d'accès connecté et entraîner la perte de son porteur.
• Le pilote de l'interface se réinitialise lorsque la MTU est modifiée.

Lorsque Bond= est spécifié pour une interface sans fil, la valeur par défaut est de 3 secondes. Lorsque le client DHCPv4 est activé et que UseMTU= dans la section [DHCPv4] est activé, la valeur par défaut est de 5 secondes. Sinon, la valeur par défaut est celle spécifiée avec ConfigureWithoutCarrier=. KeepConfiguration=

Prend une valeur booléenne ou l'une des valeurs "static", "dynamic-on-stop", et "dynamic". Lorsque "static", systemd-networkd ne supprimera pas les adresses et routes configurées statiquement au démarrage. Lorsque "dynamic-on-stop", les adresses et routes configurées dynamiquement, telles que DHCPv4, DHCPv6, SLAAC, et l'adresse link-local IPv4, ne seront pas supprimées lorsque systemd-networkd s'arrête. Lorsque "dynamic", les adresses et routes configurées dynamiquement ne seront jamais supprimées, et la durée de vie des baux DHCPv4 sera ignorée. Ceci est contraire à la spécification DHCP, mais peut être le meilleur choix si, par exemple, le système de fichiers racine dépend de cette connexion. Le réglage "dynamic" implique "dynamic-on-stop", et "yes" implique "dynamic" et "static". Par défaut, "dynamic-on-stop" lorsque systemd-networkd fonctionne en initrd, "yes" lorsque le système de fichiers racine est un système de fichiers réseau, et "no" sinon.

NetLabel=label

Ce paramètre fournit une méthode pour intégrer la configuration réseau statique et dynamique dans les règles du sous-système NetLabel[16] de Linux, utilisé par les Modules de Sécurité Linux (LSM)[17] pour le contrôle d'accès réseau. L'étiquette, avec des règles LSM appropriées, peut être utilisée pour contrôler la connectivité de (par exemple) un service avec des pairs sur le réseau local. Au moins avec SELinux, seule l'entrée peut être contrôlée mais pas la sortie. L'avantage d'utiliser ce paramètre est qu'il peut être possible d'appliquer la partie indépendante de l'interface de la configuration NetLabel à un stade très précoce de la séquence de démarrage du système, au moment où les interfaces réseau ne sont pas encore disponibles, avec netlabelctl(8), et la configuration par interface avec systemd-networkd une fois que les interfaces apparaissent plus tard. Actuellement, cette fonctionnalité est uniquement implémentée pour SELinux.

L'option attend une seule étiquette NetLabel. L'étiquette doit être conforme aux restrictions lexicales des étiquettes LSM. Lorsqu'une interface est configurée avec des adresses IP, les adresses et les masques de sous-réseau seront ajoutés aux règles de NetLabel Fallback Peer Labeling[18]. Ils seront supprimés lorsque l'interface sera déconfigurée. Les échecs de gestion des étiquettes seront ignorés.


Attention
Une fois l'étiquetage activé pour le trafic réseau, de nombreux points de contrôle d'accès LSM dans la pile réseau Linux passent de dormants à actifs. Il faut veiller à éviter de se retrouver dans une situation où, par exemple, la connectivité à distance est rompue, car la politique de sécurité n'a pas été mise à jour pour prendre en compte les contrôles d'accès LSM par paquet et aucune règle ne permettrait le trafic réseau. Notez également qu'une configuration supplémentaire avec netlabelctl(8) est nécessaire.
Exemple : 
[Address]
NetLabel=system_u:object_r:localnet_peer_t:s0

Avec les règles d'exemple s'appliquant à l'interface « eth0 », lorsque l'interface est configurée avec une adresse IPv4 de 10.0.0.123/8, systemd-networkd effectue l'équivalent de l'opération netlabelctl

netlabelctl unlbl add interface eth0 address:10.0.0.0/8 label:system_u:object_r:localnet_peer_t:s0

et l'opération inverse lorsque l'adresse IPv4 est déconfigurée. La configuration peut être utilisée avec des règles LSM ; dans le cas de SELinux, pour permettre à un domaine SELinux de recevoir des données d'objets de la classe « peer » de SELinux. Par exemple :

type localnet_peer_t;
allow my_server_t localnet_peer_t:peer recv;

L'effet de la configuration et des règles ci-dessus (en l'absence d'autres règles, le cas échéant) est de n'autoriser que « my_server_t » (et rien d'autre) à recevoir des données du sous-réseau local 10.0.0.0/8 de l'interface « eth0 ».

NFTSet=source:family:table:set

Ce paramètre fournit une méthode pour intégrer la configuration réseau dans des règles de pare-feu avec des ensembles NFT[19]. L'avantage d'utiliser ce paramètre est que la configuration réseau statique (ou les adresses réseau obtenues dynamiquement, voir les directives similaires dans d'autres sections) peut être utilisée dans les règles de pare-feu avec l'indirection des types d'ensembles NFT. Par exemple, l'accès pourrait être accordé uniquement aux hôtes du sous-réseau local. Les règles de pare-feu utilisant l'adresse IP d'une interface sont également mises à jour instantanément lorsque la configuration réseau change, par exemple via DHCP.

Cette option attend une liste d'éléments séparés par des espaces de définitions d'ensembles NFT. Chaque définition se compose d'un tuple séparé par des deux-points : type de source (l'un de « address », « prefix » ou « ifindex »), famille d'adresses NFT (l'un de « arp », « bridge », « inet », « ip », « ip6 », ou « netdev »), nom de table et nom d'ensemble. Les noms des tables et des ensembles doivent être conformes aux restrictions lexicales des noms de tables NFT. Le type de l'élément utilisé dans le filtre NFT doit correspondre au type implicite par la directive (« address », « prefix » ou « ifindex ») et au type d'adresse (IPv4 ou IPv6) comme indiqué dans le tableau ci-dessous.

Tableau 1. Valeurs définies pour type de source

Type de source Description Nom de type NFT correspondant
« address » adresse IP d'hôte « ipv4_addr » ou « ipv6_addr »
« prefix » préfixe réseau « ipv4_addr » ou « ipv6_addr », avec « flags interval »
« ifindex » index d'interface « iface_index »

Lorsqu'une interface est configurée avec des adresses IP, les adresses, les masques de sous-réseau ou l'index de l'interface seront ajoutés aux ensembles NFT. Les informations seront supprimées lorsque l'interface sera déconfigurée.
systemd-networkd insère uniquement des éléments dans (ou les supprime de) les ensembles, les règles, tables et ensembles NFT associés doivent donc être préparés ailleurs à l'avance. Les échecs de gestion des ensembles seront ignorés.

Exemple :

[Address]
NFTSet=prefix:netdev:filter:eth_ipv4_prefix

Règles NFT correspondantes :

table netdev filter {
        set eth_ipv4_prefix {
                type ipv4_addr
                flags interval
        }
        chain eth_ingress {
                type filter hook ingress device "eth0" priority filter; policy drop;
                ip daddr != @eth_ipv4_prefix drop
                accept
        }
}

Prend une valeur booléenne. Lorsque vrai, les options envoyées au serveur DHCP suivront la RFC 7844[27] (Profils d'anonymat pour les clients DHCP) afin de minimiser la divulgation d'informations identifiables. Par défaut, la valeur est fausse.

Cela signifie que les tailles des requêtes DHCP augmenteront et que les données de bail seront plus complètes que normalement, bien que la plupart des données demandées ne soient pas réellement utilisées.

Token=

Spécifie un mode optionnel de génération d'adresse pour l'autoconfiguration d'adresse sans état (SLAAC). Les valeurs suivantes sont supportées :

eui64

L'algorithme EUI-64 sera utilisé pour générer une adresse pour ce préfixe. Supporté uniquement par les interfaces Ethernet ou InfiniBand.

Ajouté dans la version 250.

static:ADDRESS

Une adresse IPv6 doit être spécifiée après deux-points (":"), et les bits de poids faible de l'adresse fournie sont combinés avec les bits de poids fort d'un préfixe reçu dans un message d'annonce de routeur (RA) pour former une adresse complète. Notez que si plusieurs préfixes sont reçus dans un message RA, ou dans plusieurs messages RA, des adresses seront formées à partir de chacun d'eux en utilisant l'adresse fournie. Ce mode implémente SLAAC mais utilise un identifiant d'interface statique au lieu d'un identifiant généré par l'algorithme EUI-64. Étant donné que l'identifiant d'interface est statique, si la détection d'adresse dupliquée détecte que l'adresse calculée est un duplicata (utilisée par un autre nœud sur le lien), ce mode ne fournira pas d'adresse pour ce préfixe. Si une adresse IPv6 sans mode est spécifiée, alors le mode "static" est supposé.

Ajouté dans la version 250.

prefixstable[:ADDRESS][,UUID]

L'algorithme spécifié dans la **RFC 7217**[37] sera utilisé pour générer les identifiants d'interface. Ce mode peut éventuellement prendre une adresse IPv6 séparée par deux-points (":"). Si une adresse IPv6 est spécifiée, alors un identifiant d'interface est généré uniquement lorsqu'un préfixe reçu dans un message RA correspond à l'adresse fournie.

Ce mode peut également prendre éventuellement un UUID non nul dans le format que sd_id128_from_string() accepte, par exemple "86b123b969ba4b7eb8b3d8605123525a" ou "86b123b9-69ba-4b7e-b8b3-d8605123525a". Si un UUID est spécifié, la valeur est utilisée comme clé secrète pour générer les identifiants d'interface. S'il n'est pas spécifié, alors un ID spécifique à l'application généré avec le machine-ID du système sera utilisé comme clé secrète. Voir sd-id128(3), sd_id128_from_string(3), et sd_id128_get_machine(3).

Notez que l'algorithme "prefixstable" utilise à la fois le nom de l'interface et l'adresse MAC comme entrées pour le hachage afin de calculer l'identifiant d'interface, donc si l'un de ceux-ci est modifié, l'identifiant d'interface (et l'adresse) résultant sera modifié, même si le préfixe reçu dans le message RA n'a pas été modifié.

Ajouté dans la version 250.

Si aucun mode de génération d'adresse n'est spécifié (ce qui est la valeur par défaut), ou si un préfixe reçu ne correspond à aucune des adresses fournies en mode "prefixstable", alors l'algorithme EUI-64 sera utilisé pour les interfaces Ethernet ou InfiniBand, sinon "prefixstable" sera utilisé pour former un identifiant d'interface pour ce préfixe.

La section [DHCPServer] contient les paramètres du serveur DHCP, s'il est activé via l'option DHCPServer= décrite ci-dessus :

Spécifie l'adresse du serveur pour le serveur DHCP. Prend une adresse IPv4 avec une longueur de préfixe séparée par une barre oblique, par exemple "192.168.0.1/24". La valeur par défaut n'est pas définie, et une des adresses IPv4 statiques configurées dans la section [Network] ou [Address] sera automatiquement sélectionnée. Ce paramètre peut être utile lorsque l'interface sur laquelle le serveur DHCP s'exécute a plusieurs adresses IPv4 statiques.

Ceci implique Address= dans la section [Network] ou [Address] avec la même adresse et longueur de préfixe. C'est-à-dire,

[Network]
DHCPServer=yes
Address=192.168.0.1/24
Address=192.168.0.2/24
[DHCPServer]
ServerAddress=192.168.0.1/24

ou

[Network]
DHCPServer=yes
[Address]
Address=192.168.0.1/24
[Address]
Address=192.168.0.2/24
[DHCPServer]
ServerAddress=192.168.0.1/24

sont équivalents à ce qui suit :

[Network]
DHCPServer=yes
Address=192.168.0.2/24
[DHCPServer]
ServerAddress=192.168.0.1/24

Depuis la version 255, comme le réglage Address= dans la section [Network] ou [Address], ceci supporte également une adresse nulle, par exemple "0.0.0.0/24", et une adresse inutilisée sera automatiquement sélectionnée. Pour plus de détails sur la sélection automatique d'adresse, voir le réglage Address= dans la section [Network] ci-dessus.

Ajouté en version 249.

PoolOffset=, PoolSize=

Configure le pool d'adresses à distribuer. Le pool est une séquence contiguë d'adresses IP dans le sous-réseau configuré pour l'adresse serveur, qui n'inclut pas l'adresse du sous-réseau ni l'adresse de diffusion. PoolOffset= prend le décalage du pool à partir du début du sous-réseau, ou zéro pour utiliser la valeur par défaut. PoolSize= prend le nombre d'adresses IP dans le pool ou zéro pour utiliser la valeur par défaut. Par défaut, le pool commence à la première adresse après l'adresse du sous-réseau et occupe le reste du sous-réseau, à l'exclusion de l'adresse de diffusion. Si le pool inclut l'adresse du serveur (par défaut), celle-ci est réservée et non distribuée aux clients.

Contrôlent la durée par défaut et maximale des baux DHCP à passer aux clients. Ces réglages prennent des valeurs de temps en secondes ou une autre unité de temps courante, selon le suffixe. La durée de bail par défaut est utilisée pour les clients qui n'ont pas demandé de durée de bail spécifique. Si un client demande une durée de bail plus longue que la durée maximale, elle est automatiquement raccourcie au temps spécifié. La durée de bail par défaut est de 1h, la durée maximale est de 12h. Des durées de bail plus courtes sont bénéfiques si les données de configuration dans les baux DHCP changent fréquemment et que les clients doivent apprendre les nouveaux paramètres avec des latences plus courtes. Des durées de bail plus longues réduisent le trafic réseau DHCP généré.

Lorsque ":none" est utilisé, aucune interface de liaison montante ne sera sélectionnée. La valeur par défaut est ":auto".

EmitDNS=, DNS=

EmitDNS= prend une valeur booléenne. Configure si les baux DHCP attribués aux clients doivent contenir les informations du serveur DNS. Par défaut, la valeur est "yes". Les serveurs DNS à transmettre aux clients peuvent être configurés avec l'option DNS=, qui prend une liste d'adresses IPv4, ou la valeur spéciale "_server_address" qui sera convertie en l'adresse utilisée par le serveur DHCP.

Si l'option EmitDNS= est activée mais qu'aucun serveur n'est configuré, les serveurs sont automatiquement propagés à partir d'une interface "uplink" qui a des serveurs appropriés définis. L'interface "uplink" est déterminée par la route par défaut du système avec la priorité la plus élevée. Notez que ces informations sont acquises au moment où le bail est attribué, et ne prennent pas en compte les interfaces d'uplink qui acquièrent les informations du serveur DNS ultérieurement. Si aucune interface d'uplink appropriée n'est trouvée, les données du serveur DNS de /etc/resolv.conf sont utilisées. Notez également que les baux ne sont pas actualisés si la configuration du réseau d'uplink change. Pour garantir que les clients acquièrent régulièrement les informations les plus récentes du serveur DNS d'uplink, il est donc conseillé de réduire la durée du bail DHCP via MaxLeaseTimeSec= décrit ci-dessus.

Prend une valeur booléenne. Lorsqu'elle est vraie, le serveur prend en charge la RFC 4039[42]. Lorsqu'un client envoie un message DHCPDISCOVER avec l'option Rapid Commit au serveur, le serveur répond par un message DHCPACK au client, au lieu de DHCPOFFER. Par défaut, vrai.

Ajouté dans la version 255.

Prend une valeur booléenne ou la valeur spéciale "runtime". Lorsque "yes", le serveur DHCP chargera et sauvegardera les baux dans le stockage persistant. Lorsque "runtime", le serveur DHCP chargera et sauvegardera les baux dans le stockage d'exécution, donc les baux liés seront perdus lorsque le stockage d'exécution sera effacé, par exemple en appelant systemctl clean systemd-networkd.service ou que le système est redémarré. Lorsqu'il n'est pas spécifié, la valeur spécifiée dans le même paramètre dans networkd.conf(5), qui est "yes" par défaut, sera utilisée.

Point d'échantillonnage optionnel en pourcentage avec une décimale (par exemple, "75%", "87.5%") ou en millièmes (par exemple, "875‰"). Ceci sera ignoré lorsque BitRate= n'est pas spécifié.

[IPOIB] OPTIONS DE SECTION

La section [IPoIB] gère IP sur Infiniband et accepte les clés suivantes :

Mode=

Prend l'une des valeurs spéciales "datagram" ou "connected". Par défaut, elle n'est pas définie et le défaut du noyau est utilisé.

Lorsque défini sur "datagram", le transport de datagrammes non fiables (UD) d'Infiniband est utilisé, et donc l'MTU de l'interface est égale à l'MTU L2 d'IB moins l'en-tête d'encapsulation IPoIB (4 octets). Le mode connecté tire parti de la nature connectée du transport IB et permet une MTU allant jusqu'à la taille maximale de paquet IP de 64 Ko, ce qui réduit le nombre de paquets IP nécessaires pour gérer les grands datagrammes UDP, les segments TCP, etc., et augmente les performances pour les gros messages.

Ajouté dans la version 250.

Prend une valeur booléenne. Lorsque défini sur vrai, le noyau ignore les groupes de multidiffusion gérés par l'espace utilisateur. Par défaut, non défini, et le défaut du noyau est utilisé.

[Network]

#SubnetId=0
#Announce=no

#[Network]
#IPv6AcceptRA=no
#[DHCPv6]
#WithoutRA=solicit
# Si le réseau montant fournit des messages d'annonce de routeur (RA) avec le

systemd.network - 5 - Manual Pages

Nom

systemd.network - Fichier de configuration de réseau

Synopsis

Fichier .network

Description

Les fichiers .network sont utilisés pour configurer l'interface réseau de bas niveau. Ils sont placés dans des répertoires comme /etc/systemd/network/, /run/systemd/network/ ou /usr/lib/systemd/network/. La configuration est appliquée par le service systemd-networkd. Les fichiers sont identifiés par leur nom. Par exemple, .network dans /etc/systemd est prioritaire sur .network dans /usr/lib. Les fichiers dans /run ont une priorité encore plus élevée que ceux dans /etc.

Un fichier .network est divisé en trois sections : [Match], [Network], et [Link].

Section [Match]

La section [Match] spécifie les conditions qui doivent être remplies pour que la configuration s'applique. Si une seule condition est spécifiée, elle doit être remplie. Si plusieurs conditions sont spécifiées, elles doivent toutes être remplies.

  • Name= : Nom de l'interface réseau (par exemple, eth0). Des caractères génériques sont autorisés.
  • MACAddress= : Adresse MAC de l'interface réseau.
  • Virtual= : Booléen indiquant si l'interface est virtuelle (true) ou non (false).
  • Path= : Chemin du périphérique dans /sys/class/net/.
  • Driver= : Pilote du périphérique.
  • Type= : Type de l'interface réseau (ether, wlan, bridge, etc.).
  • Host= : Nom d'hôte.
  • Domain= : Domaine de recherche DNS.

Section [Network]

La section [Network] configure les paramètres réseau tels que l'adressage IP, le routage et le DNS.

  • DHCP= : Type de DHCP à utiliser (yes, no, ipv4, ipv6).
  • Address= : Adresse IP statique à attribuer à l'interface.
  • Gateway= : Passerelle par défaut.
  • DNS= : Serveurs DNS à utiliser.
  • NTP= : Serveurs NTP à utiliser.
  • Domains= : Domaines de recherche DNS.
  • IPv4LL= : Activer l'adresse auto-configurée IPv4LL (true/false).
  • LinkLocalAddressing= : Activer l'adressage Link-Local (ipv4, ipv6, both, no).
  • ConfigureWithoutCarrier= : Configurer l'interface même sans porteuse (true/false).
  • WakeOnLan= : Activer Wake-on-LAN (true/false).

Section [Link]

La section [Link] configure les paramètres de bas niveau de l'interface réseau.

  • Name= : Nom de l'interface réseau.
  • MACAddress= : Adresse MAC de l'interface réseau.
  • MTUBytes= : Taille de l'unité de transmission maximale (MTU) en octets.
  • Kind= : Type de lien (par exemple, ether, vxlan).
  • State= : État de l'interface (up, down).
  • HardwareAddress= : Adresse MAC matérielle.
  • Description= : Description de l'interface.
  • Duplex= : Type de duplex (half, full).
  • Speed= : Vitesse de l'interface en Mbps.

Exemples

Exemple de fichier /etc/systemd/network/20-wired.network pour configurer une interface filaire avec DHCP :

[Match]
Name=enp3s0

[Network]
DHCP=yes

Exemple de fichier /etc/systemd/network/30-static.network pour configurer une interface filaire avec une adresse IP statique :

[Match]
Name=enp4s0

[Network]
Address=192.168.1.100/24
Gateway=192.168.1.1
DNS=8.8.8.8

La priorité des fichiers .network est déterminée par le chemin du répertoire dans lequel ils sont placés. L'ordre de priorité est : /run/, /etc/, /usr/lib/. Les fichiers du même répertoire sont triés par nom.
