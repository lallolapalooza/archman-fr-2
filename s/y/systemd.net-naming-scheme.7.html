NOM

systemd.net-naming-scheme - Schémas de nommage des périphériques réseau

DESCRIPTION

Les noms des interfaces réseau et les adresses MAC peuvent être générés en fonction de certains attributs stables des interfaces. Ceci est possible lorsqu'il y a suffisamment d'informations sur le périphérique pour générer ces attributs et que l'utilisation de ces informations est configurée. Cette page décrit le nommage des interfaces, c'est-à-dire les noms possibles qui peuvent être générés. Ces noms sont générés par la commande intégrée net_id de systemd-udevd.service(8) et exportés en tant que propriétés udev(7) (ID_NET_NAME_ONBOARD=, ID_NET_LABEL_ONBOARD=, ID_NET_NAME_PATH=, ID_NET_NAME_SLOT=).

Les noms et adresses MAC sont dérivés de divers attributs de métadonnées stables des périphériques. Les versions plus récentes de systemd-udevd prennent en compte davantage de ces attributs, améliorant (et donc potentiellement modifiant) les noms et adresses utilisés pour les mêmes périphériques. Différentes versions de ces règles de génération sont appelées « schémas de nommage ». Le schéma de nommage par défaut est choisi au moment de la compilation. Habituellement, ce sera la dernière version implémentée, mais il est également possible de définir l'une des anciennes versions pour préserver la compatibilité. Cela peut être utile, par exemple, pour les distributions qui peuvent introduire de nouvelles versions de systemd dans les versions stables sans modifier le schéma de nommage. Le schéma de nommage peut également être remplacé en utilisant le commutateur de ligne de commande du noyau net.naming_scheme=, voir systemd-udevd.service(8). Les schémas de nommage disponibles sont décrits ci-dessous.

Après la génération des propriétés udev, des règles udev appropriées peuvent être utilisées pour renommer réellement les périphériques en fonction de ces propriétés. Voir la description de NamePolicy= et MACAddressPolicy= dans systemd.link(5).

Notez que bien que le concept de schémas de nommage des interfaces réseau soit principalement pertinent dans le contexte de systemd-udevd.service, le gestionnaire de conteneurs systemd-nspawn(1) en tient également compte lors du nommage des interfaces réseau, voir ci-dessous.

POLITIQUES

Tous les noms commencent par un préfixe de deux caractères qui signifie le type d'interface.

Tableau 1. Préfixes de deux caractères basés sur le type d'interface

Préfixe Description
en Ethernet
ib InfiniBand
sl Serial line IP (slip)
wl Réseau local sans fil (WLAN)
ww Réseau étendu sans fil (WWAN)

Le programme intégré net_id de
udev(7) exporte les propriétés de périphérique suivantes :

ID_NET_NAME_ONBOARD=prefixonumber, ID_NET_NAME_ONBOARD=prefixdnumber

Ce nom est défini en fonction des informations d'ordre numérique fournies par le firmware pour les périphériques intégrés. Différents schémas sont utilisés en fonction du type de firmware, comme décrit dans le tableau ci-dessous.

Tableau 2. Schémas de nommage pour les périphériques intégrés

Format Description
prefixonumber Indice interne PCI
prefixdnumber Indice d'alias DeviceTree

Ajouté dans la version 243.

ID_NET_LABEL_ONBOARD=label

Cette propriété est définie en fonction d'une étiquette textuelle fournie par le firmware pour les périphériques intégrés. Ceci n'est disponible que pour les périphériques PCI.

Ajouté dans la version 243.

ID_NET_NAME_MAC=prefixxAABBCCDDEEFF

Ce nom est composé du préfixe, de la lettre x et de 12 chiffres hexadécimaux de l'adresse MAC. Il est disponible si le périphérique a une adresse MAC fixe. Comme ce nom est basé sur un attribut de la carte elle-même, il reste « stable » lorsque le périphérique est déplacé (même entre machines), mais changera lors du remplacement du matériel.

Ajouté dans la version 243.

ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port], ID_NET_NAME_SLOT=prefixvslot, ID_NET_NAME_SLOT=prefixxslot, ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port]bnumber, ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port]uport...[cconfig][iinterface], ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port]vslot, ID_NET_NAME_SLOT=prefix[Pdomain]sslot[ffunction][nport_name|ddev_port]rslot

Cette propriété décrit la position du slot. Différents schémas sont utilisés en fonction du type de bus, comme décrit dans le tableau ci-dessous. Dans le cas des périphériques USB, BCMA et SR-VIO, le nom complet consiste en le préfixe, l'identifiant du slot PCI, et l'identifiant du slot USB, BCMA ou SR-VIO. Les deux premières parties sont désignées par « ... » dans le tableau ci-dessous.

Tableau 3. Schémas de nommage par slot

Format Description
prefix [Pdomain] sslot [ffunction] [nport_name | ddev_port] Numéro de slot PCI
prefix vslot Numéro de slot VIO (IBM PowerVM)
prefix Xnumber Numéro d'interface VIF (Xen)
... bnumber Numéro de cœur Broadcom bus (BCMA)
... uport... [cconfig] [iinterface] Chaîne de numéros de port USB
... vslot Numéro de slot SR-VIO
... rslot Numéro de slot SR-IOV

Le domaine PCI n'est préfixé que lorsqu'il n'est pas 0. Tous les périphériques PCI multi-fonctions porteront le numéro de
ffunction dans le nom du périphérique, y compris le périphérique de fonction 0. Pour les périphériques non multi-fonctions, le numéro est supprimé s'il est 0. Le nom du port port_name est utilisé, ou le numéro de port ddev_port si le nom n'est pas connu.

Pour les périphériques BCMA, le numéro de cœur est supprimé lorsqu'il est 0.

Pour les périphériques USB, la chaîne complète des numéros de port des hubs est composée. Si le nom dépasse la longueur maximale de 15 caractères, le nom n'est pas exporté. Les valeurs habituelles du numéro de configuration USB 1 et du numéro d'interface 0 sont supprimées.

Les périphériques virtuels SR-IOV sont nommés en fonction du nom de l'interface parente, avec un suffixe v et le numéro du périphérique virtuel, les zéros non significatifs étant supprimés. Le numéro de bus est ignoré.

Les représentants des périphériques virtuels SR-IOV sont nommés en fonction du nom de l'interface du périphérique physique, avec un suffixe r et le numéro du périphérique virtuel qui est lié au représentant particulier, les zéros non significatifs étant supprimés. Le nom du port physique et le numéro de bus sont ignorés.

Dans certaines configurations, un pont PCI parent d'un contrôleur réseau donné peut être associé à un slot. Dans ce cas, nous ne générons pas cette propriété de périphérique pour éviter d'éventuels conflits de nommage.

Ajouté dans la version 243.

ID_NET_NAME_PATH=prefixcbus_id, ID_NET_NAME_PATH=prefixavendormodeliinstance, ID_NET_NAME_PATH=prefixiaddressnport_name, ID_NET_NAME_PATH=prefixuport..., ID_NET_NAME_PATH=prefix[Pdomain]pbussslot[ffunction][nphys_port_name|dd

ev_port], ID_NET_NAME_PATH=prefix[Pdomain]pbussslot[ffunction][nphys_port_name|ddev_port]bnumber, ID_NET_NAME_PATH=prefix[Pdomain]pbussslot[ffunction][nphys_port_name|ddev_port]uport...[cconfig][iinterface]

Cette propriété décrit l'emplacement d'installation du périphérique. Différents schémas sont utilisés en fonction du type de bus, comme décrit dans le tableau ci-dessous. Pour les périphériques BCMA et USB, les informations de chemin PCI doivent être connues, et le nom complet se compose du préfixe, de l'identifiant du slot PCI et de l'emplacement USB ou BCMA. Les deux premières parties sont désignées par « ... » dans le tableau ci-dessous.

Tableau 4. Schémas de nommage des chemins

Format Description
prefix cbus_id Identifiant de périphérique CCW ou CCW groupé
prefix avendor model iinstance Noms de chemin ACPI pour les périphériques de la plateforme ARM64
prefix iaddress nport_name Numéro et nom de port du périphérique Netdevsim (périphérique réseau simulé)

... bnumber Numéro de cœur du bus Broadcom (BCMA)
... uport... [cconfig] [iinterface] Chaîne de numéros de port USB

Les périphériques CCW et CCW groupés se trouvent sur les mainframes IBM System Z. Les zéros non significatifs et les points sont supprimés.

Pour les périphériques PCI, BCMA et USB, les mêmes règles que celles décrites ci-dessus pour le nommage des slots sont utilisées.

Ajouté dans la version 243.

HISTORIQUE

Les « schémas de nommage » suivants ont été définis (qui peuvent être choisis au moment du démarrage du système via le commutateur de ligne de commande du noyau net.naming_scheme=, voir ci-dessus) :

v238

C'est le schéma de nommage qui a été implémenté dans systemd 238.

Ajouté dans la version 243.

v239

Le nommage a été modifié pour les interfaces réseau virtuelles créées avec SR-IOV et NPAR et pour les périphériques où le périphérique contrôleur réseau PCI n'a pas de numéro de slot associé.

Les périphériques virtuels SR-IOV sont nommés en fonction du nom de l'interface parente, avec un suffixe « vport », où port est le numéro du périphérique virtuel. Auparavant, ces périphériques virtuels étaient nommés comme s'ils étaient complètement indépendants.

Les neuvième et suivants périphériques virtuels NPAR sont nommés en suivant le schéma utilisé pour les huit premières partitions NPAR. Auparavant, ces périphériques n'étaient pas renommés et le défaut du noyau (« ethN ») était utilisé.

Des noms sont également générés pour les périphériques PCI où le périphérique contrôleur réseau PCI n'a pas de numéro de slot associé, mais où l'un de ses parents en a un. Auparavant, ces périphériques n'étaient pas renommés et le défaut du noyau était utilisé.

Ajouté dans la version 243.

v240

Le préfixe « ib » et les noms stables pour les périphériques Infiniband sont introduits. Auparavant, ces périphériques n'étaient pas renommés.

Le champ d'index ACPI (utilisé dans ID_NET_NAME_ONBOARD=) est maintenant également utilisé lorsque 0.

Une nouvelle politique de nommage NamePolicy=keep a été introduite. Avec cette politique, si le nom du périphérique réseau a déjà été défini par l'espace utilisateur, le périphérique ne sera pas renommé à nouveau. Auparavant, cette politique de nommage s'appliquait implicitement, et maintenant elle doit être explicitement demandée. Effectivement, cela signifie que les périphériques réseau seront renommés conformément à la configuration, même s'ils ont déjà été renommés, si keep n'est pas spécifié comme politique de nommage dans le fichier .link. Voir systemd.link(5) pour une description de NamePolicy=.

Ajouté dans la version 243.

v241

MACAddressPolicy=persistent a été étendu pour définir les adresses MAC en fonction du nom du périphérique. Auparavant, les adresses étaient basées uniquement sur les attributs ID_NET_NAME_*, ce qui signifiait que les noms d'interface ne seraient jamais générés pour les périphériques virtuels. Désormais, une adresse persistante sera générée pour la plupart des périphériques, y compris en particulier les ponts.

Note : lorsque l'espace utilisateur ne définit pas d'adresse MAC pour un périphérique pont, le noyau attribuera initialement une adresse aléatoire, puis la modifiera lorsque le premier périphérique sera asservi au pont. Avec ce changement de politique de nommage, les ponts obtiennent une adresse MAC persistante basée sur le nom du pont au lieu du premier périphérique asservi.

Ajouté dans la version 243.

v243

La prise en charge du renommage des périphériques netdevsim (réseau simulé) a été ajoutée. Auparavant, ces périphériques n'étaient pas renommés.

Auparavant, un préfixe de type d'interface à deux lettres était ajouté à ID_NET_LABEL_ONBOARD=. Ce n'est plus le cas.

Ajouté dans la version 243.

v245

Lorsque systemd-nspawn(1) dérive le nom pour le côté hôte de l'interface réseau créée avec --network-veth à partir du nom du conteneur, il tronquait précédemment simplement le résultat à 15 caractères s'il était plus long (puisque c'est la longueur maximale pour les noms d'interface réseau). Désormais, pour tout nom d'interface qui serait plus long que 15 caractères, les 4 derniers caractères sont définis sur une valeur de hachage de 24 bits du nom d'interface complet. De cette façon, les collisions de noms d'interface réseau entre plusieurs conteneurs nommés de manière similaire (qui ne diffèrent que par le suffixe du nom du conteneur) devraient être moins probables (mais toujours possibles, car la valeur de hachage de 24 bits est très petite).

Ajouté dans la version 245.

v247

Lorsqu'un slot PCI est associé à un pont PCI qui possède plusieurs contrôleurs réseau enfants, la même valeur de la propriété ID_NET_NAME_SLOT peut être dérivée pour ces contrôleurs. Cela provoquerait un conflit de nommage si la propriété est sélectionnée comme nom de périphérique. Maintenant, nous détectons cette situation et ne produisons pas la propriété ID_NET_NAME_SLOT.

Ajouté dans la version 247.

v249

Les noms de slots PCI hotplug pour le pilote PCI s390 sont une représentation hexadécimale de l'attribut de périphérique function_id. Cet attribut est maintenant utilisé pour construire le ID_NET_NAME_SLOT. Avant cela, tous les noms de slots étaient analysés comme des nombres décimaux, ce qui pouvait soit entraîner une valeur incorrecte de la propriété ID_NET_NAME_SLOT, soit aucune valeur du tout.

Certaines implémentations de firmware et d'hyperviseur signalent des nombres déraisonnablement élevés pour l'index embarqué. Pour éviter la génération de noms d'interface embarqués invalides, les numéros d'index supérieurs à 16381 (2^14-1) étaient ignorés. Pour s390 PCI, les valeurs d'index jusqu'à 65535 (2^16-1) sont valides. Pour en tenir compte, la limite a été augmentée à 65535.

La règle NAME= de udev(7) remplace « : », « / » et « % » par un tiret bas (« _ ») et refuse les chaînes qui ne contiennent que des chiffres.

Ajouté dans la version 249.

v250

Ajout d'un schéma de nommage pour les interfaces « vif » Xen netfront basé sur le numéro VIF côté invité défini à partir de la configuration Xen (ou l'index de l'interface dans AWS EC2).

Ajouté dans la version 250.

v251

Depuis la version v247, nous ne définissons plus ID_NET_NAME_SLOT si nous détectons qu'un périphérique PCI associé à un slot est un pont PCI, car cela créerait un conflit de nommage lorsqu'il y a plus de périphériques enfants sur ce pont. Désormais, cela est assoupli et nous utiliserons les informations du slot pour générer le nom basé dessus, mais uniquement si le périphérique PCI a plusieurs fonctions. C'est sûr car un numéro de fonction distinct fait partie du nom du périphérique pour les périphériques multifonctions. Notez que cela est annulé dans v255. Voir ci-dessous.

Ajouté dans la version 251.

v252

Ajout d'un schéma de nommage pour les périphériques de plateforme avec des alias devicetree.

Ajouté dans la version 252.

v253

Définition de ID_NET_NAME_PATH pour les périphériques USB non connectés via un bus PCI.

Ajouté dans la version 253.

v254

Le nommage a été modifié pour les représentants de périphériques virtuels SR-IOV, optionnellement configurables au moment de la compilation. Le suffixe « rslot » a été ajouté pour différencier les représentants de périphériques virtuels SR-IOV attachés à une interface de périphérique physique unique. En raison d'une erreur, ce schéma n'était pas le schéma par défaut pour la version systemd 254.

Ajouté dans la version 255.

v255

Le nommage a été modifié pour les représentants de périphériques virtuels SR-IOV afin d'activer par défaut le changement introduit dans v254.

Si nous détectons qu'un périphérique PCI associé à un slot est un pont PCI, nous ne définissons plus ID_NET_NAME_SLOT, annulant un changement introduit dans v251.

Ajouté dans la version 255.

v257

Le numéro de slot PCI est maintenant lu à partir du fichier sysfs firmware_node/sun.

Le schéma de nommage basé sur les alias devicetree a été étendu pour prendre en charge les alias pour les interfaces individuelles de contrôleurs avec plusieurs ports.

Ajouté dans la version 257.

v258

Lorsque aucun renommage n'est demandé, la propriété ID_NET_NAME est maintenant équivalente à la propriété INTERFACE.

Ajouté dans la version 258.

Notez que latest peut être utilisé pour désigner le dernier schéma connu (par cette version particulière de systemd).

LIMITATION DE L'UTILISATION D'ATTRIBUTS SYSFS SPÉCIFIQUES

Lors de la création de noms pour les cartes réseau, certains schémas de nommage utilisent des données de sysfs fournies par le noyau. Cela signifie que bien qu'un schéma de nommage spécifique dans udev(7) soit choisi, le nom de la carte réseau peut toujours changer lorsqu'une nouvelle version du noyau ajoute un nouvel attribut sysfs. Par exemple, si le noyau commence à définir phys_port_name, udev ajoutera le suffixe « nphys_port_name » au nom du périphérique.

ID_NET_NAME_ALLOW=BOOL

Cette propriété udev définit une politique de repli pour la lecture d'un attribut sysfs. Si définie
Pour `0`, udev ne lira aucun attribut sysfs par défaut, sauf s'il est explicitement autorisé, voir ci-dessous. S'il est défini sur `1`, udev peut utiliser n'importe quel attribut sysfs sauf s'il est explicitement interdit. La valeur par défaut est `1`.

Ajouté dans la version 256.

ID_NET_NAME_ALLOW_sysfsattr=BOOL

Cette propriété udev indique explicitement si udev doit utiliser le sysfsattr spécifié lors de la composition du nom de l'appareil.

Ajouté dans la version 256.

Avec ces options, les utilisateurs peuvent définir une liste blanche ou une liste noire pour les attributs sysfs. Pour créer une liste blanche, l'utilisateur doit définir ID_NET_NAME_ALLOW=0 pour l'appareil, puis lister les attributs autorisés avec les options ID_NET_NAME_ALLOW_sysfsattr=1. En cas de liste noire, l'utilisateur doit fournir la liste des attributs refusés avec les options ID_NET_NAME_ALLOW_sysfsattr=0.

EXEMPLES

Exemple 1. Utilisation de udevadm test-builtin pour afficher les propriétés de l'appareil

$ udevadm test-builtin net_id /sys/class/net/enp0s31f6
...
Using default interface naming scheme 'v243'.
ID_NET_NAMING_SCHEME=v243
ID_NET_NAME_MAC=enx54ee75cb1dc0
ID_OUI_FROM_DATABASE=Wistron InfoComm(Kunshan)Co.,Ltd.
ID_NET_NAME_PATH=enp0s31f6
...

Exemple 2. Carte Ethernet PCI avec index de firmware « 1 »

ID_NET_NAME_ONBOARD=eno1
ID_NET_NAME_ONBOARD_LABEL=Ethernet Port 1

Exemple 3. Carte Ethernet PCI dans un slot avec numéro d'index de firmware

# /sys/devices/pci0000:00/0000:00:1c.3/0000:05:00.0/net/ens1
ID_NET_NAME_MAC=enx000000000466
ID_NET_NAME_PATH=enp5s0
ID_NET_NAME_SLOT=ens1

Exemple 4. Carte Ethernet PCI multifonction avec 2 ports

# /sys/devices/pci0000:00/0000:00:1c.0/0000:02:00.0/net/enp2s0f0
ID_NET_NAME_MAC=enx78e7d1ea46da
ID_NET_NAME_PATH=enp2s0f0
# /sys/devices/pci0000:00/0000:00:1c.0/0000:02:00.1/net/enp2s0f1
ID_NET_NAME_MAC=enx78e7d1ea46dc
ID_NET_NAME_PATH=enp2s0f1

Exemple 5. Carte WLAN PCI

# /sys/devices/pci0000:00/0000:00:1c.1/0000:03:00.0/net/wlp3s0
ID_NET_NAME_MAC=wlx0024d7e31130
ID_NET_NAME_PATH=wlp3s0

Exemple 6. Adaptateur hôte IB PCI avec 2 ports

# /sys/devices/pci0000:00/0000:00:03.0/0000:15:00.0/net/ibp21s0f0
ID_NET_NAME_PATH=ibp21s0f0
# /sys/devices/pci0000:00/0000:00:03.0/0000:15:00.1/net/ibp21s0f1
ID_NET_NAME_PATH=ibp21s0f1

Exemple 7. Modem 3G intégré USB

# /sys/devices/pci0000:00/0000:00:1d.0/usb2/2-1/2-1.4/2-1.4:1.6/net/wwp0s29u1u4i6
ID_NET_NAME_MAC=wwx028037ec0200
ID_NET_NAME_PATH=wwp0s29u1u4i6

Exemple 8. Téléphone Android USB

# /sys/devices/pci0000:00/0000:00:1d.0/usb2/2-1/2-1.2/2-1.2:1.0/net/enp0s29u1u2
ID_NET_NAME_MAC=enxd626b3450fb5
ID_NET_NAME_PATH=enp0s29u1u2

Exemple 9. Interface CCW groupée s390

# /sys/devices/css0/0.0.0007/0.0.f5f0/group_device/net/encf5f0
ID_NET_NAME_MAC=enx026d3c00000a
ID_NET_NAME_PATH=encf5f0

Exemple 10. Définir une liste blanche pour la lecture des attributs sysfs pour la nomination des cartes réseau

/etc/udev/hwdb.d/50-net-naming-allowlist.hwdb
net:naming:drvirtio_net:*
  ID_NET_NAME_ALLOW=0
  ID_NET_NAME_ALLOW_ACPI_INDEX=1
  ID_NET_NAME_ALLOW_ADDR_ASSIGN_TYPE=1
  ID_NET_NAME_ALLOW_ADDRESS=1
  ID_NET_NAME_ALLOW_ARI_ENABLED=1
  ID_NET_NAME_ALLOW_DEV_PORT=1
  ID_NET_NAME_ALLOW_FUNCTION_ID=1
  ID_NET_NAME_ALLOW_IFLINK=1
  ID_NET_NAME_ALLOW_INDEX=1
  ID_NET_NAME_ALLOW_LABEL=1
  ID_NET_NAME_ALLOW_PHYS_PORT_NAME=1
  ID_NET_NAME_ALLOW_TYPE=1

Exemple 11. Définir une liste noire afin que les attributs sysfs spécifiés soient ignorés

/etc/udev/hwdb.d/50-net-naming-denylist.hwdb
net:naming:drvirtio_net:*
  ID_NET_NAME_ALLOW=1
  ID_NET_NAME_ALLOW_DEV_PORT=0
  ID_NET_NAME_ALLOW_PHYS_PORT_NAME=0
