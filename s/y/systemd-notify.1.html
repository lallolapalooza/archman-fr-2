NOM

systemd-notify - Notifier le gestionnaire de service de l'achèvement du démarrage et d'autres changements d'état de démon

SYNTAXE

systemd-notify [OPTIONS...] [VARIABLE=VALEUR...]

systemd-notify --exec [OPTIONS...] [VARIABLE=VALEUR...] ; -- {CMDLINE...}

systemd-notify --fork [OPTIONS...] -- {CMDLINE...}

DESCRIPTION

systemd-notify peut être appelé par les scripts de service pour notifier le gestionnaire de service appelant des changements d'état. Il peut être utilisé pour envoyer des informations arbitraires, encodées dans une liste de chaînes semblable à un bloc d'environnement. Plus important encore, il peut être utilisé pour la notification d'achèvement du démarrage.

Il s'agit principalement d'un wrapper autour de sd_notify() et rend cette fonctionnalité disponible aux scripts shell. Pour plus de détails, voir sd_notify(3).

La ligne de commande peut contenir une liste de variables d'environnement à envoyer dans le cadre de la mise à jour de l'état.

Notez que systemd refusera la réception des mises à jour d'état de cette commande, sauf si NotifyAccess= est correctement défini pour l'unité de service à partir de laquelle cette commande est appelée. Voir systemd.service(5) pour les détails.

Notez que les notifications sd_notify() ne peuvent être correctement attribuées aux unités que si soit le processus d'envoi est toujours actif au moment où le gestionnaire de service traite le message, soit si le processus d'envoi est explicitement suivi en temps réel par le gestionnaire de service. Ce dernier cas se produit si le gestionnaire de service a initialement créé le processus, c'est-à-dire pour tous les processus qui correspondent à NotifyAccess=main ou NotifyAccess=exec. Inversement, si un processus auxiliaire de l'unité envoie un message sd_notify() et se termine immédiatement, le gestionnaire de service pourrait ne pas être en mesure d'attribuer correctement le message à l'unité, et donc l'ignorer, même si NotifyAccess=all est défini pour elle. Pour remédier à cela, systemd-notify attendra que le message de notification ait été traité par le gestionnaire de service. Lorsque --no-block est utilisé, cette synchronisation pour la réception des notifications est désactivée, et donc la course mentionnée ci-dessus peut se produire si le processus appelant n'est pas le gestionnaire de service ou n'est pas généré par le gestionnaire de service.

systemd-notify tentera d'abord d'invoquer sd_notify() en prétendant avoir le PID du processus parent de systemd-notify (c'est-à-dire le processus appelant). Cela ne réussira que si l'invocation est effectuée avec des privilèges suffisants. En cas d'échec, il se rabattra sur l'invocation sous son propre PID. Ce comportement est utile afin que, lorsque l'outil est invoqué à partir d'un script shell, le processus shell — et non le processus systemd-notify — apparaisse comme l'expéditeur du message, ce qui est à son tour utile si le processus shell est le processus principal d'un service, en raison des limitations de NotifyAccess=all. Utilisez l'option --pid= pour ajuster ce comportement.

OPTIONS

Les options suivantes sont comprises :

--ready

Notifier le gestionnaire de service appelant de l'achèvement du démarrage ou du rechargement de la configuration du service. Ceci est équivalent à systemd-notify READY=1. Pour plus de détails sur la sémantique de cette option, voir sd_notify(3).

--reloading

Notifier le gestionnaire de service appelant du début d'un cycle de rechargement de configuration. Ceci est équivalent à systemd-notify RELOADING=1 (mais définit implicitement également un champ MONOTONIC_USEC= comme requis pour les services Type=notify-reload, voir systemd.service(5) pour les détails). Pour plus de détails sur la sémantique de cette option, voir sd_notify(3).

Ajouté dans la version 253.

--stopping

Notifier le gestionnaire de service appelant du début de la phase d'arrêt du service. Ceci est équivalent à systemd-notify STOPPING=1. Pour plus de détails sur la sémantique de cette option, voir sd_notify(3).

Ajouté dans la version 253.

--pid=

Notifier le gestionnaire de service du PID principal du service. Prend un PID comme argument. Si l'argument est spécifié comme "auto" ou omis, le PID du processus qui a invoqué systemd-notify est utilisé, sauf s'il s'agit du gestionnaire de service. Si l'argument est spécifié comme "self", le PID de la commande systemd-notify elle-même est utilisé, et si "parent" est spécifié, le PID du processus appelant est utilisé — même s'il s'agit du gestionnaire de service. --pid=auto est équivalent à systemd-notify --pid=$PID. Pour plus de détails sur la sémantique de cette option, voir sd_notify(3).

systemd-notify tentera d'abord d'invoquer sd_notify() en prétendant avoir le PID spécifié avec --pid=. Cela ne réussira que si l'invocation est effectuée avec des privilèges suffisants. En cas d'échec, il se rabattra sur l'invocation sous son propre PID. Effectivement, cela signifie qu'une invocation privilégiée de systemd-notify --pid= peut contourner les restrictions NotifyAccess=main ou NotifyAccess=exec appliquées à un service.

Si ce commutateur est utilisé dans une invocation non privilégiée de systemd-notify à partir d'un processus qui doit devenir le nouveau processus principal d'un service — et qui n'est pas le processus créé par le gestionnaire de service (ou le processus principal actuel) —, alors il est essentiel de définir NotifyAccess=all dans le fichier d'unité de service, sinon la notification sera ignorée pour des raisons de sécurité. Voir systemd.service(5) pour les détails.

--uid=USER

Définit l'ID utilisateur à partir duquel envoyer la notification. Prend un nom d'utilisateur UNIX ou un UID numérique. Lorsqu'il est spécifié, le message de notification sera envoyé avec l'UID spécifié comme expéditeur, à la place de l'utilisateur sous lequel la commande a été invoquée. Cette option nécessite des privilèges suffisants pour pouvoir manipuler l'identité utilisateur du processus.

Ajouté dans la version 237.

--status=

Envoie une chaîne d'état lisible par l'homme et de forme libre pour le démon au gestionnaire de service. Cette option prend la chaîne d'état comme argument. Ceci est équivalent à systemd-notify STATUS=.... Pour plus de détails sur la sémantique de cette option, voir sd_notify(3). Ces informations sont affichées dans la sortie status de systemctl(1), entre autres.

--booted

Retourne 0 si le système a été démarré avec systemd, non nul sinon. Si cette option est passée, aucun message n'est envoyé. Cette option n'est donc pas liée aux autres options. Pour plus de détails sur la sémantique de cette option, voir sd_booted(3). Une autre façon de vérifier cet état est d'appeler systemctl(1) avec la commande is-system-running. Elle retournera "offline" si le système n'a pas été démarré avec systemd.

--no-block

Ne pas attendre de manière synchrone la fin de l'opération demandée. L'utilisation de cette option est uniquement recommandée lorsque systemd-notify est généré par le gestionnaire de service, ou lorsque le processus appelant est directement généré par le gestionnaire de service et dispose de privilèges suffisants pour permettre à systemd-notify d'envoyer la notification en son nom. L'envoi de notifications avec cette option définie est sujet aux conditions de concurrence dans tous les autres cas.

Ajouté dans la version 246.

--exec

Si spécifié, systemd-notify exécutera une autre ligne de commande après avoir terminé son opération, remplaçant son propre processus. Si utilisé, la liste des affectations à inclure dans le message envoyé doit être suivie d'un caractère ";" (comme argument séparé), suivi de la ligne de commande à exécuter. Cela permet le "chaînage" de commandes, c'est-à-dire l'émission d'une opération, suivie immédiatement d'une autre, sans changer de PID.

Notez que de nombreux shells interprètent ";" comme leur propre séparateur de lignes de commande, donc lorsque systemd-notify est invoqué à partir d'un shell, le point-virgule doit généralement être échappé sous la forme "\;".

Ajouté dans la version 254.

Cette option peut être utilisée plusieurs fois pour transmettre plusieurs descripteurs de fichiers dans un seul message de notification.

Pour utiliser cette fonctionnalité depuis un shell bash(1), utilisez une expression comme suit :

Ajouté dans la version 254.

--fdname=

Définit un nom à attribuer aux descripteurs de fichiers passés via --fd= (voir ci-dessus). Cela contrôle le champ "FDNAME=". Ce paramètre ne peut être spécifié qu'une seule fois et s'applique à tous les descripteurs de fichiers passés. Appelez cet outil plusieurs fois si des descripteurs de fichiers avec différents noms de descripteurs de fichiers doivent être soumis.

Ajouté dans la version 254.

--fork

Au lieu d'envoyer un message de notification, lance une ligne de commande et attend qu'un message "READY=1" soit reçu de celle-ci. En d'autres termes : cela fait de systemd-notify le récepteur des messages de notification au lieu de l'expéditeur, inversant les rôles. Ceci est utile pour lancer rapidement un processus qui implémente le protocole sd_notify() depuis un script shell. La ligne de commande invoquée aura l'entrée standard et la sortie standard connectées à /dev/null, mais la sortie d'erreur sera héritée du processus appelant. L'identifiant numérique du processus est écrit dans la sortie standard par systemd-notify (sauf si --quiet est spécifié), qui peut être utilisé pour terminer ultérieurement le processus lancé.

Notez que les processus lancés de cette manière resteront probablement en cours d'exécution après le retour de systemd-notify, ce qui entraînera leur réparentage au processus de détection de processus le plus proche, c'est-à-dire généralement le gestionnaire de services par utilisateur ou système.

Notez que cette option ne doit pas être utilisée pour invoquer des services complets ad hoc, utilisez systemd-run pour cela.

Notez également que lorsqu'il est invoqué avec ce commutateur, systemd-notify se terminera avec succès dans deux conditions distinctes :

1.systemd-notify a reçu une notification "READY=1" de l'enfant qu'il vient de lancer.
2.Le processus enfant s'est terminé proprement (avec un code de sortie nul) avant d'envoyer "READY=1".

Exemple d'utilisation :

# PID=$(systemd-notify --fork -- mycommand)
...
kill "$PID"
unset PID

Ajouté dans la version 258.

--quiet, -q

Désactive la sortie de l'identifiant numérique du processus lorsque --fork est utilisé.

Ajouté dans la version 258.

-h, --help

Imprime un bref message d'aide et quitte.

--version

Imprime une courte chaîne de version et quitte.

STATUT DE SORTIE

En cas de succès, 0 est retourné, sinon un code d'échec non nul.

EXEMPLE

Exemple 1. Notification de démarrage et mises à jour de statut

Un simple démon shell qui envoie des notifications de démarrage après avoir mis en place son canal de communication. Pendant son exécution, il envoie d'autres mises à jour de statut au système d'init :

#!/bin/sh
mkfifo /tmp/waldo
systemd-notify --ready --status="En attente de données..."
while : ; do
        read -r a < /tmp/waldo
        systemd-notify --status="Traitement de $a"
        # Faire quelque chose avec $a ...
        systemd-notify --status="En attente de données..."
done
