NOM

systemd-pcrlock, systemd-pcrlock-file-system.service, systemd-pcrlock-firmware-code.service, systemd-pcrlock-firmware-config.service, systemd-pcrlock-machine-id.service, systemd-pcrlock-make-policy.service, systemd-pcrlock-secureboot-authority.service, systemd-pcrlock-secureboot-policy.service - Analyser et prédire les états des PCR du TPM2 et générer une politique d'accès à partir de la prédiction

SYNTAXE

/usr/lib/systemd/systemd-pcrlock [OPTIONS...]

DESCRIPTION

Note : cette commande est actuellement expérimentale. Bien qu'elle soit susceptible de devenir un composant régulier de systemd, son comportement et son interface peuvent encore changer.

systemd-pcrlock est un outil qui peut être utilisé pour analyser et prédire les mesures des PCR du TPM2, et générer des politiques d'accès au TPM2 à partir de la prédiction qu'il stocke dans un index NV du TPM2 (c'est-à-dire dans la mémoire non volatile du TPM2). Ceci peut ensuite être utilisé pour restreindre l'accès aux objets du TPM2 (tels que les clés de chiffrement de disque) aux démarrages du système n'utilisant que des composants spécifiques et approuvés.

systemd-pcrlock utilise comme entrée pour son analyse et sa prédiction :

•Le journal des événements TPM2 du firmware UEFI (c'est-à-dire /sys/kernel/security/tpm0/binary_bios_measurements) du démarrage actuel.
•Le journal des événements TPM2 de l'espace utilisateur (c'est-à-dire /run/log/systemd/tpm2-measure.log) du démarrage actuel.
•L'état actuel des PCR de la puce TPM2.
•Des fichiers de définition de composants de démarrage (*.pcrlock et *.pcrlock.d/*.pcrlock, voir systemd.pcrlock(5)) qui définissent chacun les mesures attendues pour un composant du processus de démarrage, autorisant des variantes alternatives pour chacun. (Les variantes peuvent être utilisées pour bénir plusieurs versions du noyau ou plusieurs versions du chargeur de démarrage en même temps.)

Il utilise ces entrées pour générer un journal d'événements combiné, le validant par rapport aux états des PCR. Il tente ensuite de reconnaître les enregistrements du journal d'événements et les fait correspondre aux composants définis. Pour chaque PCR pour laquelle cela peut être fait de manière exhaustive (c'est-à-dire où tous les enregistrements listés et tous les composants définis ont été mis en correspondance), cela peut ensuite être utilisé pour prédire les futures mesures des PCR, en tenant compte des variantes alternatives définies pour chaque composant. Cette prédiction peut ensuite être convertie en une politique d'accès TPM2 (composée d'éléments PolicyPCR et PolicyOR du TPM2), qui est ensuite stockée dans un index NV du TPM2. Ceci peut être utilisé pour verrouiller des secrets (tels que des clés de chiffrement de disque) à ces politiques (via une politique PolicyAuthorizeNV du TPM2).

Utilisez des outils tels que systemd-cryptenroll(1) ou systemd-repart(8) pour lier le chiffrement de disque à une telle politique TPM2 systemd-pcrlock. Spécifiquement, voir les commutateurs --tpm2-pcrlock= de ces outils.

La logique de politique d'accès nécessite un périphérique TPM2 qui implémente la commande "PolicyAuthorizeNV", c'est-à-dire qui implémente la version 1.38 ou plus récente de TPM 2.0.

COMMANDES

Les commandes suivantes sont comprises :

log

Lit le journal d'événements combiné du TPM2, le valide, le fait correspondre aux valeurs actuelles des PCR, et affiche les deux sous forme tabulaire. Combinez avec --json= pour générer une sortie au format JSON.

Ajouté dans la version 255.

cel

Lit le journal d'événements combiné du TPM2 et l'écrit sur STDOUT au format TCG Canonical Event Log Format (CEL-JSON)[1].

Ajouté dans la version 255.

list-components

Affiche une liste des définitions de composants et de leurs variantes, c'est-à-dire les fichiers *.pcrlock découverts dans /var/lib/pcrlock.d/, /usr/lib/pcrlock.d/, et les autres répertoires pris en charge. Voir systemd.pcrlock(5) pour les détails sur ces fichiers et la liste complète des répertoires recherchés.

Ajouté dans la version 255.

predict

Prédit l'état des PCR lors des futurs démarrages. Cela analysera le journal d'événements du TPM2 comme décrit ci-dessus, reconnaîtra les composants et générera ensuite toutes les valeurs de PCR résultantes possibles pour toutes les combinaisons de variantes de composants. Notez qu'aucune prédiction n'est faite pour les PCR dont la valeur ne correspond pas aux enregistrements du journal d'événements, pour lesquelles des mesures non reconnues sont découvertes, ou pour lesquelles des composants sont définis qui ne peuvent pas être trouvés dans le journal d'événements. Ceci est une mesure de sécurité pour s'assurer que toute politique d'accès générée peut être remplie correctement lors des démarrages actuels et futurs.

Ajouté dans la version 255.

make-policy

Prédit l'état des PCR pour les futurs démarrages, un peu comme la commande predict ci-dessus. Elle utilise ensuite ces données pour générer une politique d'accès TPM2 qu'elle stocke dans un index NV du TPM2. La prédiction et les informations sur le TPM2 utilisé et son index NV sont écrites dans /var/lib/systemd/pcrlock.json.

L'index NV est alloué lors de la première invocation, et mis à jour lors des invocations suivantes.

Le contenu de l'index NV peut être modifié (et donc la politique qui y est stockée mise à jour) en fournissant un code PIN d'accès. Ce code PIN est normalement généré automatiquement et stocké sous forme chiffrée (avec une politique d'accès qui le lie à l'index NV lui-même) dans le fichier de politique JSON susmentionné. Ce code PIN peut être choisi par l'utilisateur, via le commutateur --recovery-pin=. S'il est spécifié, il peut être utilisé comme chemin d'accès alternatif pour mettre à jour la politique.

Si la nouvelle prédiction correspond à l'ancienne, cette commande se termine rapidement et n'exécute aucune autre opération. (Sauf si --force est spécifié, voir ci-dessous.)

À partir de la v256, une copie du fichier de politique /var/lib/systemd/pcrlock.json est encodée dans une credential (voir systemd-creds(1) pour les détails) et écrite sur la partition système EFI ou la partition XBOOTLDR, dans le sous-répertoire /loader/credentials/. Là, elle est récupérée au démarrage par systemd-stub(7) et passée à l'initrd appelé, où elle peut être utilisée pour déverrouiller le système de fichiers racine (qui contient typiquement /var/, où se trouve la copie principale de la politique, qui ne peut donc pas être utilisée pour déverrouiller le système de fichiers racine). Le fichier credential est nommé d'après le jeton d'entrée de démarrage de l'installation (voir bootctl(1)), qui est configurable via le commutateur --entry-token=, voir ci-dessous.

Ajouté dans la version 255.

remove-policy

Supprime une politique précédemment générée. Supprime le fichier /var/lib/systemd/pcrlock.json et désalloue l'index NV.

Ajouté dans la version 255.

is-supported

Vérifie si le TPM2 local prend en charge toutes les fonctionnalités nécessaires au bon fonctionnement de systemd-pcrlock. Effectue des tests similaires à systemd-analyze has-tpm2, mais vérifie également la prise en charge des opérations TPM2 requises par systemd-pcrlock. Affiche l'une des valeurs suivantes : "no", "partial" (si certaines parties de la prise en charge du TPM2 sont disponibles matériellement, via le firmware ou le système d'exploitation, mais pas complètement), "obsolete" (si la prise en charge du TPM2 est disponible matériellement, via le firmware et le système d'exploitation, mais que les opérations requises pour systemd-pcrlock sont manquantes), "yes". Retourne un code de sortie de zéro si la prise en charge complète est disponible, sinon un code non nul.

Si combiné avec --quiet, supprime l'affichage de la chaîne.

Actuellement, vérifie la prise en charge de la commande TPM2 PolicyAuthorizeNV, ainsi que la prise en charge de l'algorithme de hachage SHA-256.

Ajouté dans la version 258.

lock-firmware-code, unlock-firmware-code

Génère/supprime des fichiers .pcrlock basés sur le journal d'événements TPM2 du démarrage actuel couvrant tous les enregistrements pour les PCR 0 ("platform-code") et 2 ("external-code").

Cette opération permet de verrouiller le processus de démarrage sur la version actuelle du firmware du système et de ses cartes d'extension. Cette opération ne devrait être utilisée que si le fournisseur du système ne fournit pas de données pcrlock appropriées à l'avance.

Notez que ces données ne correspondent qu'à la version actuelle du firmware. Cela garantit qu'une politique d'accès gérée par systemd-pcrlock est automatiquement verrouillée sur la nouvelle version du firmware chaque fois que la politique ha

lock-firmware-config, unlock-firmware-config

Ceci est similaire à lock-firmware-code/unlock-firmware-code mais verrouille la configuration du firmware, c'est-à-dire les PCR 1 (« platform-config ») et 3 (« external-config »).

Cette fonctionnalité doit être utilisée avec précaution car dans la plupart des scénarios, un petit changement de configuration du firmware ne devrait pas invalider les politiques d'accès aux objets TPM2. Notez également que certains systèmes mesurent des informations instables et imprévisibles (par exemple, les tensions actuelles du CPU, les températures, dans le cadre des données SMBIOS) pour ces PCR, ce qui signifie que cette forme de verrouillage ne peut pas être utilisée de manière fiable sur de tels systèmes. Utilisez cette fonctionnalité uniquement si le système et le matériel sont bien connus et ne souffrent pas de ces limitations, par exemple dans les environnements virtualisés.

Utilisez unlock-firmware-config avant d'apporter des modifications à la configuration du firmware. Si l'unité systemd-pcrlock-firmware-config.service est activée, elle générera automatiquement un fichier pcrlock à partir des nouvelles mesures.

Cela écrit/supprime les fichiers /var/lib/pcrlock.d/250-firmware-config-early.pcrlock.d/generated.pcrlock et /var/lib/pcrlock.d/550-firmware-config-late.pcrlock.d/generated.pcrlock.

Génère/supprime un fichier .pcrlock basé sur la politique SecureBoot actuellement appliquée. Ceci examine les variables EFI SecureBoot, PK, KEK, db, dbx, dbt, dbr et prédit leurs mesures pour la PCR 7 (« secure-boot-policy ») au prochain démarrage.

Utilisez unlock-firmware-config avant d'appliquer les mises à jour de la politique SecureBoot. Si l'unité systemd-pcrlock-secureboot-policy.service est activée, elle générera automatiquement un fichier pcrlock à partir de la politique découverte.

Cela écrit/supprime le fichier /var/lib/pcrlock.d/230-secureboot-policy.pcrlock.d/generated.pcrlock.

Génère/supprime un fichier .pcrlock basé sur les autorités SecureBoot utilisées pour valider le chemin de démarrage. Les autorités SecureBoot sont les entrées spécifiques de la base de données SecureBoot qui ont été utilisées pour valider les binaires PE UEFI exécutés au démarrage. Ceci examine le journal d'événements du démarrage actuel, et utilise les mesures pertinentes sur la PCR 7 (« secure-boot-policy »).

Cela écrit/supprime le fichier /var/lib/pcrlock.d/620-secureboot-authority.pcrlock.d/generated.pcrlock.

Ceci verrouille l'état du partitionnement du disque du support démarré, que le firmware mesure dans la PCR 5 (« boot-loader-config »).

OPTIONS

Les options suivantes sont comprises :

--raw-description

Lors de l'affichage du journal d'événements TPM2, n'essayez pas de décoder les enregistrements pour fournir une chaîne de description conviviale du journal d'événements. Au lieu de cela, affichez les données de charge utile binaire sous forme échappée.

Ajouté dans la version 255.

--pcr=

Spécifie le numéro de la PCR à utiliser. Peut être spécifié plusieurs fois pour sélectionner plusieurs PCR.

Ceci est utilisé par lock-raw et lock-pe pour sélectionner la PCR contre laquelle verrouiller.

Si utilisé avec predict et make-policy, cela remplacera les PCR à inclure dans la prédiction et la politique. Si non spécifié, cela utilise par défaut les PCR 0-5, 7, 11-15. Notez que ces commandes n'incluront aucune PCR dans la prédiction/politique (même si elles sont spécifiées explicitement) s'il existe des mesures dans le journal d'événements qui ne correspondent pas à la valeur actuelle de la PCR, ou s'il existe des mesures non reconnues dans le journal d'événements, ou si des composants définissent des mesures non vues dans le journal d'événements.

Ajouté dans la version 255.

--nv-index=

Spécifie l'index NV où stocker la politique. Pris en compte par make-policy. Si non spécifié, la commande choisira automatiquement un index NV libre.

Ajouté dans la version 255.

--components=

Prend un chemin pour lire les fichiers *.pcrlock et *.pcrlock.d/*.pcrlock. Peut être utilisé plusieurs fois pour spécifier plusieurs répertoires. S'il n'est pas spécifié, il utilise par défaut /etc/pcrlock.d/, /run/pcrlock.d/, /var/lib/pcrlock.d/, /usr/local/lib/pcrlock.d/, /usr/lib/pcrlock.d/.

Ajouté dans la version 255.

--location=

Prend soit une chaîne, soit une paire de chaînes séparées par des deux-points. Configure jusqu'à quel point dans la liste triée des composants définis pour analyser/prédire les PCR. Typiquement, l'outil systemd-pcrlock est invoqué à partir d'un système entièrement démarré après le démarrage et avant l'arrêt. Cela signifie que divers composants définis pour l'arrêt n'ont pas encore été mesurés et ne doivent pas être recherchés. Cette option permet de restreindre les composants qui sont pris en compte pour l'analyse (en ne prenant en compte que les composants avant un certain point, en ignorant ceux après). La chaîne attendue est ordonnée par rapport aux noms de fichiers des composants définis. Tous les composants avec un nom lexicographiquement plus tardif sont ignorés. Cette logique s'applique aux verbes log, predict et make-policy. Si une paire de chaînes séparées par des deux-points est spécifiée, elle sélectionne les phases du démarrage à inclure dans la prédiction/politique. La première chaîne définit où la première prédiction doit être faite, et la seconde chaîne définit où la dernière prédiction doit être faite. Toutes ces prédictions sont ensuite combinées en un ensemble.

Si utilisé avec list-components, la plage de localisation sélectionnée sera mise en évidence dans la liste des composants.

Par défaut, il vaut "760-:940-", ce qui signifie que les politiques générées par défaut couvriront essentiellement tout le temps d'exécution de l'espace utilisateur du système d'exploitation, de l'initrd (car "760-" suit de près 750-enter-initrd.pcrlock) jusqu'au temps d'exécution principal du système (inclus) (car "940-" est suivi de près par 950-shutdown.pcrlock). Voir systemd.pcrlock(5) pour une liste complète des composants bien connus, qui illustrent où cette plage est placée par défaut.

Ajouté dans la version 255.

--recovery-pin=

Prend l'une des valeurs suivantes : « hide », « show » ou « query ». Par défaut, « hide ». Pris en compte par make-policy. Si « query », demandera à l'utilisateur un code PIN pour déverrouiller systemd-pcrlock-machine-id.service(8) — systemd manual pages

NAME

systemd-pcrlock-machine-id.service, systemd-pcrlock-machine-id - manage boot integrity measurements

SYNOPSIS

 systemd-pcrlock-machine-id.service

DESCRIPTION

The systemd-pcrlock-machine-id.service is a service that is run early in the boot process. It is used to verify the integrity of the machine identity (as stored in /etc/machine-id, /var/lib/dbus/machine-id, or /run/dbus/machine-id) using systemd-pcrlock(1), and to lock it in a TPM2 NV index.

The service reads the machine-id and uses it to construct the command line arguments for systemd-pcrlock(1). The integrity measurements (PCR values) are stored in a TPM2 NV index that is associated with the machine-id. The same index is used to store the boot entry token, which is used to unlock write access to the NV index.

If the integrity check fails, the service will fail to start, and the system may refuse to boot further. This is intended to prevent booting on a system where the machine identity has been tampered with.

The service relies on the presence of a valid TPM2 device and a correctly configured TPM2 NV index. If these are not present or configured correctly, the service may fail to start.

For more details on the underlying concepts and commands, refer to systemd-pcrlock(1) and systemd.pcrlock(5).

COMMANDS

The systemd-pcrlock-machine-id.service service itself does not expose any commands. It is intended to be run by the systemd init system. However, it utilizes the systemd-pcrlock(1) utility, which has the following commands:

Commands:

make-policy
Creates a new policy for a TPM2 NV index. If a policy already exists, it will be overwritten.
set-policy
Sets a policy for a TPM2 NV index. The policy must be provided as a file path.
get-policy
Retrieves the policy for a TPM2 NV index.
lock
Locks a TPM2 NV index. This command takes PCR values as input and stores them in the TPM2 NV index. It may require a PIN to unlock write access.
unlock
Unlocks a TPM2 NV index. This command may require a PIN or a recovery PIN to regain write access.
is-supported
Checks if the system supports TPM2 PCR locking.

OPTIONS

The systemd-pcrlock-machine-id.service service does not accept command line options. Its behavior is configured through systemd unit file settings and potentially through files specified by systemd.pcrlock(5).

However, the underlying systemd-pcrlock(1) utility accepts the following options when invoked directly:

--pin=
Specifies the PIN to use for the TPM2 NV index. If no policy was created before, this PIN is used to protect the newly allocated NV index. If a policy has been created before, the PIN is used to unlock write access to the NV index. If either "hide" or "show" is used, a PIN is automatically generated, and — only in case of "show" — displayed on screen. Regardless if user supplied or automatically generated, it is stored in encrypted form in the policy metadata file. The recovery PIN may be used to regain write access to an NV index in case the access policy became out of date.
--pcrlock=
Takes a file system path as argument. If specified, configures where to write the generated pcrlock data to. Honoured by the various lock- commands. If not specified, a default path is generally used, as documented above.
--policy=
Takes a file system path as argument. If specified, configures where to write pcrlock policy metadata to. If not specified, defaults to /var/lib/systemd/pcrlock.json.
--force
If specified with make-policy, the predicted policy will be written to the NV index even if it is detected to be the same as the previously stored one.
--entry-token=
Sets the boot entry token to use for the file name for the pcrlock policy credential in the EFI System Partition or XBOOTLDR partition. See the bootctl(1) option of the same regarding expected values. This switch has an effect on the make-policy command only.
--quiet
If specified suppresses output when invoked for is-supported.
--json=MODE
Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).
--no-pager
Do not pipe output into a pager.
-h, --help
Print a short help text and exit.
--version
Print a short version string and exit.

EXIT STATUS

On success, 0 is returned, a non-zero failure code otherwise.
