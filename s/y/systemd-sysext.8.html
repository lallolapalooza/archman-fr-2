NOM

systemd-sysext, systemd-sysext.service, systemd-sysext-initrd.service, systemd-confext, systemd-confext.service, systemd-confext-initrd.service - Active les images d'extensions système

SYNOPIS

systemd-sysext [OPTIONS...] COMMANDE

systemd-sysext.service

systemd-confext [OPTIONS...] COMMANDE

systemd-confext.service

DESCRIPTION

systemd-sysext active/désactive les images d'extensions système. Les images d'extensions système peuvent - dynamiquement au moment de l'exécution - étendre les hiérarchies des répertoires /usr/ et /opt/ avec des fichiers supplémentaires. Ceci est particulièrement utile sur des images système immuables où une hiérarchie /usr/ et/ou /opt/ résidant sur un système de fichiers en lecture seule doit être étendue temporairement au moment de l'exécution sans effectuer de modifications persistantes.

Les images d'extensions système doivent contenir des fichiers et des répertoires de manière similaire à un système d'exploitation normal. Lorsqu'une ou plusieurs images d'extensions système sont activées, leurs hiérarchies /usr/ et /opt/ sont combinées via "overlayfs" avec les mêmes hiérarchies du système hôte, et les /usr/ et /opt/ de l'hôte sont remontés par-dessus ("fusion"). Lorsqu'elles sont désactivées, le point de montage est démonté - révélant à nouveau la version hôte originale non modifiée de la hiérarchie ("démontage"). La fusion rend ainsi les ressources de l'extension soudainement accessibles sous les hiérarchies /usr/ et /opt/ comme si elles étaient incluses dans l'image du système de base elle-même. Le démontage les fait disparaître à nouveau, ne laissant en place que les fichiers qui ont été expédiés avec l'image du système de base elle-même.

Les fichiers et répertoires contenus dans les images d'extension en dehors des hiérarchies /usr/ et /opt/ ne sont *pas* fusionnés, et n'ont donc aucun effet lorsqu'ils sont inclus dans une image d'extension système. En particulier, les fichiers dans /etc/ et /var/ inclus dans une image d'extension système n'apparaîtront *pas* dans les hiérarchies respectives après activation.

Les images d'extensions système sont strictement en lecture seule par défaut. Sur les systèmes de fichiers hôtes modifiables, les hiérarchies /usr/ et /opt/ deviennent en lecture seule pendant que les extensions sont fusionnées, à moins que la mutabilité ne soit activée. La mutabilité peut être activée via l'option --mutable= ; voir "Mutability" ci-dessous pour plus d'informations.

Les extensions système sont censées être purement additives, c'est-à-dire qu'elles doivent inclure uniquement des fichiers qui n'existent pas dans l'image du système de base sous-jacent. Cependant, le mécanisme sous-jacent (overlayfs) permet également de surcharger ou de supprimer des fichiers, mais il est recommandé de ne pas en faire usage.

Les images d'extensions système peuvent être fournies dans les formats suivants :

1. Répertoires simples ou sous-volumes btrfs contenant l'arborescence du système
2. Images disque avec une étiquette de disque GPT, suivant la Spécification des partitions découvrables[1]
3. Images disque sans table de partitions, avec un système de fichiers Linux nu (par exemple, erofs, squashfs ou ext4)

Ces formats d'image sont les mêmes que ceux que systemd-nspawn(1) supporte via ses options --directory=/--image= et ceux que le gestionnaire de services supporte via RootDirectory=/RootImage=. Similairement à eux, ils peuvent éventuellement transporter des informations d'authentification Verity.

Les extensions système sont recherchées dans les répertoires /etc/extensions/, /run/extensions/ et /var/lib/extensions/. Les deux premiers répertoires listés ne conviennent pas pour transporter de grandes images binaires, mais sont néanmoins utiles pour y transporter des liens symboliques. L'emplacement principal pour installer les extensions système est /var/lib/extensions/. Tout répertoire trouvé dans ces répertoires de recherche est considéré comme une image d'extension basée sur un répertoire ; tout fichier avec le suffixe .raw est considéré comme une image d'extension basée sur une image disque. Lors de l'invocation dans l'initrd, le répertoire supplémentaire /.extra/sysext/ est inclus dans les répertoires où les images d'extensions sont recherchées. Notez cependant que, par défaut, une politique d'image plus stricte s'applique aux images trouvées là, voir ci-dessous. Ce répertoire est peuplé par systemd-stub(7) avec les images d'extensions trouvées dans la partition système EFI du système.

Pendant le démarrage, les images d'extensions système sont activées automatiquement, si systemd-sysext.service est activé. Notez que ce service ne s'exécute qu'après que les systèmes de fichiers sous-jacents où les extensions système peuvent se trouver ont été montés. Cela signifie qu'ils ne conviennent pas pour expédier des ressources traitées par des sous-systèmes fonctionnant au plus tôt du démarrage. Spécifiquement, les images d'extensions système ne conviennent pas pour expédier des services système ou des définitions systemd-sysusers(8). Voir la page Services portables[2] pour un mécanisme simple pour expédier des services système dans des images disque, d'une manière similaire aux extensions système. Notez la différence d'isolation entre ces deux mécanismes : tandis que les extensions système étendent directement l'image du système sous-jacent avec des fichiers supplémentaires qui apparaissent d'une manière très similaire comme s'ils avaient été expédiés dans l'image du système elle-même et n'impliquent donc aucune isolation de sécurité, les services portables impliquent une mise en bac à sable au niveau du service d'une manière ou d'une autre. Le service systemd-sysext.service est garanti de terminer son démarrage avant que basic.target ne soit atteint ; c'est-à-dire au moment où les services réguliers s'initialisent (ceux qui n'utilisent pas DefaultDependencies=no), les fichiers et répertoires fournis par les extensions système sont disponibles dans /usr/ et /opt/ et peuvent être accédés.

Notez qu'il n'y a pas de concept d'activation/désactivation des images d'extensions système installées : toutes les images d'extensions installées sont automatiquement activées au démarrage. Cependant, vous pouvez placer un répertoire vide nommé comme l'extension (pas .raw) dans /etc/extensions/ pour "masquer" une extension portant le même nom dans un dossier système de moindre priorité.

Un mécanisme simple de compatibilité de version est appliqué : une image d'extension système doit porter un fichier /usr/lib/extension-release.d/extension-release.NOM, qui doit correspondre à son nom d'image, et qui est comparé au fichier os-release de l'hôte : les champs ID= contenus doivent correspondre à moins que "_any" ne soit défini pour l'extension. Si l'extension ID= n'est pas "_any", le champ SYSEXT_LEVEL= (s'il est défini) doit correspondre. Si ce dernier n'est pas défini, le champ VERSION_ID= doit plutôt correspondre. Si l'extension définit le champ ARCHITECTURE= et que la valeur n'est pas "_any", elle doit correspondre à l'architecture du noyau rapportée par uname(2) mais les identifiants d'architecture utilisés sont les mêmes que pour ConditionArchitecture= décrits dans systemd.unit(5). EXTENSION_RELOAD_MANAGER= peut être défini sur 1 si l'extension nécessite un rechargement du gestionnaire de services après l'application de l'extension. Notez que pour les raisons mentionnées précédemment, les Services portables[2] restent le moyen recommandé pour expédier les services système. Les extensions système ne doivent pas expédier un fichier /usr/lib/os-release (car cela serait fusionné dans l'arborescence /usr/ de l'hôte, remplaçant les données de version de l'OS hôte, ce qui n'est pas souhaitable). Le fichier extension-release suit le même format et la même sémantique, et contient le même contenu que le fichier os-release de l'OS, mais il décrit les ressources contenues dans l'image d'extension.

Le concept systemd-confext suit le même principe que la fonctionnalité systemd-sysext(8) mais au lieu de travailler sur /usr et /opt, confext étendra seulement /etc. Les fichiers et répertoires contenus dans les images confext en dehors de la hiérarchie /etc/ ne sont *pas* fusionnés, et n'ont donc aucun effet lorsqu'ils sont inclus dans l'image. Les formats pour ces images sont les mêmes que pour les images sysext. La hiérarchie fusionnée sera montée avec "nosuid" et (sauf si désactivé via --noexec=false) "noexec".

Tout comme les sysexts, les confexts sont strictement en lecture seule par défaut. La fusion de confexts sur des systèmes de fichiers hôtes modifiables résultera en un /etc/ en lecture seule. Comme pour les sysexts, la mutabilité peut être activée via l'option --mutable=. Référez-vous à "Mutability" ci-dessous pour plus d'informations.

Les confexts sont recherchés dans les répertoires /run/confexts/, /var/lib/confexts/, /usr/lib/confexts/ et /usr/local/lib/confexts/. Le premier répertoire listé ne convient pas pour transporter de grandes images binaires, mais est néanmoins utile pour y transporter des liens symboliques. L'emplacement principal pour installer les extensions de configuration est /var/lib/confexts/. Tout répertoire trouvé dans ces répertoires de recherche est considéré comme une image de confext basée sur un répertoire ; tout fichier avec le suffixe .raw est considéré comme une image de confext basée sur une image disque.

Encore une fois, tout comme les images sysext, les images confext contiendront un /etc/extensio

NOM

systemd-sysext – Gestionnaire d'images d'extension système et de configuration

SYNOPSIS

systemd-sysext --root=ROOT COMMAND

systemd-sysext COMMAND

DESCRIPTION

Le système systemd-sysext (system extension) permet à un administrateur système de déployer des ressources supplémentaires dans une image système de base immuable, en particulier pour les systèmes construits à l'aide de technologies d'images disque comme systemd-image-builder(8). Il se compose de deux concepts principaux :

• Les images d'extension système (sysext) : Ces images sont conçues pour étendre les hiérarchies /usr/ et /opt/ du système hôte. Elles sont particulièrement utiles pour ajouter des outils facultatifs de débogage ou de développement qui ne sont pas inclus dans l'image de base immuable.

• Les images d'extension de configuration (confext) : Celles-ci sont destinées à modifier ou à étendre la hiérarchie /etc/ du système hôte. Elles permettent de mettre à jour la configuration sans reconstruire ou redéployer l'ensemble du système.

Les deux types d'extensions utilisent des images disque, généralement au format tar.gz, qui sont placées dans le répertoire /var/lib/extensions/. Ces images doivent être nommées selon un schéma spécifique pour être reconnues par systemd-sysext. Pour les images sysext, le nom de fichier doit commencer par app- suivi du nom de l'image et se terminer par .raw.tar.gz (ou une autre extension suffixée par .tar.gz). Pour les images confext, le nom de fichier doit commencer par etc- suivi du nom de la configuration et se terminer par .raw.tar.gz.

Lorsqu'une extension est activée (fusionnée), son contenu est superposé aux hiérarchies correspondantes du système hôte à l'aide d'un système de fichiers overlayfs. Cela permet de conserver l'immuabilité de l'image de base tout en offrant la flexibilité d'ajouter ou de modifier des fichiers. Le retrait d'une extension (démontée) supprime simplement la superposition overlayfs, restaurant ainsi l'état d'origine du système hôte.

Le système vérifie les métadonnées contenues dans les images d'extension pour s'assurer de leur compatibilité avec le système hôte. Les informations de version et d'identification sont stockées dans un fichier /usr/lib/extension-release.NAME (pour sysext) ou /etc/extension-release.NAME (pour confext), où NAME correspond au nom de l'image. Le fichier doit contenir des lignes au format ID=, VERSION_ID= et CONFEXT_LEVEL. Ces informations sont ensuite comparées à celles du système hôte pour vérifier la compatibilité.

UTILISATION

Le cas d'utilisation principal des images système est les environnements immuables où les outils de débogage et de développement doivent être facultativement disponibles, mais non inclus dans l'image de base immuable du système d'exploitation elle-même (par exemple, strace(1) et gdb(1) doivent être une addition installable en option afin de faciliter le débogage/développement). Les images d'extension système ne doivent pas être confondues avec un framework générique d'empaquetage logiciel, car aucun schéma de dépendance n'est disponible : les extensions système doivent transporter elles-mêmes tous les fichiers dont elles ont besoin, à l'exception de ceux déjà expédiés dans l'image du système hôte sous-jacent. Typiquement, les images d'extension système sont construites en même temps que l'image de base du système d'exploitation — au sein du même système de build.

Un autre cas d'utilisation du concept d'extension système est la substitution temporaire de ressources fournies par le système d'exploitation par des plus récentes, par exemple pour installer une version de développement compilée localement d'un composant de bas niveau par-dessus l'image du système d'exploitation immuable sans effectuer une reconstruction complète du système d'exploitation ou modifier l'image nominalement immuable. (par exemple, "installer" un paquet construit localement avec DESTDIR=/var/lib/extensions/mytest make install && systemd-sysext refresh, le rendant disponible dans /usr/ comme s'il avait été installé dans l'image du système d'exploitation elle-même.) Ce cas fonctionne, que la hiérarchie /usr/ de l'hôte sous-jacent soit gérée comme une image disque immuable ou qu'il s'agisse d'un arbre contrôlé par un gestionnaire de paquets traditionnel (c'est-à-dire inscriptible).

Avec systemd-confext, il est possible de reconfigurer à l'exécution les services du système d'exploitation. Parfois, il est nécessaire d'échanger certaines valeurs de paramètres de configuration ou de redémarrer un service spécifique sans déployer de nouveau code ou un déploiement complet du système d'exploitation. En d'autres termes, nous voulons pouvoir lier les options les plus fréquemment configurées à des indicateurs mis à jour à l'exécution qui peuvent être modifiés sans redémarrage du système. Cela aidera à réduire les temps de maintenance lorsqu'il est nécessaire de modifier la configuration du système d'exploitation. Il fournit également un outil fiable pour la gestion de la configuration, car tous les anciens fichiers de configuration disparaissent lorsque l'image systemd-confext est supprimée.

MUTABILITE

Par défaut, la fusion des extensions système sur les systèmes de fichiers hôtes modifiables rend les hiérarchies /usr/ et /opt/ inscriptibles en lecture seule. La fusion des extensions de configuration aura le même effet sur /etc/. Le mode modifiable permet les écritures dans ces emplacements lorsque les extensions sont fusionnées.

Les modes suivants sont pris en charge :

1.désactivé : Force le mode immuable même si des répertoires de routage d'écriture existent sous /var/lib/extensions.mutable/. C'est le mode par défaut.
2.auto : Mode automatique. La mutabilité est désactivée par défaut et n'est activée que si un répertoire de routage d'écriture correspondant existe sous /var/lib/extensions.mutable/.
3.activé : Force le mode modifiable et crée automatiquement des répertoires de routage d'écriture sous /var/lib/extensions.mutable/ lorsque nécessaire.
4.importer : Force le mode immuable comme désactivé ci-dessus, mais fusionne le contenu des répertoires sous /var/lib/extensions.mutable/ dans le système de fichiers hôte.
5.éphémère : Force le mode modifiable comme activé ci-dessus, mais au lieu d'utiliser le répertoire de routage d'écriture sous /var/lib/extensions.mutable/, systemd-sysext utilisera des répertoires éphémères vides. Cela signifie que les modifications apportées aux hiérarchies fusionnées disparaîtront lorsque les hiérarchies seront démontées.
6.éphémère-importer : Force le mode modifiable comme éphémère ci-dessus, mais au lieu d'ignorer le contenu des répertoires de routage d'écriture sous /var/lib/extensions.mutable/, les fusionne dans le système de fichiers hôte, comme le fait importer.

Voir "Options" ci-dessous pour spécifier les modes à l'aide de l'option de ligne de commande --mutable=.

À l'exception du mode éphémère, le mode modifiable achemine les écritures vers des sous-répertoires dans /var/lib/extensions.mutable/.

Les écritures dans /usr/ sont dirigées vers /var/lib/extensions.mutable/usr/
les écritures dans /opt/ sont dirigées vers /var/lib/extensions.mutable/opt/, et
les écritures dans /etc/ aboutissent dans /var/lib/extensions.mutable/etc/.

Si usr/, opt/, ou etc/ dans /var/lib/extensions.mutable/ sont des liens symboliques, alors les écritures sont dirigées vers les cibles des liens symboliques. Par conséquent, pour conserver la mutabilité d'un système de fichiers hôte, créez des liens symboliques

/var/lib/extensions.mutable/etc/ → /etc/
/var/lib/extensions.mutable/usr/ → /usr/
/var/lib/extensions.mutable/opt/ → /opt/
pour rediriger les écritures vers la hiérarchie de répertoires de base d'origine.

Alternativement, un système de fichiers temporaire peut être monté sur /var/lib/extensions.mutable/, ou des liens symboliques dans /var/lib/extensions.mutable/ peuvent pointer vers des sous-répertoires sur un système de fichiers temporaire (par exemple, sous /tmp/) pour autoriser uniquement les modifications éphémères. Notez que cela n'est pas la même chose que le mode éphémère, car le système de fichiers temporaire existera toujours après le démontage.

Ajouté dans la version 256.

COMMANDES

Les commandes suivantes sont comprises par les concepts sysext et confext :

status

Lorsqu'il est appelé sans verbe de commande, ou lorsque status est spécifié, l'état de fusion actuel est affiché, séparément (pour /usr/ et /opt/ de sysext et pour /etc/ de confext).

Ajouté dans la version 248.

merge

Fusionne toutes les images d'extension système actuellement installées dans /usr/ et /opt/, en superposant ces hiérarchies avec un système de fichiers "overlayfs" combinant les hiérarchies sous-jacentes avec celles incluses dans les images d'extension. Cette commande échouera si les hiérarchies sont déjà fusionnées. Pour confext, la fusion se fait dans le répertoire /etc/ à la place.

Ajouté dans la version 248.

unmerge

Démonte toutes les images d'extension système actuellement installées de /usr/ et /opt/ pour sysext et de /etc/, pour confext, en démontant les systèmes de fichiers "overlayfs" créés par merge précédemment.

Ajouté dans la version 248.

refresh

Une combinaison de unmerge et merge : si déjà monté, l'instance "overlayfs" existante est temporairement démontée, puis remplacée par une nouvelle version. Cette commande est utile après l'installation/la suppression d'images d'extension système, afin de mettre à jour le système de fichiers "overlayfs" en conséquence. Si aucune extension système n'est installée lorsque cette commande est exécutée, l'équivalent de unmerge est exécuté, sans établir de nouvelle instance "overlayfs". Notez qu'il existe actuellement un bref instant où ni l'ancienne ni la nouvelle instance "overlayfs" n'est montée. Cela implique que toutes les ressources fournies par une extension système disparaîtront brièvement — même si elles existent en continu pendant l'opération de rafraîchissement.

Ajouté dans la version 248.

list

Une liste brève des images d'extension installées est affichée.

Ajouté dans la version 248.

-h, --help

Affiche un court message d'aide et quitte.

--version

Affiche une courte chaîne de version et quitte.

OPTIONS

--root=

Opère par rapport au répertoire racine spécifié, c'est-à-dire établit le montage "overlayfs" non pas sur les hiérarchies /usr/ et /opt/ de niveau supérieur de sysext ou sur /etc/ de confext, mais sous un répertoire racine spécifié.

Ajouté dans la version 248.

--force

Lors de la fusion des extensions système dans /usr/ et /opt/ pour sysext et /etc/ pour confext, ignore les incompatibilités de version, c'est-à-dire force la fusion, que les informations de version incluses dans les images correspondent ou non à l'hôte.

Ajouté dans la version 248.

--image-policy=politique

Prend une chaîne de politique d'image comme argument, conformément à systemd.image-policy(7). La politique est appliquée lors de l'opération sur les images disque d'extension système. Si elle n'est pas spécifiée, la valeur par défaut est "root=verity+signed+encrypted+unprotected+absent:usr=verity+signed+encrypted+unprotected+absent" pour les extensions système, c'est-à-dire que seuls les systèmes de fichiers racine et /usr/ de l'image sont utilisés. Pour les extensions de configuration, la valeur par défaut est "root=verity+signed+encrypted+unprotected+absent". Lors de l'exécution dans l'initrd et de l'opération sur une image d'extension système stockée dans le répertoire /.extra/sysext/ une politique légèrement plus stricte est utilisée par défaut : "root=signed+absent:usr=signed+absent", voir ci-dessus pour les détails.

Ajouté dans la version 254.

Ajouté dans la version 256.

ephemeral

force le mode modifiable, mais avec le contenu des répertoires de routage d'écriture dans /var/lib/extensions.mutable/ ignoré, et les modifications du système de fichiers hôte étant abandonnées après le démontage.

Ajouté dans la version 256.

NAME

systemd-sysext.service, systemd-sysext - service and utility for system extension images

SYNOPSIS

systemd-sysext [OPTIONS...] {COMMAND}

DESCRIPTION

systemd-sysext is a service and utility to manage system extension images, which may contain additional binaries, libraries, or other data to be made available to the system.

System extension images are typically read-only file system images (e.g. SquashFS) that are mounted at /usr, /boot, or other system directories. They are primarily intended to allow system administrators to bundle large amounts of additional data or optional features with an operating system in a disjoint manner. This is useful for distributing large toolsets, different versions of libraries, or extensive documentation.

The primary use case for system extensions is the extension of the container runtime environment. systemd-sysext allows container runtimes like systemd-nspawn(1) to access container images, for example, in order to make additional binaries available at runtime.

The system extension images are usually stored in /var/lib/systemd/sysext/.

The systemd-sysext service is automatically activated on boot and installs available system extension images into the system's file system hierarchy. It discovers and mounts system extension images, respecting the contents of Discoverable Partitions Specification. It also removes images that are no longer available.

USES

A system extension image should contain a file named --systemd.preset in its root directory. This file may list systemd units (like services, sockets, etc.) that should be enabled system-wide, and potentially executed when the extension image is mounted. If this file is not present, no units are enabled from the image.

System extension images may also contain executables in /usr/bin, libraries in /usr/lib, or other data in various locations under /usr. If such content is placed under /usr, it will be mounted read-only into the main system's /usr directory.

System extension images may also contain a --systemd.link file. If present, this file may describe network interface configuration using systemd.link(5) syntax. It may also contain information about how to configure network devices when the extension is activated.

Additionally, system extension images may contain a --systemd.nspawn file. This file might specify parameters that should be passed to systemd-nspawn(1) when it is invoked in the context of the extension image. This is mostly useful for passing environment variables or specifying default boot parameters.

If a system extension image provides a --systemd.socket file, the units defined therein will be activated if the corresponding socket unit is started.

For more details, see Portable Services.

MUTABILITY

System extension images are mounted read-only. Any modifications made to the files within the extension image after it has been mounted will be discarded when the system extension is unmounted or discarded.

COMMANDS

The following commands are supported:

list
List all available system extension images. This includes images that are currently installed and those that are not. The output will indicate whether an image is currently installed or not.
link
Install available system extension images. This command should be run as root. It scans the configured directories for system extension images, checks their validity, and installs them by mounting them read-only into the system's file system hierarchy (e.g. under /usr). This command should typically be run automatically by the systemd-sysext.service systemd unit during boot.
unlink
Uninstall system extension images. This command should be run as root. It removes currently installed system extension images from the system's file system hierarchy. This command should typically be run automatically by the systemd-sysext.service systemd unit during boot.
update
This is a compatibility command, it is equivalent to link. It was added for backwards compatibility with older versions of systemd.
refresh
This is a compatibility command, it is equivalent to link. It was added for backwards compatibility with older versions of systemd.
status
Show the current status of the system extension images, including which ones are installed and mounted.

OPTIONS

The following options are understood:

Options may be provided on the command line to modify the behavior of the commands listed above.

--directory=DIR

Specifies the directory to search for system extension images. Defaults to /var/lib/systemd/sysext/. This option may be specified multiple times.

--image=PATH

Operates on the specified system extension image file instead of scanning directories. This option may be specified multiple times.

--json=MODE

Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

--auto-update

When used with link, automatically update installed system extension images if newer versions are found. This means that any already installed image will be unmounted and replaced with the newer one. This is the default behavior.

--no-update

When used with link, do not update installed system extension images. This means that any already installed image will be kept, and newer versions found will be ignored.

--discard-unmerged

When used with unlink, discard the host file system entries of unmerged system extension images.

Added in version 256.

--noexec=BOOL

When merging configuration extensions into /etc/ the "MS_NOEXEC" mount flag is used by default. This option can be used to disable it.

Added in version 254.

--no-reload

When used with merge, unmerge or refresh, do not reload daemon after executing the changes even if an extension that is applied requires a reload via the EXTENSION_RELOAD_MANAGER= set to 1.

Added in version 255.

--no-pager

Do not pipe output into a pager.

--no-legend

Do not print the legend, i.e. column headers and the footer with hints.

--json=MODE

Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

EXIT STATUS

On success, 0 is returned.
