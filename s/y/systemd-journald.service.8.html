DESCRIPTION

systemd-journald est un service système qui collecte et stocke les données de journalisation. Il crée et maintient des journaux structurés et indexés basés sur les informations de journalisation reçues de diverses sources :

•Messages de journal du noyau, via kmsg
•Messages de journal système simples, via l'appel libc syslog(3)
•Messages de journal système structurés via l'API native du journal, voir sd_journal_print(3) et Protocole natif du journal[1]
•Sortie standard et erreur standard des unités de service. Pour plus de détails, voir ci-dessous.
•Enregistrements d'audit, provenant du sous-système d'audit du noyau

Le démon collectera implicitement de nombreux champs de métadonnées pour chaque message de journal de manière sécurisée et non falsifiable. Voir systemd.journal-fields(7) pour plus d'informations sur les métadonnées collectées.

Les données du journal collectées par le journal sont principalement basées sur du texte mais peuvent également inclure des données binaires si nécessaire. Les champs individuels composant un enregistrement de journal stocké dans le journal peuvent avoir une taille allant jusqu'à 2^64-1 octets.

Le service journal stocke les données du journal soit de manière persistante sous /var/log/journal, soit de manière volatile sous /run/log/journal/ (dans ce dernier cas, elles sont perdues au redémarrage). Par défaut, les données du journal sont stockées de manière persistante si /var/log/journal/ existe au démarrage, avec un repli implicite vers le stockage volatile sinon. Utilisez Storage= dans journald.conf(5) pour configurer l'emplacement des données du journal, indépendamment de l'existence de /var/log/journal/.

Notez que journald utilisera initialement le stockage volatile, jusqu'à ce qu'un appel à journalctl --flush (ou l'envoi de SIGUSR1 à journald) le fera passer à la journalisation persistante (dans les conditions mentionnées ci-dessus). Ceci est fait automatiquement au démarrage via « systemd-journal-flush.service ».

Sur les systèmes où /var/log/journal/ n'existe pas encore mais où la journalisation persistante est souhaitée (et où le journald.conf par défaut est utilisé), il suffit de créer le répertoire et de s'assurer qu'il a les modes d'accès et la propriété corrects :

mkdir -p /var/log/journal
systemd-tmpfiles --create --prefix /var/log/journal

Voir journald.conf(5) pour des informations sur la configuration de ce service.

CONNEXION PAR FLUX

Le gestionnaire de services systemd invoque tous les processus de service avec la sortie standard et l'erreur standard connectées au journal par défaut. Ce comportement peut être modifié via les paramètres de fichier d'unité StandardOutput=/StandardError=, voir systemd.exec(5) pour les détails. Le journal convertit le flux d'octets de journal reçu de cette manière en enregistrements de journal individuels, divisant le flux aux caractères de nouvelle ligne (« \n », ASCII 10) et NUL.

Si systemd-journald.service est arrêté, les connexions de flux associées à tous les services sont terminées. Les écritures ultérieures sur ces flux par le service entraîneront des erreurs EPIPE. Afin de réagir gracieusement dans ce cas, il est recommandé aux programmes journalisant vers la sortie/erreur standard d'ignorer de telles erreurs. Si le gestionnaire de signaux SIGPIPE n'est pas bloqué ou désactivé, les tentatives d'écriture généreront également de tels signaux de processus, voir signal(7). Pour atténuer ce problème, le gestionnaire de services systemd désactive explicitement le signal SIGPIPE pour tous les processus invoqués par défaut (cela peut être modifié pour chaque unité individuellement via l'option IgnoreSIGPIPE=, voir systemd.exec(5) pour les détails). Après la terminaison des flux de sortie/erreur standard, ils peuvent ne pas être récupérés avant que les services auxquels ils sont associés ne soient redémarrés. Notez que pendant le fonctionnement normal, systemd-journald.service stocke des copies des descripteurs de fichiers de ces flux dans le gestionnaire de services. Si systemd-journald.service est redémarré en utilisant systemctl restart ou une opération équivalente au lieu d'une paire de commandes distinctes systemctl stop et systemctl start (ou opérations équivalentes), ces connexions de flux ne sont pas terminées et survivent au redémarrage. Il est donc sûr de redémarrer systemd-journald.service, mais son arrêt n'est pas recommandé.

Notez que les métadonnées des enregistrements de journal transférés via ces flux de sortie/erreur standard reflètent les métadonnées du pair pour lequel le flux a été initialement créé. Si la connexion de flux est transmise à d'autres processus (tels que d'autres processus enfants issus du processus de service principal), les enregistrements de journal ne refléteront pas leurs métadonnées, mais continueront à décrire le processus d'origine. Ceci est différent des autres transports de journalisation énumérés ci-dessus, qui sont intrinsèquement basés sur des enregistrements et où les métadonnées sont toujours associées à l'enregistrement individuel.

En plus de la journalisation implicite de la sortie/erreur standard des services, la journalisation par flux est également disponible via l'outil en ligne de commande systemd-cat(1).

Actuellement, le nombre de flux de journalisation parallèles que systemd-journald acceptera est limité à 4096. Lorsque cette limite est atteinte, les flux de journalisation supplémentaires peuvent être établis mais recevront EPIPE dès le début.

ESPACES DE NOMS DU JOURNAL

Les « espaces de noms » du journal sont à la fois un mécanisme pour isoler logiquement le flux de journal des projets composés d'un ou plusieurs services du reste du système et un mécanisme pour améliorer les performances. Plusieurs espaces de noms de journal peuvent exister simultanément, chacun définissant son propre flux de journal indépendant géré par sa propre instance de systemd-journald. Les espaces de noms sont indépendants les uns des autres, tant dans le stockage des données que dans l'interface IPC. Par défaut, il n'existe qu'un seul « espace de noms par défaut », géré par systemd-journald.service (et ses unités de socket associées). Des espaces de noms supplémentaires sont créés en démarrant une instance du modèle de service systemd-journald@.service. Le nom de l'instance est l'identifiant de l'espace de noms, qui est une courte chaîne utilisée pour référencer l'espace de noms du journal. Les unités de service peuvent être assignées à un espace de noms de journal spécifique via le réglage LogNamespace= du fichier d'unité, voir systemd.exec(5) pour les détails. Le commutateur --namespace= de journalctl(1) peut être utilisé pour visualiser le flux de journal d'un espace de noms spécifique. Si le commutateur n'est pas utilisé, le flux de journal de l'espace de noms par défaut est affiché, c'est-à-dire que les données de journal des autres espaces de noms ne sont pas visibles.

Les services associés à un espace de noms de journal spécifique peuvent journaliser via syslog(3), le protocole de journalisation natif du journal et via stdout/stderr ; la journalisation de ces trois transports est associée à l'espace de noms.

Par défaut, seul l'espace de noms par défaut collectera les messages de journal du noyau et d'audit.

L'instance systemd-journald de l'espace de noms par défaut est configurée via /etc/systemd/journald.conf (voir ci-dessous), tandis que les autres instances sont configurées via /etc/systemd/journald@NAMESPACE.conf. Les données du journal du journal pour l'espace de noms par défaut sont placées dans /var/log/journal/MACHINE_ID (voir ci-dessous) tandis que les données pour les autres espaces de noms sont situées dans /var/log/journal/MACHINE_ID.NAMESPACE.

SIGHUP

Upon reception of the SIGHUP process signal systemd-journald will reload its configuration values and update the kernel log buffer and journals to reflect the new configuration. If ReadKmsg= has changed, the kernel log buffer will be flushed and updated as part of the reload. The active journal (e.g., persistent, volatile) will continue to be used with the updated configuration. However, if the storage mode has changed from persistent to volatile and the current journal in use is the persistent journal, then the active journal will be switched to the volatile journal.

Added in version 258.

CONTRÔLE D'ACCÈS

Journal files are, by default, owned and readable by the "systemd-journal" system group but are not writable. Adding a user to this group thus enables them to read the journal files.

By default, each user, with a UID outside the range of system users, dynamic service users, and the nobody user, will get their own set of journal files in /var/log/journal/. See Users, Groups, UIDs and GIDs on systemd systems[2] for more details about UID ranges. These journal files will not be owned by the user, however, in order to avoid that the user can write to them directly. Instead, file system ACLs are used to ensure the user gets read access only.

Additional users and groups may be granted access to journal files via file system access control lists (ACL). Distributions and administrators may choose to grant read access to all members of the "wheel" and "adm" system groups with a command such as the following:

# setfacl -Rnm g:wheel:rx,d:g:wheel:rx,g:adm:rx,d:g:adm:rx /var/log/journal/

Note that this command will update the ACLs both for existing journal files and for future journal files created in the /var/log/journal/ directory.

/etc/systemd/journald.conf

Configure systemd-journald behavior. See journald.conf(5).

Added in version 206.

/run/log/journal/machine-id/*.journal, /run/log/journal/machine-id/*.journal~, /var/log/journal/machine-id/*.journal, /var/log/journal/machine-id/*.journal~

systemd-journald writes entries to files in /run/log/journal/machine-id/ or /var/log/journal/machine-id/ with the ".journal" suffix. If the daemon is stopped uncleanly, or if the files are found to be corrupted, they are renamed using the ".journal~" suffix, and systemd-journald starts writing to a new file. /run/ is used when /var/log/journal is not available, or when Storage=volatile is set in the journald.conf(5) configuration file.

When systemd-journald ceases writing to a journal file, it will be renamed to "original-name@suffix.journal" (or "original-name@suffix.journal~"). Such files are "archived" and will not be written to any more.

In general, it is safe to read or copy any journal file (active or archived). journalctl(1) and the functions in the sd-journal(3) library should be able to read all entries that have been fully written.

systemd-journald will automatically remove the oldest archived journal files to limit disk use. See SystemMaxUse= and related settings in journald.conf(5).

Added in version 206.

/dev/kmsg, /dev/log, /run/systemd/journal/dev-log, /run/systemd/journal/socket, /run/systemd/journal/stdout

Sockets and other file node paths that systemd-journald will listen on and are visible in the file system. In addition to these, systemd-journald can listen for audit events using netlink(7), depending on whether "systemd-journald-audit.socket" is enabled or not.

Added in version 228.

If journal namespacing is used these paths are slightly altered to include a namespace identifier, see above.
