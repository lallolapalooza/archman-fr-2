NOM

systemd-coredump, systemd-coredump.socket, systemd-coredump@.service - Acquérir, sauvegarder et traiter les dumps de noyau

SYNTAXE

/usr/lib/systemd/systemd-coredump

/usr/lib/systemd/systemd-coredump --backtrace

systemd-coredump@.service

systemd-coredump.socket

DESCRIPTION

systemd-coredump@.service est un service système pour traiter les dumps de noyau. Il enregistrera un résumé de l'événement dans systemd-journald.service(8), incluant des informations sur l'identifiant du processus, le propriétaire, le signal qui a tué le processus et la trace de pile si possible. Il peut également sauvegarder le dump de noyau pour un traitement ultérieur. Voir la section "Informations sur le processus en panne" ci-dessous.

Le comportement d'un programme spécifique lors de la réception d'un signal est régi par quelques facteurs qui sont décrits en détail dans core(5). En particulier, le dump de noyau ne sera traité que lorsque les limites de ressources du processus associées (RLIMIT_CORE) seront suffisantes.

Les dumps de noyau peuvent être écrits dans le journal ou sauvegardés sous forme de fichier. Dans les deux cas, ils peuvent être récupérés pour un traitement ultérieur, par exemple dans gdb(1). Voir coredumpctl(1), en particulier les verbes list et debug.

Par défaut, systemd-coredump écrira le dump de noyau dans le journal, incluant une trace de pile si possible, et stockera le dump de noyau (une image du contenu mémoire du processus) dans un fichier externe dans /var/lib/systemd/coredump/. Ces dumps de noyau sont supprimés après quelques jours par défaut ; voir /usr/lib/tmpfiles.d/systemd.conf pour plus de détails. Notez que la suppression des fichiers de noyau du système de fichiers et la purge des entrées du journal sont indépendantes, et le fichier de noyau peut être présent sans l'entrée du journal, et les entrées du journal peuvent pointer vers des noyaux depuis supprimés. Certaines métadonnées sont attachées aux fichiers de noyau sous forme d'attributs étendus, donc les fichiers de noyau sont utiles à certaines fins même sans les métadonnées complètes disponibles dans l'entrée du journal.

Pour plus de détails, voir systemd Coredump Handling[1].

Invocation de systemd-coredump

L'exécutable systemd-coredump effectue le travail réel. Il est invoqué deux fois : une fois comme gestionnaire par le noyau, et une seconde fois dans systemd-coredump@.service pour écrire réellement les données dans le journal et traiter et sauvegarder le fichier de noyau.

Lorsque le noyau invoque systemd-coredump pour gérer un dump de noyau, il s'exécute en mode privilégié et se connectera au socket créé par l'unité systemd-coredump.socket, qui à son tour lancera une instance non privilégiée de systemd-coredump@.service pour traiter le dump de noyau. Par conséquent, systemd-coredump.socket et systemd-coredump@.service sont des unités auxiliaires qui effectuent le traitement réel des dumps de noyau et sont soumises à la gestion normale des services.

Il est également possible d'invoquer systemd-coredump avec l'option --backtrace. Dans ce cas, systemd-coredump attend une entrée de journal au format Journal Export Format[2] sur l'entrée standard. L'entrée doit contenir un champ MESSAGE= et tout champ de métadonnées supplémentaire que l'appelant juge raisonnable. systemd-coredump ajoutera des champs de métadonnées supplémentaires de la même manière qu'il le fait pour les dumps de noyau reçus du noyau. Dans ce mode, aucun dump de noyau n'est stocké dans le journal.

Dumps de noyau dans des conteneurs/espaces de noms

Le service systemd-coredump@.service tentera automatiquement d'extraire une trace de pile d'un processus lors de son plantage. Pour cette trace de pile, les symboles seront résolus en fonction des informations de débogage intégrées dans l'image ELF en panne, ou des informations de débogage équivalentes disponibles séparément sur le système hôte. Pour les processus qui tombent en panne dans des conteneurs locaux ou d'autres sandboxes basées sur des espaces de noms de montage, ces informations de débogage auxiliaires ne sont typiquement pas disponibles sur l'hôte (simplement parce que les conteneurs exécutent généralement des versions logicielles différentes de celles de l'hôte). systemd-coredump fournit deux mécanismes pour résoudre ce problème:

1.Pour les conteneurs système complets exécutant systemd à l'intérieur, il est conseillé d'activer CoredumpReceive= sur l'unité (voir systemd.resource-control(5)), ce qui garantit que les dumps de noyau d'un conteneur sont tentés d'être transférés à systemd-coredump@.service s'exécutant à l'intérieur du conteneur, c'est-à-dire que le conteneur traite et stocke ses propres dumps de noyau. Notez que systemd-nspawn(8) utilise ce mode par défaut lorsqu'il est appelé avec l'option --boot. Ce mode de fonctionnement est généralement recommandé pour des raisons de sécurité: le traitement sensible à la sécurité du dump de noyau est effectué dans les limites du conteneur lui-même, par le code propre du conteneur, soutenu par le stockage propre du conteneur.
2.Alternativement, pour les conteneurs plus restreints (qui n'exécutent pas de système d'initialisation approprié comme PID 1) il est possible d'activer le traitement du dump de noyau sur l'hôte, avec un accès aux données d'informations de débogage du conteneur lui-même. Ce mode de fonctionnement doit être activé via EnterNamespace= dans coredump.conf(5), et désactivé par défaut, pour des raisons de sécurité.

Si à la fois CoredumpReceive= est activé sur l'unité du conteneur auquel appartient le dump de noyau, et EnterNamespace= est activé dans le fichier de configuration coredump.conf, le premier a la priorité.

CONFIGURATION

Pour les programmes démarrés par systemd, les limites de ressources du processus peuvent être définies par la directive LimitCORE=, voir systemd.exec(5).

Afin d'être utilisé par le noyau pour gérer les dumps de noyau, systemd-coredump doit être configuré dans le paramètre kernel.core_pattern de sysctl(8). La syntaxe de ce paramètre est expliquée dans core(5). systemd installe le fichier /usr/lib/sysctl.d/50-coredump.conf qui configure kernel.core_pattern en conséquence. Ce fichier peut être masqué ou remplacé pour utiliser un paramètre différent en suivant les règles normales de sysctl.d(5). Si la configuration sysctl est modifiée, elle doit être mise à jour dans le noyau avant qu'elle ne prenne effet, voir sysctl(8) et systemd-sysctl(8).

Afin d'être utilisé en mode --backtrace, un gestionnaire de trace de pile approprié doit être installé du côté de l'expéditeur. Par exemple, dans le cas de python(1), il faut installer un sys.excepthook, voir systemd-coredump-python[3].

Le comportement de systemd-coredump lui-même est configuré via le fichier de configuration /etc/systemd/coredump.conf et les snippets correspondants /etc/systemd/coredump.conf.d/*.conf, voir coredump.conf(5). Une nouvelle instance de systemd-coredump est invoquée à la réception de chaque dump de noyau. Par conséquent, les modifications apportées à ces fichiers prendront effet la prochaine fois qu'un dump de noyau sera reçu.

Les ressources utilisées par les fichiers de dumps de noyau sont restreintes de deux manières. Des paramètres comme la taille maximale des dumps de noyau acquis et des fichiers peuvent être définis dans les fichiers /etc/systemd/coredump.conf et les snippets mentionnés ci-dessus. De plus, la durée de stockage des fichiers de dumps de noyau est restreinte par systemd-tmpfiles, les paramètres correspondants se trouvant par défaut dans /usr/lib/tmpfiles.d/systemd.conf. Par défaut, les dumps de noyau sont supprimés après quelques jours ; voir le fichier ci-dessus pour les détails.

Désactivation du traitement des dumps de noyau

Pour désactiver le traitement potentiellement gourmand en ressources par systemd-coredump, définissez

Storage=none
ProcessSizeMax=0

dans coredump.conf(5).

Les champs suivants sont enregistrés (si connus) avec l'entrée du journal :

COREDUMP_UID=, COREDUMP_PID=, COREDUMP_GID=

Le numéro de processus (PID), l'identifiant utilisateur propriétaire (UID) et l'identifiant groupe (GID) du processus planté.

Lorsque le processus planté faisait partie d'un conteneur (ou d'un espace de noms de processus ou d'utilisateur en général), ce sont les valeurs telles qu'elles sont vues *à l'extérieur*, dans l'espace de noms où s'exécute systemd-coredump.

Ajouté dans la version 248.

COREDUMP_BY_PIDFD=

Si le processus planté a été analysé à l'aide d'un PIDFD fourni par le noyau (nécessite le noyau v6.16), ce champ sera présent et défini sur "1". Si ce champ n'est pas défini, le processus planté a été analysé via un PID, ce qui est connu pour être sujet à des conditions de course.

Ajouté dans la version 258.

COREDUMP_TIMESTAMP=

L'heure du plantage telle que rapportée par le noyau (en µs depuis l'époque).

Ajouté dans la version 248.

COREDUMP_RLIMIT=

La limite de ressources logicielle pour la taille du fichier core, voir getrlimit(2).

Ajouté dans la version 248.

COREDUMP_UNIT=, COREDUMP_SLICE=

Les noms de l'unité système et de la tranche.

Lorsque le processus planté se trouvait dans un conteneur, ce sont les noms d'unités *à l'extérieur*, dans le gestionnaire système principal.

Ajouté dans la version 248.

COREDUMP_CGROUP=

Le cgroup principal de l'unité du processus planté.

Lorsque le processus planté se trouvait dans un conteneur, il s'agit du chemin complet, tel qu'il est vu à l'extérieur du conteneur.

Ajouté dans la version 248.

COREDUMP_PROC_CGROUP=

Informations sur le groupe de contrôle au format utilisé dans /proc/self/cgroup. Sur les systèmes avec la hiérarchie cgroup unifiée, il s'agit d'un chemin unique préfixé par "0::", et de plusieurs chemins préfixés par des numéros de contrôleur sur les systèmes hérités.

Lorsque le processus planté se trouvait dans un conteneur, il s'agit du chemin complet, tel qu'il est vu à l'extérieur du conteneur.

Ajouté dans la version 248.

COREDUMP_OWNER_UID=, COREDUMP_USER_UNIT=, COREDUMP_SESSION=

L'UID numérique de l'utilisateur propriétaire de la session de connexion ou de l'unité utilisateur systemd du processus planté, l'unité du gestionnaire utilisateur et l'identifiant de session. Ces trois champs sont présents uniquement pour les processus utilisateur.

Lorsque le processus planté se trouvait dans un conteneur, ce sont les valeurs *à l'extérieur*, dans le système principal.

Ajouté dans la version 248.

COREDUMP_SIGNAL_NAME=, COREDUMP_SIGNAL=

Le nom du signal de terminaison (avec le préfixe "SIG" [4]) et sa valeur numérique. (Les deux sont inclus car les numéros de signal varient selon l'architecture.)

Ajouté dans la version 248.

COREDUMP_CWD=, COREDUMP_ROOT=

Le répertoire de travail actuel et le répertoire racine du processus planté.

Lorsque le processus planté se trouve dans un conteneur, ces chemins sont relatifs à la racine de l'espace de noms de montage du conteneur.

Ajouté dans la version 248.

COREDUMP_DUMPABLE=

Le champ PR_GET_DUMPABLE tel que rapporté par le noyau, voir prctl(2).

Ajouté dans la version 258.

COREDUMP_OPEN_FDS=

Informations sur les descripteurs de fichiers ouverts, au format suivant : 
fd:/chemin/vers/fichier
pos:     ...
flags:   ...
...
fd:/chemin/vers/fichier
pos:     ...
flags:   ...
...

La première ligne contient le numéro du descripteur de fichier fd et le chemin, tandis que les lignes suivantes montrent le contenu de /proc/pid/fdinfo/fd.

Ajouté dans la version 248.

COREDUMP_EXE=

La destination du lien symbolique /proc/pid/exe.

Lorsque le processus planté se trouve dans un conteneur, ce chemin est relatif à la racine de l'espace de noms de montage du conteneur.

Ajouté dans la version 248.

COREDUMP_CMDLINE=, COREDUMP_COMM=, COREDUMP_ENVIRON=, COREDUMP_PROC_AUXV=, COREDUMP_PROC_LIMITS=, COREDUMP_PROC_MAPS=, COREDUMP_PROC_MOUNTINFO=, COREDUMP_PROC_STATUS=

Champs qui mappent les entrées par processus dans le système de fichiers /proc/ : /proc/pid/cmdline (la ligne de commande du processus planté), /proc/pid/comm (le nom de commande associé au processus), /proc/pid/environ (le bloc d'environnement du processus planté), /proc/pid/auxv (le vecteur auxiliaire du processus planté, voir getauxval(3)), /proc/pid/limits (les limites de ressources logicielles et strictes), /proc/pid/maps (les régions mémoire visibles par le processus et leurs permissions d'accès), /proc/pid/mountinfo (les points de montage dans l'espace de noms de montage du processus), /proc/pid/status (divers métadonnées sur le processus).

Voir proc(5) pour plus d'informations.

Ajouté dans la version 248.

COREDUMP_HOSTNAME=

Le nom d'hôte du système.

Lorsque le processus planté se trouvait dans un conteneur, il s'agit du nom d'hôte du conteneur.

Ajouté dans la version 248.

COREDUMP_CONTAINER_CMDLINE=

Pour les processus s'exécutant dans un conteneur, la ligne de commande du processus qui lance le conteneur (le premier processus parent avec un espace de noms de montage différent).

Ajouté dans la version 248.

COREDUMP=

Lorsque le core est stocké dans le journal, l'image core elle-même.

Ajouté dans la version 248.

COREDUMP_FILENAME=

Lorsque le core est stocké en externe, le chemin du fichier core.

Ajouté dans la version 248.

COREDUMP_TRUNCATED=

Défini sur "1" lorsque le coredump sauvegardé a été tronqué. (Une image core partielle peut toujours être traitée par certains outils, bien que évidemment toutes les informations ne soient pas disponibles.)

Ajouté dans la version 248.

COREDUMP_PACKAGE_NAME=, COREDUMP_PACKAGE_VERSION=, COREDUMP_PACKAGE_JSON=

Si l'exécutable contenait des notes ELF de métadonnées .package, elles seront analysées et jointes. Le *package* et la *version* du module ELF 'principal' (c'est-à-dire l'exécutable) seront ajoutés individuellement. Le contenu au format JSON de tous les modules sera ajouté en tant qu'objet JSON unique, chacun avec le nom du module comme clé. Pour plus d'informations sur ce format et ce contenu de métadonnées, voir le document Métadonnées de package pour les fichiers exécutables[5].

Ajouté dans la version 249.

MESSAGE=

Le message généré par systemd-coredump qui inclut la trace si elle a été générée avec succès. Lorsque systemd-coredump est appelé avec --backtrace, ce champ est fourni par l'appelant.

Ajouté dans la version 248.

Divers autres champs existent dans l'entrée du journal, mais concernent le processus d'enregistrement, c'est-à-dire systemd-coredump, et non le processus planté. Voir systemd.journal-fields(7).

Les champs suivants sont enregistrés (si connus) dans le fichier externe listé dans COREDUMP_FILENAME= sous forme d'attributs étendus :

user.coredump.pid, user.coredump.uid, user.coredump.gid, user.coredump.signal, user.coredump.timestamp, user.coredump.rlimit, user.coredump.hostname, user.coredump.comm, user.coredump.exe

Ce sont les mêmes que COREDUMP_PID=, COREDUMP_UID=, COREDUMP_GID=, COREDUMP_SIGNAL=, COREDUMP_TIMESTAMP=, COREDUMP_RLIMIT=, COREDUMP_HOSTNAME=, COREDUMP_COMM=, et COREDUMP_EXE=, décrits ci-dessus.

Ajouté dans la version 248.

Ceux-ci peuvent être visualisés à l'aide de getfattr(1). Pour le fichier core décrit dans l'entrée de journal montrée ci-dessus :

$ getfattr --absolute-names -d /var/lib/systemd/coredump/core.Web....552351.....zst

user.coredump.signal="11"
