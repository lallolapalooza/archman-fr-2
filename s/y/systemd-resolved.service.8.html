NOM

systemd-resolved.service, systemd-resolved - Gestionnaire de résolution de noms réseau

SYNPOSIS

systemd-resolved.service

/usr/lib/systemd/systemd-resolved

DESCRIPTION

systemd-resolved est un service système qui fournit la résolution de noms réseau aux applications locales. Il implémente un cache et un résolveur stub DNS/DNSSEC valideur, ainsi qu'un résolveur et un répondeur LLMNR et MulticastDNS. Les applications locales peuvent soumettre des requêtes de résolution de noms réseau via trois interfaces :

•L'API native et complète que systemd-resolved expose via D-Bus, voir org.freedesktop.resolve1(5) et org.freedesktop.LogControl1(5) pour plus de détails. L'utilisation de cette API est généralement recommandée aux clients car elle est asynchrone et complète (par exemple, renvoie correctement le statut de validation DNSSEC et la portée de l'interface pour les adresses, comme nécessaire pour prendre en charge le réseau local).
•L'API native que systemd-resolved expose via Varlink sur le socket AF_UNIX /run/systemd/resolve/io.systemd.Resolve. Celle-ci fournit des fonctionnalités similaires à l'interface D-Bus, mais est disponible pendant toute la durée d'exécution, sans nécessiter un service de courtier de bus système D-Bus en cours d'exécution.
•L'API glibc getaddrinfo(3) telle que définie par la RFC3493[1] et ses fonctions de résolution associées, y compris gethostbyname(3). Cette API est largement prise en charge, y compris au-delà de la plateforme Linux. Sous sa forme actuelle, elle n'expose pas d'informations sur le statut de validation DNSSEC et est uniquement synchrone. Cette API est prise en charge par le module Name Service Switch (NSS) de glibc (nss(5)). L'utilisation du module NSS de glibc nss-resolve(8) est requise pour permettre aux fonctions de résolution de noms de glibc de résoudre les noms d'hôte via systemd-resolved.
•De plus, systemd-resolved fournit un écouteur DNS stub local sur les adresses IP 127.0.0.53 et 127.0.0.54 sur l'interface de boucle locale. Les programmes émettant des requêtes DNS directement, en contournant toute API locale, peuvent être dirigés vers ce stub, afin de les connecter à systemd-resolved. Notez cependant qu'il est fortement recommandé aux programmes locaux d'utiliser plutôt les API glibc NSS ou bus (comme décrit ci-dessus), car divers concepts de résolution réseau (tels que l'adressage local, ou les domaines Unicode LLMNR) ne peuvent pas être mappés au protocole DNS unicast.

Le résolveur stub DNS sur 127.0.0.53 fournit l'ensemble complet des fonctionnalités du résolveur local, qui comprend l'offre de résolution LLMNR/MulticastDNS. Le résolveur stub DNS sur 127.0.0.54 fournit un résolveur plus limité, qui fonctionne uniquement en mode "proxy", c'est-à-dire qu'il transmettra la plupart des messages DNS relativement inchangés aux serveurs DNS distants actuels et retour, mais n'essaiera pas de traiter les messages localement, et donc ne valide pas DNSSEC, ni n'offre LLMNR/MulticastDNS. (Il se traduira cependant par une communication DNS-over-TLS si nécessaire.)

Les serveurs DNS contactés sont déterminés à partir des paramètres globaux dans /etc/systemd/resolved.conf, des paramètres statiques par lien dans les fichiers /etc/systemd/network/*.network (si systemd-networkd.service(8) est utilisé), des paramètres dynamiques par lien reçus via DHCP, des informations fournies via resolvectl(1), et de toute information de serveur DNS mise à disposition par d'autres services système. Voir resolved.conf(5) et systemd.network(5) pour les détails sur les propres fichiers de configuration de systemd pour les serveurs DNS. Pour améliorer la compatibilité, /etc/resolv.conf est lu afin de découvrir les serveurs DNS système configurés, mais uniquement s'il ne s'agit pas d'un lien symbolique vers /run/systemd/resolve/stub-resolv.conf, /usr/lib/systemd/resolv.conf ou /run/systemd/resolve/resolv.conf (voir ci-dessous).

ENREGISTREMENTS SYNTHETIQUES

systemd-resolved synthétise des enregistrements de ressources DNS (RR) pour les cas suivants :

•Le nom d'hôte local configuré est résolu en toutes les adresses IP configurées localement, classées par leur portée, ou — si aucune n'est configurée — l'adresse IPv4 127.0.0.2 (qui se trouve sur l'interface de boucle locale) et l'adresse IPv6 ::1 (qui est l'hôte local).
•Les noms d'hôte "localhost" et "localhost.localdomain" ainsi que tout nom d'hôte se terminant par ".localhost" ou ".localhost.localdomain" sont résolus en adresses IP 127.0.0.1 et ::1.
•Le nom d'hôte "_gateway" est résolu en toutes les adresses de passerelle par défaut actuelles, classées par leur métrique. Cela attribue un nom d'hôte stable à la passerelle actuelle, utile pour la référencer indépendamment de l'état actuel de la configuration réseau.
•Le nom d'hôte "_outbound" est résolu en adresses IPv4 et IPv6 locales les plus susceptibles d'être utilisées pour la communication avec d'autres hôtes. Ce sont les adresses sources préférées des passerelles par défaut si elles sont spécifiées, ou déterminées en demandant une décision de routage vers les passerelles par défaut configurées auprès du noyau, puis en utilisant les adresses IP locales sélectionnées par cette décision. Ce nom d'hôte n'est disponible que s'il y a au moins une passerelle par défaut locale configurée. Cela attribue un nom d'hôte stable aux adresses IP sortantes locales, utile pour les référencer indépendamment de l'état actuel de la configuration réseau.
•Le nom d'hôte "_localdnsstub" est résolu en l'adresse IP 127.0.0.53, c'est-à-dire l'adresse sur laquelle le stub DNS local (voir ci-dessus) écoute.
•Le nom d'hôte "_localdnsproxy" est résolu en l'adresse IP 127.0.0.54, c'est-à-dire l'adresse sur laquelle le proxy DNS local (voir ci-dessus) écoute.
•Les mappages définis dans /etc/hosts sont résolus en leurs adresses configurées et vice-versa, mais ils n'affecteront pas les recherches pour les types autres que d'adresses (comme MX). La prise en charge de /etc/hosts peut être désactivée avec ReadEtcHosts=no, voir resolved.conf(5).

PROTOCOLES ET ROUTAGE

Les requêtes de résolution que systemd-resolved.service reçoit sont routées vers les serveurs DNS, les interfaces LLMNR et MulticastDNS disponibles selon les règles suivantes :

•Les noms pour lesquels des enregistrements synthétiques sont générés (le nom d'hôte local, "localhost" et "localdomain", la passerelle locale, tels que listés dans la section précédente) et les adresses configurées dans /etc/hosts ne sont jamais routés sur le réseau et une réponse est envoyée immédiatement.
•Les noms à étiquette unique sont résolus en utilisant LLMNR sur toutes les interfaces locales où LLMNR est activé. Les requêtes pour les adresses IPv4 sont uniquement envoyées via LLMNR sur IPv4, et les requêtes pour les adresses IPv6 sont uniquement envoyées via LLMNR sur IPv6. Notez que les requêtes pour les noms synthétiques à étiquette unique ne sont pas routées vers LLMNR, MulticastDNS ou DNS unicast.
•Les requêtes pour les enregistrements d'adresses (A et AAAA) des noms non synthétiques à étiquette unique sont résolues via DNS unicast en utilisant des domaines de recherche. Pour toute interface qui définit des domaines de recherche, de telles requêtes sont routées vers les serveurs définis pour cette interface, suffixés avec chacun de ces domaines de recherche. Lorsque des domaines de recherche globaux sont définis, de telles requêtes sont routées vers les serveurs globaux. Pour chaque domaine de recherche, les requêtes sont effectuées en ajoutant le domaine de recherche au nom. De plus, la résolution des noms à étiquette unique via DNS unicast peut être activée avec le paramètre ResolveUnicastSingleLabel=yes. Les détails sur les serveurs interrogés et la manière dont la réponse finale est choisie sont décrits ci-dessous. Notez que cela signifie que les requêtes d'adresse pour les noms à étiquette unique ne sont jamais envoyées par défaut aux serveurs DNS distants, et la résolution n'est possible que si des domaines de recherche sont définis.
•Les noms à étiquettes multiples avec le suffixe de domaine ".local" sont résolus en utilisant MulticastDNS sur toutes les interfaces locales où MulticastDNS est activé. Comme avec LLMNR, les requêtes d'adresse IPv4 sont envoyées via IPv4 et les requêtes d'adresse IPv6 sont envoyées via IPv6.
•Les requêtes pour les noms à étiquettes multiples sont routées via DNS unicast sur les interfaces locales ayant un serveur DNS configuré, plus les serveurs DNS globalement configurés s'il y en a. y défaut, les recherches de domaines avec le suffixe « .local » ne sont pas acheminées vers les serveurs DNS, à moins que le domaine ne soit explicitement spécifié comme domaine de routage ou de recherche pour le serveur DNS et l'interface. Cela signifie que sur les réseaux où le domaine « .local » est défini dans un serveur DNS spécifique au site, des domaines de recherche ou de routage explicites doivent être configurés pour que les recherches fonctionnent dans ce domaine DNS. Notez que, de nos jours, il est généralement recommandé d'éviter de définir « .local » dans un serveur DNS, car la RFC6762[2] réserve ce domaine pour une utilisation exclusive par MulticastDNS.
• Les recherches d'adresses (recherches inversées) sont acheminées de manière similaire aux noms multi-étiquettes, à l'exception des adresses de la plage d'adresses locales au lien qui ne sont jamais acheminées vers DNS unicast et sont uniquement résolues à l'aide de LLMNR et MulticastDNS (lorsqu'ils sont activés).

Si les recherches sont acheminées vers plusieurs interfaces, la première réponse réussie est renvoyée (fusionnant ainsi efficacement les zones de recherche sur toutes les interfaces correspondantes). Si la recherche a échoué sur toutes les interfaces, la dernière réponse échouée est renvoyée.

Le routage des recherches est déterminé par les domaines de routage par interface (recherche et uniquement routage) et les domaines de recherche globaux. Voir systemd.network(5) et resolvectl(1) pour une description de la manière dont ces paramètres sont définis dynamiquement et la discussion de Domains= dans resolved.conf(5) pour une description des paramètres DNS configurés globalement.

La logique de routage des requêtes suivante s'applique aux recherches DNS unicast initiées par systemd-resolved.service :

• Si un nom à rechercher correspond (c'est-à-dire : est égal ou a comme suffixe) à l'un des domaines de routage configurés (recherche ou uniquement routage) de n'importe quel lien, ou aux paramètres DNS configurés globalement, le domaine de routage « correspondant le mieux » est déterminé : celui correspondant avec le plus d'étiquettes. La requête est ensuite envoyée à tous les serveurs DNS de n'importe quel lien ou aux serveurs DNS configurés globalement associés à ce domaine de routage « correspondant le mieux ». (Notez que plus d'un lien peut avoir ce même domaine de routage « correspondant le mieux » configuré, auquel cas la requête est envoyée à tous en parallèle).

Dans le cas de noms à étiquette unique, lorsque des domaines de recherche sont définis, la même logique s'applique, sauf que le nom est d'abord suffixé par chacun des domaines de recherche tour à tour. Notez que cette logique de recherche ne s'applique pas aux noms contenant au moins un point. Voir également la discussion sur la compatibilité avec le résolveur glibc traditionnel ci-dessous.

• Si une requête ne correspond à aucun domaine de routage configuré (par lien ou global), elle est envoyée à tous les serveurs DNS configurés sur les liens configurés comme route par défaut, ainsi qu'au serveur DNS configuré globalement.
• S'il n'y a pas de serveurs DNS configurés sur un lien également configuré comme route par défaut et aucun serveur DNS global configuré, l'un des serveurs DNS de secours intégrés est utilisé.
• Sinon, la requête DNS unicast échoue, car aucun serveur DNS approprié ne peut être déterminé.

Qu'un lien soit la route par défaut ou non peut être configuré avec la commande resolvectl default-route ou le paramètre DNSDefaultRoute= dans les fichiers .network. S'il n'est pas configuré explicitement, il est déterminé implicitement en fonction des domaines DNS configurés pour un lien : s'il existe un domaine uniquement routage autre que « ~. », il est par défaut à faux, sinon à vrai.

En pratique, cela signifie : pour prendre en charge les noms à étiquette unique non synthétisés, définir des domaines de recherche appropriés. Pour préférer acheminer toutes les requêtes DNS qui ne correspondent pas explicitement à la configuration du domaine de routage vers un lien spécifique, configurez-y un domaine uniquement routage « ~. ». Cela garantira que les autres liens ne seront pas pris en compte pour ces requêtes (sauf s'ils portent également un tel domaine de routage). Pour acheminer toutes ces requêtes DNS vers un lien spécifique uniquement si aucun autre lien n'est préféré, configurez le lien comme route par défaut et ne configurez pas de domaine uniquement routage « ~. » dessus. Enfin, pour éviter qu'un lien spécifique ne reçoive de trafic DNS ne correspondant à aucun de ses domaines de routage configurés, ne pas en faire une route par défaut.

Voir org.freedesktop.resolve1(5) pour des informations sur les API D-Bus fournies par systemd-resolved.

COMPATIBILITE AVEC LE RESOLVEUR STUB GLIBC TRADITIONNEL

Cette section fournit un bref résumé des différences dans le résolveur implémenté par nss-resolve(8) avec systemd-resolved et le résolveur stub traditionnel implémenté dans nss-dns.

• Certains noms sont toujours résolus en interne (voir Enregistrements Synthétiques ci-dessus). Traditionnellement, ils seraient résolus par nss-files s'ils étaient fournis dans /etc/hosts. Mais notez que les détails de la construction d'une requête sont sous le contrôle de la bibliothèque cliente. nss-dns essaiera d'abord de résoudre les noms en utilisant les domaines de recherche et même si ces requêtes sont acheminées vers systemd-resolved, il les enverra sur le réseau en utilisant les règles habituelles pour le routage de noms multi-étiquettes [3].
• Les noms à étiquette unique ne sont pas résolus pour les enregistrements A et AAAA à l'aide de DNS unicast (sauf remplacement avec ResolveUnicastSingleLabel=, voir resolved.conf(5)). Ceci est similaire à l'option no-tld-query définie dans resolv.conf(5).
• Les domaines de recherche ne sont pas utilisés pour le « suffixage » des noms multi-étiquettes. (Les domaines de recherche sont néanmoins utilisés pour le routage de recherche, pour les noms qui étaient à l'origine spécifiés comme des étiquettes uniques ou multi-étiquettes.) Tout nom comportant au moins un point est toujours interprété comme un FQDN. nss-dns résoudrait les noms à la fois comme des FQDN relatifs (utilisant les domaines de recherche) et absolus. Certains noms seraient d'abord résolus comme relatifs, et après l'échec de cette requête, comme absolus, tandis que d'autres noms seraient résolus dans l'ordre inverse. L'option ndots dans /etc/resolv.conf était utilisée pour contrôler combien de points le nom doit avoir pour être résolu d'abord comme relatif. Ce résolveur stub n'implémente pas cela du tout : les noms multi-étiquettes ne sont résolus que comme des FQDN.[4]
• Ce résolveur a une notion du domaine spécial « .local » utilisé pour MulticastDNS, et n'acheminera pas les requêtes avec ce suffixe vers les serveurs DNS unicast à moins d'une configuration explicite, voir ci-dessus. De plus, les recherches inversées pour les adresses locales au lien ne sont pas envoyées aux serveurs DNS unicast.
• Ce résolveur lit et met en cache /etc/hosts en interne. (En d'autres termes, nss-resolve remplace nss-files en plus de nss-dns). Les entrées dans /etc/hosts ont la plus haute priorité.
• Ce résolveur implémente également LLMNR et MulticastDNS en plus du protocole DNS unicast classique, et résoudra les noms à étiquette unique à l'aide de LLMNR (lorsqu'il est activé) et les noms se terminant par « .local » à l'aide de MulticastDNS (lorsqu'il est activé).
• Les variables d'environnement $LOCALDOMAIN et $RES_OPTIONS décrites dans resolv.conf(5) ne sont actuellement pas prises en charge.
• Le résolveur nss-dns maintient peu d'état entre les requêtes DNS successives, et pour chaque requête, il communique d'abord avec le premier serveur DNS listé dans /etc/resolv.conf, et en cas d'échec, il continue avec le suivant jusqu'à la fin de la liste, moment auquel la requête échoue. Le résolveur de systemd-resolved maintient cependant un état, et communiquera continuellement avec le même serveur pour toutes les requêtes dans une portée de recherche particulière jusqu'à ce qu'une forme d'erreur soit constatée, auquel cas il passera au serveur suivant, et restera avec lui pour toutes les requêtes dans la portée jusqu'à la prochaine erreur, et ainsi de suite, revenant finalement au premier serveur configuré. Ceci est fait pour optimiser les temps de recherche, en particulier étant donné que le résolveur doit généralement d'abord sonder les ensembles de fonctionnalités du serveur lors de la communication avec celui-ci, ce qui prend du temps. Ce comportement différent implique que les serveurs DNS listés par portée de recherche doivent être équivalents dans les zones qu'ils desservent, de sorte que l'envoi d'une requête à l'un d'eux donnera les mêmes résultats que l'envoi à un autre serveur DNS configuré.

/ETC/RESOLV.CONF

Quatre modes de gestion de /etc/resolv.conf (voir resolv.conf(5)) sont pris en charge :

• systemd-resolved maintient le fichier /run/systemd/resolve/stub-resolv.conf pour la compatibilité avec les programmes Linux traditionnels. Ce fichier liste le stub DNS 127.0.0.53 (voir ci-dessus) comme seul serveur DNS. Il contient également une liste de domaines de recherche utilisés par systemd-resolved. La liste des domaines de recherche est toujours mise à jour. Notez que /run/systemd/resolve/stub-resolv.conf ne doit pas être utilisé directement par les applications, mais uniquement via un lien symbolique depuis /etc/resolv.conf. Ce fichier peut être lié symboliquement depuis /etc/resolv.conf afin de connecter tous les clients locaux qui contournent les API DNS locales à systemd-resolved avec des paramètres de domaine de recherche corrects. Ce mode de fonctionnement est recommandé.
• Un fichier statique /usr/lib/systemd/resolv.conf est fourni et liste le stub DNS 127.0.0.53 (voir ci-dessus) comme seul serveur DNS. Ce fichier peut être lié symboliquement depuis /etc/resolv.conf afin de connecter tous les clients locaux qui contournent les API DNS locales à systemd-resolved. Ce fichier ne contient aucun domaine de recherche.
• systemd-resolved maintient le fichier /run/systemd/resolve/resolv.conf pour la compatibilité avec les programmes Linux traditionnels. Ce fichier peut être lié symboliquement depuis /etc/resolv.conf et est toujours mis à jour, contenant des informations sur tous les serveurs DNS connus. Notez les limitations du format du fichier : il ne connaît pas le concept de serveurs DNS par interface et ne contient donc que des définitions de serveurs DNS à l'échelle du système. Notez que /run/systemd/resolve/resolv.conf ne doit pas être utilisé directement par les applications, mais uniquement via un lien symbolique depuis /etc/resolv.conf. Si ce mode de fonctionnement est utilisé, les clients locaux qui contournent toute API DNS locale contourneront également systemd-resolved et communiqueront directement avec les serveurs DNS connus.
• Alternativement, /etc/resolv.conf peut être géré par d'autres paquets, auquel cas systemd-resolved le lira pour obtenir des données de configuration DNS. Dans ce mode de fonctionnement, systemd-resolved est un consommateur plutôt qu'un fournisseur de ce fichier de configuration.

Notez que le mode de fonctionnement sélectionné pour ce fichier est détecté de manière entièrement automatique, selon que /etc/resolv.conf est un lien symbolique vers /run/systemd/resolve/resolv.conf ou qu'il liste 127.0.0.53 comme serveur DNS.

SIGNALS

SIGUSR1

Lors de la réception du signal de processus SIGUSR1, systemd-resolved videra le contenu de tous les DN
S record les caches qu'il maintient, ainsi que toutes les informations sur les fonctionnalités qu'il a apprises sur les serveurs DNS configurés dans les journaux système.

Ajouté dans la version 231.

SIGUSR2

À la réception du signal de processus SIGUSR2, systemd-resolved videra tous les caches qu'il maintient. Notez qu'il ne devrait normalement pas être nécessaire de le demander explicitement – sauf à des fins de débogage – car systemd-resolved vide les caches automatiquement de toute façon chaque fois que la configuration réseau de l'hôte change. Envoyer ce signal à systemd-resolved équivaut à la commande resolvectl flush-caches, bien que cette dernière soit recommandée car elle fonctionne de manière synchrone.

Ajouté dans la version 231.

SIGRTMIN+1

À la réception du signal de processus SIGRTMIN+1, systemd-resolved oubliera tout ce qu'il a appris sur les serveurs DNS configurés. Plus précisément, toutes les informations sur la prise en charge des fonctionnalités du serveur seront vidées, et la logique de sondage des fonctionnalités du serveur sera redémarrée lors de la prochaine requête, en commençant par le niveau de fonctionnalités le plus complet. Notez qu'il ne devrait normalement pas être nécessaire de le demander explicitement – sauf à des fins de débogage – car systemd-resolved oublie automatiquement les informations apprises chaque fois que la configuration du serveur DNS change. Envoyer ce signal à systemd-resolved équivaut à la commande resolvectl reset-server-features, bien que cette dernière soit recommandée car elle fonctionne de manière synchrone.

Ajouté dans la version 235.

SIGHUP

À la réception du signal de processus SIGHUP, systemd-resolved videra tous les caches qu'il maintient, abandonnera toutes les connexions TCP ouvertes (le cas échéant) et rechargera ses fichiers de configuration.

Ajouté dans la version 256.

IDENTIFIANTS

systemd-resolved prend en charge la logique des identifiants de service telle qu'implémentée par ImportCredential=/LoadCredential=/SetCredential= (voir systemd.exec(5) pour plus de détails). Les identifiants suivants sont utilisés lorsqu'ils sont transmis :

network.dns, network.search_domains

Peut contenir une liste séparée par des espaces d'adresses IP de serveur DNS et de domaines de recherche DNS. Ces informations ne sont utilisées qu'en l'absence de configuration explicite via /etc/systemd/resolved.conf, /etc/resolv.conf ou la ligne de commande du noyau.

Ajouté dans la version 253.

LIGNE DE COMMANDE DU NOYAU

systemd-resolved respecte également deux options de ligne de commande du noyau :

nameserver=, domain=

Prend l'adresse IP d'un serveur DNS (dans le cas de nameserver=) et un domaine de recherche DNS (dans le cas de domain=). Peut être utilisé plusieurs fois pour définir plusieurs serveurs DNS / domaines de recherche. Si l'une de ces options est spécifiée, /etc/resolv.conf ne sera pas lu et les paramètres DNS= et Domains= de resolved.conf(5) seront ignorés. Ces deux options de ligne de commande du noyau remplacent donc la configuration système.

Ajouté dans la version 253.

PORTS IP

Le service systemd-resolved écoute sur les ports IP suivants :

•Port 53 sur les adresses IPv4 127.0.0.53 et 127.0.0.54 (toutes deux sur l'interface de bouclage locale "lo"). C'est le stub DNS local, comme discuté ci-dessus. UDP et TCP sont couverts.
•Port 5353 sur toutes les adresses locales, IPv4 et IPv6 (0.0.0.0 et ::0), pour MulticastDNS sur UDP. Notez que même si le socket est lié à toutes les interfaces locales via les adresses IP "wildcard" sélectionnées, les datagrammes entrants sont filtrés par l'interface réseau sur laquelle ils arrivent, et des étendues locales distinctes pour MulticastDNS sont maintenues pour chacune, en tenant compte du fait que MulticastDNS est activé ou non pour l'interface.
•Port 5355 sur toutes les adresses locales, IPv4 et IP6 (0.0.0.0 et ::0), pour LLMNR, sur TCP et UDP. Comme pour MulticastDNS, le filtrage par interface réseau entrante est appliqué.

Il existe actuellement plus de 1500 noms de domaine de premier niveau définis, et de nouveaux noms sont ajoutés régulièrement, utilisant souvent des noms "attractifs" qui sont également susceptibles d'être utilisés localement. Ne pas rechercher de noms multi-étiquettes de cette manière évite la fragilité dans les deux sens : un nom global valide pourrait être obscurci par un nom local, et la résolution d'un nom local relatif pourrait soudainement échouer lors de la création d'un nouveau domaine de premier niveau, ou lors de l'enregistrement d'un nouveau sous-domaine d'un domaine de premier niveau. La résolution de n'importe quel nom donné comme relatif ou absolu évite cette ambiguïté.
