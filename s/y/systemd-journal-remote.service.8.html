NOM

systemd-journal-remote.service, systemd-journal-remote.socket, systemd-journal-remote - Recevoir des messages du journal via le réseau

SYNOPIS

systemd-journal-remote.service

systemd-journal-remote.socket

/usr/lib/systemd/systemd-journal-remote [OPTIONS...] [-o/--output=DIR|FICHIER] [SOURCES...]

DESCRIPTION

systemd-journal-remote est une commande pour recevoir des événements de journal sérialisés et les stocker dans des fichiers de journal. Les flux d'entrée sont au format Journal Export Format[1], c'est-à-dire similaire à la sortie de journalctl --output=export. Pour le transport sur le réseau, ce flux sérialisé est généralement transporté via une connexion HTTPS.

systemd-journal-remote.service est un service système qui utilise systemd-journal-remote pour écouter les connexions. systemd-journal-remote.socket configure l'adresse réseau sur laquelle systemd-journal-remote.service écoute. Par défaut, il s'agit du port 19532. Quelles connexions sont acceptées et comment les données reçues sont stockées peuvent être configurés via le fichier de configuration journal-remote.conf(5).

SOURCES

Les sources peuvent être soit "actives" (systemd-journal-remote demande et extrait les données), soit "passives" (systemd-journal-remote attend une connexion et reçoit ensuite les événements poussés par l'autre côté).

systemd-journal-remote peut lire plus d'un flux d'événements à la fois. Ils seront entrelacés dans le fichier de sortie. Dans le cas des connexions "actives", chaque "source" est un flux, et dans le cas des connexions "passives", chaque connexion peut résulter en un flux distinct. Les sockets peuvent être configurés en mode "accept" (c'est-à-dire une seule connexion), ou en mode "listen" (c'est-à-dire plusieurs connexions, chacune résultant en un flux).

Quand il n'y a plus de connexions, et qu'aucune autre ne peut être créée (il n'y a pas de sockets d'écoute), alors systemd-journal-remote se terminera.

Les sources actives peuvent être spécifiées de la manière suivante :

[SOURCES]

Lorsque - est donné comme argument positionnel, les événements seront lus depuis l'entrée standard. D'autres arguments positionnels seront traités comme des noms de fichiers à ouvrir et à lire.

Ajouté en version 239.

--url=ADRESSE

Avec l'option --url=ADRESSE, les événements seront récupérés via HTTP depuis ADRESSE. Cette URL doit pointer vers la racine d'une instance distante de systemd-journal-gatewayd(8), par exemple http://some.host:19531/ ou https://some.host:19531/.

Ajouté en version 239.

--getter='PROG [OPTIONS]'

Programme à invoquer pour récupérer les données. Le flux d'événements du journal doit être généré sur la sortie standard.

Exemples :

--getter='curl "-HAccept: application/vnd.fdo.journal" https://some.host:19531/'
--getter='wget --header="Accept: application/vnd.fdo.journal" -O- https://some.host:19531/'

Ajouté en version 239.

Les sources passives peuvent être spécifiées de la manière suivante :

--listen-raw=ADRESSE

ADRESSE doit être une adresse appropriée pour ListenStream= (cf. systemd.socket(5)). systemd-journal-remote écoutera sur ce socket pour les connexions. Chaque connexion est attendue comme étant un flux d'événements du journal.

Ajouté en version 239.

--listen-http=ADRESSE, --listen-https=ADRESSE

ADRESSE doit être soit un entier négatif, auquel cas il sera interprété comme le descripteur de fichier (numéro) correspondant (mis en négatif), soit une adresse appropriée pour ListenStream= (voir systemd.socket(5)). Dans le premier cas, le serveur écoute par défaut sur le port 19532, et le descripteur de fichier correspondant doit être hérité via $LISTEN_FDS/$LISTEN_PID. Dans le second cas, un serveur HTTP ou HTTPS sera lancé sur ce port, respectivement pour --listen-http= et --listen-https=. Actuellement, seules les requêtes POST vers /upload avec "Content-Type: application/vnd.fdo.journal" sont prises en charge.

Ajouté en version 239.

$LISTEN_FDS

systemd-journal-remote supporte le protocole $LISTEN_FDS/$LISTEN_PID. Les sockets ouverts hérités via l'activation de socket se comportent comme ceux ouverts avec --listen-raw= décrit ci-dessus, sauf s'ils sont spécifiés comme argument dans --listen-http=-n ou --listen-https=-n ci-dessus. Dans ce dernier cas, un serveur HTTP ou HTTPS sera lancé en utilisant ce descripteur et les connexions devront se faire via le protocole HTTP.

Ajouté en version 239.

--key=

Prend un chemin vers un fichier de clé secrète SSL au format PEM. Par défaut, c'est /etc/ssl/private/journal-remote.pem. Cette option peut être utilisée avec --listen-https=. Si le chemin fait référence à un socket de flux AF_UNIX dans le système de fichiers, une connexion est établie avec lui et la clé en est lue.

Ajouté en version 239.

--cert=

Prend un chemin vers un fichier de certificat SSL au format PEM. Par défaut, c'est /etc/ssl/certs/journal-remote.pem. Cette option peut être utilisée avec --listen-https=. Si le chemin fait référence à un socket de flux AF_UNIX dans le système de fichiers, une connexion est établie avec lui et le certificat en est lu.

Ajouté en version 239.

--trust=

Prend un chemin vers un fichier de certificat CA SSL au format PEM, ou all. Si all est défini, la vérification du certificat sera désactivée. Par défaut, c'est /etc/ssl/ca/trusted.pem. Cette option peut être utilisée avec --listen-https=. Si le chemin fait référence à un socket de flux AF_UNIX dans le système de fichiers, une connexion est établie avec lui et le certificat en est lu.

Ajouté en version 239.

--gnutls-log=

Prend une liste de catégories de journalisation gnutls séparées par des virgules. Cette option peut être utilisée avec --listen-http= ou --listen-https=.

Ajouté en version 239.

PUITS

L'emplacement du journal de sortie peut être spécifié avec -o ou --output=.

-o FICHIER, --output=FICHIER

Écrira dans ce fichier journal. Le nom de fichier doit se terminer par .journal. Le fichier sera créé s'il n'existe pas. Si nécessaire (journal plein ou corrompu), le fichier sera renommé en suivant les règles normales de journald et un nouveau fichier journal sera créé à sa place.

Ajouté en version 239.

-o DIR, --output=DIR

Créera des fichiers journaux dans le répertoire DIR. Le répertoire doit exister. Si nécessaire (fichiers journaux trop grands ou corrompus), les fichiers journaux seront mis en rotation en suivant les règles normales de journald. Les noms des fichiers sous DIR seront générés selon les règles décrites ci-dessous.

Ajouté en version 239.

Si --output= n'est pas utilisé, le répertoire de sortie /var/log/journal/remote/ sera utilisé. Dans le cas où le fichier de sortie n'est pas spécifié, les fichiers journaux seront créés sous le répertoire sélectionné. Les fichiers seront nommés remote-nomhôte.journal, où la partie nomhôte est le nom d'hôte échappé du point d'extrémité source de la connexion, ou l'adresse numérique si le nom d'hôte ne peut pas être déterminé.

Dans le cas où des sources "actives" sont fournies par les arguments positionnels ou l'option --getter=, le nom du fichier de sortie doit toujours être donné explicitement.

OPTIONS

Les options suivantes sont comprises :

--split-mode

Une de none ou host. Pour la première, un seul fichier journal de sortie est utilisé. Pour la seconde, un fichier de sortie séparé est utilisé, basé sur le nom d'hôte du point d'extrémité de la connexion.

systemd-journal-remote.service(8) — systemd manual pages

NAME

systemd-journal-remote.service, systemd-journal-remote - Relay journal messages to a remote systemd-journal-remote daemon or listen for journal exports

SYNOPSIS

 systemd-journal-remote [OPTIONS...] [URL...]

DESCRIPTION

systemd-journal-remote is a systemd service that accepts journal data from remote systems and forwards it to the local journal, or forwards local journal data to a remote system.

It may be configured to listen for journal data to be pushed to it, or to connect to remote journal gateway instances and pull journal data from them. In the latter case, it acts as a client to systemd-journal-gatewayd.service(8).

The service may be configured with the journal-remote.conf(5) file.

SOURCES

The service may be configured to obtain journal data from various sources:

URL input

The service may be started with one or more URLs on the command line or in the configuration file. The URLs are used to pull journal data from remote systems. Typically, these URLs point to a systemd-journal-gatewayd.service(8) instance.

The following URL schemes are supported:

http://, https://
Connect to a journal gateway. The gateway address must be followed by an optional path and query parameters. See systemd-journal-gatewayd.service(8) for a description of supported query parameters. If no path is specified, / is used, which is equivalent to /entries.
fd://
Connect to a journal gateway using a file descriptor passed via socket activation. This is typically used when systemd itself invokes the journal gateway daemon.

UDP input

If the socket option is set in the configuration file, the service will listen on the specified UDP port for journal data.

SINKS

The service may be configured to write received journal data to a local file:

File output

When using the journalctl(1) -o export output format (which is the default when reading from a URL or UDP), the received journal data is written to a file. The output file name must be specified using the --output-file= option or the second command line argument.

If the output file name is -, data is sent to standard output.

If the output file name is none, the data is discarded.

Note: Only one output file may be specified.

OPTIONS

The following options are understood:

--log-target=DEST

Sets the default logging destination. See systemd-journald.service(8).

Added in version 258.

--listen-http=ADDRESS

Listen on the given TCP ADDRESS for incoming HTTP connections using the journal export protocol. This is useful for remote journal hosts to push data to this machine.

Added in version 231.

--listen-udp=ADDRESS

Listen on the given UDP ADDRESS for incoming journal export datagrams. This is useful for remote journal hosts to push data to this machine.

Added in version 231.

--output-file=FILE

Writes the received journal data to the specified FILE. If - is given, writes to standard output. If none is given, discards the data.

If this option is used, any positional argument is ignored. If this option is not used, the first positional argument is taken as the output file name.

This option was added in version 239.

--url=URL

Connect to the journal gateway specified by URL and retrieve journal data. This option may be used multiple times to connect to multiple gateways. If this option is used, any positional arguments are ignored.

This option was added in version 239.

--compress [BOOL]

If this is set to "yes" then compress the data in the journal using XZ. The default is "yes".

Added in version 239.

--seal [BOOL]

If this is set to "yes" then periodically sign the data in the journal using Forward Secure Sealing. The default is "no".

Added in version 239.

-h, --help

Print a short help text and exit.

--version

Print a short version string and exit.

EXAMPLES

Copy local journal events to a different journal directory:

 journalctl -o export | systemd-journal-remote -o /tmp/dir/foo.journal -

Retrieve all available events from a remote systemd-journal-gatewayd.service(8) instance and store them in /var/log/journal/remote/remote-some.host.journal:

 systemd-journal-remote --url http://some.host:19531/

Retrieve current boot events and wait for new events from a remote systemd-journal-gatewayd.service(8) instance, and store them in /var/log/journal/remote/remote-some.host.journal:

 systemd-journal-remote --url http://some.host:19531/entries?boot&follow

journal-remote.conf(5), journalctl(1), systemd-journal-gatewayd.service(8), systemd-journal-upload.service(8), systemd-journald.service(8)

NOM

systemd-journal-remote.service, systemd-journal-remote - Relayer les messages du journal à un démon systemd-journal-remote distant ou écouter les exportations du journal

SYNOPSIS

 systemd-journal-remote [OPTIONS...] [URL...]

DESCRIPTION

systemd-journal-remote est un service systemd qui accepte les données du journal provenant de systèmes distants et les transmet au journal local, ou transmet les données du journal local à un système distant.

Il peut être configuré pour écouter les données du journal qui lui sont envoyées, ou pour se connecter à des instances distantes de journal gateway et en extraire les données du journal. Dans ce dernier cas, il agit comme un client de systemd-journal-gatewayd.service(8).

Le service peut être configuré à l'aide du fichier journal-remote.conf(5).

SOURCES

Le service peut être configuré pour obtenir les données du journal à partir de diverses sources :

Entrée URL

Le service peut être démarré avec une ou plusieurs URL sur la ligne de commande ou dans le fichier de configuration. Les URL sont utilisées pour extraire les données du journal des systèmes distants. Typiquement, ces URL pointent vers une instance de systemd-journal-gatewayd.service(8).

Les schémas d'URL suivants sont pris en charge :

http://, https://
Se connecter à un journal gateway. L'adresse du gateway doit être suivie d'un chemin optionnel et de paramètres de requête. Voir systemd-journal-gatewayd.service(8) pour une description des paramètres de requête pris en charge. Si aucun chemin n'est spécifié, / est utilisé, ce qui est équivalent à /entries.
fd://
Se connecter à un journal gateway en utilisant un descripteur de fichier passé via l'activation par socket. Ceci est généralement utilisé lorsque systemd lui-même invoque le démon de journal gateway.

Entrée UDP

Si l'option socket est définie dans le fichier de configuration, le service écoutera sur le port UDP spécifié pour les données du journal.

PUITS

Le service peut être configuré pour écrire les données du journal reçues dans un fichier local :

Sortie fichier

Lors de l'utilisation du format de sortie journalctl(1) -o export (qui est le défaut lors de la lecture depuis une URL ou UDP), les données du journal reçues sont écrites dans un fichier. Le nom du fichier de sortie doit être spécifié à l'aide de l'option --output-file= ou du second argument de la ligne de commande.

Si le nom du fichier de sortie est -, les données sont envoyées à la sortie standard.

Si le nom du fichier de sortie est none, les données sont ignorées.

Note : Un seul fichier de sortie peut être spécifié.

OPTIONS

Les options suivantes sont comprises :

--log-target=DEST

Définit la destination de journalisation par défaut. Voir systemd-journald.service(8).

Ajouté dans la version 258.

--listen-http=ADDRESS

Écoute sur le ADDRESS TCP donné pour les connexions HTTP entrantes utilisant le protocole d'exportation du journal. Ceci est utile pour que les hôtes de journal distants poussent des données vers cette machine.

Ajouté dans la version 231.

--listen-udp=ADDRESS

Écoute sur le ADDRESS UDP donné pour les datagrammes d'exportation du journal entrants. Ceci est utile pour que les hôtes de journal distants poussent des données vers cette machine.

Ajouté dans la version 231.

--output-file=FICHIER

Écrit les données du journal reçues dans le FICHIER spécifié. Si - est donné, écrit sur la sortie standard. Si none est donné, ignore les données.

Si cette option est utilisée, tout argument positionnel est ignoré. Si cette option n'est pas utilisée, le premier argument positionnel est pris comme nom de fichier de sortie.

Cette option a été ajoutée dans la version 239.

--url=URL

Se connecte au journal gateway spécifié par URL et récupère les données du journal. Cette option peut être utilisée plusieurs fois pour se connecter à plusieurs gateways. Si cette option est utilisée, les arguments positionnels sont ignorés.

Cette option a été ajoutée dans la version 239.

--compress [BOOL]

Si ceci est défini à "yes", alors compresse les données dans le journal en utilisant XZ. Le défaut est "yes".

Ajouté dans la version 239.

--seal [BOOL]

Si ceci est défini à "yes", alors signe périodiquement les données dans le journal en utilisant Forward Secure Sealing. Le défaut est "no".

Ajouté dans la version 239.

-h, --help

Imprime un court texte d'aide et quitte.

--version

Imprime une courte chaîne de version et quitte.

EXEMPLES

Copier les événements du journal local vers un répertoire de journal différent :

 journalctl -o export | systemd-journal-remote -o /tmp/dir/foo.journal -

Récupérer tous les événements disponibles d'une instance distante de systemd-journal-gatewayd.service(8) et les stocker dans /var/log/journal/remote/remote-some.host.journal :

 systemd-journal-remote --url http://some.host:19531/

Récupérer les événements de démarrage actuels et attendre de nouveaux événements d'une instance distante de systemd-journal-gatewayd.service(8), et les stocker dans /var/log/journal/remote/remote-some.host.journal :

 systemd-journal-remote --url http://some.host:19531/entries?boot&follow
