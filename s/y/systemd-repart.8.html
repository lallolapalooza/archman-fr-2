SYSTEMD-REPART(8) systemd-repart SYSTEMD-REPART(8)

NOM

systemd-repart, systemd-repart.service - Grow and add partitions, and generate disk images (DDIs) automatically

SYNOPSIS

systemd-repart [OPTIONS...] [[BLOCKDEVICE]...]

systemd-repart.service

DESCRIPTION

systemd-repart crée des tables de partitions, et ajoute ou agrandit des partitions, sur la base des fichiers de configuration décrits dans repart.d(5).

systemd-repart est utilisé lors de la construction d'images de système d'exploitation, ainsi que lors du déploiement d'images pour les ajuster automatiquement, au démarrage, au système sur lequel elles s'exécutent. De cette façon, l'image peut être de taille minimale et peut être augmentée automatiquement au démarrage, prenant possession de l'espace disque disponible.

S'il est appelé sans arguments, systemd-repart opère sur le périphérique bloc supportant la partition du système de fichiers racine du système d'exploitation en cours d'exécution, ajoutant et agrandissant ainsi les partitions du système d'exploitation démarré lui-même. Lorsqu'il est appelé dans l'initrd, il opère sur le périphérique bloc supportant /sysroot/ à la place, c'est-à-dire sur le périphérique bloc dans lequel le système basculera bientôt. Si --image= est utilisé, il opérera sur le périphérique ou le fichier image spécifié. Le service systemd-repart.service est généralement exécuté au démarrage dans l'initrd, afin d'augmenter la table de partitions du système d'exploitation avant que ses partitions ne soient montées.

Les opérations de systemd-repart sont majoritairement incrémentales : il agrandit les partitions existantes ou en ajoute de nouvelles, mais ne réduit, ne supprime ou ne déplace pas les partitions existantes. Le service est destiné à être exécuté à chaque démarrage, mais lorsqu'il détecte que la table de partitions correspond déjà à la configuration des fichiers repart.d/*.conf installés, il n'exécute aucune opération.

Les cas d'utilisation suivants font partie de ceux couverts :

•La partition racine peut être agrandie pour couvrir tout l'espace disque disponible.
•Une partition /home/, swap, ou /srv/ peut être ajoutée.
•Une deuxième (ou troisième, ...) partition racine peut être ajoutée, pour couvrir des configurations de type A/B où une deuxième version du système de fichiers racine est alternativement utilisée pour implémenter des schémas de mise à jour. L'image déployée ne contiendrait qu'une seule partition ("A") mais lors du premier démarrage, une deuxième partition ("B") à cet effet serait automatiquement créée.

L'algorithme exécuté par systemd-repart est approximativement le suivant :

1.Les fichiers de configuration repart.d/*.conf sont chargés et analysés, et ordonnés par nom de fichier (sans le préfixe du répertoire). Pour chaque fichier de configuration, les fichiers de remplacement sont chargés à partir des répertoires portant le même nom que le fichier de configuration avec le suffixe ".d" ajouté.
2.La table de partitions sur le périphérique bloc est chargée et analysée, si présente.
3.Les partitions existantes dans la table de partitions sont mises en correspondance avec les fichiers repart.d/*.conf par l'UUID du type de partition GPT. La première partition existante d'un type spécifique est assignée au premier fichier de configuration déclarant le même type. La deuxième partition existante d'un type spécifique est alors assignée au deuxième fichier de configuration déclarant le même type, et ainsi de suite. Une fois cette assignation itérative terminée, toutes les partitions existantes qui n'ont pas de fichier de configuration correspondant sont considérées comme "étrangères" et laissées telles quelles. Et tous les fichiers de configuration pour lesquels aucune partition n'a été trouvée sont traités comme des demandes de création de partition.
4.Les partitions qui doivent être créées sont maintenant allouées sur le disque, en tenant compte des contraintes de taille et des poids déclarés dans les fichiers de configuration. L'espace libre est utilisé dans les limites fixées par les requêtes de taille et de remplissage. De plus, les partitions existantes qui doivent être agrandies sont agrandies. Les nouvelles partitions sont toujours ajoutées à la fin de la table de partitions, occupant le premier emplacement de la table de partitions dont l'index est supérieur aux index de toutes les partitions existantes. Les partitions ne sont jamais réordonnées et par conséquent les numéros de partitions restent stables. Lorsque des partitions sont créées, elles sont placées dans la plus petite zone d'espace libre suffisamment grande pour satisfaire les limites de taille et de remplissage. Cela signifie que les partitions peuvent avoir un ordre différent sur le disque que dans la table de partitions. Notez que cette allocation se fait uniquement en mémoire, la table de partitions sur le disque n'est pas encore mise à jour.
5.Toutes les partitions existantes pour lesquelles des fichiers de configuration existent et qui n'ont actuellement aucun libellé GPT défini se verront attribuer un libellé, soit explicitement configuré dans la configuration, soit — si cela manque — dérivé automatiquement du type de partition. Il en va de même pour toutes les partitions nouvellement créées. Ces attributions se font uniquement en mémoire, le disque n'est pas encore mis à jour.
6.De même, toutes les partitions existantes pour lesquelles des fichiers de configuration existent et qui ont actuellement un UUID d'identification composé uniquement de zéros se verront attribuer un nouvel UUID. Cet UUID est calculé par hachage cryptographique à partir d'une valeur de germe commune, conjointement avec l'UUID du type de partition (et un compteur au cas où plusieurs partitions du même type sont définies), voir ci-dessous. Il en va de même pour toutes les partitions nouvellement créées. Ces attributions se font uniquement en mémoire, le disque n'est pas encore mis à jour.
7.De même, si l'UUID du volume du disque est composé uniquement de zéros, il est également initialisé, également calculé par hachage cryptographique à partir de la même valeur de germe commune. Ceci est également fait uniquement en mémoire.
8.L'espace disque attribué aux nouvelles partitions (c'est-à-dire ce qui était auparavant de l'espace libre) est maintenant effacé. Plus précisément, toutes les signatures de système de fichiers sont supprimées et, si le périphérique le supporte, la commande de contrôle d'E/S BLKDISCARD est émise pour informer le matériel que l'espace est maintenant vide. De plus, tout "remplissage" entre les partitions et à la fin du périphérique est de même effacé.
9.La nouvelle table de partitions est finalement écrite sur le disque. Le noyau est invité à relire la table de partitions.

À titre d'exception à l'opération incrémentale normale, lorsqu'il est appelé dans un mode spécial de "réinitialisation d'usine", systemd-repart peut être utilisé pour effacer les partitions existantes afin de ramener une installation aux valeurs par défaut du fabricant. Ce mode de fonctionnement est utilisé lorsque le commutateur --factory-reset=yes est passé sur la ligne de commande de l'outil, ou lorsque l'option systemd.factory_reset=yes est spécifiée sur la ligne de commande du noyau, ou lorsque la variable EFI FactoryResetRequest (UUID du fournisseur 8cf2644b-4b0b-428f-9387-6d876050dc67) est définie sur "yes". Il modifie légèrement l'algorithme ci-dessus : entre la 3ème et la 4ème étape ci-dessus, toute partition marquée explicitement via le booléen FactoryReset= est supprimée, et l'algorithme redémarre, recréant ainsi immédiatement ces partitions vides.

Notez que systemd-repart ne modifie par défaut que les tables de partitions, il ne crée ni ne redimensionne de systèmes de fichiers dans ces partitions, sauf si l'option Format= est spécifiée. Notez également qu'il existe des mécanismes distincts à cette fin, par exemple systemd-growfs(8) et systemd-makefs.

Les UUID identifiant les nouvelles partitions créées (ou assignées aux partitions existantes qui n'ont pas encore d'UUID), ainsi que le disque dans son ensemble sont hachés cryptographiquement à partir d'une valeur de germe commune. Cette valeur de germe est généralement le machine-id(5) du système, de sorte que l'ID de machine détermine de manière reproductible les UUID assignés à toutes les partitions. Si l'ID de machine ne peut être lu (ou si l'utilisateur passe --seed=random, voir ci-dessous), le germe est généré aléatoirement à la place, de sorte que les UUID des partitions sont également effectivement aléatoires. La valeur du germe peut également être définie explicitement, formatée en UUID via l'option --seed=. En hachant ces UUID à partir d'un germe commun, les images préparées avec cet outil deviennent reproductibles et le résultat de l'algorithme ci-dessus déterministe.

L'argument positionnel doit spécifier le périphérique bloc ou un fichier ordinaire sur lequel opérer. Si --empty=create est spécifié, le chemin spécifié est créé comme un fichier ordinaire, ce qui est utile pour générer des images disque à partir de zéro.

Prend une valeur booléenne. Si ce commutateur n'est pas spécifié, --dry-run=yes est l'option par défaut. Sauf si --dry-run=no est spécifié, systemd-repart ne touchera pas réellement la table de partitions du périphérique.

Si "refuse", systemd-repart exige que le périphérique de bloc sur lequel il doit opérer porte déjà une table de partitions et refuse l'opération si aucune n'est trouvée. Si "allow", la commande étend une table de partitions existante ou en crée une nouvelle si aucune n'existe. Si "require", la commande crée une nouvelle table de partitions si aucune n'existe jusqu'à présent et refuse l'opération si une existe déjà. Si "force", elle crée une nouvelle table de partitions sans condition, effaçant ainsi complètement le disque. Si "force", aucune partition existante ne sera prise en compte ou ne survivra à l'opération. Par conséquent : à utiliser avec précaution, c'est un excellent moyen de perdre toutes vos données. Si "create", un nouveau fichier de boucle est créé sous le chemin passé via le paramètre de nœud de périphérique, de la taille indiquée avec --size=, voir ci-dessous.

Ajouté en version 245.

--discard=

Prend une valeur booléenne. Si ce commutateur n'est pas spécifié, --discard=yes est la valeur par défaut implicite. Contrôle s'il faut émettre la commande de contrôle d'E/S BLKDISCARD sur l'espace occupé par les partitions ajoutées ou sur l'espace entre elles. Généralement, il est bon d'émettre cette requête car elle indique au matériel sous-jacent que les blocs couverts doivent être considérés comme vides, améliorant ainsi les performances. Si l'on opère sur un fichier régulier au lieu d'un nœud de périphérique de bloc, un fichier éparse est généré.

Ajouté en version 245.

--size=

Prend une taille en octets, en utilisant les suffixes habituels K, M, G, T, ou la valeur spéciale "auto". Si utilisé, le chemin du nœud de périphérique spécifié doit faire référence à un fichier régulier, qui est ensuite agrandi à la taille spécifiée s'il est plus petit, avant toute modification de la table de partitions. Si spécifié comme "auto", la taille minimale de l'image disque est déterminée automatiquement (c'est-à-dire que les tailles minimales de toutes les partitions sont additionnées, en tenant compte de l'espace pour les métadonnées supplémentaires). Ce commutateur n'est pas pris en charge si le nœud spécifié est un périphérique de bloc. Ce commutateur n'a aucun effet si le fichier est déjà aussi grand que la taille spécifiée ou plus grand. La taille spécifiée est implicitement arrondie à des multiples de 4096. Lorsqu'elle est utilisée avec --empty=create, elle spécifie la taille initiale du fichier de boucle à créer.

L'option --size=auto prend en compte les tailles des partitions préexistantes. Cependant, elle ne tient pas compte des tables de partitions qui ne sont pas compactes : les partitions configurées pourraient toujours ne pas tenir dans le périphérique sous-jacent s'il existe de l'espace vide entre les partitions préexistantes (ou avant la première partition) qui ne peut pas être entièrement rempli par les partitions à agrandir ou à créer.

Notez également que la détermination automatique de la taille ne tient pas compte des fichiers ou répertoires spécifiés avec CopyFiles= : l'opération pourrait échouer si les fichiers ou répertoires spécifiés nécessitent plus d'espace disque que la limite de taille minimale par partition configurée.

Ajouté en version 246.

--factory-reset=

Prend une valeur booléenne. Si ce commutateur n'est pas spécifié, --factory-reset=no est la valeur par défaut implicite. Contrôle si l'on opère en mode "réinitialisation d'usine", voir ci-dessus. Si défini sur vrai, cela supprimera toutes les partitions existantes marquées avec FactoryReset= défini sur oui tôt dans l'exécution de l'algorithme de repartitionnement. À utiliser avec précaution, c'est un excellent moyen de perdre toutes vos données. Notez que les fichiers de partition doivent explicitement activer FactoryReset=, car l'option est désactivée par défaut. Si aucune partition n'est marquée pour la réinitialisation d'usine, ce commutateur n'a aucun effet. Notez qu'il existe deux autres méthodes pour demander une opération de réinitialisation d'usine : via la ligne de commande du noyau et via une variable EFI, voir ci-dessus.

Ajouté en version 245.

--can-factory-reset

Si ce commutateur est spécifié, le disque n'est pas repartitionné. Au lieu de cela, il est déterminé si des partitions existantes sont marquées avec FactoryReset=. Si c'est le cas, l'outil se terminera avec le statut de sortie zéro, sinon non-zéro. Ce commutateur peut être utilisé pour déterminer rapidement si le système en cours prend en charge un mécanisme de réinitialisation d'usine basé sur systemd-repart.

Ajouté en version 245.

--root=

Prend un chemin vers un répertoire à utiliser comme système de fichiers racine lors de la recherche des fichiers repart.d/*.conf, pour le fichier ID de la machine à utiliser comme amorce et pour les fichiers et répertoires sources de CopyFiles= et CopyBlocks=. Par défaut, lorsqu'il est appelé sur le système régulier, il est défini sur le système de fichiers racine de l'hôte /. S'il est appelé depuis l'initrd, il est défini sur /sysroot/, de sorte que l'outil opère sur la configuration et l'ID de la machine stockés dans le système de fichiers racine qu'il utilise ensuite.

Voir --copy-source= pour une option plus restreinte qui n'affecte que CopyFiles=.

Ajouté en version 245.

--image=

Prend un chemin vers un fichier image disque ou un périphérique à monter et à utiliser de manière similaire à --root=, voir ci-dessus.

Ajouté en version 249.

--image-policy=policy

--key-file=

Prend un chemin de système de fichiers. Configure la clé de chiffrement à utiliser lors de la configuration de volumes LUKS2 configurés avec le paramètre Encrypt=key-file dans les fichiers de partition. Doit faire référence à un fichier régulier contenant la clé, ou à un socket de flux AF_UNIX dans le système de fichiers. Dans ce dernier cas, une connexion y est établie et la clé en est lue. Ce comportement est utile pour configurer des partitions chiffrées lors du premier démarrage, qui ne recevront leur mot de passe fourni par l'utilisateur que lors d'une étape de configuration ultérieure.

Si --exclude-partitions= est utilisé, toutes les partitions spécifiées sont exclues. Cette option spécifie pour quels types de partitions systemd-repart doit reporter. L'effet net de cette option est que si vous exécutez systemd-repart à nouveau sans cette option, les partitions manquantes seront ajoutées comme si elles n'avaient pas été reportées la première fois que systemd-repart a été exécuté.

Ajouté dans la version 253.

Cette option permet de remplacer l'architecture utilisée pour les types de partitions spécifiques à l'architecture. Par exemple, si défini sur "arm64", un type de partition "root-x86-64" référencé dans les drop-ins repart.d/ sera patché dynamiquement pour faire référence à "root-arm64" à la place. Prend l'une des valeurs : "alpha", "arc", "arm", "arm64", "ia64", "loongarch64", "mips-le", "mips64-le", "parisc", "ppc", "ppc64", "ppc64-le", "riscv32", "riscv64", "s390", "s390x", "tilegx", "x86" ou "x86-64".

--offline=BOOL

Indique à systemd-repart de construire l'image hors ligne. Prend une valeur booléenne ou "auto". Par défaut "auto". Si activé, l'image est construite sans utiliser de périphériques loop. Ceci est utile pour construire des images sans privilèges ou lorsque les périphériques loop ne sont pas disponibles. Si désactivé, l'image est toujours construite en utilisant des périphériques loop. Si "auto", systemd-repart construira l'image en ligne si possible et se rabattra sur la construction hors ligne si les périphériques loop ne sont pas disponibles ou ne peuvent pas être accédés en raison de permissions manquantes.

Ajouté dans la version 254.

--copy-from=PATH

Indique à systemd-repart de synthétiser des définitions de partitions à partir de la table des partitions dans l'image ou le périphérique donné. Les définitions générées copieront les partitions dans la table des partitions de destination. Les partitions copiées auront la même taille, les mêmes métadonnées et le même contenu, mais pourraient avoir un numéro de partition différent et pourraient être situées à un décalage différent dans la table des partitions de destination. Ces définitions peuvent être combinées avec des définitions de partitions lues à partir de fichiers de définition de partitions réguliers. Prend l'une des valeurs "sysext", "confext" ou "portable". Génère une image de disque découvrable (DDI) pour une extension système (sysext, voir systemd-sysext(8) pour les détails), une extension de configuration (confext) ou des Services Portables[1]. --append-fstab=

Si "auto", systemd-repart recherchera dans le fichier préexistant la section qui appartient au contenu généré automatiquement et la remplacera par le contenu généré le plus récent, tout en conservant la section fournie par l'utilisateur s'il y en a une. La section générée est identifiée en recherchant le contenu automatique entouré par "# Start section ↓ of automatically generated fstab by systemd-repart" et "# End section ↑ of automatically generated fstab by systemd-repart". Le contenu qui précède et suit ces commentaires est considéré comme fourni par l'utilisateur et est conservé dans le nouveau fichier.

NOM

systemd-repart ‐ Créer des partitions et des systèmes de fichiers avec métadonnées systemd-fstab

SYNOPSIS

systemd-repart [OPTION…] [‑r|‑r PÉRIPHÉRIQUE…]

DESCRIPTION

La commande systemd-repart peut être utilisée pour créer ou mettre à jour un schéma de partitionnement et des systèmes de fichiers sur des périphériques de stockage. Elle lit les fichiers de configuration de partitionnement trouvés dans le répertoire /etc/repart.d/, dans le répertoire .d/ de l'un des répertoires listés dans le chemin repart.d=, ou des paramètres de ligne de commande, pour déterminer comment les partitions et les systèmes de fichiers doivent être créés.

Le but principal de systemd-repart est de créer des images de système d'exploitation portables, mais il peut être utilisé pour configurer n'importe quel périphérique de stockage. Pour les systèmes d'exploitation portables, les informations sur les partitions et les systèmes de fichiers sont généralement stockées dans des fichiers .sysext (voir systemd.unit(5)) ou directement dans l'image de disque, et peuvent être appliqués et utilisés avec systemd-sysext(8).

La commande systemd-repart peut être appelée sans aucun argument de ligne de commande. Dans ce cas, elle recherche les fichiers de configuration dans /etc/repart.d/, puis dans le répertoire .d/ de chaque répertoire listé dans le chemin repart.d=. Si aucun chemin repart.d= n'est défini, elle recherche /etc/repart.d/ et /usr/lib/repart.d/.

Si un ou plusieurs arguments de périphérique sont fournis, systemd-repart les utilise comme cibles. Sinon, elle utilise les périphériques listés dans /etc/kernel/cmdline ou /proc/cmdline correspondant aux entrées de type root=, usr=, usr-verity= ou var-verity=.

Les fichiers de configuration sont écrits dans un format INI et contiennent des sections [Partition]. Chaque section décrit une partition ou un système de fichiers à créer. Les options suivantes sont prises en charge dans la section [Partition]:

Type=
Spécifie le type de partition ou de système de fichiers. Les types courants incluent :
root
Partition racine du système d'exploitation.
usr
Partition pour /usr.
usr-verity
Partition système de fichiers chiffrée avec dm-verity pour /usr.
usr-verity-hash
Partition pour le contenu du système de fichiers de hachage de dm-verity pour /usr.
usr-verity-sig
Partition pour la signature dm-verity de /usr.
var
Partition pour /var.
home
Partition pour /home.
boot
Partition pour /boot.
efi
Partition système EFI.
esp
Partition système EFI.
swap
Partition d'échange.
state
Partition pour les données d'état.
tmpfs
Système de fichiers temporaire en mémoire.
alloc
Partition libre à allouer.
copy
Copier le contenu d'une autre partition.
verity
Partition chiffrée avec dm-verity.
verity-hash
Partition pour le contenu du système de fichiers de hachage dm-verity.
verity-sig
Partition pour la signature dm-verity.
Label=
Spécifie l'étiquette de la partition ou du système de fichiers. Peut utiliser des substitutions comme %o (OS ID), %w (OS Version) et %p (Type de partition).
Format=
Spécifie le format du système de fichiers (par exemple, ext4, xfs, btrfs, vfat, erofs). Par défaut, ext4 est utilisé.
SizeMinBytes=
Taille minimale de la partition en octets.
SizeMaxBytes=
Taille maximale de la partition en octets.
SizeDefault=
Taille par défaut de la partition en octets.
Grow=
Spécifie si la partition doit s'agrandir pour remplir l'espace disponible.
Verity=
Spécifie le niveau de vérification dm-verity pour la partition (par exemple, data, hash, signature).
VerityMatchKey=
Spécifie la clé de correspondance pour la vérification dm-verity.
RootHash=
Spécifie le hachage racine pour la vérification dm-verity.
CopyFrom=
Spécifie le chemin de la partition source à copier.
Source=
Spécifie le chemin du contenu à copier dans la partition.
Empty=
Spécifie comment gérer une partition vide. Les options sont create, skip.

OPTIONS

Les options suivantes sont comprises par systemd-repart:

‑‑definitions=FICHIERS
Spécifie un ou plusieurs fichiers de configuration de partitionnement à lire. Les chemins peuvent être séparés par des deux-points.
‑‑copy-source=RÉPERTOIRE
Copie le contenu du répertoire spécifié dans la partition créée. Utile pour les partitions root ou usr.
‑‑empty=MODE
Définit comment gérer les partitions vides. Les modes possibles sont create et skip.
‑‑dry-run
Ne crée aucune partition ni aucun système de fichiers, mais affiche ce qui serait fait.
‑‑json=FORMAT
Affiche les informations sur les partitions créées au format JSON. Les formats possibles sont short et full.
‑‑join-signature=CHEMINS
Joint une signature dm-verity à une partition existante. Les chemins doivent être au format hachage:signature.
‑‑private-key-source=SOURCE
Source de la clé privée pour la signature dm-verity.
‑‑private-key=CHEMIN
Chemin vers la clé privée pour la signature dm-verity.
‑‑certificate=CHEMIN
Chemin vers le certificat pour la signature dm-verity.
‑‑defer-partitions=LISTE
Spécifie les partitions qui doivent être créées après toutes les autres.
‑‑make-ddi=MODE
Spécifie le mode de création de l'image DDI (Disk Device Image) pour les services portables.
‑‑size=TAILLE
Taille totale de l'image disque à créer.
-r, ‑‑root=PÉRIPHÉRIQUE
Spécifie le périphérique racine à utiliser. Peut être spécifié plusieurs fois.

STATUT DE SORTIE

Retourne 0 si toutes les opérations ont réussi, une valeur d'erreur non nulle sinon.

EXEMPLE

Exemple 1. Création d'une image système d'exploitation portable avec dm-verity

Cet exemple crée une image système d'exploitation portable avec une partition racine chiffrée dm-verity.

mkdir -p tree/usr/lib/
cat >tree/usr/lib/extension-release.d/extension-release.my-os <<EOF
ID=fedora
VERSION_ID=38
EOF
cat >repart.d/10-root.conf <<EOF
[Partition]
Type=root
Format=ext4
SizeMinBytes=100M
SizeMaxBytes=100M
Verity=data
VerityMatchKey=root
EOF
cat >repart.d/11-root-verity.conf <<EOF
[Partition]
Type=root-verity
Label=%o_%w_verity
Verity=hash
VerityMatchKey=root
SizeMinBytes=400M
SizeMaxBytes=400M
EOF
cat >repart.d/12-root-verity-sig.conf <<EOF
[Partition]
Type=root-verity-sig
Label=%o_%w_verity_sig
Verity=signature
VerityMatchKey=root
EOF
systemd-repart --definitions=repart.d \
  --copy-source=tree/ \
  --empty=create --size=600M \
  --json=short \
  /tmp/my-os.sysext.raw

L'image résultante /tmp/my-os.sysext.raw peut être appliquée au système avec systemd-sysext(8).

Exemple 2. Création d'une image système d'exploitation portable hors ligne

Cet exemple crée une image système d'exploitation portable qui est ensuite signée hors ligne. La signature est ajoutée à l'image.

mkdir -p tree/usr/lib/
cat >tree/usr/lib/extension-release.d/extension-release.my-foo <<EOF
ID=fedora
VERSION_ID=38
IMAGE_ID=my-foo
IMAGE_VERSION=7
EOF
systemd-repart --make-ddi=sysext \
  --private-key-source=engine:pkcs11 \
  --private-key="pkcs11:model=PKCS%2315%20emulated;manufacturer=piv_II;serial=0123456789abcdef;token=Some%20Cert" \
  --certificate=verity-certificate.pem \
  -s tree/ \
  /var/lib/extensions/my-foo.sysext.raw
systemd-sysext refresh

Le DDI généré de cette manière peut être appliqué au système avec systemd-sysext(8).

Exemple 3. Génération d'une signature dm-verity hors ligne et ajout à une image pré-construite

Ce qui suit crée une image avec des métadonnées dm-verity, la signe séparément pour simuler un système de signature hors ligne, puis ajoute la signature à l'image :

mkdir -p repart.d/ /tmp/tree/usr/lib/
cat >/tmp/tree/usr/lib/os-release <<EOF
ID=debian
VERSION_ID=13
EOF
cat >repart.d/10-root.conf <<EOF
[Partition]
Type=root
Format=erofs
SizeMinBytes=100M
SizeMaxBytes=100M
Verity=data
VerityMatchKey=root
EOF
cat >repart.d/11-root-verity.conf <<EOF
[Partition]
Type=root-verity
Label=%o_%w_verity
Verity=hash
VerityMatchKey=root
SizeMinBytes=400M
SizeMaxBytes=400M
EOF
cat >repart.d/12-root-verity-sig.conf <<EOF
[Partition]
Type=root-verity-sig
Label=%o_%w_verity_sig
Verity=signature
VerityMatchKey=root
EOF
systemd-repart --definitions repart.d \
  --defer-partitions=root-verity-sig \
  --copy-source=/tmp/tree/ \
  --empty=create --size=600M \
  --json=short \
  /tmp/img.raw | | jq --raw-output0 .[-1].roothash > /tmp/img.roothash
openssl smime -sign -in /tmp/img.roothash \
  -inkey verity-private-key.pem \
  -signer verity-certificate.pem \
  -noattr -binary -outform der \
  -out /tmp/img.roothash.p7s
systemd-repart --definitions repart.d \
  --dry-run=no --root=/tmp/tree/ \
  --join-signature="$(cat /tmp/img.roothash):/tmp/img.roothash.p7s" \
  --certificate=verity-certificate.pem \
  /tmp/img.raw
