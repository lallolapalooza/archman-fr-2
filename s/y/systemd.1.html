NOM

systemd, init - gestionnaire système et de services systemd

SYNOPIS

/usr/lib/systemd/systemd [OPTIONS...]

init [OPTIONS...]

DESCRIPTION

systemd est un gestionnaire système et de services pour les systèmes d'exploitation Linux. Lorsqu'il est exécuté en tant que premier processus au démarrage (PID 1), il agit comme un système d'initialisation qui démarre et maintient les services de l'espace utilisateur. Des instances séparées sont démarrées pour les utilisateurs connectés afin de gérer leurs services.

systemd n'est généralement pas invoqué directement par l'utilisateur, mais est installé comme lien symbolique /sbin/init et démarré tôt dans le processus de démarrage. Les instances de gestionnaire utilisateur sont démarrées automatiquement via le service user@.service(5).

Lorsqu'il est exécuté en tant qu'instance système, systemd interprète le fichier de configuration systemd.conf et les fichiers des répertoires systemd.conf.d ; lorsqu'il est exécuté en tant qu'instance utilisateur, systemd interprète le fichier de configuration user.conf et les fichiers des répertoires user.conf.d. Voir systemd-system.conf(5) pour plus d'informations.

systemd contient des implémentations natives de diverses tâches qui doivent être exécutées dans le cadre du processus de démarrage. Par exemple, il définit le nom d'hôte ou configure l'interface réseau de bouclage. Il met également en place et monte divers systèmes de fichiers d'API, tels que /sys/, /proc/ et /dev/.

systemd réinitialisera également l'horloge système au début du démarrage si elle semble incorrectement réglée. Voir la section « Époque de l'horloge système » ci-dessous.

Notez que certaines, mais pas toutes, les interfaces fournies par systemd sont couvertes par la Promesse de portabilité et de stabilité de l'interface[1].

L'API D-Bus de systemd est décrite dans org.freedesktop.systemd1(5) et org.freedesktop.LogControl1(5).

Les systèmes qui invoquent systemd dans un environnement conteneurisé ou initrd doivent implémenter les spécifications de l'Interface Conteneur[2] ou de l'Interface initrd[3], respectivement.

UNITÉS

systemd fournit un système de dépendances entre diverses entités appelées « unités » de 11 types différents. Les unités encapsulent divers objets pertinents pour le démarrage et la maintenance du système. La majorité des unités sont configurées dans des fichiers de configuration d'unités, dont la syntaxe et l'ensemble de base des options sont décrits dans systemd.unit(5), mais certaines sont créées automatiquement à partir d'autres fichiers de configuration, dynamiquement à partir de l'état du système ou programmatiquement au moment de l'exécution. Les unités peuvent se trouver dans plusieurs états, décrits dans le tableau suivant. Notez que les différents types d'unités peuvent avoir plusieurs sous-états supplémentaires, qui sont mappés aux états généraux des unités décrits ici.

Tableau 1. États ACTIFS des unités

État Description
active Démarré, lié, branché, ..., selon le type d'unité.
inactive Arrêté, délié, débranché, ..., selon le type d'unité.
failed Similaire à inactive, mais l'unité a échoué d'une manière ou d'une autre (le processus a renvoyé un code d'erreur à la sortie, a planté, une opération a expiré, ou après trop de redémarrages).
activating Transition de inactive à active.
deactivating Transition de active à inactive.
maintenance L'unité est inactive et une opération de maintenance est en cours.
reloading L'unité est active et elle recharge sa configuration.
refreshing L'unité est active et un nouveau montage est en cours d'activation dans son espace.

Les types d'unités suivants sont disponibles :

1.Unités de service (Service units), qui démarrent et contrôlent les démons et les processus qu'ils constituent. Pour plus de détails, voir systemd.service(5).
2.Unités de socket (Socket units), qui encapsulent les sockets IPC locaux ou réseau dans le système, utiles pour l'activation basée sur les sockets. Pour plus de détails sur les unités de socket, voir systemd.socket(5), pour plus de détails sur l'activation basée sur les sockets et d'autres formes d'activation, voir daemon(7).
3.Unités de cible (Target units) sont utiles pour regrouper des unités, ou fournir des points de synchronisation bien connus pendant le démarrage, voir systemd.target(5).
4.Unités de périphérique (Device units) exposent les périphériques du noyau dans systemd et peuvent être utilisées pour implémenter l'activation basée sur les périphériques. Pour plus de détails, voir systemd.device(5).
5.Unités de montage (Mount units) contrôlent les points de montage dans le système de fichiers, pour plus de détails voir systemd.mount(5).
6.Unités d'automontage (Automount units) fournissent des capacités d'automontage, pour le montage à la demande de systèmes de fichiers ainsi que le démarrage parallèle. Voir systemd.automount(5).
7.Unités de minuteur (Timer units) sont utiles pour déclencher l'activation d'autres unités basées sur des minuteries. Vous trouverez des détails dans systemd.timer(5).
8.Unités d'échange (Swap units) sont très similaires aux unités de montage et encapsulent les partitions ou fichiers d'échange mémoire du système d'exploitation. Elles sont décrites dans systemd.swap(5).
9.Unités de chemin (Path units) peuvent être utilisées pour activer d'autres services lorsque des objets de système de fichiers changent ou sont modifiés. Voir systemd.path(5).
10.Unités de tranche (Slice units) peuvent être utilisées pour regrouper des unités qui gèrent les processus système (telles que les unités de service et de portée) dans un arbre hiérarchique à des fins de gestion des ressources. Voir systemd.slice(5).
11.Unités de portée (Scope units) sont similaires aux unités de service, mais gèrent des processus étrangers au lieu de les démarrer. Voir systemd.scope(5).

Les unités sont nommées d'après leurs fichiers de configuration. Certaines unités ont des sémantiques spéciales. Une liste détaillée est disponible dans systemd.special(7).

systemd connaît plusieurs types de dépendances, y compris des dépendances de nécessité positives et négatives (c'est-à-dire Requires= et Conflicts=) ainsi que des dépendances d'ordre (After= et Before=). NB : les dépendances d'ordre et de nécessité sont orthogonales. Si seule une dépendance de nécessité existe entre deux unités (par exemple, foo.service nécessite bar.service), mais aucune dépendance d'ordre (par exemple, foo.service après bar.service) et que les deux sont demandées pour être démarrées, elles seront démarrées en parallèle. Il est courant que des dépendances de nécessité et d'ordre soient placées entre deux unités. Notez également que la majorité des dépendances sont créées implicitement et gérées par systemd. Dans la plupart des cas, il ne devrait pas être nécessaire de déclarer manuellement des dépendances supplémentaires, mais il est possible de le faire.

Les programmes d'application et les unités (via des dépendances) peuvent demander des changements d'état des unités. Dans systemd, ces requêtes sont encapsulées en tant que 'jobs' et gérées dans une file d'attente de jobs. Les jobs peuvent réussir ou échouer, leur exécution est ordonnancée en fonction des dépendances d'ordre des unités pour lesquelles ils ont été planifiés.

Au démarrage, systemd active la cible par défaut.target dont le rôle est d'activer les services et autres unités au démarrage en les tirant par le biais de dépendances. Généralement, le nom de l'unité est simplement un alias (lien symbolique) pour graphical.target (pour un démarrage complet vers l'interface utilisateur) ou multi-user.target (pour des démarrages limités en console pour une utilisation dans des environnements embarqués ou serveur, ou similaires ; un sous-ensemble de graphical.target). Cependant, il appartient à l'administrateur de le configurer comme un alias pour toute autre unité cible. Voir systemd.special(7) pour plus de détails sur ces unités cibles.

Lors du premier démarrage, systemd activera ou désactivera les unités conformément à la politique prédéfinie. Voir systemd.preset(5) et « Sémantique du premier démarrage » dans machine-id(5).

systemd ne conserve qu'un ensemble minimal de

f unités chargées en mémoire. Spécifiquement, les seules unités qui sont gardées chargées en mémoire sont celles pour lesquelles au moins l'une des conditions suivantes est vraie :

1.Elle est dans un état actif, en cours d'activation, en cours de désactivation ou échoué (c'est-à-dire dans tout état d'unité sauf "inactif")
2.Elle a un travail mis en file d'attente pour elle
3.Elle est une dépendance d'au moins une autre unité qui est chargée en mémoire
4.Elle a une forme de ressource encore allouée (par exemple, une unité de service inactive mais pour laquelle un processus persiste et a ignoré la demande de terminaison)
5.Elle a été épinglée en mémoire par programme via un appel D-Bus

systemd chargera automatiquement et implicitement les unités depuis le disque — si elles ne sont pas encore chargées — dès que des opérations seront demandées pour elles. Ainsi, à bien des égards, le fait qu'une unité soit chargée ou non est invisible pour les clients. Utilisez systemctl list-units --all pour lister de manière exhaustive toutes les unités actuellement chargées. Toute unité pour laquelle aucune des conditions ci-dessus ne s'applique est rapidement déchargée. Notez que lorsqu'une unité est déchargée de la mémoire, ses données de comptabilité sont également effacées. Cependant, ces données ne sont généralement pas perdues, car un enregistrement de journal est généré déclarant les ressources consommées à chaque fois qu'une unité s'arrête.

Les processus que systemd crée sont placés dans des groupes de contrôle Linux individuels nommés d'après l'unité à laquelle ils appartiennent dans la hiérarchie privée de systemd. (voir Control Groups v2[4] pour plus d'informations sur les groupes de contrôle, ou "cgroups" en abrégé). systemd utilise cela pour suivre efficacement les processus. Les informations sur les groupes de contrôle sont maintenues dans le noyau et sont accessibles via la hiérarchie du système de fichiers (sous /sys/fs/cgroup/), ou dans des outils tels que systemd-cgls(1) ou ps(1) (ps xawf -eo pid,user,cgroup,args est particulièrement utile pour lister tous les processus et les unités systemd auxquels ils appartiennent).

systemd est compatible avec diverses fonctionnalités Unix établies telles que /etc/fstab ou la base de données utmp.

systemd possède un système de transactions minimal : si une unité doit être démarrée ou arrêtée, elle sera ajoutée, ainsi que toutes ses dépendances, à une transaction temporaire. Ensuite, il vérifiera si la transaction est cohérente (c'est-à-dire si l'ordonnancement de toutes les unités est sans cycle). Si ce n'est pas le cas, systemd tentera de la réparer et supprimera les travaux non essentiels de la transaction qui pourraient supprimer la boucle. De plus, systemd essaie de supprimer les travaux non essentiels de la transaction qui arrêteraient un service en cours d'exécution. Enfin, il est vérifié si les travaux de la transaction contredisent les travaux déjà mis en file d'attente, et éventuellement la transaction est annulée. Si tout s'est bien passé, que la transaction est cohérente et minimisée dans son impact, elle est fusionnée avec tous les travaux déjà en attente et ajoutée à la file d'attente d'exécution. En pratique, cela signifie qu'avant d'exécuter une opération demandée, systemd vérifiera si elle a du sens, la réparera si possible, et n'échouera que si elle ne peut vraiment pas fonctionner.

Notez que les transactions sont générées indépendamment de l'état d'une unité au moment de l'exécution. Par conséquent, par exemple, si un travail de démarrage est demandé sur une unité déjà démarrée, il générera toujours une transaction et réveillera toutes les dépendances inactives (et provoquera la propagation d'autres travaux selon les relations définies). Cela est dû au fait que le travail mis en file d'attente est comparé à l'état de l'unité cible au moment de l'exécution et est marqué comme réussi et terminé lorsque les deux satisfont. Cependant, ce travail entraîne également d'autres dépendances en raison des relations définies et conduit donc, dans notre exemple, à des travaux de démarrage pour toutes les unités inactives correspondantes également mises en file d'attente.

Les unités peuvent être générées dynamiquement au démarrage et lors du rechargement du gestionnaire système, par exemple en fonction d'autres fichiers de configuration ou de paramètres passés sur la ligne de commande du noyau. Pour plus de détails, voir systemd.generator(7).

RÉPERTOIRES

Répertoires d'unités système

Le gestionnaire système systemd lit la configuration des unités à partir de divers répertoires. Les paquets qui souhaitent installer des fichiers d'unité doivent les placer dans le répertoire retourné par pkg-config systemd --variable=systemdsystemunitdir. D'autres répertoires vérifiés sont /usr/local/lib/systemd/system et /usr/lib/systemd/system. La configuration utilisateur a toujours priorité. pkg-config systemd --variable=systemdsystemconfdir renvoie le chemin du répertoire de configuration système. Les paquets ne doivent modifier le contenu de ces répertoires qu'avec les commandes enable et disable de l'outil systemctl(1). La liste complète des répertoires est fournie dans systemd.unit(5).

Répertoires d'unités utilisateur

Des règles similaires s'appliquent aux répertoires d'unités utilisateur. Cependant, ici, la spécification XDG Base Directory[5] est suivie pour trouver les unités. Les applications doivent placer leurs fichiers d'unité dans le répertoire retourné par pkg-config systemd --variable=systemduserunitdir. La configuration globale est effectuée dans le répertoire indiqué par pkg-config systemd --variable=systemduserconfdir. Les commandes enable et disable de l'outil systemctl(1) peuvent gérer l'activation/désactivation globale (c'est-à-dire pour tous les utilisateurs) et privée (pour un utilisateur) des unités. La liste complète des répertoires est fournie dans systemd.unit(5).

SIGNaux

Le service écoute divers signaux de processus UNIX qui peuvent être utilisés pour demander diverses actions de manière asynchrone. La gestion des signaux est activée très tôt pendant le démarrage, avant que tout autre processus ne soit invoqué. Cependant, un gestionnaire de conteneur superviseur ou similaire qui a l'intention de demander ces opérations via ce mécanisme doit tenir compte du fait que cette fonctionnalité n'est pas disponible pendant la phase d'initialisation la plus précoce. Un message de notification sd_notify() transportant le champ X_SYSTEMD_SIGNALS_LEVEL=2 est émis une fois les gestionnaires de signaux activés, voir ci-dessous. Cela peut être utilisé pour planifier la soumission correcte de ces signaux.

SIGTERM

À la réception de ce signal, le gestionnaire système systemd sérialise son état, se réexécute et désérialise à nouveau l'état sauvegardé. Ceci est globalement équivalent à systemctl daemon-reexec.

Les gestionnaires utilisateur de systemd démarreront l'unité exit.target lors de la réception de ce signal. Ceci est globalement équivalent à systemctl --user start exit.target --job-mode=replace-irreversibly.

SIGINT

À la réception de ce signal, le gestionnaire système systemd démarrera l'unité ctrl-alt-del.target. Ceci est globalement équivalent à systemctl start ctrl-alt-del.target --job-mode=replace-irreversibly. Si ce signal est reçu plus de 7 fois par 2 secondes, un redémarrage immédiat est déclenché. Notez que l'appui sur Ctrl+Alt+Del sur la console déclenchera ce signal. Par conséquent, si un redémarrage est bloqué, appuyer sur Ctrl+Alt+Del plus de 7 fois en 2 secondes est un moyen relativement sûr de déclencher un redémarrage immédiat.

Les gestionnaires utilisateur de systemd traitent ce signal de la même manière que SIGTERM.

SIGWINCH

Lors de la réception de ce signal, le gestionnaire système systemd démarrera l'unité kbrequest.target. Ceci est globalement équivalent à systemctl start kbrequest.target.

Ce signal est ignoré par les gestionnaires utilisateur de systemd.

SIGPWR

Lors de la réception de ce signal, le gestionnaire systemd démarrera l'unité sigpwr.target. Ceci est globalement équivalent à systemctl start sigpwr.target.

SIGUSR1

Lors de la réception de ce signal, le gestionnaire systemd tentera de se reconnecter au bus D-Bus.

SIGUSR2

Lors de la réception de ce signal, le gestionnaire systemd enregistrera son état complet sous une forme lisible par l'homme. Les données enregistrées sont les mêmes que celles imprimées par systemd-analyze dump.

SIGHUP

Recharge la configuration complète du démon. Ceci est globalement équivalent à systemctl daemon-reload.

SIGRTMIN+0

Entre en mode par défaut, démarre l'unité default.target. Ceci est globalement équivalent à systemctl isolate default.target.

SIGRTMIN+1

Entre en mode de secours, démarre l'unité rescue.target. Ceci est globalement équivalent à systemctl isolate rescue.target.

SIGRTMIN+2

Entre en mode d'urgence, démarre l'unité emergency.service. Ceci est globalement équivalent à systemctl isolate emergency.service.

SIGRTMIN+3

Arrête la machine, démarre l'unité halt.target. Ceci est globalement équivalent à systemctl start halt.target --job-mode=replace-irreversibly.

SIGRTMIN+4

Éteint la machine, démarre l'unité poweroff.target. Ceci est globalement équivalent à systemctl start poweroff.target --job-mode=replace-irreversibly.

SIGRTMIN+5

Redémarre la machine, démarre l'unité reboot.target. Ceci est globalement équivalent à systemctl start reboot.target --job-mode=replace-irreversibly.

SIGRTMIN+6

Redémarre la machine via kexec, démarre l'unité kexec.target. Ceci est globalement équivalent à systemctl start kexec.target --job-mode=replace-irreversibly.

SIGRTMIN+7

Redémarre l'espace utilisateur, démarre l'unité soft-reboot.target. Ceci est globalement équivalent à systemctl start soft-reboot.target --job-mode=replace-irreversibly.

Ajouté dans la version 254.

SIGRTMIN+13

Arrête immédiatement la machine.

SIGRTMIN+14

Éteint immédiatement la machine.

SIGRTMIN+15

Redémarre immédiatement la machine.

SIGRTMIN+16

Redémarre immédiatement la machine avec kexec.

SIGRTMIN+17

Redémarre immédiatement l'espace utilisateur.

Ajouté dans la version 254.

SIGRTMIN+20

Active l'affichage des messages de statut sur la console, tel que contrôlé par systemd.show_status=1 sur la ligne de commande du noyau.

Vous pourriez vouloir utiliser SetShowStatus() au lieu de SIGRTMIN+20 afin d'éviter les conditions de concurrence. Voir org.freedesktop.systemd1(5).

SIGRTMIN+21

Désactive l'affichage des messages de statut sur la console, tel que contrôlé par systemd.show_status=0 sur la ligne de commande du noyau.

Vous pourriez vouloir utiliser SetShowStatus() au lieu de SIGRTMIN+21 afin d'éviter les conditions de concurrence. Voir org.freedesktop.systemd1(5).

SIGRTMIN+22

Définit le niveau de journalisation du gestionnaire de service sur "debug", d'une manière équivalente à systemd.log_level=debug sur la ligne de commande du noyau.

SIGRTMIN+23

Restaure le niveau de journalisation à sa valeur configurée. La valeur configurée est dérivée de – dans l'ordre de priorité – la valeur spécifiée avec systemd.log-level= sur la ligne de commande du noyau, ou la valeur spécifiée avec LogLevel= dans le fichier de configuration, ou la valeur par défaut intégrée de "info".

Ajouté dans la version 239.

SIGRTMIN+24

Fait sortir immédiatement le gestionnaire (disponible uniquement pour les instances --user).

Ajouté dans la version 195.

SIGRTMIN+25

À la réception de ce signal, le gestionnaire systemd se réexécutera lui-même. Ceci est principalement équivalent à systemctl daemon-reexec, à l'exception qu'il sera fait de manière asynchrone.

Le gestionnaire système systemd traite ce signal de la même manière que SIGTERM.

Ajouté dans la version 250.

SIGRTMIN+26

Restaure la cible de journalisation à sa valeur configurée. La valeur configurée est dérivée de – dans l'ordre de priorité – la valeur spécifiée avec systemd.log-target= sur la ligne de commande du noyau, ou la valeur spécifiée avec LogTarget= dans le fichier de configuration, ou la valeur par défaut intégrée.

Ajouté dans la version 239.

SIGRTMIN+27, SIGRTMIN+28

Définit la cible de journalisation sur "console" avec SIGRTMIN+27 (ou "kmsg" avec SIGRTMIN+28), d'une manière équivalente à systemd.log_target=console (ou systemd.log_target=kmsg avec SIGRTMIN+28) sur la ligne de commande du noyau.

Ajouté dans la version 239.

ENVIRONNEMENT

Le bloc d'environnement pour le gestionnaire système est initialement défini par le noyau. (En particulier, les affectations "clé=valeur" sur la ligne de commande du noyau sont transformées en variables d'environnement pour PID 1). Pour le gestionnaire utilisateur, le gestionnaire système définit l'environnement comme décrit dans la section « Variables d'environnement dans les processus lancés » de systemd.exec(5). Le réglage DefaultEnvironment= dans le gestionnaire système s'applique à tous les services, y compris user@.service. Des entrées supplémentaires peuvent être configurées (comme pour tout autre service) via les réglages Environment= et EnvironmentFile= pour user@.service (voir systemd.exec(5)). De plus, des variables d'environnement supplémentaires peuvent être définies via le réglage ManagerEnvironment= dans systemd-system.conf(5) et systemd-user.conf(5).

Certaines des variables comprises par systemd :

$SYSTEMD_LOG_LEVEL

Le niveau de journalisation maximal des messages émis (les messages d'un niveau de journalisation supérieur, c'est-à-dire moins importants, seront supprimés). Prend une liste de valeurs séparées par des virgules. Une valeur peut être soit l'une des suivantes (par ordre d'importance décroissante) : emerg, alert, crit, err, warning, notice, info, debug, soit un entier dans la plage 0...7. Voir syslog(3) pour plus d'informations. Chaque valeur peut éventuellement être précédée de l'un des préfixes console, syslog, kmsg ou journal suivi d'un deux-points pour définir le niveau de journalisation maximal pour cette cible de journalisation spécifique (par exemple, SYSTEMD_LOG_LEVEL=debug,console:info spécifie de journaliser au niveau debug, sauf lors de la journalisation sur la console où le niveau devrait être info). Notez que le niveau de journalisation maximal global a la priorité sur tous les niveaux de journalisation maximaux par cible.

Ceci peut être remplacé par --log-level=.

$SYSTEMD_LOG_COLOR

Un booléen. S'il est vrai, les messages écrits sur le tty seront colorés en fonction de la priorité.

Ceci peut être remplacé par --log-color=.

$SYSTEMD_LOG_TIME

Un booléen. S'il est vrai, les messages de journalisation sur console seront préfixés par un horodatage.

Ceci peut être remplacé par --log-time=.

Ajouté dans la version 246.

$SYSTEMD_LOG_LOCATION

Un booléen. S'il est vrai, les messages seront préfixés par le nom de fichier et le numéro de ligne dans le code source d'où provient le message.

Ceci peut être remplacé par --log-location=.

$SYSTEMD_LOG_TID

Un booléen. S'il est vrai, les messages seront préfixés par l'identifiant de thread (TID) numérique actuel.

Ajouté dans la version 247.

$SYSTEMD_LOG_TARGET

La destination des messages de journalisation. L'une des options suivantes : console (journaliser sur le tty connecté), console-prefixed (journaliser sur le tty connecté mais avec des préfixes encodant le niveau de journalisation et la « facilité », voir syslog(3), kmsg (journaliser dans le tampon de journalisation circulaire du noyau), journal (journaliser dans le journal), journal-or-kmsg (journaliser dans le journal si disponible, et dans kmsg sinon), auto (déterminer automatiquement la cible de journalisation appropriée, par défaut), null (désactiver la sortie de journalisation).

Ceci peut être remplacé par --log-target=.

$SYSTEMD_LOG_RATELIMIT_KMSG

Indique s'il faut limiter le débit des messages kmsg ou non. Prend une valeur booléenne. La valeur par défaut est "true". Si désactivé, systemd ne limitera pas le débit des messages écrits dans kmsg.

Ajouté dans la version 254.

$XDG_CONFIG_HOME, $XDG_CONFIG_DIRS, $XDG_DATA_HOME, $XDG_DATA_DIRS

Le gestionnaire utilisateur de systemd utilise ces variables conformément à la **spécification des répertoires de base XDG**[5] pour trouver sa configuration.

$SYSTEMD_UNIT_PATH, $SYSTEMD_GENERATOR_PATH, $SYSTEMD_ENVIRONMENT_GENERATOR_PATH

Contrôle où systemd recherche les fichiers d'unité et les générateurs.

Ces variables peuvent contenir une liste de chemins, séparés par des deux-points (":"). Lorsqu'elles sont définies, si la liste se termine par un composant vide ("...:"), cette liste est ajoutée au début de l'ensemble habituel de chemins. Sinon, la liste spécifiée remplace l'ensemble habituel de chemins.

$SYSTEMD_PAGER, $PAGER

Pagineur à utiliser lorsque --no-pager n'est pas donné. $SYSTEMD_PAGER est utilisé s'il est défini ; sinon $PAGER est utilisé. Si ni $SYSTEMD_PAGER ni $PAGER ne sont définis, un ensemble d'implémentations de pagineurs bien connues est essayé tour à tour, y compris less(1) et more(1), jusqu'à ce qu'un soit trouvé. Si aucune implémentation de pagineur n'est découverte, aucun pagineur n'est invoqué. Définir ces variables d'environnement sur une chaîne vide ou la valeur "cat" équivaut à passer --no-pager.

Note : si $SYSTEMD_PAGERSECURE n'est pas défini, $SYSTEMD_PAGER et $PAGER ne peuvent être utilisés que pour désactiver le pagineur (avec "cat" ou ""), et sont sinon ignorés.

$SYSTEMD_LESS

Remplace les options passées à less (par défaut "FRSXMK").

Les utilisateurs pourraient vouloir modifier deux options en particulier :

K

Cette option demande au pagineur de quitter immédiatement lorsque Ctrl+C est pressé. Pour permettre à less de gérer Ctrl+C lui-même afin de revenir à l'invite de commande du pagineur, désactivez cette option.

Si la valeur de $SYSTEMD_LESS n'inclut pas "K", et que le pagineur invoqué est less, Ctrl+C sera ignoré par l'exécutable, et devra être géré par le pagineur.

X

Cette option demande au pagineur de ne pas envoyer de chaînes d'initialisation et de désinitialisation termcap au terminal. Elle est définie par défaut pour permettre à la sortie de la commande de rester visible dans le terminal même après la sortie du pagineur. Néanmoins, cela empêche certaines fonctionnalités du pagineur de fonctionner, en particulier la sortie paginée ne peut pas être défilée avec la souris.

Notez que la définition de la variable d'environnement $LESS régulière n'a aucun effet pour les invocations de less par les outils systemd.

Voir less(1) pour plus de détails.

$SYSTEMD_LESSCHARSET

Remplace le jeu de caractères passé à less (par défaut "utf-8", si le terminal appelant est déterminé comme étant compatible UTF-8).

Notez que la définition de la variable d'environnement $LESSCHARSET régulière n'a aucun effet pour les invocations de less par les outils systemd.

$SYSTEMD_PAGERSECURE

Les commandes de pagineur courantes comme less(1), en plus de la « pagination », c'est-à-dire du défilement de la sortie, prennent en charge l'ouverture ou l'écriture d'autres fichiers et l'exécution de commandes shell arbitraires. Lorsque les commandes sont invoquées avec des privilèges élevés, par exemple sous sudo(8) ou pkexec(1), le pagineur devient une limite de sécurité. Il faut veiller à ce que seuls les programmes aux fonctionnalités strictement limitées soient utilisés comme pagineurs, et que les fonctionnalités interactives involontaires telles que l'ouverture ou la création de nouveaux fichiers ou le lancement de sous-processus ne soient pas autorisées. Le « mode sécurisé » pour le pagineur peut être activé comme décrit ci-dessous, si le pagineur le prend en charge (la plupart des pagineurs ne sont pas écrits d'une manière qui prend cela en considération). Il est recommandé soit d'activer explicitement le « mode sécurisé », soit de désactiver complètement le pagineur en utilisant --no-pager ou PAGER=cat lorsque des utilisateurs non fiables sont autorisés à exécuter des commandes avec des privilèges élevés.

Cette option prend un argument booléen. Lorsqu'elle est définie sur vrai, le « mode sécurisé » du pagineur est activé. En « mode sécurisé », LESSSECURE=1 sera défini lors de l'invocation du pagineur, ce qui demande au pagineur de désactiver les commandes qui ouvrent ou créent de nouveaux fichiers ou démarrent de nouveaux sous-processus. Actuellement, seul less(1) est connu pour comprendre cette variable et implémenter le « mode sécurisé ».

Lorsqu'elle est définie sur faux, aucune limitation n'est placée sur le pagineur. Définir SYSTEMD_PAGERSECURE=0 ou ne pas le supprimer de l'environnement hérité peut permettre à l'utilisateur d'invoquer des commandes arbitraires.

Lorsque $SYSTEMD_PAGERSECURE n'est pas défini, les outils systemd tentent de déterminer automatiquement si le « mode sécurisé » doit être activé et si le pagineur le prend en charge. Le « mode sécurisé » est activé si l'UID effectif n'est pas le même que le propriétaire de la session de connexion, voir geteuid(2) et sd_pid_get_owner_uid(3), ou lors de l'exécution sous sudo(8) ou des outils similaires ($SUDO_UID est défini [6]). Dans ces cas, SYSTEMD_PAGERSECURE= 1 sera défini et les pagineurs qui ne sont pas connus pour implémenter le "mode sécurisé" ne seront pas utilisés du tout. Notez que cette autodétection ne couvre que les mécanismes les plus courants pour élever les privilèges et est destinée à des fins de commodité. Il est recommandé de définir explicitement $SYSTEMD_PAGERSECURE ou de désactiver le pagineur.

Notez que si les variables $SYSTEMD_PAGER ou $PAGER doivent être respectées, autres que pour désactiver le pagineur, $SYSTEMD_PAGERSECURE doit également être défini.

$SYSTEMD_COLORS

Prend un argument booléen. S'il est vrai, systemd et les utilitaires associés utiliseront des couleurs dans leur sortie, sinon la sortie sera monochrome. De plus, la variable peut prendre l'une des valeurs spéciales suivantes : "16", "256" pour restreindre l'utilisation des couleurs aux 16 ou 256 couleurs ANSI de base, respectivement. Ceci peut être spécifié pour remplacer la décision automatique basée sur $TERM et sur ce à quoi la console est connectée.

$SYSTEMD_URLIFY

La valeur doit être booléenne. Contrôle si des liens cliquables doivent être générés dans la sortie pour les émulateurs de terminaux qui prennent en charge cela. Ceci peut être spécifié pour remplacer la décision que systemd prend en fonction de $TERM et d'autres conditions.

$LISTEN_PID, $LISTEN_FDS, $LISTEN_FDNAMES

Défini par systemd pour les processus supervisés lors de l'activation basée sur les sockets. Voir sd_listen_fds(3) pour plus d'informations.

$NOTIFY_SOCKET

Défini par le gestionnaire de services pour ses services afin de notifier l'état et la disponibilité. Également consommé par le gestionnaire de services pour notifier les gestionnaires de conteneurs superviseurs ou les gestionnaires de services plus haut dans la pile de son propre progrès. Voir sd_notify(3) et la section pertinente ci-dessous pour plus d'informations.

Pour d'autres variables d'environnement comprises par systemd et ses divers composants, voir Variables d'environnement connues[7].

LIGNE DE COMMANDE DU NOYAU

Lorsqu'il est exécuté en tant qu'instance système, systemd analyse un certain nombre d'options listées ci-dessous. Elles peuvent être spécifiées comme arguments de ligne de commande du noyau qui sont analysés à partir d'un certain nombre de sources en fonction de l'environnement dans lequel systemd est exécuté. S'il est exécuté à l'intérieur d'un conteneur Linux, ces options sont analysées à partir des arguments de ligne de commande passés à systemd lui-même, en plus de toute option de ligne de commande listée dans la section Options ci-dessus. S'il est exécuté en dehors des conteneurs Linux, ces arguments sont analysés à partir de /proc/cmdline à la place.

Les variables suivantes sont comprises :

systemd.unit=, rd.systemd.unit=

Remplace l'unité à activer au démarrage. Par défaut, default.target. Ceci peut être utilisé pour démarrer temporairement avec une unité de démarrage différente, par exemple rescue.target ou emergency.service. Voir systemd.special(7) pour les détails sur ces unités. L'option préfixée par "rd." n'est honorée que dans l'initrd, tandis que celle qui n'est pas préfixée n'est honorée que dans le système principal.

systemd.dump_core

Prend un argument booléen ou active l'option si spécifié sans argument. Si activé, le gestionnaire systemd (PID 1) crée un core dump en cas de crash. Sinon, aucun core dump n'est créé. Par défaut, il est activé.

Ajouté dans la version 233.

systemd.crash_chvt

Prend un entier positif, ou un argument booléen. Peut également être spécifié sans argument, avec le même effet qu'un booléen positif. Si un entier positif (dans la plage 1–63) est spécifié, le gestionnaire système (PID 1) activera le terminal virtuel spécifié lorsqu'il se bloque. Par défaut, il est désactivé, ce qui signifie qu'aucun changement n'est tenté. S'il est défini sur activé, le terminal virtuel auquel les messages du noyau sont écrits est utilisé à la place.

Ajouté dans la version 233.

systemd.crash_shell

Prend un argument booléen ou active l'option si spécifié sans argument. Si activé, le gestionnaire système (PID 1) lance un shell en cas de crash. Sinon, aucun shell n'est lancé. Par défaut, il est désactivé, pour des raisons de sécurité, car le shell n'est pas protégé par une authentification par mot de passe.

Ajouté dans la version 233.

systemd.crash_action=

Prend l'une des valeurs "freeze", "reboot" ou "poweroff". Par défaut, "freeze". S'il est défini sur "freeze", le système restera bloqué indéfiniment lorsque le gestionnaire système (PID 1) plante. S'il est défini sur "reboot", le gestionnaire système (PID 1) redémarrera la machine automatiquement en cas de crash, après un délai de 10 secondes. S'il est défini sur "poweroff", le gestionnaire système (PID 1) éteindra la machine immédiatement en cas de crash. Combiné avec systemd.crash_shell, l'action de crash configurée est exécutée après la sortie du shell.

Ajouté dans la version 256.

systemd.confirm_spawn

Prend un argument booléen ou un chemin vers la console virtuelle où les messages de confirmation doivent être émis. Peut également être spécifié sans argument, avec le même effet qu'un booléen positif. S'il est activé, le gestionnaire système (PID 1) demande une confirmation lors du lancement de processus utilisant /dev/console. Si un chemin ou un nom de console (tel que "ttyS0") est fourni, la console virtuelle pointée par ce chemin ou décrite par le nom donné sera utilisée à la place. Par défaut, il est désactivé.

Ajouté dans la version 233.

systemd.service_watchdogs=

Prend un argument booléen. S'il est désactivé, tous les watchdogs de temps d'exécution des services (WatchdogSec=) et les actions d'urgence (par exemple OnFailure= ou StartLimitAction=) sont ignorés par le gestionnaire système (PID 1) ; voir systemd.service(5). Par défaut, il est activé, c'est-à-dire que les watchdogs et les actions de défaillance sont traités normalement. Le watchdog matériel n'est pas affecté par cette option.

Ajouté dans la version 237.

systemd.show_status

Prend un argument booléen ou les constantes error et auto. Peut également être spécifié sans argument, avec le même effet qu'un booléen positif. S'il est activé, le gestionnaire systemd (PID 1) affiche des mises à jour d'état de service concises sur la console pendant le démarrage. Avec error, seuls les messages concernant les échecs sont affichés, mais le démarrage est par ailleurs silencieux. auto se comporte comme false jusqu'à ce qu'il y ait un retard significatif au démarrage. Par défaut, il est activé, sauf si quiet est passé comme option de ligne de commande du noyau, auquel cas il prend par défaut la valeur error. S'il est spécifié, il remplace l'option de fichier de configuration du gestionnaire système ShowStatus=, voir systemd-system.conf(5).

Ajouté dans la version 233.

systemd.status_unit_format=

Prend name, description ou combined comme valeur. Si name, le gestionnaire système utilisera les noms d'unités dans les messages d'état. Si combined, le gestionnaire système utilisera les noms d'unités et la description dans les messages d'état. Lorsqu'il est spécifié, remplace l'option de fichier de configuration du gestionnaire système StatusUnitFormat=, voir systemd-system.conf(5).

Ajouté dans la version 243.

systemd.log_color, systemd.log_level=, systemd.log_location, systemd.log_target=, systemd.log_time, systemd.log_tid, systemd.log_ratelimit_kmsg

Contrôle la sortie des journaux, avec le même effet que les variables d'environnement $SYSTEMD_LOG_COLOR, $SYSTEMD_LOG_LEVEL, $SYSTEMD_LOG_LOCATION, $SYSTEMD_LOG_TARGET, $SYSTEMD_LOG_TIME, $SYSTEMD_LOG_TID et $SYSTEMD_LOG_RATELIMIT_KMSG décrites ci-dessus. systemd.log_color, systemd.log_location, systemd.log_time, systemd.log_tid et systemd.log_ratelimit_kmsg peuvent être spécifiés sans argument, avec le même effet qu'un booléen positif.

systemd.default_standard_output=, systemd.default_standard_error=

Contrôle la sortie standard par défaut et la sortie d'erreur pour les services et les sockets. C'est-à-dire qu'il contrôle la valeur par défaut de StandardOutput= et StandardError= (voir systemd.exec(5) pour les détails). Prend l'une des valeurs inherit, null, tty, journal, journal+console, kmsg, kmsg+console. Si l'argument est omis, systemd.default-standard-output= prend par défaut journal et systemd.default-standard-error= prend par défaut inherit.

systemd.setenv=

Prend un argument de chaîne sous la forme VARIABLE=VALEUR. Peut être utilisé pour définir des variables d'environnement par défaut à ajouter aux processus enfants créés. Peut être utilisé plusieurs fois pour définir plusieurs variables.

systemd.machine_id=

Prend une valeur hexadécimale de 32 caractères pour définir l'identifiant de la machine. Principalement destiné au démarrage réseau où le même identifiant de machine est souhaité pour chaque démarrage.

Ajouté dans la version 229.

systemd.set_credential=, systemd.set_credential_binary=

Définit une information d'identification système, qui peut ensuite être propagée aux services système en utilisant le réglage ImportCredential= ou LoadCredential=, voir systemd.exec(5) pour les détails. Prend une paire nom d'information d'identification et valeur, séparées par deux-points. Le paramètre systemd.set_credential= attend la valeur de l'information d'identification sous forme de texte littéral, le paramètre systemd.set_credential_binary= prend des données binaires encodées en Base64. Notez que la ligne de commande du noyau est généralement accessible par les programmes non privilégiés dans /proc/cmdline. Par conséquent, ce mécanisme ne convient pas pour transférer des données sensibles. Utilisez-le uniquement pour des données non sensibles (par exemple, des clés publiques/certificats, plutôt que des clés privées), ou dans des environnements de test/débogage.

Pour plus d'informations, voir la documentation Informations d'identification système et de service[8].

Ajouté dans la version 251.

systemd.import_credentials=

Prend un argument booléen. S'il est faux, désactive l'importation des informations d'identification à partir de la ligne de commande du noyau, de la table des chaînes OEM DMI/SMBIOS, du sous-système qemu_fw_cfg ou du stub du noyau EFI.

Ajouté dans la version 251.

quiet

Désactive la sortie d'état au démarrage, un peu comme le ferait systemd.show_status=no. Notez que cette option est également lue par le noyau lui-même et désactive la sortie du journal du noyau. Passer cette option désactive donc la sortie normale du gestionnaire système et du noyau.

Ajouté dans la version 186.

debug

Active la sortie de débogage. Ceci est équivalent à systemd.log_level=debug. Notez que cette option est également lue par le noyau lui-même et active la sortie de débogage du noyau. Passer cette option active donc la sortie de débogage du gestionnaire système et du noyau. kernel.

Ajouté dans la version 205.

emergency, rd.emergency, -b

Démarre en mode d'urgence. Ceci est équivalent à systemd.unit=emergency.target ou rd.systemd.unit=emergency.target, respectivement, et est fourni pour des raisons de compatibilité et pour être plus facile à taper.

Ajouté dans la version 186.

rescue, rd.rescue, single, s, S, 1

Démarre en mode de secours. Ceci est équivalent à systemd.unit=rescue.target ou rd.systemd.unit=rescue.target, respectivement, et est fourni pour des raisons de compatibilité et pour être plus facile à taper.

Ajouté dans la version 186.

2, 3, 4, 5

Démarre dans le niveau d'exécution SysV hérité spécifié. 2, 3 et 4 sont équivalents à systemd.unit=multi-user.target ; et 5 est équivalent à systemd.unit=graphical.target, et est fourni pour des raisons de compatibilité et pour être plus facile à taper.

Ajouté dans la version 186.

locale.LANG=, locale.LANGUAGE=, locale.LC_CTYPE=, locale.LC_NUMERIC=, locale.LC_TIME=, locale.LC_COLLATE=, locale.LC_MONETARY=, locale.LC_MESSAGES=, locale.LC_PAPER=, locale.LC_NAME=, locale.LC_ADDRESS=, locale.LC_TELEPHONE=, locale.LC_MEASUREMENT=, locale.LC_IDENTIFICATION=

Définit la locale système à utiliser. Ceci remplace les paramètres dans /etc/locale.conf. Pour plus d'informations, voir locale.conf(5) et locale(7).

Ajouté dans la version 186.

Pour d'autres paramètres de ligne de commande du noyau compris par les composants du système d'exploitation de base, veuillez vous référer à kernel-command-line(7).

IDENTIFIANTS SYSTÈME

Pendant l'initialisation, le gestionnaire de services importera des identifiants de diverses sources dans l'ensemble des identifiants du système, qui pourront ensuite être propagés dans les services et consommés par les générateurs :

•Lorsque le gestionnaire de services s'initialise pour la première fois, il lira les identifiants système à partir des chaînes de fournisseur SMBIOS Type 11 io.systemd.credential:nom=valeur, et io.systemd.credential.binary:nom=valeur.
•Dans le même temps, il importera les identifiants de QEMU "fw_cfg". (Notez que le mécanisme SMBIOS est généralement préféré, car il est plus rapide et générique.)
•Les identifiants peuvent être passés via la ligne de commande du noyau, en utilisant le paramètre systemd.set-credential=, voir ci-dessus.
•Les identifiants peuvent être passés depuis l'environnement UEFI via systemd-stub(7).
•Lorsque le gestionnaire de services est invoqué pendant la transition initrd → hôte, il importera tous les fichiers dans /run/credentials/@initrd/ en tant qu'identifiants système.

Invoquez systemd-creds(1) comme suit pour voir la liste des identifiants passés au système :

# systemd-creds --system list

Pour plus d'informations, consultez la documentation Identifiants système et service[8].

Le gestionnaire de services, lorsqu'il est exécuté en tant que PID 1, consomme les identifiants système suivants :

vmm.notify_socket

Contient une adresse AF_VSOCK ou AF_UNIX vers laquelle envoyer un message de notification READY=1 lorsque le gestionnaire de services a terminé son démarrage. Voir sd_notify(3) et la section suivante pour plus d'informations. Notez qu'au cas où l'hyperviseur ne prend pas en charge SOCK_DGRAM sur AF_VSOCK, SOCK_SEQPACKET sera essayé à la place. La charge utile de l'identifiant pour AF_VSOCK doit être une chaîne de caractères sous la forme "vsock:CID:PORT". "vsock-stream", "vsock-dgram" et "vsock-seqpacket" peuvent être utilisés à la place de "vsock" pour forcer l'utilisation du type de socket correspondant.

Cette fonctionnalité est utile pour les gestionnaires de machines ou d'autres processus sur l'hôte afin de recevoir une notification via VSOCK lorsqu'une machine virtuelle a fini de démarrer.

Ajouté dans la version 254.

system.machine_id

Prend un identifiant hexadécimal de 128 bits pour initialiser /etc/machine-id, si le fichier n'est pas déjà configuré. Voir machine-id(5) pour les détails.

Ajouté dans la version 254.

Pour une liste des identifiants système que divers autres composants de systemd consomment, voir systemd.system-credentials(7).

PROTOCOLE DE PRÊT

Le gestionnaire de services implémente un protocole de notification de préparation à la fois entre le gestionnaire et ses services (c'est-à-dire vers le bas dans la pile), et entre le gestionnaire et un superviseur potentiel plus haut dans la pile (ce dernier pourrait être un gestionnaire de machines ou de conteneurs, ou dans le cas d'un gestionnaire de services par utilisateur, l'instance du gestionnaire de services système). Le protocole de base (et l'API suggérée pour celui-ci) est décrit dans sd_notify(3).

Le socket de notification que le gestionnaire de services (y compris PID 1) utilise pour signaler sa disponibilité à son propre superviseur est défini via la variable d'environnement habituelle $NOTIFY_SOCKET (voir ci-dessus). Comme cela ne peut être défini directement que pour les gestionnaires de conteneurs et pour l'instance par utilisateur du gestionnaire de services, un mécanisme supplémentaire pour configurer cela est disponible, particulièrement destiné à être utilisé dans les environnements VM : l'identifiant système vmm.notify_socket (voir ci-dessus) peut être défini sur un socket approprié (typiquement un AF_VSOCK) via les chaînes de fournisseur SMBIOS Type 11. Pour plus de détails, voir ci-dessus.

Le protocole de notification du gestionnaire de services vers le haut de la pile vers un superviseur prend en charge un certain nombre de champs d'extension qui permettent à un superviseur d'apprendre des propriétés spécifiques du système et de suivre sa progression de démarrage. Spécifiquement, les champs suivants sont envoyés :

•Un message X_SYSTEMD_HOSTNAME=... sera envoyé une fois que le nom d'hôte initial du système a été déterminé. Notez que pendant l'exécution ultérieure, le nom d'hôte peut être modifié à nouveau programmablement, et (actuellement) aucune notification supplémentaire n'est envoyée dans ce cas.

Ajouté dans la version 256.

•Un message X_SYSTEMD_MACHINE_ID=... sera envoyé une fois que l'identifiant machine du système a été déterminé. Voir machine-id(5) pour les détails.

Ajouté dans la version 256.

•Un message X_SYSTEMD_SIGNALS_LEVEL=... sera envoyé une fois que le gestionnaire de services a installé les différents gestionnaires de signaux de processus UNIX décrits ci-dessus. La valeur du champ est un entier non signé formaté sous forme de chaîne décimale, et indique le niveau de fonctionnalité pris en charge par le gestionnaire de services pour les signaux de processus UNIX. Actuellement, un seul niveau de fonctionnalité est défini :
•X_SYSTEMD_SIGNALS_LEVEL=2 couvre les divers signaux de processus UNIX documentés ci-dessus – ; qui sont un sur-ensemble de ceux pris en charge par le système d'initialisation SysV historique.

Les signaux envoyés au PID 1 avant que ce message ne soit envoyé pourraient ne pas être gérés correctement. Un consommateur de ces messages doit analyser la valeur comme un entier non signé qui indique le niveau de prise en charge. Pour l'instant, seul le niveau 2 mentionné est défini, mais plus tard, des niveaux supplémentaires pourront être définis avec des entiers plus élevés, qui implémenteront un sur-ensemble du comportement actuellement défini.

Ajouté dans la version 256.

•Les messages X_SYSTEMD_UNIT_ACTIVE=... et X_SYSTEMD_UNIT_INACTIVE=... seront envoyés pour chaque unité cible lorsqu'elle devient active ou cesse de l'être. Ceci est utile pour suivre la progression et la fonctionnalité du démarrage. Par exemple, une fois que l'unité ssh-access.target est rapportée comme démarrée, l'accès SSH est généralement disponible, voir systemd.special(7) pour les détails.

Ajouté dans la version 256.

•Un message X_SYSTEMD_SHUTDOWN=... sera envoyé très peu de temps avant que le système ne s'arrête. La valeur est l'une des chaînes "reboot", "halt", "poweroff", "kexec" et indique quel type d'arrêt est exécuté.

Ajouté dans la version 256.

•Un message X_SYSTEMD_REBOOT_PARAMETER=... sera également envoyé très peu de temps avant que le système ne s'arrête. Sa valeur est l'argument de redémarrage tel que configuré avec systemctl --reboot-argument=....

Ajouté dans la version 256.

Notez que ces champs d'extension sont envoyés en plus des notifications régulières "READY=1" et "RELOADING=1".

OPTIONS

systemd est rarement invoqué directement, car il est démarré tôt et est déjà en cours d'exécution au moment où les utilisateurs peuvent interagir avec lui. Normalement, des outils comme systemctl(1) sont utilisés pour donner des commandes au gestionnaire. Comme systemd n'est généralement pas invoqué directement, les options listées ci-dessous sont principalement utiles pour le débogage et des usages spéciaux.

Options d'introspection et de débogage

Ces options sont utilisées pour les tests et l'introspection, et systemd peut être invoqué avec elles à tout moment :

--dump-configuration-items

Affiche les éléments de configuration compris. Ceci produit une liste concise mais complète des éléments de configuration compris dans les fichiers de définition d'unités.

--dump-bus-properties

Affiche les propriétés exposées sur le bus. Ceci produit une liste concise mais complète des propriétés exposées sur D-Bus.

Ajouté dans la version 239.

--test

Détermine la transaction de démarrage initiale (c'est-à-dire la liste des jobs mis en file d'attente au démarrage), l'affiche et quitte — sans exécuter réellement aucun des jobs déterminés. Cette option est utile uniquement pour le débogage. Notez que lors du démarrage régulier du gestionnaire de services, des unités supplémentaires qui ne sont pas montrées par cette opération peuvent être démarrées, car l'activation matérielle, par socket, par bus ou d'autres types d'activation peuvent ajouter des jobs supplémentaires à mesure que la transaction est exécutée. Utilisez --system pour demander la transaction initiale du gestionnaire de services système (c'est aussi le défaut implicite), combinez avec --user pour demander la transaction initiale du gestionnaire de services par utilisateur à la place.

--system, --user

Lorsqu'il est utilisé en conjonction avec --test, sélectionne s'il faut calculer la transaction initiale

OPTIONS

When invoked directly, systemd takes various command-line options. These options have a similar effect to the kernel command line parameters documented in kernel-command-line(7), but are typically used only when systemd is invoked in --test mode, or to adjust behaviour when running as a user instance.

Options starting with --system and --user control whether systemd operates in system-wide mode or in per-user mode. These options have no effect when invoked without --test, as during regular (i.e. non---test) invocations the service manager will automatically detect whether it shall operate in system or per-user mode, by checking whether the PID it is run as is 1 or not. Note that it is not supported booting and maintaining a system with the service manager running in --system mode but with a PID other than 1.

-h, --help

Print a short help text and exit.

--version

Print a short version string and exit.

Options that duplicate kernel command line settings

Those options correspond directly to options listed above in "Kernel Command Line". Both forms may be used equivalently for the system manager, but it is recommended to use the forms listed above in this context, because they are properly namespaced. When an option is specified both on the kernel command line and as a normal command line argument, the latter has higher precedence.

When systemd is used as a user manager, the kernel command line is ignored and only the options described below are understood. Nevertheless, systemd is usually started in this mode through the user@.service(5) service, which is shared between all users. It may be more convenient to use configuration files to modify settings (see systemd-user.conf(5)), or environment variables. See the "Environment" section above for a discussion of how the environment block is set.

--unit=

Set default unit to activate on startup. If not specified, defaults to default.target. See systemd.unit= above.

--dump-core

Enable core dumping on crash. This switch has no effect when running as user instance. Same as systemd.dump_core= above.

--crash-vt=VT

Switch to a specific virtual console (VT) on crash. This switch has no effect when running as user instance. Same as systemd.crash_chvt= above (but not the different spelling!).

--crash-action=

Specify what to do when the system manager (PID 1) crashes. This switch has no effect when systemd is running as user instance. See systemd.crash_action= above.

Added in version 256.

--confirm-spawn

Ask for confirmation when spawning processes. This switch has no effect when run as user instance. See systemd.confirm_spawn above.

--show-status

Show terse unit status information on the console during boot-up and shutdown. See systemd.show_status above.

Added in version 244.

--log-color

Highlight important log messages. See systemd.log_color above.

Added in version 244.

SYSTEM CLOCK EPOCH

When systemd is started or restarted, it may set the system clock to the "epoch". This mechanism is used to ensure that the system clock remains somewhat reasonably initialized and roughly monotonic across reboots, in case no battery-backed local RTC is available or it does not work correctly.

The epoch is the lowest date above which the system clock time is assumed to be set correctly. When initializing, the local clock is advanced to the epoch if it was set to a lower value. As a special case, if the local clock is sufficiently far in the future (by default 15 years, but this can be configured at build time), the hardware clock is assumed to be broken, and the system clock is rewound to the epoch.

The epoch is set to the highest of: the build time of systemd, the modification time ("mtime") of /usr/lib/clock-epoch, and the modification time of /var/lib/systemd/timesync/clock.

FILES

/run/systemd/notify

Daemon status notification socket. This is an AF_UNIX datagram socket and is used to implement the daemon notification logic as implemented by sd_notify(3).

/run/systemd/private

Used internally as communication channel between systemctl(1) and the systemd process. This is an AF_UNIX stream socket. This interface is private to systemd and should not be used in external projects.

/usr/lib/clock-epoch

The modification time ("mtime") of this file is used for the time epoch, see previous section.

Added in version 247.

/var/lib/systemd/timesync/clock

The modification time ("mtime") of this file is updated by systemd-timesyncd.service(8). If present, the modification time of file is used for the epoch, see previous section.

Added in version 257.
