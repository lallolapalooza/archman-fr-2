NOM

systemd.resource-control - Paramètres de contrôle des ressources

SYNTAXE

slice.slice, scope.scope, service.service, socket.socket, mount.mount, swap.swap

DESCRIPTION

Les fichiers de configuration d'unités pour les services, slices, scopes, sockets, points de montage et périphériques swap partagent un sous-ensemble d'options de configuration pour le contrôle des ressources des processus lancés. En interne, cela repose sur le concept de noyaux des Groupes de Contrôle (cgroups) de Linux pour organiser les processus dans une hiérarchie d'arborescence de groupes nommés dans le but de gérer les ressources.

Cette page de manuel liste les options de configuration partagées par ces six types d'unités. Voir systemd.unit(5) pour les options communes à tous les fichiers de configuration d'unités, et systemd.slice(5), systemd.scope(5), systemd.service(5), systemd.socket(5), systemd.mount(5), et systemd.swap(5) pour plus d'informations sur les fichiers de configuration d'unités spécifiques. Les options de configuration de contrôle des ressources sont configurées dans les sections [Slice], [Scope], [Service], [Socket], [Mount], ou [Swap], selon le type d'unité.

En outre, les options qui contrôlent les ressources disponibles pour les programmes exécutés par systemd sont listées dans systemd.exec(5). Ces options complètent celles listées ici.

Activation et désactivation des contrôleurs

Les contrôleurs dans la hiérarchie des cgroups sont hiérarchiques, et le contrôle des ressources est réalisé en distribuant les affectations de ressources entre les frères et sœurs dans les branches de la hiérarchie des cgroups. Il n'est pas nécessaire d'activer explicitement un contrôleur cgroup pour une unité. systemd demandera au noyau d'activer un contrôleur pour une unité donnée lorsque cette unité a une configuration pour un contrôleur donné. Par exemple, lorsque CPUWeight= est défini, le contrôleur cpu sera activé, et lorsque TasksMax= est défini, le contrôleur pids sera activé. De plus, divers contrôleurs peuvent également être activés explicitement via les paramètres MemoryAccounting=/TasksAccounting=/IOAccounting=. En raison du fonctionnement de la hiérarchie des cgroups, les contrôleurs seront automatiquement activés pour toutes les unités parentes et pour tous les frères et sœurs des unités, en commençant par le niveau le plus bas auquel un contrôleur est activé. Les unités pour lesquelles un contrôleur est activé peuvent être soumises au contrôle des ressources même si elles n'ont aucune configuration explicite.

La définition de Delegate= active tous les contrôleurs délégués pour cette unité (voir ci-dessous). Le délégué peut alors activer les contrôleurs pour ses enfants comme il convient. En particulier, si le délégué est systemd (dans l'unité user@.service), il répétera la même logique que l'instance système et activera les contrôleurs pour les unités utilisateur qui ont des limites de ressources configurées, ainsi que leurs frères et sœurs et leurs parents et les parents de leurs parents.

Les contrôleurs peuvent être désactivés pour des parties de la hiérarchie des cgroups avec DisableControllers= (voir ci-dessous).

Exemple 1. Activation et désactivation des contrôleurs

                      -.slice
                     /       \
              /-----/         \--------------\
             /                                \
      system.slice                       user.slice
        /       \                          /      \
       /         \                        /        \
      /           \              user@42.service  user@1000.service
     /             \             Delegate=        Delegate=yes
a.service       b.slice                             /        \
CPUWeight=20   DisableControllers=cpu              /          \
                 /  \                      app.slice      session.slice
                /    \                     CPUWeight=100  CPUWeight=100
               /      \
       b1.service   b2.service
                    CPUWeight=1000

Dans cette hiérarchie, le contrôleur cpu est activé pour toutes les unités montrées sauf b1.service et b2.service. Comme il n'y a pas de configuration explicite pour system.slice et user.slice, les ressources CPU seront réparties également entre elles. De même, les ressources sont affectées également aux enfants de user.slice et entre les slices enfants sous user@1000.service. En supposant qu'il n'y ait pas d'autres configurations de ressources ou de délégation sous les slices app.slice ou session.slice, le contrôleur cpu ne serait pas activé pour les unités de ces slices et les ressources CPU seraient allouées davantage par d'autres mécanismes, par exemple, en fonction des niveaux de priorité.

Le réglage CPUWeight= dans le service b2.service est neutralisé par DisableControllers= dans le slice b.slice, de sorte que le contrôleur cpu ne serait pas activé pour les services b1.service et b2.service, et les ressources CPU seraient allouées davantage par d'autres mécanismes, par exemple, en fonction des niveaux de priorité.

Définir des contrôles de ressources pour un groupe d'unités apparentées

Comme décrit dans systemd.unit(5), les paramètres listés ici peuvent être définis via le fichier principal d'une unité et des snippets de remplacement dans les répertoires *.d/. La liste des répertoires recherchés pour les remplacements inclut des noms formés en tronquant répétitivement le nom de l'unité après tous les tirets. Ceci est particulièrement pratique pour définir des limites de ressources pour un groupe d'unités aux noms similaires.

Par exemple, chaque utilisateur obtient sa propre slice user-nnn.slice. Des remplacements avec une configuration locale qui affectent l'utilisateur 1000 peuvent être placés dans /etc/systemd/system/user-1000.slice, /etc/systemd/system/user-1000.slice.d/*.conf, mais aussi /etc/systemd/system/user-.slice.d/*.conf. Ce dernier répertoire s'applique à toutes les slices utilisateur.

Voir les Nouvelles Interfaces de Groupe de Contrôle[1] pour une introduction sur la façon d'utiliser les API de contrôle des ressources depuis des programmes.

OPTIONS

Les unités des types listés ci-dessus peuvent avoir des paramètres pour la configuration du contrôle des ressources :

Contrôle CPU

CPUWeight=poids, StartupCPUWeight=poids

Ces paramètres contrôlent le contrôleur cpu dans la hiérarchie unifiée.

Ces options acceptent une valeur entière ou la chaîne spéciale "idle" :

•Si elle est définie sur une valeur entière, affectez le poids de temps CPU spécifié aux processus exécutés, si la hiérarchie unifiée des groupes de contrôle est utilisée sur le système. Ces options contrôlent l'attribut de contrôle "cpu.weight". La plage autorisée est de 1 à 10000. La valeur par défaut est non définie, mais la valeur par défaut du noyau est 100. Pour les détails sur cet attribut de groupe de contrôle, voir Groupes de Contrôle v2[2] et Planificateur CFS[3]. Le temps CPU disponible est réparti entre toutes les unités au sein d'une slice par rapport à leur poids de temps CPU. Un poids plus élevé signifie plus de temps CPU, un poids plus faible signifie moins.
•Si elle est définie sur la chaîne spéciale "idle", marquez le cgroup pour la "planification idle", ce qui signifie qu'il n'obtiendra des ressources CPU que lorsqu'il n'y aura pas de processus non marqués ainsi à exécuter dans ce cgroup ou ses frères et sœurs. Ce paramètre correspond à l'attribut cgroup "cpu.idle".

Notez que cette valeur n'a d'effet que sur cgroup-v2, pour cgroup-v1 elle est équivalente au poids minimum.

Alors que StartupCPUWeight= s'applique à la s

démarrage et arrêt phases du système, CPUWeight= s'applique à l'exécution normale du système et, si le premier n'est pas défini, également aux phases de démarrage et d'arrêt. L'utilisation de StartupCPUWeight= permet de prioriser des services spécifiques au démarrage et à l'arrêt différemment de l'exécution normale.

En plus de l'allocation de ressources effectuée par le contrôleur cpu, le noyau peut diviser automatiquement les ressources en fonction du regroupement par ID de session, voir « La fonctionnalité autogroup » dans sched(7). L'effet de cette fonctionnalité est similaire au contrôleur cpu sans configuration explicite, les utilisateurs doivent donc faire attention à ne pas confondre l'un avec l'autre.

Ajouté dans la version 232.

CPUQuota=

Ce paramètre contrôle le contrôleur cpu dans la hiérarchie unifiée.

Attribue le quota de temps CPU spécifié aux processus exécutés. Prend une valeur en pourcentage, suffixée par « % ». Le pourcentage spécifie la quantité de temps CPU que l'unité recevra au maximum, par rapport au temps CPU total disponible sur un CPU. Utilisez des valeurs supérieures à 100 % pour allouer du temps CPU sur plusieurs CPU. Ceci contrôle l'attribut « cpu.max » sur la hiérarchie de groupes de contrôle unifiés et « cpu.cfs_quota_us » sur l'ancien système. Pour plus de détails sur ces attributs de groupe de contrôle, voir Control Groups v2[2] et CFS Bandwidth Control[4]. La définition de CPUQuota= sur une valeur vide annule le quota.

Exemple : CPUQuota=20% garantit que les processus exécutés ne recevront jamais plus de 20 % de temps CPU sur un CPU.

Ajouté dans la version 213.

CPUQuotaPeriodSec=

Ce paramètre contrôle le contrôleur cpu dans la hiérarchie unifiée.

Attribue la durée pendant laquelle le quota de temps CPU spécifié par CPUQuota= est mesuré. Prend une valeur de durée en secondes, avec un suffixe optionnel tel que « ms » pour les millisecondes (ou « s » pour les secondes). Le réglage par défaut est de 100 ms. La période est limitée à la plage prise en charge par le noyau, qui est de [1 ms, 1000 ms]. De plus, la période est ajustée de manière à ce que l'intervalle de quota soit également d'au moins 1 ms. La définition de CPUQuotaPeriodSec= sur une valeur vide la réinitialise à la valeur par défaut.

Ceci contrôle le deuxième champ de l'attribut « cpu.max » sur la hiérarchie de groupes de contrôle unifiés et « cpu.cfs_period_us » sur l'ancien système. Pour plus de détails sur ces attributs de groupe de contrôle, voir Control Groups v2[2] et CFS Scheduler[3].

Exemple : CPUQuotaPeriodSec=10ms pour demander que le quota CPU soit mesuré sur des périodes de 10 ms.

Ajouté dans la version 242.

AllowedCPUs=, StartupAllowedCPUs=

Ce paramètre contrôle le contrôleur cpuset dans la hiérarchie unifiée.

Restreint les processus à être exécutés sur des CPU spécifiques. Prend une liste d'indices de CPU ou de plages séparées par des espaces blancs ou des virgules. Les plages de CPU sont spécifiées par les indices de CPU inférieur et supérieur séparés par un tiret.

La définition de AllowedCPUs= ou StartupAllowedCPUs= ne garantit pas que tous les CPU seront utilisés par les processus, car cela peut être limité par les unités parentes. La configuration effective est rapportée comme EffectiveCPUs=.

Alors que StartupAllowedCPUs= s'applique aux phases de démarrage et d'arrêt du système, AllowedCPUs= s'applique à l'exécution normale du système et, si le premier n'est pas défini, également aux phases de démarrage et d'arrêt. L'utilisation de StartupAllowedCPUs= permet de prioriser des services spécifiques au démarrage et à l'arrêt différemment de l'exécution normale.

Ce paramètre n'est pris en charge qu'avec la hiérarchie de groupes de contrôle unifiés.

Ajouté dans la version 244.

Comptabilité et contrôle de la mémoire

MemoryAccounting=

Ce paramètre contrôle le contrôleur memory dans la hiérarchie unifiée.

Active la comptabilité de la mémoire des processus et du noyau pour cette unité. Prend un argument booléen. Notez que l'activation de la comptabilité de la mémoire pour une unité l'activera également implicitement pour toutes les unités contenues dans la même tranche et pour toutes ses tranches parentes et les unités qu'elles contiennent. La valeur par défaut du système pour ce paramètre peut être contrôlée avec DefaultMemoryAccounting= dans systemd-system.conf(5).

Ajouté dans la version 208.

MemoryMin=octets, MemoryLow=octets, StartupMemoryLow=octets, DefaultStartupMemoryLow=octets

Ces paramètres contrôlent le contrôleur memory dans la hiérarchie unifiée.

Spécifie la protection de l'utilisation de la mémoire des processus exécutés dans cette unité. Lors de la récupération de mémoire, l'unité est traitée comme si elle utilisait moins de mémoire, ce qui entraîne une récupération préférentielle de mémoire à partir des unités non protégées. L'utilisation de MemoryLow= entraîne une protection plus faible où la mémoire peut toujours être récupérée pour éviter d'invoquer le tueur OOM s'il n'y a pas d'autre mémoire récupérable.

Pour qu'une protection soit efficace, il est généralement nécessaire de définir une allocation correspondante sur tous les ancêtres, qui est ensuite distribuée entre les enfants (à l'exception de la tranche racine). Toute allocation MemoryMin= ou MemoryLow= qui n'est pas explicitement distribuée à des enfants spécifiques est utilisée pour créer une protection partagée pour tous les enfants. Comme il s'agit d'une protection partagée, les enfants rivaliseront librement pour la mémoire.

Prend une taille de mémoire en octets. Si la valeur est suffixée par K, M, G ou T, la taille de mémoire spécifiée est analysée en Kilooctets, Mégaoctets, Gigaoctets ou Téraoctets (avec la base 1024), respectivement. Alternativement, une valeur en pourcentage peut être spécifiée, qui est relative à la mémoire physique installée sur le système. Si la valeur spéciale « infinity » est assignée, toute la mémoire disponible est protégée, ce qui peut être utile afin d'hériter toujours de toute la protection offerte par les ancêtres. Ceci contrôle l'attribut de groupe de contrôle « memory.min » ou « memory.low ». Pour plus de détails sur cet attribut de groupe de contrôle, voir Memory Interface Files[5].

Les unités peuvent avoir leurs enfants utilisant une valeur par défaut « memory.min » ou « memory.low » en spécifiant DefaultMemoryMin= ou DefaultMemoryLow=, qui a la même sémantique que MemoryMin= et MemoryLow=, ou DefaultStartupMemoryLow= qui a la même sémantique que StartupMemoryLow=. Ce paramètre n'affecte pas « memory.min » ou « memory.low » dans l'unité elle-même. Son utilisation pour définir une allocation enfant par défaut n'est utile que sur les noyaux antérieurs à 5.7, qui ne prennent pas en charge l'option de montage cgroup2 « memory_recursiveprot ».

Alors que StartupMemoryLow= s'applique aux phases de démarrage et d'arrêt du système, MemoryMin= s'applique à l'exécution normale du système et, si le premier n'est pas défini, également aux phases de démarrage et d'arrêt. L'utilisation de StartupMemoryLow= permet de prioriser des services spécifiques au démarrage et à l'arrêt différemment de l'exécution normale.

Ajouté dans la version 240.

MemoryHigh=octets, StartupMemoryHigh=octets

Ces paramètres contrôlent le contrôleur memory dans la hiérarchie unifiée.

Spécifie la limite d'étranglement sur l'utilisation de la mémoire des processus exécutés dans cette unité. L'utilisation de la mémoire peut dépasser la limite si elle est inévitable, mais les processus sont fortement ralentis et la mémoire est retirée agressivement dans de tels cas. C'est le principal mécanisme pour contrôler l'utilisation de la mémoire d'une unité.

Prend une taille de mémoire en octets. Si la valeur est suffixée par K, M, G ou T, la taille de mémoire spécifiée est analysée en Kilooctets, Mégaoctets, Gigaoctets ou Téraoctets (avec la base 1024), respectivement. Alternativement, une valeur en pourcentage peut être spécifiée, qui est relative à la mémoire physique installée sur le système. Si la valeur spéciale « infinity » est assignée, aucun étranglement de mémoire n'est appliqué. Ceci contrôle l'attribut de groupe de contrôle « memory.high ». Pour plus de détails sur cet attribut de groupe de contrôle, voir Memory Interface Files[5]. La configuration effective est rapportée comme EffectiveMemoryHigh= (voir aussi EffectiveMemoryMax=).

Alors que StartupMemoryHigh= s'applique aux phases de démarrage et d'arrêt du système, MemoryHigh= s'applique à l'exécution normale du système et, si le premier n'est pas défini, également aux phases de démarrage et d'arrêt. L'utilisation de StartupMemoryHigh= permet de prioriser des services spécifiques au démarrage et à l'arrêt différemment de l'exécution normale.

Ajouté dans la version 231.

MemoryMax=octets, StartupMemoryMax=octets

Ces paramètres contrôlent le contrôleur memory dans la hiérarchie unifiée.

Spécifie la limite absolue sur l'utilisation de la mémoire des processus exécutés dans cette unité. Si l'utilisation de la mémoire ne peut pas être contenue sous la limite, le tueur « out-of-memory » est invoqué à l'intérieur de l'unité. Il est recommandé d'utiliser MemoryHigh= comme principal mécanisme de contrôle et d'utiliser MemoryMax= comme dernier recours.

Prend une taille de mémoire en octets. Si la valeur est suffixée par K, M, G ou T, la taille de mémoire spécifiée est analysée en Kilooctets, Mégaoctets, Gigaoctets ou Téraoctets (avec la base 1024), respectivement. Alternativement, une valeur en pourcentage peut être spécifiée, qui est relative à la mémoire physique installée sur le système. Si la valeur spéciale « infinity » est assignée, aucune limite de mémoire n'est appliquée. Ceci contrôle l'attribut de groupe de contrôle « memory.max ». Pour plus de détails sur cet attribut de groupe de contrôle, voir Memory Interface Files[5]. La configuration effective est rapportée comme EffectiveMemoryMax= (la valeur est la limite la plus stricte de l'unité et des tranches parentes et elle est plafonnée par la mémoire physique).

Alors que StartupMemoryMax= s'applique aux phases de démarrage et d'arrêt du système, MemoryMax= s'applique à l'exécution normale du système et, si le premier n'est pas défini, également aux phases de démarrage et d'arrêt. L'utilisation de StartupMemoryMax= permet de prioriser des services spécifiques au démarrage et à l'arrêt différemment de l'exécution normale.

Ajouté dans la version 231.

MemorySwapMax=octets, StartupMemorySwapMax=octets

Ces paramètres contrôlent le contrôleur memory dans la hiérarchie unifiée.

Spécifie la limite absolue sur l'utilisation du swap des processus exécutés dans cette unité.

Prend une taille de swap en octets. Si la valeur est suffixée par K, M, G ou T, la taille de swap spécifiée est analysée en Kilooctets, Mégaoctets, Gigaoctets ou Téraoctets (avec la base 1024), respectivement. Alternativement, une valeur en pourcentage peut être spécifiée, qui est taken par rapport à la taille d'échange spécifiée sur le système. Si la valeur spéciale « infinity » est attribuée, aucune limite d'échange n'est appliquée. Ces paramètres contrôlent l'attribut de groupe de contrôle « memory.swap.max ». Pour plus de détails sur cet attribut de groupe de contrôle, voir **Fichiers d'interface mémoire**[5].

Tandis que StartupMemorySwapMax= s'applique aux phases de démarrage et d'arrêt du système, MemorySwapMax= s'applique au fonctionnement normal du système, et si le premier n'est pas défini, également aux phases de démarrage et d'arrêt. L'utilisation de StartupMemorySwapMax= permet de prioriser certains services au démarrage et à l'arrêt différemment que pendant le fonctionnement normal.

Ajouté dans la version 232.

MemoryZSwapMax=octets, StartupMemoryZSwapMax=octets

Ces paramètres contrôlent le contrôleur **memory** dans la hiérarchie unifiée.

Spécifiez la limite absolue de l'utilisation de zswap par les processus de cette unité. Zswap est un cache léger compressé pour les pages d'échange. Il prend les pages en cours d'échange et tente de les compresser dans un pool de mémoire dynamique basé sur la RAM. Si la limite spécifiée est atteinte, aucune entrée de cette unité ne sera stockée dans le pool tant que les entrées existantes ne seront pas ramenées ou écrites sur disque. Voir la documentation du noyau sur **Zswap**[6] pour plus de détails.

Prend une taille en octets. Si la valeur est suffixée par K, M, G ou T, la taille spécifiée est analysée en Kilooctets, Mégaoctets, Gigaoctets ou Téraoctets (avec la base 1024), respectivement. Si la valeur spéciale « infinity » est attribuée, aucune limite n'est appliquée. Ces paramètres contrôlent l'attribut de groupe de contrôle « memory.zswap.max ». Pour plus de détails sur cet attribut de groupe de contrôle, voir **Fichiers d'interface mémoire**[5].

Tandis que StartupMemoryZSwapMax= s'applique aux phases de démarrage et d'arrêt du système, MemoryZSwapMax= s'applique au fonctionnement normal du système, et si le premier n'est pas défini, également aux phases de démarrage et d'arrêt. L'utilisation de StartupMemoryZSwapMax= permet de prioriser certains services au démarrage et à l'arrêt différemment que pendant le fonctionnement normal.

Ajouté dans la version 253.

MemoryZSwapWriteback=

Ce paramètre contrôle le contrôleur **memory** dans la hiérarchie unifiée.

Prend un argument booléen. Si vrai, les pages stockées dans le cache Zswap sont autorisées à être écrites sur le stockage de secours, sinon faux. Par défaut, c'est vrai. Cela permet de désactiver la réécriture des pages d'échange pour les applications intensives en IO, tout en conservant la capacité de stocker des pages compressées dans Zswap. Voir la documentation du noyau sur **Zswap**[6] pour plus de détails.

Ajouté dans la version 256.

Les plages de nœuds NUMA mémoire sont spécifiées par les indices des nœuds NUMA inférieurs et supérieurs séparés par un tiret.

La définition de AllowedMemoryNodes= ou StartupAllowedMemoryNodes= ne garantit pas que tous les nœuds NUMA mémoire seront utilisés par les processus, car cela peut être limité par les unités parentes. La configuration effective est rapportée sous EffectiveMemoryNodes=.

L'utilisation de StartupAllowedMemoryNodes= permet de prioriser certains services au démarrage et à l'arrêt différemment que pendant le fonctionnement normal.

Comptabilité et Contrôle des Processus

TasksAccounting=

Ce paramètre contrôle le contrôleur **pids** dans la hiérarchie unifiée.

Activer la comptabilité des tâches pour cette unité. Prend un argument booléen. Si activé, le noyau suivra le nombre total de tâches dans l'unité et ses enfants. Ce nombre inclut les threads du noyau et les processus utilisateur, chaque thread étant compté individuellement. Notez que l'activation de la comptabilité des tâches pour une unité l'activera également implicitement pour toutes les unités contenues dans la même tranche et pour toutes ses tranches parentes et les unités qui y sont contenues. Le réglage par défaut du système pour ce paramètre peut être contrôlé avec DefaultTasksAccounting= dans systemd-system.conf(5).

Ajouté dans la version 227.

TasksMax=N

Ce paramètre contrôle le contrôleur **pids** dans la hiérarchie unifiée.

Spécifiez le nombre maximum de tâches qui peuvent être créées dans l'unité. Cela garantit que le nombre de tâches comptabilisées pour l'unité (voir ci-dessus) reste en dessous d'une limite spécifique. Cela prend soit un nombre absolu de tâches, soit un pourcentage relatif au nombre maximum de tâches configuré sur le système. Si la valeur spéciale « infinity » est attribuée, aucune limite de tâches n'est appliquée. Cela contrôle l'attribut de groupe de contrôle « pids.max ». Pour plus de détails sur cet attribut de groupe de contrôle, voir le **contrôleur pids**[7]. La configuration effective est rapportée sous EffectiveTasksMax=.

Le réglage par défaut du système pour ce paramètre peut être contrôlé avec DefaultTasksMax= dans systemd-system.conf(5).

Ajouté dans la version 227.

Comptabilité et Contrôle des IO

IOAccounting=

Ce paramètre contrôle le contrôleur **io** dans la hiérarchie unifiée.

Activer la comptabilité des E/S de bloc pour cette unité, si la hiérarchie unifiée des groupes de contrôle est utilisée sur le système. Prend un argument booléen. Notez que l'activation de la comptabilité des E/S de bloc pour une unité l'activera également implicitement pour toutes les unités contenues dans la même tranche et pour toutes ses tranches parentes et les unités qui y sont contenues. Le réglage par défaut du système pour ce paramètre peut être contrôlé avec DefaultIOAccounting= dans systemd-system.conf(5).

Ajouté dans la version 230.

IOWeight=poids, StartupIOWeight=poids

Ces paramètres contrôlent le contrôleur **io** dans la hiérarchie unifiée.

Définir le poids par défaut global des E/S de bloc pour les processus exécutés, si la hiérarchie unifiée des groupes de contrôle est utilisée sur le système. Prend une seule valeur de poids (entre 1 et 10000) pour définir le poids par défaut des E/S de bloc. Cela contrôle l'attribut de groupe de contrôle « io.weight », qui par défaut est 100. Pour plus de détails sur cet attribut de groupe de contrôle, voir **Fichiers d'interface IO**[8]. La bande passante E/S disponible est répartie entre toutes les unités au sein d'une même tranche par rapport à leur poids E/S de bloc. Un poids plus élevé signifie plus de bande passante E/S, un poids plus faible signifie moins.

Comptabilité et Contrôle Réseau

IPAccounting=

Prend un argument booléen. S'il est vrai, active la comptabilité du trafic réseau IPv4 et IPv6 pour les paquets envoyés ou reçus par l'unité. Lorsque cette option est activée, tous les sockets IPv4 et IPv6 créés par un processus de l'unité sont comptabilisés.

Lorsque cette option est utilisée dans les unités de socket, elle s'applique à tous les sockets IPv4 et IPv6 qui y sont associés (y compris les sockets d'écoute et les sockets de connexion applicables). Notez que pour les services activés par socket, ce paramètre de configuration et les données de comptabilité de l'unité de service et de l'unité de socket sont conservés séparément et affichés séparément. Aucune propagation du paramètre et des statistiques collectées n'est effectuée, dans un sens comme dans l'autre. De plus, tout trafic envoyé ou reçu sur l'un des sockets de l'unité de socket est comptabilisé pour l'unité de socket — et jamais pour l'unité de service qu'elle a pu activer, même si le socket est utilisé par celle-ci.

Le défaut du système pour ce paramètre peut être contrôlé avec DefaultIPAccounting= dans systemd-system.conf(5).

Notez que cette fonctionnalité n'est actuellement disponible que pour les services système, pas pour les services par utilisateur.

Ajouté dans la version 235.

IPAddressAllow=ADDRESS[/PREFIXLENGTH]..., IPAddressDeny=ADDRESS[/PREFIXLENGTH]...

Active le filtrage du trafic réseau pour les paquets IP envoyés et reçus sur les sockets AF_INET et AF_INET6. Les deux directives prennent une liste séparée par des espaces d'adresses IPv4 ou IPv6, chacune éventuellement suffixée d'une longueur de préfixe d'adresse en bits après un caractère « / ». Si le suffixe est omis, l'adresse est considérée comme une adresse hôte, c'est-à-dire que le filtre couvre toute l'adresse (32 bits pour IPv4, 128 bits pour IPv6).

Les listes d'accès configurées avec cette option s'appliquent à tous les sockets créés par les processus de cette unité (ou dans le cas des unités de socket, qui y sont associés). Les listes sont implicitement combinées avec toutes les listes configurées pour les unités de slice parentes dont cette unité pourrait être membre. Par défaut, les deux listes d'accès sont vides. Le trafic entrant et sortant est filtré par ces paramètres. En cas de trafic entrant, l'adresse IP source est vérifiée par rapport à ces listes d'accès, en cas de trafic sortant, l'adresse IP de destination est vérifiée. Les règles suivantes sont appliquées à tour de rôle :

•L'accès est accordé lorsque l'adresse IP vérifiée correspond à une entrée dans la liste IPAddressAllow=.
•Sinon, l'accès est refusé lorsque l'adresse IP vérifiée correspond à une entrée dans la liste IPAddressDeny=.
•Sinon, l'accès est accordé.

Pour implémenter un pare-feu IP basé sur une liste d'autorisation, il est recommandé d'utiliser un réglage IPAddressDeny=any sur une unité de slice de niveau supérieur (comme la slice racine -.slice ou la slice contenant tous les services système system.slice — voir systemd.special(7) pour les détails sur ces unités de slice), plus des lignes IPAddressAllow= individuelles par service autorisant l'accès réseau aux services pertinents, et uniquement à eux.

Notez que pour les services activés par socket, la liste d'accès IP configurée sur l'unité de socket s'applique à tous les sockets qui y sont directement associés, mais pas à tous les sockets créés par les services finalement activés pour celle-ci. Inversement, la liste d'accès IP configurée pour le service ne s'applique pas aux sockets passés au service via l'activation de socket. Par conséquent, il est généralement judicieux de reproduire les listes d'accès IP sur l'unité de socket et l'unité de service. Néanmoins, il peut être judicieux de maintenir une liste plus ouverte et l'autre plus restrictive, en fonction du cas d'utilisation.

Si ces paramètres sont utilisés plusieurs fois dans la même unité, les listes spécifiées sont combinées. Si une chaîne vide est assignée à ces paramètres, la liste d'accès spécifique est réinitialisée et tous les paramètres précédents sont annulés.

Au lieu de spécifications explicites d'adresses et de longueurs de préfixe IPv4 ou IPv6, un petit ensemble de noms symboliques peut être utilisé. Les noms suivants sont définis :

Table 1. Noms d'adresses/réseaux spéciaux

Nom Symbolique Définition Signification
any 0.0.0.0/0 ::/0 Tout hôte
localhost 127.0.0.0/8 ::1/128 Toutes les adresses de bouclage local
link-local 169.254.0.0/16 fe80::/64 Toutes les adresses IP locales au lien
multicast 224.0.0.0/4 ff00::/8 Toutes les adresses de multidiffusion IP

Notez que ces paramètres peuvent ne pas être pris en charge sur certains systèmes (par exemple, si le support eBPF des cgroups n'est pas activé dans le noyau sous-jacent ou le gestionnaire de conteneurs). Ces paramètres n'auront aucun effet dans ce cas. Si la compatibilité avec de tels systèmes est souhaitée, il est donc recommandé de ne pas s'y fier exclusivement pour la sécurité IP.

Cette option ne peut pas être contournée en ajoutant « + » au chemin de l'exécutable dans l'unité de service, car elle s'applique à l'ensemble du cgroup.

SocketBindAllow=bind-rule, SocketBindDeny=bind-rule

Configure des restrictions sur la capacité des processus de l'unité à invoquer bind(2) sur un socket. Les deux règles, d'autorisation et de refus, peuvent être définies pour restreindre les adresses auxquelles un socket peut être lié.

bind-rule décrit les propriétés du socket telles que address-family, transport-protocol et ip-ports.

bind-rule := { [address-family:][transport-protocol:][ip-ports] | any }

address-family := { ipv4 | ipv6 }

transport-protocol := { tcp | udp }

ip-ports := { ip-port | ip-port-range }

Une address-family optionnelle attend les valeurs ipv4 ou ipv6. Si elle n'est pas spécifiée, une règle sera appliquée aux adresses IPv4 et IPv6 et appliquée en fonction d'autres champs de socket, par exemple transport-protocol, ip-port.

Un transport-protocol optionnel attend les noms de protocoles de transport tcp ou udp. S'il n'est pas spécifié, une règle sera appliquée à n'importe quel protocole de transport.

Une valeur ip-port optionnelle doit être comprise entre 1 et 65535 inclusivement, c'est-à-dire que le port dynamique 0 n'est pas autorisé. Une plage de ports séquentiels est décrite par ip-port-range := ip-port-low-ip-port-high, où ip-port-low est inférieur ou égal à ip-port-high et les deux sont compris entre 1 et 65535 inclusivement.

Une valeur spéciale any peut être utilisée pour appliquer une règle à n'importe quelle famille d'adresses, protocole de transport et n'importe quel port avec une valeur positive.

Pour autoriser plusieurs règles, assignez SocketBindAllow= ou SocketBindDeny= plusieurs fois. Pour annuler les affectations existantes, passez une affectation vide à SocketBindAllow= ou SocketBindDeny=.

Pour chacun de SocketBindAllow= et SocketBindDeny=, le nombre maximal d'affectations autorisées est de 128.

•La liaison à un socket est autorisée lorsqu'une adresse de socket correspond à une entrée dans la liste SocketBindAllow=.
•Sinon, la liaison est refusée lorsque l'adresse de socket correspond à une entrée dans la liste SocketBindDeny=.
•Sinon, la liaison est autorisée.

La fonctionnalité est implémentée avec les hooks cgroup bpf cgroup/bind4 et cgroup/bind6.

Notez que ces paramètres s'appliquent à toute invocation de l'appel système bind(2) par les processus de l'unité, quel que soit l'espace de noms réseau dans lequel ils sont placés. Autrement dit : changer l'espace de noms réseau n'est pas un mécanisme approprié pour échapper à ces restrictions sur bind().

Exemples :

...
# Autoriser la liaison des adresses de socket IPv6 avec un port supérieur ou égal à 10000.
[Service]
SocketBindAllow=ipv6:10000-65535
SocketBindDeny=any
...
# Autoriser la liaison des adresses de socket IPv4 et IPv6 avec les ports 1234 et 4321.
[Service]
SocketBindAllow=1234
SocketBindAllow=4321
SocketBindDeny=any
...
# Refuser la liaison des adresses de socket IPv6.
[Service]
SocketBindDeny=ipv6
...
# Refuser la liaison des adresses de socket IPv4 et IPv6.
[Service]
SocketBindDeny=any
...
# Autoriser la liaison uniquement sur TCP
[Service]
SocketBindAllow=tcp
SocketBindDeny=any
...
# Autoriser la liaison o
nly sur IPv6/TCP [Service] SocketBindAllow=ipv6:tcp SocketBindDeny=any ... # Autoriser la liaison des ports dans la plage 10000-65535 sur IPv4/UDP. [Service] SocketBindAllow=ipv4:udp:10000-65535 SocketBindDeny=any ...

Cette option ne peut pas être contournée en préfixant "+" au chemin de l'exécutable dans l'unité de service, car elle s'applique à l'ensemble du cgroup.

RestrictNetworkInterfaces=

Prend une liste de noms d'interfaces réseau séparés par des espaces. Cette option restreint les interfaces réseau que les processus de cette unité peuvent utiliser. Par défaut, les processus ne peuvent utiliser que les interfaces réseau listées (liste d'autorisation). Si le premier caractère de la règle est "~", l'effet est inversé : les processus ne peuvent utiliser que les interfaces réseau non listées (liste de refus).

Cette option peut apparaître plusieurs fois, auquel cas les noms d'interfaces réseau sont fusionnés. Si la chaîne vide est attribuée, l'ensemble est réinitialisé, toutes les affectations précédentes n'auront aucun effet.

Si vous spécifiez les deux types de cette option (c'est-à-dire la liste d'autorisation et la liste de refus), la première rencontrée aura la priorité et déterminera l'action par défaut (autorisation ou refus). Ensuite, les occurrences suivantes de cette option ajouteront ou supprimeront les noms d'interfaces réseau listés de l'ensemble, en fonction de leur type et de l'action par défaut.

L'interface de bouclage ("lo") n'est traitée d'aucune manière spéciale, vous devez la configurer explicitement dans le fichier d'unité.

Exemple 1 : liste d'autorisation

RestrictNetworkInterfaces=eth1
RestrictNetworkInterfaces=eth2

Les programmes de l'unité ne pourront utiliser que les interfaces réseau eth1 et eth2.

Exemple 2 : liste de refus

RestrictNetworkInterfaces=~eth1 eth2

Les programmes de l'unité pourront utiliser n'importe quelle interface réseau sauf eth1 et eth2.

Exemple 3 : mixte

RestrictNetworkInterfaces=eth1 eth2
RestrictNetworkInterfaces=~eth1

Les programmes de l'unité ne pourront utiliser que l'interface réseau eth2.

IPIngressFilterPath=BPF_FS_PROGRAM_PATH, IPEgressFilterPath=BPF_FS_PROGRAM_PATH

Ajoute des filtres de trafic réseau personnalisés implémentés sous forme de programmes BPF, s'appliquant à tous les paquets IP envoyés et reçus sur les sockets AF_INET et AF_INET6. Prend un chemin absolu vers un programme BPF épinglé dans le système de fichiers virtuel BPF (/sys/fs/bpf/).

Les filtres configurés avec cette option s'appliquent à tous les sockets créés par les processus de cette unité (ou dans le cas des unités de socket, qui lui sont associés). Les filtres sont chargés en plus des filtres de toutes les unités de slice parentes dont cette unité pourrait être membre, ainsi que des filtres IPAddressAllow= et IPAddressDeny= dans l'une de ces unités. Par défaut, aucun filtre n'est spécifié.

Si ces paramètres sont utilisés plusieurs fois dans la même unité, tous les programmes spécifiés sont attachés. Si une chaîne vide est attribuée à ces paramètres, la liste des programmes est réinitialisée et tous les programmes précédemment spécifiés sont ignorés.

Si le chemin BPF_FS_PROGRAM_PATH dans l'affectation IPIngressFilterPath= est déjà géré par le hook d'entrée BPFProgram=, par exemple BPFProgram=ingress:BPF_FS_PROGRAM_PATH, l'affectation sera toujours considérée comme valide et le programme sera attaché à un cgroup. Même chose pour le chemin IPEgressFilterPath= et le hook egress.

Notez que pour les services activés par socket, les programmes de filtrage IP configurés sur l'unité de socket s'appliquent à tous les sockets qui lui sont directement associés, mais pas aux sockets créés par les services finalement activés pour celle-ci. Inversement, les programmes de filtrage IP configurés pour le service ne s'appliquent pas aux sockets passés au service via l'activation par socket. Ainsi, il est généralement conseillé de répliquer les programmes de filtrage IP sur l'unité de socket et l'unité de service, bien qu'il soit souvent judicieux de maintenir une configuration plus ouverte et l'autre plus restreinte, en fonction du cas d'utilisation.

Notez que ces paramètres peuvent ne pas être pris en charge sur certains systèmes (par exemple, si le support des groupes de contrôle eBPF n'est pas activé dans le noyau sous-jacent ou le gestionnaire de conteneurs). Ces paramètres feront échouer le service dans ce cas. Si la compatibilité avec de tels systèmes est souhaitée, il est donc recommandé d'attacher votre filtre manuellement (nécessite Delegate=yes) au lieu d'utiliser ce paramètre.

BPFProgram=type:chemin du programme

BPFProgram= permet d'attacher des programmes BPF personnalisés au cgroup d'une unité. (Cela généralise la fonctionnalité exposée via IPEgressFilterPath= et IPIngressFilterPath= pour d'autres hooks.) Les hooks cgroup-bpf sous forme de programmes BPF chargés dans le système de fichiers BPF sont attachés avec des drapeaux d'attachement cgroup-bpf déterminés par l'unité. Pour plus de détails sur les types d'attachement et les drapeaux, voir bpf.h[10]. Se référer également à la documentation générale BPF[11].

La spécification du programme BPF consiste en une paire du type de programme BPF et du chemin du programme dans le système de fichiers, avec ":" comme séparateur : type:chemin du programme.

Le type de programme BPF est équivalent au type d'attachement BPF utilisé dans bpftool(8). Il peut s'agir de egress, ingress, sock_create, sock_ops, device, bind4, bind6, connect4, connect6, post_bind4, post_bind6, sendmsg4, sendmsg6, sysctl, recvmsg4, recvmsg6, getsockopt, ou setsockopt.

Le chemin du programme spécifié doit être un chemin absolu faisant référence à un inode de programme BPF dans le système de fichiers bpffs (ce qui signifie généralement qu'il doit commencer par /sys/fs/bpf/). Si un programme spécifié n'existe pas (c'est-à-dire qu'il n'a pas encore été téléchargé dans le sous-système BPF du noyau), il ne sera pas installé mais l'activation de l'unité se poursuivra (un avertissement sera imprimé dans les journaux).

Définir BPFProgram= à une valeur vide rend les affectations précédentes inefficaces.

Plusieurs affectations de la même paire type/chemin de programme ont le même effet qu'une seule affectation : le programme sera attaché une seule fois.

Si le programme BPF egress épinglé au chemin program-path est déjà géré par IPEgressFilterPath=, l'affectation BPFProgram= sera considérée comme valide et BPFProgram= sera attaché à un cgroup. Idem pour le hook ingress et l'affectation IPIngressFilterPath=.

Les programmes BPF passés avec BPFProgram= sont attachés au cgroup d'une unité avec le drapeau d'attachement BPF multi, qui permet d'autres attachements du même type au sein de la hiérarchie des cgroups dont le cgroup de l'unité est le sommet.

Exemples :

BPFProgram=egress:/sys/fs/bpf/egress-hook
BPFProgram=bind6:/sys/fs/bpf/sock-addr-hook

Ajouté dans la version 249.

Accès aux périphériques

DeviceAllow=

Contrôle l'accès à des nœuds de périphériques spécifiques par les processus exécutés. Prend deux chaînes séparées par des espaces : un spécificateur de nœud de périphérique suivi d'une combinaison de r, w, m pour contrôler la lecture, l'écriture ou la création (mknod) des nœuds de périphériques spécifiques par l'unité, respectivement. Cette fonctionnalité est implémentée à l'aide du filtrage eBPF.

Lorsque l'accès à tous les périphériques physiques doit être refusé, PrivateDevices= peut être utilisé à la place

ad. Voir systemd.exec(5).

Le spécificateur de nœud de périphérique est soit un chemin d'accès à un nœud de périphérique dans le système de fichiers, commençant par /dev/, soit une chaîne commençant par "char-" ou "block-" suivie d'un nom de groupe de périphériques, tel que listé dans /proc/devices. Ce dernier est utile pour autoriser toutes les périphériques actuels et futurs appartenant à un groupe de périphériques spécifique à la fois. Le groupe de périphériques est correspondant selon les règles de globbing de noms de fichiers, vous pouvez donc utiliser les caractères génériques "*" et "?". (Notez que de tels caractères génériques de globbing ne sont pas disponibles pour les spécificateurs de chemins de nœuds de périphériques !) Afin de faire correspondre les nœuds de périphériques par majeur/mineur numérique, utilisez les chemins de nœuds de périphériques dans les répertoires /dev/char/ et /dev/block/. Cependant, la correspondance des périphériques par majeur/mineur n'est généralement pas recommandée car les affectations ne sont ni stables ni portables entre les systèmes ou les différentes versions du noyau.

Exemples : /dev/sda5 est un chemin d'accès à un nœud de périphérique, faisant référence à un périphérique bloc ATA ou SCSI. "char-pts" et "char-alsa" sont des spécificateurs pour tous les TTY pseudo et tous les périphériques sonores ALSA, respectivement. "char-cpu/*" est un spécificateur faisant correspondance à tous les groupes de périphériques liés au CPU.

Notez que les listes d'autorisation définies de cette manière ne devraient référencer que des groupes de périphériques qui sont résolubles au moment où l'unité est démarrée. Tous les groupes de périphériques non résolubles alors ne sont pas ajoutés à la liste d'autorisation des périphériques. Afin de contourner cette limitation, envisagez d'étendre les unités de service avec une paire de lignes After=modprobe@xyz.service et Wants=modprobe@xyz.service qui chargent le module noyau nécessaire implémentant le groupe de périphériques s'il manque. Exemple :

...
[Unit]
Wants=modprobe@loop.service
After=modprobe@loop.service
[Service]
DeviceAllow=block-loop
DeviceAllow=/dev/loop-control
...

Cette option ne peut pas être contournée en préfixant "+" au chemin d'accès de l'exécutable dans l'unité de service, car elle s'applique à tout le groupe de contrôle.

Ajouté dans la version 208.

DevicePolicy=auto|closed|strict

Contrôle la politique d'autorisation d'accès aux périphériques :

strict

signifie n'autoriser que les types d'accès qui sont explicitement spécifiés.

Ajouté dans la version 208.

closed

en outre, autorise l'accès aux périphériques pseudo standards, y compris /dev/null, /dev/zero, /dev/full, /dev/random et /dev/urandom.

Ajouté dans la version 208.

auto

en outre, autorise l'accès à tous les périphériques si aucun DeviceAllow= explicite n'est présent. C'est le défaut.

Ajouté dans la version 208.

Cette option ne peut pas être contournée en préfixant "+" au chemin d'accès de l'exécutable dans l'unité de service, car elle s'applique à tout le groupe de contrôle.

Ajouté dans la version 208.

Gestion des groupes de contrôle

Slice=

Le nom de l'unité slice dans laquelle placer l'unité. Par défaut, system.slice pour toutes les unités non instanciées de tous les types d'unités (sauf pour les unités slice elles-mêmes, voir ci-dessous). Les unités instanciées sont par défaut placées dans une sous-slice de system.slice nommée d'après le nom du modèle.

Cette option peut être utilisée pour organiser les unités systemd dans une hiérarchie de slices auxquelles des paramètres de ressources pourraient être appliqués.

Pour les unités de type slice, la seule valeur acceptée pour ce paramètre est la slice parente. Étant donné que le nom d'une unité slice implique la slice parente, il est donc redondant de définir ce paramètre directement pour les unités slice.

Une attention particulière doit être portée lors de la dépendance à l'affectation par défaut de slice dans les unités de service de type modèle avec DefaultDependencies=no défini, voir systemd.service(5), section "Default Dependencies" pour plus de détails.

Ajouté dans la version 208.

Delegate=

Active la délégation de la partition supplémentaire de contrôle des ressources aux processus de l'unité. Les unités où cela est activé peuvent créer et gérer leur propre sous-hiérarchie privée de groupes de contrôle en dessous du groupe de contrôle de l'unité elle-même. Pour les services non privilégiés (c'est-à-dire ceux utilisant le paramètre User=), le groupe de contrôle de l'unité sera rendu accessible à l'utilisateur concerné.

Lorsque cela est activé, le gestionnaire de services s'abstiendra de manipuler les groupes de contrôle ou de déplacer des processus en dessous du groupe de contrôle de l'unité, de sorte qu'un concept clair de propriété soit établi : l'arbre des groupes de contrôle au niveau du groupe de contrôle de l'unité et au-dessus (c'est-à-dire vers le groupe de contrôle racine) est possédé et géré par le gestionnaire de services de l'hôte, tandis que l'arbre des groupes de contrôle en dessous du groupe de contrôle de l'unité est possédé et géré par l'unité elle-même.

Prend soit un argument booléen, soit une liste (éventuellement vide) de noms de contrôleurs de groupes de contrôle. Si vrai, la délégation est activée, et tous les contrôleurs pris en charge sont activés pour l'unité, les rendant disponibles pour la gestion par les processus de l'unité. Si faux, la délégation est complètement désactivée (et aucun contrôleur supplémentaire n'est activé). S'il est défini sur une liste de contrôleurs, la délégation est activée et les contrôleurs spécifiés sont activés pour l'unité. L'affectation d'une chaîne vide activera la délégation, mais réinitialisera la liste des contrôleurs, et toutes les affectations antérieures à celle-ci n'auront aucun effet. Notez que des contrôleurs supplémentaires autres que ceux spécifiés pourraient également être rendus disponibles, en fonction de la configuration de l'unité slice parente ou d'autres unités qu'elle contient. Par défaut, faux.

Notez que la délégation de contrôleurs à du code moins privilégié n'est sûre que sur la hiérarchie unifiée des groupes de contrôle. Par conséquent, l'accès aux contrôleurs spécifiés ne sera pas accordé aux services non privilégiés sur la hiérarchie héritée, même s'il est demandé.

Les noms de contrôleurs suivants peuvent être spécifiés : cpu, cpuset, io, memory, pids, bpf-firewall, bpf-devices, bpf-foreign, bpf-socket-bind, et bpf-restrict-network-interfaces.

Tous ces contrôleurs ne sont cependant pas disponibles sur tous les noyaux, et certains sont spécifiques à la hiérarchie unifiée tandis que d'autres sont spécifiques à la hiérarchie héritée. Notez également que le noyau peut prendre en charge des contrôleurs supplémentaires, qui ne sont pas encore couverts ici, car la délégation n'est supportée ni du tout pour eux, ni définie proprement.

Notez qu'en raison de la nature hiérarchique de la hiérarchie cgroup, tous les contrôleurs qui sont délégués seront activés pour les unités parentes et sœurs de l'unité avec délégation.

Pour plus de détails sur le modèle de délégation, consultez APIs et délégation des groupes de contrôle[12].

Ajouté dans la version 218.

DelegateSubgroup=

Place les processus de l'unité dans le sous-groupe spécifié du groupe de contrôle de l'unité. Prend un nom de groupe de contrôle valide (pas un chemin !) comme paramètre, ou une chaîne vide pour désactiver cette fonctionnalité. Par défaut, désactivé. Le nom du groupe de contrôle doit être utilisable comme nom de fichier et éviter les conflits avec les fichiers d'attributs de groupe de contrôle du noyau (c'est-à-dire que cgroup.procs n'est pas un nom acceptable, car le noyau expose un fichier d'attribut de groupe de contrôle natif sous ce nom). Cette option n'a aucun effet sauf si la délégation de groupe de contrôle est activée via Delegate=, voir ci-dessus. Notez que ce paramètre ne s'applique qu'aux processus "principaux" d'une unité, c'est-à-dire pour les services à ExecStart=, mais pas pour ExecReload= et similaires. Si la délégation est activée, ces derniers sont toujours placés dans un sous-groupe nommé .control. Le sous-groupe spécifié est automatiquement créé (et potentiellement la propriété est transmise à l'utilisateur/groupe configuré de l'unité) lorsqu'un processus y est démarré.

Cette option est utile pour éviter de déplacer manuellement le processus invoqué dans un sous-groupe après son démarrage. Comme aucun processus ne doit vivre dans les nœuds internes de l'arbre des groupes de contrôle, il est presque toujours nécessaire d'exécuter le processus principal ("supervisant") d'une unité pour laquelle la délégation est activée dans un sous-groupe.

Ajouté dans la version 254.

DisableControllers=

Désactive les contrôleurs pour les enfants d'une unité. Si un contrôleur listé est déjà utilisé dans son sous-arbre, le contrôleur sera retiré du sous-arbre. Ceci peut être utilisé pour éviter que la configuration dans les unités enfants ne puisse activer implicitement ou explicitement un contrôleur. Par défaut, vide.

Plusieurs contrôleurs peuvent être spécifiés, séparés par des espaces. Vous pouvez également passer DisableControllers= plusieurs fois, auquel cas chaque nouvelle instance ajoute un contrôleur à désactiver. Passer DisableControllers= seul sans nom de contrôleur présent réinitialise la liste des contrôleurs désactivés.

Il peut ne pas être possible de désactiver un contrôleur après le démarrage des unités, si l'unité ou un enfant de l'unité en question délègue des contrôleurs à ses enfants, car tout sous-arbre délégué de la hiérarchie cgroup est non géré par systemd.

Les noms de contrôleurs suivants peuvent être spécifiés : cpu, cpuset, io, memory, pids, bpf-firewall, bpf-devices, bpf-foreign, bpf-socket-bind, et bpf-restrict-network-interfaces.

Ajouté dans la version 240.

Gestion de la pression mémoire

ManagedOOMSwap=auto|kill, ManagedOOMMemoryPressure=auto|kill

Spécifie comment systemd-oomd.service(8) agira sur les cgroups de cette unité. Par défaut, auto.

Lorsqu'il est défini sur kill, l'unité devient un candidat pour la surveillance par systemd-oomd. Si le cgroup dépasse les limites fixées par oomd.conf(5) ou la configuration de l'unité, systemd-oomd sélectionnera un cgroup descendant et enverra SIGKILL à tous les processus qui s'y trouvent. Vous trouverez plus de détails sur les candidats et le comportement d'arrêt dans systemd-oomd.service(8) et oomd.conf(5).

Définir l'une de ces propriétés sur kill entraînera également des dépendances After= et Wants= sur systemd-oomd.service, sauf si DefaultDependencies=no.

Lorsqu'il est défini sur auto, systemd-oomd n'utilisera pas activement les données de ce cgroup pour la surveillance et la détection. Cependant, si un cgroup parent a l'une de ces propriétés définie sur kill, une unité avec auto peut toujours être un candidat pour que systemd-oomd y mette fin.

Ajouté dans la version 247.

ManagedOOMMemoryPressureLimit=

Remplace la limite de pression mémoire par défaut définie par oomd.conf(5) pour le cgroup de cette unité. Prend un pourcentage entre 0% et 100%, inclus. Par défaut, 0%, ce qui signifie utiliser le défaut défini par href='/man/oomd.conf.5.fr'>oomd.conf(5). Cette propriété est ignorée sauf si ManagedOOMMemoryPressure=kill.

Ajouté dans la version 247.

ManagedOOMMemoryPressureDurationSec=

Remplace la durée de pression mémoire par défaut définie par oomd.conf(5) pour le cgroup de cette unité. La valeur spécifiée prend en charge une unité de temps comme « ms » ou « µs », voir systemd.time(7) pour les détails sur la syntaxe autorisée. Doit être réglé soit à vide, soit à une valeur d'au moins 1 s. La valeur par défaut est vide, ce qui signifie qu'elle utilisera la valeur par défaut définie par oomd.conf(5). Cette propriété est ignorée sauf si ManagedOOMMemoryPressure=kill.

Ajouté dans la version 257.

ManagedOOMPreference=none|avoid|omit

Permet de déprioriser ou d'omettre le cgroup de cette unité en tant que candidat lorsque systemd-oomd doit agir. Nécessite la prise en charge des attributs étendus (voir xattr(7)) pour utiliser avoid ou omit.

Lors du calcul des candidats pour soulager l'utilisation du swap, systemd-oomd ne respectera ces attributs étendus que si le cgroup de l'unité appartient à root.

Lors du calcul des candidats pour soulager la pression mémoire, systemd-oomd ne respectera ces attributs étendus que si le cgroup de l'unité appartient à root, ou si le propriétaire du cgroup de l'unité et le propriétaire du cgroup ancêtre surveillé sont les mêmes. Par exemple, si systemd-oomd calcule des candidats pour -.slice, alors les attributs étendus définis sur les descendants de /user.slice/user-1000.slice/user@1000.service/ seront ignorés car les descendants appartiennent à l'UID 1000 et -.slice appartient à l'UID 0. Mais, si des candidats sont calculés pour /user.slice/user-1000.slice/user@1000.service/, alors les attributs étendus définis sur les descendants seraient respectés.

Si cette propriété est définie à avoid, le gestionnaire de services le communiquera à systemd-oomd, qui ne sélectionnera ce cgroup que s'il n'y a pas d'autres candidats viables.

Si cette propriété est définie à omit, le gestionnaire de services le communiquera à systemd-oomd, qui ignorera ce cgroup en tant que candidat et n'effectuera aucune action dessus.

Il est recommandé d'utiliser avoid et omit avec parcimonie, car cela peut affecter négativement le comportement d'arrêt de systemd-oomd. Notez également que ces attributs étendus ne sont pas appliqués récursivement aux cgroups sous le cgroup de cette unité.

Par défaut, none, ce qui signifie que systemd-oomd classera le cgroup de cette unité tel que défini dans systemd-oomd.service(8) et oomd.conf(5).

Ajouté dans la version 248.

MemoryPressureWatch=

Contrôle la surveillance de la pression mémoire pour les processus invoqués. Prend un argument booléen ou l'une des valeurs « auto » et « skip ». Si « no », indique au service de ne pas surveiller les événements de pression mémoire, en définissant la variable d'environnement $MEMORY_PRESSURE_WATCH sur la chaîne littérale /dev/null. Si « yes », indique au service de surveiller les événements de pression mémoire. Cela active la comptabilité mémoire pour le service et garantit que le fichier d'attribut cgroup memory.pressure est accessible en lecture et en écriture par l'utilisateur du service. Il définit ensuite la variable d'environnement $MEMORY_PRESSURE_WATCH pour les processus invoqués par l'unité vers le chemin du système de fichiers de ce fichier. Les informations de seuil configurées avec MemoryPressureThresholdSec= sont codées dans la variable d'environnement $MEMORY_PRESSURE_WRITE. Si la valeur « auto » est définie, le protocole est activé si la comptabilité mémoire est de toute façon activée pour l'unité, et désactivé sinon. Si défini à « skip », la logique n'est ni activée ni désactivée et les deux variables d'environnement ne sont pas définies.

Notez que les services sont libres d'utiliser les deux variables d'environnement, mais il n'y a pas de problème s'ils les ignorent. La gestion de la pression mémoire doit être implémentée individuellement dans chaque service, et signifie généralement des choses différentes pour des logiciels différents. Pour plus de détails sur la gestion de la pression mémoire, voir Gestion de la pression mémoire dans systemd[13].

Les services implémentés à l'aide de sd-event(3) peuvent utiliser sd_event_add_memory_pressure(3) pour surveiller et gérer les événements de pression mémoire.

Si non explicitement défini, la valeur par défaut est le paramètre DefaultMemoryPressureWatch= dans systemd-system.conf(5).

Ajouté dans la version 254.

MemoryPressureThresholdSec=

Définit le temps de seuil de pression mémoire pour le moniteur de pression mémoire tel que configuré via MemoryPressureWatch=. Spécifie la latence d'allocation maximale avant qu'un événement de pression mémoire ne soit signalé au service, par fenêtre de 2 secondes. Si non spécifié, la valeur par défaut est le paramètre DefaultMemoryPressureThresholdSec= dans systemd-system.conf(5) (qui par défaut est de 200 ms). La valeur spécifiée attend une unité de temps comme « ms » ou « µs », voir systemd.time(7) pour les détails sur la syntaxe autorisée.

Ajouté dans la version 254.

Contrôle des CoreDumps

CoredumpReceive=

Prend un argument booléen. Ce paramètre est utilisé pour activer la transmission des coredumps pour les conteneurs qui appartiennent au cgroup de cette unité. Les unités avec CoredumpReceive=yes doivent également être configurées avec Delegate=yes. La valeur par défaut est false.

Lorsque systemd-coredump gère un coredump pour un processus provenant d'un conteneur, si le processus leader du conteneur est un descendant d'un cgroup avec CoredumpReceive=yes et Delegate=yes, alors systemd-coredump tentera de transmettre le coredump à systemd-coredump à l'intérieur du conteneur. Voir également systemd-coredump(8).

NAME

systemd.resource-control - Cgroups and resource control in systemd

SYNOPSIS

systemd.resource-control.service, systemd.resource-control.scope, systemd.resource-control.slice, systemd.resource-control.machine

DESCRIPTION

systemd uses cgroups (control groups) to organize processes and control their resource usage. Cgroups are a Linux kernel feature that allows you to allocate, limit, and account for the usage of system resources such as CPU, memory, disk I/O, and network bandwidth.

systemd manages cgroups in a hierarchical structure, mirroring the hierarchy of systemd units. Each unit can be placed in its own cgroup, allowing for fine-grained resource control. The resource control parameters for a unit can be configured using directives in its unit file or dynamically via the systemd API.

The resource control mechanism in systemd is primarily exposed through the following unit types:

  • .service: Used to manage system services. Resource control settings can be applied to the processes started by a service.
  • .scope: Used to manage a group of processes that are not necessarily related to each other, typically created dynamically. Resource control can be applied to all processes within a scope.
  • .slice: Used to represent a subtree in the cgroup hierarchy. Slices are used to group units and apply resource limits to the entire group. By default, all units are placed in the system slice (system.slice) or the user slice (user.slice).
  • .machine: Used to represent a system or a container. Units belonging to a machine are placed within the machine's cgroup.

Directives related to resource control are placed within the [Resources] section of a unit file. These directives allow you to specify limits for CPU, memory, I/O, and other resources.

IMPLICIT DEPENDENCIES

The resource control functionality relies on the availability and proper configuration of the Linux cgroup subsystem. systemd automatically sets up and manages cgroup hierarchies for units.

OPTIONS

Resource control options are specified as directives within the [Resources] section of unit files. Some common directives include:

  • CPUQuota=: Specifies the maximum CPU time that a cgroup can use.
  • MemoryLimit=: Sets the maximum amount of memory a cgroup can allocate.
  • IOWeight=: Controls the relative I/O bandwidth of a cgroup.
  • DevicePolicy=: Restricts access to specific devices.

For a comprehensive list of resource control directives, refer to the systemd.resource-control(5) man page and the systemd documentation.

HISTORY

The systemd resource control features have evolved significantly with the development of systemd and the cgroup subsystem in the Linux kernel. Initial versions focused on basic cgroup management, while later versions introduced more advanced features and finer-grained control.

systemd.unit(5), systemd.service(5), systemd.slice(5), systemd.scope(5), systemd.machine(5), cgroups(7)

NOTES

Resource control settings can significantly impact system performance and stability. It is recommended to test resource limits thoroughly before applying them in production environments. Misconfiguration can lead to performance degradation or unexpected service failures.

The specific directives and their behavior may vary slightly between different versions of systemd and Linux kernel. Always consult the man pages relevant to your system version for the most accurate information.
