SYSTEM(3P) Manuel du programmeur POSIX SYSTEM(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

system — émettre une commande

SYNTAXE

#include <stdlib.h>
int system(const char *command);

DESCRIPTION

La fonctionnalité décrite sur cette page de référence est alignée sur la norme ISO C. Tout conflit entre les exigences décrites ici et la norme ISO C est involontaire. Ce volume de POSIX.1‐2017 s'en remet à la norme ISO C.

Si command est un pointeur nul, la fonction system() détermine si l'environnement hôte possède un processeur de commandes. Si command n'est pas un pointeur nul, la fonction system() transmet la chaîne pointée par command à ce processeur de commandes pour qu'il l'exécute d'une manière définie par l'implémentation ; cela peut alors amener le programme appelant system() à se comporter d'une manière non conforme ou à se terminer.

La fonction system() se comporte comme si un processus fils avait été créé en utilisant fork(), et le processus fils avait invoqué l'utilitaire sh en utilisant execl() comme suit :

execl(<chemin du shell>, "sh", "-c", command, (char *)0);

où <chemin du shell> est un chemin non spécifié vers l'utilitaire sh. Il n'est pas spécifié si les gestionnaires enregistrés avec pthread_atfork() sont appelés dans le cadre de la création du processus fils.

La fonction system() ignore les signaux SIGINT et SIGQUIT, et bloque le signal SIGCHLD, en attendant la fin de la commande. Si cela risque de faire manquer à l'application un signal qui l'aurait tuée, alors l'application doit examiner la valeur de retour de system() et prendre les mesures appropriées à l'application si la commande s'est terminée suite à la réception d'un signal.

La fonction system() n'affecte pas le statut de terminaison des fils des processus appelants autres que le processus ou les processus qu'elle crée elle-même.

La fonction system() ne retourne pas tant que le processus fils ne s'est pas terminé.

La fonction system() n'a pas besoin d'être thread-safe.

VALEUR DE RETOUR

Si command est un pointeur nul, system() renvoie une valeur non nulle pour indiquer qu'un processeur de commandes est disponible, ou zéro si aucun n'est disponible. La fonction system() renvoie toujours une valeur non nulle lorsque command est NULL.

Si command n'est pas un pointeur nul, system() renvoie le statut de terminaison de l'interpréteur de commandes dans le format spécifié par waitpid(). Le statut de terminaison est tel que défini pour l'utilitaire sh ; sinon, le statut de terminaison n'est pas spécifié. Si une erreur empêche l'exécution de l'interpréteur de commandes après la création du processus fils, la valeur de retour de system() sera comme si l'interpréteur de commandes s'était terminé en utilisant exit(127) ou _exit(127). Si un processus fils ne peut pas être créé, ou si le statut de terminaison de l'interpréteur de commandes ne peut pas être obtenu, system() renvoie -1 et définit errno pour indiquer l'erreur.

ERREURS

La fonction system() peut définir des valeurs errno telles que décrites par fork().

De plus, system() peut échouer si :

ECHILD
Le statut du processus fils créé par system() n'est plus disponible.

Les sections suivantes sont informatives.

USAGE APPLICATIF

Si la valeur de retour de system() n'est pas -1, sa valeur peut être décodée en utilisant les macros décrites dans <sys/wait.h>. Pour plus de commodité, ces macros sont également fournies dans <stdlib.h>.

Notez que, bien que system() doive ignorer SIGINT et SIGQUIT et bloquer SIGCHLD en attendant la fin du fils, la gestion des signaux dans la commande exécutée est telle que spécifiée par fork() et exec. Par exemple, si SIGINT est capturé ou défini sur SIG_DFL lors de l'appel de system(), alors le fils est lancé avec la gestion de SIGINT définie sur SIG_DFL.

Ignorer SIGINT et SIGQUIT dans le processus parent évite les problèmes de coordination (deux processus lisant sur le même terminal, par exemple) lorsque la commande exécutée ignore ou capture l'un des signaux. C'est aussi généralement l'action correcte lorsque l'utilisateur a donné une commande à l'application à exécuter de manière synchrone (comme dans la commande '!' de nombreuses applications interactives). Dans les deux cas, le signal ne doit être délivré qu'au processus fils, et non à l'application elle-même. Il y a une situation où ignorer les signaux peut avoir moins d'effet que souhaité. C'est lorsque l'application utilise system() pour effectuer une tâche invisible pour l'utilisateur. Si l'utilisateur tapait le caractère d'interruption ("^C", par exemple) pendant que system() est utilisé de cette manière, on s'attendrait à ce que l'application soit tuée, mais seule la commande exécutée est tuée. Les applications qui utilisent system() de cette manière doivent examiner attentivement le statut de retour de system() pour voir si la commande exécutée a réussi, et doivent prendre les mesures appropriées en cas d'échec de la commande.

Bloquer SIGCHLD en attendant la fin du fils empêche l'application de capturer le signal et d'obtenir le statut du processus fils de system() avant que system() ne puisse obtenir le statut lui-même.

Le contexte dans lequel l'utilitaire est finalement exécuté peut différer de celui dans lequel system() a été appelé. Par exemple, les descripteurs de fichiers qui ont le drapeau FD_CLOEXEC défini sont fermés, et l'ID de processus et l'ID de processus parent sont différents. De plus, si l'utilitaire exécuté modifie ses variables d'environnement ou son répertoire de travail actuel, ce changement n'est pas reflété dans le contexte de l'appelant.

Il n'y a pas de moyen défini pour une application de trouver le chemin spécifique du shell. Cependant, confstr() peut fournir une valeur pour PATH qui garantit de trouver l'utilitaire sh.

L'utilisation de la fonction system() dans plus d'un fil d'exécution dans un processus ou lorsque le signal SIGCHLD est manipulé par plus d'un fil d'exécution dans un processus peut produire des résultats inattendus.

JUSTIFICATION

La fonction system() ne doit pas être utilisée par des programmes qui ont des privilèges d'ID utilisateur (ou de groupe) définis. Les fonctions fork() et la famille exec (sauf execlp() et execvp()), doivent être utilisées à la place. Cela empêche toute manipulation imprévue de l'environnement de l'utilisateur qui pourrait entraîner l'exécution de commandes non anticipées par le programme appelant.

Il existe trois niveaux de spécification pour la fonction system(). La norme ISO C donne la plus basique. Elle exige que la fonction existe et définit un moyen pour une application de vérifier si un interpréteur de langage de commande existe. Elle ne dit rien sur le langage de commande ni sur l'environnement dans lequel la commande est interprétée.

POSIX.1‐2008 impose des restrictions supplémentaires à system(). Il exige que, s'il existe un interpréteur de langage de commande, l'environnement soit tel que spécifié par fork() et exec. Cela garantit, par exemple, que close-on-exec fonctionne, que les verrous de fichiers ne sont pas hérités et que l'ID de processus est différent. Il spécifie également la valeur de retour de system() lorsque la ligne de commande peut être exécutée, donnant ainsi à l'application des informations sur le statut d'achèvement de la commande.

Enfin, POSIX.1‐2008 exige que la commande soit interprétée comme dans le langage de commande shell défini dans le volume Shell et utilitaires de POSIX.1‐2017.

Notez que system(NULL) est tenu de renvoyer une valeur non nulle, indiquant qu'il existe un interpréteur de langage de comman

reter. À première vue, cela pourrait sembler contredire la norme ISO C qui autorise system(NULL) à retourner zéro. Il n'y a cependant aucun conflit. Un système doit disposer d'un interpréteur de langage de commande, et n'est non conforme si aucun n'est présent. Il est donc permis que la fonction system() sur un tel système implémente le comportement spécifié par la norme ISO C tant qu'il est entendu que l'implémentation n'est pas conforme à POSIX.1‐2008 si system(NULL) retourne zéro.

Il a été explicitement décidé que lorsque command est NULL, system() ne devrait pas être tenu de vérifier si l'interpréteur de langage de commande existe réellement avec le bon mode, s'il y a suffisamment de processus pour l'exécuter, etc. L'appel system(NULL) pourrait, théoriquement, vérifier des problèmes tels qu'un trop grand nombre de processus enfants existants et retourner zéro. Cependant, il serait inapproprié de retourner zéro en raison d'une condition (vraisemblablement) transitoire. Si une condition existe qui n'est pas sous le contrôle de cette application et qui entraînerait l'échec de tout appel system(), ce système a été rendu non conforme.

Les premières ébauches exigeaient, ou autorisaient, system() à retourner avec errno défini sur [EINTR] s'il était interrompu par un signal. Ce retour d'erreur a été supprimé, et une exigence que system() ne retourne pas avant que l'enfant n'ait terminé a été ajoutée. Cela signifie que si un appel waitpid() dans system() se termine avec errno défini sur [EINTR], system() doit réémettre le waitpid(). Ce changement a été apporté pour deux raisons :

1.
Il n'y a aucun moyen pour une application de se nettoyer si system() retourne [EINTR], sans appeler wait(), et cela pourrait avoir l'effet indésirable de retourner le statut d'enfants autres que celui démarré par system().
2.
Bien que cela puisse nécessiter une modification de certaines implémentations historiques, ces implémentations ont déjà dû être modifiées car elles utilisent wait() au lieu de waitpid().

Notez que si l'application intercepte les signaux SIGCHLD, elle recevra un tel signal avant qu'un appel system() réussi ne retourne.

Pour être conforme à POSIX.1‐2008, system() doit utiliser waitpid(), ou une fonction similaire, au lieu de wait().

L'exemple de code suivant illustre comment system() pourrait être implémenté sur une implémentation conforme à POSIX.1‐2008.

#include <signal.h>
int system(const char *cmd)
{
    int stat;
    pid_t pid;
    struct sigaction sa, savintr, savequit;
    sigset_t saveblock;
    if (cmd == NULL)
        return(1);
    sa.sa_handler = SIG_IGN;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sigemptyset(&savintr.sa_mask);
    sigemptyset(&savequit.sa_mask);
    sigaction(SIGINT, &sa, &savintr);
    sigaction(SIGQUIT, &sa, &savequit);
    sigaddset(&sa.sa_mask, SIGCHLD);
    sigprocmask(SIG_BLOCK, &sa.sa_mask, &saveblock);
    if ((pid = fork()) == 0) {
        sigaction(SIGINT, &savintr, (struct sigaction *)0);
        sigaction(SIGQUIT, &savequit, (struct sigaction *)0);
        sigprocmask(SIG_SETMASK, &saveblock, (sigset_t *)0);
        execl("/bin/sh", "sh", "-c", cmd, (char *)0);
        _exit(127);
    }
    if (pid == -1) {
        stat = -1; /* errno comes from fork() */
    } else {
        while (waitpid(pid, &stat, 0) == -1) {
            if (errno != EINTR){
                stat = -1;
                break;
            }
        }
    }
    sigaction(SIGINT, &savintr, (struct sigaction *)0);
    sigaction(SIGQUIT, &savequit, (struct sigaction *)0);
    sigprocmask(SIG_SETMASK, &saveblock, (sigset_t *)0);
    return(stat);
}

Notez que, bien qu'une implémentation particulière de system() (comme celle ci-dessus) puisse supposer un chemin particulier pour le shell, un tel chemin n'est pas nécessairement valide sur un autre système. L'exemple ci-dessus n'est pas portable, et n'a pas l'intention de l'être.

Notez également que l'implémentation ci-dessus n'est pas thread-safe. Les implémentations peuvent fournir une fonction system() thread-safe, mais cela implique des complications telles que la manière de restaurer correctement les dispositions de signal pour SIGINT et SIGQUIT en cas d'appels chevauchants, et comment gérer les annulations. L'exemple ci-dessus ne restaurerait pas les dispositions de signal et laisserait fuir un ID de processus s'il était annulé. Cela n'a pas d'importance pour une implémentation non thread-safe car l'annulation d'une fonction non thread-safe entraîne un comportement indéfini (voir Section 2.9.5.2, Points d'annulation). Pour éviter de laisser fuir un ID de processus, une implémentation thread-safe devrait terminer le processus enfant lors de l'annulation.

Un examinateur a suggéré qu'une implémentation de system() pourrait vouloir utiliser une variable d'environnement telle que SHELL pour déterminer quel interpréteur de commande utiliser. L'implémentation supposée utiliserait l'interpréteur de commande par défaut si celui spécifié par la variable d'environnement n'était pas disponible. Cela permettrait à un utilisateur, lors de l'utilisation d'une application qui invite à saisir des lignes de commande à traiter via system(), de spécifier un interpréteur de commande différent. Une telle implémentation est déconseillée. Si l'interpréteur de commande alternatif ne suivait pas la syntaxe de ligne de commande spécifiée dans le volume Shell et Utilitaires de POSIX.1‐2017, alors changer SHELL rendrait system() non conforme. Cela affecterait les applications qui attendaient le comportement spécifié de system(), et comme le volume Shell et Utilitaires de POSIX.1‐2017 ne mentionne pas que SHELL affecte system(), l'application ne saurait pas qu'elle doit désactiver SHELL.
