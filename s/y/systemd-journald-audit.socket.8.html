DESCRIPTION

systemd-journald est un service système qui collecte et stocke les données de journalisation. Il crée et maintient des journaux structurés et indexés basés sur les informations de journalisation reçues de diverses sources :

•Messages du journal du noyau, via kmsg
•Messages simples du journal système, via l'appel syslog(3) de la libc
•Messages du journal système structurés via l'API native du journal, voir sd_journal_print(3) et le Protocole natif du journal[1]
•Sortie standard et erreur standard des unités de service. Pour plus de détails, voir ci-dessous.
•Enregistrements d'audit, provenant du sous-système d'audit du noyau

Le démon collectera implicitement de nombreux champs de métadonnées pour chaque message de journal de manière sécurisée et infalsifiable. Voir systemd.journal-fields(7) pour plus d'informations sur les métadonnées collectées.

Les données du journal collectées par le journal sont principalement basées sur du texte mais peuvent également inclure des données binaires si nécessaire. Les champs individuels constituant un enregistrement de journal stocké dans le journal peuvent avoir une taille allant jusqu'à 2^64-1 octets.

Le service journal stocke les données du journal soit de manière persistante sous /var/log/journal, soit de manière volatile sous /run/log/journal/ (dans ce dernier cas, elles sont perdues au redémarrage). Par défaut, les données du journal sont stockées de manière persistante si /var/log/journal/ existe au démarrage, avec un repli implicite vers un stockage volatile sinon. Utilisez Storage= dans journald.conf(5) pour configurer où les données du journal sont placées, indépendamment de l'existence de /var/log/journal/.

Notez que journald utilisera initialement un stockage volatil, jusqu'à ce qu'un appel à journalctl --flush (ou l'envoi de SIGUSR1 à journald) le fasse basculer vers la journalisation persistante (dans les conditions mentionnées ci-dessus). Ceci est fait automatiquement au démarrage via le service "systemd-journal-flush.service".

Sur les systèmes où /var/log/journal/ n'existe pas encore mais où la journalisation persistante est souhaitée (et où la configuration par défaut de journald.conf est utilisée), il suffit de créer le répertoire et de s'assurer qu'il a les modes d'accès et la propriété corrects :

mkdir -p /var/log/journal
systemd-tmpfiles --create --prefix /var/log/journal

Voir journald.conf(5) pour des informations sur la configuration de ce service.

JOURNALISATION PAR FLUX

Le gestionnaire de services systemd invoque tous les processus de service avec la sortie standard et l'erreur standard connectées au journal par défaut. Ce comportement peut être modifié via les paramètres de fichier d'unité StandardOutput=/StandardError=, voir systemd.exec(5) pour les détails. Le journal convertit le flux d'octets de journalisation reçu de cette manière en enregistrements de journal individuels, en divisant le flux aux caractères de fin de ligne ("\n", ASCII 10) et NUL.

Si systemd-journald.service est arrêté, les connexions de flux associées à tous les services sont terminées. Les écritures ultérieures dans ces flux par le service entraîneront des erreurs EPIPE. Afin de réagir gracieusement dans ce cas, il est recommandé aux programmes qui journalisent vers la sortie standard/erreur d'ignorer ces erreurs. Si le gestionnaire de signal UNIX SIGPIPE n'est pas bloqué ou désactivé, les tentatives d'écriture entraîneront également la génération de signaux de processus, voir signal(7). Pour atténuer ce problème, le gestionnaire de services systemd désactive explicitement le signal SIGPIPE pour tous les processus invoqués par défaut (cela peut être modifié pour chaque unité individuellement via l'option IgnoreSIGPIPE=, voir systemd.exec(5) pour les détails). Une fois les flux de sortie standard/erreur standard terminés, ils peuvent ne pas être récupérables avant que les services auxquels ils sont associés ne soient redémarrés. Notez que pendant le fonctionnement normal, systemd-journald.service stocke des copies des descripteurs de fichiers pour ces flux dans le gestionnaire de services. Si systemd-journald.service est redémarré en utilisant systemctl restart ou une opération équivalente au lieu d'une paire de commandes distinctes systemctl stop et systemctl start (ou opérations équivalentes), ces connexions de flux ne sont pas terminées et survivent au redémarrage. Il est donc sûr de redémarrer systemd-journald.service, mais l'arrêter n'est pas recommandé.

Notez que les métadonnées des enregistrements de journal pour les enregistrements transférés via ces flux de sortie/erreur standard reflètent les métadonnées du pair pour lequel le flux a été initialement créé. Si la connexion de flux est transmise à d'autres processus (tels que des processus enfants supplémentaires issus du processus de service principal), les enregistrements de journal ne refléteront pas leurs métadonnées, mais continueront à décrire le processus d'origine. Ceci est différent des autres transports de journalisation listés ci-dessus, qui sont intrinsèquement basés sur les enregistrements et où les métadonnées sont toujours associées à l'enregistrement individuel.

En plus de la journalisation implicite de la sortie standard/erreur des services, la journalisation par flux est également disponible via l'outil en ligne de commande systemd-cat(1).

Actuellement, le nombre de flux de journal parallèles que systemd-journald acceptera est limité à 4096. Lorsque cette limite est atteinte, d'autres flux de journal peuvent être établis mais recevront EPIPE dès le début.

ESPACES DE NOM DU JOURNAL

Les 'espaces de noms' du journal sont à la fois un mécanisme pour isoler logiquement le flux de journal des projets composés d'un ou plusieurs services du reste du système et un mécanisme pour améliorer les performances. Plusieurs espaces de noms de journal peuvent exister simultanément, chacun définissant son propre flux de journal indépendant géré par sa propre instance de systemd-journald. Les espaces de noms sont indépendants les uns des autres, tant au niveau du magasin de données qu'au niveau de l'interface IPC. Par défaut, il n'existe qu'un seul 'espace de noms par défaut', géré par systemd-journald.service (et ses unités de socket associées). Des espaces de noms supplémentaires sont créés en démarrant une instance du service modèle systemd-journald@.service. Le nom de l'instance est l'identifiant de l'espace de noms, qui est une courte chaîne de caractères utilisée pour référencer l'espace de noms du journal. Les unités de service peuvent être attribuées à un espace de noms de journal spécifique via le paramètre de fichier d'unité LogNamespace=, voir systemd.exec(5) pour les détails. Le commutateur --namespace= de journalctl(1) peut être utilisé pour visualiser le flux de journal d'un espace de noms spécifique. Si le commutateur n'est pas utilisé, le flux de journal de l'espace de noms par défaut est affiché, c'est-à-dire que les données de journal provenant d'autres espaces de noms ne sont pas visibles.

Les services associés à un espace de noms de journal spécifique peuvent journaliser via syslog(3), le protocole de journalisation natif du journal et via stdout/stderr ; la journalisation provenant des trois transports est associée à l'espace de noms.

Par défaut, seul l'espace de noms par défaut collectera les messages du noyau et des journaux d'audit.

L'instance systemd-journald de l'espace de noms par défaut est configurée via /etc/systemd/journald.conf (voir ci-dessous), tandis que les autres instances sont configurées via /etc/systemd/journald@NAMESPACE.conf. Les données du journal du journal pour l'espace de noms par défaut sont placées dans /var/log/journal/MACHINE_ID (voir ci-dessous) tandis que les données pour les autres espaces de noms se trouvent dans /var/log/journal/MACHINE_ID.NAMESPACE.

NAME

systemd-journald-audit.socket, systemd-journald-dev-log.socket, systemd-journald-fd.socket, systemd-journald-listen.socket, systemd-journald-null.socket, systemd-journald-sock.socket, systemd-journald-stdout-forwarder.socket - systemd journal audit and forwarding sockets

SYNOPSIS

systemd-journald-audit.socket

systemd-journald-dev-log.socket

systemd-journald-fd.socket

systemd-journald-listen.socket

systemd-journald-null.socket

systemd-journald-sock.socket

systemd-journald-stdout-forwarder.socket

DESCRIPTION

These are socket unit files. They activate systemd-journald.service(8) when a connection is received on the corresponding socket.

The following sockets are provided:

systemd-journald-audit.socket
Listens on the netlink audit socket (see netlink(7)). This socket is used to receive audit messages. Audit messages are forwarded to journald for processing.
systemd-journald-dev-log.socket
Listens on the socket at /run/systemd/journal/dev-log. This socket is used to receive messages from processes that log to /dev/log using the traditional UNIX domain socket. This allows systemd-journald to receive syslog messages when it is running as the primary syslog daemon.
systemd-journald-fd.socket
Listens on file descriptor 3. This socket is used for the sd_journal_print() function in the application library. It allows applications to send log messages to systemd-journald directly via a file descriptor passed during service startup.
systemd-journald-listen.socket
Listens on the socket at /run/systemd/journal/socket. This socket is used for the native journal protocol, allowing clients to send log messages to systemd-journald.
systemd-journald-null.socket
Listens on the socket at /run/systemd/journal/null. This socket is used to discard log messages sent to it.
systemd-journald-sock.socket
Listens on the socket at /run/systemd/journal/syslog. This socket is used to receive messages from processes that log to /dev/log using the traditional UNIX domain socket. This allows systemd-journald to receive syslog messages when it is running as the primary syslog daemon.
systemd-journald-stdout-forwarder.socket
Listens on the socket at /run/systemd/journal/stdout. This socket is used to forward log messages to the standard output of the systemd-journald service itself. This is primarily used for debugging systemd-journald.

When systemd-journald is started, it attempts to claim these sockets. If it succeeds, the sockets are activated and systemd-journald can begin receiving log messages. If it fails, the sockets remain inactive until systemd-journald is able to claim them.

These socket units are enabled by default and will be started automatically during the boot process.

STREAM LOGGING

In addition to the socket unit files, systemd-journald also supports stream logging via the sd-journal(3) library. This allows applications to send log messages to systemd-journald directly via a socket connection.

JOURNAL NAMESPACES

If journal namespacing is enabled, the socket paths listed above will be altered to include a namespace identifier. For example, /run/systemd/journal/socket might become /run/systemd/journal/ns/namespace-id/socket.

SIGNALS

The systemd-journald service responds to the following signals:

SIGUSR1

Request flushing of the journal files. Use the journalctl --flush command to request flushing of the journal files, and wait for the operation to complete. See journalctl(1) for details.

Added in version 186.

SIGUSR2

Request immediate rotation of the journal files. Use the journalctl --rotate command to request journal file rotation, and wait for the operation to complete.

Added in version 186.

SIGRTMIN+1

Request that all unwritten log data is written to disk. Use the journalctl --sync command to trigger journal synchronization, and wait for the operation to complete.

Added in version 228.

SIGHUP

Upon reception of the SIGHUP process signal systemd-journald will reload its configuration values and update the kernel log buffer and journals to reflect the new configuration. If ReadKmsg= has changed, the kernel log buffer will be flushed and updated as part of the reload. The active journal (e.g., persistent, volatile) will continue to be used with the updated configuration. However, if the storage mode has changed from persistent to volatile and the current journal in use is the persistent journal, then the active journal will be switched to the volatile journal.

Added in version 258.

KERNEL COMMAND LINE

A few configuration parameters from journald.conf may be overridden on the kernel command line:

systemd.journald.forward_to_syslog=, systemd.journald.forward_to_kmsg=, systemd.journald.forward_to_console=, systemd.journald.forward_to_wall=

Enables/disables forwarding of collected log messages to syslog, the kernel log buffer, the system console or wall.

See journald.conf(5) for information about these settings.

Added in version 186.

systemd.journald.max_level_store=, systemd.journald.max_level_syslog=, systemd.journald.max_level_kmsg=, systemd.journald.max_level_console=, systemd.journald.max_level_wall=, systemd.journald.max_level_socket=

Controls the maximum log level of messages that are stored in the journal, forwarded to syslog(3), kmsg, the console, wall(1), or a socket. This kernel command line options override the settings of the same names in the journald.conf(5) file.

Added in version 232.

Note that these kernel command line options are only honoured by the default namespace, see above.

ACCESS CONTROL

Journal files are, by default, owned and readable by the "systemd-journal" system group but are not writable. Adding a user to this group thus enables them to read the journal files.

By default, each user, with a UID outside the range of system users, dynamic service users, and the nobody user, will get their own set of journal files in /var/log/journal/. See Users, Groups, UIDs and GIDs on systemd systems[2] for more details about UID ranges. These journal files will not be owned by the user, however, in order to avoid that the user can write to them directly. Instead, file system ACLs are used to ensure the user gets read access only.

Additional users and groups may be granted access to journal files via file system access control lists (ACL). Distributions and administrators may choose to grant read access to all members of the "wheel" and "adm" system groups with a command such as the following:

# setfacl -Rnm g:wheel:rx,d:g:wheel:rx,g:adm:rx,d:g:adm:rx /var/log/journal/

Note that this command will update the ACLs both for existing journal files and for future journal files created in the /var/log/journal/ directory.

FILES

/etc/systemd/journald.conf

Configure systemd-journald behavior. See journald.conf(5).

Added in version 206.

/run/log/journal/machine-id/*.journal, /run/log/journal/machine-id/*.journal~, /var/log/journal/machine-id/*.journal, /var/log/journal/machine-id/*.journal~

systemd-journald writes entries to files in /run/log/journal/machine-id/ or /var/log/journal/machine-id/ with the ".journal" suffix. If the daemon is stopped uncleanly, or if the files are found to be corrupted, they are renamed using the ".journal~" suffix, and systemd-journald starts writing to a new file. /run/ is used when /var/log/journal is not available, or when Storage=volatile is set in the journald.conf(5) configuration file.

When systemd-journald ceases writing to a journal file, it will be renamed to "original-name@suffix.journal" (or "original-name@suffix.journal~"). Such files are "archived" and will not be written to any more.

In general, it is safe to read or copy any journal file (active or archived). journalctl(1) and the functions in the sd-journal(3) library should be able to read all entries that have been fully written.

systemd-journald will automatically remove the oldest archived journal files to limit disk use. See SystemMaxUse= and related settings in journald.conf(5).

Added in version 206.

/dev/kmsg, /dev/log, /run/systemd/journal/dev-log, /run/systemd/journal/socket, /run/systemd/journal/stdout

Sockets and other file node paths that systemd-journald will listen on and are visible in the file system. In addition to these, systemd-journald can listen for audit events using netlink(7), depending on whether "systemd-journald-audit.socket" is enabled or not.

Added in version 228.

If journal namespacing is used these paths are slightly altered to include a namespace identifier, see above.
