NOM

homectl, systemd-homed-firstboot.service - Créer, supprimer, modifier ou inspecter des répertoires personnels

SYNTAXE

homectl [OPTIONS...] {COMMANDE} [NOM...]

DESCRIPTION

homectl peut être utilisé pour créer, supprimer, modifier ou inspecter le répertoire personnel d'un utilisateur. C'est principalement une commande d'interface avec systemd-homed.service(8) qui gère les répertoires personnels des utilisateurs.

Les répertoires personnels gérés par systemd-homed.service sont autonomes et incluent donc l'intégralité de l'enregistrement des métadonnées de l'utilisateur dans le stockage de données du répertoire personnel lui-même, ce qui les rend faciles à migrer entre machines. En particulier, un répertoire personnel décrit un enregistrement utilisateur correspondant, et chaque enregistrement utilisateur géré par systemd-homed.service implique également l'existence et l'encapsulation d'un répertoire personnel. Le compte utilisateur et le répertoire personnel deviennent le même concept.

Les mécanismes de stockage de sauvegarde suivants sont pris en charge :

•Un fichier de boucle LUKS2 individuel crypté pour un utilisateur, stocké dans /home/*.home. Lors de la connexion, le système de fichiers contenu dans ce fichier est monté après que le volume crypté LUKS2 a été attaché. Le mot de passe de l'utilisateur est identique à la phrase secrète de cryptage du volume LUKS2. L'accès aux données sans authentification préalable de l'utilisateur n'est donc pas possible, même pour l'administrateur système. Ce mécanisme de stockage offre la sécurité des données la plus forte et est donc recommandé.
•Similaire, mais le système de fichiers LUKS2 crypté se trouve sur un périphérique de bloc régulier, tel qu'une clé USB. Dans ce mode, les répertoires personnels et toutes les données qu'ils incluent sont facilement migratifs entre les machines, simplement en branchant la clé USB sur différents systèmes à différents moments.
•Un répertoire crypté utilisant "fscrypt" sur les systèmes de fichiers qui le prennent en charge (pour le moment, il s'agit principalement de "ext4"), situé dans /home/*.homedir. Ce mécanisme fournit également un cryptage, mais considérablement plus faible que LUKS2, car la plupart des métadonnées du système de fichiers ne sont pas protégées. De plus, il ne prend actuellement pas en charge la modification des mots de passe des utilisateurs une fois le répertoire personnel créé.
•Une sous-volume "btrfs" pour chaque utilisateur, également située dans /home/*.homedir. Cela ne fournit pas de cryptage, mais une bonne prise en charge des quotas.
•Un répertoire régulier pour chaque utilisateur, également situé dans /home/*.homedir. Cela ne fournit pas de cryptage, mais constitue une solution de repli appropriée disponible sur toutes les machines, même lorsque le support LUKS2, "fscrypt" ou "btrfs" n'est pas disponible.
•Un partage de fichiers Windows (CIFS) individuel pour chaque utilisateur.

Notez que systemd-homed.service et homectl ne géreront pas les comptes d'utilisateurs UNIX "classiques" tels que créés avec useradd(8) ou des outils similaires. En particulier, cette fonctionnalité ne convient pas à la gestion des utilisateurs système (c'est-à-dire les utilisateurs avec un UID inférieur à 1000) mais est exclusive aux utilisateurs réguliers ("humains").

Notez que les utilisateurs/répertoires personnels gérés via systemd-homed.service n'apparaissent pas dans /etc/passwd et les fichiers similaires ; ils sont synthétisés via glibc NSS pendant l'exécution. Ils sont donc résolubles et peuvent être énumérés via l'outil getent(1).

Cet outil interagit directement avec systemd-homed.service et peut exécuter des commandes spécifiques sur les répertoires personnels qu'il gère. Comme chaque répertoire personnel géré de cette manière définit également un enregistrement utilisateur et groupe JSON, ces répertoires personnels peuvent également être inspectés et énumérés via userdbctl(1).

Les répertoires personnels gérés par systemd-homed.service sont généralement dans l'un des deux états suivants, ou dans un état de transition entre eux : lorsqu'ils sont "actifs", ils sont déverrouillés et montés, et donc accessibles au système et à ses programmes ; lorsqu'ils sont "inactifs", ils ne sont pas montés et donc pas accessibles. L'activation se produit automatiquement lors de la connexion de l'utilisateur et ne peut généralement s'achever qu'après la saisie d'un mot de passe (ou d'un autre jeton d'authentification). La désactivation se produit après la déconnexion complète de l'utilisateur. Un répertoire personnel reste actif tant que l'utilisateur est connecté au moins une fois, c'est-à-dire qu'il a au moins une session ouverte. Lorsque l'utilisateur se connecte une deuxième fois simultanément, le répertoire personnel reste actif. Il n'est désactivé qu'après la fin de la dernière session de l'utilisateur.

OPTIONS

Les options générales suivantes sont comprises (d'autres options qui contrôlent les diverses propriétés des enregistrements utilisateur gérés par systemd-homed.service sont documentées plus bas) :

--identity=FICHIER

Lit l'enregistrement utilisateur JSON à partir du fichier spécifié. Si passé comme "-" lit l'enregistrement utilisateur à partir de l'entrée standard. L'objet JSON fourni doit suivre la structure documentée dans Enregistrements Utilisateur JSON[1]. Cette option peut être utilisée conjointement avec les commandes create et update (voir ci-dessous), où elle permet de configurer l'enregistrement utilisateur en JSON tel quel, au lieu de définir les propriétés individuelles de l'enregistrement utilisateur (voir ci-dessous).

Ajouté dans la version 245.

--json=FORMAT, -j

Contrôle si l'enregistrement utilisateur doit être affiché au format JSON, si la commande inspect (voir ci-dessous) est utilisée. Prend l'une des valeurs "pretty", "short" ou "off". Si "pretty", des espaces et des sauts de ligne lisibles par l'homme sont insérés dans la sortie pour rendre les données JSON plus lisibles. Si "short", tous les espaces superflus sont supprimés. Si "off" (par défaut), les informations utilisateur ne sont pas affichées au format JSON mais dans un format lisible par l'homme. L'option -j choisit "pretty" lorsqu'elle est exécutée interactivement et "short" sinon.

Ajouté dans la version 245.

--export-format=FORMAT, -E, -EE

Lorsqu'elle est utilisée avec le verbe inspect en mode JSON (voir ci-dessus), elle peut être utilisée pour supprimer certains aspects de l'enregistrement utilisateur JSON de la sortie. Spécifiquement, si le format "stripped" est utilisé, les champs de liaison et d'exécution de l'enregistrement sont supprimés. Si le format "minimal" est utilisé, la signature cryptographique est également supprimée. Si le format "full" est utilisé, l'intégralité de l'enregistrement JSON est affichée (c'est le défaut). Cette option est utile pour copier un enregistrement utilisateur existant vers un autre système afin d'y créer un utilisateur similaire avec les mêmes paramètres. Spécifiquement : homectl inspect -EE | ssh root@autresystem homectl create -i- peut être utilisé comme commande simple pour répliquer un utilisateur sur un autre hôte. -E est équivalent à -j --export-format=stripped, -EE à -j --export-format=minimal. Notez que lors de la réplication de comptes utilisateurs, les enregistrements d'utilisateurs acquis en mode "stripped" conserveront les signatures cryptographiques d'origine et ne pourront donc être modifiés que lorsque la clé privée pour les mettre à jour est disponible sur la machine de destination. Lors de la réplication d'utilisateurs en mode "minimal", la signature est supprimée pendant la réplication et l'enregistrement sera donc implicitement signé avec la clé de la machine de destination et pourra y être mis à jour sans aucune réplication de clé privée.

Ajouté dans la version 245.

--offline

Ne tente pas de mettre à jour la copie de l'enregistrement utilisateur et du répertoire blob qui sont intégrés à la zone personnelle. Cela permet de travailler sur des zones personnelles absentes, ou sans avoir à s'authentifier en tant qu'utilisateur modifié.

Ajouté dans la version 256.

--key-name=

Lorsqu'elle est utilisée avec la commande add-signing-key, spécifie ou remplace le nom sous lequel stocker la clé publique ajoutée. Le nom spécifié peut être choisi librement, mais doit être suffixé par ".public". Si cette option n'est pas utilisée, le nom est dérivé du nom de fichier spécifié. Si une clé est lue depuis l'entrée standard, cette option est obligatoire afin de fournir un nom approprié pour la clé ajoutée.

Ajouté dans la version 258.

--seize=

Prend un argument booléen. Lorsqu'elle est utilisée avec create ou register, contrôle si les signatures cryptographiques doivent être retirées des enregistrements utilisateur JSON fournis, ce qui a pour effet de les signer avec la clé de signature locale (local.public) à la place. Si ce commutateur est défini sur true, les enregistrements utilisateur ajoutés deviennent donc gérés localement (et peuvent donc être modifiés localement), tandis que s'il est défini sur false, les enregistrements utilisateur restent gérés et appartiennent à leur origine (et ne peuvent donc pas être modifiés localement). Ce commutateur est défini par défaut sur true pour create et false pour register.

Ajouté dans la version 258.

--prompt-new-user

Si utilisé en conjonction avec firstb

OPTIONS

The following options are understood:

--user-account=, -U

Takes a user name, and creates a user account for it. This option may be used multiple times to create multiple user accounts. This is specifically useful when the user account does not exist in any other directory service (like LDAP, AD, etc.) and no regular user account exists on the system so far the tool will interactively query for user information and create an account.

Added in version 256.

--match=, -A, -N, -T

Takes one of "this", "other", "any" or "auto". Some user record settings can be defined to match only specific machines, or all machines but one, or all machines. With this switch it is possibly to control to which machines to apply the settings appearing on the command line after it. If "this" is specified the setting will only apply to the local system (positive match), if "other" it will apply to all but the local system (negative match), if "any" it will apply to all systems (unless there's a matching positive or negative per-machine setting). If "auto" returns to the default logic: whether a setting applies by default to the local system or all systems depends on the option in question.

Note that only some user record settings can be conditioned like this. This option has no effect on the others and is ignored there. This option may appear multiple times in a single command line to apply settings conditioned by different matches to the same user record. See JSON User Records[1] for details on which settings may be used with such per-machine matching and which ones may not.

-A is a shortcut for --match=any, -T is short for --match=this and -N is short for --match=other.

Here's an example call that sets the storage field to "luks" on the local system, but to "cifs" on all others:

# homectl update lennart -T --storage=luks -N --storage=cifs

Added in version 258.

-H, --host=

Execute the operation remotely. Specify a hostname, or a username and hostname separated by "@", to connect to. The hostname may optionally be suffixed by a port ssh is listening on, separated by ":", and then a container name, separated by "/", which connects directly to a specific container on the specified host. This will use SSH to talk to the remote machine manager instance. Container names may be enumerated with machinectl -H HOST. Put IPv6 addresses in brackets.

-M, --machine=

Execute operation on a local container. Specify a container name to connect to, optionally prefixed by a user name to connect as and a separating "@" character. If the special string ".host" is used in place of the container name, a connection to the local system is made (which is useful to connect to a specific user's user bus: "--user --machine=lennart@.host"). If the "@" syntax is not used, the connection is made as root user. If the "@" syntax is used either the left hand side or the right hand side may be omitted (but not both) in which case the local user name and ".host" are implied.

--no-pager

Do not pipe output into a pager.

--no-legend

Do not print the legend, i.e. column headers and the footer with hints.

--no-ask-password

Do not query the user for authentication for privileged operations.

-h, --help

Print a short help text and exit.

--version

Print a short version string and exit.

PROPRIÉTÉS GÉNÉRALES DES ENREGISTREMENTS UTILISATEUR

Les options suivantes contrôlent diverses propriétés des enregistrements utilisateur/répertoires personnels que `systemd-homed.service` gère. Ces commutateurs peuvent être utilisés conjointement avec les commandes create et update pour configurer divers aspects du répertoire personnel et du compte utilisateur :

--real-name=NOM, -c NOM

Le nom réel de l'utilisateur. Ceci correspond au champ GECOS dans les enregistrements UNIX NSS classiques.

Ajouté dans la version 245.

--realm=DOMAINE

Le domaine de l'utilisateur. Le domaine associe un utilisateur à une organisation ou une installation spécifique, et permet de distinguer les utilisateurs du même nom définis dans des contextes différents. Le domaine peut être toute chaîne de caractères qui est également un nom de domaine DNS valide, et il est recommandé d'utiliser le nom de domaine de l'organisation ou de l'installation à cette fin, mais ce n'est ni imposé ni requis. Sur chaque système, un seul utilisateur du même nom peut exister, et si un utilisateur portant le même nom et le même domaine est rencontré, il est supposé faire référence au même utilisateur, tandis qu'un utilisateur portant le même nom mais avec un domaine différent est considéré comme un utilisateur différent. Notez que cela signifie que deux utilisateurs partageant le même nom mais avec des domaines distincts ne sont pas autorisés sur le même système. L'attribution d'un domaine à un utilisateur est facultative.

Ajouté dans la version 245.

--alias=NOM[,NOM...]

Noms supplémentaires pour l'utilisateur. Accepte un ou plusieurs noms d'utilisateur UNIX valides, séparés par des virgules. Peut être utilisé plusieurs fois pour définir plusieurs alias. Un nom d'utilisateur alias peut être spécifié partout où le nom d'utilisateur principal peut être spécifié, et il résout le même enregistrement utilisateur.

Ajouté dans la version 258.

--email-address=EMAIL

Accepte une adresse électronique à associer à l'utilisateur. Lors de la connexion, la variable d'environnement $EMAIL est initialisée à partir de cette valeur.

Ajouté dans la version 245.

--location=TEXTE

Accepte une spécification de localisation pour cet utilisateur. Il s'agit d'un texte libre, qui peut ou non être utilisable par des applications de géolocalisation. Exemple : --location="Berlin, Germany" ou --location="Basement, Room 3a"

Ajouté dans la version 245.

--icon-name=ICONE

Accepte un nom d'icône à associer à l'utilisateur, suivant le schéma défini par la spécification de nommage d'icônes[2].

Ajouté dans la version 245.

--home-dir=CHEMIN, -dCHEMIN

Accepte un chemin à utiliser comme répertoire personnel pour l'utilisateur. Notez qu'il s'agit du répertoire où le répertoire personnel de l'utilisateur est monté lorsque l'utilisateur est connecté. Ce n'est pas là que les données de l'utilisateur sont réellement stockées, voir --image-path= pour cela. Si non spécifié, par défaut à /home/$USER.

Ajouté dans la version 245.

--uid=UID

Accepte un UID UNIX numérique préféré à attribuer à cet utilisateur. Si un utilisateur doit être créé avec l'UID spécifié et qu'il est déjà pris par un autre utilisateur sur le système local, la création du répertoire personnel est refusée. Notez cependant que si après la création du répertoire personnel il est utilisé sur un système différent et que l'UID configuré est pris par un autre utilisateur, alors systemd-homed peut attribuer un UID différent à l'utilisateur sur ce système. L'UID spécifié doit être en dehors de la plage des utilisateurs système. Il est recommandé d'utiliser la plage UID 60001...60513 à cette fin. Si non spécifié, l'UID est choisi automatiquement. Si le répertoire personnel est trouvé appartenant à un UID différent lors de la connexion, le répertoire personnel et tout ce qu'il contient verront leur propriété automatiquement changée avant la fin de la connexion.

Notez que la modification de cette option pour les répertoires personnels existants n'a généralement aucun effet sur les répertoires personnels qui ont déjà été enregistrés localement (ont une liaison locale), car l'UID utilisé pour un compte sur le système local est déterminé lorsque le répertoire personnel est activé pour la première fois, puis reste en vigueur jusqu'à ce que le répertoire personnel soit supprimé.

Notez que les utilisateurs gérés par systemd-homed ont toujours un groupe correspondant portant le même nom ainsi qu'un GID correspondant à l'UID de l'utilisateur. Par conséquent, la configuration séparée du GID n'est pas autorisée.

Ajouté dans la version 245.

--member-of=GROUPE, -G GROUPE

Accepte une liste de groupes UNIX auxiliaires séparée par des virgules auxquels cet utilisateur doit appartenir. Exemple : --member-of=wheel pour fournir à l'utilisateur des privilèges d'administrateur. Notez que systemd-homed ne gère aucun groupe autre qu'un groupe correspondant au nom de l'utilisateur et à l'UID/GID numérique. Par conséquent, tous les groupes listés ici doivent être enregistrés indépendamment, par exemple avec groupadd(8). Les groupes inexistants sont ignorés. Cette option peut être utilisée plus d'une fois, auquel cas toutes les listes de groupes spécifiées sont combinées. Si l'utilisateur est actuellement membre d'un groupe qui n'est pas listé, l'utilisateur sera retiré du groupe.

Ajouté dans la version 245.

--capability-bounding-set=CAPACITÉS, --capability-ambient-set=CAPACITÉS

Ces options acceptent une liste de capacités de processus séparée par des espaces (par exemple, CAP_WAKE_ALARM, CAP_BLOCK_SUSPEND, ...) qui doivent être définies dans les ensembles de limites et ambiants de capacités pour toutes les sessions de l'utilisateur. Voir capabilities(7) pour plus de détails sur le concept de capacités. Ces options peuvent être utilisées plus d'une fois, auquel cas les listes spécifiées sont combinées. Si le paramètre commence par un caractère "~", l'effet est inversé : la capacité spécifiée est supprimée de l'ensemble spécifique.

Ajouté dans la version 254.

--access-mode=MODE

Accepte un mode d'accès aux fichiers UNIX écrit en octal. Configure le mode d'accès du répertoire personnel lui-même. Notez que ceci n'est utilisé que lors de la première création du répertoire, et que l'utilisateur peut le modifier ultérieurement. Exemple : --access-mode=0700

Ajouté dans la version 245.

--umask=MASQUE

Accepte le masque de mode d'accès (en syntaxe octale) à appliquer aux fichiers et répertoires nouvellement créés de l'utilisateur ("umask"). S'il est défini, il contrôle l'umask initiale définie pour toutes les sessions de connexion de l'utilisateur, remplaçant éventuellement les valeurs par défaut du système.

Ajouté dans la version 245.

--skel=CHEMIN

Accepte un chemin d'accès au système de fichiers vers un répertoire. Spécifie le répertoire squelette pour initialiser le répertoire personnel. Tous les fichiers et répertoires du chemin spécifié sont copiés dans tout nouveau répertoire personnel créé. Si non spécifié, par défaut à /etc/skel/.

Ajouté dans la version 245.

--shell=SHELL

Accepte un chemin d'accès au système de fichiers. Spécifie le binaire du shell à exécuter lors des connexions au terminal. Si non spécifié, par défaut à /bin/bash.

Ajouté dans la version 245.

--setenv=VARIABLE[=VALEUR]

Accepte une variable d'environnement
le assignment pour définir pour tout les processus utilisateur. Peut être utilisé plusieurs fois pour définir plusieurs variables d'environnement . Lorsque "=" et *VALEUR* sont omis, la valeur de la variable du même nom dans l'environnement du programme sera utilisée.

Notez qu'un certain nombre d'autres paramètres entraînent également la définition de variables d'environnement pour l'utilisateur, notamment --email=, --timezone= et --language=.

Ajouté dans la version 245.

--timezone=FUSEAUHORAIRE

Prend un nom de fuseau horaire qui définit le fuseau horaire pour l'utilisateur spécifié. Lorsque l'utilisateur se connecte, la variable d'environnement $TZ est initialisée à partir de ce paramètre. Exemple : --timezone=Europe/Amsterdam entraînera la variable d'environnement "TZ=:Europe/Amsterdam". (":" est utilisé intentionnellement dans le cadre de la spécification du fuseau horaire, voir tzset(3).)

Ajouté dans la version 245.

--language=LANG

Prend une liste de langues séparées par des virgules ou des deux-points préférées par l'utilisateur, par ordre de priorité décroissante. Les variables d'environnement $LANG et $LANGUAGE sont initialisées à partir de cette valeur lors de la connexion, et les valeurs appropriées pour ces variables d'environnement sont donc acceptées ici, par exemple --language=de_DE.UTF-8. Cette option peut être utilisée plus d'une fois, auquel cas les listes de langues sont concaténées.

Ajouté dans la version 245.

--default-area=ZONE

Prend une chaîne identifiant une "zone" de répertoire personnel à utiliser par défaut. Les zones sont des répertoires personnels secondaires dans le répertoire personnel principal d'un utilisateur. Lors de la connexion, un utilisateur peut spécifier la zone dans laquelle il souhaite se connecter, ce qui garantit que la variable d'environnement $HOME est définie sur ~/Areas/ suffixé par le nom de la zone.

Pour plus de détails sur le concept de zone, voir pam_systemd_home(8). Notez que cette option définit simplement la zone par défaut, qui peut être remplacée lors de la connexion.

Lorsque cette option est spécifiée avec une chaîne vide comme valeur, toute zone par défaut déclarée précédemment est supprimée de l'enregistrement utilisateur.

Ajouté dans la version 258.

PROPRIÉTÉS DE L'ENREGISTREMENT UTILISATEUR D'AUTHENTIFICATION

--ssh-authorized-keys=CLÉS

Prend soit une ligne de clé autorisée SSH à associer à l'enregistrement utilisateur, soit un caractère "@" suivi d'un chemin vers un fichier pour lire une ou plusieurs lignes de ce type. Les clés SSH configurées de cette manière sont mises à disposition de SSH pour permettre l'accès à ce répertoire personnel et à cet enregistrement utilisateur. Cette option peut être utilisée plus d'une fois pour configurer plusieurs clés SSH.

Ajouté dans la version 245.

--pkcs11-token-uri=URI

Prend une URI PKCS#11 RFC 7512 référençant un jeton de sécurité (par exemple, YubiKey ou carte à puce PIV) qui pourra déverrouiller le compte utilisateur. L'URI du jeton de sécurité doit référencer un jeton de sécurité avec exactement une paire de certificat X.509 et de clé privée. Une clé secrète aléatoire est alors générée, chiffrée avec la clé publique du certificat X.509, et stockée dans l'enregistrement utilisateur. Lors de la connexion, elle est déchiffrée avec le module PKCS#11, puis utilisée pour déverrouiller le compte et les ressources associées. Voir ci-dessous pour un exemple de configuration de l'authentification avec un jeton de sécurité.

Au lieu d'une URI PKCS#11 valide, les chaînes spéciales "list" et "auto" peuvent être spécifiées. Si "list" est passé, un bref tableau des jetons matériels PKCS#11 appropriés, actuellement connectés, est affiché, ainsi que leurs URI. Si "auto" est passé, un jeton matériel PKCS#11 approprié est automatiquement sélectionné (cette opération échouera s'il n'y a pas exactement un jeton approprié découvert). Ce dernier est un raccourci utile pour le cas le plus courant où un seul jeton matériel PKCS#11 est connecté.

Notez que de nombreux jetons de sécurité matériels implémentent à la fois PKCS#11/PIV et FIDO2 avec l'extension "hmac-secret" (par exemple : la série YubiKey 5), comme pris en charge avec l'option --fido2-device= ci-dessous. Les deux mécanismes sont de puissance similaire, bien que FIDO2 soit la technologie la plus moderne. Les jetons PKCS#11/PIV ont l'avantage d'être reconnaissables avant l'authentification et peuvent donc être utilisés pour impliquer l'identité de l'utilisateur à utiliser pour la connexion, ce que FIDO2 ne permet pas. Les périphériques PKCS#11/PIV nécessitent généralement une initialisation (c'est-à-dire le stockage d'une paire de clés privée/publique dessus, voir l'exemple ci-dessous) avant de pouvoir être utilisés ; les jetons de sécurité FIDO2 ne nécessitent généralement pas cela et fonctionnent directement.

Ajouté dans la version 245.

--fido2-credential-algorithm=CHAÎNE

Spécifie l'algorithme COSE utilisé dans la génération des identifiants. La valeur par défaut est "es256". Les valeurs prises en charge sont "es256", "rs256" et "eddsa".

"es256" désigne ECDSA sur NIST P-256 avec SHA-256. "rs256" désigne RSA 2048 bits avec remplissage PKCS#1.5 et SHA-256. "eddsa" désigne EDDSA sur Curve25519 avec SHA-512.

Notez que votre authentificateur peut choisir de ne pas prendre en charge certains algorithmes.

Ajouté dans la version 251.

--fido2-device=CHEMIN

Prend un chemin vers un périphérique "hidraw" Linux (par exemple, /dev/hidraw1), faisant référence à un jeton de sécurité FIDO2 implémentant l'extension "hmac-secret" qui pourra déverrouiller le compte utilisateur. Une valeur de sel aléatoire est générée sur l'hôte et transmise au périphérique FIDO2, qui calcule un hachage HMAC du sel à l'aide d'une clé secrète interne. Le résultat est alors utilisé comme clé pour déverrouiller le compte utilisateur. Le sel aléatoire est inclus dans l'enregistrement utilisateur, de sorte que chaque fois qu'une authentification est nécessaire, il peut être à nouveau transmis au jeton FIDO2.

Au lieu d'un chemin valide vers un périphérique "hidraw" FIDO2, les chaînes spéciales "list" et "auto" peuvent être spécifiées. Si "list" est passé, un bref tableau des périphériques FIDO2 appropriés découverts est affiché. Si "auto" est passé, un jeton FIDO2 approprié est automatiquement sélectionné, s'il n'en est découvert qu'un seul. Ce dernier est un raccourci utile pour le cas le plus courant où un seul jeton matériel FIDO2 est connecté.

Notez que les périphériques FIDO2 appropriés pour cette option doivent implémenter l'extension "hmac-secret". La plupart des périphériques actuels (tels que la série YubiKey 5) le font. Si l'extension n'est pas implémentée, le périphérique ne peut pas être utilisé pour déverrouiller les répertoires personnels.

Le périphérique FIDO2 peut être ultérieurement supprimé en définissant le chemin du périphérique sur une chaîne vide (par exemple, homectl update $USER --fido2-device="").

Notez que de nombreux jetons de sécurité matériels implémentent à la fois FIDO2 et PKCS#11/PIV (et peuvent donc être utilisés avec --fido2-device= ou --pkcs11-token-uri=), pour une discussion voir ci-dessus.

--auto-resize-mode=

Configure si le système de fichiers hôte doit être automatiquement agrandi et/ou rétréci à la connexion et à la déconnexion. Prend l'une des chaînes "off", "grow", "shrink-and-grow". Enregistre un ou plusieurs utilisateurs, sans créer leurs répertoires personnels. Prend un ou plusieurs chemins vers des fichiers d'enregistrement utilisateur JSON. Si le chemin est spécifié comme "-" lit l'enregistrement utilisateur JSON à partir de l'entrée standard.

L'enregistrement d'un utilisateur le rend accessible sur le système local sans créer de nouveau répertoire personnel. Ceci est particulièrement utile pour rendre un utilisateur accessible sur un système sur lequel il n'a pas été créé à l'origine.

Voici un exemple pour rendre un compte utilisateur local avec son répertoire personnel accessible sur un système distant, en utilisant le partage de fichiers SMB/CIFS. Avec Samba installé dans sa configuration par défaut, appelez en tant que "root" :

# smbpasswd -a lennart

Continuez en tant qu'utilisateur régulier "lennart" :

$ homectl update lennart --ssh-authorized-keys=... -N --storage=cifs --cifs-service="//$HOSTNAME/lennart"
$ homectl get-signing-key | ssh targetsystem homectl add-signing-key --key-name="$HOSTNAME".public
$ homectl inspect -E lennart | ssh targetsystem homectl register -
$ ssh lennart@targetsystem

Cela garantit d'abord que le compte utilisateur "lennart" est connu et accessible par Samba. Il enregistre ensuite un accès SSH local qui sera utilisé pour accéder à cet utilisateur, et configure CIFS comme stockage par défaut pour les systèmes non locaux sur le compte. Il ajoute ensuite la clé de signature du compte du système local au système cible. Ensuite, il enregistre le compte utilisateur local auprès du système cible. Enfin, il se connecte au compte sur le système cible. Le système cible se reconnectera alors via SMB/CIFS pour accéder au répertoire personnel.

Modifie l'espace disque alloué au répertoire personnel spécifié. Si le mécanisme de stockage LUKS2 est utilisé, cela redimensionnera automatiquement le fichier de bouclage et le système de fichiers qu'il contient. Notez que si "ext4" est utilisé à l'intérieur du volume LUKS2, il est nécessaire de désactiver le répertoire personnel avant de le réduire (c'est-à-dire que l'utilisateur doit se déconnecter). Les chaînes spéciales "min" et "max" peuvent être spécifiées à la place d'une valeur de taille numérique, pour minimiser ou maximiser l'espace disque alloué à la zone personnelle, en tenant compte des contraintes du système de fichiers, de l'utilisation du disque à l'intérieur de la zone personnelle et sur le stockage de support.

ENVIRONNEMENT

$SYSTEMD_LOG_LEVEL

Le niveau de journalisation maximum des messages émis (les messages avec un niveau de journalisation plus élevé, c'est-à-dire moins importants, seront supprimés). Prend une liste de valeurs séparées par des virgules. Une valeur peut être l'un des niveaux suivants (par ordre de décroissance d'importance) : emerg, alert, crit, err, warning, notice, info, debug, ou un entier dans la plage 0...7. Voir syslog(3) pour plus d'informations. Chaque valeur peut éventuellement être préfixée par l'un des mots-clés console, syslog, kmsg ou journal suivi d'un deux-points pour définir le niveau de journalisation maximum pour cette cible de journalisation spécifique (par exemple, SYSTEMD_LOG_LEVEL=debug,console:info spécifie de journaliser au niveau debug, sauf lorsqu'il s'agit de journaliser sur la console, qui devrait être au niveau info). Notez que le niveau de journalisation maximum global a la priorité sur tous les niveaux de journalisation maximum par cible.

$SYSTEMD_LOG_COLOR

Un booléen. Si vrai, les messages écrits sur le tty seront colorés en fonction de la priorité.

Ce paramètre est utile uniquement lorsque les messages sont écrits directement sur le terminal, car journalctl(1) et d'autres outils qui affichent les journaux coloreront les messages en fonction du niveau de journalisation par eux-mêmes.

$SYSTEMD_LOG_TIME

Un booléen. Si vrai, les messages de journal de la console seront préfixés par un horodatage.

Ce paramètre est utile uniquement lorsque les messages sont écrits directement sur le terminal ou dans un fichier, car journalctl(1) et d'autres outils qui affichent les journaux ajouteront des horodatages en fonction des métadonnées de l'entrée par eux-mêmes.

$SYSTEMD_LOG_LOCATION

Un booléen. Si vrai, les messages seront préfixés par un nom de fichier et un numéro de ligne dans le code source où le message provient.

Notez que l'emplacement du journal est souvent joint comme métadonnées aux entrées du journal de toute façon. L'inclure directement dans le texte du message peut néanmoins être pratique lors du débogage de programmes.

$SYSTEMD_LOG_TID

Un booléen. Si vrai, les messages seront préfixés par l'ID de thread (TID) numérique actuel.

Notez que ces informations sont jointes comme métadonnées aux entrées du journal de toute façon. L'inclure directement dans le texte du message peut néanmoins être pratique lors du débogage de programmes.

$SYSTEMD_LOG_TARGET

La destination des messages de journal. L'un des choix suivants : console (journaliser vers le tty attaché), console-prefixed (journaliser vers le tty attaché mais avec des préfixes codant le niveau de journalisation et la "facility", voir syslog(3), kmsg (journaliser vers le tampon de journal circulaire du noyau), journal (journaliser vers le journal), journal-or-kmsg (journaliser vers le journal si disponible, et vers kmsg sinon), auto (déterminer automatiquement la cible de journalisation appropriée, par défaut), null (désactiver la sortie de journal).

$SYSTEMD_LOG_RATELIMIT_KMSG

Indique s'il faut limiter la fréquence des messages kmsg ou non. Prend un booléen. Par défaut "true". Si désactivé, systemd ne limitera pas la fréquence des messages écrits dans kmsg.

$SYSTEMD_PAGER, $PAGER

Paginator à utiliser lorsque --no-pager n'est pas spécifié. $SYSTEMD_PAGER est utilisé s'il est défini ; sinon $PAGER est utilisé. Si ni $SYSTEMD_PAGER ni $PAGER ne sont définis, un ensemble d'implémentations de paginator bien connues sont essayées tour à tour, y compris less(1) et more(1), jusqu'à ce qu'un soit trouvé. Si aucune implémentation de paginator n'est découverte, aucun paginator n'est invoqué. Définir ces variables d'environnement sur une chaîne vide ou la valeur "cat" équivaut à passer --no-pager.

Note : si $SYSTEMD_PAGERSECURE n'est pas défini, $SYSTEMD_PAGER et $PAGER ne peuvent être utilisés que pour désactiver le paginator (avec "cat" ou ""), et sont sinon ignorés.

$SYSTEMD_LESS

Remplace les options passées à less (par défaut "FRSXMK").

Les utilisateurs pourraient vouloir changer deux options en particulier :

K

Cette option demande au paginator de quitter immédiatement lorsque Ctrl+C est pressé. Pour permettre à less de gérer lui-même Ctrl+C pour revenir à l'invite de commande du paginator, désactivez cette option.

Si la valeur de $SYSTEMD_LESS n'inclut pas "K", et que le paginator invoqué est less, Ctrl+C sera ignoré par l'exécutable et devra être géré par le paginator.

X

Cette option demande au paginator de ne pas envoyer les chaînes d'initialisation et de désinitialisation termcap au terminal. Elle est définie par défaut pour permettre à la sortie de la commande de rester visible dans le terminal même après la sortie du paginator. Néanmoins, cela empêche certaines fonctionnalités du paginator de fonctionner, en particulier la sortie paginée ne peut pas être défilée avec la souris.

Notez que la définition de la variable d'environnement régulière $LESS n'a aucun effet pour les invocations de less par les outils systemd.

Voir less(1) pour plus de discussion.

$SYSTEMD_LESSCHARSET

Remplace le jeu de caractères passé à less (par défaut "utf-8", si le terminal appelant est déterminé comme étant compatible UTF-8).

Notez que la définition de la variable d'environnement régulière $LESSCHARSET n'a aucun effet pour les invocations de less par les outils systemd.

$SYSTEMD_PAGERSECURE

Les commandes de paginator courantes comme less(1), en plus de la "pagination", c'est-à-dire le défilement de la sortie, supportent l'ouverture ou l'écriture dans d'autres fichiers et l'exécution de commandes shell arbitraires. Lorsque des commandes sont invoquées avec des privilèges élevés, par exemple sous sudo(8) ou pkexec(1), le paginator devient une limite de sécurité. Il faut veiller à ce que seuls des programmes aux fonctionnalités strictement limitées soient utilisés comme paginators, et que les fonctionnalités interactives non intentionnelles comme l'ouverture ou la création de nouveaux fichiers ou le lancement de sous-processus ne soient pas autorisées. Le "mode sécurisé" pour le paginator peut être activé comme décrit ci-dessous, si le paginator le supporte (la plupart des paginators ne sont pas écrits d'une manière qui en tienne compte). Il est recommandé soit d'activer explicitement le "mode sécurisé", soit de désactiver complètement le paginator en utilisant --no-pager ou PAGER=cat lors de l'autorisation d'utilisateurs non fiables à exécuter des commandes avec des privilèges élevés.

Cette option prend un argument booléen. Lorsqu'il est défini sur vrai, le "mode sécurisé" du paginator est activé. En "mode sécurisé", LESSSECURE=1 sera défini lors de l'invocation du paginator, ce qui demande au paginator de désactiver les commandes qui ouvrent ou créent de nouveaux fichiers ou démarrent de nouveaux sous-processus. Actuellement, seul less(1) est connu pour comprendre cette variable et implémenter le "mode sécurisé".

Lorsqu'il est défini sur faux, aucune limitation n'est imposée au paginator. Définir SYSTEMD_PAGERSECURE=0 ou ne pas le supprimer de l'environnement hérité peut permettre à l'utilisateur d'invoquer des commandes arbitraires.

Lorsque $SYSTEMD_PAGERSECURE n'est pas défini, les outils systemd tentent de déterminer automatiquement si le "mode sécurisé" doit être activé et si le paginator le supporte. Le "mode sécurisé" est activé si l'UID effectif n'est pas le même que le propriétaire de la session de connexion, voir geteuid(2) et sd_pid_get_owner_uid(3), ou lors de l'exécution sous sudo(8) ou des outils similaires ($SUDO_UID est défini [5]). Dans ces cas, SYSTEMD_PAGERSECURE=1 sera défini et les paginators qui ne sont pas connus pour implémenter le "mode sécurisé" ne seront pas utilisés du tout. Notez que cette autodétection ne couvre que les mécanismes les plus courants pour élever les privilèges et est prévue comme une commodité. Il est recommandé de définir explicitement $SYSTEMD_PAGERSECURE ou de désactiver le paginator.

Notez que si les variables $SYSTEMD_PAGER ou $PAGER doivent être prises en compte, autre que pour désactiver le paginator, $SYSTEMD_PAGERSECURE doit également être défini.

$SYSTEMD_COLORS

Prend un argument booléen. Lorsqu'il est vrai, systemd et les utilitaires associés utiliseront des couleurs dans leur sortie, sinon la sortie sera monochrome. De plus, la variable peut prendre l'une des valeurs spéciales suivantes : "16", "256" pour restreindre l'utilisation des couleurs aux couleurs ANSI de base 16 ou 256, respectivement. Ceci peut être spécifié pour remplacer la décision automatique basée sur $TERM et ce à quoi le console est connecté.

$SYSTEMD_URLIFY

La valeur doit être un booléen. Contrôle si des liens cliquables doivent être générés dans la sortie pour les émulateurs de terminal supportant cela. Ceci peut être spécifié pour remplacer la décision que systemd prend en fonction de $TERM et d'autres conditions.

EXAMPLES

Example 1. Create a user "waldo" with the real name "Waldo McWaldo", assign them to the administrator group "wheel", and assign 500 MiB disk space to them.

homectl create waldo --real-name="Waldo McWaldo" -G wheel --disk-size=500M

Example 2. Create a user "wally" on a USB stick, and assign a maximum of 500 concurrent tasks to them.

homectl create wally --real-name="Wally McWally" --image-path=/dev/disk/by-id/usb-SanDisk_Ultra_Fit_476fff954b2b5c44-0:0 --tasks-max=500

Example 3. Change nice level of user "odlaw" to +5 and make sure the environment variable $SOME is set to the string "THING" for them on login.

homectl update odlaw --nice=5 --setenv=SOME=THING

Example 4. Set up authentication with a YubiKey security token using PKCS#11/PIV:

# Clear the Yubikey from any old keys (careful!)
ykman piv reset
# Generate a new private/public key pair on the device, store the public key in 'pubkey.pem'.
ykman piv generate-key -a RSA2048 9d pubkey.pem
# Create a self-signed certificate from this public key, and store it on the device.
ykman piv generate-certificate --subject "Knobelei" 9d pubkey.pem
# We do not need the public key on disk anymore
rm pubkey.pem
# Allow the security token to unlock the account of user 'lafcadio'.
homectl update lafcadio --pkcs11-token-uri=auto

Example 5. Set up authentication with a FIDO2 security token:

# Allow a FIDO2 security token to unlock the account of user 'nihilbaxter'.
homectl update nihilbaxter --fido2-device=auto
