NOM

systemd-measure - Pré-calculer et signer les valeurs attendues de TPM2 PCR 11 pour les images de noyau unifiées amorcées

SYNTAXE

/usr/lib/systemd/systemd-measure [OPTIONS...]

DESCRIPTION

Note : cette commande est actuellement expérimentale. Bien qu'elle soit susceptible de devenir un composant régulier de systemd, son comportement et son interface peuvent encore changer.

systemd-measure est un outil qui peut être utilisé pour pré-calculer et signer les valeurs attendues de TPM2 PCR 11 qui devraient être observées lors du démarrage d'une Image de Noyau Unifiée (UKI)[1] basée sur systemd-stub(7). Il accepte les chemins du fichier image du noyau ELF, du fichier image initrd, du fichier de configuration de l'arbre de périphériques (devicetree), du fichier de ligne de commande du noyau, du fichier os-release(5), du fichier d'écran de démarrage (boot splash), et du fichier de clé publique PEM TPM2 PCR qui composent l'image du noyau unifiée, et détermine les valeurs PCR attendues après le démarrage de l'image. Le calcul commence avec un PCR 11 initialisé à zéro et est exécuté d'une manière compatible avec ce que fait systemd-stub au démarrage. Le résultat peut éventuellement être signé cryptographiquement, pour permettre des politiques TPM2 qui ne peuvent être déverrouillées que si un ensemble de noyaux est démarré, pour lequel une telle signature PCR peut être fournie.

Il n'est généralement pas judicieux d'appeler cet outil directement lors de la construction d'une UKI. Au lieu de cela, ukify(1) devrait être utilisé ; il invoquera systemd-measure et s'occupera d'intégrer les mesures résultantes dans l'UKI.

COMMANDES

Les commandes suivantes sont comprises :

status

C'est la commande par défaut si aucune n'est spécifiée. Elle interroge les valeurs TPM2 PCR 11 du système local et les affiche. Les données sont écrites dans un format similaire à la commande calculate ci-dessous, et peuvent être utilisées pour comparer rapidement l'attente et la réalité.

Ajouté dans la version 252.

calculate

Pré-calcule les valeurs attendues dans le registre PCR 11 après le démarrage d'une image de noyau unifiée composée des composants spécifiés avec --linux=, --osrel=, --cmdline=, --initrd=, --ucode=, --splash=, --dtb=, --uname=, --sbat=, --pcrpkey=, --profile=, --dtbauto=, --hwids=, voir ci-dessous. Seul --linux= est obligatoire. (Alternativement, spécifiez --current pour utiliser les valeurs actuelles du registre PCR 11 à la place.)

Ajouté dans la version 252.

sign

Comme avec la commande calculate, pré-calcule la valeur attendue dans le registre TPM2 PCR 11 après le démarrage d'une image de noyau unifiée. Ensuite, signe cryptographiquement les valeurs résultantes avec la paire de clés privée/publique (RSA) configurée via --private-key= et --public-key=. Cela écrira un objet JSON sur la sortie standard contenant des signatures pour toutes les banques PCR spécifiées (voir l'option --bank= ci-dessous), qui peuvent être utilisées pour déverrouiller des identifiants chiffrés (voir systemd-creds(1)) ou des volumes LUKS (voir systemd-cryptsetup@.service(8)). Cela permet de lier des secrets à un ensemble de noyaux pour lesquels de telles signatures PCR 11 peuvent être fournies.

Notez qu'un périphérique TPM2 doit être disponible pour que cette signature ait lieu, même si le résultat n'est lié à aucun périphérique TPM2 ni à son état.

Ajouté dans la version 252.

policy-digest

Comme pour la commande sign, pré-calcule la valeur attendue dans le registre TPM2 PCR 11 après le démarrage d'une image de noyau unifiée. Ensuite, calcule la politique TPM2 résultante et imprime son résumé (digest). Cela écrira un objet JSON sur la sortie standard contenant les résumés de politique pour toutes les banques PCR spécifiées (voir l'option --bank= ci-dessous), afin qu'ils puissent être signés hors ligne, pour les cas où la clé privée n'est pas directement accessible. Si --public-key= ou --certificate= sont spécifiés, l'objet JSON contiendra également l'empreinte de la clé.

Ajouté dans la version 258.

OPTIONS

Les options suivantes sont comprises :

--linux=CHEMIN, --osrel=CHEMIN, --cmdline=CHEMIN, --initrd=CHEMIN, --ucode=CHEMIN, --splash=CHEMIN, --dtb=CHEMIN, --uname=CHEMIN, --sbat=CHEMIN, --pcrpkey=CHEMIN, --profile=CHEMIN, --dtbauto=CHEMIN, --hwids=CHEMIN

Lorsqu'elles sont utilisées avec le verbe calculate ou sign, configurent les fichiers à lire pour les composants de l'image du noyau unifiée. Chaque option correspond à la section de nom identique dans le fichier PE du noyau unifié. Le commutateur --linux= attend le chemin du fichier noyau ELF que le noyau PE unifié encapsulera. Tous les commutateurs, sauf --linux=, sont facultatifs. Chaque option ne peut être utilisée qu'une seule fois.

Ajouté dans la version 252.

À l'exception de --profile=, --dtbauto= et --hwids=, qui ont été ajoutés dans la version 257.

--current

Lorsqu'elle est utilisée avec le verbe calculate ou sign, prend les valeurs PCR 11 actuellement en vigueur pour le système (qui devraient généralement refléter les hachages du noyau actuellement démarré). Cela peut être utilisé à la place de --linux= et des autres commutateurs listés ci-dessus.

Ajouté dans la version 252.

--bank=SOMME

Contrôle les banques PCR pour lesquelles les valeurs PCR doivent être pré-calculées – dans le cas où calculate ou sign est invoqué – ou les banques à afficher dans la sortie status. Peut être utilisé plusieurs fois pour spécifier plusieurs banques. S'il n'est pas spécifié, les quatre banques "sha1", "sha256", "sha384", "sha512" sont utilisées par défaut.

Notez que certains systèmes d'exploitation désactivent le support des signatures basées sur SHA1, auquel cas cette opération échouera. Veuillez consulter la documentation de votre système d'exploitation pour savoir comment outrepasser la politique de sécurité du système à ce sujet.

Ajouté dans la version 252.

--private-key=CHEMIN, --public-key=CHEMIN, --certificate=CHEMIN

Ces commutateurs prennent les chemins vers une paire de fichiers de clés RSA codés en PEM, à utiliser avec la commande sign.

Notez la différence entre les commutateurs --pcrpkey= et --public-key=. Le premier sélectionne les données à inclure dans la section PE ".pcrpkey" de l'image du noyau unifiée, le second choisit la clé publique de la paire de clés utilisée pour signer les valeurs PCR 11 résultantes. Le premier est la clé que le système démarré utilisera probablement pour verrouiller le chiffrement du disque et des identifiants, le second est la clé utilisée pour déverrouiller ces ressources à nouveau. Par conséquent, généralement la même clé PEM devrait être fournie dans les deux cas.

Si --public-key= n'est pas spécifié mais que --private-key= est spécifié, la clé publique est automatiquement dérivée de la clé privée.

--certificate= peut être utilisé pour spécifier un certificat X.509 comme alternative à --public-key= depuis la v256.

Ajouté dans la version 252.

--private-key=CHEMIN/URI, --private-key-source=TYPE[:NOM], --certificate=CHEMIN/URI, --certificate-source=TYPE[:NOM]

En alternative à --public-key= pour la commande sign, ces commutateurs peuvent être utilisés pour signer avec un jeton matériel. L'option clé privée peut prendre un chemin ou une URI qui sera passé au moteur ou au fournisseur OpenSSL, comme spécifié par --private-key-source= sous forme de tuple type:nom, tel que engine:pkcs11. Le moteur ou fournisseur de signature OpenSSL spécifié sera utilisé pour signer.

L'option --certificate= prend également un chemin ou une URI qui sera passé au fournisseur OpenSSL, comme spécifié par --certificate-source= sous forme de tuple "type:nom", tel que "provider:pkcs11". Notez que contrairement à --private-key-source=, cette option ne prend en charge que les fournisseurs et non les moteurs.

Ajouté dans la version 256.

--phase=PHASE

Contrôle quelles phases de démarrage doivent avoir leurs valeurs PCR 11 attendues calculées. Ceci prend une série de chaînes séparées par des deux-points qui encodent des "chemins" de démarrage pour entrer dans une phase spécifique du processus de démarrage. Chacune des chaînes spécifiées est mesurée par les services systemd-pcrphase-initrd.service, systemd-pcrphase-sysinit.service, et systemd-pcrphase.service(8) dans le PCR 11 lors de différentes étapes du processus de démarrage. Ce commutateur peut être spécifié plusieurs fois pour calculer les valeurs PCR pour plusieurs phases de démarrage à la fois. S'il n'est pas utilisé, la valeur par défaut est "enter-initrd", "enter-initrd:leave-initrd", "enter-initrd:leave-initrd:sysinit", "enter-initrd:leave-initrd:sysinit:ready", c'est-à-dire qu'il calcule les valeurs PCR attendues pour la phase de démarrage dans l'initrd, pendant le démarrage précoce, pendant le démarrage tardif, et pendant le temps d'exécution du système, mais excluant les phases avant l'initrd ou lors de l'arrêt. Ce paramètre est respecté à la fois par calculate et sign. Lorsqu'il est utilisé avec ce dernier, il est particulièrement utile pour générer des signatures PCR qui ne peuvent être utilisées que pour déverrouiller des ressources pendant des parties spécifiques du processus de démarrage.

Pour plus de détails sur les phases de démarrage PCR, voir systemd-pcrphase.service(8).

Ajouté dans la version 252.

--append=CHEMIN

Lors de la génération d'une signature PCR JSON (via la commande sign), elle est combinée avec une signature PCR JSON générée précédemment, et le résultat est affiché en un seul bloc. Le chemin spécifié doit faire référence à un fichier régulier contenant un objet de signature PCR JSON valide. Le fichier spécifié n'est pas modifié. Il sera lu en premier, puis la signature nouvellement générée lui sera ajoutée, et l'objet résultant sera écrit sur la sortie standard. Utilisez ceci pour générer un seul objet JSON composé de signatures faites avec plusieurs clés de signature (par exemple, pour avoir une clé par phase de démarrage). La commande supprimera les doublons : si une signature spécifique est déjà incluse dans un objet de signature JSON, elle n'est pas ajoutée une seconde fois.

Ajouté dans la version 253.

--json=MODE

Affiche la sortie formatée en JSON. Attend l'une des valeurs suivantes : "short" (pour une sortie la plus courte possible sans espaces blancs superflus ni sauts de ligne), "pretty" (pour une version joliment formatée de la même chose, avec indentation et sauts de ligne) ou "off" (pour désactiver la sortie JSON, par défaut).

--no-pager

Ne pas rediriger la sortie vers un paginateur.

-h, --help

Affiche un court message d'aide et quitte.

--version

Affiche une courte chaîne de version et quitte.

EXEMPLES

Exemple 1. Générer une image de noyau unifiée et calculer la valeur TPM PCR 11 attendue

$ ukify build \
     --linux=vmlinux \
     --initrd=initrd.cpio \
     --os-release=@os-release.txt \
     --cmdline=@cmdline.txt \
     --splash=splash.bmp \
     --devicetree=devicetree.dtb \
     --measure \
     --output=vmlinux.efi
11:sha1=d775a7b4482450ac77e03ee19bda90bd792d6ec7
11:sha256=bc6170f9ce28eb051ab465cd62be8cf63985276766cf9faf527ffefb66f45651
11:sha384=1cf67dff4757e61e5...7f49ad720be02fd07263e1f93061243aec599d1ee4b4
11:sha512=8e79acd3ddbbc8282...0c3e8ec0c714821032038f525f744960bcd082d937da

ukify(1) appelle systemd-measure en interne. La sortie avec les hachages provient de systemd-measure.

Exemple 2. Générer une paire de clés privée/publique, une image de noyau unifiée et une signature TPM PCR 11 pour celle-ci, et intégrer la signature et la clé publique dans l'image

$ openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out tpm2-pcr-private-key.pem
..+.+++++++++......+.........+......+.......+....+.....+.+...+..........
$ openssl rsa -pubout -in tpm2-pcr-private-key.pem -out tpm2-pcr-public-key.pem
$ systemd-measure sign \
     --linux=vmlinux \
     --osrel=os-release.txt \
     --cmdline=cmdline.txt \
     --initrd=initrd.cpio \
     --splash=splash.bmp \
     --dtb=devicetree.dtb \
     --pcrpkey=tpm2-pcr-public-key.pem \
     --bank=sha1 \
     --bank=sha256 \
     --private-key=tpm2-pcr-private-key.pem \
     --public-key=tpm2-pcr-public-key.pem >tpm2-pcr-signature.json
$ ukify build \
     --linux=vmlinux \
     --initrd=initrd.cpio \
     --os-release=@os-release.txt \
     --cmdline=@cmdline.txt \
     --splash=splash.bmp \
     --devicetree=devicetree.dtb \
     --pcr-private-key=tpm2-pcr-private-key.pem \
     --pcr-public-key=tpm2-pcr-public-key.pem \
     --pcr-banks=sha1,sha256 \
     --output=vmlinuz.efi

Plus tard, enregistrer la politique PCR signée sur un volume LUKS :

# systemd-cryptenroll --tpm2-device=auto \
     --tpm2-public-key=tpm2-pcr-public-key.pem \
     --tpm2-signature=tpm2-pcr-signature.json \
     /dev/sda5

Et ensuite déverrouiller le périphérique avec la signature :

# systemd-cryptsetup attach \
     volume5 /dev/sda5 - \
     tpm2-device=auto,tpm2-signature=/path/to/tpm2-pcr-signature.json

Notez que lorsque l'image de noyau unifiée générée vmlinux.efi est démarrée, les fichiers de signature et de clé publique seront placés aux emplacements où systemd-cryptenroll et systemd-cryptsetup les rechercheront de toute façon, et donc ces chemins n'ont pas besoin d'être spécifiés.

Exemple 3. Introduire une seconde clé publique, signant les mêmes mesures PCR du noyau, mais uniquement pour la phase de démarrage initrd

Cet exemple étend le précédent, mais nous introduisons maintenant une seconde clé de signature qui est uniquement utilisée pour signer des politiques PCR restreintes à la phase de démarrage initrd. Ceci peut être utilisé pour verrouiller les volumes racines de manière à ce qu'ils ne puissent être déverrouillés qu'avant la transition vers le système hôte. Ainsi, nous avons deux classes de secrets ou d'identifiants : l'un qui peut être déverrouillé pendant toute la durée d'exécution, et l'autre qui ne peut être utilisé que dans l'initrd.

$ openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out tpm2-pcr-private-key.pem
.+........+.+........+........+......+........+....+.....+.+..+..........
$ openssl rsa -pubout -in tpm2-pcr-private-key.pem -out tpm2-pcr-public-key.pem
$ openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out tpm2-pcr-initrd-private-key.pem
..+.......++........+........+......+........+....+.....+.+..+..........
$ openssl rsa -pubout -in tpm2-pcr-initrd-private-key.pem -out tpm2-pcr-initrd-public-key.pem
$ ukify build \
     --linux=vmlinux-1.2.3 \
     --initrd=initrd.cpio \
     --os-release=@os-release.txt \
     --cmdline=@cmdline.txt \
     --splash=splash.bmp \
     --devicetree=devicetree.dtb \
     --pcr-private-key=tpm2-pcr-private-key.pem \
     --pcr-public-key=tpm2-pcr-public-key.pem \
     --phases=enter-initrd,enter-initrd:leave-initrd,enter-initrd:leave-initrd:sysinit,enter-initrd:leave-initrd:sysinit:ready \
     --pcr-banks=sha1,sha256 \
     --pcr-private-key=tpm2-pcr-initrd-private-key.pem \
     --pcr-public-key=tpm2-pcr-initrd-public-key.pem \
     --phases=enter-initrd \
     --uname=1.2.3 \
     --output=vmlinux-1.2.3.efi
+ /usr/lib/systemd/systemd-measure sign --linux=vmlinux-1.2.3 \
--osrel=os-release.txt --cmdline=cmdline.txt --dtb=devicetree.dtb \
--splash=splash.bmp --initrd=initrd.cpio --bank=sha1 --bank=sha256 \
--private-key=tpm2-pcr-private-key.pem --public-key=tpm2-pcr-public-key.pem \
--phase=enter-initrd --phase=enter-initrd:leave-initrd \
--phase=enter-initrd:leave-initrd:sysinit \
--phase=enter-initrd:leave-initrd:sysinit:ready
+ /usr/lib/systemd/systemd-measure sign --linux=vmlinux-1.2.3 \
--osrel=os-release.txt --cmdline=cmdline.txt --dtb=devicetree.dtb \
--splash=splash.bmp --initrd=initrd.cpio --bank=sha1 --bank=sha256 \
--private-key=tpm2-pcr-initrd-private-key.pem \
--public-key=tpm2-pcr-initrd-public-key.pem \
--phase=enter-initrd
Wrote unsigned vmlinux-1.2.3.efi

ukify affiche les deux invocations de systemd-measure en sortie informative (les lignes commençant par "+") ; cela nous permet de voir comment systemd-measure est appelé. Il fusionne ensuite la sortie des deux invocations dans la section ".pcrsig". systemd-measure peut également effectuer cette fusion lui-même en utilisant l'option --append=.

Notez que dans cet exemple, la section PE ".pcrpkey" contient la clé spécifiée par la première option --pcr-private-key=, couvrant toutes les phases de démarrage. La section ".pcrpkey" est utilisée dans les politiques par défaut de systemd-cryptenroll et systemd-creds. Pour utiliser la politique plus stricte liée à tpm2-pcr-initrd-public-key.pem, spécifiez --tpm2-public-key= sur la ligne de commande de ces outils.

STATUT DE SORTIE

En cas de succès, 0 est retourné, sinon un code d'échec non nul.
