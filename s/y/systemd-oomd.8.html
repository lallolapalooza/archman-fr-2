NOM

systemd-oomd.service, systemd-oomd - Un tueur hors-mémoire (OOM) en espace utilisateur

SYNTAXE

systemd-oomd.service

/usr/lib/systemd/systemd-oomd

DESCRIPTION

systemd-oomd est un service système qui utilise les cgroups-v2 et les informations de pression de blocage (PSI) pour surveiller et prendre des mesures correctives avant qu'un OOM ne se produise dans l'espace du noyau.

Vous pouvez activer la surveillance et les actions sur les unités en définissant ManagedOOMSwap= et ManagedOOMMemoryPressure= dans la configuration de l'unité, voir systemd.resource-control(5). systemd-oomd récupère les informations sur ces unités à partir de systemd(1) lorsqu'il démarre et surveille les changements ultérieurs.

Les cgroups des unités avec ManagedOOMSwap= ou ManagedOOMMemoryPressure= réglé sur kill seront surveillés. systemd-oomd interroge périodiquement les statistiques PSI pour le système et ces cgroups afin de décider quand agir. Si les limites configurées sont dépassées, systemd-oomd sélectionnera une cgroup à terminer et enverra SIGKILL à tous les processus qu'elle contient. Notez que seuls les cgroups descendants sont des candidats éligibles pour le ciblage, l'unité avec sa propriété définie sur kill n'est pas un candidat (sauf si l'un de ses ancêtres a défini sa propriété sur kill). De plus, seuls les cgroups feuilles et les cgroups dont memory.oom.group est réglé sur 1 sont des candidats éligibles ; voir OOMPolicy= dans systemd.service(5).

oomctl(1) peut être utilisé pour lister les cgroups surveillées et les informations de pression.

Voir oomd.conf(5) pour plus d'informations sur la configuration de ce service.

Voir org.freedesktop.oom1(5) et org.freedesktop.LogControl1(5) pour une description de l'API D-Bus.

EXIGENCES ET CONFIGURATION DU SYSTÈME

Le système doit exécuter systemd avec une hiérarchie cgroup unifiée complète pour les fonctionnalités cgroups-v2 attendues. De plus, la comptabilisation de la mémoire doit être activée pour toutes les unités surveillées par systemd-oomd. La manière la plus simple d'activer la comptabilisation de la mémoire est de s'assurer que la valeur de DefaultMemoryAccounting= est définie sur true dans systemd-system.conf(5).

Le noyau doit être compilé avec le support PSI. Ceci est disponible dans Linux 4.20 et versions ultérieures.

Il est fortement recommandé que le système ait le swap activé pour que systemd-oomd fonctionne de manière optimale. Avec le swap activé, le système passe suffisamment de temps à échanger des pages pour permettre à systemd-oomd de réagir. Sans swap, le système entre dans un état de blocage beaucoup plus rapidement et peut empêcher systemd-oomd de répondre dans un délai raisonnable. Voir "In defence of swap: common misconceptions"[1] pour plus de détails sur le swap. Toutes les actions basées sur le swap sur les systèmes sans swap seront ignorées. Bien que systemd-oomd puisse effectuer des actions basées sur la pression sur un tel système, les augmentations de pression seront plus abruptes et peuvent nécessiter plus de réglages pour obtenir les seuils et le comportement souhaités.

Soyez conscient que si vous avez l'intention d'activer la surveillance et les actions sur user.slice, user-$UID.slice, ou leurs cgroups ancêtres, il est fortement recommandé que vos programmes soient gérés par le gestionnaire d'utilisateurs systemd pour éviter d'exécuter trop de processus sous le même scope de session (et ainsi éviter une situation où les tâches gourmandes en mémoire déclenchent systemd-oomd pour tuer tout ce qui se trouve sous la cgroup). Si vous utilisez un environnement de bureau comme GNOME ou KDE, il lance déjà de nombreux composants de session avec le gestionnaire d'utilisateurs systemd.

RECOMMANDATIONS D'UTILISATION

ManagedOOMSwap= fonctionne avec les valeurs de swap globales, donc le définir sur la slice racine -.slice, et permettre à tous les cgroups descendants d'être des candidats éligibles peut avoir le plus de sens.

ManagedOOMMemoryPressure= a tendance à mieux fonctionner sur les cgroups sous la slice racine. Pour les unités qui ont tendance à avoir des processus moins sensibles à la latence (par exemple, system.slice), une limite plus élevée comme la valeur par défaut de 60% peut être acceptable, car ces processus peuvent généralement supporter les ralentissements causés par le manque de mémoire sans conséquences graves. Cependant, quelque chose comme user@$UID.service pourrait préférer une valeur beaucoup plus faible, comme 40%.

OPTIONS

--dry-run

Faire un essai à blanc de systemd-oomd : lorsqu'un kill est déclenché, l'afficher dans le log au lieu de tuer la cgroup.

Ajouté dans la version 253.

-h, --help

Afficher un court message d'aide et quitter.

--version

Afficher une courte chaîne de version et quitter.

SIGNAUX

SIGHUP

À la réception du signal de processus SIGHUP, systemd-oomd rechargera son fichier de configuration.

Ajouté dans la version 258.
