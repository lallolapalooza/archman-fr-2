NOM

systemd-cryptsetup, systemd-cryptsetup@.service - Logique de déchiffrement complet du disque

SYNTAXE

systemd-cryptsetup [OPTIONS...] attach VOLUME SOURCE-DEVICE [KEY-FILE] [CRYPTTAB-OPTIONS]

systemd-cryptsetup [OPTIONS...] detach VOLUME

systemd-cryptsetup@.service

system-systemd\x2dcryptsetup.slice

DESCRIPTION

systemd-cryptsetup est utilisé pour configurer (avec attach) et démonter (avec detach) l'accès à un périphérique bloc chiffré. Il est principalement utilisé via systemd-cryptsetup@.service pendant le démarrage précoce, mais peut également être appelé manuellement. Les arguments positionnels VOLUME, SOURCE-DEVICE, KEY-FILE et CRYPTTAB-OPTIONS ont la même signification que les champs dans crypttab(5).

systemd-cryptsetup@.service est un service responsable de fournir l'accès aux périphériques bloc chiffrés. Il est instancié pour chaque périphérique qui nécessite un déchiffrement.

Les instances de systemd-cryptsetup@.service font partie de la tranche systemd-systemd\x2dcryptsetup.slice, qui n'est détruite que très tard dans la procédure d'arrêt. Cela permet aux périphériques chiffrés de rester actifs jusqu'à ce que les systèmes de fichiers aient été démontés.

systemd-cryptsetup@.service demandera les mots de passe des disques durs via la logique de l'agent de mot de passe[1], afin d'interroger l'utilisateur pour le mot de passe en utilisant le bon mécanisme au démarrage et pendant l'exécution.

Au démarrage précoce et lorsque la configuration du gestionnaire système est rechargée, /etc/crypttab est traduit en unités systemd-cryptsetup@.service par systemd-cryptsetup-generator(8).

Afin de déverrouiller un volume, un mot de passe ou une clé binaire est requis. systemd-cryptsetup@.service tente d'acquérir un mot de passe ou une clé binaire approprié via les mécanismes suivants, essayés dans l'ordre :

1.Si un fichier clé est explicitement configuré (via la troisième colonne de /etc/crypttab), une clé lue à partir de celui-ci est utilisée. Si un jeton PKCS#11, un jeton FIDO2 ou un périphérique TPM2 est configuré (en utilisant les options pkcs11-uri=, fido2-device=, tpm2-device=), la clé est déchiffrée avant utilisation.
2.Si aucun fichier clé n'est configuré explicitement de cette manière, un fichier clé est automatiquement chargé à partir de /etc/cryptsetup-keys.d/volume.key et /run/cryptsetup-keys.d/volume.key, s'ils sont présents. Ici aussi, si un jeton/périphérique PKCS#11/FIDO2/TPM2 est configuré, toute clé trouvée de cette manière est déchiffrée avant utilisation.
3.Si l'option try-empty-password est spécifiée, le déverrouillage du volume avec un mot de passe vide est tenté.
4.Si l'option password-cache= est définie sur "yes" ou "read-only", le keyring du noyau est ensuite vérifié pour un mot de passe mis en cache approprié provenant de tentatives précédentes.
5.Enfin, l'utilisateur est interrogé pour un mot de passe, éventuellement plusieurs fois, sauf si l'option headless est définie.

Si aucune clé appropriée ne peut être acquise via l'un des mécanismes décrits ci-dessus, l'activation du volume échoue.

CREDENTIALS

systemd-cryptsetup prend en charge la logique des crédentiels de service telle qu'implémentée par ImportCredential=/LoadCredential=/SetCredential= (voir systemd.exec(5) pour plus de détails). Les identifiants suivants sont utilisés par "systemd-crypsetup@root.service" (généré par systemd-gpt-auto-generator) lorsqu'ils sont transmis :

cryptsetup.passphrase

Cet identifiant spécifie la phrase de passe du volume LUKS.

Ajouté dans la version 256.

cryptsetup.tpm2-pin

Cet identifiant spécifie le code PIN TPM.

Ajouté dans la version 256.

cryptsetup.fido2-pin

Cet identifiant spécifie le code PIN du jeton FIDO2.

Ajouté dans la version 256.

cryptsetup.pkcs11-pin

Cet identifiant spécifie le code PIN du jeton PKCS11.

Ajouté dans la version 256.

cryptsetup.luks2-pin

Cet identifiant spécifie le code PIN demandé par les modules génériques de jeton LUKS2.

Ajouté dans la version 256.
