NOM

systemd-coredump, systemd-coredump.socket, systemd-coredump@.service - Acquérir, sauvegarder et traiter les vidages de mémoire (core dumps)

SYNOPSIS

/usr/lib/systemd/systemd-coredump

/usr/lib/systemd/systemd-coredump --backtrace

systemd-coredump@.service

systemd-coredump.socket

DESCRIPTION

systemd-coredump@.service est un service système pour traiter les vidages de mémoire (core dumps). Il enregistrera un résumé de l'événement dans systemd-journald.service(8), incluant des informations sur l'identifiant du processus, le propriétaire, le signal qui a tué le processus, et la trace de la pile si possible. Il peut également sauvegarder le vidage de mémoire pour un traitement ultérieur. Voir la section « Informations sur le processus en défaut » ci-dessous.

Le comportement d'un programme spécifique lors de la réception d'un signal est régi par quelques facteurs qui sont décrits en détail dans core(5). En particulier, le vidage de mémoire ne sera traité que lorsque les limites de ressources du processus associé (RLIMIT_CORE) sont suffisantes.

Les vidages de mémoire peuvent être écrits dans le journal ou sauvegardés sous forme de fichier. Dans les deux cas, ils peuvent être récupérés pour un traitement ultérieur, par exemple dans gdb(1). Voir coredumpctl(1), en particulier les verbes list et debug.

Par défaut, systemd-coredump enregistrera le vidage de mémoire dans le journal, y compris une trace de pile si possible, et stockera le vidage de mémoire lui-même (une image du contenu de la mémoire du processus) dans un fichier externe dans /var/lib/systemd/coredump/. Ces vidages de mémoire sont supprimés après quelques jours par défaut ; voir /usr/lib/tmpfiles.d/systemd.conf pour les détails. Notez que la suppression des fichiers de vidage de la mémoire du système de fichiers et la purge des entrées du journal sont indépendantes, et le fichier de vidage peut être présent sans l'entrée du journal, et les entrées du journal peuvent pointer vers des fichiers de vidage depuis supprimés. Certaines métadonnées sont attachées aux fichiers de vidage sous forme d'attributs étendus, de sorte que les fichiers de vidage sont utiles à certaines fins même sans les métadonnées complètes disponibles dans l'entrée du journal.

Pour plus de détails, voir Gestion des vidages de mémoire par systemd[1].

Invocation de systemd-coredump

L'exécutable systemd-coredump effectue le travail réel. Il est invoqué deux fois : une fois comme gestionnaire par le noyau, et la seconde fois dans le service systemd-coredump@.service pour écrire effectivement les données dans le journal et traiter et sauvegarder le fichier de vidage.

Lorsque le noyau invoque systemd-coredump pour gérer un vidage de mémoire, il s'exécute en mode privilégié et se connectera au socket créé par l'unité systemd-coredump.socket, qui à son tour lancera une instance non privilégiée de systemd-coredump@.service pour traiter le vidage de mémoire. Par conséquent, systemd-coredump.socket et systemd-coredump@.service sont des unités d'aide qui effectuent le traitement réel des vidages de mémoire et sont soumises à la gestion normale des services.

Il est également possible d'invoquer systemd-coredump avec l'option --backtrace. Dans ce cas, systemd-coredump attend une entrée de journal au format Format d'exportation du journal[2] sur l'entrée standard. L'entrée doit contenir un champ MESSAGE= et tout champ de métadonnées supplémentaire que l'appelant juge raisonnable. systemd-coredump ajoutera des champs de métadonnées supplémentaires de la même manière qu'il le fait pour les vidages de mémoire reçus du noyau. Dans ce mode, aucun vidage de mémoire n'est stocké dans le journal.

Vidages de mémoire dans les conteneurs/espaces de noms

Le service systemd-coredump@.service tentera automatiquement d'extraire une trace de pile d'un processus lorsqu'il plante. Pour cette trace de pile, les symboles seront résolus en fonction des informations de débogage intégrées dans l'image ELF plantée, ou des informations de débogage équivalentes disponibles séparément sur le système hôte. Pour les processus qui plantent à l'intérieur de conteneurs locaux ou d'autres sandboxes basées sur des espaces de noms de montage, ces informations de débogage auxiliaires ne sont généralement pas disponibles sur l'hôte (simplement parce que les conteneurs exécutent généralement des versions logicielles différentes de celles de l'hôte). systemd-coredump fournit deux mécanismes pour résoudre ce problème :

1.Pour les conteneurs système complets exécutant systemd à l'intérieur, il est bon d'activer CoredumpReceive= sur l'unité (voir systemd.resource-control(5)), ce qui garantit que les vidages de mémoire d'un conteneur sont tentés d'être transmis à systemd-coredump@.service s'exécutant à l'intérieur du conteneur, c'est-à-dire que le conteneur peut traiter et stocker ses propres vidages de mémoire. Notez que systemd-nspawn(8) utilise ce mode par défaut s'il est invoqué avec l'option --boot. Ce mode de fonctionnement est généralement recommandé pour des raisons de sécurité : le traitement sensible à la sécurité du vidage de mémoire est effectué à l'intérieur des limites du conteneur lui-même, par le code du conteneur, soutenu par le stockage du conteneur.
2.Alternativement, pour les conteneurs plus restreints (qui n'exécutent pas un système d'init approprié en tant que PID 1), il est possible d'activer le traitement du vidage de mémoire sur l'hôte, avec un accès aux données d'informations de débogage du conteneur lui-même. Ce mode de fonctionnement doit être activé via EnterNamespace= dans coredump.conf(5), et est désactivé par défaut, pour des raisons de sécurité.

Si à la fois CoredumpReceive= est activé sur l'unité du conteneur auquel appartient le vidage de mémoire, et EnterNamespace= est activé dans le fichier de configuration coredump.conf, le premier a la priorité.

CONFIGURATION

Pour les programmes démarrés par systemd, les limites de ressources des processus peuvent être définies par la directive LimitCORE=, voir systemd.exec(5).

Afin d'être utilisé par le noyau pour gérer les vidages de mémoire, systemd-coredump doit être configuré dans le paramètre kernel.core_pattern de sysctl(8). La syntaxe de ce paramètre est expliquée dans core(5). systemd installe le fichier /usr/lib/sysctl.d/50-coredump.conf qui configure kernel.core_pattern en conséquence. Ce fichier peut être masqué ou remplacé pour utiliser un autre paramètre suivant les règles normales de sysctl.d(5). Si la configuration sysctl est modifiée, elle doit être mise à jour dans le noyau avant qu'elle ne prenne effet, voir sysctl(8) et systemd-sysctl(8).

Afin d'être utilisé en mode --backtrace, un gestionnaire de trace de pile approprié doit être installé côté expéditeur. Par exemple, dans le cas de python(1), cela signifie qu'un sys.excepthook doit être installé, voir systemd-coredump-python[3].

Le comportement de systemd-coredump lui-même est configuré via le fichier de configuration /etc/systemd/coredump.conf et les snippets correspondants /etc/systemd/coredump.conf.d/*.conf, voir coredump.conf(5). Une nouvelle instance de systemd-coredump est invoquée à la réception de chaque vidage de mémoire. Par conséquent, les changements dans ces fichiers prendront effet la prochaine fois qu'un vidage de mémoire sera reçu.

Les ressources utilisées par les fichiers de vidage de mémoire sont restreintes de deux manières. Les paramètres comme la taille maximale des vidages de mémoire acquis et les fichiers peuvent être définis dans les fichiers /etc/systemd/coredump.conf et les snippets mentionnés ci-dessus. De plus, le temps de stockage des fichiers de vidage de mémoire est restreint par systemd-tmpfiles, les paramètres correspondants se trouvent par défaut dans /usr/lib/tmpfiles.d/systemd.conf. La valeur par défaut est de supprimer les vidages de mémoire après quelques jours ; voir le fichier ci-dessus pour les détails.

Désactivation du traitement des vidages de mémoire

Pour désactiver le traitement potentiellement gourmand en ressources par systemd-coredump, définissez

Storage=none
ProcessSizeMax=0

dans coredump.conf(5).

Les champs suivants sont enregistrés (si connus) avec l'entrée du journal

COREDUMP_UID=, COREDUMP_PID=, COREDUMP_GID=

Le numéro de processus (PID), le numéro d'utilisateur propriétaire (UID) et le numéro de groupe (GID) du processus ayant planté.

Lorsque le processus ayant planté faisait partie d'un conteneur (ou d'un espace de noms de processus ou utilisateur en général), ce sont les valeurs telles qu'elles sont vues *à l'extérieur*, dans l'espace de noms où systemd-coredump s'exécute.

Ajouté dans la version 248.

COREDUMP_BY_PIDFD=

Si le processus ayant planté a été analysé à l'aide d'un PIDFD fourni par le noyau (nécessite le noyau v6.16), ce champ sera présent et défini sur "1". Si ce champ n'est pas défini, le processus ayant planté a été analysé via un PID, ce qui est connu pour être sujet à des conditions de concurrence.

Ajouté dans la version 258.

COREDUMP_TIMESTAMP=

L'heure du plantage telle que rapportée par le noyau (en µs depuis l'époque).

Ajouté dans la version 248.

COREDUMP_RLIMIT=

La limite logicielle de taille de fichier core, voir getrlimit(2).

Ajouté dans la version 248.

COREDUMP_UNIT=, COREDUMP_SLICE=

Les noms d'unité et de slice système.

Lorsque le processus ayant planté se trouvait dans un conteneur, ce sont les noms d'unités *à l'extérieur*, dans le gestionnaire système principal.

Ajouté dans la version 248.

COREDUMP_CGROUP=

Le cgroup principal de l'unité du processus ayant planté.

Lorsque le processus ayant planté se trouvait dans un conteneur, il s'agit du chemin complet, tel qu'il est vu à l'extérieur du conteneur.

Ajouté dans la version 248.

COREDUMP_PROC_CGROUP=

Informations sur le groupe de contrôle dans le format utilisé dans /proc/self/cgroup. Sur les systèmes avec la hiérarchie cgroup unifiée, il s'agit d'un seul chemin préfixé par "0::", et de plusieurs chemins préfixés par des numéros de contrôleur sur les systèmes hérités.

Lorsque le processus ayant planté se trouvait dans un conteneur, il s'agit du chemin complet, tel qu'il est vu à l'extérieur du conteneur.

Ajouté dans la version 248.

COREDUMP_OWNER_UID=, COREDUMP_USER_UNIT=, COREDUMP_SESSION=

L'UID numérique de l'utilisateur propriétaire de la session de connexion ou de l'unité utilisateur systemd du processus ayant planté, l'unité de gestion utilisateur et l'identifiant de session. Ces trois champs ne sont présents que pour les processus utilisateur.

Lorsque le processus ayant planté se trouvait dans un conteneur, ce sont les valeurs *à l'extérieur*, dans le système principal.

Ajouté dans la version 248.

COREDUMP_SIGNAL_NAME=, COREDUMP_SIGNAL=

Le nom du signal de terminaison (avec le préfixe "SIG" [4]) et sa valeur numérique. (Les deux sont inclus car les numéros de signal varient selon l'architecture.)

Ajouté dans la version 248.

COREDUMP_CWD=, COREDUMP_ROOT=

Le répertoire de travail actuel et le répertoire racine du processus ayant planté.

Lorsque le processus ayant planté se trouve dans un conteneur, ces chemins sont relatifs à la racine de l'espace de noms de montage du conteneur.

Ajouté dans la version 248.

COREDUMP_DUMPABLE=

Le champ PR_GET_DUMPABLE tel que rapporté par le noyau, voir prctl(2).

Ajouté dans la version 258.

COREDUMP_OPEN_FDS=

Informations sur les descripteurs de fichiers ouverts, dans le format suivant : 
fd:/chemin/vers/fichier
pos:     ...
flags:   ...
...
fd:/chemin/vers/fichier
pos:     ...
flags:   ...
...

La première ligne contient le numéro du descripteur de fichier fd et le chemin, tandis que les lignes suivantes montrent le contenu de /proc/pid/fdinfo/fd.

Ajouté dans la version 248.

COREDUMP_EXE=

La destination du lien symbolique /proc/pid/exe.

Lorsque le processus ayant planté se trouve dans un conteneur, ce chemin est relatif à la racine de l'espace de noms de montage du conteneur.

Ajouté dans la version 248.

COREDUMP_CMDLINE=, COREDUMP_COMM=, COREDUMP_ENVIRON=, COREDUMP_PROC_AUXV=, COREDUMP_PROC_LIMITS=, COREDUMP_PROC_MAPS=, COREDUMP_PROC_MOUNTINFO=, COREDUMP_PROC_STATUS=

Champs qui mappent les entrées par processus du système de fichiers /proc/ : /proc/pid/cmdline (la ligne de commande du processus ayant planté), /proc/pid/comm (le nom de commande associé au processus), /proc/pid/environ (le bloc d'environnement du processus ayant planté), /proc/pid/auxv (le vecteur auxiliaire du processus ayant planté, voir getauxval(3)), /proc/pid/limits (les limites de ressources logicielles et matérielles), /proc/pid/maps (les régions mémoire visibles par le processus et leurs permissions d'accès), /proc/pid/mountinfo (les points de montage dans l'espace de noms de montage du processus), /proc/pid/status (divers métadonnées sur le processus).

Voir proc(5) pour plus d'informations.

Ajouté dans la version 248.

COREDUMP_HOSTNAME=

Le nom d'hôte du système.

Lorsque le processus ayant planté se trouvait dans un conteneur, il s'agit du nom d'hôte du conteneur.

Ajouté dans la version 248.

COREDUMP_CONTAINER_CMDLINE=

Pour les processus s'exécutant dans un conteneur, la ligne de commande du processus qui lance le conteneur (le premier processus parent avec un espace de noms de montage différent).

Ajouté dans la version 248.

COREDUMP=

Lorsque le core est stocké dans le journal, l'image core elle-même.

Ajouté dans la version 248.

COREDUMP_FILENAME=

Lorsque le core est stocké en externe, le chemin vers le fichier core.

Ajouté dans la version 248.

COREDUMP_TRUNCATED=

Défini à "1" lorsque le coredump sauvegardé a été tronqué. (Une image core partielle peut encore être traitée par certains outils, bien que toutes les informations ne soient évidemment pas disponibles.)

Ajouté dans la version 248.

COREDUMP_PACKAGE_NAME=, COREDUMP_PACKAGE_VERSION=, COREDUMP_PACKAGE_JSON=

Si l'exécutable contenait des notes ELF de métadonnées .package, elles seront analysées et jointes. Le *package* et la *version* du module ELF 'principal' (c'est-à-dire l'exécutable) seront ajoutés individuellement. Le contenu formaté en JSON de tous les modules sera ajouté en tant qu'objet JSON unique, avec le nom du module comme clé pour chacun. Pour plus d'informations sur ce format et ce contenu de métadonnées, voir le document Package Metadata for Executable Files[5].

Ajouté dans la version 249.

MESSAGE=

Le message généré par systemd-coredump qui inclut la trace de la pile s'il a été généré avec succès. Lorsque systemd-coredump est appelé avec --backtrace, ce champ est fourni par l'appelant.

Ajouté dans la version 248.

D'autres champs divers existent dans l'entrée du journal, mais ils concernent le processus de journalisation, c'est-à-dire systemd-coredump, et non le processus ayant planté. Voir systemd.journal-fields(7).

Les champs suivants sont enregistrés (si connus) avec le fichier externe listé dans COREDUMP_FILENAME= sous forme d'attributs étendus :

user.coredump.pid, user.coredump.uid, user.coredump.gid, user.coredump.signal, user.coredump.timestamp, user.coredump.rlimit, user.coredump.hostname, user.coredump.comm, user.coredump.exe

Ce sont les mêmes que COREDUMP_PID=, COREDUMP_UID=, COREDUMP_GID=, COREDUMP_SIGNAL=, COREDUMP_TIMESTAMP=, COREDUMP_RLIMIT=, COREDUMP_HOSTNAME=, COREDUMP_COMM=, et COREDUMP_EXE=, décrits ci-dessus.

Ajouté dans la version 248.

Ceux-ci peuvent être visualisés en utilisant getfattr(1). Pour le fichier core décrit dans l'entrée de journal ci-dessus :

$ getfattr --absolute-names -d /var/lib/systemd/coredump/core.Web....552351.....zst
# file: /var/lib/systemd/coredump/core.Web....552351.....zst
user.coredump.pid="552351"
user.coredump.uid="1000"
user.coredump.gid="1000"
user.coredump.signal="11"
user.coredump.timestamp="1614342930000000"
user.coredump.comm="Web Content"
user.coredump.exe="/usr/lib64/firefox/firefox"
...
