NOM

systemd-creds - Liste, affiche, chiffre et déchiffre les identifiants de service

SYNTAXE

systemd-creds [OPTIONS...] COMMAND [ARGS...]

DESCRIPTION

systemd-creds est un outil pour lister, afficher, chiffrer et déchiffrer les identifiants d'unités. Les identifiants sont des objets binaires ou textuels de taille limitée qui peuvent être passés aux processus des unités. Ils sont principalement utilisés pour transmettre des clés cryptographiques (publiques et privées) ou des certificats, des informations de compte utilisateur ou des informations d'identité de l'hôte aux services.

Les identifiants sont configurés dans les fichiers d'unités via les paramètres ImportCredential=, LoadCredential=, SetCredential=, LoadCredentialEncrypted= et SetCredentialEncrypted=, voir systemd.exec(5) pour plus de détails.

Pour plus d'informations, consultez la documentation Identifiants système et de service[1].

COMMANDES

Les commandes suivantes sont comprises :

list

Affiche une liste des identifiants passés dans le contexte d'exécution actuel. Cette commande affiche les fichiers du répertoire référencé par la variable d'environnement $CREDENTIALS_DIRECTORY et est destinée à être exécutée depuis le contexte du service.

Avec chaque nom d'identifiant, la taille et l'état de sécurité sont affichés. Ce dernier est l'un des suivants : "secure" (si l'identifiant est sauvegardé dans une mémoire non échangeable, c'est-à-dire "ramfs"), "weak" (s'il est sauvegardé dans un autre type de mémoire), ou "insecure" (s'il a un mode d'accès autre que 0400, c'est-à-dire s'il est lisible par quelqu'un d'autre que le propriétaire).

Ajouté dans la version 250.

cat identifiant...

Affiche le contenu des identifiants spécifiés passés dans le contexte d'exécution actuel. Prend un ou plusieurs noms d'identifiants, dont le contenu doit être écrit sur la sortie standard.

Lorsqu'il est combiné avec --json= ou --transcode=, la sortie est transcodée de manière simple avant d'être affichée.

Ajouté dans la version 250.

setup

Génère une clé de chiffrement hôte pour les identifiants, si elle n'a pas déjà été générée. Cela garantit que le fichier /var/lib/systemd/credential.secret est initialisé avec une clé secrète aléatoire s'il n'existe pas encore. Cette clé secrète est utilisée lors du chiffrement/déchiffrement des identifiants avec encrypt ou decrypt, et n'est accessible qu'à l'utilisateur root. Notez qu'il n'est généralement pas nécessaire d'invoquer cette commande explicitement, car elle est appelée implicitement lorsque encrypt est invoqué et que le chiffrement de la clé d'identifiant hôte est sélectionné.

Ajouté dans la version 250.

encrypt entrée|- sortie|-

Charge le fichier d'identifiant d'entrée spécifié (texte brut non chiffré), le chiffre et écrit le fichier d'identifiant cible (texte chiffré chiffré). Le fichier résultant peut être référencé dans le paramètre LoadCredentialEncrypted= des fichiers d'unités, ou son contenu peut être utilisé littéralement dans les paramètres SetCredentialEncrypted=.

Prend deux chemins de système de fichiers. La partie nom de fichier du chemin de sortie est intégrée en tant que nom dans l'identifiant chiffré, afin de garantir que les identifiants chiffrés ne puissent pas être renommés et réutilisés à d'autres fins sans que cela soit remarqué. Le nom de l'identifiant à intégrer peut être remplacé par le paramètre --name=. Les chemins d'entrée ou de sortie peuvent être spécifiés comme "-", auquel cas les données de l'identifiant sont lues depuis/écrites sur l'entrée standard et la sortie standard. Si le chemin de sortie est spécifié comme "-", le nom de l'identifiant ne peut pas être dérivé du chemin du système de fichiers et doit donc être spécifié explicitement via le commutateur --name=.

Les données de l'identifiant sont chiffrées et authentifiées symétriquement avec l'une des clés de chiffrement suivantes :

1. Une clé secrète dérivée automatiquement de la puce TPM2 du système. Cette clé de chiffrement n'est pas stockée sur le système hôte et donc le déchiffrement n'est possible qu'avec l'accès à la puce TPM2 d'origine. Autrement dit, l'identifiant sécurisé de cette manière ne peut être déchiffré à nouveau que par la machine locale.
2. Une clé secrète stockée dans le fichier /var/lib/systemd/credential.secret, qui n'est accessible qu'à l'utilisateur root. Cette clé de chiffrement "hôte" est stockée sur le système de fichiers hôte, et donc le déchiffrement est possible avec l'accès au système de fichiers hôte et les privilèges suffisants. La clé est automatiquement générée lorsque nécessaire, mais peut également être créée explicitement avec la commande setup, voir ci-dessus.
3. Une combinaison des éléments ci-dessus : une clé de chiffrement dérivée à la fois de la puce TPM2 et du système de fichiers hôte. Cela signifie que le déchiffrement nécessite à la fois l'accès à la puce TPM2 d'origine et à l'installation du système d'exploitation. C'est le mode de fonctionnement par défaut si une puce TPM2 est disponible et que /var/lib/systemd/ réside sur un support persistant.

Laquelle des trois clés doit être utilisée pour le chiffrement peut être configurée avec le commutateur --with-key=. Selon le cas d'utilisation de l'identifiant chiffré, la clé à utiliser peut différer. Par exemple, pour les identifiants qui doivent être accessibles depuis l'initrd, le chiffrement avec la clé hôte n'est pas approprié, car l'accès à la clé hôte n'est généralement pas disponible depuis l'initrd. Ainsi, pour de tels identifiants, seule la clé TPM2 doit être utilisée.

Les identifiants chiffrés sont toujours encodés en Base64.

Utilisez decrypt (voir ci-dessous) pour annuler l'opération de chiffrement et obtenir l'identifiant texte brut déchiffré à partir de l'identifiant texte chiffré.

Les données de l'identifiant sont chiffrées à l'aide d'AES256-GCM, c'est-à-dire offrant à la fois la confidentialité et l'intégrité, utilisées avec un hachage SHA256 de l'une ou des deux clés secrètes décrites ci-dessus.

Ajouté dans la version 250.

decrypt entrée|- [sortie|-]

Annule l'effet de l'opération encrypt : charge le fichier d'identifiant d'entrée spécifié (texte chiffré chiffré), le déchiffre et l'authentifie, et écrit le fichier d'identifiant cible (texte brut déchiffré).

Prend un ou deux chemins de système de fichiers. La partie nom de fichier du chemin d'entrée est comparée au nom de l'identifiant intégré dans le fichier chiffré. S'il ne correspond pas, le déchiffrement échoue. Ceci est fait pour garantir que les identifiants chiffrés ne soient pas réutilisés sans que cela soit détecté. Le nom de l'identifiant à comparer avec le nom de l'identifiant intégré peut également être remplacé par le commutateur --name=. Si le chemin d'entrée est spécifié comme "-", l'identifiant chiffré est lu depuis l'entrée standard. Si un seul chemin est spécifié ou si le chemin de sortie est spécifié comme "-", l'identifiant déchiffré est écrit sur la sortie standard. Dans ce mode, le nom attendu intégré dans l'identifiant ne peut pas être dérivé du chemin et doit être spécifié explicitement avec --name=.

Le déchiffrement des identifiants nécessite l'accès à la puce TPM2 d'origine et/ou à la clé hôte des identifiants, voir ci-dessus. Les informations sur les clés requises sont intégrées dans les données de l'identifiant chiffré, et donc le déchiffrement est entièrement automatique.

Ajouté dans la version 250.

--no-ask-password

Ne pas demander à l'utilisateur de s'authentifier pour les opérations privilégiées.

-h, --help

Affiche un bref message d'aide et quitte.

--version

Affiche une courte chaîne de version et quitte.

OPTIONS

--system

Lorsque spécifié avec les commandes list et cat, opère sur les identifiants passés au système dans son ensemble plutôt que sur ceux passés au contexte d'exécution actuel. Ceci est utile dans les environnements de conteneurs où les identifiants peuvent être transmis par le gestionnaire de conteneurs.

Ajouté dans la version 250.

--user

Lorsque spécifié avec les commandes encrypt et decrypt, chiffre un identifiant à portée utilisateur (plutôt qu'à portée système). Utilisez --uid= pour sélectionner l'utilisateur dont provient l'identifiant. De tels identifiants ne peuvent être déchiffrés qu'à partir du contexte de l'utilisateur spécifié, sauf si des privilèges peuvent être acquis. Généralement, lorsqu'un identifiant chiffré doit être utilisé dans le gestionnaire de services par utilisateur, il doit être chiffré avec cette option activée, et lorsqu'il doit être utilisé dans le gestionnaire de services système, il doit être chiffré sans cette option.

En interne, cela garantit que l'UID numérique et le nom d'utilisateur de l'utilisateur sélectionné, ainsi que le machine-id(5) du système sont incorporés.

orated into la clé de chiffrement.

Ajouté dans la version 256.

--uid=

Spécifie l'utilisateur pour lequel la credential doit être chiffrée. Prend un nom d'utilisateur ou un UID numérique. S'il est défini, il implique --user. S'il est défini sur la chaîne spéciale "self", il définit l'utilisateur sur celui du processus appelant. Si --user est utilisé sans --uid=, alors --uid=self est implicite, c'est-à-dire que la credential est chiffrée pour l'utilisateur appelant.

Ajouté dans la version 256.

--transcode=

Lorsqu'il est spécifié avec les commandes cat ou decrypt, transcodes la sortie avant de l'afficher. Prend l'une des valeurs "base64", "unbase64", "hex" ou "unhex" comme argument, afin d'encoder/décoder les données de credential avec Base64 ou comme série de valeurs hexadécimales. La valeur spéciale "help" peut être utilisée pour lister les types de transcodage pris en charge.

Notez que cela n'a aucun effet sur la commande encrypt, car les credentials chiffrées sont inconditionnellement encodées en Base64.

Ajouté dans la version 250.

--newline=

Lorsqu'il est spécifié avec cat ou decrypt, contrôle s'il faut ajouter un caractère de nouvelle ligne final à la fin de la sortie si celle-ci n'en possède pas déjà un. Prend l'une des valeurs "auto", "yes" ou "no". Le mode par défaut "auto" suffixera la sortie d'un seul caractère de nouvelle ligne uniquement lors de l'écriture des données de credential vers un TTY.

Ajouté dans la version 250.

--pretty, -p

Lorsqu'il est spécifié avec encrypt, contrôle si la credential chiffrée doit être affichée sous forme de paramètre SetCredentialEncrypted= qui peut être directement collé dans un fichier d'unité. N'a d'effet que lorsqu'il est utilisé avec --name= et "-" comme fichier de sortie.

Ajouté dans la version 250.

--name=name

Lorsqu'il est spécifié avec la commande encrypt, contrôle le nom de la credential à intégrer dans les données de credential chiffrées. S'il n'est pas spécifié, le nom est choisi automatiquement à partir du composant du nom de fichier du chemin de sortie spécifié. S'il est spécifié comme une chaîne vide, aucun nom de credential n'est intégré dans la credential chiffrée, et aucune vérification du nom de credential n'est effectuée lors du déchiffrement de la credential.

Lorsqu'il est spécifié avec la commande decrypt, contrôle le nom de la credential à valider par rapport au nom de credential intégré dans la credential chiffrée. S'il n'est pas spécifié, le nom est choisi automatiquement à partir du composant du nom de fichier du chemin d'entrée spécifié. Si aucun nom de credential n'est intégré dans le fichier de credential chiffrée (c'est-à-dire que --name= avec une chaîne vide a été utilisé lors du chiffrement), le nom spécifié n'a aucun effet car aucune validation du nom de credential n'est effectuée.

L'intégration du nom de la credential dans la credential chiffrée est effectuée afin de se protéger contre la réutilisation des credentials à des fins pour lesquelles elles n'étaient pas initialement destinées, en supposant que le nom de la credential est choisi avec soin pour encoder son objectif.

Ajouté dans la version 250.

--timestamp=timestamp

Lorsqu'il est spécifié avec la commande encrypt, contrôle l'horodatage à intégrer dans la credential chiffrée. Par défaut, il s'agit de l'heure actuelle. Prend une spécification d'horodatage dans le format décrit dans systemd.time(7).

Lorsqu'il est spécifié avec la commande decrypt, contrôle l'horodatage à utiliser pour valider l'horodatage "not-after" qui a été configuré avec --not-after= lors du chiffrement. S'il n'est pas spécifié, il prend par défaut l'heure système actuelle.

Ajouté dans la version 250.

--not-after=timestamp

Lorsqu'il est spécifié avec la commande encrypt, contrôle l'heure à partir de laquelle la credential ne doit plus être utilisée. Ceci intègre l'horodatage spécifié dans la credential chiffrée. Lors du déchiffrement, l'horodatage est vérifié par rapport à l'horloge système actuelle, et si l'horodatage est dans le passé, le déchiffrement échouera. Par défaut, aucun horodatage de ce type n'est défini. Prend une spécification d'horodatage dans le format décrit dans systemd.time(7).

Ajouté dans la version 250.

--with-key=, -H, -T

Lorsqu'il est spécifié avec la commande encrypt, contrôle la clé de chiffrement/signature à utiliser. Prend l'une des valeurs "host", "tpm2", "host+tpm2", "null", "auto", "auto-initrd". Voir ci-dessus pour les détails sur les trois types de clés. S'il est défini sur "auto" (qui est la valeur par défaut), la clé TPM2 est utilisée si un périphérique TPM2 est trouvé et que le système ne fonctionne pas dans un conteneur. La clé hôte est utilisée si /var/lib/systemd/ se trouve sur un support persistant. Cela signifie que sur les systèmes typiques, le chiffrement est par défaut lié à la fois à la puce TPM2 et à l'installation du système d'exploitation, et les deux doivent être disponibles pour déchiffrer à nouveau la credential. Si "auto" est sélectionné mais qu'aucun TPM2 n'est disponible (ou que le système fonctionne dans un conteneur) ni que /var/lib/systemd/ ne se trouve sur un support persistant, le chiffrement échouera. S'il est défini sur "null", une clé de longueur nulle fixe est utilisée (ainsi, dans ce mode, aucune confidentialité ni authenticité n'est fournie !). Cette logique est utile pour couvrir les systèmes qui manquent d'une puce TPM2 mais où les credentials doivent être générées. Notez que le déchiffrement de telles credentials est refusé sur les systèmes qui ont une puce TPM2 et où UEFI SecureBoot est activé (cela est fait afin qu'un tel système verrouillé ne puisse pas être trompé en chargeant une credential générée de cette manière qui manque d'informations d'authentification). S'il est défini sur "auto-initrd", une clé TPM2 est utilisée si un TPM2 est trouvé. Sinon, une clé de longueur nulle fixe est utilisée, équivalente au mode "null". Cette option est particulièrement utile pour générer des fichiers de credentials qui sont chiffrés/authentifiés contre TPM2 là où c'est possible mais qui fonctionnent toujours sur des systèmes n'offrant pas ce support. La valeur spéciale "help" peut être utilisée pour lister les types de clés pris en charge.

Le commutateur -H est un raccourci pour --with-key=host. De même, -T est un raccourci pour --with-key=tpm2.

Lors du chiffrement de credentials qui doivent être utilisées dans l'initrd (où /var/lib/systemd/ n'est généralement pas disponible), assurez-vous d'utiliser le mode --with-key=auto-initrd pour désactiver la liaison au secret de l'hôte.

Ce commutateur n'a aucun effet sur la commande decrypt, car les informations sur la clé à utiliser pour le déchiffrement sont déjà incluses dans la credential chiffrée.

Ajouté dans la version 250.

--tpm2-device=PATH

Contrôle le périphérique TPM2 à utiliser. Attend un chemin de nœud de périphérique faisant référence à la puce TPM2 (par exemple, /dev/tpmrm0). Alternativement, la valeur spéciale "auto" peut être spécifiée, afin de déterminer automatiquement le nœud de périphérique d'un périphérique TPM2 approprié (dont il doit y en avoir exactement un). La valeur spéciale "list" peut être utilisée pour énumérer tous les périphériques TPM2 appropriés actuellement découverts.

Ajouté dans la version 250.

--tpm2-pcrs=PCR[+PCR...]

Configure les PCR (Platform Configuration Registers) TPM2 auxquels lier la clé de chiffrement. Prend une liste séparée par "+" d'index PCR numériques dans la plage 0...23. Si une chaîne vide est spécifiée, la clé de chiffrement est liée à aucune PCR (c'est aussi la valeur par défaut si cette option n'est pas utilisée). Pour plus de détails sur les PCR disponibles, voir la documentation du commutateur du même nom pour systemd-cryptenroll(1).

Ajouté dans la version 250.

--tpm2-public-key=PATH, --tpm2-public-key-pcrs=PCR[+PCR...]

Configure une politique de PCR signée par TPM2 pour la lier, à utiliser avec la commande encrypt. L'option --tpm2-public-key= accepte un chemin vers une clé publique RSA encodée en PEM, pour la lier. Si elle n'est pas explicitement spécifiée, mais qu'un fichier tpm2-pcr-public-key.pem existe dans l'un des répertoires /etc/systemd/, /run/systemd/, /usr/lib/systemd/ (recherchés dans cet ordre), il est automatiquement utilisé. L'option --tpm2-public-key-pcrs= prend une liste d'index PCR TPM2 auxquels se lier (même syntaxe que --tpm2-pcrs= décrit ci-dessus). S'il n'est pas spécifié, la valeur par défaut est 11 (c'est-à-dire qu'il lie la politique à toute image noyau unifiée pour laquelle une signature PCR peut être fournie).

Notez la différence entre --tpm2-pcrs= et --tpm2-public-key-pcrs= : le premier lie le déchiffrement aux valeurs PCR actuelles et spécifiques ; le second lie le déchiffrement à tout ensemble de valeurs PCR pour lesquelles une signature par la clé publique spécifiée peut être fournie. Ce dernier est donc plus utile dans les scénarios où les mises à jour logicielles doivent être possibles sans perdre l'accès à tous les secrets précédemment chiffrés.

Ajouté dans la version 252.

--tpm2-signature=PATH

Prend un chemin vers un fichier de signature PCR TPM2 tel que généré par l'outil systemd-measure(1) et qui peut être utilisé pour permettre à la commande decrypt de déchiffrer les credentials qui sont liées à des valeurs PCR signées spécifiques. Si ce n'est pas spécifié explicitement, et qu'une tentative de déchiffrement d'une credential avec une politique PCR signée est effectuée, un fichier de signature approprié tpm2-pcr-signature.json est recherché dans /etc/systemd/, /run/systemd/, /usr/lib/systemd/ (dans cet ordre) et utilisé.

Ajouté dans la version 252.

--allow-null

Autorise le déchiffrement des credentials qui utilisent une clé vide.

Ajouté dans la version 256.

--quiet, -q

Supprime la sortie supplémentaire.

Ajouté dans la version 251.

--no-pager

Ne pas rediriger la sortie vers un pagineur.

--no-legend

Ne pas imprimer la légende, c'est-à-dire les en-têtes de colonnes et le pied de page avec des indications.

--json=MODE

Affiche la sortie formatée en JSON. Attend l'une des valeurs "short" (pour la sortie la plus courte possible sans espaces blancs redondants ni sauts de ligne), "pretty" (pour une version jolie de la même sortie, avec indentation et sauts de ligne) ou "off" (pour désactiver la sortie JSON, par défaut).

STATUT DE SORTIE

En cas de succès, 0 est retourné.

EXEMPLES

Exemple 1. Chiffrement d'un mot de passe à utiliser comme credential

La ligne de commande suivante chiffre le mot de passe spécifié "hunter2", écrivant le résultat dans le fichier password.cred.

# echo -n hunter2 | systemd-creds encrypt - password.cred

Ceci déchiffre le fichier password.cred à nouveau, révélant le mot de passe littéral :

# systemd-creds decrypt password.cred
hunter2

Exemple 2. Chiffrement d'un mot de passe

systemd-creds(1) - Arch Linux

NAME

systemd-creds - securely store and retrieve credentials

SYNOPSIS

systemd-creds -h
systemd-creds --set ...
systemd-creds --get ...
systemd-creds --list ...
systemd-creds --delete ...
systemd-creds --wipe ...

DESCRIPTION

systemd-creds is a tool to manage and use credentials. Credentials are small, encrypted blobs of data that are typically used to store secrets like passwords or API keys. systemd-creds focuses on storing credentials securely on disk and making them available to systemd units.

systemd-creds can be used to create, retrieve, list, and delete credentials. It can also wipe all credentials stored on the system.

COMMANDS

--set, -s

Creates a new credential or updates an existing one. Requires the --name option to specify the name of the credential. The value of the credential can be provided via standard input or with the --value option.

--get, -g

Retrieves the value of a credential. Requires the --name option to specify the name of the credential. The value is printed to standard output.

--list, -l

Lists all available credentials. The output is a list of credential names.

--delete, -d

Deletes a credential. Requires the --name option to specify the name of the credential.

--wipe, -w

Deletes all credentials stored on the system. This operation is irreversible.

OPTIONS

--name=NAME

Specifies the name of the credential. This option is required for --set, --get, and --delete.

--value=VALUE

Specifies the value of the credential. If this option is not provided, the value is read from standard input.

--input-file=FILE

Reads the credential value from the specified file.

--output-file=FILE

Writes the retrieved credential value to the specified file instead of standard output.

-p, --prompt

Prompt the user for the credential value interactively. This option is useful when creating or updating credentials.

-n, --no-tty

Do not use a TTY for interaction. This option is useful when scripting and piping input.

--directory=DIR

Specifies the directory where credentials are stored. The default is /etc/systemd/system/credentials/.

-h, --help

Show help message and exit.

--version

Show version information and exit.

EXIT STATUS

Returns 0 on success, and a non-zero value on failure.

EXAMPLES

Store a password for MySQL

# systemd-creds --set --name=mysql-password <<< 'my-secret-password'

Retrieve the MySQL password

# systemd-creds --get --name=mysql-password
my-secret-password

List all credentials

# systemd-creds --list
mysql-password

Delete a credential

# systemd-creds --delete --name=mysql-password

Wipe all credentials

# systemd-creds --wipe

Encrypt and include it in a unit file

The following command line prompts the user for a password and generates a SetCredentialEncrypted= line from it for a credential named "mysql-password", suitable for inclusion in a unit file.

Utilizing the unit file drop-in logic this can be used to securely pass a password credential to a unit. A similar, more comprehensive set of commands to insert a password into a service xyz.service:

# mkdir -p /etc/systemd/system/xyz.service.d
# systemd-ask-password -n | ( echo "[Service]" && systemd-creds encrypt --name=mysql-password -p - - ) >/etc/systemd/system/xyz.service.d/50-password.conf
# systemctl daemon-reload
# systemctl restart xyz.service
