NOM

systemd.path - Configuration des unités de chemin

SYNTAXE

chemin.path

DESCRIPTION

Un fichier de configuration d'unité dont le nom se termine par « .path » encode des informations sur un chemin surveillé par systemd, pour l'activation basée sur les chemins.

Cette page de manuel liste les options de configuration spécifiques à ce type d'unité. Voir systemd.unit(5) pour les options communes à tous les fichiers de configuration d'unité. Les éléments de configuration communs sont configurés dans les sections génériques [Unit] et [Install]. Les options de configuration spécifiques aux chemins sont configurées dans la section [Path].

Pour chaque fichier de chemin, un fichier d'unité correspondant doit exister, décrivant l'unité à activer lorsque le chemin change. Par défaut, un service portant le même nom que le chemin (sauf pour le suffixe) est activé. Exemple : un fichier de chemin foo.path active un service correspondant foo.service. L'unité à activer peut être contrôlée par Unit= (voir ci-dessous).

Internement, les unités de chemin utilisent l'API inotify(7) pour surveiller les systèmes de fichiers. De ce fait, elle souffre des mêmes limitations qu'inotify, et ne peut par exemple pas être utilisée pour surveiller des fichiers ou des répertoires modifiés par d'autres machines sur des systèmes de fichiers NFS distants.

Lorsqu'un service déclenché par une unité de chemin se termine (qu'il ait réussi ou échoué), les chemins surveillés sont immédiatement vérifiés à nouveau, et le service est en conséquence redémarré instantanément. Comme protection contre le bouclage intensif dans ce cycle de déclenchement/démarrage, une limite de taux de démarrage est appliquée au service, voir StartLimitIntervalSec= et StartLimitBurst= dans systemd.unit(5). Contrairement aux autres échecs de service, l'état d'erreur indiquant que la limite de taux de démarrage est atteinte est propagé du service à l'unité de chemin et fait également échouer l'unité de chemin, mettant ainsi fin à la boucle.

DÉPENDANCES AUTOMATIQUES

Dépendances implicites

Les dépendances suivantes sont ajoutées implicitement :

•Si une unité de chemin se trouve sous une autre unité de montage dans la hiérarchie du système de fichiers, une dépendance d'exigence et une dépendance d'ordonnancement sont automatiquement créées entre les deux unités.
•Une dépendance implicite Before= est ajoutée entre une unité de chemin et l'unité qu'elle est censée activer.

Dépendances par défaut

Les dépendances suivantes sont ajoutées sauf si DefaultDependencies=no est défini :

•Les unités de chemin auront automatiquement des dépendances de type Before= sur paths.target, des dépendances de type After= et Requires= sur sysinit.target, et des dépendances de type Conflicts= et Before= sur shutdown.target. Celles-ci garantissent que les unités de chemin sont terminées proprement avant l'arrêt du système. Seules les unités de chemin impliquées dans le démarrage précoce ou l'arrêt tardif du système devraient désactiver l'option DefaultDependencies=.

OPTIONS

Les fichiers d'unité de chemin peuvent inclure les sections [Unit] et [Install], qui sont décrites dans systemd.unit(5).

Les fichiers d'unité de chemin doivent inclure une section [Path], qui contient des informations sur le ou les chemins qu'elle surveille. Les options spécifiques à la section [Path] des unités de chemin sont les suivantes :

PathExists=, PathExistsGlob=, PathChanged=, PathModified=, DirectoryNotEmpty=

Définit les chemins à surveiller pour certains changements : PathExists= peut être utilisé pour surveiller la simple existence d'un fichier ou d'un répertoire. Si le fichier spécifié existe, l'unité configurée est activée. PathExistsGlob= fonctionne de manière similaire, mais vérifie l'existence d'au moins un fichier correspondant au modèle globbing spécifié. PathChanged= peut être utilisé pour surveiller un fichier ou un répertoire et activer l'unité configurée chaque fois qu'il change. Il n'est pas activé à chaque écriture dans le fichier surveillé, mais il est activé si le fichier qui était ouvert en écriture est fermé. PathModified= est similaire, mais il est en outre activé également lors d'écritures simples sur le fichier surveillé. DirectoryNotEmpty= peut être utilisé pour surveiller un répertoire et activer l'unité configurée chaque fois qu'il contient au moins un fichier.

Les arguments de ces directives doivent être des chemins absolus du système de fichiers.

Plusieurs directives peuvent être combinées, de même type ou de types différents, pour surveiller plusieurs chemins. Si la chaîne vide est assignée à l'une de ces options, la liste des chemins à surveiller est réinitialisée, et toute affectation antérieure de ces options n'aura aucun effet.

Si un chemin existe déjà (dans le cas de PathExists= et PathExistsGlob=) ou si un répertoire est déjà non vide (dans le cas de DirectoryNotEmpty=) au moment où l'unité de chemin est activée, alors l'unité configurée est immédiatement activée également. Quelque chose de similaire ne s'applique pas à PathChanged= et PathModified=.

Si le chemin lui-même ou l'un des répertoires contenant le chemin ne sont pas accessibles, systemd surveillera les changements de permissions et constatera que les conditions sont satisfaites lorsque les permissions le permettront.

Notez que les fichiers dont le nom commence par un point (c'est-à-dire les fichiers cachés) sont généralement ignorés lors de la surveillance de ces chemins.

Unit=

L'unité à activer lorsque l'un des chemins configurés change. L'argument est un nom d'unité, dont le suffixe n'est pas ".path". Si elle n'est pas spécifiée, cette valeur est par défaut un service portant le même nom que l'unité de chemin, sauf pour le suffixe. (Voir ci-dessus.) Il est recommandé que le nom de l'unité qui est activée et le nom de l'unité de chemin soient nommés de manière identique, à l'exception du suffixe.

MakeDirectory=

Prend un argument booléen. S'il est vrai, les répertoires à surveiller sont créés avant la surveillance. Cette option est ignorée pour les paramètres PathExists=. Par défaut, c'est false.

DirectoryMode=

Si MakeDirectory= est activé, utilisez le mode spécifié ici pour créer les répertoires en question. Prend un mode d'accès en notation octale. Par défaut, c'est 0755.

TriggerLimitIntervalSec=, TriggerLimitBurst=

Configure une limite sur la fréquence à laquelle cette unité de chemin peut être activée dans un intervalle de temps spécifique. TriggerLimitIntervalSec= peut être utilisé pour configurer la durée de l'intervalle de temps dans les unités de temps habituelles "us", "ms", "s", "min", "h", ... et par défaut à 2s. Voir systemd.time(7) pour plus de détails sur les différentes unités de temps comprises. Le paramètre TriggerLimitBurst= prend une valeur entière positive et spécifie le nombre d'activations permises par intervalle de temps, et par défaut à 200. Définissez l'un ou l'autre à 0 pour désactiver toute forme de limitation du taux de déclenchement. Si la limite est atteinte, l'unité est placée en mode échec et ne surveillera plus les chemins jusqu'à ce qu'elle soit redémarrée. Notez que cette limite est appliquée avant que l'activation du service ne soit mise en file d'attente.

Ajouté dans la version 250.

Consultez systemd.unit(5), systemd.exec(5), et systemd.kill(5) pour plus de paramètres.

VOIR AUSSI

Les variables d'environnement détaillant le déclenchement seront définies pour les unités déclenchées. Voir la section « Variables d'environnement définies ou propagées par le gestionnaire de services » dans systemd.exec(5) pour plus de détails.
