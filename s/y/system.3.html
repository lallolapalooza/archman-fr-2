system(3) Manuel des fonctions de bibliothèque system(3)

NOM

system - exécuter une commande shell

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <stdlib.h>
int system(const char *command);

DESCRIPTION

La fonction de bibliothèque system() se comporte comme si elle utilisait fork(2) pour créer un processus fils qui exécutait la commande shell spécifiée dans command en utilisant execl(3) comme suit :


execl("/bin/sh", "sh", "-c", command, (char *) NULL);

system() retourne après que la commande a été terminée.

Pendant l'exécution de la commande, SIGCHLD sera bloqué, et SIGINT et SIGQUIT seront ignorés, dans le processus qui appelle system(). (Ces signaux seront gérés selon leurs valeurs par défaut à l'intérieur du processus fils qui exécute command.)

Si command est NULL, alors system() retourne un état indiquant si un shell est disponible sur le système.

VALEUR DE RETOUR

La valeur de retour de system() est l'un des éléments suivants :

•
Si command est NULL, alors une valeur non nulle si un shell est disponible, ou 0 si aucun shell n'est disponible.
•
Si un processus fils n'a pas pu être créé, ou si son état n'a pas pu être récupéré, la valeur de retour est -1 et errno est défini pour indiquer l'erreur.
•
Si un shell n'a pas pu être exécuté dans le processus fils, alors la valeur de retour est comme si le shell fils avait terminé en appelant _exit(2) avec l'état 127.
•
Si tous les appels système réussissent, alors la valeur de retour est l'état de terminaison du shell fils utilisé pour exécuter command. (L'état de terminaison d'un shell est l'état de terminaison de la dernière commande qu'il exécute.)

Dans les deux derniers cas, la valeur de retour est un "état d'attente" qui peut être examiné à l'aide des macros décrites dans waitpid(2). (c'est-à-dire, WIFEXITED(), WEXITSTATUS(), et ainsi de suite).

system() n'affecte pas l'état d'attente des autres fils.

ERREURS

system() peut échouer avec les mêmes erreurs que fork(2).

ATTRIBUTS

Pour une explication des termes utilisés dans cette section, voir attributes(7).

Interface Attribut Valeur
system () Sécurité des threads MT-Safe

NORMES

C11, POSIX.1-2008.

HISTORIQUE

POSIX.1-2001, C89.

NOTES

system() offre simplicité et commodité : elle gère tous les détails de l'appel à fork(2), execl(3), et waitpid(2), ainsi que les manipulations nécessaires des signaux ; de plus, le shell effectue les substitutions habituelles et les redirections d'E/S pour command. Le coût principal de system() est l'inefficacité : des appels système supplémentaires sont nécessaires pour créer le processus qui exécute le shell et pour exécuter le shell.

Si le macro de test de fonctionnalité _XOPEN_SOURCE est défini (avant d'inclure n'importe quel fichier d'en-tête), alors les macros décrites dans waitpid(2) (WEXITSTATUS(), etc.) sont rendues disponibles lors de l'inclusion de <stdlib.h>.

Comme mentionné, system() ignore SIGINT et SIGQUIT. Cela peut rendre les programmes qui l'appellent en boucle ininterrompables, à moins qu'ils ne prennent soin eux-mêmes de vérifier l'état de sortie du fils. Par exemple :


while (quelque chose) {
    int ret = system("foo");
    if (WIFSIGNALED(ret) &&
        (WTERMSIG(ret) == SIGINT || WTERMSIG(ret) == SIGQUIT))
            break;
}

Selon POSIX.1, il n'est pas spécifié si les gestionnaires enregistrés à l'aide de pthread_atfork(3) sont appelés pendant l'exécution de system(). Dans l'implémentation glibc, de tels gestionnaires ne sont pas appelés.

Avant glibc 2.1.3, la vérification de la disponibilité de /bin/sh n'était pas réellement effectuée si command était NULL ; au lieu de cela, il était toujours supposé être disponible, et system() retournait toujours 1 dans ce cas. Depuis glibc 2.1.3, cette vérification est effectuée car, bien que POSIX.1-2001 exige qu'une implémentation conforme fournisse un shell, ce shell peut ne pas être disponible ou exécutable si le programme appelant a préalablement appelé chroot(2) (ce qui n'est pas spécifié par POSIX.1-2001).

Il est possible que la commande shell se termine avec un état de 127, ce qui donne une valeur de retour de system() indiscernable du cas où aucun shell n'a pu être exécuté dans le processus fils.

Mises en garde

N'utilisez pas system() à partir d'un programme privilégié (un programme set-user-ID ou set-group-ID, ou un programme avec des capacités) car des valeurs étranges pour certaines variables d'environnement pourraient être utilisées pour saper l'intégrité du système. Par exemple, PATH pourrait être manipulé de manière à ce qu'un programme arbitraire soit exécuté avec des privilèges. Utilisez la famille de fonctions exec(3) à la place, mais pas execlp(3) ou execvp(3) (qui utilisent également la variable d'environnement PATH pour rechercher un exécutable).

system() ne fonctionnera pas correctement à partir de programmes avec des privilèges set-user-ID ou set-group-ID sur des systèmes sur lesquels /bin/sh est bash version 2 : par mesure de sécurité, bash 2 abandonne les privilèges au démarrage. (Debian utilise un shell différent, dash(1), qui ne le fait pas lorsqu'il est invoqué comme sh.)

Toute entrée utilisateur employée dans le cadre de command devrait être soigneusement assainie, pour s'assurer que des commandes shell ou des options de commande inattendues ne sont pas exécutées. De tels risques sont particulièrement graves lors de l'utilisation de system() à partir d'un programme privilégié.

BOGUES

Si le nom de la commande commence par un trait d'union, sh(1) interprète le nom de la commande comme une option, et le comportement est indéfini. (Voir l'option -c de sh(1).) Pour contourner ce problème, préfixez la commande par un espace comme dans l'appel suivant :


    system(" -commande-malheureuse-nom");

VOIR AUSSI

sh(1), execve(2), fork(2), sigaction(2), sigprocmask(2), wait(2), exec(3), signal(7)
