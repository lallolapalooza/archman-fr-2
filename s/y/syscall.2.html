syscall(2) Manuel des appels système syscall(2)

NOM

syscall - appel système indirect

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/syscall.h>      /* Définition des constantes SYS_* */
#include <unistd.h>
long syscall(long number, ...);
Exigences de macro de test de fonctionnalités pour glibc (voir feature_test_macros(7)) :

syscall() :

    Depuis glibc 2.19 :
        _DEFAULT_SOURCE
    Avant glibc 2.19 :
        _BSD_SOURCE || _SVID_SOURCE

DESCRIPTION

syscall() est une petite fonction de bibliothèque qui invoque l'appel système dont l'interface en langage assembleur a le numéro spécifié number avec les arguments spécifiés. L'utilisation de syscall() est utile, par exemple, lors de l'invocation d'un appel système qui n'a pas de fonction d'en-tête dans la bibliothèque C.

syscall() enregistre les registres du processeur avant d'effectuer l'appel système, restaure les registres au retour de l'appel système et stocke toute erreur retournée par l'appel système dans errno(3).

Les constantes symboliques pour les numéros d'appels système se trouvent dans le fichier d'en-tête <sys/syscall.h>.

VALEUR DE RETOUR

La valeur de retour est définie par l'appel système invoqué. En général, une valeur de retour de 0 indique un succès. Une valeur de retour de -1 indique une erreur, et un numéro d'erreur est stocké dans errno.

ERREURS

ENOSYS
Le numéro d'appel système demandé n'est pas implémenté.

D'autres erreurs sont spécifiques à l'appel système invoqué.

NOTES

syscall() est apparu pour la première fois dans 4BSD.

Exigences spécifiques à l'architecture

Chaque ABI d'architecture a ses propres exigences quant à la manière dont les arguments des appels système sont transmis au noyau. Pour les appels système qui ont une fonction d'en-tête glibc (par exemple, la plupart des appels système), glibc gère les détails de la copie des arguments dans les bons registres d'une manière adaptée à l'architecture. Cependant, lors de l'utilisation de syscall() pour effectuer un appel système, l'appelant peut avoir besoin de gérer les détails dépendants de l'architecture ; cette exigence est le plus souvent rencontrée sur certaines architectures 32 bits.

Par exemple, sur l'architecture ARM avec l'ABI embarquée (EABI), une valeur de 64 bits (par exemple, long long) doit être alignée sur une paire de registres pairs. Ainsi, en utilisant syscall() au lieu de l'en-tête fourni par glibc, l'appel système readahead(2) serait invoqué comme suit sur l'architecture ARM avec l'EABI en mode little endian :


syscall(SYS_readahead, fd, 0,
        (unsigned int) (offset & 0xFFFFFFFF),
        (unsigned int) (offset >> 32),
        count);

Étant donné que l'argument offset est de 64 bits et que le premier argument (fd) est passé dans r0, l'appelant doit manuellement diviser et aligner la valeur de 64 bits afin qu'elle soit passée dans la paire de registres r2/r3. Cela signifie insérer une valeur factice dans r1 (le deuxième argument de 0). Il faut également faire attention à ce que la division respecte les conventions d'endianness (selon l'ABI C de la plateforme).

Des problèmes similaires peuvent survenir sur MIPS avec l'ABI O32, sur PowerPC et parisc avec l'ABI 32 bits, et sur Xtensa.

Notez que bien que l'ABI C parisc utilise également des paires de registres alignées, elle utilise une couche de transition pour masquer le problème à l'espace utilisateur.

Les appels système affectés sont fadvise64_64(2), ftruncate64(2), posix_fadvise(2), pread64(2), pwrite64(2), readahead(2), sync_file_range(2), et truncate64(2).

Cela n'affecte pas les appels système qui divisent et assemblent manuellement des valeurs de 64 bits tels que _llseek(2), preadv(2), preadv2(2), pwritev(2), et pwritev2(2). Bienvenue dans le merveilleux monde de l'héritage historique.

Conventions d'appel spécifiques à l'architecture

Chaque architecture a sa propre manière d'invoquer et de passer des arguments au noyau. Les détails pour diverses architectures sont listés dans les deux tableaux ci-dessous.

Le premier tableau liste l'instruction utilisée pour la transition vers le mode noyau (qui pourrait ne pas être le moyen le plus rapide ou le meilleur pour passer au noyau, vous pourriez donc devoir vous référer à vdso(7)), le registre utilisé pour indiquer le numéro d'appel système, le ou les registres utilisés pour retourner le résultat de l'appel système, et le registre utilisé pour signaler une erreur.

Notes :

•
Sur quelques architectures, un registre est utilisé comme booléen (0 indiquant aucune erreur, et -1 indiquant une erreur) pour signaler que l'appel système a échoué. La valeur d'erreur réelle est toujours contenue dans le registre de retour. Sur sparc, le bit de retenue (csr) dans le registre d'état du processeur (psr) est utilisé à la place d'un registre complet. Sur powerpc64, le bit de débordement de résumé (SO) dans le champ 0 du registre de condition (cr0) est utilisé.
•
NR est le numéro de l'appel système.
•
Pour s390 et s390x, NR (le numéro de l'appel système) peut être transmis directement avec svc NR s'il est inférieur à 256.
•
Sur SuperH, des numéros de piège supplémentaires sont pris en charge pour des raisons historiques, mais trapa#31 est l'ABI « unifié » recommandé.
•
L'ABI x32 partage la table des appels système avec l'ABI x86-64, mais il y a quelques nuances :
•
Afin d'indiquer qu'un appel système est appelé sous l'ABI x32, un bit supplémentaire, __X32_SYSCALL_BIT, est mis en OR bit à bit avec le numéro de l'appel système. L'ABI utilisé par un processus affecte certains comportements du processus, y compris la gestion des signaux ou la reprise des appels système.
•
Comme x32 a des tailles différentes pour les types long et pointeur, les dispositions de certaines structures (mais pas toutes ; struct timeval ou struct rlimit font 64 bits, par exemple) sont différentes. Pour gérer cela, des appels système supplémentaires sont ajoutés à la table des appels système, à partir du numéro 512 (sans le __X32_SYSCALL_BIT). Par exemple, __NR_readv est défini comme 19 pour l'ABI x86-64 et comme __X32_SYSCALL_BIT | 515 pour l'ABI x32. La plupart de ces appels système supplémentaires sont en fait identiques aux appels système utilisés pour fournir la compatibilité i386. Il existe cependant quelques exceptions notables, telles que preadv2(2), qui utilise des entités struct iovec avec des pointeurs et des tailles de 4 octets (« compat_iovec » en termes de noyau), mais transmet un argument pos de 8 octets dans un seul registre et non deux, comme cela se fait dans toutes les autres ABI.
•
Certaines architectures (à savoir Alpha, IA-64, MIPS, SuperH, sparc/32 et sparc/64) utilisent un registre supplémentaire (« Retval2 » dans le tableau ci-dessus) pour renvoyer une deuxième valeur de retour de l'appel système pipe(2) ; Alpha utilise cette technique dans les appels système spécifiques à l'architecture getxpid(2), getxuid(2) et getxgid(2) également. D'autres architectures n'utilisent pas le registre de seconde valeur de retour dans l'interface d'appel système, même s'il est défini dans l'ABI System V.

EXEMPLES

#define _GNU_SOURCE
#include <signal.h>
#include <sys/syscall.h>
#include <sys/types.h>
#include <unistd.h>
int
main(void)
{
    pid_t tid;
    tid = syscall(SYS_gettid);
    syscall(SYS_tgkill, getpid(), tid, SIGHUP);
}
