SYSTEMD-PCRLOCK(8) systemd-pcrlock SYSTEMD-PCRLOCK(8)

NOM

systemd-pcrlock, systemd-pcrlock-file-system.service, systemd-pcrlock-firmware-code.service, systemd-pcrlock-firmware-config.service, systemd-pcrlock-machine-id.service, systemd-pcrlock-make-policy.service, systemd-pcrlock-secureboot-authority.service, systemd-pcrlock-secureboot-policy.service - Analyser et prédire les états des PCR de TPM2 et générer une politique d'accès à partir de la prédiction

SYNTAXE

/usr/lib/systemd/systemd-pcrlock [OPTIONS...]

DESCRIPTION

Note : cette commande est actuellement expérimentale. Bien qu'elle devienne probablement un composant régulier de systemd, son comportement et son interface peuvent encore changer.

systemd-pcrlock est un outil qui peut être utilisé pour analyser et prédire les mesures des PCR de TPM2, et générer des politiques d'accès TPM2 à partir de la prédiction, qu'il stocke dans un index NV de TPM2 (c'est-à-dire dans la mémoire non volatile de TPM2). Cela peut alors être utilisé pour restreindre l'accès aux objets TPM2 (tels que les clés de chiffrement de disque) aux démarrages système lors desquels seuls des composants spécifiques et approuvés sont utilisés.

systemd-pcrlock utilise comme entrées pour son analyse et sa prédiction :

•Le journal d'événements TPM2 du firmware UEFI (c'est-à-dire /sys/kernel/security/tpm0/binary_bios_measurements) du démarrage actuel.
•Le journal d'événements TPM2 de l'espace utilisateur (c'est-à-dire /run/log/systemd/tpm2-measure.log) du démarrage actuel.
•L'état actuel des PCR de la puce TPM2.
•Les fichiers de définition des composants de démarrage (*.pcrlock et *.pcrlock.d/*.pcrlock, voir systemd.pcrlock(5)) qui définissent chacun les mesures attendues pour un composant du processus de démarrage, autorisant des variantes alternatives pour chacun. (Les variantes peuvent être utilisées pour bénir plusieurs versions du noyau ou du chargeur de démarrage en même temps.)

Il utilise ces entrées pour générer un journal d'événements combiné, le validant par rapport aux états des PCR. Il tente ensuite de reconnaître les enregistrements du journal d'événements et les fait correspondre aux composants définis. Pour chaque PCR où cela peut être fait de manière exhaustive (c'est-à-dire où tous les enregistrements listés et tous les composants définis ont été fais correspondre), cela peut alors être utilisé pour prédire les mesures futures des PCR, en tenant compte des variantes alternatives définies pour chaque composant. Cette prédiction peut alors être convertie en une politique d'accès TPM2 (composée d'éléments TPM2 PolicyPCR et PolicyOR), qui est ensuite stockée dans un index NV du TPM2. Ceci peut être utilisé pour verrouiller des secrets (tels que des clés de chiffrement de disque) à ces politiques (via une politique TPM2 PolicyAuthorizeNV).

Utilisez des outils tels que systemd-cryptenroll(1) ou systemd-repart(8) pour lier le chiffrement de disque à une telle politique TPM2 systemd-pcrlock. Plus précisément, voir les commutateurs --tpm2-pcrlock= de ces outils.

La logique de politique d'accès nécessite un périphérique TPM2 qui implémente la commande "PolicyAuthorizeNV", c'est-à-dire qu'il implémente TPM 2.0 version 1.38 ou plus récente.

COMMANDES

Les commandes suivantes sont comprises :

log

Ceci lit le journal d'événements TPM2 combiné, le valide, le fait correspondre aux valeurs actuelles des PCR et affiche les deux sous forme tabulaire. Combinez avec --json= pour générer la sortie au format JSON.

Ajouté dans la version 255.

cel

Ceci lit le journal d'événements TPM2 combiné et l'écrit sur STDOUT au Format de journal d'événements canoniques TCG (CEL-JSON)[1].

Ajouté dans la version 255.

list-components

Affiche une liste des définitions de composants et de leurs variantes, c'est-à-dire les fichiers *.pcrlock découverts dans /var/lib/pcrlock.d/, /usr/lib/pcrlock.d/ et les autres répertoires supportés. Voir systemd.pcrlock(5) pour les détails sur ces fichiers et la liste complète des répertoires recherchés.

Ajouté dans la version 255.

predict

Prédit l'état des PCR lors des futurs démarrages. Ceci analysera le journal d'événements TPM2 comme décrit ci-dessus, reconnaîtra les composants, puis générera toutes les valeurs de PCR résultantes possibles pour toutes les combinaisons de variantes de composants. Notez qu'aucune prédiction n'est faite pour les PCR dont la valeur ne correspond pas aux enregistrements du journal d'événements, pour lesquels des mesures non reconnues sont découvertes ou pour lesquels des composants sont définis qui ne peuvent pas être trouvés dans le journal d'événements. Il s'agit d'une mesure de sécurité pour garantir que toute politique d'accès générée puisse être remplie correctement lors des démarrages actuels et futurs.

Ajouté dans la version 255.

make-policy

Ceci prédit l'état des PCR pour les futurs démarrages, tout comme la commande predict ci-dessus. Il utilise ensuite ces données pour générer une politique d'accès TPM2 qu'il stocke dans un index NV de TPM2. La prédiction et les informations sur le TPM2 utilisé et son index NV sont écrites dans /var/lib/systemd/pcrlock.json.

L'index NV est alloué lors de la première invocation et mis à jour lors des invocations ultérieures.

Le contenu de l'index NV peut être modifié (et donc la politique qui y est stockée mise à jour) en fournissant un code d'accès PIN. Ce PIN est normalement généré automatiquement et stocké sous forme chiffrée (avec une politique d'accès le liant à l'index NV lui-même) dans le fichier de politique JSON susmentionné. Ce PIN peut être choisi par l'utilisateur, via le commutateur --recovery-pin=. S'il est spécifié, il peut être utilisé comme chemin d'accès alternatif pour mettre à jour la politique.

Si la nouvelle prédiction correspond à l'ancienne, cette commande se termine rapidement et n'exécute aucune autre opération. (Sauf si --force est spécifié, voir ci-dessous.)

À partir de la v256, une copie du fichier de politique /var/lib/systemd/pcrlock.json est encodée dans un identifiant (voir systemd-creds(1) pour les détails) et écrite sur la partition EFI System ou la partition XBOOTLDR, dans le sous-répertoire /loader/credentials/. Là, elle est récupérée au démarrage par systemd-stub(7) et passée à l'initrd invoqué, où elle peut être utilisée pour déverrouiller le système de fichiers racine (qui contient typiquement /var/, qui est où se trouve la copie principale de la politique, qui ne peut donc pas être utilisée pour déverrouiller le système de fichiers racine). Le fichier d'identifiant est nommé d'après le jeton d'entrée de démarrage de l'installation (voir bootctl(1)), qui est configurable via le commutateur --entry-token=, voir ci-dessous.

Ajouté dans la version 255.

remove-policy

Supprime une politique précédemment générée. Supprime le fichier /var/lib/systemd/pcrlock.json et désalloue l'index NV.

Ajouté dans la version 255.

is-supported

Vérifie si le TPM2 local prend en charge toutes les fonctionnalités pour que systemd-pcrlock fonctionne correctement. Ceci effectue des tests similaires à systemd-analyze has-tpm2, mais vérifie également la prise en charge des opérations TPM2 requises par systemd-pcrlock. Affiche "no", "partial" (si certaines parties de la prise en charge TPM2 sont disponibles dans le matériel, le firmware, l'OS, mais pas complet), "obsolete" (si la prise en charge TPM2 est disponible dans le matériel, le firmware et l'OS, mais les opérations requises pour systemd-pcrlock sont manquantes), ou "yes". Retourne un code de sortie de zéro si une prise en charge complète est disponible, sinon un code non nul.

Si combiné avec --quiet, supprime l'affichage de la chaîne.

Actuellement, ceci vérifie la prise en charge de la commande TPM2 PolicyAuthorizeNV, ainsi que la prise en charge de l'algorithme de hachage SHA-256.

Ajouté dans la version 258.

lock-firmware-code, unlock-firmware-code

Génère/supprime des fichiers .pcrlock basés sur le journal d'événements TPM2 du démarrage actuel couvrant tous les enregistrements pour les PCR 0 ("plateforme-code") et 2 ("code-externe").

Cette opération permet de verrouiller le processus de démarrage sur la version actuelle du firmware du système et de ses cartes d'extension. Cette opération ne doit être utilisée que si le fournisseur du système ne fournit pas de données pcrlock appropriées à l'avance.

Notez que ces données ne correspondent qu'à la version actuelle du firmware. Si une mise à jour du firmware est appliquée, ces données seront obsolètes et toute politique d'accès générée à partir d'elles ne sera plus valide. Il est donc recommandé d'invoquer unlock-firmware-code avant de faire une mise à jour du firmware, suivi de make-policy pour actualiser la politique.

systemd-pcrlock lock-firmware-code est automatiquement invoqué au démarrage via l'unité systemd-pcrlock-firmware-code.service, si elle est activée. Cela garantit qu'une politique d'accès gérée par systemd-pcrlock est automatiquement verrouillée sur la nouvelle version du firmware chaque fois que la politique

Les fichiers ne sont générés à partir du journal d'événements que si le journal d'événements correspond à l'état actuel des PCR du TPM2.

Cela écrit/supprime les fichiers /var/lib/pcrlock.d/250-firmware-code-early.pcrlock.d/generated.pcrlock et /var/lib/pcrlock.d/550-firmware-code-late.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-firmware-config, unlock-firmware-config

Ceci est similaire à lock-firmware-code/unlock-firmware-code mais verrouille la configuration du micrologiciel, c'est-à-dire les PCR 1 (« platform-config ») et 3 (« external-config »).

Cette fonctionnalité doit être utilisée avec précaution car, dans la plupart des scénarios, une modification mineure de la configuration du micrologiciel ne devrait pas invalider les politiques d'accès aux objets TPM2. Notez également que certains systèmes mesurent des informations instables et imprévisibles (par exemple, les tensions actuelles du CPU, les températures, dans le cadre des données SMBIOS) pour ces PCR, ce qui signifie que cette forme de verrouillage ne peut pas être utilisée de manière fiable sur de tels systèmes. Utilisez cette fonctionnalité uniquement si le système et le matériel sont bien connus et ne souffrent pas de ces limitations, par exemple dans les environnements virtualisés.

Utilisez unlock-firmware-config avant d'apporter des modifications à la configuration du micrologiciel. Si l'unité systemd-pcrlock-firmware-config.service est activée, elle générera automatiquement un fichier pcrlock à partir des nouvelles mesures.

Cela écrit/supprime les fichiers /var/lib/pcrlock.d/250-firmware-config-early.pcrlock.d/generated.pcrlock et /var/lib/pcrlock.d/550-firmware-config-late.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-secureboot-policy, unlock-secureboot-policy

Génère/supprime un fichier .pcrlock basé sur la politique SecureBoot actuellement appliquée. Cela examine les variables EFI SecureBoot, PK, KEK, db, dbx, dbt, dbr et prédit leurs mesures dans la PCR 7 (« secure-boot-policy ») au prochain démarrage.

Utilisez unlock-firmware-config avant d'appliquer les mises à jour de la politique SecureBoot. Si l'unité systemd-pcrlock-secureboot-policy.service est activée, elle générera automatiquement un fichier pcrlock à partir de la politique découverte.

Cela écrit/supprime le fichier /var/lib/pcrlock.d/230-secureboot-policy.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-secureboot-authority, unlock-secureboot-authority

Génère/supprime un fichier .pcrlock basé sur les autorités SecureBoot utilisées pour valider le chemin de démarrage. Les autorités SecureBoot sont les entrées spécifiques de la base de données SecureBoot qui ont été utilisées pour valider les binaires PE UEFI exécutés au démarrage. Cela examine le journal d'événements du démarrage actuel et utilise les mesures pertinentes sur la PCR 7 (« secure-boot-policy »).

Cela écrit/supprime le fichier /var/lib/pcrlock.d/620-secureboot-authority.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-gpt [DEVICE], unlock-gpt

Génère/supprime un fichier .pcrlock basé sur la table de partition GPT du disque spécifié. Si aucun disque n'est spécifié, détermine automatiquement le périphérique bloc qui supporte le système de fichiers racine. Cela verrouille l'état du partitionnement du disque du support amorcé, que le micrologiciel mesure dans la PCR 5 (« boot-loader-config »).

Cela écrit/supprime le fichier /var/lib/pcrlock.d/600-gpt.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-pe [BINARY], unlock-pe

Génère/supprime un fichier .pcrlock basé sur le binaire PE spécifié. Ceci est utile pour prédire les mesures que le micrologiciel effectue dans la PCR 4 (« boot-loader-code ») si le binaire spécifié fait partie du processus de démarrage UEFI. Utilisez ceci sur les binaires de chargeur de démarrage et similaires. Utilisez lock-uki (voir ci-dessous) pour les binaires PE qui sont des images de noyau unifiées (UKI).

Attend un chemin vers le binaire PE comme argument. S'il n'est pas spécifié, lit le binaire depuis STDIN à la place.

Le fichier pcrlock à écrire doit être spécifié via le commutateur --pcrlock=.

Ajouté dans la version 255.

lock-uki [UKI], unlock-uki

Génère/supprime un fichier .pcrlock basé sur le binaire PE UKI spécifié. Ceci est utile pour prédire les mesures que le micrologiciel effectue dans la PCR 4 (« boot-loader-code »), et que systemd-stub(7) effectue dans la PCR 11 (« kernel-boot »), si l'UKI spécifié est démarré. Ceci est un sur-ensemble de lock-pe.

Attend un chemin vers le binaire PE UKI comme argument. S'il n'est pas spécifié, lit le binaire depuis STDIN à la place.

Le fichier pcrlock à écrire doit être spécifié via le commutateur --pcrlock=.

Ajouté dans la version 255.

lock-machine-id, unlock-machine-id

Génère/supprime un fichier .pcrlock basé sur /etc/machine-id. Ceci est utile pour prédire les mesures que systemd-pcrmachine.service(8) effectue dans la PCR 15 (« system-identity »).

Cela écrit/supprime le fichier /var/lib/pcrlock.d/820-machine-id.pcrlock.

Ajouté dans la version 255.

lock-file-system [PATH], unlock-file-system [PATH]

Génère/supprime un fichier .pcrlock basé sur l'identité du système de fichiers. Ceci est utile pour prédire les mesures que systemd-pcrfs@.service(8) effectue dans la PCR 15 (« system-identity ») pour les systèmes de fichiers racine et /var/.

Cela écrit/supprime les fichiers /var/lib/pcrlock.d/830-root-file-system.pcrlock et /var/lib/pcrlock.d/840-file-system-path.pcrlock.

Ajouté dans la version 255.

lock-kernel-cmdline [FILE], unlock-kernel-cmdline

Génère/supprime un fichier .pcrlock basé sur /proc/cmdline (ou le fichier spécifié si donné). Ceci est utile pour prédire les mesures que le noyau Linux effectue dans la PCR 9 (« kernel-initrd »).

Cela écrit/supprime le fichier /var/lib/pcrlock.d/710-kernel-cmdline.pcrlock/generated.pcrlock.

Ajouté dans la version 255.

lock-kernel-initrd FILE, unlock-kernel-initrd

Génère/supprime un fichier .pcrlock basé sur une archive cpio d'initrd du noyau. Ceci est utile pour prédire les mesures que le noyau Linux effectue dans la PCR 9 (« kernel-initrd »). Ne pas utiliser pour les UKI de systemd-stub(7), car l'initrd est combiné dynamiquement à partir de diverses sources et ne prend donc pas une entrée unique, comme cette commande.

Cela écrit/supprime le fichier /var/lib/pcrlock.d/720-kernel-initrd.pcrlock/generated.pcrlock.

Ajouté dans la version 255.

lock-raw [FILE], unlock-raw

Génère/supprime un fichier .pcrlock basé sur des données binaires brutes. Les données sont lues à partir du fichier spécifié ou de STDIN (si aucun n'est spécifié). Cela nécessite que --pcrs= soit spécifié. Le fichier .pcrlock généré est écrit dans le fichier spécifié via --pcrlock= ou dans STDOUT (si aucun n'est spécifié).

Ajouté dans la version 255.

OPTIONS

Les options suivantes sont comprises :

--raw-description

Lors de l'affichage du journal d'événements TPM2, n'essayez pas de décoder les enregistrements pour fournir une chaîne de description d'événement conviviale. Au lieu de cela, affichez les données de charge utile binaires sous forme échappée.

Ajouté dans la version 255.

--pcr=

Spécifie le numéro de PCR à utiliser. Peut être spécifié plusieurs fois pour sélectionner plusieurs PCR.

Ceci est utilisé par lock-raw et lock-pe pour sélectionner la PCR contre laquelle verrouiller.

Si utilisé avec predict et make-policy, cela remplacera les PCR à inclure dans la prédiction et la politique. Si non spécifié, cela prend par défaut les PCR 0-5, 7, 11-15. Notez que ces commandes n'incluront aucune PCR dans la prédiction/politique (même si spécifiée explicitement) s'il existe des mesures dans le journal d'événements qui ne correspondent pas à la valeur actuelle de la PCR, s'il existe des mesures non reconnues dans le journal d'événements, ou si des composants définissent des mesures non vues dans le journal d'événements.

Ajouté dans la version 255.

--nv-index=

Spécifie l'index NV dans lequel stocker la politique. Respecté par make-policy. Si non spécifié, la commande choisira automatiquement un index NV libre.

Ajouté dans la version 255.

--components=

Prend un chemin pour lire les fichiers *.pcrlock et *.pcrlock.d/*.pcrlock. Peut être utilisé plusieurs fois pour spécifier plusieurs répertoires. S'il n'est pas spécifié, prend par défaut /etc/pcrlock.d/, /run/pcrlock.d/, /var/lib/pcrlock.d/, /usr/local/lib/pcrlock.d/, /usr/lib/pcrlock.d/.

Ajouté dans la version 255.

--location=

Prend soit une chaîne, soit une paire de chaînes séparées par des deux-points. Configure jusqu'à quel point dans la liste triée des composants définis pour analyser/prédire les PCR. Typiquement, l'outil systemd-pcrlock est invoqué à partir d'un système complètement démarré après le démarrage et avant l'arrêt. Cela signifie que divers composants définis pour l'arrêt n'ont pas encore été mesurés et ne doivent pas être recherchés. Cette option permet de restreindre les composants à prendre en compte pour l'analyse (en ne tenant compte que des composants avant un certain point, en ignorant ceux qui suivent). La chaîne attendue est ordonnée par rapport aux noms de fichiers des composants définis. Tous les composants dont le nom est lexicographiquement postérieur sont ignorés. Cette logique s'applique aux verbes log, predict et make-policy. Si une paire de chaînes séparées par des deux-points est spécifiée, elles sélectionnent les phases de démarrage à inclure dans la prédiction/politique. La première chaîne définit où la première prédiction doit être faite, et la deuxième chaîne définit où la dernière prédiction doit être faite. Toutes ces prédictions sont ensuite combinées en un seul ensemble.

Si utilisé avec list-components, la plage de localisation sélectionnée sera mise en évidence dans la liste des composants.

Par défaut, il prend la valeur « 760-:940- », ce qui signifie que les politiques générées par défaut couvriront essentiellement toute la durée de vie de l'espace utilisateur du système d'exploitation, de l'initrd (car « 760- » suit de près 750-enter-initrd.pcrlock) jusqu'au (et y compris le) fonctionnement principal du système (car « 940- » est suivi de près par 950-shutdown.pcrlock). Voir systemd.pcrlock(5) pour une liste complète des composants bien connus, qui illustrent où cette plage est placée par défaut.

Ajouté dans la version 255.

--recovery-pin=

Prend l'une des valeurs « hide », « show » ou « query ». Par défaut, prend « hide ». Respecté par make-policy. Si « query », demandera à l'utilisateur un code PIN pour déverrouiller
systemd-pcrlock-firmware-code.service(8)

NAME

systemd-pcrlock-firmware-code.service, systemd-pcrlock.service, systemd-pcrlock-setup.service - Lock TPM2 NV memory

SYNOPSIS

 /etc/systemd/system/systemd-pcrlock.service
 /etc/systemd/system/systemd-pcrlock-firmware-code.service
 /etc/systemd/system/systemd-pcrlock-setup.service

DESCRIPTION

The TPM2 module systemd-pcrlock.service(8) may be used to lock access to TPM2 NVRAM indexes.

This service is intended to be used in conjunction with PCR measurement and sealing. The idea is to create a policy that is only satisfied if the PCRs have been extended with specific measurements, and then to seal the NV index to that policy. When the system boots, if the PCRs are extended as expected, the NV index may be unsealed, and access granted. Otherwise, the NV index is locked.

This service is not intended to be used directly. Instead, use the systemd-creds(1) utility.

The systemd-pcrlock-firmware-code.service(8) and systemd-pcrlock-setup.service(8) units are helpers that invoke systemd-creds(1) to create the policy and to lock the TPM2 NV index.

COMMANDS

make-policy
Creates a new policy for a TPM2 NV index. If a policy already exists, it will be overwritten. The policy will be stored in the specified policy file. See --policy=.
lock-policy
Locks the NV index associated with the specified policy file. Requires write access to the NV index.
unlock
Unlocks the NV index associated with the specified policy file. Requires write access to the NV index.
show
Prints the policy metadata and the associated PIN for the specified policy file. This command is only useful if a PIN was previously specified when creating the policy.
hide
Creates a policy and locks the NV index associated with it. This command is a shortcut for running make-policy followed by lock-policy with an automatically generated PIN.
is-supported
Checks if the TPM2 NV index locking functionality is supported by the system. Prints "yes" or "no".

OPTIONS

The following options are understood by the commands listed above:

--pin=

PIN to use with the TPM2 NV index. If no policy was created before, this PIN is used to protect the newly allocated NV index. If a policy has been created before, the PIN is used to unlock write access to the NV index. If either "hide" or "show" is used, a PIN is automatically generated, and — only in case of "show" — displayed on screen. Regardless if user supplied or automatically generated, it is stored in encrypted form in the policy metadata file. The recovery PIN may be used to regain write access to an NV index in case the access policy became out of date.

Added in version 255.

--pcrlock=

Takes a file system path as argument. If specified, configures where to write the generated pcrlock data to. Honoured by the various lock-* commands. If not specified, a default path is generally used, as documented above.

Added in version 255.

--policy=

Takes a file system path as argument. If specified, configures where to write pcrlock policy metadata to. If not specified, defaults to /var/lib/systemd/pcrlock.json.

Added in version 255.

--force

If specified with make-policy, the predicted policy will be written to the NV index even if it is detected to be the same as the previously stored one.

Added in version 255.

--entry-token=

Sets the boot entry token to use for the file name for the pcrlock policy credential in the EFI System Partition or XBOOTLDR partition. See the bootctl(1) option of the same regarding expected values. This switch has an effect on the make-policy command only.

Added in version 256.

--quiet

If specified suppresses output when invoked for is-supported.

Added in version 258.

--json=MODE

Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

--no-pager

Do not pipe output into a pager.

-h, --help

Print a short help text and exit.

--version

Print a short version string and exit.

EXIT STATUS

On success, 0 is returned, a non-zero failure code otherwise.
