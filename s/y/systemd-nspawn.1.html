NOM

systemd-nspawn - Lancer une commande ou un système d'exploitation dans un conteneur léger

SYNTAXE

systemd-nspawn [OPTIONS...] [COMMANDE [ARGUMENTS...]]

systemd-nspawn --boot [OPTIONS...] [ARGUMENTS...]

DESCRIPTION

systemd-nspawn peut être utilisé pour lancer une commande ou un système d'exploitation dans un conteneur de type namespace léger. À bien des égards, il est similaire à chroot(1), mais plus puissant car il virtualise la hiérarchie du système de fichiers, ainsi que l'arbre des processus, les divers sous-systèmes IPC, et les noms d'hôte et de domaine.

systemd-nspawn peut être invoqué sur n'importe quelle arborescence de répertoires contenant un système d'exploitation, en utilisant l'option en ligne de commande --directory=. En utilisant l'option --machine=, une arborescence de système d'exploitation est automatiquement recherchée dans quelques emplacements, notamment dans /var/lib/machines/, le répertoire suggéré pour placer les images de conteneurs de système d'exploitation installées sur le système.

Contrairement à chroot(1), systemd-nspawn peut être utilisé pour démarrer des systèmes d'exploitation complets basés sur Linux dans un conteneur.

systemd-nspawn limite l'accès à diverses interfaces du noyau dans le conteneur en lecture seule, telles que /sys/, /proc/sys/, ou /sys/fs/selinux/. Les interfaces réseau de l'hôte et l'horloge système ne peuvent pas être modifiées depuis l'intérieur du conteneur. Les nœuds de périphérique ne peuvent pas être créés. Le système hôte ne peut pas être redémarré et les modules du noyau ne peuvent pas être chargés depuis l'intérieur du conteneur. Ce bac à sable peut être facilement contourné depuis l'intérieur du conteneur si les namespaces utilisateur ne sont pas utilisés. Cela signifie que le code non fiable doit toujours être exécuté dans un namespace utilisateur, voir la discussion sur l'option --private-users= ci-dessous.

Utilisez un outil tel que dnf(8), debootstrap(8), ou pacman(8) pour configurer une arborescence de répertoires de système d'exploitation adaptée comme hiérarchie de système de fichiers pour les conteneurs systemd-nspawn. Voir la section Exemples ci-dessous pour les détails sur l'invocation appropriée de ces commandes.

En tant que vérification de sécurité, systemd-nspawn vérifiera l'existence de /usr/lib/os-release ou /etc/os-release dans l'arborescence du conteneur avant de démarrer un conteneur (voir os-release(5)). Il peut être nécessaire d'ajouter ce fichier à l'arborescence du conteneur manuellement si le système d'exploitation du conteneur est trop ancien pour contenir ce fichier directement.

systemd-nspawn peut être invoqué directement depuis la ligne de commande interactive ou exécuté comme un service système en arrière-plan. Dans ce mode, chaque instance de conteneur s'exécute comme sa propre instance de service ; un fichier d'unité modèle par défaut systemd-nspawn@.service est fourni pour faciliter cela, prenant le nom du conteneur comme identifiant d'instance. Notez que différentes options par défaut s'appliquent lorsque systemd-nspawn est invoqué par le fichier d'unité modèle par rapport à l'invocation interactive en ligne de commande. La plupart des différences importantes sont documentées avec les différentes options prises en charge ci-dessous.

L'outil machinectl(1) peut être utilisé pour exécuter un certain nombre d'opérations sur les conteneurs. En particulier, il fournit des commandes faciles à utiliser pour exécuter des conteneurs en tant que services système en utilisant le fichier d'unité modèle systemd-nspawn@.service.

Parallèlement à chaque conteneur, un fichier de configuration avec le suffixe .nspawn peut exister, contenant des paramètres supplémentaires à appliquer lors de l'exécution du conteneur. Voir systemd.nspawn(5) pour plus de détails. Les fichiers de configuration remplacent les options par défaut utilisées par le fichier d'unité modèle systemd-nspawn@.service, ce qui rend généralement inutile la modification directe de ce fichier modèle.

Notez que systemd-nspawn montera des systèmes de fichiers privés au conteneur vers /dev/, /run/, et similaires. Ceux-ci ne seront pas visibles en dehors du conteneur, et leur contenu sera perdu lorsque le conteneur se terminera.

Notez que l'exécution de deux conteneurs systemd-nspawn à partir de la même arborescence de répertoires ne fera pas en sorte que les processus à l'intérieur se voient. La séparation de namespace des PID des deux conteneurs est complète et les conteneurs partageront très peu d'objets d'exécution, à l'exception du système de fichiers sous-jacent. Utilisez plutôt les commandes login ou shell de machinectl(1) pour demander une session de connexion supplémentaire dans un conteneur en cours d'exécution.

systemd-nspawn implémente la spécification Container Interface[1].

Lors de son exécution, les conteneurs invoqués avec systemd-nspawn sont enregistrés auprès du service systemd-machined(8) qui garde une trace des conteneurs en cours d'exécution et fournit des interfaces de programmation pour interagir avec eux.

FONCTIONNEMENT SANS PRIVILÈGES

systemd-nspawn peut être invoqué avec ou sans privilèges. La fonctionnalité complète n'est actuellement disponible que lorsqu'il est invoqué avec des privilèges. Lorsqu'il est invoqué sans privilèges, diverses limitations s'appliquent, notamment, mais sans s'y limiter :

•Seuls les conteneurs basés sur des images disque sont pris en charge (c'est-à-dire --image=). Ceux basés sur des répertoires (c'est-à-dire --directory=) ne sont pas pris en charge.
•L'enregistrement des machines via --machine= n'est pas pris en charge.
•Seuls les modes réseau --private-network et --network-veth sont pris en charge.

Lors de l'exécution en mode sans privilèges, certaines fonctionnalités nécessaires sont fournies via systemd-mountfsd.service(8) et systemd-nsresourced.service(8).

OPTIONS

Si l'option --boot est spécifiée, les arguments sont utilisés comme arguments pour le programme init. Sinon, COMMANDE spécifie le programme à lancer dans le conteneur, et les arguments restants sont utilisés comme arguments pour ce programme. Si --boot n'est pas utilisé et qu'aucun argument n'est spécifié, un shell est lancé dans le conteneur.

Les options suivantes sont comprises :

-q, --quiet

Désactive toute sortie de statut de l'outil lui-même. Lorsque ce commutateur est utilisé, la seule sortie de nspawn sera la sortie console du système d'exploitation du conteneur lui-même.

Ajouté dans la version 209.

--settings=MODE

Contrôle si systemd-nspawn doit rechercher et utiliser des configurations supplémentaires par conteneur à partir des fichiers .nspawn. Prend une valeur booléenne ou les valeurs spéciales override ou trusted.

Si activé (par défaut), un fichier de configuration nommé d'après la machine (tel que spécifié avec le paramètre --machine=, ou dérivé du nom du répertoire ou du fichier image) avec le suffixe .nspawn est recherché dans /etc/systemd/nspawn/ et /run/systemd/nspawn/. S'il est trouvé là, ses configurations sont lues et utilisées. S'il n'est pas trouvé là, il est ensuite recherché dans le même répertoire que le fichier image ou dans le parent immédiat du répertoire racine du conteneur. Dans ce cas, si le fichier est trouvé, ses configurations seront également lues et utilisées, mais les configurations potentiellement dangereuses seront ignorées. Notez que dans ces deux cas, les configurations de la ligne de commande priment sur les configurations correspondantes des fichiers .nspawn chargés, si les deux sont spécifiées. Les configurations dangereuses incluent toutes les configurations qui élèvent les privilèges du conteneur ou accordent l'accès à des ressources supplémentaires telles que des fichiers ou des répertoires de l'hôte. Pour plus de détails sur le format et le contenu des fichiers .nspawn, consultez systemd.nspawn(5).

Si cette option est définie sur override, le fichier est recherché, lu et utilisé de la même manière, cependant, l'ordre de priorité est inversé : les configurations lues à partir du fichier .nspawn priment sur les options de ligne de commande correspondantes, si les deux sont spécifiées.

Si cette option est définie sur trusted, le fichier est recherché, lu et utilisé de la même manière, mais indépendamment du fait qu'il soit trouvé dans /etc/systemd/nspawn/, /run/systemd/nspawn/ ou à côté du fichier image ou du répertoire racine du conteneur, toutes les configurations prendront effet, cependant, les arguments de ligne de commande priment toujours sur les configurations correspondantes.

Si désactivé, aucun fichier .nspawn n'est lu et aucune configuration, sauf celles de la ligne de commande, n'est en vigueur.

Ajouté dans la version 226.

Options d'image

-D, --directory=

Répertoire à utiliser comme racine du système de fichiers pour le conteneur.

Si ni --directory= ni --image= n'est spécifié, le répertoire est déterminé en recherchant un répertoire portant le même nom que le nom de la machine spécifié avec --machine=. Voir la section « Fichiers et Répertoires » de machinectl(1) pour le chemin de recherche exact.

Au lieu du chemin du répertoire, un répertoire versionné « .v/ » peut être spécifié, voir systemd.v(7) pour les détails.

Si ni --directory=, --image=, ni --machine= ne sont spécifiés, le répertoire courant sera utilisé. Ne peut pas être spécifié avec --image=.

--template=

Répertoire ou sous-volume « btrfs » à utiliser comme modèle pour le répertoire racine du conteneur. Si ceci est spécifié et que le répertoire racine du conteneur (tel que configuré par --directory=) n'existe pas encore, il est créé comme un snapshot « btrfs » (si supporté) ou un répertoire simple (sinon) et peuplé à partir de cet arbre modèle. Idéalement, le chemin du modèle spécifié fait référence à la racine d'un sous-volume « btrfs », auquel cas un simple snapshot copy-on-write est pris, et le peuplement du répertoire racine est instantané. Si le chemin du modèle spécifié ne fait pas référence à la racine d'un sous-volume « btrfs » (ou même à un système de fichiers « btrfs »), l'arbre est copié (bien que potentiellement dans un schéma copy-on-write 'reflink' – si le système de fichiers le supporte), ce qui peut prendre beaucoup plus de temps. Notez que le snapshot pris est de répertoire ou de sous-volume spécifié, y compris tous les sous-répertoires et sous-volumes en dessous, mais excluant tous les sous-montages. Ne peut pas être spécifié avec --image= ou --ephemeral.

Notez que ce commutateur laisse le nom d'hôte, l'ID de machine et tous les autres paramètres qui pourraient identifier l'instance inchangés.

Ajouté dans la version 219.

-x, --ephemeral

Si spécifié, le conteneur est exécuté avec un snapshot temporaire de son système de fichiers qui est supprimé immédiatement lorsque le conteneur se termine. Ne peut pas être spécifié avec --template=.

Notez que ce commutateur laisse le nom d'hôte, l'ID de machine et tous les autres paramètres qui pourraient identifier l'instance inchangés. Veuillez noter que – comme avec --template= – la prise du snapshot temporaire est plus efficace sur les systèmes de fichiers qui supportent nativement les snapshots de sous-volumes ou les 'reflinks' (« btrfs » ou nouveau « xfs ») que sur les systèmes de fichiers plus traditionnels qui ne le font pas (« ext4 »). Notez que le snapshot pris est du répertoire ou sous-volume spécifié, y compris tous les sous-répertoires et sous-volumes en dessous, mais excluant tous les sous-montages.

Avec cette option, aucune modification de l'image du conteneur n'est conservée. Utilisez --volatile= (décrit ci-dessous) pour d'autres mécanismes permettant de restreindre la persistance des images de conteneur pendant l'exécution.

Ajouté dans la version 219.

-i, --image=

Image disque à partir de laquelle monter la racine du système de fichiers pour le conteneur. Prend un chemin vers un fichier régulier ou un nœud de périphérique bloc. Le fichier ou le périphérique bloc doit contenir l'un des éléments suivants :
•Une table de partitions MBR avec une seule partition de type 0x83 marquée comme démarrable.
•Une table de partitions GUID (GPT) avec une seule partition de type 0fc63daf-8483-4772-8e79-3d69d8477de4.
•Une table de partitions GUID (GPT) avec une partition racine marquée qui est montée comme répertoire racine du conteneur. Optionnellement, les images GPT peuvent contenir une partition pour le répertoire personnel (home) et/ou une partition de données serveur qui sont montées aux endroits appropriés dans le conteneur. Toutes ces partitions doivent être identifiées par les types de partition définis par la Spécification des Partitions Découvrables[2].
•Aucune table de partitions, et un seul système de fichiers couvrant toute l'image.

Sur les images GPT, si une partition système EFI (ESP) est découverte, elle est automatiquement montée sur /efi (ou /boot en fallback) si un répertoire portant ce nom existe et est vide.

Les partitions chiffrées avec LUKS sont automatiquement déchiffrées. De plus, sur les images GPT, les partitions de hachage d'intégrité de données dm-verity sont configurées si le hachage racine est spécifié à l'aide de l'option --root-hash=.

Les systèmes de fichiers uniques (c'est-à-dire les systèmes de fichiers sans table de partitions environnante) peuvent être ouverts en utilisant dm-verity si les données d'intégrité sont passées en utilisant les options --root-hash= et --verity-data= (et éventuellement --root-hash-sig=).

Toutes les autres partitions, telles que les partitions étrangères ou les partitions de swap, ne sont pas montées. Ne peut pas être spécifié avec --directory=, --template=.

Au lieu du chemin de l'image, un répertoire versionné « .v/ » peut être spécifié, voir systemd.v(7) pour les détails.

Ajouté dans la version 211.

--image-policy=politique

Prend une chaîne de politique d'image comme argument, conformément à systemd.image-policy(7). La politique est appliquée lors de l'opération sur l'image disque spécifiée via --image=, voir ci-dessus. Si non spécifié, la valeur par défaut est « root=verity+signed+encrypted+unprotected+absent:usr=verity+signed+encrypted+unprotected+absent:home=encrypted+unprotected+absent:srv=encrypted+unprotected+absent:esp=unprotected+absent:xbootldr=unprotected+absent:tmp=encrypted+unprotected+absent:var=encrypted+unprotected+absent », c'est-à-dire que tous les systèmes de fichiers reconnus dans l'image sont utilisés, mais pas la partition de swap.

Ajouté dans la version 254.

--oci-bundle=

Prend le chemin d'un bundle d'exécution OCI à invoquer, tel que spécifié dans la Spécification d'Exécution OCI[3]. Dans ce cas, aucun fichier .nspawn n'est chargé, et le répertoire racine ainsi que divers paramètres sont lus à partir des données JSON du runtime OCI (mais les données passées sur la ligne de commande ont la priorité).

Ajouté dans la version 242.

--read-only

Monte le système de fichiers racine du conteneur (et tous les autres systèmes de fichiers contenus dans l'image du conteneur) en lecture seule. Ceci n'a aucun effet sur les montages supplémentaires effectués avec --bind=, --tmpfs= et des options similaires. Ce mode est implicite si le fichier ou le répertoire de l'image du conteneur est lui-même marqué en lecture seule. Il est également implicite si --volatile= est utilisé. Dans ce cas, l'image du conteneur sur disque est strictement en lecture seule, tandis que les modifications sont autorisées mais conservées en mémoire uniquement de manière non persistante. Pour plus de détails, voir ci-dessous.

--volatile, --volatile=MODE

Démarre le conteneur en mode volatil. Lorsqu'aucun paramètre de mode n'est passé ou lorsque le mode est spécifié comme yes, le mode volatil complet est activé. Cela signifie que le répertoire racine est monté comme une instance « tmpfs » principalement non peuplée, et /usr/ de l'arborescence du système d'exploitation y est monté en lecture seule (le système démarre donc avec une image OS en lecture seule, mais un état et une configuration vierges, toute modification est perdue à l'arrêt). Lorsque le paramètre de mode est spécifié comme state, l'arborescence du système d'exploitation est montée en lecture seule, mais /var/ est monté comme une instance « tmpfs » inscriptible dedans (le système démarre donc avec des ressources et une configuration OS en lecture seule, mais un état vierge, et toute modification de ce dernier est perdue à l'arrêt). Lorsque le paramètre de mode est spécifié comme overlay, le système de fichiers racine en lecture seule est combiné avec une instance tmpfs inscriptible via « overlayfs », de sorte qu'il apparaisse normalement, mais que toute modification soit appliquée uniquement au système de fichiers temporaire et perdue lorsque le conteneur est terminé. Lorsque le paramètre de mode est spécifié comme no (la valeur par défaut), l'intégralité de l'arborescence du système d'exploitation est rendue inscriptible (sauf si --read-only est spécifié, voir ci-dessus).

Notez que si l'un des modes volatils est choisi, son effet est limité au système de fichiers racine (ou à /var/ dans le cas de state), et tous les autres montages placés dans la hiérarchie ne sont pas affectés – qu'ils soient établis automatiquement (par exemple, la partition système EFI qui pourrait être montée sur /efi/ ou /boot/) ou explicitement (par exemple, via une option de ligne de commande supplémentaire telle que --bind=, voir ci-dessous). Cela signifie que, même si --volatile=overlay est utilisé, les modifications apportées à /efi/ ou /boot/ sont interdites si une telle partition existe dans l'image du conteneur en cours d'exploitation, et même si --volatile=state est utilisé, le fichier hypothétique /etc/foobar est potentiellement inscriptible si --bind=/etc/foobar est utilisé pour le monter depuis l'extérieur du répertoire /etc/ du conteneur en lecture seule.

L'option --ephemeral est étroitement liée à ce paramètre et offre un comportement similaire en créant une copie temporaire et éphémère de l'intégralité de l'image système et en l'exécutant. Pour plus de détails, voir ci-dessus.

Les options --tmpfs= et --overlay= fournissent des fonctionnalités similaires, mais uniquement pour des sous-répertoires spécifiques de l'image système. Pour les détails, voir ci-dessous.

Cette option fournit des fonctionnalités similaires pour les conteneurs que le commutateur de ligne de commande du noyau « systemd.volatile= » fournit pour les systèmes hôtes. Voir kernel-command-line(7) pour les détails.

Notez que la définition de cette option sur yes ou state ne fonctionnera correctement qu'avec les systèmes d'exploitation du conteneur qui peuvent démarrer avec uniquement /usr/ monté, et qui sont capables de peupler automatiquement /var/ (et /etc/ dans le cas de « --volatile=yes »). Plus précisément, cela signifie que les systèmes d'exploitation qui suivent la séparation historique de /bin/ et /lib/ (et répertoires associés) de /usr/ (c'est-à-dire où les premiers ne sont pas des liens symboliques vers les derniers) ne sont pas pris en charge par « --volatile=yes » en tant que charge utile du conteneur. L'option overlay ne nécessite aucune préparation particulière dans le système d'exploitation, mais notez que le comportement « overlayfs » diffère des systèmes de fichiers réguliers à plusieurs égards, et donc la compatibilité est limitée.

Ajouté dans la version 216.

--root-hash=

Prend un hachage racine d'intégrité de données (dm-verity) spécifié en hexadécimal. Cette option active les vérifications d'intégrité des données à l'aide de dm-verity, si l'image utilisée contient les données d'intégrité appropriées (voir ci-dessus). Le hachage spécifié doit correspondre au hachage racine des données d'intégrité, et est généralement d'au moins 256 bits (et donc 64 caractères hexadécimaux formatés) de long (dans le cas de SHA256 par exemple). Si cette option n'est pas spécifiée, mais que le fichier image porte l'attribut de fichier étendu « user.verity.roothash » (voir xattr(7)), puis le hachage racine est lu à partir de celui-ci, également sous forme de caractères hexadécimaux formatés. Si l'attribut de fichier étendu n'est pas trouvé (ou n'est pas pris en charge par le système de fichiers sous-jacent), mais qu'un fichier avec le suffixe .roothash est trouvé à côté du fichier image, portant par ailleurs le même nom (sauf si l'image a le suffixe .raw, auquel cas le fichier de hachage racine ne doit pas l'avoir dans son nom), le hachage racine est lu à partir de celui-ci et utilisé automatiquement, également sous forme de caractères hexadécimaux formatés.

Notez que cela configure le hachage racine pour le système de fichiers racine. Les images disque peuvent également contenir des systèmes de fichiers séparés pour la hiérarchie /usr/, qui peuvent également être protégés par Verity. Le hachage racine pour cette protection peut être configuré via l'attribut de fichier étendu "user.verity.usrhash" ou via un fichier .usrhash adjacent à l'image disque, suivant le même format et la même logique que pour le hachage racine du système de fichiers racine décrit ici. Notez qu'il n'y a actuellement pas d'option pour configurer le hachage racine pour le /usr/ depuis la ligne de commande.

Voir également l'option RootHash= dans systemd.exec(5).

Ajouté dans la version 233.

--root-hash-sig=

Prend une signature PKCS7 de l'option --root-hash=. La sémantique est la même que pour l'option RootHashSignature=, voir systemd.exec(5).

Ajouté dans la version 246.

--verity-data=

Prend le chemin d'un fichier d'intégrité des données (dm-verity). Cette option active les vérifications d'intégrité des données à l'aide de dm-verity, si un hachage racine est passé et si l'image utilisée elle-même ne contient pas les données d'intégrité. Les données d'intégrité doivent correspondre au hachage racine. Si cette option n'est pas spécifiée, mais qu'un fichier avec le suffixe .verity est trouvé à côté du fichier image, portant par ailleurs le même nom (sauf si l'image a le suffixe .raw, auquel cas le fichier de données verity ne doit pas l'avoir dans son nom), les données verity sont lues à partir de celui-ci et utilisées automatiquement.

Ajouté dans la version 246.

--pivot-root=

Pivote le répertoire spécifié vers / à l'intérieur du conteneur, et soit démonte l'ancienne racine du conteneur, soit la pivote vers un autre répertoire spécifié. Prend l'une des valeurs suivantes : un argument de chemin – auquel cas le chemin spécifié sera pivoté vers / et l'ancienne racine sera démontée ; ou une paire séparée par des deux-points du nouveau chemin racine et de la destination de pivotement pour l'ancienne racine. Le nouveau chemin racine sera pivoté vers /, et l'ancien / sera pivoté vers l'autre répertoire. Les deux chemins doivent être absolus, et sont résolus dans l'espace de noms du système de fichiers du conteneur.

Ceci est destiné aux conteneurs qui ont plusieurs répertoires bootables ; par exemple, plusieurs déploiements OSTree[4]. Il émule le comportement du chargeur de démarrage et de l'initrd qui sélectionnent normalement quel répertoire monter comme racine et y démarrer le PID 1 du conteneur.

Ajouté dans la version 233.

Options d'exécution

-a, --as-pid2

Invoque le shell ou le programme spécifié comme processus ID (PID) 2 au lieu du PID 1 (init). Par défaut, si ni cette option ni --boot n'est utilisé, le programme sélectionné est exécuté comme processus avec le PID 1, un mode adapté uniquement aux programmes qui sont conscients des sémantiques spéciales que le processus avec le PID 1 a sur UNIX. Par exemple, il doit récupérer tous les processus qui lui sont réparentés, et doit implémenter la gestion des signaux compatible sysvinit (spécifiquement : il doit redémarrer sur SIGINT, se réexécuter sur SIGTERM, recharger la configuration sur SIGHUP, etc.). Avec --as-pid2, un stub minimal d'init est exécuté comme PID 1 et le programme sélectionné est exécuté comme PID 2 (et n'a donc pas besoin d'implémenter de sémantiques spéciales). Le stub init récupérera les processus si nécessaire et réagira de manière appropriée aux signaux. Il est recommandé d'utiliser ce mode pour invoquer des commandes arbitraires dans des conteneurs, sauf s'ils ont été modifiés pour s'exécuter correctement en tant que PID 1. Ou en d'autres termes : ce commutateur devrait être utilisé pour pratiquement toutes les commandes, sauf lorsque la commande fait référence à une implémentation d'init ou de shell, car celles-ci sont généralement capables de s'exécuter correctement en tant que PID 1. Cette option ne peut pas être combinée avec --boot.

Ajouté dans la version 229.

-b, --boot

--suppress-sync=

Attend un argument booléen. S'il est vrai, désactive toute forme de synchronisation du système de fichiers sur disque pour la charge utile du conteneur. Cela signifie que tous les appels système tels que sync(2), fsync(), syncfs(), ... n'effectueront aucune opération, et les drapeaux O_SYNC/O_DSYNC lors de open(2) et des appels associés seront rendus indisponibles. C'est potentiellement dangereux, car les garanties d'intégrité des données supposées pour la charge utile du conteneur ne sont pas réellement appliquées (c'est-à-dire que les données supposées avoir été écrites sur disque pourraient être perdues si le système est arrêté de manière anormale). Cependant, cela peut améliorer considérablement les performances d'exécution du conteneur – tant que ces garanties ne sont pas requises ou souhaitables, par exemple parce que toutes les données écrites par le conteneur sont de nature temporaire, redondante, ou juste un artefact intermédiaire qui sera traité ultérieurement et finalisé par une étape ultérieure d'un pipeline. Par défaut, c'est faux.

Options de namespacing utilisateur

--private-users=

Contrôle le namespacing utilisateur. S'il est activé, le conteneur s'exécutera avec son propre ensemble privé d'identifiants d'utilisateur et de groupe UNIX (UID et GID). Cela implique la traduction des UID/GID privés utilisés dans le conteneur (à partir de l'utilisateur root du conteneur 0 et au-delà) vers une plage d'UID/GID sur l'hôte qui ne sont pas utilisés pour d'autres usages (généralement dans la plage au-delà de l'UID/GID 65536 de l'hôte). Le paramètre peut être spécifié comme suit :
1.Si un ou deux nombres séparés par des deux-points sont spécifiés, le namespacing utilisateur est activé. Le premier paramètre spécifie le premier UID/GID hôte à attribuer au conteneur, le second paramètre spécifie le nombre d'UID/GID hôtes à attribuer au conteneur. Si le second paramètre est omis, 65536 UID/GID sont attribués.
2.Si le paramètre est "yes", le namespacing utilisateur est activé. La plage d'UID/GID à utiliser est déterminée automatiquement à partir de la propriété des fichiers du répertoire racine de l'arbre de répertoires du conteneur. Pour utiliser cette option, assurez-vous de préparer l'arbre de répertoires à l'avance et assurez-vous que tous les fichiers et répertoires qu'il contient appartiennent à des UID/GID dans la plage que vous souhaitez utiliser. Assurez-vous également que les ACL de fichiers utilisés référencent exclusivement des UID/GID dans la plage appropriée. Dans ce mode, le nombre d'UID/GID attribués au conteneur est de 65536, et l'UID/GID propriétaire du répertoire racine doit être un multiple de 65536.
3.La valeur spéciale "pick" active le namespacing utilisateur. Dans ce cas, la plage d'UID/GID est choisie automatiquement. Comme première étape, l'UID/GID du propriétaire du fichier du répertoire racine de l'arbre de répertoires du conteneur est lu, et il est vérifié qu'aucun autre conteneur ne l'utilise actuellement. Si cette vérification est réussie, la plage d'UID/GID déterminée de cette manière est utilisée, de manière similaire au comportement si "yes" est spécifié. Si la vérification n'est pas réussie (et donc la plage d'UID/GID indiquée dans le propriétaire du fichier du répertoire racine est déjà utilisée ailleurs), une nouvelle plage d'UID/GID de 65536 UID/GID (actuellement inutilisée) est choisie aléatoirement entre les UID/GID hôtes 524288 et 1878982656, commençant toujours à un multiple de 65536, et, si possible, hachée de manière cohérente à partir du nom de la machine. Ce paramètre implique --private-users-ownership=auto (voir ci-dessous), ce qui a potentiellement pour effet que les fichiers et répertoires de l'arbre de répertoires du conteneur appartiennent aux utilisateurs appropriés de la plage choisie. L'utilisation de cette option rend le comportement du namespace utilisateur entièrement automatique. Notez que la première invocation d'une image de conteneur auparavant inutilisée peut entraîner le choix d'une nouvelle plage d'UID/GID pour celle-ci, et donc l'opération (potentiellement coûteuse) d'ajustement de la propriété des fichiers. Cependant, les invocations ultérieures du conteneur seront peu coûteuses (sauf si, bien sûr, la plage d'UID/GID choisie est attribuée à une autre utilisation).
4.Si le paramètre est "no", le namespacing utilisateur est désactivé. C'est le comportement par défaut lorsque systemd-nspawn est invoqué directement. (Notez que l'unité systemd-nspawn@.service active les utilisateurs privés.) Cette option n'est pas sécurisée et ne doit pas être utilisée pour exécuter du code non fiable.
5.Si le paramètre est "identity", le namespacing utilisateur est utilisé avec une correspondance d'identité pour les 65536 premiers UID/GID. Ceci est principalement équivalent à --private-users=0:65536. Bien qu'il ne fournisse pas d'isolation des UID/GID, puisque tous les UID/GID hôtes et conteneurs sont choisis identiquement, il fournit une isolation des capacités de processus, mais peut être utile si un namespacing utilisateur approprié avec des maps d'UID distinctes n'est pas possible. Cette option n'est pas sécurisée et ne doit pas être utilisée pour exécuter du code non fiable.
6.Si le paramètre est "managed", le namespacing utilisateur est utilisé en mode *géré*, c'est-à-dire que l'allocation d'une plage d'UID est déléguée à systemd-nsresourced.service(8). Ce mode est sélectionné par défaut lorsqu'il est invoqué sans privilèges, mais peut aussi être demandé explicitement lorsqu'il est privilégié. Dans ce mode, une plage d'UID de 64K est automatiquement choisie.

Il est recommandé d'attribuer au moins 65536 UID/GID à chaque conteneur, afin que la plage d'UID/GID utilisable dans le conteneur couvre 16 bits. Pour une sécurité optimale, n'attribuez pas de plages d'UID/GID chevauchantes à plusieurs conteneurs. Il est donc judicieux d'utiliser les 16 bits supérieurs des UID/GID 32 bits de l'hôte comme identifiant du conteneur, tandis que les 16 bits inférieurs encodent l'UID/GID du conteneur utilisé. C'est en fait le comportement imposé par l'option --private-users=pick.

Lorsque des namespaces utilisateur sont utilisés, la plage GID attribuée à chaque conteneur est toujours choisie identique à la plage UID.

Dans la plupart des cas, --private-users=managed (ou lorsqu'il est privilégié, --private-users=pick aussi) est l'option recommandée car le namespacing utilisateur est conseillé pour la sécurité, et cette option améliore massivement la sécurité des conteneurs tout en fonctionnant de manière entièrement automatique dans la plupart des cas.

Notez que la plage UID/GID choisie n'est pas écrite dans /etc/passwd ou /etc/group. En fait, l'allocation de la plage n'est pas stockée de manière persistante, sauf éventuellement dans la propriété des fichiers de l'arbre de répertoires du conteneur, voir --private-users-ownership=.

Notez que lorsque le namespacing utilisateur est utilisé sans traduction UID (voir ci-dessous), la propriété des fichiers sur le disque reflète cela, et tous les fichiers et répertoires du conteneur appartiennent aux identifiants utilisateur et groupe effectifs du conteneur. Cela signifie que la copie de fichiers depuis et vers l'image du conteneur nécessite la correction des valeurs numériques d'UID/GID, conformément au décalage d'UID/GID appliqué.

Notez que pour un fonctionnement entièrement sans privilèges en mode "managed", toute image de répertoire doit appartenir à la plage d'UID étrangère.

Ajouté dans la version 220.

--private-users-ownership=

Contrôle comment ajuster les UID et GID de l'image du conteneur pour correspondre à la plage UID/GID choisie avec --private-users=, voir ci-dessus. Prend l'une des valeurs suivantes : "off" (pour laisser l'image telle quelle), "chown" (pour récursivement chown() l'arbre de répertoires du conteneur selon les besoins), "map" (pour utiliser des montages de traduction d'ID transparents de l'UID 0 à la plage d'UID cible), "foreign" (la même chose, mais à partir de la base de la plage d'UID étrangère) ou "auto" pour utiliser automatiquement "map" ou "foreign", lorsqu'ils sont disponibles et applicables, et "chown" sinon.

Si "chown" est sélectionné, tous les fichiers et répertoires de l'arbre de répertoires du conteneur seront ajustés de sorte qu'ils appartiennent aux UID/GID appropriés sélectionnés pour le conteneur (voir ci-dessus). Cette opération est potentiellement coûteuse, car elle implique de parcourir l'arborescence complète du répertoire du conteneur. Outre la propriété réelle des fichiers, les ACL de fichiers sont également ajustées.

Généralement, "foreign" ou "map" est le meilleur choix, car il traduit de manière transparente les UID/GID en mémoire selon les besoins sans modifier l'image, et sans nécessiter une opération coûteuse d'ajustement récursif. Cependant, ce n'est pas disponible pour tous les systèmes de fichiers actuellement.

L'option --private-users-ownership=auto est implicite si --private-users=pick est utilisée. Cette option n'a aucun effet si le namespacing utilisateur n'est pas utilisé.

Le commutateur --shift de systemd-dissect(1) peut être utilisé pour décaler la propriété UID/GID à partir de ou vers 0, la base d'UID/GID étrangère ou spécifique au conteneur, en dehors de toute invocation de systemd-nspawn.

Ajouté dans la version 230.

-U

Si le noyau prend en charge la fonctionnalité de namespaces utilisateur, équivalent à --private-users=pick --private-users-ownership=auto, sinon équivalent à --private-users=no.

Notez que -U est le comportement par défaut si le fichier d'unité modèle systemd-nspawn@.service est utilisé.

Note : il est possible d'annuler l'effet de --private-users-ownership=chown (ou -U) sur le système de fichiers en refaisant l'opération avec le premier UID de 0 :

systemd-nspawn ... --private-users=0 --private-users-ownership=chown

Options Réseau

--private-network

Déconnecte le réseau du conteneur de l'hôte. Cela rend toutes les interfaces réseau indisponibles dans le conteneur, à l'exception du périphérique de bouclage et de ceux spécifiés avec --network-interface= et configurés avec --network-veth. Si cette option est spécifiée, la capacité CAP_NET_ADMIN sera ajoutée à l'ensemble des capacités que le conteneur conserve. Cette dernière peut être désactivée en utilisant --drop-capability=. Si cette option n'est pas spécifiée (ou implicite par l'une des options listées ci-dessous), le conteneur aura un accès complet au réseau de l'hôte.

--network-interface=

Attribue l'interface réseau spécifiée au conteneur. Prend soit un nom d'interface unique, faisant référence au nom sur l'hôte, soit une paire d'interfaces séparées par des deux-points, auquel cas la première fait référence au nom sur l'hôte et la seconde au nom dans le conteneur. Lorsque le conteneur se termine, l'interface est déplacée vers l'espace de noms appelant et renommée avec son nom d'origine. Notez que --network-interface= implique --private-network. Cette option peut être utilisée plusieurs fois pour ajouter plusieurs interfaces réseau au conteneur.

Notez que toute interface réseau spécifiée de cette manière doit déjà exister au moment où le conteneur démarre. Si le conteneur doit démarrer automatiquement au démarrage via une instance de fichier d'unité systemd-nspawn@.service, il peut donc être judicieux d'ajouter un drop-in de fichier d'unité à l'instance de service (par exemple, /etc/systemd/system/systemd-nspawn@foobar.service.d/50-network.conf) avec un contenu comme suit :

[Unit]
Wants=sys-subsystem-net-devices-ens1.device
After=sys-subsystem-net-devices-ens1.device

Cela garantira que l'activation du service du conteneur sera retardée jusqu'à ce que l'interface réseau "ens1" apparaisse. Ceci est requis car la sonde matérielle est entièrement asynchrone et les interfaces réseau peuvent être découvertes plus tard pendant le processus de démarrage, après que le conteneur aurait normalement été démarré sans ces dépendances explicites.

Ajouté dans la version 209.

--network-macvlan=

Crée une interface "macvlan" de l'interface réseau Ethernet spécifiée et l'ajoute au conteneur. Prend soit un nom d'interface unique, faisant référence au nom sur l'hôte, soit une paire d'interfaces séparées par des deux-points, auquel cas la première fait référence au nom sur l'hôte et la seconde au nom dans le conteneur. Une interface "macvlan" est une interface virtuelle qui ajoute une deuxième adresse MAC à un lien Ethernet physique existant. Si le nom de l'interface du conteneur n'est pas défini, l'interface dans le conteneur sera nommée d'après l'interface sur l'hôte, préfixée par "mv-". Notez que --network-macvlan= implique --private-network. Cette option peut être utilisée plusieurs fois pour ajouter plusieurs interfaces réseau au conteneur.

Comme avec --network-interface=, l'interface réseau Ethernet sous-jacente doit déjà exister au moment où le conteneur démarre, et donc des drop-ins de fichiers d'unité similaires à ceux décrits ci-dessus pourraient être utiles.

Ajouté dans la version 211.

--network-ipvlan=

Crée une interface "ipvlan" de l'interface réseau Ethernet spécifiée et l'ajoute au conteneur. Prend soit un nom d'interface unique, faisant référence au nom sur l'hôte, soit une paire d'interfaces séparées par des deux-points, auquel cas la première fait référence au nom sur l'hôte et la seconde au nom dans le conteneur. Une interface "ipvlan" est une interface virtuelle, similaire à une interface "macvlan", qui utilise la même adresse MAC que l'interface sous-jacente. Si le nom de l'interface du conteneur n'est pas défini, l'interface dans le conteneur sera nommée d'après l'interface sur l'hôte, préfixée par "iv-". Notez que --network-ipvlan= implique --private-network. Cette option peut être utilisée plusieurs fois pour ajouter plusieurs interfaces réseau au conteneur.

Comme avec --network-interface=, l'interface réseau Ethernet sous-jacente doit déjà exister au moment où le conteneur démarre, et donc des drop-ins de fichiers d'unité similaires à ceux décrits ci-dessus pourraient être utiles.

Ajouté dans la version 219.

-n, --network-veth

Crée un lien Ethernet virtuel ("veth") entre l'hôte et le conteneur. Le côté hôte du lien Ethernet sera disponible sous le nom d'une interface réseau nommée d'après le nom du conteneur (tel que spécifié avec --machine=), préfixé par "ve-". Le côté conteneur du lien Ethernet sera nommé "host0". L'option --network-veth implique --private-network.

Notez que systemd-networkd.service(8) inclut par défaut un fichier réseau /usr/lib/systemd/network/80-container-ve.network correspondant aux interfaces côté hôte créées de cette manière, qui contient des paramètres pour activer l'approvisionnement automatique d'adresses sur le lien virtuel via DHCP, ainsi que le routage IP automatique vers les interfaces réseau externes de l'hôte. Il contient également /usr/lib/systemd/network/80-container-host0.network correspondant à l'interface côté conteneur créée de cette manière, contenant des paramètres pour activer l'assignation d'adresses côté client via DHCP. Si systemd-networkd fonctionne à la fois sur l'hôte et à l'intérieur du conteneur, la communication IP automatique du conteneur vers l'hôte est ainsi disponible, avec une connectivité supplémentaire vers le réseau externe.

Notez que --network-veth est l'option par défaut si le fichier d'unité modèle systemd-nspawn@.service est utilisé.

Notez que sous Linux, les noms d'interfaces réseau peuvent avoir une longueur maximale de 15 caractères, tandis que les noms de conteneurs peuvent avoir une longueur allant jusqu'à 64 caractères. Comme cette option dérive le nom de l'interface côté hôte du nom du conteneur, le nom est potentiellement tronqué. Par conséquent, il faut veiller à ce que les noms d'interface restent uniques dans ce cas, ou mieux encore, que les noms de conteneurs ne soient généralement pas choisis plus longs que 12 caractères pour éviter la troncature. Si le nom est tronqué, systemd-nspawn ajoutera automatiquement une valeur de hachage à 4 chiffres au nom pour réduire le risque de collisions. Cependant, l'algorithme de hachage n'est pas sans collision. (Voir systemd.net-naming-scheme(7) pour les détails sur les anciens algorithmes de nommage pour cette interface). Alternativement, l'option --network-veth-extra= peut être utilisée, ce qui permet une configuration libre du nom de l'interface côté hôte indépendamment du nom du conteneur — mais peut nécessiter un peu plus de configuration supplémentaire si un pontage similaire à --network-bridge= est souhaité.

Ajouté dans la version 209.

--network-veth-extra=

Ajoute un lien Ethernet virtuel supplémentaire entre l'hôte et le conteneur. Prend une paire nom d'interface hôte et nom d'interface conteneur séparée par des deux-points. Ce dernier peut être omis, auquel cas les côtés conteneur et hôte recevront le même nom. Ce commutateur est indépendant de --network-veth et — contrairement à celui-ci — peut être utilisé plusieurs fois, et permet la configuration des noms d'interfaces réseau. Notez que --network-bridge= n'a aucun effet sur les interfaces créées avec --network-veth-extra=.

Ajouté dans la version 228.

--network-bridge=

Ajoute le côté hôte du lien Ethernet créé avec --network-veth à l'interface de pont Ethernet spécifiée. Attend un nom d'interface réseau valide d'un périphérique de pont comme argument. Notez que --network-bridge= implique --network-veth. Si cette option est utilisée, le côté hôte du lien Ethernet utilisera le préfixe "vb-" au lieu de "ve-". Indépendamment du préfixe de nommage utilisé, les mêmes limites de longueur de nom d'interface réseau imposées par Linux s'appliquent, avec les complications que cela crée (voir ci-dessus pour les détails).

Comme avec --network-interface=, l'interface réseau de pont sous-jacente doit déjà exister au moment où le conteneur démarre, et donc des drop-ins de fichiers d'unité similaires à ceux décrits ci-dessus pourraient être utiles.

Ajouté dans la version 209.

--network-zone=

Crée un lien Ethernet virtuel ("veth") vers le conteneur et l'ajoute à une interface de pont Ethernet gérée automatiquement. L'interface de pont est nommée d'après l'argument passé, préfixée par "vz-". L'interface de pont est créée automatiquement lorsque le premier conteneur configuré pour son nom démarre, et est automatiquement supprimée lorsque le dernier conteneur configuré pour son nom se termine. Par conséquent, chaque interface de pont configurée de cette manière n'existe que tant qu'au moins un conteneur la référençant est en cours d'exécution. Cette option est très similaire à --network-bridge=, à l'exception de cette création/suppression automatique du périphérique de pont.

Ce réglage facilite le placement de plusieurs conteneurs liés dans un domaine de diffusion commun basé sur Ethernet virtuel, ici appelé une "zone". Chaque conteneur ne peut faire partie que d'une seule zone, mais chaque zone peut contenir n'importe quel nombre de conteneurs. Chaque zone est référencée par son nom. Les noms peuvent être choisis librement (tant qu'ils forment des noms d'interface réseau valides lorsqu'ils sont préfixés par "vz-"), et il suffit de passer le même nom à l'interrupteur --network-zone= des différents conteneurs s'exécutant simultanément pour les joindre dans une même zone.

Notez que systemd-networkd.service(8) inclut par défaut un fichier réseau /usr/lib/systemd/network/80-container-vz.network correspondant aux interfaces de pont créées de cette manière, qui contient des paramètres pour activer l'approvisionnement automatique d'adresses sur le réseau virtuel créé via DHCP, ainsi que le routage IP automatique vers les interfaces réseau externes de l'hôte. L'utilisation de --network-zone= est donc dans la plupart des cas entièrement automatique et suffisante pour connecter plusieurs conteneurs locaux dans un domaine de diffusion commun à l'hôte, avec une connectivité supplémentaire vers le réseau externe.

Ajouté dans la version 230.

--network-namespace-path=

Prend le chemin vers un fichier représentant un espace de noms réseau du noyau dans lequel le conteneur doit s'exécuter. Le chemin spécifié doit faire référence à un fichier d'espace de noms réseau (éventuellement monté par liaison), tel qu'exposé par le noyau sous /proc/$PID/ns/net. Cela fait entrer le conteneur dans l'espace de noms réseau donné. L'un des cas d'utilisation typiques est de donner un espace de noms réseau sous /run/netns créé par ip-netns(8), par exemple, --network-namespace-path=/run/netns/foo. Notez que cette option ne peut pas être utilisée avec d'autres options liées au réseau, telles que --private-network ou --network-interface=.

Options de ressources

--rlimit=

Définit la limite de ressources POSIX spécifiée pour la charge utile du conteneur. Attend une assignation de la forme « LIMIT=SOFT:HARD » ou « LIMIT=VALUE », où LIMIT doit faire référence à un type de limite de ressources, tel que RLIMIT_NOFILE ou RLIMIT_NICE. Les champs SOFT et HARD doivent faire référence aux valeurs numériques des limites de ressources douces et dures. Si la deuxième forme est utilisée, VALUE peut spécifier une valeur utilisée à la fois comme limite douce et dure. À la place d'une valeur numérique, la chaîne spéciale « infinity » peut être utilisée pour désactiver la limitation des ressources pour le type de ressource spécifique. Cette option de ligne de commande peut être utilisée plusieurs fois pour contrôler les limites sur plusieurs types de limites. Si elle est utilisée plusieurs fois pour le même type de limite, la dernière utilisation l'emporte. Pour plus de détails sur les limites de ressources, voir setrlimit(2). Par défaut, les limites de ressources pour le processus d'initialisation du conteneur (PID 1) sont définies aux mêmes valeurs que le noyau Linux a initialement transmises au système d'initialisation de l'hôte. Notez que certaines limites de ressources sont appliquées aux ressources comptées par utilisateur, en particulier RLIMIT_NPROC. Cela signifie que, sauf si l'espace de noms d'utilisateur est déployé (c'est-à-dire si --private-users= est utilisé, voir ci-dessus), toutes les limites définies seront appliquées à l'utilisation des ressources du même utilisateur sur tous les conteneurs locaux ainsi que sur l'hôte. Cela signifie qu'une attention particulière doit être accordée à ces limites car elles pourraient être déclenchées par du code potentiellement moins fiable. Exemple : « --rlimit=RLIMIT_NOFILE=8192:16384 ».

Prend un entier dans la plage -1000...1000.

Options d'intégration

--resolv-conf=

Configure comment /etc/resolv.conf à l'intérieur du conteneur doit être géré (c'est-à-dire synchronisation de la configuration DNS de l'hôte vers le conteneur). Prend l'une des valeurs suivantes : « off », « copy-host », « copy-static », « copy-uplink », « copy-stub », « replace-host », « replace-static », « replace-uplink », « replace-stub », « bind-host », « bind-static », « bind-uplink », « bind-stub », « delete » ou « auto ».

Si défini sur « off », le fichier /etc/resolv.conf dans le conteneur est laissé tel qu'il est inclus dans l'image, et n'est ni modifié ni monté par liaison.

Si défini sur « copy-host », le fichier /etc/resolv.conf de l'hôte est copié dans le conteneur, sauf si le fichier existe déjà et n'est pas un fichier régulier (par exemple, un lien symbolique). De même, si « replace-host » est utilisé, le fichier est copié, remplaçant tout inode existant, y compris les liens symboliques. De même, si « bind-host » est utilisé, le fichier est monté par liaison de l'hôte dans le conteneur.

Si défini sur « copy-static », « replace-static » ou « bind-static », le fichier resolv.conf statique fourni avec systemd-resolved.service(8) (spécifiquement : /usr/lib/systemd/resolv.conf) est copié ou monté par liaison dans le conteneur.

Si défini sur « copy-uplink », « replace-uplink » ou « bind-uplink », le fichier resolv.conf de liaison géré par systemd-resolved.service (spécifiquement : /run/systemd/resolve/resolv.conf) est copié ou monté par liaison dans le conteneur.

Si défini sur « copy-stub », « replace-stub » ou « bind-stub », le fichier resolv.conf de stub géré par systemd-resolved.service (spécifiquement : /run/systemd/resolve/stub-resolv.conf) est copié ou monté par liaison dans le conteneur.

Si défini sur « delete », le fichier /etc/resolv.conf dans le conteneur est supprimé s'il existe.

Enfin, si défini sur « auto », le fichier est laissé tel quel si le réseau privé est activé (voir --private-network). Sinon, si systemd-resolved.service est en cours d'exécution, son fichier resolv.conf de stub est utilisé, et sinon, le fichier /etc/resolv.conf de l'hôte. Dans ces derniers cas, le fichier est copié si l'image est inscriptible, et monté par liaison sinon.

Il est recommandé d'utiliser « copy-... » ou « replace-... » si le conteneur doit être capable d'apporter des modifications à la configuration DNS par lui-même, en s'écartant des paramètres de l'hôte. Sinon, « bind » est préférable, car cela signifie que les modifications directes apportées à /etc/resolv.conf dans le conteneur ne sont pas autorisées, car il s'agit d'un montage par liaison en lecture seule (mais notez que si le conteneur dispose de privilèges suffisants, il pourrait simplement démonter le montage par liaison de toute façon). Notez que si le fichier est monté par liaison et s'il est copié, aucune propagation supplémentaire

de configuration est généralement effectuée après l'initialisation précoce unique (car le fichier est généralement mis à jour par copie et renommage). Par défaut : "auto".

Ajouté dans la version 239.

--timezone=

Configure comment le fichier /etc/localtime à l'intérieur du conteneur (c'est-à-dire la synchronisation de fuseau horaire local de l'hôte vers le conteneur) doit être gérée. Accepte l'une des valeurs suivantes : "off", "copy", "bind", "symlink", "delete" ou "auto". Si défini sur "off", le fichier /etc/localtime dans le conteneur est laissé tel quel dans l'image, et n'est ni modifié ni monté par liaison. Si défini sur "copy", le fichier /etc/localtime de l'hôte est copié dans le conteneur. De même, si "bind" est utilisé, le fichier est monté par liaison depuis l'hôte vers le conteneur. S'il est défini sur "symlink", un lien symbolique est créé pointant de /etc/localtime dans le conteneur vers le fichier de fuseau horaire dans le conteneur qui correspond au paramètre de fuseau horaire sur l'hôte. S'il est défini sur "delete", le fichier dans le conteneur est supprimé s'il existe. S'il est défini sur "auto" et que le fichier /etc/localtime de l'hôte est un lien symbolique, alors le mode "symlink" est utilisé, et "copy" sinon, sauf si l'image est en lecture seule, auquel cas "bind" est utilisé à la place. Ajouté dans la version 239.

--link-journal=

Contrôle si le journal du conteneur doit être visible par le système hôte. S'il est activé, permet de visualiser les fichiers journaux du conteneur depuis l'hôte (mais pas l'inverse). Accepte l'une des valeurs suivantes : "no", "host", "try-host", "guest", "try-guest", "auto". Si "no", le journal n'est pas lié. Si "host", les fichiers journaux sont stockés sur le système de fichiers hôte (sous /var/log/journal/machine-id) et le sous-répertoire est monté par liaison dans le conteneur au même emplacement. Si "guest", les fichiers journaux sont stockés sur le système de fichiers invité (sous /var/log/journal/machine-id) et le sous-répertoire est lié symboliquement vers l'hôte au même emplacement. "try-host" et "try-guest" font la même chose mais ne génèrent pas d'erreur si l'hôte n'a pas de journalisation persistante activée, ou si le conteneur est en mode --ephemeral. Si "auto" (par défaut), et que le sous-répertoire droit de /var/log/journal existe, il sera monté par liaison dans le conteneur. Si le sous-répertoire n'existe pas, aucune liaison n'est effectuée. Essentiellement, démarrer un conteneur une fois avec "guest" ou "host" liera le journal de manière persistante si par la suite la valeur par défaut "auto" est utilisée.

Notez que --link-journal=try-guest est la valeur par défaut si l'unité de service modèle systemd-nspawn@.service est utilisée.

Options de montage

--bind=, --bind-ro=

Monte par liaison un fichier ou un répertoire de l'hôte dans le conteneur. Accepte l'une des formes suivantes : un argument de chemin  — dans ce cas, le chemin spécifié sera monté depuis l'hôte vers le même chemin dans le conteneur, ou une paire de chemins séparés par des deux-points  — dans ce cas, le premier chemin spécifié est la source sur l'hôte, et le second chemin est la destination dans le conteneur, ou un triple chemin séparé par des deux-points : chemin source, chemin de destination et options de montage. Le chemin source peut éventuellement être préfixé par un caractère "+". Si c'est le cas, le chemin source est pris par rapport au répertoire racine de l'image. Cela permet de configurer des montages par liaison à l'intérieur de l'image du conteneur. Le chemin source peut être spécifié comme une chaîne vide, auquel cas un répertoire temporaire sous /var/tmp/ de l'hôte est utilisé. Il est automatiquement supprimé lorsque le conteneur est arrêté. Si le chemin source n'est pas absolu, il est résolu par rapport au répertoire de travail courant. L'option --bind-ro= crée des montages par liaison en lecture seule. Les échappements de barre oblique inverse sont interprétés, donc "\:" peut être utilisé pour intégrer des deux-points dans l'un ou l'autre des chemins. Cette option peut être spécifiée plusieurs fois pour créer plusieurs points de montage par liaison indépendants.

Les options de montage sont séparées par des virgules. rbind et norbind contrôlent s'il faut créer un montage par liaison récursif ou régulier. Par défaut : rbind. noidmap, idmap, rootidmap et owneridmap contrôlent le mappage des identifiants.

L'utilisation de idmap, rootidmap ou owneridmap nécessite le support du système de fichiers source pour les montages avec mappage d'identifiants d'utilisateur/groupe. Par défaut : noidmap. Avec x étant le décalage de la plage d'UID du conteneur, y étant la longueur de la plage d'UID du conteneur, et p étant l'UID propriétaire du nœud source du montage par liaison sur l'hôte :

•Si noidmap est utilisé, tout utilisateur z dans la plage 0 ... y vu de l'intérieur du conteneur est mappé à x + z dans la plage x ... x + y sur l'hôte. Les autres utilisateurs hôtes sont mappés à nobody à l'intérieur du conteneur.
•Si idmap est utilisé, tout utilisateur z dans la plage d'UID 0 ... y vu de l'intérieur du conteneur est mappé au même z dans la même plage 0 ... y sur l'hôte. Les autres utilisateurs hôtes sont mappés à nobody à l'intérieur du conteneur.
•Si rootidmap est utilisé, l'utilisateur 0 vu de l'intérieur du conteneur est mappé à p sur l'hôte. Les autres utilisateurs hôtes sont mappés à nobody à l'intérieur du conteneur.
•Si owneridmap est utilisé, le propriétaire du répertoire cible à l'intérieur du conteneur est mappé à p sur l'hôte. Les autres utilisateurs hôtes sont mappés à nobody à l'intérieur du conteneur.

Quelle que soit l'option de mappage d'identifiants utilisée, le même mappage sera utilisé pour les identifiants d'utilisateurs et de groupes. Si rootidmap ou owneridmap sont utilisés, le groupe propriétaire du répertoire monté par liaison n'aura aucun effet.

Notez que lorsque cette option est utilisée en combinaison avec --private-users, les points de montage résultants seront détenus par l'utilisateur nobody. En effet, le montage et ses fichiers et répertoires restent la propriété des utilisateurs et groupes hôtes pertinents, qui n'existent pas dans le conteneur, et apparaissent donc sous l'UID 65534 (nobody). Si de tels montages par liaison sont créés, il est recommandé de les rendre en lecture seule, en utilisant --bind-ro=. Alternativement, vous pouvez utiliser l'option de montage "idmap" pour mapper les identifiants du système de fichiers.

Ajouté dans la version 198.

--bind-user=

Lie le répertoire personnel de l'utilisateur spécifié sur l'hôte dans le conteneur. Accepte le nom d'un utilisateur existant sur l'hôte comme argument. Peut être utilisé plusieurs fois pour lier plusieurs utilisateurs dans le conteneur. Cela fait deux choses :
1.Le répertoire personnel de l'utilisateur est monté par liaison depuis l'hôte vers /run/host/home/, en utilisant un montage idmapped pour mapper l'UID/GID de l'utilisateur hôte à son UID/GID attribué dans le conteneur.
2.Un enregistrement utilisateur et groupe JSON est généré dans /run/userdb/ décrivant l'utilisateur mappé. Il contient une représentation minimisée de l'enregistrement utilisateur de l'hôte, ajustée à l'UID/GID et au chemin du répertoire personnel attribués à l'utilisateur dans le conteneur. Le module nss-systemd(8) de glibc récupérera ces enregistrements à partir de là et les rendra disponibles dans les bases de données utilisateur/groupe du conteneur.

La combinaison des deux opérations ci-dessus garantit qu'il est possible de se connecter au conteneur en utilisant les mêmes informations de compte que sur l'hôte. L'utilisateur n'est mappé que de manière transitoire, pendant que le conteneur est en cours d'exécution, et le mappage lui-même n'entraîne pas de modifications persistantes dans le conteneur (sauf peut-être pour les messages de journal générés lors de la connexion, et similaires). Notez qu'en particulier l'attribution d'UID/GID dans le conteneur n'est pas faite de manière persistante. Si l'utilisateur est mappé de manière transitoire, il est préférable de ne pas autoriser l'utilisateur à apporter des modifications persistantes au conteneur. Si l'utilisateur laisse des fichiers ou des répertoires lui appartenant, et que ces UID/GID sont réutilisés lors d'invocations ultérieures du conteneur (éventuellement avec un mappage --bind-user= différent), ces fichiers et répertoires seront accessibles au "nouvel" utilisateur.

Le mappage de l'enregistrement utilisateur/groupe ne fonctionne que si le conteneur contient systemd 249 ou plus récent, avec nss-systemd correctement configuré dans nsswitch.conf. Voir nss-systemd(8) pour les détails.

Notez que l'enregistrement utilisateur transmis de l'hôte au conteneur contiendra le hachage de mot de passe UNIX de l'utilisateur, permettant ainsi des connexions transparentes dans le conteneur. Si le conteneur est moins fiable que l'hôte, il est donc important d'utiliser une fonction de hachage de mot de passe UNIX robuste (par exemple, yescrypt ou similaire, avec le préfixe de hachage "$y$").

Lors de la liaison d'un utilisateur de l'hôte au conteneur, des vérifications sont effectuées pour s'assurer que le nom d'utilisateur n'est pas encore connu dans le conteneur. De plus, il est vérifié que l'UID/GID qui lui est attribué n'est actuellement pas défini dans les bases de données utilisateur/groupe du conteneur. Ces deux vérifications accèdent directement aux fichiers /etc/passwd et /etc/group du conteneur, et peuvent donc ne pas détecter les comptes existants dans d'autres bases de données.

Ajouté dans la version 249.

--bind-user-shell=

Lorsqu'il est utilisé avec --bind-user=, inclut le shell spécifié dans les enregistrements utilisateur des utilisateurs liés dans le conteneur. Accepte soit une valeur booléenne, soit un chemin absolu.
•Si false (par défaut), aucun shell n'est passé dans les enregistrements utilisateur pour les utilisateurs liés dans le conteneur. Cela amène les utilisateurs liés à utiliser le shell par défaut du conteneur.
•Si true, les shells spécifiés par les enregistrements utilisateur de l'hôte sont inclus dans les enregistrements utilisateur de tous les utilisateurs liés dans le conteneur.
•Si un chemin absolu est passé, ce chemin est défini comme shell pour les enregistrements utilisateur de tous les utilisateurs liés dans le conteneur.

Note : Cela ne vérifiera pas si les shells spécifiés existent dans le conteneur.

Cette opération n'est prise en charge qu'en combinaison avec --bind-user=.

Ajouté dans la version 258.

--inaccessible=

Rend le chemin spécifié inaccessible dans le conteneur. Cela superpose le chemin spécifié (qui doit exister dans le conteneur) avec un nœud de fichier du même type qui est vide et possède le mode d'accès le plus restrictif pris en charge. C'est un moyen efficace de masquer des fichiers, des répertoires et d'autres objets du système de fichiers à la charge utile du conteneur. Cette option peut être utilisée plusieurs fois si tous les chemins spécifiés sont masqués.

Ajouté dans la version 242.

--tmpfs=

Monte un système de fichiers tmpfs dans le conteneur. Accepte un unique argument de chemin absolu qui spécifie où monter l'instance tmpfs (auquel cas le mode d'accès au répertoire sera choisi comme 0755, appartenant à root/root), ou éventuellement une paire chemin séparée par deux-points aoption de montage nd chaîne utilisée pour le montage (auquel cas la valeur par défaut du noyau pour le mode d'accès et le propriétaire sera choisie, sauf indication contraire). Les échappements de barre oblique inverse sont interprétés dans le chemin, ainsi "\:" peut être utilisé pour intégrer des deux-points dans le chemin.

Notez que cette option ne peut pas être utilisée pour remplacer le système de fichiers racine du conteneur par un système de fichiers temporaire. Cependant, l'option --volatile= décrite ci-dessous fournit une fonctionnalité similaire, en mettant l'accent sur l'implémentation d'images système d'exploitation sans état.

Ajouté dans la version 214.

--overlay=, --overlay-ro=

Combine plusieurs arborescences de répertoires en un seul système de fichiers de superposition et le monte dans le conteneur. Prend une liste de chemins séparés par deux-points vers les arborescences de répertoires à combiner et le point de montage de destination.

Les échappements de barre oblique inverse sont interprétés dans les chemins, ainsi "\:" peut être utilisé pour intégrer des deux-points dans les chemins.

Si trois chemins ou plus sont spécifiés, le dernier chemin spécifié est le point de montage de destination dans le conteneur, tous les chemins spécifiés avant font référence à des arborescences de répertoires sur l'hôte et sont combinés dans l'ordre spécifié en un seul système de fichiers de superposition. Le chemin le plus à gauche est donc l'arborescence de répertoire la plus basse, le chemin avant-dernier l'arborescence de répertoire la plus haute dans l'ordre d'empilement. Si --overlay-ro= est utilisé à la place de --overlay=, un système de fichiers de superposition en lecture seule est créé. Si un système de fichiers de superposition inscriptible est créé, toutes les modifications qui y sont apportées sont écrites dans l'arborescence de répertoire la plus haute dans l'ordre d'empilement, c'est-à-dire l'avant-dernier spécifié.

Si seulement deux chemins sont spécifiés, le deuxième chemin spécifié est utilisé à la fois comme arborescence de répertoire de niveau supérieur dans l'ordre d'empilement vu depuis l'hôte, ainsi que comme point de montage pour le système de fichiers de superposition dans le conteneur. Au moins deux chemins doivent être spécifiés.

Les chemins sources peuvent éventuellement être préfixés par le caractère "+". Si c'est le cas, ils sont pris par rapport au répertoire racine de l'image. Le chemin source le plus haut peut également être spécifié comme une chaîne vide, auquel cas un répertoire temporaire sous /var/tmp/ de l'hôte est utilisé. Le répertoire est automatiquement supprimé lorsque le conteneur est arrêté. Ce comportement est utile pour rendre les répertoires de conteneur en lecture seule inscriptibles pendant que le conteneur est en cours d'exécution. Par exemple, utilisez "--overlay=+/var::/var" pour superposer automatiquement un répertoire temporaire inscriptible sur un répertoire /var/ en lecture seule. Si un chemin source n'est pas absolu, il est résolu par rapport au répertoire de travail actuel.

Pour plus de détails sur les systèmes de fichiers de superposition, voir Système de fichiers de superposition[5]. Notez que la sémantique des systèmes de fichiers de superposition est substantiellement différente des systèmes de fichiers normaux, en particulier concernant les informations de périphérique et d'inode rapportées. Les informations de périphérique et d'inode peuvent changer pour un fichier pendant qu'il est écrit, et les processus peuvent voir des versions obsolètes des fichiers à certains moments. Notez que ce commutateur dérive automatiquement l'option de montage "workdir=" pour le système de fichiers de superposition de l'arborescence de répertoire de niveau supérieur, en en faisant un frère. Il est donc essentiel que l'arborescence de répertoire de niveau supérieur ne soit pas un point de montage en soi (car le répertoire de travail doit être sur le même système de fichiers que l'arborescence de répertoire la plus haute). Notez également que l'option de montage "lowerdir=" reçoit les chemins à empiler dans l'ordre inverse de ce commutateur.

Notez que cette option ne peut pas être utilisée pour remplacer le système de fichiers racine du conteneur par un système de fichiers de superposition. Cependant, l'option --volatile= décrite ci-dessus fournit une fonctionnalité similaire, en mettant l'accent sur l'implémentation d'images système d'exploitation sans état.

Ajouté dans la version 220.

Options d'entrée/sortie

--console=MODE

Configure comment configurer l'entrée standard, la sortie et la sortie d'erreur pour la charge utile du conteneur, ainsi que le périphérique /dev/console pour le conteneur. Prend l'une des valeurs : interactive, read-only, passive, pipe ou autopipe. Si interactive, un pseudo-TTY est alloué et mis à disposition en tant que /dev/console dans le conteneur. Il est ensuite connecté de manière bidirectionnelle à l'entrée et à la sortie standard passées à systemd-nspawn. read-only est similaire mais seule la sortie du conteneur est propagée et aucune entrée de l'appelant n'est lue. Si passive, un pseudo-TTY est alloué, mais il n'est connecté nulle part. En mode pipe, aucun pseudo-TTY n'est alloué, mais les descripteurs de fichiers pour l'entrée standard, la sortie et la sortie d'erreur passés à systemd-nspawn sont transmis — tels quels — à la charge utile du conteneur, voir le paragraphe suivant. Enfin, le mode autopipe fonctionne comme interactive lorsque systemd-nspawn est invoqué sur un terminal, et comme pipe sinon. Par défaut : interactive si systemd-nspawn est invoqué depuis un terminal, et read-only sinon.

En mode pipe, /dev/console n'existera pas dans le conteneur. Cela signifie que la charge utile du conteneur ne peut généralement pas être un système d'initialisation complet car les systèmes d'initialisation ont tendance à nécessiter que /dev/console soit disponible. D'un autre côté, dans ce mode, les invocations de conteneur peuvent être utilisées dans des pipelines shell. En effet, les pseudo-TTY intermédiaires ne permettent pas une propagation bidirectionnelle indépendante de la condition de fin de fichier (EOF), ce qui est nécessaire pour que les pipelines shell fonctionnent correctement. Notez que le mode pipe doit être utilisé avec précaution, car la transmission de descripteurs de fichiers arbitraires à des charges utiles de conteneur moins fiables pourrait ouvrir des interfaces indésirables pour l'accès par la charge utile du conteneur. Par exemple, si un descripteur de fichier transmis fait référence à un TTY sous une forme quelconque, des API telles que TIOCSTI peuvent être utilisées pour synthétiser des entrées qui pourraient être utilisées pour s'échapper du conteneur. Par conséquent, le mode pipe ne doit être utilisé que si la charge utile est suffisamment fiable ou lorsque les descripteurs de fichiers d'entrée/sortie/erreur standard sont connus pour être sûrs, par exemple des pipes.

Ajouté dans la version 242.

--pipe, -P

Équivalent à --console=pipe.

Ajouté dans la version 242.

--background=COULEUR

Change la couleur d'arrière-plan du terminal à la couleur ANSI spécifiée tant que le conteneur s'exécute. La couleur spécifiée doit être une couleur d'arrière-plan SGR ANSI X3.64, c'est-à-dire des chaînes telles que "40", "41", ..., "47", "48;2;...", "48;5;...". Voir Code d'échappement ANSI (Wikipedia)[6] pour plus de détails. Attribuez une chaîne vide pour désactiver toute coloration.

Ajouté dans la version 256.

Identifiants

--load-credential=ID:CHEMIN, --set-credential=ID:VALEUR

Passe un identifiant au conteneur. Ces deux options correspondent aux paramètres LoadCredential= et SetCredential= dans les fichiers d'unité. Voir systemd.exec(5) pour plus de détails sur ces concepts, ainsi que sur la syntaxe des arguments de l'option.

Note : lorsque systemd-nspawn s'exécute en tant que service système systemd, il peut propager les identifiants qu'il a reçus via LoadCredential=/SetCredential= à la charge utile du conteneur. Un gestionnaire de service systemd s'exécutant en tant que PID 1 dans le conteneur peut les propager davantage aux services qu'il démarre lui-même. Il est donc possible de propager facilement des identifiants d'un gestionnaire de service parent à un gestionnaire de service de conteneur et de là à sa charge utile. Cela peut même être fait récursivement.

Afin d'intégrer des données binaires dans les données d'identifiant pour --set-credential=, utilisez l'échappement de style C (c'est-à-dire "\n" pour intégrer un retour à la ligne, ou "\x00" pour intégrer un octet NUL). Notez que le shell appelant peut déjà appliquer un déséchappement une fois, cela pourrait donc nécessiter un double échappement !

Les services systemd-sysusers.service(8) et systemd-firstboot(1) lisent les identifiants configurés de cette manière dans le but de configurer le mot de passe et le shell de l'utilisateur root du conteneur, ainsi que la locale du système, la disposition du clavier et le fuseau horaire lors du premier démarrage du conteneur. Ceci est particulièrement utile en combinaison avec --volatile=yes où chaque démarrage apparaît comme un premier démarrage, car la configuration appliquée à /etc/ est perdue lors des cycles de redémarrage du conteneur. Voir les pages de manuel respectives pour plus de détails. Exemple :

# systemd-nspawn -i image.raw \
          --volatile=yes \
          --set-credential=firstboot.locale:de_DE.UTF-8 \
          --set-credential=passwd.hashed-password.root:'$y$j9T$yAuRJu1o5HioZAGDYPU5d.$F64ni6J2y2nNQve90M/p0ZP0ECP/qqzipNyaY9fjGpC' \
          -b

La ligne de commande ci-dessus invoquera le fichier image spécifié image.raw en mode volatile, c'est-à-dire avec /etc/ et /var/ vides. La charge utile du conteneur reconnaîtra cela comme un premier démarrage et invoquera systemd-firstboot.service, qui lira ensuite les deux identifiants passés pour configurer la locale initiale et le mot de passe root du système.

Ajouté dans la version 247.

ENVIRONNEMENT

$SYSTEMD_LOG_LEVEL

Le niveau de journalisation maximum des messages émis (les messages avec un niveau de journalisation plus élevé, c'est-à-dire moins importants, seront supprimés). Prend une liste de valeurs séparées par des virgules. Une valeur peut être l'une des suivantes (par ordre d'importance décroissante) : emerg, alert, crit, err, warning, < b>avis, info, debug ou un entier dans la plage 0...7. Voir syslog(3) pour plus d'informations. Chaque valeur peut facultativement être précédée de console, syslog, kmsg ou journal suivie d'un deux-points pour définir le niveau de journalisation maximal pour cette cible de journalisation spécifique (par exemple, SYSTEMD_LOG_LEVEL=debug,console:info spécifie de journaliser au niveau debug sauf lors de la journalisation vers la console qui devrait être au niveau info). Notez que le niveau de journalisation maximal global a la priorité sur tous les niveaux de journalisation maximaux par cible.

$SYSTEMD_LOG_COLOR

Un booléen. S'il est vrai, les messages écrits sur le tty seront colorés en fonction de leur priorité.

Ce paramètre n'est utile que lorsque les messages sont écrits directement sur le terminal, car journalctl(1) et d'autres outils qui affichent les journaux coloreront eux-mêmes les messages en fonction du niveau de journalisation.

$SYSTEMD_LOG_TIME

Un booléen. S'il est vrai, les messages de journalisation console seront précédés d'un horodatage.

Ce paramètre n'est utile que lorsque les messages sont écrits directement sur le terminal ou dans un fichier, car journalctl(1) et d'autres outils qui affichent les journaux y attacheront eux-mêmes des horodatages basés sur les métadonnées de l'entrée.

$SYSTEMD_LOG_LOCATION

Un booléen. S'il est vrai, les messages seront précédés du nom de fichier et du numéro de ligne dans le code source d'où provient le message.

Notez que l'emplacement du journal est souvent déjà attaché comme métadonnées aux entrées du journal. L'inclure directement dans le texte du message peut néanmoins être pratique lors du débogage de programmes.

$SYSTEMD_LOG_TID

Un booléen. S'il est vrai, les messages seront précédés de l'identifiant numérique du thread (TID) actuel.

Notez que ces informations sont de toute façon attachées comme métadonnées aux entrées du journal. Les inclure directement dans le texte du message peut néanmoins être pratique lors du débogage de programmes.

$SYSTEMD_LOG_TARGET

La destination des messages de journalisation. L'un des choix suivants : console (journalisation sur le tty attaché), console-prefixed (journalisation sur le tty attaché mais avec des préfixes codant le niveau de journalisation et la "facility", voir syslog(3), kmsg (journalisation sur le tampon circulaire du noyau), journal (journalisation dans le journal), journal-or-kmsg (journalisation dans le journal si disponible, et dans kmsg sinon), auto (détermination automatique de la cible de journalisation appropriée, par défaut), null (désactivation de la sortie de journalisation).

$SYSTEMD_LOG_RATELIMIT_KMSG

Indique s'il faut limiter la fréquence des messages kmsg ou non. Prend une valeur booléenne. La valeur par défaut est "true". Si désactivé, systemd ne limitera pas la fréquence des messages écrits dans kmsg.

$SYSTEMD_PAGER, $PAGER

Le pager à utiliser lorsque --no-pager n'est pas spécifié. $SYSTEMD_PAGER est utilisé s'il est défini ; sinon, $PAGER est utilisé. Si ni $SYSTEMD_PAGER ni $PAGER ne sont définis, un ensemble d'implémentations de pager connues sont essayées tour à tour, y compris less(1) et more(1), jusqu'à ce qu'une soit trouvée. Si aucune implémentation de pager n'est découverte, aucun pager n'est invoqué. Définir ces variables d'environnement sur une chaîne vide ou la valeur "cat" équivaut à passer --no-pager.

Note : si $SYSTEMD_PAGERSECURE n'est pas défini, $SYSTEMD_PAGER et $PAGER ne peuvent être utilisés que pour désactiver le pager (avec "cat" ou ""), et sont autrement ignorés.

$SYSTEMD_LESS

Surcharge les options passées à less (par défaut "FRSXMK").

Les utilisateurs pourraient vouloir changer deux options en particulier :

K

Cette option indique au pager de quitter immédiatement lorsque Ctrl+C est pressé. Pour permettre à less de gérer Ctrl+C lui-même afin de revenir à l'invite de commande du pager, désactivez cette option.

Si la valeur de $SYSTEMD_LESS n'inclut pas "K", et que le pager invoqué est less, Ctrl+C sera ignoré par l'exécutable et devra être géré par le pager.

X

Cette option indique au pager de ne pas envoyer les chaînes d'initialisation et de désinitialisation termcap au terminal. Elle est définie par défaut pour permettre à la sortie de la commande de rester visible dans le terminal même après la sortie du pager. Néanmoins, cela empêche certaines fonctionnalités du pager de fonctionner, en particulier la sortie paginée ne peut pas être défilée avec la souris.

Notez que la définition de la variable d'environnement $LESS normale n'a aucun effet pour les invocations de less par les outils systemd.

Voir less(1) pour plus de détails.

$SYSTEMD_LESSCHARSET

Surcharge le jeu de caractères passé à less (par défaut "utf-8", si le terminal appelant est déterminé comme compatible UTF-8).

Notez que la définition de la variable d'environnement $LESSCHARSET normale n'a aucun effet pour les invocations de less par les outils systemd.

$SYSTEMD_PAGERSECURE

Les commandes de pager courantes comme less(1), en plus de la "pagination", c'est-à-dire le défilement de la sortie, supportent l'ouverture ou l'écriture d'autres fichiers et l'exécution de commandes shell arbitraires. Lorsque des commandes sont invoquées avec des privilèges élevés, par exemple sous sudo(8) ou pkexec(1), le pager devient une frontière de sécurité. Il faut veiller à ce que seuls des programmes aux fonctionnalités strictement limitées soient utilisés comme pagers, et que des fonctionnalités interactives involontaires comme l'ouverture ou la création de nouveaux fichiers ou le lancement de sous-processus ne soient pas autorisées. Le "mode sécurisé" pour le pager peut être activé comme décrit ci-dessous, si le pager le supporte (la plupart des pagers ne sont pas écrits de manière à en tenir compte). Il est recommandé soit d'activer explicitement le "mode sécurisé", soit de désactiver complètement le pager en utilisant --no-pager ou PAGER=cat lorsque l'on autorise des utilisateurs non fiables à exécuter des commandes avec des privilèges élevés.

Cette option prend un argument booléen. Lorsqu'elle est définie sur vrai, le "mode sécurisé" du pager est activé. En "mode sécurisé", LESSSECURE=1 sera défini lors de l'invocation du pager, ce qui indique au pager de désactiver les commandes qui ouvrent ou créent de nouveaux fichiers ou lancent de nouveaux sous-processus. Actuellement, seul less(1) est connu pour comprendre cette variable et implémenter le "mode sécurisé".

Lorsqu'elle est définie sur faux, aucune limitation n'est imposée au pager. Définir SYSTEMD_PAGERSECURE=0 ou ne pas la supprimer de l'environnement hérité peut permettre à l'utilisateur d'invoquer des commandes arbitraires.

Lorsque $SYSTEMD_PAGERSECURE n'est pas défini, les outils systemd tentent de déterminer automatiquement si le "mode sécurisé" doit être activé et si le pager le supporte. Le "mode sécurisé" est activé si l'UID effectif n'est pas le même que le propriétaire de la session de connexion, voir geteuid(2) et sd_pid_get_owner_uid(3), ou lors de l'exécution sous sudo(8) ou des outils similaires ($SUDO_UID est défini [7]). Dans ces cas, SYSTEMD_PAGERSECURE=1 sera défini et les pagers qui ne sont pas connus pour implémenter le "mode sécurisé" ne seront pas utilisés du tout. Notez que cette auto-détection ne couvre que les mécanismes les plus courants pour élever les privilèges et est destinée à des fins de commodité. Il est recommandé de définir explicitement $SYSTEMD_PAGERSECURE ou de désactiver le pager.

Notez que si les variables $SYSTEMD_PAGER ou $PAGER doivent être prises en compte, autre que pour désactiver le pager, $SYSTEMD_PAGERSECURE doit également être défini.

$SYSTEMD_COLORS

Prend un argument booléen. S'il est vrai, systemd et les utilitaires associés utiliseront des couleurs dans leur sortie, sinon la sortie sera monochrome. De plus, la variable peut prendre l'une des valeurs spéciales suivantes : "16", "256" pour restreindre l'utilisation des couleurs aux couleurs ANSI de base 16 ou 256, respectivement. Cela peut être spécifié pour remplacer la décision automatique basée sur $TERM et ce à quoi le console est connectée.

$SYSTEMD_URLIFY

La valeur doit être un booléen. Contrôle si des liens cliquables doivent être générés dans la sortie pour les émulateurs de terminaux qui le supportent. Ceci peut être spécifié pour remplacer la décision que systemd prend en fonction de $TERM et d'autres conditions.

EXEMPLES

Exemple 1. Télécharger une image TAR Ubuntu et ouvrir un shell dedans

# importctl pull-tar -mN https://cloud-images.ubuntu.com/jammy/current/jammy-server-cloudimg-amd64-root.tar.xz
# systemd-nspawn -M jammy-server-cloudimg-amd64-root

Ceci télécharge et vérifie l'image .tar spécifiée, puis utilise systemd-nspawn(1) pour ouvrir un shell dedans.

Exemple 2. Construire et démarrer une distribution Fedora minimale dans un conteneur

# dnf -y --releasever=42 --installroot=/var/lib/machines/f42 \
      --use-host-config --setopt=install_weak_deps=0 \
      --repo=fedora --repo=updates install \
      passwd dnf fedora-release nano util-linux systemd systemd-networkd
# systemd-nspawn -bD /var/lib/machines/f42

(Omettez --use-host-config lors de l'utilisation de dnf <= 4.) Ceci installe une distribution Fedora minimale dans le répertoire /var/lib/machines/f42 et démarre ensuite ce système d'exploitation dans un conteneur d'espace de noms. Comme l'installation est située sous le répertoire standard /var/lib/machines/, il est également possible de démarrer la machine en utilisant systemd-nspawn -M f42.

Exemple 3. Lancer un shell dans un conteneur d'une distribution Debian instable minimale

# debootstrap unstable ~/debian-tree/
# systemd-nspawn -D ~/debian-tree/

Ceci installe une distribution Debian instable minimale dans le répertoire ~/debian-tree/ et lance ensuite un shell à partir de cette image dans un conteneur d'espace de noms.

debootstrap supporte Debian[8] et Ubuntu[9] directement, donc la même commande peut être utilisée pour installer l'une d'elles. Pour d'autres distributions de la famille Debian, un miroir doit être spécifié, voir debootstrap(8).

Exemple 4. Démarrer une distribution Arch Linux minimale dans un conteneur

# pacstrap -c ~/arch-tree/ base
# systemd-nspawn -bD ~/arch-tree/

Ceci installe une distribution Arch Linux minimale dans le répertoire ~/arch-tree/ et démarre ensuite un système d'exploitation dans un conteneur d'espace de noms.

Exemple 5. Installer la distribution roulante OpenSUSE Tumbleweed 

# zypper --root=/v
ar/lib/machines/tumbleweed ar -c \ https://download.opensuse.org/tumbleweed/repo/oss tumbleweed # zypper --root=/var/lib/machines/tumbleweed refresh # zypper --root=/var/lib/machines/tumbleweed install --no-recommends \ systemd shadow zypper openSUSE-release vim # systemd-nspawn -M tumbleweed passwd root # systemd-nspawn -M tumbleweed -b

Exemple 6. Démarrer dans un instantané éphémère du système hôte

# systemd-nspawn -D / -xb

Ceci exécute une copie du système hôte dans un instantané qui est supprimé immédiatement à la sortie du conteneur. Toutes les modifications du système de fichiers effectuées pendant l'exécution seront perdues à l'arrêt, d'où.

Exemple 7. Exécuter un conteneur avec des contextes de sécurité SELinux de type sandbox
