NOM

systemd-boot, sd-boot - Un gestionnaire de démarrage UEFI simple

DESCRIPTION

systemd-boot (abrégé : sd-boot) est un gestionnaire de démarrage UEFI simple. Il fournit un menu textuel pour sélectionner l'entrée à démarrer et un éditeur pour la ligne de commande du noyau. systemd-boot ne prend en charge que les systèmes équipés du firmware UEFI.

systemd-boot charge les informations des entrées de démarrage depuis la partition système EFI (ESP), généralement montée sur /efi/, /boot/, ou /boot/efi/ pendant l'exécution du système d'exploitation, ainsi que depuis la partition du chargeur de démarrage étendu (XBOOTLDR) si elle existe (généralement montée sur /boot/). Les fichiers de configuration, les noyaux, les initrds et autres images EFI à démarrer doivent généralement résider sur l'ESP ou la partition du chargeur de démarrage étendu. Les noyaux Linux doivent être compilés avec CONFIG_EFI_STUB pour pouvoir être exécutés directement en tant qu'image EFI. Pendant le démarrage, systemd-boot assemble automatiquement une liste d'entrées de démarrage à partir des sources suivantes :

•Entrées de démarrage définies avec les fichiers de description Type #1 de la Spécification du chargeur de démarrage[1] situés dans /loader/entries/ sur l'ESP et la partition du chargeur de démarrage étendu. Ceux-ci décrivent généralement des images de noyau Linux avec des images initrd associées, mais peuvent alternativement décrire d'autres exécutables EFI arbitraires.
•Images de noyau unifiées, Type #2 de la Spécification du chargeur de démarrage[1], qui sont des binaires EFI exécutables dans /EFI/Linux/ sur l'ESP et la partition du chargeur de démarrage étendu.
•Le gestionnaire de démarrage EFI de Microsoft Windows, s'il est installé.
•Le gestionnaire de démarrage EFI de macOS d'Apple, s'il est installé.
•Le binaire EFI Shell, s'il est installé.
•Une option « Redémarrer vers l'interface du firmware », si elle est prise en charge par le firmware UEFI.
•L'enrôlement des variables de Secure Boot si le firmware UEFI est en mode configuration et que des fichiers sont fournis sur l'ESP.

systemd-boot prend en charge les fonctionnalités suivantes :

•Les modifications de base de la configuration du gestionnaire de démarrage (telles que la configuration du délai d'attente, la sélection de l'entrée de démarrage par défaut, ...) peuvent être effectuées directement depuis l'interface utilisateur du chargeur de démarrage au moment du démarrage, ainsi que pendant l'exécution du système avec les variables EFI.
•Le gestionnaire de démarrage s'intègre à la commande systemctl pour implémenter des fonctionnalités telles que systemctl reboot --boot-loader-entry=... (pour redémarrer vers une entrée de menu de démarrage spécifique, c'est-à-dire « redémarrer vers Windows ») et systemctl reboot --boot-loader-menu=... (pour redémarrer vers le menu du chargeur de démarrage), en implémentant l'Interface du chargeur de démarrage[2]. Voir systemctl(1) pour plus de détails.
•Une variable EFI définie par le chargeur de démarrage informe le système d'exploitation de l'ESP utilisée pendant le démarrage. Ceci est utilisé pour monter automatiquement la bonne partition système EFI sur /efi/ ou /boot/ pendant l'exécution du système d'exploitation. Voir systemd-gpt-auto-generator(8) pour plus de détails.
•Le gestionnaire de démarrage fournit des informations sur le temps de démarrage passé dans le firmware UEFI en utilisant l'Interface du chargeur de démarrage[2]. Ces informations peuvent être affichées en utilisant systemd-analyze(1).
•Le gestionnaire de démarrage implémente le comptage des démarrages et le retour automatique à d'anciennes entrées de démarrage fonctionnelles en cas d'échec. Voir Évaluation automatique du démarrage[3].
•Le gestionnaire de démarrage lit optionnellement une graine aléatoire à partir de la partition ESP, la combine avec un « jeton système » stocké dans une variable EFI persistante et dérive une graine aléatoire à utiliser par le système d'exploitation comme initialisation du pool d'entropie, fournissant un pool d'entropie complet pendant le démarrage précoce.
•Le gestionnaire de démarrage permet l'enrôlement des variables de Secure Boot si le firmware UEFI est en mode configuration. De plus, les variables peuvent être automatiquement enrôlées si configurées.

L'outil bootctl(1) peut être utilisé depuis un système en cours d'exécution pour localiser l'ESP et la partition du chargeur de démarrage étendu, lister les entrées disponibles et installer systemd-boot lui-même.

L'outil kernel-install(8) peut être utilisé pour copier des images de noyau sur l'ESP ou la partition du chargeur de démarrage étendu et pour générer des fichiers de description conformes à la spécification du chargeur de démarrage.

L'outil systemd-stub(7) peut être utilisé comme point d'ancrage de démarrage UEFI pour les noyaux exécutés, ce qui est utile pour afficher des écrans de démarrage graphiques avant de passer au monde Linux. Il est également capable de récupérer automatiquement les fichiers auxiliaires d'identification (pour la paramétrisation des arguments de démarrage) et les images d'extension système, en tant que fichiers compagnons des images de noyau démarrées.

FICHIERS

Les fichiers traités par systemd-boot résident généralement sur l'ESP UEFI, qui est généralement monté sur /efi/, /boot/ ou /boot/efi/ pendant l'exécution du système d'exploitation. Il traite également les fichiers sur la partition Extended Boot Loader, qui est typiquement montée sur /boot/, si elle existe.

systemd-boot lit la configuration d'exécution, telle que le délai de démarrage et l'entrée par défaut, à partir de /loader/loader.conf sur l'ESP (en combinaison avec les données lues à partir des variables EFI). Voir loader.conf(5).

Les fichiers de description des entrées de démarrage suivant la Spécification du chargeur de démarrage[1] sont lus à partir de /loader/entries/ sur l'ESP et la partition Extended Boot Loader.

Les entrées de démarrage de noyau unifié suivant la Spécification du chargeur de démarrage[1] sont lues à partir de /EFI/Linux/ sur l'ESP et la partition Extended Boot Loader.

Optionnellement, une graine aléatoire pour la fourniture du pool d'entropie au démarrage précoce est stockée dans /loader/random-seed sur l'ESP.

Lors de l'initialisation, sd-boot charge automatiquement tous les fichiers de pilotes placés dans le répertoire /EFI/systemd/drivers/ de l'ESP. Les fichiers placés là doivent avoir une extension de l'identifiant de l'architecture EFI suivie de .efi (par exemple, pour x86-64, cela signifie un suffixe x64.efi). Ceci peut être utilisé pour charger automatiquement des pilotes de système de fichiers et similaires, afin d'étendre le support natif du firmware.

L'enrôlement des variables de Secure Boot peut être effectué manuellement ou automatiquement si des fichiers sont disponibles sous /loader/keys/NOM/{db,dbx,KEK,PK}.auth, NOM étant le nom d'affichage de l'ensemble des variables dans le menu. Si l'un des ensembles est nommé auto, il peut être enrôlé automatiquement en fonction de si "secure-boot-enroll" est défini sur force ou non.

systemd-boot peut être configuré à l'aide des chaînes SMBIOS Type 11. Les chaînes applicables consistent en un nom, suivi de "=", suivi de la valeur. À moins que systemd-boot ne détecte qu'il s'exécute dans un environnement de calcul confidentiel, systemd-boot recherchera dans la table une chaîne avec un nom spécifique, et si elle est trouvée, utilisera sa valeur. Les chaînes suivantes sont lues :

io.systemd.boot.kernel-cmdline-extra

Si elle est définie, la valeur de cette chaîne est ajoutée à la liste des arguments de la ligne de commande du noyau pour les entrées de la spécification du chargeur de démarrage de type 1 qui sont mesurées dans PCR12 et transmises au noyau.

Ajouté dans la version 256.

io.systemd.boot-entries.extra:ID=DÉFINITION

Cela permet d'insérer des entrées supplémentaires dans le menu systemd-boot. Prenez une paire d'identifiant d'entrée de menu et de chaîne de définition d'entrée de menu. Le premier doit être utilisable comme nom de fichier d'une entrée de la spécification du chargeur de démarrage de type #1 (notez qu'il est utilisé à des fins d'identification uniquement, aucun fichier de ce nom n'est réellement accédé), le second doit suivre la syntaxe du contenu d'une entrée de type #1. Toute entrée de menu définie de cette manière est traitée et affichée à peu près de la même manière qu'une entrée de type #1 lue depuis la partition ESP ou XBOOTLDR. Exemple : 
io.systemd.boot-entries.extra:fooos-current.conf=title FooOS (Current)
uki-url http://example.com/somedir/fooos.efi

Notez que cet exemple contient un caractère de nouvelle ligne. Lors de la génération de cette chaîne à partir d'un shell, il faut veiller à l'encoder correctement.

Passez plusieurs chaînes formatées de cette manière pour générer des entrées multiples.

systemd-boot.7 - Arch Linux

NAME

systemd-boot — Simple UEFI boot manager

DESCRIPTION

systemd-boot is a simple boot manager for systems that support the UEF I firmware interface. It works by loading EFI executables from the EFI system partition (ESP).

When the system boots, the UEFI firmware locates and runs systemd-boot (typically located at /EFI/systemd/systemd-bootx64.efi or /EFI/BOOT/BOOTX64.EFI on the EFI system partition). systemd-boot then enumerates available EFI executables (including kernel executables and other boot loaders) from the ESP and displays a menu to the user. If no user interaction occurs within a timeout period, the default entry is booted.

The boot loader configuration is stored in loader/loader.conf and loader/entries/*.conf files on the ESP.

When a boot entry is selected or the timeout expires, systemd-boot loads the specified EFI executable into memory and transfers control to it. For kernel entries, this typically involves loading the kernel and an optional initramfs into memory and passing command line arguments.

systemd-boot supports the Boot Loader Specification[1], which defines a standard way to specify boot entries, kernel command lines, and other boot-related information. This allows other tools, such as kernel-install(8), to integrate with systemd-boot.

systemd-boot implements a boot counting mechanism for automatic fallback to older kernel versions or boot loader entries when a specific entry continuously fails. See BOOT COUNTING for details.

Added in version 239.

BOOT COUNTING

systemd-boot implements a simple boot counting mechanism on top of the Boot Loader Specification[1], for automatic and unattended fallback to older kernel versions/boot loader entries when a specific entry continuously fails. Any boot loader entry file and unified kernel image file that contains a "+" followed by one or two numbers (if two they need to be separated by a "-"), before the .conf or .efi suffix is subject to boot counting: the first of the two numbers ('tries left') is decreased by one on every boot attempt, the second of the two numbers ('tries done') is increased by one (if 'tries done' is absent it is considered equivalent to 0). Depending on the current value of these two counters the boot entry is considered to be in one of three states:

1.If the 'tries left' counter of an entry is greater than zero the entry is considered to be in 'indeterminate' state. This means the entry has not completed booting successfully yet, but also has not been determined not to work.
2.If the 'tries left' counter of an entry is zero it is considered to be in 'bad' state. This means no further attempts to boot this item will be made (that is, unless all other boot entries are also in 'bad' state), as all attempts to boot this entry have not completed successfully.
3.If the 'tries left' and 'tries done' counters of an entry are absent it is considered to be in 'good' state. This means further boot counting for the entry is turned off, as it successfully booted at least once. The systemd-bless-boot.service(8) service moves the currently booted entry from 'indeterminate' into 'good' state when a boot attempt completed successfully.

Generally, when new entries are added to the boot loader, they first start out in 'indeterminate' state, i.e. with a 'tries left' counter greater than zero. The boot entry remains in this state until either it managed to complete a full boot successfully at least once (in which case it will be in 'good' state) — or the 'tries left' counter reaches zero (in which case it will be in 'bad' state).

Example: let's say a boot loader entry file foo.conf is set up for 3 boot tries. The installer will hence create it under the name foo+3.conf. On first boot, the boot loader will rename it to foo+2-1.conf. If that boot does not complete successfully, the boot loader will rename it to foo+1-2.conf on the following boot. If that fails too, it will finally be renamed foo+0-3.conf by the boot loader on next boot, after which it will be considered 'bad'. If the boot succeeds however the entry file will be renamed to foo.conf by the OS, so that it is considered 'good' from then on.

The boot menu takes the 'tries left' counter into account when sorting the menu entries: entries in 'bad' state are ordered at the beginning of the list, and entries in 'good' or 'indeterminate' at the end. The user can freely choose to boot any entry of the menu, including those already marked 'bad'. If the menu entry to boot is automatically determined, this means that 'good' or 'indeterminate' entries are generally preferred (as the bottom item of the menu is the one booted by default), and 'bad' entries will only be considered if there are no 'good' or 'indeterminate' entries left.

The kernel-install(8) kernel install framework optionally sets the initial 'tries left' counter to the value specified in /etc/kernel/tries when a boot loader entry is first created.

USING SYSTEMD-BOOT IN VIRTUAL MACHINES

When using qemu with OVMF (UEFI Firmware for virtual machines) the -kernel switch works not only for linux kernels, but for any EFI binary, including sd-boot and unified linux kernels. Example command line for loading systemd-boot on x64:

qemu-system-x86_64 [ ... ] -kernel /usr/lib/systemd/boot/efi/systemd-bootx64.efi

systemd-boot will detect that it was started directly instead of being loaded from ESP and will search for the ESP in that case, taking into account boot order information from the hypervisor (if available).
