NOM

systemd-pcrphase.service, systemd-pcrphase-sysinit.service, systemd-pcrphase-initrd.service, systemd-pcrmachine.service, systemd-pcrfs-root.service, systemd-pcrfs@.service, systemd-pcrextend - Mesurer la phase de démarrage dans le PCR 11 de TPM2, l'ID machine et l'identité du système de fichiers dans le PCR 15

SYNOPIS

systemd-pcrphase.service

systemd-pcrphase-sysinit.service

systemd-pcrphase-initrd.service

systemd-pcrmachine.service

systemd-pcrfs-root.service

systemd-pcrfs@.service

/usr/lib/systemd/systemd-pcrextend [CHAINE]

DESCRIPTION

systemd-pcrphase.service, systemd-pcrphase-sysinit.service et systemd-pcrphase-initrd.service sont des services système qui mesurent des chaînes spécifiques dans le PCR 11 de TPM2 lors du démarrage, à divers jalons du processus de démarrage.

systemd-pcrmachine.service est un service système qui mesure l'ID machine (voir machine-id(5)) dans le PCR 15.

systemd-pcrfs-root.service et systemd-pcrfs@.service sont des services qui mesurent des informations d'identité de système de fichiers (c'est-à-dire point de montage, type de système de fichiers, label et UUID, label et UUID de partition) dans le PCR 15. systemd-pcrfs-root.service le fait pour le système de fichiers racine, systemd-pcrfs@.service est une unité modèle qui mesure plutôt le système de fichiers indiqué par son identifiant d'instance.

Ces services nécessitent l'utilisation de systemd-stub(7) dans une image de noyau unifiée (UKI). Ils n'exécutent aucune opération lorsque le stub n'a pas été utilisé pour invoquer le noyau. Le stub mesurera le noyau invoqué et les ressources vendor associées dans le PCR 11 avant de lui céder le contrôle ; une fois l'espace utilisateur invoqué, ces services étendront alors le PCR 11 de TPM2 avec certaines chaînes littérales indiquant les phases du processus de démarrage. Lors d'un processus de démarrage normal, le PCR 11 est étendu avec les chaînes suivantes :

1."enter-initrd" — tôt, lorsque l'initrd s'initialise, avant d'activer les images d'extension système pour l'initrd. Il agit comme une barrière entre le moment où le noyau s'initialise et celui où l'initrd commence à fonctionner et active les images d'extension système, c'est-à-dire le code expédié en dehors de l'UKI. (Cette extension se produit lorsque le service systemd-pcrphase-initrd.service(8) démarre.)
2."leave-initrd" — lorsque l'initrd est sur le point de passer au système de fichiers hôte. Il agit comme une barrière entre le code de l'initrd et le code du système d'exploitation hôte. (Cette extension se produit lorsque le service systemd-pcrphase-sysinit.service(8) s'arrête.)
3."sysinit" — lorsque l'initialisation système de base est terminée (ce qui inclut le montage des systèmes de fichiers locaux), et que le système commence à démarrer les services système réguliers. (Cette extension se produit lorsque le service systemd-pcrphase-sysinit.service(8) démarre.)
4."ready" — plus tard dans le processus de démarrage, après que les systèmes de fichiers distants aient été activés (c'est-à-dire après remote-fs.target), mais avant que les utilisateurs ne soient autorisés à se connecter (c'est-à-dire avant systemd-user-sessions.service). Il agit comme une barrière entre le moment où les utilisateurs réguliers non privilégiés sont toujours interdits de connexion et celui où ils sont autorisés à se connecter. (Cette extension se produit lorsque le service systemd-pcrphase-sysinit.service(8) démarre.)
5."shutdown" — lorsque l'arrêt du système commence. Il agit comme une barrière entre le moment où le système est pleinement opérationnel et celui où il s'apprête à s'arrêter. (Cette extension se produit lorsque le service systemd-pcrphase.service s'arrête.)
6."final" — à la fin de l'arrêt du système. Il agit comme une barrière entre le moment où le gestionnaire de services est toujours en cours d'exécution et celui où il passe à la phase d'arrêt finale où la gestion des services n'est plus disponible. (Cette extension se produit lorsque le service systemd-pcrphase-sysinit.service(8) s'arrête.)

Lors d'un cycle de vie système normal, le PCR 11 est étendu avec les chaînes "enter-initrd", "leave-initrd", "sysinit", "ready", "shutdown", et "final".

Les phases spécifiques du processus de démarrage peuvent être référencées via la série de chaînes mesurées, séparées par des deux-points (le "chemin de phase"). Par exemple, le chemin de phase pour le runtime système normal est "enter-initrd:leave-initrd:sysinit:ready", tandis que celui de l'initrd est simplement "enter-initrd". Le chemin de phase pour la phase de démarrage avant l'initrd est une chaîne vide ; comme cela est difficile à passer, un seul deux-points (":") peut être utilisé à la place. Notez que les six chaînes susmentionnées ne sont que les chaînes par défaut et que les systèmes individuels peuvent mesurer d'autres chaînes à d'autres moments, et ainsi implémenter des phases de démarrage différentes et plus granulaires pour y lier les politiques.

En liant des politiques d'objets TPM2 à un chemin de phase spécifique, il est possible de restreindre leur accès à des phases spécifiques du processus de démarrage, par exemple en rendant impossible l'accès à la clé de chiffrement du système de fichiers racine après que le système soit passé de l'initrd au système de fichiers racine hôte.

Utilisez systemd-measure(1) pour pré-calculer les valeurs PCR 11 attendues pour des phases de démarrage spécifiques (via le commutateur --phase=).

systemd-pcrfs-root.service et systemd-pcrfs@.service sont automatiquement tirés dans la transaction initiale par systemd-gpt-auto-generator(8) pour les systèmes de fichiers racine et /var/. systemd-fstab-generator(8) fera cela pour tous les montages avec l'option de montage x-systemd.pcrfs dans /etc/fstab.

OPTIONS

L'exécutable /usr/lib/systemd/system-pcrextend peut également être invoqué depuis la ligne de commande, où il attend le mot à étendre dans le PCR 11, ainsi que les commutateurs suivants :

--bank=

Prend les banques PCR dans lesquelles étendre le mot spécifié. Si non spécifié, l'outil détermine automatiquement toutes les banques PCR activées et mesure le mot dans toutes.

Ajouté dans la version 252.

--pcr=

Prend l'indice du PCR à étendre. Si --machine-id ou --file-system= sont spécifiés, la valeur par défaut est 15, sinon elle est 11.

Ajouté dans la version 255.

--tpm2-device=CHEMIN

Contrôle quel périphérique TPM2 utiliser. Attend un chemin de nœud de périphérique faisant référence à la puce TPM2 (par exemple, /dev/tpmrm0). Alternativement, la valeur spéciale "auto" peut être spécifiée, afin de déterminer automatiquement le nœud de périphérique d'un périphérique TPM2 adapté (dont il doit y avoir exactement un). La valeur spéciale "list" peut être utilisée pour énumérer tous les périphériques TPM2 adaptés actuellement découverts.

Ajouté dans la version 252.

--graceful

Si aucun firmware TPM2, sous-système noyau, pilote noyau ou support de périphérique n'est trouvé, sortir avec le code de sortie 0 (c'est-à-dire indiquer le succès). Si ce n'est pas spécifié, toute tentative de mesure sans périphérique TPM2 entraînera l'échec de l'invocation.

Ajouté dans la version 253.

--machine-id

Au lieu de mesurer un mot spécifié sur la ligne de commande dans le PCR 11, mesure l'ID machine de l'hôte dans le PCR 15.

Ajouté dans la version 253.

--file-system=

Au lieu de mesurer un mot spécifié sur la ligne de commande dans le PCR 11, mesure les informations d'identité du système de fichiers spécifié dans le PCR 15. Le paramètre doit être le chemin vers le point de montage établi du système de fichiers à mesurer.

Ajouté dans la version 253.

-h, --help

Affiche un bref texte d'aide et quitte.

--version

Affiche une courte chaîne de version et quitte.

FICHIERS

/run/log/systemd/tpm2-measure.log

Les mesures sont enregistrées dans un fichier journal d'événements maintenu dans /run/log/systemd/tpm2-measure.log, qui contient une série d'objets JSON-SEQ[1] suivant la structure générale des objets d'événement du Format de Journal d'Événements Canonique TCG (CEL-JSON)[2] (mais sans le champ "recnum").

Un verrou de fichier BSD LOCK_EX (flock(2

.fr'>flock(2) sur le fichier journal est acquise pendant que la mesure est effectuée et que le fichier est mis à jour. Ainsi, les applications qui ont l'intention d'acquérir une citation cohérente du TPM avec l'instantané associé du journal d'événements doivent acquérir un verrou LOCK_SH pendant ce processus.

Ajouté dans la version 252.
