SYSTEMD-SYSTEM.CONF(5) systemd-system.conf SYSTEMD-SYSTEM.CONF(5)

NOM

systemd-system.conf, system.conf.d, systemd-user.conf, user.conf.d - Fichiers de configuration du gestionnaire de services système et de session

SYNTAXE

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/system.conf.d/*.conf, /run/systemd/system.conf.d/*.conf, /usr/lib/systemd/system.conf.d/*.conf

~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf, /etc/systemd/user.conf.d/*.conf, /run/systemd/user.conf.d/*.conf, /usr/lib/systemd/user.conf.d/*.conf

DESCRIPTION

Lorsqu'il est exécuté en tant qu'instance système, systemd interprète le fichier de configuration system.conf et les fichiers des répertoires system.conf.d ; lorsqu'il est exécuté en tant qu'instance utilisateur, il interprète le fichier de configuration user.conf (par ordre de priorité, dans le répertoire personnel de l'utilisateur et sous /etc/systemd/, /run/systemd/, et /usr/lib/systemd/) et les fichiers des répertoires user.conf.d. Ces fichiers de configuration contiennent quelques paramètres contrôlant les opérations de base du gestionnaire.

Voir systemd.syntax(7) pour une description générale de la syntaxe.

RÉPERTOIRES DE CONFIGURATION ET PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation, donc aucune configuration n'est nécessaire sauf s'il est nécessaire de s'écarter de ces valeurs par défaut. Le fichier de configuration principal est chargé à partir de l'un des répertoires listés par ordre de priorité, seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du vendeur du fichier contient des entrées commentées montrant les valeurs par défaut comme guide pour l'administrateur. Des remplacements locaux peuvent également être créés en créant des fichiers drop-in, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cet effet (ou une copie dans /etc/ s'il est livré sous /etc/), cependant, l'utilisation de fichiers drop-in pour la configuration locale est recommandée plutôt que des modifications du fichier de configuration principal.

En plus du fichier de configuration principal, des extraits de configuration drop-in sont lus à partir de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, et /etc/systemd/*.conf.d/. Ces fichiers drop-in ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers des sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier dans l'ordre lexicographique, quel que soit le sous-répertoire dans lequel ils résident. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée dans le fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées telles qu'elles apparaissent dans les fichiers triés.

Lorsque des paquets doivent personnaliser la configuration, ils peuvent installer des fichiers drop-in sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets vendeurs. Des fichiers drop-in doivent être utilisés pour remplacer les fichiers drop-in des paquets, car le fichier de configuration principal a une priorité plus basse. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un numéro à deux chiffres et un trait d'union, pour simplifier l'ordre. Cela définit également un concept de priorités de fichiers drop-in pour permettre aux fournisseurs de systèmes d'exploitation de livrer des fichiers drop-in dans une plage spécifique inférieure à la plage utilisée par les utilisateurs. Cela devrait réduire le risque que les fichiers drop-in des paquets remplacent accidentellement les fichiers drop-in définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les fichiers drop-in dans /usr/ et la plage 60-90 pour les fichiers drop-in dans /etc/ et /run/, afin de s'assurer que les fichiers drop-in locaux et transitoires prennent la priorité sur les fichiers drop-in fournis par le vendeur du système d'exploitation.

Pour désactiver un fichier de configuration fourni par le vendeur, la méthode recommandée consiste à placer un lien symbolique vers /dev/null dans le répertoire de configuration de /etc/, avec le même nom de fichier que le fichier de configuration du vendeur.

OPTIONS

Toutes les options sont configurées dans la section [Manager] :

LogColor=, LogLevel=, LogLocation=, LogTarget=, LogTime=, DumpCore=yes, CrashChangeVT=no, CrashShell=no, CrashAction=freeze, ShowStatus=yes, DefaultStandardOutput=journal, DefaultStandardError=inherit

Configure divers paramètres des opérations de base du gestionnaire. Ces options peuvent être remplacées par les arguments respectifs du processus et de la ligne de commande du noyau. Voir systemd(1) pour plus de détails.

Ajouté dans la version 198.

CtrlAltDelBurstAction=

Définit l'action qui sera effectuée si l'utilisateur appuie plus de 7 fois sur Ctrl-Alt-Suppr en 2 secondes. Peut être défini sur "reboot-force", "poweroff-force", "reboot-immediate", "poweroff-immediate" ou désactivé avec "none". La valeur par défaut est "reboot-force".

Ajouté dans la version 232.

StatusUnitFormat=

Accepte name, description ou combined comme valeur. Si name, le gestionnaire système utilisera les noms d'unités dans les messages d'état (par exemple, "systemd-journald.service"), au lieu des descriptions plus longues et plus informatives définies avec Description= (par exemple, "Journal Logging Service"). Si combined, le gestionnaire système utilisera à la fois les noms d'unités et les descriptions dans les messages d'état (par exemple, "systemd-journald.service - Journal Logging Service").

Voir systemd.unit(5) pour plus de détails sur les noms d'unités et Description=.

Ajouté dans la version 243.

DefaultTimerAccuracySec=

Définit la précision par défaut des unités de minuterie. Cela contrôle la valeur par défaut globale du paramètre AccuracySec= des unités de minuterie, voir systemd.timer(5) pour plus de détails. AccuracySec= défini dans des unités individuelles remplace la valeur par défaut globale pour l'unité spécifique. La valeur par défaut est 1 minute. Notez que la précision des unités de minuterie est également affectée par le délai d'attente de minuterie configuré pour PID 1, voir TimerSlackNSec= ci-dessus.

Ajouté dans la version 212.

GESTION DES RESSOURCES

TimerSlackNSec=

Définit le délai d'attente de la minuterie en nanosecondes pour PID 1, qui est hérité par tous les processus exécutés, sauf s'il est remplacé individuellement, par exemple avec le paramètre TimerSlackNSec= dans les unités de service (voir systemd.exec(5) pour plus de détails). Le délai d'attente de la minuterie contrôle la précision des réveils déclenchés par les minuteries du système. Voir prctl(2) pour plus d'informations. Notez que contrairement à la plupart des autres définitions de périodes de temps, ce paramètre prend une valeur entière en nanosecondes si aucune unité n'est spécifiée. Les unités de temps habituelles sont également comprises.

Ajouté dans la version 198.

CPUAffinity=

Configure l'affinité CPU pour le gestionnaire de services ainsi que l'affinité CPU par défaut pour tous les processus dérivés. Prend une liste d'indices ou de plages de CPU séparés par des espaces ou des virgules. Les plages de CPU sont spécifiées par les indices de CPU inférieur et supérieur séparés par un tiret. Cette option peut être spécifiée plusieurs fois, auquel cas les masques d'affinité CPU spécifiés sont fusionnés. Si la chaîne vide est attribuée, le masque est réinitialisé, toutes les attributions antérieures n'auront aucun effet. Les services individuels peuvent remplacer l'affinité CPU pour leurs processus avec le paramètre CPUAffinity= dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 198.

NUMAPolicy=

Configure la politique mémoire NUMA pour le gestionnaire de services et la politique mémoire NUMA par défaut pour tous les processus dérivés. Les services individuels peuvent remplacer la politique par défaut avec le paramètre NUMAPolicy= dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 243.

NUMAMask=

Configure le masque de nœud NUMA qui sera associé à la politique NUMA sélectionnée. Notez que les politiques NUMA default et local ne nécessitent pas de masque de nœud NUMA explicite et que la valeur de l'option peut être vide. Similairement à NUMAPolicy=, la valeur peut être remplacée par des services individuels dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 243.

DefaultMemoryAccounting=, DefaultTasksAccounting=, DefaultIOAccounting=, DefaultIPAccounting=

MemoryAccounting=, TasksAccounting=, IOAccounting= et IPAccounting=. Voir systemd.resource-control(5) pour les détails sur les paramètres par unité.

DefaultMemoryAccounting= est défini par défaut sur yes. DefaultTasksAccounting= est défini par défaut sur yes. Les autres paramètres sont définis par défaut sur no.

Ajouté dans la version 211.

DefaultTasksMax=

Configure la valeur par défaut du paramètre par unité TasksMax=. Voir systemd.resource-control(5) pour les détails. Ce paramètre s'applique à tous les types d'unités qui prennent en charge les paramètres de contrôle des ressources, à l'exception des unités de type slice. La valeur par défaut est 15 % du minimum de kernel.pid_max=, kernel.threads-max= et pids.max du cgroup racine. Le noyau a une valeur par défaut pour kernel.pid_max= et un algorithme de comptage dans le cas de plus de 32 cœurs. Par exemple, avec la valeur par défaut kernel.pid_max=, DefaultTasksMax= est par défaut à 4915, mais peut être plus grand sur d'autres systèmes ou plus petit dans les conteneurs OS.

Ajouté dans la version 228.

DefaultLimitCPU=, DefaultLimitFSIZE=, DefaultLimitDATA=, DefaultLimitSTACK=, DefaultLimitCORE=, DefaultLimitRSS=, DefaultLimitNOFILE=, DefaultLimitAS=, DefaultLimitNPROC=, DefaultLimitMEMLOCK=, DefaultLimitLOCKS=, DefaultLimitSIGPENDING=, DefaultLimitMSGQUEUE=, DefaultLimitNICE=, DefaultLimitRTPRIO=, DefaultLimitRTTIME=

Ces paramètres contrôlent diverses limites de ressources par défaut pour les processus exécutés par les unités. Voir setrlimit(2) pour les détails. Ces paramètres peuvent être remplacés dans des unités individuelles en utilisant les directives LimitXXX= correspondantes et ils acceptent la même syntaxe de paramètre, voir systemd.exec(5) pour les détails. Notez que ces limites de ressources ne sont que des valeurs par défaut pour les unités, elles ne sont pas appliquées au processus du gestionnaire de services (c'est-à-dire PID 1) lui-même.

La plupart de ces paramètres ne sont pas définis, ce qui signifie que les limites de ressources sont héritées du noyau ou, si invoqués dans un conteneur, du gestionnaire de conteneur. Cependant, les suivants ont des valeurs par défaut :

•DefaultLimitNOFILE= est par défaut à 1024:524288.
•DefaultLimitMEMLOCK= est par défaut à 8M.
•DefaultLimitCORE= n'a pas de valeur par défaut mais il convient de mentionner que RLIMIT_CORE est défini sur "infinity" par PID 1 qui est hérité par ses enfants.

Notez que le gestionnaire de services, en interne dans PID 1, augmente RLIMIT_NOFILE et RLIMIT_MEMLOCK à des valeurs plus élevées, cependant la limite est rétablie aux valeurs par défaut mentionnées pour tous les processus enfants issus.

Ajouté dans la version 198.

DefaultOOMPolicy=

Configure la politique par défaut pour réagir aux processus tués par le tueur Out-Of-Memory (OOM) de Linux ou systemd-oomd. Cela peut être utilisé pour choisir une valeur par défaut globale pour le paramètre par unité OOMPolicy=. Voir systemd.service(5) pour les détails. Notez que cette valeur par défaut n'est pas utilisée pour les services dont Delegate= est activé.

Ajouté dans la version 243.

DefaultOOMScoreAdjust=

Configure les ajustements de score OOM par défaut des processus exécutés par le gestionnaire de services. Par défaut, cette option n'est pas définie (ce qui signifie que les processus issus héritent de la valeur d'ajustement du score OOM du gestionnaire de services), sauf si le gestionnaire de services est exécuté pour un utilisateur non privilégié, auquel cas il est par défaut égal à la valeur d'ajustement OOM du gestionnaire de services plus 100 (cela rend les processus de service légèrement plus susceptibles d'être tués sous pression mémoire que le gestionnaire lui-même). Cela peut être utilisé pour choisir une valeur par défaut globale pour le paramètre par unité OOMScoreAdjust=. Voir systemd.exec(5) pour les détails. Notez que ce paramètre n'a aucun effet sur la valeur d'ajustement du score OOM du processus du gestionnaire de services lui-même, il conserve la valeur d'origine définie lors de son invocation.

Ajouté dans la version 250.

DefaultMemoryPressureWatch=, DefaultMemoryPressureThresholdSec=

Configure les paramètres par défaut pour les paramètres par unité MemoryPressureWatch= et MemoryPressureThresholdSec=. Voir systemd.resource-control(5) pour les détails. Par défaut, "auto" et "200ms", respectivement. Cela définit également le seuil de surveillance de la pression mémoire pour le gestionnaire de services lui-même.

Ajouté dans la version 254.

SURVEILLANCE MATÉRIELLE

RuntimeWatchdogSec=, RebootWatchdogSec=, KExecWatchdogSec=

Configure la surveillance matérielle à l'exécution et au redémarrage. Prend une valeur de délai en secondes (ou dans d'autres unités de temps si suffixée par "ms", "min", "h", "d", "w"), ou les chaînes spéciales "off" ou "default". Si définie sur "off" (alternativement : "0"), la logique de surveillance est désactivée : aucun périphérique de surveillance n'est ouvert, configuré ou contacté. Si définie sur la chaîne spéciale "default", la surveillance est ouverte et contactée à intervalles réguliers, mais le délai n'est pas modifié par rapport à la valeur par défaut. Si définie sur une autre valeur temporelle, le délai de surveillance est configuré sur la valeur spécifiée (ou une valeur proche, selon les capacités matérielles).

Si RuntimeWatchdogSec= est défini sur une valeur non nulle, le matériel de surveillance (/dev/watchdog0 ou le chemin spécifié avec WatchdogDevice= ou l'option du noyau systemd.watchdog_device=) sera programmé pour redémarrer automatiquement le système s'il n'est pas contacté dans le délai spécifié. Le gestionnaire système s'assurera de le contacter au moins une fois dans la moitié du délai spécifié. Cette fonctionnalité nécessite la présence d'un périphérique de surveillance matérielle, comme c'est souvent le cas dans les systèmes embarqués et les serveurs. Tous les matériels de surveillance ne permettent pas la configuration de toutes les valeurs de délai de redémarrage possibles, auquel cas la valeur de délai disponible la plus proche est choisie.

RebootWatchdogSec= peut être utilisé pour configurer la surveillance matérielle lorsque le système est invité à redémarrer. Il fonctionne comme une mesure de sécurité pour garantir que le redémarrage a lieu même si une tentative de redémarrage propre expire. Notez que le délai RebootWatchdogSec= s'applique uniquement à la deuxième phase du redémarrage, c'est-à-dire après que tous les services réguliers sont déjà terminés, et après que le processus du système et du gestionnaire de services (PID 1) a été remplacé par le binaire systemd-shutdown, voir le manuel bootup(7) pour les détails. Pendant la première phase de l'opération d'arrêt, le système et le gestionnaire de services restent en cours d'exécution et donc RuntimeWatchdogSec= est toujours respecté. Afin de définir un délai pour cette première phase de l'arrêt du système, configurez JobTimeoutSec= et JobTimeoutAction= dans la section [Unit] de l'unité shutdown.target. Par défaut, RuntimeWatchdogSec= est égal à 0 (désactivé), et RebootWatchdogSec= à 10 minutes.

KExecWatchdogSec= peut être utilisé pour activer la surveillance lors de l'exécution de kexec plutôt que lors d'un redémarrage. Notez que si le noyau ne réinitialise pas la surveillance lors de kexec (selon le matériel et/ou le pilote spécifique), dans ce cas la surveillance peut ne pas être désactivée après un kexec réussi et donc le système pourrait redémarrer, sauf si RuntimeWatchdogSec= est également activé en même temps. Pour cette raison, il est recommandé d'activer KExecWatchdogSec= uniquement si RuntimeWatchdogSec= est également activé.

Ces paramètres n'ont aucun effet si un dispositif de surveillance matérielle n'est pas disponible.

Ajouté dans la version 198.

RuntimeWatchdogPreSec=

Configure la valeur de pré-délai du périphérique de surveillance matérielle. Prend une valeur de délai en secondes (ou dans d'autres unités de temps similaires à RuntimeWatchdogSec=). Un pré-délai de surveillance est une notification générée par la surveillance avant que la réinitialisation de la surveillance ne se produise si la surveillance n'a pas été entretenue. Cette notification est gérée par le noyau et peut être configurée pour effectuer une action (c'est-à-dire générer un panic du noyau) en utilisant RuntimeWatchdogPreGovernor=. Tout le matériel de surveillance ou tous les pilotes ne prennent pas en charge la génération d'un pré-délai et, selon l'état du système, le noyau peut être incapable d'effectuer l'action configurée avant le redémarrage de la surveillance. La surveillance sera configurée pour générer l'événement de pré-délai au temps spécifié par RuntimeWatchdogPreSec= avant le délai de surveillance d'exécution (défini par RuntimeWatchdogSec=). Par exemple, si nous avons RuntimeWatchdogSec=30 et RuntimeWatchdogPreSec=10, alors l'événement de pré-délai se produira si la surveillance n'a pas été contactée pendant 20 secondes (10 secondes avant que la surveillance ne se déclenche). Par défaut, RuntimeWatchdogPreSec= est égal à 0 (désactivé). La valeur définie pour RuntimeWatchdogPreSec= doit être inférieure à la valeur de délai pour RuntimeWatchdogSec=. Ce paramètre n'a aucun effet si un dispositif de surveillance matérielle n'est pas disponible ou si le dispositif de surveillance matérielle ne prend pas en charge un pré-délai et sera ignoré par le noyau si le paramètre est supérieur au délai de surveillance réel.

Ajouté dans la version 251.

RuntimeWatchdogPreGovernor=

Configure l'action effectuée par le périphérique de surveillance matérielle lorsque le pré-délai expire. L'action par défaut pour l'événement de pré-délai dépend de la configuration du noyau, mais il s'agit généralement d'un message du noyau journalisé. Pour une liste des actions valides disponibles pour un périphérique de surveillance donné, vérifiez le contenu du fichier /sys/class/watchdog/watchdogX/pretimeout_available_governors. Généralement, les types de gouverneurs disponibles sont noop et panic. La disponibilité, les noms et les fonctionnalités peuvent varier en fonction du pilote de périphérique spécifique utilisé. Si le fichier sysfs pretimeout_available_governors est vide, le gouverneur peut être intégré en tant que module du noyau et peut nécessiter d'être chargé manuellement (par exemple, pretimeout_noop.ko), ou le périphérique de surveillance peut ne pas prendre en charge les pré-délais.

Ajouté dans la version 251.

WatchdogDevice=

Configure le périphérique de surveillance matérielle que les minuteurs de surveillance d'exécution et d'arrêt ouvriront et utiliseront. Par défaut, /dev/watchdog0. Ce paramètre n'a aucun effet si un dispositif de surveillance matérielle n'est pas disponible.

Ajouté dans la version 236.

SÉCURITÉ

CapabilityBoundingSet=

Contrôle quelles capacités inclure dans l'ensemble des limites de capacités pour PID 1 et ses enfants. Voir capabilities(7) pour les détails. Prend une liste de noms de capacités séparés par des espaces, telle que lue par cap_from_name(3). Les capacités listées seront incluses dans l'ensemble des limites, toutes les autres seront supprimées. Si la liste des capacités est précédée de ~,
toutes les capacités sauf celles listées seront incluses, l'effet de l'assignation étant inversé. Notez que cette option affecte également les capacités respectives dans les ensembles de capacités effectives, permises et héritables. L'ensemble des capacités de limitation peut également être configuré individuellement pour les unités en utilisant la directive CapabilityBoundingSet= pour les unités, mais notez que les capacités supprimées pour PID 1 ne peuvent pas être regagnées dans les unités individuelles, elles sont perdues définitivement.

Ajouté dans la version 198.

NoNewPrivileges=

Accepte un argument booléen. Si vrai, garantit que PID 1 et tous ses enfants ne pourront jamais acquérir de nouveaux privilèges via execve(2) (par exemple, via les bits setuid ou setgid, ou les capacités du système de fichiers). Par défaut, la valeur est fausse. Les distributions généralistes s'appuient couramment sur des exécutables avec des bits setuid ou setgid et ne fonctionneront donc pas correctement avec cette option activée. Les unités individuelles ne peuvent pas désactiver cette option. Voir également le **drapeau No New Privileges**[2].

Ajouté dans la version 239.

ProtectSystem=

Accepte un argument booléen ou la chaîne de caractères « auto ». Si réglé sur vrai, remonte /usr/ en lecture seule. Si réglé sur « auto » (par défaut) et exécuté dans un initrd, équivalent à vrai, sinon faux. Cela implémente un sous-ensemble restreint du réglage par unité du même nom, voir systemd.exec(5) pour les détails : actuellement, les valeurs « full » ou « strict » ne sont pas supportées.

Ajouté dans la version 256.

SystemCallArchitectures=

Accepte une liste d'identifiants d'architecture séparés par des espaces. Sélectionne à partir de quelles architectures les appels système peuvent être invoqués sur ce système. Ceci peut être utilisé comme un moyen efficace de désactiver l'invocation de binaires non natifs au niveau du système, par exemple pour interdire l'exécution de binaires x86 32 bits sur des systèmes x86-64 64 bits. Cette option fonctionne au niveau du système et agit de manière similaire au réglage SystemCallArchitectures= des fichiers d'unité, voir systemd.exec(5) pour les détails. Ce réglage par défaut est une liste vide, auquel cas aucun filtrage d'appels système basé sur l'architecture n'est appliqué. Les identifiants d'architecture connus sont « x86 », « x86-64 », « x32 », « arm » et l'identifiant spécial « native ». Ce dernier est implicitement mappé à l'architecture native du système (ou plus précisément, à l'architecture pour laquelle le gestionnaire système a été compilé). Réglez ce paramètre sur « native » pour interdire l'exécution de tout binaire non natif. Lorsqu'un binaire exécute un appel système d'une architecture qui n'est pas listée dans ce réglage, il sera immédiatement terminé avec le signal SIGSYS.

Ajouté dans la version 209.

DefaultSmackProcessLabel=

Accepte une étiquette de sécurité SMACK64 comme argument. Le processus exécuté par une unité sera démarré sous cette étiquette si SmackProcessLabel= n'est pas défini dans l'unité. Voir systemd.exec(5) pour les détails.

Si la valeur est « / », seules les étiquettes spécifiées avec SmackProcessLabel= sont assignées et la valeur par défaut à la compilation est ignorée.

Ajouté dans la version 252.

DefaultRestrictSUIDSGID=

Accepte un argument booléen. Ceci est utilisé comme valeur par défaut pour les unités qui n'ont pas de définition explicite pour RestrictSUIDSGID=. Voir systemd.exec(5) pour les détails.

Ajouté dans la version 258.

TEMPORISATIONS ET LIMITES DE TAUX

DefaultTimeoutStartSec=, DefaultTimeoutStopSec=, DefaultTimeoutAbortSec=, DefaultRestartSec=

Configure les temporisations par défaut pour le démarrage, l'arrêt et l'abandon des unités, ainsi que le temps par défaut pour attendre entre les redémarrages automatiques des unités, tels que configurés par unité dans TimeoutStartSec=, TimeoutStopSec=, TimeoutAbortSec= et RestartSec= (pour les services, voir systemd.service(5) pour les détails sur les réglages par unité). Pour les unités non-service, DefaultTimeoutStartSec= définit la valeur par défaut de TimeoutSec=.

DefaultTimeoutStartSec= et DefaultTimeoutStopSec= valeur par défaut à 90 s dans le gestionnaire système et 90 s dans le gestionnaire utilisateur. DefaultTimeoutAbortSec= n'est pas défini par défaut afin que toutes les unités se rabattent sur TimeoutStopSec=. DefaultRestartSec= défaut à 100 ms.

Ajouté dans la version 209.

DefaultDeviceTimeoutSec=

Configure la temporisation par défaut pour l'attente des périphériques. Elle peut être modifiée par périphérique via l'option x-systemd.device-timeout= dans /etc/fstab et /etc/crypttab (voir systemd.mount(5), crypttab(5)). Par défaut à 90 s dans le gestionnaire système et 90 s dans le gestionnaire utilisateur.

Ajouté dans la version 252.

DefaultStartLimitIntervalSec=, DefaultStartLimitBurst=

Configure la limitation du taux de démarrage des unités par défaut, telle que configurée par service via StartLimitIntervalSec= et StartLimitBurst=. Voir systemd.service(5) pour les détails sur les réglages par service. DefaultStartLimitIntervalSec= défaut à 10 s. DefaultStartLimitBurst= défaut à 5.

Ajouté dans la version 209.

ReloadLimitIntervalSec=, ReloadLimitBurst=

Limitation du taux pour les requêtes daemon-reload et (depuis v256) daemon-reexec. Le réglage s'applique aux deux opérations, mais les limites de taux sont suivies séparément. Par défaut à non défini, et n'importe quel nombre d'opérations peut être demandé à tout moment. ReloadLimitIntervalSec= prend une valeur en secondes pour configurer la fenêtre de limite de taux, et ReloadLimitBurst= prend un entier positif pour configurer le nombre maximum d'opérations autorisées dans la fenêtre de temps configurée.

Ajouté dans la version 253.

ENVIRONNEMENT

DefaultEnvironment=

Configure les variables d'environnement passées à tous les processus exécutés. Accepte une liste d'affectations de variables séparées par des espaces. Voir environ(7) pour les détails sur les variables d'environnement. Ce bloc d'environnement est interne, et les changements ne sont pas reflétés dans /proc/PID/environ du gestionnaire.

Une expansion simple de spécificateur « % » est supportée, voir ci-dessous pour une liste des spécificateurs supportés.

Exemple :

DefaultEnvironment="VAR1=mot1 mot2" VAR2=mot3 "VAR3=mot 5 6"

Définit trois variables « VAR1 », « VAR2 », « VAR3 ».

Ajouté dans la version 205.

ManagerEnvironment=

Définit les variables d'environnement pour le processus gestionnaire lui-même. Accepte une liste d'affectations de variables séparées par des espaces dans le même format que DefaultEnvironment=, voir ci-dessus. Ces variables sont fusionnées dans le bloc d'environnement existant du processus gestionnaire. En particulier, dans le cas du gestionnaire système, ce bloc inclut les variables définies par le noyau basées sur la ligne de commande du noyau, et dans le cas du gestionnaire utilisateur, les variables passées par le gestionnaire système. Après que ces variables aient été fusionnées, elles persisteront jusqu'à être remplacées, même si le gestionnaire est rechargé ou réexécuté. Dans le cas du gestionnaire utilisateur, ces variables sont également héritées par les processus lancés par le gestionnaire. Comme avec DefaultEnvironment=, ce bloc d'environnement est interne, et les changements ne sont pas reflétés dans /proc/PID/environ du gestionnaire.

Définir des variables d'environnement pour le processus gestionnaire peut être utile pour modifier son comportement. Voir les **Variables d'Environnement Connues**[3] pour une description de certaines variables comprises par **systemd**.

Une expansion simple de spécificateur « % » est supportée, voir ci-dessous pour une liste des spécificateurs supportés.

Ajouté dans la version 248.

NOM

systemd.directives — directives pour les fichiers de configuration systemd

SYNOPIS

systemd.directives

DESCRIPTION

Les fichiers de configuration de systemd utilisent des directives pour configurer le comportement du système. Cette page de manuel décrit un sous-ensemble de directives couramment utilisées, qui sont disponibles dans la plupart des fichiers de configuration de systemd, y compris les unités, les fichiers d'environnement, les fichiers d'environnement de service, etc.

Les directives sont organisées en sections, généralement délimitées par des crochets [Section]. Chaque directive prend la forme MotClef=Valeur.

RÉPERTOIRES DE CONFIGURATION ET PRÉCÉDENCE

systemd recherche les fichiers de configuration dans plusieurs répertoires, en suivant un ordre de précédence défini. Les répertoires et fichiers qui sont définis dans le chemin suivant sont lus dans l'ordre. Les directives définies dans les fichiers ultérieurs remplacent celles des fichiers précédents.

Le chemin de configuration est le suivant :

  1. Le répertoire /etc/systemd/system/.
  2. Les répertoires *.conf.d sous /etc/systemd/system/.
  3. Le répertoire /run/systemd/system/.
  4. Les répertoires *.conf.d sous /run/systemd/system/.
  5. Le répertoire /usr/lib/systemd/system/.
  6. Les répertoires *.conf.d sous /usr/lib/systemd/system/.

Les fichiers de configuration à l'intérieur de ces répertoires sont lus dans l'ordre alphabétique.

Par exemple, les directives définies dans /etc/systemd/system/foo.service remplacent les directives du même nom dans /usr/lib/systemd/system/foo.service.

Voir systemd.unit(5) pour plus d'informations sur la précédence des fichiers de configuration.

OPTIONS

Les directives sont généralement spécifiques à la section dans laquelle elles apparaissent. Cependant, certaines directives sont disponibles dans plusieurs sections ou ont une signification globale.

Les directives courantes incluent:

Description=
Une description lisible par l'homme de l'unité. Cette chaîne peut être utilisée pour identifier l'unité dans les messages et les journaux.
Documentation=
Un ou plusieurs URL pointant vers une documentation supplémentaire concernant cette unité.
Requires=
Une liste d'autres unités qui doivent être démarrées avant que celle-ci ne puisse démarrer, et qui doivent être arrêtées si celle-ci est arrêtée. Si une unité requise échoue au démarrage, celle-ci échouera également.
Wants=
Similaire à Requires=, mais plus faible. Si une unité voulue échoue, cela n'affectera pas le démarrage de celle-ci.
BindsTo=
Similaire à Requires=, mais si l'unité liée est arrêtée, celle-ci sera également arrêtée. Si l'unité liée est supprimée, celle-ci sera également supprimée.
PartOf=
Définit une appartenance forte. Si l'unité fait partie d'une autre unité, alors l'arrêt ou le redémarrage de l'unité principale entraînera l'arrêt ou le redémarrage de celle-ci.
Conflicts=
Définit une relation de conflit. Si cette unité est démarrée, toutes les unités listées dans Conflicts= seront arrêtées, et vice versa.
Before=, After=
Contrôle l'ordre de démarrage. Before= garantit que cette unité démarre avant les unités spécifiées. After= garantit que cette unité démarre après les unités spécifiées.
OnFailure=
Liste des unités qui seront démarrées si cette unité échoue.
OnSuccess=
Liste des unités qui seront démarrées si cette unité réussit.

Vérifie si un fichier existe ou non avant de démarrer l'unité.
ConditionDirectoryNotEmpty=
Vérifie si un répertoire n'est pas vide.
ConditionCPUFeature=

ConditionHostName=

ConditionKernelCommandLine=

Une ou plusieurs unités dont l'arrêt désactivera également cette unité.
