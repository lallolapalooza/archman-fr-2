NOM

systemd-cryptsetup-generator - Générateur d'unités pour /etc/crypttab

SYNTAXE

/usr/lib/systemd/system-generators/systemd-cryptsetup-generator

DESCRIPTION

systemd-cryptsetup-generator est un générateur qui traduit /etc/crypttab en unités systemd natives tôt au démarrage et lorsque la configuration du gestionnaire système est rechargée. Cela créera des unités systemd-cryptsetup@.service(8) au besoin.

systemd-cryptsetup-generator implémente systemd.generator(7).

LIGNE DE COMMANDE DU NOYAU

systemd-cryptsetup-generator comprend les paramètres de ligne de commande du noyau suivants :

luks=, rd.luks=

Prend un argument booléen. Par défaut, "yes". Si "no", désactive complètement le générateur. rd.luks= est pris en compte uniquement dans l'initrd tandis que luks= est pris en compte à la fois par le système principal et dans l'initrd.

Ajouté dans la version 186.

luks.crypttab=, rd.luks.crypttab=

Prend un argument booléen. Par défaut, "yes". Si "no", fait en sorte que le générateur ignore tous les périphériques configurés dans /etc/crypttab (luks.uuid= fonctionnera toujours cependant). rd.luks.crypttab= est pris en compte uniquement dans l'initrd tandis que luks.crypttab= est pris en compte à la fois par le système principal et dans l'initrd.

Ajouté dans la version 186.

luks.uuid=, rd.luks.uuid=

Prend un UUID de superblock LUKS comme argument. Cela activera le périphérique spécifié dans le processus de démarrage comme s'il était listé dans /etc/crypttab. Cette option peut être spécifiée plusieurs fois afin de configurer plusieurs périphériques. rd.luks.uuid= est pris en compte uniquement dans l'initrd, tandis que luks.uuid= est pris en compte à la fois par le système principal et dans l'initrd.

Si /etc/crypttab contient des entrées avec le même UUID, alors le nom, le fichier clé et les options spécifiés ici seront utilisés. Sinon, le périphérique portera le nom "luks-UUID".

Si /etc/crypttab existe, seuls les UUIDs spécifiés sur la ligne de commande du noyau seront activés dans l'initrd ou la racine réelle.

Ajouté dans la version 186.

luks.name=, rd.luks.name=

Prend un UUID de superblock LUKS suivi d'un "=" et d'un nom. Ceci implique rd.luks.uuid= ou luks.uuid= et fera en plus apparaître le périphérique LUKS donné par l'UUID sous le nom fourni.

Ce paramètre est l'analogue du premier champ de crypttab(5) nom-volume.

rd.luks.name= est pris en compte uniquement dans l'initrd, tandis que luks.name= est pris en compte à la fois par le système principal et dans l'initrd.

Ajouté dans la version 218.

luks.data=, rd.luks.data=

Prend un UUID de superblock LUKS suivi d'un "=" et d'une spécification de périphérique bloc pour le périphérique hébergeant les données cryptées.

Pour les entrées spécifiées avec rd.luks.uuid= ou luks.uuid=, le périphérique de données sera défini sur celui spécifié par rd.luks.data= ou luks.data= de l'UUID correspondant.

Le paramètre de périphérique de données LUKS est utile pour spécifier des périphériques de données cryptées avec des en-têtes séparés spécifiés dans l'entrée luks.options contenant l'argument "header=". Par exemple, rd.luks.uuid=b40f1abf-2a53-400a-889a-2eccc27eaa40 rd.luks.options=b40f1abf-2a53-400a-889a-2eccc27eaa40=header=/chemin/vers/luks.hdr rd.luks.data=b40f1abf-2a53-400a-889a-2eccc27eaa40=/dev/sdx. Par conséquent, dans ce cas, nous tenterons de déverrouiller le périphérique LUKS assemblé à partir du périphérique de données "/dev/sdx" et de l'en-tête LUKS (métadonnées) placé dans le fichier "/chemin/vers/luks.hdr". Cette syntaxe n'est actuellement prise en charge que par périphérique, c'est-à-dire que vous devez spécifier l'UUID du périphérique LUKS.

Ce paramètre est l'analogue du deuxième champ de crypttab(5) périphérique-chiffré.

rd.luks.data= est pris en compte uniquement dans l'initrd, tandis que luks.data= est pris en compte à la fois par le système principal et dans l'initrd.

Ajouté dans la version 247.

luks.key=, rd.luks.key=

Prend un nom de fichier mot de passe ou un UUID de superblock LUKS suivi d'un "=" et d'un nom de fichier mot de passe comme argument.

Pour les entrées spécifiées avec rd.luks.uuid= ou luks.uuid=, le fichier mot de passe sera défini sur celui spécifié par rd.luks.key= ou luks.key= de l'UUID correspondant, ou le fichier mot de passe qui a été spécifié sans UUID.

Il est également possible de spécifier un périphérique externe qui devrait être monté avant que nous tentions de déverrouiller le périphérique LUKS. systemd-cryptsetup utilisera le fichier mot de passe stocké sur ce périphérique. Le périphérique contenant le fichier mot de passe est spécifié en ajoutant deux points et un identifiant de périphérique au chemin du fichier mot de passe. Par exemple, rd.luks.uuid=b40f1abf-2a53-400a-889a-2eccc27eaa40 rd.luks.key=b40f1abf-2a53-400a-889a-2eccc27eaa40=/fichiercle:LABEL=peripherique_cle. Par conséquent, dans ce cas, nous tenterons de monter le système de fichiers résidant sur le périphérique bloc avec le label "peripherique_cle". Cette syntaxe n'est actuellement prise en charge que par périphérique, c'est-à-dire que vous devez spécifier l'UUID du périphérique LUKS.

Ce paramètre est l'analogue du troisième champ de crypttab(5) fichier-clé.

rd.luks.key= est pris en compte uniquement dans l'initrd, tandis que luks.key= est pris en compte à la fois par le système principal et dans l'initrd.

Ajouté dans la version 202.

luks.options=, rd.luks.options=

Prend un UUID de superblock LUKS suivi d'un "=" et d'une chaîne d'options séparées par des virgules comme argument. Cela remplacera les options pour l'UUID donné.

Si seule une liste d'options, sans UUID, est spécifiée, elles s'appliquent à tout UUID non spécifié ailleurs, et sans entrée dans /etc/crypttab.

Ce paramètre est l'analogue du quatrième champ de crypttab(5) options.

Il est possible de spécifier un périphérique externe qui devrait être monté avant que nous tentions de déverrouiller le périphérique LUKS. systemd-cryptsetup assemblera le périphérique LUKS en combinant le périphérique de données spécifié dans luks.data avec l'en-tête LUKS détaché trouvé dans l'argument "header=". Par exemple, rd.luks.uuid=b40f1abf-2a53-400a-889a-2eccc27eaa40 rd.luks.options=b40f1abf-2a53-400a-889a-2eccc27eaa40=header=/luks.hdr:LABEL=devhdr rd.luks.data=b40f1abf-2a53-400a-889a-2eccc27eaa40=/dev/sdx. Par conséquent, dans ce cas, nous tenterons de monter le système de fichiers résidant sur le périphérique bloc avec le label "devhdr", et de chercher "luks.hdr" sur ce système de fichiers. Cet en-tête sera utilisé pour déverrouiller (déchiffrer) les données cryptées stockées sur /dev/sdx. Cette syntaxe n'est actuellement prise en charge que par périphérique, c'est-à-dire que vous devez spécifier l'UUID du périphérique LUKS.

rd.luks.options= est pris en compte uniquement par le disque RAM initial (initrd) tandis que luks.options= est pris en compte à la fois par le système principal et dans l'initrd.

Ajouté dans la version 208.
