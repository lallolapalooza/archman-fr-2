USER@.SERVICE(5) user@.service USER@.SERVICE(5)

NOM

user@.service, user-runtime-dir@.service, systemd-user-runtime-dir - Services système pour démarrer le gestionnaire utilisateur

SYNTAXE

user@UID.service

user-runtime-dir@UID.service

/usr/lib/systemd/systemd-user-runtime-dir

user-UID.slice

DESCRIPTION

Le gestionnaire système systemd(1) (PID 1) démarre des instances du gestionnaire utilisateur sous le nom user@UID.service, en utilisant l'UID numérique de l'utilisateur comme identifiant d'instance. Ces instances utilisent le même exécutable que le gestionnaire système, mais exécuté dans un mode où il démarre un ensemble différent d'unités. Chaque instance de systemd --user gère une hiérarchie d'unités spécifiques à cet utilisateur. Voir systemd(1) pour une discussion sur les unités et systemd.special(7) pour une liste des unités qui constituent la base des hiérarchies d'unités système et utilisateur.

user@UID.service est accompagné par l'unité système user-runtime-dir@UID.service, qui crée le répertoire d'exécution de l'utilisateur /run/user/UID lors de son démarrage et le supprime lors de son arrêt. Il peut également appliquer des limites de quota d'exécution sur /tmp/ et/ou /dev/shm/ pour l'utilisateur. user-runtime-dir@UID.service exécute le binaire systemd-user-runtime-dir pour effectuer le travail réel.

Les processus utilisateur peuvent être démarrés par l'instance user@.service, auquel cas ils feront partie de cette unité dans la hiérarchie système. Ils peuvent également être démarrés ailleurs, par exemple par sshd(8) ou un gestionnaire d'affichage comme gdm, auquel cas ils forment une unité .scope (voir systemd.scope(5)). Les deux, user@UID.service et les unités scope, sont regroupés sous user-UID.slice.

Les slices individuelles user-UID.slice sont regroupées sous user.slice, voir systemd.special(7).

CONTRÔLE DES RESSOURCES POUR LES UTILISATEURS CONNECTÉS

Les options qui contrôlent les ressources disponibles pour les utilisateurs connectés peuvent être configurées à plusieurs niveaux. Comme décrit dans la section précédente, user.slice contient les processus de tous les utilisateurs, donc toute limite de ressources sur cette slice s'applique à tous les utilisateurs ensemble. La méthode habituelle pour les configurer serait via des drop-ins, par exemple /etc/systemd/system/user.slice.d/resources.conf.

Les processus d'un seul utilisateur sont regroupés sous user-UID.slice. Les limites de ressources pour cet utilisateur peuvent être configurées via des drop-ins pour cette unité, par exemple /etc/systemd/system/user-1000.slice.d/resources.conf. Si les limites doivent s'appliquer à tous les utilisateurs, elles peuvent être configurées via des drop-ins pour le nom d'unité tronqué, user-.slice. Par exemple, la configuration dans /etc/systemd/system/user-.slice.d/resources.conf est incluse dans toutes les unités user-UID.slice, voir systemd.unit(5) pour une discussion sur le mécanisme des drop-ins.

Lorsqu'un utilisateur se connecte et qu'une unité .scope est créée pour la session (voir section précédente), la création du scope peut être gérée par pam_systemd(8). Ce module PAM communique avec systemd-logind(8) pour créer le scope de session et fournir un accès aux ressources matérielles. Les limites de ressources pour le scope peuvent être configurées via la configuration du module PAM, voir pam_systemd(8). Leur configuration via la configuration normale des unités est également possible, mais comme le nom de l'unité slice est généralement imprévisible, c'est moins utile.

En général, toutes les ressources qui s'appliquent aux unités peuvent être définies pour user@UID.service et les unités slice discutées ci-dessus, voir systemd.resource-control(5) pour un aperçu.

EXEMPLES

Exemple 1. Hiérarchie des groupes de contrôle avec deux utilisateurs connectés

$ systemd-cgls
Control group /:
-.slice
├─user.slice
│ ├─user-1000.slice
│ │ ├─user@1000.service
│ │ │ ├─pulseaudio.service
│ │ │ │ └─2386 /usr/bin/pulseaudio --daemonize=no
│ │ │ └─gnome-terminal-server.service
│ │ │   └─init.scope
│ │ │     ├─ 4127 /usr/libexec/gnome-terminal-server
│ │ │     └─ 4198 zsh
│ │ └─session-4.scope
│ │   ├─ 1264 gdm-session-worker [pam/gdm-password]
│ │   ├─ 2339 /usr/bin/gnome-shell
│ │   ...
│ │ ├─session-19.scope
│ │   ├─6497 sshd: zbyszek [priv]
│ │   ├─6502 sshd: zbyszek@pts/6
│ │   ├─6509 -zsh
│ │   └─6602 systemd-cgls --no-pager
│ ...
│ └─user-1001.slice
│   ├─session-20.scope
│   │ ├─6675 sshd: guest [priv]
│   │ ├─6708 sshd: guest@pts/6
│   │ └─6717 -bash
│   └─user@1001.service
│     ├─init.scope
│     │ ├─6680 /usr/lib/systemd/systemd --user
│     │ └─6688 (sd-pam)
│     └─sleep.service
│       └─6706 /usr/bin/sleep 30
...

L'utilisateur avec l'UID 1000 est connecté via gdm (session-4.scope) et ssh(1) (session-19.scope), et a également une instance de gestionnaire utilisateur en cours d'exécution (user@1000.service). L'utilisateur avec l'UID 1001 est connecté via ssh (session-20.scope) et a également une instance de gestionnaire utilisateur en cours d'exécution (user@1001.service). Ce sont toutes des unités système (feuilles), et elles font partie de la hiérarchie des slices, avec user-1000.slice et user-1001.slice sous user.slice. Les unités utilisateur sont visibles sous les instances user@.service (pulseaudio.service, gnome-terminal-server.service, init.scope, sleep.service).

Exemple 2. Limites de ressources utilisateur par défaut

$ systemctl cat user-1000.slice
# /usr/lib/systemd/system/user-.slice.d/10-defaults.conf
# ...
[Unit]
Description=User Slice of UID %j
After=systemd-user-sessions.service
[Slice]
TasksMax=33%

Les unités user-UID.slice n'ont par défaut pas de fichier d'unité. Les limites de ressources sont définies via un drop-in, qui peut être facilement remplacé ou étendu en suivant les mécanismes de drop-in standard discutés dans la première section.
