SYSUPDATE.D(5) sysupdate.d SYSUPDATE.D(5)

NOM

sysupdate.d - Fichiers de définition de transfert pour mises à jour automatiques

SYNTAXE

/etc/sysupdate.d/*.transfer
/run/sysupdate.d/*.transfer
/usr/local/lib/sysupdate.d/*.transfer
/usr/lib/sysupdate.d/*.transfer

DESCRIPTION

Ces fichiers décrivent comment des ressources spécifiques du système local doivent être mises à jour à partir d'une source distante. Chaque fichier définit un tel transfert : typiquement une ressource HTTP/HTTPS distante comme source ; et un fichier, un répertoire ou une partition locale comme cible. Ceci peut être utilisé comme un mécanisme de mise à jour simple, automatique et atomique pour le système d'exploitation lui-même, pour des conteneurs, des services portables ou des images d'extension système — mais peut en fait être utilisé pour mettre à jour tout type de fichier à partir d'une source distante.

La commande systemd-sysupdate(8) lit ces fichiers et les utilise pour déterminer quelles ressources locales doivent être mises à jour, puis exécute la mise à jour.

Tant la source HTTP/HTTPS distante que la cible locale existent typiquement en multiples versions concurrentes, afin de mettre en œuvre des schémas de mise à jour flexibles, par exemple la mise à jour A/B (ou un sur-ensemble de celle-ci, par exemple A/B/C, A/B/C/D, ...).

Chaque fichier *.transfer définit un transfert, c'est-à-dire décrit une ressource à mettre à jour. Typiquement, plusieurs de ces fichiers (c'est-à-dire plusieurs de ces transferts) sont définis ensemble, et sont liés par un identifiant de version commun afin de mettre à jour plusieurs ressources en une seule fois lors de chaque opération de mise à jour, par exemple pour mettre à jour un noyau, un système de fichiers racine et une partition Verity en une seule opération combinée et synchronisée, de sorte que seule une mise à jour combinée des trois constitue une mise à jour complète. Nous appellerons une telle collection de transferts une cible. systemd-sysupdate(8) opère toujours sur une seule cible.

Les transferts peuvent être groupés en ensembles qui peuvent être individuellement activés ou désactivés par l'administrateur système, appelés "Fonctionnalités Optionnelles" : sysupdate.features(5).

Chaque fichier *.transfer contient trois sections : [Transfer], [Source] et [Target].

MODE OPÉRATOIRE DE BASE

Les mises à jour du système d'exploitation basées sur des images disque consistent typiquement en de multiples ressources différentes qui doivent être mises à jour ensemble, par exemple une mise à jour sécurisée du système pourrait consister en une image de système de fichiers racine à placer dans une partition, une image de partition d'intégrité Verity correspondante, et une image de noyau préparée pour démarrer la combinaison des deux partitions. Les deux premières ressources sont des fichiers téléchargés et placés dans une partition disque, la dernière est un fichier téléchargé et placé dans un fichier régulier dans le système de fichiers de démarrage (par exemple, la partition système EFI). Par conséquent, lors de la mise à jour d'un système d'exploitation hypothétique "foobarOS" vers une version hypothétique 47, les opérations suivantes devraient avoir lieu :

1.Un fichier "https://download.example.com/foobarOS_47.root.xz" devrait être téléchargé, décompressé et écrit dans une partition précédemment inutilisée avec le type de partition GPT UUID 4f68bce3-e8cd-4db1-96e7-fbcaf984b709 pour x86-64, conformément à la Spécification des Partitions Découvrables[1].
2.De même, un fichier "https://download.example.com/foobarOS_47.verity.xz" devrait être téléchargé, décompressé et écrit dans une partition précédemment vide avec le type de partition GPT UUID 2c7357ed-ebd2-46d9-aec1-23d437ec2bf5 (c'est-à-dire le type de partition pour les informations d'intégrité Verity pour les systèmes de fichiers racine x86-64).
3.Enfin, un fichier "https://download.example.com/foobarOS_47.efi" (un noyau unifié, conformément à la Spécification du Chargeur de Démarrage[2] Type #2) devrait être téléchargé, décompressé et écrit sur le système de fichiers $BOOT, c'est-à-dire dans EFI/Linux/foobarOS_47.efi dans l'ESP ou la partition XBOOTLDR.

La généralisation indépendante de la version de ceci serait (en utilisant le marqueur spécial "@v" comme joker pour l'identifiant de version) :

1.Un transfert d'un fichier "https://download.example.com/foobarOS_@v.root.xz" → une partition GPT locale, précédemment vide, de type 4f68bce3-e8cd-4db1-96e7-fbcaf984b709, avec l'étiquette à définir sur "foobarOS_@v".
2.Un transfert d'un fichier "https://download.example.com/foobarOS_@v.verity.xz" → une partition GPT locale, précédemment vide, de type 2c7357ed-ebd2-46d9-aec1-23d437ec2bf5, avec l'étiquette à définir sur "foobarOS_@v_verity".
3.Un transfert d'un fichier "https://download.example.com/foobarOS_@v.efi" → un fichier local $BOOT/EFI/Linux/foobarOS_@v.efi.

Une mise à jour ne peut être complétée que si les URL pertinentes fournissent leurs ressources pour la même version, c'est-à-dire pour la même valeur de "@v".

Ce qui précède peut être traduit en trois fichiers *.transfer dans sysupdate.d/, un pour chaque ressource à transférer. Les fichiers *.transfer configurent le type de téléchargement, et quel emplacement écrire le téléchargement (c'est-à-dire si dans une partition ou un fichier dans le système de fichiers). Plus important encore, ces fichiers contiennent les modèles d'URL, de nom de partition et de nom de fichier montrés ci-dessus qui décrivent comment ces ressources sont nommées sur la source et comment elles doivent être nommées sur la cible.

Afin d'énumérer les versions disponibles et de trouver des candidats à mettre à jour, un mécanisme est nécessaire pour lister les fichiers adéquats :

•Pour les partitions : la table de partitions GPT environnante contient une liste des partitions définies, incluant un UUID de type de partition et une étiquette de partition (dans ce schéma, l'étiquette de partition joue un rôle similaire au nom de fichier pour un fichier régulier).
•Pour les fichiers réguliers : la liste du répertoire contenant les fichiers fournit une liste des fichiers existants d'une manière simple.
•Pour les sources HTTP/HTTPS un schéma simple est utilisé : un fichier manifeste SHA256SUMS, suivant le format défini par sha256sum(1), liste les noms de fichiers et leurs hachages SHA256.

Les transferts sont effectués dans l'ordre alphabétique des noms des fichiers .transfer dans lesquels ils sont définis. D'abord, les données de la ressource sont téléchargées directement dans un fichier/répertoire/partition cible. Une fois que cela est terminé pour tous les transferts définis, dans une deuxième étape, les fichiers/répertoires/partitions sont renommés à leurs noms finaux tels que définis par le MatchPattern= cible, à nouveau dans l'ordre dicté par les noms des fichiers .transfer. Cette étape n'est pas atomique, cependant il est garanti qu'elle est exécutée strictement dans l'ordre avec une synchronisation de disque appropriée en place. Typiquement, lors de la mise à jour d'un système d'exploitation, l'un des transferts définit le point d'entrée lors du démarrage. Ainsi, il est généralement judicieux d'ordonner les ressources via les noms des fichiers de configuration de transfert afin que le point d'entrée soit écrit en dernier, garantissant que toute terminaison anormale ne laisse pas un point d'entrée dont le support n'est pas encore établi. Dans l'exemple ci-dessus, il serait donc logique d'établir l'image du noyau EFI en dernier et ainsi de donner à son fichier de configuration de transfert le nom alphabétiquement le plus tardif.

Voir ci-dessous pour un exemple étendu et plus spécifique basé sur ce qui précède.

TYPES DE RESSOURCES

Chaque fichier de transfert définit une ressource source à transférer vers une ressource cible. Les types de ressources suivants sont supportés :

1.Les ressources de type "url-file" encapsulent un fichier sur un serveur web, référencé via une URL HTTP ou HTTPS. Lorsqu'une mise à jour a lieu, le fichier est téléchargé et décompressé, puis écrit dans le fichier ou la partition cible. Ce type de ressource n'est disponible que pour les sources, pas pour les cibles. La liste des versions disponibles des ressources de ce type est codée dans des fichiers manifeste SHA256SUMS, accompagnés de signatures détachées SHA256SUMS.gpg.
2.Le type de ressource "url-tar" est similaire, mais le fichier doit être une archive .tar. Lorsqu'une mise à jour a lieu, le fichier est décompressé et dépaqueté dans un répertoire ou un sous-volume btrfs. Ce type de ressource n'est disponible que pour les sources, pas pour les cibles. Tout comme "url-file", l'énumération des versions de "url-tar" utilise les fichiers SHA256SUMS, authentifiés via SHA256SUMS.gpg.

3. Le type de ressource « regular-file » encapsule un fichier régulier local sur le disque. Lors des mises à jour, le fichier est décompressé et écrit dans le fichier ou la partition cible. Ce type de ressource est disponible en tant que source et cible. Lors de la mise à jour, aucune vérification d'intégrité ou d'authentification n'est effectuée pour les ressources de ce type.
4. Le type de ressource « partition » est similaire à « regular-file » et encapsule une partition GPT sur le disque. Lors de la mise à jour, la partition doit déjà exister et avoir le bon type de partition GPT. Une partition dont le label de partition GPT est défini sur « _empty » est considérée comme vide et candidate pour y placer une ressource nouvellement téléchargée. Le label de partition GPT est utilisé pour stocker les informations de version, une fois une partition mise à jour. Ce type de ressource n'est disponible que pour les ressources cibles.
5. Le type de ressource « tar » encapsule des fichiers d'archive .tar locaux. Lors d'une mise à jour, les fichiers sont décompressés et dépaquetés dans un répertoire cible ou un sous-volume btrfs. Le comportement de « tar » et « url-tar » est généralement similaire, mais ce dernier télécharge à partir de sources distantes et effectue des vérifications d'intégrité et d'authentification, tandis que le premier ne le fait pas. Le type de ressource « tar » n'est disponible que pour les ressources sources.
6. Le type de ressource « directory » encapsule des arbres de répertoires locaux. Ce type est disponible pour les ressources sources et cibles. Si une mise à jour a lieu sur une ressource source de ce type, une copie récursive du répertoire est effectuée.
7. Le type de ressource « subvolume » est identique à « directory », sauf lorsqu'il est utilisé comme cible, auquel cas l'arborescence de fichiers est placée dans un sous-volume btrfs au lieu d'un répertoire ordinaire, si le système de fichiers sous-jacent le prend en charge (c'est-à-dire s'il s'agit de btrfs).

MODÈLES DE CORRESPONDANCE

Les ressources sources et cibles existent généralement en plusieurs versions simultanément. Une opération de mise à jour est effectuée lorsque la plus récente des versions sources est plus récente que la plus récente des versions cibles. Pour déterminer la version la plus récente des ressources, une liste du répertoire, une liste des partitions ou une liste de manifestes est utilisée, un sous-ensemble des entrées qualifiées est sélectionné à partir de celle-ci, et l'identifiant de version est extrait des noms de fichiers ou des étiquettes de partitions de ces entrées sélectionnées. La sélection du sous-ensemble et l'extraction de l'identifiant de version (ainsi que potentiellement d'autres métadonnées) sont effectuées via des modèles de correspondance, configurés dans
MatchPattern= dans les sections [Source] et [Target]. Ces modèles sont des chaînes qui décrivent comment les fichiers ou les partitions sont nommés, avec des caractères génériques nommés pour des champs spécifiques tels que l'identifiant de version. Les caractères génériques suivants sont définis :

Tableau 2. Caractères génériques des modèles de correspondance

Caractère générique Description Format Notes
« @v » Identifiant de version Chaîne de version valide Obligatoire
« @u » UUID de partition GPT Chaîne UUID valide 128 bits Uniquement pertinent si le type de ressource cible est choisi comme partition
« @f » Drapeaux de partition GPT Entier hexadécimal formaté Uniquement pertinent si le type de ressource cible est choisi comme partition
« @a » Drapeau de partition GPT NoAuto Soit « 0 » soit « 1 » Contrôle le bit NoAuto des drapeaux de partition GPT, conformément à la Spécification des partitions découvrables[1] ; uniquement pertinent si le type de ressource cible est choisi comme partition
« @g » Drapeau de partition GPT GrowFileSystem Soit « 0 » soit « 1 » Contrôle le bit GrowFileSystem des drapeaux de partition GPT, conformément à la Spécification des partitions découvrables[1] ; uniquement pertinent si le type de ressource cible est choisi comme partition
« @r » Drapeau lecture seule Soit « 0 » soit « 1 » Contrôle le bit ReadOnly des drapeaux de partition GPT, conformément à la Spécification des partitions découvrables[1] et à d'autres drapeaux de sortie en lecture seule, voir ReadOnly= ci-dessous
« @t » Heure de modification du fichier Entier décimal formaté, µs depuis l'époque UNIX le 1er janvier 1970 Uniquement pertinent si le type de ressource cible est choisi comme regular-file
« @m » Mode d'accès au fichier Entier octal formaté, à la manière UNIX Uniquement pertinent si le type de ressource cible est choisi comme regular-file
« @s » Taille du fichier après décompression Entier décimal formaté Utile pour mesurer la progression et améliorer la logique d'allocation des partitions
« @d » Tentatives effectuées Entier décimal formaté Utile lors de l'opération avec des fichiers d'image de noyau, conformément à l'Évaluation automatique du démarrage[3]
« @l » Tentatives restantes Entier décimal formaté Utile lors de l'opération avec des fichiers d'image de noyau, conformément à l'Évaluation automatique du démarrage[3]

Parmi ces caractères génériques, seul
« @v » doit être présent dans un modèle valide, tous les autres caractères génériques sont facultatifs. Chaque caractère générique peut être utilisé au plus une fois dans chaque modèle. Un modèle typique correspondant à une image source de système de fichiers pourrait être « MatchPattern=foobar_@v.raw.xz », c'est-à-dire tout fichier dont le nom commence par « foobar_ », suivi d'un identifiant de version et se terminant par « .raw.xz ».

Ne pas confondre le préfixe de caractère générique « @ » des modèles avec le préfixe de spécificateur « % ». Le premier encapsule une partie variable d'une chaîne de modèle de correspondance, le second sont des raccourcis simples qui sont développés lors de l'analyse des fichiers drop-in. Pour plus de détails sur les spécificateurs, voir ci-dessous.

OPTIONS DE SECTION [TRANSFERT]

Cette section définit les propriétés générales de ce transfert.

MinVersion=

Spécifie la version minimale requise pour que ce transfert ait lieu. Si les modèles sources et cibles dans cette définition de transfert correspondent à des fichiers plus anciens que cette version, ils seront considérés comme obsolètes et ne seront jamais pris en compte pour l'opération de mise à jour.

Ajouté dans la version 251.

ProtectVersion=

Accepte une ou plusieurs chaînes de version à marquer comme « protégées ». Les versions protégées ne sont jamais supprimées lors de la création d'espace pour de nouvelles versions mises à jour. Ceci est utile pour garantir que la version du système d'exploitation actuellement démarrée (ou les ressources auxiliaires qui y sont associées) ne soit pas remplacée/écrasée lors des mises à jour, afin d'éviter les corruptions du système de fichiers en cours d'exécution.

Comme de nombreux paramètres dans ces fichiers de configuration, ce paramètre prend en charge le développement de spécificateurs. Il est particulièrement utile de définir ce paramètre sur l'un des spécificateurs « %A », « %B » ou « %w » pour faire référence automatiquement à la version actuelle du système d'exploitation du système en cours d'exécution. Voir ci-dessous pour plus de détails sur les spécificateurs pris en charge.

Ajouté dans la version 251.

Verify=

Accepte une valeur booléenne, par défaut à oui. Contrôle si les ressources téléchargées doivent être vérifiées cryptographiquement (spécifiquement : valider les signatures GPG des fichiers manifestes SHA256SUMS téléchargés, via leurs fichiers de signature détachés SHA256SUMS.gpg en combinaison avec le trousseau système /usr/lib/systemd/import-pubring.pgp ou /etc/systemd/import-pubring.pgp).

Cette option est essentielle pour fournir des garanties d'intégrité pour les ressources téléchargées et doit donc être laissée activée, en dehors des environnements de test.

Notez que les fichiers de charge utile téléchargés sont vérifiés inconditionnellement par rapport aux hachages SHA256 répertoriés dans le manifeste. Cette option contrôle uniquement si les signatures de ces manifestes sont vérifiées.

Cette option n'a d'effet que si le type de ressource source est sélectionné comme url-file ou url-tar, car la vérification d'intégrité et d'authentification n'est disponible que pour les transferts à partir de sources distantes.

Ajouté dans la version 251.

ChangeLog=

Accepte éventuellement une URL présentable par l'homme vers un site Web contenant un journal des modifications de la ressource en cours de mise à jour.

OPTIONS

Ces options définissent les propriétés d'une ressource à mettre à jour.

URLs=

Spécifie une ou plusieurs URL où trouver les versions des ressources de cette définition de transfert. Peut être défini plusieurs fois dans une seule définition de transfert. Si défini plusieurs fois, les valeurs sont rassemblées dans une liste d'URL. L'ajout d'une valeur de chaîne vide effacera la liste existante de toutes les valeurs.

Ce paramètre prend en charge l'expansion des spécificateurs. Voir ci-dessous pour les détails sur les spécificateurs pris en charge. Ce paramètre développera également le modèle générique « @v ». Voir ci-dessus pour les détails.

Ajouté dans la version 257.

AppStream=

Prend éventuellement une URL vers un fichier XML de catalogue AppStream[4]. Ceci peut être utilisé par les centres logiciels (comme GNOME Software ou KDE Discover) pour présenter des métadonnées riches sur les ressources mises à jour. Cela inclut les noms d'affichage, les journaux de modifications, les icônes, etc. Le catalogue spécifié doit inclure des métadonnées spéciales[5] pour être correctement associé à systemd-sysupdate(8) par les centres logiciels.

Ce paramètre prend en charge l'expansion des spécificateurs. Voir ci-dessous pour les détails sur les spécificateurs pris en charge.

Ajouté dans la version 257.

Features=

Une liste séparée par des espaces de sysupdate.features(5) auxquels appartient ce transfert, par nom. Cette option peut être spécifiée plus d'une fois, auquel cas la liste des fonctionnalités spécifiées est fusionnée. Si la chaîne vide est assignée à cette option, la liste est réinitialisée et toutes les affectations précédentes n'auront aucun effet. Par exemple : « Features=foo bar » spécifie que le transfert appartient à « foo.feature » et « bar.feature ».

Si la liste des fonctionnalités est vide, alors ce transfert est toujours utilisé. Si ce transfert appartient à plus d'une fonctionnalité, alors il sera utilisé si *une* quelconque des fonctionnalités listées est activée. Un nom qui ne correspond pas à une fonctionnalité définie résoudra en une fonctionnalité implicite qui est toujours désactivée.

Ajouté dans la version 257.

RequisiteFeatures=

Ceci est similaire à Features=, sauf que *toutes* les fonctionnalités listées ici doivent être activées pour que ce transfert soit activé. Si les deux options sont spécifiées, alors elles s'appliquent toutes les deux : le transfert sera activé uniquement si toutes les fonctionnalités spécifiées ici sont activées, et au moins une fonctionnalité listée dans Features= est activée.

Ajouté dans la version 257.

[SOURCE] SECTION OPTIONS

Cette section définit les propriétés de la source du transfert.

Type=

Spécifie le type de ressource de la source pour le transfert. Prend l'une des valeurs url-file, url-tar, tar, regular-file, directory ou subvolume. Pour plus de détails sur les types de ressources, voir ci-dessus. Cette option est obligatoire.

Notez que seules certaines combinaisons de types de ressources source et cible sont prises en charge, voir ci-dessus.

Ajouté dans la version 251.

Path=

Spécifie où trouver les versions sources de cette ressource.

Si le type de source est sélectionné comme url-file ou url-tar, il doit s'agir d'une URL HTTP/HTTPS. L'URL est suffixée par /SHA256SUMS pour acquérir le fichier manifeste, par /SHA256SUMS.gpg pour acquérir la signature détachée de celui-ci, et par les noms de fichiers listés dans le fichier manifeste dans le cas où une mise à jour est exécutée et qu'une ressource doit être téléchargée.

Pour tous les autres types de ressources sources, il doit s'agir d'un chemin local dans le système de fichiers, faisant référence à un répertoire local où trouver les versions de cette ressource.

Ajouté dans la version 251.

MatchPattern=

Spécifie un ou plusieurs modèles de correspondance de noms de fichiers qui sélectionnent le sous-ensemble de fichiers qui sont des candidats à la mise à jour comme source pour ce transfert. Voir ci-dessus pour les détails sur les modèles de correspondance.

Cette option est obligatoire. Tout motif listé doit contenir au moins le joker « @v », afin qu'un identifiant de version puisse être extrait du nom de fichier. Tous les autres jokers sont facultatifs.

Si le type de source est regular-file ou directory, le motif peut contenir des caractères slash. Dans ce cas, il correspondra au fichier ou répertoire dans le sous-répertoire correspondant. Par exemple, « MatchPattern=foo_@v/bar.efi » correspondra à « bar.efi » dans le répertoire « foo_1 ».

Ajouté dans la version 251.

[TARGET] SECTION OPTIONS

Cette section définit les propriétés de la cible du transfert.

Type=

Spécifie le type de ressource de la cible pour le transfert. Prend l'une des valeurs partition, regular-file, directory ou subvolume. Pour plus de détails sur les types de ressources, voir ci-dessus. Cette option est obligatoire.

Notez que seules certaines combinaisons de types de ressources source et cible sont prises en charge, voir ci-dessus.

Ajouté dans la version 251.

Path=

Spécifie un chemin du système de fichiers où rechercher les versions déjà installées ou placer les versions nouvellement téléchargées de cette ressource configurée. Si Type= est défini sur partition, attend un chemin vers un nœud de périphérique bloc (entier) ou la chaîne spéciale « auto » auquel cas le périphérique bloc qui contient le système de fichiers racine du système actuellement démarré est automatiquement déterminé et utilisé. Si Type= est défini sur regular-file, directory ou subvolume, doit faire référence à un chemin dans le système de fichiers local référençant le répertoire où trouver ou placer les fichiers ou répertoires de version.

Notez que ce mécanisme ne peut pas être utilisé pour créer ou supprimer des partitions, si Type= est défini sur partition. Les partitions doivent déjà exister, et une étiquette de partition spéciale « _empty » est utilisée pour indiquer les partitions vides. Pour générer automatiquement des partitions appropriées au premier démarrage, utilisez un outil tel que systemd-repart(8).

Ajouté dans la version 251.

PathRelativeTo=

Spécifie par rapport à quel point d'ancrage Path= doit être résolu. Prend l'une des valeurs root, esp, xbootldr, boot ou explicit. Si non spécifié, la valeur par défaut est root.

Si défini sur root, esp, xbootldr, le Path= spécifié sera résolu par rapport au point de montage de la partition correspondante, tel que défini par la spécification du chargeur de démarrage[2].

Si défini sur boot, le Path= spécifié sera résolu par rapport au point de montage de la partition $BOOT (c'est-à-dire l'ESP ou XBOOTLDR), tel que défini par la spécification du chargeur de démarrage[2].

Si défini sur explicit, le Path= spécifié sera résolu par rapport au répertoire spécifié avec --transfer-source= lors de l'appel de systemd-sysupdate(8).

Les valeurs esp, xbootldr et boot ne sont prises en charge que lorsque Type= est défini sur regular-file ou directory.

Ajouté dans la version 254.

MatchPattern=

Spécifie un ou plusieurs modèles de correspondance de noms de fichiers ou d'étiquettes de partition qui sélectionnent le sous-ensemble de fichiers ou de partitions qui sont des candidats à la mise à jour en tant que cibles pour ce transfert. Voir ci-dessus pour les détails sur les modèles de correspondance.

Cette option est obligatoire. Tout motif listé doit contenir au moins le joker « @v », afin qu'un identifiant de version puisse être extrait du nom de fichier. Tous les autres jokers sont facultatifs.

Ce motif est utilisé à la fois pour faire correspondre les versions installées existantes et pour déterminer le nom des nouvelles versions à installer. Si plusieurs motifs sont spécifiés, le premier spécifié est utilisé pour nommer les nouvelles versions installées.

Si le type de cible est regular-file ou directory, le motif peut contenir des caractères slash. Dans ce cas, il correspondra au fichier ou répertoire dans le sous-répertoire correspondant. Par exemple, « MatchPattern=foo_@v/bar.efi » correspondra à « bar.efi » dans le répertoire « foo_1 ». Les répertoires dans le chemin seront créés lors de l'installation du fichier. Les répertoires vides seront supprimés lors de la suppression du fichier.

Ajouté dans la version 251.

MatchPartitionType=

Lorsque le type cible Type= est choisi comme partition, spécifie le type de partition GPT à rechercher. Seules les partitions de ce type sont prises en compte, toutes les autres partitions sont ignorées. Si non spécifié, le type de partition GPT linux-generic est utilisé. Accepte soit un UUID de type littéral, soit un identifiant de type symbolique. Pour une liste des identifiants de type pris en charge, voir le paramètre Type= dans repart.d(5).

Ajouté dans la version 251.

PartitionUUID=, PartitionFlags=, PartitionNoAuto=, PartitionGrowFileSystem=

Lorsque le type cible Type= est choisi comme partition, sélectionne l'UUID de partition GPT et les indicateurs de partition à utiliser pour la partition mise à jour. Attend une chaîne UUID valide, un entier hexadécimal ou des booléens, respectivement. Si non défini, mais que le motif de correspondance source inclut des jokers pour ces champs (c'est-à-dire « @u », « @f », « @a », ou « @g »), les valeurs des motifs sont utilisées. Si ni configuré avec des jokers ni ces paramètres explicites, les valeurs ne sont pas modifiées. Si à la fois le paramètre général PartitionFlags= et les paramètres individuels des indicateurs PartitionNoAuto= et PartitionGrowFileSystem= sont utilisés (ou les jokers correspondants), alors ces derniers remplacent le premier, c'est-à-dire que le bit d'indicateur individuel remplace la valeur globale des indicateurs. Voir la spécification des partitions découvrables[1] pour plus de détails sur ces indicateurs.

Notez que ces paramètres ne sont pas utilisés pour la correspondance, ils n'ont d'effet que sur les partitions nouvellement écrites en cas de transfert.

Ajouté dans la version 251.

ReadOnly=

Contrôle si le fichier, le sous-volume ou la partition résultant doit être marqué en lecture seule. Si le type de cible est partition, cela contrôle l'indicateur de partition ReadOnly, conformément à la spécification des partitions découvrables[1], similaire aux indicateurs PartitionNoAuto= et PartitionGrowFileSystem= décrits ci-dessus. Si le type de cible est regular-file, le bit d'écriture est supprimé du mode d'accès. Si le type de cible est subvolume, le sous-volume sera marqué en lecture seule dans son ensemble. Enfin, si le type cible Type= est sélectionné comme directory, l'attribut de fichier « immutable » est défini, voir chattr(1) pour plus de détails.

Ajouté dans la version 251.

Mode=

Le mode d'accès aux fichiers UNIX à utiliser pour les nouveaux fichiers dans le cas où le type de ressource cible est choisi comme regular-file. Attend un entier octal, typique de UNIX. Si non défini, mais que le motif de correspondance source inclut un joker pour ce champ (c'est-à-dire « @t »), la valeur fr
utilisé.

Notez que ce réglage n'est pas utilisé pour la correspondance, il n'a qu'un effet sur les fichiers nouvellement écrits lors d'un transfert.

Ajouté dans la version 251.

TriesDone=, TriesLeft=

Ces options acceptent des entiers décimaux positifs et contrôlent le nombre de tentatives effectuées et restantes pour ce fichier. Ces réglages sont utiles pour gérer les images de noyau, en suivant le schéma défini dans Automatic Boot Assessment[3], et n'ont d'effet que si le modèle cible inclut les jokers "@d" ou "@l".

Ajouté dans la version 251.

InstancesMax=

Accepte un entier décimal égal ou supérieur à 2. Configure le nombre de versions concurrentes de la ressource à conserver. Chaque fois qu'une nouvelle mise à jour est initiée, il est veillé à ce qu'il n'y ait pas plus que le nombre de versions spécifié ici moins une existant dans la cible. Les versions excédentaires sont supprimées (si le type de cible Type= de regular-file, directory, subvolume est utilisé) ou vidées (si le type de cible Type= de partition est utilisé ; vider dans ce cas signifie simplement définir l'étiquette de la partition sur la chaîne spéciale "_empty" ; notez qu'aucune partition n'est réellement supprimée). Une fois la mise à jour terminée, le nombre de versions concurrentes des ressources cibles est inférieur ou égal au nombre spécifié ici.

Notez que ce réglage peut être défini différemment pour chaque transfert. Cependant, il est généralement conseillé de conserver ce réglage identique pour tous les transferts, car sinon des combinaisons incomplètes de fichiers ou de partitions resteront installées.

Si le type de cible Type= est sélectionné comme partition, le nombre de versions concurrentes à conserver est en outre restreint par le nombre d'emplacements de partitions du bon type dans la table des partitions. C'est-à-dire si il n'y a que 2 emplacements de partitions pour le type de partition sélectionné, régler cette valeur à plus de 2 est sans effet, car pas plus de 2 versions concurrentes ne pourraient être stockées dans l'image de toute façon.

Ajouté dans la version 251.

RemoveTemporary=

Accepte un argument booléen. Si cette option est activée (ce qui est le cas par défaut) avant d'initier une mise à jour, toutes les mises à jour restantes et incomplètes d'une tentative précédente sont supprimées du répertoire cible. Cela n'a d'effet que si le type de ressource cible Type= est sélectionné comme regular-file, directory ou subvolume.

Ajouté dans la version 251.

CurrentSymlink=

Accepte un nom de lien symbolique comme argument. Si cette option est utilisée, lors de la dernière étape de la mise à jour, un lien symbolique sous le nom spécifié est créé/mis à jour, pointant vers la mise à jour terminée. Ceci est utile pour fournir un nom stable pointant toujours vers la dernière version de la ressource. Ceci n'est pris en charge que si le type de ressource cible Type= est sélectionné comme regular-file, directory ou subvolume.

Ajouté dans la version 251.

SPÉCIFICATEURS

Les spécificateurs peuvent être utilisés dans les réglages MinVersion=, ProtectVersion=, Path=, MatchPattern= et CurrentSymlink=. Les expansions suivantes sont comprises :

Tableau 3. Spécificateurs disponibles

Spécificateur Signification Détails
"%a" Architecture Une courte chaîne identifiant l'architecture du système local. Une chaîne telle que x86, x86-64 ou arm64. Voir les architectures définies pour ConditionArchitecture= dans systemd.unit(5) pour une liste complète.
"%A" Version de l'image du système d'exploitation L'identifiant de version de l'image du système d'exploitation du système en cours d'exécution, tel que lu dans le champ IMAGE_VERSION= de /etc/os-release. S'il n'est pas défini, il est résolu en une chaîne vide. Voir os-release(5) pour plus d'informations.
"%b" ID de démarrage L'ID de démarrage du système en cours d'exécution, formaté sous forme de chaîne. Voir random(4) pour plus d'informations.
"%B" ID de construction du système d'exploitation L'identifiant de construction du système d'exploitation du système en cours d'exécution, tel que lu dans le champ BUILD_ID= de /etc/os-release. S'il n'est pas défini, il est résolu en une chaîne vide. Voir os-release(5) pour plus d'informations.
"%H" Nom de l'hôte Le nom d'hôte du système en cours d'exécution.
"%l" Nom court de l'hôte Le nom d'hôte du système en cours d'exécution, tronqué au premier point pour supprimer tout composant de domaine.
"%m" ID de machine L'ID de machine du système en cours d'exécution, formaté sous forme de chaîne. Voir machine-id(5) pour plus d'informations.
"%M" Identifiant de l'image du système d'exploitation L'identifiant de l'image du système d'exploitation du système en cours d'exécution, tel que lu dans le champ IMAGE_ID= de /etc/os-release. S'il n'est pas défini, il est résolu en une chaîne vide. Voir os-release(5) pour plus d'informations.
"%o" ID du système d'exploitation L'identifiant du système d'exploitation du système en cours d'exécution, tel que lu dans le champ ID= de /etc/os-release. Voir os-release(5) pour plus d'informations.
"%v" Version du noyau Identique à la sortie de uname -r.
"%w" ID de version du système d'exploitation L'identifiant de version du système d'exploitation du système en cours d'exécution, tel que lu dans le champ VERSION_ID= de /etc/os-release. S'il n'est pas défini, il est résolu en une chaîne vide. Voir os-release(5) pour plus d'informations.
"%W" ID de variante du système d'exploitation L'identifiant de variante du système d'exploitation du système en cours d'exécution, tel que lu dans le champ VARIANT_ID= de /etc/os-release. S'il n'est pas défini, il est résolu en une chaîne vide. Voir os-release(5) pour plus d'informations.
"%T" Répertoire pour les fichiers temporaires Il s'agit soit de /tmp, soit du chemin défini par "$TMPDIR", "$TEMP" ou "$TMP". (Notez que le répertoire peut être spécifié sans barre oblique finale.)
"%V" Répertoire pour les fichiers temporaires plus grands et persistants Il s'agit soit de /var/tmp, soit du chemin défini par "$TMPDIR", "$TEMP" ou "$TMP". (Notez que le répertoire peut être spécifié sans barre oblique finale.)
"%%" Signe de pourcentage unique Utilisez "%%" à la place de "%" pour spécifier un seul signe de pourcentage.

Ne pas confondre l'expansion du préfixe de spécificateur
"%" avec le préfixe du joker de correspondance de modèle "@". Les premiers sont des raccourcis simples qui sont développés lors de l'analyse des fichiers drop-in, les seconds encapsulent une partie variable d'une chaîne de modèle de correspondance. Pour plus de détails sur les jokers de correspondance de modèle, voir ci-dessus.

EXEMPLES

Exemple 1. Mises à jour pour un OS sécurisé activé pour Verity

Avec les trois fichiers suivants, nous définissons une partition du système de fichiers racine, une partition Verity correspondante et une image de noyau unifiée à mettre à jour en bloc. Cet exemple est une extension de l'exemple discuté précédemment dans ce manuel.

# /usr/lib/sysupdate.d/50-verity.transfer
[Transfer]
ProtectVersion=%A
[Source]
Type=url-file
Path=https://download.example.com/
MatchPattern=foobarOS_@v_@u.verity.xz
[Target]
Type=partition
Path=auto
MatchPattern=foobarOS_@v_verity
MatchPartitionType=root-verity
PartitionFlags=0
ReadOnly=1

Ce qui précède définit le mécanisme de mise à jour de la partition Verity du système de fichiers racine. Les images de partition Verity sont téléchargées depuis "https://download.example.com/foobarOS_@v_@u.verity.xz" et écrites sur une partition locale appropriée, marquée comme lecture seule. En supposant que cette mise à jour est exécutée à partir de l'image elle-même, la version actuelle de l'image (c'est-à-dire le spécificateur "%A") est marquée comme protégée, afin de s'assurer qu'elle ne soit pas corrompue pendant le démarrage. Notez que l'UUID de la partition cible est codé dans le nom du fichier source. La fixation de l'UUID de la partition peut être utile pour garantir que "roothash=" sur la ligne de commande du noyau soit suffisant pour localiser à la fois la partition Verity et la partition du système de fichiers racine, et également pour coder le hachage de niveau racine de Verity (en supposant que l'UUID dans les noms de fichiers corresponde à leur hachage de niveau supérieur, comme suggéré par systemd-gpt-auto-generator(8)).

# /usr/lib/sysupdate.d/60-root.transfer
[Transfer]
ProtectVersion=%A
[Source]
Type=url-file
Path=https://download.example.com/
MatchPattern=foobarOS_@v_@u.root.xz
[Target]
Type=partition
Path=auto
MatchPattern=foobarOS_@v
MatchPartitionType=root
PartitionFlags=0
ReadOnly=1

Ce qui précède définit une définition de transfert correspondante pour le système de fichiers racine.

# /usr/lib/sysupdate.d/70-kernel.transfer
[Transfer]
ProtectVersion=%A
[Source]
Type=url-file
Path=https://download.example.com/
MatchPattern=foobarOS_@v.efi
[Target]
Type=regular-file
Path=/EFI/Linux
PathRelativeTo=boot
MatchPattern=foobarOS_@v+@l-@d.efi \
             foobarOS_@v+@l.efi \
             foobarOS_@v.efi
Mode=0644
TriesLeft=3
TriesDone=0
InstancesMax=2

Ce qui précède installe une image de noyau unifiée dans la partition $BOOT, conformément à la spécification du chargeur de démarrage Boot Loader Specification[2] Type #2. Ceci définit trois modèles possibles pour les noms des images de noyau, conformément à Automatic Boot Assessment[3], et garantit lors de l'installation de nouveaux noyaux, qu'ils sont configurés avec 3 tentatives restantes. Pas plus de deux noyaux parallèles ne sont conservés.

Avec cette configuration, le serveur Web servirait les fichiers suivants, pour une version hypothétique 7 de l'OS :

•SHA256SUMS – Le fichier manifeste, contenant les fichiers disponibles et leurs hachages SHA256
•SHA256SUMS.gpg – La signature cryptographique détachée du fichier manifeste
•foobarOS_7_8b8186b1-2b4e-4eb6-ad39-8d4d18d2a8fb.verity.xz – L'image Verity pour la version 7
•foobarOS_7_f4d1234f-3ebf-47c4-b31d-4052982f9a2f.root.xz – L'image du système de fichiers racine pour la version 7
Le contenu est déjà en français. Il semble qu'il y ait eu une confusion. La seule partie qui pourrait être considérée comme non française est le code `foobarOS_7.efi` et la date du système, mais ce sont des noms de fichiers et des informations système qui ne sont généralement pas traduits. Si vous souhaitez que je traduise un autre contenu en français, n'hésitez pas à me le fournir.
