SYSTEMD-PCRLOCK(8) systemd-pcrlock SYSTEMD-PCRLOCK(8)

NOM

systemd-pcrlock, systemd-pcrlock-file-system.service, systemd-pcrlock-firmware-code.service, systemd-pcrlock-firmware-config.service, systemd-pcrlock-machine-id.service, systemd-pcrlock-make-policy.service, systemd-pcrlock-secureboot-authority.service, systemd-pcrlock-secureboot-policy.service - Analyser et prédire les états des PCR TPM2 et générer une politique d'accès à partir de la prédiction

SYNTAXE

/usr/lib/systemd/systemd-pcrlock [OPTIONS...]

DESCRIPTION

Note : cette commande est actuellement expérimentale. Bien qu'elle soit susceptible de devenir un composant régulier de systemd, son comportement et son interface peuvent encore changer.

systemd-pcrlock est un outil qui peut être utilisé pour analyser et prédire les mesures des PCR TPM2, et générer des politiques d'accès TPM2 à partir de la prédiction, qu'il stocke dans un index NV TPM2 (c'est-à-dire dans la mémoire non volatile du TPM2). Ceci peut ensuite être utilisé pour restreindre l'accès aux objets TPM2 (tels que les clés de chiffrement de disque) aux démarrages du système dans lesquels seuls des composants spécifiques et approuvés sont utilisés.

systemd-pcrlock utilise comme entrée pour son analyse et sa prédiction :

•Le journal d'événements TPM2 du micrologiciel UEFI (c'est-à-dire /sys/kernel/security/tpm0/binary_bios_measurements) du démarrage actuel.
•Le journal d'événements TPM2 en espace utilisateur (c'est-à-dire /run/log/systemd/tpm2-measure.log) du démarrage actuel.
•L'état actuel des PCR de la puce TPM2.
•Des fichiers de définition de composants de démarrage (*.pcrlock et *.pcrlock.d/*.pcrlock, voir systemd.pcrlock(5)) qui définissent chacun les mesures attendues pour un composant du processus de démarrage, autorisant des variantes alternatives pour chacun. (Les variantes peuvent être utilisées pour approuver plusieurs versions du noyau ou du chargeur de démarrage en même temps.)

Il utilise ces entrées pour générer un journal d'événements combiné, le validant par rapport aux états des PCR. Il tente ensuite de reconnaître les enregistrements du journal d'événements et les fait correspondre aux composants définis. Pour chaque PCR pour laquelle cela peut être fait de manière complète (c'est-à-dire où tous les enregistrements listés et tous les composants définis ont été mis en correspondance), cela peut alors être utilisé pour prédire les mesures futures des PCR, en tenant compte des variantes alternatives définies pour chaque composant. Cette prédiction peut ensuite être convertie en une politique d'accès TPM2 (composée d'éléments PolicyPCR et PolicyOR de TPM2), qui est ensuite stockée dans un index NV du TPM2. Ceci peut être utilisé pour verrouiller des secrets (tels que les clés de chiffrement de disque) à ces politiques (via une politique PolicyAuthorizeNV de TPM2).

Utilisez des outils tels que systemd-cryptenroll(1) ou systemd-repart(8) pour lier le chiffrement de disque à une telle politique TPM2 systemd-pcrlock. Spécifiquement, voir les options --tpm2-pcrlock= de ces outils.

La logique de politique d'accès nécessite un périphérique TPM2 qui implémente la commande "PolicyAuthorizeNV", c'est-à-dire qui implémente TPM 2.0 version 1.38 ou plus récente.

COMMANDES

Les commandes suivantes sont comprises :

log

Lit le journal d'événements TPM2 combiné, le valide, le fait correspondre aux valeurs actuelles des PCR et affiche les deux sous forme tabulaire. Combiner avec --json= pour générer la sortie au format JSON.

Ajouté dans la version 255.

cel

Lit le journal d'événements TPM2 combiné et l'écrit sur la sortie standard au format TCG Canonical Event Log Format (CEL-JSON)[1].

Ajouté dans la version 255.

list-components

Affiche une liste des définitions de composants et de leurs variantes, c'est-à-dire les fichiers *.pcrlock découverts dans /var/lib/pcrlock.d/, /usr/lib/pcrlock.d/, et les autres répertoires pris en charge. Voir systemd.pcrlock(5) pour les détails sur ces fichiers et la liste complète des répertoires recherchés.

Ajouté dans la version 255.

predict

Prédit l'état des PCR lors des futurs démarrages. Ceci analysera le journal d'événements TPM2 comme décrit ci-dessus, reconnaîtra les composants, puis générera toutes les valeurs PCR résultantes possibles pour toutes les combinaisons de variantes de composants. Notez qu'aucune prédiction n'est faite pour les PCR dont la valeur ne correspond pas aux enregistrements du journal d'événements, pour lesquelles des mesures non reconnues sont découvertes ou pour lesquelles des composants sont définis qui ne peuvent pas être trouvés dans le journal d'événements. Il s'agit d'une mesure de sécurité pour garantir que toute politique d'accès générée peut être satisfaite correctement lors des démarrages actuels et futurs.

Ajouté dans la version 255.

make-policy

Prédit l'état des PCR pour les futurs démarrages, tout comme la commande predict ci-dessus. Elle utilise ensuite ces données pour générer une politique d'accès TPM2 qu'elle stocke dans un index NV TPM2. La prédiction et les informations sur le TPM2 utilisé et son index NV sont écrites dans /var/lib/systemd/pcrlock.json.

L'index NV est alloué lors de la première invocation et mis à jour lors des invocations ultérieures.

Le contenu de l'index NV peut être modifié (et donc la politique qui y est stockée mise à jour) en fournissant un code PIN d'accès. Ce code PIN est normalement généré automatiquement et stocké sous forme chiffrée (avec une politique d'accès le liant à l'index NV lui-même) dans le fichier de politique JSON susmentionné. Ce code PIN peut être choisi par l'utilisateur, via le commutateur --recovery-pin=. S'il est spécifié, il peut être utilisé comme chemin d'accès alternatif pour mettre à jour la politique.

Si la nouvelle prédiction correspond à l'ancienne, cette commande se termine rapidement et n'exécute aucune autre opération. (Sauf si --force est spécifié, voir ci-dessous.)

À partir de la v256, une copie du fichier de politique /var/lib/systemd/pcrlock.json est encodée dans un identifiant (voir systemd-creds(1) pour les détails) et écrite sur la partition système EFI ou la partition XBOOTLDR, dans le sous-répertoire /loader/credentials/. Là, elle est récupérée au démarrage par systemd-stub(7) et passée à l'initrd invoqué, où elle peut être utilisée pour déverrouiller le système de fichiers racine (qui contient typiquement /var/, qui est où se trouve la copie principale de la politique, qui ne peut donc pas être utilisée pour déverrouiller le système de fichiers racine). Le fichier d'identifiant est nommé d'après le jeton d'entrée de démarrage de l'installation (voir bootctl(1)), qui est configurable via le commutateur --entry-token=, voir ci-dessous.

Ajouté dans la version 255.

remove-policy

Supprime une politique précédemment générée. Supprime le fichier /var/lib/systemd/pcrlock.json et désalloue l'index NV.

Ajouté dans la version 255.

is-supported

Vérifie si le TPM2 local prend en charge toutes les fonctionnalités nécessaires au bon fonctionnement de systemd-pcrlock. Ceci effectue des tests similaires à ceux de systemd-analyze has-tpm2, mais vérifie également la prise en charge des opérations TPM2 requises par systemd-pcrlock. Affiche l'une des valeurs suivantes : "no", "partial" (si certaines parties de la prise en charge TPM2 sont disponibles en matériel, micrologiciel, OS, mais pas complètement), "obsolete" (si la prise en charge TPM2 est disponible en matériel, micrologiciel et OS, mais que les opérations requises pour systemd-pcrlock sont manquantes), "yes". Retourne un code de sortie de zéro si la prise en charge complète est disponible, sinon un code non nul.

Si elle est combinée avec --quiet, supprime l'affichage de la chaîne.

Actuellement, ceci vérifie la prise en charge de la commande TPM2 PolicyAuthorizeNV, ainsi que la prise en charge de l'algorithme de hachage SHA-256.

Ajouté dans la version 258.

lock-firmware-code, unlock-firmware-code

Génère/supprime des fichiers .pcrlock basés sur le journal d'événements TPM2 du démarrage actuel couvrant tous les enregistrements pour les PCR 0 ("platform-code") et 2 ("external-code").

Cette opération permet de verrouiller le processus de démarrage sur la version actuelle du micrologiciel du système et de ses cartes d'extension. Cette opération ne doit être utilisée que si le fournisseur du système ne fournit pas de données pcrlock appropriées à l'avance.

Notez que ces données ne correspondent qu'à la version actuelle du micrologiciel. Si une mise à jour du micrologiciel est appliquée, ces données seront obsolètes et toute politique d'accès générée à partir d'elles ne passera plus. Il est donc recommandé d'invoquer unlock-firmware-code avant de procéder à une mise à jour du micrologiciel, suivie de make-policy pour actualiser la politique.

systemd-pcrlock lock-firmware-code est automatiquement invoqué au démarrage via l'unité systemd-pcrlock-firmware-code.service, si elle est activée. Ceci garantit qu'une politique d'accès gérée par systemd-pcrlock est automatiquement verrouillée à la nouvelle version du micrologiciel chaque fois que le

Les fichiers ne sont générés à partir du journal des événements que si le journal des événements correspond à l'état actuel des PCR du TPM2.

Ceci écrit/supprime les fichiers /var/lib/pcrlock.d/250-firmware-code-early.pcrlock.d/generated.pcrlock et /var/lib/pcrlock.d/550-firmware-code-late.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-firmware-config, unlock-firmware-config

Ceci est similaire à lock-firmware-code/unlock-firmware-code mais verrouille la configuration du firmware, c'est-à-dire les PCR 1 ("platform-config") et 3 ("external-config").

Cette fonctionnalité doit être utilisée avec précaution car, dans la plupart des scénarios, un changement mineur de la configuration du firmware ne devrait pas invalider les politiques d'accès aux objets TPM2. Notez également que certains systèmes mesurent des informations instables et imprévisibles (par exemple, les tensions CPU actuelles, les températures, dans le cadre des données SMBIOS) pour ces PCR, ce qui signifie que cette forme de verrouillage ne peut pas être utilisée de manière fiable sur de tels systèmes. Utilisez cette fonctionnalité uniquement si le système et le matériel sont bien connus et ne souffrent pas de ces limitations, par exemple dans les environnements virtualisés.

Utilisez unlock-firmware-config avant d'apporter des modifications à la configuration du firmware. Si l'unité systemd-pcrlock-firmware-config.service est activée, elle générera automatiquement un fichier pcrlock à partir des nouvelles mesures.

Ceci écrit/supprime les fichiers /var/lib/pcrlock.d/250-firmware-config-early.pcrlock.d/generated.pcrlock et /var/lib/pcrlock.d/550-firmware-config-late.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-secureboot-policy, unlock-secureboot-policy

Génère/supprime un fichier .pcrlock basé sur la politique SecureBoot actuellement appliquée. Ceci examine les variables EFI SecureBoot, PK, KEK, db, dbx, dbt, dbr et prédit leurs mesures pour la PCR 7 ("secure-boot-policy") au prochain démarrage.

Utilisez unlock-firmware-config avant d'appliquer les mises à jour de la politique SecureBoot. Si l'unité systemd-pcrlock-secureboot-policy.service est activée, elle générera automatiquement un fichier pcrlock à partir de la politique découverte.

Ceci écrit/supprime le fichier /var/lib/pcrlock.d/230-secureboot-policy.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-secureboot-authority, unlock-secureboot-authority

Génère/supprime un fichier .pcrlock basé sur les autorités SecureBoot utilisées pour valider le chemin de démarrage. Les autorités SecureBoot sont les entrées spécifiques de la base de données SecureBoot qui ont été utilisées pour valider les binaires PE UEFI exécutés au démarrage. Ceci examine le journal des événements du démarrage actuel, et utilise les mesures pertinentes sur la PCR 7 ("secure-boot-policy").

Ceci écrit/supprime le fichier /var/lib/pcrlock.d/620-secureboot-authority.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-gpt [DEVICE], unlock-gpt

Génère/supprime un fichier .pcrlock basé sur la table de partitionnement GPT du disque spécifié. Si aucun disque n'est spécifié, il détermine automatiquement le périphérique bloc sous-jacent au système de fichiers racine. Ceci verrouille l'état du partitionnement du disque du support démarré, que le firmware mesure dans la PCR 5 ("boot-loader-config").

Ceci écrit/supprime le fichier /var/lib/pcrlock.d/600-gpt.pcrlock.d/generated.pcrlock.

Ajouté dans la version 255.

lock-pe [BINARY], unlock-pe

Génère/supprime un fichier .pcrlock basé sur le binaire PE spécifié. Ceci est utile pour prédire les mesures que le firmware prend pour la PCR 4 ("boot-loader-code") si le binaire spécifié fait partie du processus de démarrage UEFI. Utilisez ceci sur les binaires de chargeur de démarrage et similaires. Utilisez lock-uki (voir ci-dessous) pour les binaires PE qui sont des images de noyau unifiées (UKI).

Attend un chemin vers le binaire PE comme argument. S'il n'est pas spécifié, lit le binaire depuis STDIN à la place.

Le fichier pcrlock à écrire doit être spécifié via le commutateur --pcrlock=.

Ajouté dans la version 255.

lock-uki [UKI], unlock-uki

Génère/supprime un fichier .pcrlock basé sur l'image de noyau unifiée (UKI) PE spécifiée. Ceci est utile pour prédire les mesures que le firmware prend pour la PCR 4 ("boot-loader-code"), et que systemd-stub(7) prend pour la PCR 11 ("kernel-boot"), si l'UKI spécifiée est démarrée. Ceci est un sur-ensemble de lock-pe.

Attend un chemin vers le binaire UKI PE comme argument. S'il n'est pas spécifié, lit le binaire depuis STDIN à la place.

Le fichier pcrlock à écrire doit être spécifié via le commutateur --pcrlock=.

Ajouté dans la version 255.

lock-machine-id, unlock-machine-id

Génère/supprime un fichier .pcrlock basé sur /etc/machine-id. Ceci est utile pour prédire les mesures que systemd-pcrmachine.service(8) prend pour la PCR 15 ("system-identity").

Ceci écrit/supprime le fichier /var/lib/pcrlock.d/820-machine-id.pcrlock.

Ajouté dans la version 255.

lock-file-system [PATH], unlock-file-system [PATH]

Génère/supprime un fichier .pcrlock basé sur l'identité du système de fichiers. Ceci est utile pour prédire les mesures que systemd-pcrfs@.service(8) prend pour la PCR 15 ("system-identity") pour les systèmes de fichiers racine et /var/.

Ceci écrit/supprime les fichiers /var/lib/pcrlock.d/830-root-file-system.pcrlock et /var/lib/pcrlock.d/840-file-system-path.pcrlock.

Ajouté dans la version 255.

lock-kernel-cmdline [FILE], unlock-kernel-cmdline

Génère/supprime un fichier .pcrlock basé sur /proc/cmdline (ou le fichier spécifié si fourni). Ceci est utile pour prédire les mesures que le noyau Linux prend pour la PCR 9 ("kernel-initrd").

Ceci écrit/supprime le fichier /var/lib/pcrlock.d/710-kernel-cmdline.pcrlock/generated.pcrlock.

Ajouté dans la version 255.

lock-kernel-initrd FILE, unlock-kernel-initrd

Génère/supprime un fichier .pcrlock basé sur une archive cpio d'initrd de noyau. Ceci est utile pour prédire les mesures que le noyau Linux prend pour la PCR 9 ("kernel-initrd"). Ne pas utiliser pour les UKI de systemd-stub(7), car l'initrd est combiné dynamiquement à partir de diverses sources et ne prend donc pas une seule entrée, comme cette commande.

Ceci écrit/supprime le fichier /var/lib/pcrlock.d/720-kernel-initrd.pcrlock/generated.pcrlock.

Ajouté dans la version 255.

lock-raw [FILE], unlock-raw

Génère/supprime un fichier .pcrlock basé sur des données binaires brutes. Les données sont soit lues à partir du fichier spécifié, soit depuis STDIN (si aucun n'est spécifié). Ceci nécessite que --pcrs= soit spécifié. Le fichier .pcrlock généré est écrit dans le fichier spécifié via --pcrlock= ou sur STDOUT (si aucun n'est spécifié).

Ajouté dans la version 255.

OPTIONS

Les options suivantes sont comprises :

--raw-description

Lors de l'affichage du journal des événements TPM2, ne pas tenter de décoder les enregistrements pour fournir une description conviviale du journal des événements. Au lieu de cela, afficher les données de charge utile binaires sous forme échappée.

Ajouté dans la version 255.

--pcr=

Spécifie le numéro de PCR à utiliser. Peut être spécifié plusieurs fois pour sélectionner plusieurs PCR.

Ceci est utilisé par lock-raw et lock-pe pour sélectionner la PCR sur laquelle verrouiller.

Si utilisé avec predict et make-policy, cela remplacera les PCR qui seront incluses dans la prédiction et la politique. Si non spécifié, la valeur par défaut est les PCR 0-5, 7, 11-15. Notez que ces commandes n'incluront aucune PCR dans la prédiction/politique (même si spécifié explicitement) s'il existe des mesures dans le journal des événements qui ne correspondent pas à la valeur PCR actuelle, ou s'il existe des mesures non reconnues dans le journal des événements, ou si des composants définissent des mesures non vues dans le journal des événements.

Ajouté dans la version 255.

--nv-index=

Spécifie l'index NV dans lequel stocker la politique. Respecté par make-policy. Si non spécifié, la commande choisira automatiquement un index NV libre.

Ajouté dans la version 255.

--components=

Prend un chemin pour lire les fichiers *.pcrlock et *.pcrlock.d/*.pcrlock. Peut être utilisé plusieurs fois pour spécifier plusieurs répertoires. Si non spécifié, la valeur par défaut est /etc/pcrlock.d/, /run/pcrlock.d/, /var/lib/pcrlock.d/, /usr/local/lib/pcrlock.d/, /usr/lib/pcrlock.d/.

Ajouté dans la version 255.

--location=

Prend soit une chaîne, soit une paire de chaînes séparées par des deux-points. Configure jusqu'à quel point dans la liste triée des composants définis pour analyser/prédire les PCR. Typiquement, l'outil systemd-pcrlock est invoqué à partir d'un système entièrement démarré après le démarrage et avant l'arrêt. Cela signifie que divers composants définis pour l'arrêt n'ont pas encore été mesurés et ne doivent pas être recherchés. Cette option permet de restreindre les composants à considérer pour l'analyse (en ne tenant compte que des composants avant un certain point, en ignorant ceux après). La chaîne attendue est triée par rapport aux noms de fichiers des composants définis. Tous les composants dont le nom est lexicographiquement postérieur sont ignorés. Cette logique s'applique aux verbes log, predict et make-policy. Si une paire de chaînes séparées par des deux-points est spécifiée, elles sélectionnent les phases du démarrage à inclure dans la prédiction/politique. La première chaîne définit le point de la première prédiction, et la seconde chaîne définit le point de la dernière prédiction. Toutes ces prédictions sont ensuite combinées en un seul ensemble.

Si utilisé avec list-components, la plage de localisation sélectionnée sera mise en surbrillance dans la liste des composants.

La valeur par défaut est ""760-:940-"", ce qui signifie que les politiques générées par défaut couvriront essentiellement toute la durée d'exécution de l'espace utilisateur du système d'exploitation, de l'initrd (car ""760-"" suit de près 750-enter-initrd.pcrlock) jusqu'à (et y compris) l'exécution principale du système (car "940-"" est suivi de près par 950-shutdown.pcrlock). Voir systemd.pcrlock(5) pour une liste complète des composants bien connus, qui illustrent où cette plage est placée par défaut.

Ajouté dans la version 255.

--recovery-pin=

Prend l'une des valeurs ""hide"", ""show"" ou ""query"". La valeur par défaut est ""hide"". Respecté par make-policy. Si ""query"", interrogera l'utilisateur pour un PIN pour déverrouiller l'index TPM2 NV avec. S'il n'y avait pas de politique créée auparavant, ce code PIN est utilisé pour protéger l'index NV nouvellement alloué. Si une politique a été créée auparavant, le code PIN est utilisé pour déverrouiller l'accès en écriture à l'index NV. Si "hide" ou "show" est utilisé, un code PIN est automatiquement généré et — uniquement en cas de "show" — affiché à l'écran. Indépendamment du fait qu'il soit fourni par l'utilisateur ou généré automatiquement, il est stocké sous forme chiffrée dans le fichier de métadonnées de la politique. Le code PIN de récupération peut être utilisé pour retrouver l'accès en écriture à un index NV au cas où la politique d'accès serait devenue obsolète.

Ajouté dans la version 255.

--pcrlock=

Prend un chemin de système de fichiers comme argument. S'il est spécifié, il configure où écrire les données pcrlock générées. Respecté par les différentes commandes lock-*. S'il n'est pas spécifié, un chemin par défaut est généralement utilisé, comme documenté ci-dessus.

Ajouté dans la version 255.

--policy=

Prend un chemin de système de fichiers comme argument. S'il est spécifié, il configure où écrire les métadonnées de politique pcrlock. S'il n'est pas spécifié, il utilise par défaut /var/lib/systemd/pcrlock.json.

Ajouté dans la version 255.

--force

S'il est spécifié avec make-policy, la politique prédite sera écrite dans l'index NV même si elle est détectée comme étant identique à celle précédemment stockée.

Ajouté dans la version 255.

--entry-token=

Définit le jeton d'entrée de démarrage à utiliser pour le nom de fichier de la politique de preuve pcrlock dans la partition EFI System Partition ou XBOOTLDR. Voir l'option bootctl(1) du même nom concernant les valeurs attendues. Ce commutateur n'a d'effet que sur la commande make-policy.

Ajouté dans la version 256.

--quiet

S'il est spécifié, supprime la sortie lorsqu'il est appelé pour is-supported.

Ajouté dans la version 258.

--json=MODE

Affiche la sortie formatée en JSON. Attend l'une des valeurs suivantes : "short" (pour la sortie la plus courte possible sans espaces blancs redondants ni sauts de ligne), "pretty" (pour une version jolie de celle-ci, avec indentation et sauts de ligne) ou "off" (pour désactiver la sortie JSON, par défaut).

--no-pager

Ne pas rediriger la sortie vers un pagineur.

-h, --help

Affiche un court texte d'aide et quitte.

--version

Affiche une courte chaîne de version et quitte.

STATUT DE SORTIE

En cas de succès, 0 est retourné, un code d'échec non nul sinon.
