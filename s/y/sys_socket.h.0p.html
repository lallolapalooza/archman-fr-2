sys_socket.h(0P) Manuel du programmeur POSIX sys_socket.h(0P)

PROLOG

Ce manuel est une page du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

sys/socket.h — en-tête principal des sockets

SYNTAXE

#include <sys/socket.h>

DESCRIPTION

L'en-tête <sys/socket.h> définit le type socklen_t, qui est un type entier d'une largeur d'au moins 32 bits ; voir APPLICATION USAGE.

L'en-tête <sys/socket.h> définit le type entier non signé sa_family_t.

L'en-tête <sys/socket.h> définit la structure sockaddr, qui comprendra au moins les membres suivants :

sa_family_t  sa_family  Famille d'adresses.
char         sa_data[]  Adresse de socket (données de longueur variable).

La structure sockaddr est utilisée pour définir une adresse de socket qui est utilisée dans les fonctions bind(), connect(), getpeername(), getsockname(), recvfrom() et sendto().

L'en-tête <sys/socket.h> définit la structure sockaddr_storage, qui sera :

*
Suffisamment grande pour accueillir toutes les structures d'adresses spécifiques au protocole prises en charge
*
Alignée sur une frontière appropriée de sorte que les pointeurs vers elle puissent être transtypés en pointeurs vers des structures d'adresses spécifiques au protocole et utilisés pour accéder aux champs de ces structures sans problèmes d'alignement

La structure sockaddr_storage comprendra au moins les membres suivants :

sa_family_t   ss_family

Lorsqu'un pointeur vers une structure sockaddr_storage est transtypé en pointeur vers une structure sockaddr, le champ ss_family de la structure sockaddr_storage sera mappé sur le champ sa_family de la structure sockaddr. Lorsqu'un pointeur vers une structure sockaddr_storage est transtypé en pointeur vers une structure d'adresse spécifique au protocole, le champ ss_family sera mappé sur un champ de cette structure qui est de type sa_family_t et qui identifie la famille d'adresses du protocole.

L'en-tête <sys/socket.h> définit la structure msghdr, qui comprendra au moins les membres suivants :

void          *msg_name        Adresse optionnelle.
socklen_t      msg_namelen     Taille de l'adresse.
struct iovec  *msg_iov         Tableau scatter/gather.
int            msg_iovlen      Membres dans msg_iov.
void          *msg_control     Données auxiliaires ; voir ci-dessous.
socklen_t      msg_controllen  Taille du tampon de données auxiliaires len.
int            msg_flags       Indicateurs sur le message reçu.

La structure msghdr est utilisée pour minimiser le nombre de paramètres directement fournis aux fonctions recvmsg() et sendmsg(). Cette structure est utilisée comme paramètre valeur‐résultat dans la fonction recvmsg() et seulement en valeur pour la fonction sendmsg().

L'en-tête <sys/socket.h> définit la structure iovec telle que décrite dans <sys/uio.h>.

L'en-tête <sys/socket.h> définit la structure cmsghdr, qui comprendra au moins les membres suivants :

socklen_t  cmsg_len    Nombre d'octets de données, y compris le cmsghdr.
int        cmsg_level  Protocole d'origine.
int        cmsg_type   Type spécifique au protocole.

La structure cmsghdr est utilisée pour le stockage des informations des objets de données auxiliaires.

Les données auxiliaires consistent en une séquence de paires, chacune composée d'une structure cmsghdr suivie d'un tableau de données. Le tableau de données contient le message de données auxiliaires, et la structure cmsghdr contient des informations descriptives qui permettent à une application de correctement analyser les données.

Les valeurs pour cmsg_level seront des valeurs légales pour l'argument level des fonctions getsockopt() et setsockopt(). La documentation système spécifiera les définitions de cmsg_type pour les protocoles pris en charge.

Les données auxiliaires sont également possibles au niveau du socket. L'en-tête <sys/socket.h> définit la constante symbolique suivante pour une utilisation comme valeur cmsg_type lorsque cmsg_level est SOL_SOCKET :

SCM_RIGHTS
Indique que le tableau de données contient les droits d'accès à envoyer ou recevoir.

L'en-tête <sys/socket.h> définit les macros suivantes pour accéder aux tableaux de données dans les données auxiliaires associées à un en-tête de message :

CMSG_DATA(cmsg)

Si l'argument est un pointeur vers une structure cmsghdr, cette macro renvoie un pointeur de caractère non signé vers le tableau de données associé à la structure cmsghdr.
CMSG_NXTHDR(mhdr,cmsg)

Si le premier argument est un pointeur vers une structure msghdr et le second argument est un pointeur vers une structure cmsghdr dans les données auxiliaires pointées par le champ msg_control de cette structure msghdr, cette macro renvoie un pointeur vers la structure cmsghdr suivante, ou un pointeur nul si cette structure est la dernière cmsghdr dans les données auxiliaires.
CMSG_FIRSTHDR(mhdr)

Si l'argument est un pointeur vers une structure msghdr, cette macro renvoie un pointeur vers la première structure cmsghdr dans les données auxiliaires associées à cette structure msghdr, ou un pointeur nul s'il n'y a pas de données auxiliaires associées à la structure msghdr.

L'en-tête <sys/socket.h> définit la structure linger, qui comprendra au moins les membres suivants :

int  l_onoff   Indique si l'option linger est activée.
int  l_linger  Temps de linger, en secondes.

L'en-tête <sys/socket.h> définit les constantes symboliques suivantes avec des valeurs distinctes :

SOCK_DGRAM
Socket de datagramme.
SOCK_RAW
Interface de protocole brut.
SOCK_SEQPACKET
Socket de paquet séquencé.
SOCK_STREAM
Socket de flux d'octets.

L'en-tête <sys/socket.h> définit la constante symbolique suivante pour une utilisation comme argument level de setsockopt() et getsockopt().

SOL_SOCKET
Options à accéder au niveau du socket, pas au niveau du protocole.

L'en-tête <sys/socket.h> définit les constantes symboliques suivantes avec des valeurs distinctes pour une utilisation comme argument option_name dans les appels getsockopt() ou setsockopt() (voir le volume Interfaces système de POSIX.1‐2017, Section 2.10.16, Utilisation des options) :

SO_ACCEPTCONN
Le socket accepte des connexions.
SO_BROADCAST
La transmission de messages de diffusion est prise en charge.
SO_DEBUG
Les informations de débogage sont enregistrées.
SO_DONTROUTE
Ignorer le routage normal.
SO_ERROR
État d'erreur du socket.
SO_KEEPALIVE
Les connexions sont maintenues actives avec des messages périodiques.
SO_LINGER
Le socket reste actif à la fermeture.
SO_OOBINLINE
Les données hors bande sont transmises en ligne.
SO_RCVBUF
Taille du tampon de réception.

NOM

socket, accept, bind, connect, getpeername, getsockname, getsockopt, listen, recv, recvfrom, recvmsg, send, sendmsg, sendto, setsockopt, shutdown, sockatmark, socketpair - interfaces de sockets

SYNOPSIS

#include <sys/socket.h>

DESCRIPTION

Le fichier d'en-tête <sys/socket.h> définit diverses constantes, structures et types nécessaires pour la programmation des sockets.

Il définit les constantes symboliques suivantes pour le type de socket, utilisé comme deuxième argument de la fonction socket():

SOCK_DGRAM
Socket datagramme.
SOCK_RAW
Socket brut.
SOCK_RDM
Socket de datagramme fiable (non spécifié).
SOCK_SEQPACKET
Socket de paquet séquentiel.
SOCK_STREAM
Socket de flux.

Il définit également les constantes symboliques suivantes pour le niveau et le nom de l'option de socket, utilisés avec les fonctions getsockopt() et setsockopt():

SOL_SOCKET
Niveau pour les options de socket générales.
SO_ACCEPTCONN
Indique si le socket est en état d'écoute pour les connexions.
SO_BROADCAST
Autorise l'envoi de datagrammes de diffusion.
SO_DEBUG
Active/désactive la journalisation de débogage du socket.
SO_DONTROUTE
Indique si le routage doit être ignoré.
SO_ERROR
Obtenir les informations d'erreur non traitées pour le socket.
SO_KEEPALIVE
Maintient la connexion active.
SO_LINGER
Active/désactive la suspension de la fermeture du socket.
SO_OOBINLINE
Indique si les données hors bande doivent être placées dans le flux de données normal.
SO_RCVBUF
Taille du tampon de réception.
SO_RCVLOWAT
Seuil bas de réception (low water mark).
SO_RCVTIMEO
Délai d'attente de réception.
SO_REUSEADDR
Autorise la réutilisation des adresses locales.
SO_SNDBUF
Taille du tampon d'envoi.
SO_SNDLOWAT
Seuil bas d'envoi (low water mark).
SO_SNDTIMEO
Délai d'attente d'envoi.
SO_TYPE
Type du socket.

Le fichier d'en-tête <sys/socket.h> définit la constante symbolique suivante pour être utilisée comme longueur maximale de la file d'attente de backlog qui peut être spécifiée par le champ backlog de la fonction listen():

SOMAXCONN
Longueur maximale de la file d'attente de backlog.

Le fichier d'en-tête <sys/socket.h> définit les constantes symboliques suivantes avec des valeurs distinctes pour être utilisées comme valeurs valides pour le champ msg_flags de la structure msghdr, ou le paramètre flags dans les appels recv(), recvfrom(), recvmsg(), send(), sendmsg(), ou sendto():

MSG_CTRUNC
Données de contrôle tronquées.
MSG_DONTROUTE
Envoi sans utiliser les tables de routage.
MSG_EOR
Termine un enregistrement (si supporté par le protocole).
MSG_OOB
Données hors bande (out-of-band).
MSG_NOSIGNAL
Aucun signal SIGPIPE généré lors d'une tentative d'envoi sur un socket orienté flux qui n'est plus connecté.
MSG_PEEK
Laisse les données reçues dans la file d'attente.
MSG_TRUNC
Données normales tronquées.
MSG_WAITALL
Tente de remplir le tampon de lecture.

Le fichier d'en-tête <sys/socket.h> définit les constantes symboliques suivantes avec des valeurs distinctes:

AF_INET
Sockets du domaine Internet pour une utilisation avec les adresses IPv4.
AF_INET6
Sockets du domaine Internet pour une utilisation avec les adresses IPv6.
AF_UNIX
Sockets du domaine UNIX.
AF_UNSPEC
Non spécifié.

La valeur de AF_UNSPEC sera 0.

Le fichier d'en-tête <sys/socket.h> définit les constantes symboliques suivantes avec des valeurs distinctes:

SHUT_RD
Désactive les futures opérations de réception.
SHUT_RDWR
Désactive les futures opérations d'envoi et de réception.
SHUT_WR
Désactive les futures opérations d'envoi.

Le fichier d'en-tête <sys/socket.h> déclare les types size_t et ssize_t comme décrit dans <sys/types.h>.

Les éléments suivants seront déclarés comme fonctions et pourront également être définis comme macros. Les prototypes de fonctions seront fournis.

int     listen(int, int);
ssize_t recv(int, void *, size_t, int);

        struct sockaddr *restrict, socklen_t *restrict);
ssize_t recvmsg(int, struct msghdr *, int);
ssize_t send(int, const void *, size_t, int);
ssize_t sendmsg(int, const struct msghdr *, int);
ssize_t sendto(int, const void *, size_t, int, const struct sockaddr *,
        socklen_t);
int     setsockopt(int, int, int, const void *, socklen_t);

UTILISATION APPLICATIVE

Pour éviter les problèmes de portabilité, il est recommandé que les applications n'utilisent pas de valeurs supérieures à 231 -1 pour le type socklen_t.

La structure sockaddr_storage résout le problème de la déclaration de stockage pour les variables automatiques qui est suffisamment grande et suffisamment alignée pour stocker la structure de données d'adresse de socket de n'importe quelle famille. Par exemple, un code avec un descripteur de fichier et sans le contexte de la famille d'adresses peut passer un pointeur vers une variable de ce type, où un pointeur vers une structure d'adresse de socket est attendu dans des appels tels que getpeername(), et déterminer la famille d'adresses en accédant au contenu reçu après l'appel.

L'exemple ci-dessous illustre une structure de données qui s'aligne sur une frontière de 64 bits. Un champ défini par l'implémentation _ss_align suivant _ss_pad1 est utilisé pour forcer un alignement de 64 bits qui couvre un alignement approprié suffisant pour les besoins d'au moins les structures de données d'adresse sockaddr_in6 (IPv6) et sockaddr_in (IPv4). La taille du champ de remplissage _ss_pad1 dépend de la frontière d'alignement choisie. La taille du champ de remplissage _ss_pad2 dépend de la valeur de la taille globale choisie pour la taille totale de la structure. Cette taille et cet alignement sont représentés dans l'exemple ci-dessus par des constantes définies par l'implémentation (non requises) _SS_MAXSIZE (valeur choisie 128) et _SS_ALIGNMENT (valeur choisie 8). Les constantes _SS_PAD1SIZE (valeur dérivée 6) et _SS_PAD2SIZE (valeur dérivée 112) sont également à titre d'illustration et ne sont pas requises. Les définitions définies par l'implémentation et les noms de champs de structure ci-dessus commencent par un <underscore> pour indiquer l'espace de noms privé de l'implémentation. Le code portable ne doit pas accéder ni faire référence à ces champs ou constantes.

/*
 * Conception souhaitée de la taille et de l'alignement maximum.
 */
#define _SS_MAXSIZE 128
    /* Taille maximale définie par l'implémentation. */
#define _SS_ALIGNSIZE (sizeof(int64_t))
    /* Alignement souhaité défini par l'implémentation. */
/*
 * Définitions utilisées pour la conception du remplissage de la structure
 * sockaddr_storage.
 */
#define _SS_PAD1SIZE (_SS_ALIGNSIZE - sizeof(sa_family_t))
#define _SS_PAD2SIZE (_SS_MAXSIZE - (sizeof(sa_family_t)+ \
                      _SS_PAD1SIZE + _SS_ALIGNSIZE))
struct sockaddr_storage {
    sa_family_t  ss_family;  /* Famille d'adresses. */
/*
 * Les champs suivants sont définis par l'implémentation.
 */
    char _ss_pad1[_SS_PAD1SIZE];
        /* Remplissage de 6 octets ; ceci est pour faire en sorte que le remplissage
           défini par l'implémentation jusqu'au champ d'alignement qui suit
           explicitement dans la structure de données. */
    int64_t _ss_align;  /* Champ pour forcer l'alignement du stockage de la
                           structure souhaité. */
    char _ss_pad2[_SS_PAD2SIZE];
        /* Remplissage de 112 octets pour atteindre la taille souhaitée,
           la valeur _SS_MAXSIZE moins la taille des champs ss_family,
           __ss_pad1, __ss_align est 112. */
};
