NOM

st discosrv - Serveur de découverte Syncthing

SYNTAXE

st discosrv [--debug] [--http] [--compression] [--version]
           [--cert=<fichier>] [--key=<chaîne>]
           [--listen=<adresse>] [--metrics-listen=<adresse>]
           [--db-dir=<chaîne>] [--db-flush-interval=<chaîne>]

DESCRIPTION

Syncthing utilise un serveur de découverte pour trouver des pairs sur Internet. N'importe qui peut exécuter un serveur de découverte et y pointer les installations Syncthing. Le projet Syncthing maintient également un cluster global pour un usage public.

OPTIONS

--debug
Activer la sortie de débogage.
--http
Écouter en HTTP (derrière un proxy HTTPS).
--version
Afficher le numéro de version actuel et quitter.
--compression
Activer la compression GZIP des réponses HTTP.
--cert=<fichier>
Fichier de certificat (par défaut “./cert.pem”). Non utilisé en mode –http.
--key=<fichier>
Fichier de clé (par défaut “./key.pem”). Non utilisé en mode –http.
--listen=<adresse>
Adresse d'écoute (par défaut “:8443”).
--metrics-listen=<adresse>
Adresse d'écoute du point d'accès aux métriques compatible Prometheus (désactivé par défaut).
--db-dir=<chaîne>
Répertoire de la base de données, où les données sont stockées (par défaut “.”).
--db-flush-interval=<chaîne>
Intervalle auquel la base de données en mémoire est vidée sur le disque (par défaut “5m”).

POINTER SYNCTHING VERS VOTRE SERVEUR DE DÉCOUVERTE

Par défaut, Syncthing utilise un certain nombre de serveurs de découverte globaux, représentés par l'entrée default dans la liste des serveurs de découverte. Pour que Syncthing utilise votre propre instance de st discosrv, ouvrez l'interface graphique web de Syncthing. Allez dans les paramètres, Serveur de découverte global et ajoutez l'adresse hôte de st discosrv à la liste séparée par des virgules, par exemple https://disco.example.com:8443/. Notez que st discosrv utilise le port 8443 par défaut. Pour que st discosrv soit disponible sur Internet avec une adresse IP dynamique, vous aurez besoin d'un service DNS dynamique.

Obsolète depuis la version v0.14.44 : Les versions antérieures nécessitent l'ajout de /v2/ à l'adresse du serveur de découverte, par exemple https://disco.example.com:8443/v2/.

Si vous souhaitez utiliser *uniquement* votre propre serveur de découverte, supprimez l'entrée default de la liste.

MISE EN PLACE

Description

Ce guide suppose que vous avez déjà configuré Syncthing. Si ce n'est pas le cas, consultez d'abord *Premiers pas*.

Installation

Configuration

NOTE :

Si vous exécutez une instance de Syncthing sur le serveur de découverte, vous devez soit ajouter cette instance à d'autres appareils en utilisant une adresse statique, soit lier le serveur de découverte et les instances Syncthing à des adresses IP différentes.

Certificats

Le serveur de découverte fournit un service via HTTPS. Pour garantir des connexions sécurisées depuis les clients, il y a trois options :

  • Utiliser une paire de certificats signés par une AC pour le nom de domaine que vous utiliserez pour le serveur de découverte. C'est comme pour tout autre site web HTTPS ; les clients authentifieront le serveur en fonction de son certificat et de son nom de domaine.
  • Utiliser n'importe quelle paire de certificats et laisser les clients authentifier le serveur en fonction de son « ID d'appareil » (similaire à l'authentification Syncthing à Syncthing). Cette option peut être utilisée avec le certificat généré automatiquement par le serveur de découverte.
  • Passer l'option --http si le serveur de découverte est derrière un proxy inverse sécurisé par SSL. Voir ci-dessous pour la configuration.

Pour les deux premières options, le serveur de découverte doit se voir indiquer les chemins vers le certificat et la clé au démarrage. Ce n'est pas nécessaire avec l'option http :

$ st discosrv --cert=/chemin/vers/cert.pem --key=/chemin/vers/key.pem
L'ID d'appareil du serveur est 7DDRT7J-UICR4PM-PBIZYL3-MZOJ7X7-EX56JP6-IK6HHMW-S7EK32W-G3EUPQA

Le serveur de découverte affiche son ID d'appareil au démarrage. Dans le cas où vous utiliseriez un certificat non signé par une AC, cet ID d'appareil (empreinte) doit être donné aux clients dans l'URL du serveur de découverte :

https://disco.example.com:8443/?id=7DDRT7J-UICR4PM-PBIZYL3-MZOJ7X7-EX56JP6-IK6HHMW-S7EK32W-G3EUPQA

Sinon, l'URL sera :

https://disco.example.com:8443/

Configuration du Proxy Inverse

Ajouté dans la version 1.8.0 : Un nouveau header HTTP « X-Client-Port » a été ajouté.

Le serveur de découverte peut être exécuté derrière un proxy inverse sécurisé par SSL. Cela permet :

  • D'utiliser un nom de sous-domaine sans avoir besoin d'ajouter un numéro de port à l'URL
  • De partager un certificat SSL avec plusieurs services sur le même serveur

Notez qu'après cette configuration, si le proxy utilise un certificat HTTPS valide, les clients doivent omettre le paramètre ?id=... de l'URL du serveur de découverte dans leur configuration. La validation côté client sera effectuée en vérifiant le certificat HTTPS du serveur proxy visible. Si, cependant, le proxy utilise un certificat auto-signé ou invalide d'une manière ou d'une autre, les clients doivent toujours définir le paramètre ?id=... avec le hachage calculé du certificat du proxy. L'utilisation d'une telle configuration est déconseillée et n'est pas couverte sur cette page. Privilégiez toujours l'utilisation de certificats valides et largement reconnus.

NAME

syncthing-discosrv - Syncthing discovery server

SYNOPSIS

syncthing-discosrv [-paths=PATH,...] [-local-discovery=PATH] [-http]

DESCRIPTION

The discovery server is a simple HTTP server that implements the Syncthing discovery protocol. It is used to find peers on the local network or across the internet. By default, it listens on UDP port 22027 for discovery requests.

The discovery server itself does not require any configuration file. Its behavior can be controlled by command line flags.

It is also possible to run the discovery server behind a reverse proxy. See SETTING UP for more information.

OPTIONS

-paths=PATH,...
A comma-separated list of paths to be served by the discovery server. These paths will be available at the root of the HTTP server. For example, if you specify -paths=/foo,/bar, then “/foo” will serve the discovery protocol, and “/bar” will also serve the discovery protocol.
-local-discovery=PATH
If set, the discovery server will listen on the specified path for local discovery requests. This is useful for running the discovery server behind a reverse proxy that handles SSL termination.
-http
Enable HTTP support. By default, the discovery server only listens on UDP port 22027. This flag enables it to listen on HTTP as well, on port 21027 by default.

POINTING SYNCTHING AT YOUR DISCOVERY SERVER

To make Syncthing use your custom discovery server, you need to add it to the discovery servers list in Syncthing's configuration. You can do this by editing the config.xml file and adding the following lines to the <options> section:

<list>
    <servers>
        <server>your-discovery-server.example.com</server>
    </servers>
</list>

Replace “your-discovery-server.example.com” with the actual hostname or IP address of your discovery server.

If you are using the HTTP interface of the discovery server, you should also specify the port: “your-discovery-server.example.com:21027”.

SETTING UP

The discovery server is intended to be run behind a reverse proxy, especially if you want to use HTTPS. The proxy will handle SSL termination and forward requests to the discovery server.

Requirements

  • Run the discovery server using the -http flag: st discosrv -http.
  • SSL certificate/key configured for the reverse proxy.
  • The “X-Forwarded-For” HTTP header must be passed through with the client's real IP address.
  • The “X-Client-Port” HTTP header should be passed through, containing the client's real connection port.
  • The “X-SSL-Cert” HTTP header must be passed through with the PEM-encoded client SSL certificate. This will be present in POST requests and may be empty in GET requests from clients. If you see syncthing-discosrv outputting no certificates when receiving POST requests, that’s because the proxy is not passing this header through.
  • The proxy must request the client SSL certificate but not require it to be signed by a trusted CA.

RequestHeader set X-SSL-Cert "%{SSL_CLIENT_CERT}s"
