NOM

systemd-coredump, systemd-coredump.socket, systemd-coredump@.service - Acquérir, sauvegarder et traiter les vidages mémoire (core dumps)

SYNTAXE

/usr/lib/systemd/systemd-coredump

/usr/lib/systemd/systemd-coredump --backtrace

systemd-coredump@.service

systemd-coredump.socket

DESCRIPTION

systemd-coredump@.service est un service système pour traiter les vidages mémoire (core dumps). Il enregistrera un résumé de l'événement dans systemd-journald.service(8), incluant des informations sur l'identifiant du processus, le propriétaire, le signal qui a tué le processus, et la trace de la pile si possible. Il peut également sauvegarder le vidage mémoire pour un traitement ultérieur. Voir la section "Informations sur le processus planté" ci-dessous.

Le comportement d'un programme spécifique lors de la réception d'un signal est régi par quelques facteurs décrits en détail dans core(5). En particulier, le vidage mémoire ne sera traité que lorsque les limites de ressources du processus liées (RLIMIT_CORE) sont suffisantes.

Les vidages mémoire peuvent être écrits dans le journal ou sauvegardés sous forme de fichier. Dans les deux cas, ils peuvent être récupérés pour un traitement ultérieur, par exemple dans gdb(1). Voir coredumpctl(1), en particulier les verbes list et debug.

Par défaut, systemd-coredump enregistrera le vidage mémoire dans le journal, incluant une trace de pile si possible, et stockera le vidage mémoire lui-même (une image du contenu de la mémoire du processus) dans un fichier externe dans /var/lib/systemd/coredump/. Ces vidages mémoire sont supprimés après quelques jours par défaut ; voir /usr/lib/tmpfiles.d/systemd.conf pour les détails. Notez que la suppression des fichiers core du système de fichiers et la suppression des entrées du journal sont indépendantes, et le fichier core peut être présent sans l'entrée du journal, et les entrées du journal peuvent pointer vers des fichiers core supprimés depuis. Des métadonnées sont attachées aux fichiers core sous forme d'attributs étendus, donc les fichiers core sont utiles à certaines fins même sans toutes les métadonnées disponibles dans l'entrée du journal.

Pour plus de détails, voir systemd Coredump Handling[1].

Invocation de systemd-coredump

L'exécutable systemd-coredump effectue le travail réel. Il est appelé deux fois : une fois en tant que gestionnaire par le noyau, et une seconde fois dans systemd-coredump@.service pour écrire réellement les données dans le journal et traiter et sauvegarder le fichier core.

Lorsque le noyau invoque systemd-coredump pour gérer un vidage mémoire, il s'exécute en mode privilégié et se connectera au socket créé par l'unité systemd-coredump.socket, qui à son tour lancera une instance non privilégiée de systemd-coredump@.service pour traiter le vidage mémoire. Par conséquent, systemd-coredump.socket et systemd-coredump@.service sont des unités auxiliaires qui effectuent le traitement réel des vidages mémoire et sont soumises à la gestion normale des services.

Il est également possible d'invoquer systemd-coredump avec l'option --backtrace. Dans ce cas, systemd-coredump attend une entrée de journal dans le Journal Export Format sur l'entrée standard. L'entrée devrait contenir un champ MESSAGE= et tous les champs de métadonnées supplémentaires que l'appelant juge raisonnables. systemd-coredump ajoutera des champs de métadonnées supplémentaires de la même manière qu'il le fait pour les vidages mémoire reçus du noyau. Dans ce mode, aucun vidage mémoire n'est stocké dans le journal.

Vidages mémoire dans les Conteneurs/Espaces de noms (Namespaces)

Le service systemd-coredump@.service tentera automatiquement d'extraire une trace de pile d'un processus lorsqu'il plante. Pour cette trace de pile, les symboles seront résolus en fonction des informations de débogage intégrées dans l'image ELF plantée, ou des informations de débogage équivalentes disponibles séparément sur le système hôte. Pour les processus qui plantent dans des conteneurs locaux ou d'autres sandboxes basées sur des espaces de noms de montage, ces informations de débogage auxiliaires ne sont généralement pas disponibles sur l'hôte (simplement parce que les conteneurs exécutent généralement des versions logicielles différentes de celles de l'hôte). systemd-coredump fournit deux mécanismes pour résoudre ce problème :

1.Pour les conteneurs de système d'exploitation complet exécutant systemd à l'intérieur, il est conseillé d'activer CoredumpReceive= sur l'unité (voir systemd.resource-control(5)), ce qui garantit que les vidages mémoire d'un conteneur sont tentés d'être transférés à systemd-coredump@.service s'exécutant à l'intérieur du conteneur, c'est-à-dire que le conteneur traite et stocke ses propres vidages mémoire. Notez que systemd-nspawn(8) utilise ce mode par défaut si invoqué avec le commutateur --boot. Ce mode de fonctionnement est généralement recommandé pour des raisons de sécurité : le traitement des vidages mémoire, sensible à la sécurité, est effectué dans les limites du conteneur lui-même, par le propre code du conteneur, soutenu par son propre stockage.
2.Alternativement, pour des conteneurs plus restreints (qui n'exécutent pas un système d'init approprié comme PID 1), il est possible d'activer le traitement du vidage mémoire sur l'hôte, avec accès aux informations de débogage du conteneur lui-même. Ce mode de fonctionnement doit être activé via EnterNamespace= dans coredump.conf(5), et est désactivé par défaut pour des raisons de sécurité.

Si CoredumpReceive= est activé sur l'unité du conteneur auquel appartient le vidage mémoire, et EnterNamespace= est activé dans le fichier de configuration coredump.conf, la première option a la priorité.

CONFIGURATION

Pour les programmes démarrés par systemd, les limites de ressources du processus peuvent être définies par la directive LimitCORE=, voir systemd.exec(5).

Afin d'être utilisé par le noyau pour gérer les vidages mémoire, systemd-coredump doit être configuré dans le paramètre kernel.core_pattern de sysctl(8). La syntaxe de ce paramètre est expliquée dans core(5). systemd installe le fichier /usr/lib/sysctl.d/50-coredump.conf qui configure kernel.core_pattern en conséquence. Ce fichier peut être masqué ou remplacé pour utiliser un paramètre différent en suivant les règles normales de sysctl.d(5). Si la configuration sysctl est modifiée, elle doit être mise à jour dans le noyau avant de prendre effet, voir sysctl(8) et systemd-sysctl(8).

Afin d'être utilisé en mode --backtrace, un gestionnaire de trace de pile approprié doit être installé du côté de l'expéditeur. Par exemple, dans le cas de python(1), cela signifie qu'un sys.excepthook doit être installé, voir systemd-coredump-python[3].

Le comportement de systemd-coredump lui-même est configuré via le fichier de configuration /etc/systemd/coredump.conf et les snippets correspondants /etc/systemd/coredump.conf.d/*.conf, voir coredump.conf(5). Une nouvelle instance de systemd-coredump est invoquée à chaque réception d'un vidage mémoire. Par conséquent, les modifications apportées à ces fichiers prendront effet la prochaine fois qu'un vidage mémoire sera reçu.

Les ressources utilisées par les fichiers de vidage mémoire sont restreintes de deux manières. Les paramètres tels que la taille maximale des vidages mémoire acquis et des fichiers peuvent être définis dans les fichiers /etc/systemd/coredump.conf et les snippets mentionnés ci-dessus. De plus, le temps de stockage des fichiers de vidage mémoire est restreint par systemd-tmpfiles, les paramètres correspondants se trouvent par défaut dans /usr/lib/tmpfiles.d/systemd.conf. Par défaut, les vidages mémoire sont supprimés après quelques jours ; voir le fichier ci-dessus pour les détails.

Désactivation du traitement des vidages mémoire

Pour désactiver le traitement potentiellement gourmand en ressources par systemd-coredump, définissez

Storage=none
ProcessSizeMax=0

dans coredump.conf(5).

COREDUMP_BY_PIDFD=

Ajouté dans la version 258.

COREDUMP_TIMESTAMP=

L'heure du crash telle que rapportée par le noyau (en μs depuis l'époque).

Ajouté dans la version 248.

COREDUMP_RLIMIT=

La limite logicielle de la taille des fichiers core, voir getrlimit(2).

Ajouté dans la version 248.

COREDUMP_UNIT=, COREDUMP_SLICE=

Les noms de l'unité système et du slice.

Lorsque le processus qui a planté se trouvait dans un conteneur, ce sont les noms d'unités à l'extérieur, dans le gestionnaire système principal.

Ajouté dans la version 248.

COREDUMP_CGROUP=

Le cgroup principal de l'unité du processus qui a planté.

Lorsque le processus qui a planté se trouvait dans un conteneur, il s'agit du chemin complet, tel qu'il est vu de l'extérieur du conteneur.

Ajouté dans la version 248.

COREDUMP_PROC_CGROUP=

Informations sur le groupe de contrôle au format utilisé dans /proc/self/cgroup. Sur les systèmes avec la hiérarchie cgroup unifiée, il s'agit d'un seul chemin préfixé par "0::", et de plusieurs chemins préfixés par des numéros de contrôleur sur les systèmes hérités.

Lorsque le processus qui a planté se trouvait dans un conteneur, il s'agit du chemin complet, tel qu'il est vu de l'extérieur du conteneur.

Ajouté dans la version 248.

COREDUMP_OWNER_UID=, COREDUMP_USER_UNIT=, COREDUMP_SESSION=

L'UID numérique de l'utilisateur propriétaire de la session de connexion ou de l'unité utilisateur systemd du processus qui a planté, l'unité de gestion des utilisateurs et l'identifiant de session. Ces trois champs ne sont présents que pour les processus utilisateur.

Lorsque le processus qui a planté se trouvait dans un conteneur, ce sont les valeurs à l'extérieur, dans le système principal.

Ajouté dans la version 248.

COREDUMP_SIGNAL_NAME=, COREDUMP_SIGNAL=

Le nom du signal de terminaison (avec le préfixe "SIG" [4]) et sa valeur numérique. (Les deux sont inclus car les numéros de signaux varient selon l'architecture.)

Ajouté dans la version 248.

COREDUMP_CWD=, COREDUMP_ROOT=

Le répertoire de travail actuel et le répertoire racine du processus qui a planté.

Lorsque le processus qui a planté se trouve dans un conteneur, ces chemins sont relatifs à la racine de l'espace de noms de montage du conteneur.

Ajouté dans la version 248.

COREDUMP_DUMPABLE=

Le champ PR_GET_DUMPABLE tel que rapporté par le noyau, voir prctl(2).

Ajouté dans la version 258.

COREDUMP_OPEN_FDS=

Informations sur les descripteurs de fichiers ouverts, dans le format suivant :

Ajouté dans la version 248.

COREDUMP_EXE=

La destination du lien symbolique /proc/pid/exe.

Lorsque le processus qui a planté se trouve dans un conteneur, ce chemin est relatif à la racine de l'espace de noms de montage du conteneur.

Ajouté dans la version 248.

COREDUMP_CMDLINE=, COREDUMP_COMM=, COREDUMP_ENVIRON=, COREDUMP_PROC_AUXV=, COREDUMP_PROC_LIMITS=, COREDUMP_PROC_MAPS=, COREDUMP_PROC_MOUNTINFO=, COREDUMP_PROC_STATUS=

Champs qui mappent les entrées par processus dans le système de fichiers /proc/ : /proc/pid/cmdline (la ligne de commande du processus qui a planté), /proc/pid/comm (le nom de commande associé au processus), /proc/pid/environ (le bloc d'environnement du processus qui a planté), /proc/pid/auxv (le vecteur auxiliaire du processus qui a planté, voir getauxval(3)), /proc/pid/limits (les limites de ressources douces et dures), /proc/pid/maps (les régions mémoire visibles par le processus et leurs permissions d'accès), /proc/pid/mountinfo (les points de montage dans l'espace de noms de montage du processus), /proc/pid/status (divers métadonnées sur le processus).

Voir proc(5) pour plus d'informations.

Ajouté dans la version 248.

COREDUMP_HOSTNAME=

Le nom d'hôte du système.

Lorsque le processus qui a planté se trouvait dans un conteneur, il s'agit du nom d'hôte du conteneur.

Ajouté dans la version 248.

COREDUMP_CONTAINER_CMDLINE=

Pour les processus exécutés dans un conteneur, la ligne de commande du processus qui lance le conteneur (le premier processus parent avec un espace de noms de montage différent).

Ajouté dans la version 248.

COREDUMP=

Lorsque le core est stocké dans le journal, l'image core elle-même.

Ajouté dans la version 248.

COREDUMP_FILENAME=

Lorsque le core est stocké en externe, le chemin vers le fichier core.

Ajouté dans la version 248.

COREDUMP_TRUNCATED=

Défini sur "1" lorsque le coredump enregistré a été tronqué. (Une image core partielle peut encore être traitée par certains outils, bien que toutes les informations ne soient évidemment pas disponibles.)

Ajouté dans la version 248.

COREDUMP_PACKAGE_NAME=, COREDUMP_PACKAGE_VERSION=, COREDUMP_PACKAGE_JSON=

Si l'exécutable contenait des notes ELF de métadonnées .package, elles seront analysées et attachées. Le package et la version du module ELF 'principal' (c'est-à-dire l'exécutable) seront ajoutés individuellement. Le contenu JSON de tous les modules sera ajouté sous forme d'un seul objet JSON, chacun avec le nom du module comme clé. Pour plus d'informations sur ce format de métadonnées et son contenu, voir le document Package Metadata for Executable Files[5].

Ajouté dans la version 249.

MESSAGE=

Le message généré par systemd-coredump qui inclut la trace de la pile s'il a été généré avec succès. Lorsque systemd-coredump est invoqué avec --backtrace, ce champ est fourni par l'appelant.

Ajouté dans la version 248.

NAME

systemd-coredump.socket, systemd-coredump - Core dump handling socket

SYNOPSIS

systemd-coredump.socket

DESCRIPTION

The systemd-coredump.socket is a systemd socket unit that listens for incoming connections for core dumps. When a process crashes and generates a core dump, the kernel can be configured to send this core dump to a specified handler. This socket unit provides the mechanism for that handler, typically systemd-coredump(8), to receive the core dump data.

The primary purpose of this socket is to enable the systemd-coredump service to collect and process core dumps from crashing processes. When a core dump is generated, the kernel sends it to the path specified in /proc/sys/kernel/core_pattern. If this pattern includes the socket option (e.g., using a pipe character `|` followed by the path to systemd-coredump), the core dump data will be sent over this socket to the systemd-coredump service.

CONFIGURATION

This socket unit is typically enabled and started by default as part of the systemd-coredump service. No specific user configuration is usually required, as it is managed by the systemd-coredump package.

The /proc/sys/kernel/core_pattern setting determines how core dumps are handled. To ensure core dumps are captured by systemd-coredump, this file should contain a pattern that directs the output to |/usr/lib/systemd/systemd-coredump (the exact path may vary depending on the distribution).

INFORMATION ABOUT THE CRASHED PROCESS

When systemd-coredump receives a core dump via this socket, it automatically collects various pieces of information about the crashed process, including:

  • The executable file.
  • The command line arguments.
  • The environment variables.
  • The current working directory.
  • The process ID and parent process ID.
  • The username and group of the user running the process.
  • System information like the kernel version and distribution.

This information is crucial for diagnosing the cause of the crash.

SEE ALSO

systemd-coredump(8), core(5)

NOTES

This socket unit is a key component in systemd's centralized core dump management. It allows for consistent and automated handling of core dumps across the system.

For more detailed information on configuring core dump handling, refer to the systemd documentation or your distribution's specific guides.
