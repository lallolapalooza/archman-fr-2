SYSTEMD-SYSTEM.CONF(5) systemd-system.conf SYSTEMD-SYSTEM.CONF(5)

NOM

systemd-system.conf, system.conf.d, systemd-user.conf, user.conf.d - Fichiers de configuration du gestionnaire de services système et de session

SYNTAXE

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/system.conf.d/*.conf, /run/systemd/system.conf.d/*.conf, /usr/lib/systemd/system.conf.d/*.conf

~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf, /etc/systemd/user.conf.d/*.conf, /run/systemd/user.conf.d/*.conf, /usr/lib/systemd/user.conf.d/*.conf

DESCRIPTION

Lorsqu'il est exécuté en tant qu'instance système, systemd interprète le fichier de configuration system.conf et les fichiers des répertoires system.conf.d ; lorsqu'il est exécuté en tant qu'instance utilisateur, il interprète le fichier de configuration user.conf (par ordre de priorité, dans le répertoire personnel de l'utilisateur et sous /etc/systemd/, /run/systemd/, et /usr/lib/systemd/) et les fichiers des répertoires user.conf.d. Ces fichiers de configuration contiennent quelques paramètres contrôlant les opérations de base du gestionnaire.

Voir systemd.syntax(7) pour une description générale de la syntaxe.

RÉPERTOIRES DE CONFIGURATION ET PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation, donc une configuration n'est nécessaire que lorsqu'il est nécessaire de s'écarter de ces valeurs par défaut. Le fichier de configuration principal est chargé depuis l'un des répertoires listés par ordre de priorité, seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du vendeur du fichier contient des entrées commentées montrant les valeurs par défaut pour guider l'administrateur. Des substitutions locales peuvent également être créées en créant des drop-ins, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est fourni sous /usr/), cependant, l'utilisation de drop-ins pour la configuration locale est recommandée plutôt que des modifications du fichier de configuration principal.

En plus du fichier de configuration principal, des fragments de configuration drop-in sont lus à partir de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, et /etc/systemd/*.conf.d/. Ces drop-ins ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier dans l'ordre lexicographique, indépendamment du sous-répertoire dans lequel ils résident. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée dans le fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées au fur et à mesure qu'elles apparaissent dans les fichiers triés.

Lorsque les paquets doivent personnaliser la configuration, ils peuvent installer des drop-ins sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du vendeur. Les drop-ins doivent être utilisés pour remplacer les drop-ins de paquets, car le fichier de configuration principal a une priorité inférieure. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires par un nombre à deux chiffres et un tiret, pour simplifier l'ordre. Cela définit également un concept de priorités de drop-in pour permettre aux fournisseurs d'OS de fournir des drop-ins dans une plage spécifique inférieure à la plage utilisée par les utilisateurs. Cela devrait réduire le risque que les drop-ins de paquets remplacent accidentellement les drop-ins définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les drop-ins dans /usr/ et la plage 60-90 pour les drop-ins dans /etc/ et /run/, afin de s'assurer que les drop-ins locaux et transitoires ont la priorité sur les drop-ins fournis par le vendeur de l'OS.

Pour désactiver un fichier de configuration fourni par le vendeur, la méthode recommandée consiste à placer un lien symbolique vers /dev/null dans le répertoire de configuration dans /etc/, avec le même nom de fichier que le fichier de configuration du vendeur.

OPTIONS

Toutes les options sont configurées dans la section [Manager] :

LogColor=, LogLevel=, LogLocation=, LogTarget=, LogTime=, DumpCore=yes, CrashChangeVT=no, CrashShell=no, CrashAction=freeze, ShowStatus=yes, DefaultStandardOutput=journal, DefaultStandardError=inherit

Configure divers paramètres de fonctionnement de base du gestionnaire. Ces options peuvent être remplacées par les arguments respectifs du processus et de la ligne de commande du noyau. Voir systemd(1) pour plus de détails.

Ajouté dans la version 198.

CtrlAltDelBurstAction=

Définit l'action qui sera effectuée si l'utilisateur appuie plus de 7 fois sur Ctrl-Alt-Suppr en 2 secondes. Peut être défini sur "reboot-force", "poweroff-force", "reboot-immediate", "poweroff-immediate" ou désactivé avec "none". Par défaut : "reboot-force".

Ajouté dans la version 232.

StatusUnitFormat=

Accepte name, description ou combined comme valeur. Si name, le gestionnaire système utilisera les noms d'unités dans les messages d'état (par ex. "systemd-journald.service"), au lieu des descriptions plus longues et plus informatives définies avec Description= (par ex. "Journal Logging Service"). Si combined, le gestionnaire système utilisera à la fois les noms d'unités et les descriptions dans les messages d'état (par ex. "systemd-journald.service - Journal Logging Service").

Voir systemd.unit(5) pour les détails sur les noms d'unités et Description=.

Ajouté dans la version 243.

DefaultTimerAccuracySec=

Définit la précision par défaut des unités de minuterie. Ceci contrôle la valeur par défaut globale pour le réglage AccuracySec= des unités de minuterie, voir systemd.timer(5) pour les détails. AccuracySec= défini dans les unités individuelles remplace la valeur par défaut globale pour l'unité spécifique. Par défaut : 1 minute. Notez que la précision des unités de minuterie est également affectée par le délai de temporisation configuré pour PID 1, voir TimerSlackNSec= ci-dessus.

Ajouté dans la version 212.

GESTION DES RESSOURCES

TimerSlackNSec=

Définit le délai de temporisation en nanosecondes pour PID 1, qui est hérité par tous les processus exécutés, sauf s'il est remplacé individuellement, par exemple avec le réglage TimerSlackNSec= dans les unités de service (pour les détails, voir systemd.exec(5)). Le délai de temporisation contrôle la précision des réveils déclenchés par les minuteries système. Voir prctl(2) pour plus d'informations. Notez que contrairement à la plupart des autres définitions de laps de temps, ce paramètre prend une valeur entière en nanosecondes si aucune unité n'est spécifiée. Les unités de temps habituelles sont également comprises.

Ajouté dans la version 198.

CPUAffinity=

Configure l'affinité CPU pour le gestionnaire de services ainsi que l'affinité CPU par défaut pour tous les processus démarrés. Prend une liste d'indices CPU ou de plages séparées par des espaces blancs ou des virgules. Les plages CPU sont spécifiées par les indices CPU inférieur et supérieur séparés par un tiret. Cette option peut être spécifiée plusieurs fois, auquel cas les masques d'affinité CPU spécifiés sont fusionnés. Si la chaîne vide est attribuée, le masque est réinitialisé, toutes les attributions précédentes n'auront aucun effet. Les services individuels peuvent remplacer l'affinité CPU pour leurs processus avec le réglage CPUAffinity= dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 198.

NUMAPolicy=

Configure la politique mémoire NUMA pour le gestionnaire de services et la politique mémoire NUMA par défaut pour tous les processus démarrés. Les services individuels peuvent remplacer la politique par défaut avec le réglage NUMAPolicy= dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 243.

NUMAMask=

Configure le masque de nœud NUMA qui sera associé à la politique NUMA sélectionnée. Notez que les politiques NUMA default et local ne nécessitent pas de masque de nœud NUMA explicite et la valeur de l'option peut être vide. Similairement à NUMAPolicy=, la valeur peut être remplacée par des services individuels dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 243.

DefaultMemoryAccounting=, DefaultTasksAccounting=, DefaultIOAccounting=, DefaultIPAccounting=

Configure si la comptabilité de la mémoire, des tâches, des I/O et des paquets IP doit être activée par défaut pour toutes les unités. Si activée, ces ressources seront enregistrées pour chaque unité et peuvent être consultées via les commandes systemd-cgtop(1) et systemd-analyze(1). Par défaut, ces options sont désactivées.

Ajouté dans la version 245.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Configure les paramètres par défaut de la comptabilité des ressources, tels que configurés par unité par MemoryAccounting=, TasksAccounting=, IOAccounting= et IPAccounting=. Voir systemd.resource-control(5) pour les détails sur les paramètres par unité.

DefaultMemoryAccounting= est activé par défaut (yes). DefaultTasksAccounting= est activé par défaut (yes). Les autres paramètres sont désactivés par défaut (no).

Ajouté dans la version 211.

DefaultTasksMax=

Configure la valeur par défaut du paramètre par unité TasksMax=. Voir systemd.resource-control(5) pour les détails. Ce paramètre s'applique à tous les types d'unités qui prennent en charge les paramètres de contrôle des ressources, à l'exception des unités de tranche (slice units). La valeur par défaut est de 15% du minimum entre kernel.pid_max=, kernel.threads-max= et le cgroup racine pids.max. Le noyau a une valeur par défaut pour kernel.pid_max= et un algorithme de comptage en cas de plus de 32 cœurs. Par exemple, avec la valeur par défaut de kernel.pid_max=, DefaultTasksMax= est défini par défaut sur 4915, mais peut être supérieur sur d'autres systèmes ou inférieur dans les conteneurs de système d'exploitation.

Ajouté dans la version 228.

DefaultLimitCPU=, DefaultLimitFSIZE=, DefaultLimitDATA=, DefaultLimitSTACK=, DefaultLimitCORE=, DefaultLimitRSS=, DefaultLimitNOFILE=, DefaultLimitAS=, DefaultLimitNPROC=, DefaultLimitMEMLOCK=, DefaultLimitLOCKS=, DefaultLimitSIGPENDING=, DefaultLimitMSGQUEUE=, DefaultLimitNICE=, DefaultLimitRTPRIO=, DefaultLimitRTTIME=

Ces paramètres contrôlent diverses limites de ressources par défaut pour les processus exécutés par les unités. Voir setrlimit(2) pour les détails. Ces paramètres peuvent être remplacés dans les unités individuelles en utilisant les directives LimitXXX= correspondantes et ils acceptent la même syntaxe de paramètre, voir systemd.exec(5) pour les détails. Notez que ces limites de ressources ne sont que des valeurs par défaut pour les unités, elles ne s'appliquent pas au processus de gestion du système (c'est-à-dire PID 1) lui-même.

La plupart de ces paramètres ne sont pas définis, ce qui signifie que les limites de ressources sont héritées du noyau ou, si elles sont invoquées dans un conteneur, du gestionnaire de conteneur. Cependant, les paramètres suivants ont des valeurs par défaut :

•DefaultLimitNOFILE= est défini par défaut sur 1024:524288.
•DefaultLimitMEMLOCK= est défini par défaut sur 8M.
•DefaultLimitCORE= n'a pas de valeur par défaut, mais il est utile de mentionner que RLIMIT_CORE est défini sur "infinité" par le PID 1, qui est hérité par ses enfants.

Notez que le gestionnaire de service interne, le PID 1, augmente RLIMIT_NOFILE et RLIMIT_MEMLOCK à des valeurs plus élevées, cependant la limite est rétablie aux valeurs par défaut mentionnées pour tous les processus enfants créés.

Ajouté dans la version 198.

DefaultOOMPolicy=

Configure la politique par défaut pour réagir aux processus étant tués par le tueur OOM (Out-Of-Memory) de Linux ou par systemd-oomd. Ceci peut être utilisé pour choisir une valeur par défaut globale pour le paramètre par unité OOMPolicy=. Voir systemd.service(5) pour les détails. Notez que cette valeur par défaut n'est pas utilisée pour les services dont Delegate= est activé.

Ajouté dans la version 243.

DefaultOOMScoreAdjust=

Configure les ajustements du score OOM par défaut des processus exécutés par le gestionnaire de service. Ceci est défini par défaut sur non défini (ce qui signifie que les processus issus de fork héritent de la valeur d'ajustement du score OOM du gestionnaire de service), sauf si le gestionnaire de service est exécuté pour un utilisateur non privilégié, auquel cas il est défini par défaut sur la valeur d'ajustement OOM du gestionnaire de service plus 100 (ce qui rend les processus de service légèrement plus susceptibles d'être tués en cas de manque de mémoire que le gestionnaire lui-même). Ceci peut être utilisé pour choisir une valeur par défaut globale pour le paramètre par unité OOMScoreAdjust=. Voir systemd.exec(5) pour les détails. Notez que ce paramètre n'a aucun effet sur la valeur d'ajustement du score OOM du processus de gestion du service lui-même, il conserve la valeur d'origine définie lors de son invocation.

Ajouté dans la version 250.

DefaultMemoryPressureWatch=, DefaultMemoryPressureThresholdSec=

Configure les paramètres par défaut pour les paramètres par unité MemoryPressureWatch= et MemoryPressureThresholdSec=. Voir systemd.resource-control(5) pour les détails. La valeur par défaut est "auto" et "200ms", respectivement. Ceci définit également le seuil de surveillance de la pression mémoire pour le gestionnaire de service lui-même.

Ajouté dans la version 254.

MONTRE MATERIELLE

RuntimeWatchdogSec=, RebootWatchdogSec=, KExecWatchdogSec=

Configure la montre matérielle (watchdog) à l'exécution et au redémarrage. Prend une valeur de délai d'attente en secondes (ou dans d'autres unités de temps si suffixée avec "ms", "min", "h", "d", "w"), ou les chaînes spéciales "off" ou "default". Si défini sur "off" (alternativement : "0"), la logique du watchdog est désactivée : aucun périphérique de watchdog n'est ouvert, configuré ou contacté. Si défini sur la chaîne spéciale "default", le watchdog est ouvert et contacté à intervalles réguliers, mais le délai d'attente n'est pas modifié par rapport à la valeur par défaut. Si défini sur toute autre valeur temporelle, le délai d'attente du watchdog est configuré à la valeur spécifiée (ou une valeur proche, en fonction des capacités matérielles).

Si RuntimeWatchdogSec= est défini sur une valeur non nulle, le matériel du watchdog (/dev/watchdog0 ou le chemin spécifié avec WatchdogDevice= ou l'option du noyau systemd.watchdog_device=) sera programmé pour redémarrer automatiquement le système s'il n'est pas contacté dans le délai spécifié. Le gestionnaire de système s'assurera de le contacter au moins une fois dans la moitié du délai spécifié. Cette fonctionnalité nécessite la présence d'un périphérique de watchdog matériel, comme c'est souvent le cas dans les systèmes embarqués et les serveurs. Tous les watchdogs matériels ne permettent pas la configuration de toutes les valeurs de délai de redémarrage possibles, dans ce cas, le délai le plus proche disponible est choisi.

RebootWatchdogSec= peut être utilisé pour configurer le watchdog matériel lorsque le système est invité à redémarrer. Il sert de filet de sécurité pour garantir que le redémarrage a lieu même si une tentative de redémarrage propre expire. Notez que le délai d'attente RebootWatchdogSec= ne s'applique qu'à la seconde phase du redémarrage, c'est-à-dire après que tous les services réguliers sont déjà terminés, et après que le gestionnaire du système et de service (PID 1) a été remplacé par le binaire systemd-shutdown, voir bootup(7) pour les détails. Pendant la première phase de l'opération de mise hors tension, le système et le gestionnaire de service restent en cours d'exécution et par conséquent RuntimeWatchdogSec= est toujours respecté. Afin de définir un délai d'attente sur cette première phase de l'arrêt du système, configurez JobTimeoutSec= et JobTimeoutAction= dans la section [Unit] de l'unité shutdown.target. Par défaut, RuntimeWatchdogSec= est défini à 0 (désactivé), et RebootWatchdogSec= à 10 minutes.

KExecWatchdogSec= peut être utilisé pour activer en plus le watchdog lors de l'exécution de kexec plutôt que lors d'un redémarrage. Notez que si le noyau ne réinitialise pas le watchdog lors de kexec (en fonction du matériel et/ou du pilote spécifique), dans ce cas le watchdog pourrait ne pas être désactivé après la réussite de kexec et donc le système pourrait être redémarré, à moins que RuntimeWatchdogSec= ne soit également activé en même temps. Pour cette raison, il est recommandé d'activer KExecWatchdogSec= uniquement si RuntimeWatchdogSec= est également activé.

Ces paramètres n'ont aucun effet si un watchdog matériel n'est pas disponible.

Ajouté dans la version 198.

RuntimeWatchdogPreSec=

Configure la valeur de pré-délai d'attente du périphérique de watchdog matériel. Prend une valeur de délai d'attente en secondes (ou dans d'autres unités de temps similaires à RuntimeWatchdogSec=). Un pré-délai d'attente du watchdog est une notification générée par le watchdog avant que la réinitialisation du watchdog ne se produise si le watchdog n'a pas été servi. Cette notification est gérée par le noyau et peut être configurée pour déclencher une action (c'est-à-dire générer une panique du noyau) en utilisant RuntimeWatchdogPreGovernor=. Tous les matériels ou pilotes de watchdog ne prennent pas en charge la génération d'un pré-délai d'attente et, en fonction de l'état du système, le noyau peut être incapable d'effectuer l'action configurée avant le redémarrage du watchdog. Le watchdog sera configuré pour générer l'événement de pré-délai d'attente à la durée spécifiée par RuntimeWatchdogPreSec= avant le délai d'attente du watchdog d'exécution (défini par RuntimeWatchdogSec=). Par exemple, si nous avons RuntimeWatchdogSec=30 et RuntimeWatchdogPreSec=10, alors l'événement de pré-délai d'attente se produira si le watchdog n'a pas été contacté pendant 20 secondes (10 secondes avant que le watchdog ne se déclenche). Par défaut, RuntimeWatchdogPreSec= est défini sur 0 (désactivé). La valeur définie pour RuntimeWatchdogPreSec= doit être inférieure à la valeur de délai d'attente pour RuntimeWatchdogSec=. Ce paramètre n'a aucun effet si un watchdog matériel n'est pas disponible ou si le watchdog matériel ne prend pas en charge un pré-délai d'attente et sera ignoré par le noyau si le paramètre est supérieur au délai d'attente réel du watchdog.

Ajouté dans la version 251.

RuntimeWatchdogPreGovernor=

Configure l'action entreprise par le périphérique de watchdog matériel lorsque le pré-délai d'attente expire. L'action par défaut pour l'événement de pré-délai d'attente dépend de la configuration du noyau, mais il s'agit généralement d'enregistrer un message du noyau. Pour une liste des actions valides disponibles pour un périphérique watchdog donné, vérifiez le contenu du fichier /sys/class/watchdog/watchdogX/pretimeout_available_governors. Généralement, les types de gouverneurs disponibles sont noop et panic. La disponibilité, les noms et les fonctionnalités peuvent varier en fonction du pilote de périphérique spécifique utilisé. Si le fichier sysfs pretimeout_available_governors est vide, le gouverneur peut être compilé en tant que module du noyau et pourrait nécessiter d'être chargé manuellement (par exemple, pretimeout_noop.ko), ou le périphérique watchdog pourrait ne pas prendre en charge les pré-délais d'attente.

Ajouté dans la version 251.

WatchdogDevice=

Configure le périphérique de watchdog matériel que les minuteries de watchdog d'exécution et d'arrêt ouvriront et utiliseront. La valeur par défaut est /dev/watchdog0. Ce paramètre n'a aucun effet si un watchdog matériel n'est pas disponible.

Ajouté dans la version 236.

SÉCURITÉ

CapabilityBoundingSet=

Contrôle quelles capacités inclure dans l'ensemble de limites de capacités (capability bounding set) pour le PID 1 et ses enfants. Voir capabilities(7) pour les détails. Prend une liste de noms de capacités séparés par des espaces, tels que lus par cap_from_name(3). Les capacités listées seront incluses
dans le ensemble de contraintes, tous les autres sont supprimés. Si la liste des capacités est précédée de ~, toutes les capacités sauf celles listées seront incluses, l'effet de l'affectation est inversé. Notez que cette option affecte également les capacités respectives dans les ensembles de capacités effectif, autorisé et héritables. L'ensemble de contraintes de capacité peut également être configuré individuellement pour les unités en utilisant la directive CapabilityBoundingSet= pour les unités, mais notez que les capacités rejetées pour PID 1 ne peuvent pas être récupérées dans les unités individuelles, elles sont perdues définitivement.

Ajouté dans la version 198.

NoNewPrivileges=

Prend un argument booléen. Si vrai, garantit que PID 1 et tous ses enfants ne pourront jamais acquérir de nouveaux privilèges via execve(2) (par exemple, via les bits setuid ou setgid, ou les capacités du système de fichiers). La valeur par défaut est false. Les distributions à usage général s'appuient couramment sur des exécutables avec des bits setuid ou setgid et ne fonctionneront donc pas correctement avec cette option activée. Les unités individuelles ne peuvent pas désactiver cette option. Voir également No New Privileges Flag[2].

Ajouté dans la version 239.

ProtectSystem=

Prend un argument booléen ou la chaîne "auto". Si défini à vrai, remonte /usr/ en lecture seule. Si défini à "auto" (la valeur par défaut) et exécuté dans un initrd équivalent à vrai, sinon faux. Ceci implémente un sous-ensemble restreint du paramètre par unité du même nom, voir systemd.exec(5) pour les détails : actuellement, les valeurs "full" ou "strict" ne sont pas prises en charge.

Ajouté dans la version 256.

SystemCallArchitectures=

Prend une liste d'identifiants d'architecture séparés par des espaces. Sélectionne à partir de quelles architectures les appels système peuvent être invoqués sur ce système. Ceci peut être utilisé comme un moyen efficace de désactiver l'invocation de binaires non natifs dans tout le système, par exemple pour interdire l'exécution de binaires x86 32 bits sur des systèmes x86-64 64 bits. Ce paramètre s'applique à l'ensemble du système et agit de manière similaire au paramètre SystemCallArchitectures= des fichiers d'unités, voir systemd.exec(5) pour les détails. Ce paramètre est vide par défaut, auquel cas aucun filtrage des appels système basé sur l'architecture n'est appliqué. Les identifiants d'architecture connus sont "x86", "x86-64", "x32", "arm" et l'identifiant spécial "native". Ce dernier est implicitement mappé à l'architecture native du système (ou plus spécifiquement, à l'architecture pour laquelle le gestionnaire du système a été compilé). Définissez ce paramètre à "native" pour interdire l'exécution de tout binaire non natif. Lorsqu'un binaire exécute un appel système d'une architecture qui n'est pas listée dans ce paramètre, il sera immédiatement terminé avec le signal SIGSYS.

Ajouté dans la version 209.

DefaultSmackProcessLabel=

Prend une étiquette de sécurité SMACK64 comme argument. Le processus exécuté par une unité sera démarré sous cette étiquette si SmackProcessLabel= n'est pas défini dans l'unité. Voir systemd.exec(5) pour les détails.

Si la valeur est "/", seules les étiquettes spécifiées avec SmackProcessLabel= sont attribuées et la valeur par défaut à la compilation est ignorée.

Ajouté dans la version 252.

DefaultRestrictSUIDSGID=

Prend un argument booléen. Ceci est utilisé comme valeur par défaut pour les unités qui n'ont pas de définition explicite pour RestrictSUIDSGID=. Voir systemd.exec(5) pour les détails.

Ajouté dans la version 258.

TEMPORISATIONS ET LIMITATIONS DE TAUX

DefaultTimeoutStartSec=, DefaultTimeoutStopSec=, DefaultTimeoutAbortSec=, DefaultRestartSec=

Configure les temporisations par défaut pour le démarrage, l'arrêt et l'abandon des unités, ainsi que le temps par défaut pour attendre entre les redémarrages automatiques des unités, tels que configurés par unité dans TimeoutStartSec=, TimeoutStopSec=, TimeoutAbortSec= et RestartSec= (pour les services, voir systemd.service(5) pour les détails sur les paramètres par unité). Pour les unités autres que les services, DefaultTimeoutStartSec= définit la valeur TimeoutSec= par défaut.

DefaultTimeoutStartSec= et DefaultTimeoutStopSec= valent 90 s par défaut dans le gestionnaire système et 90 s dans le gestionnaire utilisateur. DefaultTimeoutAbortSec= n'est pas défini par défaut afin que toutes les unités reviennent à TimeoutStopSec=. DefaultRestartSec= vaut 100 ms par défaut.

Ajouté dans la version 209.

DefaultDeviceTimeoutSec=

Configure la temporisation par défaut pour l'attente des périphériques. Elle peut être modifiée par périphérique via l'option x-systemd.device-timeout= dans /etc/fstab et /etc/crypttab (voir systemd.mount(5), crypttab(5)). Vaut 90 s par défaut dans le gestionnaire système et 90 s dans le gestionnaire utilisateur.

Ajouté dans la version 252.

DefaultStartLimitIntervalSec=, DefaultStartLimitBurst=

Configure la limitation de taux de démarrage d'unité par défaut, telle que configurée par service via StartLimitIntervalSec= et StartLimitBurst=. Voir systemd.service(5) pour les détails sur les paramètres par service. DefaultStartLimitIntervalSec= vaut 10 s par défaut. DefaultStartLimitBurst= vaut 5 par défaut.

Ajouté dans la version 209.

ReloadLimitIntervalSec=, ReloadLimitBurst=

Limitation de taux pour les demandes daemon-reload et (depuis v256) daemon-reexec. Le paramètre s'applique aux deux opérations, mais les limites de taux sont suivies séparément. La valeur est non définie par défaut, et un nombre quelconque d'opérations peut être demandé à tout moment. ReloadLimitIntervalSec= prend une valeur en secondes pour configurer la fenêtre de limitation de taux, et ReloadLimitBurst= prend un entier positif pour configurer le nombre maximum d'opérations autorisées dans la fenêtre de temps configurée.

Ajouté dans la version 253.

ENVIRONNEMENT

DefaultEnvironment=

Configure les variables d'environnement passées à tous les processus exécutés. Prend une liste de variables séparées par des espaces. Voir environ(7) pour les détails sur les variables d'environnement. Ce bloc d'environnement est interne, et les modifications ne sont pas reflétées dans /proc/PID/environ du gestionnaire.

L'expansion simple de spécificateurs "%" est prise en charge, voir ci-dessous pour une liste des spécificateurs pris en charge.

Exemple :

DefaultEnvironment="VAR1=mot1 mot2" VAR2=mot3 "VAR3=mot 5 6"

Définit trois variables : "VAR1", "VAR2", "VAR3".

Ajouté dans la version 205.

ManagerEnvironment=

Définit les variables d'environnement pour le processus gestionnaire lui-même. Prend une liste de variables séparées par des espaces dans le même format que DefaultEnvironment=, voir ci-dessus. Ces variables sont fusionnées dans le bloc d'environnement existant du processus gestionnaire. En particulier, dans le cas du gestionnaire système, ce bloc inclut les variables définies par le noyau basées sur la ligne de commande du noyau, et dans le cas du gestionnaire utilisateur, les variables transmises par le gestionnaire système. Après la fusion de ces variables, elles persisteront jusqu'à ce qu'elles soient remplacées, même si le gestionnaire est rechargé ou réexécuté. Dans le cas du gestionnaire utilisateur, ces variables sont également héritées par les processus lancés par le gestionnaire. Comme pour DefaultEnvironment=, ce bloc d'environnement est interne, et les modifications ne sont pas reflétées dans /proc/PID/environ du gestionnaire.

La définition de variables d'environnement pour le processus gestionnaire peut être utile pour modifier son comportement. Voir Known Environment Variables[3] pour une description de certaines variables comprises par systemd.

L'expansion simple de spécificateurs "%" est prise en charge, voir ci-dessous pour une liste des spécificateurs pris en charge.

Ajouté dans la version 248.

NAME

systemd-system.conf — systemd system and service manager configuration file

SYNOPSIS

/etc/systemd/system.conf, /etc/systemd/user.conf

DESCRIPTION

The systemd system and service manager is configured via several files. The two main configuration files are `/etc/systemd/system.conf` and `/etc/systemd/user.conf`. The former controls the behavior of systemd in its system-wide instance, and the latter controls the behavior of systemd in its per-user instance.

These files are grouped into two directories: `/etc/systemd/system` for system-wide configuration and `/etc/systemd/user` for per-user configuration. The configuration files are simple INI-style files. They are read by systemd during initialization.

There are two main configuration files, `/etc/systemd/system.conf` and `/etc/systemd/user.conf`. The former configures the system-wide systemd instance, the latter configures the per-user systemd instance.

These files are used to configure systemd itself.

CONFIGURATION DIRECTORIES AND PRECEDENCE

Configuration files are loaded from directories in the following order:

1. /etc/systemd/system/ (system-wide)

2. /run/systemd/system/ (runtime, for temporary configuration)

3. /usr/lib/systemd/system/ (packaged configuration)

When multiple configuration files exist for the same unit, the one in the highest-precedence directory takes precedence.

OPTIONS

The configuration file is divided into sections, each starting with a `[` character, followed by the section name, and ending with a `]` character. The following sections are recognized:

[Manager]
Controls systemd manager options.
[Login]
Controls systemd login options.
[User]
Controls systemd user options.
[System]
Controls systemd system options.
[Network]
Controls systemd network options.
[Time]
Controls systemd time options.
[Bus]
Controls systemd bus options.
[TLS]
Controls systemd TLS options.

RESOURCE MANAGEMENT

The following options control resource management:

DefaultCPUAccounting=
Enables or disables CPU accounting for all services.
DefaultIOAccounting=
Enables or disables I/O accounting for all services.
DefaultMemoryAccounting=
Enables or disables memory accounting for all services.
DefaultBlockIOAccounting=
Enables or disables block I/O accounting for all services.
DefaultTasksAccounting=
Enables or disables task accounting for all services.

HARDWARE WATCHDOG

The following options control the hardware watchdog:

HardwareWatchdog=
Enables or disables the hardware watchdog.

SECURITY

The following options control security settings:

ProtectSystem=
Controls how the system root is protected.
ProtectHome=
Controls how user home directories are protected.
PrivateTmp=
Controls whether a private /tmp directory is created for services.
NoNewPrivileges=
Controls whether services are allowed to gain new privileges.

TIMEOUTS AND RATE LIMITS

The following options control timeouts and rate limits:

DefaultTimeoutStartSec=
Default timeout for starting services.
DefaultTimeoutStopSec=
Default timeout for stopping services.
DefaultTimeoutAbortSec=
Default timeout for aborting services.
DefaultRestartSec=
Default interval for restarting services.
DefaultStartLimitIntervalSec=
Default interval for limiting the start rate of services.
DefaultStartLimitBurst=
Default burst count for limiting the start rate of services.

ENVIRONMENT

The following options control the environment:

DefaultEnvironment=
Sets default environment variables for all services.
DefaultEnvironmentFile=
Sets default environment variables from a file for all services.
