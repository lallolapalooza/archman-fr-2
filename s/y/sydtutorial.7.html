NOM

sydtutorial - Introduction au tutoriel Syd

SYNOPSIS

syd *

DESCRIPTION

Ce tutoriel explique comment sandboxer des applications avec Syd, écrire des profils de sandbox, et configurer Syd à l'exécution depuis l'intérieur du sandbox. Si vous êtes principalement intéressé par l'utilisation de Syd comme sandbox de compilation de paquets, comme nous le faisons chez Exherbo Linux, vous préférerez peut-être commencer par syd(2) et le profil "paludis" dont les règles peuvent être listées en utilisant "syd-cat -p paludis".

INTRODUCTION

Syd est sécurisé par défaut et hautement configurable pour l'usage de votre application. Au fur et à mesure, vous apprendrez comment restreindre une application de diverses manières tout en gardant le sandbox flexible pour les cas où une restriction n'est pas possible et/ou nécessaire. Pour tirer le meilleur parti de ce tutoriel, il est recommandé de choisir une application dont la fonctionnalité système vous est connue et d'essayer de sandboxer cette application de manière similaire aux instructions du chapitre correspondant. Cette fonctionnalité inclut, avant tout, les appels système que le processus appelle pour interagir avec le noyau Linux et quelles parties du système de fichiers/réseau l'application doit accéder pour remplir sa fonctionnalité correctement. bpftrace(1) et strace(1) sont vos amis. Dans un autre chapitre, nous découvrirons également pandora(1) qui est un outil pour générer automatiquement des profils Syd pour une application donnée, restez à l'écoute !

Dans son sens le plus simple, vous pouvez considérer Syd comme un proxy entre le noyau Linux et le processus sandboxé : Syd vérifie les arguments des appels système pour l'accès et si l'accès est accordé, Syd exécutera l'appel système au nom du processus sandboxé et retournera le résultat au processus sandboxé. Dorénavant, il est important de garder cela à l'esprit : du point de vue du noyau Linux, c'est l'un des threads de gestionnaire d'appels système de Syd qui exécute l'appel système, pas le processus sandboxé. Ceci est nécessaire pour obtenir un sandbox exempt de Time-of-check to Time-of-use. Syd fait de son mieux pour réduire les effets secondaires, par exemple avec ls /proc/self, le processus sandboxé verra toujours son propre identifiant de processus, pas celui de Syd.

1.
Apprendre en faisant : Tracez vos applications, apprenez les détails !
2.
Expérimenter : Modifiez Syd de diverses manières et observez les effets !
3.
Faites-en un jeu : Essayez de casser votre propre profil de sandbox que vous avez configuré, puis rendez-le plus strict et réessayez !

INSTALLATION RAPIDE SYD

Vous avez les alternatives suivantes :

1.
Utilisez le binaire de la dernière version situé @ https://distfiles.exherbo.org/#sydbox/
2.
cave resolve sys-apps/sydbox:3 # si Exherbo (démasquer avec le mot-clé testing)
3.
emerge sys-apps/syd # si Gentoo
4.
cargo install syd # Vous n'obtiendrez pas les pages de manuel, vérifiez: https://man.exherbo.org
5.
Prenez le temps de packager Syd pour votre distribution Linux et partagez l'amour !

Notez que les versions sont signées avec cette clé PGP https://keybase.io/alip/pgp_keys.asc, alors prenez le temps de vérifier l'archive tar que vous avez téléchargée. Si vous utilisez cargo pour installer, vous devez installer manuellement la bibliothèque "libseccomp". C'est une bibliothèque relativement courante et elle est packagée par presque toutes les distributions Linux de nos jours. Deux choses à garder à l'esprit :

1.
Installez les en-têtes de développement de libseccomp (généralement inclus ou livrés avec, par exemple, le paquet libseccomp-devel).
2.
Installez les bibliothèques statiques de libseccomp si vous souhaitez lier Syd statiquement (généralement inclus ou livrés avec, par exemple, le paquet libseccomp-static).

Une dernière note, au moment de la rédaction avec la version 2.5.5 de libseccomp, une libseccomp patchée est requise pour que les interruptions fonctionnent correctement sous Syd (libseccomp.git prend déjà en charge le nouveau flag du noyau Linux, nous ajoutons également un patch pour le définir par défaut). La version binaire est compilée avec une libseccomp patchée et le build source d'Exherbo patch le paquet libseccomp pendant la phase de préparation. Notez que, selon notre expérience, ce bug est principalement perceptible lorsque vous sandboxez des applications écrites en langage Go. Sinon, vous le remarquerez rarement avec la dernière version de libseccomp. À titre de référence, le patchset se trouve ici : https://gitlab.exherbo.org/exherbo/arbor/-/tree/master/packages/sys-libs/libseccomp/files

SYD 101

Premièrement, si vous exécutez Syd sans arguments, vous entrerez silencieusement dans un nouveau shell. C'est parce que Syd est conçu pour agir comme un shell de connexion et dans ce cas, il utilise le profil de sandbox "user". Nous aborderons les profils plus tard, mais si vous êtes curieux, tapez "syd-cat -p user | less" et lisez les règles.

Deuxièmement, Syd est sécurisé par défaut et vous permet de construire un sandbox adapté aux besoins de vos applications. Voici à quoi ressemble l'état du sandbox avant que nous passions des options à Syd :

$ syd -mstat
syd:
Process ID: 0
Lock: None
Capabilities: Read, Stat, Write, Execute, Connect, Bind
Options:
Memory Max: 134217728
Virtual Memory Max: 4294967296
Pid Max: 128
SegvGuard Max Crashes: 5
SegvGuard Expiry: 120 seconds
SegvGuard Suspension: 600 seconds
Allowed UID Transitions: (total: 0, source -> target)
Allowed GID Transitions: (total: 0, source -> target)
Cidr Rules: (total 0, highest precedence first)
Glob Rules: (total 0, highest precedence first)
Mask Rules: (total 1)
1. Pattern: /proc/cmdline
Force Rules: (total 0, default action: Kill)
$

Pour l'instant, concentrons-nous uniquement sur la ligne "Capabilities". Ce sont les types de sandboxing qui sont activés par défaut au démarrage.

Initialement, nous allons faire le minimum et essayer d'exécuter un binaire lié statiquement sous Syd. busybox(1) est un outil pratique pour notre expérience :

$ file $(which busybox)
/usr/host/bin/busybox: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, stripped
$ syd busybox true
syd: exec error: No such file or directory
$ echo $?
2
$ syd-sys -e 2
2       ENOENT  No such file or directory
$

Nous obtenons une erreur indiquant que le chemin n'existe pas. Ceci est dû au fait que le "Stat Sandboxing" est activé par défaut et que le chemin vers le binaire busybox(1) est caché. Nous voyons que Syd clarifie l'erreur qui a provoqué l'échec de l'exécution grâce à sa valeur de sortie. Nous utilisons l'utilitaire syd-sys(1), l'un des nombreux utilitaires livrés avec syd(1), pour rechercher la définition de l'erreur par le code de sortie.

Essayons d'autoriser et de réessayer :

$ syd -m'allow/stat+/usr/host/bin/busybox' busybox true
syd: exec error: No such file or directory
$

Pas de succès, nous obtenons la même erreur. C'est parce que le chemin que nous avons spécifié pour "allow/stat" n'est pas un chemin canonisé. Un chemin canisé est un chemin qui commence par "/" et ne contient ni "." ni ".." ni de barres obliques répétées ni de liens symboliques dans aucun de ses composants de chemin. Trouvons le chemin canisé de notre binaire busybox(1) et réessayons avec.

$ readlink -f /usr/host/bin/busybox
/usr/x86_64-pc-linux-musl/bin/busybox
$ syd -m'allow/stat+/usr/x86_64-pc-linux-musl/bin/busybox' busybox true
{"act":"Deny","cap":"x","ctx":"access","id":"nostalgic_black","l":2,"path":"/usr/x86_64-pc-linux-musl/bin/busybox","pid":2602591,"sys":"execve","uid":1000,...}
syd: exec error: Permission denied
$ echo $?
13
$ syd-sys -e 13
13      EACCES  Permission denied
$

Nous obtenons à nouveau une erreur, mais cette fois nous avons du contexte. Comme le Stat Sandboxing consiste à cacher les chemins, signaler les violations d'accès à ce sujet sur la sortie d'erreur standard irait à l'encontre de son objectif, Syd était donc silencieux. Cependant, cette fois, nous voyons "Exec Sandboxing" à l'œuvre et Syd nous donne des détails sur la violation d'accès. Le format est des lignes JSON. Il peut être difficile à lire au début, mais le fait qu'il soit facilement analysable

seable vous permet de rechercher facilement des journaux de violation d'accès Syd dans le journal de votre système et de les filtrer à l'aide d'outils tels que jq(1).

Pour en revenir à la tâche, observons brièvement que il s'agit d'une violation d'accès ("ctx":"access") concernant l'appel système execve(2) ("sys":"execve"). La violation d'accès est de catégorie Exec ("cap":"x") et le chemin cible est "/usr/x86_64-pc-linux-musl/bin/busybox". La décision a été de refuser l'appel système ("act":"Deny"). Nous avons également des métadonnées utiles telles que l'identifiant du processus ("pid") et l'identifiant de l'utilisateur ("uid") exécutant l'appel système fautif. Le champ "id" est un nom lisible par l'homme généré à partir du champ "pid" pour faciliter le suivi des journaux. Il y a plus d'informations dans les champs omis, il est recommandé de jeter un coup d'œil à une entrée de journal de violation d'accès complète par vous-même et de noter les champs qui vous sont utiles. Permettons cette fois notre binaire busybox(1) pour l'exécution et retentons :

$ syd -m'allow/exec,stat+/usr/x86_64-pc-linux-musl/bin/busybox' busybox true
$ echo $?
$ 0

Tâche accomplie ! Notez comment nous avons utilisé la notation courte "allow/exec,stat+/chemin" qui est un moyen pratique de passer -m "allow/exec+/chemin" -m "allow/stat+/chemin" en tant que règle unique.

Essayons maintenant à nouveau avec un exécutable lié dynamiquement et découvrons ce que nous devons ajouter pour que cela fonctionne. Cette fois, nous utiliserons l'utilitaire gtrue(1) du projet GNU coreutils, qui est lié dynamiquement sur ce système :

$ file $(which gtrue)
/usr/host/bin/gtrue: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /usr/x86_64-pc-linux-musl/lib/ld-musl-x86_64.so.1, stripped
$ lddtree $(which gtrue)
/usr/x86_64-pc-linux-musl/lib/ld-musl-x86_64.so.1 => /usr/x86_64-pc-linux-musl/lib/libc.so
libc.so => /usr/x86_64-pc-linux-musl/lib/libc.so
$ readlink -f $(which gtrue)
/usr/x86_64-pc-linux-musl/bin/gtrue
$ syd -m'allow/exec,stat+/usr/x86_64-pc-linux-musl/bin/gtrue' gtrue
{"act":"Kill","cap":"x","ctx":"access","id":"compassionate_spence","l":2,"path":"/usr/x86_64-pc-linux-musl/lib/libc.so","pid":2601331,"sys":"exec","uid":1000,...}
$ echo $?
137
$

En observant le chemin fautif de la nouvelle violation d'accès, nous comprenons que libc.so s'est vu refuser l'accès en exécution. Nous pouvons également observer que cette fois, Syd a terminé le processus ("act":"Kill") plutôt que de refuser l'accès à l'appel système ("act":"Deny"). Ceci est également évident d'après le code de sortie qui est 137 = 128 + 9, où 9 est la valeur du signal "SIGKILL". La distinction deny/kill provient des internes de Syd et n'est pas significative pour nous à ce stade. Il suffit de dire que dans les deux cas, l'exécution a été arrêtée avant que tout code du binaire cible ait eu une chance de s'exécuter.

Lors de la vérification d'accès pour le Sandboxing d'exécution, Syd traite les exécutables liés dynamiquement et leur arborescence de dépendances de bibliothèques dynamiques comme une seule unité. En ce sens, "allow/read+/chemin/vers/libc.so" et "allow/exec+/chemin/vers/libc.so" servent deux objectifs différents : le premier vous permet de lire littéralement le contenu du fichier tandis que le dernier vous permet de charger le fichier en mémoire dans le cadre d'un exécutable.

Ayant clarifié cela, permettons à libc.so et retentons :

$ syd -m'allow/exec,stat+/usr/x86_64-pc-linux-musl/bin/gtrue' -m 'allow/exec+/usr/x86_64-pc-linux-musl/lib/libc.so' gtrue
$ echo $?
0
$

Tâche accomplie ! Le lecteur curieux reconnaîtra que nous n'avons pas eu à ajouter une clause "allow/stat" pour "libc.so". C'est parce que les concepts de Sandboxing de Stat et de Masquage de Chemin concernent spécifiquement l'accès direct aux chemins de fichiers. Le chargement de bibliothèques en mémoire fait partie du processus d'exécution et est donc soumis uniquement au Sandboxing d'exécution (et au Sandboxing Forcé, alias Vérification de Binaire, dont nous parlerons plus en détail plus tard).

Maintenant, à la troisième étape, généralisons notre petit sandbox de sorte qu'il autorise quelle que soit la version du binaire true(1) que nous exécutons, de plus il autorisera également l'exécution de tout autre utilitaire coreutils préfixé par "g*". Nous ne voulons pas non plus nous soucier si "libc.so" a un suffixe de version et voulons autoriser toutes les bibliothèques sous les chemins de bibliothèques communs sans avoir à les lister une par une. Pour y parvenir, nous allons utiliser des motifs glob(3) :

$ eclectic coreutils list
Available providers for coreutils:
[1]   gnu
[2]   busybox *
$ readlink -f /bin/true
/usr/x86_64-pc-linux-musl/bin/busybox
$ syd -m'allow/stat,exec+/usr/**/bin/{busybox,g*}' -m 'allow/exec+/usr/**/lib*/*.so*' true
$ echo $?
0
$ doas eclectic coreutils set -1
$ readlink -f /bin/true
/usr/x86_64-pc-linux-musl/bin/gtrue
$ syd -m'allow/stat,exec+/usr/**/bin/{busybox,g*}' -m 'allow/exec+/usr/**/lib*/*.so*' true
$ echo $?
0
$

Nous avons vu comment les motifs glob(3) nous facilitent la vie dans la configuration de notre sandbox. Nous avons vu qu'il est possible d'utiliser "**" pour faire une correspondance récursive et que les alternances de la forme "{foo,bar}" sont prises en charge. Syd prend également en charge les **alternances vides** de la forme "foo/{bar/,}baz" et l'**extension triple étoile**, c'est-à-dire que "foo/*** "est équivalent à la combinaison des deux motifs "foo" et "foo/**". Enfin, nous pouvons voir que nous avons réussi à autoriser beaucoup plus en utilisant le même nombre de règles. Syd dispose de nombreuses autres fonctionnalités puissantes qui rendent l'édition de règles simple et efficace, telles que :

  • Vous pouvez spécifier des chemins interdits avec "deny/" en plus de "allow/".
  • Vous pouvez spécifier des chemins filtrés avec "filter/", similaire à "deny/" et "allow/" pour silencier les violations d'accès tout en refusant l'accès.
  • Si plus d'une règle correspond au chemin cible, la dernière règle correspondante l'emporte.
  • Plusieurs règles peuvent être assemblées dans un fichier de configuration et passées à Syd avec -P<path>.
  • Les fichiers ayant des ensembles de règles communs peuvent être inclus à partir d'autres fichiers de configuration en utilisant la clause "include <path>".
  • Les chemins relatifs dans les clauses "include" sont canonisés en fonction du répertoire parent du fichier de configuration actuel (et non du répertoire de travail actuel !).
  • Les variables d'environnement sont développées dans les fichiers de configuration. Les variables d'environnement non définies provoqueront une erreur.
  • La configuration peut être verrouillée à tout moment avec la clause "lock:on" empêchant toute modification ultérieure du sandbox.

À ce stade, il est fortement recommandé d'expérimenter avec la configuration de Syd. N'ayez pas peur d'ajouter autant de règles que vous le souhaitez. En interne, Syd conserve les motifs glob(3) sous forme de globsets et les compile en une seule expression régulière pour une correspondance efficace. Cela offre des performances acceptables jusqu'à environ 10 000 règles sur mon système, votre expérience peut varier.

Nous avons eu un aperçu de la manière de configurer les listes blanches de chemins Syd. Cela est similaire pour les autres types de sandboxing. Laissons cela pour plus tard et explorons une autre façon de configurer Syd. Cette fois, nous le ferons à l'exécution, depuis l'intérieur du sandbox. Il peut être choquant d'un point de vue sécuritaire d'autoriser l'accès à la politique du sandbox depuis l'intérieur du sandbox, mais Syd dispose d'un bon ensemble de restrictions pour fournir ce cas d'utilisation en toute sécurité et comme nous le verrons plus tard, cela donne la possibilité de restreindre davantage le processus du sandbox. Une autre alternative consiste à faire charger par Syd une bibliothèque dynamique au démarrage plutôt que d'exécuter une commande, ce qui est un autre sujet avancé pour plus tard. L'idée de configuration à l'exécution dépend du Verrouillage du Sandbox et le verrou peut avoir trois états : "on", "off" et "exec". Les deux premiers s'expliquent d'eux-mêmes tandis que "exec" permet l'accès à la politique du sandbox uniquement pour le processus initial du sandbox. Une fois le verrou du sandbox défini sur "on", il n'y a pas de retour en arrière, donc les modifications ultérieures du sandbox ne seront plus possibles. Exécutons maintenant un shell sous Syd. Cette fois, nous ne soumettrons aucune configuration au démarrage et exécuterons Syd sans arguments. Cela placera Syd en mode de connexion, où Syd utilisera le profil "user" intégré et dynamique et lancera un shell. Nous n'approfondirons pas les détails du profil utilisateur pour le moment, consultez "syd-cat -p user" si vous êtes curieux. Il suffit de dire qu'il fournit un ensemble relativement sûr de règles d'accès aux chemins système et un accès en lecture+écriture à votre répertoire HOME et aux chemins "/run" d'exécution de l'utilisateur. NAME
sydtutorial - Un tutoriel pour sydutils

DESCRIPTION
Ce document est un tutoriel pour les utilisateurs de sydutils.

SYNTAXE
La syntaxe de base pour utiliser sydutils est la suivante :

sydcmd [options] argument

EXEMPLES
Voici quelques exemples d'utilisation courante :

sydlist --all
Liste tous les paquets disponibles.
sydinstall package_name
Installe un paquet spécifique.
sydremove package_name
Supprime un paquet spécifique.

OPTIONS
Les options courantes incluent :

  • --help: Affiche l'aide.
  • --version: Affiche la version.
