NOM

systemd-journal-remote.service, systemd-journal-remote.socket, systemd-journal-remote - Recevoir les messages du journal sur le réseau

SYNỚPSIȘ

systemd-journal-remote.service

systemd-journal-remote.socket

/usr/lib/systemd/systemd-journal-remote [OPTIONS...] [-o/--output=DIR|FICHIER] [SOURCES...]

DESCRIPTION

systemd-journal-remote est une commande pour recevoir des événements de journal sérialisés et les stocker dans des fichiers journaux. Les flux d'entrée sont au format Journal Export Format[1], c'est-à-dire similaires à la sortie de journalctl --output=export. Pour le transport sur le réseau, ce flux sérialisé est généralement transporté via une connexion HTTPS.

systemd-journal-remote.service est un service système qui utilise systemd-journal-remote pour écouter les connexions. systemd-journal-remote.socket configure l'adresse réseau sur laquelle systemd-journal-remote.service écoute. Par défaut, il s'agit du port 19532. Quelles connexions sont acceptées et comment les données reçues sont stockées peuvent être configurés via le fichier de configuration journal-remote.conf(5).

SOURCES

Les sources peuvent être soit "actives" (systemd-journal-remote demande et récupère les données), soit "passives" (systemd-journal-remote attend une connexion et reçoit ensuite les événements poussés par l'autre partie).

systemd-journal-remote peut lire plus d'un flux d'événements à la fois. Ils seront entrelacés dans le fichier de sortie. Dans le cas des connexions "actives", chaque "source" est un flux, et dans le cas des connexions "passives", chaque connexion peut résulter en un flux distinct. Les sockets peuvent être configurés en mode "accept" (c'est-à-dire une seule connexion), ou en mode "listen" (c'est-à-dire plusieurs connexions, chacune résultant en un flux).

Lorsqu'il n'y a plus de connexions, et qu'aucune autre ne peut être créée (il n'y a pas de sockets d'écoute), alors systemd-journal-remote se terminera.

Les sources actives peuvent être spécifiées de la manière suivante :

[SOURCES]

Lorsque - est donné comme argument positionnel, les événements seront lus depuis l'entrée standard. D'autres arguments positionnels seront traités comme des noms de fichiers à ouvrir et à lire.

Ajouté dans la version 239.

--url=ADRESSE

Avec l'option --url=ADRESSE, les événements seront récupérés via HTTP depuis ADRESSE. Cette URL doit pointer vers la racine d'une instance distante de systemd-journal-gatewayd(8), par exemple http://some.host:19531/ ou https://some.host:19531/.

Ajouté dans la version 239.

--getter='PROG [OPTIONS]'

Programme à invoquer pour récupérer les données. Le flux d'événements du journal doit être généré sur la sortie standard.

Exemples :

--getter='curl "-HAccept: application/vnd.fdo.journal" https://some.host:19531/'
--getter='wget --header="Accept: application/vnd.fdo.journal" -O- https://some.host:19531/'

Ajouté dans la version 239.

Les sources passives peuvent être spécifiées de la manière suivante :

--listen-raw=ADRESSE

ADRESSE doit être une adresse appropriée pour ListenStream= (voir systemd.socket(5)). systemd-journal-remote écoutera sur ce socket pour les connexions. Chaque connexion est attendue comme un flux d'événements de journal.

Ajouté dans la version 239.

--listen-http=ADRESSE, --listen-https=ADRESSE

ADRESSE doit être soit un entier négatif, auquel cas il sera interprété comme le descripteur de fichier (numéro inversé), soit une adresse appropriée pour ListenStream= (voir systemd.socket(5)). Dans le premier cas, le serveur écoute sur le port 19532 par défaut, et le descripteur de fichier correspondant doit être hérité via $LISTEN_FDS/$LISTEN_PID. Dans le second cas, un serveur HTTP ou HTTPS sera lancé sur ce port, respectivement pour --listen-http= et --listen-https=. Actuellement, seules les requêtes POST vers /upload avec "Content-Type: application/vnd.fdo.journal" sont prises en charge.

Ajouté dans la version 239.

$LISTEN_FDS

systemd-journal-remote prend en charge le protocole $LISTEN_FDS/$LISTEN_PID. Les sockets ouverts hérités par activation de socket se comportent comme ceux ouverts avec --listen-raw= décrit ci-dessus, sauf s'ils sont spécifiés comme argument dans --listen-http=-n ou --listen-https=-n ci-dessus. Dans ce dernier cas, un serveur HTTP ou HTTPS sera lancé en utilisant ce descripteur et les connexions devront se faire via le protocole HTTP.

Ajouté dans la version 239.

--key=

Prend le chemin d'un fichier de clé secrète SSL au format PEM. Par défaut, c'est /etc/ssl/private/journal-remote.pem. Cette option peut être utilisée avec --listen-https=. Si le chemin fait référence à un socket de flux AF_UNIX dans le système de fichiers, une connexion y sera établie et la clé en sera lue.

Ajouté dans la version 239.

--cert=

Prend le chemin d'un fichier de certificat SSL au format PEM. Par défaut, c'est /etc/ssl/certs/journal-remote.pem. Cette option peut être utilisée avec --listen-https=. Si le chemin fait référence à un socket de flux AF_UNIX dans le système de fichiers, une connexion y sera établie et le certificat en sera lu.

Ajouté dans la version 239.

--trust=

Prend le chemin d'un fichier de certificat CA SSL au format PEM, ou all. Si all est défini, alors la vérification des certificats sera désactivée. Par défaut, c'est /etc/ssl/ca/trusted.pem. Cette option peut être utilisée avec --listen-https=. Si le chemin fait référence à un socket de flux AF_UNIX dans le système de fichiers, une connexion y sera établie et le certificat en sera lu.

Ajouté dans la version 239.

--gnutls-log=

Prend une liste de catégories de journalisation gnutls séparées par des virgules. Cette option peut être utilisée avec --listen-http= ou --listen-https=.

Ajouté dans la version 239.

DESTINATIONS

L'emplacement du journal de sortie peut être spécifié avec -o ou --output=.

-o FICHIER, --output=FICHIER

Écrira dans ce fichier journal. Le nom de fichier doit se terminer par .journal. Le fichier sera créé s'il n'existe pas. Si nécessaire (fichier journal plein ou corrompu), le fichier sera renommé selon les règles normales de journald et un nouveau fichier journal sera créé à sa place.

Ajouté dans la version 239.

-o DIR, --output=DIR

Créera des fichiers journaux sous le répertoire DIR. Le répertoire doit exister. Si nécessaire (fichiers journaux hors limite, ou corrompus), les fichiers journaux seront déplacés selon les règles normales de journald. Les noms des fichiers sous DIR seront générés en utilisant les règles décrites ci-dessous.

Ajouté dans la version 239.

Si --output= n'est pas utilisé, le répertoire de sortie /var/log/journal/remote/ sera utilisé. Dans le cas où le fichier de sortie n'est pas spécifié, les fichiers journaux seront créés sous le répertoire sélectionné. Les fichiers seront nommés remote-nom_hote.journal, où la partie nom_hote est le nom d'hôte échappé du point d'extrémité source de la connexion, ou l'adresse numérique si le nom d'hôte ne peut pas être déterminé.

Dans le cas où des sources "actives" sont fournies par les arguments positionnels ou l'option --getter=, le nom du fichier de sortie doit toujours être donné explicitement.

OPTIONS

Les options suivantes sont comprises :

--split-mode

L'un des modes suivants : none ou host. Pour le premier, un seul fichier journal de sortie est utilisé. Pour le second, un fichier de sortie distinct est utilisé, basé sur le nom d'hôte du point d'extrémité de la connexion.

Dans le cas où des sources "actives" sont fournies par les arguments positionnels ou l'option --getter=, le nom du fichier de sortie doit toujours être donné explicitement

Ajouté dans la version 239.

--compress [BOOL]

S'il est défini sur « yes », les données du journal seront compressées en utilisant XZ. La valeur par défaut est « yes ».

Ajouté dans la version 239.

--seal [BOOL]

S'il est défini sur « yes », les données du journal seront signées périodiquement en utilisant le scellement sécurisé direct (Forward Secure Sealing). La valeur par défaut est « no ».

Ajouté dans la version 239.

-h, --help

Affiche un court message d'aide et quitte.

--version

Affiche une courte chaîne de version et quitte.

EXEMPLES

Copier les événements du journal local vers un autre répertoire de journal :

journalctl -o export | systemd-journal-remote -o /tmp/dir/foo.journal -

Récupérer tous les événements disponibles d'une instance distante de systemd-journal-gatewayd(8) et les stocker dans /var/log/journal/remote/remote-some.host.journal :

systemd-journal-remote --url http://some.host:19531/

Récupérer les événements du démarrage actuel et attendre de nouveaux événements d'une instance distante de systemd-journal-gatewayd(8), et les stocker dans /var/log/journal/remote/remote-some.host.journal :

systemd-journal-remote --url http://some.host:19531/entries?boot&follow
