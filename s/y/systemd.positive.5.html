NOM

dnssec-trust-anchors.d, systemd.positive, systemd.negative - Fichiers de configuration des ancres de confiance DNSSEC

SYNTAXE

/etc/dnssec-trust-anchors.d/*.positive
/run/dnssec-trust-anchors.d/*.positive
/usr/local/lib/dnssec-trust-anchors.d/*.positive
/usr/lib/dnssec-trust-anchors.d/*.positive
/etc/dnssec-trust-anchors.d/*.negative
/run/dnssec-trust-anchors.d/*.negative
/usr/local/lib/dnssec-trust-anchors.d/*.negative
/usr/lib/dnssec-trust-anchors.d/*.negative

DESCRIPTION

Les fichiers de configuration des ancres de confiance DNSSEC définissent les ancres de confiance positives et négatives sur lesquelles systemd-resolved.service(8) base les preuves d'intégrité DNSSEC.

ANCRES DE CONFIANCE POSITIVES

Les fichiers de configuration des ancres de confiance positives contiennent des définitions d'enregistrements de ressources DNSKEY et DS à utiliser comme base pour les preuves d'intégrité DNSSEC. Voir la RFC 4035, Section 4.4[1] pour plus d'informations sur les ancres de confiance DNSSEC.

Les ancres de confiance positives sont lues à partir des fichiers avec le suffixe .positive situés dans /etc/dnssec-trust-anchors.d/, /run/dnssec-trust-anchors.d/ et /usr/lib/dnssec-trust-anchors.d/. Ces répertoires sont recherchés dans l'ordre spécifié, et un fichier d'ancre de confiance du même nom dans un chemin antérieur remplace les fichiers d'ancres de confiance dans un chemin ultérieur. Pour désactiver un fichier d'ancre de confiance fourni dans /usr/lib/dnssec-trust-anchors.d/, il suffit de fournir un fichier portant le même nom dans /etc/dnssec-trust-anchors.d/ ou /run/dnssec-trust-anchors.d/ qui est soit vide, soit un lien symbolique vers /dev/null ("masqué").

Les fichiers d'ancres de confiance positives sont des fichiers texte simples ressemblant à des fichiers de zone DNS, tels que documentés dans la RFC 1035, Section 5[2]. Un enregistrement de ressource DS ou DNSKEY peut être listé par ligne. Les lignes vides et les lignes commençant par "#" ou ";" sont ignorées, ce qui peut être utilisé pour les commentaires. Un enregistrement de ressource DS est spécifié comme dans l'exemple suivant :

. IN DS 19036 8 2 49aac11d7b6f6446702e54a1607371607a1a41855200fd2ce1cdde32f24e8fb5

Le premier mot spécifie le domaine, utilisez "." pour le domaine racine. Le domaine peut être spécifié avec ou sans point final, ce qui est considéré comme équivalent. Le deuxième mot doit être "IN", le troisième mot "DS". Les mots suivants spécifient le tag de clé, l'algorithme de signature, l'algorithme de digest, suivi de l'empreinte de clé encodée en hexadécimal. Voir la RFC 4034, Section 5[3] pour les détails sur la syntaxe précise et la signification de ces champs.

Alternativement, les enregistrements de ressources DNSKEY peuvent être utilisés pour définir des ancres de confiance, comme dans l'exemple suivant :

. IN DNSKEY 257 3 8 AwEAAagAIKlVZrpC6Ia7gEzahOR+9W29euxhJhVVLOyQbSEW0O8gcCjFFVQUTf6v58fLjwBd0YI0EzrAcQqBGCzh/RStIoO8g0NfnfL2MTJRkxoXbfDaUeVPQuYEhg37NZWAJQ9VnMVDxP/VHL496M/QZxkjf5/Efucp2gaDX6RS6CXpoY68LsvPVjR0ZSwzz1apAzvN9dlzEheX7ICJBBtuA6G3LQpzW5hOA2hzCTMjJPJ8LbqF6dsV6DoBQzgul0sGIcGOYl7OyQdXfZ57relSQageu+ipAdTTJ25AsRTAoub8ONGcLmqrAmRLKBP1dfwhYB4N7knNnulqQxA+Uk1ihz0=

Le premier mot spécifie à nouveau le domaine, le deuxième mot doit être "IN", suivi de "DNSKEY". Les mots suivants encodent les drapeaux, le protocole et les champs d'algorithme du DNSKEY, suivis des données de clé encodées en Base64. Voir la RFC 4034, Section 2[4] pour les détails sur la syntaxe précise et la signification de ces champs.

Si plusieurs enregistrements DS ou DNSKEY sont définis pour le même domaine (peut-être même dans différents fichiers d'ancres de confiance), toutes les clés sont utilisées et sont considérées comme équivalentes comme base pour les preuves DNSSEC.

Notez que systemd-resolved utilisera automatiquement une clé d'ancre de confiance intégrée pour le domaine racine d'Internet si aucune ancre de confiance positive n'est définie pour le domaine racine. Dans la plupart des cas, il n'est donc pas nécessaire de définir une clé explicite avec des fichiers d'ancres de confiance. La clé intégrée est désactivée dès qu'au moins une clé d'ancre de confiance pour le domaine racine est définie dans les fichiers d'ancres de confiance.

Il est généralement recommandé d'encoder les ancres de confiance dans des enregistrements de ressources DS, plutôt que dans des enregistrements DNSKEY.

Si une ancre de confiance spécifiée via un enregistrement DS est trouvée révoquée, elle est automatiquement supprimée de la base de données des ancres de confiance pour la durée d'exécution. Voir la RFC 5011[5] pour les détails sur les ancres de confiance révoquées. Notez que systemd-resolved ne mettra pas à jour sa base de données d'ancres de confiance à partir des serveurs DNS automatiquement. Il est plutôt recommandé de mettre à jour le logiciel résolveur ou de mettre à jour la nouvelle ancre de confiance en l'ajoutant dans de nouveaux fichiers d'ancres de confiance.

L'ancre de confiance DNSSEC actuelle pour le domaine racine d'Internet est disponible sur la page des Ancres de confiance et clés IANA[6].

ANCRES DE CONFIANCE NÉGATIVES

Les ancres de confiance négatives définissent les domaines où la validation DNSSEC doit être désactivée. Les fichiers d'ancres de confiance négatives se trouvent au même endroit que les fichiers d'ancres de confiance positives et suivent les mêmes règles de remplacement. Ce sont des fichiers texte avec le suffixe .negative. Les lignes vides et les lignes dont le premier caractère est ";" sont ignorées. Chaque ligne spécifie un nom de domaine qui est la racine d'un sous-arbre DNS où la validation doit être désactivée. Par exemple :

# Mappages inversés IPv4
10.in-addr.arpa
16.172.in-addr.arpa
168.192.in-addr.arpa
...
# Certains domaines personnalisés
prod
stag

Les ancres de confiance négatives sont utiles pour prendre en charge des sous-arbres DNS privés qui ne sont pas référencés dans la hiérarchie DNS d'Internet et qui ne sont pas signés.

Voir la RFC 7646[7] pour les détails sur les ancres de confiance négatives.

Si aucun fichier d'ancres de confiance négatives n'est configuré, un ensemble intégré de domaines de zones DNS privés bien connus est utilisé comme ancres de confiance négatives.

Il est également possible de définir des ancres de confiance négatives par interface en utilisant le réglage DNSSECNegativeTrustAnchors= dans les fichiers systemd.network(5).

NOM

systemd.positive - Points d'ancrage de confiance pour les unités de journal

SYNTAXE

/etc/systemd/journald.conf.d/*.conf, /run/systemd/journald.conf.d/*.conf, /usr/lib/systemd/journald.conf.d/*.conf

DESCRIPTION

Le fichier journald.conf peut être utilisé pour configurer le démon systemd-journald. Les paramètres sont groupés dans les sections suivantes : [Journal].

Le démon systemd-journald est le composant central du système de journalisation de systemd. Il collecte et stocke les journaux de journalisation de toutes les parties du système et de toutes les applications. Il est conçu pour être un démon de journalisation efficace, avec des fonctionnalités telles que le traitement en temps réel des entrées de journal, le filtrage, le regroupement et la rotation automatique des fichiers de journal.

Le fichier systemd.positive spécifie des points d'ancrage de confiance pour les entrées de journal. Ces points d'ancrage sont utilisés pour garantir l'intégrité et l'authenticité des journaux. Les points d'ancrage de confiance positifs sont des identifiants qui doivent être présents dans les entrées de journal pour qu'elles soient considérées comme fiables. Les points d'ancrage de confiance négatifs sont des identifiants qui, s'ils sont présents, rendent une entrée de journal non fiable.

POINTS D'ANCRAGE DE CONFIANCE POSITIFS

Les points d'ancrage de confiance positifs sont spécifiés dans la configuration de journald. Ils peuvent inclure des identifiants tels que les noms d'unités, les identifiants de processus, les noms d'utilisateurs ou les identifiants de système. Par exemple, une entrée de journal provenant de l'unité "systemd-networkd.service" peut être considérée comme un point d'ancrage de confiance positif.

La directive TrustedDomain= dans journald.conf peut être utilisée pour spécifier des points d'ancrage de confiance positifs. Par exemple :

[Journal]
TrustedDomain=systemd-networkd.service
TrustedDomain=root

Cela indiquerait que les entrées de journal provenant de "systemd-networkd.service" et celles générées par l'utilisateur "root" sont considérées comme fiables.

POINTS D'ANCRAGE DE CONFIANCE NÉGATIFS

Les points d'ancrage de confiance négatifs sont utilisés pour exclure certaines entrées de journal de la considération comme fiables. Cela peut être utile pour ignorer les journaux provenant de sources potentiellement non fiables ou de processus spécifiques qui génèrent des journaux indésirables.

La directive UntrustedDomain= dans journald.conf peut être utilisée pour spécifier des points d'ancrage de confiance négatifs. Par exemple :

[Journal]
UntrustedDomain=unimportant-service.service

Cela indiquerait que les entrées de journal provenant de "unimportant-service.service" ne doivent pas être considérées comme fiables.

VOIR AUSSI

systemd-journald.service(8), journalctl(1), journald.conf(5)

NOTES

La gestion des points d'ancrage de confiance est essentielle pour maintenir l'intégrité et la sécurité du système de journalisation. Il est recommandé de configurer soigneusement les points d'ancrage de confiance positifs et négatifs en fonction des besoins spécifiques de votre système.
