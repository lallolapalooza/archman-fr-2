SYSTEMD-VMSPAWN(1) systemd-vmspawn SYSTEMD-VMSPAWN(1)

NOM

systemd-vmspawn - Lancer un système d'exploitation dans une machine virtuelle

SYNTAXE

systemd-vmspawn [OPTIONS...] [ARGUMENTS...]

DESCRIPTION

systemd-vmspawn peut être utilisé pour démarrer une machine virtuelle à partir d'une image système. À bien des égards, il est similaire à systemd-nspawn(1), mais lance une machine virtuelle complète au lieu d'utiliser des espaces de noms.

Les descripteurs de fichiers pour /dev/kvm et /dev/vhost-vsock peuvent être passés à systemd-vmspawn via l'interface de passage de sockets native de systemd (voir sd_listen_fds(3) pour les détails sur le protocole précis utilisé et l'ordre dans lequel les descripteurs de fichiers sont passés), ces descripteurs de fichiers doivent être passés avec les noms "kvm" et "vhost-vsock" respectivement.

Note : sur les dérivés d'Ubuntu/Debian, systemd-vmspawn nécessite que l'utilisateur appartienne au groupe "kvm" pour utiliser les options VSOCK.

OPTIONS

Les arguments excédentaires sont passés comme arguments de ligne de commande supplémentaires du noyau en utilisant SMBIOS.

Les options suivantes sont comprises :

-q, --quiet

Désactive toute sortie d'état par l'outil lui-même. Lorsque ce commutateur est utilisé, la seule sortie de vmspawn sera la sortie console du système d'exploitation de la machine virtuelle elle-même.

Ajouté dans la version 256.

Options d'image

-D, --directory=

Répertoire à utiliser comme racine du système de fichiers pour la machine virtuelle.

L'une des options --directory= ou --image= doit être spécifiée. Si aucune n'est spécifiée, --directory=. est supposé.

Note : si vous montez un répertoire qui n'est pas détenu par root, vous pourriez avoir besoin de --private-users= pour mapper dans l'espace de noms des sous-UID de l'utilisateur. Un exemple d'utilisation de /etc/subuid à cet effet est donné plus loin.

Ajouté dans la version 256.

-i, --image=

Image disque (ou nœud de périphérique) de la racine du système de fichiers pour la machine virtuelle.

Ajouté dans la version 255.

Configuration de l'hôte

--cpus=CPUS

Le nombre de CPU à allouer à la machine virtuelle. Par défaut, 1.

Ajouté dans la version 255.

--ram=OCTETS

La quantité de mémoire à allouer à la machine virtuelle. Par défaut, 2G.

Ajouté dans la version 255.

--kvm=BOOL

Si --kvm= n'est pas spécifié, le support KVM sera détecté automatiquement. Si vrai, KVM est toujours utilisé, et si faux, KVM n'est jamais utilisé.

Ajouté dans la version 255.

--vsock=BOOL

Si --vsock= n'est pas spécifié, le support réseau VSOCK sera détecté automatiquement. Si vrai, le réseau VSOCK est toujours utilisé, et si faux, le réseau VSOCK n'est jamais utilisé.

Ajouté dans la version 255.

--vsock-cid=CID

Définit le CID spécifique à utiliser pour l'invité. Les CID valides sont dans la plage 3 à 4294967294 (0xFFFF_FFFE). Les CID en dehors de cette plage sont réservés. Par défaut, vmspawn tentera de dériver un CID pour l'invité à partir du nom de la machine, en se rabattant sur un CID aléatoire si ce CID est déjà pris.

Ajouté dans la version 255.

--tpm=BOOL

Si --tpm= n'est pas spécifié, vmspawn détectera la présence de swtpm(8) et l'utilisera si disponible. Si oui est spécifié, swtpm(8) est toujours utilisé, et si non est défini, swtpm(8) n'est jamais utilisé.

Ajouté dans la version 256.

--tpm-state=CHEMIN|auto|off

Configure où placer l'état du TPM, au cas où le support TPM serait activé (voir --tpm= ci-dessus). Ceci prend un chemin absolu dans le système de fichiers vers un répertoire pour placer de manière persistante l'état. Si le répertoire est manquant, il est créé selon les besoins. S'il est défini à la chaîne spéciale "auto", un chemin persistant est automatiquement dérivé du chemin de l'image VM ou du chemin du répertoire, avec le suffixe ".tpmstate" ajouté. S'il est défini à la chaîne spéciale "off", l'état du TPM n'est maintenu que de manière transitoire et est effacé lorsque la VM s'arrête. Ce mode n'est pas adapté aux VM qui verrouillent les clés de chiffrement de disque au TPM, car ces clés seront perdues à chaque redémarrage. Par défaut, "auto".

Ajouté dans la version 258.

--linux=CHEMIN

Définit l'image du noyau Linux à utiliser pour le démarrage direct du noyau. Si une image de type répertoire est utilisée et que --linux= a été omis, vmspawn recherchera les entrées du chargeur de démarrage conformément à la Spécification du chargeur de démarrage[1], en supposant que XBOOTLDR se trouve à /boot et ESP à /efi respectivement. Si aucun noyau n'a été installé dans l'image, l'image échouera au démarrage.

Ajouté dans la version 256.

--initrd=CHEMIN

Définit l'initrd à utiliser pour le démarrage direct du noyau. Si le noyau fourni par --linux= est une entrée de type #2 de la Spécification du chargeur de démarrage[1], alors cet argument n'est pas requis. Si aucun initrd n'a été installé dans l'image, l'image échouera au démarrage.

--initrd= peut être spécifié plusieurs fois et vmspawn les fusionnera.

Ajouté dans la version 256.

-n, --network-tap

Crée un périphérique TAP pour le réseau avec la machine virtuelle.

Note : les privilèges root sont requis pour utiliser le réseau TAP. De plus, systemd-networkd(8) doit être en cours d'exécution et correctement configuré sur l'hôte pour provisionner l'interface hôte. Le fichier ".network" pertinent peut être trouvé à l'adresse /usr/lib/systemd/network/80-vm-vt.network.

Ajouté dans la version 255.

--network-user-mode

Utilise le réseau en mode utilisateur.

Ajouté dans la version 255.

--firmware=CHEMIN

Prend un chemin absolu, ou un chemin relatif commençant par './'. Spécifie un fichier de définition de firmware JSON, qui permet de sélectionner le firmware à démarrer dans la VM. Si non spécifié, un firmware approprié est automatiquement découvert. Si la chaîne spéciale "list" est spécifiée, elle liste tous les firmwares découverts.

Ajouté dans la version 256.

--discard-disk=BOOL

Contrôle si qemu traite les demandes de rejet de la VM. Cela empêche les VM en cours d'exécution de longue durée d'utiliser plus d'espace disque que nécessaire. Ceci est activé par défaut.

Ajouté dans la version 256.

--secure-boot=BOOL

Configure s'il faut rechercher un firmware qui prend en charge le démarrage sécurisé.

Si l'option n'est pas spécifiée, le premier firmware détecté sera utilisé. Si l'option est définie à oui, alors le premier firmware avec support de démarrage sécurisé sera sélectionné. Si non est spécifié, alors le premier firmware sans démarrage sécurisé sera sélectionné.

Ajouté dans la version 255.

--grow-image=OCTETS, -G OCTETS

Augmente la taille du fichier image spécifié par --image= à la taille spécifiée en octets s'il est plus petit. N'exécute aucune opération si aucun fichier image n'est utilisé ou si le fichier image est déjà aussi grand ou plus grand que demandé. La taille spécifiée accepte les suffixes K, M, G habituels (à la base 1024). Les valeurs spécifiées sont arrondies aux multiples de 4096.

Ajouté dans la version 258.

--smbios11=CHAINE, -s CHAINE

Passe la chaîne spécifiée dans la VM en tant que chaîne de vendeur SMBIOS Type #11. Ceci est utile pour paramétrer la VM invoquée de diverses manières. Voir smbios-type-11(7) pour plus de détails.

Ajouté dans la version 258.

--notify-ready=

Configure le support des notifications du processus d'initialisation de la VM à systemd-vmspawn. Si vrai, systemd-vmspawn considérera la machine comme prête uniquement lorsqu'elle aura reçu un message "READY=1" du processus d'initialisation dans la VM. Si faux, systemd-vmspawn considérera la machine comme prête immédiatement après sa création. Dans les deux cas,

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

systemd-vmspawn envoie sa propre notification de disponibilité à son gestionnaire une fois la VM démarrée prête. Pour plus de détails sur les notifications, voir sd_notify(3).

Par défaut, true. (Notez que cela diffère de l'option du même nom de systemd-vmspawn(1) qui vaut false par défaut.)

Ajouté dans la version 258.

Options d'identité du système

-M, --machine=

Définit le nom de la machine pour cette machine virtuelle. Ce nom peut être utilisé pour identifier cette machine virtuelle pendant son exécution (par exemple dans des outils comme machinectl(1) et similaires).

Ajouté dans la version 255.

--uuid=

Définit l'UUID spécifié pour la machine virtuelle. Le système d'init initialisera /etc/machine-id à partir de ceci si ce fichier n'est pas encore défini. Notez que cette option ne prend effet que si /etc/machine-id dans la machine virtuelle est vide.

Ajouté dans la version 256.

Options de propriété

-S, --slice=

Intègre la VM dans la tranche spécifiée, au lieu de la tranche machine par défaut. Ceci ne s'applique que si la machine est exécutée dans sa propre unité de portée (scope), c'est-à-dire si --keep-unit n'est pas utilisé.

Ajouté dans la version 258.

--property=

Définit une propriété d'unité sur l'unité de portée à enregistrer pour la machine. Ceci ne s'applique que si la machine est exécutée dans sa propre unité de portée, c'est-à-dire si --keep-unit n'est pas utilisé. Prend des affectations de propriétés d'unité dans le même format que systemctl set-property. Ceci est utile pour définir des limites de mémoire et similaires pour la VM.

Ajouté dans la version 258.

--register=

Contrôle si la machine virtuelle est enregistrée auprès de systemd-machined(8). Prend un argument booléen, qui vaut par défaut "yes" lorsque exécuté en tant que root, et "no" lorsque exécuté en tant qu'utilisateur régulier. Ceci garantit que la machine virtuelle est accessible via machinectl(1).

Note : les privilèges root sont requis pour utiliser cette option, car l'enregistrement auprès de systemd-machined(8) nécessite des appels de méthodes D-Bus privilégiés.

Ajouté dans la version 256.

Options de nommage d'espace utilisateur

--private-users=UID_SHIFT[:UID_RANGE]

Contrôle le nommage d'espace utilisateur sous --directory=. S'il est activé, virtiofsd(1) est chargé de mapper les identifiants d'utilisateur et de groupe (UIDs et GIDs). Cela implique de mapper les UIDs/GIDs privés utilisés dans la machine virtuelle (en commençant par l'utilisateur root 0 de la machine virtuelle et au-delà) à une plage d'UIDs/GIDs sur l'hôte qui ne sont utilisés à aucune autre fin (généralement au-delà de 65536 pour les UIDs/GIDs de l'hôte).

Si un ou deux nombres séparés par deux points sont spécifiés, le nommage d'espace utilisateur est activé. UID_SHIFT spécifie le premier UID/GID de l'hôte à mapper, UID_RANGE est facultatif et spécifie le nombre d'UIDs/GIDs de l'hôte à attribuer à la machine virtuelle. Si UID_RANGE est omis, 65536 UIDs/GIDs sont attribués.

Lorsque des espaces de noms utilisateur sont utilisés, la plage de GIDs attribuée à chaque machine virtuelle est toujours choisie identique à la plage d'UIDs.

Ajouté dans la version 256.

Options de montage

--bind=PATH, --bind-ro=PATH

Monte un répertoire de l'hôte dans la machine virtuelle. Prend l'un des arguments suivants : un chemin — dans ce cas, le chemin spécifié sera monté de l'hôte vers le même chemin dans la machine virtuelle, ou une paire de chemins séparés par des deux-points — dans ce cas, le premier chemin spécifié est la source sur l'hôte, et le second chemin est la destination dans la machine virtuelle. Si le chemin source n'est pas absolu, il est résolu par rapport au répertoire de travail actuel. L'option --bind-ro= crée des montages bind en lecture seule. Les échappements de barre oblique inverse sont interprétés, donc "\:" peut être utilisé pour intégrer des deux-points dans l'un ou l'autre chemin. Cette option peut être spécifiée plusieurs fois pour créer plusieurs points de montage bind indépendants.

Ajouté dans la version 256.

--extra-drive=PATH

Prend une image disque ou un périphérique bloc sur l'hôte et la fournit à la machine virtuelle comme un autre lecteur.

Ajouté dans la version 256.

Options d'intégration

--forward-journal=FILE|DIR

Transmet le journal de la machine virtuelle à l'hôte. systemd-journal-remote(8) est actuellement utilisé pour recevoir les entrées du journal transférées de la VM invitée. Cette option détermine où ce journal est sauvegardé sur l'hôte et a la même sémantique que -o/--output décrite dans systemd-journal-remote(8).

Ajouté dans la version 256.

--pass-ssh-key=BOOL

Par défaut, une clé SSH est générée pour permettre à systemd-vmspawn d'ouvrir une connexion D-Bus au bus système de la VM. Définir ceci sur "no" désactivera la génération de clé SSH.

Les clés générées sont éphémères. C'est-à-dire qu'elles ne sont valides que pour l'invocation actuelle de systemd-vmspawn, et ne sont généralement pas persistantes.

Ajouté dans la version 256.

--ssh-key-type=TYPE

Configure le type de clé SSH à générer, voir ssh-keygen(1) pour plus d'informations.

Par défaut, des clés "ed25519" sont générées, cependant des clés "rsa" peuvent également être utiles si la VM a une version particulièrement ancienne de sshd(8).

Ajouté dans la version 256.

Options d'entrée/sortie

--console=MODE

Configure la manière de configurer la console de la VM. Prend l'une des valeurs suivantes : "interactive", "read-only", "native", "gui". Par défaut, "interactive". "interactive" fournit une interface terminal interactive à la VM. "read-only" est similaire, mais est strictement en lecture seule, c'est-à-dire qu'elle n'accepte aucune entrée de l'utilisateur. "native" fournit également une interface basée sur TTY, mais utilise l'implémentation native de qemu (ce qui signifie que le moniteur qemu est disponible). "gui" affiche l'interface graphique qemu.

Ajouté dans la version 256.

--background=COLOR

Change la couleur d'arrière-plan du terminal à la couleur ANSI spécifiée tant que la VM est en cours d'exécution. La couleur spécifiée doit être une couleur d'arrière-plan SGR ANSI X3.64, c'est-à-dire des chaînes comme "40", "41", ..., "47", "48;2;...", "48;5;...". Voir ANSI Escape Code (Wikipedia)[2] pour plus de détails. Attribuez une chaîne vide pour désactiver toute coloration. Ceci n'a d'effet que dans les modes --console=interactive et --console=read-only.

Ajouté dans la version 256.

Identifiants

--load-credential=ID:PATH, --set-credential=ID:VALUE

Passe un identifiant à la machine virtuelle. Ces deux options correspondent aux paramètres LoadCredential= et SetCredential= dans les fichiers d'unité. Voir systemd.exec(5) pour plus de détails sur ces concepts, ainsi que sur la syntaxe des arguments de l'option.

Afin d'intégrer des données binaires dans les données d'identifiant pour --set-credential=, utilisez l'échappement de style C (c'est-à-dire "\n" pour intégrer un saut de ligne, ou "\x00" pour intégrer un octet NUL. Notez que le shell appelant peut déjà appliquer un déséchappement une fois, ce qui pourrait nécessiter un double échappement !

Ajouté dans la version 255.

Autres options

--no-pager

Ne pas rediriger la sortie vers un pagineur.

-h, --help

Affiche un court message d'aide et quitte.

--version

Affiche une courte chaîne de version et quitte.

--no-ask-password

Ne pas demander à l'utilisateur de s'authentifier pour les opérations privilégiées.

ENVIRONNEMENT

$SYSTEMD_LOG_LEVEL

Le niveau de journalisation maximal des messages émis (les messages d'un niveau de journalisation supérieur, c'est-à-dire moins importants, seront supprimés). Prend une liste de valeurs séparées par des virgules. Une valeur peut être l'une des suivantes (par ordre d'importance décroissante) : emerg, alert, crit, err, warning, notice, info, debug, ou un entier dans la plage 0...7. Voir syslog(3) pour plus d'informations. Chaque valeur peut optionnellement être préfixée par l'un des mots-clés suivants : console, syslog, kmsg ou journal suivi de deux points pour définir le niveau de journalisation maximal pour cette cible de journal spécifique (par exemple, SYSTEMD_LOG_LEVEL=debug,console:info spécifie de journaliser au niveau debug sauf lorsque l'on journalise vers la console, qui devrait être au niveau info). Notez que le niveau de journalisation maximal global a la priorité sur les niveaux de journalisation maximaux par cible.

$SYSTEMD_LOG_COLOR

Un booléen. S'il est vrai, les messages écrits sur le tty seront colorés en fonction de leur priorité.

Ce paramètre n'est utile que lorsque les messages sont écrits directement sur le terminal, car journalctl(1) et d'autres outils qui affichent les journaux coloreront les messages en fonction du niveau de journalisation par eux-mêmes.

$SYSTEMD_LOG_TIME

Un booléen. S'il est vrai, les messages de journalisation de la console seront préfixés par un horodatage.

Ce paramètre n'est utile que lorsque les messages sont écrits directement sur le terminal ou dans un fichier, car journalctl(1) et d'autres outils qui affichent les journaux ajouteront des horodatages basés sur les métadonnées de l'entrée par eux-mêmes.

$SYSTEMD_LOG_LOCATION

Un booléen. S'il est vrai, les messages seront préfixés par le nom du fichier et le numéro de ligne
dans le code source où le message est généré.

Notez que l'emplacement du journal est souvent joint en tant que métadonnées aux entrées du journal de toute façon. L'inclure directement dans le texte du message peut néanmoins être pratique lors du débogage de programmes.

$SYSTEMD_LOG_TID

Un booléen. S'il est vrai, les messages seront préfixés par l'ID numérique actuel du thread (TID).

Notez que ces informations sont jointes en tant que métadonnées aux entrées du journal de toute façon. L'inclure directement dans le texte du message peut néanmoins être pratique lors du débogage de programmes.

$SYSTEMD_LOG_TARGET

La destination des messages de journal. L'un des éléments suivants : console (journal vers le tty attaché), console-prefixed (journal vers le tty attaché mais avec des préfixes codant le niveau de journalisation et la "facilité", voir syslog(3), kmsg (journal vers le tampon de journal circulaire du noyau), journal (journal vers le journal), journal-or-kmsg (journal vers le journal si disponible, et sinon vers kmsg), auto (détermine automatiquement la cible de journal appropriée, par défaut), null (désactive la sortie du journal).

$SYSTEMD_LOG_RATELIMIT_KMSG

Si le kmsg doit être limité en débit ou non. Prend un booléen. Par défaut, "true". Si désactivé, systemd ne limitera pas le débit des messages écrits dans kmsg.

$SYSTEMD_PAGER, $PAGER

Le pagineur à utiliser lorsque --no-pager n'est pas donné. $SYSTEMD_PAGER est utilisé s'il est défini ; sinon, $PAGER est utilisé. Si ni $SYSTEMD_PAGER ni $PAGER ne sont définis, un ensemble d'implémentations de pagineurs bien connues sont essayées tour à tour, y compris less(1) et more(1), jusqu'à ce qu'un soit trouvé. Si aucune implémentation de pagineur n'est découverte, aucun pagineur n'est invoqué. Définir ces variables d'environnement sur une chaîne vide ou sur la valeur "cat" équivaut à passer --no-pager.

Note : si $SYSTEMD_PAGERSECURE n'est pas défini, $SYSTEMD_PAGER et $PAGER ne peuvent être utilisés que pour désactiver le pagineur (avec "cat" ou "") et sont par ailleurs ignorés.

$SYSTEMD_LESS

Remplace les options passées à less (par défaut "FRSXMK").

Les utilisateurs pourraient vouloir changer deux options en particulier :

K

Cette option indique au pagineur de quitter immédiatement lorsque Ctrl+C est pressé. Pour permettre à less de gérer Ctrl+C lui-même afin de revenir à l'invite de commande du pagineur, désactivez cette option.

Si la valeur de $SYSTEMD_LESS n'inclut pas "K", et que le pagineur invoqué est less, Ctrl+C sera ignoré par l'exécutable, et devra être géré par le pagineur.

X

Cette option indique au pagineur de ne pas envoyer les chaînes d'initialisation et de désinitialisation de terme cap au terminal. Elle est définie par défaut pour permettre à la sortie des commandes de rester visible dans le terminal même après la sortie du pagineur. Néanmoins, cela empêche certaines fonctionnalités du pagineur de fonctionner, en particulier la sortie paginée ne peut pas être défilée avec la souris.

Notez que la définition de la variable d'environnement régulière $LESS n'a aucun effet pour les invocations de less par les outils systemd.

Voir less(1) pour plus de détails.

$SYSTEMD_LESSCHARSET

Remplace le jeu de caractères passé à less (par défaut "utf-8", si le terminal appelant est déterminé comme étant compatible UTF-8).

Notez que la définition de la variable d'environnement régulière $LESSCHARSET n'a aucun effet pour les invocations de less par les outils systemd.

$SYSTEMD_PAGERSECURE

Les commandes de pagineur courantes comme less(1), en plus de la "pagination", c'est-à-dire du défilement de la sortie, prennent en charge l'ouverture ou l'écriture d'autres fichiers et l'exécution de commandes shell arbitraires. Lorsque des commandes sont invoquées avec des privilèges élevés, par exemple sous sudo(8) ou pkexec(1), le pagineur devient une frontière de sécurité. Il faut veiller à ce que seuls des programmes aux fonctionnalités strictement limitées soient utilisés comme pagineurs, et que les fonctionnalités interactives involontaires telles que l'ouverture ou la création de nouveaux fichiers ou le lancement de sous-processus ne soient pas autorisées. Le "mode sécurisé" pour le pagineur peut être activé comme décrit ci-dessous, si le pagineur le prend en charge (la plupart des pagineurs ne sont pas écrits de manière à en tenir compte). Il est recommandé soit d'activer explicitement le "mode sécurisé", soit de désactiver complètement le pagineur en utilisant --no-pager ou PAGER=cat lorsque des utilisateurs non fiables sont autorisés à exécuter des commandes avec des privilèges élevés.

Cette option prend un argument booléen. Lorsqu'elle est définie sur vrai, le "mode sécurisé" du pagineur est activé. En "mode sécurisé", LESSSECURE=1 sera défini lors de l'invocation du pagineur, ce qui indique au pagineur de désactiver les commandes qui ouvrent ou créent de nouveaux fichiers ou lancent de nouveaux sous-processus. Actuellement, seul less(1) est connu pour comprendre cette variable et implémenter le "mode sécurisé".

Lorsqu'elle est définie sur faux, aucune restriction n'est placée sur le pagineur. Définir SYSTEMD_PAGERSECURE=0 ou ne pas la supprimer de l'environnement hérité peut permettre à l'utilisateur d'invoquer des commandes arbitraires.

Lorsque $SYSTEMD_PAGERSECURE n'est pas défini, les outils systemd tentent de déterminer automatiquement si le "mode sécurisé" doit être activé et si le pagineur le prend en charge. Le "mode sécurisé" est activé si l'UID effectif n'est pas le même que le propriétaire de la session de connexion, voir geteuid(2) et sd_pid_get_owner_uid(3), ou lors de l'exécution sous sudo(8) ou des outils similaires ($SUDO_UID est défini [3]). Dans ces cas, SYSTEMD_PAGERSECURE=1 sera défini et les pagineurs qui ne sont pas connus pour implémenter le "mode sécurisé" ne seront pas utilisés du tout. Notez que cette autodétection ne couvre que les mécanismes les plus courants d'élévation des privilèges et est destinée à être pratique. Il est recommandé de définir explicitement $SYSTEMD_PAGERSECURE ou de désactiver le pagineur.

Notez que si les variables $SYSTEMD_PAGER ou $PAGER doivent être respectées, autre que pour désactiver le pagineur, $SYSTEMD_PAGERSECURE doit également être défini.

$SYSTEMD_COLORS

Prend un argument booléen. Lorsqu'il est vrai, systemd et les utilitaires associés utiliseront des couleurs dans leur sortie, sinon la sortie sera monochrome. De plus, la variable peut prendre l'une des valeurs spéciales suivantes : "16", "256" pour restreindre l'utilisation des couleurs aux 16 ou 256 couleurs ANSI de base, respectivement. Ceci peut être spécifié pour remplacer la décision automatique basée sur $TERM et sur ce à quoi le console est connecté.

$SYSTEMD_URLIFY

La valeur doit être un booléen. Contrôle si des liens cliquables doivent être générés dans la sortie pour les émulateurs de terminaux qui prennent en charge cela. Ceci peut être spécifié pour remplacer la décision prise par systemd en fonction de $TERM et d'autres conditions.

EXEMPLES

Exemple 1. Exécuter une image de VM Arch Linux générée par mkosi

$ mkosi -d arch -p systemd -p linux --autologin -o image.raw -f build
$ systemd-vmspawn --image=image.raw

Exemple 2. Importer et exécuter une image cloud Fedora 42 en utilisant machinectl

$ curl -L \
       -O https://download.fedoraproject.org/pub/fedora/linux/releases/42/Cloud/x86_64/images/Fedora-Cloud-Base-42-1.1.x86_64.raw.xz \
       -O https://download.fedoraproject.org/pub/fedora/linux/releases/42/Cloud/x86_64/images/Fedora-Cloud-42-1.1-x86_64-CHECKSUM \
       -O https://fedoraproject.org/fedora.gpg
$ gpgv --keyring ./fedora.gpg Fedora-Cloud-42-1.1-x86_64-CHECKSUM
$ sha256sum -c Fedora-Cloud-42-1.1-x86_64-CHECKSUM
# machinectl import-raw Fedora-Cloud-Base-42-1.1.x86_64.raw.xz fedora-42-cloud
# systemd-vmspawn -M fedora-42-cloud

Exemple 3. Construire et exécuter l'image système de systemd et transférer le journal de la VM vers un fichier local

$ mkosi build
$ systemd-vmspawn \
    -D mkosi.output/system \
    --private-users $(grep $(whoami) /etc/subuid | cut -d: -f2) \
    --linux mkosi.output/system.efi \
    --forward-journal=vm.journal \
    enforcing=0

Note : cet exemple utilise également un argument de ligne de commande du noyau pour s'assurer que SELinux n'est pas démarré en mode d'application.

Exemple 4. Se connecter à une VM en cours d'exécution en utilisant systemd-ssh-proxy

$ mkosi build
$ my_vsock_cid=3735928559
$ systemd-vmspawn \
    -D mkosi.output/system \
    --private-users $(grep $(whoami) /etc/subuid | cut -d: -f2) \
    --linux mkosi.output/system.efi \
    --vsock-cid $my_vsock_cid \
    enforcing=0
$ ssh root@vsock/$my_vsock_cid -i /run/user/$UID/systemd/vmspawn/machine-*-system-ed25519

STATUT DE SORTIE

En cas d'erreur, la valeur errno est propagée au code de retour. Si EXIT_STATUS est fourni par l'image en cours d'exécution, il est retourné. Sinon, EXIT_SUCCESS est retourné.
