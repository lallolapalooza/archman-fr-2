NOM

dnssec-trust-anchors.d, systemd.positive, systemd.negative - fichiers de configuration des ancres de confiance DNSSEC

SYNTAXE

/etc/dnssec-trust-anchors.d/*.positive
/run/dnssec-trust-anchors.d/*.positive
/usr/local/lib/dnssec-trust-anchors.d/*.positive
/usr/lib/dnssec-trust-anchors.d/*.positive
/etc/dnssec-trust-anchors.d/*.negative
/run/dnssec-trust-anchors.d/*.negative
/usr/local/lib/dnssec-trust-anchors.d/*.negative
/usr/lib/dnssec-trust-anchors.d/*.negative

DESCRIPTION

Les fichiers de configuration des ancres de confiance DNSSEC définissent les ancres de confiance positives et négatives sur lesquelles systemd-resolved.service(8) base les preuves d'intégrité DNSSEC.

ANCres de confiance POSITIVES

Les fichiers de configuration des ancres de confiance positives contiennent les définitions d'enregistrements de ressources DNSKEY et DS à utiliser comme base pour les preuves d'intégrité DNSSEC. Voir RFC 4035, Section 4.4[1] pour plus d'informations sur les ancres de confiance DNSSEC.

Les ancres de confiance positives sont lues à partir des fichiers dont le suffixe est .positive, situés dans /etc/dnssec-trust-anchors.d/, /run/dnssec-trust-anchors.d/ et /usr/lib/dnssec-trust-anchors.d/. Ces répertoires sont recherchés dans l'ordre spécifié, et un fichier d'ancre de confiance du même nom dans un chemin antérieur remplace les fichiers d'ancres de confiance dans un chemin ultérieur. Pour désactiver un fichier d'ancre de confiance fourni dans /usr/lib/dnssec-trust-anchors.d/, il suffit de fournir un fichier de nom identique dans /etc/dnssec-trust-anchors.d/ ou /run/dnssec-trust-anchors.d/ qui est soit vide, soit un lien symbolique vers /dev/null (« masqué »).

Les fichiers d'ancres de confiance positives sont des fichiers texte simples ressemblant aux fichiers de zone DNS, tels que documentés dans RFC 1035, Section 5[2]. Un enregistrement de ressource DS ou DNSKEY peut être listé par ligne. Les lignes vides et les lignes commençant par « # » ou « ; » sont ignorées, ce qui peut être utilisé pour les commentaires. Un enregistrement de ressource DS est spécifié comme dans l'exemple suivant :

. IN DS 19036 8 2 49aac11d7b6f6446702e54a1607371607a1a41855200fd2ce1cdde32f24e8fb5

Le premier mot spécifie le domaine, utilisez « . » pour le domaine racine. Le domaine peut être spécifié avec ou sans point final, ce qui est considéré comme équivalent. Le deuxième mot doit être « IN », le troisième mot « DS ». Les mots suivants spécifient la balise de clé, l'algorithme de signature, l'algorithme de hachage, suivis de l'empreinte de clé encodée en hexadécimal. Voir RFC 4034, Section 5[3] pour les détails sur la syntaxe précise et la signification de ces champs.

Alternativement, les enregistrements de ressources DNSKEY peuvent être utilisés pour définir des ancres de confiance, comme dans l'exemple suivant :

. IN DNSKEY 257 3 8 AwEAAagAIKlVZrpC6Ia7gEzahOR+9W29euxhJhVVLOyQbSEW0O8gcCjFFVQUTf6v58fLjwBd0YI0EzrAcQqBGCzh/RStIoO8g0NfnfL2MTJRkxoXbfDaUeVPQuYEhg37NZWAJQ9VnMVDxP/VHL496M/QZxkjf5/Efucp2gaDX6RS6CXpoY68LsvPVjR0ZSwzz1apAzvN9dlzEheX7ICJBBtuA6G3LQpzW5hOA2hzCTMjJPJ8LbqF6dsV6DoBQzgul0sGIcGOYl7OyQdXfZ57relSQageu+ipAdTTJ25AsRTAoub8ONGcLmqrAmRLKBP1dfwhYB4N7knNnulqQxA+Uk1ihz0=

Le premier mot spécifie à nouveau le domaine, le deuxième mot doit être « IN », suivi de « DNSKEY ». Les mots suivants encodent les indicateurs DNSKEY, le protocole et les champs d'algorithme, suivis des données clés encodées en Base64. Voir RFC 4034, Section 2[4] pour les détails sur la syntaxe précise et la signification de ces champs.

Si plusieurs enregistrements DS ou DNSKEY sont définis pour le même domaine (potentiellement même dans différents fichiers d'ancres de confiance), toutes les clés sont utilisées et considérées comme équivalentes comme base pour les preuves DNSSEC.

Notez que systemd-resolved utilisera automatiquement une clé d'ancre de confiance intégrée pour le domaine racine d'Internet si aucune ancre de confiance positive n'est définie pour le domaine racine. Dans la plupart des cas, il est donc inutile de définir une clé explicite avec des fichiers d'ancres de confiance. La clé intégrée est désactivée dès qu'au moins une clé d'ancre de confiance pour le domaine racine est définie dans les fichiers d'ancres de confiance.

Il est généralement recommandé d'encoder les ancres de confiance dans les enregistrements de ressources DS, plutôt que dans les enregistrements de ressources DNSKEY.

Si une ancre de confiance spécifiée via un enregistrement DS est trouvée révoquée, elle est automatiquement supprimée de la base de données des ancres de confiance pour la durée d'exécution. Voir RFC 5011[5] pour les détails sur les ancres de confiance révoquées. Notez que systemd-resolved ne mettra pas à jour automatiquement sa base de données d'ancres de confiance à partir des serveurs DNS. Il est plutôt recommandé de mettre à jour le logiciel résolveur ou de mettre à jour la nouvelle ancre de confiance en l'ajoutant dans de nouveaux fichiers d'ancres de confiance.

L'ancre de confiance DNSSEC actuelle pour le domaine racine d'Internet est disponible sur la page IANA Trust Anchor and Keys[6].

ANCres de confiance NEGATIVES

Les ancres de confiance négatives définissent les domaines pour lesquels la validation DNSSEC doit être désactivée. Les fichiers d'ancres de confiance négatives se trouvent au même endroit que les fichiers d'ancres de confiance positives et suivent les mêmes règles de substitution. Ce sont des fichiers texte avec le suffixe .negative. Les lignes vides et les lignes dont le premier caractère est « ; » sont ignorées. Chaque ligne spécifie un nom de domaine qui est la racine d'un sous-arbre DNS où la validation doit être désactivée. Par exemple :

# Reverse IPv4 mappings
10.in-addr.arpa
16.172.in-addr.arpa
168.192.in-addr.arpa
...
# Some custom domains
prod
stag

Les ancres de confiance négatives sont utiles pour prendre en charge les sous-arbres DNS privés qui ne sont pas référencés depuis la hiérarchie DNS Internet et qui ne sont pas signés.

Voir RFC 7646[7] pour les détails sur les ancres de confiance négatives.

Si aucun fichier d'ancres de confiance négatives n'est configuré, un ensemble intégré de domaines de zone DNS privés bien connus est utilisé comme ancres de confiance négatives.

Il est également possible de définir des ancres de confiance négatives par interface en utilisant le paramètre DNSSECNegativeTrustAnchors= dans les fichiers systemd.network(5).

NOM

systemd.negative — Ancrages de confiance négatifs pour systemd-cryptenroll

SYNOPSIS

/etc/systemd/system-cryptenroll/ USERNAME.negative
/usr/local/etc/systemd/system-cryptenroll/ USERNAME.negative
/etc/systemd/system-cryptenroll/HOST.negative
/usr/local/etc/systemd/system-cryptenroll/HOST.negative

DESCRIPTION

Le fichier .negative est utilisé par systemd-cryptenroll(1) pour spécifier les certificats X.509 qui ne doivent pas être utilisés pour déverrouiller un disque chiffré à l'aide de la technologie TPM2. Les ancrages de confiance négatifs sont enregistrés dans la zone de configuration du TPM2, de la même manière que les ancrages de confiance positifs définis dans systemd.positive(5).

Pour chaque utilisateur ou hôte, un fichier .negative peut être créé. Ce fichier contient une liste de certificats, chacun identifié par son empreinte numérique de hachage SHA-256. Si un certificat présenté par le client ne correspond à aucun des ancrages de confiance positifs mais correspond à un ancrage de confiance négatif, il est rejeté.

La structure du fichier est la suivante :

#
# Ligne de commentaires, ignorée.
#
SHA256=HASH
SHA256=HASH
...

Chaque ligne commençant par SHA256= doit être suivie d'une empreinte numérique de hachage SHA-256 d'un certificat, représentée sous forme de 64 caractères hexadécimaux. Des espaces blancs autour de la valeur du hachage sont ignorés.

POINTS DE CONFIANCE POSITIFS

Pour pouvoir utiliser un certificat comme ancrage de confiance négatif, il doit d'abord être enregistré comme ancrage de confiance positif. Voir systemd.positive(5) pour plus de détails.

POINTS DE CONFIANCE NÉGATIFS

Les ancrages de confiance négatifs sont utilisés pour bloquer des certificats spécifiques. Ceci est utile dans les scénarios où un certificat a été compromis ou n'est plus valide, mais qu'il serait trop complexe de le révoquer complètement du système. En ajoutant le certificat compromis à la liste des ancrages de confiance négatifs, on s'assure qu'il ne sera plus jamais accepté pour déverrouiller le disque, même s'il existe toujours comme ancrage de confiance positif.

VOIR AUSSI

systemd-cryptenroll(1), systemd.positive(5), systemd.cert(5)

NOTES

Les fichiers d'ancrage de confiance négatifs sont gérés par systemd-cryptenroll. Les modifications apportées à ces fichiers ne seront prises en compte qu'après avoir exécuté systemd-cryptenroll --wipe-slot=SLOT pour réenregistrer les ancrages de confiance dans le TPM2.
