NOM

systemd.socket - Configuration d'unité de socket

SYNOPSIS

socket.socket

DESCRIPTION

Un fichier de configuration d'unité dont le nom se termine par ".socket" encode des informations sur un socket IPC ou réseau ou un FIFO de système de fichiers contrôlé et supervisé par systemd, pour l'activation basée sur les sockets.

Cette page de manuel liste les options de configuration spécifiques à ce type d'unité. Voir systemd.unit(5) pour les options communes à tous les fichiers de configuration d'unité. Les éléments de configuration communs sont configurés dans les sections génériques [Unit] et [Install]. Les options de configuration spécifiques au socket sont configurées dans la section [Socket].

Des options supplémentaires sont listées dans systemd.exec(5), qui définissent l'environnement d'exécution dans lequel les commandes ExecStartPre=, ExecStartPost=, ExecStopPre= et ExecStopPost= sont exécutées, et dans systemd.kill(5), qui définissent la manière dont les processus sont terminés, et dans systemd.resource-control(5), qui configurent les paramètres de contrôle des ressources pour les processus du socket.

Pour chaque unité de socket, une unité de service correspondante doit exister, décrivant le service à démarrer en cas de trafic entrant sur le socket (voir systemd.service(5) pour plus d'informations sur les unités .service). Le nom de l'unité .service est par défaut le même que celui de l'unité .socket, mais peut être modifié avec l'option Service= décrite ci-dessous. Selon le réglage de l'option Accept= décrite ci-dessous, cette unité .service doit soit avoir un nom comme l'unité .socket, mais avec le suffixe remplacé, sauf si cela est écrasé par Service=; soit elle doit être une unité modèle nommée de la même manière. Exemple : un fichier socket foo.socket nécessite un service correspondant foo.service si Accept=no est défini. Si Accept=yes est défini, un modèle de service foo@.service doit exister à partir duquel les services sont instanciés pour chaque connexion entrante.

Aucune dépendance implicite WantedBy= ou RequiredBy= du socket vers le service n'est ajoutée. Cela signifie que le service peut être démarré sans le socket, auquel cas il doit être capable d'ouvrir des sockets par lui-même. Pour éviter cela, une dépendance explicite Requires= peut être ajoutée.

Les unités de socket peuvent être utilisées pour implémenter le démarrage à la demande des services, ainsi que le démarrage parallélisé des services. Voir les articles de blog liés à la fin pour une introduction.

Notez que le logiciel démon configuré pour l'activation par socket avec des unités de socket doit être capable d'accepter les sockets de systemd, soit via l'interface native de passage de sockets de systemd (voir sd_listen_fds(3) pour les détails du protocole précis utilisé et l'ordre dans lequel les descripteurs de fichiers sont passés) soit via le passage de sockets de style inetd(8) traditionnel (c'est-à-dire les sockets passés via l'entrée et la sortie standard, en utilisant StandardInput=socket dans le fichier de service).

Tous les sockets réseau alloués via les unités .socket sont alloués dans l'espace de noms réseau de l'hôte (voir network_namespaces(7)). Cela ne signifie toutefois pas que le service activé par une unité de socket configurée doit également faire partie de l'espace de noms réseau de l'hôte. Il est pris en charge et même recommandé d'exécuter les services dans leur propre espace de noms réseau (par exemple via PrivateNetwork=, voir systemd.exec(5)), ne recevant que les sockets configurés via l'activation par socket depuis l'espace de noms de l'hôte. Dans une telle configuration, la communication au sein de l'espace de noms réseau de l'hôte n'est autorisée que via les sockets d'activation passés, tandis que tous les sockets alloués à partir du code de service seront associés au propre espace de noms du service, et donc potentiellement soumis à une configuration restrictive.

DEPENDANCES IMPLICITES

Dépendances Implicites

Les dépendances suivantes sont ajoutées implicitement :

•Les unités de socket obtiennent automatiquement une dépendance Before= sur les unités de service qu'elles activent.
•Les unités de socket faisant référence à des chemins du système de fichiers (comme les sockets AF_UNIX ou les FIFOs) obtiennent implicitement des dépendances Requires= et After= sur toutes les unités de montage nécessaires pour accéder à ces chemins.
•Les unités de socket utilisant le réglage BindToDevice= obtiennent automatiquement une dépendance BindsTo= et After= sur l'unité de périphérique qui encapsule l'interface réseau spécifiée.

Des dépendances implicites supplémentaires peuvent être ajoutées suite aux paramètres d'exécution et de contrôle des ressources, tels que documentés dans systemd.exec(5) et systemd.resource-control(5).

Dépendances par Défaut

Les dépendances suivantes sont ajoutées sauf si DefaultDependencies=no est défini :

•Les unités de socket obtiennent automatiquement une dépendance Before= sur sockets.target.
•Les unités de socket obtiennent automatiquement une paire de dépendances After= et Requires= sur sysinit.target, et une paire de dépendances Before= et Conflicts= sur shutdown.target. Ces dépendances garantissent que l'unité de socket est démarrée avant les services normaux au démarrage, et est arrêtée à l'extinction. Seuls les sockets impliqués dans le démarrage précoce ou l'arrêt tardif du système devraient désactiver l'option DefaultDependencies=.

OPTIONS

Les fichiers d'unité de socket peuvent inclure les sections [Unit] et [Install], qui sont décrites dans systemd.unit(5).

Les fichiers d'unité de socket doivent inclure une section [Socket], qui contient des informations sur le socket ou le FIFO qu'elle supervise. Un certain nombre d'options pouvant être utilisées dans cette section sont partagées avec d'autres types d'unités. Ces options sont documentées dans systemd.exec(5), systemd.kill(5) et systemd.resource-control(5). Les options spécifiques à la section [Socket] des unités de socket sont les suivantes :

ListenStream=, ListenDatagram=, ListenSequentialPacket=

Spécifie une adresse sur laquelle écouter pour un socket de flux (SOCK_STREAM), de datagramme (SOCK_DGRAM), ou de paquet séquentiel (SOCK_SEQPACKET), respectivement. L'adresse peut être écrite dans divers formats :

Si l'adresse commence par une barre oblique ("/"), elle est lue comme un socket de système de fichiers dans la famille de sockets AF_UNIX.

Si l'adresse commence par un symbole @ ("@"), elle est lue comme un socket de l'espace de noms abstrait dans la famille AF_UNIX. Le "@" est remplacé par un caractère NUL avant la liaison. Pour plus de détails, voir unix(7).

Si la chaîne d'adresse est un seul nombre, elle est lue comme un numéro de port sur lequel écouter via IPv6. Selon la valeur de BindIPv6Only= (voir ci-dessous) cela peut entraîner la disponibilité du service via IPv6 et IPv4 (par défaut) ou uniquement via IPv6.

Si la chaîne d'adresse est une chaîne au format "v.w.x.y:z", elle est interprétée comme l'adresse IPv4 v.w.x.y et le port z.

Si la chaîne d'adresse est une chaîne au format "[x]:y", elle est interprétée comme l'adresse IPv6 x et le port y. Une portée d'interface optionnelle (nom d'interface ou numéro) peut être spécifiée après un symbole "%" : "[x]:y%dev". Les portées d'interface ne sont utiles qu'avec les adresses locales de liaison, car le noyau les ignore dans les autres cas. Notez que si une adresse est spécifiée comme IPv6, elle peut toujours rendre le service disponible via IPv4 également, en fonction du réglage BindIPv6Only= (voir ci-dessous).

Si la chaîne d'adresse est une chaîne au format "vsock:x:y", elle est lue comme un CID x sur un port y dans la famille AF_VSOCK. Le CID est un identifiant entier de 32 bits unique dans AF_VSOCK, analogue à une adresse IP. La spécification du CID est facultative et peut être laissée vide. "vsock" peut être remplacé par "vsock-stream", "vsock-dgram" ou "vsock-seqpacket" pour forcer l'utilisation du type de socket correspondant.

Notez que SOCK_SEQPACKET (c'est-à-dire ListenSequentialPacket=) n'est disponible que pour les sockets AF_UNIX. SOCK_STREAM (c'est-à-dire ListenStream=) lorsqu'il est utilisé pour les sockets IP fait référence aux sockets TCP, SOCK_DGRAM (c'est-à-dire ListenDatagram=) aux sockets UDP.

Ces options peuvent être spécifiées plus d'une fois, auquel cas le trafic entrant sur n'importe lequel des sockets déclenchera l'activation du service, et tous les sockets listés seront passés au service, qu'il y ait du trafic entrant sur eux ou non. Si la chaîne vide est assignée à l'une de ces options, la liste des adresses sur lesquelles écouter est réinitialisée, toutes les utilisations antérieures de ces options n'auront aucun effet.

Il est également possible d'avoir plusieurs unités de sockets pour le même service en utilisant Service=, et le service recevra tous les sockets configurés dans toutes les unités de sockets. Les sockets configurés dans une unité sont passés dans l'ordre de configuration, mais aucun ordre entre les unités de sockets n'est spécifié.

Si une adresse IP est utilisée ici, il est souvent souhaitable d'écouter sur cette adresse avant que l'interface sur laquelle elle est configurée ne soit opérationnelle, et même indépendamment du fait qu'elle le sera ou non. Pour gérer cela, il est recommandé de définir l'option FreeBind= décrite ci-dessous.

ListenFIFO=

Spécifie un FIFO du système de fichiers (voir fifo(7) pour les détails) sur lequel écouter. Ceci attend un chemin de fichier absolu comme argument. Le comportement est par ailleurs très similaire à la directive ListenDatagram= ci-dessus.

ListenSpecial=

Spécifie un fichier spécial dans le système de fichiers sur lequel écouter. Ceci attend un chemin de fichier absolu comme argument. Le comportement est par ailleurs très similaire à la directive ListenFIFO= ci-dessus. Utilisez ceci pour ouvrir des nœuds de périphériques caractères ainsi que des fichiers spéciaux dans /proc/ et /sys/.

ListenNetlink=

Spécifie une famille Netlink pour créer un socket et écouter dessus. Ceci attend une courte chaîne faisant référence au nom de la famille AF_NETLINK (comme audit ou kobject-uevent) comme argument, éventuellement suffixée par un espace suivi d'un entier de groupe multicast. Le comportement est par ailleurs très similaire à la directive ListenDatagram= ci-dessus.

ListenMessageQueue=

Spécifie un nom de file d'attente de messages POSIX sur lequel écouter (voir mq_overview(7) pour les détails). Ceci attend un nom de file d'attente de messages valide (c'est-à-dire commençant par "/"). Le comportement est par ailleurs très similaire à la directive ListenFIFO= ci-dessus. Sous Linux, les descripteurs de files d'attente de messages sont en fait des descripteurs de fichiers et peuvent être hérités entre processus.

ListenUSBFunction=

Spécifie un emplacement de points d'extrémité USB FunctionFS[1] sur lequel écouter, pour l'implémentation de fonctions gadget USB. Ceci attend un chemin de fichier absolu d'un point de montage FunctionFS comme argument. Le comportement est par ailleurs très similaire à la directive ListenFIFO= ci-dessus. Utilisez ceci pour ouvrir le point d'extrémité FunctionFS ep0. Lors de l'utilisation de cette option, le service activé doit avoir les options USBFunctionDescriptors= et USBFunctionStrings= définies.

Ajouté dans la version 227.

SocketProtocol=

Prend l'une des valeurs udplite, sctp ou mptcp. Le socket utilisera respectivement le protocole UDP-Lite (IPPROTO_UDPLITE), SCTP (IPPROTO_SCTP) ou MPTCP (IPPROTO_MPTCP).

Ajouté dans la version 229.

BindIPv6Only=

Prend l'une des valeurs default, both ou ipv6-only. Contrôle l'option de socket IPV6_V6ONLY (voir ipv6(7) pour les détails). Si both, les sockets IPv6 liés seront accessibles via IPv4 et IPv6. S'ils sont ipv6-only, ils ne seront accessibles que via IPv6. Si default (ce qui est la valeur par défaut, surprise !), le paramètre système global est utilisé, tel que contrôlé par /proc/sys/net/ipv6/bindv6only, qui par défaut est équivalent à both.

Backlog=

Prend un argument entier non signé 32 bits. Spécifie le nombre de connexions à mettre en file d'attente qui n'ont pas encore été acceptées. Ce paramètre n'est pertinent que pour les sockets de flux et de paquets séquentiels. Voir listen(2) pour les détails. La valeur par défaut est 4294967295. Notez que cette valeur est silencieusement plafonnée par le ctl sys "net.core.somaxconn", qui est généralement fixé à 4096, donc généralement le ctl sys est le paramètre qui compte réellement.

BindToDevice=

Spécifie le nom d'une interface réseau à laquelle lier ce socket. Si défini, le trafic ne sera accepté que depuis les interfaces réseau spécifiées. Ceci contrôle l'option de socket SO_BINDTODEVICE (voir socket(7) pour les détails). Si ce paramètre est utilisé, une dépendance implicite de cette unité de socket sur l'unité de périphérique d'interface réseau est créée (voir systemd.device(5)). Notez que la définition de ce paramètre peut entraîner l'ajout de dépendances supplémentaires à l'unité (voir ci-dessus).

SocketUser=, SocketGroup=

Prend un nom d'utilisateur/groupe UNIX. Si spécifié, tous les sockets AF_UNIX, les nœuds FIFO et les files d'attente de messages appartiennent à l'utilisateur et au groupe spécifiés. S'il n'est pas défini (par défaut), les nœuds appartiennent à l'utilisateur/groupe root (s'il est exécuté dans un contexte système) ou à l'utilisateur/groupe appelant (s'il est exécuté dans un contexte utilisateur). Si seul un utilisateur est spécifié mais aucun groupe, alors le groupe est dérivé du groupe par défaut de l'utilisateur.

Ajouté dans la version 214.

SocketMode=

Si vous écoutez sur un socket de système de fichiers, un FIFO, ou une file d'attente de messages, cette option spécifie le mode d'accès au système de fichiers utilisé lors de la création du nœud de fichier. Prend un mode d'accès en notation octale. La valeur par défaut est 0666.

DirectoryMode=

Si vous écoutez sur un socket de système de fichiers ou un FIFO, les répertoires parents sont automatiquement créés si nécessaire. Cette option spécifie le mode d'accès au système de fichiers utilisé lors de la création de ces répertoires. Prend un mode d'accès en notation octale. La valeur par défaut est 0755.

Accept=

Prend un argument booléen. Si oui, une instance de service est lancée pour chaque connexion entrante et seul le socket de connexion lui est passé. Si non, tous les sockets d'écoute eux-mêmes sont passés à l'unité de service démarrée, et une seule unité de service est lancée pour toutes les connexions (voir aussi ci-dessus). Cette valeur est ignorée pour les sockets datagrammes et les FIFOs où une seule unité de service gère inconditionnellement tout le trafic entrant. La valeur par défaut est no.

Généralement, pour les services sensibles aux performances, le choix de Accept=no est préférable, car ainsi seule la première connexion devra supporter le coût de la ressource d'activation. D'un autre côté, pour les services utilisés sporadiquement, Accept=yes peut être préférable car il simplifie l'implémentation (le code du programme de service n'ayant qu'à traiter une seule connexion au lieu de plusieurs) et permet une sécurité renforcée (car les diverses options de sandboxing peuvent être utilisées pour isoler les connexions parallèles les unes des autres, chacune étant traitée par une instance de service et un processus séparés).

Un service écoutant sur un socket AF_UNIX peut, mais n'est pas obligé de, appeler close(2) sur le socket reçu avant de se terminer. Cependant, il ne doit pas désunir (unlink) le socket du système de fichiers. Il ne doit pas invoquer shutdown(2) sur les sockets qu'il a reçus avec Accept=no, mais il peut le faire pour les sockets qu'il a reçus avec Accept=yes défini.

Définir Accept=yes est particulièrement utile pour permettre aux démons conçus pour être utilisés avec inetd(8) de fonctionner sans modification avec l'activation par socket de systemd.

Notez que selon ce paramètre, les services activés par les unités de ce type sont soit des services réguliers (dans le cas de Accept=no) soit des instances de services templatisés (dans le cas de Accept=yes). Voir la section Description ci-dessus pour une discussion plus détaillée des règles de nommage des services déclenchés.

Pour les connexions IPv4 et IPv6, la variable d'environnement $REMOTE_ADDR contiendra l'adresse IP distante, et $REMOTE_PORT contiendra le numéro de port distant. Ces deux variables correspondent à celles définies par l'interface CGI pour les services web (voir RFC 3875[2]).

Pour les connexions de socket AF_UNIX, la variable d'environnement $REMOTE_ADDR contiendra soit le chemin du système de fichiers du socket distant commençant par un slash ("/"), soit son adresse dans l'espace abstrait commençant par un symbole at ("@"). Si le socket n'est pas nommé, $REMOTE_ADDR ne sera pas défini.

Si Accept=yes est utilisé, le processus de service activé aura défini la variable d'environnement $SO_COOKIE sur le cookie du socket Linux, formaté en entier décimal. Le cookie du socket peut par ailleurs être obtenu via getsockopt(7).

Il est recommandé de définir CollectMode=inactive-or-failed pour les instances de service activées via Accept=yes, afin de garantir que les services de connexion échoués soient nettoyés et libérés de la mémoire, et ne s'accumulent pas.

Writable=

Prend un argument booléen. Ne peut être utilisé qu'en conjonction avec ListenSpecial=. Si vrai, le fichier spécial spécifié est ouvert en mode lecture-écriture, si faux, en mode lecture seule. La valeur par défaut est faux.

Ajouté dans la version 227.

FlushPending=

Prend un argument booléen. Ne peut être utilisé que lorsque Accept=no. Si oui, les tampons du socket sont vidés après la sortie du service déclenché. Cela provoque la vidange de toutes les données en attente et le rejet de toutes les connexions entrantes en attente. Si non, les tampons du socket ne seront pas vidés, permettant au service de gérer les connexions en attente après le redémarrage, ce qui est le comportement généralement attendu. La valeur par défaut est no.

Ajouté dans la version 247.

MaxConnections=

Le nombre maximum d'instances de services à exécuter simultanément, lorsque Accept=yes est défini. Si des connexions concurrentes supplémentaires arrivent, elles seront refusées jusqu'à ce qu'au moins une connexion existante soit terminée. Ce paramètre n'a aucun effet sur les sockets configurés avec Accept=no ou les sockets datagrammes. La valeur par défaut est 64.

MaxConnectionsPerSource=

Le nombre maximum de connexions pour un service par adresse IP source (en cas d'IPv4/IPv6), par CID source (en cas d'AF_VSOCK), ou par UID source (en cas d'AF_UNIX). Ceci est très similaire à la directive MaxConnections= ci-dessus. La valeur par défaut est 0, c'est-à-dire désactivé.

Ajouté dans la version 232.

KeepAlive=

Prend un argument booléen. Si vrai, la pile TCP/IP enverra un message keep alive après 2h (selon la configuration de /proc/sys/net/ipv4/tcp_keepalive_time) pour tous les flux TCP acceptés sur cette socket. Ceci contrôle l'option de socket SO_KEEPALIVE (voir socket(7) et le TCP Keepalive HOWTO[3] pour plus de détails.) La valeur par défaut est false.

KeepAliveTimeSec=

Prend une durée (en secondes) comme argument. La connexion doit rester inactive avant que TCP commence à envoyer des sondes keepalive. Ceci contrôle l'option de socket TCP_KEEPIDLE (voir socket(7) et le TCP Keepalive HOWTO[3] pour plus de détails.) La valeur par défaut est de 7200 secondes (2 heures).

Ajouté dans la version 216.

KeepAliveIntervalSec=

Prend une durée (en secondes) comme argument entre chaque sonde keepalive, si l'option de socket SO_KEEPALIVE a été définie sur cette socket. Ceci contrôle l'option de socket TCP_KEEPINTVL (voir socket(7) et le TCP Keepalive HOWTO[3] pour plus de détails.) La valeur par défaut est de 75 secondes.

Ajouté dans la version 216.

KeepAliveProbes=

Prend un entier comme argument. C'est le nombre de sondes non acquittées à envoyer avant de considérer la connexion comme morte et de notifier la couche application. Ceci contrôle l'option de socket TCP_KEEPCNT (voir socket(7) et le TCP Keepalive HOWTO[3] pour plus de détails.) La valeur par défaut est de 9.

Ajouté dans la version 216.

NoDelay=

Prend un argument booléen. L'algorithme de Nagle de TCP fonctionne en combinant un certain nombre de petits messages sortants, et en les envoyant tous en une fois. Ceci contrôle l'option de socket TCP_NODELAY (voir tcp(7)). La valeur par défaut est false.

Ajouté dans la version 216.

Priority=

Prend un argument entier contrôlant la priorité pour tout le trafic envoyé depuis cette socket. Ceci contrôle l'option de socket SO_PRIORITY (voir socket(7) pour plus de détails.).

DeferAcceptSec=

Prend une durée (en secondes) comme argument. Si défini, le processus d'écoute ne sera réveillé que lorsque des données arriveront sur la socket, et non immédiatement lors de l'établissement de la connexion. Lorsque cette option est définie, l'option de socket TCP_DEFER_ACCEPT sera utilisée (voir tcp(7)), et le noyau ignorera les paquets ACK initiaux sans données. L'argument spécifie la durée approximative pendant laquelle le noyau doit attendre les données entrantes avant de revenir au comportement normal d'acceptation des paquets ACK vides. Cette option est bénéfique pour les protocoles où le client envoie d'abord les données (par exemple, HTTP, contrairement à SMTP), car le processus serveur ne sera pas réveillé inutilement avant de pouvoir agir.

Si le client utilise également l'option TCP_DEFER_ACCEPT, la latence de la connexion initiale peut être réduite, car le noyau enverra des données dans le dernier paquet établissant la connexion (le troisième paquet de la "poignée de main en trois étapes").

Désactivé par défaut.

Ajouté dans la version 216.

ReceiveBuffer=, SendBuffer=

Prend un argument entier contrôlant respectivement la taille des tampons de réception ou d'envoi de cette socket. Ceci contrôle les options de socket SO_RCVBUF et SO_SNDBUF (voir socket(7) pour plus de détails.). Les suffixes habituels K, M, G sont supportés et sont interprétés à la base de 1024.

IPTOS=

Prend un argument entier contrôlant le champ Type de Service IP pour les paquets générés à partir de cette socket. Ceci contrôle l'option de socket IP_TOS (voir ip(7) pour plus de détails.). Une chaîne numérique ou l'une des valeurs low-delay, throughput, reliability ou low-cost peut être spécifiée.

IPTTL=

Prend un argument entier contrôlant le champ Durée de Vie IPv4 / Nombre de sauts IPv6 pour les paquets générés à partir de cette socket. Ceci définit les options de socket IP_TTL/IPV6_UNICAST_HOPS (voir ip(7) et ipv6(7) pour plus de détails.)

Mark=

Prend une valeur entière. Contrôle la marque du pare-feu des paquets générés par cette socket. Ceci peut être utilisé dans la logique du pare-feu pour filtrer les paquets provenant de cette socket. Ceci définit l'option de socket SO_MARK. Voir iptables(8) pour plus de détails.

ReusePort=

Prend une valeur booléenne. Si vrai, permet plusieurs bind(2) sur ce port TCP ou UDP. Ceci contrôle l'option de socket SO_REUSEPORT. Voir socket(7) pour plus de détails.

Ajouté dans la version 206.

SmackLabel=, SmackLabelIPIn=, SmackLabelIPOut=

Prend une valeur chaîne de caractères. Contrôle les attributs étendus "security.SMACK64", "security.SMACK64IPIN" et "security.SMACK64IPOUT", respectivement, c'est-à-dire l'étiquette de sécurité du FIFO, ou l'étiquette de sécurité pour les connexions entrantes ou sortantes de la socket, respectivement. Voir Smack[4] pour plus de détails.

Ajouté dans la version 196.

SELinuxContextFromNet=

Prend un argument booléen. Lorsque vrai, systemd tentera de déduire l'étiquette SELinux utilisée pour le service instancié à partir des informations transmises par le pair sur le réseau. Notez que seul le niveau de sécurité est utilisé parmi les informations fournies par le pair. Les autres parties du contexte SELinux résultant proviennent soit du binaire cible qui est effectivement déclenché par l'unité socket, soit de la valeur de l'option SELinuxContext=. Cette option de configuration ne s'applique que lorsqu'un service activé est passé via un descripteur de fichier socket unique, c'est-à-dire les instances de service dont l'entrée standard est connectée à une socket ou les services déclenchés par exactement une unité socket. Notez également que cette option n'est utile que lorsque la politique SELinux MLS/MCS est déployée. La valeur par défaut est "false".

Ajouté dans la version 217.

PipeSize=

Prend une taille en octets. Contrôle la taille du tampon de pipe des FIFOs configurés dans cette unité socket. Voir fcntl(2) pour plus de détails. Les suffixes habituels K, M, G sont supportés et sont interprétés à la base de 1024.

MessageQueueMaxMessages=, MessageQueueMessageSize=

Ces deux paramètres prennent des valeurs entières et contrôlent respectivement le champ mq_maxmsg ou le champ mq_msgsize, lors de la création de la file d'attente de messages. Notez que soit aucun, soit les deux de ces variables doivent être définis. Voir mq_setattr(3) pour plus de détails.

FreeBind=

Prend une valeur booléenne. Contrôle si la socket peut être liée à des adresses IP non locales. Ceci est utile pour configurer des sockets écoutant sur des adresses IP spécifiques avant que ces adresses IP ne soient correctement configurées sur une interface réseau. Ceci définit l'option de socket IP_FREEBIND/IPV6_FREEBIND. Pour des raisons de robustesse, il est recommandé d'utiliser cette option chaque fois que vous liez une socket à une adresse IP spécifique. La valeur par défaut est false.

Transparent=

Prend une valeur booléenne. Contrôle l'option de socket IP_TRANSPARENT/IPV6_TRANSPARENT. La valeur par défaut est false.

Broadcast=

Prend une valeur booléenne. Ceci contrôle l'option de socket SO_BROADCAST, qui permet d'envoyer des datagrammes de diffusion depuis cette socket. La valeur par défaut est false.

PassCredentials=

Prend une valeur booléenne. Ceci contrôle l'option de socket SO_PASSCRED, qui permet aux sockets AF_UNIX de recevoir les identifiants du processus d'envoi dans un message annexe. La valeur par défaut est false.

PassPIDFD=

Prend une valeur booléenne. Ceci contrôle l'option de socket SO_PASSPIDFD, qui permet aux sockets AF_UNIX de recevoir le pidfd du processus d'envoi dans un message annexe. La valeur par défaut est false.

Ajouté dans la version 258.

PassSecurity=

Prend une valeur booléenne. Ceci contrôle l'option de socket SO_PASSSEC, qui permet aux sockets AF_UNIX de recevoir le contexte de sécurité du processus d'envoi dans un message annexe. La valeur par défaut est false.

PassPacketInfo=

Prend une valeur booléenne. Ceci contrôle les options IP_PKTINFO, IPV6_RECVPKTINFO, NETLINK_PKTINFO ou PACKET_AUXDATA, qui permettent la réception de métadonnées supplémentaires par paquet sous forme de message annexe, sur les sockets AF_INET, AF_INET6, AF_UNIX et AF_PACKET. La valeur par défaut est false.

Ajouté dans la version 246.

AcceptFileDescriptors=

Prend une valeur booléenne. Ceci contrôle l'option de socket SO_PASSRIGHTS, qui lorsqu'elle est désactivée, interdit au pair d'envoyer des messages annexes SCM_RIGHTS (aussi appelés descripteurs de fichiers) via les sockets AF_UNIX. La valeur par défaut est true.

Ajouté dans la version 258.

Timestamping=

Prend l'une des valeurs "off", "us" (alias : "usec", "μs") ou "ns" (alias : "nsec"). Ceci contrôle les options de socket SO_TIMESTAMP ou SO_TIMESTAMPNS, et détermine si le trafic réseau entrant doit porter des métadonnées d'horodatage. La valeur par défaut est off.

Ajouté dans la version 247.

TCPCongestion=

Prend une valeur chaîne. Contrôle l'algorithme de congestion TCP utilisé par cette socket. Devrait être l'un des algorithmes "westwood", "reno", "cubic", "lp" ou tout autre algorithme disponible supporté par la pile IP. Ce réglage ne s'applique qu'aux sockets de flux.

ExecStartPre=, ExecStartPost=

Prend une ou plusieurs lignes de commande, qui sont exécutées avant ou après la création et la liaison des sockets/FIFOs d'écoute, respectivement. Le premier jeton de la ligne de commande doit être un nom de fichier absolu, suivi des arguments du processus. Plusieurs lignes de commande peuvent être spécifiées en suivant le même schéma que celui utilisé pour ExecStartPre= des fichiers d'unité de service.

ExecStopPre=, ExecStopPost=

Commandes supplémentaires qui sont exécutées avant ou après la fermeture et la suppression des sockets/FIFOs d'écoute, respectivement. Plusieurs lignes de commande peuvent être spécifiées en suivant le même schéma que celui utilisé pour ExecStartPre= des fichiers d'unité de service.

TimeoutSec=

Configure le temps d'attente pour que les commandes spécifiées dans ExecStartPre=, ExecStartPost=, ExecStopPre= et ExecStopPost= se terminent. Si une commande ne se termine pas dans le délai configuré, la socket sera considérée comme défaillante et sera à nouveau arrêtée. Toutes les commandes encore en cours seront terminées de force via SIGTERM, et après un nouveau délai de cette durée avec SIGKILL. (Voir KillMode= en systemd.kill(5).) Prend une valeur sans unité en secondes, ou une période de temps telle que « 5min 20s ». Passer « 0 » pour désactiver la logique de délai d'expiration. Par défaut, utilise la valeur de DefaultTimeoutStartSec= du fichier de configuration du gestionnaire (voir systemd-system.conf(5)).

Service=

Spécifie le nom de l'unité de service à activer lors de la réception de trafic. Ce paramètre n'est autorisé que pour les sockets avec Accept=no. Il prend par défaut le service portant le même nom que le socket (avec le suffixe remplacé). Dans la plupart des cas, il ne devrait pas être nécessaire d'utiliser cette option. Notez que la définition de ce paramètre pourrait entraîner l'ajout de dépendances supplémentaires à l'unité (voir ci-dessus).

RemoveOnStop=

Prend un argument booléen. S'il est activé, les nœuds de fichier créés par cette unité de socket sont supprimés lorsqu'elle est arrêtée. Ceci s'applique aux sockets AF_UNIX dans le système de fichiers, aux files d'attente de messages POSIX, aux FIFO, ainsi qu'à tout lien symbolique les concernant configuré avec Symlinks=. Normalement, il ne devrait pas être nécessaire d'utiliser cette option, et elle n'est pas recommandée car les services pourraient continuer à fonctionner après la terminaison de l'unité de socket et il devrait toujours être possible de communiquer avec eux via leur nœud de système de fichiers. Par défaut, elle est désactivée.

Ajouté dans la version 214.

Symlinks=

Prend une liste de chemins de système de fichiers. Les chemins spécifiés seront créés en tant que liens symboliques vers le chemin du socket AF_UNIX ou le chemin FIFO de cette unité de socket. Si ce paramètre est utilisé, un seul socket AF_UNIX dans le système de fichiers ou un seul FIFO peut être configuré pour l'unité de socket. Utilisez cette option pour gérer un ou plusieurs noms d'alias sous forme de liens symboliques pour un socket, en liant leur cycle de vie. Notez que si la création d'un lien symbolique échoue, cela n'est pas considéré comme fatal pour l'unité de socket, et l'unité de socket peut toujours démarrer. Si une chaîne vide est attribuée, la liste des chemins est réinitialisée. Par défaut, une chaîne vide.

Ajouté dans la version 214.

FileDescriptorName=

Attribue un nom à tous les descripteurs de fichier que cette unité de socket encapsule. Ceci est utile pour aider les services activés à identifier des descripteurs de fichier spécifiques, si plusieurs descripteurs de fichier sont passés. Les services peuvent utiliser l'appel sd_listen_fds_with_names(3) pour acquérir les noms configurés pour les descripteurs de fichier reçus. Les noms peuvent contenir tout caractère ASCII, mais doivent exclure les caractères de contrôle et « : », et doivent avoir une longueur maximale de 255 caractères. Si ce paramètre n'est pas utilisé, le nom du descripteur de fichier prend par défaut le nom de l'unité de socket (y compris son suffixe .socket) lorsque Accept=no, « connection » sinon.

Ajouté dans la version 227.

TriggerLimitIntervalSec=, TriggerLimitBurst=

Configure une limite sur la fréquence à laquelle cette unité de socket peut être activée dans un intervalle de temps spécifique. Le paramètre TriggerLimitIntervalSec= peut être utilisé pour configurer la durée de l'intervalle de temps dans les unités de temps habituelles « us », « ms », « s », « min », « h », ... et prend par défaut 2s (voir systemd.time(7) pour les détails sur les diverses unités de temps comprises). Le paramètre TriggerLimitBurst= prend une valeur entière positive et spécifie le nombre d'activations permises par intervalle de temps, et prend par défaut 200 pour les sockets avec Accept=yes (permettant ainsi par défaut 200 activations par 2s), et 20 sinon (20 activations par 2s). Mettez l'un des deux à 0 pour désactiver toute forme de limitation du taux de déclenchement.

Si la limite est atteinte, l'unité de socket est placée en mode d'échec et ne sera plus connectable tant qu'elle n'aura pas été redémarrée. Notez que cette limite est appliquée avant que l'activation du service ne soit mise en file d'attente.

Comparez avec PollLimitIntervalSec=/PollLimitBurst= décrit ci-dessous, qui implémente un ralentissement temporaire si une unité de socket est inondée de trafic entrant, par opposition à l'état d'échec permanent résultant de TriggerLimitIntervalSec=/TriggerLimitBurst=.

Ajouté dans la version 230.

PollLimitIntervalSec=, PollLimitBurst=

Configure une limite sur la fréquence à laquelle les événements de polling sur les descripteurs de fichier qui soutiennent cette unité de socket seront considérés. Cette paire de paramètres est similaire à TriggerLimitIntervalSec=/TriggerLimitBurst= mais au lieu de placer une limite (fatale) sur la fréquence d'activation, elle place une limite (transitoire) sur la fréquence de polling. La syntaxe attendue des paramètres et la plage sont identiques à celles des options susmentionnées, et peuvent être désactivées de la même manière.

Si la limite de polling est atteinte, le polling est temporairement désactivé jusqu'à ce que la fenêtre de temps spécifiée soit écoulée. La limite de polling ralentit donc les tentatives de connexion si elle est atteinte, mais contrairement à la limite de déclenchement, elle ne provoquera pas d'échecs permanents. C'est le mécanisme recommandé pour traiter les tentatives de Déni de Service (DoS) par inondation de paquets.

La limite de polling est appliquée par descripteur de fichier à écouter, contrairement à la limite de déclenchement qui est appliquée à l'ensemble de l'unité de socket. Cette distinction est importante pour les unités de socket qui écoutent sur plusieurs descripteurs de fichier (c'est-à-dire qui ont plusieurs sections ListenXYZ=).

Ces paramètres prennent par défaut 150 (en cas de Accept=yes) et 15 (sinon) événements de polling par 2s. C'est considérablement moins que les valeurs par défaut pour la limite de déclenchement (voir ci-dessus), ce qui signifie que la limite de polling devrait généralement garantir que la limite de déclenchement n'est jamais atteinte, sauf si l'une d'elles est reconfigurée ou désactivée.

Ajouté dans la version 255.

DeferTrigger=

Prend un argument booléen, ou « patient ». Peut uniquement être utilisé lorsque Accept=no. S'il est activé, le mode de travail « lenient » (souple) au lieu de « replace » est utilisé lors du déclenchement du service, ce qui signifie que les unités en cours d'activation/exécution qui entrent en conflit avec le service ne seront pas dérangées/arrêtées. De plus, s'il existe un conflit, l'unité de socket attendra que la file d'attente des travaux en cours soit terminée et reportera potentiellement l'activation à ce moment-là. Une limite supérieure du temps total d'attente peut être configurée via DeferTriggerMaxSec=. S'il est défini sur yes, l'unité de socket échouera si tous les travaux sont terminés ou si le délai d'attente est atteint mais que le conflit persiste. Si défini sur patient, attendez toujours que DeferTriggerMaxSec= soit écoulé. Par défaut, désactivé.

Ce paramètre est particulièrement utile si l'unité de socket doit rester active lors des opérations de switch-root/soft-reboot pendant que le service déclenché est arrêté.

Ajouté dans la version 258.

DeferTriggerMaxSec=

Configure le temps maximum pour reporter le déclenchement lorsque DeferTrigger= est activé. Si le service ne peut pas être activé dans le temps spécifié, le socket sera considéré comme défaillant et sera terminé. Prend une valeur sans unité en secondes, ou une période de temps telle que « 5min 20s ». Passer « 0 » ou « infinity » pour désactiver la logique de délai d'expiration (par défaut).

Ajouté dans la version 258.

PassFileDescriptorsToExec=

Prend un argument booléen. Par défaut, désactivé. S'il est activé, les descripteurs de fichier créés par l'unité de socket sont passés aux commandes ExecStartPost=, ExecStopPre= et ExecStopPost= de l'unité de socket. Les descripteurs de fichier passés peuvent être accédés avec sd_listen_fds(3) comme si les commandes étaient invoquées depuis les unités de service associées. Notez que la commande ExecStartPre= ne peut pas accéder aux descripteurs de fichier du socket.

Ajouté dans la version 256.

Consultez systemd.unit(5), systemd.exec(5), et systemd.kill(5) pour plus de paramètres.
