NOM

sqlalchemy-continuum - Documentation de SQLAlchemy-Continuum

SQLAlchemy-Continuum est une extension de versionnement pour SQLAlchemy.

INTRODUCTION

Pourquoi ?

En tant que passionné de Python/SQLAlchemy, je voulais créer un outil de versionnement de base de données pour Python avec toutes les fonctionnalités d'Envers et avec une API aussi intuitive que papertrail. Je voulais aussi le rendre _rapide_ en gardant les choses aussi proches que possible de la base de données.

Fonctionnalités

  • Ne stocke pas les mises à jour qui ne changent rien
  • Prend en charge les migrations alembic
  • Peut restaurer les données des objets ainsi que toutes les relations d'objets à une transaction donnée, même si l'objet a été supprimé
  • Les transactions peuvent être interrogées ultérieurement en utilisant la syntaxe de requête SQLAlchemy
  • Interrogation des enregistrements modifiés dans une transaction donnée
  • Interrogation des versions d'une entité qui ont modifié une propriété donnée
  • Interrogation des transactions lors desquelles les entités d'une classe donnée ont été modifiées
  • Les modèles d'historique donnent accès aux relations des objets parents à tout moment

Installation

pip install SQLAlchemy-Continuum

Bases

Pour rendre vos modèles versionnés, vous avez besoin de deux choses :

1.
Appeler make_versioned() avant que vos modèles ne soient définis.
2.
Ajouter __versioned__ à tous les modèles pour lesquels vous souhaitez ajouter le versionnement
import sqlalchemy as sa
from sqlalchemy_continuum import make_versioned
make_versioned(user_cls=None)
class Article(Base):
    __versioned__ = {}
    __tablename__ = 'article'
    id = sa.Column(sa.Integer, primary_key=True, autoincrement=True)
    name = sa.Column(sa.Unicode(255))
    content = sa.Column(sa.UnicodeText)
# après avoir défini tous vos modèles, appelez configure_mappers :
sa.orm.configure_mappers()

Après cette configuration, SQLAlchemy-Continuum effectue les actions suivantes :

1.
Il crée un modèle ArticleHistory qui sert d'historique de versions pour le modèle Article
2.
Il crée des modèles TransactionLog et TransactionChanges pour le suivi de l'historique transactionnel
3.
Il ajoute quelques écouteurs pour que chaque insertion, mise à jour et suppression d'objet Article soit enregistrée

Lorsque les modèles ont été configurés, soit en appelant configure_mappers() soit en accédant à certains d'entre eux pour la première fois, les éléments suivants deviennent disponibles :

from sqlalchemy_continuum import version_class, parent_class
version_class(Article)  # Classe ArticleHistory
parent_class(version_class(Article))  # Classe Article

Versions et transactions

À la fin de chaque transaction, SQLAlchemy-Continuum rassemble toutes les modifications et crée des objets de version pour chaque entité versionnée modifiée. Continuum crée également une entité TransactionLog et N entités TransactionChanges par transaction (ici N est le nombre de classes affectées par transaction). Les entités TransactionLog et TransactionChanges sont créées pour le suivi transactionnel.

article = Article(name=u'Un article')
session.add(article)
session.commit()
article.versions[0].name == u'Un article'
article.name = u'Un article mis à jour'
session.commit()
article.versions[1].name == u'Un article mis à jour'

OBJETS DE VERSION

Types d'opérations

Lors de la modification des entités et de la validation des résultats dans la base de données, Continuum enregistre les opérations utilisées (INSERT, UPDATE ou DELETE) dans les entités de version. Les types d'opérations sont stockés par défaut dans un petit champ entier nommé 'operation_type'. La classe nommée 'Operation' contient des constantes pratiques pour ces valeurs, comme montré ci-dessous :

from sqlalchemy_continuum import Operation
article = Article(name=u'Un article')
session.add(article)
session.commit()
article.versions[0].operation_type == Operation.INSERT
article.name = u'Un article mis à jour'
session.commit()
article.versions[1].operation_type == Operation.UPDATE
session.delete(article)
session.commit()
article.versions[2].operation_type == Operation.DELETE

Parcours des versions

premiere_version = article.versions[0]
premiere_version.index
# 0
deuxieme_version = premiere_version.next
assert deuxieme_version == article.versions[1]
deuxieme_version.previous == premiere_version
# True
deuxieme_version.index
# 1

Ensemble de modifications

Continuum offre un moyen simple d'obtenir l'ensemble des modifications d'un objet de version donné. Chaque objet de version contient une propriété `changeset` qui contient un dictionnaire des champs modifiés dans cette version.

article = Article(name=u'Nouvel article', content=u'Du contenu')
session.add(article)
session.commit(article)
version = article.versions[0]
version.changeset
# {
#   'id': [None, 1],
#   'name': [None, u'Nouvel article'],
#   'content': [None, u'Du contenu']
# }
article.name = u'Article mis à jour'
session.commit()
version = article.versions[1]
version.changeset
# {
#   'name': [u'Nouvel article', u'Article mis à jour'],
# }
session.delete(article)
version = article.versions[2]
version.changeset
# {
#   'id': [1, None]
#   'name': [u'Article mis à jour', None],
#   'content': [u'Du contenu', None]
# }

SQLAlchemy-Continuum fournit également une fonction utilitaire appelée `changeset`. Avec cette fonction, vous pouvez facilement vérifier l'ensemble des modifications d'un objet donné dans la transaction actuelle.

from sqlalchemy_continuum import changeset
article = Article(name=u'Un article')
changeset(article)
# {'name': [None, u'Un article']}

Relations de version

Chaque objet de version reflète toutes les relations des objets parents. Vous pouvez considérer les relations d'un objet de version comme des 'relations de l'objet parent à un moment donné'.

Supposons que vous ayez deux modèles : `Article` et `Category`. Chaque `Article` a une `Category`. Dans l'exemple suivant, nous ajoutons d'abord des objets `Article` et `Category` dans la base de données.

Continuum enregistre en arrière-plan de nouveaux enregistrements `ArticleVersion` et `CategoryVersion`. Ensuite, nous mettons à jour l'entité `Article` créée pour utiliser une autre catégorie. Continuum crée de nouveaux objets de version en conséquence.

Enfin, nous vérifions les relations de catégorie des différentes versions d'article.

category = Category(name=u'Une catégorie')
article = Article(
    name=u'Un article',
    category=category
)
session.add(article)
session.commit()
article.category = Category(name=u'Une autre catégorie')
session.commit()
article.versions[0].category.name  # u'Une catégorie'
article.versions[1].category.name  # u'Une autre catégorie'

La logique selon laquelle SQLAlchemy-Continuum construit ces relations se trouve dans la classe `RelationshipBuilder`.

Relations avec des classes non versionnées

Prenons l'exemple précédent d'Articles et de Catégories. Considérons maintenant que seul le modèle `Article` est versionné :

class Article(Base):
    __tablename__ = 'article'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    name = sa.Column(sa.Unicode(255), nullable=False)
class Category(Base):
    __tablename__ = 'tag'
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    name = sa.Column(sa.Unicode(255))
    article_id = sa.Column(sa.Integer, sa.ForeignKey(Article.id))
    article = sa.orm.relationship(
        Article,
        backref=sa.orm.backref('categories')
    )

Ici, les versions d'Article refléteront toujours les relations du modèle Article mais retourneront simplement des objets Category au lieu d'objets CategoryVersion :

category = Category(name=u'Une catégorie')
article = Article(
    name=u'Un article',
    category=category
)
session.add(article)
session.commit()
article.category = Category(name=u'Une autre catégorie')
session.commit()
version = article.versions[0]
version.category.name                   # u'Une autre catégorie'
isinstance(version.category, Category)  # True

Relations dynamiques

Si la classe parente a une relation dynamique, elle sera reflétée comme une propriété qui retourne une requête dans la classe de version associée.

class Article(Base):
    __tablename__ = 'article'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    name = sa.Column(sa.Unicode(255), nullable=False)
class Tag(Base):
    __tablename__ = 'tag'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    name = sa.Column(sa.Unicode(255))
    article_id = sa.Column(sa.Integer, sa.ForeignKey(Article.id))
    article = sa.orm.relationship(
        Article,
        backref=sa.orm.backref(
            'tags',
            lazy='dynamic'
        )
    )
article = Article()
article.name = u'Un article'
article.content = u'Un contenu'
session.add(article)
session.commit()
tag_query = article.versions[0].tags
tag_query.all()  # retourne toutes les tags pour la version donnée
tag_query.count()  # retourne le nombre de tags pour la version donnée

ANNULATION DES CHANGEMENTS

L'un des principaux avantages de SQLAlchemy-Continuum est sa capacité à annuler les changements.

Annuler mise à jour

article = Article(name=u'Nouvel article', content=u'Un contenu')
session.add(article)
session.commit(article)
version = article.versions[0]
article.name = u'Article mis à jour'
session.commit()
version.revert()
session.commit()
article.name
# u'Nouvel article'

Annuler suppression

article = Article(name=u'Nouvel article', content=u'Un contenu')
session.add(article)
session.commit(article)
version = article.versions[0]
session.delete(article)
session.commit()
version.revert()
session.commit()
# L'article revit !
session.query(Article).first()

Annuler relations

Parfois, vous pouvez vouloir annuler un objet ainsi que certaines de ses relations à un état spécifique. Considérez la définition de modèle suivante :

class Article(Base):
    __tablename__ = 'article'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    name = sa.Column(sa.Unicode(255))
class Tag(Base):
    __tablename__ = 'tag'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    name = sa.Column(sa.Unicode(255))
    article_id = sa.Column(sa.Integer, sa.ForeignKey(Article.id))
    article = sa.orm.relationship(Article, backref='tags')

Supposons maintenant qu'un utilisateur ajoute d'abord un article avec quelques tags :

article = Article(
    name=u'Un article',
    tags=[Tag(u'Bon'), Tag(u'Intéressant')]
)
session.add(article)
session.commit()

Ensuite, supposons qu'un autre utilisateur supprime l'un des tags :

tag = session.query(Tag).filter_by(name=u'Intéressant')
session.delete(tag)
session.commit()

Maintenant, le premier utilisateur veut ramener l'article à son état d'origine. Cela peut être réalisé comme suit (notez comment nous utilisons le paramètre `relations`) :

article = session.get(Article, 1)
article.versions[0].revert(relations=['tags'])
session.commit()

REQUETES

Vous pouvez interroger les modèles d'historique comme n'importe quel autre modèle déclaratif SQLAlchemy.

from sqlalchemy_continuum import version_class
ArticleVersion = version_class(Article)
session.query(ArticleVersion).filter_by(name=u'nom quelconque').all()

Combien de transactions ont été exécutées ?

from sqlalchemy_continuum import transaction_class
Transaction = transaction_class(Article)
Transaction.query.count()

Interroger les entités d'une classe à une révision donnée

Dans l'exemple suivant, nous trouvons tous les articles qui ont été affectés par la transaction 33.

session.query(ArticleVersion).filter_by(transaction_id=33)

Interroger les transactions, auxquelles les entités d'une classe donnée ont changé

Dans cet exemple, nous trouvons toutes les transactions qui ont affecté une instance du modèle 'Article'. Cette requête nécessite le plugin `TransactionChangesPlugin`.

TransactionChanges = Article.__versioned__['transaction_changes']
entries = (
    session.query(Transaction)
    .innerjoin(Transaction.changes)
    .filter(
        TransactionChanges.entity_name.in_(['Article'])
    )
)

Interroger les versions d'une entité qui ont modifié une propriété donnée

Dans l'exemple suivant, nous voulons trouver toutes les versions de la classe Article qui ont modifié l'attribut 'name'. Cet exemple suppose que vous utilisez le `PropertyModTrackerPlugin`.

ArticleVersion = version_class(Article)
session.query(ArticleHistory).filter(ArticleVersion.name_mod).all()

TRANSACTIONS

Transaction

Pour chaque transaction validée, SQLAlchemy-Continuum crée un nouvel enregistrement de transaction.

Les transactions peuvent être interrogées comme n'importe quel autre modèle déclaratif SQLAlchemy.

from sqlalchemy_continuum import transaction_class
Transaction = transaction_class(Article)
# trouver toutes les transactions
session.query(Transaction).all()

UnitOfWork

Pour chaque connexion de base de données, SQLAlchemy-Continuum crée un objet `UnitOfWork` interne. Normalement, ces objets sont créés lors de la phase `before_flush` du flux de travail de la session. Cependant, vous pouvez également forcer la création de l'unité de travail avant cette phase.

uow = versioning_manager.unit_of_work(session)

Les objets transaction sont normalement créés automatiquement lors de la phase `before_flush`. Si vous avez besoin d'accéder à l'objet transaction avant le début de la phase de flush, vous pouvez le faire en appelant la méthode `create_transaction` de la classe `UnitOfWork`.

transaction = uow.create_transaction(session)

Les objets de version sont normalement créés pendant la phase `after_flush`, mais vous pouvez également forcer leur création à tout moment en appelant la méthode `make_versions`.

uow.make_versions(session)

Internals du flux de travail

Considérez le fragment de code suivant où nous créons un nouvel article.

article = Article()
article.name = u'Un article'
article.content = u'Un contenu'
session.add(article)
session.commit()

Cela exécuterait les requêtes SQL suivantes (sur PostgreSQL)

1.
INSERT INTO article (name, content) VALUES (?, ?)
params: ('Un article', 'Un contenu')
2.
INSERT INTO transaction (issued_at) VALUES (?)
params: (datetime.utcnow())
3.
INSERT INTO article_version (id, name, content, transaction_id) VALUES (?, ?, ?, ?)
params: (<id d'article de la requête 1>, 'Un article', 'Un contenu', <id de transaction de la requête 2>)

VERSIONNEMENT Natif

Depuis la version 1.1, SQLAlchemy-Continuum prend en charge le versionnement natif pour le dialecte PostgreSQL. Le versionnement natif crée des déclencheurs SQL pour tous les modèles versionnés. Ces déclencheurs suivent les modifications apportées aux modèles versionnés. Comparé au versionnement basé sur les objets, le versionnement natif présente

  • Beaucoup plus rapide que la version basée sur des objets normale
  • Empreinte mémoire minimale lorsqu'elle est utilisée avec les options de configuration create_tables=False et create_models=False.
  • Migrations de base de données plus compliquées, car les déclencheurs doivent également être mis à jour.

Utilisation

Pour activer la version native, vous devez définir l'option de configuration native_versioning à True.

make_versioned(options={'native_versioning': True})

Migrations de schéma

Lorsque vous effectuez des migrations de schéma (par exemple, l'ajout de nouvelles colonnes aux tables de version), vous devez vous souvenir d'appeler sync_trigger afin de maintenir le déclencheur de version à jour.

from sqlalchemy_continuum.dialects.postgresql import sync_trigger
sync_trigger(conn, 'article_version')

Si vous n'utilisez pas PropertyModTrackerPlugin, vous devez le désactiver :

sync_trigger(conn, 'article_version', use_property_mod_tracking=False)

PLUGINS

Utilisation des plugins

from sqlalchemy_continuum.plugins import PropertyModTrackerPlugin
versioning_manager.plugins.append(PropertyModTrackerPlugin())
versioning_manager.plugins  # <PluginCollection [...]>
# Vous pouvez également supprimer un plugin
del versioning_manager.plugins[0]

Activité

L'ActivityPlugin est le plugin le plus puissant pour suivre les modifications d'entités individuelles. Si vous utilisez ActivityPlugin, vous n'avez probablement pas besoin d'utiliser les plugins TransactionChanges ni TransactionMeta.

Vous pouvez initialiser l'ActivityPlugin en l'ajoutant au gestionnaire de version.

Colonne Type Description
id BigInteger La clé primaire de l'activité
verb Unicode Le verbe définit l'action de l'activité
data JSON Données supplémentaires pour l'activité au format JSON
transaction_id BigInteger La transaction à laquelle cette activité était associée
object_id BigInteger La clé primaire de l'objet. L'objet peut être n'importe quelle entité ayant un entier comme clé primaire.
object_type Unicode Le type de l'objet (nom de la classe sous forme de chaîne)
object_tx_id BigInteger Le dernier transaction_id associé à l'objet. Ceci est utilisé pour récupérer efficacement la version de l'objet associée à cette activité.
target_id BigInteger La clé primaire de la cible. La cible peut être n'importe quelle entité ayant un entier comme clé primaire.
target_type Unicode Le type de la cible (nom de la classe sous forme de chaîne)
target_tx_id BigInteger Le dernier transaction_id associé à la cible.

Limitations

Actuellement, toutes les modifications apportées aux modèles parents doivent être validées (flushed) ou validées (committed) avant la création des activités. Cela est dû au fait qu'il n'existe toujours pas de processeurs de dépendances pour les relations génériques. Ainsi, lorsque vous créez des activités et que vous leur assignez des objets/cibles, n'oubliez pas de valider (flush) la session avant de créer une activité :

article = Article(name=u'Un article')
session.add(article)
session.flush()  # <- IMPORTANT !
first_activity = Activity(verb=u'create', object=article)
session.add(first_activity)
session.commit()

Les cibles et les objets d'une activité donnée doivent avoir une colonne clé primaire entière nommée id.

Créer des activités

Une fois vos modèles configurés, vous pouvez obtenir le modèle Activity à partir de la propriété activity_cls de la classe ActivityPlugin :

Activity = activity_plugin.activity_cls

Supposons maintenant que nous ayons un modèle appelé Article et Category. Chaque Article a une Category. Les activités doivent être créées en même temps que les modifications apportées à ces modèles.

article = Article(name=u'Un article')
session.add(article)
session.flush()
first_activity = Activity(verb=u'create', object=article)
session.add(first_activity)
session.commit()

La transaction actuelle est automatiquement attribuée à l'objet activité :

first_activity.transaction  # Objet Transaction

Mettre à jour des activités

La propriété object de l'objet Activity contient l'objet actuel et object_version contient la version de l'objet au moment où l'activité a été créée.

article.name = u'Un article mis à jour !'
session.flush()
second_activity = Activity(verb=u'update', object=article)
session.add(second_activity)
session.commit()
second_activity.object.name  # u'Un article mis à jour !'
first_activity.object.name  # u'Un article mis à jour !'
first_activity.object_version.name  # u'Un article'

Supprimer des activités

Les propriétés de version sont particulièrement utiles pour les activités de suppression. Une fois que l'activité est récupérée de la base de données, l'objet n'est plus disponible (car supprimé), donc la seule façon de montrer des informations sur l'objet que l'utilisateur a supprimé est d'accéder à la propriété object_version.

session.delete(article)
session.flush()
third_activity = Activity(verb=u'delete', object=article)
session.add(third_activity)
session.commit()
third_activity.object_version.name  # u'Un article mis à jour !'

Historiques de versions locaux utilisant des cibles

La propriété target du modèle Activity offre un moyen de suivre les modifications d'un objet associé donné. Dans l'exemple ci-dessous, nous créons une nouvelle activité lors de l'ajout d'une catégorie à un article, puis nous marquons l'article comme cible de cette activité.

session.add(Category(name=u'Première catégorie', article=article))
session.flush()
activity = Activity(
    verb=u'create',
    object=category,
    target=article
)
session.add(activity)
session.commit()

Maintenant, si nous voulions trouver toutes les modifications qui ont affecté un article donné, nous pourrions le faire en recherchant toutes les activités où l'objet ou la cible est l'article donné.

import sqlalchemy as sa
activities = session.query(Activity).filter(
    sa.or_(
        Activity.object == article,
        Activity.target == article
    )
)

Flask

FlaskPlugin offre un moyen d'intégrer le framework Flask avec SQLAlchemy-Continuum. Flask-Plugin ajoute deux colonnes au modèle Transaction, à savoir user_id et remote_addr.

Ces colonnes sont automatiquement remplies lors de la création de l'objet transaction. La colonne remote_addr est remplie avec la valeur de l'adresse distante qui a effectué la requête actuelle. La colonne user_id est remplie avec l'identifiant de l'objet current_user.

from sqlalchemy_continuum.plugins import FlaskPlugin
from sqlalchemy_continuum import make_versioned
make_versioned(plugins=[FlaskPlugin()])

PropertyModTracker

Le PropertyModTrackerPlugin offre un moyen de suivre efficacement les modifications de propriétés individuelles. Avec PropertyModTrackerPlugin, vous pouvez effectuer des requêtes efficaces telles que :

Trouver toutes les versions du modèle X où l'utilisateur a mis à jour la propriété A ou la propriété B.

Trouver toutes les versions du modèle X où l'utilisateur n'a pas mis à jour la propriété A.

PropertyModTrackerPlugin ajoute une colonne de suivi des modifications distincte pour chaque colonne versionnée. Ainsi, par exemple, si vous avez un modèle versionné appelé Article avec les colonnes name et content, ce plugin ajouterait deux colonnes booléennes supplémentaires name_mod et content_mod pour le modèle de version. Lorsque l'utilisateur valide les transactions, le plugin met automatiquement à jour ces colonnes booléennes.

TransactionChanges

TransactionChanges fournit un moyen de suivre efficacement quels modèles déclaratifs ont été modifiés dans une transaction donnée. Cela peut être utile lorsque des transactions doivent être interrogées ultérieurement pour des problèmes tels que :

1.
Trouver toutes les transactions qui ont affecté le modèle User.
2.
Trouver toutes les transactions qui n'ont pas affecté les modèles Entity et Event.

Le plugin fonctionne de deux manières. Lors de la phase d'instrumentation de classe, ce plugin crée un modèle de transaction spécial appelé TransactionChanges. Ce modèle est associé à une table appelée transaction_changes, qui n'a que deux champs : transaction_id et entity_name. Si, par exemple, une transaction consistait à enregistrer 5 nouvelles entités User et 1 entité Article, deux nouvelles lignes seraient insérées dans la table transaction_changes.

transaction_id entity_name
233678 User
233678 Article

TransactionMeta

TransactionMetaPlugin offre un moyen d'enregistrer des données clé-valeur pour les transactions. Vous pouvez utiliser le plugin de la même manière que les autres plugins :

meta_plugin = TransactionMetaPlugin()
versioning_manager.plugins.append(meta_plugin)

TransactionMetaPlugin crée un modèle simple appelé TransactionMeta. Cette classe a trois colonnes : transaction_id, key et value. TransactionMeta plugin crée également un proxy d'association entre TransactionMeta et Transaction classes pour un accès facile basé sur un dictionnaire aux paires clé-valeur.

Vous pouvez facilement 'taguer' les transactions avec certaines paires clé-valeur en donnant ces clés et valeurs à la propriété meta de la classe Transaction.

from sqlalchemy_continuum import versioning_manager
article = Article()
session.add(article)
uow = versioning_manager.unit_of_work(session)
tx = uow.create_transaction(session)
tx.meta = {u'some_key': u'some value'}
session.commit()
TransactionMeta = meta_plugin.model_class
Transaction = versioning_manager.transaction_cls
# trouver toutes les transactions avec les tags 'article'
query = (
    session.query(Transaction)
    .join(Transaction.meta_relation)
    .filter(
        db.and_(
            TransactionMeta.key == 'some_key',
            TransactionMeta.value == 'some value'
        )
    )
)

CONFIGURATION

Configuration globale et par classe

Tous les paramètres de configuration de Continuum peuvent être définis au niveau global (niveau du gestionnaire) et au niveau de la classe. Définir une option au niveau du gestionnaire affecte toutes les classes dans la portée du gestionnaire d'écoute d'instrumentation de classe du gestionnaire (par défaut, tous les modèles déclaratifs SQLAlchemy).

Dans l'exemple suivant, nous définissons l'option de configuration 'transaction_column_name' sur False au niveau du gestionnaire.

make_versioned(options={'transaction_column_name': 'my_tx_id'})

Comme son nom l'indique, la configuration au niveau de la classe ne s'applique qu'à la classe donnée. La configuration au niveau de la classe peut être passée à l'attribut de classe __versioned__.

class User(Base):
    __versioned__ = {
        'transaction_column_name': 'tx_id'
    }

Stratégies de versionnement

Similaire à Hibernate Envers, SQLAlchemy-Continuum propose deux stratégies de versionnement distinctes : 'validity' et 'subquery'. La stratégie par défaut est 'validity'.

Validité

La stratégie 'validity' enregistre deux colonnes dans chaque table d'historique, à savoir 'transaction_id' et 'end_transaction_id'. Les noms de ces colonnes peuvent être configurés avec les options de configuration transaction_column_name et end_transaction_column_name.

Comme avec la stratégie 'subquery', pour chaque entité insérée, mise à jour et supprimée, Continuum crée une nouvelle version dans la table d'historique. Cependant, elle met également à jour le end_transaction_id de la version précédente pour pointer vers la version actuelle. Cela crée une légère surcharge lors de la manipulation des données.

Avec la stratégie 'validity', le parcours des versions est très rapide. Lors de l'accès à une version précédente, Continuum essaie de trouver l'enregistrement de version où les clés primaires correspondent et où le end_transaction_id est le même que le transaction_id de l'enregistrement de version donné. Lors de l'accès à la version suivante, Continuum essaie de trouver l'enregistrement de version où les clés primaires correspondent et où le transaction_id est le même que le end_transaction_id de l'enregistrement de version donné.

Avantages :
•
Le parcours des versions est beaucoup plus rapide car aucune sous-requête corrélée n'est nécessaire
Inconvénients :
•
Les mises à jour, insertions et suppressions sont un peu plus lentes

Sous-requête

La stratégie 'subquery' utilise une colonne dans chaque table d'historique, à savoir 'transaction_id'. Le nom de cette colonne peut être configuré avec l'option de configuration transaction_column_name.

Après chaque entité insérée, mise à jour et supprimée, Continuum crée une nouvelle version dans la table d'historique et définit la colonne 'transaction_id' pour pointer vers la transaction actuelle.

Avec la stratégie 'subquery', le parcours des versions est lent. L'accès aux versions précédentes et suivantes d'un objet de version donné nécessite des sous-requêtes corrélées.

Avantages :
•
Les mises à jour, insertions et suppressions sont un peu plus rapides qu'avec la stratégie 'validity'
Inconvénients :
•
Le parcours des versions est beaucoup plus lent

Exclusion et inclusion de colonnes

Avec l'option de configuration exclude, vous pouvez définir quels attributs d'entité vous souhaitez versionner. Par défaut, Continuum versionne tous les attributs d'entité.

class User(Base):
    __versioned__ = {
        'exclude': ['picture']
    }
    id = sa.Column(sa.Integer, primary_key=True)
    name = sa.Column(sa.Unicode(255))
    picture = sa.Column(sa.LargeBinary)

Schéma Continuum

Tables de versions

Par défaut, SQLAlchemy-Continuum crée une table de version pour chaque table d'entité versionnée. Les tables de version sont suffixées par '_version'. Ainsi, par exemple, si vous avez deux tables versionnées 'article' et 'category', SQLAlchemy-Continuum créerait deux tables de version 'article_version' et 'category_version'.

Par défaut, les tables de version contiennent les colonnes suivantes :

  • l'identifiant de l'entité d'origine (cela peut être plus d'une colonne dans le cas de clés primaires composites)
  • transaction_id - un entier qui correspond au numéro d'identifiant dans la table transaction_log.
  • end_transaction_id - un entier qui correspond au transaction_id du prochain enregistrement de version. S'il s'agit de l'enregistrement de version actuel, ce champ est nul.
  • operation_type - un petit entier définissant le type de l'opération
  • champs versionnés de l'entité d'origine

Si vous utilisez PropertyModTracker, Continuum crée également un champ booléen pour chaque champ versionné. Par défaut, ces champs booléens sont suffixés par '_mod'.

La clé primaire de chaque table de version est la combinaison de la clé primaire de la table parente + le transaction_id. Cela signifie qu'il ne peut y avoir qu'une seule entrée de table de version pour une instance d'entité donnée à une transaction donnée.

Tables de transactions

Par défaut, Continuum crée une table de transaction appelée transaction. De nombreux plugins continuum créent également des tables supplémentaires pour un stockage efficace des transactions. Si vous souhaitez interroger efficacement les transactions par la suite, vous devriez envisager d'utiliser certains de ces plugins.

La table de transaction ne contient que deux champs par défaut : id et issued_at.

Migrations Alembic

Chaque fois que vous apportez des modifications à la structure de la base de données, vous devez également modifier les tables d'historique associées. Lorsque vous modifiez vos modèles, SQLAlchemy-Continuum modifie automatiquement les définitions des modèles d'historique, vous pouvez donc utiliser alembic revision --autogenerate comme auparavant. Il vous suffit de vous assurer que la fonction make_versioned est appelée avant qu'Alembic ne rassemble tous vos modèles et que configure_mappers soit appelée ensuite.

Soyez très attentif lors de la suppression ou du déplacement de données des tables parentes et de la réflexion de ces modifications sur les tables d'historique.

Dépannage

Si Alembic n'a détecté aucun changement ou génère une migration inversée (essaie de supprimer les tables *_version de la base de données au lieu de les créer), assurez-vous que configure_mappers a été appelé par la commande Alembic.
