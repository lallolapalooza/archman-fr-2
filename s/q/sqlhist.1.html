NOM

sqlhist - Outil qui utilise le langage SQL pour créer / afficher la création d'histogrammes tracefs et d'événements synthétiques.

SYNOPSIS

sqlhist [OPTIONS] [commande-SELECT-SQL]

DESCRIPTION

Le programme sqlhist(1) prendra une instruction de type SQL pour créer des histogrammes tracefs et des événements synthétiques qui peuvent effectuer diverses actions pour diverses manipulations des données.

Le système de fichiers tracefs interagit avec l'infrastructure de traçage Linux qui possède divers événements dynamiques et statiques dans tout le noyau. Chacun de ces événements peut avoir un "histogramme" qui lui est attaché, où les champs de l'événement définissent les compartiments de l'histogramme.

Un événement synthétique est un moyen de lier deux événements distincts et d'utiliser les champs et les horodatages de ces événements pour créer un nouvel événement dynamique. Ce nouvel événement dynamique est appelé un événement synthétique. Les champs de chaque événement peuvent subir des calculs simples où, par exemple, la différence entre un champ d'un événement et un champ de l'autre événement peut être calculée. Cela fonctionne également pour les horodatages des événements où la différence de temps entre les deux événements peut également être extraite et placée dans l'événement synthétique.

D'autres actions peuvent être effectuées à partir des champs des événements. Un instantané peut être pris du tampon circulaire du noyau lorsqu'une variable utilisée dans l'événement synthétique atteignant un maximum, ou simplement lorsqu'elle change.

Les commandes pour créer des histogrammes et des événements synthétiques sont complexes et difficiles à mémoriser. sqlhist est utilisé pour convertir la syntaxe SQL en commandes nécessaires pour créer l'histogramme ou l'événement synthétique.

La commande-SELECT-SQL est une chaîne SQL définie par tracefs_sql(3).

Notez que cela doit être exécuté en tant que root (ou avec sudo) car l'interaction avec le répertoire tracefs nécessite des privilèges root, sauf si l'option -t est donnée avec une copie du répertoire tracefs et ses événements.

sqlhist est un programme simple dont le code existe en fait dans la page de manuel tracefs_sql(3).

OPTIONS

-n nom

Le nom de l'événement synthétique à créer. Cet événement peut ensuite être utilisé comme tout autre événement, et activé via trace-cmd(1).

-t dir-tracefs

Afin de tester ceci en tant qu'utilisateur non root, une copie du répertoire tracefs peut être utilisée, et passer ce répertoire avec cette option permettra au programme de fonctionner. Évidemment, -e ne fonctionnera pas en tant que non-root car il ne pourra pas exécuter. 
# mkdir /tmp/tracing
# cp -r /sys/kernel/tracing/events /tmp/tracing
# exit
$ ./sqlhist -t /tmp/tracing ...

-e

Non seulement afficher les commandes pour créer l'histogramme, mais aussi les exécuter. Cela nécessite des privilèges root.

-f fichier

Au lieu de lire les commandes SQL depuis la ligne de commande, les lire depuis fichier. Si fichier est -, alors lire depuis l'entrée standard.

-m var

Effectuer l'action donnée lorsque la variable var atteint un nouveau maximum. Ceci ne peut pas être utilisé avec -c.

-c var

Effectuer l'action donnée lorsque la variable var change de valeur. Ceci ne peut pas être utilisé avec -m.

-s

Effectuer un instantané au lieu d'appeler l'événement synthétique.

-T

Effectuer à la fois un instantané et tracer l'événement synthétique.

-S champs[,champs]

Sauvegarder les champs donnés. Les champs doivent être des champs de l'événement "fin" donné dans la commande-SELECT-SQL

-B instance

Pour les instructions simples qui ne produisent qu'un histogramme, l'instance donnée ici sera l'endroit où l'histogramme sera créé. Ceci est ignoré pour la création complète d'événements synthétiques, car les événements synthétiques ont un effet global sur toutes les instances de traçage, tandis que les histogrammes n'affectent qu'une seule instance.

EXEMPLES

Créer l'exécutable sqlhist :

   man tracefs_sql | sed -ne '/^EXAMPLE/,/FILES/ { /EXAMPLE/d ; /FILES/d ; p}' > sqlhist.c
   gcc -o sqlhist sqlhist.c `pkg-config --cflags --libs libtracefs`

Comme décrit ci-dessus, à des fins de test, faites une copie du répertoire d'événements :

   $ mkdir /tmp/tracing
   $ sudo cp -r /sys/kernel/tracing/events /tmp/tracing/
   $ sudo chmod -R 0644 /tmp/tracing/

Pour un exemple de sortie d'histogramme simple utilisant la copie du répertoire tracefs.

   $ ./sqlhist -t /tmp/tracing/ 'SELECT CAST(call_site as SYM-OFFSET), bytes_req, CAST(bytes_alloc AS _COUNTER_) FROM kmalloc'

Produit la sortie :

   echo 'hist:keys=call_site.sym-offset,bytes_req:vals=bytes_alloc' > /sys/kernel/tracing/events/kmem/kmalloc/trigger

NAME

sqlhist - sqlhist is a tracer that uses a SQL query to build synthetic events

SYNOPSIS

sqlhist [OPTIONS] [SQL STATEMENT]

DESCRIPTION

The sqlhist command is an example of how to use the tracepoints that are available in the tracefs filesystem. Tracefs is a filesystem that exposes the kernel's tracing infrastructure. A lot of the trace infrastructure can be found under /sys/kernel/debug/tracing. Many of the trace events that are generated by the kernel are saved in a ring buffer. This ring buffer can be read by tools like trace-cmd(1).

Trace events are stored in the ring buffer as structures. The fields of these structures can be accessed by tools like trace-cmd. sqlhist takes this a step further by allowing you to write SQL queries that can parse these structures and create new synthetic events. This allows for complex analysis of the trace data.

The sqlhist tool is written as an example and it is not meant for production use. It shows how to query the trace event buffer using SQL syntax.

The sqlhist tool works by accessing the trace buffer created by the kernel. It can then parse specific trace events and process them using SQL queries. The results of these queries can be displayed directly or saved as new synthetic events.

The main idea is to use the trace event data to create new synthetic events that might not exist in the kernel.

Note, although the examples use uppercase for the SQL keywords, they do not have to be. SELECT could also be select or even sElEcT.

By using the full SQL language, synthetic events can be made and processed. For example, using sqlhist along with trace-cmd(1), wake up latency can be recorded by creating a synthetic event by attaching the sched_waking and the sched_switch events.

  # sqlhist -n wakeup_lat -e -T -m lat 'SELECT end.next_comm AS comm, (end.TIMESTAMP_USECS - start.TIMESTAMP_USECS) AS lat FROM ' \
    'sched_waking AS start JOIN sched_switch AS end ON start.pid = end.next_pid WHERE end.next_prio < 100 && end.next_comm == "cyclictest"'
  # trace-cmd start -e all -e wakeup_lat -R stacktrace
  # cyclictest -l 1000 -p80 -i250  -a -t -q -m -d 0 -b 1000 --tracemark

Here’s the options for sqlhist explained:

-n wakeup_lat

Name the synthetic event to use wakeup_lat.

-e

Execute the commands that are printed.

-T

Perform both a trace action and then a snapshot action (swap the buffer into the static snapshot buffer).

-m lat

Trigger the actions whenever lat hits a new maximum value.

Now a breakdown of the SQL statement:

 'SELECT end.next_comm AS comm, (end.TIMESTAMP_USECS - start.TIMESTAMP_USECS) AS lat FROM ' \
    'sched_waking AS start JOIN sched_switch AS end ON start.pid = end.next_pid WHERE end.next_prio < 100 && end.next_comm == "cyclictest"'

end.next_comm AS comm

Save the sched_switch field next_comm and place it into the comm field of the wakeup_lat synthetic event.

(end.TIMESTAMP_USECS - start.TIMESTAMP_USECS) AS lat

Take the delta of the time stamps from the sched_switch event and the sched_waking event. As time stamps are usually recorded in nanoseconds, TIMESTAMP would give the full nanosecond time stamp, but here, the TIMESTAMP_USECS will truncate it into microseconds. The value is saved in the variable lat, which will also be recorded in the synthetic event.

FROM sched_waking AS start JOIN sched_switch AS end ON start.pid = end.next_pid

Create the synthetic event by joining sched_waking to sched_switch, matching the sched_waking pid field with the sched_switch next_pid field. Also make start an alias for sched_waking and end an alias for sched_switch which then an use start and end as a subsitute for sched_waking and sched_switch respectively through out the rest of the SQL statement.

WHERE end.next_prio < 100 && end.next_comm == "cyclictest"

Filter the logic where it executes only if sched_waking next_prio field is less than 100. (Note, in the Kernel, priorities are inverse, and the real-time priorities are represented from 0-100 where 0 is the highest priority). Also only trace when the next_comm (the task scheduling in) of the sched_switch event has the name "cyclictest".

For the trace-cmd(3) command:

   trace-cmd start -e all -e wakeup_lat -R stacktrace

trace-cmd start

Enables tracing (does not record to a file).

-e all

Enable all events

-e wakeup_lat -R stacktrace

have the "wakeup_lat" event (our synthetic event) enable the stacktrace trigger, were for every instance of the "wakeup_lat" event, a kernel stack trace will be recorded in the ring buffer.

After calling cyclictest (a real-time tool to measure wakeup latency), read the snapshot buffer.

trace-cmd show -s

trace-cmd show reads the kernel ring buffer, and the -s option will read the snapshot buffer instead of the normal one.
 <idle>-0       [002] d..4 23454.902256: wakeup_lat: next_comm=cyclictest lat=17
We see on the "wakeup_lat" event happened on CPU 2, with a wake up latency 17 microseconds.
