NOM

stunnel - tunnel universel de protocole TLS

SYNTAXE

Unix:
stunnel [FICHIER] | -fd N | -help | -version | -sockets | -options
WIN32:
stunnel [ [ -install | -uninstall | -start | -stop |
-reload | -reopen | -exit ] [-quiet] [FICHIER] ] |
-help | -version | -sockets | -options

DESCRIPTION

stunnel est conçu pour encapsuler des connexions entre des clients distants et des serveurs locaux ou distants dans le protocole TLS. Un serveur local est une application destinée à être exécutée avec inetd. Stunnel permet de mettre en place simplement des serveurs qui ne possèdent pas la fonctionnalité TLS, via des canaux TLS sécurisés.

stunnel peut ajouter la fonctionnalité TLS à des démons couramment utilisés par inetd, tels que pop3 ou imap, à des démons autonomes comme nntp, smtp ou http, et même tunneliser ppp via des sockets réseau sans modifier le code source.

FICHIER DE CONFIGURATION

Une ligne dans le fichier de configuration peut être :

  • vide (ignorée)
  • un commentaire commençant par le caractère ';' (ignoré)
  • une paire « nom_option = valeur_option »
  • un texte « [nom_service] » indiquant le début de la définition d'un service

Le paramètre adresse peut être :

  • un numéro de port
  • une paire adresse (IPv4, IPv6 ou nom de domaine) et numéro de port, séparée par des points-virgules
  • un chemin vers un socket Unix (Unix seulement)

OPTIONS GLOBALES

chroot = REPERTOIRE (Unix seulement)
répertoire racine de travail du système de fichiers

L'option spécifie le répertoire dans lequel le processus stunnel sera enfermé immédiatement après son initialisation, avant de commencer à accepter des connexions. Les chemins spécifiés dans les options CApath, CRLpath, pid et exec doivent être situés à l'intérieur du répertoire spécifié dans l'option chroot et être spécifiés par rapport à ce répertoire.

Certaines fonctions du système d'exploitation peuvent nécessiter des fichiers supplémentaires placés dans le répertoire spécifié par l'argument chroot :

  • la résolution différée des noms DNS nécessite généralement /etc/nsswitch.conf et /etc/resolv.conf
  • la localisation du fuseau horaire dans les logs nécessite le fichier /etc/timezone
  • certains autres fichiers peuvent nécessiter des fichiers périphériques, comme /dev/zero ou /dev/null
compression = deflate | zlib
choisir l'algorithme de compression des données transférées

par défaut : pas de compression

L'algorithme deflate est la méthode de compression standard conformément à la RFC 1951.

debug = [SOUS_SYSTEME].NIVEAU
niveau de détail du logging

Le niveau de logging peut être spécifié à l'aide de l'une des appellations ou nombres suivants : emerg (0), alert (1), crit (2), err (3), warning (4), notice (5), info (6) ou debug (7). Les messages de niveau inférieur (numériquement) ou égal au niveau spécifié sont enregistrés. Le niveau par défaut est notice (5).

Bien que l'utilisation de debug = debug ou debug = 7 fournisse les logs les plus détaillés, leur contenu n'est utile que pour les développeurs travaillant sur stunnel. Utilisez ce niveau de logging uniquement si vous êtes un(e) développeur(se) de stunnel, ou si vous préparez des informations détaillées à envoyer au support technique. Sinon, tenter d'analyser le contenu des logs sera une source supplémentaire de confusion.

Sauf si un sous-système est spécifié, le sous-système par défaut daemon sera utilisé. Les sous-systèmes ne sont pas supportés par la plateforme Win32.

La casse est ignorée pour le niveau et le sous-système.

OPTIONS DE SERVICE

Chaque section de configuration de service commence par son nom entre crochets. Le nom du service est utilisé pour le contrôle d'accès par la bibliothèque libwrap (TCP wrappers) et permet de distinguer les services individuels dans les journaux.

Si stunnel doit être utilisé en mode inetd, où un programme séparé (généralement inetd, xinetd ou tcpserver) est responsable de la réception de la connexion, vous devez lire la section MODE INETD ci-dessous.

accept = [HOTE:]PORT
écoute les connexions sur l'adresse et le port spécifiés

Si aucune adresse n'est spécifiée, stunnel écoute par défaut sur toutes les adresses IPv4 des interfaces locales.

Pour écouter sur toutes les adresses IPv6, utilisez :

accept = :::port
CAengine = IDENTIFIANT_CA_DANS_ENGINE
charge les certificats de confiance de l'autorité de certification depuis un moteur

L'option permet de spécifier l'emplacement du fichier contenant les certificats utilisés par l'option verifyChain ou verifyPeer.

L'option peut être utilisée plusieurs fois dans une même section.

Moteurs actuellement supportés : pkcs11, cng.

CApath = REPERTOIRE_CA
charge les certificats de confiance de l'autorité de certification depuis un répertoire

L'option spécifie le répertoire où stunnel cherchera les certificats si les options verifyChain ou verifyPeer ont été utilisées. Les fichiers de certificats doivent avoir des noms spéciaux XXXXXXXX.0, où XXXXXXXX est un hash cryptographique de la représentation DER du nom du sujet du certificat.

Cette option peut également être utilisée pour fournir le certificat de la racine de l'AC, qui est nécessaire pour la vérification correcte du stapling OCSP côté serveur.

La fonction de hachage a été modifiée dans OpenSSL 1.0.0. Il est nécessaire d'exécuter c_rehash lors du passage de OpenSSL 0.x.x à 1.x.x.

Si un répertoire chroot est défini, le chemin vers CApath est déterminé par rapport à ce répertoire.

CAfile = FICHIER_CA
charge les certificats de confiance de l'autorité de certification depuis un fichier

L'option permet de spécifier l'emplacement du fichier contenant les certificats utilisés par l'option verifyChain ou verifyPeer.

Cette option peut également être utilisée pour fournir le certificat de la racine de l'AC, qui est nécessaire pour la vérification correcte du stapling OCSP côté serveur.

CAstore = URI_CA
charge les certificats de confiance de l'autorité de certification depuis une ressource spécifiée par une URI

L'option permet de charger les certificats d'AC depuis un magasin externe géré par le mécanisme OSSL_STORE, tel qu'un module PKCS#11 (par exemple, un token matériel), un magasin de certificats système ou une ressource réseau.

L'option peut être utilisée indépendamment de CAfile et CAdir, elle sert de manière analogue à la validation de la chaîne de certificats en utilisant les options verifyChain ou verifyPeer, ainsi qu'à la vérification du stapling OCSP côté serveur.

Cette option nécessite la bibliothèque OpenSSL version 3.0 ou ultérieure.

cert = FICHIER_CERT | URI
fichier contenant la chaîne de certificats

L'option spécifie l'emplacement du fichier contenant les certificats utilisés par le programme stunnel pour s'authentifier auprès de l'autre partie de la connexion. Le fichier devrait contenir la chaîne de certificats complète, en commençant par le certificat client/serveur, et en terminant

#x0144;en que le certificat racine de l'AC soit auto-signé. Les fichiers au format PEM ou P12 sont pris en charge.

Un certificat est nécessaire pour utiliser le programme en mode serveur. En mode client, le certificat est facultatif.

L'option cert peut être spécifiée plusieurs fois. Le premier certificat rencontré sera utilisé comme certificat serveur ou client, tandis que les certificats suivants seront traités comme des intermédiaires dans la chaîne. Cette fonctionnalité nécessite OpenSSL version 1.0.2 ou ultérieure.

Si un moteur cryptographique ou un fournisseur est utilisé, l'option cert permet de sélectionner l'identifiant (URI PKCS#11) du certificat utilisé.

Remarque : le fournisseur nécessite OpenSSL 3.0 ou ultérieur

checkEmail = EMAIL
adresse e-mail du sujet du certificat présenté

Une section unique peut contenir plusieurs occurrences de l'option checkEmail. Les certificats sont acceptés si la section ne vérifie pas le sujet du certificat, ou si l'adresse e-mail du certificat présenté correspond à l'une des adresses e-mail spécifiées avec checkEmail.

Cette option nécessite OpenSSL version 1.0.2 ou ultérieure.

checkHost = NOM_SERVEUR
nom d'hôte du sujet du certificat présenté

Une section unique peut contenir plusieurs occurrences de l'option checkHost. Les certificats sont acceptés si la section ne vérifie pas le sujet du certificat, ou si le nom d'hôte du certificat présenté correspond à l'un des noms spécifiés avec checkHost.

Cette option nécessite OpenSSL version 1.0.2 ou ultérieure.

checkIP = IP
adresse IP du sujet du certificat présenté

Une section unique peut contenir plusieurs occurrences de l'option checkIP. Les certificats sont acceptés si la section ne vérifie pas le sujet du certificat, ou si l'adresse IP du certificat présenté correspond à l'une des adresses IP spécifiées avec checkIP.

Cette option nécessite OpenSSL version 1.0.2 ou ultérieure.

ciphers = LISTE_CHIFFREMENTS
liste des chiffrements autorisés pour les protocoles SSLv2, SSLv3, TLSv1, TLSv1.1, TLSv1.2

Cette option n'affecte pas la liste des suites de chiffrements pour le protocole TLSv1.3.

Le paramètre de cette option est une liste de chiffrements qui seront utilisés lors de l'ouverture de nouvelles connexions TLS, par exemple : DES-CBC3-SHA:IDEA-CBC-MD5.

ciphersuites = LISTE_SUITES_CHIFFREMENT
liste des suites de chiffrements autorisés pour le protocole TLSv1.3

Le paramètre de cette option est une liste de suites de chiffrements par ordre de préférence.

À partir d'OpenSSL 3.0, l'option ciphersuites ignore les chiffrements inconnus.

L'option ciphersuites est disponible à partir d'OpenSSL 1.1.1.

par défaut : TLS_CHACHA20_POLY1305_SHA256: TLS_AES_256_GCM_SHA384: TLS_AES_128_GCM_SHA256

par défaut : no (mode serveur)

config = COMMANDE[:PARAMETRE]
commande de configuration OpenSSL

La commande de configuration OpenSSL est exécutée avec le paramètre spécifié. Cela permet d'émettre des commandes de configuration OpenSSL à partir du fichier de configuration du tunnel. Les commandes disponibles sont décrites dans la page de manuel SSL_CONF_cmd(3ssl).

Il est possible de spécifier plusieurs options OpenSSL en utilisant plusieurs fois la commande config.

Au lieu d'écrire config = Curves:list_curves, utilisez l'option curves pour définir les courbes elliptiques.

Cette option nécessite OpenSSL version 1.0.2 ou ultérieure.

connect = [HOTE:]PORT
se connecter au serveur distant sur le port spécifié

Si aucun hôte n'est spécifié, stunnel se connecte par défaut au serveur local.

La commande peut être utilisée plusieurs fois dans une section unique pour assurer une haute disponibilité ou pour répartir la charge entre plusieurs serveurs.

répertoire des listes de révocation de certificats (CRL)

L'option spécifie le répertoire dans lequel stunnel recherchera les listes CRL utilisées par les options verifyChain et verifyPeer. Les fichiers de listes CRL doivent avoir des noms spéciaux XXXXXXXX.r0, où XXXXXXXX est le hachage de la liste CRL.

La fonction de hachage a été modifiée dans OpenSSL 1.0.0. Il faut exécuter c_rehash lors du passage d'OpenSSL 0.x.x à 1.x.x.

Si un répertoire chroot est défini, le chemin vers CRLpath est spécifié par rapport à ce répertoire.

CRLfile = FICHIER_CRL
fichier des listes de révocation de certificats (CRL)

L'option permet de spécifier l'emplacement du fichier contenant les listes CRL utilisées par les options verifyChain et verifyPeer.

courbes ECDH séparées par ':'

La liste des courbes disponibles peut être obtenue avec la commande :

openssl ecparam -list_curves

logId = TYPE
type d'identifiant de connexion client

Cet identifiant permet de distinguer les entrées de journal générées pour chaque connexion.

Types actuellement pris en charge :

sequential
Le numéro séquentiel de connexion n'est unique que dans une instance de stunnel, mais il est très court. Il est particulièrement utile pour l'analyse manuelle des journaux.
unique
Ce type d'identifiant est globalement unique, mais beaucoup plus long qu'un numéro de connexion séquentiel. Il est particulièrement utile pour l'analyse automatisée des journaux.
thread
L'identifiant du thread du système d'exploitation n'est ni unique (même au sein d'une instance de stunnel), ni court. Il est particulièrement utile pour le diagnostic des problèmes logiciels ou de configuration.
process
L'identifiant du processus (PID) peut être utile en mode inetd.

par défaut : sequential

securityLevel = NIVEAU
définir le niveau de sécurité

La signification de chaque niveau est décrite ci-dessous :

niveau 0
Tout est autorisé.
niveau 1
Niveau de sécurité offrant un minimum de 80 bits de sécurité. Aucun paramètre cryptographique offrant un niveau de sécurité inférieur à 80 bits ne peut être utilisé. Par conséquent, les clés RSA, DSA et DH de moins de 1024 bits, ainsi que les clés ECC de moins de 160 bits et tous les suites de chiffrement d'exportation sont interdites. L'utilisation de SSLv2 est interdite. Toutes les listes de paramètres cryptographiques utilisant MD5 pour le MAC sont interdites. À partir d'OpenSSL 3.0, les versions de TLS antérieures à 1.2 sont désactivées.
niveau 2
Niveau de sécurité offrant 112 bits de sécurité. Par conséquent, les clés RSA, DSA et DH de moins de 2048 bits, ainsi que les clés ECC de moins de 224 bits sont interdites. En plus des exclusions du niveau 1, l'utilisation des suites de chiffrement utilisant RC4 est également interdite. La compression est désactivée. L'utilisation de SSLv3 est interdite pour les versions d'OpenSSL antérieures à 3.0.
niveau 3
Niveau de sécurité offrant 128 bits de sécurité. Par conséquent, les clés RSA, DSA et DH de moins de 3072 bits, ainsi que les clés ECC de moins de 256 bits sont interdites. En plus des exclusions du niveau 2, l'utilisation des suites de chiffrement ne fournissant pas de chiffrement post-compromission (forward secrecy) est également interdite. Les tickets de session sont désactivés. Les versions de TLS antérieures à 1.1 sont interdites pour les versions d'OpenSSL antérieures à 3.0.
niveau 4
Niveau de sécurité offrant 192 bits de sécurité. Par conséquent, les clés RSA, DSA et DH de moins de 7680 bits, ainsi que les clés ECC de moins de 384 bits sont interdites. Les listes de paramètres cryptographiques utilisant SHA1 pour le MAC sont interdites. Les versions de TLS antérieures à 1.2 sont interdites pour les versions d'OpenSSL antérieures à 3.0.
niveau 5
Niveau de sécurité offrant 256 bits de sécurité. Par conséquent, les clés RSA, DSA et DH de moins de 15360 bits, ainsi que les clés ECC de moins de 512 bits sont interdites.
par défaut : 2

stunnel renvoie zéro en cas de succès, ou une valeur non nulle en cas d'erreur.

SIGNaux

Les signaux suivants peuvent être utilisés pour contrôler le programme sous Unix :

SIGHUP
Recharger le fichier de configuration.

Certaines options globales ne seront pas rechargées :

  • chroot
  • foreground
  • pid
  • setgid
  • setuid

Si l'option 'setuid' est utilisée, stunnel ne pourra pas recharger la configuration utilisant des ports privilégiés (<1024).

Si l'option 'chroot' est utilisée, stunnel recherchera tous les fichiers nécessaires (y compris le fichier de configuration, les certificats, le journal et le fichier pid) à l'intérieur du répertoire spécifié par 'chroot'.

SIGUSR1
Fermer et rouvrir le journal. Cette fonction peut être utilisée dans un script de rotation de journal pour le programme stunnel.
SIGUSR2
Écrire dans le journal la liste des connexions actives.
SIGTERM, SIGQUIT, SIGINT
Terminer le fonctionnement du programme.

L'effet de l'envoi d'autres signaux n'est pas défini.

EXEMPLES

Le chiffrement des connexions vers un serveur local imapd peut être utilisé :

[imapd]
accept = 993
exec = /usr/sbin/imapd
execArgs = imapd

ou en mode distant :

[imapd]
accept = 993
connect = 143

Pour permettre à un client de messagerie local d'utiliser le serveur imapd via TLS, il faut configurer la récupération du courrier depuis l'adresse localhost et le port 119, et utiliser la configuration suivante :

[imap]
client = yes
accept = 143
connect = serveur:993

En combinaison avec le programme pppd, stunnel permet d'établir un VPN simple. Du côté du serveur écoutant sur le port 2020, sa configuration peut ressembler à ceci :

[vpn]
accept = 2020
exec = /usr/sbin/pppd
execArgs = pppd local
pty = yes

Le fichier de configuration suivant peut être utilisé pour lancer le programme stunnel en mode inetd. Il convient de noter qu'il n'y a pas de section [nom_service] dans le fichier de configuration.

exec = /usr/sbin/imapd
execArgs = imapd

[socks_client]
client = yes
accept = 127.0.0.1:1080

La configuration correspondante du serveur vpn_server :

[socks_server]
protocol = socks
accept = 9080
cert = stunnel.pem
key = stunnel.key

curl --socks4a localhost http://www.example.com/

NOTES

LIMITATIONS

stunnel ne peut pas être utilisé pour chiffrer le protocole FTP, car celui-ci utilise des connexions supplémentaires ouvertes sur des ports dont les numéros sont attribués dynamiquement pour le transfert des fichiers individuels. Il existe cependant des versions spéciales de clients et de serveurs FTP qui permettent le chiffrement des données transférées à l'aide du protocole TLS.

MODE INETD (UNIQUEMENT UNIX)

Dans la plupart des cas, stunnel écoute lui-même sur le port spécifié dans le fichier de configuration et établit une connexion vers un autre port spécifié dans l'option connect ou vers un nouveau programme spécifié dans l'option exec. Certains préfèrent cependant utiliser un programme séparé qui reçoit les connexions, puis lance stunnel. Les programmes inetd, xinetd et tcpserver en sont des exemples.

Une ligne typique dans le fichier /etc/inetd.conf pourrait ressembler à ceci :

imaps stream tcp nowait root /usr/bin/stunnel stunnel /etc/stunnel/imaps.conf

Dans de tels cas, la connexion sur le port défini (ici imaps) est établie par un programme séparé (ici inetd), stunnel ne peut donc pas utiliser l'option accept. Aucune section de service ([service_name]) ne peut être définie dans le fichier de configuration, car une telle configuration ne permettrait d'ouvrir qu'une seule connexion. Toutes les OPTIONS DE SERVICE doivent être placées avec les options globales. Un exemple d'une telle configuration se trouve dans la section EXEMPLES.

CERTIFICATS

Le protocole TLS exige que chaque serveur présente un certificat X.509 valide au client qui tente d'établir la connexion. La vérification de l'identité du serveur consiste à prouver que le serveur possède la clé privée correspondant au certificat. La méthode la plus simple pour obtenir un certificat est de le générer à l'aide de la suite logicielle libre OpenSSL. Vous trouverez plus d'informations sur la génération de certificats dans les pages ci-dessous.

Le fichier .pem doit contenir la clé privée et le certificat signé (pas une demande de certificat). Le fichier obtenu doit avoir le format suivant :

-----BEGIN RSA PRIVATE KEY-----
[key encoded]
-----END RSA PRIVATE KEY-----
-----BEGIN CERTIFICATE-----
[certificate encoded]
-----END CERTIFICATE-----

ALÉATOIRITÉ

stunnel a besoin d'initialiser un PRNG (générateur de nombres pseudo-réels) car le protocole TLS nécessite une bonne source d'aléatoirisation pour la sécurité cryptographique. Les sources suivantes sont lues consécutivement jusqu'à ce qu'une quantité suffisante d'entropie soit obtenue :

  • Contenu du fichier spécifié dans l'option RNDfile.
  • Contenu du fichier nommé selon la variable d'étendue RANDFILE, si elle est définie.
  • Le fichier .rnd situé dans le répertoire personnel de l'utilisateur, si la variable RANDFILE n'est pas définie.
  • Le fichier spécifié dans l'option --with-random lors de la configuration du programme.
  • Le contenu de l'écran sous Windows.
  • Le socket egd, si l'option EGD a été utilisée.
  • Le socket egd spécifié dans l'option --with-egd-socket lors de la configuration du programme.
  • Le périphérique /dev/urandom.

Il est important de noter que sur les machines sous Windows où aucun utilisateur n'est connecté à la console, le contenu de l'écran n'est pas suffisamment variable pour initialiser le PRNG. Dans ce cas, l'option RNDfile doit être utilisée pour initialiser le générateur.

Le fichier RNDfile doit contenir des données aléatoires -- y compris dans le sens où elles doivent être différentes à chaque exécution du programme stunnel. Sauf si l'option RNDoverwrite est utilisée, cela est fait automatiquement. La commande openssl rand, fournie avec les versions modernes de la suite logicielle OpenSSL, peut être utile pour obtenir manuellement un tel fichier.

Une autre information importante : si le périphérique /dev/urandom est disponible, la bibliothèque OpenSSL a tendance à l'utiliser pour alimenter le PRNG lors de la vérification de l'état du générateur. Sur les systèmes avec /dev/urandom, ce périphérique sera très probablement utilisé, même s'il se trouve à la toute fin de la liste ci-dessus. C'est une fonctionnalité de la bibliothèque OpenSSL, et non du programme stunnel.

PARAMETRES DH

Depuis la version 4.40, stunnel inclut des paramètres DH de 2048 bits dans le code source. Depuis la version 5.18, ces valeurs initiales des paramètres DH sont remplacées par des paramètres temporaires générés automatiquement. La génération des paramètres DH peut prendre plusieurs minutes.

Alternativement, les paramètres DH peuvent être placés dans le fichier avec le certificat, ce qui désactive la génération de paramètres temporaires :

openssl dhparam 2048 >> stunnel.pem
