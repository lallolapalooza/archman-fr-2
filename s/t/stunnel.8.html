stunnel(8) Proxy TLS stunnel stunnel(8)

NOM

stunnel - Proxy de déchargement et d'équilibrage de charge TLS

SYNTAXE

Unix :
stunnel [FICHIER] | -fd N | -help | -version | -sockets | -options
WIN32 :
stunnel [ [ -install | -uninstall | -start | -stop |
-reload | -reopen | -exit ] [-quiet] [FICHIER] ] |
-help | -version | -sockets | -options

DESCRIPTION

Le programme stunnel est conçu pour fonctionner comme une enveloppe de chiffrement TLS entre des clients distants et des serveurs locaux (démarrables par inetd) ou distants. Le concept est qu'en ayant des démons non-TLS sur votre système, vous pouvez facilement les configurer pour communiquer avec les clients via des canaux sécurisés TLS.

stunnel peut être utilisé pour ajouter des fonctionnalités TLS à des démons couramment utilisés comme les serveurs POP-2, POP-3 et IMAP, à des démons autonomes comme NNTP, SMTP et HTTP, et pour tunneliser PPP sur des sockets réseau sans modifier le code source.

Ce produit inclut un logiciel cryptographique écrit par Eric Young (eay@cryptsoft.com)

FICHIER DE CONFIGURATION

Chaque ligne du fichier de configuration peut être :

  • Une ligne vide (ignorée).
  • Un commentaire commençant par ';' (ignoré).
  • Une paire 'nom_option = valeur_option'.
  • '[nom_service]' indiquant le début d'une définition de service.

Un paramètre d'adresse d'une option peut être :

  • Un numéro de port.
  • Une paire séparée par des deux-points d'une adresse IP (IPv4, IPv6 ou nom de domaine) et d'un numéro de port.
  • Un chemin de socket Unix (Unix uniquement).

OPTIONS GLOBALES

chroot = RÉPERTOIRE (Unix uniquement)
répertoire dans lequel stunnel doit être exécuté en mode chroot

chroot maintient stunnel dans une prison chroot. CApath, CRLpath, pid et exec sont situés à l'intérieur de la prison et les chemins doivent être relatifs au répertoire spécifié avec chroot.

Plusieurs fonctions du système d'exploitation nécessitent également que leurs fichiers soient situés dans la prison chroot, par exemple :

  • Le résolveur retardé nécessite généralement /etc/nsswitch.conf et /etc/resolv.conf.
  • L'heure locale dans les fichiers journaux nécessite /etc/timezone.
  • D'autres fonctions peuvent nécessiter des périphériques, par exemple /dev/zero ou /dev/null.
compression = deflate | zlib
sélectionne l'algorithme de compression des données

par défaut : aucune compression

Deflate est la méthode de compression standard décrite dans la RFC 1951.

debug = [FACILITÉ.]NIVEAU
niveau de débogage

Le niveau est l'un des noms ou numéros de niveau syslog : emerg (0), alert (1), crit (2), err (3), warning (4), notice (5), info (6), ou debug (7). Tous les journaux pour le niveau spécifié et tous les niveaux numériquement inférieurs seront affichés.

Le niveau de journalisation debug (ou l'équivalent <debug = 7>) produit une sortie de journal très détaillée. Ce niveau de journalisation est uniquement destiné aux développeurs de stunnel, et non aux utilisateurs. Veuillez utiliser le niveau de débogage uniquement si un développeur de stunnel vous le demande, ou si vous avez l'intention d'être confus.

Le niveau de journalisation par défaut est notice (5).

La facilité syslog 'daemon' sera utilisée à moins qu'un nom de facilité ne soit fourni. (Les facilités ne sont pas prises en charge sous Win32.)

La casse est ignorée pour les facilités et les niveaux.

EGD = CHEMIN_EGD (Unix uniquement)
chemin du socket du démon de collecte d'entropie

Socket du démon de collecte d'entropie à utiliser pour alimenter le générateur de nombres aléatoires OpenSSL.

engine = auto | ENGINE_ID
sélectionne le moteur cryptographique matériel ou logiciel

par défaut : cryptographie uniquement logicielle

Voir la section Exemples pour une configuration de moteur permettant d'utiliser le certificat et la clé privée correspondante à partir d'un périphérique cryptographique.

engineCtrl = COMMANDE[:PARAMÈTRE]
contrôle le moteur matériel
engineDefault = LISTE_TÂCHES
définit les tâches OpenSSL déléguées au moteur courant

Le paramètre spécifie une liste de tâches séparées par des virgules à déléguer au moteur courant.

Les tâches suivantes peuvent être disponibles, si elles sont prises en charge par le moteur : ALL, RSA, DSA, ECDH, ECDSA, DH, RAND, CIPHERS, DIGESTS, PKEY, PKEY_CRYPTO, PKEY_ASN1.

fips = oui | non
active ou désactive le mode FIPS 140-2.

Cette option vous permet de désactiver le passage en mode FIPS si stunnel a été compilé avec le support FIPS 140-2.

par défaut : non (depuis la version 5.00)

foreground = oui | quiet | non (Unix uniquement)
mode premier plan

Rester en premier plan (ne pas forker).

Avec le paramètre oui, il journalise également vers stderr en plus des destinations spécifiées avec syslog et output.

par défaut : arrière-plan en mode démon

iconActive = FICHIER_ICONE (GUI uniquement)
icône de l'interface graphique à afficher lorsqu'il y a des connexions établies

Sur la plateforme Windows, le paramètre doit être un fichier .ico contenant une image de 16x16 pixels.

iconError = FICHIER_ICONE (GUI uniquement)
icône de l'interface graphique à afficher lorsqu'aucune configuration valide n'est chargée

Sur la plateforme Windows, le paramètre doit être un fichier .ico contenant une image de 16x16 pixels.

iconIdle = FICHIER_ICONE (GUI uniquement)
icône de l'interface graphique à afficher lorsqu'il n'y a pas de connexions établies

Sur la plateforme Windows, le paramètre doit être un fichier .ico contenant une image de 16x16 pixels.

log = appen
append
d | overwrite
gestion du fichier journal

Cette option vous permet de choisir si le fichier journal (spécifié avec l'option output) doit être ajouté ou écrasé lors de son ouverture ou de sa réouverture.

par défaut : append

output = FILE
ajouter les messages du journal dans un fichier

Le périphérique /dev/stdout peut être utilisé pour envoyer les messages du journal vers la sortie standard (par exemple, pour les enregistrer avec le splogger de daemontools).

pid = FICHIER (Unix seulement)
emplacement du fichier pid

Si l'argument est vide, aucun fichier pid ne sera créé.

Le chemin pid est relatif au répertoire chroot s'il est spécifié.

provider = ID_FOURNISSEUR
Spécifie l'identifiant du fournisseur à utiliser. ID_FOURNISSEUR est un identifiant unique faisant référence à un fournisseur de services cryptographiques spécifique.

Cette option nécessite OpenSSL 3.0 ou une version ultérieure.

Définit un paramètre spécifique pour le fournisseur donné. ID_FOURNISSEUR identifie le fournisseur, PARAMÈTRE est le nom du paramètre et VALEUR est sa valeur. Cette option permet de personnaliser la configuration du fournisseur de services cryptographiques sélectionné.

Cette option nécessite OpenSSL 3.5 ou une version ultérieure.

RNDbytes = OCTETS
octets à lire depuis les fichiers de seed aléatoire
RNDfile = FICHIER
chemin vers le fichier contenant les données de seed aléatoire

La bibliothèque OpenSSL utilisera d'abord les données de ce fichier pour initialiser le générateur de nombres aléatoires.

RNDoverwrite = oui | non
écraser les fichiers de seed aléatoire avec de nouvelles données aléatoires

par défaut : oui

service = SERVICE (Unix seulement)
nom du service stunnel

Le nom de service spécifié est utilisé pour syslog et comme nom de service pour le mode inetd pour TCP Wrappers. Bien que cette option puisse techniquement être spécifiée dans les sections de service, elle n'est utile que dans les options globales.

par défaut : stunnel

setEnv = NOM_VAR=VALEUR
Modifie ou ajoute une variable d'environnement pour les processus enfants. Si NOM_VAR existe déjà, sa valeur sera mise à jour ; sinon, une nouvelle variable sera créée. Cette modification s'applique uniquement aux processus enfants lancés et n'affecte pas l'environnement actuel.
syslog = oui | non (Unix seulement)
activer la journalisation via syslog

par défaut : oui

taskbar = oui | non (WIN32 seulement)
activer l'icône de la barre des tâches

par défaut : oui

OPTIONS DE NIVEAU DE SERVICE

Chaque section de configuration commence par un nom de service entre crochets. Le nom de service est utilisé pour le contrôle d'accès libwrap (TCP Wrappers) et vous permet de distinguer les services stunnel dans vos fichiers journaux.

Notez que si vous souhaitez exécuter stunnel en mode inetd (où il reçoit un socket réseau d'un serveur tel que inetd, xinetd ou tcpserver), vous devez lire la section intitulée MODE INETD ci-dessous.

accept = [HÔTE:]PORT
accepter les connexions sur l'adresse spécifiée

Si aucun hôte n'est spécifié, la valeur par défaut est toutes les adresses IPv4 de l'hôte local.

Pour écouter sur toutes les adresses IPv6, utilisez :

accept = :::PORT
CAengine = IDENTIFIANT_CERTIFICAT_CA_SPÉCIFIQUE_MOTEUR
charger un certificat d'autorité de certification (CA) de confiance à partir d'un moteur

Les certificats CA chargés seront utilisés avec les options verifyChain et verifyPeer.

Plusieurs options CAengine sont autorisées dans une même section de service.

Moteurs actuellement pris en charge : pkcs11, cng.

CApath = RÉPERTOIRE_CA
charger les certificats CA de confiance à partir d'un répertoire

Les certificats CA chargés seront utilisés avec les options verifyChain et verifyPeer. Notez que les certificats de ce répertoire doivent être nommés XXXXXXXX.0 où XXXXXXXX est la valeur de hachage du sujet du certificat encodé en DER.

Ce paramètre peut également être utilisé pour fournir le certificat CA racine nécessaire à la validation de l'agrafage OCSP en mode serveur.

L'algorithme de hachage a été modifié dans OpenSSL 1.0.0. Il est nécessaire de rehacher le répertoire (c_rehash) lors de la mise à niveau d'OpenSSL 0.x.x vers OpenSSL 1.x.x ou une version ultérieure.

Le chemin CApath est relatif au répertoire chroot s'il est spécifié.

CAfile = FICHIER_CA
charger les certificats CA de confiance à partir d'un fichier

Les certificats CA chargés seront utilisés avec les options verifyChain et verifyPeer.

Ce paramètre peut également être utilisé pour fournir le certificat CA racine nécessaire à la validation de l'agrafage OCSP en mode serveur.

CAstore = URI_CA
charger les certificats CA de confiance à partir d'une ressource spécifiée par une URI

Cette option permet de charger des certificats CA à partir d'une source externe prise en charge par le framework OSSL_STORE, tel qu'un module PKCS#11 (par exemple, un token matériel), le magasin de certificats système ou une ressource distante.

Cette option peut être utilisée indépendamment de CAfile et CAdir, et fournit de manière similaire les certificats utilisés par verifyChain ou verifyPeer, ainsi que pour la validation de l'agrafage OCSP en mode serveur.

Cette option nécessite OpenSSL 3.0 ou une version ultérieure.

cert = FICHIER_CERT | URI
nom du fichier de chaîne de certificats

Le paramètre spécifie le fichier contenant les certificats utilisés par stunnel pour s'authentifier auprès du client ou du serveur distant. Le fichier doit contenir toute la chaîne de certificats, en commençant par le certificat réel du serveur/client et en terminant par le certificat CA racine auto-signé. Le fichier doit être au format PEM ou P12.

Une chaîne de certificats est requise en mode serveur, et facultative en mode client.

L'option cert peut être spécifiée plusieurs fois. Le premier certificat rencontré est utilisé comme certificat serveur ou client, tandis que tout certificat ultérieur est traité comme un élément de chaîne intermédiaire. Cette fonctionnalité nécessite la version d'OpenSSL 1.0.2 ou une version ultérieure.

Ce paramètre est également utilisé comme identifiant de certificat (URI PKCS#11) lorsqu'un moteur ou un fournisseur matériel est activé.

Note : Le fournisseur nécessite OpenSSL 3.0 ou une version ultérieure

checkEmail = EMAIL
vérifier l'adresse e-mail du sujet du certificat du pair entité finale (feuille)

Les certificats sont acceptés si aucune vérification de sujet n'a été spécifiée, ou si l'adresse e-mail du certificat du pair entité finale (feuille) correspond à l'une des adresses e-mail spécifiées avec checkEmail.

Plusieurs options checkEmail sont autorisées dans une même section de service.

Cette option nécessite OpenSSL 1.0.2 ou une version ultérieure.

checkHost = HÔTE
vérifier l'hôte du sujet du certificat du pair entité finale (feuille)

Les certificats sont acceptés si aucune vérification de sujet n'a été spécifiée, ou si le nom d'hôte du certificat du pair entité finale (feuille) correspond à l'un des hôtes spécifiés avec checkHost.

Plusieurs options checkHost sont autorisées dans une même section de service.

Cette option nécessite OpenSSL 1.0.2 ou une version ultérieure.

checkIP = IP
vérifier l'adresse IP du sujet du certificat du pair entité finale (feuille)

Les certificats sont acceptés si aucune vérification de sujet n'a été spécifiée, ou si l'adresse IP du certificat du pair entité finale (feuille) correspond à l'une des adresses IP spécifiées avec checkIP.

Plusieurs options checkIP sont autorisées dans une même section de service.

Cette option nécessite OpenSSL 1.0.2 ou une version ultérieure.

ciphers = LISTE_CHIFFREMENTS
sélectionner les chiffrements TLS autorisés (TLSv1.2 et inférieur)

Cette option n'a pas d'impact sur les suites de chiffrement TLSv1.3.

Une liste de chiffrements délimitée par des deux-points à autoriser dans la connexion TLS, par exemple DES-CBC3-SHA:IDEA-CBC-MD5.

ciphersuites = LISTE_SUITES_CHIFFREMENT
sélectionner les suites de chiffrement TLSv1.3 autorisées

Une liste de noms de suites de chiffrement TLSv1.3 délimitée par des deux-points, par ordre de préférence.

L'option ciphersuites ignore les chiffrements inconnus lorsqu'elle est compilée avec OpenSSL 3.0 ou une version ultérieure.

Cette option nécessite OpenSSL 1.1.1 ou une version ultérieure.

par défaut : TLS_CHACHA20_POLY1305_SHA256:TLS_AES_256_GCM_SHA384:TLS_AES_128_GCM_SHA256

client = oui | non
mode client (service distant utilise TLS)

par défaut : non (mode serveur)

config = COMMANDE[:PARAMÈTRE]
commande de configuration OpenSSL

La commande de configuration OpenSSL est exécutée avec le paramètre spécifié. Cela permet d'appeler toute commande de configuration depuis le fichier de configuration stunnel. Les commandes prises en charge sont décrites dans la page de manuel SSL_CONF_cmd(3ssl).

Plusieurs lignes config peuvent être utilisées pour spécifier plusieurs commandes de configuration.

Utilisez l'option curves au lieu d'activer config = Curves:list_curves pour prendre en charge les courbes elliptiques.

Cette option nécessite OpenSSL 1.0.2 ou une version ultérieure.

connect = [HÔTE:]PORT
se connecter à une adresse distante

Si aucun hôte n'est spécifié, l'hôte par défaut est localhost.

Plusieurs options connect sont autorisées dans une seule section de service. Si l'hôte se résout en plusieurs adresses et/ou si plusieurs options connect sont spécifiées, alors l'adresse distante est choisie selon un algorithme de round-robin.

CRLpath = RÉPERTOIRE
Répertoire des listes de révocation de certificats

Il s'agit du répertoire dans lequel stunnel recherchera les CRL lors de l'utilisation des options verifyChain et verifyPeer. Notez que les CRL de ce répertoire doivent être nommées XXXXXXXX.r0 où XXXXXXXX est la valeur de hachage de la CRL.

L'algorithme de hachage a été modifié dans OpenSSL 1.0.0. Il est nécessaire de ré-hacher le répertoire lors de la mise à niveau de OpenSSL 0.x.x vers OpenSSL 1.x.x.

Le chemin CRLpath est relatif au répertoire chroot s'il est spécifié.

CRLfile = FICHIER_CRL
Fichier des listes de révocation de certificats

Ce fichier contient plusieurs CRL, utilisées avec les options verifyChain et verifyPeer.

curves = liste
Courbes ECDH séparées par ':'

Un seul nom de courbe est autorisé pour OpenSSL avant la version 1.1.1.

Pour obtenir une liste des courbes prises en charge, utilisez :

openssl ecparam -list_curves

par défaut :

X25519:P-256:X448:P-521:P-384 (OpenSSL 1.1.1 ou ultérieur)
prime256v1 (OpenSSL avant 1.1.1)
logId = TYPE
type d'identifiant de connexion

Cet identifiant vous permet de distinguer les entrées de journal générées pour chacune des connexions.

Types actuellement pris en charge :

sequential
L'identifiant séquentiel numérique n'est unique que dans une seule instance de stunnel, mais très compact. Il est très utile pour l'analyse manuelle des journaux.
unique
Cet identifiant alphanumérique est globalement unique, mais plus long que le numéro séquentiel. Il est très utile pour l'analyse automatisée des journaux.
thread
L'identifiant de thread du système d'exploitation n'est ni unique (même dans une seule instance de stunnel) ni court. Il est très utile pour le débogage logiciel ou de configuration.
process
L'identifiant de processus du système d'exploitation (PID) peut être utile en mode inetd.

par défaut : sequential

debug = NIVEAU
niveau de débogage

Le niveau est l'un des noms ou numéros de niveau syslog : emerg (0), alert (1), crit (2), err (3), warning (4), notice (5), info (6), ou debug (7). Tous les journaux pour le niveau spécifié et tous les niveaux numériquement inférieurs seront affichés. Le niveau par défaut est notice (5).

Bien que le niveau debug = debug ou debug = 7 génère la sortie la plus détaillée, il est uniquement destiné aux développeurs de stunnel. Veuillez n'utiliser cette valeur que si vous êtes un développeur, ou si vous avez l'intention d'envoyer vos journaux à notre support technique. Sinon, les journaux générés seront déroutants.

delay = yes | no
retarder la résolution DNS pour l'option connect

Cette option est utile pour le DNS dynamique, ou lorsque le DNS n'est pas disponible lors du démarrage de stunnel (VPN pour voyageurs, configurations de modem).

Le mode de résolution retardée est automatiquement activé lorsque stunnel ne parvient pas à résoudre au démarrage l'une des cibles connect pour un service.

Le résolveur retardé impose failover = prio.

par défaut : no

engineId = ID_MOTEUR
sélectionner l'ID du moteur pour le service
engineNum = NUMÉRO_MOTEUR
sélectionner le numéro du moteur pour le service

Les moteurs sont numérotés à partir de 1.

exec = CHEMIN_EXÉCUTABLE
exécuter un programme local de type inetd

Le chemin exec est relatif au répertoire chroot s'il est spécifié.

Les variables d'environnement suivantes sont définies sur les plateformes Unix : REMOTE_HOST, REMOTE_PORT, SSL_CLIENT_DN, SSL_CLIENT_I_DN.

execArgs = $0 $1 $2 ...
arguments pour exec y compris le nom du programme ($0)

L'échappement n'est actuellement pas pris en charge. Les arguments sont séparés par une quantité arbitraire d'espaces blancs.

failover = rr | prio
Stratégie de basculement pour plusieurs cibles "connect".
rr
round robin - distribution de charge équitable
prio
priorité - utiliser l'ordre spécifié dans le fichier de configuration

par défaut : prio

ident = NOM_UTILISATEUR
utiliser la vérification du nom d'utilisateur IDENT (RFC 1413)
include = RÉPERTOIRE
inclure toutes les parties du fichier de configuration situées dans le RÉPERTOIRE

Les fichiers sont inclus dans l'ordre alphabétique ascendant de leurs noms. La convention de nommage recommandée est

pour les options globales :

00-global.conf

pour les options locales au niveau du service :

01-service.conf
02-service.conf
key = FICHIER_CLÉ | URI
clé privée pour le certificat spécifié avec l'option cert

Une clé privée est nécessaire pour authentifier le propriétaire du certificat. Comme ce fichier doit rester secret, il ne devrait être lisible que par son propriétaire. Sur les systèmes Unix, vous pouvez utiliser la commande suivante :

chmod 600 fichier_cle

Ce paramètre est également utilisé comme identifiant de clé privée (URI PKCS#11) lorsqu'un moteur matériel ou un fournisseur est activé.

Note : le fournisseur nécessite OpenSSL 3.0 ou ultérieur

par défaut : la valeur de l'option cert

libwrap = yes | no
Activer ou désactiver l'utilisation de /etc/hosts.allow et /etc/hosts.deny.

par défaut : no (depuis la version 5.00)

local = HÔTE
Par défaut, l'adresse IP de l'interface sortante est utilisée comme source pour les connexions distantes. Utilisez cette option pour lier une adresse IP locale statique à la place.
OCSP = URL
sélectionner le répondeur OCSP pour la vérification du certificat de l'entité finale (feuille)
OCSPaia = yes | no
valider les certificats avec leurs répondeurs OCSP AIA

Cette option permet à stunnel de valider les certificats avec la liste des URL des répondeurs OCSP récupérées de leur extension AIA (Authority Information Access).

OCSPflag = DRAPEAU_OCSP
spécifier le drapeau du répondeur OCSP

Plusieurs OCSPflag peuvent être utilisés pour spécifier plusieurs drapeaux.

drapeaux actuellement pris en charge : NOCERTS, NOINTERN, NOSIGS, NOCHAIN, NOVERIFY, NOEXPLICIT, NOCASIGN, NODELEGATED, NOCHECKS, TRUSTOTHER, RESPID_KEY, NOTIME

OCSPnonce = yes | no
envoyer et vérifier l'extension nonce OCSP

Cette option protège le protocole OCSP contre les attaques par rejeu. En raison de sa surcharge calculatoire, l'extension nonce n'est généralement prise en charge que sur les répondeurs internes (par exemple, en entreprise), et non sur les répondeurs OCSP publics.

OCSPrequire = yes | no
exiger une réponse OCSP conclusive

Désactivez cette option pour autoriser une connexion même si aucune réponse OCSP conclusive n'a été récupérée via le stapling et une requête directe au répondeur OCSP.

par défaut : yes

options = OPTIONS_SSL
options de la bibliothèque OpenSSL

Le paramètre est le nom de l'option OpenSSL tel que décrit dans la page de manuel SSL_CTX_set_options(3ssl), mais sans le préfixe SSL_OP_. stunnel -options liste les options autorisées dans la combinaison actuelle de stunnel et de la bibliothèque OpenSSL utilisée pour sa compilation.

Plusieurs lignes option peuvent être utilisées pour spécifier plusieurs options. Un nom d'option peut être précédé d'un tiret ("-") pour désactiver l'option.

Par exemple, pour la compatibilité avec l'implémentation erronée de TLS d'Eudora, l'option suivante peut être utilisée :

options = DONT_INSERT_EMPTY_FRAGMENTS

par défaut :

options = NO_SSLv2
options = NO_SSLv3

Utilisez l'option sslVersionMax ou sslVersionMin au lieu de désactiver des versions de protocole TLS spécifiques lors de la compilation avec OpenSSL 1.1.0 ou ultérieur.

protocol = PROTO
protocole applicatif pour négocier TLS

Cette option active la négociation initiale spécifique au protocole du chiffrement TLS. L'option protocol ne doit pas être utilisée avec le chiffrement TLS sur un port séparé.

Protocoles actuellement pris en charge :

cifs
Extension propriétaire (non documentée) du protocole CIFS implémentée dans Samba. Le support de cette extension a été abandonné dans Samba 3.0.0.
capwin
support de l'application http://www.capwin.org/
capwinctrl
http://www.capwin.org/ prise en charge de l'application

Ce protocole n'est pris en charge qu'en mode client.

connect
Basé sur la RFC 2817 - Upgrading to TLS Within HTTP/1.1, section 5.2 - Requesting a Tunnel with CONNECT

Ce protocole n'est pris en charge qu'en mode client.

imap
Basé sur la RFC 2595 - Using TLS with IMAP, POP3 and ACAP
ldap
Basé sur la RFC 2830 - Lightweight Directory Access Protocol (v3): Extension for Transport Layer Security
nntp
Basé sur la RFC 4642 - Using Transport Layer Security (TLS) with Network News Transfer Protocol (NNTP)

securityLevel = NIVEAU
définir le niveau de sécurité

La signification de chaque niveau est décrite ci-dessous :

niveau 0
Tout est autorisé.
niveau 1
Le niveau de sécurité correspond à un minimum de 80 bits de sécurité. Tous les paramètres offrant moins de 80 bits de sécurité sont exclus. Par conséquent, les clés RSA, DSA et DH de moins de 1024 bits et les clés ECC de moins de 160 bits sont interdites. Tous les chiffrements d'exportation sont interdits car ils offrent tous moins de 80 bits de sécurité. SSL version 2 est interdit. Tout chiffrement utilisant MD5 pour le MAC est également interdit. De plus, SSLv3, TLS 1.0, TLS 1.1 sont tous désactivés pour OpenSSL 3.0 et versions ultérieures.
niveau 2
Niveau de sécurité défini à 112 bits de sécurité. Par conséquent, les clés RSA, DSA et DH de moins de 2048 bits et les clés ECC de moins de 224 bits sont interdites. En plus des exclusions du niveau 1, tout chiffrement utilisant RC4 est également interdit. La compression est désactivée. SSL version 3 n'est pas non plus autorisé pour OpenSSL antérieur à 3.0.
niveau 3
Niveau de sécurité défini à 128 bits de sécurité. Par conséquent, les clés RSA, DSA et DH de moins de 3072 bits et les clés ECC de moins de 256 bits sont interdites. En plus des exclusions du niveau 2, les chiffrements n'offrant pas de secret parfait sont interdits. Les tickets de session sont désactivés. Les versions TLS inférieures à 1.1 ne sont pas autorisées pour OpenSSL antérieur à 3.0.
niveau 4
Niveau de sécurité défini à 192 bits de sécurité. Par conséquent, les clés RSA, DSA et DH de moins de 7680 bits et les clés ECC de moins de 384 bits sont interdites. Les chiffrements utilisant SHA1 pour le MAC sont interdits. Les versions TLS inférieures à 1.2 ne sont pas autorisées pour OpenSSL antérieur à 3.0.
niveau 5
Niveau de sécurité défini à 256 bits de sécurité. Par conséquent, les clés RSA, DSA et DH de moins de 15360 bits et les clés ECC de moins de 512 bits sont interdites.
par défaut : 2

L'option securityLevel n'est disponible que lorsqu'elle est compilée avec OpenSSL 1.1.0 et versions ultérieures.

VALEUR DE RETOUR

stunnel retourne zéro en cas de succès, une valeur non nulle en cas d'erreur.

SIGNAUX

Les signaux suivants peuvent être utilisés pour contrôler stunnel dans l'environnement Unix :

SIGHUP
Forcer le rechargement du fichier de configuration.

Certaines options globales ne seront pas rechargées :

  • chroot
  • foreground
  • pid
  • setgid
  • setuid

L'utilisation de l'option 'setuid' empêchera également stunnel de se lier à des ports privilégiés (<1024) lors du rechargement de la configuration.

Lorsque l'option 'chroot' est utilisée, stunnel recherchera tous ses fichiers (y compris le fichier de configuration, les certificats, le fichier de log et le fichier pid) dans la prison chroot.

SIGUSR1
Fermer et rouvrir le fichier de log de stunnel. Cette fonction peut être utilisée pour la rotation des logs.
SIGUSR2
Journaliser la liste des connexions actives.
SIGTERM, SIGQUIT, SIGINT
Arrêter stunnel.

Le résultat de l'envoi de tout autre signal au serveur est indéfini.

EXEMPLES

Pour fournir un encapsulage TLS à votre service local imapd, utilisez :

[imapd]
accept = 993
exec = /usr/sbin/imapd
execArgs = imapd

ou en mode distant :

[imapd]
accept = 993
connect = 143

Pour permettre à votre client de messagerie local de se connecter à un service imapd activé pour TLS sur un autre serveur, configurez le client de messagerie pour qu'il se connecte à localhost sur le port 119 et utilisez :

[imap]
client = oui
accept = 143
connect = nom_serveur:993

Si vous souhaitez fournir un tunneling à votre démon pppd sur le port 2020, utilisez quelque chose comme :

[vpn]
accept = 2020
exec = /usr/sbin/pppd
execArgs = pppd local
pty = oui

Si vous souhaitez utiliser stunnel en mode inetd pour lancer votre processus imapd, vous utiliseriez ce stunnel.conf. Notez qu'il ne doit y avoir aucune section [nom_service].

exec = /usr/sbin/imapd
execArgs = imapd

Pour configurer un VPN SOCKS, configurez le service client suivant :

[client_socks]
client = oui
accept = 127.0.0.1:1080
connect = serveur_vpn:9080
verifyPeer = oui
CAfile = stunnel.pem

La configuration correspondante sur l'hôte serveur_vpn :

[serveur_socks]
protocol = socks
accept = 9080
cert = stunnel.pem
key = stunnel.key

Testez maintenant votre configuration sur la machine cliente avec :

curl --socks4a localhost http://www.example.com/

Un exemple de configuration SNI côté serveur :

[virtuel]
; service principal
accept = 443
cert =  défaut.pem
connect = virtuel.interne.mondomaine.com:8080
[sni1]
; service secondaire 1
sni = virtuel:serveur1.mondomaine.com
cert = serveur1.pem
connect = serveur1.interne.mondomaine.com:8081
[sni2]
; service secondaire 2
sni = virtuel:serveur2.mondomaine.com
cert = serveur2.pem
connect = serveur2.interne.mondomaine.com:8082
verifyPeer = oui
CAfile = serveur2-clients-autorises.pem

Un exemple de configuration avancée de moteur permet une authentification avec des clés privées stockées dans le magasin de certificats Windows (Windows uniquement). Avec le moteur CAPI, vous n'avez pas besoin de sélectionner manuellement la clé client à utiliser. La clé client est automatiquement sélectionnée en fonction de la liste des AC approuvées par le serveur.

engine = capi
[service]
engineId = capi
client = oui
accept = 127.0.0.1:8080
connect = example.com:8443

engine = pkcs11
engineCtrl = MODULE_PATH:opensc-pkcs11.so

[service]

client = oui
accept = 127.0.0.1:8080
connect = example.com:843

engine = pkcs11

[service]

NOTES

RESTRICTIONS

stunnel ne peut pas être utilisé pour le démon FTP en raison de la nature du protocole FTP qui utilise plusieurs ports pour les transferts de données. Il existe cependant des versions activées pour TLS des démons FTP et telnet.

MODE INETD

L'utilisation la plus courante de stunnel est d'écouter sur un port réseau et d'établir une communication soit avec un nouveau port via l'option connect, soit avec un nouveau programme via l'option exec. Cependant, il existe un cas particulier lorsque vous souhaitez qu'un autre programme accepte les connexions entrantes et lance stunnel, par exemple avec inetd, xinetd, ou tcpserver.

Par exemple, si vous avez la ligne suivante dans inetd.conf :

imaps stream tcp nowait root /usr/bin/stunnel stunnel /etc/stunnel/imaps.conf

Dans ces cas, le programme de style inetd est responsable de la liaison d'une socket réseau (imaps ci-dessus) et de la remise à stunnel lorsqu'une connexion est reçue. Ainsi, vous ne voulez pas que stunnel ait d'option accept. Toutes les Options au Niveau du Service doivent être placées dans la section des options globales, et aucune section [nom_service] ne sera présente. Voir la section EXEMPLES pour des exemples de configurations.

CERTIFICATS

Chaque démon activé pour TLS doit présenter un certificat X.509 valide au pair. Il a également besoin d'une clé privée pour déchiffrer les données entrantes. La manière la plus simple d'obtenir un certificat et une clé est de les générer avec le package gratuit OpenSSL. Vous pouvez trouver plus d'informations sur la génération de certificats sur les pages listées ci-dessous.

Le fichier .pem doit contenir la clé privée non chiffrée et un certificat signé (pas une demande de certificat). Le fichier doit donc ressembler à ceci :

-----BEGIN RSA
-----BEGIN RSA PRIVATE KEY----- [clé encodée] -----END RSA PRIVATE KEY----- -----BEGIN CERTIFICATE----- [certificat encodé] -----END CERTIFICATE-----

ALÉATOIRE

stunnel a besoin d'initialiser le PRNG (générateur de nombres pseudo-aléatoires) pour que TLS puisse utiliser une bonne source d'aléatoire. Les sources suivantes sont chargées dans l'ordre jusqu'à ce qu'une quantité suffisante de données aléatoires ait été collectée :

  • Le fichier spécifié par l'indicateur RNDfile.
  • Le fichier spécifié par la variable d'environnement RANDFILE, s'il est défini.
  • Le fichier .rnd dans votre répertoire personnel, si RANDFILE n'est pas défini.
  • Le fichier spécifié avec '--with-random' lors de la compilation.
  • Le contenu de l'écran sous Windows.
  • Le socket EGD spécifié par l'indicateur EGD.
  • Le socket EGD spécifié avec '--with-egd-sock' lors de la compilation.
  • Le périphérique /dev/urandom.

Notez que sur les machines Windows qui n'ont pas d'interaction avec l'utilisateur du console (mouvements de souris, création de fenêtres, etc.), le contenu de l'écran n'est pas suffisamment variable pour être suffisant, et vous devriez fournir un fichier aléatoire à utiliser avec l'indicateur RNDfile.

Notez que le fichier spécifié par l'indicateur RNDfile doit contenir des données aléatoires -- cela signifie qu'il doit contenir des informations différentes à chaque exécution de stunnel. Ceci est géré automatiquement à moins que l'indicateur RNDoverwrite ne soit utilisé. Si vous souhaitez mettre à jour ce fichier manuellement, la commande openssl rand des versions récentes d'OpenSSL peut être utile.

Note importante : Si /dev/urandom est disponible, OpenSSL l'utilise souvent pour initialiser le PRNG lors de la vérification de l'état aléatoire. Sur les systèmes avec /dev/urandom, OpenSSL est susceptible de l'utiliser bien qu'il soit listé tout en bas de la liste ci-dessus. C'est le comportement d'OpenSSL et non de stunnel.

PARAMETRES DH

stunnel 4.40 et versions ultérieures contiennent des paramètres DH 2048 bits codés en dur. À partir de stunnel 5.18, ces paramètres DH codés en dur sont remplacés toutes les 24 heures par des paramètres DH temporaires générés automatiquement. La génération de paramètres DH peut prendre plusieurs minutes.

Alternativement, il est possible de spécifier des paramètres DH statiques dans le fichier de certificat, ce qui désactive la génération de paramètres DH temporaires :

openssl dhparam 2048 >> stunnel.pem
