NOM

stap-server - gestion du serveur de compilation systemtap

SYNTAXE

[ service ] stap-server { start | stop | restart | condrestart | try-restart | force-reload | status } [ options ]

DESCRIPTION

Un serveur de compilation systemtap écoute les connexions des clients stap sur un port réseau sécurisé SSL et accepte les requêtes d'exécution du module frontal stap. Chaque serveur annonce sa présence et sa configuration sur le réseau local en utilisant mDNS (avahi) ce qui permet une détection automatique par les clients.

Le script stap-server vise à fournir :

  • la gestion des serveurs de compilation systemtap en tant que service.
  • un contrôle pratique sur les serveurs configurés et les serveurs individuels (ad hoc).

ARGUMENTS

Une des actions ci-dessous doit être spécifiée :

start
Démarre les serveurs. Les serveurs spécifiés sont démarrés. Si aucun serveur n'est spécifié, les serveurs configurés sont démarrés. Si aucun serveur n'est configuré, un serveur pour la version du noyau et l'architecture de l'hôte est démarré. Si un serveur spécifié est déjà démarré, cette action sera ignorée pour ce serveur. Si un serveur ne parvient pas à démarrer, cette action échoue.
stop
Arrête le(s) serveur(s). Les serveurs spécifiés sont arrêtés. Si aucun serveur n'est spécifié, tous les serveurs en cours d'exécution sont arrêtés. Si un serveur spécifié n'est pas en cours d'exécution, cette action réussira pour ce serveur. Si un serveur ne parvient pas à s'arrêter, cette action échoue.
restart
Arrête et redémarre les serveurs. Les serveurs spécifiés sont arrêtés puis redémarrés. Si aucun serveur n'est spécifié, tous les serveurs en cours d'exécution sont arrêtés puis redémarrés. Si aucun serveur n'est en cours d'exécution, cette action se comporte comme start.
condrestart
Arrête et redémarre les serveurs. Les serveurs spécifiés sont arrêtés puis redémarrés. Si un serveur spécifié n'est pas en cours d'exécution, il n'est pas démarré. Si aucun serveur n'est spécifié, tous les serveurs en cours d'exécution sont arrêtés puis redémarrés. Si aucun serveur n'est en cours d'exécution, aucun ne sera démarré.
try-restart
Cette action est identique à condrestart.
force-reload
Arrête tous les serveurs en cours d'exécution, recharge les fichiers de configuration et redémarre le service comme si start avait été spécifié.
status
Affiche des informations sur les serveurs en cours d'exécution. Des informations sur le(s) serveur(s) spécifié(s) seront affichées. Si aucun serveur n'est spécifié, des informations sur tous les serveurs en cours d'exécution seront affichées.

OPTIONS

Les options suivantes sont utilisées pour fournir une configuration supplémentaire et pour spécifier les serveurs à gérer :

-c fichier-config
Cette option spécifie un fichier de configuration global en plus du fichier de configuration global par défaut décrit ci-dessous. Ce fichier sera traité après le fichier de configuration global par défaut. Si l'option -c est spécifiée plus d'une fois, le dernier fichier de configuration spécifié sera utilisé.
-a architecture
Cette option spécifie l'architecture cible du serveur et est analogue à l'option -a de stap. Voir la page de manuel stap(1) pour plus de détails. L'architecture par défaut est celle de l'hôte.
-r version-noyau
Cette option spécifie une version de noyau cible pour le serveur et est analogue à l'option -r de stap. Voir la page de manuel stap(1) pour plus de détails. La version par défaut est celle du noyau en cours d'exécution. Un serveur peut gérer plusieurs versions en spécifiant plusieurs indicateurs -r.
-I chemin
Cette option spécifie un chemin supplémentaire à rechercher par le(s) serveur(s) pour les tapsets et est analogue à l'option -I de stap. Voir la page de manuel stap(1) pour plus de détails.
-R chemin
Cette option spécifie l'emplacement de l'exécution systemtap à utiliser par le(s) serveur(s) et est analogue à l'option -R de stap. Voir la page de manuel stap(1) pour plus de détails.
-B options
Cette option spécifie les options à passer à make lors de la compilation des modules systemtap et est analogue à l'option -B de stap. Voir la page de manuel stap(1) pour plus de détails.
-i
Cette option est un raccourci qui spécifie un serveur qui gère toutes les versions installées dans /lib/modules/.
-n nom-surnom
Cette option permet de spécifier une configuration de serveur par surnom. Lorsque -n est spécifié, un serveur en cours d'exécution avec le surnom donné sera recherché. Si aucun serveur en cours d'exécution avec ce surnom n'est trouvé, une configuration de serveur avec ce surnom sera recherchée dans les fichiers de configuration pour les serveurs par défaut, ou dans le chemin configuré dans le fichier de configuration global ou le fichier de configuration spécifié par l'option -c. Si une configuration de serveur pour le surnom donné est trouvée, les options -a, -r, -I, -R, -B et -u pour ce serveur seront utilisées comme si elles avaient été spécifiées sur la ligne de commande. Si aucune configuration avec le surnom donné n'est trouvée, et que l'action est start (ou une action se comportant comme start (voir ARGUMENTS), le serveur sera démarré avec le surnom donné. Si aucun surnom n'est spécifié pour un serveur en cours de démarrage, son surnom sera son identifiant de processus.
-p pid
Cette option permet de spécifier une configuration de serveur par identifiant de processus. Lorsque -p est spécifié, un serveur en cours d'exécution avec l'identifiant de processus donné sera recherché. Si aucun serveur de ce type n'est trouvé, c'est une erreur. Si un serveur avec l'identifiant de processus donné est trouvé, les options -a, -r, -I, -R, -B et -u pour ce serveur seront utilisées comme si elles avaient été spécifiées sur la ligne de commande.
-u nom-utilisateur
Chaque serveur de compilation systemtap est normalement exécuté par le nom d'utilisateur stap-server (pour le script d'initialisation) ou par l'utilisateur qui invoque stap-server, sauf configuration contraire (voir FICHIERS). Cette option spécifie le nom d'utilisateur utilisé pour exécuter le(s) serveur(s). Le nom d'utilisateur spécifié doit être membre du groupe stap-server.
--log fichier-journal
Cette option permet de spécifier un fichier journal séparé pour chaque serveur. Chaque option --log est ajoutée à une liste qui sera appliquée, à tour de rôle, à chaque serveur spécifié. S'il y a plus de serveurs spécifiés que d'options --log, le fichier journal par défaut (voir FICHIERS) sera utilisé pour les serveurs suivants.
--port numéro-port
Cette option permet de spécifier un port réseau spécifique pour chaque serveur. Chaque option --port est ajoutée à une liste qui sera appliquée, à tour de rôle, à chaque serveur spécifié. S'il y a plus de serveurs spécifiés que d'options --port, un port sélectionné aléatoirement est utilisé pour les serveurs suivants.
--ssl chemin-db-certificats
Cette option permet de spécifier une base de données de certificats NSS séparée pour chaque serveur. Chaque option --ssl est ajoutée à une liste qui sera appliquée, à tour de rôle, à chaque serveur spécifié. S'il y a plus de

--max-threads threads
Cette option permet de spécifier le nombre maximum de threads de travail pour gérer les requêtes concurrentes. Si threads == 0, chaque requête sera traitée sur le thread principal, de manière sérielle. La valeur par défaut est le nombre de cœurs de processeur disponibles.
--max-request-size size
Cette option permet de spécifier la taille maximale d'une requête client non compressée. L'argument size est spécifié en octets. La valeur par défaut est de 50000 octets.
--max-compressed-request size
Cette option permet de spécifier la taille maximale d'une requête client compressée. L'argument size est spécifié en octets. La valeur par défaut est de 5000 octets.

CONFIGURATION

Les fichiers de configuration nous permettent de :

  • spécifier la configuration globale de la journalisation, des fichiers de configuration des serveurs, des fichiers d'état et d'autres paramètres globaux.
  • spécifier quels serveurs doivent être démarrés par défaut.

Configuration globale

Le fichier de configuration globale contient des affectations de variables utilisées pour configurer le fonctionnement général du service. Chaque ligne commençant par un caractère '#' est ignorée. Toutes les autres lignes doivent être de la forme VARIABLE=VALEUR. Ce n'est pas un script shell. L'intégralité du contenu de la ligne après le = sera assignée telle quelle à la variable.

Les variables suivantes peuvent être affectées :

CONFIG_PATH
Spécifie le chemin absolu du répertoire contenant les configurations de serveur par défaut.
STAT_PATH
Spécifie le chemin absolu du répertoire d'état des serveurs en cours d'exécution.
LOG_FILE
Spécifie le chemin absolu du fichier journal.
STAP_USER
Spécifie l'identifiant utilisateur qui sera utilisé pour exécuter le(s) serveur(s) (par défaut : pour le script d'initialisation stap-server, sinon l'utilisateur exécutant stap-server).

Voici un exemple de fichier de configuration globale :

CONFIG_PATH=~<utilisateur>/mes-configs-stap-server
LOG_FILE=/tmp/stap-server/log

Configuration individuelle du serveur

Chaque fichier de configuration de serveur configure un serveur à démarrer lorsqu'aucun serveur n'est spécifié pour l'action start, ou une action se comportant comme l'action start (voir ARGUMENTS). Chaque fichier de configuration contient des affectations de variables utilisées pour configurer un serveur individuel.

Chaque ligne commençant par un caractère '#' est ignorée. Toutes les autres lignes doivent être de la forme VARIABLE=VALEUR. Ce n'est pas un script shell. L'intégralité du contenu de la ligne après le = sera assignée telle quelle à la variable.

Chaque fichier de configuration doit avoir un suffixe de nom de fichier de .conf. Voir stappaths(7) pour l'emplacement par défaut de ces fichiers. Cet emplacement par défaut peut être remplacé dans le fichier de configuration globale en utilisant l'option -c (voir OPTIONS).

Les variables suivantes peuvent être affectées :

ARCH
Spécifie l'architecture cible pour ce serveur et correspond à l'option -a (voir OPTIONS). Si ARCH n'est pas définie, l'architecture de l'hôte sera utilisée.
RELEASE
Spécifie une version de noyau pour ce serveur et correspond à l'option -r (voir OPTIONS). Si RELEASE n'est pas définie, la version du noyau en cours d'exécution sur l'hôte sera utilisée.
BUILD
Spécifie les options à passer au processus make utilisé par systemtap pour construire des modules noyau. C'est une variable de tableau avec chaque élément correspondant à une option -B (voir OPTIONS). Utiliser la forme BUILD=CHAÎNE efface le tableau et définit le premier élément à CHAÎNE. Utiliser la forme BUILD+=CHAÎNE ajoute CHAÎNE comme élément supplémentaire au tableau.
INCLUDE
Spécifie une liste de répertoires à rechercher par le serveur pour les tapsets. C'est une variable de tableau avec chaque élément correspondant à une option -I (voir OPTIONS). Utiliser la forme INCLUDE=CHEMIN efface le tableau et définit le premier élément à CHEMIN. Utiliser la forme INCLUDE+=CHEMIN ajoute CHEMIN comme élément supplémentaire au tableau.
RUNTIME
Spécifie le répertoire qui contient le code d'exécution systemtap à utiliser par ce serveur et correspond à l'option -R (voir OPTIONS).
USER
Spécifie le nom d'utilisateur à utiliser pour exécuter ce serveur et correspond à l'option -u (voir OPTIONS).
NICKNAME
Spécifie le surnom à utiliser pour faire référence à ce serveur et correspond à l'option -n (voir OPTIONS).
LOG
Spécifie l'emplacement du fichier journal à utiliser par ce serveur et correspond à l'option --log (voir OPTIONS).
PORT
Spécifie le port réseau à utiliser par ce serveur et correspond à l'option --port (voir OPTIONS).
SSL
Spécifie l'emplacement de la base de données de certificats NSS à utiliser par ce serveur et correspond à l'option --ssl (voir OPTIONS).
MAXTHREADS
Spécifie le nombre maximum de threads de travail pour gérer les requêtes concurrentes à utiliser par ce serveur et correspond à l'option --max-threads (voir OPTIONS).
MAXREQSIZE
Spécifie la taille maximale d'une requête client non compressée, à utiliser par ce serveur et correspond à l'option --max-request-size (voir OPTIONS).
MAXCOMPRESSEDREQ
Spécifie la taille maximale d'une requête client compressée, à utiliser par ce serveur et correspond à l'option --max-compressed-request (voir OPTIONS).

Voici un exemple de fichier de configuration de serveur :

ARCH=
USER=
RELEASE=
NICKNAME=natif

En laissant les champs ARCH, USER et RELEASE vides, ils prendront par défaut l'architecture et la version actuelles et utiliseront l'utilisateur par défaut.

Un exemple plus spécifique :

ARCH=i386
RELEASE=2.6.18-128.el5
PORT=5001
LOG=/chemin/vers/fichier/log

Et voici un exemple plus complexe :

USER=utilisateur-serveur
RELEASE=/kernels/2.6.18-92.1.18.el5/build
INCLUDE=/mes-tapsets
INCLUDE+=/vos-tapsets
BUILD='VARIABLE1=VALEUR1 VARIABLE2=VALEUR2'
DEFINE=STP_MAXMEMORY=1024
DEFINE+=DEBUG_TRANS
RUNTIME=/monruntime
NICKNAME=mon-serveur
SSL=/chemin/vers/base-de-donnees-de-certificats-NSS

AUTHENTIFICATION DU SERVEUR

La sécurité de la connexion réseau SSL entre le client et le serveur dépend de la gestion appropriée des certificats serveur.

La fiabilité d'un serveur de compilation systemtap donné ne peut pas être déterminée automatiquement sans une autorité de certification de confiance émettant des certificats de serveur de compilation systemtap. Ceci n'est pas pratique dans un usage quotidien et par conséquent, les clients doivent authentifier les serveurs par rapport à leur propre base de données de certificats serveur de confiance. Dans ce contexte, établir un serveur donné comme étant de confiance par un client donné signifie ajouter le certificat de ce serveur à la base de données de serveurs de confiance du client.

Pour le script d'initialisation stap-server, sur l'hôte local, cela est géré automatiquement. Lorsque le paquet systemtap-server est installé, le certificat du serveur pour l'utilisateur par défaut (stap-server) est automatiquement généré et installé. Cela signifie que les serveurs démarrés par le script d'initialisation stap-server, avec l'utilisateur par défaut, sont automatiquement approuvés par les clients sur l'hôte local, à la fois en tant que pair SSL et en tant que signataire de module systemtap.

De plus, lorsque stap est invoqué par un utilisateur non privilégié (pas root, pas membre du groupe stapdev, mais membre du groupe stapusr et éventuellement du groupe stapsys), les options --use-server et --privilege sont automatiquement ajoutées aux options spécifiées. Cela signifie que les utilisateurs non privilégiés sur l'hôte local peuvent utiliser un serveur sur l'hôte local en mode non privilégié sans aucune configuration ou option supplémentaire requise. Les utilisateurs normaux (ceux n'appartenant à aucun des groupes SystemTap) peuvent également utiliser les serveurs de compilation via les options --use-server et --privilege. Mais ils seront naturellement incapables de charger le module (l'option -p4 peut être utilisée pour s'arrêter avant le chargement).

Afin d'utiliser un serveur s'exécutant sur un autre hôte, le certificat de ce serveur doit être installé sur l'hôte du client. Voir l'option --trust-servers dans la page de manuel de stap(1) pour plus de détails et README.unprivileged dans les sources de systemtap pour plus de détails.

EXEMPLES

Voir la page de manuel stapex(3stap) pour une collection de scripts systemtap d'exemple.

Pour démarrer les serveurs configurés, ou le serveur par défaut, si aucun n'est configuré :

$ [ service ] stap-server start

Pour démarrer un serveur qui gère toutes les versions de noyau installées dans /lib/modules :

$ [ service ] stap-server start -i

Pour obtenir des informations sur le(s) serveur(s) en cours d'exécution :

$ [ service ] stap-server status

stap-server(8) — SystemTap — Arch Linux

NAME

stap-server, stap-server daemon — SystemTap compile server

SYNOPSIS

stap-server [-d] [-F] [-g] [-h] [-k] [-l] [-p] [-P] [-q] [-s] [-t] [-v] [-w] [-W] [--help] [--version]

service stap-server command

DESCRIPTION

The stap-server daemon provides a network interface to the SystemTap scripting language compiler. Client machines may use the services of a remote machine to compile scripts, rather than performing the work locally. This is useful for various reasons:

  • Client machines may not have the necessary kernel debuginfo packages installed.
  • Client machines may not have the necessary development tools installed.
  • Client machines may not have sufficient resources (CPU, memory) to perform the compilation.
  • Target machines may have different architectures or kernel versions than the client.

The daemon may be run directly from the command line or invoked as a service via the system service manager (e.g. systemd, SysVinit).

ARGUMENTS

When invoked directly from the command line, stap-server accepts the following arguments:

-a, --arch ARCH
Start a server instance for the specified architecture. Defaults to the architecture of the host on which the server is run.
-C, --config CONFIG
Use the specified configuration file in place of the default /etc/systemtap/stap-server.conf.
-c, --command CMD
Used by the service manager to control the daemon. See service(8).
-d, --daemon
Run the server in the background as a daemon.
-f, --foreground
Run the server in the foreground. Useful for debugging.
-F, --force
Force the server to start even if it is already running.
-g, --global
Use the global configuration file /etc/systemtap/stap-server.conf.
-h, --help
Display a help message and exit.
-i, --inactive
Do not start any servers. Useful for configuration changes.
-k, --kill
Kill any running server instances.
-l, --list
List the status of all running server instances.
-n, --nick NICKNAME
Assign a nickname to the server instance. This is useful when running multiple server instances on the same host.
-p, --pid PID
Specify the process ID of the server to control (used with stop/restart commands).
-P, --pidfile PIDFILE
Specify the location of the PID file.
-q, --quiet
Suppress informational messages.
-r, --release RELEASE
Start a server instance for the specified kernel release. This is useful for cross-compiling for a kernel not installed on the host.
-s, --script SCRIPT
Run the specified script on the server. This is used when invoking stap with --use-server.
-t, --timeout TIMEOUT
Set the timeout for server startup and shutdown.
-u, --user USER
Run the server as the specified user.
-v, --verbose
Enable verbose output.
-w, --wait
Wait for the server to start before returning.
-W, --wait-all
Wait for all servers to start before returning.
--help
Display a help message and exit.
--version
Display version information and exit.

When invoked as a service, the following commands are supported:

start
Start the stap-server daemon.
stop
Stop the stap-server daemon.
restart
Restart the stap-server daemon.
status
Display the status of the stap-server daemon.
force-reload
Force a reload of the configuration files and restart of any affected servers.

OPTIONS

Some options are only available when invoked directly from the command line, while others are primarily intended for use by the service manager.

CONFIGURATION

The stap-server daemon is configured via configuration files. The primary configuration file is /etc/systemtap/stap-server.conf. Individual server instances may also have their own configuration files specified via the -C option.

Global Configuration

The global configuration file specifies general settings for the stap-server daemon, such as the user to run the servers as, the location of log files, and the location of status files.

Key-value pairs are used in the configuration file. Example:

STAP_USER=stapdev
LOG_FILE=/var/log/stap-server.log
STAT_PATH=/var/run/stap-server

Individual Server Configuration

Individual server configuration files allow for more granular control over server instances. These files can specify options such as the architecture, kernel release, and port number for a specific server instance.

Example:

ARCH=x86_64
RELEASE=5.4.101-1-MANJARO
PORT=8080

SERVER AUTHENTICATION

The systemtap compile server and its related utilities use the Secure Socket Layer (SSL) as implemented by Network Security Services (NSS) for network security. NSS is also used for the generation and management of certificates. The related certificate databases must be protected in order to maintain the security of the system. Use of the utilities provided will help to ensure that the proper protection is maintained. The systemtap client will check for proper access permissions before making use of any certificate database.

EXAMPLES

To start a server like another one, except targeting a different architecture, by referencing the first server's nickname:

$ [ service ] stap-server start -n NICKNAME -a ARCH

To start a server for a kernel release not installed (cross-compiling)

$ [ service ] stap-server start -a ARCH -r /BUILDDIR

To stop one of the servers by referencing its process id (obtained by running stap-server status):

$ [ service ] stap-server stop -p PID

To run a script using a compile server:

$ stap SCRIPT --use-server

To run a script as an unprivileged user using a compile server:

$ stap SCRIPT

To stop all running servers:

$ [ service ] stap-server stop

To restart servers after a global configuration change and/or when default servers have been added, changed, or removed:

$ [ service ] stap-server force-reload

SAFETY AND SECURITY

Systemtap is an administrative tool. It exposes kernel internal data structures and potentially private user information. See the stap(1) manual page for additional information on safety and security.

As a network server, stap-server should be activated with care in order to limit the potential effects of bugs or mischevious users. Consider the following prophylactic measures.

1
Run stap-server as an unprivileged user, never as root.

When invoked as a service (i.e. service stap-server ...), each server is run, by default, as the user stap-server. When invoked directly (i.e. stap-server ...), each server is run, by default, as the invoking user. In each case, another user may be selected by using the -u option on invocation, by specifying STAP_USER=username in the global configuration file or by specifying USER=username in an individual server configuration file. The invoking user must have authority to run processes as another user. See CONFIGURATION.

The selected user must have write access to the server log file. The location of the server log file may be changed by setting LOG_FILE=path in the global configuration file. See CONFIGURATION.

The selected user must have read/write access to the directory containing the server status files. The location of the server status files may be changed by setting STAT_PATH=path in the global configuration file. See CONFIGURATION.

The selected user must have read/write access to the uprobes.ko build directory and its files.

Neither form of stap-server will run if the selected user is root.

2
Run stap-server requests with resource limits that impose maximum cpu time, file size, memory consumption, in order to bound the effects of processing excessively large or bogus inputs.

When the user running the server is stap-server, each server request is run with limits specified in ~stap-server/.systemtap/rc otherwise, no limits are imposed.

3
Run stap-server with a TMPDIR environment variable that points to a separate and/or quota-enforced directory, in order to prevent filling up of important filesystems.

The default TMPDIR is /tmp/.

4
Activate network firewalls to limit stap client connections to relatively trustworthy networks.

For automatic selection of servers by clients, avahi must be installed on both the server and client hosts and mDNS messages must be allowed through the firewall.

The systemtap compile server and its related utilities use the Secure Socket Layer (SSL) as implemented by Network Security Services (NSS) for network security. NSS is also used for the generation and management of certificates. The related certificate databases must be protected in order to maintain the security of the system. Use of the utilities provided will help to ensure that the proper protection is maintained. The systemtap client will check for proper access permissions before making use of any certificate database.
