NOM

stap - traducteur/pilote de scripts systemtap

SYNTAXE

stap [ OPTIONS ] NOMFICHIER [ ARGUMENTS ]
stap [ OPTIONS ] - [ ARGUMENTS ]
stap [ OPTIONS ] -e SCRIPT [ ARGUMENTS ]
stap [ OPTIONS ] -l SONDE [ ARGUMENTS ]
stap [ OPTIONS ] -L SONDE [ ARGUMENTS ]
stap [ OPTIONS ] --dump-probe-types
stap [ OPTIONS ] --dump-probe-aliases
stap [ OPTIONS ] --dump-functions

DESCRIPTION

Le programme stap est la façade de l'outil Systemtap. Il accepte des instructions de sondage écrites dans un langage simple spécifique à un domaine, traduit ces instructions en code C, compile ce code C et charge le module résultant dans un noyau Linux en cours d'exécution ou dans un mutateur d'espace utilisateur Dyninst, pour effectuer les fonctions de trace/sondage système demandées. Vous pouvez fournir le script dans un fichier nommé (NOMFICHIER), depuis l'entrée standard (utilisez - au lieu de NOMFICHIER), ou depuis la ligne de commande (en utilisant -e SCRIPT). Le programme s'exécute jusqu'à ce qu'il soit interrompu par l'utilisateur, ou si le script invoque volontairement la fonction exit(), ou en cas d'un nombre suffisant d'erreurs logicielles.

Le langage, décrit dans la section LANGAGE DE SCRIPT ci-dessous, est strictement typé, expressif, sans déclaration, procédural, adapté au prototypage et inspiré par awk et C. Il permet d'associer des points de code source ou des événements dans le système à des gestionnaires, qui sont des sous-routines exécutées de manière synchrone. Il est conceptuellement assez similaire aux « listes de commandes de point d'arrêt » dans le débogueur gdb.

OPTIONS

Le traducteur systemtap prend en charge les options suivantes. Toute autre option affiche une liste des options prises en charge. Les options peuvent être fournies sur la ligne de commande, comme d'habitude. Si le fichier $SYSTEMTAP_DIR/rc existe, les options sont également chargées à partir de là et interprétées en premier. ($SYSTEMTAP_DIR par défaut $HOME/.systemtap si non défini.)

Dans certains cas, la valeur par défaut d'une option dépend de la configuration particulière du système et ne peut donc pas être mentionnée ici directement. Dans certains de ces cas, l'exécution de « stap --help » peut afficher la valeur par défaut.

-
Utiliser l'entrée standard au lieu d'un NOMFICHIER donné comme entrée du langage de sonde, sauf si -e SCRIPT est donné.
-h --help
Afficher le message d'aide.
-V --version
Afficher le message de version.
-p NUM
S'arrêter après la passe NUM. Les passes sont numérotées de 1 à 5 : analyse syntaxique, élaboration, traduction, compilation, exécution. Voir la section TRAITEMENT pour plus de détails.
-v
Augmenter la verbosité pour toutes les passes. Produire un plus grand volume de sortie informative (?) à chaque répétition de l'option.
--vp ABCDE
Augmenter la verbosité par passe. Par exemple, « --vp 002 » ajoute 2 unités de verbosité à la passe 3 seulement. La combinaison « -v --vp 00004 » ajoute 1 unité de verbosité pour toutes les passes, et 4 supplémentaires pour la passe 5.
-k
Conserver le répertoire temporaire après tout traitement. Cela peut être utile pour examiner le code C généré, ou pour réutiliser l'objet noyau compilé.
-g
Mode gourou. Activer l'analyse des constructions non sûres de niveau expert comme le C embarqué.
-P
Mode de recherche de prologue. Ceci est équivalent à --prologue-searching=always. Active les heuristiques pour contourner les informations de débogage incorrectes pour les variables de contexte des paramètres de fonction.
-u
Mode non optimisé. Désactive l'élision du code inutilisé et de nombreuses autres optimisations pendant l'élaboration/traduction.
-w
Mode de suppression des avertissements. Désactive tous les messages d'avertissement.
-W
Traiter tous les avertissements comme des erreurs.
-b
Utiliser le mode de diffusion (fichiers percpu) pour le transfert de données du noyau vers l'utilisateur. Utiliser le programme stap-merge pour les multiplexer à nouveau plus tard.
-i --interactive
Mode interactif. Active une interface pour construire le script systemtap de manière incrémentale et interactive.
-t
Collecter des informations de synchronisation sur le nombre de fois où une sonde s'exécute et la quantité moyenne de temps passée à chaque point de sonde. Affiche également la dérivation pour chaque point de sonde.
-s NUM
Utiliser des tampons de NUM mégaoctets pour le transfert de données du noyau vers l'utilisateur par processeur. La valeur par défaut est 16 Mo, ou moins sur les machines à mémoire plus petite.
-I DIR
Ajouter le répertoire donné au répertoire de recherche des tapsets. Voir la description de la passe 2 pour plus de détails.
-D NOM=VALEUR
Ajouter la directive de préprocesseur C donnée au Makefile du module. Celles-ci peuvent être utilisées pour remplacer les paramètres de limite décrits ci-dessous.
-B NOM=VALEUR
En mode d'exécution noyau, ajouter la directive make donnée à l'invocation make de la construction du module noyau. Celles-ci peuvent être utilisées pour ajouter ou remplacer des options kconfig. Par exemple, utiliser 
-B CONFIG_DEBUG_INFO=y

pour ajouter des informations de débogage.

-B FLAG
En mode d'exécution dyninst

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

mode, ajoutez le paramètre donné aux CFLAGS du compilateur utilisés pour construire la bibliothèque partagée dyninst. Par exemple, utilisez 
-B -g

pour ajouter des informations de débogage.

-a ARCH
Utilisez un mode de compilation croisée pour l'architecture cible donnée. Cela nécessite l'accès au compilateur croisé et à l'arborescence de compilation du noyau, et va de pair avec les options 
-B CROSS_COMPILE=arch-tool-prefix-
et
-r /build/tree

.

--modinfo NAME=VALUE
Ajoutez la paire nom/valeur comme appel de macro MODULE_INFO au module généré. Ceci peut être utile pour informer ou remplacer diverses vérifications relatives aux modules dans le noyau.
-G NAME=VALUE
Définit la valeur de la variable globale NAME à VALUE lors de l'invocation de staprun. Cela s'applique aux variables scalaires déclarées globales dans le script/tapset.
-R DIR
Recherchez les sources d'exécution de systemtap dans le répertoire donné. Votre valeur par défaut pour DIR peut être vue en utilisant "stap --help".
-r /DIR
Compilez pour le noyau dans l'arborescence de compilation donnée. Peut également être défini avec la variable d'environnement SYSTEMTAP_RELEASE.
-r RELEASE
Compilez pour le noyau dans l'arborescence de compilation /lib/modules/RELEASE/build. Peut également être défini avec la variable d'environnement SYSTEMTAP_RELEASE.
-m MODULE
Utilisez le nom donné pour le module objet du noyau généré, au lieu d'un nom aléatoire unique. Le module objet du noyau généré est copié dans le répertoire courant.
-d MODULE
Ajoutez des informations de symbole/déroulement pour le module donné dans le module objet du noyau. Cela peut permettre des tracebacks symboliques depuis ces modules/programmes, même s'ils n'ont pas de sonde explicite placée en eux.
--ldd
Ajoutez des informations de symbole/déroulement pour toutes les bibliothèques partagées de l'espace utilisateur suspectées par ldd d'être nécessaires aux binaires de l'espace utilisateur sondés ou listés avec l'option -d. Attention : cela peut rendre les modules de sonde considérablement plus volumineux. Notez que cette option ne traite pas les modules de l'espace noyau : voir plutôt --all-modules ci-dessous.
--all-modules
Équivalent à spécifier "-dkernel" et un "-d" pour chaque module noyau actuellement chargé. Attention : cela peut rendre les modules de sonde considérablement plus volumineux.
-o FILE
Envoyez la sortie standard vers le fichier nommé. En mode de masse, les fichiers percpu commenceront par FILE_ (FILE_cpu avec -F) suivi du numéro de CPU. Cela prend en charge les formats strftime(3) pour FILE.
-c CMD
Démarrez les sondes, exécutez CMD, et sortez lorsque CMD est terminé. Cela a également pour effet de définir target() sur le pid de ce processus. Notez que de nombreux types de sondes se déclenchent indépendamment de ce réglage. Envisagez d'inclure quelque chose comme ceci pour cibler votre script. 
   probe FOO { if (pid() != target()) next; .... }
-x PID
Définit target() sur PID. Le script s'exécute indépendamment de la durée de vie du PID.
-e SCRIPT
Exécutez le SCRIPT donné spécifié sur la ligne de commande.
-E SCRIPT
Exécutez le SCRIPT donné spécifié. Ce SCRIPT est exécuté en plus du script principal spécifié, via -e, ou en tant que fichier script. Cette option peut être répétée pour exécuter plusieurs scripts, et peut être utilisée en mode de listage (-l/-L).
-l PROBE
Au lieu d'exécuter un script de sonde, listez simplement tous les points de sonde disponibles correspondant au seul point de sonde donné. Le modèle peut inclure des jokers et des alias, mais pas des points de sonde multiples séparés par des virgules. Le code de résultat du processus indiquera un échec s'il n'y a pas de correspondances. 
% stap -e 'probe syscall.* { }'
[...]
% stap -l 'syscall.*'
syscall.accept
[...]
syscall.writev
-L PROBE
Similaire à "-l", mais liste les points de sonde correspondants plus leurs variables de contexte disponibles. Lorsque -v est défini avec -L, la sortie inclut des points de sonde dupliqués qui sont distingués par leur adresse PC. 
% stap -L 'process("/lib64/libpython*.so.*").mark("*")'
process("/usr/lib64/libpython2.7.so.1.0").mark("function__entry") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython2.7.so.1.0").mark("function__return") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("function__entry") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("function__return") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("gc__done") $arg1:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("gc__start") $arg1:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("line") $arg1:long $arg2:long $arg3:long
-F
Sans l'option -o, chargez le module et démarrez les sondes, puis détachez-vous du module en laissant les sondes en cours d'exécution. Avec l'option -o, exécutez staprun en arrière-plan comme un démon et affichez son pid.
-S taille[,N]
Définit la taille maximale du fichier de sortie et le nombre maximal de fichiers de sortie. Si la taille du fichier de sortie dépasse taille mégaoctets, systemtap bascule vers le fichier de sortie suivant. Et si le nombre de fichiers de sortie dépasse N, systemtap supprime le fichier de sortie le plus ancien. Vous pouvez omettre le second argument.
-T TIMEOUT
Quittez le script après TIMEOUT secondes.
--skip-badvars
Ignorez les variables de contexte non résolubles ou inaccessibles à l'exécution et substituez par 0, sans erreurs.
--prologue-searching[=WHEN]
Mode recherche de prologue. Activez les heuristiques pour contourner les informations de débogage incorrectes pour les variables de contexte des paramètres de fonction $context. WHEN peut être soit "never", "always", soit "auto" (c'est-à-dire activé par heuristique). Si WHEN est manquant, alors "always" est supposé. Si l'option est manquante, alors "auto" est supposé.
--suppress-handler-errors
Enveloppez tous les gestionnaires de sonde dans quelque chose comme 
try { ... } catch { next }

bloc, ce qui fait que toutes les erreurs d'exécution sont silencieusement supprimées. Les erreurs supprimées ne comptent pas pour les limites MAXERRORS. Dans ce mode, les limites MAXSKIPPED sont également supprimées, de sorte que de nombreuses erreurs et sondes ignorées peuvent être accumulées pendant l'exécution d'un script. Tous les décomptes globaux seront toujours rapportés à l'arrêt.

--compatible VERSION
Supprimez les changements récents du langage de script ou des tapsets qui sont incompatibles avec la version plus ancienne de systemtap donnée. Cela peut être utile si un script systemtap beaucoup plus ancien échoue à s'exécuter. Voir la section DEPRECATION pour plus de détails.
--check-version
Cette option est utilisée pour vérifier si le script actif contient des constructions qui peuvent être spécifiques à la version de systemtap. Voir la section DEPRECATION pour plus de détails.
--clean-cache
Cette option élague les entrées obsolètes du répertoire de cache. Cela est normalement fait automatiquement après des exécutions réussies, mais cette option déclenchera le nettoyage manuellement puis quittera. Voir la section CACHING pour plus de détails sur les limites du cache.
--color[=WHEN], --colour[=WHEN]
Cette option contrôle la coloration des messages d'erreur. WHEN peut être soit "never", "always", soit "auto" (c'est-à-dire activer uniquement si à un terminal). Si WHEN est manquant, alors "always" est supposé. Si l'option est manquante, alors "auto" est supposé.

Les couleurs peuvent être modifiées à l'aide de la variable d'environnement SYSTEMTAP_COLORS. Le format doit être de la forme clé1=val1:clé2=val2:clé3=val3 ...etc. Les clés valides sont "error", "warning", "source", "caret", et "token". Les valeurs constituent des paramètres de rendition graphique Select (SGR). Consultez la documentation de votre terminal pour les SGR qu'il prend en charge. Par exemple, les couleurs par défaut seraient exprimées comme error=01;31:warning=00;33:source=00;34:caret=01:token=01. Si SYSTEMTAP_COLORS est absent, les couleurs par défaut seront utilisées. S'il est vide ou invalide, la coloration est désactivée.

--disable-cache
Cette option désactive toute utilisation du répertoire de cache. Aucun fichier ne sera lu ni écrit dans le cache.
--poison-cache
Cette option traite les fichiers du répertoire de cache comme invalides. Aucun fichier ne sera lu à partir du cache, mais les fichiers résultant de cette exécution seront toujours écrits dans le cache. Ceci est destiné à aider au dépannage lorsque le comportement mis en cache de stap semble défectueux. Si cela a aidé, il y a probablement un bug dans systemtap que les développeurs aimeraient que vous signaliez.
--privilege[=stapusr | =stapsys | =stapdev]
Cette option demande à stap d'examiner le script à la recherche de constructions qui ne sont pas autorisées pour le niveau de privilège spécifié (voir UTILISATEURS NON PRIVILÉGIÉS). La compilation échoue si de telles constructions sont utilisées. Si stapusr ou stapsys sont spécifiés lors de l'utilisation d'un serveur de compilation (voir --use-server), le serveur examinera le script et, si la compilation réussit, le serveur signera cryptographiquement le module noyau résultant, certifiant qu'il est sûr à utiliser par les utilisateurs du niveau de privilège spécifié.

Si --privilege n'a pas été spécifié, -pN n'a pas été spécifié avec N < 5, et l'utilisateur appelant n'est pas root, et n'est pas membre du groupe stapdev, alors stap ajoutera automatiquement l'option --privilege appropriée aux options déjà spécifiées.

--unprivileged
Cette option est équivalente à --privilege=stapusr.
--use-server[=HOSTNAME[:PORT] | =IP_ADDRESS[:PORT] | =CERT_SERIAL]
Spécifie les serveurs de compilation à utiliser pour la compilation et/ou conjointement avec --list-servers et --trust-servers (voir ci-dessous) pour l'affichage. Si aucun argument n'est fourni, alors par défaut en mode non privilégié (voir --privilege) est de sélectionner des serveurs compatibles qui sont fiables en tant que pairs SSL et en tant que signataires de modules et qui sont actuellement en ligne. Sinon, la valeur par défaut est de sélectionner des serveurs compatibles qui sont fiables en tant que pairs SSL et actuellement en ligne. --use-server peut être spécifié plusieurs fois, auquel cas une liste de serveurs est accumulée dans l'ordre spécifié. Les serveurs peuvent être spécifiés par nom d'hôte, adresse IP ou numéro de série de certificat (obtenu à l'aide de --list-servers). Ce dernier est le plus couramment utilisé lors de l'ajout ou de la révocation de la confiance dans un serveur (voir --trust-servers ci-dessous). Si un serveur est spécifié par nom d'hôte ou adresse IP, un numéro de port optionnel peut être spécifié. Ceci est utile pour accéder à des serveurs qui ne sont pas sur le réseau local ou pour spécifier un serveur particulier.

Les adresses IP peuvent être des adresses IPv4 ou IPv6.

Si une adresse IPv6 particulière est locale à la liaison et existe sur plus d'une interface, l'interface souhaitée peut être spécifiée en ajoutant l'adresse avec un signe de pourcentage (%) suivi du nom de l'interface souhaitée. Par exemple, "fe80::5eff:35ff:fe07:55ca%eth0".

Afin de spécifier un numéro de port avec une adresse IPv6, il est nécessaire d'enfermer l'adresse IPv6 entre crochets ([]) afin de séparer le numéro de port du reste de l'adresse. Par exemple, "[fe80::5eff:35ff:fe07:55ca]:5000" ou "[fe80::5eff:35ff:fe07:55ca%eth0]:5000".

Si --use-server n'a pas été spécifié, -pN n'a pas été spécifié avec N < 5, et que l'utilisateur appelant n'est pas root, n'est pas membre du groupe stapdev, mais est membre du groupe stapusr, alors stap ajoutera automatiquement --use-server aux options déjà spécifiées.

--use-server-on-error[=yes|=no]
Indique à stap de réessayer la compilation d'un script en utilisant un serveur de compilation si la compilation sur l'hôte local échoue d'une manière qui suggère qu'elle pourrait réussir en utilisant un serveur. Si cette option n'est pas spécifiée, la valeur par défaut est no. Si aucun argument n'est fourni, la valeur par défaut est yes. La compilation sera retentée pour certains types d'erreurs (par exemple, données ou ressources insuffisantes) qui pourraient ne pas survenir lors d'une recompilation par un serveur de compilation. Les serveurs de compilation seront sélectionnés automatiquement pour la tentative de recompilation comme si --use-server avait été spécifié sans arguments.
--list-servers[=SERVERS]
Affiche l'état des SERVERS demandés, où SERVERS est une liste d'attributs de serveur séparés par des virgules. La liste des attributs est combinée pour filtrer la liste des serveurs affichés. Les attributs pris en charge sont :
all
spécifie tous les serveurs connus (pairs SSL fiables, signataires de modules fiables, serveurs en ligne).
specified
spécifie les serveurs spécifiés à l'aide de --use-server.
online
filtre la sortie en conservant les informations sur les serveurs qui sont actuellement en ligne.
trusted
filtre la sortie en conservant les informations sur les serveurs qui sont fiables en tant que pairs SSL.
signer
filtre la sortie en conservant les informations sur les serveurs qui sont fiables en tant que signataires de modules (voir --privilege).
compatible
filtre la sortie en conservant les informations sur les serveurs qui sont compatibles avec la version du noyau et l'architecture actuelles.
Si aucun argument n'est fourni, la valeur par défaut est specified. Si aucun serveur n'a été spécifié à l'aide de --use-server, les serveurs par défaut pour --use-server sont affichés.

Notez que --list-servers utilise le service avahi-daemon pour détecter les serveurs en ligne. Si ce service n'est pas disponible, --list-servers ne parviendra pas à détecter de serveurs en ligne. Pour que --list-servers puisse détecter les serveurs écoutant sur des adresses IPv6, le fichier de configuration avahi-daemon /etc/avahi/avahi-daemon.conf doit contenir une ligne active "use-ipv6=yes". Le service doit être redémarré après avoir ajouté cette ligne pour que l'IPv6 soit activé.

--trust-servers[=TRUST_SPEC]
Accorde ou révoque la confiance aux serveurs de compilation, spécifiés à l'aide de --use-server comme spécifié par TRUST_SPEC, où TRUST_SPEC est une liste séparée par des virgules spécifiant la confiance à accorder ou à révoquer. Les éléments pris en charge sont :
ssl
fait confiance aux serveurs spécifiés en tant que pairs SSL.
signer
fait confiance aux serveurs spécifiés en tant que signataires de modules (voir --privilege). Seul root peut spécifier signer.
all-users
accorde la confiance en tant que pair ssl pour tous les utilisateurs de l'hôte local. La valeur par défaut est d'accorder la confiance en tant que pair ssl uniquement pour l'utilisateur actuel. La confiance en tant que signataire de module est toujours accordée pour tous les utilisateurs. Seul root peut spécifier all-users.
revoke
révoque la confiance spécifiée. La valeur par défaut est de l'accorder.
no-prompt
ne demande pas à l'utilisateur de confirmer avant d'exécuter l'action demandée. La valeur par défaut est de demander à l'utilisateur de confirmer.
Si aucun argument n'est fourni, la valeur par défaut est ssl. Si aucun serveur n'a été spécifié à l'aide de --use-server, aucune confiance ne sera accordée ou révoquée.
Sauf si no-prompt a été spécifié, l'utilisateur sera invité à confirmer la confiance à accorder ou à révoquer avant que l'opération ne soit effectuée.
--sign-module
Signe le module avec une MOK (Machine Owner Key) sur les systèmes UEFI/SecureBoot. Voir la section SECUREBOOT pour plus de détails.
--dump-probe-types
Affiche une liste des types de sondes pris en charge et quitte. Si --privilege=stapusr est également spécifié, la liste sera limitée aux types de sondes disponibles pour les utilisateurs non privilégiés.
--dump-probe-aliases
Affiche une liste de tous les alias de sondes trouvés dans les fichiers de bibliothèque et quitte.
--dump-functions
Affiche une liste de toutes les fonctions publiques trouvées dans les fichiers de bibliothèque et quitte. Inclut également leurs paramètres et leurs types. Une fonction de type 'unknown' indique une fonction qui ne retourne pas de valeur. Notez que tous les types de fonctions/paramètres ne peuvent pas être résolus (ceux-ci sont également affichés comme 'unknown'). Cette fonctionnalité est très gourmande en mémoire et peut donc ne pas fonctionner correctement avec --use-server si le serveur cible impose une rlimit sur la mémoire du processus (c'est-à-dire via le fichier de configuration ~stap-server/.systemtap/rc, voir stap-server(8)).
--remote URL
Définit la cible d'exécution à l'hôte donné. Cette option peut être répétée pour cibler plusieurs cibles d'exécution. Les passes 1 à 4 sont effectuées localement normalement pour construire le script, puis la passe 5 copiera le module vers la cible et l'exécutera. Les formes d'URL acceptables incluent :
[USER@]HOSTNAME, ssh://[USER@]HOSTNAME
Ce mode utilise ssh, en utilisant éventuellement un nom d'utilisateur différent du vôtre. Si un fichier ssh_config personnalisé est utilisé, ajoutez SendEnv LANG pour conserver les fonctionnalités d'internationalisation.
libvirt://DOMAIN, libvirt://DOMAIN/LIBVIRT_URI
Ce mode utilise stapvirt pour exécuter le script sur un domaine géré par libvirt. Optionnellement, LIBVIRT_URI peut être spécifié pour se connecter à un pilote spécifique et/ou à un hôte distant. Par exemple, pour se connecter au pilote QEMU privilégié local, utilisez : 
--remote libvirt://MonDomaine/qemu:///system

LANGAGE DE SCRIPT

Le langage de script systemtap ressemble à awk et C. Il existe deux constructions principales : les sondes et les fonctions. À l'intérieur de celles-ci, les instructions et les expressions utilisent une syntaxe et une précédence d'opérateurs similaires à celles de C.

SYNTAXE GÉNÉRALE

Les espaces sont ignorés. Trois formes de commentaires sont supportées :


# ... style shell, jusqu'à la fin de la ligne, sauf pour $# et @#
// ... style C++, jusqu'à la fin de la ligne
/* ... style C ... */
Les littéraux sont soit des chaînes de caractères entourées de guillemets doubles (passant par les codes d'échappement C habituels avec des barres obliques inverses, et avec des littéraux de chaîne adjacents collés ensemble, comme en C), soit des entiers (en décimal, hexadécimal ou octal, en utilisant la même notation qu'en C). Toutes les chaînes sont limitées à une longueur raisonnable (quelques centaines d'octets). Les entiers sont des quantités signées de 64 bits, bien que l'analyseur accepte également (et encapsule) des valeurs supérieures à 2**63 positif.

De plus, les arguments de script donnés à la fin de la ligne de commande peuvent être insérés. Utilisez $1 ... $<NN> pour l'insertion non citée, @1 ... @<NN> pour l'insertion en tant que littéral de chaîne. Le nombre d'arguments peut être accédé via $# (en tant que nombre non cité) ou via @# (en tant que nombre cité). Ceux-ci peuvent être utilisés partout où un jeton peut commencer, y compris pendant la phase de prétraitement. La référence à un numéro d'argument au-delà de ce qui a été réellement donné est une erreur.

PRÉTRAITEMENT

Une étape simple de prétraitement conditionnel est exécutée dans le cadre de l'analyse. La forme générale est similaire à l'opérateur ternaire cond ? exp1 : exp2 :

%( CONDITION %? VRAIS-JETONS %)
%( CONDITION %? VRAIS-JETONS %: FAUX-JETONS %)

La CONDITION est soit une expression dont le format est déterminé par son premier mot-clé, soit une comparaison de littéraux de chaîne, soit une comparaison de littéraux numériques. Elle peut également être composée de nombreuses alternatives et conjonctions de CONDITIONS (au sens de la phrase précédente) en utilisant || et && respectivement. Cependant, les parenthèses ne sont pas encore supportées, il est donc important de se souvenir que la conjonction a priorité sur l'alternative.

Si la première partie est l'identifiant kernel_vr ou kernel_v pour faire référence au numéro de version du noyau, avec ("2.6.13-1.322FC3smp") ou sans ("2.6.13") le suffixe de code de publication, alors la deuxième partie est l'un des six opérateurs de comparaison numérique standard <, <=, ==, !=, >, et >=, et la troisième partie est un littéral de chaîne qui contient une valeur version-release de style RPM. La condition est jugée satisfaite si la version du noyau cible (telle qu'éventuellement remplacée par l'option -r) se compare à la chaîne de version donnée. La comparaison est effectuée par la fonction strverscmp de glibc. À titre de cas spécial, si l'opérateur est pour une égalité simple (==) ou une inégalité (!=), et que la troisième partie contient des caractères génériques (* ou ? ou [), alors l'expression est traitée comme une correspondance (ou non-correspondance) par caractère générique, telle qu'évaluée par fnmatch.

Si, en revanche, la première partie est l'identifiant arch pour faire référence à l'architecture du processeur (telle que nommée par le système de construction du noyau ARCH/SUBARCH), alors la deuxième partie est l'un des deux opérateurs de comparaison de chaînes == ou !=, et la troisième partie est un littéral de chaîne pour la faire correspondre. Cette comparaison est une correspondance par caractère générique.

De même, si la première partie est un identifiant comme CONFIG_something pour faire référence à une option de configuration du noyau, alors la deuxième partie est == ou !=, et la troisième partie est un littéral de chaîne pour faire correspondre la valeur (communément "y" ou "m"). Les options de configuration du noyau inexistantes ou non définies sont représentées par une chaîne vide. Cette comparaison est également une correspondance par caractère générique.

Si la première partie est l'identifiant systemtap_v, le test fait référence à la version de compatibilité systemtap, qui peut être remplacée pour les anciens scripts avec le drapeau --compatible. L'opérateur de comparaison est tel quel pour kernel_v et la droite

operand est une chaîne de version. Voir aussi la section DEPRECATION ci-dessous. Si la première partie est l'identifiant systemtap_privilege, le test fait référence au niveau de privilège avec lequel le script systemtap est compilé. Ici, la deuxième partie est == ou !=, et la troisième partie est une chaîne littérale, soit "stapusr", soit "stapsys", soit "stapdev". Si la première partie est l'identifiant guru_mode, le test fait référence si le script systemtap est compilé avec guru_mode. Ici, la deuxième partie est == ou !=, et la troisième partie est un nombre, soit 1, soit 0. Si la première partie est l'identifiant runtime, le test fait référence au mode d'exécution systemtap. Voir RUNTIMES ALTERNATIFS ci-dessous pour plus d'informations sur les runtimes. La deuxième partie est l'un des deux opérateurs de comparaison de chaînes == ou !=, et la troisième partie est une chaîne littérale pour la faire correspondre. Cette comparaison est une correspondance (erronée) avec des caractères génériques. Sinon, le CONDITION est censé être une comparaison entre deux chaînes littérales ou deux nombres littéraux. Dans ce cas, les arguments sont les seules variables utilisables. Les VRAIS_JETONS et FAUX_JETONS sont zéro ou plusieurs jetons de parseur généraux (pouvant inclure des conditions de préprocesseur imbriquées), et sont passés dans le flux d'entrée si la condition est vraie ou fausse. Par exemple, le code suivant induit une erreur d'analyse syntaxique à moins que la version du noyau cible ne soit plus récente que 2.6.5 : %( kernel_v <= "2.6.5" %? **ERROR** %) # séquence de jetons invalide Le code suivant pourrait s'adapter à une dérive hypothétique de la version du noyau : probe kernel.function ( %( kernel_v <= "2.6.12" %? " __mm_do_fault" %: %( kernel_vr == "2.6.13*smp" %? "do_page_fault" %: UNSUPPORTED %) %) ) { /* ... */ } %( arch == "ia64" %? probe syscall.vliw = kernel.function("vliw_widget") {} %) MACROS DU PRÉPROCESSEUR Le préprocesseur prend également en charge une installation de macros simple, exécutée comme une passe séparée avant le préprocesseur conditionnel. Les macros sont définies en utilisant la construction suivante : @define NOM %( CORPS %) @define NOM(PARAM_1, PARAM_2, ...) %( CORPS %) Les macros, et les paramètres à l'intérieur d'un corps de macro, sont tous deux appelés en préfixant le nom de la macro avec un symbole @ : @define foo %( x %) @define add(a,b) %( ((@a)+(@b)) %) @foo = @add(2,2) L'expansion des macros est actuellement effectuée dans une passe séparée avant la compilation conditionnelle. Par conséquent, les VRAIS et FAUX jetons dans les expressions conditionnelles seront développés par macro, indépendamment de la façon dont la condition est évaluée. Cela peut parfois entraîner des erreurs : // Le résultat suivant est un conflit : %( CONFIG_UPROBE == "y" %? @define foo %( process.syscall %) %: @define foo %( **ERROR** %) %) // Le résultat suivant fonctionne correctement comme prévu : @define foo %( %( CONFIG_UPROBE == "y" %? process.syscall %: **ERROR** %) %) Le premier exemple est incorrect car les deux @defines sont évalués dans une passe antérieure à l'évaluation de la condition. Normalement, une définition de macro est locale au fichier dans lequel elle apparaît. Ainsi, définir une macro dans un tapset ne la rend pas disponible à l'utilisateur du tapset. Les macros de bibliothèque publiquement disponibles peuvent être définies en incluant des fichiers .stpm dans le chemin de recherche des tapsets. Ces fichiers ne peuvent contenir que des constructions @define, qui deviennent visibles dans tous les tapsets et scripts utilisateur. Facultativement, dans les fichiers .stpm, une définition de macro publique peut être entourée d'une condition de préprocesseur comme décrit ci-dessus. CONSTANTES Les tapsets ou les scripts utilisateur en mode guru peuvent accéder aux jetons de constante des fichiers d'en-tête, généralement des macros, en utilisant l'opérateur intégré @const(). L'inclusion du fichier d'en-tête respectif est possible soit via la bibliothèque de tapsets, soit en utilisant une construction embedded-C de niveau supérieur en mode guru. Cela entraîne des commentaires de pragma embedded-C appropriés. @const("STP_SKIP_BADVARS") VARIABLES Les identifiants de variables et de fonctions sont une séquence alphanumérique et peuvent inclure les caractères _ et $. Ils ne peuvent pas commencer par un chiffre simple, comme en C. Chaque variable est par défaut locale à la sonde ou au bloc d'instructions de fonction dans lequel elle est mentionnée, et par conséquent sa portée et sa durée de vie sont limitées à une invocation de sonde ou de fonction particulière. Les variables scalaires sont implicitement typées comme chaîne de caractères ou entier. Les tableaux associatifs ont également une valeur de chaîne ou d'entier, et un tuple de chaînes et/ou d'entiers servant d'index. Voici quelques expressions de base. var1 = 5 var2 = "bar" array1 [pid()] = "name" # index numérique unique array2 ["foo",4,i++] += 5 # vecteur d'index chaîne/num/num if (["hello",5,4] in array2) println ("yes") # test d'appartenance Le traducteur effectue une *inférence de type* sur tous les identifiants, y compris les index de tableaux et les paramètres de fonction. L'utilisation incohérente des identifiants liée au type signale une erreur. Les variables peuvent être déclarées globales, de sorte qu'elles soient partagées entre toutes les sondes et fonctions et vivent aussi longtemps que toute la session systemtap. Il existe un seul espace de noms pour toutes les variables globales, quel que soit le fichier de script dans lequel elles se trouvent. Les accès concurrents aux variables globales sont automatiquement protégés par des verrous, voir la section SÉCURITÉ ET PROTECTION pour plus de détails. Une déclaration globale peut être écrite au niveau le plus externe n'importe où, pas dans un bloc de code. Les variables globales qui sont écrites mais jamais lues seront automatiquement affichées à l'arrêt de la session. Le traducteur en déduira le type de valeur de chacune, et si elle est utilisée comme tableau, ses types d'index. Facultativement, les scalaires globaux peuvent être initialisés avec une chaîne ou un nombre littéral. La déclaration suivante marque les variables comme globales. global var1, var2, var3=4 Les variables globales peuvent également être définies comme options de module. On peut le faire soit en utilisant l'option -G, soit le module doit d'abord être compilé en utilisant stap -p4. Les variables globales peuvent ensuite être définies sur la ligne de commande lors de l'appel de staprun sur le module généré par stap -p4. Voir staprun(8) pour plus d'informations. La portée d'une variable globale peut être limitée à un tapset ou à un fichier de script utilisateur en utilisant le mot-clé private. Le mot-clé global est facultatif lors de la définition d'une variable globale privée. La déclaration suivante marque var1 et var2 comme globales privées. private global var1=2 private var2 Les tableaux sont limités en taille par la variable MAXMAPENTRIES -- voir la section SÉCURITÉ ET PROTECTION pour les détails. Facultativement, les tableaux globaux peuvent être déclarés avec une taille maximale entre crochets, remplaçant MAXMAPENTRIES pour ce tableau uniquement. Notez que cela n'indique pas le type des index pour le tableau, juste la taille. global tiny_array[10], normal_array, big_array[50000] Les tableaux peuvent être configurés pour un enroulement en utilisant le suffixe %. Cela entraîne l'écrasement des éléments plus anciens si plus d'éléments sont insérés que le tableau ne peut en contenir. Cela fonctionne pour les tableaux associatifs et statistiques. global wrapped_array1%[10], wrapped_array2% De nombreux types de points de sonde fournissent des variables de contexte, qui sont des valeurs d'exécution, extraites en toute sécurité du noyau ou du programme utilisateur sondé. Ceux-ci sont préfixés par le caractère $. La section VARIABLES DE CONTEXTE dans stapprobes(3stap) liste ce qui est disponible pour chaque type de point de sonde. Ces variables de contexte deviennent des scalaires normaux de type chaîne ou numérique une fois stockées dans des variables de script normales. Voir la section CONVERSION DE TYPE ci-dessous sur la façon de les retransformer en pointeurs typés pour un traitement ultérieur en tant que variables de contexte. Il y a une certaine automatisation pour aider ! INSTRUCTIONS Les instructions permettent le flux de contrôle procédural. Elles peuvent apparaître dans des fonctions et des gestionnaires de sonde. Le nombre total d'instructions exécutées en réponse à un seul événement de sonde est limité à un certain nombre défini par la macro MAXACTION dans le code C traduit, et est de l'ordre de 1000. EXP Exécutez l'expression de valeur chaîne ou entière et jetez la valeur. { STMT1 STMT2 ... } Exécutez chaque instruction séquentiellement dans ce bloc. Notez que les séparateurs ou terminateurs ne sont généralement pas nécessaires entre les instructions. ; Instruction nulle, ne rien faire. Elle est utile comme séparateur facultatif entre les instructions pour améliorer la détection d'erreurs de syntaxe et gérer certaines ambiguïtés grammaticales. if (EXP) STMT1 [ else STMT2 ] Comparez EXP à valeur entière à zéro. Exécutez la première (non nulle) ou la deuxième STMT (zéro). while (EXP) STMT Tant que EXP à valeur entière évalue à non nul, exécutez STMT. for (EXP1; EXP2; EXP3) STMT Exécutez EXP1 comme initialisation. Tant que EXP2 est non nul, exécutez STMT, puis l'expression d'itération EXP3. foreach (VAR in ARRAY [ limit EXP ]) STMT Boucle sur chaque élément du tableau global nommé, attribuant l'index courant à VAR. Le tableau ne peut pas être modifié dans l'instruction. En ajoutant un seul opérateur + ou - après l'identifiant VAR ou ARRAY, l'itération se poursuivra dans un ordre trié, par index ou valeur ascendante ou descendante. Si le tableau contient des agrégats statistiques, l'ajout de l'opérateur @ souhaité entre l'identifiant ARRAY et le + ou - spécifiera la fonction d'agrégation de tri. Voir la section STATISTIQUES ci-dessous pour ceux qui sont disponibles. La valeur par défaut est @count. L'utilisation du mot-clé optionnel limit limite le nombre d'itérations de la boucle à EXP fois. Identique à ci-dessus, où les itérations sont limitées aux éléments du tableau dont les clés correspondent aux valeurs d'index spécifiées. Le symbole * peut être utilisé pour spécifier un index et sera traité comme un caractère générique.

Cette variante de foreach enregistre la valeur actuelle dans VAR0 à chaque itération, elle est donc identique à ARRAY[VAR]. Cela fonctionne également avec un tuple de clés. Les suffixes de tri sur VAR0 ont le même effet que sur ARRAY.

Identique à ci-dessus, où les itérations sont limitées aux éléments du tableau dont les clés correspondent aux valeurs d'index spécifiées. Le symbole * peut être utilisé pour spécifier un index et sera traité comme un caractère générique.

Quitte ou itère la boucle la plus interne (while ou for ou foreach) instruction.

Retourne la valeur EXP de la fonction englobante. Si la valeur de la fonction n'est pas récupérée quelque part, une instruction return n'est pas nécessaire et la fonction aura un type spécial "inconnu" sans valeur de retour.
next
Retourne immédiatement du gestionnaire de sonde englobant. Ceci est particulièrement utile dans les alias de sonde qui appliquent des prédicats de filtrage d'événements. Utilisé dans les fonctions, l'exécution sera immédiatement transférée à la fonction surchargée suivante.

Identique à ci-dessus, plus assigne le message d'erreur à la variable scalaire de chaîne VAR.
delete ARRAY[INDEX1, INDEX2, ...]
Supprime du tableau ARRAY l'élément spécifié par le tuple d'index. Si le tuple d'index contient un * à la place d'un index, le * est traité comme un caractère générique et tous les éléments dont les clés correspondent au tuple d'index seront supprimés du tableau ARRAY. La valeur ne sera plus disponible et les itérations ultérieures ne signaleront pas l'élément. Ce n'est pas une erreur de supprimer un élément qui n'existe pas.

CORRESPONDANCE D'EXPRESSIONS RÉGULIÈRES

Le langage de script prend en charge la correspondance d'expressions régulières. La syntaxe de base est la suivante :

exp =~ regex
exp !~ regex

(Le premier opérande doit être une expression évaluant à une chaîne ; le second opérande doit être une chaîne littérale contenant une expression régulière syntaxiquement valide.)

La syntaxe des expressions régulières prend en charge les fonctionnalités d'expressions régulières étendues POSIX telles que documentées dans grep(1) à l'exception de la fonctionnalité de réutilisation des sous-expressions ("\1").

Après une correspondance réussie, le contenu de la chaîne correspondante et des sous-expressions peut être extrait à l'aide des fonctions tapset matched() et ngroups() comme suit :

if ("une chaîne d'exemple" =~ "str(ing)") {
  matched(0) // -> renvoie "string", la sous-chaîne correspondante
  matched(1) // -> renvoie "ing", la 1ère sous-expression correspondante
  ngroups()  // -> renvoie 2, le nombre de groupes correspondants
}

SONDES

La construction principale du langage de script identifie les sondes. Les sondes associent des événements abstraits à un bloc d'instructions ("gestionnaire de sonde") qui doit être exécuté lorsque l'un de ces événements se produit. La syntaxe générale est la suivante :

probe PROBEPOINT [, PROBEPOINT] { [STMT ...] }
probe PROBEPOINT [, PROBEPOINT] if (CONDITION) { [STMT ...] }

Les événements sont spécifiés dans une syntaxe spéciale appelée "points de sonde". Il existe plusieurs variétés de points de sonde définis par le traducteur, et les scripts tapset peuvent en définir d'autres à l'aide d'alias. Les points de sonde peuvent être masqués par des caractères génériques, groupés ou listés dans des séquences de préférence, ou déclarés optionnels. Plus de détails sur la syntaxe et la sémantique des points de sonde sont listés dans la page de manuel stapprobes(3stap).

Le gestionnaire de sonde est interprété par rapport au contexte de chaque événement. Pour les événements associés au code du noyau, ce contexte peut inclure des variables définies dans le code source à cet endroit. Ces "variables de contexte" sont présentées au script comme des variables dont les noms sont préfixés par "$". Elles ne peuvent être accessibles que si le compilateur du noyau les a préservées malgré l'optimisation. C'est la même contrainte qu'un utilisateur de débogueur rencontre lorsqu'il travaille avec du code optimisé. De plus, les objets doivent exister dans la mémoire paginée au moment de l'exécution du gestionnaire de sonde systemtap, car systemtap ne doit pas provoquer (supprimer) de pagination supplémentaire. Certains types de sondes ont très peu de contexte. Consultez les pages de manuel stapprobes(3stap) pour connaître les types de variables de contexte disponibles à chaque type de point de sonde. Depuis la version 4.3 de systemtap, les fonctions appelées depuis les gestionnaires de certains types de points de sonde peuvent également faire référence à des variables de contexte. Celles-ci sont traitées comme si un clone de cette fonction était intégré dans le gestionnaire de sonde appelant et que les variables $ étaient évaluées dans son contexte.

Les sondes peuvent être décorées d'une condition d'activation, composée d'une simple expression booléenne sur des variables globales de script en lecture seule. Lorsqu'elles sont désactivées (inactives, condition évaluée à faux), certains types de sondes réduisent ou éliminent leurs surcoûts d'exécution. Lorsqu'une condition d'activation est évaluée à vrai, les sondes seront bientôt réactivées, et leurs gestionnaires commenceront à être appelés lorsque les événements se produiront. (Certains événements peuvent être perdus pendant l'intervalle d'activation. Si cela est inacceptable, n'utilisez pas de conditions d'activation pour ces sondes.) Exemple de syntaxe :

probe timer.us(TIMER) if (enabled) {
}

De nouveaux points de sonde peuvent être définis à l'aide d'"alias". Les alias de points de sonde ressemblent aux définitions de sonde, mais au lieu d'activer une sonde au point donné, ils définissent simplement un nouveau nom de point de sonde comme alias d'un point existant. Il existe deux types d'alias : le style prologue et le style épilogue, identifiés respectivement par "=" et "+=".

Pour l'alias de style prologue, le bloc d'instructions qui suit une définition d'alias est implicitement ajouté en prologue à toute sonde qui fait référence à l'alias. Alors que pour l'alias de style épilogue, le bloc d'instructions qui suit une définition d'alias est implicitement ajouté en épilogue à toute sonde qui fait référence à l'alias. Par exemple :

probe syscall.read = kernel.function("sys_read") {
  fildes = $fd
  if (execname() == "init") next  # sauter le reste de la sonde
}

définit un nouveau point de sonde syscall.read, qui s'étend à kernel.function("sys_read"), avec l'instruction donnée comme prologue, ce qui est utile pour prédéfinir certaines variables pour l'utilisateur de l'alias et/ou pour sauter complètement le traitement de la sonde en fonction de certaines conditions. Et

probe syscall.read += kernel.function("sys_read") {
  if (tracethis) println ($fd)
}

définit un nouveau point de sonde avec l'instruction donnée comme épilogue, ce qui est utile pour prendre des mesures basées sur des variables définies ou laissées par l'utilisateur de l'alias. Veuillez noter que dans chaque cas, les instructions dans le bloc de gestionnaire d'alias sont traitées normalement, de sorte que les variables qui y sont assignées ne constituent qu'une initialisation, pas une substitution de macro.

Les alias peuvent également être définis pour inclure à la fois un prologue et un épilogue.

probe syscall.read = kernel.function("sys_read") {
  fildes = $fd
  if (execname() == "init") next
},{
  if (tracethis) println ($fd)
}

Un alias est utilisé comme un type de sonde intégré.

probe syscall.read {
  printf("lecture fd=%d\n", fildes)
  if (fildes > 10) tracethis = 1
}

Les sondes avec un alias peuvent utiliser le prédicat @probewrite. Cette vérification est utilisée pour détecter si une variable de script ou une variable cible a été écrite dans le corps du gestionnaire de sonde.

@probewrite(var)
s'étend à 1 si var a été écrit dans le corps du gestionnaire de sonde, sinon il s'étend à 0.

Dans l'exemple suivant, @probewrite(var) s'étend à 1 car var a été écrit dans le corps du gestionnaire de sonde et par conséquent, l'instruction conditionnelle sera exécutée.

probe foo = begin { var = 0 }, { if (@probewrite(var)) println(var) }
probe foo {
  var = 1
}

FONCTIONS

Les scripts Systemtap peuvent définir des sous-programmes pour factoriser le travail commun. Les fonctions acceptent n'importe quel nombre d'arguments scalaires (entier ou chaîne), et doivent retourner un seul scalaire (entier ou chaîne). Un exemple de déclaration de fonction ressemble à ceci :

function thisfn (arg1, arg2) {
   return arg1 + arg2
}

Notez l'absence générale de déclarations de type, qui sont plutôt inférées par le traducteur. Cependant, si désiré, une définition de fonction peut inclure des déclarations de type explicites pour sa valeur de retour et/ou ses arguments. Ceci est particulièrement utile pour les fonctions C embarquées. Dans l'exemple suivant, le moteur d'inférence de type n'a besoin d'inférer que le type de arg2 (une chaîne).

function thatfn:string (arg1:long, arg2) {
   return sprint(arg1) . arg2
}

Les fonctions peuvent appeler d'autres fonctions ou se rappeler récursivement, jusqu'à une limite de profondeur fixe. Cette limite est définie par la macro MAXNESTING dans le code C traduit et est de l'ordre de 10.

Les fonctions peuvent être marquées comme privées à l'aide du mot-clé private pour limiter leur portée au tapset ou au fichier de script utilisateur dans lequel elles sont définies. Un exemple de définition de fonction privée suit :

private function three:long () { return 3 }

Les fonctions qui se terminent sans atteindre une instruction de retour explicite retourneront un 0 ou une chaîne vide "" implicite, déterminé par l'inférence de type.

Les fonctions peuvent être surchargées à la fois au moment de l'exécution et au moment de la compilation.

Le surcharge d'exécution permet de sélectionner la fonction exécutée pendant que le module tourne, en fonction des conditions d'exécution et est réalisé en utilisant l'instruction "next" dans les fonctions de script et la macro STAP_NEXT pour les fonctions C embarquées. Par exemple,

function f() { if (condition) next; print("first function") }
function f() %{ STAP_NEXT; print("second function") %}
function f() { print("third function") }

Lors d'un appel de fonction f(), l'exécution sera transférée à la troisième fonction si la condition est évaluée à vrai et imprimera "third function". Notez que la deuxième fonction est inconditionnellement passée.

La surcharge de paramètre permet de sélectionner la fonction à exécuter au moment de la compilation en fonction du nombre d'arguments fournis à l'appel de fonction. Par exemple,

function g() { print("first function") }
function g(x) { print("second function") }
g() -> "first function"
g(1) -> "second function"

Notez que la surcharge d'exécution ne se produit pas dans l'exemple ci-dessus, car une seule fonction sera résolue pour l'appel de fonction. L'utilisation d'une instruction next à l'intérieur d'une fonction alors qu'il ne reste plus de surcharges déclenchera une exception d'exécution. La surcharge d'exécution ne se produira que si les fonctions ont la même arité ; les fonctions de même nom mais avec un nombre différent de paramètres ne sont absolument pas liées.

L'ordre d'exécution est déterminé par une valeur de priorité qui peut être spécifiée. Si aucune priorité explicite n'est spécifiée, les fonctions de script utilisateur reçoivent une priorité plus élevée que les fonctions de bibliothèque. Les fonctions de script utilisateur et les fonctions de bibliothèque se voient attribuer une valeur de priorité par défaut de 0 et 1 respectivement. Les fonctions ayant la même priorité sont exécutées dans l'ordre de déclaration. Par exemple,

function f():3 { if (condition) next; print("first function") }
function f():1 { if (condition) next; print("second function") }
function f():2 { print("third function") }

Étant donné que la deuxième fonction a la priorité la plus élevée, elle est exécutée en premier. La première fonction n'est jamais exécutée car il n'y a pas d'instructions "next" dans la troisième fonction pour transférer l'exécution.

IMPRESSION

Il existe un ensemble de noms de fonctions qui sont spécialement traités par le traducteur. Ils formatent les valeurs pour l'impression sur le flux de sortie standard de systemtap de manière plus pratique (notez que les données générées dans le module noyau doivent être transférées dans l'espace utilisateur pour être imprimées).


Les variantes sprint* retournent la chaîne formatée au lieu de l'imprimer.

print, sprint
Imprime une ou plusieurs valeurs de n'importe quel type, concaténées directement ensemble.
println, sprintln
Imprime les valeurs comme print et sprint, mais ajoute également un saut de ligne.
printd, sprintd
Prend une chaîne délimiteur et deux ou plusieurs valeurs de n'importe quel type, et imprime les valeurs avec le délimiteur intercalé. Le délimiteur doit être une constante de chaîne littérale.
printdln, sprintdln
Imprime les valeurs avec un délimiteur comme printd et sprintd, mais ajoute également un saut de ligne.
printf, sprintf
Prend une chaîne de formatage et un nombre de valeurs de types correspondants, et les imprime toutes. Le format doit être une constante de chaîne littérale.

Les directives de formatage printf sont similaires à celles de C, sauf qu'elles sont entièrement vérifiées par le traducteur :

%b
Écrit un bloc binaire de la valeur donnée, au lieu d'un texte ASCII. Le spécificateur de largeur détermine le nombre d'octets à écrire ; les spécificateurs valides sont %b %1b %2b %4b %8b. Par défaut (%b) est de 8 octets.
%c
Caractère.
%d,%i
Entier signé décimal.
%m
Lit en toute sécurité la mémoire du noyau (sans #) ou de l'utilisateur (avec #) à l'adresse donnée, et en affiche le contenu. Le spécificateur de précision optionnel (pas la largeur du champ) détermine le nombre d'octets à lire - par défaut 1 octet. %10.4m imprime 4 octets de la mémoire dans un champ de 10 caractères de large. Notez que sur certaines architectures, la mémoire utilisateur peut toujours être lue sans #.
%M
Identique à %m, mais affiche en hexadécimal. La taille minimale de la sortie est le double du spécificateur de précision optionnel - par défaut 1 octet (2 caractères hexadécimaux). %10.4M imprime 4 octets de la mémoire sous forme de 8 caractères hexadécimaux dans un champ de 10 caractères de large. %.*M dumps en hexadécimal un nombre donné d'octets à partir d'un tampon donné.
%o
Entier non signé octal.
%p
Adresse de pointeur non signée.
%s
Chaîne de caractères.
%u
Entier décimal non signé.
%x
Valeur hexadécimale non signée, en minuscules.
%X
Valeur hexadécimale non signée, en majuscules.
%%
Écrit un %.

Le drapeau # sélectionne les formes alternatives. Pour l'octal, il préfixe un 0. Pour l'hexadécimal, il préfixe 0x ou 0X, selon la casse. Pour les caractères, il échappe les valeurs non imprimables avec des échappements de type C ou des octales brutes. Dans le cas de %#m/%#M, cela accède en toute sécurité à la mémoire de l'espace utilisateur plutôt qu'à la mémoire de l'espace noyau.

Exemples :

a = "alice", b = "bob", p = 0x1234abcd, i = 123, j = -1, id[a] = 1234, id[b] = 4567
print("hello")
	Imprime : hello
println(b)
	Imprime : bob\n
println(a . " is " . sprint(16))
	Imprime : alice is 16
foreach (name in id)  printdln("|", strlen(name), name, id[name])
	Imprime : 5|alice|1234\n3|bob|4567
printf("%c is %s; %x or %X or %p; %d or %u\n",97,a,p,p,p,j,j)
	Imprime : a is alice; 1234abcd or 1234ABCD or 0x1234abcd; -1 or 18446744073709551615\n
printf("2 bytes of kernel buffer at address %p: %2m", p, p)
	Imprime : 2 byte of kernel buffer at address 0x1234abcd: <binary data>
printf("%4b", p)
	Imprime (ces valeurs en données binaires) : 0x1234abcd
printf("%#o %#x %#X\n", 1, 2, 3)
	Imprime : 01 0x2 0X3
printf("%#c %#c %#c\n", 0, 9, 42)
	Imprime : \000 \t *

STATISTIQUES

Il est souvent souhaitable de collecter des statistiques d'une manière qui évite les pénalités liées au verrouillage exclusif répété des variables globales dans lesquelles ces chiffres sont stockés. Systemtap offre une solution utilisant un opérateur spécial pour accumuler les valeurs, et plusieurs pseudo-fonctions pour extraire les agrégats statistiques.

L'opérateur d'agrégation est <<<, et ressemble à une affectation, ou à une opération de streaming de sortie C++. L'opérande gauche spécifie une lvalue scalaire ou d'index de tableau, qui doit être déclarée globale. L'opérande droit est une expression numérique. La signification est intuitive : ajouter le nombre donné à la pile de nombres pour calculer des statistiques. (La liste spécifique des statistiques à collecter est donnée séparément, par les fonctions d'extraction.)

foo <<< 1
stats[pid()] <<< memsize

Les fonctions d'extraction sont également spéciales. Pour chaque apparition d'une fonction d'extraction distincte opérant sur un identifiant donné, le traducteur s'arrange pour calculer un ensemble de statistiques qui la satisfont. Le système de statistiques est ainsi "à la demande". Chaque exécution d'une fonction d'extraction provoque le calcul de l'agrégation pour ce moment précis sur tous les processeurs.

Voici l'ensemble des fonctions d'extraction. Le premier argument de chacune est du même style que l'lvalue utilisée dans la partie gauche de l'opération d'accumulation. Les fonctions d'extraction @count(v), @sum(v), @min(v), @max(v), @avg(v), @variance(v[, b]) calculent le nombre/total/minimum/maximum/moyenne/variance de toutes les valeurs accumulées. Les valeurs résultantes sont toutes des entiers simples. Les tableaux contenant des agrégats peuvent être triés et parcourus. Voir la construction foreach ci-dessus.

La variance utilise l'algorithme en ligne de Welford. Les calculs sont basés sur l'arithmétique entière et peuvent donc souffrir d'une faible précision et de dépassement. Pour améliorer cela, @variance(v[, b]) accepte un paramètre optionnel b, le décalage de bits, allant de 0 (par défaut) à 62, pour la mise à l'échelle interne. Une seule valeur de décalage de bits peut être utilisée avec une variable globale donnée. Une valeur de décalage de bits plus grande augmente la précision, mais augmente la probabilité de dépassement.

$ stap -e \
> 'global x probe oneshot { for(i=1;i<=5;i++) x<<<i println(@variance(x)) }'
12
$ stap -e \
> 'global x probe oneshot { for(i=1;i<=5;i++) x<<<i println(@variance(x,1)) }'
2
$ python3 -c 'import statistics; print(statistics
.variance([1, 2, 3, 4, 5]))' 2.5 $

Des dépassements (dus à la multiplication interne de grands nombres) peuvent se produire et entraîner un résultat de variance négatif. Envisagez de normaliser vos données d'entrée. L'ajout ou la soustraction d'une valeur fixe à toutes les entrées de variance préserve la variance d'origine. La division des entrées de variance par une valeur fixe réduit la variance d'origine d'autant au carré.

Les histogrammes sont également disponibles, mais ils sont plus compliqués car ils ont une valeur vectorielle plutôt que scalaire. @hist_linear(v,start,stop,interval) représente un histogramme linéaire de "start" à "stop" (inclus) par incréments de "interval". L'intervalle doit être positif. De même, @hist_log(v) représente un histogramme logarithmique en base 2. L'impression d'un histogramme avec la famille de fonctions print rend un objet histogramme sous forme de graphique à barres tabulaire en "art ASCII".

probe timer.profile {
  x[1] <<< pid()
  x[2] <<< uid()
  y <<< tid()
}
global x // un tableau contenant des agrégats
global y // un scalaire
probe end {
  foreach ([i] in x @count+) {
     printf ("x[%d]: avg %d = sum %d / count %d\n",
             i, @avg(x[i]), @sum(x[i]), @count(x[i]))
     println (@hist_log(x[i]))
  }
  println ("y:")        
  println (@hist_log(y))  
}

Les décomptes de chaque compartiment d'histogramme peuvent être individuellement accessibles via l'opérateur [index]. Chaque compartiment est adressé de 1 à N (pour chaque compartiment naturel). De plus, le compartiment n°0 compte tous les échantillons inférieurs à la valeur de début, et le compartiment n°N+1 compte tous les échantillons supérieurs à la valeur de fin. Les compartiments d'histogramme (y compris les deux compartiments hors limites) peuvent également être parcourus avec foreach.

global x
probe oneshot {
  x <<< -100
  x <<< 1
  x <<< 2
  x <<< 3
  x <<< 100
  foreach (bucket in @hist_linear(x,1,3,1))
    // attendu : 1 compartiment hors limite inférieure
    //             3 compartiments de données utiles
    //             1 compartiment hors limite supérieure
    printf("compartiment %d décompte %d\n",
           bucket, @hist_linear(x,1,3,1)[bucket])
}

CONVERSION DE TYPES

Une fois qu'un pointeur (voir la section VARIABLES DE CONTEXTE de stapprobes(3stap)) a été enregistré dans une variable entière du script, le traducteur tente de conserver les informations de type nécessaires pour accéder aux membres de ce pointeur.

Le traducteur tente de suivre le typage DWARF associé aux variables de script affectées à partir d'adresses de variables de contexte, des opérateurs @cast ou @var. Selon la complexité du code du script, cette association peut être transmise à des variables liées, de sorte que les opérateurs -> et [] puissent être utilisés sur celles-ci, tout comme sur la variable de contexte d'origine. Par exemple :

foo = $param->foo; printf("x:%d y:%d\n", foo->x, foo->y)
printf("ma valeur est %d\n", ($type == 42 ? $foo : $bar)->value)
printf("mon pid parent est %d\n", task_parent(task_current())->tgid)

Cependant, si cette heuristique d'association ne fonctionne pas pour un script, l'opérateur @cast() indique au traducteur comment interpréter le nombre comme un pointeur typé.

@cast(p, "nom_type"[, "module"])->membre

Cela interprétera p comme un pointeur vers une struct/union nommée nom_type et désérencera la valeur membre. D'autres expressions ->sous_champ peuvent être ajoutées pour désérencier plus de niveaux. Notez que pour la désérendérisation directe d'un pointeur, {kernel,user}_{char,int,...}($p) doit être utilisé. (Reportez-vous à stapfuncs(5) pour plus de détails.) NOTE : le même opérateur de désérendérisation -> est utilisé pour faire référence à la fois au confinement direct ou à l'indirection de pointeur. Systemtap détermine automatiquement lequel. Le module optionnel indique au traducteur où rechercher les informations sur ce type. Plusieurs modules peuvent être spécifiés sous forme de liste avec des séparateurs :. Si le module n'est pas spécifié, il sera par défaut soit le module de sonde pour les sondes dwarf, soit "kernel" pour les fonctions et tous les autres types de sondes.

Précédemment, jusqu'à la version 4.2 de systemtap, "kernel" était inféré si non spécifié. Utilisez --compatible=4.2 pour activer cette valeur par défaut.

Le traducteur peut créer son propre module avec des informations de type à partir d'un en-tête entouré d'accolades. Si les informations de débogage normales ne sont pas disponibles. Pour les en-têtes du noyau, préfixez-le avec "kernel" pour utiliser le système de construction approprié. Tous les autres en-têtes sont construits avec des paramètres GCC par défaut dans un module utilisateur. Plusieurs en-têtes peuvent être spécifiés en séquence pour résoudre une codépendance.

Depuis la version 5.4 de systemtap, l'en-tête du noyau "<vmlinux.h>" est essayé avant tout en-tête ou module du noyau spécifié, ce qui peut rendre inutile la liste de noms de modules ou de fichiers d'en-tête explicites pour les structures de données du noyau.

@cast(tv, "timeval", "<sys/time.h>")->tv_sec
@cast(task, "task_struct", "kernel<linux/sched.h>")->tgid
@cast(task, "task_struct",
      "kernel<linux/sched.h><linux/fs_struct.h>")->fs->umask

Les valeurs acquises par @cast peuvent être joliment imprimées par les opérateurs suffixes $ et $$, de la même manière que décrit dans la section VARIABLES DE CONTEXTE de la page de manuel stapprobes(3stap).

En mode guru, le traducteur permettra également aux scripts d'affecter de nouvelles valeurs aux membres des pointeurs transtypés.

La conversion de types est également utile dans le cas de membres void* dont le type peut être déterminé à l'exécution.

probe foo {
  if ($var->type == 1) {
    value = @cast($var->data, "type1")->bar
  } else {
    value = @cast($var->data, "type2")->baz
  }
  print(value)
}

C INTÉGRÉ

En mode guru, le traducteur accepte du code C intégré au niveau supérieur du script. Ce code est délimité par les marqueurs %{ et %}, et est transcrit verbatim, sans analyse, dans un ordre donné, au niveau supérieur du code C généré. Au niveau le plus externe, cela peut être utile pour ajouter des instructions #include et des définitions auxiliaires à utiliser par d'autres codes intégrés.

Un autre endroit où le code intégré est autorisé est le corps d'une fonction. Dans ce cas, le corps du langage de script est entièrement remplacé par un morceau de code C délimité à nouveau par les marqueurs %{ et %}. Ce code C peut faire tout ce qui est raisonnable et sûr. Il existe un certain nombre de contraintes de sécurité non documentées mais complexes sur l'atomicité, la concurrence, la consommation de ressources et les limites d'exécution, il s'agit donc d'une technique avancée.

Les emplacements mémoire réservés aux valeurs d'entrée et de sortie leur sont rendus accessibles à l'aide des macros STAP_ARG_* et STAP_RETVALUE. Les erreurs peuvent être signalées avec STAP_ERROR. Les sorties peuvent être écrites avec STAP_PRINTF. La fonction peut retourner prématurément avec STAP_RETURN. Voici quelques exemples :

function integer_ops (val) %{
  STAP_PRINTF("%d\n", STAP_ARG_val);
  STAP_RETVALUE = STAP_ARG_val + 1;
  if (STAP_RETVALUE == 4)
      STAP_ERROR("mauvaise supposition : %d", (int) STAP_RETVALUE);
  if (STAP_RETVALUE == 3)
      STAP_RETURN(0);
  STAP_RETVALUE ++;
%}
function string_ops (val) %{
  strlcpy (STAP_RETVALUE, STAP_ARG_val, MAXSTRINGLEN);
  strlcat (STAP_RETVALUE, "one", MAXSTRINGLEN);
  if (strcmp (STAP_RETVALUE, "three-two-one"))
      STAP_RETURN("le paramètre devrait être three-two-");
%}
function no_ops () %{
    STAP_RETURN(); /* fonction déduite sans valeur de retour */
%}

Les types des arguments et des valeurs de retour de la fonction doivent être inférés par le traducteur à partir des sites d'appel pour que cela fonctionne. L'utilisateur doit examiner le code C généré pour les fonctions ordinaires en langage de script afin d'écrire des fonctions C intégrées compatibles.

Le dernier endroit où le code intégré est autorisé est une valeur rvalue d'expression. Dans ce cas, le code C délimité par les marqueurs %{ et %} est interprété comme une valeur d'expression normale. Il est supposé être un nombre signé normal de 64 bits, à moins que le marqueur /* string */ ne soit inclus, auquel cas il est traité comme une chaîne.

function add_one (val) {
  return val + %{ 1 %}
}
function add_string_two (val) {
  return val . %{ /* chaîne */ "deux" %}
}
@define SOME_STAP_MACRO %( %{ SOME_C_MACRO %} %)
probe begin {
      printf("LA MACRO SOME_C_MACRO a la valeur : %d\n", @SOME_STAP_MACRO);
}

Le code C intégré peut contenir des marqueurs pour affirmer les propriétés d'optimisation et de sécurité.

/* pure */
signifie que le code C n'a pas d'effets de bord et peut être entièrement supprimé si sa valeur n'est pas utilisée par le code du script.
/* stable */
signifie que le code C a toujours la même valeur (dans toute invocation de gestionnaire de sonde donnée), donc les appels répétés peuvent être automatiquement remplacés par des valeurs mémoïsées. De telles fonctions ne doivent prendre aucun paramètre et être également pure.
/* unprivileged */
signifie que le code C est si sûr que même les utilisateurs non privilégiés sont autorisés à l'utiliser.
/* myproc-unprivileged */
signifie que le code C est si sûr que même les utilisateurs non privilégiés sont autorisés à l'utiliser, à condition que la cible de la sonde actuelle soit à l'intérieur du propre processus de l'utilisateur.
/* guru */
signifie que le code C est si dangereux qu'un utilisateur de systemtap doit spécifier -g (mode guru) pour l'utiliser. (Les tapsets sont autorisés et supposés les appeler en toute sécurité.)
/* unmangled */
dans une fonction C intégrée, signifie que la syntaxe d'accès aux arguments héritée (avant 1.8) doit être disponible à l'intérieur de la fonction. Par conséquent, en plus de STAP_ARG_foo et STAP_RETVALUE, on peut utiliser THIS->foo et THIS->__retvalue respectivement à l'intérieur de la fonction. Ceci est utile pour migrer rapidement du code écrit pour SystemTap version 1.7 et antérieures.
/* pragma:suffix */
Émettre le fichier contenant le code C à la fin du fichier source du module noyau résultant.
/* unmodified-fnargs */
dans une fonction C intégrée, signifie que les arguments de la fonction ne sont pas modifiés dans le corps de la fonction.
/* string */
dans les expressions C intégrées uniquement, signifie que l'expression a un type const char * et doit être traitée comme une chaîne de caractères, au lieu du nombre entier long par défaut.

Les variables globales au niveau du script peuvent être accédées dans les fonctions et blocs C intégrés. Pour lire ou écrire la variable globale var, le marqueur /* pragma:read:var */ ou /* pragma:write:var */ doit d'abord être placé dans la fonction ou le bloc C intégré. Ceci fournit les macros STAP_GLOBAL_GET_* et STAP_GLOBAL_SET_* pour permettre

reading and writing, respectivement. Par exemple :

global var
global var2[100]
function increment() %{
    /* pragma:read:var */ /* pragma:write:var */
    /* pragma:read:var2 */ /* pragma:write:var2 */
    STAP_GLOBAL_SET_var(STAP_GLOBAL_GET_var()+1); //var++
    STAP_GLOBAL_SET_var2(1, 1, STAP_GLOBAL_GET_var2(1, 1)+1); //var2[1,1]++
%}

Les variables peuvent être lues et définies dans les fonctions embarquées en C et dans les expressions. Les chaînes de caractères renvoyées par le code embarqué en C sont ramenées à des pointeurs. Les variables doivent également être assignées au niveau du script pour permettre l'inférence de type. L'affectation de mappe ne renvoie pas la valeur écrite, donc le chaînage ne fonctionne pas.

DEREFERENCING

Les entiers peuvent être déréférencés à partir de pointeurs sauvegardés en tant que variables entières de script en utilisant les opérateurs @kderef() ou @uderef(). @kderef() est utilisé pour les adresses de l'espace noyau et @uderef() est utilisé pour les adresses de l'espace utilisateur.

@kderef(SIZE, addr)
@uderef(SIZE, addr)

Cela interprétera addr comme une adresse noyau/utilisateur et lira SIZE octets à partir de cette adresse. SIZE doit être 1, 2, 4 ou 8 octets.

Le registre d'intérêt est spécifié en utilisant son numéro DWARF.

@uregister(5)

TRAITEMENT

Le traducteur commence la passe 1 en analysant le script d'entrée donné, et tous les scripts (fichiers nommés *.stp) trouvés dans un répertoire tapset. Les répertoires listés avec -I sont traités séquentiellement, chacun étant traité en mode "guru". Pour chaque répertoire, un certain nombre de sous-répertoires sont également recherchés. Ces sous-répertoires sont dérivés de la version du noyau sélectionnée (option -R), afin de permettre à des scripts plus spécifiques à une version du noyau de remplacer ceux moins spécifiques. Par exemple, pour une version de noyau 2.6.12-23.FC3, les motifs suivants seraient recherchés, séquentiellement : 2.6.12-23.FC3/*.stp, 2.6.12/*.stp, 2.6/*.stp, et enfin *.stp. Arrêter le traducteur après la passe 1 lui fait imprimer les arbres d'analyse syntaxique.

En passe 2, le traducteur analyse le script d'entrée pour résoudre les symboles et les types. Les références à des variables, fonctions et alias de sonde qui ne sont pas résolus en interne sont satisfaites en recherchant dans les fichiers de script tapset analysés. Si un fichier de script tapset est sélectionné parce qu'il définit un symbole non résolu, alors l'intégralité de ce fichier est ajoutée à la file de résolution du traducteur. Ce processus itère jusqu'à ce que tous les symboles soient résolus et qu'un sous-ensemble de fichiers de script tapset soit sélectionné.

Ensuite, toutes les descriptions des points de sonde sont validées par rapport à la grande variété supportée par le traducteur. Les points de sonde qui font référence à des emplacements de code ("points de sonde synchrones") nécessitent l'installation des informations de débogage du noyau appropriées. Dans les gestionnaires de sonde associés, les variables côté cible (dont les noms commencent par "$") sont trouvées et leurs emplacements d'exécution sont décodés.

Ensuite, toutes les sondes et fonctions sont analysées pour détecter les opportunités d'optimisation, afin de supprimer les variables, expressions et fonctions qui n'ont aucune valeur utile et aucun effet secondaire. Les fonctions embarquées en C sont supposées avoir des effets secondaires, sauf si elles incluent la chaîne magique /* pure */. Étant donné que cette optimisation peut masquer des erreurs de code latentes telles que des incompatibilités de types ou des variables $context invalides, il peut parfois être utile de désactiver les optimisations avec l'option -u.

Enfin, tous les types de variables, fonctions, paramètres, tableaux et indices sont déduits du contexte (littéraux et opérateurs). Arrêter le traducteur après la passe 2 lui fait lister toutes les sondes, fonctions et variables, ainsi que tous les types déduits. Tous les types incohérents ou non résolus provoquent une erreur.

En passe 3, le traducteur écrit du code C qui représente les actions de tous les fichiers de script sélectionnés, et crée un Makefile pour le compiler en un objet noyau. Ces fichiers sont placés dans un répertoire temporaire. Arrêter le traducteur à ce stade lui fait imprimer le contenu du fichier C.

En passe 4, le traducteur invoque le système de construction du noyau Linux pour créer le fichier objet noyau réel. Cela implique d'exécuter make dans le répertoire temporaire, et nécessite qu'un système de construction de modules noyau (en-têtes, configuration et Makefiles) soit installé à l'emplacement habituel /lib/modules/VERSION/build. Arrêter le traducteur après la passe 4 est la dernière chance avant d'exécuter l'objet noyau. Cela peut être utile si vous souhaitez archiver le fichier.

En passe 5, le traducteur invoque le programme utilitaire staprun de systemtap pour l'objet noyau donné. Ce programme organise le chargement du module puis communique avec lui, copiant les données de trace du noyau vers des fichiers temporaires, jusqu'à ce que l'utilisateur envoie un signal d'interruption. Toute erreur d'exécution rencontrée par les gestionnaires de sonde, comme un manque de mémoire, une division par zéro, le dépassement des limites de récursion ou d'exécution, entraîne une indication d'erreur douce. Les erreurs douces dépassant un bloc MAXERRORS bloquent toutes les sondes ultérieures (sauf les sondes de gestion d'erreurs) et terminent la session. Enfin, staprun décharge le module et nettoie.

TERMINAISON ANORMALE

Il faut éviter de tuer le processus stap de force, par exemple avec SIGKILL, car le processus stapio (un processus enfant du processus stap) et le module chargé peuvent rester en cours d'exécution sur le système. Si cela se produit, envoyez SIGTERM ou SIGINT aux processus stapio restants, puis utilisez rmmod pour décharger le module systemtap.

MISE EN CACHE

Le traducteur systemtap met en cache la sortie de la passe 3 (le code C généré) et la sortie de la passe 4 (le module noyau compilé) si la passe 4 se termine avec succès. Cette sortie mise en cache est réutilisée si le même script est traduit à nouveau, en supposant que les mêmes conditions existent (même version de noyau, même version de systemtap, etc.). Les fichiers mis en cache sont stockés dans le répertoire $SYSTEMTAP_DIR/cache. La taille du cache peut être limitée en plaçant le fichier cache_mb_limit dans le répertoire de cache (indiqué ci-dessus) contenant uniquement un entier ASCII représentant la limite en MiB du cache. En l'absence de ce fichier, une valeur par défaut sera créée avec la limite fixée à 256MiB. Il s'agit d'une limite "douce" dans le sens où le cache sera nettoyé après l'ajout d'une nouvelle entrée si l'intervalle de nettoyage du cache est dépassé, de sorte que la taille totale du cache peut temporairement dépasser cette limite. Cet intervalle peut être spécifié en plaçant le fichier cache_clean_interval_s dans le répertoire de cache (indiqué ci-dessus) contenant uniquement un entier ASCII représentant l'intervalle en secondes. En l'absence de ce fichier, une valeur par défaut sera créée avec l'intervalle fixé à 300 s.

SÉCURITÉ ET SÛRETÉ

Systemtap peut être utilisé comme un outil administratif puissant. Il peut exposer des structures de données internes du noyau et potentiellement des informations privées de l'utilisateur. (En mode d'exécution dyninst, ce n'est pas le cas, voir la section ALTERNATE RUNTIMES ci-dessous.)

Le traducteur fait respecter de nombreuses contraintes de sécurité lors de la compilation et davantage lors de l'exécution. Il vise à garantir qu'aucune routine de gestion ne puisse s'exécuter trop longtemps, allouer une mémoire sans limite, effectuer des opérations dangereuses ou interférer involontairement avec le système. Les utilisations des variables globales du script sont automatiquement verrouillées en lecture/écriture de manière appropriée, pour éviter toute manipulation par des gestionnaires de sonde concurrents. Les verrous sont pris de manière à exécuter la partie manipulation des variables globales des gestionnaires de sonde de manière atomique (les verrous sont pris tous ou rien). Les interblocages sont détectés avec des timeouts. Utilisez l'option -t pour recevoir des rapports de contention excessive de verrous. L'expérimentation avec les scripts est donc généralement sûre. L'option de mode guru -g permet aux administrateurs de contourner la plupart des mesures de sécurité, ce qui autorise des opérations invasives ou modifiant l'état, du code embarqué en C, et augmente le risque de perturbations. Par défaut, la prévention de surcharge est activée pour tous les modules. Si vous souhaitez désactiver le traitement de surcharge, utilisez l'option --suppress-time-limits.

Les erreurs détectées à l'exécution entraînent normalement un arrêt propre du script et un message d'erreur de passe 5. L'option --suppress-handler-errors permet aux scripts de tolérer les erreurs douces sans arrêt.

AUTORISATIONS

Pour l'exécution normale du module noyau Linux, pour exécuter les objets noyau que systemtap crée, un utilisateur doit être l'un des suivants :

  • l'utilisateur root ;
  • un membre des groupes stapdev et stapusr ;
  • un membre des groupes stapsys et stapusr ; ou
  • un membre du groupe stapusr.

L'utilisateur root ou un utilisateur membre des groupes stapdev et stapusr peut créer et exécuter n'importe quel script systemtap.

Un utilisateur membre des groupes stapsys et stapusr ne peut utiliser que des modules pré-compilés sous les conditions suivantes :

  • Le module a été signé par un signataire de confiance. Les signataires de confiance sont normalement les serveurs de compilation systemtap qui signent les modules lorsque l'option --privilege est spécifiée par le client. Voir la page de manuel stap-server(8) pour plus d'informations.
  • Le module a été créé en utilisant les options --privilege=stapsys ou --privilege=stapusr.

Les membres du groupe stapusr uniquement peuvent utiliser des modules pré-compilés sous les conditions suivantes :

•
Lemodule se trouve dans le répertoire /lib/modules/VERSION/systemtap. Ce répertoire doit appartenir à root et ne doit pas être accessible en écriture à tout le monde.

ou

  • Le module a été signé par un signataire de confiance. Les signataires de confiance sont normalement les serveurs de compilation systemtap qui signent les modules lorsque l'option --privilege est spécifiée par le client. Voir la page de manuel stap-server(8) pour plus d'informations.
  • Le module a été construit en utilisant l'option --privilege=stapusr.

Les modules du noyau générés par le programme stap sont exécutés par le programme staprun. Ce dernier fait partie du package Systemtap, dédié au chargement et au déchargement des modules (mais uniquement dans la zone blanche), et au transfert de données du noyau vers l'utilisateur. Comme staprun n'effectue aucune vérification de sécurité supplémentaire sur les objets du noyau qui lui sont donnés, il serait imprudent pour un administrateur système d'ajouter des utilisateurs non fiables aux groupes stapdev ou stapusr.

SECUREBOOT

Si le système actuel a SecureBoot activé dans le firmware UEFI, tous les modules du noyau doivent être signés. (Certains noyaux peuvent permettre de désactiver SecureBoot bien après le démarrage avec une séquence de touches comme SysRq-X, rendant inutile la signature des modules.) Il existe deux façons de signer un module systemtap. Le serveur de compilation systemtap peut signer les modules avec une clé MOK (Machine Owner Key) qu'il partage avec un système client. Par exemple :

stap --use-server=HOSTNAME:PORT -e 'SCRIPT'
# S'il n'y a pas de clé mok commune entre la liste des clés mok du systemtap du serveur et la base de données mok du client, l'utilisateur est invité par stap à invoquer : 
sudo mokutil --import signing_key.x509
# puis après le redémarrage du système :
stap --use-server=HOSTNAME:PORT -e 'SCRIPT'
# utilisera le serveur pour construire et signer le module, et le module s'exécutera
# sur le client

Une autre façon de signer des modules est d'utiliser l'option stap --sign-module, qui utilise une clé MOK sur le système client sans utiliser de serveur. Par exemple :

stap --sign-module -e 'SCRIPT'
# S'il n'y a pas de clé mok systemtap dans la base de données mok du système
# l'utilisateur est invité par stap à invoquer :
sudo mokutil --import /home/USER/.systemtap/ssl/server/moks/FINGERPRINT/signing_key.x509
# puis après le redémarrage du système :
stap --sign-module -e 'SCRIPT'
# signera et exécutera le module

Voir la page wiki suivante pour plus de détails :

https://sourceware.org/systemtap/wiki/SecureBoot

Certains noyaux ne permettent pas à systemtap de deviner si la signature de module est activée. Sur de telles machines, définissez la variable d'environnement SYSTEMTAP_SIGN à n'importe quelle valeur tout en exécutant stap.

LIMITES DE RESSOURCES

De nombreuses limites d'utilisation des ressources sont définies par des macros dans le code C généré. Celles-ci peuvent être remplacées par des options -D. Une sélection de ces options est la suivante :

MAXNESTING
Nombre maximal d'appels de fonctions imbriqués. La valeur par défaut est déterminée par l'analyse du script, avec 10 emplacements supplémentaires ajoutés pour les scripts récursifs.
MAXSTRINGLEN
Longueur maximale des chaînes, par défaut 128.
MAXTRYLOCK
Nombre maximal d'itérations pour attendre les verrous sur les variables globales avant de déclarer un possible interblocage et d'ignorer la sonde, par défaut 1000.
MAXACTION
Nombre maximal d'instructions à exécuter lors d'un seul déclenchement de sonde (avec les interruptions désactivées), par défaut 1000. Notez que pour les gestionnaires de sondes directs sans boucles ni récursion, en raison de l'optimisation, ce paramètre peut être interprété de manière trop conservatrice.
MAXACTION_INTERRUPTIBLE
Nombre maximal d'instructions à exécuter lors d'un seul déclenchement de sonde qui est exécuté avec les interruptions activées (comme les sondes begin/end), par défaut (MAXACTION * 10).
MAXBACKTRACE
Nombre maximal d'images de pile qui seront traitées par le décodeur d'exécution de stap comme produit par les fonctions de backtrace dans les tapsets [u]context-unwind.stp, par défaut 20.
MAXMAPENTRIES
Nombre maximal de lignes dans un tableau global unique, par défaut 2048. Les tableaux individuels peuvent être déclarés avec une limite plus grande ou plus petite à la place : 
global big[10000],little[5]

ou désignés avec % pour les faire s'enrouler (remplacer les anciennes entrées) automatiquement, comme dans

global big%

ou les deux.

MAPHASHBIAS
Le nombre de puissances de deux à ajouter ou soustraire de la taille naturelle de la table de hachage qui soutient chaque tableau associatif global. La valeur par défaut est 0. Essayez de petits nombres positifs pour obtenir des performances supplémentaires au détriment d'une consommation de mémoire plus importante, car cela devrait réduire les collisions de la table de hachage. Essayez de petits nombres négatifs pour le compromis inverse.
MAXERRORS
Nombre maximal d'erreurs légères avant le déclenchement d'une sortie, par défaut 0, ce qui signifie que la première erreur provoquera la sortie du script. Notez qu'avec l'option --suppress-handler-errors, cette limite n'est pas appliquée.
MAXSKIPPED
Nombre maximal de sondes ignorées avant le déclenchement d'une sortie, par défaut 100. L'exécution de systemtap en mode -t (chronométrage) donne plus de détails sur les sondes ignorées. Avec le réglage par défaut -DINTERRUPTIBLE=1, les sondes ignorées en raison de la réentrance ne sont pas accumulées contre cette limite. Notez qu'avec l'option --suppress-handler-errors, cette limite n'est pas appliquée.
MINSTACKSPACE
Nombre minimal d'octets de pile noyau libres requis pour exécuter un gestionnaire de sonde, par défaut 1024. Ce nombre doit être suffisamment grand pour les besoins du gestionnaire de sonde, plus une marge de sécurité.
MAXUPROBES
Nombre maximal de sondes de l'espace utilisateur (uprobes) armées simultanément, par défaut légèrement supérieur au nombre de points de sonde de l'espace utilisateur nommés dans le script. Ce pool doit être potentiellement grand car des objets uprobe individuels (environ 64 octets chacun) sont alloués pour chaque processus pour chaque sonde correspondante au niveau du script.
STP_MAXMEMORY
Quantité maximale de mémoire (en kilo-octets) que le module systemtap doit utiliser, par défaut illimitée. La taille de la mémoire comprend la taille du module lui-même, plus les allocations supplémentaires. Cela ne suit que les allocations directes par le runtime systemtap. Cela ne suit pas les allocations indirectes (comme celles faites par les internes des kprobes/uprobes/etc.).
STP_OVERLOAD_THRESHOLD, STP_OVERLOAD_INTERVAL
Nombre maximal de cycles machine dépensés dans les sondes sur n'importe quel CPU par intervalle donné, avant qu'une condition de surcharge ne soit déclarée et que le script ne soit arrêté. Les valeurs par défaut sont 500 millions et 1 milliard, afin de limiter la consommation CPU des scripts stap à environ 50 %.
STP_PROCFS_BUFSIZE
Taille des tampons de lecture de sonde procfs (en octets). La valeur par défaut est MAXSTRINGLEN. Cette valeur peut être remplacée pour chaque fichier procfs à l'aide du paramètre .maxsize(MAXSIZE) de la sonde de lecture procfs.

Avec des scripts contenant des sondes sur un chemin d'interruption quelconque, il est possible que ces interruptions surviennent au milieu d'un autre gestionnaire de sonde. La sonde dans le gestionnaire d'interruption serait ignorée dans ce cas pour éviter la réentrance. Pour contourner ce problème, exécutez stap avec l'option -DINTERRUPTIBLE=0 pour masquer les interruptions tout au long du gestionnaire de sonde. Cela ajoute une surcharge supplémentaire aux sondes, mais peut éviter la réentrance dans les cas problématiques courants. Cependant, les sondes dans les gestionnaires NMI et dans la chaîne d'appels du runtime stap peuvent toujours être ignorées en raison de la réentrance.

En cas de problème avec stap ou staprun après qu'une sonde a déjà commencé à s'exécuter, vous pouvez arrêter en toute sécurité les deux processus utilisateur et supprimer le module noyau de sonde actif avec rmmod. Les messages de trace en attente peuvent être perdus.

UTILISATEURS NON PRIVILÉGIÉS

Systemtap expose les structures de données internes du noyau et potentiellement des informations privées des utilisateurs. Pour cette raison, l'utilisation des capacités complètes de systemtap est limitée à root et aux utilisateurs qui sont membres des groupes stapdev et stapusr.

Cependant, un ensemble restreint de fonctionnalités de systemtap peut être rendu disponible aux utilisateurs de confiance non privilégiés. Ces utilisateurs sont membres du groupe stapusr uniquement, ou membres des groupes stapusr et stapsys. Ces utilisateurs peuvent charger des modules systemtap qui ont été compilés et certifiés par un serveur de compilation systemtap de confiance. Voir les descriptions des options --privilege et --use-server. Voir README.unprivileged dans le code source de systemtap pour des informations sur la configuration d'un serveur de compilation de confiance.

Les restrictions appliquées lorsque --privilege=stapsys est spécifié sont conçues pour empêcher les utilisateurs non privilégiés de :

•
nuire au système de manière malveillante.

Les restrictions appliquées lorsque --privilege=stapusr est spécifié sont conçues pour empêcher les utilisateurs non privilégiés de :

  • nuire au système de manière malveillante.
  • accéder à des informations qui ne seraient normalement pas disponibles à un utilisateur non privilégié.
  • perturber les performances des processus appartenant à d'autres utilisateurs du système. Une certaine surcharge pour le système en général est inévitable car les sondes de l'utilisateur non privilégié seront déclenchées aux moments appropriés. Ce que nous souhaiterions éviter, c'est l'interruption ciblée des processus d'un autre utilisateur qui ne serait normalement pas possible par un utilisateur non privilégié.

  • Les options suivantes ne peuvent pas être utilisées par le client du serveur de compilation : 
    -a, -B, -D, -I, -r, -R

RESTRICTIONS DE L'ENVIRONNEMENT

Les variables d'environnement suivantes ne doivent pas être définies pour tous les utilisateurs non privilégiés :

SYSTEMTAP_RUNTIME
SYSTEMTAP_TAPSET
SYSTEMTAP_DEBUGINFO_PATH

RESTRICTIONS TAPSET

En général, les fonctions tapset ne sont disponibles que pour les membres du groupe stapusr lorsqu'elles ne collectent pas d'informations auxquelles un programme ordinaire exécuté avec les privilèges de cet utilisateur se verrait refuser l'accès.

Il existe deux catégories de fonctions tapset non privilégiées. La première catégorie comprend des fonctions utilitaires qui sont disponibles inconditionnellement pour tous les utilisateurs ; celles-ci incluent des éléments tels que :

cpu:long ()
exit ()
str_replace:string (prnt_str:string, srch_str:string, rplc_str:string)

La seconde catégorie comprend les fonctions dites myproc-unprivileged qui ne peuvent collecter des informations qu'au sein de leurs propres processus. Les scripts qui souhaitent utiliser ces fonctions doivent tester le résultat de la fonction tapset is_myproc et ne l'appeler que si le résultat est 1. Le script se terminera immédiatement si l'une de ces fonctions est appelée par un utilisateur non privilégié dans une sonde d'un processus qui n'appartient pas à cet utilisateur. Des exemples de fonctions myproc-unprivileged incluent :

print_usyms (stk:string)
user_int:long (addr:long)
usymname:string (addr:long)

Une erreur de compilation est déclenchée lorsque toute fonction ne figurant pas dans l'une des catégories ci-dessus est utilisée par des membres du groupe stapusr uniquement.

Aucune autre fonction tapset intégrée ne peut être utilisée par les membres du groupe stapusr uniquement.

RUNTIMES ALTERNATIFS

Comme décrit ci-dessus, le mode d'exécution par défaut de systemtap implique la compilation et le chargement de modules noyau, avec divers compromis de sécurité présentés. Systemtap inclut maintenant deux nouveaux backends prototypes : --runtime=dyninst et --runtime=bpf.

--runtime=dyninst utilise Dyninst pour instrumenter les propres processus d'un utilisateur à l'exécution. Ce backend n'utilise pas de modules noyau et ne nécessite pas de privilèges root, mais il est limité quant aux types de sondes et autres constructions qu'un script peut utiliser. Le runtime dyninst fonctionne en mode attachement à la cible, il nécessite donc un processus -c COMMAND ou -x PID. Par exemple :

stap --runtime=dyninst -c 'stap -V' \
     -e 'probe process.function("main")
         { println("hi from dyninst!") }'

Il peut être nécessaire de désactiver une vérification selinux conflittuelle avec

# setsebool allow_execstack 1

--runtime=bpf compile le script utilisateur en programmes extended Berkeley Packet Filter (eBPF) au lieu d'un module noyau. Les programmes eBPF sont vérifiés par le noyau pour leur sécurité et sont exécutés par une machine virtuelle intégrée au noyau. Ce runtime est à un stade précoce de développement et manque actuellement de prise en charge d'un certain nombre de fonctionnalités disponibles dans le runtime par défaut. Veuillez consulter la page de manuel stapbpf(8) pour plus d'informations.

STATUT DE SORTIE

Le traducteur systemtap se termine généralement avec un code de succès de 0 si le script demandé a été traité et exécuté avec succès à travers le passage demandé. Sinon, des erreurs peuvent être imprimées sur stderr et un code d'échec est retourné. Utilisez -v ou -vp N pour augmenter la verbosité (globale ou par passage) afin d'identifier la source du problème.

En mode liste (-l et -L), les messages d'erreur sont normalement supprimés. Un code de succès de 0 est retourné si au moins une sonde correspondante a été trouvée.

Un script s'exécutant en passage 5 et interrompu par ^C / SIGINT est considéré comme réussi.

DÉPRÉCATION

Au fil du temps, certaines fonctionnalités du langage de script et de la bibliothèque tapset peuvent subir des changements incompatibles, de sorte qu'un script écrit pour une ancienne version de systemtap peut ne plus s'exécuter. Dans ces cas, il peut être utile d'exécuter systemtap avec le drapeau --compatible VERSION, en spécifiant la dernière version connue pour fonctionner. L'exécution de systemtap avec le drapeau --check-version affichera un avertissement si des éléments potentiellement incompatibles ont été analysés. Les détails historiques de la dépréciation se trouvent dans le fichier NEWS.

Le but de la facilité de dépréciation est d'améliorer l'expérience des scripts écrits pour les versions plus récentes de systemtap (en ajoutant de meilleures alternatives et en supprimant les alternatives anciennes, conflictuelles ou confuses), tout en permettant aux scripts écrits pour les versions plus anciennes de systemtap de continuer à fonctionner. La dépréciation est donc destinée à être un service aux utilisateurs (et un inconvénient pour les développeurs de systemtap), plutôt que l'inverse.

Veuillez noter que les identificateurs commençant par un trait de soulignement dans le tapset subissent parfois des changements qu'il est difficile de préserver la compatibilité, même avec les mécanismes de dépréciation. Évitez de vous y fier dans vos scripts ; proposez-les plutôt pour une promotion à un statut sans trait de soulignement.

STAP(1)

STAP - Un utilitaire d'interface pour SystemTap

SYNOPSIS

stap [options] [-] [scriptfile] [script args]

DESCRIPTION

La commande stap est l'interface utilisateur principale pour le système d'instrumentation SystemTap. Elle est utilisée pour compiler et exécuter des scripts SystemTap.

OPTIONS

-
Lit le script depuis l'entrée standard.
-d, --dump-module
Affiche le module noyau compilé.
-e, --execute
Compile et exécute le script.
-c, --command commande
Exécute le script uniquement lorsqu'une commande spécifiée est lancée.
-o, --output fichier
Spécifie un fichier de sortie pour les résultats.
-v, --verbose
Active le mode verbeux.
-h, --help
Affiche un message d'aide.

EXEMPLES

Exécuter un script simple :

stap mon_script.stp

Exécuter un script depuis l'entrée standard :

cat mon_script.stp | stap -
