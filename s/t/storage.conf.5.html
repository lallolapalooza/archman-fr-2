STORAGE.CONF(5) Documentation InterNetNews STORAGE.CONF(5)

NOM

storage.conf - Fichier de configuration du gestionnaire de stockage

DESCRIPTION

Le fichier pathetc/storage.conf contient les règles à utiliser pour attribuer des articles à différentes méthodes de stockage. Ces règles déterminent où les articles entrants seront stockés.

Le gestionnaire de stockage est une interface unifiée entre INN et une variété de méthodes de stockage différentes, permettant à l'administrateur de nouvelles de choisir entre différentes méthodes de stockage avec des compromis différents (ou même d'en utiliser plusieurs en même temps pour différents groupes de nouvelles, ou articles de tailles différentes). Le reste d'INN n'a pas besoin de se soucier du type de méthode de stockage utilisée pour un article donné ; le gestionnaire de stockage le déterminera automatiquement lorsque cet article sera récupéré via l'API de stockage. Notez que vous pourriez également vouloir consulter les options fournies dans inn.conf(5) concernant le stockage des articles.

Le fichier storage.conf se compose d'une série d'entrées de méthode de stockage. Les lignes vides et les lignes commençant par un signe dièse ("#") sont ignorées. Le nombre maximum de caractères par ligne est de 255. L'ordre des entrées dans ce fichier est important, voir ci-dessous.

Chaque entrée spécifie une méthode de stockage et un ensemble de règles. Les articles qui correspondent à toutes les règles d'une entrée de méthode de stockage seront stockés en utilisant cette méthode de stockage ; si un article correspond à plusieurs entrées de méthode de stockage, la première sera utilisée. Chaque entrée est formatée comme suit :

méthode <nom_méthode> {
    newsgroups: <wildmat>
    class: <classe_stockage>
    size: <taille_min>[,<taille_max>]
    expires: <temps_min>[,<temps_max>]
    options: <options>
    exactmatch: <bool>
    filtered: <bool>
    path: <wildmat>
}

Si des espaces ou des tabulations sont inclus dans une valeur, cette valeur doit être entourée de guillemets doubles (""). Si un signe dièse ("#") ou un guillemet double est censé être inclus textuellement dans une valeur, il doit être échappé avec "\".

<nom_méthode> est le nom d'une méthode de stockage à utiliser pour les articles qui correspondent aux règles de cette entrée. Les méthodes de stockage actuellement disponibles sont :

cnfs
timecaf
timehash
tradspool
trash

Voir la section "MÉTHODES DE STOCKAGE" ci-dessous pour plus de détails.

Les significations des clés dans chaque entrée de méthode de stockage sont les suivantes :

newsgroups: <wildmat>
Quels groupes de nouvelles sont stockés en utilisant cette méthode de stockage. <wildmat> est un motif uwildmat qui est comparé aux groupes de nouvelles auxquels un article est posté. Si storeonxref dans inn.conf est vrai, ce motif sera comparé aux noms de groupes de nouvelles dans le corps du champ d'en-tête Xref ; sinon, il sera comparé aux noms de groupes de nouvelles dans le corps du champ d'en-tête Newsgroups (voir inn.conf(5) pour une discussion sur les différences entre ces possibilités). Des expressions wildmat empoisonnées (expressions commençant par "@") sont autorisées et peuvent être utilisées pour exclure certains motifs de groupe : les articles postés en crosspost aux groupes de nouvelles empoisonnés ne seront pas stockés en utilisant cette méthode de stockage. Le motif <wildmat> est comparé dans l'ordre.

Il n'y a pas de motif de groupes de nouvelles par défaut ; si une entrée doit correspondre à tous les groupes de nouvelles, utilisez explicitement "newsgroups: *".

class: <classe_stockage>
Un identifiant pour cette entrée de méthode de stockage. <classe_stockage> doit être un nombre compris entre 0 et 255. Il doit être unique parmi toutes les entrées de ce fichier. Il est principalement utilisé pour spécifier les temps d'expiration par classe de stockage, comme décrit dans expire.ctl(5) ; "timehash" et "timecaf" définiront également le répertoire de premier niveau dans lequel les articles acceptés par cette classe de stockage sont stockés. Les classes de stockage peuvent être, par exemple, numérotées séquentiellement dans storage.conf.

L'attribution d'un nombre particulier à une classe de stockage est arbitraire mais permanente (car elle est utilisée dans les jetons de stockage). En fait, un article se voit attribuer une classe de stockage en fonction des règles de stockage en vigueur au moment de son arrivée. Cet identifiant ne changera pas même si storage.conf est modifié ultérieurement et que le même article aurait été attribué à une autre classe de stockage, s'il avait été reçu après cette modification. L'article est toujours parfaitement valide et récupérable. La seule différence concernera l'expiration avec groupbaseexpiry défini sur false dans inn.conf : les règles dans expire.ctl s'appliquent à la classe de stockage attribuée aux articles lors de leur arrivée.

size: <taille_min>[,<taille_max>]
Une plage de tailles d'articles (en octets) qui devraient être stockées en utilisant cette méthode de stockage. Si <taille_max> est 0 ou n'est pas spécifié, la taille maximale des articles est limitée uniquement par maxartsize dans inn.conf. Le champ size: est facultatif et peut être omis entièrement si vous souhaitez que des articles de n'importe quelle taille soient stockés dans cette méthode de stockage (si, bien sûr, ces articles remplissent toutes les autres exigences de cette entrée de méthode de stockage). Par défaut, <taille_min> est défini sur 0.
expires: <temps_min>[,<temps_max>]
Une plage de temps d'expiration d'articles qui devraient être stockées en utilisant cette méthode de stockage. Faites attention ; ceci est moins utile qu'il n'y paraît au premier abord. Ceci est basé **uniquement** sur le champ d'en-tête Expires de l'article, et non sur des politiques d'expiration locales ou quoi que ce soit dans expire.ctl ! Si <temps_min> est différent de zéro, alors cette entrée **ne correspondra pas** à un article sans champ d'en-tête Expires. Cette clé est donc vraiment utile uniquement pour attribuer des articles avec des temps d'expiration demandés plus longs à une méthode de stockage distincte. Les articles ne correspondent que si le temps jusqu'à l'expiration (c'est-à-dire la durée pendant laquelle le champ d'en-tête Expires de l'article demande qu'il reste disponible) tombe dans l'intervalle spécifié par <temps_min> et <temps_max>.

Le format de ces paramètres est "0j0h0m0s" (jours, heures, minutes et secondes à venir). Si <temps_max> est "0s" ou n'est pas spécifié, il n'y a pas de limite supérieure aux temps d'expiration tombant dans cette entrée (notez que cette clé n'a aucun effet sur le moment où l'article sera effectivement expiré, mais seulement sur le fait que l'article sera stocké ou non en utilisant cette méthode de stockage). Ce champ est également facultatif et peut être omis entièrement si vous ne souhaitez pas stocker les articles en fonction de leur champ d'en-tête Expires, le cas échéant.

Une valeur de <temps_min> supérieure à "0s" implique que cette méthode de stockage ne correspondra à aucun article sans champ d'en-tête Expires.

options: <options>
Cette clé sert à passer des options spéciales aux méthodes de stockage qui en ont besoin (actuellement uniquement "cnfs"). Voir la section "MÉTHODES DE STOCKAGE" ci-dessous pour une description de son utilisation.
exactmatch: <bool>
Si cette clé est définie sur vrai, tous les groupes de nouvelles dans le corps du champ d'en-tête Newsgroups (ou Xref si storeonxref dans inn.conf est vrai) des articles entrants seront examinés pour voir s'ils correspondent aux motifs de groupes de nouvelles. (Normalement, n'importe quel nombre non nul de groupes de nouvelles correspondants suffit, à condition qu'aucun groupe de nouvelles ne corresponde à un motif empoisonné, comme décrit ci-dessus.) C'est une valeur booléenne ; "true", "yes" et "on" peuvent être utilisés pour activer cette clé. La casse de ces valeurs n'est pas significative. La valeur par défaut est false.
filtered: <bool>
Si cette clé est définie sur vrai, l'article doit avoir été rejeté par tous les filtres d'articles activés (Perl ou Python) pour innd. Ceci nécessite également que dontrejectfiltered soit défini sur vrai dans inn.conf. Les articles filtrés sont généralement stockés dans un petit tampon CNFS, ou une autre méthode de stockage avec une politique d'expiration plutôt stricte. C'est une valeur booléenne ; "true", "yes" et "on"
sont utilisables pour activer cette clé. La casse de ces valeurs n'est pas significative. La valeur par défaut est false.

Si toutes les classes de stockage ont cette clé définie sur false, les articles filtrés sont stockés dans la même classe de stockage que les articles acceptés. Ce n'est que lorsqu'au moins une classe de stockage a cette clé définie sur true que les articles filtrés et les articles acceptés ne sont plus stockés mélangés dans une classe de stockage quelconque.

chemin: <motclewild>
Quels articles, selon leur en-tête Path, sont stockés en utilisant cette méthode de stockage. <motclewild> est un motif de type motclewilduwildmat qui est comparé au corps de l'en-tête Path des articles, ce qui correspond aux endroits où les articles sont passés ou ont été postés. Les expressions de poison wildmat (expressions commençant par "@") sont autorisées et peuvent être utilisées pour exclure certains motifs de chemin (au lieu des expressions commençant par "!" qui ne sont pas considérées comme niées car "!" a une signification spéciale dans les champs d'en-tête Path). Le motif <motclewild> est comparé dans l'ordre.

Un cas d'utilisation typique pourrait être de stocker des articles provenant d'un site spam dans un petit tampon CNFS pour éviter d'impacter la rétention globale :

chemin: "*!spam-site.example.com!not-for-mail"

Par défaut, tous les articles correspondent.

Si un article correspond à toutes les contraintes d'une entrée, il est stocké via cette méthode de stockage et est associé à cette <classe_de_stockage>. Ce fichier est parcouru dans l'ordre et la première entrée correspondante est utilisée pour stocker l'article.

Si un article ne correspond à aucune entrée, soit parce qu'il est posté dans un groupe de discussion qui ne correspond à aucun des motifs <motclewild>, soit parce qu'il est en dehors des plages de taille et d'expiration de toutes les entrées auxquelles son motif de groupes de discussion correspond, l'article n'est pas stocké et est rejeté par innd. Lorsque cela se produit, le message d'erreur :

impossible de stocker l'article : aucune entrée correspondante dans storage.conf

est enregistré dans syslog. Si vous souhaitez ignorer silencieusement les articles correspondant à certains motifs de groupes de discussion ou à certaines plages de taille ou d'expiration, assignez-les à la méthode de stockage "trash" plutôt que de ne pas les faire correspondre à une entrée de méthode de stockage.

MÉTHODES DE STOCKAGE

Actuellement, cinq méthodes de stockage sont disponibles. Chaque méthode a ses avantages et ses inconvénients ; vous pouvez choisir n'importe quel mélange de celles-ci selon votre environnement. Notez que chaque méthode possède un attribut EXPENSIVESTAT qui indique si la vérification de l'existence d'un article est coûteuse ou non. Ceci est utilisé pour exécuter expireover(8).

cnfs
La méthode de stockage "cnfs" stocke les articles dans de grands tampons cycliques (CNFS signifie Cyclic News File System). Les articles sont stockés dans les tampons CNFS dans l'ordre d'arrivée, et lorsque le tampon est plein, il revient au début et stocke les nouveaux articles par-dessus les articles les plus anciens du tampon. Le temps d'expiration des articles stockés dans les tampons CNFS est donc entièrement déterminé par la rapidité avec laquelle le tampon se remplit, ce qui dépend de la rapidité avec laquelle les données y sont stockées. (Cette méthode est donc dite avoir une fonctionnalité d'auto-expiration. Elle signifie également que lorsqu'un article est annulé, le tampon cyclique ne revient pas en arrière pour utiliser l'espace tant qu'il ne tourne pas et que l'ensemble du tampon cyclique n'est pas réutilisé.) EXPENSIVESTAT est false pour cette méthode.

CNFS possède son propre fichier de configuration, cycbuff.conf, qui décrit quelques subtilités par rapport à la description de base donnée ci-dessus. Les entrées de méthode de stockage pour la méthode de stockage "cnfs" doivent avoir un champ options: spécifiant le métacycbuff dans lequel les articles correspondant à cette entrée doivent être stockés ; voir cycbuff.conf(5) pour les détails sur les métacycbuffs.

Avantages : De loin la plus rapide de toutes les méthodes de stockage (à l'exception de "trash"), car elle élimine la surcharge liée à la gestion d'un système de fichiers et à la création de nouveaux fichiers. Contrairement à toutes les autres méthodes de stockage, elle ne nécessite pas d'expiration manuelle des articles. Avec CNFS, le serveur ne se ralentira jamais à cause d'un disque de spool plein, et les groupes sont limités aux fichiers de tampon donnés de sorte qu'ils ne peuvent jamais utiliser plus d'espace disque qui leur est alloué.

Inconvénients : Les temps de rétention des articles sont plus difficiles à contrôler car les articles anciens sont écrasés automatiquement. Les attaques sur Usenet, telles que le flooding ou une quantité massive de spam, peuvent entraîner l'expiration des articles souhaités beaucoup plus rapidement que prévu (sans avertissement).

timecaf
Cette méthode stocke plusieurs articles dans un seul fichier, dont le nom est basé sur l'heure d'arrivée de l'article et la classe de stockage. Le nom du fichier sera : 
<chemin_articles>/timecaf-nn/bb/aacc.CF

où "nn" est la valeur hexadécimale de <classe_de_stockage>, "bb" et "aacc" sont les composantes hexadécimales de l'heure d'arrivée, et "CF" est une extension codée en dur. (L'heure d'arrivée, en secondes depuis l'epoch, est convertie en hexadécimal et interprétée comme 0xaabbccdd, avec "aa", "bb", et "cc" utilisés pour construire le chemin.) Cette méthode n'a pas de fonctionnalité d'auto-expiration (ce qui signifie que expire doit être exécuté périodiquement pour supprimer les articles anciens, ainsi que les articles annulés si immediatecancel n'est pas défini sur true dans inn.conf). EXPENSIVESTAT est false pour cette méthode.

Un fichier CAF donné contient tous les articles reçus pendant une période d'environ 4 minutes (256 secondes), et est limité à 262 144 articles et environ 3,5 Go. C'est suffisant pour les opérations normales. Le seul inconvénient est lorsque vous alimentez à haute vitesse des lots d'articles entre deux serveurs ; vous voudrez alors le limiter à cette quantité d'articles pendant la période où un fichier CAF stocke les articles nouvellement arrivés.

Avantages : Il est environ quatre fois plus rapide que "timehash" pour l'écriture des articles, car une grande partie de la surcharge du système de fichiers est contournée, tout en conservant le même contrôle fin sur le temps de rétention des articles.

Inconvénients : L'utilisation de cette méthode signifie renoncer à tout ce qui n'est pas une manipulation manuelle très minutieuse du spool d'articles ; à cet égard, elle ressemble à "cnfs". Étant l'un des types de stockage les plus récents et les moins utilisés, "timecaf" n'a pas été aussi rigoureusement testé que les autres méthodes. Il nécessite l'exécution d'un programme expire nocturne pour supprimer les articles anciens en compactant les fichiers CAF s'ils contiennent encore des articles disponibles, ou en les supprimant.

timehash
Cette méthode est très similaire à "timecaf" sauf que chaque article est stocké dans un fichier séparé. Le nom du fichier pour un article donné sera : 
<chemin_articles>/time-nn/bb/cc/yyyy-aadd

où "nn" est la valeur hexadécimale de <classe_de_stockage>, "yyyy" est une séquence hexadécimale numérique, et "bb", "cc", et "aadd" sont des composantes de l'heure d'arrivée en hexadécimal (l'heure d'arrivée est interprétée comme documenté ci-dessus sous "timecaf"). Cette méthode n'a pas de fonctionnalité d'auto-expiration. Les articles annulés sont supprimés immédiatement. EXPENSIVESTAT est true pour cette méthode.

Avantages : Les groupes à fort trafic ne provoquent pas de goulots d'étranglement, et un contrôle fin du temps de rétention des articles est toujours possible.

Inconvénients : La capacité de trouver facilement tous les articles d'un groupe de discussion donné et de manipuler manuellement le spool d'articles est perdue, et INN souffre toujours d'une dégradation de la vitesse due à la surcharge du système de fichiers (la création et la suppression de fichiers individuels sont des opérations lentes) et à une utilisation accrue des inodes. Elle nécessite également un programme expire nocturne pour supprimer les anciens articles du spool de nouvelles.

tradspool
Spool traditionnel, ou "tradspool", est le format de stockage traditionnel des articles de nouvelles. Chaque article est stocké dans un fichier texte individuel nommé : 
<chemin_articles>/news/group/name/nnnnn

où "news/group/name" est le nom du groupe de discussion auquel l'article a été posté, avec chaque point remplacé par une barre oblique, et "nnnnn" est le numéro de séquence de l'article dans ce groupe de discussion. Pour les articles crosspostés, l'article est lié à chaque groupe de discussion auquel il est crossposté (en utilisant des liens durs ou symboliques). C'est ainsi que les versions d'INN antérieures à 2.0 stockaient tous les articles, et c'est aussi le format de stockage d'articles utilisé par C News et les systèmes de nouvelles plus anciens. Cette méthode n'a pas de fonctionnalité d'auto-expiration. Les articles annulés sont supprimés immédiatement. EXPENSIVESTAT est true pour cette méthode.

Avantages : Il est largement utilisé et bien compris ; il peut lire les spools d'articles écrits par d'anciennes versions d'INN et il est compatible avec tous les modules complémentaires tiers d'INN. Ce mécanisme de stockage fournit un accès facile et direct aux articles stockés sur le serveur, facilite l'écriture de programmes qui manipulent le spool de nouvelles, offre un contrôle fin sur les temps de rétention des articles et est livré avec l'utilitaire de support scanspool pour effectuer des vérifications de cohérence.

Inconvénients : Il nécessite un système de fichiers et un système d'E/S plus rapides que les méthodes de stockage cnfs et timecaf en raison de la surcharge du système de fichiers. Les groupes à fort trafic ont tendance à créer un goulot d'étranglement en raison des inefficacités de stockage d'un grand nombre de fichiers d'articles dans un seul répertoire. Il consomme plus d'inodes et nécessite un programme expire nocturne pour supprimer les anciens articles du spool de nouvelles.

trash
Cette méthode écarte silencieusement tous les articles qui y sont stockés. Ses seuls usages réels sont pour les tests et pour écarter silencieusement les articles correspondant à une entrée de méthode de stockage particulière (pour quelque raison que ce soit). Les articles stockés dans ce méthode ne prend pas de place sur le disque et ne peut jamais être récupérée, donc cette méthode a une sorte de fonctionnalité d'auto-expiration. EXPENSIVESTAT est faux pour cette méthode.

EXEMPLES

Le fichier storage.conf suivant stockerait tous les articles postés sur alt.binaries.* dans le tampon CNFS nommé "BINARIES", tous les articles de plus d'environ 50 Ko dans toute autre hiérarchie dans le tampon CNFS nommé "LARGE", tous les autres articles sur alt.* dans une classe timehash, et tous les autres articles de n'importe quel newsgroup dans une deuxième classe timehash, à l'exception de la hiérarchie internal.* qui est stockée au format spool traditionnel.

method tradspool {
    class: 1
    newsgroups: internal.*
}
method cnfs {
    class: 2
    newsgroups: alt.binaries.*
    options: BINARIES
}
method cnfs {
    class: 3
    newsgroups: *
    size: 50000
    options: LARGE
}
method timehash {
    class: 4
    newsgroups: alt.*
}
method timehash {
    class: 5
    newsgroups: *
}

Notez que la dernière entrée de méthode de stockage attrapera tout. C'est une bonne habitude à prendre ; assurez-vous d'avoir au moins une entrée "attrape-tout" au cas où quelque chose que vous n'aviez pas prévu passerait entre les mailles du filet. Notez également que la règle spéciale pour la hiérarchie internal.* est la première, de sorte qu'elle attrapera même les articles publiés en crosspost sur alt.binaries.* ou de plus de 50 Ko.

Concernant les expressions de type poison wildmat, si vous avez par exemple un article publié en crosspost entre misc.foo et misc.bar, le motif :

misc.*,!misc.bar

correspondra à cet article, tandis que le motif :

misc.*,@misc.bar

ne correspondra pas à cet article. Un article posté uniquement sur misc.bar ne correspondra à aucun des deux motifs.

Habituellement, les groupes à haut volume et les groupes dont les articles ne doivent pas être conservés très longtemps (groupes binaires, *.jobs*, news.lists.filters, etc.) sont stockés dans des tampons CNFS. Utilisez les autres méthodes (ou des tampons CNFS à nouveau) pour tout le reste. Cependant, il est souvent plus pratique de conserver dans des "tradspool" des hiérarchies spéciales comme les hiérarchies locales et les hiérarchies qui ne devraient jamais expirer ou à travers lesquelles vous devez passer manuellement.
