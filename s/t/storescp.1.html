NOM

storescp - Fournisseur de Service (SCP) de stockage DICOM (C-STORE)

SYNTAXE

storescp [options] [port]

DESCRIPTION

L'application storescp implémente un Fournisseur de Service (SCP) pour la classe de service de stockage. Elle écoute sur un port TCP/IP spécifique pour les requêtes d'association entrantes d'un Utilisateur de Classe de Service (SCU) et peut recevoir des images DICOM ainsi que d'autres objets composites DICOM. L'application storescp supporte également la classe de service de vérification en tant que SCP.

PARAMETRES

port  numéro de port TCP/IP sur lequel écouter
      (ce paramètre est requis sauf si l'option --inetd est spécifiée)

NOTES

L'impact sémantique des options mentionnées ci-dessus est clair pour la majorité des options. Certaines options particulières, cependant, sont si spécifiques qu'elles nécessitent des descriptions détaillées qui seront données dans ce passage.

L'option --sort-conc-studies permet à l'utilisateur de trier tous les objets DICOM reçus dans différents sous-répertoires. Le tri sera effectué en fonction des études auxquelles appartiennent les objets individuels, c'est-à-dire que les objets appartenant à la même étude seront stockés dans le même sous-répertoire. En général, un objet DICOM d_n+1 est considéré comme appartenant à la même étude qu'un objet DICOM d_n si et seulement si d_n et d_n+1 présentent exactement les mêmes valeurs pour l'attribut Study Instance UID. Les noms des sous-répertoires résultants commencent toujours par un préfixe p qui a été passé à cette option en paramètre. En plus de ce préfixe, les noms des sous-répertoires contiennent des informations d'horodatage relatives à la date et à l'heure de réception du premier objet DICOM de cette étude particulière. En détail, la détermination des noms de sous-répertoires suit le modèle

  [prefix]_[YYYYMMDD]_[HHMMSSPPP]

où YYYY représente l'année (4 chiffres), MM le mois (01-12), DD le jour (01-31), HH l'heure (00-23), MM la minute (00-59), SS la seconde (00-59) et PPP les millisecondes (000-999). Si le préfixe est une chaîne vide, le premier "_" est omis.

Les autres options --sort-xxx fonctionnent de manière similaire, seuls les noms des sous-répertoires sont créés différemment. Pour l'option --sort-on-study-uid, le modèle est

  [prefix]_[StudyInstanceUID]

et pour l'option --sort-on-patientname

  [PatientName]_[YYYYMMDD]_[HHMMSSPPP]

où 'PatientName' est remplacé par "ANONYMOUS" si l'élément de données est vide ou absent dans l'ensemble de données. Tout nom de patient existant est transformé afin d'utiliser uniquement des caractères ASCII. Veuillez noter que dans ce contexte, seuls le jeu de caractères par défaut DICOM (ASCII, c'est-à-dire aucune entrée dans l'attribut Specific Character Set) et Latin-1 (Specific Character Set valorisé à "ISO_IR 100") sont pris en charge. Si un autre jeu de caractères est trouvé et que le nom du patient contient des caractères non ASCII, un avertissement est imprimé et la transformation est effectuée comme si le jeu de caractères Latin-1 était défini dans le fichier. Cela peut entraîner des répertoires et des comportements de noms de patients illisibles ou inattendus. Il est donc conseillé d'utiliser --sort-on-patientname uniquement si des noms de patients en Latin-1 ou ASCII sont attendus.

Pour l'option --sort-on-study-uid, le même sous-répertoire sera utilisé pour tous les objets DICOM appartenant à la même étude, c'est-à-dire, contrairement aux autres options --sort-xxx, il n'y a aucune garantie qu'un répertoire d'étude soit jamais complété.

L'option --timenames crée des noms de fichiers à partir des horodatages correspondant à l'heure à laquelle storescp écrit un fichier sur disque. Le format est

  [YYYYMMDDHHMMSSPPP]_[SERIALNO].[MD]

où YYYY, MM, DD, HH, MM, SS, PPP sont interprétés comme décrit ci-dessus. Si plusieurs fichiers sont créés à la même heure, SERIALNO est inséré. Il consiste en un nombre de 4 chiffres consécutifs (0000 à 9999). Pour le premier fichier, qui existe pour une heure spécifique, aucun numéro (et aucun "_") n'est inséré. MD représente un code d'identification (2 lettres) pour le type d'objet stocké dans le fichier (voir les notes sur --rename-on-eostudy).

L'option --filename-extension ajoute un suffixe spécifié à chaque nom de fichier (un point "." n'est pas ajouté automatiquement). Ce suffixe n'est pas ajouté aux noms de fichiers créés par --rename-on-eostudy afin de maintenir la longueur de 8 caractères.

L'option --exec-on-reception permet d'exécuter une ligne de commande spécifique après avoir reçu et traité un objet DICOM (via un message C-STORE-RQ). La ligne de commande à exécuter est passée à cette option en tant que paramètre. La ligne de commande spécifiée peut contenir un certain nombre de placeholders qui seront remplacés à l'exécution :

  • #p: chemin complet vers le répertoire de sortie dans lequel le dernier objet DICOM a été stocké (non disponible avec l'option --ignore cependant)
  • #f: nom du fichier de sortie courant (non disponible avec l'option --ignore cependant)
  • #a: titre de l'application appelante de l'entité de l'initiateur Storage SCU distant
  • #c: titre de l'application appelée utilisée par l'initiateur Storage SCU distant pour adresser storescp
  • #r: adresse de présentation de l'appelant, c'est-à-dire le nom d'hôte ou l'adresse IP de l'initiateur Storage SCU distant

La ligne de commande spécifiée est exécutée comme un processus séparé, de sorte que l'exécution de storescp ne sera pas retardée. Ce comportement peut être influencé avec l'option --exec-sync.

Notez que les titres des entités d'application ('#a' et '#c') seront 'nettoyés' pour éviter tout comportement indésirable lorsque les paramètres sont transmis au shell. Les caractères inhabituels seront mappés au caractère '_' . Un avertissement est imprimé dans le journal dans ce cas.

L'option --exec-on-eostudy permet d'exécuter une ligne de commande spécifique lorsque tous les objets DICOM appartenant à une étude ont été reçus par storescp. Les mêmes placeholders que pour --exec-on-reception peuvent être utilisés, à l'exception de '#f', qui n'est pas pris en charge. Une étude est considérée comme complète par storescp lorsqu'un objet appartenant à une étude différente est reçu ou que le délai d'attente spécifié avec --eostudy-timeout se produit. Si l'option --rename-on-eostudy est active, le renommage a lieu avant l'exécution de la commande externe.

L'option --rename-on-eostudy fait référence aux options --sort-xxx mentionnées ci-dessus et ne peut être utilisée qu'en combinaison avec l'une de ces options. Si un utilisateur spécifie l'option --rename-on-eostudy et que storescp détermine que tous les objets DICOM appartenant à une étude particulière ont été reçus, tous les fichiers DICOM appartenant à la dernière étude seront renommés dans le répertoire de sortie correspondant. Les noms de fichiers dans lesquels les fichiers seront renommés seront calculés en utilisant le modèle

  [prefix][numérotation consécutive]

où [prefix] est un préfixe de 2 caractères qui révèle le type d'objet DICOM stocké dans le fichier et [numérotation consécutive] est un nombre de 6 chiffres numéroté consécutivement, commençant à "000001". En général, la question de savoir si tous les objets DICOM appartenant à une étude ont été reçus par storescp recevra une réponse positive si et seulement si deux objets DICOM reçus consécutivement d_n et d_n+1 n'affichent pas les mêmes valeurs dans l'attribut Study Instance UID ; dans un tel cas, d_n+1 est considéré comme appartenant à une nouvelle étude.

En utilisant l'option --eostudy-timeout, l'utilisateur peut modifier le processus de détermination pour savoir si tous les objets DICOM appartenant à une étude ont déjà été reçus par storescp. À cet égard, il est clair que cette option ne peut être utilisée qu'en combinaison avec au moins l'une des options suivantes : --sort-xxx, --exec-on-eostudy et --rename-on-eostudy. Si l'option --eostudy-timeout est spécifiée, la fin d'une étude est considérée comme survenue non seulement si deux objets DICOM reçus consécutivement d_n et d_n+1 n'affichent pas les mêmes valeurs dans l'attribut Study Instance UID, mais aussi si, dans un intervalle de temps de x secondes après la réception d'un objet DICOM d_n, aucun autre objet DICOM n'a été reçu sur le réseau. Notez que la quantité x de secondes (qui détermine la durée de cet intervalle de temps) doit être passée à cette option en tant que paramètre.

Veuillez noter que deux connexions réseau consécutives peuvent transférer des objets pour la même étude. L'étude ne sera considérée comme complète que lorsqu'un objet d'une étude différente sera reçu ou que le délai --eostudy-timeout sera atteint. Pour cette raison, les options --fork et --inet sont i

incompatible avec --exec-on-eostudy, --rename-on-eostudy et --sort-conc-studies.

Contrôle d'accès

Lorsqu'il est compilé sur des plateformes Unix avec le support de TCP Wrapper, le contrôle d'accès basé sur l'hôte peut être activé avec l'option de ligne de commande --access-control. Dans ce cas, les règles de contrôle d'accès définies dans les tables de contrôle d'accès d'hôte du système pour storescp sont appliquées. Les emplacements par défaut des tables de contrôle d'accès d'hôte sont /etc/hosts.allow et /etc/hosts.deny. Plus de détails sont décrits dans hosts_access(5).

Lancement de storescp depuis inetd

Sur les plateformes Posix, storescp peut être initié via le super-serveur inetd(8). Cela nécessite que storescp soit configuré dans le fichier de configuration /etc/inetd.conf. Une ligne de configuration typique pourrait ressembler à ceci :

acr-nema stream tcp nowait root /usr/sbin/storescp -id +ac -od /tmp/storescp

où -id (--inetd) active le mode inetd dans lequel l'association DICOM est effectivement acceptée par inetd et transmise à storescp, +ac (--access-control) active le contrôle d'accès basé sur TCP Wrapper décrit ci-dessus et -od (--output-directory) définit le répertoire dans lequel storescp stocke les objets DICOM entrants. Notez que le nom du service ("acr-nema" dans cet exemple) détermine le numéro de port sur lequel les associations DICOM sont acceptées et doit être défini dans /etc/services. Lors de l'exécution via inetd, les flux stdout et stderr sont ignorés. Cependant, vous pouvez toujours configurer la journalisation via l'option --log-config (voir ci-dessous).

Veuillez noter que lorsqu'il est exécuté via inetd, storescp est exécuté avec des privilèges root, ce qui peut présenter un risque de sécurité.

Profils de négociation d'association et fichiers de configuration

storescp supporte un mécanisme flexible pour spécifier le comportement de négociation d'association réseau DICOM, basé sur des "profils de négociation d'association" qui peuvent être lus à partir d'un fichier de configuration. Le format et la sémantique de ce fichier de configuration sont documentés dans asconfig.txt.

JOURNALISATION

Le niveau de sortie de journalisation des différents outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seuls les erreurs et les avertissements sont écrits sur le flux d'erreur standard. En utilisant l'option --verbose, des messages informationnels, tels que les messages de connexion ou de déconnexion de client, sont également affichés. L'option --debug active les messages de débogage des bibliothèques sous-jacentes, qui sont généralement destinés à aider au développement et à la maintenance de Dcmtk.

Il est également possible de configurer la journalisation à l'aide d'un fichier de configuration (voir l'option de ligne de commande --log-config). Ce fichier de configuration peut être utilisé pour spécifier un niveau de journalisation différent pour différentes parties de l'outil et des bibliothèques sous-jacentes. De plus, il permet de diriger les messages de journalisation vers différents fichiers de sortie, tels que stdout, stderr ou des fichiers individuels. Le format de ce fichier est documenté dans config.html, disponible dans le répertoire de documentation de Dcmtk.

LOGGING

Le niveau de journalisation par défaut est le niveau d'information. Les détails de traitement sont rapportés. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level. En mode --quiet, seules les erreurs fatales sont rapportées. Dans des événements d'erreur aussi très graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module "oflog".

Dans le cas où la sortie de journalisation doit être écrite dans un fichier (facultativement avec rotation de fichier journal), vers syslog (Unix) ou le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/logger.cfg.

LIGNE DE COMMANDE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets carrés encadrent les valeurs optionnelles (0-1), trois points de suspension indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie 0 à n valeurs.

Les options de ligne de commande se distinguent des paramètres par un signe '+' ou '-' respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si des options sont mutuellement exclusives, l'apparition la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix courants.

De plus, un ou plusieurs fichiers de commande peuvent être spécifiés à l'aide d'un signe '@' comme préfixe du nom de fichier (par exemple, @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (les espaces multiples sont traités comme un unique séparateur à moins qu'ils n'apparaissent entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite les lignes de commande trop longues et confuses (un exemple est fourni dans le fichier <datadir>/dumppat.txt).

ENVIRONNEMENT

L'utilitaire storescp tentera de charger les dictionnaires de données DICOM spécifiés dans la variable d'environnement DCMDICTPATH. Par défaut, c'est-à-dire si la variable d'environnement DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé, sauf si le dictionnaire est intégré à l'application (par défaut pour Windows).

Le comportement par défaut doit être préféré et la variable d'environnement DCMDICTPATH ne doit être utilisée que lorsque des dictionnaires de données alternatifs sont requis. La variable d'environnement DCMDICTPATH a le même format que la variable PATH du shell Unix, en ce sens qu'un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données tentera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH. C'est une erreur si aucun dictionnaire de données ne peut être chargé.
