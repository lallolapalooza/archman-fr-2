NOM

strongswan.conf - fichier de configuration de strongSwan

DESCRIPTION

Alors que le fichier de configuration ipsec.conf(5) est bien adapté pour définir les paramètres de configuration liés à IPsec, il n'est pas utile que d'autres applications de strongSwan lisent des options de ce fichier. Le fichier est difficile à analyser et seul ipsec starter est capable de le faire. Le nombre de composants du projet strongSwan ne cessant de croître, un fichier de configuration plus flexible était nécessaire, facile à étendre et utilisable par tous les composants. Avec strongSwan 4.2.1, strongswan.conf(5) a été introduit, répondant à ces exigences.

SYNTAXE

Le format du fichier strongswan.conf se compose de sections hiérarchiques et d'une liste de paires clé/valeur dans chaque section. Chaque section a un nom, suivi d'accolades de style C définissant le corps de la section. Chaque corps de section contient un ensemble de sous-sections et de paires clé/valeur :

settings := (section|keyvalue)*
section  := name { settings }
keyvalue := key = value\n

Les valeurs doivent être terminées par un retour à la ligne.

Les commentaires sont possibles en utilisant le caractère #.

Les noms de sections et les clés peuvent contenir n'importe quel caractère imprimable, sauf :

. , : { } = " # \n \t espace

Un exemple de fichier dans ce format pourrait ressembler à ceci :

a = b
section-one {
	somevalue = asdf
	subsection {
		othervalue = xxx
	}
	# yei, un commentaire
	yetanother = zz
}
section-two {
	x = 12
}

L'indentation est facultative, vous pouvez utiliser des tabulations ou des espaces.

FORMATS DE NOMBRE

Les options qui définissent une valeur entière peuvent être spécifiées en décimal (par défaut) ou en hexadécimal (préfixe "0x", les lettres majuscules ou minuscules sont acceptées). Les chaînes dépendantes de la locale (par exemple, le séparateur de milliers de la locale actuelle) peuvent également être acceptées dans des locales autres que "C".

Les options qui définissent une valeur à virgule flottante peuvent être spécifiées en décimal (par défaut) ou en hexadécimal (préfixe "0x", les lettres majuscules ou minuscules sont acceptées). Le caractère de base (séparateur décimal) dans les deux cas dépend de la locale, généralement ".".

FORMATS DE TEMPS

Sauf indication contraire, les options qui définissent un temps sont spécifiées en secondes. Les suffixes "s", "m", "h" et "d" peuvent être utilisés pour convertir automatiquement les valeurs données en secondes, minutes, heures ou jours (par exemple, au lieu de configurer un temps de rekeying de 4 heures comme "14400" secondes, "4h" peut être utilisé).

Il existe des options globales qui n'acceptent pas ces suffixes car elles sont configurées comme des valeurs entières en secondes ou millisecondes, ou même comme des nombres à virgule flottante (par exemple, le temps de retransmission). Les options qui acceptent les suffixes ont une valeur par défaut correspondante.

RÉFÉRENCEMENT D'AUTRES SECTIONS

Il est possible d'hériter de paramètres et de sections d'une autre section. Cette fonctionnalité est principalement utile dans swanctl.conf (qui utilise le même format de fichier). La syntaxe est la suivante :

section    := name : references { settings }
references := absname[, absname]*
absname    := name[.name]*

Toutes les paires clé/valeur et toutes les sous-sections des sections référencées seront héritées par la section qui les référence via leur nom absolu. Les valeurs peuvent être remplacées dans la section ou dans l'une de ses sous-sections (utilisez une affectation vide pour effacer une valeur afin que sa valeur par défaut, le cas échéant, s'applique). Il n'est actuellement pas possible de limiter le niveau d'inclusion ou d'effacer/supprimer des sous-sections héritées.

Si l'ordre est important (par exemple, pour les tours d'authentification dans une connexion, si round n'est pas utilisé), il convient de noter que les paramètres/sections hérités suivront ceux définis dans la section actuelle (si plusieurs sections sont référencées, leurs paramètres sont énumérés de gauche à droite).

Les références sont évaluées dynamiquement à l'exécution, il n'y a donc aucun problème à référencer des sections plus loin dans le fichier de configuration ou inclus via d'autres fichiers.

Voici un exemple de ce à quoi cela pourrait ressembler :

conn-defaults {
	# paramètres par défaut pour toutes les connexions (par exemple, un certificat ou des pools d'adresses IP)
}
eap-defaults {
	# paramètres par défaut si EAP est utilisé (par exemple, une séquence d'authentification distante)
}
child-defaults {
	# paramètres par défaut pour les configurations d'enfants (par exemple, sélecteurs de trafic)
}
connections {
	conn-a : conn-defaults, eap-defaults {
		# définir/remplacer des éléments spécifiques à cette connexion
		children {
			child-a : child-defaults {
				# définir/remplacer des éléments spécifiques à cet enfant
			}
		}
	}
	conn-b : conn-defaults {
		# définir/remplacer des éléments spécifiques à cette connexion
		children {
			child-b : child-defaults {
				# définir/remplacer des éléments spécifiques à cet enfant
			}
		}
	}
	conn-c : connections.conn-a {
		# tout est hérité, y compris tout ce que conn-a
		# hérite déjà des sections auxquelles elle et ses
		# sous-sections font référence
	}
}

INCLUSION DE FICHIERS

En utilisant l'instruction include, il est possible d'inclure d'autres fichiers dans strongswan.conf, par exemple :

include /some/path/*.conf

Si le nom de fichier n'est pas un chemin absolu, il est considéré comme relatif au répertoire du fichier contenant l'instruction include. Le nom de fichier peut inclure des jokers shell (voir sh(1)). De plus, de telles inclusions peuvent être imbriquées.

Les sections chargées à partir de fichiers inclus étendent les sections précédemment chargées ; les valeurs existantes sont remplacées. Il est important de noter que les paramètres sont ajoutés par rapport à la section dans laquelle se trouve l'instruction include.

Par exemple, les trois fichiers suivants résultent dans la même configuration finale que celle donnée ci-dessus :

	a = b
	section-one {
		somevalue = before include
		include include.conf
	}
	include other.conf
include.conf:
	# les paramètres chargés à partir de ce fichier sont ajoutés à section-one
	# le suivant remplace la valeur précédente
	somevalue = asdf
	subsection {
		othervalue = yyy
	}
	yetanother = zz
other.conf:
	# ceci étend section-one et subsection
	section-one {
		subsection {
			# ceci remplace la valeur précédente
			othervalue = xxx
		}
	}
	section-two {
		x = 12
}

LECTURE DES VALEURS

Les valeurs sont accessibles en utilisant une liste de sections séparées par des points et une clé. En référence à l'exemple ci-dessus, l'accès à section-one.subsection.othervalue renverra xxx.

charon.identity_privacy [no]
If enabled, the initiator will send its identity only after the authentication method has been negotiated, and it will send it as an anonymous identity (type 0) if the peer identity is unspecified. This prevents passive attackers from sniffing the peer's identity during the initial IKE message exchange.

However, if the peer does not support this option, authentication might fail. Furthermore, a non-passive attacker can still perform an active man-in-the-middle attack to obtain the identity during the authentication phase.

Note: This option has no effect if public key authentication is used, as the identity is implicitly revealed by the signature.

Implications: A passive attacker can sniff the negotiated Identity, and start brute forcing the PSK using the HASH payload.

It is recommended to keep this option to no, unless you know exactly what the implications are and require compatibility to such devices (for example, some SonicWall boxes).

charon.rdn_matching [strict]
Comment les RDN (Relative Distinguished Names) dans les DN de sujet des certificats sont mis en correspondance avec les identités configurées. Les valeurs possibles sont strict (par défaut), reordered (réordonné), et relaxed (relâché). Avec strict, le nombre, le type et l'ordre de tous les RDN doivent correspondre, les caractères génériques (*) pour les valeurs des RDN sont autorisés (c'est le cas pour les trois variantes). Utiliser reordered correspond également aux DN si les RDN apparaissent dans un ordre différent, le nombre et le type devant toujours correspondre. Enfin, relaxed autorise également la correspondance des DN qui contiennent plus de RDN que l'identité configurée (les RDN manquants sont traités comme une correspondance générique).

Notez que reordered et relaxed imposent une surcharge considérable en termes d'utilisation de la mémoire et de temps d'exécution, en particulier en cas d'échec de correspondance, par rapport à strict.

NAME

ipsec.conf - IPsec connection configuration file

SYNOPSIS

/etc/ipsec.conf

DESCRIPTION

The file /etc/ipsec.conf contains configuration entries for IPsec connections and various other options controlling the behavior of the daemon.

The configuration file consists of logical sections, each starting with a section keyword followed by curly braces { }. Sections can contain key-value pairs or nested sections. Comments start with a # and continue to the end of the line.

The daemon reads the configuration file at startup and whenever it receives a SIGHUP signal. Some options can be changed without a daemon restart using the ipsec rereadconf command.

File Format

The file format is a simple key-value configuration format. Lines starting with a # are ignored. Keys and values are separated by =. String values may be enclosed in double quotes. Multi-word values are automatically concatenated. Complex values like the algorithm proposals are defined using sub-sections.

A section is defined by a keyword, followed by a name if specified, and then enclosed in curly braces. For example:

conn myconn
    left=10.0.0.1
    right=%any

This defines a connection named myconn with two options.

The daemon accepts several keywords at the top level:

config
Sets configuration options of the daemon.
conn
Defines a connection.
include
Includes another configuration file.
secrets
Includes the secrets file (e.g. /etc/ipsec.secrets).

Options defined in the config section apply globally to the daemon.

The conn section defines parameters for specific IPsec connections. It consists of a connection name followed by key-value pairs that specify the connection's behavior. Multiple conn sections can be defined to specify different configurations.

The include directive allows to include other configuration files. This is useful for organizing the configuration into multiple files. The included file is parsed as if it were part of the main file.

JOB PRIORITY MANAGEMENT

Some operations in the IKEv2 daemon charon are currently implemented synchronously and blocking. Two examples for such operations are communication with a RADIUS server via EAP-RADIUS, or fetching CRL/OCSP information during certificate chain verification. Under high load conditions, the thread pool may run out of available threads, and some more important jobs, such as liveness checking, may not get executed in time.

To prevent thread starvation in such situations job priorities were introduced. The job processor will reserve some threads for higher priority jobs, these threads are not available for lower priority, locking jobs.

Implementation

Currently 4 priorities have been defined, and they are used in charon as follows:

CRITICAL
Priority for long-running dispatcher jobs.
HIGH
INFORMATIONAL exchanges, as used by liveness checking (DPD).
MEDIUM
Everything not HIGH/LOW, including IKE_SA_INIT processing.
LOW
IKE_AUTH message processing. RADIUS and CRL fetching block here

Although IKE_SA_INIT processing is computationally expensive, it is explicitly assigned to the MEDIUM class. This allows charon to do the DH exchange while other threads are blocked in IKE_AUTH. To prevent the daemon from accepting more IKE_SA_INIT requests than it can handle, use IKE_SA_INIT DROPPING.

The thread pool processes jobs strictly by priority, meaning it will consume all higher priority jobs before looking for ones with lower priority. Further, it reserves threads for certain priorities. A priority class having reserved n threads will always have n threads available for this class (either currently processing a job, or waiting for one).

Configuration

To ensure that there are always enough threads available for higher priority tasks, threads must be reserved for each priority class.

charon.processor.priority_threads.critical [0]
Threads reserved for CRITICAL priority class jobs
charon.processor.priority_threads.high [0]
Threads reserved for HIGH priority class jobs
charon.processor.priority_threads.medium [0]
Threads reserved for MEDIUM priority class jobs
charon.processor.priority_threads.low [0]
Threads reserved for LOW priority class jobs

Let's consider the following configuration:

charon {
	processor {
		priority_threads {
			high = 1
			medium = 4
		}
	}
}

With this configuration, one thread is reserved for HIGH priority tasks. As currently only liveness checking and stroke message processing is done with high priority, one or two threads should be sufficient.

The MEDIUM class mostly processes non-blocking jobs. Unless your setup is experiencing many blocks in locks while accessing shared resources, threads for one or two times the number of CPU cores is fine.

It is usually not required to reserve threads for CRITICAL jobs. Jobs in this class rarely return and do not release their thread to the pool.

The remaining threads are available for LOW priority jobs. Reserving threads does not make sense (until we have an even lower priority).

Monitoring

To see what the threads are actually doing, invoke ipsec statusall. Under high load, something like this will show up:

worker threads: 2 or 32 idle, 5/1/2/22 working,
	job queue: 0/0/1/149, scheduled: 198

From 32 worker threads,

2
are currently idle.
5
are running CRITICAL priority jobs (dispatching from sockets, etc.).
1
is currently handling a HIGH priority job. This is actually the thread currently providing this information via stroke.
2
are handling MEDIUM priority jobs, likely IKE_SA_INIT or CREATE_CHILD_SA messages.
22
are handling LOW priority jobs, probably waiting for an EAP-RADIUS response while processing IKE_AUTH messages.

The job queue load shows how many jobs are queued for each priority, ready for execution. The single MEDIUM priority job will get executed immediately, as we have two spare threads reserved for MEDIUM class jobs.

IKE_SA_INIT DROPPING

If a responder receives more connection requests per seconds than it can handle, it does not make sense to accept more IKE_SA_INIT messages. And if they are queued but can't get processed in time, an answer might be sent after the client has already given up and restarted its connection setup. This additionally increases the load on the responder.

To limit the responder load resulting from new connection attempts, the daemon can drop IKE_SA_INIT messages just after reception. There are two mechanisms to decide if this should happen, configured with the following options:

charon.init_limit_half_open [0]
Limit based on the number of half open IKE_SAs. Half open IKE_SAs are SAs in connecting state, but not yet established.
charon.init_limit_job_load [0]
Limit based on the number of jobs currently queued for processing (sum over all job priorities).

The second limit includes load from other jobs, such as rekeying. Choosing a good value is difficult and depends on the hardware and expected load.

The first limit is simpler to calculate, but includes the load from new connections only. If your responder is capable of negotiating 100 tunnels/s, you might set this limit to 1000. The daemon will then drop new connection attempts if generating a response would require more than 10 seconds. If you are allowing for a maximum response time of more than 30 seconds, consider adjusting the timeout for connecting IKE_SAs (charon.half_open_timeout). A responder, by default, deletes an IKE_SA if the initiator does not establish it within 30 seconds. Under high load, a higher value might be required.

LOAD TESTS

To do stability testing and performance optimizations, the IKE daemon charon provides the load-tester plugin. This plugin allows one to setup thousands of tunnels concurrently against the daemon itself or a remote host.

WARNING: Never enable the load-testing plugin on productive systems. It provides preconfigured credentials and allows an attacker to authenticate as any user.

Configuration details

For public key authentication, the responder uses the "CN=srv, OU=load-test, O=strongSwan" identity. For the initiator, each connection attempt uses a different identity in the form "CN=c1-r1, OU=load-test, O=strongSwan", where the first number indicates the client number, the second the authentication round (if multiple authentication rounds are used).

For PSK authentication, FQDN identities are used. The server uses srv.strongswan.org, the client uses an identity in the form c1-r1.strongswan.org.

For EAP authentication, the client uses a NAI in the form 100000000010001@strongswan.org.

To configure multiple authentication rounds, concatenate multiple methods using, e.g.

initiator_auth = pubkey|psk|eap-md5|eap-aka

The responder uses a hardcoded certificate based on a 1024-bit RSA key. This certificate additionally serves as CA certificate. A peer uses the same private key, but generates client certificates on demand signed by the CA certificate. Install the Responder/CA certificate on the remote host to authenticate all clients.

To speed up testing, the load tester plugin implements a special Diffie-Hellman implementation called modpnull. By setting

proposal = aes128-sha1-modpnull
this wicked fast DH implementation is used. It does not provide any security at all, but allows one to run tests without DH calculation overhead.

Examples

In the simplest case, the daemon initiates IKE_SAs against itself using the loopback interface. This will actually establish double the number of IKE_SAs, as the daemon is initiator and responder for each IKE_SA at the same time. Installation of IPsec SAs would fail, as each SA gets installed twice. To simulate the correct behavior, a fake kernel interface can be enabled which does not install the IPsec SAs at the kernel level.

A simple loopback configuration might look like this:

charon {
	# create new IKE_SAs for each CHILD_SA to simulate
	# different clients
	reuse_ikesa = no
	# turn off denial of service protection
	dos_protection = no

NAME

configuration file for strongSwan

DESCRIPTION

The configuration files of strongSwan contain various configuration parameters, that control the behavior of the daemon and its plugins.

The configuration files are loaded in the following order:

  • /etc/strongswan.conf
  • /etc/strongswan.d/*.conf

The configuration files are read by the charon daemon on startup, and some settings can be changed at runtime via charon-cmd(8).

Configuration is split into sections. The top-level section is charon, which contains the main daemon configuration. Additional sections define the configuration of plugins.

SYNTAX

The configuration file syntax is an INI-like format. Sections are defined by square brackets, e.g. [section]. Options are defined as key = value pairs. Values can be numbers, strings, booleans, lists, or nested sections.

Strings are typically enclosed in double quotes. Boolean values are yes or no. Lists are comma-separated values, enclosed in square brackets, e.g. list = [value1, value2, value3].

Boolean values are case-insensitive, so yes, YES, Yes, no, NO, and No are all accepted.

Comments start with a hash sign (#) and extend to the end of the line.

The configuration file supports variable substitution. These variables are defined in the VARIABLES section. Variables are substituted using the ${VARNAME} syntax.

Values can reference other configuration keys using the ${KEY} syntax. This allows for the creation of default values or referencing settings in other sections.

NUMBER FORMATS

Numbers can be specified as decimal, hexadecimal, or octal. Hexadecimal numbers are prefixed with 0x, and octal numbers with 0. Numbers can also be suffixed with units like k, M, or G for kilobytes, megabytes, and gigabytes, respectively. This is primarily used for sizes, e.g. 10M for 10 megabytes.

TIME FORMATS

Time values can be specified as seconds, or with time units appended, like s (seconds), m (minutes), h (hours), d (days). E.g. 30m for 30 minutes.

A list of time values can be specified as comma-separated values. For example, timeouts = [10s, 1m, 5m].

REFERENCING OTHER SECTIONS

Configuration values can reference other sections or keys using the syntax ${section.key} or ${key} to reference a key in the current section.

This allows for default values to be specified in a general section, and then overridden in specific sections.

charon {

The included files are read in alphabetical order. This allows for modular configuration, for example, by placing plugin-specific configurations in separate files.
