NOM

sg_verify - invoquer des commandes SCSI VERIFY sur un périphérique bloc

SYNOPSIS

sg_verify [--0] [--16] [--bpc=BPC] [--count=COUNT] [--dpo] [--ff] [--ebytchk=BCH] [--group=GN] [--help] [--in=IF] [--lba=LBA] [--ndo=NDO] [--quiet] [--readonly] [--verbose] [--version] [--vrprotect=VRP] PÉRIPHÉRIQUE

DESCRIPTION

Envoie une ou plusieurs commandes SCSI VERIFY (10 ou 16) à PÉRIPHÉRIQUE. Ces commandes SCSI sont définies dans les normes SBC-2 et SBC-3 sur https://www.t10.org et les brouillons SBC-4.

Lorsque --ndo=NDO n'est pas spécifié, la vérification commence à l'adresse de bloc logique donnée par l'option --lba=LBA et se poursuit sur --count=COUNT blocs. Pas plus de --bpc=BPC blocs ne sont vérifiés par chaque commande VERIFY, donc si nécessaire, plusieurs commandes VERIFY sont envoyées. Les opérations de vérification du support sont effectuées par le PÉRIPHÉRIQUE (par exemple, en supposant que chaque bloc a des données EEC supplémentaires, vérifiez cela par rapport au contenu des blocs logiques). Aucune nouvelle n'est une bonne nouvelle (c'est-à-dire que s'il n'y a pas d'erreurs de vérification détectées, aucun message n'est envoyé sur stderr et le statut de sortie Unix est 0).

Lorsque --ndo=NDO est spécifié, l'option --bpc=BPC est ignorée. Une seule commande VERIFY est émise et une comparaison commence à l'adresse de bloc logique donnée par l'option --lba=LBA et se poursuit sur --count=COUNT blocs. La commande VERIFY a un tampon de données de sortie associé qui fait NDO octets de long. Le contenu du tampon de données de sortie est obtenu du fichier FN (si --in=FN est spécifié) ou depuis stdin. Une comparaison a lieu entre le tampon de données de sortie et les blocs logiques sur le PÉRIPHÉRIQUE. Si la comparaison est correcte, aucun message n'est envoyé sur stderr et le statut de sortie Unix est 0. Si la comparaison échoue, un tampon de sense avec une clé de sense MISCOMPARE est retourné ; dans ce cas, le statut de sortie Unix sera 14. Des messages seront envoyés sur stderr associés au tampon de sense MISCOMPARE, sauf si l'option --quiet est spécifiée.

Dans la révision 34 de SBC-3, le champ BYTCHK dans toutes les commandes SCSI VERIFY a été étendu d'un à deux bits. Cela a nécessité quelques modifications dans les options de cet utilitaire, voir la section ci-dessous sur LES CHANGEMENTS D'OPTIONS.

OPTIONS

Les arguments des options longues sont obligatoires pour les options courtes également. Les options sont classées par ordre alphabétique basé sur le nom de l'option longue.

-0, --0
un tampon de NDO octets rempli de zéros est envoyé comme partie de données de sortie d'une commande VERIFY. Ainsi, stdin n'est pas lu et si --in=IF est spécifié, une erreur est générée. Utile lorsque BCH est 3 pour vérifier si tout ou partie du PÉRIPHÉRIQUE (par exemple, un disque) est rempli de blocs nuls.
-S, --16
utilise une commande VERIFY(16) (VERIFY(10) par défaut). Même sans cette option, l'utilisation d'un --lba=LBA trop grand entraînera l'émission d'une commande VERIFY(16) par l'utilitaire.
-b, --bpc=BPC
cette option est ignorée si --ndo=NDO est spécifié. Sinon, BPC spécifie le nombre maximum de blocs qui seront vérifiés par une seule commande SCSI VERIFY. La valeur par défaut est de 128 blocs, ce qui équivaut à 64 Ko pour un disque avec des blocs de 512 octets. Si BPC est inférieur à COUNT, plusieurs commandes SCSI VERIFY sont envoyées au PÉRIPHÉRIQUE. Pour le VERIFY(10) par défaut, BPC ne peut pas dépasser 0xffff (65 535) tandis que pour VERIFY(16), BPC ne peut pas dépasser 0x7fffffff (2 147 483 647). Pour les périphériques bloc récents (disques), cette valeur peut être contrainte par le champ de longueur de transfert maximale de la page de limites de bloc VPD.
-c, --count=COUNT
où COUNT spécifie le nombre de blocs à vérifier. La valeur par défaut est 1. Si COUNT est supérieur à BPC (ou sa valeur par défaut de 128) et que NDO n'est pas spécifié, 0 ou moins de plusieurs commandes SCSI VERIFY sont envoyées au périphérique. Sinon, COUNT devient le contenu du champ de longueur de vérification de la commande SCSI VERIFY émise. L'utilitaire sg_readcap peut être utilisé pour trouver le nombre maximum de blocs d'un périphérique bloc (par exemple, un disque).
-d, --dpo
désactiver le changement de page out, la priorité de rétention du cache des blocs lus dans le cache du périphérique à la priorité la plus basse. Cela signifie que les blocs lus par d'autres commandes sont plus susceptibles de rester dans le cache du périphérique.
-E, --ebytchk=BCH
définit le champ BYTCHK à BCH, remplaçant la valeur (1) définie par l'option --ndo=NDO. Les valeurs 1, 2 ou 3 sont acceptées pour BCH, cependant sbc3r34 réserve la valeur 2. Si cette option est spécifiée, --ndo=NDO doit également être spécifié. Si BCH est 3, alors NDO doit être la taille d'un bloc logique (plus la taille de tout ou partie des informations de protection si VRP est supérieur à 0).
-f, --ff
un tampon de NDO octets rempli d'octets 0xff est envoyé comme partie de données de sortie d'une commande VERIFY. Ainsi, stdin n'est pas lu et si --in=IF est spécifié, une erreur est générée. Utile lorsque BCH est 3 pour vérifier si tout ou partie du PÉRIPHÉRIQUE (par exemple, un disque) est rempli d'octets 0xff.
-g, --group=GN
où GN devient le contenu du champ numéro de groupe dans la commande SCSI VERIFY(16). Il peut être compris entre 0 et 63 inclus. La valeur par défaut pour GN est 0. Notez que cette option est ignorée pour la commande SCSI VERIFY(10).
-h, --help
affiche le message d'utilisation puis quitte.
-i, --in=IF
où IF est le nom d'un fichier à partir duquel NDO octets seront lus et placés dans le tampon de données de sortie. Ceci n'est fait que lorsque l'option --ndo=NDO est spécifiée. Si cette option n'est pas spécifiée, stdin est lu. Si IF est "-", stdin est également utilisé.
-l, --lba=LBA
où LBA spécifie l'adresse de bloc logique du premier bloc pour commencer l'opération de vérification. LBA est supposé être décimal sauf s'il est préfixé par '0x' ou suivi d'un 'h' (voir ci-dessous). La valeur par défaut est 0 (c'est-à-dire le début du périphérique).
-n, --ndo=NDO
NDO est le nombre d'octets à obtenir du fichier FN (si --in=FN est spécifié) ou depuis stdin. Ces octets sont placés dans le tampon de données de sortie associé à la commande SCSI VERIFY et NDO est placé dans le champ de longueur de vérification du cdb. La valeur par défaut de NDO est 0 et la valeur maximale dépend du système d'exploitation. Si l'option --ebytchk=BCH n'est pas spécifiée, le champ BYTCHK du cdb est défini à 1.
-q, --quiet
supprime les messages du tampon de sense associés à une clé de sense MISCOMPARE qui seraient autrement envoyés sur stderr. Définit toujours le statut de sortie à 14, qui est la valeur de la clé de sense indiquant un MISCOMPARE.
-r, --readonly
ouvre le PÉRIPHÉRIQUE en lecture seule plutôt qu'en lecture-écriture, ce qui est le comportement par défaut. Le pilote sg Linux nécessite un accès en lecture-écriture pour la commande SCSI VERIFY, mais d'autres méthodes d'accès peuvent nécessiter un accès en lecture seule.
-v, --verbose
augmente le niveau de verbosité (c'est-à-dire la sortie de débogage).
-V, --version
affiche la chaîne de version puis quitte.
-P, --vrprotect=VRP
où VRP est la valeur du champ vrprotect dans le cdb de la commande VERIFY. Il doit s'agir d'une valeur comprise entre 0 et 7 inclus. La valeur par défaut est zéro.

BYTCHK

BYTCHK est le nom d'un champ (de deux bits de large) dans les commandes VERIFY(10) et VERIFY(16). Lorsqu'il est défini à 1 ou 3 (sbc3r34 réserve la valeur 2), il indique qu'associé à la commande SCSI VERIFY, un tampon de données de sortie sera envoyé pour que le périphérique (disque) vérifie. sg_verify(8)

NOM

sg_verify - vérifie les données sur un périphérique de stockage SCSI.

SYNOPIS

sg_verify [OPTIONS] LBA [COUNT] [--in=FN]

DESCRIPTION

Ce utilitaire envoie une commande VERIFY ( SCSI-3) au périphérique de stockage.

Le champ BYTCHK dans le CDB de la commande VERIFY est défini sur 1 par défaut. Cela signifie que les données lues à partir de LBA (Logical Block Address) sont comparées aux données de vérification dérivées des codes de correction d'erreurs (ECC) du périphérique.

Si le périphérique ne peut pas effectuer la vérification, ou si l'on souhaite une vérification différent, le champ BYTCHK peut être défini sur 0. Ce utilitaire prend en charge le champ BYTCHK surchargé.

Le champ BYTCHK est défini sur 1 par défaut. La commande VERIFY est exécutée avec le champ BYTCHK défini sur 1. La quantité de données à vérifier est déterminée par COUNT (qui peut être 0) et le champ BYTCHK.

Les données de vérification sont obtenues à partir du périphérique, soit à partir de ses codes ECC, soit à partir d'une autre source spécifiée par l'utilisateur.

OPTIONS

-b, --bytchk=BCH
Définit le champ BYTCHK dans le CDB. Les valeurs possibles sont :
0
La vérification est spécifique au vendeur. Elle peut utiliser les données du flux d'entrée (voir --in=FN).
1
Vérifie les données à l'aide des codes ECC (par défaut).
2
Vérifie les données à l'aide des données du flux d'entrée.
3
Vérifie les données à l'aide des données du flux d'entrée et des codes ECC.
-e, --ebytchk=BCH
Surcharge la valeur du champ BYTCHK. Si BCH est différent de 1, cela oblige la vérification à utiliser les données du flux d'entrée. Voir la description de l'option --bytchk.
-i, --in=FN
Lit les données de vérification à partir du fichier FN (ou stdin si FN est un trait d'union).
-n, --ndo=NDO
Définit la longueur des données de vérification. Cette option est obsolète et a été remplacée par --bytchk.
-v, --verbose
Augmente le niveau de détail de la sortie.
-h, --help
Affiche l'aide et quitte.
-V, --version
Affiche les informations de version et quitte.

BYTCHK

Le champ BYTCHK dans le CDB VERIFY spécifie comment le périphérique doit effectuer la vérification. Les valeurs sont :

0 : la vérification est spécifique au vendeur. Les données de vérification proviennent du flux d'entrée (par exemple, le contenu de l'option --in=FN). La longueur des données à vérifier est spécifiée par le champ NDO du CDB.

1 : la vérification est effectuée en comparant les données à vérifier avec les codes ECC des données sur le périphérique. La longueur des données à vérifier est spécifiée par le champ NDO du CDB.

2 : les données de vérification proviennent du flux d'entrée. La longueur des données est la valeur du champ NDO du CDB. Le périphérique compare ces données à ce qui se trouve sur le périphérique.

3 : les données de vérification proviennent du flux d'entrée et sont comparées à la fois aux données sur le périphérique et aux codes ECC de ces données. La longueur des données est la valeur du champ NDO du CDB.

Le nombre d'octets placés dans le tampon de sortie de données. Ces octets sont obtenus à partir de stdin ou IF (depuis l'option --in=FN). L'option --ebytchk=BCH peut être utilisée pour remplacer la valeur du champ BYTCHK de 1 par BCH.

Le calcul de NDO est laissé à l'utilisateur. Sa valeur dépend de la taille logique du bloc (qui peut être trouvée avec l'utilitaire sg_readcap), des valeurs COUNT et VRP. Si VRP est supérieur à 0, chaque bloc logique contiendra 8 octets supplémentaires (au minimum) d'informations de protection.

Lorsque le champ BYTCHK est 0, le processus de vérification effectué par le périphérique (disque) est spécifique au vendeur. Il implique généralement la vérification de chaque bloc sur le disque par rapport à ses codes de correction d'erreurs (ECC), qui sont des données supplémentaires également conservées sur le disque.

De nombreux systèmes d'exploitation imposent des limites à la taille maximale du tampon de sortie de données (et d'entrée de données). Pour Linux, la limite était autrefois inférieure à 1 Mo, mais elle a été quelque peu augmentée.

CHANGEMENTS D'OPTIONS

Les versions antérieures de cet utilitaire avaient une option --bytchk=NDO qui définissait le bit BYTCHK et définissait le champ de longueur de vérification cdb sur NDO. La forme la plus courte de cette option était -B NDO. Pour des raisons de compatibilité ascendante, cette option est toujours présente mais non documentée. À sa place se trouve --ndo=NDO dont la forme la plus courte est -n NDO. --ndo=NDO définit le champ BYTCHK sur 1, sauf si cela est remplacé par --ebytchk=BCH.

NOTES

Divers arguments numériques (par exemple, LBA) peuvent inclure des suffixes multiplicatifs ou être donnés en hexadécimal. Voir la section «ARGUMENTS NUMÉRIQUES» dans la page de manuel sg3_utils(8).

La quantité de correction d'erreurs et le nombre de tentatives avant qu'un bloc ne soit considéré comme défectueux sont contrôlés en partie par la page de mode de récupération d'erreurs de vérification. Une note dans le projet SBC-3 (révision 29 section 6.4.9 sur la page de mode de récupération d'erreurs de vérification) conseille que pour minimiser le nombre de vérifications (et donc avoir la vérification la plus «sensible»), il faut faire ce qui suit dans cette page de mode : définir le bit EER sur 0, le bit PER sur 1, le bit DTE sur 1, le bit DCR sur 1, le nombre de tentatives de vérification sur 0 et la limite de temps de récupération de vérification sur 0. Les pages de mode peuvent être modifiées avec l'utilitaire sdparm.

La commande SCSI VERIFY(6) définie dans la norme SSC-2 et ultérieures (c'est-à-dire pour les systèmes de lecteurs de bandes) n'est pas prise en charge par cet utilitaire.

STATUT DE SORTIE

Le statut de sortie de sg_verify est 0 en cas de succès. Lorsque BCH est différent de 0, une comparaison a lieu et si elle échoue, le statut de sortie est 14, ce qui correspond au code de clé de détection MISCOMPARE.

Les versions antérieures de cet utilitaire définissaient un statut de sortie de 98 en cas de MISCOMPARE.
