NOM

sg3_utils - un ensemble d'utilitaires pour envoyer des commandes SCSI

SYNOPSIS

sg_* [--dry-run] [--enumerate] [--help] [--hex] [--in=FN] [--inhex=FN] [--json[=JO]] [--js-file=JFN] [--maxlen=LEN] [--raw] [--timeout=SECS] [--verbose] [--version] [AUTRES_OPTIONS] [PÉRIPHÉRIQUE]

DESCRIPTION

sg3_utils est un ensemble d'utilitaires qui envoient des commandes SCSI au PÉRIPHÉRIQUE donné via une interface de passage SCSI fournie par le système d'exploitation hôte.

Les noms de tous les utilitaires commencent par "sg" et la plupart commencent par "sg_", souvent suivi du nom, ou d'une abréviation du nom, de la commande SCSI qu'ils envoient. Par exemple, l'utilitaire "sg_verify" envoie la commande SCSI VERIFY. Une correspondance entre les commandes SCSI et les utilitaires sg3_utils qui les émettent est montrée dans le fichier COVERAGE. L'utilitaire sg_raw peut être utilisé pour envoyer une commande SCSI arbitraire (fournie sur la ligne de commande) au PÉRIPHÉRIQUE donné.

sg_decode_sense peut être utilisé pour décoder les données de sense SCSI fournies sur la ligne de commande ou dans un fichier. sg_raw -vvv affichera le nom T10 d'une commande SCSI donnée qui fait le plus souvent 16 octets ou moins de longueur.

Les brouillons de normes SCSI peuvent être trouvés sur https://www.t10.org . Les normes elles-mêmes peuvent être achetées auprès de l'ANSI et d'autres organisations de normalisation. Un bon aperçu de diverses normes SCSI peut être vu sur https://www.t10.org/scsi-3.htm avec les ensembles de commandes SCSI dans la partie supérieure du diagramme. Le document de plus haut niveau (c'est-à-dire le plus abstrait) est le modèle d'architecture SCSI (SAM) avec SAM-5 étant la norme la plus récente (ANSI INCITS 515-2016) avec le projet le plus récent étant la révision 4 de SAM-6. Les commandes SCSI communes à tous les types de périphériques se trouvent dans les commandes primaires SCSI (SPC), dont SPC-5 est la norme la plus récente (ANSI INCITS 502-2020). Le projet SPC le plus récent est SPC-6 révision 6. Les commandes spécifiques aux périphériques de bloc (par exemple, telles qu'utilisées par les disques) sont dans SBC, celles pour les lecteurs de bandes dans SSC, celles pour les boîtiers SCSI dans SES et celles pour les lecteurs de CD/DVD/BD dans MMC.

Il devient de plus en plus courant de contrôler les disques ATA avec l'ensemble de commandes SCSI. Cela implique la traduction des commandes SCSI en leurs équivalents ATA correspondants (et c'est une correspondance imparfaite dans certains cas). La norme pertinente s'appelle SCSI to ATA Translation (SAT, SAT-2 et SAT-3 sont maintenant des normes chez INCITS(ANSI) et ISO, tandis que SAT-4 est au stade de projet). La logique pour effectuer la traduction des commandes est souvent appelée couche SAT ou SATL et peut se trouver dans un système d'exploitation, dans le firmware de l'adaptateur de bus hôte ou dans un périphérique externe (par exemple, associé à un expanseur SAS). Voir https://www.t10.org pour plus d'informations.

Il existe un certain support pour les périphériques de bande SCSI mais pas pour leur fonctionnement de base. Le lecteur est renvoyé à l'utilitaire "mt".

Il existe deux générations d'utilisation des options de ligne de commande. Les utilitaires les plus récents (écrits depuis juillet 2004) utilisent la fonction getopt_long() pour analyser les options de ligne de commande. Avec cette fonction, chaque option a deux représentations : une forme courte (par exemple, '-v') et une forme plus longue (par exemple, '--verbose'). Si un argument est requis, il suit un espace (facultativement) dans la forme courte et un "=" dans la forme longue (par exemple, dans l'utilitaire sg_verify, '-l 2a6h' et '--lba=2a6h' sont équivalents). Notez qu'avec getopt_long(), les options courtes peuvent être élidées, par exemple : '-all' équivaut à '-a -l -l'. L'argument PÉRIPHÉRIQUE peut apparaître après, entre ou avant toute option.

Les utilitaires plus anciens, y compris sg_inq, sg_logs, sg_modes, sg_opcode, sg_rbuff, sg_readcap, sg_senddiag, sg_start et sg_turs avaient un code de traitement de ligne de commande individuel basé typiquement sur un seul "-" suivi d'un ou plusieurs caractères. Si un argument est nécessaire, il suit un "=" (par exemple, '-p=1f' dans sg_modes avec son ancienne interface). Diverses options peuvent être élidées tant qu'elles ne sont pas ambiguës (par exemple, '-vv' pour augmenter la verbosité).

Au fil du temps, l'interface de ligne de commande de ces anciens utilitaires est devenue désordonnée et surchargée d'options. Ainsi, dans la version 1.23 de sg3_utils, l'interface de ligne de commande de ces anciens utilitaires a été modifiée pour avoir à la fois une interface getopt_long() plus propre et leur ancienne interface pour la compatibilité ascendante. Par défaut, ces anciens utilitaires utilisent leur interface basée sur getopt_long(). getopt_long() est une extension GNU (c'est-à-dire pas encore certifiée POSIX) mais les utilitaires de ligne de commande plus récents ont tendance à l'utiliser. Cela peut être remplacé en définissant la variable d'environnement SG3_UTILS_OLD_OPTS ou en utilisant '-O' ou '--old' comme première option de ligne de commande. Les pages man des anciens utilitaires documentent les détails.

Plusieurs utilitaires sg3_utils sont basés sur la commande Unix dd (par exemple, sg_dd) et permettent de copier des données au niveau des commandes SCSI READ et WRITE. sg_dd est étroitement lié à Linux et n'est donc pas porté sur d'autres systèmes d'exploitation. Un utilitaire plus générique (que sg_dd) appelé ddpt dans un paquet du même nom a été porté sur d'autres systèmes d'exploitation.

VARIABLES D'ENVIRONNEMENT

La variable d'environnement SG3_UTILS_OLD_OPTS est expliquée dans la section précédente. Elle ne sert qu'à la compatibilité ascendante des options de ligne de commande pour les anciens utilitaires.

La variable d'environnement SG3_UTILS_INVOCATION a été implémentée sur certains utilitaires qui décodent beaucoup de données. Lorsque SG3_UTILS_INVOCATION est définie, ces utilitaires impriment une ligne de 60 caractères "v". Après cela, le nom de l'utilitaire et sa version (qui comprend une date) suivis d'une ventilation ligne par ligne des arguments de ligne de commande avec lesquels l'utilitaire a été invoqué. Les arguments de ligne de commande incluent le nom de l'utilitaire et les options dans l'ordre où ils ont été donnés. La sortie est envoyée à stdout. L'option est conçue pour aider aux tests automatiques des utilitaires du paquet.

La variable d'environnement SG3_UTILS_DSENSE peut être définie sur un nombre. Elle n'est utilisée que par le SNTL embarqué dans la bibliothèque utilisée par les utilitaires de cette bibliothèque. SNTL est une couche de traduction SCSI vers NVMe. Cette variable d'environnement est définie par défaut sur 0, ce qui amène tout utilitaire émettant une commande SCSI traduite en commande NVMe (par le SNTL embarqué) qui échoue au niveau du périphérique NVMe, à renvoyer le sense SCSI au format 'fixed'. Si cette variable est non nulle, le sense SCSI renvoyé sera au format 'descriptor'.

Plusieurs utilitaires ont leur propre variable d'environnement (par exemple, sg_persist a SG_PERSIST_IN_RDONLY). Voir les pages man individuelles des utilitaires pour plus d'informations.

Il existe une variable d'environnement spécifique à Linux appelée SG3_UTILS_LINUX_NANO qui, si elle est définie et si le pilote sg du système est 4.0.30 ou ultérieur, affichera les durées des commandes en nanosecondes plutôt qu'en millisecondes par défaut. Les durées des commandes ne sont généralement affichées que si --verbose est utilisé 3 fois ou plus. En raison d'un problème d'interface (un entier 32 bits qui devrait être 64 bits avec le recul), la durée maximale pouvant être représentée en nanosecondes est d'environ 4,2 secondes. Si des durées plus longues peuvent survenir, ne définissez pas cette variable d'environnement (ou supprimez-la).

NOMMAGE DES PÉRIPHÉRIQUES LINUX

La plupart des périphériques de blocs de disques ont des noms comme /dev/sda, /dev/sdb, /dev/sdc, etc. Les disques SCSI sous Linux ont toujours eu de tels noms, mais dans les noyaux Linux récents, il est devenu plus courant que de nombreux autres disques (y compris les disques SATA et les périphériques de stockage USB) portent ces noms. Les partitions à l'intérieur d'un disque sont spécifiées par un numéro ajouté au nom du périphérique, commençant à 1 (par exemple, /dev/sda1).

Les lecteurs de bandes sont nommés /dev/st<num> ou /dev/nst<num> où <num> commence à zéro. De plus, une lettre de cette liste : "lma" peut être ajoutée au nom. Les lecteurs (et graveurs) CD, DVD et BD sont nommés /dev/sr<num> où <num> commence à zéro. Il existe des noms de types de périphériques SCSI moins utilisés, les commandes dmesg et lsscsi peuvent aider à trouver si certains sont connectés à un système en cours d'exécution.

Il existe également un pilote de périphérique SCSI qui offre un accès générique alternatif aux périphériques SCSI. Il utilise des noms de la forme /dev/sg<num> où <num> commence à zéro. La commande "lsscsi -g" peut être utile pour trouver ceux-ci et quel nom générique correspond à un nom de type de périphérique (par exemple, /dev/sg2 peut correspondre à /dev/sda). Dans la série lk 2.6, un pilote générique SCSI de bloc a été introduit et ses noms sont de la forme /dev/bsg/<h:c:t:l> où h, c, t et l sont des nombres. Encore une fois, voir la commande lsscsi pour trouver la correspondance entre ce tuple SCSI (c'est-à-dire <

h:c:t:l>) et des noms de périphériques alternatifs.

Avant la série 2.6 du noyau Linux, ces utilitaires ne pouvaient utiliser que des noms de périphériques génériques (par exemple, /dev/sg1). Dans presque tous les cas de la série 2.6 du noyau Linux, tout nom de périphérique peut être utilisé par ces utilitaires.

Très peu de choses ont changé dans la dénomination des périphériques Linux dans les séries 3 et 4 du noyau Linux.

NOMMAGE DES PÉRIPHÉRIQUES SOUS WINDOWS

Les périphériques de stockage et les périphériques associés peuvent avoir plusieurs noms sous Windows. Le plus courant est probablement le nom du volume (par exemple, « D: »). Il existe également des noms de périphériques de "classe" tels que "PhysicalDrive<n>", "CDROM<n>" et "TAPE<n>". <n> est un entier commençant à 0, alloué par ordre croissant à mesure que les périphériques sont découverts (et parfois redécouverts).

Certains périphériques de stockage ont un nom de périphérique de bas niveau SCSI qui commence par un nom d'adaptateur SCSI (pseudo) de la forme "SCSI<n>:". À cela s'ajoute une sous-adressage sous la forme d'un numéro de "bus", d'un identifiant de "cible" et d'un LUN (Logical Unit Number). Le numéro de "bus" est également connu sous le nom de "PathId". Ceux-ci sont assemblés pour former un nom de périphérique de la forme : "SCSI<n>:<bus>,<cible>,<lun>". Le ",<lun>" final peut être omis, auquel cas un LUN de zéro est supposé. Ce nom de périphérique de bas niveau ne peut souvent pas être utilisé directement car Windows bloque les tentatives de l'utiliser si un pilote de classe a "réclamé" le périphérique. Il existe des types de périphériques SCSI (par exemple, type d'interface Automatisation/Lecteur) pour lesquels il n'existe pas de pilote de classe. Au moins deux transports ("types de bus" dans le jargon Windows) : USB et IEEE 1394 n'ont pas de noms de périphériques "scsi" de cette forme.

Conformément aux conventions du système de fichiers DOS, les noms de périphériques peuvent être en majuscules, en minuscules ou en casse mixte. Comme "PhysicalDrive<n>" est fastidieux à écrire, une forme abrégée "PD<n>" est autorisée par tous les utilitaires de ce package.

Un seul périphérique (par exemple, un disque) peut avoir plusieurs noms de périphérique. Par exemple : "PD0" peut aussi être "C:", "D:" et "SCSI0:0,1,0". Les deux noms de volume reflètent que le disque a deux partitions. Les partitions de disque non reconnues par Windows ne reçoivent généralement pas de nom de volume. Cependant, Vista affiche un nom de volume pour un disque qui n'a pas de partitions reconnues par lui et lorsqu'il est sélectionné, invite l'utilisateur à le formater (ce qui peut être plutôt inamical pour d'autres OS).

Ces utilitaires supposent qu'un nom de périphérique donné se trouve dans l'espace de noms des périphériques Win32. Pour le rendre explicite, "\\.\" peut être préfixé aux noms de périphériques mentionnés dans cette section. Attention, la barre oblique inverse est un caractère d'échappement dans les shells de type Unix et le langage de programmation C. Dans un shell comme Msys (de MinGW), chaque barre oblique inverse peut devoir être tapée deux fois.

L'utilitaire sg_scan inclus dans ce package liste les noms de périphériques Windows dans un format approprié pour les autres utilitaires de ce package.

NOMMAGE DES PÉRIPHÉRIQUES SOUS FREEBSD

Les disques SCSI ont des noms de blocs de la forme /dev/da<num> où <num> est un entier commençant à zéro. Le "da" est remplacé par "sa" pour les lecteurs de bande SCSI et par "cd" pour les lecteurs CD/DVD/BD SCSI. Chaque périphérique SCSI a un nom de périphérique de transmission correspondant de la forme /dev/pass<num> où <num> est un entier commençant à zéro. La commande "camcontrol devlist" peut être utile pour savoir quels noms de périphériques SCSI sont disponibles et la correspondance entre les classes et les noms de transmission.

FreeBSD permet de donner les noms de périphériques sans le préfixe "/dev/" (par exemple, da0 au lieu de /dev/da0). Cela fonctionnait dans ce package jusqu'à la version 1.43, où le nom de périphérique sans ornement (par exemple, "da0") provoquait une erreur. L'action originale (c'est-à-dire permettre les noms de périphériques sans ornement) a été rétablie dans la version 1.46. Notez également que les liens symboliques (vers les noms de périphériques) sont suivis avant de préfixer "/dev/" si le nom résultant ne commence pas par un "/".

Le nommage NVMe de FreeBSD a évolué. Le nommage du contrôleur est identique à celui de Linux : "/dev/nvme<n>", mais les espaces de noms ont un "s" supplémentaire (par exemple, "/dev/nvme0ns1"). Ce dernier n'est pas strictement un périphérique bloc (GEOM). Initialement, FreeBSD avait des périphériques GEOM "/dev/nvd<m>" qui n'étaient pas basés sur le sous-système CAM. Puis, dans la version 12 de FreeBSD, un nouveau pilote nda a été ajouté, basé sur CAM (et GEOM) pour les espaces de noms NVMe ; il a des noms comme "/dev/nda0". Les nœuds de périphérique préférés pour ce package sont "/dev/nvme0" pour les contrôleurs NVMe et "/dev/nda0" pour les espaces de noms NVMe.

NOMMAGE DES PÉRIPHÉRIQUES SOUS SOLARIS

Les noms de périphériques SCSI sous le répertoire /dev ont une forme comme : c5t4d3s2 où le numéro après "c" est le numéro du contrôleur (HBA), le numéro après "t" est le numéro de cible (de l'époque de l'interface parallèle SCSI) et le numéro après "d" est le LUN. Après le "s" se trouve le numéro de tranche qui est lié à une partition et, par convention, "s2" représente le disque entier.

OpenSolaris a également une forme c5t4d3p2 où le numéro après "p" est le numéro de partition, à l'exception de "p0" qui représente le disque entier. Ainsi, un disque entier peut être désigné par c5t4d3, c5t4d3s2 ou c5t4d3p0.

Et ces noms de périphériques sont dupliqués dans les répertoires /dev/dsk et /dev/rdsk. Le premier est le nom du périphérique bloc et le second est pour l'accès "brut" (ou périphérique caractère), dont sg3_utils a besoin. Ainsi, dans OpenSolaris, une commande comme 'sg_inq /dev/rdsk/c5t4d3p0' devrait fonctionner. Si cela ne fonctionne pas, ajoutez une option '-vvv' pour plus d'informations de débogage. Essayer la forme 'sg_inq /dev/dsk/c5t4d3p0' (notez que "rdsk" a été changé en "dsk") entraînera une erreur "ioctl inapproprié pour le périphérique".

Les noms de périphériques dans le répertoire /dev sont généralement des liens symboliques vers des noms topologiques beaucoup plus longs dans le répertoire /device. Sous Solaris, les lecteurs CD/DVD/BD sont traités comme des disques et se trouvent donc dans le répertoire /dev/rdsk. Les lecteurs de bande apparaissent dans le répertoire /dev/rmt.

Il existe également un pilote sgen (SCSI générique) qui, par défaut, ne s'attache à aucun périphérique. Voir le fichier /kernel/drv/sgen.conf pour contrôler ce qui est attaché. Tout périphérique attaché aura un nom de périphérique de la forme /dev/scsi/c5t4d3.

Lister les périphériques SCSI disponibles sous Solaris semble être un défi. Le conseil "Utilisez la commande 'format'" fonctionne, mais semble être une manière très dangereuse de lister les périphériques. [Elle demande confirmation avant de causer des dommages.] 'devfsadm -Cv' nettoie le désordre dans le répertoire /dev/rdsk, ne laissant que ce qui est "vivant". La commande "cfgadm -v" semble prometteuse.

PRISE EN CHARGE NVME

NVMe (ou NVM Express) est un transport de stockage et un jeu de commandes relativement nouveaux. Le niveau d'abstraction du jeu de commandes NVMe est quelque peu inférieur à celui des jeux de commandes SCSI, plus proche du niveau d'abstraction des jeux de commandes ATA (et SATA). NVMe prétend être conçu pour le stockage flash et les "disques durs" modernes, ce qui était inimaginable lorsque SCSI a été initialement développé dans les années 1980.

L'avantage des jeux de commandes SCSI réside dans leur ancienneté et les outils existants (comme ceux-ci) pour les prendre en charge. De plus, le niveau d'abstraction des jeux de commandes SCSI est à la fois un avantage et un inconvénient. Récemment, les concepteurs de NVME-MI (Management Interface) ont décidé d'utiliser la norme SCSI Enclosure Services (SES-3) "telle quelle", avec l'ajout de deux commandes NVME-MI de tunneling : SES Send et SES Receive. Cela signifie qu'après avoir pris en compte les différences d'interface de l'OS, les utilitaires sg_ses, sg_ses_microcode et sg_senddiag peuvent être utilisés sur un périphérique NVMe qui prend en charge une version plus récente de NVME-MI.

Les commandes NVME-MI SES Send et SES Receive correspondent respectivement aux commandes SCSI SEND DIAGNOSTIC et RECEIVE DIAGNOSTIC RESULTS. Il y a cependant quelques autres commandes qui doivent être traduites, la plus importante étant la commande SCSI INQUIRY vers l'identification du contrôleur/espace de noms NVMe. À partir de la version 1.43, ces utilitaires contiennent une petite couche de traduction (SNTL - SCSI to NVMe Translation Layer) pour s'occuper de ces détails.

En tant qu'effet secondaire de ce "jonglage", si l'utilitaire sg_inq est utilisé (sans l'option --page=) sur un PÉRIPHÉRIQUE NVMe, les réponses réelles d'identification NVMe (contrôleur et éventuellement espace de noms) sont décodées et affichées. Cependant, si 'sg_inq --page=sinq <périphérique>' est donné pour le même PÉRIPHÉRIQUE, alors des parties de la réponse d'identification du contrôleur et de l'espace de noms NVMe sont traduites en une réponse INQUIRY standard SCSI, qui est ensuite décodée et affichée.

En dehors du cas spécial avec sg_inq, tous les autres utilitaires du package supposent qu'ils communiquent avec un périphérique SCSI et décodent toute réponse en conséquence. Une méthode simple pour les utilisateurs de voir le périphérique sous-jacent est qu'un périphérique NVMe est la réponse INQUIRY standard, le champ Vendor Identification étant "NVMe " (une chaîne de 8 caractères avec 4 espaces à droite).

Les commandes SCSI suivantes sont actuellement prises en charge par la bibliothèque SNTL : INQUIRY, MODE SELECT(10), MODE SENSE(10), READ(10,16), READ CAPACITY(10,16), RECEIVE DIAGNOSTIC RESULTS, REQUEST SENSE, REPORT LUNS, REPORT SUPPORTED OPERATION CODES, REPORT SUPPORTED TASK MANAGEMENT FUNCTIONS, SEND DIAGNOSTICS, START STOP UNIT, SYNCHRONIZE CACHE(10,16), TEST UNIT READY, VERIFY(10,16), WRITE(10,16) et WRITE SAME(10,16).

STATUT DE SORTIE

Pour aider les scripts qui appellent ces utilitaires, le statut de sortie est défini pour indiquer le succès (0) ou l'échec (1 ou plus). Notez que certaines des valeurs inférieures correspondent aux valeurs de la clé de sens SCSI.

Les valeurs de statut de sortie listées ci-dessous peuvent être données à l'utilitaire sg_decode_sense (qui se trouve dans ce package) comme suit :


sg_decode_sense --err=<statut_sortie>

et une courte chaîne explicative sera affichée sur stdout.

Les valeurs de statut de sortie sont :

0
succès. Également utilisé pour certains utilitaires qui souhaitent renvoyer une valeur booléenne pour le cas "vrai" (et qu'aucune erreur ne s'est produite). Le cas faux est transmis par le statut de sortie 36.
1
erreur de syntaxe. Soit des options de ligne de commande illégales, des options avec des arguments incorrects, soit une combinaison d'options qui n'est pas autorisée.
2
le PÉRIPHÉRIQUE signale qu'il n'est pas prêt pour l'opération requ
2
Le DEVICE pourrait être en cours de préparation (par exemple, en cours de démarrage mais pas encore à la bonne vitesse) et l'utilitaire pourrait fonctionner après un délai. Sous Linux, le DEVICE peut être temporairement bloqué pendant que des opérations de récupération d'erreur sont en cours. Voir les valeurs de statut de sortie 12 et 13 ci-dessous qui affinent cette valeur de sortie.
3
Le DEVICE signale une erreur de support ou matérielle (ou un contrôle de blanc). Par exemple, une tentative de lecture d'un bloc corrompu sur un disque donnera cette valeur.
5
Le DEVICE signale une « requête illégale » avec un code de sensibilité supplémentaire autre que « code d'opération de commande illégal ». Il s'agit souvent d'une commande prise en charge avec un champ défini demandant une capacité non prise en charge. Pour les commandes nécessitant un champ « action de service », cette valeur peut indiquer que la commande avec cette valeur d'action de service n'est pas prise en charge.
6
Le DEVICE signale une condition « attention de l'unité ». Cela indique généralement que quelque chose sans rapport avec la commande demandée s'est produit (par exemple, une réinitialisation de l'appareil) potentiellement avant l'envoi de la commande SCSI actuelle. La commande demandée n'a pas été exécutée par l'appareil. Notez que les conditions d'attention de l'unité ne sont généralement signalées qu'une seule fois par un appareil.
7
Le DEVICE signale une clé de sensibilité « protection des données ». Cela implique qu'un mécanisme a bloqué les écritures (ou potentiellement tout accès au support).
9
Le DEVICE signale une requête illégale avec un code de sensibilité supplémentaire « code d'opération de commande illégal », ce qui signifie qu'il ne prend pas en charge la commande demandée.
10
Le DEVICE signale une « copie abandonnée ». Cela implique qu'une autre commande ou un autre problème d'appareil a interrompu une opération de copie. La famille de commandes EXTENDED COPY (y compris WRITE USING TOKEN) peut renvoyer cette clé de sensibilité.
11
Le DEVICE signale une commande abandonnée. Dans certains cas, les commandes abandonnées peuvent être retentées immédiatement (par exemple, si le transport a abandonné la commande en raison d'une congestion).
12
Le DEVICE signale une clé de sensibilité « pas prêt » avec un code de sensibilité supplémentaire « port cible en état de veille ».
13
Le DEVICE signale une clé de sensibilité « pas prêt » avec un code de sensibilité supplémentaire « port cible en état indisponible ».
14
Le DEVICE signale une clé de sensibilité de non-concordance. Les commandes VERIFY et COMPARE AND WRITE peuvent signaler cela.
15
L'utilitaire ne parvient pas à ouvrir, fermer ou utiliser le DEVICE donné ou un autre fichier. Le nom de fichier donné pourrait être incorrect ou il pourrait y avoir des problèmes d'autorisation. L'ajout de l'option '-v' peut fournir plus d'informations.
17
Un code de sensibilité « requête illégale » SCSI reçu avec un indicateur indiquant que le champ Info est valide. Il s'agit souvent d'un LBA, mais sa signification est spécifique à la commande.
18
Le DEVICE signale une erreur de support ou matérielle (ou un contrôle de blanc) avec un indicateur indiquant que le champ Info est valide. Il s'agit souvent d'un LBA (de la première erreur rencontrée), mais sa signification est spécifique à la commande.
19
Le DEVICE signale une requête illégale avec un code de sensibilité supplémentaire « champ illégal dans la liste de paramètres ». La liste de paramètres sont des données supplémentaires envoyées au DEVICE pour certaines commandes (par exemple, FORMAT UNIT).
20
Le DEVICE signale qu'il a une condition de vérification mais « pas de sensibilité » et des informations non nulles dans ses codes de sensibilité supplémentaires. Certaines commandes de scrutation (par exemple, REQUEST SENSE) peuvent recevoir cette réponse. Il peut y avoir des informations utiles dans les données de sensibilité, comme une indication de progression.
21
Le DEVICE signale une « erreur récupérée ». La commande demandée a réussi. Le plus probable est qu'un utilitaire signalera une erreur récupérée sur stderr et continuera, laissant probablement l'utilitaire avec un statut de sortie de 0.
22
Le DEVICE signale que la commande actuelle ou ses paramètres impliquent une adresse de bloc logique (LBA) hors limites. Cela se produit étonnamment souvent lors de la tentative d'accès au dernier bloc d'un périphérique de stockage ; soit une erreur logique classique « un de plus » ou une mauvaise interprétation de la réponse de READ CAPACITY (10 ou 16) dans laquelle l'adresse du dernier bloc plutôt que le nombre de blocs sur le DEVICE est retournée. Puisque les LBA sont originaires de zéro, elles vont de 0 à n-1 où n est le nombre de blocs sur le DEVICE, donc le LBA du dernier bloc est inférieur de un au nombre total de blocs.
24
Le DEVICE signale un statut SCSI de « conflit de réservation ». Cela signifie que l'accès au DEVICE avec la commande actuelle a été bloqué parce qu'une autre machine (HBA ou « initiateur » SCSI) détient une réservation sur ce DEVICE. Sur les systèmes SCSI modernes, cela est lié à l'utilisation de la famille de commandes PERSISTENT RESERVATION.
25
Le DEVICE signale un statut SCSI de « condition remplie ». Actuellement, seule la commande PRE-FETCH (voir SBC-4) renvoie ce statut.
26
Le DEVICE signale un statut SCSI de « occupé ». SAM-6 définit ce statut comme l'unité logique étant temporairement incapable de traiter une commande. Il est recommandé de réémettre la commande.
27
Le DEVICE signale un statut SCSI de « jeu de tâches complet ».
28
Le DEVICE signale un statut SCSI de « ACA actif ». ACA signifie « auto contingent allegiance » et est rarement utilisé.
29
Le DEVICE signale un statut SCSI de « tâche abandonnée ». SAM-5 dit : « Ce statut doit être renvoyé si une commande est abandonnée par une fonction de gestion de commande ou de tâche sur un autre nexus I_T et que le bit TAS de la page de mode Control est défini sur un ».
31
Erreur impliquant deux options ou plus de la ligne de commande. Elles peuvent être contradictoires, sélectionner un mode non pris en charge, ou une option requise (compte tenu du contexte) est manquante.
32
Il y a une erreur logique dans l'utilitaire. Elle correspond à des commentaires de code comme « ne devrait pas/ne peut pas arriver ici ». Peut-être que l'auteur devrait en être informé.
33
La commande envoyée au DEVICE a expiré.
34
Il s'agit d'un statut de sortie spécifique à Windows et indique que le numéro d'erreur Windows (32 bits) ne peut pas être mappé de manière significative à un numéro d'erreur Unix équivalent renvoyé sous forme de statut de sortie (7 bits).
35
Une erreur de transport s'est produite. Cela se produira soit dans le pilote (par exemple, pilote HBA), soit dans l'interconnexion entre l'hôte (initiateur) et l'appareil (cible). Par exemple, dans SAS, un expanseur peut manquer de chemins et ne pas être en mesure de renvoyer les données utilisateur d'une commande READ.
36
Aucune erreur ne s'est produite et l'utilitaire souhaite transmettre une valeur booléenne fausse. La valeur vraie correspondante est transmise par un statut de sortie de 0.
40
La commande envoyée au DEVICE a reçu une clé de sensibilité « commande abandonnée » avec un code de sensibilité supplémentaire de 0x10. Cette valeur est liée à des problèmes d'informations de protection (PI ou DIF). Par exemple, cette erreur peut survenir lors de la lecture d'un bloc sur un disque qui n'a jamais été écrit (ou qui est non mappé) si ce disque a été formaté avec une protection de type 1, 2 ou 3.
41
La commande envoyée au DEVICE a reçu une clé de sensibilité « commande abandonnée » avec un code de sensibilité supplémentaire de 0x10 (comme avec le code d'erreur) plus un indicateur indiquant que le champ Info est valide.
47
Erreur flock (appel système Unix).
48
Il s'agit d'un message interne indiquant qu'un champ de statut NVMe (SF) est différent de zéro après l'exécution d'une commande (c'est-à-dire que quelque chose s'est mal passé). Le travail dans ce domaine est actuellement expérimental.
49
Le pilote de bas niveau signale un nombre résiduel de réponse (c'est-à-dire que le nombre d'octets réellement reçus par le HBA est 'octets_demandés - nombre_résiduel') qui est absurde.
50
Les appels système d'OS qui échouent renvoient souvent un petit nombre entier pour aider. Sous Unix, on les appelle des valeurs « errno », où 0 implique aucune erreur. Ces codes d'erreur réservent 51 à 96 pour le mappage de ces valeurs errno, mais cela peut ne pas être suffisant. Les valeurs errno supérieures qui ne peuvent pas être mappées sont toutes mappées à cette valeur (c'est-à-dire 50).
Notez qu'une valeur errno de 0 est mappée au code d'erreur 0.
50 + <numéro_erreur_os>
Les appels système d'OS qui échouent renvoient souvent un petit nombre entier pour aider à indiquer quelle est l'erreur. Par exemple, sous Unix, l'impossibilité pour un appel système d'allouer de la mémoire renvoie (dans 'errno') ENOMEM, qui est souvent associée à l'entier 12. Ainsi, 62 (c'est-à-dire '50 + 12') peut être renvoyé par un utilitaire dans ce cas. Il est également possible qu'un utilitaire de ce package signale 50+ENOMEM lorsqu'il ne peut pas allouer de mémoire, pas nécessairement à partir d'un appel système d'OS. Dans les versions récentes de Linux, le fichier montrant le mappage entre les constantes symboliques (par exemple, ENOMEM) et l'entier correspondant se trouve dans le fichier source du noyau : include/uapi/asm-generic/errno-base.h
Notez que les valeurs errno supérieures ou égales à 47 ne rentrent pas dans la plage fournie. Au lieu de cela, elles sont toutes mappées à 50 comme discuté dans l'entrée précédente.
97
Une réponse de commande SCSI a échoué aux vérifications de cohérence.
98
Le DEVICE signale qu'il a une condition de vérification, mais l'erreur ne rentre dans aucune des catégories ci-dessus.
99
Toutes les erreurs qui ne peuvent pas être catégorisées dans les valeurs 1 à 98 peuvent produire cette valeur. Cela inclut les erreurs de transport et du système d'exploitation après que la commande a été envoyée à l'appareil.
100-125
Ces codes d'erreur sont utilisés par l'utilitaire ddpt qui utilise la bibliothèque sg3_utils. Ce sont principalement des codes d'erreur spécialisés associés aux copies déchargées.
126
L'utilitaire a été trouvé mais n'a pas pu être exécuté. Cela pourrait se produire si l'exécutable n'a pas les permissions d'exécution.
127
C'est le statut de sortie pour utilitaire non trouvé. Cela pourrait se produire lorsqu'un script appelle un utilitaire de ce package mais que la variable d'environnement PATH n'a pas été correctement configurée, de sorte que le script ne peut pas trouver l'exécutable.
128 + <signum>
Si un signal tue un utilitaire, le statut de sortie est 128 plus le numéro du signal. Par exemple, si une faute de segmentation se produit, un utilitaire est généralement tué par SIGSEGV qui, selon 'man 7 signal', a un numéro de signal associé de 11 ; le statut de sortie sera donc 139.
255
L'utilitaire a tenté de renvoyer un statut de sortie de 255 ou plus. Cela ne devrait pas arriver ; donné ici pour plus de complétude.

La plupart des conditions d'erreur signalées ci-dessus seront répétables (un exemple de celles qui ne le sont pas est « attention de l'unité ») de sorte que l'utilitaire puisse être exécuté à nouveau avec le '-v'

option (ou plusieurs) pour obtenir plus d'informations.

OPTIONS COMMUNES

Les arguments des options longues sont obligatoires pour les options courtes également. Sous forme courte, un argument d'option utilise zéro ou plusieurs espaces comme séparateur (c'est-à-dire que la forme courte n'utilise pas "=" comme séparateur).

Si une option prend un argument numérique, cet argument est supposé être décimal sauf indication contraire (par exemple avec un préfixe "0x", un suffixe "h" ou comme indiqué dans le message d'utilisation).

Certaines options sont utilisées uniformément dans la plupart des utilitaires de ce paquet. Ces options sont listées ci-dessous. Notez qu'il existe quelques exceptions.

-d, --dry-run
les utilitaires qui peuvent entraîner la perte ou l'écrasement de nombreuses données utilisateur disposent parfois d'une option --dry-run. Les actions de modification de périphérique sont généralement ignorées (ou sautées) pour appliquer une politique de "ne pas nuire". Cela permet de tester des invocations de ligne de commande complexes avant que l'action requise (par exemple, formater un disque) ne soit effectuée. L'option --dry-run est devenue une fonctionnalité courante de nombreux utilitaires en ligne de commande (par exemple, la commande Unix 'patch'), pas seulement ceux de ce paquet.
Notez que la plupart des noms d'options avec trait d'union de ce paquet peuvent également être donnés avec un trait de soulignement au lieu d'un trait d'union (par exemple, --dry_run).
-e, --enumerate
certains utilitaires (par exemple, sg_ses et sg_vpd) stockent de nombreuses informations dans des tables internes. Cette option affichera ces informations sous une forme lisible (par exemple, triées par acronyme ou par numéro de page), puis se terminera. Notez qu'avec cette option, DEVICE est ignoré (comme la plupart des autres options) et aucune opération d'E/S SCSI n'est effectuée, de sorte que l'appelant n'a pas besoin de privilèges élevés.
-h, -?, --help
affiche le message d'utilisation puis se termine. Dans quelques utilitaires plus anciens, l'option '-h' demande une sortie hexadécimale. Dans ces cas, l'option '-?' affichera le message d'utilisation puis se terminera.
-H, --hex
pour les commandes SCSI qui renvoient une réponse non triviale, imprimez cette réponse sous forme de quelques octets hexadécimaux ASCII. Utilisée une fois, 16 octets sont imprimés sur chaque ligne, préfixés par une adresse relative, commençant à 0 (hex). Utilisée deux fois, un rendu ASCII des 16 octets est ajouté à chaque ligne, les caractères non imprimables étant remplacés par un '.' . Utilisée trois fois, seuls les 16 octets hexadécimaux sont imprimés sur chaque ligne (donc pas de préfixe d'adresse ni de rendu ASCII ajouté). Pour produire une sortie hexadécimale pouvant être analysée par d'autres utilitaires, utilisez cette option trois, quatre ou cinq fois.
L'utilisation de cette option, en particulier lorsqu'elle est utilisée plusieurs fois, a évolué au fil du temps car elle est devenue plus utile (au moins pour tester et corriger des bugs). Vérifiez donc la description de cette option dans la page de manuel de l'utilitaire utilisé. Un exemple de cas limite avec l'option '-HHH' concerne l'utilitaire sg_inq et la page d'information ATA VPD. L'utilitaire sg_inq ne décode pas la réponse de la commande ATA IDENTIFY DEVICE mais affiche plutôt des mots hexadécimaux de 16 bits (little-endian) adaptés au décodage par l'utilitaire hdparm.
-i, --in=FN
de nombreuses commandes SCSI récupèrent une quantité importante de données (renvoyées dans le tampon d'entrée de données) que plusieurs de ces utilitaires décodent (par exemple, sg_vpd et sg_logs). Pour séparer les deux étapes consistant à récupérer les données d'un périphérique SCSI, puis à les décoder, cette option a été ajoutée. La première étape (récupération des données) peut être effectuée à l'aide de l'option --hex ou --raw et en redirigeant la sortie de la ligne de commande vers un fichier (souvent fait avec ">" sur les systèmes d'exploitation basés sur Unix). La différence entre --hex et --raw est que le premier produit une sortie en hexadécimal ASCII tandis que --raw produit sa sortie en binaire "brut".
La seconde étape (c'est-à-dire le décodage des données de réponse SCSI maintenant contenues dans un fichier) peut être effectuée à l'aide de cette option --in=FN où le nom de fichier est FN. Si "-" est utilisé pour FN, stdin est supposé, ce qui permet à nouveau une redirection (ou un pipe) de ligne de commande. Ce fichier (ou stdin) est supposé contenir de l'hexadécimal ASCII, sauf si l'option --raw est également donnée, auquel cas il est supposé être binaire. Notez que la signification de l'option --raw est "inversée" lorsqu'elle est utilisée avec --in=FN pour agir sur l'entrée, alors qu'elle agit typiquement sur les données de sortie.
Étant donné que la structure des données renvoyées par les commandes SCSI varie considérablement, il convient de vérifier les informations d'utilisation ou la page de manuel de l'utilitaire utilisé. Dans certains cas, --hex peut doit être utilisé plusieurs fois (et est plus commodément donné en '-HH' ou '-HHH).
-i, --inhex=FN
cette option a la même fonctionnalité ou une fonctionnalité similaire que --in=FN. Et peut-être 'inhex' est plus descriptif car par défaut, l'hexadécimal ASCII est attendu dans le contenu du fichier : FN. Alternativement, l'option courte peut être -I ou -X. Voir la section "FORMATS HEXADÉCIMAL, BINAIRE ET JSON" ci-dessous pour plus d'informations.
--json[=JO]
la sortie par défaut de la plupart des utilitaires qui décodent les informations renvoyées par les périphériques SCSI est conçue pour être lisible par l'homme. Parfois, une forme de sortie plus analysable est nécessaire et le JSON est un moyen populaire de le faire. Seuls les utilitaires qui décodent une quantité significative de données SCSI prennent en charge cette option.
L'option courte correspondante est généralement -j[JO] mais peut être -J[JO] si -j est déjà utilisé. Notez que dans tous les cas, l'argument JO est facultatif. Voir la page de manuel sg3_utils_json pour plus d'informations.
-J, --js-file=JFN
la sortie est au format JSON et est envoyée à un fichier nommé JFN. Si ce fichier existe, il est tronqué. Par défaut, la sortie JSON est envoyée à stdout.
Lorsque cette option est donnée, l'option --json[=JO] est implicite et n'a pas besoin d'être donnée. L'option --json[=JO] peut toujours être nécessaire pour définir le paramètre JO sur des valeurs non défaut.
-m, --maxlen=LEN
plusieurs commandes SCSI importantes (par exemple, INQUIRY et MODE SENSE) ont des longueurs de réponse qui varient en fonction de nombreux facteurs, dont seuls certains sont pris en compte par ces utilitaires. La longueur de réponse maximale est généralement spécifiée dans le champ 'longueur d'allocation' du cdb. En l'absence de cette option, plusieurs utilitaires utilisent une longueur d'allocation par défaut (parfois recommandée dans les ébauches de normes SCSI) ou une stratégie de "double récupération" (double fetch). Voir sg_logs(8) pour sa description d'une stratégie de "double récupération". Ces techniques sont imparfaites et en présence de cibles SCSI défectueuses, elles peuvent causer des problèmes (par exemple, certains périphériques de stockage de masse USB se bloquent si ils reçoivent une longueur d'allocation INQUIRY autre que 36). L'utilisation de cette option désactive également toute stratégie de "double récupération" qui aurait pu être utilisée autrement.
Pour éviter une classe de bugs dégénérés, si LEN est inférieur à 16, il est ignoré (généralement avec un message d'avertissement) et la valeur par défaut est utilisée à la place. Certains utilitaires utilisent 4 (octets) plutôt que 16 comme valeur de coupure.
-r, --raw
pour les commandes SCSI qui renvoient une réponse non triviale, imprimez cette réponse en binaire sur stdout. S'il y a des messages d'erreur ou des avertissements, ils sont généralement envoyés sur stderr afin de ne pas interférer avec la sortie de cette option.
Certains utilitaires qui consomment des données à envoyer au DEVICE avec la commande SCSI, utilisent cette option. Alternativement, l'option --in=FN fait que DEVICE est ignoré et que les données de réponse (à décoder) sont récupérées d'un fichier nommé FN. Dans ces cas, cette option peut indiquer que des données binaires peuvent être lues depuis stdin ou depuis un fichier désigné (par exemple, FN).
-t, --timeout=SECS
les utilitaires qui émettent des commandes SCSI potentiellement longues ont souvent une option --timeout=SECS. Cela demande généralement au système d'exploitation d'annuler la commande SCSI en question une fois que le délai expire. L'annulation des commandes SCSI est généralement une affaire compliquée et, dans le cas de commandes de formatage, peut laisser le périphérique dans un état de "format corrompu" nécessitant l'envoi d'une autre commande de réinitialisation longue. L'argument, SECS, est généralement en secondes et la forme courte de l'option peut être autre que -t car l'option de délai a été généralement ajoutée plus tard, les périphériques de stockage devenant plus grands et les commandes d'initialisation prenant plus de temps. Étant donné que de nombreux utilitaires avaient des délais de commande internes relativement longs avant l'introduction de cette option, le délai de commande réel donné aux systèmes d'exploitation est le plus élevé entre le délai interne et SECS.
De nombreuses commandes SCSI longues ont un bit IMMED dans le CDB qui fait que la commande retourne relativement rapidement, mais l'opération demandée n'a été que commencée, pas terminée. Dans de tels cas, la commande REQUEST SENSE peut être utilisée pour surveiller la progression via son champ d'indication de progression (voir les utilitaires sg_requests et sg_turs). Les utilitaires qui envoient de telles commandes SCSI ont soit une option --immed, soit une option --wait qui est l'inverse logique de l'action "immédiate". Envoyer une commande d'accès aux données SCSI à un périphérique qui est occupé à exécuter une commande SCSI longue (en arrière-plan) entraînera généralement une clé de détection NOT READY avec un code de sens supplémentaire de 0x04 et un code qualificateur qui indique quelle opération longue le périphérique est en train d'exécuter.
Une forme alternative d'option longue est --tmo=SECS.
-v, --verbose
augmente le niveau de verbosité (c'est-à-dire la sortie de débogage). Peut être utilisé plusieurs fois pour augmenter davantage la verbosité. La sortie supplémentaire causée par cette option est presque toujours envoyée sur stderr.
-V, --version
imprime la chaîne de version puis se termine. Chaque utilitaire a son propre numéro de version et date de dernière modification du code.

ARGUMENTS NUMÉRIQUES

De nombreux utilitaires ont des options en ligne de commande qui prennent des arguments numériques. Ces arguments numériques peuvent être de grandes valeurs (par exemple, une adresse de bloc logique (LBA) sur un disque) et peuvent être peu pratiques à saisir dans la représentation décimale par défaut. Ainsi, diverses autres représentations sont

NUMERICAL ARGUMENTS

Les arguments numériques peuvent être précédés de zéros et de préfixes comme ci-dessous.

Les nombres peuvent être décimaux, hexadécimaux ou octaux. Les nombres octaux sont préfixés par un zéro (par exemple, 010 pour 8). Les nombres hexadécimaux sont préfixés par 0x ou 0X (par exemple, 0x10 pour 16). Les autres nombres sont traités comme décimaux.

L'utilisation de suffixes multiplicatifs est autorisée. Ce sont des chaînes de un, deux ou trois caractères ajoutées directement après le nombre auquel elles s'appliquent :


c C *1
w W *2
b B *512
k K KiB *1024
KB kB *1000
m M MiB *1048576
MB mB *1000000
g G GiB *(2^30)
GB gB *(10^9)
t T TiB *(2^40)
TB *(10^12)
p P PiB *(2^50)
PB *(10^15)

Un exemple est "2k" pour 2048. Les grands suffixes tera et peta ne sont disponibles que pour les arguments numériques qui pourraient nécessiter 64 bits pour être représentés en interne.

Ces suffixes multiplicatifs sont compatibles avec la commande dd de GNU (depuis 2002) qui prétend être conforme aux normes SI et IEC 60027-2.

Un suffixe de la forme "x<n>" multiplie le nombre précédent par <n>. Un exemple est "2x33" pour "66". L'argument de gauche ne peut pas être '0' car '0x' sera interprété comme un préfixe de nombre hexadécimal (voir ci-dessous). L'argument de gauche de la multiplication doit se terminer par un chiffre hexadécimal (c'est-à-dire 0 à f) et l'ensemble de l'expression ne doit pas contenir d'espaces intégrés (par exemple, des espaces). Un exemple peu élégant : "0xfx0x2" pour 30.

Un suffixe de la forme "+<n>" ajoute le nombre précédent à <n>. Un exemple est "3+1k" pour "1027". L'argument de gauche de l'addition doit se terminer par un chiffre hexadécimal (c'est-à-dire 0 à f) et l'ensemble de l'expression ne doit pas contenir d'espaces intégrés (par exemple, des espaces). Un autre exemple : "0xf+0x2" pour 17.

Alternativement, les arguments numériques peuvent être donnés en hexadécimal. Il existe deux syntaxes. Le nombre peut être précédé de "0x" ou "0X" comme on le trouve dans le langage de programmation C. La deuxième représentation hexadécimale est un "h" ou "H" final comme on le trouve dans les normes (de stockage). Lorsque des nombres hexadécimaux sont donnés, les multiplicateurs ne peuvent pas être utilisés. Par exemple, la valeur décimale "256" peut être donnée sous forme de "0x100" ou "100h".

FORMATS HEXADÉCIMAL, BINAIRE ET JSON

L'hexadécimal (ASCII) et le binaire peuvent tous deux être utilisés comme sortie de bas niveau des réponses SCSI, qui peuvent être redirigées vers un fichier et décodées lors d'une invocation ultérieure. La sortie JSON est généralement générée après décodage et considérée comme une sortie de haut niveau qui peut être analysée par un autre outil. Aucun utilitaire dans sg3_utils ne peut analyser du JSON en entrée.

La sortie JSON est décrite dans sa propre page de manuel, voir : sg3_utils_json(8).

La sortie binaire et surtout hexadécimale peut avoir deux rôles : pour l'affichage immédiat (par exemple, lors du débogage) ou comme une sortie analysable qui peut être décodée plus tard. Cette dernière action utilise l'option --inhex=FN. Pour afficher la sortie hexadécimale (par exemple, provenant d'une réponse de commande SCSI), l'option --hex peut être utilisée une ou deux fois. Les deux ont une sortie similaire à :
$ hexdump --no-squeezing -C

Lorsqu'il y a une seule option --hex, le rendu ASCII à droite de chaque ligne n'est pas affiché ; lorsqu'elle est utilisée deux fois, le rendu ASCII est affiché.
Lorsque l'option --hex est utilisée trois fois ou plus, on suppose qu'elle sera analysée plus tard. Seuls les octets de données hexadécimales sont affichés, jusqu'à 16 par ligne. Ceci est proche de cette invocation hexdump :
$ hexdump --no-squeezing -C | cut -s -d ' ' -f 2-19

Cela supprimera la première colonne (c'est-à-dire le compte) et le rendu ASCII à droite. Cela rend l'analyse de l'hexadécimal beaucoup plus facile. Lorsqu'elle est utilisée 4 fois ou plus, l'option --hex ajoute des commentaires (c'est-à-dire des lignes commençant par le symbole dièse) :
$ sg_logs -HHHH -A /dev/sdc


# Supported log pages log page [0x0]:
00 00 00 03 00 0d 2f


# Supported log pages and subpages log page [0x0, 0xff]:
40 ff 00 0e 00 00 00 ff 0d 00 0d 01 0d ff 2f 00
2f ff
...

Les commentaires peuvent également être placés après les hexadécimaux sur une ligne, tout ce qui se trouve du '#' à la fin de la ligne est ignoré.

Il existe de nombreux exemples de fichiers hexadécimaux adaptés à l'option --inhex=FN dans le répertoire 'inhex'. La dénomination des fichiers dans ce répertoire est le nom de l'utilitaire qui le décodera avec le préfixe "sg_" supprimé et un suffixe ".hex" ajouté. Ces fichiers hexadécimaux peuvent être consultés avec un éditeur de texte et la plupart contiennent un exemple d'invocation dans les commentaires en tête.

Le format hexadécimal peut être converti en binaire à l'aide de l'utilitaire sg_decode_sense avec les options suivantes : "--inhex=HFN --nodecode --write=WFN". L'entrée (en hex) se trouve dans le fichier HFN tandis que la sortie est placée dans le fichier WFN.

Pour convertir un fichier binaire en forme hexadécimale qui peut être fournie en entrée à divers utilitaires sg3_utils, l'utilitaire sg_decode_sense peut également être utilisé avec ces options : "--binary=BFN --nodecode -HHH" et la sortie hexadécimale sera envoyée à la console (stdout).

MICROCODE ET FIRMWARE

Il existe deux méthodes standardisées pour télécharger du microcode (c'est-à-dire le firmware de l'appareil) vers un périphérique SCSI. La méthode la plus générale consiste à utiliser la commande SCSI WRITE BUFFER, voir l'utilitaire sg_write_buffer. Les boîtiers SCSI ont leur propre méthode basée sur la page de diagnostic Download microcode control/status, voir l'utilitaire sg_ses_microcode.

SCRIPTS, EXEMPLES et UTILS

Il existe plusieurs scripts shell bash dans le sous-répertoire 'scripts' qui invoquent des utilitaires compilés (par exemple, sg_readcap). Plusieurs des scripts commencent par 'scsi_' plutôt que par 'sg_'. L'un des buts de ces scripts est d'appeler le même utilitaire (par exemple, sg_readcap) sur plusieurs périphériques. La plupart des utilitaires compilés de base ne permettent qu'un seul périphérique comme argument. Certaines distributions installent ces scripts dans un répertoire plus visible (par exemple, /usr/bin). Certains de ces scripts ont des entrées de manuel. Voir le fichier README dans le sous-répertoire 'scripts'.

Il existe du code C exemple ainsi que des exemples d'invocations complexes dans le sous-répertoire 'examples'. Il y a aussi un fichier README. Le code C exemple peut être un exemple plus simple de la façon d'utiliser un passe-travers SCSI sous Linux que les utilitaires principaux (trouvés dans le sous-répertoire 'src'). Cela est dû aux moins nombreuses couches d'abstraction (par exemple, ils ne s'inquiètent pas du fait que MinGW sous Windows puisse ouvrir un fichier en mode texte plutôt qu'en mode binaire).

Certains utilitaires que l'auteur a trouvés utiles ont été placés dans le sous-répertoire 'utils'.

DÉBOGAGE

Chaque utilitaire et la plupart des scripts ont une option --verbose (forme courte : -v) qui peut être utilisée plusieurs fois pour augmenter la verbosité de la sortie afin d'aider au débogage. La sortie normale (le cas échéant) est envoyée à stdout tandis que la sortie verbeuse (et la sortie d'erreur) est envoyée à stderr. Cela peut être important lorsque la (sortie normale) d'un utilitaire est redirigée vers une autre commande (par exemple, la commande grep pour trouver un champ particulier dans la sortie).

Le sous-système SCSI Linux dispose d'un pseudo-fichier pour obtenir et modifier le niveau de journalisation SCSI : /proc/sys/dev/scsi/logging_level . Le script scsi_logging_level de ce package peut être utilisé pour manipuler le niveau de journalisation d'une manière conviviale pour la ligne de commande. Voir sa page de manuel.

Le niveau de journalisation va de 0 (aucune journalisation et par défaut) à 7 (beaucoup de journalisation) et s'applique à tous les périphériques de stockage qui utilisent le sous-système SCSI. La sortie de journalisation va vers "le journal" qui est souvent le fichier /var/log/syslog.

Le pilote générique SCSI (sg) de Linux est souvent utilisé avec les utilitaires de ce package. Il utilise un type de journalisation SCSI_LOG_TIMEOUT rarement utilisé (sinon). Un exemple de son utilisation pour activer le débogage complet est :


scsi_logging_level -s -T 7

Pour réduire la quantité de sortie aux seuls chemins d'erreur, le suivi est suggéré :


scsi_logging_level -s -T 3

Et pour désactiver la journalisation dans le pilote sg :


scsi_logging_level -s -T 0

Pour analyser les plantages de machine associés à une commande SCSI, rien ne vaut un vrai port série. Par "vrai" on entend qu'il ne s'agit PAS d'un port série USB. La raison est que, comme SCSI, USB a besoin d'une pile logicielle fonctionnelle au sein du noyau du système d'exploitation, la même chose qui peut être crippled pendant un crash de machine.

Les ordinateurs portables modernes n'ont pas de vrais ports série et beaucoup de machines serveur non plus (ou c'est une option supplémentaire). Sous Linux, le module netconsole fait un très bon travail en envoyant des entrées de journal à une autre machine (sur le même sous-réseau) en utilisant le protocole réseau UDP ("fire and forget").
