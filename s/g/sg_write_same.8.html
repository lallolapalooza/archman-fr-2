NOM

sg_write_same - envoie la commande SCSI WRITE SAME

SYNTAXE

sg_write_same [--10] [--16] [--32] [--anchor] [--ff] [--grpnum=GN] [--help] [--in=IF] [--lba=LBA] [--lbdata] [--num=NUM] [--ndob] [--pbdata] [--timeout=TO] [--unmap] [--verbose] [--version] [--wrprotect=WPR] [--xferlen=LEN] PÉRIPHÉRIQUE

DESCRIPTION

Envoie la commande SCSI WRITE SAME (10, 16 ou 32 octets) au PÉRIPHÉRIQUE. Cette commande écrit les NUM blocs donnés plusieurs fois sur des blocs consécutifs du PÉRIPHÉRIQUE à partir de l'adresse de bloc logique LBA.

La longueur du bloc à écrire plusieurs fois est obtenue soit de l'argument LEN, soit de la longueur du fichier d'entrée donné IF, soit en appelant READ CAPACITY(16) sur le PÉRIPHÉRIQUE. Le contenu du bloc à écrire est obtenu à partir du fichier d'entrée IF ou des zéros sont utilisés. Si READ CAPACITY(16) est appelée (ce qui implique que IF n'a pas été donné) et que le bit PROT_EN est défini, alors 8 octets supplémentaires (c'est-à-dire plus que la taille du bloc logique) de 0xff sont envoyés. Si READ CAPACITY(16) échoue, alors READ CAPACITY(10) est utilisé pour déterminer la taille du bloc.

Si ni --10, ni --16, ni --32 n'est donné, alors WRITE SAME(10) est envoyé, sauf si l'une des conditions suivantes est remplie. Si LBA (plus NUM) dépasse 32 bits, NUM dépasse 65535, ou l'option --unmap est donnée, alors WRITE SAME(16) est envoyé. Les options --10, --16 et --32 sont mutuellement exclusives.

La révision 35d de SBC-3 a introduit un bit « No Data-Out Buffer » (NDOB) qui, s'il est défini, contourne l'exigence d'envoyer un seul bloc de données au PÉRIPHÉRIQUE avec la commande. Seuls WRITE SAME (16 et 32 octets) prennent en charge le bit NDOB. S'il est donné, un bloc d'utilisateurs de zéros est supposé ; si nécessaire, des informations de protection de 0xff sont supposées.

Dans la révision 26 de SBC-3, les bits UNMAP et ANCHOR ont été ajoutés à la commande WRITE SAME (10). Étant donné que le bit UNMAP est présent dans WRITE SAME (16) et WRITE SAME (32) depuis la révision 18 de SBC-3, la plus faible des deux (c'est-à-dire WRITE SAME (16)) est la valeur par défaut lorsque l'option --unmap est donnée. Pour envoyer WRITE SAME (10), utilisez l'option --10.

Attention : Les commandes WRITE SAME(10, 16 et 32) peuvent interpréter une valeur NUM de zéro comme une écriture jusqu'à la fin du PÉRIPHÉRIQUE. Cet utilitaire fait passer NUM par défaut à 1. Les commandes WRITE SAME n'ont pas de bit IMMED, donc si NUM est grand (ou zéro), une invocation de cet utilitaire pourrait prendre beaucoup de temps, potentiellement autant qu'une commande FORMAT UNIT. Dans de telles situations, la valeur de délai d'attente de la commande TO peut devoir être augmentée par rapport à sa valeur par défaut de 60 secondes. Dans la révision 26 de SBC-3, le bit WSNZ (write same no zero) a été ajouté à la page VPD Block Limits [0xB0]. S'il est défini, les commandes WRITE SAME n'accepteront pas une valeur NUM de zéro. La même révision SBC-3 a ajouté le champ « Maximum Write Same Length » à la page VPD Block Limits.

La page VPD Logical Block Provisioning [0xB2] contient les bits LBPWS et LBPWS10. Si LBPWS est défini, WRITE SAME (16) prend en charge le bit UNMAP. Si LBPWS10 est défini, WRITE SAME (10) prend en charge le bit UNMAP. Si LBPWS ou LBPWS10 est défini et que WRITE SAME (32) est pris en charge, alors WRITE SAME (32) prend en charge le bit UNMAP.

Par mesure de sécurité contre un `sg_write_same /dev/sda` accidentel (par exemple) qui écraserait le LBA 0 sur /dev/sda avec des zéros, au moins une des options --in=IF, --lba=LBA ou --num=NUM doit être donnée. Évidemment, cet utilitaire peut détruire beaucoup de données utilisateur, alors vérifiez attentivement les options.

OPTIONS

Les arguments des options longues sont obligatoires pour les options courtes également. Les options sont classées par ordre alphabétique en fonction du nom de l'option longue.

-R, --10
envoie une commande SCSI WRITE SAME (10) au PÉRIPHÉRIQUE. La possibilité de définir les options --unmap (et --anchor) pour cette commande a été ajoutée dans la révision 26 de SBC-3.
-S, --16
envoie une commande SCSI WRITE SAME (16) au PÉRIPHÉRIQUE.
-T, --32
envoie une commande SCSI WRITE SAME (32) au PÉRIPHÉRIQUE.
-a, --anchor
définit le bit ANCHOR dans le cdb. Introduit dans la révision 22 de SBC-3. Cette ébauche exige que l'option --unmap soit également spécifiée.
-f, --ff
le tampon de données sortantes envoyé avec cette commande est initialisé avec des octets 0xff lorsque cette option est donnée.
-g, --grpnum=GN
définit le champ « Group number » à GN. La valeur par défaut est zéro. GN doit être une valeur comprise entre 0 et 63.
-h, --help
affiche le message d'utilisation puis quitte.
-i, --in=IF
lit les données (binaires) depuis le fichier nommé IF et les utilise comme tampon de données sortantes pour la commande SCSI WRITE SAME. La longueur du tampon de données sortantes est --xferlen=LEN ou, si celle-ci n'est pas donnée, la longueur du fichier IF. Si IF est « - », stdin est lu. Si cette option et l'option --ff ne sont pas données, des octets 0x00 sont utilisés comme remplissage avec la longueur du tampon de données sortantes obtenue à partir de --xferlen=LEN ou en appelant READ CAPACITY(16 ou 10). Si la réponse à READ CAPACITY(16) a le bit PROT_EN défini, la taille du tampon de données sortantes est modifiée en conséquence avec les 8 derniers octets définis à 0xff.
-l, --lba=LBA
où LBA est l'adresse du bloc logique à partir de laquelle la commande WRITE SAME doit commencer. La valeur par défaut est le LBA 0, ce qui est un bloc dangereux à écraser sur un disque en cours d'utilisation. Supposé être en décimal sauf s'il est précédé de '0x' ou a un 'h' final.
-L, --lbdata
définit le bit LBDATA dans le cdb WRITE SAME. Ce bit a été rendu obsolète dans sbc3r32 en septembre 2012.
-N, --ndob
définit le bit NDOB dans les commandes WRITE SAME (16 et 32 octets). NDOB signifie « No Data-Out Buffer ». Par défaut, ce bit est effacé. Lorsque cette option est donnée, --in=IF n'est pas autorisée et --xferlen=LEN ne peut être donné que si LEN est 0.
Par défaut, des zéros sont écrits dans chaque bloc, mais il est possible que le « motif d'initialisation de provisionnement » soit écrit en fonction d'autres paramètres.
-n, --num=NUM
où NUM est le nombre de blocs, à partir de LBA, vers lesquels écrire le tampon de données sortantes. La valeur par défaut de NUM est 1. La valeur correspond au champ « Number of logical blocks » dans le cdb WRITE SAME.
Notez qu'une valeur de 0 dans NUM peut être interprétée comme l'écriture du tampon de données sortantes sur chaque bloc à partir de LBA jusqu'à la fin du PÉRIPHÉRIQUE. Si le bit WSNZ (introduit dans sbc3r26, janvier 2011) dans la page VPD Block Limits est défini, la valeur 0 est interdite, générant une clé de détection « Invalid request ».
-P, --pbdata
définit le bit PBDATA dans le cdb WRITE SAME. Ce bit a été rendu obsolète dans sbc3r32 en septembre 2012.
-t, --timeout=TO
où TO est la valeur de délai d'attente de la commande en secondes. La valeur par défaut est 60 secondes. Si NUM est grand (ou zéro), une commande WRITE SAME peut nécessiter beaucoup plus de temps que 60 secondes pour s'achever.
-U, --unmap
définit le bit UNMAP dans le cdb WRITE SAME(10, 16 et 32). Voir la section UNMAP ci-dessous.
-v, --verbose
augmente le niveau de verbosité (messages de débogage).
-V, --version
affiche la chaîne de version puis quitte.
-w, --wrprotect=WPR
définit le champ « Write protect » dans le cdb WRITE SAME à WPR. La valeur par défaut est zéro. WPR doit être une valeur comprise entre 0 et 7. Lorsque WPR est 1 ou plus, et que le type de protection du disque est 1 ou plus, alors 8 octets supplémentaires d'informations de protection sont attendus ou génér

UNMAP

Le bit UNMAP dans la commande WRITE SAME est utilisé pour déprovisionner des blocs logiques. Si UNMAP est défini, le bloc de données sortantes (si envoyé) est ignoré et le périphérique marque les blocs spécifiés comme n'étant plus utilisés. Cela peut avoir pour effet de libérer de l'espace sur le stockage sous-jacent (par exemple, dans un pool de stockage SSD ou sur un système de fichiers qui prend en charge le déprovisionnement).

Lorsqu'UNMAP est défini, la valeur de NUM spécifie le nombre de blocs à déprovisionner, en commençant par LBA. Si NUM est zéro, tous les blocs à partir de LBA jusqu'à la fin du périphérique sont déprovisionnés.

Il est important de noter que l'utilisation de l'option --unmap peut entraîner une perte de données si elle est appliquée aux mauvais blocs ou périphériques. Vérifiez soigneusement vos commandes.

EXEMPLES

Pour écrire un bloc de 512 octets à l'adresse logique de bloc 1000 sur le périphérique /dev/sdc, et répéter cette écriture 5 fois:

sg_write_same --lba=1000 --num=5 --xferlen=512 /dev/sdc

Pour envoyer une commande WRITE SAME (16 octets) pour déprovisionner tous les blocs à partir de LBA 5000 sur /dev/sdb:

sg_write_same --16 --unmap --lba=5000 --num=0 /dev/sdb

Pour lire 4096 octets à partir du fichier data.bin et les écrire une seule fois à l'adresse logique de bloc 2048 sur /dev/sdc, en utilisant une commande WRITE SAME (10 octets):

sg_write_same --10 --in=data.bin --lba=2048 --num=1 /dev/sdc

OPTIONS

--0x
Treats numeric arguments as hexadecimal. It is equivalent to prefixing numeric arguments with '0x'.
-a, --all
Unmap or write all blocks in the specified range. When used with UNMAP, all blocks in the LBA range are unmapped. When used with WRITE SAME, all blocks in the LBA range are written with the given data (or zeros/pattern if no input file is specified). By default, only the first block in the range is affected unless this option is specified.
-d, --dpo
Set the DPO (Disable Page Out) bit in the cdb. This is typically ignored by storage devices but may be used to indicate that subsequent cache management operations should not be affected.
-f, --force
Force the operation. This option is used to override certain safety checks. For example, it can be used to bypass checks on the data-out buffer when using the UNMAP command.
-i, --in=IF
Read data from the file IF to be written to the device. If this option is not given, then zeros are used as the data to be written. If the data needs to be padded to fill the block size, zeros are used as pad bytes.
-l, --lba=LBA
Where LBA is the Logical Block Address (starting from 0) from which to begin the operation. Defaults to 0.
-n, --num=NUM
Where NUM is the number of logical blocks to write or unmap. If NUM is 0, it means all blocks from the starting LBA to the end of the device. Defaults to 1.
-p, --protective
Set the PROT_EN bit in the cdb. This indicates that protection information is enabled for the operation.
-r, --rdprotect=RPROT
Set the RDPROT field in the cdb. This field controls the type of protection information expected by the device. Valid values are 0 to 7. Defaults to 0.
-s, --sense
Report sense data if the command fails. This is useful for diagnosing errors.
-t, --t10_dif
Enable T10 DIF (Data Integrity Field) for the operation. This adds protection information (like CRC) to the data blocks.
-u, --unmap
Use the UNMAP command instead of WRITE SAME. This marks the specified blocks as unused, which can help with storage management and performance on some devices (e.g., SSDs).
-v, --verbose
Increase verbosity. Print detailed information about the operation.
-w, --wrprotect=WPR
Set the WRPROT field in the cdb. This field controls write protection settings for the operation. Valid values are 0 to 7. Defaults to 0.
-x, --xferlen=LEN
where LEN is the length of the data-out buffer. Defaults to the length of the IF file or, if that is not given, then the READ CAPACITY(16 or 10) command is used to find the 'Logical block length in bytes'. That figure may be increased by 8 bytes if the DEVICE's protection type is 1 or greater and the WRPROTECT field (see --wrprotect=WPR) is 1 or greater. If both this option and the IF option are given and LEN exceeds the length of the IF file then LEN is the data-out buffer length with zeros used as pad bytes.

UNMAP

Le provisionnement de blocs logiques est un nouveau terme introduit dans la révision 25 de SBC-3 pour la capacité de marquer des blocs comme inutilisés. Pour les grands réseaux de stockage, c'est un moyen de fournir moins de stockage physique que ce que le rapport de la commande READ CAPACITY indique comme disponible, allouant potentiellement plus de stockage physique lorsque les commandes WRITE en ont besoin. Pour la mémoire flash (par ex. les disques SSD), c'est un moyen potentiel d'économiser de l'énergie (et peut-être du temps d'accès) lorsqu'il est connu que de grandes sections (ou la quasi-totalité) de la mémoire flash ne sont pas utilisées. Les SSD nécessitent des algorithmes d'équilibrage de l'usure pour avoir une endurance acceptable et provisionnent généralement en excès pour simplifier ces algorithmes ; par conséquent, ils contiennent généralement plus de stockage flash physique que leur taille logique ne le dicterait.

La prise en charge du provisionnement de blocs logiques est indiquée par le bit LBPME défini dans la réponse de la commande READ CAPACITY(16) (voir l'utilitaire sg_readcap). Cela implique qu'au moins une des commandes UNMAP ou WRITE SAME(16) est implémentée. Si la commande UNMAP est implémentée, alors les champs "Maximum unmap LBA count" et "Maximum unmap block descriptor count" de la page VPD Block Limits doivent tous deux être supérieurs à zéro. La réponse de la commande READ CAPACITY(16) contient également un bit LBPRZ qui, s'il est défini, signifie que si des blocs non mappés sont lus, des zéros seront retournés pour les données (et si les informations de protection sont actives, des octets 0xff seront retournés pour celles-ci). Dans la révision 27 de SBC-3, le même bit LBPRZ a été ajouté à la page VPD Logical Block Provisioning.

Dans la révision 25 de SBC-3, les bits LBPU et ANC_SUP ont été ajoutés à la page VPD Logical Block Provisioning. Lorsque LBPU est défini, cela indique que le périphérique prend en charge la commande UNMAP (voir l'utilitaire sg_unmap). Lorsque le bit ANC_SUP est défini, cela indique que le périphérique prend en charge les LBA ancrés.

Lorsque le bit UNMAP est défini dans le cdb, le tampon de sortie de données est également envoyé. De plus, la section de données de ce tampon de sortie de données doit être remplie d'octets 0x00 tandis que le bloc de protection des données, 8 octets à la fin s'il est présent, doit être défini sur des octets 0xff. Si ces conditions ne sont pas remplies et que le bit LBPRZ est défini, le bit UNMAP est ignoré et le tampon de sortie de données est écrit sur le DEVICE comme si le bit UNMAP était zéro. En l'absence de l'option --in=IF, cet utilitaire tentera de construire un tampon de sortie de données qui répond aux exigences pour que le bit UNMAP dans le cdb soit traité par le DEVICE.

Les blocs logiques peuvent également être non mappés par les commandes SCSI UNMAP et FORMAT UNIT (voir les utilitaires sg_unmap et sg_format).

La capacité de démappage dans SCSI est étroitement liée à la commande ATA DATA SET MANAGEMENT avec le bit "Trim" défini. Cette capacité de trim ATA n'interagit pas bien avec la mise en file d'attente des commandes SATA connue sous le nom de NCQ. T13 a introduit une nouvelle commande appelée SFQ DATA SET MANAGEMENT avec également un bit "Trim" pour résoudre ce problème. Les commandes SCSI WRITE SAME avec le bit UNMAP défini et les commandes UNMAP n'ont aucun problème avec la mise en file d'attente SCSI.

NOTES

Divers arguments numériques (par ex. LBA) peuvent inclure des suffixes multiplicatifs ou être donnés en hexadécimal. Voir la section "ARGUMENTS NUMÉRIQUES" dans la page de manuel sg3_utils(8).

Sous Linux, avant lk 3.17, le pilote sg ne prenait pas en charge les tailles de cdb supérieures à 16 octets. Par conséquent, un nœud de périphérique comme /dev/sg1 associé au pilote sg échouerait avec cet utilitaire si l'option --32 était donnée (ou implicite par d'autres options). Le pilote bsg avec des nœuds de périphérique comme /dev/bsg/6:0:0:1 prend en charge les tailles de cdb supérieures à 16 octets depuis son introduction dans lk 2.6.28.

STATUT DE SORTIE

Le statut de sortie de sg_write_same est 0 en cas de succès. Sinon, voir la page de manuel sg3_utils(8).

EXEMPLES

ATTENTION : tous ces exemples écraseront les données sur un ou plusieurs blocs, potentiellement en EFFACANT LE DISQUE ENTIER.

Une utilisation simple consiste à écrire des blocs de zéros à partir (et y compris) d'un LBA donné pour 63 blocs :


sg_write_same --lba=0x1234 --num=63 /dev/sdc

Comme --xferlen=LEN n'a pas été donné, cet utilitaire appellera la commande READ CAPACITY sur /dev/sdc pour déterminer le nombre d'octets dans un bloc logique. Supposons que ce soit 512 octets. Comme --in=IF n'est pas donné, un bloc de zéros est supposé. Donc 63 blocs de zéros (chacun contenant 512 octets) seront écrits à partir (et y compris) du LBA 0x1234. Notez qu'un seul bloc de zéros est passé à la commande SCSI WRITE SAME dans le tampon de sortie de données (comme requis par SBC-3). L'utilisation de la commande SCSI WRITE SAME pour écrire un ou plusieurs blocs de zéros est équivalente à la commande NVMe : Write Zeroes.
Maintenant, nous allons écrire des blocs de zéros sur le disque ENTIER. [Note : les commandes de type 'sanitize' effacent également des blocs et des métadonnées qui ne sont pas directement visibles] :


sg_write_same --lba=0x0 --num=0 /dev/sdc

Oui, dans ce contexte, --num=0 signifie le reste du disque. L'invocation ci-dessus peut donner une erreur car le bit WSNZ dans la page VPD Block Limits est défini. Pour contourner cela, essayez :


sg_write_same --lba=0x0 --ndob /dev/sdc

Cette invocation, si elle est prise en charge, a l'avantage supplémentaire de ne pas envoyer de tampon de sortie de données de zéros. Notez qu'il est possible que le "modèle d'initialisation de provisionnement" soit écrit dans chaque bloc au lieu de zéros.

Un exemple similaire suit, mais dans ce cas, les blocs sont "non mappés" ("trimés" dans le jargon ATA) plutôt que zéroés :


sg_write_same --unmap -L 0x1234 -n 63 /dev/sdc

Notez que si le bit LBPRZ dans la réponse READ CAPACITY(16) est défini (c'est-à-dire que LPPRZ est un acronyme pour logical block provisioning read zeros), alors ces deux exemples font la même chose, du moins du point de vue des lectures ultérieures.

Cet utilitaire peut également être utilisé pour écrire des informations de protection (PI) sur des disques formatés avec un type de protection supérieur à zéro. PI est 8 octets de données supplémentaires ajoutées aux données utilisateur d'un bloc logique : les deux premiers octets sont une CRC (le "guard"), les deux octets suivants sont le "application tag" et les quatre derniers octets sont le "reference tag". Avec les types de protection 1 et 2, si le application tag est 0xffff, le guard ne doit pas être vérifié (par rapport aux données utilisateur).

Dans cet exemple, nous supposons que la taille du bloc logique (des données utilisateur) est de 512 octets et que le disque a été formaté avec le type de protection 1. Puisque nous allons modifier le LBA 2468, nous en prenons d'abord une copie :


dd if=/dev/sdb skip=2468 bs=512 of=2468.bin count=1

La commande suivante définit les données utilisateur sur des zéros et le PI sur 8 octets 0xFF sur le LBA 2468 :


sg_write_same --lba=2468 /dev/sdb

Lire ce bloc devrait réussir car le application tag est 0xffff, ce qui supprime la vérification du guard (CRC) (qui serait sinon incorrecte) :


dd if=/dev/sdb skip=2468 bs=512 of=/dev/null count=1

Maintenant, une tentative est faite pour créer un fichier binaire avec des zéros dans les données utilisateur, 0x0000 dans le application tag et des octets 0xff dans les deux autres champs PI. Il est difficile de créer des octets 0xff dans un fichier (sous Unix), comme le montre la commande "tr" ci-dessous :
dd if=/dev/zero bs=1 count=512 of=ud.bin
tr "\000" "\377" < /dev/zero | dd bs=1 of=ff_s.bin count=8
cat ud.bin ff_s.bin > lb.bin
dd if=/dev/zero bs=1 count=2 seek=514 conv=notrunc of=lb.bin

Le fichier résultant peut être visualisé avec 'hexdump -C lb.bin' et devrait contenir 520 octets. Ce fichier peut maintenant être écrit sur le LBA 2468 comme suit :


sg_write_same --lba=2468 wrprotect=3 --in=lb.bin /dev/sdb

Notez le --wrprotect=3 au lieu d'être défini sur 1, car nous voulons que la commande WRITE SAME réussisse même si les données PI indiquent maintenant que les données utilisateur sont corrompues. Lors d'une tentative de lecture du LBA, une erreur devrait se produire :


dd if=/dev/sdb skip=2468 bs=512 of=/dev/null count=1

Les erreurs dd ne sont pas très expressives ; si dmesg est vérifié, il devrait y avoir une ligne du genre : "[sdb] Add. Sense: Logical block guard check failed". Le bloc peut être corrigé en faisant à nouveau un "sg_write_same --lba=1234 /dev/sdb" ou en restaurant le contenu original de ce LBA :


dd if=2468.bin bs=512 seek=2468 of=/dev/sdb conv=notrunc count=1

On espère que la commande dd n'essaiera jamais de tronquer le fichier de sortie lorsqu'il s'agit d'un périphérique bloc.
