NOM

sg_raw - envoie une commande SCSI ou NVMe arbitraire à un périphérique

SYNTAXE

sg_raw [--binaire] [--fichier-cmd=FC] [--set-cmd=SC] [--lister] [--aide] [--fichier-entree=FICHIER_E] [--pas-de-sens] [--nvm] [--fichier-sortie=FICHIER_S] [--brut] [--lecture-seule] [--longueur-requete=LR] [--balayer=DE,A] [--envoyer=LEN] [--sauter=KS] [--timeout=SECS] [--verbeux] [--version] PERIPHERIQUE [CDB0 CDB1 ...]

DESCRIPTION

Cet utilitaire envoie une commande SCSI arbitraire (entre 6 et 256 octets) au PERIPHERIQUE. Il peut ne pas y avoir de transfert de données associé ; ou des données peuvent être lues à partir d'un fichier et envoyées au PERIPHERIQUE ; ou des données peuvent être reçues du PERIPHERIQUE puis affichées ou écrites dans un fichier. Si pris en charge par le passage, des commandes bidirectionnelles peuvent être envoyées (c'est-à-dire contenant à la fois des données à envoyer au PERIPHERIQUE et à recevoir du PERIPHERIQUE).

La commande SCSI peut être longue de 6 à 256 octets. Chaque octet de commande est spécifié au format hexadécimal brut (00..FF) sans préfixe ni suffixe. La commande peut être fournie soit sur la ligne de commande, soit via l'option --fichier-cmd=FC. Voir la section EXEMPLES ci-dessous.

Les commandes passent par une interface SCSI générique qui est implémentée pour plusieurs systèmes d'exploitation, notamment Linux, FreeBSD et Windows.

Un support expérimental a été ajouté pour envoyer des commandes NVMe Admin et NVM au PERIPHERIQUE. Comme toutes les commandes NVMe font 64 octets, il est plus pratique d'utiliser l'option --fichier-cmd=FC plutôt que de taper les 64 octets de la commande NVMe sur la ligne de commande. Voir la section sur NVME ci-dessous. Une heuristique basée sur la longueur de la commande est utilisée pour décider si la commande donnée est SCSI ou NVMe, pour outrepasser cette heuristique, utilisez l'option --set-cmd=SC.

OPTIONS

Les arguments des options longues sont obligatoires pour les options courtes également. Les options sont classées par ordre alphabétique basé sur le nom de l'option longue.

-b, --binaire
Affiche les données en format binaire, même lors de l'écriture sur stdout.
-c, --fichier-cmd=FC
FC est le nom d'un fichier contenant la commande à exécuter. Sans cette option, la commande doit être fournie sur la ligne de commande, après les options et le PERIPHERIQUE.
-C, --set-cmd=SC
SC est un nombre indiquant quel jeu de commandes (c'est-à-dire SCSI ou NVMe) utiliser. 0, par défaut, déclenche une heuristique basée sur la longueur de la commande. Utilisez un SC de 1 pour outrepasser cette heuristique et choisir le jeu de commandes SCSI. Utilisez un SC de 2 pour outrepasser cette heuristique et choisir le jeu de commandes NVMe.
-h, --aide
Affiche les informations d'utilisation et quitte.
-i, --fichier-entree=FICHIER_E
Lit les données binaires depuis FICHIER_E au lieu de stdin. Cette option est ignorée si --envoyer n'est pas spécifié. Ces données, si utilisées, deviendront le tampon de "data-out" de la commande.
-n, --pas-de-sens
N'affiche pas les informations SCSI Sense.
-N, --nvm
Lors de l'envoi de commandes NVMe, le jeu de commandes Admin est supposé. Pour envoyer le jeu de commandes NVM (par exemple les commandes Read et Write (données utilisateur)), cette option doit être fournie.
-o, --fichier-sortie=FICHIER_S
Écrit les données reçues du PERIPHERIQUE dans FICHIER_S. Ces données sont le tampon de "data-in" de la commande. Les données sont écrites en binaire. Par défaut, les données sont affichées en format hexadécimal sur stdout. Si FICHIER_S est '-' alors les données sont affichées en binaire sur stdout. Cette option est ignorée si --longueur-requete n'est pas spécifié.
-w, --brut
interprète FC (c'est-à-dire le fichier de commande) comme contenant du binaire. Par défaut, il est supposé qu'il contient de l'hexadécimal ASCII.
-R, --lecture-seule
Ouvre le PERIPHERIQUE en lecture seule. Par défaut (sans cette option), il est ouvert en lecture-écriture.
-r, --longueur-requete=LR
Attend de recevoir jusqu'à LR octets de données du PERIPHERIQUE. LR peut être suffixé par 'k' pour utiliser des kilo-octets (1024 octets) au lieu d'octets. LR est décimal sauf s'il a un préfixe '0x' ou un suffixe 'h'.
Si LR est trop petit (c'est-à-dire soit plus petit que celui indiqué par le cdb (généralement le champ "allocation length") et/ou plus petit que celui que le PERIPHERIQUE essaie de renvoyer) alors le pilote HBA peut se plaindre. Rendre LR plus grand que nécessaire ne devrait pas poser de problème. La plupart des commandes SCSI de "data-in" renvoient un bloc de données qui contient (dans ses premiers octets) une longueur que le PERIPHERIQUE "aimerait" renvoyer si le champ "allocation length" dans le cdb est suffisamment grand. En pratique, le PERIPHERIQUE ne renverra pas plus d'octets que ceux indiqués dans le champ "allocation length" du cdb.
-Q, --balayer=DE,A
Balaye une plage d'opcodes (c'est-à-dire le premier octet de chaque commande). Le premier opcode de la plage est DE (qui est décimal sauf s'il a un préfixe '0x' ou un suffixe 'h'). Le dernier opcode de la plage est A. La valeur maximale de A est 255. Les octets restants de la commande SCSI/NVMe sont ceux fournis lors de l'appel.
Attention : cette option peut être **dangereuse**. Envoyer des commandes quelque peu arbitraires à un périphérique peut avoir des résultats inattendus. Il est recommandé d'utiliser cette option avec l'option --set-cmd=SC où SC est 1 ou 2 afin d'arrêter le jeu de commandes qui pourrait changer pendant le balayage.
-s, --envoyer=LEN
Lit LEN octets de données, soit depuis stdin, soit depuis un fichier, et les envoie au PERIPHERIQUE. Dans le transport SCSI, LEN devient la longueur (en octets) du tampon "data-out". LEN est décimal sauf s'il a un préfixe '0x' ou un suffixe 'h'.
Il est de la responsabilité de l'utilisateur de s'assurer que la longueur "data-out" implicite ou spécifiée dans le cdb correspond à LEN. Notez que certaines commandes SCSI courantes comme WRITE(10) ont un champ "transfer length" dont les unités sont des blocs logiques (qui sont généralement de 512 ou 4096 octets).
-k, --sauter=KS
Saute les KS premiers octets du fichier ou du flux d'entrée. Cette option est ignorée si --envoyer n'est pas spécifié. Si --envoyer est donné et que cette option n'est pas donnée, alors zéro octet est sauté.
-t, --timeout=SECS
Attend jusqu'à SECS secondes pour l'achèvement de la commande (défaut : 20). Notez que si une commande expire, le système d'exploitation peut commencer par l'annuler et si cela échoue, il peut tenter de réinitialiser le périphérique. Une forme alternative d'option longue est --tmo=SECS.
-v, --verbeux
Augmente le niveau de verbosité. Peut être utilisé plusieurs fois.
-V, --version
Affiche la version et les informations de licence, puis quitte.

NOTES

L'utilitaire sg_inq peut être utilisé pour envoyer une commande INQUIRY à un périphérique afin de déterminer son type de périphérique périphérique (par exemple '1' pour un périphérique de streaming (lecteur de bande)) qui détermine quels jeux de commandes SCSI un périphérique doit prendre en charge (par exemple SPC et SSC). L'utilitaire sg_vpd lit et décode les Vital Product Pages d'un périphérique qui peuvent contenir des informations utiles.

La capacité d'envoyer des CDB de plus de 16 octets (dans certains cas 12 octets) peut être limitée par l'interface de passage, le pilote de bas niveau ou le transport. Dans les noyaux Linux série 3, le pilote bsg peut gérer des CDB plus longs, les périphériques de bloc (par exemple /dev/sdc) accédés via l'ioctl SG_IO ne peuvent pas gérer des CDB plus longs que 16 octets, et le pilote sg peut gérer des CDB plus longs à partir de lk 3.17.

sg_raw(8) — sg3_utils

NAME

sg_raw

send SCSI commands or NVMe commands

SYNOPSIS

sg_raw [--cmddepth=CD] [--cmdset=CS] [--ctl=CT] [--extended] [--force]
       [--inhex=IF] [--infile=IF] [--input=IF] [--mask=MS] [--nvm]
       [--num=NU] [--outfile=OF] [--outhex=OH] [--page=PG] [--raw] [--reader=RD]
       [--request=RQ] [--sense_len=SL] [--send=SD] [--send_len=SL]
       [--serial=SN] [--single_peer] [--size=SZ] [--src_file=SF] [--src_len=SL]
       [--verbose=VER] [--version] [--vpdfill] [--vwords=VW] [--writer=WR]
       DEVICE CDB...
sg_raw --help

DESCRIPTION

This utility, when given a device name and a SCSI command descriptor block (CDB), will send that CDB to the device. It is designed to be a simple utility to send arbitrary SCSI commands to devices. For common SCSI commands there are usually specific utilities (e.g. sg_inq(8) for SCSI INQUIRY commands).

The CDB is given as a sequence of hexadecimal bytes following the device name.

This utility can also send NVMe commands, but this is considered experimental and is less well tested than the SCSI support.

OPTIONS

--cmddepth=CD
Set CDB depth to CD. Default is 1.
--cmdset=CS
Set command set to CS. Default is 0 (SCSI). Valid values are 0 (SCSI) and 1 (NVMe).
--ctl=CT
Sets the ctl (control) byte of the SCSI CDB to CT (in hex).
--extended
Use extended CDB length reporting. Only applies to SCSI commands.
--force
Force the CDB length to be interpreted correctly even if it's larger than 32 bytes.
--inhex=IF
Read CDB from file IF, interpreting contents as hex bytes.
--infile=IF
Read CDB from file IF. If the file contains binary data then the length of the CDB is inferred from the file length. If the file contains ASCII hex digits then the CDB length is twice the file length.
--input=IF
Alias for --infile=IF.
--mask=MS
Mask the output buffer with MS (in hex) before returning.
--nvm
Send command using NVMe NVM command set. Default is Admin command set.
--num=NU
Number of CDBs to send. Default is 1.
--outfile=OF
Write data-in from device to file OF.
--outhex=OH
Write data-in from device to file OH, interpreting contents as hex bytes.
--page=PG
For SCSI CDBs, interpret the CDBs as being in page PG. Default is 0.
--raw
Read CDB from stdin as binary data.
--reader=RD
Read data-out from RD. RD can be a file name or a device name. This option is often used with the --send option.
--request=RQ
Request RQ bytes of data-in from the device. This option is often used with the --outfile option.
--sense_len=SL
Set the maximum sense data length to SL bytes. Default is 96.
--send=SD
Send SD bytes of data-out to the device. This option is often used with the --reader option.
--send_len=SL
Set the maximum data-out length to SL bytes. Default is 0.
--serial=SN
Set the serial number to SN. Only useful when sending commands to the device controller itself.
--single_peer
Use only one peer for sending/receiving data.
--size=SZ
Alias for --request=SZ.
--src_file=SF
Read data-out from file SF.
--src_len=SL
Send SL bytes of data-out from SF.
--verbose=VER
Set the verbosity level to VER. Default is 0.
--version
Print version string and exit.
--vpdfill
Fill missing Vital Product Data (VPD) pages with zeroes.
--vwords=VW
Set the number of words to read for Vital Product Data (VPD) pages.
--writer=WR
Write data-in to WR. WR can be a file name or a device name.

NOTES

The CDB is given as a sequence of hexadecimal bytes following the device name. For example: `sg_raw /dev/sg0 08 01 00 00 00 00` This sends the SCSI command `08 01 00 00 00 00` to the device `/dev/sg0`.

The length of the CDB is determined by the number of hex bytes provided on the command line. If the CDB is longer than 32 bytes, sg_raw will attempt to send it, but some operating system device drivers or SCSI transport drivers might have problems with this. The --force option can be used to help with this, but it does not guarantee success.

If data-out needs to be sent to the device (e.g. for a SCSI WRITE command) then the --send=SD option should be used, where SD is the number of bytes to send. The data itself can be provided via the --infile=IF or --reader=RD options.

If data-in is expected from the device (e.g. for a SCSI READ command) then the --request=RQ option should be used, where RQ is the number of bytes expected. The data received can be saved to a file using the --outfile=OF option.

The --scan=FO,LO option is intended to help find hidden or undocumented commands. It is used by iterating through command sets (FO) and opcode values (LO). The default ranges are 0-7 for command sets and 0-255 for opcodes. Be aware that using this option can produce a large number of commands and may be noisy as not all commands are valid or expected by the DEVICE since the CDB command name decoding is done before the DEVICE is checked.

The intention of the --scan=FO,LO option is to slightly simplify the process of finding hidden or undocumented commands. It should be used with care; for example checking for vendor specific SCSI commands: 'sg_raw --cmdset=1 --scan=0xc0,0xff /dev/sg1 0 0 0 0 0 0 0'.

NVME SUPPORT

Support for NVMe (a.k.a. NVM Express) is currently experimental. NVMe concepts map reasonably well to the SCSI architecture. A SCSI logical unit (LU) is similar to a NVMe namespace (although LUN 0 is very common in SCSI while namespace IDs start at 1). A SCSI target device is similar to a NVMe controller. SCSI commands vary from 6 to 260 bytes long (although SCSI command descriptor blocks (cdb_s) longer than 32 bytes are uncommon) while all NVMe commands are currently 64 bytes long. The SCSI architecture makes a clear distinction between an initiator (often called a HBA) and a target (device) while (at least on the PCIe transport) the NVMe controller plays both roles. This utility defaults to assuming the user provided 64 byte command belongs to NVMe's Admin command set. To issue commands from the "NVM" command set, the --nvm option must be given. Admin and NVM commands are sent to submission queue 0.

One significant difference is that SCSI uses a big endian representation for integers that are longer than 8 bits (i.e. longer than 1 byte) while NVMe uses a little endian representation (like most things that have originated from the Intel organisation). NVMe specifications talk about Words (16 bits), Double Words (32 bits) and sometimes Quad Words (64 bits) and has tighter alignment requirements than SCSI.

One difference that impacts this utility is that NVMe places pointers to host memory in its commands while SCSI leaves this detail to whichever transport it is using (e.g. SAS, iSCSI, SRP). Since this utility takes the command from the user (either on the command line or in a file named CF) but this utility allocates a data-in or data-out buffer as required, the user does not know in advance what the address of that buffer will be. Some special addresses have been introduced to help with this problem: the address 0xfffffffffffffffe is interpreted as "use the data-in buffer's address" while 0xfffffffffffffffd is interpreted as "use the data-out buffer's address". Since NVMe uses little endian notation then that first address appears in the NVMe command byte stream as "fe" followed by seven "ff"s. A similar arrangement is made for the length of that buffer (in bytes), but since that is a 32 byte quantity, the first 4 bytes (all "ff"s) are removed.

Several command file examples can be found in the inhex directory of this package's source tarball: nvme_identify_ctl.hex, nvme_dev_self_test.hex, nvme_read_ctl.hex and nvme_write_ctl.hex .

Beware: the NVMe standard often refers to some of its fields as "0's based". They are typically counts of something like the number of blocks to be read. For example in NVMe Read command, a "0's based" number of blocks field containing the value 3 means to read 4 blocks! No, this is not a joke.

EXAMPLES

These examples, apart from the last one, use Linux device names. For suitable device names in other supported Operating Systems see the sg3_utils(8) man page.

sg_raw /dev/scd0 1b 00 00 00 02 00
Eject the medium in CD drive /dev/scd0.
sg_raw -r 1k /dev/sg0 12 00 00 00 60 00
Perform an INQUIRY on /dev/sg0 and dump the response data (up to 1024 bytes) to stdout.
sg_raw -s 512 -i i512.bin /dev/sda 3b 02 00 00 00 00 00 02 00 00
Showing an example of writing 512 bytes to a sector on a disk is a little dangerous. Instead this example will read i512.bin (assumed to be 512 bytes long) and use the SCSI WRITE BUFFER command to send it to the "data" buffer (that is mode 2). This is a safe operation.
sg_raw -r 512 -o o512.bin /dev/sda 3c 02 00 00 00 00 00 02 00 00
This will use the SCSI READ BUFFER command to read 512 bytes from the "data" buffer (i.e. mode 2) then write it to the o512.bin file. When used in conjunction with the previous example, if both commands work then 'cmp i512.bin o512.bin' should show a match.
sg_raw --infile=urandom.bin --send=512 --request=512 --outfile=out.bin "/dev/bsg/7:0:0:0" 53 00 00 00 00 00 00 00 01 00
This is a bidirectional XDWRITEREAD(10) command being sent via a Linux bsg device. Note that data is being read from "urandom.bin" and sent to the device (data-out) while resulting data (data-in) is placed in the "out.bin" file. Also note the length of both is 512 bytes which corresponds to the transfer length of 1 (block) in the cdb (i.e. the second last byte). urandom.bin can be produced like this:
dd if=/dev/urandom bs=512 count=1 of=urandom.bin
sg_raw.exe PhysicalDrive1 a1 0c 0e 00 00 00 00 00 00 e0 00 00
This example is from Windows and shows a ATA STANDBY IMMEDIATE command being sent to PhysicalDrive1. That ATA command is contained within the SCSI ATA PASS-THROUGH(12) command (see the SAT or SAT-2 standard at https://www.t10.org). Notice that the STANDBY IMMEDIATE command does not send or receive any additional data, however if it fails sense data should be returned and displayed.
For NVME examples see the files in this package's inhex directory that
start with 'nvme_' such as inhex/nvme_identify_ctl.hex .

EXIT STATUS

The exit status of sg_raw is 0 when it is successful. Otherwise see the sg3_utils(8) man page.
