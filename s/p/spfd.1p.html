NOM

spfd - (Mail::SPF) - Démon simple à fork pour fournir des services de requête SPF

VERSION

version 3.20250505

SYNTAXE

spfd --port|-p port [--set-user|-u uid|nom_utilisateur] [--set-group|-g gid|nom_groupe] [OPTIONS]

spfd --socket|-s nom_fichier [--socket-user uid|nom_utilisateur] [--socket-group gid|nom_groupe] [--socket-perms perms_octales] [--set-user|-u uid|nom_utilisateur] [--set-group|-g gid|nom_groupe] [OPTIONS]

spfd --version|-V

spfd --help

DESCRIPTION

spfd est un serveur simple à fork pour les requêtes Sender Policy Framework (SPF). spfd reçoit et répond aux requêtes SPF sur un socket TCP/IP ou UNIX domain. Pour plus d'informations sur SPF, voir https://tools.ietf.org/html/rfc7208.

La forme --port écoute sur un socket TCP/IP sur le port spécifié. Le port par défaut est 5970.

La forme --socket écoute sur un socket UNIX domain qui est créé avec le nom_fichier spécifié. Le socket peut se voir attribuer une propriété utilisateur et groupe spécifique avec les options --socket-user et --socket-group, et des permissions de système de fichiers spécifiques avec l'option --socket-perms.

Généralement, spfd peut être configuré avec les options --set-user et --set-group pour abandonner les privilèges root et changer vers un autre utilisateur et groupe avant de commencer à écouter les requêtes.

L'option --version affiche les informations de version de spfd. L'option --help affiche les informations d'utilisation pour spfd.

OPTIONS

spfd accepte les OPTIONS suivantes :

--default-explanation chaine
--def-exp chaine
Utilise la chaine spécifiée comme explication par défaut si le domaine d'autorité ne spécifie pas sa propre chaîne d'explication.
--hostname nom_hote
Utilise nom_hote comme nom d'hôte du système local au lieu de le détecter automatiquement.
--debug
Affiche des informations de débogage sur le fonctionnement de spfd, les requêtes entrantes et les réponses envoyées.

REQUÊTE

Une requête consiste en une série de lignes délimitées par des caractères \x0A (LF) (ou ce que votre système considère comme une nouvelle ligne). Chaque ligne doit être de la forme option=valeur, où les options suivantes sont prises en charge :

versions
Une liste de numéros de version SPF séparés par des virgules pour les enregistrements SPF qui peuvent être utilisés. 1 signifie que les enregistrements "v=spf1" doivent être utilisés. 2 signifie que les enregistrements "spf2.0" doivent être utilisés. Par défaut, 1,2, c'est-à-dire qu'il utilise tous les enregistrements SPF disponibles. Les enregistrements de version supérieure sont préférés.
scope
La portée d'autorisation de l'identité qui doit être vérifiée. Par défaut, 'mfrom'. Les valeurs de portée suivantes sont prises en charge : 'helo', 'mfrom', 'pra'. Voir "new" dans Mail::SPF::Request pour plus d'informations.
identity
Requis. L'identité de l'expéditeur dont l'autorisation doit être vérifiée. Il s'agit d'un nom de domaine pour la portée "helo", et d'une adresse e-mail pour les portées "mfrom" et "pra".
ip_address
Requis pour les vérifications avec les portées "helo", "mfrom" et "pra". L'adresse IP de l'hôte revendiquant l'identité en cours de vérification. Peut être une adresse IPv4 ou IPv6. Une adresse IPv6 mappée IPv4 (par exemple, '::ffff:192.168.0.1') est traitée comme une adresse IPv4.
helo_identity
Le paramètre de transaction SMTP "HELO" dans le cas où l'identité principale est d'une portée autre que "helo". Cette identité est alors utilisée uniquement pour l'expansion des macros "%{h}" lors de l'évaluation de la politique de l'identité principale. Si elle n'est pas spécifiée avec une portée autre que "helo", elle vaut par défaut "unknown". Si l'identité principale est de la portée "helo", cette option n'est pas utilisée.

RÉPONSE

spfd répond aux requêtes SPF avec des séries de lignes similaires de la forme clé=valeur. Les clés de réponse les plus importantes sont :

result
Le code de résultat de la vérification SPF :
pass
L'adresse IP spécifiée est un expéditeur SMTP autorisé pour l'identité.
fail
L'adresse IP spécifiée n'est pas un expéditeur SMTP autorisé pour l'identité.
softfail
L'adresse IP spécifiée n'est pas un expéditeur SMTP autorisé pour l'identité, cependant le domaine d'autorité teste toujours sa politique SPF.
neutral
Le domaine d'autorité de l'identité ne fait aucune assertion sur le statut de l'adresse IP.
permerror
Une erreur permanente s'est produite lors de l'évaluation de la politique du domaine d'autorité (par exemple, une erreur de syntaxe dans l'enregistrement SPF). Une intervention manuelle est requise de la part du domaine d'autorité.
temperror
Une erreur temporaire s'est produite lors de l'évaluation de la politique du domaine d'autorité (par exemple, une erreur DNS). Réessayez plus tard.
none
Il n'y a pas de politique SPF applicable pour le domaine de l'identité.
local_explanation
Une explication générée localement du résultat SPF.
authority_explanation
L'explication du domaine d'autorité pour le résultat SPF. Sachez que le domaine d'autorité peut être une partie malveillante et donc l'explication de l'autorité ne doit pas être considérée comme une vérité absolue. Voir RFC 4408, 10.5, pour une discussion détaillée de ce problème.
received_spf_header
Un champ d'en-tête "Received-SPF" approprié pour le résultat SPF.
spf_record
L'enregistrement SPF du domaine d'autorité qui a été utilisé pour l'évaluation de la politique.

EXEMPLE

Un spfd en cours d'exécution pourrait être testé en utilisant l'utilitaire "netcat" comme ceci (les sauts de ligne sont ajoutés pour plus de clarté) :

$ echo -e "identity=user@example.com\nip_address=1.2.3.4\n" \
    | nc localhost 5970
result=fail
local_explanation=example.com: Sender is not authorized by default to use
    'user@example.com' in 'mfrom' identity (mechanism '-all' matched)
authority_explanation=Rejected by SPF record.
received_spf_header=Received-SPF: fail (example.com: Sender is not
    authorized by default to use 'user@example.com' in 'mfrom' identity
    (mechanism '-all' matched)) receiver=localhost; identity=mfrom;
    env

spfd(1p) — Arch manual pages

NAME

spfd — SPF daemon

VERSION

This man page documents version 2.000 of spfd.

SYNOPSIS

  spfd --config-file=/path/to/spfd.conf

DESCRIPTION

spfd is a daemon that performs SPF record lookups. It receives requests from other programs, performs the SPF checks, and returns the results.

OPTIONS

--config-file=/path/to/spfd.conf
Specifies the configuration file to use. If not provided, /etc/mail/spfd.conf is used.

REQUEST

spfd accepts requests in the following format:

  identity=type[:value],ip_address=address[,helo_identity=value][,scope=type]

Where:

type
The type of identity. Can be mfrom (MAIL FROM), helo (HELO identity), or ip (IP address).
value
The value of the identity. For mfrom, this is the sender email address. For helo, this is the HELO hostname.
address
The IP address of the connecting client.
scope
The scope of the check. Can be mfrom, helo, or both.

RESPONSE

spfd returns results in the following format:

  result=code,local_explanation=explanation,authority_explanation=explanation,spf_record=record,received_spf_header=header

Where:

code
The SPF result code (e.g., pass, fail, neutral, softfail, permerror, temperror).
explanation
An explanation of the result.
record
The SPF record that was evaluated.
header
The Received-SPF header that should be added to the email.

EXAMPLE

A sample request and response:

  Request: identity=mfrom:user@example.com,ip_address=1.2.3.4,helo_identity=mail.example.com
  Response: result=pass,local_explanation=Authentication successful,authority_explanation=None,spf_record=v=spf1 mx -all,received_spf_header=Received-SPF: pass (sender SPF authorized) client-ip=1.2.3.4; envelope-from="user@example.com";

A request with an empty MAIL FROM:

  identity=mfrom:postmaster@example.com,ip_address=1.2.3.4
  spf_record=v=spf1 mx -all

COMPATIBILITY

spfd has undergone the following interface changes compared to earlier versions:

2.000
  • A new preferred request style has been introduced. Instead of the old "sender" request option, which is specific to the "MAIL FROM" SMTP identity, a generic "identity" option should now be specified. In addition, a "scope" option may be given to specify the identity's scope, otherwise a scope of "mfrom" is assumed. The old "ip" and "helo" options have been replaced by the "ip_address" and "helo_identity" options, respectively.

    This is how legacy requests with the "mfrom" scope would translate to the new preferred request style:

     Legacy request style       | New request style
----------------------------+---------------------------------------
                            | scope=mfrom
 sender=<mfrom-identity>    | identity=<mfrom-identity>
 ip=<ip-address>            | ip_address=<ip-address>
 helo=<helo-identity>       | helo_identity=<helo-identity>

    A new response style featuring new response values has also been introduced:

     Legacy response style      | New response style
----------------------------+---------------------------------------
 result=<result-code>       | result=<result-code>
 header_comment=<local-exp> | local_explanation=<local-exp>
 smtp_comment=<local-exp    | authority_explanation=<authority-exp>
   or authority-exp>        | 
 spf_record=<spf-record>    | spf_record=<spf-record>
                            | received_spf_header=<header>

    The legacy request style is deprecated but still supported for backwards compatibility. The legacy response values are still returned for backwards compatibility in addition to the new response values, but may be removed in the future. Adjust your code to use the new request and response styles.

  • The former "unknown" and "error" result codes have been renamed to "permerror" and "temperror", respectively, in order to comply with RFC 4408 terminology.
  • In the case of an empty "MAIL FROM" SMTP transaction parameter ("MAIL FROM:<>"), the identity checked will be postmaster@helo name as specified in RFC 7208.
