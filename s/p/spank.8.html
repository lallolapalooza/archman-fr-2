SPANK(8) Composant Slurm SPANK(8)

NOM

SPANK - Architecture de plug-ins Slurm pour le contrôle des nœuds et des tâches (K)ontrol

DESCRIPTION

Ce manuel décrit brièvement les capacités de l'Architecture de plug-ins Slurm pour le contrôle des nœuds et des tâches (SPANK) ainsi que le fichier de configuration SPANK : (Par défaut : plugstack.conf.)

SPANK fournit une interface très générique pour des plug-ins empilables qui peuvent être utilisés pour modifier dynamiquement le code de lancement des tâches dans Slurm. Les plug-ins SPANK peuvent être compilés sans accès au code source de Slurm. Ils ont seulement besoin d'être compilés contre le fichier d'en-tête spank.h de Slurm, ajoutés au fichier de configuration SPANK plugstack.conf, et ils seront chargés à l'exécution lors du prochain lancement de tâche. Ainsi, l'infrastructure SPANK offre aux administrateurs et autres développeurs une capacité à faible coût et faible effort pour modifier dynamiquement le comportement d'exécution du lancement des tâches Slurm.

NOTE : Tous les plug-ins SPANK doivent être recompilés lors de la mise à niveau de Slurm vers une nouvelle version majeure. L'API SPANK n'est pas garantie d'être compatible ABI entre les versions majeures. Tout plug-in SPANK se liant à l'une des bibliothèques Slurm doit être soigneusement vérifié car les API et les en-têtes Slurm peuvent changer entre les versions majeures.

PLUGINS SPANK

Les plug-ins SPANK sont chargés dans jusqu'à cinq contextes distincts lors d'une tâche Slurm. Brièvement, les cinq contextes sont :

local
Dans le contexte local, le plug-in est chargé par srun. (c.-à-d. la partie "locale" d'une tâche parallèle).
remote
Dans le contexte remote, le plug-in est chargé par slurmstepd. (c.-à-d. la partie "distante" d'une tâche parallèle).
allocator
Dans le contexte allocator, le plug-in est chargé dans l'un des utilitaires d'allocation de tâches salloc, sbatch ou scrontab.
slurmd
Dans le contexte slurmd, le plug-in est chargé dans le démon slurmd lui-même. NOTE : Les plug-ins chargés dans le contexte slurmd persistent pendant toute la durée d'exécution de slurmd, donc si la configuration est modifiée ou si les plug-ins sont mis à jour, slurmd doit être redémarré pour que les changements prennent effet.
job_script
Dans le contexte job_script, les plug-ins sont chargés dans le contexte du prolog ou de l'epilog de la tâche. NOTE : Les plug-ins sont chargés dans le contexte job_script à chaque exécution du prolog ou de l'epilog de la tâche, dans un espace d'adressage séparé de celui des plug-ins dans le contexte slurmd. Cela signifie qu'il n'y a pas d'état partagé entre ce contexte et les autres contextes, ni même entre un appel à slurm_spank_job_prolog ou slurm_spank_job_epilog et les appels ultérieurs.

En contexte local, seules les fonctions init, exit, init_post_opt et local_user_init sont appelées. En contexte allocateur, seules les fonctions init, exit et init_post_opt sont appelées. De même, en contexte slurmd, seules les appels de fonction init et slurmd_exit sont actifs, et en contexte job_script, seuls les appels de fonction job_prolog et job_epilog sont utilisés. Les plug-ins peuvent interroger le contexte dans lequel ils s'exécutent avec les fonctions spank_context et spank_remote définies dans spank.h.

Les plug-ins SPANK peuvent être appelés à plusieurs points pendant le lancement des tâches Slurm. Un plug-in peut définir les fonctions suivantes :

slurm_spank_init
Appelée juste après le chargement des plug-ins. En contexte distant, ceci se produit juste après l'initialisation de la tâche. Cette fonction est appelée avant le traitement de toute option du plug-in.
slurm_spank_job_prolog
Appelée en même temps que le prolog de la tâche. Si cette fonction retourne une valeur non nulle et que le plug-in SPANK qui la contient est requis dans plugstack.conf, le nœud sur lequel elle s'exécute sera mis en drain.
slurm_spank_init_post_opt
Appelée au même moment que slurm_spank_init, mais après que toutes les options utilisateur du plug-in aient été traitées. La raison pour laquelle les appels de fonction init et init_post_opt sont séparés est afin que les plug-ins puissent traiter les options globales du système spécifiées dans plugstack.conf dans l'appel de fonction init, puis traiter les options utilisateur, et enfin prendre une action dans slurm_spank_init_post_opt si nécessaire. Dans le cas d'une tâche hétérogène, slurm_spank_init est invoqué une fois par composant de tâche.
slurm_spank_local_user_init
Appelée en contexte local (srun) uniquement après que toutes les options aient été traitées. Ceci est appelé après que les identifiants de tâche et de pas soient disponibles. Cela se produit dans srun après que l'allocation soit faite, mais avant que les tâches ne soient lancées.
slurm_spank_user_init
Appelée après que les privilèges aient été temporairement abandonnés. (contexte distant seulement)
slurm_spank_task_init_privileged
Appelée pour chaque tâche juste après le fork, mais avant que tous les privilèges élevés ne soient abandonnés. Ceci peut s'exécuter en parallèle avec slurm_spank_task_post_fork. (contexte distant seulement)
slurm_spank_task_init
Appelée pour chaque tâche juste avant execve (2). Si vous limitez la mémoire avec les cgroups, la mémoire allouée ici sera dans le cgroup de la tâche. (contexte distant seulement)
slurm_spank_task_post_fork
Appelée pour chaque tâche depuis le processus parent après la fin du fork (2). En raison du fait que slurmd n'exécute aucune tâche avant que toutes les tâches aient terminé le fork (2), cet appel est garanti de s'exécuter avant que la tâche utilisateur ne soit exécutée. Ceci peut s'exécuter en parallèle avec slurm_spank_task_init_privileged. (contexte distant seulement)
slurm_spank_task_exit
Appelée pour chaque tâche lorsque son statut de sortie est collecté par Slurm. (contexte distant seulement)
slurm_spank_exit
Appelée une fois juste avant que slurmstepd ne quitte en contexte distant. En contexte local, appelée avant que srun ne quitte.
slurm_spank_job_epilog
Appelée en même temps que l'epilog de la tâche. Si cette fonction retourne une valeur non nulle et que le plug-in SPANK qui la contient est requis dans plugstack.conf, le nœud sur lequel elle s'exécute sera mis en drain.
slurm_spank_slurmd_exit
Appelée dans slurmd lorsque le démon est arrêté.

Toutes ces fonctions ont le même prototype, par exemple :

   int slurm_s

pank_init (spank_t spank, int ac, char *argv[])

Où spank est le handle SPANK qui doit être renvoyé à Slurm lorsque le plugin appelle des fonctions comme spank_get_item et spank_getenv. Les arguments configurés (Voir CONFIGURATION ci-dessous) sont passés dans le vecteur d'arguments argv avec le compteur d'arguments ac.

Un plugin peut également définir les variables suivantes qui seront utilisées par Slurm :

slurm_spank_init_failure_mode
Lorsqu'un appel à slurm_spank_init échoue, modifie la façon dont cet échec est géré par Slurm. Les valeurs reconnues sont :
ESPANK_NODE_FAILURE
Slurm considère que le nœud est en faute et le marque comme vidangé. Le travail peut être remis en file d'attente. C'est le comportement par défaut.
ESPANK_JOB_FAILURE
Slurm considère que le travail est en faute et le marque comme échoué (ne devant pas être remis en file d'attente). Le nœud ne sera pas vidangé.

Les plugins SPANK peuvent interroger la liste actuelle des symboles slurm_spank pris en charge pour déterminer si la version actuelle prend en charge un crochet de plugin donné. Cela peut être utile car la liste des symboles de plugin peut croître à l'avenir. L'interrogation se fait à l'aide de la fonction spank_symbol_supported, dont le prototype est le suivant :

    int spank_symbol_supported (const char *sym);

La valeur de retour est 1 si le symbole est pris en charge, 0 sinon.

Les plugins SPANK n'ont pas d'accès direct aux structures de données internes de Slurm. Au lieu de cela, les informations sur le travail en cours d'exécution sont obtenues via l'appel de fonction spank_get_item.

  spank_err_t spank_get_item (spank_t spank, spank_item_t item, ...);

L'appel spank_get_item doit recevoir le handle SPANK actuel ainsi que l'élément demandé, défini par le spank_item_t passé. Un nombre variable d'arguments pointeurs sont également passés, en fonction de l'élément demandé par le plugin. Une liste des valeurs valides pour item est conservée dans le fichier d'en-tête spank.h. Quelques exemples sont :

S_JOB_UID
ID utilisateur du travail en cours d'exécution. (uid_t *) est le troisième argument de spank_get_item
S_JOB_STEPID
ID de l'étape du travail en cours d'exécution. (uint32_t *) est le troisième argument de spank_get_item.
S_TASK_EXIT_STATUS
Statut de sortie de la tâche terminée. Valide uniquement à partir de slurm_spank_task_exit. (int *) est le troisième argument de spank_get_item.
S_JOB_ARGV
Ligne de commande complète du travail. Les troisième et quatrième arguments de spank_get_item sont (int *, char ***).

Voir spank.h pour plus de détails.

Les plugins SPANK dans l'environnement local et allocator doivent utiliser les fonctions getenv, setenv, et unsetenv pour consulter et modifier l'environnement du travail. Les plugins SPANK dans l'environnement remote doivent utiliser les fonctions spank_getenv, spank_setenv, et spank_unsetenv pour consulter et modifier l'environnement du travail. spank_getenv recherche dans l'environnement du travail la variable d'environnement var et copie la valeur actuelle dans un tampon buf de longueur len. spank_setenv permet à un plugin SPANK de définir ou écraser une variable dans l'environnement du travail, et spank_unsetenv supprime une variable d'environnement de l'environnement du travail. Les prototypes sont :

 spank_err_t spank_getenv (spank_t spank, const char *var,
		           char *buf, int len);
 spank_err_t spank_setenv (spank_t spank, const char *var,
		           const char *val, int overwrite);
 spank_err_t spank_unsetenv (spank_t spank, const char *var);

Ceci n'est nécessaire que dans un contexte distant car les modifications de l'environnement de processus standard à l'aide de setenv(3), getenv(3), et unsetenv(3) peuvent être utilisées dans un contexte local.

Des fonctions sont également disponibles depuis les plugins SPANK pour établir des variables d'environnement qui seront exportées vers les programmes PrologSlurmctld, Prolog, Epilog et EpilogSlurmctld de Slurm (le soi-disant environnement de contrôle des travaux). Le nom des variables d'environnement établies par ces appels sera précédé de la chaîne SPANK_ afin d'éviter toute implication de sécurité liée au contrôle arbitraire des variables d'environnement. (Après tout, les scripts de contrôle des travaux s'exécutent en tant que root ou utilisateur Slurm.).

Ces fonctions ne sont disponibles que dans le contexte local.

  spank_err_t spank_job_control_getenv(spank_t spank, const char *var,
		             char *buf, int len);
  spank_err_t spank_job_control_setenv(spank_t spank, const char *var,
		             const char *val, int overwrite);
  spank_err_t spank_job_control_unsetenv(spank_t spank, const char *var);

Voir spank.h pour plus d'informations.

Beaucoup des fonctions SPANK décrites disponibles pour les plugins renvoient des erreurs via le type d'erreur spank_err_t. En cas de succès, la valeur de retour sera définie sur ESPANK_SUCCESS, tandis qu'en cas d'échec, la valeur de retour sera définie sur l'une des nombreuses valeurs d'erreur définies dans spank.h. L'interface SPANK fournit une fonction simple

  const char * spank_strerror(spank_err_t err);
qui peut être utilisée pour traduire une valeur spank_err_t en sa représentation sous forme de chaîne de caractères.

La fonction slurm_spank_log peut être utilisée pour afficher des messages à l'utilisateur à un niveau d'erreur. Cela évite aux utilisateurs de devoir s'appuyer sur la fonction slurm_error, qui peut être déroutante car elle ajoute "&#34;error:&#34;" à chaque message.

OPTIONS SPANK

Les plugins SPANK ont également une interface par laquelle ils peuvent définir et implémenter des options de travail supplémentaires. Ces options sont mises à la disposition de l'utilisateur via les commandes Slurm telles que srun(1), salloc(1), et sbatch(1). Si l'option est spécifiée par l'utilisateur, sa valeur est transmise et enregistrée auprès du plugin dans slurmd lorsque le travail est exécuté. De cette manière, les plugins SPANK peuvent dynamiquement fournir de nouvelles options et fonctionnalités à Slurm.

Chaque option enregistrée par un plugin auprès de Slurm prend la forme d'une struct spank_option déclarée dans spank.h comme suit :

   struct spank_option {
      char *         name;
      char *         arginfo;
      char *         usage;
      int            has_arg;
      int            val;
      spank_opt_cb_f cb;
   };

Où

name
est le nom de l'option. Sa longueur est limitée à SPANK_OPTION_MAXLEN défini dans spank.h.
arginfo
est une description de l'argument de l'option, si l'option prend un argument.
usage
est une brève description de l'option appropriée pour la sortie --help.
has_arg
0 si l'option ne prend pas d'argument, 1 si l'option prend un argument, et 2 si l'option prend un argument optionnel. (Voir getopt_long(3)).
val
Une valeur locale au plugin à renvoyer à la fonction de rappel de l'option.
cb
Une fonction de rappel qui est appelée lorsque l'option du plugin est enregistrée auprès de Slurm. spank_opt_cb_f est un typedef dans spank.h comme suit :
  typedef int (*spank_opt_cb_f) (int val, const char *optarg,
		                 int remote);
Où val est la valeur du champ val dans la structure spank_option, optarg est l'argument fourni le cas échéant, et remote est 0 si la fonction est appelée depuis l'hôte "local" (par exemple, l'hôte où srun ou sbatch/salloc sont invoqués) ou 1 depuis l'hôte "distant" (hôte où slurmd/slurmstepd s'exécutent) mais exécuté uniquement par slurmstepd (contexte distant) si l'option a été enregistrée pour un tel contexte.

Les options de plugin peuvent être enregistrées auprès de Slurm en utilisant la fonction spank_option_register. Cette fonction n'est valide que lorsqu'elle est appelée depuis le gestionnaire slurm_spank_init du plugin, et enregistre une option à la fois. Le prototype est :

   spank_err_t spank_option_register (spank_t sp,
		   struct spank_option *opt);
Cette fonction renverra ESPANK_SUCCESS en cas d'enregistrement réussi d'une option, ou ESPANK_BAD_ARG en cas d'erreurs, y compris un handle spank_t invalide, ou lorsque la fonction n'est pas appelée depuis la fonction slurm_spank_init. Toutes les options doivent être enregistrées depuis tous les contextes dans lesquels elles seront utilisées. Par exemple, si une option n'est utilisée que dans les contextes local (srun) et distant (slurmd), alors spank_option_register ne devrait être appelée que dans ces contextes. Par exemple : 
   if (spank_context() != S_CTX_ALLOCATOR)
      spank_option_register (sp, opt);
Si, cependant, l'option est utilisée dans tous les contextes, spank_option_register doit être appelée partout.

En plus de spank_option_register, les plugins peuvent également exporter des options vers Slurm en définissant une table de struct spank_option avec le nom de symbole spank_options. Cette méthode n'est cependant pas prise en charge pour une utilisation avec sbatch et salloc (contexte de l'allocateur), par conséquent l'utilisation de spank_option_register est préférée. Lors de l'utilisation de la table spank_options, le dernier élément du tableau doit être rempli de zéros. Un SPANK_OPTIONS

Options

Le macro Slurm_spank_option_register est fournie dans spank.h dans ce but.

Lorsqu'une option est fournie par l'utilisateur du côté local, que ce soit par des options de ligne de commande ou par des variables d'environnement, Slurm invoquera immédiatement la fonction de rappel de l'option avec remote=0. Ceci est destiné au plug-in pour effectuer une vérification locale de l'option avant que la valeur ne soit envoyée au côté distant lors du lancement du travail. Si l'argument spécifié par l'utilisateur est invalide, le plug-in doit émettre une erreur et retourner un code de retour non nul à partir de la fonction de rappel. Le plug-in doit pouvoir gérer les cas où l'option spank est définie plusieurs fois par le biais de variables d'environnement et d'options de ligne de commande. Les variables d'environnement sont traitées avant les options de ligne de commande.

Du côté distant, les options et leurs arguments sont enregistrés juste après le chargement des plug-ins SPANK et avant l'appel du gestionnaire spank_init. Cela permet aux plug-ins de modifier le comportement de toutes les fonctionnalités des plug-ins en fonction de la valeur des options fournies par l'utilisateur.

En alternative à l'utilisation d'une fonction de rappel d'option et d'une variable globale, les plug-ins peuvent utiliser l'option spank_option_getopt pour vérifier les options fournies après le traitement des options. Cette fonction a le prototype suivant :

   spank_err_t spank_option_getopt(spank_t sp,
       struct spank_option *opt, char **optargp);
Cette fonction retourne ESPANK_SUCCESS si l'option définie dans la structure spank_option opt a été utilisée par l'utilisateur. Si optargp n'est pas NULL, il est défini sur l'argument d'option passé (si l'option prend un argument). L'utilisation de cette méthode est requise pour traiter les options dans le contexte job_script (slurm_spank_job_prolog et slurm_spank_job_epilog). Cette fonction est valide dans les contextes suivants : slurm_spank_job_prolog, slurm_spank_local_user_init, slurm_spank_user_init, slurm_spank_task_init_privileged, slurm_spank_task_init, slurm_spank_task_exit, et slurm_spank_job_epilog.

CONFIGURATION

Le fichier de configuration par défaut pour la pile de plug-ins SPANK est plugstack.conf dans le même répertoire que slurm.conf(5), bien que cela puisse être modifié via le paramètre de configuration Slurm PlugStackConfig. Normalement, le fichier plugstack.conf doit être identique sur tous les nœuds du cluster. Le fichier de configuration liste les plug-ins SPANK, un par ligne, ainsi que si le plug-in est requis ou optionnel, et tous les arguments globaux qui doivent être passés au plug-in pour la configuration à l'exécution. Les commentaires sont précédés de '#' et s'étendent jusqu'à la fin de la ligne. Si le fichier de configuration est manquant ou vide, il sera simplement ignoré.

NOTE : Les plug-ins SPANK doivent être installés sur les machines qui exécutent slurmd (nœuds de calcul) ainsi que sur les machines qui exécutent les utilitaires d'allocation de travaux tels que salloc, sbatch, etc. (nœuds de connexion).

Le format de chaque ligne non commentée dans le fichier de configuration est le suivant : 

  required/optional   plugin   arguments
Par exemple : 
  optional /usr/lib/slurm/test.so
Indique à slurmd de charger le plug-in test.so sans passer d'arguments. Si un plug-in SPANK est requis, alors l'échec de l'une des fonctions du plug-in entraînera la terminaison du travail par slurmd ou par la commande d'allocation, tandis que les plug-ins optionnels ne provoqueront qu'un avertissement.

Si un chemin entièrement qualifié n'est pas spécifié pour un plug-in, alors le répertoire PluginDir actuellement configuré dans slurm.conf(5) est recherché.

Les plug-ins SPANK sont empilables, ce qui signifie que plus d'un plug-in peut être placé dans le fichier de configuration. Les plug-ins seront simplement appelés dans l'ordre, l'un après l'autre, et l'action appropriée sera entreprise en cas d'échec, compte tenu de l'état du drapeau optional du plug-in.

Des fichiers de configuration supplémentaires ou des répertoires de fichiers de configuration peuvent être inclus dans plugstack.conf avec le mot-clé include. Le mot-clé include doit apparaître sur sa propre ligne et prend un glob comme paramètre, de sorte que plusieurs fichiers puissent être inclus sur une seule ligne include. Par exemple, la syntaxe suivante chargera tous les fichiers de configuration du répertoire /etc/slurm/plugstack.conf.d, dans l'ordre de collation locale :

  include /etc/slurm/plugstack.conf.d/*
ce qui pourrait être considéré comme une méthode plus flexible pour construire une pile de plug-ins spank.

Le fichier de configuration SPANK est relu à chaque lancement de travail, donc la modification du fichier de configuration n'affectera pas les travaux en cours. Cependant, il convient de veiller à ce qu'un fichier de configuration partiellement modifié ne soit pas lu par un travail en cours de lancement.

spank(8) - Slurm component

NAME

spank - Slurm Plug-in API for parallel application

DESCRIPTION

SPANK is an API that provides support for developing and loading plug-ins into the Slurm daemons and commands. SPANK plug-ins can be loaded dynamically by the Slurm daemons and commands and can hook into various points in the Slurm execution flow.

This man page provides an overview of the SPANK API and its associated components.

SPANK PLUGINS

SPANK plug-ins are shared libraries that implement functions defined by the SPANK API. These functions are called by Slurm components at specific points in their execution flow.

The following functions are exported by SPANK plug-ins:

  • slurm_spank_init: Called when the plug-in is loaded. Used for initialization.
  • slurm_spank_fini: Called when the plug-in is unloaded. Used for cleanup.
  • slurm_spank_job_submit: Called when a job is submitted.
  • slurm_spank_job_modify: Called when a job is modified.
  • slurm_spank_job_cancel: Called when a job is cancelled.
  • slurm_spank_task_init: Called when a task is launched.
  • slurm_spank_task_exit: Called when a task exits.
  • slurm_spank_register_callbacks: Called to register callback functions.
  • slurm_spank_select_job_g_step: Called during job step selection.
  • slurm_spank_node_complete: Called when a node completes its tasks.
  • slurm_spank_notify: Called for various notifications.
  • slurm_spank_thread_init: Called when a new thread is created.
  • slurm_spank_thread_exit: Called when a thread exits.
  • slurm_spank_task_post_fork: Called after a task forks.
  • slurm_spank_exit: Called before the Slurm component exits.

The specific functions called and their arguments depend on the context in which the plug-in is loaded (e.g., `sbatch`, `srun`, `slurmctld`, `slurmd`).

SPANK OPTIONS

SPANK plug-ins can be configured with options that are passed to them when they are loaded. These options are specified in the `plugstack.conf` file or on the command line.

The following table lists some common SPANK plug-ins and their associated functions and contexts:

Command SPANK Function Context Priority External Internal
sbatch slurm_spank_init allocator 1 yes yes
sbatch slurm_spank_task_init remote 1 no yes
sbatch slurm_spank_task_exit remote 0 no no
sbatch slurm_spank_exit allocator 0 no no
scrontab slurm_spank_init allocator 1 no no
scrontab slurm_spank_exit allocator 0 no no

NOTE: The behavior for ProctrackType=proctrack/pgid may result in timeouts for slurm_spank_task_post_fork with remote context on failure.

CONFIGURATION

SPANK plug-ins are configured using the `plugstack.conf` file. This file specifies which plug-ins to load, in what order, and with what options.

The format of `plugstack.conf` is as follows:

PluginName [options]

For example:

libjob.so foo=bar baz=1

This command loads the `libjob.so` plug-in with options `foo=bar` and `baz=1`.

The `plugstack.conf` file can be placed in several locations, including `/etc/slurm/plugstack.conf` and `/etc/slurm-llnl/plugstack.conf`.

Errors

SPANK plug-ins can return error codes to indicate success or failure. Slurm components can check these return codes to determine whether to proceed or to take corrective action.
