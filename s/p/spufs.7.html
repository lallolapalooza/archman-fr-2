NOM

spufs - Système de fichiers SPU

DESCRIPTION

Le système de fichiers SPU est utilisé sur les machines PowerPC qui implémentent l'architecture Cell Broadband Engine afin d'accéder aux unités de traitement Synergistic (SPU).

Le système de fichiers fournit un espace de noms similaire à la mémoire partagée POSIX ou aux files de messages. Les utilisateurs ayant des permissions d'écriture sur le système de fichiers peuvent utiliser spu_create(2) pour établir des contextes SPU sous le répertoire racine de spufs.

Chaque contexte SPU est représenté par un répertoire contenant un ensemble prédéfini de fichiers. Ces fichiers peuvent être utilisés pour manipuler l'état du SPU logique. Les utilisateurs peuvent modifier les permissions sur les fichiers, mais ne peuvent pas ajouter ou supprimer de fichiers.

Options de montage

uid=<uid>
Définit l'utilisateur propriétaire du point de montage ; la valeur par défaut est 0 (root).
gid=<gid>
Définit le groupe propriétaire du point de montage ; la valeur par défaut est 0 (root).
mode=<mode>
Définit le mode du répertoire de niveau supérieur dans spufs, sous forme de chaîne octale. La valeur par défaut est 0775.

Fichiers

Les fichiers dans spufs suivent majoritairement le comportement standard des appels système réguliers comme read(2) ou write(2), mais ne supportent souvent qu'un sous-ensemble des opérations prises en charge sur les systèmes de fichiers réguliers. Cette liste détaille les opérations prises en charge et les déviations par rapport au comportement standard décrit dans les pages de manuel respectives.

Tous les fichiers qui prennent en charge l'opération read(2) prennent également en charge readv(2) et tous les fichiers qui prennent en charge l'opération write(2) prennent également en charge writev(2). Tous les fichiers prennent en charge la famille d'opérations access(2) et stat(2), mais pour ce dernier appel, les seuls champs de la structure stat retournée contenant des informations fiables sont st_mode, st_nlink, st_uid et st_gid.

Tous les fichiers prennent en charge les opérations chmod(2)/fchmod(2) et chown(2)/fchown(2), mais ne pourront pas accorder des permissions qui contredisent les opérations possibles (par exemple, un accès en lecture sur le fichier wbox).

L'ensemble actuel de fichiers est :

/capabilities
Contient une chaîne délimitée par des virgules représentant les capacités de ce contexte SPU. Les capacités possibles sont :
sched
Ce contexte peut être planifié.
step
Ce contexte peut être exécuté en mode pas à pas, pour le débogage.

De nouveaux indicateurs de capacité peuvent être ajoutés à l'avenir.

/mem
le contenu de la mémoire de stockage locale du SPU. Il peut être accédé comme un fichier de mémoire partagée ordinaire et contient à la fois le code et les données dans l'espace d'adressage du SPU. Les opérations possibles sur un fichier mem ouvert sont :
read(2)
pread(2)
write(2)
pwrite(2)
lseek(2)
Ceux-ci fonctionnent comme d'habitude, à l'exception que lseek(2), write(2), et pwrite(2) ne sont pas pris en charge au-delà de la fin du fichier. La taille du fichier est la taille du stockage local du SPU, qui est normalement de 256 kilo-octets.
mmap(2)
Mapper mem dans l'espace d'adressage du processus fournit un accès au stockage local du SPU dans l'espace d'adressage du processus. Seuls les mappages MAP_SHARED sont autorisés.
/regs
Contient les registres d'usage général sauvegardés du contexte SPU. Ce fichier contient les valeurs de 128 bits de chaque registre, du registre 0 au registre 127, dans l'ordre. Cela permet d'inspecter les registres d'usage général pour le débogage.
La lecture ou l'écriture dans ce fichier nécessite que le contexte soit planifié, donc l'utilisation de ce fichier n'est pas recommandée en fonctionnement normal du programme.
Le fichier regs n'est pas présent sur les contextes qui ont été créés avec l'indicateur SPU_CREATE_NOSCHED.
/mbox
La première boîte aux lettres de communication SPU-à-CPU. Ce fichier est en lecture seule et peut être lu par unités de 4 octets. Le fichier ne peut être utilisé qu'en mode non bloquant - même poll(2) ne peut pas être utilisé pour bloquer sur ce fichier. La seule opération possible sur un fichier mbox ouvert est :
read(2)
Si count est inférieur à quatre, read(2) renvoie -1 et définit errno à EINVAL. S'il n'y a pas de données disponibles dans la boîte aux lettres (c'est-à-dire que le SPU n'a pas envoyé de message de boîte aux lettres), la valeur de retour est définie à -1 et errno est défini à EAGAIN. Lorsque des données ont été lues avec succès, quatre octets sont placés dans le tampon de données et la valeur quatre est retournée.
/ibox
La deuxième boîte aux lettres de communication SPU-à-CPU. Ce fichier est similaire au premier fichier de boîte aux lettres, mais peut être lu en mode d'E/S bloquant, donc l'appel à read(2) sur un fichier ibox ouvert bloquera jusqu'à ce que le SPU ait écrit des données sur son canal de boîte aux lettres d'interruption (sauf si le fichier a été ouvert avec O_NONBLOCK, voir ci-dessous). De plus, poll(2) et les appels système similaires peuvent être utilisés pour surveiller la présence de données dans la boîte aux lettres.
Les opérations possibles sur un fichier ibox ouvert sont :
read(2)
Si count est inférieur à quatre, read(2) renvoie -1 et définit errno à EINVAL. S'il n'y a pas de données disponibles dans la boîte aux lettres et que le descripteur de fichier a été ouvert avec O_NONBLOCK, la valeur de retour est définie à -1 et errno est défini à EAGAIN.
S'il n'y a pas de données disponibles dans la boîte aux lettres et que le descripteur de fichier a été ouvert sans O_NONBLOCK, l'appel bloquera jusqu'à ce que le SPU écrive sur son canal de boîte aux lettres d'interruption. Lorsque des données ont été lues avec succès, quatre octets sont placés dans le tampon de données et la valeur quatre est retournée.
poll(2)
Poll sur le fichier ibox renvoie (POLLIN | POLLRDNORM) chaque fois que des données sont disponibles en lecture.
/wbox
La boîte aux lettres de communication CPU-vers-SPU. Elle est en écriture seule et peut être écrite par unités de quatre octets. Si la boîte aux lettres est pleine, write(2) bloquera, et poll(2) peut être utilisé pour bloquer jusqu'à ce que la boîte aux lettres soit à nouveau disponible pour l'écriture. Les opérations possibles sur un fichier wbox ouvert sont :
write(2)
Si count est inférieur à quatre, write(2) renvoie -1 et définit errno à EINVAL. S'il n'y a pas d'espace disponible dans la boîte aux lettres et que le descripteur de fichier a été ouvert avec O_NONBLOCK, la valeur de retour est définie à -1 et errno est défini à EAGAIN.
Si la boîte aux lettres est pleine et que le descripteur de fichier a été ouvert sans O_NONBLOCK, l'appel bloquera jusqu'à ce qu'il y ait assez d'espace pour écrire les données demandées dans la boîte aux lettres. Lorsque les données ont été écrites avec succès, la valeur retournée est le nombre d'octets écrits (généralement 4).
poll(2)
Poll sur le fichier wbox renvoie (POLLOUT | POLLWRNORM) chaque fois que des données peuvent être écrites.
/event
Ce fichier peut être lu pour recevoir les événements de fin d'exécution du SPU. Il renvoie jusqu'à 4 octets d'informations par événement. L'appel read(2) sur ce fichier est bloquant s'il n'y a pas d'événements. Il est donc possible d'utiliser poll(2) pour surveiller la disponibilité d'événements.
read(2)
Si count est inférieur à quatre, renvoie -1 et définit errno à EINVAL. S'il n'y a pas d'événements disponibles et que le descripteur de fichier a été ouvert avec O_NONBLOCK, renvoie -1 et définit errno à EAGAIN. Sinon, bloque jusqu'à ce qu'un événement soit disponible. Renvoie le nombre d'octets lus (4 en cas de succès).
poll(2)
Renvoie (POLLIN | POLLRDNORM) lorsqu'un événement est disponible en lecture.
/run
Écrire dans ce fichier démarre le SPU. Le contenu écrit est le nombre d'octets de code à exécuter, qui doit être un multiple de 128 octets (la taille d'un cache d'instructions SPU). L'écriture doit être effectuée sur le fichier /mem avant d'écrire dans /run.
write(2)
La taille du buffer doit être un multiple de 128 octets. L'opération est bloquante et ne renvoie que lorsque le SPU a terminé son exécution.
/stop
Écrire dans ce fichier arrête le SPU. L'écriture d'un octet quelconque (par exemple, '1') dans ce fichier arrête le SPU.
/clear
Écrire dans ce fichier efface l'état du SPU. L'écriture d'un octet quelconque (par exemple, '1') dans ce fichier efface le SPU.
/exit
Écrire dans ce fichier termine le thread SPU.
/contextid
Ce fichier contient l'ID du contexte SPU sous forme de chaîne ASCII terminée par un saut de ligne. Il peut être lu.
/privilege
Ce fichier contient l'ID du privilège sous forme de chaîne ASCII terminée par un saut de ligne. Il peut être lu.
/spu_thread_id
Ce fichier contient l'ID du thread SPU sous forme de chaîne ASCII terminée par un saut de ligne. Il peut être lu.
/spu_name
Ce fichier contient le nom du thread SPU sous forme de chaîne ASCII terminée par un saut de ligne. Il peut être lu.
/spu_priority
Ce fichier contient la priorité du thread SPU sous forme de chaîne ASCII terminée par un saut de ligne. Il peut être lu.
/spu_state
Ce fichier contient l'état du thread SPU sous forme de chaîne ASCII terminée par un saut de ligne. Il peut être lu. Les états possibles sont : RUNNING, STOPPED, FINISHED.
/spu_run_quantum
Ce fichier contient le quantum d'exécution du SPU sous forme de chaîne ASCII terminée par un saut de ligne. Il peut être lu.
/spu_program_name
Ce fichier contient le nom du programme SPU sous forme de chaîne ASCII terminée par un saut de ligne. Il peut être lu.

Lorsque les données ont été écrites avec succès, l'appel système renvoie quatre comme résultat de sa fonction.
poll(2)
Un appel poll sur le fichier wbox renvoie (POLLOUT | POLLWRNORM) dès que de l'espace est disponible pour l'écriture.
/mbox_stat
/ibox_stat
/wbox_stat
Ce sont des fichiers en lecture seule qui contiennent la longueur de la file d'attente actuelle de chaque boîte aux lettres — c'est-à-dire, combien de mots peuvent être lus depuis mbox ou ibox ou combien de mots peuvent être écrits dans wbox sans bloquer. Les fichiers ne peuvent être lus que par unités de quatre octets et renvoient un nombre entier binaire en big-endian. La seule opération possible sur un fichier *box_stat ouvert est :
read(2)
Si count est inférieur à quatre, read(2) renvoie -1 et définit errno à EINVAL. Sinon, une valeur de quatre octets est placée dans le tampon de données. Cette valeur est le nombre d'éléments qui peuvent être lus depuis (pour mbox_stat et ibox_stat) ou écrits dans (pour wbox_stat) la boîte aux lettres respective sans bloquer ou renvoyer une erreur EAGAIN.
/npc
/decr
/decr_status
/spu_tag_mask
/event_mask
/event_status
/srr0
/lslr
Registres internes du SPU. Ces fichiers contiennent une chaîne ASCII représentant la valeur hexadécimale du registre spécifié. Les lectures et écritures sur ces fichiers (sauf pour npc, voir ci-dessous) nécessitent que le contexte SPU soit désactivé, donc un accès fréquent à ces fichiers n'est pas recommandé pour le fonctionnement normal du programme.
Le contenu de ces fichiers est :
npc
Prochain compteur de programme — valide uniquement lorsque le SPU est à l'état arrêté.
decr
Décrémenteur SPU
decr_status
Statut du décrémenteur
spu_tag_mask
Masque de balise MFC pour le DMA SPU
event_mask
Masque d'événements pour les interruptions SPU
event_status
Nombre d'événements SPU en attente (lecture seule)
srr0
Registre d'adresse de retour d'interruption
lslr
Registre de limite de magasin local
Les opérations possibles sur ces fichiers sont :
read(2)
Lit la valeur actuelle du registre. Si la valeur du registre est supérieure à la taille du tampon passé à l'appel système read(2), les lectures ultérieures continueront de lire depuis le même tampon, jusqu'à ce que la fin du tampon soit atteinte.
Lorsqu'une chaîne complète a été lue, toutes les opérations de lecture ultérieures renverront zéro octet et un nouveau descripteur de fichier devra être ouvert pour lire une nouvelle valeur.
write(2)
Une opération write(2) sur le fichier définit le registre à la valeur indiquée dans la chaîne. La chaîne est analysée depuis le début jusqu'au premier caractère non numérique ou jusqu'à la fin du tampon. Les écritures ultérieures sur le même descripteur de fichier écrasent le réglage précédent.
À l'exception du fichier npc, ces fichiers ne sont pas présents sur les contextes qui ont été créés avec le drapeau SPU_CREATE_NOSCHED.
/fpcr
Ce fichier donne accès au registre d'état et de contrôle des nombres à virgule flottante (fcpr) sous forme de fichier binaire de quatre octets. Les opérations sur le fichier fpcr sont :
read(2)
Si count est inférieur à quatre, read(2) renvoie -1 et définit errno à EINVAL. Sinon, une valeur de quatre octets est placée dans le tampon de données ; il s'agit de la valeur actuelle du registre fpcr.
write(2)
Si count est inférieur à quatre, write(2) renvoie -1 et définit errno à EINVAL. Sinon, une valeur de quatre octets est copiée depuis le tampon de données, mettant à jour la valeur du registre fpcr.
/signal1
/signal2
Ces fichiers donnent accès aux deux canaux de notification de signal d'un SPU. Ce sont des fichiers de lecture-écriture qui opèrent sur des mots de quatre octets. L'écriture dans l'un de ces fichiers déclenche une interruption sur le SPU. La valeur écrite dans les fichiers de signal peut être lue depuis le SPU via une lecture de canal ou depuis l'espace utilisateur hôte via le fichier. Une fois la valeur lue par le SPU, elle est remise à zéro. Les opérations possibles sur un fichier signal1 ou signal2 ouvert sont :
read(2)
Si count est inférieur à quatre, read(2) renvoie -1 et définit errno à EINVAL. Sinon, une valeur de quatre octets est placée dans le tampon de données ; il s'agit de la valeur actuelle du registre de notification de signal spécifié.
write(2)
Si count est inférieur à quatre, write(2) renvoie -1 et définit errno à EINVAL. Sinon, une valeur de quatre octets est copiée depuis le tampon de données, mettant à jour la valeur du registre de notification de signal spécifié. Le registre de notification de signal sera soit remplacé par les données d'entrée, soit mis à jour avec l'opération OU logique de la valeur précédente et des données d'entrée, selon le contenu des fichiers signal1_type ou signal2_type respectivement.
/signal1_type
/signal2_type
Ces deux fichiers modifient le comportement des fichiers de notification signal1 et signal2. Ils contiennent une chaîne ASCII numérique qui est lue comme "1" ou "0". En mode 0 (remplacement), le matériel remplace le contenu du canal de signal par les données qui y sont écrites. En mode 1 (OU logique), le matériel accumule les bits qui sont ensuite écrits. Les opérations possibles sur un fichier signal1_type ou signal2_type ouvert sont :
read(2)
Lorsque le nombre spécifié dans l'appel read(2) est inférieur à la longueur requise pour le chiffre (plus un caractère de nouvelle ligne), les lectures ultérieures depuis le même descripteur de fichier compléteront la chaîne. Lorsqu'une chaîne complète a été lue, toutes les opérations de lecture ultérieures renverront zéro octet et un nouveau descripteur de fichier devra être ouvert pour relire la valeur.
write(2)
Une opération write(2) sur le fichier définit le registre à la valeur indiquée dans la chaîne. La chaîne est analysée depuis le début jusqu'au premier caractère non numérique ou jusqu'à la fin du tampon. Les écritures ultérieures sur le même descripteur de fichier écrasent le réglage précédent.
/mbox_info
/ibox_info
/wbox_info
/dma_into
/proxydma_info
Fichiers en lecture seule qui contiennent l'état sauvegardé des boîtes aux lettres et des files d'attente DMA du SPU. Cela permet d'inspecter l'état du SPU, principalement pour le débogage. Les fichiers mbox_info et ibox_info contiennent chacun le message de boîte aux lettres de quatre octets qui a été écrit par le SPU. Si aucun message n'a été écrit dans ces boîtes aux lettres, le contenu de ces fichiers est indéfini. Les fichiers mbox_stat, ibox_stat et wbox_stat contiennent le nombre de messages disponibles.
Le fichier wbox_info contient un tableau de messages de boîte aux lettres de quatre octets, qui ont été envoyés au SPU. Avec les machines CBEA actuelles, le tableau a une longueur de quatre éléments, donc jusqu'à 4 * 4 = 16 octets peuvent être lus depuis ce fichier. Si une entrée de file d'attente de boîte aux lettres est vide, alors les octets lus à l'emplacement correspondant sont indéfinis.
Le fichier dma_info contient le contenu de la file d'attente DMA SPU MFC, représenté par la structure suivante :

struct spu_dma_info {
    uint64_t         dma_info_type;
    uint64_t         dma_info_mask;
    uint64_t         dma_info_status;
    uint64_t         dma_info_stall_and_notify;
    uint64_t         dma_info_atomic_command_status;
    struct mfc_cq_sr dma_info_command_data[16];
};

Le dernier membre de cette structure de données est la file d'attente DMA réelle, contenant 16 entrées. La structure mfc_cq_sr est définie comme suit :

struct mfc_cq_sr {
    uint64_t mfc_cq_data0_RW;
    uint64_t mfc_cq_data1_RW;
    uint64_t mfc_cq_data2_RW;
    uint64_t mfc_cq_data3_RW;
};

Le fichier proxydma_info contient des informations similaires, mais décrit la file d'attente DMA proxy (c'est-à-dire, les DMAs initiés par des entités externes au SPU) à la place. Le fichier est dans le format suivant :

struct spu_proxydma_info {
    uint64_t         proxydma_info_type;
    uint64_t         proxydma_info_mask;
    uint64_t         proxydma_info_status;
    struct mfc_cq_sr proxydma_info_command_data[8];
};

L'accès à ces fichiers nécessite que le contexte SPU soit désactivé — une utilisation fréquente peut être inefficace. Ces fichiers ne doivent pas être utilisés pour ni
mal opération du programme.
Ces fichiers ne sont pas présents sur les contextes créés avec le drapeau SPU_CREATE_NOSCHED.
/cntl
Ce fichier donne accès aux registres de contrôle d'exécution et d'état du SPU, sous forme de chaîne ASCII. Les opérations suivantes sont prises en charge :
read(2)
Les lectures du fichier cntl retourneront une chaîne ASCII avec la valeur hexadécimale du registre d'état du SPU.
write(2)
Les écritures dans le fichier cntl définiront le registre de contrôle d'exécution du SPU du contexte.
/mfc
Permet d'accéder au Memory Flow Controller (MFC) du SPU. La lecture du fichier retourne le contenu du registre d'état des étiquettes du MFC, et l'écriture dans le fichier initie un DMA depuis le MFC. Les opérations suivantes sont prises en charge :
write(2)
Les écritures dans ce fichier doivent être dans le format d'une commande DMA du MFC, définie comme suit :

struct mfc_dma_command {
    int32_t  pad;    /* réservé */
    uint32_t lsa;    /* adresse de stockage local */
    uint64_t ea;     /* adresse effective */
    uint16_t size;   /* taille du transfert */
    uint16_t tag;    /* étiquette de commande */
    uint16_t class;  /* identifiant de classe */
    uint16_t cmd;    /* opcode de commande */
};

Les écritures doivent être exactement de sizeof(struct mfc_dma_command) octets. La commande sera envoyée à la file d'attente proxy du MFC du SPU, et l'étiquette sera stockée dans le noyau (voir ci-dessous).
read(2)
Lit le contenu du registre d'état des étiquettes. Si le fichier est ouvert en mode bloquant (c'est-à-dire sans O_NONBLOCK), la lecture bloquera jusqu'à ce qu'une étiquette DMA (effectuée par une écriture précédente) soit terminée. En mode non bloquant, le registre d'état des étiquettes du MFC sera retourné sans attendre.
poll(2)
Appeler poll(2) sur le fichier mfc bloquera jusqu'à ce qu'un nouveau DMA puisse être démarré (en vérifiant POLLOUT) ou jusqu'à ce qu'un DMA précédemment démarré (en vérifiant POLLIN) soit terminé.
/mss Permet d'accéder à la fonction MultiSource Synchronization (MSS) du MFC. En effectuant un mmap(2) sur ce fichier, les processus peuvent accéder à la zone MSS du SPU.
Les opérations suivantes sont prises en charge :
mmap(2)
Mapper mss dans l'espace d'adressage du processus donne accès à la zone MSS du SPU dans l'espace d'adressage du processus. Seuls les mappings MAP_SHARED sont autorisés.
/psmap
Fournit un accès à l'ensemble du mappage de l'état du problème (problem-state) du SPU. Les applications peuvent utiliser cette zone pour interagir avec le SPU, plutôt que d'écrire dans des fichiers de registres individuels dans spufs.
Les opérations suivantes sont prises en charge :
mmap(2)
Mapper psmap donne à un processus une carte directe de la zone d'état du problème du SPU. Seuls les mappings MAP_SHARED sont pris en charge.
/phys-id
Fichier en lecture seule contenant le numéro physique du SPU sur lequel le contexte SPU est en cours d'exécution. Lorsque le contexte n'est pas en cours d'exécution, ce fichier contient la chaîne ""-1"".
Le numéro physique du SPU est donné par une chaîne hexadécimale ASCII.
/object-id
Permet aux applications de stocker (ou de récupérer) un identifiant unique de 64 bits dans le contexte. Cet identifiant est ensuite utilisé par les outils de profilage pour identifier uniquement le contexte.
write(2)
En écrivant une valeur hexadécimale ASCII dans ce fichier, les applications peuvent définir l'identifiant d'objet du contexte SPU. Toute valeur précédente de l'identifiant d'objet est écrasée.
read(2)
La lecture de ce fichier donne une chaîne hexadécimale ASCII représentant l'identifiant d'objet pour ce contexte SPU.

EXEMPLES

Pour monter automatiquement le système de fichiers SPU au démarrage, à l'emplacement /spu choisi par l'utilisateur, ajoutez cette ligne au fichier de configuration fstab(5) :

none /spu spufs gid=spu 0 0
