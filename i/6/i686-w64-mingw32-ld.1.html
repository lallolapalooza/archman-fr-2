LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNOPSIS

ld [options] fichier_objet ...

DESCRIPTION

ld combine un certain nombre de fichiers objet et d'archives, relocalise leurs données et résout les références de symboles. Habituellement, la dernière étape de la compilation d'un programme consiste à exécuter ld.

ld accepte les fichiers de langage de commande de l'éditeur de liens écrits dans une sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus de liaison.

Cette page manuel ne décrit pas le langage de commande ; voir l'entrée ld dans "info" pour tous les détails sur le langage de commande et sur les autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour manipuler les fichiers objet. Cela permet à ld de lire, combiner et écrire des fichiers objet dans de nombreux formats différents---par exemple COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

En plus de sa flexibilité, l'éditeur de liens GNU est plus utile que les autres éditeurs de liens pour fournir des informations de diagnostic. Beaucoup d'éditeurs de liens abandonnent l'exécution immédiatement lorsqu'ils rencontrent une erreur ; chaque fois que c'est possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations, et pour être aussi compatible que possible avec les autres éditeurs de liens. En conséquence, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options de ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld consiste à lier des fichiers objet Unix standard sur un système Unix standard et pris en charge. Sur un tel système, pour lier un fichier "hello.o":

ld -o <sortie> /lib/crt0.o hello.o -lc

Cela indique à ld de produire un fichier appelé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion de l'option -l ci-dessous.)

Certaines des options de ligne de commande pour ld peuvent être spécifiées à n'importe quel point de la ligne de commande. Cependant, les options qui se réfèrent à des fichiers, telles que -l ou -T, provoquent la lecture du fichier au point où l'option apparaît dans la ligne de commande, par rapport aux fichiers objet et aux autres options de fichier. Répéter des options non-fichier avec un argument différent n'aura soit aucun effet supplémentaire, soit remplacera les occurrences précédentes (celles situées plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être significativement spécifiées plus d'une fois sont notées dans les descriptions ci-dessous.

Les arguments non-option sont des fichiers objet ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de ligne de commande, sauf qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Habituellement, l'éditeur de liens est invoqué avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -Ret le langage de commande des scripts. Si aucun fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et émet le message No input files.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script de l'éditeur de liens. Un script spécifié de cette manière complète le script principal de l'éditeur de liens utilisé pour la liaison (soit le script par défaut de l'éditeur de liens, soit celui spécifié en utilisant -T). Cette fonctionnalité permet à l'éditeur de liens de lier avec un fichier qui semble être un objet ou une archive, mais qui définit en réalité certaines valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. Spécifier un script de cette manière complète simplement le script principal de l'éditeur de liens, avec les commandes supplémentaires placées après le script principal ; utilisez l'option -T pour remplacer entièrement le script par défaut de l'éditeur de liens, mais notez l'effet de la commande "INSERT" .

Pour les options dont les noms sont d'une seule lettre, les arguments de l'option doivent soit suivre la lettre de l'option sans espace blanc intermédiaire, soit être donnés comme des arguments séparés immédiatement après l'option qui les requiert.

Pour les options dont les noms sont de plusieurs lettres, un seul tiret ou deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez---il y a une exception à cette règle. Les options à lettres multiples qui commencent par un 'o' minuscule ne peuvent être précédées que par deux tirets. Cela est fait pour réduire la confusion avec l'option -o . Ainsi, par exemple -omagic définit le nom du fichier de sortie à magic alors que --omagic définit l'indicateur NMAGIC sur la sortie.

Les arguments des options à lettres multiples doivent soit être séparés du nom de l'option par un signe égal, soit être donnés comme des arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Les abréviations uniques des noms des options à lettres multiples sont acceptées.

Notez---si l'éditeur de liens est invoqué indirectement, via un pilote de compilateur (par ex. gcc) alors toutes les options de ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote de compilateur particulier) comme ceci :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

C'est important, car sinon le programme pilote de compilateur peut silencieusement abandonner les options de l'éditeur de liens, résultant en une mauvaise liaison. De la confusion peut aussi survenir lors du passage d'options nécessitant des valeurs via un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et fait que le pilote ne passe que l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est le plus simple d'utiliser les formes jointes des options à une seule lettre et à lettres multiples, telles que :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

@fichier
Lire les options de ligne de commande à partir de fichier. Les options lues sont insérées à la place de l'option originale @fichier . Si fichier n'existe pas ou ne peut pas être lu, alors l'option sera traitée littéralement et ne sera pas supprimée.

Les options dans fichier sont séparées par des espaces blancs. Un caractère d'espace blanc peut être inclus dans une option en entourant l'option entière soit par des guillemets simples, soit par des guillemets doubles. N'importe quel caractère (y compris une barre oblique inverse) peut être inclus en préfixant le caractère à inclure avec une barre oblique inverse. Le fichier peut lui-même contenir des options @fichier supplémentaires ; toutes ces options seront traitées récursivement.

-a mot-clé
Cette option est prise en charge pour la compatibilité avec HP/UX. L'argument mot-clé doit être l'une des chaînes archive, sharedou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée un nombre quelconque de fois.
--audit BIBLIOTHÈQUE_AUDIT
Ajoute BIBLIOTHÈQUE_AUDIT à l'entrée "DT_AUDIT" de la section dynamique. BIBLIOTHÈQUE_AUDIT n'est pas vérifiée pour son existence, et n'utilisera pas non plus le DT_SONAME spécifié dans la bibliothèque. Si spécifiée plusieurs fois, "DT_AUDIT" contiendra une liste d'interfaces d'audit séparées par des deux-points à utiliser. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée "DT_DEPAUDIT" correspondante dans le fichier de sortie. Cette option n'est significative que sur les plateformes ELF prenant en charge l'interface rtld-audit.
-b format-entrée
--format=format-entrée
ld peut être configuré pour prendre en charge plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire des fichiers objet d'entrée qui suivent cette option sur la ligne de commande. Même lorsque ld est configuré pour prendre en charge des formats d'objet alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour s'attendrect en tant que format d'entrée par défaut, le format le plus courant sur chaque machine. format-entrée est une chaîne de caractères, le nom d'un format particulier pris en charge par les bibliothèques BFD. (Vous pouvez lister les formats binaires disponibles avec objdump -i.)

Vous voudrez peut-être utiliser cette option si vous liez des fichiers avec un format binaire inhabituel. Vous pouvez également utiliser -b pour commuter explicitement les formats (lorsque vous liez des fichiers objet de formats différents), en incluant -b format-entrée avant chaque groupe de fichiers objet d'un format particulier.

Le format par défaut est pris de la variable d'environnement "GNUTARGET".

Vous pouvez également définir le format d'entrée à partir d'un script, en utilisant la commande "TARGET" ;

--mri-script=fichier-commande-MRI
Pour la compatibilité avec les éditeurs de liens produits par MRI, ld accepte des fichiers script écrits dans un langage de commande alternatif et restreint, décrit dans la section « MRI Compatible Script Files » de la documentation GNU ld. Introduisez les fichiers script MRI avec l'option -c ; utilisez l'option -T pour exécuter des scripts d'éditeur de liens écrits dans le langage de script ld généraliste. Si fichier-commande-MRI n'existe pas, ld le recherche dans les répertoires spécifiés par toutes options -L.

--enable-linker-version
Active la directive de script d'éditeur de liens "LINKER_VERSION", décrite dans Données de section de sortie. Si cette directive est utilisée dans un script d'éditeur de liens et que cette option a été activée, une chaîne contenant la version de l'éditeur de liens sera insérée au point courant.

Notez que l'emplacement de cette option sur la ligne de commande de l'éditeur de liens est significatif. Elle n'affectera que les scripts d'éditeur de liens qui la suivent sur la ligne de commande, ou ceux qui sont intégrés à l'éditeur de liens.

--disable-linker-version
Désactive la directive de script d'éditeur de liens "LINKER_VERSION", de sorte qu'elle n'insère pas de chaîne de version. C'est le comportement par défaut.
--enable-non-contiguous-regions
Cette option évite de générer une erreur si une section d'entrée ne correspond pas à une section de sortie correspondante. L'éditeur de liens essaie d'allouer la section d'entrée aux sections de sortie correspondantes suivantes, et ne génère une erreur que si aucune section de sortie n'est suffisamment grande. Ceci est utile lorsque plusieurs régions mémoire non contiguës sont disponibles et que la section d'entrée n'en requiert aucune en particulier. L'ordre d'évaluation des sections d'entrée ne change pas, par exemple : 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

avec les sections d'entrée :
.data.1: taille 8
.data.2: taille 0x10
.data.3: taille 4

résulte en .data.1 affecté à mem1, et .data.2 et .data.3
affectés à mem2, même si .data.3 pourrait tenir dans mem3.

Cette option est incompatible avec les instructions INSERT car elle modifie la façon dont les sections d'entrée sont mappées aux sections de sortie.

--enable-non-contiguous-regions-warnings
Cette option active les avertissements lorsque "--enable-non-contiguous-regions" permet des correspondances potentiellement inattendues dans le mappage des sections, ce qui pourrait conduire à ignorer silencieusement une section au lieu d'échouer parce qu'elle ne rentre dans aucune région de sortie.
-e point-entrée
--entry=point-entrée
Utilise point-entrée comme symbole explicite pour le début de l'exécution de votre programme, plutôt que le point d'entrée par défaut. S'il n'y a pas de symbole nommé point-entrée, l'éditeur de liens essaiera de parser point-entrée comme un nombre et de l'utiliser comme adresse de point d'entrée (le nombre sera interprété en base 10 ; vous pouvez utiliser un préfixe 0x pour la base 16, ou un préfixe 0 pour la base 8). Pour i386 PE, point-entrée peut également être le nom de fonction d'origine (sans le trait de soulignement initial et/ou le suffixe stdcall @nombre le cas échéant).
--exclude-libs lib,lib,...
Spécifie une liste de bibliothèques d'archives à partir desquelles les symboles ne doivent pas être automatiquement exportés. Les noms de bibliothèques peuvent être délimités par des virgules ou des deux-points. Spécifier "--exclude-libs ALL" exclut les symboles de toutes les bibliothèques d'archives de l'exportation automatique. Cette option n'est disponible que pour le port cible i386 PE de l'éditeur de liens et pour les ports cibles ELF. Pour i386 PE, les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option. Pour les ports cibles ELF, les symboles affectés par cette option seront traités comme cachés.
--exclude-modules-for-implib module,module,...
Spécifie une liste de fichiers objet ou de membres d'archive, à partir desquels les symboles ne doivent pas être automatiquement exportés, mais qui doivent être copiés en bloc dans la bibliothèque d'importation générée pendant l'édition de liens. Les noms de modules peuvent être délimités par des virgules ou des deux-points, et doivent correspondre exactement aux noms de fichiers utilisés par ld pour ouvrir les fichiers ; pour les membres d'archive, il s'agit simplement du nom du membre, mais pour les fichiers objet, le nom listé doit inclure et correspondre précisément à tout chemin utilisé pour spécifier le fichier d'entrée sur la ligne de commande de l'éditeur de liens. Cette option n'est disponible que pour le port cible i386 PE de l'éditeur de liens. Les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option.
-E
--export-dynamic
--no-export-dynamic
Lors de la création d'un exécutable lié dynamiquement, l'utilisation de l'option -E ou de l'option --export-dynamic fait que l'éditeur de liens ajoute tous les symboles à la table des symboles dynamiques. La table des symboles dynamiques est l'ensemble des symboles qui sont visibles depuis les objets dynamiques à l'exécution.

Si vous n'utilisez aucune de ces options (ou si vous utilisez l'option --no-export-dynamic pour rétablir le comportement par défaut), la table des symboles dynamiques contiendra normalement uniquement les symboles qui sont référencés par un objet dynamique mentionné dans la liaison.

Si vous utilisez "dlopen" pour charger un objet dynamique qui doit se référer aux symboles définis par le programme, plutôt qu'à un autre objet dynamique, alors vous devrez probablement utiliser cette option lors de l'édition de liens du programme lui-même.

Vous pouvez également utiliser la liste dynamique pour contrôler quels symboles doivent être ajoutés à la table des symboles dynamiques si le format de sortie le prend en charge. Voir la description de --dynamic-list.

Notez que cette option est spécifique aux ports cibles ELF. Les cibles PE prennent en charge une fonction similaire pour exporter tous les symboles d'une DLL ou d'un EXE ; voir la description de --export-all-symbols ci-dessous.

--export-dynamic-symbol=glob
Lors de la création d'un exécutable lié dynamiquement, les symboles correspondant à glob seront ajoutés à la table des symboles dynamiques. Lors de la création d'une bibliothèque partagée, les références aux symboles correspondant à glob ne seront pas liées aux définitions au sein de la bibliothèque partagée. Cette option est sans effet lors de la création d'une bibliothèque partagée si -Bsymbolic ou --dynamic-list ne sont pas spécifiés. Cette option n'est significative que sur les plateformes ELF qui prennent en charge les bibliothèques partagées.
--export-dynamic-symbol-list=fichier
Spécifie un --export-dynamic-symbol pour chaque modèle dans le fichier. Le format du fichier est le même que celui du nœud de version sans portée ni nom de nœud. Voir VERSION pour plus d'informations.

-( archives -)

The archives should be a list of archive files. They may be either explicit file names, or -l options.

The specified archives are searched repeatedly until no new undefined references are created. Normally, an archive is searched only once in the order that it is specified on the command line. If a symbol in that archive is needed to resolve an undefined symbol referred to by an object in an archive that appears later on the command line, the linker would not be able to resolve that reference. By grouping the archives, they will all be searched repeatedly until all possible references are resolved.

Using this option has a significant performance cost. It is best to use it only when there are unavoidable circular references between two or more archives.

Avec --copy-dt-needed-entries les bibliothèques dynamiques mentionnées sur la ligne de commande seront recherchées récursivement, en suivant leurs balises DT_NEEDED vers d'autres bibliothèques, afin de résoudre les symboles requis par le binaire de sortie. Avec le réglage par défaut, cependant, la recherche des bibliothèques dynamiques qui le suivent s'arrêtera à la bibliothèque dynamique elle-même. Aucun lien DT_NEEDED ne sera traversé pour résoudre les symboles.

--cref
Produire une table de références croisées. Si un fichier de carte d'édition de liens est généré, la table de références croisées est imprimée dans le fichier de carte. Sinon, elle est imprimée sur la sortie standard.

Le format de la table est volontairement simple, afin qu'elle puisse être facilement traitée par un script si nécessaire. Les symboles sont imprimés, triés par nom. Pour chaque symbole, une liste de noms de fichiers est donnée. Si le symbole est défini, le premier fichier listé est l'emplacement de la définition. Si le symbole est défini comme une valeur commune, tous les fichiers où cela se produit apparaissent ensuite. Enfin, tous les fichiers qui référencent le symbole sont listés.

--ctf-variables
--no-ctf-variables
Le format de débogage CTF prend en charge une section qui encode les noms et les types des variables trouvées dans le programme qui n'apparaissent dans aucune table de symboles. Ces variables ne peuvent clairement pas être recherchées par adresse par les débogueurs conventionnels, donc l'espace utilisé pour leurs types et leurs noms est généralement gaspillé : les types sont généralement petits mais les noms souvent pas. --ctf-variables provoque la génération d'une telle section. Le comportement par défaut peut être restauré avec --no-ctf-variables.
--ctf-share-types=method
Ajuster la méthode utilisée pour partager les types entre les unités de traduction dans CTF.
share-unconflicted
Placer tous les types qui n'ont pas de définitions ambiguës dans le dictionnaire partagé, où les débogueurs peuvent facilement y accéder, même s'ils n'apparaissent que dans une unité de traduction. C'est le comportement par défaut.
share-duplicated
Placer uniquement les types qui apparaissent dans plusieurs unités de traduction dans le dictionnaire partagé : les types avec une seule définition vont dans les dictionnaires par unité de traduction. Les types avec des définitions ambiguës dans plusieurs unités de traduction vont toujours dans les dictionnaires par unité de traduction. Cela tend à rendre le CTF plus grand, mais peut réduire la quantité de CTF dans le dictionnaire partagé. Pour les projets très grands, cela peut accélérer l'ouverture du CTF et économiser de la mémoire dans le consommateur de CTF à l'exécution.
--no-define-common
Cette option inhibe l'assignation d'adresses aux symboles communs. La commande de script "INHIBIT_COMMON_ALLOCATION" a le même effet.

L'option --no-define-common permet de découpler la décision d'assigner des adresses aux symboles Common du choix du type de fichier de sortie ; sinon, un type de sortie non relocalisable force l'assignation d'adresses aux symboles Common. L'utilisation de --no-define-common permet aux symboles Common référencés d'une bibliothèque partagée pour se voir attribuer des adresses uniquement dans le programme principal. Cela élimine l'espace dupliqué inutilisé dans la bibliothèque partagée, et empêche également toute confusion possible quant à la résolution vers le mauvais duplicata lorsqu'il y a de nombreux modules dynamiques avec des chemins de recherche spécialisés pour la résolution des symboles à l'exécution.

--force-group-allocation
Cette option force l'éditeur de liens à placer les membres de groupe de sections comme des sections d'entrée normales, et à supprimer les groupes de sections. C'est le comportement par défaut pour une liaison finale, mais cette option peut être utilisée pour modifier le comportement d'une liaison déplaçable (-r). La commande de script "FORCE_GROUP_ALLOCATION" a le même effet.
--defsym=symbole=expression
Crée un symbole global dans le fichier de sortie, contenant l'adresse absolue donnée par expression. Vous pouvez utiliser cette option autant de fois que nécessaire pour définir plusieurs symboles sur la ligne de commande. Une forme limitée d'arithmétique est prise en charge pour l'expression dans ce contexte : vous pouvez donner une constante hexadécimale ou le nom d'un symbole existant, ou utiliser "+" et "-" pour additionner ou soustraire des constantes hexadécimales ou des symboles. Si vous avez besoin d'expressions plus élaborées, envisagez d'utiliser le langage de commande de l'éditeur de liens depuis un script. Remarque : il ne doit y avoir aucun espace blanc entre le symbole, le signe égal ("="), et l'expression.

L'éditeur de liens traite les arguments --defsym et -T dans l'ordre ; placer --defsym avant -T définira le symbole avant que le script de liens de -T ne soit traité, tandis que placer --defsym après -T définira le symbole après que le script de liens a été traité. Cette différence a des conséquences pour les expressions dans le script de liens qui utilisent les symboles --defsym ; l'ordre correct dépendra de ce que vous essayez d'atteindre.

--demangle[=style]
--no-demangle
Ces options contrôlent si les noms de symboles doivent être dé-manglés (démanglés) dans les messages d'erreur et les autres sorties. Différents compilateurs ont différents styles de mangling. L'argument de style de dé-mangling facultatif peut être utilisé pour choisir un style de dé-mangling approprié pour votre compilateur. L'éditeur de liens dé-manglera par défaut, sauf si la variable d'environnement COLLECT_NO_DEMANGLE est définie. Ces options peuvent être utilisées pour remplacer le comportement par défaut.

--dynamic-linker=fichier

--no-dynamic-linker

Cela n'a de sens que pour les exécutables ELF contenant des relocalisations dynamiques, et nécessite généralement un code de point d'entrée capable de traiter ces relocalisations.
--embedded-relocs
Cette option est similaire à l'option --emit-relocs sauf que les relocalisations sont stockées dans une section spécifique à la cible. Cette option n'est prise en charge que par les cibles BFIN, CR16 et M68K .
--disable-multiple-abs-defs
Ne pas autoriser les définitions multiples avec les symboles inclus dans le fichier nommé par -R ou --just-symbols
--fatal-warnings
--no-fatal-warnings

-w
--no-warnings

--force-exe-suffix

Cette option est utile lors de l'utilisation de Makefiles Unix non modifiés sur un hôte Microsoft Windows, car certaines versions de Windows n'exécuteront pas une image à moins qu'elle ne se termine par un suffixe ".exe" .

--gc-sections
--no-gc-sections
Active la collecte des sections d'entrée inutilisées. C'est ignoré sur les cibles qui ne prennent pas en charge cette option. Le comportement par défaut (ne pas effectuer cette collecte) peut être restauré en spécifiant --no-gc-sections sur la ligne de commande. Notez que la collecte pour les cibles au format COFF et PE est prise en charge, mais l'implémentation est actuellement considérée comme expérimentale.

--gc-sections décide quelles sections d'entrée sont utilisées en examinant les symboles et les relocalisations. La section contenant le symbole d'entrée et toutes les sections contenant des symboles non définis sur la ligne de commande seront conservées, tout comme les sections contenant des symboles référencés par des objets dynamiques. Notez que lors de la construction de bibliothèques partagées, l'éditeur de liens doit supposer que tout symbole visible est référencé. Une fois cet ensemble initial de sections déterminé, l'éditeur de liens marque récursivement comme utilisée toute section référencée par leurs relocalisations. Voir --entry, --undefined, et --gc-keep-exported.

Cette option peut être définie lors d'une liaison partielle (activée avec l'option -r). Dans ce cas, la racine des symboles conservés doit être explicitement spécifiée soit par l'une des options --entry, --undefined, ou --gc-keep-exported soit par une commande "ENTRY" dans le script de liens.

En tant qu'extension GNU, les sections d'entrée ELF marquées avec l'indicateur "SHF_GNU_RETAIN" ne seront pas collectées.

--print-gc-sections
--no-print-gc-sections
Liste toutes les sections supprimées par la collecte. La liste est imprimée sur stderr. Cette option n'est efficace que si la collecte a été activée via l'option --gc-sections. Le comportement par défaut (ne pas lister les sections qui sont supprimées) peut être restauré en spécifiant --no-print-gc-sections sur la ligne de commande.
--gc-keep-exported
Quand --gc-sections est activé, cette option empêche la collecte des sections d'entrée inutilisées qui contiennent des symboles globaux ayant une visibilité par défaut ou protégée. Cette option est destinée à être utilisée pour les exécutables où les sections non référencées seraient autrement collectées quelle que soit la visibilité externe des symboles qu'elles contiennent. Notez que cette option n'a aucun effet lors de la liaison d'objets partagés car c'est déjà le comportement par défaut. Cette option n'est prise en charge que pour les cibles au format ELF.
--print-output-format
Affiche le nom du format de sortie par défaut (peut-être influencé par d'autres options de la ligne de commande). C'est la chaîne qui apparaîtrait dans une commande de script de liens "OUTPUT_FORMAT" .
--print-memory-usage
Affiche la taille utilisée, la taille totale et la taille utilisée des régions mémoire créées avec la commande MEMORY . C'est utile sur les cibles embarquées pour avoir une vue rapide de la quantité de mémoire libre. Le format de la sortie a un en-tête et une ligne par région. C'est à la fois lisible par l'humain et facilement analysable par les outils. Voici un exemple de sortie : 
Région mémoire         Taille utilisée  Taille région  % utilisé
             ROM:        256 Ko         1 Mo     25,00%
             RAM:          32 o         2 Go      0,00%

Remarque : si vous voulez connaître l'utilisation mémoire de l'éditeur de liens lui-même, alors l'option --stats fera cela.

Affiche un résumé des options de la ligne de commande sur la sortie standard et termine.

-Map=fichier_carte
Affiche une carte de liaison dans le fichier fichier_carte. Voir la description de l'option -M , ci-dessus. Si fichier_carte est juste le caractère "-" alors la carte sera écrite sur stdout.

Spécifier un répertoire comme fichier_carte fait que la carte de l'éditeur de liens est écrite comme un fichier à l'intérieur du répertoire. Normalement, le nom du fichier à l'intérieur du répertoire est calculé comme le nom de base du fichier de sortie avec ".map" ajouté. Si cependant le caractère spécial "%" est utilisé, alors il sera remplacé par le chemin complet du fichier de sortie. De plus, s'il y a des caractères après le symbole % alors ".map" ne sera plus ajouté.

-o foo.exe -Map=bar                  [Crée ./bar]
-o ../dir/foo.exe -Map=bar           [Crée ./bar]
-o foo.exe -Map=../dir               [Crée ../dir/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir       [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%                    [Crée ./foo.exe.map]
-o ../dir/foo.exe -Map=%             [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%.bar                [Crée ./foo.exe.bar]
-o ../dir/foo.exe -Map=%.bar         [Crée ../dir/foo.exe.bar]
-o ../dir2/foo.exe -Map=../dir/%     [Crée ../dir/../dir2/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir/%.bar [Crée ../dir/../dir2/foo.exe.bar]

Il est une erreur de spécifier plus d'un "%" caractère.

Si le fichier de carte existe déjà, il sera écrasé par cette opération.

Cette option indique à ld de plutôt optimiser pour l'utilisation de la mémoire, en relisant les tables de symboles au besoin. Cela peut être nécessaire si ld manque d'espace mémoire lors de l'édition de liens d'un exécutable volumineux.
--no-undefined
-z defs
Signaler les références à des symboles non résolus provenant de fichiers objets réguliers. Cela est fait même si l'éditeur de liens crée une bibliothèque partagée non symbolique. Le commutateur --[no-]allow-shlib-undefined contrôle le comportement pour signaler les références non résolues trouvées dans les bibliothèques partagées en cours d'édition de liens.

Les effets de cette option peuvent être annulés en utilisant "-z undefs".

--allow-multiple-definition
-z muldefs
Normalement, lorsqu'un symbole est défini plusieurs fois, l'éditeur de liens signalera une erreur fatale. Ces options permettent des définitions multiples et la première définition sera utilisée.
--allow-shlib-undefined
--no-allow-shlib-undefined
Autorise ou interdit les symboles non définis dans les bibliothèques partagées. Ce commutateur est similaire à --no-undefined sauf qu'il détermine le comportement lorsque les symboles non définis se trouvent dans une bibliothèque partagée plutôt que dans un fichier objet régulier. Cela n'affecte pas la manière dont les symboles non définis dans les fichiers objets réguliers sont traités.

Le comportement par défaut est de signaler des erreurs pour tout symbole non défini référencé dans les bibliothèques partagées si l'éditeur de liens est utilisé pour créer un exécutable, mais de les autoriser si l'éditeur de liens est utilisé pour créer une bibliothèque partagée.

Les raisons d'autoriser les références à des symboles non définis dans les bibliothèques partagées spécifiées au moment de l'édition de liens sont que :

  • Une bibliothèque partagée spécifiée au moment de l'édition de liens peut ne pas être la même que celle qui est disponible au moment du chargement, de sorte que le symbole pourrait en fait être résolvable au moment du chargement.
  • Il existe certains systèmes d'exploitation, par exemple BeOS et HPPA, où les symboles non définis dans les bibliothèques partagées sont normaux.

    Le noyau BeOS par exemple patche les bibliothèques partagées au moment du chargement pour sélectionner la fonction la plus appropriée pour l'architecture courante. Cela est utilisé, par exemple, pour sélectionner dynamiquement une fonction memset appropriée.

Deux arguments seront passés au script : le mot-clé "undefined-symbol" ou `missing-lib" et le nom du symbole non défini ou de la bibliothèque manquante. L'intention est que le script fournisse des suggestions à l'utilisateur quant à l'endroit où le symbole ou la bibliothèque pourrait être trouvé. La disponibilité de cette option est contrôlée par un commutateur de configuration, elle peut donc ne pas être présente dans des implémentations spécifiques.

--no-undefined-version

--no-warn-mismatch

Cette option indique à ld qu'il doit autoriser silencieusement ces erreurs possibles. Cette option ne doit être utilisée qu'avec précaution, dans les cas où vous avez pris une action spéciale qui garantit que les erreurs de l'éditeur de liens sont inappropriées.
--no-warn-search-mismatch

--no-whole-archive

--noinhibit-exec

-nostdlib
Rechercher uniquement dans les répertoires de bibliothèques explicitement spécifiés sur la ligne de commande. Les répertoires de bibliothèques spécifiés dans les scripts d'édition de liens (y compris les scripts d'édition de liens spécifiés sur la ligne de commande) sont ignorés.
--oformat=output-format

--relax
--no-relax

-rpath=dir
Ajouter un répertoire au chemin de recherche des bibliothèques d'exécution. C'est utilisé lors de l'édition de liens d'un exécutable ELF avec des objets partagés. Tous les arguments -rpath sont concaténés et passés à l'éditeur de liens d'exécution, qui les utilise pour localiser les objets partagés au moment de l'exécution.

L'option -rpath est également utilisée lors de la localisation des objets partagés dont ont besoin les objets partagés explicitement inclus dans l'édition de liens ; voir la description de l'option -rpath-link . La recherche -rpath de cette manière n'est prise en charge que par les éditeurs de liens natifs et les éditeurs de liens croisés qui ont été configurés avec l'option --with-sysroot .

Si -rpath</b> n'est pas utilisé lors de la liaison d'un exécutable ELF, le contenu de la variable d'environnement "LD_RUN_PATH" sera utilisé s'il est défini.

L'option -rpath peut également être utilisée sur SunOS. Par défaut, sur SunOS, l'éditeur de liens forme un chemin de recherche d'exécution à partir de toutes les options -L qui lui sont fournies. Si une option -rpath est utilisée, le chemin de recherche d'exécution sera formé exclusivement à l'aide des options -rpath, ignorant les options -L. Cela peut être utile lors de l'utilisation de gcc, qui ajoute de nombreuses options -L qui peuvent se trouver sur des systèmes de fichiers montés NFS.

Pour assurer la compatibilité avec d'autres éditeurs de liens ELF, si l'option -R est suivie d'un nom de répertoire, plutôt que d'un nom de fichier, elle est traitée comme l'option -rpath.

-rpath-link=dir
Lors de l'utilisation d'ELF ou de SunOS, une bibliothèque partagée peut en nécessiter une autre. Cela se produit lorsqu'un lien "ld -shared" inclut une bibliothèque partagée comme l'un des fichiers d'entrée.

Lorsque l'éditeur de liens rencontre une telle dépendance lors d'une liaison non partagée, non déplaçable, il essaiera automatiquement de localiser la bibliothèque partagée requise et de l'inclure dans la liaison, si elle n'est pas incluse explicitement. Dans un tel cas, plusieurs répertoires sont recherchés comme décrit ci-dessous. L'option -rpath-link spécifie le premier ensemble de répertoires à rechercher. Cette option peut spécifier une séquence de noms de répertoires soit en fournissant une liste de noms séparés par des deux-points, soit en apparaissant plusieurs fois.

Les jetons $ORIGIN et $LIB peuvent apparaître dans ces répertoires de recherche. Ils seront remplacés par le chemin complet vers le répertoire contenant le programme ou l'objet partagé dans le cas de $ORIGIN et soit lib - pour les binaires 32 bits - soit lib64 - pour les binaires 64 bits - dans le cas de $LIB.

La forme alternative de ces jetons - ${ORIGIN} et ${LIB} peut également être utilisée. Le jeton $PLATFORM n'est pas pris en charge.

L'option --rpath-link doit être utilisée avec prudence car elle remplace le chemin de recherche qui aurait pu être intégré en dur dans une bibliothèque partagée. Dans un tel cas, il est possible d'utiliser involontairement un chemin de recherche différent de celui qu'utiliserait l'éditeur de liens d'exécution.

Lorsque des bibliothèques partagées supplémentaires sont requises, l'éditeur de liens recherchera les répertoires dans l'ordre indiqué ci-dessous afin de les trouver. Notez cependant que cela ne s'applique qu'aux bibliothèques supplémentaires nécessaires pour satisfaire les bibliothèques partagées déjà incluses. Cela ne s'applique pas aux bibliothèques incluses via l'option de ligne de commande -l. Les recherches pour les bibliothèques -l ne sont effectuées que dans les répertoires spécifiés par l'option -L.

1.
Tous les répertoires spécifiés par les options -rpath-link.
2.
Tous les répertoires spécifiés par les options -rpath. La différence entre -rpath et -rpath-link est que les répertoires spécifiés par les options -rpath sont inclus dans l'exécutable et utilisés au moment de l'exécution, tandis que l'option -rpath-link n'est efficace qu'au moment de la liaison. La recherche de -rpath de cette manière n'est prise en charge que par les éditeurs de liens natifs et les éditeurs de liens croisés qui ont été configurés avec l'option --with-sysroot.
3.
Sur un système ELF, pour les éditeurs de liens natifs, si les options -rpath et -rpath-link n'ont pas été utilisées, rechercher le contenu de la variable d'environnement "LD_RUN_PATH".
4.
Sur SunOS, si l'option -rpath n'a pas été utilisée, rechercher tous les répertoires spécifiés à l'aide des options -L.
5.
Pour un éditeur de liens natif, rechercher le contenu de la variable d'environnement "LD_LIBRARY_PATH".
6.
Pour un éditeur de liens ELF natif, les répertoires dans "DT_RUNPATH" ou "DT_RPATH" d'une bibliothèque partagée sont recherchés pour les bibliothèques partagées dont elle a besoin. Les entrées "DT_RPATH" sont ignorées si les entrées "DT_RUNPATH" existent.
7.
Pour un éditeur de liens pour un système Linux, si le fichier /etc/ld.so.conf existe, la liste des répertoires trouvés dans ce fichier. Remarque : le chemin de ce fichier est préfixé par la valeur "sysroot", si elle est définie, puis par toute chaîne "prefix" si l'éditeur de liens a été configuré avec l'option --prefix=<path>.
8.
Pour un éditeur de liens natif sur un système FreeBSD, tous les répertoires spécifiés par la macro "_PATH_ELF_HINTS" définie dans le fichier d'en-tête elf-hints.h.
9.
Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'éditeur de liens fourni sur la ligne de commande, y compris les scripts spécifiés par -T (mais pas -dT).
10.
Les répertoires par défaut, normalement /lib et /usr/lib.
11.
Tous les répertoires spécifiés par un LDPT_SET_EXTRA_LIBRARY_PATH de plugin.
12.
Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'éditeur de liens par défaut.

Notez cependant sur les systèmes basés sur Linux qu'il y a une mise en garde supplémentaire : Si l'option --as-needed est active et qu'une bibliothèque partagée est trouvée qui satisferait normalement la recherche et que cette bibliothèque n'a pas la balise DT_NEEDED pour libc.so et qu'une bibliothèque partagée se trouve plus loin dans l'ensemble des répertoires de recherche qui satisfait également la recherche et que cette deuxième bibliothèque a une balise DT_NEEDED pour libc.so alors la deuxième bibliothèque sera sélectionnée au lieu de la première.

Si la bibliothèque partagée requise n'est pas trouvée, l'éditeur de liens émettra un avertissement et continuera la liaison.

--section-ordering-file=script
Cette option est utilisée pour augmenter le script d'éditeur de liens actuel avec un mappage supplémentaire des sections d'entrée vers les sections de sortie. Ce fichier doit utiliser la même syntaxe pour "SECTIONS" que celle utilisée dans les scripts d'éditeur de liens normaux, mais il ne doit rien faire d'autre que de placer les sections d'entrée dans les sections de sortie. @pxref{SECTIONS}

Une deuxième contrainte sur le script d'ordonnancement des sections est qu'il ne peut faire référence qu'à des sections de sortie déjà définies par le script d'éditeur de liens actuellement utilisé. (C'est-à-dire le script d'éditeur de liens par défaut ou un script spécifié sur la ligne de commande). L'avantage du script d'ordonnancement des sections est cependant que les sections d'entrée sont mappées au début des sections de sortie, de sorte qu'elles peuvent garantir l'ordonnancement des sections dans la section de sortie. Par exemple, imaginez que le script d'éditeur de liens par défaut ressemble à ceci :

SECTIONS {
  .text : { *(.text.hot) ; *(.text .text.*) }
  .data : { *(.data.big) ; *(.data .data.*) }
  }

Ensuite, si un fichier d'ordonnancement de sections comme celui-ci est utilisé :

.text : { *(.text.first) ; *(.text.z*) }
.data : { foo.o(.data.first) ; *(.data.small) }

Cela équivaudrait à un script d'éditeur de liens comme celui-ci :

SECTIONS {
  .text : { *(.text.first) ; *(.text.z*) ; *(.text.hot) ; *(.text .text.*) }
  .data : { foo.o(.data.first) ; *(.data.small) ; *(.data.big) ; *(.data .data.*) }
  }

L'avantage du fichier d'ordonnancement des sections est qu'il peut être utilisé pour ordonner les sections qui importent à l'utilisateur sans avoir à se soucier des autres sections, des régions mémoire, ou de quoi que ce soit d'autre.

--stats[=filename]
Calcule et affiche des statistiques sur le fonctionnement de l'éditeur de liens, telles que le temps d'exécution et l'utilisation de la mémoire.

Si l'argument facultatif filename n'est pas fourni, alors seules les informations de base sont rapportées, et elles sont envoyées au flux de sortie d'erreur standard. Si l'argument filename est fourni, alors des informations étendues sont écrites dans le fichier nommé. Si filename est défini à simplement le symbole - , alors les informations étendues sont envoyées au flux de sortie standard. Si filename commence par + , alors le fichier est ouvert en mode ajout plutôt qu'en mode écrasement.

Si l'option -Map a été activée, alors les informations sont également enregistrées dans le fichier de carte. Remarque : si à la fois l'option --stats et les options -Map ont reçu des arguments filename qui correspondent, alors les informations ne seront écrites qu'une seule fois et non deux.

Si la variable d'environnement "LD_STATS" est définie, alors cela se comporte comme l'option --stats . Si la valeur de la variable est une chaîne de caractères, alors celle-ci sera utilisée comme nom d'un fichier dans lequel les informations doivent être enregistrées. Sinon, les informations seront envoyées au flux de sortie standard. L'utilisation de la variable d'environnement permet d'enregistrer les statistiques sans avoir à modifier la ligne de commande de l'éditeur de liens. Remarque : si à la fois la variable d'environnement et l'option --stats sont utilisées, alors l'option --stats a la priorité.

De plus, les informations sont également rapportées pour une phase spéciale appelée ALL qui couvre l'ensemble du processus de liaison. Notez que les phases individuelles peuvent se contenir ou se chevaucher, il ne faut donc pas supposer que les ressources globales utilisées par l'éditeur de liens sont la somme des ressources utilisées par les phases individuelles.

De plus, lorsque des informations étendues sont rapportées, la version de l'éditeur de liens, les arguments de la ligne de commande et l'heure de démarrage de l'éditeur de liens sont également inclus. Ce message apparaît lorsque certaines (sous-)expressions accèdent à une adresse finalement donnée par la somme de deux constantes (les tables d'importation Win32 n'en permettent qu'une seule). Les cas où cela peut se produire incluent les accès aux champs de membre de variables de structure importées depuis une DLL, ainsi que l'utilisation d'un index constant dans une variable de tableau importée depuis une DLL. Toute variable multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée problématique, ld le détectera toujours, émettra l'avertissement et

terminera.

Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée

:

Une façon est d'utiliser l'option --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client pour l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette

La cible C6X uClinux utilise un format binaire appelé DSBT pour prendre en charge les bibliothèques partagées. Chaque bibliothèque partagée du système doit avoir un indice unique ; tous les exécutables utilisent un indice de 0.

--dsbt-size taille
Cette option définit le nombre d'entrées dans le DSBT de l'exécutable ou de la bibliothèque partagée actuelle à taille. La valeur par défaut est de créer une table avec 64 entrées.
--dsbt-index indice
Cette option définit l'indice DSBT de l'exécutable ou de la bibliothèque partagée actuelle à indice. La valeur par défaut est 0, ce qui convient à la génération d'exécutables. Le commutateur --no-merge-exidx-entries désactive la fusion des entrées exidx adjacentes dans les informations de déroulement de pile.

--branch-stub
Cette option active la relaxation de branche par l'éditeur de liens en insérant des sections de souche de branche si nécessaire pour étendre la portée des branches. Cette option n'est généralement pas requise car C-SKY prend en charge les instructions de branche et d'appel qui peuvent accéder à la portée mémoire complète et la relaxation de branche est normalement gérée par le compilateur ou l'assembleur.
--stub-group-size=N
Cette option permet un contrôle plus fin de la création de souches de branche par l'éditeur de liens. Elle définit la taille maximale d'un groupe de sections d'entrée qui peuvent être gérées par une section de souche. Une valeur négative de N place les sections de souche après leurs branches, tandis qu'une valeur positive permet aux sections de souche d'apparaître avant ou après les branches. Les valeurs de 1 ou -1 indiquent que l'éditeur de liens doit choisir des valeurs par défaut appropriées.

Pour la cible pdp11-aout, trois variantes du format de sortie peuvent être produites comme sélectionnées par les options suivantes. La variante par défaut pour pdp11-aout est l'option --omagic, tandis que pour d'autres cibles, --nmagic est la valeur par défaut. L'option --imagic est définie uniquement pour la cible pdp11-aout, tandis que les autres sont décrites ici telles qu'elles s'appliquent à la cible pdp11-aout.

-N
--omagic
Marque la sortie comme "OMAGIC" (0407) dans l'en-tête a.out pour indiquer que le segment de texte ne doit pas être protégé en écriture et partagé. Comme les segments de texte et de données sont tous deux lisibles et inscriptibles, le segment de données est alloué immédiatement après le segment de texte. C'est le format le plus ancien pour les programmes exécutables PDP11 et c'est le comportement par défaut de ld sur les systèmes Unix PDP11 depuis le début jusqu'à 2.11BSD.
-n
--nmagic
Marque la sortie comme "NMAGIC" (0410) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, la partie texte sera en lecture seule et partageable entre tous les processus exécutant le même fichier. Cela implique de déplacer les zones de données jusqu'à la première limite de page de 8 Ko possible suivant la fin du texte. Cette option crée un format d'exécutable pur.
-z
--imagic
Marque la sortie comme "IMAGIC" (0411) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, les zones de texte et de données du programme seront chargées dans des espaces d'adressage séparés à l'aide de la fonctionnalité d'instruction et d'espace de données fractionnés de l'unité de gestion mémoire dans les modèles plus grands du PDP11. Cela double l'espace d'adressage disponible pour le programme. Le segment de texte est à nouveau pur, protégé en écriture et partageable. La seule différence dans le format de sortie entre cette option et les autres, outre le nombre magique, est que les segments de texte et de données commencent tous deux à l'emplacement 0. L'option -z sélectionnait ce format dans 2.11BSD. Cette option crée un format exécutable séparé.
--no-omagic
Équivalent à --nmagic pour pdp11-aout.

ENVIRONNEMENT

Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

"GNUTARGET" détermine le format objet des fichiers d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers d'entrée binaires ; cette méthode réussit souvent, mais il existe des ambiguïtés potentielles, car il n'existe aucun moyen de garantir que le nombre magique utilisé pour spécifier les formats de fichiers objet est unique. Cependant, la procédure de configuration de BFD sur chaque système place le format conventionnel pour ce système en première position dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

"LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement de l'éditeur de liens, en particulier le script de l'éditeur de liens par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

Normalement, l'éditeur de liens ne démanglera pas les symboles par défaut. Cependant, si "COLLECT_NO_DEMANGLE" est défini dans l'environnement, alors il ne démanglera pas les symboles par défaut. Cette variable d'environnement est utilisée dans un

de manière similaire par le "gcc" programme enveloppe de l'éditeur de liens. La valeur par défaut peut être remplacée par les --demangle et --no-demangle options.

Si l'option spécifique PE/COFF --insert-timestamp est active et que la SOURCE_DATE_EPOCH variable d'environnement est définie, alors la valeur d'horodatage dans cette variable sera insérée dans l'en-tête COFF au lieu de l'heure actuelle.

Si la "LD_STATS" variable d'environnement est définie, alors des informations sur l'utilisation des ressources de l'éditeur de liens seront enregistrées, comme si l'option --stats avait été utilisée. Si la variable "LD_STATS" a une valeur de chaîne alors celle-ci sera utilisée comme nom d'un fichier dans lequel les informations doivent être stockées. Sinon, les informations seront envoyées au flux de sortie standard.
