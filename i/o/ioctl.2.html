ioctl(2) Manuel des appels système ioctl(2)

NOM

ioctl - contrôler un périphérique

BIBLIOTHÈQUE

Bibliothèque C standard (libc,-lc)

SYNOPSIS

#include <sys/ioctl.h>
int ioctl(int fd, unsigned long op, ...);  /* glibc, BSD */
int ioctl(int fd, int op, ...);            /* musl, other UNIX */

DESCRIPTION

L'appel système ioctl() manipule les paramètres sous-jacents du périphérique des fichiers spéciaux. En particulier, de nombreuses caractéristiques de fonctionnement des fichiers spéciaux de type caractère (par ex. les terminaux) peuvent être contrôlées avec des opérations ioctl(). L'argument fd doit être un descripteur de fichier ouvert.

Le deuxième argument est un code d'opération dépendant du périphérique. Le troisième argument est un pointeur non typé vers la mémoire. Il est traditionnellement char *argp (de l'époque où void * n'était pas un C valide), et sera ainsi nommé pour cette discussion.

Un ioctl() op encode si l'argument est un paramètre in (entrée) ou un paramètre out (sortie), ainsi que la taille de l'argument argp en octets. Les macros et définitions utilisées pour spécifier un ioctl() op se trouvent dans le fichier <sys/ioctl.h>. Voir NOTES.

VALEUR RENVOYÉE

Habituellement, zéro est renvoyé en cas de succès. Quelques opérations ioctl() utilisent la valeur de retour comme paramètre de sortie et renvoient une valeur non négative en cas de succès. En cas d'erreur, -1 est renvoyé, et errno est défini pour indiquer l'erreur.

ERREURS

EBADF
fd n'est pas un descripteur de fichier valide.
EFAULT
argp référence une zone mémoire inaccessible.
EINVAL
op ou argp n'est pas valide.
ENOTTY
fd n'est pas associé à un périphérique de type caractère.
ENOTTY
L'opération spécifiée ne s'applique pas au type d'objet que le descripteur de fichier fd référence.

VERSIONS

Les arguments, les retours et la sémantique de ioctl() varient selon le pilote de périphérique en question (l'appel est utilisé comme solution universelle pour les opérations qui ne s'intègrent pas proprement dans le modèle d'E/S de flux UNIX).

NORMES

Aucune.

HISTORIQUE

La version 7 AT&T UNIX a 

ioctl(int fd, int op, struct sgttyb *argp);

(où struct sgttyb a historiquement été utilisé par stty(2) et gtty(2), et est polymorphe selon le type d'opération (comme un void * l'aurait été, s'il avait été disponible)).

SysIII documente arg sans aucun type.

4.3BSD a 

ioctl(int d, unsigned long op, char *argp);

(avec char * de la même manière à la place de void *).

SysVr4 a 

int ioctl(int fd, int op, ...  /* arg */);

NOTES

Afin d'utiliser cet appel, on a besoin d'un descripteur de fichier ouvert. Souvent l'appel open(2) a des effets de bord indésirables, qui peuvent être évités sous Linux en lui donnant l'indicateur O_NONBLOCK .

Structure ioctl

Les valeurs op d'ioctl sont des constantes de 32 bits. En principe, ces constantes sont complètement arbitraires, mais les gens ont essayé d'y intégrer une certaine structure.

L'ancienne situation sur Linux était celle de constantes principalement sur 16 bits, où le dernier octet est un numéro de série, et l'octet (ou les octets) précédent donnent un type indiquant le pilote. Parfois le numéro majeur était utilisé : 0x03 pour les HDIO_* ioctls, 0x06 pour les LP* ioctls. Et parfois une ou plusieurs lettres ASCII étaient utilisées. Par exemple, TCGETS a la valeur 0x00005401, avec 0x54 = 'T' indiquant le pilote de terminal, et CYGETTIMEOUT a la valeur 0x00435906, avec 0x43 0x59 = 'C' 'Y' indiquant le pilote cyclades.

Plus tard (0.98p5), plus d'informations ont été intégrées dans le nombre. On a 2 bits de direction (00 : aucun, 01 : écriture, 10 : lecture, 11 : lecture/écriture) suivis de 14 bits de taille (donnant la taille de l'argument), suivis d'un type sur 8 bits (regroupant les ioctls en groupes pour un usage commun ou un pilote commun), et un numéro de série sur 8 bits.

Les macros décrivant cette structure se trouvent dans <asm/ioctl.h> et sont _IO(type,nr) et {_IOR,_IOW,_IOWR}(type,nr,size). Elles utilisent sizeof(size) de sorte que size est un nom inapproprié ici : ce troisième argument est un type de données.

Notez que les bits de taille sont très peu fiables : dans de nombreux cas ils sont erronés, soit à cause de macros défectueuses utilisant sizeof(sizeof(struct)), soit à cause de valeurs héritées.

Ainsi, il semble que la nouvelle structure n'ait apporté que des inconvénients : elle n'aide pas à la vérification, mais elle provoque des valeurs variables selon les différentes architectures.
