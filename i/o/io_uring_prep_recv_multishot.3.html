NOM

io_uring_prep_recv - préparer une requête de réception

SYNOPSIS

#include <liburing.h>
void io_uring_prep_recv(struct io_uring_sqe *sqe,
                        int sockfd,
                        void *buf,
                        size_t len,
                        int flags);
void io_uring_prep_recv_multishot(struct io_uring_sqe *sqe,
                                  int sockfd,
                                  void *buf,
                                  size_t len,
                                  int flags);

DESCRIPTION

La fonction io_uring_prep_recv(3) prépare une requête de réception. L'entrée de la file d'attente de soumission sqe est configurée pour utiliser le descripteur de fichier sockfd afin de commencer à recevoir les données dans le tampon de destination buf d'une taille de len et avec les indicateurs modificateurs flags.

Cette fonction prépare une requête asynchrone de recv(2). Voir cette page de manuel pour les détails sur les arguments spécifiés à cette aide à la préparation.

La version multishot permet à l'application d'émettre une seule requête de réception, qui publie à plusieurs reprises une CQE lorsque des données sont disponibles. Elle nécessite que la longueur soit de 0, que l'indicateur IOSQE_BUFFER_SELECT soit défini et que l'indicateur MSG_WAITALL ne soit pas défini. Par conséquent, chaque CQE prendra un tampon provenant d'un pool de tampons fourni pour la réception. L'application doit vérifier les indicateurs de chaque CQE, indépendamment de son résultat. Si une CQE publiée n'a pas l'indicateur IORING_CQE_F_MORE défini, alors la réception multishot est terminée et l'application doit émettre une nouvelle requête si elle souhaite toujours recevoir des données du socket. Les variantes multishot sont disponibles depuis le noyau 6.0.

Après avoir appelé cette fonction, des indicateurs modificateurs internes supplémentaires d'io_uring peuvent être définis dans le champ ioprio de la SQE. Les indicateurs suivants sont pris en charge :

IORING_RECVSEND_POLL_FIRST
Si défini, io_uring supposera que le socket est actuellement vide et que toute tentative de réception de données échouera. Dans ce cas, io_uring activera le sondage interne et déclenchera une réception des données lorsque le socket aura des données à lire. Cette première tentative de réception peut être coûteuse dans le cas où le socket est censé être vide ; définir cet indicateur évitera la première tentative de réception et passera directement à l'activation du sondage. Si le sondage indique que des données sont prêtes à être reçues, l'opération se poursuivra.

Peut être utilisé avec l'indicateur de CQE IORING_CQE_F_SOCK_NONEMPTY, que io_uring définira sur les CQE après une opération recv(2) ou recvmsg(2). Si défini, le socket avait encore des données à lire après la fin de l'opération. Ces deux indicateurs sont disponibles depuis la version 5.19.

IORING_RECVSEND_BUNDLE
Si défini et que des tampons fournis sont utilisés avec IOSQE_BUFFER_SELECT , l'opération de réception tentera de remplir plusieurs tampons plutôt que de simplement en choisir un seul à remplir. Pour recevoir plusieurs tampons en une seule réception, l'ID de groupe de tampons défini dans la SQE doit être du type de bague fourni. S'il est défini, le champ res de la CQE indique le nombre total d'octets reçus, et l'ID de tampon retourné dans le champ flags de la CQE indique le premier tampon de l'opération de réception. L'application doit traiter l'ID de tampon initial indiqué et jusqu'à ce que tous les octets res aient été vus pour savoir quel est le dernier tampon de l'opération de réception. Les tampons consommés seront contigus à partir du tampon initial, dans l'ordre où ils apparaissent dans la bague de tampons. La structure CQE ne contient pas la position du tampon dans la bague de tampons, par conséquent, afin d'identifier les tampons contenus par le paquet, il est conseillé de maintenir l'index de tête mis en cache par bague de tampon. Cet index uint16_t représente la position du prochain tampon à consommer dans la bague. Lors de l'achèvement d'une opération de réception, l'index de tête mis en cache doit être incrémenté en conséquence. La réception en paquets peut améliorer les performances lorsque plus d'un bloc de données est disponible pour la réception, en éliminant les allers-retours redondants dans la pile réseau. Les paquets de réception peuvent être utilisés par les opérations de réception à coup unique et multishot. Notez qu'en interne, les paquets reposent sur la pile réseau qui renvoie la quantité de données restantes dans le socket après la réception initiale. Cela signifie que la réception initiale peut contenir moins de paquets que ce qui est disponible, les réceptions suivantes (followup) contenant plus de paquets. Disponible depuis la version 6.10.

VALEUR DE RETOUR

Aucune

ERREURS

Le champ res de la CQE contiendra le résultat de l'opération. Voir la page de manuel associée pour les détails sur les valeurs possibles. Notez que là où les appels système synchrones renvoient -1 en cas d'échec et définissent errno à la valeur d'erreur réelle, io_uring n'utilise jamais errno. Au lieu de cela, il renvoie directement l'errno négativé dans le champ res de la CQE.
