NOM

io_uring_prep_recvmsg - prépare une requête recvmsg

SYNTAXE

#include <sys/types.h>
#include <sys/socket.h>
#include <liburing.h>
void io_uring_prep_recvmsg(struct io_uring_sqe *sqe,
                           int fd,
                           struct msghdr *msg,
                           unsigned flags);
void io_uring_prep_recvmsg_multishot(struct io_uring_sqe *sqe,
                                     int fd,
                                     struct msghdr *msg,
                                     unsigned flags);

DESCRIPTION

La fonction io_uring_prep_recvmsg(3) prépare une requête recvmsg. L'entrée de la file d'attente de soumission sqe est configurée pour utiliser le descripteur de fichier fd afin de commencer à recevoir les données indiquées par msg avec les drapeaux recvmsg(2) définis dans l'argument flags.

Cette fonction prépare une requête recvmsg(2) asynchrone. Voir cette page de manuel pour les détails sur les arguments spécifiés à cette fonction d'aide à la préparation.

La version multishot permet à l'application d'émettre une seule requête de réception, qui publie répétitivement un CQE lorsque des données sont disponibles. Elle nécessite que le drapeau IOSQE_BUFFER_SELECT soit défini et qu'aucun drapeau MSG_WAITALL ne soit défini. Par conséquent, chaque CQE retirera un tampon d'un pool de tampons fourni pour la réception. L'application doit vérifier les drapeaux de chaque CQE, quel que soit son résultat. Si un CQE publié n'a pas le drapeau IORING_CQE_F_MORE défini, alors la réception multishot est terminée et l'application doit émettre une nouvelle requête si elle souhaite toujours recevoir des données du socket.

Contrairement à recvmsg(2), multishot recvmsg préfixera un struct io_uring_recvmsg_out qui décrit la disposition du reste du tampon en combinaison avec le struct msghdr initial soumis avec la requête. Voir io_uring_recvmsg_out(3) pour plus d'informations sur l'accès aux données.

Les variantes multishot sont disponibles depuis le noyau 6.0.

Après avoir appelé cette fonction, des drapeaux modificateurs internes supplémentaires io_uring peuvent être définis dans le champ ioprio du SQE. Les drapeaux suivants sont pris en charge :

IORING_RECVSEND_POLL_FIRST
S'il est défini, io_uring supposera que le socket est actuellement vide et que toute tentative de réception de données échouera. Dans ce cas, io_uring armera le poll interne et déclenchera une réception des données lorsque le socket aura des données à lire. Cette tentative de réception initiale peut être inutile dans le cas où le socket est censé être vide, définir ce drapeau contournera la tentative de réception initiale et passera directement à l'armement du poll. Si le poll indique que des données sont prêtes à être reçues, l'opération se poursuivra.

Peut être utilisé avec le drapeau CQE IORING_CQE_F_SOCK_NONEMPTY, que io_uring définira sur les CQE après une opération recv(2) ou recvmsg(2). S'il est défini, le socket avait encore des données à lire après la fin de l'opération. Ces deux drapeaux sont disponibles depuis 5.19.

VALEUR DE RETOUR

Aucune

ERREURS

Le champ res du CQE contiendra le résultat de l'opération. Voir la page de manuel correspondante pour les détails sur les valeurs possibles. Notez que là où les appels système synchrones renverront -1 en cas d'échec et définiront errno à la valeur d'erreur réelle, io_uring n'utilise jamais errno. Au lieu de cela, il renvoie l'errno négativé directement dans le champ res du CQE.

NOTES

Comme pour toute requête qui transmet des données dans une structure, ces données doivent rester valides jusqu'à ce que la requête ait été soumise avec succès. Elles n'ont pas besoin de rester valides jusqu'à la complétion. Une fois qu'une requête a été soumise, l'état dans le noyau est stable. Les premiers noyaux (5.4 et antérieurs) nécessitaient que l'état reste stable jusqu'à la complétion. Les applications peuvent tester ce comportement en inspectant le drapeau IORING_FEAT_SUBMIT_STABLE renvoyé par io_uring_queue_init_params(3).
