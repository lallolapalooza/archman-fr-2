DESCRIPTIO

N

La fonction io_uring_prep_send(3) prépare une requête d'envoi. L'entrée de la file de soumission sqe est configurée pour utiliser le descripteur de fichier sockfd afin de commencer à envoyer les données de buf de taille len octets et avec les indicateurs modificateurs flags

.

Après l'appel de cette fonction, des indicateurs modificateurs internes supplémentaires à io_uring peuvent être définis dans le champ ioprio de la SQE. Les indicateurs suivants sont pris en charge

:
IORING_RECVSEND_POLL_FI
RST
S'il est défini, io_uring supposera que le socket est actuellement plein et que la tentative d'envoi de données échouera. Dans ce cas, io_uring armera le poll interne et déclenchera l'envoi des données lorsque le socket aura de l'espace disponible. Si le poll indique que de l'espace est disponible dans le socket, l'opération se poursuivra
immédiatement.
IORING_RECVSEND_BUN
DLE
S'il est défini, l'opération d'envoi tentera de remplir plusieurs tampons plutôt que de simplement en choisir un seul à remplir. Pour envoyer plusieurs tampons dans un seul envoi, l'ID de groupe de tampons défini dans la SQE doit être du type fourni par la ring. S'il est défini, le champ res de la CQE indique le nombre total d'octets envoyés, et l'ID de tampon renvoyé dans le champ flags de la CQE indique le premier tampon de l'opération d'envoi. L'application doit traiter l'ID de tampon initial indiqué jusqu'à ce que tous les res octets aient été vus pour savoir quel est le dernier tampon de l'opération d'envoi. Les tampons consommés seront contigus à partir du tampon initial, dans l'ordre dans lequel ils apparaissent dans la ring de tampons. La structure CQE ne contient pas la position du tampon dans la ring de tampons ; par conséquent, afin d'identifier les tampons contenus par le bundle, il est conseillé de maintenir l'index de tête en cache par ring de tampons. Cet index uint16_t représente la position du prochain tampon à consommer dans la ring. Lors de la fin de l'opération d'envoi par bundle, l'index de tête en cache doit être incrémenté en conséquence. L'envoi par bundles peut améliorer les performances lorsqu'il y a plus d'un morceau de données disponible en éliminant les allers-retours redondants à travers la pile
réseau.
IORING_SEND_VECTORI
ZED
S'il est défini, addr doit pointer vers un tableau de struct iovec et len doit être le nombre de vecteurs dans ce tableau. Cela permet l'utilisation de l'E/S vectorisée p
our une opération d'envoi normale, au lieu d'avoir bes
oin d'une variante sendmsg pour accomplir cela.

Notez que l'utilisation de IOSQE_IO_LINK avec ce type de requête nécessite la définition de MSG_WAITALL dans l'argument flags, car un envoi partiel n'est pas considéré comme une condition d'erreur sans que cela soit

défini.

Cette fonction prépare une requête send(2) asynchrone. Voir cette page man pour plus de

détails.

La fonction io_uring_prep_sendto(3) prépare une requête sendto. L'entrée de la file de soumission sqe est configurée pour utiliser le descripteur de fichier sockfd afin de commencer à envoyer les données de buf de taille len octets et avec les indicateurs modificateurs flags. L'adresse de destination est spécifiée par addr et addrlen et doit être une adresse valide pour le type de

socket.

Cette fonction prépare une requête sendto(2) asynchrone. Voir cette page man pour plus de

détails.

Les deux variantes d'envoi ci-dessus peuvent être utilisées avec des tampons fournis, où, plutôt que de passer un tampon directement avec la requête, IOSQE_BUFFER_SELECT est défini dans le champ flags de la SQE, et de plus un ID de groupe de tampons est défini dans le champ buf_group de la SQE. En utilisant des tampons fournis avec les requêtes d'envoi, l'application peut empêcher tout type de réordonnancement des données sortantes qui pourrait autrement survenir si l'application a plus d'une requête d'envoi en vol pour un même socket. Cela fournit un meilleur pipelining des données, là où auparavant l'application devait sérialiser manuellement les

envois.

La version bundle permet à l'émettre une seule requête d'envoi, avec un ID de groupe de tampons donné dans le champ buf_group de la SQE, qui continue d'envoyer depuis ce groupe de tampons jusqu'à ce qu'il n'ait plus de tampons. Comme pour toute autre requête utilisant des tampons fournis, IOSQE_BUFFER_SELECT doit également être défini dans le champ flags de la SQE avant la soumission. Actuellement, len doit être donné comme 0, sinon la requête sera erronée avec -EINVAL comme code de résultat. Les versions futures pourront permettre de définir pour limiter la taille du transfert. Une seule CQE est publiée pour l'envoi, avec comme résultat le nombre d'octets envoyés, en cas de succès. Lorsqu'il est utilisé avec des tampons fournis, l'envoi ou l'envoi par bundle contiendra l'ID de groupe de tampons de départ dans le champ flags de la CQE. Le nombre d'octets envoyés commence à partir de là, et sera dans des ID de tampons contigus après cela. L'envoi par bundle, et l'envoi avec des tampons fournis en général, sont disponibles depuis le noyau 6.10, et peuvent être plus précisément identifiés en vérifiant la présence de l'indicateur IORING_FEAT_SEND_BUF_SELECT renvoyé lors de l'utilisation de io_uring_init_queue_params(

3) pour confi
gurer la ring.

Le champ res de la CQE contiendra le résultat de l'opération. Voir la page man correspondante pour plus de détails sur les valeurs possibles.
