io_uring(7) Manuel du programmeur Linux io_uring(7)

NOM

io_uring - Fonctionnalité d'E/S asynchrones

SYNOPSIS

#include <linux/io_uring.h>

DESCRIPTION

io_uring est une API spécifique à Linux pour les E/S asynchrones. Elle permet à l'utilisateur de soumettre une ou plusieurs requêtes d'E/S, qui sont traitées de manière asynchrone sans bloquer le processus appelant. io_uring tire son nom des tampons circulaires (ring buffers) qui sont partagés entre l'espace utilisateur et l'espace noyau. Cette disposition permet des E/S efficaces, tout en évitant la surcharge de la copie des tampons entre les deux, lorsque c'est possible. Cette interface rend io_uring différent des autres API d'E/S UNIX, où, plutôt que de simplement communiquer entre le noyau et l'espace utilisateur avec des appels système, des tampons circulaires sont utilisés comme mode principal de communication. Cette disposition présente divers avantages en termes de performances qui sont discutés dans une section séparée ci-dessous. Cette page man utilise les termes tampons partagés, tampons circulaires partagés et files d'attente de manière interchangeable.

Le modèle de programmation général que vous devez suivre pour io_uring est décrit ci-dessous

  • Configurez les tampons partagés avec io_uring_setup(2) et mmap(2), en faisant le mappage dans l'espace utilisateur des tampons partagés pour la file d'attente de soumission (SQ) et la file d'attente d'achèvement (CQ). Vous placez les requêtes d'E/S que vous voulez effectuer sur la SQ, tandis que le noyau place les résultats de ces opérations sur la CQ.
  • Pour chaque requête d'E/S que vous devez effectuer (comme lire un fichier, écrire un fichier, accepter une connexion de socket, etc.), vous créez une entrée de file d'attente de soumission, ou SQE, décrivez l'opération d'E/S que vous devez faire effectuer et l'ajoutez à la queue de la file d'attente de soumission (SQ). Chaque opération d'E/S est, en essence, l' équivalent d'un appel système que vous auriez fait autrement, si vous n'utilisiez pas io_uring. Par exemple, une SQE avec l' opcode défini à IORING_OP_READ demandera l'émission d'une opération de lecture qui est similaire à l' appel système read(2) . Consultez la documentation des opcodes dans io_uring_enter(2) pour tous les opcodes pris en charge et leurs propriétés. Vous pouvez ajouter plus d'une SQE à la file d'attente en fonction du nombre d'opérations que vous voulez demander.
  • Après avoir ajouté une ou plusieurs SQEs, vous devez appeler io_uring_enter(2) pour dire au noyau de défiler vos requêtes d'E/S hors de la SQ et de commencer à les traiter.
  • Pour chaque SQE que vous soumettez, une fois qu'il a fini de traiter la requête, le noyau place un événement de file d'attente d'achèvement ou CQE à la queue de la file d'attente d'achèvement ou CQ. Le noyau place exactement une CQE correspondante dans la CQ pour chaque SQE que vous soumettez sur la SQ. Après avoir récupéré une CQE, au minimum, vous pourriez vouloir vérifier le champ res de la structure CQE, qui correspond à la valeur de retour de l'équivalent de l'appel système, si vous l'aviez utilisé directement sans utiliser io_uring. Étant donné que io_uring est une interface asynchrone, errno n'est jamais utilisé pour transmettre des informations d'erreur. À la place, res contiendra ce que l'appel système équivalent aurait retourné en cas de succès, et en cas d'erreur res contiendra -errno. Par exemple, si l'appel système read normal avait retourné -1 et défini errno à EINVAL, alors res contiendrait -EINVAL. Si l'appel système normal avait retourné une taille de lecture de 1024, alors res contiendrait 1024.
  • De manière optionnelle, io_uring_enter(2) peut aussi attendre qu'un nombre spécifié de requêtes soit traité par le noyau avant de retourner. Si vous spécifiez un certain nombre d'achèvements à attendre, le noyau aura placé au moins ce nombre de CQEs sur la CQ, que vous pouvez alors lire facilement, juste après le retour de io_uring_enter(2).
  • Il est important de se rappeler que les requêtes d'E/S soumises au noyau peuvent se terminer dans n'importe quel ordre. Il n'est pas nécessaire que le noyau traite une requête après l'autre, dans l'ordre où vous les avez placées. Étant donné que l'interface est un anneau, les requêtes sont tentées dans l'ordre, cependant cela n'implique aucun type d'ordre sur leur exécution ou leur achèvement. Lorsque plus d'une requête est en vol, il n'est pas possible de déterminer laquelle s'exécutera ou se terminera en premier. Lorsque vous défilez des CQEs hors de la CQ, vous devez toujours vérifier à quelle requête soumise elle correspond. La méthode la plus courante pour ce faire est d'utiliser le champ user_data dans la requête, qui est transmis côté achèvement.
  • Concrètement, pour les opérations où un ordonnancement strict est requis, comme pour les envois et les réceptions sur un socket TCP orienté flux, il est généralement peu sûr d'avoir plus d'un envoi en attente, ou plus d'une réception en attente (les deux directions sont indépendantes) sur un socket donné à la fois, car le noyau peut réordonner leur exécution si l'armement de poll ou d'autres activités de fond du noyau sont impliquées. Cependant, io_uring fournit diverses fonctionnalités pour permettre aux applications de mettre en pipeline efficacement leurs opérations de manière sûre. Si les requêtes sont soumises dans un seul lot, l'application peut utiliser IOSQE_IO_LINK pour imposer un ordre d'exécution dans le noyau. Sinon, io_uring fournit des fonctionnalités avancées comme multi shot et les bundles d'envoi/réception pour permettre aux applications de fournir plus de données en moins de trajets, plus efficaces, vers le noyau. Même si ces fonctionnalités sont utilisées, les applications doivent toujours s'assurer qu'elles ne se chevauchent pas entre différents envois ou différentes réceptions sur un fichier donné.

Ajouter à et lire depuis les files d'attente :

  • Vous ajoutez des SQEs à la queue de la SQ. Le noyau lit les SQEs depuis la tête de la file d'attente.
  • Le noyau ajoute des CQEs à la queue de la CQ. Vous lisez les CQEs depuis la tête de la file d'attente.

Il convient de noter que selon la configuration, le comportement de io_uring peut dévier du comportement décrit ci-dessus, comme ne pas publier une CQE pour chaque SQE lors du réglage de IOSQE_CQE_SKIP_SUCCESS dans la SQE ou publier plusieurs CQEs pour une seule SQE pour des opérations multi shot ou nécessiter un appel système io_uring_enter(2) pour faire commencer au noyau le traitement des SQEs nouvellement ajoutées lors de l'utilisation du sondage de la file d'attente de soumission.

Sondage de la file d'attente de soumission

L'un des objectifs de io_uring est de fournir un moyen pour des E/S efficaces. À cette fin, io_uring prend en charge un mode de sondage qui vous permet d'éviter l'appel à io_uring_enter(2), que vous utilisez pour informer le noyau que vous avez mis en file d'attente des SQEs sur la SQ. Avec le sondage SQ, io_uring démarre un thread de noyau qui sonde la file d'attente de soumission pour toutes les requêtes d'E/S que vous soumettez en ajoutant des SQEs. Avec le sondage SQ activé, il n'est pas nécessaire que vous appeliez io_uring_enter(2), vous permettant d'éviter la surcharge des appels système. Un thread de noyau désigné défile les SQEs hors de la SQ à mesure que vous les ajoutez et les distribue pour un traitement asynchrone.

Configuration de io_uring

Les étapes principales pour configurer io_uring consistent à faire le mappage des tampons partagés avec des appels mmap(2) . Dans le programme d'exemple inclus dans cette page man, la fonction app_setup_uring() configure io_uring avec une file d'attente de soumission de profondeur QUEUE_DEPTH. Faites attention aux 2 appels mmap(2) qui configurent les files d'attente de soumission et d'achèvement partagées. Si votre noyau est plus ancien que la version 5.4, trois appels mmap(2) sont requis.

Soumission de requêtes d'E/S

Le processus de soumission d'une requête consiste à décrire l'opération d'E/S que vous devez faire effectuer en utilisant une instance de structure io_uring_sqe . Ces détails décrivent l'appel système équivalent et ses paramètres. Parce que la gamme des opérations d'E/S que Linux prend en charge est très variée et que la structure io_uring_sqe doit être capable de les décrire, elle a plusieurs champs, certains regroupés dans des unions pour une efficacité spatiale. Voici une version simplifiée de struct io_uring_sqe avec certains des champs les plus souvent utilisés :


struct io_uring_sqe {
        __u8    opcode;         /* type d'opération pour cette sqe */
        __s32   fd;             /* descripteur de fichier sur lequel faire des E/S */
        __u64   off;            /* décalage dans le fichier */
        __u64   addr;           /* pointeur vers un tampon ou des iovecs */
        __u32   len;            /* taille du tampon ou nombre d'iovecs */

        __u64   user_data;      /* données à renvoyer au moment de l'achèvement */
        __u8    flags;          /* drapeaux IOSQE_ */
        ...
};

Voici la structure io_uring_sqe en entier :


struct io_uring_sqe {
	__u8	opcode;		/* type d'opération pour cette sqe */
	__u8	flags;		/* drapeaux IOSQE_ */
	__u16	ioprio;		/* ioprio pour la requête */
	__s32	fd;		/* descripteur de fichier sur lequel effectuer l'E/S */
	union {
		__u64	off;	/* décalage dans le fichier */
		__u64	addr2;
		struct {
			__u32	cmd_op;
			__u32	__pad1;
		};
	};
	union {
		__u64	addr;	/* pointeur vers le tampon ou les iovecs */
		__u64	splice_off_in;
		struct {
			__u32	level;
			__u32	optname;
		};
	};
	__u32	len;		/* taille du tampon ou nombre d'iovecs */
	union {
		__kernel_rwf_t	rw_flags;
		__u32		fsync_flags;
		__u16		poll_events;	/* compatibilité */
		__u32		poll32_events;	/* inversé par mots pour BE */
		__u32		sync_range_flags;
		__u32		msg_flags;
		__u32		timeout_flags;
		__u32		accept_flags;
		__u32		cancel_flags;
		__u32		open_flags;
		__u32		statx_flags;
		__u32		fadvise_advice;
		__u32		splice_flags;
		__u32		rename_flags;
		__u32		unlink_flags;
		__u32		hardlink_flags;
		__u32		xattr_flags;
		__u32		msg_ring_flags;
		__u32		uring_cmd_flags;
		__u32		waitid_flags;
		__u32		futex_flags;
		__u32		install_fd_flags;
		__u32		nop_flags;
	};
	__u64	user_data;	/* données à renvoyer au moment de l'achèvement */
	/* empiler ceci pour éviter les fausses plaintes de l'arm OABI */
	union {
		/* index dans les tampons fixes, s'ils sont utilisés */
		__u16	buf_index;
		/* pour la sélection de tampons groupés */
		__u16	buf_group;
	} __attribute__((packed));
	/* personnalité à utiliser, si utilisée */
	__u16	personality;
	union {
		__s32	splice_fd_in;
		__u32	file_index;
		__u32	optlen;
		struct {
			__u16	addr_len;
			__u16	__pad3[1];
		};
	};
	union {
		struct {
			__u64	addr3;
			__u64	__pad2[1];
		};
		__u64	optval;
		/*
		 * Si l'anneau est initialisé avec IORING_SETUP_SQE128, alors
		 * ce champ est utilisé pour 80 octets de données de commande
		 * arbitraires
		 */
		__u8	cmd[0];
	};
};

Pour soumettre une requête E/S à io_uring, vous devez acquérir une entrée de file de soumission (SQE) depuis la file de soumission (SQ), la remplir avec les détails de l'opération que vous souhaitez soumettre et appeler io_uring_enter(2). Il existe des fonctions d'aide de la forme io_uring_prep_X pour permettre une configuration correcte de la SQE. Si vous souhaitez éviter d'appeler io_uring_enter(2), vous avez la possibilité de configurer l'interrogation de la file de soumission (Submission Queue Polling).

Les SQE sont ajoutées à l'extrémité de la file de soumission. Le noyau prélève les SQE depuis la tête de la SQ. L'algorithme général pour obtenir la SQE disponible suivante et mettre à jour l'extrémité est le suivant.


struct io_uring_sqe *sqe;
unsigned tail, index;
tail = *sqring->tail;
index = tail & (*sqring->ring_mask);
sqe = &sqring->sqes[index];
/* remplir les détails de cette requête E/S */
describe_io(sqe);
/* remplir l'index de la sqe dans le tableau de l'anneau SQ */
sqring->array[index] = index;
tail++;
atomic_store_explicit(sqring->tail, tail, memory_order_release);

Pour obtenir l'index d'une entrée, l'application doit masquer l'index d'extrémité courant avec le masque de taille de l'anneau. Cela s'applique aussi bien aux SQ qu'aux CQ. Une fois la SQE acquise, les champs nécessaires sont remplis, décrivant la requête. Alors que l'anneau CQ indexe directement le tableau partagé de CQE, le côté soumission a un tableau d'indirection entre eux. Le tampon d'anneau côté soumission est un index dans ce tableau, qui contient à son tour l'index dans les SQE.

L'extrait de code suivant montre comment une op lecture, équivalente à un appel système preadv2(2) , est décrite en remplissant une SQE avec les paramètres nécessaires.


struct iovec iovecs[16];
 ...
sqe->opcode = IORING_OP_READV;
sqe->fd = fd;
sqe->addr = (unsigned long) iovecs;
sqe->len = 16;
sqe->off = offset;
sqe->flags = 0;
Ordonnancement de la mémoire
Les compilateurs et processeurs modernes réordonnent librement les lectures et écritures sans affecter le résultat du programme afin d'optimiser les performances. Certains aspects de cela doivent être gardés à l'esprit sur les systèmes SMP puisque io_uring implique des tampons partagés entre le noyau et l'espace utilisateur. Ces tampons sont à la fois visibles et modifiables depuis le noyau et l'espace utilisateur. Étant donné que les têtes et extrémités appartenant à ces tampons partagés sont mises à jour par le noyau et l'espace utilisateur, les changements doivent être visibles de manière cohérente des deux côtés, indépendamment du fait qu'un changement de CPU se soit produit après le passage en mode noyau-utilisateur. Nous utilisons des barrières de mémoire pour imposer cette cohérence. Étant des sujets considérablement vastes en soi, les barrières de mémoire sont hors du champ de discussion de cette page de manuel. Pour plus d'informations sur les modèles de mémoire modernes, le lecteur peut consulter le Documentation/memory-barriers.txt dans l'arbre du noyau ou la documentation du modèle formel C11 ou du modèle de mémoire du noyau.
Informer le noyau des soumissions d'E/S
Une fois que vous avez placé une ou plusieurs SQE sur la SQ, vous devez informer le noyau que vous l'avez fait. Vous pouvez le faire en appelant l'appel système io_uring_enter(2) . Cet appel système est également capable d'attendre qu'un nombre spécifié d'événements se termine. De cette façon, vous pouvez être sûr de trouver des événements d'achèvement dans la file d'achèvement sans avoir à l'interroger pour des événements plus tard.

Lire les événements d'achèvement

De manière similaire à la file de soumission (SQ), la file d'achèvement (CQ) est un tampon partagé entre le noyau et l'espace utilisateur. Alors que vous placiez les entrées de file de soumission à l'extrémité de la SQ et que le noyau lisait depuis la tête, en ce qui concerne la CQ, le noyau place les événements de file d'achèvement ou CQE à l'extrémité de la CQ et vous lisez depuis sa tête.

La soumission est flexible (et donc un peu plus complexe) car elle doit être capable d'encoder différents types d'appels système qui prennent divers paramètres. L'achèvement, d'autre part, est plus simple car nous cherchons seulement une valeur de retour du noyau. Cela est facilement compris en regardant la structure d'événement de file d'achèvement, struct io_uring_cqe:


struct io_uring_cqe {
	__u64	user_data;  /* sqe->data de soumission renvoyée */
	__s32	res;        /* code de résultat pour cet événement */
	__u32	flags;
};

Ici, user_data sont des données personnalisées qui sont passées inchangées de la soumission à l'achèvement. C'est-à-dire, des SQE aux CQE. Ce champ peut être utilisé pour définir le contexte, identifiant de manière unique les soumissions qui ont été achevées. Étant donné que les requêtes E/S peuvent se terminer dans n'importe quel ordre, ce champ peut être utilisé pour corréler une soumission avec un achèvement. res est le résultat de l'appel système qui a été effectué dans le cadre de la soumission ; sa valeur de retour.

Le flags champ porte des informations spécifiques à la requête. En tant que tel, dans le noyau 6.12, les drapeaux suivants sont définis :

IORING_CQE_F_BUFFER
S'il est défini, les 16 bits supérieurs du champ flags portent l'ID du tampon qui a été choisi pour cette requête. La requête doit avoir été émise avec IOSQE_BUFFER_SELECT défini, et utilisée avec un type de requête qui prend en charge la sélection de tampons. De plus, les tampons doivent avoir été fournis à l'avance soit via les méthodes IORING_OP_PROVIDE_BUFFERS ou IORING_REGISTER_PBUF_RING .
IORING_CQE_F_MORE
S'il est défini, l'application doit s'attendre à plus d'achèvements de la requête. Cela est utilisé pour les requêtes qui peuvent générer plusieurs achèvements, telles que les requêtes multi-shot, receive ou accept.
IORING_CQE_F_SOCK_NONEMPTY
S'il est défini, lors de la réception des données du socket dans la requête courante, le socket avait encore des données restantes à la fin de cette requête.
IORING_CQE_F_NOTIF
Défini pour les CQE de notification, comme on le voit avec la prise en charge de l'envoi et de la réception réseau sans copie (zero-copy).
IORING_CQE_F_BUF_MORE
S'il est défini, l'ID de tampon défini dans l'achèvement recevra plus d'achèvements. Cela signifie que le tampon fourni a été partiellement consommé et qu'il reste de l'espace de tampon, et par conséquent l'application doit s'attendre à plus d'achèvements avec cet ID de tampon. Chaque achèvement continuera là où le précédent s'est arrêté. Cela ne peut se produire que si l'anneau de tampons fourni a été configuré avec IOU_PBUF_RING_INC pour permettre la consommation incrémentielle / partielle des tampons.

La séquence générale pour lire les événements d'achèvement depuis la file d'achèvement est la suivante :


unsigned head;
head = *cqring->head;
if (head != atomic_load_acquire(cqring->tail)) {
    struct io_uring_cqe *cqe;
    unsigned index;
    index = head & (cqring->mask);
    cqe = &cqring->cqes[index];
    /* traiter la CQE achevée */
    process_cqe(cqe);
    /* consommation de la CQE terminée */
    head++;
}
atomic_store_explicit(cqring->head, head, memory_order_release);

Il est utile de rappeler que le noyau ajoute les CQE à l'extrémité de la CQ, alors que vous devez les défiler depuis la tête. Pour obtenir l'index d'une entrée à la tête, l'application doit masquer l'index de tête courant avec le masque de taille de l'anneau. Une fois la CQE consommée ou traitée, la tête doit être mise à jour pour refléter la consommation de la CQE. Une attention doit être portée aux barrières de lecture et d'écriture pour assurer la lecture et la mise à jour réussies de la tête.

Performances de io_uring

En raison des tampons d'anneau partagés entre le noyau et l'espace utilisateur, io_uring peut être un système sans copie (zero-copy). La copie des tampons vers et depuis devient nécessaire lorsque des appels système transférant des données entre le noyau et l'espace utilisateur sont impliqués. Mais puisque la majeure partie de la communication dans io_uring se fait via des tampons partagés entre le noyau et l'espace utilisateur, cette énorme surcharge de performance est complètement évitée.

Bien que les appels système puissent ne pas sembler une surcharge significative, dans les applications haute performance, en faire beaucoup commencera à compter. Bien que les contournements que le système d'exploitation a en place pour faire face à Spectre et Meltdown soient idéalement mieux supprimés, malheureusement, certains de ces contournements sont autour de l'interface d'appel système, rendant les appels système moins bon marché qu'avant sur le matériel affecté. Bien que le matériel plus récent ne devrait pas avoir besoin de ces contournements, on peut s'attendre à ce que le matériel présentant ces vulnérabilités soit répandu pendant longtemps. Bien que l'utilisation d'interfaces de programmation synchrone ou même l'utilisation d'interfaces de programmation asynchrone sous Linux, il y a au moins un appel système impliqué dans la soumission de chaque requête. Dans io_uring, en revanche, vous pouvez regrouper plusieurs requêtes en une seule opération, simplement en mettant en file d'attente plusieurs SQE, chacun décrivant une opération d'E/S que vous souhaitez, et en effectuant un seul appel à io_uring_enter(2). Cela est possible grâce à la conception basée sur les tampons partagés de io_uring.

Bien que ce regroupement en lui-même puisse éviter la surcharge associée à des appels système potentiellement multiples et fréquents, vous pouvez réduire encore davantage cette surcharge grâce à l'interrogation de la file d'attente de soumission (Submission Queue Polling), en faisant en sorte que le noyau interroge et récupère vos SQE pour les traiter à mesure que vous les ajoutez à la file d'attente de soumission. Cela évite l'appel io_uring_enter(2) que vous devez effectuer pour dire au noyau de récupérer les SQE. Pour les applications haute performance, cela signifie encore moins de surcharge due aux appels système.

CONFORMITÉ

io_uring est spécifique à Linux.

EXEMPLES

L'exemple suivant utilise io_uring pour copier stdin vers stdout. En utilisant la redirection du shell, vous devriez pouvoir copier des fichiers avec cet exemple. Parce qu'il utilise une profondeur de file d'attente d'un seul élément, cet exemple traite les requêtes d'E/S une après l'autre. Il est volontairement conçu de cette manière pour aider à la compréhension. Dans les scénarios du monde réel, cependant, vous voudrez avoir une profondeur de file d'attente plus grande pour paralléliser le traitement des requêtes d'E/S afin de tirer parti du type de bénéfices de performance io_uring fournit grâce à son traitement asynchrone des requêtes.

#include <stdio.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <sys/ioctl.h>
#include <sys/syscall.h>
#include <sys/mman.h>
#include <sys/uio.h>
#include <linux/fs.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>
#include <stdatomic.h>
#include <linux/io_uring.h>
#define QUEUE_DEPTH 1
#define BLOCK_SZ    1024
/* Macros for barriers needed by io_uring */
#define io_uring_smp_store_release(p, v)            \
    atomic_store_explicit((_Atomic typeof(*(p)) *)(p), (v), \
                  memory_order_release)
#define io_uring_smp_load_acquire(p)                \
    atomic_load_explicit((_Atomic typeof(*(p)) *)(p),   \
                 memory_order_acquire)
int ring_fd;
unsigned *sring_tail, *sring_mask, *sring_array, 
            *cring_head, *cring_tail, *cring_mask;
struct io_uring_sqe *sqes;
struct io_uring_cqe *cqes;
char buff[BLOCK_SZ];
off_t offset;
/*
 * System call wrappers provided since glibc does not yet
 * provide wrappers for io_uring system calls.
* */
int io_uring_setup(unsigned entries, struct io_uring_params *p)
{
    int ret;
    ret = syscall(__NR_io_uring_setup, entries, p);
    return (ret < 0) ? -errno : ret;
}
int io_uring_enter(int ring_fd, unsigned int to_submit,
                   unsigned int min_complete, unsigned int flags)
{
    int ret;
    ret = syscall(__NR_io_uring_enter, ring_fd, to_submit,
                  min_complete, flags, NULL, 0);
    return (ret < 0) ? -errno : ret;
}
int app_setup_uring(void) {
    struct io_uring_params p;
    void *sq_ptr, *cq_ptr;
    /* See io_uring_setup(2) for io_uring_params.flags you can set */
    memset(&p, 0, sizeof(p));
    ring_fd = io_uring_setup(QUEUE_DEPTH, &p);
    if (ring_fd < 0) {
        perror("io_uring_setup");
        return 1;
    }
    /*
     * io_uring communication happens via 2 shared kernel-user space ring
     * buffers, which can be jointly mapped with a single mmap() call in
     * kernels >= 5.4.
     */
    int sring_sz = p.sq_off.array + p.sq_entries * sizeof(unsigned);
    int cring_sz = p.cq_off.cqes + p.cq_entries * sizeof(struct io_uring_cqe);
    /* Rather than check for kernel version, the recommended way is to
     * check the features field of the io_uring_params structure, which is a 
     * bitmask. If IORING_FEAT_SINGLE_MMAP is set, we can do away with the
     * second mmap() call to map in the completion ring separately.
     */
    if (p.features & IORING_FEAT_SINGLE_MMAP) {
        if (cring_sz > sring_sz)
            sring_sz = cring_sz;
        cring_sz = sring_sz;
    }
    /* Map in the submission and completion queue ring buffers.
     *  Kernels < 5.4 only map in the submission queue, though.
     */
    sq_ptr = mmap(0, sring_sz, PROT_READ | PROT_WRITE,
                  MAP_SHARED | MAP_POPULATE,
                  ring_fd, IORING_OFF_SQ_RING);
    if (sq_ptr == MAP_FAILED) {
        perror("mmap");
        return 1;
    }
    if (p.features & IORING_FEAT_SINGLE_MMAP) {
        cq_ptr = sq_ptr;
    } else {
        /* Map in the completion queue ring buffer in older kernels separately */
        cq_ptr = mmap(0, cring_sz, PROT_READ | PROT_WRITE,
                      MAP_SHARED | MAP_POPULATE,
                      ring_fd, IORING_OFF_CQ_RING);
        if (cq_ptr == MAP_FAILED) {
            perror("mmap");
            return 1;
        }
    }
    /* Save useful fields for later easy reference */
    sring_tail = sq_ptr + p.sq_off.tail;
    sring_mask = sq_ptr + p.sq_off.ring_mask;
    sring_array = sq_ptr + p.sq_off.array;
    /* Map in the submission queue entries array */
    sqes = mmap(0, p.sq_entries * sizeof(struct io_uring_sqe),
                   PROT_READ | PROT_WRITE, MAP_SHARED | MAP_POPULATE,
                   ring_fd, IORING_OFF_SQES);
    if (sqes == MAP_FAILED) {
        perror("mmap");
        return 1;
    }
    /* Save useful fields for later easy reference */
    cring_head = cq_ptr + p.cq_off.head;
    cring_tail = cq_ptr + p.cq_off.tail;
    cring_mask = cq_ptr + p.cq_off.ring_mask;
    cqes = cq_ptr + p.cq_off.cqes;
    return 0;
}
/*
* Read from completion queue.
* In this function, we read completion events from the completion queue.
* We dequeue the CQE, update and head and return the result of the operation.
* */
int read_from_cq() {
    struct io_uring_cqe *cqe;
    unsigned head;
    /* Read barrier */
    head = io_uring_smp_load_acquire(cring_head);
    /*
    * Remember, this is a ring buffer. If head == tail, it means that the
    * buffer is empty.
    * */
    if (head == *cring_tail)
        return -1;
    /* Get the entry */
    cqe = &cqes[head & (*cring_mask)];
    if (cqe->res < 0)
        fprintf(stderr, "Error: %s\n", strerror(abs(cqe->res)));
    head++;
    /* Write barrier so that update to the head are made visible */
    io_uring_smp_store_release(cring_head, head);
    return cqe->res;
}
/*
* Submit a read or a write request to the submission queue.
* */
int submit_to_sq(int fd, int op) {
    unsigned index, tail;
    /* Add our submission queue entry to the tail of the SQE ring buffer */
    tail = *sring_tail;
    index = tail & *sring_mask;
    struct io_uring_sqe *sqe = &sqes[index];
    /* Fill in the parameters required for the read or write operation */
    sqe->opcode = op;
    sqe->fd = fd;
    sqe->addr = (unsigned long) buff;
    if (op == IORING_OP_READ) {
        memset(buff, 0, sizeof(buff));
        sqe->len = BLOCK_SZ;
    }
    else {
        sqe->len = strlen(buff);
    }
    sqe->off = offset;
    sring_array[index] = index;
    tail++;
    /* Update the tail */
    io_uring_smp_store_release(sring_tail, tail);
    /*
    * Tell the kernel we have submitted events with the io_uring_enter()
    * system call. We also pass in the IORING_ENTER_GETEVENTS flag which
    * causes the io_uring_enter() call to wait until min_complete
    * (the 3rd param) events complete.
    * */
    int ret =  io_uring_enter(ring_fd, 1,1,
                              IORING_ENTER_GETEVENTS);
    if(ret < 0) {
        perror("io_uring_enter");
        return -1;
    }
    return ret;
}
int main(int argc, char *argv[]) {
    int res;
    /* Setup io_uring for use */
    if(app_setup_uring()) {
        fprintf(stderr, "Unable to setup uring!\n");
        return 1;
    }
    /* 
    * A while loop that reads from stdin and writes to stdout.
    * Breaks on EOF.
    */
    while (1) {
        /* Initiate read from stdin and wait for it to complete */
        submit_to_sq(STDIN_FILENO, IORING_OP_READ);
        /* Read completion queue entry */
        res = read_from_cq();
        if (res > 0) {
            /* Read successful. Write to stdout. */
            submit_to_sq(STDOUT_FILENO, IORING_OP_WRITE);
            read_from_cq();
        } else if (res == 0) {
            /* reached EOF */
            break;
        }
        else if (res < 0) {
            /* Error reading file */
            fprintf(stderr, "Error: %s\n", strerror(abs(res)));
            break;
        }
        offset += res;
    }
    return 0;
}
