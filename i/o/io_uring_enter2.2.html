DESCRIPTIO

N

io_uring_enter(2) est utilisé pour initier et terminer des E/S en utilisant les files d'attente de soumission et d'achèvement partagées configurées par un appel à io_uring_setup(2). Un seul appel peut à la fois soumettre de nouvelles E/S et attendre l'achèvement des E/S initiées par cet appel ou par des appels précédents à io_uring_ent

er(2).

fd est le descripteur de fichier retourné par io_uring_setup(2). to_submit spécifie le nombre d'E/S à soumettre depuis la file d'attente de soumission. flags est un masque de bits des valeurs suivantes

:
IORING_ENTER_GETEVE
NTS
Si ce drapeau est défini, l'appel système attendra le nombre spécifié d'événements dans min_complete avant de retourner. Ce drapeau peut être défini en même temps que to_submit pour à la fois soumettre et terminer des événements dans un seul appel système. Si ce drapeau est défini, soit le drapeau IORING_SETUP_DEFER_TASKRUN ne doit pas être défini, soit le thread émettant l'appel système doit être le thread qui a créé l'io_uring associé à fd, ou être le thread qui a activé l'anneau initialement créé avec IORING_SETUP_R_DISABLED via io_uring_register(2) ou io_uring_enable_r
ings(3).
IORING_ENTER_SQ_WAK
EUP
Si l'anneau a été créé avec IORING_SETUP_SQPOLL, alors ce drapeau demande au noyau de réveiller le thread noyau SQ pour soumettre des
E/S.

AIT

Cela peut mener à une situation où l'application ne peut plus obtenir une entrée SQE libre pour soumettre, sans savoir quand une entrée deviendra disponible alors que le thread noyau SQ les consomme. Si l'appel système est utilisé avec ce drapeau défini, alors il attendra jusqu'à ce qu'au moins une entrée soit libre dans la file d'anneau
SQ.

Si l'instance io_uring était configurée pour le sondage, en spécifiant IORING_SETUP_IOPOLL dans l'appel à io_uring_setup(2), alors min_complete a une signification légèrement différente. Passer une valeur de 0 indique au noyau de retourner tous les événements qui sont déjà terminés, sans bloquer. Si min_complete est une valeur non nulle, le noyau retournera toujours immédiatement si des événements d'achèvement sont disponibles. Si aucun événement d'achèvement n'est disponible, alors l'appel sondera jusqu'à ce qu'une ou plusieurs complétions deviennent disponibles, ou jusqu'à ce que le processus ait dépassé sa tranche de temps d'ordonnancement

.

Notez que, pour les E/S pilotées par interruption (où IORING_SETUP_IOPOLL n'a pas été spécifié dans l'appel à io_uring_setup(2)), une application peut vérifier la file d'achèvement pour les événements d'achèvement sans entrer dans le noyau du

tout.

Lorsque l'appel système retourne qu'une certaine quantité de SQEs a été consommée et soumise, il est sûr de réutiliser les entrées SQE dans l'anneau. C'est vrai même si la soumission d'E/S réelle a dû être transférée au contexte asynchrone, ce qui signifie que le SQE peut en fait ne pas avoir été soumis encore. Si le noyau a besoin d'utiliser ultérieurement une entrée SQE particulière, il aura fait une copie privée de

celle-ci.

sig est un pointeur vers un masque de signaux (voir sigprocmask(2)) ; si sig n'est pas NULL, io_uring_enter(2) remplace d'abord le masque de signaux courant par celui vers lequel pointe sig, puis attend que des événements deviennent disponibles dans la file d'achèvement, et restaure ensuite le masque de signaux original. L'appel io_uring_enter(2) suivant

: 


ret = io_uring_enter(fd, 0, 1, IORING_ENTER_GETEVENTS, &sig)
;

est équivalent à l'exécution atomique des appels suivants

: 


pthread_sigmask(SIG_SETMASK, &sig, &orig);
ret = io_uring_enter(fd, 0, 1, IORING_ENTER_GETEVENTS, NULL);
pthread_sigmask(SIG_SETMASK, &orig, NULL)
;

Voir la description de pselect(2) pour une explication de pourquoi le paramètre sig est

nécessaire.

Opérations de lecture et d'écriture vectorielles, similaires à preadv2(2) et pwritev2(2). Si le fichier n'est pas séquentiellement accessible, off doit être défini à zéro ou
-1.

Lire depuis ou écrire vers des tampons pré-mappés. Voir io_uring_register(2) pour les détails sur la façon de configurer un contexte pour les lectures et écritures
fixes.
IORING_OP_FS
YNC
Synchronisation de fichier. Voir aussi fsync(2). En option, off et len peuvent être utilisés pour spécifier une plage dans le fichier à synchroniser plutôt que de synchroniser l'entier du fichier, qui est le comportement par défaut. Notez que, bien que les E/S soient initiées dans l'ordre où elles apparaissent dans la file de soumission, les achèvements ne sont pas ordonnés. Par exemple, une application qui place une écriture E/S suivie d'un fsync dans la file de soumission ne peut pas s'attendre à ce que le fsync s'applique à l'écriture. Les deux opérations s'exécutent en parallèle, de sorte que le fsync peut se terminer avant que l'écriture ne soit émise vers le stockage. Il en va de même pour les écritures précédemment émises qui ne se sont pas terminées avant le fsync. Pour faire respecter l'ordre, on peut utiliser des SQE liées, IOSQE_IO_DRAIN ou attendre l'arrivée des CQE des requêtes qui doivent être ordonnées avant une requête donnée avant de soumettre son
SQE.
IORING_OP_POLL_
ADD
Interroger le fd spécifié dans l'entrée de la file de soumission pour les événements spécifiés dans le champ poll_events. Contrairement à poll ou epoll sans EPOLLONESHOT, par défaut cette interface fonctionne toujours en mode one shot. C'est-à-dire qu'une fois l'opération de sondage terminée, elle devra être resoumise.

Si IORING_POLL_ADD_MULTI est défini dans le champ len du SQE, alors le sondage fonctionnera en mode multi shot à la place. Cela signifie qu'il se déclenchera à plusieurs reprises lorsque l'événement demandé devient vrai, et donc plusieurs CQE peuvent être générés à partir de ce seul SQE. Le champ flags du CQE aura IORING_CQE_F_MORE défini à l'achèvement si l'application doit s'attendre à d'autres entrées CQE de la requête originale. Si ce drapeau n'est pas défini à l'achèvement, alors la requête de sondage a été terminée et aucun autre événement ne sera généré. Ce mode est disponible depuis la version

5.13.

Cette commande fonctionne comme un poll(2) asynchrone et le résultat de l'événement d'achèvement est le masque d'événements

renvoyé.

Sans IORING_POLL_ADD_MULTI et l'opération de sondage initiale avec IORING_POLL_ADD_MULTI, l'opération est déclenchée par niveau, c'est-à-dire que s'il y a des données prêtes ou des événements en attente, etc. au moment de la soumission, un CQE correspondant sera publié. Les achèvements potentiels supplémentaires au-delà du premier causés par un IORING_POLL_ADD_MULTI sont déclenchés

par

IORING_OP_TIMEOUT
Cette commande enregistre une opération de délai d'attente. Le champ addr doit contenir un pointeur vers une structure struct __kernel_timespec, len doit contenir 1 pour signifier une structure struct __kernel_timespec, timeout_flags peut contenir IORING_TIMEOUT_ABS pour une valeur de délai d'attente absolue, ou 0 pour un délai d'attente relatif. off peut contenir un compteur d'événements d'achèvement. Un délai d'attente déclenchera un événement de réveil sur la file d'attente d'achèvement pour quiconque attend des événements. Une condition de délai d'attente est remplie lorsque soit le délai spécifié expire, soit le nombre spécifié d'événements est terminé. L'une ou l'autre condition déclenchera l'événement. Si défini sur 0, les événements terminés ne sont pas comptés, ce qui agit effectivement comme une minuterie. Les délais d'attente io_uring utilisent CLOCK_MONOTONIC comme source d'horloge par défaut. La requête se terminera avec -ETIME si le délai d'attente s'est terminé par expiration du minuteur, ou 0 si le délai d'attente s'est terminé par l'achèvement des requêtes elles-mêmes. Si le délai d'attente a été annulé avant son expiration, la requête se terminera avec -ECANCELED. Disponible depuis 5.4.

Depuis 5.15, cette commande prend également en charge les modificateurs suivants dans timeout_flags :


IORING_TIMEOUT_BOOTTIME Si défini, l'horloge utilisée est CLOCK_BOOTTIME au lieu de CLOCK_MONOTONIC. Cette horloge diffère en ce qu'elle inclut le temps écoulé si le système a été suspendu alors qu'une demande de délai d'attente était en cours.

IORING_TIMEOUT_REALTIME Si défini, l'horloge utilisée est CLOCK_REALTIME au lieu de CLOCK_MONOTONIC.


Depuis 5.16, IORING_TIMEOUT_ETIME_SUCCESS peut être défini dans timeout_flags, ce qui entraînera l'expiration du minuteur et son achèvement ultérieur avec -ETIME non interprété comme une erreur. Ceci est surtout pertinent pour les SQE liés, car les requêtes suivantes dans la chaîne ne seraient pas annulées par le délai d'attente si ce drapeau est défini. Voir IOSQE_IO_LINK pour plus de détails sur les SQE liés.


Depuis 6.4, IORING_TIMEOUT_MULTISHOT peut être défini dans timeout_flags, ce qui entraînera la production de plusieurs achèvements consécutifs par le minuteur, comme d'autres opérations multi-prises e.g. IORING_OP_READ_MULTISHOT ou IORING_POLL_ADD_MULTI. off doit être défini sur le nombre d'achèvements souhaités. IORING_TIMEOUT_MULTISHOT ne doit pas être utilisé avec IORING_TIMEOUT_ABS.

IORING_OP_TIMEOUT_REMOVE
Si timeout_flags sont nuls, il tente de supprimer une opération de délai d'attente existante. addr doit contenir le champ user_data de l'opération de délai d'attente précédemment émise. Si la demande de délai d'attente spécifiée est trouvée et annulée avec succès, cette demande se terminera avec une valeur de résultat de 0. Si la demande de délai d'attente a été trouvée mais que l'expiration était déjà en cours, cette demande se terminera avec une valeur de résultat de -EBUSY. Si la demande de délai d'attente n'a pas été trouvée, la demande se terminera avec une valeur de résultat de -ENOENT. Disponible depuis 5.5.

Si timeout_flags contient IORING_TIMEOUT_UPDATE, au lieu de supprimer une opération existante, il la met à jour. addr et les valeurs de retour sont les mêmes qu'auparavant. Le champ addr2 doit contenir un pointeur vers une structure struct __kernel_timespec. timeout_flags peut également contenir IORING_TIMEOUT_ABS, auquel cas la valeur donnée est une valeur absolue, pas une valeur relative. Disponible depuis 5.11.

IORING_OP_ACCEPT
Émet l'équivalent d'un appel système accept4(2). fd doit être défini sur le descripteur de fichier de socket, addr doit contenir le pointeur vers la structure sockaddr, et addr2 doit contenir un pointeur vers le champ de socklen_t addrlen. Les drapeaux peuvent être passés en utilisant le champ accept_flags. Voir également accept4(2) pour la description générale de l'appel système associé. Disponible depuis 5.5.

Si le champ file_index est défini sur un nombre positif, le fichier ne sera pas installé dans la table de fichiers normale comme d'habitude, mais sera placé dans la table de fichiers fixe à l'index file_index - 1. Dans ce cas, au lieu de renvoyer un descripteur de fichier, le résultat contiendra soit 0 en cas de succès, soit une erreur. Si l'index pointe vers un emplacement vide valide, l'installation est garantie de ne pas échouer. S'il y a déjà un fichier dans l'emplacement, il sera remplacé, similaire à IORING_OP_FILES_UPDATE. Veuillez noter que seul io_uring a accès à de tels fichiers et aucun autre appel système ne peut les utiliser. Voir IOSQE_FIXED_FILE et IORING_REGISTER_FILES.

Cela signifie que, par exemple, une lecture courte terminera également le reste de la chaîne. Si une chaîne de liens de SQE est interrompue, la partie restante non démarrée de la chaîne sera terminée et complétée avec -ECANCELED comme code d'erreur. Disponible depuis la version
5.3.

Notez que le lien sera tout de même rompu si nous échouons à soumettre la requête parente ; les liens durs ne sont résilients qu'en présence de résultats de complétion pour les requêtes qui ont été soumises correctement. IOSQE_IO_HARDLINK implique IOSQE_IO_LINK. Disponible depuis la version

Le fonctionnement normal de io_uring consiste à essayer d'émettre une sqe en mode non bloquant d'abord, et si cela échoue, à l'exécuter de manière asynchrone. Pour prendre en charge une opération superposée plus efficace des requêtes que l'application sait/suppose bloquer toujours (ou la plupart du temps), l'application peut demander qu'une sqe soit émise de manière asynchrone dès le début. Utilisé en conjonction avec la commande IORING_OP_PROVIDE_BUFFERS, qui enregistre un pool de tampons à utiliser par les commandes qui lisent ou reçoivent des données. Lorsque des tampons sont enregistrés pour ce cas d'utilisation, et que cet indicateur est défini dans la commande, io_uring prendra un tampon de ce pool lorsque la requête est prête à recevoir ou lire des données. En cas de succès, la CQE résultante aura IORING_CQE_F_BUFFER défini dans la partie flags de la structure, et les bits supérieurs IORING_CQE_BUFFER_SHIFT contiendront l'ID des tampons sélectionnés. Cela permet à l'application de savoir exactement quel tampon a été sélectionné pour l'opération. Si aucun tampon n'est disponible et que cet indicateur est défini, la requête échouera avec -ENOBUFS comme code d'erreur. Une fois qu'un tampon a été utilisé, il n'est plus disponible dans le pool du noyau. L'application doit réenregistrer le tampon donné à nouveau lorsqu'elle est prête à le recycler (par exemple, lorsqu'elle a terminé de l'utiliser). Disponible depuis la version
5.7.
IOSQE_CQE_SKIP_SUCC
ESS
Ne pas générer de CQE si la requête se termine avec succès. Si la requête échoue, une CQE appropriée sera publiée comme d'habitude et s'il n'y a pas de IOSQE_IO_HARDLINK, les CQE pour toutes les requêtes liées seront omises. La notion d'échec/succès est spécifique à l'opcode et est la même que pour la rupture des chaînes de IOSQE_IO_LINK. Un cas particulier est lorsque la requête a un délai d'attente lié (linked timeout) ; la génération de CQE pour le délai lié est alors décidée uniquement par la présence de IOSQE_CQE_SKIP_SUCCESS défini, que le délai ait expiré ou ait été annulé. En d'autres termes, si un délai lié a l'indicateur défini, il est garanti de ne pas publier de CQE.

La sémantique est choisie pour s'adapter à plusieurs cas d'utilisation. Premièrement, lorsque toutes les requêtes sauf la dernière d'un lien normal sans délais liés sont marquées avec l'indicateur, une seule CQE est publiée par lien. De plus, cela permet la suppression des CQE dans les cas où les effets de bord d'une opération exécutée avec succès suffisent pour que l'espace utilisateur connaisse l'état du système. Un tel exemple serait l'écriture dans un fichier de

synchronisation.

Cet indicateur est incompatible avec IOSQE_IO_DRAIN. L'utilisation des deux dans une même ring est un comportement indéfini, même lorsqu'ils ne sont pas utilisés ensemble dans une même requête. Actuellement, après la première requête avec IOSQE_CQE_SKIP_SUCCESS, toutes les requêtes suivantes marquées avec drain échoueront au moment de la soumission. Notez que la notification d'erreur est à titre indicatif seulement, et les restrictions peuvent changer à

l'avenir.

Elles sont décrites dans la section ERREURS CQE

.
