ALL
Normalement, io_uring arrête de soumettre un lot de requêtes si l'une de ces requêtes entraîne une erreur. Cela peut entraîner la soumission de moins que ce qui est attendu, si une requête se termine par une erreur lors de sa soumission. Si l'anneau est créé avec ce drapeau, io_uring_enter(2) continueraContinuez la soumission des requêtes même s'il rencontre une erreur lors de la soumission d'une requête. Les CQE sont toujours publiées pour les requêtes erronées, indépendamment du fait que ce drapeau soit défini ou non au moment de la création de l'anneau, la seule différence est si la séquence de soumission est arrêtée ou continuée lorsqu'une erreur est observée. Disponible depuis la version 5.18.
IORING_SETUP_COOP_TASKRUN
Par défaut, io_uring interrompra une tâche s'exécutant dans l'espace utilisateur lorsqu'un événement de complétion arrive. Ceci afin de garantir que les complétions s'exécutent en temps opportun. Pour de nombreux cas d'utilisation, cela est excessif et peut entraîner une réduction des performances due à l'interruption inter-processeurs utilisée à cette fin, à la transition noyau/utilisateur, à l'interruption inutile des activités de l'espace utilisateur de la tâche, et à la réduction du traitement par lots si les complétions arrivent à un rythme rapide. La plupart des applications n'ont pas besoin de l'interruption forcée, car les événements sont traités lors de toute transition noyau/utilisateur. L'exception concerne les configurations où l'application utilise plusieurs threads opérant sur le même anneau, où la tâche attendant les complétions n'est pas celle qui les a soumises. Pour la plupart des autres cas d'utilisation, la définition de ce drapeau améliorera les performances. Disponible depuis la version 5.19.
IORING_SETUP_TASKRUN_FLAG
Utilisé conjointement avec IORING_SETUP_COOP_TASKRUN, cela fournit un drapeau, IORING_SQ_TASKRUN, qui est défini dans le champ flags de l'anneau SQ chaque fois qu'il y a des complétions en attente qui devraient être traitées. liburing vérifiera ce drapeau même lors de l'appel de io_uring_peek_cqe(3) et entrera dans le noyau pour les traiter, et les applications peuvent faire de même. Cela rend IORING_SETUP_TASKRUN_FLAG sûr à utiliser même lorsque les applications s'appuient sur une opération de type "peek" sur l'anneau CQ pour voir s'il y a quelque chose en attente à récupérer. Disponible depuis la version 5.19.
IORING_SETUP_SQE128
Si défini, io_uring utilisera des SQE de 128 octets plutôt que la variante normale de 64 octets. Ceci est une exigence pour utiliser certains types de requêtes, à partir de la version 5.19, seule la commande de passage IORING_OP_URING_CMD pour le passage NVMe nécessite cela. Disponible depuis la version 5.19.
IORING_SETUP_CQE32
Si défini, io_uring utilisera des CQE de 32 octets plutôt que la variante normale de 16 octets. Ceci est une exigence pour utiliser certains types de requêtes, à partir de la version 5.19, seule la commande de passage IORING_OP_URING_CMD pour le passage NVMe nécessite cela. Disponible depuis la version 5.19.
IORING_SETUP_SINGLE_ISSUER
Une indication au noyau qu'un seul tâche (ou thread) soumettra des requêtes, ce qui est utilisé pour des optimisations internes. La tâche de soumission est soit la tâche qui a créé l'anneau, soit, si IORING_SETUP_R_DISABLED est spécifié, c'est la tâche qui active l'anneau via io_uring_register(2). Le noyau applique cette règle, rejetant les requêtes avec -EEXIST si la restriction est violée. Il convient de noter que lorsque IORING_SETUP_SQPOLL est défini, on considère que la tâche de sondage effectue toutes les soumissions pour le compte de l'espace utilisateur et respecte donc toujours la règle, quelle que soit le nombre de tâches utilisateur qui appellent io_uring_enter(2). Disponible depuis la version 6.0.
IORING_SETUP_DEFER_TASKRUN
Par défaut, io_uring traitera tout le travail en suspens à la fin de tout appel système ou interruption de thread. Cela peut retarder la progression de l'application. La définition de ce drapeau indiquera à io_uring de reporter le travail jusqu'à un appel à io_uring_enter(2) avec le drapeau IORING_ENTER_GETEVENTS défini. Cela permet à l'application de demander l'exécution du travail juste avant qu'elle ne souhaite traiter les complétions. Ce drapeau nécessite que le drapeau IORING_SETUP_SINGLE_ISSUER soit défini, et impose également que l'appel à io_uring_enter(2) soit appelé depuis le même thread qui a soumis les requêtes. Notez que si ce drapeau est défini, il incombe à l'application de déclencher périodiquement le travail (par exemple, via l'une des fonctions d'attente de CQE) sans quoi les complétions pourraient ne pas être livrées. Disponible depuis la version 6.1.
IORING_SETUP_NO_MMAP
Par défaut, io_uring alloue de la mémoire noyau que les appelants doivent ensuite mmap(2). Si ce drapeau est défini, io_uring utilise à la place des tampons alloués par l'appelant ; p->cq_off.user_addr doit pointer vers la mémoire des anneaux SQ/CQ, et p->sq_off.user_addr doit pointer vers la mémoire des SQE. Chaque allocation doit être de la mémoire contiguë. Typiquement, les appelants devraient allouer cette mémoire en utilisant mmap(2) pour allouer une huge page. Si ce drapeau est défini, une tentative ultérieure de mmap(2) du descripteur de fichier io_uring échouera. Disponible depuis la version 6.5.
IORING_SETUP_REGISTERED_FD_ONLY
Si ce drapeau est défini, io_uring enregistrera le descripteur de fichier de l'anneau, et renverra l'index du descripteur enregistré, sans jamais allouer de descripteur de fichier non enregistré. L'appelant devra utiliser IORING_REGISTER_USE_REGISTERED_RING lors de l'appel à io_uring_register(2). Ce drapeau n'a de sens que lorsqu'il est utilisé conjointement avec IORING_SETUP_NO_MMAP, qui doit également être défini. Disponible depuis la version 6.5.
IORING_SETUP_NO_SQARRAY
Si ce drapeau est défini, les entrées de la file de soumission seront soumises dans l'ordre, revenant à la première entrée après avoir atteint la fin de la file. En d'autres termes, il n'y aura plus d'indirection via le tableau d'entrées de soumission, et la file sera indexée directement par la queue de soumission et la plage d'indices représentée par celle-ci modulo la taille de la file. Par conséquent, l'utilisateur ne devrait pas mapper le tableau des entrées de la file de soumission, et l'offset correspondant dans struct io_sqring_offsets sera mis à zéro. Disponible depuis la version 6.6.

Si aucun drapeau n'est spécifié, l'instance io_uring est configurée pour les E/S pilotées par interruption. Les E/S peuvent être soumises en utilisant io_uring_enter(2) et peuvent être récupérées en sondant la file de complétion.

Le tableau resv doit être initialisé à zéro.

features est rempli par le noyau, qui spécifie diverses fonctionnalités prises en charge par la version actuelle du noyau.

IORING_FEAT_SINGLE_MMAP
Si ce drapeau est défini, les deux anneaux SQ et CQ peuvent être mappés avec un seul appel mmap(2). Les SQE doivent toujours être allouées séparément. Cela réduit le nombre d'appels mmap(2) nécessaires de trois à deux. Disponible depuis le noyau 5.4.
IORING_FEAT_NODROP
Si ce drapeau est défini, io_uring prend en charge de ne quasiment jamais perdre d'événements de complétion. Une perte d'événement ne peut se produire que si le noyau manque de mémoire, auquel cas vous avez des problèmes plus graves qu'un événement perdu. Votre application et les autres seront probablement tuées par le système OOM de toute façon. Si un événement de complétion se produit et que l'anneau CQ est plein, le noyau stocke l'événement en interne jusqu'à ce que l'anneau CQ ait de la place pour plus d'entrées. Dans les noyaux précédents, si cette condition de dépassement est atteinte, tenter de soumettre plus d'E/S échouerait avec la valeur d'erreur -EBUSY, s'il ne peut pas évacuer les événements débordés vers l'anneau CQ. Si cela se produit, l'application doit récupérer les événements de l'anneau CQ et réessayer la soumission. Si le noyau n'a pas de mémoire libre pour stocker l'événement en interne, cela sera visible par une augmentation de la valeur de dépassement sur l'anneau CQ. Disponible depuis le noyau 5.5. De plus, io_uring_enter(2) retournera -EBADR la prochaine fois qu'il serait autrement en attente d'achèvement (depuis le noyau 5.19).
IORING_FEAT_SUBMIT_STABLE
Si ce drapeau est défini, les applications peuvent être certaines que toute donnée destinée à un déchargement asynchrone a été consommée lorsque le noyau a consommé le SQE. Disponible depuis le noyau 5.5.
IORING_FEAT_RW_CUR_POS
Si ce drapeau est défini, les applications peuvent spécifier offset == -1 avec IORING_OP_{READV,WRITEV}, IORING_OP_{READ,WRITE}_FIXED, et IORING_OP_{READ,WRITE} pour signifier la position actuelle du fichier, ce qui se comporte comme preadv2(2) et pwritev2(2) avec offset == -1. Il utilisera (et mettra à jour) la position actuelle du fichier. Cela s'accompagne évidemment de la mise en garde que si l'application a plusieurs lectures ou écritures en cours, le résultat final ne sera pas celui attendu. Ceci est similaire à des threads partageant un descripteur de fichier et effectuant des E/S en utilisant la position actuelle du fichier. Disponible depuis le noyau 5.6.
IORING_FEAT_CUR_PERSONALITY
Si ce drapeau est défini, alors io_uring garantit que l'exécution synchrone et asynchrone d'une requête assume les identifiants de la tâche qui a appelé io_uring_enter(2) pour mettre en file d'attente les requêtes. Si ce drapeau n'est pas défini, alors les requêtes sont émises avec les identifiants de la tâche qui a initialement enregistré l'io_uring. Si une seule tâche utilise un anneau, alors ce drapeau n'a pas d'importance car les identifiants seront toujours les mêmes. Notez que c'est le comportement par défaut, les tâches peuvent toujours enregistrer différentes personnalités via io_uring_register(2) avec IORING_REGISTER_PERSONALITY et spécifier la personnalité à utiliser dans le SQE. Disponible depuis le noyau 5.6.
IORING_FEAT_FAST_POLL
Si ce drapeau est défini, alors io_uring prend en charge l'utilisation d'un mécanisme de sondage interne pour piloter la disponibilité des données/espaces. Cela signifie que les requêtes qui ne peuvent pas lire ou écrire de données dans un fichier n'ont plus besoin d'être transmises à un thread asynchrone pour être traitées ; elles commenceront plutôt leur opération lorsque le fichier sera prêt. Ceci est similaire à la réalisation de sondages + lecture/écriture dans l'espace utilisateur, mais élimine la nécessité de le faire. Si ce drapeau est défini, les requêtes en attente d'espace/données consomment un lo
t moins de ressources car elles ne bloquent pas un thread. Disponible depuis le noyau 5.7.

Le reste des champs dans la struct io_uring_params est rempli par le noyau et fournit les informations nécessaires pour mapper en mémoire la file de soumission, la file d'achèvement et le tableau des entrées de file de soumission. sq_entries spécifie le nombre d'entrées de file de soumission allouées. sq_off décrit les décalages de divers champs du tampon circulaire

: 


struct io_sqring_offsets {
    __u32 head;
    __u32 tail;
    __u32 ring_mask;
    __u32 ring_entries;
    __u32 flags;
    __u32 dropped;
    __u32 array;
    __u32 resv1;
    __u64 user_addr;
}
;

Pris ensemble, sq_entries et sq_off fournissent toutes les informations nécessaires pour accéder au tampon circulaire de la file de soumission et au tableau des entrées de file de soumission. La file de soumission peut être mappée avec un appel comme

: 


ptr = mmap(0, sq_off.array + sq_entries * sizeof(__u32),
           PROT_READ|PROT_WRITE, MAP_SHARED|MAP_POPULATE,
           ring_fd, IORING_OFF_SQ_RING)
;

où sq_off est la structure io_sqring_offsets, et ring_fd est le descripteur de fichier retourné par io_uring_setup(2). L'ajout de sq_off.array à la longueur de la région tient compte du fait que l'anneau est situé à la fin de la structure de données. Par exemple, le pointeur de tête du tampon circulaire peut être accessible en ajoutant sq_off.head à l'adresse retournée par mmap(2)

: 


head = ptr + sq_off.
head;

Le champ flags est utilisé par le noyau pour communiquer des informations d'état à l'application. Actuellement, il est utilisé pour informer l'application quand un appel à io_uring_enter(2) est nécessaire. Voir la documentation pour le indicateur IORING_SETUP_SQPOLL ci-dessus. Le membre dropped est incrémenté pour chaque entrée de file de soumission invalide rencontrée dans le tampon

circulaire.

La tête et la queue suivent l'état du tampon circulaire. La queue est incrémentée par l'application lors de la soumission de nouvelles E/S, et la tête est incrémentée par le noyau lorsque l'E/S a été soumise avec succès. Déterminer l'index de la tête ou de la queue dans l'anneau s'effectue en appliquant un masque

: 


index = tail &
ring_mask;

Le tableau des entrées de file de soumission est mappé avec

: 


sqentries = mmap(0, sq_entries * sizeof(struct io_uring_sqe),
                 PROT_READ|PROT_WRITE, MAP_SHARED|MAP_POPULATE,
                 ring_fd, IORING_OFF_SQES)
;

La file d'achèvement est décrite par cq_entries et cq_off montrés ici

: 


struct io_cqring_offsets {
    __u32 head;
    __u32 tail;
    __u32 ring_mask;
    __u32 ring_entries;
    __u32 overflow;
    __u32 cqes;
    __u32 flags;
    __u32 resv1;
    __u64 user_addr;
}
;

La file d'achèvement est plus simple, car les entrées ne sont pas séparées de la file elle-même, et peut être mappée avec

: 


ptr = mmap(0, cq_off.cqes + cq_entries * sizeof(struct io_uring_cqe),
           PROT_READ|PROT_WRITE, MAP_SHARED|MAP_POPULATE, ring_fd,
           IORING_OFF_CQ_RING)
;

Fermer le descripteur de fichier retourné par io_uring_setup(2) libérera toutes les ressources associées au contexte io_uring. Notez que cela peut se produi

re de manière asynchrone dans le noyau, il n'est donc pas
garanti que les ressources soient libérées immédiatement.
