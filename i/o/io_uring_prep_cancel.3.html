NOM

io_uring_prep_cancel - préparer une requête d'annulation

SYNOPSIS

#include <liburing.h>
void io_uring_prep_cancel64(struct io_uring_sqe *sqe,
                            __u64 user_data,
                            int flags);
void io_uring_prep_cancel(struct io_uring_sqe *sqe,
                          void *user_data,
                          int flags);
void io_uring_prep_cancel_fd(struct io_uring_sqe *sqe,
                          int fd,
                          unsigned int flags);

DESCRIPTION

La fonction io_uring_prep_cancel(3) prépare une requête d'annulation. L'entrée de la file d'attente de soumission sqe est préparée pour annuler une requête existante identifiée par user_data. Pour l'argument flags, voir ci-dessous.

io_uring_prep_cancel64(3) est identique à io_uring_prep_cancel(3), sauf qu'elle accepte un entier 64 bits plutôt qu'un type pointeur.

La requête d'annulation tentera de trouver la requête précédemment émise identifiée par user_data et de l'annuler. L'identifiant est ce que la requête précédemment émise a dans son champ user_data dans le SQE.

La fonction io_uring_prep_cancel_fd(3) prépare une requête d'annulation. L'entrée de la file d'attente de soumission sqe est préparée pour annuler une requête existante qui utilisait le descripteur de fichier fd. Pour l'argument flags, voir ci-dessous.

La requête d'annulation tentera de trouver la requête précédemment émise qui utilisait fd comme descripteur de fichier et de l'annuler.

Par défaut, la première requête correspondant aux critères donnés sera annulée. Ceci peut être modifié en utilisant l'un des drapeaux suivants passés :

IORING_ASYNC_CANCEL_ALL
Annuler toutes les requêtes correspondant aux critères donnés, plutôt que d'annuler seulement la première trouvée. Disponible depuis 5.19.
IORING_ASYNC_CANCEL_FD
Correspondance basée sur le descripteur de fichier utilisé dans la requête d'origine plutôt que sur user_data. C'est ce que configure io_uring_prep_cancel_fd(3). Disponible depuis 5.19.
IORING_ASYNC_CANCEL_FD_FIXED
Défini conjointement avec IORING_ASYNC_CANCEL_FD , indiquant que le descripteur de fichier donné est un descripteur direct plutôt qu'un descripteur de fichier normal. Disponible depuis 6.0.
IORING_ASYNC_CANCEL_ANY
Correspond à toute requête dans le ring, indépendamment de user_data ou du descripteur de fichier. Peut être utilisé pour annuler toute requête en attente dans le ring. Disponible depuis 5.19.
IORING_ASYNC_CANCEL_USERDATA
Correspond à une requête basée sur le champ user_data défini dans la requête d'origine. C'est la clé de recherche par défaut, si aucune autre clé correspondante n'a été spécifiée. Disponible depuis 6.6.
IORING_ASYNC_CANCEL_OP
Utiliser l'opcode de la requête d'origine comme clé de correspondance. L'opcode demandé doit être défini dans le champ len du sqe après avoir utilisé l'une des fonctions de préparation d'annulation génériques. Disponible depuis 6.6.

VALEUR DE RETOUR

Aucune

ERREURS

Ce sont les erreurs qui sont rapportées dans le champ res du CQE. Si aucun drapeau n'est utilisé pour annuler plusieurs requêtes, 0 est retourné en cas de succès. Si des drapeaux sont utilisés pour faire correspondre plusieurs requêtes, une valeur positive est retournée indiquant combien de requêtes ont été trouvées et annulées.

-ENOENT
La requête identifiée par user_data n'a pas pu être trouvée. Cela peut être parce qu'elle s'est terminée avant que la requête d'annulation ne soit émise, ou si un identifiant invalide est utilisé.
-EINVAL
L'un des champs définis dans le SQE était invalide.
-EALREADY
L'état d'exécution de la requête a suffisamment progressé pour que l'annulation ne soit plus possible. Cela signifie normalement qu'elle se terminera bientôt, soit avec succès, soit interrompue en raison de l'annulation.

NOTES

Bien que la requête d'annulation utilise la syntaxe des requêtes asynchrones, le côté noyau de l'annulation est toujours exécuté de manière synchrone. Il est garanti qu'un CQE est toujours généré au moment où la requête d'annulation a été soumise. Si l'annulation réussit, l'achèvement de la requête ciblée pour l'annulation aura été posté au moment où la soumission retourne. Pour -EALREADY, cela peut prendre un certain temps. Dans ce cas, l'appelant doit attendre que la requête annulée poste son événement d'achèvement.
