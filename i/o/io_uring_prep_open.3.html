io_uring_prep_openat(3) Manuel liburing io_uring_prep_openat(3)

NOM

io_uring_prep_openat - préparer une requête d'ouverture

SYNTAXE

#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <liburing.h>
void io_uring_prep_open(struct io_uring_sqe *sqe,
                          const char *path,
                          int flags,
                          mode_t mode);
void io_uring_prep_open_direct(struct io_uring_sqe *sqe,
                                 const char *path,
                                 int flags,
                                 mode_t mode,
                                 unsigned file_index);
void io_uring_prep_openat(struct io_uring_sqe *sqe,
                          int dfd,
                          const char *path,
                          int flags,
                          mode_t mode);
void io_uring_prep_openat_direct(struct io_uring_sqe *sqe,
                                 int dfd,
                                 const char *path,
                                 int flags,
                                 mode_t mode,
                                 unsigned file_index);

DESCRIPTION

La fonction io_uring_prep_openat(3) prépare une requête d'ouverture. L'entrée de la file d'attente de soumission sqe est configurée pour utiliser le descripteur de fichier du répertoire dfd pour commencer l'ouverture d'un fichier décrit par path et en utilisant les drapeaux d'ouverture dans flags et les bits de mode de fichier spécifiés dans mode. De même, io_uring_prep_open(3) prépare une requête d'ouverture.

Si la variante directe est utilisée, l'application doit d'abord avoir enregistré une table de fichiers à l'aide de io_uring_register_files(3) de la taille appropriée. Une fois enregistrée, une requête d'acceptation directe peut utiliser n'importe quelle entrée de cette table et est spécifiée dans file_index , tant qu'elle est dans les limites de la taille de la table enregistrée. Si une entrée spécifiée contient déjà un fichier, le fichier sera d'abord retiré de la table et fermé. C'est cohérent avec le comportement de mise à jour d'un fichier existant avec io_uring_register_files_update(3).

Si IORING_FILE_INDEX_ALLOC est utilisé comme file_index pour une ouverture directe, alors io_uring allouera un descripteur direct libre dans la table existante. Le descripteur alloué est retourné dans le champ res du CQE, comme il le serait pour une requête d'ouverture non directe. Si plus aucune entrée n'est disponible dans la table des descripteurs directs, -ENFILE est retourné à la place.

Les descripteurs directs sont des descripteurs de fichiers privés d'io_uring. Ils évitent une partie de la surcharge associée aux tables de fichiers partagées par les threads et peuvent être utilisés dans toute requête io_uring ultérieure qui prend un descripteur de fichier. Pour ce faire, IOSQE_FIXED_FILE doit être défini dans le membre flags du SQE, et le champ fd du SQE doit utiliser la valeur du descripteur direct plutôt que le descripteur de fichier régulier. Les descripteurs directs sont gérés comme des fichiers enregistrés.

Le descripteur de fichier du répertoire dfd est toujours un descripteur de fichier régulier.

Notez que les anciens noyaux ne vérifient pas le champ file_index du SQE, ce qui n'est pas un problème pour les aides de liburing, mais les utilisateurs de l'interface io_uring brute doivent initialiser les SQE à zéro pour éviter un comportement inattendu.

Ces fonctions préparent une requête asynchrone d'openat(2) ou d'open(2). Voir la page man correspondante pour les détails.

VALEUR DE RETOUR

Aucune

ERREURS

Le champ res du CQE contiendra le résultat de l'opération. Voir la page man associée pour les détails sur les valeurs possibles. Notez que là où les appels système synchrones retourneront -1 en cas d'échec et définiront errno à la valeur d'erreur réelle, io_uring n'utilise jamais errno. Il retourne plutôt l'errno négativé directement dans le champ res du CQE.

NOTES

Comme pour toute requête qui passe des données dans une structure, ces données doivent rester valides jusqu'à ce que la requête ait été soumise avec succès. Elles n'ont pas besoin de rester valides jusqu'à l'achèvement. Une fois qu'une requête a été soumise, l'état interne au noyau est stable. Les tout premiers noyaux (5.4 et antérieurs) exigeaient que l'état soit stable jusqu'à l'achèvement. Les applications peuvent tester ce comportement en inspectant le drapeau IORING_FEAT_SUBMIT_STABLE renvoyé par io_uring_queue_init_params(3).
