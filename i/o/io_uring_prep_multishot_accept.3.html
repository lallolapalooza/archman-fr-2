DESCRIPTIO

N

La fonction io_uring_prep_accept(3) et ses trois variantes préparent une requête accept similaire à accept4(2). L'entrée de file d'attente de soumission (SQE) sqe est configurée pour utiliser le descripteur de fichier sockfd afin de commencer à accepter une requête de connexion décrite par l'adresse de socket à addr et de longueur de structure addrlen, en utilisant les indicateurs de modification dans flags

.

Les trois variantes permettent de combiner les fonctionnalités de table de fichiers directe et

multishot.

Les descripteurs directs sont des descripteurs de fichier privés à io_uring. Ils évitent certaines des surcharges associées aux tables de fichiers partagées entre threads et peuvent être utilisés dans n'importe quelle requête io_uring qui prend un descripteur de fichier. Les deux variantes directes ici créent de tels descripteurs directs. Après leur création, ils peuvent être utilisés en définissant IOSQE_FIXED_FILE dans le membre flags de la SQE, et en définissant le champ fd de la SQE à la valeur du descripteur direct plutôt qu'au descripteur de fichier normal. Les descripteurs directs sont gérés comme des fichiers

enregistrés.

Pour utiliser une variante directe d'accept, l'application doit d'abord avoir enregistré une table de fichiers de la taille souhaitée en utilisant io_uring_register_files(3) ou io_uring_register_files_sparse(3). Une fois enregistrée, io_uring_prep_accept_direct(3) permet qu'une entrée de cette table soit spécifiquement sélectionnée via l'argument file_index. Si l'entrée spécifiée contient déjà un fichier, le fichier sera d'abord retiré de la table et fermé, conformément au comportement de mise à jour d'un fichier existant avec io_uring_register_files_update(3). file_index peut également être défini à IORING_FILE_INDEX_ALLOC pour cette variante et un index de table inutilisé sera choisi dynamiquement et renvoyé. De même, io_uring_prep_multishot_accept_direct aura un index de table inutilisé choisi dynamiquement et renvoyé pour chaque connexion acceptée. Si les deux formes de sélection directe seront utilisées, spécifique et dynamique, voir io_uring_register_file_alloc_range(3) pour configurer la table afin que les entrées choisies dynamiquement soient faites contre une plage différente de celle visée par les requêtes

spécifiques.

Notez que les anciens noyaux ne vérifient pas le champ file_index de la SQE, ce qui signifie que les applications ne peuvent pas compter sur un CQE -EINVAL res étant renvoyé lorsque le noyau est trop ancien, car les anciens noyaux peuvent ne pas reconnaître qu'on leur demande d'utiliser un emplacement de table

directe.

Lorsqu'une requête accept avec descripteur direct demande qu'un emplacement de table soit choisi dynamiquement mais qu'il n'y a pas d'entrées libres, -ENFILE est renvoyé comme res du

CQE.

Les variantes multishot permettent à une application d'émettre une seule requête accept, qui déclenchera à plusieurs reprises un CQE lorsqu'une requête de connexion arrive. Comme pour les autres requêtes de type multishot, l'application doit examiner les flags du CQE et voir si IORING_CQE_F_MORE est défini à la fin comme indication de savoir si la requête accept générera d'autres CQE. Notez que pour les variantes multishot, définir addr et addrlen peut ne pas avoir beaucoup de sens, car la même valeur serait utilisée pour chaque connexion acceptée. Cela signifie que les données écrites dans addr peuvent être écrasées par une nouvelle connexion avant que l'application ait eu le temps de traiter une connexion passée. Si l'application sait qu'une nouvelle connexion ne peut pas arriver avant qu'une précédente ait été traitée, elle peut être utilisée comme prévu. Les variantes multishot sont disponibles depuis la version 5.

19.

ERREUR

S

Le champ res du CQE contiendra le résultat de

l'opération.

io_uring_prep_accept(3) génère le descripteur de fichier installé comme

résultat.

io_uring_prep_accept_direct(3) et file_index défini à un descripteur direct spécifique génère 0 en cas de succès. L'appelant doit se souvenir de quel descripteur direct a été choisi pour cette

requête.

io_uring_prep_accept_direct(3) et file_index défini à IORING_FILE_INDEX_ALLOC génère le descripteur direct choisi

dynamiquement.

io_uring_prep_multishot_accept(3) génère le descripteur de fichier installé dans chaque

résultat.

io_uring_prep_multishot_accept_direct(3) génère le descripteur direct choisi dynamiquement dans chaque

résultat.

Notez que là où les appels système synchrones renverront -1 en cas d'échec et définiront errno à la valeur d'erreur réelle, io_uring n'utilise jamais errno. Au lieu de cela, il génère le errno négé directement dans le champ res du

C
QE.

NOTE

S

Comme pour toute requête qui transmet des données dans une struct, ces données doivent rester valides jusqu'à ce que la requête ait été soumise avec succès. Elles n'ont pas besoin de rester valides jusqu'à l'achèvement. Une fois qu'une requête a été soumise, l'état dans le noyau est stable. Les noyaux très anciens (5.4 et antérieurs) exigeaient que l'état soit stable jusqu'à ce que l'achèvement se produise. Les applications peuvent tester ce comportement en inspectant l'indicateur IORING_FEAT_SUBMIT_STABLE renvoyé par io_uring_queue_init_

params(3).

Notez que les versions directes de accept n'acceptent pas SOCK_CLOEXEC , et définir cet indicateur entraînera une erreur -EINV

AL dans
le CQE.
