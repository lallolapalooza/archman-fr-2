N

io_uring_enter(2) est utilisé pour initier et terminer des E/S en utilisant les files d'attente de soumission et d'achèvement partagées configurées par un appel à io_uring_setup(2). Un appel unique peut à la fois soumettre de nouvelles E/S et attendre les achèvements des E/S initiées par cet appel ou par des appels précédents à io_uring_ent

er(2).

fd est le descripteur de fichier renvoyé par io_uring_setup(2). to_submit spécifie le nombre d'E/S à soumettre depuis la file d'attente de soumission. flags est un masque de bits des valeurs suivantes

:
IORING_ENTER_GETEVE
NTS
Si ce drapeau est défini, l'appel système attendra le nombre spécifié d'événements dans min_complete avant de renvoyer. Ce drapeau peut être défini en même temps que to_submit pour à la fois soumettre et terminer des événements dans un appel système unique. Si ce drapeau est défini, soit le drapeau IORING_SETUP_DEFER_TASKRUN ne doit pas être défini, soit le thread qui émet l'appel système doit être le thread qui a créé l'io_uring associé à fd, ou être le thread qui a activé l'anneau initialement créé avec IORING_SETUP_R_DISABLED via io_uring_register(2) ou io_uring_enable_r
ings(3).
IORING_ENTER_SQ_WAK

Cela peut conduire à une situation où l'application ne peut plus obtenir d'entrée SQE libre pour soumettre, sans savoir quand une entrée deviendra disponible alors que le thread noyau SQ les consomme. Si l'instance io_uring était configurée pour l'interrogation (polling), en spécifiant IORING_SETUP_IOPOLL dans l'appel à io_uring_setup(2), alors min_complete a une signification légèrement différente. Passer une valeur de 0 indique au noyau de renvoyer tous les événements déjà terminés, sans bloquer. Si min_complete est une valeur non nulle, le noyau renverra toujours immédiatement si des événements d'achèvement sont disponibles. Si aucun achèvement d'événement n'est disponible, l'appel interrogera jusqu'à ce qu'une ou plusieurs complétions deviennent disponibles, ou jusqu'à ce que le processus ait dépassé sa tranche de temps d'ordonnancement

.

Notez que, pour les E/S pilotées par interruption (où IORING_SETUP_IOPOLL n'a pas été spécifié dans l'appel à io_uring_setup(2)), une application peut vérifier la file d'achèvement pour les achèvements d'événements sans entrer dans le noyau du

tout.

Lorsque l'appel système renvoie qu'une certaine quantité d'SQE a été consommée et soumise, il est sûr de réutiliser les entrées SQE dans l'anneau. C'est vrai même si la soumission d'E/S réelle a dû être déléguée au contexte asynchrone, ce qui signifie que l'SQE peut en fait ne pas avoir été soumis encore. Si le noyau a besoin d'utiliser ultérieurement une entrée SQE particulière, il aura fait une copie privée de

celle-ci.

sig est un pointeur vers un masque de signaux (voir sigprocmask(2)) ; si sig n'est pas NULL, io_uring_enter(2) remplace d'abord le masque de signaux courant par celui vers lequel pointe sig, puis attend que des événements deviennent disponibles dans la file d'achèvement, et restaure ensuite le masque de signaux d'origine. L'appel io_uring_enter(2) suivant

: 


ret = io_uring_enter(fd, 0, 1, IORING_ENTER_GETEVENTS, &sig)
;

est équivalent à l'exécution atomique des appels suivants

: 


pthread_sigmask(SIG_SETMASK, &sig, &orig);
ret = io_uring_enter(fd, 0, 1, IORING_ENTER_GETEVENTS, NULL);
pthread_sigmask(SIG_SETMASK, &orig, NULL)
;

Voir la description de pselect(2) pour une explication de pourquoi le paramètre sig est

nécessaire.

L'opcode décrit l'opération à effectuer. Il peut s'agir de l'un des suivants :

IORING_OP_NOP
Ne pas effectuer d'opération d'E/S. Ceci est utile pour tester les performances de l'implémentation io_uring elle-même.
IORING_OP_READV
IORING_OP_WRITEV
Opérations de lecture et écriture vectorielles, similaires à preadv2(2) et pwritev2(2). Si le fichier n'est pas positionnable, off doit être défini sur zéro ou -1.
IORING_OP_READ_FIXED
IORING_OP_WRITE_FIXED
Lire depuis ou écrire dans des tampons pré-mappés. Voir io_uring_register(2) pour les détails sur la configuration d'un contexte pour les lectures et écritures fixes.
IORING_OP_FSYNC
Synchronisation de fichier. Voir aussi fsync(2). Optionnellement, off et len peuvent être utilisés pour spécifier une plage dans le fichier à synchroniser plutôt que de synchroniser le fichier entier, ce qui est le comportement par défaut. Notez que, bien que les E/S soient initiées dans l'ordre où elles apparaissent dans la file d'attente de soumission, les achèvements ne sont pas ordonnés. Par exemple, une application qui place une opération d'écriture suivie d'une opération fsync dans la file d'attente de soumission ne peut pas s'attendre à ce que l'opération fsync s'applique à l'écriture. Les deux opérations s'exécutent en parallèle, de sorte que l'opération fsync peut s'achever avant que l'écriture ne soit émise vers le stockage. Il en va de même pour les écritures précédemment émises qui ne sont pas encore terminées avant l'opération fsync. Pour imposer l'ordre, on peut utiliser des SQE liés, IOSQE_IO_DRAIN ou attendre l'arrivée des CQE des requêtes qui doivent être ordonnées avant une requête donnée avant de soumettre son SQE.
IORING_OP_POLL_ADD
Interroger le fd spécifié dans l'entrée de la file d'attente de soumission pour les événements spécifiés dans le champ poll_events. Contrairement à poll ou epoll sans EPOLLONESHOT, par défaut, cette interface fonctionne toujours en mode "one shot". C'est-à-dire qu'une fois l'opération de sondage terminée, elle devra être resoumise.

Si IORING_POLL_ADD_MULTI est défini dans le champ len du SQE, alors le sondage fonctionnera en mode "multi shot" à la place. Cela signifie qu'il se déclenchera à plusieurs reprises lorsque l'événement demandé deviendra vrai, et donc plusieurs CQE peuvent être générés à partir de ce seul SQE. Le champ flags du CQE aura IORING_CQE_F_MORE défini à l'achèvement si l'application doit s'attendre à d'autres entrées CQE provenant de la requête d'origine. Si ce drapeau n'est pas défini à l'achèvement, alors la requête de sondage a été terminée et aucun autre événement ne sera généré. Ce mode est disponible depuis 5.13.

Cette commande fonctionne comme un poll(2) asynchrone et le résultat de l'événement d'achèvement est le masque des événements retournés.

Sans IORING_POLL_ADD_MULTI et avec l'opération de sondage initiale avec IORING_POLL_ADD_MULTI, l'opération est déclenchée par niveau, c'est-à-dire que s'il y a des données prêtes ou des événements en attente etc. au moment de la soumission, un CQE correspondant sera posté. Les futures completions potentielles au-delà de la première causée par un IORING_POLL_ADD_MULTI sont déclenchées par front.

IORING_OP_POLL_REMOVE
Supprimer ou mettre à jour une requête de sondage existante. Si trouvée, le champ res de la struct io_uring_cqe contiendra 0. Si non trouvée, res contiendra -ENOENT, ou -EALREADY si la requête de sondage était déjà en cours d'achèvement.

Si IORING_POLL_UPDATE_EVENTS est défini dans le champ len du SQE, alors la requête mettra à jour une requête de sondage existante avec le masque d'événements passé avec cette requête. La recherche est basée sur le champ user_data du SQE soumis à l'origine, et cette valeur est passée dans le champ addr du SQE. Si IORING_POLL_UPDATE_USER_DATA est défini dans le champ len du SQE, alors la requête mettra à jour le user_data d'une requête de sondage existante en fonction de la valeur passée dans le champ off. La mise à jour d'un sondage existant est disponible depuis 5.13.

IORING_OP_EPOLL_CTL
Ajouter, supprimer ou modifier des entrées dans la liste d'intérêt de epoll(7). Voir epoll_ctl(2) pour les détails de l'appel système. fd contient le descripteur de fichier qui représente l'instance epoll, off contient le descripteur de fichier à ajouter, supprimer ou modifier, len contient l'opération ( EPOLL_CTL_ADD, EPOLL_CTL_DEL, EPOLL_CTL_MOD) à effectuer et addr contient un pointeur vers la structure epoll_event. Disponible depuis 5.6.
IORING_OP_SYNC_FILE_RANGE
Émettre l'équivalent d'un sync_file_range(2) sur le descripteur de fichier. Le champ fd est le descripteur de fichier à synchroniser, le champ off contient le décalage en octets, le champ len contient la longueur en octets, et le champ sync_range_flags contient les indicateurs de la commande. Voir aussi sync_file_range(2) pour la description générale de l'appel système associé. Disponible depuis 5.2.

OUT
Cette commande enregistrera une opération de temporisation. Le addr doit contenir un pointeur vers une structure struct __kernel_timespec, len doit contenir 1 pour signifier une structure __kernel_timespec, timeout_flags peut contenir IORING_TIMEOUT_ABS pour une valeur de temporisation absolue, ou 0 pour une temporisation relative. off peut contenir un compte d'événements de complétion. Une temporisation déclenchera un événement de réveil sur l'anneau de complétion pour quiconque attend des événements. Une condition de temporisation est remplie lorsque soit la temporisation spécifiée expire, soit le nombre spécifié d'événements est complété. L'une ou l'autre condition déclenchera l'événement. Si défini à 0, les événements complétés ne sont pas comptés, ce qui agit effectivement comme un minuteur. Les temporisations io_uring utilisent le CLOCK_MONOTONIC comme source d'horloge par défaut. La requête se complétera avec -ETIME si la temporisation s'est complétée par l'expiration du minuteur, ou 0 si la temporisation s'est complétée par des requêtes se complétant d'elles-mêmes. Si la temporisation a été annulée avant son expiration, la requête se complétera avec -ECANCELED. Disponible depuis 5.4.

Ce drapeau n'a aucun effet sur les soumissions de SQE précédentes, ni n'affecte les SQE qui se trouvent en dehors de la fin de la chaîne. Cela signifie que plusieurs chaînes peuvent être exécutées en parallèle, ou des chaînes et des SQE individuels. Seuls les membres à l'intérieur de la chaîne sont sérialisés. Une chaîne de SQE sera interrompue si une requête de cette chaîne se termine par une erreur. io_uring considère tout résultat inattendu comme une erreur. Cela signifie que, par exemple, une lecture courte terminera également le reste de la chaîne. Si une chaîne de liens de SQE est interrompue, la partie non démarrée restante de la chaîne sera terminée et complétée avec -ECANCELED comme code d'erreur. Disponible depuis la version
5.3.
IOSQE_IO_HARDL
INK
Comme IOSQE_IO_LINK, mais il ne se rompt pas quel que soit le résultat de la complétion. Notez que le lien se rompra toujours si nous échouons à soumettre la requête parente, les liens durs ne sont résilients qu'en présence de résultats de complétion pour les requêtes qui ont été soumises correctement. IOSQE_IO_HARDLINK implique IOSQE_IO_LINK. Disponible depuis la version
5.5.

NC
Le fonctionnement normal de io_uring est de tenter d'émettre un sqe en non-bloquant d'abord, et si cela échoue, de l'exécuter de manière asynchrone. Pour prendre en charge une opération superposée plus efficace des requêtes que l'application sait/supposera toujours (ou la plupart du temps) bloquer, l'application peut demander qu'un sqe soit émis de manière asynchrone dès le début. Disponible depuis la version
5.6.
IOSQE_BUFFER_SEL
ECT
Utilisé en conjonction avec la commande IORING_OP_PROVIDE_BUFFERS, qui enregistre un pool de tampons à utiliser par les commandes qui lisent ou reçoivent des données. Lorsque des tampons sont enregistrés pour ce cas d'utilisation, et que ce drapeau est défini dans la commande, io_uring prendra un tampon de ce pool lorsque la requête est prête à recevoir ou lire des données. En cas de succès, le CQE résultant aura IORING_CQE_F_BUFFER défini dans la partie flags de la structure, et les bits supérieurs IORING_CQE_BUFFER_SHIFT contiendront l'ID des tampons sélectionnés. Cela permet à l'application de savoir exactement quel tampon a été sélectionné pour l'opération. Si aucun tampon n'est disponible et que ce drapeau est défini, la requête échouera avec -ENOBUFS comme code d'erreur. Une fois qu'un tampon a été utilisé, il n'est plus disponible dans le pool du noyau. L'application doit ré-enregistrer le tampon donné à nouveau lorsqu'elle est prête à le recycler (par exemple, lorsqu'elle a terminé de l'utiliser). Disponible depuis la version
5.7.
IOSQE_CQE_SKIP_SUCC
ESS
Ne pas générer de CQE si la requête se termine avec succès. Si la requête échoue, un CQE approprié sera publié comme d'habitude et s'il n'y a pas de IOSQE_IO_HARDLINK, les CQE pour toutes les requêtes liées seront omis. La notion d'échec/succès est spécifique à l'opcode et est la même que pour l'interruption des chaînes de IOSQE_IO_LINK. Un cas particulier est lorsque la requête a un délai d'attente lié, auquel cas la génération du CQE pour le délai d'attente lié est décidée uniquement par le fait qu'il a IOSQE_CQE_SKIP_SUCCESS défini, qu'il ait expiré ou qu'il ait été annulé. En d'autres termes, si un délai d'attente lié a le drapeau défini, il est garanti de ne pas publier de CQE.

La sémantique est choisie pour s'adapter à plusieurs cas d'utilisation. Premièrement, lorsque toutes les requêtes sauf la dernière d'un lien normal sans délais d'attente liés sont marquées avec le drapeau, un seul CQE par lien est publié. De plus, cela permet la suppression des CQE dans les cas où les effets secondaires d'une opération exécutée avec succès suffisent à l'espace utilisateur pour connaître l'état du système. Un tel exemple serait l'écriture dans un fichier de

synchronisation.

Ce drapeau est incompatible avec IOSQE_IO_DRAIN. L'utilisation des deux dans une seule ring est un comportement indéfini, même lorsqu'ils ne sont pas utilisés ensemble dans une seule requête. Actuellement, après la première requête avec IOSQE_CQE_SKIP_SUCCESS, toutes les requêtes suivantes marquées avec drain échoueront au moment de la soumission. Notez que la déclaration d'erreur n'est qu'au mieux, et les restrictions pourraient changer à

l'avenir.
