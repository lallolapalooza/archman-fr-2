io_uring_prep_accept(3) Manuel liburing io_uring_prep_accept(3)

NOM

io_uring_prep_accept - préparer une requête d'acceptation

SYNTAXE

#include <sys/socket.h>
#include <liburing.h>
void io_uring_prep_accept(struct io_uring_sqe *sqe,
                          int sockfd,
                          struct sockaddr *addr,
                          socklen_t *addrlen,
                          int flags);
void io_uring_prep_accept_direct(struct io_uring_sqe *sqe,
                                 int sockfd,
                                 struct sockaddr *addr,
                                 socklen_t *addrlen,
                                 int flags,
                                 unsigned int file_index);
void io_uring_prep_multishot_accept(struct io_uring_sqe *sqe,
                                    int sockfd,
                                    struct sockaddr *addr,
                                    socklen_t *addrlen,
                                    int flags);
void io_uring_prep_multishot_accept_direct(struct io_uring_sqe *sqe,
                                           int sockfd,
                                           struct sockaddr *addr,
                                           socklen_t *addrlen,
                                           int flags);

DESCRIPTION

La fonction io_uring_prep_accept(3) et ses trois variantes préparent une requête d'acceptation similaire à accept4(2). L'entrée de la file d'attente de soumission sqe est configurée pour utiliser le descripteur de fichier sockfd afin d'accepter une demande de connexion décrite par l'adresse de socket à addr, de longueur de structure addrlen et utilisant les drapeaux modificateurs dans flags.

Les trois variantes permettent de combiner le descripteur de fichier direct et les fonctionnalités multishot.

Les descripteurs directs sont des descripteurs de fichiers privés io_uring. Ils évitent une partie de la surcharge associée aux tables de fichiers partagées par les threads et peuvent être utilisés dans toute requête io_uring qui prend un descripteur de fichier. Les deux variantes directes ici créent de tels descripteurs directs. Après leur création, ils peuvent être utilisés en définissant IOSQE_FIXED_FILE dans le membre flags du SQE, et en définissant le champ fd du SQE à la valeur du descripteur direct plutôt qu'au descripteur de fichier régulier. Les descripteurs directs sont gérés comme des fichiers enregistrés.

Pour utiliser une variante d'acceptation directe, l'application doit d'abord avoir enregistré une table de fichiers d'une taille désirée en utilisant io_uring_register_files(3) ou io_uring_register_files_sparse(3). Une fois enregistrée, io_uring_prep_accept_direct(3) permet à une entrée de cette table d'être spécifiquement sélectionnée via l'argument file_index. Si l'entrée spécifiée contient déjà un fichier, le fichier sera d'abord retiré de la table et fermé, conformément au comportement de mise à jour d'un fichier existant avec io_uring_register_files_update(3). file_index peut également être défini à IORING_FILE_INDEX_ALLOC pour cette variante et un index de table non utilisé sera choisi dynamiquement et retourné. De même, io_uring_prep_multishot_accept_direct aura un index de table non utilisé choisi dynamiquement et retourné pour chaque connexion acceptée. Si les deux formes de sélection directe seront utilisées, spécifiques et dynamiques, voir io_uring_register_file_alloc_range(3) pour configurer la table afin que les entrées choisies dynamiquement soient ciblées sur une plage différente de celle visée par les requêtes spécifiques.

Notez que les anciens noyaux ne vérifient pas le champ file_index du SQE, ce qui signifie que les applications ne peuvent pas s'attendre à recevoir un CQE res de -EINVAL lorsque le noyau est trop ancien, car les anciens noyaux peuvent ne pas reconnaître qu'on leur demande d'utiliser un emplacement de table directe.

Lorsqu'une requête d'acceptation directe demande un emplacement de table à choisir dynamiquement mais qu'il n'y a pas d'entrées libres, -ENFILE est retourné comme res du CQE.

Les variantes multishot permettent à une application d'émettre une seule requête d'acceptation, qui déclenchera répétitivement un CQE lorsqu'une demande de connexion arrivera. Comme les autres requêtes de type multishot, l'application doit examiner les flags du CQE et voir si IORING_CQE_F_MORE est défini à la fin comme indication de si la requête d'acceptation générera ou non d'autres CQEs. Notez que pour les variantes multishot, définir addr et addrlen peut ne pas avoir beaucoup de sens, car la même valeur serait utilisée pour chaque connexion acceptée. Cela signifie que les données écrites dans addr peuvent être écrasées par une nouvelle connexion avant que l'application n'ait eu le temps de traiter une connexion précédente. Si l'application sait qu'une nouvelle connexion ne peut pas arriver avant qu'une précédente n'ait été traitée, elle peut être utilisée comme prévu. Les variantes multishot sont disponibles depuis la version 5.19.

Voir la page de manuel accept4(2) pour les détails de la fonction d'acceptation elle-même.

VALEUR RETOURNÉE

Aucune

ERREURS

Le champ res du CQE contiendra le résultat de l'opération.

io_uring_prep_accept(3) génère le descripteur de fichier installé comme résultat.

io_uring_prep_accept_direct(3) et file_index défini à un descripteur direct spécifique génère 0 en cas de succès. L'appelant doit se souvenir du descripteur direct qui a été choisi pour cette requête.

io_uring_prep_accept_direct(3) et file_index défini à IORING_FILE_INDEX_ALLOC génère le descripteur direct choisi dynamiquement.

io_uring_prep_multishot_accept(3) génère le descripteur de fichier installé dans chaque résultat.

io_uring_prep_multishot_accept_direct(3), génère le descripteur direct choisi dynamiquement dans chaque résultat.

Notez que là où les appels système synchrones retourneront -1 en cas d'échec et définiront errno à la valeur d'erreur réelle, io_uring n'utilise jamais errno. Au lieu de cela, il génère l'errno négativé directement dans le champ res du CQE.

NOTES

Comme pour toute requête qui passe des données dans une struct, ces données doivent rester valides jusqu'à ce que la requête ait été soumise avec succès. Elles n'ont pas besoin de rester valides jusqu'à l'achèvement. Une fois qu'une requête a été soumise, l'état en noyau est stable. Les noyaux très anciens (5.4 et antérieurs) exigeaient que l'état reste stable jusqu'à l'achèvement. Les applications peuvent tester ce comportement en inspectant le drapeau IORING_FEAT_SUBMIT_STABLE renvoyé par io_uring_queue_init_params(3).

Notez que les versions directes d'accept n'acceptent pas SOCK_CLOEXEC, et la définition de ce drapeau entraînera une erreur -EINVAL dans le CQE.
