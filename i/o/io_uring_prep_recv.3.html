NOM

io_uring_prep_recv - préparer une requête de réception

SYNTAXE

#include <liburing.h>
void io_uring_prep_recv(struct io_uring_sqe *sqe,
                        int sockfd,
                        void *buf,
                        size_t len,
                        int flags);
void io_uring_prep_recv_multishot(struct io_uring_sqe *sqe,
                                  int sockfd,
                                  void *buf,
                                  size_t len,
                                  int flags);

DESCRIPTION

La fonction io_uring_prep_recv(3) prépare une requête de réception. L'entrée de la file d'attente de soumission sqe est configurée pour utiliser le descripteur de fichier sockfd afin de commencer à recevoir les données dans le tampon de destination buf d'une taille de len et avec les indicateurs modificateurs flags.

Cette fonction prépare une requête asynchrone de recv(2). Voir cette page de manuel pour les détails sur les arguments spécifiés à cette fonction d'aide de préparation.

La version multishot permet à l'application d'émettre une seule requête de réception, qui publie répétitivement un CQE lorsque des données sont disponibles. Elle nécessite que la longueur soit de 0, que le drapeau IOSQE_BUFFER_SELECT soit défini et que le drapeau MSG_WAITALL ne soit pas défini. Par conséquent, chaque CQE retirera un tampon d'un pool de tampons fourni pour la réception. L'application doit vérifier les drapeaux de chaque CQE, quel que soit son résultat. Si un CQE publié n'a pas le drapeau IORING_CQE_F_MORE défini, alors la réception multishot est terminée et l'application doit émettre une nouvelle requête si elle souhaite toujours recevoir des données du socket. Les variantes multishot sont disponibles depuis le noyau 6.0.

Après avoir appelé cette fonction, des indicateurs modificateurs internes supplémentaires d'io_uring peuvent être définis dans le champ ioprio du SQE. Les indicateurs suivants sont pris en charge :

IORING_RECVSEND_POLL_FIRST
S'il est défini, io_uring supposera que le socket est actuellement vide et que la tentative de réception de données sera infructueuse. Dans ce cas, io_uring armera un sondage interne et déclenchera une réception des données lorsque le socket disposera de données à lire. Cette tentative de réception initiale peut être inutile dans le cas où le socket est censé être vide ; la définition de cet indicateur contournera la tentative de réception initiale et passera directement à l'armement du sondage. Si le sondage indique que des données sont prêtes à être reçues, l'opération se poursuivra.

Peut être utilisé avec l'indicateur CQE IORING_CQE_F_SOCK_NONEMPTY, que io_uring définira sur les CQE après une opération recv(2) ou recvmsg(2). S'il est défini, le socket avait encore des données à lire après la fin de l'opération. Ces deux indicateurs sont disponibles depuis la version 5.19.

IORING_RECVSEND_BUNDLE
S'il est défini et que des tampons sont fournis avec IOSQE_BUFFER_SELECT, l'opération de réception tentera de remplir plusieurs tampons plutôt que d'en remplir un seul. Pour recevoir plusieurs tampons en une seule réception, l'ID du groupe de tampons défini dans le SQE doit être du type de ring fourni. S'il est défini, le champ res du CQE indique le nombre total d'octets reçus, et l'ID du tampon renvoyé dans le champ flags du CQE indique le premier tampon dans l'opération de réception. L'application doit traiter l'ID du tampon initial indiqué et jusqu'à ce que tous les octets res aient été vus pour savoir quel est le dernier tampon dans l'opération de réception. Les tampons consommés seront contigus à partir du tampon initial, dans l'ordre où ils apparaissent dans le ring de tampons. La structure CQE ne contient pas la position du tampon dans le ring de tampons ; par conséquent, afin d'identifier les tampons contenus par le paquet, il est conseillé de maintenir l'index de tête mis en cache par ring de tampons. Cet index de type uint16_t représente la position du prochain tampon à consommer dans le ring. À la fin d'une opération de réception, l'index de tête mis en cache doit être incrémenté en conséquence. La réception en paquets peut améliorer les performances lorsque plus d'un bloc de données est disponible à recevoir, en éliminant les allers-retours redondants dans la pile réseau. Les paquets de réception peuvent être utilisés par les opérations de réception à plan unique et multishot. Notez que, en interne, les paquets s'appuient sur la pile réseau pour renvoyer la quantité de données restante dans le socket après la réception initiale. Cela signifie que la réception initiale peut contenir moins de paquets que ce qui est disponible, les réceptions suivantes en contenant plus. Disponible depuis la version 6.10.

VALEUR DE RETOUR

Aucune

ERREURS

Le champ res du CQE contiendra le résultat de l'opération. Voir la page de manuel correspondante pour les détails sur les valeurs possibles. Notez que là où les appels système synchrones retourneront -1 en cas d'échec et définiront errno à la valeur d'erreur réelle, io_uring n'utilise jamais errno. Au lieu de cela, il renvoie directement le errno négativé dans le champ res du CQE.
