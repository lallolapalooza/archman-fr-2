NOM

ibacm - services de résolution d'adresses et de routage pour InfiniBand.

SYNTAXE

ibacm [-D] [-P] [-A fichier_addr] [-O fichier_options]

DESCRIPTION

L'IB ACM implémente et fournit un cadre pour les services de résolution de noms, d'adresses et de routes (chemins) sur InfiniBand. Il est destiné à résoudre les problèmes de mise à l'échelle de la configuration des connexions pour l'exécution d'applications MPI sur de grands clusters. L'IB ACM fournit les informations nécessaires pour établir une connexion, mais n'implémente pas le protocole CM.

Un utilisateur principal du service ibacm est la bibliothèque librdmacm. Cela permet aux applications d'utiliser le service ibacm sans modification de code ni nécessité d'être conscient que le service est utilisé. Les versions de librdmacm 1.0.12 - 1.0.15 peuvent invoquer les services IB ACM lorsqu'elles sont compilées avec l'option --with-ib_acm. Les versions 1.0.16 et ultérieures de librdmacm utiliseront automatiquement l'IB ACM s'il est installé. Les services IB ACM s'intègrent sous les routines rdma_resolve_addr, rdma_resolve_route et rdma_getaddrinfo. Pour un bénéfice maximal, la routine rdma_getaddrinfo devrait être utilisée, cependant les applications existantes devraient toujours bénéficier d'une amélioration significative de la mise à l'échelle des connexions en utilisant les appels disponibles dans librdmacm 1.0.11 et les versions précédentes.

L'IB ACM est axé sur la scalabilité, l'efficacité et l'extensibilité. Il implémente une architecture de plugins qui permet à un fournisseur de fournir son propre fournisseur propriétaire en plus du fournisseur par défaut. L'implémentation actuelle du fournisseur par défaut, ibacmp, limite le trafic réseau, les interactions SA et les services centralisés. Ibacmp prend en charge plusieurs protocoles de résolution afin de gérer différentes topologies de réseau.

Le package IB ACM est composé de trois éléments : le service central ibacm, la bibliothèque partagée du fournisseur par défaut ibacmp, et un utilitaire de test/configuration - ib_acme. Tous les trois sont des composants en espace utilisateur et sont disponibles pour Linux. Des détails supplémentaires sont donnés ci-dessous.

OPTIONS

-D
exécuter en mode démon (par défaut)
-P
exécuter comme processus standard
-A fichier_addr
fichier de configuration des adresses
-O fichier_options
fichier de configuration des options
--systemd
Activer l'intégration systemd. Cela inclut l'activation optionnelle par socket du socket d'écoute du démon.

GUIDE DE DÉMARRAGE RAPIDE

1. Prérequis : libibverbs et libibumad doivent être installés. La pile IB doit être en cours d'exécution avec IPoIB configuré. Ces étapes supposent que l'utilisateur a des privilèges administratifs.

2. Installer le package IB ACM. Cela installe ibacm, ibacmp, ib_acme et les scripts init.d.

3. Exécuter 'ibacm' en tant qu'administrateur pour démarrer le démon ibacm.

4. Facultativement, exécuter 'ib_acme -d <ip_destination> -v' pour vérifier que le service ibacm est en cours d'exécution.

5. Installer librdmacm, en utilisant l'option de compilation --with-ib_acm si nécessaire. Cette option de compilation n'est pas nécessaire avec librdmacm 1.0.17 ou plus récent. librdmacm utilisera automatiquement le service ibacm. En cas d'échec, librdmacm reviendra à la résolution normale.

6. Vous pouvez utiliser ib_acme -P pour collecter des statistiques de performance du démon ibacm local afin de voir si le service fonctionne correctement. De même, la commande ib_acme -e pourrait être utilisée pour énumérer tous les points de terminaison créés par le service ibacm local.

NOTES

ib_acme:

Le programme ib_acme a un double rôle. Il agit comme un utilitaire pour tester le fonctionnement de ibacm et aider à vérifier si le service ibacm et le protocole sélectionné sont utilisables pour une configuration de cluster donnée. De plus, il génère automatiquement des fichiers de configuration ibacm pour aider à la configuration manuelle ou l'éliminer.

fichiers de configuration ibacm:

Le service ibacm repose sur deux fichiers de configuration.

Le fichier ibacm_addr.cfg contient les correspondances noms et adresses pour chaque point de terminaison IB <périphérique, port, pkey>. Bien que les noms dans le fichier ibacm_addr.cfg puissent être n'importe quoi, ib_acme fait correspondre le nom d'hôte aux points de terminaison IB. Les adresses IP, en revanche, sont attribuées dynamiquement. Si le fichier d'adresses ne peut être trouvé, le service ibacm tentera d'en créer un en utilisant des valeurs par défaut.

Le fichier ibacm_opts.cfg fournit un ensemble d'options configurables pour le service central ibacm et le fournisseur par défaut, telles que le délai d'attente, le nombre de nouvelles tentatives, le niveau de journalisation, etc. ib_acme génère le fichier ibacm_opts.cfg en utilisant des informations statiques. Si un fichier d'options ne peut être trouvé, ibacm utilisera les valeurs par défaut.

ibacm:

Le service ibacm est responsable de la résolution des noms et des adresses en informations de chemin InfiniBand et de la mise en cache de ces données. Il devrait s'exécuter avec des privilèges administratifs.

ibacm implémente une interface client via des sockets TCP, qui est abstraite par la bibliothèque librdmacm. Un ou plusieurs fournisseurs peuvent être chargés par le service central, en fonction de la configuration. Dans le fournisseur par défaut ibacmp, un ou plusieurs protocoles backend sont utilisés pour satisfaire les requêtes utilisateur. Bien qu'ibacmp prenne en charge les requêtes d'enregistrement de chemin SA standard en backend, il prend également en charge un protocole de résolution basé sur le trafic multicast. Ce dernier n'est pas utilisable sur toutes les topologies de réseau, en particulier celles qui pourraient ne pas avoir de chemins réversibles ou des réseaux utilisant un routage torique. Les utilisateurs doivent utiliser l'utilitaire ib_acme pour vérifier que le protocole multicast est utilisable avant d'exécuter d'autres applications.

Conceptuellement, le fournisseur par défaut ibacmp implémente un protocole de type ARP et utilise soit des enregistrements multicast IB pour construire les données d'enregistrement de chemin, soit interroge directement la SA, en fonction du protocole de routage sélectionné. Par défaut, le fournisseur ibacmp utilise et met en cache les requêtes d'enregistrement de chemin SA.

Spécifiquement, tous les points de terminaison IB rejoignent un certain nombre de groupes multicast. Les groupes multicast diffèrent en fonction des débits, MTU, SL, etc., et sont priorisés. Tous les points de terminaison participants doivent pouvoir communiquer sur le groupe multicast de priorité la plus basse. ibacmp attribue un ou plusieurs noms/adresses à chaque point de terminaison IB en utilisant le fichier ibacm_addr.cfg. Les clients fournissent des noms ou adresses source et destination en entrée du service, et reçoivent en sortie des données d'enregistrement de chemin.

Le service fait correspondre le nom/adresse source d'un client à un point de terminaison IB local. Si le nom/adresse de destination n'est pas mis en cache localement dans le fournisseur par défaut, il envoie une requête multicast sur le groupe multicast de priorité la plus basse sur le point de terminaison local. La requête transporte une liste de groupes multicast que l'expéditeur peut utiliser. Le destinataire de la requête sélectionne le groupe multicast de priorité la plus élevée qu'il peut également utiliser et renvoie cette information directement à l'expéditeur. Les données de la requête sont mises en cache par tous les points de terminaison qui reçoivent le message de requête multicast. Le point de terminaison source met également en cache la réponse et utilise le groupe multicast qui a été sélectionné pour construire ou obtenir les données d'enregistrement de chemin, qui sont renvoyées au client.

L'implémentation actuelle du fournisseur ibacmp présente plusieurs restrictions supplémentaires :

- ibacmp est limité dans sa gestion des changements dynamiques. ibacm doit être arrêté et redémarré si un cluster est reconfiguré.

- Le support d'IPv6 n'a pas été vérifié.

- Le nombre de groupes multicast qu'un point de terminaison peut supporter est limité à 2.

ibacmp contient plusieurs caches internes. Ceux-ci incluent des caches pour les adresses de destination GID et LID. Ces caches peuvent être préchargés optionnellement. ibacm prend en charge le format "full" PathRecord du plugin dump_pr d'OpenSM, qui est utilisé pour précharger ces caches. Le format du fichier est spécifié dans le fichier ibacm_opts.cfg via le paramètre route_preload qui devrait être réglé sur full_opensm_v1 pour ce format de fichier. Le format par défaut est none, ce qui ne précharge pas ces caches. Voir dump_pr.notes.txt dans dump_pr pour plus d'informations sur le format de fichier full_opensm_v1 et comment configurer OpenSM pour générer ce fichier.

De plus, les caches de noms, IPv4 et IPv6 peuvent être préchargés en utilisant l'option addr_preload. La valeur par défaut est none, ce qui ne précharge pas ces caches. Pour précharger ces caches, réglez cette option sur acm_hosts et configurez addr_data_file de manière appropriée.
