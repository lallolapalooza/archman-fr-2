DESCRIPTIO

N

ibv_reg_mr() enregistre une région mémoire (MR) associée au domaine de protection pd. L'adresse de début de la MR est addr et sa taille est length. L'argument access décrit les attributs de protection mémoire souhaités ; il vaut soit 0, soit le OU bit à bit d'un ou plusieurs des drapeaux suivants

ING
Ce paramètre permet à la carte réseau d'assouplir l'ordre dans lequel les données sont transférées entre le réseau et la région mémoire cible. L'ordre assoupli permet aux écritures initiées par le réseau (telles que les opérations d'envoi de message entrant ou d'écriture RDMA) d'atteindre la mémoire dans un ordre arbitraire. Cela peut améliorer
les performances de certaines applications. Cependant, l'ordre assoupli a l'impact suivant : l'ordre des messages d'écriture RDMA écriture-écriture n'est plus garanti. (Les messages envoyés correspondront toujours aux tampons de réception postés dans l'ordre.) Les écritures réseau consécutives ciblant la même région mémoire laissent la ré
gion dans un état inconnu. L'ordre assoupli ne change pas la sémantique d'achèvement, telle que la visibilité des données. C'est-à-dire qu'un achèvement garantit toujours que toutes les données sont visibles, y compris celles des transferts antérieurs. Les opérations en ordre assoupli ne contourneront pas non plus les opérations atomiques.

Si IBV_ACCESS_REMOTE_WRITE ou IBV_ACCESS_REMOTE_ATOMIC est défini, alors IBV_ACCESS_LOCAL_WRITE doit également être

défini.

L'accès en lecture local est toujours activé pour la

MR.

Pour créer une MR ODP implicite, IBV_ACCESS_ON_DEMAND doit être défini, addr doit valoir 0 et length doit valoir

SIZE_MAX.

Si IBV_ACCESS_HUGETLB est défini, l'application sait que pour cette MR toutes les pages sont volumineuses et doit promettre de ne jamais faire quoi que ce soit qui briserait les pages

volumineuses.

ibv_reg_mr_iova() ibv_reg_mr_iova est identique à reg_mr normal, sauf que l'utilisateur est autorisé à spécifier l'adresse de base virtuelle de la MR lorsqu'elle est accessible via une lkey ou rkey. L'offset dans la région mémoire est calculé comme 'addr + (iova - hca_va)'. Spécifier 0 pour hca_va a le même effet que IBV_ACCESS_ZERO_BASED

.

ibv_reg_dmabuf_mr() enregistre une région mémoire basée sur dma-buf (MR) associée au domaine de protection pd. La MR commence à offset du dma-buf et sa taille est length. Le dma-buf est identifié par le descripteur de fichier fd. L'argument iova spécifie l'adresse de base virtuelle de la MR lorsqu'elle est accessible via une lkey ou rkey. Elle doit avoir le même offset de page que offset. L'argument access décrit les attributs de protection mémoire souhaités ; il est similaire au cas de ibv_reg_mr, sauf que seuls les drapeaux suivants sont pris en charge : IBV_ACCESS_LOCAL_WRITE, IBV_ACCESS_REMOTE_WRITE, IBV_ACCESS_REMOTE_READ, IBV_ACCESS_REMOTE_ATOMIC, IBV_ACCESS_RELAXED_ORDERING

.

ibv_reg_mr_ex() ibv_reg_mr_ex est une API qui permet toutes les variantes des autres ibv_reg_mr_xxx() décrites dans cette page de manuel. Elle possède le champ mr_init_attr->comp_mask pour permettre à l'application d'indiquer les champs applicables. De plus, elle inclut mr_init_attr->dmah qui peut être utilisé pour inclure un objet ibv_dmah qui sera utilisé pour cette MR. Les autres champs du pointeur d'entrée ont la même signification que les champs décrits dans cette page de manuel pour les autres

verbes.

RETOUR

ibv_reg_mr() / ibv_reg_mr_iova() / ibv_reg_dmabuf_mr() / ibv_reg_mr_ex() renvoie un pointeur vers la MR enregistrée, ou NULL si la requête échoue. Le champ de clé locale (L_Key) lkey est utilisé comme champ lkey de struct ibv_sge lors de la publication de tampons avec les verbes ibv_post_*, et le champ de clé distante (R_Key) rkey est utilisé par les processus distants pour effectuer des opérations atomiques et RDMA. Le processus distant place cette rkey comme champ rkey de struct ibv_send_wr passé à la fonction

ibv_post_send.

ibv_dereg_mr() renvoie 0 en cas de succès, ou la valeur de er

rno en cas d'échec (ce qui
indique la raison de l'échec).
