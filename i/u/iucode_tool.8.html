NOM

iucode_tool - Outil pour manipuler les paquets de microcodes Intel® IA‐32/X86‐64

SYNTAXE

iucode_tool [options] [[-ttype] nom_fichier|nom_répertoire] ...

DESCRIPTION

iucode_tool est un utilitaire capable de charger des données de microcodes de processeurs Intel® à partir de fichiers aux formats texte et paquet binaire.

Il peut lister les microcodes contenus dans ces fichiers, les fusionner, les téléverser dans le noyau (pour mettre à jour le microcode dans les cœurs de processeur du système) ou en exporter certains dans un fichier au format binaire pour une utilisation ultérieure.

iucode_tool chargera tous les microcodes des fichiers et répertoires spécifiés en mémoire, afin de les traiter. Les microcodes dupliqués et obsolètes seront rejetés. Il peut lire les données de microcodes depuis l'entrée standard (stdin), en spécifiant le nom de fichier “-” (signe moins).

Les fichiers de données de microcodes sont supposés être au format texte .dat s'ils ont l'extension .dat, et au format binaire sinon. L'entrée standard (stdin) est supposée être au format texte .dat. L'option -t peut être utilisée pour changer le type des fichiers spécifiés après elle, y compris pour stdin.

Si un répertoire est spécifié, tous les fichiers dont le nom ne commence pas par un point seront chargés, dans un ordre non spécifié. Les sous-répertoires sont ignorés.

Les fichiers et répertoires vides sont ignorés et seront sautés.

Vous pouvez sélectionner les microcodes à exporter, lister ou téléverser dans le noyau en utilisant les options -S, -s, --date-before et --date-after. Si aucune de ces options n'est spécifiée, tous les microcodes seront sélectionnés.

Vous pouvez téléverser les microcodes sélectionnés dans le noyau, les exporter dans un fichier (au format binaire), dans une archive initramfs précoce Linux, dans des fichiers par signature de processeur dans un répertoire, ou dans des fichiers par microcode dans un répertoire en utilisant les options -w, --write-earlyfw, -k, -K et -W.

iucode_tool identifiera les microcodes dans ses messages de sortie et d'erreur en utilisant une notation “n/k”, où “n” est le numéro du paquet, et “k” est le numéro du microcode dans ce paquet. La sortie de l'option --list-all lors du traitement de plusieurs fichiers d'entrée est le meilleur exemple de son fonctionnement.

Pour plus d'informations sur les microcodes des processeurs Intel, veuillez lire la documentation incluse et les manuels Intel listés dans la section VOIR AUSSI.

OPTIONS

iucode_tool accepte les options suivantes :

-q, --quiet
Inhibe la sortie habituelle.
-v, --verbose
Affiche plus d'informations. Utiliser plusieurs fois pour augmenter la verborosité.
-h, -?, --help
Liste toutes les options disponibles et leur signification.
--usage
Affiche un résumé des options.
-V, --version
Affiche la version du programme.
-t type
Définit le type de fichier des fichiers suivants. type peut être :
b
Format binaire. C'est le même format utilisé par le pilote du noyau et le BIOS/EFI, qui est décrit en détail dans le manuel Intel 64 and IA‐32 Architectures Software Developer's Manual, Volume 3A, section 9.11.
d
Format texte .dat de microcode Intel. C'est le format normalement utilisé par Intel pour distribuer les fichiers de données de microcodes.
r
Récupérer le microcode au format binaire. Recherche dans les fichiers binaires génériques non compressés des microcodes au format binaire de microcode Intel pour les récupérer. Note : Il peut trouver des microcodes qui ne passeront pas les vérifications strictes, et ainsi provoquer la sortie de iucode_tool si les options --no-strict-checks ou --ignore-broken ne sont pas actives.
a
(par défaut) iucode_tool utilise le suffixe du nom de fichier pour sélectionner le type de fichier : format texte .dat pour les fichiers ayant une extension .dat, et type binaire sinon. Notez que pour stdin, le format texte .dat est supposé.
--downgrade
Lorsque plusieurs versions du microcode pour un processeur spécifique sont disponibles à partir de différents fichiers, conserve celle du fichier chargé en dernier, quelles que soient les révisions. Les fichiers sont toujours chargés dans l'ordre où ils ont été spécifiés sur la ligne de commande. Cette option n'a aucun effet lorsqu'un seul fichier a été chargé.
--no-downgrade
Lorsque plusieurs versions du microcode pour un processeur spécifique sont disponibles à partir de différents fichiers, conserve celle ayant le niveau de révision le plus élevé. C'est le mode de fonctionnement par défaut.
--strict-checks
Effectue des vérifications strictes sur les données du microcode. Il refusera de charger des microcodes et des fichiers de données de microcodes dont la taille et les métadonnées sont inattendues. Il refusera également de charger des entrées de microcode ayant les mêmes métadonnées, mais une charge utile différente. C'est le mode de fonctionnement par défaut.
--no-strict-checks
Effectue des vérifications moins strictes sur les données du microcode. À utiliser uniquement si vous rencontrez un fichier de données de microcode contenant des microcodes avec des tailles inhabituelles ou des métadonnées non critiques incorrectes (telles que des dates invalides), que vous souhaitez conserver. Si vous voulez simplement les ignorer, utilisez l'option --ignore-broken.
--ignore-broken
Ignore les entrées de microcode corrompues lors du chargement d'un fichier de données de microcode, au lieu d'arrêter l'exécution du programme. Si l'entrée de microcode a un format non pris en charge ou si son en-tête est gravement corrompu, toutes les données restantes dans le fichier devront être ignorées. Dans ce cas, il est recommandé d'utiliser un type de fichier de récupération de microcode au format binaire (option -tr), car cela permet d'ignorer les données de microcode mal endommagées.
--no-ignore-broken
Arrête l'exécution du programme si un microcode corrompu est trouvé lors du chargement d'un fichier de données de microcode. C'est le mode de fonctionnement par défaut.
-s ! | [!]signature[,[pf_mask][,[lt:|eq:|gt:]revision]]
Sélectionne les microcodes par signature, masque de flags du processeur (pf_mask) et révision spécifiés.

Si le masque de flags du processeur est spécifié, il ne sélectionnera que les microcodes qui conviennent à au moins une des combinaisons de flags du processeur présentes dans le masque.

Si la révision est spécifiée, éventuellement préfixée par l'un des opérateurs “eq:”, “lt:” ou “gt:”, elle ne sélectionnera que les microcodes qui ont cette même révision (si aucun opérateur, ou si l'opérateur “eq:” est utilisé), ou les microcodes dont la révision est inférieure (opérateur “lt:”), ou supérieure (opérateur “gt:”), à celle spécifiée.

Spécifiez plusieurs fois pour sélectionner plus de microcodes. Cette option peut être combinée avec l'option --scan-system pour sélectionner plus de microcodes. Si signature est préfixée par un “!” (point d'exclamation), elle désélectionnera les microcodes à la place. L'ordre compte, les options -s ultérieures annulant les précédentes, y compris --scan-system.

Lors de la spécification de signature et pf_mask, les nombres hexadécimaux doivent être préfixés par “0x”, et les nombres octaux par “0”. Les nombres décimaux ne doivent pas avoir de zéros non significatifs, sinon ils seraient interprétés comme des nombres octaux.

-S, --scan-system[=mode]
Sélectionne les microcodes en balayant les processeurs en ligne de ce système pour leurs signatures.

Cette option ne peut être utilisée qu'une seule fois et peut être combinée avec l'option -s pour sélectionner plus de microcodes. Les microcodes sélectionnés par --scan-system peuvent également être désélectionnés par une option ultérieure -s !signature.

L'argument optionnel mode (accepté uniquement par la version longue de l'option) sélectionne la stratégie utilisée pour balayer les processeurs :

0 ou auto
Actuellement identique à fast, mais cela pourrait changer dans les futures versions si Intel déployait des systèmes multi-signatures allant au-delà du mixed-stepping. C'est le mode de fonctionnement par défaut, pour la compatibilité ascendante avec les versions précédentes de iucode_tool.
1 ou fast
Utilise l'instruction cpuid pour détecter la signature du processeur sur lequel iucode_tool s'exécute, et sélectionne tous les steppings pour le type, la famille et le modèle de ce processeur. Prend en charge les systèmes mixed-stepping.
2 ou exact
Utilise les pilotes du noyau pour balayer directement la signature de chaque processeur en ligne. Ce mode prend en charge les systèmes multi-signatures. Ce mode de balayage sera lent sur les grands systèmes comportant de nombreux processeurs, et nécessitera probablement des permissions spéciales (comme l'exécution en tant qu'utilisateur root). Si le balayage échoue pour une raison quelconque, en guise de mesure de sécurité, il émettra un avertissement et considérera tous les steppings possibles pour chaque signature qu'il aura réussi à balayer avec succès.
--date-before=AAAA-MM-JJ et --date-after=AAAA-MM-JJ
Limite les microcodes sélectionnés par une plage de dates. La date doit être donnée au format ISO, avec quatre chiffres pour l'année et deux chiffres pour le mois et le jour et un signe «–» (tiret) comme séparateur. Les dates ne sont pas vérifiées en plage, vous pouvez donc utiliser --date-after=2000-00-00 pour sélectionner tous les microcodes datés depuis le 1er janvier 2000.
--loose-date-filtering
Lorsqu'une plage de dates est spécifiée, toutes les révisions du microcode seront considérées pour la sélection (en ignorant uniquement la plage de dates, tous les autres filtres s'appliquent toujours) si l'une des révisions du microcode se trouve dans la plage de dates.
--strict-date-filtering
Lorsqu'une plage de dates est spécifiée, sélectionnez uniquement les microcodes qui se trouvent dans la plage de dates. C'est le mode de fonctionnement par défaut.
-l, --list
Liste les signatures de microcodes sélectionnés sur la sortie standard (stdout).
-L, --list-all
Liste toutes les signatures de microcodes pendant leur traitement sur la sortie standard (stdout).
-k[périphérique], --kernel[=périphérique]
Charge les microcodes sélectionnés dans le noyau. Le chemin du périphérique peut être spécifié en option (défaut : /dev/cpu/microcode). Cette méthode de mise à jour est obsolète : elle sera éventuellement supprimée du noyau et de iucode_tool.
-K[répertoire], --write-firmware[=répertoire]
Écrit les microcodes sélectionnés avec les noms de fichiers attendus par le chargeur de firmware du noyau Linux. Le répertoire de destination peut être spécifié en option (défaut : /lib/firmware/intel‐ucode).
-wfichier, --write-to=fichier
Écrit les microcodes sélectionnés dans un fichier au format binaire.
--write-earlyfw=fichier
Écrit les microcodes sélectionnés dans une archive initramfs précoce, qui devrait être préfixée à l'initramfs régulier pour permettre au noyau de mettre à jour le microcode du processeur très tôt pendant le démarrage du système.
-Wrépertoire, --write-named-to=répertoire
Écrit les microcodes sélectionnés dans le répertoire spécifié, un microcode par fichier, au format binaire. Les noms de fichiers reflètent la signature du microcode, le masque des drapeaux du processeur et la révision.
--write-all-named-to=répertoire
Écrit chaque microcode dans le répertoire spécifié, un microcode par fichier, au format binaire. Les noms de fichiers reflètent la signature du microcode, le masque des drapeaux du processeur et la révision. C'est la seule façon d'écrire toutes les révisions du même microcode.
--overwrite
Supprime le fichier de destination avant l'écriture, s'il existe et n'est pas un répertoire. Le fichier de destination n'est pas écrasé sur place. Les hardlinks seront rompus, et les permissions d'accès existantes, les ACL et d'autres attributs étendus de l'ancien fichier de destination seront perdus.
--no-overwrite
Annule si le fichier de destination existe déjà. C'est le mode de fonctionnement par défaut. Notez que iucode_tool ne suit pas les liens symboliques non-répertoires lors de l'écriture des fichiers.
--mini-earlyfw
Optimise le conteneur cpio de l'initramfs précoce pour une taille minimale. Il modifiera la taille du bloc cpio à 16 octets et supprimera les entrées d'en-tête des répertoires parents du fichier de données du microcode. Par conséquent, le fichier de données du microcode ne sera pas disponible pour l'initramfs régulier, et les outils pourraient se plaindre de la taille de bloc cpio non standard.

Cela réduira généralement la taille de l'initramfs précoce de 736 octets.

--normal-earlyfw
Optimise la taille de l'initramfs précoce pour la compatibilité avec les outils. C'est le mode de fonctionnement par défaut. Le fichier de données du microcode sera également disponible dans l'initramfs régulier.

NOTES

iucode_tool lit toutes les données en mémoire avant d'effectuer un quelconque traitement. Il applique une limite de sécurité d'un maximum de 1 Gio de données de microcode binaires par fichier de données de microcode.

Tous les messages d'information et d'erreur sont envoyés sur la sortie d'erreur standard (stderr), tandis que la sortie demandée par l'utilisateur (telle que la sortie générée par les options de liste) est envoyée sur la sortie standard (stdout).

iucode_tool crée des fichiers avec les permissions 0644 (rw-r--r--), modifiées par l'umask actuel.

La liste des microcodes sélectionnés et les fichiers de sortie des microcodes de iucode_tool sont triés d'abord par signature du processeur (par ordre croissant), puis par masque des drapeaux du processeur (par ordre décroissant).

Lorsque plusieurs révisions d'un microcode sont sélectionnées, les plus anciennes seront ignorées. Seule la révision sélectionnée la plus récente d'un microcode (ou la dernière dans l'ordre de chargement lorsque l'option --downgrade est active) sera écrite dans un fichier ou chargée dans le noyau.

Les fichiers de données de microcode Intel, aux formats binaire et texte, peuvent être concaténés pour générer un fichier de données de microcode plus grand et toujours valide.

iucode_tool ne suit pas les liens symboliques lors de l'écriture des fichiers de données de microcode. Il refusera soit d'écrire le fichier et d'annuler (mode de fonctionnement par défaut), soit (lorsque l'option --overwrite est active) il supprimera le lien symbolique ou le fichier cible (et donc brisera les hardlinks) avant d'écrire le nouveau fichier.

iucode_tool suit les liens symboliques de répertoire pour localiser le répertoire dans lequel écrire les fichiers.

Notes Linux

Avant Linux v4.4, le pilote de mise à jour du microcode était divisé en deux parties : le pilote de mise à jour précoce du microcode (qui récupère les données du microcode depuis l'initramfs) et le pilote de mise à jour tardif du microcode, qui pouvait être un module et récupérait les données du microcode depuis le sous-système firmware. Les deux pilotes ont été unifiés dans Linux v4.4.

Le pilote de mise à jour du microcode doit être présent dans le système à tout moment pour garantir que les mises à jour du microcode sont réappliquées lors de la reprise après une mise en veille et lors du hotplug des CPU. Ne déchargez pas le module microcode, à moins de savoir vraiment ce que vous faites. Depuis Linux v4.4, le pilote de microcode tardif ne peut plus être un module et sera toujours présent dans le système lorsqu'il est activé.

La mise à jour précoce du microcode est plus sûre. Elle ne peut être effectuée qu'au démarrage et nécessite une initramfs, mais elle est fortement recommandée : les mises à jour tardives du microcode (qui lisent les données du microcode depuis /lib/firmware) ne peuvent pas modifier en toute sécurité les fonctionnalités visibles du processeur.

Les mises à jour précoces du microcode sont disponibles depuis Linux v3.9. Elles peuvent modifier en toute sécurité les fonctionnalités visibles du processeur (comme les mises à jour du microcode qui ont désactivé les instructions TSX d'Intel sur les cœurs Haswell d'Intel). Elles nécessitent une image initramfs non compressée avec les données de mise à jour du microcode dans /kernel/x86/microcode/GenuineIntel.bin. Cette image initramfs non compressée doit précéder toute image initramfs compressée, et elle porte un nom spécial : early initramfs.

Les données de mise à jour du microcode dans l'image initramfs précoce doivent être alignées sur une frontière de 16 octets en raison d'un bug dans plusieurs versions du pilote de mise à jour précoce du microcode du noyau Linux. Cela nécessite des étapes spéciales lors de la création de l'archive initramfs avec les données du microcode, et sera géré automatiquement par l'option --write-earlyfw de iucode_tool.

Depuis Linux v4.2, il est également possible de compiler un noyau avec les données de mise à jour du microcode en tant que firmware intégré, en utilisant la fonctionnalité CONFIG_FIRMWARE_IN_KERNEL. Cette fonctionnalité n'est pas encore mature dans les versions Linux v4.2.8, v4.4.11, v4.5.5 et v4.6, et pourrait ne pas fonctionner dans tous les cas.

L'interface de mise à jour /dev/cpu/microcode est obsolète et ne devrait pas être utilisée. Elle a une exigence spéciale : chaque appel système d'écriture doit contenir des microcodes entiers. Elle est accessible via iucode_tool --kernel.

Jusqu'à Linux v3.5, les mises à jour tardives du microcode devaient être déclenchées par cœur, en écrivant le nombre 1 dans /sys/devices/system/cpu/*/microcode/reload pour chaque CPU. Selon la version du noyau, vous devez soit le déclencher sur chaque cœur pour éviter une situation dangereuse où certains cœurs utilisent un microcode obsolète, soit le noyau acceptera la requête uniquement pour le processeur de démarrage et l'utilisera pour déclencher une mise à jour sur tous les cœurs du processeur du système.

Depuis Linux v3.6, le pilote de mise à jour tardive du microcode dispose d'une nouvelle interface qui déclenche explicitement une mise à jour pour chaque cœur à la fois lorsque le nombre 1 est écrit dans /sys/devices/system/cpu/microcode/reload.

EXIT

L'outil se termine avec le code de sortie 0 en cas de succès, et un code de sortie non nul en cas d'erreur.

EXEMPLES

Les exemples suivants montrent comment utiliser iucode_tool pour différentes tâches :

Lire et valider un fichier de microcode :
iucode_tool /lib/firmware/intel-ucode/*
Afficher les signatures de microcodes qui seront chargés :
iucode_tool --list --cpu-microcode /lib/firmware/intel-ucode/*
Écrire les microcodes dans un fichier binaire pour une utilisation ultérieure : 
iucode_tool --write-to=intel-ucode.bin /lib/firmware/intel-ucode/*
Détecter automatiquement les microcodes appropriés pour le système et les charger dans le noyau : 
iucode_tool --scan-system --load-to-kernel
Sélectionner les microcodes pour des familles et modèles spécifiques et les écrire dans un répertoire pour le chargeur de firmware du noyau : 
iucode_tool -s 'family=6,model=45' -s 'family=6,model=44' \
        --write-firmware=/lib/firmware/intel-ucode/
Sélectionner les microcodes datant d'avant le 1er janvier 2020 et les écrire dans un répertoire, un fichier par microcode : 
iucode_tool --date-before=2020-01-01 \
        --write-named-to=/path/to/microcodes/

BOGUE

S

Le microcode avec des numéros de révision négatifs n'est pas traité de manière spécifique et ne sera pas préféré au microcode

régulier.

Le mode de rétrogradation ne doit être utilisé que pour des microcodes avec le même masque de drapeaux de processeur. Il ne peut pas gérer les cas limites où la modification d'un masque de drapeaux de processeur serait nécessaire pour forcer le noyau à charger une révision inférieure d'un microcode, et iucode_tool émettra un avertissement lorsque cela se produit. Jusqu'à présent, cela ne s'est pas avéré être une limitation pertinente car les modifications du masque de drapeaux de processeur des mises à jour de microcode de production post-lancement sont très

rares.

Le champ de métadonnées de microcode de version du chargeur est ignoré par iucode_tool. Cela ne devrait pas causer de problèmes tant que la même signature n'a jamais besoin de plus d'un seul type de

chargeur.

Les fichiers ne sont pas remplacés de manière atomique : si iucode_tool est interrompu pendant l'écrit

ure dans un fichier, ce
fichier sera corrompu.
