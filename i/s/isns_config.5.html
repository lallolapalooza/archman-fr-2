DESCRIPTIO

N

Toutes les utilitaires Open-iSNS lisent leur configuration depuis un fichier dans /etc/isns. Il existe un fichier de configuration distinct pour chaque application, isnsd, isnsadm, et isnsdd. La syntaxe et l'ensemble des options prises en charge sont identiques, même si certaines options sont spécifiques, par exemple, au serveur. Sauf indication contraire, les options s'appliquent à tous les

utilitaires.

Un fichier de configuration Open-iSNS contient des paires mot-clé-argument, une par ligne. Tous les mots-clés ne sont pas sensibles à la

casse.

Un caractère # introduit un commentaire, qui s'étend jusqu'à la fin de la ligne. Les lignes vides sont

ignorées.

Il n'y a pas de poursuite de ligne, et vous ne pouvez pas utiliser de guillemets autour des

arguments.

Certaines options spécifient des valeurs de délai d'attente, qui sont données en unités de secondes par défaut. Vous pouvez cependant spécifier une unité explicite, comme d (jours), h (heures), m (minutes), ou s (secondes)

.

Par défaut, les applications Open-iSNS récupèrent le nom d'hôte de la machine à l'aide de l'appel système gethostname(3) et utilisent une recherche DNS pour trouver le nom canonique. En utilisant l'option HostName, vous pouvez remplacer ce comportement. Cette option est rarement
nécessaire.

client.

Options liées à la

sécurité

La norme iSNS définit une méthode d'authentification basée sur l'algorithme DSA. Les participants à un échange de messages authentifient les messages en ajoutant un « bloc d'authentification » contenant un horodatage, une chaîne identifiant la clé utilisée et une signature numérique du message. La même méthode est également utilisée par SLP, le Service Location

Protocol.

La chaîne contenue dans le bloc d'authentification est appelée Security Policy Index (SPI). Cette chaîne peut être utilisée par le serveur pour rechercher la clé publique du client par n'importe quel mécanisme ; ainsi, la chaîne pourrait être utilisée comme nom d'un fichier de clé publique dans un répertoire, ou pour récupérer un certificat X509 depuis

LDAP.

Du point de vue des applications clientes Open-iSNS, il n'y a que deux clés : la clé (privée) propre au client, utilisée pour signer les messages qu'il envoie au serveur, et la clé publique du serveur, utilisée pour vérifier les signatures des messages entrants du

serveur.

Le serveur iSNS a besoin, en plus de sa propre clé privée, d'un accès à toutes les clés publiques des clients qui communiqueront avec lui. Ces dernières sont conservées dans ce que l'on appelle un magasin de clés (key store). Les magasins de clés et leur fonctionnement seront discutés dans la section Magasins de clés et politiq

ue ci-dessous.

Les options de configuration suivantes contrôlent l'authentification

:
Securi
ty
Cela active ou désactive l'authentification DSA. Lorsqu'il
est défini à 1, le client signera tous les messages et s'at
tendra à ce que tous les messages du serveur soient signés.
Lors de l'activation de la sécurité dans le serveur, les messages entrants sont vérifiés pour la présence d'un bloc d'authentification. Si aucun n'est présent, ou si le serveur ne peut pas trouver une clé publique correspondant au SPI, le message est traité comme provenant d'une source anonyme. Si le SPI est connu mais que la signature est incorrecte, le message est rejeté
silencieusement.
Les messages provenant d'une source anonyme se verront attribuer une politique très restrictive qui n'autorise que les requêtes sur la base de
données.
Définir cette option à 0 désactivera l'authentificati
on.
La valeur par défaut est -1, ce qui indique à iSNS d'
utiliser l'authentification si les clés requises sont
installées, et d'utiliser iSNS non authentifié sinon.

Magasins de clés et

politique

L'implémentation actuelle prend en charge deux types de magasins de

clés.

Le magasin de clés simple utilise un répertoire plat pour stocker les clés publiques, chaque clé dans son propre fichier. Le fichier doit contenir la clé publique du client encodée en PEM, et il doit utiliser le SPI du client comme nom. Ce type de magasin de clés n'est pas vraiment recommandé, car il ne stocke aucune information de

politique.

Un magasin de clés simple peut être configuré en définissant l'option KeyStore sur le chemin d'accès du

répertoire.

L'approche recommandée est d'utiliser la base de données comme magasin de clés. Cela utilise des objets de politique spécifiques au fournisseur pour lier la chaîne SPI, la clé publique, le nom de l'entité, le nom source et d'autres éléments de politique, et les stocke de manière

persistante.

Le magasin de clés de base de données est configuré en définissant l'option KeyStore sur la valeur réservée DB:, qui est également la valeur par

défaut.

Actuellement, les objets de politique Open-iSNS ont les attributs suivants, en plus du SPI

:
Source
:
C'est le nom du nœud source que le client doit utiliser. Il par défaut à la chaîne
SPI.
Functions
:
C'est un bitmap détaillant les fonctions que le client est autorisé à invoquer. Les noms de bits correspondent aux noms abréviatifs utilisés dans la RFC 4171, tels que DevAttrReg, DevAttrQry, etc. La valeur par défaut est d'autoriser l'enregistrement, l'interrogation et le désenregistrement, ainsi que
SCNRegister.
Nom de l'entité
:
C'est le nom d'entité attribué au client. S'il est défini, un enregistrement par le client n'est pas autorisé à utiliser un nom d'entité différent. Si le client envoie un enregistrement sans identifiant d'entité, le serveur attribuera le nom d'entité donné dans la politique. La valeur par défaut est de ne pas restreindre le nom de
l'entité.
Accès aux objets
:
C'est un champ de bits décrivant les permissions d'accès pour chaque type d'objet. Pour chaque type d'objet, vous pouvez accorder les permissions de lecture et/ou d'écriture. L'accès en lecture s'applique aux appels Query et GetNext ; toutes les autres opérations nécessitent la permission d'écriture. La valeur par défaut accorde l'accès en lecture et en écriture aux objets de type Entity, Storage Node, Portal et Portal Group ; et l'accès en lecture aux Discovery
Domains.
Types de nœuds
:
Ce champ de bits décrit les types de nœuds de stockage qu'un client est autorisé à enregistrer ; les noms de bits valides sont target, initiator et control. La valeur par défaut est de restr
eindre les nœuds à l
'enregistrement des i
nitiators uniquement.
