NOM

idmap_ad - Backend idmap_ad de Samba pour Winbind

DESCRIPTION

Le plugin idmap_ad fournit un moyen à Winbind de lire les mappings d'identifiants à partir d'un serveur AD utilisant les extensions de schéma RFC2307/SFU. Ce module implémente uniquement l'API "idmap" et est en lecture seule (READONLY). Les mappings doivent être fournis à l'avance par l'administrateur en ajoutant les attributs uidNumber pour les utilisateurs et gidNumber pour les groupes dans AD. Winbind ne mapper que les utilisateurs qui ont un uidNumber et dont le groupe principal a un attribut gidNumber défini. Il est cependant recommandé que tous les groupes utilisés aient des attributs gidNumber attribués, sinon ils ne fonctionneront pas.

Actuellement, le backend ad ne fonctionne pas comme backend idmap par défaut, mais il doit être configuré séparément pour chaque domaine pour lequel on souhaite l'utiliser, en utilisant des plages disjointes. On doit généralement configurer une plage idmap par défaut inscriptible, en utilisant par exemple le backend tdb ou ldap, afin de pouvoir mapper les SID intégrés (BUILTIN) et éventuellement d'autres domaines de confiance. La configuration par défaut inscriptible est également nécessaire pour pouvoir créer des mappings de groupes. Cette configuration idmap globale par défaut devrait avoir une plage qui est disjointe de celle de tout domaine configuré explicitement avec le backend idmap ad. Voir l'exemple ci-dessous.

OPTIONS IDMAP

range = bas - haut

Définit la plage disponible de UID et GID correspondants pour laquelle le backend est faisant autorité. Notez que la plage agit comme un filtre. Si elle est spécifiée, tout UID ou GID stocké dans AD qui tombe en dehors de la plage est ignoré et le mapping correspondant est rejeté. Il est destiné à éviter les chevauchements accidentels d'UID/GID entre les identifiants locaux et ceux définis à distance.

schema_mode = <rfc2307 | sfu | sfu20>

Définit le schéma que idmap_ad doit utiliser lors de l'interrogation d'Active Directory concernant les informations d'utilisateurs et de groupes. Il peut s'agir soit du schéma RFC2307 inclus dans Windows Server 2003 R2 et versions ultérieures, soit du schéma Service for Unix (SFU) pour les versions antérieures à Windows Server 2003 R2. Pour SFU 3.0 ou 3.5, veuillez choisir "sfu", pour SFU 2.0, veuillez choisir "sfu20". Veuillez noter que le comportement de l'appartenance au groupe principal est contrôlé par l'option unix_primary_group.

Par défaut : rfc2307

unix_primary_group = oui/non

Définit si le groupe principal de l'utilisateur est récupéré depuis les attributs SFU ou le groupe principal AD. S'il est défini sur oui, l'appartenance au groupe principal est récupérée à partir des attributs LDAP (gidNumber). S'il est défini sur non, l'appartenance au groupe principal est calculée via l'attribut LDAP "primaryGroupID".

Par défaut : non

unix_nss_info = oui/non

Si défini sur oui, winbind récupérera le shell de connexion et le répertoire personnel à partir des attributs LDAP. S'il est défini sur non ou si l'entrée LDAP AD manque des attributs SFU, les options template shell et template homedir sont utilisées.

Par défaut : non

all_groupmem = oui/non

Si défini sur oui, winbind récupérera tous les membres de groupe pour les appels getgrnam(3), getgrgid(3) et getgrent(3), y compris ceux avec un uidNumber manquant.

Par défaut : non

deny ous

Ce paramètre est une liste d'unités d'organisation (OU) à partir desquelles les objets ne seront pas mappés via le module idmap ad. Si deny ous est défini mais pas allow ous, tout objet en dehors des OU listées dans deny ous est autorisé.

Par défaut : aucun

allow ous

Ce paramètre est une liste d'unités d'organisation (OU) à partir desquelles les objets seront mappés via le module idmap ad. Si allow ous est défini mais pas deny ous, tout objet en dehors des OU spécifiées dans allow ous est refusé.

Si allow ous et deny ous sont tous deux définis, deny ous est évalué en premier, puis allow ous est pris en compte. Si un objet AD ne correspond à aucun des deux, il est refusé.

Par défaut : aucun

EXEMPLES

L'exemple suivant montre comment récupérer les mappings d'identifiants de nos domaines AD principaux et de confiance. S'il y a des domaines de confiance, les conflits d'identifiants doivent être résolus au préalable, il n'y a aucune garantie sur l'ordre dans lequel les mappings conflictuels seront résolus à ce stade. Cet exemple montre également comment laisser une petite plage non conflictuelles pour l'allocation d'identifiants locaux qui peut être utilisée dans des backends internes comme BUILTIN.

[global]
workgroup = CORP
idmap config * : backend = tdb
idmap config * : range = 1000000-1999999
idmap config CORP : backend  = ad
idmap config CORP : range = 1000-999999
