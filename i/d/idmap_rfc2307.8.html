NOM

idmap_rfc2307 - Backend idmap_rfc2307 de Samba pour Winbind

DESCRIPTION

Le plugin idmap_rfc2307 fournit un moyen pour winbind de lire les mappings d'identifiants à partir d'enregistrements dans un serveur LDAP, tels que définis dans la RFC 2307. Le serveur LDAP peut être autonome ou le serveur LDAP fourni par le serveur AD. Un serveur AD est toujours requis pour fournir le mapping entre le nom et le SID, et le serveur LDAP est interrogé pour le mapping entre le nom et uid/gid. Ce module implémente uniquement l'API "idmap", et est EN LECTURE SEULE.

Les mappings doivent être fournis à l'avance par l'administrateur en créant les comptes utilisateurs sur le serveur Active Directory et les objets posixAccount et posixGroup sur le serveur LDAP. Les noms sur le serveur Active Directory et sur le serveur LDAP doivent être identiques.

Cette approche de mapping d'identifiants permet la réutilisation de serveurs d'authentification LDAP existants qui stockent des enregistrements au format RFC 2307.

Lors de la connexion au serveur LDAP fourni par un serveur AD, le paramètre ldap ssl ads détermine si SSL doit être utilisé. Lors de l'utilisation d'un serveur LDAP autonome, ldap ssl s'applique.

OPTIONS IDMAP

range = bas - haut

Définit la plage correspondante disponible de UID et GID pour laquelle le backend est faisant autorité. Notez que la plage agit comme un filtre. Si spécifié, tout UID ou GID stocké dans AD qui tombe en dehors de la plage est ignoré et le mapping correspondant est rejeté. Il est destiné à éviter les chevauchements accidentels d'UID/GID entre les identifiants locaux et ceux définis à distance.

ldap_server = <ad | autonome>

Définit le type de serveur LDAP à utiliser. Il peut s'agir du serveur LDAP fourni par le serveur Active Directory (ad) ou d'un serveur LDAP autonome.

bind_path_user

Spécifie la base de recherche où les objets utilisateurs peuvent être trouvés sur le serveur LDAP.

bind_path_group

Spécifie la base de recherche où les objets groupes peuvent être trouvés sur le serveur LDAP.

user_cn = <oui | non>

Interroge l'attribut cn au lieu de l'attribut uid pour le nom d'utilisateur en LDAP. Cette option n'est pas obligatoire, la valeur par défaut est non.

realm

Ajoute @domaine aux cn pour les groupes (et les utilisateurs si user_cn est défini) dans les requêtes LDAP. Cette option n'est pas obligatoire, la valeur par défaut est de ne pas ajouter le domaine.

ldap_domain

Lors de l'utilisation du serveur LDAP dans le serveur Active Directory, cela permet de spécifier le domaine où accéder au serveur Active Directory. Cela permet d'utiliser des relations d'approbation tout en conservant tous les enregistrements RFC 2307 en un seul endroit. Ce paramètre est optionnel, la valeur par défaut est d'accéder au serveur AD du domaine actuel pour interroger les enregistrements LDAP.

ldap_url

Lors de l'utilisation d'un serveur LDAP autonome, ce paramètre spécifie l'URL ldap pour accéder au serveur LDAP.

ldap_user_dn

Définit le DN utilisateur à utiliser pour l'authentification. Le mot de passe pour authentifier cet utilisateur doit être stocké avec net idmap secret (voir net(8)). S'il est absent, une connexion anonyme sera effectuée.

EXEMPLES

L'exemple suivant montre comment récupérer les mappings d'identifiants depuis un serveur LDAP autonome. Cet exemple montre également comment laisser une petite plage non conflictuelle pour l'allocation d'identifiants locaux qui pourrait être utilisée dans des backends internes comme BUILTIN.

[global]
idmap config * : backend = tdb
idmap config * : range = 1000000-1999999
idmap config DOMAIN : backend = rfc2307
idmap config DOMAIN : range = 2000000-2999999
idmap config DOMAIN : ldap_server = stand-alone
idmap config DOMAIN : ldap_url = ldap://ldap1.example.com
idmap config DOMAIN : ldap_user_dn = cn=ldapmanager,dc=example,dc=com
idmap config DOMAIN : bind_path_user = ou=People,dc=example,dc=com
idmap config DOMAIN : bind_path_group = ou=Group,dc=example,dc=com
