DESCRIPTIO

N

Le compilateur IDL-to-Java génère les liaisons Java pour un fichier IDL spécifié. Pour les détails sur les liaisons, voir Java IDL : IDL to Java Language Mapping à l'adresse http://docs.oracle.com/javase/8/docs/technotes/guides/idl/mapping/jidlMapping.

html

Certaines versions antérieures du compilateur IDL-to-Java étaient nommées idltojava

.

GÉNÉRER LES LIAISONS CLIENT ET

SERVEUR

La commande idlj suivante génère un fichier IDL nommé My.idl avec des liaisons côté

client. 
idlj My.
idl

La syntaxe précédente est équivalente à la suivante

: 
idlj -fclient My.
idl

L'exemple suivant génère les liaisons côté serveur, et inclut les liaisons côté client ainsi que le squelette, le tout étant POA (modèle d'héritage)

. 
idlg -fserver My.
idl

Si vous souhaitez générer à la fois les liaisons côté client et côté serveur, utilisez l'une des commandes suivantes (équivalentes)

: 
idlj -fclient -fserver My.
idl 
idlj -fall My.
idl

Il existe deux modèles possibles côté serveur : le modèle d'héritage du serviteur portable et le modèle Tie. Voir Modèle de délégation

Tie.

Modèle d'héritage du serviteur portable. Le modèle côté serveur par défaut est le modèle d'héritage du serviteur portable. Étant donné une interface My définie dans My.idl, le fichier MyPOA.java est généré. Vous devez fournir l'implémentation pour l'interface My, et l'interface My doit hériter de la classe MyPOA. MyPOA.java est un squelette basé sur les flux qui étend la classe org.omg.PortableServer.Servant à l'adresse http://docs.oracle.com/javase/8/docs/api/org/omg/PortableServer/Servant.html L'interface My implémente l'interface callHandler et l'interface des opérations associée à l'interface IDL implémentée par le squelette. Le module PortableServer pour l'adaptateur d'objet portable (POA) définit le type natif Servant. Voir Portable Object Adapter (POA) à l'adresse http://docs.oracle.com/javase/8/docs/technotes/guides/idl/POA.html Dans le langage de programmation Java, le type Servant est mappé sur la classe Java org.omg.PortableServer.Servant. Elle sert de classe de base pour toutes les implémentations de serviteurs POA et fournit un certain nombre de méthodes pouvant être appelées par le programmeur de l'application, ainsi que des méthodes appelées par le POA et pouvant être surchargées par l'utilisateur pour contrôler certains aspects du comportement du serviteur. Une autre option pour le modèle d'héritage est d'utiliser le drapeau -oldImplBase pour générer des liaisons côté serveur compatibles avec les versions du langage de programmation Java antérieures à Java SE 1.4. Le drapeau -oldImplBase est non standard, et ces API sont dépréciées. Vous n'utiliseriez ce drapeau que pour la compatibilité avec des serveurs existants écrits en Java SE 1.3. Dans ce cas, vous devriez modifier un fichier make existant pour ajouter le drapeau -oldImplBase au compilateur idlj. Sinon, des mappages côté serveur basés sur POA sont générés. Pour générer des liaisons côté serveur rétrocompatibles, faites ce qui suit

: 
idlj -fclient -fserver -oldImplBase My.
idl 
idlj -fall -oldImplBase My.
idl

Étant donné une interface My définie dans My.idl, le fichier _MyImplBase.java est généré. Vous devez fournir l'implémentation pour l'interface My, et l'interface My doit hériter de la classe _MyImplBase

.

Modèle de délégation Tie. L'autre modèle côté serveur est appelé le modèle Tie. C'est un modèle de délégation. Comme il n'est pas possible de générer les ties et les squelettes en même temps, ils doivent être générés séparément. Les commandes suivantes génèrent les liaisons pour le modèle Tie

: 
idlj -fall My.
idl 
idlj -fallTIE My.
idl

Pour l'interface My, la deuxième commande génère MyPOATie.java. Le constructeur de la classe MyPOATie prend un délégué. Dans cet exemple, en utilisant le modèle POA par défaut, le constructeur a également besoin d'un POA. Vous devez fournir l'implémentation du délégué, mais il n'a pas besoin d'hériter d'une autre classe, seulement de l'interface MyOperations. Pour l'utiliser avec l'ORB, vous devez envelopper votre implémentation dans la classe MyPOATie, par exemple

: 
ORB orb = ORB.init(args, System.getProperties())
; 
// Get reference to rootpoa & activate the
POAManager 
POA rootpoa = (POA)orb.resolve_initial_references("RootPOA")
; 
rootpoa.the_POAManager().activate()
; 
// create servant and register it with the
ORB 
MyServant myDelegate = new MyServant()
; 
myDelegate.setORB(orb)
; 
// create a tie, with servant being the
delegate. 
MyPOATie tie = new MyPOATie(myDelegate, rootpoa)
; 
// obtain the objectRef for the
tie

Vous pourriez vouloir utiliser le modèle Tie au lieu du modèle d'héritage typique lorsque votre implémentation doit hériter d'une autre implémentation. Java permet un nombre quelconque d'héritages d'interfaces, mais il n'y a qu'un seul emplacement pour l'héritage de classes. Si vous utilisez le modèle d'héritage, cet emplacement est alors occupé. Avec le modèle Tie, cet emplacement est libéré pour votre propre utilisation. L'inconvénient est qu'il introduit un niveau d'indirection : un appel de méthode supplémentaire se produit lorsqu'une méthode est

appelée.

Pour la génération côté serveur, des liaisons au modèle Tie compatibles avec les versions du mappage IDL vers le langage Java antérieures à Java SE 1.

4. 
idlj -oldImplBase -fall My.
idl 
idlj -oldImplBase -fallTIE My.
idl

Pour l'interface My, cela génère My_Tie.java. Le constructeur de la classe My_Tie prend un objet impl. Vous devez fournir l'implémentation pour impl, mais il n'a pas besoin d'hériter d'une autre classe, seulement de l'interface HelloOperations. Mais pour l'utiliser avec l'ORB, vous devez envelopper votre implémentation dans My_Tie, par exemple

SPÉCIFIER DES EMPLACEMENTS ALTERNATIFS POUR LES FICHIERS

D'INCLUSION

Si le fichier My.idl inclut un autre fichier idl, MyOther.idl, le compilateur suppose que le fichier MyOther.idl se trouve dans le répertoire local. S'il se trouve dans /includes, par exemple, appelez le compilateur avec la commande suivante

: 
idlj -i /includes My.
idl

Si My.idl incluait également Another.idl qui se trouvait dans /moreIncludes, par exemple, appelez le compilateur avec la commande suivante

: 
idlj -i /includes -i /moreIncludes My.
idl

Comme cette forme de include peut devenir longue, une autre façon pour indiquer au compilateur où rechercher les fichiers inclus est fournie. Cette technique est similaire au concept de variable d'environnement. Créez un fichier nommé idl.config dans un répertoire qui figure dans votre CLASSPATH variable. À l'intérieur de idl.config, fournissez une ligne de la forme suivante

: 
includes=/includes;/moreIncludes
Le

compilateur trouvera ce fichier et lira la liste des inclusions. Notez que dans cet exemple, le caractère sé

parateur entre les deux répertoires est un point-virgule (;). Ce caractère séparateur dépend de la platef
