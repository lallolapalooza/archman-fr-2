NOM

img2dcm - Convertir des formats d'image standard au format DICOM

SYNOPIS

img2dcm [options] imgfile-in... dcmfile-out

DESCRIPTION

L'outil img2dcm sert d'outil de conversion de formats d'image standard comme JPEG (y compris JPEG-LS) ou BMP au format DICOM. Différentes Classes SOP de sortie peuvent être sélectionnées. Les informations supplémentaires (concernant les patients, séries, etc.) stockées dans le fichier DICOM de sortie peuvent être extraites d'autres fichiers DICOM qui servent de "modèle" pour l'objet DICOM résultant. img2dcm peut également être configuré pour inventer des attributs DICOM de type 1 et 2 manquants afin de fonctionner même sans jeu de données modèle.

dcmfile-out  nom de fichier DICOM de sortie ("-" pour stdout)

NOTES

Sources d'attributs

Pour convertir un format d'image général au format DICOM, l'application img2dcm peut être alimentée avec des entrées supplémentaires pour remplir les attributs obligatoires (et optionnels) dans le nouveau fichier DICOM, tels que les informations du patient, de l'étude et de la série. Ces informations peuvent être collectées en utilisant différentes approches, qui peuvent être combinées et sont appliquées au fichier résultant dans l'ordre suivant :

  • En utilisant l'option --dataset-from, img2dcm est forcé d'importer les attributs d'un fichier DICOM existant. Le fichier DICOM donné est entièrement importé et sert de base à toutes les opérations d'exportation ultérieures. À titre d'exception, l'UID de l'instance SOP n'est pas copié par cette option. Les données liées à l'image comme les lignes, colonnes, etc. sont également échangées pendant la conversion. Notez que img2dcm ne vérifie pas la validité des autres valeurs d'attributs, par exemple, il ne regarde pas dans les séquences pour adapter des attributs au nouvel objet (images référencées, etc.). Par conséquent, il est recommandé d'utiliser les modèles dans le répertoire data pour les objets SC et VLP (anciens). Voir aussi la section "Modèles d'entrée". Comme alternative à l'option --dataset-from, l'option mutuellement exclusive --dataset-from-xml peut être utilisée. Dans ce cas, cependant, le fichier doit contenir des données XML dans le format tel que produit par dcm2xml.
  • Les options --study-from et --series-from peuvent être utilisées pour importer des informations du patient, de l'étude et de la série à partir d'un fichier DICOM existant. Si --series-from est spécifié, alors le fichier DICOM donné est ouvert par img2dcm et toutes les informations obligatoires jusqu'au niveau de la série sont importées. Notez que cela inclut les informations du patient, de l'étude et de la série. Dans le cas de --study-from, les informations de la série sont exclues. L'utilisation de --study-from et --series-from en même temps a du sens. Si les deux options sont fournies sur la ligne de commande, l'option la plus à droite l'emporte. Veuillez noter que ces options ne sont évaluées que si l'option --do-checks est activée (par défaut). Si l'option --no-checks est activée, aucune insertion automatique d'attribut n'aura lieu.
  • L'option --key peut être utilisée pour ajouter des attributs supplémentaires au fichier DICOM de sortie. Il est également possible de spécifier des séquences, des éléments et des attributs imbriqués en utilisant l'option --key. Dans ces cas, une notation "chemin" spéciale doit être utilisée. Les détails sur cette notation de chemin peuvent être trouvés dans la documentation de dcmodify. L'option --key peut être présente plus d'une fois. La partie valeur (après le '=') peut être absente, ce qui entraîne la définition de l'attribut avec une longueur nulle. Veuillez noter que l'option --key est appliquée à la toute fin, juste avant la sauvegarde du fichier DICOM, il n'y a donc pas
vérification de valeur quelconque.

JOURNALISATI

ON

Le niveau de sortie de journalisation des différentes lignes de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seules les erreurs et les avertissements sont écrits sur le flux d'erreur standard. En utilisant l'option --verbose, des messages informatifs tels que les détails de traitement sont également rapportés. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés en utilisant l'option --log-level. En mode --quiet, seules les erreurs fatales sont rapportées. Dans de tels événements d'erreur très graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module

"oflog".

Si la sortie de journalisation doit être écrite dans un fichier (éventuellement avec rotation des fichiers journal), vers syslog (Unix) ou le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/l

ogger
.cfg.

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets enclos des valeurs facultatives (0-1), trois points de suspension indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie de 0 à n

valeurs.

Les options de la ligne de commande se distinguent des paramètres par un signe '+' ou '-' en tête, respectivement. Habituellement, l'ordre et la position des options de la ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si des options sont mutuellement exclusives, l'apparence la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix

courants.

De plus, un ou plusieurs fichiers de commande peuvent être spécifiés en utilisant un signe '@' comme préfixe du nom de fichier (par exemple @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces blancs sont traités comme un seul séparateur s'ils n'apparaissent pas entre deux guillemets) avant toute autre évaluation. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite des lignes de commande longues et déroutantes (un exemple est fourni dans le fichier <datadir>/du

mppat
.txt).

ENVIRONNEMEN

T

L'utilitaire img2dcm essaiera de charger les dictionnaires de données DICOM spécifiés dans la variable d'environnement DCMDICTPATH. Par défaut, c'est-à-dire si la variable d'environnement DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé, à moins que le dictionnaire ne soit intégré à l'application (par défaut sous Windows)

.

Le comportement par défaut doit être préféré et la variable d'environnement DCMDICTPATH doit être utilisée uniquement lorsque des dictionnaires de données alternatifs sont requis. La variable d'environnement DCMDICTPATH a le même format que la variable Unix shell PATH, où un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données essaiera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH. C'est une erre

ur si aucun dictionnaire de
données ne peut être chargé.
