Il gère le protocole standard IHAVE ainsi que l'extension de flux CHECK/TAKETHIS. innfeed peut alimenter un nombre quelconque de hôtes distants à la fois et ouvrira plusieurs connexions à chaque hôte si cela est configuré. Les seules limites sont les limites du processus concernant les descripteurs de fichiers ouverts et la mémoire. En alternative à l'utilisation de NNTP, INN

peut

également être alimenté vers un serveur IMAP. Cela se fait en utilisant un exécutable appelé imapfeed, qui est identique à innfeed à l'exception du processus de livraison. La nouvelle version a deux types de connexions : une connexion LMTP pour livrer les messages réguliers et une connexion IMAP pour gérer les messages de contrôle. Utilisé en conjonction avec delayer(8)

,

innfeed peut envoyer un flux différé aux pairs distants ou à une autre instance locale de innd, notamment pour permettre le rejet du spam avant qu'il n'arrive réellement. MODE

S innfeed a trois mode

canal

,

fichier-entonnoir et lot. Le mode canal est utilisé lorsqu'aucun nom de

fichier

n'est donné sur la ligne de commande, que le mot-clé input-file n'est pas donné dans le fichier de configuration, et que l' [[54]] option -x n'est pas donnée. En mode canal, innfeed s'exécute avec stdin connecté via un tube à innd. Chaque fois que innd ferme ce tube (et il a plusieurs raisons de le faire lors du traitement normal), innfeed se terminera. Il essaiera d'abord de terminer l'envoi de tous les articles qu'il était en train de transmettre, avant d'émettre une commande QUIT. Cela signifie que innfeed peut prendre un certain temps pour se terminer, selon la lenteur de vos pairs. Il ne coupe jamais (ou presque jamais) la connexion. La manière recommandée de redémarrer innfeed lorsqu'il s'exécute en mode canal est donc de dire à innd de fermer le tube et de lancer un nouveau processus innfeed. Cela peut être fait avec "ctlinnd flush feed " où feed est le nom du flux decanal innfeed dans le fichier newsfeeds. Le mode fichier-entonnoir est utilisé lor

squ'un

nom de fichier est donné en argument ou que le mot-clé input-file est donné dans le fichier de configuration. En mode fichier-entonnoir, il lit le fichier spécifié pour les mêmes informations formatées que innd donnerait en mode canal. On s'attend à ce que innd écrive continuellement dans ce fichier, donc lorsque innfeed atteint la fin du fichier, il vérifiera périodiquement la présence de nouvelles informations. Pour empêcher le fichier entonnoir de croître sans limites, vous devrez périodiquement déplacer le fichier sur le côté (ou simplement le supprimer) et faire innd vider le fichier. Ensuite, après que le fichier a été vidé par innd, vous pouvez envoyer un SIGALRM à innfeed, et il fermera également le fichier et ouvrira le nouveau fichier créé par innd. Quelque chose comme : innfeed -p

while true; do

Les statistiques de l'hôte sont générées pour un pair donné à des intervalles réguliers après la première connexion (ou, si le distant est inaccessible, après le début de la mise en spool). Les statistiques de l'hôte donnent les totaux sur toutes les connexions qui ont été actives pendant la période donnée. OPTIONS

-a batch-name
Le drapeau -a permet de spécifier le nom du fichier à utiliser pour les lots d'articles. Le chemin est relatif à pathspool comme défini dans inn.conf. Le défaut est out.going.
-c count
Le drapeau -c spécifie le nombre de connexions à établir. Ceci s'applique uniquement à la configuration de flux parallèle.
-d
Le drapeau -d est utilisé pour le mode de débogage. Si ce drapeau est activé, les informations des articles sont imprimées sur stderr.
-i
Le drapeau -i est utilisé pour dire à innfeed de ne pas s'attendre à des informations d'article de innd mais juste de traiter tous les fichiers en attente existants et de sortir. C'est équivalent à l'option -x.
-k count
Le drapeau -k est utilisé pour spécifier le nombre de connexions qui doivent être supprimées. Ceci s'applique uniquement à la configuration de flux parallèle.
-m count
Le drapeau -m est utilisé pour spécifier le nombre maximum de connexions par serveur. Ceci s'applique uniquement à la configuration de flux parallèle.
-p pid-file
Le drapeau -p est utilisé pour spécifier le nom du fichier dans lequel écrire le pid du processus. Un chemin relatif est relatif à pathrun comme défini dans inn.conf. Le défaut est innfeed.pid.

Il est conseillé d'utiliser le paramètre pid-file dans le fichier de configuration pour déclarer un nom de fichier spécifique, car sinon scanlogs ne l'obtiendra pas et le fichier journal ne sera pas correctement vidé avant d'être mis en rotation.

-s command
Le drapeau -s spécifie le nom d'une commande à exécuter dans un sous-processus et à lire les informations d'article à partir. Ceci est similaire à une opération en mode canal, seulement command prend la place habituellement occupée par innd.
-S status-file
Le drapeau -S spécifie le nom du fichier dans lequel écrire le statut périodique. Si le chemin est relatif, il est considéré comme relatif à pathlog comme défini dans inn.conf. Le défaut est innfeed.status.
-v
Lorsque le drapeau -v est donné, les informations de version sont imprimées sur stderr et innfeed se termine.
-x
Le drapeau -x est utilisé pour dire à innfeed de ne pas attendre d'informations d'article de innd mais juste de traiter les fichiers en attente qui existent et de sortir.
-y
Le drapeau -y est utilisé pour permettre la liaison dynamique des pairs. Si ce drapeau est utilisé et que des informations d'article sont reçues de innd qui spécifient un pair inconnu, alors le nom du pair est pris comme étant aussi le nom IP, et une association avec lui est créée. En utilisant ceci, il est possible de n'avoir que les valeurs par défaut globales dans le fichier innfeed.conf, à condition que le nom du pair tel qu'utilisé par innd soit le même que le nom IP.

Notez que innfeed avec -y et aucun pair dans innfeed.conf causerait un problème où innfeed laisserait tomber le premier article.

-z
Le drapeau -z est utilisé pour faire en sorte que chaque connexion, dans une configuration de flux parallèle, rapporte des statistiques lorsque le contrôleur des connexions imprime ses statistiques.

BUGS

Lors de l'utilisation de l'option -x, le champ initial-connections de l'entrée du fichier de configuration sera le nombre total de connexions créées et utilisées, quelle que soit la taille du fichier de lots, et quel que soit le champ max-connections spécifié. Ainsi, une valeur de 0 pour initial-connections signifie que rien ne se passera en mode -x.

innfeed ne récupère pas automatiquement le fichier de pathoutgoing. Cela doit être préparé pour lui par des moyens externes.

Probablement trop d'autres bugs pour les compter.

ALTERNATIVE

Une alternative à innfeed peut être innduct, maintenu par Ian Jackson et disponible à http://www.chiark.greenend.org.uk/ucgi/~ian/git-manpage/innduct.git/innduct.8. Il est destiné à résoudre un problème de conception dans la façon dont innfeed fonctionne. En fait, le protocole de flux des programmes parlé entre innd et innfeed est sujet à pertes : si innfeed meurt de manière inattendue, les articles que innd a écrits dans le tube vers innfeed seront ignorés. innd n'a aucun moyen de savoir quels articles il s'agit, aucun enregistrement utile, et aucune tentative de renvoyer ces articles.
