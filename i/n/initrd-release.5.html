NOM

os-release, initrd-release, extension-release - Identification du système d'exploitation

SYNTAXE

/etc/os-release
/usr/lib/os-release
/etc/initrd-release
/usr/lib/extension-release.d/extension-release.IMAGE

DESCRIPTION

Les fichiers /etc/os-release et /usr/lib/os-release contiennent des données d'identification du système d'exploitation.

Le format de os-release est une liste d'affectations de variables, séparées par des sauts de ligne, compatibles avec le shell (de type environnement). Il est possible de sourcer la configuration depuis des scripts shell Bourne, cependant, au-delà des simples affectations de variables, aucune fonctionnalité shell n'est supportée (cela signifie que l'expansion des variables n'est explicitement pas supportée), permettant aux applications de lire le fichier sans implémenter un moteur d'exécution compatible avec shell. Les valeurs d'affectation de variables doivent être entourées de guillemets doubles ou simples si elles contiennent des espaces, des points-virgules ou d'autres caractères spéciaux en dehors de A–Z, a–z, 0–9. (Les affectations qui ne contiennent pas ces caractères spéciaux peuvent également être entourées de guillemets, mais c'est facultatif.) Les caractères spéciaux de shell ("$", guillemets, antislash, backtick) doivent être échappés avec des antislashs, suivant le style shell. Toutes les chaînes doivent être encodées en UTF-8, et les caractères non imprimables ne doivent pas être utilisés. La concaténation de plusieurs chaînes citées individuellement n'est pas supportée. Les lignes commençant par "#" sont traitées comme des commentaires. Les lignes vides sont permises et ignorées.

Le fichier /etc/os-release a priorité sur /usr/lib/os-release. Les applications doivent vérifier l'existence du premier et utiliser exclusivement ses données s'il existe, et seulement se rabattre sur /usr/lib/os-release si ce dernier est absent. Les applications ne doivent pas combiner les données des deux fichiers. /usr/lib/os-release est l'endroit recommandé pour stocker les informations de version de l'OS dans le cadre des arbres de fournisseurs. /etc/os-release devrait être un lien symbolique relatif vers /usr/lib/os-release, pour assurer la compatibilité avec les applications qui ne recherchent que dans /etc/. Un lien symbolique relatif au lieu d'un lien symbolique absolu est nécessaire pour éviter de casser le lien dans un environnement chroot ou initrd.

os-release contient des données définies par le fournisseur du système d'exploitation et ne devrait généralement pas être modifié par l'administrateur.

Comme ce fichier ne code que des noms et des identifiants, il ne doit pas être localisé.

Les fichiers /etc/os-release et /usr/lib/os-release peuvent être des liens symboliques vers d'autres fichiers, mais il est important que le fichier soit disponible dès le démarrage le plus tôt possible, et doit donc être situé sur le système de fichiers racine.

os-release ne doit pas contenir de clés répétées. Néanmoins, les lecteurs devraient choisir les entrées situées plus loin dans le fichier en cas de répétition, de manière similaire à ce qu'un shell sourçant le fichier ferait. Un lecteur peut avertir des entrées répétées.

Pour une justification plus détaillée d'os-release, veuillez vous référer à l'Annonce de /etc/os-release[1].

/etc/initrd-release

Dans l'initrd[2] et l'exitrd, /etc/initrd-release joue le même rôle que os-release dans le système principal. De plus, la présence de ce fichier signifie que le système est en phase initrd/exitrd. /etc/os-release devrait être lié symboliquement à /etc/initrd-release (ou vice versa), afin que les programmes qui ne recherchent que /etc/os-release (comme décrit ci-dessus) fonctionnent correctement.

Le reste de ce document qui parle d'os-release doit être compris comme s'appliquant également à initrd-release.

/usr/lib/extension-release.d/extension-release.IMAGE

/usr/lib/extension-release.d/extension-release.IMAGE joue le même rôle pour les images d'extension que os-release pour le système principal, et suit la syntaxe et les règles décrites sur la page Services Portables[3]. Le but de ce fichier est d'identifier l'extension et de permettre au système d'exploitation de vérifier que l'image d'extension correspond à l'OS de base. Ceci est généralement implémenté en vérifiant que l'option ID= de l'extension correspond à l'option ID= de l'hôte ou est incluse dans l'option ID_LIKE= de l'hôte, et que soit SYSEXT_LEVEL= existe et correspond, soit si elle n'est pas présente, VERSION_ID= existe et correspond. Cela assure la compatibilité ABI/API entre les couches et empêche la fusion d'une image incompatible dans une superposition.

Afin d'identifier l'image d'extension elle-même, les mêmes champs définis ci-dessous peuvent être ajoutés au fichier d'extension avec un préfixe SYSEXT_ (pour éviter toute ambiguïté avec les champs utilisés pour la correspondance sur l'image de base). Par exemple : SYSEXT_ID=myext, SYSEXT_VERSION_ID=1.2.3.

Dans le nom de fichier extension-release.IMAGE, la partie IMAGE doit correspondre exactement au nom du fichier de l'image contenant, sans le suffixe. Dans le cas où il n'est pas possible de garantir qu'un nom de fichier d'image est stable et ne change pas entre les phases de construction et de déploiement, il est possible d'assouplir cette vérification : si exactement un fichier dont le nom correspond à "extension-release.*" est présent dans ce répertoire, et que le fichier est marqué avec un attribut xattr(7) user.extension-release.strict avec la chaîne "0", il sera utilisé à la place.

Le reste de ce document qui parle d'os-release doit être compris comme s'appliquant également à extension-release.

OPTIONS

Les paramètres d'identification du système d'exploitation suivants peuvent être définis à l'aide d'os-release :

Informations générales identifiant le système d'exploitation

NAME=

Une chaîne identifiant le système d'exploitation, sans composant de version, et adaptée à la présentation à l'utilisateur. Si non défini, une valeur par défaut de "NAME=Linux" peut être utilisée.

Exemples : "NAME=Fedora", "NAME="Debian GNU/Linux"".

ID=

Une chaîne en minuscules (sans espaces ou autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant le système d'exploitation, excluant toute information de version et adaptée au traitement par des scripts ou à une utilisation dans des noms de fichiers générés. Si non défini, une valeur par défaut de "ID=linux" peut être utilisée. Notez que même si cette chaîne peut ne pas inclure de caractères nécessitant un échappement shell, un échappement peut néanmoins être utilisé.

Exemples : "ID=fedora", "ID=debian".

ID_LIKE=

Une liste d'identifiants de systèmes d'exploitation séparés par des espaces, dans la même syntaxe que le paramètre ID=. Elle devrait lister les identifiants des systèmes d'exploitation qui sont étroitement liés au système d'exploitation local en termes de paquets et d'interfaces de programmation, par exemple en listant un ou plusieurs identifiants d'OS dont l'OS local est un dérivé. Un OS ne devrait généralement lister que les identifiants d'autres OS dont il est lui-même un dérivé, et aucun OS qui en est dérivé, bien que des relations symétriques soient possibles. Les scripts de construction et similaires devraient vérifier cette variable s'ils ont besoin d'identifier le système d'exploitation local et que la valeur de ID= n'est pas reconnue. Les systèmes d'exploitation devraient être listés dans l'ordre de la relation du système d'exploitation local avec les systèmes listés, en commençant par le plus proche. Ce champ est facultatif.

Exemples : pour un système d'exploitation avec "ID=centos", une affectation de "ID_LIKE="rhel fedora"" serait appropriée. Pour un système d'exploitation avec "ID=ubuntu", une affectation de "ID_LIKE=debian" est appropriée.

PRETTY_NAME=

Un nom de système d'exploitation joli, dans un format adapté à la présentation à l'utilisateur. Peut contenir ou non un nom de code de version ou une version d'OS d'une sorte ou d'une autre, selon ce qui est approprié. Si non défini, une valeur par défaut de "PRETTY_NAME="Linux"" peut être utilisée.

Exemple : "PRETTY_NAME="Fedora 17 (Beefy Miracle)"".

CPE_NAME=

Un nom CPE pour le système d'exploitation, en syntaxe de liaison URI, suivant la Spécification d'Énumération Commune de Plateforme[4] telle que proposée par le NIST. Ce champ est facultatif.

Exemple : "CPE_NAME="cpe:/o:fedoraproject:fedora:17""

VARIANT=

Une chaîne identifiant une variante ou une édition spécifique du système d'exploitation, adaptée à la présentation à l'utilisateur. Ce champ est facultatif.

Exemple : "VARIANT=Server Edition"

VARIANT_ID=

Une chaîne identique à VARIANT=, mais en minuscules, sans espaces ni caractères spéciaux, et adaptée au traitement par des scripts. Ce champ est facultatif.

Exemple : "VARIANT_ID=server-edition"

Informations sur la version du système d'exploitation

VERSION=

Une chaîne identifiant la version du système d'exploitation, adaptée à la présentation à l'utilisateur.

Exemple : "VERSION=17"

VERSION_ID=

Une chaîne identifiant la version du système d'exploitation, dans un format adapté au traitement par des scripts ou à une utilisation dans des noms de fichiers générés. Il est recommandé de ne spécifier que la version majeure et mineure, et aucun autre numéro de version ou nom de code. Ce champ est obligatoire pour les systèmes d'exploitation qui ont des versions distinctes.

Exemple : "VERSION_ID=17.1"

VERSION_CODENAME=

Un nom de code pour la version du système d'exploitation, adapté à la présentation à l'utilisateur.

Exemple : "VERSION_CODENAME=beefy-miracle"

Informations sur l'image du système d'exploitation

BUILD_ID=

Un identifiant unique pour la construction du système d'exploitation. Il est recommandé qu'il soit spécifique et qu'il change à chaque nouvelle construction.

Exemple : "BUILD_ID=2012-04-26-0240"

OS_RELEASE_IMG_ID=

Identifiant unique de l'image du système d'exploitation. Si défini, il est recommandé de le définir à une valeur qui change à chaque nouvelle construction.

Exemple : "OS_RELEASE_IMG_ID=debian-11-x86_64"

OS_RELEASE_IMG_ID_LIKE=

Liste d'identifiants de systèmes d'exploitation séparés par des espaces, dans la même syntaxe que ID_LIKE=. Il devrait lister les identifiants des systèmes d'exploitation, dont les images sont étroitement liées à l'image locale.

Exemple : "OS_RELEASE_IMG_ID_LIKE=debian"

OS_RELEASE_IMG_VERSION=

La version de l'image du système d'exploitation, dans un format adapté au traitement par des scripts.

Exemple : "OS_RELEASE_IMG_VERSION=11.1"

OS_RELEASE_IMG_VERSION_ID=

La version de l'image du système d'exploitation, dans un format adapté au traitement par des scripts. Il est recommandé de ne spécifier que la version majeure et mineure.

Exemple : "OS_RELEASE_IMG_VERSION_ID=11.1"

OS_RELEASE_IMG_VERSION_CODENAME=

Le nom de code de l'image du système d'exploitation.

Exemple : "OS_RELEASE_IMG_VERSION_CODENAME=bullseye"

Informations sur l'architecture et la virtualisation

HOME_URL=

URL pointant vers la page d'accueil du système d'exploitation.

Exemple : "HOME_URL=https://fedoraproject.org/"

SUPPORT_URL=

URL pointant vers la page de support du système d'exploitation.

Exemple : "SUPPORT_URL=https://fedoraproject.org/wiki/Support"

BUG_REPORT_URL=

URL pointant vers l'outil de signalement de bugs du système d'exploitation.

Exemple : "BUG_REPORT_URL=https://bugzilla.redhat.com/"

PRIVACY_POLICY_URL=

URL pointant vers la politique de confidentialité du système d'exploitation.

Exemple : "PRIVACY_POLICY_URL=https://fedoraproject.org/wiki/Legal:PrivacyPolicy"

LOGO=

Nom du fichier du logo du système d'exploitation, situé dans /usr/share/icons/hicolor/scalable/apps/ ou un répertoire similaire.

Exemple : "LOGO=distro-logo"

LOGO_ICONS=

Liste d'icônes de logo séparées par des espaces, dans la même syntaxe que LOGO=.

Exemple : "LOGO_ICONS=distro-logo distro-logo-icon"

DEFAULT_HOSTNAME=

Le nom d'hôte par défaut à utiliser pour un nouveau système.

Exemple : "DEFAULT_HOSTNAME=arch"

SYSEXT_LEVEL=

Niveau de compatibilité de l'image d'extension.

Exemple : "SYSEXT_LEVEL=1"

Variables spécifiques à l'initrd

INITRD_IMAGE=

Le nom du fichier de l'image initrd.

Exemple : "INITRD_IMAGE=initramfs-linux.img"

INITRD_MODULES=

Liste de modules à inclure dans l'initrd.

Exemple : "INITRD_MODULES=virtio_blk ext4"

EXEMPLES

Voici un exemple typique pour un système Arch Linux :

/etc/os-release:
NAME="Arch Linux"
ID=arch
ID_LIKE=
PRETTY_NAME="Arch Linux"
ANSI_COLOR="0;38;2;24;144;255"
HOME_URL="https://archlinux.org/"
SUPPORT_URL="https://bbs.archlinux.org/"
BUG_REPORT_URL="https://bugs.archlinux.org/"
LOGO=archlinux-logo
BUILD_ID=rolling

Et pour une image d'extension (par exemple, le noyau Linux) :

/usr/lib/extension-release.d/extension-release.kernel:
ID=linux
ID_LIKE=
SYSEXT_ID=linux
SYSEXT_VERSION_ID=5.19.0
SYSEXT_LEVEL=1
VERSION_ID=5.19.0
VERSION_CODENAME=

VARIANT_ID=

Cela peut être interprété par d'autres paquets afin de déterminer une configuration par défaut divergente. Ce champ est facultatif et peut ne pas être implémenté sur tous les systèmes.

Exemples : "VARIANT_ID=server", "VARIANT_ID=embedded".

Informations sur la version du système d'exploitation

VERSION=

Une chaîne identifiant la version du système d'exploitation, excluant toute information de nom du système d'exploitation, pouvant inclure un nom de code de version, et adaptée pour être présentée à l'utilisateur. Ce champ est facultatif.

Exemples : "VERSION=17", "VERSION="17 (Beefy Miracle)"".

VERSION_ID=

Une chaîne en minuscules (principalement numérique, sans espaces ni autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant la version du système d'exploitation, excluant toute information de nom du système d'exploitation ou nom de code de version, et adaptée au traitement par des scripts ou à l'utilisation dans des noms de fichiers générés. Ce champ est facultatif.

Exemples : "VERSION_ID=17", "VERSION_ID=11.04".

VERSION_CODENAME=

Une chaîne en minuscules (sans espaces ni autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant le nom de code de version du système d'exploitation, excluant toute information de nom du système d'exploitation ou version de release, et adaptée au traitement par des scripts ou à l'utilisation dans des noms de fichiers générés. Ce champ est facultatif et peut ne pas être implémenté sur tous les systèmes.

Exemples : "VERSION_CODENAME=buster", "VERSION_CODENAME=xenial".

Ajouté dans la version 231.

BUILD_ID=

Une chaîne identifiant de manière unique l'image système initialement utilisée comme base d'installation. Dans la plupart des cas, VERSION_ID ou IMAGE_ID+IMAGE_VERSION sont mis à jour lorsque l'image système entière est remplacée lors d'une mise à jour. BUILD_ID peut être utilisé dans les distributions où la version de l'image d'installation d'origine est importante : VERSION_ID changerait lors des mises à jour incrémentales du système, mais BUILD_ID ne changerait pas. Ce champ est facultatif.

Exemples : "BUILD_ID="2013-03-20.3"", "BUILD_ID=201303203".

Ajouté dans la version 200.

IMAGE_ID=

Une chaîne en minuscules (sans espaces ni autres caractères en dehors de 0–9, a–z, ".", "_" et "-"), identifiant une image spécifique du système d'exploitation. Cela est destiné à être utilisé pour les environnements où les images du système d'exploitation sont préparées, construites, distribuées et mises à jour en tant qu'images complètes et cohérentes du système d'exploitation. Ce champ est facultatif et peut ne pas être implémenté sur tous les systèmes, en particulier pas sur ceux qui ne sont pas gérés via des images mais assemblés et mis à jour à partir de paquets individuels sur le système local.

Exemples : "IMAGE_ID=vendorx-cashier-system", "IMAGE_ID=netbook-image".

Ajouté dans la version 249.

IMAGE_VERSION=

Une chaîne en minuscules (principalement numérique, sans espaces ni autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant la version de l'image du système d'exploitation. Cela est destiné à être utilisé avec IMAGE_ID décrit ci-dessus, pour distinguer différentes versions de la même image.

Exemples : "IMAGE_VERSION=33", "IMAGE_VERSION=47.1rc1".

Ajouté dans la version 249.

RELEASE_TYPE=

Une chaîne en minuscules (sans espaces ni autres caractères en dehors de 0-9, a-z, ".", "_", et "-"), décrivant le type de release de cette version du système d'exploitation. Les valeurs connues sont les suivantes :
•"stable" est pour les releases normales du système, adaptées à une utilisation en production. Généralement, les releases stables deviennent obsolètes peu après la sortie de la prochaine release stable majeure, bien que cela ne soit pas toujours le cas si, par exemple, une distribution adopte un modèle de release continue tout en restant prête pour la production. Les exemples incluent Fedora 40, Ubuntu 23.10, OpenSUSE Tumbleweed et Arch Linux.
•"lts" est pour les releases à support à long terme du système, adaptées à une utilisation en production et supportées pendant une période étendue. Généralement, les releases LTS continuent de recevoir du support même si des releases majeures plus récentes de la distribution sont disponibles. Les exemples incluent Ubuntu 24.04, Debian 12 Bookworm et RHEL 9.4.
•"development" est pour les versions instables du système, inadaptées à une utilisation en production, telles que les releases alpha, bêta ou continues instables. Les exemples incluent Fedora Rawhide, Debian Testing, Fedora 40 Bêta et GNOME OS Nightly.
•"experiment" est pour les builds expérimentaux du système, créés spécifiquement pour tester une fonctionnalité en cours de développement. Cela est destiné à être utilisé en combinaison avec EXPERIMENT=.

Si non défini, ou pour une valeur inconnue, supposer que la release est "stable".

Exemples : "RELEASE_TYPE=development", "RELEASE_TYPE=lts".

Ajouté dans la version 257.

Pour résumer : si les mises à jour de l'image sont construites et distribuées en tant qu'unités complètes, IMAGE_ID+IMAGE_VERSION est le meilleur choix. Sinon, si les mises à jour finissent par remplacer complètement les contenus précédemment installés, comme dans une distribution binaire typique, VERSION_ID devrait être utilisé pour identifier les releases majeures du système d'exploitation. BUILD_ID peut être utilisé à la place ou en plus de VERSION_ID lorsque la version de l'image système d'origine est importante.

Informations de présentation et liens

HOME_URL=, DOCUMENTATION_URL=, SUPPORT_URL=, BUG_REPORT_URL=, PRIVACY_POLICY_URL=

Liens vers des ressources sur Internet liées au système d'exploitation. HOME_URL= devrait référencer la page d'accueil du système d'exploitation, ou alternativement une page d'accueil de la version spécifique du système d'exploitation. DOCUMENTATION_URL= devrait référencer la page principale de documentation pour ce système d'exploitation. SUPPORT_URL= devrait référencer la page principale de support du système d'exploitation, s'il y en a une. Cela est principalement destiné aux systèmes d'exploitation pour lesquels les fournisseurs offrent du support. BUG_REPORT_URL= devrait référencer la page principale de signalement de bogues pour le système d'exploitation, s'il y en a une. Cela est principalement destiné aux systèmes d'exploitation qui reposent sur une QA communautaire. PRIVACY_POLICY_URL= devrait référencer la page principale de la politique de confidentialité pour le système d'exploitation, s'il y en a une. Ces paramètres sont facultatifs, et il est courant de ne fournir que certains d'entre eux. Ces URL sont destinées à être exposées dans les interfaces utilisateur "À propos de ce système" derrière des liens avec des libellés tels que "À propos de ce système d'exploitation", "Obtenir du support", "Signaler un bogue" ou "Politique de confidentialité". Les valeurs devraient être au format RFC3986[5], et devraient être des URL "http:" ou "https:", et éventuellement "mailto:" ou "tel:". Une seule URL doit être listée dans chaque paramètre. Si plusieurs ressources doivent être référencées, il est recommandé de fournir une page de destination en ligne liant toutes les ressources disponibles.

Exemples : "HOME_URL="https://fedoraproject.org/"", "BUG_REPORT_URL="https://bugzilla.redhat.com/"".

SUPPORT_END=

La date à laquelle le support pour cette version du système d'exploitation se termine. (Ce que signifie exactement le "manque de support" varie entre les fournisseurs, mais généralement les utilisateurs doivent supposer que les mises à jour, y compris les correctifs de sécurité, ne seront pas fournies.) La valeur est une date au format ISO 8601 "AAAA-MM-JJ", et spécifie le premier jour où le support n'est pas fourni.

Par exemple, "SUPPORT_END=2001-01-01" signifie que le système a été supporté jusqu'à la fin du dernier jour du millénaire précédent.

Ajouté dans la version 252.

LOGO=

Une chaîne, spécifiant le nom d'une icône telle que définie par la Spécification de thème d'icônes freedesktop.org[6]. Cela peut être utilisé par des applications graphiques pour afficher le logo d'un système d'exploitation ou d'un distributeur. Ce champ est facultatif et peut ne pas nécessairement être implémenté sur tous les systèmes.

Exemples : "LOGO=fedora-logo", "LOGO=distributor-logo-opensuse"

Ajouté dans la version 240.

ANSI_COLOR=

Une couleur de présentation suggérée lors de l'affichage du nom du système d'exploitation sur la console. Cela devrait être spécifié comme une chaîne adaptée à l'inclusion dans le code d'échappement ANSI/ECMA-48 ESC [ m pour définir la présentation graphique. Ce champ est facultatif.

Exemples : "ANSI_COLOR="0;31"" pour le rouge, "ANSI_COLOR="1;34"" pour le bleu clair, ou "ANSI_COLOR="0;38;2;60;110;180"" pour le bleu Fedora.

VENDOR_NAME=

Le nom du fournisseur du système d'exploitation. C'est le nom de l'organisation ou de l'entreprise qui produit le système d'exploitation. Ce champ est facultatif.

Ce nom est destiné à être exposé dans les interfaces utilisateur "À propos de ce système" ou les interfaces de mise à jour logicielle lorsque c'est nécessaire pour distinguer le fournisseur du système d'exploitation du système lui-même. Il est destiné à être lisible par l'humain.

Exemples : "VENDOR_NAME="Fedora Project"" pour Fedora Linux, "VENDOR_NAME="Canonical"" pour Ubuntu.

Ajouté dans la version 254.

VENDOR_URL=

La page d'accueil du fournisseur du système d'exploitation. Ce champ est facultatif. Le champ VENDOR_NAME= devrait être défini si celui-ci l'est, bien que les clients doivent être robustes contre l'absence de définition de l'un ou l'autre champ.

La valeur devrait être au format RFC3986[5], et devrait être des URL "http:" ou "https:". Une seule URL doit être listée dans le paramètre.

Exemples : "VENDOR_URL="g/'>https://fedoraproject.org/"", "VENDOR_URL="https://canonical.com/"".

Ajouté dans la version 254.

EXPERIMENT=

Une description lisible par l'humain de ce qui rend cette version du système d'exploitation expérimentale. Ce champ est facultatif. Le RELEASE_TYPE champ doit être défini à "experiment" si ce champ est défini, sinon les clients doivent ignorer ce champ.

Cette description est destinée à être exposée au moment de l'installation du système, ou dans les interfaces "À propos de ce système", pour avertir l'utilisateur qu'il installe/exécute une version expérimentale du système d'exploitation. Si RELEASE_TYPE est "experiment" mais que ce champ n'est pas défini, l'interface devrait quand même avertir l'utilisateur, mais elle sera incapable d'expliquer ce qui est exactement expérimental dans la version actuelle du système d'exploitation.

Exemples : "EXPERIMENT="Passage à DNF5"" pour une version expérimentale de Fedora Linux créée pour tester DNF5, "EXPERIMENT="Portage sur la puce Apple M3"" pour des versions expérimentales d'Asahi Linux portées sur le SoC Apple M3, "EXPERIMENT="Mutter !1441 : Triple/double tamponnage dynamique (v4)"" pour des versions de GNOME OS créées par l'CI de Mutter pour la demande de fusion !1441.

Ajouté dans la version 257.

EXPERIMENT_URL=

La page informative principale sur ce qui rend la version actuelle du système d'exploitation expérimentale, où les utilisateurs peuvent en apprendre davantage sur l'état de l'expérience et potentiellement laisser des commentaires. Ce champ est facultatif. Le EXPERIMENT= champ devrait être défini si celui-ci l'est, bien que les clients doivent être robustes face à l'absence de définition de l'un ou l'autre champ.

La valeur devrait être au format RFC3986[5], et devrait être des URL "http:" ou "https:". Une seule URL doit être listée dans le paramètre.

Exemples, correspondant aux exemples ci-dessus dans EXPERIMENT=: "EXPERIMENT_URL="https://fedoraproject.org/wiki/Changes/SwitchToDnf5"", "EXPERIMENT_URL="https://github.com/AsahiLinux/docs/wiki/M3-Series-Feature-Support"", "EXPERIMENT_URL="https://gitlab.gnome.org/GNOME/mutter/-/merge_requests/1441"".

Ajouté dans la version 257.

Valeurs par défaut et métadonnées au niveau de la distribution

DEFAULT_HOSTNAME=

Une chaîne de caractères spécifiant le nom d'hôte si hostname(5) n'est pas présent et qu'aucune autre source de configuration ne spécifie le nom d'hôte. Doit être soit une étiquette DNS unique (une chaîne composée de caractères ASCII 7 bits en minuscules, sans espaces ni points, limitée au format autorisé pour les étiquettes de noms de domaine DNS), soit une séquence de telles étiquettes séparées par des points simples formant un FQDN DNS valide. Le nom d'hôte doit faire au plus 64 caractères, ce qui est une limitation de Linux (DNS autorise des noms plus longs).

Si le caractère point d'interrogation "?" apparaît dans le nom d'hôte, il est automatiquement remplacé par un caractère hexadécimal dérivé du machine-id(5) lorsqu'il est appliqué, de manière sécurisée et déterministe par hachage cryptographique. Exemple : "foobar-????-????" sera automatiquement étendu en "foobar-92a9-061c" ou similaire, selon l'identifiant de la machine locale.

Voir org.freedesktop.hostname1(5) pour une description de la manière dont systemd-hostnamed.service(8) détermine le nom d'hôte de repli.

Ajouté dans la version 248.

ARCHITECTURE=

Une chaîne de caractères spécifiant l'architecture de processeur requise par les binaires de l'espace utilisateur. Les identifiants d'architecture sont les mêmes que pour ConditionArchitecture= décrit dans systemd.unit(5). Le champ est facultatif et ne devrait être utilisé que lorsqu'une seule architecture est prise en charge. Il peut fournir des informations redondantes lorsqu'il est utilisé dans une partition GPT avec un type GUID qui encode déjà l'architecture. Si ce n'est pas le cas, l'architecture devrait être spécifiée dans, par exemple, une image d'extension, pour empêcher un hôte incompatible de la charger.

Ajouté dans la version 252.

SYSEXT_LEVEL=

Une chaîne en minuscules (principalement numérique, sans espaces ni autres caractères en dehors de 0–9, a–z, ".", "_" et "-") identifiant le niveau de prise en charge des extensions du système d'exploitation, pour indiquer quelles images d'extension sont prises en charge. Voir /usr/lib/extension-release.d/extension-release.IMAGE, initrd[2] et systemd-sysext(8)) pour plus d'informations.

Exemples : "SYSEXT_LEVEL=2", "SYSEXT_LEVEL=15.14".

Ajouté dans la version 248.

CONFEXT_LEVEL=

Sémantiquement identique à SYSEXT_LEVEL= mais pour les images confext. Voir /etc/extension-release.d/extension-release.IMAGE pour plus d'informations.

Exemples : "CONFEXT_LEVEL=2", "CONFEXT_LEVEL=15.14".

Ajouté dans la version 254.

SYSEXT_SCOPE=

Prend une liste d'au moins une chaîne parmi "system", "initrd" et "portable", séparées par des espaces. Ce champ n'est pris en charge que dans les fichiers extension-release.d/ et indique les environnements auxquels l'extension système s'applique : c'est-à-dire aux systèmes réguliers, aux initrds et exitrds, ou aux images de service portables. S'il n'est pas spécifié, "SYSEXT_SCOPE=system portable" est implicite, c'est-à-dire que toute extension système sans ce champ s'applique aux systèmes réguliers et aux environnements de service portable, mais pas aux environnements initrd/exitrd.

Ajouté dans la version 250.

CONFEXT_SCOPE=

Sémantiquement identique à SYSEXT_SCOPE= mais pour les images confext.

Ajouté dans la version 254.

PORTABLE_PREFIXES=

Prend une liste d'au moins une chaîne de correspondance de préfixe valide pour la logique des Services portables[3]. Ce champ sert deux objectifs : il est informatif, identifiant les images de service portable en tant que telles (et permettant ainsi de les distinguer des autres images du système d'exploitation, telles que les images système bootables). Il est également utilisé lorsqu'une image de service portable est attachée : le préfixe de service portable spécifié ou implicite est vérifié par rapport à la liste spécifiée ici, pour faire respecter les restrictions sur la manière dont les images peuvent être attachées à un système.

Ajouté dans la version 250.

Notes

Si vous utilisez ce fichier pour déterminer le système d'exploitation ou une version spécifique de celui-ci, utilisez les champs ID et VERSION_ID , éventuellement avec ID_LIKE comme solution de repli pour ID. Lorsque vous recherchez une chaîne d'identification du système d'exploitation à présenter à l'utilisateur, utilisez le champ PRETTY_NAME .

Notez que les fournisseurs de systèmes d'exploitation peuvent choisir de ne pas fournir d'informations de version, par exemple pour prendre en charge les versions continues. Dans ce cas, VERSION et VERSION_ID peuvent ne pas être définis. Les applications ne doivent pas compter sur la définition de ces champs.

Les fournisseurs de systèmes d'exploitation peuvent étendre le format du fichier et introduire de nouveaux champs. Il est fortement recommandé de préfixer les nouveaux champs avec un nom spécifique au système d'exploitation afin d'éviter les conflits de noms. Les applications lisant ce fichier doivent ignorer les champs inconnus.

Exemple : "DEBIAN_BTS="debbugs://bugs.debian.org/"".

Les gestionnaires d'exécution de conteneurs et de bac à sable peuvent rendre les données d'identification de l'hôte disponibles aux applications en fournissant le /etc/os-release de l'hôte (s'il est disponible, sinon /usr/lib/os-release en solution de repli) en tant que /run/host/os-release.

Exemple 5. Lecture de os-release dans python(1) (toute version)

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
import ast
import re
import sys
def read_os_release():
    try:
        filename = '/etc/os-release'
        f = open(filename)
    except FileNotFoundError:
        filename = '/usr/lib/os-release'
        f = open(filename)
    for line_number, line in enumerate(f, start=1):
        line = line.rstrip()
        if not line or line.startswith('#'):
            continue
        m = re.match(r'([A-Z][A-Z_0-9]+)=(.*)', line)
        if m:
            name, val = m.groups()
            if val and val[0] in '"\'':
                val = ast.literal_eval(val)
            yield name, val
        else:
            print(f'{filename}:{line_number}: bad line {line!r}',
                  file=sys.stderr)

initrd-release.5.en.html









NAME


initrd-release — information about the initial ramdisk environment






SYNOPSIS


The initrd-release interface is described by the
    file /etc/initrd-release.


The file is a simple newline-separated list of environment
    variables, one per line, in the format KEY=VALUE.
    Empty lines and lines starting with # are ignored.






DESCRIPTION


The initrd-release file is used to convey
    information about the operating system and environment to the userspace
    programs running within the initial ramdisk. It is primarily intended to
    allow differentiation between various Linux distributions and their specific
    versions, especially when the actual operating system is not yet mounted.


This file is the successor to the older /etc/os-release
    file, and aims to provide more specific details about the initrd environment
    itself, rather than the final operating system.


The contents of /etc/initrd-release are used
    by tools like systemd-fstab-generator to mount
    filesystems correctly, and potentially by other system services that need to
    adapt their behavior based on the initrd environment.


The format is intended to be compatible with the freedesktop.org
    base directory specification.




AVAILABLE VARIABLES


The following variables are defined:



  
NAME=

  
A lowercase ASCII string identifying the OS, without any version
      component, and suitable for use in scripts or configuration files.
      

      Example: NAME=debian

  
VERSION=

  
A lowercase ASCII string identifying the OS, including the version,
      and suitable for use in scripts or configuration files.
      

      Example: VERSION=11.0.0

  
ID=

  
A lowercase ASCII string identifying the initrd variant, without any
      version component, and suitable for use in scripts or configuration
      files. This is intended for distinguishing between different initrd
      implementations.
      

      Example: ID=systemd-initrd

  
ID_LIKE=

  
A space-separated list of strings, each of which is a lowercase ASCII
      string identifying a certain abstraction of the initrd, including any
      version component and suitable for use in scripts or configuration
      files. This field is optional. This is intended to group different
      initrd implementations that share commonalities.
      

      Example: ID_LIKE=busybox sysvinit

  
PRETTY_NAME=

  
A UTF-8 encoded string suitable for displaying to end users. It contains
      the OS name, version, and potentially other identifying information.
      

      Example: PRETTY_NAME="Debian GNU/Linux 11 (bullseye)"

  
VERSION_CODENAME=

  
A lowercase ASCII string containing the version codename of the initrd,
      if available.
      

      Example: VERSION_CODENAME=bullseye

  
HOME_URL=

  
A URL to the operating system's home page.
      

      Example: HOME_URL="https://www.debian.org/"

  
SUPPORT_URL=

  
A URL to the operating system's support page.
      

      Example: SUPPORT_URL="https://www.debian.org/support"

  
BUG_REPORT_URL=

  
A URL to the operating system's bug reporting page.
      

      Example: BUG_REPORT_URL="https://bugs.debian.org/"

  
BUILD_ID=

  
An identifier for the specific build of the initrd. This should be a
      string that is unique to a specific build, and may change between
      builds.
      

      Example: BUILD_ID=20230101

  
VARIANT=

  
A string identifying the variant of the initrd. This could be used to
      distinguish between different flavors of the same distribution.
      

      Example: VARIANT=desktop

  
VARIANT_ID=

  
A lowercase ASCII string identifying the variant of the initrd, without
      any version component, and suitable for use in scripts or configuration
      files.
      

      Example: VARIANT_ID=desktop








EXAMPLES


A typical /etc/initrd-release file might
    look like this:




NAME=debian
VERSION="11.0.0"
ID=debian
ID_LIKE=debian
PRETTY_NAME="Debian GNU/Linux 11 (bullseye)"
VERSION_CODENAME=bullseye
HOME_URL="https://www.debian.org/"
SUPPORT_URL="https://www.debian.org/support"
BUG_REPORT_URL="https://bugs.debian.org/"
BUILD_ID=20230101
VARIANT=desktop
VARIANT_ID=desktop





To read and use this information in a shell script:




#!/bin/sh

. /etc/initrd-release

echo "Running on ${PRETTY_NAME} (${NAME} ${VERSION})"

if [ "$ID" = "debian" ] || echo "$ID_LIKE" | grep -q "debian"; then
    echo "This is a Debian-based initrd."
fi





Or using Python:




import os

def read_initrd_release():
    release_info = {}
    try:
        with open('/etc/initrd-release', 'r') as f:
            for line in f:
                line = line.strip()
                if line and not line.startswith('#'):
                    key, value = line.split('=', 1)
                    release_info[key] = value.strip('"')
    except FileNotFoundError:
        pass
    return release_info

initrd_release = dict(read_initrd_release())
pretty_name = initrd_release.get('PRETTY_NAME', 'Linux Initrd')
print(f'Running on {pretty_name!r}')
if 'debian' in [initrd_release.get('ID', 'linux'),
                *initrd_release.get('ID_LIKE', '').split()]:
    print('Looks like Debian initrd!')
