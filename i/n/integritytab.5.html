INTEGRITYTAB(5) integritytab INTEGRITYTAB(5)

NOM

integritytab - Configuration pour les périphériques bloc à intégrité protégée

SYNOPSIS

/etc/integritytab

DESCRIPTION

Le fichier /etc/integritytab décrit les périphériques bloc protégés en intégrité qui sont configurés au démarrage du système.

Les lignes vides et les lignes commençant par le caractère "#" sont ignorées. Chacune des lignes restantes décrit un périphérique bloc protégé en intégrité verity. Les champs sont séparés par des espaces blancs.

Chaque ligne est de la forme

nom-volume périphérique-bloc
    [fichier-clé|-] [options|-]

Les deux premiers champs sont obligatoires, les deux restants sont facultatifs et ne sont requis que si l'utilisateur a spécifié des options non par défaut lors du formatage de l'intégrité.

Le premier champ contient le nom du volume d'intégrité résultant ; son périphérique bloc est configuré sous /dev/mapper/.

Le second champ contient un chemin vers le périphérique bloc sous-jacent, ou une spécification d'un périphérique bloc via "UUID=" suivie de l'UUID, "PARTUUID=" suivie de l'UUID de la partition, "LABEL=" suivie du label, "PARTLABEL=" suivie du label de la partition.

Le troisième champ, s'il est présent, contient un chemin absolu vers un fichier clé ou un "-" pour spécifier aucun. Lorsque le nom de fichier est présent, l'« intégrité-algorithme » vaut par défaut « hmac-sha256 » avec une longueur de clé dérivée du nombre d'octets dans le fichier clé. À ce stade, le seul algorithme d'intégrité pris en charge lors de l'utilisation d'un fichier clé est hmac-sha256. La taille maximale du fichier clé est de 4096 octets.

Le quatrième champ, s'il est présent, est une liste d'options séparées par des virgules ou un "-" pour spécifier aucun. Les options suivantes sont reconnues :

allow-discards

Autorise l'utilisation des requêtes de suppression (TRIM) pour le périphérique. Cette option est disponible depuis la version 5.7 du noyau Linux.

Ajouté dans la version 250.

mode=(journal|bitmap|direct)

Active le mode journalisé, bitmap ou direct (passthrough). Le mode journalisé est le défaut lorsque cette option n'est pas spécifiée. Il offre une sécurité contre les plantages, mais peut être lent car toutes les données doivent être écrites deux fois. Le mode bitmap est plus efficace car il ne nécessite qu'une seule écriture, mais il est moins fiable car si une corruption de données se produit lors d'un plantage de la machine, elle pourrait ne pas être détectée. Le mode direct désactive le journal et le bitmap. Correspond au mode « écritures directes » documenté dans la documentation dm-integrity[1]. Notez que sans journal, en cas de plantage, il est possible que les balises d'intégrité et les données ne correspondent pas. Si utilisé, les options journal-* ci-dessous n'auront aucun effet si elles sont passées.

Ajouté dans la version 254.

journal-watermark=[0..100]%

Seuil du journal en pourcentage. Lorsque le pourcentage du journal dépasse ce seuil, la vidange du journal sera démarrée. Définir une valeur de "0%" utilise la valeur par défaut.

Ajouté dans la version 250.

journal-commit-time=[0..N]

Temps de validation en millisecondes. Lorsque ce temps s'est écoulé (et qu'aucune opération de vidange explicite n'a été émise), le journal est écrit. Définir une valeur de zéro utilise la valeur par défaut.

Ajouté dans la version 250.

data-device=/dev/disk/by-...

Spécifie un périphérique bloc séparé qui contient des données existantes. Le second champ spécifié dans integritytab pour le périphérique bloc contiendra alors les balises d'intégrité calculées et le journal pour le data-device, mais pas les données utilisateur finales.

Ajouté dans la version 250.

integrity-algorithm=[crc32c|crc32|xxhash64|sha1|sha256|hmac-sha256]

L'algorithme utilisé pour la vérification de l'intégrité. Le défaut est crc32c. Doit correspondre à l'option utilisée lors du formatage.

Ajouté dans la version 250.

_netdev

Marque ce périphérique veritysetup comme nécessitant un réseau. Il sera démarré après la disponibilité du réseau, de manière similaire aux unités systemd.mount(5) marquées avec _netdev. L'unité de service pour configurer ce périphérique sera ordonnancée entre remote-fs-pre.target et remote-integritysetup.target, au lieu de integritysetup-pre.target et integritysetup.target.

Indice : si ce périphérique est utilisé pour un point de montage spécifié dans fstab(5), l'option _netdev devrait également être utilisée pour le point de montage. Sinon, une boucle de dépendance pourrait être créée où le point de montage sera tiré par local-fs.target, tandis que le service de configuration du réseau n'est généralement démarré qu'après le montage du système de fichiers local.

Ajouté dans la version 258.

noauto

Ce périphérique ne sera pas ajouté à integritysetup.target. Cela signifie qu'il ne sera pas automatiquement activé au démarrage, à moins que quelque chose d'autre ne le tire. En particulier, si le périphérique est utilisé pour un point de montage, il sera automatiquement activé au démarrage, à moins que le point de montage lui-même ne soit également désactivé avec noauto.

Ajouté dans la version 258.

nofail

Ce périphérique ne sera pas une dépendance forte de integritysetup.target. Il sera toujours tiré et démarré, mais le système n'attendra pas que le périphérique apparaisse et soit activé, et le démarrage ne échouera pas si cela échoue. Notez que d'autres unités dépendant du périphérique activé peuvent toujours échouer. En particulier, si le périphérique est utilisé pour un point de montage, le point de montage lui-même doit également avoir l'option nofail, sinon le démarrage échouera si le périphérique n'est pas activé avec succès.

Ajouté dans la version 258.

Au début du démarrage et lorsque la configuration du gestionnaire système est rechargée, ce fichier est traduit en unités systemd natives par systemd-integritysetup-generator(8).

EXEMPLES

Exemple 1. /etc/integritytab

Configuration de deux périphériques bloc protégés en intégrité.

home PARTUUID=4973d0b8-1b15-c449-96ec-94bab7f6a7b8 - journal-commit-time=10,allow-discards,journal-watermark=55%
data PARTUUID=5d4b1808-be76-774d-88af-03c4c3a41761 - allow-discards

Exemple 2. /etc/integritytab

Configuration de 1 périphérique bloc protégé en intégrité en utilisant les défauts

home PARTUUID=4973d0b8-1b15-c449-96ec-94bab7f6a7b8

Exemple 3. /etc/integritytab

Configuration de 1 périphérique d'intégrité utilisant un périphérique bloc de données existant qui contient des données utilisateur

home PARTUUID=4973d0b8-1b15-c449-96ec-94bab7f6a7b8 - data-device=/dev/disk/by-uuid/9276d9c0-d4e3-4297-b4ff-3307cd0d092f

Exemple 4. /etc/integritytab

Configuration de 1 périphérique d'intégrité utilisant un fichier clé HMAC en utilisant les défauts

home PARTUUID=4973d0b8-1b15-c449-96ec-94bab7f6a7b8 /etc/hmac.key
