Cette page man est générée à partir du fichier indent.texinfo. Il s'agit de l'édition de "The indent Manual", pour la version de Indent, mise à jour le

.

Le programme indent peut être utilisé pour rendre le code plus facile à lire. Il peut également convertir d'un style d'écriture C à un

autre.

indent comprend une quantité substantielle de la syntaxe de C, mais il essaie également de faire face à une syntaxe incomplète et

malformée.

Dans la version 1.2 et les versions

plus récentes, le style GNU de
indentation est celui par défaut.

APPEL

D'INDENT

Depuis la version 1.3, le format de la commande indent est

: 


indent [options] [fichiers-d'entrée]
indent [options] [fichier-d'entrée-unique] [-o fichier-de-sortie]

Ce format diffère des versions antérieures et des autres versions de indent

.

Dans la première forme, un ou plusieurs fichiers d'entrée sont spécifiés. indent crée une copie de sauvegarde de chaque fichier, et le fichier original est remplacé par sa version indentée. Voir FICHIERS DE SAUVEGARDE, pour une explication de la manière dont les sauvegardes sont

effectuées.

Dans la seconde forme, un seul fichier d'entrée est spécifié. Dans ce cas, ou lorsque l'entrée standard est utilisée, vous pouvez spécifier un fichier de sortie après l'option

‘-o’.

Pour faire en sorte que indent écrive sur la sortie standard, utilisez l'option ‘-st’. Cela n'est autorisé que s'il n'y a qu'un seul fichier d'entrée, ou si l'entrée standard est

utilisée.

Si aucun fichier d'entrée n'est nommé, l'entrée standard est lue. De même, si un nom de fichier ‘-’ est spécifié, alors l'entrée standard est

lue.

À titre d'exemple, chacune des commandes suivantes lira le programme ‘slithy_toves.c’ et écrira son texte indenté dans ‘slithy_toves.out’

: 


indent slithy_toves.c -o slithy_toves.out
indent -st slithy_toves.c > slithy_toves.out
cat slithy_toves.c | indent -o slithy_toves.out

La plupart des autres options de indent contrôlent la manière dont les programmes sont formatés. Depuis la version 1.2, indent reconnaît également un nom long pour chaque nom d'option. Les options longues sont préfixées par ‘--’ ou ‘+’. [ ‘+’ est remplacé par ‘--’ pour maintenir la cohérence avec la norme POSIX.]
Dans la plupart de ce document, les noms traditionnels, courts, sont utilisés par souci de concision. Voir RÉSUMÉ DES OPTIONS, pour une liste des options, incluant à la fois les noms longs et

courts.

Voici un autre exemple

: 


indent -br test/metabolism.c -l85

Cela indentera le programme ‘test/metabolism.c’ en utilisant les options ‘-br’ et ‘-l85’, écrira la sortie dans ‘test/metabolism.c’, et écrira le contenu original de ‘test/metabolism.c’ dans un fichier de sauvegarde dans le répertoire

‘test’.

Des appels équivalents utilisant les noms longs d'options pour cet exemple seraient

: 


indent --braces-on-if-line --line-length185 test/metabolism.c
indent +braces-on-if-line +line-length185 test/metabolism.c

Si vous trouvez que vous utilisez souvent indent avec les mêmes options, vous pouvez placer ces options dans un fichier nommé ‘.indent.pro’. indent cherchera un fichier de profil à trois endroits. D'abord, il vérifiera la variable d'environnement INDENT_PROFILE. Si elle existe, sa valeur doit nommer le fichier à utiliser. Si la variable d'environnement n'existe pas, indent cherche ‘.indent.pro’ dans le répertoire courant
et l'utilise s'il est trouvé. Enfin indent cherchera dans votre répertoire personnel ‘.indent.pro’ et utilisera ce fichier s'il est trouvé. Ce comportement diffère de celui des autres versions de indent, qui chargent les deux fichiers s'ils existent tous les

deux.

Le format de ‘.indent.pro’ est simplement une liste d'options, exactement comme elles apparaîtraient sur la ligne de commande, séparées par des espaces blancs (tabulations, espaces et retours à la ligne). Les options dans ‘.indent.pro’ peuvent être entourées de commentaires C ou C++, auquel cas elles sont

ignorées.

Les options de la ligne de commande sont traitées après le traitement de ‘ ?.indent.pro’. Les options spécifiées plus tard remplacent les arguments spécifiés plus tôt, à une exception près : les options explicitement spécifiées remplacent toujours les options de fond (voir STYLES COURANTS). Vous pouvez empêcher indent de lire un fichier ‘.indent.pro

’ en spécifiant
l'option ‘-npro’.

FICHIERS DE

SAUVEGARDE

Depuis la version 1.3, GNU indent crée des fichiers de sauvegarde de style GNU, de la même manière que GNU Emacs. Cela signifie que soit des noms de fichiers de sauvegarde simples ou numérotés peuvent être

créés.

Les noms de fichiers de sauvegarde simples sont générés en ajoutant un suffixe au nom du fichier original. La valeur par défaut de ce suffixe est la chaîne d'un seul caractère ‘~’ (tilde). Ainsi, le fichier de sauvegarde de ‘python.c’ serait ‘python.

c~’.

Au lieu de la valeur par défaut, vous pouvez spécifier n'importe quelle chaîne comme suffixe en définissant la variable d'environnement SIMPLE_BACKUP_SUFFIX avec votre suffixe

préféré.

Les versions numérotées de sauvegarde d'un fichier ‘momeraths.c’ ressemblent à ‘momeraths.c.~23~’, où 23 est la version de cette sauvegarde particulière. Lors de la création d'une sauvegarde numérotée du fichier ‘src/momeraths.c’, le fichier de sauvegarde sera nommé ‘src/momeraths.c.~V~’, où V est supérieur d'une unité à la version la plus élevée existant actuellement dans le répertoire ‘src’. La variable d'environnement VERSION_WIDTH contrôle le nombre de chiffres, en complétant par des zéros à gauche si nécessaire. Par exemple, définir cette variable à "2" conduira à ce que le fichier de sauvegarde soit nommé ‘momeraths.c.

~04~’.

Le type de fichier de sauvegarde créé est contrôlé par la valeur de la variable d'environnement VERSION_CONTROL. Si c'est la chaîne ‘simple’, alors seules des sauvegardes simples seront créées. Si sa valeur est la chaîne ‘numbered’, alors des sauvegardes numérotées seront créées. Si sa valeur est ‘numbered-existing’, alors des sauvegardes numérotées seront créées s'il existe déjà des sauvegardes numérotées pour le fichier en cours d'indentation ; sinon, une sauvegarde simple est créée. Si VERSION_CONTROL n'est pas défini, alors indent suppose le comportement de ‘numbered-existing’

.

D'autres versions de indent utilisent le suffixe ‘.BAK’ pour nommer les fichiers de sauvegarde. Ce comportement peut être imité en définissant SIMPLE_BACKUP_SUFFIX à ‘.

BAK’.

Notez également que d'autres versions de indent créent des sauvegardes dans le répertoire courant, plutôt que dans le répertoire du fichier source comme GNU indent le fai

t maint
enant.

STYLES

COURANTS

Il existe plusieurs styles courants de code C, y compris le style GNU, le style Kernighan & Ritchie, et le style Berkeley original. Un style peut être sélectionné avec une seule option de fond, qui spécifie un ensemble de valeurs pour toutes les autres options. Cependant, les options explicitement spécifiées remplacent toujours les options impliquées par une option de

fond.

Depuis la version 1.2, le style par défaut de GNU indent est le style GNU. Ainsi, il n'est plus nécessaire de spécifier l'option ‘-gnu’ pour obtenir ce format, bien que cela ne provoque pas d'erreur. Les paramètres d'options correspondant au style GNU sont

: 


-nbad -bap -nbc -bbo -bl -bli2 -bls -ncdb -nce -cp1 -cs -di2
-ndj -nfc1 -nfca -hnl -i2 -ip5 -lp -pcs -nprs -psl -saf -sai
-saw -nsc -nsob

Le style de codage GNU est celui préféré par le projet GNU. C'est le style que le mode C de GNU Emacs encourage et qui est utilisé dans les parties C de GNU Emacs. (Les personnes intéressées à écrire des programmes pour le Projet GNU devraient obtenir une copie de "The GNU Coding Standards", qui couvre également les questions sémantiques et de portabilité telles que l'utilisation de la mémoire, la taille des entiers, etc.

)

Le style Kernighan & Ritchie est utilisé tout au long de leur livre bien connu "The C Programming Language". Il est activé avec l'option ‘-kr’. Le style Kernighan & Ritchie correspond à l'ensemble d'options suivant

: 


-nbad -bap -bbo -nbc -br -brs -c33 -cd33 -ncdb -ce -ci4 -cli0
-cp33 -cs -d0 -di1 -nfc1 -nfca -hnl -i4 -ip0 -l75 -lp -npcs
-nprs -npsl -saf -sai -saw -nsc -nsob -nss -par

Le style Kernighan & Ritchie ne place pas les commentaires à droite du code dans la même colonne en permanence (et n'utilise pas non plus un seul espace à droite du code), donc pour ce style indent a arbitrairement choisi la colonne

33.

Le style de l'indent original de Berkeley peut être obtenu en spécifiant ‘-orig’ (ou en spécifiant ‘--original’, en utilisant le nom long de l'option). Ce style est équivalent aux paramètres suivants

: 


-nbad -nbap -bbo -bc -br -brs -c33 -cd33 -cdb -ce -ci4 -cli0
-cp33 -di16 -fc1 -fca -hnl -i4 -ip4 -l75 -lp -npcs -nprs -psl
-saf -sai -saw -sc -nsob -nss -ts8

Le style Linux est utilisé dans le code du noyau Linux et les pilotes. Le code doit généralement suivre le style de codage Linux pour être accepté. Ce style est équivalent aux paramètres suivants

: 


-nbad -bap -nbc -bbo -hnl -br -brs -c33 -cd33 -ncdb -ce -ci4 
-cli0 -d0 -di1 -nfc1 -i8 -ip0 -l80 -lp -npcs -nprs -npsl -sai
-saf -saw -ncs -nsc -sob -nfca -cp33 -ss -ts8 -il1

VIDES

COMMENTAIRE

S

indent met en forme les commentaires C et C++. Les commentaires C commencent par ‘/*’, se terminent par ‘*/’ et peuvent contenir des caractères de nouvelle ligne. Les commentaires C++ commencent avec le délimiteur ‘//’ et se terminent à la nouvelle

ligne.

indent traite les commentaires différemment selon leur contexte. indent tente de distinguer entre les commentaires qui suivent des instructions, les commentaires qui suivent des déclarations, les commentaires suivant des directives de préprocesseur, et les commentaires qui ne sont précédés par aucun code, c’est-à-dire qu’ils commencent le texte de la ligne (bien que pas nécessairement en colonne 1)

.

indent distingue en outre entre les commentaires trouvés en dehors des procédures et des agrégats, et ceux qui s’y trouvent. En particulier, un commentaire commençant une ligne à l’intérieur d’une procédure sera indenté à la colonne à laquelle le code est actuellement indenté. L’exception à cela est un commentaire commençant dans la colonne la plus à gauche ; un tel commentaire est produit à cette

colonne.

indent tente de laisser les commentaires encadrés non modifiés. L’idée générale d’un tel commentaire est qu’il est enclos dans un rectangle ou une « boîte » d’astérisques ou de tirets pour le distinguer visuellement. Plus précisément, les commentaires encadrés sont définis comme ceux dans lesquels le ‘/*’ initial est immédiatement suivi du caractère ‘*’, ‘=’, ‘_’, ou ‘-’, ou ceux dans lesquels le délimiteur de début de commentaire (‘/*’) est sur une ligne à lui seul, et la ligne suivante commence par un ‘*’ dans la même colonne que l’astérisque du délimiteur

d’ouverture.

Exemples de commentaires encadrés

: 


/**********************
 * Comment in a box!! *
 **********************/
       /*
        * A different kind of scent,
        * for a different kind of comment.
        */

indent tente de laisser les commentaires encadrés exactement tels qu’ils sont trouvés dans le fichier source. Ainsi, l’indentation du commentaire est inchangée, et sa longueur n’est pas vérifiée d’aucune manière. La seule modification effectuée est qu’un caractère de tabulation incorporé peut être converti en le nombre approprié

d’espaces.

Si l’option ‘-bbb’ est spécifiée, tous ces commentaires encadrés seront précédés d’une ligne vide, sauf si un tel commentaire est précédé par du

code.

Les commentaires qui ne sont pas des commentaires encadrés peuvent être mis en forme, ce qui signifie que la ligne est coupée pour tenir dans une marge de droite et remplie à gauche avec des espaces. Les nouvelles lignes simples sont équivalentes à un espace, mais les lignes vides (deux nouvelles lignes ou plus à la suite) sont considérées comme un saut de paragraphe. La mise en forme des commentaires qui commencent après la première colonne est activée avec l’option ‘-fca’. Pour mettre en forme ceux qui commencent en colonne un, spécifiez ‘-fc1’. Cette mise en forme est désactivée par

défaut.

La marge de droite pour la mise en forme est par défaut à 78, mais peut être changée avec l’option ‘-lc’. Si la marge spécifiée ne permet pas d’imprimer le commentaire, la marge sera automatiquement étendue pour la durée de ce commentaire. La marge n’est pas respectée si le commentaire n’est pas mis en

forme.

Si l’option ‘-fnc’ est spécifiée, tous les commentaires avec ‘/*’ incorporé auront cette séquence de caractères remplacée par un espace suivi du caractère ‘*’, éliminant ainsi

l’imbrication.

Si le commentaire commence une ligne (c’est-à-dire qu’il n’y a pas de texte de programme à sa gauche), il sera indenté à la colonne où il a été trouvé, sauf si le commentaire se trouve à l’intérieur d’un bloc de code. Dans ce cas, un tel commentaire sera aligné avec le code indenté de ce bloc (sauf si le commentaire commençait dans la première colonne). Cet alignement peut être affecté par l’option ‘-d’, qui spécifie un décalage de combien de tels commentaires sont déplacés vers la gauche, ou désindentés. Par exemple, ‘-d2’ place les commentaires deux espaces à gauche du code. Par défaut, les commentaires sont alignés avec le code, sauf s’ils commencent dans la première colonne, auquel cas ils y sont laissés par défaut --- pour les aligner avec le code, spécifiez

‘-fc1’.

Les commentaires à droite du code apparaîtront par défaut en colonne 33. Cela peut être changé avec l’une des trois options. ‘-c’ spécifie la colonne pour les commentaires suivant le code, ‘-cd’ spécifie la colonne pour les commentaires suivant les déclarations, et ‘-cp’ spécifie la colonne pour les commentaires suivant les directives de préprocesseur #else et #endif. ‘-dj’ combiné avec ‘-cd0’ peut être utilisé pour supprimer l’alignement des commentaires à droite des déclarations, faisant en sorte que le commentaire suive un tabulateur après la fin de la déclaration. Normalement ‘-cd0’ fait en sorte que ‘-c’ devienne

effectif.

Si le code à gauche du commentaire dépasse la colonne de début, la colonne du commentaire sera étendue à la prochaine colonne de tabulation après la fin du code, sauf si l’option ‘-ntac’ est spécifiée. Dans le cas des directives de préprocesseur, les commentaires sont étendus d’un espace après la fin de la directive. Cette extension ne dure que pour la sortie de ce commentaire

particulier.

L’option ‘-cdb’ place les délimiteurs de commentaire sur des lignes vides. Ainsi, un commentaire sur une seule ligne comme /* Loving hug */ peut être transformé en

: 


/*
   Loving hug
 */

Des astérisques peuvent être placés au début des commentaires multi-lignes avec l’option ‘-sc’. Ainsi, le commentaire sur une seule ligne ci-dessus peut être transformé (avec ‘-cdb -sc’) en

: 


/*
 * Loving hug
 */

INSTRUCTION

S

L’option ‘-br’ ou ‘-bl’ spécifie comment mettre en forme les

accolades.

L’option ‘-br’ met en forme les accolades d’instruction comme ceci

: 


if (x > 0) {
  x--;
}

L’option ‘-bl’ les met en forme comme ceci

: 


if (x > 0)
  {
    x--;
  }

Si vous utilisez l’option ‘-bl’, vous voudrez peut-être aussi spécifier l’option ‘-bli’. Cette option spécifie le nombre d’espaces de décalage des accolades. ‘-bli2’, la valeur par défaut, donne le résultat montré ci-dessus. ‘-bli0’ donne le résultat suivant

: 


if (x > 0)
{
  x--;
}

Si vous utilisez l’option ‘-br’, vous voudrez probablement aussi utiliser l’option ‘-ce’. Cela fait en sorte que le else dans une construction si-alors-sinon se colle au ‘}’ immédiatement précédent. Par exemple, avec ‘-br -ce’ vous obtenez le résultat suivant

: 


if (x > 0) {
  x--;
} else {
  fprintf (stderr, "...something wrong?\n");
}

Avec ‘-br -nce’ ce code apparaîtrait

comme 


if (x > 0) {
  x--;
}
else {
  fprintf (stderr, "...something wrong?\n");
}

Une exception à ce comportement se produit lorsqu’il y a un commentaire entre l’accolade fermante et l’instruction else suivante. Bien que l’option ‘-br’ fasse en sorte qu’une accolade ouvrante saute par-dessus le commentaire, le else ne saute pas par-dessus le commentaire pour se coller, car il y a une forte probabilité de changer le sens du

commentaire.

L’option ‘-cdw’ fait en sorte que le while dans une boucle do-while se colle au ‘}’ immédiatement précédent. Par exemple, avec ‘-cdw’ vous obtenez le résultat suivant

: 


do {
  x--;
} while (x);

Avec ‘-ncdw’ ce code apparaîtrait

comme 


do {
  x--;
}
while (x);

L’option ‘-slc’ permet à un conditionnel sans accolades et à son instruction interne d’apparaître sur la même ligne. Par exemple

: 


if (x) x--;
else x++;

Sans ‘-slc’ ce code apparaîtrait

comme 


if (x)
  x--;
else
  x++;

L’option ‘-cli’ spécifie le nombre d’espaces de décalage vers la droite des étiquettes case par rapport à laaining switch stat

ement.

The default gives code

like: 


switch (i)
  {
  case 0:
    break;
  case 1:
    {
      ++i;
    }
  default:
    break;
  }

Using the ‘-cli2’ that would

become: 


switch (i)
  {
    case 0:
      break;
    case 1:
      {
        ++i;
      }
    default:
      break;
  }

The indentation of the braces below a case statement can be controlled with the ‘-cbin’ option. For example, using ‘-cli2 -cbi0’ results

in: 


switch (i)
  {
    case 0:
      break;
    case 1:
    {
      ++i;
    }
    default:
      break;
  }

If a semicolon is on the same line as a for or while statement, the ‘-ss’ option will cause a space to be placed before the semicolon. This emphasizes the semicolon, making it clear that the body of the for or while statement is an empty statement. ‘-nss’ disables this

feature.

The ‘-pcs’ option causes a space to be placed between the name of the procedure being called and the ‘(’ (for example, puts ("Hi");. The ‘-npcs’ option would give puts("Hi");)

.

If the ‘-cs’ option is specified, indent puts a space between a cast operator and the object to be cast. The ‘-ncs’ ensures that there is no space between the cast operator and the object. Remember that indent only knows about the standard C data types and so cannot recognise user-defined types in casts. Thus (mytype)thing is not treated as a

cast.

The ‘-bs’ option ensures that there is a space between the keyword sizeof and its argument. In some versions, this is known as the ‘Bill_Shannon’

option.

The ‘-saf’ option forces a space between a for and the following parenthesis. This is the

default.

The ‘-sai’ option forces a space between a if and the following parenthesis. This is the

default.

The ‘-saw’ option forces a space between a while and the following parenthesis. This is the

default.

The ‘-prs’ option causes all parentheses to be separated with a space from whatever is between them. For example, using ‘-prs’ results in code

like:

    {

      *e_code++ = ’ ’;

DECLARATION

S

By default indent will line up identifiers, in the column specified by the ‘-di’ option. For example, ‘-di16’ makes things look

like: 


int             foo;
char           *bar;

Using a small value (such as one or two) for the ‘-di’ option can be used to cause the identifiers to be placed in the first available position; for

example: 


int foo;
char *bar;

The value given to the ‘-di’ option will still affect variables which are put on separate lines from their types, for example ‘-di2’ will lead

to: 


int
  foo;

If the ‘-bc’ option is specified, a newline is forced after each comma in a declaration. For

example, 


int a,
  b,
  c;

With the ‘-nbc’ option this would look

like 


int a, b, c;

The ‘-bfda’ option causes a newline to be forced after the comma separating the arguments of a function declaration. The arguments will appear at one indention level deeper than the function declaration. This is particularly helpful for functions with long argument lists. The option ‘-bfde’ causes a newline to be forced before the closing bracket of the function declaration. For both options the ’n’ setting is the default: -nbfda and

-nbfde.

For

example, 


void foo (int arg1, char arg2, int *arg3, long arg4, char arg5);
With the ‘-bfda’ option this would look like 


void foo (
    int arg1,
    char arg2,
    int *arg3,
    long arg4,
    char arg5);

With, in addition, the ‘-bfde’ option this would look

like 


void foo (
    int arg1,
    char arg2,
    int *arg3,
    long arg4,
    char arg5
    );

The ‘-psl’ option causes the type of a procedure being defined to be placed on the line before the name of the procedure. This style is required for the etags program to work correctly, as well as some of the c-mode functions of

Emacs.

You must use the ‘-T’ option to tell indent the name of all the typenames in your program that are defined by typedef. ‘-T’ can be specified more than once, and all names specified are used. For example, if your program

contains 


typedef unsigned long CODE_ADDR;
typedef enum {red, blue, green} COLOR;

you would use the options ‘-T CODE_ADDR -T

COLOR’.

The ‘-brs’ or ‘-bls’ option specifies how to format braces in struct declarations. The ‘-brs’ option formats braces like

this: 


struct foo {
  int x;
};

The ‘-bls’ option formats them like

this: 


struct foo
{
  int x;
};

Similarly to the structure brace ‘-brs’ and ‘-bls’ options,
the function brace options ‘-brf’ or ‘-blf’ specify how to format the braces in function definitions. The ‘-brf’ option formats braces like

this: 


int one(void) {
  return 1;
};

The ‘-blf’ option formats them like

this: 


int one(void)
{
  return 1;
};

The ‘-sar’ option affects how indent will render initializer lists. Without ‘-sar’ they are formatted like

this: 


int a[] = {1, 2, 3, 4};
struct s {
  const char *name;
  int x;
} a[] = {
  {"name", 0},
  {"a", 1}
};

With ‘-sar’ they are formatted like this, with spaces inside the

braces: 


int a[] = { 1, 2, 3, 4 };
struct s {
  const char *name;
  int x;
} a[] = {
  { "name", 0 },
  { "a", 1 }
};

INDENTATIO

N

The most basic, and most controversial issues with regard to code formatting is precisely how indentation should be acoomplished. Fortunately, indent supports several different styles of identation. The default is to use tabs for indentation, which is specified by the ‘-ut’ option. Assuming the default tab size of 8, the code would look like

this: 


int a(int b)
{
        return b;
|------|
 1 tab
}

For those that prefer spaces to tabs, ‘indent’ provides the ‘-nut’ option. The same code would look like

this: 


int a(int b)
{
        return b;
|------|
8 spaces
}

Another issue in the formatting of code is how far each line should be indented from the left margin. When the beginning of a statement such as if or for is encountered, the indentation level is increased by the value specified by the ‘-i’ option. For example, use ‘-i8’ to specify an eight character indentation for each level. When a statement is broken across two lines, the second line is indented by a number of additional spaces specified by the ‘-ci’ option. ‘-ci’ defaults to 0. However, if the ‘-lp’ option is specified, and a line has a left parenthesis which is not closed on that line, then continuation lines will be lined up to start at the character position just after the left parenthesis. This processing also applies to ‘[’ and applies to ‘{’ when it occurs in initialization lists. For example, a piece of continued code might look like this with ‘-nlp -ci3’ in

effect: 


  p1 = first_procedure (second_procedure (p2, p3),
     third_procedure (p4, p5));

With ‘-lp’ in effect the code looks somewhat

clearer: 


  p1 = first_procedure (second_procedure (p2, p3),
                        third_procedure (p4, p5));

When a statement is broken in between two or more paren pairs (...), each extra pair causes the indentation level extra

indentation: 


if ((((i < 2 &&
        k > 0) || p == 0) &&
    q == 1) ||
  n = 0)

The option ‘-ipN’ can be used to set the extra offset per paren. For instance, ‘-ip0’ would format the above

as: 


if ((((i < 2 &&
  k > 0) || p == 0) &&
  q == 1) ||
  n = 0)

indent assumes that tabs are placed at regular intervals of both input and output character streams. These intervals are by default 8 columns wide, but (as of version 1.2) may be changed by the ‘-ts’ option. Tabs are treated as the equivalent number of

spaces.

By default, indent will use tabs to indent as far as possible, and then pad with spaces until the desired position is reached. However, with the ‘-as’ option, spaces will be used for alignment beyond the current indentation level. By default, assuming ‘-lp’ is enabled, the code would be indented like so (‘t’ represents tabs, ‘s’ represents spaces)

Les options suivantes peuvent être utilisées pour modifier la façon dont indent met en forme le code.

Le paramètre ‘-kr’ (ou ‘--kernighan’) force indent à placer les accolades ouvrantes sur la même ligne que la déclaration, comme dans cet exemple :

BRISER LES LIGNES LONGUES

Avec l'option ‘-ln’, ou ‘--line-lengthn’, il est possible de spécifier la longueur maximale d'une ligne de code C, sans inclure les commentaires éventuels qui la suivent.

Lorsque les lignes deviennent plus longues que la longueur spécifiée, GNU indent essaie de briser la ligne à un endroit logique. Ceci est nouveau depuis la version 2.1 cependant et n'est pas encore très intelligent ni flexible.

Actuellement, trois options permettent d'interférer avec l'algorithme qui détermine où briser une ligne.

L'option ‘-bbo’ (ou ‘--break-before-boolean-operators’) fait en sorte que GNU indent préfère briser les lignes longues avant les opérateurs booléens && et ||. L'option ‘-nbbo’ (ou ‘--no-break-before-boolean-operators’) fait que GNU indent n'a pas cette préférence. Par exemple, l'option par défaut ‘-bbo’ (avec ‘--line-length60’ et ‘--ignore-newlines’) donne au code l'aspect suivant :


  if (mask
      && ((mask[0] == ’\0’)
          || (mask[1] == ’\0’
              && ((mask[0] == ’0’) || (mask[0] == ’*’)))))

En utilisant l'option ‘-nbbo’, cela ressemblera à ceci :


  if (mask &&
      ((mask[0] == ’\0’) ||
       (mask[1] == ’\0’ &&
        ((mask[0] == ’0’) || (mask[0] == ’*’)))))

L'option par défaut ‘-hnl’ (ou ‘--honour-newlines’), cependant, respecte les sauts de ligne dans le fichier d'entrée en leur donnant la plus haute priorité possible pour briser les lignes. Par exemple, lorsque le fichier d'entrée ressemble à ceci :


  if (mask
      && ((mask[0] == ’\0’)
      || (mask[1] == ’\0’ && ((mask[0] == ’0’) || (mask[0] == ’*’)))))

Alors, en utilisant l'option ‘-hnl’, ou ‘--honour-newlines’, conjointement avec les options ‘-nbbo’ et ‘--line-length60’ mentionnées précédemment, le résultat ne sera pas celui donné dans le dernier exemple, mais privilégiera plutôt le bris aux positions où le code était brisé dans le fichier d'entrée :


  if (mask
      && ((mask[0] == ’\0’)
          || (mask[1] == ’\0’ &&
              ((mask[0] == ’0’) || (mask[0] == ’*’)))))

L'idée derrière cette option est que les lignes trop longues, mais déjà séparées, ne seront pas touchées par GNU indent. Un code vraiment désordonné devrait cependant être traité par indent au moins une fois en utilisant l'option ‘--ignore-newlines’.

L'option ‘-gts’ (ou ‘--gettext-support’) affecte la manière dont les macros standard gettext _() et N_() sont traitées. Le comportement par défaut (ou l'utilisation de ‘-ngts’) amène indent à les traiter comme les autres fonctions, de sorte qu'une longue chaîne de caractères est brisée comme dans l'exemple suivant.


  if (mask)
    {
      warning (_
               ("This is a long string that stays together."));
    }

Avec l'option ‘-gts’, le trait de soulignement est traité comme faisant partie de la chaîne, le liant à celle-ci, et respectant le fait que gettext fournit discrètement une chaîne localisée. Cela ne fonctionne que si _(" est groupé comme une unité au début de la chaîne et ") est groupé comme une unité à la fin.


  if (mask)
    {
      warning 
        (_("This is a long string that stays together."));
    }

DÉSACTIVER LA MISE EN FORME

La mise en forme du code C peut être désactivée pour certaines parties d'un programme en intégrant des *commentaires de contrôle* spéciaux dans le programme. Pour désactiver la mise en forme d'une section d'un programme, placez le commentaire de désactivation /* *INDENT-OFF* */ sur une ligne seule juste avant cette section. Le texte du programme analysé après ce commentaire de contrôle est affiché exactement tel qu'il a été saisi, sans modification, jusqu'à ce que le commentaire d'activation correspondant soit rencontré sur une ligne seule. Le commentaire d'activation est /* *INDENT-ON* */, et tout texte suivant le commentaire sur la ligne est également affiché sans mise en forme. La mise en forme reprend avec la ligne d'entrée suivant le commentaire d'activation.

Plus précisément, indent n'essaie pas de vérifier le délimiteur de fermeture (*/) pour ces commentaires C, et tout espace blanc sur la ligne est totalement transparent.

Ces commentaires de contrôle fonctionnent également dans leurs formats C++, à savoir // *INDENT-OFF* et // *INDENT-ON*.

Il convient de noter que l'état interne d'indent reste inchangé pendant la durée de la section non formatée. Ainsi, par exemple, désactiver la mise en forme au milieu d'une fonction et la reprendre après la fin de la fonction peut entraîner des résultats bizarres. Il est donc judicieux d'être quelque peu modulaire dans la sélection du code à laisser sans mise en forme.

Comme note historique, certaines versions antérieures d'indent produisaient des messages d'erreur commençant par *INDENT**. Ces versions d'indent étaient écrites pour ignorer toutes les lignes de texte d'entrée qui commençaient par de tels messages d'erreur. J'ai supprimé cette fonctionnalité incestueuse d'indent GNU.

OPTIONS DIVERSES

Pour savoir quelle version d'indent vous utilisez, utilisez la commande indent -version. Cela affichera le numéro de version d'indent, sans effectuer aucun traitement normal.

L'option ‘-v’ (ou ‘--verbose’) peut être utilisée pour activer le mode verbeux. En mode verbeux, indent signale lorsqu'il divise une ligne d'entrée en deux lignes ou plus de sortie, et donne quelques statistiques de taille à la fin.

L'option ‘-pmt’ (ou ‘--preserve-mtime’) demande à indent de préserver les heures d'accès et de modification sur les fichiers de sortie. L'utilisation de cette option a l'avantage que l'exécution d'indent sur tous les fichiers source et d'en-tête d'un projet ne déclenchera pas la reconstruction de toutes les cibles par make. Cette option n'est disponible que sur les systèmes d'exploitation qui disposent de la fonction POSIX utime(2).

BOGUES

Veuillez signaler tout bogue à bug-indent@gnu.org.

Lorsque indent est exécuté deux fois sur un fichier, avec le même profil, il ne devrait *jamais* modifier ce fichier la deuxième fois. Avec la conception actuelle d'indent, cela ne peut être garanti, et cela n'a pas été testé de manière extensive.

indent ne comprend pas le C. Dans certains cas, cela conduit à l'incapacité de joindre des lignes. Le résultat est que l'exécution d'un fichier via indent est *irréversible*, même si le fichier d'entrée utilisé était le résultat de l'exécution d'indent avec un profil donné (‘.indent.pro’).

Bien qu'une tentative ait été faite pour faire fonctionner indent pour C++, il ne fera pas un bon travail sur aucun code source C++ sauf le plus simple.

indent ne prend pas en compte l'option ‘--line-length’ donnée lorsqu'il écrit des commentaires dans le fichier de sortie. Cela résulte souvent en des commentaires placés très loin à droite. Afin d'interdire à indent de joindre une ligne brisée qui a un commentaire à la fin, assurez-vous que les commentaires commencent sur la première ligne de la rupture.

indent ne compte pas les lignes

et les commentaires (voir l’option ‘-v’) lorsque indent est désactivé avec /* *INDENT-OFF*

*/.

Les commentaires de la forme /*UPPERCASE*/ ne sont pas traités comme des commentaires mais comme un identifiant, ce qui les fait joindre à la ligne su

ivante. Cela rend les commentaires de ce type inutiles, à m
oins qu’ils ne soient intégrés dans le code dès le départ.
