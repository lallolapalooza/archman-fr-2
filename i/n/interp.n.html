Tcl qui coexistent avec l'interpréteur créateur dans la même application. L'interpréteur créateur est appelé le parent et le nouvel interpréteur est appelé un enfant. Un parent peut créer un nombre quelconque d'enfants, et chaque enfant peut lui-même créer des enfants supplémentaires dont il est le parent, résultant en une hiérarchie d'interpréteurs. Chaque interpréteur est indépendant des autres : il possède son

propre

espace de noms pour les commandes, les procédures et les variables globales. Un interpréteur parent peut créer des connexions entre ses enfants et lui-même à l'aide d'un mécanisme appelé un alias. Un alias est une commande dans un interpréteur enfant qui, lorsqu'elle est invoquée, provoque l'invocation d'une commande dans son interpréteur parent ou dans un autre interpréteur enfant. Les seules autres connexions entre interpréteurs sont via les variables d'environnement (la variable env), qui sont normalement partagées entre tous les interpréteurs de l'application, et par les rappels de dépassement de limite de ressources. Notez que l'espace de noms pour les fichiers (tels que les noms renvoyés par la commande open) n'est plus partagé entre les interpréteurs. Des commandes explicites sont fournies pour partager des fichiers et pour transférer des références à des fichiers ouverts d'un interpréteur à un

autre.

La commande interp fournit également un support pour les interpréteurs sûrs. Un interpréteur sûr est un enfant dont les fonctions ont été fortement restreintes, de sorte qu'il est sûr d'exécuter des scripts non fiables sans crainte qu'ils n'endommagent d'autres interpréteurs ou l'environnement de l'application. Par exemple, toutes les commandes de création de canaux d'E/S et les commandes de création de sous-processus sont rendues inaccessibles aux interpréteurs sûrs. Voir INTERPRÉTEURS SÛRS ci-dessous pour plus d'informations sur les fonctionnalités présentes dans un interpréteur sûr. Les fonctionnalités dangereuses ne sont pas supprimées de l'interpréteur sûr ; au lieu de cela, elles sont cachées, de sorte que seuls les interpréteurs de confiance peuvent y accéder. Pour une explication détaillée des commandes cachées, voir COMMANDES CACHÉES, ci-dessous. Le mécanisme d'alias peut être utilisé pour une communication protégée (analogue à un appel système) entre un interpréteur enfant et son parent.

child COMMAND

Pour chaque interpréteur enfant créé avec la commande interp, une nouvelle commande Tcl est créée dans l'interpréteur parent, portant le même nom que le nouvel interpréteur. Cette commande peut être utilisée pour invoquer diverses opérations sur l'interpréteur. Elle a la forme générale suivante :

enfant commande ?arg arg ...?

enfant est le nom de l'interpréteur, et commande ainsi que les arguments déterminent le comportement exact de la commande. Les formes valides de cette commande sont :

enfant alias
Retourne une liste Tcl dont les éléments sont les jetons de tous les alias dans enfant. Les jetons correspondent aux valeurs retournées lors de la création des alias (qui peuvent ne pas être les mêmes que les noms actuels des commandes).
enfant alias srcToken
Retourne une liste Tcl dont les éléments sont la targetCmd et les arguments associés à l'alias représenté par srcToken (c'est la valeur retournée lors de la création de l'alias ; il est possible que la commande source réelle dans l'enfant soit différente de srcToken).
enfant alias srcToken {}
Supprime l'alias pour srcToken dans l'interpréteur enfant. srcToken fait référence à la valeur retournée lors de la création de l'alias ; si la commande source a été renommée, la commande renommée sera supprimée.
enfant alias srcCmd targetCmd ?arg ..?
Crée un alias tel que chaque fois que srcCmd est invoquée dans enfant, targetCmd est invoquée dans le parent. Les arguments arg seront transmis à targetCmd en tant qu'arguments supplémentaires, précédant tous les arguments transmis lors de l'invocation de srcCmd. Voir INVOCATION D'ALIAS ci-dessous pour plus de détails. La commande retourne un jeton qui identifie de manière unique la commande créée srcCmd, même si la commande est renommée par la suite. Le jeton peut être égal à srcCmd, mais ce n'est pas obligatoire.
enfant bgerror ?cmdPrefix?
Cette commande récupère ou définit le gestionnaire d'exceptions en arrière-plan actuel pour l'interpréteur enfant. Si cmdPrefix est absent, le gestionnaire d'exceptions en arrière-plan actuel est retourné, et s'il est présent, c'est une liste de mots (d'une longueur minimale de un) qui décrit ce à quoi le gestionnaire d'exceptions en arrière-plan de l'interpréteur doit être défini. Voir la section GESTION DES EXCEPTIONS EN ARRIÈRE-PLAN pour plus de détails.
enfant eval arg ?arg ..?
Cette commande concatène tous les arguments arg de la même manière que la commande concat, puis évalue la chaîne résultante comme un script Tcl dans enfant. Le résultat de cette évaluation (y compris toutes les options return, telles que les informations -errorinfo et -errorcode, en cas d'erreur) est retourné à l'interpréteur appelant. Notez que le script sera exécuté dans le cadre de pile de contexte actuel de enfant ; cela permet aux implémentations (dans un interpréteur parent) des alias dans un interpréteur enfant d'exécuter des scripts dans l'enfant qui obtiennent des informations sur l'état actuel et le cadre de pile de l'enfant.

Cette commande expose la commande cachée hiddenName, la ramenant éventuellement sous un nouveau nom exposedCmdName (ce nom est actuellement accepté uniquement s'il s'agit d'un nom d'espace de noms global valide sans aucun ::), dans enfant. Si une commande exposée portant le nom ciblé existe déjà, cette commande échoue. Pour plus de détails sur les commandes cachées, voir COMMANDES CACHÉES, ci-dessous.

Cette commande masque la commande exposée exposedCmdName, la renommant en commande cachée hiddenCmdName, ou en conservant le même nom si l'argument n'est pas donné, dans l'interpréteur enfant. Si une commande cachée portant le nom ciblé existe déjà, cette commande échoue. Actuellement, ni exposedCmdName ni hiddenCmdName ne peuvent contenir de qualificateurs d'espace de noms, sinon une erreur est levée. Les commandes à cacher sont recherchées dans l'espace de noms global même si l'espace de noms actuel n'est pas le global. Cela empêche les enfants de tromper un interpréteur parent en lui faisant cacher la mauvaise commande, en faisant en sorte que l'espace de noms actuel soit différent du global. Pour plus de détails sur les commandes cachées, voir COMMANDES CACHÉES, ci-dessous.

Marque l'interpréteur enfant comme approuvé. Ne peut être invoqué que par un interpréteur approuvé. Cette commande n'expose aucune commande cachée dans l'interpréteur enfant. La commande n'a aucun effet si l'enfant est déjà approuvé.

Retourne la profondeur d'imbrication maximale autorisée pour l'interpréteur enfant. Si newlimit est spécifié, la limite de récursion dans enfant sera définie de sorte que toute imbrication de plus de newlimit appels à Tcl_Eval() et procédures associées dans enfant retournera une erreur. La valeur newlimit est également retournée. La valeur newlimit doit être un entier positif compris entre 1 et la valeur maximale d'un entier non-long sur la plateforme.

La commande définit uniquement la taille maximale de la pile d'appels Tcl. Elle ne peut pas à elle seule empêcher les dépassements de pile sur la pile C utilisée par l'application. Si votre machine a une limite sur la taille de la pile C, vous pourriez obtenir des dépassements de pile avant d'atteindre la limite définie par la commande. Si cela se produit, vérifiez s'il existe un mécanisme dans votre système pour augmenter la taille maximale de la pile C.

INTERPRÉTEURS SÛRS

Un interpréteur sûr est un interpréteur dont les fonctionnalités sont restreintes, de sorte qu'il est sûr d'exécuter un script arbitraire de votre pire ennemi sans craindre que ce script n'endommage l'application englobante ou le reste de votre environnement informatique. Pour qu'un interpréteur soit sûr, certaines commandes et variables sont supprimées de l'interpréteur. Par exemple, les commandes de création de fichiers sur disque sont supprimées, ainsi que la commande exec, car elle pourrait être utilisée pour causer des dommages via des sous-processus. Un accès limité à ces facilités peut être fourni en créant des alias vers l'interpréteur parent qui vérifient attentivement leurs arguments et fournissent un accès restreint à un sous-ensemble sûr de facilités. Par exemple, la création de fichiers pourrait être autorisée dans un sous-répertoire particulier et l'invocation de sous-processus pourrait être autorisée pour un ensemble d'programmes soigneusement sélectionnés et fixes.

Un interpréteur sûr est créé en spécifiant le commutateur -safe à la commande interp create. De plus, tout enfant créé par un interpréteur sûr sera également sûr.

INVOCATION D'ALIAS Le mécanisme d'alias a été soigneusement conçu de sorte qu'il puisse être utilisé en toute sécurité dans un script non fiable qui s'exécute dans

un

interpréteur sûr même si la cible de l'alias n'est pas un interpréteur sûr. La chose la plus importante pour garantir la sécurité est de s'assurer que les informations passées de l'enfant au parent ne sont jamais évaluées ou substituées dans le parent ; si cela se produisait, cela permettrait à un script malveillant dans l'enfant d'invoquer des fonctions arbitraires dans le parent, ce qui compromettrait la sécurité. Lorsque la source d'un alias est invoquée dans l'interpréteur enfant, les substitutions Tclhabituelles sont effectuées lors de l'analyse de cette commande. Cessubstitutions sont effectuées dans l'interpréteur source exactement comme elles le seraient pour toute autre commande invoquée dans cet interpréteur. La procédure de commande pour la commande source prend ses arguments et les fusionne avec le targetCmd et args de l'alias pour créer un nouveau tableau d' arguments. Si les mots de srcCmd étaient « srcCmd arg1 arg2 ... argN », le nouveau jeu de mots sera « targetCmd arg arg ... arg arg1 arg2 ... argN », où targetCmd et args sont les valeurs fournies lors de la création de l'alias. TargetCmd est ensuite utilisé pour localiser une procédure de commande dans l'interpréteur cible, et cette procédure de commande est invoquée avec le nouveau jeu d' arguments. Une erreur se produit s'il n'y a pas de commande nommée targetCmd dans l'interpréteur cible. Aucune substitution supplémentaire n'est effectuée sur les mots

:

la procédure de commande cible est invoquée directement, sans passer par le mécanisme d'évaluation Tcl normal. Les substitutions sont ainsi effectuées sur chaque mot exactement une fois : targ

etCmd et args ont été substitués lors de l'analyse de la commande qui a créé l'alias, e
t arg1 - argN sont substitués lorsque la commande source de l'alias est analysée dans l'

interpréteu

r

source. Lors de l'écriture des targetCmds pour les alias dans les interpréteurs sûrs, il est très important que les arguments de cette commande ne soient jamais évalués ou substitués, car cela fournirait un mécanisme d'évasion par lequel l'interpréteur enfant pourrait exécuter du code arbitraire dans le parent. Cela compromettrait à son tour la sécurité du système. COMMANDES CACHÉES Les interpréteurs sûrs restreignent fortement la fonctionnalité disponible pour les programmes Tcl qui s'exécutent en leur sein. Permettre au programme Tcl non fiable d' avoir un accès direct à cette fonctionnalité est dangereux, car elle peut être utilisée pour une variété d'attaques sur l'environnement. Cependant, il y a des moments où il y a un besoin légitime d'utiliser la

fonctionnalité

dangereuse dans le contexte de l'interpréteur sûr. Par exemple, parfois un programme doit être sourcé dans l'interpréteur. Un autre exemple est Tk, où les fenêtres sont liées à la hiérarchie des fenêtres pour un interpréteur spécifique ; certaines fonctions potentiellement dangereuses, par ex. la gestion des fenêtres, doivent être effectuées sur ces fenêtres dans le contexte de l'interpréteur. La commande interp fournit une solution à ce problème sous la forme de commandes cachées. Au lieu de supprimer complètement les commandes dangereuses d'un interpréteur sûr, ces commandes sont cachées pour qu'elles deviennent indisponibles pour les scripts Tcl s'exécutant

dans

l'interpréteur. Cependant, de telles commandes cachées peuvent être invoquées par tout ancêtre fiable de l'interpréteur sûr, dans le contexte de l'interpréteur sûr, en utilisant interp invoke. Les commandes cachées et les commandes exposées résident dans des espaces de noms séparés. Il est possible de définir une commande cachée et une commande exposée portant le même nom au sein d'un même interpréteur. Les commandes cachées dans un interpréteur enfant peuvent être invoquées dans le corps des procédures appelées dans le parent lors de l'invocation d'un alias. Par exemple, un alias pour source dans l'interpréteur enfant pour réellement sourcer le contenu du fichier. Notez que deux commandes nommées source existent

dans

l'interpréteur enfant : l'alias, et la commande cachée. Parce qu'un interpréteur parent peut invoquer une commande cachée dans le cadre du traitement d'une invocation d'alias, une grande prudence doit être prise pour éviter d'évaluer les arguments passés via l'invocation d'alias. Sinon, des interpréteurs enfants malveillants pourraient amener un interpréteur parent fiable à exécuter des commandes dangereuses en leur nom. Voir la section sur INVOCATION D'ALIAS pour une discussion plus complète de ce sujet. Pour aider à éviter ce problème, aucune substitution ni évaluation

n'est

appliquée aux arguments de interp invokehidden. Les interpréteurs sûrs ne sont pas autorisés à invoquer des commandes cachées en eux-mêmes ou chez leurs descendants. Cela les empêche d'obtenir l'accès à des

fonctionnalités

cachées en eux-mêmes ou chez leurs descendants. L'ensemble des commandes cachées dans un interpréteur peut être manipulé par un interpréteur fiable en utilisant interp expose et interp hide. La commande interp expose déplace une commande cachée vers l'ensemble des commandes exposées dans l'interpréteur identifié par path, potentiellement en renommant la commande au passage. Si une commande exposée portant le nom cible existe déjà, l'opération échoue. De même, interp hide déplace une commande exposée vers l'ensemble des commandes cachées dans cet interpréteur. Les interpréteurs sûrs ne sont pas autorisés à déplacer des commandes entre l'ensemble des commandes cachées et

exposées,

ni en eux-mêmes ni chez leurs descendants. Actuellement, les noms des commandes cachées ne peuvent pas contenir de qualificateurs de namespace, et vous devez d'abord renommer une commande dans un namespace vers le namespace global avant de pouvoir la cacher. Les commandes à cacher par interp hide sont recherchées dans le namespace global même si le namespace actuel n'e

st pas le global. Cela empêche les enfants de tromper un interpréteur
parent pour qu'il cache la mauvaise commande, en faisant que le namespace

actuel soit

différent

du global. LIMITES DE RESSOURCES Chaque interpréteur a deux types de limites de ressources qui peuvent être imposées par n'importe quel interpréteur parent à ses enfants. GESTION DES EXCEPTIONS EN

ARRIÈRE-PLAN

Lorsqu'une exception se produit dans une situation où elle ne peut pas être signalée directement dans la pile (par exemple lors du traitement d'événements dans un appel update ou vwait), l'exception est plutôt signalée par le mécanisme de gestion des exceptions en arrière-plan. Chaque interpréteur a un gestionnaire d'exceptions en arrière-plan enregistré ; le gestionnaire d'exceptions par défaut fait en sorte que la commande bgerror dans l'espace de noms global de l'interpréteur soit appelée, mais d'autres gestionnaires d'exceptions peuvent être installés et traiter les exceptions en arrière-plan de manière substantiellement

différente.

Un gestionnaire d'exceptions en arrière-plan se compose d'une liste non vide de mots à laquelle seront ajoutés deux autres mots au moment de l'invocation. Le premier mot sera le résultat de l'interpréteur au moment de l'exception, généralement un message d'erreur, et le second sera le dictionnaire des options de retour au moment de l'exception. Ce sont les mêmes valeurs que catch peut capturer lorsqu'il contrôle l'évaluation d'un script dans une situation non arrière-plan. La liste résultante se

ra ensuite exécutée dans l'espace de noms global de l'inter
préteur sans qu'aucune autre substitution ne soit effectuée.
