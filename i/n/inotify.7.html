NOTE

S

Les descripteurs de fichier inotify peuvent être surveillés en utilisant select(2), poll(2), et epoll(7). Lorsqu'un événement est disponible, le descripteur de fichier indique qu'il est

lisible.

Depuis Linux 2.6.25, la notification d'E/S pilotée par signal est disponible pour les descripteurs de fichier inotify ; voir la discussion de F_SETFL (pour définir le drapeau O_ASYNC), F_SETOWN, et F_SETSIG dans fcntl(2). La structure siginfo_t (décrite dans sigaction(2)) qui est passée au gestionnaire de signal a les champs suivants définis : si_fd est défini au numéro du descripteur de fichier inotify ; si_signo est défini au numéro du signal ; si_code est défini à POLL_IN ; et POLLIN est défini dans si_band

.

Si les sorties successives d'événements inotify produites sur le descripteur de fichier inotify sont identiques (même wd, mask, cookie, et name), tlorsqu'elles sont fusionnées en un seul événement si l'événement le plus ancien n'a pas encore été lu (mais voir BUGS). Cela réduit la quantité de mémoire du noyau requise pour la file d'événements, mais signifie aussi qu'une application ne peut pas utiliser inotify pour compter de manière fiable les événements de

fichiers.

Les événements renvoyés par la lecture depuis un descripteur de fichier inotify forment une file ordonnée. Ainsi, par exemple, il est garanti que lors d'un renommage d'un répertoire vers un autre, des événements seront produits dans le bon ordre sur le descripteur de fichier

inotify.

L'ensemble des descripteurs de surveillance qui est surveillé via un descripteur de fichier inotify peut être consulté via l'entrée pour le descripteur de fichier inotify dans le /proc/pid/fdinfo du processus. Voir proc(5) pour plus de détails. Le FIONREAD ioctl(2) renvoie le nombre d'octets disponibles à lire depuis un descripteur de fichier

inotify.

Limitations et

réserves

L'API inotify ne fournit aucune information sur l'utilisateur ou le processus qui a déclenché l'événement inotify. En particulier, il n'y a pas de moyen simple pour un processus qui surveille des événements via inotify de distinguer les événements qu'il déclenche lui-même de ceux qui sont déclenchés par d'autres

processus.

Inotify ne signale que les événements déclenchés par un programme en espace utilisateur via l'API du système de fichiers. En conséquence, il ne capte pas les événements distants qui se produisent sur les systèmes de fichiers réseau. (Les applications doivent se rabattre sur l'interrogation du système de fichiers pour capter de tels événements.) De plus, divers pseudo-systèmes de fichiers tels que /proc, /sys, et /dev/pts ne sont pas surveillables avec

inotify.

L'API inotify ne signale pas les accès et modifications de fichiers qui peuvent survenir à cause de mmap(2), msync(2), et munmap(

2).

L'API inotify identifie les fichiers affectés par leur nom de fichier. Cependant, au moment où une application traite un événement inotify, le nom de fichier a peut-être déjà été supprimé ou

renommé.

L'API inotify identifie les événements via des descripteurs de surveillance. Il est de la responsabilité de l'application de mettre en cache une correspondance (si une est nécessaire) entre les descripteurs de surveillance et les chemins d'accès. Sachez que les renommages de répertoires peuvent affecter plusieurs chemins d'accès mis en

cache.

La surveillance inotify des répertoires n'est pas récursive : pour surveiller les sous-répertoires d'un répertoire, des surveillances supplémentaires doivent être créées. Cela peut prendre un temps considérable pour de grands arbres de

répertoires.

Si vous surveillez une arborescence de répertoires entière, et qu'un nouveau sous-répertoire est créé dans cette arborescence ou qu'un répertoire existant est renommé dans cette arborescence, sachez qu'au moment où vous créez une surveillance pour le nouveau sous-répertoire, de nouveaux fichiers (et sous-répertoires) peuvent déjà exister à l'intérieur du sous-répertoire. Par conséquent, vous voudrez peut-être parcourir le contenu du sous-répertoire immédiatement après l'ajout de la surveillance (et, si vous le souhaitez, ajouter récursivement des surveillances pour tous les sous-répertoires qu'il contient)

.

Notez que la file d'événements peut déborder. Dans ce cas, des événements sont perdus. Les applications robustes devraient gérer gracieusement la possibilité d'événements perdus. Par exemple, il peut être nécessaire de reconstruire une partie ou la totalité du cache de l'application. (Une approche simple, mais potentiellement coûteuse, est de fermer le descripteur de fichier inotify, de vider le cache, de créer un nouveau descripteur de fichier inotify, puis de recréer les surveillances et les entrées de cache pour les objets à surveiller.

)

Si un système de fichiers est monté au-dessus d'un répertoire surveillé, aucun événement n'est généré, et aucun

événement n'est généré pour les objets immédiatement sous le nouveau point de montage. Si le système de fichi
ers est ensuite démonté, des événements seront ensuite générés pour le répertoire et les objets qu'il contient.

Gestion des événements

rename()

Comme noté ci-dessus, la paire d'événements IN_MOVED_FROM et IN_MOVED_TO générée par rename(2) peut être appariée via leur valeur de cookie partagée. Cependant, la tâche d'appariement présente certaines

difficultés.

Ces deux événements sont généralement consécutifs dans le flux d'événements disponible lors de la lecture depuis le descripteur de fichier inotify. Cependant, ce n'est pas garanti. Si plusieurs processus déclenchent des événements pour des objets surveillés, alors (rarement) un nombre arbitraire d'autres événements peuvent apparaître entre les événements IN_MOVED_FROM et IN_MOVED_TO. De plus, il n'est pas garanti que la paire d'événements soit insérée atomiquement dans la file : il peut y avoir un bref intervalle où le IN_MOVED_FROM est apparu, mais le IN_MOVED_TO

non.

Apparier la paire d'événements IN_MOVED_FROM et IN_MOVED_TO générée par rename(2) est donc intrinsèquement sujette à des conditions de course. (N'oubliez pas que si un objet est renommé en dehors d'un répertoire surveillé, il peut ne même pas y avoir d'événement IN_MOVED_TO.) Des approches heuristiques (par ex., supposer que les événements sont toujours consécutifs) peuvent être utilisées pour assurer un appariement dans la plupart des cas, mais manqueront inévitablement certains cas, amenant l'application à percevoir les événements IN_MOVED_FROM et IN_MOVED_TO comme non liés. Si les descripteurs de surveillance sont détruits et recréés en conséquence, alors ces descripteurs de surveillance seront incohérents avec les descripteurs de surveillance dans tout événement en attente. (Recréer le descripteur de fichier inotify et reconstruire le cache peut être utile pour gérer ce scénario.

)

Les applications devraient également prévoir la possibilité que l'événement IN_MOVED_FROM ait été le dernier événement qui pouvait tenir dans le buffer renvoyé par l'appel courant à read(2), et que l'événement IN_MOVED_TO accompagnant ne soit récupéré que lors du prochain read(2), ce qui devrait être fait avec un délai d'attente (court) pour tenir compte du fait que l'insertion de la paire d'événements IN_MOVED_FROM+IN_MOVED_TO n'est pas atomique, et aussi de la possibilité qu'il n'y ait pas d'événement IN_MO

BUG

Avant Linux 3.19, fallocate(2) ne créait aucun événement inotify. Depuis Linux 3.19, les appels à fallocate(2) génèrent des événements IN

_MODIFY.

Avant Linux 2.6.16, le drapeau de masque IN_ONESHOT ne fonctionne

pas.

Tel que conçu et implémenté à l'origine, le drapeau IN_ONESHOT ne provoquait pas la génération d'un événement IN_IGNORED lorsque la surveillance était abandonnée après un événement. Cependant, comme effet non voulu d'autres changements, depuis Linux 2.6.36, un événement IN_IGNORED est généré dans ce

cas.

Avant Linux 2.6.25, le code du noyau destiné à fusionner des événements identiques successifs (c'est-à-dire que les deux événements les plus récents pouvaient potentiellement être fusionnés si le plus ancien n'avait pas encore été lu) vérifiait à la place si l'événement le plus récent pouvait être fusionné avec l' événement non lu le plus

ancien.

Lorsqu'un descripteur de surveillance est supprimé en appelant inotify_rm_watch(2) (ou parce qu'un fichier de surveillance est supprimé ou le système de fichiers qui le contient est démonté), tout événement en attente non lu pour ce descripteur de surveillance reste disponible à la lecture. Comme les descripteurs de surveillance sont ensuite alloués avec inotify_add_watch(2), le noyau parcourt la plage de descripteurs de surveillance possibles (1 à INT_MAX) de manière incrémentale. Lors de l'allocation d'un descripteur de surveillance libre, aucune vérification n'est faite pour voir si ce numéro de descripteur de surveillance a des événements en attente non lus dans la file inotify. Ainsi, il peut arriver qu'un descripteur de surveillance soit réalloué même si des événements en attente non lus existent pour une incarnation précédente de ce numéro de descripteur de surveillance, avec pour résultat que l'application pourrait alors lire ces événements et les interpréter comme appartenant au fichier associé au descripteur de surveillance nouvellement recyclé. En pratique, la probabilité de rencontrer ce bug peut être extrêmement faible, car cela nécessite qu'une application parcoure INT_MAX descripteurs de surveillance, libère un descripteur de surveillance tout en laissant des événements non lus pour ce descripteur de surveillance dans la file, et recycle ensuite ce descripteur de sur

veillance. Pour cette raison, et parce qu'il n'y a eu aucun rapport de ce bug survenant dans des applica
tions réelles, à Linux 3.15, aucun changement du noyau n'a encore été fait pour éliminer ce bug possible.

DESCRIPTION

The inotify subsystem of the Linux kernel provides an interface that allows applications to monitor filesystem events. These events can include actions such as opening, closing, modifying, moving, or deleting files or directories.

To use inotify, an application first creates an inotify file descriptor using inotify_init(2) or inotify_init1(2). This file descriptor is then used to add "watches" on specific files or directories using inotify_add_watch(2). Each watch is associated with a unique watch descriptor (wd).

When an event occurs on a watched file or directory, the kernel generates an inotify event. These events are queued on the inotify file descriptor. An application can then read these events from the file descriptor. Each event is represented by a structure of type struct inotify_event, followed by the filename if the event is associated with a file within a watched directory.

The inotify_rm_watch(2) system call is used to remove watches.

The inotify interface is suitable for implementing features such as file synchronization tools, backup utilities, or real-time file indexers.

Note that inotify does not generate events for all filesystem operations. For example, it does not report access times (atime) changes. For more comprehensive filesystem monitoring, especially for network filesystems or broader system-wide monitoring, consider alternatives like fanotify.

STANDARDS

This is a Linux-specific API and is not part of any C programming standard.

HISTORY

The inotify API was introduced in Linux kernel 2.6.13.

NOTES

The inotify_init1(2) function allows setting the O_CLOEXEC and O_NONBLOCK flags at creation time, which is generally preferred over using fcntl(2) afterwards.

The maximum number of inotify watches per user is controlled by the kernel parameter /proc file as root.

When watching a directory, inotify can generate events for file operations within that directory. The name field in the inotify_event structure will contain the name of the file or subdirectory that caused the event. If the event occurs on the watched directory itself (e.g., deletion of the directory), the name field will be empty.

The total size of events read from the inotify file descriptor can be larger than the size of a single inotify_event structure, as multiple events might be coalesced into a single read operation. The inotify_event structure is followed by the filename, if present. The size of the name is given by the len field. The events in the buffer are arranged sequentially, with padding to ensure proper alignment.

The mask of events reported by inotify can be filtered using flags passed to inotify_add_watch(2). Common flags include IN_CREATE (a file/directory was created), IN_DELETE (a file/directory was deleted), IN_MODIFY (a file was modified), IN_MOVED_FROM (a file/directory was moved out of the watched directory), IN_MOVED_TO (a file/directory was moved into the watched directory), IN_CLOSE_WRITE (a file opened for writing was closed), and IN_CLOSE_NOWRITE (a file not opened for writing was closed).

Recursive watching of directories is not supported directly by inotify. Applications typically need to implement this by iterating through subdirectories and adding watches for each one, and also handling IN_CREATE and IN_DELETE events to dynamically add/remove watches as directories are created/deleted.

Resource limits: Ensure that the system has enough resources (memory, file descriptors) to handle the desired number of watches. Consider using poll(2) or epoll(7) to efficiently wait for events on the inotify file descriptor without blocking.

Example code demonstrating inotify usage:

#include <sys/inotify.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <poll.h>

#define BUF_LEN (10 * (sizeof(struct inotify_event) + 16))

static void
handle_events(int fd, int *wd, int argc, char **argv)
{
    /* Some space for reading event data. */
    char buf[BUF_LEN];
    /* Pointer to the current event's location within the buffer. */
    const struct inotify_event *event;
    ssize_t len = read(fd, buf, BUF_LEN);
    /* If the length is less than 1, ignore. */
    if (len <= 0)
        return;
    /* Loop over all events in the buffer.  */
    for (char *ptr = buf; ptr < buf + len;
            ptr += sizeof(struct inotify_event) + event->len) {
        event = (const struct inotify_event *) ptr;
        /* Print event type.  */
        if (event->mask & IN_OPEN)
            printf("IN_OPEN: ");
        if (event->mask & IN_CLOSE_NOWRITE)
            printf("IN_CLOSE_NOWRITE: ");
        if (event->mask & IN_CLOSE_WRITE)
            printf("IN_CLOSE_WRITE: ");
        /* Print the name of the watched directory.  */
        for (size_t i = 1; i < argc; ++i) {
            if (wd[i] == event->wd) {
                printf("%s/", argv[i]);
                break;
            }
        }
        /* Print the name of the file.  */
        if (event->len)
            printf("%s", event->name);
        /* Print type of filesystem object.  */
        if (event->mask & IN_ISDIR)
            printf(" [directory]\n");
        else
            printf(" [file]\n");
    }
}

int
main(int argc, char* argv[])
{
    char buf;
    int fd, i, poll_num;
    int *wd;
    nfds_t nfds;
    struct pollfd fds[2];
    if (argc < 2) {
        printf("Usage: %s PATH [PATH ...]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    printf("Press ENTER key to terminate.\n");
    /* Create the file descriptor for accessing the inotify API.  */
    fd = inotify_init1(IN_NONBLOCK);
    if (fd == -1) {
        perror("inotify_init1");
        exit(EXIT_FAILURE);
    }
    /* Allocate memory for watch descriptors.  */
    wd = calloc(argc, sizeof(int));
    if (wd == NULL) {
        perror("calloc");
        exit(EXIT_FAILURE);
    }
    /* Mark directories for events
       - file was opened
       - file was closed */
    for (i = 1; i < argc; i++) {
        wd[i] = inotify_add_watch(fd, argv[i],
                                  IN_OPEN | IN_CLOSE);
        if (wd[i] == -1) {
            fprintf(stderr, "Cannot watch '%s': %s\n",
                    argv[i], strerror(errno));
            exit(EXIT_FAILURE);
        }
    }
    /* Prepare for polling.  */
    nfds = 2;
    fds[0].fd = STDIN_FILENO;       /* Console input */
    fds[0].events = POLLIN;
    fds[1].fd = fd;                 /* Inotify input */
    fds[1].events = POLLIN;
    /* Wait for events and/or terminal input.  */
    printf("Listening for events.\n");
    while (1) {
        poll_num = poll(fds, nfds, -1);
        if (poll_num == -1) {
            if (errno == EINTR)
                continue;
            perror("poll");
            exit(EXIT_FAILURE);
        }
        if (poll_num > 0) {
            if (fds[0].revents & POLLIN) {
                /* Console input is available.  Empty stdin and quit.  */
                while (read(STDIN_FILENO, &buf, 1) > 0 && buf != '\n')
                    continue;
                break;
            }
            if (fds[1].revents & POLLIN) {
                /* Inotify events are available.  */
                handle_events(fd, wd, argc, argv);
            }
        }
    }
    printf("Listening for events stopped.\n");
    /* Close inotify file descriptor.  */
    close(fd);
    free(wd);
    exit(EXIT_SUCCESS);
}

BUGS

The inotify API does not provide a way to distinguish between accesses to a file within a watched directory and accesses to the directory itself. A separate watch is needed for the directory itself. Also, the events IN_ATTRIB, IN_MODIFY, IN_CLOSE_WRITE, and IN_CLOSE_NOWRITE may be generated for any file or directory within the watched directory, and the event reported does not specify which file was affected unless it is a rename operation.

There is no mechanism for recursive watching. If you need to watch a directory tree recursively, you must add watches for each subdirectory explicitly and handle the creation and deletion of subdirectories yourself.

inotify does not distinguish between accesses by different processes. For example, if multiple processes write to the same file, inotify will report a single IN_MODIFY event when the file is closed.

EXAMPLES

The example code provided in the NOTES section demonstrates how to set up inotify watches, poll for events, and handle them.

A simple command-line tool using inotify could look like this:

#!/bin/bash
# simple_inotify_watch.sh

if [ -z "$1" ]; then
  echo "Usage: $0 DIRECTORY"
  exit 1
fi

DIR="$1"
inotifywait -m -r -e modify,create,delete,move "$DIR"

This script uses the inotifywait utility (which itself uses the inotify API) to monitor events recursively (-r) in the specified directory (-m for monitor mode, which keeps running). The events being watched are modify, create, delete, and move.
