DESCRIPTIO

N

La construction fondamentale dans [incr Tcl] est la définition de extendedclass. Chaque extendedclass sert de modèle pour les objets réels qui peuvent être créés. La extendedclass elle-même est un espace de noms qui contient les éléments communs à tous les objets. Chaque objet possède son propre ensemble unique de données contenant les instances des « variables » définies dans la définition de la extendedclass. Chaque objet possède également une variable intégrée nommée « this », qui contient le nom de l'objet. Les extendedclasses peuvent également avoir des membres de données « communs » partagés par tous les objets d'une

extendedclass.

Deux types de fonctions peuvent être incluses dans la définition de la extendedclass. Les « méthodes » sont des fonctions qui opèrent sur un objet spécifique et ont donc accès aux « variables » ainsi qu'aux membres de données « communs ». Les « procs » sont des procédures ordinaires dans l'espace de noms de la extendedclass et n'ont accès qu'aux membres de données « communs »

.

Si le corps d'une méthode ou d'une proc commence par «@ », il est traité comme le nom symbolique d'une procédure C. Sinon, il est traité comme un script de code Tcl. Voir ci-dessous pour les détails sur l'enregistrement et l'utilisation des procédures

C.

Une extendedclass ne peut être définie qu'une seule fois, bien que les corps des méthodes et des procs de la extendedclass puissent être définis encore et encore pour le débogage interactif. Voir les commandes body et configbody pour les

détails.

Chaque espace de noms peut avoir sa propre collection d'objets et de extendedclasses. La liste des extendedclasses disponibles dans le contexte courant peut être interrogée à l'aide de la commande «itcl::find extendedclasses », et la liste des objets, avec la commande «itcl::find objects »

.

Une extendedclass peut être supprimée à l'aide de la commande «delete extendedclass ». Les objets individuels peuvent être supprimés à l'aide de la commande «delete o

bjec
t ».

L'ordre des noms baseExtendedclass dans la liste inherit affecte la résolution des noms des membres de la extendedclass. Lorsque le même nom de membre apparaît dans deux ou plusieurs extendedclasses de base, la extendedclass de base qui apparaît en premier dans la liste inherit a la priorité. UTILISATION

Une fois qu'une classe étendue a été définie, le nom de la classe étendue peut être utilisé comme une commande pour créer de nouveaux objets appartenant à la classe

étendue.

Celle-ci passe à son tour les arguments aux constructeurs des classes étendues de base avant d'invoquer son propre corps de commandes. MÉTHODES/PROCÉDURES DE

CHAÎNAGE

Parfois, une classe de base possède une méthode ou une procédure qui est redéfinie avec le même nom dans une classe dérivée. C'est une manière de faire en sorte que la classe dérivée gère les mêmes opérations que la classe de base, mais avec son propre comportement spécialisé. Par exemple, supposons que nous ayons une classe Toaster qui ressemble à ceci

: 
itcl::extendedclass Toaster {
    variable crumbs 0
    method toast {nslices} {
        if {$crumbs > 50} {
            error "== FIRE! FIRE! =="
        }
        set crumbs [expr {$crumbs+4*$nslices}]
    }
    method clean {} {
        set crumbs 0
    }
}

Nous pourrions créer une autre classe comme SmartToaster qui redéfinit la méthode "toast". Si nous voulons accéder à la méthode de la classe de base, nous pouvons la qualifier avec le nom de la classe de base, pour éviter l'ambiguïté

: 
itcl::extendedclass SmartToaster {
    inherit Toaster
    method toast {nslices} {
        if {$crumbs > 40} {
            clean
        }
        return [Toaster::toast $nslices]
    }
}

Au lieu de coder en dur le nom de la classe de base, nous pouvons utiliser la commande "chain" comme ceci

: 
itcl::extendedclass SmartToaster {
    inherit Toaster
    method toast {nslices} {
        if {$crumbs > 40} {
            clean
        }
        return [chain $nslices]
    }
}

La commande chain recherche dans la hiérarchie des classes une implémentation légèrement plus générique (classe de base) d'une méthode ou d'une procédure, e

t l'invoque avec les arguments spécifiés. Elle commence par le contexte de la classe courante et recherche dans les classes de base dans l'ordre dans leque
l elles sont rapportées par la commande "info heritage". Si une autre implémentation n'est pas trouvée, cette commande ne fait rien et retourne la chaîne nulle.

CHARGEMENT

AUTOMATIQUE

Les définitions de classes n'ont pas besoin d'être chargées explicitement ; elles peuvent être chargées au besoin par la mécanisme habituel de chargement automatique de Tcl. Chaque répertoire contenant des fichiers de définition de classes doit avoir un fichier "tclIndex" associé. Chaque ligne dans ce fichier identifie une procédure Tcl ou une définition de classe [incr Tcl] et le fichier où la définition peut être

trouvée.

Par exemple, supposons qu'un répertoire contienne les définitions pour les classes "Toaster" et "SmartToaster". Alors le fichier "tclIndex" pour ce répertoire ressemblerait à

: 
# Tcl autoload index file, version 2.0 for [incr Tcl]
# This file is generated by the "auto_mkindex" command
# and sourced to set up indexing information for on
e or # more commands. Typically each line is a command that # sets an element in the auto_index array, where the # element name is the name of a command and the
value is # a script that loads the command. set auto_index(::Toaster) "source $dir/Toaster.itcl" set auto_index(::SmartToaster) "source $dir/SmartToaster.itcl"

La commande auto_mkindex est utilisée pour générer automatiquement les fichiers

"tclIndex".

Le chargeur automatique doit être informé de ce répertoire en ajoutant le nom du r

épertoire à la variable "auto_path". Une fois cela en place, les classes seront ch
argées automatiquement au besoin lorsqu'elles sont utilisées dans une application.

PROCÉDURES

C

Les procédures C peuvent être intégrées dans une définition de classe [incr Tcl] pour implémenter des méthodes, des procédures et le code "config" pour les variables publiques. Tout corps qui commence par "@" est traité comme le nom symbolique d'une procédure

C.

Les noms symboliques sont établis en enregistrant des procédures via Itcl_RegisterC(). Cela se fait généralement dans la procédure Tcl_AppInit(), qui est automatiquement appelée lorsque l'interpréteur démarre. Dans l'exemple suivant, la procédure My_FooCmd() est enregistrée avec le nom symbolique "foo". Cette procédure peut être référencée dans la commande body comme

"@foo". 
int
Tcl_AppInit(interp)
    Tcl_Interp *interp;     /* Interpreter for application. */
{
    if (Itcl_Init(interp) == TCL_ERROR) {
        return TCL_ERROR;
    }
    if (Itcl_RegisterC(interp, "foo", My_FooCmd) != TCL_OK) {
        return TCL_ERROR;
    }
}

Les procédures C sont implémentées exactement comme des commandes Tcl ordinaires. Voir la page de manuel CrtCommand pour plus de détails. Au sein de la procédure, les membres de données de la classe peuvent être accédés comme des variables ordinaires en utilisant Tcl_SetVar(), Tcl_GetVar(), Tcl_TraceVar(), etc. Les méthodes et procédures de la classe peuvent être exécutées comme des commandes ordinaires en utilisant Tcl_Eval(). [incr Tcl] rend cela possible en configurant automatiquement le contexte avant d'exécuter la procédure

C.

Ce schéma fournit un chemin de migration naturel pour le développement de code. Les classes peuvent être développées rap

idement en utilisant du code Tcl pour implémenter les corps. Une application entière peut être construite et testée. Lors
que c'est nécessaire, des corps individuels peuvent être implémentés avec du code C pour améliorer les performances.
