Paquet: tcl

widget(n) [incr Tcl] widget(n)

NOM

itcl::widget - créer une classe de widgets d'objets

AVERTISSEMENT!

Il s'agit d'une nouvelle fonctionnalité dans [incr Tcl] où l'API peut encore changer !!

SYNOPSIS

itcl::widget nomWidget {
    inherit widgetBase ?widgetBase...?
    constructor args ?init? corps
    destructor corps
    public method nom ?args? ?corps?
    protected method nom ?args? ?corps?
    private method nom ?args? ?corps?
    public proc nom ?args? ?corps?
    protected proc nom ?args? ?corps?
    private proc nom ?args? ?corps?
    public variable nomVar ?init? ?config?
    protected variable nomVar ?init? ?config?
    private variable nomVar ?init? ?config?
    public common nomVar ?init?
    protected common nomVar ?init?
    private common nomVar ?init?
    public commande ?arg arg ...?
    protected commande ?arg arg ...?
    private commande ?arg arg ...?
    <informations de délégation> voir page de délégation
    <informations d'option> voir page d'option
    set nomVar ?valeur?
    array option ?arg arg ...?
}
nomWidget nomObjet ?arg arg ...?
nomObjet méthode ?arg arg ...?
nomWidget::proc ?arg arg ...?

DESCRIPTION

L'une des constructions fondamentales de [incr Tcl] est la définition de widget. Un widget est comme une classe avec des fonctionnalités supplémentaires. Chaque widget agit comme un modèle pour les objets réels qui peuvent être créés. Le widget lui-même est un espace de noms qui contient les éléments communs à tous les objets. Chaque objet possède son propre ensemble de données unique contenant les instances des "variables" définies dans la définition du widget. Chaque objet possède également une variable intégrée nommée "this", qui contient le nom de l'objet. Les widgets peuvent également avoir des membres de données "communs" qui sont partagés par tous les objets d'un widget.

Deux types de fonctions peuvent être inclus dans la définition du widget. Les "méthodes" sont des fonctions qui opèrent sur un objet spécifique et ont donc accès aux "variables" et aux membres de données "communs". Les "procs" sont des procédures ordinaires dans l'espace de noms du widget et n'ont accès qu'aux membres de données "communs".

Si le corps de toute méthode ou proc commence par "@", il est traité comme le nom symbolique d'une procédure C. Sinon, il est traité comme un script de code Tcl. Voir ci-dessous pour les détails sur l'enregistrement et l'utilisation des procédures C.

Un widget ne peut être défini qu'une seule fois, bien que les corps des méthodes et procs de widget puissent être définis encore et encore pour le débogage interactif. Voir les commandes body et configbody pour plus de détails.

Chaque espace de noms peut avoir sa propre collection d'objets et de widgets. La liste des widgets disponibles dans le contexte actuel peut être interrogée à l'aide de la commande "itcl::find widgets", et la liste des objets, avec la commande "itcl::find objects".

Un widget peut être supprimé à l'aide de la commande "delete widget". Les objets individuels peuvent être supprimés à l'aide de la commande "delete object".

DÉFINITIONS DE WIDGET

widget nomWidget définition
Fournit la définition d'un widget nommé nomWidget. Si le widget nomWidget existe déjà, ou si une commande nommée nomWidget existe dans le contexte de l'espace de noms actuel, cette commande renvoie une erreur. Si la définition du widget est analysée avec succès, nomWidget devient une commande dans le contexte actuel, gérant la création d'objets pour ce widget.

La définition du widget est évaluée comme une série d'instructions Tcl qui définissent des éléments au sein du widget. Les commandes de définition de widget suivantes sont reconnues :

inherit widgetBase ?widgetBase...?
Fait hériter le widget actuel des caractéristiques d'un ou plusieurs widgets de base. Les widgets doivent avoir été définis par une commande widget précédente, ou doivent être disponibles pour le mécanisme de chargement automatique (voir "CHARGEMENT AUTOMATIQUE" ci-dessous). Une seule définition de widget ne peut contenir qu'une seule commande inherit.

L'ordre des noms widgetBase dans la liste inherit affecte la résolution des noms pour les membres du widget. Lorsque le même nom de membre apparaît dans deux widgets de base ou plus, le widget de base qui apparaît en premier dans la liste inherit a la priorité. Par exemple, si les widgets "Foo" et "Bar" contiennent tous deux le membre "x", et si un autre widget a l'instruction "inherit" :

inherit Foo Bar

alors le nom "x" signifie "Foo::x". Les autres membres hérités nommés "x" doivent être référencés avec leur nom explicite, comme "Bar::x".

constructor args ?init? corps
Déclare la liste d'arguments args et le corps utilisés pour le constructeur, qui est automatiquement invoqué chaque fois qu'un objet est créé.

Avant que le corps ne soit exécuté, l'instruction optionnelle init est utilisée pour invoquer les constructeurs de widgets de base qui nécessitent des arguments. Les variables dans la spécification args peuvent être accédées dans le fragment de code init et passées aux constructeurs de widgets de base. Après avoir évalué l'instruction init, tous les constructeurs de widgets de base qui n'ont pas été exécutés sont invoqués automatiquement sans arguments. Cela garantit que tous les widgets de base sont entièrement construits avant que le corps du constructeur ne soit exécuté. Par défaut, ce mécanisme fait appeler les constructeurs dans l'ordre du moins spécifique au plus spécifique. C'est exactement l'inverse de l'ordre dans lequel les widgets sont signalés par la commande info heritage.

Si la construction réussit, le constructeur renvoie toujours le nom de l'objet - indépendamment de la façon dont le corps est défini - et le nom de l'objet devient une commande dans le contexte de l'espace de noms actuel. Si la construction échoue, un message d'erreur est renvoyé.

destructor corps
Déclare le corps utilisé pour le destructeur, qui est automatiquement invoqué lorsqu'un objet est supprimé. Si le destructeur réussit, les données de l'objet sont détruites et le nom de l'objet est supprimé en tant que commande de l'interpréteur. Si la destruction échoue, un message d'erreur est renvoyé et l'objet reste.

Lorsqu'un objet est détruit, tous les destructeurs de sa hiérarchie de widgets sont invoqués dans l'ordre du plus spécifique au moins spécifique. C'est l'ordre dans lequel les widgets sont signalés par la commande "info heritage", et c'est exactement l'inverse de l'ordre par défaut des constructeurs.

method nom ?args? ?corps?
Déclare une méthode nommée nom. Lorsque le corps de la méthode est exécuté, il aura un accès automatique aux variables spécifiques à l'objet et aux membres de données communs.

Si la liste args est spécifiée, elle établit les informations d'utilisation pour cette méthode. La commande body peut être utilisée pour redéfinir le corps de la méthode, mais la liste args doit correspondre à cette spécification.

Dans le corps d'une autre méthode de widget, une méthode peut être invoquée comme toute autre commande - simplement en utilisant son nom. En dehors du contexte du widget, le nom de la méthode doit être précédé du nom d'un objet, ce qui fournit le contexte des données qu'il manipule. Les méthodes d'un widget de base qui sont redéfinies dans le widget actuel, ou masquées par un autre widget de base, peuvent être qualifiées en utilisant la syntaxe "nomWidget::méthode".

proc nom ?args? ?corps?
Déclare une procédure nommée nom. Une procédure est une procédure ordinaire au sein de l'espace de noms du wid

Contrairement à une méthode, un proc est invoqué sans faire référence à un objet spécifique. Lorsque le corps du proc est exécuté, il n'a un accès automatique qu'aux données communes.

Si la liste args est spécifiée, elle établit les informations d'utilisation pour ce proc. La commande body peut être utilisée pour redéfinir le corps du proc, mais la liste args doit correspondre à cette spécification.

Dans le corps d'une autre méthode ou proc de widget, un proc peut être invoqué comme n'importe quelle autre commande, simplement en utilisant son nom. Dans tout autre contexte de namespace, le proc est invoqué en utilisant un nom qualifié commewidgetName::proc". Les procs dans un widget de base qui sont redéfinis dans le widget actuel, ou masqués par un autre widget de base, peuvent également être accessibles via leur nom qualifié.

variable varName ?init? ?config?
Définit une variable spécifique à l'objet nommée varName. Toutes les variables spécifiques à l'objet sont automatiquement disponibles dans les méthodes de widget. Elles n'ont pas besoin d'être déclarées avec quelque chose comme la commande global .

Si la chaîne optionnelle init est spécifiée, elle est utilisée comme valeur initiale de la variable lorsqu'un nouvel objet est créé. L'initialisation force la variable à être une valeur scalaire simple ; les variables non initialisées, d'autre part, peuvent être définies dans le constructeur et utilisées comme des tableaux.

Le script optionnel config n'est autorisé que pour les variables publiques. S'il est spécifié, ce fragment de code est exécuté chaque fois qu'une variable publique est modifiée par la méthode intégrée "configure". Le script config peut également être spécifié en dehors de la définition du widget en utilisant la commande configbody .

common varName ?init?
Déclare une variable commune nommée varName. Les variables communes résident dans le namespace du widget et sont partagées par tous les objets appartenant au widget. Elles sont exactement comme les variables globales, sauf qu'elles n'ont pas besoin d'être déclarées avec la commande habituelle global . Elles sont automatiquement visibles dans toutes les méthodes et procs du widget.

Si la chaîne optionnelle init est spécifiée, elle est utilisée comme valeur initiale de la variable. L'initialisation force la variable à être une valeur scalaire simple ; les variables non initialisées, d'autre part, peuvent être définies avec les commandes set et array ultérieures et utilisées comme des tableaux.

Une fois qu'un membre de données commun a été défini, il peut être défini en utilisant les commandes set et array dans la définition du widget. Cela permet d'initialiser les membres de données communs en tant que tableaux. Par exemple :

itcl::widget Foo {
    protected common boolean
    set boolean(true) 1
    set boolean(false) 0
}

Notez que si les membres de données communs sont initialisés dans le constructeur, ils sont réinitialisés encore et encore chaque fois que de nouveaux objets sont créés.

public command ?arg arg ...?
protected command ?arg arg ...?
private command ?arg arg ...?
Ces commandes sont utilisées pour définir le niveau de protection des membres du widget qui sont créés lorsque command est évalué. La commande command est généralement method, proc, variable oucommon, et les argrestants complètent la définition du membre. Cependant, command peut aussi être un script contenant de nombreuses définitions de membres différentes, et le niveau de protection s'appliquera à tous les membres qui sont créés.

UTILISATION DU WIDGET

Une fois qu'un widget a été défini, le nom du widget peut être utilisé comme une commande pour créer de nouveaux objets appartenant au widget.

widgetName objName ?args...?
Crée un nouvel objet dans le widget widgetName avec le nom objName. Les arguments restants sont passés au constructeur du widget le plus spécifique. Celui-ci passe à son tour les arguments aux constructeurs des widgets de base avant d'invoquer son propre corps de commandes. Si la construction est réussie, une commande appelée objName est créée dans le contexte de namespace actuel, et objName est retourné comme résultat de cette opération. Si une erreur est rencontrée pendant la construction, les destructeurs sont automatiquement invoqués pour libérer toutes les ressources qui ont été allouées, l'objet est supprimé, et une erreur est retournée.

Si objName contient la chaîne "#auto", cette chaîne est remplacée par un nom généré automatiquement. Les noms ont la forme widgetName<number>, où la partie widgetName est modifiée pour commencer par une lettre minuscule. Dans le widget "Toaster", par exemple, la spécification "#auto" produirait des noms comme toaster0, toaster1, etc. Notez que "#auto" peut aussi être enfoui dans un nom d'objet :

fileselectiondialog .foo.bar.#auto -background red

Cela générerait un objet nommé ".foo.bar.fileselectiondialog0".

UTILISATION DE L'OBJET

Une fois qu'un objet a été créé, le nom de l'objet peut être utilisé comme une commande pour invoquer des méthodes qui opèrent sur l'objet.

objName method ?args...?
Invoque une méthode nommée method sur un objet nommé objName. Les arguments restants sont passés à la liste d'arguments de la méthode. Le nom de la méthode peut être "constructor", "destructor", n'importe quel nom de méthode apparaissant dans la définition du widget, ou l'une des méthodes intégrées suivantes.

MÉTHODES INTÉGRÉES

objName cget option
Fournit l'accès aux variables publiques en tant qu'options de configuration. Cela imite le comportement de l'opération "cget" habituelle pour les widgets Tk. L'argument option est une chaîne de la forme-varName", et cette méthode retourne la valeur actuelle de la variable publique varName.
objName configure ?option? ?value option value ...?
Fournit l'accès aux variables publiques en tant qu'options de configuration. Cela imite le comportement de l'opération "configure" habituelle pour les widgets Tk. Sans arguments, cette méthode retourne une liste de listes décrivant toutes les variables publiques. Chaque liste a trois éléments : le nom de la variable, sa valeur initiale et sa valeur actuelle.

Si une seule option de la forme-varName" est spécifiée, alors cette méthode retourne les informations pour cette seule variable.

Sinon, les arguments sont traités comme des paires option/value assignant de nouvelles valeurs aux variables publiques. Chaque variable se voit attribuer sa nouvelle valeur, et si elle a un code "config" associé, il est exécuté dans le contexte du widget où il a été défini. Si le code "config" génère une erreur, la variable est rétablie à sa valeur précédente, et la méthode configure retourne une erreur.

objName isa widgetName
Retourne non-zéro si le widgetName donné peut être trouvé dans l'héritage de l'objet, et zéro sinon.
objName info option ?args...?
Retourne des informations relatives à un objet particulier nommé objName, ou à sa définition de widget. Le paramètre option inclut les éléments suivants, ainsi que les options reconnues par la commande Tcl habituelle "info" :
objName info widget
Retourne le nom du widget le plus spécifique pour l'objet objName.
objName info inherit
Retourne la liste des widgets de base tels qu'ils ont été définis dans la commande "inherit", ou une chaîne vide si ce widget n'a pas de widgets de base.
objName info heritage
Retourne le nom du widget actuel et la liste complète des widgets de base dans l'ordre où ils sont parcourus pour la recherche de membres et la destruction d'objets.
objName info function ?cmdName? ?-protection? ?-type? ?-name? ?-args? ?-body?
Sans arguments, cette commande retourne une liste de toutes les méthodes et procs du widget. Si cmdName est spécifié, elle retourne les informations pour une méthode ou un proc spécifique. Si aucun drapeau n'est spécifié, cette commande retourne une liste avec les éléments suivants : le niveau de protection, le type (method/proc), le nom qualifié, la liste d'arguments et le corps. Les drapeaux peuvent être utilisés pour demander des éléments spécifiques de cette liste.
objName info variable ?varName? ?-protection? ?-type? ?-name? ?-init? ?-value? ?-config?
Sans arguments, cette commande retourne une liste de toutes les variables spécifiques à l'objet et des membres de données communs. Si varName est spécifié, elle retourne les informations pour un membre de données spécifique. Si aucun drapeau n'est spécifié, cette commande retourne une liste avec les éléments suivants : le niveau de protection, le type (variable/common), le nom qualifié, la valeur initiale et la valeur actuelle. Si varName est une variable publique, le code "config" est inclus dans cette liste. Les drapeaux peuvent être utilisés pour demander des éléments spécifiques de cette liste.

ENCHAÎNEMENT DES MÉTHODES/PROCS

Parfois, un widget de base a une méthode ou un proc qui est redéfini avec le même nom dans un widget dérivé. C'est une façon de faire en sorte que le widget dérivé gère les mêmes opérations que le widget de base, mais avec ses propres spécialisations.d comportement. Par exemple, supposons que nous ayons un widget Toaster qui ressemble à ceci

: 
itcl::widget Toaster {
    variable crumbs 0
    method toast {nslices} {
        if {$crumbs > 50} {
            error "== FIRE! FIRE! =="
        }
        set crumbs [expr {$crumbs+4*$nslices}]
    }
    method clean {} {
        set crumbs 0
    }
}

Nous pourrions créer un autre widget comme SmartToaster qui redéfinit la méthode "toast". Si nous voulons accéder à la méthode du widget de base, nous pouvons la qualifier avec le nom du widget de base, pour éviter l'ambiguïté

: 
itcl::widget SmartToaster {
    inherit Toaster
    method toast {nslices} {
        if {$crumbs > 40} {
            clean
        }
        return [Toaster::toast $nslices]
    }
}

Au lieu de coder en dur le nom du widget de base, nous pouvons utiliser la commande "chain" comme ceci

: 
itcl::widget SmartToaster {
    inherit Toaster
    method toast {nslices} {
        if {$crumbs > 40} {
            clean
        }
        return [chain $nslices]
    }
}

La commande chain recherche dans la hiérarchie des widgets une implémentation légèrement plus générique (du widget de base) d'une méthode ou proc, et l'

invoque avec les arguments spécifiés. Elle commence par le contexte du widget actuel et recherche à travers les widgets de base dans l'ordre dans lequel ils
sont rapportés par la commande "info heritage". Si une autre implémentation n'est pas trouvée, cette commande ne fait rien et retourne la chaîne nulle.

CHARGEMENT

AUTOMATIQUE

Les définitions de widgets n'ont pas besoin d'être chargées explicitement ; elles peuvent être chargées au besoin par la mécanisme habituel de chargement automatique de Tcl. Chaque répertoire contenant des fichiers de définition de widgets doit avoir un fichier "tclIndex" correspondant. Chaque ligne dans ce fichier identifie une procédure Tcl ou une définition de widget [incr Tcl] et le fichier où la définition peut être

trouvée.

Par exemple, supposons qu'un répertoire contienne les définitions des widgets "Toaster" et "SmartToaster". Alors le fichier "tclIndex" pour ce répertoire ressemblerait à

: 
# Tcl autoload index file, version 2.0 for [incr Tcl]
# This file is generated by the "auto_mkindex" command
# and sourced to set up indexing information for on
e or # more commands. Typically each line is a command that # sets an element in the auto_index array, where the # element name is the name of a command and the
value is # a script that loads the command. set auto_index(::Toaster) "source $dir/Toaster.itcl" set auto_index(::SmartToaster) "source $dir/SmartToaster.itcl"

La commande auto_mkindex est utilisée pour générer automatiquement les fichiers

"tclIndex".

Le chargeur automatique doit être informé de ce répertoire en ajoutant le nom du

répertoire à la variable "auto_path". Une fois cela en place, les widgets seron
t chargés automatiquement au besoin lorsqu'ils sont utilisés dans une application.

C

PROCÉDURES

Les procédures C peuvent être intégrées dans une définition de widget [incr Tcl] pour implémenter des méthodes, des procs, et le code "config" pour les variables publiques. Tout corps qui commence par "@" est traité comme le nom symbolique d'une procédure

C.

Les noms symboliques sont établis en enregistrant des procédures via Itcl_RegisterC(). Cela se fait généralement dans la procédure Tcl_AppInit(), qui est automatiquement appelée lorsque l'interpréteur démarre. Dans l'exemple suivant, la procédure My_FooCmd() est enregistrée avec le nom symbolique "foo". Cette procédure peut être référencée dans la commande body comme

"@foo". 
int
Tcl_AppInit(interp)
    Tcl_Interp *interp;     /* Interpreter for application. */
{
    if (Itcl_Init(interp) == TCL_ERROR) {
        return TCL_ERROR;
    }
    if (Itcl_RegisterC(interp, "foo", My_FooCmd) != TCL_OK) {
        return TCL_ERROR;
    }
}

Les procédures C sont implémentées tout comme les commandes Tcl ordinaires. Voir la page de man CrtCommand pour les détails. Au sein de la procédure, les membres de données du widget peuvent être accédés comme des variables ordinaires en utilisant Tcl_SetVar(), Tcl_GetVar(), Tcl_TraceVar(), etc. Les méthodes et procs du widget peuvent être exécutés comme des commandes ordinaires en utilisant Tcl_Eval(). [incr Tcl] rend cela possible en configurant automatiquement le contexte avant d'exécuter la procédure

C.

Ce schéma fournit un chemin de migration naturel pour le développement de code. Les widgets peuvent être développés rap

idement en utilisant du code Tcl pour implémenter les corps. Une application entière peut être construite et testée. L
orsque c'est nécessaire, des corps individuels peuvent être implémentés avec du code C pour améliorer les performances.
