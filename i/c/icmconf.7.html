icmconf - Fichier de configuration pour le programme de maintenance d

icmbuild(1)

DESCRIPTIO

N

Le fichier de configuration icmconf est utilisé pour configurer la maintenance de programme effectuée par icmbuild(1). Il utilise diverses directives déterminant la manière dont la maintenance du programme ou de la bibliothèque est

effectuée.

Les directives d'Icmconf sont orientées vers la construction de programmes C++, mais la maintenance de programmes pour d'autres langages (par ex., C) peut aussi être facilement

configurée.

Le script icmbuild(1) ignore les lignes vides et les lignes dont les premiers caractères non vides sont deux barres obliques consécutives (//) ou commencent par un caractère dièse (#). Les lignes longues peuvent être réparties sur plusieurs lignes en écrivant un c

aractère barre oblique inverse final aux li
gnes se poursuivant à la ligne suivante.

DÉPENDANCES DE

CLASSE

Les utilitaires make traditionnels recompilent toutes les sources dépendantes une fois que les fichiers d'en-tête sont modifiés. Lors du développement de programmes C++, cela est presque jamais requis, car l'ajout de nouvelles fonctions membres aux classes ne vous oblige pas à recompiler les fichiers source déjà existants. La recompilation est requise lorsque l'organisation des membres de données des classes est

modifiée.

Pour gérer les dépendances de classe de manière plus sensée, icmake(1) vérifie les dépendances de classe à l'aide de ses programmes de support icm-dep, visitant les classes listées dans le fichier CLASSES si la directive USE_ALL d'icmconf a été spécifiée. Si un répertoire mentionné dans le fichier CLASSES contient un fichier dont le nom est égal à celui spécifié au paramètre USE_ALL, alors toutes les sources des classes qui dépendent de cette classe particulière sont aussi recompilées. En pratique, cela signifie que lorsque vous changez l'organisation des données d'une classe vous n'avez besoin que de toucher dans ce répertoire le fichier dont le nom a été spécifié par la directive USE_ALL. Par ex., si votre classe est nommée Data, ses sources sont dans le sous-répertoire ./data, et #define USE_ALL "a" a été spécifié, alors après avoir modifié l'organisation des données de la classe Data vous n'avez besoin que d'émettre la commande touch data/a. Ensuite, lors du prochain appel d'icmbuild toutes les sources dans ./data ainsi que toutes les sources dans les répertoires dont les fichiers (d'en-tête) incluent data.h sont aussi

recompilées.

De même, si #define SPCH ou (obsolète) #define PRECOMP a été utilisé, une action similaire est effectuée pour les en-têtes précompilés : si un fichier local qui est inclus (directement ou indirectement) par des fichiers d'en-tête internes a changé, alors le fichier d'En-tête Pré-Compilé Unique (SPCH) est recompilé (ou (obsolète), ayant spécifié PRECOMP les en-têtes de classe modifiés sont recompilés)

.

Le script icmbuild(1) lui-même n'inspecte pas ces dépendances, mais appelle les programmes de support icm-spch et icm-dep pour effectuer les tests requis. Les résumés d'utilisation de ces programmes sont écrits sur le flux de sortie standard lors de l'appel, respectivement icmake -S et icmake -d

.

Lorsque la directive (obsolète) PRECOMP est spécifiée, la fraîcheur des en-têtes précompilés est assurée (voir aussi la description de SPCH, ci-dessous). Par défaut icm_dep est appelé avec les arguments par défaut montrés. Si icm_dep ne doit pas être appelé, définissez ICM_DEP comme une chaîne vide (""). La page man de icmake(1) contient une section séparée à propos du programme de support icm_dep

#define IH ".ih"

//#define LDFLAGS ""
options de l'éditeur de liens à utiliser. Par défaut aucune option n'est passée à l'éditeur de liens. Son réglage est remplacé par une variable d'environnement de même
nom ;

//#define LIBRARY "ofiles"
en définissant cette directive, une bibliothèque locale (libofiles.a) est construite. Lorsqu'un programme binaire est construit, il est lié contre cette bibliothèque plutôt qu'aux fichiers objet
individuels.
Si une bibliothèque doit être construite à la place d'un programme (voir aussi la directive DEFCOM), alors la directive LIBRARY spécifie le nom de base de la bibliothèque (sans le préfixe libd sans l'extension .a). Dans ce cas, les fichiers sources sont attendus dans des sous-répertoires du répertoire principal du projet (c.-à-d. le répertoire contenant icmconf). Dans ce cas, évitez d'avoir des fichiers sources et d'en-tête dans le répertoire principal du projet. Déplacez plutôt de tels fichiers vers un sous-répertoire séparé
;
o
//#define MAIN "main.cc"
le fichier source dans lequel la fonction int main est définie. Cette directive est requise lors de la maintenance d'un programme (plutôt que d'une bibliothèque)
.
Remarque : si les fichiers sources se trouvent dans le répertoire principal du projet mais que la maintenance d'une bibliothèque est prévue (p. ex. en spécifiant #define DEFCOM library) alors définissez MAIN pour spécifier une source pseudo-main, dont le nom de base est le nom de base du fichier d'en-tête dans le répertoire principal du projet. Cependant, cela est considéré comme un bricolage et devrait être évité en déplaçant ces fichiers sources et d'en-tête vers un sous-répertoire séparé
;

//#define MULTICOMP "..."
Exemple : #define MULTICOMP "jobs
-q"
Cette directive active la compilation en threads des fichiers sources. Lorsqu'elle est utilisée, son premier mot spécifie le nom d'un fichier contenant des informations sur les fichiers qui doivent être compilés. Il doit s'agir d'un nom de fichier simple, ne contenant pas de spécificateurs de répertoire (comme /). Consultez la section ICM-MULTICOMP de la page de manuel icmake(1) couvrant les options, les arguments et l'utilisation de icm-multicomp qui est appelé lorsque #define MULTICOMP est spécifié
;
o
//#define NO_PRECOMP_WARNING"
lorsque #define PRECOMP (désormais obsolète) est spécifié (voir ci-dessous), un avertissement est émis lorsqu'un répertoire de classes ne contient pas de fichier IH. De tels avertissements sont supprimés en définissant NO_PRECOMP_WARNING. Cette option n'est prise en compte que lorsque #define PRECOMP est spécifié
;
o
#define OBJ_EXT ".o"
cette directive spécifie l'extension des modules objet créés par le compilateur
;
o
//#define PRECOMP "-x c++-header"
(obsolète, envisagez plutôt de déclarer #define SPCH)
définissez cette directive pour construire des en-têtes précompilés spécifiques aux classes (auquel cas la directive IH) doit également être spécifiée. Les dépendances entre les en-têtes (précompilés) sont automatiquement prises en compte.
Les en-têtes précompilés existants sont supprimés par icmbuild cleangch (ou icmbuild clean. Lorsque des fichiers sources d'autres langages sont compilés, l'argument -x de PRECOMP doit être adapté à ces langages
;
o
//#define REFRESH
définissez REFRESH pour relier le programme binaire lorsque icmbuild program est appelé, même si aucun fichier n'a été (re)compilé. Cela est utile lorsque le programme est lié à des bibliothèques externes qui ont été mises à jour séparément du projet courant
;
o
//#define SHARED
cette directive n'est interprétée que lorsque LIBRARY est également spécifié. Si elle est définie, une bibliothèque partagée (extension .so*) est construite en plus d'une bibliothèque statique (extension .a) ;
La bibliothèque partagée reçoit VERSION comme son numéro de version, tandis que des liens symboliques utilisant le numéro de version majeur de VERSION (voir ci-dessous) et sans numéro de version sont également mis à disposition. Par exemple, si VERSION est défini comme 1.02.03 et #define LIBRARY "demo" alors la bibliothèque partagée devient libdemo.so.1.02.03, avec libdemo.so.1 pointant vers elle par lien symbolique, et libdemo.so pointant vers libdemo.so.1 par lien
symbolique ;
o
//#define SHAREDREQ ""
lors de la création d'une bibliothèque partagée SHAREDREQ spécifie les noms des bibliothèques et les chemins de bibliothèques requis par la bibliothèque partagée construite elle-même. Par exemple, si une bibliothèque se trouve dans /usr/lib/special, en supposant que le nom de la bibliothèque requise est libspecial.so, utilisez la spécification #define SHAREDREQ "-L/usr/lib/special -lspecial". Les chemins /lib et /usr/lib sont généralement automatiquement parcourus par l'éditeur de liens et n'ont pas besoin d'être spécifiés. Cette directive est requise (éventuellement sous forme de chaîne vide) si SHARED est défini
;
o
#define SOURCES "*.cc"
le motif pour localiser les sources dans les répertoires
;
o
//#define SPCH "..."
Exemple : #define SPCH ""
Si #define SPCH est spécifié alors #define IH doit également être spécifié.
Cette directive active l'utilisation d'en-têtes précompilés uniques (consultez la page de manuel icmake(1) pour plus de détails). La chaîne d'argument peut être vide, ou elle peut contenir des spécifications utilisées lors de la construction d'un SPCH. Consultez la section ICM-SPCH de la page de manuel icmake(1) pour plus de détails
;
o
//#define SPCH_FILE "..."
Exemple : #define SPCH_FILE "specs"
Cette directive peut être utilisée en combinaison avec la directive #define SPCH. Par défaut, les en-têtes utilisés pour construire le SPCH sont écrits dans le fichier spch. Si ce nom ne doit pas être utilisé, la directive SPCH_FILE peut être utilisée pour spécifier un autre nom de fichier. Le nom spécifié doit être un nom de fichier simple, ne contenant pas de spécificateurs de répertoire (comme / ou une extension)
.
o
#define TMP_DIR "tmp"
le répertoire dans lequel les résultats intermédiaires sont stockés. Pour éviter les communications inter-périphériques, il est probablement préférable de définir TMP_DIR comme sous-répertoire du répertoire principal du projet
;
o
//#define USE_ALL "a"
lors de la définition de cette directive icmbuild recherche les répertoires contenant des fichiers ayant les noms définis par la spécification USE_ALL. Tous les fichiers sources de ces répertoires ainsi que tous les fichiers sources des répertoires qui dépendent (récursivement) de l'ensemble de répertoires considérés sont recompilés, après quoi les fichiers USE_ALL sont supprimés
;
o
//#define USE_ECHO ON
lorsqu'elle est définie comme ON (plutôt que OFF), les commandes (système) exécutées par icmbuild sont affichées
;
o
//#define USE_VERSION

Le fichier VERSION doit être disponible dans le répertoire principal du projet et devrait contenir des lignes comme celles-ci : 
    VERSION=11.01.00
    YEARS=1992-2024
