DESCRIPTIO

N

Bien que les modules soient disponibles depuis un certain temps, le compilateur gnu g++ présente encore un certain nombre de bogues liés aux modules C++ (cf. https://gcc.gnu.org/bugzilla/show_bug.cgi?id=103524). Il est donc possible que lorsque vous utilisez les modules, vous rencontriez certains de ces bogues (ou de nouveaux). Les bogues seront probablement corrigés dans les futures versions du compilateur, et l'état actuel des choses vous permet au moins d'acquérir une certaine expérience dans l'utilisation des

modules.

Les modules ne peuvent pas s'importer mutuellement. Par conséquent, il existe toujours une hiérarchie de modules linéaire et non circulaire, ce qui doit être pris en compte lors de la compilation des fichiers définissant et utilisant des modules. Le programme icmodmap détermine cet ordre et prépare la construction des modules utilisés par les

programmes.

Icmodmap suppose que les modules sont définis dans des sous-répertoires séparés, et que les interfaces de modules sont définies dans (par défaut) des fichiers nommés module.cc. Si un programme définit deux modules First et Second (par ex., dans les sous-répertoires first et second et que le second/module.cc importe le module First alors first/module.cc doit être compilé avant la compilation de second/module.cc. Ceci est géré par icmodmap. Une fois que les fichiers module.cc ont été compilés, les fichiers source restants du programme peuvent être compilés comme

d'habitude.

Icmodmap s'attend à ce que les projets utilisant les modules soient organisés comme suit

:
o
Le répertoire de premier niveau du projet contient un fichier CLASSES, où chaque ligne (en ignorant les commentaires (C++)) spécifie le nom d'un sous-répertoire implémentant l'un des composants du projet. Alternativement, un (sous-ensemble des) sous-répertoires du répertoire peut être spécifié. Chaque sous-répertoire peut définir un module, une partition de module, une classe (ne faisant pas partie d'un module, mais pouvant utiliser des modules), ou des fonctions de niveau global (éventuellement utilisant aussi des modules)
;
o
Si le projet définit un programme, le répertoire de premier niveau du projet contient des fichiers source (comme main.cc) définissant la fonction main . Le répertoire de premier niveau ne définit pas de module, mais ses sources peuvent utiliser des modules
;
o
Les sous-répertoires définissant des modules ou des partitions contiennent par défaut un fichier module.cc, définissant le nom du module et son interface (au lieu de module.cc, un autre nom de fichier peut être spécifié)
;
o
Les modules et les partitions peuvent définir des classes (une classe par mod
ule, une classe par partition). Si c'est le cas, les fonctions membres de ce
s classes sont définies dans le sous-répertoire du module ou de la partition.

Icmodmap(1) inspecte chaque sous-répertoire spécifié. S'il contient le fichier module.cc (ou son nom alternatif), alors ce fichier (ayant la structure suivante) est inspecté

:
o
sa première ligne non vide : définit le nom du module ou de la partition
;
o
les lignes import peuvent spécifier de
s en-têtes système,
des modules et
/ou des partitions.

OPTION

S

Icmodmap prend en charge les options suivantes

:
o
--colors (-c)
par défaut, le compilateur est appelé en utilisant l'option -fdiagnostics-color=never . Utilisez cette option pour supprimer cette option
;
o
--dependencies (-d)
les dépendances entre modules sont affichées avec cette option. Les fichiers source définissant des modules ne sont pas compilés. La sortie d'icmodmap peut ressembler à ceci : 
    Square:l
    DepSquare: Square
ici, le suffixe :l indique que Square est un module défini par le projet, ne dépendant pas d'autres modules. Lorsque les définitions de modules dépendent d'autres modules, elles sont listées ensuite : DepSquare est un autre module défini par le projet, dépendant du module Square
.
Il est également possible que des modules dépendent de modules définis par d'autres projets. Dans ce cas, la sortie peut ressembler à ceci : 
    Square:e
    Mod1: Square:e
    Mod2: Square:e Mod1 
    Mod3: Square:e Mod1  Mod2
Dans cet exemple, le module Square est un module externe, indiqué par le suffixe :e. Tous les autres modules dépendent de Square, et (par ex.) Mod3 dépend également des modules définis localement Mod1 et Mod2. Dans ce dernier exemple, le fichier Square.gcm doit être disponible dans le répertoire gcm.cache du projet (il pourrait être un lien symbolique vers le fichier réel)
;
o
--help (-h)
Fournit les informations d'utilisation, renvoyant 0 au système d'exploitation
;
o
--module=fichier (-m)
Par défaut, les modules sont définis dans les fichiers source module.cc. Si les modules sont définis dans des fichiers source ayant d'autres noms, alors ces noms peuvent être spécifiés en utilisant cette option. Par ex., lorsque les modules sont définis dans des fichiers interface.cc, alors spécifiez l'option --module interface.cc. L'utilisation de fichiers de définition de modules avec des noms différents n'est pas prise en charge
;
o
--subdir (-s)
Par défaut, les fichiers compilés définissant des modules sont situés dans le sous-répertoire tmp/o du projet, où chaque fichier compilé a reçu un préfixe de numéro d'ordre de compilation (par ex., tmp/o/1module.o, tmp/o/2module.o, ...). Lorsque l'option --subdir est spécifiée, les fichiers compilés sont situés dans le même sous-répertoire que les fichiers définissant les modules eux-mêmes (sans utiliser le préfixe de numéro d'ordre)
;
o
--version (-v)
Affiche la version d'icm
odmap.
o
--verbose (-V)
Affiche une sortie supplémentaire lors de
la détermination de l'ordre de compi
lation des modules et de la compilation des
fichiers de définition des modules.

EXEMPL

E

Le programme suivant définit un module Square dans son sous-répertoire square, contenant ce fichier module.cc

: 
export module Square;
export
{
    double square(double value);
    class Square
    {
        double d_amount;
        public:
            Square(double amount = 0);          // initialize
            void amount(double value);          // change d_amount
            double amount() const;              // return d_amount
            double lastSquared() const;         // returns g_squared
            double square() const;              // returns sqr(d_amount)
    };
}
double
g_squared;

La fonction main importe le module Square et utilise ses fonctionnalités. Elle importe également l'en-tête système compilé en module iostream. Cet en-tête n'est pas inspecté par icmodmap et doit être disponible avant que le fichier main.cc puisse être compilé. Voici le fichier source main.cc

: 
import Square;
import <iostream>;
int main(int argc, char **argv)
{
    std::cout << "the square of " << argc << " is " 
                                        << square(argc) << ’\n’;
    Square obj{12};
    std::cout << "the square of 12 is " << obj.square() << "\n"
                "the last computed square is " << 
                obj.lastSquared() << ’\n’;
}

l

e.cc : 
    Module: Square

NAME

icmodmap — icmake utilities for the International Components for Unicode (ICU)

SYNOPSIS

icmodmap [options]

DESCRIPTION

The icmodmap utility finds the module-compiled system header files. It also defines the soft-link square/gcm.cache -> ../gcm.cache: those soft-links are defined in all sub-directories used by the program, allowing all source files in all of the program’s sub-directories to import all modules defined in the main directory’s gcm.cache directory.

icmake(1).
