NOM

freeipmi_interpret_sensor.conf - spécifier les règles d'interprétation des capteurs

DESCRIPTION

Le fichier /etc/freeipmi//freeipmi_interpret_sensor.conf définit comment les capteurs IPMI doivent être interprétés. Les capteurs basés sur IPMI spécifient un certain nombre d'états/seuils lorsqu'ils sont lus. Sur la base de ces états/seuils, les bibliothèques et les outils tels que libfreeipmi(3), libipmimonitoring(3) et ipmi-sensors(8) peuvent indiquer si une lecture de capteur est "bonne" ou "mauvaise" via un rapport d'état NOMINAL, D'AVERTISSEMENT ou CRITIQUE.

Chacun des états listés ci-dessous est (espérons-le) suffisamment descriptif pour décrire les conditions d'état qui peuvent être activées/désactivées pour chaque type de capteur. Pour plus d'informations sur chacun des états individuels listés ci-dessous, veuillez consulter la spécification IPMI "Sensor and Event Code Tables". Ipmi-sensors(8) peut être utilisé pour déterminer les types de capteurs et les états/seuils existants sur un système en générant une sortie très verbeuse et en voyant quels types d'événements d'assertion ou de désassertion sont possibles.

Les valeurs possibles pour tous les états/seuils ci-dessous sont :

Nominal - Signal de lecture Nominale si état/seuil déclenché

Avertissement - Signal d'Avertissement si état/seuil déclenché

Critique - Signal Critique si état/seuil déclenché

Tous les types de capteurs IPMI et tous les types d'événements ne sont pas actuellement pris en charge. Si vous souhaitez que plus de types soient pris en charge, veuillez envoyer un e-mail à la liste de diffusion FreeIPMI.

Les valeurs par défaut sélectionnées pour les états/seuils individuels déclenchés sont basées sur des suppositions et l'analyse des cartes mères. Si vous pensez qu'elles devraient être modifiées, veuillez envoyer un e-mail à la liste de diffusion FreeIPMI pour discuter des valeurs par défaut.

La plupart des interprétations par défaut peuvent être déterminées assez facilement et répondre aux besoins de la plupart des utilisateurs. Par exemple, une lecture de "Performance_Met" est normalement meilleure que "Performance_Lags". Cependant, certains capteurs peuvent être ambigus et dépendent entièrement du fabricant. Par exemple, "State_Asserted" contre "State_Deasserted" dépend entièrement de l'interprétation du vendeur. Il est conseillé aux utilisateurs d'ajuster les interprétations ci-dessous selon leurs besoins pour leurs machines.

Chaque groupe de conditions d'état ci-dessous inclut une configuration pour "No_Event". C'est la condition dans laquelle aucun état/événement de capteur ne s'est produit ou n'est déclenché. Dans la plupart des conditions, un mappage sur "Nominal" est préféré. Cependant, dans certaines circonstances, il peut être utile de rapporter autre chose. Par exemple, si un capteur sur une carte mère particulière doit signaler un état/événement, une condition d'état de capteur nul pourrait indiquer un capteur défectueux. Ceci dépend fortement de la carte mère.

FORMAT

Les options de configuration qui peuvent être spécifiées dans le fichier de configuration sont listées ci-dessous. Chaque option de configuration doit être listée sur une ligne distincte. Les arguments d'une option sont séparés par n'importe quelle quantité d'espaces blancs. Plusieurs arguments sont également séparés par des espaces blancs. Les commentaires peuvent être marqués en utilisant le caractère dièse (#), et les lignes peuvent être continuées sur la suivante en utilisant la barre oblique inverse (\).

NAME

ipmi_monitoring_sensors.conf – FreeIPMI sensor interpretation configuration file

DESCRIPTION

This file can be used to specify how sensor readings are interpreted by FreeIPMI.

The file consists of a set of configuration sections, each beginning with a section-name tag. Each section contains a set of tag-value pairs, one per line. Blank lines are ignored. Lines beginning with a hash symbol (#) are comments.

Sections can be nested. For example, the following is a valid configuration:

section-name {
    tag-name = value
    nested-section-name {
        another-tag = another-value
    }
}

FORMAT

The following tags are supported:

IPMI_Version_Change_Entity_Is_Of_An_Invalid_Or_Unsupported_Hardware_Version
Defaults to Critical.
IPMI_Version_Change_Entity_Contains_An_Invalid_Or_Unsupported_Firmware_Or_Software_Version
Defaults to Critical.
IPMI_Version_Change_Hardware_Change_Detected_With_Associated_Entity_Was_Successful
Defaults to Nominal.
IPMI_Version_Change_Software_Or_FW_Change_Detected_With_Associated_Entity_Was_Successful
Defaults to Nominal.

IPMI_OEM
The following configuration options can be used to configure OEM specific interpretations. Users should be aware that both IPMI_OEM_Bitmask and IPMI_OEM_Value can be configured for an identical Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination. All interpretations rules for a specific combination are iterated through and the worst resulting sensor state is returned (i.e. Warning < Nominal, Critical < Warning). If no match is found, no sensor state is returned for the OEM sensor reading. For each of the configuration options below, <Manufacturer-ID> is the numeric IANA manufacturer ID for the manufacturer in question. The <Product-ID> is one or more numeric IDs representing the manufacturer's product. The <Product-ID> can be listed as a single numeric number (e.g. 1234), a range of IDs separated by a dash (e.g. 12-20), or a list of specific product IDs separated by a plus (e.g. 12+19+22). Both the Manufacturer-ID and Product-ID can be found using bmc-info(8). Multiple <Manufacturer-ID> and <Product-ID> pairs can be input separated by commas. The Event-Reading-Type-Code and Sensor-Type need not be OEM types. They may be non-OEM types and used to provide interpretation rules for sensors that may be behaving outside the standard of the IPMI specification.
IPMI_OEM_Bitmask <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Sensor-Event-Bitmask State
IPMI_OEM_Bitmask can be used to configure a state interpretation for a specific Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination and a specific bitmask of the Sensor-Event. The state will be accepted as the sensor interpretation if the inputted bitmask ANDed with the actual sensor event bitmask reading is true. As a special case, the state will be accepted if the inputted bitmask and the actual sensor event bitmask are both 0. In other words, if no events happened, an OEM interpretation can be configured for this case by inputing a bitmask of 0x0000.
IPMI_OEM_Value <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Sensor-Event-Bitmask-Value State
IPMI_OEM_Value can be used to configure a state interpretation for a specific Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination and a specific value for the Sensor-Event-Bitmask. The state will be accepted as the sensor interpretation if the inputted bitmask value is equal to the actual sensor event bitmask reading.
