FREEIPMI_INTERPRET_SENSOR(5) Configuration FREEIPMI_INTERPRET_SENSOR(5)

NOM

freeipmi_interpret_sensor.conf - spécifier les règles d'interprétation des capteurs

DESCRIPTION

Le fichier /etc/freeipmi//freeipmi_interpret_sensor.conf définit la manière dont les capteurs IPMI doivent être interprétés. Les capteurs basés sur IPMI spécifient un certain nombre d'états/seuils lorsqu'ils sont lus. En fonction de ces états/seuils, les bibliothèques et outils tels que libfreeipmi(3), libipmimonitoring(3) et ipmi-sensors(8) peuvent indiquer si une lecture de capteur est « bonne » ou « mauvaise » via un rapport d'état NOMINAL, WARNING (Avertissement) ou CRITICAL (Critique).

Chacun des états listés ci-dessous est (espérons-le) suffisamment descriptif pour décrire les conditions d'état qui peuvent être activées/désactivées pour chaque type de capteur. Pour plus d'informations détaillées sur chacun des états individuels listés ci-dessous, veuillez consulter la spécification IPMI « Tables de codes des capteurs et événements ». Ipmi-sensors(8) peut être utilisé pour déterminer les types de capteurs et les états/seuils existants sur un système en produisant une sortie très verbeuse et en observant les types d'événements d'Assertion ou de Désassertion possibles.

Les valeurs possibles pour tous les états/seuils ci-dessous sont :

Nominal - Indique une lecture nominale si l'état/seuil est déclenché

Warning - Indique une lecture d'avertissement si l'état/seuil est déclenché

Critical - Indique une lecture critique si l'état/seuil est déclenché

Tous les types de capteurs IPMI et types d'événements ne sont pas actuellement pris en charge. Si vous souhaitez que davantage soient pris en charge, veuillez envoyer un e-mail à la liste de diffusion FreeIPMI.

Les valeurs par défaut sélectionnées pour les états/seuils individuels déclenchés sont basées sur des conjectures éclairées et l'analyse des cartes mères. Si vous pensez qu'elles devraient être modifiées, veuillez envoyer un e-mail à la liste de diffusion FreeIPMI pour discuter des valeurs par défaut.

La plupart des interprétations par défaut peuvent être déterminées assez facilement et répondre aux besoins de la plupart des utilisateurs. Par exemple, une lecture de « Performance_Met » est normalement meilleure que « Performance_Lags ». Cependant, certains capteurs peuvent être ambigus et dépendent entièrement du fabricant. Par exemple, « State_Asserted » vs « State_Deasserted » dépendent entièrement de l'interprétation du vendeur. Il est conseillé aux utilisateurs d'ajuster les interprétations ci-dessous selon leurs besoins pour leurs machines.

Chaque groupe de conditions d'état ci-dessous comprend une configuration pour « No_Event ». C'est la condition selon laquelle aucun état/événement de capteur ne s'est produit ou n'est déclenché. Dans la plupart des conditions, un mappage à « Nominal » est préféré. Cependant, dans certaines circonstances, il peut être utile de signaler autre chose. Par exemple, si un capteur sur une carte mère particulière doit signaler un état/événement, une condition sans état de capteur pourrait indiquer un capteur défectueux. Cela dépend fortement de la carte mère.

FORMAT

Les options de configuration pouvant être spécifiées dans le fichier de configuration sont listées ci-dessous. Chaque option de configuration doit être listée sur une ligne séparée. Les arguments d'une option sont séparés par n'importe quelle quantité d'espaces blancs. Les arguments multiples sont également séparés par des espaces blancs. Les commentaires peuvent être marqués en utilisant le caractère dièse (« # »), et les lignes peuvent être continuées sur la ligne suivante en utilisant une barre oblique inverse (« \ »).

EM
Les options de configuration suivantes peuvent être utilisées pour configurer des interprétations spécifiques aux OEM. Les utilisateurs doivent noter que les deux IPMI_OEM_Bitmask et IPMI_OEM_Value peuvent être configurés pour une combinaison identique de Manufacturer-ID, Product-ID, Event-Reading-Type-Code, et Sensor-Type. Toutes les règles d'interprétation pour une combinaison spécifique sont parcourues et l'état de capteur résultant le plus grave est retenu (c'est-à-dire Avertissement < Nominal, Critique < Avertissement). Si aucune correspondance n'est trouvée, aucun état de capteur n'est retenu pour la lecture du capteur OEM. Pour chacune des options de configuration ci-dessous, <Manufacturer-ID> est l'identifiant numérique IANA du fabricant en question. Le <Product-ID> est un ou plusieurs identifiants numériques représentant le produit du fabricant. Le <Product-ID> peut être listé comme un nombre numérique unique (par ex. 1234), une plage d'identifiants séparés par un tiret (par ex. 12-20), ou une liste d'identifiants de produits spécifiques séparés par un plus (par ex. 12+19+22). Le Manufacturer-ID et le Product-ID peuvent être trouvés à l'aide de bmc-info(8). Plusieurs paires <Manufacturer-ID> et <Product-ID> peuvent être saisies séparées par des virgules. Le Event-Reading-Type-Code et le Sensor-Type n'ont pas besoin d'être des types OEM. Ils peuvent être des types non-OEM et utilisés pour fournir des rè
gles d'interprétation pour des capteurs qui peuvent se
comporter en dehors des normes de la spécification IPMI.
IPMI_OEM_Bitmask <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Sensor-Event-Bitmask Sta
te
IPMI_OEM_Bitmask peut être utilisé pour configurer une interprétation d'état pour une combinaison spécifique de Manufacturer-ID, Product-ID, Event-Reading-Type-Code, et Sensor-Type ainsi qu'un masque de bits spécifique du Sensor-Event. L'état sera accepté comme interprétation du capteur si le masque de bits saisi ET logique avec le masque de bits réel de l'événement du capteur est vrai. Comme cas particulier, l'état sera accepté si le masque de bits saisi et le masque de bits réel de l'événement du capteur sont tous deux à 0. En d'autres termes, si aucun événement ne s'est produit, une interprétation OEM peut être configurée pour ce cas en saisissant un masque de bits de
0x0000.
