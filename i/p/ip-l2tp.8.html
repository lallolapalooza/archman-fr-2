DESCRIPTIO

N

Les commandes ip l2tp sont utilisées pour établir des tunnels Ethernet L2TPv3 statiques, aussi appelés non gérés. Pour les tunnels non gérés, il n'y a pas de protocole de contrôle L2TP, donc aucun démon en espace utilisateur n'est requis - les tunnels sont créés manuellement en émettant des commandes sur un système local et sur un pair

distant.

L2TPv3 est adapté au tunneling de couche 2. Les tunnels statiques sont utiles pour établir des liens réseau à travers des réseaux IP lorsque les tunnels sont fixes. Les tunnels L2TPv3 peuvent transporter les données de plus d'une session. Chaque session est identifiée par un session_id et le tunnel_id de son tunnel parent. Un tunnel doit être créé avant qu'une session puisse être créée dans le

tunnel.

Lors de la création d'un tunnel L2TP, l'adresse IP du pair distant est spécifiée, qui peut être soit une adresse IPv4 soit une adresse IPv6. L'adresse IP locale utilisée pour atteindre le pair doit également être spécifiée. C'est l'adresse sur laquelle le système local écoutera et acceptera les paquets de données L2TP reçus du

pair.

L2TPv3 définit deux formats d'encapsulation de paquets : UDP ou IP. L'encapsulation UDP est la plus courante. L'encapsulation IP utilise une valeur de protocole IP dédiée pour transporter les données L2TP sans le surcoût de UDP. Utilisez l'encapsulation IP uniquement s'il n'y a pas de périphériques NAT ou de pare-feu dans le chemin

réseau.

Lorsqu'une session Ethernet L2TPv3 est créée, une interface réseau virtuelle est créée pour la session, qui doit ensuite être configurée et activée, comme n'importe quelle autre interface réseau. Lorsque des données passent à travers l'interface, elles sont transportées à travers le tunnel L2TP vers le pair. En configurant les tables de routage du système ou en ajoutant l'interface à un pont, l'interface L2TP est comme un fil virtuel (pseudowire) connecté au

pair.

L'établissement d'un pseudowire Ethernet L2TPv3 non géré implique la création manuelle de contextes L2TP sur le système local et sur le pair. Les paramètres utilisés à chaque site doivent correspondre, sinon aucune donnée ne sera transmise. Aucune vérification de cohérence n'est possible puisqu'aucun protocole de contrôle n'est utilisé pour établir des tunnels L2TP non gérés. Une fois que l'interface réseau virtuelle d'une session L2TP donnée est configurée et activée, les données peuvent être transmises, même si le pair n'est pas encore configuré. Si le pair n'est pas configuré, les paquets de données L2TP seront ignorés par le

pair.

Pour établir un tunnel L2TP non géré, utilisez les commandes l2tp add tunnel et l2tp add session décrites dans ce document. Configurez et activez ensuite l'interface réseau virtuelle du tunnel, selon les

besoins.

Notez que les tunnels non gérés ne transportent que des trames Ethernet. Si vous devez transporter du trafic PPP (L2TPv2) ou si votre pair ne prend pas en charge les tunnels L2TPv3 non gérés, vous aurez besoin d'un serveur L2TP qui implémente le protocole de contrôle L2TP. Le protocole de contrôle L2TP permet d'établir des tunnels et des sessions L2TP dynamiques et fournit la détection et la gestion des pannes

réseau.

Configuration comme interfaces

pontées

Pour transporter des données non IP, l'interface réseau L2TP est ajoutée à un pont au lieu de lui attribuer sa propre adresse IP, à l'aide des utilitaires Linux standard. Étant donné que des trames Ethernet brutes sont alors transportées à l'intérieur du tunnel, le MTU des interfaces L2TP doit être défini pour laisser de la place à ces

en-têtes. 
site-A:# ip link set l2tpeth0 up mtu 1446
site-A:# ip link add br0 type bridge
site-A:# ip link set l2tpeth0 master br0
site-A:# ip link set eth0 master br0
site-A:# ip link set br0
up

Si vous utilisez des VLAN, configurez un pont par VLAN et pontez chaque VLAN sur une session L2TP distincte. Par exemple, pour ponter l'ID VLAN 5 sur eth1 via un pseudofilaire L2TP

: 
site-A:# ip link set l2tpeth0 up mtu 1446
site-A:# ip link add brvlan5 type bridge
site-A:# ip link set l2tpeth0.5 master brvlan5
site-A:# ip link set eth1.5 master brvlan5
site-A:# ip link set brvlan5
up

L'ajout de l'interface L2TP à un pont fait que le pont transmet le trafic via le pseudofilaire L2TP tout comme il le fait via n'importe quelle autre interface. Le pont apprend les adresses MAC des hôtes connectés à chaque interface et transmet intelligemment les trames d'un port du pont à un autre. Aucune adresse IP n'est attribuée aux interfaces l2tpethN. Si le pont est correctement configuré des deux côtés du pseudofilaire L2TP, il devrait être possible d'atteindre les hôtes du réseau ponté du

pair.

Lorsque des trames Ethernet brutes sont pontées via un tunnel L2TP, les trames volumineuses peuvent être fragmentées et transmises sous forme de fragments IP individuels au destinataire, en fonction du MTU de l'interface physique utilisée par le tunnel. Lorsque les trames Ethernet transportent des protocoles qui sont réassemblés par le destinataire, comme IP, ce n'est pas un problème. Cependant, une telle fragmentation peut causer des problèmes pour des protocoles comme PPPoE où le destinataire s'attend à recevoir les trames Ethernet exactement telles qu'elles ont été transmises. Dans de tels cas, il est important que les trames quittant le tunnel soient réassemblées en une seule trame avant d'être transmises. Pour ce faire, activez le suivi des connexions netfilter (conntrack) ou chargez manuellement les modules de défragmentation netfilter de Linux à chaque extrémité du

tunnel. 
site-A:# modprobe nf_defrag_ipv4
site-B:# modprobe
nf_defrag_ipv4

INTEROPÉRABILIT

É

Les tunnels L2TPv3 non gérés (statiques) sont pris en charge par certains fabricants d'équipements réseau tels que

Cisco.

Dans Linux, les messages Hello L2TP ne sont pas pris en charge dans les tunnels non gérés. Les messages Hello sont utilisés par les clients et les serveurs L2TP pour détecter les pannes de lien afin d'automatiser la déconnexion et la réétablissement des tunnels dynamiques. Si un pair non-Linux prend en charge les messages Hello dans les tunnels non gérés, il doit être désactivé pour assurer l'interopérabilité avec

Linux.

Linux utilise par défaut le type Default Layer2SpecificHeader tel que défini dans la spécification du pro

tocole L2TPv3, RFC3931. Ce paramètre doit être cohérent avec celui configuré au niveau du pair. Certaines
implémentations de fabricants (par ex. Cisco) utilisent par défaut un type Layer2SpecificHeader de None.
