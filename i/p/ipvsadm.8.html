DESCRIPTION Ipvsadm(8) est utilisé pour configurer, maintenour inspecter la table des serveurs virtuels dans le noyau Linux. Le serveur virtuel Linux peut être utilisé pour construire des services réseau évolutifs basés sur un cluster de deux nœuds ou plus. Le nœud actif du cluster redirige les requêtes de service vers un ensemble d'hôtes serveurs qui effectueront réellement les services. Les fonctionnalités prises en charge incluent trois protocoles (TCP, UDP et SCTP), trois méthodes de transfert de paquets (NAT, tunneling et routage direct) et huit algorithmes de répartition de charge (round robin, round robin pondéré, moins de connexions, moins de connexions pondéré, moins de connexions basé sur la localité, moins de connexions basé sur la localité avec réplication, hachage de destination et hachage de source).
La commande possède deux formats d'exécution de base :ipvsadm
COMMAND virtual-service[ scheduling-method ] [ [[77 ]] options de persistance
] ipvsadm command virtual-service server-address
[ packet-forwarding-method ] [
options de pondération ] Le premier format manipule un service virtuel et l'algorithme d'attribution des requêtes de service aux serveurs réels. Une valeur de timeout de persistance et un masque réseau pour la granularité d'un service persistant ainsi qu'un moteur de persistance peuvent éventuellement être spécifiés. Le second format manipule un serveur réel associé à un service virtuel existant. Lors de la spécification d'un serveur réel, la méthode de transfert de paquets et le poids du serveur réel, par rapport aux autres serveurs réels du service virtuel, peuvent être spécifiés, sinon les valeurs par défaut seront utilisées.

-s, --scheduler scheduling-method scheduling-method Algorithme d'allocation des connexions TCP et des datagrammes UDP aux serveurs réels. Les algorithmes d'ordonnancement sont implémentés sous forme de modules du noyau. Dix sont fournis avec le Linux Virtual Server :

rr
- Round Robin (tourniquet) : répartit les tâches également entre les serveurs réels disponibles. wrr - Weighted Round Robin (tourniquet pondéré) : attribue les tâches aux serveurs réels proportionnellement au poids de ces serveurs réels. lc

wlc

PARAMÈTRES POUR LE DÉMON DE SYNCHRONISATION

L'option --start-daemon requiert zéro ou plusieurs des paramètres suivants.

--syncid syncid
Spécifier le syncid que le démon maître de synchronisation remplit dans l'en-tête SyncID lors de l'envoi de messages multicast, ou que le démon esclave de synchronisation utilise pour filtrer les messages multicast ne correspondant pas à la valeur SyncID. Les valeurs valides de syncid vont de 0 à 255. La valeur par défaut est 0, ce qui signifie aucun filtrage du tout.
--sync-maxlen length
Spécifier la longueur souhaitée des messages de synchronisation (taille de la charge utile UDP). On s'attend à ce que le serveur esclave utilise une valeur non inférieure à celle utilisée par le serveur maître. Les valeurs valides de length se situent dans la plage 1 .. (65535 - 20 - 8) mais le noyau garantit un espace pour au moins un message de synchronisation. Si la valeur est inférieure au MTU, les messages de synchronisation seront fragmentés par la couche IP. La valeur par défaut est dérivée de la valeur MTU lorsque le démon est démarré, mais le démon maître ne dépassera pas par défaut la valeur 1500 pour des raisons de compatibilité.
--mcast-interface interface
Spécifier l'interface multicast par laquelle le démon maître de synchronisation envoie les multicasts sortants, ou à laquelle le démon esclave de synchronisation écoute les multicasts.
--mcast-group address
Spécifier l'adresse multicast IPv4 ou IPv6 pour les messages de synchronisation. La valeur par défaut est 224.0.0.81.
--mcast-port port
Spécifier le port UDP pour les messages de synchronisation. La valeur par défaut est 8848.
--mcast-ttl ttl
Spécifier la valeur TTL pour les messages de synchronisation (1 .. 255). La valeur par défaut est 1.

EXEMPLE 1 - Service Virtuel Simple

Les commandes suivantes configurent un Linux Director pour distribuer les requêtes entrantes adressées au port 80 sur 207.175.44.110 également au port 80 sur cinq serveurs réels. La méthode de transfert utilisée dans cet exemple est NAT, chaque serveur réel étant masqué par le Linux Director.

ipvsadm -A -t 207.175.44.110:80 -s rr
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.1:80 -m
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.2:80 -m
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.3:80 -m
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.4:80 -m
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.5:80 -m

Alternativement, cela pourrait être réalisé en une seule commande ipvsadm.

echo "
-A -t 207.175.44.110:80 -s rr
-a -t 207.175.44.110:80 -r 192.168.10.1:80 -m
-a -t 207.175.44.110:80 -r 192.168.10.2:80 -m
-a -t 207.175.44.110:80 -r 192.168.10.3:80 -m
-a -t 207.175.44.110:80 -r 192.168.10.4:80 -m
-a -t 207.175.44.110:80 -r 192.168.10.5:80 -m
" | ipvsadm -R

Comme le masquage est utilisé comme mécanisme de transfert dans cet exemple, la route par défaut des serveurs réels doit être définie vers le linux director, qui devra être configuré pour transférer et masquer les paquets. Cela peut être réalisé à l'aide des commandes suivantes :

echo "1" > /proc/sys/net/ipv4/ip_forward

EXEMPLE 2 - Service Virtuel Firewall-Mark

Les commandes suivantes configurent un Linux Director pour distribuer les requêtes entrantes adressées à n'importe quel port sur 207.175.44.110 ou 207.175.44.111 également au port correspondant sur cinq serveurs réels. Comme dans l'exemple précédent, la méthode de transfert utilisée dans cet exemple est NAT, chaque serveur réel étant masqué par le Linux Director.

ipvsadm -A -f 1  -s rr
ipvsadm -a -f 1 -r 192.168.10.1:0 -m
ipvsadm -a -f 1 -r 192.168.10.2:0 -m
ipvsadm -a -f 1 -r 192.168.10.3:0 -m
ipvsadm -a -f 1 -r 192.168.10.4:0 -m
ipvsadm -a -f 1 -r 192.168.10.5:0 -m

Comme le masquage est utilisé comme mécanisme de transfert dans cet exemple, la route par défaut des serveurs réels doit être définie vers le linux director, qui devra être configuré pour transférer et masquer les paquets. Le serveur réel devrait également être configuré pour marquer les paquets entrants adressés à n'importe quel port sur 207.175.44.110 et 207.175.44.111 avec le firewall-mark 1. Si le trafic FTP doit être traité par ce service virtuel, alors le module noyau ip_vs_ftp doit être inséré dans le noyau. Ces opérations peuvent être réalisées à l'aide des commandes suivantes :

echo "1" > /proc/sys/net/ipv4/ip_forward
modprobe ip_tables
iptables  -A PREROUTING -t mangle -d 207.175.44.110/31 -j MARK --set-mark 1
modprobe ip_vs_ftp

EXEMPLE 3 - Service Virtuel avec Tunneling GUE

Les commandes suivantes configurent un Linux Director pour distribuer les requêtes entrantes adressées au port 80 sur 207.175.44.110 également au port 80 sur cinq serveurs réels. La méthode de transfert utilisée dans cet exemple est le tunneling avec encapsulation gue.

ipvsadm -A -t 207.175.44.110:80 -s rr
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.1:80 -i --tun-type gue --tun-port 6080 --tun-nocsum
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.2:80 -i --tun-type gue --tun-port 6080 --tun-csum
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.3:80 -i --tun-type gue --tun-port 6080 --tun-remcsum
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.4:80 -i --tun-type gue --tun-port 6078
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.5:80 -i --tun-type gue --tun-port 6079

Alternativement, cela pourrait être réalisé en une seule commande ipvsadm.

echo "
-A -t 207.175.44.110:80 -s rr
-a -t 207.175.44.110:80 -r 192.168.10.1:80 -i --tun-type gue --tun-port 6080 --tun-nocsum
-a -t 207.175.44.110:80 -r 192.168.10.2:80 -i --tun-type gue --tun-port 6080 --tun-csum
-a -t 207.175.44.110:80 -r 192.168.10.3:80 -i --tun-type gue --tun-port 6080 --tun-remcsum
-a -t 207.175.44.110:80 -r 192.168.10.4:80 -i --tun-type gue --tun-port 6078
-a -t 207.175.44.110:80 -r 192.168.10.5:80 -i --tun-type gue --tun-port 6079
" | ipvsadm -R

EXEMPLE 4 - Service Virtuel avec Tunneling GRE

Les commandes suivantes configurent un Linux Director pour utiliser l'encapsulation GRE.

ipvsadm -A -t 10.0.0.1:80 -s rr
ipvsadm -a -t 10.0.0.1:80 -r 192.168.11.1:80 -i --tun-type gre --tun-csum

IPv6

Les adresses IPv6 doivent être entourées de crochets ([ et ]).

ipvsadm -A -t [2001:db8::80]:80 -s rr
ipvsadm -a -t [2001:db8::80]:80 -r [2001:db8::a0a0]:80 -m

Les services fwmark IPv6 nécessitent l'option -6.

NOTES

Le Linux Virtual Server implémente trois stratégies de défense contre certains types d'attaques par déni de service (DoS). Le Linux Director crée une entrée pour chaque connexion afin de conserver son état, et chaque entrée occupe 128 octets de mémoire effective. La vulnérabilité de LVS à une attaque DoS réside dans la possibilité d'augmenter le nombre d'entrées autant que possible jusqu'à ce que le linux director manque de mémoire. Les trois stratégies de défense contre l'attaque sont : Abandonner aléatoirement certaines entrées du tableau. Abandonner 1/rate paquets avant de les transférer. Et utiliser un tableau de transition d'état tcp sécurisé et des timeouts courts. Les stratégies sont contrôlées par les variables sysctl et les entrées correspondantes dans le système de fichiers /proc :

/proc/sys/net/ipv4/vs/drop_entry /proc/sys/net/ipv4/vs/drop_packet /proc/sys/net/ipv4/vs/secure_tcp

Les valeurs valides pour chaque variable vont de 0 à 3. La valeur par défaut est 0, ce qui désactive la stratégie de défense respective. 1 et 2 sont des modes automatiques - lorsqu'il n'y a pas assez de mémoire disponible, la stratégie respective sera activée et la variable est automatiquement définie à 2, sinon la stratégie est désactivée et la variable est définie à 1. Une valeur de 3 indique que la stratégie respective est toujours activée. Le seuil de mémoire disponible et les temporisations TCP sécurisées peuvent être réglés à l'aide des variables sysctl et des entrées correspondantes dans le système de fichiers /proc :

/proc/sys/net/ipv4/vs/amemthresh /proc/sys/net/ipv4/vs/timeout_*
