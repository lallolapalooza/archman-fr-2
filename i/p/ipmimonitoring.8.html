NOM

ipmi-sensors - afficher les informations des capteurs IPMI

SYNOPSIS

ipmi-sensors [OPTION...]

DESCRIPTION

Ipmi-sensors affiche les lectures actuelles des capteurs et les informations du référentiel de données des capteurs (SDR). L'affichage par défaut montre l'ID d'enregistrement de chaque capteur, le nom du capteur, le nom du type de capteur, la lecture du capteur (si approprié) et l'événement actuel du capteur. Des informations plus détaillées peuvent être trouvées en utilisant les options verbeuses spécifiées ci-dessous. Ipmi-sensors n'informe pas l'utilisateur si un problème existe avec un capteur particulier car les lectures et les événements des capteurs ne sont pas analysés par défaut. Les utilisateurs peuvent souhaiter utiliser l'option --output-sensor-state pour afficher l'état analysé du capteur. Certains capteurs peuvent avoir une lecture de capteur ou un événement de capteur de "N/A" si l'information n'est pas disponible. Ceci est typique d'un capteur qui n'est pas activé ou qui n'est pas possédé par un BMC. Veuillez consulter l'option --bridge-sensors ci-dessous pour gérer les capteurs non possédés par un BMC. Les capteurs peuvent afficher un événement de capteur de "Unknown" si la lecture du capteur ne peut pas être lue. Ceci est typique d'un capteur occupé ou d'une lecture qui ne peut pas être calculée. Si les capteurs signalent "Unrecognized State", cela indique un type de capteur inconnu, généralement un capteur OEM. Si l'interprétation OEM du capteur est disponible, l'option --interpret-oem-data peut permettre de signaler l'état approprié du capteur. Les capteurs n'ont pas toujours besoin de signaler un événement de capteur. Lorsqu'un événement de capteur n'est pas présent, "OK" est généralement signalé.

Ci-dessous sont listées les options générales IPMI, les options spécifiques à l'outil, les informations de dépannage, les informations de contournement, les exemples et les problèmes connus. Pour une introduction générale à FreeIPMI, veuillez consulter freeipmi(7). Pour configurer les capteurs IPMI, veuillez consulter ipmi-config(8). Pour effectuer une gestion avancée du SDR, veuillez consulter bmc-device(8).

OPTIONS GÉNÉRALES

Les options suivantes sont des options générales pour configurer la communication IPMI et exécuter des commandes d'outils générales.

-D PILOTEIPMI, --driver-type=PILOTEIPMI
Spécifiez le type de pilote à utiliser au lieu de faire une sélection automatique. Les pilotes hors bande actuellement disponibles sont LAN et LAN_2_0, qui effectuent respectivement IPMI 1.5 et IPMI 2.0. Les pilotes en bande actuellement disponibles sont KCS, SSIF, OPENIPMI, SUNBMC et INTELDCMI.
--disable-auto-probe
Ne pas sonder les périphériques IPMI en bande pour les paramètres par défaut.
--driver-address=ADRESSEDUPILOTE
Spécifiez l'adresse du pilote en bande à utiliser au lieu de la valeur sondée. ADRESSEDUPILOTE doit être préfixée par "0x" pour une valeur hexadécimale et '0' pour une valeur octale.
--driver-device=PÉRIPHÉRIQUE
Spécifiez le chemin du périphérique du pilote en bande à utiliser au lieu du chemin sondé.
--register-spacing=ESPACEMENTDESREGISTRES
Spécifiez l'espacement des registres du pilote en bande au lieu de la valeur sondée. L'argument est en octets (c'est-à-dire, espacement des registres 32 bits = 4)
--target-channel-number=NUMÉRODECANAL
Spécifiez le numéro de canal cible du pilote en bande auquel envoyer les requêtes IPMI.
--target-slave-address=ADRESSESCLAVE
Spécifiez le numéro d'esclave cible du pilote en bande auquel envoyer les requêtes IPMI.
-h HÔTEIPMI1,HÔTEIPMI2,..., --hostname=HÔTEIPMI1[:PORT],HÔTEIPMI2[:PORT],...
Spécifiez les hôtes distants avec lesquels communiquer. Plusieurs noms d'hôtes peuvent être séparés par une virgule ou spécifiés sous forme de plage; voir le SUPPORT DES PLAGES D'HÔTES ci-dessous. Un port optionnel peut être spécifié avec chaque hôte, ce qui peut être utile dans des situations de redirection de port ou similaires. Si vous spécifiez une adresse IPv6 et un port, utilisez le format [ADRESSE]:PORT.
-u NOMDUTILISATEUR, --username=NOMDUTILISATEUR
Spécifiez le nom d'utilisateur à utiliser lors de l'authentification auprès de l'hôte distant. S'il n'est pas spécifié, un nom d'utilisateur nul (c'est-à-dire anonyme) est supposé. L'utilisateur doit avoir au moins les privilèges OPÉRATEUR pour que cet outil fonctionne pleinement.
-p MOTDEPASSE, --password=MOTDEPASSE
Spécifiez le mot de passe à utiliser lors de l'authentification auprès de l'hôte distant. S'il n'est pas spécifié, un mot de passe nul est supposé. La longueur maximale du mot de passe est de 16 pour IPMI 1.5 et de 20 pour IPMI 2.0.
-P, --password-prompt
Demandez le mot de passe pour éviter la possibilité de le lister dans les listes de processus.
-k CLÉK_G, --k-g=CLÉK_G
Spécifiez la clé K_g du BMC à utiliser lors de l'authentification auprès de l'hôte distant pour IPMI 2.0. S'il n'est pas spécifié, une clé nulle est supposée. Pour saisir la clé sous forme hexadécimale, préfixez la chaîne par '0x'. Par exemple, la clé 'abc' peut être saisie avec la chaîne 'abc' ou la chaîne '0x616263'.
-K, --k-g-prompt
Demandez la clé k-g pour éviter la possibilité de la lister dans les listes de processus.
--session-timeout=MILLISECONDES
Spécifiez le délai d'expiration de session en millisecondes. Par défaut, 20000 millisecondes (20 secondes) si non spécifié.
--retransmission-timeout=MILLISECONDES
Spécifiez le délai d'expiration de retransmission des paquets en millisecondes. Par défaut, 1000 millisecondes (1 seconde) si non spécifié. Le délai d'expiration de retransmission ne peut pas être supérieur au délai d'expiration de session.
-a TYPE_AUTHENTIFICATION, --authentication-type=TYPE_AUTHENTIFICATION
Spécifiez le type d'authentification IPMI 1.5 à utiliser. Les types d'authentification actuellement disponibles sont NONE, STRAIGHT_PASSWORD_KEY, MD2 et MD5. Par défaut, MD5 si non spécifié.
-I ID_SUITE_CHIFFREMENT, --cipher-suite-id=ID_SUITE_CHIFFREMENT
Spécifiez l'ID de la suite de chiffrement IPMI 2.0 à utiliser. L'ID de la suite de chiffrement identifie un ensemble d'algorithmes d'authentification, d'intégrité et de confidentialité à utiliser pour la communication IPMI 2.0. L'algorithme d'authentification identifie l'algorithme à utiliser pour la configuration de la session, l'algorithme d'intégrité identifie l'algorithme à utiliser pour les signatures de paquets de session, et l'algorithme de confidentialité identifie l'algorithme à utiliser pour le chiffrement de la charge utile. Par défaut, l'ID de la suite de chiffrement 3 si non spécifié. Les ID de suite de chiffrement suivants sont actuellement pris en charge :

0 - Algorithme d'authentification = Aucun; Algorithme d'intégrité = Aucun; Algorithme de confidentialité = Aucun

1 - Algorithme d'authentification = HMAC-SHA1; Algorithme d'intégrité = Aucun; Algorithme de confidentialité = Aucun

2 - Algorithme d'authentification = HMAC-SHA1; Algorithme d'intégrité = HMAC-SHA1-96; Algorithme de confidentialité = Aucun

3 - Algorithme d'authentification = HMAC-SHA1; Algorithme d'intégrité = HMAC-SHA1-96; Algorithme de confidentialité = AES-CBC-128

6 - Algorithme d'authentification = HMAC-MD5; Algorithme d'intégrité = Aucun; Algorithme de confidentialité = Aucun

7 - Algorithme d'authentification = HMAC-MD5; Algorithme d'intégrité = HMAC-MD5-128; Algorithme de confidentialité = Aucun

8 - Algorithme d'authentification = HMAC-MD5; Algorithme d'intégrité = HMAC-MD5-128; Algorithme de confidentialité = AES-CBC-128

11 - Algorithme d'authentification = HMAC-MD5; Algorithme d'intégrité = MD5-128; Algorithme de confidentialité = Aucun

12 - Algorithme d'authentification = HMAC-MD5; Algorithme d'intégrité = MD5-128; Algorithme de confidentialité = AES-CBC-128

15 - Algorithme d'authentification = HMAC-SHA256; Algorithme d'intégrité = Aucun; Algorithme de confidentialité = Aucun

16 - Algorithme d'authentification = HMAC-SHA256; Algorithme d'intégrité = HMAC_SHA256_128; Algorithme de confidentialité = Aucun

17 - Algorithme d'authentification = HMAC-SHA256; Algorithme d'intégrité = HMAC_SHA256_128; Algorithme de confidentialité = AES-CBC-128

-l NIVEAU_PRIVILÈGE, --privilege-level=NIVEAU_PRIVILÈGE
-NIVEAU
Spécifie le niveau de privilège à utiliser. Les niveaux de privilège actuellement disponibles sont USER, OPERATOR et ADMIN. Par défaut, OPERATOR est utilisé si rien n'est spécifié.
--config-file=FICHIER
Spécifie un fichier de configuration alternatif.
-W CORRECTIFS, --workaround-flags=CORRECTIFS
Spécifie les contournements pour les problèmes de conformité des fournisseurs. Plusieurs correctifs peuvent être spécifiés, séparés par des virgules. Une valeur spéciale "none" indiquera l'absence de correctifs (peut être utile pour remplacer les valeurs par défaut configurées). Voir CORRECTIFS ci-dessous pour la liste des correctifs disponibles.
--debug
Active le débogage.
-?, --help
Affiche une liste d'aide et quitte.
--usage
Affiche un message d'utilisation et quitte.
-V, --version
Affiche la version du programme et quitte.

OPTIONS IPMI-SENSORS

Les options suivantes sont spécifiques à ipmi-sensors.

-v, --verbose
Affiche une sortie détaillée des capteurs. Cette option affichera des informations supplémentaires sur les capteurs telles que les seuils, les plages, les numéros et les codes de type d'événement/lecture.
-vv
Affiche une sortie très détaillée des capteurs. Cette option affichera plus d'informations que l'option verbose, telles que des informations sur les événements, d'autres types de capteurs et les capteurs OEM.
-i, --sdr-info
Affiche les informations du dépôt de données des capteurs (SDR)
-q, --quiet-readings
Ne pas afficher par défaut les valeurs de lecture des capteurs. Cette option est particulièrement utile si vous souhaitez utiliser une sortie multi-hôtes sur un cluster et voulez consolider la sortie.
-r LISTE-DE-RECORD-IDS, --record-ids=LISTE-DE-RECORD-IDS
Spécifie les capteurs à afficher par identifiant de record. Plusieurs identifiants de record peuvent être séparés par des virgules ou des espaces. Si à la fois --record-ids et --sensor-types sont spécifiés, --record-ids a la priorité. Un identifiant de record spécial "all" indiquera que tous les identifiants de record doivent être affichés (peut être utile pour remplacer les valeurs par défaut configurées).
-R LISTE-DE-RECORD-IDS, --exclude-record-ids=LISTE-DE-RECORD-IDS
Spécifie les capteurs à ne pas afficher par identifiant de record. Plusieurs identifiants de record peuvent être séparés par des virgules ou des espaces. Un identifiant de record spécial "none" indiquera qu'aucun identifiant de record ne doit être exclu (peut être utile pour remplacer les valeurs par défaut configurées).
-t LISTE-DE-TYPES-DE-CAPTEURS, --sensor-types=LISTE-DE-TYPES-DE-CAPTEURS
Spécifie les types de capteurs pour lesquels afficher les sorties. Plusieurs types peuvent être séparés par des virgules ou des espaces. Si à la fois --record-ids et --sensor-types sont spécifiés, --record-ids a la priorité. Un type spécial "all" indiquera que tous les types doivent être affichés (peut être utile pour remplacer les valeurs par défaut configurées). Les utilisateurs peuvent spécifier les types de capteurs par chaîne de caractères (voir --list-sensor-types ci-dessous) ou par nombre (décimal ou hexadécimal).
-T LISTE-DE-TYPES-DE-CAPTEURS, --exclude-sensor-types=LISTE-DE-TYPES-DE-CAPTEURS
Spécifie les types de capteurs pour lesquels ne pas afficher les sorties. Plusieurs types peuvent être séparés par des virgules ou des espaces. Un type spécial "none" indiquera qu'aucun type ne doit être exclu (peut être utile pour remplacer les valeurs par défaut configurées). Les utilisateurs peuvent spécifier les types de capteurs par chaîne de caractères (voir --list-sensor-types ci-dessous) ou par nombre (décimal ou hexadécimal).
-L, --list-sensor-types
Liste les types de capteurs.
-b, --bridge-sensors
Par défaut, les lectures des capteurs ne sont pas tentées pour les capteurs dont le propriétaire n'est pas le BMC. En définissant cette option, les requêtes de capteurs peuvent être relayées vers des propriétaires non-BMC pour obtenir les lectures des capteurs. Le relais peut ne pas fonctionner sur certains types d'interfaces/pilotes.
--shared-sensors
Certains capteurs partagent le même enregistrement de données de capteur (SDR). Cela est généralement utilisé pour les entrées du journal des événements système (SEL) et non pour les lectures de capteurs. Cependant, il peut y avoir certaines cartes mères où ce format est utilisé pour plusieurs capteurs actifs, ou l'utilisateur souhaite simplement voir la permutation des entrées partagées par une entrée SDR. En définissant cette option, chaque numéro de capteur partagé par un record sera itéré et affiché.
--interpret-oem-data
Tente d'interpréter les données OEM, telles que les données d'événement, les lectures de capteurs ou des informations générales supplémentaires, etc. Si une interprétation OEM n'est pas disponible, la sortie par défaut sera générée. La justesse des interprétations OEM ne peut être garantie en raison des changements potentiels que les fournisseurs OEM peuvent apporter aux produits, au microprogramme, etc. Voir INTERPRÉTATION OEM ci-dessous pour les interprétations de cartes mères confirmées et prises en charge.
--ignore-not-available-sensors
Ignore les capteurs non disponibles (c'est-à-dire N/A) dans la sortie.
--ignore-unrecognized-events
Ignore les événements de capteurs non reconnus. Cela supprimera la sortie des événements non reconnus, généralement affichés comme 'Unrecognized Event = XXXXh' dans la sortie. De plus, les événements non reconnus seront ignorés lors du calcul de l'état du capteur avec --output-sensor-state ci-dessous.
--output-event-bitmask
Affiche la valeur du masque de bits de l'événement au lieu de la représentation sous forme de chaîne.
--output-sensor-state
Affiche l'état du capteur dans la sortie. Cela ajoutera une sortie supplémentaire indiquant si un capteur est dans un état NOMINAL, WARNING ou CRITICAL. L'état du capteur est une valeur interprétée basée sur l'événement actuel du capteur. Les interprétations de l'état du capteur sont déterminées par le fichier de configuration /etc/freeipmi//freeipmi_interpret_sensor.conf. Voir freeipmi_interpret_sensor.conf(5) pour plus d'informations. Cette option donne une sortie identique à l'état du capteur précédemment affiché par ipmimonitoring(8).
--sensor-state-config-file=FICHIER
Spécifie un fichier de configuration d'état de capteur alternatif. Option ignorée si --output-sensor-state n'est pas spécifié.
--entity-sensor-names
Affiche les noms des capteurs préfixés par leur identifiant d'entité et leur numéro d'instance lorsque c'est approprié. Cela peut être nécessaire sur certaines cartes mères pour aider à identifier les capteurs auxquels il est fait référence. Par exemple, une carte mère peut avoir plusieurs capteurs nommés 'TEMP'. L'identifiant d'entité et le numéro d'instance peuvent aider à clarifier quel capteur fait référence au "Processor 1" par rapport au "Processor 2".
--output-sensor-thresholds
Affiche les seuils des capteurs dans la sortie. Cela ajoutera des colonnes à la sortie par défaut pour les seuils non récupérables inférieurs, critiques inférieurs, non critiques inférieurs, non critiques supérieurs, critiques supérieurs et non récupérables supérieurs.
--no-sensor-type-output
N'affiche pas le type de capteur pour chaque entrée. Sur de nombreux systèmes, le type de capteur est redondant avec le nom du capteur. Cela peut être particulièrement vrai si --entity-sensor-names est spécifié. Si le nom du capteur est suffisant, ou si le type de capteur n'est d'aucun intérêt pour l'utilisateur, cette option peut être spécifiée pour condenser la sortie.
--comma-separated-output
Affiche les champs au format séparé par des virgules.
--no-header-output
N'affiche pas les en-têtes de colonnes. Peut être utile dans les scripts.
--non-abbreviated-units
Affiche les unités non abrégées (par ex. 'Amps' au lieu de 'A'). Peut aider à désambiguïser les unités (par ex. 'C' pour Celsius ou Coulombs).
--legacy-output
Affiche au format hérité. Les options plus récentes peuvent ne pas être applicables à la sortie héritée.
--ipmimonitoring-legacy-output
Affiche au format hérité de l'outil hérité ipmimonitoring . Les options plus récentes peuvent ne pas être applicables à la sortie héritée.

OPTIONS DE CACHE SDR

Cet outil nécessite l'accès au cache du dépôt de données des capteurs (SDR) pour un fonctionnement général. Par défaut, les données SDR seront téléchargées et mises en cache sur la machine locale. Les options suivantes s'appliquent au cache SDR.

--flush-cache
Vide la version en cache du cache du dépôt de données des capteurs (SDR). Le SDR est généralement mis en cache pour un accès ultérieur plus rapide. Cependant, il peut être nécessaire de le vider et de le régénérer si le SDR a été mis à jour sur un système.
--quiet-cache
N'affiche pas d'informations sur la création/suppression du cache. Peut être utile dans les scripts.
--sdr-cache-recreate
Si le cache SDR est périmé ou invalide, recrée automatiquement le cache du dépôt de données des capteurs (SDR). Cette option peut être utile à des fins de script.
--sdr-cache-file=FICHIER
Spécifie un fichier de cache du dépôt de données des capteurs (SDR) spécifique à utiliser pour le stockage ou la lecture. Si cette option est utilisée lorsque plusieurs hôtes sont spécifiés, le même fichier de cache SDR sera utilisé pour tous les hôtes.
--sdr-cache-directory=RÉPERTOIRE
Spécifie un répertoire alternatif où les caches du dépôt de données des capteurs (SDR) doivent être stockés ou lus. Par défaut, le répertoire personnel est utilisé si rien n'est spécifié.

OPTIONS DE TEMPS

Par définition IPMI, toutes les heures et horodatages IPMI sont stockés en heure locale. Cependant, dans de nombreuses situations, les horodatages ne seront pas stockés en heure locale. Le fait qu'un système stocke ou non les horodatages en heure locale dépend de nombreux facteurs, tels que le fournisseur, le BIOS et le système d'exploitation. Les options suivantes permettront à l'utilisateur d'ajuster l'interprétation des horodatages stockés et la manière dont ils doivent être affichés.

--utc-to-localtime
Suppose que toutes les heures sont rapportées en temps UTC et convertit l'heure en heure locale avant de l'afficher.
--localtime-to-utc
Convertit tous les horodatages en heure locale en temps UTC avant de les afficher.
--utc-offset=SECONDES
Spécifie un décalage UTC spécifique en secondes à ajouter aux horodatages. La valeur peut varier de -86400 à 86400 secondes. La valeur par défaut est 0.

OPTIONS HOSTRANGED

Les options suivantes manipulent la sortie hostranged. Voir le SUPPORT HOSTRANGED ci-dessous pour des informations supplémentaires sur les hostranges.

-B, --buffer-output
Met en mémoire tampon la sortie hostranged. Pour chaque nœud, met en mémoire tampon la sortie standard jusqu'à ce que le nœud ait terminé son opération IPMI. Lorsque cette option est spécifiée, les données peuvent apparaître plus lentement à l'utilisateur car l'opération IPMI entière doit être terminée avant que toute donnée puisse être affichée. Voir le SUPPORT HOSTRANGED ci-dessous pour des informations supplémentaires.
-C, --consolidate-output
Consolide la sortie hostranged. La sortie standard complète de chaque nœud spécifié sera consolidée de sorte que les nœuds avec une sortie identique ne soient pas affichés deux fois. Un en-tête listera les nœuds avec la sortie consolidée. Lorsque cette option est spécifiée, aucune sortie ne peut être vue tant que les opérations IPMI sur tous les nœuds ne sont pas terminées. Si l'utilisateur interrompt le programme prématurément, toute la sortie consolidée actuellement sera déversée. Voir le SUPPORT HOSTRANGED ci-dessous pour des informations supplémentaires.
-F NUM, --fanout=NUM
Spécifie le fanout de plusieurs hôtes. Un algorithme de "fenêtre glissante" (ou fanout) est utilisé pour la communication parallèle IPMI de sorte que les nœuds lents ou les nœuds ayant expiré ne ralentissent pas la communication parallèle. Le nombre maximum de threads disponibles en même temps est limité par le fanout. La valeur par défaut est 64.
-E, --eliminate
Élimine les hôtes déterminés comme non détectés par ipmidetect. Cela tente de résoudre le problème courant de dépassement de délai d'exécution de hostranged dû à la suppression de plusieurs nœuds du service dans un grand cluster. Le démon ipmidetectd doit être en cours d'exécution sur le nœud exécutant la commande.
--always-prefix
Précède toujours la sortie, même si un seul hôte est spécifié ou communique en bande. Cette option est principalement utile à des fins de script. L'option sera ignorée si elle est spécifiée avec l'option -C.

SUPPORT HOSTRANGED

Plusieurs hôtes peuvent être saisis soit sous forme de listes explicites d'hôtes séparées par des virgules, soit sous forme de plages de noms d'hôtes dans la forme générale : préfixe[n-m,l-k,...], où n < m et l < k, etc. Cette dernière forme ne doit pas être confondue avec les classes de caractères d'expression régulière (également désignées par []). Par exemple, foo[19] ne représente pas foo1 ou foo9, mais plutôt une plage dégénérée : foo19.

Cette syntaxe de plage est destinée uniquement à la commodité sur les clusters avec une convention de nommage préfixeNN et la spécification de plages ne doit pas être considérée comme nécessaire -- la liste foo1,foo9 pourrait être spécifiée comme telle, ou par la plage foo[1,9].

Voici quelques exemples d'utilisation de plages :

    foo[01-05] au lieu de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] au lieu de foo7,foo9,foo10
    foo[0-3] au lieu de foo0,foo1,foo2,foo3

Pour rappel au lecteur, certains shells interpréteront les crochets ([ et ]) pour la mise en correspondance de motifs. Selon votre shell, il peut être nécessaire d'encadrer les listes de plages entre guillemets.

Lorsque plusieurs hôtes sont spécifiés par l'utilisateur, un thread sera exécuté pour chaque hôte en parallèle jusqu'au fanout configuré (qui peut être ajusté via l'option -F). Cela permettra une communication avec un grand nombre de nœuds beaucoup plus rapidement que si elle était effectuée en série.

Par défaut, la sortie standard de chaque nœud spécifié sera affichée avec le nom d'hôte préfixé à chaque ligne. Bien que cette sortie soit lisible dans de nombreuses situations, elle peut être difficile à lire dans d'autres situations. Par exemple, la sortie de plusieurs nœuds peut être mélangée. Les options -B et -C peuvent être utilisées pour modifier ce comportement par défaut.

La communication IPMI en bande sera utilisée lorsque l'hôte "localhost" est spécifié. Cela permet à l'utilisateur d'ajouter le localhost à la sortie hostranged.

DÉPANNAGE GENERAL

Le plus souvent, les problèmes IPMI sont dus à des problèmes de configuration.

Les problèmes IPMI sur LAN impliquent une mauvaise configuration du BMC de la machine distante. Vérifiez attentivement que les éléments suivants sont correctement configurés dans le BMC de la machine distante : adresse IP, adresse MAC, masque de sous-réseau, nom d'utilisateur, activation de l'utilisateur, privilèges de l'utilisateur, mot de passe, privilèges LAN, activation LAN et types d'authentification autorisés. Pour les connexions IPMI 2.0, vérifiez attentivement que les privilèges de la suite de chiffrement et la clé K_g sont correctement configurés. L'outil ipmi-config(8) peut être utilisé pour vérifier et/ou modifier ces paramètres de configuration.

Les problèmes IPMI en bande sont généralement causés par des pilotes mal configurés ou des BMC non standard.

En plus des conseils de dépannag e ci-dessous, veuillez également consulter les SOLUTIONS DE CONTOURNEMENT ci-dessous s'il existe des bogues spécifiques au fournisseur qui ont été découverts et contournés.

Vous trouverez ci-dessous de nombreux problèmes courants pour les messages d'erreur. Pour une assistance supplémentaire, veuillez envoyer un courriel à la liste de diffusion <freeipmi-users@gnu.org>.

"username invalid" - Le nom d'utilisateur saisi (ou un nom d'utilisateur NULL s'il n'en a pas été saisi) n'est pas disponible sur la machine distante. Il est également possible que la configuration du nom d'utilisateur du BMC distant soit incorrecte.

"password invalid" - Le mot de passe saisi (ou un mot de passe NULL s'il n'en a pas été saisi) n'est pas correct. Il est également possible que le mot de passe de l'utilisateur ne soit pas correctement configuré sur le BMC distant.

"password verification timeout" - La vérification du mot de passe a expiré. Une erreur "password invalid" (décrite ci-dessus) ou une erreur générique "session timeout" (décrite ci-dessous) s'est produite. À ce stade du protocole, il ne peut pas être différencié laquelle s'est produite.

"k_g invalid" - La clé K_g saisie (ou une clé K_g NULL si aucune n'a été saisie) n'est pas correcte. Il est également possible que la clé K_g ne soit pas correctement configurée sur le BMC distant.

"privilege level insufficient" - Une commande IPMI nécessite un privilège utilisateur plus élevé que celui avec lequel vous vous êtes authentifié. Veuillez essayer de vous authentifier avec un privilège plus élevé. Cela peut nécessiter de s'authentifier auprès d'un autre utilisateur qui a un privilège maximum plus élevé.

"privilege level cannot be obtained for this user" - Le niveau de privilège que vous tentez d'utiliser pour vous authentifier est plus élevé que le maximum autorisé pour cet utilisateur. Veuillez réessayer avec un privilège inférieur. Il est également possible que le niveau de privilège maximum autorisé pour un utilisateur ne soit pas correctement configuré sur le BMC distant.

"authentication type unavailable for attempted privilege level" - Le type d'authentification que vous souhaitez utiliser pour vous authentifier n'est pas disponible pour ce niveau de privilège. Veuillez réessayer avec un type d'authentification alternatif ou un niveau de privilège alternatif. Il est également possible que les types d'authentification disponibles avec lesquels vous pouvez vous authentifier ne soient pas correctement configurés sur le BMC distant.

"cipher suite id unavailable" - L'identifiant de la suite de chiffrement que vous souhaitez utiliser pour vous authentifier n'est pas disponible sur le BMC distant. Veuillez réessayer avec un identifiant de suite de chiffrement alternatif. Il est également possible que les identifiants de suites de chiffrement disponibles ne soient pas correctement configurés sur le BMC distant.

"ipmi 2.0 unavailable" - IPMI 2.0 n'a pas été détecté sur la machine distante. Veuillez essayer d'utiliser IPMI 1.5 à la place.

"connection timeout" - La communication IPMI initiale a échoué. Un certain nombre d'erreurs potentielles sont possibles, y compris un nom d'hôte invalide spécifié, une adresse IP IPMI qui ne peut pas être résolue, IPMI n'est pas activé sur le serveur distant, la connexion réseau est mauvaise, etc. Veuillez vérifier la configuration et la connectivité.

"session timeout" - La session IPMI a expiré. Veuillez vous reconnecter. Si cette erreur se produit souvent, vous pourriez souhaiter augmenter le délai de retransmission. Certains BMC distants sont considérablement plus lents que d'autres.

"device not found" - Le périphérique spécifié n'a pas pu être trouvé. Veuillez vérifier la configuration ou les entrées et réessayer.

"driver timeout" - La communication avec le pilote ou le périphérique a expiré. Veuillez réessayer.

"message timeout" - La communication avec le pilote ou le périphérique a expiré. Veuillez réessayer.

"BMC busy" - Le BMC est actuellement occupé. Il peut être en train de traiter des informations ou avoir trop de sessions simultanées à gérer. Veuillez patienter et réessayer.

"could not find inband device" - Aucun périphérique en bande n'a pu être trouvé. Veuillez vérifier la configuration ou spécifier un périphérique ou un pilote spécifique sur la ligne de commande.

"driver timeout" - Le pilote en bande a expiré dans la communication avec le BMC local ou le processeur de service. Le BMC ou le processeur de service peut être occupé ou (dans le pire des cas) potentiellement non fonctionnel.

"internal IPMI error" - Une erreur IPMI s'est produite que FreeIPMI ne sait pas comment gérer. Veuillez envoyer un courriel à <freeipmi-users@gnu.org> pour signaler le problème.

"sensor config file parse error" - Une erreur d'analyse a été trouvée dans le fichier de configuration d'interprétation des capteurs. Veuillez consulter freeipmi_interpret_sensor.conf(5).

SOLUTIONS DE CONTOURNEMENT

Avec tant de fournisseurs différents implémentant leurs propres solutions IPMI, différents fournisseurs peuvent implémenter leurs protocoles IPMI incorrectement. Ce qui suit décrit un certain nombre de solutions de contournement actuellement disponibles pour gérer les problèmes de conformité découverts. Lorsque cela est possible, les solutions de contournement ont été implémentées de manière à être transparentes pour l'utilisateur. Cependant, certaines nécessiteront à l'utilisateur de spécifier qu'une solution de contournement doit être utilisée via l'option -W option

.

Le matériel listé ci-dessous peut simplement indiquer le matériel sur lequel un problème a été découvert. Des versions plus récentes de matériel peuvent corriger les problèmes indiqués ci-dessous. Des machines similaires provenant de différents fabricants peuvent ou non présenter les mêmes problèmes. Différents fabricants peuvent obtenir leur firmware auprès du même développeur de firmware IPMI, il peut donc être utile d'essayer les solutions de contournement listées ci-dessous même si votre carte mère n'est pas listée. Si vous pensez que votre matériel présente un problème de conformité supplémentaire nécessitant une solution de contournement, veuillez contacter les responsables de FreeIPMI sur <freeipmi-users@gnu.org> ou <freeipmi-devel@gnu.org>

assumeio - Ce drapeau de contournement supposera que les interfaces inband communiquent avec l'E/S du système plutôt que d'être mappées en mémoire. Cela contournera les systèmes qui rapportent des adresses de base invalides. Ceux qui rencontrent ce problème peuvent voir les erreurs "device not supported" ou "could not find inband device". Problème observé sur HP ProLiant DL145 G1. spinpoll - Ce drapeau de contournement informera certains pilotes inband (notamment le pilote KCS) pour qu'ils tournent en boucle lors de l'interrogation plutôt que de mettre le processus en veille. Cela peut améliorer considérablement le temps d'exécution réel des outils car la granularité du planificateur du système d'exploitation peut être beaucoup plus grande que le temps nécessaire pour effectuer une seule transaction de message IPMI. Cependant, en tournant en boucle, votre système peut effectuer moins de travail utile en ne libérant pas le contexte de l'outil pour une tâche plus

utile.

EXEMPLES

# ipmi-sensors

Affiche tous les capteurs et relevés sur la machine locale.

# ipmi-sensors --verbose

Affiche les capteurs et relevés de manière verbeuse sur la machine locale.

# ipmi-sensors --record-ids="7,11,102"

Affiche les enregistrements de capteurs 7, 11 et 102 sur la machine locale.

# ipmi-sensors --sensor-types=fan

Affiche tous les capteurs de type ventilateur sur la machine locale.

# ipmi-sensors -h ahost -u myusername -p mypassword

Affiche tous les capteurs sur une machine distante en utilisant IPMI over LAN.

# ipmi-sensors -h mycluster[0-127] -u myusername -p mypassword

Affiche tous les capteurs sur un cluster en utilisant IPMI over LAN.

DIAGNOSTICS

En cas d'exécution réussie, le code de sortie est 0. En cas d'erreur, le code de sortie est 1.

Si plusieurs hôtes sont spécifiés pour la communication, le code de sortie est 0 si et seulement si toutes les cibles s'exécutent avec succès. Sinon, le code de sortie est 1.

PROBLÈMES CONNUS

Sur les systèmes d'exploitation plus anciens, si vous saisissez votre nom d'utilisateur, votre mot de passe et d'autres informations potentiellement pertinentes pour la sécurité sur la ligne de commande, ces informations peuvent être découvertes par d'autres utilisateurs lors de l'utilisation d'outils comme la commande ps(1) ou en consultant le système de fichiers /proc. Il est généralement plus sûr de saisir les informations de mot de passe avec des options comme les options -P ou -K. Configurer les informations pertinentes pour la sécurité dans le fichier de configuration FreeIPMI serait également un moyen approprié de masquer ces informations.

Afin de prévenir les attaques par force brute, certains BMC se « verrouillent » temporairement après un certain nombre d'erreurs d'authentification à distance. Vous devrez peut-être attendre un certain temps pour que ce verrouillage temporaire soit levé avant de pouvoir vous authentifier à nouveau.

Certains capteurs peuvent être affichés comme non disponibles (c'est-à-dire N/A) car le propriétaire du capteur n'est pas le BMC. Pour tenter de faire le pont vers des capteurs et d'accéder à des capteurs qui ne sont pas sur le BMC, les utilisateurs peuvent essayer les options -b ou --bridge-sensors .
