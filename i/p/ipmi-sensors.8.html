NOM

ipmi-sensors - affiche les informations des capteurs IPMI

SYNOPSIS

ipmi-sensors [OPTION...]

DESCRIPTION

Ipmi-sensors affiche les relevés actuels des capteurs et les informations du dépôt de données des capteurs (SDR). L'affichage par défaut produit pour chaque capteur son identifiant d'enregistrement, son nom, le nom de son type, son relevé (le cas échéant) et l'événement actuel du capteur. Des informations plus détaillées peuvent être obtenues à l'aide des options de verbosité spécifiées ci-dessous. Ipmi-sensors n'informe pas l'utilisateur de l'existence d'un problème avec un capteur particulier car les relevés et les événements des capteurs ne sont pas analysés par défaut. Les utilisateurs peuvent souhaiter utiliser l'option --output-sensor-state pour afficher l'état analysé du capteur. Certains capteurs peuvent avoir un relevé ou un événement « N/A » si l'information n'est pas disponible. C'est typique d'un capteur qui n'est pas activé ou qui n'est pas géré par un BMC. Veuillez consulter l'option --bridge-sensors ci-dessous pour traiter les capteurs qui ne sont pas gérés par un BMC. Les capteurs peuvent afficher un événement « Unknown » si le relevé du capteur ne peut pas être lu. C'est typique d'un capteur occupé ou d'un relevé qui ne peut pas être calculé. Si les capteurs signalent « Unrecognized State », cela indique un type de capteur inconnu, généralement un capteur OEM. Si l'interprétation OEM du capteur est disponible, l'option --interpret-oem-data peut être capable de signaler l'état approprié du capteur. Les capteurs ne signalent pas toujours un événement. Lorsqu'un événement de capteur est absent, « OK » est généralement signalé.

Ci-dessous sont listées les options IPMI générales, les options spécifiques à l'outil, les informations de dépannage, les informations de contournement, des exemples et des problèmes connus. Pour une introduction générale à FreeIPMI, veuillez consulter freeipmi(7). Pour effectuer la configuration des capteurs IPMI, veuillez consulter ipmi-config(8). Pour effectuer une gestion avancée du SDR, veuillez consulter bmc-device(8).

OPTIONS GÉNÉRALES

Les options suivantes sont des options générales pour configurer la communication IPMI et exécuter des commandes générales de l'outil.

-D IPMIDRIVER, --driver-type=IPMIDRIVER
Spécifier le type de pilote à utiliser au lieu de faire une sélection automatique. Les pilotes hors bande actuellement disponibles sont LAN et LAN_2_0, qui réalisent respectivement IPMI 1.5 et IPMI 2.0. Les pilotes en bande actuellement disponibles sont KCS, SSIF, OPENIPMI, SUNBMC et INTELDCMI.
--disable-auto-probe
Ne pas interroger les périphériques IPMI en bande pour les paramètres par défaut.
--driver-address=DRIVER-ADDRESS
Spécifier l'adresse du pilote en bande à utiliser au lieu de la valeur interrogée. DRIVER-ADDRESS doit être préfixé par « 0x » pour une valeur hexadécimale et « 0 » pour une valeur octale.
--driver-device=DEVICE
Spécifier le chemin du périphérique du pilote en bande à utiliser au lieu du chemin interrogé.
--register-spacing=REGISTER-SPACING
Spécifier l'espacement des registres du pilote en bande au lieu de la valeur interrogée. L'argument est en octets (c'est-à-dire espacement de registre 32 bits = 4).
--target-channel-number=CHANNEL-NUMBER
Spécifier le numéro de canal cible du pilote en bande vers lequel envoyer les requêtes IPMI.
--target-slave-address=SLAVE-ADDRESS
Spécifier le numéro d'esclave cible du pilote en bande vers lequel envoyer les requêtes IPMI.
-h IPMIHOST1,IPMIHOST2,..., --hostname=IPMIHOST1[:PORT],IPMIHOST2[:PORT],...
Spécifier le ou les hôtes distants avec lesquels communiquer. Plusieurs noms d'hôtes peuvent être séparés par des virgules ou spécifiés sous forme de plage ; voir la section PRÉSENTE DE PLAGES D'HÔTES ci-dessous. Un port optionnel peut être spécifié pour chaque hôte, ce qui peut être utile dans des situations de transfert de port ou similaires. Si vous spécifiez une adresse IPv6 et un port, utilisez le format [ADDRESS]:PORT.
-u USERNAME, --username=USERNAME
Spécifier le nom d'utilisateur à utiliser lors de l'authentification avec l'hôte distant. S'il n'est pas spécifié, un nom d'utilisateur nul (c'est-à-dire anonyme) est supposé. L'utilisateur doit avoir au moins les privilèges OPERATOR pour que cet outil fonctionne pleinement.
-p PASSWORD, --password=PASSWORD
Spécifier le mot de passe à utiliser lors de l'authentification avec l'hôte distant. S'il n'est pas spécifié, un mot de passe nul est supposé. La longueur maximale du mot de passe est de 16 pour IPMI 1.5 et de 20 pour IPMI 2.0.
-P, --password-prompt
Demander le mot de passe pour éviter la possibilité de le lister dans les listes de processus.
-k K_G, --k-g=K_G
Spécifier la clé K_g du BMC à utiliser lors de l'authentification avec l'hôte distant pour IPMI 2.0. S'il n'est pas spécifié, une clé nulle est supposée. Pour saisir la clé sous forme hexadécimale, préfixez la chaîne par « 0x ». Par exemple, la clé « abc » peut être saisie avec soit la chaîne « abc », soit la chaîne « 0x616263 ».
-K, --k-g-prompt
Demander le k-g pour éviter la possibilité de le lister dans les listes de processus.
--session-timeout=MILLISECONDS
Spécifier le délai d'expiration de la session en millisecondes. Par défaut, 20000 millisecondes (20 secondes) si non spécifié.
--retransmission-timeout=MILLISECONDS
Spécifier le délai d'expiration de retransmission des paquets en millisecondes. Par défaut, 1000 millisecondes (1 seconde) si non spécifié. Le délai d'expiration de retransmission ne peut pas être supérieur au délai d'expiration de la session.
-a AUTHENTICATION-TYPE, --authentication-type=AUTHENTICATION-TYPE
Spécifier le type d'authentification IPMI 1.5 à utiliser. Les types d'authentification actuellement disponibles sont NONE, STRAIGHT_PASSWORD_KEY, MD2 et MD5. Par défaut, MD5 si non spécifié.
-I CIPHER-SUITE-ID, --cipher-suite-id=CIPHER-SUITE-ID
Spécifier l'ID de suite de chiffrement IPMI 2.0 à utiliser. L'ID de suite de chiffrement identifie un ensemble d'algorithmes d'authentification, d'intégrité et de confidentialité à utiliser pour la communication IPMI 2.0. L'algorithme d'authentification identifie l'algorithme à utiliser pour l'établissement de session, l'algorithme d'intégrité identifie l'algorithme à utiliser pour les signatures des paquets de session, et l'algorithme de confidentialité identifie l'algorithme à utiliser pour le chiffrement des charges utiles. Par défaut, l'ID de suite de chiffrement 3 si non spécifié. Les ID de suite de chiffrement suivants sont actuellement pris en charge :

0 - Algorithme d'authentification = None ; Algorithme d'intégrité = None ; Algorithme de confidentialité = None

1 - Algorithme d'authentification = HMAC-SHA1 ; Algorithme d'intégrité = None ; Algorithme de confidentialité = None

2 - Algorithme d'authentification = HMAC-SHA1 ; Algorithme d'intégrité = HMAC-SHA1-96 ; Algorithme de confidentialité = None

3 - Algorithme d'authentification = HMAC-SHA1 ; Algorithme d'intégrité = HMAC-SHA1-96 ; Algorithme de confidentialité = AES-CBC-128

6 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = None ; Algorithme de confidentialité = None

7 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = HMAC-MD5-128 ; Algorithme de confidentialité = None

8 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = HMAC-MD5-128 ; Algorithme de confidentialité = AES-CBC-128

11 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = MD5-128 ; Algorithme de confidentialité = None

12 - Algorithme d'authentification = HMAC-MD5 ; Algorithme d'intégrité = MD5-128 ; Algorithme de confidentialité = AES-CBC-128

15 - Algorithme d'authentification = HMAC-SHA256 ; Algorithme d'intégrité = None ; Algorithme de confidentialité = None

16 - Algorithme d'authentification = HMAC-SHA256 ; Algorithme d'intégrité = HMAC_SHA256_128 ; Algorithme de confidentialité = None

17 - Algorithme d'authentification = HMAC-SHA256 ; Algorithme d'intégrité = HMAC_SHA256_128 ; Algorithme de confidentialité = AES-CBC-128

-l PRIVILEGE-LEVEL, --privilege-level=PRIVILEGE-LNIVEAU
Spécifie le niveau de privilège à utiliser. Les niveaux de privilège actuellement disponibles sont USER, OPERATOR et ADMIN. Par défaut, c'est OPERATOR si rien n'est spécifié.
--config-file=FICHIER
Spécifie un fichier de configuration alternatif.
-W CORRECTIFS, --workaround-flags=CORRECTIFS
Spécifie les contournements pour les problèmes de conformité des fournisseurs. Plusieurs correctifs peuvent être spécifiés, séparés par des virgules. Une valeur spéciale « none » sur la ligne de commande indiquera qu'aucun correctif ne doit être appliqué (peut être utile pour remplacer les valeurs par défaut configurées). Voir CORRECTIFS ci-dessous pour une liste des correctifs disponibles.
--debug
Active le débogage.
-?, --help
Affiche une liste d'aide et se termine.
--usage
Affiche un message d'utilisation et se termine.
-V, --version
Affiche la version du programme et se termine.

OPTIONS IPMI-SENSORS

Les options suivantes sont spécifiques à ipmi-sensors.

-v, --verbose
Affiche une sortie détaillée des capteurs. Cette option affichera des informations supplémentaires sur les capteurs telles que les seuils, les plages, les numéros et les codes de type d'événement/lecture.
-vv
Affiche une sortie très détaillée des capteurs. Cette option affichera plus d'informations que l'option verbose, telles que des informations sur les événements, d'autres types de capteurs et les capteurs OEM.
-i, --sdr-info
Affiche les informations du dépôt de données des capteurs (SDR)
-q, --quiet-readings
Ne pas afficher par défaut les valeurs de lecture des capteurs. Cette option est particulièrement utile si vous souhaitez utiliser une sortie multi-hôtes sur un cluster et voulez consolider la sortie.
-r LISTE-ID-ENREGISTREMENT, --record-ids=LISTE-ID-ENREGISTREMENT
Spécifie les capteurs à afficher par identifiant d'enregistrement. Plusieurs identifiants peuvent être séparés par des virgules ou des espaces. Si à la fois --record-ids et --sensor-types sont spécifiés, --record-ids a la priorité. Un identifiant d'enregistrement spécial « all » sur la ligne de commande indiquera que tous les identifiants doivent être affichés (peut être utile pour remplacer les valeurs par défaut configurées).
-R LISTE-ID-ENREGISTREMENT, --exclude-record-ids=LISTE-ID-ENREGISTREMENT
Spécifie les capteurs à ne pas afficher par identifiant d'enregistrement. Plusieurs identifiants peuvent être séparés par des virgules ou des espaces. Un identifiant d'enregistrement spécial « none » sur la ligne de commande indiquera qu'aucun identifiant ne doit être exclu (peut être utile pour remplacer les valeurs par défaut configurées).
-t LISTE-TYPE-CAPTEUR, --sensor-types=LISTE-TYPE-CAPTEUR
Spécifie les types de capteurs pour lesquels afficher les sorties. Plusieurs types peuvent être séparés par des virgules ou des espaces. Si à la fois --record-ids et --sensor-types sont spécifiés, --record-ids a la priorité. Un type spécial « all » sur la ligne de commande indiquera que tous les types doivent être affichés (peut être utile pour remplacer les valeurs par défaut configurées). Les utilisateurs peuvent spécifier les types de capteurs par chaîne (voir --list-sensor-types ci-dessous) ou par nombre (décimal ou hexadécimal).
-T LISTE-TYPE-CAPTEUR, --exclude-sensor-types=LISTE-TYPE-CAPTEUR
Spécifie les types de capteurs pour lesquels ne pas afficher les sorties. Plusieurs types peuvent être séparés par des virgules ou des espaces. Un type spécial « none » sur la ligne de commande indiquera qu'aucun type ne doit être exclu (peut être utile pour remplacer les valeurs par défaut configurées). Les utilisateurs peuvent spécifier les types de capteurs par chaîne (voir --list-sensor-types ci-dessous) ou par nombre (décimal ou hexadécimal).
-L, --list-sensor-types
Liste les types de capteurs.
-b, --bridge-sensors
Par défaut, aucune tentative n'est faite pour lire les capteurs appartenant à des entités autres que le BMC. En définissant cette option, les requêtes de capteurs peuvent être relayées vers des entités autres que le BMC pour obtenir les lectures des capteurs. Le relais peut ne pas fonctionner sur certains types d'interfaces/pilotes.
--shared-sensors
Certains capteurs partagent le même enregistrement de données de capteur (SDR). Cela est généralement utilisé pour les entrées du journal des événements système (SEL) et non pour les lectures de capteurs. Cependant, certaines cartes mères peuvent utiliser ce format pour plusieurs capteurs actifs, ou l'utilisateur souhaite simplement voir la permutation des entrées partagées par une entrée SDR. En définissant cette option, chaque numéro de capteur partagé par un enregistrement sera itéré et affiché.
--interpret-oem-data
Tente d'interpréter les données OEM, telles que les données d'événement, les lectures de capteurs ou des informations générales supplémentaires, etc. Si une interprétation OEM n'est pas disponible, la sortie par défaut sera générée. La justesse des interprétations OEM ne peut être garantie en raison des modifications potentielles que les fournisseurs OEM peuvent apporter aux produits, au microprogramme, etc. Voir INTERPRÉTATION OEM ci-dessous pour les interprétations de cartes mères confirmées et prises en charge.
--ignore-not-available-sensors
Ignore les capteurs non disponibles (c.-à-d. N/A) dans la sortie.
--ignore-unrecognized-events
Ignore les événements de capteur non reconnus. Cela supprimera la sortie des événements non reconnus, généralement affichés comme « Unrecognized Event = XXXXh » dans la sortie. De plus, les événements non reconnus seront ignorés lors du calcul de l'état du capteur avec --output-sensor-state ci-dessous.
--output-event-bitmask
Affiche la valeur du masque de bits de l'événement au lieu de sa représentation textuelle.
--output-sensor-state
Affiche l'état du capteur dans la sortie. Cela ajoutera une sortie supplémentaire indiquant si un capteur est dans un état NOMINAL, WARNING ou CRITICAL. L'état du capteur est une valeur interprétée basée sur l'événement actuel du capteur. Les interprétations de l'état du capteur sont déterminées par le fichier de configuration /etc/freeipmi//freeipmi_interpret_sensor.conf. Voir freeipmi_interpret_sensor.conf(5) pour plus d'informations. Cette option donne une sortie identique à l'état du capteur précédemment affiché par ipmimonitoring(8).
--sensor-state-config-file=FICHIER
Spécifie un fichier de configuration d'état de capteur alternatif. Option ignorée si --output-sensor-state n'est pas spécifié.
--entity-sensor-names
Affiche les noms des capteurs préfixés par leur identifiant d'entité et leur numéro d'instance lorsque c'est approprié. Cela peut être nécessaire sur certaines cartes mères pour aider à identifier les capteurs auxquels font référence les entrées. Par exemple, une carte mère peut avoir plusieurs capteurs nommés « TEMP ». L'identifiant d'entité et le numéro d'instance peuvent aider à clarifier quel capteur se réfère au « Processeur 1 » par rapport au « Processeur 2 ».
--output-sensor-thresholds
Affiche les seuils des capteurs dans la sortie. Cela ajoutera des colonnes à la sortie par défaut pour les seuils non récupérables inférieurs, critiques inférieurs, non critiques inférieurs, non critiques supérieurs, critiques supérieurs et non récupérables supérieurs.
--no-sensor-type-output
Ne pas afficher le type de capteur pour chaque entrée. Sur de nombreux systèmes, le type de capteur est redondant avec le nom du capteur. Cela est particulièrement vrai si --entity-sensor-names est spécifié. Si le nom du capteur est suffisant, ou si le type de capteur n'est pas d'intérêt pour l'utilisateur, cette option peut être spécifiée pour condenser la sortie.
--comma-separated-output
Affiche les champs au format séparé par des virgules.
--no-header-output
Ne pas afficher les en-têtes de colonnes. Peut être utile dans les scripts.
--non-abbreviated-units
Affiche les unités non abrégées (par ex. « Amps » au lieu de « A »). Peut aider à lever l'ambiguïté des unités (par ex. « C » pour Celsius ou Coulombs).
--legacy-output
Affiche au format historique. Les options plus récentes peuvent ne pas être applicables à la sortie historique.
--ipmimonitoring-legacy-output
Affiche le format historique de l'outil historique ipmimonitoring . Les options plus récentes peuvent ne pas être applicables à la sortie historique.

OPTIONS DU CACHE SDR

Cet outil nécessite l'accès au cache du dépôt de données des capteurs (SDR) pour son fonctionnement général. Par défaut, les données SDR seront téléchargées et mises en cache sur la machine locale. Les options suivantes s'appliquent au cache SDR.

--flush-cache
Vide la version en cache du cache du dépôt de données des capteurs (SDR). Le SDR est généralement mis en cache pour un accès ultérieur plus rapide. Cependant, il peut être nécessaire de le vider et de le régénérer si le SDR a été mis à jour sur un système.
--quiet-cache
Ne pas afficher d'informations sur la création/suppression du cache. Peut être utile dans les scripts.
--sdr-cache-recreate
Si le cache SDR est périmé ou invalide, recrée automatiquement le cache du dépôt de données des capteurs (SDR). Cette option peut être utile à des fins de script.
--sdr-cache-file=FICHIER
Spécifie un fichier de cache du dépôt de données des capteurs (SDR) spécifique à stocker ou à lire. Si cette option est utilisée lorsque plusieurs hôtes sont spécifiés, le même fichier de cache SDR sera utilisé pour tous les hôtes.
--sdr-cache-directory=RÉPERTOIRE
Spécifie un répertoire alternatif pour stocker ou lire les caches du dépôt de données des capteurs (SDR). Par défaut, c'est le répertoire personnel si rien n'est spécifié.

DÉPANN

AGE G
ÉNÉRAL

Le plus souvent, les problèmes IPMI sont dus à des problèmes de

configuration.

Les problèmes IPMI sur LAN impliquent une mauvaise configuration du BMC de la machine distante. Vérifiez à deux reprises que les éléments suivants sont correctement configurés dans le BMC de la machine distante : adresse IP, adresse MAC, masque de sous-réseau, nom d'utilisateur, activation de l'utilisateur, privilège de l'utilisateur, mot de passe, privilège LAN, activation LAN et type(s) d'authentification autorisé(s). Pour les connexions IPMI 2.0, vérifiez à deux reprises que le(s) privilège(s) de la suite de chiffrement et la clé K_g sont correctement

configurés. L'

outil ipmi-config(8) peut être utilisé pour vérifier et/ou modifier ces paramètres de

configuration.

Les problèmes IPMI en bande sont généralement causés par des pilotes mal configurés ou des BMC non

standard.

En plus des conseils de dépannage ci-dessous, veuillez consulter la section SOLUTIONS DE CONTORNEMENT ci-dessous pour voir également s'il existe des bugs spécifiques à un fournisseur qui ont été découverts et

contournés.

Ci-dessous sont listés de nombreux problèmes courants pour les messages d'erreur. Pour un support supplémentaire, veuillez envoyer un courriel à la liste de diffusion <freeipmi-users@gnu.org>

.

« username invalid » - Le nom d'utilisateur saisi (ou un nom d'utilisateur NULL si aucun n'a été saisi) n'est pas disponible sur la machine distante. Il est également possible que la configuration du nom d'utilisateur du BMC distant soit

incorrecte.

« password invalid » - Le mot de passe saisi (ou un mot de passe NULL si aucun n'a été saisi) n'est pas correct. Il est également possible que le mot de passe de l'utilisateur ne soit pas correctement configuré sur le BMC

distant.

« password verification timeout » - La vérification du mot de passe a expiré. Une erreur « password invalid » (décrite ci-dessus) ou une « session timeout » générique (décrite ci-dessous) s'est produite. À ce stade du protocole, il ne peut être différencié laquelle s'est

produite.

« k_g invalid » - La clé K_g saisie (ou une clé K_g NULL si aucune n'a été saisie) n'est pas correcte. Il est également possible que la clé K_g ne soit pas correctement configurée sur le BMC

distant.

« privilege level insufficient » - Une commande IPMI requiert un privilège utilisateur plus élevé que celui avec lequel l'authentification a été effectuée. Veuillez essayer de vous authentifier avec un privilège plus élevé. Cela peut nécessiter de s'authentifier auprès d'un utilisateur différent ayant un privilège maximum plus

élevé.

« privilege level cannot be obtained for this user » - Le niveau de privilège avec lequel vous essayez de vous authentifier est supérieur au maximum autorisé pour cet utilisateur. Veuillez réessayer avec un privilège plus bas. Il est également possible que le niveau de privilège maximum autorisé pour un utilisateur ne soit pas correctement configuré sur le BMC

distant.

« authentication type unavailable for attempted privilege level » - Le type d'authentification avec lequel vous souhaitez vous authentifier n'est pas disponible pour ce niveau de privilège. Veuillez réessayer avec un type d'authentification alternatif ou un niveau de privilège alternatif. Il est également possible que les types d'authentification disponibles avec lesquels vous pouvez vous authentifier ne soient pas correctement configurés sur le BMC

distant.

« cipher suite id unavailable » - L'identifiant de suite de chiffrement avec lequel vous souhaitez vous authentifier n'est pas disponible sur le BMC distant. Veuillez réessayer avec un identifiant de suite de chiffrement alternatif. Il est également possible que les identifiants de suites de chiffrement disponibles ne soient pas correctement configurés sur le BMC

distant.

« ipmi 2.0 unavailable » - IPMI 2.0 n'a pas été découvert sur la machine distante. Veuillez essayer d'utiliser IPMI 1.5 à la

place.

« connection timeout » - La communication IPMI initiale a échoué. Un certain nombre d'erreurs potentielles sont possibles, y compris un nom d'hôte invalide spécifié, une adresse IP IPMI qui ne peut pas être résolue, IPMI n'est pas activé sur le serveur distant, la connexion réseau est mauvaise, etc. Veuillez vérifier la configuration et la

connectivité.

« session timeout » - La session IPMI a expiré. Veuillez vous reconnecter. Si cette erreur se produit souvent, vous pourriez souhaiter augmenter le délai d'attente de retransmission. Certains BMC distants sont considérablement plus lents que

d'autres.

« device not found » - Le périphérique spécifié n'a pas pu être trouvé. Veuillez vérifier la configuration ou les entrées et

réessayer.

« driver timeout » - La communication avec le pilote ou le périphérique a expiré. Veuillez

réessayer.

« message timeout » - La communication avec le pilote ou le périphérique a expiré. Veuillez

réessayer.

« BMC busy » - Le BMC est actuellement occupé. Il peut être en train de traiter des informations ou avoir trop de sessions simultanées à gérer. Veuillez patienter et

réessayer.

« could not find inband device » - Un périphérique en bande n'a pas pu être trouvé. Veuillez vérifier la configuration ou spécifier un périphérique ou pilote précis sur la ligne de

commande.

« driver timeout » - Le pilote en bande a expiré lors de la communication avec le BMC ou le processeur de service local. Le BMC ou le processeur de service peut être occupé ou (pire cas) possiblement non

fonctionnel.

« internal IPMI error » - Une erreur IPMI s'est produite que FreeIPMI ne sait pas gérer. Veuillez envoyer un courriel à <freeipmi-users@gnu.org> pour signaler le

problème.

« sensor config file parse error » - Une erreur d'analyse a été trouvée dans le fichier de configuration d'interprétation des capteurs. Veuillez consulter freeipmi_in

terpret_sens
or.conf(5).

SOLUTIONS DE

CONTORNEMENT

Avec autant de fournisseurs différents implémentant leurs propres solutions IPMI, différents fournisseurs peuvent implémenter incorrectement leurs protocoles IPMI. Ce qui suit décrit un certain nombre de solutions de contournement actuellement disponibles pour gérer les problèmes de conformité découverts. Lorsque c'est possible, des solutions de contournement ont été mises en œuvre afin qu'elles soient transparentes pour l'utilisateur. Cependant, certaines nécessiteront à l'utilisateur de spécifier qu'une solution de contournement doit être utilisée via l'option -W

PROBLÈMES CONTOURNÉS

Le matériel listé ci-dessous peut seulement indiquer le matériel sur lequel un problème a été découvert. Des versions plus récentes du matériel peuvent corriger les problèmes indiqués ci-dessous. Des machines similaires de fournisseurs peuvent présenter ou non les mêmes problèmes. Différents fournisseurs peuvent licencier leur micrologiciel auprès du même développeur de micrologiciel IPMI, il peut donc être utile d'essayer les solutions de contournement listées ci-dessous même si votre carte mère n'est pas listée.

Si vous estimez que votre matériel présente un problème de conformité supplémentaire nécessitant la mise en œuvre d'une solution de contournement, veuillez contacter les mainteneurs de FreeIPMI à l'adresse <freeipmi-users@gnu.org> ou <freeipmi-devel@gnu.org>.

assumeio - Ce drapeau de contournement supposera que les interfaces en bande communiquent avec les E/S du système plutôt qu'être mappées en mémoire. Cela contournera les systèmes qui signalent des adresses de base invalides. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que « device not supported » ou « could not find inband device ». Problème observé sur HP ProLiant DL145 G1.

spinpoll - Ce drapeau de contournement informera certains pilotes en bande (notamment le pilote KCS) de tourner en boucle lors de l'interrogation plutôt que de mettre le processus en veille. Cela peut améliorer considérablement le temps d'exécution des outils, car la granularité d'un ordonnanceur de système d'exploitation peut être beaucoup plus grande que le temps nécessaire pour effectuer une seule transaction de message IPMI. Cependant, en tournant en boucle, votre système peut effectuer moins de travail utile en ne passant pas le contexte de l'outil à une tâche plus utile.

authcap - Ce drapeau de contournement ignorera les vérifications précoces des capacités de nom d'utilisateur, des capacités d'authentification et du support K_g, et permettra à l'authentification IPMI de réussir. Il contourne plusieurs problèmes dans lesquels le système distant ne signale pas correctement les capacités de nom d'utilisateur, les capacités d'authentification ou l'état K_g. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que « username invalid », « authentication type unavailable for attempted privilege level » ou « k_g invalid ». Problème observé sur Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML, et Sun Fire 2200/4150/4450 avec ELOM.

nochecksumcheck - Ce drapeau de contournement indiquera à FreeIPMI de ne pas vérifier les sommes de contrôle retournées par les réponses aux commandes IPMI. Il contourne les systèmes qui retournent des sommes de contrôle invalides en raison d'erreurs d'implémentation, mais dont le paquet est par ailleurs valide. Les utilisateurs sont avertis de l'utilisation de cette option, car elle supprime la validation de l'intégrité du paquet dans un certain nombre de circonstances. Cependant, il est peu probable que cela pose problème dans la plupart des situations. Ceux qui rencontrent ce problème peuvent voir des erreurs telles que « connection timeout », « session timeout » ou « password verification timeout ». Sur les connexions IPMI 1.5, le contournement « noauthcodecheck » peut également être nécessaire. Problème observé sur Supermicro X9SCM-iiF, Supermicro X9DRi-F, et Supermicro X9DRFR.

idzero - Ce drapeau de contournement permettra aux identifiants de session vides d'être acceptés par le client. Il contourne les sessions IPMI qui signalent des identifiants de session vides au client. Ceux qui rencontrent ce problème peuvent voir des erreurs « session timeout ». Problème observé sur Tyan S2882 avec M3289 BMC.

unexpectedauth - Ce drapeau de contournement permettra de vérifier les codes d'authentification inattendus non nuls comme s'ils étaient attendus. Il contourne un problème où les paquets contiennent des données d'authentification non nulles alors qu'ils devraient être nuls en raison de la désactivation de l'authentification par message. Ceux qui rencontrent ce problème peuvent voir des erreurs « session timeout ». Problème observé sur Dell PowerEdge 2850, SC1425. Confirmé comme corrigé sur un micrologiciel plus récent.

forcepermsg - Ce drapeau de contournement forcera l'utilisation de l'authentification par message, peu importe ce qui est annoncé par le système distant. Il contourne un problème où l'authentification par message est annoncée comme désactivée sur le système distant, mais elle est en fait requise pour le protocole. Ceux qui rencontrent ce problème peuvent voir des erreurs « session timeout ». Problème observé sur IBM eServer 325.

endianseq - Ce drapeau de contournement inversera l'endianness des numéros de séquence de session pour permettre à la session de continuer correctement. Il contourne les numéros de séquence IPMI 1.5 dont l'endianness est incorrecte. Ceux qui rencontrent ce problème peuvent voir des erreurs « session timeout ». Problème observé sur certains Sun ILOM 1.0/2.0 (dépend de l'endianness du processeur de service).

noauthcodecheck - Ce drapeau de contournement indiquera à FreeIPMI de ne pas vérifier les codes d'authentification retournés par les réponses aux commandes IPMI 1.5. Il contourne les systèmes qui retournent des codes d'authentification invalides en raison d'erreurs de hachage ou d'implémentation. Les utilisateurs sont avertis de l'utilisation de cette option, car elle supprime une vérification d'authentification validant l'intégrité d'un paquet. Cependant, dans la plupart des organisations, cela ne devrait pas poser de problème de sécurité. Ceux qui rencontrent ce problème peuvent voir des erreurs « connection timeout », « session timeout » ou « password verification timeout ». Problème observé sur Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell, et Wiwynn Windmill.

intel20 - Ce drapeau de contournement permettra de contourner plusieurs problèmes d'authentification Intel IPMI 2.0. Les problèmes couverts comprennent le remplissage des noms d'utilisateur et la troncature des mots de passe si l'algorithme d'authentification est HMAC-MD5-128. Ceux qui rencontrent ce problème peuvent voir des erreurs « username invalid », « password invalid » ou « k_g invalid ». Problème observé sur Intel SE7520AF2 avec Intel Server Management Module (Professional Edition).

supermicro20 - Ce drapeau de contournement permettra de contourner plusieurs problèmes d'authentification Supermicro IPMI 2.0 sur les cartes mères avec un micrologiciel IPMI Peppercon. Les problèmes couverts comprennent la gestion des codes d'authentification de longueur invalide. Ceux qui rencontrent ce problème peuvent voir des erreurs « password invalid ». Problème observé sur Supermicro H8QME avec carte fille SIMSO. Confirmé comme corrigé sur un micrologiciel plus récent.

sun20 - Ce drapeau de contournement permettra de contourner plusieurs problèmes d'authentification Sun IPMI 2.0. Les problèmes couverts comprennent les clés de hachage de longueur invalide, les clés mal hachées et les enregistrements de suite de chiffrement invalides. Ceux qui rencontrent ce problème peuvent voir des erreurs « password invalid » ou « bmc error ». Problème observé sur Sun Fire 4100/4200/4500 avec ILOM. Ce contournement inclut automatiquement le contournement « opensesspriv ».

opensesspriv - Ce drapeau de contournement modifiera légèrement le protocole de connexion IPMI 2.0 de FreeIPMI pour contourner un algorithme de hachage invalide utilisé par le système distant. Le niveau de privilège envoyé lors de l'étape d'ouverture de session d'une connexion IPMI 2.0 est utilisé pour le hachage des clés au lieu du niveau de privilège envoyé lors de l'étape de connexion RAKP1. Ceux qui rencontrent ce problème peuvent voir des erreurs « password invalid », « k_g invalid », « bad rmcpplus status code » ou « privilege level cannot be obtained for this user ». Problème observé sur Sun Fire 4100/4200/4500 avec ILOM, Inventec 5441/Dell Xanadu II, Supermicro X8DTH, Supermicro X8DTG, Intel S5500WBV/Penguin Relion 700, Intel S2600JF/Appro 512X, Quanta QSSC-S4R/Appro GB812X-CN, Dell C5220, et le BMC logiciel OpenIPMI. Ce contournement est automatiquement déclenché avec le contournement « sun20 ».

integritycheckvalue - Ce drapeau de contournement permettra de contourner une valeur de contrôle d'intégrité invalide lors de l'établissement d'une session IPMI 2.0 en utilisant la suite de chiffrement ID 0. La valeur de contrôle d'intégrité devrait être de longueur 0, cependant la carte mère distante répond avec un champ non vide. Ceux qui rencontrent ce problème peuvent voir des erreurs « k_g invalid ». Problème observé sur Supermicro X8DTG, Supermicro X8DTU, et Intel S5500WBV/Penguin Relion 700, et Intel S2600JF/Appro 512X.

assumemaxsdrrecordcount - Ce contournement indiquera à la lecture SDR de s'arrêter après avoir lu un nombre maximum connu d'enregistrements SDR. Cela contournera les systèmes qui ont mal implémenté les fonctions de lecture SDR. Ceux qui rencontrent ce problème peuvent voir des erreurs « SDR record count invalid ». Problème observé sur une carte mère Inspur non spécifiée.

discretereading - Cette option de contournement permettra de lire les relevés de capteurs analogiques (c'est-à-dire rpm, degrés, etc.) même si le code de type d'événement/relevé pour le capteur concerne un capteur discret (c'est-à-dire assert vs deassert). Cette option contourne les enregistrements SDR mal définis (et sans doute illégaux) qui s'attendent à ce que les relevés de capteurs analogiques soient lus en même temps que les capteurs discrets. Cette option est confirmée comme corrigeant les problèmes sur les cartes mères HP Proliant DL380 G7 et HP ProLiant ML310 G5.

ignorescanningdisabled - Cette option de contournement permettra de lire les relevés de capteurs même si le bit de balayage du capteur indique qu'un capteur est désactivé. Cette option contourne les cartes mères qui indiquent incorrectement les capteurs comme désactivés. Ce problème peut exister sur votre carte mère si des capteurs sont listés comme « N/A » même s'ils devraient être disponibles. Cette option est confirmée comme corrigeant les problèmes sur les cartes mères Dell Poweredge 2900, Dell Poweredge 2950, Dell Poweredge R410, Dell Poweredge R610, et HP Integrity rx3600.

assumebmcowner - Cette option de contournement permettra de lire les relevés de capteurs si le propriétaire du capteur est le BMC, mais que le propriétaire du capteur signalé n'est pas le BMC. Typiquement, les capteurs appartenant à un propriétaire de capteur non-BMC doivent être pontés (par exemple, avec l'option --bridge-sensors), cependant si le propriétaire du capteur non-BMC est invalide, le pontage échoue. Cette option contourne les cartes mères qui signalent incorrectement un propriétaire de capteur non-BMC en supposant toujours que le propriétaire du capteur est le BMC. Ce problème peut exister sur votre carte mère si des capteurs sont listés comme « N/A » même s'ils devraient être disponibles. Cette option est confirmée comme corrigeant les problèmes sur les cartes mères Fujitsu RX300 et Fujitsu RX300S2.

ignoreauthcode - Cette option de contournement permettra de lire les relevés de capteurs si la machine distante calcule de manière invalide les codes d'authentification (c'est-à-dire les hachages d'authentification) lors de la communication sur le réseau. Ce problème peut exister sur votre système si l'erreur « session timeout » se produit ou s'il y a une apparence de blocage. Les utilisateurs sont avertis de l'utilisation de cette option, car elle supprime une vérification d'authentification validant l'intégrité d'un paquet. Cependant, dans la plupart des organisations, cela ne devrait pas poser de problème de sécurité. L'ignorance des paquets d'authentification est limitée à la période pendant laquelle les relevés de capteurs sont effectués, et non à une partie de l'authentification de session ou de la terminaison de session. Cette option est confirmée comme fonctionnant sur Inventec 5441/Dell Xanadu II et Inventec 5442/Dell Xanadu III. (Remarque : Sur les systèmes ci-dessus, ce problème n'a été observé que lorsque --bridge-sensors est utilisé.)

Aucun support IPMI 1.5 - Certaines cartes mères qui prennent en charge IPMI 2.0 se sont révélées ne pas prendre en charge IPMI 1.5. Ceux qui rencontrent ce problème peuvent voir des erreurs « ipmi 2.0 unavailable » ou « connection timeout ». Ce problème peut être contourné en utilisant IPMI 2.0 au lieu d'IPMI 1.5 en spécifiant --driver-type=LAN_2_0. Problème observé sur un certain nombre de cartes mères HP et Supermicro.

EXEMPLES

# ipmi-sensors

Affiche tous les capteurs et relevés sur la machine locale.

# ipmi-sensors --verbose

Affiche les capteurs et relevés de manière détaillée sur la machine locale.

# ipmi-sensors --record-ids="7,11,102"

Affiche les identifiants d'enregistrement de capteurs 7, 11 et 102 sur la machine locale.

# ipmi-sensors --sensor-types=fan

Affiche tous les capteurs de type ventilateur sur la machine locale.

# ipmi-sensors -h ahost -u myusername -p mypassword

Affiche tous les capteurs sur une machine distante en utilisant IPMI sur LAN.

# ipmi-sensors -h mycluster[0-127] -u myusername -p mypassword

Affiche tous les capteurs sur un cluster en utilisant IPMI sur LAN.

DIAGNOSTICS

En cas d'exécution réussie, le code de sortie est 0. En cas d'erreur, le code de sortie est 1.

Si plusieurs hôtes sont spécifiés pour la communication, le code de sortie est 0 si et seulement si toutes les cibles s'exécutent avec succès. Sinon, le code de sortie est 1.

PROBLÈMES CONNUS

Sur les systèmes d'exploitation plus anciens, si vous saisissez votre nom d'utilisateur, votre mot de passe et d'autres informations potentiellement sensibles sur la ligne de commande, ces informations peuvent être découvertes par d'autres utilisateurs lors de l'utilisation d'outils comme la commande ps(1) ou en consultant le système de fichiers /proc. Il est généralement plus sûr de saisir les informations de mot de passe avec des options comme les options -P ou -K. Configurer les informations sensibles dans le fichier de configuration FreeIPMI serait également un moyen approprié de masquer ces informations.

Afin de prévenir les attaques par force brute, certains BMC se « verrouillent » temporairement après un certain nombre d'erreurs d'authentification à distance. Vous devrez peut-être attendre un certain temps pour que ce verrouillage temporaire soit levé avant de pouvoir vous authentifier à nouveau.

Certains capteurs peuvent être affichés comme non disponibles (c'est-à-dire N/A) car le propriétaire du capteur n'est pas le BMC. Pour tenter de faire le pont vers les capteurs et d'accéder à des capteurs qui ne sont pas sur le BMC, les utilisateurs peuvent essayer les options -b ou --bridge-sensors .
