NOM

zmq_setsockopt - définir les options de socket 0MQ

SYNTAXE

int zmq_setsockopt (void *socket, int option_name, const void *option_value, size_t option_len);

Attention : Toutes les options, à l'exception de ZMQ_SUBSCRIBE, ZMQ_UNSUBSCRIBE, ZMQ_LINGER, ZMQ_ROUTER_HANDOVER, ZMQ_ROUTER_MANDATORY, ZMQ_PROBE_ROUTER, ZMQ_XPUB_VERBOSE, ZMQ_XPUB_VERBOSER, ZMQ_REQ_CORRELATE, ZMQ_REQ_RELAXED, ZMQ_SNDHWM et ZMQ_RCVHWM, ne prennent effet qu'après les appels ultérieurs de bind/connect du socket.

Plus spécifiquement, les options de sécurité prennent effet pour les appels bind/connect ultérieurs, et peuvent être modifiées à tout moment pour affecter les binds et/ou connects ultérieurs.

DESCRIPTION

La fonction zmq_setsockopt() définit l'option spécifiée par l'argument option_name à la valeur pointée par l'argument option_value pour le socket 0MQ pointé par l'argument socket. L'argument option_len est la taille de la valeur de l'option en octets. Pour les options qui prennent une valeur de type "chaîne de caractères", les données binaires fournies ne doivent contenir aucun octet nul, ou se terminer par un seul octet nul (caractère NUL ASCII de terminaison).

Les options de socket suivantes peuvent être définies avec la fonction zmq_setsockopt() :

ZMQ_AFFINITY: Définir l'affinité du thread I/O

L'option ZMQ_AFFINITY définit l'affinité du thread I/O pour les connexions nouvellement créées sur le socket spécifié.

L'affinité détermine quels threads du pool de threads I/O 0MQ associés au contexte du socket géreront les nouvelles connexions créées. Une valeur de zéro spécifie aucune affinité, ce qui signifie que le travail sera distribué équitablement entre tous les threads I/O 0MQ du pool. Pour les valeurs non nulles, le bit le plus bas correspond au thread 1, le deuxième bit le plus bas au thread 2, et ainsi de suite. Par exemple, une valeur de 3 spécifie que les connexions ultérieures sur le socket seront gérées exclusivement par les threads I/O 1 et 2.

Voir également zmq_init(3) pour les détails sur l'allocation du nombre de threads I/O pour un contexte spécifique.

Type de valeur d'option uint64_t
Unité de valeur d'option N/A (bitmap)
Valeur par défaut 0
Types de sockets applicables N/A

ZMQ_BACKLOG: Définir la longueur maximale de la file d'attente des connexions en attente

L'option ZMQ_BACKLOG définit la longueur maximale de la file d'attente des connexions pairs en attente pour le socket spécifié ; cela ne s'applique qu'aux transports orientés connexion. Pour plus de détails, reportez-vous à la documentation de votre système d'exploitation concernant la fonction listen.

Type de valeur d'option int
Unité de valeur d'option connexions
Valeur par défaut 100
Types de sockets applicables tous, uniquement pour les transports orientés connexion.

ZMQ_BINDTODEVICE: Définir le nom du périphérique auquel lier le socket

L'option ZMQ_BINDTODEVICE lie ce socket à un périphérique particulier, par exemple une interface ou un VRF. Si un socket est lié à une interface, seuls les paquets reçus de cette interface particulière sont traités par le socket. Si le périphérique est un périphérique VRF, les binds/connects ultérieurs à ce socket utilisent les adresses de la table de routage VRF.

nécessite de définir CAP_NET_RAW sur le programme compilé.

Type de valeur d'option chaîne de caractères
Unité de valeur d'option N/A
Valeur par défaut non défini
Types de sockets applicables tous, lors de l'utilisation des transports TCP ou UDP.

ZMQ_BUSY_POLL: Cela supprime les retards causés par l'interruption et le changement de contexte résultant.

Le sondage intensif (busy polling) aide à réduire la latence dans le chemin de réception réseau en permettant au code de la couche socket de sonder la file d'attente de réception d'un périphérique réseau, et en désactivant les interruptions réseau. Cela supprime les retards causés par l'interruption et le changement de contexte qui en résulte. Cependant, cela augmente également l'utilisation du CPU. Le sondage intensif empêche également le CPU de se mettre en veille, ce qui peut entraîner une consommation d'énergie supplémentaire.

Type de valeur d'option int
Unité de valeur d'option 0,1
Valeur par défaut 0
Types de sockets applicables tous

ZMQ_CONNECT_RID: Attribuer le prochain ID de connexion sortante

Ce nom d'option est maintenant obsolète. Utilisez ZMQ_CONNECT_ROUTING_ID à la place. ZMQ_CONNECT_RID reste un alias pour le moment.

ZMQ_CONNECT_ROUTING_ID: Attribuer le prochain ID de routage sortant

L'option ZMQ_CONNECT_ROUTING_ID définit l'identifiant pair du pair connecté via le prochain appel zmq_connect(), de telle sorte que cette connexion soit immédiatement prête pour le transfert de données avec l'identifiant de routage donné. Cette option s'applique uniquement au premier appel suivant à zmq_connect() ; les appels zmq_connect() ultérieurs utilisent le comportement de connexion par défaut.

L'utilisation typique consiste à définir cette option de socket avant chaque appel zmq_connect(). Chaque connexion DOIT se voir attribuer un identifiant de routage unique. L'attribution d'un identifiant de routage déjà utilisé n'est pas autorisée.

Utile lors de la connexion de ROUTER à ROUTER, ou de STREAM à STREAM, car cela permet l'envoi immédiat aux pairs. Les exigences de l'encapsulation des identifiants de routage sortants pour les sockets ROUTER et STREAM s'appliquent.

L'identifiant de routage doit avoir une longueur comprise entre 1 et 255 octets et NE PEUT PAS commencer par un octet nul (de tels identifiants de routage sont réservés à un usage interne par l'infrastructure 0MQ).

Types de sockets applicables ZMQ_ROUTER, ZMQ_STREAM

ZMQ_HANDSHAKE_IVL : Définir l'intervalle maximum de négociation

L'option ZMQ_HANDSHAKE_IVL définit l'intervalle maximum de négociation pour le socket spécifié. La négociation est l'échange d'informations de configuration du socket (type de socket, ID de routage, sécurité) qui se produit lorsqu'une connexion est ouverte pour la première fois, uniquement pour les transports orientés connexion. Si la négociation ne se termine pas dans le délai configuré, la connexion sera fermée. La valeur 0 signifie aucune limite de temps pour la négociation.

Type de valeur d'option int
Unité de valeur d'option millisecondes
Valeur par défaut 30000
Types de socket applicables tous sauf ZMQ_STREAM, uniquement pour les transports orientés connexion

ZMQ_HELLO_MSG : définir un message de bienvenue qui sera envoyé lorsqu'un nouveau pair se connecte

Lorsqu'elle est définie, le socket enverra automatiquement un message de bienvenue lorsqu'une nouvelle connexion est établie ou acceptée. Vous pouvez définir cela sur les sockets DEALER, ROUTER, CLIENT, SERVER et PEER. La combinaison avec ZMQ_HEARTBEAT_IVL est puissante et simplifie les protocoles, car maintenant les battements de cœur et l'envoi du message de bienvenue peuvent être laissés de côté dans les protocoles et être gérés par zeromq.

L'option ZMQ_HEARTBEAT_IVL définit l'intervalle entre l'envoi des battements de cœur ZMTP pour le socket spécifié. Si cette option est définie et supérieure à 0, alors une commande ZMTP PING sera envoyée toutes les ZMQ_HEARTBEAT_IVL millisecondes.

ZMQ_HEARTBEAT_TIMEOUT : Définir le délai d'attente pour les battements de cœur ZMTP

L'option ZMQ_HEARTBEAT_TIMEOUT définit la durée pendant laquelle attendre avant d'atteindre le délai d'expiration d'une connexion après l'envoi d'une commande ZMTP PING et sans recevoir de trafic. Cette option n'est valide que si ZMQ_HEARTBEAT_IVL est également définie et est supérieure à 0. La connexion atteindra le délai d'expiration s'il n'y a pas de trafic reçu après l'envoi de la commande PING, mais le trafic reçu n'a pas besoin d'être une commande PONG - tout trafic reçu annulera le délai d'attente.

L'option ZMQ_HEARTBEAT_TTL définit le délai d'expiration sur le pair distant pour les battements de cœur ZMTP. Si cette option est supérieure à 0, le côté distant expirera la connexion s'il ne reçoit plus de trafic dans le délai TTL. Cette option n'a aucun effet si ZMQ_HEARTBEAT_IVL n'est pas définie ou est égale à 0. En interne, cette valeur est arrondie à la déciseconde la plus proche, toute valeur inférieure à 100 n'aura aucun effet.

ZMQ_IMMEDIATE : Mettre en file d'attente les messages uniquement pour les connexions terminées

Par défaut, les files d'attente se remplissent sur les connexions sortantes, même si la connexion n'est pas terminée. Cela peut entraîner des messages « perdus » sur les sockets avec routage en round-robin (REQ, PUSH, DEALER). Si cette option est définie sur 1, les messages ne seront mis en file d'attente que pour les connexions terminées. Cela provoquera le blocage du socket s'il n'y a pas d'autres connexions, mais évitera que les files d'attente ne se remplissent sur des tuyaux en attente de connexion.

Type de valeur d'option int
Unité de valeur d'option booléen
Valeur par défaut 0 (faux)
Types de socket applicables tous, uniquement pour les transports orientés connexion.

ZMQ_INVERT_MATCHING : Inverser le filtrage des messages

Inverse le comportement de filtrage des sockets PUB-SUB, lorsqu'il est défini sur 1.

Sur les sockets PUB et XPUB, cela entraîne l'envoi de messages à tous les sockets connectés sauf ceux qui sont abonnés à un préfixe qui correspond au message. Sur les sockets SUB, cela oblige uniquement les messages entrants qui ne correspondent pas à l'un des abonnements du socket à être reçus par l'utilisateur.

Lorsque ZMQ_INVERT_MATCHING est défini sur 1 sur un socket PUB, tous les sockets SUB qui s'y connectent doivent également avoir l'option définie sur 1. Ne pas le faire entraînera le rejet de tout ce que le socket PUB leur envoie par les sockets SUB. Les sockets XSUB n'ont pas besoin de le faire car ils ne filtrent pas les messages entrants.

Type de valeur d'option int
Unité de valeur d'option 0,1
Valeur par défaut 0
Types de socket applicables ZMQ_PUB, ZMQ_XPUB, ZMQ_SUB

ZMQ_LINGER : Définir la période de latence pour l'arrêt du socket

L'option ZMQ_LINGER définit la période de latence pour le socket spécifié. La période de latence détermine combien de temps les messages en attente qui n'ont pas encore été envoyés à un pair doivent rester en mémoire après qu'un socket soit déconnecté avec zmq_disconnect(3) ou fermé avec zmq_close(3), et affecte en outre la terminaison du contexte du socket avec zmq_ctx_term(3). Ce qui suit décrit les différents comportements :

•Une valeur de -1 spécifie une période de latence infinie. Les messages en attente ne seront pas supprimés après un appel à zmq_disconnect() ou zmq_close() ; tenter de terminer le contexte du socket avec zmq_ctx_term() bloquera jusqu'à ce que tous les messages en attente aient été envoyés à un pair.
•La valeur de 0 spécifie aucune période de latence. Les messages en attente seront immédiatement supprimés après un appel à zmq_disconnect() ou zmq_close().
•Les valeurs positives spécifient une limite supérieure pour la période de latence en millisecondes. Les messages en attente ne seront pas supprimés après un appel à zmq_disconnect() ou zmq_close() ; tenter de terminer le contexte du socket avec zmq_ctx_term() bloquera jusqu'à ce que tous les messages en attente aient été envoyés à un pair, ou que la période de latence expire, après quoi tous les messages en attente seront supprimés.
Type de valeur d'option int
Unité de valeur d'option millisecondes
Valeur par défaut -1 (infini)
Types de socket applicables tous

Type de valeur d'option int64_t

ZMQ_METADATA : Ajouter des propriétés de métadonnées d'application à un socket

L'option ZMQ_METADATA ajoute des métadonnées d'application au socket spécifié, les métadonnées sont échangées avec les pairs lors de l'établissement de la connexion. Une propriété de métadonnées est spécifiée sous forme de chaîne, délimitée par deux points, commençant par la propriété de métadonnées suivie de la valeur de métadonnées, par exemple « X-key:valeur ». Les noms de propriétés sont limités à 255 caractères maximum et doivent être précédés de « X- ». Plusieurs propriétés de métadonnées d'application peuvent être ajoutées à un socket en exécutant zmq_setsockopt() plusieurs fois. Comme l'argument est une chaîne terminée par un caractère nul, les données binaires doivent être encodées avant d'être ajoutées, par exemple en utilisant Z85 (zmq_z85_encode(3)).


Remarque

SYNOPSIS

#include <zmq.h>
int zmq_setsockopt (void *socket, int option_name, const void *option_value, size_t option_len);

DESCRIPTION

La fonction zmq_setsockopt() permet de modifier les caractéristiques d'un objet socket 0MQ. Les options de socket disponibles sont définies dans l'en-tête <zmq.h> et sont préfixées par ZMQ_.

Le paramètre option_name spécifie l'option à définir. Le paramètre option_value est un pointeur vers la valeur à définir pour l'option spécifiée. Le paramètre option_len spécifie la taille en octets de la valeur de l'option.

Il existe de nombreuses options de socket. Les plus courantes sont traitées dans les sections suivantes.

L'option ZMQ_SUBSCRIBE permet de s'abonner à des messages dont le préfixe correspond à la valeur spécifiée. Si la valeur est une chaîne vide (option_value = "", option_len = 0), le socket s'abonnera à tous les messages. Pour les sockets de type ZMQ_SUB, cela est une opération obligatoire avant de pouvoir recevoir des messages.

L'option ZMQ_UNSUBSCRIBE permet de se désabonner de messages dont le préfixe correspond à la valeur spécifiée.

L'option ZMQ_AFFINITY permet de définir l'affinité des threads d'E/S pour un socket donné. La valeur est un masque de bits où chaque bit correspond à un thread d'E/S disponible dans le contexte 0MQ. Si ce bit est défini, le socket sera traité par le thread d'E/S correspondant.

L'option ZMQ_IMPLICIT_SLOW_START est une option expérimentale qui, si définie à 1 (true), active la gestion de la congestion pour le protocole de transport 0MQ, en implémentant une version modifiée du TCP Slow Start. Cette option est en état DRAFT, non encore disponible dans les versions stables.

Option de valeur : int

Unité de valeur d'option : booléen

Valeur par défaut : 0 (faux)

Types de socket applicables : Tous, lors de l'utilisation du transport NORM.

RETURN VALUE

La fonction zmq_setsockopt() retourne zéro en cas de succès. Sinon, elle retourne -1 et définit errno à l'une des valeurs définies ci-dessous.

ERRORS

EINVAL

Le nom d'option option_name demandé est inconnu, ou la longueur option_len ou la valeur option_value demandée est invalide.

ETERM

Le contexte 0MQ associé au socket spécifié a été terminé.

ENOTSOCK

Le socket fourni était invalide.

EINTR

L'opération a été interrompue par la livraison d'un signal.

EXAMPLE

Abonnement aux messages sur un socket ZMQ_SUB.

/* S'abonner à tous les messages */
rc = zmq_setsockopt (socket, ZMQ_SUBSCRIBE, "", 0);
assert (rc == 0);
/* S'abonner aux messages préfixés par "ANIMALS.CATS" */
rc = zmq_setsockopt (socket, ZMQ_SUBSCRIBE, "ANIMALS.CATS", 12);

Définition de l'affinité des threads d'E/S.

int64_t affinity;
/* Les connexions entrantes sur le port TCP 5555 seront gérées par le thread d'E/S 1 */
affinity = 1;
rc = zmq_setsockopt (socket, ZMQ_AFFINITY, &affinity, sizeof (affinity));
assert (rc);
rc = zmq_bind (socket, "tcp://lo:5555");
assert (rc);
/* Les connexions entrantes sur le port TCP 5556 seront gérées par le thread d'E/S 2 */
affinity = 2;
rc = zmq_setsockopt (socket, ZMQ_AFFINITY, &affinity, sizeof (affinity));
assert (rc);
rc = zmq_bind (socket, "tcp://lo:5556");
assert (rc);
