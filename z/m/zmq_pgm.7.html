NOM

zmq_pgm - transport de multidiffusion fiable de 0MQ utilisant PGM

SYNOPIS

PGM (Pragmatic General Multicast) est un protocole de transport de multidiffusion fiable de données sur les réseaux IP.

DESCRIPTION

0MQ implémente deux variantes de PGM, le protocole standard où les datagrammes PGM sont directement superposés aux datagrammes IP tels que définis par la RFC 3208 (le transport pgm) et le "PGM encapsulé" ou EPGM où les datagrammes PGM sont encapsulés dans des datagrammes UDP (le transport epgm).

Les transports pgm et epgm ne peuvent être utilisés qu'avec les types de sockets ZMQ_PUB et ZMQ_SUB.

De plus, les sockets PGM sont limités en débit par défaut. Pour plus de détails, reportez-vous aux options ZMQ_RATE et ZMQ_RECOVERY_IVL documentées dans zmq_setsockopt(3).


Attention

L'implémentation du transport pgm nécessite un accès aux sockets IP bruts. Des privilèges supplémentaires peuvent être requis sur certains systèmes d'exploitation pour cette opération. Il est conseillé aux applications n'ayant pas besoin d'interopérabilité directe avec d'autres implémentations PGM d'utiliser plutôt le transport epgm qui ne nécessite aucun privilège spécial.

ADRESSAGE

Un point d'accès 0MQ est une chaîne composée d'un transport:// suivi d'une adresse. Le transport spécifie le protocole sous-jacent à utiliser. L'adresse spécifie l'adresse spécifique au transport à laquelle se connecter.

Pour le transport PGM, le transport est pgm, et pour le protocole EPGM le transport est epgm. La signification de la partie adresse est définie ci-dessous.

Connexion d'un socket

Lors de la connexion d'un socket à une adresse de pair en utilisant zmq_connect() avec le transport pgm ou epgm, le point d'accès doit être interprété comme une interface suivie d'un point-virgule, suivie d'une adresse de multidiffusion, suivie d'un deux-points et d'un numéro de port.

Une interface peut être spécifiée par l'un des éléments suivants :

•Le nom de l'interface tel que défini par le système d'exploitation.
•L'adresse IPv4 principale assignée à l'interface, dans sa représentation numérique.

Note

Les noms d'interface ne sont standardisés d'aucune manière et doivent être considérés comme arbitraires et dépendants de la plateforme. Sur les plateformes Win32, il n'existe pas de noms d'interface courts, ainsi seule l'adresse IPv4 principale peut être utilisée pour spécifier une interface. La partie interface peut être omise, dans ce cas, celle par défaut sera sélectionnée.

Une adresse de multidiffusion est spécifiée par une adresse multidiffusion IPv4 dans sa représentation numérique.

FORMAT DES DONNÉES SUR LE RÉSEAU

Les datagrammes PGM consécutifs sont interprétés par 0MQ comme un unique flux de données continu où les messages 0MQ ne sont pas nécessairement alignés sur les frontières des datagrammes PGM et où un seul message 0MQ peut couvrir plusieurs datagrammes PGM. Ce flux de données est constitué de messages 0MQ encapsulés dans des trames comme décrit dans zmq_tcp(7).

Charge utile du datagramme PGM

La grammaire ABNF suivante représente la charge utile d'un seul datagramme PGM tel qu'utilisé par 0MQ :

datagram               = (offset data)
offset                 = 2OCTETS
data                   = *OCTETS

Afin que les consommateurs qui rejoignent tardivement puissent identifier les frontières des messages, chaque charge utile de datagramme PGM commence par un entier non signé de 16 bits en ordre d'octets réseau spécifiant soit le décalage de la première trame du message dans le datagramme, soit contenant la valeur 0xFFFF si le datagramme contient uniquement une partie intermédiaire d'un message plus grand.

Notez que le décalage spécifie où commence le premier message plutôt que la première partie du message. Ainsi, s'il y a des parties de message en fin au début du paquet, le décalage les ignore et pointe vers la première partie de message initiale dans le paquet.

Le diagramme suivant illustre la disposition de la charge utile d'un seul datagramme PGM :

+------------------+----------------------+
| décalage (16 bits) |         données      |
+------------------+----------------------+

Le diagramme suivant illustre plus en détail comment trois exemples de trames 0MQ sont disposés dans des charges utiles de datagrammes PGM consécutifs :

Charge utile du premier datagramme
+--------------+-------------+---------------------+
| décalage trame |   Trame 1   | Trame 2, partie 1   |
|    0x0000    | (Message 1) | (Message 2, partie 1) |
+--------------+-------------+---------------------+
Charge utile du deuxième datagramme
+--------------+---------------------+
| décalage trame | Trame 2, partie 2   |
| 0xFFFF       | (Message 2, partie 2) |
+--------------+---------------------+
Charge utile du troisième datagramme
+--------------+----------------------------+-------------+
| décalage trame | Trame 2, 8 derniers octets |   Trame 3   |
| 0x0008       | (Message 2, 8 derniers octets) | (Message 3) |
+--------------+----------------------------+-------------+

CONFIGURATION

Le protocole PGM est capable de multidiffuser des données à des débits élevés (500 Mbps et plus) avec de grands messages (1 Mo et plus), cependant il nécessite la configuration des options de socket ZMQ pertinentes qui sont documentées dans zmq_setsockopt(3) :

•Le ZMQ_RATE doit être réglé suffisamment haut, par ex. 1 Gbps
•Le ZMQ_RCVBUF doit être augmenté côté abonné, par ex. 4 Mo
•Le ZMQ_SNDBUF doit être augmenté côté éditeur, par ex. 4 Mo

Il est important de noter que les options ZMQ_RCVBUF et ZMQ_SNDBUF sont limitées par la taille des tampons d'émission/réception du système d'exploitation sous-jacent. Sous Linux, ceux-ci peuvent être augmentés pour la session actuelle avec les commandes suivantes :

# définir les tampons d'émission/réception à 4 Mo (la valeur par défaut peut
# également être lue comme la taille initiale du tampon)
sudo sysctl -w net.core.rmem_max=4194304
sudo sysctl -w net.core.wmem_max=4194304
sudo sysctl -w net.core.rmem_default=4194304
sudo sysctl -w net.core.wmem_default=4194304

EXEMPLE

Connexion d'un socket.

// Connexion à l'adresse de multidiffusion 239.192.1.1, port 5555,
// en utilisant la première interface réseau Ethernet sous Linux
// et le protocole Encapsulated PGM
rc = zmq_connect(socket, "epgm://eth0;239.192.1.1:5555");
assert (rc == 0);
// Connexion à l'adresse de multidiffusion 239.192.1.1, port 5555,
// en utilisant l'interface réseau avec l'adresse 192.168.1.1
// et le protocole PGM standard
rc = zmq_connect(socket, "pgm://192.168.1.1;239.192.1.1:5555");
assert (rc == 0);
