NOM

zmq_socket - créer une socket 0MQ

SYNOPSIS

void *zmq_socket (void *context, int type);

DESCRIPTION

La fonction zmq_socket() crée une socket 0MQ dans le context spécifié et retourne un handle opaque vers la nouvelle socket créée. L'argument type spécifie le type de socket, qui détermine la sémantique de la communication sur la socket.

La nouvelle socket créée est initialement non liée et non associée à des points de terminaison. Afin d'établir un flux de messages, une socket doit d'abord être connectée à au moins un point de terminaison avec zmq_connect(3), ou au moins un point de terminaison doit être créé pour accepter les connexions entrantes avec zmq_bind(3).

Différences clés par rapport aux sockets conventionnelles. D'une manière générale, les sockets conventionnelles présentent une interface synchrone soit à des flux d'octets fiables orientés connexion (SOCK_STREAM), soit à des datagrammes non fiables sans connexion (SOCK_DGRAM). En comparaison, les sockets 0MQ présentent une abstraction d'une file de messages asynchrone, les sémantiques exactes de mise en file d'attente dépendant du type de socket utilisé. Là où les sockets conventionnelles transfèrent des flux d'octets ou des datagrammes discrets, les sockets 0MQ transfèrent des messages discrets.

Les sockets 0MQ étant asynchrones signifie que les moments de l'établissement et de la fermeture de la connexion physique, de la reconnexion et de la livraison effective sont transparents pour l'utilisateur et organisés par 0MQ lui-même. De plus, les messages peuvent être mis en file d'attente si un pair n'est pas disponible pour les recevoir.

Les sockets conventionnelles ne permettent que des relations strictement un à un (deux pairs), plusieurs à un (plusieurs clients, un serveur), ou dans certains cas un à plusieurs (multidiffusion). À l'exception de ZMQ_PAIR et ZMQ_CHANNEL, les sockets 0MQ peuvent être connectées à plusieurs points de terminaison en utilisant zmq_connect(), tout en acceptant simultanément des connexions entrantes depuis plusieurs points de terminaison liés à la socket en utilisant zmq_bind(), permettant ainsi des relations plusieurs à plusieurs.

Sécurité des threads. 0MQ possède des types de sockets à la fois sécurisés pour les threads et non sécurisés pour les threads. Les applications NE DOIVENT PAS utiliser une socket non sécurisée pour les threads à partir de plusieurs threads en aucune circonstance. Faire ainsi entraîne un comportement indéfini.

Les sockets sécurisées pour les threads sont les suivantes : * ZMQ_CLIENT * ZMQ_SERVER * ZMQ_DISH * ZMQ_RADIO * ZMQ_SCATTER * ZMQ_GATHER * ZMQ_PEER * ZMQ_CHANNEL

Types de sockets. Les sections suivantes présentent les types de sockets définis par 0MQ, groupés par le modèle de messagerie général qui est construit à partir de types de sockets apparentés.

Modèle client-serveur

Le modèle client-serveur est utilisé pour permettre à un unique serveur ZMQ_SERVER de communiquer avec un ou plusieurs clients ZMQ_CLIENT. Le client initie toujours la conversation, après quoi l'un ou l'autre des pairs peut envoyer des messages de manière asynchrone à l'autre.

Le modèle client-serveur est formellement défini par http://rfc.zeromq.org/spec:41.


Note

Client-serveur est toujours en phase de brouillon.

ZMQ_CLIENT

Une socket ZMQ_CLIENT communique avec une socket ZMQ_SERVER. N'importe lequel des pairs peut se connecter, bien que le modèle habituel et recommandé soit de lier le ZMQ_SERVER et de connecter le ZMQ_CLIENT.

Si la socket ZMQ_CLIENT a établi une connexion, zmq_send(3) acceptera les messages, les mettra en file d'attente et les enverra aussi rapidement que le réseau le permet. La limite du tampon de sortie est définie par le niveau de saturation (high water mark) de la socket. Si le tampon de sortie est plein, ou, pour les transports orientés connexion, si l'option ZMQ_IMMEDIATE est définie et qu'il n'y a pas de pair connecté, zmq_send(3) bloquera. La socket ZMQ_CLIENT ne supprimera pas de messages.

Lorsqu'une socket ZMQ_CLIENT est connectée à plusieurs sockets ZMQ_SERVER, les messages sortants sont distribués entre les pairs connectés selon un principe de rotation (round-robin). De même, la socket ZMQ_CLIENT reçoit les messages de manière équitable de chaque pair connecté. Cette utilisation n'est raisonnable que pour les protocoles sans état.

Les sockets ZMQ_CLIENT sont thread-safe et peuvent être utilisées depuis plusieurs threads simultanément. Notez que les réponses d'une socket ZMQ_SERVER iront au premier thread client qui appelle zmq_msg_recv(3). Si vous avez besoin de renvoyer les réponses au thread d'origine, utilisez une socket ZMQ_CLIENT par thread.


Note

Les sockets ZMQ_CLIENT sont thread-safe. Elles n'acceptent pas l'option ZMQ_SNDMORE sur les envois ni ZMQ_RCVMORE sur les réceptions. Cela les limite à des données en une seule partie. L'intention est d'étendre l'API pour permettre la diffusion/collecte de données multi-parties.

ZMQ_SERVER

Une socket ZMQ_SERVER communique avec un ensemble de sockets ZMQ_CLIENT. Une socket ZMQ_SERVER ne peut que répondre à un message entrant : le pair ZMQ_CLIENT doit toujours initier une conversation.

Chaque message reçu possède un routing_id qui est un entier non signé de 32 bits. L'application peut le récupérer avec zmq_msg_routing_id(3). Pour envoyer un message à un pair ZMQ_CLIENT donné, l'application doit définir le routing_id du pair sur le message, en utilisant zmq_msg_set_routing_id(3).

Si le routing_id n'est pas spécifié, ou ne fait pas référence à un pair client connecté, l'appel d'envoi échouera avec EHOSTUNREACH. Si le tampon de sortie pour le pair client est plein, l'appel d'envoi bloquera, à moins que ZMQ_DONTWAIT ne soit utilisé lors de l'envoi, auquel cas il échouera avec EAGAIN. La socket ZMQ_SERVER ne supprimera des messages dans aucun cas.


Note

Les sockets ZMQ_SERVER sont thread-safe. Elles n'acceptent pas l'option ZMQ_SNDMORE sur les envois ni ZMQ_RCVMORE sur les réceptions. Cela les limite à des données en une seule partie. L'intention est d'étendre l'API pour permettre la diffusion/collecte de données multi-parties.

Modèle radio-platine

Le modèle radio-platine est utilisé pour la distribution de données d'un unique éditeur à plusieurs abonnés dans un mode de diffusion (fan-out).

Radio-platine utilise des groupes (vs sujets Pub-sub), les sockets Platine peuvent rejoindre un groupe et chaque message envoyé par les sockets Radio appartient à un groupe.

Les groupes sont des chaînes null-terminées limitées à 16 caractères (y compris le null). L'intention est d'augmenter la longueur à 40 caractères (y compris le null). L'encodage des groupes sera en UTF8.

Les groupes sont mis en correspondance par une correspondance exacte (vs

prefix matching de PubSub).


Note

Radio-dish est encore en phase de brouillon.

ZMQ_RADIO

Une socket de type ZMQ_RADIO est utilisée par un éditeur pour distribuer des données. Chaque message appartient à un groupe, un groupe est spécifié avec zmq_msg_set_group(3). Les messages sont distribués à tous les membres d'un groupe. La fonction zmq_recv(3) n'est pas implémentée pour ce type de socket.

Lorsqu'une socket ZMQ_RADIO entre dans l'état mute en raison de l'atteinte de la haute marque de l'eau (high water mark) pour un abonné, tous les messages qui seraient envoyés à l'abonné en question seront alors ignorés jusqu'à ce que l'état mute prenne fin. La fonction zmq_send() ne bloquera jamais pour ce type de socket.


Note

Les sockets ZMQ_RADIO sont thread-safe. Elles n'acceptent pas l'option ZMQ_SNDMORE lors des envois. Cela les limite aux données d'une seule partie.

La fonction zmq_send() n'est pas implémentée pour ce type de socket.

Modèle Publish-subscribe

Le modèle publish-subscribe est utilisé pour la distribution un-à-plusieurs de données à partir d'un seul éditeur vers plusieurs abonnés selon un schéma de diffusion (fan out).

Le modèle publish-subscribe est formellement défini par http://rfc.zeromq.org/spec:29.

ZMQ_PUB

Une socket de type ZMQ_PUB est utilisée par un éditeur pour distribuer des données. Les messages envoyés sont distribués en mode fan out à tous les pairs connectés. La fonction zmq_recv(3) n'est pas implémentée pour ce type de socket.

Lorsqu'une socket ZMQ_PUB entre dans l'état mute en raison de l'atteinte de la haute marque de l'eau pour un abonné, tous les messages qui seraient envoyés à l'abonné en question seront alors ignorés jusqu'à ce que l'état mute prenne fin. La fonction zmq_send() ne bloquera jamais pour ce type de socket.

ZMQ_XPUB

Identique à ZMQ_PUB, sauf que vous pouvez recevoir des abonnements des pairs sous forme de messages entrants. Un message d'abonnement est un octet 1 (pour les abonnements) ou un octet 0 (pour les désabonnements) suivi du corps de l'abonnement. Les messages sans préfixe de souscription/désabonnement sont également reçus, mais n'ont aucun effet sur le statut de l'abonnement.

Modèle Pipeline

Le modèle pipeline est utilisé pour la distribution de données vers des nœuds agencés en pipeline. Les données circulent toujours dans le sens du pipeline, et chaque étape du pipeline est connectée à au moins un nœud. Lorsqu'une étape de pipeline est connectée à plusieurs nœuds, les données sont distribuées en round-robin à tous les nœuds connectés.

Le modèle pipeline est formellement défini par http://rfc.zeromq.org/spec:30.

ZMQ_PUSH

Une socket de type ZMQ_PUSH est utilisée par un nœud de pipeline pour envoyer des messages aux nœuds de pipeline en aval. Les messages sont distribués en round-robin à tous les nœuds en aval connectés. La fonction zmq_recv() n'est pas implémentée pour ce type de socket.

Lorsqu'une socket ZMQ_PUSH entre dans l'état mute en raison de l'atteinte de la haute marque de l'eau pour tous les nœuds en aval, ou, pour les transports orientés connexion, si l'option ZMQ_IMMEDIATE est définie et qu'il n'y a aucun nœud en aval du tout, alors toute opération zmq_send(3) sur la socket sera bloquée jusqu'à ce que l'état mute prenne fin ou qu'au moins un nœud en aval devienne disponible pour l'envoi ; les messages ne sont pas rejetés.

Modèle exclusif pair

Le modèle exclusif pair est utilisé pour connecter un pair à précisément un autre pair. Ce modèle est utilisé pour la communication inter-thread via le transport inproc.

Le modèle exclusif pair est formellement défini par http://rfc.zeromq.org/spec:31.

ZMQ_PAIR

Une socket de type ZMQ_PAIR ne peut être connectée qu'à un seul pair à la fois. Aucun routage ni filtrage de messages n'est effectué sur les messages envoyés via une socket ZMQ_PAIR.

Lorsqu'une socket ZMQ_PAIR entre dans l'état muet parce qu'elle a atteint la limite supérieure (high water mark) pour le pair connecté, ou, pour les transports orientés connexion, si l'option ZMQ_IMMEDIATE est définie et qu'il n'y a pas de pair connecté, alors toute opération zmq_send(3) sur la socket bloquera jusqu'à ce que le pair soit disponible pour l'envoi ; les messages ne sont pas rejetés.

Bien que les sockets ZMQ_PAIR puissent être utilisées sur des transports autres que zmq_inproc(7), leur incapacité à se reconnecter automatiquement, combinée au fait que les nouvelles connexions entrantes seront terminées tant que des connexions précédentes (y compris celles en état de fermeture) existent, les rend inadaptées au TCP dans la plupart des cas.


Note

Les sockets ZMQ_PAIR sont conçues pour la communication inter-thread via le transport zmq_inproc(7) et n'implémentent pas de fonctionnalités telles que la reconnexion automatique.

Modèle pair-à-pair

Le modèle pair-à-pair est utilisé pour connecter un pair à plusieurs pairs. Un pair peut à la fois se connecter et se lier, et mélanger les deux avec la même socket. Le modèle pair-à-pair est utile pour construire des réseaux pair-à-pair (par exemple, zyre, bitcoin, torrent) où un pair peut accepter des connexions d'autres pairs ou s'y connecter.


Note

Le pair-à-pair est encore en phase de brouillon.

ZMQ_PEER

Une socket ZMQ_PEER communique avec un ensemble de sockets ZMQ_PEER.

Pour se connecter et obtenir l' routing_id du pair, utilisez zmq_connect_peer(3).

Chaque message reçu possède un routing_id qui est un entier non signé de 32 bits. L'application peut le récupérer avec zmq_msg_routing_id(3).

Pour envoyer un message à un pair ZMQ_PEER donné, l'application doit définir le routing_id du pair sur le message, en utilisant zmq_msg_set_routing_id(3).

Si le routing_id n'est pas spécifié, ou ne fait pas référence à un pair client connecté, l'appel d'envoi échouera avec EHOSTUNREACH. Si le tampon de sortie pour le pair est plein, l'appel d'envoi bloquera, sauf si ZMQ_DONTWAIT est utilisé dans l'envoi, auquel cas il échouera avec EAGAIN. La socket ZMQ_PEER ne rejettera aucun message dans tous les cas.


Note

Les sockets ZMQ_PEER sont thread-safe. Elles n'acceptent pas l'option ZMQ_SNDMORE lors des envois, ni ZMQ_RCVMORE lors des réceptions. Cela les limite aux données en une seule partie.

Modèle natif

Le modèle natif est utilisé pour communiquer avec des pairs TCP et permet des requêtes et des réponses asynchrones dans les deux directions.

ZMQ_STREAM

Une socket de type ZMQ_STREAM est utilisée pour envoyer et recevoir des données TCP depuis un pair non-0MQ, lors de l'utilisation du transport tcp://. Une socket ZMQ_STREAM peut agir comme client et/ou serveur, envoyant et/ou recevant des données TCP de manière asynchrone.

Lors de la réception de données TCP, une socket ZMQ_STREAM préfixera une partie de message contenant l' routing id du pair d'origine au message avant de le transmettre à l'application. Les messages reçus sont distribués de manière équitable parmi tous les pairs connectés.

Lors de l'envoi de données TCP, une socket ZMQ_STREAM retirera la première partie du message et l'utilisera pour déterminer l' routing id du pair vers lequel le message sera routé, et les messages non routables provoqueront une erreur EHOSTUNREACH ou EAGAIN.

ZMQ_STREAM

A socket of type ZMQ_STREAM is a special socket type that simplifies the implementation of application-level protocols. It can be used to implement protocols such as HTTP, SMTP, etc. on top of ZeroMQ.

When using ZMQ_STREAM sockets, an application must first connect to a specific peer using zmq_connect, and then fetch the socket's routing ID using zmq_getsockopt with the ZMQ_ROUTING_ID option.

To close a specific connection, send the routing ID frame followed by a zero-length message (see section EXAMPLE).

When a connection is made, a zero-length message will be received by the application. Similarly, when the peer disconnects (or the connection is lost), a zero-length message will be received by the application.

You must send one routing ID frame followed by one data frame. The zmq_send(3) flag ZMQ_SNDMORE is required for routing ID frames but is ignored on data frames.

Modèle requête-réponse

Le modèle requête-réponse est utilisé pour envoyer des requêtes d'un client ZMQ_REQ à un ou plusieurs services ZMQ_REP, et pour recevoir les réponses subséquentes à chaque requête envoyée.

Le modèle requête-réponse est formellement défini par http://rfc.zeromq.org/spec:28.

ZMQ_REQ

Un socket de type ZMQ_REQ est utilisé par un client pour envoyer des requêtes et recevoir des réponses d'un service. Ce type de socket ne permet qu'une séquence alternée d'appels zmq_send(requête) et zmq_recv(réponse) subséquents. Chaque requête envoyée est distribuée en round-robin parmi tous les services, et chaque réponse reçue est mise en correspondance avec la dernière requête émise.

Pour les transports orientés connexion, si l'option ZMQ_IMMEDIATE est définie et qu'aucun service n'est disponible, toute opération d'envoi sur le socket bloquera jusqu'à ce qu'au moins un service devienne disponible. Le socket REQ ne doit pas rejeter de messages.

Sockets pairs compatibles ZMQ_REP, ZMQ_ROUTER
Direction Bidirectionnel
Modèle d'envoi/réception Envoi, Réception, Envoi, Réception, ...
Stratégie de routage sortant Round-robin
Stratégie de routage entrant Dernier pair
Action en état muet Bloquer

ZMQ_REP

Un socket de type ZMQ_REP est utilisé par un service pour recevoir des requêtes et envoyer des réponses à un client. Ce type de socket ne permet qu'une séquence alternée d'appels zmq_recv(requête) et zmq_send(réponse) subséquents. Chaque requête reçue est mise en file d'attente équitable parmi tous les clients, et chaque réponse envoyée est routée vers le client qui a émis la dernière requête. Si le destinataire d'origine n'existe plus, la réponse est silencieusement ignorée.

Table 15. Résumé des caractéristiques de ZMQ_REP

Sockets pairs compatibles ZMQ_REQ, ZMQ_DEALER
Direction Bidirectionnel
Modèle d'envoi/réception Réception, Envoi, Réception, Envoi, ...
Stratégie de routage entrant File d'attente équitable
Stratégie de routage sortant Dernier pair

ZMQ_DEALER

Un socket de type ZMQ_DEALER est un modèle avancé utilisé pour étendre les sockets requête/réponse. Chaque message envoyé est distribué en round-robin parmi tous les pairs connectés, et chaque message reçu est mis en file d'attente équitable à partir de tous les pairs connectés.

Lorsqu'un socket ZMQ_DEALER entre dans l'état muet parce qu'il a atteint la limite de la haute file d'attente pour tous les pairs, ou, pour les transports orientés connexion, si l'option ZMQ_IMMEDIATE est définie et qu'il n'y a aucun pair du tout, alors toute opération zmq_send(3) sur le socket bloquera jusqu'à ce que l'état muet prenne fin ou qu'au moins un pair devienne disponible pour l'envoi ; les messages ne sont pas rejetés.

Lorsqu'un socket ZMQ_DEALER est connecté à un socket ZMQ_REP, chaque message envoyé doit consister en une partie de message vide, le délimiteur, suivie d'une ou plusieurs parties de corps.

ZMQ_ROUTER

Un socket de type ZMQ_ROUTER est un type de socket avancé utilisé pour étendre les sockets requête/réponse. Lors de la réception de messages, un socket ZMQ_ROUTER préfixera une partie de message contenant l'ID de routage du pair d'origine au message avant de le transmettre à l'application. Les messages reçus sont mis en file d'attente équitable parmi tous les pairs connectés. Lors de l'envoi de messages, un socket ZMQ_ROUTER supprimera la première partie du message et l'utilisera pour déterminer l' ID de routage du pair vers lequel le message doit être routé. Si le pair n'existe plus, ou n'a jamais existé, le message sera silencieusement ignoré. Cependant, si l'option de socket ZMQ_ROUTER_MANDATORY est définie à 1, le socket échouera avec EHOSTUNREACH dans les deux cas.

Lorsqu'un socket ZMQ_ROUTER entre dans l'état muet parce qu'il a atteint la limite de la haute file d'attente pour tous les pairs, tous les messages envoyés au socket seront rejetés jusqu'à ce que l'état muet prenne fin. De même, tous les messages routés vers un pair pour lequel la limite individuelle de la haute file d'attente a été atteinte seront également rejetés. Si ZMQ_ROUTER_MANDATORY est défini à 1, le socket bloquera ou retournera EAGAIN dans les deux cas.

Lorsqu'un socket ZMQ_ROUTER a le drapeau ZMQ_ROUTER_MANDATORY défini à 1, le socket générera des événements ZMQ_POLLIN lors de la réception de messages d'un ou plusieurs pairs. De même, le socket générera des événements ZMQ_POLLOUT lorsqu'au moins un message peut être envoyé à un ou plusieurs pairs.

Lorsqu'un socket ZMQ_REQ est connecté à un socket ZMQ_ROUTER, en plus de l'ID de routage du pair d'origine, chaque message reçu contiendra une partie de message vide, le délimiteur. Par conséquent, la structure entière de chaque message reçu telle que vue par l'application devient : une ou plusieurs parties d'ID de routage, une partie de délimiteur, une ou plusieurs parties de corps. Lors de l'envoi de réponses à un socket ZMQ_REQ, l'application doit inclure la partie de délimiteur.

zmq_socket(3) — 0MQ 4.3.5

NAME

zmq_socket — create a new ØMQ socket of the specified type

SYNOPSIS

#include <zmq.h>

void *zmq_socket (void *context, int type);

DESCRIPTION

The zmq_socket 0MQ function shall create a new socket and return its handle. The context argument is a pointer to the ØMQ context the socket will be associated with.

The type argument specifies the socket type. The following socket types are available:

ZMQ_REQ

Client socket that sends requests and blocks until a reply is received.

ZMQ_REP

Server socket that receives requests and sends replies.

ZMQ_PUB

Publisher socket that publishes messages to connected subscribers.

ZMQ_SUB

Subscriber socket that subscribes to messages published by publishers.

ZMQ_PUSH

Push socket that sends messages to connected pull sockets.

ZMQ_PULL

Pull socket that receives messages from connected push sockets.

ZMQ_ROUTER

Router socket that can send and receive messages. It also supports sticky sessions.

ZMQ_DEALER

Dealer socket that can send and receive messages. It does not support sticky sessions.

ZMQ_PAIR

Pair socket that can send and receive messages.

RETURN VALUE

On success, the zmq_socket 0MQ function shall return a pointer to the new socket. On failure, it shall return NULL and set an error code describing the error.

ERRORS

EINVAL

Invalid context or socket type specified.

EMFILE

Maximum number of file descriptors allowed on this system has been reached.

ENFILE

Maximum number of files is open in the system.

ENOMEM

Insufficient memory available.

EXAMPLE

Example code demonstrating the usage of zmq_socket:

/*  Get HTTP request; routing id frame and then request */
        routing_id_size = zmq_recv (socket, routing_id, 256, 0);
        assert (routing_id_size > 0);
        do {
                raw_size = zmq_recv (socket, raw, 256, 0);
                assert (raw_size >= 0);
        } while (raw_size == 256);
        /* Prepares the response */
        char http_response [] =
                "HTTP/1.0 200 OK\r\n"
                "Content-Type: text/plain\r\n"
                "\r\n"
                "Hello, World!";
        /* Sends the routing id frame followed by the response */
        zmq_send (socket, routing_id, routing_id_size, ZMQ_SNDMORE);
        zmq_send (socket, http_response, strlen (http_response), 0);
        /* Closes the connection by sending the routing id frame followed by a zero response */
        zmq_send (socket, routing_id, routing_id_size, ZMQ_SNDMORE);
        zmq_send (socket, 0, 0, 0);
}
zmq_close (socket);
zmq_ctx_destroy (ctx);
