NOM

zshbuiltins - commandes internes de zsh

COMMANDES INTERNES DU SHELL

Certaines commandes internes du shell acceptent des options comme décrit dans les entrées individuelles ; celles-ci sont souvent appelées des `flags' dans la liste ci-dessous pour éviter la confusion avec les options du shell, qui peuvent également avoir un effet sur le comportement des commandes internes. Dans cette section d'introduction, `option' a toujours le sens d'une option d'une commande qui devrait être familière à la plupart des utilisateurs de ligne de commande.

Typiquement, les options sont des lettres uniques précédées d'un trait d'union (-). Les options qui prennent un argument l'acceptent soit immédiatement après la lettre de l'option, soit après un espace blanc, par exemple `print -C3 {1..9}' ou `print -C 3 {1..9}' sont équivalents. Les arguments des options ne sont pas les mêmes que les arguments de la commande ; la documentation indique lesquels sont lesquels. Les options qui ne prennent pas d'argument peuvent être combinées en un seul mot, par exemple `print -rca -- *' et `print -r -c -a -- *' sont équivalents.

Certaines commandes internes du shell acceptent également des options qui commencent par `+' au lieu de `-'. La liste ci-dessous précise quelles commandes sont concernées.

Les options (ainsi que leurs arguments individuels, le cas échéant) doivent apparaître dans un groupe avant tout argument non optionnel ; une fois le premier argument non optionnel trouvé, le traitement des options est terminé.

Toutes les commandes internes, à l'exception de `echo' et des modificateurs de précommande, même celles qui n'ont pas d'options, peuvent recevoir l'argument `--' pour terminer le traitement des options. Cela indique que les mots suivants sont des arguments non optionnels, mais est par ailleurs ignoré. C'est utile dans les cas où les arguments de la commande peuvent commencer par `-'. Pour des raisons historiques, la plupart des commandes internes (y compris `echo') reconnaissent également un seul `-' dans un mot séparé à cet effet ; notez que c'est moins standard et que l'utilisation de `--' est recommandée.

- commande simple
Voir la section `Modificateurs de précommande' dans zshmisc(1).
. fichier [ arg ... ]
Lit les commandes à partir de fichier et les exécute dans l'environnement shell actuel.

Si fichier ne contient pas de slash, ou si PATH_DIRS est défini, le shell recherche dans les composants de $path pour trouver le répertoire contenant fichier. Les fichiers du répertoire courant ne sont pas lus à moins que `.' n'apparaisse quelque part dans $path. Si un fichier nommé `fichier.zwc' est trouvé, qu'il est plus récent que fichier, et qu'il s'agit de la forme compilée (créée avec la commande interne zcompile) de fichier, alors les commandes sont lues à partir de ce fichier au lieu de fichier.

Si des arguments arg sont donnés, ils deviennent les paramètres positionnels ; les anciens paramètres positionnels sont restaurés lorsque fichier a fini de s'exécuter. Cependant, si aucun argument n'est donné, les paramètres positionnels restent ceux du contexte d'appel, et aucune restauration n'est effectuée.

Si fichier n'a pas été trouvé, le statut de retour est 127 ; si fichier a été trouvé mais contenait une erreur de syntaxe, le statut de retour est 126 ; sinon, le statut de retour est le statut de sortie de la dernière commande exécutée.

: [ arg ... ]
Cette commande ne fait rien, bien que les expansions normales d'arguments soient effectuées, ce qui peut avoir des effets sur les paramètres du shell. Un statut de sortie nul est retourné.
alias [ {+|-}gmrsL ] [ nom[=valeur] ... ]
Pour chaque nom avec une valeur correspondante, définit un alias avec cette valeur. Un espace final dans valeur fait que le mot suivant est vérifié pour l'expansion d'alias. Si le drapeau -g est présent, définit un alias global ; les alias globaux sont étendus même s'ils n'apparaissent pas en position de commande :
% perldoc --help 2>&1 | grep 'built-in functions'
    -f   Search Perl built-in functions
% alias -g HG='--help 2>&1 | grep'
% perldoc HG 'built-in functions'
    -f   Search Perl built-in functions

Si le drapeau -s est présent, définit un alias de suffixe : si le mot commande sur une ligne de commande est sous la forme `texte.nom', où texte est toute chaîne non vide, il est remplacé par le texte `valeur texte.nom'. Notez que nom est traité comme une chaîne littérale, pas comme un modèle. Un espace final dans valeur n'est pas spécial dans ce cas. Par exemple,

alias -s ps='gv --'

fera que la commande `*.ps' sera étendue en `gv -- *.ps'. Comme l'expansion d'alias est effectuée plus tôt que le globbing, le `*.ps' sera alors étendu. Les alias de suffixe constituent un espace de noms différent des autres alias (donc dans l'exemple ci-dessus, il est toujours possible de créer un alias pour la commande ps) et les deux ensembles ne sont jamais listés ensemble.

Pour chaque nom sans valeur, affiche la valeur de nom, le cas échéant. Sans arguments, affiche tous les alias actuellement définis, autres que les alias de suffixe. Si le drapeau -m est donné, les arguments sont pris comme des modèles (ils doivent être cités pour éviter qu'ils ne soient interprétés comme des modèles de globbing), et les alias correspondant à ces modèles sont affichés. Lors de l'affichage des alias et si l'un des drapeaux -g, -r ou -s est présent, restreint l'affichage aux alias globaux, réguliers ou de suffixe, respectivement ; un alias régulier est celui qui n'est ni global ni de suffixe. Utiliser `+' au lieu de `-', ou terminer la liste des options par un seul `+', empêche l'affichage des valeurs des alias.

Si le drapeau -L est présent, alors affiche chaque alias d'une manière adaptée à être placée dans un script de démarrage. Le statut de sortie est non nul si un nom (sans valeur) est donné pour lequel aucun alias n'a été défini.

Pour en savoir plus sur les alias, y compris les problèmes courants, consultez la section ALIASING dans zshmisc(1).

autoload [ {+|-}RTUXdkmrtWz ] [ -w ] [ nom ... ]
Voir la section `Fonctions auto-chargées' dans zshmisc(1) pour tous les détails. Le paramètre fpath sera recherché pour trouver la définition de la fonction lors de la première référence à la fonction.

Si nom consiste en un chemin absolu, la fonction est définie pour se charger à partir du fichier donné (recherchant comme d'habitude les fichiers de vidage dans l'emplacement donné). Le nom de la fonction est le nom de base (partie non répertoire) du fichier. C'est normalement une erreur si la fonction n'est pas trouvée à l'emplacement donné ; cependant, si l'option -d est donnée, la recherche de la fonction prend par défaut $fpath. Si une fonction est chargée par chemin absolu, toute fonction chargée à partir de celle-ci et marquée pour autoload sans chemin absolu aura le chemin de chargement de la fonction parente temporairement ajouté à $fpath.

Si l'option -r ou -R est donnée, la fonction est recherchée immédiatement et son emplacement est enregistré en interne pour être utilisé lors de l'exécution de la fonction ; un chemin relatif est développé en utilisant la valeur de $PWD. Cela protège contre un changement de $fpath après l'appel à autoload. Avec -r, si la fonction n'est pas trouvée, elle reste silencieusement non résolue jusqu'à son exécution ; avec -R, un message d'erreur est affiché et le traitement de la commande est immédiatement interrompu si la recherche échoue, c'est-à-dire lors de la commande autoload plutôt qu'à l'exécution de la fonction.

Le drapeau -X ne peut être utilisé qu'à l'intérieur d'une fonction shell. Il provoque le marquage de la fonction appelante pour l'auto-chargement, puis son chargement et son exécution immédiats, avec le tableau actuel des paramètres positionnels comme arguments. Cela remplace la définition précédente de la fonction. Si aucune définition de fonction n'est trouvée, une erreur est affichée et la fonction reste indéfinie et marquée pour l'auto-chargement. Si un argument est donné, il est utilisé comme répertoire (c'est-à-dire qu'il n'inclut pas le nom de la fonction) dans lequel la fonction doit être trouvée ; cela peut être combiné avec l'option -d pour permettre à la recherche de fonction de prendre par défaut $fpath si elle n'est pas à l'emplacement donné.

Le drapeau +X tente de charger chaque nom en tant que fonction auto-chargée, mais ne l'exécute pas. Le statut de sortie est zéro (succès) si la fonction n'était pas précédemment définie et qu'une définition pour celle-ci a été trouvée. Cela ne remplace aucune définition existante de la fonction. Dans le cas où la fonction reste indéfinie et marquée pour le chargement automatique. Si le chargement automatique de style ksh est activé, la fonction créée contiendra le contenu du fichier plus un appel à la fonction elle-même ajouté à celui-ci, donnant ainsi un comportement de chargement automatique ksh normal lors du premier appel à la fonction. Si le flag -m est également donné, chaque nom est traité comme un motif et toutes les fonctions déjà marquées pour le chargement automatique qui correspondent au motif sont chargées.

Avec le flag -t, active le traçage d'exécution ; avec -T, active le traçage d'exécution uniquement pour la fonction actuelle, le désactivant à l'entrée de toute fonction appelée qui n'a pas également le traçage activé.

Avec le flag -U, l'expansion des alias est supprimée lors du chargement de la fonction.

Avec le flag -w, les noms sont pris comme noms de fichiers compilés avec l'utilitaire zcompile, et toutes les fonctions définies dans ceux-ci sont marquées pour le chargement automatique.

Les flags -z et -k marquent la fonction pour être chargée automatiquement en utilisant le style zsh ou ksh, comme si l'option KSH_AUTOLOAD était désactivée ou activée, respectivement. Les flags remplacent le réglage de l'option au moment où la fonction est chargée.

Notez que la commande autoload ne tente pas de garantir que les options du shell définies lors du chargement ou de l'exécution du fichier aient une valeur particulière. Pour cela, la commande emulate peut être utilisée :

emulate zsh -c 'autoload -Uz func'

arrange que lorsque func est chargé, le shell soit en émulation native zsh, et que cette émulation soit également appliquée lorsque func est exécuté.

Certaines des fonctions de autoload sont également fournies par functions -u ou functions -U, mais autoload est une interface plus complète.

cd [ -qsLP ] [ arg ]
cd [ -qsLP ] old new
cd [ -qsLP ] {+|-}n
Change le répertoire courant. Dans la première forme, change le répertoire courant vers arg, ou vers la valeur de $HOME si arg n'est pas spécifié. Si arg est `-', change vers le répertoire précédent.

Sinon, si arg commence par un slash, tente de changer pour le répertoire donné par arg.

Si arg ne commence pas par un slash, le comportement dépend de si le répertoire courant `.' apparaît dans la liste des répertoires contenus dans le paramètre shell cdpath. S'il n'y apparaît pas, tente d'abord de changer pour le répertoire arg sous le répertoire courant, et si cela échoue mais que cdpath est défini et contient au moins un élément, tente de changer pour le répertoire arg sous chaque composant de cdpath tour à tour jusqu'à succès. Si `.' apparaît dans cdpath, alors cdpath est recherché strictement dans l'ordre, de sorte que `.' ne soit essayé qu'au point approprié.

L'ordre de test de cdpath est modifié si l'option POSIX_CD est définie, comme décrit dans la documentation de l'option.

Si aucun répertoire n'est trouvé, que l'option CDABLE_VARS est définie, et qu'un paramètre nommé arg existe dont la valeur commence par un slash, traite sa valeur comme le répertoire. Dans ce cas, le paramètre est ajouté à la table de hachage des répertoires nommés.

La deuxième forme de cd substitue la chaîne new à la chaîne old dans le nom du répertoire courant, et essaie de changer pour ce nouveau répertoire.

La troisième forme de cd extrait une entrée de la pile de répertoires, et change pour ce répertoire. Un argument de la forme `+n' identifie une entrée de pile en comptant depuis la gauche de la liste affichée par la commande dirs, en commençant par zéro. Un argument de la forme `-n' compte depuis la droite. Si l'option PUSHD_MINUS est définie, les significations de `+' et `-' dans ce contexte sont échangées. Si l'option POSIX_CD est définie, cette forme de cd n'est pas reconnue et sera interprétée comme la première forme.

Si l'option -q (quiet) est spécifiée, la fonction hook chpwd et les fonctions du tableau chpwd_functions ne sont pas appelées. Ceci est utile pour les appels à cd qui ne modifient pas l'environnement vu par un utilisateur interactif.

Si l'option -s est spécifiée, cd refuse de changer le répertoire courant si le chemin donné contient des liens symboliques. Si l'option -P est donnée ou si l'option CHASE_LINKS est définie, les liens symboliques sont résolus en leurs vraies valeurs. Si l'option -L est donnée, les liens symboliques sont conservés dans le répertoire (et non résolus) quelle que soit l'état de l'option CHASE_LINKS.

disable [ -afmprs ] name ...
Désactive temporairement les éléments de table de hachage ou les motifs nommés. La valeur par défaut est de désactiver les commandes internes. Cela vous permet d'utiliser une commande externe portant le même nom qu'une commande interne. L'option -a fait que disable agit sur les alias réguliers ou globaux. L'option -s fait que disable agit sur les alias de suffixe. L'option -f fait que disable agit sur les fonctions shell. L'option -r fait que disable agit sur les mots réservés. Sans arguments, tous les éléments de table de hachage désactivés de la table de hachage correspondante sont affichés. Avec le flag -m, les arguments sont pris comme des motifs (qui devraient être mis entre guillemets pour éviter leur expansion de nom de fichier), et tous les éléments de table de hachage de la table de hachage correspondante correspondant à ces motifs sont désactivés. Les objets désactivés peuvent
être activé avec la commande enable.

Avec l'option -p, name ... fait référence à des éléments de la syntaxe de modèles du shell, tels que décrits dans la section `Génération de noms de fichiers'. Certains éléments peuvent être désactivés séparément, comme indiqué ci-dessous.

Notez que les modèles non autorisés par les paramètres actuels des options EXTENDED_GLOB, KSH_GLOB et SH_GLOB ne sont jamais activés, quelle que soit la configuration ici. Par exemple, si EXTENDED_GLOB n'est pas actif, le modèle ^ est inefficace même si `disable -p "^"' n'a pas été émis. La liste ci-dessous indique tous les paramètres d'options qui restreignent l'utilisation du modèle. Il convient de noter que la définition de SH_GLOB a un effet plus large que la simple désactivation des modèles, car certaines expressions, en particulier celles impliquant des parenthèses, sont analysées différemment.

Les modèles suivants peuvent être désactivés ; toutes les chaînes doivent être mises entre guillemets sur la ligne de commande pour les empêcher d'être interprétées immédiatement comme des modèles, et les modèles sont présentés ci-dessous entre guillemets simples pour rappel.

emulate [ -lLR ] [ {zsh|sh|ksh|csh} [ flags ... ] ]
Sans aucun argument, imprime le mode d'émulation actuel.

Avec un seul argument, configure les options zsh pour émuler le shell spécifié autant que possible. csh ne sera jamais complètement émulé. Si l'argument n'est pas l'un des shells listés ci-dessus, zsh sera utilisé par défaut ; plus précisément, les tests effectués sur l'argument sont les mêmes que ceux utilisés pour déterminer l'émulation au démarrage en fonction du nom du shell, voir la section COMPATIBILITY dans zsh(1). En plus de définir les options du shell, la commande restaure également l'état vierge des activations de modèles, comme si tous les modèles avaient été activés à l'aide de enable -p.

Si la commande emulate se trouve à l'intérieur d'une fonction qui a été marquée pour le traçage d'exécution avec functions -t, alors l'option xtrace sera activée quelle que soit l'émulation ou les autres options. Notez que le code exécuté à l'intérieur de la fonction par les commandes ., source ou eval n'est pas considéré comme étant exécuté directement à partir de la fonction, et ne provoque donc pas ce comportement.

Si le commutateur -R est donné, toutes les options modifiables sont réinitialisées à leur valeur par défaut correspondant au mode d'émulation spécifié, à l'exception de certaines options décrivant l'environnement interactif ; sinon, seules les options susceptibles de causer des problèmes de portabilité dans les scripts et les fonctions sont modifiées. Si le commutateur -L est donné, les options LOCAL_OPTIONS, LOCAL_PATTERNS et LOCAL_TRAPS seront également définies, rendant les effets de la commande emulate et de toutes les commandes setopt, disable -p ou enable -p, et trap locaux à la fonction shell immédiatement englobante, le cas échéant ; normalement, ces options sont désactivées dans tous les modes d'émulation sauf ksh. Le commutateur -L est mutuellement exclusif avec l'utilisation de -c dans flags.

Si un seul argument est donné et que le commutateur -l est activé, les options qui seraient définies ou désactivées (ces dernières indiquées par le préfixe `no') sont listées. -l peut être combiné avec -L ou -R et la liste sera modifiée de manière appropriée. Notez que la liste ne dépend pas du réglage actuel des options, c'est-à-dire qu'elle comprend toutes les options qui peuvent en principe changer, et pas seulement celles qui changeraient réellement.

Les flags peuvent être n'importe lequel des drapeaux de temps d'invocation décrits dans la section INVOCATION dans zsh(1), sauf que `-o EMACS' et `-o VI' ne peuvent pas être utilisés. Les drapeaux tels que `+r'/`+o RESTRICTED' peuvent être interdits dans certaines circonstances.

Si -c arg apparaît dans flags, arg est évalué pendant que l'émulation demandée est temporairement en vigueur. Dans ce cas, le mode d'émulation et toutes les options sont restaurés à leurs valeurs précédentes avant que emulate ne retourne. Le commutateur -R peut précéder le nom du shell à émuler ; notez que cela a un sens distinct de l'inclusion de -R dans flags.

L'utilisation de -c active le mode d'émulation `collant' pour les fonctions définies dans l'expression évaluée : le mode d'émulation est associé par la suite à la fonction de sorte que chaque fois que la fonction est exécutée, l'émulation (respectant le commutateur -R, le cas échéant) et toutes les options sont définies (et les désactivations de modèles sont effacées) avant l'entrée dans la fonction, et l'état est restauré après la sortie. Si la fonction est appelée alors que l'émulation collante est déjà en vigueur, soit dans une expression `emulate shell -c', soit dans une autre fonction avec la même émulation collante, l'entrée et la sortie de la fonction ne provoquent pas de modification des options (sauf en raison du traitement standard tel que l'option LOCAL_OPTIONS). Cela s'applique également aux fonctions marquées pour l'autoloading dans l'émulation collante ; l'ensemble approprié d'options sera appliqué au moment où la fonction est chargée ainsi qu'à son exécution.

Par exemple :

emulate sh -c 'fni() { setopt cshnullglob; }
fno() { fni; }'
fno

Les deux fonctions fni et fno sont définies avec une émulation sh collante. fno est ensuite exécutée, ce qui amène les options associées aux émulations à être définies à leurs valeurs dans sh. fno appelle ensuite fni ; comme fni est également marquée pour l'émulation sh collante, aucun changement d'option ne se produit à l'entrée ou à la sortie de celle-ci. Par conséquent, l'option cshnullglob, désactivée par l'émulation sh, sera activée dans fni et restera activée au retour à fno. À la sortie

from fno, le mode d'émulation et toutes les options seront restaurés à l'état dans lequel ils étaient avant l'entrée dans l'émulation temporaire.

La documentation ci-dessus est généralement suffisante pour le but visé d'exécuter du code conçu pour d'autres shells dans un environnement approprié. Des règles plus détaillées suivent.

1.
L'environnement d'émulation collant fourni par `emulate shell -c' est identique à celui fourni par l'entrée dans une fonction marquée pour l'émulation collante en conséquence de sa définition dans un tel environnement. Par conséquent, par exemple, l'émulation collante est héritée par les sous-fonctions définies dans des fonctions avec émulation collante.
2.
Aucun changement d'options n'a lieu à l'entrée ou à la sortie des fonctions qui ne sont pas marquées pour l'émulation collante, autres que ceux qui auraient normalement lieu, même si ces fonctions sont appelées dans une émulation collante.
3.
Aucun traitement spécial n'est fourni pour les fonctions marquées pour autoload ni pour les fonctions présentes dans le wordcode créé par la commande zcompile.
4.
La présence ou l'absence du commutateur -R à emulate correspond à différents modes d'émulation collante, donc par exemple `emulate sh -c', `emulate -R sh -c' et `emulate csh -c' sont traités comme trois émulations collantes distinctes.
5.
Une différence dans les options de shell fournies en plus de l'émulation de base signifie également que les émulations collantes sont différentes, donc par exemple `emulate zsh -c' et `emulate zsh -o cbases -c' sont traités comme des émulations collantes distinctes.

Si aucun argument n'est spécifié, la liste d'historique est laissée vide, $HISTFILE est désactivé, et $HISTSIZE et $SAVEHIST sont définis à leurs valeurs par défaut. $SAVEHIST est défini sur une valeur distincte de $HISTSIZE. Vous êtes libre de modifier ces valeurs d'environnement pour la nouvelle liste d'historique comme vous le souhaitez afin de manipuler la nouvelle liste d'historique.

`fc -P' ramène la liste d'historique à une ancienne liste sauvegardée par `fc -p'. La liste actuelle est sauvegardée dans son $HISTFILE avant d'être détruite (en supposant que $HISTFILE et $SAVEHIST sont correctement définis, bien sûr). Les valeurs de $HISTFILE, $HISTSIZE et $SAVEHIST sont restaurées aux valeurs qu'elles avaient lorsque `fc -p' a été appelé. Notez que cette restauration peut entrer en conflit avec la déclaration de ces variables comme "locales", il est donc préférable d'éviter les déclarations locales pour ces variables dans les fonctions qui utilisent `fc -p'. La seule autre combinaison garantie de sécurité est de déclarer ces variables comme locales en haut de votre fonction et d'utiliser l'option automatique (-a) avec `fc -p'. Enfin, notez qu'il est légal de faire sortir manuellement une pile marquée pour une sortie automatique si vous avez besoin de le faire avant que la fonction ne se termine.

Si l'option -I est ajoutée à -A ou -W, seuls les événements nouveaux depuis la dernière inclusion/écriture incrémentielle dans le fichier d'historique sont inclus/écrits. Les indicateurs -M et +M

L'utilisation de l'option -M ne peut pas être combinée avec aucune des options gérées par typeset -f.

functions -M fnmath définit fnmath comme le nom d'une fonction mathématique reconnue dans toutes les formes d'expressions arithmétiques ; voir la section `Évaluation Arithmétique' dans zshmisc(1). Par défaut, fnmath peut prendre n'importe quel nombre d'arguments séparés par des virgules. Si min est donné, il doit avoir exactement min arguments ; si min et max sont tous deux donnés, il doit avoir au moins min et au plus max arguments. max peut être -1 pour indiquer qu'il n'y a pas de limite supérieure.

Par défaut, la fonction est implémentée par une fonction shell du même nom ; si fnshell est spécifié, il donne le nom de la fonction shell correspondante, tandis que fnmath reste le nom utilisé dans les expressions arithmétiques. Le nom de la fonction dans $0 est fnmath (pas fnshell comme ce serait normalement le cas), à condition que l'option FUNCTION_ARGZERO soit activée. Les paramètres positionnels dans la fonction shell correspondent aux arguments de l'appel de la fonction mathématique.

Le résultat de la dernière expression arithmétique évaluée à l'intérieur de la fonction shell donne le résultat de la fonction mathématique. Ceci ne se limite pas aux substitutions arithmétiques de la forme $((...)), mais inclut également les expressions arithmétiques évaluées de toute autre manière, y compris par l'intermédiaire de la commande intégrée let, par les instructions ((...)), et même par la commande intégrée return et par les indices de tableau. Par conséquent, il faut veiller à ne pas utiliser de constructions syntaxiques qui effectuent une évaluation arithmétique après avoir évalué ce qui doit être le résultat de la fonction. Par exemple :

# FAUX
zmath_cube() {
  (( $1 * $1 * $1 ))
  return 0
}
functions -M cube 1 1 zmath_cube
print $(( cube(3) ))

Cela affichera `0' à cause du return.

Commenter le return entraînerait un problème différent : l'instruction ((...)) deviendrait la dernière instruction de la fonction, donc le statut de retour ($?) de la fonction serait non nul (indiquant un échec) chaque fois que le résultat arithmétique de la fonction serait nul (numériquement) :

# FAUX
zmath_cube() {
  (( $1 * $1 * $1 ))
}
functions -M cube 1 1 zmath_cube
print $(( cube(0) ))

Au lieu de cela, la commande intégrée true peut être utilisée :

# CORRECT
zmath_cube() {
  (( $1 * $1 * $1 ))
  true
}
functions -M cube 1 1 zmath_cube
print $(( cube(3) ))

Si l'option supplémentaire -s est donnée à functions -M, l'argument de la fonction est une chaîne unique : tout ce qui se trouve entre la parenthèse ouvrante et la parenthèse fermante correspondante est passé à la fonction comme un seul argument, même s'il contient des virgules ou des espaces blancs. Les spécificateurs d'arguments minimum et maximum doivent donc être 1 s'ils sont donnés. Une liste d'arguments vide est passée sous forme de chaîne de longueur nulle. Ainsi, la fonction de chaîne suivante prend un seul argument, y compris les virgules, et affiche 11 :

stringfn() { (( $#1 )); true }
functions -Ms stringfn
print $(( stringfn(foo,bar,rod) ))

functions -M sans arguments liste toutes ces fonctions définies par l'utilisateur sous la même forme qu'une définition. Avec l'option supplémentaire -m et une liste d'arguments, toutes les fonctions dont le fnmath correspond à l'un des arguments de motif sont listées.

function +M supprime la liste des fonctions mathématiques ; avec l'option supplémentaire -m, les arguments sont traités comme des motifs et toutes les fonctions dont le fnmath correspond au motif sont supprimées. Notez que la fonction shell implémentant le comportement n'est pas supprimée (même si son nom coïncide avec fnmath).

hash [ -Ldfmrv ] [ nom[=valeur] ] ...
hash peut être utilisé pour modifier directement le contenu de la table de hachage des commandes, et la table de hachage des répertoires nommés. Normalement, on modifierait ces tables en modifiant son PATH (pour la table de hachage des commandes) ou en créant des paramètres shell appropriés (pour la table de hachage des répertoires nommés). Le choix de la table de hachage sur laquelle travailler est déterminé par l'option -d ; sans l'option, la commande a
h table est utilisé, et avec l' option, la table de hachage de répertoires nommés est utilisée.

Une commande name commençant par un / n'est jamais hachée, que ce soit par l'utilisation explicite de la commande hash ou autrement. Une telle commande est toujours trouvée par une recherche directe dans le système de fichiers.

L'option -r vide la table de hachage sélectionnée. Elle sera ensuite reconstruite de manière normale. L'option -f reconstruit immédiatement et entièrement la table de hachage sélectionnée. Pour la table de hachage des commandes, cela hache tous les répertoires absolus dans le PATH, et pour la table de hachage des répertoires nommés, cela ajoute tous les répertoires personnels des utilisateurs. Ces deux options ne peuvent pas être utilisées avec des arguments.

L'option -m fait que les arguments sont considérés comme des modèles (qui doivent être mis entre guillemets) et les éléments de la table de hachage correspondant à ces modèles sont imprimés. C'est la seule façon d'afficher une sélection limitée d'éléments de la table de hachage.

Pour chaque name avec une value correspondante, mettez `name' dans la table de hachage sélectionnée, en l'associant au chemin d'accès `value'. Dans la table de hachage des commandes, cela signifie que chaque fois que `name' est utilisé comme argument de commande, le shell essaiera d'exécuter le fichier donné par `value'. Dans la table de hachage des répertoires nommés, cela signifie que `value' peut être référencé comme `~name'.

Pour chaque name sans value correspondante, essayez d'ajouter name à la table de hachage, en vérifiant quelle est la value appropriée de la manière normale pour cette table de hachage. Si aucune value appropriée ne peut être trouvée, la table de hachage ne sera pas modifiée.

L'option -v fait que les entrées de la table de hachage sont listées au fur et à mesure de leur ajout par spécification explicite. Elle n'a aucun effet si elle est utilisée avec -f.

Envoie soit le signal SIGTERM, soit le signal spécifié aux tâches ou processus donnés. Les signaux sont donnés par numéro ou par noms, avec ou sans le préfixe `SIG'. Si le signal envoyé n'est pas `KILL' ou `CONT', alors la tâche recevra un signal `CONT' si elle est arrêtée. Sur certains systèmes, des noms de signaux alternatifs sont autorisés pour quelques signaux. Si aucun argument n'est fourni, les noms de toutes les options actuellement définies sont imprimés. La forme est choisie de manière à minimiser les différences par rapport aux options par défaut pour l'émulation en cours (l'émulation par défaut étant le zsh natif, montré comme <Z> dans zshoptions(1)). Les options qui sont activées par défaut pour l'émulation sont montrées avec le préfixe no seulement si elles sont désactivées, tandis que les autres options sont montrées sans le préfixe no et seulement si elles sont activées. En plus des options modifiées par l'utilisateur par rapport à l'état par défaut, toutes les options activées automatiquement par le shell (par exemple, SHIN_STDIN ou INTERACTIVE) seront montrées dans la liste. Le format est en outre modifié par l'option KSH_OPTION_PRINT, cependant la raison pour laquelle on choisit les options avec ou sans le préfixe no reste la même dans ce cas.

Si l'indicateur -m est donné, les arguments sont pris comme des motifs (qui devraient être mis entre guillemets pour les protéger de l'expansion des noms de fichiers), et toutes les options dont les noms correspondent à ces motifs sont définies.

Notez qu'un nom d'option incorrect ne provoque pas l'abandon de l'exécution du code shell suivant ; ce comportement est différent de celui de `set -o'. C'est parce que set est considéré comme une commande interne spéciale par la norme POSIX, mais setopt ne l'est pas.

shift [ -p ] [ n ] [ nom ... ]
Les paramètres positionnels ${n+1} ... sont renommés en $1 ..., où n est une expression arithmétique qui vaut par défaut 1. Si des names sont donnés, alors les tableaux avec ces noms sont décalés au lieu des paramètres positionnels.

Si l'option -p est donnée, les arguments sont plutôt retirés (popped) de la fin plutôt que du début du tableau.

source fichier [ arg ... ]
Identique à `.', sauf que le répertoire courant est toujours recherché et est toujours recherché en premier, avant les répertoires dans $path.
stat
Voir la section « Le module zsh/stat » dans zshmodules(1).
suspend [ -f ]
Suspend l'exécution du shell (lui envoie un SIGTSTP) jusqu'à ce qu'il reçoive un SIGCONT. Sauf si l'option -f est donnée, cela refusera de suspendre un shell de connexion.
test [ arg ... ]
[ [ arg ... ] ]
Comme la version système de test. Ajouté pour la compatibilité ; utilisez plutôt des expressions conditionnelles (voir la section « Expressions Conditionnelles »). Les principales différences entre la syntaxe des expressions conditionnelles et les commandes internes test et [ sont : ces commandes ne sont pas traitées syntaxiquement, donc par exemple une expansion de variable vide peut provoquer l'omission d'un argument ; les erreurs de syntaxe retournent le statut 2 au lieu d'une erreur de shell ; et les opérateurs arithmétiques attendent des arguments entiers plutôt que des expressions arithmétiques.

La commande tente d'implémenter POSIX et ses extensions là où elles sont spécifiées. Malheureusement, il y a des ambiguïtés intrinsèques dans la syntaxe ; en particulier, il n'y a pas de distinction entre les opérateurs de test et les chaînes qui leur ressemblent. La norme tente de les résoudre pour un petit nombre d'arguments (jusqu'à quatre) ; pour cinq arguments ou plus, la compatibilité ne peut pas être garantie. Les utilisateurs sont invités, dans la mesure du possible, à utiliser la syntaxe de test `[[' qui ne présente pas ces ambiguïtés.

times
Imprime les temps utilisateur et système accumulés pour le shell et pour les processus exécutés depuis le shell.
trap [ arg ] [ sig ... ]
arg est une série de commandes (généralement mises entre guillemets pour les protéger de l'évaluation immédiate par le shell) à lire et exécuter lorsque le shell reçoit l'un des signaux spécifiés par un ou plusieurs arguments sig. Chaque sig peut être donné sous forme de nombre, ou sous forme de nom de signal avec ou sans la chaîne SIG devant (par exemple, 1, HUP et SIGHUP correspondent tous au même signal).

Si arg est `-', alors les signaux spécifiés sont réinitialisés à leurs valeurs par défaut, ou, si aucun argument sig n'est présent, tous les pièges sont réinitialisés.

Si arg est une chaîne vide, alors les signaux spécifiés sont ignorés par le shell (et par les commandes qu'il invoque).

Si arg est omis mais qu'un ou plusieurs arguments sig sont présents (c'est-à-dire que le premier argument est un nombre de signal ou un nom de signal valide), l'effet est le même que si arg avait été spécifié comme `-'.

La commande trap sans arguments imprime une liste des commandes associées à chaque signal.

Si sig est ZERR, alors arg sera exécuté après chaque commande avec un statut de sortie non nul. ERR est un alias pour ZERR sur les systèmes qui n'ont pas de signal SIGERR (ce qui est le cas habituel).

Si sig est DEBUG, alors arg sera exécuté avant chaque commande si l'option DEBUG_BEFORE_CMD est définie (comme elle l'est par défaut), sinon après chaque commande. Ici, une `commande' est ce qui est décrit comme une `sous-liste' dans la grammaire du shell, voir la section COMMANDES SIMPLES ET PIPELINES dans zshmisc(1). Si DEBUG_BEFORE_CMD est définie, diverses fonctionnalités supplémentaires sont disponibles. Premièrement, il est possible de sauter la commande suivante en définissant l'option ERR_EXIT ; voir la description de l'option ERR_EXIT dans zshoptions(1). De plus, le paramètre shell ZSH_DEBUG_CMD est défini sur la chaîne correspondant à la commande à exécuter après le piège. Notez que cette chaîne est reconstruite à partir du format interne et peut ne pas être formatée de la même manière que le texte original. Le paramètre est désactivé après l'exécution du piège.

Si sig est 0 ou EXIT et que l'instruction trap est exécutée à l'intérieur du corps d'une fonction, alors la commande arg est exécutée après la fin de la fonction. La valeur de $? au début de l'exécution est le statut de sortie du shell ou le statut de retour de la fonction qui se termine. Si sig est 0 ou EXIT et que l'instruction trap n'est pas exécutée à l'intérieur du corps d'une fonction, alors la commande arg est exécutée lorsque le shell se termine ; le piège s'exécute avant toute fonction de hook zshexit.

Les pièges ZERR, DEBUG et EXIT ne sont pas exécutés à l'intérieur d'autres pièges. Les pièges ZERR et DEBUG sont conservés dans les sous-shells, tandis que les autres pièges sont réinitialisés.

Notez que les pièges définis avec la commande interne trap sont légèrement différents de ceux définis comme `TRAPNAL () { ... }', car ces derniers ont leur propre environnement de fonction (numéros de ligne, variables locales, etc.) tandis que les premiers utilisent l'environnement de la commande dans laquelle ils ont été appelés. Par exemple,

trap 'print $LINENO' DEBUG

imprimera le numéro de ligne d'une commande exécutée après son exécution, tandis que

TRAPDEBUG() { print $LINENO; }

imprimera toujours le numéro zéro.

Des noms de signaux alternatifs sont autorisés comme décrit sous kill ci-dessus. La définition d'un piège sous l'un ou l'autre nom entraîne la suppression de tout piège sous un nom alternatif. Cependant, il est recommandé pour la cohérence que les utilisateurs s'en tiennent exclusivement à un nom ou à l'autre.

true [ arg ... ]
Ne rien faire et renvoyer un statut de sortie de 0.
ttyctl [ -fu ]
L'option -f gèle le tty (c'est-à-dire le terminal ou l'émulateur de terminal), et -u le dégèle. Lorsque le tty est gelé, aucun changement apporté aux paramètres du tty par des programmes externes ne sera honoré par le shell, à l'exception des changements de taille de l'écran ; le shell réinitialisera simplement les paramètres à leurs valeurs précédentes dès que chaque commande se termine ou est suspendue. Ainsi, stty et des programmes similaires n'ont aucun effet lorsque le tty est gelé. Geler le tty ne provoque pas la mémorisation de l'état actuel : au lieu de cela, cela empêche les changements futurs de l'état d'être bloqués.

Sans options, il indique si le terminal est gelé ou non.

Notez que, que le tty soit gelé ou non, le shell doit changer les paramètres

gs au démarrage de l'éditeur de ligne, donc le déblocage du tty ne garantit pas que les paramètres définis sur la ligne de commande soient préservés. Les chaînes de commandes exécutées entre l'édition de la ligne de commande verront un état de tty cohérent. Voir également la variable shell STTY pour un moyen d'initialiser le tty avant d'exécuter des commandes externes et/ou de bloquer le tty autour d'une seule commande.

type [ -wfpamsS ] nom ...
Équivalent à whence -v.
typeset [ {+|-}AHUaghlmrtux ] [ {+|-}EFLRZip [ n ] ]
[ + ] [ nom[=valeur] ... ]
typeset -T [ {+|-}Uglrux ] [ {+|-}LRZp [ n ] ]
[ + | SCALAR[=valeur] tableau[=(valeur ...)] [ sep ] ]
typeset -f [ {+|-}TUkmtuz ] [ + ] [ nom ... ]
Définit ou affiche les attributs et les valeurs des paramètres shell.

Sauf indication contraire ci-dessous pour les indicateurs de contrôle qui modifient le comportement, un paramètre est créé pour chaque nom qui n'y fait pas encore référence. Lorsque vous êtes à l'intérieur d'une fonction, un nouveau paramètre est créé pour chaque nom (même ceux qui existent déjà), et est désactivé à nouveau lorsque la fonction se termine. Voir « Paramètres locaux » dans zshparam(1). Les mêmes règles s'appliquent aux paramètres spéciaux du shell, qui conservent leurs attributs spéciaux lorsqu'ils sont rendus locaux.

Pour chaque assignation nom=valeur, le paramètre nom est défini à valeur. Si l'assignation est omise et que nom ne fait pas référence à un paramètre existant, un nouveau paramètre est initialisé à une chaîne vide, zéro ou un tableau vide (selon le cas), sauf si l'option shell TYPESET_TO_UNSET est définie. Lorsque cette option est définie, les attributs du paramètre sont enregistrés mais le paramètre reste non défini.

Si l'option shell TYPESET_SILENT n'est pas définie, pour chaque nom restant qui fait référence à un paramètre déjà défini, le nom et la valeur du paramètre sont imprimés sous forme d'une assignation. Rien n'est imprimé pour les paramètres nouvellement créés, ou lorsque des indicateurs d'attributs listés ci-dessous sont donnés avec le nom. Utiliser `+' au lieu de moins pour introduire un attribut le désactive.

Si aucun nom n'est présent, les noms et les valeurs de tous les paramètres sont imprimés. Dans ce cas, les indicateurs d'attributs limitent l'affichage à uniquement les paramètres qui ont les attributs spécifiés, et l'utilisation de `+' plutôt que `-' pour introduire l'indicateur supprime l'impression des valeurs des paramètres lorsqu'il n'y a pas de nom de paramètre.

Toutes les formes de la commande gèrent l'assignation scalaire. L'assignation de tableau est possible si l'un des mots réservés declare, export, float, integer, local, readonly ou typeset correspond lors de l'analyse de la ligne (N.B. pas lors de son exécution). Dans ce cas, les arguments sont analysés comme des assignations, à l'exception du fait que la syntaxe `+=' et l'option GLOB_ASSIGN ne sont pas prises en charge, et les valeurs scalaires après = ne sont pas davantage divisées en mots, même si elles sont développées (indépendamment du réglage de l'option KSH_TYPESET; cette option est obsolète).

Exemples des différences entre l'analyse des commandes et des mots réservés:

# Analyse des mots réservés
typeset svar=$(echo un mot) avar=(plusieurs mots)

Ce qui précède crée un paramètre scalaire svar et un paramètre de tableau avar comme si les assignations avaient été

svar="un mot"
avar=(plusieurs mots)

En revanche :

# Interface de commande intégrée normale
builtin typeset svar=$(echo deux mots)

Le mot-clé builtin fait que ce qui précède utilise l'interface intégrée standard de typeset dans laquelle l'analyse des arguments est effectuée de la même manière que pour les autres commandes. Cet exemple crée un scalaire svar contenant la valeur deux et un autre paramètre scalaire mots sans valeur. Une valeur de tableau dans ce cas provoquerait soit une erreur, soit serait traitée comme un ensemble obscur de qualificateurs globaux.

Des arguments arbitraires sont autorisés s'ils prennent la forme d'assignations après expansion de la ligne de commande ; cependant, ceux-ci n'effectuent que des assignations scalaires :

var='svar=val'
typeset $var

Ce qui précède définit le paramètre scalaire svar à la valeur val. Les parenthèses autour de la valeur dans var ne provoqueraient pas d'assignation de tableau car elles seraient traitées comme des caractères ordinaires lorsque $var est substitué. Toute expansion non triviale dans la partie nom de l'assignation provoque le traitement de l'argument de cette manière :

typeset {var1,var2,var3}=nom

La syntaxe ci-dessus est valide, et a l'effet attendu de définir les trois paramètres à la même valeur, mais la ligne de commande est analysée comme un ensemble de trois arguments de ligne de commande normaux pour typeset après expansion. Par conséquent, il n'est pas possible d'assigner à plusieurs tableaux par ce biais.

Notez que chaque interface de l'une des commandes peut être désactivée séparément. Par exemple, `disable -r typeset' désactive l'interface de mot réservé pour typeset, exposant l'interface intégrée, tandis que `disable typeset' désactive l'intégrée. Notez que la désactivation de l'interface de mot réservé pour typeset peut causer des problèmes avec la sortie de `typeset -p', qui suppose que l'interface de mot réservé est disponible pour restaurer les valeurs de tableau et de tableau associatif.

Contrairement aux instructions d'assignation de paramètres, le code de sortie de typeset pour une assignation impliquant une substitution de commande ne reflète pas le code de sortie de la substitution de commande. Par conséquent, pour tester une erreur dans une substitution de commande, séparez la déclaration du paramètre de son initialisation :

# FAUX
typeset var1=$(exit 1) || echo "Problème avec var1"
# VRAI
typeset var1 && var1=$(exit 1) || echo "Problème avec var1"

Pour initialiser un paramètre param avec la sortie d'une commande et le marquer comme en lecture seule, utilisez typeset -r param ou readonly param après l'instruction d'assignation du paramètre.

Si aucun indicateur d'attribut n'est donné, et soit aucun argument nom n'est présent, soit l'indicateur +m est utilisé, alors chaque nom de paramètre imprimé est précédé d'une liste des attributs de ce paramètre (array, association, exported, float, integer, readonly, ou undefined pour les paramètres chargés automatiquement non encore chargés). Si +m est utilisé avec des indicateurs d'attributs, et que tous ces indicateurs sont introduits avec +, les noms de paramètres correspondants sont imprimés mais leurs valeurs ne le sont pas.

Les indicateurs de contrôle suivants modifient le comportement de typeset :

+
Si `+' apparaît seul dans un mot séparé comme dernière option, alors les noms de tous les paramètres (fonctions avec -f) sont imprimés, mais les valeurs (corps de fonctions) ne le sont pas. Aucun argument nom ne peut apparaître, et toute autre option suivant `+' est une erreur. L'effet de `+' est comme si tous les indicateurs d'attributs qui le précèdent étaient donnés avec un préfixe `+'. Par exemple, `typeset -U +' est équivalent à `typeset +U' et affiche les noms de tous les tableaux ayant l'attribut d'unicité, alors que `typeset -f -U +' affiche les noms de toutes les fonctions chargeables automatiquement. Si + est la seule option, alors des informations de type (tableau, lecture seule, etc.) sont également imprimées pour chaque paramètre, de la même manière que `typeset +m "*"'.
-g
Le -g (global) signifie que tout paramètre résultant ne sera pas limité à la portée locale. Notez que cela ne signifie pas nécessairement que le paramètre sera global, car l'indicateur s'appliquera à tout paramètre existant (même s'il n'est pas défini) d'une fonction englobante. Cet indicateur n'affecte pas le paramètre après sa création, il n'a donc aucun effet lors de la liste des paramètres existants, et l'indicateur +g n'a aucun effet sauf en combinaison avec -m (voir ci-dessous).
-m
Si l'indicateur -m est donné, les arguments nom sont considérés comme des modèles (utilisez des guillemets pour éviter qu'ils ne soient interprétés comme des modèles de fichiers). Sans indicateurs d'attributs, tous les paramètres (ou fonctions avec l'indicateur -f) avec des noms correspondants sont imprimés (l'option shell TYPESET_SILENT n'est pas utilisée dans ce cas).

Si l'indicateur +g est combiné avec -m, un nouveau paramètre local est créé pour chaque paramètre correspondant qui n'est pas déjà local. Sinon, -m applique tous les autres indicateurs ou assignations aux paramètres existants.

Sauf lorsque des assignations sont faites avec nom=valeur, l'utilisation de +m force l'impression des paramètres correspondants et de leurs attributs, même à l'intérieur d'une fonction. Notez que -m est ignoré si aucun modèle n'est donné, donc `typeset -m' affiche les attributs mais `typeset -a +m' ne le fait pas.

-p [ n ]
Si l'option -p est donnée, les paramètres et les valeurs sont imprimés sous la forme d'une commande typeset avec une assignation, indépendamment des autres indicateurs et options. Notez que l'indicateur -H sur les paramètres est respecté ; aucune valeur ne sera affichée pour ces paramètres.

-p peut être suivi d'un argument entier optionnel. Actuellement, seule la valeur 1 est prise en charge. Dans ce cas, les tableaux et les tableaux associatifs sont imprimés avec des sauts de ligne entre les éléments indentés pour plus de lisibilité.

-T [ scalaire[=valeur] tableau[=(valeur ...)] [ sep ] ]
Cet indicateur a une signification différente lorsqu'il est utilisé avec -f ; voir ci-dessous. Sinon, l'option -T nécessite zéro, deux ou trois arguments. Sans arguments, la liste des paramètres créés de cette manière est affichée. Avec deux ou trois arguments, les deux premiers sont le nom d'un scalaire et d'un paramètre de tableau (dans cet ordre) qui seront liés de la même manière que $PATH et $path. L'argument optionnel troisième est un séparateur à un seul caractère qui sera utilisé pour joindre les éléments du tableau afin de former le scalaire ; s'il est absent, deux-points est utilisé, comme avec $PATH. Seul le premier caractère du séparateur est significatif ; tous les caractères restants sont ignorés. Multibyte ch
caractères ne sont pas encore pris en charge.

Un seul des paramètres scalaires et tableaux peut recevoir une valeur initiale (les restrictions sur les formes d'affectation décrites ci-dessus s'appliquent également).

Le scalaire et le tableau peuvent tous deux être manipulés normalement. Si l'un est désaffecté, l'autre le sera automatiquement également. Il n'y a aucun moyen de détacher les variables sans les désaffecter, ni de convertir le type de l'une d'elles avec une autre commande typeset ; +T ne fonctionne pas, l'affectation d'un tableau à scalaire est une erreur, et l'affectation d'un scalaire à tableau le définit comme un tableau à un seul élément.

Notez que `typeset -xT ...' et `export -T ...' fonctionnent, mais seul le scalaire sera marqué pour exportation. La définition de la valeur en utilisant la version scalaire provoque une division sur tous les séparateurs (qui ne peuvent pas être cités). Il est possible d'appliquer -T à deux variables précédemment liées mais avec un caractère séparateur différent, auquel cas les variables restent jointes comme auparavant mais le séparateur est modifié.

Lorsqu'un scalaire existant est lié à un nouveau tableau, la valeur du scalaire est préservée mais aucun attribut autre que l'exportation ne sera préservé.

Les indicateurs d'attributs qui transforment la valeur finale (-L, -R, -Z, -l, -u) ne sont appliqués qu'à la valeur développée au moment d'une expression d'expansion de paramètre utilisant `$'. Ils ne sont pas appliqués lorsque le paramètre est récupéré interne par le shell à quelque fin que ce soit.

Les indicateurs d'attributs suivants peuvent être spécifiés :

-A
Les noms font référence à des paramètres de tableau associatif ; voir `Paramètres de tableau' dans zshparam(1).
-L [ n ]
Justification à gauche et suppression des blancs de début lors de l'expansion du paramètre. Si n est non nul, il définit la largeur du champ. Si n est zéro, la largeur est déterminée par la largeur de la valeur de la première affectation. Dans le cas de paramètres numériques, la longueur de la valeur complète affectée au paramètre est utilisée pour déterminer la largeur, et non la valeur qui serait affichée.

La largeur est le nombre de caractères, qui peuvent être des caractères multioctets si l'option MULTIBYTE est activée. Notez que la largeur d'écran du caractère n'est pas prise en compte ; si cela est nécessaire, utilisez le remplissage avec les indicateurs d'expansion de paramètre ${(ml...)...} comme décrit dans `Indicateurs d'expansion de paramètre' dans zshexpn(1).

Lorsque le paramètre est développé, il est rempli à droite avec des blancs ou tronqué si nécessaire pour s'adapter au champ. Notez que la troncature peut entraîner des résultats inattendus avec les paramètres numériques. Les zéros de début sont supprimés si l'indicateur -Z est également défini.

-R [ n ]
Similaire à -L, sauf que la justification à droite est utilisée ; lorsque le paramètre est développé, le champ est rempli à gauche avec des blancs ou tronqué par la fin. Ne peut pas être combiné avec l'indicateur -Z.
-U
Pour les tableaux (mais pas pour les tableaux associatifs), ne conserver que la première occurrence de chaque valeur dupliquée. Ceci peut également être défini pour des paramètres liés (voir -T) ou des paramètres spéciaux séparés par des deux-points comme PATH ou FIGNORE, etc. Notez que l'indicateur prend effet à l'affectation, et le type de la variable à laquelle on affecte est déterminant ; pour les variables ayant des valeurs partagées, il est donc recommandé de définir l'indicateur pour toutes les interfaces, par exemple `typeset -U PATH path'.

Cet indicateur a une signification différente lorsqu'il est utilisé avec -f ; voir ci-dessous.

-Z [ n ]
Traitement spécial si défini avec l'indicateur -L. Sinon, similaire à -R, sauf que les zéros de début sont utilisés pour le remplissage au lieu des blancs si le premier caractère non blanc est un chiffre. Les paramètres numériques sont traités spécialement : ils sont toujours éligibles pour le remplissage avec des zéros, et les zéros sont insérés à un endroit approprié dans la sortie.
-a
Les noms font référence à des paramètres de tableau. Un paramètre de tableau peut être créé de cette manière, mais il ne peut lui être affecté dans l'instruction typeset que si la forme du mot réservé de typeset est activée (comme elle l'est par défaut). Lors de l'affichage, les tableaux normaux et associatifs sont montrés.
-f
Les noms font référence à des fonctions plutôt qu'à des paramètres. Aucune affectation ne peut être faite, et les seuls autres indicateurs valides sont -t, -T, -k, -u, -U et -z. L'indicateur -t active le traçage d'exécution pour cette fonction ; l'indicateur -T fait de même, mais désactive le traçage pour toute fonction nommée (non anonyme) appelée depuis la fonction actuelle, à moins que cette fonction n'ait également l'indicateur -t ou -T. Les indicateurs -u et -U provoquent le marquage de la fonction pour l'autoloading ; -U supprime également l'expansion des alias lors du chargement de la fonction. Voir la description de la commande intégrée `autoload' pour les détails.

Notez que la commande intégrée functions fournit les mêmes capacités de base que typeset -f mais donne accès à quelques options supplémentaires ; autoload fournit des options supplémentaires pour le cas typeset -fu et typeset -fU.

-h
Masquer : utile uniquement pour les paramètres spéciaux (ceux marqués `<S>' dans le tableau de zshparam(1)), et pour les paramètres locaux portant le même nom qu'un paramètre spécial, bien qu'inoffensif pour les autres. Un paramètre spécial avec cet attribut ne conservera pas son effet spécial lorsqu'il est rendu local. Ainsi, après `typeset -h PATH', une fonction contenant `typeset PATH' créera un paramètre local ordinaire sans le comportement habituel de PATH. Alternativement, le paramètre local peut lui-même recevoir cet attribut ; ainsi, à l'intérieur d'une fonction, `typeset -h PATH' crée un paramètre local ordinaire et le paramètre spécial PATH n'est en rien modifié. Il est également possible de créer un paramètre local en utilisant `typeset +h spécial', où la copie locale de spécial conservera ses propriétés spéciales indépendamment de la présence de l'attribut -h. Les paramètres spéciaux globaux chargés à partir de modules shell (actuellement ceux de zsh/mapfile et zsh/parameter) reçoivent automatiquement l'attribut -h pour éviter les conflits de noms.
-H
Masquer la valeur : spécifie que typeset n'affichera pas la valeur du paramètre lors de la liste des paramètres ; l'affichage pour de tels paramètres se fait toujours comme si l'indicateur `+' avait été donné. L'utilisation du paramètre est par ailleurs normale, et l'option ne s'applique pas si le paramètre est spécifié par nom, ou par motif avec l'option -m. Ceci est activé par défaut pour les paramètres des modules zsh/parameter et zsh/mapfile. Notez cependant que, contrairement à l'indicateur -h, ceci est également utile pour les paramètres non spéciaux.
-i [ n ]
Utiliser une représentation entière interne. Si n est non nul, il définit la base arithmétique de sortie, sinon elle est déterminée par la première affectation. Les bases de 2 à 36 inclus sont autorisées.
-E [ n ]
Utiliser une représentation en virgule flottante double précision interne. En sortie, la variable sera convertie en notation scientifique. Si n est non nul, il définit le nombre de chiffres significatifs à afficher ; la valeur par défaut est dix.

Utiliser une représentation en virgule flottante double précision interne. En sortie, la variable sera convertie en notation décimale à virgule fixe. Si n est non nul, il définit le nombre de chiffres à afficher après la virgule décimale ; la valeur par défaut est dix.
-l
Convertir le résultat en minuscules chaque fois que le paramètre est développé. La valeur n'est pas convertie lors de l'affectation.
-r
Les noms donnés sont marqués comme lecture seule. Notez que si nom est un paramètre spécial, l'attribut en lecture seule peut être activé, mais ne peut pas être désactivé par la suite.

Si l'option POSIX_BUILTINS est définie, l'attribut en lecture seule est plus restrictif : les variables non définies peuvent être marquées en lecture seule et ne peuvent ensuite pas être définies ; de plus, l'attribut en lecture seule ne peut pas être supprimé d'une variable.

Il est toujours possible de modifier d'autres attributs de la variable, certains comme -U ou -Z affecteraient la valeur. Plus généralement, l'attribut en lecture seule ne doit pas être considéré comme un mécanisme de sécurité.

Notez que dans zsh (comme dans pdksh mais contrairement à la plupart des autres shells) il est toujours possible de créer une variable locale du même nom car cela est considéré comme une variable différente (bien que cette variable puisse également être marquée comme lecture seule). Les variables spéciales qui ont été rendues lecture seule conservent leur valeur et leur attribut lecture seule lorsqu'elles sont rendues locales.

-t
Marque les paramètres nommés. Les marques n'ont pas de signification spéciale pour le shell. Cet indicateur a une signification différente lorsqu'il est utilisé avec -f ; voir ci-dessus.
-u
Convertir le résultat en majuscules chaque fois que le paramètre est développé. La valeur n'est pas convertie lors de l'affectation. Cet indicateur a une signification différente lorsqu'il est utilisé avec -f ; voir ci-dessus.

Marquer pour exportation automatique vers l'environnement des commandes exécutées ultérieurement. Si l'option GLOBAL_EXPORT est définie, cela implique l'option -g, sauf si +g est également explicitement donné ; en d'autres termes, le paramètre n'est pas rendu local à la fonction englobante. Ceci est pour la compatibilité avec les versions précédentes de zsh.

Attend les jobs ou processus spécifiés. Si job n'est pas donné, tous les processus enfants actifs sont attendus. Chaque job peut être soit une spécification de job, soit l'ID de processus d'un job dans la table des jobs. Le statut de sortie de cette commande est celui du job attendu. Il est possible d'attendre des processus récents (spécifiés par leur ID de processus, pas par job) qui étaient en cours d'exécution en arrière-plan même si le processus s'est terminé. Notez qu'il n'y a aucune protection contre le retour en arrière de l'ID de processus, c'est-à-dire si l'attente n'est pas exécutée assez tôt, il y a une chance que le processus attendu soit le mauvais. zcompile [ -U ] [ -z | -k ] [ -R | -M ] file [ name ... ]
zcompile -ca [ -m ] [ -R | -M ] file [ name ... ]
zcompile -t file [ name ... ]
Cette commande intégrée peut être utilisée pour compiler des fonctions ou des scripts, stocker la forme compilée dans un fichier, et pour examiner les fichiers contenant la forme compilée. Cela permet un chargement automatique plus rapide des fonctions et un sourcing de scripts en évitant l'analyse du texte lorsque les fichiers sont lus.

La première forme (sans les options -c, -a ou -t) crée un fichier compilé. Si seul l'argument file est donné, le fichier de sortie s'appelle `file.zwc' et sera placé dans le même répertoire que file. Le shell chargera le fichier compilé au lieu du fichier de fonction normal lorsque la fonction sera chargée automatiquement ; voir la section `Chargement automatique des fonctions' dans zshmisc(1) pour une description de la façon dont les fonctions chargées automatiquement sont recherchées. L'extension .zwc signifie `zsh word code'.

S'il y a au moins un argument name, tous les fichiers nommés sont compilés dans le fichier de sortie file donné comme premier argument. Si file ne se termine pas par .zwc, cette extension est automatiquement ajoutée. Les fichiers contenant plusieurs fonctions compilées sont appelés fichiers `digest', et sont destinés à être utilisés comme éléments du tableau spécial FPATH/fpath.

La deuxième forme, avec les options -c ou -a, écrit les définitions compilées pour toutes les fonctions nommées dans file. Pour -c, les noms doivent être des fonctions actuellement définies dans le shell, pas celles marquées pour le chargement automatique. Les fonctions non définies qui sont marquées pour le chargement automatique peuvent être écrites en utilisant l'option -a, auquel cas fpath est recherché et le contenu des fichiers de définition pour ces fonctions, s'ils sont trouvés, est compilé dans file. Si -c et -a sont tous deux donnés, les noms des fonctions définies et des fonctions marquées pour le chargement automatique peuvent être donnés. Dans les deux cas, les fonctions dans les fichiers écrits avec l'option -c ou -a seront chargées automatiquement comme si l'option KSH_AUTOLOAD était désactivée.

La raison pour laquelle les fonctions chargées et non encore chargées sont traitées avec des options différentes est que certains fichiers de définition pour le chargement automatique définissent plusieurs fonctions, y compris la fonction avec le même nom que le fichier, et, à la fin, appellent cette fonction. Dans de tels cas, la sortie de `zcompile -c' n'inclut pas les fonctions supplémentaires définies dans le fichier, et tout autre code d'initialisation dans le fichier est perdu. L'utilisation de `zcompile -a' capture toutes ces informations supplémentaires.

Si l'option -m est combinée avec -c ou -a, les names sont utilisés comme motifs et toutes les fonctions dont les noms correspondent à l'un de ces motifs seront écrites. Si aucun name n'est donné, les définitions de toutes les fonctions actuellement définies ou marquées pour le chargement automatique seront écrites.

Notez que la deuxième forme ne peut pas être utilisée pour compiler des fonctions qui incluent des redirections dans le cadre de la définition plutôt qu'à l'intérieur du corps de la fonction ; par exemple

fn1() { { ... } >~/logfile }

peut être compilé mais

fn1() { ... } >~/logfile

ne peut pas. Il est possible d'utiliser la première forme de zcompile pour compiler des fonctions chargeables automatiquement qui incluent la définition complète de la fonction au lieu du simple corps de la fonction.

La troisième forme, avec l'option -t, examine un fichier compilé existant. Sans arguments supplémentaires, les noms des fichiers d'origine compilés dedans sont listés. La première ligne de sortie affiche la version du shell qui a compilé le fichier et comment le fichier sera utilisé (c'est-à-dire en le lisant directement ou en le mappant en mémoire). Avec des arguments, rien n'est affiché et le statut de retour est défini à zéro si les définitions pour tous les names ont été trouvées dans le fichier compilé, et non nul si la définition pour au moins un name n'a pas été trouvée.

Autres options :

-U
Les alias ne sont pas développés lors de la compilation des fichiers nommés.
-R
Lorsque le fichier compilé est lu, son contenu est copié dans la mémoire du shell, plutôt que mappé en mémoire (voir -M). Cela se produit automatiquement sur les systèmes qui ne supportent pas le mappage mémoire.

Lors de la compilation de scripts au lieu de fonctions chargeables automatiquement, il est souvent souhaitable d'utiliser cette option ; sinon, l'ensemble du fichier, y compris le code pour définir des fonctions déjà définies, restera mappé, gaspillant ainsi de la mémoire.

-M
Le fichier compilé est mappé en mémoire du shell lors de sa lecture. Ceci est fait de telle manière que plusieurs instances du shell fonctionnant sur le même hôte partageront ce fichier mappé. Si ni -R ni -M ne sont donnés, la commande intégrée zcompile décide quoi faire en fonction de la taille du fichier compilé.
-k
-z
Ces options sont utilisées lorsque le fichier compilé contient des fonctions qui doivent être chargées automatiquement. Si -z est donné, la fonction sera chargée automatiquement comme si l'option KSH_AUTOLOAD n'était *pas* définie, même si elle l'est au moment où le fichier compilé est lu, tandis que si -k est donné, la fonction sera chargée comme si KSH_AUTOLOAD l'était. Ces options ont également la priorité sur toute option -k ou -z spécifiée à la commande intégrée autoload. Si aucune de ces options n'est donnée, la fonction sera chargée comme déterminé par le réglage de l'option KSH_AUTOLOAD au moment où le fichier compilé est lu.

Ces options peuvent également apparaître autant de fois que nécessaire entre les names listés pour spécifier le style de chargement de toutes les fonctions suivantes, jusqu'au prochain -k ou -z.

Le fichier créé contient toujours deux versions du format compilé, une pour les machines big-endian et une pour les machines small-endian. L'effet est que le fichier compilé est indépendant de la machine et s'il est lu ou mappé, seule une moitié du fichier est réellement utilisée (et mappée).

zmodload [ -dL ] [ -s ] [ ... ]
zmodload -F [ -alLme -P param ] module [ [+-]feature ... ]
zmodload -e [ -A ] [ ... ]
zmodload [ -a [ -bcpf [ -I ] ] ] [ -iL ] ...
zmodload -u [ -abcdpf [ -I ] ] [ -iL ] ...
zmodload -A [ -L ] [ modalias[=module] ... ]
zmodload -R modalias ...
Effectue des opérations relatives aux modules chargeables de zsh. Le chargement de modules pendant que le shell est en cours d'exécution (`chargement dynamique') n'est pas disponible sur tous les systèmes d'exploitation, ou sur toutes les installations d'un système d'exploitation particulier, bien que la commande zmodload elle-même soit toujours disponible et puisse être utilisée pour manipuler les modules intégrés aux versions de l'exécutable du shell sans chargement dynamique.

Sans arguments, les noms de tous les modules binaires actuellement chargés sont affichés. L'option -L fait en sorte que cette liste soit sous la forme d'une série de commandes zmodload. Les formes avec arguments sont :

zmodload [ -is ] name ...
zmodload -u [ -i ] name ...
Dans le cas le plus simple, zmodload charge un module binaire. Le module doit se trouver dans un fichier dont le nom est constitué du name spécifié suivi d'un suffixe standard, généralement `.so' (`.sl' sur HPUX). Si le module à charger est déjà chargé, le module dupliqué est ignoré. Si zmodload détecte une incohérence, telle qu'un nom de module invalide ou une liste de dépendances circulaire, le bloc de code actuel est abandonné. S'il est disponible, le module est chargé si nécessaire, tandis que s'il n'est pas disponible, un statut non nul est retourné silencieusement. L'option -i est acceptée pour la compatibilité mais n'a aucun effet.

Le module nommé est recherché de la même manière qu'une commande, en utilisant $module_path à la place de $path. Cependant, la recherche dans le chemin est effectuée même lorsque le nom du module contient un `/', ce qui est généralement le cas. Il n'y a aucun moyen d'empêcher la recherche dans le chemin.

Si le module prend en charge des fonctionnalités (voir ci-dessous), zmodload essaie d'activer toutes les fonctionnalités lors du chargement d'un module. Si le module a été chargé avec succès mais que toutes les fonctionnalités n'ont pas pu être activées, zmodload renvoie le statut 2.

Si l'option -s est donnée, aucune erreur n'est affichée si le module n'était pas disponible (bien que d'autres erreurs indiquant un problème avec le module soient affichées). Le statut de retour indique si le module a été chargé. Ceci est approprié si l'appelant considère le module comme facultatif.

Avec -u, zmodload décharge les modules. Le même nom doit être donné que celui qui a été donné lors du chargement du module, mais il n'est pas nécessaire que le module existe dans le système de fichiers. L'option -i supprime l'erreur si le module est déjà déchargé (ou n'a jamais été chargé).

Chaque module possède une fonction de démarrage et une fonction de nettoyage. Le module ne sera pas chargé si sa fonction de démarrage échoue. De même, un module ne peut être déchargé que si sa fonction de nettoyage s'exécute avec succès.

zmodload -F [ -almLe -P param ] module [ [+-]fonctionnalité ... ]
zmodload -F permet un contrôle plus sélectif sur les fonctionnalités fournies par les modules. Sans aucune option autre que -F, le module nommé module est chargé, s'il n'a pas déjà été chargé, et la liste des fonctionnalités est définie à l'état requis. Si aucune fonctionnalité n'est spécifiée, le module est chargé, s'il n'a pas déjà été chargé, mais l'état des fonctionnalités reste inchangé. Chaque fonctionnalité peut être précédée d'un + pour l'activer, ou d'un - pour la désactiver ; le + est supposé si aucun caractère n'est présent. Toute fonctionnalité non explicitement mentionnée reste dans son état actuel ; si le module n'a pas été chargé auparavant, cela signifie que toutes ces fonctionnalités resteront désactivées. Le statut de retour est zéro si toutes les fonctionnalités ont été définies, 1 si le module n'a pas pu être chargé, et 2 si certaines fonctionnalités n'ont pas pu être définies (par exemple, un paramètre n'a pas pu être ajouté car il existait un paramètre différent du même nom) mais que le module a été chargé.

Les fonctionnalités standard sont les fonctions intégrées (builtins), les conditions, les paramètres et les fonctions mathématiques ; celles-ci sont indiquées par le préfixe `b:', `c:' (`C:' pour une condition infixée), `p:' et `f:', respectivement, suivies du nom que la fonctionnalité correspondante aurait dans le shell. Par exemple, `b:strftime' indique une fonction intégrée nommée strftime et p:EPOCHSECONDS indique un paramètre nommé EPOCHSECONDS. Le module peut fournir d'autres fonctionnalités (`abstraites') qui lui sont propres, comme indiqué dans sa documentation ; celles-ci n'ont pas de préfixe.

Avec -l ou -L, les fonctionnalités fournies par le module sont listées. Avec -l seul, une liste des fonctionnalités avec leur état est affichée, une fonctionnalité par ligne. Avec -L seul, une commande zmodload -F qui activerait les fonctionnalités du module est affichée. Avec -lL, une commande zmodload -F qui définirait toutes les fonctionnalités à leur état actuel est affichée. Si l'une de ces combinaisons est donnée avec l'option -P param, alors le paramètre param est défini à un tableau de fonctionnalités, soit des fonctionnalités avec leur état, soit (si -L seul est donné) des fonctionnalités activées.

Avec l'option -L, le nom du module peut être omis ; alors une liste de toutes les fonctionnalités activées pour tous les modules fournissant des fonctionnalités est imprimée sous la forme de commandes zmodload -F. Si -l est également donné, l'état des fonctionnalités activées et désactivées est affiché sous cette forme. Une liste de fonctionnalités peut être fournie avec -l ou -L et un nom de module ; dans ce cas, seul l'état de ces fonctionnalités est pris en compte. Chaque fonctionnalité peut être précédée de + ou -, mais le caractère n'a aucun effet. Si aucune liste de fonctionnalités n'est fournie, toutes les fonctionnalités sont prises en compte.

Avec -e, la commande teste d'abord que le module est chargé ; s'il ne l'est pas, le statut 1 est renvoyé. Si le module est chargé, la liste des fonctionnalités fournies en argument est examinée. Toute fonctionnalité donnée sans préfixe est simplement testée pour voir si le module la fournit ; toute fonctionnalité donnée avec un préfixe + ou - est testée pour voir si elle est fournie et dans l'état donné. Si les tests sur toutes les fonctionnalités de la liste réussissent, le statut 0 est renvoyé, sinon le statut 1.

Avec -m, chaque entrée de la liste de fonctionnalités donnée est traitée comme un motif à faire correspondre avec la liste des fonctionnalités fournies par le module. Un + ou - initial doit être donné explicitement. Ceci ne peut pas être combiné avec l'option -a car les chargements automatiques doivent être spécifiés explicitement.

Avec -a, la liste de fonctionnalités donnée est marquée pour le chargement automatique à partir du module spécifié, qui peut ne pas être encore chargé. Un + optionnel peut apparaître avant le nom de la fonctionnalité. Si la fonctionnalité est précédée de -, tout chargement automatique existant est supprimé. Les options -l et -L peuvent être utilisées pour lister les chargements automatiques. Le chargement automatique est spécifique à chaque fonctionnalité ; lorsque le module est chargé, seule la fonctionnalité demandée est activée. Les demandes de chargement automatique sont conservées si le module est ensuite déchargé, jusqu'à ce qu'un `zmodload -Fa module -fonctionnalité' explicite soit émis. Il n'est pas une erreur de demander un chargement automatique pour une fonctionnalité d'un module déjà chargé.

Lorsque le module est chargé, chaque chargement automatique est vérifié par rapport aux fonctionnalités réellement fournies par le module ; si la fonctionnalité n'est pas fournie, la demande de chargement automatique est supprimée. Un message d'avertissement est affiché ; si le module est chargé pour fournir une autre fonctionnalité, et que ce chargement automatique réussit, il n'y a aucun effet sur le statut de la commande actuelle. Si le module est déjà chargé au moment où zmodload -Fa est exécuté, un message d'erreur est affiché et le statut 1 est renvoyé.

zmodload -Fa peut être utilisé avec les options -l, -L, -e et -P pour lister et tester l'existence de fonctionnalités chargeables automatiquement. Dans ce cas, -l est ignoré si -L est spécifié. zmodload -FaL sans nom de module liste les chargements automatiques pour tous les modules.

Notez que seules les fonctionnalités standard décrites ci-dessus peuvent être chargées automatiquement ; d'autres fonctionnalités nécessitent que le module soit chargé avant d'être activées.

zmodload -d [ -L ] [ nom ]
zmodload -d nom dep ...
zmodload -ud nom [ dep ... ]
L'option -d peut être utilisée pour spécifier les dépendances des modules. Les modules nommés dans le deuxième argument et les arguments suivants seront chargés avant le module nommé dans le premier argument.

Avec -d et un argument, toutes les dépendances de ce module sont listées. Avec -d et aucun argument, toutes les dépendances des modules sont listées. Cette liste est par défaut dans un format de type Makefile. L'option -L modifie ce format en une liste de commandes zmodload -d.

Si -d et -u sont tous deux utilisés, les dépendances sont supprimées. Si un seul argument est donné, toutes les dépendances de ce module sont supprimées.

zmodload -ab [ -L ]
zmodload -ab [ -i ] nom [ builtin ... ]
zmodload -ub [ -i ] builtin ...
L'option -ab définit les fonctions intégrées (builtins) chargeables automatiquement. Elle définit les builtins spécifiés. Lorsque l'une de ces fonctions intégrées est appelée, le module spécifié dans le premier argument est chargé et toutes ses fonctionnalités sont activées (pour un contrôle sélectif des fonctionnalités, utilisez `zmodload -F -a' comme décrit ci-dessus). Si seul le nom est donné, une fonction intégrée est définie, portant le même nom que le module. -i supprime l'erreur si la fonction intégrée est déjà définie ou chargée automatiquement, mais pas si une autre fonction intégrée du même nom est déjà définie.

Avec -ab et aucun argument, toutes les fonctions intégrées chargeables automatiquement sont listées, le nom du module (s'il est différent) étant affiché entre parenthèses après le nom de la fonction intégrée. L'option -L modifie ce format en une liste de commandes zmodload -a.

Si -b est utilisé avec l'option -u, il supprime les fonctions intégrées précédemment définies avec -ab. Ceci n'est possible que si la fonction intégrée n'est pas encore chargée. -i supprime l'erreur si la fonction intégrée est déjà supprimée (ou n'a jamais existé).

Les demandes de chargement automatique sont conservées si le module est ensuite déchargé, jusqu'à ce qu'un `zmodload -ub builtin' explicite soit émis.

zmodload -ac [ -IL ]
zmodload -ac [ -iI ] nom [ cond ... ]
zmodload -uc [ -iI ] cond ...
L'option -ac est utilisée pour définir des codes de condition chargeables automatiquement. Les chaînes cond donnent les noms des conditions définies par le module. L'option facultative -I est utilisée pour définir des noms de condition infixée. Sans cette option, des noms de condition préfixés sont définis.

Si aucun nom de condition n'est donné, tous les noms définis sont listés (sous forme d'une série de commandes zmodload si l'option -L est donnée).

L'option -uc supprime les définitions des conditions chargeables automatiquement.

zmodload -ap [ -L ]
zmodload -ap [ -i ] nom [ paramètre ... ]
zmodload -up [ -i ] paramètre ...
L'option -p est similaire aux options -b et -c, mais fait que zmodload fonctionne sur les paramètres chargeables automatiquement à la place.
zmodload -af [ -L ]
zmodload -af [ -i ] nom [ fonction ... ]
zmodload -uf [ -i ] fonction ...
L'option -f est similaire aux options -b, -p et -c, mais fait que zmodload fonctionne sur les fonctions mathématiques chargeables automatiquement à la place.
zmodload -a [ -L ]
zmodload -a [ -i ] nom [ builtin ... ]
zmodload -ua [ -i ] builtin ...
Équivalent à -ab et -ub.
zmodload -e [ -A ] [ chaîne ... ]
L'option -e sans arguments liste tous les modules chargés ; si l'option -A est également donnée, les alias de modules correspondant aux modules chargés sont également listés.
o indiqué. Si des arguments sont fournis, rien n'est imprimé ; le statut de retour est défini à zéro si toutes les strings données en arguments sont des noms de modules chargés et à un si au moins une string n'est pas le nom d'un module chargé. Ceci peut être utilisé pour tester la disponibilité de choses implémentées par des modules. Dans ce cas, tous les alias sont automatiquement résolus et le drapeau -A n'est pas utilisé.
zmodload -A [ -L ] [ modalias[=module] ... ]
Pour chaque argument, si à la fois modalias et module sont donnés, définir modalias comme un alias pour le module module. Si le module modalias est jamais demandé par la suite, soit via un appel à zmodload soit implicitement, le shell tentera de charger module à la place. Si module n'est pas donné, afficher la définition de modalias. Si aucun argument n'est donné, lister tous les alias de modules définis. Lors de l'affichage, si le drapeau -L a également été donné, afficher la définition comme une commande zmodload pour recréer l'alias.

L'existence d'alias pour les modules est complètement indépendante de savoir si le nom résolu est réellement chargé en tant que module : tant que l'alias existe, le chargement et le déchargement du module sous n'importe quel alias ont exactement le même effet que l'utilisation du nom résolu, et n'affectent pas la connexion entre l'alias et le nom résolu qui peut être supprimée soit par zmodload -R soit par redéfinition de l'alias. Les chaînes d'alias (c'est-à-dire où le premier nom résolu est lui-même un alias) sont valides tant qu'elles ne sont pas circulaires. Comme les alias prennent le même format que les noms de modules, ils peuvent inclure des séparateurs de chemin : dans ce cas, il n'est pas requis qu'une partie du chemin nommé existe car l'alias sera résolu en premier. Par exemple, `any/old/alias' est toujours un alias valide.

Les dépendances ajoutées aux modules alias sont réellement ajoutées au module résolu ; elles restent si l'alias est supprimé. Il est valide de créer un alias dont le nom est l'un des modules shell standards et qui résout vers un module différent. Cependant, si un module a des dépendances, il ne sera pas possible d'utiliser le nom du module comme alias car le module sera déjà marqué comme un module chargeable en soi.

En dehors de ce qui précède, les alias peuvent être utilisés dans la commande zmodload partout où des noms de modules sont requis. Cependant, les alias ne seront pas affichés dans les listes de modules chargés avec un simple `zmodload'.

zmodload -R modalias ...
Pour chaque argument modalias qui a été précédemment défini comme un alias de module via zmodload -A, supprimer l'alias. Si l'un d'eux n'était pas défini, une erreur est provoquée et le reste de la ligne est ignoré.

Notez que zsh ne fait aucune distinction entre les modules qui ont été liés au shell et les modules qui sont chargés dynamiquement. Dans les deux cas, cette commande intégrée doit être utilisée pour rendre disponibles les commandes intégrées et autres choses définies par les modules (à moins que le module ne soit chargé automatiquement à ces définitions). Ceci est vrai même pour les systèmes qui ne supportent pas le chargement dynamique de modules.
