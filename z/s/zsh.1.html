DESCRIPTION

Zsh est un interpréteur de commandes UNIX (shell) utilisable comme shell de connexion interactif et comme processeur de commandes de script shell. Parmi les shells standard, zsh ressemble le plus à ksh mais inclut de nombreuses améliorations. Il ne fournit pas de compatibilité avec POSIX ou d'autres shells dans son mode de fonctionnement par défaut : voir la section `Compatibilité' ci-dessous.

Zsh dispose de l'édition de ligne de commande, de la correction orthographique intégrée, de la complétion de commandes programmable, de fonctions shell (avec chargement automatique), d'un mécanisme d'historique et d'une multitude d'autres fonctionnalités.

APPEL

Les indicateurs suivants sont interprétés par le shell lors de son appel pour déterminer d'où le shell lira les commandes :

-c
Prend le premier argument comme une commande à exécuter, plutôt que de lire les commandes à partir d'un script ou de l'entrée standard. Si des arguments supplémentaires sont donnés, le premier est assigné à $0, plutôt que d'être utilisé comme paramètre positionnel.
-i
Force le shell à être interactif. Il est toujours possible de spécifier un script à exécuter.
-s
Force le shell à lire les commandes à partir de l'entrée standard. Si l'indicateur -s n'est pas présent et qu'un argument est donné, le premier argument est pris comme le nom de chemin d'un script à exécuter.

S'il reste des arguments après le traitement des options, et que ni l'une ni l'autre des options -c ou -s n'a été fournie, le premier argument est pris comme nom de fichier d'un script contenant des commandes shell à exécuter. Si l'option PATH_SCRIPT est définie, et que le nom du fichier ne contient pas de chemin de répertoire (c'est-à-dire qu'il n'y a pas de `/' dans le nom), le répertoire courant est alors recherché pour le script, suivi du chemin de commande donné par la variable PATH. Si l'option n'est pas définie ou si le nom du fichier contient un `/', il est utilisé directement.

Après que les un ou deux premiers arguments ont été a

ppropriées telles que décrites ci-dessus, les arguments restants sont assignés aux paramètres positionnels.

Pour des options supplémentaires, communes à l'invocation et à la commande intégrée set, voir zshoptions(1).

L'option longue `--emulate' suivie (dans un mot séparé) d'un mode d'émulation peut être passée au shell. Les modes d'émulation sont ceux décrits pour la commande intégrée emulate, voir zshbuiltins(1). L'option `--emulate' doit précéder toute autre option (qui pourrait sinon être remplacée), mais les options suivantes sont respectées, et peuvent donc être utilisées pour modifier le mode d'émulation demandé. Notez que des étapes supplémentaires sont prises pour assurer une émulation fluide lorsque cette option est utilisée par rapport à la commande emulate dans le shell : par exemple, les variables qui entrent en conflit avec l'usage POSIX telles que path ne sont pas définies dans le shell.

Les options peuvent être spécifiées par leur nom en utilisant l'option -o. -o agit comme une option à une seule lettre, mais prend une chaîne suivante comme nom d'option. Par exemple,

zsh -x -o shwordsplit scr

exécute le script scr, en réglant l'option XTRACE par la lettre correspondante `-x' et l'option SH_WORD_SPLIT par son nom. Les options peuvent être désactivées en utilisant +o au lieu de -o. -o peut être empilé avec des options à une seule lettre précédentes, donc par exemple `-xo shwordsplit' ou `-xoshwordsplit' est équivalent à `-x -o shwordsplit'.

Les options peuvent également être spécifiées par leur nom en style d'option longue GNU, `--nom-option'. Lorsque cela est fait, les caractères `-' dans le nom de l'option sont autorisés : ils sont traduits en `_', et donc ignorés. Ainsi, par exemple, `zsh --sh-word-split' invoque zsh avec l'option SH_WORD_SPLIT activée. Comme les autres syntaxes d'options, les options peuvent être désactivées en remplaçant le `-' initial par un `+' ; ainsi `+-sh-word-split' est équivalent à `--no-sh-word-split'. Contrairement aux autres syntaxes d'options, les options longues de style GNU ne peuvent pas être empilées avec d'autres options, donc par exemple `-x-shwordsplit' est une erreur, plutôt que d'être traité comme `-x --shwordsplit'.

L'option spéciale de style GNU `--version' est gérée ; elle envoie la version du shell à la sortie standard, puis se termine avec succès. `--help' est également gérée ; elle envoie une liste des options pouvant être utilisées lors de l'invocation du shell à la sortie standard, puis se termine avec succès.

Le traitement des options peut être terminé, permettant aux arguments suivants commençant par `-' ou `+' d'être traités comme des arguments normaux, de deux manières. Premièrement, un `-' (ou `+') solitaire comme argument termine le traitement des options. Deuxièmement, une option spéciale `--' (ou `+-'), qui peut être spécifiée seule (ce qui est l'usage POSIX standard) ou peut être empilée avec des options précédentes (donc `-x-' est équivalent à `-x --'). Les options ne sont pas autorisées à être empilées après `--' (donc `-x-f' est une erreur), mais notez la forme d'option de style GNU discutée ci-dessus, où `--shwordsplit' est autorisée et ne termine pas le traitement des options.

Sauf lorsque les options à une seule lettre d'émulation sh/ksh sont actives, l'option `-b' (ou `+b') termine le traitement des options. `-b' est comme `--', sauf que des options supplémentaires à une seule lettre peuvent être empilées après `-b' et prendront effet normalement.

COMPATIBILITÉ

Zsh essaie d'émuler sh ou ksh lorsqu'il est invoqué comme sh ou ksh respectivement ; plus précisément, il regarde la première lettre du nom par lequel il a été invoqué, en excluant tout `r' initial (supposé représenter `restricted'), et si c'est `b', `s' ou `k', il émule sh ou ksh. De plus, s'il est invoqué comme su (ce qui se produit sur certains systèmes lorsque le shell est exécuté par la commande su), le shell essaiera de trouver un nom alternatif à partir de la variable d'environnement SHELL et effectuera une émulation basée sur celle-ci.

En modes de compatibilité sh et ksh, les paramètres suivants ne sont pas spéciaux et ne sont pas initialisés par le shell : ARGC, argv, cdpath, fignore, fpath, HISTCHARS, mailpath, MANPATH, manpath, path, prompt, PROMPT, PROMPT2, PROMPT3, PROMPT4, psvar, status.

Les scripts de démarrage/arrêt habituels de zsh ne sont pas exécutés. Les shells de connexion lisent /etc/profile suivi de $HOME/.profile. Si la variable d'environnement ENV est définie à l'invocation, $ENV est lu après les scripts de profil. La valeur de ENV est soumise à l'expansion des paramètres, à la substitution de commandes et à l'expansion arithmétique avant d'être interprétée comme un nom de chemin. Notez que l'option PRIVILEGED affecte également l'exécution des fichiers de démarrage.

Les options suivantes sont définies si le shell est invoqué comme sh ou ksh : NO_BAD_PATTERN, NO_BANG_HIST, NO_BG_NICE, NO_EQUALS, NO_FUNCTION_ARGZERO, GLOB_SUBST, NO_GLOBAL_EXPORT, NO_HUP, INTERACTIVE_COMMENTS, KSH_ARRAYS, NO_MULTIOS, NO_NOMATCH, NO_NOTIFY, POSIX_BUILTINS, NO_PROMPT_PERCENT, RM_STAR_SILENT, SH_FILE_EXPANSION, SH_GLOB, SH_OPTION_LETTERS, SH_WORD_SPLIT. De plus, les options BSD_ECHO et IGNORE_BRACES sont définies si zsh est invoqué comme sh. Également, les options KSH_OPTION_PRINT, LOCAL_OPTIONS, PROMPT_BANG, PROMPT_SUBST et SINGLE_LINE_ZLE sont définies si zsh est invoqué comme ksh.

Veuillez noter que, bien que des efforts raisonnables soient faits pour résoudre les incompatibilités lorsqu'elles surviennent, zsh ne garantit pas une émulation complète des autres shells, ni la conformité POSIX. Pour plus d'informations sur les différences entre zsh et les autres shells, veuillez vous référer au chapitre 2 de la FAQ du shell, https://www.zsh.org/FAQ/.

SHELL RESTREINT

Lorsque le nom de base de la commande utilisée pour invoquer zsh commence par la lettre `r' ou que l'option de ligne de commande `-r' est fournie à l'invocation, le shell devient restreint. Le mode d'émulation est déterminé après avoir retiré la lettre `r' du nom d'invocation. Les éléments suivants sont désactivés en mode restreint :

•
le changement de répertoire avec la commande intégrée cd
•
le changement ou la désactivation des paramètres EGID, EUID, GID, HISTFILE, HISTSIZE, IFS, LD_AOUT_LIBRARY_PATH, LD_AOUT_PRELOAD, LD_LIBRARY_PATH, LD_PRELOAD, MODULE_PATH, module_path, PATH, path, SHELL, UID et USERNAME
•
la spécification de noms de commandes contenant /
•
la spécification de noms de chemins de commandes à l'aide de hash
•
la redirection de la sortie vers des fichiers
•
l'utilisation de la commande intégrée exec pour remplacer le shell par une autre commande
•
l'utilisation de jobs -Z pour écraser l'espace d'arguments et d'environnement du processus shell
•
l'utilisation du paramètre ARGV0 pour remplacer argv[0] pour les commandes externes
•
la désactivation du mode restreint avec set +r ou unsetopt RESTRICTED

Ces restrictions sont appliquées après le traitement des fichiers de démarrage. Les fichiers de démarrage doivent configurer PATH pour pointer vers un répertoire de commandes pouvant être appelées en toute sécurité dans l'environnement restreint. Ils peuvent également ajouter des restrictions supplémentaires en désactivant des commandes intégrées sélectionnées.

Le mode restreint peut également être activé à tout moment en réglant l'option RESTRICTED. Cela active immédiatement toutes les restrictions décrites ci-dessus, même si le shell n'a pas encore traité tous les fichiers de démarrage.

Un mode restreint de shell est une ancienne façon de restreindre ce que les utilisateurs peuvent faire : les systèmes modernes disposent de moyens meilleurs, plus sûrs et plus fiables pour confiner les actions des utilisateurs, tels que les environnements chroot, les conteneurs et les zones.

Un shell restreint est très difficile à implémenter en toute sécurité. La fonctionnalité pourrait être supprimée dans une future version de zsh.

Il est important de réaliser que les restrictions ne s'appliquent qu'au shell, et non aux commandes qu'il exécute (à l'exception de certaines commandes intégrées du shell). Alors qu'un shell restreint ne peut exécuter que la liste restreinte de commandes accessibles via la variable prédéfinie `PATH', il n'empêche pas ces commandes d'en exécuter d'autres.

Par exemple, si `env' fait partie de la liste des commandes autorisées, alors il permet à l'utilisateur d'exécuter n'importe quelle commande car `env' n'est pas une commande intégrée du shell et peut exécuter des exécutables arbitraires.

Ainsi, lors de la mise en œuvre d'un cadre de shell restreint, il est important d'être pleinement conscient des actions que chaque commande ou fonctionnalité autorisée (qui peut être considérée comme des modules) peut effectuer.

De nombreuses commandes peuvent voir leur comportement affecté par les variables d'environnement. À l'exception des quelques-unes listées ci-dessus, zsh ne restreint pas la définition des variables d'environnement.

Si un script interprété comme `perl', `python', `bash', ou un autre script d'interprétation à usage général est traité comme une commande restreinte, l'utilisateur peut contourner la restriction en définissant des variables d'environnement spécialement conçues telles que `PERL5LIB', `PYTHONPATH', `BASHENV' (etc.). Sur les systèmes GNU, toute commande peut être amenée à exécuter du code arbitraire lors de la conversion de jeu de caractères (y compris zsh lui-même) en définissant une variable d'environnement `GCONV_PATH'. Ce ne sont là que quelques exemples.

Gardez à l'esprit que, contrairement à certains autres shells, `readonly' n'est pas une fonctionnalité de sécurité dans zsh car elle peut être annulée et ne peut donc pas être utilisée pour atténuer ce qui précède.

Un shell restreint ne fonctionne que si les commandes autorisées sont peu nombreuses et soigneusement écrites afin de ne pas accorder plus d'accès aux utilisateurs que prévu. Il est également important de restreindre le module zsh que l'utilisateur peut charger, car certains d'entre eux, tels que `zsh/system', `zsh/mapfile' et `zsh/files', permettent de contourner la plupart des restrictions.

FICHIERS DE DÉMARRAGE/ARRÊT

Les commandes sont d'abord lues depuis /etc/zsh/zshenv ; cela ne peut pas être annulé. Le comportement ultérieur est modifié par les options RCS et GLOBAL_RCS ; la première affecte tous les fichiers de démarrage, tandis que

Le second n'affecte que les fichiers de démarrage globaux (ceux affichés ici avec un chemin commençant par un /). Si l'une des options est désactivée à un moment donné, les fichiers de démarrage subséquents du type correspondant ne seront pas lus. Il est également possible qu'un fichier dans $ZDOTDIR réactive GLOBAL_RCS. Les deux options RCS et GLOBAL_RCS sont activées par défaut.

Les commandes sont ensuite lues à partir de $ZDOTDIR/.zshenv. Si le shell est un shell de connexion, les commandes sont lues à partir de /etc/zsh/zprofile puis $ZDOTDIR/.zprofile. Ensuite, si le shell est interactif, les commandes sont lues à partir de /etc/zsh/zshrc puis $ZDOTDIR/.zshrc. Enfin, si le shell est un shell de connexion, /etc/zsh/zlogin et $ZDOTDIR/.zlogin sont lus.

Lorsqu'un shell de connexion se termine, les fichiers $ZDOTDIR/.zlogout puis /etc/zsh/zlogout sont lus. Cela se produit soit avec une sortie explicite via les commandes exit ou logout, soit avec une sortie implicite en lisant la fin de fichier depuis le terminal. Cependant, si le shell se termine en raison de l'exécution d'un autre processus via exec, les fichiers de déconnexion ne sont pas lus. Ceux-ci sont également affectés par les options RCS et GLOBAL_RCS. Notez également que l'option RCS affecte la sauvegarde des fichiers d'historique, c'est-à-dire si RCS est désactivée à la sortie du shell, aucun fichier d'historique ne sera sauvegardé.

Si ZDOTDIR est désactivé, HOME est utilisé à la place. Les fichiers listés ci-dessus comme étant dans /etc peuvent se trouver dans un autre répertoire, en fonction de l'installation.

Comme /etc/zsh/zshenv est exécuté pour toutes les instances de zsh, il est important qu'il soit maintenu aussi petit que possible. En particulier, il est conseillé de placer le code qui ne nécessite pas d'être exécuté pour chaque shell individuel derrière un test de la forme `if [[ -o rcs ]]; then ...' afin qu'il ne soit pas exécuté lorsque zsh est invoqué avec l'option `-f'.

N'importe lequel de ces fichiers peut être pré-compilé avec la commande intégrée zcompile (voir zshbuiltins(1)). Si un fichier compilé existe (nommé d'après le fichier original plus l'extension .zwc) et qu'il est plus récent que le fichier original, le fichier compilé sera utilisé à la place.
