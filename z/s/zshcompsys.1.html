NOM

zshcompsys - Système de complétion zsh

DESCRIPTION

Ceci décrit le code du shell pour le `nouveau' système de complétion, appelé compsys. Il est écrit en fonctions shell basées sur les fonctionnalités décrites dans zshcompwid(1).

Les fonctionnalités sont contextuelles, sensibles au point auquel la complétion est démarrée. De nombreuses complétions sont déjà fournies. Pour cette raison, un utilisateur peut accomplir une grande quantité de tâches sans connaître de détails au-delà de la façon d'initialiser le système, ce qui est décrit ci-dessous dans INITIALISATION.

Le contexte qui décide quelle complétion doit être effectuée peut être

•
une position d'argument ou d'option : celles-ci décrivent la position sur la ligne de commande où la complétion est demandée. Par exemple `premier argument de rmdir, le mot en cours de complétion nomme un répertoire' ;
•
un contexte spécial, désignant un élément de la syntaxe du shell. Par exemple `un mot en position de commande' ou `un indice de tableau'.

Une spécification de contexte complète contient d'autres éléments, comme nous allons le décrire.

Outre les noms de commandes et les contextes, le système utilise deux autres concepts, les styles et les étiquettes (tags). Ceux-ci fournissent des moyens à l'utilisateur de configurer le comportement du système.

Les étiquettes jouent un double rôle. Elles servent de système de classification pour les correspondances, indiquant typiquement une classe d'objet que l'utilisateur peut avoir besoin de distinguer. Par exemple, lors de la complétion des arguments de la commande ls, l'utilisateur peut préférer essayer les fichiers avant les répertoires, donc les deux sont des étiquettes. Elles apparaissent également comme l'élément le plus à droite dans une spécification de contexte.

Les styles modifient diverses opérations du système de complétion, comme le formatage de la sortie, mais aussi quels types de compléteurs sont utilisés (et dans quel ordre), ou quelles étiquettes sont examinées. Les styles peuvent accepter des arguments et sont manipulés en utilisant la commande zstyle décrite dans zshmodules(1).

En résumé, les étiquettes décrivent quoi sont les objets de complétion, et le style comment ils doivent être complétés. À divers points de l'exécution, le système de complétion vérifie quels styles et/ou étiquettes sont définis pour le contexte actuel, et utilise cela pour modifier son comportement. La description complète de la gestion du contexte, qui détermine comment les étiquettes et d'autres éléments du contexte influencent le comportement des styles, est décrite ci-dessous dans CONFIGURATION DU SYSTÈME DE COMPLÉTION.

Lorsqu'une complétion est demandée, une fonction de dispatch est appelée ; voir la description de _main_complete dans la liste des fonctions de contrôle ci-dessous. Ce dispatch détermine quelle fonction doit être appelée pour produire les complétions, et l'appelle. Le résultat est passé à un ou plusieurs compléteurs, des fonctions qui implémentent des stratégies de complétion individuelles : complétion simple, correction d'erreurs, complétion avec correction d'erreurs, sélection par menu, etc.

Plus généralement, les fonctions shell contenues dans le système de complétion sont de deux types :

•
celles commençant par `comp' doivent être appelées directement ; il n'y en a que quelques-unes ;
•
celles commençant par `_' sont appelées par le code de complétion. Les fonctions shell de cet ensemble, qui implémentent le comportement de complétion et peuvent être liées à des combinaisons de touches, sont appelées `widgets'. Celles-ci prolifèrent à mesure que de nouvelles complétions sont requises.

INITIALISATION

Si le système a été installé complètement, il devrait suffire d'appeler la fonction shell compinit depuis votre fichier d'initialisation ; voir la section suivante. Cependant, la fonction compinstall peut être exécutée par un utilisateur pour configurer divers aspects du système de complétion.

Habituellement, compinstall insérera du code dans .zshrc, bien que si celui-ci n'est pas accessible en écriture, il le sauvegardera dans un autre fichier et vous indiquera l'emplacement de ce fichier. Notez qu'il vous appartient de vous assurer que les lignes ajoutées à .zshrc sont bien exécutées ; vous devrez peut-être, par exemple, les déplacer plus haut dans le fichier si .zshrc se termine habituellement tôt. Tant que vous les gardez toutes ensemble (y compris les lignes de commentaire au début et à la fin), vous pouvez réexécuter compinstall et il trouvera et modifiera correctement ces lignes. Notez cependant que tout code que vous ajoutez à cette section manuellement est susceptible d'être perdu si vous réexécutez compinstall, bien que les lignes utilisant la commande `zstyle' soient gérées avec soin.

Le nouveau code prendra effet la prochaine fois que vous démarrerez le shell, ou exécuterez .zshrc manuellement ; il existe également une option pour les faire prendre effet immédiatement. Cependant, si compinstall a supprimé des définitions, vous devrez redémarrer le shell pour voir les changements.

Pour exécuter compinstall, vous devrez vous assurer qu'il se trouve dans un répertoire mentionné dans votre paramètre fpath, ce qui devrait déjà être le cas si zsh a été correctement configuré tant que vos fichiers de démarrage ne suppriment pas les répertoires appropriés de fpath. Ensuite, il doit être chargé automatiquement (`autoload -U compinstall' est recommandé). Vous pouvez interrompre l'installation à tout moment où l'on vous demande des informations, et votre .zshrc ne sera pas modifié du tout ; les changements n'ont lieu qu'à la fin, où vous êtes spécifiquement invité à confirmer.

Utilisation de compinit

Cette section décrit l'utilisation de compinit pour initialiser la complétion pour la session en cours lorsqu'elle est appelée directement ; si vous avez exécuté compinstall, elle sera appelée automatiquement depuis votre .zshrc.

Pour initialiser le système, la fonction compinit doit se trouver dans un répertoire mentionné dans le paramètre fpath, et doit être chargée automatiquement (`autoload -U compinit' est recommandé), puis exécutée simplement comme `compinit'. Cela définira quelques fonctions utilitaires, arrangera le chargement automatique de toutes les fonctions shell nécessaires, et redéfinira tous les widgets qui font de la complétion pour utiliser le nouveau système. Si vous utilisez le widget menu-select, qui fait partie du module zsh/complist, vous devez vous assurer que ce module est chargé avant l'appel à compinit afin que ce widget soit également redéfini. Si les styles de complétion (voir ci-dessous) sont configurés pour effectuer une expansion ainsi qu'une complétion par défaut, et que la touche TAB est liée à expand-or-complete, compinit la liera à complete-word ; ceci est nécessaire pour utiliser la forme correcte d'expansion.

Si vous avez besoin d'utiliser les commandes de complétion d'origine, vous pouvez toujours lier des touches aux anciens widgets en plaçant un `.' devant le nom du widget, par exemple `.expand-or-complete'.

Pour accélérer l'exécution de compinit, il peut être fait pour produire une configuration déversée qui sera lue lors des invocations futures ; c'est le comportement par défaut, mais il peut être désactivé en appelant compinit avec l'option -D. Le fichier déversé est .zcompdump dans le même répertoire que les fichiers de démarrage (c'est-à-dire $ZDOTDIR ou $HOME) ; alternativement, un nom de fichier explicite peut être donné par `compinit -d nom_fichier_déversé'. La prochaine invocation de compinit lira le fichier déversé au lieu d'effectuer une initialisation complète.

Si le nombre de fichiers de complétion change, compinit le reconnaîtra et produira un nouveau fichier déversé. Cependant, si le nom d'une fonction ou les arguments de la première ligne d'une fonction #compdef (comme décrit ci-dessous) changent, il est plus simple de supprimer le fichier déversé manuellement pour que compinit le recrée la prochaine fois qu'il sera exécuté. La vérification effectuée pour voir s'il y a de nouvelles fonctions peut être omise en donnant l'option -C. Dans ce cas, le fichier déversé ne sera créé que s'il n'en existe pas déjà.

Le déversement est en fait effectué par une autre fonction, compdump, mais vous n'aurez besoin de l'exécuter vous-même que si vous changez la configuration (par exemple, en utilisant compdef) et que vous souhaitez ensuite déverser la nouvelle. Le nom de l'ancien fichier déversé sera mémorisé à cet effet.

Si le paramètre _compdir est défini, compinit l'utilise comme répertoire où les fonctions de complétion peuvent être trouvées ; ceci n'est nécessaire que si elles ne sont pas déjà dans le chemin de recherche des fonctions.

Pour des raisons de sécurité, compinit vérifie également si le système de complétion utiliserait des fichiers qui n'appartiennent ni à root ni à l'utilisateur courant, ou des fichiers dans des répertoires qui sont inscriptibles par tous ou par le groupe, ou qui n'appartiennent ni à root ni à l'utilisateur courant. Si de tels fichiers ou répertoires sont trouvés, compinit demandera si le système de complétion doit vraiment être utilisé. Pour éviter ces tests et faire utiliser tous les fichiers trouvés sans demander, utilisez l'option -u.

, et pour faire en sorte que compinit ignore silencieusement tous les fichiers et répertoires non sécurisés, utilisez l'option -i. Cette vérification de sécurité est entièrement ignorée lorsque l'option -C est donnée, à condition que le fichier dump existe.

La vérification de sécurité peut être répétée à tout moment en appelant la fonction compaudit. Il s'agit de la même vérification utilisée par compinit, mais lorsqu'elle est exécutée directement, toutes les modifications apportées à fpath sont locales à la fonction afin qu'elles ne persistent pas. Les répertoires à vérifier peuvent être passés en arguments ; si aucun n'est donné, compaudit utilise fpath et _compdir pour trouver les répertoires du système de complétion, ajoutant ceux qui manquent à fpath si nécessaire. Pour forcer une vérification des répertoires actuellement nommés dans fpath, définissez _compdir sur une chaîne vide avant d'appeler compaudit ou compinit.

La fonction bashcompinit assure la compatibilité avec le système de complétion programmable de bash. Lorsqu'elle est exécutée, elle définit les fonctions compgen et complete qui correspondent aux commandes intégrées de bash du même nom. Il sera alors possible d'utiliser des spécifications de complétion et des fonctions écrites pour bash.

Fichiers autoloadés

La convention pour les fonctions autoloadées utilisées dans la complétion est qu'elles commencent par un tiret bas ; comme déjà mentionné, le paramètre fpath/FPATH doit contenir le répertoire dans lequel elles sont stockées. Si zsh a été correctement installé sur votre système, alors fpath/FPATH contient automatiquement les répertoires requis pour les fonctions standard.

Pour les installations incomplètes, si compinit ne trouve pas suffisamment de fichiers commençant par un tiret bas (moins de vingt) dans le chemin de recherche, il essaiera d'en trouver d'autres en ajoutant le répertoire _compdir au chemin de recherche. Si ce répertoire a un sous-répertoire nommé Base, tous les sous-répertoires seront ajoutés au chemin. De plus, si le sous-répertoire Base a un sous-répertoire nommé Core, compinit ajoutera tous les sous-répertoires des sous-répertoires au chemin : cela permet aux fonctions d'être dans le même format que dans la distribution source de zsh.

Lorsque compinit est exécuté, il recherche tous ces fichiers accessibles via fpath/FPATH et lit la première ligne de chacun d'eux. Cette ligne doit contenir l'une des balises décrites ci-dessous. Les fichiers dont la première ligne ne commence pas par l'une de ces balises ne sont pas considérés comme faisant partie du système de complétion et ne seront pas traités spécialement.

Les balises sont :

#compdef nom ... [ -{p|P} motif ... [ -N nom ... ] ]
Le fichier sera rendu autoloadable et la fonction qui y est définie sera appelée lors de la complétion de noms, chacun étant soit le nom d'une commande dont les arguments doivent être complétés, soit l'un des contextes spéciaux sous la forme -contexte- décrits ci-dessous.

Chaque nom peut également être de la forme `cmd=service'. Lors de la complétion de la commande cmd, la fonction se comporte généralement comme si la commande (ou le contexte spécial) service était complétée à la place. Cela fournit un moyen de modifier le comportement des fonctions qui peuvent effectuer de nombreuses complétions différentes. Ceci est implémenté en définissant le paramètre $service lors de l'appel de la fonction ; la fonction peut choisir de l'interpréter comme elle le souhaite, et les fonctions plus simples l'ignoreront probablement.

Si la ligne #compdef contient l'une des options -p ou -P, les mots suivants sont considérés comme des motifs. La fonction sera appelée lorsque la complétion sera tentée pour une commande ou un contexte qui correspond à l'un des motifs. Les options -p et -P sont utilisées pour spécifier les motifs à essayer avant ou après les autres complétions respectivement. Par conséquent, -P peut être utilisé pour spécifier des actions par défaut.

L'option -N est utilisée après une liste suivant -p ou -P ; elle spécifie que les mots restants ne définissent plus de motifs. Il est possible de basculer entre les trois options autant de fois que nécessaire.

#compdef -k style séquence-clé ...
Cette option crée un widget se comportant comme le widget intégré style et le lie aux séquence-clés données, le cas échéant. Le style doit être l'un des widgets intégrés qui effectuent la complétion, à savoir complete-word, delete-char-or-list, expand-or-complete, expand-or-complete-prefix, list-choices, menu-complete, menu-expand-or-complete, ou reverse-menu-complete. Si le module zsh/complist est chargé (voir zshmodules(1)), le widget menu-select est également disponible.

Lorsqu'une des séquence-clés est tapée, la fonction du fichier sera invoquée pour générer les correspondances. Notez qu'une touche ne sera pas re-liée si elle l'était déjà (c'est-à-dire, si elle était liée à autre chose que undefined-key). Le widget créé porte le même nom que le fichier et peut être lié à d'autres touches en utilisant bindkey comme d'habitude.

#compdef -K nom-widget style séquence-clé [ nom style seq ... ]
Ceci est similaire à -k sauf qu'un seul argument séquence-clé peut être donné pour chaque paire nom-widget style. Cependant, l'ensemble complet de trois arguments peut être répété avec un ensemble différent d'arguments. Notez en particulier que le nom-widget doit être distinct dans chaque ensemble. S'il ne commence pas par `_', il sera ajouté. Le nom-widget ne doit pas entrer en conflit avec le nom d'un widget existant : les noms basés sur le nom de la fonction sont les plus utiles. Par exemple,
#compdef -K _foo_complete complete-word "^X^C" \
  _foo_list list-choices "^X^D"

(tout sur une seule ligne) définit un widget _foo_complete pour la complétion, lié à `^X^C', et un widget _foo_list pour la liste, lié à `^X^D'.

#autoload [ options ]
Les fonctions avec la balise #autoload sont marquées pour l'autoloading mais ne sont pas traitées autrement de manière spéciale. Typiquement, elles doivent être appelées depuis l'une des fonctions de complétion. Toutes les options fournies seront passées à la commande intégrée autoload ; une utilisation typique est +X pour forcer le chargement immédiat de la fonction. Notez que les indicateurs -U et -z sont toujours ajoutés implicitement.

Le # fait partie du nom de la balise et aucun espace blanc n'est autorisé après. Les balises #compdef utilisent la fonction compdef décrite ci-dessous ; la principale différence est que le nom de la fonction est fourni implicitement.

Les contextes spéciaux pour lesquels des fonctions de complétion peuvent être définies sont :

-array-value-
La partie droite d'une assignation de tableau (`nom=(...)')
-assign-parameter-
Le nom d'un paramètre dans une assignation, c'est-à-dire du côté gauche d'un `='
-brace-parameter-
Le nom d'une expansion de paramètre entre accolades (`${...}')
-command-
Un mot en position de commande
-condition-
Un mot à l'intérieur d'une condition (`[[...]]')
-default-
Tout mot pour lequel aucune autre complétion n'est définie
-equal-
Un mot commençant par un signe égal
-first-
Ceci est essayé avant toute autre fonction de complétion. La fonction appelée peut définir le paramètre _compskip sur l'une des valeurs suivantes : all : aucune autre complétion n'est tentée ; une chaîne contenant la sous-chaîne patterns : aucune fonction de complétion de motif ne sera appelée ; une chaîne contenant default : la fonction pour le contexte `-default-' ne sera pas appelée, mais les fonctions définies pour les commandes le seront.
-math-
Dans des contextes mathématiques, tels que `((...))'
-parameter-
Le nom d'une expansion de paramètre (`$...')
-redirect-
Le mot après un opérateur de redirection.
-subscript-
Le contenu d'un sous-script de paramètre.
-tilde-
Après un tilde initial (`~'), mais avant le premier slash dans le mot.
-value-
Du côté droit d'une assignation.

Des implémentations par défaut sont fournies pour chacun de ces contextes. Dans la plupart des cas, le contexte -contexte- est implémenté par une fonction correspondante _contexte, par exemple le contexte `-tilde-' et la fonction `_tilde').

Les contextes -redirect- et -value- permettent des informations supplémentaires spécifiques au contexte. (En interne, cela est géré par les fonctions de chaque contexte appelant la fonction _dispatch.) Les informations supplémentaires sont ajoutées séparées par des virgules.

Pour le contexte -redirect-, les informations supplémentaires sont sous la forme `-redirect-,op,commande', où op est l'opérateur de redirection et commande est le nom de la commande sur la ligne. S'il n'y a pas encore de commande sur la ligne, le champ commande sera vide.

Pour le contexte -value-, la forme est `-value-,nom,commande', où nom est le nom du paramètre à gauche de l'assignation. Dans le cas d'éléments d'un tableau associatif, par exemple `assoc=(clé <TAB>', nom est développé en `nom-clé'. Dans certains contextes spéciaux, comme la complétion après `make CFLAGS=', la partie commande donne le nom de la commande, ici make ; sinon elle est vide.

Il n'est pas nécessaire de définir des complétions entièrement spécifiques car les fonctions fournies essaieront de générer des complétions en remplaçant progressivement les éléments par `-default-'. Par exemple, lors de la complétion après `foo=<TAB>', _value essaiera les noms `-value-,foo,' (notez la commande vide

part), `-valeur-,foo,-défaut-' et `-valeur-,-défaut-,-défaut-', dans cet ordre, jusqu'à ce qu'elle trouve une fonction pour gérer le contexte.

À titre d'exemple :

compdef '_fichiers -g "*.log"' '-redirection-,2>,-défaut-'

complète les fichiers correspondant à `*.log' après `2> <TAB>' pour toute commande sans gestionnaire plus spécifique défini.

Aussi :

compdef _foo -valeur-,-défaut-,-défaut-

spécifie que _foo fournit des complétions pour les valeurs des paramètres pour lesquels aucune fonction spéciale n'a été définie. Ceci est généralement géré par la fonction _valeur elle-même.

Les mêmes règles de recherche sont utilisées lors de la recherche de styles (comme décrit ci-dessous) ; par exemple

zstyle ':complétion:*:*:-redirection-,2>,*:*' motifs-fichiers '*.log'

est une autre façon de faire en sorte que la complétion après `2> <TAB>' complète les fichiers correspondant à `*.log'.

Fonctions

La fonction suivante est définie par compinit et peut être appelée directement.

compdef [ -ane ] fonction nom ... [ -{p|P} motif ... [ -N nom ...]]
compdef -d nom ...
compdef -k [ -an ] fonction style séquence-touche [ séquence-touche ... ]
compdef -K [ -an ] fonction nom style seq-touche [ nom style seq ... ]
La première forme définit la fonction à appeler pour la complétion dans les contextes donnés, comme décrit pour la balise #compdef ci-dessus.

Alternativement, tous les arguments peuvent avoir la forme `cmd=service'. Ici, service devrait déjà avoir été défini par des lignes `cmd1=service' dans les fichiers #compdef, comme décrit ci-dessus. L'argument pour cmd sera complété de la même manière que service.

L'argument fonction peut alternativement être une chaîne contenant presque tout code shell. Si la chaîne contient un signe égal, ce qui précède sera prioritaire. L'option -e peut être utilisée pour spécifier que le premier argument doit être évalué comme du code shell, même s'il contient un signe égal. La chaîne sera exécutée en utilisant la commande interne eval pour générer les complétions. Cela permet d'éviter de devoir définir une nouvelle fonction de complétion. Par exemple, pour compléter les fichiers se terminant par `.h' comme arguments de la commande foo :

compdef '_fichiers -g ".h"' foo

L'option -n empêche que les complétions déjà définies pour la commande ou le contexte ne soient écrasées.

L'option -d supprime toute complétion définie pour la commande ou les contextes listés.

Les noms peuvent également contenir les options -p, -P et -N, comme décrit pour la balise #compdef. L'effet sur la liste d'arguments est identique, basculant entre les définitions des motifs essayés initialement, des motifs essayés finalement, et des commandes et contextes normaux.

Le paramètre $_compskip peut être défini par toute fonction définie pour un contexte de motif. S'il est défini avec une valeur contenant la sous-chaîne `patterns', aucune des fonctions de motif ne sera appelée ; s'il est défini avec une valeur contenant la sous-chaîne `all', aucune autre fonction ne sera appelée. Définir $_compskip de cette manière est particulièrement utile lorsque l'option -p est utilisée, car sinon le répartiteur passera à des fonctions supplémentaires (probablement celle par défaut) après avoir appelé la fonction de contexte de motif, ce qui peut brouiller l'affichage des possibilités de complétion si ce n'est pas géré correctement.

La forme avec -k définit un widget portant le même nom que la fonction qui sera appelée pour chacune des séquence-touches ; cela est similaire à la balise #compdef -k. La fonction doit générer les complétions nécessaires et se comportera sinon comme le widget intégré dont le nom est donné comme argument style. Les widgets utilisables à cette fin sont : compléter-mot, supprimer-caractère-ou-liste, étendre-ou-compléter, étendre-ou-compléter-préfixe, lister-choix, menu-compléter, menu-étendre-ou-compléter, et menu-compléter-inverse, ainsi que menu-sélectionner si le module zsh/complist est chargé. L'option -n empêche la liaison de la touche si elle est déjà liée à autre chose que touche-non-définie.

La forme avec -K est similaire et définit plusieurs widgets basés sur la même fonction, chacun nécessitant l'ensemble de trois arguments : nom, style et seq-touche, où les deux derniers sont comme pour -k et le premier doit être un nom de widget unique commençant par un underscore.

Lorsque cela est applicable, l'option -a rend la fonction chargeable automatiquement, équivalent à `autoload -U fonction'.

La fonction compdef peut être utilisée pour associer des fonctions de complétion existantes à de nouvelles commandes. Par exemple,

compdef _pids foo

utilise la fonction _pids pour compléter les identifiants de processus pour la commande foo.

Notez également la fonction _gnu_generic décrite ci-dessous, qui peut être utilisée pour compléter les options des commandes qui comprennent l'option `--help'.

CONFIGURATION DU SYSTÈME DE COMPLÉTION

Cette section donne un bref aperçu du fonctionnement du système de complétion, puis plus de détails sur la façon dont les utilisateurs peuvent configurer comment et quand les correspondances sont générées.

Aperçu

Lorsque la complétion est tentée quelque part sur la ligne de commande, le système de complétion commence à construire le contexte. Le contexte représente tout ce que le shell sait sur la signification de la ligne de commande et l'importance de la position du curseur. Cela prend en compte un certain nombre de choses, y compris le mot de commande (tel que `grep' ou `zsh') et les options auxquelles le mot actuel peut être un argument (tel que l'option `-o' de zsh qui prend une option shell comme argument).

Le contexte commence très générique ("nous commençons une complétion") et devient plus spécifique à mesure que l'on apprend ("le mot actuel est dans une position qui est généralement un nom de commande" ou "le mot actuel pourrait être un nom de variable", etc.). Par conséquent, le contexte variera au cours du même appel au système de complétion.

Ces informations contextuelles sont condensées en une chaîne composée de plusieurs champs séparés par des deux-points, appelés simplement `le contexte' dans le reste de la documentation. Notez qu'un utilisateur du système de complétion n'a rarement besoin de composer une chaîne de contexte, sauf, par exemple, si une nouvelle fonction est écrite pour effectuer la complétion d'une nouvelle commande. Ce qu'un utilisateur pourrait avoir besoin de faire est de composer un motif de style, qui est mis en correspondance avec un contexte lorsque nécessaire pour rechercher des options sensibles au contexte qui configurent le système de complétion.

Les paragraphes suivants expliquent comment un contexte est composé au sein de la suite de fonctions de complétion. Vient ensuite la discussion sur la manière dont les styles sont définis. Les styles déterminent, par exemple, comment les correspondances sont générées, de manière similaire aux options shell mais avec beaucoup plus de contrôle. Ils sont définis avec la commande intégrée zstyle (voir zshmodules(1)).

La chaîne de contexte se compose toujours d'un ensemble fixe de champs, séparés par des deux-points et avec un deux-points initial avant le premier. Les champs qui ne sont pas encore connus sont laissés vides, mais les deux-points environnants apparaissent de toute façon. Les champs sont toujours dans l'ordre :complétion:fonction:compléteur:commande:argument:balise. Ceux-ci ont la signification suivante :

•
La chaîne littérale complétion, indiquant que ce style est utilisé par le système de complétion. Cela distingue le contexte de ceux utilisés par, par exemple, les widgets zle et les fonctions ZFTP.
•
La fonction, si la complétion est appelée depuis un widget nommé plutôt que via le système de complétion normal. Typiquement, ceci est vide, mais il est défini par des widgets spéciaux tels que predict-on et les diverses fonctions du répertoire Widget de la distribution, au nom de cette fonction, souvent sous une forme abrégée.
•
Le compléteur actuellement actif, le nom de la fonction sans le underscore initial et avec les autres underscores convertis en traits d'union. Un `compléteur' contrôle globalement la manière dont la complétion doit être effectuée ; `compléter' est le plus simple, mais d'autres compléteurs existent pour effectuer des tâches connexes telles que la correction, ou pour modifier le comportement d'un compléteur ultérieur. Voir la section `Fonctions de contrôle' ci-dessous pour plus d'informations.
•
La commande ou un -contexte- spécial, tel qu'il apparaît après la balise #compdef ou la fonction compdef. Les fonctions de complétion pour les commandes ayant des sous-commandes modifient généralement ce champ pour contenir le nom de la commande suivi d'un trait d'union et de la sous-commande. Par exemple, la fonction de complétion pour la commande cvs définit ce champ à cvs-add lors de la complétion des arguments de la sous-commande add.
•
L'argument ; ceci indique quel argument de ligne de commande ou d'option nous sommes en train de compléter. Pour les arguments de commande, cela prend généralement la forme argument-n, où n est le numéro de l'argument, et pour les arguments d'options, la forme option-opt-n où n est le numéro de l'argument de l'option opt. Cependant, ce n'est que si la ligne de commande est analysée avec des options et des arguments de style UNIX standard, donc de nombreuses complétions ne définissent pas cela.
•
La balise. Comme décrit précédemment, les balises sont utilisées pour différencier les types de correspondances qu'une fonction de complétion peut générer dans un certain contexte. Toute fonction de complétion peut utiliser n'importe quel nom de balise, mais une liste des plus courantes est donnée ci-dessous.

Le contexte est progressivement assemblé au fur et à mesure de l'exécution des fonctions, en commençant par le point d'entrée principal, qui ajoute :complétion: et l'élément fonction si nécessaire. Le compléteur ajoute ensuite l'élément compléteur. La complétion contextuelle ajoute les options commande et argument. Enfin, la balise est ajoutée lorsque les types de complétion sont connus. zstyle

La commande zstyle est utilisée pour définir et lire les paramètres du système de complétion de zsh. Elle est appelée avec deux arguments principaux : une chaîne de contexte et un nom de style.

zstyle [-eoption] [-L] [-l] [-s] [-x] [-aarray]
    context pattern style [value ...]

Le contexte pattern est une chaîne qui décrit l'endroit où la complétion est en cours. Les contextes sont structurés sous forme de chaînes séparées par des deux-points, par exemple :

:completion:function:completer:command:argument:tag

Les champs sont les suivants :

function
Le nom de la fonction de complétion en cours d'exécution. Il s'agit généralement d'un nom commençant par un underscore, comme _files ou _program.
completer
Le nom du completer en cours d'exécution. Il peut s'agir de quelque chose comme -compinit, -menu, -list, etc.
command
Le nom de la commande pour laquelle la complétion est en cours. Par exemple, ls, cd, kill.
argument
L'index de l'argument pour lequel la complétion est en cours (en commençant à 0 pour le premier argument). Un astérisque (*) est utilisé si la complétion est effectuée pour plusieurs arguments.
tag
Une balise qui décrit le type d'élément que la complétion est en train de rechercher. Les exemples incluent files, directories, commands, users, etc.

Les modèles de contexte peuvent utiliser des caractères génériques (* et ?) pour correspondre à différents champs.

Le style est le nom de la configuration spécifique que vous souhaitez définir ou lire. Les noms de style sont arbitraires et dépendent de la fonction de complétion.

Si aucune valeur n'est fournie, la commande zstyle essaie de lire la valeur du style pour le contexte donné. Si une ou plusieurs valeurs sont fournies, la commande zstyle définit le style pour le modèle de contexte donné à ces valeurs.

L'option -e à zstyle permet d'utiliser du code zsh comme valeur pour un style. Cela est utile pour des configurations dynamiques.

La commande zstyle sélectionne la correspondance la plus spécifique pour un contexte donné. Par exemple, :completion::complete:*:files est plus spécifique que :completion::complete:*.

Voici un exemple de la façon dont la complétion pour dvips avec l'option -o peut être configurée :

:completion::complete:dvips:option-o-1:files

indique qu'une complétion normale a été tentée en tant que premier argument de l'option -o de la commande dvips :

dvips -o ...

et que la fonction de complétion générera des noms de fichiers.

Normalement, la complétion sera essayée pour toutes les balises possibles dans un ordre donné par la fonction de complétion. Cependant, cela peut être modifié en utilisant le style tag-order. La complétion est alors limitée à la liste des balises données dans l'ordre spécifié.

La commande _complete_help bindable affiche tous les contextes et balises disponibles pour la complétion à un point donné. Cela fournit un moyen facile de trouver des informations pour tag-order et d'autres styles. Elle est décrite dans la section 'Commandes Bindables' ci-dessous.

Lors de la recherche de styles, le système de complétion utilise des noms de contexte complets, y compris la balise. La recherche de la valeur d'un style se compose donc de deux choses : le contexte, qui est mis en correspondance avec le modèle le plus spécifique (le mieux adapté), et le nom du style lui-même, qui doit correspondre exactement. Les exemples suivants démontrent que les modèles peuvent être définis de manière souple pour les styles qui s'appliquent largement, ou aussi précisément que souhaité pour les styles qui s'appliquent dans des circonstances plus restreintes.

Par exemple, de nombreuses fonctions de complétion peuvent générer des correspondances sous une forme simple et une forme verbeuse et utiliser le style verbose pour décider quelle forme doit être utilisée. Pour faire en sorte que toutes ces fonctions utilisent la forme verbeuse, mettez

zstyle ':completion:*' verbose yes

dans un fichier de démarrage (probablement .zshrc). Cela donne au style verbose la valeur yes dans chaque contexte du système de complétion, à moins que ce contexte n'ait une définition plus spécifique. Il est préférable d'éviter de donner le modèle comme `*' au cas où le style aurait une signification en dehors du système de complétion.

De nombreux styles généraux de ce type peuvent être configurés simplement en utilisant la fonction compinstall.

Un exemple plus spécifique de l'utilisation du style verbose est donné par la complétion pour le built-in kill. Si le style est défini, le built-in liste les textes complets des jobs et les lignes de commande des processus ; sinon, il affiche les numéros de jobs et les PID bruts. Pour désactiver le style uniquement pour cet usage :

zstyle ':completion:*:*:kill:*:*' verbose no

Pour un contrôle encore plus fin, le style peut utiliser l'une des balises `jobs' ou `processes'. Pour désactiver l'affichage verbeux uniquement pour les jobs :

zstyle ':completion:*:*:kill:*:jobs' verbose no

L'option -e de zstyle permet même au code de la fonction de complétion d'apparaître comme argument d'un style ; cela nécessite une certaine compréhension des détails internes des fonctions de complétion (voir voir zshcompwid(1))). Par exemple,

zstyle -e ':completion:*' hosts 'reply=($myhosts)'

Cela force la valeur du style hosts à être lue à partir de la variable myhosts chaque fois qu'un nom d'hôte est nécessaire ; ceci est utile si la valeur de myhosts peut changer dynamiquement. Pour un autre exemple utile, voir l'exemple dans la description du style file-list ci-dessous. Cette forme peut être lente et doit être évitée pour les styles couramment examinés tels que menu et list-rows-first.

Notez que l'ordre dans lequel les styles sont *définis* n'a pas d'importance ; le mécanisme de style utilise la correspondance la plus spécifique possible pour un style donné afin de déterminer l'ensemble des valeurs. Les chaînes sont préférées aux modèles (par exemple, `:completion::complete:::foo' est plus spécifique que `:completion::complete:::*'), et les modèles plus longs sont préférés au modèle `*'. Voir zmodules(1) pour les détails.

Les modèles de contexte qui utilisent autre chose qu'un caractère générique (*) pour faire correspondre les parties médianes du contexte -- le completer, la commande et l'*argument* dans :completion:function:completer:command:argument:tag -- doivent inclure explicitement les six deux-points (:). Sans cela, un modèle tel que :completion:*:foo:* pourrait faire correspondre foo à un composant autre que celui prévu (par exemple, au completer alors qu'une correspondance avec la commande était prévue).

Les noms de style, comme ceux des balises, sont arbitraires et dépendent de la fonction de complétion. Cependant, les deux sections suivantes listent certaines des balises et des styles les plus courants.

Styles Standard

Notez que les valeurs de plusieurs de ces styles représentent des valeurs booléennes. N'importe laquelle des chaînes `true', `on', `yes' et `1' peut être utilisée pour la valeur `true' et n'importe laquelle des chaînes `false', `off', `no' et `0' pour la valeur `false'. Le comportement pour toute autre valeur est indéfini, sauf indication contraire explicite. La valeur par défaut peut être `true' ou `false' si le style n'est pas défini.

Certains de ces styles sont testés en premier pour chaque balise possible correspondant à un type de correspondance, et si aucun style n'est trouvé, pour la balise défaut. Les styles les plus notables de ce type sont menu, list-colors et les styles contrôlant l'affichage de la complétion tels que list-packed et last-prompt. Lorsqu'ils sont testés pour la balise défaut, seul le champ fonction du contexte sera défini afin qu'un style utilisant la balise défaut soit normalement défini dans le style de :

zstyle ':completion:*:default' menu ...
accept-exact
Ceci est testé pour la balise défaut en plus des balises valides pour le contexte actuel. S'il est défini à `true' et que l'une des correspondances d'essai est identique à la chaîne sur la ligne de commande, cette correspondance sera immédiatement acceptée (même si elle serait autrement considérée comme ambiguë).

Lors de la complétion de chemins (où la balise utilisée est `chemins'), ce style accepte tout nombre de motifs comme valeur en plus des valeurs booléennes. Les chemins correspondant à l'un de ces motifs seront immédiatement acceptés même si la ligne de commande contient d'autres composants de chemin partiellement tapés et que ceux-ci ne correspondent à aucun fichier sous le répertoire accepté.

Ce style est également utilisé par le compléteur _expand pour décider si les mots commençant par un tilde ou une expansion de paramètre doivent être étendus. Par exemple, s'il existe des paramètres foo et foobar, la chaîne `$foo' ne sera étendue que si accept-exact est défini à `true'; sinon, le système de complétion sera autorisé à compléter $foo en $foobar. Si le style est défini à `continue', _expand ajoutera l'expansion comme correspondance et le système de complétion sera également autorisé à continuer.

accept-exact-dirs
Ceci est utilisé pour la complétion de noms de fichiers. Contrairement à accept-exact, il s'agit d'une valeur booléenne. Par défaut, la complétion de noms de fichiers examine tous les composants d'un chemin pour voir s'il existe des complétions de ce composant, même si le composant correspond à un répertoire existant. Par exemple, lors de la complétion après /usr/bin/, la fonction examine les complétions possibles pour /usr.

Lorsque ce style est `true', tout préfixe d'un chemin qui correspond à un répertoire existant est accepté sans aucune tentative de complétion supplémentaire. Par conséquent, dans l'exemple donné, le chemin /usr/bin/ est immédiatement accepté et la complétion est tentée dans ce répertoire.

Ce style est également utile lors de la complétion après des répertoires qui apparaissent magiquement lorsqu'ils sont référencés, tels que les répertoires .zfs de ZFS ou les répertoires .snapshot de NetApp. Lorsque le style est défini, le shell ne vérifie pas l'existence du répertoire dans le répertoire parent.

Si vous souhaitez interdire entièrement ce comportement, définissez le style path-completion (voir ci-dessous) sur `false'.

add-space
Ce style est utilisé par le compléteur _expand. S'il est `true' (par défaut), un espace sera inséré après tous les mots résultant de l'expansion, ou une barre oblique dans le cas des noms de répertoires. Si la valeur est `file', le compléteur n'ajoutera un espace qu'aux noms de fichiers existants. Une valeur booléenne `true' ou la valeur `file' peuvent être combinées avec `subst', auquel cas le compléteur n'ajoutera pas d'espace aux mots générés à partir de l'expansion d'une substitution de la forme `$(...)' ou `${...}'.

Le compléteur _prefix utilise ce style comme simple valeur booléenne pour décider si un espace doit être inséré avant le suffixe.

ambiguous
Ceci s'applique lors de la complétion de composants non finaux de chemins de noms de fichiers, c'est-à-dire ceux avec une barre oblique finale. S'il est défini, le curseur est laissé après le premier composant ambigu, même si la complétion par menu est utilisée. Le style est toujours testé avec la balise paths.
assign-list
Lors de la complétion après un signe égal qui est traité comme une affectation, le système de complétion ne complète normalement qu'un seul nom de fichier. Dans certains cas, la valeur peut être une liste de noms de fichiers séparés par des deux-points, comme pour PATH et les paramètres similaires. Ce style peut être défini à une liste de motifs correspondant aux noms de tels paramètres.

Par défaut, les listes sont complétées lorsque le mot sur la ligne contient déjà un deux-points.

auto-description
S'il est défini, la valeur de ce style sera utilisée comme description pour les options qui ne sont pas
décrites par les fonctions de complétion, mais qui n'ont exactement qu'un seul argument. La séquence `%d' dans la valeur sera remplacée par la description de cet argument. Selon les préférences personnelles, il peut être utile de définir ce style sur quelque chose comme `specify: %d'. Notez que cela peut ne pas fonctionner pour certaines commandes.
avoid-completer
Ceci est utilisé par le compléteur _all_matches pour décider si la chaîne composée de toutes les correspondances doit être ajoutée à la liste en cours de génération. Sa valeur est une liste de noms de completers. Si l'un de ceux-ci est le nom du compléteur qui a généré les correspondances dans cette complétion, la chaîne ne sera pas ajoutée.

La valeur par défaut pour ce style est `_expand _old_list _correct _approximate', c'est-à-dire qu'il contient les completers pour lesquels une chaîne avec toutes les correspondances ne sera presque jamais souhaitée.

cache-path
Ce style définit le chemin où sont stockés les éventuels fichiers de cache contenant les données de complétion vidées. Il vaut par défaut `$ZDOTDIR/.zcompcache', ou `$HOME/.zcompcache' si $ZDOTDIR n'est pas défini. Le cache de complétion ne sera pas utilisé à moins que le style use-cache ne soit défini.
cache-policy
Ce style définit la fonction qui sera utilisée pour déterminer si un cache doit être reconstruit. Voir la section sur la fonction _cache_invalid ci-dessous.
call-command
Ce style est utilisé dans la fonction pour des commandes telles que make et ant où l'appel direct de la commande pour générer les correspondances pose des problèmes tels qu'être lent ou, comme dans le cas de make, peut potentiellement provoquer l'exécution d'actions dans le makefile. S'il est défini sur `true', la commande est appelée pour générer les correspondances. La valeur par défaut de ce style est `false'.
command
Dans de nombreux endroits, les fonctions de complétion doivent appeler des commandes externes pour générer la liste des complétions. Ce style peut être utilisé pour remplacer la commande appelée dans certains de ces cas. Les éléments de la valeur sont joints avec des espaces pour former une ligne de commande à exécuter. La valeur peut également commencer par un trait d'union, auquel cas la commande habituelle sera ajoutée à la fin ; ceci est particulièrement utile pour placer `builtin' ou `command' devant afin de s'assurer que la version appropriée d'une commande est appelée, par exemple pour éviter d'appeler une fonction shell portant le même nom qu'une commande externe.

Par exemple, la fonction de complétion pour les identifiants de processus utilise ce style avec le tag processes pour générer les identifiants à compléter et la liste des processus à afficher (si le style verbose est `true'). La liste produite par la commande doit ressembler à la sortie de la commande ps. La première ligne n'est pas affichée, mais est recherchée pour la chaîne `PID' (ou `pid') afin de trouver la position des identifiants de processus dans les lignes suivantes. Si la ligne ne contient pas `PID', les premiers nombres de chacune des autres lignes sont considérés comme les identifiants de processus à compléter.

Notez que la fonction de complétion doit généralement appeler la commande spécifiée pour chaque tentative de génération de la liste de complétion. Par conséquent, il faut veiller à ne spécifier que des commandes qui prennent peu de temps à s'exécuter, et en particulier à éviter celles qui pourraient ne jamais se terminer.

command-path
Ceci est une liste de répertoires à rechercher pour les commandes à compléter. La valeur par défaut pour ce style est la valeur du paramètre spécial path.
commands
Ceci est utilisé par la fonction complétant les sous-commandes des scripts d'initialisation système (résidant dans /etc/init.d ou quelque part pas trop loin de là). Ses valeurs donnent les commandes par défaut à compléter pour les commandes pour lesquelles la fonction de complétion ne parvient pas à les trouver automatiquement. La valeur par défaut pour ce style sont les deux chaînes `start' et `stop'.
complete
Ceci est utilisé par la fonction _expand_alias lorsqu'elle est invoquée comme commande bindable. Si défini sur `true' et que le mot sur la ligne de commande n'est pas le nom d'un alias, les noms d'alias correspondants seront complétés.
complete-options
Ceci est utilisé par le compléteur pour cd, chdir et pushd. Pour ces commandes, un - est utilisé pour introduire une entrée de la pile de répertoires et la complétion de celles-ci est beaucoup plus courante que la complétion d'options. Par conséquent, à moins que la valeur de ce style ne soit `true', les options ne seront pas complétées, même après un - initial. Si elle est `true', les options seront complétées après un - initial à moins qu'un -- ne précède sur la ligne de commande.
completer
Les chaînes données comme valeur de ce style fournissent les noms des fonctions de compléteur à utiliser. Les fonctions de compléteur disponibles sont décrites dans la section `Fonctions de contrôle' ci-dessous.

Chaque chaîne peut être soit le nom d'une fonction de compléteur, soit une chaîne de la forme `function:name'. Dans le premier cas, le champ completer du contexte contiendra le nom du compléteur sans le tiret initial et avec tous les autres tirets remplacés par des traits d'union. Dans le second cas, function est le nom du compléteur à appeler, mais le contexte contiendra le name défini par l'utilisateur dans le champ completer du contexte. Si le name commence par un trait d'union, la chaîne pour le contexte sera construite à partir du nom de la fonction de compléteur comme dans le premier cas avec le name ajouté. Par exemple :

zstyle ':completion:*' completer _complete _complete:-foo

Ici, la complétion appellera le compléteur _complete deux fois, une fois en utilisant `complete' et une fois en utilisant `complete-foo' dans le champ completer du contexte. Normalement, utiliser le même compléteur plus d'une fois n'a de sens que lorsqu'il est utilisé avec la forme `functions:name', car sinon le nom du contexte sera le même dans tous les appels au compléteur ; des exceptions possibles à cette règle sont les completers _ignored et _prefix.

La valeur par défaut pour ce style est `_complete _ignored' : seule la complétion sera effectuée, d'abord en utilisant le style ignored-patterns et le tableau $fignore, puis sans ignorer les correspondances.

condition
Ce style est utilisé par la fonction de compléteur _list pour décider si l'insertion des correspondances doit être retardée inconditionnellement. La valeur par défaut est `true'.
delimiters
Ce style est utilisé lors de l'ajout d'un délimiteur à utiliser avec les modificateurs d'historique ou les qualificateurs glob qui ont des arguments délimités. C'est un tableau de délimiteurs préférés à ajouter. Les caractères non spéciaux sont préférés car le système de complétion pourrait autrement se confondre. La liste par défaut est :, +, /, -, %. La liste peut être vide pour forcer la saisie d'un délimiteur.
disabled
Si ceci est défini sur `true', le compléteur _expand_alias et la commande bindable essaieront également de développer les alias désactivés. La valeur par défaut est `false'.
domains
Une liste de noms de domaines réseau pour la complétion. Si ce n'est pas défini, les noms de domaine seront pris dans le fichier /etc/resolv.conf.
environ
Le style environ est utilisé lors de la complétion pour `sudo'. Il est défini sur un tableau d'affectations `VAR=value' à exporter dans l'environnement local avant que la complétion pour la commande cible ne soit invoquée.
zstyle ':completion:*:sudo::' environ \ 
  PATH="/sbin:/usr/sbin:$PATH" HOME="/root"
expand
Ce style est utilisé lors de la complétion de chaînes composées de plusieurs parties, telles que des noms de chemins.

Si l'une de ses valeurs est la chaîne `prefix', le mot partiellement tapé sur la ligne sera développé autant que possible même si les parties finales ne peuvent pas être complétées.

Si l'une de ses valeurs est la chaîne `suffix', les noms correspondants pour les composants après le premier ambigu seront également ajoutés. Cela signifie que la chaîne résultante est la chaîne non ambiguë la plus longue possible. Cependant, la complétion par menu peut être utilisée pour parcourir toutes les correspondances.

extra-verbose
Si défini, la liste de complétion est plus verbeuse au détriment d'une probable diminution de la vitesse de complétion. Les performances de complétion seront affectées si ce style est défini sur `true'.
fake
Ce style peut être défini pour n'importe quel contexte de complétion. Il spécifie des chaînes supplémentaires qui seront toujours complétées dans ce contexte. La forme de chaque chaîne est `value:description' ; les deux-points et la description peuvent être omis, mais tous les deux-points littéraux dans value doivent être échappés avec une barre oblique inverse. Toute description fournie est affichée à côté de la valeur dans les listes de complétion.

Il est important d'utiliser un contexte suffisamment restrictif lors de la spécification de chaînes fictives. Notez que les styles fake-files et fake-parameters offrent des fonctionnalités supplémentaires lors de la complétion de fichiers ou de paramètres.

fake-always
Cela fonctionne de manière identique au style fake, à l'exception du fait que le style ignored-patterns ne lui est pas appliqué. Cela permet de remplacer un ensemble de correspondances complètement en définissant les motifs ignorés sur `*'.

Ce qui suit montre une manière de compléter toute étiquette avec des données arbitraires, tout en la faisant se comporter comme une étiquette distincte à des fins d'affichage. Dans cet exemple, nous utilisons les fonctionnalités du style tag-order pour diviser l'étiquette named-directories en deux lors de la complétion avec le compléteur standard complete pour les arguments de cd. L'étiquette named-directories-normal se comporte normalement, mais l'étiquette named-directories-mine c

contient un ensemble fixe de répertoires. Cela a pour effet d'ajouter le groupe de correspondances `répertoires supplémentaires' avec les complétions données.

zstyle ':completion::complete:cd:*' tag-order \ 
  'named-directories:-mine:extra\ directories
  named-directories:-normal:named\ directories *'
zstyle ':completion::complete:cd:*:named-directories-mine' \ 
  fake-always mydir1 mydir2
zstyle ':completion::complete:cd:*:named-directories-mine' \ 
  ignored-patterns '*'
fake-files
Ce style est utilisé lors de la complétion de fichiers et recherché sans étiquette. Ses valeurs sont de la forme `rép:noms...'. Cela ajoutera les noms (chaînes séparées par des espaces) comme correspondances possibles lors de la complétion dans le répertoire rép, même si aucun fichier de ce type n'existe réellement. Le répertoire peut être un motif ; les caractères de motif ou les deux-points dans rép doivent être échappés avec une barre oblique inverse pour être traités littéralement.

Cela peut être utile sur les systèmes qui prennent en charge les systèmes de fichiers spéciaux dont les noms de chemin de niveau supérieur ne peuvent pas être listés ou générés avec des motifs glob (mais voir accept-exact-dirs pour une manière plus générale de traiter ce problème). Cela peut également être utilisé pour les répertoires pour lesquels on n'a pas la permission de lecture.

La forme de motif peut être utilisée pour ajouter une entrée `magique' à tous les répertoires d'un système de fichiers particulier.

fake-parameters
Ceci est utilisé par la fonction de complétion pour les noms de paramètres. Ses valeurs sont des noms de paramètres qui ne sont peut-être pas encore définis mais qui devraient néanmoins être complétés. Chaque nom peut également être suivi d'un deux-points et d'une chaîne spécifiant le type du paramètre (comme `scalar', `array' ou `integer'). Si le type est donné, le nom ne sera complété que si des paramètres de ce type sont requis dans le contexte particulier. Les noms pour lesquels aucun type n'est spécifié seront toujours complétés.
file-list
Ce style contrôle si les fichiers complétés à l'aide du mécanisme intégré standard sont affichés avec une liste longue similaire à ls -l. Notez que cette fonctionnalité utilise le module shell zsh/stat pour les informations sur les fichiers ; cela charge le builtin stat qui remplacera tout exécutable stat externe. Pour éviter cela, le code suivant peut être inclus dans un fichier d'initialisation :
zmodload -i zsh/stat
disable stat

Le style peut être défini sur une valeur `vraie' (ou `all'), ou l'une des valeurs `insert' ou `list', indiquant que les fichiers doivent être listés en format long dans toutes les circonstances, ou lors de la tentative d'insertion d'un nom de fichier, ou lors de la liste des noms de fichiers sans tentative d'insertion.

Plus généralement, la valeur peut être un tableau de l'une des valeurs ci-dessus, optionnellement suivi de =num. Si num est présent, il donne le nombre maximum de correspondances pour lesquelles le style de liste longue sera utilisé. Par exemple,

zstyle ':completion:*' file-list list=20 insert=10

spécifie que le format long sera utilisé lors de la liste de jusqu'à 20 fichiers ou de l'insertion d'un fichier avec jusqu'à 10 correspondances (en supposant qu'une liste doit être affichée), sinon le format court sera utilisé.

zstyle -e ':completion:*' file-list \ 
       '(( ${+NUMERIC} )) && reply=(true)'

spécifie que le format long sera utilisé chaque fois qu'un argument numérique est fourni, sinon le format court.

file-patterns
Ceci est utilisé par la fonction standard de complétion des noms de fichiers, _files. Si le style n'est pas défini, jusqu'à trois étiquettes sont proposées : `globbed-files', `directories' et `all-files', en fonction des types de fichiers attendus par l'appelant de _files. Les deux premières (`globbed-files' et `directories') sont normalement proposées ensemble pour faciliter la complétion des fichiers dans les sous-répertoires.

Le style file-patterns fournit des alternatives aux étiquettes par défaut, qui ne sont pas utilisées. Sa valeur se compose d'éléments de la forme `motif:étiquette' ; chaque chaîne peut contenir un nombre quelconque de telles spécifications séparées par des espaces.

Le motif est un motif utilisé pour générer les noms de fichiers. Toute occurrence de la séquence `%p' est remplacée par les motifs passés par la fonction appelant _files. Les deux-points dans le motif doivent être précédés d'une barre oblique inverse pour les distinguer du deux-points avant l'étiquette. Si plusieurs motifs sont nécessaires, les motifs peuvent être donnés entre accolades, séparés par des virgules.

Les étiquettes de toutes les chaînes de la valeur seront proposées par _files et utilisées lors de la recherche d'autres styles. Les étiquettes dans le même mot seront proposées en même temps et avant les mots suivants. Si aucun `:étiquette' n'est donné, l'étiquette `files' sera utilisée.

L'étiquette peut également être suivie d'un deuxième deux-points optionnel et d'une description, qui sera utilisée pour le `%d' dans la valeur du style format (si elle est définie) au lieu de la description par défaut fournie par la fonction de complétion. L'inclusion d'une description donne également la priorité aux options associées, comme pour le regroupement des complétions, afin qu'elle puisse être utilisée lorsque les fichiers doivent être séparés.

Par exemple, pour que la commande rm complète d'abord uniquement les noms de fichiers objets, puis les noms de tous les fichiers s'il n'y a pas de fichier objet correspondant :

zstyle ':completion:*:*:rm:*:*' file-patterns \ 
    '*.o:object-files' '%p:all-files'

Pour modifier le comportement par défaut de la complétion de fichiers - proposer des fichiers correspondant à un motif et des répertoires lors de la première tentative, puis tous les fichiers - pour proposer uniquement des fichiers correspondants lors de la première tentative, puis des répertoires, et enfin tous les fichiers :

zstyle ':completion:*' file-patterns \ 
    '%p:globbed-files' '*(-/):directories' '*:all-files'

Cela fonctionne même là où il n'y a pas de motif spécial : _files correspond à tous les fichiers en utilisant le motif `*' à la première étape et s'arrête lorsqu'il voit ce motif. Notez qu'il n'essaiera jamais un motif plus d'une fois pour une seule tentative de complétion.

Pour séparer les répertoires dans un groupe distinct des fichiers mais toujours les compléter lors de la première tentative, une description doit être fournie. Notez que les répertoires doivent être explicitement exclus des fichiers globés car `*' correspondra aux répertoires. Pour le regroupement, il est également nécessaire de définir le style group-name.

zstyle ':completion:*' file-patterns \ 
    '%p(^-/):globbed-files *(-/):directories:location'

Pendant l'exécution des fonctions de complétion, l'option EXTENDED_GLOB est activée, de sorte que les caractères `#', `~' et `^' ont des significations spéciales dans les motifs.

file-sort
La fonction standard de complétion de noms de fichiers utilise ce style sans étiquette pour déterminer dans quel ordre les noms doivent être listés ; la complétion par menu les parcourra dans le même ordre. Les valeurs possibles sont : `size' pour trier par la taille du fichier ; `links' pour trier par le nombre de liens vers le fichier ; `modification' (ou `time' ou `date') pour trier par l'heure de dernière modification ; `access' pour trier par l'heure de dernier accès ; et `inode' (ou `change') pour trier par l'heure de dernière modification de l'inode. Si le style est défini sur toute autre valeur, ou n'est pas défini, les fichiers seront triés par ordre alphabétique par nom. Si la valeur contient la chaîne `reverse', le tri s'effectue dans l'ordre inverse. Si la valeur contient la chaîne `follow', les horodatages sont associés aux cibles des liens symboliques ; par défaut, les horodatages des liens eux-mêmes sont utilisés.
file-split-chars
Un ensemble de caractères qui provoquera la division de *toutes* les complétions de fichiers pour le contexte donné au point où l'un des caractères apparaît. Une utilisation typique est de définir le style sur : ; alors tout jusqu'au dernier : inclus dans la chaîne actuelle est ignoré lors de la complétion des fichiers. Comme cela est assez radical, il est généralement préférable de mettre à jour les fonctions de complétion pour les contextes où ce comportement est utile.
filter
Le plugin ldap de la complétion des adresses e-mail (voir _email_addresses) utilise ce style pour spécifier les attributs sur lesquels faire correspondre lors du filtrage des entrées. Ainsi, par exemple, si le style est défini sur `sn', la correspondance s'effectue sur les noms de famille. Le filtrage LDAP standard est utilisé, de sorte que la correspondance de complétion normale est contournée. Si ce style n'est pas défini, le plugin LDAP est ignoré. Vous devrez peut-être également définir le style command pour spécifier comment vous connecter à votre serveur LDAP.
force-list
Cela force l'affichage d'une liste de complétions à tout moment où une liste est affichée, même dans les cas où la liste serait normalement supprimée. Par exemple, normalement la liste n'est affichée que s'il y a au moins deux correspondances différentes. En définissant ce style sur `always', la liste sera toujours affichée, même s'il n'y a qu'une seule correspondance qui sera immédiatement acceptée. Le style peut également être défini sur un nombre. Dans ce cas, la liste sera affichée s'il y a au moins ce nombre de correspondances, même si elles insèrent toutes la même chaîne.

Ce style est testé pour l'étiquette par défaut ainsi que pour chaque étiquette valide pour la complétion actuelle. Par conséquent, la liste peut être forcée uniquement pour certains types de correspondances.

format
Si ceci est défini pour l'étiquette descriptions, sa valeur est utilisée comme chaîne à afficher au-dessus des correspondances dans les listes de complétion. La séquence `%d' dans cette chaîne sera remplacée par une brève description de ce que sont ces correspondances. Cette chaîne peut également contenir les séquences d'attributs de sortie comprises par compadd -X (voir zshcompwid(1)).

Le style est testé avec chaque étiquette valide pour la complétion actuelle avant d'être testé pour l'étiquette descriptions. Par conséquent, des chaînes de format différentes peuvent être définies pour différents types de correspondances.

Notez également que certaines fonctions de complétion définissent des séquences `%' supplémentaires. Celles-ci sont décrites pour les fonctions de complétion qui les utilisent.

hem.

Certaines fonctions de complétion affichent des messages qui peuvent être personnalisés en définissant ce style pour la balise messages. Ici, le `%d' est remplacé par un message donné par la fonction de complétion.

Enfin, la chaîne de format est recherchée avec la balise warnings, pour une utilisation lorsque aucune correspondance n'a pu être générée du tout. Dans ce cas, le `%d' est remplacé par les descriptions des correspondances attendues, séparées par des espaces. La séquence `%D' est remplacée par les mêmes descriptions séparées par des sauts de ligne.

Il est possible d'utiliser des spécificateurs de largeur de champ de style printf avec `%d' et des séquences d'échappement similaires. Ceci est géré par la commande intégrée zformat du module zsh/zutil, voir zshmodules(1).

gain-privileges
Si cette option est définie sur true, ce style active l'utilisation de commandes telles que sudo ou doas pour obtenir des privilèges supplémentaires lors de la récupération d'informations pour la complétion. Ceci n'est fait que lorsqu'une commande telle que sudo apparaît sur la ligne de commande. Pour forcer l'utilisation de, par exemple, sudo ou pour remplacer tout préfixe qui pourrait être ajouté en raison de gain-privileges, le style command peut être utilisé avec une valeur commençant par un trait d'union.
glob
Ceci est utilisé par le compléteur _expand. S'il est défini sur `true' (par défaut), une tentative de globbing sera effectuée sur les mots résultant d'une substitution précédente (voir le style substitute) ou sur la chaîne d'origine de la ligne.
global
Si cette option est définie sur `true' (par défaut), le compléteur _expand_alias et la commande bindable tenteront d'étendre les alias globaux.
group-name
Le système de complétion peut grouper différents types de correspondances, qui apparaissent dans des listes séparées. Ce style peut être utilisé pour donner les noms des groupes pour des balises particulières. Par exemple, en position de commande, le système de complétion génère les noms des commandes intégrées et externes, les noms des alias, les fonctions shell et les paramètres ainsi que les mots réservés comme complétions possibles. Pour que les commandes externes et les fonctions shell soient listées séparément :
zstyle ':completion:*:*:-command-:*:commands' \ 
       group-name commands
zstyle ':completion:*:*:-command-:*:functions' \ 
       group-name functions

En conséquence, toute correspondance portant la même balise sera affichée dans le même groupe.

Si le nom donné est la chaîne vide, le nom de la balise pour les correspondances sera utilisé comme nom de groupe. Ainsi, pour que tous les différents types de correspondances soient affichés séparément, on peut simplement définir :

zstyle ':completion:*' group-name ''

Toutes les correspondances pour lesquelles aucun nom de groupe n'est défini seront placées dans un groupe nommé -default-.

Pour afficher le nom du groupe dans la sortie, voir le style format (voir ci-dessus) sous la balise descriptions.

group-order
Ce style est supplémentaire au style group-name pour spécifier l'ordre d'affichage des groupes définis par ce style (comparer à tag-order, qui détermine quelles complétions apparaissent du tout). Les groupes nommés sont affichés dans l'ordre donné ; tous les autres groupes sont affichés dans l'ordre défini par la fonction de complétion.

Par exemple, pour que les noms des commandes intégrées, des fonctions shell et des commandes externes apparaissent dans cet ordre lors de la complétion en position de commande :

zstyle ':completion:*:*:-command-:*:*' group-order \ 
       builtins functions commands
groups
Une liste de noms de groupes UNIX. Si ceci n'est pas défini, les noms de groupes sont pris de la base de données YP ou du fichier `/etc/group'.
hidden
Si cette option est définie sur `true', les correspondances pour le contexte donné ne seront pas listées, bien que toute description des correspondances définie avec le style format sera affichée. Si elle est définie sur `all', même la description ne sera pas affichée.

Notez que les correspondances seront toujours complétées ; elles ne sont tout simplement pas affichées dans la liste. Pour éviter que des correspondances ne soient considérées du tout comme des complétions possibles, le style tag-order peut être modifié comme décrit ci-dessous.

hosts
Une liste de noms d'hôtes qui devraient être complétés. Si ceci n'est pas défini, les noms d'hôtes sont pris du fichier `/etc/hosts'.
hosts-ports
Ce style est utilisé par les commandes qui ont besoin ou acceptent des noms d'hôtes et des ports réseau. Les chaînes de la valeur doivent être de la forme `hôte:port'. Les ports valides sont déterminés par la présence de noms d'hôtes ; plusieurs ports pour le même hôte peuvent apparaître.
ignore-line
Ceci est testé pour chaque balise valide pour la complétion actuelle. Si elle est définie sur `true', aucun des mots déjà présents sur la ligne ne sera considéré comme une complétion possible. Si elle est définie sur `current', le mot sur lequel se trouve le curseur ne sera pas considéré comme une complétion possible. La valeur `current-shown' est similaire mais ne s'applique que si la liste des complétions est actuellement affichée à l'écran. Enfin, si le style est défini sur `other', tous les mots sur la ligne sauf celui actuel seront exclus des complétions possibles.

Les valeurs `current' et `current-shown' sont un peu comme l'inverse du style accept-exact : seules les chaînes avec des caractères manquants seront complétées.

Notez que vous ne voudrez presque certainement pas définir ceci sur `true' ou `other' pour un contexte général tel que `:completion:*'. C'est parce que cela interdirait la complétion, par exemple, d'options plusieurs fois même si la commande en question accepte l'option plus d'une fois.

ignore-parents
Le style est testé sans balise par la fonction complétant les noms de chemin afin de déterminer s'il faut ignorer les noms de répertoires déjà mentionnés dans le mot actuel, ou le nom du répertoire de travail actuel. La valeur doit inclure l'une ou les deux des chaînes suivantes :
parent
Le nom de tout répertoire dont le chemin est déjà contenu dans le mot sur la ligne est ignoré. Par exemple, lors de la complétion après foo/../, le répertoire foo ne sera pas considéré comme une complétion valide.
pwd
Le nom du répertoire de travail actuel ne sera pas complété ; par conséquent, par exemple, la complétion après ../ n'utilisera pas le nom du répertoire actuel.

En outre, la valeur peut inclure l'un ou les deux des éléments suivants :

..
Ignorer les répertoires spécifiés uniquement lorsque le mot sur la ligne contient la sous-chaîne `../'.
directory
Ignorer les répertoires spécifiés uniquement lorsque les noms de répertoires sont complétés, pas lors de la complétion des noms de fichiers.

Les valeurs exclues agissent de manière similaire aux valeurs du style ignored-patterns, elles peuvent donc être remises en considération par le compléteur _ignored.

ignored-patterns
Une liste de motifs ; toute tentative de complétion correspondant à l'un des motifs sera exclue de la considération. Le compléteur _ignored peut apparaître dans la liste des completers pour restaurer les correspondances ignorées. Ceci est une version plus configurable du paramètre shell $fignore.

Notez que l'option EXTENDED_GLOB est définie lors de l'exécution des fonctions de complétion, donc les caractères `#', `~' et `^' ont des significations spéciales dans les motifs.

insert
Ce style est utilisé par le compléteur _all_matches pour décider s'il faut insérer la liste de toutes les correspondances inconditionnellement au lieu d'ajouter la liste comme une autre correspondance.
insert-ids
Lors de la complétion des identifiants de processus, par exemple comme arguments pour les commandes intégrées kill et wait, le nom d'une commande peut être converti en l'identifiant de processus approprié. Un problème survient lorsque le nom du processus tapé n'est pas unique. Par défaut (ou si ce style est explicitement défini sur `menu'), le nom sera immédiatement converti en un ensemble d'identifiants possibles, et la complétion par menu sera lancée pour les parcourir.

Si la valeur du style est `single', le shell attendra que l'utilisateur ait tapé suffisamment pour rendre la commande unique avant de convertir le nom en un identifiant ; les tentatives de complétion seront infructueuses jusqu'à ce point. Si la valeur est une autre chaîne, la complétion par menu sera lancée lorsque la chaîne tapée par l'utilisateur est plus longue que le préfixe commun des identifiants correspondants.

insert-sections
Ce style est utilisé avec les balises de la forme `manuals.X' lors de la complétion des noms de pages de manuel. Si défini et que le X dans le nom de la balise correspond au numéro de section de la page en cours de complétion, le numéro de section est inséré avec le nom de la page. Par exemple, étant donné
zstyle ':completion:*:manuals.*' insert-sections true

man ssh_<TAB> peut être complété en man 5 ssh_config.

La valeur peut également être définie sur l'une des valeurs `prepend', ou `suffix'. `prepend' se comporte de la même manière que `true' comme dans l'exemple ci-dessus, tandis que `suffix' complèterait man ssh_<TAB> en man ssh_config.5.

Ceci est particulièrement utile en conjonction avec separate-sections, car cela garantit que la page demandée à man correspond à celle affichée dans la liste de complétion lorsqu'il existe plusieurs pages portant le même nom (par exemple, printf(1) et printf(3)).

La valeur par défaut pour ce style est `false'.

insérer-tab
Si cette option est définie sur `true', le système de complétion insérera un caractère TAB (en supposant que ce caractère a été utilisé pour démarrer la complétion) au lieu d'effectuer la complétion lorsqu'il n'y a aucun caractère non vide à gauche du curseur. Si elle est définie sur `false', la complétion sera effectuée même dans ce cas.

La valeur peut également contenir les sous-chaînes `en attente' ou `en attente=val'. Dans ce cas, le caractère tapé sera inséré au lieu de démarrer la complétion lorsqu'il y a une entrée non traitée en attente. Si une val est donnée, la complétion ne sera pas effectuée s'il y a au moins ce nombre de caractères d'entrée non traitée. Ceci est souvent utile lors du collage de caractères dans un terminal. Notez cependant que cela repose sur le paramètre spécial $PENDING du module zsh/zle qui doit être correctement défini, ce qui n'est pas garanti sur toutes les plateformes.

La valeur par défaut de ce style est `true', sauf pour la complétion au sein de la commande intégrée vared où elle est `false'.

insert-unambiguous
Ceci est utilisé par les compléteurs _match et _approximate. Ces compléteurs sont souvent utilisés avec la complétion par menu car le mot tapé peut peu ressembler à la complétion finale. Cependant, si ce style est `true', le compléteur ne démarrera la complétion par menu que s'il ne trouve aucune chaîne initiale non ambiguë d'une longueur au moins égale à la chaîne originale tapée par l'utilisateur.

Dans le cas du compléteur _approximate, le champ compléteur dans le contexte aura déjà été défini sur l'un des termes correct-nombre ou approximate-nombre, où nombre est le nombre d'erreurs acceptées.

Dans le cas du compléteur _match, le style peut également être défini sur la chaîne `pattern'. La forme de la ligne n'est alors pas modifiée si elle ne correspond pas sans ambiguïté.

keep-prefix
Ce style est utilisé par le compléteur _expand. S'il est défini sur `true', le completeur essaiera de conserver un préfixe contenant une expansion tilde ou paramètre. Ainsi, par exemple, la chaîne `~/f*' serait développée en `~/foo' au lieu de `/home/user/foo'. Si le style est défini sur `changed' (la valeur par défaut), le préfixe ne sera laissé inchangé que s'il y a eu d'autres changements entre les mots développés et le mot d'origine de la ligne de commande. Toute autre valeur force l'expansion du préfixe inconditionnellement.

Le comportement de _expand lorsque ce style est `true' est de faire abandonner _expand lorsqu'une seule expansion avec le préfixe restauré est identique à l'original ; ainsi, les compléteurs restants peuvent être appelés.

known-hosts-files
Ce style doit contenir une liste de fichiers dans lesquels rechercher les noms d'hôtes et (si le style use-ip est défini) les adresses IP, dans un format compatible avec les fichiers known_hosts de ssh. S'il n'est pas défini, les fichiers /etc/ssh/ssh_known_hosts et ~/.ssh/known_hosts sont utilisés.
last-prompt
C'est une forme plus flexible de l'option ALWAYS_LAST_PROMPT. Si elle est définie sur `true', le système de complétion essaiera de ramener le curseur à la ligne de commande précédente après avoir affiché une liste de complétion. Elle est testée pour toutes les balises valides pour la complétion actuelle, puis pour la balise default. Le curseur sera ramené à la ligne précédente si ce style est `true' pour tous les types de correspondance. Notez que, contrairement à l'option ALWAYS_LAST_PROMPT, cela est indépendant de l'argument numérique.
list
Ce style est utilisé par la commande de raccourci clavier _history_complete_word. S'il est défini sur `true', il n'a aucun effet. S'il est défini sur `false', les correspondances ne seront pas listées. Cela remplace le réglage des options contrôlant le comportement de listage, en particulier AUTO_LIST. Le contexte commence toujours par `:completion:history-words'.
list-colors
Si le module zsh/complist est chargé, ce style peut être utilisé pour définir des spécifications de couleurs. Ce mécanisme remplace l'utilisation des paramètres ZLS_COLORS et ZLS_COLOURS décrits dans la section `Le module zsh/complist' de zshmodules(1), mais la syntaxe est la même.

Si ce style est défini pour la balise default, les chaînes de la valeur sont considérées comme des spécifications à utiliser partout. Si elle est définie pour d'autres balises, les spécifications ne sont utilisées que pour les correspondances du type décrit par la balise. Pour que cela fonctionne au mieux, le style group-name doit être défini sur une chaîne vide.

En plus de définir des styles pour des balises spécifiques, il est également possible d'utiliser des noms de groupe spécifiés explicitement par la balise group-name avec la syntaxe `(groupe)' autorisée par les paramètres ZLS_COLORS et ZLS_COLOURS et en utilisant simplement la balise default.

Il est possible d'utiliser toutes les spécifications de couleurs déjà configurées pour la version GNU de la commande ls :

zstyle ':completion:*:default' list-colors \ 
       ${(s.:.)LS_COLORS}

Les couleurs par défaut sont les mêmes que celles de la commande GNU ls et peuvent être obtenues en définissant le style sur une chaîne vide (c'est-à-dire '').

list-dirs-first
Ceci est utilisé pour la complétion de fichiers et correspond à un réglage particulier du style file-patterns. Si défini, les répertoires par défaut à compléter sont listés séparément et avant la complétion pour les autres fichiers.
list-grouped
Si ce style est défini sur `true' (la valeur par défaut), le système de complétion essaiera de rendre certains listages de complétion plus compacts en regroupant les correspondances. Par exemple, les options de commandes ayant la même description (affichée lorsque le style verbose est défini sur `true') apparaîtront comme une seule entrée. Cependant, la sélection par menu peut être utilisée pour parcourir toutes les correspondances.
list-packed
Ceci est testé pour chaque balise valide dans le contexte actuel ainsi que pour la balise default. S'il est défini sur `true', les correspondances correspondantes apparaissent dans les listages comme si l'option LIST_PACKED était définie. S'il est défini sur `false', elles sont listées normalement.
list-prompt
Si ce style est défini pour la balise default, les listes de complétion qui ne tiennent pas sur l'écran peuvent être déroulées (voir la description du module zsh/complist dans zshmodules(1)). La valeur, si elle n'est pas la chaîne vide, sera affichée après chaque écran et le shell demandera une pression de touche ; si le style est défini sur la chaîne vide, un prompt par défaut sera utilisé.

La valeur peut contenir les séquences d'échappement : `%l' ou `%L', qui seront remplacées par le numéro de la dernière ligne affichée et le nombre total de lignes ; `%m' ou `%M', le numéro de la dernière correspondance affichée et le nombre total de correspondances ; et `%p' et `%P', `Top' lorsque vous êtes au début de la liste, `Bottom' lorsque vous êtes à la fin et la position affichée en pourcentage de la longueur totale sinon. Dans chaque cas, la forme avec la lettre majuscule sera remplacée par une chaîne de largeur fixe, complétée à droite avec des espaces, tandis que la forme en minuscules sera remplacée par une chaîne de largeur variable. Comme dans d'autres chaînes de prompt, les séquences d'échappement `%S', `%s', `%B', `%b', `%U', `%u' pour entrer et sortir des modes d'affichage en relief, gras et souligné, et `%F', `%f', `%K', `%k' pour changer la couleur du premier plan et de l'arrière-plan, sont également disponibles, ainsi que la forme `%{...%}' pour encapsuler les séquences d'échappement qui s'affichent avec une largeur nulle (ou, avec un argument numérique, une largeur différente).

Après avoir supprimé ce prompt, la variable LISTPROMPT doit être désactivée pour que la suppression prenne effet.

list-rows-first
Ce style est testé de la même manière que le style list-packed et détermine si les correspondances doivent être listées dans un ordre ligne par ligne, comme si l'option LIST_ROWS_FIRST était définie.
list-separator
La valeur de ce style est utilisée dans le listage de complétion pour séparer la chaîne à compléter d'une description lorsque c'est possible (par exemple, lors de la complétion d'options). Elle est par défaut `--' (deux tirets).
list-suffixes
Ce style est utilisé par la fonction qui complète les noms de fichiers. S'il est défini sur `true', et que la complétion est tentée sur une chaîne contenant plusieurs composants de chemin d'accès partiellement tapés, tous les composants ambigus seront affichés. Sinon, la complétion s'arrête au premier composant ambigu.
local
Ceci est destiné aux fonctions qui complètent des URL pour lesquelles les fichiers correspondants sont disponibles directement depuis le système de fichiers. Sa valeur doit consister en trois chaînes : un nom d'hôte, le chemin vers les pages Web par défaut du serveur, et le nom du répertoire utilisé par un utilisateur pour placer des pages Web dans sa zone personnelle.

Par exemple :

zstyle ':completion:*' local toast \ 
    /var/http/public/toast public_html

La complétion après `http://toast/stuff/' recherchera les fichiers dans le répertoire /var/http/public/toast/stuff, tandis que la complétion après `http://toast/~yousir/' recherchera les fichiers dans le répertoire ~yousir/public_html.

mail-directory
Si défini, zsh supposera que les fichiers de boîte aux lettres peuvent être trouvés dans le répertoire spécifié. Il est par défaut défini sur `~/Mail'.
match-original
Ceci est utilisé par le compléteur _match. S'il est défini sur only, _match essaiera de générer des correspondances sans insérer de `*' à la position du curseur. S'il est défini sur toute autre valeur non vide, il essaiera d'abord de générer des correspondances sans insérer le `*' et si cela ne donne aucune correspondance, il essaiera à nouveau avec le `*' inséré. S'il est non défini ou défini sur la chaîne vide, la correspondance ne sera effectuée qu'avec le `*' inséré.
matcher
Ce style est testé séparément pour chaque balise valide dans le contexte actuel. Sa valeur est placée avant toute spécification de correspondance donnée par le style matcher-list et peut donc les remplacer via l'utilisation d'une spécification x:. La valeur doit être sous la forme décrite dans la section `Contrôle de la correspondance de complétion' de zshcompwid(1). Pour des exemples, voir la description du style tag-order.

Pour des notes comparant l'utilisation de ce style et du style matcher-list, voir sous la description du style tag-order.

matcher-list
Ce style peut être défini sur une liste de spécifications de correspondance qui doivent être appliquées partout. Les spécifications de correspondance sont décrites dans la section `Contrôle de la correspondance de complétion' de zshcompwid(1). Le système de complétion les essaiera une par une pour chaque completer sélectionné. Par exemple, pour essayer d'abord la complétion simple et, si elle ne génère aucune correspondance, la complétion insensible à la casse :
zstyle ':completion:*' matcher-list '' 'm:{a-zA-Z}={A-Za-z}'

Par défaut, chaque spécification remplace la précédente ; cependant, si une spécification est précédée de +, elle est ajoutée à la liste existante. Il est donc possible de créer des spécifications de plus en plus générales sans répétition :

zstyle ':completion:*' matcher-list \ 
       '' '+m:{a-z}={A-Z}' '+m:{A-Z}={a-z}'

Il est possible de créer des spécifications de correspondance valides pour des completers particuliers en utilisant le troisième champ du contexte. Cela ne s'applique qu'aux completers qui remplacent la liste globale des correspondances, ce qui, à l'heure actuelle, n'inclut que _prefix et _ignored. Par exemple, pour utiliser les completers _complete et _prefix mais autoriser la complétion insensible à la casse uniquement avec _complete :

zstyle ':completion:*' completer _complete _prefix
zstyle ':completion:*:complete:*:*:*' matcher-list \ 
       '' 'm:{a-zA-Z}={A-Za-z}'

Les noms définis par l'utilisateur, comme expliqué pour le style completer, sont disponibles. Cela permet d'essayer le même completer plusieurs fois avec des spécifications de correspondance différentes à chaque fois. Par exemple, pour essayer la complétion normale sans spécification de correspondance, puis la complétion normale avec une correspondance insensible à la casse, puis la correction, et enfin la complétion de mots partiels :

zstyle ':completion:*' completer \ 
    _complete _correct _complete:foo
zstyle ':completion:*:complete:*:*:*' matcher-list \ 
    '' 'm:{a-zA-Z}={A-Za-z}'
zstyle ':completion:*:foo:*:*:*' matcher-list \ 
    'm:{a-zA-Z}={A-Za-z} r:[-_./]=* r:|=*'

Si le style n'est pas défini dans un contexte donné, aucune spécification de correspondance n'est appliquée. Notez également que certains completers tels que _correct et _approximate n'utilisent pas du tout les spécifications de correspondance, bien que ces completers ne soient appelés qu'une seule fois, même si matcher-list contient plus d'un élément.

Lorsque plusieurs spécifications sont utiles, notez que la complétion *entière* est effectuée pour chaque élément de matcher-list, ce qui peut rapidement réduire les performances du shell. En règle générale, une à trois chaînes donneront des performances acceptables. D'autre part, placer plusieurs valeurs séparées par des espaces dans la même chaîne n'a pas d'impact appréciable sur les performances.

S'il n'y a pas de matcher actuel ou s'il est vide, et que l'option NO_CASE_GLOB est active, la correspondance des fichiers est effectuée de toute façon de manière insensible à la casse. Cependant, tout matcher doit spécifier explicitement la correspondance insensible à la casse si elle est requise.

Pour des notes comparant l'utilisation de ce style et du style matcher, voir sous la description du style tag-order.

max-errors
Ceci est utilisé par les fonctions de complétion _approximate et _correct pour déterminer le nombre maximum d'erreurs à autoriser. Le completer essaiera de générer des complétions en autorisant d'abord une erreur, puis deux erreurs, et ainsi de suite, jusqu'à ce qu'une ou plusieurs correspondances soient trouvées ou que le nombre maximum d'erreurs spécifié par ce style soit atteint.

Si la valeur de ce style contient la chaîne `numeric', la fonction de complétion prendra tout argument numérique comme nombre maximum d'erreurs autorisées. Par exemple, avec

zstyle ':completion:*:approximate:::' max-errors 2 numeric

deux erreurs sont autorisées si aucun argument numérique n'est donné, mais avec un argument numérique de six (comme dans `ESC-6 TAB'), jusqu'à six erreurs sont acceptées. Par conséquent, avec une valeur de `0 numeric', aucune complétion corrective ne sera tentée à moins qu'un argument numérique ne soit donné.

Si la valeur contient la chaîne `not-numeric', le completer n'essaiera *pas* de générer de complétions corrigées lorsqu'il reçoit un argument numérique, donc dans ce cas, le nombre donné doit être supérieur à zéro. Par exemple, `2 not-numeric' spécifie que la complétion corrective avec deux erreurs sera généralement effectuée, mais si un argument numérique est donné, la complétion corrective ne sera pas effectuée.

La valeur par défaut pour ce style est `2 numeric'.

max-matches-width
Ce style est utilisé pour déterminer le compromis entre la largeur de l'affichage réservée aux correspondances et la largeur réservée à leurs descriptions lorsque le style verbose est activé. La valeur donne le nombre de colonnes d'affichage à réserver pour les correspondances. La valeur par défaut est la moitié de la largeur de l'écran.

Cela a le plus d'impact lorsque plusieurs correspondances ont la même description et seront donc regroupées. Augmenter le style permettra de regrouper plus de correspondances ; le diminuer permettra de rendre plus de descriptions visibles.

menu
Si c'est `true' dans le contexte de l'une des balises définies pour le menu de complétion actuel, la complétion par menu sera utilisée. La valeur pour une balise spécifique prévaut sur celle de la balise `default'.

Si aucune des valeurs trouvées de cette manière n'est `true' mais qu'au moins une est définie sur `auto', le shell se comporte comme si l'option AUTO_MENU était définie.

Si l'une des valeurs est explicitement définie sur `false', la complétion par menu sera explicitement désactivée, remplaçant l'option MENU_COMPLETE et d'autres paramètres.

Sous la forme `yes=num', où `yes' peut être l'une des valeurs `true' (`yes', `true', `on' et `1'), la complétion par menu sera activée s'il y a au moins num correspondances. Sous la forme `yes=long', la complétion par menu sera activée si la liste ne tient pas sur l'écran. Cela n'active pas la complétion par menu si le widget ne liste normalement que les complétions, mais la complétion par menu peut être activée dans ce cas avec la valeur `yes=long-list' (Typiquement, la valeur `select=long-list' décrite plus loin est plus utile car elle permet de contrôler le défilement.)

De même, avec l'une des valeurs `false' (comme dans `no=10'), la complétion par menu ne sera *pas* utilisée s'il y a num correspondances ou plus.

La valeur de ce widget contrôle également la sélection par menu, telle qu'implémentée par le module zsh/complist. Les valeurs suivantes peuvent apparaître soit aux côtés, soit à la place des valeurs ci-dessus.

Si la valeur contient la chaîne `select', la sélection par menu sera démarrée sans condition.

Sous la forme `select=num', la sélection par menu ne sera démarrée que s'il y a au moins num correspondances. Si les valeurs de plusieurs balises fournissent un nombre, le plus petit nombre est retenu.

La sélection par menu peut être explicitement désactivée en définissant une valeur contenant la chaîne `no-select'.

Il est également possible de démarrer la sélection par menu uniquement si la liste des correspondances ne tient pas sur l'écran en utilisant la valeur `select=long'. Pour démarrer la sélection par menu même si le widget actuel ne fait que lister, utilisez la valeur `select=long-list'.

Pour activer la complétion par menu ou la sélection par menu lorsqu'il y a un certain nombre de correspondances *ou* que la liste des correspondances ne tient pas sur l'écran, les deux `yes=' et `select=' peuvent être donnés deux fois, une fois avec un nombre et une fois avec `long' ou `long-list'.

Enfin, il est possible d'activer deux modes spéciaux de sélection par menu. Le mot `interactive' dans la valeur provoque l'entrée en mode interactif immédiatement lorsque la sélection par menu est démarrée ; voir la description du module zsh/complist dans zshmodules(1) pour une description du mode interactif. Inclure la chaîne `search' fait de même pour le mode de recherche incrémentielle. Pour sélectionner la recherche incrémentielle arrière, inclure la chaîne `search-backward'.

muttrc
Si défini, indique l'emplacement du fichier de configuration mutt. Par défaut, c'est `~/.muttrc'.
numbers
Ceci est utilisé avec la balise jobs. S'il est `true', le shell complètera les numéros de job au lieu du préfixe non ambigu le plus court du texte de commande du job. Si la valeur est un nombre, les numéros de job ne seront utilisés que si ce nombre de mots des descriptions de job est nécessaire pour résoudre les ambiguïtés. Par exemple, si la valeur est `1', les chaînes ne seront utilisées que si tous les jobs diffèrent par le premier mot de leurs lignes de commande.
old-list
Ceci est utilisé par le completer _oldlist. S'il est défini sur `always', alors les widgets standards qui effectuent un listage conserveront la liste actuelle des correspondances, quelle qu'en soit la génération ; cela peut être explicitement désactivé avec la valeur `never', donnant le comportement sans le completer _oldlist. Si le style n'est pas défini, ou toute autre valeur, alors la liste existante des complétions est affichée si elle n'est pas déjà là ; sinon, la liste de complétion standard est générée ; c'est le comportement par défaut de _oldlist. Cependant, s'il y a une ancienne liste et que ce style contient le nom de la fonction de complétion qui a généré la liste, alors l'ancienne liste sera utilisée même si elle a été générée par un widget qui ne fait pas de listage.

Par exemple, supposez que vous tapez ^Xc pour utiliser le widget _correct_word, qui génère une liste de corrections pour le mot sous le

cursor. Habituellement, taper ^D génère une liste standard de complétions pour le mot sur la ligne de commande, et l'affiche. Avec _oldlist, il affiche au lieu de cela la liste des corrections déjà générées.

Prenons un autre exemple avec le completer _match : avec le style insert-unambiguous réglé sur `true', il insère uniquement un préfixe commun, s'il y en a un. Cependant, cela peut supprimer des parties du motif original, de sorte que des complétions supplémentaires pourraient produire plus de correspondances que lors de la première tentative. En utilisant le completer _oldlist et en réglant ce style sur _match, la liste des correspondances générée lors de la première tentative sera utilisée à nouveau.

old-matches
Ceci est utilisé par le completer _all_matches pour décider si une ancienne liste de correspondances doit être utilisée si elle existe. Ceci est sélectionné par l'une des valeurs `true' ou par la chaîne `only'. Si la valeur est `only', _all_matches utilisera uniquement une ancienne liste et n'aura aucun effet sur la liste des correspondances actuellement générée.

Si ce style est défini, il est généralement déconseillé d'appeler le completer _all_matches de manière inconditionnelle. Une utilisation possible est de définir soit ce style, soit le style completer avec l'option -e de zstyle pour rendre le style conditionnel.

old-menu
Ceci est utilisé par le completer _oldlist. Il contrôle le comportement de la complétion de menu lorsqu'une complétion a déjà été insérée et que l'utilisateur tape une touche de complétion standard telle que TAB. Le comportement par défaut de _oldlist est que la complétion de menu continue toujours avec la liste de complétions existante. Si ce style est réglé sur `false', cependant, une nouvelle complétion est démarrée si l'ancienne liste a été générée par une commande de complétion différente ; c'est le comportement sans le completer _oldlist.

Par exemple, supposez que vous tapez ^Xc pour générer une liste de corrections, et que la complétion de menu est démarrée de l'une des manières habituelles. Habituellement, ou avec ce style réglé sur `false', taper TAB à ce stade essayerait de compléter la ligne telle qu'elle apparaît maintenant. Avec _oldlist, cela continue au lieu de cela à parcourir la liste des corrections.

original
Ceci est utilisé par les completers _approximate et _correct pour décider si la chaîne originale doit être ajoutée comme complétion possible. Normalement, cela n'est fait que s'il y a au moins deux corrections possibles, mais si ce style est réglé sur `true', il est toujours ajouté. Notez que le style sera examiné avec le champ completer dans le nom du contexte réglé sur correct-num ou approximate-num, où num est le nombre d'erreurs qui ont été acceptées.
packageset
Ce style est utilisé lors de la complétion des arguments du programme Debian `dpkg'. Il contient un remplacement pour l'ensemble de paquets par défaut pour un contexte donné. Par exemple,
zstyle ':completion:*:complete:dpkg:option--status-1:*' \ 
               packageset avail

ce qui permet de compléter les paquets disponibles, plutôt que seulement les paquets installés, pour `dpkg --status'.

path
La fonction qui complète les noms de couleurs utilise ce style avec la balise colors. La valeur doit être le chemin d'accès d'un fichier contenant des noms de couleurs au format d'un fichier X11 rgb.txt. Si le style n'est pas défini mais que ce fichier est trouvé dans l'un des divers emplacements standards, il sera utilisé par défaut.
path-completion
Ceci est utilisé pour la complétion de noms de fichiers. Par défaut, la complétion de noms de fichiers examine tous les composants d'un chemin pour voir s'il existe des complétions de ce composant. Par exemple, /u/b/z peut être complété en /usr/bin/zsh. Définir explicitement ce style sur `false' inhibe ce comportement pour les composants de chemin jusqu'au / avant le curseur ; cela surcharge le réglage de accept-exact-dirs.

Même avec le style réglé sur `false', il est toujours possible de compléter plusieurs chemins en réglant l'option COMPLETE_IN_WORD et en déplaçant le curseur vers le premier composant du chemin à compléter. Par exemple, /u/b/z peut être complété en /usr/bin/zsh si le curseur est après le /u.

pine-directory
S'il est défini, spécifie le répertoire contenant les fichiers de boîtes aux lettres PINE. Il n'y a pas de valeur par défaut, car la recherche récursive de ce répertoire est peu pratique pour ceux qui n'utilisent pas PINE.
ports
Une liste de noms de services Internet (ports réseau) à compléter. Si ce n'est pas défini, les noms de services sont pris du fichier `/etc/services'.
prefix-hidden
Ceci est utilisé pour certaines complétions qui partagent un préfixe commun, par exemple les options de commande commençant par des tirets. S'il est à `true', le préfixe ne sera pas affiché dans la liste des correspondances.

La valeur par défaut pour ce style est `false'.

prefix-needed
Ce style est également pertinent pour les correspondances avec un préfixe commun. S'il est réglé sur `true', ce préfixe commun doit être tapé par l'utilisateur pour générer les correspondances.

Le style est applicable aux balises de complétion options, signals, jobs, functions et parameters.

Pour les options de commande, cela signifie que le `-', `+' ou `--' initial doit être tapé explicitement avant que les noms d'options ne soient complétés.

Pour les signaux, un `-' initial est requis avant que les noms de signaux ne soient complétés.

Pour les jobs, un `%' initial est requis avant que les noms de jobs ne soient complétés.

Pour les noms de fonctions et de paramètres, un `_' ou `.' initial est requis avant que les noms de fonctions ou de paramètres commençant par ces caractères ne soient complétés.

La valeur par défaut pour ce style est `false' pour les complétions de function et parameter, et `true' sinon.

preserve-prefix
Ce style est utilisé lors de la complétion des noms de chemin. Sa valeur doit être un motif correspondant à un préfixe initial du mot à compléter qui doit être laissé inchangé en toutes circonstances. Par exemple, sur certains Unix, un `//' initial (double slash) a une signification spéciale ; régler ce style sur la chaîne `//' le préservera. Autre exemple, régler ce style sur `?:/' sous Cygwin permettrait la complétion après `a:/...' et ainsi de suite.
range
Ceci est utilisé par le completer _history et la commande bindable _history_complete_word pour décider quels mots doivent être complétés.

S'il s'agit d'un seul nombre, seuls les N derniers mots de l'historique seront complétés.

S'il s'agit d'une plage de la forme `max:slice', les slice derniers mots seront complétés ; ensuite, si cela ne donne aucune correspondance, les slice mots précédents seront essayés et ainsi de suite. Ce processus s'arrête soit lorsqu'au moins une correspondance a été trouvée, soit lorsque max mots ont été essayés.

Par défaut, tous les mots de l'historique sont complétés en même temps.

recursive-files
Si ce style est défini, sa valeur est un tableau de motifs à tester contre `$PWD/' : notez le slash final, qui permet de délimiter sans ambiguïté les répertoires dans le motif en incluant des slashs des deux côtés. Si une complétion de fichier ordinaire échoue et que le mot sur la ligne de commande n'a pas encore de partie répertoire dans son nom, le style est récupéré en utilisant la même balise que pour la complétion tentée, puis les éléments sont testés tour à tour contre $PWD/. Si l'un d'eux correspond, le shell retente la complétion en préfixant le mot sur la ligne de commande avec chaque répertoire de l'expansion de **/*(/) à tour de rôle. Typiquement, les éléments du style seront définis pour restreindre le nombre de répertoires sous le répertoire courant à un nombre gérable, par exemple `*/.git/*'.

Par exemple,

zstyle ':completion:*' recursive-files '*/zsh/*'

Si le répertoire courant est /home/pws/zsh/Src, alors zle_tr<TAB> peut être complété en Zle/zle_tricky.c.

regular
Ce style est utilisé par le completer et la commande bindable _expand_alias. S'il est réglé sur `true' (par défaut), les alias réguliers seront développés mais uniquement en position de commande. S'il est réglé sur `false', les alias réguliers ne seront jamais développés. S'il est réglé sur `always', les alias réguliers seront développés même s'ils ne sont pas en position de commande.
rehash
Si ceci est défini lors de la complétion de commandes externes, la liste interne (hash) des commandes sera mise à jour pour chaque recherche en émettant la commande rehash. Il y a une pénalité de vitesse pour cela qui ne sera probablement perceptible que lorsque les répertoires dans le chemin d'accès ont un accès fichier lent.
remote-access
S'il est réglé sur `false', certaines commandes seront empêchées d'établir des connexions Internet pour récupérer des informations distantes. Cela inclut la complétion pour la commande CVS.

Il n'est pas toujours possible de savoir si les connexions sont effectivement vers un site distant, certaines peuvent donc être empêchées inutilement.

Dans de nombreux cas où un widget appelant sélectionne explicitement un ordre particulier au lieu de l'ordre par défaut, une valeur de `**true**' n'est pas honorée. Un exemple où ce n'est pas le cas est pour l'historique des commandes où l'ordre par défaut de tri des correspondances chronologiquement peut être remplacé en définissant le style sur `true'. Dans le completer **_expand**, s'il est défini sur `true', les expansions générées seront toujours triées. S'il est défini sur `**menu**', alors les expansions ne sont triées que lorsqu'elles sont proposées comme chaînes uniques, mais pas dans la chaîne contenant toutes les expansions possibles. * **special-dirs** : Normalement, le code de complétion ne produira pas les noms de répertoires `**.**' et `**..**' comme complétions possibles. L'exemple suivant définit **special-dirs** sur `**..**' lorsque le préfixe actuel est vide, est un seul `**.**', ou ne consiste qu'en un chemin commençant par `**../\**'. Sinon, la valeur est `false'. * **squeeze-slashes** : S'il est défini sur `true', les séquences de barres obliques dans les chemins de fichiers (par exemple dans `**foo//bar**') seront traitées comme une seule barre oblique. C'est le comportement habituel des chemins UNIX. Cependant, par défaut, la fonction de complétion de fichiers se comporte comme s'il y avait un `****' entre les barres obliques. * **stop** : S'il est défini sur `true', la commande bindable **_history_complete_word** s'arrêtera une fois arrivée au début ou à la fin de l'historique. La valeur par défaut de ce style est `false'. * **substitute** : Ce style booléen contrôle si le completer **_expand** essaiera d'abord d'étendre toutes les substitutions dans la chaîne (telles que `**$(***...***)****' et `**${***...***}\***'). La valeur par défaut est `true'. * **suffix** : Ceci est utilisé par le completer **_expand** si le mot commence par un tilde ou contient une expansion de paramètre. S'il est défini sur `true', le mot ne sera étendu que s'il n'a pas de suffixe, c'est-à-dire s'il s'agit de quelque chose comme `**~foo**' ou `**$foo**' plutôt que `**~foo/**' ou `**$foo/bar**', à moins que ce suffixe ne contienne lui-même des caractères éligibles à l'expansion. La valeur par défaut de ce style est `true'. * **tag-order** : Ceci fournit un mécanisme pour trier la manière dont les étiquettes disponibles dans un contexte particulier seront utilisées. Les valeurs pour le style sont des ensembles de listes d'étiquettes séparées par des espaces. Les étiquettes de chaque valeur seront essayées en même temps ; si aucune correspondance n'est trouvée, la valeur suivante est utilisée. (Voir le style **file-patterns** pour une exception à ce comportement.) Par exemple : définit que la complétion en position de commande propose d'abord des commandes externes et des fonctions shell. Les autres étiquettes seront essayées si aucune complétion n'est trouvée. En plus des noms d'étiquettes, chaque chaîne de la valeur peut prendre l'une des formes suivantes : * **-** : Si une valeur se compose uniquement d'un tiret, alors *seulement* les étiquettes spécifiées dans les autres valeurs sont générées. Normalement, toutes les étiquettes non explicitement sélectionnées sont essayées en dernier si les étiquettes spécifiées ne génèrent aucune correspondance. Cela signifie qu'une seule valeur composée uniquement d'un seul tiret désactive la complétion. * **!** *tags*... : Une chaîne commençant par un point d'exclamation spécifie les noms d'étiquettes qui *ne doivent pas* être utilisés. L'effet est le même que si toutes les autres étiquettes possibles pour le contexte avaient été listées. * ***tag***:***label*** ... : Ici, *tag* est l'une des étiquettes standard et *label* est un nom arbitraire. Les correspondances sont générées normalement, mais le nom *label* est utilisé dans les contextes à la place de *tag*. Ce n'est pas utile pour les mots commençant par **!**. Si le *label* commence par un tiret, le *tag* est préfixé au *label* pour former le nom utilisé pour la recherche. Cela peut être utilisé pour faire en sorte que le système de complétion essaie une certaine étiquette plus d'une fois, en fournissant des paramètres de style différents pour chaque tentative ; voir ci-dessous pour un exemple. * ***tag***:***label***:***description*** : Comme précédemment, mais **description** remplacera le `****%d****' dans la valeur du style **format** à la place de la description par défaut fournie par la fonction de complétion. Les espaces dans la description doivent être mis entre guillemets avec une barre oblique inverse. Un `****%d****' apparaissant dans *description* est remplacé par la description fournie par la fonction de complétion. Dans l'une des formes ci-dessus, le tag peut être un motif ou plusieurs motifs sous la forme `**{***pat1***,***pat2***...}****'. Dans ce cas, tous les tags correspondants seront utilisés, sauf ceux donnés explicitement dans la même chaîne. Une utilisation de ces fonctionnalités est d'essayer un tag plus d'une fois, en définissant d'autres styles différemment à chaque tentative, mais toujours en utilisant tous les autres tags sans avoir à les répéter. Par exemple, pour ignorer les fonctions de complétion commençant par un underscore lors de la première tentative de complétion des noms de fonctions en position de commande : Lors de la première tentative, toutes les étiquettes seront proposées, mais l'étiquette **functions** sera remplacée par **functions-non-comp**. Le style **ignored-patterns** est défini pour cette étiquette afin d'exclure les fonctions commençant par un underscore. S'il n'y a pas de correspondances, la deuxième valeur du style **tag-order** est utilisée, qui complète les fonctions en utilisant the balise par défaut, censée inclure cette fois tous les noms de fonctions.

Les correspondances pour une balise peuvent être réparties en différents groupes. Par exemple :

zstyle ':completion:*' tag-order \ 
    'options:-long:long\ options
     options:-short:short\ options
     options:-single-letter:single\ letter\ options'
zstyle ':completion:*:options-long' \ 
     ignored-patterns '[-+](|-|[^-]*)'
zstyle ':completion:*:options-short' \ 
     ignored-patterns '--*' '[-+]?'
zstyle ':completion:*:options-single-letter' \ 
     ignored-patterns '???*'

Avec le style group-names défini, les options commençant par `--', les options commençant par un seul `-' ou `+' mais contenant plusieurs caractères, et les options à une seule lettre seront affichées dans des groupes séparés avec des descriptions différentes.

Une autre utilisation des motifs est d'essayer plusieurs spécifications de correspondance les unes après les autres. Le style matcher-list offre quelque chose de similaire, mais il est testé très tôt dans le système de complétion et ne peut donc pas être défini pour des commandes uniques ni pour des contextes plus spécifiques. Voici comment essayer la complétion normale sans aucune spécification de correspondance et, si cela ne génère aucune correspondance, réessayer avec une correspondance insensible à la casse, en limitant l'effet aux arguments de la commande foo :

zstyle ':completion:*:*:foo:*:*' tag-order '*' '*:-case'
zstyle ':completion:*-case' matcher 'm:{a-z}={A-Z}'

D'abord, toutes les balises proposées lors de la complétion après foo sont essayées en utilisant le nom de balise normal. Si cela ne génère aucune correspondance, la deuxième valeur de tag-order est utilisée, qui essaie à nouveau toutes les balises, sauf que cette fois, -case est ajouté à leur nom pour la recherche des styles. Par conséquent, cette fois, la valeur pour le style matcher du deuxième appel à zstyle dans l'exemple est utilisée pour rendre la complétion insensible à la casse.

Il est possible d'utiliser l'option -e de la commande intégrée zstyle pour spécifier des conditions pour l'utilisation de balises particulières. Par exemple :

zstyle -e '*:-command-:*' tag-order '
    if [[ -n $PREFIX$SUFFIX ]]; then
      reply=( )
    else
      reply=( - )
    fi'

La complétion en position de commande sera tentée uniquement si la chaîne tapée jusqu'à présent n'est pas vide. Ceci est testé à l'aide du paramètre spécial PREFIX ; voir zshcompwid pour une description des paramètres spéciaux dans les widgets de complétion. Définir reply sur un tableau vide fournit le comportement par défaut consistant à essayer toutes les balises à la fois ; le définir sur un tableau ne contenant qu'un trait d'union désactive l'utilisation de toutes les balises et donc de toutes les complétions.

Si aucun style tag-order n'a été défini pour un contexte, les chaînes `(|*-)argument-* (|*-)option-* values' et `options' plus toutes les balises offertes par la fonction de complétion seront utilisées pour fournir un comportement par défaut raisonnable qui fait que les arguments (qu'ils soient des arguments de commande normaux ou des arguments d'options) sont complétés avant les noms d'options pour la plupart des commandes.

urls
Ceci est utilisé conjointement avec la balise urls par les fonctions qui complètent les URL.

Si la valeur se compose de plus d'une chaîne, ou si la seule chaîne ne nomme pas un fichier ou un répertoire, les chaînes sont utilisées comme les URL à compléter.

Si la valeur ne contient qu'une seule chaîne qui est le nom d'un fichier normal, les URL sont extraites de ce fichier (où les URL peuvent être séparées par des espaces ou des sauts de ligne).

Enfin, si la seule chaîne de la valeur nomme un répertoire, la hiérarchie de répertoires dont la racine est ce répertoire donne les complétions. Le répertoire de niveau supérieur devrait être la méthode d'accès aux fichiers, telle que `http', `ftp', `bookmark' et ainsi de suite. Dans de nombreux cas, le niveau suivant de répertoires sera un nom de fichier. La hiérarchie de répertoires peut descendre aussi profondément que nécessaire.

Par exemple,

zstyle ':completion:*' urls ~/.urls
mkdir -p ~/.urls/ftp/ftp.zsh.org/pub

permet la complétion de tous les composants de l'URL ftp://ftp.zsh.org/pub après des commandes appropriées telles que `netscape' ou `lynx'. Notez cependant que les méthodes d'accès et les fichiers sont complétés séparément, donc si le style hosts est défini, les hôtes peuvent être complétés sans référence au style urls.

Consultez la description dans la fonction _urls elle-même pour plus d'informations (par exemple, `more $^fpath/_urls(N)').

use-cache
Si ceci est défini, la couche de mise en cache des complétions est activée pour toutes les complétions qui l'utilisent (via les fonctions _store_cache, _retrieve_cache et _cache_invalid). Le répertoire contenant les fichiers de cache peut être modifié avec le style cache-path.
use-compctl
Si ce style est défini sur une chaîne différente de false, 0, no, et off, le système de complétion peut utiliser toutes les spécifications de complétion définies avec la commande intégrée compctl. Si le style n'est pas défini, cela n'est fait que si le module zsh/compctl est chargé. La chaîne peut également contenir la sous-chaîne `first' pour utiliser les complétions définies avec `compctl -T', et la sous-chaîne `default' pour utiliser la complétion définie avec `compctl -D'.

Notez que ceci est uniquement destiné à faciliter la transition de compctl vers le nouveau système de complétion et pourrait disparaître à l'avenir.

Notez également que les définitions de compctl ne seront utilisées que s'il n'y a pas de fonction de complétion spécifique pour la commande en question. Par exemple, s'il existe une fonction _foo pour compléter les arguments de la commande foo, compctl ne sera jamais appelé pour foo. Cependant, la version compctl sera essayée si foo n'utilise que la complétion par défaut.

use-ip
Par défaut, la fonction _hosts qui complète les noms d'hôtes supprime les adresses IP des entrées lues à partir des bases de données d'hôtes telles que NIS et les fichiers ssh. Si ce style est défini sur `true', les adresses IP correspondantes peuvent également être complétées. Ce style n'est pas utilisé dans un contexte où le style hosts est défini ; notez également qu'il doit être défini avant que le cache des noms d'hôtes ne soit généré (typiquement la première tentative de complétion).
users
Ceci peut être défini sur une liste de noms d'utilisateurs à compléter. S'il n'est pas défini, tous les noms d'utilisateurs seront complétés. Notez que s'il est défini, seule cette liste d'utilisateurs sera complétée ; c'est parce que sur certains systèmes, interroger tous les utilisateurs peut prendre un temps prohibitif.
users-hosts
Les valeurs de ce style doivent être de la forme `utilisateur@hôte' ou `utilisateur:hôte'. Il est utilisé pour les commandes qui nécessitent des paires de noms d'utilisateur et d'hôtes. Ces commandes complèteront les noms d'utilisateurs à partir de ce style (uniquement), et restreindront la complétion ultérieure des noms d'hôtes aux hôtes associés à cet utilisateur dans l'une des valeurs du style.

Il est possible de regrouper les valeurs pour des ensembles de commandes qui permettent une connexion à distance, telles que rlogin et ssh, en utilisant la balise my-accounts. De même, les valeurs pour des ensembles de commandes qui se réfèrent généralement aux comptes d'autres personnes, telles que talk et finger, peuvent être regroupées en utilisant la balise other-accounts. Les commandes plus ambivalentes peuvent utiliser la balise accounts.

users-hosts-ports
Similaire à users-hosts mais utilisé pour des commandes telles que telnet et contenant des chaînes de la forme `utilisateur@hôte:port'.
verbose
Si défini, comme c'est le cas par défaut, la liste de complétion est plus verbeuse. En particulier, de nombreuses commandes affichent des descriptions pour les options si ce style est défini sur `true'.
word
Ceci est utilisé par le compléteur _list, qui empêche l'insertion de complétions jusqu'à une deuxième tentative de complétion lorsque la ligne n'a pas changé. La manière normale de savoir si la ligne a changé est de comparer son contenu entier entre les deux occasions. Si ce style est défini sur `true', la comparaison est effectuée uniquement sur le mot courant. Par conséquent, si la complétion est effectuée sur un autre mot ayant le même contenu, la complétion ne sera pas retardée.

FONCTIONS DE CONTRÔLE

Le script d'initialisation compinit redéfinit tous les widgets qui effectuent la complétion pour appeler la fonction de widget fournie _main_complete. Cette fonction agit comme un wrapper appelant les fonctions dites 'completers' qui génèrent des correspondances. Si _main_complete est appelé avec des arguments, ceux-ci sont considérés comme les noms des fonctions completers à appeler dans l'ordre donné. Si aucun argument n'est donné, l'ensemble des fonctions à essayer est pris à partir du style completer. Par exemple, pour utiliser la complétion et la correction normales si cela ne génère aucune correspondance :

zstyle ':completion:*' completer _complete _correct

après avoir appelé compinit. La valeur par défaut pour ce style est `_complete _ignored', c'est-à-dire qu'en général seule la complétion ordinaire est essayée, d'abord avec l'effet du style ignored-patterns et ensuite sans. La fonction _main_complete utilise le statut de retour des fonctions completers pour décider si d'autres completers doivent être appelés. Si le statut de retour est zéro, aucun autre completer n'est essayé et la fonction _main_complete retourne.

Si le premier argument de _main_complete est un trait d'union unique, les arguments ne seront pas pris comme noms de completers. Au lieu de cela, le deuxième argument donne un nom à utiliser dans le champ completer du contexte et les autres arguments donnent une commande et ses arguments à appeler pour générer les correspondances.

Les fonctions completers suivantes sont contenues dans la distribution, bien que les utilisateurs puissent écrire les leurs. Notez que dans les contextes, l'underscore initial est supprimé, par exemple la complétion de base est effectuée dans le contexte `:completion::complete:...'.

_all_matches
Ce completer peut être utilisé pour ajouter une chaîne constituée de toutes les autres correspondances. Comme il influence les completers suivants, il doit apparaître comme le premier completer de la liste. La liste de toutes les correspondances est affectée par le style avoid-compl
de `old-matches` décrits plus haut.

Il peut être utile d'utiliser la fonction _generic décrite plus bas pour lier _all_matches à sa propre combinaison de touches, par exemple :

zle -C all-matches complete-word _generic
bindkey '^Xa' all-matches
zstyle ':completion:all-matches:*' old-matches only
zstyle ':completion:all-matches::::' completer _all_matches

Notez que cela ne génère pas de complétions par soi-même : utilisez d'abord l'une des méthodes standard pour générer une liste de complétions, puis utilisez ^Xa pour afficher toutes les correspondances. Il est possible à la place d'ajouter un compléteur standard à la liste et de demander que la liste de toutes les correspondances soit directement insérée :

zstyle ':completion:all-matches::::' completer \ 
       _all_matches _complete
zstyle ':completion:all-matches:*' insert true

Dans ce cas, le style old-matches ne doit pas être défini.

_approximate
Ceci est similaire au compléteur de base _complete mais permet aux complétions de subir des corrections. Le nombre maximum d'erreurs peut être spécifié par le style max-errors ; voir la description de la correspondance approximative dans zshexpn(1) pour savoir comment les erreurs sont comptées. Normalement, ce compléteur ne sera essayé qu'après le compléteur normal _complete :
zstyle ':completion:*' completer _complete _approximate

Ceci donnera une complétion corrective si et seulement si la complétion normale ne produit aucune complétion possible. Lorsque des complétions corrigées sont trouvées, le compléteur commencera normalement la complétion par menu, vous permettant de parcourir ces chaînes.

Ce compléteur utilise les étiquettes corrections et original lors de la génération des corrections possibles et de la chaîne originale. Le style format pour la première peut contenir les séquences supplémentaires `%e' et `%o' qui seront remplacées par le nombre d'erreurs acceptées pour générer les corrections et la chaîne originale, respectivement.

Le compléteur augmente progressivement le nombre d'erreurs autorisées jusqu'à la limite spécifiée par le style max-errors, donc si une complétion est trouvée avec une erreur, aucune complétion avec deux erreurs ne sera affichée, et ainsi de suite. Il modifie le nom du compléteur dans le contexte pour indiquer le nombre d'erreurs en cours d'essai : lors de la première tentative, le champ completer contient `approximate-1', lors de la seconde, `approximate-2', et ainsi de suite.

Lorsque _approximate est appelé depuis une autre fonction, le nombre d'erreurs à accepter peut être passé avec l'option -a. L'argument est dans le même format que le style max-errors, le tout dans une seule chaîne.

Notez que ce compléteur (et le compléteur _correct mentionné ci-dessous) peuvent être assez coûteux à appeler, surtout lorsqu'un grand nombre d'erreurs sont autorisées. Une façon d'éviter cela est de configurer le style completer en utilisant l'option -e de zstyle afin que certains compléteurs ne soient utilisés que lorsque la complétion est tentée une seconde fois sur la même chaîne, par exemple :

zstyle -e ':completion:*' completer '
  if [[ $_last_try != "$HISTNO$BUFFER$CURSOR" ]]; then
    _last_try="$HISTNO$BUFFER$CURSOR"
    reply=(_complete _match _prefix)
  else
    reply=(_ignored _correct _approximate)
  fi'

Ceci utilise le paramètre HISTNO et les paramètres spéciaux BUFFER et CURSOR disponibles dans les widgets zle et de complétion pour déterminer si la ligne de commande n'a pas changé depuis la dernière tentative de complétion. Ce n'est qu'alors que les compléteurs _ignored, _correct et _approximate sont appelés.

_canonical_paths [ -A var ] [ -N ] [ -MJV12nfX ] tag descr [ paths ... ]
Cette fonction de complétion complète tous les chemins qui lui sont donnés, et essaie également d'offrir des complétions qui pointent vers le même fichier que l'un des chemins donnés (chemin relatif lorsqu'un chemin absolu est donné, et vice versa ; lorsque .. est présent dans le mot à compléter ; et certains chemins obtenus à partir de liens symboliques).

-A, si spécifié, prend les chemins depuis la variable tableau spécifiée. Les chemins peuvent également être spécifiés en ligne de commande comme indiqué ci-dessus. -N, si spécifié, empêche la canonisation des chemins donnés avant de les utiliser pour la complétion, au cas où ils le seraient déjà. Les options -M, -J, -V, -1, -2, -n, -F, -X sont passées à compadd.

Voir _description pour une description de tag et descr.

_cmdambivalent
Complète les arguments positionnels restants comme une commande externe. La commande externe et ses arguments sont complétés comme des arguments séparés (d'une manière appropriée pour la complétion de /usr/bin/env) s'il y a deux arguments positionnels restants ou plus sur la ligne de commande, et comme une chaîne de commande mise entre guillemets (de la manière de system(...)) sinon. Voir également _cmdstring et _precommand.

Cette fonction ne prend aucun argument.

_cmdstring
Complète une commande externe comme un seul argument, comme pour system(...).
_complete
Ce compléteur génère toutes les complétions possibles de manière sensible au contexte, c'est-à-dire en utilisant les paramètres définis avec la fonction compdef expliquée ci-dessus et les paramètres actuels de tous les paramètres spéciaux. Ceci donne le comportement de complétion normal.

Pour compléter les arguments des commandes, _complete utilise la fonction utilitaire _normal, qui est responsable de trouver la fonction particulière ; elle est décrite ci-dessous. Divers contextes de la forme -contexte- sont traités spécifiquement. Ceux-ci sont tous mentionnés ci-dessus comme arguments possibles pour l'étiquette #compdef.

Avant d'essayer de trouver une fonction pour un contexte spécifique, _complete vérifie si le paramètre `compcontext' est défini. La définition de `compcontext' permet de remplacer le dispatching de complétion habituel, ce qui est utile dans des endroits comme une fonction qui utilise vared pour l'entrée. S'il est défini comme un tableau, les éléments sont considérés comme les correspondances possibles qui seront complétées en utilisant l'étiquette `values' et la description `value'. S'il est défini comme un tableau associatif, les clés sont utilisées comme complétions possibles et les valeurs (si elles ne sont pas vides) sont utilisées comme descriptions pour les correspondances. Si `compcontext' est défini comme une chaîne contenant des deux-points, elle doit être de la forme `tag:descr:action'. Dans ce cas, tag et descr donnent l'étiquette et la description à utiliser et action indique ce qui doit être complété dans l'une des formes acceptées par la fonction utilitaire _arguments décrite ci-dessous.

Enfin, si `compcontext' est défini comme une chaîne sans deux-points, la valeur est prise comme le nom du contexte à utiliser et la fonction définie pour ce contexte sera appelée. À cette fin, il existe un contexte spécial nommé -command-line- qui complète des lignes de commande entières (commandes et leurs arguments). Ceci n'est pas utilisé par le système de complétion lui-même mais est néanmoins géré lorsqu'il est explicitement appelé.

_correct
Génère des corrections, mais pas de complétions, pour le mot courant ; ceci est similaire à _approximate mais n'autorisera aucun nombre de caractères supplémentaires au curseur comme le fait ce compléteur. L'effet est similaire à la correction orthographique. Il est basé sur _approximate, mais le champ compléteur dans le nom du contexte est correct.

Par exemple, avec :

zstyle ':completion:::::' completer \ 
       _complete _correct _approximate
zstyle ':completion:*:correct:::' max-errors 2 not-numeric
zstyle ':completion:*:approximate:::' max-errors 3 numeric

la correction acceptera jusqu'à deux erreurs. Si un argument numérique est donné, la correction ne sera pas effectuée, mais la complétion corrective le sera, et acceptera autant d'erreurs que le nombre donné. Sans argument numérique, la correction d'abord puis la complétion corrective seront essayées, la première acceptant deux erreurs et la seconde trois erreurs.

Lorsque _correct est appelé comme une fonction, le nombre d'erreurs à accepter peut être donné après l'option -a. L'argument est dans la même forme que les valeurs pour le style accept, le tout dans une seule chaîne.

Cette fonction de compléteur est destinée à être utilisée sans le compléteur _approximate ou, comme dans l'exemple, juste avant lui. L'utiliser après le compléteur _approximate est inutile puisque _approximate générera au moins les chaînes corrigées générées par le compléteur _correct -- et probablement plus.

_expand
Cette fonction de compléteur n'effectue pas réellement de complétion, mais vérifie si le mot sur la ligne de commande est éligible pour une expansion et, si c'est le cas, donne un contrôle détaillé sur la manière dont cette expansion est effectuée. Pour que cela se produise, le système de complétion doit être invoqué avec complete-word, et non expand-or-complete (la liaison par défaut pour TAB), car sinon la chaîne sera développée par le mécanisme interne du shell avant le démarrage du système de complétion. Notez également que ce compléteur doit être appelé avant la fonction de compléteur _complete.

Les étiquettes utilisées lors de la génération des expansions sont all-expansions pour la chaîne contenant toutes les expansions possibles, expansions lors de l'ajout des expansions possibles comme correspondances uniques et original lors de l'ajout de la chaîne originale de la ligne. L'ordre dans lequel ces chaînes sont générées, le cas échéant, peut être contrôlé par les styles group-order et tag-order, comme d'habitude.

La chaîne de format pour all-expansions et pour expansions peut contenir la séquence `%o' qui sera remplacée par la chaîne originale de la ligne.

Le type d'expansion à essayer est contrôlé par les styles substitute, glob et subst-globs-only.

Il est également possible d'appeler _expand comme une fonction, auquel cas les différents modes peuvent être sélectionnés avec des options : -s pour substitute, -g pour glob et -o pour subst-globs-only.

_expand_alias
Si le mot sur lequel se trouve le curseur est un alias, il est développé et aucun autre compléteur n'est appelé. Les types d'alias qui doivent être développés peuvent être contrôlés avec les styles regular, global et ddisabled.

Cette fonction est également une commande bindable, voir la section `Commandes bindables' ci-dessous.

_extensions
Si le curseur suit la chaîne `*.', les extensions de nom de fichier sont complétées. Les extensions sont tirées des fichiers du répertoire courant ou d'un répertoire spécifié au début du mot courant. Pour des correspondances exactes, la complétion continue pour permettre à d'autres compléteurs tels que _expand de développer le motif. Les styles standard add-space et prefix-hidden sont observés.
_external_pwds
Complète les répertoires courants d'autres processus zsh appartenant à l'utilisateur courant.

Ceci est destiné à être utilisé via _generic, lié à une combinaison de touches personnalisée. Notez que la correspondance de motifs est activée, donc la correspondance est effectuée de manière similaire à la façon dont elle fonctionne avec le compléteur _match.

_history
Complète les mots de l'historique des commandes du shell. Ce compléteur peut être contrôlé par les styles remove-all-dups et sort comme pour la commande bindable _history_complete_word, voir la section `Commandes bindables' ci-dessous et la section `Configuration du système de complétion' ci-dessus.
_ignored
Le style ignored-patterns peut être défini sur une liste de motifs qui sont comparés aux complétions possibles ; les correspondances sont supprimées. Avec ce compléteur, ces correspondances peuvent être rétablies, comme si aucun style ignored-patterns n'était défini. Le compléteur génère en fait sa propre liste de correspondances ; les compléteurs qui sont invoqués sont déterminés de la même manière que pour le compléteur _prefix. Le style single-ignored est également disponible comme décrit ci-dessus.
_list
Ce compléteur permet que l'insertion des correspondances soit retardée jusqu'à ce que la complétion soit tentée une seconde fois sans que le mot sur la ligne ne soit modifié. Lors de la première tentative, seule la liste des correspondances sera affichée. Il est affecté par les styles condition et word, voir la section `Configuration du système de complétion' ci-dessus.
_match
Ce compléteur est destiné à être utilisé après le compléteur _complete. Il se comporte de manière similaire, mais la chaîne sur la ligne de commande peut être un motif à faire correspondre avec les complétions d'essai. Cela donne l'effet de l'option GLOB_COMPLETE.

Normalement, la complétion sera effectuée en prenant le motif de la ligne, en insérant un `*' à la position du curseur et en comparant le motif résultant avec les complétions possibles générées. Ceci peut être modifié avec le style match-original décrit ci-dessus.

Les correspondances générées seront proposées dans une complétion par menu, sauf si le style insert-unambiguous est défini sur `true' ; voir la description ci-dessus pour d'autres options pour ce style.

Notez que les spécifications des correspondances définies globalement ou utilisées par les fonctions de complétion (les styles matcher-list et matcher) ne seront pas utilisées.

_menu
Ce compléteur a été écrit comme une simple fonction exemple pour montrer comment la complétion par menu peut être activée dans le code du shell. Cependant, il a pour effet notable de désactiver la sélection par menu, ce qui peut être utile avec les widgets basés sur _generic. Il doit être utilisé comme premier compléteur dans la liste. Notez que ceci est indépendant du réglage de l'option MENU_COMPLETE et ne fonctionne pas avec les autres widgets de complétion par menu tels que reverse-menu-complete ou accept-and-menu-complete.
_oldlist
Ce compléteur contrôle le comportement des widgets de complétion standard lorsqu'il existe une liste existante de complétions qui peut avoir été générée par une complétion spéciale (c'est-à-dire une commande de complétion liée séparément). Il permet aux touches de complétion ordinaires de continuer à utiliser la liste de complétions ainsi générée, au lieu de produire une nouvelle liste de complétions contextuelles ordinaires. Il doit apparaître dans la liste des compléteurs avant l'un des widgets qui génèrent des correspondances. Il utilise deux styles : old-list et old-menu, voir la section `Configuration du système de complétion' ci-dessus.
_precommand
Complète une commande externe dans des arguments séparés par des mots, comme pour exec et /usr/bin/env.
_prefix
Ce compléteur peut être utilisé pour essayer la complétion en ignorant le suffixe (tout ce qui suit le curseur). En d'autres termes, le suffixe ne sera pas considéré comme faisant partie du mot à compléter. L'effet est similaire à la commande expand-or-complete-prefix.

Le style completer est utilisé pour décider quels autres compléteurs doivent être appelés pour générer des correspondances. Si ce style n'est pas défini, la liste des compléteurs définis pour le contexte courant est utilisée -- à l'exception, bien sûr, du compléteur _prefix lui-même. De plus, si ce compléteur apparaît plus d'une fois dans la liste des compléteurs, seuls les compléteurs qui n'ont pas déjà été essayés par la dernière invocation de _prefix seront appelés.

Par exemple, considérons ce style completer global :

zstyle ':completion:*' completer \
    _complete _prefix _correct _prefix:foo

Ici, le compléteur _prefix essaie la complétion normale mais en ignorant le suffixe. Si cela ne génère aucune correspondance, et pas plus l'appel au compléteur _correct qui suit, _prefix sera appelé une seconde fois et, maintenant, essayant seulement la correction avec le suffixe ignoré. Lors de la seconde invocation, la partie compléteur du contexte apparaît comme `foo'.

Pour utiliser _prefix comme dernier recours et essayer uniquement la complétion normale lorsqu'il est invoqué :

zstyle ':completion:*' completer _complete ... _prefix
zstyle ':completion::prefix:*' completer _complete

Le style add-space est également respecté. S'il est défini sur `true', alors _prefix insérera un espace entre les correspondances générées (le cas échéant) et le suffixe.

Notez que ce compléteur n'est utile que si l'option COMPLETE_IN_WORD est définie ; sinon, le curseur sera déplacé à la fin du mot courant avant que le code de complétion ne soit appelé et il n'y aura donc pas de suffixe.

_user_expand
Ce compléteur se comporte de manière similaire au compléteur _expand mais effectue à la place des expansions définies par les utilisateurs. Les styles add-space et sort spécifiques au compléteur _expand sont utilisables avec _user_expand en plus d'autres styles gérés plus généralement par le système de complétion. Le tag all-expansions est également disponible.

L'expansion dépend du style de tableau user-expand étant défini pour le contexte courant ; rappelez-vous que le contexte pour les compléteurs est moins spécifique que celui pour la complétion contextuelle car le contexte complet n'a pas encore été déterminé. Les éléments du tableau peuvent avoir l'une des formes suivantes :

$hash

hash est le nom d'un tableau associatif. Notez qu'il ne s'agit pas d'une expression de paramètre complète, simplement d'un $, correctement cité pour empêcher une expansion immédiate, suivi du nom d'un tableau associatif. Si le mot d'expansion d'essai correspond à une clé dans hash, l'expansion résultante est la valeur correspondante.

_func

_func est le nom d'une fonction shell dont le nom doit commencer par _ mais n'est pas autrement spécial pour le système de complétion. La fonction est appelée avec le mot d'essai comme argument. Si le mot doit être développé, la fonction doit définir le tableau reply avec une liste d'expansions. Optionnellement, elle peut définir REPLY avec un mot qui sera utilisé comme description pour l'ensemble des expansions. Le statut de retour de la fonction est sans importance.

COMMANDES BINDABLES

En plus des complétions dépendant du contexte fournies, qui sont censées fonctionner de manière intuitivement évidente, il existe quelques widgets implémentant un comportement spécial qui peuvent être liés séparément à des touches. La liste suivante est celle de ces commandes et de leurs liaisons par défaut.

_bash_completions
Cette fonction est utilisée par deux widgets, _bash_complete-word et _bash_list-choices. Elle existe pour assurer la compatibilité avec les liaisons de complétion dans bash. Le dernier caractère de la liaison détermine ce qui est complété : `!', noms de commandes ; `$', variables d'environnement ; `@', noms d'hôtes ; `/', noms de fichiers ; `~' noms d'utilisateurs. Dans bash, la liaison précédée de `\e' effectue la complétion, et celle précédée de `^X' liste les options. Comme certaines de ces liaisons entrent en conflit avec les liaisons zsh standard, seuls `\e~' et `^X~' sont liés par défaut. Pour ajouter les autres, le code suivant doit être ajouté à .zshrc après que compinit ait été exécuté :
for key in '!' '$' '@' '/' '~'; do
  bindkey ""\e$key"" _bash_complete-word
  bindkey ""^X$key"" _bash_list-choices
done

Cela inclut les liaisons pour `~' au cas où elles seraient déjà liées à autre chose ; le code de complétion ne remplace pas les liaisons utilisateur.

_correct_filename (^XC)
Corrige le chemin du nom de fichier à la position du curseur. Permet jusqu'à six erreurs dans le nom. Peut également être appelé avec un argument pour corriger un chemin de nom de fichier, indépendamment de zle ; la correction est imprimée sur la sortie standard.
_correct_word (^Xc)
Effectue la correction du mot courant en utilisant les complétions contextuelles habituelles comme choix possibles. Cela stocke la chaîne `correct-word' dans le champ function du nom de contexte, puis appelle le compléteur _correct.
_expand_alias (^Xa)
Cette fonction peut être utilisée comme compléteur et comme commande bindable. Elle développe le mot sur lequel se trouve le curseur s'il s'agit d'un alias. Les types d'alias développés peuvent être contrôlés avec les styles regular, global et disabled.

Lorsqu'elle est utilisée comme commande bindable, il existe une fonctionnalité supplémentaire qui peut être sélectionnée en définissant le style complete sur `true'. Dans ce cas, si le mot n'est pas le nom d'un alias, _expand_alias essaie de compléter le mot pour en faire un nom d'alias complet sans le développer. Il laisse le curseur directement après le mot complété, de sorte qu'en invoquant _expand_alias une fois de plus, on développera le nom d'alias maintenant complet.

_expand_word (^Xe)
Effectue un développement sur le mot courant : équivalent à la commande standard expand-word comma
nd, mais en utilisant le compléteur _expand. Avant de l'appeler, le champ function du contexte est défini sur `expand-word'.
_generic
Cette fonction n'est pas définie comme un widget et n'est pas liée par défaut. Cependant, elle peut être utilisée pour définir un widget et stockera alors le nom de ce widget dans le champ function du contexte et appellera le système de complétion. Cela permet de définir facilement des widgets de complétion personnalisés avec leur propre ensemble de paramètres de style. Par exemple, pour définir un widget qui effectue une complétion normale et lance la sélection de menu :
zle -C foo complete-word _generic
bindkey '...' foo
zstyle ':completion:foo:*' menu yes select=1

Notez en particulier que le style completer peut être défini pour le contexte afin de changer l'ensemble des fonctions utilisées pour générer les correspondances possibles. Si _generic est appelé avec des arguments, ceux-ci sont transmis à _main_complete en tant que liste de compléteurs à la place de ceux définis par le style completer.

_history_complete_word (\e/)
Complète les mots à partir de l'historique des commandes du shell. Ceci utilise les styles list, remove-all-dups, sort et stop.
_most_recent_file (^Xm)
Complète le nom du fichier le plus récemment modifié correspondant au motif sur la ligne de commande (qui peut être vide). Si un argument numérique N est donné, complète le N-ième fichier le plus récemment modifié. Notez que la complétion, le cas échéant, est toujours unique.
_next_tags (^Xn)
Cette commande modifie l'ensemble des correspondances utilisées pour la balise suivante, ou l'ensemble des balises, soit comme spécifié par le style tag-order, soit par défaut ; ces correspondances ne seraient autrement pas disponibles. Des invocations successives de la commande parcourent tous les ensembles de balises possibles.
_read_comp (^X^R)
Invite l'utilisateur à entrer une chaîne de caractères et l'utilise pour effectuer une complétion sur le mot courant. Il y a deux possibilités pour la chaîne. Premièrement, il peut s'agir d'un ensemble de mots commençant par `_', par exemple `_files -/', auquel cas la fonction avec ses arguments sera appelée pour générer les complétions. Les parties non ambiguës du nom de la fonction seront complétées automatiquement (la complétion normale n'est pas disponible à ce stade) jusqu'à ce qu'un espace soit tapé.

Deuxièmement, toute autre chaîne sera passée comme ensemble d'arguments à compadd et devrait donc être une expression spécifiant ce qui doit être complété.

Un ensemble très restreint de commandes d'édition est disponible lors de la lecture de la chaîne : `DEL' et `^H' suppriment le dernier caractère ; `^U' supprime la ligne, et `^C' et `^G' avortent la fonction, tandis que `RET' accepte la complétion. Notez que la chaîne est utilisée telle quelle comme une ligne de commande, donc les arguments doivent être mis entre guillemets conformément aux règles standard du shell.

Une fois qu'une chaîne a été lue, le prochain appel à _read_comp utilisera la chaîne existante au lieu d'en lire une nouvelle. Pour forcer la lecture d'une nouvelle chaîne, appelez _read_comp avec un argument numérique.

_complete_debug (^X?)
Ce widget effectue une complétion ordinaire, mais capture dans un fichier temporaire une trace des commandes shell exécutées par le système de complétion. Chaque tentative de complétion obtient son propre fichier. Une commande pour visualiser chacun de ces fichiers est empilée sur la pile du buffer d'édition.
_complete_help (^Xh)
Ce widget affiche des informations sur les noms de contexte, les balises et les fonctions de complétion utilisées lors de la complétion à la position actuelle du curseur. Si un argument numérique autre que 1 est donné (comme dans `ESC-2 ^Xh'), alors les styles utilisés et les contextes pour lesquels ils sont utilisés seront également affichés.

Notez que les informations sur les styles peuvent être incomplètes ; cela dépend des informations disponibles auprès des fonctions de complétion appelées, qui dépendent à leur tour des propres styles et autres paramètres de l'utilisateur.

_complete_help_generic
Contrairement aux autres commandes listées ici, celle-ci doit être créée comme un widget ZLE normal plutôt qu'un widget de complétion (c'est-à-dire avec zle -N). Elle est utilisée pour générer de l'aide avec un widget lié au widget _generic décrit ci-dessus.

Si ce widget est créé en utilisant le nom de la fonction, comme c'est le cas par défaut, alors lorsqu'il est exécuté, il lira une séquence de touches. Celle-ci est censée être liée à un appel d'une fonction de complétion qui utilise le widget _generic. Ce widget sera exécuté, et fournira des informations dans le même format que celui affiché par le widget _complete_help pour la complétion contextuelle.

Si le nom du widget contient debug, par exemple s'il est créé comme `zle -N _complete_debug_generic _complete_help_generic', il lira et exécutera la chaîne de touches pour un widget générique comme précédemment, puis générera des informations de débogage comme le fait _complete_debug pour la complétion contextuelle.

Si le nom du widget contient noread, il ne lira pas de chaîne de touches mais organisera plutôt la prochaine utilisation d'un widget générique exécuté dans le même shell pour avoir l'effet décrit ci-dessus.

Le widget fonctionne en définissant le paramètre shell ZSH_TRACE_GENERIC_WIDGET qui est lu par _generic. La désinstallation du paramètre annule tout effet en attente de la forme noread.

Par exemple, après avoir exécuté ce qui suit :

zle -N _complete_debug_generic _complete_help_generic
bindkey '^x:' _complete_debug_generic

taper `C-x :' suivi de la séquence de touches pour un widget générique provoquera l'enregistrement des informations de trace pour ce widget dans un fichier.

_complete_tag (^Xt)
Ce widget complète les balises de symboles créées par les programmes etags ou ctags (notez qu'il n'y a pas de lien avec les balises du système de complétion) stockées dans un fichier TAGS, au format utilisé par etags, ou tags, au format créé par ctags. Il recherchera en remontant la hiérarchie des chemins la première occurrence de l'un ou l'autre fichier ; si les deux existent, le fichier TAGS est préféré. Vous pouvez spécifier le chemin complet d'un fichier TAGS ou tags en définissant le paramètre $TAGSFILE ou $tagsfile respectivement. Les balises de complétion correspondantes utilisées sont etags et vtags, respectivement après emacs et vi.

FONCTIONS UTILITAIRES

Les descriptions suivantes concernent les fonctions utilitaires qui peuvent être utiles lors de l'écriture de fonctions de complétion. Si les fonctions sont installées dans des sous-répertoires, la plupart d'entre elles résident dans le sous-répertoire Base. Comme les fonctions d'exemple pour les commandes de la distribution, les fonctions utilitaires qui génèrent des correspondances suivent toutes la convention de retourner un statut zéro si elles ont généré des complétions et non-zéro si aucune complétion correspondante n'a pu être ajoutée.

_absolute_command_paths
Cette fonction complète les commandes externes sous forme de chemins absolus (contrairement à _command_names -e qui complète leurs noms de base). Elle ne prend aucun argument.
_all_labels [ -x ] [ -12VJ ] tag name descr [ command arg ... ]
Il s'agit d'une interface pratique pour la fonction _next_label ci-dessous, implémentant la boucle montrée dans l'exemple de _next_label. La commande command et ses arguments sont appelés pour générer les correspondances. Les options stockées dans le paramètre name seront automatiquement insérées dans les args passés à la command. Normalement, elles sont placées directement après la command, mais si l'un des args est un simple trait d'union, elles sont insérées directement avant celui-ci. Si le trait d'union est le dernier argument, il sera supprimé de la liste des arguments avant que la command ne soit appelée. Cela permet d'utiliser _all_labels dans presque tous les cas où les correspondances peuvent être générées par un seul appel à la commande intégrée compadd ou par un appel à l'une des fonctions utilitaires.

Par exemple :

local expl
...
if _requested foo; then
  ...
  _all_labels foo expl '...' compadd ... - $matches
fi

Complétera les chaînes du paramètre matches, en utilisant compadd avec des options supplémentaires qui auront la priorité sur celles générées par _all_labels.

_alternative [ -O name ] [ -C name ] spec ...
Cette fonction est utile dans les cas simples où plusieurs balises sont disponibles. Elle implémente essentiellement une boucle comme celle décrite pour la fonction _tags ci-dessous.

Les balises à utiliser et l'action à effectuer si une balise est demandée sont décrites à l'aide des specs qui sont de la forme : `tag:descr:action'. Les tags sont proposés à l'aide de _tags et si la balise est demandée, l'action est exécutée avec la description donnée descr. Les actions sont celles acceptées par la fonction _arguments (décrite ci-dessous), à l'exception des suivantes :

•
Les formes `->state' et `=...' ne sont pas supportées.
•
La forme `((a\:bar b\:baz))' n'a pas besoin que le deux-points soit échappé, car les specs n'ont pas de champs séparés par des deux-points après l'action.

Par exemple, l'*action* peut être un simple appel de fonction :

_alternative \ 
    'users:user:_users' \ 
    'hosts:host:_hosts'

propose des noms d'utilisateurs et des noms d'hôtes comme correspondances possibles, générés par les fonctions _users et _hosts respectivement.

Comme _arguments, cette fonction utilise _all_labels pour exécuter les actions, qui bouclera sur tous les ensembles de balises. Une manipulation spéciale n'est nécessaire que s'il existe une balise valide supplémentaire, par exemple à l'intérieur d'une fonction appelée depuis _alternative.

L'option `-O name' est utilisée de la même manière que par la fonction _arguments. En d'autres termes, les éléments du tableau name seront passés à compadd lors de l'exécution d'une action.

Comme _tags, cette fonction prend en charge l'option -C pour donner un nom différent au champ de contexte d'argument.

_arguments [ -nswWCRS ] [ -A pat ] [ -O name ] [ -M matchspec ]
[ : ] spec ...
_arguments [ opt ... ] -- [ -l ] [ -i pats ] [ -s pair ]
[ helpspec ...]
Cette fonction peut être utilisée pour donner une spécification complète pour la complétion d'une commande dont les arguments suivent les conventions standard des options et arguments UNIX.

Aperçu des options

Les options de _arguments lui-même doivent être des mots séparés, c'est-à-dire -s -w, pas -sw. Les options sont suivies de specs qui décrivent les options et les arguments de la commande analysée. Pour éviter toute ambiguïté, toutes les options de _arguments lui-même peuvent être séparées des formes spec par un seul deux-points.

La forme `--' est utilisée pour déduire les formes spec à partir de la sortie d'aide de la commande analysée, et est décrite en détail ci-dessous. Les opts pour la forme `--' sont par ailleurs les mêmes options que la première forme. Notez que `-s' suivant `--' a une signification distincte de `-s' précédant `--', et les deux peuvent apparaître.

Les commutateurs d'options -s, -S, -A, -w et -W affectent la façon dont _arguments analyse les options de la ligne de commande analysée. Ces commutateurs sont utiles pour les commandes avec une analyse d'arguments standard.

Les options de _arguments ont les significations suivantes :

-n
Avec cette option, _arguments définit le paramètre NORMARG sur la position du premier argument normal dans le tableau $words, c'est-à-dire la position après la fin des options. Si cet argument n'a pas été atteint, NORMARG est défini sur -1. L'appelant doit déclarer `integer NORMARG' si l'option -n est passée ; sinon, le paramètre n'est pas utilisé.
-s
Active l' empilement d'options pour les options à une seule lettre, où plusieurs options à une seule lettre peuvent être combinées en un seul mot. Par exemple, les deux options `-x' et `-y' peuvent être combinées en un seul mot `-xy'. Par défaut, chaque mot correspond à un nom d'option unique (`-xy' est une seule option nommée `xy').

Les options commençant par un seul trait d'union ou un signe plus sont éligibles pour l'empilement ; les mots commençant par deux traits d'union ne le sont pas.

Notez que -s après -- a une signification différente, documentée dans le segment intitulé `Dérivation des formes spec à partir de la sortie d'aide'.

-w
En combinaison avec -s, permet l'empilement d'options même si une ou plusieurs des options prennent des arguments. Par exemple, si -x prend un argument, sans -s, `-xy' est considéré comme une seule option (non gérée) ; avec -s, -xy est une option avec l'argument `y' ; avec -s et -w, -xy est l'option -x et l'option -y avec des arguments pour -x (et pour -y, si elle prend des arguments) encore à venir dans les mots suivants.
-W
Cette option va un cran plus loin que -w : il est possible de compléter des options à une seule lettre même après un argument qui se produit dans le même mot. Cependant, cela dépend de l'action effectuée pour savoir si les options seront réellement complétées à ce stade. Pour plus de contrôle, utilisez une fonction utilitaire comme _guard dans le cadre de l'action.
-C
Modifie le paramètre curcontext pour une action de la forme `->state'. Ceci est discuté en détail ci-dessous.
-R
Retourne le statut 300 au lieu de zéro lorsqu'un $state doit être géré, dans la syntaxe `->string'.
-S
Ne complète pas les options après un `--' apparaissant sur la ligne, et ignore le `--'. Par exemple, avec -S, dans la ligne
foobar -x -- -y

le `-x' est considéré comme une option, le `-y' est considéré comme un argument, et le `--' n'est considéré comme ni l'un ni l'autre.

-A pat
Ne complète pas les options après le premier argument non-option sur la ligne. pat est un modèle correspondant à toutes les chaînes qui ne doivent pas être prises comme arguments. Par exemple, pour que _arguments arrête de compléter les options après le premier argument normal, mais ignore toutes les chaînes commençant par un trait d'union même si elles ne sont pas décrites par l'un des optspecs, la forme est `-A "-*"'.
-O name
Passe les éléments du tableau name comme arguments aux fonctions appelées pour exécuter les actions. Ceci est discuté en détail ci-dessous.
-M matchspec
Utilise la spécification de correspondance matchspec pour la complétion des noms et des valeurs d'options. La matchspec par défaut permet la complétion de mots partiels après `_' et `-', comme compléter `-f-b' en `-foo-bar'. La matchspec par défaut est :
r:|[_-]=* r:|=*
-0
Lors du remplissage des valeurs du tableau associatif `opt_args', n'échappe pas avec des barres obliques inverses les deux-points et les barres obliques inverses et utilise NUL plutôt que deux-points pour joindre plusieurs valeurs. Cette option est décrite plus en détail ci-dessous, sous le titre spécifications : actions.

spécifications : aperçu

Chacune des formes suivantes est une spec décrivant des ensembles individuels d'options ou d'arguments sur la ligne de commande analysée.

n:message:action
n::message:action
Ceci décrit le n-ième argument normal. Le message sera imprimé au-dessus des correspondances générées et l' action indique ce qui peut être complété à cette position (voir ci-dessous). S'il y a deux deux-points avant le message, l'argument est facultatif. Si le message ne contient que des espaces blancs, rien ne sera imprimé au-dessus des correspondances à moins que l'action n'ajoute elle-même une chaîne d'explication.
:message:action
::message:action
Similaire, mais décrit l'argument *suivant*, quel que soit son numéro. Si tous les arguments sont spécifiés sous cette forme dans le bon ordre, les numéros ne sont pas nécessaires.
*:message:action
*::message:action
*:::message:action
Ceci décrit comment les arguments (généralement les arguments non-option, ceux qui ne commencent pas par - ou +) doivent être complétés lorsqu'aucune des deux premières formes n'a été fournie. Un nombre quelconque d'arguments peut être complété de cette manière.

Avec deux deux-points avant le message, le tableau spécial words et le paramètre spécial CURRENT sont modifiés pour ne faire référence qu'aux arguments normaux lorsque l' action est exécutée ou évaluée. Avec trois deux-points avant le message, ils sont modifiés pour ne faire référence qu'aux arguments normaux couverts par cette description.

optspec
optspec:...
Ceci décrit une option. Le deux-points indique la gestion d'un ou plusieurs arguments pour l'option ; s'il n'est pas présent, l'option est supposée ne prendre aucun argument.

Les formes suivantes sont disponibles pour l' optspec initial, que l'option ait ou non des arguments.

*optspec
Ici, optspec est l'une des formes restantes ci-dessous. Ceci indique que l' optspec suivant peut être répété. Sinon, si l'option correspondante est déjà présente sur la ligne de commande à gauche du curseur, elle ne sera plus proposée.
-optname
+optname
Dans la forme la plus simple, l' optspec est simplement le nom de l'option commençant par un moins ou un plus, tel que `-foo'. Le premier argument de l'option (le cas échéant) doit suivre comme un mot *séparé* directement après l'option.

Soit `-+optname' soit `+-optname' peuvent être utilisés pour spécifier que -optname et +optname sont tous deux valides.

Dans toutes les formes restantes, le `-' initial peut être remplacé par ou jumelé avec `+' de cette manière.

-optname-
Le premier argument de l'option doit venir directement après le nom de l'option dans le même mot. Par exemple, `-foo-:...' spécifie que l'option et l'argument complétés ressembleront à `-fooarg'.
-optname+
Le premier argument peut apparaître immédiatement après optname dans le même mot, ou peut apparaître comme un mot séparé après l'option. Par exemple, `-foo+:...' spécifie que l'option et l'argument complétés ressembleront soit à `-fooarg' soit à `-foo arg'.
-optname=
L'argument peut apparaître comme le mot suivant, ou dans le même mot que le nom de l'option à condition qu'il soit séparé par un signe égal, par exemple `-foo=arg' ou `-foo arg'.
-optname=-
L'argument de l'option doit apparaître après un signe égal dans le même mot, et ne peut pas être donné dans l'argument suivant.
optspec[explication]
Une chaîne d'explication peut être ajoutée à n'importe laquelle des formes précédentes d' optspec en l'encapsulant entre crochets, comme dans `-q[opération de requête]'.

Le style verbose est utilisé pour décider si les chaînes d'explication sont affichées avec l'option dans une liste de complétion.

Si aucune chaîne d'explication entre crochets n'est donnée mais que le style auto-description est défini et qu'un seul argument est décrit pour cette optspec, la valeur du style est affichée, avec toute occurrence de la séquence `%d' remplacée par la valeur du message du premier optarg qui suit l' optspec.

/i>; voir ci-dessous.

Il est possible que des options avec un `+' ou un `=' littéral apparaissent, mais ce caractère doit être cité, par exemple `-\+'.

Chaque optarg suivant un optspec doit prendre l'une des formes suivantes :

:message:action
::message:action
Un argument de l'option ; message et action sont traités comme pour les arguments ordinaires. Dans la première forme, l'argument est obligatoire, et dans la seconde forme, il est facultatif.

Ce groupe peut être répété pour les options qui prennent plusieurs arguments. Autrement dit, :message1:action1:message2:action2 spécifie que l'option prend deux arguments.

:*pattern:message:action
:*pattern::message:action
:*pattern:::message:action
Ceci décrit plusieurs arguments. Seul le dernier optarg pour une option prenant plusieurs arguments peut être donné sous cette forme. Si le pattern est vide (c'est-à-dire :*:), tous les mots restants sur la ligne doivent être complétés comme décrit par l'action ; sinon, tous les mots jusqu'à et y compris un mot correspondant au pattern doivent être complétés en utilisant l'action.

Les deux-points multiples sont traités comme pour les formes `*:...' pour les arguments ordinaires : lorsque le message est précédé de deux deux-points, le tableau spécial words et le paramètre spécial CURRENT sont modifiés pendant l'exécution ou l'évaluation de l'action pour ne se référer qu'aux mots après l'option. Lorsqu'il est précédé de trois deux-points, ils sont modifiés pour ne se référer qu'aux mots couverts par cette description.

Tout deux-points littéral dans un optname, un message, ou une action doit être précédé d'une barre oblique inverse, `\:'.

Chacune des formes ci-dessus peut être précédée d'une liste entre parenthèses de noms d'options et de numéros d'arguments. Si l'option donnée est sur la ligne de commande, les options et arguments indiqués entre parenthèses ne seront pas proposés. Par exemple, `(-two -three 1)-one:...' complète l'option `-one' ; si cela apparaît sur la ligne de commande, les options -two et -three et le premier argument ordinaire ne seront pas complétés après.

`(-foo):...' spécifie un achèvement d'argument ordinaire ; -foo ne sera pas complété si cet argument est déjà présent.

D'autres éléments peuvent apparaître dans la liste des options exclues pour indiquer divers autres éléments qui ne devraient pas être appliqués lorsque la spécification actuelle correspond : une étoile simple (*) pour les arguments restants (c'est-à-dire une spécification de la forme `*:...') ; un deux-points (:) pour tous les arguments normaux (non-options) ; et un trait d'union (-) pour toutes les options. Par exemple, si `(*)' apparaît avant une option et que l'option apparaît sur la ligne de commande, la liste des arguments restants (ceux qui commencent par `*:' dans le tableau ci-dessus) ne sera pas complétée.

Pour faciliter la réutilisation des spécifications, il est possible de précéder l'une des formes ci-dessus de `!' ; alors la forme ne sera plus complétée, bien que si l'option ou l'argument apparaît sur la ligne de commande, ils seront ignorés comme d'habitude. L'utilisation principale de cela est lorsque les arguments sont donnés par un tableau, et _arguments est appelé à plusieurs reprises pour des contextes plus spécifiques : lors du premier appel, `_arguments $global_options' est utilisé, et lors des appels ultérieurs, `_arguments !$^global_options'.

spécifications: actions

Dans chacune des formes ci-dessus, l'action détermine comment les complétions doivent être générées. À l'exception de la forme `->string' ci-dessous, l'action sera exécutée en appelant la fonction _all_labels pour traiter toutes les étiquettes. Aucun traitement spécial des étiquettes n'est nécessaire à moins qu'un appel de fonction n'en introduise une nouvelle.

Les fonctions appelées pour exécuter les actions seront appelées avec les éléments du tableau nommé par l'option `-O' *name* comme arguments. Ceci peut être utilisé, par exemple, pour passer le même ensemble d'options pour le builtin compadd à toutes les actions.

Les formes pour action sont les suivantes.

(espace simple non cité)
Ceci est utile lorsqu'un argument est requis mais qu'il n'est pas possible ou souhaitable de générer des correspondances pour lui. Le message sera affiché mais aucune complétion ne sera listée. Notez que même dans ce cas, le deux-points à la fin du message est nécessaire ; il ne peut être omis que lorsqu'aucun message ni action n'est donné.
(item1 item2 ...)
Une correspondance parmi une liste de correspondances possibles, par exemple :
:foo:(foo bar baz)
((item1\:desc1 ...))
Similaire à ce qui précède, mais avec des descriptions pour chaque correspondance possible. Notez la barre oblique inverse avant le deux-points. Par exemple,
:foo:((a\:bar b\:baz))

Les correspondances seront listées avec leurs descriptions si le style description est défini avec l'étiquette values dans le contexte.

->string
Dans cette forme, _arguments traite les arguments et les options, puis rend le contrôle à la fonction appelante avec les paramètres définis pour indiquer l'état du traitement ; la fonction appelante prend alors ses propres dispositions pour générer les complétions. Par exemple, les fonctions qui implémentent une machine à états peuvent utiliser ce type d'action.

Là où _arguments rencontre une action au format `->string', il supprimera tous les espaces blancs de tête et de fin de string et définira le tableau state avec l'ensemble de toutes les strings pour lesquelles une action doit être effectuée. Les éléments du tableau state_descr reçoivent le champ message correspondant de chaque optarg contenant une telle action.

Par défaut et comme toutes les autres fonctions de complétion bien comportées, _arguments retourne un statut zéro s'il a pu ajouter des correspondances et non-zéro sinon. Cependant, si l'option -R est donnée, _arguments retournera à la place un statut de 300 pour indiquer que $state doit être géré.

En plus de $state et $state_descr, _arguments définit également les paramètres globaux `context', `line' et `opt_args' comme décrit ci-dessous, et ne réinitialise aucune des modifications apportées aux paramètres spéciaux tels que PREFIX et words. Cela donne à la fonction appelante le choix de réinitialiser ces paramètres ou de propager les changements apportés à ceux-ci.

Une fonction appelant _arguments avec au moins une action contenant un `->string' doit donc déclarer des paramètres locaux appropriés :

local context state state_descr line
typeset -A opt_args

pour éviter que _arguments ne modifie l'environnement global.

{eval-string}
Une chaîne entre accolades est évaluée comme du code shell pour générer des correspondances. Si l'eval-string elle-même ne commence pas par une parenthèse ouvrante ou une accolade, elle est divisée en mots distincts avant l'exécution.
= action
Si l'action commence par `= ' (un signe égal suivi d'un espace), _arguments insérera le contenu du champ argument du contexte actuel comme premier nouvel élément dans le tableau spécial words et incrémentera la valeur du paramètre spécial CURRENT. Ceci a pour effet d'insérer un mot factice sur la ligne de commande de complétion sans modifier le point auquel la complétion a lieu.

C'est le plus utile avec l'un des spécificateurs qui restreignent les mots sur la ligne de commande sur lesquels l'action doit opérer (les formes à deux et trois deux-points ci-dessus). Une utilisation particulière est lorsqu'une action elle-même provoque un appel à _arguments sur une plage restreinte ; il est nécessaire d'utiliser cette astuce pour insérer un nom de commande approprié dans la plage pour que le second appel à _arguments puisse analyser la ligne.

word...
word...
Ceci couvre toutes les formes autres que celles ci-dessus. Si l'action commence par un espace, la liste restante de mots sera invoquée inchangée.

Sinon, elle sera invoquée avec des chaînes supplémentaires placées après le premier mot ; celles-ci doivent être transmises comme options au builtin compadd. Elles garantissent que l'état spécifié par _arguments, en particulier les descriptions des options et des arguments, est correctement transmis à la commande de complétion. Ces arguments supplémentaires sont tirés du paramètre de tableau `expl' ; celui-ci sera configuré avant l'exécution de l'*action* et peut donc y être référencé, typiquement dans une expansion de la forme `$expl[@]' qui préserve les éléments vides du tableau.

Lors de l'exécution de l'action, le tableau `line' sera défini sur les arguments normaux de la ligne de commande, c'est-à-dire les mots de la ligne de commande après le nom de la commande, à l'exclusion de toutes les options et de leurs arguments. Les options sont stockées dans le tableau associatif `opt_args' avec les noms d'options comme clés et leurs arguments comme valeurs. Par défaut, tous les deux-points et barres obliques inverses dans la valeur sont échappés avec des barres obliques inverses, et si une option a plusieurs arguments (par exemple, lors de l'utilisation d'un optspec de la forme `*optspec'), ils sont joints par des deux-points (non échappés). Cependant, si l'option -0 a été passée, aucun échappement par barre oblique inverse n'est effectué, et les valeurs multiples sont jointes par des octets NUL. Par exemple, après `zsh -o foo:foo -o bar:bar -o <TAB>', le contenu de `opt_args' serait

typeset -A opt_args=( [-o]='foo\:foo:bar\:bar:' )

par défaut, et

typeset -A opt_args=( [-o]=$'foo:foo\x00bar:bar\x00' )

si _arguments avait été appelé avec l'option -0.

Le paramètre `context' est défini lors du retour à la fonction appelante pour effectuer une action de la forme `->string'. Il est défini sur un tableau d'éléments correspondant aux éléments de $state. Chaque élément est un nom approprié pour le champ argument du contexte : soit une chaîne de la forme `

option-opt-n' pour le n'ème argument de l'option -opt, ou une chaîne de la forme `argument-n' pour le n'ème argument. Pour les arguments `rest', c'est-à-dire ceux figurant en fin de liste et non gérés par position, n est la chaîne `rest'. Par exemple, lors de la complétion de l'argument de l'option -o, le nom est `option-o-1', tandis que pour le deuxième argument normal (sans option-) c'est `argument-2'.

De plus, lors de l'évaluation de l'action, le nom du contexte dans le paramètre curcontext est modifié pour y ajouter la même chaîne qui est stockée dans le paramètre context.

L'option -C indique à _arguments de modifier le paramètre curcontext pour une action de la forme `->state'. C'est le paramètre standard utilisé pour suivre le contexte actuel. Ici, il (et non le tableau context) doit être rendu local à la fonction appelante pour éviter de renvoyer la valeur modifiée et doit être initialisé à la valeur actuelle au début de la fonction :

local curcontext="$curcontext"

Ceci est utile lorsqu'il n'est pas possible que plusieurs états soient valides simultanément.

Regroupement d'options

Les options peuvent être regroupées pour simplifier les listes d'exclusion. Un groupe est introduit par `+' suivi d'un nom pour le groupe dans le mot suivant. Les groupes entiers peuvent ensuite être référencés dans une liste d'exclusion, ou le nom d'un groupe peut être utilisé pour lever une ambiguïté entre deux formes de la même option. Par exemple :

_arguments \ 
    '(group2--x)-a' \ 
  + group1 \ 
    -m \ 
    '(group2)-n' \ 
  + group2 \ 
    -x -y

Si le nom d'un groupe est spécifié sous la forme `(name)', alors une seule valeur de ce groupe sera complétée ; plus formellement, toutes les spécifications sont mutuellement exclusives avec toutes les autres spécifications de ce groupe. Ceci est utile pour définir des options qui sont des alias les unes des autres. Par exemple :

_arguments \ 
    -a -b \ 
  + '(operation)' \ 
    {-c,--compress}'[compress]' \ 
    {-d,--decompress}'[decompress]' \ 
    {-l,--list}'[list]'

Si une option d'un groupe apparaît sur la ligne de commande, elle est stockée dans le tableau associatif `opt_args' avec 'group-option' comme clé. Dans l'exemple ci-dessus, une clé `operation--c' est utilisée si l'option `-c' est présente sur la ligne de commande.

Spécification de plusieurs ensembles d'arguments

Il est possible de spécifier plusieurs ensembles d'options et d'arguments, les ensembles étant séparés par des tirets simples. Ceci diffère des groupes en ce que les ensembles sont considérés comme mutuellement exclusifs les uns des autres.

Les spécifications avant le premier ensemble et de n'importe quel groupe sont communes à tous les ensembles. Par exemple :

_arguments \ 
    -a \ 
  - set1 \ 
    -c \ 
  - set2 \ 
    -d \ 
    ':arg:(x2 y2)'

Ceci définit deux ensembles. Lorsque la ligne de commande contient l'option `-c', l'option `-d' et l'argument ne seront pas considérés comme des complétions possibles. Lorsqu'elle contient `-d' ou un argument, l'option `-c' ne sera pas considérée. Cependant, après `-a', les deux ensembles seront toujours considérés comme valides.

Comme pour les groupes, le nom d'un ensemble peut apparaître dans les listes d'exclusion, soit seul, soit précédant une spécification normale d'option ou d'argument.

Le code de complétion doit analyser la ligne de commande séparément pour chaque ensemble. Cela peut être lent, donc les ensembles ne doivent être utilisés que lorsque c'est nécessaire. Une alternative utile est souvent une spécification d'option avec des arguments restants (comme dans `-foo:*:...'); ici, l'option -foo avale tous les arguments restants comme décrit par les définitions optarg.

Dérivation des formes spec à partir de la sortie d'aide

L'option `--' permet à _arguments de déterminer les noms des options longues qui supportent l'option `--help', ce qui est standard dans de nombreuses commandes GNU. Le mot de commande est appelé avec l'argument `--help' et la sortie est examinée pour trouver les noms d'options. Clairement, il peut être dangereux de passer ceci à des commandes qui pourraient ne pas supporter cette option, car le comportement de la commande n'est pas spécifié.

En plus des options, `_arguments --' essaiera de déduire les types d'arguments disponibles pour les options lorsque la forme `--opt=val' est valide. Il est également possible de fournir des indices en examinant le texte d'aide de la commande et en ajoutant des helpspec de la forme `pattern:message:action'; notez que d'autres formes de spec _arguments ne sont pas utilisées. Le pattern est comparé au texte d'aide pour une option, et s'il correspond, le message et l'*action* sont utilisés comme pour d'autres spécificateurs d'arguments. Le cas spécial de `*:' signifie que le message et l'*action* sont vides, ce qui a pour effet de faire en sorte que les options sans description dans la sortie d'aide soient classées avant les options qui ont une description.

Par exemple :

_arguments -- '*\*:toggle:(yes no)' \ 
              '*=FILE*:file:_files' \ 
              '*=DIR*:directory:_files -/' \ 
              '*=PATH*:directory:_files -/'

Ici, `yes' et `no' seront complétés comme argument des options dont la description se termine par une étoile ; les noms de fichiers seront complétés pour les options qui contiennent la sous-chaîne `=FILE' dans la description ; et les répertoires seront complétés pour les options dont la description contient `=DIR' ou `=PATH'. Les trois derniers sont en fait par défaut et n'ont donc pas besoin d'être donnés explicitement, bien qu'il soit possible de remplacer l'utilisation de ces motifs. Un texte d'aide typique utilisant cette fonctionnalité est :

  -C, --directory=DIR          change to directory DIR

de sorte que les spécifications ci-dessus entraînent la complétion des répertoires après `--directory', mais pas après `-C'.

Notez également que _arguments essaie de déterminer automatiquement si l'argument d'une option est facultatif. Ceci peut être spécifié explicitement en doublant le deux-points avant le message.

Si le pattern se termine par `(-)', il sera retiré du motif et l'*action* sera utilisée uniquement directement après le `=', pas dans le mot suivant. C'est le comportement d'une spécification normale définie avec la forme `=-'.

Par défaut, la commande (avec l'option `--help') est exécutée après avoir réinitialisé toutes les catégories de locale (à l'exception de LC_CTYPE) à `C'. Si la sortie d'aide localisée est connue pour fonctionner, l'option `-l' peut être spécifiée après `_arguments --' afin que la commande soit exécutée dans la locale actuelle.

Le `_arguments --' peut être suivi de l'option `-i patterns' pour donner des motifs pour les options qui ne doivent pas être complétées. Les motifs peuvent être donnés sous forme de nom d'un paramètre de tableau ou sous forme de liste littérale entre parenthèses. Par exemple,

_arguments -- -i \ 
    "(--(en|dis)able-FEATURE*)"

indiquera à la complétion d'ignorer les options `--enable-FEATURE' et `--disable-FEATURE' (cet exemple est utile avec GNU configure).

Le `_arguments --' peut également être suivi de l'option `-s pair' pour décrire des alias d'options. Le pair consiste en une liste alternée de motifs et de remplacements correspondants, enfermée entre parenthèses et mise entre guillemets afin qu'elle forme un seul mot argument dans l'appel _arguments.

Par exemple, certaines sorties d'aide de scripts configure décrivent les options uniquement comme `--enable-foo', mais le script accepte également la forme niée `--disable-foo'. Pour permettre la complétion de la deuxième forme :

_arguments -- -s "((#s)--enable- --disable-)"

Notes diverses

Enfin, notez que _arguments s'attend généralement à être la fonction principale gérant toute complétion pour laquelle elle est utilisée. Elle peut avoir des effets secondaires qui modifient le traitement de toute correspondance ajoutée par d'autres fonctions appelées après elle. Pour combiner _arguments avec d'autres fonctions, ces fonctions doivent être appelées soit avant _arguments, soit comme une action dans une spec, soit dans des gestionnaires pour les actions `->state'.

Voici un exemple plus général de l'utilisation de _arguments :

_arguments '-l+:left border:' \ 
           '-format:paper size:(letter A4)' \ 
           '*-copy:output file:_files::resolution:(300 600)' \ 
           ':postscript file:_files -g \*.\(ps\|eps\)' \ 
           '*:page number:'

Ceci décrit trois options : `-l', `-format', et `-copy'. La première prend un argument décrit comme `bordure gauche' pour lequel aucune complétion ne sera offerte en raison de l'action vide. Son argument peut venir directement après le `-l' ou il peut être donné comme le mot suivant sur la ligne.

L'option `-format' prend un argument dans le mot suivant, décrit comme `taille de papier' pour lequel seules les chaînes `letter' et `A4' seront complétées.

L'option `-copy' peut apparaître plus d'une fois sur la ligne de commande et prend deux arguments. Le premier est obligatoire et sera complété comme un nom de fichier. Le second est facultatif (en raison du deuxième deux-points avant la description `résolution') et sera complété à partir des chaînes `300' et `600'.

Les deux dernières descriptions indiquent ce qui doit être complété comme arguments. La première décrit le premier argument comme un `fichier postscript' et fait compléter les fichiers se terminant par `ps' ou `eps'. La dernière description donne à tous les autres arguments la description `numéro de page' mais n'offre pas de complétions.

_cache_invalid cache_identifier
Cette fonction renvoie zéro si le cache de complétion correspondant à l'identificateur de cache donné doit être reconstruit. Elle le détermine en consultant le style cache-policy pour le contexte actuel. Cela devrait fournir un nom de fonction qui est exécuté avec le chemin complet du fichier de cache pertinent comme seul argument.

Exemple :

_example_caching_policy () {
    # reconstruire si le cache a plus d'une semaine
    local -a oldp
    oldp=( "$1"(Nm+7) )
    (( $#oldp ))
}
_call_function return name [ arg ... ]
Si une fonction name existe, elle est appelée avec les arguments args. L'argument return donne le nom d'un paramètre dans lequel le statut de retour de la fonction name doit être stocké ; si return est vide ou un simple trait d'union, il est ignoré.

Le statut de retour de _call_function lui-même est zéro si la fonction name existe et a été appelée, et non zéro sinon.

_call_program [ -l ] [ -p ] tag string ...
Cette fonction fournit un mécanisme pour que l'utilisateur remplace l'utilisation d'une commande externe. Elle recherche le style command avec le tag fourni. Si le style est défini, sa valeur est utilisée comme commande à exécuter. Les strings de l'appel à _call_program, ou du style s'il est défini, sont concaténés avec des espaces entre eux et la chaîne résultante est évaluée. Le statut de retour est le statut de retour de la commande appelée.

Par défaut, la commande est exécutée dans un environnement où toutes les catégories de localisation (à l'exception de LC_CTYPE) sont réinitialisées à `C' en appelant la fonction utilitaire _comp_locale (voir ci-dessous). Si l'option `-l' est donnée, la commande est exécutée avec la localisation actuelle.

Si l'option `-p' est fournie, elle indique que la sortie de la commande est influencée par les permissions avec lesquelles elle est exécutée. Si le style gain-privileges est défini sur vrai, _call_program utilisera des commandes telles que sudo, si elles sont présentes sur la ligne de commande, pour faire correspondre les permissions à celles sous lesquelles la commande finale est susceptible de s'exécuter. Lors de la recherche des styles gain-privileges et command, le composant commande du contexte zstyle se terminera par une barre oblique (`/') suivie de la commande qui serait utilisée pour gagner des privilèges.

_combination [ -s pattern ] tag style spec ... field opts ...
Cette fonction est utilisée pour compléter des combinaisons de valeurs, par exemple des paires de noms d'hôtes et d'utilisateurs. L'argument style donne le style qui définit les paires ; il est recherché dans un contexte avec le tag spécifié.

Le nom du style se compose de noms de champs séparés par des traits d'union, par exemple `users-hosts-ports'. Pour chaque champ pour lequel une valeur est déjà connue, un spec de la forme `field=pattern' est donné. Par exemple, si la ligne de commande spécifie jusqu'à présent un utilisateur `pws', l'argument `users=pws' devrait apparaître.

L'argument suivant sans signe égal est pris comme nom du champ pour lequel des complétions doivent être générées (vraisemblablement pas l'un des fields pour lesquels la valeur est connue).

Les correspondances générées seront tirées de la valeur du style. Celles-ci doivent contenir les valeurs possibles pour les combinaisons dans l'ordre approprié (utilisateurs, hôtes, ports dans l'exemple ci-dessus). Les valeurs pour les différents champs sont séparées par des deux-points. Ceci peut être modifié avec l'option -s de _combination qui spécifie un motif. Typiquement il s'agit d'une classe de caractères, comme par exemple `-s "[:@]"' dans le cas du style users-hosts. Chaque spécification `field=pattern' restreint les complétions qui s'appliquent aux éléments du style avec des champs correspondants de manière appropriée.

Si aucun style du nom donné n'est défini pour le tag donné, ou si aucune des chaînes dans la valeur du style ne correspond, mais qu'un nom de fonction requis pour le champ, précédé d'un underscore, est défini, cette fonction sera appelée pour générer les correspondances. Par exemple, s'il n'y a pas de `users-hosts-ports' ou pas d'hôte correspondant lorsqu'un hôte est requis, la fonction `_hosts' sera automatiquement appelée.

Si le même nom est utilisé pour plus d'un champ, à la fois dans `field=pattern' et dans l'argument qui donne le nom du champ à compléter, le numéro du champ (à partir de un) peut être donné après le nom du champ, séparé de celui-ci par un deux-point.

Tous les arguments après le nom de champ requis sont passés à compadd lors de la génération de correspondances à partir de la valeur du style, ou aux fonctions des champs s'ils sont appelés.

_command_names [ -e | - ]
Cette fonction complète les mots valides en position de commande : noms d'alias, commandes internes, commandes hachées, fonctions, etc. Avec le drapeau -e, seules les commandes hachées sont complétées. Le drapeau - est ignoré.
_comp_locale
Cette fonction réinitialise toutes les catégories de localisation autres que LC_CTYPE à `C' afin que la sortie des commandes externes puisse être facilement analysée par le système de complétion. LC_CTYPE conserve la valeur actuelle (en tenant compte de LC_ALL et LANG), garantissant que les caractères non ASCII dans les noms de fichiers sont toujours correctement gérés.

Cette fonction ne devrait normalement être exécutée que dans un sous-shell, car la nouvelle localisation est exportée dans l'environnement. Une utilisation typique serait `$(_comp_locale; command ...)'.

_completers [ -p ]
Cette fonction complète les noms des compléteurs.
-p
Inclure l'underscore initial (`_') dans les correspondances.
_default
Cette fonction correspond au contexte spécial -default- qui est appliqué là où aucune complétion n'est définie. Il est utile de l'appeler dans certaines conditions d'erreur telles qu'une complétion après une sous-commande non reconnue. Ceci applique le concept de dégradation gracieuse au système de complétion, lui permettant de se rabattre sur la complétion de base d'éléments couramment utiles comme les noms de fichiers.
_describe [-12JVx] [ -oO | -t tag ] descr name1 [ name2 ] [ opt ... ]
[ -- name1 [ name2 ] [ opt ... ] ... ]
Cette fonction associe des complétions à des descriptions. Plusieurs groupes séparés par -- peuvent être fournis, potentiellement avec différentes options de complétion opts.

Le descr est pris comme une chaîne à afficher au-dessus des correspondances si le style format pour le tag descriptions est défini. Ceci est suivi par un ou deux noms de tableaux suivis d'options à passer à compadd. Le tableau name1 contient les complétions possibles avec leurs descriptions sous la forme `completion:description'. Tous les deux-points littéraux dans completion doivent être échappés avec une barre oblique inversée. Si un name2 est donné, il doit avoir le même nombre d'éléments que name1 ; dans ce cas, les éléments correspondants sont ajoutés comme complétions possibles à la place des chaînes completion de name1. La liste de complétion conservera les descriptions de name1. Enfin, un ensemble d'options de complétion peut apparaître.

Si l'option `-o' apparaît avant le premier argument, les correspondances ajoutées seront traitées comme des noms d'options de commande (N.B. pas des options de shell), typiquement suivant un `-', `--' ou `+' sur la ligne de commande. Dans ce cas, _describe utilise les styles prefix-hidden, prefix-needed et verbose pour déterminer si les chaînes doivent être ajoutées comme complétions et si les descriptions doivent être affichées. Sans l'option `-o', seul le style verbose est utilisé pour décider comment les descriptions sont affichées. Si `-O' est utilisé à la place de `-o', les options de commande sont complétées comme ci-dessus mais _describe ne gérera pas le style prefix-needed.

Avec l'option -t, un tag peut être spécifié. La valeur par défaut est `values' ou, si l'option -o est donnée, `options'.

Les options -1, -2, -J, -V, -x sont passées à _next_label.

Si elles sont sélectionnées par le style list-grouped, les chaînes ayant la même description apparaîtront ensemble dans la liste.

_describe utilise la fonction _all_labels pour générer les correspondances, il n'a donc pas besoin d'apparaître dans une boucle sur les tags.

_description [ -x ] [ -12VJ ] tag name descr [ spec ... ]
Cette fonction ne doit pas être confondue avec la précédente ; elle est utilisée comme fonction d'aide pour la création d'options pour compadd. Elle est enfouie dans de nombreuses fonctions de complétion de haut niveau et n'a donc souvent pas besoin d'être appelée directement.

Les styles listés ci-dessous sont testés dans le contexte actuel en utilisant le tag donné. Les options résultantes pour compadd sont placées dans le tableau nommé name (c'est traditionnellement `expl', mais cette convention n'est pas imposée). La description pour l'ensemble correspondant de correspondances est passée à la fonction dans descr.

Les styles testés sont : format, hidden, matcher, ignore-line, ignored-patterns, group-name et sort. Le style format est d'abord testé pour le tag donné puis pour le tag descriptions si aucune valeur n'a été trouvée, tandis que les autres ne sont testés que pour le tag donné comme premier argument. La fonction appelle également _setup qui teste quelques styles supplémentaires.

La chaîne retournée par le style format (s'il y en a une) sera modifiée de manière à ce que la séquence `%d' soit remplacée par le descr donné comme troisième argument sans aucun espace blanc en tête ou en queue. Si, après avoir retiré les espaces blancs, le descr est la chaîne vide, le style de format ne sera pas utilisé et les options placées dans le tableau name ne contiendront pas de chaîne d'explication à afficher au-dessus des correspondances.

Si _description est appelée avec plus de trois arguments, les specs supplémentaires doivent être de la forme `char:str'. Celles-ci fournissent des remplacements de séquences d'échappement pour le style format : chaque apparition de `%char' sera remplacée par la string. Si aucune spec supplémentaire n'est donnée mais que la description dans descr correspond à une forme courante, alors des séquences d'échappement supplémentaires sont définies pour les éléments de cette description. Ces éléments correspondent à une valeur par défaut (`%o'), les unités (`%m'), la plage de valeurs acceptables (`%r') et la partie initiale restante de la description (`%h'). La forme que prend la description consiste à spécifier les unités et la plage entre parenthèses et la valeur par défaut entre crochets, par exemple :

_description times expl 'timeout (seconds) (0-60) [20]'

Il est possible d'utiliser des expressions conditionnelles zformat lors de la stylisation de ces éléments. Ainsi, par exemple, pour ajouter `default:' comme tag

but only when there is a default value to show, the format style might include %(o.default: %o.)'.

If the -x option is given, the description will be passed to compadd using the -x option instead of the default -X. This means that the description will be displayed even if there are no corresponding matches.

The options placed in the array name take account of the group-name style, so matches are placed in a separate group where necessary. The group normally has its elements sorted (by passing the option -J to compadd), but if an option starting with `-V', `-J', `-1', or `-2' is passed to _description, that option will be included in the array. Hence it is possible for the completion group to be unsorted by giving the option `-V', `-1V', or `-2V'.

In most cases, the function will be used like this:

local expl
_description files expl file
compadd "$expl[@]" - "$files[@]"

Note the use of the parameter expl, the hyphen, and the list of matches. Almost all calls to compadd within the completion system use a similar format; this ensures that user-specified styles are correctly passed down to the builtins which implement the internals of completion.

Écrire des plugins

Les plugins sont écrits comme des fonctions séparées dont les noms commencent par `_email-'. Ils sont appelés avec l'option -c et les options compadd. Ils doivent soit effectuer leur propre complétion, soit définir le tableau $reply avec une liste d'éléments `alias:address' et retourner 300. De nouveaux plugins seront automatiquement détectés et exécutés.

_files
La fonction _files est un wrapper autour de _path_files. Elle prend en charge toutes les mêmes fonctionnalités, avec quelques améliorations -- notamment, elle respecte le style list-dirs-first et permet aux utilisateurs de remplacer le comportement des options -g et -/ avec le style file-patterns. _files devrait donc être préférée à _path_files dans la plupart des cas.

Cette fonction accepte l'ensemble complet des options autorisées par _path_files, décrites ci-dessous.

_gnu_generic
Cette fonction est un simple wrapper autour de la fonction _arguments décrite ci-dessus. Elle peut être utilisée pour déterminer automatiquement les options longues comprises par les commandes qui produisent une liste lorsqu'elles reçoivent l'option `--help'. Elle est destinée à être utilisée comme fonction de complétion de haut niveau en soi. Par exemple, pour activer la complétion des options pour les commandes foo et bar, utilisez
compdef _gnu_generic foo bar

après l'appel à compinit.

Le système de complétion tel qu'il est fourni est conservateur dans son utilisation de cette fonction, car il est important d'être sûr que la commande comprend l'option `--help'.

_guard [ options ] pattern descr
Cette fonction affiche descr si pattern correspond à la chaîne à compléter. Elle est destinée à être utilisée dans l'*action* des spécifications passées à _arguments et fonctions similaires.

Le statut de retour est zéro si le message a été affiché et que le mot à compléter n'est pas vide, et non-zéro sinon.

Le pattern peut être précédé par n'importe laquelle des options comprises par compadd qui sont transmises depuis _description, à savoir -M, -J, -V, -1, -2, -n, -F et -X. Toutes ces options seront ignorées. Cela s'intègre commodément avec les conventions de passage d'arguments des actions pour _arguments.

Par exemple, considérons une commande prenant les options -n et -none, où -n doit être suivi d'une valeur numérique dans le même mot. En utilisant :

_arguments '-n-: :_guard "[0-9]#" "numeric value"' '-none'

_arguments peut à la fois afficher le message `numeric value' et compléter les options après `-n<TAB>'. Si le `-n' est déjà suivi d'un ou plusieurs chiffres (le pattern passé à _guard), seul le message sera affiché ; si le `-n' est suivi d'un autre caractère, seules les options seront complétées.

_message [ -r12 ] [ -VJ group ] descr
_message -e [ tag ] descr
Le descr est utilisé de la même manière que le troisième argument de la fonction _description, sauf que la chaîne résultante sera toujours affichée, que des correspondances aient été générées ou non. Ceci est utile pour afficher un message d'aide là où aucune complétion ne peut être générée.

Le style format est examiné avec l'étiquette messages pour trouver un message ; l'étiquette habituelle, descriptions, n'est utilisée que si le style n'est pas défini avec la première.

Si l'option -r est donnée, aucun style n'est utilisé ; le descr est pris littéralement comme la chaîne à afficher. Ceci est le plus utile lorsque le descr provient d'une liste d'arguments pré-traitée qui contient déjà une description développée. Notez que cette option ne désactive pas l'analyse des séquences `%' effectuée par compadd.

Les options -12VJ et le group sont passées à compadd et déterminent donc le groupe auquel la chaîne de message est ajoutée.

La seconde forme -e donne une description pour les complétions avec l'étiquette tag à afficher même s'il n'y a pas de correspondances pour cette étiquette. Cette forme est appelée par _arguments si aucune action n'est spécifiée pour une option. L'étiquette peut être omise et, dans ce cas, elle est prise du paramètre $curtag ; ceci est maintenu par le système de complétion et est donc généralement correct. Notez que s'il n'y a pas de correspondances au moment où cette fonction est appelée, compstate[insert] est effacé, de sorte que les correspondances supplémentaires générées plus tard ne sont pas insérées dans la ligne de commande.

_multi_parts [ -i ] sep array
L'argument sep est un caractère séparateur. L'array peut être soit le nom d'un paramètre de type tableau, soit un tableau littéral sous la forme `(foo bar)', une liste de mots séparés par des espaces entre parenthèses. Les complétions possibles sont les chaînes du tableau. Cependant, chaque segment délimité par sep sera complété séparément. Par exemple, la fonction _tar utilise `_multi_parts / patharray' pour compléter des chemins de fichiers partiels à partir du tableau donné de chemins de fichiers complets.

L'option -i fait que _multi_parts insère une correspondance unique même si cela nécessite l'insertion de plusieurs séparateurs. Ce n'est généralement pas le comportement attendu avec les noms de fichiers, mais certains autres types de complétion, par exemple ceux avec un ensemble fixe de possibilités, peuvent mieux convenir à cette forme.

Comme les autres fonctions utilitaires, cette fonction accepte les options `-V', `-J', `-1', `-2', `-n', `-f', `-X', `-M', `-P', `-S', `-r', `-R', et `-q' et les passe à l'interne compadd.

_next_label [ -x ] [ -12VJ ] tag name descr [ option ... ]
Cette fonction est utilisée pour implémenter la boucle sur différentes étiquettes de balise pour une balise particulière, comme décrit ci-dessus pour le style tag-order. À chaque appel, elle vérifie s'il reste d'autres étiquettes de balise ; s'il y en a, elle retourne le statut zéro, sinon non-zéro. Comme cette fonction nécessite une balise actuelle définie, elle doit toujours suivre un appel à _tags ou _requested.

Les options -x12VJ et les trois premiers arguments sont passés à la fonction _description. Le cas échéant, le tag sera remplacé par une étiquette de balise dans cet appel. Toute description donnée dans le style tag-order est préférée au descr passé à _next_label.

Les options données après le descr sont définies dans le paramètre donné par name, et sont donc à passer à compadd ou quelle que soit la fonction appelée pour ajouter les correspondances.

Voici une utilisation typique de cette fonction pour la balise foo. L'appel à _requested détermine si la balise foo est nécessaire ; la boucle sur _next_label gère les étiquettes définies pour la balise dans le style tag-order.

local expl ret=1
...
if _requested foo; then
  ...
  while _next_label foo expl '...'; do
    compadd "$expl[@]" ... && ret=0
  done
  ...
fi
return ret
_normal [ -P | -p precommand ]
C'est la fonction standard appelée pour gérer la complétion en dehors de tout -contexte- spécial. Elle est appelée à la fois pour compléter le mot de commande et les arguments d'une commande. Dans le second cas, _normal recherche une complétion spéciale pour cette commande, et s'il n'y en a pas, elle utilise la complétion pour le contexte -default-.

Une deuxième utilisation consiste à réexaminer la ligne de commande spécifiée par le tableau $words et le paramètre $CURRENT après que ceux-ci aient été modifiés. Par exemple, la fonction _precommand, qui complète après les spécificateurs de précommande tels que nohup, supprime le premier mot du tableau words, décrémente le paramètre CURRENT, puis appelle `_normal -p $service'. L'effet est que `nohup cmd ...' est traité de la même manière que `cmd ...'.

-P
Réinitialise la liste des précommandes. Cette option doit être utilisée si l'on complète une ligne de commande qui autorise les commandes internes (par exemple, les builtins et les fonctions) indépendamment des précommandes précédentes (par exemple, `zsh -c').
-p precommand
Ajoute precommand à la liste des précommandes. Cette option doit être utilisée dans presque tous les cas où -P n'est pas applicable.

Si le nom de commande correspond à l'un des motifs donnés par l'une des options -p ou -P de compdef, la fonction de complétion correspondante est appelée, puis le paramètre _compskip est vérifié. S'il est défini, la complétion est terminée à ce moment-là même si aucune correspondance n'a été trouvée. C'est le même effet que dans le contexte -first-.

_numbers [ option ... ] [ description ] [ suffixe ... ]
Ceci peut être utilisé lorsque un nombre est suivi d'un suffixe pour indiquer les unités. Les suffixes d'unité sont complétés et peuvent également être inclus dans la description utilisée lorsque la complétion est invoquée pour le nombre précédent.

En plus des options courantes de compadd, _numbers accepte les options suivantes :

-t tag
Spécifie une balise à utiliser à la place de celle par défaut numbers.
-u units
Indique les unités par défaut pour le nombre, par exemple bytes.
-l min
Spécifie la plus petite valeur possible pour le nombre.
-m max
Spécifie la plus grande valeur possible pour le nombre.
-d default
Spécifie la valeur par défaut.
-N
Autorise les nombres négatifs. Ceci est implicite si la plage inclut un nombre négatif.
-f
Autorise les nombres décimaux.

Lorsqu'un suffixe particulier représente les unités par défaut pour un nombre, il doit être précédé de deux-points. De plus, les suffixes peuvent être suivis de deux-points et d'une description. Ainsi, par exemple, ce qui suit permet de spécifier l'âge de quelque chose, soit en secondes, soit avec un suffixe optionnel avec une unité de temps plus longue :

_numbers -u seconds age :s:seconds m:minutes h:hours d:days

Il est généralement utile que les unités soient présentées par ordre de grandeur lors de la complétion. Pour faciliter cela, l'ordre dans lequel elles sont données est préservé.

Lorsque le style format est recherché avec la balise descriptions ou la balise spécifiée avec -t, la liste des suffixes est disponible sous forme de séquence d'échappement `%x'. Ceci s'ajoute aux séquences habituelles documentées sous le style format. La forme que prend cette liste peut également être configurée. À cette fin, le style format est d'abord recherché avec la balise unit-suffixes. Le format récupéré est appliqué à chaque suffixe tour à tour et les résultats sont ensuite concaténés pour former la liste complétée. Pour le style unit-suffixes, `%x' s'étend au suffixe individuel et `%X' à sa description. `%d' indique un suffixe par défaut et peut être utilisé dans une condition. L'indice et l'indice inversé sont définis dans `%i' et `%r' respectivement et sont utiles pour le texte inclus uniquement avec les premiers et derniers suffixes de la liste. Ainsi, par exemple, ce qui suit joint les suffixes sous forme de liste séparée par des virgules :

zstyle ':completion:*:unit-suffixes' format '%x%(r::,)'
_options
Ceci peut être utilisé pour compléter les noms des options du shell. Il fournit une spécification de correspondance qui ignore un préfixe `no', ignore les underscores et autorise les lettres majuscules à correspondre à leurs homologues minuscules (par exemple, `glob', `noglob', `NO_GLOB' sont tous complétés). Tous les arguments sont propagés au builtin compadd.
_options_set et _options_unset
Ces fonctions complètent uniquement les options définies ou non définies, avec la même spécification de correspondance utilisée dans la fonction _options.

Notez que vous devez décommenter quelques lignes dans la fonction _main_complete pour que ces fonctions fonctionnent correctement. Les lignes en question sont utilisées pour stocker les paramètres des options en vigueur avant que le widget de complétion ne définisse localement les options dont il a besoin. Par conséquent, ces fonctions ne sont généralement pas utilisées par le système de complétion.

_parameters
Ceci est utilisé pour compléter les noms des paramètres du shell.

L'option `-g pattern' limite la complétion aux paramètres dont le type correspond au pattern. Le type d'un paramètre est celui affiché par `print ${(t)param}', donc une utilisation judicieuse de `*' dans pattern est probablement nécessaire.

Tous les autres arguments sont passés au builtin compadd.

_path_files
Cette fonction est utilisée dans tout le système de complétion pour compléter les noms de fichiers. Elle permet la complétion de chemins partiels. Par exemple, la chaîne `/u/i/s/sig' peut être complétée en `/usr/include/sys/signal.h'.

Les options acceptées par _path_files et _files sont :

-f
Complète tous les noms de fichiers. C'est le défaut.
-/
Spécifie que seuls les répertoires doivent être complétés.
-g pattern
Spécifie que seuls les fichiers correspondant au pattern doivent être complétés.
-W paths
Spécifie les préfixes de chemin qui doivent être ajoutés au début de la chaîne de la ligne de commande pour générer les noms de fichiers mais qui ne doivent pas être insérés comme complétions ni affichés dans les listes de complétion. Ici, paths peut être le nom d'un paramètre tableau, une liste littérale de chemins entre parenthèses ou un nom de chemin absolu.
-F ignored-files
Ceci se comporte comme pour l'option correspondante du builtin compadd. Il donne un contrôle direct sur les noms de fichiers qui doivent être ignorés. Si l'option n'est pas présente, le style ignored-patterns est utilisé.

_path_files et _files acceptent également les options suivantes qui sont passées à compadd : `-J', `-V', `-1', `-2', `-n', `-X', `-M', `-P', `-S', `-q', `-r', et `-R'.

Enfin, la fonction _path_files utilise les styles expand, ambiguous, special-dirs, list-suffixes et file-sort décrits ci-dessus.

_pick_variant [ -b builtin-label ] [ -c command ] [ -r name ]
label=pattern ... label [ arg ... ]
Cette fonction est utilisée pour résoudre les situations où un seul nom de commande nécessite plus d'un type de traitement, soit parce qu'il a plus d'une variante, soit parce qu'il y a un conflit de noms entre deux commandes différentes.

La commande à exécuter est prise du premier élément du tableau words, sauf si cela est remplacé par l'option -c. Cette commande est exécutée et sa sortie est comparée à une série de motifs. Les arguments à passer à la commande peuvent être spécifiés à la fin après tous les autres arguments. Les motifs à essayer dans l'ordre sont donnés par les arguments label=pattern ; si la sortie de `command arg ...' contient pattern, alors label est sélectionné comme étiquette pour la variante de commande. Si aucun des motifs ne correspond, l'étiquette de commande finale est sélectionnée et le statut 1 est retourné.

Si l'option `-b builtin-label' est donnée, la commande est testée pour voir si elle est fournie comme un builtin du shell, éventuellement autoloadée ; si c'est le cas, l'étiquette builtin-label est sélectionnée comme étiquette pour la variante.

Si l'option `-r name' est donnée, l'label choisi est stocké dans le paramètre nommé name.

Les résultats sont également mis en cache dans le tableau associatif _cmd_variant indexé par le nom de la commande exécutée.

_regex_arguments name spec ...
Cette fonction génère une fonction de complétion name qui correspond aux spécifications specs, un ensemble d'expressions régulières comme décrit ci-dessous. Après avoir exécuté _regex_arguments, la fonction name doit être appelée comme une fonction de complétion normale. Le motif à faire correspondre est donné par le contenu du tableau words jusqu'à la position actuelle du curseur, joint avec des caractères nuls ; aucune citation n'est appliquée.

Les arguments sont regroupés en ensembles d'alternatives séparées par `|', qui sont essayées les unes après les autres jusqu'à ce que l'une corresponde. Chaque alternative consiste en une ou plusieurs spécifications qui sont essayées de gauche à droite, chaque motif correspondant étant retiré à tour de rôle de la ligne de commande testée, jusqu'à ce que tout le groupe réussisse ou jusqu'à ce que l'un échoue ; dans ce dernier cas, l'alternative suivante

Le _regex_arguments est une fonction utilitaire pour définir des règles de complétion complexes basées sur des motifs d'expressions régulières. La fonction est appelée comme suit: 
_regex_arguments fonction spec ...
Où fonction est le nom de la fonction de complétion à définir, et spec ... sont une série d'arguments qui décrivent les motifs et les actions à effectuer. La structure des spec peut être imbriquée à l'aide de parenthèses; la correspondance progresse de l'intérieur vers l'extérieur. Un traitement spécial est appliqué si aucun test ne réussit mais que la chaîne de ligne de commande restante ne contient aucun caractère nul (impliquant que le mot restant est celui pour lequel les complétions doivent être générées). La cible de complétion est limitée au mot restant et toutes les actions pour les motifs correspondants sont exécutées. Dans ce cas, rien n'est retiré de la chaîne de ligne de commande. L'ordre d'évaluation des actions peut être déterminé par le style tag-order; les divers formats pris en charge par _alternative peuvent être utilisés dans action. Le descr est utilisé pour configurer le paramètre de tableau expl. Les arguments de spécification prennent l'une des formes suivantes, dans lesquelles les métacaractères tels que `(', `)', `#' et `|' doivent être mis entre guillemets.
/pattern/ [%lookahead%] [-guard] [:tag:descr:action]
Ceci est un composant primitif unique. La fonction teste si le motif combiné `(#b)((#B)pattern)lookahead*' correspond à la chaîne de ligne de commande. Si c'est le cas, 'guard' est évalué et son statut de retour est examiné pour déterminer si le test a réussi. La chaîne de pattern `[]' ne correspond jamais. Le lookahead n'est pas retiré de la ligne de commande avant que le motif suivant ne soit examiné.

L'argument commençant par : est utilisé de la même manière qu'un argument pour _alternative.

Un composant est utilisé comme suit : pattern est testé pour voir si le composant existe déjà sur la ligne de commande. S'il existe, les spécifications suivantes sont examinées pour trouver quelque chose à compléter. Si un composant est atteint mais qu'aucun motif de ce type n'existe encore sur la ligne de commande, la chaîne contenant l'action est utilisée pour générer des correspondances à insérer à cet endroit.

/pattern/+ [%lookahead%] [-guard] [:tag:descr:action]
Ceci est similaire à `/pattern/ ...' mais la partie gauche de la chaîne de ligne de commande (c'est-à-dire la partie déjà correspondue par les motifs précédents) est également considérée comme faisant partie de la cible de complétion.
/pattern/- [%lookahead%] [-guard] [:tag:descr:action]
Ceci est similaire à `/pattern/ ...' mais les actions du composant actuel et des composants précédemment correspondus sont ignorées même si le `pattern' suivant correspond à la chaîne vide.
( spec )
Les parenthèses peuvent être utilisées pour regrouper des specs; notez que chaque parenthèse est un seul argument pour _regex_arguments.
spec #
Ceci permet un nombre quelconque de répétitions de spec.
spec spec
Les deux specs doivent correspondre l'une après l'autre comme décrit ci-dessus.
spec | spec
L'un ou l'autre des deux specs peut correspondre.

La fonction _regex_words peut être utilisée comme fonction d'aide pour générer des correspondances pour un ensemble de mots alternatifs éventuellement avec leurs propres arguments en tant qu'argument de ligne de commande.

Exemples:

_regex_arguments _tst /$'[^\0]#\0'/ \ 
    /$'[^\0]#\0'/ :'compadd aaa'

Ceci génère une fonction _tst qui complète aaa comme seul argument. Le tag et la description pour l'action ont été omis par souci de brièveté (cela fonctionne mais n'est pas recommandé en usage normal). Le premier composant correspond au mot de commande, qui est arbitraire; le second correspond à n'importe quel argument. Comme l'argument est également arbitraire, tout composant suivant ne dépendrait pas de la présence de aaa.

_regex_arguments _tst /$'[^\0]#\0'/ \ 
    /$'aaa\0'/ :'compadd aaa'

C'est une utilisation plus typique; elle est similaire, mais tous les motifs suivants ne correspondront que si aaa est présent comme premier argument.

_regex_arguments _tst /$'[^\0]#\0'/ \( \ 
    /$'aaa\0'/ :'compadd aaa' \ 
    /$'bbb\0'/ :'compadd bbb' \) \#

Dans cet exemple, un nombre indéfini d'arguments de commande peut être complété. Les arguments impairs sont complétés comme aaa et les arguments pairs comme bbb. La complétion échoue à moins que l'ensemble des arguments aaa et bbb avant celui en cours ne corresponde correctement.

_regex_arguments _tst /$'[^\0]#\0'/ \ 
    \( /$'aaa\0'/ :'compadd aaa' \| \ 
    /$'bbb\0'/ :'compadd bbb' \) \#

Ceci est similaire, mais soit aaa soit bbb peut être complété pour n'importe quel argument. Dans ce cas, _regex_words pourrait être utilisé pour générer une expression appropriée pour les arguments.

_regex_words tag description spec ...
Cette fonction peut être utilisée pour générer des arguments pour la commande _regex_arguments qui peuvent être insérés à tout endroit où un ensemble de règles est attendu. Le tag et la description donnent un tag et une description standard relatifs au contexte actuel. Chaque spec contient deux ou trois arguments séparés par un deux-points: notez qu'il n'y a pas de deux-points en tête dans ce cas.

Chaque spec donne l'un d'un ensemble de mots qui peuvent être complétés à cet endroit, avec des arguments. Il est donc à peu près équivalent à la fonction _arguments lorsqu'elle est utilisée dans la complétion normale (non-regex).

La partie du spec avant le premier deux-points est le mot à compléter. Cela peut contenir un *; le mot entier, avant et après le * est complété, mais seul le texte avant le * est requis pour que le contexte corresponde, de sorte que des arguments supplémentaires puissent être complétés après la forme abrégée.

La deuxième partie du spec est une description du mot en cours de complétion.

La troisième partie optionnelle du spec décrit comment les mots suivant celui en cours de complétion doivent eux-mêmes être complétés. Elle sera évaluée dans l'ordre pour éviter les problèmes de guillemets. Cela signifie qu'elle contient généralement une référence à un tableau contenant des arguments regex précédemment générés.

L'option -t term spécifie un terminateur pour le mot au lieu de l'espace habituel. Ceci est géré comme un suffixe auto-amovible de la manière de l'option -s sep de _values.

Le résultat du traitement par _regex_words est placé dans le tableau reply, qui doit être rendu local à la fonction appelante. Si l'ensemble des mots et des arguments peut être correspondu de manière répétée, un # doit être ajouté au tableau généré à cet endroit.

Par exemple:

local -a reply
_regex_words mydb-commands 'mydb commands' \ 
  'add:add an entry to mydb:$mydb_add_cmds' \ 
  'show:show entries in mydb'
_regex_arguments _mydb "$reply[@]"
_mydb "$@"

Ceci montre une fonction de complétion pour une commande mydb qui prend deux arguments de commande, add et show. show ne prend aucun argument, tandis que les arguments pour add ont déjà été préparés dans un tableau mydb_add_cmds, très probablement par un appel précédent à _regex_words.

_requested [ -x ] [ -12VJ ] tag [ name descr [ command [ arg ... ] ]]
Cette fonction est appelée pour décider si un tag déjà enregistré par un appel à _tags (voir ci-dessous) a été demandé par l'utilisateur et donc si la complétion doit être effectuée pour celui-ci. Elle renvoie le statut zéro si le tag est demandé et non-zéro sinon. La fonction est typiquement utilisée dans le cadre d'une boucle sur différents tags comme suit:
_tags foo bar baz
while _tags; do
  if _requested foo; then
    ... # effectuer la complétion pour foo
  fi
  ... # tester les tags bar et baz de la même manière
  ... # sortir de la boucle si des correspondances ont été générées
done

Notez que le test pour savoir si des correspondances ont été générées n'est pas effectué avant la fin de la boucle _tags. Ceci afin que l'utilisateur puisse définir le style tag-order pour spécifier un ensemble de tags à compléter en même temps.

Si name et descr sont donnés, _requested appelle la fonction _description avec ces arguments ainsi que les options passées à _requested.

Si command est donné, la fonction _all_labels sera appelée immédiatement avec les mêmes arguments. Dans des cas simples, cela permet d'effectuer le test pour le tag et la correspondance en une seule fois. Par exemple:

local expl ret=1
_tags foo bar baz
while _tags; do
  _requested foo expl 'description' \ 
      compadd foobar foobaz && ret=0
  ...
  (( ret )) || break
done

Si la commande n'est pas compadd, elle doit néanmoins être capable de gérer les mêmes options.

_retrieve_cache cache_identifier
Cette fonction récupère les informations de complétion à partir du fichier donné par cache_identifier, stocké dans un répertoire spécifié par le style cache-path qui, par défaut, est ~/.zcompcache. Le statut de retour est zéro si la récupération a réussi. Elle ne tentera la récupération que si le style use-cache est défini, vous pouvez donc appeler cette fonction sans vous soucier si l'utilisateur souhaitait utiliser la couche de mise en cache.

Voir _store_cache ci-dessous pour plus de détails.

_sep_parts
Cette fonction reçoit des tableaux et des séparateurs en alternance comme arguments. Les tableaux spécifient les complétions pour les parties de chaînes à séparer par les séparateurs. Les tableaux peuvent être les noms de paramètres de tableaux ou une liste de mots entre guillemets entre parenthèses. Par exemple, avec le tableau `hosts=(ftp news)' l'appel `_sep_parts '(foo bar)' @ hosts' complétera la chaîne `f' par `foo' et la chaîne `b@n' par `bar@news'.

Cette fonction accepte les options compadd `-V', `-J', `-1', `-2', `-n', `-X', `-M', `-P', `-S', `-r', `-R', et `-q' et les transmet à la commande interne compadd utilisée pour ajouter les correspondances.

_sequence [ -s sep ] [ -n max ] [ -d ] function [ - ] ...
Cette fonction est un wrapper pour d'autres fonctions permettant de compléter des éléments dans une liste séparée. La même fonction est utilisée pour compléter chaque élément de la liste. Le séparateur est spécifié avec l'option -s. Si -s est omis, il utilisera `,'. Les valeurs dupliquées ne sont pas correspondantes, sauf si -d est spécifié. S'il y a un nombre fixe ou maximum d'éléments dans la liste, cela peut être spécifié avec l'option -n.

Les options courantes de compadd sont transmises à la fonction. Il est possible d'utiliser compadd directement avec _sequence, bien que _values puisse être plus approprié dans cette situation.

_setup tag [ group ]
Cette fonction configure les paramètres spéciaux utilisés par le système de complétion de manière appropriée pour le tag donné comme premier argument. Elle utilise les styles list-colors, list-packed, list-rows-first, last-prompt, accept-exact, menu et force-list.

Le group optionnel fournit le nom du groupe dans lequel les correspondances seront placées. S'il n'est pas donné, le tag est utilisé comme nom de groupe.

Cette fonction est appelée automatiquement à partir de _description et n'est donc normalement pas appelée explicitement.

_store_cache cache_identifier param ...
Cette fonction, avec _retrieve_cache et _cache_invalid, implémente une couche de mise en cache qui peut être utilisée dans toute fonction de complétion. Les données obtenues par des opérations coûteuses sont stockées dans des paramètres ; cette fonction enregistre ensuite les valeurs de ces paramètres dans un fichier. Les données peuvent ensuite être récupérées rapidement de ce fichier via _retrieve_cache, même dans différentes instances du shell.

L'cache_identifier spécifie le fichier dans lequel les données doivent être enregistrées. Le fichier est stocké dans un répertoire spécifié par le style cache-path qui est par défaut ~/.zcompcache. Les autres arguments param sont les paramètres à enregistrer dans le fichier.

Le statut de retour est zéro si le stockage a réussi. La fonction ne tentera le stockage que si le style use-cache est défini, vous pouvez donc appeler cette fonction sans vous soucier de savoir si l'utilisateur voulait utiliser la couche de mise en cache.

La fonction de complétion peut éviter d'appeler _retrieve_cache lorsqu'elle dispose déjà des données de complétion sous forme de paramètres. Cependant, dans ce cas, elle devrait appeler _cache_invalid pour vérifier si les données dans les paramètres et dans le cache sont toujours valides.

Voir la fonction de complétion _perl_modules pour un exemple simple d'utilisation de la couche de mise en cache.

_tags [ [ -C name ] tag ... ]
Si appelée avec des arguments, ceux-ci sont considérés comme les noms des tags valides pour les complétions dans le contexte actuel. Ces tags sont stockés en interne et triés en utilisant le style tag-order.

Ensuite, _tags est appelée de manière répétée sans arguments par la même fonction de complétion. Cela sélectionne successivement le premier, le deuxième, etc. ensemble de tags demandés par l'utilisateur. Le statut de retour est zéro si au moins un des tags est demandé et non nul sinon. Pour tester si un tag particulier est à essayer, la fonction _requested doit être appelée (voir ci-dessus).

Si `-C name' est donné, name est temporairement stocké dans le champ argument (le cinquième) du contexte dans le paramètre curcontext pendant l'appel à _tags ; le champ est restauré à la sortie. Cela permet à _tags d'utiliser un contexte plus spécifique sans avoir à modifier et réinitialiser le paramètre curcontext (ce qui a le même effet).

_tilde_files
Similaire à _files, mais résout les tildes en tête selon les règles d'expansion des noms de fichiers, de sorte que les complétions suggérées ne commencent pas par un `~' même si le nom de fichier sur la ligne de commande le fait.
_values [ -O name ] [ -s sep ] [ -S sep ] [ -wC ] desc spec ...
Ceci est utilisé pour compléter des mots-clés arbitraires (valeurs) et leurs arguments, ou des listes de telles combinaisons.

Si le premier argument est l'option `-O name', il sera utilisé de la même manière que par la fonction _arguments. Autrement dit, les éléments du tableau name seront passés à compadd lors de l'exécution d'une action.

Si le premier argument (ou le premier argument après `-O name') est `-s', l'argument suivant est utilisé comme caractère qui sépare plusieurs valeurs. Ce caractère est automatiquement ajouté après chaque valeur de manière auto-amovible (voir ci-dessous) ; toutes les valeurs complétées par `_values -s' apparaissent dans le même mot sur la ligne de commande, contrairement à la complétion utilisant _arguments. Si cette option n'est pas présente, seule une seule valeur sera complétée par mot.

Normalement, _values n'utilisera que le mot courant pour déterminer quelles valeurs sont déjà présentes sur la ligne de commande et ne doivent donc pas être à nouveau complétées. Si l'option -w est donnée, d'autres arguments sont également examinés.

Le premier argument sans option, desc, est utilisé comme une chaîne de caractères à imprimer comme description avant de lister les valeurs.

Tous les autres arguments décrivent les valeurs possibles et leurs arguments dans le même format utilisé pour la description des options par la fonction _arguments (voir ci-dessus). Les seules différences sont qu'aucun signe moins ou plus n'est requis au début, les valeurs ne peuvent avoir qu'un seul argument, et les formes d'action commençant par un signe égal ne sont pas supportées.

Le caractère séparant une valeur de son argument peut être défini en utilisant l'option -S (comme -s, suivi du caractère à utiliser comme séparateur dans l'argument suivant). Par défaut, le signe égal sera utilisé comme séparateur entre les valeurs et les arguments.

Exemple :

_values -s , 'description' \ 
        '*foo[bar]' \ 
        '(two)*one[number]:first count:' \ 
        'two[another number]::second count:(1 2 3)'

Ceci décrit trois valeurs possibles : `foo', `one', et `two'. La première est décrite comme `bar', ne prend pas d'argument et peut apparaître plus d'une fois. La deuxième est décrite comme `number', peut apparaître plus d'une fois, et prend un argument obligatoire décrit comme `first count' ; aucune action n'est spécifiée, elle ne sera donc pas complétée. Le `(two)' au début indique que si la valeur `one' est sur la ligne, la valeur `two' ne sera plus considérée comme une complétion possible. Enfin, la dernière valeur (`two') est décrite comme `another number' et prend un argument optionnel décrit comme `second count' pour lequel les complétions (à apparaître après un `=') sont `1', `2', et `3'. La fonction _values complétera des listes de ces valeurs séparées par des virgules.

Comme _arguments, cette fonction ajoute temporairement un autre composant de nom de contexte aux arguments de l'élément (le cinquième) du contexte actuel lors de l'exécution de l'*action*. Ici, ce nom est simplement le nom de la valeur pour laquelle l'argument est complété.

Le style verbose est utilisé pour décider si les descriptions des valeurs (mais pas celles des arguments) doivent être imprimées.

Le tableau associatif val_args est utilisé pour rapporter les valeurs et leurs arguments ; cela fonctionne de manière similaire au tableau associatif opt_args utilisé par _arguments. Par conséquent, la fonction appelant _values doit déclarer les paramètres locaux state, state_descr, line, context et val_args :

local context state state_descr line
typeset -A val_args

lorsqu'elle utilise une action de la forme `->string'. Avec cette fonction, le paramètre context sera défini sur le nom de la valeur dont l'argument doit être complété. Notez que pour _values, state et state_descr sont des scalaires plutôt que des tableaux. Un seul état correspondant est retourné.

Notez également que _values ajoute normalement le caractère utilisé comme séparateur entre les valeurs comme suffixe auto-amovible (similaire à un `/' après un répertoire). Cependant, ce n'est pas possible pour une action `->string' car les correspondances pour l'argument sont générées par la fonction appelante. Pour obtenir le comportement habituel, la fonction appelante peut ajouter le séparateur x comme suffixe en passant les options `-qS x' directement ou indirectement à compadd.

L'option -C est traitée de la même manière qu'elle l'est par _arguments. Dans ce cas, le paramètre curcontext doit être rendu local au lieu de context (comme décrit ci-dessus).

_wanted [ -x ] [ -C name ] [ -12VJ ] tag name descr command [ arg ...]
Dans de nombreux contextes, la complétion ne peut générer qu'un ensemble particulier de correspondances, correspondant généralement à un seul tag. Cependant, il est toujours nécessaire de décider si l'utilisateur nécessite des correspondances de ce type. Cette fonction est utile dans un tel cas.

Les arguments de _wanted sont les mêmes que ceux de _requested, c'est-à-dire les arguments à passer à _description. NAME

zshcompsys — Zsh completion system

DESCRIPTION

This manual page describes the Zsh completion system, which allows the shell to provide completion matches for commands, arguments, filenames, and so on.

The completion system is built around a central function, _main_complete, which is responsible for calling completion functions for particular commands. Completion functions themselves are typically provided by a hierarchy of other functions.

INITIALIZATION

The completion system is typically initialized by calling the function compinit. This function reads the Zsh function path ($fpath) for files that are marked as completion functions (usually by having a name starting with an underscore). It then performs various initial setup tasks, including:

  • Scanning the function path for existing completion functions.
  • Disabling shell options that interfere with completions (e.g. HISTVERIFY).
  • Setting up the internal data structures for the completion system.
  • Loading any completion functions that are required by default.

compinit can be called with a number of options to control its behaviour. See the zshcompwid(1) manual page for details.

COMPLETION SYSTEM CONFIGURATION

The completion system can be configured by setting certain variables and by adding functions to specific arrays.

fpath
The completion functions are searched for in the directories listed in $fpath. For the completion system to work, these directories must contain the necessary completion functions, organised in a specific structure. See the section on Completion Directories below.
_compsys_complete
This is the main completion function called by the shell when completion is invoked. It is usually set up by compinit.
_compsys_setup
This function is called by _compsys_complete to set up the completion environment for a specific command. It reads completion definitions from files in the completion directories.

CONTROL FUNCTIONS

These functions are used to control the behaviour of the completion system.

compinit
Initialises the completion system. It scans the directories in $fpath for completion functions and sets up the necessary internal data structures.
compdef
Associates a completion function with a command. For example, compdef _git git associates the completion function _git with the command git.
compmessage
Displays a message to the user during completion. This is useful for indicating that completion is in progress or that an error has occurred.
compstate
Sets or retrieves the current completion state. This can be used to control the behaviour of completion functions.
compadd
Adds completion matches to the list of possible completions. This is the primary way that completion functions generate matches.

BINDABLE COMMANDS

The following commands can be bound to keys using the shell's key-binding mechanism (e.g., using bindkey).

completions-around-self
Insert all completions available at the current cursor position.
complete-word
Complete the word at the current cursor position.
expand-or-complete
Complete the word at the current cursor position. If the word is already fully completed, attempt to expand it to show all possible completions.
menu-complete
Complete the word at the current cursor position, cycling through the possible completions one by one.
menu-complete-down
Cycle forward through the possible completions for the word at the current cursor position.
menu-complete-up
Cycle backward through the possible completions for the word at the current cursor position.
complete-manual
Expand the word at the current cursor position to show all possible completions.

UTILITY FUNCTIONS

These are helper functions used by completion functions to perform common tasks.

_call_program
Calls an external program to generate completion matches. This is often used to get completions from programs that have built-in completion support (e.g., git, docker).
_describe
Describes a set of completion matches. This is used to provide additional information about the matches, such as their type or a short description.
_files
Provides completion for filenames and directories. This is a general-purpose function that can be used in most situations where file completion is needed.
_options
Provides completion for command-line options. This function is typically used to complete options for a specific command.
_arguments
A powerful function for defining the structure of command-line arguments and their corresponding completions. It allows for complex argument parsing and completion logic to be defined in a declarative way.
_main_complete
The main completion dispatch function. It determines which completion function to call based on the current command and context.
_call_fdsafe
A wrapper around _call_program that ensures file descriptors are handled safely when calling external programs.
_retrieve_completions
Retrieves completions from a program that supports completion via standard input/output. This is often used for programs that don't have a dedicated completion command-line interface.

See also the zshzle(1) manual page for descriptions of other built-in commands and functions, including those related to the Zsh Line Editor (ZLE) and the zshmodules(1) manual page for details on the zsh/zleparameter Module.

COMPLETION SYSTEM VARIABLES

There are some standard variables, initialised by the _main_complete function and then used from other functions.

The standard variables are:

_comp_caller_options
The completion system uses setopt to set a number of options. This allows functions to be written without concern for compatibility with every possible combination of user options. However, sometimes completion needs to know what the user's option preferences are. These are saved in the _comp_caller_options associative array. Option names, spelled in lowercase without underscores, are mapped to one or other of the strings `on' and `off'.
_comp_priv_prefix
Completion functions such as _sudo can set the _comp_priv_prefix array to a command prefix that may then be used by _call_program to match the privileges when calling programs to generate matches.

Two more features are offered by the _main_complete function. The arrays compprefuncs and comppostfuncs may contain names of functions that are to be called immediately before or after completion has been tried. A function will only be called once unless it explicitly reinserts itself into the array.

COMPLETION DIRECTORIES

In the source distribution, the files are contained in various subdirectories of the Completion directory. They may have been installed in the same structure, or into one single function directory. The following is a description of the files found in the original directory structure. If you wish to alter an installed file, you will need to copy it to some directory which appears earlier in your fpath than the standard directory where it appears.

Base
The core functions and special completion widgets automatically bound to keys. You will certainly need most of these, though will probably not need to alter them. Many of these are documented above.
Zsh
Functions for completing arguments of shell builtin commands and utility functions for this. Some of these are also used by functions from the Unix directory.
Unix
Functions for completing arguments of external commands and suites of commands. They may need modifying for your system, although in many cases some attempt is made to decide which version of a command is present. For example, completion for the mount command tries to determine the system it is running on, while completion for many other utilities try to decide whether the GNU version of the command is in use, and hence whether the --help option is supported.
X, AIX, BSD, ...
Completion and utility function for commands available only on some systems. These are not arranged hierarchically, so, for example, both the Linux and Debian directories, as well as the X directory, may be useful on your system.
