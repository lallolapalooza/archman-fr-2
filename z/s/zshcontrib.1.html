NOM

zshcontrib - contributions utilisateur à zsh

DESCRIPTION

La distribution source de Zsh inclut un certain nombre d'éléments contribués par la communauté d'utilisateurs. Ceux-ci ne font pas intrinsèquement partie du shell, et certains peuvent ne pas être disponibles dans toutes les installations zsh. Les plus significatifs d'entre eux sont documentés ici. Pour la documentation sur d'autres éléments contribués tels que les fonctions shell, recherchez les commentaires dans les fichiers source des fonctions.

UTILITAIRES

Accès à l'aide en ligne

La séquence de touches ESC h est normalement liée par ZLE pour exécuter le widget run-help (voir zshzle(1)). Ceci invoque la commande run-help avec le mot commande de la ligne d'entrée courante comme argument. Par défaut, run-help est un alias de la commande man, donc cela échoue souvent lorsque le mot commande est un builtin shell ou une fonction définie par l'utilisateur. En redéfinissant l'alias run-help, on peut améliorer l'aide en ligne fournie par le shell.

L'utilitaire helpfiles, trouvé dans le répertoire Util de la distribution, est un programme Perl qui peut être utilisé pour traiter le manuel de zsh afin de produire un fichier d'aide séparé pour chaque builtin shell et pour de nombreuses autres fonctionnalités shell également. La fonction run-help autoloadable, trouvée dans Functions/Misc, recherche ces fichiers d'aide et effectue plusieurs autres tests pour produire l'aide la plus complète possible pour la commande.

Les fichiers d'aide sont installés par défaut dans un sous-répertoire de /usr/share/zsh ou /usr/local/share/zsh.

Pour créer vos propres fichiers d'aide avec helpfiles, choisissez ou créez un répertoire où résideront les fichiers d'aide de chaque commande. Par exemple, vous pourriez choisir ~/zsh_help. Si vous avez décompressé la distribution zsh dans votre répertoire personnel, vous utiliseriez les commandes :

mkdir ~/zsh_help
perl ~/zsh-5.9/Util/helpfiles ~/zsh_help

Le paramètre HELPDIR indique à run-help où chercher les fichiers d'aide. Lorsqu'il n'est pas défini, il utilise le chemin d'installation par défaut. Pour utiliser votre propre ensemble de fichiers d'aide, définissez-le sur le chemin approprié dans l'un de vos fichiers de démarrage :

HELPDIR=~/zsh_help

Pour utiliser la fonction run-help, vous devez ajouter des lignes similaires à celles ci-dessous à votre fichier .zshrc ou équivalent :

unalias run-help
autoload run-help

Notez que pour que `autoload run-help' fonctionne, le fichier run-help doit se trouver dans l'un des répertoires nommés dans votre tableau fpath (voir zshparam(1)). Cela devrait déjà être le cas si vous avez une installation zsh standard ; sinon, copiez Functions/Misc/run-help dans un répertoire approprié.

Recompilation des fonctions

Si vous modifiez fréquemment vos fonctions zsh, ou si vous mettez à jour périodiquement votre installation zsh pour suivre les derniers développements, vous pourriez constater que les digests de fonctions compilés avec le builtin zcompile sont souvent obsolètes par rapport aux fichiers source des fonctions. Ce n'est généralement pas un problème, car zsh recherche toujours le fichier le plus récent lors du chargement d'une fonction, mais cela peut entraîner un démarrage plus lent du shell et du chargement des fonctions. De plus, si un fichier de digest est explicitement utilisé comme élément de fpath, zsh ne vérifiera pas si l'un de ses fichiers source a changé.

La fonction autoloadable zrecompile, trouvée dans Functions/Misc, peut être utilisée pour maintenir à jour les digests des fonctions.

zrecompile [ -qt ] [ nom ... ]
zrecompile [ -qt ] -p arg ... [ -- arg ... ]
Ceci essaie de trouver des fichiers *.zwc et de les recompiler automatiquement si au moins un des fichiers d'origine est plus récent que le fichier compilé. Ceci ne fonctionne que si les noms stockés dans les fichiers compilés sont des chemins absolus ou relatifs au répertoire contenant le fichier .zwc.

Dans la première forme, chaque nom est le nom d'un fichier compilé ou d'un répertoire contenant des fichiers *.zwc qui devraient être vérifiés. Si aucun argument n'est donné, les répertoires et les fichiers *.zwc dans fpath sont utilisés.

Lorsque -t est donné, aucune compilation n'est effectuée, mais un statut de retour de zéro (vrai) est défini s'il y a des fichiers qui nécessitent une recompilation et non-zéro (faux) sinon. L'option -q rend silencieux la sortie verbeuse décrivant ce que fait zrecompile.

Sans l'option -t, le statut de retour est zéro si tous les fichiers qui nécessitaient une recompilation ont pu être compilés et non-zéro si la compilation pour au moins un des fichiers a échoué.

Si l'option -p est donnée, les args sont interprétés comme un ou plusieurs ensembles d'arguments pour zcompile, séparés par `--'. Par exemple :

zrecompile -p \ 
           -R ~/.zshrc -- \ 
           -M ~/.zcompdump -- \ 
           ~/zsh/comp.zwc ~/zsh/Completion/*/_*

Ceci compile ~/.zshrc en ~/.zshrc.zwc si ce dernier n'existe pas ou s'il est plus ancien que ~/.zshrc. Le fichier compilé sera marqué pour la lecture au lieu du mappage. Il en va de même pour ~/.zcompdump et ~/.zcompdump.zwc, mais ce fichier compilé est marqué pour le mappage. La dernière ligne recrée le fichier ~/zsh/comp.zwc si l'un des fichiers correspondant au motif donné est plus récent que lui.

Sans l'option -p, zrecompile ne crée pas de digests de fonctions qui n'existent pas déjà, et n'ajoute pas de nouvelles fonctions au digest.

La boucle shell suivante est un exemple de méthode pour créer des digests de fonctions pour toutes les fonctions de votre fpath, en supposant que vous ayez les droits d'écriture dans les répertoires :

for ((i=1; i <= $#fpath; ++i)); do
  dir=$fpath[i]
  zwc=${dir:t}.zwc
  if [[ $dir == (.|..) || $dir == (.|..)/* ]]; then
    continue
  fi
  files=($dir/*(N-.))
  if [[ -w $dir:h && -n $files ]]; then
    files=(${${(M)files%/*/*}#/})
    if ( cd $dir:h &&
         zrecompile -p -U -z $zwc $files ); then
      fpath[i]=$fpath[i].zwc
    fi
  fi
done

Les options -U et -z sont appropriées pour les fonctions dans le fpath de l'installation zsh par défaut ; vous devrez peut-être utiliser des options différentes pour vos répertoires de fonctions personnels.

Une fois les digests créés et votre fpath modifié pour y faire référence, vous pouvez les maintenir à jour en exécutant zrecompile sans arguments.

Définition du clavier

Le grand nombre de combinaisons possibles de claviers, stations de travail, terminaux, émulateurs et systèmes de fenêtrage rend impossible pour zsh d'avoir des liaisons de touches intégrées pour chaque situation. L'utilitaire zkbd, trouvé dans Functions/Misc, peut vous aider à créer rapidement des liaisons de touches pour votre configuration.

Exécutez zkbd soit en tant que fonction autoloadable, soit en tant que script shell :

zsh -f ~/zsh-5.9/Functions/Misc/zkbd

Lorsque vous exécutez zkbd, il vous demande d'abord d'entrer votre type de terminal ; si celui par défaut qu'il propose est correct, appuyez simplement sur Entrée. Il vous demande ensuite d'appuyer sur un certain nombre de touches différentes pour déterminer les caractéristiques de votre clavier et de votre terminal ; zkbd vous avertit s'il trouve quelque chose d'inhabituel, comme une touche Suppr qui n'envoie ni ^H ni ^?.

Les frappes de touches lues par zkbd sont enregistrées comme définition pour un tableau associatif nommé key, écrites dans un fichier du sous-répertoire .zkbd dans votre répertoire HOME ou ZDOTDIR. Le nom du fichier est composé des paramètres TERM, VENDOR et OSTYPE, joints par des tirets.

Vous pouvez lire ce fichier dans votre .zshrc ou un autre fichier de démarrage avec les commandes `source' ou `.', puis référencer le paramètre key dans les commandes bindkey, comme ceci :

source ${ZDOTDIR:-$HOME}/.zkbd/$TERM-$VENDOR-$OSTYPE
[[ -n ${key[Left]} ]] && bindkey "${key[Left]}" backward-char
[[ -n ${key[Right]} ]] && bindkey "${key[Right]}" forward-char
# etc.

Vidage de l'état du shell

Il peut arriver que vous rencontriez ce qui semble être un bug dans le shell, particulièrement si vous utilisez une version bêta de zsh ou une version de développement. Habituellement, il suffit d'envoyer une description du problème à l'une des listes de diffusion de zsh (voir zsh(1)), mais parfois, l'un des développeurs de zsh aura besoin de recréer votre environnement afin de traquer le problème.

Le script nommé reporter, trouvé dans le répertoire Util de la distribution, est fourni à cet effet. (Il est également possible d'utiliser autoload reporter, mais reporter n'est pas installé dans fpath par défaut.) Ce script produit un vidage détaillé de l'état du shell, sous la forme d'un autre script qui peut être lu avec `zsh -f' pour recréer cet état.

Pour utiliser reporter, lisez le script dans votre shell avec la commande `.' et redirigez la sortie dans un fichier :

. ~/zsh-5.9/Util/reporter > zsh.report

Vous devriez vérifier le fichier zsh.report pour toute information sensible telle que des mots de passe et les supprimer manuellement avant d'envoyer le script aux développeurs. De plus, comme la sortie peut être volumineuse, il est préférable d'attendre que les développeurs demandent cette information avant de l'envoyer.

Vous pouvez également utiliser reporter pour vider uniquement un sous-ensemble de l'état du shell. Ceci est parfois utile pour créer des fichiers de démarrage pour la première fois. La plupart des sorties de reporter sont bien plus détaillées que nécessaire pour un fichier de démarrage, mais les états aliases, options et zstyles peuvent être utiles car ils n'incluent que les changements par rapport aux valeurs par défaut. L'état bindings peut être utile si vous avez créé vos propres tables de raccourcis, car reporter s'arrange pour vider les commandes de création de tables de raccourcis ainsi que les liaisons pour chaque table de raccourcis.

Comme d'habitude avec les outils automatisés, si vous créez un fichier de démarrage avec reporter, vous devriez éditer les résultats pour supprimer les commandes inutiles. Notez que si vous utilisez le nouveau système de complétion, vous ne devriez *pas* vider l'état functions dans vos fichiers de démarrage avec reporter ; utilisez plutôt la fonction compdump (voir zshcompsys(1)).

reporter [ état ... ]
Imprime sur la sortie standard le sous-ensemble indiqué de l'état actuel du shell. Les arguments état peuvent être un ou plusieurs des éléments suivants :
all
Sortie de tout ce qui est listé ci-dessous.
aliases
Sortie des définitions d'alias.
bindings
Sortie des tables de raccourcis et des liaisons ZLE.
completion
Sortie des commandes compctl de l'ancien style. La nouvelle complétion est couverte par functions et zstyles.
functions
Sortie des autoloads et des définitions de fonctions.
limits
Sortie des commandes limit.
options
Sortie des commandes setopt.
styles
Identique à zstyles.
variables
Sortie des affectations de paramètres du shell, plus les commandes export pour les variables d'environnement.
zstyles
Sortie des commandes zstyle.

Si état est omis, all est supposé.

À l'exception de `all', chaque état peut être abrégé par n'importe quel préfixe, même une seule lettre ; ainsi a est identique à aliases, z est identique à zstyles, etc.

Manipulation des fonctions de hook

add-zsh-hook [ -L | -dD ] [ -Uzk ] hook fonction
Plusieurs fonctions sont spéciales pour le shell, comme décrit dans la section FONCTIONS SPÉCIALES, voir zshmisc(1), en ce sens qu'elles sont appelées automatiquement à des points spécifiques pendant l'exécution du shell. Chacune a un tableau associé contenant les noms des fonctions à appeler au même point ; ce sont les soi-disant `fonctions de hook'. La fonction shell add-zsh-hook offre un moyen simple d'ajouter ou de supprimer des fonctions du tableau.

hook est l'un des noms suivants : chpwd, periodic, precmd, preexec, zshaddhistory, zshexit, ou zsh_directory_name, les fonctions spéciales en question. Notez que zsh_directory_name est appelé différemment des autres fonctions, mais peut néanmoins être manipulé comme un hook.

fonction est le nom d'une fonction shell ordinaire. Si aucune option n'est donnée, elle sera ajoutée au tableau des fonctions à exécuter dans le contexte donné. Les fonctions sont invoquées dans l'ordre où elles ont été ajoutées.

Si l'option -L est donnée, les valeurs actuelles des tableaux de hooks sont listées avec typeset.

Si l'option -d est donnée, la fonction est supprimée du tableau des fonctions à exécuter.

Si l'option -D est donnée, la fonction est traitée comme un motif et tous les noms de fonctions correspondants sont supprimés du tableau des fonctions à exécuter.

Les options -U, -z et -k sont passées comme arguments à autoload pour fonction. Pour les fonctions fournies avec zsh, les options -Uz sont appropriées.

add-zle-hook-widget [ -L | -dD ] [ -Uzk ] hook nom_widget
Plusieurs noms de widgets sont spéciaux pour l'éditeur de ligne, comme décrit dans la section Widgets spéciaux, voir zshzle(1), en ce sens qu'ils sont automatiquement appelés à des points spécifiques pendant l'édition. Contrairement aux hooks de fonction, ceux-ci n'utilisent pas un tableau prédéfini d'autres noms à appeler au même point ; la fonction shell add-zle-hook-widget maintient un tableau similaire et s'arrange pour que le widget spécial invoque ces widgets supplémentaires.

hook est l'un des noms suivants : isearch-exit, isearch-update, line-pre-redraw, line-init, line-finish, history-line-set, ou keymap-select, correspondant à chacun des widgets spéciaux zle-isearch-exit, etc. Les noms de widgets spéciaux sont également acceptés comme argument hook.

nom_widget est le nom d'un widget ZLE. Si aucune option n'est donnée, il est ajouté au tableau des widgets à invoquer dans le contexte de hook donné. Les widgets sont invoqués dans l'ordre où ils ont été ajoutés, avec

zle nom_widget -Nw -f "nolast" -- "$@"

Notez que cela signifie que le paramètre spécial `WIDGET' suit le nom_widget lorsque la fonction du widget est appelée, plutôt que de suivre le nom du widget hook spécial correspondant.

Si l'option -d est donnée, le nom_widget est supprimé du tableau des widgets à exécuter.

Si l'option -D est donnée, le nom_widget est traité comme un motif et tous les noms de widgets correspondants sont supprimés du tableau.

Si nom_widget ne nomme pas un widget existant lors de son ajout au tableau, on suppose qu'une fonction shell portant également le nom nom_widget est destinée à fournir l'implémentation du widget. Ce nom est donc marqué pour autoload, et les options -U, -z et -k sont passées comme arguments à autoload comme avec add-zsh-hook. Le widget est également créé avec `zle -N nom_widget' pour provoquer le chargement de la fonction correspondante lors du premier appel du hook.

Les tableaux de nom_widget sont actuellement maintenus dans des contextes zstyle, un pour chaque contexte de hook, avec un style de `widgets'. Si l'option -L est donnée, cet ensemble de styles est listé avec `zstyle -L'. Cette implémentation peut changer, et les widgets spéciaux qui font référence aux styles sont créés uniquement si add-zle-hook-widget est appelé pour ajouter au moins un widget, donc si cette fonction est utilisée pour des hooks, alors tous les hooks doivent être gérés uniquement via cette fonction.

SE RAPPROCHER DES RÉPERTOIRES RÉCENTS

La fonction cdr permet de changer de répertoire de travail vers un répertoire précédent à partir d'une liste maintenue automatiquement. Elle est similaire en concept à la pile de répertoires contrôlée par les builtins pushd, popd et dirs, mais est plus configurable, et comme elle stocke toutes les entrées dans des fichiers, elle est maintenue entre les sessions et (par défaut) entre les émulateurs de terminaux de la session actuelle. Les doublons sont automatiquement supprimés, de sorte que la liste reflète l'utilisation la plus récente unique de chaque répertoire.

Notez que la pile de répertoires pushd n'est pas réellement modifiée ou utilisée par cdr à moins que vous ne la configuriez pour ce faire, comme décrit dans la section de configuration ci-dessous.

Installation

Le système fonctionne au moyen d'une fonction de hook appelée chaque fois que le répertoire change. Pour installer le système, chargez automatiquement les fonctions requises et utilisez la fonction add-zsh-hook décrite ci-dessus :

autoload -Uz chpwd_recent_dirs cdr add-zsh-hook
add-zsh-hook chpwd chpwd_recent_dirs

Maintenant, chaque fois que vous changez de répertoire de manière interactive, quelle que soit la commande que vous utilisez, le répertoire vers lequel vous changez sera mémorisé dans l'ordre du plus récent au moins récent.

Utilisation

Toute interaction directe avec l'utilisateur se fait via la fonction cdr.

L'argument de cdr est un nombre N correspondant au Nème répertoire le plus récemment changé.

ctory. 1 est le répertoire immédiatement précédent ; le répertoire courant est mémorisé mais n'est pas proposé comme destination. Notez que si vous avez plusieurs fenêtres ouvertes, 1 peut faire référence à un répertoire changé dans une autre fenêtre ; vous pouvez éviter cela en ayant des fichiers par terminal pour stocker les répertoires comme décrit pour le style recent-dirs-file ci-dessous.

Si vous définissez le style recent-dirs-default décrit ci-dessous, cdr se comportera de la même manière que cd s'il reçoit un argument non numérique, ou plus d'un argument. La liste des répertoires récents est mise à jour, quelle que soit la manière dont vous changez de répertoire.

Si l'argument est omis, 1 est supposé. Ceci est similaire au comportement de pushd qui échange les deux répertoires les plus récents sur la pile.

La complétion pour l'argument de cdr est disponible si compinit a été exécuté ; la sélection par menu est recommandée, en utilisant :

zstyle ':completion:*:*:cdr:*:*' menu selection

pour vous permettre de parcourir les répertoires récents ; l'ordre est préservé, donc le premier choix est le répertoire le plus récent avant celui courant. Le style verbeux est également recommandé pour s'assurer que le répertoire est affiché ; ce style est activé par défaut, donc aucune action n'est requise sauf si vous l'avez modifié.

Options

Le comportement de cdr peut être modifié par les options suivantes.

-l
liste les numéros et les répertoires correspondants sous forme abrégée (c'est-à-dire avec la substitution de ~ réappliquée), un par ligne. Les répertoires ici ne sont pas mis entre guillemets (ce ne serait un problème que si un nom de répertoire contenait un saut de ligne). Ceci est utilisé par le système de complétion.
-r
définit la variable reply avec l'ensemble actuel des répertoires. Rien n'est imprimé et le répertoire n'est pas changé.
-e
vous permet de modifier la liste des répertoires, un par ligne. La liste peut être modifiée à volonté ; aucune vérification de cohérence n'est effectuée. La complétion est disponible. Aucune citation n'est nécessaire (sauf pour les sauts de ligne, pour lesquels je n'ai de toute façon aucune sympathie) ; les répertoires sont sous forme non abrégée et contiennent un chemin absolu, c'est-à-dire qu'ils commencent par /. Habituellement, la première entrée doit être laissée telle quelle pour le répertoire courant.
-p 'motif'
Supprime tous les éléments de la liste de répertoires qui correspondent au motif de glob étendu donné ; le motif doit être mis entre guillemets pour éviter une expansion immédiate sur la ligne de commande. Le motif est comparé à chaque nom de fichier entièrement développé dans la liste ; la chaîne complète doit correspondre, donc des caractères génériques à la fin (par exemple, '*removeme*') sont nécessaires pour supprimer les entrées contenant une sous-chaîne donnée.

Si la sortie est dirigée vers un terminal, la fonction affichera la nouvelle liste après la suppression et demandera une confirmation à l'utilisateur. Cette étape de sortie et de confirmation peut être ignorée en utilisant -P au lieu de -p.

Configuration

La configuration se fait via le mécanisme des styles, qui devrait vous être familier grâce à la complétion ; sinon, consultez la description de la commande zstyle dans zshmodules(1). Le contexte pour la définition des styles devrait être ':chpwd:*' au cas où la signification du contexte serait étendue à l'avenir, par exemple :

zstyle ':chpwd:*' recent-dirs-max 0

définit la valeur du style recent-dirs-max à 0. En pratique, le nom du style est suffisamment spécifique pour qu'un contexte de '*' convienne.

Une exception est recent-dirs-insert, qui est utilisé exclusivement par le système de complétion et a donc le contexte habituel du système de complétion (':completion:*' si rien de plus spécifique n'est nécessaire), bien qu'encore une fois, '*' convienne en pratique.

recent-dirs-default
Si vrai, et que la commande attend un index de répertoire récent, et qu'il y a plus d'un argument ou que l'argument n'est pas un entier, alors passer à "cd". Ceci permet aux paresseux de n'utiliser qu'une seule commande pour changer de répertoire. La complétion le reconnaît également ; voir recent-dirs-insert pour savoir comment contrôler la complétion lorsque cette option est utilisée.
recent-dirs-file
Le fichier où la liste des répertoires est sauvegardée. Le défaut est ${ZDOTDIR:-$HOME}/.chpwd-recent-dirs, c'est-à-dire que c'est dans votre répertoire personnel, sauf si vous avez défini la variable ZDOTDIR pour pointer ailleurs. Les noms de répertoires sont sauvegardés sous forme citée $'...', de sorte que chaque ligne du fichier peut être fournie directement au shell comme argument.

La valeur de ce style peut être un tableau. Dans ce cas, le premier fichier de la liste sera toujours utilisé pour enregistrer les répertoires tandis que tout autre fichier restera inchangé. Lors de la lecture de la liste des répertoires récents, s'il y a moins que le nombre maximum d'entrées dans le premier fichier, le contenu des fichiers suivants dans le tableau sera ajouté, les doublons étant supprimés de la liste affichée. Le contenu des deux fichiers n'est pas trié ensemble, c'est-à-dire que toutes les entrées du premier fichier sont affichées en premier. La valeur spéciale + peut apparaître dans la liste pour indiquer que le fichier par défaut doit être lu à ce moment-là. Ceci permet des effets tels que les suivants :

zstyle ':chpwd:*' recent-dirs-file \ 
~/.chpwd-recent-dirs-${TTY##*/} +

Les répertoires récents sont lus à partir d'un fichier numéroté selon le terminal. S'il y a des entrées insuffisantes, la liste est complétée à partir du fichier par défaut.

Il est possible d'utiliser zstyle -e pour rendre le répertoire configurable au moment de l'exécution :

zstyle -e ':chpwd:*' recent-dirs-file pick-recent-dirs-file
pick-recent-dirs-file() {
  if [[ $PWD = ~/text/writing(|/*) ]]; then
    reply=(~/.chpwd-recent-dirs-writing)
  else
    reply=(+)
  fi
}

Dans cet exemple, si le répertoire courant est ~/text/writing ou un répertoire en dessous, alors utilisez un fichier spécial pour enregistrer les répertoires récents, sinon utilisez le défaut.

recent-dirs-insert
Utilisé par la complétion. Si recent-dirs-default est vrai, alors définir cette option à true provoque l'insertion du répertoire réel, plutôt que son index, sur la ligne de commande ; cela a le même effet que l'utilisation de l'index correspondant, mais rend l'historique plus clair et la ligne plus facile à modifier. Avec ce réglage, si une partie d'un argument a déjà été tapée, la complétion normale de répertoire plutôt que la complétion de répertoire récent est effectuée ; ceci est dû au fait que la complétion de répertoire récent est censée être effectuée en parcourant les entrées en mode menu.

Si la valeur du style est always, alors seuls les répertoires récents seront complétés ; dans ce cas, utilisez la commande cd lorsque vous souhaitez compléter d'autres répertoires.

Si la valeur est fallback, les répertoires récents seront essayés en premier, puis la complétion de répertoire normale sera effectuée si la complétion de répertoire récent n'a pas trouvé de correspondance.

Enfin, si la valeur est both, alors les deux ensembles de complétions sont présentés ; le mécanisme de balisage habituel peut être utilisé pour distinguer les résultats, les répertoires récents étant balisés comme recent-dirs. Notez que les répertoires récents insérés sont abrégés avec des noms de répertoires lorsque cela est approprié.

recent-dirs-max
Le nombre maximum de répertoires à enregistrer dans le fichier. S'il est nul ou négatif, il n'y a pas de maximum. Le défaut est de 20. Notez que cela inclut le répertoire courant, qui n'est pas proposé, donc le nombre le plus élevé de répertoires qui vous seront proposés est inférieur de un au maximum.
recent-dirs-prune
Ce style est un tableau déterminant quels répertoires doivent (ou ne doivent pas) être ajoutés à la liste récente. Les éléments du tableau peuvent inclure :
parent
Supprime les parents (plus précisément, les ancêtres) de la liste récente. S'il est présent, changer directement vers le bas d'un certain nombre de répertoires provoque l'écrasement du répertoire courant. Par exemple, passer de ~pws à ~pws/some/other/dir fait que ~pws n'est pas laissé sur la pile des répertoires récents. Ceci ne s'applique qu'aux changements directs vers les répertoires descendants ; les répertoires précédents dans la liste ne sont pas supprimés. Par exemple, passer de ~pws/yet/another à ~pws/some/other/dir ne provoque pas la suppression de ~pws.
pattern:motif
Fournit un motif zsh pour les répertoires qui ne doivent pas être ajoutés à la liste récente (s'ils n'y sont pas déjà). Cet élément peut être répété pour ajouter différents motifs. Par exemple, 'pattern:/tmp(|/*)' empêche /tmp ou ses descendants d'être ajoutés. L'option EXTENDED_GLOB est toujours activée pour ces motifs.
recent-dirs-pushd
S'il est défini à vrai, cdr utilisera pushd au lieu de cd pour changer de répertoire, de sorte que le répertoire soit sauvegardé sur la pile de répertoires. Comme la pile de répertoires est complètement séparée de la liste des fichiers sauvegardés par le mécanisme utilisé dans ce fichier, il n'y a pas de raison évidente de le faire.

Utilisation avec la dénomination dynamique de répertoire

Il est possible de faire référence à des répertoires récents en utilisant la syntaxe de nom de répertoire dynamique en utilisant la fonction fournie zsh_directory_name_cdr comme hook :

autoload -Uz add-zsh-hook
add-zsh-hook -Uz zsh_directory_name zsh_directory_name_cdr

Lorsque cela est fait, ~[1] fera référence au répertoire le plus récent autre que $PWD, et ainsi de suite. La complétion après ~[... fonctionne également.

Détails de la gestion des répertoires

Cette section s'adresse aux curieux ou aux confus ; la plupart des utilisateurs n'auront pas besoin de cette information.

Les répertoires récents sont sauvegardés dans un fichier immédiatement et sont donc préservés d'une session à l'autre. Notez qu'aucun verrouillage de fichier n'est appliqué actuellement : la liste est mise à jour immédiatement pour les commandes interactives et nulle part ailleurs (contrairement à l'historique), et on suppose que vous ne changerez de répertoire que dans une seule fenêtre.

Bien sûr, voici la traduction de votre contenu en français, tout en conservant la structure du fichier : ```french une fois. Ce n'est pas sûr sur les comptes partagés, mais dans tous les cas, le système a une utilité limitée lorsque quelqu'un d'autre change d'ensemble de répertoires derrière votre dos.

Pour rendre cela un peu plus sûr, seuls les changements de répertoire initiés depuis la ligne de commande, soit directement, soit indirectement par des appels de fonctions shell (mais pas par des sous-shells, evals, traps, fonctions de complétion et similaires) sont sauvegardés. Les fonctions shell doivent utiliser cd -q ou pushd -q pour éviter les effets secondaires si le changement de répertoire doit être invisible sur la ligne de commande. Voir le contenu de la fonction chpwd_recent_dirs pour plus de détails.

REFERENCES DYNAMIQUES ABREGEES AUX REPERTOIRES

Le système de nommage dynamique de répertoires est décrit dans la sous-section Répertoires nommés dynamiques de la section Expansion de noms de fichiers dans zshexpn(1). Dans celle-ci, une référence à ~[...] est développée par une fonction trouvée par le mécanisme des hooks.

La fonction contribuée zsh_directory_name_generic fournit un système permettant à l'utilisateur de faire référence à des répertoires avec seulement une quantité limitée de nouveau code. Elle prend en charge les trois interfaces standard pour le nommage de répertoires : conversion d'un nom vers un répertoire, conversion dans la direction inverse pour trouver un nom court, et complétion des noms.

La caractéristique principale de cette fonction est une syntaxe de type chemin, combinant des abréviations à plusieurs niveaux séparées par ":". Par exemple, ~[g:p:s] pourrait spécifier :

g
Le répertoire de niveau supérieur pour votre zone git. Ce premier composant doit correspondre, sinon la fonction retournera en indiquant qu'une autre fonction de hook de nom de répertoire doit être essayée.
p
Le nom d'un projet dans votre zone git.
s
La zone source dans ce projet. Cela vous permet de réduire les références à des hiérarchies longues à une forme très compacte, particulièrement si les hiérarchies sont similaires dans différentes zones du disque.

Les composants de nom peuvent être complétés : si une description est affichée en haut de la liste des complétions, elle inclut le chemin vers lequel les composants précédents se développent, tandis que la description d'une complétion individuelle montre le segment de chemin qu'elle ajouterait. Aucune configuration supplémentaire n'est nécessaire car le système de complétion est conscient du mécanisme de nommage dynamique de répertoire.

Usage

Pour utiliser la fonction, définissez d'abord une fonction wrapper pour votre cas spécifique. Nous supposerons qu'elle doit être chargée à la demande (autoload). Celle-ci peut avoir n'importe quel nom mais nous la référencerons comme zdn_mywrapper. Cette fonction wrapper définira diverses variables puis appellera cette fonction avec les mêmes arguments que ceux reçus par la fonction wrapper. Cette configuration est décrite ci-dessous.

Ensuite, assurez-vous que le wrapper soit exécuté comme un hook zsh_directory_name :

autoload -Uz add-zsh-hook zsh_directory_name_generic zdn_mywrapper
add-zsh-hook -U zsh_directory_name zdn_mywrapper

Configuration

La fonction wrapper doit définir un tableau associatif local zdn_top. Alternativement, cela peut être défini avec un style appelé mapping. Le contexte pour le style est :zdn:nom-wrapper où nom-wrapper est la fonction appelant zsh_directory_name_generic ; par exemple :

zstyle :zdn:zdn_mywrapper: mapping zdn_mywrapper_top

Les clés de ce tableau associatif correspondent au premier composant du nom. Les valeurs sont des répertoires correspondants. Elles peuvent avoir un suffixe optionnel avec une barre oblique suivie d'un deux-points et du nom d'une variable dans le même format pour donner le composant suivant. (La barre oblique avant le deux-points sert à désambiguïser le cas où un deux-points serait nécessaire dans le chemin pour un lecteur. Il n'y a autrement aucune syntaxe pour échapper cela, donc les composants de chemin dont les noms commencent par un deux-points ne sont pas pris en charge.) Un composant spécial :default: spécifie une variable sous la forme /:var (la section chemin est ignorée et est donc généralement vide) qui sera utilisée pour le composant suivant si aucune variable n'est donnée pour le chemin. Les variables référencées dans zdn_top ont le même format que zdn_top lui-même, mais contiennent des chemins relatifs.

Par exemple,

local -A zdn_top=(
  g   ~/git
  ga  ~/alternate/git
  gs  /scratch/$USER/git/:second2
  :default: /:second1
)

Ceci spécifie le comportement d'un répertoire référencé comme ~[g:...] ou ~[ga:...] ou ~[gs:...]. Les composants de chemin ultérieurs sont optionnels ; dans ce cas, ~[g] se développe en ~/git, et ainsi de suite. gs se développe en /scratch/$USER/git et utilise le tableau associatif second2 pour faire correspondre le deuxième composant ; g et ga utilisent le tableau associatif second1 pour faire correspondre le deuxième composant.

Lors du développement d'un nom vers un répertoire, si le premier composant n'est pas g ou ga ou gs, ce n'est pas une erreur ; la fonction retourne simplement 1 afin qu'une fonction hook ultérieure puisse être essayée. Cependant, la correspondance du premier composant engage la fonction, donc si un composant ultérieur ne correspond pas, une erreur est affichée (bien que cela n'empêche pas l'exécution des hooks ultérieurs).

Pour les composants après le premier, un chemin relatif est attendu, mais notez que plusieurs niveaux peuvent toujours apparaître. Voici un exemple de second1 :

local -A second1=(
  p   myproject
  s   somproject
  os  otherproject/subproject/:third
)

Le chemin tel que trouvé depuis zdn_top est étendu avec le répertoire correspondant, donc ~[g:p] devient ~/git/myproject. La barre oblique entre les deux est ajoutée automatiquement (il n'est pas possible qu'un composant ultérieur modifie le nom d'un répertoire déjà trouvé). Seul os spécifie une variable pour un troisième composant, et il n'y a pas de :default:, donc c'est une erreur d'utiliser un nom comme ~[g:p:x] ou ~[ga:s:y] car il n'y a nulle part où chercher le x ou le y.

Les tableaux associatifs doivent être visibles dans cette fonction ; la fonction générique utilise donc des noms de variables internes commençant par _zdn_ afin d'éviter les conflits. Notez que la variable reply doit être renvoyée au shell, donc ne doit pas être locale dans la fonction appelante.

La fonction ne teste pas si les répertoires assemblés par composant existent réellement ; cela permet au système de fonctionner sur des systèmes de fichiers montés automatiquement. L'erreur provenant de la commande essayant d'utiliser un répertoire inexistant devrait suffire à indiquer le problème.

Exemple complet

Voici une définition autoloadable fictive mais utilisable de la fonction exemple définie par le code ci-dessus. Ainsi, ~[gs:p:s] se développe en /scratch/$USER/git/myscratchproject/top/srcdir (avec $USER également développé).

local -A zdn_top=(
  g   ~/git
  ga  ~/alternate/git
  gs  /scratch/$USER/git/:second2
  :default: /:second1
)
local -A second1=(
  p   myproject
  s   somproject
  os  otherproject/subproject/:third
)
local -A second2=(
  p   myscratchproject
  s   somescratchproject
)
local -A third=(
  s   top/srcdir
  d   top/documentation
)
# autoload non nécessaire si vous avez fait cela lors de l'initialisation...
autoload -Uz zsh_directory_name_generic
zsh_directory_name_generic "$@

Il est également possible d'utiliser des tableaux associatifs globaux, convenablement nommés, et de définir le style pour le contexte de votre fonction wrapper pour y faire référence. Votre code de configuration contiendrait alors ce qui suit :

typeset -A zdn_mywrapper_top=(...)
# ... et ainsi de suite pour d'autres tableaux associatifs ...
zstyle ':zdn:zdn_mywrapper:' mapping zdn_mywrapper_top
autoload -Uz add-zsh-hook zsh_directory_name_generic zdn_mywrapper
add-zsh-hook -U zsh_directory_name zdn_mywrapper

et la fonction zdn_mywrapper contiendrait uniquement ce qui suit :

zsh_directory_name_generic "$@"

Démarrage rapide

Pour que cette fonctionnalité fonctionne rapidement (y compris les couleurs), vous pouvez faire ce qui suit (en supposant que vous ayez chargé vcs_info correctement - voir ci-dessus) :

zstyle ':vcs_info:*' actionformats \
    '%F{5}(%f%s%F{5})%F{3}-%F{5}[%F{2}%b%F{3}|%F{1}%a%F{5}]%f '
zstyle ':vcs_info:*' formats       \
    '%F{5}(%f%s%F{5})%F{3}-%F{5}[%F{2}%b%F{5}]%f '
zstyle ':vcs_info:(sv[nk]|bzr):*' branchformat '%b%F{1}:%F{3}%r'
precmd () { vcs_info }
PS1='%F{5}[%F{2}%n%F{5}] %F{3}%3~ ${vcs_info_msg_0_}%f%# '

Évidemment, les deux dernières lignes sont là pour la démonstration. Vous devez appeler vcs_info depuis votre fonction precmd. Une fois que c'est fait, vous avez besoin d'un '${vcs_info_msg_0_}' *entre apostrophes simples* dans votre invite.

Pour pouvoir utiliser '${vcs_info_msg_0_}' directement dans votre invite de cette manière, vous devrez avoir l'option PROMPT_SUBST activée.

Appelez maintenant l'utilitaire vcs_info_printsys depuis la ligne de commande :

% vcs_info_printsys

## les systèmes désactivés sont précédés d'un signe dièse (#)
bzr
cdv

darcs
fossil

## saveurs (ne peuvent pas être utilisées dans les styles enable ou disable ; elles

## elles *peuvent* être utilisées dans les contextes : ':vcs_info:git-svn:*'.

Vous ne voudrez peut-être pas de tous ces systèmes car il est inutile d'exécuter le code pour détecter les systèmes que vous n'utilisez pas. Il existe donc un moyen de désactiver certains backends :

zstyle ':vcs_info:*' disable bzr cdv darcs mtn svk tla

Vous pouvez également choisir quelques éléments de cette liste et n'activer que ceux-ci :

zstyle ':vcs_info:*' enable git cvs svn

Si vous réexécutez vcs_info_printsys après l'une de ces commandes, vous verrez les backends listés dans le style disable (ou les backends non présents dans le style enable, si vous l'avez utilisé) marqués comme désactivés par un signe dièse. Cela signifie que la détection de ces systèmes est complètement ignorée. Pas de temps perdu.

Configuration

La fonctionnalité vcs_info peut être configurée via zstyle.

Premièrement, le contexte dans lequel nous travaillons :

:vcs_info:chaine-vcs:contexte-utilisateur:nom-racine-repo
chaine-vcs
est l'un des suivants : git, git-svn, git-p4, hg, hg-git, hg-hgsubversion, hg-hgsvn, darcs, bzr, cdv, mtn, svn, cvs, svk, tla, p4 ou fossil. Ceci est suivi de `.quilt-mode-quilt' en mode Quilt (voir Prise en charge de Quilt pour plus de détails) et de `+nom-hook' lorsque des hooks sont actifs (voir Hooks dans vcs_info pour plus de détails).

Actuellement, les hooks en mode quilt n'ajoutent pas l'information `.quilt-mode-quilt'. Cela pourrait changer à l'avenir.

contexte-utilisateur
est une chaîne librement configurable, assignable par l'utilisateur comme premier argument à vcs_info (voir sa description ci-dessous).
nom-racine-repo
est le nom d'un dépôt dans lequel vous souhaitez qu'un style corresponde. Ainsi, si vous voulez un réglage spécifique à /usr/src/zsh, ce dernier étant une copie CVS, vous pouvez définir nom-racine-repo à zsh pour ce faire.

Il existe trois valeurs spéciales pour chaine-vcs : La première est nommée -init-, elle est effective tant qu'aucune décision n'a été prise quant au backend VCS à utiliser. La seconde est -preinit- ; elle est utilisée *avant* l'exécution de vcs_info, lors de l'initialisation des variables d'exportation de données. La troisième valeur spéciale est formats et est utilisée par vcs_info_lastmsg pour rechercher ses styles.

La valeur initiale de nom-racine-repo est -all- et elle est remplacée par le nom réel, dès qu'il est connu. N'utilisez cette partie du contexte que pour définir les styles formats, actionformats ou branchformat, car il est garanti que nom-racine-repo est correctement configuré pour ceux-ci uniquement. Pour tous les autres styles, utilisez simplement '*' à la place.

Il existe deux valeurs prédéfinies pour contexte-utilisateur :

default
celui utilisé si aucun n'est spécifié
command
utilisé par vcs_info_lastmsg pour rechercher ses styles

Vous pouvez bien sûr utiliser ':vcs_info:*' pour faire correspondre tous les VCS dans tous les contextes utilisateur simultanément.

Voici une description de tous les styles qui sont recherchés.

formats
Une liste de formats, utilisée lorsque actionformats n'est pas utilisé (ce qui est le cas la plupart du temps).
actionformats
Une liste de formats, utilisée s'il y a une action spéciale en cours dans votre dépôt actuel ; comme un rebase interactif ou un conflit de fusion.
branchformat
Certains backends remplacent %b dans les styles formats et actionformats ci-dessus, non seulement par un nom de branche mais aussi par un numéro de révision. Ce style vous permet de modifier l'apparence de cette chaîne.
nvcsformats
Ces "formats" sont définis lorsque nous n'avons pas détecté de système de contrôle de version pour le répertoire actuel ou que vcs_info a été désactivé. Ceci est utile si vous souhaitez que vcs_info prenne complètement en charge la génération de votre invite. Vous feriez quelque chose comme PS1='${vcs_info_msg_0_}' pour y parvenir.
hgrevformat
hg utilise à la fois un hash et un numéro de révision pour référencer un changeset spécifique dans un dépôt. Avec ce style, vous pouvez formater la chaîne de révision (voir branchformat) pour inclure l'un ou l'autre, ou les deux. Il n'est utile que lorsque get-revision est vrai. Notez que l'ID de révision complet de 40 caractères n'est pas disponible (sauf lors de l'utilisation de l'option use-simple) car l'exécution de hg plus d'une fois par invite est trop lente ; vous pouvez personnaliser ce comportement à l'aide de hooks.
max-exports
Définit le nombre maximum de variables vcs_info_msg_*_ que vcs_info configurera.
enable
Une liste de backends que vous souhaitez utiliser. Vérifié dans le contexte -init-. Si cette liste contient un élément appelé NONE, aucun backend n'est utilisé du tout et vcs_info ne fera rien. Si cette liste contient ALL, vcs_info utilisera tous les backends connus. Ce n'est qu'avec ALL dans enable que le style disable aura un effet. ALL et NONE ne sont pas sensibles à la casse.
disable
Une liste de VCS que vous ne voulez pas que vcs_info teste pour les dépôts (également vérifié dans le contexte -init-). Utilisé uniquement si enable contient ALL.
disable-patterns
Une liste de motifs qui sont vérifiés par rapport à $PWD. Si un motif correspond, vcs_info sera désactivé. Ce style est vérifié dans le contexte :vcs_info:-init-:*:-all-.

Par exemple, si ~/.zsh est un répertoire sous contrôle de version, dans lequel vous ne souhaitez pas que vcs_info soit actif, faites ceci :

zstyle ':vcs_info:*' disable-patterns ""${(b)HOME}/.zsh(|/*)""
use-quilt
Si activé, le code de prise en charge de quilt est actif en mode `addon'. Voir Prise en charge de Quilt pour plus de détails.
quilt-standalone
Si activé, une détection en mode `standalone' est tentée si aucun VCS n'est actif dans un répertoire donné. Voir Prise en charge de Quilt pour plus de détails.
quilt-patch-dir
Remplace la valeur de la variable d'environnement $QUILT_PATCHES. Voir Prise en charge de Quilt pour plus de détails.
quiltcommand
Lorsque quilt lui-même est appelé dans le cadre de la prise en charge de quilt, la valeur de ce style est utilisée comme nom de commande.
check-for-changes
Si activé, ce style fait que les échappements de format %c et %u s'affichent lorsque le répertoire de travail a des modifications non commitées. Les chaînes affichées par ces échappements peuvent être contrôlées via les styles stagedstr et unstagedstr. Les seuls backends qui prennent actuellement en charge cette option sont git, hg et bzr (ces deux derniers ne prennent en charge que les modifications non enregistrées).

Pour que ce style soit évalué avec le backend hg, le style get-revision doit être défini et le style use-simple doit être désactivé. Ce dernier est le défaut ; le premier ne l'est pas.

Avec le backend bzr, les *checkouts légers* n'honorent ce style que si le style use-server est défini.

Notez que les actions entreprises si ce style est activé peuvent être coûteuses (c'est-à-dire qu'elles peuvent être lentes, en fonction de la taille du dépôt actuel). Par conséquent, il est désactivé par défaut.

check-for-staged-changes
Ce style est
comme check-for-changes, mais il ne vérifie jamais les fichiers de l'espace de travail, seulement les métadonnées du répertoire .${vcs}. Par conséquent, ce style initialise uniquement le code d'échappement %c (avec stagedstr) mais pas le code d'échappement %u. Ce style est plus rapide que check-for-changes.

Dans le backend git, ce style vérifie les changements dans l'index. Les autres backends n'implémentent pas ce style actuellement.

Ce style est désactivé par défaut.

stagedstr
Cette chaîne sera utilisée dans le code d'échappement %c s'il y a des changements préparés dans le dépôt.
unstagedstr
Cette chaîne sera utilisée dans le code d'échappement %u s'il y a des changements non préparés dans le dépôt.
command
Ce style amène vcs_info à utiliser la chaîne fournie comme commande pour utiliser le binaire du VCS. Notez qu'il n'est pas judicieux de définir cela dans ':vcs_info:*'.

Si la valeur de ce style est vide (ce qui est le cas par défaut), le nom du binaire utilisé est le nom du backend en cours d'utilisation (par exemple, svn est utilisé dans un dépôt svn).

La partie repo-root-name dans le contexte est toujours -all- par défaut lorsque ce style est consulté.

Par exemple, ce style peut être utilisé pour utiliser des binaires provenant de répertoires d'installation non par défaut. Supposons que git est installé dans /usr/bin mais que votre administrateur système a installé une version plus récente dans /usr/local/bin. Au lieu de modifier l'ordre de votre paramètre $PATH, vous pouvez faire ceci :

zstyle ':vcs_info:git:*:-all-' command /usr/local/bin/git
use-server
Ceci est utilisé par le backend Perforce (p4) pour décider s'il doit contacter le serveur Perforce pour savoir si un répertoire est géré par Perforce. C'est la seule façon fiable de le faire, mais il y a un risque de retard si le nom du serveur ne peut pas être trouvé. Si le serveur (plus spécifiquement, la paire hôte:port décrivant le serveur) ne peut pas être contacté, son nom est placé dans le tableau associatif vcs_info_p4_dead_servers et ne sera plus contacté pendant la session jusqu'à ce qu'il soit supprimé manuellement. Si vous ne définissez pas ce style, le backend p4 n'est utilisable que si vous avez défini la variable d'environnement P4CONFIG sur un nom de fichier et que vous avez des fichiers correspondants dans les répertoires racines de chaque client Perforce. Voir les commentaires dans la fonction VCS_INFO_detect_p4 pour plus de détails.

Le backend Bazaar (bzr) utilise ceci pour permettre de contacter le serveur concernant les checkouts légers, voir le style check-for-changes.

use-simple
S'il existe deux façons différentes de collecter des informations, vous pouvez sélectionner la plus simple en définissant ce style sur vrai ; par défaut, le code pas si simple est utilisé, potentiellement beaucoup plus lent mais peut-être plus précis dans tous les cas possibles. Ce style est utilisé par les backends bzr, hg et git. Dans le cas de hg, il invoquera le programme externe hexdump pour analyser le fichier de cache binaire dirstate ; cette méthode ne renverra pas le numéro de révision local.
get-revision
S'il est défini sur vrai, vcs_info fait un effort supplémentaire pour trouver la révision de l'espace de travail d'un dépôt (actuellement pour les backends git et hg, où ce type d'information n'est pas toujours vital). Particularités

Si vous voulez utiliser l'expansion de prompt %b (gras désactivé) dans formats, qui étend %b lui-même, utilisez %%b. Cela fera que l'expansion vcs_info remplacera %%b par %b, de sorte que le mécanisme d'expansion de prompt de zsh puisse le gérer. De même, pour transmettre %b depuis branchformat, utilisez %%%%b. Désolé pour ce désagrément, mais il ne peut pas être facilement évité. Heureusement, nous n'avons pas beaucoup de conflits avec les expansions de prompt et cela ne nécessite d'être fait que pour celles-ci.

Lorsqu'un des hooks gen-applied-string, gen-unapplied-string et set-patch-format est défini, l'application de l'échappement des % (`foo=${foo//'%'/%%}') aux valeurs interpolées pour une utilisation dans le prompt est la responsabilité de ces hooks (conjointement) ; lorsque ni l'un ni l'autre de ces hooks n'est défini, vcs_info gère l'échappement lui-même. Nous regrettons ce couplage, mais il était requis pour la compatibilité descendante.

Support Quilt

Quilt n'est pas un système de contrôle de version, par conséquent il n'est pas implémenté comme un backend. Il peut aider à suivre une série de patchs. Les gens l'utilisent pour garder une collection de modifications qu'ils souhaitent utiliser par-dessus des packages logiciels (ce qui est étroitement intégré au processus de construction des packages - le projet Debian le fait pour un grand nombre de packages). Quilt peut également aider les développeurs individuels à suivre leurs propres patchs par-dessus de vrais systèmes de contrôle de version.

L'intégration vcs_info essaie de supporter les deux façons d'utiliser quilt en ayant deux modes de fonctionnement légèrement différents : le mode `addon' et le mode `standalone').

L'intégration Quilt est désactivée par défaut ; pour l'activer, définissez le style use-quilt et ajoutez %Q à votre style formats ou actionformats :

zstyle ':vcs_info:*' use-quilt true

Les styles recherchés par le code de support Quilt incluent `.quilt-quilt-mode' dans la partie vcs-string du contexte, où quilt-mode est soit addon, soit standalone. Exemple : :vcs_info:git.quilt-addon:default:nom-racine-repo.

Pour que le mode `addon' devienne actif, vcs_info doit déjà avoir détecté un vrai système de contrôle de version contrôlant le répertoire. Si c'est le cas, un répertoire qui contient les patchs de quilt doit être trouvé. Ce répertoire est configurable via la variable d'environnement `QUILT_PATCHES'. Si cette variable existe, sa valeur est utilisée, sinon la valeur `patches' est supposée. La valeur de $QUILT_PATCHES peut être remplacée en utilisant le style `quilt-patch-dir'. (Note : vous pouvez utiliser vcs_info pour maintenir la valeur de $QUILT_PATCHES correcte en permanence via le hook post-quilt).

Lorsque le répertoire en question est trouvé, quilt est supposé être actif. Pour recueillir plus d'informations, vcs_info recherche un répertoire appelé `.pc' ; Quilt utilise ce répertoire pour suivre son état actuel. Si ce répertoire n'existe pas, nous savons que quilt n'a rien fait au répertoire de travail (c'est-à-dire qu'aucun patch n'a encore été appliqué).

Si des patchs sont appliqués, vcs_info essaiera de découvrir lesquels. Si vous voulez savoir quels patchs d'une série ne sont pas encore appliqués, vous devez activer le style get-unapplied dans le contexte approprié.

vcs_info permet un contrôle très détaillé sur la façon dont les informations collectées sont présentées (voir les sections Configuration et Hooks in vcs_info), tout cela est documenté ci-dessous. Notez qu'il existe un certain nombre d'autres systèmes de suivi de patchs qui fonctionnent par-dessus un certain système de contrôle de version (comme stgit pour git, ou mq pour hg) ; la configuration pour de tels systèmes est généralement configurée de la même manière que le support quilt.

Si le support quilt fonctionne en mode `addon', la chaîne produite est disponible comme un simple remplacement de format (%Q pour être précis), qui peut être utilisé dans formats et actionformats ; voir ci-dessous pour les détails).

Si, au contraire, le code de support fonctionne en mode `standalone', vcs_info fera semblant que quilt est un système de contrôle de version réel. Cela signifie que l'identifiant du système de contrôle de version (qui serait autrement quelque chose comme `svn' ou `cvs') sera défini sur `-quilt-'. Cela a des implications sur le contexte de style utilisé où cet identifiant est le deuxième élément. vcs_info aura rempli une valeur appropriée pour le répertoire racine du « dépôt » et la chaîne contenant les informations sur l'état de quilt sera disponible comme remplacement `misc' (et %Q pour la compatibilité avec le mode `addon').

Ce qu'il reste à discuter, c'est comment le mode `standalone' est détecté. La détection elle-même est une série de recherches de répertoires. Vous pouvez avoir cette détection activée tout le temps dans chaque répertoire qui n'est pas autrement sous contrôle de version. Si vous savez qu'il n'y a qu'un ensemble limité d'arbres où vous aimeriez que vcs_info essaie de chercher Quilt en mode `standalone' pour minimiser la quantité de recherche à chaque appel de vcs_info, il existe un certain nombre de façons de le faire :

Essentiellement, la détection du mode `standalone' est contrôlée par un style appelé `quilt-standalone'. C'est un style de chaîne et sa valeur peut avoir différents effets. Les valeurs les plus simples sont : `always' pour exécuter la détection à chaque fois que vcs_info est exécuté, et `never' pour désactiver complètement la détection.

Si la valeur de quilt-standalone est autre chose, elle est interprétée différemment. Si la valeur est le nom d'une variable scalaire, la valeur de cette variable est vérifiée et cette valeur est utilisée de la même manière `always'/'never' que décrit ci-dessus.

Si la valeur de quilt-standalone est un tableau, les éléments de ce tableau sont utilisés comme noms de répertoires sous lesquels vous souhaitez que la détection soit active.

Si quilt-standalone est un tableau associatif, les clés sont prises comme noms de répertoires sous lesquels vous souhaitez que la détection soit active, mais seulement si la valeur correspondante est la chaîne `true'.

Enfin, si la valeur de quilt-standalone est le nom d'une fonction, la fonction est appelée sans arguments et la valeur de retour décide si la détection doit être active. Une valeur de retour `0' est vraie ; une valeur de retour non nulle est interprétée comme fausse.

Notez que s'il existe à la fois une fonction et une variable nommées quilt-standalone, la fonction aura la priorité.

La fonction principale, qui exécute tous les backends et assemble toutes les données dans ${vcs_info_msg_*_}. C'est la fonction que vous voulez appeler depuis precmd si vous voulez inclure des informations à jour dans votre prompt (voir Variable Description ci-dessous). Si un argument est donné, cette chaîne sera utilisée à la place de default dans le champ user-context du contexte de style.
vcs_info_hookadd
Enregistre statiquement un certain nombre de fonctions à un hook donné. Le hook doit être donné comme premier argument ; ce qui suit est une liste de noms de fonctions de hook à enregistrer au hook. Le préfixe `+vi-' doit être omis ici. Voir Hooks in vcs_info ci-dessous pour les détails.

Sinon, seule la dernière occurrence est supprimée (si une fonction a été enregistrée sur un hook plus d'une fois). Le préfixe `+vi-' doit être omis ici. Voir Hooks in vcs_info ci-dessous pour les détails.
vcs_info_lastmsg
Affiche les valeurs actuelles de ${vcs_info_msg_*_}. Prend en compte la valeur du style use-prompt-escapes dans ':vcs_info:formats:command:-all-'. Il n'affiche également que les valeurs max-exports.
vcs_info_printsys [user-context]
Affiche une liste de tous les systèmes de contrôle de version supportés. Utile pour trouver les contextes possibles (et lesquels sont activés) ou les valeurs pour le style disable.
vcs_info_setsys
In

Description des variables

${vcs_info_msg_N_} (Notez le trait de soulignement final)
Où N est un entier, par exemple, vcs_info_msg_0_. Ces variables stockent le message d'information assemblé par le dernier appel à vcs_info. Elles sont étroitement liées aux styles formats, actionformats et nvcsformats décrits ci-dessus. Ces styles sont des listes. Le premier membre de cette liste est développé en ${vcs_info_msg_0_}, le second en ${vcs_info_msg_1_}, et le Nième en ${vcs_info_msg_N-1_}. (Voir le style max-exports ci-dessus.)

Toutes les variables nommées VCS_INFO_* sont réservées à un usage interne.

Hooks dans vcs_info

Les hooks sont des endroits dans vcs_info où vous pouvez exécuter votre propre code. Ce code peut communiquer avec le code qui l'a appelé et, par ce biais, modifier le comportement du système.

Pour la configuration, les hooks modifient le contexte de style :

:vcs_info:chaîne-vcs+nom-hook:contexte-utilisateur:nom-racine-repo

Pour enregistrer des fonctions dans un hook, vous devez les lister dans le style hooks dans le contexte approprié.

Exemple :

zstyle ':vcs_info:*+foo:*' hooks bar baz

Ceci enregistre les fonctions dans le hook `foo' pour tous les backends. Afin d'éviter les problèmes d'espace de noms, tous les noms de fonctions enregistrées sont précédés de `+vi-', donc les fonctions réellement appelées pour le hook `foo' sont `+vi-bar' et `+vi-baz'.

Si vous souhaitez enregistrer une fonction dans un hook quel que soit le contexte actuel, vous pouvez utiliser la fonction vcs_info_hookadd. Pour supprimer une fonction qui a été ajoutée de cette manière, la fonction vcs_info_hookdel peut être utilisée.

Si quelque chose semble étrange, vous pouvez activer le style booléen `debug' dans le contexte approprié et le code d'appel des hooks imprimera ce qu'il a essayé d'exécuter et si la fonction en question existait.

Lorsque vous enregistrez plus d'une fonction dans un hook, toutes les fonctions sont exécutées les unes après les autres jusqu'à ce qu'une fonction retourne une valeur non nulle ou jusqu'à ce que toutes les fonctions aient été appelées. Les fonctions de hook sensibles au contexte sont exécutées avant celles enregistrées statiquement (celles ajoutées par vcs_info_hookadd).

Vous pouvez passer des données entre les fonctions via un tableau associatif, user_data. Par exemple :


+vi-git-myfirsthook(){
    user_data[myval]=$myval
}
+vi-git-mysecondhook(){
    # fait quelque chose avec ${user_data[myval]}
}

Il existe un certain nombre de variables spéciales dans les contextes de hook :

ret
La valeur de retour que le système de hooks retournera à l'appelant. La valeur par défaut est un entier `zéro'. Si et comment une valeur de ret modifiée change l'exécution de l'appelant dépend du hook spécifique. Voir la documentation des hooks ci-dessous pour plus de détails.
hook_com
Un tableau associatif utilisé pour la communication bidirectionnelle entre l'appelant et les fonctions de hook. Les clés utilisées dépendent du hook spécifique.
context
Le contexte actif du hook. Les fonctions qui souhaitent modifier cette variable doivent d'abord la rendre locale.
vcs
Le VCS actuel après sa détection. Les mêmes valeurs que dans le style enable/disable sont utilisées. Disponible dans tous les hooks sauf start-up.

Enfin, la liste complète des hooks actuellement disponibles :

start-up
Appelé après le démarrage de vcs_info mais avant que le VCS dans ce répertoire ne soit déterminé. Il peut être utilisé pour désactiver temporairement vcs_info si nécessaire. Lorsque ret est défini sur 1, vcs_info s'interrompt et ne fait rien ; lorsqu'il est défini sur 2, vcs_info configure tout comme si aucun système de contrôle de version n'était actif et se termine.
pre-get-data
Identique à start-up mais après la détection du VCS.
gen-hg-bookmark-string
Appelé dans le backend Mercurial lorsqu'une chaîne de bookmark est générée ; les styles get-revision et get-bookmarks doivent être vrais.

Ce hook reçoit les noms des bookmarks Mercurial que vcs_info a collectés à partir de `hg'.

Si un bookmark est actif, la clé ${hook_com[hg-active-bookmark]} est définie sur son nom. La clé est sinon non définie.

En définissant ret à une valeur non nulle, la chaîne dans ${hook_com[hg-bookmark-string]} sera utilisée dans l'échappement %m dans formats et actionformats et sera disponible dans le tableau global backend_misc en tant que ${backend_misc[bookmarks]}.

gen-applied-string
Appelé dans les backends git (avec stgit ou pendant rebase ou merge), et hg (avec mq) et dans le support quilt lorsque la chaîne applied-string est générée ; le style use-quilt doit être vrai pour quilt (les backends mq et stgit sont actifs par défaut).

Les arguments de ce hook décrivent les patchs appliqués dans l'ordre inverse, ce qui signifie que le premier argument est le patch le plus haut et ainsi de suite.

Lorsque les messages de log des patchs peuvent être extraits, ils sont incorporés dans chaque argument après un espace, de sorte que chaque argument est de la forme `nom-patch première ligne du message de log', où nom-patch ne contient pas d'espace. Le backend mq passe des arguments de la forme `nom de patch', avec des espaces possibles incorporés, mais sans extraire le message de log du patch.

En définissant ret à une valeur non nulle, la chaîne dans ${hook_com[applied-string]} sera disponible en tant que %p dans les styles patch-format et nopatch-format. Ce hook est, en concertation avec set-patch-format, responsable de l'échappement en % de cette valeur pour une utilisation dans le prompt. (Voir la section Particularités.)

Le backend quilt passe à ce hook les entrées ${hook_com[quilt-patches-dir]} et, si elle a été déterminée, ${hook_com[quilt-pc-dir]}.

gen-unapplied-string
Appelé dans les backends git (avec stgit ou pendant rebase), et hg (avec mq) et dans le support quilt lorsque la chaîne unapplied-string est générée ; le style get-unapplied doit être vrai.

Ce hook reçoit les noms de tous les patchs non appliqués que vcs_info ordonne, ce qui signifie que le premier argument est le patch suivant à appliquer et ainsi de suite.

Le format de chaque argument est le même que pour gen-applied-string, ci-dessus.

En définissant ret à une valeur non nulle, la chaîne dans ${hook_com[unapplied-string]} sera disponible en tant que %u dans les styles patch-format et nopatch-format. Ce hook est, en concertation avec set-patch-format, responsable de l'échappement en % de cette valeur pour une utilisation dans le prompt. (Voir la section Particularités.)

Le backend quilt passe à ce hook les entrées ${hook_com[quilt-patches-dir]} et, si elle a été déterminée, ${hook_com[quilt-pc-dir]}.

gen-mqguards-string
Appelé dans le backend hg lorsque la chaîne guards-string est générée ; le style get-mq doit être vrai (par défaut).

Ce hook reçoit les noms de tous les gardes mq actifs.

En définissant ret à une valeur non nulle, la chaîne dans ${hook_com[guards-string]} sera utilisée dans l'échappement %g dans les styles patch-format et nopatch-format.

no-vcs
Ce hook est appelé lorsqu'aucun système de contrôle de version n'a été détecté.

Le paramètre `hook_com' n'est pas utilisé.

post-backend
Appelé dès que le backend a fini de collecter les informations.

Les clés `hook_com' disponibles sont les mêmes que pour le hook set-message.

post-quilt
Appelé après que le support quilt soit terminé. Les informations suivantes sont passées en arguments au hook : 1. le mode de support quilt (`addon' ou `standalone') ; 2. le répertoire qui contient la série de patchs ; 3. le répertoire qui contient les informations de statut de quilt (le répertoire `.pc') ou la chaîne "-nopc-" si ce répertoire n'a pas été trouvé.

Le paramètre `hook_com' n'est pas utilisé.

set-branch-format
Appelé avant que `branchformat' ne soit défini. Le seul argument du hook est le format configuré à ce moment.

Les clés `hook_com' considérées sont `branch' et `revision'. Elles sont définies aux valeurs déterminées jusqu'à présent par vcs_info et tout changement sera utilisé directement lorsque le remplacement réel sera effectué.

Si ret est défini à une valeur non nulle, la chaîne dans ${hook_com[branch-replace]} sera utilisée inchangée comme le remplacement `%b' dans les variables définies par vcs_info.

set-hgrev-format
Appelé avant qu'un `hgrevformat' ne soit défini. Le seul argument du hook est le format configuré à ce moment.

Les clés `hook_com' considérées sont `hash' et `localrev'. Elles sont définies aux valeurs déterminées jusqu'à présent par vcs_info et tout changement sera utilisé directement lorsque le remplacement réel sera effectué.

Si ret est défini à une valeur non nulle, la chaîne dans ${hook_com[rev-replace]} sera utilisée inchangée comme le remplacement `%i'cement dans les variables définies par vcs_info.

pre-addon-quilt
Ce hook est utilisé lorsque la fonctionnalité quilt de vcs_info est active en mode "addon" (quilt utilisé par-dessus un système de contrôle de version réel). Il est activé juste avant qu'une action spécifique à quilt ne soit effectuée.

Définir la variable `ret' dans ce hook à une valeur non nulle évite que des actions spécifiques à quilt ne soient exécutées.

set-patch-format
Ce hook est utilisé pour contrôler certaines des expansions possibles dans les styles patch-format et nopatch-format avec des systèmes de files de patchs tels que quilt, mqueue et autres.

Ce hook est utilisé dans les backends git, hg et quilt.

Le hook permet de contrôler l'expansion de %p ( ${hook_com[applied]}) et %u (${hook_com[unapplied]}) dans tous les backends qui utilisent le hook. Avec le backend mercurial, l'expansion %g (${hook_com[guards]}) est contrôlable en plus de cela.

Si ret est défini à une valeur non nulle, la chaîne de caractères dans ${hook_com[patch-replace]} sera utilisée telle quelle au lieu d'un format développé à partir de patch-format ou nopatch-format.

Ce hook, de concert avec les hooks gen-applied-string ou gen-unapplied-string s'ils sont définis, est responsable de l'échappement des caractères % de la valeur finale de patch-format pour l'utilisation dans l'invite. (Voir la section Oddities.)

Le backend quilt transmet à ce hook les entrées ${hook_com[quilt-patches-dir]} et, si elle a été déterminée, ${hook_com[quilt-pc-dir]}.

set-message
Appelé chaque fois avant qu'un message `vcs_info_msg_N_' ne soit défini. Il prend deux arguments ; le premier étant le `N' dans le nom de la variable du message, le second étant les formats ou actionformats actuellement configurés.

Il existe un certain nombre de clés `hook_com' utilisées ici : `action', `branch', `base', `base-name', `subdir', `staged', `unstaged', `revision', `misc', `vcs' et une entrée `miscN' pour chaque champ de données spécifique au backend (N commençant à zéro). Elles sont définies aux valeurs déterminées jusqu'à présent par vcs_info et tout changement sera utilisé directement lors du remplacement réel.

Comme ce hook est déclenché plusieurs fois (une fois pour chaque formats ou actionformats configuré), chacune des clés `hook_com' mentionnées ci-dessus (à l'exception des entrées miscN) a un pendant `_orig', donc même si vous avez modifié une valeur à votre convenance, vous pouvez toujours obtenir la valeur d'origine lors de la prochaine exécution. Modifier les valeurs `_orig' n'est probablement pas une bonne idée.

Si ret est défini à une valeur non nulle, la chaîne dans ${hook_com[message]} sera utilisée telle quelle comme message par vcs_info.

Si tout cela vous semble assez confus, jetez un œil à la section Exemples ci-dessous ainsi qu'au fichier Misc/vcs_info-examples dans la source de Zsh. Ils contiennent du code explicatif.

Exemples

Ne pas utiliser vcs_info du tout (même s'il est dans votre invite) :

zstyle ':vcs_info:*' enable NONE

Désactiver les backends pour bzr et svk :

zstyle ':vcs_info:*' disable bzr svk

Désactiver tout sauf bzr et svk :

zstyle ':vcs_info:*' enable bzr svk

Fournir des formats spéciaux pour git :

zstyle ':vcs_info:git:*' formats       ' GIT, BABY! [%b]'
zstyle ':vcs_info:git:*' actionformats ' GIT ACTION! [%b|%a]'

Toutes les expansions %x dans toutes sortes de formats (formats, actionformats, branchformat, etc.) sont effectuées à l'aide de la commande intégrée `zformat' du module `zsh/zutil'. Cela signifie que vous pouvez faire avec ces éléments %x tout ce que zformat prend en charge. En particulier, si vous voulez qu'une chaîne très longue ait une largeur fixe, comme un hash dans un branchformat mercurial, vous pouvez faire ceci : %12.12i. Cela réduira le hash de 40 caractères à ses 12 premiers caractères. La forme est en fait `%min.maxx'. Plus est possible. Voir la section `The zsh/zutil Module' dans zshmodules(1) pour plus de détails.

Utiliser le backend bzr plus rapide

zstyle ':vcs_info:bzr:*' use-simple true

Si vous utilisez use-simple, veuillez signaler si cela fait `la bonne chose[tm]'.

Afficher le numéro de révision en jaune pour bzr et svn :

zstyle ':vcs_info:(svn|bzr):*' \ 
       branchformat '%b%%F{yellow}:%r'

Le double signe pour cent s'explique dans la section Oddities.

Alternativement, on peut utiliser directement les codes de couleur bruts :

zstyle ':vcs_info:(svn|bzr):*' \ 
       branchformat '%b%{'${fg[yellow]}'%}:%r'

Normalement, lorsqu'une variable est interpolée dans une chaîne de format, la variable doit être échappée avec des caractères %. Dans cet exemple, nous avons omis cela car nous supposons que la valeur de ${fg[yellow]} ne contient aucun signe %.

Assurez-vous d'enfermer les codes de couleur dans %{...%} si vous souhaitez utiliser la chaîne fournie par vcs_info dans les invites.

Voici comment afficher les informations VCS sous forme de commande (pas dans une invite) :

vcsi() { vcs_info interactive; vcs_info_lastmsg }

De cette façon, vous pouvez même définir différents formats pour la sortie via vcs_info_lastmsg dans l'espace de noms ':vcs_info:*:interactive:*'.

Maintenant, comme promis, voici un code qui utilise des hooks : disons, vous aimeriez remplacer la chaîne `svn' par `subversion' dans le remplacement des formats %s de vcs_info.

Tout d'abord, nous allons dire à vcs_info d'appeler une fonction lors du remplissage des variables de message avec les informations collectées :

zstyle ':vcs_info:*+set-message:*' hooks svn2subversion

Rien ne se passe. Ce qui est raisonnable, car nous n'avons pas encore défini la fonction réelle. Pour voir ce que le sous-système de hooks essaie de faire, activez le style `debug' :

zstyle ':vcs_info:*+*:*' debug true

Cela devrait vous donner une idée de ce qui se passe. Spécifiquement, la fonction que nous recherchons est `+vi-svn2subversion'. Notez le préfixe `+vi-'. Donc, tout est en ordre, comme documenté. Lorsque vous avez fini de vérifier la sortie de débogage, désactivez-la à nouveau :

zstyle ':vcs_info:*+*:*' debug false

Maintenant, définissons la fonction :


function +vi-svn2subversion() {
    [[ ${hook_com[vcs_orig]} == svn ]] && hook_com[vcs]=subversion
}

Assez simple. Et cela aurait pu être encore plus simple, si seulement nous avions enregistré notre fonction dans un contexte moins générique. Si nous le faisons uniquement dans le contexte du backend `svn', nous n'avons pas besoin de tester quel est le backend actif :

zstyle ':vcs_info:svn+set-message:*' hooks svn2subversion

function +vi-svn2subversion() {
    hook_com[vcs]=subversion
}

Et enfin, un exemple un peu plus élaboré, qui utilise un hook pour créer une chaîne de signets personnalisée pour le backend hg.

Là encore, nous commençons par enregistrer une fonction :

zstyle ':vcs_info:hg+gen-hg-bookmark-string:*' hooks hgbookmarks

Et ensuite, nous définissons la fonction `+vi-hgbookmarks' :


function +vi-hgbookmarks() {
    # La valeur par défaut consiste à connecter tous les noms de signets par
    # des virgules. Cela mélange un peu les choses.
    # Imaginez, il y a un type de signets qui est
    # spécial pour vous. Par exemple, parce que c'est *votre* travail.
    # Ces signets ressemblent toujours à ceci : "sh/*"
    # (parce que vos initiales sont sh, par exemple).
    # Cela fait que la chaîne de signets n'utilise que ces
    # signets. S'il y en a plus d'un, cela
    # les concatène en utilisant des virgules.
    # Les signets retournés par `hg' sont disponibles dans
    # les paramètres positionnels de la fonction.
    local s="${(Mj:,:)@:#sh/*}"
    # Maintenant, la communication avec le code qui appelle
    # les fonctions de hook se fait via le tableau associatif hook_com[]
    # La clé sur laquelle le hook `gen-hg-bookmark-string'
    # recherche est `hg-bookmark-string'. Donc :
    hook_com[hg-bookmark-string]=$s
    # Et pour signaler que nous voulons utiliser la chaîne que nous
    # venons de générer, définissez la variable spéciale `ret' à
    # autre chose que le zéro par défaut :
    ret=1
    return 0
}

Des exemples plus longs et des extraits de code qui pourraient être utiles sont disponibles dans le fichier d'exemples situé à Misc/vcs_info-examples dans le répertoire source de Zsh.

Ceci conclut notre visite guidée de vcs_info de zsh.

PROMPT THEMES

Installation

Vous devriez vous assurer que toutes les fonctions du répertoire Functions/Prompts de la distribution source sont disponibles ; elles commencent toutes par la chaîne `prompt_' à l'exception de la fonction spéciale `promptinit'. Vous avez également besoin des fonctions `colors' et `add-zsh-hook' de Functions/Misc. Toutes ces fonctions sont peut-être déjà installées sur votre système ; sinon, vous devrez les trouver et les copier. Le répertoire devrait apparaître comme l'un des éléments du tableau fpath (ce qui devrait déjà être le cas s'ils ont été installés), et au moins la fonction promptinit devrait être chargée automatiquement ; elle chargera automatiquement les autres. Enfin, pour initialiser l'utilisation du système, vous devez appeler la fonction promptinit. Le code suivant dans votre .zshrc organisera cela ; supposez que les fonctions sont stockées dans le répertoire ~/myfns :

fpath=(~/myfns $fpath)
autoload -U promptinit
promptinit

Sélection du thème

Utilisez la commande prompt pour sélectionner votre thème préféré. Cette commande peut être ajoutée à votre .zshrc après l'appel à promptinit afin de démarrer zsh avec un thème déjà sélectionné.

prompt [ -c | -l ]
prompt [ -p | -h ] [ thème ... ]
prompt [ -s ] thème [ arg ... ]
Définit ou examine le thème de l'invite. Sans options et avec un argument thème, le thème portant ce nom est défini comme thème actuel. Les thèmes disponibles sont déterminés au moment de l'exécution ; utilisez l'option -l pour voir une liste. Le thème spécial `random' sélectionne au hasard l'un des thèmes disponibles et définit votre invite à celui-ci.

Dans certains cas, le thème peut être modifié par un ou plusieurs arguments, qui doivent être donnés après le nom du thème. Voir l'aide de chaque thème pour la description de ces arguments.

Options :

-c
Affiche le thème actuellement sélectionné et ses paramètres, le cas échéant.
-l
Liste tous les thèmes d'invite disponibles.
-p
Aperçu du thème nommé par thème, ou de tous les thèmes si aucun thème n'est donné.
-h
Affiche l'aide pour le thème nommé par thème, ou pour la fonction prompt si aucun thème n'est donné.
-s
Définit thème comme thème actuel et sauvegarde l'état.
prompt_thème_setup
Chaque thème disponible a une fonction de configuration qui est appelée par la fonction prompt pour installer ce thème. Cette fonction peut définir d'autres fonctions si nécessaire pour maintenir l'invite, y compris des fonctions utilisées pour prévisualiser l'invite ou fournir de l'aide pour son utilisation. Normalement, vous ne devriez pas appeler directement la fonction de configuration d'un thème.

Thèmes utilitaires

prompt off
Le thème `off' définit toutes les variables d'invite à des valeurs minimales sans effets spéciaux.
prompt default
Le thème `default' définit toutes les variables d'invite dans le même état que si un zsh interactif était démarré sans fichiers d'initialisation.
prompt restore
Le thème spécial `restore' efface tous les paramètres du thème et redéfinit les variables d'invite à leur état antérieur à la première exécution de la fonction `prompt', à condition que chaque thème ait correctement défini son nettoyage (voir ci-dessous).

Notez que vous pouvez annuler `prompt off' et `prompt default' avec `prompt restore', mais un second restore n'annule pas le premier.

Écriture de thèmes

La première étape pour ajouter votre propre thème est de choisir un nom pour celui-ci et de créer un fichier `prompt_nom_setup' dans un répertoire de votre fpath, tel que ~/myfns dans l'exemple ci-dessus. Le fichier doit au minimum contenir les affectations pour les variables d'invite que votre thème souhaite modifier. Par convention, les thèmes utilisent PS1, PS2, RPS1, etc., plutôt que les plus longs PROMPT et RPROMPT.

Le fichier est chargé automatiquement en tant que fonction dans le contexte de shell actuel, il peut donc contenir toutes les commandes nécessaires pour personnaliser votre thème, y compris la définition de fonctions supplémentaires. Pour faciliter certaines tâches complexes, votre fonction de configuration peut également faire l'une des choses suivantes :

Affecter prompt_opts
Le tableau prompt_opts peut être affecté à l'une des valeurs "bang", "cr", "percent", "sp", et/ou "subst". Les `setopts` correspondants (promptbang, etc.) sont activés, toutes les autres options liées à l'invite sont désactivées. Le tableau prompt_opts conserve les `setopts` même au-delà de la portée de localoptions, si votre fonction en a besoin.
Modifier les hooks
L'utilisation de add-zsh-hook et add-zle-hook-widget est recommandée (voir la section Manipulation des fonctions de hook ci-dessus). Tous les hooks qui suivent le modèle de nommage prompt_thème_hook sont automatiquement supprimés lorsque le thème de l'invite change ou est désactivé.
Déclarer le nettoyage
Si votre fonction effectue d'autres modifications qui doivent être annulées lorsque le thème est désactivé, votre fonction de configuration peut appeler
prompt_cleanup commande

où commande doit être correctement citée. Si votre thème est jamais désactivé ou remplacé par un autre, commande est exécutée avec eval. Vous pouvez déclarer plusieurs hooks de nettoyage.

Définir un aperçu
Définir ou charger automatiquement une fonction prompt_nom_preview pour afficher une version simulée de votre invite. Un aperçu simple par défaut est défini par promptinit pour les thèmes qui n'en définissent pas. Cette fonction d'aperçu est appelée par `prompt -p'.
Fournir de l'aide
Définir ou charger automatiquement une fonction prompt_nom_help pour afficher la documentation ou le texte d'aide pour votre thème. Cette fonction d'aide est appelée par `prompt -h'.

FONCTIONS ZLE

Widgets

Ces fonctions implémentent toutes des widgets ZLE définis par l'utilisateur (voir zshzle(1)) qui peuvent être associés à des combinaisons de touches dans les shells interactifs. Pour les utiliser, votre .zshrc doit contenir des lignes de la forme

autoload fonction
zle -N fonction

suivies d'une commande bindkey appropriée pour associer la fonction à une séquence de touches. Les liaisons suggérées sont décrites ci-dessous.

Fonctions de mot de style bash
Si vous recherchez des fonctions pour implémenter le déplacement sur et l'édition de mots à la manière de bash, où seuls les caractères alphanumériques sont considérés comme des caractères de mot, vous pouvez utiliser les fonctions décrites dans la section suivante. Ce qui suit est suffisant :
autoload -U select-word-style
select-word-style bash
forward-word-match, backward-word-match
kill-word-match, backward-kill-word-match
transpose-words-match, capitalize-word-match
up-case-word-match, down-case-word-match
delete-whole-word-match, select-word-match
select-word-style, match-word-context, match-words-by-style
Les huit premières fonctions `-match' sont des remplacements directs des widgets intégrés sans le suffixe. Par défaut, elles se comportent de manière similaire. Cependant, grâce à l'utilisation de styles et de la fonction select-word-style, la manière dont les mots sont correspondus peut être modifiée. select-word-match est destiné à être utilisé comme un objet texte en mode vi mais avec des styles de mot personnalisés. À titre de comparaison, les widgets décrits dans zshzle(1) sous Objets texte utilisent des définitions de mots fixes, compatibles avec l'éditeur vim.

La manière la plus simple de configurer les fonctions est d'utiliser select-word-style, qui peut être appelé comme une fonction normale avec l'argument approprié, ou invoqué comme un widget défini par l'utilisateur qui demandera le premier caractère du style de mot à utiliser. La première fois qu'il est invoqué, les huit premières fonctions -match remplaceront automatiquement les versions intégrées, elles n'ont donc pas besoin d'être chargées explicitement.

Les styles de mots disponibles sont les suivants. Seul le premier caractère est examiné.

bash
Les caractères de mot sont uniquement des caractères alphanumériques.
normal
Comme dans le fonctionnement normal du shell : les caractères de mot sont les caractères alphanumériques plus tous les caractères présents dans la chaîne donnée par le paramètre $WORDCHARS.
shell
Les mots sont des arguments de commande shell complets, incluant éventuellement des chaînes entre guillemets complètes, ou tout jeton spécial pour le shell.
whitespace
Les mots sont des ensembles de caractères délimités par des espaces blancs.
default
Restaure les paramètres par défaut ; c'est généralement la même chose que `normal'.

Tous les styles, sauf `default', peuvent être entrés comme un caractère majuscule, ce qui a le même effet mais avec la correspondance de sous-mots activée. Dans ce cas, les mots avec des majuscules sont traités spécialement : chaque suite distincte de majuscules, ou une majuscule suivie d'un nombre quelconque d'autres caractères, est considérée comme un mot. Le style subword-range peut fournir une plage de caractères alternative à la plage par défaut `[:upper:]' ; la valeur du style est traitée comme le contenu d'un motif `[...]' (notez que les crochets externes ne doivent pas être fournis, uniquement ceux qui entourent les plages nommées).

Un contrôle plus fin peut être obtenu en utilisant la commande zstyle, comme décrit dans zshmodules(1). Chaque style est recherché dans le contexte :zle:widget où widget est le nom du widget défini par l'utilisateur, et non le nom de la fonction qui l'implémente. Dans le cas des définitions fournies par select-word-style, les contextes appropriés sont :zle:forward-word, et ainsi de suite. La fonction select-word-style elle-même définit toujours des styles pour le contexte `:zle:*' qui peuvent être remplacés par des motifs plus spécifiques (plus longs) ainsi que des contextes explicites.

Le style word-style spécifie

ifies les règles à utiliser. Cela peut avoir les valeurs suivantes.

normal
Utiliser les règles standard du shell, c'est-à-dire les caractères alphanumériques et $WORDCHARS, sauf dérogation par les styles word-chars ou word-class.
specified
Similaire à normal, mais *uniquement* les caractères spécifiés, et non pas aussi les caractères alphanumériques, sont considérés comme des caractères de mots.
unspecified
La négation de specified. Les caractères donnés sont ceux qui ne seront *pas* considérés comme faisant partie d'un mot.
shell
Les mots sont obtenus en utilisant les règles syntaxiques pour générer des arguments de commande shell. De plus, les jetons spéciaux qui ne sont jamais des arguments de commande tels que `()' sont également traités comme des mots.
whitespace
Les mots sont des chaînes de caractères délimitées par des espaces blancs.

Les trois premières de ces règles utilisent généralement $WORDCHARS, mais la valeur du paramètre peut être remplacée par le style word-chars, qui fonctionne exactement de la même manière que $WORDCHARS. De plus, le style word-class utilise la syntaxe des classes de caractères pour regrouper les caractères et a la priorité sur word-chars si les deux sont définis. Le style word-class n'inclut pas les crochets environnants de la classe de caractères ; par exemple, `-:[:alnum:]' est une word-class valide pour inclure tous les caractères alphanumériques plus les caractères `-' et `:'. Faites attention à inclure `]', `^' et `-' car ils sont spéciaux à l'intérieur des classes de caractères.

word-style peut également avoir `-subword' ajouté à sa valeur pour activer la correspondance de sous-mots, comme décrit ci-dessus.

Le style skip-chars est principalement utile pour transpose-words et les fonctions similaires. S'il est défini, il donne un compte de caractères à partir de la position du curseur qui ne seront pas considérés comme faisant partie du mot et qui sont traités comme des espaces, quelle que soit leur nature réelle. Par exemple, si

zstyle ':zle:transpose-words' skip-chars 1

a été défini, et que transpose-words-match est appelé avec le curseur sur le *X* de fooXbar, où *X* peut être n'importe quel caractère, alors l'expression résultante est barXfoo.

Un contrôle plus fin peut être obtenu en définissant le style word-context à un tableau de paires d'entrées. Chaque paire d'entrées se compose d'un *motif* et d'un *sous-contexte*. L'argument shell sur lequel se trouve le curseur est mis en correspondance avec chaque *motif* successivement jusqu'à ce que l'un corresponde ; s'il correspond, le contexte est étendu par un deux-points et le *sous-contexte* correspondant. Notez que le test est effectué sur le mot d'origine sur la ligne, sans suppression des guillemets. Une gestion spéciale est effectuée entre les mots : le contexte actuel est examiné et s'il contient la chaîne between, le mot est défini sur un seul espace ; sinon, s'il contient la chaîne back, le mot avant le curseur est considéré ; sinon, le mot après le curseur est considéré. Quelques exemples sont donnés ci-dessous.

Le style skip-whitespace-first n'est utilisé qu'avec le widget forward-word. S'il est défini à vrai, alors forward-word saute tous les caractères non-mot, suivis de tous les caractères non-mot : ceci est similaire au comportement des autres widgets orientés mot, et aussi à celui utilisé par d'autres éditeurs, cependant il diffère du comportement standard de zsh. Lors de l'utilisation de select-word-style, le widget est défini dans le contexte :zle:* à true si le style de mot est bash et false sinon. Il peut être remplacé en le définissant dans le contexte plus spécifique :zle:forward-word*.

Il est possible de créer des widgets avec un comportement spécifique en définissant un nouveau widget implémenté par la fonction générique appropriée, puis en définissant un style pour le contexte du widget spécifique. Par exemple, le code suivant définit un widget backward-kill-space-word utilisant backward-kill-word-match, la fonction générique implémentant le comportement de backward-kill-word, et garantit que le nouveau widget implémente toujours un comportement délimité par des espaces.

zle -N backward-kill-space-word backward-kill-word-match
zstyle :zle:backward-kill-space-word word-style space

Le widget backward-kill-space-word peut maintenant être lié à une touche.

Voici quelques exemples supplémentaires d'utilisation des styles, en fait tirés de l'interface simplifiée de select-word-style:

zstyle ':zle:*' word-style standard
zstyle ':zle:*' word-chars ''

Implémente la gestion des mots de style bash pour tous les widgets, c'est-à-dire que seuls les caractères alphanumériques sont des caractères de mots ; équivalent à définir le paramètre WORDCHARS vide pour le contexte donné.

style ':zle:*kill*' word-style space

Utilise des mots délimités par des espaces pour les widgets dont le nom contient le mot `kill'. Ni les styles word-chars ni word-class ne sont utilisés dans ce cas.

Voici quelques exemples d'utilisation du style word-context pour étendre le contexte.

zstyle ':zle:*' word-context \
       "*/*" filename "[[:space:]]" whitespace
zstyle ':zle:transpose-words:whitespace' word-style shell
zstyle ':zle:transpose-words:filename' word-style normal
zstyle ':zle:transpose-words:filename' word-chars ''

Ceci fournit deux manières différentes d'utiliser transpose-words selon que le curseur se trouve sur un espace blanc entre les mots ou sur un nom de fichier, ici tout mot contenant un /. Sur un espace blanc, les arguments complets tels que définis par les règles standard du shell seront transposés. Dans un nom de fichier, seuls les caractères alphanumériques seront transposés. Ailleurs, les mots seront transposés en utilisant le style par défaut pour :zle:transpose-words.

La mise en correspondance des mots et toute la gestion des paramètres zstyle est en réalité implémentée par la fonction match-words-by-style. Celle-ci peut être utilisée pour créer de nouveaux widgets définis par l'utilisateur. La fonction appelante doit définir le paramètre local curcontext à :zle:widget, créer le paramètre local matched_words et appeler match-words-by-style sans arguments. Au retour, matched_words sera défini comme un tableau avec les éléments : (1) le début de la ligne (2) le mot avant le curseur (3) les caractères non-mot entre ce mot et le curseur (4) le ou les caractères non-mot à la position du curseur plus les caractères non-mot restants avant le mot suivant, y compris tous les caractères spécifiés par le style skip-chars, (5) le mot au niveau ou après le curseur (6) les caractères non-mot suivant ce mot (7) le reste de la ligne. N'importe lequel des éléments peut être une chaîne vide ; la fonction appelante doit tester cela pour décider si elle peut effectuer sa fonction.

Si la variable matched_words est définie par l'appelant de match-words-by-style comme un tableau associatif (local -A matched_words), alors les sept valeurs données ci-dessus doivent être récupérées à partir d'elle sous forme d'éléments nommés start, word-before-cursor, ws-before-cursor, ws-after-cursor, word-after-cursor, ws-after-word, et end. De plus, l'élément is-word-start vaut 1 si le curseur se trouve au début d'un mot ou d'un sous-mot, ou sur un espace blanc avant celui-ci (les cas peuvent être distingués en testant l'élément ws-after-cursor) et 0 sinon. Cette forme est recommandée pour la compatibilité future.

Il est possible de passer des options avec des arguments à match-words-by-style pour remplacer l'utilisation des styles. Les options sont :

-w
word-style
-s
skip-chars
-c
word-class
-C
word-chars
-r
subword-range

Par exemple, match-words-by-style -w shell -c 0 peut être utilisé pour extraire l'argument de commande autour du curseur.

Le style word-context est implémenté par la fonction match-word-context. Celle-ci ne devrait normalement pas avoir besoin d'être appelée directement.

bracketed-paste-magic
Le widget bracketed-paste (voir la sous-section `Divers' dans zshzle(1)) insère le texte collé littéralement dans le tampon de l'éditeur au lieu de l'interpréter comme des frappes. Cela désactive certaines utilisations courantes où le widget d'auto-insertion est remplacé afin d'effectuer un traitement supplémentaire. Un exemple est le widget contributeur url-quote-magic décrit ci-dessous.

Le widget bracketed-paste-magic est destiné à remplacer bracketed-paste par un wrapper qui réactive ces actions d'auto-insertion, et d'autres actions sélectionnées par zstyles. Par conséquent, ce widget est installé avec

autoload -Uz bracketed-paste-magic
zle -N bracketed-paste bracketed-paste-magic

Outre l'activation de certains traitements de widgets, bracketed-paste-magic tente de répliquer bracketed-paste aussi fidèlement que possible.

Les zstyles suivants peuvent être définis pour contrôler le traitement du texte collé. Tous sont recherchés dans le contexte `:bracketed-paste-magic'.

active-widgets
Une liste de motifs correspondant aux noms de widgets qui doivent être activés pendant le collage. Toutes les autres séquences de touches sont traitées comme self-insert-unmeta. La valeur par défaut est `self-*' de sorte que tous les widgets définis par l'utilisateur portant ce préfixe soient actifs avec l'auto-insertion intégrée.

Si ce style n'est pas défini (explicitement supprimé) ou défini à une valeur vide, aucun widget n'est actif et le texte collé est inséré littéralement. Si la valeur inclut `undefined-key', les séquences inconnues sont supprimées du texte collé.

inactive-keys
L'inverse de active-widgets, une liste de séquences de touches qui utilisent toujours self-insert-unmeta même lorsqu'elles sont liées à un widget actif. Notez qu'il s'agit d'une liste de séquences de touches littérales, pas de motifs.
paste-init
Une liste de noms de fonctions, appelées dans le contexte du widget (mais pas comme des widgets). Les fonctions sont appelées dans l'ordre jusqu'à ce que l'une d'elles retourne un statut non nul. Le paramètre `PASTED' contient l'état initial du texte collé. Tout autre Z
LE tels que `BUFFER' ont leurs valeurs normales et effets secondaires, et l'historique complet est disponible, donc par exemple les fonctions paste-init peuvent déplacer des mots de BUFFER vers PASTED pour rendre ces mots visibles aux active-widgets.

Un retour non nul d'une fonction paste-init n'empêche pas que le collage lui-même se poursuive.

Charger bracketed-paste-magic définit backward-extend-paste, une fonction d'aide à utiliser dans paste-init.

zstyle :bracketed-paste-magic paste-init \ 
       backward-extend-paste

Lorsqu'un collage insérerait au milieu d'un mot ou ajouterait du texte à un mot déjà sur la ligne, backward-extend-paste déplace le préfixe de LBUFFER vers PASTED afin que les active-widgets voient le mot complet jusqu'à présent. Cela peut être utile avec url-quote-magic.

paste-finish
Une autre liste de noms de fonctions appelées dans l'ordre jusqu'à ce que l'une d'elles retourne une valeur non nulle. Ces fonctions sont appelées *après* que le texte collé a été traité par les active-widgets, mais *avant* qu'il ne soit inséré dans `BUFFER'. Les paramètres ZLE ont leurs valeurs normales et effets secondaires.

Un retour non nul d'une fonction paste-finish n'empêche pas que le collage lui-même se poursuive.

Charger bracketed-paste-magic définit également quote-paste, une fonction d'aide à utiliser dans paste-finish.

zstyle :bracketed-paste-magic paste-finish \ 
       quote-paste
zstyle :bracketed-paste-magic:finish quote-style \ 
       qqq

Lorsque le texte collé est inséré dans BUFFER, il est cité selon la valeur de quote-style. Pour désactiver de force le citage numérique intégré du préfixe de bracketed-paste, utilisez :

zstyle :bracketed-paste-magic:finish quote-style \ 
       none

Important : Pendant le traitement par les active-widgets du collage (après paste-init et avant paste-finish), BUFFER est vide et l'historique est restreint, donc les mouvements du curseur, etc., peuvent ne pas dépasser le contenu collé. Le texte assigné à BUFFER par les widgets actifs est copié dans PASTED avant paste-finish.

copy-earlier-word
Ce widget fonctionne comme une combinaison de insert-last-word et copy-prev-shell-word. Des invocations répétées du widget récupèrent des mots précédents sur la ligne d'historique pertinente. Avec un argument numérique N, insère le Nème mot de la ligne d'historique ; N peut être négatif pour compter à partir de la fin de la ligne.

Si insert-last-word a été utilisé pour récupérer le dernier mot d'une ligne d'historique précédente, des invocations répétées remplaceront ce mot par des mots précédents de la même ligne.

Sinon, le widget s'applique aux mots de la ligne en cours d'édition. Le style widget peut être défini sur le nom d'un autre widget qui devrait être appelé pour récupérer des mots. Ce widget doit accepter les mêmes trois arguments que insert-last-word.

cycle-completion-positions
Après avoir inséré une chaîne non ambiguë dans la ligne de commande, le nouveau système de complétion basé sur les fonctions peut connaître plusieurs endroits dans cette chaîne où des caractères manquent ou diffèrent d'au moins une des correspondances possibles. Il placera alors le curseur à la position qu'il considère comme la plus intéressante, c'est-à-dire celle où l'on peut désambiguïser entre autant de correspondances que possible avec le moins de frappes possible.

Ce widget permet de déplacer facilement le curseur vers les autres points intéressants. Il peut être invoqué plusieurs fois pour parcourir toutes les positions signalées par le système de complétion.

delete-whole-word-match
C'est une autre fonction qui fonctionne comme les fonctions -match décrites immédiatement ci-dessus, c'est-à-dire en utilisant des styles pour décider des limites de mots. Cependant, ce n'est pas un remplacement pour une fonction existante.

Le comportement de base est de supprimer le mot autour du curseur. Il n'y a pas de gestion d'arguments numériques ; seul le mot unique autour du curseur est pris en compte. Si le widget contient la chaîne kill, le texte supprimé sera placé dans le tampon de copie pour des collages ultérieurs. Ceci peut être obtenu en définissant kill-whole-word-match comme suit :

zle -N kill-whole-word-match delete-whole-word-match

et ensuite en liant le widget kill-whole-word-match.

up-line-or-beginning-search, down-line-or-beginning-search
Ces widgets sont similaires aux fonctions intégrées up-line-or-search et down-line-or-search : s'ils sont dans un tampon multiligne, ils se déplacent vers le haut ou vers le bas dans le tampon, sinon ils recherchent une ligne d'historique correspondant au début de la ligne actuelle. Dans ce cas, ils recherchent une ligne qui correspond à la ligne actuelle jusqu'à la position actuelle du curseur, à la manière de history-beginning-search-backward et -forward, plutôt que le premier mot de la ligne.
edit-command-line
Éditez la ligne de commande en utilisant votre éditeur visuel, comme dans ksh.
bindkey -M vicmd v edit-command-line

L'éditeur à utiliser peut également être spécifié en utilisant le style editor dans le contexte du widget. Il est spécifié comme un tableau de commande et d'arguments :

zstyle :zle:edit-command-line editor gvim -f
expand-absolute-path
Développe le nom de fichier sous le curseur en un chemin absolu, en résolvant les liens symboliques. Dans la mesure du possible, le segment de chemin initial est transformé en un répertoire nommé ou une référence au répertoire personnel de l'utilisateur.
history-search-end
Cette fonction implémente les widgets history-beginning-search-backward-end et history-beginning-search-forward-end. Ces commandes fonctionnent en appelant d'abord le widget intégré correspondant (voir `Contrôle de l'historique' dans zshzle(1)) puis en déplaçant le curseur à la fin de la ligne. La position initiale du curseur est mémorisée et restaurée avant d'appeler une seconde fois le widget intégré, de sorte que la même recherche soit répétée pour regarder plus loin dans l'historique.

Bien que vous autoloadiez une seule fonction, les commandes pour l'utiliser sont légèrement différentes car elle implémente deux widgets.

zle -N history-beginning-search-backward-end \ 
       history-search-end
zle -N history-beginning-search-forward-end \ 
       history-search-end
bindkey '\e^P' history-beginning-search-backward-end
bindkey '\e^N' history-beginning-search-forward-end
history-beginning-search-menu
Cette fonction implémente une autre forme de recherche dans l'historique. Le texte avant le curseur est utilisé pour sélectionner des lignes dans l'historique, comme pour history-beginning-search-backward, sauf que toutes les correspondances sont affichées dans un menu numéroté. La saisie des chiffres appropriés insère la ligne complète de l'historique. Notez que les zéros initiaux doivent être saisis (ils ne sont affichés que lorsque nécessaire pour éliminer l'ambiguïté). L'intégralité de l'historique est recherchée ; il n'y a pas de distinction entre avant et arrière.

Avec un argument numérique, la recherche n'est pas ancrée au début de la ligne ; la chaîne tapée par l'utilisateur peut apparaître n'importe où dans la ligne de l'historique.

Si le nom du widget contient `-end', le curseur est déplacé à la fin de la ligne insérée. Si le nom du widget contient `-space', tout espace dans le texte tapé est traité comme un joker et peut correspondre à n'importe quoi (donc un espace initial équivaut à donner un argument numérique). Les deux formes peuvent être combinées, par exemple :

zle -N history-beginning-search-menu-space-end \ 
       history-beginning-search-menu
history-pattern-search
La fonction history-pattern-search implémente des widgets qui demandent un motif pour rechercher dans l'historique en arrière ou en avant. Le motif est au format zsh habituel, cependant le premier caractère peut être ^ pour ancrer la recherche au début de la ligne, et le dernier caractère peut être $ pour ancrer la recherche à la fin de la ligne. Si la recherche n'était pas ancrée à la fin de la ligne, le curseur est positionné juste après le motif trouvé.

Les commandes pour créer des widgets liables sont similaires à celles de l'exemple immédiatement ci-dessus :

autoload -U history-pattern-search
zle -N history-pattern-search-backward history-pattern-search
zle -N history-pattern-search-forward history-pattern-search
incarg
Taper les séquences de touches de ce widget avec le curseur placé sur ou à gauche d'un entier provoque l'incrémentation de cet entier de un. Avec un argument numérique, le nombre est incrémenté du montant de l'argument (décrémenté si l'argument numérique est négatif). Le paramètre shell incarg peut être défini pour changer l'incrément par défaut à autre chose qu'un.
bindkey '^X+' incarg
incremental-complete-word
Ceci permet la complétion incrémentielle d'un mot. Après avoir lancé cette commande, une liste de choix de complétion peut être affichée après chaque caractère que vous tapez, que vous pouvez supprimer avec ^H ou DEL. Appuyer sur retour accepte la complétion jusqu'à présent et vous ramène à l'édition normale (c'est-à-dire que la ligne de commande n'est *pas* exécutée immédiatement). Vous pouvez appuyer sur TAB pour faire une complétion normale, ^G pour abandonner et revenir à l'état où vous étiez lorsque vous avez commencé, et ^D pour lister les correspondances.

Ceci ne fonctionne qu'avec le nouveau système de complétion basé sur les fonctions.

bindkey '^Xi' incremental-complete-word
insert-composed-char
Cette fonction vous permet de composer des caractères qui n'apparaissent pas sur le clavier pour les insérer dans la ligne de commande. La commande est suivie de deux touches correspondant à des caractères ASCII (il n'y a pas d'invite). Pour les caractères accentués, les deux touches sont un caractère de base suivi d'un code pour l'accent, tandis que pour d'autres caractères spéciaux, les deux caractères forment ensemble une mnémonique pour le caractère à insérer. Les codes à deux caractères sont un sous-ensemble de ceux donnés par la RFC 1345 (voir par exemple http://www.faqs.org/rfcs/rfc1345.html).

La fonction peut éventuellement être suivie de un à deux caractères qui remplacent un ou deux des caractères lus depuis le clavier ; si les deux caractères sont fournis, aucune entrée n'est lue. Par exemple, insert-composed-char a: peut être utilisé dans un widget pour insérer un a avec tréma dans la ligne de commande. Cela présente des avantages par rapport à l'utilisation d'un caractère littéral, car c'est plus portable.

Pour de meilleurs résultats, zsh devrait avoir été compilé avec le support des caractères multibytes (configuré avec --enable-multibyte) ; cependant, la fonction fonctionne pour la gamme limitée de caractères disponibles dans les jeux de caractères à une seule octet tels que l'ISO-8859-1.

Le caractère est converti dans la représentation locale et inséré dans la ligne de commande à la position du curseur. (La conversion est effectuée dans le shell, en utilisant les facilités fournies par la bibliothèque C.) Avec un argument numérique, le caractère et son code sont prévisualisés dans la ligne de statut.

La fonction peut être exécutée en dehors de zle auquel cas elle imprime le caractère (avec un retour à la ligne) sur la sortie standard. L'entrée est toujours lue à partir des frappes.

Voir insert-unicode-char pour une manière alternative d'insérer des caractères Unicode en utilisant leur numéro de caractère hexadécimal.

L'ensemble des caractères accentués est raisonnablement complet jusqu'à le caractère Unicode U+0180, l'ensemble des caractères spéciaux moins. Cependant, il est très sporadique à partir de ce point. narrow-to-region-invisible
Resserre la partie éditable du tampon vers la région située entre le curseur et la marque, qui peuvent être dans n'importe quel ordre. La région ne peut pas être vide.

narrow-to-region peut être utilisé comme widget ou appelé comme fonction à partir d'un widget défini par l'utilisateur ; par défaut, le texte en dehors de la zone éditable reste visible. Une recursive-edit est effectuée et l'état de l'élargissement d'origine est ensuite restauré. Diverses options et arguments sont disponibles lorsqu'il est appelé comme fonction.

Les options -p pretext et -P posttext peuvent être utilisées pour remplacer le texte avant et après l'affichage pour la durée de la fonction ; l'un ou l'autre ou les deux peuvent être une chaîne vide.

Si l'option -n est également fournie, pretext ou posttext ne sera inséré que s'il y a du texte avant ou après la région respectivement qui sera rendu invisible.

Deux arguments numériques peuvent être fournis et seront utilisés à la place des positions du curseur et de la marque.

L'option -S statepm est utilisée pour resserrer selon les autres options tout en sauvegardant l'état d'origine dans le paramètre nommé statepm, tandis que l'option -R statepm est utilisée pour restaurer l'état à partir du paramètre ; notez dans les deux cas que le *nom* du paramètre est requis. Dans le second cas, les autres options et arguments sont sans importance. Lorsque cette méthode est utilisée, aucune recursive-edit n'est effectuée ; le widget appelant doit appeler cette fonction avec l'option -S, effectuer sa propre édition sur la ligne de commande ou passer le contrôle à l'utilisateur via `zle recursive-edit', puis appeler cette fonction avec l'option -R. L'argument statepm doit être un nom approprié pour un paramètre ordinaire, à l'exception des paramètres commençant par le préfixe _ntr_ qui sont réservés à l'usage interne de narrow-to-region. Typiquement, le paramètre sera local à la fonction appelante.

Les options -l lbufvar et -r rbufvar peuvent être utilisées pour spécifier des paramètres où le widget stockera le texte résultant de l'opération. Le paramètre lbufvar contiendra LBUFFER et rbufvar contiendra RBUFFER. Aucune de ces deux options ne peut être utilisée avec -S ou -R.

narrow-to-region-invisible est un widget simple qui appelle narrow-to-region avec des arguments qui remplacent tout texte en dehors de la région par `...'. Il ne prend aucun argument.

L'affichage est restauré (et le widget retourne) lors de toute commande zle qui accepterait ou abandonnerait normalement la ligne. Par conséquent, une commande supplémentaire de ce type est requise pour accepter ou abandonner la ligne actuelle.

Le statut de retour des deux widgets est zéro si la ligne a été acceptée, sinon non nul.

Voici un exemple trivial de widget utilisant cette fonctionnalité.

local state
narrow-to-region -p $'Édition de région restreinte\n' \ 
  -P '' -S state
zle recursive-edit
narrow-to-region -R state
predict-on
Cet ensemble de fonctions implémente la frappe prédictive à l'aide de la recherche dans l'historique. Après predict-on, la saisie de caractères amène l'éditeur à rechercher dans l'historique la première ligne commençant par ce que vous avez tapé jusqu'à présent. Après predict-off, l'édition redevient normale pour la ligne trouvée. En fait, vous n'avez souvent même pas besoin d'utiliser predict-off, car si la ligne ne correspond à rien dans l'historique, l'ajout d'une touche effectue une complétion standard, puis s'insère si aucune complétion n'a été trouvée. Cependant, l'édition au milieu d'une ligne risque de perturber la prédiction ; voir le style toggle ci-dessous.

Avec le système de complétion basé sur les fonctions (qui est nécessaire pour cela), vous devriez être capable de taper TAB à presque n'importe quel endroit pour avancer le curseur jusqu'à la prochaine position de caractère « intéressante » (généralement la fin du mot actuel, mais parfois quelque part au milieu du mot). Et bien sûr, dès que la ligne entière correspond à ce que vous voulez, vous pouvez l'accepter avec retour, sans avoir besoin de déplacer le curseur à la fin d'abord.

La première fois que predict-on est utilisé, il crée plusieurs fonctions de widget supplémentaires :

delete-backward-and-predict
Remplace le widget backward-delete-char. Vous n'avez pas besoin de le lier vous-même.
insert-and-predict
Implémente la frappe prédictive en remplaçant le widget self-insert. Vous n'avez pas besoin de le lier vous-même.
predict-off
Désactive la frappe prédictive.

Bien que vous utilisiez autoload uniquement pour la fonction predict-on, il est nécessaire de créer également une liaison de touche pour predict-off.

zle -N predict-on
zle -N predict-off
bindkey '^X^Z' predict-on
bindkey '^Z' predict-off
read-from-minibuffer
Ceci est plus utile lorsqu'il est appelé comme fonction à l'intérieur d'un widget, mais fonctionnera correctement en tant que widget à part entière. Il demande une valeur en dessous de la ligne de commande actuelle ; une valeur peut être saisie en utilisant toutes les opérations zle standard (et pas seulement l'ensemble restreint disponible lors de l'exécution, par exemple, execute-named-cmd). La valeur est ensuite retournée à la fonction appelante dans le paramètre $REPLY et le tampon d'édition est restauré à son état précédent. Si la lecture a été annulée par une interruption clavier (généralement ^G), la fonction retourne le statut 1 et $REPLY n'est pas défini.

Si un argument est fourni à la fonction, il est pris comme invite, sinon `? ' est utilisé. Si deux arguments sont fournis, ce sont l'invite et la valeur initiale de $LBUFFER, et si un troisième argument est donné, c'est la valeur initiale de $RBUFFER. Ceci fournit une valeur par défaut et un placement initial du curseur. Au retour, le tampon entier est la valeur de $REPLY.

Une option est disponible : `-k num' spécifie que num caractères doivent être lus au lieu d'une ligne entière. L'éditeur de ligne n'est pas appelé récursivement dans ce cas, donc en fonction des paramètres du terminal, l'entrée peut ne pas être visible, et seules les touches d'entrée sont placées dans $REPLY, pas tout le tampon. Notez que contrairement à la commande intégrée read, num doit être donné ; il n'y a pas de valeur par défaut.

Le nom est une légère erreur, car en fait le propre minibuffer du shell n'est pas utilisé. Par conséquent, il est toujours possible d'appeler executed-named-cmd et des fonctions similaires tout en lisant une valeur.

replace-argument, replace-argument-edit
La fonction replace-argument peut être utilisée pour remplacer un argument de ligne de commande dans la ligne de commande actuelle ou, si la ligne de commande actuelle est vide, dans la dernière ligne de commande exécutée (la nouvelle ligne de commande n'est pas exécutée). Les arguments sont délimités par la syntaxe standard du shell,

Si un argument numérique est fourni, celui-ci spécifie l'argument à remplacer. 0 signifie le nom de la commande, comme dans l'expansion d'historique. Un argument numérique négatif compte à rebours à partir du dernier mot.

Si aucun argument numérique n'est fourni, l'argument courant est remplacé ; c'est le dernier argument si la ligne d'historique précédente est utilisée.

La fonction demande un argument de remplacement.

Si le widget contient la chaîne edit, par exemple est défini comme

zle -N replace-argument-edit replace-argument

alors la fonction présente la valeur actuelle de l'argument pour édition, sinon le tampon d'édition pour le remplacement est initialement vide.

replace-string, replace-pattern
replace-string-again, replace-pattern-again
La fonction replace-string implémente trois widgets. Si elle est définie sous le même nom que la fonction, elle demande deux chaînes ; la première chaîne (source) sera remplacée par la seconde partout où elle apparaît dans le tampon d'édition de ligne.

Si le nom du widget contient le mot `pattern', par exemple en définissant le widget à l'aide de la commande `zle -N replace-pattern replace-string', alors la correspondance est effectuée à l'aide des motifs zsh. Tous les motifs de globbing étendus de zsh peuvent être utilisés dans la chaîne source ; notez que contrairement à la génération de noms de fichiers, le motif n'a pas besoin de correspondre à un mot entier, et les qualificateurs de glob n'ont aucun effet. De plus, la chaîne de remplacement peut contenir des substitutions de paramètres ou de commandes. De plus, un `&' dans la chaîne de remplacement sera remplacé par la chaîne source correspondante, et un chiffre entre guillemets inversés `\N' sera remplacé par la Nème expression entre parenthèses correspondante. La forme `\{N}' peut être utilisée pour protéger le chiffre des chiffres suivants.

Si le widget contient au lieu de cela le mot `regex' (ou `regexp'), alors la correspondance est effectuée à l'aide d'expressions régulières, en respectant le réglage de l'option RE_MATCH_PCRE (voir la description de la fonction regexp-replace ci-dessous). Les facilités de remplacement spéciales décrites ci-dessus pour la correspondance de motifs sont disponibles.

Par défaut, la chaîne source ou de remplacement précédente ne sera pas proposée pour l'édition. Cependant, cette fonctionnalité peut être activée en définissant le style edit-previous dans le contexte :zle:widget (par exemple, :zle:replace-string) à true. De plus, un argument numérique positif force l'offre des valeurs précédentes, un argument négatif ou nul force leur non-offre.

La fonction replace-string-again peut être utilisée pour répéter le remplacement précédent ; aucune invite n'est faite. Comme avec replace-string, si le nom du widget contient le mot `pattern' ou `regex', une correspondance de motif ou d'expression régulière est effectuée, sinon une légère

ral replacement de chaînes. Notez que le texte source et le texte de remplacement précédents sont les mêmes, que la correspondance de motifs, d'expressions régulières ou de chaînes soit utilisée.

De plus, replace-string affiche le remplacement précédent au-dessus de l'invite, tant qu'il y en a eu un pendant la session en cours ; si la chaîne source est vide, ce remplacement sera répété sans que le widget ne demande une chaîne de remplacement.

Par exemple, en partant de la ligne :

print This line contains fan and fond

et en appelant replace-pattern avec la chaîne source `f(?)n' et la chaîne de remplacement `c\1r' produit la ligne peu utile :

print This line contains car and cord

La plage de la chaîne de remplacement peut être limitée en utilisant le widget narrow-to-region-invisible. Une limitation de la version actuelle est que undo cyclera à travers les modifications apportées aux chaînes de remplacement et source avant d'annuler le remplacement lui-même.

send-invisible
Ceci est similaire à read-from-minibuffer en ce sens qu'il peut être appelé comme fonction depuis un widget ou comme widget propre, et lit interactivement des entrées depuis le clavier. Cependant, l'entrée tapée est dissimulée et une chaîne d'astérisques (`*') est affichée à la place. La valeur est sauvegardée dans le paramètre $INVISIBLE auquel une référence est insérée dans le tampon d'édition à la position du curseur restaurée. Si la lecture a été interrompue par une interruption clavier (typiquement ^G) ou une autre sortie de l'édition comme push-line, $INVISIBLE est défini sur vide et le tampon d'origine est restauré inchangé.

Si un argument est fourni à la fonction, il est pris comme invite, sinon `Non-echoed text: ' est utilisé (comme dans emacs). Si un deuxième et un troisième argument sont fournis, ils sont utilisés pour commencer et terminer la référence à $INVISIBLE qui est insérée dans le tampon. Par défaut, il s'ouvre avec ${, puis INVISIBLE, et se ferme avec }, mais de nombreux autres effets sont possibles.

smart-insert-last-word
Cette fonction peut remplacer le widget insert-last-word, comme ceci :
zle -N insert-last-word smart-insert-last-word

Avec un argument numérique, ou lorsqu'il est passé des arguments de ligne de commande dans un appel depuis un autre widget, il se comporte comme insert-last-word, sauf que les mots dans les commentaires sont ignorés lorsque INTERACTIVE_COMMENTS est défini.

Sinon, le dernier mot « intéressant » de la commande précédente est trouvé et inséré. La définition par défaut de « intéressant » est qu'un mot contient au moins un caractère alphabétique, une barre oblique ou une barre oblique inversée. Cette définition peut être remplacée par l'utilisation du style match. Le contexte utilisé pour rechercher le style est le nom du widget, donc généralement le contexte est :insert-last-word. Cependant, vous pouvez lier cette fonction à différents widgets pour utiliser différents modèles :

zle -N insert-last-assignment smart-insert-last-word
zstyle :insert-last-assignment match '[[:alpha:]][][[:alnum:]]#=*'
bindkey '\e=' insert-last-assignment

Si aucun mot intéressant n'est trouvé et que le style auto-previous est défini sur une valeur vraie, la recherche continue vers le haut dans l'historique. Lorsque auto-previous est non défini ou faux (par défaut), le widget doit être invoqué à plusieurs reprises pour rechercher des lignes d'historique antérieures.

transpose-lines
Utile uniquement avec un tampon d'édition multi-lignes ; les lignes ici sont des lignes dans le tampon actuel à l'écran, pas des lignes d'historique. L'effet est similaire à la fonction du même nom dans Emacs.

Transpose la ligne actuelle avec la ligne précédente et déplace le curseur au début de la ligne suivante. Répéter cela (ce qui peut être fait en fournissant un argument numérique positif) a pour effet de déplacer la ligne au-dessus du curseur vers le bas d'un certain nombre de lignes.

Avec un argument numérique négatif, deux lignes au-dessus du curseur sont nécessaires. Ces deux lignes sont transposées et le curseur est déplacé au début de la ligne précédente. L'utilisation d'un argument numérique inférieur à -1 a pour effet de déplacer la ligne au-dessus du curseur vers le haut d'un nombre de lignes égal à l'opposé de cet argument.

url-quote-magic
Ce widget remplace le widget intégré self-insert pour faciliter la saisie d'URL comme arguments de ligne de commande. Lorsque vous tapez, le caractère d'entrée est analysé et, s'il doit être mis entre guillemets, le mot actuel est vérifié pour un schéma d'URI. S'il en est trouvé un et que le mot actuel n'est pas déjà entre guillemets, une barre oblique inversée est insérée avant le caractère d'entrée.

Styles pour contrôler le comportement des guillemets :

url-metas
Ce style est recherché dans le contexte `:url-quote-magic:scheme' (où scheme est celui de l'URL actuelle, par exemple "ftp"). La valeur est une chaîne répertoriant les caractères à traiter comme des métacaractères de globbing lorsqu'ils apparaissent dans une URL utilisant ce schéma. Par défaut, tous les caractères de globbing étendus de zsh sont mis entre guillemets, à l'exception de '<' et '>' mais y compris les accolades (comme dans l'expansion d'accolades). Voir aussi url-seps.
url-seps
Comme url-metas, mais répertorie les caractères qui doivent être considérés comme des séparateurs de commandes, des redirections, des références d'historique, etc. Par défaut, les ensembles standard de séparateurs de shell sont mis entre guillemets, à l'exception de ceux qui chevauchent les caractères de globbing étendus, mais y compris '<' et '>' et le premier caractère de $histchars.
url-globbers
Ce style est recherché dans le contexte `:url-quote-magic'. Les valeurs forment une liste de noms de commandes qui sont censées effectuer leur propre globbing sur la chaîne d'URL. Cela implique qu'elles sont aliasées pour utiliser le modificateur `noglob'. Lorsque le premier mot de la ligne correspond à l'une des valeurs et que l'URL fait référence à un fichier local (voir url-local-schema), seuls les caractères url-seps sont mis entre guillemets ; les url-metas sont laissés tels quels, leur permettant d'affecter l'analyse de la ligne de commande, la complétion, etc. Les valeurs par défaut sont une chaîne littérale `noglob' plus (lorsque le module zsh/parameter est disponible) toutes les commandes aliasées à la fonction d'aide `urlglobber' ou à son alias `globurl'.
url-local-schema
Ce style est toujours recherché dans le contexte `:urlglobber', bien qu'il soit utilisé à la fois par url-quote-magic et urlglobber. Les valeurs forment une liste de schémas d'URI qui doivent être traités comme faisant référence à des fichiers locaux par leurs noms de chemin d'accès locaux réels, par opposition aux fichiers qui sont spécifiés par rapport à une racine de document définie par le serveur Web. Les valeurs par défaut sont "ftp" et "file".
url-other-schema
Comme url-local-schema, mais liste tous les autres schémas d'URI sur lesquels urlglobber et url-quote-magic doivent agir. Si l'URI sur la ligne de commande n'a pas de schéma apparaissant soit dans cette liste, soit dans url-local-schema, il n'est pas mis entre guillemets magiquement. Les valeurs par défaut sont "http", "https", et "ftp". Lorsqu'un schéma apparaît à la fois ici et dans url-local-schema, il est mis entre guillemets différemment selon que le nom de commande apparaît ou non dans url-globbers.

Le chargement de url-quote-magic définit également une fonction d'aide `urlglobber' et des alias `globurl' vers `noglob urlglobber'. Cette fonction décompose une URL locale, tente de faire correspondre le modèle à la partie fichier local du chemin d'URL, puis remet les résultats au format URL.

vi-pipe
Cette fonction lit une commande de déplacement depuis le clavier, puis demande une commande externe. La partie du tampon couverte par le déplacement est envoyée à la commande externe via un pipe, puis remplacée par la sortie de la commande. Si la commande de déplacement est liée à vi-pipe, la ligne actuelle est utilisée.

La fonction sert d'exemple pour lire une commande de déplacement vi depuis un widget défini par l'utilisateur.

which-command
Cette fonction remplace directement le widget intégré which-command. Elle a un comportement amélioré, en ce sens qu'elle détecte correctement si le mot de commande doit être développé en alias ; si c'est le cas, elle continue à suivre le mot de commande à partir de l'alias développé jusqu'à atteindre la commande qui sera exécutée.

Le style whence est disponible dans le contexte :zle:$WIDGET ; il peut être défini sur un tableau pour donner la commande et les options qui seront utilisées pour enquêter sur le mot de commande trouvé. Par défaut, il s'agit de whence -c.

zcalc-auto-insert
Cette fonction est utile conjointement avec la fonction zcalc décrite dans la section « Fonctions mathématiques ». Elle doit être liée à une touche représentant un opérateur binaire tel que `+', `-', `*' ou `/'. Lors de l'exécution dans zcalc, si la touche se trouve au début de la ligne ou immédiatement après une parenthèse ouvrante, le texte "ans " est inséré avant la représentation de la touche elle-même. Cela permet une utilisation facile de la réponse du calcul précédent dans la ligne actuelle. Le texte à insérer avant le symbole tapé peut être modifié en définissant la variable ZCALC_AUTO_INSERT_PREFIX.

Ainsi, par exemple, taper `+12' suivi de retour ajoute 12 au résultat précédent.

Si zcalc est en mode RPN (option -r), l'effet de cette liaison est automatiquement supprimé car les opérateurs seuls sur une ligne sont significatifs.

Lorsqu'il n'est pas dans zcalc, la touche insère simplement le symbole lui-même.

Fonctions utilitaires

Ces fonctions sont utiles pour construire des widgets. Elles doivent être chargées avec `autoload -U function' et appelées comme indiqué depuis des widgets définis par l'utilisateur.

split-shell-arguments
Cette fonction divise la ligne en cours d'édition en arguments de shell et en espaces blancs. Le résultat est stocké dans le tableau
reply. Le tableau contient toutes les parties de la ligne dans l'ordre, en commençant par tout espace avant le premier argument et en terminant par tout espace après le dernier argument. Par conséquent (tant que l'option KSH_ARRAYS n'est pas définie), les espaces sont donnés par les indices impairs dans le tableau et les arguments par les indices pairs. Notez qu'aucun retrait de guillemets n'est effectué ; joindre tous les éléments de reply dans l'ordre est garanti de produire la ligne d'origine.

Le paramètre REPLY est défini à l'indice du mot dans reply qui contient le caractère après le curseur, où le premier élément a l'indice 1. Le paramètre REPLY2 est défini à l'indice du caractère sous le curseur dans ce mot, où le premier caractère a l'indice 1.

Par conséquent, reply, REPLY et REPLY2 devraient tous être rendus locaux à la fonction englobante.

Voir la fonction modify-current-argument, décrite ci-dessous, pour un exemple d'appel de cette fonction.

modify-current-argument [ expr-utilisant-$ARG | func ]
Cette fonction fournit une méthode simple pour permettre aux widgets définis par l'utilisateur de modifier l'argument de la ligne de commande sous le curseur (ou immédiatement à gauche du curseur si le curseur se trouve entre deux arguments).

L'argument peut être une expression qui, une fois évaluée, opère sur le paramètre shell ARG, qui aura été défini à l'argument de la ligne de commande sous le curseur. L'expression doit être correctement entre guillemets pour éviter qu'elle ne soit évaluée trop tôt.

Alternativement, si l'argument ne contient pas la chaîne ARG, il est supposé être une fonction shell, à laquelle l'argument actuel de la ligne de commande est passé comme seul argument. La fonction doit définir la variable REPLY à la nouvelle valeur pour l'argument de la ligne de commande. Si la fonction retourne un statut non nul, il en va de même pour la fonction appelante.

Par exemple, un widget défini par l'utilisateur contenant le code suivant convertit les caractères de l'argument sous le curseur en majuscules :

modify-current-argument '${(U)ARG}'

Ce qui suit retire tout guillemet du mot actuel (qu'il s'agisse d'anti-slashs ou d'un des styles de guillemets), et le remplace par des guillemets simples partout :

modify-current-argument '${(qq)${(Q)ARG}}'

Ce qui suit effectue une expansion de répertoire sur l'argument de la ligne de commande et le remplace par le chemin absolu :

expand-dir() {
  REPLY=${~1}
  REPLY=${REPLY:a}
}
modify-current-argument expand-dir

En pratique, la fonction expand-dir ne serait probablement pas définie dans le widget où modify-current-argument est appelée.

Styles

Le comportement de plusieurs des widgets ci-dessus peut être contrôlé par l'utilisation du mécanisme zstyle. En particulier, les widgets qui interagissent avec le système de complétion transmettent leur contexte à toutes les complétions qu'ils invoquent.

break-keys
Ce style est utilisé par le widget incremental-complete-word. Sa valeur doit être un motif, et toutes les touches correspondant à ce motif provoqueront l'arrêt de la complétion incrémentielle sans que la touche ait d'autre effet. Comme tous les styles utilisés directement par incremental-complete-word, ce style est recherché en utilisant le contexte `:incremental'.
completer
Les widgets incremental-complete-word et insert-and-predict définissent leur nom de contexte de haut niveau avant d'appeler la complétion. Cela permet de définir différents ensembles de fonctions de complétion pour la complétion normale et pour ces widgets. Par exemple, pour utiliser la complétion, l'approximation et la correction pour la complétion normale, la complétion et la correction pour la complétion incrémentielle et seulement la complétion pour la prédiction, on pourrait utiliser :
zstyle ':completion:*' completer \ 
        _complete _correct _approximate
zstyle ':completion:incremental:*' completer \ 
        _complete _correct
zstyle ':completion:predict:*' completer \ 
        _complete

Il est conseillé de restreindre les compléteurs utilisés en prédiction, car ils peuvent être automatiquement invoqués lorsque vous tapez. Les compléteurs _list et _menu ne doivent jamais être utilisés avec la prédiction. Les compléteurs _approximate, _correct, _expand et _match peuvent être utilisés, mais gardez à l'esprit qu'ils peuvent modifier des caractères n'importe où dans le mot derrière le curseur, vous devez donc surveiller attentivement que le résultat est ce que vous vouliez.

cursor
Le widget insert-and-predict utilise ce style, dans le contexte `:predict', pour décider où placer le curseur après l'essai de complétion. Les valeurs sont :
complete
Le curseur reste là où il était lorsque la complétion s'est terminée, mais seulement s'il est après un caractère égal à celui qui vient d'être inséré par l'utilisateur. S'il est après un autre caractère, cette valeur est la même que `key'.
key
Le curseur reste après la nème occurrence du caractère qui vient d'être tapé, où n est le nombre de fois que ce caractère est apparu dans le mot avant que la complétion ne soit tentée. En bref, cela a pour effet de laisser le curseur après le caractère qui vient d'être tapé, même si le code de complétion a découvert qu'aucun autre caractère ne doit être inséré à cette position.

Toute autre valeur pour ce style laisse inconditionnellement le curseur à la position où le code de complétion l'a laissé.

list
Lors de l'utilisation du widget incremental-complete-word, ce style indique si les correspondances doivent être listées à chaque pression de touche (si elles tiennent à l'écran). Utilisez le préfixe de contexte `:completion:incremental'.

Le widget insert-and-predict utilise ce style pour décider si la complétion doit être affichée même s'il n'y a qu'une seule complétion possible. Cela est fait si la valeur de ce style est la chaîne always. Dans ce cas, le contexte est `:predict' (pas `:completion:predict').

match
Ce style est utilisé par smart-insert-last-word pour fournir un motif (utilisant la syntaxe complète de EXTENDED_GLOB) qui correspond à un mot intéressant. Le contexte est le nom du widget auquel smart-insert-last-word est lié (voir ci-dessus). Le comportement par défaut de smart-insert-last-word est équivalent à :
zstyle :insert-last-word match '*[[:alpha:]/\\]*'

Cependant, vous pourriez vouloir inclure des mots contenant des espaces :

zstyle :insert-last-word match '*[[:alpha:][:space:]/\\]*'

Ou inclure des nombres tant que le mot a au moins deux caractères de long :

zstyle :insert-last-word match '*([[:digit:]]?|[[:alpha:]/\\])*'

L'exemple ci-dessus provoque l'inclusion de redirections telles que "2>".

prompt
Le widget incremental-complete-word affiche la valeur de ce style dans la ligne de statut pendant la complétion incrémentielle. La valeur de la chaîne peut contenir l'une des sous-chaînes suivantes, de la même manière que les paramètres de prompt PS1 et autres :
%c
Remplacé par le nom de la fonction de complétion qui a généré les correspondances (sans le tiret de soulignement initial).
%l
Lorsque le style list est défini, remplacé par `...' si la liste des correspondances est trop longue pour tenir à l'écran et par une chaîne vide sinon. Si le style list est `false' ou non défini, `%l' est toujours supprimé.
%n
Remplacé par le nombre de correspondances générées.
%s
Remplacé par `-no match-', `-no prefix-', ou une chaîne vide s'il n'y a pas de complétion correspondant au mot sur la ligne, si les correspondances n'ont pas de préfixe commun différent du mot sur la ligne, ou s'il y a un tel préfixe commun, respectivement.
%u
Remplacé par la partie non ambiguë de toutes les correspondances, s'il y en a une, et si elle est différente du mot sur la ligne.

Comme `break-keys', ceci utilise le contexte `:incremental'.

stop-keys
Ce style est utilisé par le widget incremental-complete-word. Sa valeur est traitée de manière similaire à celle du style break-keys (et utilise le même contexte : `:incremental'). Cependant, dans ce cas, toutes les touches correspondant au motif donné comme valeur arrêteront la complétion incrémentielle et exécuteront ensuite leur fonction habituelle.
toggle
Ce style booléen est utilisé par predict-on et ses widgets associés dans le contexte `:predict'. S'il est défini sur l'une des valeurs `true' standard, la frappe prédictive est automatiquement désactivée dans les situations où elle est peu susceptible d'être utile, comme lors de l'édition d'un tampon multi-lignes ou après s'être déplacé au milieu d'une ligne puis avoir supprimé un caractère. La valeur par défaut est de laisser la prédiction activée jusqu'à un appel explicite à predict-off.
verbose
Ce style booléen est utilisé par predict-on et ses widgets associés dans le contexte `:predict'. S'il est défini sur l'une des valeurs `true' standard, ces widgets affichent un message sous l'invite lorsque l'état prédictif est basculé. Ceci est particulièrement utile en combinaison avec le style toggle. La valeur par défaut n'affiche pas ces messages.
widget
Ce style est similaire au style command : Pour les fonctions de widget qui utilisent zle pour appeler d'autres widgets, ce style peut parfois être utilisé pour remplacer le widget qui est appelé. Le contexte pour ce style est le nom du widget appelant (pas le nom de la fonction appelante, car une seule fonction peut être liée à plusieurs noms de widget).
zstyle :copy-earlier-word widget smart-insert-last-word

Consultez la documentation du widget ou de la fonction appelante pour déterminer si le style widget est utilisé.

GESTION DES EXCEPTIONS

Deux fonctions sont fournies pour permettre à zsh de gérer les exceptions d'une manière qui devrait être familière à partir d'autres langages.

throw exception
La fonction throw lance l'exception nommée. Le nom est une chaîne arbitraire et n'est utilisé que par les fonctions throw et catch. Une exception est traitée dans la plupart des cas comme une erreur de shell, c'est-à-dire qu'une exception non gérée entraînera l'abandon par le shell de tout traitement dans une fonction ou un script et le retour au niveau supérieur dans un shell interactif.
catch exception-pattern
La fonction catch renvoie le statut zéro si une exception a été lancée et que le motif exception-pattern correspond à son nom. Sinon, elle renvoie le statut 1. exception-pattern est un motif de shell standard, respectant le paramètre actuel de l'option EXTENDED_GLOB. Un alias catch est également défini pour empêcher l'argument de la fonction de correspondre aux noms de fichiers, de sorte que les motifs puissent être utilisés sans guillemets. Notez que comme les exceptions ne sont pas fondamentalement différentes des autres erreurs de shell, il est possible de gérer les erreurs de shell en utilisant une chaîne vide comme nom d'exception. La variable de shell CAUGHT est définie par catch avec le nom de l'exception capturée. Il est possible de relancer une exception en appelant à nouveau la fonction throw une fois qu'une exception a été capturée.

Les fonctions sont conçues pour être utilisées avec la construction always décrite dans zshmisc(1). Ceci est important car seule cette construction fournit le support requis pour les exceptions. Un exemple typique est le suivant.

{
  # Bloc "try"
  # ... code imbriqué ici appelle "throw MyExcept"
} always {
  # Bloc "always"
  if catch MyExcept; then
    print "Exception MyExcept capturée"
  elif catch ''; then
    print "Erreur shell capturée. Propagation..."
    throw ''
  fi
  # Les autres exceptions ne sont pas gérées mais peuvent être capturées plus loin
  # dans la pile d'appels.
}

Si toutes les exceptions doivent être capturées, l'idiome suivant peut être préférable.

{
  # ... le code imbriqué lance une exception
} always {
  if catch *; then
    case $CAUGHT in
      (MyExcept)
      print "Ma propre exception capturée"
      ;;
      (*)
      print "Autre exception capturée"
      ;;
    esac
  fi
}

Conformément à la gestion des exceptions dans d'autres langages, l'exception peut être lancée par du code profondément imbriqué dans le bloc `try'. Cependant, notez qu'elle doit être lancée dans le shell actuel, et non dans un sous-shell créé pour un pipeline, une construction de shell courant entre parenthèses, ou une forme de substitution de commande ou de processus.

Le système utilise en interne la variable de shell EXCEPTION pour enregistrer le nom de l'exception entre le lancement et la capture. Un inconvénient de ce système est que si l'exception n'est pas gérée, la variable EXCEPTION reste définie et peut être incorrectement reconnue comme le nom d'une exception si une erreur de shell se produit ultérieurement. L'ajout de unset EXCEPTION au début de la couche la plus externe de tout code utilisant la gestion des exceptions éliminera ce problème.

FONCTIONS MIME

Trois fonctions sont disponibles pour gérer les fichiers reconnus par leur extension, par exemple pour distribuer un fichier text.ps lorsqu'il est exécuté comme une commande vers un visualiseur approprié.

zsh-mime-setup [ -fv ] [ -l [ suffix ... ] ]
zsh-mime-handler [ -l ] command argument ...
Ces deux fonctions utilisent les fichiers ~/.mime.types et /etc/mime.types, qui associent types et extensions, ainsi que les fichiers ~/.mailcap et /etc/mailcap, qui associent types et programmes qui les gèrent. Ceux-ci sont fournis sur de nombreux systèmes avec les extensions de courrier électronique Internet multimédia (Multimedia Internet Mail Extensions).

Pour activer le système, la fonction zsh-mime-setup doit être chargée automatiquement et exécutée. Cela permet aux fichiers avec extensions d'être traités comme exécutables ; ces fichiers seront complétés par le système de complétion de fonction. La fonction zsh-mime-handler ne devrait pas avoir besoin d'être appelée par l'utilisateur.

Le système fonctionne en configurant des alias de suffixe avec `alias -s'. Les alias de suffixe déjà installés par l'utilisateur ne seront pas écrasés.

Pour les suffixes définis en minuscules, les variantes en majuscules seront également gérées automatiquement (par exemple, PDF est automatiquement géré si la gestion du suffixe pdf est définie), mais pas l'inverse.

Les appels répétés à zsh-mime-setup n'écrasent pas le mappage existant entre les suffixes et les fichiers exécutables, sauf si l'option -f est donnée. Notez cependant que cela n'écrase pas les alias de suffixe existants attribués à des gestionnaires autres que zsh-mime-handler.

L'appel à zsh-mime-setup avec l'option -l liste les mappages existants sans les modifier. Des suffixes à lister (qui peuvent contenir des caractères de motif qui devraient être protégés de l'interprétation immédiate sur la ligne de commande) peuvent être fournis comme arguments supplémentaires, sinon tous les suffixes sont listés.

L'appel à zsh-mime-setup avec l'option -v affiche des informations détaillées pendant l'opération de configuration.

Le système respecte les indicateurs mailcap needsterminal et copiousoutput ; voir mailcap(4) ou mailcap(5) (le nom de la page de manuel varie selon les plateformes).

Les fonctions utilisent les styles suivants, qui sont définis avec la commande intégrée zstyle (voir zshmodules(1)). Ils doivent être définis avant l'exécution de zsh-mime-setup. Les contextes utilisés commencent tous par :mime:, avec des composants supplémentaires dans certains cas. Il est recommandé d'ajouter un * final (adéquatement protégé) aux motifs de style au cas où le système serait étendu à l'avenir. Quelques exemples sont donnés ci-dessous.

Pour les fichiers ayant plusieurs suffixes, par exemple .pdf.gz, où le contexte inclut le suffixe, il sera recherché en commençant par le suffixe le plus long possible jusqu'à ce qu'une correspondance pour le style soit trouvée. Par exemple, si .pdf.gz produit une correspondance pour le gestionnaire, celle-ci sera utilisée ; sinon, le gestionnaire pour .gz sera utilisé. Notez que, compte tenu de la manière dont fonctionnent les alias de suffixe, il est toujours requis qu'il y ait un gestionnaire pour le suffixe le plus court possible, donc dans cet exemple .pdf.gz ne peut être géré que si .gz est également géré (bien que pas nécessairement de la même manière). Alternativement, si aucun traitement pour .gz seul n'est nécessaire, il suffit d'ajouter la commande

alias -s gz=zsh-mime-handler

au code d'initialisation ; .gz ne sera pas géré seul, mais pourra l'être en combinaison avec d'autres suffixes.

current-shell
Si ce style booléen est vrai, le gestionnaire mailcap pour le contexte en question est exécuté en utilisant la commande intégrée eval au lieu de démarrer un nouveau processus sh. Ceci est plus efficace, mais peut ne pas fonctionner dans les cas occasionnels où le gestionnaire mailcap utilise une syntaxe POSIX stricte.
disown
Si ce style booléen est vrai, les gestionnaires mailcap démarrés en arrière-plan seront "disowned" (détachés), c'est-à-dire qu'ils ne seront pas soumis au contrôle des travaux au sein du shell parent. De tels gestionnaires produisent presque toujours leurs propres fenêtres, de sorte que le seul effet secondaire potentiellement néfaste de la définition du style est qu'il devient plus difficile de tuer des travaux depuis le shell.
execute-as-is
Ce style donne une liste de motifs à faire correspondre aux fichiers passés pour exécution avec un programme gestionnaire. Si le fichier correspond au motif, la ligne de commande entière est exécutée sous sa forme actuelle, sans gestionnaire. Ceci est utile pour les fichiers qui pourraient avoir des suffixes mais être néanmoins exécutables en eux-mêmes. Si le style n'est pas défini, le motif *(*) *(/) est utilisé ; par conséquent, les fichiers exécutables sont exécutés directement et non passés à un gestionnaire, et l'option AUTO_CD peut être utilisée pour changer de répertoire qui ont par hasard des suffixes MIME.
execute-never
Ce style est utile en combinaison avec execute-as-is. Il est défini sur un tableau de motifs correspondant aux chemins complets de fichiers qui ne doivent jamais être traités comme exécutables, même si le fichier passé au gestionnaire MIME correspond à execute-as-is. Ceci est utile pour les systèmes de fichiers qui ne gèrent pas la permission d'exécution ou qui contiennent des exécutables d'un autre système d'exploitation. Par exemple, si /mnt/windows est un montage Windows, alors
zstyle ':mime:*' execute-never '/mnt/windows/*'

garantira que tous les fichiers trouvés dans cette zone seront exécutés en tant que types MIME même s'ils sont exécutables. Comme le montre cet exemple, le nom de fichier complet est mis en correspondance avec le motif, indépendamment de la manière dont le fichier a été passé au gestionnaire. Le fichier est résolu en un chemin complet à l'aide du modificateur :P décrit dans la sous-section `Modificateurs' de zshexpn(1) ; cela signifie que les liens symboliques sont résolus lorsque c'est possible, de sorte que les liens vers d'autres systèmes de fichiers se comportent correctement.

file-path
Utilisé si le style find-file-in-path est vrai pour le même contexte. Défini sur un tableau de répertoires utilisés pour rechercher le fichier à gérer ; la valeur par défaut est le chemin des commandes donné par le paramètre spécial path. L'option de shell PATH_DIRS est respectée ; si elle est définie, le chemin approprié sera recherché même si le nom du fichier à gérer tel qu'il apparaît sur la ligne de commande contient un `/'. Le contexte complet est :mime:.suffix:, comme décrit pour le style handler.
find-file-in-path
S'il est défini, permet de rechercher des fichiers dont les noms ne contiennent pas de chemins absolus dans le chemin des commandes ou dans le chemin spécifié par le style file-path. Si le fichier n'est pas trouvé dans le chemin, il est recherché localement (que le curren
t est dans le chemin) ; si ce n'est pas trouvé localement, le gestionnaire avortera à moins que le style handle-nonexistent ne soit défini. Les fichiers trouvés dans le chemin sont testés comme décrit pour le style execute-as-is. Le contexte complet est :mime:.suffixe:, comme décrit pour le style handler.
flags
Définit les indicateurs (flags) à associer à un gestionnaire ; le contexte est le même que pour le style handler, et le format est le même que pour les indicateurs dans mailcap.
handle-nonexistent
Par défaut, les arguments qui ne correspondent pas à des fichiers ne sont pas passés au gestionnaire MIME afin de l'empêcher d'intercepter des commandes trouvées dans le chemin qui ont des suffixes par hasard. Ce style peut être défini sur un tableau de modèles glob étendus pour les arguments qui seront passés au gestionnaire même s'ils n'existent pas. S'il n'est pas explicitement défini, il vaut par défaut [[:alpha:]]#:/*, ce qui permet de passer des URL au gestionnaire MIME même s'ils n'existent pas sous cette forme dans le système de fichiers. Le contexte complet est :mime:.suffixe:, comme décrit pour le style handler.
handler
Spécifie un gestionnaire pour un suffixe ; le suffixe est donné par le contexte comme :mime:.suffixe:, et le format du gestionnaire est exactement celui de mailcap. Notez en particulier le `.' et le deux-points final pour distinguer cette utilisation du contexte. Ceci remplace tout gestionnaire spécifié par les fichiers mailcap. Si le gestionnaire nécessite un terminal, le style flags doit être défini pour inclure le mot needsterminal, ou si la sortie doit être affichée via un pager (mais pas si le gestionnaire est lui-même un pager), il doit inclure copiousoutput.
mailcap
Une liste de fichiers au format de ~/.mailcap et /etc/mailcap à lire lors de la configuration, remplaçant la liste par défaut qui se compose de ces deux fichiers. Le contexte est :mime:. Un + dans la liste sera remplacé par les fichiers par défaut.
mailcap-priorities
Ce style est utilisé pour résoudre plusieurs entrées mailcap pour le même type MIME. Il se compose d'un tableau des éléments suivants, dans l'ordre de priorité décroissant ; les entrées ultérieures seront utilisées si les entrées précédentes ne peuvent pas résoudre les entrées comparées. Si aucun des tests ne résout les entrées, la première entrée rencontrée est conservée.
files
L'ordre des fichiers (entrées dans le style mailcap) lus. Les fichiers précédents sont préférés. (Notez que cela ne résout pas les entrées dans le même fichier.)
priority
L'indicateur de priorité de l'entrée mailcap. La priorité est un entier de 0 à 9, la valeur par défaut étant 5.
flags
Le test donné par l'option mailcap-prio-flags est utilisé pour résoudre les entrées.
place
Les entrées ultérieures sont préférées ; comme les entrées sont strictement ordonnées, ce test réussit toujours.

Notez que puisque ce style est géré lors de l'initialisation, le contexte est toujours :mime:, sans discrimination par suffixe.

mailcap-prio-flags
Ce style est utilisé lorsque le mot-clé flags est rencontré dans la liste des tests spécifiés par le style mailcap-priorities. Il doit être défini sur une liste de modèles, chacun étant testé par rapport aux indicateurs spécifiés dans l'entrée mailcap (en d'autres termes, les ensembles d'assignations trouvés avec certaines entrées dans le fichier mailcap). Les modèles précédents de la liste sont préférés aux suivants, et les modèles correspondants sont préférés aux modèles non correspondants.
mime-types
Une liste de fichiers au format de ~/.mime.types et /etc/mime.types à lire lors de la configuration, remplaçant la liste par défaut qui se compose de ces deux fichiers. Le contexte est :mime:. Un + dans la liste sera remplacé par les fichiers par défaut.
never-background
Si ce style booléen est défini, le gestionnaire pour le contexte donné est toujours exécuté en premier plan, même si les indicateurs fournis dans l'entrée mailcap suggèrent qu'il n'est pas nécessaire de le faire (par exemple, il ne nécessite pas de terminal).
pager
S'il est défini, sera utilisé à la place de $PAGER ou more pour gérer les suffixes pour lesquels l'indicateur copiousoutput est défini. Le contexte est le même que pour handler, c'est-à-dire :mime:.suffixe: pour gérer un fichier avec le suffixe donné.

Exemples :

zstyle ':mime:*' mailcap ~/.mailcap /usr/local/etc/mailcap
zstyle ':mime:.txt:' handler less %s
zstyle ':mime:.txt:' flags needsterminal

Lorsque zsh-mime-setup sera exécuté par la suite, il recherchera des entrées mailcap dans les deux fichiers spécifiés. Les fichiers de suffixe .txt seront gérés en exécutant `less fichier.txt'. L'indicateur needsterminal est défini pour indiquer que ce programme doit être exécuté attaché à un terminal.

Comme il y a plusieurs étapes pour le lancement d'une commande, il convient de vérifier les points suivants si l'exécution d'un fichier par extension .ext n'a pas l'effet escompté.

La commande `alias -s ext' devrait afficher `ps=zsh-mime-handler'. Si elle affiche autre chose, un autre alias de suffixe a déjà été installé et n'a pas été écrasé. Si elle n'affiche rien, aucun gestionnaire n'a été installé : cela est très probablement dû au fait qu'aucun gestionnaire n'a été trouvé dans la combinaison .mime.types et mailcap pour les fichiers .ext. Dans ce cas, une gestion appropriée devrait être ajoutée à ~/.mime.types et mailcap.

Si l'extension est gérée par zsh-mime-handler mais que le fichier n'est pas ouvert correctement, soit le gestionnaire défini pour le type est incorrect, soit les indicateurs qui lui sont associés sont inappropriés. L'exécution de zsh-mime-setup -l affichera le gestionnaire et, s'il y en a, les indicateurs. Un %s dans le gestionnaire est remplacé par le fichier (correctement mis entre guillemets si nécessaire). Vérifiez que le programme gestionnaire listé peut être exécuté de la manière indiquée. Vérifiez également que les indicateurs needsterminal ou copiousoutput sont définis si le gestionnaire doit être exécuté sous un terminal ; le deuxième indicateur est utilisé si la sortie doit être envoyée à un pager. Un exemple d'entrée mailcap appropriée pour un tel programme est :

text/html; /usr/bin/lynx '%s'; needsterminal

L'exécution de `zsh-mime-handler -l ligne de commande' affiche la ligne de commande qui serait exécutée, simplifiée pour supprimer l'effet de tous les indicateurs, et mise entre guillemets de manière à ce que la sortie puisse être exécutée comme une ligne de commande zsh complète. Ceci est utilisé par le système de complétion pour décider comment compléter après un fichier géré par zsh-mime-setup.

pick-web-browser
Cette fonction est distincte des deux fonctions MIME décrites ci-dessus et peut être assignée directement à un suffixe :
autoload -U pick-web-browser
alias -s html=pick-web-browser

Elle est fournie comme une interface intelligente pour lancer un navigateur web. Elle peut être exécutée comme une fonction ou un script shell. Le statut 255 est renvoyé si aucun navigateur n'a pu être démarré.

Divers styles sont disponibles pour personnaliser le choix des navigateurs :

browser-style
La valeur du style est un tableau donnant les préférences par ordre décroissant pour le type de navigateur à utiliser. Les valeurs des éléments peuvent être :
running
Utiliser un navigateur graphique déjà en cours d'exécution lorsqu'un écran X Window est disponible. Les navigateurs listés dans le style x-browsers sont essayés dans l'ordre jusqu'à ce qu'un soit trouvé ; s'il l'est, le fichier sera affiché dans ce navigateur, l'utilisateur pourrait donc avoir besoin de vérifier s'il est apparu. Si aucun navigateur en cours d'exécution n'est trouvé, aucun n'est démarré. Les navigateurs autres que Firefox, Opera et Konqueror sont supposés comprendre la syntaxe Mozilla pour ouvrir une URL à distance.
x
Démarrer un nouveau navigateur graphique lorsqu'un écran X Window est disponible. Rechercher la disponibilité de l'un des navigateurs listés dans le style x-browsers et démarrer le premier qui est trouvé. Aucune vérification n'est effectuée pour un navigateur déjà en cours d'exécution.
tty
Démarrer un navigateur basé sur terminal. Rechercher la disponibilité de l'un des navigateurs listés dans le style tty-browsers et démarrer le premier qui est trouvé.

Si le style n'est pas défini, le défaut running x tty est utilisé.

x-browsers
Un tableau par ordre de préférence décroissant des navigateurs à utiliser lorsqu'on s'exécute sous le système X Window. Le tableau se compose du nom de la commande sous laquelle démarrer le navigateur. Ils sont recherchés dans le contexte :mime: (qui pourrait être étendu à l'avenir, donc ajouter `*' est recommandé). Par exemple,
zstyle ':mime:*' x-browsers opera konqueror firefox

spécifie que pick-web-browser doit d'abord rechercher une instance en cours d'exécution d'Opera, Konqueror ou Firefox, dans cet ordre, et s'il ne parvient à en trouver aucune, il tentera de démarrer Opera. Le défaut est firefox mozilla netscape opera konqueror.

tty-browsers
Un tableau similaire à x-browsers, sauf qu'il donne les navigateurs à utiliser lorsqu'aucun écran X Window n'est disponible. Le défaut est elinks links lynx.
command
S'il est défini, ce style est utilisé pour choisir la commande utilisée pour ouvrir une page pour un navigateur. Le contexte est :mime:browser:new:$browser: pour démarrer un nouveau navigateur ou :mime:browser:running:$browser: pour ouvrir une URL dans un navigateur déjà en cours d'exécution sur l'affichage X actuel, où $browser est la valeur correspondante dans le style x-browsers ou tty-browsers. La séquence d'échappement %b dans la valeur du style sera remplacée par le navigateur, tandis que %u sera remplacé par l'URL. Si le style n'est pas défini, le défaut pour toutes les nouvelles instances est équivalent à %b %u et les défauts pour l'utilisation des navigateurs en cours d'exécution sont équivalents à
o les valeurs kfmclient openURL %u pour Konqueror, firefox -new-tab %u pour Firefox, opera -newpage %u pour Opera, et %b -remote "openUrl(%u)" pour tous les autres.

FONCTIONS MATHÉMATIQUES

zcalc [ -erf ] [ expression ... ]
Un calculateur raisonnablement puissant basé sur la facilité d'évaluation arithmétique de zsh. La syntaxe est similaire à celle des formules dans la plupart des langages de programmation ; voir la section « Évaluation arithmétique » dans zshmisc(1) pour les détails.

Les non-programmeurs doivent noter que, comme dans de nombreux autres langages de programmation, les expressions impliquant uniquement des entiers (qu'il s'agisse de constantes sans « . », de variables contenant de telles constantes sous forme de chaînes, ou de variables déclarées comme étant des entiers) sont évaluées par défaut en utilisant l'arithmétique entière, ce qui n'est pas la façon dont fonctionne un calculateur de bureau ordinaire. Pour forcer l'opération en virgule flottante, passez l'option -f ; voir les notes supplémentaires ci-dessous.

Si le fichier ~/.zcalcrc existe, il sera sourcé à l'intérieur de la fonction une fois qu'elle sera configurée et sur le point de traiter la ligne de commande. Ceci peut être utilisé, par exemple, pour définir des options de shell ; emulate -L zsh et setopt extendedglob sont en vigueur à ce moment. Tout échec de sourcing du fichier s'il existe est traité comme fatal. Comme avec d'autres fichiers d'initialisation, le répertoire $ZDOTDIR est utilisé à la place de $HOME s'il est défini.

La bibliothèque mathématique zsh/mathfunc sera chargée si elle est disponible ; voir la section « Le Module zsh/mathfunc » dans zshmodules(1). Les fonctions mathématiques correspondent aux bibliothèques système brutes, de sorte que les fonctions trigonométriques sont évaluées en radians, etc.

Chaque ligne tapée est évaluée comme une expression. L'invite affiche un numéro, qui correspond à un paramètre positionnel où le résultat de ce calcul est stocké. Par exemple, le résultat du calcul sur la ligne précédée de `4> ' est disponible sous le nom $4. La dernière valeur calculée est disponible sous le nom ans. L'édition complète de ligne de commande, y compris l'historique des calculs précédents, est disponible ; l'historique est sauvegardé dans le fichier ~/.zcalc_history. Pour sortir, entrez une ligne vide ou tapez `:q` seul (`q` est autorisé pour des raisons de compatibilité historique).

Une ligne se terminant par une seule barre oblique inverse est traitée de la même manière qu'en édition de ligne de commande : la barre oblique inverse est supprimée, la fonction demande davantage d'entrée (l'invite est précédée de `...' pour l'indiquer), et les lignes sont combinées en une pour obtenir le résultat final. De plus, si l'entrée contient plus de parenthèses ouvertes que fermées, zcalc demandera davantage d'entrée.

Si des arguments sont donnés à zcalc au démarrage, ils sont utilisés pour amorcer les premiers paramètres positionnels. Une indication visuelle de ceci est donnée au démarrage du calculateur.

Les constantes PI (3.14159...) et E (2.71828...) sont fournies. L'affectation de paramètres est possible, mais notez que tous les paramètres seront placés dans l'espace de noms global sauf si la commande spéciale :local est utilisée. La fonction crée des variables locales dont les noms commencent par _, donc les utilisateurs devraient éviter de le faire. Les variables ans (la dernière réponse) et stack (la pile en mode RPN) peuvent être référencées directement ; stack est un tableau mais ses éléments sont numériques. Divers autres variables spéciales sont utilisées localement avec leur signification standard, par exemple compcontext, match, mbegin, mend, psvar.

La base de sortie peut être initialisée en passant l'option `-#base', par exemple `zcalc -#16' (le `#' peut devoir être cité, selon les options de globbing définies).

Si l'option `-e' est définie, la fonction s'exécute de manière non interactive : les arguments sont traités comme des expressions à évaluer comme s'ils étaient entrés interactivement ligne par ligne.

Si l'option `-f' est définie, tous les nombres sont traités comme des nombres à virgule flottante, donc par exemple l'expression `3/4' s'évalue à 0.75 plutôt qu'à 0. Les options doivent apparaître comme des mots séparés.

Si l'option `-r' est définie, le mode RPN (Notations Polonaise Inverse) est activé. Ceci a diverses propriétés supplémentaires :

Pile
Les valeurs évaluées sont maintenues dans une pile ; celle-ci est contenue dans un tableau nommé stack, la valeur la plus récente étant dans ${stack[1]}.
Opérateurs et fonctions
Si la ligne entrée correspond à un opérateur (+, -, *, /, **, ^, | ou &) ou à une fonction fournie par la bibliothèque zsh/mathfunc, l'élément ou les éléments du bas de la pile sont dépilés pour être utilisés comme argument ou arguments. Les éléments supérieurs de la pile (les moins récents) sont utilisés comme arguments précédents. Le résultat est ensuite empilé dans ${stack[1]}.
Expressions
Les autres expressions sont évaluées normalement, imprimées, et ajoutées à la pile en tant que valeurs numériques. La syntaxe dans les expressions sur une ligne unique est l'arithmétique normale du shell (pas RPN).
Affichage de la pile
Si un entier suit l'option -r sans espace, alors à chaque évaluation, autant d'éléments de la pile, si disponibles, sont imprimés au lieu de seulement le résultat le plus récent. Ainsi, par exemple, zcalc -r4 affiche $stack[4] à $stack[1] à chaque fois que des résultats sont imprimés.
Duplication : =
Le pseudo-opérateur = provoque la duplication de l'élément le plus récent de la pile sur celle-ci.
pop
La pseudo-fonction pop provoque le dépilage de l'élément le plus récent de la pile. Un `>' seul a le même effet.
>ident
L'expression > suivie (sans espace) d'un identifiant de shell provoque le dépilage de l'élément le plus récent de la pile et son affectation à la variable de ce nom. La variable est locale à la fonction zcalc.
<ident
L'expression < suivie (sans espace) d'un identifiant de shell provoque l'empilement de la valeur de la variable de ce nom sur la pile. ident peut être un entier, dans ce cas le résultat précédent avec ce numéro (tel qu'affiché avant le > dans l'invite standard zcalc) est mis sur la pile.
Échange : xy
La pseudo-fonction xy provoque l'échange des deux éléments les plus récents de la pile. `<>' a le même effet.

L'invite est configurable via le paramètre ZCALCPROMPT, qui subit l'expansion d'invite standard. L'indice de l'entrée actuelle est stocké localement dans le premier élément du tableau psvar, qui peut être référencé dans ZCALCPROMPT comme `%1v'. L'invite par défaut est `%1v> '.

La variable ZCALC_ACTIVE est définie dans la fonction et peut être testée par des fonctions imbriquées ; elle a la valeur rpn si le mode RPN est actif, sinon 1.

Quelques commandes spéciales sont disponibles ; elles sont introduites par un deux-points. Pour des raisons de compatibilité ascendante, les deux-points peuvent être omis pour certaines commandes. La complétion est disponible si compinit a été exécuté.

La précision de sortie peut être spécifiée dans zcalc par des commandes spéciales familières de nombreux calculateurs.

:norm
Le format de sortie par défaut. Il correspond à la spécification %g de printf. Typiquement, cela affiche six chiffres décimaux.
:sci chiffres
Notation scientifique, correspondant au format de sortie %g de printf avec la précision donnée par chiffres. Ceci produit soit une notation à virgule fixe, soit une notation exponentielle selon la valeur de sortie.
:fix chiffres
Notation à virgule fixe, correspondant au format de sortie %f de printf avec la précision donnée par chiffres.
:eng chiffres
Notation exponentielle, correspondant au format de sortie %E de printf avec la précision donnée par chiffres.
:raw
Sortie brute : c'est la forme par défaut de la sortie d'une évaluation mathématique. Ceci peut afficher plus de précision que le nombre n'en possède réellement.

zargs [ option ... -- ] [ entrée ... ] [ -- commande [ arg ... ] ]
Cette fonction a un but similaire à GNU xargs. Au lieu de lire des lignes d'arguments depuis l'entrée standard, elle les prend sur la ligne de commande. Ceci est utile car zsh, en particulier avec les opérateurs globaux récursifs, peut souvent construire une ligne de commande pour une fonction shell qui est plus longue que ce qu'une commande externe peut accepter.

La liste option représente les options de la commande zargs elle-même, qui sont les mêmes que celles de xargs. La liste entrée est la collection de chaînes (souvent des noms de fichiers) qui deviennent les arguments de la commande, analogue à l'entrée standard de xargs. Enfin, la liste arg se compose de ces arguments (généralement des options) qui sont passés à la commande à chaque fois qu'elle s'exécute. La liste arg précède les éléments de la liste entrée lors de chaque exécution. Si aucune commande n'est fournie, alors aucune liste arg ne peut être fournie, et dans ce cas, la commande par défaut est `print' avec les arguments `-r --'.

Par exemple, pour obtenir une longue liste ls de tous les fichiers plats non cachés dans le répertoire courant ou ses sous-répertoires :

autoload -U zargs
zargs -- **/*(.) -- ls -ld --

La première et la troisième occurrence de `--' sont utilisées pour marquer la fin des options pour zargs et ls respectivement afin de se prémunir contre les noms de fichiers commençant par `-', tandis que la seconde est utilisée pour séparer la liste des fichiers de la commande à exécuter (`ls -ld --').

Le premier `--' serait également nécessaire s'il y avait une chance que la liste soit vide, comme dans :

zargs -r -- ./*.back(#qN) -- rm -f

Dans le cas où la chaîne `--' est ou peut être une entrée, l'option -e peut être utilisée pour changer le marqueur de fin d'entrées. Notez que cela ne change pas le marqueur de fin d'options. Par exemple, pour utiliser `..' comme marqueur :

zargs -e.. -- **/*(.) .. ls -ld --

C'est un bon choix dans cet exemple car aucun fichier plat ne peut s'appeler `..', mais le meilleur marqueur de fin dépend des circonstances.

Les options -i, -I, -l, -L et -n diffèrent légèrement de leur utilisation dans xargs. Il n'y a pas de lignes d'entrée que zargs doit compter, donc -l et -L comptent à travers la liste entrée, et -n compte le nombre d'arguments passés à chaque exécution de commande, y compris toute liste arg. De plus, chaque fois que -i ou -I est utilisé, chaque entrée est traitée séparément comme si par `-L 1'.

Pour plus de détails sur les autres options de zargs, consultez la page de manuel de xargs(1) (mais notez la différence de fonction entre zargs et xargs) ou exécutez zargs avec l'option --help.

zmv

The zmv function is used to move or rename files, but it is much more powerful than mv. It uses zsh's powerful pattern matching and substitution capabilities. The basic syntax is:

zmv [options] pattern replacement

The pattern is a glob pattern that matches the files to be renamed. The replacement is a string that specifies how the names should be changed. The pattern matching is done using extendedglob; see zshglob(1) for details.

For example, to rename all files ending in .txt to .bak, you could use:

zmv '*.txt' '$f.bak'

Here, `*.txt' matches all files ending in .txt. The replacement string `$f.bak' uses the variable $f, which expands to the full original filename. The `.bak' part is simply appended.

The pattern can contain parentheses to capture parts of the filename. These captured parts can be referred to in the replacement string using numbered variables, like ${1}, ${2}, etc.

For example, to rename files like `YYYY-MM-DD.txt' to `YYYYMMDD.txt', you could use:

zmv '(*)-(*).txt' '${1}${2}.txt'

This captures the year part into ${1} and the month part into ${2}. The replacement string then concatenates them without the hyphen.

If you use the -w option, the pattern is treated as if it were enclosed in parentheses, so you don't need to explicitly add them. The -W option is similar but also automatically converts any wildcard characters in the replacement string into references to the corresponding captured parts.

The zmv function performs substitutions on filenames. The pattern is always treated as an EXTENDED_GLOB pattern. Any file whose name is not changed by the substitution is simply ignored. Any error (a substitution resulted in an empty string, two substitutions gave the same result, the destination was an existing regular file and -f was not given) causes the entire function to abort without doing anything.

In addition to pattern replacement, the variable $f can be referred to in the second (replacement) argument. This makes it possible to use variable substitution to alter the argument; see examples below.

Options:

-f
Force overwriting of destination files. Not currently passed down to the mv/cp/ln command due to vagaries of implementations (but you can use -o-f to do that).
-i
Interactive: show each line to be executed and ask the user whether to execute it. `Y' or `y' will execute it, anything else will skip it. Note that you just need to type one character.
-n
No execution: print what would happen, but don't do it.
-q
Turn bare glob qualifiers off: now assumed by default, so this has no effect.
-Q
Force bare glob qualifiers on. Don't turn this on unless you are actually using glob qualifiers in a pattern.
-s
Symbolic, passed down to ln; only works with -L.
-v
Verbose: print each command as it's being executed.
-w
Pick out wildcard parts of the pattern, as described above, and implicitly add parentheses for referring to them.
-W
Just like -w, with the addition of turning wildcards in the replacement pattern into sequential ${1} .. ${N} references.
-C
-L
-M
Force cp, ln or mv, respectively, regardless of the name of the function.
-p program
Call program instead of cp, ln or mv. Whatever it does, it should at least understand the form `program -- oldname newname' where oldname and newname are filenames generated by zmv. program will be split into words, so might be e.g. the name of an archive tool plus a copy or rename subcommand.
-P program
As -p program, except that program does not accept a following -- to indicate the end of options. In this case filenames must already be in a sane form for the program in question.
-o optstring
The optstring is split into words and passed down verbatim to the cp, ln or mv command called to perform the work. It should probably begin with a `-'.

Further examples:

zmv -v '(* *)' '${1// /_}'

For any file in the current directory with at least one space in the name, replace every space by an underscore and display the commands executed.

zmv -v '* *' '${f// /_}'

This does exactly the same by referring to the file name stored in $f.

       +':baz'     style2 value2 \
       +':frob'    style3 value3

This defines style1 with value1 for the context :foo:bar as usual, but it also defines style2 with value2 for the context :foo:bar:baz and style3 with value3 for :foo:bar:frob. Any subcontext may be the empty string to re-use the first context unchanged.

Styles

insert-tab
The zed function sets this style in context `:completion:zed:*' to turn off completion when TAB is typed at the beginning of a line. You may override this by setting your own value for this context and style.
pager
The nslookup function looks up this style in the context `:nslookup' to determine the program used to display output that does not fit on a single screen.
prompt
rprompt
The nslookup function looks up this style in the context `:nslookup' to set the prompt and the right-side prompt, respectively. The usual expansions for the PS1 and RPS1 parameters may be used (see EXPANSION OF PROMPT SEQUENCES in zshmisc(1)).
