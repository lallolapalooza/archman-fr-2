NOM

zone2sql - convertir les zones BIND en SQL

SYNOPSIS

zone2sql {--named-conf=CHEMIN,--zone-file=CHEMIN [--zone-name=NOM]} [Options]

DESCRIPTION

zone2sql analyse les fichiers named.conf et les fichiers de zone BIND et génère du SQL sur la sortie standard, qui peut ensuite être alimenté dans votre base de données.

zone2sql comprend l'extension de fichier maître BIND $GENERATE et respecte également $ORIGIN et $TTL.

Pour les backends prenant en charge l'opération secondaire, il existe également une option pour conserver les zones secondaires en tant que telles, et ne pas les convertir en opération native.

zone2sql peut générer du SQL pour les backends Générique MySQL, Générique PostgreSQL, Générique SQLite3.

OPTIONS

OPTIONS D'ENTRÉE

--named-conf=<CHEMIN>
Lit CHEMIN pour obtenir la configuration BIND.
--zone=<CHEMIN>
Analyse uniquement le fichier de zone à CHEMIN. Conflit avec le paramètre --named-conf.
--zone-name=<NOM>
Lors de l'analyse d'une zone unique sans instruction $ORIGIN, définit ZONE comme nom de la zone.

BACKENDS

--gmysql
Génère la sortie dans un format adapté à la configuration par défaut du backend Générique MySQL.
--gpgsql
Génère la sortie dans un format adapté à la configuration par défaut du backend Générique PostgreSQL.
--gsqlite
Génère la sortie dans un format adapté à la configuration par défaut du backend Générique SQLite3.

OPTIONS DE SORTIE

--json-comments
Analyse le JSON dans les commentaires des fichiers de zone pour définir les champs 'disabled' et 'comment' dans la base de données. Voir COMMENTAIRES JSON pour plus d'informations.
--transactions
Si le backend SQL cible prend en charge les transactions, encapsule chaque domaine dans une transaction pour l'intégrité et potentiellement une vitesse accrue.

AUTRES OPTIONS

--delete-matching-domains
Ajoute une instruction de suppression à la sortie SQL pour permettre la réimportation des zones. Principalement utile lors des tests. Étant donné que cela ne supprimera que le domaine, mais pas ses enregistrements, vous devriez avoir la relation de clé étrangère optionnelle activée dans votre schéma afin d'éviter de laisser des enregistrements orphelins.
--filter-duplicate-soa
S'il y a plus d'un enregistrement SOA dans la zone (potentiellement parce qu'elle a été obtenue via AXFR), l'ignorer. Si cette option n'est pas définie, tous les enregistrements SOA de la zone sont émis.
--help
Liste toutes les options.
--on-error-resume-next
Ignore les fichiers de zone manquants lors de l'analyse. Dangereux.
--secondary
Maintient le statut secondaire des zones listées dans named.conf comme étant des esclaves. Le comportement par défaut est de convertir toutes les zones en opération native.
--verbose
Être verbeux pendant la conversion.

COMMENTAIRES JSON

Les backends SQL génériques ont les champs 'comment' et 'disabled' dans la table 'records'. Le champ 'comment' contient un commentaire pour cet enregistrement (le cas échéant) et le champ 'disabled' indique à PowerDNS si l'enregistrement peut être servi aux clients.

Lorsqu'un fichier de zone contient un commentaire comme ; json={"comment": "Quelque chose", "disabled": true} et que --json-comments est fourni, le champ 'comment' contiendra "Quelque chose" et le champ 'disabled' sera défini sur la valeur booléenne vraie native de la base de données.

AVERTISSEMENT : L'utilisation de commentaires JSON pour désactiver des enregistrements signifie que la zone dans PowerDNS est différente de celle servie par BIND, car BIND ne gère pas le statut désactivé dans le commentaire.
